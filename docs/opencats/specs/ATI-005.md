**Ticket type:** Test
**Priority:** P2
**Estimate:** 1 day
**Source:** `docs/opencats/ATS_INTEGRATION_TICKETS.md` §ATI-005
**Flags:** All parent flags (toggled per case). No new top-level flag introduced.

---

## 1. Summary & Goal

ATI-001 through ATI-004 each ship their own hermetic unit tests and an E2E section.
ATI-005 adds the **cross-ticket integration and flag-matrix** layer that no single ticket owns:
it verifies that the four thin ATS extensions compose correctly through their shared DynamoDB
tables, that every new surface degrades gracefully to the pre-ATI baseline when its parent flag
is off, and that the additive Pydantic model fields serialise safely for legacy rows that
predate ATI.

The result is a single offline pytest module, `tests/test_ati_005_integration.py`, covering
three distinct axes:

1. **End-to-end thread (flags on):** a recruiter creates an org account with ATS-specific
   fields (ATI-001), seeds and runs two recruiting reports (ATI-002), calls the combined
   log-and-schedule action against a candidate (ATI-003), and searches for that candidate and
   a job order (ATI-004); shared DynamoDB state is observed across all four modules.

2. **Flag matrix (flags off):** for each of the seven parent flags, toggled off in isolation,
   every ATI surface returns the correct inert response — 503, 404, `HTTPException(400)` for
   invalid search type, or `None`/`[]`/`False` defaults — and performs zero writes to its
   backing table.

3. **Additive-projection regression:** `EventOut`, `CrmOrgAccountOut`, and `CrmPartyOut`
   serialise the new optional fields as `null`, `[]`, or `False` for rows written before ATI.

No new production code is shipped by this ticket. All code additions are test infrastructure
(test helpers, moto table factories, `object.__setattr__` frozen-handle patching) that live
entirely under `tests/`.

### 2.2 Hermetic test pattern used across this repo

Every recent regression test in this repo follows the same three-part isolation recipe,
illustrated at `tests/test_gap_0265_0266_kyc_risk_scoring.py:1–28`:

1. **Moto in-process DynamoDB** — `@mock_aws` context manager provides a real in-memory DDB
   endpoint; each table is created with `ddb.create_table(...)` before the test body runs.
2. **Frozen handle injection** — the live singleton `T` (a `frozen=True` dataclass declared at
   `app/core/tables.py:68`) is mutated via `object.__setattr__(T, "handle_name", moto_table)`.
   The same technique patches `S` settings flags. Both are restored on teardown.
3. **Direct handler invocation** — async route handlers are driven on a fresh
   `asyncio.new_event_loop()` via `loop.run_until_complete(handler(...))` with dependency
   arguments built manually (no FastAPI `TestClient`, which is broken in this repo).

ATI-005 follows this recipe verbatim. The cross-ticket integration test creates **one shared
moto context** covering all tables needed by all four ATI modules; no separate mock context
per module.

## 5. Detailed Behavior & Edge Cases

### 5.1 End-to-end thread (all flags on)

The integration thread is a single `unittest.TestCase.test_full_ats_thread` method that
exercises all four ATI deltas sequentially against one shared moto DynamoDB context:

1. **Seed entities.** Write a PARTY_GROUP META row (org account) and a PERSON META row
   (contact) directly to the moto `party` table. Write a candidate item to the moto
   `candidates` table and a job-order item to the moto `job_orders` table.
   [CORRECTED: DDB table names are `"candidates"` and `"job_orders"` per CND-001/JOB-001, not `"ats_candidates"`/`"ats_job_orders"`.]

2. **ATI-001 — org PATCH.** Call `update_org_account(org_id, actor_id, fields={"key_technologies": ["Python", "AWS"], "fein": "12-3456789"})`.
   Assert the moto `party` table item now carries `key_technologies=["aws", "python"]`
   (deduped + lower-trimmed) and `fein="12-3456789"`. Assert `audit_event` row written
   to moto `alerts` table with `event="party_org_account_updated"`.

3. **ATI-002 — report seed + run.** Call `seed_recruiting_reports(owner_sub="recruiter_1")`.
   Assert exactly five META rows written to moto `crm_reports`. Call
   `run_report(pipeline_breakdown_report_id, "recruiter_1")` — seeded pipeline items carry
   statuses `["new", "submitted", "placed"]`; assert grouped output has three rows, each
   with `status` and `count`. Call `run_report(candidates_by_source_report_id, "recruiter_1")`
   — seeded candidates carry sources `["website", "referral"]`; assert two group rows.
   Second call to `seed_recruiting_reports` must not create additional rows (conditional
   put idempotency).

4. **ATI-003 — log-and-schedule.** Call `log_and_schedule(entity_type="candidate", entity_id=<candidate_id>, body=CrmLogAndScheduleIn(activity_type="call", summary="Initial screen", next_event=EventCreateIn(...)))`.
   Assert one row written to moto `crm_activity_timeline` with matching `entity_key`.
   Assert one event item written to moto `calendar` with `linked_entity_type="candidate"`.
   Assert one pointer item written to moto `calendar` with
   `calendar_id="ENTITY#candidate#<candidate_id>"`. Call `get_events_by_entity("candidate", <candidate_id>)`;
   assert the returned `EventOut` list contains the scheduled event.

5. **ATI-004 — global search.** Call `_search_candidates("python", "recruiter_1", 10)`;
   assert the seeded candidate appears in `items` with `type="candidate"` and a resolvable
   `/ats/candidates/...` URL. Call `_search_job_orders("senior engineer", "recruiter_1", 10)`;
   assert the seeded job order appears. Assert both results carry the
   `{"items", "total_estimate", "has_more"}` shape from `_make_result_item`
   (`search.py:64–85`).

6. **Cross-module state check.** Assert the moto `party` table has not been written to by
   any ATI-002/003/004 code path (isolation test: module boundaries are respected).

### 5.3 Additive-projection regression

Three `unittest.TestCase` methods covering "legacy row → new field defaults":

**`test_legacy_event_out_fields`** — create a `calendar` table item that predates ATI-003
(no `linked_entity_type`, no `linked_entity_id` attributes). Call the `_event_out` serialiser
(`app/routers/calendar.py:979`). Assert the resulting `EventOut` carries `linked_entity_type=None`
and `linked_entity_id=None` (Pydantic default), not a `KeyError` or `ValidationError`.

**`test_legacy_org_account_out_fields`** — create a `party` table item representing a
PARTY_GROUP META row that predates ATI-001 (no `key_technologies`, `fein`, or
`billing_contact_party_id` attributes). Call the `_item_to_org_account_out` projection
(delivered by CCT-001). Assert `key_technologies=[]`, `fein=None`,
`billing_contact_party_id=None`.

**`test_legacy_party_out_fields`** — create a `party` table item representing a PERSON META
row that predates ATI-001 (no `title` or `is_hot` attributes). Call the `_item_to_party_out`
projection (delivered by CCT-003, extended by ATI-001). Assert `title=None`, `is_hot=False`.

These three tests are the regression fence: they confirm that any existing API consumer that
GETs an old record without the new fields will not see a 500 or a missing-key error, only
safe defaults.

### 5.4 Edge cases explicitly covered

- **Re-seeding reports is idempotent.** `seed_recruiting_reports` uses a `ConditionExpression="attribute_not_exists(report_id)"` conditional put (matching the RPT-002 conditional-put pattern). A second call to `seed_recruiting_reports` with the same `owner_sub` must leave the `crm_reports` item count unchanged and not raise a `ConditionalCheckFailedException` (the exception must be caught and swallowed in the seeder).
- **Partial flag-off does not bleed.** [CORRECTED] ATI-003 §5.7 confirms that `_gate_activities()` checks `if not (S.crm_activities_enabled and S.crm_activity_timeline_enabled)` — both flags are ANDed. When either flag is off, the `log-and-schedule` handler raises `HTTPException(404)` before any write occurs. The original claim that "log-and-schedule returns `event_created: true, activity_id: null` when only `CRM_ACTIVITY_TIMELINE_ENABLED=False`" is incorrect: the gate fires before `activity_id = uuid.uuid4().hex` is reached, so neither `activity_id` nor a calendar event is produced. The flag-matrix test for `crm_activity_timeline_enabled=False` must assert `HTTPException(404)` and zero writes to both tables — not partial success.
- **`billing_contact_party_id` referencing non-existent party.** The integration thread does NOT test this case (it is covered by `test_ati_001_ats_field_gaps.py`); the flag-matrix test for `party_org` off does not need it either. ATI-005 explicitly delegates validation-error cases to the per-ticket tests.
- **Decimal safety in report aggregates.** The pipeline-breakdown report uses COUNT (no arithmetic on Decimal values). The placements report uses SUM on `fee_cents` (Decimal). ATI-005 seeds one "placed" pipeline item carrying `fee_cents=Decimal("5000")` and asserts the SUM aggregate returns `5000` (integer), not `Decimal("5000")` — exercising the Decimal-safe coercion in `_apply_group_by` (RPT-003 §2.2).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

Since ATI-005 ships no production code, SECOPS-007 parity applies to the test scaffolding
rather than to application logic. The following constraints govern the test module:

**No `dev_mode` branches in test setup.** The moto table factories replicate the exact
same table schemas (key names, GSI definitions, `attr_types`) that the production
`scripts/local-ddb-init.py` uses. There is no test-only schema simplification. A schema
mismatch that causes `ValidationException` in the test would also occur in production.

**No real AWS calls.** The `@mock_aws` (moto) context intercepts all boto3 calls at the
botocore layer. The test module must not import or reference any real AWS endpoint. The
`T.*` handles are rebound to moto-backed table objects before any service function is
called; the originals are never invoked.

**Idempotency of `seed_recruiting_reports`.** The seeder must use conditional-put semantics
(pre-existing RPT-002 pattern) so a second call in any environment — dev, staging, prod —
does not overwrite manually customised report definitions. ATI-005 asserts this behavour.

**`audit_event` observability without side-effects.** The integration test binds a moto
`alerts` table so `audit_event` writes succeed without hitting real AWS SES/SNS. This is
the same pattern used by `tests/test_gap_0265_0266_kyc_risk_scoring.py` and confirmed at
`app/services/alerts.py:644` where the function writes only to `T.alerts` before any
downstream notification path.

**No network calls.** `_search_candidates` and `_search_job_orders` are pure DynamoDB
functions; no external search service is called. The test drives them by calling the
functions directly (not the HTTP handler) and supplying a pre-populated moto table.

## 8. Backward Compatibility & Migration

ATI-005 is test-only and introduces no schema changes, no new DynamoDB tables, no new
settings, and no new Pydantic models. There is no migration to perform and no backward
