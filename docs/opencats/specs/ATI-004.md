# ATI-004 — Candidate + job-order branches in global search

**Type:** Feature | **Priority:** P2 | **Estimate:** 1d
**Cluster:** ATS Integration (ATI) — thin extension of `app/routers/search.py`
**Source:** `docs/opencats/ATS_INTEGRATION_TICKETS.md` §ATI-004

---

## 1. Summary & Goal

ATI-004 wires two new domain branches — `candidates` and `job_orders` — into the existing
`global_search` fan-out in `app/routers/search.py`. It is the thinnest possible change: two
new per-module functions (`_search_candidates`, `_search_job_orders`) following the exact
contract of the nine already-registered branches, plus three-line dispatch-table registrations
inside `_search_aggregator`. No new endpoint, no new DynamoDB table, no new Pydantic model.

The goal is that a recruiter typing a name or job title in the platform's global search bar
immediately surfaces both candidates they own and job orders they are assigned to, alongside
the results from existing domains (messages, tickets, contacts, etc.), without disrupting any
existing search path.

### 2.1 `ALLOWED_TYPES` and the `_EXTENDED_SEARCH` gate

`app/routers/search.py` (hereafter `search.py`) builds the type allow-set at module

- Validation guard (line 856): `invalid = set(requested_types) - ALLOWED_TYPES` → 400 if

Because `ALLOWED_TYPES` is built at import time from an `os.environ.get`, adding new types to

### 2.2 `_search_aggregator` dispatch

`_search_aggregator(q, user_id, types, limit)` (search.py:645) builds a `search_fns` dict
and fans out in parallel:

```python
# search.py:655-693  (abridged)

if "users" in types:    search_fns["users"]    = lambda: _search_users(q, user_id, limit)
if "messages" in types: search_fns["messages"] = lambda: _search_messages(q, user_id, limit)

max_workers = min(len(search_fns), 8) if search_fns else 1
with ThreadPoolExecutor(max_workers=max_workers) as executor:
    futures = {executor.submit(fn): name for name, fn in search_fns.items()}
    for future in as_completed(futures, timeout=5):
        name = futures[future]
        try:
            results[name] = future.result(timeout=2)
        except Exception:
            results[name] = _empty_section()
            partial = True
# Fill-in loop writes _empty_section() for every type in ALLOWED_TYPES not yet in results
for t in ALLOWED_TYPES:
    if t not in results:
        results[t] = _empty_section()
return {"results": results, "partial": partial}
```

Key properties that ATI-004 inherits unchanged:
- Per-branch 2-second timeout; overall 5-second timeout (line 679/682).
- Failed/timed-out branch yields `_empty_section()` + `partial=True` (line 685-686).
- Fill-in loop (line 689-691) produces an empty section for every `ALLOWED_TYPES` member not
  explicitly searched — so an `if "candidates" in types:` guard is sufficient; the fill-in
  handles the "not requested" case.
- `max_workers = min(len(search_fns), 8)` caps the thread pool; adding two more branches
  raises the cap from 9 to 11 but the `min(n, 8)` hard cap means no thread-pool growth
  until the total exceeds 8 concurrent branches, which is already true today with 9 modules.
  The cap stays at 8 — no change needed.

### 2.5 ATS entity tables and GSIs (CND-001 / JOB-001 — hard dependencies)

The candidate and job-order tables are **owned and defined by the CND and JOB clusters
respectively**. ATI-004 only reads them.

**Candidate table** (`T.candidates`, `CND-001` §3):
- Table: `candidates` (`pk`, `sk`).
- `ByOwner` GSI: `GSI1PK = "OWNER#{owner_sub}"` (S), `GSI1SK = created_at` (N, numeric).
- `ByStatus` GSI: `GSI2PK = "STATUS#{status}"` (S), `GSI2SK = created_at` (N, numeric).
- Candidate META rows have `sk = "META"`, fields: `candidate_id`, `first_name`, `last_name`,
  `email`, `title` (current job title), `key_skills` (free-text blob), `owner_sub`, `status`.
- `attr_types={"GSI1SK":"N","GSI2SK":"N","GSI3SK":"N"}` (CND-001 §3.4). Note: `"created_at":"N"` is NOT included — `created_at` is a plain item attribute, not a GSI key schema attribute name (the aliases `GSI1SK`/`GSI2SK`/`GSI3SK` are). Including a non-key attribute in `attr_types` causes DynamoDB to raise `ValidationException: Number of attributes in KeySchema does not exactly match number of attributes defined in AttributeDefinitions` (CND-001 §3.4 explains this explicitly).

**Job-order table** (`T.job_orders`, `JOB-001` §JOB-001):
- Table: `job_orders` (`pk`, `sk`).
- `GSI_BY_RECRUITER` GSI: `recruiter_sub` (S) → `created_at` (N, numeric).
- `GSI_BY_STATUS` GSI: `status` (S) → `created_at` (N, numeric).
- `GSI_DIRECT` GSI: `job_id` (S) — direct-lookup by `job_id`.
- Job order META rows: `pk = "COMPANY#{client_company_id}"`, `sk = "JOB#{job_id}"`, fields:
  `job_id`, `title`, `client_company_id`, `status`, `description`, `city`, `state`,
  `recruiter_subs` (List[str]), `created_at`.
- Recruiter index rows: `pk = "COMPANY#{client_company_id}"`,
  `sk = "RECRUITER#{sub}#JOB#{job_id}"` — indexed under `GSI_BY_RECRUITER`.
- `attr_types={"created_at":"N","updated_at":"N"}` (JOB-001 §JOB-001).

## 3. Data Model

ATI-004 introduces **no new DynamoDB tables, GSIs, or attributes**. It is read-only against
two tables owned by the CND and JOB clusters:

### 3.1 `T.candidates` access pattern

`_search_candidates` performs two DynamoDB operations in sequence:

1. **GSI query** — `T.candidates.query(IndexName="ByOwner", KeyConditionExpression=
   Key("GSI1PK").eq(f"OWNER#{user_id}"), Limit=limit * 4, ScanIndexForward=False)` — returns
   candidates owned by the requesting recruiter, newest first. Using `limit * 4` as the DDB
   `Limit` pre-filter cap (mirroring `_search_tickets`'s inner `Limit=200`) because DynamoDB
   applies `FilterExpression` AFTER consuming the `Limit` quota (CLAUDE.md "DDB
   FilterExpression doesn't reduce page size"). A multiplier of 4× the requested `limit`
   provides enough candidates to survive the token-match filter for typical queries.

2. **Token-match filter** applied client-side over the returned items. This avoids a full-table
   scan and keeps the operation owner-scoped. The haystack per item is:

   ```
   " ".join([first_name, last_name, email, title or "", key_skills or ""])
   ```

   all lowercased. The query token list is produced by the same regex already used by
   `_search_tickets` and `_search_contacts`:

   ```python
   tokens = [t for t in re.findall(r"[a-z0-9@._-]+", q.lower()) if t]
   ```

   Match requires all tokens to appear in the haystack (`all(tok in haystack for tok in
   tokens)`).

### 3.2 `T.job_orders` access pattern

`_search_job_orders` queries the `GSI_BY_RECRUITER` index to scope results to job orders
where the requester is a listed recruiter. Because `recruiter_subs` is a list attribute (not
a scalar), the service (JOB-002) writes one sparse per-recruiter index row per recruiter sub
(row: `pk="COMPANY#{client_company_id}"`, `sk="RECRUITER#{sub}#JOB#{job_id}"`, carrying
`recruiter_sub`, `created_at`, `job_id` as projected attributes). ATI-004 queries:

```python
T.job_orders.query(
    IndexName="GSI_BY_RECRUITER",
    KeyConditionExpression=Key("recruiter_sub").eq(user_id),
    Limit=limit * 4,
    ScanIndexForward=False,
)
```

Each returned index row carries a projected `job_id`. To resolve the full job title and
description for snippet generation, ATI-004 calls `T.job_orders.get_item` on the META row
(`pk="COMPANY#{client_company_id}"`, `sk="JOB#{job_id}"`) for each index row — capped to
`limit` items after deduplication. Token-match haystack per job order:

```
" ".join([title, client_company_id, description or "", city or "", state or ""])
```

all lowercased; same `all(tok in haystack)` predicate.

### 3.3 No new `TableDef`, `T.*` fields, or `attr_types`

No changes to `scripts/local-ddb-init.py`, `app/core/tables.py`, or `app/core/settings.py`
beyond the `ALLOWED_TYPES` extension at module scope in `search.py`. The numeric GSI sort
keys (`GSI1SK` on `candidates`, `created_at` on `job_orders`) are already declared with
`attr_types` by their owning tickets — ATI-004 takes them as given.

## 4. API / Service Design

### 4.1 New private functions in `app/routers/search.py`

#### `_search_candidates`

```python
def _search_candidates(q: str, user_id: str, limit: int) -> Dict[str, Any]:
    """Search candidates owned by the requesting recruiter.

    Owner-scoped via the ByOwner GSI (OWNER#{user_id}). Token-match against
    name, email, current job title, and key_skills free-text blob.
    Returns standard section shape {items, total_estimate, has_more}.
    """
    try:
        from app.core.tables import T  # already imported at module level; local import
                                       # avoids circular dep if CND tables added later
        tokens = [t for t in re.findall(r"[a-z0-9@._-]+", q.lower()) if t]
        if not tokens:
            return _empty_section()

        resp = T.candidates.query(
            IndexName="ByOwner",
            KeyConditionExpression=Key("GSI1PK").eq(f"OWNER#{user_id}"),
            FilterExpression="sk = :meta",
            ExpressionAttributeValues={":meta": "META"},
            Limit=min(limit * 4, 200),
            ScanIndexForward=False,
        )
        matches: List[Dict[str, Any]] = []
        for item in resp.get("Items", []):
            first = str(item.get("first_name", ""))
            last  = str(item.get("last_name", ""))
            haystack = " ".join([
                first, last,
                str(item.get("email", "")).lower(),
                str(item.get("title", "") or "").lower(),
                str(item.get("key_skills", "") or "").lower(),
            ]).lower()
            if not all(tok in haystack for tok in tokens):
                continue
            candidate_id = item.get("candidate_id", "")
            matches.append(_make_result_item(
                type="candidate",
                id=candidate_id,
                title=f"{first} {last}".strip(),
                snippet=str(item.get("title") or item.get("status", ""))[:120],
                url=f"/ats/candidates/{candidate_id}",
                meta={
                    "status": item.get("status", ""),
                    "owner_sub": item.get("owner_sub", ""),
                    "email": item.get("email", ""),
                },
            ))
            if len(matches) >= limit:
                break

        has_more = len(matches) >= limit
        return {"items": matches[:limit], "total_estimate": len(matches), "has_more": has_more}
    except Exception:
        logger.exception("Candidate search failed")
        return _empty_section()
```

#### `_search_job_orders`

```python
def _search_job_orders(q: str, user_id: str, limit: int) -> Dict[str, Any]:
    """Search job orders where the requester is a listed recruiter.

    Queries GSI_BY_RECRUITER for index rows scoped to user_id, resolves each
    META row via get_item, token-matches title/client/description.
    Returns standard section shape {items, total_estimate, has_more}.
    """
    try:
        from app.core.tables import T
        tokens = [t for t in re.findall(r"[a-z0-9@._-]+", q.lower()) if t]
        if not tokens:
            return _empty_section()

        idx_resp = T.job_orders.query(
            IndexName="GSI_BY_RECRUITER",
            KeyConditionExpression=Key("recruiter_sub").eq(user_id),
            Limit=min(limit * 4, 200),
            ScanIndexForward=False,
        )
        seen_job_ids: set = set()
        matches: List[Dict[str, Any]] = []

        for idx_row in idx_resp.get("Items", []):
            job_id = idx_row.get("job_id", "")
            if not job_id or job_id in seen_job_ids:
                continue
            seen_job_ids.add(job_id)

            # Resolve META row for full fields
            company_id = idx_row.get("client_company_id", "") or idx_row.get("pk", "").lstrip("COMPANY#")
            meta = T.job_orders.get_item(
                Key={"pk": f"COMPANY#{company_id}", "sk": f"JOB#{job_id}"}
            ).get("Item")
            if not meta:
                # Fallback: query GSI_DIRECT for job_id (handles multi-company edge case)
                dr = T.job_orders.query(
                    IndexName="GSI_DIRECT",
                    KeyConditionExpression=Key("job_id").eq(job_id),
                    Limit=1,
                )
                items = dr.get("Items", [])
                if not items:
                    continue
                meta = items[0]

            haystack = " ".join([
                str(meta.get("title", "")).lower(),
                str(meta.get("client_company_id", "")).lower(),
                str(meta.get("description", "") or "").lower(),
                str(meta.get("city", "") or "").lower(),
                str(meta.get("state", "") or "").lower(),
            ])
            if not all(tok in haystack for tok in tokens):
                continue

            status = meta.get("status", "")
            city   = meta.get("city")
            state  = meta.get("state")
            location = ", ".join(filter(None, [city, state]))
            snippet = location or status

            matches.append(_make_result_item(
                type="job_order",
                id=job_id,
                title=str(meta.get("title", "")),
                snippet=snippet[:120],
                url=f"/ats/job-orders/{job_id}",
                meta={
                    "status": status,
                    "client_company_id": meta.get("client_company_id", ""),
                    "openings": int(meta.get("openings", 0) or 0),
                    "placed_count": int(meta.get("placed_count", 0) or 0),
                },
            ))
            if len(matches) >= limit:
                break

        has_more = len(matches) >= limit
        return {"items": matches[:limit], "total_estimate": len(matches), "has_more": has_more}
    except Exception:
        logger.exception("Job order search failed")
        return _empty_section()
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off is zero code path

When `S.candidates_enabled = False`, `"candidates"` is never added to `ALLOWED_TYPES`.
Requesting `types=candidates` returns `HTTPException(400, "Invalid search types: candidates")`
via the existing guard at search.py:856-858 — no new code path for the flag-off case. The
fill-in loop at search.py:689-691 also excludes `candidates` (since it iterates `ALLOWED_TYPES`
only). Byte-for-byte identical to pre-ATI behaviour. Same for `job_orders`.

### 5.2 `ALLOWED_TYPES` default `types` parameter

`Query(default=",".join(sorted(ALLOWED_TYPES)))` is evaluated once at module import time
(FastAPI Query default values are resolved eagerly on first handler invocation but fixed to the
value at definition time for default strings). Because `ALLOWED_TYPES` is mutated before the
router is registered in `app/main.py`, the default string will include `"candidates"` and/or
`"job_orders"` if the flags are on at startup. This is the same mechanism that currently
includes `"calendar"` when `_EXTENDED_SEARCH=True`. No special action needed.

### 5.3 Owner-scoping and authorization

`_search_candidates` queries `OWNER#{user_id}` via the `ByOwner` GSI — only returns
candidates where `GSI1PK = "OWNER#{user_id}"`, i.e. candidates this recruiter created or was
assigned as owner. A recruiter never sees another recruiter's candidates; no additional ACL
check is required beyond the GSI partition key.

`_search_job_orders` queries `GSI_BY_RECRUITER` scoped to `user_id` — only returns job
orders where this recruiter appears as a listed recruiter (per the per-recruiter index rows
written by JOB-002). A recruiter does not see job orders they are not assigned to.

Neither function exposes public/hot flagged entities to unauthenticated callers — `global_search`
always requires `require_ui_session` (cookie auth + CSRF, or Bearer JWT for API clients).

### 5.4 `FilterExpression` on `sk = "META"` for candidates

The `ByOwner` GSI indexes **all** candidate table rows under `OWNER#{owner_sub}`, including
both META rows (`sk = "META"`) and any future sub-items (attachments, activity rows). The
`FilterExpression="sk = :meta"` ensures only META rows are returned. Per CLAUDE.md: DDB
applies FilterExpression after consuming `Limit` quota, so setting `Limit=min(limit * 4, 200)`
gives adequate headroom. If a candidate owner has > 200 DDB items (unlikely for the typical
`limit=5-20` call), the query may return fewer results; a paginated loop is not worth the
complexity at this read volume.

### 5.5 `get_item` for job-order META resolution

`_search_job_orders` fires one `get_item` per index row (up to `limit * 4` rows, capped at
200). With `limit = 5` (default) and `4×` factor, worst case is 20 `get_item` calls in the
2-second per-branch timeout. At DynamoDB Local latency (~1 ms/op) this is safe. In prod
(~5-10 ms/op per single-digit-millisecond DDB p99), 20 serial `get_item` calls ≈ 100-200 ms,
well inside the 2-second timeout. If the per-recruiter index row already carries a projected
`job_id` and `client_company_id` (which JOB-002 writes), the `pk` can be reconstructed
directly, avoiding the `GSI_DIRECT` fallback lookup. The fallback is defensive-only.

### 5.6 Empty query tokens

`_sanitize_query` (search.py:52) strips control characters and collapses whitespace before
`_search_aggregator` is called. A query of only punctuation (e.g. `"!!!"`) produces an empty
`tokens` list via `re.findall(r"[a-z0-9@._-]+", q.lower())` — both functions return
`_empty_section()` immediately.

### 5.7 Partial results

If either new branch raises an unhandled exception or exceeds the 2-second timeout (e.g. DDB
cold-start), `_search_aggregator` catches it (search.py:683-686), sets `partial=True`, and
returns `_empty_section()` for that branch. The caller receives a valid response body with
`partial: true` and the other sections intact. This matches the existing behavior for all nine
current branches.

### 5.8 `has_more` semantics

Both functions set `has_more = len(matches) >= limit` before the final `[:limit]` slice. This
is a conservative estimate: `True` if exactly `limit` results were found (there may be more).
This matches the convention used by `_search_calendar` (search.py:631-634). Note: `_search_contacts`
(search.py:507-511) uses `len(matches) > limit` (strict greater than), which returns `False` when
`len(matches) == limit` — a subtle difference. The new functions follow `_search_calendar`'s `>=`
semantics (conservative / inclusive), not `_search_contacts`'s `>` semantics.

### 5.9 `meta` fields for frontend routing

`meta.email` on candidate results exposes the recruiter-owner's email for display. Because
`global_search` is session-auth-only, the caller is always a recruiter who already owns the
record — no PII disclosure beyond what the authenticated user already has access to.

`meta.placed_count` and `meta.openings` on job-order results are denormalized ints, defaulting
to 0 until the PIP (pipeline) cluster ships. `int(meta.get("placed_count", 0) or 0)` guards
against a `None` or absent attribute.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007

Both `_search_candidates` and `_search_job_orders` call `T.candidates` / `T.job_orders` via
the existing `_safe_table`-wrapped handles. In dev, DynamoDB Local at port 8001 serves these
tables. In prod, real DynamoDB serves them. No `if S.dev_mode` branch exists or is needed.
Read operations are side-effect-free; no mock path is required.

### 7.2 Idempotency

Both functions are pure read operations — they do not write to DynamoDB, emit audit events,
or update search history. `record_search_history` (search.py:721) is called by the
`POST /ui/search/history` endpoint (search.py:866), not by `global_search` directly; the
search handler itself does not write history. No idempotency concern.

### 7.3 Rate limiting

The global search rate limit (`_GLOBAL_SEARCH_MAX_PER_WINDOW = 30`, window 60 s, keyed on
`user_id`) at search.py:833-849 applies to the entire `global_search` handler before the
fan-out. Adding two more branches does not change the rate-limit logic; the two new branches
are subject to the same per-user cap as all others.

### 7.4 Authorization

- `require_ui_session` (search.py:829): every call to `global_search` is authenticated. CSRF
  is enforced for cookie-auth non-GET requests; `GET /ui/search` is exempt from CSRF (it is a
  GET verb — confirmed by `app/auth/deps.py` CSRF guard which checks `request.method not in
  ("GET", "HEAD", "OPTIONS")`).
- Owner-scoping inside `_search_candidates` uses `GSI1PK = "OWNER#{user_id}"` — enforced by
  the DynamoDB key condition, not a post-hoc filter. A recruiter cannot observe another
  recruiter's candidate data regardless of what `q` they supply.
- `_search_job_orders` uses `GSI_BY_RECRUITER` keyed on the session `user_id`. Same guarantee.
- Neither function has a public (no-auth) code path. The `API_KEY_ROUTE_EXEMPTIONS` dict
  (`app/services/api_key_route_scope_registry.py:70`) does not list `GET:/ui/search` — no
  change needed. ATI-004 introduces no public-portal endpoint (the career portal and public
  job-board are separate Tier-2 tickets per the gap analysis §D).

### 7.5 Input safety

`q` is sanitized by `_sanitize_query` (strip control chars, normalize Unicode, collapse
whitespace, cap 200 chars) before reaching either function. The `tokens` list is further
filtered to `[a-z0-9@._-]+` tokens — no SQL injection, path injection, or DDB injection
vector (all values are passed as `ExpressionAttributeValues`).

## 8. Backward Compatibility & Migration

### 8.1 Zero impact with flags off

With `CANDIDATES_ENABLED` and `JOB_ORDERS_ENABLED` absent or `"0"`:
- `ALLOWED_TYPES` is not extended; `"candidates"` and `"job_orders"` are absent.
- `GET /ui/search?q=x` with no `types` param returns the same types as before (no ATS types
  in the default).
- `GET /ui/search?q=x&types=candidates` returns 400 `"Invalid search types: candidates"` via
  the existing validation guard (search.py:856-858). No new error shape.
- `_search_candidates` and `_search_job_orders` are defined in the module but never called.
- `T.candidates` and `T.job_orders` handles are available (wired by CND-001/JOB-001) but
  never read. No `ResourceNotFoundException` risk because the tables exist when those tickets
  are merged.

### 8.2 No DynamoDB migration

ATI-004 is read-only. No new rows, no schema changes, no `just restart` requirement specific
to this ticket (a `just restart` is required when CND-001/JOB-001 create their tables, but
that is those tickets' concern).

### 8.3 Frontend: search results panel

The frontend search UI (`frontend/src/pages/` global search component, not specified in this
ticket) will receive new `results.candidates` and `results.job_orders` sections only when the
flags are on. Both sections follow the existing `{items, total_estimate, has_more}` shape;
the frontend need only register the new `type` values (`"candidate"`, `"job_order"`) in its
result renderer. This is additive and does not break existing rendering of other sections.
Frontend wiring is the responsibility of CND-006 / the JOB frontend ticket.

### 8.4 `ALLOWED_TYPES` fill-in loop

The fill-in loop at search.py:689-691 iterates `ALLOWED_TYPES`. When both ATS flags are on
and a caller requests only `types=users`, the loop fills `results.candidates` and
`results.job_orders` with `_empty_section()`. This is consistent with how `results.calendar`
is filled when the caller omits `types=calendar` but `_EXTENDED_SEARCH=True`. Existing
callers that rely on specific result-set key names are not affected: new keys appear, existing
keys retain their shape.

## 10. Open Questions / Assumptions

1. **`client_company_id` availability on per-recruiter index rows.** ATI-004 assumes JOB-002
   writes `client_company_id` as a projected attribute on the `GSI_BY_RECRUITER` index row,
   enabling the `pk` for `get_item` to be reconstructed as `"COMPANY#{client_company_id}"`.
   If JOB-002's index row only carries `job_id` (without `client_company_id`), the function
   falls back to `GSI_DIRECT` (a second `query` call). The spec prefers the zero-extra-query
   path but handles both. This assumption should be confirmed against the JOB-002 implementation
   before ATI-004 is merged.

2. **`key_skills` free-text search adequacy.** CND-001 §5.4 notes that `key_skills` is a
   free-text blob up to 4000 chars. The token-match `contains(haystack, tok)` approach may
   produce false positives on skill blobs with common substrings (e.g. querying "java" matches
   "javascript"). This is acceptable for the initial implementation (consistent with the
   approach used by `_search_tickets` on the subject field) and can be improved via a dedicated
   search index in a follow-up if the Tier-2 skill-tags cluster (gap analysis §D, "Cross-module
   tags / skill tags") ships.

3. **`ALLOWED_TYPES` re-evaluation if flags change at runtime.** The current design evaluates
   `ALLOWED_TYPES` once at module import time. If a feature flag is toggled live (e.g. via a
   config push without restart), the `ALLOWED_TYPES` set would not update until the process
   restarts. This is consistent with how `_EXTENDED_SEARCH` works today and is acceptable for
   a flag that is expected to be set once at deploy time.

4. **`placed_count` availability.** `JobOrderOut.placed_count` defaults to 0 until the PIPE
   (pipeline) cluster ships. ATI-004 reads `meta.get("placed_count", 0)` defensively; a
   missing attribute is treated as 0. No pipeline data dependency.

5. **Global search rate limit with more branches.** Adding two branches increases fan-out CPU
   and DDB read consumption per search request. The existing 30 req/min per-user rate limit
   (search.py:31) should be monitored and may need tuning once the ATS entity counts grow.
   No change is required at ATI-004 time.
