## 1. Summary & Goal

ATI-002 closes the gap-analysis row "Reports (submissions / placements / recruiter / pipeline / source)" which is rated **PARTIAL (framework)** in `docs/opencats/OPENCATS_GAP_ANALYSIS.md:90`: the RPT-002/RPT-003 report builder already exists; what is missing is the ATS data wiring. This ticket delivers exactly that — and nothing else:

1. **Three new module adapters** registered in `_fetch_and_filter`'s per-module dispatch table (`app/services/crm_reports.py`, RPT-002 §4.2): `ats_pipeline`, `ats_candidates`, `ats_job_orders`. Each adapter iterates its source ATS table, applies owner-scoping and condition filtering, and projects to the requested fields — following the identical iterator contract established by the `tickets`, `billing_ledger`, and `subscriptions` adapters in RPT-002 §4.2.

2. **Five canonical recruiting report definitions** seeded as ordinary `ReportCreateIn`-shaped rows in `T.crm_reports` (RPT-001 §3.1) via an idempotent `seed_recruiting_reports(owner_sub)` helper. These are DynamoDB rows, not code; they use the existing `POST /ui/crm/reports` + `POST /ui/crm/reports/{id}/run` surface from RPT-002 with RPT-003 `group_by` / `aggregates` — not a new endpoint.

The goal is parity with the OpenCATS built-in reports for submissions, placements, recruiter productivity, pipeline breakdown by status, and candidates by source. After this ticket a recruiter can run any of the five seeded reports and see grouped counts and sums over live ATS data.

`app/services/crm_reports.py` (RPT-002, not yet in HEAD at `app/core/settings.py` line 2772 — no `crm_reports_enabled` exists at HEAD) will implement:

### 3.1 No new DynamoDB tables

ATI-002 writes only to `T.crm_reports` (the existing RPT-001 table, PK `report_id` / SK `sk`). It reads from `T.ats_pipeline`, `T.candidates`, and `T.job_orders` (all owned by sibling clusters). No new `TableDef` entry, no new GSI, no `attr_types` change.

### 3.2 Five seeded report definition rows (`T.crm_reports`)

Each row is a standard META row (`sk = "META"`) with a deterministic `report_id`. The `GSI1PK`/`GSI1SK` fields are written so the rows appear in the owner's `list_reports` response (RPT-002 §3.2).

| Deterministic `report_id` | `name` | `module` | `group_by` | `aggregates` | Maps to |
|---|---|---|---|---|---|
| `RPT#ati002_submissions` | "Submissions by Recruiter" | `ats_pipeline` | `recruiter_sub` | `[{field:"*", function:"COUNT"}]` | OpenCATS "Submissions" |
| `RPT#ati002_placements` | "Placements by Recruiter" | `ats_pipeline` | `recruiter_sub` | `[{field:"*",function:"COUNT"},{field:"fee_cents",function:"SUM"}]` | OpenCATS "Placements" |
| `RPT#ati002_recruiter_activity` | "Recruiter Activity" | `ats_pipeline` | `recruiter_sub` | `[{field:"*",function:"COUNT"}]` | Recruiter productivity |
| `RPT#ati002_pipeline_breakdown` | "Pipeline Breakdown by Status" | `ats_pipeline` | `status` | `[{field:"*",function:"COUNT"}]` | Pipeline-by-status |
| `RPT#ati002_candidates_by_source` | "Candidates by Source" | `ats_candidates` | `source` | `[{field:"*",function:"COUNT"}]` | "Candidates by Source" |

The Submissions report applies a pre-filter condition `[{field:"status_rank", operator:"gte", value:"400"}]` (rank ≥ 400 = submitted threshold; uses the existing `_eval_condition` `gte` operator from RPT-002 §4.2) to exclude pipeline entries that have never been submitted. The Placements report applies `[{field:"status", operator:"eq", value:"900_placed"}]` (or whatever the configured `is_placed` key resolves to; the default value `900_placed` is used in the seed row — operators are evaluated at run time against live data).

#### 4.2.1 Three iterator helpers

```python
def _iter_ats_pipeline(owner_sub: str) -> Generator[Dict[str, Any], None, None]:
    """Yield all pipeline entry items for owner_sub, looping LastEvaluatedKey.

    Uses T.ats_pipeline with pk = USER#{owner_sub}, sk.begins_with("PIPE#"),
    excluding #PLACEMENT sub-rows (sk.endswith("#PLACEMENT") filtered out
    client-side — a FilterExpression cannot reduce DDB page size so we loop).
    Each yielded dict has 'recruiter_sub' aliased from 'owner_sub' so report
    consumers can use 'recruiter_sub' as a group_by field.
    """
    pk_val = f"USER#{owner_sub}"
    kce = Key("pk").eq(pk_val) & Key("sk").begins_with("PIPE#")
    kwargs: Dict[str, Any] = {
        "KeyConditionExpression": kce,
        "FilterExpression": Attr("sk").not_contains("#PLACEMENT"),
    }
    while True:
        resp = T.ats_pipeline.query(**kwargs)
        for item in resp.get("Items", []):
            item.setdefault("recruiter_sub", item.get("owner_sub", ""))
            yield item
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek


def _iter_ats_candidates(owner_sub: str) -> Generator[Dict[str, Any], None, None]:
    """Yield all active (non-deleted) candidate META items for owner_sub.

    Uses T.candidates ByOwner GSI: GSI1PK = OWNER#{owner_sub}, sort GSI1SK (N).
    Excludes soft-deleted candidates (deleted_at present).
    """
    gsi_pk = f"OWNER#{owner_sub}"
    kwargs: Dict[str, Any] = {
        "IndexName": "ByOwner",
        "KeyConditionExpression": Key("GSI1PK").eq(gsi_pk),
        "FilterExpression": Attr("deleted_at").not_exists(),
    }
    while True:
        resp = T.candidates.query(**kwargs)
        yield from resp.get("Items", [])
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek


def _iter_ats_job_orders(owner_sub: str) -> Generator[Dict[str, Any], None, None]:
    """Yield all non-deleted job order META items for owner_sub (recruiter).

    Uses T.job_orders GSI_BY_RECRUITER: recruiter_sub = owner_sub.
    [CORRECTED: handle is T.job_orders (JOB-001), not T.ats_job_orders.]

    IMPORTANT: GSI_BY_RECRUITER is on sparse per-recruiter INDEX ROWS (pk=COMPANY#...,
    sk=RECRUITER#{sub}#JOB#{job_id}), which carry only recruiter_sub + created_at + job_id.
    To yield full META rows with all projectable fields (title, status, openings, etc.),
    each index row's job_id must be resolved to the META row via a secondary get_item
    (using GSI_DIRECT on T.job_orders). The iterator below shows the corrected two-step
    approach. Soft-delete exclusion is handled by get_job_order raising 404 for deleted rows.

    [CORRECTED: original code (yield from resp.Items directly) would only yield sparse index
    rows missing title/status/openings/placed_count/client_company_id/updated_at — not the
    full META items needed for field projection. The GSI_BY_RECRUITER fan-out pattern is
    documented in ATS_JOB_ORDERS_TICKETS.md §JOB-004 list_mine which resolves each index
    row's job_id to the META row (batch get / per-row get).]
    """
    from app.services.ats_job_orders import get_job_order  # lazy import; raises ImportError if JOB cluster absent
    kwargs: Dict[str, Any] = {
        "IndexName": "GSI_BY_RECRUITER",
        "KeyConditionExpression": Key("recruiter_sub").eq(owner_sub),
    }
    while True:
        resp = T.job_orders.query(**kwargs)
        for index_row in resp.get("Items", []):
            job_id = index_row.get("job_id")
            if not job_id:
                continue
            try:
                meta = get_job_order(job_id)  # raises HTTPException(404) if deleted or missing
                yield meta.__dict__ if hasattr(meta, "__dict__") else dict(meta)
            except Exception:
                pass  # deleted or concurrent race — skip
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
```

```python
def seed_recruiting_reports(owner_sub: str) -> List[str]:
    """Idempotently seed the five canonical recruiting report definitions.

    Uses a conditional put (attribute_not_exists(report_id)) per row so
    re-running is a no-op. Returns list of report_ids that were newly written
    (empty list if all already existed). Caller is responsible for ensuring
    S.crm_reports_enabled before calling.

    Emits audit_event("ats_reports.seeded", owner_sub, None, ...) for each
    newly written row.
    """
    ts = now_ts()
    written: List[str] = []
    for defn in _SEED_DEFINITIONS:
        item = {
            "report_id":  defn["report_id"],
            "sk":         "META",
            "GSI1PK":     f"OWNER#{owner_sub}",
            "GSI1SK":     ts,
            "name":       defn["name"],
            "description": None,
            "module":     defn["module"],
            "fields":     json.dumps(defn["fields"]),
            "conditions": json.dumps(defn["conditions"]),
            "group_by":   defn.get("group_by"),
            "aggregates": json.dumps(defn.get("aggregates", [])),
            "owner_sub":  owner_sub,
            "created_at": ts,
            "updated_at": ts,
        }
        try:
            T.crm_reports.put_item(
                Item=item,
                ConditionExpression="attribute_not_exists(report_id)",
            )
            written.append(defn["report_id"])
            audit_event(
                "ats_reports.seeded",
                owner_sub,
                None,
                report_id=defn["report_id"],
                module=defn["module"],
            )
        except T.crm_reports.meta.client.exceptions.ConditionalCheckFailedException:
            pass  # already exists — idempotent
    return written
```

## 5. Detailed Behavior & Edge Cases

### 5.1 `_iter_ats_pipeline` — PLACEMENT sub-row exclusion

Pipeline entries and placement sub-rows coexist on the same table under `pk = USER#{owner_sub}`. Placement SK has suffix `#PLACEMENT` (PIP-006 §3.2: `sk = PIPE#{job_order_id}#CAND#{candidate_id}#PLACEMENT`). The iterator applies a DynamoDB `FilterExpression = Attr("sk").not_contains("#PLACEMENT")` to exclude them server-side. Per the CLAUDE.md "DDB FilterExpression doesn't reduce page size" gotcha, pagination continues until all items are yielded — the `FilterExpression` does not terminate early. The `MAX_REPORT_ROWS = 2000` cap in `_fetch_and_filter` stops iteration once 2000 qualifying items are accumulated.

### 5.2 `recruiter_sub` alias in `_iter_ats_pipeline`

Pipeline entry items store the recruiter's identity in `owner_sub`, not `recruiter_sub`. The Submissions, Placements, and Recruiter Activity seeded reports `group_by = "recruiter_sub"`. The iterator injects a synthetic `recruiter_sub` key by doing `item.setdefault("recruiter_sub", item.get("owner_sub", ""))` on each yielded item before it reaches `_eval_condition` and `_project_row`. This is transparent to the RPT-002 engine and does not mutate the original DDB item dict (`.setdefault` on the yielded copy).

### 5.3 `fee_cents` Decimal-safe SUM

The Placements report requests `SUM(fee_cents)`. Placement sub-rows are excluded from the iterator (§5.1); `fee_cents` on pipeline entry items is set to `0` or absent (the fee lives on the `#PLACEMENT` sub-row). For a correct placements SUM, the Placements report must read the `fee_cents` field from the pipeline entry itself **if the pipeline entry was written with a denormalised `fee_cents`** (a PIP-006 implementation choice). If PIP-006 does not denormalise `fee_cents` onto the junction row, the SUM will always be `0` for the seeded Placements report. This is an **open question** (§10.1).

`_apply_group_by` from RPT-003 uses `_coerce_numeric(value)` which handles `Decimal` → `float` safely (RPT-003 §4.2.1). For integer-cent precision, the seeding definition uses `{"field": "fee_cents", "function": "SUM"}` and the caller should interpret the output as integer cents (divide by 100 for display).
[CORRECTED: the claim that `_apply_group_by` does `int(round(...))` "per RPT-003 §2.3 guidance" is inaccurate. RPT-003 §4.2.2 shows `_apply_group_by` returns `sum(numeric_vals)` as a Python `float` for SUM — no `int(round(...))` round-trip is defined. RPT-003 §2.3 discusses only how `_apply_group_by` should use `int()` when reading `amount_cents` from billing items before summing, not an int(round) cast on the aggregate output. The SUM output for `fee_cents` will be a Python `float`; callers must round to int for display.]

### 5.4 `status_rank` condition on Submissions

The Submissions report applies `{field:"status_rank", operator:"gte", value:"400"}`. `_eval_condition` with `gte` coerces both sides to `float` before comparison (RPT-002 §4.2). `status_rank` is stored as a DynamoDB `N` (int), deserialised by boto3 as `Decimal`. `_coerce_numeric(Decimal("400"))` → `400.0`; `float("400")` → `400.0`. The comparison holds. If a pipeline entry has no `status_rank` (e.g. created before PIP-002 was merged), `_coerce_numeric(None)` → `0.0` < `400.0` → correctly excluded.

### 5.5 Owner-scoping and cross-tenant isolation

All three iterators scope to the calling `owner_sub`. `_iter_ats_pipeline` uses `pk = USER#{owner_sub}`, so the DDB query physically cannot return another recruiter's items (key-based isolation, OPP-004 §5 pattern). `_iter_ats_candidates` uses the `ByOwner` GSI with `GSI1PK = OWNER#{owner_sub}` (CND-001 §3.3). `_iter_ats_job_orders` uses `GSI_BY_RECRUITER` with `recruiter_sub = owner_sub` (ATS_JOB_ORDERS_TICKETS.md §JOB-004) — but this GSI indexes sparse per-recruiter index rows owned by that recruiter, which by construction are only written for job orders where `owner_sub ∈ recruiter_subs`, so cross-tenant isolation is preserved. The corrected two-step resolution in §4.2.1 (index row → `get_job_order`) enforces the same ownership because `get_job_order` uses `GSI_DIRECT` which returns only the single META row for the given `job_id`. A recruiter cannot observe another recruiter's data even if they share the same tenant — no cross-tenant aggregation is exposed.

### 5.6 Seeding idempotency and re-seeding safety

`seed_recruiting_reports` uses `attribute_not_exists(report_id)` conditional puts. If the row already exists (second call, or concurrent calls), the `ConditionalCheckFailedException` is caught silently. The function is therefore safe to call from deployment scripts, admin tooling, and tests without side effects beyond the first write. Concurrent calls cannot produce duplicate rows because DynamoDB's conditional-put is atomic.

### 5.7 Flag-off gating during `_fetch_and_filter`

If `CRM_REPORTS_ENABLED = false`, the RPT-002 router never registers `/ui/crm/reports`, so `_fetch_and_filter` is never called. If `CRM_REPORTS_ENABLED = true` but `ATS_PIPELINE_ENABLED = false` and a user tries to run the seeded Submissions report, `_fetch_and_filter` raises `ValueError("module_unavailable:ats_pipeline_disabled")` → the router returns 422 with a descriptive detail. If `CANDIDATES_ENABLED = false` (CND-001 flag), running the candidates-by-source report raises `ValueError("module_unavailable:candidates_disabled")`. If `ATS_ENABLED = false` or `JOB_ORDERS_ENABLED = false` (JOB-001 flags), running job-order reports raises `ValueError("module_unavailable:job_orders_disabled")`. The seeded rows remain in `T.crm_reports` but are inert until the relevant flags are enabled. This is the correct behaviour: report definitions can exist before the data they query.
[CORRECTED: updated to use the actual flag names from CND-001 and JOB-001.]

### 5.8 Empty result sets

All three adapters may return zero rows (no pipeline entries / candidates / job orders for the owner). `_apply_group_by` on an empty list returns an empty list. `ReportRunOut` carries `row_count = 0`, `rows = []`, `status = "ok"`. The existing RPT-002 router serialises this correctly. No special-case handling is needed.

### 5.9 `_iter_ats_candidates` deleted-at filter

Soft-deleted candidates (`deleted_at` present) are excluded via `FilterExpression = Attr("deleted_at").not_exists()`. DynamoDB `FilterExpression` does not reduce page size; the iterator loops `LastEvaluatedKey` unconditionally. Under CLAUDE.md's "DDB FilterExpression doesn't reduce page size" rule this is correct: each page is fetched fully before filtering, and pagination continues until all items are exhausted or the `MAX_REPORT_ROWS` cap is reached.

## 10. Open Questions / Assumptions

### 10.1 `fee_cents` denormalisation on pipeline junction rows

The Placements report SUM(`fee_cents`) depends on `fee_cents` being present on pipeline junction rows, not only on `#PLACEMENT` sub-rows. The PIP-006 spec (§3.2) defines `fee_cents` only on the `#PLACEMENT` sub-row. If PIP-006 does not write a denormalised `fee_cents` onto the junction row, the Placements SUM will always be 0.

**Resolution options (for implementation):**
- (a) PIP-006 denormalises `fee_cents` onto the junction row's `update_item` when creating the placement. This is the preferred option — one additional field on `update_item` in PIP-006.
- (b) ATI-002 seeded Placements report uses `ats_pipeline` with a different field name (e.g., reads `#PLACEMENT` sub-rows directly). This would require the iterator to yield placement sub-rows optionally, complicating §5.1.
- (c) Accept SUM = 0 and document it as a known limitation until PIP-006 is updated.

**Assumption for this spec**: option (a) — PIP-006 is updated to denormalise `fee_cents` onto the junction row when a placement is recorded. The iterator guard at §5.1 still excludes `#PLACEMENT` sub-rows.

### 10.2 `status_rank` values and the 400 threshold

The "submitted" threshold of `status_rank >= 400` is hardcoded in the seeded Submissions report condition. The default PIP-002 status config has `is_submitted` on `400_submitted` with `rank = 400`. If an admin reconfigures the status ladder (e.g., moves `is_submitted` to rank 350), the seeded report condition does not automatically update. This is intentional: the seeded reports are ordinary user-editable rows, not code. Operators can PATCH the report definition's `conditions` if they reconfigure the status ladder.

### 10.3 Multi-tenant seeding

`seed_recruiting_reports(owner_sub)` seeds five reports under a single owner. For a multi-recruiter tenant, each recruiter can seed their own copy (or run the existing reports via `list_reports` + `run`). The seeded rows are not "global" — they are partitioned under `OWNER#{owner_sub}` in the GSI. A future ATI-002 extension could add system-level template rows (different `GSI1PK` prefix, e.g. `TEMPLATE`), but that is out of scope.
