# CND-004 — Candidate change-history feed (reuse LED-012 / ACT-009 timeline)

**Type:** Feature · **Priority:** P1 · **Estimate:** 1 day  
**Cluster:** ATS Candidates (CND) · **Gap analysis:** `docs/opencats/OPENCATS_GAP_ANALYSIS.md` §A  
**Source ticket:** `docs/opencats/ATS_CANDIDATES_TICKETS.md` §CND-004  
**Depends on:** CND-001 (table, flag, models), CND-002 (CRUD service — caller)  
**Required by:** CND-005 (router exposes `GET /ui/candidates/{id}/history`)

---

## 1. Summary & Goal

CND-004 adds a per-candidate **change-history feed** so recruiters see a chronological
audit trail of every field edit, status move, owner reassignment, and résumé upload/removal
that has occurred on a candidate record.

This ticket owns **only the thin candidate-side adapter**. It does not build a new timeline
engine, a new table, or new background work. It wires two primitives already specified
elsewhere:

- **Preferred path (ACT-009):** when `app/services/crm_activity_timeline.py` is present
  (ships with ACT-009), CND-004 calls `record_crm_activity(entity_type="candidate", ...)`.
  The `crm_activity_timeline` table is owned by ACT-001/ACT-009 and requires no changes
  here; `"candidate"` is simply a new value in the open `entity_type` string field
  (`ACT-009 §3.1`, `docs/suitecrm/specs/ACT-009.md`).

- **Fallback path (LED-012 pattern):** when ACT-009 has not yet shipped, CND-004 writes
  an `ACTIVITY#{inverted_ts}#{activity_id}` sub-item directly onto the candidate's own
  `candidates` table (same PK as the candidate META row). This is the single-table
  `ACTIVITY#` sub-item pattern that LED-012 uses on the `leads` table
  (`docs/suitecrm/specs/LED-012.md §3.1`).

Both paths are wrapped in `try/except` (fire-and-forget, never raises). CND-002's
`update_candidate` and CND-003's `add_resume`/`delete_resume` call
`record_candidate_change` at the appropriate points.

**The net result:** a recruiter opens the History tab on a candidate detail page and sees,
newest first, every change event with its actor, timestamp, and short description — with
zero new tables if ACT-009 is already deployed, and a local fallback that self-heals when
ACT-009 ships later.

## 2. Context & Current State

### 2.1 `app/services/crm_activity_timeline.py` — preferred target (not yet present)

`app/services/crm_activity_timeline.py` does not exist in the live codebase today
(verified: `ls app/services/crm_activity_timeline.py` → NOT FOUND). ACT-009
(`docs/suitecrm/specs/ACT-009.md`) creates it with `record_crm_activity(entity_type,
entity_id, activity_type, activity_id, user_sub, *, summary="", metadata=None)` and
`list_entity_activities(entity_type, entity_id, *, activity_type=None, cursor=None,
limit=20)`. The entity_key for ACT-009 is `f"{entity_type}#{entity_id}"` (ACT-009 §3.1)
with `entity_type` stored as an open string — adding `"candidate"` requires no schema
change to the `crm_activity_timeline` table.

### 2.2 `app/services/activity_feed.py` — existing social feed (not used)

The platform's social activity stream (`app/services/activity_feed.py`) writes to
`T.activity_feed` (PK `user_id` / SK `{ts}#{activity_id}`, confirmed at
`app/services/activity_feed.py:70`). It carries social types `follow`, `like`, `comment`,
`post`, `mention`, `share`, `tip` (`activity_feed.py:22-30`). CND-004 does **not** use
this table or service — recruiter change-history is CRM data, not a social event stream.

### 2.3 LED-012 fallback pattern (`docs/suitecrm/specs/LED-012.md`)

LED-012 (`docs/suitecrm/specs/LED-012.md`) adds a `ByTarget` sparse GSI to
`activity_feed` and a new service function `record_activity_for_entity`. LED-012 stores
its activity rows in the existing `activity_feed` table (PK=`lead_id` acting as the
"feed owner", SK=`{ts}#{activity_id}`) — it does **not** write ACTIVITY# sub-items on
the `leads` table itself. CND-004's fallback takes a different approach: it writes
`ACTIVITY#`-prefixed sub-items directly on the entity's own `candidates` table. This
avoids a hard dependency on the `activity_feed` table while staying within the
`candidates` partition. The key pattern is inspired by `call_history.py:31`'s `_make_sk`
inverted-timestamp technique: `inverted = 9999999999999 - created_at`, yielding a string
SK that sorts newest-first without `ScanIndexForward=False`. CND-004 does NOT call
`record_activity_for_entity`; the LED-012 spec is cited only as the source of the
`ByTarget` context, not as the sub-item pattern.

### 2.4 ACT-007 lazy-import caller pattern

ACT-007 (`docs/suitecrm/specs/ACT-007.md §2.4`) is the canonical example of how to call
`record_crm_activity` from an unrelated service module: lazy local import inside
`try/except`, fire-and-forget, no retry. CND-004 uses the identical pattern.

### 2.5 `app/services/call_history.py` — inverted-ts SK

`app/services/call_history.py:28-32` defines `_make_sk`:

```python
def _make_sk(created_at: int, call_id: str) -> str:
    inverted = 9999999999999 - created_at
    return f"CALL#{inverted:013d}#{call_id}"
```

CND-004's fallback uses the same arithmetic with an `ACTIVITY#` prefix and a
`activity_id` suffix instead of `call_id`.

### 2.6 `app/core/cursor.py` — pagination

`encode_cursor` / `decode_cursor` at `app/core/cursor.py:94` / `:103` produce HMAC-signed
opaque cursors from DynamoDB `LastEvaluatedKey`. Both are already imported and used by
`app/services/activity_feed.py:18`.

### 2.7 `app/services/alerts.py` — audit

`audit_event(event, user_sub, request=None, **fields)` at `app/services/alerts.py:644`
writes structured audit rows to `T.alerts`. CND-004 calls this for each
`record_candidate_change` invocation only from the preferred (ACT-009) code path; the

### 2.8 `app/core/time.py` — timestamps

`now_ts()` at `app/core/time.py:2` returns an integer Unix-second timestamp. Used for
`created_at` on every activity/history row.

### 2.9 `candidates` table — single-table sub-item space (CND-001)

CND-001 provisions the `candidates` DynamoDB table with `PK=pk` (S) / `SK=sk` (S) and
three GSIs. The fallback path writes `ACTIVITY#` sub-items under the same partition key
`"CANDIDATE#{candidate_id}"` using `SK = f"ACTIVITY#{inverted_ts}#{activity_id}"`. The
existing `ByOwner` / `ByStatus` / `BySource` GSIs are sparse on `GSI1PK` / `GSI2PK` /
`GSI3PK` respectively; `ACTIVITY#` sub-items carry none of these GSI keys and therefore
never appear in any of those indexes — zero index pollution.

### 2.10 CND-002 — caller

CND-002 (`docs/opencats/specs/CND-002.md`) calls `record_candidate_change` at the end of
`update_candidate` (before returning the updated item), at the end of `delete_candidate`
(soft-delete), and inside `set_owner` (best-effort, CND-002 spec §4.1 line 309). CND-003
calls it at the end of `add_resume` and `delete_resume`. All calls are wrapped in
`try/except` at the CND-002/003 layer per the fire-and-forget contract; the calls are
already specified in those tickets. Note: CND-002 spec §11.2 lists `update_candidate`,
`delete_candidate`, and `set_owner` as callers (not `create_candidate`); the `created`
change-type in CND-004 §4.4 is a forward specification of a call that CND-004 adds to
`create_candidate` — it is not already present in the CND-002 spec.

## 3. Data Model

### 3.1 Fallback: `ACTIVITY#` sub-items on `candidates` table

No new DynamoDB table. The fallback path writes sub-items into the **existing** `candidates`
table (CND-001) using the single-table sub-item pattern.

**Item shape:**

| Attribute | Type | Value / Notes |
|---|---|---|
| `pk` | S (PK) | `"CANDIDATE#{candidate_id}"` — same partition as the META row |
| `sk` | S (SK) | `"ACTIVITY#{inverted_ts:013d}#{activity_id}"` |
| `activity_id` | S | `"chg_" + uuid4().hex[:16]` |
| `candidate_id` | S | denormalised for readback |
| `change_type` | S | see closed set §3.3 |
| `summary` | S | short human-readable description (≤ 200 chars) |
| `actor_sub` | S | `user_sub` of the person who triggered the change |
| `metadata` | M | arbitrary JSON (field-level diff, old/new status, etc.) |
| `created_at` | N | `now_ts()` integer |

`inverted_ts = 9999999999999 - created_at` (mirrors `call_history.py:31`). The SK sorts
oldest-last under natural ascending order, so `ScanIndexForward=True` on a query of
`SK begins_with "ACTIVITY#"` yields newest-first — **no** `ScanIndexForward=False` needed.

The `ACTIVITY#` sub-items carry **none** of the three GSI partition keys (`GSI1PK` /
`GSI2PK` / `GSI3PK`), so they are invisible to the `ByOwner`, `ByStatus`, and `BySource`
indexes. There is no risk of GSI key collision with candidate META rows.

### 3.2 Preferred path: ACT-009 `crm_activity_timeline` table

When ACT-009 is present, the `record_crm_activity` call writes to the `crm_activity_timeline`
table (owned by ACT-001/ACT-009, `entity_key="candidate#{candidate_id}"`,
`sk="{inverted_ts}#{activity_type}#{activity_id}"`, `GSI1PK="TYPE#{activity_type}"`).
CND-004 makes no schema changes to that table. The `entity_type="candidate"` value is an
open string field in the ACT-009 table schema (ACT-009 §3.1).

### 3.3 `change_type` closed set

```python
CANDIDATE_CHANGE_TYPES = {
    "created",          # candidate record first written (CND-002.create_candidate)
    "updated",          # field-level update (CND-002.update_candidate)
    "status_changed",   # status field specifically (CND-002.update_candidate, status changed)
    "owner_changed",    # owner_sub changed (CND-002.set_owner)
    "resume_added",     # résumé attachment uploaded (CND-003.add_resume)
    "resume_removed",   # résumé attachment soft-deleted (CND-003.delete_resume)
    "deleted",          # candidate soft-deleted (CND-002.delete_candidate)

```

Each caller passes the appropriate `change_type`. ACT-009 uses `activity_type` which maps
1-to-1: `change_type` is passed verbatim as `activity_type` when delegating to ACT-009.
The ACT-009 `_VALID_ACTIVITY_TYPES` set is extended (or the service-level check is
bypassed) since CND-004 calls the service function directly, not the router endpoint.

## 4. API / Service Design

### 4.1 `record_candidate_change` (write adapter)

**Location:** new function in `app/services/candidates.py` (CND-002's file),
appended after `delete_candidate`.

```python
def record_candidate_change(
    candidate_id: str,
    actor_sub: str,
    *,
    change_type: str,
    summary: str,
    metadata: Optional[Dict[str, Any]] = None,
) -> None:
    """Fire-and-forget history row. Never raises."""
    ...
```

**Implementation logic (within a single outer `try/except Exception: logger.warning(...)`):**

1. Call `now_ts()` for `ts`; generate `activity_id = "chg_" + uuid4().hex[:16]`.

2. **ACT-009 preferred path** — try to import `record_crm_activity` via a lazy local
   import:
   ```python
   try:
       from app.services.crm_activity_timeline import record_crm_activity  # noqa: PLC0415
       record_crm_activity(
           "candidate", candidate_id,
           change_type,           # activity_type
           activity_id,
           actor_sub,
           summary=summary[:200],
           metadata=metadata or {},
       )
       return
   except ImportError:
       pass   # ACT-009 not yet deployed → fall through to local path
   except Exception:
       logger.warning("crm_activity_timeline unavailable; using local fallback", exc_info=True)
       # fall through
   ```
   The `ImportError` path catches the case where `crm_activity_timeline.py` does not
   exist. A runtime exception (e.g., DDB unavailable) falls through to the local path —
   this means a DDB failure in ACT-009 does NOT silence the fallback (defense in depth).

3. **LED-012-pattern fallback path** — write `ACTIVITY#` sub-item to `T.candidates`:
   ```python
   inverted = 9999999999999 - ts
   sk = f"ACTIVITY#{inverted:013d}#{activity_id}"
   T.candidates.put_item(Item={
       "pk": f"CANDIDATE#{candidate_id}",
       "sk": sk,
       "activity_id": activity_id,
       "candidate_id": candidate_id,
       "change_type": change_type,
       "summary": summary[:200],
       "actor_sub": actor_sub,
       "metadata": metadata or {},
       "created_at": ts,
   })
   ```

4. The entire body is wrapped in `try/except Exception: logger.warning(...)` — no
   exception ever propagates to the caller.

**Guard on `S.candidates_enabled`:** the function checks `if not S.candidates_enabled:
return` as the very first statement (before the try/except), consistent with all other
CND-002 functions. With the flag off, no DDB write is attempted.

### 4.2 `list_candidate_history` (read function)

**Location:** `app/services/candidates.py`, appended after `record_candidate_change`.

```python
def list_candidate_history(
    candidate_id: str,
    *,
    cursor: Optional[str] = None,
    limit: int = 50,
) -> Dict[str, Any]:
    """Return paginated change-history for a candidate, newest-first.

    Delegates to ACT-009 when available; falls back to local ACTIVITY# query.
    Returns {"events": [...], "next_cursor": str|None}.
    """
```

**Implementation logic:**

1. Guard: `if not S.candidates_enabled: return {"events": [], "next_cursor": None}`.

2. Clamp: `limit = max(1, min(limit, 100))`.

3. **ACT-009 preferred path:**
   ```python
   try:
       from app.services.crm_activity_timeline import list_entity_activities
       result = list_entity_activities(
           "candidate", candidate_id,
           cursor=cursor,
           limit=limit,
       )
       return {"events": result["items"], "next_cursor": result.get("next_cursor")}
   except ImportError:
       pass
   except Exception:
       logger.warning("crm_activity_timeline read unavailable; using local fallback",
                      exc_info=True)
   ```

4. **Fallback — query `T.candidates` for `ACTIVITY#` sub-items:**
   ```python
   eks = decode_cursor(cursor)
   kwargs = {
       "KeyConditionExpression": (
           Key("pk").eq(f"CANDIDATE#{candidate_id}")
           & Key("sk").begins_with("ACTIVITY#")
       ),
       "ScanIndexForward": True,   # inverted SK → ascending = newest first
       "Limit": limit,
   }
   if eks:
       kwargs["ExclusiveStartKey"] = eks
   resp = T.candidates.query(**kwargs)
   items = resp.get("Items", [])
   last_key = resp.get("LastEvaluatedKey")
   next_cursor = encode_cursor(last_key) if last_key else None
   events = [
       {
           "event_id": i["activity_id"],
           "candidate_id": i["candidate_id"],
           "change_type": i["change_type"],
           "summary": i.get("summary", ""),
           "actor_sub": i["actor_sub"],
           "metadata": i.get("metadata") or {},
           "created_at": int(i["created_at"]),
       }
       for i in items
   ]
   return {"events": events, "next_cursor": next_cursor}
   ```

No `FilterExpression` is applied (the `begins_with("ACTIVITY#")` key condition already
scopes the result set tightly). This avoids the CLAUDE.md gotcha that
`FilterExpression` does not reduce the DDB page size.

### 4.3 Router endpoint (specified here, implemented in CND-005)

CND-005 exposes this endpoint:

```
GET /ui/candidates/{candidate_id}/history
Auth: require_ui_session (app/services/sessions.py:330)
Query params: cursor (str, optional), limit (int, 1–100, default 50)
Response: CandidateHistoryResponse
```

The handler in `app/routers/candidates.py` (CND-005):
1. Gate: `if not S.candidates_enabled: raise HTTPException(404)`.
2. Verify candidate exists via `get_candidate(candidate_id)` → 404 if absent.
3. Owner/admin access check (same pattern as other CND-005 endpoints):
   `user_sub == candidate["owner_sub"] or user_sub == candidate["created_by"] or _is_admin(user)`.
4. Call `await asyncio.to_thread(list_candidate_history, candidate_id, cursor=cursor, limit=limit)`.
5. Return `CandidateHistoryResponse(**result)`.

This endpoint must be declared **before** the `/{candidate_id}` catch-all path parameter
route in `app/routers/candidates.py` (the same route-ordering constraint documented for
`/resumes` and `/history` in CND-005 and the GAP-0210/KB-003 §4.3 precedent). The literal
segment `history` must precede `/{candidate_id}` in FastAPI declaration order to prevent
shadowing.

## 5. Detailed Behavior & Edge Cases

### 5.1 ACT-009 absent at import time

`ImportError` in the ACT-009 try/except silently falls to the local `ACTIVITY#` path.
No log message at WARNING level for `ImportError` (it is an expected, normal condition
pre-ACT-009); only true runtime exceptions log a warning.

### 5.2 ACT-009 runtime failure

If `record_crm_activity` raises (e.g., DDB throttle), the `except Exception` block logs a
WARNING and the code falls through to the local `ACTIVITY#` write. This gives the
recruiter a history row even when the ACT-009 table is unavailable. Once ACT-009 recovers,
subsequent changes go back to the preferred path. This means a candidate may briefly have
history split across both tables; `list_candidate_history` will show only ACT-009 rows
when ACT-009 is active (since the preferred path short-circuits on success). This
dual-write window is an acceptable trade-off for resilience. A future consolidation
migration is out of scope for this ticket.

### 5.3 `list_candidate_history` when both paths have rows

Once ACT-009 ships and `list_entity_activities` returns successfully, the preferred path
always wins. Local `ACTIVITY#` fallback rows written during the ACT-009-absent window are
**not** merged into the response. This is an accepted limitation documented here:
pre-ACT-009 history remains accessible only via a direct DynamoDB scan (admin tool) until
a future backfill ticket migrates them. The recruiter sees a continuous feed from the
moment ACT-009 was deployed; pre-deployment history is available on request.

### 5.4 `change_type` vs ACT-009 `_VALID_ACTIVITY_TYPES`

The ACT-009 router (`app/routers/crm_activity_timeline.py`) validates `activity_type`
against `_VALID_ACTIVITY_TYPES = {"call", "task", "note", "calendar_event", "email"}` at
the HTTP boundary. CND-004 calls the **service function** `record_crm_activity` directly
(not the HTTP endpoint), so the router-level validation is not applied. The service
function itself does not restrict `activity_type` to an allowlist — it accepts any string
(ACT-009 §5.5: "service layer does not validate entity_type to allow internal callers").
CND-004's `change_type` values (`created`, `updated`, `status_changed`, `owner_changed`,
`resume_added`, `resume_removed`, `deleted`) will be stored as-is in the `activity_type`
field of the `crm_activity_timeline` table.

### 5.5 Pagination cursor validity

`decode_cursor(cursor)` at `app/core/cursor.py:103` returns `None` for a tampered or
expired cursor, which the fallback query interprets as "start from the beginning" — no
error raised. This matches `app/services/activity_feed.py:118`.

### 5.6 Concurrent writes ordering

Because DynamoDB does not provide atomic ordering across concurrent `put_item` calls, two
simultaneous changes by different recruiters may arrive with the same `now_ts()` value.
In this case the `activity_id` hex suffix provides a stable but arbitrary tie-break within
the same second. The recruiter UI shows newest-first; sub-second ordering ambiguity is
inconsequential for a human-readable audit trail.

### 5.7 Empty history

`list_candidate_history` returns `{"events": [], "next_cursor": None}` for a candidate
with no history rows. This is correct for newly created candidates before CND-002 has
emitted any `record_candidate_change` calls.

### 5.8 Soft-deleted candidate

`list_candidate_history` does not gate on the candidate's `deleted_at` field — history
is still queryable after soft-delete (an admin may need to audit who deleted it and when).
The `get_candidate` call in the router handler returns the item regardless of `deleted_at`
(it is a direct key lookup, not the `list_candidates` path that filters soft-deleted
rows). CND-005 exposes the history endpoint on soft-deleted candidates for admin actors;
non-admin, non-owner access to a soft-deleted candidate history returns 403 consistent
with the general candidate access model.

### 5.9 `metadata` field guidance

Callers should pass a flat `metadata` dict with string/int/bool values only. Recommended
keys per `change_type`:

| `change_type` | Recommended `metadata` keys |
|---|---|
| `updated` | `{"fields": ["email", "title"], "old_status": null, "new_status": null}` |
| `status_changed` | `{"old_status": "active", "new_status": "interviewing"}` |
| `owner_changed` | `{"old_owner": "sub_abc", "new_owner": "sub_xyz"}` |
| `resume_added` | `{"filename": "cv_2026.pdf", "attachment_id": "att_xxx"}` |
| `resume_removed` | `{"filename": "cv_old.pdf", "attachment_id": "att_yyy", "was_primary": true}` |

These are advisory; the service layer does not validate `metadata` structure.

## 6. Feature Flag & Config

### 6.1 Master flag (owned by CND-001)

`S.candidates_enabled` (`CANDIDATES_ENABLED`, default `"0"` → `False`) gates the entire
Candidate module. `record_candidate_change` and `list_candidate_history` both check
this flag first and return immediately (no-op) when it is off.

No new sub-flag is introduced by CND-004. The change-history sub-feature does not
need independent gating; disabling the candidate module disables all CND endpoints.

### 6.2 Settings keys (all from CND-001)

All settings keys used by CND-004 are already declared by CND-001:
`S.candidates_table_name` (for `T.candidates`) and `S.candidates_enabled`. No new
`app/core/settings.py` entries are required.

### 6.3 ACT-009 flags (soft dependency)

When ACT-009 is deployed, the preferred path activates automatically — no additional
flag or config change is required in the Candidate module. The lazy import detects
the module's presence at runtime.

### 6.4 Environment variable summary for CND-004

|---|---|---|
| `CANDIDATES_ENABLED` | `"0"` (False) | Master gate for the entire CND cluster |

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 compliance

`record_candidate_change` and `list_candidate_history` contain **no `S.dev_mode`
branch**. Both the fallback `T.candidates.put_item` path and the `record_crm_activity`
delegation write to DynamoDB Local (port 8001) in dev and to AWS DynamoDB in prod via
identical code paths. The `T.candidates` handle is resolved from
`S.candidates_table_name` by `_safe_table(...)` in `app/core/tables.py` (same wiring as
`contacts=_safe_table(S.contacts_table_name)` at `tables.py:354`). Moto intercepts boto3
calls in-process in dev; real DDB in prod. No mock branch, no inline data.

### 7.2 Idempotency

`record_candidate_change` is **not** idempotent by design — each call generates a fresh
`activity_id` and `ts`, producing a distinct row. This is correct for a change log (two
successive saves produce two audit entries). `list_candidate_history` is read-only and
idempotent.

### 7.3 No write amplification risk

`record_candidate_change` writes exactly one DynamoDB item per invocation (either to
`crm_activity_timeline` via ACT-009 or to the `ACTIVITY#` sub-item). There is no fan-out,
no multi-item transaction, and no S3 interaction.

### 7.4 Security: no new auth surface

CND-004 adds no new HTTP endpoints (those are in CND-005). The `record_candidate_change`
function is an internal service-layer helper, not a publicly reachable path. Input
sanitization: `summary[:200]` truncation is applied at write time; `change_type` is
from a caller-controlled closed set (no free-text injection path). `metadata` is stored
as a DynamoDB Map — no SQL or shell injection risk.

### 7.5 Security: actor attribution

Every history row records `actor_sub` (the `user_sub` from `require_ui_session`). This
provides a non-repudiable audit trail. The `actor_sub` is passed by the router handler
into the service, not inferred from the stored candidate record.

### 7.6 PII in `metadata` and `summary`

`summary` and `metadata` may contain PII (email addresses, recruiter names). These are
stored in DynamoDB unencrypted, consistent with the `candidates` META row and the
platform's broader DynamoDB storage policy. No additional encryption is required at this
tier.

### 7.7 CSRF

CND-004 adds no HTTP-writable endpoints. The `GET .../history` endpoint added by CND-005
is read-only; no CSRF token is required for GET requests (CLAUDE.md: CSRF enforcement
applies to non-GET requests only).

## 8. Backward Compatibility & Migration

### 8.1 `candidates` table — additive sub-item SK space

`ACTIVITY#` sub-items are written under the same partition as candidate META rows but
use a disjoint SK prefix. The three GSIs (`ByOwner`, `ByStatus`, `BySource`) are sparse
on `GSI1PK`/`GSI2PK`/`GSI3PK`; `ACTIVITY#` sub-items carry none of these attributes
and are therefore never indexed. No schema change or `just restart` is required for the
fallback path; the change is purely additive at runtime.

### 8.2 `crm_activity_timeline` table — no schema change

When ACT-009 deploys, the `crm_activity_timeline` table already exists with
`entity_type` as an open string. Writing `entity_type="candidate"` rows requires no
`UpdateTable` call, no new attribute definitions, and no backfill.

### 8.3 Pre-ACT-009 fallback rows

Fallback `ACTIVITY#` rows written before ACT-009 ships remain in the `candidates` table
indefinitely (no TTL is set on them). They are not deleted when ACT-009 ships. The
`list_candidate_history` function reads them only via the fallback path; once ACT-009 is
active, these rows are silently bypassed (as documented in §5.3). A future migration
ticket can backfill them into `crm_activity_timeline` if a complete unified timeline is
required.

### 8.4 No changes to existing files

CND-004 appends two functions to `app/services/candidates.py` (CND-002's file) and
appends two Pydantic models to `app/models.py`. No other existing file is modified.
`app/services/activity_feed.py`, `app/services/crm_activity_timeline.py`, and
`app/routers/candidates.py` are either untouched or not yet created.
