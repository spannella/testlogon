# ATI-003 — Calendar event↔entity linking + combined log-activity-and-schedule

**Ticket type:** Feature
**Priority:** P2
**Estimate:** 2 days
**Source:** `docs/opencats/ATS_INTEGRATION_TICKETS.md` §ATI-003
**Flags:** `CRM_ACTIVITIES_ENABLED` + `CRM_ACTIVITY_TIMELINE_ENABLED` (existing, owned by ACT-001).
No new top-level flag is introduced.

---

## 1. Summary & Goal

ATI-003 closes two gap-matrix items flagged as **MISSING** in `docs/opencats/OPENCATS_GAP_ANALYSIS.md` §C:

1. **Event↔entity linking.** `EventOut` / `EventCreateIn` / `EventUpdateIn`
   (`app/models.py:1256–1313`) carry no reference to a CRM or ATS entity. Recruiters need to
   pin a calendar event (an interview, follow-up call, or debrief) to a candidate, contact,
   job order, or opportunity so that all entity-linked events are queryable in one place.

2. **Combined "log activity AND schedule next event."** OpenCATS lets a recruiter close a
   call-log form and, in a single save, record what happened (an ACT-009 timeline entry) _and_
   schedule the next follow-up step (a new calendar event). Both writes currently require two
   separate round trips.

The goal is to deliver both capabilities additively on top of the existing calendar and
ACT-009 timeline primitives — no forking of any existing service, no new top-level flags, and
byte-for-byte parity when every flag is off.

## 3. Data Model

### 3.1 No new DynamoDB table

ATI-003 reuses `T.calendar` (the existing `calendar` table). The entity-pointer row is a
**sparse secondary item** stored in the same table with a synthetic `calendar_id` that acts as
an index partition.

### 3.2 Entity-pointer item shape (new row type in `T.calendar`)

When an event is created with `linked_entity_type` + `linked_entity_id`, a second item is
written to `T.calendar` alongside the canonical event item:

| Attribute | Value | Notes |
|---|---|---|
| `calendar_id` | `ENTITY#{linked_entity_type}#{linked_entity_id}` | Pointer partition key |
| `sk` | `event#{event_id}` | Same SK format as canonical events; `begins_with("event#")` query works unchanged |
| `type` | `"entity_event_pointer"` | Distinguishes pointer rows from canonical event rows |
| `event_id` | `<event_id>` | Copy of the event identifier |
| `source_calendar_id` | `<calendar_id>` | Used to resolve the canonical event item |
| `name` | `<event name>` | Denormalised for cheap listing without a second get |
| `start_utc` | `<start_utc>` | Denormalised; updated on `update_event` |
| `end_utc` | `<end_utc>` | Denormalised; updated on `update_event` |
| `linked_entity_type` | `<entity_type>` | Stored for convenience (readable from pointer) |
| `linked_entity_id` | `<entity_id>` | Stored for convenience |

The query `Key("calendar_id").eq(f"ENTITY#{entity_type}#{entity_id}") & Key("sk").begins_with("event#")` on `T.calendar` returns all pointers for a given entity. Each pointer is resolved to its canonical event via `_load_event(source_calendar_id, event_id)`.

### 3.3 Additive fields on the canonical event item

`create_event` and `update_event` store two new optional attributes on the event item itself
(no schema change — DynamoDB is schemaless):

| Attribute | DDB type | Constraint |
|---|---|---|
| `linked_entity_type` | S | Allow-list value (see §5.1); absent when `None` |
| `linked_entity_id` | S | Opaque string, max 128 chars; absent when `None` |

Both fields must be set together (one without the other → 422 at the router layer). Neither
is indexed on the canonical item partition — the pointer partition handles all by-entity
queries.

### 3.4 `scripts/local-ddb-init.py` changes

No new table or GSI is required. The `calendar` table already uses
`attr_types` only when a GSI numeric sort key is introduced (CLAUDE.md gotcha); since no GSI

## 4. API / Service Design

### 4.1 Service helpers: `app/services/crm_entity_calendar.py` (new file)

A thin service module that owns pointer writes and the by-entity query. Keeping this logic
out of `calendar.py` avoids growing that 2000-line file further and isolates testable units.

```python
# app/services/crm_entity_calendar.py

from __future__ import annotations

import logging
from typing import Any, Dict, List, Optional

from boto3.dynamodb.conditions import Key

from app.core.tables import T

logger = logging.getLogger(__name__)

_POINTER_TYPE = "entity_event_pointer"

ALLOWED_ENTITY_TYPES = frozenset({
    "contact", "lead", "account", "opportunity", "candidate", "job_order"
})


def _pointer_pk(entity_type: str, entity_id: str) -> str:
    return f"ENTITY#{entity_type}#{entity_id}"


def upsert_entity_pointer(
    *,
    entity_type: str,
    entity_id: str,
    event_id: str,
    source_calendar_id: str,
    name: str,
    start_utc: Optional[str],
    end_utc: Optional[str],
) -> None:
    """Write or overwrite the entity-pointer row for a linked event."""
    item: Dict[str, Any] = {
        "calendar_id": _pointer_pk(entity_type, entity_id),
        "sk": f"event#{event_id}",
        "type": _POINTER_TYPE,
        "event_id": event_id,
        "source_calendar_id": source_calendar_id,
        "name": name,
        "start_utc": start_utc,
        "end_utc": end_utc,
        "linked_entity_type": entity_type,
        "linked_entity_id": entity_id,
    }
    T.calendar.put_item(Item=item)


def delete_entity_pointer(
    *,
    entity_type: str,
    entity_id: str,
    event_id: str,
) -> None:
    """Remove the entity-pointer row (called on event delete or entity unlink)."""
    T.calendar.delete_item(Key={
        "calendar_id": _pointer_pk(entity_type, entity_id),
        "sk": f"event#{event_id}",
    })


def list_events_for_entity(
    entity_type: str,
    entity_id: str,
) -> List[Dict[str, Any]]:
    """
    Return all pointer items for the given entity.
    Callers resolve each to a full EventOut via _load_event(source_calendar_id, event_id).
    Loops via LastEvaluatedKey per the CLAUDE.md DDB pagination gotcha.
    """
    pk = _pointer_pk(entity_type, entity_id)
    items: List[Dict[str, Any]] = []
    last_key = None
    for _ in range(10):   # safety cap — prevents runaway loops
        kwargs: Dict[str, Any] = {
            "KeyConditionExpression": (
                Key("calendar_id").eq(pk) & Key("sk").begins_with("event#")
            ),
            "ScanIndexForward": True,
        }
        if last_key:
            kwargs["ExclusiveStartKey"] = last_key
        resp = T.calendar.query(**kwargs)
        items.extend(resp.get("Items", []))
        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break
    return items
```

No import of `S` settings is needed here because the flag gate lives at the router layer.

        "crm_log_and_schedule",

        entity_type=entity_type,
        entity_id=entity_id,

## 5. Detailed Behavior & Edge Cases

### 5.1 Entity-type allow-list enforcement

The allow-list (`ALLOWED_ENTITY_TYPES`) lives in `crm_entity_calendar.py` as a `frozenset`:

```python
frozenset({"contact", "lead", "account", "opportunity", "candidate", "job_order"})
```

The validation fires at the router layer for both the creation/update path and the by-entity
query. Unknown values return 422. The CND/JOB table handles are never accessed by ATI-003
itself — the link fields are opaque strings, so adding `"candidate"` and `"job_order"` to the
allow-list is safe before those clusters ship.

### 5.2 Paired-field constraint

`linked_entity_type` and `linked_entity_id` must be set together. Providing only one returns
422 with `detail="linked_entity_type and linked_entity_id must both be set or both omitted"`.
Setting both to `null`/omitting both means "no link" (not an error). Providing both as
non-null attaches the link.

### 5.3 Pointer lifecycle: update and entity-change

When an event's entity link changes (e.g., was linked to `candidate/X`, now relinked to
`contact/Y`), `update_event` must:
1. Delete the old pointer at `ENTITY#candidate#X / event#{event_id}`.
2. Write the new pointer at `ENTITY#contact#Y / event#{event_id}`.

Both writes are best-effort (`try/except`). If the old pointer delete fails, the stale
pointer stays in the old partition but the canonical event item's `linked_entity_type` and
`linked_entity_id` are updated correctly. The by-entity query for the old entity will return
the pointer but `_load_event` will find the canonical event with the new entity values and
the stale pointer will be silently skipped on next resolution (the pointer row exists but
the canonical item no longer agrees — caller code in `list_events_by_entity` resolves the
canonical item and returns it, including the new entity link fields; the stale pointer is
harmless and will be cleaned up by the eventual consistent DDB delete retry in a future
maintenance pass). This is acceptable: orphaned pointers are non-functional (they resolve to
a canonical event with a different entity) and do not affect correctness.

### 5.4 Pointer lifecycle: delete

When `delete_event` is called, the pointer is deleted in a best-effort block. If the delete
fails (transient DDB error), the stale pointer points to a now-missing canonical event. The
`list_events_by_entity` handler wraps `_load_event` in `try/except HTTPException` and silently
skips 404s, so a dangling pointer is invisible to callers.

### 5.5 `log-and-schedule`: best-effort ordering

The endpoint writes Step 1 (timeline row) first, unconditionally. If Step 2 (event creation)
fails, the timeline row is preserved and the response carries `event_created: false` with an
`error` field. This mirrors ACT-009's no-op-guard philosophy (ACT-009 §5.1): the timeline
write is the authoritative record of what happened; the calendar event is a convenience. No
rollback of a `record_crm_activity` write is ever performed.

If `record_crm_activity` itself raises (e.g., DDB unavailable), the exception propagates and
the endpoint returns 500. Neither write is atomic — the endpoint has no distributed
transaction, consistent with all other multi-table writes in the codebase.

### 5.6 `log-and-schedule`: calendar resolution

`CrmLogAndScheduleIn` includes an optional `calendar_id: Optional[str] = None` field. When
supplied, the event is created on that calendar. When omitted, the handler calls
`_resolve_default_calendar(user_sub)` which queries `T.calendar` for the first item with
`type="calendar"` and `owner_user_sub=user_sub` (using the existing calendar-listing logic).
If no calendar exists for the user, `event_created=false` and `error="no_default_calendar"`.
Supplying `calendar_id` directly is the recommended path; relying on `_resolve_default_calendar`
requires the user to have at least one calendar.

### 5.7 Flag-off behaviour

When `S.crm_activities_enabled=False` or `S.crm_activity_timeline_enabled=False`:

- `GET /ui/calendar/events/by-entity` returns 404 (via `_gate_activities()`).
- `POST /ui/crm/entities/{type}/{id}/log-and-schedule` returns 404 (via `_gate()`).
- `EventCreateIn` / `EventUpdateIn` / `EventOut` still carry `linked_entity_type` and
  `linked_entity_id` fields but they are always `None` for existing events and silently
  stored (no pointer written) when the caller supplies them — effectively a no-op. This
  keeps the additive model fields inert when the flag is off, which is safe: the pointer
  write in `create_event` is gated by `if body.linked_entity_type and body.linked_entity_id:`,
  so no extra DDB write occurs.

### 5.8 Recurrence events

`linked_entity_type` / `linked_entity_id` are stored on the parent recurring event item only.
The pointer covers the series, not individual occurrences. Occurrence overrides do not create
separate pointers. This matches the simplest correct interpretation: all occurrences of a
recurring interview are linked to the same entity.

### 5.9 `EventOut` backward compatibility

Existing callers of `EventOut` that do not read `linked_entity_type` or `linked_entity_id`
are unaffected: both fields default to `None` and legacy event items (written before ATI-003)
will have the fields absent from DDB, which `item.get("linked_entity_type")` returns as `None`.
No `model_rebuild()` call is needed for `EventOut`; the additive optional fields with `None`
defaults do not break existing serialisation.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 compliance

ATI-003 contains **no `if S.dev_mode:` branch** anywhere. `crm_entity_calendar.py` uses
`T.calendar` directly; in dev this resolves to DynamoDB Local (port 8001); in prod it
resolves to real DynamoDB. The pointer write/delete/query paths are identical. `create_event`
and `update_event` modifications call `_entity_cal.upsert_entity_pointer` / `delete_entity_pointer`
in both environments — the try/except wraps transient failures only, not an environment branch.

### 7.2 Idempotency

- **Pointer upsert**: `put_item` is unconditional. Re-creating an event pointer with the same
  `(calendar_id, sk)` key simply overwrites the existing row with the same or updated
  denormalised fields. This is safe and idempotent.
- **Pointer delete**: `delete_item` on a non-existent key is a no-op in DynamoDB. Calling
  `delete_entity_pointer` twice on the same `(entity_type, entity_id, event_id)` is safe.
- **`log-and-schedule`**: Not idempotent. Two calls create two timeline rows and (if both
  succeed) two calendar events. Callers must not retry on success; the fire-and-forget
  best-effort pattern (no retry) is the contract, per ACT-009 §5.1.

### 7.3 Security: input validation

- `entity_type` is validated against `ALLOWED_ENTITY_TYPES` (422 for unknown values) at the
  router layer — the service layer accepts any string to support future entity types added
  without a router change.
- `entity_id` is max 128 chars (422 beyond this limit) to prevent oversized DDB partition keys.
- Both fields must be set together; one without the other → 422.
- `activity_type` in `CrmLogAndScheduleIn` is validated against `_VALID_ACTIVITY_TYPES` in the
  ACT-009 router's `_gate` logic; unrecognised values return 422.
- `summary` in `CrmLogAndScheduleIn` is truncated to 200 chars by `record_crm_activity` (ACT-009
  §5.6); no error is raised on overflow.

### 7.4 Security: no money-out path

ATI-003 writes only structured strings to DynamoDB. No payment operations, no S3 writes, no
KMS calls.

### 7.5 Security: CSRF

`log-and-schedule` (POST) and `by-entity` (GET via `require_ui_session`) both use cookie
auth. POST requests require `x-csrf-token` header as enforced by `require_ui_session`
(`CLAUDE.md` CSRF section). Bearer-auth requests skip CSRF per existing platform convention.

### 7.6 Audit trail

Every successful `log-and-schedule` call emits `audit_event("crm_log_and_schedule", ...)` via
`app/services/alerts.audit_event` (line 644). Individual event creates already emit
`audit_event("calendar_event_create", ...)` in the existing `create_event` handler (line 1589).
Pointer writes are not separately audited (they are bookkeeping rows, not user-visible actions).

## 8. Backward Compatibility & Migration

### 8.1 Existing event create/update/delete callers

Existing callers of `POST /ui/calendars/{id}/events`, `PATCH /ui/calendars/{calendar_id}/events/{event_id}`,
and `DELETE /ui/calendars/{calendar_id}/events/{event_id}` pass no `linked_entity_type` or `linked_entity_id`.
The new optional fields default to `None`; the `if body.linked_entity_type and body.linked_entity_id:`

### 8.2 Existing `EventOut` consumers

`EventOut` gains two new `Optional[str]` fields defaulting to `None`. Pydantic serialises
absent DDB attributes as `None`; the JSON response now includes `"linked_entity_type": null`
and `"linked_entity_id": null` for legacy events. TypeScript consumers that use
`EventOut` will receive these fields as `null`; if they do not reference them nothing breaks.
Frontend `EventOut`-typed objects should be extended with the two optional fields in
`frontend/src/api/types.ts`.

### 8.3 No data migration

Existing event items in DDB carry no `linked_entity_type` or `linked_entity_id`. No backfill
is needed or performed. Legacy events are surfaced with both fields as `null` in `EventOut`.
No pointer rows exist for pre-ATI-003 events; querying `by-entity` for an entity that had
events linked before ATI-003 shipped returns an empty list, which is correct.

### 8.4 ACT-009 router extension

`log-and-schedule` is appended to the ACT-009 router file after the existing
`DELETE /{entity_type}/{entity_id}/activities/{sk}` route. No route conflict arises because
`log-and-schedule` uses a static suffix segment, not a path parameter.

## 10. Open Questions / Assumptions

| # | Question | Assumption / Deferral |

| OQ-1 | Should `by-entity` results be sorted by `start_utc` or by event creation order? | The pointer query uses `ScanIndexForward=True` (ascending event SK / UUID order). The link fields are opaque strings; stale IDs result in a successfully linked event that simply never appears on the entity's entity-page (if the entity is deleted). |
