# PRT-005 — Résumé upload + optional per-posting screening questionnaire

**Prefix:** `PRT` · **Area:** ATS / Public Career Portal  
**Type:** Feature · **Priority:** P1 · **Estimate:** 2d  
**Source:** `docs/opencats/ATS_CAREER_PORTAL_TICKETS.md` §PRT-005 (lines 185–215); gap: `docs/opencats/OPENCATS_GAP_ANALYSIS.md:83` ("Résumé upload from portal; per-posting screening questionnaire: PARTIAL — file manager + questionnaires exist; not wired")

---

## 1. Summary & Goal

PRT-005 adds two additive layers onto the apply flow delivered by PRT-004. Both are optional: an applicant may apply with neither, either, or both.

**(a) Résumé upload.** A dedicated public, no-auth, presign endpoint — `POST /public/careers/jobs/{slug}/resume-presign` — mints a short-lived S3 presigned PUT URL (via the existing `presign_upload` helper at `app/services/filemanager.py:2207`) that the browser client uses to upload a résumé directly to S3. The apply POST (`PRT-004`) gains an optional `resume_ticket_id`. When present, `create_application` finalises the file-manager node via `register_presigned_upload` (`filemanager.py:2264`) and attaches the resulting file path to the created Candidate via the CND-* résumé-linkage method.

**(b) Screening questionnaire.** A job order (managed by JOB-*) may carry an optional `screening_questionnaire_id`. When set, `CareerJobDetailOut.screening_questionnaire_slug` (PRT-002) surfaces the published questionnaire's slug; the browser renders the existing published-questionnaire form at `/questionnaires/published/{slug}` and submits it, obtaining a `response_session_id`. The apply POST gains an optional `screening_response_session_id`. When present, `create_application` reads the submitted answers via `REPO.list_session_answers` (`questionnaires_repository.py:573`) and stores them on the Candidate.

Neither layer adds a new DynamoDB table, a new questionnaire system, or new file-manager infrastructure. Both compose entirely from primitives already live in the codebase. Both are best-effort: a résumé-finalize failure or an answer-read failure never rolls back or blocks the candidate creation delivered by PRT-004. The feature is default-OFF (`CAREER_PORTAL_ENABLED=0`) and byte-for-byte additive.

## 2. Context & Current State

### 2.1 The gap

`docs/opencats/OPENCATS_GAP_ANALYSIS.md:83` rates this capability **PARTIAL**: "file manager + questionnaires exist; not wired." The two primitives needed are independently complete; they have simply never been joined into the apply flow.

### 2.2 Résumé upload — existing primitives (code-grounded)

**`presign_upload(user, path, *, content_type) -> dict`** (`app/services/filemanager.py:2207`).  
Validates the path is new (`require_not_exists`), generates a UUID `s3_key`, writes a ticket row to `T.filemanager` (`pk=USER#{user}`, `sk=TICKET#{ticket_id}`), and returns `{upload_url, bucket, key, ticket_id, path, content_type, name, parent}`. In dev mode (`S.dev_mode`) the URL is `/mock/s3/{bucket}/{s3_key}` (`filemanager.py:2223-2224`); in prod it is a proper presigned PUT URL generated via `_s3.generate_presigned_url` (`filemanager.py:2226-2238`). This dev/prod branching lives entirely inside `presign_upload` — PRT-005 has no `if S.dev_mode:` branch.

**`register_presigned_upload(user, path, *, s3_key, ticket_id, content_type, ...) -> dict`** (`app/services/filemanager.py:2264`).  
Validates the ticket exists and has not expired, calls `_s3.head_object` to confirm the object landed in S3, enforces quota, and creates the file-manager node (with `put_item` on `T.filemanager`). Returns `{"path": p, "size": size, "content_type": ..., "duration_seconds": ...}` — note: the return dict does **not** include `node_id` or `file_path`; it uses `"path"` (the normalized file-manager path). Step 9a must read `node.get("path")` for `resume_file_path`; `resume_node_id` is always `None` from this return and must be omitted or derived via a separate lookup if needed.

**System user pattern.** `presign_upload` accepts any string as `user`. PRT-005 passes `user="system_career_portal"` so all résumés land in the namespace `system_career_portal/objects/{obj_id}` — isolated from per-user file trees, consistent with the `"system_web_lead"` creator pattern used in LED-005 (`docs/suitecrm/specs/LED-005.md:182` — the `"system_web_lead"` value appears at line 182 in the table row; line 180 is a table separator).

**Content-type allow-list.** The résumé presign endpoint validates `content_type ∈ {"application/pdf", "application/msword", "application/vnd.openxmlformats-officedocument.wordprocessingml.document"}` (pdf / doc / docx). This is a PRT-layer guard; `presign_upload` itself accepts any content-type.

**Size guard.** `S.career_portal_resume_max_bytes` (env `CAREER_PORTAL_RESUME_MAX_BYTES`, default `10 * 1024 * 1024` — defined by PRT-001 in `app/core/settings.py` following the int-env idiom at `:821`). PRT-005 validates the client-declared `size_bytes` against this threshold before calling `presign_upload`. A client may lie about size; `register_presigned_upload` re-validates against the actual `ContentLength` from `_s3.head_object` (`filemanager.py:2297`).

**Résumé linkage on CND-*.** The CND-* Candidate entity (delivered by CND-003) exposes `add_resume(candidate_id, ...)` and `set_primary_resume(candidate_id, attachment_id, actor_sub)` in `app/services/candidates.py` (CND-003 §4). The function `attach_resume_to_candidate` **does not exist in any CND spec**; the assumed signature in Open Question §10.1 should be reconciled against CND-003's actual API when that ticket is designed. PRT-005 calls the CND résumé-attachment function only inside `try/except`, so any signature mismatch raises `TypeError` or `ImportError`, which is caught. If CND-* is absent or raises, the résumé node is still present in the file manager; only the linkage is lost. The Application row stores `resume_file_path` unconditionally so recruiters can locate the résumé even if the candidate link failed.

### 2.3 Screening questionnaire — existing primitives (code-grounded)

**`DynamoQuestionnaireRepository.get_questionnaire(questionnaire_id)`** (`app/services/questionnaires_repository.py:41`).  
Point lookup: `pk=QNR#{questionnaire_id}`, `sk=META`. Returns the questionnaire META item (including `status`, `published_version_id`, `questionnaire_id`) or `None`.

**`DynamoQuestionnaireRepository.get_published_by_slug(published_slug)`** (`app/services/questionnaires_repository.py:666`).

Used by PRT-002 to resolve the questionnaire slug for `CareerJobDetailOut.screening_questionnaire_slug`. (Line 23 is the protocol stub on the abstract class; the concrete implementation is at line 666.)

**`DynamoQuestionnaireRepository.list_session_answers(*, questionnaire_id, response_session_id)`** (`app/services/questionnaires_repository.py:573`).  
Queries `pk=QNR#{questionnaire_id}`, `sk begins_with ANSWER#{response_session_id}#`. Returns a `dict[question_id, value]` with sensitive answers KMS-decrypted on read (`kms_decrypt` at `questionnaires_repository.py:566-570`). This is the same function the LED-005 `create_lead_from_submission` spec cites at `docs/suitecrm/specs/LED-005.md:127`.

**Published questionnaire form.** The frontend submits questionnaire responses through the existing `/questionnaires/published/{slug}/sessions` → `POST /answers` → `POST /submit` pipeline (`app/routers/questionnaires.py:644-819`). PRT-005 does **not** add to this pipeline. When the applicant finishes the questionnaire, the browser has a `response_session_id` that it includes in the subsequent apply POST. No new questionnaire endpoint is needed.

**`_validate_questionnaire_link(questionnaire_id)` (CMP-005 pattern)** (`docs/suitecrm/specs/CMP-005.md:123-160`).  
Verifies `get_questionnaire(questionnaire_id)` exists and `status == "published"`. PRT-005 implements an identical inline guard in `_resolve_screening_questionnaire_slug(questionnaire_id)` (see §4.2 below). A questionnaire in `"draft"` or `"archived"` status must not surface its slug in the public job detail.

**Answers-to-entity pattern (LED-005)** (`docs/suitecrm/specs/LED-005.md:117-129`).  
LED-005's `create_lead_from_submission` calls `REPO.list_session_answers` and maps the flat `dict[question_id, value]` onto Lead fields. PRT-005 adapts this pattern to Candidate: the raw answers dict is stored on the Candidate row (as `screening_answers`) rather than being field-mapped. Field-mapping is deferred to recruiter review — it is not enforced at apply time.

## 3. Data Model

### 3.1 No new DynamoDB table

PRT-005 introduces no new table and no new GSI. All changes are additive sparse attributes on existing rows.

**`T.career_portal`** (`CareerPortal` table, introduced by PRT-001, key schema `pk` (S) / `sk` (S)):

New sparse attributes on the **Application row** (`pk=APPLICATION#{application_id}`, `sk=META`; schema established by PRT-004 §3.2):

| Attribute | DDB type | Notes |
|---|---|---|
| `resume_ticket_id` | S, absent if no résumé | Ticket ID returned by `presign_upload`; stored pre-finalize for traceability |
| `resume_file_path` | S, absent if no résumé | Finalized file-manager path (e.g. `/career-portal/resumes/{job_order_id}/{uuid}.pdf`); set by `register_presigned_upload` after confirmation |
| `resume_node_id` | S, absent if not finalized | File-manager node ID; set alongside `resume_file_path` |
| `resume_linked` | BOOL, absent if no résumé | `True` once `attach_resume_to_candidate` succeeds; absent / False if candidate link failed |
| `screening_response_session_id` | S, absent if not provided | Forwarded from apply request; stored for audit |
| `screening_questionnaire_id` | S, absent if not provided | Resolved at apply time from the job order; stored alongside answers |
| `screening_answers` | M (map), absent if not provided | Flat `{question_id: value}` dict returned by `list_session_answers`; stored verbatim |
| `screening_answers_stored_at` | N, absent | `now_ts()` at the point answers were read and stored |

All new attributes are **sparse**: absent for applications submitted without a résumé or questionnaire. This follows the standard DynamoDB sparse attribute pattern used throughout the codebase (e.g., `assigned_admin_sub` on KYC case items — `scripts/local-ddb-init.py:156`).

**No `attr_types` change required.** The new attributes are either non-indexed strings, booleans, or maps. Only the pre-existing `GSI1SK` (numeric `created_at`) required `attr_types`, and that is already declared in the PRT-004 `TableDef`.

**`T.questionnaires`** (managed by the questionnaires subsystem, `app/services/questionnaires_repository.py`): No schema change. PRT-005 reads from this table via `REPO.list_session_answers` and `REPO.get_questionnaire`; it never writes to it.

**`T.filemanager`** (managed by `app/services/filemanager.py`): No schema change. `presign_upload` writes a ticket row and `register_presigned_upload` writes the node row using the existing schema; PRT-005 is a caller only.

### 3.2 `REPO` singleton

PRT-005 uses the module-level `REPO = DynamoQuestionnaireRepository()` singleton already instantiated at the top of `app/routers/questionnaires.py` (or an equivalent module-level instance in `app/services/career_portal.py`). ### 4.2 Service functions — `app/services/career_portal.py`

#### `presign_resume_upload(*, slug, data, source_ip) -> CareerResumePresignOut`

```python
def presign_resume_upload(
    *,
    slug: str,
    data: CareerResumePresignIn,
    source_ip: str,
) -> CareerResumePresignOut:
```

**Step 1 — Flag guard.** `_require_enabled()`.

**Step 2 — Honeypot.** `if data.honeypot: return CareerResumePresignOut(upload_url="", ticket_id="bot", key="", path="", content_type="")`. Fake response; no DDB write or rate-limit increment.

**Step 3 — Rate limit.** Same gate as `create_application`: `_bucket_limit(f"ip#{_ip_prefix(source_ip)}", "rl#career_apply", S.career_portal_apply_rate_limit_per_ip_per_hour, 3600)` → `HTTPException(429)` on breach. The presign and apply endpoints share the same rate-limit bucket so a bot cannot bypass the apply limit by hammering presign instead.

**Step 4 — Slug resolution.** Point-read `SLUG#{slug}` row from `T.career_portal` → extract `job_order_id`. Missing slug → `HTTPException(404)`.

**Step 5 — Content-type validation.** `if data.content_type not in _CAREER_RESUME_ALLOWED_TYPES: raise HTTPException(415, {"code": "unsupported_content_type", ...})`.

**Step 6 — Size validation.** `if data.size_bytes > S.career_portal_resume_max_bytes: raise HTTPException(413, {"code": "file_too_large", "max_bytes": S.career_portal_resume_max_bytes})`.

**Step 7 — Build file-manager path.**
```python
ext_map = {
    "application/pdf": "pdf",
    "application/msword": "doc",
    "application/vnd.openxmlformats-officedocument.wordprocessingml.document": "docx",
}
ext = ext_map[data.content_type]
obj_id = uuid4().hex
path = f"/career-portal/resumes/{job_order_id}/{obj_id}.{ext}"
```

**Step 8 — Presign.** Lazy-import `presign_upload` and call synchronously:
```python
from app.services.filemanager import presign_upload
result = presign_upload(
    user="system_career_portal",
    path=path,
    content_type=data.content_type,
)
```

**Step 9 — Return.**
```python
return CareerResumePresignOut(
    upload_url=result["upload_url"],
    ticket_id=result["ticket_id"],
    key=result["key"],
    path=result["path"],
    content_type=result["content_type"],
)
```

#### `_resolve_screening_questionnaire_slug(questionnaire_id) -> Optional[str]`

**This function is already defined by PRT-002 in `app/services/career_portal.py`.** PRT-005 reuses PRT-002's implementation unchanged. This would return the `questionnaire_id` string instead of the actual published slug for questionnaires that were published with a custom slug (i.e. where `published_slug != questionnaire_id`). The PRT-002 implementation via `get_version_by_id(...).get("published_slug")` is the correct approach and must not be overridden.

PRT-005 adds no new questionnaire-resolution logic. PRT-002 must land before PRT-005.

## 5. Detailed Behavior & Edge Cases

### 5.1 Résumé presign — path collision

`presign_upload` calls `require_not_exists(user, path)` (`filemanager.py:2212`), which raises `HTTPException(409)` if the file-manager node already exists at that path. Because the path includes a UUID (`obj_id = uuid4().hex`), collisions are astronomically unlikely. If one occurs (e.g., a test environment restart with the same seed), the 409 propagates to the caller as a 409. This is correct behavior; the client should request a new presign.

### 5.2 Ticket expiry

`presign_upload` sets `expires_at = now + 15 minutes` (`filemanager.py:2217`). `register_presigned_upload` checks this at finalize time (`filemanager.py:2292-2294`). An applicant who takes more than 15 minutes between presigning and calling apply will receive an `HTTPException(403, "upload ticket expired")` from the finalize step. Because finalize is wrapped in `try/except`, the application is **not** blocked — it proceeds without the résumé, and `resume_file_path` remains `None`. PRT-005 does not increase the ticket TTL; 15 minutes is standard for the platform.

### 5.3 Résumé already present in S3 but finalize fails

If `head_object` returns the wrong metadata (e.g., `filemgr-ticket` mismatch), `register_presigned_upload` raises `HTTPException(403, "uploaded object metadata mismatch")`. This is caught by the `try/except` in Step 9a and the application proceeds without the résumé. The orphaned S3 object is left in place (no rollback). A lifecycle rule on the S3 bucket (operational concern, outside PRT scope) cleans up orphaned objects.

### 5.4 Screening answers for a wrong / stale session

`list_session_answers` (`questionnaires_repository.py:573`) returns an empty dict if no answer rows exist for the given session. It never raises on a missing session — it simply returns `{}`. An empty dict is stored as `screening_answers: {}` if the session is provided but has no answers. This is not treated as an error; the recruiter sees an empty answers map and can re-request the questionnaire.

If the `response_session_id` belongs to a different questionnaire than the one linked to the job order, `list_session_answers` queries `pk=QNR#{q_id}` scoped to the correct questionnaire. An unmatched session will return an empty dict (no rows match the prefix `ANSWER#{wrong_session_id}#`). The cross-session attack surface is therefore narrow: answers are always read from the questionnaire linked to the job order, not from any questionnaire the applicant designates.

### 5.5 Draft or unpublished screening questionnaire

`_resolve_screening_questionnaire_slug` checks `item.get("status") == "published"` before returning the slug. A draft or archived questionnaire returns `None`, and `CareerJobDetailOut.screening_questionnaire_slug` is `null` in the API response. The apply endpoint does not enforce that a `screening_response_session_id` was provided even when the posting has a questionnaire — it is optional. Mandatory questionnaires are a JOB-* and frontend concern, not enforced in the apply path.

### 5.6 CND-* `attach_resume_to_candidate` absent at runtime

When the CND-* module is not yet deployed, the lazy import in Step 9b raises `ImportError`, which is caught. The résumé is finalized in the file manager (`resume_file_path` is set on the Application row) but `resume_linked = False`. The résumé is not lost; it can be linked manually or re-processed when CND-* ships.

### 5.7 Oversize declared but undersized uploaded

The presign validates `data.size_bytes <= S.career_portal_resume_max_bytes`. `register_presigned_upload` uses the actual `ContentLength` from `head_object`. A client that declares a small size but uploads a large file will pass the presign guard but fail in `_enforce_upload_and_storage_quotas` (`filemanager.py:2308-2314`), which is inside the `try/except` of Step 9a. The application proceeds without the résumé.

### 5.8 Multiple presign calls for the same application

An applicant may call `resume-presign` multiple times (e.g., to change the file before submitting). Each call generates a new UUID path and a new ticket. The apply POST uses exactly one `resume_ticket_id`. Unused tickets expire after 15 minutes via the `expires_at` field; the corresponding S3 objects become orphans cleaned up by the lifecycle rule.

### 5.9 `screening_answers` DynamoDB type

DynamoDB natively supports the `M` (map) type. The answers dict from `list_session_answers` is a flat `dict[str, Any]` where values may be strings, numbers, booleans, or lists (depending on question types). All are DynamoDB-serializable via boto3's standard type serializer. Nested maps or sets are valid. No transformation is needed before `put_item`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

PRT-005 contains no `if S.dev_mode:` branch. The only environment-determined behavior difference is the `upload_url` format returned by `presign_upload` (`filemanager.py:2223-2238`): `/mock/s3/{bucket}/{s3_key}` in dev, a proper AWS presigned URL in prod. This branching lives entirely inside `presign_upload` — PRT-005 passes through the URL unchanged. DynamoDB I/O, questionnaire reads, rate-limit writes, and audit events execute identically in both environments (SECOPS-007 parity requirement from `ATS_CAREER_PORTAL_TICKETS.md:26`).

### 7.2 Idempotency

The resume-presign endpoint is **not idempotent**: each call mints a new ticket and a new S3 path. This is intentional and safe — repeated calls by the same browser generate short-lived tickets that auto-expire.

The apply endpoint inherits PRT-004's idempotency behavior: the Application row uses a generated `application_id` (`"app_" + uuid4().hex[:20]`), so retried applies create new Application rows. CND-* is expected to deduplicate by email (`CND-002` idempotent-on-email provision). PRT-005 does not change this behavior.

### 7.3 Honeypot on both endpoints

Both `presign_resume_upload` and `create_application` check the honeypot field (Step 2 in both). A bot that calls presign with a non-empty honeypot receives a fake success (`ticket_id="bot"`) and then calls apply, where the honeypot check fires again. Two independent traps reduce the chance that a sophisticated bot passes one but not both.

### 7.4 PII handling

Résumés contain PII (name, address, employment history). The file-manager path `/career-portal/resumes/{job_order_id}/{uuid}.ext` is opaque; no PII appears in the S3 key. The system user `"system_career_portal"` owns the namespace, preventing candidate-to-candidate cross-access via the file manager. Screening answers may contain sensitive data (address, date fields). `list_session_answers` applies KMS decryption for fields marked `value_encrypted=True` (`questionnaires_repository.py:586-587`) before returning the dict; PRT-005 stores the decrypted values in the Application row (map type in DDB). At-rest DDB encryption (AWS-managed KMS) applies to the `CareerPortal` table. The stored `source_ip` is always the last-octet-**truncated** anonymized form via `_ip_prefix` (`rate_limit.py:84-91`): for IPv4 `"a.b.c.d"` this returns `"a.b.c"` (three octets; the fourth is dropped, not zeroed). Raw IP is never persisted.

### 7.5 S3 upload security

The presigned URL is scoped to a single `PUT` on a specific `s3_key` with a 15-minute expiry. S3 enforces that only the declared `ContentType` and the metadata set at presign time are accepted. `register_presigned_upload` validates the `filemgr-ticket` and `filemgr-user` metadata fields on the uploaded object (`filemanager.py:2302-2303`) before accepting the finalize. A malicious actor cannot substitute a different file by reusing an expired ticket or a ticket belonging to a different user.

### 7.6 Rate-limit shared bucket

The resume-presign and apply endpoints share the `"rl#career_apply"` bucket keyed on the anonymized IP. This means the combined rate is `S.career_portal_apply_rate_limit_per_ip_per_hour` presign+apply calls total, not per-endpoint. An operator who wants a higher presign limit (e.g., to allow re-uploads) can set `CAREER_PORTAL_RESUME_PRESIGN_RATE_LIMIT_PER_IP_PER_HOUR` as a future extension without touching the apply budget.

## 8. Backward Compatibility & Migration

### 8.1 No breaking changes

All additions are backward-compatible:

- `CareerApplyIn` gains two new optional fields (`resume_ticket_id`, `screening_response_session_id`) with `None` defaults. Existing clients sending the PRT-004 shape work unchanged.
- The Application row gains new sparse attributes. Existing rows (written by PRT-004 before PRT-005 is deployed) simply lack these attributes; `item.get("resume_file_path")` returns `None`, which is the same as "no résumé". No migration of existing rows is needed.
- `CareerJobDetailOut.screening_questionnaire_slug` is already optional in PRT-002 (`Optional[str] = None`). Its value remains `None` for postings with no linked questionnaire.

### 8.2 DynamoDB table migration

No table structural change (no new GSI, no new attribute type declaration). `alter table` is not a DynamoDB concept for adding sparse attributes.

### 8.3 File-manager namespace pre-creation

**`ensure_folder_exists(owner, folder_path)` (`filemanager.py:2926`) does NOT create folders** — it raises `HTTPException(400, "parent folder does not exist")` if the folder is absent. `presign_upload` calls it at line 2211. Consequently, the first call to `presign_upload("system_career_portal", "/career-portal/resumes/{job_order_id}/{uuid}.pdf", ...)` will fail with HTTP 400 unless the parent directories already exist in the `system_career_portal` file-manager namespace.

The correct approach is to call `_auto_create_parents(user, parent)` (`filemanager.py:3889`) before calling `presign_upload`, or to call `presign_upload` via a thin wrapper that invokes `_auto_create_parents` first. Alternatively, a one-time startup/seeding script can pre-create the `/career-portal/` and `/career-portal/resumes/` top-level folders. Job-order-specific sub-folders (`/career-portal/resumes/{job_order_id}/`) must also be created on first use since `ensure_folder_exists` will raise for each new job_order_id sub-path.

Recommended pattern in `presign_resume_upload` (after Step 7 path construction, before Step 8):
```python
from app.services.filemanager import _auto_create_parents
_auto_create_parents("system_career_portal", f"/career-portal/resumes/{job_order_id}/")
```
This is idempotent (a no-op for already-existing folders) and does not affect dev/prod parity.

### 8.4 Deployment ordering

PRT-005 has two forward dependencies not yet built: CND-* `attach_resume_to_candidate` and JOB-* `get_screening_questionnaire_id`. Both are called only inside `try/except` blocks. Deploying PRT-005 before CND-* or JOB-* ships is safe: the functions raise `ImportError`, which is caught, and the application proceeds without those enrichments. The platform is never in a broken state.

## 10. Open Questions / Assumptions

1. **`attach_resume_to_candidate` function name and signature.** This spec assumes CND-002 delivers `attach_resume_to_candidate(candidate_id: str, file_path: str, node_id: Optional[str]) -> None` in `app/services/candidates.py`. If CND-002 uses a different name (e.g. `set_primary_resume`), the call site in Step 9b must be updated to match.

2. **`get_screening_questionnaire_id` on JOB-*.** PRT-005 assumes JOB-* provides `get_screening_questionnaire_id(job_order_id: str) -> Optional[str]` that returns the linked questionnaire ID or `None`. The exact function name and location (service vs. router) must be confirmed when JOB-* is designed.

3. **`screening_answers` storage size.** DynamoDB item size limit is 400 KB. A questionnaire with many large text answers could approach this limit when stored in the Application row map. If this becomes a concern, answers should be stored in a separate `ANSWERS#{application_id}` row with `pk=APPLICATION#{application_id}`, `sk=ANSWERS#{session_id}`. For v1, inline storage in the map is assumed to be within limits (questionnaires are structured forms, not essay exams).

4. **Résumé antivirus scan.** This spec does not include an antivirus or malware scan on uploaded résumés. If required, a post-finalize async scan (triggering on S3 PutObject event or as a background task) should be designed separately. PRT-005 does not block on any such scan.

5. **Résumé download by recruiters.** The Application row stores `resume_file_path` in the `system_career_portal` file-manager namespace. Recruiters accessing the résumé will need an admin file-manager endpoint or a dedicated `GET /ui/admin/career-portal/applications/{id}/resume` endpoint that generates a presigned download URL from the stored path. This is deferred to a future admin-view ticket (PRT-* admin surface, outside PRT-005 scope).

6. **Answer schema validation.** PRT-005 stores answers verbatim without validating them against the questionnaire schema. A future enhancement could validate required questions or question types. Not in scope here.
