# RSK-006 — Candidate hot-lists / named shortlists + quick-add-from-résumé

**Type:** Feature · **Priority:** P2 · **Estimate:** 2 days  
**Cluster:** ATS Résumé / Skills (RSK) — Terminal ticket  
**Source:** `docs/opencats/ATS_RESUME_SKILLS_TICKETS.md` §RSK-006 + `docs/opencats/OPENCATS_GAP_ANALYSIS.md` §A (line 51), §D  
**Depends on:** CND-001 (table, flag, settings, models), CND-002 (candidate CRUD), CND-003 (résumé attachment + S3), RSK-002 (text extraction), RSK-003 (full-text index), RSK-001 (skill assignment, optional)

## 1. Summary & Goal

`docs/opencats/OPENCATS_GAP_ANALYSIS.md:51` (§A) states:

> Candidate hot-list / quick-add-from-résumé — **MISSING** — no shortlist concept.

OpenCATS lets recruiters maintain named **hot-lists** (saved shortlists) of candidate records for bulk actions: bulk email campaigns, bulk pipeline additions, and CSV export. Today the `candidates` table (owned by CND-001) stores individual records but offers no grouping surface, no named list concept, and no way to associate a set of candidates with a recruiter-defined label. A recruiter who wants to track "Shortlist for Client Acme Q3" or "Python senior pool 2026" must manage that list outside the system.

RSK-006 delivers two tightly coupled features:

1. **Named hot-lists** — named, owner-scoped sets of candidate references with per-member metadata (`added_by`, `added_at`), a running `member_count` counter, an optional `is_shared` flag for cross-recruiter visibility, and full CRUD including bulk-add.

2. **Quick-add-from-résumé** — a single-endpoint flow that accepts a raw résumé file upload (PDF or DOCX), creates a stub candidate record, stores the résumé in S3 via the CND-003 attachment path, triggers RSK-002 text extraction, writes the RSK-003 search index, and optionally drops the new candidate onto a target hot-list — all in one round-trip. Each enrichment step is best-effort: a parse failure yields a usable candidate stub, not an error response.

Both features are entirely additive, gated by `S.candidates_enabled` (owned by CND-001), and produce zero behavioral change with the flag off. No new DynamoDB table is introduced: all row types live on the `candidates` table (single-table design).

### 2.3 `candidates` table single-table design (CND-001, CND-003)

`docs/opencats/specs/CND-001.md` §3.1 defines the `candidates` table as `PK=pk` / `SK=sk` single-table. Current SK prefix space: `"META"` (candidate record), `"ATTACHMENT#{attachment_id}"` (CND-003 résumé sub-item), `"ACTIVITY#{inverted_ts}#{activity_id}"` (CND-004 fallback). RSK-006 adds three new prefix families: `"HOTLIST#{list_id}"` (hot-list META), `"MEMBER#{candidate_id}"` (membership forward row), and `"HOTLIST#{list_id}"` on `pk="CANDIDATE#{candidate_id}"` (reverse row). None of these prefixes are a prefix-of or equal to any existing prefix.

CND-001 `TableDef` (`docs/opencats/specs/CND-001.md` §3.4) already declares three GSIs: `ByOwner` (GSI1), `ByStatus` (GSI2), `BySource` (GSI3), all with `attr_types={"GSI1SK": "N", "GSI2SK": "N", "GSI3SK": "N"}`. Note: `"created_at": "N"` does NOT appear in CND-001's `attr_types` — `created_at` is a plain item attribute (not a GSI sort key alias) and must not appear in `attr_types` (see CLAUDE.md and CND-001 §3.4 verification entry #21). RSK-006 adds a fourth GSI — `ByHotlistOwner` (GSI4) — to support "my lists" queries. The `TableDef` entry for the `candidates` table must be **extended in-place** with this GSI and `attr_types={"GSI4SK": "N"}` added.

### 2.4 Dual-row forward/reverse membership pattern

The bidirectional write technique is established in two places:

- `docs/opencats/specs/RSK-001.md` §3 — `SKILL#→ENTITY#` forward rows and `ENTITY#→SKILL#` reverse rows in the `ats_skills` table, written in a single `batch_writer()` call. RSK-001 §3.1.1 line 116 explicitly calls this the "dual-row technique" and states it is "the same approach used by LED-009 §3 and newsfeed `_write_tag_index`."
- `app/routers/newsfeed.py:440` — `_write_tag_index` uses `batch_writer()` to write forward and stats rows, establishing the batch-writer + counter-increment pattern.

Note: LED-009 §3 (`docs/suitecrm/specs/LED-009.md`) describes adding the ByPhone GSI5 for duplicate *detection* via index lookups — it does not itself introduce a dual-row write pattern. The cross-referencing attribution comes from RSK-001 §3.1.1 which cites LED-009 §3 as prior art; the dual-row write pattern RSK-006 actually reuses is from RSK-001.

RSK-006 applies the same technique: a forward membership row (`pk="HOTLIST#{list_id}"`, `sk="MEMBER#{candidate_id}"`) enables "list all members of list L" queries; a reverse row (`pk="CANDIDATE#{candidate_id}"`, `sk="HOTLIST#{list_id}"`) enables "list all lists containing candidate C" queries — both via primary-key lookups, zero scans.

### 2.5 `member_count` counter-increment pattern (`app/routers/newsfeed.py:440`)

`app/routers/newsfeed.py:453–459` uses `update_item` with `UpdateExpression="SET #n = if_not_exists(#n, :z) + :one"` for `TAG_STATS` counters. RSK-006 applies the same DynamoDB `ADD` expression pattern to increment `member_count` on the hot-list META row atomically:

```python
UpdateExpression="ADD member_count :one",
ExpressionAttributeValues={":one": Decimal(1)},
```

Decrement uses `":negone": Decimal(-1)` with a conditional expression `member_count > :z` to floor at zero — the same floor-zero pattern described in `docs/opencats/ATS_RESUME_SKILLS_TICKETS.md` §RSK-006.

### 2.6 Cursor-based pagination (`app/core/cursor.py:94`)

`app/core/cursor.py:94` defines `encode_cursor(last_evaluated_key)` and `decode_cursor(cursor)`. These HMAC-signed opaque tokens are the canonical pagination mechanism used throughout the platform (confirmed in `app/services/tickets.py`, `app/services/questionnaires_repository.py`, `app/services/leads.py`). `list_members` uses them for paginated membership scans.

### 2.7 Multipart upload + size guard (`app/routers/newsfeed.py:3114`)

`app/routers/newsfeed.py:3114` guards file uploads with a `_MAX_UPLOAD_BYTES = 10 * 1024 * 1024` check. `app/routers/kyc_partner_api.py:186` uses FastAPI's `UploadFile` with `await file.read()` for multipart forms. The `quick_add_from_resume` endpoint follows both patterns: `UploadFile` for the multipart part, then an explicit byte-length guard before processing.

### 2.8 CND-003 résumé attachment path

`docs/opencats/specs/CND-003.md` §4.1 defines the service functions. The function for uploading résumé bytes is `add_resume(candidate_id, *, uploaded_by, filename, content_type, size_bytes, s3_key, s3_bucket, source="upload", make_primary=False) -> dict`. ## 3. Data Model

### 3.1 No new table — all rows on `candidates`

RSK-006 introduces **zero new DynamoDB tables**. All new row types live on the `candidates` table (owned by CND-001, `T.candidates`), following the same single-table pattern used by CND-003 attachments, CND-004 activities, and RSK-003 token rows.

### 3.2 New row types

#### Hot-list META row

One row per hot-list.

| Attribute | DDB Type | Value / Notes |
|---|---|---|
| `pk` | S | `"HOTLIST#{list_id}"` — e.g. `"HOTLIST#hl_a1b2c3d4e5f6"` |
| `sk` | S | `"META"` |
| `list_id` | S | `"hl_" + uuid4().hex[:20]` — generated at create time |
| `name` | S | Recruiter-supplied display name; max 500 chars |
| `owner_sub` | S | `user_sub` of the creating recruiter |
| `member_count` | N | Running counter; defaults to `0`; incremented/decremented atomically |
| `is_shared` | BOOL | `False` by default; `True` makes the list visible to all recruiters (not just owner) |
| `created_at` | N | `now_ts()` — Unix epoch integer |
| `updated_at` | N | `now_ts()` at last mutation |
| `GSI4PK` | S | `"HOTLIST_OWNER#{owner_sub}"` |
| `GSI4SK` | N | `created_at` — numeric sort key for newest-first ordering |

#### Membership forward row

One row per `(list_id, candidate_id)` pair.

| Attribute | DDB Type | Value / Notes |
|---|---|---|
| `pk` | S | `"HOTLIST#{list_id}"` |
| `sk` | S | `"MEMBER#{candidate_id}"` |
| `candidate_id` | S | The referenced candidate |
| `added_by` | S | `user_sub` who added this candidate to the list |
| `added_at` | N | `now_ts()` |

#### Reverse membership row

One row per `(candidate_id, list_id)` pair — enables the "what lists is candidate C on?" query.

| Attribute | DDB Type | Value / Notes |
|---|---|---|
| `pk` | S | `"CANDIDATE#{candidate_id}"` |
| `sk` | S | `"HOTLIST#{list_id}"` |
| `list_id` | S | |
| `name` | S | Denormalized list name — so the candidate detail view does not require a second lookup |
| `added_at` | N | `now_ts()` |

This row sits alongside the candidate's `sk="META"` row, `sk="ATTACHMENT#…"` rows, and `sk="RESUME_TOKEN#…"` rows (RSK-003) on the same `pk="CANDIDATE#{candidate_id}"` partition — fully within the single-table design.

### 3.3 New GSI — `ByHotlistOwner` (GSI4)

| Attribute | Value |
|---|---|
| Index name | `ByHotlistOwner` |
| Partition key | `GSI4PK` (S) — value `"HOTLIST_OWNER#{owner_sub}"` |
| Sort key | `GSI4SK` (N) — value `created_at` |
| Projection | `ALL` |

This index supports `list_hotlists(owner_sub)` — returning all hot-lists owned by a recruiter, sorted newest-first — without scanning the full table.

**Critical:** `GSI4SK` is a numeric sort key. The `TableDef` entry for the `candidates` table in `scripts/local-ddb-init.py` must be extended with `{"index_name": "ByHotlistOwner", "partition_key": "GSI4PK", "sort_key": "GSI4SK"}` in the `gsi` list, and `"GSI4SK": "N"` added to `attr_types`. Omitting this causes `ValidationException` at query time (CLAUDE.md "DynamoDB numeric GSI sort keys"; confirmed via `users` table at `scripts/local-ddb-init.py:49–54` which declares `attr_types={"kyc_tier": "N", "kyc_tier_updated_at": "N"}`).

The extended `TableDef` becomes:

```python
TableDef(
    _resolve_table_name(S.candidates_table_name, "candidates"),
    "pk",
    "sk",
    gsi=[
        {"index_name": "ByOwner",         "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "ByStatus",        "partition_key": "GSI2PK", "sort_key": "GSI2SK"},
        {"index_name": "BySource",        "partition_key": "GSI3PK", "sort_key": "GSI3SK"},
        {"index_name": "ByHotlistOwner",  "partition_key": "GSI4PK", "sort_key": "GSI4SK"},
    ],
    attr_types={
        "GSI1SK": "N",
        "GSI2SK": "N",
        "GSI3SK": "N",
        "GSI4SK": "N",
        # NOTE: "created_at": "N" must NOT be included here. `created_at` is a plain
        # item attribute, not a GSI sort key (the sort keys are aliased as GSI1SK..GSI4SK).
        # Including a non-key attribute in attr_types causes DynamoDB to raise
        # ValidationException (confirmed by CND-001 spec §3.4 verification entry #21 and
        # _attribute_definitions at scripts/local-ddb-init.py:2496-2506).
    },
),
```

## 4. API / Service Design

### 4.1 Service layer — `app/services/candidate_hotlists.py` (new file)

All functions accept and return plain `dict` objects (not Pydantic models), following the leads/contacts service convention. All are synchronous; async callers dispatch via `asyncio.to_thread` where needed.

#### `create_hotlist(owner_sub: str, name: str, *, is_shared: bool = False) -> dict`

1. Generate `list_id = "hl_" + uuid4().hex[:20]`.
2. Build META item: `pk="HOTLIST#{list_id}"`, `sk="META"`, all attributes from §3.2.
3. `T.candidates.put_item(Item=meta_item)`.
4. `audit_event("ats.hotlist.created", owner_sub, list_id=list_id, name=name)`.
5. Return the META item dict.

Idempotency: `list_id` is UUID-derived; two concurrent `create_hotlist` calls never produce the same `list_id`. No conditional expression required.

#### `get_hotlist(list_id: str) -> dict | None`

`T.candidates.get_item(Key={"pk": f"HOTLIST#{list_id}", "sk": "META"}).get("Item")`.

#### `list_hotlists(owner_sub: str, *, include_shared: bool = False) -> list[dict]`

Query `ByHotlistOwner` GSI: `KeyConditionExpression=Key("GSI4PK").eq(f"HOTLIST_OWNER#{owner_sub}")`, `ScanIndexForward=False` (newest-first), loop `LastEvaluatedKey`. When `include_shared=True`, additionally query `GSI4PK="HOTLIST_OWNER#*"` is not feasible without a scan; instead, for shared-list discovery a separate `list_shared_hotlists()` function runs a scan with `FilterExpression=Attr("is_shared").eq(True) & Attr("sk").eq("META")` — only called explicitly by admins, never in the hot path.

#### `update_hotlist(list_id: str, actor_sub: str, *, name: str = None, is_shared: bool = None) -> dict`

Owner-only. Builds a partial `update_item` expression for whichever fields are non-None, adds `updated_at = now_ts()`. Returns the updated META item via `get_hotlist`.

#### `delete_hotlist(list_id: str, actor_sub: str) -> None`

1. Query all `MEMBER#` rows: `pk="HOTLIST#{list_id}"`, `begins_with(sk, "MEMBER#")`, loop `LastEvaluatedKey`.
2. For each membership forward row: delete both the forward row AND the reverse row (`pk="CANDIDATE#{candidate_id}"`, `sk="HOTLIST#{list_id}"`) in a `batch_writer()`.
3. Delete the META row.
4. `audit_event("ats.hotlist.deleted", actor_sub, list_id=list_id)`.

Cascade deletion prevents orphaned reverse rows on candidates. The batch writer handles up to 25 items per batch; pages of membership rows are processed in batches of 25. For very large lists (> 500 members) the delete loops over pages — callers must tolerate a slow delete for large lists. A `max_delete_pages` guard (default 200 pages × 50 items = 10 000 members) protects against runaway deletes; beyond that threshold the function raises `HTTPException(400, "list too large to delete via API; use admin tooling")`.

#### `add_to_hotlist(list_id: str, candidate_id: str, actor_sub: str) -> bool`

1. Check if forward row already exists via `get_item` — if present, return `False` (already member, no-op).
2. Write both rows in a `batch_writer()` context.
3. `T.candidates.update_item(Key={"pk": f"HOTLIST#{list_id}", "sk": "META"}, UpdateExpression="ADD member_count :one", ...)`.
4. Return `True` (newly added).

Idempotency: the existence check at step 1 makes re-add a clean no-op without double-counting.

#### `remove_from_hotlist(list_id: str, candidate_id: str, actor_sub: str) -> bool`

1. Delete forward row.
2. Delete reverse row.
3. Conditional decrement: `UpdateExpression="ADD member_count :neg", ConditionExpression="member_count > :z"` with `:neg = Decimal(-1)`, `:z = Decimal(0)`. Catch `ConditionalCheckFailedException` silently (already at zero).
4. Return `True`.

#### `bulk_add_to_hotlist(list_id: str, candidate_ids: list[str], actor_sub: str) -> dict`

Calls `add_to_hotlist` per `candidate_id`. Maintains `added` / `skipped` counters. Returns `{"added": N, "skipped": M}`. Input is capped at 200 IDs by the Pydantic model (`BulkAddIn.candidate_ids` has `max_length=200`).

#### `list_members(list_id: str, *, cursor: str | None = None, limit: int = 50) -> dict`

```
KeyConditionExpression = Key("pk").eq(f"HOTLIST#{list_id}") & Key("sk").begins_with("MEMBER#")
ScanIndexForward = False   # newest-first by DynamoDB natural sort
Limit = min(limit, 100)
ExclusiveStartKey = decode_cursor(cursor) or absent
```

Returns `{"members": [HotlistMemberOut dicts], "cursor": encode_cursor(last_key) or None}`.

#### `list_candidate_hotlists(candidate_id: str) -> list[dict]`

Query reverse rows: `pk="CANDIDATE#{candidate_id}"`, `begins_with(sk, "HOTLIST#")`, loop `LastEvaluatedKey`. Returns list of `{"list_id", "name", "added_at"}` dicts.

#### `quick_add_from_resume(owner_sub: str, raw_bytes: bytes, filename: str, *, list_id: str | None = None) -> dict`

This is the orchestrating function for the quick-add flow. Each step is wrapped in `try/except` so that a failure in any enrichment step still yields a usable result:

```python
def quick_add_from_resume(owner_sub, raw_bytes, filename, *, list_id=None):
    # Step 1: Create stub candidate (CND-002)
    # NOTE: CND-002 signature is create_candidate(creator_sub, data: CandidateCreateIn).
    # source="import": this value is ALREADY in CND-001's CANDIDATE_SOURCES frozenset and
    # the CandidateCreateIn.source pattern regex (CND-001 §3.6 / §4.2 line 227:
    # ^(direct|referral|job_board|linkedin|agency|career_portal|import|other)$). Reusing it
    # avoids any cross-ticket CND-001 regex extension — a résumé quick-add is an import of a
    # candidate from an uploaded file. (See §10.1.)
    from app.services.candidates import create_candidate
    from app.models import CandidateCreateIn
    stub_name = _stem_from_filename(filename) or "Unparsed Candidate"
    first, _, last = stub_name.partition(" ")
    candidate = create_candidate(
        owner_sub,
        CandidateCreateIn(
            first_name=first or stub_name,
            last_name=last or "—",
            email=f"resume-import-{uuid4().hex[:8]}@placeholder.invalid",
            source="import",  # valid in CND-001 CANDIDATE_SOURCES — no regex extension needed
            owner_sub=owner_sub,
        ),
    )
    candidate_id = candidate["candidate_id"]

    # Step 2: Store résumé via CND-003
    # CND-003 separates the S3 put_object (router-side) from the DDB metadata write
    # (add_resume service call). The quick-add service function must replicate this
    # two-step pattern: put to S3 first, then call add_resume with s3_key/s3_bucket.
    attachment_id = None
    try:
        from app.core.aws_clients import s3_client as _s3_factory
        from app.core.settings import S
        from app.services.candidates import add_resume as _add_resume
        safe_name = re.sub(r"[^A-Za-z0-9._-]", "_", filename or "resume")[:255]
        s3_key = f"{S.candidate_resume_s3_prefix}{candidate_id}/tmp/{safe_name}"
        s3_bucket = S.candidate_resume_bucket
        ct = _detect_content_type(filename)  # helper: "application/pdf" or "application/vnd.openxmlformats..."
        _s3_factory().put_object(Bucket=s3_bucket, Key=s3_key, Body=raw_bytes, ContentType=ct)
        att = _add_resume(
            candidate_id,
            uploaded_by=owner_sub,
            filename=filename or "resume",
            content_type=ct,
            size_bytes=len(raw_bytes),
            s3_key=s3_key,
            s3_bucket=s3_bucket,
            source="upload",
        )
        attachment_id = att["attachment_id"]
    except Exception:
        pass

    # Step 3: Extract text (RSK-002) — best-effort
    extraction_status = None
    try:
        from app.services.resume_extraction import extract_resume_text
        if attachment_id:
            result = extract_resume_text(
                candidate_id, attachment_id,
                raw_bytes=raw_bytes, actor_sub=owner_sub,
            )
            extraction_status = result.get("extraction_status")
    except Exception:
        pass

    # Step 4: Write search index (RSK-003) — best-effort
    # NOTE: _write_resume_index signature is (candidate_id, name, owner_sub, text) — 4 args.
    try:
        from app.services.resume_search import _write_resume_index
        if extraction_status == "ok":
            extracted = (
                T.candidates
                .get_item(Key={"pk": f"CANDIDATE#{candidate_id}", "sk": f"ATTACHMENT#{attachment_id}"})
                .get("Item", {})
                .get("extracted_text", "")
            )
            if extracted:
                _write_resume_index(candidate_id, stub_name, owner_sub, extracted)
    except Exception:
        pass

    # Step 5: Add to hot-list — best-effort
    hotlist_id = None
    try:
        if list_id:
            add_to_hotlist(list_id, candidate_id, owner_sub)
            hotlist_id = list_id
    except Exception:
        pass

    audit_event("ats.hotlist.quick_add", owner_sub,
                candidate_id=candidate_id, list_id=list_id,
                extraction_status=extraction_status)

    return {
        "candidate_id": candidate_id,
        "attachment_id": attachment_id,
        "extraction_status": extraction_status,
        "hotlist_id": hotlist_id,
    }
```

`_stem_from_filename(filename)` strips extension and replaces underscores/hyphens with spaces for a human-readable default name. Placeholder email uses `.invalid` TLD (RFC 2606) so it never routes to a real mailbox and is visually distinguished for cleanup.

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent add

`add_to_hotlist` performs a `get_item` check before writing. If the forward row already exists, both the row write and the `member_count` increment are skipped, and `False` is returned. The bulk endpoint accumulates `skipped` for each such case. On concurrent double-add the race condition is benign: at worst both concurrent calls see "absent" and write the row; DynamoDB's single-key writes are atomic per item, so the row is written once (last writer wins on the same key). The `member_count` may be incremented twice in the extreme race — this is accepted as an eventually-consistent approximation, consistent with the same counter-approximation philosophy used in newsfeed `TAG_STATS` (`app/routers/newsfeed.py:453–459`).

### 5.2 Cascade delete correctness

`delete_hotlist` queries all `MEMBER#` forward rows **before** deleting the META row. This ordering ensures that if the delete is interrupted mid-way (process crash), a re-run can query the surviving forward rows and continue cleanup. The META row is deleted last; surviving forward rows still point to a valid `list_id` but the META is gone, so the list is effectively invisible before all members are cleaned up. Reverse rows are deleted alongside each forward row in the same batch — a crash between deleting the forward and reverse row for a given member leaves an orphan reverse row, which is tolerated (the list META is gone so the dangling reverse row is unreachable via the primary list view, only via `list_candidate_hotlists`). A background cleanup sweep (deferred to a follow-up) can remove orphans by checking whether the referenced `HOTLIST#` META exists.

### 5.3 `member_count` floor-zero decrement

`remove_from_hotlist` uses `ConditionExpression="member_count > :z"`. If `member_count` is already `0` (e.g. due to a concurrent double-remove race), `ConditionalCheckFailedException` is caught silently and the function returns `True` (the rows are deleted regardless). This prevents the counter going negative.

### 5.4 Quick-add placeholder email

`resume-import-{uuid4().hex[:8]}@placeholder.invalid` uses the RFC 2606 `.invalid` TLD to ensure the address is syntactically valid (passes `normalize_email` at CND-002's service layer) but can never route to a real mailbox. The recruiter UI should surface a visual indicator ("no real email") and prompt for update. This is the minimal viable stub that satisfies CND-002's `email` required field.

### 5.5 Quick-add with missing RSK-002/003 (not yet shipped)

The lazy imports in `quick_add_from_resume` (`from app.services.resume_extraction import ...` inside `try/except`) ensure that if RSK-002 or RSK-003 has not yet been merged, the quick-add flow degrades gracefully to "stub candidate + résumé stored, extraction skipped". This allows RSK-006 to ship before its enrichment dependencies are fully deployed.

### 5.6 Shared list access for non-owners

`is_shared=True` makes the list **readable** by all recruiters but not mutable. A shared list owned by recruiter A is returned in recruiter B's `GET /ui/ats/hotlists` only when `include_shared=true` is passed. Recruiter B can call `GET /ui/ats/hotlists/{list_id}` to view it but cannot add/remove members or delete it.

### 5.7 Large-list pagination

`list_members` uses a DynamoDB key-condition query on `pk="HOTLIST#{list_id}"` with `begins_with(sk, "MEMBER#")`. DynamoDB returns up to 1MB per page before applying the key condition. A list with 10 000 members may require many pages; the `LastEvaluatedKey` loop inside `list_members` fetches exactly one page per API call and hands the cursor back to the client. Clients must paginate using the returned cursor until `cursor` is `null`.

### 5.8 Quick-add filename parsing

`_stem_from_filename("John_Smith_Resume_2026.pdf")` → `"John Smith Resume 2026"`. The function strips the extension, replaces `[_\-]+` with a space, and capitalizes words (`str.title()`). The first space-delimited token becomes `first_name`, the remainder becomes `last_name`. If the filename produces no whitespace-separated tokens, `first_name="Unparsed"` / `last_name="Candidate"` are used.

### 5.9 `list_id` validation on quick-add

If `list_id` is provided, the endpoint calls `get_hotlist(list_id)` before invoking the async thread. If the list does not exist or the caller is not the owner and the list is not shared, `HTTPException(404)` or `(403)` is raised before any S3/DDB write occurs. This prevents the silent failure of uploading a résumé and then failing to add to the list.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 — no `if S.dev_mode:` branches

All DDB reads and writes in `app/services/candidate_hotlists.py` go exclusively through `T.candidates` (the `_FloatSafeTable`-wrapped boto3 handle from `app/core/tables.py`). No `if S.dev_mode:` branch exists in the hot-list service. The same code path runs against DynamoDB Local in dev (`DDB_ENDPOINT_URL=http://localhost:8001`) and against real DynamoDB in prod — identical structural guarantee to RSK-001 through RSK-004.

The only dev/prod divergence in the entire RSK-006 call chain is `_make_download_url` in CND-003 (`docs/opencats/specs/CND-003.md` §4.1), which is CND-003's single permitted branch. RSK-006's quick-add flow calls `s3_client().put_object(...)` (parity-safe: moto intercepts in dev) and `add_resume(...)` (DDB-only), then separately calls `extract_resume_text` and `_write_resume_index`; none of those paths branch on `S.dev_mode`. The `_make_download_url` branch is only exercised when download URLs are constructed (by the router on GET endpoints), not in the quick-add write path.

### 7.2 Idempotency

- **`create_hotlist`** — UUID-keyed; no conditional expression needed; two rapid calls produce two distinct lists.
- **`add_to_hotlist`** — `get_item` guard before write; re-add is a clean no-op. Counter increment skipped on re-add.
- **`delete_hotlist`** — calling `delete_hotlist` on an already-deleted list is a safe no-op (DynamoDB `delete_item` on a non-existent key succeeds silently).
- **`quick_add_from_resume`** — not idempotent by design (each call creates a new stub candidate). Callers should not retry on success. On error before step 1 completes (before `create_candidate` returns), the caller may retry safely; after step 1 succeeds, a retry creates a second stub. The UI should disable the submit button after a successful or in-flight submission.

### 7.3 Authorization

- **No unauthenticated endpoints.** All RSK-006 routes require `Depends(require_ui_session)`. There is no public hot-list surface (unlike the career portal tickets PRT-\* which expose public job listings). No `API_KEY_ROUTE_EXEMPTIONS` entries are needed for RSK-006.
- **Owner-only mutations.** `DELETE /hotlists/{list_id}`, `PATCH /hotlists/{list_id}`, and `POST /hotlists/{list_id}/members` check `ctx["user_sub"] == owner_sub OR ctx["role"] >= Role.ADMIN` before proceeding. The `Role` import comes from `app/auth/roles.py`.
- **Private list enumeration.** `GET /hotlists/{list_id}` returns HTTP 404 (not 403) for a private list accessed by a non-owner, preventing list-ID oracle attacks.
- **CSRF.** All mutating endpoints (POST, PATCH, DELETE) automatically inherit CSRF enforcement from `require_ui_session` on cookie-auth requests (CLAUDE.md §Auth). Bearer-auth requests bypass CSRF.
- **File upload.** `quick_add_from_resume` enforces the `candidate_resume_max_bytes` limit before dispatching to the thread pool. Filename is sanitized via the `re.sub(r"[^A-Za-z0-9._-]", "_", ...)` regex from `app/services/kyc_partner_api.py:489` before S3 key construction.

### 7.4 Rate limiting

The `quick_add_from_resume` endpoint is the only computationally expensive RSK-006 operation (S3 write + DDB writes + optional extraction). A per-user `_bucket_limit(ctx["user_sub"], "rl#ats_quickadd", 20, 3600)` check at the route handler limits quick-adds to 20 per hour per recruiter — fail-open (allows through on sessions-table unavailability). The cap is consistent with the 30/60 s cap used by RSK-003's résumé search endpoint; it is tighter here because quick-add is a write path, not a read.

## 8. Backward Compatibility & Migration

### 8.1 Additive only

With `CANDIDATES_ENABLED=0` (the default) the platform is byte-for-byte unchanged:
- No new routes are reachable (all return 404).
- No new DDB items are written.
- No existing service file is modified.
- No existing router file is modified.

### 8.2 `candidates` table GSI addition

The `ByHotlistOwner` GSI (GSI4) is added to an existing table definition in `scripts/local-ddb-init.py`. In a **fresh dev environment** (`just restart` wipes and recreates all tables), the GSI is created automatically. In a **running dev environment** with existing data, a `just restart` is required to recreate the table with the new GSI (DynamoDB Local does not support `UpdateTable`; data is wiped). In **production**, an `UpdateTable` operation is required to add the GSI, followed by the async DynamoDB backfill period (typically minutes for a sparse table). No rollout ordering issue: the GSI is queried only after `CANDIDATES_ENABLED=1`, which is set after the GSI backfill completes.

### 8.3 No new tokens, no new S3 buckets

RSK-006 reuses `T.candidates` (no new table), `S.candidate_resume_bucket` (CND-001), and `S.candidate_resume_s3_prefix` (CND-001). No data migration or backfill is required for existing candidates.

### 8.4 SK prefix non-collision

Three new SK prefix families are introduced:
- `"HOTLIST#{list_id}"` on `pk="HOTLIST#…"` — distinct PK prefix from all existing rows.
- `"MEMBER#{candidate_id}"` on `pk="HOTLIST#…"` — distinct from `"META"` and `"HOTLIST#"`.
- `"HOTLIST#{list_id}"` on `pk="CANDIDATE#…"` — distinct from `"META"`, `"ATTACHMENT#"`, `"ACTIVITY#"`, and `"RESUME_TOKEN#"` (RSK-003).

`begins_with("HOTLIST#", "HOTLIST")` is true, but `"HOTLIST#"` as a sort key on a candidate partition would only collide with another SK beginning with `"HOTLIST"` — no existing SK prefix starts with that string (confirmed by inspection of CND-001 §3.1 and RSK-003 §3).

## 10. Open Questions / Assumptions

1. **Candidate `source` value for résumé quick-add — RESOLVED (no CND-001 change):** Earlier drafts used `source="resume_quickadd"`, which is NOT in CND-001's closed `CANDIDATE_SOURCES` frozenset / `CandidateCreateIn.source` regex (`^(direct|referral|job_board|linkedin|agency|career_portal|import|other)$`, CND-001 §3.6 / §4.2 line 227) and would raise a Pydantic `ValidationError` at runtime. `quick_add_from_resume` now uses the already-valid `source="import"` (a résumé quick-add is an import of a candidate from an uploaded file), so **no cross-ticket CND-001 regex extension is required** and RSK-006 has no `CANDIDATE_SOURCES` dependency. (CND-001 §3.6 line 197 documents `"import"` as "for the future CSV import cluster" — résumé quick-add fits the same semantics.)

2. **`is_shared=True` and mass-email:** The gap analysis §D notes MKT-009 (mass email) and MKT-007 (static lists) as separate planned tickets. RSK-006 does not implement bulk email from a hot-list. The `is_shared` flag on a hot-list is the future integration point: MKT-009 can accept a `hotlist_id` parameter to target a shared hot-list. This connection is out of scope for RSK-006.

3. **Orphan reverse rows on candidate delete:** CND-002's `delete_candidate` soft-deletes by setting `status="archived"` and `deleted_at`. It does not currently know about RSK-006 reverse rows. A deleted candidate's `HOTLIST#` reverse rows will remain on the partition, invisible to the live UI but present in DDB. Options: (a) CND-002's `delete_candidate` calls `list_candidate_hotlists` then removes each reverse row (best); (b) ignore for now, clean up in a background sweep. Assumption for RSK-006: deferred to a CND-002 follow-up; the orphan rows are benign since `list_candidate_hotlists` is only called from a candidate detail view that checks `deleted_at` first.

4. **Hot-list export (CSV):** OpenCATS supports CSV export from a hot-list. RSK-006 does not implement export. The `list_members` pagination endpoint provides all data needed for a future export endpoint; that can be a follow-up that reuses `app/services/csv_export.py`.

5. **`ByHotlistOwner` GSI and `is_shared=True` filtering:** The current GSI key is `GSI4PK="HOTLIST_OWNER#{owner_sub}"`. Finding all shared lists across all owners requires a scan with a `FilterExpression`. This is acceptable for the admin view (low frequency, bounded table size) but not for the recruiter-facing "browse shared lists" use case. If the shared-lists browse becomes a hot path, a secondary `GSI5PK="HOTLIST_SHARED#true"` sparse index should be added. Deferred; current design is explicit about the limitation.

6. **`member_count` eventual consistency:** The counter is incremented with a non-conditional `ADD` (no lock). Under concurrent bulk-adds, `member_count` may be momentarily inconsistent. It is treated as an approximate counter (display only), not as a correctness invariant. The authoritative member count is always `len(list_members(list_id, limit=<large>))`.
