# JOB-003 — Job Order REST router + main.py registration

**Ticket cluster:** ATS / Recruiting — Tier 1 Core Entity: Job Order
**Priority:** P0  **Estimate:** 2d  **Type:** Feature (REST layer)
**Source:** `docs/opencats/ATS_JOB_ORDERS_TICKETS.md` §JOB-003 + `docs/opencats/OPENCATS_GAP_ANALYSIS.md` §B

## 1. Summary & Goal

Expose the JOB-002 CRUD service (`app/services/job_orders.py`) as a REST router under the
prefix `/ui/ats/job-orders`, then register it in `app/main.py`. The router is the sole
boundary between HTTP callers and the service layer: it validates auth, enforces the
feature flag, translates service exceptions to HTTP status codes, and delegates all
business logic to the service.

Deliverables are exactly:

1. `app/routers/job_orders.py` — a new `APIRouter` with five CRUD endpoints plus a
   `/feature-status` utility endpoint needed by JOB-007 (frontend nav gating).
2. Two lines in `app/main.py` — one import and one `app.include_router(...)` call,
   adjacent to the existing `contacts_router` wiring.
3. Entries in `app/services/api_key_route_scope_registry.py`
   (`API_KEY_ROUTE_EXEMPTIONS`) so the API-key middleware does not block the new
   session-auth routes.
4. Focused hermetic pytest (`tests/test_job_orders_router.py`) covering the five
   endpoints, flag-off 503 behavior, and the status-transition 409.

No new DynamoDB tables, no new Pydantic models, no service functions, and no frontend
code ship in this ticket. Those belong to JOB-001, JOB-002, and JOB-007 respectively.

**Why now:** JOB-001 laid the data model and JOB-002 built the service. Without this
ticket there is no HTTP surface; the feature cannot be exercised by clients, the
frontend (JOB-007), or the integration E2E tests (JOB-008).

## 4. API / Service Design

### 4.1 Router file: `app/routers/job_orders.py`

```python
from fastapi import APIRouter, Depends, HTTPException, Response
from app.services.sessions import require_ui_session
from app.core.settings import S
from app.models import JobOrderCreateIn, JobOrderOut, JobOrderUpdateIn
import app.services.job_orders as _svc

router = APIRouter(prefix="/ui/ats/job-orders", tags=["ats-job-orders"])


def _require_flag() -> None:
    """Raise 503 if either the master ATS gate or the job-orders sub-gate is off."""
    if not (S.ats_enabled and S.job_orders_enabled):
        raise HTTPException(
            status_code=503,
            detail={"code": "job_orders_disabled"},
        )
```

The `_require_flag()` helper is called as the first statement inside every endpoint
handler body — matching the per-endpoint inline guard pattern in
`app/routers/chat_bot.py:82-83`. It is a plain function (not a FastAPI `Depends`), so
tests can call it independently and service tests never import the router.

### 4.2 Endpoints

All five endpoints use `Depends(require_ui_session)` (`app/services/sessions.py:330`)
and call `_require_flag()` before any service delegation.

**Declaration order constraint:** The list endpoints specified in JOB-004 (`/open`,
`/hot`, `/mine`) and the `/feature-status` utility endpoint must be declared **before**
`/{job_id}` in the router file. FastAPI matches routes in declaration order; a
`/{job_id}` declared first would capture the literal strings `open`, `hot`, `mine`, and
`feature-status` as path-parameter values. This is the same ordering rule documented in
CLAUDE.md for the audit export scheduler (`/schedules` before `/{export_id}`).

**Placeholder stubs for JOB-004 list routes:** The file registers three stub handlers
for `/open`, `/hot`, and `/mine` that return `{"items": [], "next_cursor": null}` +
503-when-off. These prevent JOB-004 from having to reorder the file and guarantee no
accidental route shadowing as the codebase evolves. JOB-004 replaces the stub bodies
with real service calls.

#### POST `/ui/ats/job-orders`

```python
@router.post("/", status_code=201, response_model=JobOrderOut)
async def create_job_order(
    body: JobOrderCreateIn,
    session: dict = Depends(require_ui_session),
) -> JobOrderOut:
    _require_flag()
    return _svc.create_job_order(actor_sub=session["user_sub"], data=body)
```

- Returns `JobOrderOut` (HTTP 201).
- Validation errors from Pydantic (`type` / `status` not in enum) surface as HTTP 422
  (FastAPI default); the router adds no additional validation.
- `_svc.create_job_order` raises `HTTPException(400)` for business-rule violations
  (e.g., `openings < 0` slipping past the model); these propagate unchanged.

#### GET `/ui/ats/job-orders/{job_id}`

```python
@router.get("/{job_id}", response_model=JobOrderOut)
async def get_job_order(
    job_id: str,
    session: dict = Depends(require_ui_session),
) -> JobOrderOut:
    _require_flag()
    return _svc.get_job_order(job_id=job_id)
```

- Returns `JobOrderOut` or raises `HTTPException(404)` (emitted by the service when
  `GSI_DIRECT` query finds no item or the item has `deleted_at` set).
- The `?expand=links` variant specified in JOB-006 is added to this handler in JOB-006
  via an optional `expand: Optional[str] = Query(None)` parameter; the JOB-003 baseline
  ignores expand.

#### PATCH `/ui/ats/job-orders/{job_id}`

```python
@router.patch("/{job_id}", response_model=JobOrderOut)
async def update_job_order(
    job_id: str,
    body: JobOrderUpdateIn,
    session: dict = Depends(require_ui_session),
) -> JobOrderOut:
    _require_flag()
    return _svc.update_job_order(
        actor_sub=session["user_sub"], job_id=job_id, data=body
    )
```

- Returns the updated `JobOrderOut`.
- Service raises `HTTPException(404)` for unknown `job_id`; `HTTPException(409)` for
  optimistic-concurrency conflict (stale `updated_at`); `HTTPException(409)` for illegal
  status transition if `status` is included in the body. All propagate unchanged.
- Partial update: all `JobOrderUpdateIn` fields are `Optional`; a body of `{}` is a
  valid no-op (returns current record, bumps `updated_at`).

#### POST `/ui/ats/job-orders/{job_id}/status`

```python
class SetStatusIn(BaseModel):
    status: str  # validated against JOB_ORDER_STATUSES by the service

@router.post("/{job_id}/status", response_model=JobOrderOut)
async def set_job_order_status(
    job_id: str,
    body: SetStatusIn,
    session: dict = Depends(require_ui_session),
) -> JobOrderOut:
    _require_flag()
    return _svc.set_status(
        actor_sub=session["user_sub"], job_id=job_id, new_status=body.status
    )
```

- The `SetStatusIn` model lives in the router file (not `app/models.py`), as it is a
  thin request container rather than a domain model.
- Service returns a no-op `JobOrderOut` for same-status (HTTP 200); raises
  `HTTPException(409, detail={"code": "invalid_status_transition", "from": ..., "to":
  ...})` for illegal transitions; `HTTPException(404)` for unknown `job_id`.
- This endpoint is a sub-resource (`/{job_id}/status`) and is unambiguous with respect
  to the list-route ordering constraint; it can be declared anywhere after `/{job_id}`.

#### DELETE `/ui/ats/job-orders/{job_id}`

```python
@router.delete("/{job_id}", status_code=204)
async def delete_job_order(
    job_id: str,
    session: dict = Depends(require_ui_session),
) -> Response:
    _require_flag()
    _svc.delete_job_order(actor_sub=session["user_sub"], job_id=job_id)
    return Response(status_code=204)
```

- Returns HTTP 204 with no body (soft-delete; the service writes `deleted_at`).
- Service raises `HTTPException(404)` for unknown / already-deleted `job_id`.

#### GET `/ui/ats/job-orders/feature-status`

```python
@router.get("/feature-status")
async def feature_status() -> dict:
    return {
        "ats_enabled": S.ats_enabled,
        "job_orders_enabled": S.job_orders_enabled,
    }
```

- No auth required (`require_ui_session` is **not** applied). The frontend (JOB-007)
  calls this at mount time to decide whether to show the sidebar "Job Orders" entry.
  Unauthenticated reads of a boolean flag carry no information risk.
- Does **not** call `_require_flag()` — it must return `{"job_orders_enabled": false}`
  when the flag is off so the frontend can hide the nav entry. Calling `_require_flag`
  here would 503 the frontend before it can determine the flag state.
- This endpoint must be declared **before** `/{job_id}` (the literal segment
  `feature-status` must not be captured as a `job_id`).

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-gate behavior

When either `S.ats_enabled` or `S.job_orders_enabled` is `False`, every endpoint that
calls `_require_flag()` returns HTTP 503 with body
`{"detail": {"code": "job_orders_disabled"}}`. The one exception is `feature-status`,
which always returns HTTP 200 with the current flag values so the frontend can determine
whether to display ATS UI.

The test must assert the 503 body shape exactly — downstream clients (the JOB-007
frontend error boundary) parse `code` to distinguish a disabled feature from a transient
server error.

### 5.2 Route ordering and path-parameter shadowing

The router file must declare routes in this order to prevent shadowing:

1. `GET /feature-status` — literal; before `/{job_id}`
2. `GET /open`, `GET /hot`, `GET /mine` — JOB-004 stubs (literal); before `/{job_id}`
3. `POST /` — no path param; order-independent
4. `GET /{job_id}` — dynamic
5. `PATCH /{job_id}` — dynamic
6. `POST /{job_id}/status` — dynamic sub-resource (unambiguous)
7. `DELETE /{job_id}` — dynamic

Violating this order causes FastAPI to route `GET /feature-status` to `get_job_order`
with `job_id="feature-status"`, which returns 404 (from the service GSI lookup) instead
of the flag dict — breaking frontend nav detection silently.

### 5.3 HTTP semantics

| Scenario | HTTP status | Body |
|---|---|---|
| Create success | 201 | `JobOrderOut` |
| Get / update / status success | 200 | `JobOrderOut` |
| Delete success | 204 | empty |
| Unknown `job_id` | 404 | `{"detail": "Job order not found"}` (service) |
| Invalid Pydantic body | 422 | FastAPI validation error |
| Illegal status transition | 409 | `{"detail": {"code": "invalid_status_transition", "from": ..., "to": ...}}` (service) |
| Optimistic-concurrency conflict | 409 | `{"detail": {"code": "optimistic_lock_conflict"}}` (service) |
| Flag off (all except feature-status) | 503 | `{"detail": {"code": "job_orders_disabled"}}` |
| Auth absent / invalid | 401 | `{"detail": "Missing user"}` (session dep) |

### 5.4 Actor propagation

Every mutating endpoint extracts `actor_sub = session["user_sub"]` from the session dict
returned by `require_ui_session` and passes it to the service. The service uses it in:
- `JobOrderOut.created_by` (create path)
- `audit_event("job_order.created" | "job_order.status_changed" | "job_order.deleted", actor_sub, ...)` (all mutating paths, `app/services/alerts.py:644`)

The router does not perform any role check beyond authentication. Authorization for
admin-only actions (e.g., bulk delete, recruiter assignment on behalf of another user)
is a JOB-* follow-on concern; at this tier any authenticated user can create/update
their own job orders.

### 5.5 CSRF enforcement

Cookie-auth non-GET requests require the `x-csrf-token` header matching the session's
`csrf_token`. This is enforced by `require_ui_session` / `app/auth/deps.py`
automatically — the router adds no CSRF logic. E2E tests that POST via `page.request`
(session auth) must include `headers: {"x-csrf-token": sessions[identity].csrf_token}`
(CLAUDE.md E2E patterns).

### 5.6 Soft-delete visibility

`GET /{job_id}` on a soft-deleted record returns HTTP 404 (the service checks
`deleted_at` and raises `HTTPException(404)`). A caller who POSTed a delete and
immediately GETs the same `job_id` should expect 404, not a record with a `deleted_at`
field. The `JobOrderOut` model does not expose `deleted_at`.

### 5.7 `SetStatusIn` model placement

`SetStatusIn` is defined in `app/routers/job_orders.py` (not `app/models.py`) because
it has no independent use as a domain model; it is purely a request-body container for
one endpoint. The pattern follows `app/routers/chat_bot.py`'s inline `BaseModel`
subclasses.

### 5.8 `feature-status` and auth

`feature-status` deliberately does not depend on `require_ui_session`. The frontend
calls it before login to determine whether to render ATS UI at all. Requiring auth would
create a chicken-and-egg situation where the flag check fails with 401 before the user
has a session. This is safe: flag values are not secrets, and the endpoint exposes no
user data. The same no-auth pattern is used for health probes and `/openapi.json` (both
in `API_KEY_ROUTE_EXEMPTIONS`).

## 6. Feature Flag & Config

### 6.1 Flag hierarchy

```
ATS_ENABLED=0        →  S.ats_enabled = False   (master gate; JOB-001)
JOB_ORDERS_ENABLED=0 →  S.job_orders_enabled = False  (sub-gate; JOB-001)
```

Both must be `True` for the endpoints to be reachable. The sub-gate allows enabling the
ATS feature cluster incrementally — future ATS sub-features (candidates, pipeline,

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 — no `dev_mode` branches

The router contains zero `if S.dev_mode` branches. The service layer (JOB-002) is
equally branch-free. `T.job_orders` is a `_FloatSafeTable` proxy (`app/core/tables.py:65`)
wrapping a real boto3 Table; in dev it points at DynamoDB Local (port 8001); in prod
it points at real DynamoDB. The same code path runs in both environments.

### 7.2 Idempotency

- **Create** is NOT idempotent — each `POST /` mints a new `job_id` via `uuid4().hex`.
  Callers that lose the response and retry will create a duplicate; deduplication is a
  future JOB-* concern (analogous to LED-009 dedupe).
- **PATCH**, **status**, and **DELETE** are idempotent in the HTTP sense: repeating
  the same PATCH with the same values produces the same result (modulo `updated_at`);
  repeating a DELETE on a soft-deleted record returns 404.
- **Optimistic concurrency** (JOB-002's `ConditionExpression` on `updated_at`) prevents
  lost updates from concurrent PATCHes. The router propagates the resulting
  `HTTPException(409)` to the caller.

### 7.3 Input validation and injection

- All request bodies are validated by Pydantic before reaching the handler. String
  fields have `max_length` constraints (title=255, description=20000, etc.) defined on
  the models in JOB-001.
- `job_id` path parameters are opaque strings passed directly to the service.
  The service looks them up via `GSI_DIRECT` keyed on `job_id`; DynamoDB key lookups
  are not susceptible to injection.
- `SetStatusIn.status` is validated by the service's state-machine guard, not the
  router; an unknown status string produces `HTTPException(400)` from the service.

### 7.4 Auth and CSRF

- All mutable endpoints require an authenticated session (`require_ui_session`). Absent
  or expired sessions → 401. Cookie-auth non-GET requests require the CSRF token (see
  §5.5). Bearer-auth requests (API clients) bypass CSRF.
- `feature-status` is unauthenticated by design (§5.8). It returns only boolean flags
  and is registered in `API_KEY_ROUTE_EXEMPTIONS`.

### 7.5 Audit trail

Every state-mutating service call (`create_job_order`, `update_job_order`,
`delete_job_order`, `set_status`) emits `audit_event(...)` to `T.alerts`
(`app/services/alerts.py:644`). The router does not add a second audit call. Audit
events are fire-and-forget best-effort; a write failure does not roll back the DDB
mutation.

## 8. Backward Compatibility & Migration

### 8.1 Existing routes

No existing route changes. The new `/ui/ats/job-orders/*` prefix is entirely novel.
FastAPI's route matching is prefix-based; adding a new prefix never shadows existing
routes.

### 8.2 `app/main.py`

The two added lines (`import` + `include_router`) are purely additive. With
`ATS_ENABLED=0` / `JOB_ORDERS_ENABLED=0`, the router is mounted but every endpoint
except `feature-status` returns 503; the application's existing behavior is
byte-for-byte unchanged for all non-ATS requests.

### 8.3 `API_KEY_ROUTE_EXEMPTIONS`

The six new entries are additive dict entries. The existing exemption validation logic
(`is_route_registered_or_exempt` at `app/services/api_key_route_scope_registry.py:316`)
checks membership in a union of both the registry and the exemptions dict; adding entries
only expands the accepted set.

### 8.4 DynamoDB

No schema migration. `T.job_orders` is created by running `scripts/local-ddb-init.py`
(which `just restart` / `just up` does automatically). In production, the table must be
created via `UpdateTable` or a migration script before `ATS_ENABLED=1` is deployed;
the feature flag default of `False` ensures no traffic reaches the service until the
table exists. The `attr_types={"created_at": "N", "updated_at": "N"}` declaration on
the `TableDef` (JOB-001) is required before the table is created — it cannot be added
retroactively to an existing DDB table's GSI.

### 8.5 JOB-004 forward compatibility

The three stub route handlers (`/open`, `/hot`, `/mine`) registered here are
`response_model`-free and return a static empty list. JOB-004 replaces the bodies in
place — the route signatures and positions in the file do not change. This prevents JOB-004
from having to reorder declarations and risk introducing shadowing bugs.

## 10. Open Questions / Assumptions

1. **Role-based access control** — The current design allows any authenticated user to
   create/update/delete job orders. Should recruiters be restricted to editing only job
   orders where they appear in `recruiter_subs`? If so, the router needs an ownership
   check (`if session["user_sub"] not in out.recruiter_subs and session["role"] != "ADMIN"`)
   after the service call. This ticket assumes open access among authenticated users
   pending a future ACL ticket (STU-002/003/004 per the gap analysis).

2. **`feature-status` caching** — The frontend may call `/feature-status` on every
   mount. Should the response carry `Cache-Control: max-age=60`? Current assumption:
   no cache header (live read of `S` settings, which are process-local constants anyway);
   the flag only changes at deploy time.

3. **Concurrent create deduplication** — Creating a job order is not idempotent; a
   double-POST creates two records. Assumption: acceptable at P0 tier; deduplication
   is LED-009 / JOB-* follow-on work.

4. **`openings` count of 0** — `openings=0` is allowed by the model (`ge=0`). Is a
   job order with zero openings semantically valid (e.g., a "lead" requisition not yet
   approved)? Assumption: yes, consistent with the `status="lead"` use case.

5. **`job_id` format validation** — The router accepts any non-empty string as a
   `job_id` path parameter. Malformed ids (not matching `job_[0-9a-f]{32}`) reach the
   service's `GSI_DIRECT` query and return 404. Assumption: no router-level format
   validation needed; 404 is the correct response for any unknown id regardless of
   format.
