# JOB-006 — Linkage resolution — client company / contact / recruiter owners

**Ticket cluster:** ATS / Recruiting — Tier 1 Core Entity: Job Order  
**Priority:** P2  **Estimate:** 2d  **Type:** Feature (resolution layer)  
**Source:** `docs/opencats/ATS_JOB_ORDERS_TICKETS.md` §JOB-006 + `docs/opencats/OPENCATS_GAP_ANALYSIS.md` §B  
**Flag:** `ATS_ENABLED` (master) + `JOB_ORDERS_ENABLED` (sub-gate); both default `false`

---

## 1. Summary & Goal

Every Job Order record carries three reference ids that anchor it to the broader CRM: `client_company_id` (the hiring client), `client_contact_id` (the primary point of contact at that client), and `recruiter_subs` (the list of user subs responsible for filling the role). JOB-001 through JOB-003 store all three as opaque strings with only shape validation — they are not looked up or rendered anywhere. The gap analysis (`docs/opencats/OPENCATS_GAP_ANALYSIS.md:53-61`) notes that the Company and Contact entities are **planned** (PTY-008 + CCT-001 for companies, PTY-007 + CCT-003 for contacts) but do not yet exist in the codebase, and that recruiter owner-assignment management is similarly **planned** (LED-010). This ticket ships the **resolution layer** that bridges what exists today and what will exist tomorrow.

The concrete goal is to add a `?expand=links` query parameter to the existing `GET /ui/ats/job-orders/{job_id}` endpoint (introduced by JOB-003). When that parameter is present the response includes a `links` block containing `company`, `contact`, and `recruiters` sub-objects with display data resolved from whatever sources are available:

- **Company**: resolved from `app.services.party.get_party(client_company_id)` when `S.party_crm_org_accounts_enabled` is on; else `{id, name: null, unresolved: true}` with no error.
- **Contact**: same path via `party.get_party(client_contact_id)` when the flag is on; else graceful degradation.
- **Recruiters**: resolved from `T.users` + `app/services/profile.get_profile_identity(sub)` for each `recruiter_sub`; unknown subs degrade to `{sub, unresolved: true}`.

Without `?expand=links` the response is byte-for-byte the existing JOB-003 `JobOrderOut`. The resolution layer is strictly additive, guarded by the existing ATS flags, and never 500s on a missing or unbuilt dependency.

## 3. Data Model

JOB-006 introduces **no new DynamoDB table, no new GSI, and no new DynamoDB rows**. All data is resolved at read time from existing tables (the `job_orders` table seeded by JOB-001/002, the `users`/`profiles` tables, and the future `party` table).

### 3.1 `job_orders` table (pre-existing, JOB-001)

The `client_company_id`, `client_contact_id`, and `recruiter_subs` fields are already stored on the `COMPANY#{client_company_id}` / `JOB#{job_id}` META row. `resolve_links` reads them from the `JobOrderOut` it receives — no additional DDB query on `job_orders` is needed.

### 3.2 `users` table (pre-existing)

`T.users` PK = `user_sub` (no SK). `get_item(Key={"user_sub": sub})` returns the user record. The profile lookup (`get_profile_identity`) reads `T.profile` (also pre-existing). Both are single `get_item` calls; for a job with N recruiter subs, at most N profile lookups are made (serial, small N, no pagination required — `recruiter_subs` is capped at 25 entries by `JobOrderCreateIn`).

### 3.3 Derived response shape (not persisted)

The `links` block is **computed on demand and never stored**. It is appended to the `GET /{job_id}?expand=links` response as an extra key alongside the flat `JobOrderOut` fields.

```
links: {
    company:    CompanyRef | null
    contact:    ContactRef | null
    recruiters: list[UserRef]
}

CompanyRef: {
    id:         str               # == client_company_id
    name:       str | null        # resolved from party.get_party(); null when unresolved
    unresolved: bool              # true when PTY unbuilt or party not found
}

ContactRef: {
    id:          str              # == client_contact_id
    name:        str | null
    email:       str | null
    unresolved:  bool
}

UserRef: {
    sub:          str             # == recruiter_sub
    display_name: str | null      # from get_profile_identity()
    email:        str | null      # from get_profile_identity()
    unresolved:   bool            # true when user_sub not found in T.users
}
```

`links` is `null` (absent) when `client_contact_id` is `None` on the order — the `contact` key is only populated when the field is set.

### 3.4 Pydantic models added to `app/models.py`

Append adjacent to `JobOrderOut`:

```python
class CompanyRef(BaseModel):
```

## 4. API / Service Design

### 4.1 Service function — `resolve_links`

Added to `app/services/job_orders.py`:

```python
def resolve_links(out: JobOrderOut) -> JobOrderLinks:
    """
    Resolve client_company_id, client_contact_id, and recruiter_subs into
    display objects.  All resolution failures degrade gracefully; no exception
    propagates out of this function.

    Returns a JobOrderLinks instance.
    """
    company = _resolve_company(out.client_company_id)
    contact = _resolve_contact(out.client_contact_id) if out.client_contact_id else None
    recruiters = [_resolve_recruiter(sub) for sub in out.recruiter_subs]
    return JobOrderLinks(company=company, contact=contact, recruiters=recruiters)


def _resolve_company(company_id: str) -> CompanyRef:
    try:
        flag = getattr(S, "party_crm_org_accounts_enabled", False)
        if not flag:
            return CompanyRef(id=company_id, unresolved=True)
        from app.services import party  # lazy import — PTY-008 may not be built yet
        record = party.get_party(company_id)
        if not record:
            return CompanyRef(id=company_id, unresolved=True)
        return CompanyRef(id=company_id, name=record.get("name"))
    except Exception:
        return CompanyRef(id=company_id, unresolved=True)


def _resolve_contact(contact_id: str) -> ContactRef:
    try:
        flag = getattr(S, "party_crm_enabled", False)
        if not flag:
            return ContactRef(id=contact_id, unresolved=True)
        from app.services import party  # lazy import
        record = party.get_party(contact_id)
        if not record:
            return ContactRef(id=contact_id, unresolved=True)
        mechs = record.get("contact_mechs") or {}
        email = mechs.get("email") or record.get("email")
        name = record.get("name") or record.get("display_name")
        return ContactRef(id=contact_id, name=name, email=email)
    except Exception:
        return ContactRef(id=contact_id, unresolved=True)


def _resolve_recruiter(sub: str) -> UserRef:
    try:
        from app.services.profile import get_profile_identity
        identity = get_profile_identity(sub)
        if identity.get("display_name") or identity.get("email"):
            return UserRef(
                sub=sub,
                display_name=identity.get("display_name"),
                email=identity.get("email"),
            )
        # Profile exists but empty — still counts as resolved if user row exists
        item = T.users.get_item(Key={"user_sub": sub}).get("Item")
        if item:
            return UserRef(sub=sub, display_name=identity.get("display_name"), email=identity.get("email"))
        return UserRef(sub=sub, unresolved=True)
    except Exception:
        return UserRef(sub=sub, unresolved=True)
```

Key design decisions:

- **Lazy import** of `app.services.party` inside each helper (not at module level) — identical pattern to `ec2_launcher.py:326`. The module-level import of `job_orders.py` succeeds even when `party.py` does not exist.
- **`getattr(S, "party_crm_org_accounts_enabled", False)`** — tolerant attribute lookup via `getattr` with a default, since `S` is a frozen dataclass and the field does not exist until PTY-001 ships. This is safer than `S.party_crm_org_accounts_enabled` which would raise `AttributeError` before PTY-001 is merged.
- **All `except Exception` blocks return the unresolved variant** — no exception propagates to the caller; a missing/unbuilt PTY entity never 500s the read.
- **`get_profile_identity` from `app/services/profile.py:305`** is reused without modification; it already handles missing profile rows gracefully (returns all-`None` dict via `empty_profile()`).

### 4.2 Router change — extend `GET /{job_id}`

In `app/routers/job_orders.py` (introduced by JOB-003), modify the single-get endpoint to accept an optional `expand` query parameter:

```python
@router.get("/{job_id}", response_model=None)
async def get_job_order_endpoint(
    job_id: str,
    expand: Optional[str] = Query(None, description="Pass 'links' to include resolved company/contact/recruiter display data"),
    session: dict = Depends(require_ui_session),
) -> Union[JobOrderOut, JobOrderWithLinksOut]:
    _require_flag()
    out = get_job_order(job_id)        # raises 404 via HTTPException if not found
    if expand == "links":
        links = resolve_links(out)
        return JobOrderWithLinksOut(**out.model_dump(), links=links)
    return out
```

`response_model=None` prevents FastAPI from clamping `JobOrderWithLinksOut` fields to `JobOrderOut` when `expand=links` is used. The return type annotation `Union[JobOrderOut, JobOrderWithLinksOut]` serves as documentation only.

**No new route path** — this is a parameter on the existing `GET /{job_id}` route. Route ordering in the router remains: list endpoints (`/open`, `/hot`, `/mine`, `/feature-status`) declared **before** `/{job_id}` (per JOB-003 and CLAUDE.md GAP-0210 ordering rule), so the literal segments are not captured as `job_id`.

### 4.3 No new endpoint path registered

JOB-006 modifies the existing `GET /{job_id}` handler only. The `app/main.py` import and `include_router` lines added by JOB-003 are untouched. The `API_KEY_ROUTE_EXEMPTIONS` entry in `app/services/api_key_route_scope_registry.py` (added by JOB-003) already covers `GET /ui/ats/job-orders/{job_id}` and applies to the expanded variant automatically.

### 4.4 Auth dependency

`Depends(require_ui_session)` — `app/services/sessions.py:330`. No escalation required; this is a read path. Bearer token and cookie-session auth both work; CSRF enforcement applies to cookie-auth non-GET requests only (not relevant here as this is a GET).

## 5. Detailed Behavior & Edge Cases

### 5.1 `expand` absent (default path)

`GET /ui/ats/job-orders/{job_id}` with no `?expand=` param returns the existing `JobOrderOut` shape, identical byte-for-byte to the JOB-003 response. No resolution code runs.

### 5.2 `expand=links` — company resolved

When `S.party_crm_org_accounts_enabled` is `True` and `party.get_party(client_company_id)` returns a record, `CompanyRef` is `{id, name: "<name>", unresolved: False}`. The `name` field comes from `record.get("name")`, matching the `CrmOrgAccountOut.name` field in PTY-008/CCT-001 (`docs/suitecrm/specs/CCT-001.md:30`).

### 5.3 `expand=links` — company not yet built (PTY-008 unshipped)

When `S.party_crm_org_accounts_enabled` is missing or `False` (pre-PTY-001 or flag-off), `_resolve_company` returns `{id: client_company_id, name: null, unresolved: true}` immediately, without attempting the import. No error surfaces.

### 5.4 `expand=links` — company id present but party row missing

If `party.get_party(...)` returns `None` (the party id is orphaned or soft-deleted), `CompanyRef` is `{id, name: null, unresolved: True}`. The job order itself is still returned.

### 5.5 `expand=links` — `client_contact_id` is null

`contact` key in `JobOrderLinks` is `null` (Python `None`). No resolution call is made.

### 5.6 `expand=links` — `client_contact_id` set but PTY unbuilt

Same pattern as company: `ContactRef(id=..., unresolved=True)`.

### 5.7 Recruiter resolution — partial

If `recruiter_subs` contains 3 subs and the second one is an unknown sub (e.g., a deleted account), `recruiters` in the response is a 3-element list where elements 0 and 2 are fully resolved and element 1 is `{sub: "...", unresolved: True}`. The partial failure does not abort resolution of the others.

### 5.8 Recruiter resolution — empty recruiter list

`out.recruiter_subs == []` → `recruiters: []`. No DDB calls.

### 5.9 `expand=anything_else` (e.g., `expand=foo`)

The `if expand == "links":` branch is not entered; the endpoint returns the plain `JobOrderOut`. Unknown `expand` values are silently ignored (no 400). This is consistent with similar patterns in the codebase and avoids brittle client coupling to exact enum validation.

### 5.10 Stale `client_company_id` after company deletion

The party layer (PTY) uses soft-delete. `party.get_party` may return the soft-deleted record (with `status=deleted`) or `None` depending on PTY's implementation. Either case is handled: a non-None record with a `name` field is resolved normally; `None` returns `unresolved: True`. JOB-006 does **not** filter on party status — that policy belongs to PTY, not to the resolution layer.

### 5.11 Concurrency

`resolve_links` is a read-only function; no write operations. All resolution calls are serial (not concurrent) — N recruiter subs means N sequential `get_profile_identity` calls. For the cap of 25 `recruiter_subs`, this is at most 25 + 2 DDB reads. If performance is a concern for large recruiter lists, a future ticket may add a `batch_get_item` path using `T.users.meta.client.batch_get_item` (pattern: `app/services/vod_purchase.py:286`), but this is deferred to avoid premature optimization.

### 5.12 Flag-off behavior

With `S.ats_enabled=False` or `S.job_orders_enabled=False`, `_require_flag()` raises `HTTPException(503, {"code": "job_orders_disabled"})` before `resolve_links` is ever called. The behavior is the same as every other JOB-* endpoint.

### 5.13 `job_id` not found

`get_job_order(job_id)` raises `HTTPException(404)` before `resolve_links` is reached. The 404 behavior is unchanged from JOB-003.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No `if S.dev_mode` branch

`resolve_links` contains zero `if S.dev_mode` / `if S.dev_mode else ...` branches. The same code path runs in dev (DDB Local) and production (real DynamoDB + real PTY). SECOPS-007 parity is achieved by construction.

### 7.2 Idempotency

`resolve_links` is a pure read function. It can be called any number of times with the same `JobOrderOut`; each call returns the same result (assuming stable underlying data). No writes, no side effects.

### 7.3 Lazy import and import-time safety

The local `from app.services import party` import inside `_resolve_company` / `_resolve_contact` is wrapped in `try/except Exception`, so even an `ImportError` (file not found) or `AttributeError` (function missing) degrades to `unresolved: True`. The module-level parse of `job_orders.py` will always succeed.

### 7.4 Information disclosure

`_resolve_recruiter` exposes `display_name` and `email` for each recruiter sub. These are the same fields returned by existing profile endpoints that use `require_ui_session`. Since `GET /{job_id}?expand=links` also requires `require_ui_session`, no new disclosure surface is created — any authenticated session can already call `GET /ui/profile/{sub}` to retrieve the same data.

### 7.5 Input validation

The `expand` query parameter is an `Optional[str]`. Unknown values are silently ignored (§5.9). No SQL/DDB injection risk — `expand` is never used in a DDB key expression; it only controls a code branch.

### 7.6 No new attack surface

No new endpoints, no new public routes, no new unauthenticated paths. The only change is a query-param branch on an existing authenticated GET route.

## 8. Backward Compatibility & Migration

### 8.1 Existing API response unchanged

`GET /ui/ats/job-orders/{job_id}` without `?expand=links` returns the exact `JobOrderOut` shape defined in JOB-001 and exposed in JOB-003. No field is added, removed, or renamed. All existing callers (JOB-007 frontend, JOB-008 E2E tests) continue to work without modification.

### 8.2 No DynamoDB schema changes

JOB-006 adds no table, no GSI, no new DDB attribute, and no new row type. No `scripts/local-ddb-init.py` change is required. No `just restart` needed for schema reasons (only for environment if flag changes).

### 8.3 No migration script required

All resolution is at read time from existing data. There is no stored `links` block to backfill, no index to populate, and no existing row format to convert.

### 8.4 Additive-only Pydantic models

`CompanyRef`, `ContactRef`, `UserRef`, `JobOrderLinks`, and `JobOrderWithLinksOut` are new Pydantic model classes appended to `app/models.py`. They do not modify any existing class. `JobOrderWithLinksOut` inherits from `JobOrderOut` via `class JobOrderWithLinksOut(JobOrderOut)` — a purely additive subclass with one extra field.

### 8.5 Forward compatibility with PTY-008

When PTY-008 ships and `PARTY_CRM_ORG_ACCOUNTS_ENABLED=1` is set in the environment, JOB-006's `_resolve_company` and `_resolve_contact` helpers will automatically call `party.get_party(...)` and return fully-populated `CompanyRef`/`ContactRef` objects. No change to JOB-006 is needed at that point.

## 10. Open Questions / Assumptions

1. **`party.get_party` return shape when PTY-008 ships** — JOB-006 assumes `record.get("name")` returns the org account name and `record.get("contact_mechs", {}).get("email")` or `record.get("email")` returns the contact email. If PTY-008/CCT-003 uses a different field name (e.g., `"org_name"` or `"display_name"`), `_resolve_contact`/`_resolve_company` will need a one-line field-name adjustment at that time. The `unresolved` degradation path is safe regardless.

2. **`S.party_crm_enabled` vs `S.party_crm_org_accounts_enabled`** — JOB-006 uses `party_crm_org_accounts_enabled` for company resolution (sub-flag matching CCT-001's scope, `docs/suitecrm/specs/CCT-001.md:5`) and `party_crm_enabled` (the parent flag) for contact resolution. If PTY-001's flag structure differs, the flag names in `_resolve_company`/`_resolve_contact` need updating — but because both are accessed via `getattr(S, ..., False)`, no `AttributeError` is raised either way.

3. **Profile visibility** — `get_profile_identity` returns `displayed_email` (the user's public-facing email, `app/services/profile.py:313`), not the auth email from Cognito. If a recruiter has set their profile email to `None` (privacy setting), `email` will be `null` in `UserRef`. This is by design — the recruiter chose to make their email non-public.

4. **Caching** — Currently no caching of resolution results. For a job with 20 recruiter subs this is 20 sequential `get_profile_identity` calls per `?expand=links` request. If profiling shows this to be a bottleneck, a future ticket may add a short-lived TTL cache or batch the profile lookups. For now the 25-sub cap and infrequent detail-page loads make caching premature.

5. **Assumption: `recruiter_subs` are user_subs in the main platform** — LED-010 assigns platform user accounts as recruiters. JOB-006 assumes every entry in `recruiter_subs` is a `user_sub` key in `T.users`. If LED-010 later uses a different identifier scheme, this ticket would need revisiting.
