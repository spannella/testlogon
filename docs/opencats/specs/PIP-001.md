# PIP-001 — Pipeline junction model + table + master flag

**Ticket type:** Feature
**Priority:** P0
**Estimate:** 2 days
**Master gate:** `S.ats_pipeline_enabled` (`ATS_PIPELINE_ENABLED`, default `false`)
**Depends on:** JOB-* (`T.job_orders`, `get_job_order`), CND-* (`T.candidates`, `get_candidate`)
**No upstream PIP dependency.**

---

## 1. Summary & Goal

PIP-001 is the foundational layer of the ATS recruiting pipeline. It introduces the **candidate↔job-order M:N junction** as a new single-table DynamoDB `ats_pipeline`, wires the master feature flag `S.ats_pipeline_enabled`, and exposes a minimal service API (`add_to_pipeline`, `get_pipeline_entry`, `list_pipeline_for_job`, `list_pipeline_for_candidate`, `remove_from_pipeline`). Every subsequent PIP ticket (status workflow, ratings, submit-to-client, placement, bulk, router, frontend) builds on these foundations without duplicating them.

The junction row is the artefact that makes testlogon an ATS rather than a pile of independent job-order and candidate records. It models the OpenCATS "candidate↔job order" relationship directly on the OPP-004 opportunity–contact junction pattern (`docs/suitecrm/specs/OPP-004.md §3/§4`), generalising "opportunity↔contact" to "job-order↔candidate".

With `ATS_PIPELINE_ENABLED=false` (the default), the platform is byte-for-byte unchanged: no DynamoDB writes, no HTTP routes, no sidebar entry. A `_require_flag()` helper (modelled on OPP-003's pattern) is the single enforcement point.

## 2. Context & Current State

**No ATS pipeline surface exists today.** `OPENCATS_GAP_ANALYSIS.md §C` (line 66) states "Pipeline = candidate↔joborder M:N join — **MISSING** — analogue: OPP-004 junction pattern." ## 3. Data Model

### 3.1 New DynamoDB Table: `ats_pipeline`

A single new table stores all pipeline-related item types introduced across the PIP set. No existing table is modified.

**Table definition — primary key:**

| Attribute | DDB type | Role |
|---|---|---|
| `pk` | S | Partition key |
| `sk` | S | Sort key |

**Item types:**

| `pk` | `sk` | Purpose |
|---|---|---|
| `USER#{owner_sub}` | `PIPE#{job_order_id}#CAND#{candidate_id}` | Pipeline entry (junction row) — **PIP-001** |
| `PIPELINE_STATUS_CONFIG` | `META` | Admin ranked-status config — **PIP-002** |

Pipeline entry attributes:

| Attribute | DDB type | Description |
|---|---|---|
| `pk` | S | `USER#{owner_sub}` |
| `sk` | S | `PIPE#{job_order_id}#CAND#{candidate_id}` |
| `pipeline_id` | S | `pe_{uuid4().hex}` — stable projected ID for ergonomic reads |
| `job_order_id` | S | Redundant projection; matches the sk segment |
| `candidate_id` | S | Redundant projection; matches the sk segment |
| `owner_sub` | S | Redundant projection of the owning user |
| `status` | S | Current status key, default `"100_no_contact"` |
| `status_rank` | N | Denormed rank from the status config (integer) |
| `rating` | N | Integer 0–5; `0` = unrated (default). **PIP-004** owns writes |
| `created_at` | N | Unix seconds via `now_ts()` |
| `updated_at` | N | Unix seconds via `now_ts()`; updated on every mutation |

## 4. API / Service Design

### 4.1 Service: `app/services/ats_pipeline.py` (new file)

```python
from app.core.tables import T
from app.core.settings import S
from app.core.time import now_ts
from app.services.alerts import audit_event
from fastapi import HTTPException
from boto3.dynamodb.conditions import Attr
import uuid

def _require_flag() -> None:
    """Raise 503 when ATS pipeline feature is disabled."""
    if not S.ats_pipeline_enabled:
        raise HTTPException(503, detail={"code": "ats_pipeline_disabled"})

def _entry_pk(owner_sub: str) -> str:
    return f"USER#{owner_sub}"

def _entry_sk(job_order_id: str, candidate_id: str) -> str:
    return f"PIPE#{job_order_id}#CAND#{candidate_id}"
```

**`add_to_pipeline(owner_sub: str, data: PipelineEntryCreateIn) -> PipelineEntryOut`**

1. `_require_flag()`
2. Lazy-import `get_job_order` from `app.services.job_orders` inside `try/except ImportError` — if missing, raise `HTTPException(503, detail={"code": "job_orders_not_available"})`. Call `get_job_order(data.job_order_id)` — raises `HTTPException(404)` if absent. Note: JOB-002's `get_job_order` takes only `job_id` (not `owner_sub`); ownership is enforced by the `COMPANY#{client_company_id}` partition pattern in that service. If a future revision adds an `owner_sub` parameter, update this call accordingly.
3. Lazy-import `get_candidate` from `app.services.candidates` — same guard. Call `get_candidate(data.candidate_id)` — raises `HTTPException(404)` if absent. Note: CND-002's `get_candidate` takes only `candidate_id` (not `owner_sub`); ownership enforcement is the caller's responsibility or relies on the structural key pattern in that service.
4. Build the item: `pipeline_id = f"pe_{uuid.uuid4().hex}"`, `status = data.status or "100_no_contact"`, `status_rank = 100` (default; `resolve_status_rank` in PIP-002 populates this properly once PIP-002 lands), `rating = 0`, `created_at = updated_at = now_ts()`.
5. `T.ats_pipeline.put_item(Item=item, ConditionExpression=Attr("sk").not_exists())` — on `ClientError` with code `ConditionalCheckFailedException` raise `HTTPException(409, detail={"code": "pipeline_entry_exists"})`.
6. `audit_event("pipeline.candidate_added", owner_sub, None, pipeline_id=pipeline_id, job_order_id=data.job_order_id, candidate_id=data.candidate_id, status=status)` — fire-and-forget inside `try/except`.
7. Return `PipelineEntryOut(**item)`.

**`get_pipeline_entry(owner_sub: str, job_order_id: str, candidate_id: str) -> PipelineEntryOut`**

1. `_require_flag()`
2. `T.ats_pipeline.get_item(Key={"pk": _entry_pk(owner_sub), "sk": _entry_sk(job_order_id, candidate_id)})`
3. If no `"Item"` → `HTTPException(404, detail={"code": "pipeline_entry_not_found"})`.
4. Return `PipelineEntryOut(**item)`.

**`list_pipeline_for_job(owner_sub: str, job_order_id: str, cursor: Optional[str] = None, limit: int = 50) -> dict`**

1. `_require_flag()`
2. `sk_prefix = f"PIPE#{job_order_id}#CAND#"`
3. Loop with `LastEvaluatedKey` (CLAUDE.md pagination gotcha): `query(KeyConditionExpression="pk = :pk AND begins_with(sk, :prefix)", ExpressionAttributeValues={":pk": _entry_pk(owner_sub), ":prefix": sk_prefix}, Limit=limit, ExclusiveStartKey=decode_cursor(cursor) if cursor else None)`.
4. Return `{"entries": [PipelineEntryOut(**i) for i in items], "cursor": encode_cursor(resp.get("LastEvaluatedKey"))}`.

**`list_pipeline_for_candidate(owner_sub: str, candidate_id: str, cursor: Optional[str] = None, limit: int = 50) -> dict`**

Same pattern as `list_pipeline_for_job` but `sk_prefix = f"PIPE#"` filtered to items containing `#CAND#{candidate_id}`. Because DynamoDB's `begins_with` cannot express a mid-key segment, this function queries `sk begins_with "PIPE#"` and filters in Python for `item["candidate_id"] == candidate_id`. Alternatively, a `FilterExpression` can be applied — but note the CLAUDE.md 1MB-page filter warning: the loop must paginate to exhaustion regardless.

**`remove_from_pipeline(owner_sub: str, job_order_id: str, candidate_id: str) -> None`**

1. `_require_flag()`
2. `get_pipeline_entry(owner_sub, job_order_id, candidate_id)` — raises 404 if not found.
3. `T.ats_pipeline.delete_item(Key={"pk": _entry_pk(owner_sub), "sk": _entry_sk(job_order_id, candidate_id)})`.
4. `audit_event("pipeline.candidate_removed", owner_sub, None, job_order_id=job_order_id, candidate_id=candidate_id)` — fire-and-forget.

## 5. Detailed Behavior & Edge Cases

### 5.1 Ownership-by-key authorization

The partition key `USER#{owner_sub}` enforces ownership structurally: an attacker who provides a foreign `owner_sub` in their JWT will simply miss all items under that partition and receive 404 responses. No separate ACL check is required for data-plane reads. This is the "structural authorization" pattern from OPP-004 §5: the DynamoDB access pattern itself is the security boundary.

The only exception is admin-gated writes (PIP-002 status-config, PIP-008 admin router) which apply an explicit `normalize_role` guard (`app/auth/roles.py:48`).

### 5.2 Duplicate add

If a caller adds the same `(owner_sub, job_order_id, candidate_id)` triple twice, the second `put_item` hits the `Attr("sk").not_exists()` condition and raises `ConditionalCheckFailedException`. The service converts this to `HTTP 409` with `code=pipeline_entry_exists`. The client is responsible for handling re-add idempotency (e.g., bulk add, PIP-007, reports skips as `already_in_pipeline`).

### 5.3 Foreign or absent job order / candidate

The lazy-import resolution of `get_job_order` and `get_candidate` is inside `try/except ImportError`. If the JOB-* or CND-* modules are not yet deployed:
- The service raises `HTTP 503` with `code=job_orders_not_available` (or `candidates_not_available`), not 404. This distinguishes "temporarily unavailable dependency" from "foreign record".
- Once JOB-*/CND-* are deployed (`app.services.job_orders` / `app.services.candidates`), the `get_job_order`/`get_candidate` calls raise `HTTP 404` for absent records. Those functions take only a single `id` parameter (not `owner_sub`); absence of `owner_sub` means ownership enforcement is structural (key-partitioned) within those services, not an explicit foreign-sub check in PIP-001.

### 5.4 `status` on create

If `data.status` is omitted, the service defaults to `"100_no_contact"`. If a custom status is provided, it is stored as-is; PIP-002's `resolve_status_rank` (once available) validates it against the live config and sets `status_rank`. Until PIP-002 ships, `status_rank` is set to `100` as a safe default that reflects the lowest rank in the canonical OpenCATS ladder.

### 5.5 Pagination completeness for `list_pipeline_for_candidate`

`list_pipeline_for_candidate` uses `begins_with(sk, "PIPE#")` combined with a Python-side filter on `candidate_id`. DynamoDB applies the `FilterExpression` *after* the 1 MB read page (CLAUDE.md gotcha). The loop **must** follow `LastEvaluatedKey` to exhaustion, not stop after the first page returns fewer items than `limit`. The function accumulates results across pages until `LastEvaluatedKey` is absent or `len(results) >= limit`.

### 5.6 `updated_at` denormalization

`updated_at` is set to `now_ts()` on every mutation (`add_to_pipeline`, `change_status` in PIP-003, `set_rating` in PIP-004). Callers must not cache `updated_at` as a monotonic version counter across concurrent writers; it is advisory metadata for UI sorting, not a CAS token.

### 5.7 `status_rank` denormalization

`status_rank` is an integer denormed from the status config at write time. It enables sorting entries by pipeline position without joining the config row. The value is correct at write time; if an admin reconfigures the status ladder (PIP-002), existing entries retain their old `status_rank` until the next `change_status` write updates it. This is intentional: bulk re-ranking is a background migration concern outside PIP-001's scope.

### 5.8 `pipeline_id` stability

`pipeline_id = f"pe_{uuid.uuid4().hex}"` is written once at creation and never modified. It is a stable opaque reference suitable for URL paths in PIP-008, React Query cache keys, and audit log references. The primary DynamoDB key remains `pk`/`sk`; `pipeline_id` is a projected convenience attribute.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No `if S.dev_mode` branches

All DynamoDB code is identical in dev and prod. The moto in-process S3/DDB mock (started by `app/core/dev_s3.py` at startup) intercepts boto3 calls at the botocore layer transparently; PIP-001 code never needs to know whether it is talking to DynamoDB Local or AWS. There are no `if S.dev_mode:` branches anywhere in `ats_pipeline.py`.

### 7.2 Idempotency

`add_to_pipeline` is **not** idempotent — a second call with the same triple raises 409. This matches OpenCATS semantics (you cannot add the same candidate to the same job twice). Callers that need idempotency (e.g., bulk add in PIP-007) must catch 409 and treat it as `already_in_pipeline`.

`remove_from_pipeline` is idempotent in the sense that calling it twice returns 404 on the second call (the row is gone). Callers should treat 404 on remove as a success equivalent in bulk flows.

### 7.3 CSRF

Non-GET requests from cookie-authenticated browsers are automatically protected by `require_ui_session` (`sessions.py:330`), which validates the `x-csrf-token` header against the session's stored `csrf_token` and the `ui_csrf` cookie. Bearer-token API clients skip CSRF. PIP-001 introduces no custom CSRF logic.

### 7.4 Ownership structural authorization

The `pk = USER#{owner_sub}` pattern means a caller with a different `owner_sub` in their JWT can never read or modify another user's pipeline entries — the DynamoDB access pattern itself is the security boundary. There is no need for a runtime ACL check on the data plane.

### 7.5 Audit trail

Every write that modifies the pipeline state calls `audit_event(...)` (`alerts.py:644`) as a fire-and-forget best-effort secondary write. This ensures every create and remove appears in the `T.alerts` audit log even if a future caller skips the service layer. `audit_event` is not transactional with the primary DDB write; a failed audit write is swallowed and logged.

### 7.6 `_FloatSafeTable` requirement

`T.ats_pipeline` is a `_FloatSafeTable` proxy (`tables.py:29`). `status_rank` and `rating` are integers; `created_at` and `updated_at` are integer Unix seconds from `now_ts()`. No floats are expected in PIP-001's items, but the proxy is required by convention — and PIP-006 placement rows store `fee_cents` (integer cents, not float). The proxy ensures a future inadvertent float does not cause a boto3 serialization error.

## 8. Backward Compatibility & Migration

### 8.1 No existing data affected

PIP-001 introduces a brand-new `ats_pipeline` DynamoDB table. No existing table is modified. No existing row schema changes. The `PipelineEntryOut` additive fields on job-order and candidate `Out` models default to `[]` and are populated only when `include_pipeline=true` is passed to a future endpoint.

### 8.2 `just restart` recreates the table

`scripts/local-ddb-init.py` is run by `just restart` (via `scripts/local-stack-up.sh`). Adding the `TableDef` entry for `ats_pipeline` means `just restart` will recreate the table from scratch in dev. Data in the table is not preserved across restarts — this is the expected dev behavior.

### 8.3 Production rollout

In production, the `ats_pipeline` table must be created (via `CreateTable` API or IaC) before `ATS_PIPELINE_ENABLED=true` is set. With the flag off, the service code is never executed and the table handle is only initialized at process startup (a `ddb.Table(name)` object creation, which does not make a network call). Setting the flag to false and then deploying PIP-001 code is safe even if the production table does not yet exist.

### 8.4 Model forward-compatibility

`PipelineEntryOut` is additive. Future PIP tickets add fields (e.g., `submit_count` from PIP-005, `placement_id` from PIP-006) as optional fields with `default=None` or `default_factory=list`. No breaking change is ever required on the existing fields.

### 9.2 E2E tests (`frontend/e2e/ats-pipeline.spec.ts`)

The ATS E2E spec is a single file introduced across the PIP set with section blocks per ticket. PIP-001's section (flag-on) covers:

- `GET /ui/ats/pipeline/feature-status` returns `{"enabled": true}` with flag on; `{"enabled": false}` with flag off.
- `POST /ui/ats/pipeline/entries` as Alice creates a junction row; returns 201 with `pipeline_id`.
- Duplicate add → 409 `pipeline_entry_exists`.
- Foreign `job_order_id` → 404.
- `GET /ui/ats/pipeline/by-job/{id}` lists the added entry.
- `GET /ui/ats/pipeline/by-candidate/{id}` lists the same entry.
- `DELETE /ui/ats/pipeline/by-job/{j}/candidate/{c}` removes the entry; subsequent GET by-job returns empty.
- Flag-off section: `POST /ui/ats/pipeline/entries` → 503; `feature-status` → `{"enabled": false}`.

Auth uses `injectAuth(page, "alice")` and `x-csrf-token: sessions["alice"].csrf_token` on non-GET requests per the repo E2E conventions. The flag is toggled via `.env.local` (`ATS_PIPELINE_ENABLED=1`/`VITE_ATS_PIPELINE_ENABLED=1`) before the test run.

## 10. Open Questions / Assumptions

1. **JOB-* and CND-* ownership semantics.** This spec assumes `get_job_order(owner_sub, job_order_id)` enforces ownership by partition key (returns 404 for foreign records), matching the structural authorization pattern. If JOB-* or CND-* use a different model (e.g., shared/team ownership), the 404 behavior of `add_to_pipeline` needs revisiting.

2. **`list_pipeline_for_candidate` scan scope.** The current design queries the owner's partition with `begins_with(sk, "PIPE#")` and filters by `candidate_id` in Python. If a recruiter has thousands of pipeline entries, this scan can be slow. PIP-008 may introduce a GSI on `candidate_id` + `created_at` (requiring `attr_types={"created_at": "N"}`) to make this O(1). The decision is deferred to PIP-008 when the query volume is better understood.

3. **Multi-recruiter / shared job orders.** OpenCATS has an "additional recruiters" concept where multiple recruiters can work the same job order. The current single-table partition `USER#{owner_sub}` means each recruiter has their own independent pipeline view. If shared pipeline entries are required in a future ticket, a separate `SHARED#` partition or a GSI would be needed. This is out of scope for PIP-001.

4. **`status_rank` at creation time.** PIP-001 hardcodes `status_rank=100` when `status="100_no_contact"` is the default. Once PIP-002 ships and `resolve_status_rank` is available, `add_to_pipeline` should call it. The assumption here is that PIP-001 and PIP-002 are delivered sequentially and `add_to_pipeline` is updated in PIP-002 to use `resolve_status_rank`.

5. **`pipeline_id` URL-path usage.** The spec stores `pipeline_id` as a projected attribute for ergonomic reads and future URL construction. PIP-008 may choose to route via `(job_order_id, candidate_id)` instead of `pipeline_id`. Either approach is valid; the spec does not mandate which PIP-008 chooses.
