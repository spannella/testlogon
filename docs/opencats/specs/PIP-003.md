# PIP-003 — Status-change transitions + logging (timeline + audit)

**Ticket type:** Feature
**Priority:** P0
**Estimate:** 2 days
**Master gate:** `S.ats_pipeline_enabled` (`ATS_PIPELINE_ENABLED`, default `false`)
**Depends on:** PIP-001 (junction table + flag), PIP-002 (status config + `resolve_status_rank`); ACT-009 (`record_crm_activity`, soft via lazy import)

---

## 1. Summary & Goal

PIP-003 implements the **pipeline-entry status-change operation**: the single mutation that moves a candidate from one recruiting stage to another within a specific job-order pipeline. It is the workhorse called by the Kanban drag-drop (PIP-009), the submit-to-client action (PIP-005), and the placement record (PIP-006).

Every status transition is dual-logged: (1) a fire-and-forget `audit_event` write to `T.alerts` for the platform-wide audit trail, and (2) a best-effort `record_crm_activity` write to the ACT-009 CRM activity timeline, repeated once for the candidate entity and once for the job-order entity. Both logging paths are best-effort `try/except` and never block or roll back the transition itself.

The operation is idempotent when `new_status == current_status`: no write, no audit, no timeline row is produced. Forward-progress is not enforced — OpenCATS allows backward movement (e.g., `800_client_declined → 300_qualifying`) and this implementation matches that behavior; `status_rank` is recorded for reporting and UI ordering only.

With `ATS_PIPELINE_ENABLED=false` (the default), the function immediately raises HTTP 503 and the platform is byte-for-byte unchanged.

## 2. Context & Current State

**No ATS pipeline exists today.** `OPENCATS_GAP_ANALYSIS.md:66` states the pipeline M:N join is **MISSING**, and `OPENCATS_GAP_ANALYSIS.md:68` states status-change logging is **PLANNED-ISH** ("wire to ACT-009 timeline + audit_event"). No `app/services/ats_pipeline.py` file, no `ats_pipeline` DynamoDB table, and no `change_status` function exist anywhere in the repository.

**PIP-001 provides the junction table and foundation.** `docs/opencats/specs/PIP-001.md §3` specifies the `ats_pipeline` DynamoDB table (`pk=USER#{owner_sub}`, `sk=PIPE#{job_order_id}#CAND#{candidate_id}`) and the `app/services/ats_pipeline.py` service file, including the `_require_flag()` helper, `get_pipeline_entry()`, and the `_entry_pk` / `_entry_sk` key helpers. PIP-003 adds `change_status()` to that same service file without modifying any existing function.

**PIP-002 provides the status-config primitives.** `docs/opencats/specs/PIP-002.md` (see `ATS_PIPELINE_TICKETS.md:82-99`) specifies `get_status_config() -> PipelineStatusConfigOut` (returns the live stored config or the 9-status default ladder) and `resolve_status_rank(status_key: str) -> int` (looks up the integer `rank` for a given status key). PIP-003 calls both. If `new_status` is not among the current config's keys, the service raises `HTTP 400 invalid_status` — validating against the *live* config, not a hard-coded list, matching OPP-003 §5.2 step 4.

**ACT-009 provides the per-entity timeline write primitive.** `docs/suitecrm/specs/ACT-009.md §4.1` specifies `record_crm_activity(entity_type, entity_id, activity_type, activity_id, user_sub, *, summary, metadata)` in `app/services/crm_activity_timeline.py` (not yet in the live tree — ACT-009 deliverable). PIP-003 calls it via a lazy local import inside `try/except` so that a missing or disabled ACT-009 module never prevents a status change. This is the ordering-independence pattern from `ACT-009.md §2.3`.

**`audit_event` is the platform audit primitive.** `app/services/alerts.py:644` defines `audit_event(event: str, user_sub: str, request=None, **fields: Any)`. It is fire-and-forget, writes to `T.alerts`, and is used after every meaningful service mutation across the platform (e.g., OPP-003 §4.1 `"opportunity.stage_changed"`). PIP-003 calls it once per transition as `"pipeline.status_changed"`.

**`update_item` is the mutation primitive.** The `_FloatSafeTable` proxy at `app/core/tables.py:29` coerces Python floats to `Decimal` on every `put_item` and `update_item`. PIP-003 uses `T.ats_pipeline.update_item(...)` with an `UpdateExpression` to set `status`, `status_rank`, and `updated_at` atomically. This is safer than `put_item` (which would silently clobber `rating` and `pipeline_id` if the item shape changed between fetch and write).

**`now_ts()` is the timestamp primitive.** `app/core/time.py:2` defines `now_ts() -> int` returning integer Unix seconds. `updated_at` is always set with it.

**`require_ui_session` is the auth dependency.** `app/services/sessions.py:330` defines `require_ui_session`. It automatically enforces CSRF on non-GET cookie requests. PIP-003 is a service function (not a router handler), so CSRF is enforced by the calling router handler in PIP-008.

**OPP-003 is the closest analogue.** `docs/suitecrm/specs/OPP-003.md §4.1` shows the stage-change sub-pattern in `update_opportunity`: call `get_stage_config()`, validate the new stage, call `audit_event("opportunity.stage_changed", ...)`. PIP-003 mirrors this pattern and extends it with the dual ACT-009 timeline write.

## 3. Data Model

PIP-003 introduces **no new DynamoDB tables, GSIs, or item types**. It operates entirely on the `ats_pipeline` table introduced by PIP-001 and the status-config singleton row introduced by PIP-002.

### 3.1 Existing table: `ats_pipeline` (PIP-001)

| `pk` | `sk` | Purpose |
|---|---|---|
| `USER#{owner_sub}` | `PIPE#{job_order_id}#CAND#{candidate_id}` | Pipeline entry (junction row) — **read + mutated by PIP-003** |
| `PIPELINE_STATUS_CONFIG` | `META` | Admin ranked-status config — **read-only by PIP-003** |

PIP-003 mutates these attributes on the pipeline entry row:

| Attribute | DDB type | Change |
|---|---|---|
| `status` | S | Set to `new_status` |
| `status_rank` | N | Set to `resolve_status_rank(new_status)` — integer from the live config |
| `updated_at` | N | Set to `now_ts()` |

The `status_rank` attribute is numeric but is **not** a GSI sort key (it is a plain item attribute denormed for UI sorting). No `attr_types` declaration is needed in `scripts/local-ddb-init.py` for `status_rank` — only GSI sort keys require `attr_types`. This was established in PIP-001's `TableDef` (see `docs/opencats/specs/PIP-001.md §3.1`).

### 3.2 `PipelineStatusChangeIn` Pydantic model (`app/models.py`)

Append near the PIP-001/PIP-002 models:

```python
class PipelineStatusChangeIn(BaseModel):
    new_status: str = Field(..., min_length=1, max_length=80)
    note: Optional[str] = Field(None, max_length=500)
```

`note` is stored in the ACT-009 timeline `metadata` dict (`{"from_status": ..., "to_status": ..., "note": ...}`) but is **not** persisted on the pipeline entry row itself. This keeps the pipeline entry lean; the timeline is the source of truth for transition history. A future ticket may add a `last_transition_note` denorm if the UI needs it.

### 3.3 `PipelineEntryOut` (unchanged, defined in PIP-001)

`change_status` returns the existing `PipelineEntryOut` model with updated `status`, `status_rank`, and `updated_at`. No new response model is introduced by PIP-003.

### 3.4 No new `scripts/local-ddb-init.py` changes

The `ats_pipeline` `TableDef` entry is fully specified by PIP-001. PIP-003 adds no GSIs and no new attributes that require `attr_types`. `just restart` recreates the table from PIP-001's existing `TableDef` with no amendments.

## 4. API / Service Design

### 4.1 Service function: `change_status`

Added to `app/services/ats_pipeline.py` (the file introduced by PIP-001). Full signature and step-by-step behavior:

```python
def change_status(
    owner_sub: str,
    job_order_id: str,
    candidate_id: str,
    new_status: str,
    *,
    note: Optional[str] = None,
) -> PipelineEntryOut:
```

**Steps (in order):**

1. `_require_flag()` — raises `HTTP 503 ats_pipeline_disabled` when `S.ats_pipeline_enabled` is `False`.

2. `entry = get_pipeline_entry(owner_sub, job_order_id, candidate_id)` — ownership gate (the DynamoDB key pattern enforces it structurally; raises `HTTP 404 pipeline_entry_not_found` if absent or foreign). This is the structural-authorization pattern from OPP-004 §5 and PIP-001 §5.1.

3. Resolve `config = get_status_config()` (PIP-002). Build a `valid_keys` set from `{s.status_key for s in config.statuses}`. If `new_status not in valid_keys` → raise `HTTP 400 {"code": "invalid_status", "valid": sorted(valid_keys)}`. Validation is against the *live* config, not a hard-coded ladder, following OPP-003 §5.2 step 4.

4. **Idempotency no-op:** if `new_status == entry.status`, return `entry` immediately. No `update_item`, no `audit_event`, no timeline write. The caller receives the current state unchanged. This makes the function safe to call from idempotent retries and from PIP-005/PIP-006 which may re-advance a status that is already at the target.

5. Capture `from_status = entry.status`, `from_rank = entry.status_rank` for the audit payload.

6. `new_rank = resolve_status_rank(new_status)` — returns the integer `rank` (e.g., `300` for `300_qualifying`) from the live config via PIP-002's helper.

7. `T.ats_pipeline.update_item(` with:
   - `Key={"pk": _entry_pk(owner_sub), "sk": _entry_sk(job_order_id, candidate_id)}`
   - `UpdateExpression="SET #st = :st, status_rank = :sr, updated_at = :ua"`
   - `ExpressionAttributeNames={"#st": "status"}` (reserved word guard)
   - `ExpressionAttributeValues={":st": new_status, ":sr": new_rank, ":ua": now_ts()}`
   - `ReturnValues="ALL_NEW"`
   - The returned `Attributes` dict is used to build the returned `PipelineEntryOut` so the caller receives the authoritative post-write state.

8. Fire-and-forget `audit_event`:

   ```python
   try:
       audit_event(
           "pipeline.status_changed",
           owner_sub,
           None,
           pipeline_id=entry.pipeline_id,
           job_order_id=job_order_id,
           candidate_id=candidate_id,
           from_status=from_status,
           to_status=new_status,
           from_rank=from_rank,
           to_rank=new_rank,
       )
   except Exception:
       logger.warning("audit_event failed for pipeline.status_changed", exc_info=True)
   ```

   (`app/services/alerts.py:644` — writes to `T.alerts`)

9. Fire-and-forget dual `record_crm_activity` calls — one for the candidate entity, one for the job-order entity:

   ```python
   def _try_record_timeline(entity_type, entity_id):
       try:
           from app.services.crm_activity_timeline import record_crm_activity
           record_crm_activity(
               entity_type=entity_type,
               entity_id=entity_id,
               activity_type="pipeline_status",
               activity_id=entry.pipeline_id,
               user_sub=owner_sub,
               summary=f"Pipeline status → {_status_label(config, new_status)}",
               metadata={
                   "from_status": from_status,
                   "to_status": new_status,
                   "job_order_id": job_order_id,
                   "candidate_id": candidate_id,
                   "note": note or "",
               },
           )
       except Exception:
           logger.warning(
               "record_crm_activity failed for %s/%s", entity_type, entity_id,
               exc_info=True
           )

   _try_record_timeline("candidate", candidate_id)
   _try_record_timeline("job_order", job_order_id)
   ```

   The lazy `from app.services.crm_activity_timeline import record_crm_activity` is inside the `try/except` block, so a missing ACT-009 module raises `ImportError`, which is caught and logged — the status change succeeds regardless (ACT-009 §2.3 ordering-independence pattern).

   `_status_label(config, status_key)` is a private helper that returns `next((s.label for s in config.statuses if s.status_key == status_key), status_key)` — falls back to the raw key if the label is not found.

10. Return `PipelineEntryOut(**updated_attributes)` using the `ReturnValues="ALL_NEW"` response from step 7.

### 4.2 HTTP endpoint (exposed in PIP-008)

PIP-003 adds the service function only. PIP-008 (`app/routers/ats_pipeline.py`) exposes it. The anticipated route:

| Method | Path | Auth | Body | Response |
|---|---|---|---|---|
| `PATCH` | `/ui/ats/pipeline/by-job/{job_order_id}/candidate/{candidate_id}/status` | `require_ui_session` | `PipelineStatusChangeIn` | `PipelineEntryOut` |

The handler:
```python
@router.patch("/by-job/{job_order_id}/candidate/{candidate_id}/status",
              response_model=PipelineEntryOut)
async def patch_pipeline_status(
    job_order_id: str,
    candidate_id: str,
    body: PipelineStatusChangeIn,
    ctx: dict = Depends(require_ui_session),
):
    return change_status(
        ctx["user_sub"], job_order_id, candidate_id,
        body.new_status, note=body.note,
    )
```

`require_ui_session` (`app/services/sessions.py:330`) automatically enforces the `x-csrf-token` header on this non-GET cookie request. No additional CSRF logic is needed in the handler.

### 4.3 Helper `resolve_status_rank` (PIP-002 deliverable, called here)

`resolve_status_rank(status_key: str) -> int` (defined in `app/services/ats_pipeline.py` by PIP-002) calls `get_status_config()` and returns the integer `rank` of the matching status, or `0` if not found. PIP-003 treats a `0` return as valid (it can happen if the config was changed between the `valid_keys` check and the rank resolution — a harmless race since `status_rank` is for ordering only, not for business logic).

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotency: same-status no-op

If `new_status == entry.status`, `change_status` returns the existing `PipelineEntryOut` immediately with no DynamoDB write, no `audit_event`, and no `record_crm_activity`. This is intentional:

- PIP-005 (`submit_to_client`) calls `change_status` to advance to the `is_submitted` stage after the email sends. If the entry is already at `400_submitted` (e.g., re-submit), the status call is a no-op; the email still re-sends and re-logs a submission activity. No duplicate audit event is produced.
- PIP-006 (`record_placement`) calls `change_status` to advance to `900_placed`. If the entry is already at `900_placed` (duplicate placement attempt), the status call is a no-op and the placement's own conditional-put raises `409 placement_exists` as expected.
- The Kanban drag (PIP-009) may fire a PATCH for a card dragged and dropped within the same column. The no-op behavior prevents spurious timeline clutter.

### 5.2 Backward movement is allowed

`change_status` does not enforce forward-only transitions. Moving from `800_client_declined → 300_qualifying` is permitted. The `rank` values (100, 200, ..., 900) are stored on the entry as `status_rank` for UI sorting and reporting; they do not gate transitions. This matches OpenCATS behavior. A future opt-in flag `ats_pipeline_block_regression` (analogous to OPP-003's `sales_pipeline_allow_reopen`) can be introduced to restrict this in a follow-up ticket without touching PIP-003.

### 5.3 Config staleness between validation and write

Between step 3 (config validation) and step 7 (`update_item`), an admin could call `PUT /ui/admin/ats/pipeline/statuses` and remove `new_status` from the config. The `update_item` will still succeed (DynamoDB does not enforce the status value against the config row). The resulting entry will carry a `status` value that is no longer in the live config. The UI Kanban handles this with an "Unknown" overflow column (PIP-009, mirroring OPP-003 §8.1). This is an acceptable eventual-consistency trade-off for a low-concurrency admin operation.

### 5.4 `update_item` vs `put_item`

`update_item` is used (not `put_item`) to avoid clobbering other attributes on the entry row (e.g., `rating` set by PIP-004, `pipeline_id`, `created_at`). A `put_item` would require re-fetching all attributes and re-writing them, creating a TOCTOU window. The `ReturnValues="ALL_NEW"` clause retrieves the final row in the same round trip, so the return value reflects any concurrent writes to other attributes.

### 5.5 Dual timeline write: candidate and job-order

`record_crm_activity` is called twice per transition: once with `entity_type="candidate"` and once with `entity_type="job_order"`. This means the transition appears on both the candidate's history panel and the job-order's pipeline-activity panel in the UI. If ACT-009 is not yet deployed, both calls raise `ImportError`, which is caught by the wrapping `try/except`; the status change succeeds without timeline rows.

The `activity_type` used is `"pipeline_status"`. This is a new activity type not in ACT-009's current `_VALID_ACTIVITY_TYPES = {"call", "task", "note", "calendar_event", "email"}`. ACT-009 validates `activity_type` query parameters at the **router** layer, not the service layer (ACT-009 §7.4; §5.5 covers `entity_type` validation using the same pattern). Since PIP-003 calls the service function directly (not via the router), the write is accepted without the router-level validation rejecting it. The `ByType` GSI on `crm_activity_timeline` will index it under `GSI1PK="TYPE#pipeline_status"`. When ACT-009's router adds `"pipeline_status"` to `_VALID_ACTIVITY_TYPES` (a one-line additive change), filtered queries by type will work. Until then, the rows exist and are readable via direct entity-key queries.

### 5.6 `audit_event` field contract

The `audit_event("pipeline.status_changed", ...)` call emits the following `**fields` to `T.alerts`:

| Field | Value |
|---|---|
| `pipeline_id` | `entry.pipeline_id` (the `pe_…` stable ID) |
| `job_order_id` | path parameter |
| `candidate_id` | path parameter |
| `from_status` | the previous `status` value |
| `to_status` | `new_status` |
| `from_rank` | the previous `status_rank` integer |
| `to_rank` | `new_rank` integer |

These fields are sufficient for the PIP-010 E2E assertion (`assert dev-audit-log entry contains from_status/to_status`) and for future RPT-* report queries filtering by `event="pipeline.status_changed"`.

### 5.7 `note` persistence scope

`note` from `PipelineStatusChangeIn` is passed into the ACT-009 `metadata` dict as `{"note": note or ""}`. It is deliberately **not** written to the pipeline entry row. The pipeline entry carries the current state; the timeline carries the transition history. A recruiter looking for "why did we move this candidate back to Qualifying?" reads the timeline, not the entry. If the timeline flag is off, the note is silently discarded — an acceptable trade-off documented in §10.

### 5.8 Concurrent transitions

Two concurrent `change_status` calls for the same entry (e.g., two recruiters simultaneously dragging the same card) will race at `update_item`. DynamoDB's item-level writes are serialized; one will win and the other will overwrite it. The last write wins. No optimistic concurrency (`ConditionExpression` on `status`) is introduced because concurrent status changes by two recruiters for the same candidate are extremely rare, and the Kanban will re-fetch after each PATCH. A future `version` attribute CAS can be added without schema changes.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No `dev_mode` branch

`change_status` contains **no `if S.dev_mode`** business-logic branches. The DynamoDB `update_item` call is identical in dev (DynamoDB Local, port 8001, via `DDB_ENDPOINT_URL=http://localhost:8001`) and prod (real DynamoDB endpoint). The `_FloatSafeTable` proxy at `app/core/tables.py:29` handles float-to-Decimal coercion in both. `audit_event` writes to `T.alerts` in both environments. SECOPS-007 parity is complete.

### 7.2 Idempotency

- **Same-status call:** pure no-op — no write, no audit, no timeline. Safe to retry.
- **`update_item` on a non-existent key:** would silently upsert. Prevented by the `get_pipeline_entry` guard in step 2, which raises 404 first.
- **`audit_event`:** fire-and-forget; a duplicate call would write two audit rows with different timestamps. Acceptable — the audit log is append-only and two rows for the same logical event are harmless.
- **`record_crm_activity`:** not idempotent by design (ACT-009 §5.1); a retry produces a second timeline row. PIP-003 does not retry; the `try/except` is not a retry loop.

### 7.3 Structural authorization

Ownership is enforced by the DynamoDB key: `get_pipeline_entry(owner_sub, ...)` performs `T.ats_pipeline.get_item(Key={"pk": "USER#{owner_sub}", ...})`. An attacker providing a foreign `owner_sub` in their JWT will hit a different partition and receive 404 (`pipeline_entry_not_found`). No explicit ACL check is needed. This is the structural-authorization pattern from OPP-004 §5 and PIP-001 §5.1 (`docs/opencats/specs/PIP-001.md`).

### 7.4 CSRF enforcement

`change_status` is a service function. CSRF is enforced by the calling router handler via `Depends(require_ui_session)` (`app/services/sessions.py:330`). For the `PATCH .../status` endpoint (PIP-008), non-GET requests with a `ui_session` cookie are required to include `x-csrf-token: <csrf_token>` matching the session's stored `csrf_token` and the `ui_csrf` cookie value (CLAUDE.md "CSRF" section). The frontend's `api/client.ts` attaches the CSRF token automatically on every non-GET.

### 7.5 Role gate

`change_status` is a data-plane write, not an admin operation. Any authenticated user (USER, ADMIN, ROOT) with a valid session may call it, subject to the ownership gate. The admin-only surface in PIP-002/PIP-008 is `PUT /ui/admin/ats/pipeline/statuses`; that route checks `normalize_role(ctx.get("role")) in {Role.ADMIN, Role.ROOT}` (`app/auth/roles.py:48`). PIP-003 has no admin-only surface.

### 7.6 Input sanitization

`new_status` is validated against the live config's `valid_keys` set before being written to DynamoDB. The config row is admin-authored and sanitized at write time (PIP-002 `_validate_status_config`), so `new_status` values that reach `update_item` are already known-safe strings. `note` is truncated to 500 characters by the Pydantic model; the 200-char `summary` truncation in `record_crm_activity` (`ACT-009.md §5.6`) provides a secondary cap.

## 8. Backward Compatibility & Migration

### 8.1 Additive service function

`change_status` is a new function appended to `app/services/ats_pipeline.py`. It does not modify any existing function (`_require_flag`, `add_to_pipeline`, `get_pipeline_entry`, `list_pipeline_for_job`, `list_pipeline_for_candidate`, `remove_from_pipeline`). Existing callers of those functions are unaffected.

### 8.2 Additive Pydantic model

`PipelineStatusChangeIn` is a new model appended to `app/models.py`. It does not alter any existing model. No `model_rebuild()` call is needed.

### 8.3 No schema migration

The `ats_pipeline` table's `TableDef` (PIP-001) already declares `pk` / `sk` as the primary key with no numeric GSI sort keys. `status_rank` is written as a plain item attribute (numeric `N`), not as a GSI sort key, so no `attr_types` amendment is required. `just restart` recreates the table from the existing PIP-001 `TableDef` unchanged.

### 8.4 Entries created before PIP-003

Any pipeline entries written by PIP-001 (before PIP-003 lands) have `status="100_no_contact"` and `status_rank=100`. When `change_status` is first called on such an entry, step 5 captures `from_status="100_no_contact"` and `from_rank=100`; the `update_item` in step 7 writes the new `status` and `status_rank`. The entry is silently migrated by the first transition — no backfill script is needed.

### 8.5 Pipeline entries with orphaned status values

After PIP-002 ships and an admin modifies the status config, some entries may carry a `status` value no longer in the live config. `change_status` validates only `new_status` against the live config; it does not validate `entry.status` (the stored `from_status`). This means: (a) reading an entry with an orphaned status always works, (b) transitioning *from* an orphaned status to a valid new status always works, (c) the audit event accurately records `from_status` even if it is no longer in the config. The Kanban "Unknown" overflow column (PIP-009) surfaces orphaned entries visually.

## 10. Open Questions / Assumptions

| # | Question | Assumption / Deferral |
|---|----------|-----------------------|
| OQ-1 | Should forward-progress blocking (rank regression prevention) be implemented now? | **Deferred.** A future `ats_pipeline_block_regression` flag can be added without touching PIP-003. OpenCATS allows backward movement; the default must match. |
| OQ-2 | Should `note` be persisted on the pipeline entry row (e.g., `last_transition_note`) in addition to the timeline? | **Deferred.** The timeline is the canonical history store. If the UI needs a quick "last note" on the card, a `last_transition_note` denorm can be added as an additive `update_item` attribute in a follow-up. |
| OQ-3 | Should `activity_type="pipeline_status"` be added to ACT-009's `_VALID_ACTIVITY_TYPES` in a coordinated PR? | **Assumption:** ACT-009 spec declares the router validates entity types but the service does not. PIP-003 calls the service directly, bypassing the router validation. A one-line additive change to ACT-009's `_VALID_ACTIVITY_TYPES` is a separate task for the ACT-009 author. Until then, the timeline rows exist but are not reachable via the filtered ACT-009 router endpoint with `?activity_type=pipeline_status`. |
| OQ-4 | What if `get_status_config()` is slow and called twice per transition (once for validation, once in `resolve_status_rank`)? | **Assumption:** the config row is a single `get_item` (~1ms on DynamoDB Local, ~2ms on DynamoDB prod). Two reads per transition is acceptable. A process-level LRU cache can be added in a follow-up if profiling shows latency impact at high throughput. |
| OQ-5 | Should the `PATCH .../status` route return 204 No Content or 200 with the updated entry body? | **Assumption:** 200 with `PipelineEntryOut` body. The Kanban (PIP-009) uses the response to update the card's `status_rank` and re-sort columns without a separate GET. 204 would require an extra round trip. |
| OQ-6 | Should `change_status` require a reason code (from a fixed vocabulary) in addition to a free-text `note`? | **Deferred.** OpenCATS does not have reason codes on status transitions. If compliance requirements surface them, a `reason_code: Optional[str]` can be added to `PipelineStatusChangeIn` additively. |
