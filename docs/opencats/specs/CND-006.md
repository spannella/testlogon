# CND-006 — Frontend — Candidates list + detail page (with résumé section)

**Cluster:** ATS Candidates (CND) · **Tier:** 1 · **Priority:** P1  
**Estimate:** 2.5 days · **Depends on:** CND-005  
**Flag:** `CANDIDATES_ENABLED` (default `"0"` → `False`)

---

## 1. Summary & Goal

CND-006 delivers the complete Candidates UI: a **list page** with filters and
pagination, and a **detail page** with inline editing, ATS-specific fields,
a **Résumé section** (upload, list, set-primary, download, delete), and a
**History tab** (change-event feed). Together with CND-005 (backend router),
this ticket closes the recruiter-facing surface for the Candidate entity as
described in the gap analysis (§A, line 45–46) and the CND-006 section of
`docs/opencats/ATS_CANDIDATES_TICKETS.md`.

The UI follows the platform's established patterns verbatim — React Query for
server state, React Hook Form + Zod for forms, shadcn/ui primitives, cursor
pagination — and reuses the `api/client.ts` axios instance (CSRF handled at
`client.ts:179`) so no new auth plumbing is required. The module is entirely
hidden when `CANDIDATES_ENABLED=0`: the backend returns 404 for all CND-005
routes, the frontend renders a graceful disabled state, and the sidebar nav
entry is conditionally omitted.

## 4. API / Service Design

### 4.1 Endpoint wrappers — `frontend/src/api/endpoints/candidates.ts` (new file)

All calls go through the `api` helper from `api/client.ts` which attaches the
`X-CSRF-Token` header from the `ui_csrf` cookie (`client.ts:179`) and the
`Authorization: Bearer` header from the auth store (`client.ts:168–170`). No
additional auth setup is required in this file.

```typescript
import { api } from "@/api/client";
import type {
  Candidate,
  CandidateCreateInput,
  CandidateUpdateInput,
  CandidateListResponse,
  CandidateResume,
  CandidateHistoryResponse,
} from "@/api/types";

const BASE = "/ui/candidates";

// ── List ──────────────────────────────────────────────────────────
export function listCandidates(opts?: {
  owner_sub?: string;
  status?: string;
  source?: string;
  created_after?: number;
  cursor?: string;
  limit?: number;
}): Promise<CandidateListResponse> {
  const params: Record<string, string> = {};
  if (opts?.owner_sub)      params.owner_sub      = opts.owner_sub;
  if (opts?.status)         params.status         = opts.status;
  if (opts?.source)         params.source         = opts.source;
  if (opts?.created_after)  params.created_after  = String(opts.created_after);
  if (opts?.cursor)         params.cursor         = opts.cursor;
  if (opts?.limit)          params.limit          = String(opts.limit);
  return api.get<CandidateListResponse>(BASE, params);
}

// ── Create ────────────────────────────────────────────────────────
export function createCandidate(payload: CandidateCreateInput): Promise<Candidate> {
  return api.post<Candidate>(BASE, payload);
}

// ── Detail ────────────────────────────────────────────────────────
export function getCandidate(candidateId: string): Promise<Candidate> {
  return api.get<Candidate>(`${BASE}/${candidateId}`);
}

// ── Update ────────────────────────────────────────────────────────
export function updateCandidate(
  candidateId: string,
  patch: CandidateUpdateInput,
): Promise<Candidate> {
  return api.patch<Candidate>(`${BASE}/${candidateId}`, patch);
}

// ── Delete ────────────────────────────────────────────────────────
export function deleteCandidate(candidateId: string): Promise<void> {
  return api.del<void>(`${BASE}/${candidateId}`);
}

// ── Owner ─────────────────────────────────────────────────────────
export function setCandidateOwner(
  candidateId: string,
  ownerSub: string,
): Promise<Candidate> {
  return api.put<Candidate>(`${BASE}/${candidateId}/owner`, { owner_sub: ownerSub });
}

// ── Résumés ───────────────────────────────────────────────────────
export function listResumes(candidateId: string): Promise<CandidateResume[]> {
  return api.get<CandidateResume[]>(`${BASE}/${candidateId}/resumes`);
}

export function uploadResume(
  candidateId: string,
  file: File,
  makePrimary = false,
): Promise<CandidateResume> {
  const fd = new FormData();
  fd.append("file", file);
  fd.append("make_primary", String(makePrimary));
  return api.upload<CandidateResume>(
    `${BASE}/${candidateId}/resumes`,
    fd,
  );
}

export function getResume(
  candidateId: string,
  attachmentId: string,
): Promise<CandidateResume> {
  return api.get<CandidateResume>(
    `${BASE}/${candidateId}/resumes/${attachmentId}`,
  );
}

export function setPrimaryResume(
  candidateId: string,
  attachmentId: string,
): Promise<void> {
  return api.put<void>(
    `${BASE}/${candidateId}/resumes/${attachmentId}/primary`,
  );
}

export function deleteResume(
  candidateId: string,
  attachmentId: string,
): Promise<void> {
  return api.del<void>(`${BASE}/${candidateId}/resumes/${attachmentId}`);
}

// ── History ───────────────────────────────────────────────────────
export function getCandidateHistory(
  candidateId: string,
  opts?: { cursor?: string; limit?: number },
): Promise<CandidateHistoryResponse> {
  const params: Record<string, string> = {};
  if (opts?.cursor) params.cursor = opts.cursor;
  if (opts?.limit)  params.limit  = String(opts.limit);
  return api.get<CandidateHistoryResponse>(
    `${BASE}/${candidateId}/history`,
    params,
  );
}
```

**Notes:**
- `api.upload` (added at `client.ts:319`) sends multipart `FormData`; the
  browser sets `Content-Type: multipart/form-data; boundary=...` automatically.
  The `api` function must NOT set `Content-Type` for FormData bodies — this is
  already handled at `client.ts:185–187` (only sets `application/json` for
  string bodies).
- All other calls use `api.get` / `api.post` / `api.patch` / `api.put` /
  `api.del`, mirroring the pattern in `api/endpoints/contacts.ts:6–24` and
  `api/endpoints/tickets.ts:90–118`.

### 5.3 CandidatesPage — list page (`frontend/src/pages/candidates/CandidatesPage.tsx`)

**Layout:** `PageHeader` ("Candidates") + filter bar + data table +
`NewCandidateDialog`.

**Filter bar:** three controlled inputs:
- **Status** — `<Select>` over `CANDIDATE_STATUSES` values + blank "All"
  option. Clears cursor on change.
- **Owner = me** — toggle `<Button variant="outline">` that sets
  `owner_sub=currentUserSub` (from `useAuthStore((s) => s.userId)`) or clears
  it. Clears cursor on toggle.
- **Source** — free-text `<Input>` with 300 ms debounce (via `useEffect` +
  `useState`). Clears cursor on change.

**Data table:** shadcn `<Table>` (mirroring `TicketsPage.tsx:60–80`) with
columns: **Name** (link to `/candidates/:id`), **Email**, **Current Title**,
**Status** (`<Badge>` colour-coded by status tier), **Owner** (user sub or
display), **Date Available**, **Updated**.

- `useQuery({ queryKey: ["candidates", filters, cursor], queryFn: () =>
  listCandidates({...filters, cursor, limit: 25}) })`.
- Loading state: `Loader2` spinner centred.
- Empty state: `<EmptyState>` component ("No candidates found").
- Error state: if `error` is `ApiError` with `status === 404` → render
  `<ModuleDisabledState>` (see §5.6). Other errors → `toast.error`.
- **Pagination:** "Load more" `<Button>` that sets `cursor` state to
  `data?.cursor`. Page-forward only (no back); current accumulated list held in
  a `useState<Candidate[]>` that appends on each successful fetch (same pattern
  as the file manager's load-more rather than `useInfiniteQuery`, for
  simplicity).

**New Candidate dialog** (`NewCandidateDialog` sub-component in the same file
or a separate `NewCandidateDialog.tsx` in `pages/candidates/`):
- Trigger: `<Button>` "New Candidate" in the page header.
- Dialog content: React Hook Form + Zod schema validating required
  `first_name`, `last_name`, `email` (Zod `z.string().email()`), optional
  `phone`, `company`, `title`, `source`, `status` (default `"active"`), and
  the ATS-delta fields (`current_pay`, `desired_pay`, `key_skills`,
  `date_available`, `can_relocate`, `linkedin_url`, `web_url`).
- On submit: `useMutation({ mutationFn: createCandidate, onSuccess: (data) => {
  queryClient.invalidateQueries(["candidates"]); navigate(\`/candidates/${data.candidate_id}\`) } })`.
- Validation errors shown inline via `<FormMessage>` (RHF pattern consistent
  with the existing questionnaire builder).
- On HTTP 400 (normalised by `normalizeErrorDetail` at `client.ts:66–102`):
  `toast.error(detail)`.

### 5.4 CandidateDetailPage — detail + résumé + history

**Route param:** `const { candidateId } = useParams<{ candidateId: string }>()`.

**Primary query:**
```typescript
const candidateQuery = useQuery({
  queryKey: ["candidates", "detail", candidateId],
  queryFn: () => getCandidate(candidateId!),
  enabled: Boolean(candidateId),
});
```
On 404 → `<ModuleDisabledState>` (flag off) or `<ErrorPage status={404} />`
if `error.status === 404` and the list page previously succeeded (candidate was
deleted). The page must distinguish these cases by checking whether the list
page query also 404s — in practice, showing `<ModuleDisabledState>` on any 404
from the detail endpoint is acceptable (worst case the user navigates to list
which also shows the disabled state).

**Page layout:** two-column card (candidate info left, résumé/history right) on
`md:` breakpoint; single-column stack on mobile.

**Left panel — Candidate fields:**
- Display name heading: `${first_name} ${last_name}` with a status `<Badge>`.
- **Inline edit toggle:** pencil `<Button variant="ghost" size="icon">` per
  section that swaps static display for an RHF form. Alternatively a single
  "Edit" button opens a full-page drawer — the drawer pattern (used by the
  contacts page) is preferred for the ATS-delta section because it has many
  fields. Use a `<Sheet>` (shadcn slide-over) containing the full RHF form.
- **Sections displayed:**
  - *Contact*: email, email_raw (shown as "Original: …" when different),
    phone.
  - *Professional*: company, title, source, owner_sub.
  - *ATS fields*: current_pay, desired_pay, key_skills (`<Textarea>`),
    date_available (formatted with `new Date`), can_relocate (`<Badge
    variant={can_relocate ? "default" : "secondary">`), linkedin_url
    (`<a href={...} target="_blank">`), web_url (`<a>`).
  - *Address*: address, city, state, postal_code, country.
- **Status control:** `<Select>` using `CANDIDATE_STATUSES`. On change calls
  `updateCandidate(candidateId, { status })` via `useMutation`. On success:
  `queryClient.invalidateQueries(["candidates", "detail", candidateId])` and a
  `toast.success`.
- **Owner control:** free-text `<Input>` + `<Button>` "Assign" that calls
  `setCandidateOwner`. Only shown to admin/root (check
  `getRoleFromAccessToken(accessToken)` from `lib/adminCapabilities` — same
  pattern as `TicketsPage.tsx:43–44`).
- **Delete button** (owner or admin): `<ConfirmDialog>` then
  `deleteCandidate(candidateId)` → `navigate("/candidates")`.

**Right panel — tabs:** shadcn `<Tabs defaultValue="resumes">` with two values:
`resumes` and `history`.

#### Tab: Résumés

**Résumé list:**
```typescript
const resumesQuery = useQuery({
  queryKey: ["candidates", "resumes", candidateId],
  queryFn: () => listResumes(candidateId!),
  enabled: Boolean(candidateId),
});
```
Render as a `<ul>` of cards. Each card shows: filename, content_type badge,
file size (`(size_bytes / 1024).toFixed(0) + " KB"`), uploaded date
(`new Date(created_at * 1000).toLocaleDateString()`), and a **Primary** badge
(`<Badge variant="default">`) when `is_primary`. Actions (via `<DropdownMenu>`
button at card right edge):
- **Download** — `window.open(resume.url, "_blank")`. The `url` field from the
  API is a presigned URL (prod) or `/mock/s3/...` path (dev); opening it in a
  new tab triggers browser download.
- **Set as primary** (hidden when `is_primary === true`) — calls
  `setPrimaryResume(candidateId, attachment_id)`, on success invalidates
  `["candidates", "resumes", candidateId]` and `["candidates", "detail",
  candidateId]` (to refresh `primary_resume_id` on the candidate).
- **Delete** — `<ConfirmDialog>` → `deleteResume(...)` → invalidate resumes
  query.

**Upload control:**
- A `<label>` styled as a `<Button variant="outline">` wrapping a hidden
  `<input type="file" accept=".pdf,.doc,.docx,.rtf,.txt,.odt">`. On `onChange`:
  call `uploadResume(candidateId, file, makeItPrimary)` via `useMutation`.
  `makeItPrimary` is a `<Checkbox>` "Upload as primary résumé" (default
  checked when `resumes.length === 0`).
- Show upload progress via a `<Progress>` bar if the file is large; otherwise a
  spinner inline with the button. On success: `toast.success("Résumé
  uploaded")` + invalidate resumes query.
- On HTTP 413: `toast.error("File exceeds 20 MB limit")`.
- On HTTP 400 (content_type disallowed): `toast.error(detail)`.
- On HTTP 400 (`candidate_resume_limit_reached`): `toast.error("Maximum
  résumé limit reached (25)")`.

**File-manager résumé import (stretch):** a secondary "Import from Files"
`<Button>` opens `<FilePickerDialog>` (existing shared component at
`frontend/src/pages/messages/FilePickerDialog.tsx`) in read-only
pick mode. On pick, call a `POST /ui/candidates/:id/resumes` with
`{ source: "file_manager", node_path: pickedNode.path }` (JSON body, no file
bytes). This is additive and may be deferred if CND-005 does not expose a JSON
import path in the first iteration; the UI button is hidden if the endpoint
returns 422.

### 5.5 Query key conventions

All React Query keys for this module follow the pattern:

| Query | Key |
|---|---|
| List candidates | `["candidates", { owner_sub, status, source, cursor }]` |
| Candidate detail | `["candidates", "detail", candidateId]` |
| Résumé list | `["candidates", "resumes", candidateId]` |
| History | `["candidates", "history", candidateId]` |

Invalidations after mutations:
- `createCandidate` → `["candidates"]` (prefix invalidation clears all list queries)
- `updateCandidate` / `deleteCandidate` → `["candidates"]` + `["candidates", "detail", candidateId]`
- `uploadResume` / `setPrimaryResume` / `deleteResume` → `["candidates", "resumes", candidateId]` + `["candidates", "detail", candidateId]`
- `setCandidateOwner` → `["candidates", "detail", candidateId]` + `["candidates"]`

### 5.6 Module disabled state

`ModuleDisabledState` is a small reusable component
(`frontend/src/components/shared/ModuleDisabledState.tsx`) that renders a
centred card with a `ShieldOff` icon and the message: "This module is not
enabled on this instance. Contact your administrator." It accepts an optional
`label` prop for the module name. Used by both `CandidatesPage` and
`CandidateDetailPage` when the API returns 404.

### 5.7 Edge cases

| Scenario | Handling |
|---|---|
| Flag off (backend returns 404 for all CND routes) | Both pages render `<ModuleDisabledState>` |
| Candidate soft-deleted (detail returns 410) | `toast.error("Candidate has been deleted")` + `navigate("/candidates")` |
| Resume upload while another upload is in progress | Upload button disabled (`isPending` from `useMutation`) |
| Resume download URL expired (presigned 300s TTL) | `url` is fetched fresh on each `listResumes` call; React Query `staleTime=0` for the résumés query ensures a fresh URL on every tab focus. `gcTime` defaults to 5 min which is acceptable since the URL is 300s and re-fetching is cheap |
| Candidate has 0 résumés | "No résumés on file" empty state in the Résumés tab; "Upload as primary" checkbox pre-checked and hidden (meaningless when it is the first) |
| 25-résumé cap reached | Upload button disabled with tooltip "Maximum résumé count reached (25)"; the count is derived from `resumesQuery.data?.length ?? 0` |
| Status badge colours | `active`→blue, `qualified`→indigo, `submitted`→yellow, `interviewing`→orange, `placed`→green, `on_hold`→gray, `not_in_search`→red, `archived`→muted |
| Very long `key_skills` (up to 4000 chars) | `<Textarea>` with `max-h-40 overflow-y-auto` in display mode; full `<Textarea>` in edit mode |
| `owner_sub` displayed as UUID | Show raw sub; a follow-on ticket (LED-010 / user-lookup) may enrich it. For now the sub is shown in monospace with a copy button |

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007:** All API calls go through `api/client.ts` which attaches Bearer
tokens and CSRF headers. The frontend never sends raw AWS credentials, signs
S3 URLs, or calls moto directly. Résumé download URLs arrive from the API: dev
returns `/mock/s3/...` paths (handled by the FastAPI mock S3 endpoint), prod
returns 300-second presigned URLs. The frontend code for opening the URL is
identical in both environments (`window.open(resume.url, "_blank")`).

**CSRF:** Every mutating request (POST/PATCH/PUT/DELETE) carries `X-CSRF-Token`
from the `ui_csrf` cookie, set automatically by `client.ts:179`. No
candidate-specific CSRF logic is needed.

**File upload security:** the `<input type="file" accept="...">` attribute
enforces a content-type hint at the browser level, but the backend's
`_validate_content_type` allowlist (CND-005, mirroring KB-003) is the
authoritative gate. The frontend only filters in the UI layer to improve UX.

**Idempotency:** React Query's `invalidateQueries` pattern means all mutations
refetch server state after completion — no client-side optimistic state is
applied to the candidates list or detail (unlike the messaging module's
optimistic messages). This avoids stale-state bugs at the cost of a small
additional round-trip, which is acceptable for a low-frequency recruiting UI.

**No public routes** in this ticket. The CND-005 router serves only under
`/ui/candidates` (session-auth, CSRF enforced). Public career portal features
are Tier-2 ATS work and out of scope here.
