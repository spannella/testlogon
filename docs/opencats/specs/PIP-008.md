# PIP-008 — Pipeline router + admin status-config + registration

**Ticket type:** Feature
**Priority:** P0
**Estimate:** 2 days
**Depends on:** PIP-001, PIP-002, PIP-003, PIP-004, PIP-005, PIP-006, PIP-007

---

## 1. Summary & Goal

PIP-008 is the integration and exposure ticket for the ATS pipeline subsystem. Its
responsibilities are precisely three:

1. **Create `app/routers/ats_pipeline.py`** — one FastAPI router file that mounts
   every service function from PIP-001 through PIP-007 as HTTP endpoints, with
   correct route-ordering (literal segments before dynamic path parameters), the
   admin sub-router for status-config writes, and per-route auth dependencies.

2. **Register both routers in `app/main.py`** inside a flag-gated
   `if _S.ats_pipeline_enabled:` block, identical in structure to the existing
   `if _S.ticket_boards_enabled:` pattern at `app/main.py:699`.

3. **Add `GET /ui/ats/pipeline/feature-status`** — an always-mounted probe (no
   `_require_flag()` call) that returns `{"enabled": S.ats_pipeline_enabled}` so
   the React frontend can decide whether to render the sidebar entry and routes
   without triggering a 503.

After this ticket, every PIP service function is reachable over HTTP. PIP-009
(frontend Kanban + dialogs) and PIP-010 (full E2E suite) depend on this ticket.

### 2.3 Route-ordering gotcha (CLAUDE.md)

CLAUDE.md documents the audit-export `/schedules`-before-`/{export_id}` ordering
requirement: FastAPI matches in declaration order, so literal path segments must
be registered **before** any dynamic `/{…}` segment at the same level. PIP-008
applies this to:

- `GET /ui/ats/pipeline/statuses` must precede any `/{pipeline_id}` route.
- `POST /ui/ats/pipeline/bulk-add` and `bulk-remove` must precede any `/{…}` route.
- `GET /ui/ats/pipeline/by-job/{job_order_id}` and `by-candidate/{…}` are
  themselves literal at the second segment; they precede `entries` and any future
  single-resource `/{pipeline_id}` routes.
- `GET /ui/ats/pipeline/feature-status` must be listed first in the router.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off behavior

When `ATS_PIPELINE_ENABLED=false` (default):

- `GET /ui/ats/pipeline/feature-status` — always mounted, returns
  `{"enabled": false}` with HTTP 200. No `_require_flag()` is called. The
  frontend reads this on initial load to hide/show the "Recruiting" sidebar entry
  and ATS routes in `App.tsx`.
- All other `/ui/ats/pipeline/*` and `/ui/admin/ats/*` routes — not mounted (no
  router registered). FastAPI returns HTTP 404 (not 503) for these paths. The
  `_require_flag()` guard inside each service function provides a secondary 503
  if a route is reached by some other code path, but the primary defense is the
  missing registration.
- No DDB reads or writes occur.

When `ATS_PIPELINE_ENABLED=true`:

- All 14 routes are mounted.
- `_require_flag()` at the top of each service function is a no-op and returns
  immediately.
- `feature-status` returns `{"enabled": true}`.

### 5.2 Route-ordering verification

The router file must declare routes in this exact top-to-bottom order within
`router`:

```
/feature-status          ← always-mounted (separate router)
/statuses                ← GET
/bulk-add                ← POST
/bulk-remove             ← POST
/by-job/{jid}            ← GET (literal "by-job" before dynamic {jid} sub-paths)
/by-candidate/{cid}      ← GET
/entries                 ← POST
/by-job/{jid}/candidate/{cid}            ← DELETE
/by-job/{jid}/candidate/{cid}/status     ← PATCH
/by-job/{jid}/candidate/{cid}/rating     ← PUT
/by-job/{jid}/candidate/{cid}/submit     ← POST
/by-job/{jid}/candidate/{cid}/placement  ← POST (create) + GET (read)
```

FastAPI resolves path params eagerly; `placement` being a literal sub-segment
after two dynamic segments is fine since it follows the DELETE and PATCH which
also share the `{jid}/candidate/{cid}` prefix. The risk of shadowing only applies
when a dynamic param could capture a literal at the same segment depth.

### 5.3 Admin role check detail

Route 3 (`PUT /ui/admin/ats/pipeline/statuses`) calls `require_ui_session` first
(CSRF enforcement + session validity), then checks `normalize_role` inline. A
`role=USER` session results in HTTP 403 with body `{"detail": {"code":
"admin_role_required"}}`. `role=ADMIN` or `role=ROOT` passes through to
`svc.set_status_config`. The `normalize_role` function at `app/auth/roles.py:48`
returns `Role.USER` for any unknown/missing value, so omitted role keys also 403.

### 5.4 CSRF enforcement

All non-GET routes go through `require_ui_session`, which enforces the
`x-csrf-token` header matching both the session's `csrf_token` and the `ui_csrf`
cookie (CLAUDE.md CSRF section). No additional CSRF logic is added in the router.
Bearer-auth requests skip CSRF automatically (handled inside `require_ui_session`).

### 5.5 Empty list responses

`list_pipeline_for_job` and `list_pipeline_for_candidate` return `[]` (empty
array, HTTP 200) when no entries exist for the given job order or candidate.
Neither raises 404 for the empty case. This is consistent with list endpoints
throughout the codebase (e.g., `GET /ui/catalog/items`).

### 5.6 Concurrent PUT to `/statuses`

`set_status_config` performs an unconditional `put_item` (last-write-wins). Two
concurrent admin writes race; the later one wins. No optimistic-lock version check
is applied (OPP-003 §7.2 decision: full replacement, idempotent). The caller
should re-fetch after a successful write to confirm the current state.

### 5.7 Placement GET before placement exists

`GET .../placement` before a placement has been recorded returns HTTP 404 with
`{"detail": {"code": "placement_not_found"}}`. This is the expected response for
a candidate who is in the pipeline but has not yet been placed; the FE Kanban
should handle it gracefully (show a "Record placement" affordance rather than
treating 404 as an error).

### 5.8 `feature-status` accessibility to frontend with flag off

The frontend's initial load calls `GET /ui/ats/pipeline/feature-status` before
the user navigates to any ATS page, using the same `api/client.ts` Axios instance.
Because this endpoint is always mounted and returns 200 (never 503), the Axios
interceptor's 401→logout handler is not triggered. The flag check in the React
component is `isAtsPipelineEnabled()` reading `VITE_ATS_PIPELINE_ENABLED`, with
the API response as a runtime override for cases where the env var was not updated
during a rolling deploy.

### 5.9 `submit_to_client` status code

`POST .../submit` returns HTTP 200 (not 201) because it represents an action
(send email + advance status) rather than resource creation. The response body is
`SubmitToClientOut` which includes `pipeline_id`, `to_emails`, `status_advanced_to`,
`with_resume`, `sent_at`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No `dev_mode` branches in the router

`app/routers/ats_pipeline.py` contains zero `if S.dev_mode` conditionals. The
only env-conditional behavior is in the service layer and its collaborators:
- `send_alert_email` (`app/services/alerts.py:459`) logs to `S.dev_email_log` in
  dev and sends via SES in prod — unchanged by PIP-008.
- `s3_client()` (`app/core/aws_clients.py:114`) hits in-process moto in dev and
  real S3 in prod — unchanged.
- `record_crm_activity` (ACT-009) writes to the same DDB table in both envs.

### 7.2 Idempotency

- `GET /statuses` — pure read, unconditionally idempotent.
- `PUT /admin/.../statuses` — last-write-wins unconditional `put_item`; a retry
  of the same payload produces the same stored state.
- `POST /entries` — conditional put with `Attr("sk").not_exists()`. A retry
  after a 409 `pipeline_entry_exists` indicates the first request succeeded; the
  caller should treat 409 as success on retry.
- `DELETE .../candidate/{id}` — `remove_from_pipeline` raises 404 if the entry
  is absent; callers should treat 404 as success on a retry of a DELETE.
- `PATCH .../status` — `change_status` is idempotent for the same `new_status`
  (no-op path: same-status short-circuits with no write, no audit).
- `PUT .../rating` — unconditional `update_item`; idempotent.
- `POST .../submit` — re-submit re-sends the email and re-logs. Not idempotent at
  the email layer; clients wanting once-only semantics gate in the UI (PIP-009
  "Submit" button disabled after success).
- `POST .../placement` — conditional put; second call → 409 `placement_exists`.

### 7.3 Security

- **Ownership by key**: every service function is partitioned under
  `pk=USER#{owner_sub}`. A caller cannot read or mutate another user's pipeline
  entries by passing a different `job_order_id`; the DDB access pattern returns
  empty/404 for cross-owner attempts (OPP-004 §5).
- **Admin gate**: only the status-config write is admin-gated. All pipeline CRUD
  operations are available to any authenticated user who owns the referenced
  records. This mirrors the OPP pipeline data plane (any user can manage their own
  opportunities); a future per-module ACL ticket (STU-002/003/004) may add
  recruiter-scoped locks.
- **CSRF**: automatically enforced by `require_ui_session` on all non-GET routes
  (`app/services/sessions.py:330`). Bearer-auth (API keys) skips CSRF, but API
  keys are not in scope for this router in the initial rollout (all routes are
  in `API_KEY_ROUTE_EXEMPTIONS`).
- **Input validation**: path params (`job_order_id`, `candidate_id`) are plain
  strings; Pydantic validates request bodies. The service layer performs ownership
  and existence checks before any mutation.
- **Rate limiting**: the existing rate-limit middleware at
  `app/main.py:541` (`rate_limit_middleware_factory()`) applies to all routes
  including pipeline endpoints. No pipeline-specific per-route rate limit is added
  in PIP-008; bulk operations are capped at 100 ids/call by the Pydantic model

## 10. Open Questions / Assumptions

1. **`feature-status` probe always mounted vs. returning 404 when flag off.**
   This spec assumes the probe is placed on a separate always-registered router
   (a third `APIRouter` object in `ats_pipeline.py`). An alternative is to register
   only the probe router unconditionally, and the full router conditionally. The
   spec adopts the former because it is the simplest to test and mirrors the
   newsfeed recsys probe pattern.

2. **Pagination on list endpoints.** `list_pipeline_for_job` and
   `list_pipeline_for_candidate` are specified (PIP-001) to loop
   `LastEvaluatedKey` internally and return all entries as a flat list. For large
   accounts with many pipeline entries this could be slow. A future ticket may add
   cursor-based pagination using `encode_cursor`/`decode_cursor`
   (`app/core/cursor.py:94`), accepting an optional `cursor` query parameter and
   returning `{"entries": [...], "cursor": "..."}`. PIP-008 does not add pagination
   to avoid scope creep; it inherits the PIP-001 decision.

3. **No `placement` sub-resource on `by-candidate` path.** The placement is only
   readable/writable via the `by-job/{jid}/candidate/{cid}/placement` path. If a
   caller only has the `candidate_id` and wants to find placements, they must first
   call `list_pipeline_for_candidate` to discover job-order IDs. A future ticket
   may add `GET /ui/ats/pipeline/by-candidate/{cid}/placements` (plural) returning
   all placements across job orders.

4. **`SubmitToClientOut` shape.** PIP-005 defines `SubmitToClientOut`; if that
   ticket is revised to include additional fields (e.g., `email_message_id`), the
   router response model updates automatically since it delegates to the service
   return value.

5. **`submit_to_client` status code.** The spec uses 200 for the submit action.
   If the team prefers 202 (accepted/async) to signal that email delivery is
   best-effort, the handler can be changed to `status_code=202` without any
   service layer changes.
