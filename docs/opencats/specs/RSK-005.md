## 1. Summary & Goal

`docs/opencats/OPENCATS_GAP_ANALYSIS.md:89` (§D) classifies CSV import for candidates as **PARTIAL/PLANNED**: "export HAVE; lead import LED-008; **candidate import missing**". Line 49 (§A) further notes that duplicate detection + merge is **PLANNED** via LED-009, marked "(reusable if Candidate=Lead)". This ticket closes both gaps for the Candidate entity and the Company entity (soft-dep).

RSK-005 delivers:

1. **`app/services/candidate_import.py`** — a synchronous CSV-parse-validate-create pipeline for candidates, structured exactly like `LED-008`'s `import_leads_from_csv` (see `docs/suitecrm/specs/LED-008.md` §4.1). Columns map directly to `CandidateCreateIn` (CND-001/002); the `key_skills` column is split and passed to RSK-001's `assign_skill` so the skill store is populated as a side-effect of every import row.

2. **`app/services/candidate_merge.py`** — a thin candidate-scoped analogue of `LED-009`'s `find_duplicates` / `merge_leads` (`docs/suitecrm/specs/LED-009.md` §4.2), reusing the same "primary wins; secondary back-fills null fields; secondary soft-deleted with `merged_into`" merge semantics. This file is the designated home for candidate-level dedupe/merge logic until CND-002 or a later CND ticket absorbs it.

3. **Two import endpoints** (`POST /ui/candidates/import/csv`, `POST /ui/companies/import/csv` [PTY/CCT router TBD]) and **two dedupe/merge endpoints** (`GET /ui/candidates/{candidate_id}/duplicates`, `POST /ui/candidates/{candidate_id}/merge`) on the existing candidates router (`app/routers/candidates.py` from CND-005, `prefix="/ui/candidates"`) — all declared as static-segment paths before any dynamic `/{candidate_id}` route (CLAUDE.md FastAPI declaration-order gotcha; `docs/opencats/ATS_RESUME_SKILLS_TICKETS.md` cross-cutting constraint §5). CORRECTED from original draft which incorrectly used `/ui/ats/candidates/...`.

All behavior is gated by `S.candidates_enabled` (default `False`, owned by CND-001). With the flag off the platform is byte-for-byte unchanged.

### 3.2 Candidates table — additive attributes written by `candidate_merge.py`

The merge service writes two new optional attributes onto the secondary candidate's META row (`pk="CANDIDATE#{candidate_id}"`, `sk="META"`). These are the exact LED-009 §3.2 equivalents:

| Attribute | DDB type | Notes |
|---|---|---|
| `merged_into` | S (optional) | `candidate_id` of the primary when this record was merged; written on the secondary only |
| `merged_at` | N (optional) | Unix timestamp of the merge; written on the secondary only |

These attributes are additive — all existing `CANDIDATE#` META rows continue to work without them. `CandidateOut` (CND-001) gains these as optional fields with `None` default.

A merge `ACTIVITY#` sub-item is also written on the primary candidate's partition (LED-009 §3.3 pattern, adapted for `pk="CANDIDATE#{primary_id}"`):

| Attribute | Value |
|---|---|
| `pk` | `"CANDIDATE#{primary_candidate_id}"` |
| `sk` | `"ACTIVITY#{ts}#{activity_id}"` — same inverted-timestamp pattern as `app/services/call_history.py:28` |
| `activity_type` | `"merged_from"` |
| `actor_id` | `actor_sub` |
| `metadata` | `{"secondary_candidate_id": ..., "fields_merged": [...]}` |

### 3.3 ByEmail GSI on the `candidates` table — CORRECTED

**CORRECTED**: CND-002 does not introduce a `ByEmail` GSI4 analogous to LED-007's GSI4 on the `leads` table. CND-002's `find_candidate_by_email` queries the `ByStatus` GSI2 with a `FilterExpression` on the `email` attribute (CND-002 §4.3: "Queries ByStatus GSI across all statuses … returns the first non-deleted match or None"). The `candidates` table at CND-002 completion still has exactly three GSIs: `ByOwner` (GSI1), `ByStatus` (GSI2), `BySource` (GSI3) — the same three defined by CND-001 §3.4.

If a true `ByEmail` GSI is desired for O(1) email lookup (rather than the current scan-with-filter), it must be added by a future CND ticket and declared as GSI4 with `attr_types={"GSI4SK": "N"}`. Until then, `find_candidate_by_email` is correct but involves a GSI + FilterExpression rather than a hash lookup. This means the duplicate detection step in RSK-005 import is O(N) against the ByStatus index rather than O(1) — acceptable at MVP scale but worth noting.

RSK-005 continues to use `find_candidate_by_email` (CND-002) as-is. The `find_candidate_duplicates` service (§4.2.2) queries `ByStatus` GSI2 via `find_candidate_by_email` for email-based duplicate detection. Phone-based duplicate detection (below) requires the ByPhone GSI5 added in this ticket.

#### 4.1.2 `import_candidates_from_csv`

```python
def import_candidates_from_csv(
    owner_sub: str,
    csv_bytes: bytes,
    *,
    skip_duplicates: bool = True,
) -> dict:
    """Parse csv_bytes as UTF-8 CSV, validate each row, and bulk-create
    Candidate records.

    Returns: {"imported": int, "skipped": int, "errors": [{"row": int, "reason": str}]}
    """
```

Implementation steps (mirroring LED-008 §4.1.2 step-by-step):

1. **Flag guard**: `if not S.candidates_enabled: raise HTTPException(503, {"code": "candidates_disabled"})`.
2. **Decode**: `text = csv_bytes.decode("utf-8-sig", errors="replace")` — `"utf-8-sig"` strips the Excel BOM transparently (LED-008 §5.5).
3. **Parse**: `reader = csv.DictReader(io.StringIO(text))`.
4. **Header validation**: `missing = {"email"} - set(reader.fieldnames or [])`. If non-empty → `HTTPException(422, "CSV must contain an 'email' column")`. Extra columns silently ignored.
5. **Row iteration** (up to `MAX_IMPORT_ROWS`):
   a. Strip all fields: `row = {k: (v or "").strip() for k, v in raw_row.items()}`.
   b. Sanitize all string values via `_sanitize_csv_field` (imported from `app.services.csv_export:43`; not copied).
   c. **Required field check**: empty `email` → per-row error, `continue`.
   d. **Email pre-validate**: `normalize_email(row["email"])` in `try/except HTTPException`. On failure → per-row error, `continue`. Store `norm_email`.
   e. **Duplicate check**: `find_candidate_by_email(norm_email)` (CND-002). If match found and `skip_duplicates=True` → increment `skipped`, `continue`. If `skip_duplicates=False` → proceed (`create_candidate` handles idempotent email collision via its own 409 guard; RSK-005 increments `imported` when the call succeeds, not `skipped`, to signal the caller that the row was "processed" per their explicit opt-out — same semantics as LED-008 §5.4).
   f. **Build `CandidateCreateIn`**: map columns using a helper `_row_to_candidate_create(row, owner_sub)` (see §4.1.3).
   g. **Pydantic validation**: `try CandidateCreateIn(...)` — `except ValidationError` → per-row error, `continue`.
   h. **Create**: `create_candidate(owner_sub, model)` in `try/except HTTPException` — 409 from duplicate guard → `skipped++`; 4xx other → per-row error; success → `imported++`.
   i. **Key-skills assignment**: after successful `create_candidate`, split `row.get("key_skills", "")` on `[;,]` regex, strip tokens, call `assign_skill("candidate", new_candidate_id, skill_token, actor_sub=owner_sub)` per non-empty token in a best-effort `try/except Exception: pass` loop. A skill assignment failure NEVER rolls back the candidate row (same "best-effort enrich" posture as RSK-002 extraction hooks in CLAUDE.md GAP-0223).
6. **Row cap**: after `MAX_IMPORT_ROWS` rows, break loop + append synthetic error `{"row": MAX_IMPORT_ROWS + 1, "reason": "import truncated at 5000-row limit"}` (LED-008 §5.7).
7. **Audit**: `audit_event("candidate_import.completed", owner_sub, imported=imported, skipped=skipped, error_count=len(errors))` — one event per import, not per row (LED-008 §2.8).
8. Return `{"imported": imported, "skipped": skipped, "errors": errors}`.

```python
def find_candidate_duplicates(candidate_id: str) -> list[dict]:
```

#### 4.2.3 `merge_candidates(primary_id: str, secondary_id: str, actor_sub: str) -> dict`

```python
def merge_candidates(
    primary_id: str,
    secondary_id: str,
    actor_sub: str,
) -> dict:
```

Mirrors LED-009 §4.2 `merge_leads` step-by-step:

1. **Idempotency guard**: if secondary `status == "archived"` and `secondary.merged_into == primary_id` → return `get_candidate(primary_id)` (already merged, no-op, no DDB write).
2. **Conflict guard**: primary `deleted_at` set → 409 "primary candidate is deleted". `primary_id == secondary_id` → 400 "cannot merge a candidate with itself". Secondary `deleted_at` set and `merged_into != primary_id` → 409 "secondary candidate already merged elsewhere".
3. **Scope guard**: both `primary.created_by == actor_sub` and `secondary.created_by == actor_sub`, OR actor is admin/root (checked by the router layer; the service trusts the router). On failure → 403 "actor does not own both candidates".
4. **Back-fill**: iterate `CANDIDATE_MERGEABLE_FIELDS`: if `primary[field]` is `None`/empty and `secondary[field]` is non-empty → `updates[field] = secondary[field]`; `fields_merged.append(field)`.
5. **Writes** (in order):
   - `T.candidates.put_item(Item={...primary_item, **updates, "updated_at": now_ts()})` — full overwrite (same technique as CND-002 §4.2 GSI rewrite via `put_item`). If `phone` was back-filled, also write `GSI4PK`/`GSI4SK` (CORRECTED: ByPhone is GSI4, not GSI5 — see §3.4 renumbering note).
   - `T.candidates.update_item` on secondary: set `status="archived"`, `merged_into=primary_id`, `merged_at=now_ts()`, `deleted_at=now_ts()`, `GSI2PK="STATUS#archived"`, `GSI2SK=now_ts()`.
   - `T.candidates.put_item` for the ACTIVITY sub-item on primary (§3.2 above).
   - `audit_event("candidate.merged", actor_sub, primary_candidate_id=primary_id, secondary_candidate_id=secondary_id, fields_merged=fields_merged)`.
6. Returns `get_candidate(primary_id)` with a transient `_fields_merged_tmp` key (stripped by router) so the router can populate `CandidateMergeOut` without a second fetch.

## 5. Detailed Behavior & Edge Cases

### 5.1 Column header matching (case-sensitive, BOM-safe)

`csv.DictReader` uses the first row as field names. Header matching is case-sensitive. The `"utf-8-sig"` decoder strips the Excel BOM so `email` is never silently corrupted to `﻿email` (LED-008 §5.5). Extra columns beyond `CANDIDATE_CSV_COLUMNS` are silently ignored.

### 5.2 `first_name` / `last_name` absent or empty

Unlike `email`, first/last name are not required columns in the CSV. If absent or blank, `_row_to_candidate_create` substitutes `"Unknown"` — a deliberately searchable placeholder. The recruiter can later edit the record. This avoids import failure for CSVs that have only email + skills (minimal ATS seed data).

### 5.3 `key_skills` parsing and skill assignment ordering

The `key_skills` column is parsed **after** the candidate row is successfully created (step 5i in §4.1.2). If the create call fails (Pydantic error or DDB write error), skill assignment is not attempted. Skill tokens are split on the regex `[;,]` and stripped; empty tokens (e.g., from trailing delimiters) are skipped. Each non-empty token is passed to `assign_skill("candidate", new_id, token, actor_sub=owner_sub)`. A failure on one skill token does not affect other skills or the already-persisted candidate row (best-effort, `try/except Exception: pass` per token).

### 5.4 Duplicate detection semantics

`find_candidate_by_email` (CND-002) queries the `ByStatus` GSI2 with a `FilterExpression` on the `email` attribute filtering to non-deleted rows (CORRECTED — no ByEmail GSI4 exists; see §3.3). The query is scoped to `CANDIDATE#` partition keys; no `PROSPECT#` or `LEAD#` rows are written to the `candidates` table, so entity scoping is inherent. This makes duplicate detection entity-scoped: a Candidate's email matching an existing Lead does not count as a duplicate for the purpose of candidate import. The `skip_duplicates=True` default increments `skipped` and continues to the next row; `skip_duplicates=False` calls `create_candidate` which returns 409 on email collision — RSK-005 treats that 409 as a `skipped` increment to give accurate counts (same LED-008 §5.4 semantics).

### 5.5 `can_relocate` parsing

The `can_relocate` CSV field is free-text. `_row_to_candidate_create` normalizes to `bool`: case-insensitive `"true"`, `"yes"`, `"1"` → `True`; anything else → `False`. A blank/absent field → `False` (the `CandidateCreateIn` default). This avoids a validation error for the most common CSV exports which omit this column.

### 5.6 Phone normalization failures

`normalize_phone` at `app/core/normalize.py:66` raises `HTTPException(400)` on invalid format. In the import context, a bad phone must not abort the row (phone is optional). `_row_to_candidate_create` passes `phone=row.get("phone") or None`; the service-layer `create_candidate` calls `normalize_phone` only when `phone` is non-null. If `create_candidate` raises 400 from `normalize_phone`, RSK-005's step 5h catches the `HTTPException` and records a per-row error — the row is not imported. This differs from LED-008 §5.3 (which discards the phone silently and imports anyway) because `create_candidate` centralizes the normalization; RSK-005 cannot suppress the 400 post-normalization. The difference is documented in §10 Open Questions.

### 5.7 Row cap and partial-success semantics

The 5000-row cap (§4.1.1 `MAX_IMPORT_ROWS`) is enforced by a counter in the loop. All rows up to 5000 are processed; row 5001 onward is dropped, and a synthetic error entry is appended (LED-008 §5.7). The endpoint returns `200 OK` even when some rows failed — partial success. There is no transactional rollback: rows 1–N that succeeded are already committed to DynamoDB regardless of later row failures (LED-008 §5.8 accepted partial-failure design).

### 5.8 Merge idempotency (replay safety)

Identical to LED-009 §5.1: if `merge_candidates(A, B, actor)` is called twice, the second call detects `secondary.status == "archived" AND secondary.merged_into == A` and returns `get_candidate(A)` with no DDB write. This makes the endpoint safe for at-least-once delivery (network retry after server-commit but before client-receive).

### 5.9 Merge of a candidate with a résumé attachment

If the secondary candidate has `primary_resume_id` set, this field is excluded from `CANDIDATE_MERGEABLE_FIELDS` (§4.2.1). The résumé attachments (`ATTACHMENT#` sub-items on the secondary's partition) are NOT migrated to the primary during merge — they remain on the soft-deleted secondary. A follow-up action (CND-003's résumé re-attach endpoint, if implemented) would let the recruiter manually promote the secondary's résumé onto the primary. Silently inheriting a résumé pointer without re-attaching the S3 key could create dangling references.

### 5.10 Concurrent merge race

Two concurrent `POST /ui/candidates/A/merge` calls with the same `secondary_id=B` may both see B as active, then both attempt to soft-delete B. DynamoDB `update_item` is last-write-wins; both calls succeed functionally (idempotent field back-fill on A, harmless double-write on B's `deleted_at`). For stricter exactly-once, add `ConditionExpression=Attr("deleted_at").not_exists()` to the secondary's `update_item` — this is noted in §10 Open Questions.

### 5.11 CSV injection prevention

`_sanitize_csv_field` (imported from `app/services/csv_export.py:43`) prepends `'` to any field value starting with `=`, `+`, `-`, `@`, `\t`, or `\r`. This prevents stored strings from executing as formulas if the recruiter later exports the candidate data as CSV (LED-008 §7.3). All string values from the CSV pass through this sanitizer at step 5b before being used.

### 5.12 Company import soft-dependency guard

`import_companies_from_csv` raises `HTTPException(503, {"code": "companies_module_unavailable"})` immediately when `app.services.companies` cannot be imported. This guard uses a `try/except ImportError` at the top of the function body, identical to CND-002 §5.7's LED-010 shim pattern. The guard means the company import endpoint ships in the same PR as the candidate import endpoint but safely no-ops until PTY/CCT company services land.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 — no `dev_mode` branch

Neither `candidate_import.py` nor `candidate_merge.py` contains any reference to `S.dev_mode`. All DynamoDB access goes through `T.candidates` (the `_safe_table`-wired frozen handle) and `T.ats_skills` (RSK-001). In dev, moto intercepts these handles in-process; in prod, real DynamoDB is used. The code path is structurally identical (same guarantee as LED-008 §7.1, CND-002 §7.1). No mock data paths, no inline-seeded rows, no special-cased S3 URLs. `audit_event` writes to `T.alerts` DDB-only — no SES branch.

### 7.2 Idempotency

- **Import (upload-level)**: not natively idempotent. Re-submitting the same CSV with `skip_duplicates=True` results in `skipped=N`, `imported=0` on the second call. With `skip_duplicates=False`, a second submission hits `create_candidate`'s 409 guard for each row — RSK-005 counts these as `skipped`.
- **Import (row-level)**: each row is idempotent under `skip_duplicates=True` because `find_candidate_by_email` gates the create call.
- **Merge**: idempotent on exact replay (§5.8). Not idempotent if secondary was previously merged into a different primary (409).
- **Skill assignment**: `assign_skill` is idempotent per RSK-001 §Description; re-assigning the same skill to the same candidate does not double-count or double-write.

### 7.3 CSV injection prevention

`_sanitize_csv_field` (from `app/services/csv_export.py:43`) is applied to every field in every row at step 5b, before any Pydantic model construction or DDB write. This prevents formula-injection payloads from being stored verbatim (LED-008 §7.3). Pydantic length constraints (`max_length` on `CandidateCreateIn` fields) prevent oversized payloads from reaching DynamoDB.

### 7.4 Authentication and authorization

All four endpoints require a valid `ui_session` cookie or Bearer token. CSRF is enforced automatically by `require_ui_session` (`app/auth/deps.py`) for all `POST` cookie-auth requests. Bearer-auth requests bypass CSRF per the CLAUDE.md auth pattern. No additional RBAC beyond `require_ui_session` is required for import: any authenticated recruiter can import candidates into their own account. The merge scope guard (`created_by == actor_sub`, §4.2.3 step 3) prevents a user from soft-deleting another recruiter's candidate by designating it as the secondary in a merge — enforced at the service layer so it holds regardless of the router caller.

### 7.5 Rate limiting

No per-endpoint rate limiting is introduced for MVP. The standard platform middleware (if any) applies. A future ticket could add a per-user import-count rate limit to prevent abuse of the 5000-row-per-call allowance (same deferral rationale as LED-008 §7.5).

### 7.6 Partial import atomicity

RSK-005 does not implement transactional batch writes. Each row is created independently (LED-008 §5.8 accepted design). Rows 1–N that succeed are already committed to DynamoDB before row N+1 fails. There is no rollback. This is consistent with SuiteCRM, Salesforce, and HubSpot bulk import UX.

## 8. Backward Compatibility & Migration

### 8.1 Existing endpoints and models

RSK-005 introduces four new routes and five new Pydantic model classes. No existing route, model, service function, DynamoDB table, or frontend component is modified. When `CANDIDATES_ENABLED=0` (the default), all four routes return 404 and are invisible to existing callers.

### 8.2 GSI5 (`ByPhone`) on an existing `candidates` table

If CND-001 through CND-002 have been deployed before RSK-005 ships, the `candidates` table exists with **three GSIs** (GSI1 ByOwner, GSI2 ByStatus, GSI3 BySource) — CORRECTED: CND-002 does not add a ByEmail GSI4 (see §3.3). RSK-005 adds one new GSI (`ByPhone`, declared as GSI4 since the prior GSI4 slot is free). Adding `ByPhone` follows the same playbook as LED-009 §8.1:

- **Dev**: `just restart` drops and recreates the table with all five GSIs. No migration needed.
- **Prod (preferred)**: deploy CND-001 through RSK-005 in a single release. `scripts/local-ddb-init.py` creates the table with all five GSIs at once.
- **Prod (incremental)**: run a one-time migration script that calls `update_table(GlobalSecondaryIndexUpdates=[{"Create": {...}}])`. GSI backfill is asynchronous; `find_candidate_duplicates` degrades gracefully to email-only detection until backfill completes.

### 8.3 `merged_into` / `merged_at` on existing candidate rows

No existing `CANDIDATE#` META rows carry `merged_into` or `merged_at`. These attributes are additive. `CandidateOut` gains them as `Optional` fields with `None` default — existing serialization is unaffected.

### 8.4 `GSI4PK` on pre-existing candidate rows (CORRECTED: ByPhone is GSI4)

Candidate rows written before RSK-005 ships do not carry `GSI4PK`. Phone-based duplicate detection will not surface pre-existing pairs until one of the candidates is updated (which rewrites the full META row including `GSI4PK` when `phone` is set). A backfill script can optionally scan all `CANDIDATE#` rows with non-null `phone` and write `GSI4PK`/`GSI4SK` — not required for correctness but desirable for data completeness (LED-009 §8.2 same guidance).

### 8.5 No data migration required

The `candidates` table and `ats_skills` table start empty (net-new per gap analysis). No legacy candidate or skill data needs migration. Enabling `CANDIDATES_ENABLED=1` on a live instance with an existing `candidates` table is safe.

## 10. Open Questions / Assumptions

1. **Phone normalization failure in `create_candidate`**: LED-008 §5.3 silently drops a bad phone (stores `phone=None`) and imports the row anyway. CND-002's `create_candidate` applies `normalize_phone` internally and raises HTTP 400 on failure, which RSK-005 then catches as a per-row error. This means a row with a bad phone value is NOT imported, whereas the LED-008 approach would import it with phone omitted. If the desired behavior is "silently drop bad phone + import the row", the recommendation is either: (a) strip the phone column in `_row_to_candidate_create` before passing to `create_candidate`, or (b) add a pre-validate step in `_row_to_candidate_create` that calls `normalize_phone` in `try/except` and passes `None` on failure. Option (b) matches LED-008 §5.3 semantics more closely and should be chosen before implementation.

2. **ByEmail GSI on the `candidates` table — RESOLVED (CORRECTED)**: CND-002's `find_candidate_by_email` does NOT use a `ByEmail` GSI4. It queries the existing `ByStatus` GSI2 with a `FilterExpression` on the `email` attribute (CND-002 §4.3: "Queries ByStatus GSI across all statuses … returns the first non-deleted match or None"). A dedicated ByEmail index comparable to LED-007's GSI4 on `leads` is not present in either CND-001 or CND-002. If O(1) email lookup is desired later, a future CND ticket must add it and declare `attr_types={"GSI4SK": "N"}` (since ByPhone will occupy the GSI4 slot after RSK-005, the new ByEmail index would be GSI5). The implementing engineer must NOT assume a ByEmail GSI4 exists before RSK-005 is merged.

3. **Concurrent `create_candidate` race during import**: `asyncio.to_thread` runs `import_candidates_from_csv` on a thread pool thread with a single-threaded event loop per uvicorn worker. Two concurrent import calls can race on the same email; CND-002's `find_candidate_by_email` check is non-atomic. Duplicate rows are possible. This is an accepted limitation (same as LED-008 open question #3 "Partial-success HTTP status" / CND-002 §10.2 "Concurrent create race for same email" — CORRECTED: LED-008 §10 is a numbered list of open questions, not sub-sections; there is no "§10.2" heading in LED-008); LED-009 / RSK-005's merge tooling is the resolution path.

4. **Company import column schema**: The `COMPANY_CSV_COLUMNS` list above (`company_name`, `industry`, etc.) is a reasonable default. The canonical column set should be aligned with the PTY/CCT company entity schema when those tickets land. If PTY/CCT use different field names, `_row_to_company_create` will need to be updated. The company import function is implemented as a stub (`HTTPException(503)` guard) until PTY/CCT is confirmed.

5. **Merge of a candidate with pipeline entries**: If the secondary candidate is active in any pipeline stage (via PIP-001+ job-order junction rows), those rows are NOT migrated to the primary by this merge. Pipeline entries live on a separate `pipeline` table owned by PIP-001. A future cross-ticket could add a post-merge pipeline re-attribution step. Assumption for RSK-005: pipeline entries are considered secondary-candidate-scoped and remain orphaned (their candidate pointer goes to an archived record); this matches LED-009 §5.6 handling of converted leads.

6. **Strict exactly-once merge vs. last-write-wins**: The current `merge_candidates` uses `update_item` without a `ConditionExpression` on the secondary. A `ConditionExpression=Attr("deleted_at").not_exists()` could prevent double-soft-delete on concurrent merges. This is a straightforward one-line addition and is recommended for production hardening before the endpoint goes live; it is left as an open question to confirm the desired behavior with the engineering lead.
