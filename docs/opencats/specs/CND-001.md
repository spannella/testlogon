## 1. Summary & Goal

CND-001 is pure scaffolding. It delivers the entire static foundation that every other ticket in the CND cluster requires before it can compile or run:

- One master feature flag `S.candidates_enabled` (default `False`) that gates the entire Candidate module.
- Six settings keys for table name, S3 bucket/prefix, and upload limits.
- One new DynamoDB single table `candidates` with `PK=pk` / `SK=sk` and three GSIs (`ByOwner`, `ByStatus`, `BySource`), with correctly declared numeric `attr_types` on every GSI sort key.
- One new table handle `T.candidates` in `app/core/tables.py`.
- All Pydantic request/response models (`CandidateCreateIn`, `CandidateUpdateIn`, `CandidateOut`, `CandidateResumeOut`) and the sentinel sets `CANDIDATE_STATUSES` / `CANDIDATE_SOURCES`, appended to `app/models.py`.

No router, no service logic, no frontend code, and no background tasks are introduced here. With the flag off — the default — the platform is byte-for-byte unchanged: no new routes, no writes, no existing file is modified destructively.

## 3. Data Model

### 3.1 `candidates` DynamoDB table — overview

Single-table design with `PK=pk` (String) / `SK=sk` (String). Two row types share the table:

- **META rows** — one per candidate, `sk="META"`. Written by CND-002.
- **ATTACHMENT sub-items** — one per résumé, `sk="ATTACHMENT#{attachment_id}"`. Written by CND-003.
- **ACTIVITY sub-items** (fallback) — one per change event, `sk="ACTIVITY#{inverted_ts}#{activity_id}"`. Written by CND-004's LED-012-style fallback path when ACT-009 is absent.

All three row types share the same `PK=CANDIDATE#{candidate_id}`, enabling single-table item-collection reads.

### 3.3 Three GSIs

| Index name | PK | SK | Type | Purpose |
|---|---|---|---|---|
| `ByOwner` | `GSI1PK` (S) | `GSI1SK` (N) | `ProjectionType: ALL` | List candidates by recruiter, sorted newest-first |
| `ByStatus` | `GSI2PK` (S) | `GSI2SK` (N) | `ProjectionType: ALL` | List candidates by pipeline status, sorted newest-first |
| `BySource` | `GSI3PK` (S) | `GSI3SK` (N) | `ProjectionType: ALL` | List candidates by source attribution, sorted newest-first |

This GSI layout is intentionally **identical to the `leads` table** described in LED-001 (three GSIs, same PK/SK naming, all numeric sort keys) so that CND-002's service logic can be a structural mirror of `app/services/leads.py`, and the LED-009 merge engine can operate uniformly across both entity types.

### 3.4 `TableDef` entry for `scripts/local-ddb-init.py`

```python
TableDef(
    _resolve_table_name(S.candidates_table_name, "candidates"),
    "pk",
    "sk",
    gsi=[
        {"index_name": "ByOwner",  "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "ByStatus", "partition_key": "GSI2PK", "sort_key": "GSI2SK"},
        {"index_name": "BySource", "partition_key": "GSI3PK", "sort_key": "GSI3SK"},
    ],
    attr_types={
        "GSI1SK": "N",
        "GSI2SK": "N",
        "GSI3SK": "N",
    },
),
```

The `attr_types` block declares the three GSI sort key aliases as numeric. `created_at` is a plain item attribute (not a key schema attribute) and must NOT appear in `attr_types` — `_attribute_definitions` in `scripts/local-ddb-init.py:2496–2506` only adds `attr_types` entries to `AttributeDefinitions`; including a non-key attribute there causes DynamoDB to raise `ValidationException: Number of attributes in KeySchema does not exactly match number of attributes defined in AttributeDefinitions`. This matches exactly the LED-001 `leads` table which uses the identical GSI alias scheme and declares only `attr_types={"GSI1SK": "N", "GSI2SK": "N", "GSI3SK": "N"}` (confirmed at `docs/suitecrm/specs/LED-001.md:125`). Tables where `created_at` IS in `attr_types` (e.g., `BroadcastSessions` at `scripts/local-ddb-init.py:722–730`) use `created_at` directly as a GSI sort key name — not an alias.

## 5. Detailed Behavior & Edge Cases

### 5.1 `status` default and `archived` semantics

When `CandidateCreateIn.status` is `None`, the CND-002 service defaults it to `"active"`. The value `"archived"` is written by `delete_candidate` (CND-002) as part of the soft-delete path — external callers SHOULD NOT set `status="archived"` via a PATCH (the router may reject it or warn; the specification defers that enforcement to CND-005). `archived` items are excluded from `list_candidates` by default unless an explicit `status="archived"` filter is passed; the `deleted_at` FilterExpression exclusion (used by CND-002) provides the canonical filter.

### 5.2 `email` uniqueness

CND-001 does not model email uniqueness at the DynamoDB layer (no unique constraint). CND-002 will perform a same-email-active short-circuit check using a `find_candidate_by_email` helper (querying the ByStatus GSI with a `FilterExpression` on `email`). True fuzzy deduplicate-and-merge is delegated to LED-009 (gap analysis §A line 49).

### 5.3 `date_available` format

The field is stored as a free-form string to match OpenCATS' original schema. At the service layer (CND-002), if `date_available` is non-null, it MUST match `YYYY-MM-DD`; the service raises `HTTPException(400, "date_available must be YYYY-MM-DD")` on format failure. The Pydantic model enforces only `max_length=10`; this gives a clean 422 for strings longer than 10 characters before reaching the service, while the format check remains at the service layer (consistent with the normalization-at-service pattern).

### 5.4 `key_skills` free-text vs. structured tags

The gap analysis (§A line 48) notes that OpenCATS dropped résumé parsing and replaced structured tags with free-text skill blobs. CND-001 models `key_skills` as a free-text `Optional[str]` (max 4000 chars). A structured skill-tag registry is a separate Tier-2 ticket in the gap analysis and is explicitly out of scope for CND.

### 5.5 GSI fan-out consistency

All three GSI key pairs (`GSI1PK`/`GSI1SK`, `GSI2PK`/`GSI2SK`, `GSI3PK`/`GSI3SK`) must be written on every `put_item` call, including updates. CND-002 uses a full `put_item` overwrite (not `update_item`) when `status` or `source` changes — the same technique as LED-003 §5.5 — because DynamoDB does not allow atomic updates to GSI partition keys via `update_item`. Forgetting to re-write all three GSI pairs on status change would leave stale entries in the ByStatus and BySource indexes.

### 5.6 Sub-item SK prefixes must not collide

The `candidates` table's single-table design uses SK prefixes as row-type discriminators. The three current prefixes are: `"META"`, `"ATTACHMENT#"`, and `"ACTIVITY#"`. No future ticket in this cluster may introduce a sub-item whose SK prefix is a prefix-of or equal to an existing one. The `ATTACHMENT#` prefix mirrors KB-003's `ATTACHMENT#` convention. The `ACTIVITY#{inverted_ts}#{id}` prefix follows the inverted-timestamp single-table activity-row pattern from `app/services/call_history.py:31` (`9999999999999 - created_at`) and ACT-009's per-entity timeline (CND-004 §2.5, §3.1) — NOT LED-012: LED-012 stores activity rows in the existing `activity_feed` table via a sparse `ByTarget` GSI with `SK={ts}#{activity_id}`, not as `ACTIVITY#` sub-items on the entity's own table (`docs/suitecrm/specs/LED-012.md:16-17,29-33`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

CND-001 introduces zero runtime behaviour — no S3 calls, no DDB writes, no auth checks. The downstream tickets that introduce behaviour (CND-002 through CND-005) must respect SECOPS-007 with two specific exemptions:

1. **`_make_download_url` in CND-003** is the single allowed `S.dev_mode` branch (dev → `/mock/s3/...`, prod → `generate_presigned_url(..., ExpiresIn=300)`), copied verbatim from `app/services/kyc_partner_api.py:630–641`.
2. **`scripts/local-ddb-init.py`** is dev-only infrastructure by nature — no prod parity concern.

All other code paths must use the same DDB handles (`T.candidates`) and S3 factory (`s3_client()` from `app/core/aws_clients.py:114`) for both dev (moto in-process) and prod (real AWS). The `asyncio.to_thread` pattern for calling sync service functions from async routers (`app/routers/google_drive_integration.py` reference pattern) is required; no inline `await` on sync DDB calls.

### 7.2 Idempotency in `scripts/local-ddb-init.py`

`_table_defs()` is called on every `just restart` which wipes and re-creates tables from scratch. The `TableDef` entry for `candidates` must be idempotent — `local-ddb-init.py` already handles "table already exists" via a `try/except ResourceInUseException` wrapper, so no special handling is required in the `candidates` entry itself.

### 7.3 Models are flag-independent

The Pydantic models (`CandidateCreateIn`, `CandidateUpdateIn`, `CandidateOut`, `CandidateResumeOut`) must import cleanly and serialize/deserialize correctly regardless of the flag state. They are pure Python data classes with no DynamoDB or S3 dependencies. An `ImportError` in `app/models.py` would crash the entire FastAPI app at startup — this is a P0 risk.

### 7.4 Sensitive fields

`email` and `email_raw` are PII. Audit events emitted by CND-002 must not log the full email in plaintext; the `email` field in `audit_event` calls should use only the candidate_id and the normalized email (which is low-sensitivity) — consistent with the pattern in `kyc_cases.py` audit calls which log case IDs, not document content.

`linkedin_url` and `web_url` accept user-supplied URL strings. The Pydantic model enforces max_length only. The CND-005 router must NOT follow or render these URLs server-side (no SSRF risk). They are display-only fields stored as opaque strings.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact when flag is off

With `CANDIDATES_ENABLED` absent or set to `"0"` / `"false"`:

- `T.candidates` is wired at import time but points to a DynamoDB table that may not exist in the default dev environment (until `just restart` runs). The `_safe_table` wrapper is lazy — it only raises on actual calls, not on handle construction. No existing code path calls `T.candidates`, so this is safe.
- The Pydantic models in `app/models.py` are defined classes with no side effects. Their presence does not alter existing serialization or import paths.
- The `settings.py` additions are pure environment-variable reads with safe defaults; they do not interfere with any existing setting.

### 8.2 `just restart` creates the table

After CND-001 is merged, a `just restart` (which calls `scripts/local-ddb-init.py`) will create the `candidates` table with all three GSIs. This is a one-time additive operation. Pre-existing dev environments that skip `just restart` will experience a `ResourceNotFoundException` if service code is deployed before the table is created — the standard mitigation is to always `just restart` after merging infrastructure changes.

### 8.3 No prod migration required

The `candidates` table is net-new. There is no data migration. In production, the table must be created via Terraform / CloudFormation before the feature flag is enabled. Standard runbook: (1) create table + GSIs, (2) deploy code with flag off, (3) smoke test, (4) enable flag.

### 8.4 LED convergence path

The GSI naming convention (`GSI1PK`/`GSI1SK` etc.) is intentionally identical to the `leads` table so that a future refactoring can unify the two services under a common base class or shared helpers. CND-001 does not anticipate that refactoring — it establishes only the structural precondition for it.

## 10. Open Questions / Assumptions

1. **`CANDIDATE_SOURCES` closed vs. open set.** The current design uses a closed `pattern=` regex for `source`, consistent with LED-002's `LEAD_SOURCES`. If the career-portal cluster (gap analysis §D) introduces sources dynamically (e.g., per-job-board slug), the `source` field may need to shift to a free-text field with a looser validation. This is deferred to the career-portal ticket (CMP-001 equivalent).

2. **`date_available` timezone semantics.** The field is stored as `YYYY-MM-DD` string without timezone. "Available from 2026-07-01" is interpreted as a wall-clock date in the recruiter's local timezone. No TZ normalization is performed. If cross-timezone recruiting workflows require UTC normalization, this needs a migration later.

3. **`owner_sub` vs. `assigned_to`.** The Lead model uses `assigned_to` (LED-002 §3); this spec uses `owner_sub` for semantic clarity (a recruiter "owns" a candidate record). The LED-010 owner-assignment delegation in CND-002 will bridge the two field names if the LED assignment service uses `assigned_to` as its canonical key. If LED-010 ships with `owner_sub` as its canonical key, no bridging is needed. Assumption: CND-002 stores `owner_sub` internally and the LED-010 delegation adapter handles any field-name translation.

4. **`key_skills` encoding.** Free-text up to 4000 chars covers comma-separated tags, prose, or structured YAML. No normalization is applied. Full-text search against `key_skills` requires either a DynamoDB FilterExpression (expensive full-scan on the ByOwner GSI) or integration with the platform's `app/services/search.py` search indexing pipeline. That integration is the "résumé text extraction → full-text résumé search" Tier-2 gap (OPENCATS_GAP_ANALYSIS.md §A line 47) and is out of scope for CND.

5. **LED-001 / LED-002 ship order.** CND-001 is designed to be independently mergeable without LED-001 having shipped first. The GSI naming is compatible but the actual `leads` table and `T.leads` handle are independent objects. If LED-001 ships after CND-001, no migration or rename is needed.
