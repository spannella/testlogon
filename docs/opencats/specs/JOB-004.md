## 1. Summary & Goal

Add the three Job Order list views that OpenCATS surfaces on its dashboard home screen
and recruiter panels: **open** (all non-terminal, non-deleted orders), **hot**
(hot-flagged orders only), and **mine** (orders assigned to the calling recruiter).
All three are cursor-paginated, filtered at DynamoDB query time via GSIs established
in JOB-001, and exposed as authenticated GET endpoints in the existing
`app/routers/job_orders.py` router.

The deliverables are:

1. Three new service functions in `app/services/job_orders.py` — `list_open`,
   `list_hot`, `list_mine` — each returning `(List[JobOrderOut], Optional[str])`.
2. Three new GET endpoints in `app/routers/job_orders.py` — `/open`, `/hot`, `/mine`
   — declared **before** `/{job_id}` so the literal path segments are not captured as
   a job id path parameter.
3. Additions to `app/services/api_key_route_scope_registry.py`
   (`API_KEY_ROUTE_EXEMPTIONS`) for the three new session-auth routes.
4. Focused hermetic pytest (`tests/test_job_orders_lists.py`) covering list membership,
   filter correctness, pagination round-trip across soft-deleted rows, and the
   503-when-flags-off gate.

No new DynamoDB tables, no new Pydantic models, no new settings keys, and no frontend
code ship in this ticket. The table and GSIs were defined in JOB-001; the service
skeleton, soft-delete convention, and sparse GSI management were defined in JOB-002;
the router structure and `_require_flag()` guard were defined in JOB-003.

**Why now:** Without these list views the Job Order vertical has no browsable surface.
OpenCATS's value proposition is rapid access to open positions and the recruiter's own
workload — both require these views. JOB-007 (frontend) depends on these three
endpoints directly.

### 2.3 OpenCATS list-view context

OpenCATS renders three distinct list views on its home dashboard:

- **Open orders** — every order with a non-terminal status (`active`, `on_hold`,
  `full`, `lead`, `upcoming`). Optionally narrowed by company or by a single status.
  Newest-first. The primary global workload view.
- **Hot jobs** — orders marked `hot`. A visual priority queue for in-demand roles.
- **My orders** — orders where the logged-in recruiter appears in `recruiter_subs`.
  Enables each recruiter to see only their own assigned workload.

Soft-deleted orders (those with a `deleted_at` attribute set by JOB-002
`delete_job_order`) are excluded from all three views. This is enforced by
`FilterExpression=Attr("deleted_at").not_exists()`, but because DynamoDB applies
`FilterExpression` **after** reading up to 1 MB of items (the gotcha described in
CLAUDE.md), the service must loop on `LastEvaluatedKey` until it has gathered
`limit` real items or the index is exhausted — a single query call silently misses
soft-deleted-interleaved items on a busy table.

## 3. Data Model

### 3.1 DynamoDB tables and GSIs consumed by this ticket

All tables and GSIs were created by JOB-001. This ticket only **reads** them.

#### `job_orders` table — GSIs used by list functions

| GSI name | Partition key | Sort key | Type | Drives |
|---|---|---|---|---|
| `GSI_BY_STATUS` | `status` (S) | `created_at` (N) | Sparse by value | `list_open` — query each non-terminal status value separately, newest-first |
| `GSI_HOT` | `hot_flag` (S) | `created_at` (N) | Sparse (absent unless hot) | `list_hot` — query `hot_flag="1"`, newest-first |
| `GSI_BY_RECRUITER` | `recruiter_sub` (S) | `created_at` (N) | Dense; one row per recruiter per job | `list_mine` — query `recruiter_sub=caller`, newest-first |
| `GSI_DIRECT` | `job_id` (S) | — | Dense; one row per job | `list_mine` resolution step — `get_job_order` uses this to resolve each index row's `job_id` to the META item |

**Critical `attr_types` note:** The sort key `created_at` is a Number (`N`). The
`TableDef` in `scripts/local-ddb-init.py` for `job_orders` must carry
`attr_types={"created_at": "N", "updated_at": "N"}`. This was mandated in JOB-001
and follows the `users` table precedent at `scripts/local-ddb-init.py:49-54`
(`attr_types={"kyc_tier": "N", "kyc_tier_updated_at": "N"}`). Omitting `"N"` causes
DynamoDB to store `created_at` as a String → `ValidationException` when queried with
integer sort-key conditions.

#### META row attributes read by list functions

The following attributes are projected from the META row into `JobOrderOut` by the
`_item_to_out` helper (defined in JOB-002):

| Attribute | Notes |
|---|---|
| `job_id`, `title`, `type`, `status` | Core identity and state |
| `hot`, `public` | Derived from `hot_flag == "1"` and `public_flag == "1"` respectively |
| `openings`, `placed_count` | Counter fields; `openings_remaining = max(openings - placed_count, 0)` computed in `_item_to_out` |
| `client_company_id`, `client_contact_id`, `recruiter_subs` | Reference ids |
| `pay_rate_cents`, `bill_rate_cents`, `duration`, `city`, `state`, `description` | Commercial and location fields |
| `created_by`, `created_at`, `updated_at` | Audit trail |
| `deleted_at` | Soft-delete marker; present → item excluded from all list views |

#### Recruiter index row attributes read by `list_mine`

| Attribute | Notes |
|---|---|
| `recruiter_sub` | GSI_BY_RECRUITER partition key; matches the caller's `user_sub` |
| `created_at` | GSI_BY_RECRUITER sort key |
| `job_id` | Projected from META at write time; used to resolve the full META row |

## 4. API / Service Design

### 4.1 Service functions — `app/services/job_orders.py`

The three list functions are additive additions to the service file built across
JOB-002 through JOB-006. They must be placed **after** the CRUD functions and the
`_item_to_out` helper established in JOB-002, since they call `_item_to_out`
internally.

```python
from typing import Dict, List, Optional, Tuple, Any
from boto3.dynamodb.conditions import Attr, Key
from app.core.cursor import encode_cursor, decode_cursor
from app.core.tables import T
from app.models import JobOrderOut, JOB_ORDER_STATUSES, JOB_ORDER_TERMINAL

_OPEN_STATUSES: Tuple[str, ...] = tuple(
    s for s in JOB_ORDER_STATUSES if s not in JOB_ORDER_TERMINAL
)
_DEFAULT_LIST_LIMIT = 50
_MAX_LIST_LIMIT = 200


def list_open(
    cursor: Optional[str] = None,
    limit: int = _DEFAULT_LIST_LIMIT,
    *,
    company_id: Optional[str] = None,
    status: Optional[str] = None,
) -> Tuple[List[JobOrderOut], Optional[str]]:
    """Return non-terminal, non-deleted job orders, newest-first.

    When `status` is supplied the query is narrowed to that single status value;
    otherwise queries GSI_BY_STATUS once per non-terminal status and merges results
    (each sub-query paginated individually) before re-sorting the merged page.

    When `company_id` is supplied the query result is further filtered to
    `client_company_id == company_id` via FilterExpression.

    Pagination: ExclusiveStartKey is embedded in a signed cursor (encode_cursor /
    decode_cursor from app/core/cursor.py). Because FilterExpression (deleted_at not
    exists + optional company_id) is applied AFTER DynamoDB reads up to 1 MB, the
    service loops on LastEvaluatedKey until `limit` real items are gathered.
    """
    ...


def list_hot(
    cursor: Optional[str] = None,
    limit: int = _DEFAULT_LIST_LIMIT,
) -> Tuple[List[JobOrderOut], Optional[str]]:
    """Return hot-flagged, non-deleted job orders, newest-first.

    Queries GSI_HOT (hot_flag="1") with ScanIndexForward=False. FilterExpression
    excludes soft-deleted rows. LastEvaluatedKey loop applies.
    """
    ...


def list_mine(
    recruiter_sub: str,
    cursor: Optional[str] = None,
    limit: int = _DEFAULT_LIST_LIMIT,
) -> Tuple[List[JobOrderOut], Optional[str]]:
    """Return job orders assigned to `recruiter_sub`, newest-first.

    Queries GSI_BY_RECRUITER (recruiter_sub=recruiter_sub) with
    ScanIndexForward=False. Each result row is a recruiter index row carrying `job_id`;
    resolves each to the full META item via get_job_order (GSI_DIRECT).
    Stale index rows (job not found or soft-deleted) are silently skipped.
    """
    ...
```

#### 4.1.1 `list_open` — detailed behavior

`list_open` must handle the case where a single `status` is requested (one GSI query)
versus "all open" (up to five GSI queries, one per non-terminal status). The
recommended implementation uses a **merge-and-re-sort** approach for the multi-status
case:

1. If `status` is supplied, validate it is in `_OPEN_STATUSES` (not terminal); raise
   `HTTPException(400, {"code": "invalid_status_filter", "allowed": list(_OPEN_STATUSES)})`
   if invalid or terminal.
2. Build a list of `(status_value, ExclusiveStartKey | None)` tuples to query. When
   `cursor` is decoded, the cursor payload carries a `per_status_keys` dict mapping
   each status string to its last-evaluated key (or `None` when exhausted); this allows
   resuming each sub-query from its correct position on the next page.
3. For each status value, loop on `LastEvaluatedKey` until either `limit` non-deleted
   items are accumulated across all statuses or the status index is exhausted.
4. After collecting items across all statuses, sort descending by `created_at`
   (numeric), take the first `limit`, record the `LastEvaluatedKey` for each status at
   the cut-off position, and encode the per-status keys into `next_cursor`.
5. If `company_id` is supplied, add `FilterExpression=Attr("client_company_id").eq(company_id) & Attr("deleted_at").not_exists()`; otherwise `FilterExpression=Attr("deleted_at").not_exists()`.

**Cursor payload shape for `list_open`** (multi-status case):

```json
{
  "v": "v2",
  "k": {
    "active": {"pk": "...", "sk": "...", "status": "active", "created_at": 1700000000},
    "on_hold": null,
    "full": null,
    "lead": null,
    "upcoming": null
  }
}
```

When `status` is supplied (single-status mode), the cursor payload degrades to the
standard single-`LastEvaluatedKey` shape used by `encode_cursor` (the plain dict from
the DynamoDB response), matching the existing pattern in `app/services/appeals.py:313-319`.

#### 4.1.2 `list_hot` — detailed behavior

1. Query `GSI_HOT` with `KeyConditionExpression=Key("hot_flag").eq("1")`,
   `ScanIndexForward=False`, `Limit=limit * 3` (over-fetch to absorb soft-deleted rows),
   `FilterExpression=Attr("deleted_at").not_exists()`.
2. Decode cursor via `decode_cursor` → `ExclusiveStartKey`.
3. Inner loop on `LastEvaluatedKey` until `limit` items are gathered or the index is
   exhausted. Collect `_item_to_out(item)` for each non-deleted result.
4. `next_cursor = encode_cursor(last_evaluated_key)` from the final iteration; `None`
   when exhausted. Return `(items[:limit], next_cursor)`.

#### 4.1.3 `list_mine` — detailed behavior

1. Query `GSI_BY_RECRUITER` with `KeyConditionExpression=Key("recruiter_sub").eq(recruiter_sub)`,
   `ScanIndexForward=False`, `Limit=limit * 2`.
2. Each returned item is a recruiter index row containing `job_id`. Resolve each via
   `get_job_order(job_id)` (which itself queries `GSI_DIRECT`).
3. Skip silently when `get_job_order` raises `HTTPException(404, ...)` — this handles
   stale index rows left behind when a recruiter was removed from a job's
   `recruiter_subs` (JOB-002 reconcile) or when a job was soft-deleted and the recruiter
   index rows were deleted (JOB-002 `delete_job_order`). In practice stale rows should
   be rare because JOB-002's reconcile step cleans them up, but the list must be
   resilient regardless (same stale-index-row tolerance documented in JOB-002 spec §3.3
   and the OPP-003 Kanban pattern — OPP-004 is the Opportunity–Contact role junction).
4. `FilterExpression` on the index query should also add `Attr("deleted_at").not_exists()`
   as a belt-and-suspenders guard (recruiter index rows do not carry `deleted_at`, but
   the expression is a no-op on those rows and adds no overhead).
5. Loop on `LastEvaluatedKey` until `limit` resolved items are gathered.
6. Encode cursor from the index query's final `LastEvaluatedKey`. Return
   `(items[:limit], next_cursor)`.

#### 4.1.4 `_require_flag()` placement

All three functions call `_require_flag()` at the top (defined in `app/services/job_orders.py` by JOB-002; JOB-003's router also defines a local copy for defence-in-depth at the HTTP layer, but the canonical service-layer version is what the list functions and the §4.2 router import call; raises `HTTPException(503, ...)` when either flag is off). Service functions are
unconditionally importable from tests; the flag check applies when the function is
called with flags off, allowing hermetic flag-off tests.

### 4.2 Router endpoints — `app/routers/job_orders.py`

## 5. Detailed Behavior & Edge Cases

### 5.1 `list_open` — multi-status merge page boundary

When `status` is `None`, `list_open` queries up to five GSI partitions in a single
call. The challenge is pagination: cursor page 1 may exhaust `active` (e.g., 20 items)
and consume 10 of `on_hold` (total 30 = limit). The page-2 cursor must encode the
resume point for every status independently.

The **per-status cursor** approach (`per_status_keys` dict in the cursor payload)
handles this correctly. Alternative approaches — merging all items in memory, or using
a single status per page — would either require unbounded reads or degrade UX. The
per-status cursor is HMAC-signed via `encode_cursor` (the signing covers the entire
JSON envelope), so a tampered or replayed cursor returns `None` from `decode_cursor`
and the list falls back to page-1 behavior (no error, same as the existing cursor
validation behavior in `app/core/cursor.py:112-124`).

### 5.2 `list_open` — `company_id` filter on a non-key attribute

`client_company_id` is not a GSI key on `GSI_BY_STATUS`; it is a regular attribute on
the META row. The filter is therefore a `FilterExpression`, not a `KeyConditionExpression`.
DynamoDB reads up to 1 MB before applying `FilterExpression` — on a multi-company
table a company filter can result in zero items returned per page even when `Limit=100`
is set. The `LastEvaluatedKey` loop **must** continue until either `limit` items pass
the filter or `LastEvaluatedKey` is absent. This is the identical behavior described in
CLAUDE.md ("DDB FilterExpression doesn't reduce page size → loop via `LastEvaluatedKey`").

**Future optimization:** A `COMPANY#{cid}#STATUS#{status}` composite GSI key could
make the company filter key-based, but that requires a schema change in JOB-001 and is
deferred. The filter approach is correct and sufficient at current scale.

### 5.3 `list_hot` — toggling `hot` mid-page

When a recruiter flips `hot = False` on a job order (JOB-003 PATCH endpoint → JOB-002
`update_job_order`), JOB-002 removes the `hot_flag` attribute entirely via a DynamoDB
`REMOVE` expression. The item disappears from `GSI_HOT` at the next DynamoDB
propagation tick (eventually consistent). A `list_hot` call in-flight during a toggle
may briefly return the transitioning item. This is acceptable — eventual consistency is
the platform standard (no strong consistency required here). The endpoint does not
expose a `ConsistentRead` option for GSI queries (DynamoDB does not support
`ConsistentRead=True` on GSIs).

### 5.4 `list_mine` — recruiter sub from session, not query param

The `/mine` endpoint derives `recruiter_sub` from `ctx["user_sub"]` (the authenticated
session), not from a query parameter. This prevents a logged-in user from listing
another recruiter's orders via a crafted `recruiter_sub` query param. If an admin view
of "orders by recruiter" is needed in the future, a separate admin-gated endpoint with
explicit `recruiter_sub` query param should be added (not part of this ticket).

### 5.5 Stale recruiter index row handling in `list_mine`

JOB-002's `delete_job_order` removes recruiter index rows immediately after setting
`deleted_at` on the META row. JOB-002's `update_job_order` reconciles recruiter index
rows (add new, remove dropped) when `recruiter_subs` changes. Despite this, stale
rows are possible in a conflict or partial-write scenario. `list_mine` wraps each
`get_job_order(job_id)` call in a `try/except HTTPException` and skips the item on
404. A non-404 HTTPException (e.g., 503 flag-off) is re-raised. Other exceptions
(DynamoDB transient errors) are logged and the item is skipped — the list degrades
gracefully rather than failing the entire page.

### 5.6 `limit` parameter clamping

All three endpoints accept `limit` in the range `[1, 200]` (FastAPI `Query(ge=1, le=200)`).
The default is 50, matching OpenCATS's default page size. The service functions also
validate `limit` internally (clamp to `_MAX_LIST_LIMIT = 200`) so direct service-layer
callers are also safe. Values above 200 at the router layer are rejected with 422
(FastAPI validation).

### 5.7 Empty result pages

When no items match (e.g., no hot orders exist, or the recruiter has no assigned
orders), the response is `{"items": [], "next_cursor": null}` — a 200 with an empty
list, never a 404. This is consistent with the platform convention for list endpoints
(e.g., `app/services/appeals.py:321`).

### 5.8 Status filter validation for `list_open`

If a caller passes `?status=closed` (a terminal status) to `/open`, the endpoint
returns `HTTP 400` with `{"code": "invalid_status_filter", "allowed": ["active",
"on_hold", "full", "lead", "upcoming"]}`. Terminal statuses are excluded from the
"open" concept by definition. An `?status=active` on `/open` is valid and returns
only active orders.

### 5.9 `list_open` with `company_id` and cursor

When both `company_id` and `cursor` are supplied, the cursor is decoded and the
`ExclusiveStartKey` for each status sub-query is loaded from the per-status dict.
The `company_id` filter is reapplied on every page (it is a `FilterExpression`, not
embedded in the cursor). Changing `company_id` between pages while reusing a cursor
will return an inconsistent result — callers should treat cursors as opaque tokens
tied to the original query parameters.

### 5.10 Flag-off behavior

With either `S.ats_enabled` or `S.job_orders_enabled` set to `False`, all three
endpoints return `HTTP 503 {"code": "job_orders_disabled"}`. No DynamoDB reads are
performed. Existing routes are unaffected.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

There are no `if S.dev_mode` branches in any of the three service functions. The
DynamoDB read path (moto in dev, real DynamoDB in prod) is the same code path in both
environments — the boto3 client is wired via `app/core/aws.ddb` which resolves to
DynamoDB Local in dev and real AWS in prod via the `DDB_ENDPOINT_URL` env var
(`app/core/settings.py:11`). No mock data, no alternate code path, no dev-only filter.

### 7.2 Idempotency

All three functions are read-only GET endpoints. They are inherently idempotent — no
state is written. Repeated calls with the same parameters return the same result set
(modulo concurrent writes by other callers, which is acceptable given DynamoDB eventual
consistency). Cursor tokens are HMAC-signed (tamper-evident) but the list degrades
gracefully (falls back to page 1) rather than erroring on an invalid cursor — same
behavior as the existing cursor library (`app/core/cursor.py:112-124`).

### 7.3 Authentication and authorization

All three endpoints require `Depends(require_ui_session)` from
`app/services/sessions.py:330`. The session middleware enforces CSRF for cookie-auth
non-GET requests automatically; GET requests do not require CSRF headers
(`app/auth/deps.py` CSRF enforcement). Bearer-auth clients (API key or Cognito JWT)
skip CSRF per platform convention.

There is no record-level access control on Job Orders in this ticket — any authenticated
user can see all open/hot/mine orders. Per-recruiter scoping on `/mine` is
enforced by deriving `recruiter_sub` from the session (not a client-supplied parameter).
Fine-grained ACL (record-level security restricting non-recruiter users from seeing
non-public jobs) is deferred to STU-002/003/004 (CLAUDE.md "Planned" section).

### 7.4 No PII in cursor tokens

Cursor tokens encode DynamoDB `LastEvaluatedKey` values, which contain only DynamoDB
key attributes (`pk`, `sk`, `status`, `created_at`). No user PII or job-order content
appears in the cursor. The HMAC signature prevents leaking information via token
manipulation.

### 7.5 Rate limiting

The list endpoints are behind `require_ui_session` (authenticated) and are therefore
subject to the platform's existing session-based rate limiting middleware
(`app/middleware/rate_limit.py`, registered in `app/main.py:541`). No additional
per-endpoint rate limiting is needed for this ticket.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact on existing routes with flags off

With both flags at their default `false` values, the three new endpoints return 503
and the rest of the router (`/open`, `/hot`, `/mine` are new — they do not shadow any
existing route). No existing route, table, model, or setting is modified.

### 8.2 Route declaration order in `app/routers/job_orders.py`

The three new GET routes (`/open`, `/hot`, `/mine`) must appear **before** the
existing `GET /{job_id}` route in the router source file. FastAPI registers routes in
declaration order; the literal strings `/open`, `/hot`, and `/mine` would be captured
as `job_id` path parameters if `/{job_id}` appeared first. This ordering was designed
into JOB-003 (the JOB-003 spec §2.1 explicitly reserves the pre-`/{job_id}` slots for
JOB-004 list routes).

### 8.3 DynamoDB table compatibility

`list_open` and `list_hot` query GSI projections. DynamoDB GSI queries return only
projected attributes plus all attributes if `ProjectionType=ALL` (the default for
`TableDef`-created GSIs in `scripts/local-ddb-init.py`). All META row attributes are
projected. Existing items in the table written before JOB-004 ships are read correctly
— there is no migration needed.

### 8.4 Cursor format compatibility

The list functions use `encode_cursor` / `decode_cursor` from `app/core/cursor.py:94,103`.
The signed v2 cursor format supports key rotation via `CURSOR_SIGNING_SECRET_PREVIOUS`
(`app/core/cursor.py:36-41`). Existing cursors from other list views (e.g., appeals,
newsfeed) use the same format and coexist without collision. The `per_status_keys`
dict used in `list_open`'s multi-status cursor is a new payload shape but is entirely
internal — it is encoded as the `k` field of the v2 envelope and decoded transparently.

## 10. Open Questions / Assumptions

### OQ-001 — Multi-status cursor payload compatibility

The per-status cursor payload shape (`per_status_keys` dict) is novel within the
codebase — existing cursors are always a single `LastEvaluatedKey` dict. The encoding
is compatible with `encode_cursor` (it encodes any JSON-serializable dict), but the
`list_open` function must carefully distinguish "received a per-status cursor" from
"received a single-key legacy cursor" when decoding. **Assumption:** when `status` is
`None` (multi-status mode), the cursor payload is always the per-status dict. When
`status` is supplied (single-status mode), the cursor payload is the plain
`LastEvaluatedKey` dict. The two modes are not interchangeable; passing a multi-status
cursor to a single-status call (or vice versa) degrades to page-1 (the malformed key
fails `decode_cursor` validation → `None` → start from beginning). This is safe.

### OQ-002 — Sorting across multi-status GSI pages

When merging results from five `GSI_BY_STATUS` sub-queries, each sub-query returns
items sorted by `created_at` descending. After fetching `limit` items from all
sub-queries combined, the merged list must be re-sorted by `created_at` descending
before taking the first `limit`. This in-memory sort is O(N log N) where N ≤
`limit * 5 = 1000` — acceptable. **Assumption:** multi-status sort is in-memory on
the service layer; no DynamoDB `ScanIndexForward` trick is possible across multiple
GSI partitions.

### OQ-003 — `public_flag` GSI (GSI_PUBLIC) not consumed here

The `GSI_PUBLIC` index defined in JOB-001 (`public_flag="1"` → public career-portal
listing) is **not used by any list function in JOB-004**. It is reserved for the
public career portal (PORTAL-* cluster, Tier 2 from `OPENCATS_GAP_ANALYSIS.md:101`).
The career-portal list endpoint will query `GSI_PUBLIC` with no-auth (public) access,
rate limiting, and `API_KEY_ROUTE_EXEMPTIONS`, following the CMP-006/KB-011 public
portal pattern. That design is out of scope for JOB-004.

### OQ-004 — Admin view of "all orders by recruiter"

The `/mine` endpoint scopes to the authenticated user's `user_sub`. An admin/recruiter-
manager view showing "orders assigned to recruiter X" requires a separate endpoint with
`require_admin_session` and an explicit `?recruiter_sub=` query parameter. This is
deferred to a future admin-extension ticket and not designed here.

### OQ-005 — `list_open` page consistency across status sub-queries

The multi-status merge does not guarantee strong consistency across the five
sub-queries — they are separate network calls and may observe different DynamoDB
snapshots. A status change (e.g., `active` → `on_hold`) mid-page could cause an order
to appear in both sub-queries or in neither. **Assumption:** this is acceptable; the
platform uses eventual consistency throughout and ATS list views are not
transactionally sensitive. Callers should refresh the list after status changes
(which the frontend will do via React Query invalidation).
