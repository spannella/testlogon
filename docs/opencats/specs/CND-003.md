**Type:** Feature · **Priority:** P1 · **Estimate:** 2 days  
**Cluster:** ATS Candidates (CND) · **Gap analysis:** `docs/opencats/OPENCATS_GAP_ANALYSIS.md` §A (line 46)  
**Depends on:** CND-001 (table, flag, settings, models), CND-002 (candidate CRUD service)  
**Required by:** CND-005 (router), CND-007 (tests)

---

## 1. Summary & Goal

CND-003 adds résumé/CV upload, listing, per-résumé download URL, soft-delete, and an
"exactly-one primary résumé" flag to the Candidate entity introduced by CND-001 and
CND-002. The gap analysis (`docs/opencats/OPENCATS_GAP_ANALYSIS.md:46`) classifies this
as PARTIAL — the file manager and the KB-003 S3-attach pattern exist in the platform but
no candidate-résumé linkage or primary flag exists anywhere.

The design closes the gap by grafting the **KB-003 S3-attach-on-entity pattern** onto the
`candidates` table as `ATTACHMENT#` sub-items: attachment metadata is stored under distinct
SK prefixes on the same table as the candidate META row (single-table, no new table),
bytes go to S3 under a deterministic path, and a `primary_resume_id` pointer is
back-written onto the META row. A secondary "file-manager-linked" path lets recruiters
attach a résumé that already lives in their file manager by recording a pointer sub-item
(`source="file_manager"`, `node_path`) with no byte copy, reusing `filemanager.get_node`
(`app/services/filemanager.py:450`) for ownership resolution.

Goals:

1. Multiple résumés per candidate, each with its own S3 object, metadata, and download URL.
2. Exactly one résumé may be primary at any time; first upload auto-promotes; deleting the
   primary promotes the next-newest active résumé (or clears the pointer).
3. File-manager-sourced résumés record only a pointer (no byte copy).
4. The feature is entirely additive, flag-gated by `S.candidates_enabled` (CND-001), and
   produces zero behavioural change when the flag is off.
5. A single `_make_download_url` helper is the **only** dev/prod branch added (SECOPS-007).

## 3. Data Model

### 3.1 Table

CND-003 uses **only the existing `candidates` table** delivered by CND-001 (PK `pk` / SK
`sk`). No new table, no new GSI, no schema migration.

### 3.2 Attachment sub-item shape

One DDB item per résumé, stored on the same table as the candidate META row:

| Attribute | DDB Type | Notes |
|---|---|---|
| `pk` | S | `"CANDIDATE#{candidate_id}"` — same partition as META |
| `sk` | S | `"ATTACHMENT#{attachment_id}"` — `attachment_id = "att_" + uuid4().hex` |
| `attachment_id` | S | bare ID also stored for convenience |
| `candidate_id` | S | denormalized for projection |
| `filename` | S | sanitized filename (≤255 chars), stored after `_safe_filename()` |
| `filename_original` | S | original pre-sanitization name (display fidelity) |
| `content_type` | S | MIME type from upload or node metadata |
| `size_bytes` | N | integer, 0 for file-manager-linked rows where bytes were not transferred |
| `s3_key` | S | full S3 key; absent for `source="file_manager"` rows (use `node_path` instead) |
| `s3_bucket` | S | S3 bucket name; absent for `source="file_manager"` rows |
| `node_path` | S | file-manager path; only present when `source="file_manager"` |
| `source` | S | `"upload"` or `"file_manager"` |
| `is_primary` | BOOL | at most one row across the candidate's attachments has `True` at any time |
| `uploaded_by` | S | `user_sub` of the recruiter who performed the action |
| `created_at` | N | `now_ts()` — integer Unix seconds; **not** a GSI key (no `attr_types` needed) |
| `deleted_at` | N | soft-delete marker; absent until soft-deleted |

There is no GSI on attachment sub-items. All queries hit the `candidates` table primary
key directly (`pk=CANDIDATE#{id}`, `sk begins_with ATTACHMENT#`), which is a single-table
partition query and does not require a GSI.

### 3.3 Back-pointer on META row

`set_primary_resume` back-writes `primary_resume_id` (S, nullable) onto the candidate
META row (`sk="META"`). This is an in-place `update_item` expression:

```
UpdateExpression="SET primary_resume_id = :id, updated_at = :ts"
ExpressionAttributeValues={":id": attachment_id, ":ts": now_ts()}
```

When the primary is cleared (all résumés deleted), the expression removes the attribute:

```
UpdateExpression="REMOVE primary_resume_id SET updated_at = :ts"
```

`CandidateOut.primary_resume_id` (added by CND-001) surfaces this value directly.

### 3.4 S3 key convention

```
{S.candidate_resume_s3_prefix}{candidate_id}/{attachment_id}/{safe_filename}
```

With default settings:

```
candidate-resumes/{candidate_id}/{attachment_id}/resume_2024.pdf
```

The key is deterministic and derivable from stored metadata; it is also stored in the
`s3_key` attribute of the sub-item for fast retrieval.

### 3.5 Numeric attribute note

`created_at` on attachment sub-items is a number (`N`) stored on the item but is **not**
a GSI sort key. There is no new GSI. The `attr_types={"GSI1SK": "N", "GSI2SK": "N",
"GSI3SK": "N"}` declaration from CND-001's `TableDef` (covering the `candidates` table's
three existing GSIs) is not modified by this ticket.

## 4. API / Service Design

### 4.1 Service functions (`app/services/candidates.py` additions)

All functions are **synchronous** (called from async routes via `asyncio.to_thread` per
`app/routers/google_drive_integration.py:160`). All raise `HTTPException(503)` when
`S.candidates_enabled` is `False`.

---

**`add_resume(candidate_id, *, uploaded_by, filename, content_type, size_bytes, s3_key, s3_bucket, source="upload", make_primary=False) -> dict`**

1. Guard on `S.candidates_enabled`.
2. Call `get_candidate(candidate_id)` — `HTTPException(404)` if absent, `HTTPException(410)` if `deleted_at` set.
3. Count active (non-soft-deleted) `ATTACHMENT#` sub-items for this candidate. If count ≥
   `S.candidate_resume_max_per_candidate` (default 25): raise `HTTPException(400,
   {"code": "candidate_resume_limit_reached", "message": "..."})`
4. Generate `attachment_id = "att_" + uuid4().hex`.
5. Apply `_safe_filename(filename)` → `safe_name`; store both `filename=safe_name` and
   `filename_original=filename`.
6. Determine `is_primary`: `True` if `make_primary=True` OR this is the first active résumé
   (count == 0 before this insert). If `True`, call `set_primary_resume(candidate_id,
   attachment_id, uploaded_by)` after writing the sub-item (see ordering note below).
7. Write the `ATTACHMENT#{attachment_id}` sub-item to `T.candidates` via `put_item`.
8. If `is_primary`, call `set_primary_resume` to update META and clear any other
   `is_primary=True` sub-items.
9. Emit `audit_event("candidate.resume.uploaded", uploaded_by, candidate_id=candidate_id,
   attachment_id=attachment_id, filename=safe_name, source=source)`.
10. Call `record_candidate_change(candidate_id, uploaded_by, change_type="resume_added",
    summary=f"Résumé '{safe_name}' uploaded")` — best-effort, wrapped in `try/except`.
11. Return the written sub-item dict.

---

**`add_resume_from_filemanager(candidate_id, *, uploaded_by, node_path, recruiter_sub) -> dict`**

Validates that `recruiter_sub` owns the file-manager node, then records a pointer sub-item
with no byte copy:

1. Guard on `S.candidates_enabled`.
2. Call `get_candidate(candidate_id)` — 404/410 checks as above.
3. Call `filemanager.get_node(recruiter_sub, node_path)` (`filemanager.py:450`) — raises
   `HTTPException(404)` if node does not exist or is not owned by the recruiter.
4. Extract `filename`, `content_type`, `size` from the node dict. `size_bytes = 0` (no
   transfer; only a pointer is stored).
5. Enforce the count cap identically to `add_resume`.
6. Generate `attachment_id`; build sub-item with `source="file_manager"`, `node_path=node_path`,
   `s3_key` absent, `s3_bucket` absent.
7. Same `is_primary` logic, `set_primary_resume`, `audit_event`, `record_candidate_change`
   as `add_resume`.
8. Return the sub-item dict.

---

**`list_resumes(candidate_id) -> list[dict]`**

1. Guard on `S.candidates_enabled`.
2. Query `T.candidates` with:
   ```python
   KeyConditionExpression=Key("pk").eq(f"CANDIDATE#{candidate_id}") & Key("sk").begins_with("ATTACHMENT#")
   ```
   Loop via `LastEvaluatedKey` (per CLAUDE.md `FilterExpression` gotcha — a sparse
   `deleted_at` filter requires looping; `deleted_at` is absent on live rows so
   `FilterExpression=Attr("deleted_at").not_exists()` is used to drop soft-deleted rows,
   but DDB fetches up to 1 MB before applying the filter, so the loop is mandatory).
3. Sort results: primary first (`is_primary=True`), then by `created_at` descending.
4. Return list of raw dicts (router adds `url` via `_make_download_url`).

---

**`get_resume(candidate_id, attachment_id) -> dict`**

1. Guard on `S.candidates_enabled`.
2. `T.candidates.get_item(Key={"pk": f"CANDIDATE#{candidate_id}", "sk": f"ATTACHMENT#{attachment_id}"})`.
3. Raise `HTTPException(404)` if item absent or `deleted_at` present.
4. Return item dict.

---

**`set_primary_resume(candidate_id, attachment_id, actor_sub) -> None`**

Enforces the exactly-one-primary invariant:

1. Guard on `S.candidates_enabled`.
2. Call `get_resume(candidate_id, attachment_id)` — 404 if missing/soft-deleted.
3. Fetch all active attachment sub-items via a targeted `list_resumes` call (internal,
   pre-filter variant that skips the URL projection).
4. For each sub-item where `is_primary=True` and `attachment_id != target_id`: issue an
   `update_item` to set `is_primary=False`.
5. Issue `update_item` on `ATTACHMENT#{attachment_id}` to set `is_primary=True`.
6. Back-write `primary_resume_id` onto the candidate META row
   (`pk="CANDIDATE#{candidate_id}"`, `sk="META"`) via `update_item`.
7. Emit `audit_event("candidate.resume.primary_set", actor_sub, candidate_id=candidate_id,
   attachment_id=attachment_id)`.

The clear-then-set sequence is not atomic (no DDB transaction here). The invariant is
maintained by the service layer being the only writer of `is_primary`; concurrent writes
are not expected in a single-recruiter context. If strict atomicity is required in a
future concurrent-access scenario, a DDB `TransactWriteItems` can be introduced without
changing the public API.

---

**`delete_resume(candidate_id, attachment_id, actor_sub) -> None`**

1. Guard on `S.candidates_enabled`.
2. Call `get_resume(candidate_id, attachment_id)` — 404 if missing/already soft-deleted.
3. Record `was_primary = item.get("is_primary", False)`.
4. Write `deleted_at=now_ts()`, `is_primary=False` onto the sub-item via `update_item`.
5. If `was_primary`: call `_promote_next_primary(candidate_id, deleted_id=attachment_id)`
   (see below).
6. Emit `audit_event("candidate.resume.deleted", actor_sub, candidate_id=candidate_id,
   attachment_id=attachment_id)`.
7. Call `record_candidate_change(candidate_id, actor_sub, change_type="resume_removed",
   summary=f"Résumé '{item['filename']}' removed")` — best-effort, wrapped in `try/except`.
8. **Do NOT delete the S3 object.** S3 lifecycle policies handle physical deletion
   (mirroring KB-003 §5.3 / `kyc_partner_api.py` pattern — S3 deletes are not performed
   from application code for attachment removals).

**`_promote_next_primary(candidate_id, deleted_id) -> None`** (private helper):

1. Fetch remaining active sub-items (excluding `deleted_id`).
2. If none remain: issue `update_item REMOVE primary_resume_id` on the META row.
3. If there are remaining items: sort by `created_at` descending; promote the first (most
   recently uploaded) via `set_primary_resume`.

---

**`_make_download_url(s3_key: str, s3_bucket: str) -> str`** (private helper)

The **only** dev/prod branch in this ticket (SECOPS-007: exactly one branch, no other
`S.dev_mode` checks):

```python
def _make_download_url(s3_key: str, s3_bucket: str) -> str:
    if S.dev_mode:
        return f"/mock/s3/{s3_bucket}/{s3_key}"
    try:
        return s3_client().generate_presigned_url(
            "get_object",
            Params={"Bucket": s3_bucket, "Key": s3_key},
            ExpiresIn=300,
        )
    except Exception:
        logger.warning("candidate.resume.presign_failed key=%s", s3_key)
        raise HTTPException(503, detail={"code": "resume_unavailable",
                                         "message": "Résumé download temporarily unavailable"})
```

Copied directly from `app/services/kyc_partner_api.py:630-641`. For
`source="file_manager"` rows the `url` is computed by resolving the node via
`filemanager.get_node` (which itself returns a presigned URL or mock URL depending on
dev mode) — no special branch needed.

**Upload handler shape** (in CND-005 router, runs in async context):

```python
@router.post("/candidates/{candidate_id}/resumes", response_model=CandidateResumeOut)
async def upload_resume(
    candidate_id: str,
    file: UploadFile,
    make_primary: bool = False,
    user: dict = Depends(require_ui_session),
):
    if not S.candidates_enabled:
        raise HTTPException(404)
    data = await file.read()
    if len(data) > S.candidate_resume_max_bytes:
        raise HTTPException(413, detail={"code": "resume_too_large", "message": "..."})
    ct = file.content_type or "application/octet-stream"
    if ct not in CANDIDATE_RESUME_CONTENT_TYPES:
        raise HTTPException(400, detail={"code": "invalid_content_type",
                                         "message": f"Allowed: {sorted(CANDIDATE_RESUME_CONTENT_TYPES)}"})
    attachment_id = "att_" + uuid4().hex
    safe_name = _safe_filename(file.filename or "resume")
    bucket = S.candidate_resume_bucket
    s3_key = f"{S.candidate_resume_s3_prefix}{candidate_id}/{attachment_id}/{safe_name}"
    from app.core.aws_clients import s3_client as _s3_factory
    _s3_factory().put_object(Bucket=bucket, Key=s3_key, Body=data, ContentType=ct)
    item = await asyncio.to_thread(
        add_resume, candidate_id,
        uploaded_by=user["user_sub"], filename=file.filename or "resume",
        content_type=ct, size_bytes=len(data),
        s3_key=s3_key, s3_bucket=bucket,
        source="upload", make_primary=make_primary,
    )
    item["url"] = _make_download_url(s3_key, bucket)
    return CandidateResumeOut(**item)
```

Note: `s3_client()` is called inside the handler (not at module import) so the
`_FakeS3` test patch applies correctly.

## 5. Detailed Behavior & Edge Cases

### 5.1 First-upload auto-primary

When `add_resume` or `add_resume_from_filemanager` is called and no active
`ATTACHMENT#` sub-items exist for the candidate, the new résumé is automatically marked
primary regardless of the `make_primary` parameter. The count check (step 3 of
`add_resume`) returns `0` active rows, which triggers `is_primary=True`. This ensures
`CandidateOut.primary_resume_id` is always set once any résumé exists, which matches
OpenCATS' UX expectation.

### 5.2 Exactly-one-primary invariant

`set_primary_resume` enforces the invariant by scanning all active sub-items and
clearing `is_primary` from any row that currently holds `True` before setting the target.
There is no DDB-level constraint; the invariant is a service-layer guarantee. Callers
that update `is_primary` directly on sub-items (bypassing the service) can corrupt the
invariant — that pattern is disallowed; the sub-item attributes are considered
service-internal.

### 5.3 Soft-delete does not free the S3 object

Deleting a résumé writes `deleted_at` onto the sub-item but does NOT call
`s3_client().delete_object(...)`. Physical deletion is handled by an S3 lifecycle rule
(configured outside application code, identical to the KB-003 and KYC partner-API
document patterns). Attempting to generate a presigned URL for a soft-deleted key still
succeeds at the S3 level until the lifecycle rule fires; the application layer filters
soft-deleted rows from `list_resumes` so the URL is never surfaced to clients.

### 5.4 Count cap and soft-delete slot freeing

The cap (`S.candidate_resume_max_per_candidate`, default 25) counts only active (non-
soft-deleted) rows. A recruiter who soft-deletes a résumé immediately frees that slot for
a new upload. The count check queries `ATTACHMENT#` sub-items with
`FilterExpression=Attr("deleted_at").not_exists()`.

### 5.5 File-manager-linked résumés

- No bytes are transferred to the `candidate_resume_*` S3 prefix; the sub-item stores
  `node_path` and `size_bytes=0`.
- The `url` field in `CandidateResumeOut` for `source="file_manager"` rows is resolved by
  calling `filemanager.get_node(recruiter_sub, node_path)` at list/detail time to extract
  the node's S3 key/bucket, then applying `_make_download_url`. If the node has been
  deleted from the file manager, `get_node` raises 404 — the router catches this and
  returns `url=""` with a `url_unavailable: true` flag so the UI can render a graceful
  "file removed" state rather than a hard error.
- The file-manager `share_node` (`filemanager.py:3919`) is NOT called — CND-003 is
  recording a read-pointer for the recruiter's own use, not granting access to another
  user. The recruiter's existing file-manager permissions are sufficient.

### 5.6 Content-type validation

The upload handler checks `file.content_type` against `CANDIDATE_RESUME_CONTENT_TYPES`
(PDF / DOC / DOCX / RTF / plain text / ODT). If the browser sends an unknown or missing
MIME type, the handler returns `400 invalid_content_type`. Clients should set
`Content-Type` explicitly in multipart form data. The allowlist is a `frozenset` defined
in `app/models.py` (same pattern as `ALLOWED_VIDEO_CONTENT_TYPES` in
`app/routers/vod.py:39`).

### 5.7 Concurrent upload race

Two simultaneous uploads to the same candidate can both pass the count-cap check and both
succeed if the count at time of check is `max - 1`. This is accepted (the cap is a soft
limit for UX, not a hard security boundary). A future ticket may add a DDB conditional
expression for strict enforcement if needed.

### 5.8 Résumé download URL expiry

Presigned URLs expire in 300 seconds (5 minutes). Clients should not cache URLs; the
`GET .../resumes/{att_id}` endpoint always returns a fresh URL. The UI should fetch a
fresh URL on click rather than storing the URL from the list response.

### 5.9 Candidate delete interaction

When `delete_candidate` (CND-002) is called, it soft-deletes the META row. Attachment
sub-items remain in DDB (same partition, not touched). `list_resumes` is never called on
a soft-deleted candidate because the router's `GET /candidates/{id}` already returns 410,
preventing the résumé list from being served. A full hard-delete path (out of scope for
this cluster) would need to remove both the META row and all `ATTACHMENT#` sub-items.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 compliance

The single `_make_download_url` helper is the **only** code path that branches on
`S.dev_mode`. All other DDB and S3 operations use the same code in dev and prod:

- DDB access goes through `T.candidates` (moto intercepts in dev via the `_safe_table`
  → `ddb_resource()` → `aws_clients.py:104-111` chain; real DDB in prod).
- S3 `put_object` goes through `s3_client()` (`aws_clients.py:114`); moto intercepts
  in-process in dev (`_s3_endpoint_url()` returns `None` when `S.dev_mode=True`,
  `aws_clients.py:82`).
- `audit_event` (`alerts.py:644`) is DDB-only — no SES/S3 branch.
- No inline test data, no mock-only code paths, no `if S.dev_mode: return fake_data`.

### 7.2 Idempotency

- `add_resume` is not inherently idempotent (each call writes a new `attachment_id` UUID).
  Re-upload of the same file produces a second sub-item. This is intentional: résumés are
  versioned by upload time.
- `set_primary_resume(candidate_id, attachment_id, ...)` is idempotent: calling it twice
  with the same `attachment_id` produces the same state (the target remains primary).
- `delete_resume` is idempotent: soft-deleting an already-soft-deleted résumé returns 404
  (the service checks `deleted_at` before writing), preventing double-audits.

### 7.3 Security

- **Ownership enforcement** (router layer, CND-005): only the candidate's `owner_sub` or
  an `ADMIN`/`ROOT` user (checked via `_is_admin` from `tickets.py:207-208`) may upload,
  set-primary, or delete résumés. The service functions are authz-agnostic; the router
  enforces this by checking `user["user_sub"] == candidate["owner_sub"] or _is_admin(user)`.
- **Filename injection prevention**: `_safe_filename` strips everything outside
  `[A-Za-z0-9._-]` before constructing the S3 key, preventing path traversal.
- **Content-type allowlist**: only document MIME types are accepted; executable types,
  HTML, and archives are rejected at 400 before any S3 write.
- **Presigned URL scope**: URLs are scoped to `get_object` only, with a 300-second TTL;
  no `put_object` presigned URLs are issued to clients.
- **File-manager node ownership**: `add_resume_from_filemanager` calls
  `filemanager.get_node(recruiter_sub, node_path)`, which raises 404 if the node is not
  owned by `recruiter_sub`. A recruiter cannot link another user's file.
- **S3 key secrecy**: the S3 key (which includes `candidate_id` and `attachment_id`) is
  never sent directly to the client; clients receive a short-lived presigned URL only.

## 8. Backward Compatibility & Migration

### 8.1 Zero-impact on existing platform

CND-003 is entirely additive:

- No existing DDB table, router, service, or model is modified.
- The `candidates` table is created by CND-001; it does not exist before the CND cluster
  ships, so there are no pre-existing rows to migrate.
- The `candidate_resume_bucket` defaults to `"local-uploads"`, which is the same bucket
  already used by the file manager and other S3-backed features in dev. No new S3 bucket
  must be created in dev; in prod, a dedicated bucket should be provisioned.

### 8.2 No migration required at launch

Since the `candidates` table is net-new, there is no backfill. The
`primary_resume_id` field on the META row is `null`/absent until the first résumé is
uploaded; `CandidateOut` declares it as `Optional[str] = None` (CND-001), so existing
`GET /candidates/{id}` responses do not break when the field is absent.

### 8.3 Forward compatibility: résumé text extraction (Tier 3)

The Tier-3 "résumé text extraction + full-text search" ticket (gap analysis §D, line 90)
will add a `text_content` attribute to the `ATTACHMENT#` sub-item and a post-upload
background task. CND-003 reserves no space for this but the sub-item schema is open
(DDB is schemaless); the future ticket simply writes additional attributes onto existing
rows without a schema migration.

## 10. Open Questions / Assumptions

1. **Virus scanning** — résumé bytes are uploaded and stored without antivirus scanning.
   A future ticket may wire a scanning step between `put_object` and `add_resume` for
   prod hardening. Assumed out of scope for this ticket.

2. **Résumé versioning vs. replacement** — the current design treats each upload as a
   new attachment (no "replace in place"). If recruiters need to replace a résumé while
   keeping the same `attachment_id` and download link, a `PATCH .../resumes/{att_id}`
   endpoint would be needed. Assumed out of scope; multiple uploads + set-primary
   achieves the UX goal.

3. **`candidate_resume_bucket` in prod** — the default `"local-uploads"` is shared with
   the file manager and other services in dev. In prod, a dedicated bucket (e.g.,
   `{account}-candidate-resumes`) with a restricted bucket policy and an S3 lifecycle rule
   for soft-deleted objects is recommended. The bucket name is fully configurable via
   `CANDIDATE_RESUME_BUCKET`.

4. **`size_bytes` for file-manager-linked rows** — stored as `0` because no byte transfer
   occurs. This means the "total résumé storage" metric (if added later) must treat
   `source="file_manager"` rows differently. Assumption: `size_bytes=0` is acceptable for
   now; a future ticket can populate it from the node metadata.

5. **Atomicity of `set_primary_resume`** — the clear-then-set is a multi-step DDB
   operation without a transaction. Assumed acceptable for single-recruiter use. A DDB
   `TransactWriteItems` upgrade is a drop-in replacement if concurrent-write correctness
   becomes a requirement.

6. **`CANDIDATE_RESUME_CONTENT_TYPES` extensibility** — the allowlist is a `frozenset` in
   `app/models.py`. Adding new MIME types requires a code deploy. An env-var-configurable
   allowlist could be added later without breaking the current API.
