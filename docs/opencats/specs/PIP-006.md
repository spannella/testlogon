# PIP-006 — Placement record on transition to Placed

**Ticket type:** Feature
**Priority:** P1
**Estimate:** 2 days
**Master gate:** `S.ats_pipeline_enabled` (`ATS_PIPELINE_ENABLED`, default `false`) — introduced in PIP-001
**Depends on:** PIP-001 (junction table + flag), PIP-002 (status config + `is_placed` key), PIP-003
(`change_status`); ACT-009 (`record_crm_activity`, soft via lazy import); JOB-005
(`adjust_placed_count`, soft via lazy import — push-model placed counter)

---

## 1. Summary & Goal

PIP-006 delivers the **placement record**: the structured recruiting-outcome artifact that OpenCATS
writes when a candidate is formally placed in a role. When a recruiter calls the placement endpoint,
the system (1) advances the pipeline entry to the configured `is_placed` status (`900_placed` by
default), (2) writes a permanent placement sub-row capturing the start date and placement fee in
integer cents, (3) increments the job order's materialized `placed_count` counter via
`adjust_placed_count(job_id, +1)` (JOB-005, **push model** — see §4.1 / §5.11), (4) emits a
`pipeline.placed` audit event, and (5) writes best-effort dual activity timeline rows (one for the
candidate entity, one for the job-order entity) via ACT-009.

A placement can only be created once per pipeline entry. A second call on the same entry returns
`409 placement_exists`; the status stays Placed. A missing or foreign pipeline entry returns `404`.
A negative fee returns `422` at the Pydantic layer. The feature flag off returns `503
ats_pipeline_disabled`.

The placement record is the revenue artifact that feeds future recruiter-activity and placement
reports (gap analysis §C line 72, `OPENCATS_GAP_ANALYSIS.md:72` MISSING entry; RPT-002/003 data
source at `OPENCATS_GAP_ANALYSIS.md:90` §D). The spec is
fully additive — with the flag off the platform is byte-for-byte unchanged.

## 2. Context & Current State

**No placement surface exists today.** Searching `app/services/`, `app/routers/`, and all DynamoDB
table schemas finds no `placement`, `record_placement`, or `placed` symbol. The gap analysis
(`docs/opencats/OPENCATS_GAP_ANALYSIS.md:72`) lists "placement record (start date, fee) on Placed"
as **MISSING** and assigns it to the PIP ticket set. (Line 108 is in the recommended-tickets
section and also mentions the placement record but does not carry the MISSING designation.)

**PIP-001 is the foundational layer.** `docs/opencats/specs/PIP-001.md §3` specifies the
`ats_pipeline` DynamoDB table (PK `pk` / SK `sk`), the `T.ats_pipeline` table handle wired via
`_safe_table(S.ats_pipeline_table_name)` in `app/core/tables.py` (appended after `returns` at
`tables.py:571`), the `S.ats_pipeline_enabled` flag (`app/core/settings.py`, pattern at `:839`),
and the `_require_flag()` helper raising `HTTPException(503, detail={"code":
"ats_pipeline_disabled"})`. PIP-006 adds `record_placement()` and `get_placement()` to the same
`app/services/ats_pipeline.py` service file without altering any existing function.

**PIP-002 provides the `is_placed` config flag.** `docs/opencats/specs/PIP-002.md §3` specifies
the `PIPELINE_STATUS_CONFIG#META` singleton row and `get_status_config() -> PipelineStatusConfigOut`,
which returns the live stored config or the 9-status default ladder. Each status item has an
`is_placed: bool` flag; the config validator (`PipelineStatusConfigIn` root-validator) enforces
exactly one `is_placed` entry. `record_placement` calls `get_status_config()` to resolve the live
`is_placed` key dynamically — never hard-coding `"900_placed"`.

**PIP-003 provides `change_status`.** `docs/opencats/specs/PIP-003.md §4` specifies
`change_status(owner_sub, job_order_id, candidate_id, new_status, *, note=None) -> PipelineEntryOut`
in `app/services/ats_pipeline.py`. It validates `new_status` against the live config, applies an
`update_item` setting `status`, `status_rank`, and `updated_at=now_ts()`, and writes a
`pipeline.status_changed` audit event plus dual `record_crm_activity` rows. When `new_status ==
current_status` it is a no-op (no write, no log). `record_placement` calls `change_status` before
writing the placement sub-row so the entry is guaranteed to be at the `is_placed` status at the
time of commit.

**Single-table write proxy.** `app/core/tables.py:29–66` defines `_FloatSafeTable`, which coerces
Python `float` values to `Decimal` on every `put_item` and `update_item`. Money is stored as
integer cents (`fee_cents: int`), so no float coercion occurs in practice, but all writes go through
`T.ats_pipeline` (the `_FloatSafeTable` proxy) to match the platform-wide convention.

**Conditional-put duplicate guard pattern.** `app/services/group_treasury.py:604` uses
`ConditionExpression="attribute_not_exists(sk)"` and `app/services/purchase_history.py:233` uses
`"attribute_not_exists(user_sub) AND attribute_not_exists(sk)"` for idempotent one-shot inserts.
`app/routers/newsfeed.py:2561` uses the same `"attribute_not_exists(pk) AND
attribute_not_exists(sk)"` pattern. PIP-006 uses `attribute_not_exists(sk)` (or the equivalent
`Attr("sk").not_exists()` form from the OPP-004 junction pattern, `OPP-004.md §4`) on the
placement sub-row to enforce the one-placement-per-entry constraint without a read-before-write.

**Audit and timeline primitives.** `app/services/alerts.py:644` defines
`audit_event(event, user_sub, request, **fields)` — fire-and-forget, writes to `T.alerts`.
ACT-009 (`docs/suitecrm/specs/ACT-009.md §4.1`) delivers
`record_crm_activity(entity_type, entity_id, activity_type, activity_id, user_sub, *, summary,
metadata)` in `app/services/crm_activity_timeline.py`. PIP-006 calls both, with
`record_crm_activity` via a lazy local import inside `try/except` (ACT-009 §2.3 ordering-
independence pattern) so a missing or disabled ACT-009 module never prevents a placement write.

**Placed-count counter (push model, JOB-005).** JOB-005 owns a **materialized** `placed_count`
counter on the job-order record and mandates a **push model**: each placement / un-placement
transition calls `adjust_placed_count(job_id, +1)` / `adjust_placed_count(job_id, -1)` (in the
JOB-005 job-order service, e.g. `app/services/ats_job_orders.py`), which applies an atomic DDB
`ADD placed_count :delta` with a floor at 0. PIP-006 **does not** derive the placed count by
scanning `…#PLACEMENT` sub-rows (a pull model) — that would re-read every placement on each
job-order read and double-own the count. Instead PIP-006 pushes the delta at the moment of the
state change. The call is best-effort via a lazy local import inside `try/except` (same
ordering-independence posture as ACT-009): if JOB-005 has not shipped, the placement still
commits and the counter simply stays unmaintained until JOB-005 backfills. See §4.1 step 6 and
§5.11. (Reconciled per `docs/CROSS_TICKET_AUDIT.md §B2`: JOB-005 ↔ PIP-006 push-vs-pull conflict,
adopt push.)

**`now_ts()`.** `app/core/time.py:2` defines `now_ts() -> int` (integer Unix seconds). All
`created_at` timestamps use it.

**Cents formatting convention.** `frontend/src/pages/dashboard/EarningsSummaryCard.tsx:9` defines
`formatCents(cents)` as `` `$${(cents / 100).toFixed(2)}` `` (the function declaration is at line 9;
the return body is at line 10). The placement dialog in PIP-009
reuses this helper for the fee display.

## 3. Data Model

### 3.1 DynamoDB table: `ats_pipeline` (no new table, no new GSI)

PIP-006 adds a **third item type** to the existing `ats_pipeline` single-table. No new table,
no new GSI, and no `scripts/local-ddb-init.py` changes are required.

**All item types in `ats_pipeline` after PIP-006:**

| `pk` | `sk` | Purpose | Owner ticket |
|---|---|---|---|
| `USER#{owner_sub}` | `PIPE#{job_order_id}#CAND#{candidate_id}` | Pipeline entry (junction row) | PIP-001 |
| `PIPELINE_STATUS_CONFIG` | `META` | Admin ranked-status config | PIP-002 |
| `USER#{owner_sub}` | `PIPE#{job_order_id}#CAND#{candidate_id}#PLACEMENT` | **Placement record** | **PIP-006** |

The placement sub-row lives under the same partition (`pk=USER#{owner_sub}`) as the junction row it
extends. Its sort key is the junction row's sort key with the `#PLACEMENT` suffix appended — so a
single `begins_with("PIPE#{job_order_id}#CAND#{candidate_id}")` scan retrieves both the entry and
its optional placement. No additional index is required.

**Placement row attributes:**

| Attribute | DDB type | Description |
|---|---|---|
| `pk` | S | `USER#{owner_sub}` |
| `sk` | S | `PIPE#{job_order_id}#CAND#{candidate_id}#PLACEMENT` |
| `placement_id` | S | `pl_{uuid4().hex}` — stable projected ID for ergonomic reads and future reporting |
| `job_order_id` | S | Redundant projection; matches the sk segment |
| `candidate_id` | S | Redundant projection; matches the sk segment |
| `owner_sub` | S | Redundant projection; matches the pk |
| `start_date` | N | Integer Unix epoch seconds for the candidate's start date |
| `fee_cents` | N | Placement fee in integer cents; `ge=0`; stored as DynamoDB `N` via `_FloatSafeTable` |
| `status_at_placement` | S | The `is_placed` status key resolved from the live config at creation time (e.g., `"900_placed"`); immutable after write |
| `notes` | S | Optional free-text recruiter notes; absent if not supplied |
| `created_at` | N | Integer Unix epoch seconds via `now_ts()` |

**No numeric GSI sort keys are introduced.** All attributes except `start_date`, `fee_cents`, and
`created_at` are strings; the three numeric attributes are plain item attributes, not GSI sort keys.
No new `attr_types` entry is required in `scripts/local-ddb-init.py`. (The CLAUDE.md gotcha
"DynamoDB numeric GSI sort keys — omitting `attr_types` causes `ValidationException` at runtime"
applies only to GSI keys, not plain attributes.)

### 3.2 Pydantic models (`app/models.py`)

Append near the PIP-003/PIP-004/PIP-005 models in the ATS pipeline group:

```python
class PlacementIn(BaseModel):
    start_date: int = Field(..., description="Unix epoch seconds for the candidate's start date")
    fee_cents: int = Field(..., ge=0, description="Placement fee in integer cents; 0 = pro-bono")
    notes: Optional[str] = Field(None, max_length=2000)

class PlacementOut(BaseModel):
    placement_id: str
    job_order_id: str
    candidate_id: str
    owner_sub: str
    start_date: int
    fee_cents: int
    status_at_placement: str
    notes: Optional[str]
    created_at: int
```

`fee_cents` uses `ge=0` rather than `gt=0` so that a zero-fee (pro-bono) placement is valid.
`fee_cents < 0` is rejected by Pydantic with `422 Unprocessable Entity` before the service layer
is reached. `start_date` is an integer Unix timestamp (no timezone ambiguity); the frontend
formats it as a human-readable date using `new Date(start_date * 1000).toLocaleDateString()`.

#### `record_placement(owner_sub: str, job_order_id: str, candidate_id: str, data: PlacementIn) -> PlacementOut`

```python
def record_placement(
    owner_sub: str,
    job_order_id: str,
    candidate_id: str,
    data: PlacementIn,
) -> PlacementOut:
```

**Steps (in order):**

1. **Flag gate.** `_require_flag()` → raises `HTTPException(503, {"code": "ats_pipeline_disabled"})` when `S.ats_pipeline_enabled` is `False`.

2. **Ownership gate.** `get_pipeline_entry(owner_sub, job_order_id, candidate_id)` from PIP-001 — raises `HTTPException(404, {"code": "pipeline_entry_not_found"})` if the entry is absent or belongs to another owner.

3. **Resolve the `is_placed` status key.** `cfg = get_status_config()` (PIP-002). Extract `placed_key = next(s["status_key"] for s in cfg.statuses if s.get("is_placed"))`. Because `PipelineStatusConfigIn` enforces exactly one `is_placed` entry, this iteration always succeeds.

4. **Advance status to Placed.** Call `change_status(owner_sub, job_order_id, candidate_id, placed_key)` (PIP-003). If the entry is already at `placed_key` this is a no-op (PIP-003 §1 same-status idempotency — no audit/timeline row written for the transition). The status advance is intentionally done **before** the placement row write so that if the placement conditional-put fails (duplicate), the entry is still correctly Placed.

5. **Write placement sub-row (conditional).** Build the item:
   ```python
   item = {
       "pk": f"USER#{owner_sub}",
       "sk": f"PIPE#{job_order_id}#CAND#{candidate_id}#PLACEMENT",
       "placement_id": f"pl_{uuid4().hex}",
       "job_order_id": job_order_id,
       "candidate_id": candidate_id,
       "owner_sub": owner_sub,
       "start_date": data.start_date,
       "fee_cents": data.fee_cents,
       "status_at_placement": placed_key,
       "notes": data.notes,
       "created_at": now_ts(),
   }
   ```
   Issue `T.ats_pipeline.put_item(Item=item, ConditionExpression="attribute_not_exists(sk)")`.
   On `ClientError` with code `ConditionalCheckFailedException` → raise `HTTPException(409,
   {"code": "placement_exists"})`. The status advance from step 4 is **not** rolled back on 409:
   the entry is correctly Placed regardless (the placement record already exists from the first
   call). The placed-count push in step 6 is **only reached on a fresh (non-duplicate) commit** —
   a 409 short-circuits before step 6, so a duplicate placement never double-increments the counter.

6. **Push the placed-count delta (JOB-005, push model).** Via lazy local import + `try/except` so
   a missing/disabled JOB-005 never blocks the placement write:
   ```python
   try:
       from app.services.ats_job_orders import adjust_placed_count
       adjust_placed_count(job_order_id, +1)
   except Exception:
       pass  # counter maintenance is best-effort; placement is already committed
   ```
   This replaces any scan-derived (pull) count: the materialized `placed_count` on the job order
   is the single source of truth, updated atomically (`ADD placed_count :delta`, floor 0) by
   JOB-005. A future un-placement / void transition calls `adjust_placed_count(job_order_id, -1)`
   symmetrically (see §5.11). Because this runs only on a fresh commit (after the conditional-put
   in step 5 succeeds, never on the 409 path), the counter stays consistent with the at-most-once
   placement-row invariant.

7. **Audit event.** `audit_event("pipeline.placed", owner_sub, None, placement_id=..., job_order_id=..., candidate_id=..., fee_cents=data.fee_cents, start_date=data.start_date)` — fire-and-forget, never raises.

8. **Dual timeline write.** Via lazy local import + `try/except` (ACT-009 §2.3 pattern):
   ```python
   try:
       from app.services.crm_activity_timeline import record_crm_activity
       record_crm_activity(
           entity_type="candidate", entity_id=candidate_id,
           activity_type="placement", activity_id=placement_id,
           user_sub=owner_sub,
           summary=f"Placed — fee ${data.fee_cents / 100:.2f}, starts {data.start_date}",
           metadata={"fee_cents": data.fee_cents, "start_date": data.start_date,
                     "job_order_id": job_order_id, "placed_status": placed_key},
       )
       record_crm_activity(
           entity_type="job_order", entity_id=job_order_id,
           activity_type="placement", activity_id=placement_id,
           user_sub=owner_sub,
           summary=f"Placed {candidate_id} — fee ${data.fee_cents / 100:.2f}",
           metadata={"fee_cents": data.fee_cents, "start_date": data.start_date,
                     "candidate_id": candidate_id, "placed_status": placed_key},
       )
   except Exception:
       pass  # timeline failure never blocks the placement
   ```

9. **Return** `PlacementOut(**item)`.

#### `get_placement(owner_sub: str, job_order_id: str, candidate_id: str) -> PlacementOut`

```python
def get_placement(
    owner_sub: str,
    job_order_id: str,
    candidate_id: str,
) -> PlacementOut:
```

1. `_require_flag()`.
2. `T.ats_pipeline.get_item(Key={"pk": f"USER#{owner_sub}", "sk": f"PIPE#{job_order_id}#CAND#{candidate_id}#PLACEMENT"})`.
3. If no `Item` → `HTTPException(404, {"code": "placement_not_found"})`.
4. Return `PlacementOut(**item)`.

No ownership ambiguity: the `pk=USER#{owner_sub}` key provides structural authorization — a caller
cannot read another recruiter's placement sub-row because the PK partitions by `owner_sub`.

### 4.2 HTTP Endpoint (PIP-008 router)

The endpoint is declared in `app/routers/ats_pipeline.py` and registered in `app/main.py` by
PIP-008. It is included here for completeness.

| Method | Path | Handler | Auth | Notes |
|---|---|---|---|---|
| `POST` | `/ui/ats/pipeline/by-job/{job_order_id}/candidate/{candidate_id}/placement` | `record_placement_handler` | `Depends(require_ui_session)` | Creates placement |
| `GET` | `/ui/ats/pipeline/by-job/{job_order_id}/candidate/{candidate_id}/placement` | `get_placement_handler` | `Depends(require_ui_session)` | Reads existing placement |

Both handlers extract `owner_sub = ctx["user_sub"]` from the session context and delegate
immediately to the service function.

**`POST` handler:**
```python
@router.post(
    "/by-job/{job_order_id}/candidate/{candidate_id}/placement",
    response_model=PlacementOut,
    status_code=201,
)
async def record_placement_handler(
    job_order_id: str,
    candidate_id: str,
    body: PlacementIn,
    ctx: dict = Depends(require_ui_session),
):
    return record_placement(ctx["user_sub"], job_order_id, candidate_id, body)
```

**`GET` handler:**
```python
@router.get(
    "/by-job/{job_order_id}/candidate/{candidate_id}/placement",
    response_model=PlacementOut,
)
async def get_placement_handler(
    job_order_id: str,
    candidate_id: str,
    ctx: dict = Depends(require_ui_session),
):
    return get_placement(ctx["user_sub"], job_order_id, candidate_id)
```

**Route ordering.** The `placement` segment is a literal suffix of the dynamic sub-resource path
`/by-job/{job_order_id}/candidate/{candidate_id}/placement`. FastAPI resolves this without
shadowing because the `/by-job/…/placement` shape is distinct from all other routes in the router.
The CLAUDE.md route-ordering gotcha (literal segments must precede dynamic path params at the same
level) does not apply here — `placement` is a terminal segment, not at the same level as
`{candidate_id}`.

**CSRF.** `require_ui_session` (`app/services/sessions.py:330`) automatically enforces the
`x-csrf-token` header on non-GET cookie-auth requests. `POST /…/placement` is covered.

## 5. Detailed Behavior & Edge Cases

### 5.1 Normal placement flow

1. Recruiter drags a candidate card onto the "Placed" column in the Kanban (PIP-009 FE).
2. The Placement Dialog opens, collecting `start_date` (date picker, converted to Unix seconds in
   the client) and `fee_cents` (currency input using `formatCents` convention from
   `EarningsSummaryCard.tsx:9`).
3. On confirm, the FE posts `POST /ui/ats/pipeline/by-job/{job_id}/candidate/{cid}/placement` with
   `{start_date, fee_cents, notes?}`.
4. Backend advances status → writes placement row → emits audit + timeline → returns 201 `PlacementOut`.
5. FE React Query invalidates `["ats-pipeline", jobOrderId]` so the Kanban refreshes and the card
   renders with a "Placed" badge.

### 5.2 Duplicate placement (409)

A second `POST` on the same `{job_order_id, candidate_id}` pair under the same `owner_sub` hits the
conditional-put `attribute_not_exists(sk)` guard and returns `409 {"code": "placement_exists"}`.
The recruiter sees an error toast ("This candidate has already been placed."). The existing
placement row is unchanged. The pipeline entry status is already Placed from the first call (step
4's `change_status` was a no-op since `new_status == current_status` after the first success).

### 5.3 Entry already at Placed (idempotent status advance)

If a recruiter manually advances the status to `900_placed` via `PATCH …/status` (PIP-003) and
later calls `POST …/placement`, `change_status` in step 4 detects `new_status == current_status`
and short-circuits with no write, no audit. The placement sub-row is then written normally.

### 5.4 Foreign or absent entry (404)

If `job_order_id` or `candidate_id` does not exist in the calling recruiter's partition, or belongs
to another recruiter's `USER#{sub}`, `get_pipeline_entry` returns `None` and the service raises
`404 pipeline_entry_not_found` before any DDB write or status change occurs.

### 5.5 Negative fee (422)

`fee_cents < 0` is rejected by the Pydantic `ge=0` constraint and never reaches the service layer.
FastAPI returns `422 Unprocessable Entity` with the standard validation error body.

### 5.6 Zero fee (pro-bono)

`fee_cents = 0` is explicitly valid (pro-bono or contingency placements with a later invoice). The
audit event records `fee_cents=0`; the timeline summary reads "fee $0.00".

### 5.7 Timeline failure

A raised exception inside the `record_crm_activity` block is swallowed by the `try/except`. The
placement row is already committed at this point; the 201 response is returned. The recruiter sees
a successful result; the timeline entry is missing. This matches the ACT-009 §2.3 best-effort
contract throughout the PIP set.

### 5.8 `status_at_placement` captures the live key

If an admin later reconfigures the status ladder (e.g., renames `900_placed` to
`999_confirmed_placed`), the placement row's `status_at_placement` field retains the key that was
current at creation time. This provides a stable audit trail regardless of future config changes.
The field is immutable — `update_item` on the placement row is not exposed.

### 5.9 `start_date` timezone

`start_date` is stored as integer Unix epoch seconds. The frontend converts a date-picker value
(midnight local time or UTC, per UX convention) to epoch seconds before posting. The backend stores
and returns the raw integer without timezone interpretation. Reporting (RPT future ticket) renders
dates using the recruiter's configured timezone.

### 5.10 `notes` field

`notes` is optional (`None` when absent). If `notes=None` the item is written without the `notes`
attribute (absent key, not an explicit DynamoDB NULL). `PlacementOut.notes` is `Optional[str]`,
defaulting to `None` on reads where the attribute is absent.

### 5.11 Placed-count counter — push, not pull (JOB-005 reconciliation)

The job order's `placed_count` is maintained by the **push model**: `record_placement` increments
it via `adjust_placed_count(job_order_id, +1)` (step 6) and the symmetric un-placement / void
transition decrements it via `adjust_placed_count(job_order_id, -1)`. PIP-006 deliberately does
**not** derive the count by scanning `PIPE#…#PLACEMENT` sub-rows on each job-order read:

- **Read cost.** A pull/scan model is O(placements) per job-order read; the materialized counter is
  O(1). JOB-005's job-order list ("openings vs placed") reads the counter directly.
- **Single owner.** JOB-005 owns `placed_count` and its floor-at-0 atomic `ADD`. PIP-006 only emits
  the ±1 delta at the moment of the state change; it never reads or computes the aggregate.
- **Duplicate safety.** The +1 push is gated behind the conditional-put in step 5 (it runs only on a
  fresh commit, never on the 409 duplicate path), so a placement is counted at most once.
- **Un-placement direction.** The future "un-place / void placement" transition (deferred PATCH,
  §10 open question 2) calls `adjust_placed_count(job_order_id, -1)` before/after removing the
  placement sub-row, keeping the counter symmetric.
- **Best-effort.** The push is wrapped in `try/except` with a lazy import; if JOB-005 is absent the
  placement still commits and the counter is repaired by JOB-005's backfill when it ships.

This resolves the JOB-005 ↔ PIP-006 push-vs-pull inconsistency recorded in
`docs/CROSS_TICKET_AUDIT.md §B2` (item 2): **adopt push**.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

There is no `if S.dev_mode` branch in `record_placement` or `get_placement`. The only
environment-sensitive paths are the reused primitives:

- `T.ats_pipeline` writes go through `_FloatSafeTable` → boto3 → in-process moto (dev) or real DynamoDB (prod). Identical code path.
- `audit_event` writes `T.alerts` — same DDB-local (dev) or real DDB (prod).
- `record_crm_activity` (ACT-009) writes `T.crm_activity_timeline` — same.

No mock branch is needed. This matches the pattern across the PIP set (cross-cutting constraint #7,
`ATS_PIPELINE_TICKETS.md:29`).

### 7.2 Idempotency

The conditional-put guard (`attribute_not_exists(sk)`) makes `record_placement` a safe **at-most-once** write. The first successful call commits the placement; all subsequent calls return 409. The status advance (`change_status`) is idempotent by design (PIP-003 §1). Together these ensure that a network retry after a timeout that resulted in a committed placement returns 409 (with a stable status = Placed), not a duplicate placement or a corrupted entry.

A client receiving 409 on a retry can call `GET .../placement` to confirm the existing placement
record and display it to the recruiter.

### 7.3 Structural authorization

The placement sub-row's `pk=USER#{owner_sub}` structural key means an attacker who supplies another
user's `job_order_id` or `candidate_id` will hit `get_pipeline_entry`'s 404 before the placement
write (ownership-by-key authz, OPP-004 §5, cross-cutting constraint #5). The `GET` handler
similarly scopes to `pk=USER#{ctx["user_sub"]}` — a foreign recruiter's `owner_sub` never appears
in their own partition.

No role gate is needed on the placement surface. Any authenticated recruiter who owns the pipeline
entry can place the candidate. The admin-gated surface (status-config write) lives in PIP-002.

### 7.4 CSRF

`require_ui_session` (`app/services/sessions.py:330`) validates the `x-csrf-token` header on all
non-GET cookie-auth requests. The `POST …/placement` handler is protected automatically. Bearer-auth
clients (API keys, future integrations) bypass CSRF per the platform standard (CLAUDE.md §Auth).

### 7.5 Input bounds

- `fee_cents`: `ge=0` (Pydantic) + `int` type (no float accepted).
- `start_date`: `int` (Unix seconds); no lower/upper bound enforced at the service layer. Future
  validation (e.g., `>= today`) may be added without breaking the model.
- `notes`: `max_length=2000` to prevent unbounded DynamoDB item size growth.
- Path params `job_order_id` and `candidate_id` are validated by `get_pipeline_entry` (must exist
  in the partition); no additional regex is applied.

## 10. Open Questions / Assumptions

1. **`start_date` as epoch vs. ISO string.** The ticket (ATS_PIPELINE_TICKETS.md:205) says
   "`start_date` (N, Unix-day or epoch seconds)". This spec uses **epoch seconds** for consistency
   with every other timestamp in the platform (`now_ts()` convention). If the frontend prefers a
   date string, the API layer can accept an ISO date string and the service converts it. This
   decision should be confirmed before the frontend placement dialog (PIP-009) is implemented.

2. **Placement update (PATCH).** This spec intentionally omits a placement-update endpoint.
   `status_at_placement` is immutable; `fee_cents` and `start_date` corrections require a different
   business-process policy (e.g., void + re-create). A future `PATCH .../placement` can be added
   without breaking this spec.

3. **CND-* primary candidate record resolution.** `record_placement` does not currently resolve or
   embed the candidate's name in the ACT-009 timeline summary — it uses the opaque `candidate_id`.
   When CND-* ships a `get_candidate(owner_sub, candidate_id)` resolver, the timeline summary can
   be enriched with the candidate's display name. This is a non-breaking follow-up.

4. **Placement fee currency.** `fee_cents` implies USD cents. If multi-currency support is required
   in future, a `currency: str = "USD"` field can be appended to `PlacementIn`/`PlacementOut`
   without breaking existing rows (absent = USD).

5. **Placement in job-order `openings_vs_placed` counter.** The gap analysis (line 61) lists
   "openings-vs-placed" as a missing job-order list filter. The **placed** side of that counter is
   now handled by the push model: `record_placement` calls `adjust_placed_count(job_order_id, +1)`
   (JOB-005), and the materialized `placed_count` feeds the job-order list directly — no scan of
   `…#PLACEMENT` sub-rows (reconciled per `docs/CROSS_TICKET_AUDIT.md §B2`, see §5.11). The
   **openings** side (decrementing remaining openings) remains owned by JOB-005 / the JOB-* counter
   ticket; PIP-006 only pushes the placed delta. The placement sub-row still provides the durable
   per-placement audit data underneath the counter.

### Cross-ticket reconciliation (audit 2026-06-13)

Per `docs/CROSS_TICKET_AUDIT.md §B2` (item 2) and Part C item 7: the JOB-005 ↔ PIP-006 placement

push is best-effort (lazy import + `try/except`) and gated behind the conditional-put so a duplicate
placement (409) never double-increments. Amended: §1, §2 (new context paragraph + header
