# PIP-007 — Bulk add/remove candidates to/from a job-order pipeline

**Ticket type:** Feature
**Priority:** P1
**Estimate:** 2 days
**Master gate:** `S.ats_pipeline_enabled` (`ATS_PIPELINE_ENABLED`, default `false`) — introduced in PIP-001
**Depends on:** PIP-001 (`add_to_pipeline`, `remove_from_pipeline`, `_require_flag`, `T.ats_pipeline`); JOB-* (`get_job_order` — ownership gate); CND-* (`get_candidate` — soft, per-item)

---

## 1. Summary & Goal

PIP-007 delivers the **bulk pipeline operations** that let a recruiter drop a multi-select of
candidates onto a job order, or clear several at once, in a single HTTP call. This matches the
OpenCATS "add to this job order pipeline" multi-select UX documented in the gap analysis
(`docs/opencats/OPENCATS_GAP_ANALYSIS.md:71`, §C: "Bulk pipeline add/remove — **MISSING**").

Two new service functions and two new HTTP endpoints are added to the existing
`app/services/ats_pipeline.py` and (via PIP-008) `app/routers/ats_pipeline.py`:

- `bulk_add_to_pipeline(owner_sub, data)` — validates the job order once, then iterates the
  candidate list calling `add_to_pipeline` per candidate, and returns a structured
  `BulkPipelineResultOut` with `added`, `skipped` (with per-item reason), and an optional
  initial `status` applied to every successfully added entry.
- `bulk_remove_from_pipeline(owner_sub, data)` — symmetric removal; returns a
  `BulkPipelineResultOut` with `removed` and `skipped`.

Neither function is an all-or-nothing transaction. Each candidate row is independent.
Partial success (some added, some skipped) returns HTTP 200 with the full breakdown so the
caller can surface per-item diagnostics. The 100-candidate cap is enforced at the Pydantic
model boundary (422) so the service loop is bounded without DynamoDB transaction limits.

All behavior is additive and fully gated behind `S.ats_pipeline_enabled`. With the flag off:
no DDB writes, no HTTP routes, no sidebar entry — the platform is byte-for-byte unchanged.

## 2. Context & Current State

**No bulk pipeline surface exists today.** Searching the repository for `bulk_add_to_pipeline`,
`bulk_remove_from_pipeline`, or `BulkPipelineAddIn` returns zero results. The gap analysis
(`OPENCATS_GAP_ANALYSIS.md:71`) confirms the capability is fully absent.

**PIP-001** (`docs/opencats/specs/PIP-001.md`) introduces:
- `T.ats_pipeline` — the `_FloatSafeTable` proxy (`app/core/tables.py:29–66`) wrapping the
  `ats_pipeline` DynamoDB table.
- `S.ats_pipeline_enabled` / `S.ats_pipeline_table_name` in `app/core/settings.py` (style:
  `os.environ.get("ATS_PIPELINE_ENABLED", "false").lower() == "true"`, matching
  `inventory_reservations_enabled` at `settings.py:839`).
- `_require_flag()` — raises `HTTPException(503, detail={"code": "ats_pipeline_disabled"})`.
- `add_to_pipeline(owner_sub, data) -> PipelineEntryOut` — single-row insert with
  `Attr("sk").not_exists()` conditional-put; raises 409 `pipeline_entry_exists` on duplicate
  and 404 for a foreign/absent job order or candidate (lazy-import guard per PIP-001 §4.1).
- `remove_from_pipeline(owner_sub, job_order_id, candidate_id) -> None` — raises 404
  `pipeline_entry_not_found` if the row is absent.

Both primitives already emit their own per-row `audit_event` calls (`pipeline.candidate_added`
/ `pipeline.candidate_removed`). PIP-007 **calls them in a loop** and adds one summary
`audit_event` on top — it does not duplicate the single-row logic.

**`audit_event` is the platform audit primitive.** `app/services/alerts.py:644` defines
`audit_event(event, user_sub, request, **fields)`. It is fire-and-forget, writes to
`T.alerts`, and is called after every mutation. PIP-007 emits one summary audit per bulk
call (in addition to the per-row audits from `add_to_pipeline`/`remove_from_pipeline`).

**`require_ui_session` is the standard user-facing auth dependency.** `app/services/sessions.py:330`
defines the async dependency; it enforces CSRF automatically on non-GET cookie requests.
Both bulk endpoints depend on it, registered in PIP-008.

**Route ordering constraint.** `ATS_PIPELINE_TICKETS.md:270` documents the FastAPI static-
before-dynamic rule: `bulk-add` and `bulk-remove` must be declared **before** any
`/{pipeline_id}` or dynamic path-parameter routes in `app/routers/ats_pipeline.py`. PIP-008
includes `POST /ui/ats/pipeline/bulk-add` and `POST /ui/ats/pipeline/bulk-remove` in the
literal-segment-first block (alongside `statuses`, `feature-status`) above the dynamic-param
sub-resource routes.

**`normalize_role` / `Role` enum.** `app/auth/roles.py:48` and `:8`. PIP-007 itself has
no admin gate (bulk operations are user-scoped), but the admin gate pattern is established by
PIP-002/PIP-008 for `PUT /ui/admin/ats/pipeline/statuses`.

**`now_ts()` and `_FloatSafeTable`.** `app/core/time.py:2` and `app/core/tables.py:29–66`.
All timestamps are integer Unix seconds; all writes go through the proxy.

**Ownership-by-key authorization.** The `pk=USER#{owner_sub}` partition enforces data ownership
structurally (OPP-004 §5 / PIP-001 §5.1): an attacker who provides a foreign `owner_sub` in
their JWT misses all rows in that partition and gets a 404 from the inner primitive. No
separate ACL check is needed. The single `get_job_order(job_order_id)` call at
the top of each bulk function is the only cross-table ownership gate. Note: `get_job_order`
takes only `job_id` (not `owner_sub`) per JOB-002 §4.5; ownership is enforced structurally
by the `COMPANY#{client_company_id}` partition in the job-orders table.

## 3. Data Model

### 3.1 DynamoDB table: `ats_pipeline` (no new table, no new GSIs)

PIP-007 adds **no new DynamoDB tables, no new GSIs, and no `scripts/local-ddb-init.py`
changes**. All writes go through `T.ats_pipeline` via the per-item `add_to_pipeline` and
`remove_from_pipeline` primitives introduced in PIP-001. The `ats_pipeline` `TableDef` in
`scripts/local-ddb-init.py` already covers the full item shape:

```python
TableDef(
    _resolve_table_name(S.ats_pipeline_table_name, "ats_pipeline"),
    "pk",   # S — "USER#{owner_sub}"
    "sk",   # S — "PIPE#{job_order_id}#CAND#{candidate_id}"
)
```

No numeric sort-key GSI is introduced, so no `attr_types` entry is required. If a future
ticket (PIP-008 list/bulk note) adds a GSI sorted on a numeric attribute (e.g. `created_at`),
the `attr_types={"created_at": "N"}` entry must be added at that time to prevent the
`ValidationException` at query time (CLAUDE.md numeric-GSI-sort-key gotcha).

### 3.2 Pydantic Models (`app/models.py`)

Append near `PipelineEntryCreateIn` / `PipelineEntryOut` (introduced by PIP-001):

```python
class BulkPipelineAddIn(BaseModel):
    job_order_id: str
    candidate_ids: List[str] = Field(..., min_length=1, max_length=100)
    status: Optional[str] = None  # applied to every successfully added entry

class BulkPipelineRemoveIn(BaseModel):
    job_order_id: str
    candidate_ids: List[str] = Field(..., min_length=1, max_length=100)

class BulkPipelineSkipItem(BaseModel):
    candidate_id: str
    reason: str  # "already_in_pipeline" | "not_found" | "dependency_unavailable"

class BulkPipelineResultOut(BaseModel):
    added: List[str]       # candidate_ids successfully added
    skipped: List[BulkPipelineSkipItem]  # per-item failures (add path)
    removed: List[str]     # candidate_ids successfully removed (remove path)
```

`BulkPipelineResultOut` serves both the add and remove paths. For the add path `removed` is
always `[]`; for the remove path `added` and `skipped` carry the removal breakdown (with
`removed` populated and `added=[]`). This single shape keeps the API surface minimal and the
frontend handler symmetric.

The `min_length=1` / `max_length=100` on `candidate_ids` is enforced at the Pydantic
validation layer. An empty list returns `HTTP 422 Unprocessable Entity`; a list of more than
100 returns `HTTP 422`. This is consistent with the 1–10 boundary on `SubmitToClientIn.to_emails`
(PIP-005 §3) and the general Pydantic `Field(ge=..., le=...)` style used throughout the
platform.

## 4. API / Service Design

### 4.1 Service functions in `app/services/ats_pipeline.py`

Both functions are appended to the existing service file delivered by PIP-001 without
modifying any existing function.

#### `bulk_add_to_pipeline(owner_sub: str, data: BulkPipelineAddIn) -> BulkPipelineResultOut`

```
1. _require_flag()
2. Lazy-import get_job_order from app.services.job_orders inside try/except ImportError.
   If module absent → HTTPException(503, code="job_orders_not_available").
   Call get_job_order(data.job_order_id) — raises 404 if absent.
   Note: get_job_order(job_id) takes only job_id (not owner_sub) per JOB-002 §4.5; the
   job-orders table enforces ownership via the COMPANY#{client_company_id} partition.
   Fail fast: this is the upfront existence gate; the loop never runs for an absent job order.
3. added: List[str] = []
   skipped: List[BulkPipelineSkipItem] = []
4. For each candidate_id in data.candidate_ids:
     try:
         inner_data = PipelineEntryCreateIn(
             job_order_id=data.job_order_id,
             candidate_id=candidate_id,
             status=data.status,
         )
         add_to_pipeline(owner_sub, inner_data)   # PIP-001
         added.append(candidate_id)
     except HTTPException as exc:
         if exc.status_code == 409:
             skipped.append(BulkPipelineSkipItem(candidate_id=candidate_id,
                                                  reason="already_in_pipeline"))
         elif exc.status_code == 404:
             skipped.append(BulkPipelineSkipItem(candidate_id=candidate_id,
                                                  reason="not_found"))
         elif exc.status_code == 503:
             skipped.append(BulkPipelineSkipItem(candidate_id=candidate_id,
                                                  reason="dependency_unavailable"))
         else:
             raise   # unexpected — re-raise so caller gets a 5xx, not silent corruption
5. Summary audit (fire-and-forget try/except):
     audit_event("pipeline.bulk_added", owner_sub, None,
                 job_order_id=data.job_order_id,
                 added_count=len(added),
                 skipped_count=len(skipped))
6. Return BulkPipelineResultOut(added=added, skipped=skipped, removed=[])
```

#### `bulk_remove_from_pipeline(owner_sub: str, data: BulkPipelineRemoveIn) -> BulkPipelineResultOut`

```
1. _require_flag()
2. Lazy-import get_job_order from app.services.job_orders (same guard as above).
   Call get_job_order(data.job_order_id) — same upfront existence gate.
3. removed: List[str] = []
   skipped: List[BulkPipelineSkipItem] = []
4. For each candidate_id in data.candidate_ids:
     try:
         remove_from_pipeline(owner_sub, data.job_order_id, candidate_id)  # PIP-001
         removed.append(candidate_id)
     except HTTPException as exc:
         if exc.status_code == 404:
             skipped.append(BulkPipelineSkipItem(candidate_id=candidate_id,
                                                  reason="not_found"))
         else:
             raise
5. Summary audit (fire-and-forget try/except):
     audit_event("pipeline.bulk_removed", owner_sub, None,
                 job_order_id=data.job_order_id,
                 removed_count=len(removed),
                 skipped_count=len(skipped))
6. Return BulkPipelineResultOut(added=[], skipped=skipped, removed=removed)
```

Both functions deliberately do **not** call `record_crm_activity` (ACT-009) at the bulk
level. Each successful call to `add_to_pipeline` / `remove_from_pipeline` already emits its
own `audit_event`; the per-item activity timeline write (if any) is the PIP-001 /
PIP-003 responsibility. Logging N individual timeline entries per bulk call at the bulk-
function level would duplicate them. If a future requirement calls for a single "bulk
add" activity row on each candidate/job-order timeline, that is a follow-up to PIP-007.

### 4.2 HTTP Endpoints (registered in PIP-008)

PIP-007 delivers the service layer only. PIP-008 (`app/routers/ats_pipeline.py`) exposes the
following two endpoints — they are shown here for completeness:

| Method | Path | Handler body | Auth |
|--------|------|--------------|------|
| `POST` | `/ui/ats/pipeline/bulk-add` | `bulk_add_to_pipeline(ctx["user_sub"], body)` | `Depends(require_ui_session)` |

§5.3 on partial-success semantics).

an authenticated session. They are not registered in `API_KEY_ROUTE_EXEMPTIONS`
(`app/services/api_key_route_scope_registry.py:70`).

## 5. Detailed Behavior & Edge Cases

### 5.1 Upfront job-order ownership gate

`get_job_order(job_order_id)` is called exactly **once** before the loop. The function
signature is `get_job_order(job_id: str)` per JOB-002 §4.5 — no `owner_sub` parameter.
If it raises 404 (absent job order), the function raises `HTTPException(404)` immediately
and the loop never runs. This prevents an attacker from enumerating whether foreign
candidates are pipeline members by submitting bulk add/remove against an absent job order —
the 404 fires before any per-candidate lookup occurs.

If the `app.services.job_orders` module is not yet deployed, the `ImportError` guard
surfaces a 503 `job_orders_not_available`. The entire call fails fast; no partial writes
occur.

### 5.2 Per-candidate errors are collected, not re-raised

Within the loop, `HTTPException` with codes 404, 409, or 503 is converted to a
`BulkPipelineSkipItem`. All other `HTTPException` codes (e.g., an unexpected 500 from a
broken DynamoDB endpoint) are **re-raised** so the caller receives a genuine error response
rather than silent data corruption. Non-HTTP exceptions (e.g., network-level errors reaching
DynamoDB) propagate unconditionally — they indicate infrastructure failure, not per-item
semantics, and must not be swallowed.

The three expected skip reasons:
- `already_in_pipeline` — the 409 `pipeline_entry_exists` from PIP-001's conditional-put.
- `not_found` — the 404 from `add_to_pipeline` (candidate absent/foreign) or
  `remove_from_pipeline` (entry absent).
- `dependency_unavailable` — the 503 from `add_to_pipeline` when the CND-* module is not
  yet deployed. This allows bulk-add to work for candidates whose ids are already known even
  before CND-* ships (the caller pre-validates ownership).

### 5.3 Partial success is always HTTP 200

A mixed result (`added=[3], skipped=[{candidate_id, reason}]`) returns HTTP 200 with the
full `BulkPipelineResultOut` payload. The HTTP status code reflects the success of the
bulk call, not the success of every individual item. This matches the convention used by the
KYC document processing path (multiple sub-items processed independently) and the billing
ledger batch writes in `billing_ccbill.py`. The frontend reads `added.length` and
`skipped.length` to surface per-item diagnostics in the UI.

If the upfront `get_job_order` raises 404 or the flag is off and `_require_flag()` raises
503, **those** are returned as HTTP 404/503 respectively (they are fatal errors, not item-
level skips).

### 5.4 Ordering of loop iterations

The loop processes `candidate_ids` in the order supplied by the caller. There is no
deduplication of the input list: if the caller supplies the same `candidate_id` twice, the
first iteration adds it (or skips with `already_in_pipeline` if the row already exists) and
the second iteration also skips with `already_in_pipeline` (because the conditional-put from
PIP-001 fires on the second call too). The result `added` list will contain the candidate_id
at most once because the second call is skipped. No de-dup pre-pass is needed.

### 5.5 Summary audit event

The summary `audit_event` (`pipeline.bulk_added` / `pipeline.bulk_removed`) is emitted
**once** per bulk call, inside a `try/except` so an `alerts` table write failure never
aborts the response. It carries `added_count` and `skipped_count` (or `removed_count` and
`skipped_count`) for aggregate reporting. Individual per-row `audit_event` calls
(`pipeline.candidate_added` / `pipeline.candidate_removed`) are still emitted by the inner
`add_to_pipeline` / `remove_from_pipeline` primitives — the summary event is **additive**,
not a replacement.

### 5.6 Status on bulk add

`BulkPipelineAddIn.status` is optional (defaults `None`). When `None`, `add_to_pipeline`
defaults to `"100_no_contact"` (PIP-001 §5.4). When a custom status is provided it is passed
through to each `add_to_pipeline` call. If the status is not valid in the live config (PIP-002),
`add_to_pipeline` will raise a 400 (once PIP-002 / PIP-003 validation is wired). In the
current PIP-007 scope (pre-PIP-002 validation), invalid statuses are stored as-is
(PIP-001 §5.4). Once PIP-002/PIP-003 are merged, the inner call's 400 would propagate as
an unexpected re-raise (§5.2 above), correctly surfacing the misconfiguration to the caller
rather than silently skipping every candidate.

### 5.7 Performance bound

With `max_length=100` on `candidate_ids`, the loop is bounded at 100 DynamoDB
`put_item`/`delete_item` operations per call. Each operation is synchronous (the service
layer does not use `asyncio.gather` over the DynamoDB boto3 resource). For 100 candidates
against a DynamoDB Local dev endpoint this completes in well under 1 second. If future
load testing reveals latency issues, the loop can be refactored to use
`T.ats_pipeline.batch_writer()` for removes (DynamoDB batch delete) and parallel
conditional-puts for adds — but that is an optimization deferred out of scope for PIP-007.

### 5.8 `remove_from_pipeline` idempotency

`remove_from_pipeline` raises 404 when the entry does not exist (PIP-001 §4.1). In the bulk
path this becomes a `skipped` item with `reason="not_found"`. This is intentional: bulk
remove does not silently succeed for absent entries (that would hide bugs in the caller).
The frontend's "remove selected" UX should treat `not_found` as a non-critical warning (the
entry is already gone), not a hard error.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

There are **no `if S.dev_mode` branches** in PIP-007. The DynamoDB writes go through
`T.ats_pipeline` (`_FloatSafeTable` proxy, `app/core/tables.py:29–66`), which hits
DynamoDB Local at `http://localhost:8001` in dev and the real DynamoDB endpoint in prod —
the code path is identical. `audit_event` writes to `T.alerts` in both environments. No
email or S3 operations are introduced by PIP-007. SECOPS-007 parity is trivially satisfied.

### 7.2 Idempotency

`bulk_add_to_pipeline` is **not idempotent** for new entries (calling it twice adds the
candidate on the first call and skips it with `already_in_pipeline` on the second). This is
the correct behavior: the client controls whether to re-try or de-dup.

`bulk_remove_from_pipeline` is effectively idempotent in the sense that calling it twice
produces `removed=[...]` on the first call and `skipped=[..., reason="not_found"]` on the
second — the final state (entries absent) is the same. The HTTP response differs (all-removed
vs all-skipped), which is intentional for diagnostics.

### 7.3 Authorization

- **Data-plane ownership** is enforced by `pk=USER#{owner_sub}` (structural authorization,
  OPP-004 §5 / PIP-001 §5.1). An attacker who forges another user's `owner_sub` in their
  JWT will miss all rows and receive 404s.
- **Upfront job-order gate** (`get_job_order(job_order_id)`) verifies the job order exists
  before the loop begins — no partial writes occur for an absent job order. (JOB-002 §4.5:
  `get_job_order` takes `job_id` only; structural ownership is enforced by the job-orders
  table partition.)
- **No ADMIN/ROOT gate** on the bulk endpoints. Bulk add/remove is a recruiter-level operation
  (same privilege level as single `add_to_pipeline`). The admin gate applies only to the
  status-config write endpoint (`PUT /ui/admin/ats/pipeline/statuses`, PIP-002/PIP-008).
- **Input size cap** (`max_length=100`) prevents a single request from triggering an unbounded
  DynamoDB write loop. Enforced at the Pydantic model layer (422 before the service is entered).

### 7.4 CSRF

Both endpoints are `POST` methods depending on `require_ui_session` (`sessions.py:330`).
Cookie-auth callers must include `x-csrf-token: <csrf_token>` matching the session's stored
`csrf_token` and the `ui_csrf` cookie value (CLAUDE.md §Auth dependency). Bearer-auth
callers skip CSRF per the platform convention.

### 8.1 No schema changes

PIP-007 adds **no new DynamoDB item types, no new attributes on existing items, no new GSIs,
and no `scripts/local-ddb-init.py` changes**. The `ats_pipeline` table definition from

`BulkPipelineResultOut` are **new** models appended to `app/models.py`. No existing model
is modified. All previously serialised API responses are byte-for-byte unchanged.

### 8.3 No `main.py` changes

PIP-007 adds two functions to `app/services/ats_pipeline.py`. The HTTP endpoints are mounted
in PIP-008 (`app/routers/ats_pipeline.py`), which is already responsible for registering all
PIP endpoints in `app/main.py` inside the `if _S.ats_pipeline_enabled:` guard. PIP-007
itself has no `main.py` impact.

### 8.4 Forward compatibility with PIP-002/PIP-003 status validation

`BulkPipelineAddIn.status` passes through `add_to_pipeline` which, once PIP-002 and PIP-003
are merged, will validate the status key against the live config. If the status is invalid,
`add_to_pipeline` raises a 400 that the bulk loop currently re-raises (§5.6). This is
intentional: an invalid `status` in a bulk call is a caller error, not a per-candidate skip.
No change to PIP-007 is needed when PIP-002/PIP-003 merge; the behavior upgrades
automatically.

## 10. Open Questions / Assumptions

1. **Transaction semantics for "must add all or none"** — The current design is partial-
   success (no all-or-nothing transaction). DynamoDB `TransactWriteItems` supports up to 100
   items, which matches the 100-id cap. If the product team decides that bulk-add must be
   atomic (all succeed or all roll back), `TransactWriteItems` with
   `ConditionCheck`+`Put` operations is the implementation path. This is deferred because
   OpenCATS's original bulk-add is also best-effort (it commits each row independently).

2. **Per-candidate validation before the loop** — The current design validates the job order
   once upfront but resolves each candidate lazily inside the loop. An alternative
   "validate-all-then-write" approach (resolve all candidates first, then write if no errors)
   would provide a stronger "fail fast without partial writes" guarantee. Deferred pending
   product decision on UX (surfacing per-item errors vs. all-or-nothing).

3. **`get_candidate` ownership semantics** — Until CND-* ships, `get_candidate` is a lazy
   import that triggers the `503 dependency_unavailable` path. The assumption is that once
   CND-* ships, `get_candidate(candidate_id)` raises 404 for foreign/absent
   candidates — the same ownership-by-key pattern as `get_job_order`. If CND-* uses a
   different ownership model (e.g., global candidate pool shared across recruiters), the
   skip-reason classification may need updating.

4. **Status validation on bulk add** — `BulkPipelineAddIn.status` defaults to `None`
   (PIP-001 defaults to `"100_no_contact"`). Once PIP-002/PIP-003 land, an invalid status
   propagates as a re-raised 400, failing the entire bulk call. If the product team prefers
   per-item status validation (skip items with invalid status rather than aborting), the
   loop's `except HTTPException` clause should be extended to catch 400 `invalid_status`.
   Deferred.

5. **`bulk_remove` behavior for entries with placements** — PIP-006 introduces a
   `…#PLACEMENT` sub-row keyed under the same `pk`. `remove_from_pipeline` (PIP-001) calls
   `delete_item` on the junction row only; it does not delete the placement sub-row.
   If a recruiter bulk-removes a placed candidate, the placement record is orphaned. A
   follow-up (PIP-006 §5 or a future cleanup ticket) should decide whether bulk-remove
   blocks on placed entries, warns, or deletes the placement sub-row transitively.
