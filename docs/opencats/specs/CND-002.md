# CND-002 — Candidate CRUD service (extends/reuses Lead patterns)

**Type:** Feature · **Priority:** P0 · **Estimate:** 2 days  
**Cluster:** ATS Candidates (CND) · **Gap analysis:** `docs/opencats/OPENCATS_GAP_ANALYSIS.md` §A  
**Depends on:** CND-001 (table, flag, settings, models)  
**Required by:** CND-003 (résumé attachments), CND-004 (change history), CND-005 (router)

---

## 1. Summary & Goal

CND-002 delivers `app/services/candidates.py` — the complete DynamoDB data-access and
business-logic layer for the `candidates` table. The goal is a clean CRUD service that a
recruiter can call to create, read, list, update, soft-delete, and reassign candidates,
with email/phone normalization, GSI-routed pagination, idempotent email-based duplicate
short-circuiting, and per-operation audit emission. It is the CND-cluster analogue of the
planned LED-003 Lead service, mirroring its structure intentionally so the two services
stay convergent and a future consolidation can hoist shared helpers without friction.

CND-002 owns only the ATS-specific delta (candidate-pipeline status, ATS fields, the
five public functions) and deliberately delegates everything else: dedupe/merge to
LED-009, owner round-robin to LED-010, source analytics to LED-004, and the
change-history write to CND-004 via a fire-and-forget adapter. No existing file is
modified destructively; every change is a new file or an append.

## 3. Data Model

CND-001 owns the full DDB schema; this section states only the details CND-002 must
read, write, or query to implement the service correctly.

### 3.1 Table: `candidates`

Single-table. Hash key `pk` (S), sort key `sk` (S). `TableDef` in
`scripts/local-ddb-init.py` uses `attr_types={"GSI1SK": "N", "GSI2SK": "N", "GSI3SK": "N"}` — all three GSI sort keys are numeric (CLAUDE.md numeric-GSI gotcha; `local-ddb-init.py:35`). `created_at` is a plain item attribute (not a GSI key — the GSI sort keys are the `GSI?SK` aliases), so it must NOT appear in `attr_types`; including a non-key attribute there triggers `ValidationException` (CND-001 §3.4, CND-001 Verification Log row 21).

**META row** (one per candidate, written by `create_candidate`):

| Attribute | DDB type | Notes |
|---|---|---|
| `pk` | S | `"CANDIDATE#{candidate_id}"` |
| `sk` | S | `"META"` |
| `candidate_id` | S | `"cand_" + uuid4().hex[:20]` — prefix avoids collisions with attachment IDs |
| `first_name` / `last_name` | S | required on create |
| `email` | S | normalized (lowercase, `@` required, ≤ 254 chars) |
| `email_raw` | S | pre-normalization original, preserved for display fidelity |
| `phone` | S \| absent | E.164 via `normalize_phone`; absent when not provided |
| `company` / `title` | S \| absent | current employer / current title |
| `source` | S | `"other"` default; stored as LED-004 requires; closed set from `CANDIDATE_SOURCES` (CND-001 models) |
| `owner_sub` | S | recruiter `user_sub`; defaults to `creator_sub` |
| `status` | S | `"active"` default; closed set `CANDIDATE_STATUSES` (CND-001) |
| `current_pay` / `desired_pay` | S \| absent | ATS delta; free-text; max 200 chars each |
| `key_skills` | S \| absent | ATS delta; free-text; max 4 000 chars |
| `date_available` | S \| absent | ATS delta; `"YYYY-MM-DD"` ISO date string |
| `can_relocate` | BOOL | ATS delta; default `False` |
| `linkedin_url` / `web_url` | S \| absent | ATS delta; max 500 chars |
| `address` / `city` / `state` / `postal_code` / `country` | S \| absent | ATS postal address delta |
| `primary_resume_id` | S \| absent | set by CND-003 `set_primary_resume`; absent until first résumé uploaded |
| `created_by` | S | `creator_sub` |
| `created_at` | N | `now_ts()` at creation |
| `updated_at` | N | `now_ts()` on every write |
| `deleted_at` | N \| absent | soft-delete marker; absent = not deleted |
| `GSI1PK` | S | `"OWNER#{owner_sub}"` |
| `GSI1SK` | N | `created_at` |
| `GSI2PK` | S | `"STATUS#{status}"` |
| `GSI2SK` | N | `created_at` |
| `GSI3PK` | S | `"SOURCE#{source}"` |
| `GSI3SK` | N | `created_at` |

### 3.2 GSI layout (three, `ProjectionType: ALL`)

| GSI | Partition key | Sort key | Primary use |
|---|---|---|---|
| `ByOwner` | `GSI1PK` (`"OWNER#{owner_sub}"`) | `GSI1SK` = `created_at` N | list by recruiter |
| `ByStatus` | `GSI2PK` (`"STATUS#{status}"`) | `GSI2SK` = `created_at` N | list by pipeline status; also used by `find_candidate_by_email` scan |
| `BySource` | `GSI3PK` (`"SOURCE#{source}"`) | `GSI3SK` = `created_at` N | list by source; LED-004 analytics |

The GSI structure (three GSIs, same names, same numeric sort keys) is intentionally
identical to the Lead `leads` table (LED-003 §3.2), so future consolidation requires
no migration. **One semantic difference**: LED-003's `GSI1PK` encodes `created_by`
(`"OWNER#{created_by}"`), while CND-002 encodes `owner_sub` (`"OWNER#{owner_sub}"`),
which may differ when a candidate is reassigned via `set_owner`. This is intentional
(CND-001 §3 explicitly uses `owner_sub`) and is noted in CND-001 §7 open question 3.

### 3.3 Sub-item SK prefixes written by dependent tickets

CND-002 does not write sub-items, but it must preserve the prefix convention so
dependent tickets can co-exist on the same partition:

- `ATTACHMENT#{attachment_id}` — résumé sub-items (CND-003)
- `ACTIVITY#{inverted_ts}#{activity_id}` — change-history fallback rows (CND-004)

CND-002 `get_candidate` and `list_candidates` query only `sk = "META"` (via
`KeyConditionExpression`) so sub-items are never accidentally returned.

## 4. API / Service Design

### 4.1 Module: `app/services/candidates.py`

All six functions are **synchronous**. Async route handlers in CND-005 call them via
`await asyncio.to_thread(fn, ...)` (established pattern: `google_drive_integration.py:160`).
No `async def` inside this module.

The module begins with a flag guard helper used by every public function:

```python
def _require_enabled() -> None:
    if not S.candidates_enabled:
        raise HTTPException(503, {"code": "candidates_disabled",
                                  "message": "Candidates module is not enabled"})
```

### 4.2 Public function signatures

#### `create_candidate(creator_sub: str, data: CandidateCreateIn) -> dict`

```python
def create_candidate(creator_sub: str, data: CandidateCreateIn) -> dict:
    ...
```

- Calls `_require_enabled()`.
- Normalizes: `email = normalize_email(data.email)`, preserves `email_raw = data.email`.
  `phone = normalize_phone(data.phone)` when `data.phone` is non-empty; omits the field
  otherwise.
- Duplicate short-circuit: calls `find_candidate_by_email(email)` (§4.3 below); if an
  active (non-`deleted_at`) candidate already has the same normalized email, raises
  `HTTPException(409, {"code": "duplicate_candidate", "candidate_id": existing_id})`.
  True fuzzy dedupe and merge are delegated to LED-009 (not implemented here).
- Generates `candidate_id = "cand_" + uuid4().hex[:20]`.
- Applies defaults: `owner_sub = data.owner_sub or creator_sub`,
  `source = data.source or "other"`, `status = "active"`.
- Clamps ATS free-text fields defensively: `key_skills[:4000]`, `current_pay[:500]`,
  `desired_pay[:500]`, `linkedin_url[:500]`, `web_url[:500]` (mirrors the
  `max_length` bounds from CND-001 `CandidateCreateIn`).
- Validates `status` and `source` against `CANDIDATE_STATUSES` / `CANDIDATE_SOURCES`
  (from `app/models.py`); raises `HTTPException(400, ...)` on invalid value.
- Builds the full DDB item with all three GSI pairs; `created_at = updated_at = now_ts()`.
- Calls `T.candidates.put_item(Item=item)`.
- Calls `audit_event("candidate.created", creator_sub, candidate_id=candidate_id, email=email)`.
- Returns the item `dict`.

#### `get_candidate(candidate_id: str) -> Optional[dict]`

```python
def get_candidate(candidate_id: str) -> Optional[dict]:
    ...
```

- Calls `_require_enabled()`.
- `T.candidates.get_item(Key={"pk": f"CANDIDATE#{candidate_id}", "sk": "META"})`.
- Returns `item` or `None` (caller decides 404 vs. silent miss).
- Does **not** filter `deleted_at` here; callers that need to distinguish 404 from 410
  (gone / soft-deleted) do so with `item.get("deleted_at")`.

#### `list_candidates(*, owner_sub: Optional[str] = None, status: Optional[str] = None, source: Optional[str] = None, created_after: Optional[int] = None, cursor: Optional[str] = None, limit: int = 50) -> dict`

```python
def list_candidates(*, owner_sub=None, status=None, source=None,
                    created_after=None, cursor=None, limit=50) -> dict:
    ...
```

- Calls `_require_enabled()`.
- Clamps `limit` to `[1, 200]`.
- **GSI routing** (identical to LED-003 §4.3 logic):
  - `status` provided → query `ByStatus` GSI (`GSI2PK = "STATUS#{status}"`).
  - `source` provided (and `status` not) → query `BySource` GSI
    (`GSI3PK = "SOURCE#{source}"`).
  - Otherwise → query `ByOwner` GSI (`GSI1PK = "OWNER#{owner_sub}"`) when `owner_sub`
    given; fall back to a `Scan` with a `FilterExpression` if neither filter is set (only
    for admin-level list-all use; not exposed in non-admin routes).
- `created_after` is an `N`-typed `KeyConditionExpression` range filter on the GSI sort key
  (`GSI1SK` / `GSI2SK` / `GSI3SK`): `#gsi_sk >= :created_after` (mirrors LED-003 §4.3 step 3
  which uses `GSI?SK >= created_after`). Do NOT use equality (`=`) — that would return only
  exact-timestamp matches, not all candidates created on or after the cutoff.
- **Soft-delete filter**: `FilterExpression = Attr("deleted_at").not_exists()` on every
  query. Because `FilterExpression` does not reduce page size before DDB applies `Limit`
  (CLAUDE.md gotcha), the query loops via `LastEvaluatedKey` until `limit` non-deleted
  items are collected or the index is exhausted.
- Pagination: `ExclusiveStartKey = decode_cursor(cursor)` when cursor provided;
  `encode_cursor(response["LastEvaluatedKey"])` when more pages remain.
- Returns `{"candidates": [item, ...], "cursor": cursor_or_none}`.

#### `update_candidate(candidate_id: str, actor_sub: str, data: CandidateUpdateIn) -> dict`

```python
def update_candidate(candidate_id: str, actor_sub: str,
                     data: CandidateUpdateIn) -> dict:
    ...
```

- Calls `_require_enabled()`.
- Fetches `existing = get_candidate(candidate_id)`.
  - `None` → `HTTPException(404, {"code": "candidate_not_found"})`.
  - `existing.get("deleted_at")` set → `HTTPException(410, {"code": "candidate_deleted"})`.
- Normalizes updated `email` / `phone` when present in `data` (same `normalize_*`
  calls; preserves `email_raw` when email changes).
- Merges `data` fields over `existing`; skips `None`/unset fields from the partial
  `CandidateUpdateIn`.
- **Status/source GSI rewrite**: when `status` or `source` changes, the GSI partition
  keys (`GSI2PK`, `GSI3PK`) must update atomically. Because DDB cannot update a key
  attribute in place, uses a full `T.candidates.put_item(Item=updated_item)` overwrite
  (LED-003 §5.5 technique). The old GSI entry is automatically replaced by DDB since
  `pk`/`sk` are unchanged.
- Sets `updated_at = now_ts()`.
- Calls `T.candidates.put_item(Item=updated_item)` (overwrite).
- Calls `audit_event("candidate.updated", actor_sub, candidate_id=candidate_id, ...)`.
- Fire-and-forget change history: wraps a call to `record_candidate_change` (CND-004
  adapter) in `try/except Exception: pass` — never raises; CND-004 is a soft dependency.
- Returns `updated_item`.

#### `delete_candidate(candidate_id: str, actor_sub: str) -> None`

```python
def delete_candidate(candidate_id: str, actor_sub: str) -> None:
    ...
```

- Calls `_require_enabled()`.
- Fetches `existing = get_candidate(candidate_id)`.
  - `None` → `HTTPException(404, ...)`.
  - Already soft-deleted (`deleted_at` present) → idempotent no-op (returns without error).
- Sets `deleted_at = now_ts()`, `status = "archived"`, `updated_at = now_ts()`.
- Rewrites `GSI2PK = "STATUS#archived"` (status changed) via full `put_item` overwrite.
- Calls `audit_event("candidate.deleted", actor_sub, candidate_id=candidate_id)`.
- Fire-and-forget: `record_candidate_change(change_type="deleted", ...)` wrapped in
  `try/except`.

#### `set_owner(candidate_id: str, new_owner_sub: str, actor_sub: str) -> dict`

```python
def set_owner(candidate_id: str, new_owner_sub: str, actor_sub: str) -> dict:
    ...
```

- Calls `_require_enabled()`.
- Fetches and validates candidate (404 / 410 guards).
- **LED-010 delegation**: attempts
  `from app.services.leads_assignment import assign_owner` (lazy import inside
  `try/except ImportError`). When LED-010 has shipped, it calls
  `assign_owner(entity_type="candidate", entity_id=candidate_id, owner_sub=new_owner_sub, actor_sub=actor_sub)`

- **Shim fallback** (when LED-010 absent): updates `owner_sub`, rewrites
  `GSI1PK = "OWNER#{new_owner_sub}"`, sets `updated_at`, calls `put_item` overwrite,
  emits `audit_event("candidate.owner_changed", actor_sub, ...)`, fires
  `record_candidate_change(change_type="owner_changed", ...)` best-effort.
- Returns the updated item.

## 5. Detailed Behavior & Edge Cases

### 5.1 Email normalization and `email_raw`

`normalize_email` (`normalize.py:60`) lowercases and validates format. `email_raw` stores
the caller-supplied original so the UI can display the case the recruiter typed while
the system deduplicates on the canonical form. Both are always written; updating `email`
always refreshes `email_raw` from the new raw value.

### 5.2 Duplicate short-circuit

`create_candidate` performs a lightweight active-email check via `find_candidate_by_email`
before inserting. If a non-deleted candidate with the same normalized email already exists,
it returns `409` with the existing `candidate_id` so the router can surface a "view
existing record" link in the UI. This is NOT a full fuzzy-match dedupe (no Levenshtein,
no phone/name scoring) — that belongs to LED-009. The check is cheap (one GSI query) and
does not block the create path in a meaningful way.

### 5.3 Status and source validation

`status` is validated against `CANDIDATE_STATUSES` (`{"active", "qualified", "submitted", "interviewing", "placed", "on_hold", "not_in_search", "archived"}`) at the service
layer, raising `HTTPException(400, {"code": "invalid_status"})` on failure.
`source` is validated against `CANDIDATE_SOURCES` similarly. Validation occurs in
both `create_candidate` and `update_candidate`.

### 5.4 GSI rewrite via `put_item` overwrite

DynamoDB does not permit updating a key attribute (e.g., `GSI2PK`) with `update_item`.
When `status` or `source` (and therefore `GSI2PK`/`GSI3PK`) changes, the service
builds the complete updated item and calls `put_item` unconditionally. This replaces the
existing META row in place (same `pk`/`sk`). The old GSI projection is dropped atomically
by DDB. This is the same technique LED-003 §5.5 specifies; the services stay convergent.

### 5.5 `list_candidates` FilterExpression page-loop

Per the CLAUDE.md gotcha: `FilterExpression = attribute_not_exists(deleted_at)` is
applied after DDB reads up to `Limit` items. If many candidates are soft-deleted, a
single DDB page may yield fewer than `limit` live items. The implementation loops with
`ExclusiveStartKey` until either `limit` live items are accumulated or
`LastEvaluatedKey` is absent (last page). The cursor returned to the caller encodes the
`LastEvaluatedKey` of the last DDB page, not the offset into the results list.

### 5.6 `delete_candidate` idempotency

If `deleted_at` is already set, `delete_candidate` returns immediately without a DDB
write or a second audit event. This makes the endpoint safe to retry and prevents
double-audit entries.

### 5.7 `set_owner` and LED-010 shim contract

The shim fallback performs the minimum necessary DDB write (one `put_item` overwrite).
It emits the same `candidate.owner_changed` audit event that LED-010's assign path
would emit. The contract between the shim and LED-010 is explicit: when LED-010 ships
and the lazy import succeeds, the shim is bypassed entirely. LED-010 must accept
`entity_type="candidate"` as a valid entity type; that is a dependency on LED-010, not
something CND-002 enforces.

### 5.8 `find_candidate_by_email` and LED-009

`find_candidate_by_email` is designed to be called by LED-009's merge engine without
any coupling. It takes a pre-normalized email string and returns the first matching
non-deleted META item or `None`. It does not call `_require_enabled()` because LED-009
may invoke it even when the candidates module is partially initializing; callers must
handle `None` gracefully.

### 5.9 ATS free-text field lengths

`key_skills` is capped at 4 000 characters; `current_pay` and `desired_pay` at 500
characters; `linkedin_url` and `web_url` at 500 characters. These limits are already
enforced by `CandidateCreateIn`/`CandidateUpdateIn` Pydantic `max_length` constraints
(CND-001 §4.2/4.3 — `max_length=4000`, `max_length=500`, `max_length=500` respectively),
so FastAPI rejects over-length input with a 422 before the service is called. The service
applies an additional defensive truncation slice (`[:4000]`, `[:500]`, `[:500]`) before
writing to DDB as a belt-and-suspenders guard for callers that bypass the Pydantic layer
(e.g. direct service calls in tests). Excess input is silently truncated at the service
layer, not rejected, to remain compatible with the Pydantic-validated router path.

### 5.10 `updated_at` on every write

All three mutating functions (`create_candidate`, `update_candidate`, `delete_candidate`,
`set_owner`) set `updated_at = now_ts()` before writing. The field is stored as a numeric
DDB attribute (`N`) but is not a GSI sort key, so no `attr_types` declaration is needed
for it beyond `created_at`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 (no `dev_mode` branch)

`candidates.py` contains **zero** references to `S.dev_mode`. All DDB access goes through
`T.candidates` (the `_safe_table`-wired handle in `tables.py`); moto intercepts this
in-process in dev without any code change, real DDB is used in prod — the code path is
identical. There is no mock data path, no inline seeded data, and no special-cased S3
URL (that belongs to CND-003's single `_make_download_url` helper, not to this service).

### 7.2 Idempotency

- **`create_candidate`**: the email short-circuit check (§5.2) prevents exact duplicate
  META rows for the same email. Two concurrent creates with the same email may both pass
  the check and succeed (no conditional-put race guard here); the resulting duplicate is
  handled by LED-009 when it ships. The service is idempotent in the sense that
  re-calling with a distinct `candidate_id` always succeeds.
- **`delete_candidate`**: fully idempotent — second call on a deleted candidate is a
  no-op (§5.6).
- **`update_candidate`**: the full `put_item` overwrite is unconditional; concurrent
  updates on the same candidate use a last-write-wins strategy (DDB does not provide
  optimistic locking here; LED-003 uses the same approach).

### 7.3 Security

- **Normalization at service layer**: `normalize_email` and `normalize_phone` raise
  `HTTPException(400, ...)` on invalid input; the router propagates these to the
  caller without wrapping. Callers never receive un-normalized data.
- **Input length caps**: applied in `create_candidate` and `update_candidate` (§5.9)
  before any DDB write; prevents oversized items from consuming DDB capacity.
- **Authz is router-side**: `candidates.py` is intentionally authz-agnostic (LED-003
  §7.4 principle). Ownership checks (non-owner non-admin cannot delete) live in the
  CND-005 router, not in the service. The service accepts any `actor_sub` it is given.
- **Audit trail**: every mutating operation emits `audit_event` to the `T.alerts`
  DDB table via `alerts.py:644`. Audit rows are DDB-only with no S3/SES branch — fully
  parity-safe.
- **No PII in GSI keys**: GSI partition keys contain `owner_sub` (a `user_sub`
  opaque identifier, not an email or name), `status` (enum), and `source` (enum).
  The normalized email is stored only on the META item body, not projected into an
  exposed GSI key.

## 8. Backward Compatibility & Migration

### 8.1 Additive only

CND-002 is a new file (`app/services/candidates.py`). No existing file is modified;
no existing table schema changes; no existing route is altered. The `candidates` table
is created by CND-001; if `CANDIDATES_ENABLED=0`, the table need not even exist — the
service guards return 503 before touching DDB.

### 8.2 `just restart` creates the table

`scripts/local-ddb-init.py` (modified by CND-001) recreates all tables on `just restart`.
The `candidates` table with its three GSIs and the numeric `attr_types` declaration is
idempotent — if the table already exists from a previous run, `local-ddb-init.py`
skips it silently (the `_ensure_table` helper at `scripts/local-ddb-init.py:2534` checks
`list_tables` and returns early if the table name is already present).

### 8.3 No existing data migration

The `candidates` table starts empty. There are no legacy Candidate records to migrate
from any other table. Lead records in `leads` (when LED-003 ships) are not auto-converted
to Candidates; that conversion, if ever desired, is a separate administrative import
(out of scope for this cluster, related to the CSV import Tier-3 ticket).

### 8.4 LED-010 shim forward compatibility

When LED-010 (`leads_assignment.py`) ships, the `assign_owner` import in `set_owner`
will resolve, and the shim block will be bypassed automatically with no change to
`candidates.py`. The shim is guarded by `try/except ImportError`, so it degrades
gracefully if `app/services/leads_assignment` does not yet exist.

## 10. Open Questions / Assumptions

1. **LED-003 structural details**: LED-003 has not shipped yet. CND-002 mirrors its
   documented design (LED-003 §3.2, §4.3, §5.5, §7.4 in the LED spec files). If LED-003
   deviates from its spec when it ships, the CND-002 pattern comments (citing LED-003 §*)
   should be updated but no functional change is required — the CND code is self-contained.

2. **Concurrent create race for same email**: the email short-circuit check is non-atomic
   (read-then-write). Two concurrent `create_candidate` calls with the same email may
   both pass the check. This is accepted for now; LED-009 is the designated resolution
   path. A conditional `put_item` guard (`attribute_not_exists(pk)`) is already on the
   META row (only one META row per `pk`), so the `candidate_id` values will differ even
   if the emails match — LED-009 can merge them.

3. **`list_candidates` without a filter (admin scan)**: the `Scan` fallback is only
   reachable when `owner_sub`, `status`, and `source` are all absent. The CND-005 router
   restricts this to admin/root users. If the `candidates` table grows large, a full scan
   is expensive; a future ticket should add a `ByCreatedAt` GSI or enforce that at least
   one filter is always required for non-admin callers.

4. **`CandidateUpdateIn` partial model**: assumed to be all-optional, with `None` meaning
   "leave unchanged" (LED-003 §2.3 pattern). If CND-001 uses Pydantic v2
   `model_fields_set` to distinguish "omitted" from "explicitly set to None", the
   `update_candidate` merge logic should check `model_fields_set` rather than testing
   `is None`. This is the safer approach and should be confirmed when CND-001 ships.

5. **Audit volume**: `audit_event` writes to `T.alerts` on every mutating operation.
   At high candidate-creation throughput this could become a DDB hot partition; the
   existing platform absorbs this for all other entities (tickets, billing, etc.) so no
   special handling is proposed here.
