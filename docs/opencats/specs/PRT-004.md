# PRT-004 — Candidate self-apply endpoint → Candidate + pipeline "New/Applied"

**Prefix:** `PRT` · **Area:** ATS / Public Career Portal  
**Type:** Feature · **Priority:** P1 · **Estimate:** 2.5d  
**Source:** `docs/opencats/ATS_CAREER_PORTAL_TICKETS.md` §PRT-004 (lines 141–181); gap: `docs/opencats/OPENCATS_GAP_ANALYSIS.md:82-83` ("Self-apply → Candidate + pipeline: MISSING")

---

## 1. Summary & Goal

PRT-004 delivers the core conversion event of the public career portal: a single, fully unauthenticated `POST /public/careers/jobs/{slug}/apply` endpoint that takes a prospective candidate's name, email, optional phone, and optional cover note, then:

1. Resolves the posting slug to a job order (via the `SLUG#{slug}` row written by JOB-*).
2. Validates the posting is public and open.
3. Applies abuse-mitigation (honeypot silent-drop + per-IP sliding-window rate limit).
4. Normalizes the submitted email.
5. Creates a Candidate record via the CND-* service (`create_candidate`).
6. Adds that candidate to the job order's pipeline at OpenCATS initial ranked status `"100_no_contact"` (No-Contact / Applied) via the PIP-* service (`add_to_pipeline`).
7. Optionally sends a confirmation email to the applicant and a notification email to the configured support address.
8. Emits a best-effort audit event.
9. Returns `CareerApplyOut { application_id, candidate_id, status="received" }`.

The goal is feature parity with OpenCATS's self-apply form (`OPENCATS_GAP_ANALYSIS.md:67`, §D "Self-apply → Candidate + pipeline") using only existing platform primitives — no new infrastructure, no forked logic, no prod/dev code divergence.

This ticket is entirely additive and default-OFF. With `CAREER_PORTAL_ENABLED=0` the endpoint does not exist (HTTP 404) and the platform is byte-for-byte unchanged.

## 3. Data Model

### 3.1 No new DynamoDB tables

PRT-004 stores application records in the existing `CareerPortal` single table (`T.career_portal`, introduced by PRT-001). No new `TableDef` is required. All new row types below are additive sparse rows on the existing `pk`/`sk` key schema.

### 3.2 Application row — `APPLICATION#{application_id}`

One row is written per successful (non-honeypot) apply call.

| Attribute | DDB type | Notes |
|---|---|---|
| `pk` | S | `"APPLICATION#{application_id}"` |
| `sk` | S | `"META"` |
| `application_id` | S | `"app_" + uuid4().hex[:20]` — generated by `create_application` |
| `job_order_id` | S | Resolved from the slug row |
| `slug` | S | Original slug; preserved for idempotency look-ups |
| `candidate_id` | S \| absent | Set to CND-* candidate ID on success; absent if CND-* failed |
| `pipeline_entry_id` | S \| absent | Returned by PIP-*; absent if PIP-* failed |
| `first_name` | S | Submitted value |
| `last_name` | S | Submitted value |
| `email` | S | Normalized email (fallback: raw value) |
| `email_raw` | S | Pre-normalization original — mirrors CND-002 §3.1 `email_raw` pattern |
| `phone` | S \| absent | Submitted phone, present only if provided |
| `cover_note` | S \| absent | Submitted cover note, truncated at 4000 chars |
| `source_ip` | S \| absent | Last-octet-**truncated** IPv4 (returns `"a.b.c"`, not `"a.b.c.0"`) or first-4-group IPv6 via `_ip_prefix(ip)` (`rate_limit.py:84`) |
| `status` | S | `"received"` always at creation; future state changes by PIP-* |
| `created_at` | N | `now_ts()` |
| `GSI1PK` | S | `"JOB#{job_order_id}"` — ByJob index partition key |
| `GSI1SK` | N | `created_at` — ByJob index sort key |

### 3.3 ByJob GSI — applications per job order

A single new GSI on `T.career_portal` lets admin users or future PIP-* tooling enumerate all applications for a given job order, newest first. This GSI is added to the `TableDef` introduced by PRT-001.

```python
# In scripts/local-ddb-init.py, extend the CareerPortal TableDef's gsi= list:
{"index_name": "ByJob", "partition_key": "GSI1PK", "sort_key": "GSI1SK"}
# Add to attr_types:
attr_types={..., "GSI1SK": "N"}   # numeric sort key — MUST be declared (CLAUDE.md gotcha)
```

The `GSI1SK` sort key is numeric (`created_at`). Omitting `attr_types={"GSI1SK": "N"}` causes DynamoDB to store it as String and raises `ValidationException` on integer range queries — the canonical gotcha noted in `CLAUDE.md` and confirmed in `scripts/local-ddb-init.py:53` (`users` table example).

### 3.4 Interaction with CND-* and PIP-* tables

PRT-004 does not write directly to `T.candidates` or the PIP-* pipeline table. All writes to those tables flow through the CND-* and PIP-* service calls. PRT-004 only stores the `candidate_id` and `pipeline_entry_id` returned by those services onto its own Application row for traceability.

## 4. API / Service Design

### 4.1 Pydantic models — appended to `app/models.py`

```python
# ── ATS Career Portal — Self-apply (PRT-004) ─────────────────────────────

class CareerApplyIn(BaseModel):
    first_name: str = Field(..., min_length=1, max_length=120)
    last_name: str = Field(..., min_length=1, max_length=120)
    email: str = Field(..., max_length=254)
    phone: Optional[str] = Field(None, max_length=30)
    cover_note: Optional[str] = Field(None, max_length=4000)
    # Bot-trap: non-empty → silent fake-success, no DDB write (CMP-006 §5.1).
    # No max_length so arbitrarily long bot values still hit honeypot, not 422.
    honeypot: Optional[str] = None

class CareerApplyOut(BaseModel):
    application_id: str
    candidate_id: Optional[str] = None
    status: str  # always "received" on success
```

`honeypot` is intentionally absent from all admin list/read models so it never leaks to the frontend. The field is consumed and discarded in `create_application` before the Application row is written.

### 4.2 Service function — `create_application` in `app/services/career_portal.py`

The function is **synchronous** (no `async def`) following the established pattern for service layer functions (`google_drive_integration.py:160` for the `asyncio.to_thread` call site). It is added to the existing `app/services/career_portal.py` module created by PRT-001, which already contains `_require_enabled()`, `get_portal_config()`, and `set_portal_config()`.

```python
def create_application(
    *,
    slug: str,
    data: CareerApplyIn,
    source_ip: str,
) -> CareerApplyOut:
```

**Step-by-step behavior:**

**Step 1 — Flag guard.** `_require_enabled()` → `HTTPException(404)` when flag off. (Identical to `get_portal_config()` which calls the same guard as its first statement.)

**Step 2 — Honeypot check.** If `data.honeypot` is truthy (non-empty, non-None): return `CareerApplyOut(application_id="bot", status="received")` immediately. No DDB write, no rate-limit increment, no audit. This is deliberately indistinguishable from a real success response to the bot.

**Step 3 — Rate limit.** Anonymize IP: `anon_ip = _ip_prefix(source_ip)` (`rate_limit.py:84-91`). Call `_bucket_limit(f"ip#{anon_ip}", "rl#career_apply", S.career_portal_apply_rate_limit_per_ip_per_hour, 3600)`. If it returns `False`: raise `HTTPException(429, {"code": "rate_limited", "message": "Too many applications; try again later"})`. Local import of `_bucket_limit` avoids a circular dependency (pattern from `app/services/career_portal.py`'s existing local imports).

**Step 4 — Slug resolution.** `slug_row = T.career_portal.get_item(Key={"pk": f"SLUG#{slug}", "sk": "META"}).get("Item")`. If absent → `HTTPException(404, "Job posting not found")`. Extract `job_order_id = slug_row["job_order_id"]`.

**Step 5 — Job order validation.** Lazy-import JOB-* and call `get_job_order_for_apply(job_order_id)`:
```python
try:
    from app.services import job_orders as _job_svc
    job = _job_svc.get_job_order_for_apply(job_order_id)
except Exception:
    job = None
```
If `job` is `None` → `HTTPException(404, "Job posting not available")`. The function `get_job_order_for_apply` returns `None` for absent, non-public, or closed postings so PRT-004 never leaks draft or expired postings.

**Step 6 — Email normalization.** Normalize with try/except fallback:
```python
try:
    email = normalize_email(data.email)
except Exception:
    email = (data.email or "").strip()
email_raw = data.email
```
Bad emails proceed with the raw value; the CND-* service will store it as-is. This prevents blocking legitimate but unusual addresses — identical behavior to CMP-006 §5.3.

**Step 7 — Generate application ID.**
```python
application_id = "app_" + uuid4().hex[:20]
```

**Step 8 — Create Candidate.** Lazy-import CND-* with the same guard pattern:
```python
candidate_id: Optional[str] = None
try:
    from app.services import candidates as _cnd_svc
    from app.models import CandidateCreateIn
    cnd_data = CandidateCreateIn(
        first_name=data.first_name,
        last_name=data.last_name,
        email=email,
        phone=data.phone,
        source="career_portal",
        origin_job_order_id=job_order_id,
    )
    cnd_item = _cnd_svc.create_candidate(
        creator_sub="system_career_portal",
        data=cnd_data,
    )
    candidate_id = cnd_item["candidate_id"]
except Exception:
    pass  # candidate creation failure degrades gracefully
```
When CND-* raises `HTTPException(409)` (duplicate by email), the `except` swallows it and `candidate_id` remains `None`. PRT-004 does **not** surface the 409 to the anonymous applicant — a repeated submit still gets `status="received"`. Caller deduplication is a recruiter-side concern handled by CND-* / LED-009.

**Step 9 — Add to pipeline.** Best-effort, only if `candidate_id` is set:
```python
pipeline_entry_id: Optional[str] = None
if candidate_id:
    try:
        from app.services import pipeline as _pip_svc
        from app.models import PipelineEntryCreateIn as _PipIn
        pip_item = _pip_svc.add_to_pipeline(
            owner_sub="system_career_portal",
            data=_PipIn(
                job_order_id=job_order_id,
                candidate_id=candidate_id,
                status="100_no_contact",
            ),
        )
        # PipelineEntryOut has a pipeline_id field, not entry_id (PIP-001 §4.2)
        pipeline_entry_id = pip_item.pipeline_id
    except Exception:
        pass
```
`"100_no_contact"` is the OpenCATS initial ranked status (PIP-001 `docs/opencats/specs/PIP-001.md:173`; `OPENCATS_GAP_ANALYSIS.md:67` reads "100 No-Contact → 900 Placed"). The function name is `add_to_pipeline`, not `add_candidate_to_pipeline`. The return value is `PipelineEntryOut` with field `pipeline_id`, not a plain dict with `entry_id`. `owner_sub="system_career_portal"` is used because PIP-001 requires an owner. This mirrors the CMP-006 §5.4 list-add pattern: a failure to add to the pipeline must never roll back candidate creation.

**Step 10 — Persist Application row.**
```python
now = now_ts()
item = {
    "pk": f"APPLICATION#{application_id}",
    "sk": "META",
    "application_id": application_id,
    "job_order_id": job_order_id,
    "slug": slug,
    "email": email,
    "email_raw": email_raw,
    "first_name": data.first_name,
    "last_name": data.last_name,
    "source_ip": anon_ip,
    "status": "received",
    "created_at": now,
    "GSI1PK": f"JOB#{job_order_id}",
    "GSI1SK": now,
}
if candidate_id:
    item["candidate_id"] = candidate_id
if pipeline_entry_id:
    item["pipeline_entry_id"] = pipeline_entry_id
if data.phone:
    item["phone"] = data.phone
if data.cover_note:
    item["cover_note"] = (data.cover_note or "")[:4000]
T.career_portal.put_item(Item=item)
```

**Step 11 — Best-effort emails.** Both calls are inside `try/except` and never block the response:
- Applicant confirmation (when `S.career_portal_apply_autoresponder_enabled` is on): `send_alert_email([email], subject, body)` where subject defaults to `S.career_portal_apply_autoresponder_subject` and body is a plain-text confirmation with the job title from `job["title"]`.
- Admin notification (when `S.career_portal_apply_notify_email` is non-empty): `send_alert_email([S.career_portal_apply_notify_email], subject, body)` summarizing the new application.

**Step 12 — Audit event.** Inside `try/except`:
```python
audit_event(
    "career_portal.applied",
    "anonymous",
    application_id=application_id,
    job_order_id=job_order_id,
    candidate_id=candidate_id,
    source_ip=anon_ip,
)
```

**Step 13 — Return.**
```python
return CareerApplyOut(
    application_id=application_id,
    candidate_id=candidate_id,
    status="received",
)
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Unknown / non-public / closed slug → 404 (no candidate created)

The slug resolution (Step 4) and JOB-* validation (Step 5) both happen before any candidate-creation attempt. A 404 in either step terminates the function immediately. No Application row, no Candidate, no Pipeline entry, no audit event is written. This ensures draft or expired postings never attract phantom candidates.

### 5.2 Honeypot filled → 200 fake-success, zero writes

The honeypot check (Step 2) occurs before rate-limit increment, slug resolution, and all DDB writes. A bot that fills the `honeypot` field gets back a syntactically valid `CareerApplyOut` response body with `application_id="bot"` and `status="received"`. The bot cannot distinguish this from a real success. No records are created, no rate-limit token is consumed, and no audit event fires.

### 5.3 Malformed email → apply proceeds with raw value

`normalize_email` raises `HTTPException(400)` on bad input (`normalize.py:60-63`). PRT-004 wraps this in `try/except` and substitutes the raw stripped string. The CND-* service stores `email_raw` alongside the normalized value (CND-002 §3.2). This prevents rejecting addresses that are syntactically unusual but reachable.

### 5.4 CND-* duplicate → 200, existing candidate not re-created

When `create_candidate` raises `HTTPException(409, {"code": "duplicate_candidate", ...})` (CND-002 §4.2), the outer `except Exception` catches it and leaves `candidate_id = None`. The application row is still written (with `candidate_id` absent). This is a deliberate trade-off: the anonymous applicant always sees `status="received"` regardless of whether they have applied before. Deduplication and merging is a recruiter-side operation handled by CND-* / LED-009. A future enhancement could return the existing `candidate_id` if CND-* is updated to expose it in the 409 body and PRT-004 reads it from the exception detail.

### 5.5 PIP-* absent or failing → candidate survives

The pipeline-add (Step 9) is wrapped in `try/except` and only runs when `candidate_id` is set. A failure leaves `pipeline_entry_id = None` on the Application row. The Candidate record in `T.candidates` is not rolled back. A recruiter can manually add the candidate to the pipeline via the PIP-* admin UI. This mirrors CMP-006's list-add best-effort pattern (`docs/suitecrm/specs/CMP-006.md:248-249`).

### 5.6 Rate limit: (N+1)th apply from one IP in one hour → 429

`_bucket_limit` uses `T.sessions` as its DDB backing store (`rate_limit.py:60-79`). The bucket key is `user_sub=f"ip#{anon_ip}"`, `session_id="rl#career_apply"`. The window is 3600 seconds. On the (N+1)th call within the window `_bucket_limit` returns `False` and `create_application` raises `HTTPException(429)`. The 429 fires **after** the honeypot check but **before** slug resolution or candidate creation — so a rate-limited real user receives 429, not 200.

### 5.7 IP anonymization: last octet of IPv4 truncated before storage

`anon_ip = _ip_prefix(source_ip)` (`rate_limit.py:84-91`) returns `"a.b.c"` (three octets; last octet **dropped**, not zeroed to `0`) for IPv4 `"a.b.c.d"` and the first four colon-separated groups for IPv6. The anonymized form is used as both the rate-limit bucket key and the `source_ip` attribute stored on the Application row. The raw IP is never persisted.

### 5.8 `T.sessions` unavailable (e.g. empty `ddb_sessions_table` setting) → rate-limit silently passes

`_bucket_limit` checks `_sessions_table_enabled()` at `rate_limit.py:14-16` and returns `True` (allow) immediately when the sessions table is not configured. This matches the existing MFA send rate-limit behavior and prevents a misconfigured sessions table from permanently blocking applies.

### 5.9 JOB-* module absent at runtime → 404 for all apply requests

When `from app.services import job_orders` raises `ImportError` (JOB-* not yet shipped), the `except Exception` in Step 5 sets `job = None` → `HTTPException(404)`. This is correct because PRT-004 cannot validate that the posting is public/open without JOB-*, and creating candidates for unverifiable postings would be a data integrity problem. Once JOB-* ships, the behavior switches automatically.

### 5.10 Concurrent duplicate applies from the same browser → two Application rows, one Candidate

DynamoDB `put_item` (used for Application rows) is last-write-wins with no condition expression. Two near-simultaneous applies from the same IP with the same email may each create an Application row. Only one Candidate is created because CND-* raises 409 on the second call (email dedupe, CND-002 §4.2). The second Application row will have `candidate_id=None`. This is acceptable for V1; deduplication at the Application level can be added via a DynamoDB conditional expression in a follow-up.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 — no dev_mode branches in PRT-004

The `send_alert_email` function itself branches on `S.dev_mode` at `app/services/alerts.py:462-467` (writes to dev log vs. SES). PRT-004 calls it uniformly; no `if S.dev_mode:` wrapper is added in PRT code. This is the same pattern as LED-005 §7 and KB-011 §7: the mock behavior lives inside the primitive, not the caller.

`presign_upload` at `app/services/filemanager.py:2223-2238` returns `/mock/s3/...` in dev. PRT-004 does not call `presign_upload` (that is PRT-005); but the principle applies — PRT code never checks `S.dev_mode`.

DDB reads/writes, audit events, and rate-limit bucket updates all use the same code path in dev (moto in-process) and prod (real DynamoDB). No conditional logic separates them.

### 7.2 CSRF is not applicable

The apply endpoint carries no `Depends(require_ui_session)`. The CSRF gate in `app/services/sessions.py` fires only when a `ui_session` cookie is present. Anonymous `POST /public/careers/jobs/{slug}/apply` requests never carry that cookie, so CSRF is silently bypassed — this is the expected behavior documented in the PRT cross-cutting constraints (`ATS_CAREER_PORTAL_TICKETS.md:22`).

### 7.3 Idempotency

PRT-004 does not implement strict idempotency at the Application row level. Each POST creates a new `APPLICATION#{id}` row. However, the CND-* duplicate guard (409 on re-submit of the same email) provides natural idempotency at the Candidate level: repeated applies by the same person create multiple Application rows but only one Candidate. Future work (PRT-005 or a dedicated dedup ticket) can add an email-per-job conditional expression on the Application row.

### 7.4 Security properties

- No PII (email, name, IP) is logged at INFO level. Audit events write to `T.alerts` (DDB only).
- `source_ip` stored on Application row is always anonymized via `_ip_prefix`.
- `honeypot` is never persisted (checked and discarded before any write).
- Cover note is truncated to 4000 chars server-side before persistence.
- Rate-limit key uses the anonymized IP, not the raw IP, to prevent fingerprinting.
- No bearer token, API key, or session cookie is required. The endpoint accepts arbitrary unauthenticated requests; the honeypot + rate-limit combination is the only abuse surface.
- The `application_id="bot"` fake-success response leaks no internal state (no real ID, no job details).

## 10. Open Questions / Assumptions

1. **`origin_job_order_id` on `CandidateCreateIn`.** This spec assumes CND-001's `CandidateCreateIn` model includes an optional `origin_job_order_id: Optional[str] = None` field (the posting that generated the candidate). If CND-001 as shipped does not include it, PRT-004 should pass it via a separate `update_candidate` call after creation, or CND-001 should be extended before PRT-004 ships.

2. **PIP-* function name, signature, and return shape — RESOLVED.** Per PIP-001 spec (`docs/opencats/specs/PIP-001.md:168`): function is `add_to_pipeline(owner_sub: str, data: PipelineEntryCreateIn) -> PipelineEntryOut`. The pipeline identifier field on `PipelineEntryOut` is `pipeline_id` (not `entry_id`). Step 9 in §4.2 has been corrected accordingly. `owner_sub="system_career_portal"` is passed because PIP-001 requires an owner sub for DDB key construction.

3. **JOB-* `get_job_order_for_apply` contract.** This spec assumes a purpose-built helper that returns `None` for non-public or closed orders (to avoid PRT needing to understand JOB-*'s status taxonomy). An alternative is for JOB-* to expose `get_job_order(id)` and for PRT-004 to check `item.get("is_public") and item.get("status") in OPEN_STATUSES`. The lazy-import + try/except guard works identically either way; the exact function name is agreed with the JOB-* implementer.

4. **CND-* duplicate handling on re-apply.** The current spec leaves `candidate_id=None` on the Application row when a 409 fires. A richer behavior (fetching the existing candidate ID from the 409 detail and writing it onto the Application row) requires CND-002 to embed the existing ID in the 409 exception detail. This is a design decision for the CND-002 implementer; PRT-004 can adopt it opportunistically.

5. **Application row retention / TTL.** The spec does not add a DynamoDB TTL on Application rows. In high-volume deployments the `CareerPortal` table may accumulate large numbers of application rows. A `ttl` attribute (e.g. 2 years from `created_at`) can be added in a follow-up without a schema migration.
