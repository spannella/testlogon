# RSK-001 — Cross-module skill-tag registry + assignment store

**Type:** Feature · **Priority:** P1 · **Estimate:** 2 days  
**Cluster:** ATS Résumé / Skills (RSK) — Foundation ticket  
**Source:** `docs/opencats/ATS_RESUME_SKILLS_TICKETS.md` §RSK-001 + `docs/opencats/OPENCATS_GAP_ANALYSIS.md` §A, §D

---

## 1. Summary & Goal

OpenCATS replaced résumé parsing with **skill tagging** as the primary mechanism for making candidates and job orders discoverable (gap analysis §Headline; `OPENCATS_GAP_ANALYSIS.md:14`). Both §A (line 48: "Skill tagging + skill-based search — **MISSING**") and §D (line 87: "Cross-module tags / skill tags — **MISSING** — no generic tag store") confirm that no skill or tag store exists anywhere in the codebase.

RSK-001 builds that store as the foundation on which RSK-002 through RSK-006 stand. It delivers two tightly coupled responsibilities:

1. **Skill registry** — a canonical, normalized list of skill names (e.g. `"python"`, `"aws"`, `"project management"`) with a usage counter, so the UI can autocomplete and so variant spellings (e.g. `"Python 3"`, `"python3"`, `"PYTHON"`) collapse to one canonical tag. Normalization follows the style of `app/core/normalize.py` (lowercase + strip): a skill's canonical ID is the slugified name produced by `re.sub(r"[^a-z0-9]+", "-", name).strip("-")`, so `"Project Management"` and `"project  management"` both resolve to `project-management`.

2. **Assignment store** — bidirectional M:N links between a skill ID and an entity (`candidate`, `job_order`), each assignment carrying an optional `weight` (1–5 proficiency for candidates) and/or `required` flag (for job orders). An `entity_type` discriminator makes the store reusable across future modules (contacts, projects) with zero schema change.

RSK-001 is the foundation. RSK-004 (skill-based search) queries its forward index; RSK-005 (CSV import) populates it from a `key_skills` column; RSK-006 (hot-lists + quick-add) triggers its assignment path after résumé extraction.

## 3. Data Model

### 3.1 New `ats_skills` table

This is the **one new DynamoDB table** in the RSK family. All other RSK tickets add rows to the existing `candidates` table. The `ats_skills` table is single-table (`PK=pk`, `SK=sk`), following the identical layout as the `leads` and `crm_kb_articles` tables.

#### 3.1.1 Row types

**Registry META row** — one per canonical skill:

| Attribute | DDB Type | Value |
|---|---|---|
| `pk` | S | `"SKILL#{skill_id}"` |
| `sk` | S | `"META"` |
| `skill_id` | S | slugified name; PK component for convenience |
| `name` | S | canonical display name (`"project management"`) |
| `name_lc` | S | `name.lower()` — GSI1 key |
| `usage_count` | N | integer; incremented on assign, decremented on unassign (floor 0) |
| `created_at` | N | `now_ts()` — non-key numeric; no attr_types entry needed (non-GSI-sort-key) |
| `GSI1PK` | S | `"NAME_PREFIX#{name_lc[:1]}"` — first character bucket for autocomplete |
| `GSI1SK` | S | `name_lc` — string sort key enabling `begins_with` prefix scan |

**Assignment (forward) row** — one per skill↔entity link:

| Attribute | DDB Type | Value |
|---|---|---|
| `pk` | S | `"SKILL#{skill_id}"` |
| `sk` | S | `"ENTITY#{entity_type}#{entity_id}"` |
| `skill_id` | S | |
| `entity_type` | S | `"candidate"` or `"job_order"` (extensible) |
| `entity_id` | S | |
| `weight` | N\|absent | candidate proficiency 1–5 |
| `required` | BOOL\|absent | job order required flag |
| `created_at` | N | `now_ts()` |

**Reverse index row** — one per entity↔skill link (query direction: "list skills on entity Y"):

| Attribute | DDB Type | Value |
|---|---|---|
| `pk` | S | `"ENTITY#{entity_type}#{entity_id}"` |
| `sk` | S | `"SKILL#{skill_id}"` |
| `skill_id` | S | |
| `name` | S | canonical skill name — denormalized for display without additional fetch |
| `weight` | N\|absent | |
| `required` | BOOL\|absent | |
| `created_at` | N | `now_ts()` |

The forward row (`SKILL#…` → `ENTITY#…`) powers "find all entities with skill X" (RSK-004); the reverse row (`ENTITY#…` → `SKILL#…`) powers "list skills on entity Y" (candidate detail view). This dual-row technique avoids both full-table scans and GSI fan-outs in either direction — the same approach used by LED-009 §3 and newsfeed `_write_tag_index`.

#### 3.1.2 `ByName` GSI (GSI1)

| GSI attribute | DDB Type | Notes |
|---|---|---|
| GSI1PK = `"NAME_PREFIX#{name_lc[:1]}"` | S | buckets by first character |
| GSI1SK = `name_lc` | **S** (string) | enables `begins_with(sk, "pyt")` prefix scan |

**IMPORTANT:** GSI1SK is a **String** sort key, NOT numeric. Do NOT add `attr_types={"GSI1SK": "N"}`. The `attr_types` block is only required for numeric sort keys (CLAUDE.md caveat); adding a spurious `"N"` entry for a string key would cause `ValidationException`.

## 4. API / Service Design

### 4.1 Service — `app/services/ats_skills.py` (new file)

All functions are synchronous (called from async routers via direct call; no I/O-bound loops needing `asyncio.to_thread` except where noted). The `T.ats_skills` handle is imported from `app.core.tables`.

```python
# Pure normalization — unit-testable with no DDB dependency
def normalize_skill(name: str) -> tuple[str, str]:
    """Return (skill_id, canonical_name).
    
    canonical_name = name.strip().lower() with internal whitespace collapsed.
    skill_id = re.sub(r"[^a-z0-9]+", "-", canonical_name).strip("-").
    Raises HTTPException(422) if name is empty or exceeds 200 chars after normalization.
    """

# Registry
def upsert_skill(name: str) -> dict:
    """Idempotent registry create-or-increment.
    
    Writes SKILL#{skill_id}/META row. Uses conditional put (attribute_not_exists(pk))
    to create; falls back to a no-op on ConditionalCheckFailedException
    so a concurrent second upsert never double-writes (mirrors newsfeed TAG_STATS counter
    at newsfeed.py:455–459: SET #n = if_not_exists(#n, :z) + :one).
    Returns the registry dict.
    """

def get_skill(skill_id: str) -> dict | None:
    """Get SKILL#{skill_id}/META row or None."""

def search_skills(prefix: str, limit: int = 20) -> list[dict]:
    """Autocomplete by prefix using ByName GSI.
    
    prefix → normalize to lowercase, take first char as GSI1PK bucket.
    Query GSI1PK="NAME_PREFIX#{prefix[0]}" with KeyConditionExpression
    GSI1SK begins_with(name_lc, prefix).  Limit=limit.  No LastEvaluatedKey
    loop needed (autocomplete; first page is sufficient).
    Returns [] for empty/single-char prefix with no scan.
    Rate-limited by caller via _bucket_limit (app/services/rate_limit.py:60).
    """

# Assignment
def assign_skill(
    entity_type: str,
    entity_id: str,
    name: str,
    *,
    weight: int | None = None,
    required: bool | None = None,
    actor_sub: str,
) -> dict:
    """Assign skill to entity.
    
    1. normalize_skill(name) → (skill_id, canonical_name)
    2. upsert_skill(name) — ensures registry row exists
    3. Check for existing forward row; if already present, update weight/required in-place
       (idempotent: does not double-count usage or duplicate reverse rows).
    4. batch_writer(): put forward row SKILL#{skill_id}/ENTITY#{entity_type}#{entity_id}
       AND reverse row ENTITY#{entity_type}#{entity_id}/SKILL#{skill_id}.
    5. Increment usage_count: T.ats_skills.update_item ADD usage_count :one on META row.
    6. audit_event("ats.skill.assigned", actor_sub, entity_type=..., entity_id=..., skill_id=...)
    Returns assignment dict (skill_id, name, entity_type, entity_id, weight, required, created_at).
    """

def unassign_skill(
    entity_type: str,
    entity_id: str,
    skill_id: str,
    actor_sub: str,
) -> None:
    """Remove skill from entity.
    
    1. batch_writer(): delete forward row AND reverse row.
    2. Decrement usage_count with floor 0:
       SET usage_count = if_not_exists(usage_count, :z) - :one
       + ConditionExpression usage_count > :z (catch ConditionalCheckFailed, ignore).
    3. audit_event("ats.skill.unassigned", actor_sub, ...)
    """

def list_entity_skills(entity_type: str, entity_id: str) -> list[dict]:
    """List all skills assigned to an entity, from reverse rows.
    
    query(pk="ENTITY#{entity_type}#{entity_id}", begins_with(sk, "SKILL#"))
    No pagination (typical entities have ≤200 skills; single-page response).
    Returns list of dicts with skill_id, name, weight, required, created_at.
    """

def list_skill_entities(
    skill_id: str,
    entity_type: str | None = None,
    *,
    cursor: str | None = None,
    limit: int = 50,
) -> dict:
    """List entities assigned a given skill, from forward rows.
    
    query(pk="SKILL#{skill_id}", begins_with(sk, "ENTITY#{entity_type}#" if entity_type else "ENTITY#"))
    Loop via LastEvaluatedKey (CLAUDE.md "FilterExpression doesn't reduce page size"):
    when entity_type is given, the begins_with on sk already filters at DDB level, so no
    client-side FilterExpression is needed — but pages must still be looped to exhaust results.
    Paginated with encode_cursor/decode_cursor (app/core/cursor.py:94).
    Returns {"items": [...], "cursor": str|None}.
    """

# Bulk helpers consumed by CND-* / JOB-* detail editors
def set_entity_skills(
    entity_type: str,
    entity_id: str,
    names: list[str],
    actor_sub: str,
) -> dict:
    """Bulk replace: diff current vs desired, assign/unassign deltas.
    
    1. current = {s["skill_id"] for s in list_entity_skills(entity_type, entity_id)}
    2. desired = {normalize_skill(n)[0] for n in names}
    3. to_add = desired - current → assign_skill for each
    4. to_remove = current - desired → unassign_skill for each
    Returns {"assigned": int, "unassigned": int}.
    """
```

Convenience wrappers at module level:

```python
def set_candidate_skills(candidate_id: str, names: list[str], actor_sub: str) -> dict:
    return set_entity_skills("candidate", candidate_id, names, actor_sub)

def set_job_order_skills(job_order_id: str, names: list[str], actor_sub: str) -> dict:
    return set_entity_skills("job_order", job_order_id, names, actor_sub)
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Normalization rules

`normalize_skill("Project Management")` → `("project-management", "project management")`.  
`normalize_skill("project  management")` → `("project-management", "project management")` (collapsed internal whitespace).  
`normalize_skill("python3")` → `("python3", "python3")` (alphanumeric; no hyphens inserted).  
`normalize_skill("C++")` → `("c", "c")` — non-alphanumeric characters other than existing hyphens are collapsed. NOTE: short single-character results (< 2 chars after stripping) must raise `HTTPException(422, "Skill name too short after normalization")` to prevent degenerate skill IDs.  
`normalize_skill("")` or `normalize_skill("   ")` → `HTTPException(422, "Skill name required")`.  
Maximum canonical length is 200 characters; truncation is not applied — names exceeding 200 chars after normalization raise 422.

### 5.2 Idempotency of `assign_skill`

Re-assigning the same skill to the same entity (same `entity_type`, `entity_id`, `name`) is idempotent:
- The forward row `SKILL#…/ENTITY#…` is overwritten via `put_item` (last-write-wins for `weight`/`required`).
- The reverse row `ENTITY#…/SKILL#…` is overwritten similarly.
- `usage_count` is **not** re-incremented on re-assign. The check uses a `get_item` on the forward row before the batch_writer: if the row exists, skip the `update_item ADD usage_count :one` step.
- No duplicate reverse rows are written (put_item is idempotent in DynamoDB).

### 5.3 `usage_count` floor at 0

`unassign_skill` decrements with a conditional: `SET usage_count = if_not_exists(usage_count, :z) - :one` with `ConditionExpression="usage_count > :z"`. If the condition fails (`ConditionalCheckFailedException`), it is swallowed silently — the counter is already at 0 or the META row is absent. This prevents negative counts and mirrors the `member_count` floor pattern in RSK-006.

### 5.4 `list_skill_entities` pagination

The forward rows for a popular skill (`"python"`) may span many DynamoDB pages. The query uses `begins_with(sk, "ENTITY#candidate#")` when `entity_type="candidate"` is given, which is a KeyConditionExpression (not a FilterExpression) — DynamoDB evaluates it server-side and every page is dense. However, results must still be looped via `LastEvaluatedKey` because DynamoDB limits each response to 1 MB. The caller passes a signed cursor produced by `encode_cursor` (`app/core/cursor.py:94`); the service decodes it via `decode_cursor` to obtain `ExclusiveStartKey`.

### 5.5 `entity_type` validation

Valid values at the router layer: `"candidate"` and `"job_order"`. Any other value raises `HTTPException(422, "Invalid entity_type")`. At the service layer, no hard constraint is enforced (to allow future extension to `"contact"`, `"project"`, etc.), but the router is the public boundary. RSK-005 (CSV import) calls the service directly with `"candidate"` so it never touches the router's validation.

### 5.6 `search_skills` with empty or very short prefix

- `prefix=""` or `prefix` after strip is empty → return `[]` immediately (no DDB call).
- Single character `prefix="p"` is valid (GSI1PK bucket = `"NAME_PREFIX#p"`, no `begins_with` filter needed — return all skills starting with `p` up to `limit`).
- `prefix` with no matches returns `[]` (empty GSI query result is not an error).

### 5.7 Concurrent upsert / race condition on registry create

Two concurrent `assign_skill` calls for `"python"` may both attempt to put the META row. `upsert_skill` uses `ConditionExpression="attribute_not_exists(pk)"` on the initial `put_item`. The "loser" of the race catches `ConditionalCheckFailedException` and proceeds (the registry row already exists — correct outcome). No double-counting because both paths would each attempt `ADD usage_count :one` on the META row — DynamoDB's atomic ADD makes this naturally safe.

### 5.8 Deletion of entities

When a candidate or job order is deleted (soft-deleted by CND-002 or JOB-002), its skill assignments are **not** automatically cleaned up in RSK-001. The reverse rows remain on the `ats_skills` table as orphans. Reasons: (1) soft deletes do not remove DDB rows; (2) bulk-deleting reverse rows requires a full query + batch-delete that is disproportionate for a soft-delete operation. `list_entity_skills` on a deleted entity simply returns stale data; callers are expected to check the candidate/job-order status first. Hard-delete cleanup is a future enhancement (document in Open Questions §10).

### 5.9 Weight vs. required mutual exclusivity

`weight` is meaningful only for `entity_type="candidate"` (proficiency level 1–5). `required` is meaningful only for `entity_type="job_order"`. The schema allows both to be stored on any entity type (no hard enforcement at the service layer), but the router validates via `SkillAssignmentIn.weight` `ge=1, le=5`. The Pydantic model does not cross-validate `entity_type` vs `weight`/`required` — that coupling would break future extensibility. Clients should only send relevant fields.

With `S.ats_recruiting_enabled = False` OR `S.ats_skills_enabled = False`:
- All four router endpoints return HTTP 404 (the `_check_flag()` guard fires before any DDB call).
- `assign_skill`, `unassign_skill`, `list_entity_skills`, `list_skill_entities`, `search_skills` are importable by other modules (RSK-004, RSK-005, RSK-006) but are guarded at those callers' routers — the service functions themselves do not check the flag (following the pattern: flag checks at the router boundary, not deep in service logic).
- `set_candidate_skills` / `set_job_order_skills` are called from CND-*/JOB-* detail handlers, which are separately gated by their own flags. RSK-001 service functions do not double-check.
- No `ats_skills` table rows are read or written.
- The platform is byte-for-byte unchanged from the perspective of all existing routes and tables.

### 6.3 Sub-flag rationale

`ats_skills_enabled` (default ON when parent is ON) allows ops to disable skill tagging specifically while keeping the rest of the ATS module running. This matches the pattern of `messaging_translation_enabled` (CLAUDE.md MVA-001: default ON) and `messaging_transcription_enabled` (default OFF) — fine-grained sub-gates that avoid a monolithic all-or-nothing rollout.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

Every DDB read/write goes through `T.ats_skills` (the `_FloatSafeTable`-wrapped handle from `app/core/tables.py:65`). There is **no `if S.dev_mode:` branch** anywhere in RSK-001. The same code path runs against DynamoDB Local (port 8001 in dev) and real AWS DynamoDB in prod. This is the SECOPS-007 guarantee already in place for all tables in the codebase (CLAUDE.md §SECOPS-007).

### 7.2 No S3 or Cognito dependencies

RSK-001 is pure DynamoDB. No S3 reads/writes, no Cognito calls. `app/core/aws_clients.s3_client()` (line 114) is not used here; it enters the stack at RSK-002.

### 7.3 Authorization

All four endpoints require `require_ui_session` (cookie auth + CSRF on non-GET). There is no public (no-auth) endpoint in RSK-001 — skill assignments are internal recruiter data. The autocomplete `GET /search` endpoint requires a valid session cookie (unlike KB-011's public portal, which RSK-001 does not replicate).

No record-level ownership check is enforced at the RSK-001 layer: any authenticated user can read or mutate any entity's skills. Fine-grained per-entity ACL is deferred to CND-*/JOB-* (which will gate the candidate/job-order entities via `require_admin_session` or ownership checks). RSK-001 trusts the entity-level gating of its callers.

### 7.4 Audit trail

Every `assign_skill` and `unassign_skill` call emits `audit_event` to `T.alerts` via `app/services/alerts.py:644`. The events carry `entity_type`, `entity_id`, `skill_id`, and `actor_sub` so the audit log provides a full history of skill changes per entity.

### 7.5 Idempotency summary

| Operation | Idempotent? | Mechanism |
|---|---|---|
| `upsert_skill(name)` | Yes | `ConditionalCheckFailed` on second create → no-op |
| `assign_skill(...)` | Yes | `get_item` check before usage_count increment; `put_item` overwrites both rows |
| `unassign_skill(...)` | Yes | DDB `delete_item` on nonexistent key is a no-op; counter floor via condition |
| `set_entity_skills(...)` | Yes | Diff computes delta; re-calling with same list produces empty delta |

## 10. Open Questions / Assumptions

1. **Entity deletion cleanup** — RSK-001 leaves reverse rows orphaned when an entity is soft-deleted (§5.8). Options: (a) accept stale rows (current design); (b) `list_entity_skills` cross-checks entity existence before returning (adds a `T.candidates` get_item per call); (c) hard-delete cleanup in CND-002's `delete_candidate`. **Assumption:** option (a) for now; document as a known limitation.

2. **Skill name max length** — current cap is 200 chars after normalization. Is there a use case for longer skill descriptions? **Assumption:** No; recruit skill tags are concise labels, not descriptions.

3. **Case of `"C++"` and other symbol-heavy tech names** — `normalize_skill("C++")` degenerates to `"c"` (single char, rejected). Mitigation: pre-alias common symbol names before normalization (`"c++" → "cplusplus"`, `"c#" → "csharp"`) in a small lookup dict. **Assumption:** ship without the alias table; document as a follow-up.

4. **`entity_type` closed set enforcement** — should the service layer reject unknown `entity_type` values, or remain open for forward compatibility? **Assumption:** open at the service layer; closed (`"candidate"` or `"job_order"` only) at the router layer.

5. **Skill merge / rename** — if `"python 3"` and `"python"` normalize to different IDs, the registry has two distinct skills. A skill-merge admin endpoint (merge two skill IDs) is not in scope for RSK-001. **Assumption:** recruiters are expected to use autocomplete (which shows normalized names) to avoid variants.

6. **`usage_count` accuracy under concurrent deletes** — the floor-at-0 mechanism prevents negative counts but does not guarantee accuracy under concurrent assign+unassign on the same skill. For a usage counter this is acceptable (display only; not transactional). **Assumption:** eventual consistency is fine for `usage_count`.
