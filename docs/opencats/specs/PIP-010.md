# PIP-010 — Tests — hermetic pytest suite + E2E spec

## 1. Summary & Goal

PIP-010 consolidates and completes the test coverage for the entire **PIP** cluster — the candidate↔job-order pipeline (the M:N junction that turns testlogon into an ATS). The PIP set spans nine implementation tickets (PIP-001 junction table + master flag, PIP-002 ranked status config, PIP-003 status-change + logging, PIP-004 rating, PIP-005 submit-to-client, PIP-006 placement, PIP-007 bulk add/remove, PIP-008 router, PIP-009 frontend Kanban). Per the cross-cutting test constraint (`ATS_PIPELINE_TICKETS.md` cross-cutting #8), each backend ticket ships its own hermetic pytest authored alongside the feature. **This ticket is the guarantee** that:

1. The full per-ticket pytest suite (`tests/test_pip_001_*.py` … `tests/test_pip_008_*.py`) exists, is **hermetic and fully offline** (moto in-memory DynamoDB, frozen `T`/`S` patched via `object.__setattr__`, route handlers called **directly** — no `TestClient` — external collaborators `audit_event`, `record_crm_activity`, the email send fn, `s3_client`, and the JOB-*/CND-* resolvers patched at source), and passes green under `just test` with **no AWS/SES/S3/network access**.
2. A single shared end-to-end spec `frontend/e2e/ats-pipeline.spec.ts` exists, covers every PIP endpoint plus the Kanban/submit/placement/bulk-add UI flows, and passes under `just e2e` with the flag on — including a dedicated **flag-off** section asserting the sidebar entry is absent and the data routes return 503.

The goal is **net coverage of every PIP service function and every PIP UI flow**, with the test-isolation discipline already proven in `tests/test_gap_*.py` and modelled on the OPP-003 §9 / OPP-004 §9 fixtures (the closest already-specced analogue). PIP-010 adds **no production behavior** — it is a testing ticket; everything it exercises is itself additive and flag-gated default-off.

The deliverable is concrete: eight backend test modules + one E2E spec, an inventory (§9) mapping each assertion to the PIP acceptance criterion it discharges, and a guarantee that the suite is contamination-free (each test creates its own moto table and restores the frozen singletons on teardown).

## 2. Context & Current State

The repository already has a mature, repeatable hermetic-test convention. The PIP suite reuses it verbatim — no new infrastructure is invented.

**Hermetic pytest convention (the dominant pattern):**
- The overwhelming majority of backend tests use moto: `from moto import mock_aws` appears in **73** of the `tests/test_gap_*.py` modules (verified by `grep -rh "from moto import" tests/test_gap_*.py | sort | uniq -c`). This is the canonical import; a couple of legacy modules alias `mock_dynamodb as mock_aws`, which PIP avoids — PIP uses `mock_aws` directly.
- Frozen singletons are mutated with `object.__setattr__`. Both the `Settings` dataclass (`S`) and the table registry (`T`) are frozen; tests flip flags and rebind table handles through `object.__setattr__` and restore them on teardown. Representative example: `tests/test_gap_0223_0224_ec2_host_inventory.py:24` documents *"`Settings` is frozen -> flags flipped with `object.__setattr__`"* and uses it for `ec2_mock_enabled`, `security_groups_enabled`, etc. (`:110-121`).
- `TestClient` is broken in this repo (CLAUDE.md "broken per CLAUDE.md"); tests call **route handler coroutines directly** with a hand-built `ctx` dict (the `require_ui_session` return shape: `{"user_sub", "role", "admin_profile", …}`), driving async handlers on a fresh event loop where needed (the SSH/KYC tests in CLAUDE.md show `asyncio.new_event_loop()`).
- External collaborators are patched **at the source module** (where the symbol is *used*, i.e. the service module's namespace), not at the definition site. CLAUDE.md repeats this across many gotchas (e.g. KYC tests patch `_emit_kyc_event_safe` on the module, the partner-API test patches the S3 client to an in-memory `_FakeS3`).

from app.core.tables import T, _FloatSafeTable
from app.core.settings import S

@pytest.fixture(autouse=True)

            TableName="ats_pipeline",

                       {"AttributeName": "sk", "KeyType": "RANGE"}],
            AttributeDefinitions=[{"AttributeName": "pk", "AttributeType": "S"},

            BillingMode="PAY_PER_REQUEST",

## 5. Detailed Behavior & Edge Cases

The assertions each module makes (these are the acceptance gates rolled up from PIP-001…008's own ACs):

**PIP-001 (junction):**
- `add_to_pipeline` writes `PIPE#{job}#CAND#{cand}`, returns `PipelineEntryOut` with `status="100_no_contact"`, `rating=0`.
- **dup-409**: same job+candidate under same owner twice → 2nd raises `HTTPException(409, code="pipeline_entry_exists")` (the `ConditionExpression=Attr("sk").not_exists()` guard).
- **foreign-404**: `get_job_order`/`get_candidate` stub returns `None` for a foreign id → `HTTPException(404)` before any write.
- `list_pipeline_for_job`/`list_pipeline_for_candidate` return all entries under the owner partition, loop-paginated (`LastEvaluatedKey`); empty list when none.
- `remove_from_pipeline` deletes the row → subsequent list empty; removing an absent entry → 404 `pipeline_entry_not_found`.
- Each add/remove → `audit_event("pipeline.candidate_added"/"…removed", …)` (assert via captured mock).
- **flag-off-503**: with `S.ats_pipeline_enabled=False`, each function raises `HTTPException(503, code="ats_pipeline_disabled")`.

**PIP-002 (status-config):**
- `get_status_config()` with **no row** → 9 default statuses, correct `rank`/`order`, `is_submitted` on `400_submitted`, `is_placed` on `900_placed`, `is_terminal` on 700/800/900.
- `set_status_config(admin_sub, data)` writes `PIPELINE_STATUS_CONFIG#META`, round-trips (full replacement, last-write-wins, idempotent).
- Validation rejections → 400 `invalid_status_config`: **zero `is_placed`**, **two `is_placed`**, **two `is_submitted`** (at-most-one), duplicate `status_key`, <1 or >20 statuses, non-distinct ranks.
- `set_status_config` → `audit_event("ats_status_config.updated", admin_sub, None, status_count=…, submitted_key=…, placed_key=…)`.
- **status-config auth**: handler called with `ctx role=USER` → 403 `admin_role_required`; `role=ADMIN`/`ROOT` → 200 (the `normalize_role(...) in {ADMIN, ROOT}` gate). Flag-off → 503.

**PIP-003 (status change):**
- `change_status` `100_no_contact → 300_qualifying` updates `status` + `status_rank` (via `resolve_status_rank`), returns updated entry.
- `new_status` not in live config → 400 `invalid_status`; foreign entry → 404; **same-status → no-op** (no `update_item` mutation of `status`, **no audit/timeline write**).
- One `pipeline.status_changed` audit with `from_status`/`to_status`/`from_rank`/`to_rank`.
- **Dual timeline write**: `record_crm_activity` called **twice** (candidate entity + job-order entity) — assert the mock captured 2 calls. A raised exception inside `record_crm_activity` is **swallowed** (does not propagate; the transition still succeeds).

**PIP-004 (rating):**
- `set_rating(...,4)` persists `rating=4`; `rating=0` clears it.
- `rating=6`/`-1` → 422 at the Pydantic boundary (`Field(ge=0, le=5)`), 400 `invalid_rating` if forced past the model into the service. Foreign → 404; flag-off → 503.
- `pipeline.rated` audit carries `previous_rating`.

**PIP-005 (submit-to-client):**
- `resume_attachment=True`: fetches the primary résumé from the `_FakeS3`, sends a multipart email carrying it (assert the dev-email-log entry contains the attachment marker + filename), advances status to the `is_submitted` key (`400_submitted`), logs the submission on **both** timelines.
- `resume_attachment=False`: sends plain `send_alert_email` (no attachment), still advances + logs.
- No primary résumé + `resume_attachment=True` → 400 `no_primary_resume` (no email, no status change).
- Foreign → 404; flag-off → 503.
- **send-failure-non-fatal**: email fn raises → swallowed/logged, request does **not** 500; the status advance only runs on send success (matching ACT-003's best-effort contract).
- `pipeline.submitted_to_client` audit + `record_crm_activity` ×2.

**PIP-006 (placement):**
- `record_placement` advances status to `900_placed`, writes `…#PLACEMENT` sub-row with `fee_cents`/`start_date`, returns `PlacementOut`.
- **dup-409**: 2nd `record_placement` on the same entry → 409 `placement_exists` (status stays Placed).
- `fee_cents < 0` → 422; foreign → 404; flag-off → 503.
- `pipeline.placed` audit + `record_crm_activity` ×2; `get_placement` reads it back.

**PIP-007 (bulk):**
- **bulk mixed**: 3 valid + 1 already-in-pipeline + 1 foreign candidate → `added=[3 ids]`, `skipped=[{already_in_pipeline}, {not_found}]`, HTTP 200 (partial success, no all-or-nothing txn).
- Foreign `job_order_id` → 404 **before** the loop (fail-fast, single `get_job_order`).
- `bulk_remove_from_pipeline` removes present entries, reports absent ones as `skipped`.
- `candidate_ids` empty → 422; >100 → 422 (`max_length`).
- Summary `pipeline.bulk_added`/`bulk_removed` audit (plus the per-row audits from the inner `add`/`remove`). Flag-off → 503.

**PIP-008 (router):**
- All data handlers 503 when flag off; `feature_status()` returns `{"enabled": False}` without 503.
- `PUT /ui/admin/ats/pipeline/statuses` USER ctx → 403, ADMIN/ROOT → 200.
- **Route-order sanity**: literal segments (`statuses`, `bulk-add`, `bulk-remove`, `by-job`, `by-candidate`, `feature-status`) declared before dynamic `/{…_id}` so they aren't shadowed (the CLAUDE.md `/schedules`-before-`/{export_id}` gotcha) — asserted by calling each handler and confirming it routes to the right service.
- CSRF on non-GET cookie requests is enforced by `require_ui_session` (exercised in E2E, not the direct-call unit tests which bypass the dependency).

**E2E edge cases** mirror the above over HTTP: default-9-stage `GET`, root `PUT` replaces / alice `PUT` → 403 / invalid config → 400; add → dup-409; list by-job/by-candidate; `PATCH …/status` + `PUT …/rating`; foreign → 404; bulk-add mixed; submit advances to Submitted (assert dev-email-log + status moved); placement advances to Placed + dup-409; Kanban columns-from-API, drag emits `PATCH …/status`, rollback toast on a blocked move; flag-off → no sidebar entry + data routes 503 + `feature-status {enabled:false}`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity:** PIP-010 asserts the *absence* of `if S.dev_mode` business-logic branches in the code under test. The only legitimate env-fork is the delivery substrate already abstracted by the reused primitives: `send_alert_email` / the ACT-003 raw-SES path log to `S.dev_email_log` in dev and `ses.send_raw_email` in prod; `s3_client()` (`app/core/aws_clients.py:114`) hits in-process moto in dev and real S3 in prod. The tests run the **same DDB code path** that prod runs — they bind a moto table to the production `T.ats_pipeline` handle through the production `_FloatSafeTable` proxy (not a bespoke dict fake), so a parity regression (e.g. a Decimal/float coercion bug) surfaces in the test. The PIP-005 test asserts the email/S3 fork is *only* in the substrate, by patching `s3_client` + the email fn and confirming the business logic (status advance, dual timeline, audit) is identical regardless.

**Idempotency:** the tests pin every idempotency contract — `set_status_config` full-replacement last-write-wins (PIP-002 round-trip), `change_status` same-status no-op (PIP-003), submit-to-client re-submit re-sends+re-logs while the status advance is idempotent (PIP-005), placement second-call → 409 (PIP-006), bulk partial-success with per-row independence (PIP-007).

**Security:** ownership-by-key authz is asserted with **foreign-404** cases in every module (an attacker passing another user's id gets a keyed-lookup 404, never a 403 leak — OPP-004 §5 structural authz). The single role-gated surface (`PUT /ui/admin/ats/pipeline/statuses`) is asserted both ways (USER→403, ADMIN/ROOT→200) in PIP-002/PIP-008 via `normalize_role`. CSRF enforcement on non-GET cookie requests is exercised in the E2E layer (where `require_ui_session` actually runs) by sending `x-csrf-token: sessions[id].csrf_token`. The suite never touches real AWS/SES/S3/network — hermetic by construction (moto + patched collaborators + stubbed resolvers).

## 8. Backward Compatibility & Migration

PIP-010 is **purely additive and zero-risk to existing behavior**: it adds test modules and one E2E spec, no production code. With `ATS_PIPELINE_ENABLED=false` (the default), none of the PIP routes are mounted and no DDB writes occur, so the existing suite and every existing code path are byte-for-byte unchanged. No migration is required: the `ats_pipeline` table is created fresh by `scripts/local-ddb-init.py` (PIP-001) and recreated on `just restart`; the tests create their own moto tables and never touch persistent local DDB (port 8001) or production data. The additive `pipeline_entries: List[PipelineEntryOut] = Field(default_factory=list)` field on the job-order/candidate `…Out` models (PIP-001) defaults to `[]` and is wire-compatible — the tests assert it defaults empty when `include_pipeline` is not passed, so pre-existing API consumers are unaffected. No GSI backfill is needed (PIP-001 adds no GSI; any later numeric-sort GSI is a separate ticket with its own `attr_types` migration note).
