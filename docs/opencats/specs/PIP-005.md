# PIP-005 — Submit candidate to client action

**Ticket type:** Feature
**Priority:** P1
**Estimate:** 3 days
**Master gate:** `S.ats_pipeline_enabled` (`ATS_PIPELINE_ENABLED`, default `false`) — introduced in PIP-001
**Depends on:** PIP-001 (junction table + flag), PIP-002 (status config + `is_submitted` key), PIP-003 (`change_status`); CND-003 (`get_primary_resume_item` — convenience function that must be added to CND-003; see §3.2 note); ACT-003 (multipart SES email pattern); ACT-009 (`record_crm_activity`, soft via lazy import)

---

## 1. Summary & Goal

PIP-005 delivers the **signature ATS recruiter action**: send a candidate's résumé to the
hiring-company contact by email, advance the pipeline status to the configured `is_submitted`
stage, and write dual activity-timeline rows — all as a single atomic-from-the-recruiter's-POV
operation.

This is the action OpenCATS calls "Submit to Client". In the gap analysis
(`docs/opencats/OPENCATS_GAP_ANALYSIS.md:70`, §C) it is classified **MISSING**: "Submit to
client" action (email+resume, advance status, log)". PIP-005 fills the gap by composing
three already-specified primitives — the ACT-003 multipart-SES email path, the PIP-003
status-change operation, and the ACT-009 timeline write — and introducing a single new
service function and one HTTP endpoint.

The feature is entirely additive and gated behind `S.ats_pipeline_enabled`. With the flag
off, the endpoint is unreachable, no DDB writes occur, and every byte of existing platform
behavior is unchanged.

## 3. Data Model

PIP-005 introduces **no new DynamoDB tables, GSIs, or item types**. It operates entirely
on the `ats_pipeline` table (PIP-001) and reads from the `candidates` table (CND-001/003)
and S3.

### 3.1 Existing table: `ats_pipeline` (PIP-001)

PIP-005 reads and conditionally updates the pipeline-entry row. No structural change.

| PK | SK | Purpose |
|---|---|---|
| `USER#{owner_sub}` | `PIPE#{job_order_id}#CAND#{candidate_id}` | Pipeline entry (read by `get_pipeline_entry`, updated by `change_status` via PIP-003) |
| `PIPELINE_STATUS_CONFIG` | `META` | Status config (read by `get_status_config` via PIP-002) |

The `status` and `status_rank` fields on the pipeline entry are updated by the PIP-003
`change_status` call that PIP-005 delegates to. PIP-005 does not call `update_item`
directly.

### 3.2 Existing table: `candidates` (CND-001/003)

PIP-005 reads from this table but does not write to it.

| PK | SK | Purpose |
|---|---|---|
| `CANDIDATE#{candidate_id}` | `META` | Candidate record (contains `primary_resume_id` pointer) |
| `CANDIDATE#{candidate_id}` | `ATTACHMENT#{attachment_id}` | Résumé attachment sub-item (contains `s3_key`, `s3_bucket`, `filename`, `content_type`) |

`get_primary_resume_item(candidate_id)` from CND-003 does a `get_item` on the META row
for `primary_resume_id`, then a second `get_item` on the `ATTACHMENT#{id}` sub-row.

### 3.3 S3 (résumé bytes)

S3 object key format (from CND-003 §4.4): `{S.candidate_resume_s3_prefix}{candidate_id}/{attachment_id}/{safe_filename}`.
PIP-005 reads bytes via `s3_client().get_object(Bucket=item["s3_bucket"], Key=item["s3_key"])["Body"].read()`.

## 4. API / Service Design

### 4.1 New helper: `send_email_with_attachment` (`app/services/alerts.py`)

```python
def send_email_with_attachment(
    to_emails: List[str],
    subject: str,
    body_text: str,
    attachment_bytes: bytes,
    filename: str,
    mime_type: str = "application/octet-stream",
) -> None:
```

This is the generalisation of the ACT-003 `send_calendar_invite_email` multipart-SES pattern
(`docs/suitecrm/specs/ACT-003.md §4.2`), expanded to support arbitrary binary attachments.

**Dev mode** (`S.dev_mode`): writes a structured entry to `S.dev_email_log`
(`app/core/settings.py:301`) via `_write_dev_log` (`alerts.py:449`):

```
[{ts}] RESUME_SUBMIT TO={addr}
  Subject: {subject}
  Body: {body_text}
  Attachment: {filename} ({len(attachment_bytes)} bytes, {mime_type})
```

**Production** (`not S.dev_mode`): builds a raw MIME message using stdlib only
(`email.mime.multipart.MIMEMultipart`, `email.mime.text.MIMEText`,
`email.mime.base.MIMEBase`, `email.encoders`):

- Part 1: `text/plain` — the body text.
- Part 2: `application/octet-stream` (or the passed `mime_type`) with
  `Content-Disposition: attachment; filename="{filename}"` — the résumé bytes,
  base64-encoded via `email.encoders.encode_base64`.

Sends one `ses.send_raw_email` call per recipient (not bulk), identical to the ACT-003
per-recipient pattern. Guards: `if not S.alerts_email_enabled or not S.alerts_from_email:
return` (same guards as `send_alert_email:469`). On any boto3 exception: log at WARNING,
increment `EMAIL_FAILED` (`app/metrics.py`, pattern from `alerts.py:482`), never raise.

### 4.2 New service function: `submit_to_client` (`app/services/ats_pipeline.py`)

```python
def submit_to_client(
    owner_sub: str,
    job_order_id: str,
    candidate_id: str,
    data: SubmitToClientIn,
) -> SubmitToClientOut:
```

**Step-by-step execution:**

1. `_require_flag()` — raises 503 `ats_pipeline_disabled` when `S.ats_pipeline_enabled` is
   `False`.

2. `entry = get_pipeline_entry(owner_sub, job_order_id, candidate_id)` — ownership gate.
   Raises 404 `pipeline_entry_not_found` if the entry does not exist or belongs to another
   owner. (`get_pipeline_entry` is delivered by PIP-001.)

3. **Resolve candidate name and job-order title** for the email body:

   ```python
   try:
       from app.services.candidates import get_candidate
       cand = get_candidate(candidate_id)   # CND-002: single arg, returns Optional[dict]
       candidate_name = f"{(cand or {}).get('first_name', '')} {(cand or {}).get('last_name', '')}".strip() or candidate_id
   except Exception:
       candidate_name = candidate_id

   try:
       from app.services.job_orders import get_job_order   # JOB-002: module is job_orders.py
       job = get_job_order(job_order_id)   # JOB-002: single arg, returns JobOrderOut (Pydantic model)
       job_title = job.title               # attribute access, not .get() — JobOrderOut is a Pydantic model
   except Exception:
       job_title = job_order_id
   ```

   Both imports are lazy (`try/except`) per the cross-cutting ordering-independence pattern
   (`ATS_PIPELINE_TICKETS.md:19`, ACT-009 §2.3). A missing or disabled JOB-*/CND-* module
   never blocks the submission — names fall back to the opaque IDs.

   **Corrections from verification:** (a) `get_candidate` takes only `candidate_id` — no
   `owner_sub` argument (CND-002 §4.1 signature). (b) The job-orders service module is
   `app/services/job_orders.py` (JOB-002 §4 header), not `ats_job_orders`. (c) `get_job_order`
   takes only `job_id` — no `owner_sub` (JOB-002 §4.5). (d) `get_job_order` returns
   `JobOrderOut` (a Pydantic model), so `job.title` is correct; `.get("title", ...)` would
   raise `AttributeError`.

4. **Resolve and fetch résumé bytes** (only when `data.resume_attachment` is `True`):

   ```python
   attachment_bytes: Optional[bytes] = None
   attachment_filename: Optional[str] = None
   attachment_mime: Optional[str] = None

   if data.resume_attachment:
       try:
           from app.services.candidates import get_primary_resume_item
           resume_item = get_primary_resume_item(candidate_id)
       except Exception:
           resume_item = None
       if resume_item is None:
           raise HTTPException(400, detail={"code": "no_primary_resume",
               "message": "Candidate has no primary résumé on file."})
       from app.core.aws_clients import s3_client
       attachment_bytes = s3_client().get_object(
           Bucket=resume_item["s3_bucket"], Key=resume_item["s3_key"]
       )["Body"].read()
       attachment_filename = resume_item.get("filename", "resume.pdf")
       attachment_mime = resume_item.get("content_type", "application/pdf")
   ```

   `get_primary_resume_item` must be added to `app/services/candidates.py` (a CND-003
   additive function not yet present in the CND-003 spec; see V16 in §12). The `s3_client()`
   factory (`aws_clients.py:114`) hits in-process moto in dev and real S3 in prod.

5. **Build subject and body:**

   ```python
   subject = data.subject or f"Candidate submission: {candidate_name} — {job_title}"
   body_text = (data.message or "") + (
       f"\n\n---\nCandidate: {candidate_name}\nJob Order: {job_title}"
   )
   ```

6. **Send email:**

   ```python
   sent_ok = True
   try:
       if attachment_bytes is not None:
           send_email_with_attachment(
               list(data.to_emails), subject, body_text,
               attachment_bytes, attachment_filename, attachment_mime,
           )
       else:
           send_alert_email(list(data.to_emails), subject, body_text)
   except Exception:
       logger.warning("submit_to_client: email send raised; treating as best-effort")
       sent_ok = False
   ```

   `send_email_with_attachment` (§4.1) and `send_alert_email` (`alerts.py:459`) both swallow
   internal errors and never raise, so the `except` here is a belt-and-suspenders guard only.

7. **Advance pipeline status to `is_submitted` stage** (only on send success — see §5.3):

   ```python
   config = get_status_config()   # PIP-002
   # config.statuses is List[PipelineStatusItemOut] — Pydantic models, use attribute access
   submitted_key = next(
       (s.status_key for s in config.statuses if s.is_submitted), None
   )
   if sent_ok and submitted_key:
       updated_entry = change_status(
           owner_sub, job_order_id, candidate_id, submitted_key
       )   # PIP-003 — idempotent no-op if already at/past submitted
   else:
       updated_entry = entry
   ```

   **Correction from verification:** `config.statuses` elements are `PipelineStatusItemOut`
   Pydantic models (PIP-002 §4.2). `s["status_key"]` and `s.get("is_submitted")` would raise
   `AttributeError`/`TypeError`. Corrected to `s.status_key` and `s.is_submitted`.

8. **Audit event** (always, regardless of send success):

   ```python
   audit_event(
       "pipeline.submitted_to_client",
       owner_sub,
       None,
       pipeline_id=entry["pipeline_id"],
       job_order_id=job_order_id,
       candidate_id=candidate_id,
       to_emails=list(data.to_emails),
       with_resume=data.resume_attachment,
       send_ok=sent_ok,
   )
   ```

9. **Timeline writes** (best-effort, twice, via lazy import):

   ```python
   try:
       from app.services.crm_activity_timeline import record_crm_activity
       summary = f"Submitted to {', '.join(data.to_emails)}"
       meta = {"to_emails": list(data.to_emails), "with_resume": data.resume_attachment,
               "send_ok": sent_ok}
       record_crm_activity("candidate", candidate_id, "submission",
                           entry["pipeline_id"], owner_sub,
                           summary=summary, metadata=meta)
       record_crm_activity("job_order", job_order_id, "submission",
                           entry["pipeline_id"], owner_sub,
                           summary=summary, metadata=meta)
   except Exception:
       logger.debug("submit_to_client: record_crm_activity unavailable or failed")
   ```

10. **Return:**

    ```python
    ts = now_ts()
    return SubmitToClientOut(
        pipeline_id=entry["pipeline_id"],
        job_order_id=job_order_id,
        candidate_id=candidate_id,
        to_emails=list(data.to_emails),
        subject=subject,
        with_resume=data.resume_attachment,
        status_after=updated_entry["status"],
        status_rank_after=updated_entry["status_rank"],
        submitted_at=ts,
    )
    ```

### 4.3 Router endpoint (PIP-008, documented here for completeness)

PIP-008 (`docs/opencats/ATS_PIPELINE_TICKETS.md`, "PIP-008: Pipeline router") mounts this
endpoint. For clarity it is fully specified here.

```
POST /ui/ats/pipeline/by-job/{job_order_id}/candidate/{candidate_id}/submit
```

| Field | Value |
|---|---|
| Auth | `Depends(require_ui_session)` (`app/services/sessions.py:330`) |
| CSRF | Enforced automatically by `require_ui_session` on POST cookie-auth |
| Request body | `SubmitToClientIn` |
| Response | `SubmitToClientOut`, HTTP 200 |
| Flag off | `_require_flag()` raises 503 `ats_pipeline_disabled` |

Handler signature:

```python
@router.post(
    "/by-job/{job_order_id}/candidate/{candidate_id}/submit",
    response_model=SubmitToClientOut,
)
async def submit_candidate_to_client(
    job_order_id: str,
    candidate_id: str,
    body: SubmitToClientIn,
    ctx: dict = Depends(require_ui_session),
):
    _require_flag()
    return await asyncio.to_thread(
        svc.submit_to_client,
        ctx["user_sub"], job_order_id, candidate_id, body,
    )
```

`asyncio.to_thread` wraps the sync service call (S3 and SES are sync boto3 calls),
matching the pattern used in the Google Drive OAuth callback (`app/routers/google_drive_integration.py`).
The `/submit` literal segment is declared before any dynamic `/{pipeline_id}` segment in
the router to avoid route-capture ambiguity (CLAUDE.md audit-export `/schedules`-before-`/{export_id}` gotcha).

## 5. Detailed Behavior & Edge Cases

### 5.1 Email send is best-effort; status advance is conditional on send success

The email send (`send_email_with_attachment` / `send_alert_email`) never raises. If the
send silently fails at the SES layer (e.g., SES is not configured in dev), the function
returns normally. PIP-005 treats a completed send call as success and advances the pipeline
status. The `send_ok=True/False` flag in `audit_event` and the dev-log entry make failures
traceable.

The status advance runs only on `sent_ok=True`. This prevents silently advancing a
candidate to "Submitted" when no email was actually sent. The recruiter can re-call the
endpoint to retry.

### 5.2 `resume_attachment=True` with no primary résumé → 400, no side effects

When `data.resume_attachment=True` and `get_primary_resume_item` returns `None` (candidate
has uploaded no résumé, or CND-003 is not yet deployed), the function raises
`HTTPException(400, detail={"code": "no_primary_resume"})` immediately — no email is
sent, no status is changed, no audit event is emitted.

### 5.3 Status already at or past `is_submitted`

`change_status` (PIP-003) is a no-op when `new_status == current_status`. If the
config has no `is_submitted` status (invalid config state — impossible with the default
ladder but possible if an admin misconfigured and removed the flag), `submitted_key` is
`None` and the status advance is silently skipped. `status_after` in the response reflects
the actual current status.

### 5.4 Re-submission (idempotency from recruiter's POV)

There is no once-only gate at the service layer. Calling `submit_to_client` a second time
re-sends the email and re-logs activity. If the pipeline is already at `400_submitted`, the
`change_status` call is a no-op (PIP-003 §1). The UI should present a confirmation dialog
on repeat calls ("You already submitted this candidate on [date]. Send again?"), but that
is a frontend concern.

### 5.5 `to_emails` validation

`SubmitToClientIn.to_emails` is `List[EmailStr]` with `min_length=1` / `max_length=10`.
Pydantic validates at the model boundary (422 for invalid email format or out-of-range
list length) before `submit_to_client` is called. The service does not re-validate.

### 5.6 S3 `get_object` failure

If S3 is inaccessible or the object is missing (e.g., was deleted after the résumé was
registered in DDB), `s3_client().get_object(...)` raises a `ClientError`. PIP-005 does
not catch this — it propagates as a 500. Rationale: an S3 read failure is infrastructure
failure, not a business-logic error; the recruiter cannot proceed without the résumé bytes.
This matches the behavior of file-download endpoints in `app/services/filemanager.py`.

### 5.7 `get_primary_resume_item` import failure (CND-003 not yet deployed)

If CND-003 has not shipped, `from app.services.candidates import get_primary_resume_item`
will raise `ImportError`. PIP-005 wraps this import in `try/except Exception` (step 4
above), sets `resume_item = None`, and then (since `resume_attachment=True` and
`resume_item is None`) raises 400 `no_primary_resume`. The 400 is preferable to a 500
because it communicates a specific actionable problem to the caller.

### 5.8 `to_emails` cap and SES rate

The `max_length=10` cap on `to_emails` limits the maximum SES calls to 10 per submission
request. `send_email_with_attachment` issues one `send_raw_email` call per recipient.
No per-call rate-limiting is applied; SES source-level throttle errors are swallowed by the
`except Exception` guard in the helper.

### 5.9 `subject` and `message` length caps

`SubmitToClientIn.subject` is capped at 200 characters at the model level; SES subject
lines accept up to 320 characters, so no additional truncation is needed in the helper.
`message` is capped at 4000 characters.

### 5.10 Missing `is_submitted` status in config

If the admin has misconfigured the status ladder with no `is_submitted` flag, `submitted_key`
is `None`. The email still sends, the audit event is written, but no status advance occurs.
`status_after` in the response will equal the pre-submission status, making the no-advance
visible to the caller.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 compliance

There is **no `if S.dev_mode` business-logic branch** in `submit_to_client` or in
`send_email_with_attachment`'s dev path beyond writing to `S.dev_email_log` (the dev-log
branch is the same abstraction used by `send_alert_email:462` — it is the established
delivery-substrate fork, not a business-logic fork). The DDB reads (`get_pipeline_entry`,
`get_status_config`), the status advance (`change_status`), and the audit/timeline writes
all run the same code path in both environments.

The S3 `get_object` call goes through `s3_client()` (`aws_clients.py:114`), which
transparently hits in-process moto in dev and real S3 in prod — no dev-mode override
needed.

### 7.2 Idempotency

`submit_to_client` is not idempotent by design: a re-call re-sends the email (matching
OpenCATS behavior and recruiter expectations). The status advance is idempotent (PIP-003
same-status no-op). The `audit_event` writes are append-only. There is no HMAC token or
consumed-at guard (unlike cart recovery links in `cart_reminders.py`) — the action is
intentionally repeatable.

### 7.3 Security: to_emails source

`to_emails` is fully recruiter-controlled; the platform does not restrict which email
addresses a recruiter may submit to. Rate-limiting (e.g., per recruiter per day) is deferred
to a follow-up ticket. For now, the 10-recipient cap per call limits blast radius.

### 7.4 Security: résumé bytes in transit

Résumé bytes are read from S3 server-side and placed in the MIME body of a raw SES
message. They are never written to the filesystem, never stored in DDB, and never
returned to the browser. The S3 `get_object` call uses the `s3_client()` factory which
injects AWS credentials from environment variables (not user-supplied).

### 7.5 Security: no user-controlled MIME headers

`send_email_with_attachment` uses `S.alerts_from_email` as the MIME `From:` header (not
caller-controlled). The `subject` parameter goes into the MIME `Subject` header via
`MIMEMultipart["Subject"] = subject[:200]` — the 200-character cap (enforced at the Pydantic
layer) prevents header-injection payloads. The body text and filename go into MIME part
bodies/headers respectively, not raw headers. The `filename` value is taken from
`resume_item["filename"]` (a stored-in-DDB value originating from the recruiter's own
upload, not the client's email), which CND-003 already sanitises with
`re.sub(r"[^A-Za-z0-9._-]", "_", ...)` (`CND-003.md §2.3`).

### 7.6 Security: ownership enforcement

`get_pipeline_entry(owner_sub, job_order_id, candidate_id)` queries DDB with
`pk=USER#{owner_sub}`, so an attacker passing a foreign `owner_sub` gets a 404 from the
keyed lookup (structural authorization, per `PIP-001.md §5`). No role check is needed on
this action.
