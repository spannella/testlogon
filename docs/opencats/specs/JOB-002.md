## 1. Summary & Goal

Implement the `app/services/job_orders.py` service module: the five public CRUD functions (`create_job_order`, `get_job_order`, `update_job_order`, `delete_job_order`, `set_status`) and the 7-state status state-machine that guards every status transition. This is a **pure service layer ticket** — no router endpoints ship here (that is JOB-003), no list views (JOB-004), no openings counter (JOB-005), no link resolution (JOB-006).

The structural template is OPP-002 (`docs/suitecrm/CRM_OPPORTUNITIES_TICKETS.md:135-208`): same single-table DynamoDB layout, same `_require_flag()` guard, same optimistic-concurrency `update_item`, same `audit_event` emission on mutations, same hermetic offline test recipe.

**Why this ticket is the critical path:** The state-machine is the most nuanced piece of the entire Job Order vertical — it encodes OpenCATS's 7-status workflow with asymmetric transition rules, a reopen escape hatch, and an atomic `placed_count` constraint that JOB-005 will later hook into. Getting the guard logic right in isolation (before the router, before the frontend) limits the blast radius of any design changes.

### 2.3 OpenCATS state-machine context

OpenCATS's Job Order entity natively carries seven statuses. In the OpenCATS source the allowed transitions are:

- **Lead** → Active (when a tentative opening becomes confirmed)
- **Upcoming** → Active (scheduled start date arrives or is pulled forward)
- **Active** ⇄ On Hold (reciprocal; a paused search that may resume)
- **Active** → Full (all openings filled by pipeline; also manually settable)
- **Active / On Hold / Full** → Closed | Canceled (terminal transitions)
- **Closed** → Active (reopen escape hatch; configurable)

`Canceled` is fully terminal: it cannot be reopened even with the escape hatch enabled. `Closed` can be reopened when `JOB_ORDER_ALLOW_REOPEN` is `true` (default). This mirrors the `SALES_PIPELINE_ALLOW_REOPEN` env flag referenced in `docs/suitecrm/CRM_OPPORTUNITIES_TICKETS.md:233` for OPP-003.

## 4. API / Service Design

### 4.1 Module: `app/services/job_orders.py`

All functions are synchronous (FastAPI runs them in a threadpool via `run_in_executor` at the router layer). The module imports `T` from `app.core.tables`, `S` from `app.core.settings`, `now_ts` from `app.core.time`, and `audit_event` from `app.services.alerts`. No router-level imports; no `require_ui_session` call (that is the router's concern).

#### 4.2 Flag guard

```python
def _require_flag() -> None:
    """Raise 503 when either ATS gate is off.

    Called at the top of every public function. Service functions remain
    unconditionally callable from tests (tests set the flags via
    object.__setattr__ before calling); the router also calls _require_flag()
    for defence-in-depth (JOB-003).
    """
    if not (S.ats_enabled and S.job_orders_enabled):
        raise HTTPException(503, detail={"code": "job_orders_disabled"})
```

#### 4.3 Internal helper: `_item_to_out(item: dict) -> JobOrderOut`

Converts a raw DynamoDB item (with `Decimal` numerics from `_safe_table`) to a `JobOrderOut`. Coerces `Decimal → int` for all numeric fields. Derives `openings_remaining = max(int(item.get("openings", 0)) - int(item.get("placed_count", 0)), 0)`. Returns a `JobOrderOut` (model defined in JOB-001, `app/models.py`).

#### 4.4 `create_job_order`

```python
def create_job_order(actor_sub: str, data: JobOrderCreateIn) -> JobOrderOut:
```

- Calls `_require_flag()`.
- Validates `data.type in JOB_ORDER_TYPES` and `data.status in JOB_ORDER_STATUSES`; raises `HTTPException(422)` on violation (Pydantic validators in JOB-001 should catch this before the service layer, but a belt-and-suspenders check is appropriate here).
- Mints `job_id = "job_" + uuid4().hex`.
- Computes `ts = now_ts()`.
- Builds the META item. Sets `hot_flag = "1"` iff `data.hot is True` (omit the key entirely otherwise — sparse GSI_HOT); same for `public_flag`. Sets `placed_count = 0`, `created_by = actor_sub`, `created_at = ts`, `updated_at = ts`.
- Writes META row via `T.job_orders.put_item(Item=meta_item)`.
- For each `sub` in `data.recruiter_subs`: writes one per-recruiter index row (`pk=COMPANY#{client_company_id}`, `sk=RECRUITER#{sub}#JOB#{job_id}`, `recruiter_sub=sub`, `job_id=job_id`, `created_at=ts`).
- Emits `audit_event("job_order.created", actor_sub, None, job_id=job_id, client_company_id=data.client_company_id, status=data.status)`.
- Returns `_item_to_out(meta_item)`.

#### 4.5 `get_job_order`

```python
def get_job_order(job_id: str) -> JobOrderOut:
```

- Calls `_require_flag()`.
- Queries `GSI_DIRECT` with `KeyConditionExpression=Key("job_id").eq(job_id)`, `Limit=1`.
- Raises `HTTPException(404, detail={"code": "job_order_not_found"})` when no item is returned or when the item has a `deleted_at` attribute.
- Returns `_item_to_out(item)`.

**Note:** `get_job_order` takes only `job_id` (not `actor_sub`) because the router has no ownership restriction on reads — any authenticated user with the flags on can fetch any job order. Authorization narrowing (per-company, per-recruiter) is a JOB-006 / STU-002 concern, out of scope here.

#### 4.6 `update_job_order`

```python
def update_job_order(
    actor_sub: str,
    job_id: str,
    data: JobOrderUpdateIn,
) -> JobOrderOut:
```

- Calls `_require_flag()`.
- Fetches the current META item via `get_job_order(job_id)` to obtain `pk`, `sk`, and `updated_at` for the optimistic-concurrency guard.
- **Status changes are NOT handled here.** If `data.status` is set and differs from the current status, `update_job_order` delegates to `set_status(actor_sub, job_id, data.status)` and continues with the remaining non-status fields. This ensures the state-machine guard is never bypassed via the general update path.
- Builds a dynamic `UpdateExpression` from the non-`None` fields in `data` (excluding `status`, handled above). Numeric fields go through `Decimal` coercion via `_safe_table`.
- Handles `hot` / `public` flag changes: when `hot` flips to `True` add `hot_flag = "1"` to the `SET` expression; when it flips to `False` add `hot_flag` to the `REMOVE` expression (removes the attribute entirely, keeping GSI_HOT sparse). Same for `public_flag`.
- Handles `recruiter_subs` change: compute `added = new_set - old_set`, `removed = old_set - new_set`. For each added sub, `put_item` a new index row. For each removed sub, `delete_item` the `RECRUITER#{sub}#JOB#{job_id}` row.
- Appends `updated_at = now_ts()` to the `SET` expression.
- Calls `T.job_orders.update_item` with `ConditionExpression=Attr("updated_at").eq(prev_updated_at)`. On `ConditionalCheckFailedException` → raises `HTTPException(409, detail={"code": "job_order_conflict"})` (lost-update guard, OPP-002 pattern).
- Emits `audit_event("job_order.updated", actor_sub, None, job_id=job_id, fields=list(changed_fields))`.
- Returns `get_job_order(job_id)` (fresh read-after-write to return the fully consistent state).

#### 4.7 `set_status`

```python
def set_status(
    actor_sub: str,
    job_id: str,
    new_status: str,
) -> JobOrderOut:
```

This is the core of JOB-002. The full transition matrix:

```
lead       → active                  (opening confirmed)
upcoming   → active                  (start date arrives)
active     → on_hold                 (search paused)
on_hold    → active                  (search resumed)
active     → full                    (all openings manually flagged filled)
active     → closed | canceled       (terminal)
on_hold    → closed | canceled       (terminal)
full       → closed | canceled       (terminal)
closed     → active                  (reopen; only if S.job_order_allow_reopen == True)
canceled   → [any]                   (ALWAYS rejected; canceled is fully terminal)
```

Implementation:

1. Calls `_require_flag()`.
2. Fetches the current META item to get `current_status`.
3. If `new_status == current_status`: returns `_item_to_out(current_item)` immediately (no-op, no audit event emitted).
4. Validates `new_status in JOB_ORDER_STATUSES`; raises `HTTPException(422)` on unknown value.
5. Evaluates the transition:
   - If `current_status == "canceled"`: always reject → `HTTPException(409, detail={"code": "invalid_status_transition", "from": "canceled", "to": new_status})`.
   - If `current_status == "closed"` and `new_status != "active"`: reject → 409 same code.
   - If `current_status == "closed"` and `new_status == "active"`: allowed only when `S.job_order_allow_reopen` is `True`; otherwise → 409 with `{"code": "reopen_not_allowed"}`.
   - Build `ALLOWED_FROM` mapping for all other current statuses:

     | current_status | allowed new statuses |
     |---|---|
     | `lead` | `active` |
     | `upcoming` | `active` |
     | `active` | `on_hold`, `full`, `closed`, `canceled` |
     | `on_hold` | `active`, `closed`, `canceled` |
     | `full` | `closed`, `canceled` |

   - If `new_status not in ALLOWED_FROM[current_status]`: reject → 409 `{"code": "invalid_status_transition", "from": current_status, "to": new_status}`.
6. On an accepted transition: `update_item` with `SET status = :s, updated_at = :ts`.
7. Emits `audit_event("job_order.status_changed", actor_sub, None, job_id=job_id, from_status=current_status, to_status=new_status)`.
8. Returns `get_job_order(job_id)`.

**Interaction with `placed_count` (JOB-005 concern):** The `active → full` transition is allowed manually via `set_status`. JOB-005's `adjust_placed_count` will also call `set_status` when the counter reaches zero — it does not bypass the guard. No JOB-005 logic lives here.

#### 4.8 `delete_job_order`

```python
def delete_job_order(actor_sub: str, job_id: str) -> None:
```

- Calls `_require_flag()`.
- Fetches the current META item via `get_job_order(job_id)` to obtain `pk`, `sk`, and the current `recruiter_subs` list.
- Writes `deleted_at = now_ts()` and `updated_at = now_ts()` onto the META row via `update_item`.
- Deletes every `RECRUITER#{sub}#JOB#{job_id}` index row for each sub in `recruiter_subs` (iterate and `delete_item` each).
- Emits `audit_event("job_order.deleted", actor_sub, None, job_id=job_id, client_company_id=...)`.
- Returns `None` (the router returns 204).

**Soft-delete semantics:** The META row is retained in DynamoDB. `get_job_order` and all list paths in JOB-004 treat the presence of `deleted_at` as deletion (`get_job_order` raises 404; list functions add `FilterExpression=Attr("deleted_at").not_exists()`). Recruiter index rows are deleted immediately so they stop appearing in the `list_mine` GSI query.

## 5. Detailed Behavior & Edge Cases

### 5.1 Sparse GSI attributes (`hot_flag`, `public_flag`)

DynamoDB only indexes an item in a GSI when the GSI's partition key attribute is **present** on the item. Writing `hot_flag` as `None` or an empty string does not achieve sparseness — the attribute must be physically absent. The `create_job_order` and `update_job_order` implementations must:

- Use `SET hot_flag = :v` (value `"1"`) when setting the flag.
- Use `REMOVE hot_flag` when clearing it.

Failure to use `REMOVE` (e.g. setting `hot_flag = False`) would incorrectly index all job orders in `GSI_HOT` with a non-`"1"` value and break the `list_hot` queries in JOB-004.

### 5.2 Optimistic concurrency and `updated_at`

`update_job_order` reads `updated_at` from the item before building the `UpdateExpression`, then includes `ConditionExpression=Attr("updated_at").eq(prev_updated_at)` in the write call. A concurrent mutation that succeeded between the read and the write will have bumped `updated_at`, causing `ConditionalCheckFailedException`. The service catches this and raises `HTTPException(409, detail={"code": "job_order_conflict"})`. The caller (router → frontend) should retry with a fresh GET.

This guard does not apply to `set_status` because `set_status` only writes `status` and `updated_at` — the relevant invariant is the current `status` value, which is read immediately before the state-machine check. A race between two concurrent `set_status` calls is tolerated: the second call will read the post-first-call status and either succeed (if the transition from the new status is valid) or reject with a 409 `invalid_status_transition`.

### 5.3 Recruiter index row reconciliation

When `recruiter_subs` changes in `update_job_order`:

- `old_set = set(current_item["recruiter_subs"])` — from the fetched item (may be an empty set for a job with no assigned recruiter).
- `new_set = set(data.recruiter_subs)` — from the update payload.
- Items in `new_set - old_set` get a new `put_item` for their index row.
- Items in `old_set - new_set` get a `delete_item` on their `RECRUITER#{sub}#JOB#{job_id}` row.
- Items in the intersection are unchanged.

Failure modes: if a `put_item` succeeds but the subsequent META update fails (conflict), the orphaned index row will cause the recruiter's `list_mine` to include a job they can no longer access. JOB-004's `list_mine` must tolerate a `get_job_order` returning 404 (soft-deleted or otherwise absent) for a given `job_id` in the index and skip it silently. This is the standard stale-index-row degradation pattern also used by OPP Kanban (OPP-003; OPP-004 is the Opportunity–Contact role junction, not the Kanban).

### 5.4 Unknown vs. terminal `canceled`

`canceled` is distinguished from `closed` in that it is **fully and irrevocably terminal**: even with `JOB_ORDER_ALLOW_REOPEN=true` a canceled job cannot transition to any status. This reflects the OpenCATS semantics (a canceled role was abandoned, not just filled). The `set_status` guard handles this with a specific early check before the general transition matrix.

### 5.5 Same-status no-op

`set_status(actor_sub, job_id, current_status)` returns the current `JobOrderOut` without writing to DynamoDB and without emitting an `audit_event`. This is intentional: the router's `POST /{job_id}/status` endpoint may receive idempotent retries from the frontend after a network timeout; returning 200 with the unchanged object is the correct response.

### 5.6 `recruiter_subs` as a DynamoDB String Set vs. List

DynamoDB String Sets (`SS`) do not preserve insertion order and cannot be empty. The service layer must:

- Store `recruiter_subs` as a `List[str]` in the DynamoDB item using the regular `L` / `S` attribute types (not `SS`) to preserve ordering and allow an empty list.
- Use Python `list` in the META item; convert to `set` only internally for set-difference reconciliation in `update_job_order`.
- `_safe_table`'s `_FloatSafeTable` (at `app/core/tables.py:29`) handles `float → Decimal` coercion but does not convert sets to lists; this must be done explicitly in `_item_to_out`.

### 5.7 DynamoDB `Decimal` coercion

`_safe_table` wraps every write in `_FloatSafeTable` which converts Python `float` to `Decimal` (required by boto3). Reads return `Decimal` for numeric attributes. `_item_to_out` must coerce `Decimal → int` for `openings`, `placed_count`, `created_at`, `updated_at`, `pay_rate_cents`, `bill_rate_cents`, `deleted_at` before constructing `JobOrderOut`.

### 5.8 `description` length and DynamoDB item size

`description` may be up to 20 000 characters (UTF-8). DynamoDB's single-item limit is 400 KB. A 20 000-character description in UTF-8 is at most 80 KB, well within the limit alongside all other fields. No chunking or S3 offloading is required.

### 5.9 Audit event fields

| Event | Actor | Extra fields |
|---|---|---|
| `job_order.created` | `actor_sub` | `job_id`, `client_company_id`, `status`, `type` |
| `job_order.updated` | `actor_sub` | `job_id`, `fields` (list of changed field names) |
| `job_order.status_changed` | `actor_sub` | `job_id`, `from_status`, `to_status` |
| `job_order.deleted` | `actor_sub` | `job_id`, `client_company_id` |

All use `audit_event(event, actor_sub, None, **kwargs)` — the `None` for `request` is the same pattern used in `app/services/kyc_cases.py` and throughout the platform.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

There are **no `if S.dev_mode` branches** anywhere in `app/services/job_orders.py`. The same code path executes in dev (DynamoDB Local at port 8001, `AWS_ACCESS_KEY_ID=test`) and in prod (real DynamoDB with IAM). This is the platform-wide SECOPS-007 requirement. The `_safe_table` wrapper handles the transport differences transparently.

### 7.2 Idempotency

- `create_job_order` is **not idempotent**: each call mints a new `job_id`. The router (JOB-003) does not add an idempotency key; the frontend must not retry on 201 without checking for a prior success.
- `set_status` with the same `new_status` as the current status is **idempotent**: returns 200 with the unchanged record, no DDB write, no audit event.
- `delete_job_order` called twice: the second call will `get_job_order` and receive a 404 (the first call set `deleted_at`), which propagates as a 404 to the router caller. This is acceptable — a double-delete is a client-side bug.
- `update_job_order` uses optimistic concurrency, so a duplicate call with a stale `updated_at` will 409. The router does not expose `updated_at` in the update request body — the conflict check is internal; the router always reads `updated_at` from the freshly fetched item.

### 7.3 Security

- **No cross-user data exposure in this ticket.** `get_job_order` returns any non-deleted job order to any authenticated caller (the flags are the gate). Fine-grained ACL (per-company, per-recruiter visibility restriction) is a STU-002/003/004 concern, not specced here.
- **`actor_sub` provenance.** Every mutating function receives `actor_sub` from the caller (the router, which extracts it from `require_ui_session`'s `user_sub` field). The service never derives `actor_sub` from a request body.
- **Input validation.** `type` and `status` are validated against the closed tuple constants `JOB_ORDER_TYPES` and `JOB_ORDER_STATUSES`. Unknown values raise `HTTPException(422)` rather than being stored silently, preventing state-machine corruption by out-of-band writes.
- **`description` is stored verbatim.** It is a user-supplied free-text field. Sanitization for XSS is the frontend's and template-rendering layer's responsibility; the service stores it as-is (same pattern as `app/services/questionnaires_repository.py`).
- **`recruiter_subs` are stored as opaque sub strings.** The service does not validate that the subs correspond to real users. The link-resolution layer in JOB-006 handles the unresolved-sub case gracefully. Injection of a fake sub does no harm beyond that sub not resolving to a display name.

## 8. Backward Compatibility & Migration

### 8.1 No existing tables or routes are changed

`app/services/job_orders.py` is a new file. It imports from existing modules (`app.core.tables`, `app.core.settings`, `app.core.time`, `app.services.alerts`) but does not modify any of them. The first router registration happens in JOB-003.

### 8.2 No DynamoDB migration required

The `job_orders` table is created by `scripts/local-ddb-init.py` at stack startup (added in JOB-001). It starts empty. There are no existing records to migrate.

### 8.3 Additive `settings.py` addition

The `job_order_allow_reopen` setting added in §6.2 is a new field on the `Settings` dataclass. It does not change any existing field. Because the settings dataclass is a standard Python dataclass (not frozen here in terms of field additions), the new field's default value (`True`) means existing deployments that do not set `JOB_ORDER_ALLOW_REOPEN` get the permissive default — no behavior change for features that do not call `set_status`.

### 8.4 Flag-off guarantees the platform invariant

With `ATS_ENABLED=0` or `JOB_ORDERS_ENABLED=0` (the production default until the ATS vertical is ready to ship):

- No request reaches any DDB table in the `job_orders` namespace.
- No audit events with `job_order.*` event names are emitted.
- No existing route, middleware, or startup task is affected.
- The `job_orders` DynamoDB table may exist (created by `local-ddb-init.py`) or not (fresh prod deployment before the table is provisioned) — `_safe_table` will simply return a handle that raises `ResourceNotFoundException` on the first DDB call, which never happens because `_require_flag()` short-circuits first.

## 10. Open Questions / Assumptions

1. **`on_hold → full` transition.** OpenCATS does not document this direction explicitly. The spec above omits it (an on-hold job cannot be marked full without first returning to active). If a product decision allows it, add `full` to `ALLOWED_FROM["on_hold"]` — a one-line change to the transition matrix in §4.7. **Assumption: disallowed.**

2. **`lead → on_hold` / `upcoming → on_hold` transitions.** Pre-active statuses transitioning to `on_hold` without first going through `active` is not a standard OpenCATS flow. **Assumption: disallowed.** Only `active ⇄ on_hold` is bidirectional.

3. **Authorization on `set_status`.** Currently any authenticated user can transition any job order's status. In the full ACL model (STU-002/003), this should be restricted to the job's `recruiter_subs` or a user with ADMIN role. **Assumption: deferred to STU-002/003; tracked as a known gap.**

4. **`JobOrderUpdateIn.status` delegation behavior.** The spec routes a status change embedded in `update_job_order` through `set_status`. An alternative is to reject status changes in the `PATCH` body and require `POST /{job_id}/status`. The current design is more ergonomic for bulk form submissions from JOB-007. **Assumption: delegation approach is correct.**

5. **`recruiter_subs` max length.** The JOB-001 model sets `max_length=25` on the list. The service does not enforce this independently (Pydantic validation fires before the service call). If a service call is made outside the Pydantic layer (e.g., from a test or internal caller), the 25-entry limit is not enforced. **Assumption: Pydantic validation is sufficient.**

6. **`description` markdown / HTML sanitization.** Stored verbatim. The career portal rendering (PORTAL-*) will need to decide whether to render markdown, strip HTML, or display plaintext. **Assumption: no sanitization in this ticket.**
