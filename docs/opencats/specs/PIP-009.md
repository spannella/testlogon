## 1. Summary & Goal

PIP-009 is the entire frontend recruiting surface: a pipeline Kanban board, a submit-to-client dialog, a placement dialog, a bulk-add flow, and an admin status-config editor. Together these give recruiters the canonical OpenCATS workflow — drag candidate cards through configurable stages, submit a résumé to a client contact by email, and record a placement fee and start date when a hire is made — entirely within the testlogon UI.

The Kanban columns are fetched from `GET /ui/ats/pipeline/statuses` and are never hard-coded: admin-configured labels, ordering, and colors are respected automatically. Dragging a card to a new column fires an optimistic `PATCH …/status`; non-2xx responses roll back and show a `sonner` toast. The submit dialog posts to `…/submit` (advancing the card to the configured `is_submitted` column); the placement dialog posts to `…/placement` (advancing to `is_placed`). The bulk-add flow allows multi-selecting candidates from a job-order view and adding them to the pipeline in one request.

All UI is additive and fully gated behind `isAtsPipelineEnabled()`. With the flag off, no sidebar entry appears, no routes are mounted, and the existing platform is byte-for-byte unchanged.

## 4. API / Service Design

### 4.1 API endpoint wrappers (`frontend/src/api/endpoints/atsPipeline.ts`)

New file. All calls use the shared fetch-based `api` wrapper from `api/client.ts` (CSRF auto-attached). The correct import is `import { api } from "@/api/client"` — `client.ts` exports a named `api` function with typed convenience methods (`api.get<T>`, `api.post<T>`, `api.put<T>`, `api.patch<T>`, `api.del<T>`), not a default-export axios instance. Each method returns `Promise<T>` directly (no `.then(r => r.data)` unwrapping needed — the wrapper already parses the JSON response).

```ts
import { api } from "@/api/client";
import type {
  PipelineStatusConfig, PipelineStatusItem, PipelineEntry,
  SubmitToClientIn, PlacementIn, PlacementOut,
  BulkPipelineAddIn, BulkPipelineResultOut,
} from "@/api/types";

const BASE = "/ui/ats/pipeline";
const ADMIN_BASE = "/ui/admin/ats/pipeline";

// Status config
export const getPipelineStatuses = (): Promise<PipelineStatusConfig> =>
  api.get<PipelineStatusConfig>(`${BASE}/statuses`);

export const setPipelineStatuses = (data: PipelineStatusConfig): Promise<PipelineStatusConfig> =>
  api.put<PipelineStatusConfig>(`${ADMIN_BASE}/statuses`, data);

// Pipeline entries
export const listPipelineForJob = (jobOrderId: string): Promise<PipelineEntry[]> =>
  api.get<PipelineEntry[]>(`${BASE}/by-job/${jobOrderId}`);

export const listPipelineForCandidate = (candidateId: string): Promise<PipelineEntry[]> =>
  api.get<PipelineEntry[]>(`${BASE}/by-candidate/${candidateId}`);

// Status change (Kanban drag)
export const changePipelineStatus = (
  jobOrderId: string, candidateId: string, newStatus: string
): Promise<PipelineEntry> =>
  api.patch<PipelineEntry>(
    `${BASE}/by-job/${jobOrderId}/candidate/${candidateId}/status`,
    { new_status: newStatus });

// Rating
export const setPipelineRating = (
  jobOrderId: string, candidateId: string, rating: number
): Promise<PipelineEntry> =>
  api.put<PipelineEntry>(
    `${BASE}/by-job/${jobOrderId}/candidate/${candidateId}/rating`,
    { rating });

// Submit to client
export const submitToClient = (
  jobOrderId: string, candidateId: string, data: SubmitToClientIn
): Promise<{ ok: boolean }> =>
  api.post<{ ok: boolean }>(
    `${BASE}/by-job/${jobOrderId}/candidate/${candidateId}/submit`, data);

// Placement
export const recordPlacement = (
  jobOrderId: string, candidateId: string, data: PlacementIn
): Promise<PlacementOut> =>
  api.post<PlacementOut>(
    `${BASE}/by-job/${jobOrderId}/candidate/${candidateId}/placement`, data);

// Bulk add
export const bulkAddToPipeline = (data: BulkPipelineAddIn): Promise<BulkPipelineResultOut> =>
  api.post<BulkPipelineResultOut>(`${BASE}/bulk-add`, data);

// Feature-status probe
export const getAtsPipelineFeatureStatus = (): Promise<{ enabled: boolean }> =>
  api.get<{ enabled: boolean }>(`${BASE}/feature-status`);
```

## 5. Detailed Behavior & Edge Cases

### 5.1 PipelineKanban — column rendering

`PipelineKanban.tsx` calls `usePipelineStatuses()` (React Query, stale-time 5 min). The statuses array is sorted by `order` ascending before rendering — the frontend never trusts server ordering implicitly, matching OPP-003 §5.6. Each `PipelineStatusItem` maps to a `KanbanColumn` whose header color is the `color` hex (or a fallback neutral shade when `color` is absent). The "Unknown" overflow column is appended after the config columns; it catches any `PipelineEntry` whose `status` is not present in the current live config (OPP-003 §5.2 / Q3). The overflow column header is labeled "Unknown" and is not a valid drag target — cards can be dragged out of it but not into it.

### 5.2 Kanban drag-and-drop

On `dragStart`, the dragged card is stored in local React state (for `DragOverlay`). On `dragEnd`:

1. Identify the `overId` (the droppable column). If the card was dropped on its own column, no-op.
2. Check if the target column's `status_key` matches `is_placed: true`; if so, open `PlacementDialog` instead of firing the status PATCH immediately (see §5.4).
3. Otherwise, optimistically update the card's column in local state (`setOptimisticStatus(entry.pipeline_id, targetStatusKey)`).
4. Fire `changePipelineStatus(jobOrderId, candidateId, targetStatusKey)`.
5. `onSuccess`: invalidate `["ats-pipeline", jobOrderId]`.
6. `onError`: revert the optimistic update (remove it from local state) + invalidate `["ats-pipeline", jobOrderId]` (force a server re-fetch) + `toast.error("Could not move candidate: " + errorCode)`.

The optimistic update is implemented as a `Map<pipeline_id, overriddenStatus>` held in `useState`. `PipelineKanban.tsx` groups entries first by the override map, then by `entry.status`. On query invalidation (success or error path), the override map is cleared.

### 5.3 Star rating control

`StarRating.tsx` renders 5 clickable stars. Clicking a star calls `setPipelineRating(jobOrderId, candidateId, n)`. The mutation is fire-and-optimistic: the star display updates instantly; on error the previous value is restored (stored in `onMutate` via `queryClient.getQueryData`). A rating of 0 is rendered as all-empty stars. The control is always visible on the card face; it does not require opening a dialog.

### 5.4 Placement dialog

The placement dialog opens in two ways:

1. When a card is dragged onto a column with `is_placed: true`.
2. When the recruiter clicks "Place" in the card action menu.

Inputs: start date (date picker → Unix timestamp via `new Date(dateStr).getTime() / 1000 | 0`) and fee (text input validated as non-negative number, displayed as `$${(fee_cents/100).toFixed(2)}` using the `EarningsSummaryCard.tsx:9` formatter). On submit, `recordPlacement(jobOrderId, candidateId, { start_date, fee_cents, notes })` is called. On success, invalidate `["ats-pipeline", jobOrderId]` and `toast.success("Candidate placed")`. On 409 (`placement_exists`), show `toast.error("Placement already recorded")` and close the dialog. On cancel from the drag path, the card snaps back to its original column (the drag position was never optimistically committed to the status map).

### 5.5 Submit-to-client dialog

`SubmitDialog.tsx` fields:

- `to_emails`: comma-separated or tag-input (1–10 emails); validated as email strings client-side.
- `subject`: optional, pre-filled with `"Candidate submission: {candidate_name} — {job_order_title}"`.
- `message`: optional textarea.
- `resume_attachment`: boolean toggle, default true; shown as "Attach résumé".

On submit, `submitToClient(jobOrderId, candidateId, data)` is called. On success, invalidate `["ats-pipeline", jobOrderId]` and `toast.success("Submission sent")`. The card will move to the `is_submitted` column after re-fetch. On 400 `no_primary_resume`, `toast.error("No primary résumé on file — uncheck "Attach résumé" or upload one first")` and leave the dialog open. On other errors, `toast.error(errorMessage)`.

### 5.6 Bulk-add dialog

`BulkAddDialog.tsx` is opened from a job-order detail page or a candidate list page. It accepts a list of `candidate_ids` (selected from a filtered table or checkbox list) and optionally an initial status. It posts to `bulkAddToPipeline({ job_order_id, candidate_ids, status })`. The response `BulkPipelineResultOut` is displayed as:

- "Added X candidates to pipeline" (green badge).
- "Skipped Y: `candidate_name` — already in pipeline / not found" (yellow/red badge per reason).

On success, invalidate `["ats-pipeline", jobOrderId]`. The dialog is dismissible after showing results.

### 5.7 Admin status-config editor

`StatusConfigEditor.tsx` is an admin-only page at `/ats/admin/pipeline-statuses`. It is only reachable when `isAtsPipelineEnabled()` AND the `ui_access_token` JWT role is ADMIN or ROOT (checked via `useAuthStore` + the `canAccessGeneralAdminControls` guard already in `Sidebar.tsx:263`).

The editor renders a sortable list of status rows (using `@dnd-kit/sortable` — already installed at `frontend/package.json:19`) where each row has:

- `label` (text input)
- `rank` (number — the OpenCATS 100–900 weight; read-only for the default 9 or editable for custom)
- `order` (auto-derived from drag position; 1-indexed)
- `is_submitted` (radio button — exactly one row)
- `is_placed` (radio button — exactly one row)
- `is_terminal` (checkbox)
- `color` (optional `<input type="color">` or hex text)
- Delete button (disabled if only 1 row remains)

"Add status" appends a new row with a generated `status_key` (`custom_{uuid4_hex[:8]}`). "Save" calls `setPipelineStatuses(config)` via PUT. On 400 `invalid_status_config`, the validation reason is displayed inline. On success, `toast.success("Status config saved")` + invalidate `["ats-pipeline", "statuses"]`.

Non-admin users do not see the admin editor link; if they navigate directly to `/ats/admin/pipeline-statuses`, `ProtectedRoute` redirects them (the same guard used for existing admin-only pages).

### 5.8 Flag-off behavior

When `VITE_ATS_PIPELINE_ENABLED=false` (the default):

- `featureFlags.ts` exports `isAtsPipelineEnabled = () => false`.
- `Sidebar.tsx` does not render the "Recruiting" nav entry.
- `App.tsx` does not include the `/ats/*` routes; direct navigation returns the standard 404 page.
- `getAtsPipelineFeatureStatus()` returns `{ enabled: false }` from the backend without 503 (PIP-008 §5.8 — `feature-status` skips `_require_flag()`). The frontend can poll this endpoint for runtime toggling without a deploy.

### 5.9 Empty-state handling

`PipelineKanbanPage.tsx` handles three states for `listPipelineForJob`:

- **Loading**: skeleton columns rendered with 3 ghost cards each.
- **Error**: inline error alert with "Reload" button.
- **Empty columns**: each column shows an "Drop candidates here" placeholder (a dashed-border box, not shown when the column has cards).

### 5.10 Candidate card action menu

Each `CandidateCard.tsx` has a `…` (ellipsis) overflow menu with:

- "Submit to client" → opens `SubmitDialog`.
- "Place" → opens `PlacementDialog`.
- "Remove from pipeline" → confirmation popover → `DELETE /ui/ats/pipeline/by-job/{jobOrderId}/candidate/{candidateId}` → invalidate + `toast.success`.

The "Submit" and "Place" actions are also available as primary icon buttons on wider viewport sizes.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No dev_mode branches

`atsPipeline.ts` contains no `if (isDev)` or `if (import.meta.env.DEV)` branches. The API call shapes are identical in dev and prod; the only env fork is the delivery substrate: in dev the backend uses DynamoDB Local (port 8001) and moto S3 (in-process), in prod real AWS. The frontend is oblivious to this distinction — it only calls the `/ui/ats/pipeline/*` endpoints.

### 7.2 CSRF

All `POST`, `PATCH`, `PUT`, `DELETE` calls go through the shared fetch-based `api()` wrapper (`api/client.ts:179-181`) which reads the `ui_csrf` cookie and sets `X-CSRF-Token` automatically. No PIP-009 call site needs to manually attach the CSRF header. The backend `require_ui_session` dependency (`app/services/sessions.py:330`) enforces the matching check server-side.

### 7.3 Auth / role enforcement

Standard user calls use `require_ui_session` (USER role). The admin status-config editor (`PUT /ui/admin/ats/pipeline/statuses`) is additionally gated server-side by `normalize_role(ctx.get("role")) in {Role.ADMIN, Role.ROOT}` (`app/auth/roles.py:48`). The frontend mirrors this by hiding the editor route from non-admin users (`canAccessGeneralAdminControls` guard, `Sidebar.tsx:263`), but relies on the backend 403 as the authoritative enforcement — defense-in-depth.

### 7.4 Optimistic update idempotency

A status drag that fires a PATCH and is followed by a network failure will leave the optimistic UI in the moved column until `onError` fires the query invalidation. After invalidation, the server's persisted state is restored. No stale state can survive a page reload because React Query cache is in-memory only.

### 7.5 Placement fee — integer cents

`fee_cents` is transmitted as an integer (never a float) from the React form. The form input is validated with `Math.round(parseFloat(value) * 100)` before submitting. The display uses `$${(fee_cents / 100).toFixed(2)}` matching `EarningsSummaryCard.tsx:9` (`formatCents`). This is consistent with the cross-cutting "money is integer cents" convention from `ATS_PIPELINE_TICKETS.md §4`.

### 7.6 Email input validation in SubmitDialog

`to_emails` is validated client-side against a simple email regex before the POST fires. The backend additionally validates each address as `EmailStr` (Pydantic, 422 on invalid). A client-side 422 interceptor in `api/client.ts` surfaces the Pydantic validation detail as a readable toast message.

## 10. Open Questions / Assumptions

**Q1. Job-order detail page embedding.** The ticket description mentions the Kanban "embedded on the job-order detail page" (source ticket line ~311). The embedding is scoped to a `<PipelineKanban jobOrderId={id} embedded />` prop that renders without the `/ats/pipeline` page chrome. This is implemented as a prop on `PipelineKanban.tsx` rather than a separate component. **Assumption:** the job-order detail page (JOB-* FE ticket) imports `PipelineKanban` with `embedded={true}`; PIP-009 ships the component; JOB-* FE wires the embedding.

**Q2. Candidate resolution for card display.** The `PipelineEntry` only carries `candidate_id`. The Kanban card must display the candidate name. **Assumption:** `listPipelineForJob` backend response is extended by the JOB-*/CND-* tickets (or a future PIP follow-up) to include a `candidate_name` denorm field, or the frontend makes a parallel `GET /ats/candidates/{id}` call. For PIP-009, render `candidate_id.slice(0, 12)…` as a fallback if `candidate_name` is absent from the response, matching the `UserProfileLink` truncation pattern in `TicketKanbanBoard.tsx:77`.

**Q3. Résumé attachment available indicator.** The submit dialog's "Attach résumé" toggle is enabled by default. There is no pre-flight to check if a primary résumé exists. The 400 `no_primary_resume` error is shown after the user submits. A future improvement could add a `has_primary_resume: bool` field to `PipelineEntryOut` to disable the toggle proactively. **Assumption:** post-submit error feedback is sufficient for PIP-009.

**Q4. Mobile/responsive Kanban layout.** Horizontal scroll is acceptable on small screens (same as `TicketKanbanBoard.tsx`). A stacked/list view fallback for narrow viewports is a UX follow-up ticket. **Assumption:** horizontal scroll with `overflow-x-auto` on the columns container is sufficient.

**Q5. "Unknown" column drag-out target.** Cards in the "Unknown" column (orphaned status) can be dragged to a valid column. The PATCH will set the new valid status and the card leaves the overflow column. Dragging into "Unknown" is blocked client-side by skipping the optimistic update and returning early if `targetStatusKey` is not in the live config. **Assumption:** no API change is needed; the client-side guard is sufficient.

**Q6. Admin status-config editor conflict with default 9 stages.** If an admin saves a custom config that removes a status currently held by existing pipeline entries, those entries appear in the "Unknown" overflow column. The editor should warn "X entries currently have status `{label}` — removing this status will orphan them." This warning is informational and does not block the save. **Assumption:** client-side warning is sufficient; no server-side guard needed beyond the existing OPP-003 §8.1 precedent.
