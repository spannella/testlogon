## 1. Summary & Goal

`docs/opencats/OPENCATS_GAP_ANALYSIS.md:47` identifies résumé text extraction and full-text
résumé search as **MISSING**, and explicitly notes that the existing file search
"indexes filenames only (`filemanager.py:1734`)" — content-level indexing is net-new.

RSK-003 closes the second half of that gap by building an **inverted-token index over the
`extracted_text` produced by RSK-002**, enabling recruiter queries like `"python kubernetes"`
to return only candidates whose résumé text contains **both** keywords. The design adapts
the KB-009 full-text index spec (`docs/suitecrm/specs/KB-009.md`) near-verbatim, swapping
KB articles for candidate résumés. No new DynamoDB table is introduced: token rows live on
the `candidates` table already owned by CND-001, under a `RESUME_TOKEN#` PK prefix that is
distinct from every other row type on that table.

With `ATS_RECRUITING_ENABLED=0` (the default) the platform is byte-for-byte unchanged: no
token rows are written, the search endpoint returns 404, and no existing file is touched.

## 3. Data Model

### 3.1 Token index rows (new, on `candidates` table)

Token rows coexist on the `candidates` table alongside CND-001's `CANDIDATE#{id}/META`,
`CANDIDATE#{id}/ATTACHMENT#{attachment_id}` rows (CND-003 / RSK-002), and RSK-001's
`ENTITY#candidate#{id}/SKILL#{skill_id}` reverse-assignment rows. The `RESUME_TOKEN#` PK
prefix is distinct from every row type in use by the CND and RSK families.

```
pk  = "RESUME_TOKEN#{token}"       String  (HASH)
sk  = "CANDIDATE#{candidate_id}"   String  (RANGE)

Attributes:
  candidate_id    S   — the candidate's UUID (redundant for projections / fan-out hydration)
  name_snippet    S   — first 80 chars of the candidate's display name (snapshot at index time)
  owner_sub       S   — the owning recruiter's user_sub (for owner-scope filter at query time)
  updated_at      N   — integer Unix timestamp of last index write (now_ts())
```

No new GSI is required. Every query is a primary-key lookup:
`pk = "RESUME_TOKEN#{token}"` on the table's HASH key, returning all candidates whose
résumé text contains that token as a prefix substring. DynamoDB returns results sorted by
SK (`CANDIDATE#{uuid}`) — the service layer sorts in memory by `updated_at` desc.

**Single-table reasoning.** The `RESUME_TOKEN#` prefix does not collide with:
- `CANDIDATE#` (CND-001 META rows)
- `ENTITY#candidate#` (RSK-001 reverse-assignment rows, on `ats_skills` table, not here)
- `HOTLIST#` (RSK-006 — also on `candidates` table, future ticket)

Because the token rows store `owner_sub`, post-query owner-scope filtering requires no
additional DDB call. The `name_snippet` snapshot allows building a result list for display
without a second `batch_get_item` round-trip in the common case.

### 3.2 `scripts/local-ddb-init.py` — no schema changes

No new `TableDef` is needed. The `candidates` table definition (added by CND-001) already
has `pk` / `sk` as HASH/RANGE key pair of type String. Token rows introduce no new numeric
GSI sort keys, so no additional `attr_types` entries are required.

Token rows are additive rows on the existing table — `just restart` drops and recreates the
table, so no migration is needed in dev. See §8.2 for cold-start prod population.

### 3.3 Token generation rules

Given résumé text `t`:

1. Lowercase the entire string.
2. Extract word tokens: `re.findall(r"[a-z0-9]+", t.lower())` — same regex as
   `_build_kb_search_tokens` (KB-009 §4.1). Hyphens and dots split words (`"kubernetes"`
   stays one token; `"c++"` becomes `["c"]`). Note: this differs from the file-manager
   tokenizer (`filemanager.py:966`) which uses `r"[a-z0-9@._-]+"` and preserves
   hyphens/dots/at-signs within tokens; RSK-003 deliberately follows the KB-009 regex
   (no special characters) for résumé content search.
3. For each token `w` with `len(w) >= 3`, generate all prefix strings of length
   `3 .. min(len(w), _RESUME_SEARCH_MAX_PREFIX_LEN)`. The full word is included as the
   final prefix.
4. Deduplicate with `list(dict.fromkeys(out))`.
5. Cap at `_RESUME_SEARCH_MAX_TOKENS = 400` distinct token strings per résumé. This is
   higher than KB-009's 60-per-article cap because a full résumé body (50 KB after
   RSK-002's truncation) is orders of magnitude longer than an article title. 400 bounds
   DDB write amplification while maintaining recall for realistic résumé vocabularies.

Module-level constants (not env-driven — changing them requires an index rebuild):

```python
_RESUME_SEARCH_MAX_PREFIX_LEN: int = 8   # must match query-side prefix cap; mirrors
                                          # _MSG_SEARCH_MAX_PREFIX_LEN (messaging.py:2786)
_RESUME_SEARCH_MIN_TOKEN_LEN:  int = 3   # skip words shorter than 3 chars
_RESUME_SEARCH_MAX_TOKENS:     int = 400 # cap on distinct tokens per résumé
```

Example: résumé text containing `"kubernetes"` generates tokens
`"kub"`, `"kube"`, `"kuber"`, `"kubern"`, `"kuberne"`, `"kubernet"`, `"kubernete"`
(capped at 8) plus the full word `"kubernetes"` (length 10 > 8, so the 8-char prefix is
the longest stored). A query for `"kube"` will match this candidate.

## 4. API / Service Design

### 4.1 Service — `app/services/resume_search.py` (new file)

All functions are synchronous; the async router calls them in `asyncio.to_thread` where
needed (index writes are fast enough to inline in most cases; the migration helper uses
`asyncio.to_thread`).

#### `_build_resume_tokens(text: str) -> list[str]`

```python
def _build_resume_tokens(text: str) -> list[str]:
    words = re.findall(r"[a-z0-9]+", (text or "").lower())
    out: list[str] = []
    for word in words:
        if len(word) < _RESUME_SEARCH_MIN_TOKEN_LEN:
            continue
        for length in range(_RESUME_SEARCH_MIN_TOKEN_LEN,
                            min(len(word), _RESUME_SEARCH_MAX_PREFIX_LEN) + 1):
            out.append(word[:length])
    return list(dict.fromkeys(out))[:_RESUME_SEARCH_MAX_TOKENS]
```

Pure function; no I/O. Directly unit-tested.

#### `_write_resume_index(candidate_id: str, name: str, owner_sub: str, text: str) -> None`

```python
def _write_resume_index(
    candidate_id: str,
    name: str,
    owner_sub: str,
    text: str,
) -> None:
    tokens = _build_resume_tokens(text)
    if not tokens:
        return
    name_snippet = (name or "")[:80]
    ts = now_ts()
    with T.candidates.batch_writer() as batch:
        for token in tokens:
            batch.put_item(Item={
                "pk": f"RESUME_TOKEN#{token}",
                "sk": f"CANDIDATE#{candidate_id}",
                "candidate_id": candidate_id,
                "name_snippet": name_snippet,
                "owner_sub": owner_sub,
                "updated_at": ts,
            })
```

Uses `T.candidates.batch_writer()` — mirrors `_write_tag_index` at
`app/routers/newsfeed.py:444`. Best-effort: caller wraps in `try/except`; an index write
failure never blocks résumé upload or extraction. Called by RSK-002's
`extract_resume_text` after a successful extraction.

#### `_delete_resume_index(candidate_id: str, text: str) -> None`

```python
def _delete_resume_index(candidate_id: str, text: str) -> None:
    tokens = _build_resume_tokens(text)
    if not tokens:
        return
    with T.candidates.batch_writer() as batch:
        for token in tokens:
            batch.delete_item(Key={
                "pk": f"RESUME_TOKEN#{token}",
                "sk": f"CANDIDATE#{candidate_id}",
            })
```

Called before `_write_resume_index` on re-extract (delete old tokens first, then write new
ones), and from the candidate-delete path in CND-\* (best-effort `try/except`).

#### `search_resumes(q: str, *, owner_sub: str | None = None, limit: int = 25) -> list[ResumeSearchResultItem]`

Full algorithm:

1. Normalize `q`: `re.findall(r"[a-z0-9]+", q.lower())`, filter tokens `< 3` chars. Take
   at most the **first 3 tokens** to bound DDB read amplification (identical to KB-009
   §4.1 step 1).
2. If no valid tokens remain, return `[]` immediately — no DDB query issued.
3. For the first (primary) token: truncate to `_RESUME_SEARCH_MAX_PREFIX_LEN` chars, then
   `T.candidates.query(KeyConditionExpression=Key("pk").eq(f"RESUME_TOKEN#{token}"),
   Limit=200)`. Loop via `LastEvaluatedKey` until exhausted (CLAUDE.md "FilterExpression
   doesn't reduce page size" — token rows for a popular term like `"python"` can span
   multiple DDB pages of 200 rows each; all pages must be consumed before intersecting).
   Collect `(candidate_id, name_snippet, owner_sub, updated_at)` from every page.
4. For each additional token (tokens[1] and tokens[2] if present): repeat the query loop
   and **intersect** the candidate_id sets client-side — retain only IDs present in
   **all** token result sets (AND semantics, KB-009 §5.5).
5. If `owner_sub` is provided: filter the intersected set to only entries where
   `token_row["owner_sub"] == owner_sub`. Admin callers pass `owner_sub=None` to skip the
   filter.
6. Sort remaining candidates by `updated_at` descending (most recently indexed résumés
   first — a proxy for recency of the candidate record).
7. Take first `limit` results and return as `list[ResumeSearchResultItem]`.

The `owner_sub` field is stored on each token row (see §3.1), so owner-scope filtering
requires no additional DDB read beyond the token query itself.

#### `rebuild_resume_index() -> int` (migration helper, CLI-only)

Scans all `ATTACHMENT#{attachment_id}` rows on the `candidates` table via `LastEvaluatedKey`
loop (using `begins_with sk "ATTACHMENT#"` on each candidate partition or a full table scan
with a FilterExpression on `sk begins_with "ATTACHMENT#"`), reads `extracted_text`,
`extraction_status`, and the parent candidate's `name` and `owner_sub`, calls
`_write_resume_index` for each row where `extraction_status == "ok"` and `extracted_text`
is non-empty. Returns a count of résumés reindexed. Not exposed as an HTTP endpoint;
invoked via `scripts/rootctl` or a one-off admin script. Mirrors
`KbArticleService.rebuild_search_index` (KB-009 §8.2).

### 4.2 Wiring into RSK-002

`app/services/resume_extraction.py` (RSK-002) calls `_write_resume_index` inside
`extract_resume_text`, immediately after the successful `update_item` of the attachment
row:

```python
# Inside extract_resume_text(), after update_item succeeds:

    from app.services.resume_search import _write_resume_index
    _write_resume_index(candidate_id, candidate_name, owner_sub, stored_text)

    logger.exception("resume index write failed; continuing")
```

On re-extract: `extract_resume_text` fetches the previous `extracted_text` value from the
attachment row before updating it, then calls `_delete_resume_index(candidate_id, old_text)`
before writing the new text and calling `_write_resume_index` with the new text. This
delete-then-write pattern ensures stale tokens from the old résumé do not persist.

On candidate delete (CND-\*): the candidate deletion handler calls
`_delete_resume_index(candidate_id, old_text)` best-effort, reading `extracted_text` from
the attachment row before deleting the candidate record.

```python
@router.get("/ui/ats/candidates/search/resume", response_model=ResumeSearchOut)
def search_resumes_endpoint(
    q: str = Query(..., min_length=2, max_length=200),
    limit: int = Query(default=25, ge=1, le=50),
    all: bool = Query(default=False),
    session=Depends(require_ui_session),
    request: Request = None,
):
    if not S.ats_recruiting_enabled:
        raise HTTPException(404)
    user_sub = session["user_sub"]
    # Rate limit: 30 req / 60 s per user (same as global search, search.py:834)
    if not _bucket_limit(user_sub, "rl#resume_search", 30, 60):
        raise HTTPException(429, "Too many requests")
    # Owner scope
    owner_scope = None
    if not all:
        owner_scope = user_sub
    elif session["role"] < Role.ADMIN:
        raise HTTPException(403, "admin required for all=true")
    items = search_resumes(q, owner_sub=owner_scope, limit=limit)
    return ResumeSearchOut(
        items=items,
        query=q,
        total_estimate=len(items),
        has_more=len(items) >= limit,
    )
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Token write on extract vs. re-extract

At first extraction (`extraction_status` going from absent → `"ok"`): `_write_resume_index`
writes all token rows. On re-extract (operator triggers `POST
/ui/ats/candidates/{id}/resume/{attachment_id}/extract` again): `extract_resume_text`
reads the old `extracted_text` before updating the row, calls `_delete_resume_index` on the
old text, then calls `_write_resume_index` on the new text. This guarantees no stale token
rows survive a résumé replacement.

### 5.2 Stale token rows after candidate soft-delete

If `_delete_resume_index` fails (DDB unavailable, partial batch failure), stale
`RESUME_TOKEN#` rows may remain. `search_resumes` does not currently filter by candidate
`status` from the token row — token rows contain only `candidate_id`, `name_snippet`,
`owner_sub`, and `updated_at`. The recruiter who follows a stale result link to the
candidate detail page will receive a 404 (CND-002 enforces `status != "deleted"` on GET).
This is acceptable for a stale-index scenario; a future enhancement can store
`candidate_status` on the token row for pre-filter, or a scheduled scan can prune orphan
token rows. See §10.4 for the open question.

### 5.3 AND vs OR semantics

`search_resumes` AND-intersects: a résumé must contain **all** query tokens. A query
`"python kubernetes"` returns only candidates whose résumé contains both. This matches
`_search_tickets` in `search.py:401` (AND check `all(tok in haystack for tok in tokens)`
at `search.py:432`) and KB-009 §5.5.

### 5.4 Empty / sub-3-char query

If `re.findall(r"[a-z0-9]+", q.lower())` produces zero tokens with `len >= 3`, `search_resumes`
returns `[]` immediately with no DDB query. Example: `q="c++"` yields token `["c"]` which
is `< 3` chars → empty result. The endpoint's `min_length=2` constraint prevents trivially
empty strings, but single-character queries are handled gracefully.

### 5.5 Token cap and write amplification

A 50 KB résumé (RSK-002's `ATS_RESUME_EXTRACT_MAX_CHARS=50000` default) might contain
thousands of unique words. `_build_resume_tokens` caps at 400 distinct token strings;
`batch_writer()` flushes in 25-item chunks (boto3 default), so a maximum-cap write issues
at most 16 batch flushes. Each token row is a single DDB item (~200 bytes). Total write
volume per résumé: at most 400 items × 200 bytes = ~80 KB of DDB capacity, within the
1-minute indexing window of a résumé upload.

### 5.6 Pagination of query results

`LastEvaluatedKey` loops consume all pages for each token query before intersecting. For a
popular token like `"python"`, page count could be substantial. The `Limit=200` page size
limits per-page DDB reads; total pages consumed is bounded by the recruiter base size.
The result set is always bounded by `limit` (default 25, max 50) after intersection.

### 5.7 `batch_get_item` — not required

Unlike KB-009 §5.7 (which requires a `batch_get_item` to enrich article excerpts), RSK-003
stores enough display information (`name_snippet`, `owner_sub`, `updated_at`) directly on
the token row to build `ResumeSearchResultItem` without a second DDB round-trip. The
recruiter's UI can render a candidate list with name and a "View" link using
`candidate_id` alone. Full candidate detail is fetched on demand via CND-002.

### 5.8 Concurrent index writes (idempotency)

If RSK-002's `extract_resume_text` is called twice concurrently for the same
`(candidate_id, attachment_id)` (e.g. two simultaneous re-extract requests),
`batch_writer().put_item` is a full overwrite of each token row (DDB `PutItem` semantics —
last writer wins). No conditional expression is needed; duplicate writes are harmless and
result in token rows with the most recent `updated_at`.

### 5.9 `owner_sub` propagation

RSK-002's `extract_resume_text` receives `actor_sub` (the uploader) and passes it through
to `_write_resume_index` as `owner_sub`. On re-extract triggered by an admin, `actor_sub`
is the admin's sub — but the token row's `owner_sub` should remain the **original candidate
owner**, not the admin who triggered re-extraction. CND-003's attachment row stores the
owning recruiter's sub; `extract_resume_text` should read `owner_sub` from the candidate
META row (via `T.candidates.get_item(Key={"pk": f"CANDIDATE#{candidate_id}", "sk": "META"})`)
rather than using `actor_sub` directly. This ensures owner-scope searches work correctly
regardless of who triggered the extraction.

### 5.10 Rate limit fail-open

`_bucket_limit` at `rate_limit.py:60` returns `True` (allow) when the sessions table is
unavailable. The résumé-search endpoint uses this same fail-open posture: a DDB outage does
not block search, it simply stops enforcing the per-user cap. This matches the KB-009 §5.4
and global search `search.py:834` behaviors.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Single code path (SECOPS-007)

There is no `if S.dev_mode:` branch in RSK-003. All DDB operations (token writes, token
queries) go through `T.candidates` (the frozen handle wired by CND-001 at module import
time). Against DynamoDB Local (`DDB_ENDPOINT_URL=http://localhost:8001`, `AWS_ACCESS_KEY_ID=test`)
and against production DynamoDB the boto3 calls are structurally identical — no code
divergence. This mirrors the KB-009 §7.1 guarantee.

### 7.2 Idempotency

- `_write_resume_index`: `batch_writer().put_item` overwrites each token row completely
  (DDB `PutItem` is a full item replacement). Repeating with the same inputs produces
  identical DDB items and is safe.
- `_delete_resume_index`: `batch_writer().delete_item` is a no-op if an item does not exist.
- `search_resumes`: purely read-only; no side effects.
- `rebuild_resume_index`: calls `_write_resume_index` for each résumé — idempotent on
  any number of re-runs.

### 7.3 Authentication and authorization

- `GET /ui/ats/candidates/search/resume` requires `require_ui_session` (cookie + CSRF).
  Default behavior: owner-scoped to the requesting recruiter's candidates. Admin role
  required for `all=true`.
- Token rows are DDB-internal only. They are never exposed by any API endpoint. A query
  for `GET /ui/ats/candidates/RESUME_TOKEN#python` would 404 because the CND-002 GET
  handler looks up `pk=CANDIDATE#{id}` / `sk=META` — the `RESUME_TOKEN#` pattern never
  matches a candidate id.

### 7.4 Input sanitization

Query input passes through the endpoint's FastAPI `Query(min_length=2, max_length=200)`
constraint first. `search_resumes` then applies `re.findall(r"[a-z0-9]+", q.lower())` which
strips all punctuation, injection attempts, and Unicode sequences before any DDB call.
Token rows store only `candidate_id` (UUID), `name_snippet` (first 80 chars of a
recruiter-supplied name), `owner_sub`, and `updated_at` — no PII from the résumé body is
stored in the index.

### 7.5 PII posture

`extracted_text` (RSK-002) is stored on the candidates table with the same access controls
as the candidate record. RSK-003 token rows store no résumé content at all — only the
`candidate_id`, `name_snippet`, and metadata. This is consistent with the KB-009 §7.3
posture: token rows contain only identifiers and snapshots, never sensitive body content.

## 8. Backward Compatibility & Migration

### 8.1 Flag-off state (default)

With `ATS_RECRUITING_ENABLED=0` (the default):
- No token rows are written (`extract_resume_text` checks the flag before calling
  `_write_resume_index`).
- The search endpoint returns 404.
- `_search_candidates_resume` returns `_empty_section()`.
- `"candidates"` is absent from `ALLOWED_TYPES` in `search.py`.
- The existing `candidates` table schema is unchanged — `just restart` does not attempt to
  create any new tables or GSIs beyond what CND-001 already declares.
- All other platform files are byte-for-byte unchanged.

### 8.2 Cold-start index population

When RSK-003 is first deployed with `ATS_RECRUITING_ENABLED=1` against a `candidates` table
that already has résumé attachment rows (created by CND-003 + RSK-002 in a prior deployment),
no token rows exist. The one-time migration is:

1. Invoke `rebuild_resume_index()` via `scripts/rootctl` or a one-off admin script.
2. The helper scans all `pk=CANDIDATE#{id}` / `sk begins_with "ATTACHMENT#"` rows via a
   `LastEvaluatedKey` loop, reads `extracted_text` where `extraction_status == "ok"`,
   resolves `owner_sub` from the parent `META` row, and calls `_write_resume_index`.
3. In dev, `just restart` drops and recreates the table; résumé upload + extraction via
   CND-003 + RSK-002 repopulates the index automatically.
4. In prod, run the rebuild once before enabling public search; subsequent extractions
   maintain the index automatically.

### 8.3 No schema changes to existing tables

The `candidates` table receives new rows under the `RESUME_TOKEN#` prefix but no schema
changes. Existing GSI queries (`ByOwner`, `ByStatus`, `BySource`) filter on their
respective PK prefixes and never interact with `RESUME_TOKEN#` rows. The `TableDef` in
`scripts/local-ddb-init.py` is not modified by RSK-003.

## 10. Open Questions / Assumptions

1. **Token rows and soft-deleted candidates.** The current design does not store
   `candidate_status` on the token row. Stale rows from soft-deleted candidates are not
   filtered at search time; the recruiter follows the link and hits a 404 in CND-002. A
   future enhancement can either (a) store `is_active: bool` on the token row and filter
   at query time, or (b) schedule a daily scan-and-prune job. Decision deferred to CND-\*
   team.

2. **Body-text indexing depth.** RSK-003 indexes the full `extracted_text` (up to 50 KB,
   RSK-002's `ATS_RESUME_EXTRACT_MAX_CHARS`). For very long résumés, the 400-token cap
   means only the most common/unique tokens are stored. If recall for rare terms deep in
   long résumés becomes a complaint, `_RESUME_SEARCH_MAX_TOKENS` can be raised (requires
   an index rebuild via `rebuild_resume_index()`). Whether to surface this as an env-driven
   setting (`ATS_RESUME_SEARCH_MAX_TOKENS`) is left to the deployment team; the current
   module-constant approach matches KB-009 §6.2.

3. **Skill-tag vs. free-text search overlap.** RSK-001 stores skill assignments (structured
   tags, e.g. `"python"` with a proficiency weight); RSK-003 provides free-text résumé
   search. A recruiter query for `"python"` could match both. The two endpoints are
   deliberately separate: RSK-004 (skill-based search) uses the RSK-001 forward index; this
   endpoint uses the RSK-003 token index. Whether the UI should merge results or keep them
   separate (recommended: separate tabs/sections, same as KB global search) is a frontend
   concern.

4. **Owner assignment on re-extract.** §5.9 describes reading `owner_sub` from the
   candidate META row during re-extract to avoid incorrectly attributing the token row to
   the admin who triggered re-extraction. CND-001/CND-002 must store `owner_sub` on the
   META row; this spec assumes that field exists and is non-null. If CND-001's META row
   uses a different field name (e.g. `recruiter_sub`), RSK-003's implementation must align
   to the actual field name.

5. **`name_snippet` staleness.** The `name_snippet` stored on token rows is a snapshot at
   index-write time. If the candidate's name is updated after indexing, the snippet on
   existing token rows goes stale until the next re-extract (which is the only time
   `_write_resume_index` is called). A name-update hook (CND-\* update path) could call
   a lightweight `_update_resume_index_snippet(candidate_id, new_name)` helper that
   re-writes only the `name_snippet` and `updated_at` fields. This is a low-priority
   enhancement; the `candidate_id` is always current and the UI can fall back to fetching
   the live name from CND-002.
