# PIP-002 — Ranked, admin-configurable status workflow (status-config row)

**Ticket type:** Feature
**Priority:** P0
**Estimate:** 2 days
**Master gate:** `S.ats_pipeline_enabled` (`ATS_PIPELINE_ENABLED`, default `false`) — introduced in PIP-001
**Depends on:** PIP-001 (`T.ats_pipeline`, `_require_flag()`, master flag)

---

## 1. Summary & Goal

PIP-002 adds the canonical OpenCATS recruiting status workflow as an **admin-configurable, ranked, stored config row** on the `ats_pipeline` DynamoDB table introduced in PIP-001. The nine-step default ladder (`100 No-Contact → 200 Contacted → 300 Qualifying → 400 Submitted → 500 Interviewing → 600 Offered → 700 Not-in-Consideration → 800 Client-Declined → 900 Placed`) is baked in as a fallback so the system is functional from day one; admins can replace the ladder at any time without a code deployment.

This is modelled **exactly** on OPP-003 (`docs/suitecrm/specs/OPP-003.md`) — the sales-pipeline stage-config row — and delivers:

1. A `PIPELINE_STATUS_CONFIG#META` singleton row on the PIP-001 `ats_pipeline` table.
2. Service functions `get_status_config()`, `set_status_config()`, `resolve_status_rank()`, and `_default_status_config()`.
3. Two endpoints: `GET /ui/ats/pipeline/statuses` (any session) and `PUT /ui/admin/ats/pipeline/statuses` (ADMIN/ROOT only).
4. A `feature-status` endpoint that intentionally skips `_require_flag()` so the frontend can conditionally render the sidebar with the flag off.
5. Pydantic models `PipelineStatusItemIn/Out` and `PipelineStatusConfigIn/Out` appended to `app/models.py`.

Everything is additive and default-OFF. With `ATS_PIPELINE_ENABLED=false` (the default), no new route is reachable, no DDB write can occur, and every byte of existing platform behavior is unchanged.

## 3. Data Model

### 3.1 Status config row — reuses `T.ats_pipeline` (no new table)

A single new row type is appended to the `ats_pipeline` single-table introduced by PIP-001. No new DynamoDB table, no new GSI, and no `attr_types` change is required for this row.

| Attribute | DDB type | Value |
|---|---|---|
| `pk` | S | `"PIPELINE_STATUS_CONFIG"` — literal, outside the `USER#` namespace |
| `sk` | S | `"META"` — singleton per deployment |
| `statuses` | S | JSON-encoded ordered list (see element schema below) |
| `updated_at` | N | Integer Unix seconds via `now_ts()` |
| `updated_by_sub` | S | `user_sub` of the admin who last wrote the row |

`statuses` is persisted as a JSON string (not a DynamoDB List) to preserve element order and allow atomic full-replacement with a single unconditional `put_item`, identical to OPP-003 §3.1.

**Status element schema** (decoded Python dataclass / Pydantic shape):

```python
{
    "status_key": str,     # e.g. "400_submitted" — unique identifier
    "label": str,          # Display label, max 80 chars, e.g. "Submitted"
    "rank": int,           # OpenCATS numeric weight: 100, 200, … 900 (or custom)
    "order": int,          # Column position, 0-based, ascending for Kanban rendering
    "is_submitted": bool,  # At most one True per config — triggers submit-to-client action
    "is_placed": bool,     # Exactly one True per config — triggers placement record
    "is_terminal": bool,   # True for stages that end the pipeline (e.g. 700/800/900)
    "color": str | None,   # Optional "#RRGGBB" for Kanban column header
}
```

**Default ladder** (returned by `_default_status_config()` when no admin write has occurred):

| status_key | label | rank | order | is_submitted | is_placed | is_terminal |
|---|---|---|---|---|---|---|
| `100_no_contact` | No Contact | 100 | 0 | false | false | false |
| `200_contacted` | Contacted | 200 | 1 | false | false | false |
| `300_qualifying` | Qualifying | 300 | 2 | false | false | false |
| `400_submitted` | Submitted | 400 | 3 | **true** | false | false |
| `500_interviewing` | Interviewing | 500 | 4 | false | false | false |
| `600_offered` | Offered | 600 | 5 | false | false | false |
| `700_not_in_consideration` | Not in Consideration | 700 | 6 | false | false | **true** |
| `800_client_declined` | Client Declined | 800 | 7 | false | false | **true** |
| `900_placed` | Placed | 900 | 8 | false | **true** | **true** |

### 3.2 `scripts/local-ddb-init.py` — no change required

The `PIPELINE_STATUS_CONFIG#META` row has no numeric GSI key; its `updated_at` is a plain item attribute (not a GSI sort key), so no additional `attr_types` entry is required beyond whatever PIP-001 already declared for the table. The PIP-001 `TableDef` for `ats_pipeline` needs only `attr_types={}` (or an entry only if a future ticket adds a numeric GSI sort key to this table). `just restart` recreates the table; the config row is written on first `PUT /ui/admin/ats/pipeline/statuses`.

### 3.3 Pydantic models appended to `app/models.py`

Placed adjacent to the PIP-001 `PipelineEntryOut` / `PipelineEntryCreateIn` models:

```python
class PipelineStatusItemIn(BaseModel):
    status_key: str = Field(..., min_length=1, max_length=80)
    label: str = Field(..., min_length=1, max_length=80)
    rank: int = Field(..., ge=0)
    order: int = Field(ge=0, default=0)
    is_submitted: bool = False
    is_placed: bool = False
    is_terminal: bool = False
    color: Optional[str] = Field(None, max_length=7)  # "#RRGGBB"

class PipelineStatusConfigIn(BaseModel):
    statuses: List[PipelineStatusItemIn]

    @model_validator(mode="after")
    def _validate_constraints(self) -> "PipelineStatusConfigIn":
        # Enforced here (422 at model boundary) AND re-enforced in service (400)
        keys = [s.status_key for s in self.statuses]
        if len(keys) != len(set(keys)):
            raise ValueError("duplicate_status_key")
        placed_count = sum(1 for s in self.statuses if s.is_placed)
        if placed_count != 1:
            raise ValueError("exactly_one_is_placed_required")
        submitted_count = sum(1 for s in self.statuses if s.is_submitted)
        if submitted_count > 1:
            raise ValueError("at_most_one_is_submitted_allowed")
        if not (1 <= len(self.statuses) <= 20):
            raise ValueError("statuses_count_out_of_range")
        return self

class PipelineStatusItemOut(BaseModel):
    status_key: str
    label: str
    rank: int
    order: int
    is_submitted: bool
    is_placed: bool
    is_terminal: bool
    color: Optional[str]

class PipelineStatusConfigOut(BaseModel):
    statuses: List[PipelineStatusItemOut]
    updated_at: Optional[int]
    updated_by_sub: Optional[str]
```

`PipelineStatusConfigIn`'s root validator enforces:
- 1–20 statuses (422 `statuses_count_out_of_range` if violated).
- Unique `status_key` values (422 `duplicate_status_key`).
- **Exactly one** `is_placed=True` (422 `exactly_one_is_placed_required`).
- **At most one** `is_submitted=True` (422 `at_most_one_is_submitted_allowed`; zero is legal so early pipelines need not designate a submitted stage yet).

Pydantic raises `ValueError` → FastAPI 422. The service `_validate_status_config()` re-checks and raises `HTTPException(400, detail={"code": "invalid_status_config", "reason": "..."})` as defence-in-depth, consistent with OPP-003 §4.1.

## 4. API / Service Design

### 4.1 Service additions to `app/services/ats_pipeline.py`

All functions live in the same service file created by PIP-001, appended below the existing `add_to_pipeline` / `list_pipeline_for_job` / `remove_from_pipeline` functions. Each calls `_require_flag()` at entry.

#### `_default_status_config() -> PipelineStatusConfigOut`

Internal helper (no `_require_flag()` call). Constructs and returns the nine-row default ladder hard-coded above. Called by `get_status_config()` whenever the DDB row is absent.

#### `get_status_config() -> PipelineStatusConfigOut`

```python
def get_status_config() -> PipelineStatusConfigOut:
    _require_flag()
    item = T.ats_pipeline.get_item(
        Key={"pk": "PIPELINE_STATUS_CONFIG", "sk": "META"}
    ).get("Item")
    if not item:
        return _default_status_config()
    statuses = json.loads(item["statuses"])
    return PipelineStatusConfigOut(
        statuses=[PipelineStatusItemOut(**s) for s in statuses],
        updated_at=int(item.get("updated_at", 0)) or None,
        updated_by_sub=item.get("updated_by_sub"),
    )
```

Returns a well-formed response even before any admin write. Never errors (beyond 503 when flag is off).

#### `_validate_status_config(data: PipelineStatusConfigIn) -> None`

Internal. Raises `HTTPException(400, detail={"code": "invalid_status_config", "reason": reason})` for the same constraints the model validator checks. Reasons: `"exactly_one_is_placed_required"`, `"at_most_one_is_submitted_allowed"`, `"duplicate_status_key"`, `"statuses_count_out_of_range"`. This layer is defence-in-depth against callers who bypass Pydantic (e.g., direct service calls in tests).

#### `set_status_config(admin_sub: str, data: PipelineStatusConfigIn) -> PipelineStatusConfigOut`

```python
def set_status_config(admin_sub: str, data: PipelineStatusConfigIn) -> PipelineStatusConfigOut:
    _require_flag()
    _validate_status_config(data)
    now = now_ts()
    payload = {
        "pk": "PIPELINE_STATUS_CONFIG",
        "sk": "META",
        "statuses": json.dumps([s.model_dump() for s in data.statuses]),
        "updated_at": now,
        "updated_by_sub": admin_sub,
    }
    T.ats_pipeline.put_item(Item=payload)
    submitted_key = next(
        (s.status_key for s in data.statuses if s.is_submitted), None
    )
    placed_key = next(s.status_key for s in data.statuses if s.is_placed)
    audit_event(
        "ats_status_config.updated",
        admin_sub,
        None,
        status_count=len(data.statuses),
        submitted_key=submitted_key,
        placed_key=placed_key,
    )
    return get_status_config()
```

Full-replacement semantics: the entire `statuses` list is written atomically via unconditional `put_item`. Two identical PUTs produce identical state. `updated_at` stamps the last write; `updated_by_sub` gives traceability (OPP-003 §7.2).

#### `resolve_status_rank(status_key: str) -> int`

```python
def resolve_status_rank(status_key: str) -> int:
    config = get_status_config()
    for s in config.statuses:
        if s.status_key == status_key:
            return s.rank
    return 0   # Unknown status → rank 0 (PIP-003 caller already validates before calling)
```

Used by PIP-003 `change_status` to denormalize `status_rank` onto the pipeline-entry row without a second full config fetch.

router_admin = APIRouter(prefix="/ui/admin/ats", tags=["ats-pipeline-admin"])


# Declared BEFORE any /{...} dynamic segments to prevent shadowing
@router.get("/statuses", response_model=PipelineStatusConfigOut)
async def list_pipeline_statuses(
    ctx: dict = Depends(require_ui_session),

    return get_status_config()


@router_admin.put("/pipeline/statuses", response_model=PipelineStatusConfigOut)
async def update_pipeline_statuses(
    body: PipelineStatusConfigIn,
    ctx: dict = Depends(require_ui_session),

    if normalize_role(ctx.get("role")) not in {Role.ADMIN, Role.ROOT}:
        raise HTTPException(403, detail={"code": "admin_role_required"})

@router.get("/feature-status")
async def pipeline_feature_status() -> dict:

PIP-008 must observe this same ordering when mounting all PIP routes.

## 5. Detailed Behavior & Edge Cases

### 5.1 Default config fallback

`GET /ui/ats/pipeline/statuses` returns a valid `PipelineStatusConfigOut` even before any admin has called `PUT /ui/admin/ats/pipeline/statuses`. `_default_status_config()` synthesizes the nine-row ladder at runtime from a hard-coded constant in `app/services/ats_pipeline.py`. `updated_at` and `updated_by_sub` are `None` on the default response. The frontend Kanban (PIP-009) must never assume the endpoint errors on a fresh installation.

### 5.2 Validation sequence on PUT

1. FastAPI deserializes `PipelineStatusConfigIn`; the `@model_validator(mode="after")` runs. Constraint violation → 422.
2. Handler checks `normalize_role(ctx.get("role"))` → 403 if not ADMIN/ROOT.
3. `set_status_config` calls `_validate_status_config(data)` → 400 `invalid_status_config` on any violation (defence-in-depth).
4. On success, unconditional `put_item` → `audit_event`.

### 5.3 Full-replacement semantics and concurrent writes

`PUT` is idempotent: sending the same list twice produces identical stored state. Two admins writing simultaneously race at `put_item`; last write wins. No optimistic concurrency control is added (stage-config writes are infrequent, admin-only, and the window for conflict is small — identical to OPP-003 §5.4). `updated_at` and `updated_by_sub` provide an audit trail for diagnosing collisions.

### 5.4 Custom `status_key` values

`PUT /ui/admin/ats/pipeline/statuses` does not restrict `status_key` values to the default ladder keys. Admins may define custom stages (e.g., `"350_phone_screen"`) as long as the uniqueness, count, and `is_placed`/`is_submitted` constraints pass. Pre-existing pipeline entries that carry a `status` value removed by an admin PUT are not automatically migrated; they retain the old value indefinitely. `change_status` (PIP-003) validates the *incoming* `new_status` against the live config, so stale entries with orphaned status values can be read back but cannot advance to another non-existent status. PIP-009's Kanban renders an "Unknown" overflow column for orphaned values (OPP-003 §5.2 / §10 Q3 pattern).

### 5.5 Zero `is_submitted` stages

A config with zero `is_submitted=True` entries is valid (at most one is allowed, not exactly one). In that case `get_status_config()` returns `submitted_key=None` and `PIP-005 submit_to_client` must handle `None` gracefully — it logs a warning and skips the status advance (the email send and timeline write still occur).

### 5.6 `resolve_status_rank` called by PIP-003

`resolve_status_rank(status_key)` reads `get_status_config()` on every call. This is one DDB `get_item` per call, acceptable for a low-cardinality config row. If performance becomes a concern a later ticket may add an in-process `functools.lru_cache` with a short TTL; that is out of scope here.

### 5.7 `feature-status` when flag is off and router is unmounted

If the router is not mounted (flag off), `GET /ui/ats/pipeline/feature-status` returns a FastAPI 404. The frontend must treat a 404 response on this endpoint as `{"enabled": false}` — identical to the `{"enabled": false}` response received when the flag is on but off internally. PIP-009 should handle both outcomes.

### 5.8 Admin role verification detail

`normalize_role(ctx.get("role"))` at `app/auth/roles.py:48` returns `Role.USER` for any unrecognized/missing value. The role is extracted from the HS256 `ui_access_token` JWT cookie by `require_ui_session` (see `app/auth/deps.py:109-122` `_extract_role_from_claims`; the function spans lines 109–122, not 109–117). Elevation requires a new cookie issuance; the role cannot be spoofed via a request header.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No `dev_mode` branches

`get_status_config()` and `set_status_config()` contain zero `if S.dev_mode` branches. In dev, `T.ats_pipeline` is backed by DynamoDB Local (port 8001); in prod by real DynamoDB. The `_FloatSafeTable` proxy (`app/core/tables.py:29`) handles `Decimal` coercion identically in both environments. `json.loads`/`json.dumps` on the `statuses` attribute work identically in both. SECOPS-007 is fully satisfied.

### 7.2 Idempotency

`set_status_config` uses an unconditional `put_item` (no `ConditionExpression`). Two identical PUTs produce identical DDB state. A third identical PUT will differ only in `updated_at` (a new timestamp). This is acceptable for an infrequent, admin-only config operation (OPP-003 §7.2).

### 7.3 Admin authorization

`PUT /ui/admin/ats/pipeline/statuses` enforces `normalize_role(ctx.get("role")) in {Role.ADMIN, Role.ROOT}` **after** `require_ui_session` resolves the session. The role is sourced from the HS256 `ui_access_token` JWT cookie (`app/auth/deps.py:109-117`), server-signed with `UI_ACCESS_TOKEN_SECRET`. A USER-role context receives 403 `admin_role_required`; an unauthenticated request receives 401 from `require_ui_session`.

### 7.4 Config as shared mutable state

`PIPELINE_STATUS_CONFIG#META` is a single deployment-wide row, not per-recruiter. Any admin can overwrite any other admin's config. `updated_by_sub` + `updated_at` give traceability; the `audit_event` call records the change in `T.alerts`. No per-recruiter config variant is planned (consistent with OPP-003 §10 Q2 multi-tenant stance).

### 7.5 CSRF

`PUT /ui/admin/ats/pipeline/statuses` is a non-GET cookie-auth request. `require_ui_session` at `app/services/sessions.py:330` enforces the `x-csrf-token` header matching the session's stored `csrf_token` and the `ui_csrf` cookie value. The frontend `api/client.ts` attaches the CSRF token automatically on every non-GET request.

### 7.6 No money-out path

No billing, wallet, or ledger writes occur in PIP-002. The billing primitives (`app/services/billing_shared.py`, `app/routers/billing.py`) are untouched.

### 7.7 Input sanitization

`status_key` (max 80 chars), `label` (max 80 chars), and `color` (max 7 chars, `#RRGGBB`) are bounded by Pydantic `Field`. An unbounded list is capped at 20 items. These bounds prevent oversized DDB writes and protect downstream label rendering.

## 8. Backward Compatibility & Migration

### 8.1 Pipeline entries written by PIP-001

Pipeline entry rows created by PIP-001 carry `status="100_no_contact"` (the default). After PIP-002 ships and before any admin PUT, `get_status_config()` returns the default ladder, so `"100_no_contact"` is a valid key and `resolve_status_rank("100_no_contact")` returns `100`. No existing rows are affected.

If an admin later PUTs a config that omits `"100_no_contact"`, existing entries retain the value indefinitely. PIP-003 `change_status` validates the *incoming* `new_status` against the live config (not the current stored status), so stale orphaned values do not block reading; they are visible in the Kanban "Unknown" column.

### 8.2 No DDB schema migration

The `PIPELINE_STATUS_CONFIG#META` row uses only the existing `pk`/`sk` primary keys of the `ats_pipeline` table (from PIP-001). No new GSIs or attribute definitions are required. `just restart` recreates the table from scratch; the config row is absent on a fresh table and `_default_status_config()` handles this gracefully.

### 8.3 `app/models.py` additive-only

`PipelineStatusItemIn/Out` and `PipelineStatusConfigIn/Out` are appended to `app/models.py`. No existing model is modified. All consumers of existing models continue to work byte-for-byte.

### 8.4 PIP-003 forward dependency on `resolve_status_rank`

`resolve_status_rank` is introduced in this ticket and called by PIP-003 `change_status`. PIP-003 depends on PIP-002; the build order graph in `ATS_PIPELINE_TICKETS.md` §Dependency graph reflects this. Until PIP-003 is merged, `resolve_status_rank` is unused but present.

## 10. Open Questions / Assumptions

**Q1. Should `is_submitted` be required (exactly one, not at most one)?**
*Assumption:* At most one is the correct constraint. Early ATS deployments may not yet have a formal "submit to client" stage. The `submit_to_client` action in PIP-005 skips the status advance (with a warning) if `is_submitted` is absent from the config. A future enforcement policy could upgrade to exactly-one via an optional `ats_pipeline_require_submitted_stage` flag.

**Q2. Should the config row be per-recruiter or per-team rather than deployment-wide?**
*Assumption:* Deployment-wide (one `PIPELINE_STATUS_CONFIG#META` row). Multi-recruiter teams at the same deployment share one workflow, consistent with OpenCATS's single-config model and the OPP-003 §10 Q2 stance. Per-team config (keyed on `PIPELINE_STATUS_CONFIG#{team_id}`) is a future extension if needed.

**Q3. Should `rank` be forced to be unique across statuses?**
*Assumption:* No. Two stages may share the same rank (e.g., `700_not_in_consideration` and `800_client_declined` both with `rank=700` if an admin wants them peer). `order` drives Kanban column ordering; `rank` drives progress denormalization and is advisory, not a key. A uniqueness constraint would be an unnecessary restriction for custom pipelines.

**Q4. What happens to pipeline entries when an admin removes a status that entries currently hold?**
*Assumption:* No automatic migration. Entries retain the orphaned `status` value. `change_status` (PIP-003) only validates the *new* status, so entries can stay at the orphaned value indefinitely. The Kanban shows them in an "Unknown" overflow column. A future "status cleanup" admin endpoint is out of scope.

**Q5. Should `GET /ui/ats/pipeline/statuses` be public (no session)?**
*Assumption:* No. It requires `require_ui_session` to prevent anonymous probing of the platform's recruiting configuration, consistent with OPP-003 §10 Q5 and all other platform config endpoints. The public career portal (a future PRT/CMP ticket) fetches only job-order data, not the internal pipeline status workflow.
