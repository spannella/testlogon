# JOB-005 — Openings-remaining-vs-placed counter + placement hooks

**Ticket cluster:** ATS / Recruiting — Tier 1 Core Entity: Job Order
**Priority:** P1  **Estimate:** 2d  **Type:** Feature (counter + forward-compat hook)
**Source:** `docs/opencats/ATS_JOB_ORDERS_TICKETS.md` §JOB-005 + `docs/opencats/OPENCATS_GAP_ANALYSIS.md` §B

## 1. Summary & Goal

Every Job Order in OpenCATS displays an `openings_remaining` figure: the number of seats
still available to fill, computed as `openings − placed_count`. When the pipeline
(candidate↔job-order junction, future PIPE-* cluster) moves a candidate to the `Placed`
status it increments `placed_count` by one; reversing that placement decrements it. When
`openings_remaining` reaches zero on an `active` job the system auto-advances the order's
status to `full` — exactly the OpenCATS behavior that "a position is full when all seats
are filled".

This ticket ships the **counter primitives, the derived projection, and the pipeline hook
contract** without importing or depending on pipeline code:

1. `adjust_placed_count(job_id, delta, ...)` — an atomic `ADD placed_count :delta`
   `update_item` with a non-negative clamp `ConditionExpression` + auto-`full` side effect.
2. `get_openings_summary(job_id)` — a lightweight read returning `{openings,
   placed_count, openings_remaining}`.
3. `GET /ui/ats/job-orders/{job_id}/openings` — a read-only endpoint projecting the
   summary; no public mutate endpoint.
4. `JobOrderOut.placed_count` / `openings_remaining` populated on every existing read
   path (get single, all list views).
5. A documented pipeline hook contract that PIPE-* will call when it ships.

The structural dependency chain is JOB-001 (models + table) → JOB-002 (CRUD service +
`set_status`) → JOB-003 (router) → this ticket. `placed_count` and `openings_remaining`
are already declared as fields on `JobOrderOut` (JOB-001, `app/models.py`) and defaulted
to `0` / derived by JOB-002's `_item_to_out`; JOB-005 adds the write side and the hook.

### 2.3 OpenCATS counter semantics

In the OpenCATS source the `num_positions` (openings) field is set on the job order at
creation. The `getNumPlacements()` query counts rows in the `candidate_joborder` junction
table where `status = 'Placed'`. The displayed `Openings Remaining` is
`max(num_positions - getNumPlacements(), 0)`. When the pipeline moves a candidate to
`Placed`, the frontend and background tasks re-derive this value. OpenCATS does NOT write
an explicit `placed_count` field back to the job order — the count is a live join.

**testlogon departs intentionally:** because testlogon's candidate↔job-order pipeline
(PIPE-*) is a separate cluster not yet built, using a live join would require PIPE-* to
ship before `openings_remaining` is ever non-zero. Instead, JOB-005 writes a materialized
`placed_count` counter directly on the META row via an atomic `ADD`, which the pipeline
increments/decrements when it ships. This is the same materialized-counter pattern used
for `follower_count` / `following_count` in `app/services/social.py:531-565`.

## 3. Data Model

### 3.1 No new DynamoDB tables

JOB-005 adds one attribute to the existing `job_orders` META row. The table and all five
GSIs were defined in JOB-001. No `TableDef`, no `attr_types` addition, no new table
handle is needed.

### 3.2 `placed_count` attribute on the META row

| Attribute | DDB type | Notes |
|---|---|---|
| `placed_count` | N | Materialized counter; starts at `0` (written by JOB-002 `create_job_order`); atomically mutated by `adjust_placed_count`; read by `_item_to_out` via `int(item.get("placed_count", 0))` |

`placed_count` is **not** a GSI key — it is a plain numeric attribute on the META row. It
is not a sort key on any index; therefore no `attr_types` entry is required beyond what
JOB-001 already declares.

**Absent vs. zero:** JOB-002 writes `placed_count=0` at creation, so the attribute is
present on all rows created after JOB-002 merges. Rows written by tests or tooling before
JOB-002 shipped (none exist in prod; this is a new table) would have the attribute absent.
`_item_to_out` already handles this via `int(item.get("placed_count", 0))` — no migration
step needed.

### 3.3 `openings_remaining` — derived, never stored

`openings_remaining` is always `max(openings - placed_count, 0)` computed by `_item_to_out`
at read time. It is **not written to DynamoDB**. Because it is never stored, it never
diverges from `openings − placed_count` and never requires a backfill if either operand
changes. The `JobOrderOut` field was declared in JOB-001 specifically to make this
projection stable from day one.

### 3.4 Auto-`full` side-effect state

When `adjust_placed_count` observes that the post-increment `placed_count >= openings`
and the current `status == "active"`, it calls `set_status(actor_sub, job_id, "full")`.
This writes a second `update_item` to the META row (the `status` field), bumps
`updated_at`, and emits the `job_order.status_changed` audit event. No additional DDB
attributes are introduced; the state is fully captured by the existing `status` field.

The auto-`full` logic fires only when:
- `openings > 0` (a job with `openings=0` has no quota and never auto-fills — see §5.3)
- Current `status == "active"` (a job already `on_hold`, `full`, `closed`, or `canceled`
  does not re-transition)
- `placed_count` after the increment is `>= openings`

### 4.1 Service additions (`app/services/job_orders.py`)

#### 4.1.1 `adjust_placed_count`

```python
def adjust_placed_count(
    job_id: str,
    delta: int,
    *,
    actor_sub: str,
    candidate_ref: Optional[str] = None,
) -> JobOrderOut:
    """
    Atomically add `delta` (+1 or -1) to `placed_count` on the META row,
    clamped at >= 0. Auto-advances status to "full" when openings_remaining
    reaches 0 on an active order.

    Args:
        job_id:        The job order to update (resolved via GSI_DIRECT).
        delta:         +1 (candidate placed) or -1 (placement reversed).
                       Any integer is accepted but callers use ±1.
        actor_sub:     Sub of the actor triggering the change (pipeline service,
                       or admin performing a manual correction).
        candidate_ref: Opaque reference to the candidate (e.g., candidate_id);
                       stored in the audit event for traceability. None before
                       PIPE-* ships.

    Returns:
        Fresh JobOrderOut with updated placed_count and openings_remaining.

    Raises:
        HTTPException(404):  job_id not found or soft-deleted.
        HTTPException(409):  delta would push placed_count below 0
                             (code: "placed_count_underflow").
        HTTPException(503):  either ATS flag is off.
    """
```

**Implementation steps:**

1. Call `_require_flag()`.
2. Fetch current item via `get_job_order(job_id)` to read `pk`, `sk`, `openings`, current
   `status`, and current `placed_count`. (This is a read through `GSI_DIRECT` → the META
   row's full item.)
3. **Underflow guard:** if `delta < 0` and `current_placed_count + delta < 0`, raise
   `HTTPException(409, detail={"code": "placed_count_underflow", "placed_count": current_placed_count, "delta": delta})`.
   This is a pre-flight check; a concurrent increment between this check and the write
   cannot cause underflow on the result (see §5.2 for the atomic path).
4. Perform the atomic update on the META row:
   ```python
   T.job_orders.update_item(
       Key={"pk": meta_pk, "sk": meta_sk},
       UpdateExpression="ADD placed_count :d SET updated_at = :ts",
       ConditionExpression=Attr("placed_count").gte(-delta) if delta < 0 else Attr("pk").attribute_exists(),
       ExpressionAttributeValues={":d": delta, ":ts": now_ts()},
   )
   ```
   For a decrement (`delta < 0`), `ConditionExpression=Attr("placed_count").gte(abs(delta))`
   (equivalently `placed_count >= -delta`) ensures the counter never goes negative at the
   DynamoDB level. On `ConditionalCheckFailedException` for a decrement, raise
   `HTTPException(409, detail={"code": "placed_count_underflow"})`.
   For an increment (`delta > 0`), the condition is `attribute_exists(pk)` (item must
   exist; a non-existent item cannot satisfy an ADD). `get_job_order` above already
   guards existence, but the condition prevents a race with `delete_job_order`.
5. Read the updated item back via `get_job_order(job_id)` to get the post-write
   `placed_count`.
6. **Auto-`full` check:** if post-update `openings > 0` and
   `post_placed_count >= openings` and current `status == "active"`, call
   `set_status(actor_sub, job_id, "full")`. `set_status` emits the
   `job_order.status_changed` audit event itself; `adjust_placed_count` does not emit
   a separate status-change event.
7. Emit `audit_event("job_order.placement_adjusted", actor_sub, None, job_id=job_id, delta=delta, candidate_ref=candidate_ref, placed_count=post_placed_count)`.
8. Return `get_job_order(job_id)` (final consistent read after any status side-effect).

**Note on `delta` type:** The function signature accepts `int` (any sign). The pipeline
will always call with `+1` or `-1`. A larger delta (bulk correction) is valid but unusual;
the underflow guard handles it correctly for any negative value.

## 5. Detailed Behavior & Edge Cases

### 5.1 Atomic counter guarantee

DynamoDB's `ADD` operation on a numeric attribute is **atomic at the item level**: no two
concurrent `ADD placed_count :1` calls can produce a lost update. The final value is always
`initial + (number of successful increments)`. This is distinct from the read-modify-write
cycle used by `update_job_order` (which uses optimistic concurrency on `updated_at`) —
`adjust_placed_count` does not need the `updated_at` guard because `ADD` itself is atomic.

The `updated_at = now_ts()` written alongside the `ADD` in the same `update_item` call
is a best-effort timestamp: two concurrent calls may both write `updated_at` with slightly
different values, but the `placed_count` total will always be correct. This is the same
trade-off as `follower_count` in `app/services/social.py:531-544`.

### 5.2 Underflow guard — pre-flight vs. atomic ConditionExpression

The underflow guard uses two layers:

1. **Pre-flight check:** `if delta < 0 and current_placed_count + delta < 0 → 409`. This
   provides an early, readable error before reaching DynamoDB.
2. **Atomic ConditionExpression:** `Attr("placed_count").gte(abs(delta))` in the
   `update_item` call. If a concurrent increment fires between the pre-flight read and
   the write, the counter could have changed — but the `ADD` with the condition still
   protects against underflow at the DynamoDB level. On `ConditionalCheckFailedException`,
   the service raises the same 409.

This two-layer approach mirrors the pattern at `app/services/social.py:552-565` (pre-flight
`Attr(field).gt(0)` → `ConditionalCheckFailedException` catch).

### 5.3 `openings=0` — no auto-`full` transition

A job order created with `openings=0` has no headcount quota (e.g., an open-ended
contractor pool). The auto-`full` logic checks `openings > 0` before firing — a job with
`openings=0` can accumulate `placed_count > 0` without ever auto-transitioning to `full`.
The recruiter must manually set the status to `full` via `POST /{job_id}/status` (JOB-003)
when they decide the pool is closed. This matches the OpenCATS behavior where a zero-
openings order is an administrative edge case.

### 5.4 Concurrent auto-`full` race

If two pipeline calls simultaneously increment `placed_count` from `openings - 1` to
`openings` on an `active` order, both will observe `placed_count >= openings` after their
respective writes and both will call `set_status(actor_sub, job_id, "full")`. The second
call hits `set_status` with `current_status == "full"` and `new_status == "full"` — which
is the same-status no-op path in JOB-002 (returns current item, no audit emitted, no
DDB write). The result is correct: the job advances to `full` exactly once.

### 5.5 Decrement below `openings` — status stays `full`

If a job is `full` and a candidate placement is reversed (`adjust_placed_count(-1)`), the
counter drops to `openings - 1` and `openings_remaining` becomes `1`. The status remains
`full` — `adjust_placed_count` does **not** automatically revert `full → active` on a
decrement. Reverting a `full` status requires an explicit `POST /{job_id}/status` with
`{"status": "active"}` from a recruiter. This is intentional: the recruiter should make
a conscious decision to re-open a position, not have the system do it automatically when
one candidate drops out.

### 5.6 Non-`active` status — no auto-transition on increment

If the order is `on_hold` and a placement arrives via `adjust_placed_count(+1)`, the counter
increments but no status auto-transition fires (`on_hold → full` is not in the auto-`full`
check, only `active → full`). The order stays `on_hold` even if `openings_remaining` hits
zero. This is consistent with the state-machine in JOB-002 where `on_hold → full` is
explicitly disallowed (see JOB-002 §10 OQ-1).

### 5.7 `delete_job_order` and `placed_count` integrity

`delete_job_order` (JOB-002) sets `deleted_at` on the META row but does not reset
`placed_count`. The pipeline (PIPE-*) must not call `adjust_placed_count` on a soft-deleted
job order — `get_job_order` (called inside `adjust_placed_count`) will raise 404 for any
job with `deleted_at` set, rejecting the increment before any DDB mutation occurs.

### 5.8 `actor_sub` on pipeline-initiated adjustments

When PIPE-* calls `adjust_placed_count`, it passes the pipeline-event actor (the recruiter
who changed the candidate's status, or a system sub for automated transitions). The audit
event carries this sub verbatim — the pipeline should not pass a generic service account
sub when a human action triggered the placement.

### 5.9 Large deltas (bulk correction)

`adjust_placed_count` accepts any `delta`. If a bulk correction is needed (e.g., `+3` to
fix a data import error), the caller passes a larger delta. The underflow guard handles
`delta < 0 AND abs(delta) > placed_count` correctly. Auto-`full` fires if the result
satisfies `placed_count >= openings AND status == "active"` regardless of `delta` size.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

There are **no `if S.dev_mode` branches** anywhere in `app/services/job_orders.py`. The
atomic `ADD` operation goes through the same DynamoDB API call in dev (DynamoDB Local at
`http://localhost:8001`, `AWS_ACCESS_KEY_ID=test`) and prod (real DynamoDB with IAM). The
`_safe_table` wrapper at `app/core/tables.py:65-66` handles `float → Decimal` coercion
transparently. No mock path, no dev shortcut.

### 7.2 Idempotency

`adjust_placed_count` is **not idempotent**: calling it twice with `delta=+1` increments
`placed_count` by two. The pipeline (PIPE-*) is responsible for ensuring each candidate's
transition to/from `Placed` triggers exactly one `adjust_placed_count` call. It should
use a conditional put or a compare-and-swap on the pipeline row (its own DDB item) to
prevent double-processing on retry. JOB-005 does not add an idempotency key to
`adjust_placed_count` because idempotency for pipeline state-machine events is the
pipeline's invariant to enforce.

`get_openings_summary` is always idempotent (read-only).

### 7.3 Security

**No public mutate endpoint.** `adjust_placed_count` is accessible only as a Python
import by the pipeline service (`app.services.job_orders.adjust_placed_count`). There is
no HTTP POST / PATCH endpoint to mutate `placed_count` directly. An attacker with a valid
session cannot forge a counter increment via the REST API.

**`actor_sub` provenance.** Every call to `adjust_placed_count` carries an `actor_sub`
derived from the pipeline event's triggering user (as extracted by `require_ui_session` at
the pipeline router level). The service never derives `actor_sub` from the `candidate_ref`
or from any field on the job order item.

**`candidate_ref` is opaque.** The audit event stores `candidate_ref` as a string. It is
not resolved, not validated against any candidate table, and not used for any access-
control decision. Its sole purpose is traceability in the audit log.

**No PII in the counter.** `placed_count` is an integer; `openings_remaining` is derived.
Neither contains candidate PII. The `candidate_ref` in the audit event is an internal ID,
not a name or email address.

### 7.4 Rate limiting

`adjust_placed_count` is called by the pipeline service, not directly by a user-facing
endpoint. No per-user rate limiting is applied in this ticket. If the pipeline has a bulk-
add path in PIPE-*, that ticket should apply an appropriate per-user rate limit at its own
router layer.

## 8. Backward Compatibility & Migration

### 8.1 No table schema changes

JOB-005 adds no new DynamoDB attributes to the `TableDef` in `scripts/local-ddb-init.py`.
`placed_count` is a plain numeric attribute on the META row; it does not participate in

### 8.2 Existing `placed_count=0` rows are unaffected

JOB-002 already writes `placed_count=0` at job-order creation. `_item_to_out` already
reads `int(item.get("placed_count", 0))`. Adding the `adjust_placed_count` function does
not change how existing rows are read — it only adds a write path. The projection fields
`placed_count` and `openings_remaining` on `JobOrderOut` were stable from JOB-001; no
client-visible shape change occurs in this ticket.

### 8.3 Pipeline hook — forward-compat contract

The pipeline placement ticket (labelled `PIPE-*` here; the actual specced ticket is **PIP-006**, `docs/opencats/specs/PIP-006.md`) is *intended* to call:

> **OPEN CONTRACT MISMATCH:** PIP-006 as written (`PIP-006.md:601-604,639`) takes the opposite (pull) stance — it does NOT call any counter function and states the counter "will read placement sub-rows to count placed candidates". JOB-005's push contract below and PIP-006's pull description are mutually exclusive and must be reconciled before either ships (see §12 ESCALATED row).

```python
# On candidate → Placed transition:
from app.services.job_orders import adjust_placed_count
adjust_placed_count(job_id, +1, actor_sub=actor_sub, candidate_ref=candidate_id)

# On un-place (Placed → any earlier status):
adjust_placed_count(job_id, -1, actor_sub=actor_sub, candidate_ref=candidate_id)
```

This is the documented hook contract. PIPE-* must handle:
- 404 (job order deleted or not found) — the placement should be blocked or flagged.
- 409 `placed_count_underflow` (decrement below zero) — should not occur in a correctly
  sequenced pipeline but must be handled as an error.
- 503 (ATS flags off) — configuration error; the flags must be on before pipeline operates.

JOB-005 guarantees the function signature and error codes above will not change in a
breaking way before PIPE-* ships.

### 8.4 Additive service and router changes

`app/services/job_orders.py` gains two new functions at the end of the file. `app/routers/
job_orders.py` gains one new endpoint. Both are additive; no existing function signatures,
endpoint paths, or response shapes change.

## 10. Open Questions / Assumptions

**OQ-1 — Bulk-placement API surface.** PIPE-* may need to place multiple candidates
atomically (e.g., filling all three openings in one operation). `adjust_placed_count` with
`delta=3` works correctly, but the audit trail loses per-candidate granularity. Should
PIPE-* call `adjust_placed_count(+1)` in a loop (one audit event per candidate) or a
single `adjust_placed_count(+N)` (one event, `candidate_ref` must be a comma-joined list
or omitted)? **Assumption: PIPE-* calls +1 per candidate for per-candidate audit granularity.**
This spec does not prevent `delta>1`; it simply does not define how `candidate_ref` should
be structured for bulk calls.

**OQ-2 — Revert `full → active` on decrement?** §5.5 specifies that decrementing the
counter does NOT auto-revert `full → active`. Some ATS systems do this automatically.
**Assumption: manual revert only, consistent with the principle that status changes
require explicit recruiter intent.** Revisit when PIPE-* implements the un-place flow.

**OQ-3 — `placed_count` ceiling.** Currently `placed_count` can exceed `openings`
(over-placement). OpenCATS allows this edge case (recruiter places a backup candidate
before a primary candidate declines). JOB-005 does not add a ceiling check.
**Assumption: over-placement is allowed; `openings_remaining` floors at 0 via `max(..., 0)`.**

**OQ-4 — Who can call `adjust_placed_count` via an internal admin endpoint?** Currently
there is no admin/root HTTP endpoint to manually correct `placed_count`. An admin correcting
a data error must use the AWS console or a management script. **Assumption: deferred;
add a ROOT-only `POST /ui/ats/job-orders/{job_id}/openings/adjust` endpoint in a later
ticket if needed.** JOB-005 does not ship this.

**OQ-5 — `updated_at` precision under concurrent writes.** Two concurrent `adjust_placed_count`
calls both write `updated_at = now_ts()`. If they run within the same second, both write
the same integer. The `placed_count` is still correct (atomic `ADD`), but the `updated_at`
reflects only one write's timestamp. **Assumption: acceptable; `updated_at` is a
best-effort "last seen modified" timestamp, not a strict causality marker.**

**Assumption A1:** The pipeline (PIPE-*) is the sole external caller of
`adjust_placed_count`. No other ticket introduces a caller before PIPE-* ships.

**Assumption A2:** `placed_count` is a non-negative integer. The clamp ensures it never
goes below zero. It may exceed `openings` (see OQ-3). It is bounded in practice by the
number of pipeline entries for a given job order.
