## 1. Summary & Goal

`docs/opencats/OPENCATS_GAP_ANALYSIS.md:48` classifies "Skill tagging + skill-based search" as **MISSING**. RSK-001 addressed the first half of that gap by building the skill registry and assignment store. RSK-004 closes the second half: it exposes query and filter surfaces that let recruiters ask "find me candidates with skills X and Y" and "find job orders that require skill Z", and provides a matching endpoint that scores candidates against a specific job order's required skills.

The implementation is **pure query composition** over the forward index built by RSK-001. No new DynamoDB table is introduced and no new GSI is created. Every query is a targeted key-condition lookup on `pk = "SKILL#{skill_id}"` — a primary-key query with no scan, no `FilterExpression`, and full `LastEvaluatedKey` pagination. Client-side set logic (AND intersection or OR union) is applied after the per-skill pages have been fetched.

Three new endpoints are introduced:

1. `GET /ui/ats/candidates/search/skills` — candidate search by skill IDs (AND/OR).
2. `GET /ui/ats/job-orders/search/skills` — job-order search by skill IDs (AND/OR, optional `required_only`).
3. `GET /ui/ats/job-orders/{job_order_id}/matching-candidates` — ranked candidate suggestions for a job order.

All endpoints require cookie-based session authentication (`Depends(require_ui_session)`), are gated by `S.candidates_enabled`, and return `404` when the flag is off — matching the flag convention owned by CND-001.

### 2.2 RSK-001 forward index (the substrate for RSK-004 queries)

RSK-001 (`docs/opencats/specs/RSK-001.md` §3) writes two row types to the `ats_skills` table on each `assign_skill` call:

```
Forward assignment row:
  pk = "SKILL#{skill_id}"
  sk = "ENTITY#{entity_type}#{entity_id}"
  { skill_id, entity_type, entity_id, weight(N, opt), required(BOOL, opt), created_at(N) }
```

RSK-004 queries these forward rows with a key condition `pk = "SKILL#{skill_id}"` and a sort-key prefix filter `begins_with(sk, "ENTITY#candidate#")` (or `"ENTITY#job_order#"`). This is a primary-key query — O(matches), no scan, no `FilterExpression` performance gotcha (CLAUDE.md "DDB FilterExpression doesn't reduce page size").

### 2.3 AND/OR intersection semantics — existing precedent

The codebase implements AND-intersection of token sets in two places that RSK-004 mirrors:

- `app/routers/search.py:432` — `all(tok in haystack for tok in tokens)` — AND-intersection of query tokens against a ticket subject string.
- `docs/suitecrm/specs/KB-009.md` §5.5 — KB full-text search AND-intersects per-token result sets with a client-side Python `set.intersection(...)` after looping each token's DDB query page-by-page.

RSK-004 adapts the KB-009 §5.5 set-intersection approach: fetch a `set[str]` of entity IDs per skill, then intersect (AND) or union (OR) the sets. This is O(k * page_count) DDB reads where k is the number of skills queried — bounded by a configurable max.

### 2.4 `LastEvaluatedKey` pagination is mandatory

CLAUDE.md ("DDB FilterExpression doesn't reduce page size") notes that DynamoDB returns up to 1MB per page before any filter. RSK-004's per-skill queries do not use a FilterExpression for the `entity_type` — instead they use a sort-key prefix `begins_with(sk, "ENTITY#candidate#")` which **is** part of the key condition and therefore narrows the index scan server-side. However, a single skill may be assigned to many entities, and each page of 1MB could still be exhausted before all matching rows are returned. The `loop_via_last_key` helper (see §4.2) always loops until `LastEvaluatedKey` is absent.

### 3.1 No new DynamoDB tables or GSIs

RSK-004 introduces **zero new tables** and **zero new GSIs**. All data lives in the `ats_skills` table owned by RSK-001.

The relevant row structure (defined in RSK-001 §3, reproduced here for completeness):

```
ats_skills table (pk / sk single-table):

```

No `attr_types` changes are needed here because this table's GSI (`ByName`) was already declared in RSK-001 with its string sort key `name_lc`. RSK-004 does not add any GSIs to any table.

#### `find_candidates_by_skills`

```python
def find_candidates_by_skills(
    skill_ids: list[str],
    *,
    match: str = "all",          # "all" (AND) | "any" (OR)
    owner_sub: str | None = None, # when set, restricts to this recruiter's candidates
    limit: int = 50,
) -> list[dict]:
```

**Behavior:**

1. Validate `match in ("all", "any")`; raise `ValueError` on invalid input (the router raises `HTTPException(422)` from this).
2. Normalize and deduplicate `skill_ids` via `normalize_skill(sid)[0]` (RSK-001 helper). Skip unknown skill IDs silently (they simply produce empty sets). Cap query at `_MAX_SKILL_QUERY_COUNT = 10` distinct skill IDs to bound DDB read amplification; raise `HTTPException(400, code="too_many_skills")` if exceeded.
3. For each `skill_id`, call `_fetch_entities_for_skill(skill_id, entity_type="candidate")` → `set[str]` of candidate IDs.
4. Intersect (AND) or union (OR) the per-skill sets:
   - `match="all"`: result = `set.intersection(*per_skill_sets)` (candidates that have every queried skill).
   - `match="any"`: result = `set.union(*per_skill_sets)` (candidates that have at least one).
5. If `owner_sub` is given, batch-get the META rows for the result set and filter to those where `item["owner_sub"] == owner_sub`. (Batch-get is O(result size / 100) requests, capped because `limit` bounds result size.)
6. Batch-get META rows for the final set (up to `limit` items); build and return `list[dict]` including `candidate_id`, `first_name`, `last_name`, `email`, `owner_sub`, `status`, and `matched_skill_ids` (the intersection of queried IDs and the candidate's actual assignments — computed from the per-skill sets rather than a second DDB call).
7. Return sorted by `created_at` descending (newest first), truncated to `limit`.

**`_fetch_entities_for_skill` helper (private):**

```python
def _fetch_entities_for_skill(skill_id: str, entity_type: str) -> set[str]:
```

Loops with `LastEvaluatedKey` until exhausted:

```python
resp = T.ats_skills.query(
    KeyConditionExpression=(
        "pk = :pk AND begins_with(sk, :prefix)"
    ),
    ExpressionAttributeValues={
        ":pk":     f"SKILL#{skill_id}",
        ":prefix": f"ENTITY#{entity_type}#",
    },
    ProjectionExpression="sk",   # minimal projection — only the SK is needed
    Limit=500,
    **({} if last_key is None else {"ExclusiveStartKey": last_key}),
)
```

Extracts `entity_id` from the SK suffix (`sk.split("#", 2)[2]`) and accumulates in a `set`. Loops until `LastEvaluatedKey` is absent. Returns the complete set. This is O(N / 500) DDB reads where N is the number of entities assigned this skill.

#### `find_job_orders_by_skills`

```python
def find_job_orders_by_skills(
    skill_ids: list[str],
    *,
    match: str = "all",
    required_only: bool = False,  # when True, only include assignments where required=True
    limit: int = 50,
) -> list[dict]:
```

**Behavior:** Identical to `find_candidates_by_skills` except:

- Queries `begins_with(sk, "ENTITY#job_order#")`.
- When `required_only=True`, projects `sk` AND `required` from the forward row and filters client-side to rows where `required is True`. Since this is a post-fetch client-side filter (not a DDB FilterExpression), all pages must be fetched before filtering — the `_fetch_entities_for_skill` helper is extended with an optional `required_only` boolean that conditionally includes/excludes rows during accumulation.
- Batch-gets `JobOrderOut`-shaped META rows from `T.job_orders` instead of `T.candidates`.
- Returns `list[dict]` shaped as `JobOrderMatchOut`.

**`required_only` implementation detail:** Rather than a DDB FilterExpression (which doesn't reduce page size — CLAUDE.md), project both `sk` and `required` and accumulate only those rows where `item.get("required") is True`. This adds one projected attribute to the query but avoids a separate DDB call per row.

#### `match_candidates_to_job_order`

```python
def match_candidates_to_job_order(
    job_order_id: str,
    *,
    limit: int = 50,
) -> list[dict]:
```

**Behavior:**

1. Fetch the job order's required skills via RSK-001's `list_entity_skills("job_order", job_order_id)` — this queries the reverse row partition `pk="ENTITY#job_order#{job_order_id}"` for all `SKILL#…` entries.
2. Filter to those where `required is True` → `required_skill_ids: list[str]`.
3. If `required_skill_ids` is empty, return `[]` immediately (no match is possible without required skills).
4. Call `find_candidates_by_skills(required_skill_ids, match="any", limit=limit * 5)` to get a broad candidate pool (over-fetch because match-score sorting will cull the list).
5. For each candidate in the pool, compute:
   ```
   match_score = len(candidate_matched_skill_ids ∩ required_skill_ids) / len(required_skill_ids)
   ```
   `candidate_matched_skill_ids` is already available from step 4's per-skill sets — no additional DDB reads.
6. Sort the pool by `match_score` descending; secondary sort by `created_at` descending (most recent candidate breaks ties). Truncate to `limit`.
7. Emit `audit_event("ats.skill.match_candidates", actor_sub, job_order_id=job_order_id, candidate_count=len(result), top_score=result[0]["match_score"] if result else 0)`.
8. Return `list[dict]` shaped as `CandidateMatchOut` with `match_score` in `[0.0, 1.0]`.

**Score of 1.0** means the candidate has every required skill. Score of 0.0 is impossible in the result set because `match="any"` already ensures at least one skill matches.

## 5. Detailed Behavior & Edge Cases

### 5.1 Empty skill_ids after parsing

If the caller sends `skill_ids=` (empty string) or `skill_ids=,,,` (only commas), the parsed list is empty after strip+filter. The endpoint raises `HTTPException(422, code="skill_ids_required")`. This prevents an expensive union-of-all-candidates query from being issued.

### 5.2 Unknown skill IDs

If a caller sends a skill ID that does not exist in the `ats_skills` registry (no `SKILL#{id}` / `META` row and no `SKILL#{id}` / `ENTITY#…` rows), `_fetch_entities_for_skill` returns an empty set. For `match="all"`: the intersection with an empty set is the empty set → `[]` result. For `match="any"`: the union skips the empty set → still returns results from other valid skill IDs. This is the correct semantic (an unknown skill has zero assignments).

### 5.3 Single-skill queries

A single-skill query with `match="all"` is the most common recruiter query ("show me all Python candidates"). The intersection of a single set with itself is itself. Performance is O(N / 500) DDB reads for N assignments to that skill — bounded in practice by the `limit` cap on the batch-get step.

### 5.4 Large skill assignment sets — pagination correctness

When a popular skill (e.g. `"python"`) is assigned to thousands of entities, `_fetch_entities_for_skill` must loop through every page to build the complete set before intersecting. For `match="any"` this is still O(pages * k). For `match="all"` the worst case is the same. The `Limit=500` per DDB query page and the `_MAX_SKILL_QUERY_COUNT=10` cap on the number of skills queried bound the total DDB reads to at most 10 × ceil(N / 500) where N is the largest single-skill assignment count. Recruiters who find performance degraded on `match="all"` across large skill sets should reduce the number of skills in the query or use the `matching-candidates` endpoint (which fetches required skills from the job order and applies `match="any"` before scoring).

### 5.5 `required_only` with no required assignments

A job order may have skills assigned with `required=False` (informational/preferred). If `required_only=True` and no assignments on the queried skill IDs have `required=True`, the result is `[]`. This is correct — a query for "only required skill" returns nothing if no job orders have formally marked that skill as required.

### 5.6 match_score = 0.0 is impossible in `match_candidates_to_job_order` results

Because step 4 calls `find_candidates_by_skills(..., match="any")`, every candidate in the pool has at least one required skill in common with the job order. Therefore `match_score ≥ 1 / len(required_skill_ids) > 0.0` for all returned rows. Callers need not guard against zero-score rows.

### 5.7 `match_candidates_to_job_order` with zero required skills

If a job order has skills but none with `required=True`, `required_skill_ids` is empty and the function returns `[]` immediately. This is intentional: the endpoint's semantic is "candidates who satisfy this job order's requirements"; a job order with no stated requirements matches everyone, which is not a useful result. The UI should hint to the recruiter to mark at least one skill as required.

### 5.8 Over-fetch factor in `match_candidates_to_job_order`

Step 4 fetches `limit * 5` candidates via `find_candidates_by_skills`. This over-fetch is needed because the `match="any"` query retrieves a superset; after scoring and sorting by `match_score`, only the top `limit` rows are returned. The `5×` multiplier is a tunable constant `_MATCH_CANDIDATES_OVERSAMPLE = 5` at module level. If the over-fetched pool is smaller than `limit`, no candidates are dropped and the result is the full pool.

### 5.9 `owner_sub` scoping for admin callers

When the calling recruiter is not an admin (`normalize_role(ctx["role"]) not in {Role.ADMIN, Role.ROOT}`), `find_candidates_by_skills` is always called with `owner_sub=ctx["user_sub"]`, restricting results to that recruiter's own candidates. This prevents a recruiter from discovering other recruiters' candidates via skill search. Admin callers (`normalize_role(ctx["role"]) in {Role.ADMIN, Role.ROOT}`) with `all=true` query param bypass the owner filter — the same pattern used by RSK-003's `GET /ui/ats/candidates/search/resume?all=true`.

### 5.10 Hydration ordering and missing META rows

The batch-get step at the end of `find_candidates_by_skills` may encounter candidates whose META rows were deleted between the skill-query step and the batch-get step (concurrent delete, soft-delete race). Such rows simply do not appear in the batch-get response and are silently excluded from results. The result total reflects only the successfully hydrated rows.

### 5.11 Rate limit failure is partially non-blocking

`_bucket_limit` (`app/services/rate_limit.py:60`) wraps only the `put_item` write in `try/except Exception: pass`, and returns `True` early when `_sessions_table_enabled()` is `False` (table not configured). However, the `get_item` read (which reads the current bucket state) is **not** guarded by a `try/except` — a DDB transient error on that read would propagate up as a 500, not silently pass. In the common failure mode (DDB not configured / sessions table absent) the function does return `True` (allow) as documented, so the practical fail-open behavior described by `rate_limit_profile_lookup` (`rate_limit.py:198`) and KB-009's search endpoint holds for misconfiguration; a live-DDB read outage is a different risk.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007: no `if S.dev_mode:` branches

All DDB reads go through frozen `T.ats_skills` (RSK-001 table), `T.candidates` (CND-001 table), and `T.job_orders` (JOB-001 table) — the same handles used in dev (against DynamoDB Local on port 8001) and prod (against real DynamoDB). There is no `s3_client()` call in RSK-004 (it is query-only, not S3). No `dev_mode` branch exists anywhere in the service or router code.

### 7.2 All three endpoints are read-only (idempotency is trivially satisfied)

`GET` endpoints are naturally idempotent. `match_candidates_to_job_order` emits an `audit_event`, which is a fire-and-forget write to `T.alerts`; the event itself is informational and carries no state machine implications. Repeating the call produces a new audit record but does not change any candidate, job order, or skill assignment row.

### 7.3 PII protection — email field gating

`CandidateMatchOut.email` is populated in the service layer (`find_candidates_by_skills` includes `email` in the batch-get projection) but stripped at the router layer before serialization when `normalize_role(ctx["role"]) not in {Role.ADMIN, Role.ROOT}`. This follows the established pattern in the ticket system's recruiter-visibility logic (e.g. `app/routers/kyc_cases.py:2277`, `app/routers/kyc_analytics.py:43`). The stripping is explicit: `item.pop("email", None)` before constructing `CandidateMatchOut`. The `email` field in the Pydantic model is `email: str | None = None` so absent values serialize as `null` rather than causing a validation error.

### 7.4 Owner-scope enforcement (IDOR prevention)

A recruiter querying `GET /ui/ats/candidates/search/skills` can only see candidates they own (`owner_sub=ctx["user_sub"]`). The owner filter is applied at the batch-get projection step — if a skill search returns candidate IDs owned by other recruiters, those IDs are filtered during batch-hydration, not silently included. This prevents IDOR disclosure of another recruiter's candidates via the skill search surface.

For `GET /ui/ats/job-orders/{job_order_id}/matching-candidates`, the caller must be a listed recruiter on the job order or an admin. The job order's `recruiter_subs` list is read from `T.job_orders` via the `GSI_DIRECT` index (one `query(IndexName="GSI_DIRECT", ...)` call — JOB-001 §3.1/§3.2) before calling `match_candidates_to_job_order`. The authorization check is `ctx["user_sub"] in item["recruiter_subs"] or normalize_role(ctx["role"]) in {Role.ADMIN, Role.ROOT}`. If the caller is not authorized, `403` is returned — `404` would leak whether the job order exists.

### 7.5 No public (unauthenticated) endpoints

RSK-004 introduces no public career-portal endpoints. All three endpoints require `Depends(require_ui_session)`. The skill search surface is internal recruiter tooling and is therefore not added to `API_KEY_ROUTE_EXEMPTIONS` (`app/services/api_key_route_scope_registry.py:70`).

### 7.6 Input validation

`skill_ids` query parameter is a comma-separated string. After splitting: each token is passed through `normalize_skill(...)[0]` (RSK-001's idempotent normalizer); any token that fails normalization (e.g. empty string after strip) is silently dropped; if the post-normalization list is empty, `HTTPException(422)` is raised. The `pattern="^(all|any)$"` FastAPI `Query` validator on `match` ensures only the two legal values are accepted at the routing layer, before the service function is called.

## 8. Backward Compatibility & Migration

### 8.1 No existing endpoints or data modified

RSK-004 is purely additive:
- No existing router file is modified (new endpoints are added to the ATS router file introduced by RSK-001/RSK-003).
- No existing table schema is changed.
- No existing DynamoDB items are modified.
- No existing settings fields are changed.
- No `app/main.py` registration changes beyond those already performed by RSK-001's router import.

### 8.2 No cold-start migration needed

When deployed on a system where RSK-001 has already been operating, the skill assignments already written to the `ats_skills` table are immediately queryable through the RSK-004 endpoints.

### 8.4 Soft deprecation of `key_skills` free-text field

`CandidateOut.key_skills` (a free-text field on the candidate META row, defined in CND-001) is not deprecated by RSK-004. Both coexist: `key_skills` is the unstructured text blob used by RSK-003's full-text search; the `ats_skills` assignment rows are the structured skill tags used by RSK-004. Recruiters who have not yet migrated their candidate skill data to RSK-001 assignments will see no results from RSK-004's skill search. This is by design — the RSK-005 CSV import populates RSK-001 assignments from the `key_skills` column, providing a migration path.

## 10. Open Questions / Assumptions

1. **Candidate hydration source:** RSK-004 batch-gets candidate META rows from `T.candidates`. This assumes CND-001/CND-002 have shipped and the table exists. If running RSK-004 tests before CND ships, the test creates the `candidates` table in moto manually (per cross-cutting §7 in `ATS_RESUME_SKILLS_TICKETS.md`) — the same approach used by LED-008 tests before LED-007's GSI existed.

2. **Job order META row shape:** RSK-004's `find_job_orders_by_skills` batch-gets job order META rows from `T.job_orders` and projects `job_order_id`, `title`, `status`. This assumes JOB-001's META row shape (`pk="COMPANY#{client_company_id}"`, `sk="JOB#{job_id}"`). The `job_id` is available from the forward skill row's SK (`ENTITY#job_order#{job_order_id}`), but resolving `title` and `status` requires a separate lookup against `T.job_orders`. RSK-004 uses the `GSI_DIRECT` index (PK=`job_id`) declared in JOB-001 §3.2 for this batch-resolve — one `query` per job order in the result set, or a parallel batch if the JOB table's `GSI_DIRECT` index supports `batch_get_item` (standard DynamoDB `batch_get_item` requires full PK+SK; `GSI_DIRECT` is only useful for `query`). **Assumption:** RSK-004 issues individual `query(IndexName="GSI_DIRECT", pk=job_id, Limit=1)` calls for each job order in the skill-search result, bounded by `limit`. This is acceptable at `limit=50` (50 DDB reads). A follow-up can batch this if needed.

3. **`match_candidates_to_job_order` recruiter authorization:** JOB-001 §3.1 shows the META row stores `recruiter_subs` as a **list** (`List[str]`, per `JobOrderOut` at JOB-001 §4.4). The `GSI_BY_RECRUITER` index uses a scalar `recruiter_sub` partition key — that attribute belongs to the separate per-recruiter index rows (sk=`RECRUITER#{sub}#JOB#{job_id}`), not to the META row. The authorization check against the META row must therefore be `ctx["user_sub"] in item.get("recruiter_subs", [])`, not `item["recruiter_sub"] == ctx["user_sub"]`. This is already the corrected form shown in §4.2 endpoint 3 and §7.4.

4. **Skill ID vs. skill name in the API surface:** The endpoints accept `skill_ids` (normalized slug IDs, e.g. `"python"`, `"project-management"`). The RSK-001 `search_skills(prefix)` autocomplete endpoint helps the UI discover valid IDs before constructing a search URL. Accepting raw user-typed names (with normalization inside RSK-004) is also viable — the `normalize_skill` function is pure and cheap. The current spec accepts only IDs for API predictability; a `names=` alias parameter can be added in a follow-up.

5. **Pagination of search results:** The current spec does not paginate the skill-search endpoint output — it returns up to `limit` items in a single response. This is acceptable at `limit ≤ 200`. If skill searches need cursor pagination (e.g., browsing 5,000 "Python" candidates), it can be added using `app/core/cursor.py:94` (`encode_cursor`/`decode_cursor`) in a follow-up.
