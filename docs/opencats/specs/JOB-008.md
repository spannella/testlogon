was delivered by JOB-001 through JOB-007; this ticket only closes the testing gap that
occurs between individual focused unit tests (one per ticket) and a validated, integrated

## 3. Data Model

No new DynamoDB tables or GSIs are introduced by this ticket. All DDB access is through
the table already defined by JOB-001 and tested via moto:

**`job_orders` table** (JOB-001 `scripts/local-ddb-init.py` `TableDef`):

| pk | sk | row type |
|---|---|---|
| `COMPANY#{client_company_id}` | `JOB#{job_id}` | META row (all fields) |
| `COMPANY#{client_company_id}` | `RECRUITER#{sub}#JOB#{job_id}` | per-recruiter index row |

GSIs on the META row:

| GSI name | Partition key | Sort key | `attr_types` |
|---|---|---|---|
| `GSI_BY_STATUS` | `status` (S) | `created_at` (N) | `{"created_at":"N"}` |
| `GSI_BY_RECRUITER` | `recruiter_sub` (S) | `created_at` (N) | `{"created_at":"N"}` |
| `GSI_HOT` | `hot_flag` (S) | `created_at` (N) | `{"created_at":"N"}` |
| `GSI_PUBLIC` | `public_flag` (S) | `created_at` (N) | `{"created_at":"N"}` |
| `GSI_DIRECT` | `job_id` (S) | — | — |

The `attr_types={"created_at": "N", "updated_at": "N"}` declaration on the `TableDef`
(JOB-001) follows the `users` table precedent at `scripts/local-ddb-init.py:49-54` — a
numeric GSI sort key that omits `attr_types` causes a `ValidationException` at runtime when
queried with integer values (CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha).

In the hermetic pytest, the moto table is created with explicit `AttributeDefinitions`
entries for every GSI key, including `{"AttributeName": "created_at", "AttributeType": "N"}`
— the same pattern used by `_make_kyc_risk_scores_table` at
`tests/test_gap_0265_0266_kyc_risk_scoring.py:59-82`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Hermetic pytest — test class structure

The pytest module uses `unittest.TestCase` subclasses with `ExitStack` for lifecycle
management, mirroring `tests/test_gap_0265_0266_kyc_risk_scoring.py:95-132`. A single
base class `_JobOrderTestBase` performs the full setup:

```python
class _JobOrderTestBase(unittest.TestCase):
    def setUp(self):
        self.stack = ExitStack()
        self.addCleanup(self.stack.close)
        self.stack.enter_context(mock_aws())

        ddb = boto3.resource("dynamodb", region_name="us-east-1")
        self.job_orders_table = _make_job_orders_table(ddb)
        # Also create a users table for JOB-006 recruiter resolution
        self.users_table = _make_users_table(ddb)

        from app.core import tables as tables_mod
        T = tables_mod.T
        for name, handle in (
            ("job_orders", self.job_orders_table),
            ("users",      self.users_table),
        ):
            original = getattr(T, name)
            object.__setattr__(T, name, handle)
            self.addCleanup(object.__setattr__, T, name, original)

        from app.core.settings import S
        self.S = S
        for flag_name in ("ats_enabled", "job_orders_enabled"):
            orig = getattr(S, flag_name)
            object.__setattr__(S, flag_name, True)
            self.addCleanup(object.__setattr__, S, flag_name, orig)
```

The `_make_job_orders_table(ddb)` helper creates the table with all five GSIs and the
explicit `AttributeDefinitions` including `{"AttributeName": "created_at", "AttributeType": "N"}`.
This is required for moto to accept queries against `GSI_BY_STATUS` with a numeric sort key.

The `actor_sub` used across all tests is a deterministic string `"test_recruiter_sub"`;
the `client_company_id` used is `"company_abc"`. All `title` values carry a `TS` suffix
(`f"Senior Engineer {TS}"`) to avoid cross-run DDB collisions if the moto context is ever
shared.

### 5.2 CRUD round-trip

`TestJobOrderCrud._test_create_get_delete`:
1. Call `create_job_order(actor_sub, JobOrderCreateIn(title=..., type="hire", client_company_id="company_abc", recruiter_subs=["test_recruiter_sub"]))`.
2. Assert returned `JobOrderOut` has `status="active"`, `placed_count=0`, `openings_remaining == openings` (default `openings=1`).
3. `get_job_order(job_id)` round-trips the same record.
4. `delete_job_order(actor_sub, job_id)` soft-deletes; subsequent `list_open()` excludes it.
5. `get_job_order(job_id)` still returns the record (soft-delete does not destroy the META row; only list views filter `deleted_at`).

### 5.3 State-machine coverage

All 8 combinations below are tested (one test method per group):

| Transition | Expected result |
|---|---|
| `lead → active` | 200, new status persisted |
| `upcoming → active` | 200, new status persisted |
| `active → on_hold` | 200 |
| `on_hold → active` | 200 (reverse is legal) |
| `active → full` (manual) | 200 |
| `active → closed` | 200 (terminal reached) |
| `closed → active` with `JOB_ORDER_ALLOW_REOPEN=true` | 200 |
| `closed → active` with `JOB_ORDER_ALLOW_REOPEN=false` | 409 `{"code":"invalid_status_transition"}` |
| `closed → full` (direct terminal re-entry) | 409, regardless of reopen flag |
| Same-status no-op (`active → active`) | 200, no audit event emitted |

The reopen flag is toggled via `object.__setattr__(S, "job_order_allow_reopen", False)` /
`True` with cleanup restoration.

### 5.4 List endpoints — pagination and sparse GSI

`TestJobOrderLists` seeds 12 job orders: 4 `active`, 2 `on_hold`, 2 `full`, 2 `closed`,
1 `hot`-flagged, 1 soft-deleted.

- **`list_open`**: expects 10 results (excludes 2 terminal `closed` + 1 soft-deleted),
  all non-deleted non-terminal. The soft-deleted row is interleaved in DDB's natural page
  order; the `LastEvaluatedKey` loop in `list_open` (JOB-004) must gather the correct 10
  even if the deleted row falls within the first DDB page. Assert by calling with `limit=5`
  twice and verifying `next_cursor` from page 1 decodes cleanly via `decode_cursor` and
  produces a non-overlapping page 2 with the remaining 5 items.
- **`list_hot`**: expects exactly 1 result (the one with `hot_flag="1"`); toggling `hot=False`
  via `update_job_order` removes the sparse attribute and the record leaves the list.
- **`list_mine`**: seeds two orders with `recruiter_subs=["user_A"]` and one with
  `recruiter_subs=["user_B"]`. `list_mine("user_A")` returns 2; `list_mine("user_B")`
  returns 1; updating the first order's `recruiter_subs` to `["user_B"]` causes
  `list_mine("user_A")` to return 1 (index row reconciliation, JOB-002).

### 5.5 Openings counter

`TestOpeningsCounter` tests:
- `adjust_placed_count(job_id, +1, actor_sub=...)` → `placed_count=1`,
  `openings_remaining = openings - 1`.
- When the +1 brings `openings_remaining` to 0 on an `active` order, status auto-advances
  to `full` and a `job_order.status_changed` audit event is emitted.
- `adjust_placed_count(job_id, -1, ...)` decrements; subsequent `openings_remaining`
  increases; an `active` order stays `active` (the auto-full only fires on the transition
  from >0 to 0, not on any negative delta).
- `adjust_placed_count(job_id, -1, ...)` when `placed_count=0` → 409
  `{"code":"placed_count_underflow"}` (atomic `ConditionExpression` clamp, JOB-005).
- `get_openings_summary(job_id)` returns the correct `{openings, placed_count,
  openings_remaining}` triple.

Concurrent increment safety: submit two `adjust_placed_count(+1)` calls in sequence; both
succeed (atomic `ADD`); final `placed_count=2`. This confirms the `ADD` semantics
(DynamoDB `UpdateExpression: "ADD placed_count :delta"`) as used in `app/services/social.py:535` (`_increment_counts` → `"ADD follower_count :one"`).

### 5.6 Linkage resolution

`TestLinkageResolution` tests two scenarios:

**Resolved (PTY available):** `patch("app.services.job_orders.party.get_party")` returns
a fake `{"name": "ACME Corp"}` for the `client_company_id`. `resolve_links(out)` returns
`{"company": {"id": ..., "name": "ACME Corp"}, "contact": ..., "recruiters": [...]}`.
The `T.users` moto table is seeded with a row `{"user_sub": "test_recruiter_sub",
"display_name": "Alice"}` so the recruiter resolves to `{"sub": ..., "display_name": "Alice"}`.

**Unresolved (PTY unavailable):** `patch("app.services.job_orders.party")` raises
`AttributeError` (simulating the module not yet having `get_party`). `resolve_links(out)`
degrades gracefully — returns `{"company": {"id": ..., "name": None, "unresolved": True},
"contact": {..., "unresolved": True}, "recruiters": [...]}` — no exception, no 500.

Both scenarios confirm the lazy local import discipline: the `party` import inside
`resolve_links` is a `try/except` block so the `app/services/job_orders` module is
importable even if `app.services.party` does not export `get_party` yet.

### 5.10 Playwright E2E — key edge cases

**Cross-run isolation**: All `title` values include `Date.now()` suffix
(`const TS = Date.now()` at the top of the spec, per `catalog-subscriptions.spec.ts:33`).
This avoids strict-mode violations when old job orders from prior runs remain in DDB.

**Hot tab sparse GSI**: After toggling `hot=false` via PATCH, wait for the list to
refetch before asserting the order is absent from the Hot tab. Use
`page.waitForResponse(/\/ui\/ats\/job-orders\/hot/)` after the PATCH response to ensure
the query is not served from the React Query stale cache.

**Status dropdown 409 toast**: The 409 path requires the dropdown to surface an error
toast. Use `page.locator("[role=alert]").filter({ hasText: /invalid_status_transition/ })`
to assert it. Do not `waitForLoadState("networkidle")` — Vite HMR + presence polling keep the network permanently active;
use `waitForResponse` instead (CLAUDE.md E2E patterns).

**Sidebar gate (flag-off section)**: This section cannot toggle server flags at runtime.
Instead it makes a direct `page.request.get("http://localhost:8000/ui/ats/job-orders/feature-status")`
call to confirm the endpoint returns `{"job_orders_enabled": false}` when the backend was
started without the env var. If the backend under test has the flag on, this section
asserts the sidebar *is* present and the flag is reported as `true` — making it
deterministic in either configuration. An explicit note in the spec (code comment) explains
that full flag-off UI gating is validated by starting the backend with `ATS_ENABLED=0
JOB_ORDERS_ENABLED=0` and checking the sidebar.

**Pagination (§ JO-3)**: Seed 6 job orders via API, request `?limit=3`, capture
`next_cursor`, request with `?cursor=next_cursor&limit=3`, assert no overlap and the
union covers all 6 orders. The cursor is an opaque HMAC token
(`app/core/cursor.py:94-101`); the test does not decode it, only round-trips it.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

No `if S.dev_mode` branches exist in `app/services/job_orders.py` or
`app/routers/job_orders.py` (per the cross-cutting constraint in `ATS_JOB_ORDERS_TICKETS.md:14`
and CLAUDE.md SECOPS-007). All DDB operations — META row writes, index row reconciliation,
atomic `ADD placed_count`, soft-delete, `GSI_DIRECT` lookup — use the same code path in
both environments. The moto in-process DDB (dev) and the real DynamoDB endpoint (prod)
are transparent at the `T.job_orders` abstraction layer via `_safe_table` /
`_FloatSafeTable` (`app/core/tables.py:29-66`).

The hermetic tests exercise the real service code — not a dev-mode stub — so passing
offline tests are meaningful evidence of prod correctness.

### 7.2 Idempotency

- `create_job_order` mints a fresh `uuid4().hex`-prefixed `job_id` on every call; no
  client-provided id is accepted; retries safely produce separate records.
- `delete_job_order` is idempotent: calling it on an already-soft-deleted record writes
  `deleted_at` again (no error, no second audit event from the duplicate write because the
  same `deleted_at` value is already present).
- `set_status` same-status is a no-op (returns current state without writing to DDB or
  emitting an audit event).
- `adjust_placed_count` uses atomic `ADD` — concurrent callers cannot lose each other's
  increments; the `ConditionExpression` clamp on decrement prevents underflow under any
  interleaving.

### 7.3 Security

- All mutating endpoints require `require_ui_session`; unauthenticated calls are rejected
  at the dependency level before `_require_flag()` is evaluated.
- The `feature-status` endpoint is no-auth (public probe for frontend nav gating, same
  pattern as OPP-006); it returns only boolean flags, no data.
- `actor_sub` is taken from the session dict returned by `require_ui_session`, never from
  the request body — same discipline as all other service layers in the platform.
- CSRF: all non-GET requests go through the cookie session path and therefore carry the
  `x-csrf-token` header requirement enforced by `require_ui_session` (CLAUDE.md auth note).
  The Playwright E2E helpers (`catPost`, `jobPost`) include `"x-csrf-token": session.csrf_token`
  on every non-GET request.
- `recruiter_subs` is capped at 25 entries (`max_length=25` on `JobOrderOut.recruiter_subs`,
  JOB-001 `app/models.py`) to prevent unbounded index row proliferation.
- The `description` field is capped at 20 000 characters (`max_length=20000`) to prevent
  DDB item size limit violations (400 KB per item).
- `resolve_links` uses a lazy local import of `app.services.party` (not a module-level
  import) — a missing or broken `party` module cannot crash the server at startup.

## 10. Open Questions / Assumptions

1. **`just e2e` inclusion**: The ATS E2E spec should be excluded from the default `just e2e`
   run until the flags are turned on by default (currently `ATS_ENABLED` defaults to `false`).
   Assumption: a separate `just e2e-ats` recipe will be added, or CI will pass the env vars
   explicitly. This decision is deferred to the team's CI configuration ticket.

2. **`T.alerts` in hermetic tests**: `audit_event` (`app/services/alerts.py:644`) writes to
   `T.alerts`. The hermetic tests patch `audit_event` at the module level rather than
   creating a moto `alerts` table. If a future refactor makes `audit_event` uncallable
   without a real table, a second `object.__setattr__` rebind for `T.alerts` will be needed.
   Current approach (patch at module boundary) is consistent with
   `tests/test_gap_0272_0273_kyc_decision_events.py`.

3. **`app.services.party` import**: `resolve_links` (JOB-006) uses a lazy local import of
   `app.services.party`. If `party.py` has not yet been created when this test suite runs,
   the hermetic tests must patch `app.services.job_orders.party` as an `AttributeError`-
   raising mock. The spec assumes this is the case (PTY is planned, not built); tests
   verify graceful degradation.

4. **Playwright flag-off section (§ JO-8)**: Full flag-off UI testing (sidebar absent,
   routes return 503) requires a separately started backend process with the env vars off.
   This ticket's spec covers the flag probe endpoint assertion and the sidebar presence/
   absence check based on the live flag state; a dedicated CI job with a flag-off backend
   is assumed but not specified here.

5. **`openings` counter E2E coverage**: The `adjust_placed_count` primitive is internal-only
   (no mutate endpoint exposed to clients; invoked by the future PIPE-* pipeline cluster).
   The E2E spec omits counter mutation tests and covers only the `GET /openings` summary
   read endpoint (§ JO-4). Counter mutation is fully covered by hermetic pytest
   (`TestOpeningsCounter`).
