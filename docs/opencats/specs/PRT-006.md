# PRT-006 — Hermetic pytest + E2E (apply → candidate → pipeline)

**Prefix:** `PRT` · **Area:** ATS / Public Career Portal  
**Type:** Test · **Priority:** P1 · **Estimate:** 1.5d  
**Source:** `docs/opencats/ATS_CAREER_PORTAL_TICKETS.md` §PRT-006 (lines 219–257); gap: `docs/opencats/OPENCATS_GAP_ANALYSIS.md:80-83`

## 1. Summary & Goal

PRT-006 delivers the complete test harness for the public career portal vertical — the pytest suite that exercises every service- and handler-layer behavior offline, and the Playwright E2E suite that drives a live stack end-to-end through the full apply → candidate → pipeline chain.

The ticket has no runtime deliverable. It produces two new test files:

- **`tests/test_prt_career_portal.py`** — 13 hermetic offline test cases using moto in-memory DynamoDB, frozen `T`/`S` via `object.__setattr__`, and route handlers invoked directly on a fresh `asyncio.new_event_loop()`. No `TestClient`, no real AWS, no network.
- **`frontend/e2e/career-portal.spec.ts`** — six Playwright E2E sections covering public listing, full apply chain assertion, honeypot, admin branding config, résumé presign, and flag-off 404 enforcement.

The goal is to verify:

1. PRT-001 through PRT-005 fulfill their acceptance criteria end-to-end.
2. Tier-1 collaborator absence (JOB-*, CND-*, PIP-*) never causes a 500 — graceful degradation is observable via spies.
3. Abuse mitigations (honeypot, rate limit, IP anonymization) behave exactly as specified.
4. `CAREER_PORTAL_ENABLED=0` leaves the platform byte-for-byte unchanged across all surfaces.
5. The apply → candidate → pipeline chain produces a verifiable Candidate at status `"100"` (New / Applied) in the job order's pipeline.

## 2. Context & Current State

**No career portal exists in the codebase today.** `docs/opencats/OPENCATS_GAP_ANALYSIS.md:32-36` confirms the entire recruiting vertical is net-new. Grepping `app/` for `CareerApplyIn`, `create_application`, `career_portal.applied`, `SLUG#`, `CareerPortal`, or `career_portal_enabled` returns zero matches. PRT-006 therefore tests entirely new code delivered by PRT-001 through PRT-005.

**Canonical hermetic test pattern:** `tests/test_gap_0220_0221_ssh_stored_key.py` is the project-wide reference. It demonstrates:
- `mock_aws()` context from `moto` for in-process DynamoDB (lines 97, 44–46).
- `object.__setattr__(T, "ssh_keys", ...)` to patch a frozen table handle without forking the settings object (lines 108–109).
- `asyncio.new_event_loop()` to drive async handlers, never `asyncio.get_event_loop()` (the project convention for hermetic offline tests; `TestClient` is used in some simpler test modules but requires a wired app factory and does not compose cleanly with per-test moto contexts — `asyncio.new_event_loop()` is the canonical pattern for this style of test per `tests/test_gap_0220_0221_ssh_stored_key.py`).
- `patch.object(module, "function", ...)` for KMS stubs at the module boundary (lines 113, 116 — `kms_encrypt` and `kms_decrypt`).
- `patch("app.services.alerts.audit_event", lambda ...: ...)` to capture audit calls (lines 120–127).

**Rate-limiting infrastructure:** `_bucket_limit(user_sub, sid, max_n, win)` at `app/services/rate_limit.py:60` writes to `T.sessions`. For anonymous IP-keyed limiting the caller passes `f"ip#{ip}"` as `user_sub` (the `_ip_user` helper at `rate_limit.py:81`). Tests must provide a moto-backed `T.sessions` table or the rate-limit path will fail on a missing table handle.

**`normalize_email`** at `app/core/normalize.py:60` raises `HTTPException(400)` on malformed input. PRT-004's `create_application` wraps this in `try/except` and proceeds with the raw value — the test must confirm the apply returns 200 (not 400) for a bad email.

**`presign_upload`** at `app/services/filemanager.py:2207` resolves the upload URL using the `S.dev_mode` branch at line 2223: `if S.dev_mode: upload_url = f"{S.public_base_url}/mock/s3/..."`. The PRT-005 résumé presign endpoint delegates entirely to this function — no PRT-level dev/prod branch exists per SECOPS-007. Tests freeze `S.dev_mode = True` so presign returns the `/mock/s3/...` URL without a real S3 presign operation.

**`audit_event`** at `app/services/alerts.py:644` writes to `T.alerts`. Tests patch `app.services.alerts.audit_event` to a no-op lambda so audit writes do not require a live alerts table (following the pattern at `tests/test_gap_0220_0221_ssh_stored_key.py:120-127`).

**`list_session_answers`** at `app/services/questionnaires_repository.py:573` queries `T.questionnaires` by `pk=_q_pk(questionnaire_id)` and `sk BEGINS_WITH ANSWER#{response_session_id}#`. Tests provide a moto-backed `questionnaires` table (or stub the REPO instance) so the screening-answers path can be exercised offline.

**Public endpoint auth model:** `app/routers/calendar.py:2079` (`get_public_event`) carries no `Depends(...)` — it is invoked with just the path parameters. PRT public handlers follow this exact pattern. Tests therefore call handlers with keyword args only; no `request` injection is needed for the happy path.

**E2E auth patterns (`frontend/e2e/catalog-subscriptions.spec.ts:68-81`):** `injectAuth(page, identity)` sets `ui_session`, `ui_csrf`, and `ui_access_token` cookies for an identity. Unauthenticated public calls use `page.request.get/post(url, { data: ... })` without cookies. Admin calls use `injectAuth(page, "charlie_admin")` then `page.request.post(url, { headers: {"x-csrf-token": session.csrf_token}, data: ... })`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off enforcement (case 1)

With `S.career_portal_enabled = False` (toggled via `object.__setattr__(S, "career_portal_enabled", False)`), every handler must call `_require_enabled()` as its first action and raise `HTTPException(404)`. The test verifies this for all eight handlers listed in §4.2. No DDB read or write occurs in the flag-off path — the moto tables need not contain any rows for these assertions.

**Edge case:** `S.career_portal_enabled` defaults to `False` in the real settings (env `CAREER_PORTAL_ENABLED=0`). Tests that exercise the happy path must explicitly set `object.__setattr__(S, "career_portal_enabled", True)` in `setUp` and restore it in `addCleanup`. The `ExitStack` + `addCleanup` pattern from `tests/test_gap_0220_0221_ssh_stored_key.py:94-109` is the correct idiom.

### 5.2 Admin config CRUD (case 2)

`admin_set_config` must:
- Accept `role in {Role.ADMIN, Role.ROOT}` and write the CONFIG/META row.
- Reject `role == Role.USER` with HTTP 403 (checked before any DDB I/O).
- Set `updated_at` (integer `now_ts()`) and `updated_by = actor_sub`.

`admin_get_config` must return the defaults from `S` (no 500) when the CONFIG/META row is absent — the "no config row yet" cold-start scenario.

**Edge case:** `logo_file_path` is set in the config row but the file-manager node was subsequently deleted. `get_portal_config` resolves `logo_url` via `build_download_url(logo_file_path)` (`filemanager.py:2374`), which returns a URL regardless of whether the S3 object exists — resolution is deferred to fetch time. This is intentional and matches the existing file-manager download pattern.

### 5.3 Job listing + slug detail (case 3 + 4)

`list_public_jobs` queries a JOB-* service function (lazy-import + try/except). The test stubs this with a fake that returns a list of two job orders: one `is_public=True` + `status=open` (should appear), one `is_public=False` (must not appear). The listing must return results newest-first by `posted_at`.

Cursor round-trip test: page 1 returns `items=[job_A]` + `cursor=<opaque>`. Page 2 (supplying the cursor) returns `items=[job_B]` + `cursor=None`. Both pages together contain exactly the two public+open jobs. The cursor is validated to round-trip through `encode_cursor` / `decode_cursor` at `app/core/cursor.py:94,103`.

`get_job_detail` returns 404 for:
- Unknown slug (no SLUG# row in `T.career_portal`).
- Known slug but JOB-* returns non-public job order.
- Known slug but JOB-* returns closed job order.
- Known slug but JOB-* absent (ImportError caught → 404).

`CareerJobDetailOut` must omit internal fields: no `pay_rate`, `bill_rate`, or `recruiter_notes`. The test asserts these keys are absent from the returned dict.

### 5.4 RSS feed (case 5)

`build_jobs_rss()` is tested as a pure function (no async, no HTTP). The test provides two job order dicts (one public+open, one closed) to the stub and asserts:
- The returned string is valid RSS 2.0 XML containing exactly one `<item>` (only the public+open one).
- The `<link>` value is `f"{S.public_base_url}/public/careers/jobs/{slug}"`.
- A job title containing `&`, `<`, `>` is correctly XML-escaped in `<title>` and `<description>`.
- JOB-* absent → `build_jobs_rss()` returns a valid XML string with an empty `<channel>` (zero `<item>` elements) and no exception.

### 5.5 Apply happy path (case 6)

The test seeds a `SLUG#{slug}/META` row in the moto `T.career_portal` table and stubs `get_job_order_for_apply` to return a fake open+public job order. It patches `create_candidate` with a spy that returns `{"candidate_id": "cnd_test_001"}` and patches `add_candidate_to_pipeline` with a spy that returns `{"pipeline_id": "pip_test_001"}`.

`create_application(slug="test-slug", data=CareerApplyIn(first_name="Jane", last_name="Doe", email="jane@example.com"), source_ip="10.1.2.3")` must:
- Return `CareerApplyOut(application_id=..., candidate_id="cnd_test_001", status="received")`.
- Have called `create_candidate` exactly once with `source="career_portal"` and `origin_job_order_id` matching the slug-resolved ID.
- Have called `add_candidate_to_pipeline` exactly once with `status="100"`.

The `audit_event` spy must have been called once with `event="career_portal.applied"` and `user_sub="anonymous"`.

### 5.6 Honeypot rejection (case 7)

`data.honeypot = "filled_by_bot"` → `create_application` returns `CareerApplyOut(application_id="bot", status="received")`. The `T.career_portal.scan()` must return zero items. The `create_candidate` spy must not have been called. The `audit_event` spy must not have been called.

**Edge case:** A very long honeypot string (e.g., 10 000 characters) must still hit the honeypot path (not a 422 Pydantic validation error). The `CareerApplyIn.honeypot` field must have no `max_length` constraint, mirroring `docs/suitecrm/specs/CMP-006.md:191` (`WebLeadCaptureIn.honeypot: Optional[str] = None` with no length).

### 5.7 Rate-limit enforcement (case 8)

The test patches `S.career_portal_apply_rate_limit_per_ip_per_hour = 3`. A moto-backed `T.sessions` table is provided for `_bucket_limit`. Three successive calls from `source_ip="10.1.2.3"` all return `status="received"`. The fourth call raises `HTTPException(429)`. The fifth call from a different IP `source_ip="10.1.2.4"` succeeds (buckets are per-IP).

**Edge case:** `source_ip=""` (missing XFF + no direct host). `_bucket_limit("ip#unknown", "rl#career_apply", ...)` treats all such requests as sharing one budget — the test verifies this by sending `N+1` calls with empty IP, confirming the (N+1)th raises 429.

### 5.8 Malformed email captured without 400 (case 9)

`data.email = "not-an-email"` → `normalize_email` raises `HTTPException(400)` inside `create_application`'s try/except → the raw value `"not-an-email"` is passed to the `create_candidate` spy. The endpoint returns 200 with `status="received"`, not 400. The `create_candidate` spy call's `data.email` argument equals `"not-an-email"`.

### 5.9 Tier-1 absence graceful degradation (case 10)

`create_candidate` raises `ImportError("CND not installed")`. `create_application` must still return `CareerApplyOut(status="received")` with `candidate_id=None`. No 500. `add_candidate_to_pipeline` must not have been called (since there is no candidate_id to pass it). Audit event must have been called with `candidate_id=None`.

Second sub-case: `create_candidate` succeeds but `add_candidate_to_pipeline` raises `ImportError`. The endpoint still returns `status="received"` with a valid `candidate_id`. No 500.

### 5.10 Résumé presign (case 11)

`presign_resume(slug, CareerResumePresignIn(filename="cv.pdf", content_type="application/pdf", size_bytes=500_000, honeypot=None), source_ip="10.0.0.1")` must return a `CareerResumePresignOut` with a non-empty `upload_url`, a non-empty `ticket_id`, a `path` containing `"/career-portal/resumes/"`, and `content_type="application/pdf"`. In the test environment `S.dev_mode = True` so `upload_url` starts with `f"{S.public_base_url}/mock/s3/"`.

Bad content-type (`content_type="image/gif"`) → `HTTPException(422)` with `code=unsupported_content_type`.

Over-size declaration (`size_bytes=S.career_portal_resume_max_bytes + 1`) → `HTTPException(413)` with `code=resume_too_large`.

Honeypot filled → `CareerResumePresignOut` with a fake `ticket_id="bot"` and no `T.file_manager` write, mirroring the apply honeypot behavior.

### 5.11 Full apply with résumé + screening answers (case 12)

Seeds a `questionnaires` table row with `pk=_q_pk("q_001")`, `sk=ANSWER#session_abc#q1`, `value="Python"`. Patches `create_candidate` to be a spy. Calls `create_application(..., data=CareerApplyIn(..., resume_ticket_id="ticket_001", screening_response_session_id="session_abc"))`.

`register_presigned_upload` spy must have been called once. `create_candidate` spy must have been called with `screening_answers={"q1": "Python"}` in its `data`. The endpoint returns 200 with `status="received"`. A failure in `register_presigned_upload` (raises `Exception`) must still return 200 (best-effort; candidate is created regardless).

### 5.12 IP anonymization (case 13)

`source_ip="192.168.1.99"` → any persisted `source_ip` attribute on audit calls or application rows must equal `"192.168.1"` (last octet stripped — `_ip_prefix` returns `".".join(parts[:3])`, three octets only, no trailing `.0` per `rate_limit.py:84-91`). IPv6 `source_ip="2001:db8:85a3:0000:1234:5678:9abc:def0"` → stored as `"2001:db8:85a3:0000"` (first four groups only).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 compliance

PRT-006 enforces dev/prod parity by design: it tests service code with no `if S.dev_mode:` branch in the PRT service layer. The only environment-sensitive behavior is inside `presign_upload` at `app/services/filemanager.py:2223` (dev returns a `/mock/s3/...` URL, prod returns a presigned AWS URL). Tests freeze `S.dev_mode = True` so the mock URL path is taken — the production code path is unchanged and tested identically.

`audit_event` (`app/services/alerts.py:644`) is patched to a no-op in offline tests to avoid requiring a live alerts table; the patch is at the source symbol so both dev (DDB local) and prod (real DDB) code paths run identically and are only bypassed in the test fixture.

### 7.2 Idempotency

The apply endpoint is **not** idempotent by design — submitting the same email twice creates two Candidate records (or, when CND-* supports deduplication, one Candidate with the pipeline entry added once). Tests do not assert idempotency behavior because that contract belongs to CND-* (LED-005 §5.4 analogue). PRT-006 tests only that repeated calls within the rate-limit window succeed and calls beyond the limit return 429.

The `resume-presign` endpoint generates a fresh `ticket_id` (UUID) on every call — it is inherently non-idempotent. Two calls with the same `path` will fail on the second call because `require_not_exists` in `presign_upload` raises if the file node already exists. The test exercises only single calls.

### 7.3 Security assertions in tests

- **Honeypot response is structurally identical to success** — the test asserts `response["status"] == "received"` for both normal and honeypot paths. A bot that submits the honeypot receives no distinguishable signal.
- **IP anonymization** is asserted at the audit-event call level (§5.12) — no raw IP ever appears in a persisted attribute.
- **Public fields only** — `get_job_detail` response dict is checked for absence of `pay_rate`, `bill_rate`, `recruiter_notes` (§5.3).
- **USER role → 403 on admin endpoints** — `admin_set_config` with `role=Role.USER` raises 403 before any DDB write (§5.2).
- **CSRF not applicable** — public POST endpoints carry no `ui_session` cookie; the CSRF gate at `app/services/sessions.py:429` only fires when a session cookie is present (CMP-006 §7). Tests call handlers directly, bypassing middleware; E2E public calls use `page.request` without cookies.
- **No Tier-1 credentials leak** — when JOB-* is absent, the 404 response body is `{"detail": "Job posting not found"}`, not an import traceback or internal error detail.

## 8. Backward Compatibility & Migration

PRT-006 is a test-only ticket. It introduces no schema changes, no new endpoints, and no runtime behavior. It has no migration requirements.

The test file `tests/test_prt_career_portal.py` is additive to the test suite. Because it uses `mock_aws()` scoped per test case (not a module-level context), it cannot leak moto state to other test modules. The `object.__setattr__` patches on `T` and `S` are always restored via `addCleanup` callbacks, leaving the frozen objects in their original state after each test.

The E2E spec `frontend/e2e/career-portal.spec.ts` is additive to the Playwright suite. It runs with `workers: 1, retries: 1` per `frontend/playwright.config.ts`. All test data is keyed on a timestamp suffix (e.g., `slug: "e2e-test-${Date.now()}"`) to prevent cross-run collisions in the shared DDB local instance.

## 10. Open Questions / Assumptions

1. **CND-*/PIP-* admin endpoints for E2E assertion (Section B):** The full apply → candidate → pipeline E2E chain requires admin read endpoints from CND-* and PIP-* to verify the Candidate and pipeline entry were created. These are forward dependencies. Until they ship, Section B's admin assertions are conditionally skipped (test marks itself `test.skip`). The core apply assertion (`status="received"` + non-empty `candidate_id`) is always enforced.

2. **JOB-* admin seeding for E2E:** Sections A–E require at least one real job order in DDB to resolve slugs. The `SLUG#{slug}/META` row can be seeded directly into DDB local by the `beforeAll` block using `e2e_admin_session_setup.py`'s DDB client, or via a JOB-* admin create endpoint once that ticket ships. The spec assumes direct DDB seeding (`e2e_admin_session_setup.py` pattern) is acceptable for bootstrap.

3. **Rate-limit bucket isolation across test runs:** `_bucket_limit` uses `T.sessions` with key `user_sub="ip#<zeroed-ip>"`. Each test run's `beforeAll` should use a distinct IP suffix (e.g., `10.${workerIndex}.0.0`) to avoid cross-run bucket collisions. Alternatively, `just restart` between suite runs wipes DDB.

4. **`register_presigned_upload` file-manager table in pytest:** Case 12 requires `T.file_manager` to be moto-backed. The test must either provide a moto file-manager table or patch `register_presigned_upload` at the service boundary. The recommended approach is patching since the file-manager schema is complex (multiple index types) and duplicating it in test setUp is fragile.

5. **Questionnaire REPO instance in pytest (case 12):** `list_session_answers` is a method on a `DynamoQuestionnaireRepository` instance (`REPO`) held at module level in `app/routers/questionnaires.py:24` (NOT in `questionnaires_repository.py` — that file only defines the class). The test can either provide a moto-backed questionnaires table and bind it to the REPO instance via `object.__setattr__`, or patch the `REPO.list_session_answers` method directly on the router module. The patch approach is preferred for test isolation.

6. **RSS `<pubDate>` RFC-822 formatting:** `build_jobs_rss` formats `posted_at` (integer Unix timestamp) as RFC-822. The test asserts the presence of `<pubDate>` and that it does not raise; it does not assert the exact format string to avoid locale-sensitivity.
