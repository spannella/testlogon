## 1. Summary & Goal

Lay the complete data-model, DynamoDB table, settings, and Pydantic-model foundation that every subsequent JOB-* ticket depends on. **Zero application logic ships in this ticket**: no service functions, no router endpoints, no background tasks. The deliverables are exactly:

1. Two new `Settings` fields — master flag `ats_enabled` + sub-gate `job_orders_enabled` — plus the DynamoDB table-name setting.
2. One new `TableDef` in `scripts/local-ddb-init.py` with five GSIs and numeric-key `attr_types`.
3. One new `T.job_orders` handle wired into the `Tables` dataclass.
4. Three Pydantic models (`JobOrderCreateIn`, `JobOrderUpdateIn`, `JobOrderOut`) and two tuple constants (`JOB_ORDER_TYPES`, `JOB_ORDER_STATUSES`) in `app/models.py`.
5. Hermetic unit tests validating the models and confirming the settings default to `False`.

The structural template throughout is OPP-001 (`docs/suitecrm/CRM_OPPORTUNITIES_TICKETS.md` lines 18–131), the Sales Opportunities data model ticket which follows the identical table-then-models-then-flags pattern.

**Why now:** The gap analysis (`docs/opencats/OPENCATS_GAP_ANALYSIS.md:53-61`) establishes that a Job Order / requisition is entirely absent from the platform — HRM "Positions" model internal employee roles and OPP "Opportunities" model sales deals; neither is a client recruiting requisition. Every downstream JOB ticket (CRUD service JOB-002, REST router JOB-003, list views JOB-004, openings counter JOB-005, link resolution JOB-006, frontend JOB-007, full test suite JOB-008) imports from the artifacts produced here. No changes to any existing file are required except additive appends to `app/core/settings.py`, `scripts/local-ddb-init.py`, `app/core/tables.py`, and `app/models.py`.

## 3. Data Model

### 3.1 DynamoDB table — `job_orders`

**Single-table layout.** All rows share `pk` (string) + `sk` (string). Two logical row types exist (defined here for documentation; written by JOB-002):

| Row type | `pk` | `sk` | Written by |
|---|---|---|---|
| Job Order META | `COMPANY#{client_company_id}` | `JOB#{job_id}` | JOB-002 `create_job_order` |
| Per-recruiter index | `COMPANY#{client_company_id}` | `RECRUITER#{sub}#JOB#{job_id}` | JOB-002 per `recruiter_subs` entry |

The two-row approach is the same single-table de-normalization pattern used by the messaging table (conversation META row + per-participant index rows) and the KYC cases table.

### 3.2 `TableDef` entry — `scripts/local-ddb-init.py`

Add at the end of the `_table_defs()` return list, after the `returns` `TableDef` (currently the last entry, at `scripts/local-ddb-init.py:2483-2492`; the `Contacts` entry at line 691 is NOT the last — many subsequent tickets have appended entries since that reference was written). Follow the exact `TableDef` + `_resolve_table_name` pattern at `scripts/local-ddb-init.py:42-71`:

```python
# ATS — Job Orders (JOB-001)
TableDef(
    _resolve_table_name(S.job_orders_table_name, "job_orders"),
    "pk",
    "sk",
    gsi=[
        {"index_name": "GSI_BY_STATUS",    "partition_key": "status",        "sort_key": "created_at"},
        {"index_name": "GSI_BY_RECRUITER", "partition_key": "recruiter_sub", "sort_key": "created_at"},
        {"index_name": "GSI_HOT",          "partition_key": "hot_flag",      "sort_key": "created_at"},
        {"index_name": "GSI_PUBLIC",       "partition_key": "public_flag",   "sort_key": "created_at"},
        {"index_name": "GSI_DIRECT",       "partition_key": "job_id"},
    ],
    attr_types={"created_at": "N", "updated_at": "N"},
),
```

**GSI rationale:**

| Index | PK | Sort key | Consumer |
|---|---|---|---|
| `GSI_BY_STATUS` | `status` (string) | `created_at` (N) | JOB-004 `list_open` — query per non-terminal status, newest-first |
| `GSI_BY_RECRUITER` | `recruiter_sub` (string) | `created_at` (N) | JOB-004 `list_mine` — query by caller's sub, newest-first |
| `GSI_HOT` | `hot_flag` (string literal `"1"`) | `created_at` (N) | JOB-004 `list_hot` — sparse; only rows where `hot=True` carry the attr |
| `GSI_PUBLIC` | `public_flag` (string literal `"1"`) | `created_at` (N) | Future PORTAL-* / career portal public listing |
| `GSI_DIRECT` | `job_id` (string) | — (no sort key) | JOB-002 `get_job_order` resolves META row by bare `job_id` |

**`attr_types` requirement:** `GSI_BY_STATUS`, `GSI_BY_RECRUITER`, `GSI_HOT`, and `GSI_PUBLIC` all use `created_at` as their sort key, which is stored as a numeric Unix timestamp integer. DynamoDB Local and production DynamoDB require the `AttributeDefinition` to declare type `"N"` for any attribute used in a GSI key schema. Without `attr_types={"created_at": "N"}`, DDB stores the value as a `String` and queries that pass integer comparison values raise `ValidationException` at runtime. The precedent is the `users` table at `scripts/local-ddb-init.py:49-54`. `updated_at` is declared in `attr_types` as well because future tooling may project it into a secondary index.

**Sparse GSI pattern for `hot_flag` and `public_flag`:** The attribute is only written to DDB when the corresponding boolean is `True`. When `hot=False` (the default), the `hot_flag` attribute is absent from the row entirely — DynamoDB does not index absent attributes, so `GSI_HOT` contains only genuinely hot job orders. JOB-002 is responsible for setting/removing these attributes on create/update; this ticket only declares the table schema. The same pattern applies to `GSI_PUBLIC`.

### 4.2 `JobOrderCreateIn`

```python
class JobOrderCreateIn(BaseModel):
    title: str = Field(..., min_length=1, max_length=255)
    type: str = Field(..., description="One of JOB_ORDER_TYPES")
    status: str = Field(default="active", description="One of JOB_ORDER_STATUSES")
    openings: int = Field(default=1, ge=0, le=10_000)
    client_company_id: str = Field(..., min_length=1, max_length=128)
    client_contact_id: Optional[str] = Field(None, max_length=128)
    recruiter_subs: List[str] = Field(default_factory=list, max_length=25)
    hot: bool = False
    public: bool = False
    pay_rate_cents: Optional[int] = Field(None, ge=0)
    bill_rate_cents: Optional[int] = Field(None, ge=0)
    duration: Optional[str] = Field(None, max_length=120)
    city: Optional[str] = Field(None, max_length=120)
    state: Optional[str] = Field(None, max_length=120)
    description: Optional[str] = Field(None, max_length=20_000)

    @model_validator(mode="after")
    def _validate_enums(self) -> "JobOrderCreateIn":
        if self.type not in JOB_ORDER_TYPES:
            raise ValueError(f"type must be one of {JOB_ORDER_TYPES}")
        if self.status not in JOB_ORDER_STATUSES:
            raise ValueError(f"status must be one of {JOB_ORDER_STATUSES}")
        return self
```

**Field notes:**
- `client_company_id` is required and stored as an opaque string (PTY-008 ref). Shape validation only; existence is not checked here.
- `recruiter_subs` has `max_length=25` on the list to prevent unbounded RECRUITER# index row creation in JOB-002.
- `pay_rate_cents` / `bill_rate_cents` follow the platform-wide convention of storing money amounts as integer cents (consistent with `amount_cents` in `OpportunityCreateIn`, billing ledger entries, catalog prices throughout the codebase).
- `duration` is a free-text field (e.g. `"6 months"`, `"permanent"`) rather than a structured duration type, matching the OpenCATS data model.

## 5. Detailed Behavior & Edge Cases

This ticket has no runtime behavior beyond model instantiation and DDB table creation. The following edge cases pertain specifically to the model validation and table definition:

**`type` and `status` validation:** The `@model_validator(mode="after")` on both `JobOrderCreateIn` and `JobOrderUpdateIn` raises `ValueError` (converted by FastAPI to HTTP 422) for any value not in `JOB_ORDER_TYPES` / `JOB_ORDER_STATUSES`. The validator is `mode="after"` so all field-level validation (length, ge/le) runs first; the enum check only fires for strings that passed the other checks. For `JobOrderUpdateIn`, the guard is conditional on `is not None` — a missing field is always valid.

**`recruiter_subs` list length:** The `max_length=25` on the list field is enforced by Pydantic v2's `Field(max_length=...)` on list types as a max-items constraint. This prevents pathological `RECRUITER#` index row fan-out in JOB-002 (writing one DDB item per sub per create/update). If the platform later requires larger recruiter teams, this constant can be raised without a schema migration.

**`openings=0`:** Allowed. A job order with `openings=0` represents a position that exists but has no explicit quota (e.g., open-ended contract pool). JOB-005's auto-`full` transition fires only when `openings > 0` and `placed_count >= openings`; with `openings=0` it does not fire.

**`status` initial value:** `JobOrderCreateIn.status` defaults to `"active"`. A caller may pass `status="lead"` or `status="upcoming"` at creation to represent pre-sale or future orders. The state-machine (JOB-002) enforces the `lead → active` and `upcoming → active` transitions thereafter.

**`description` length cap:** 20,000 characters matches the `description` cap used on opportunities and the questionnaire long-text field max. Very long job descriptions (JD boilerplate) are accommodated; the DDB item size limit (400 KB) is not approached at this length even with all other fields set.

**`GSI_DIRECT` has no sort key:** Unlike the other four GSIs, `GSI_DIRECT` is a partition-key-only index. This is intentional: `job_id` is globally unique (UUID-based, minted by JOB-002 as `"job_" + uuid4().hex`), so the index always returns at most one item and a sort key would be redundant. The absence of a sort key also means this GSI does not appear in `attr_types` — only numeric sort keys require declaration.

**`updated_at` in `attr_types`:** `updated_at` is declared alongside `created_at` in `attr_types={"created_at": "N", "updated_at": "N"}` even though no current GSI uses it as a sort key. This is defensive: a future GSI keyed on `updated_at` (e.g. a "recently modified" view) would fail at table-creation time if the type declaration is absent. Adding it to `attr_types` costs nothing.

**Table-naming via `_resolve_table_name`:** The pattern `_resolve_table_name(S.job_orders_table_name, "job_orders")` matches every other `TableDef` in `scripts/local-ddb-init.py:42-71`. The second argument is the base name; `_resolve_table_name` prepends any configured table prefix. The default value `"job_orders"` (set by `S.job_orders_table_name`) is the table name used in tests (no prefix in the dev/test environment).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity:** No `if S.dev_mode` branch exists in this ticket. The `TableDef` and `T.job_orders` handle are defined identically in dev and prod. DynamoDB Local (dev) and DynamoDB on-prem/cloud (prod) both consume the same `TableDef` schema. The `_resolve_table_name` helper handles any environment-specific table prefixing transparently.

**Table creation idempotency:** `scripts/local-ddb-init.py` wraps each `create_table` call in a `try/except ResourceInUseException` (the existing pattern throughout the file). Running `local-ddb-init.py` a second time with the `job_orders` table already present is a no-op. No data is lost.

**Model immutability:** `JobOrderCreateIn` and `JobOrderUpdateIn` are standard Pydantic `BaseModel` instances. Validators run on construction and do not mutate state. The validator raises `ValueError`, which FastAPI translates to a well-formed 422 `RequestValidationError` response — no information leakage beyond the field name.

**`recruiter_subs` content:** The model accepts any list of strings as `recruiter_subs`. Shape validation (max items, max string length) is enforced here; existence validation (is the sub a real user?) is the concern of JOB-002 and eventually the LED-010 assignment layer. This separation prevents a hard dependency on `T.users` at model-validation time.

**No PII in the table definition:** The `job_orders` table holds commercial recruiting data (job titles, pay rates, company references). Pay rates (`pay_rate_cents`, `bill_rate_cents`) are stored as integers. No candidate PII is stored in this table; that is the CND-* cluster's concern.

## 10. Open Questions / Assumptions

**OQ-1 — `type` as string vs. `Literal` union:** Using a tuple constant + validator follows the existing `OPPORTUNITY_STAGES` pattern. An alternative is `Literal["hire","contract","contract_to_hire","referral"]`, which gives OpenAPI schema documentation automatically. Either is acceptable; the tuple approach is used here for consistency with the OPP-001 template.

**OQ-2 — `pay_rate_cents` vs. structured rate object:** OpenCATS stores pay and bill rates as plain floats with a separate `type` (hourly / yearly / flat). The simplified `pay_rate_cents` integer field here is sufficient for Tier 1 MVP; a structured `RateOut` (amount + cadence) can be added additively later without a migration.

**OQ-3 — Table naming in production:** `_resolve_table_name(name, fallback)` returns `name or fallback` (`scripts/local-ddb-init.py:38-39`) — it does **not** prepend any prefix; there is no `S.ddb_table_prefix` setting in the codebase. Environment-specific table naming is achieved entirely by setting the env var `DDB_JOB_ORDERS_TABLE` to the desired name (e.g., `prod_job_orders`). This is the same mechanism all other tables use.

**OQ-4 — `GSI_PUBLIC` capacity:** If the career portal (PORTAL-*) receives high traffic, `GSI_PUBLIC` (which indexes all public job orders globally) may become a hot partition. The mitigation at that point is sharding by `company_id` or a date-bucketed PK — but this is out of scope for Tier 1 and can be deferred to the PORTAL-* design.

**Assumption A1:** `client_company_id` and `client_contact_id` are stored as opaque strings and validated for shape only (min/max length). They are not validated against any company or contact table here or in JOB-002. Existence validation is the responsibility of the UI layer and eventually the PTY-008 / CCT-001 integration in JOB-006.

**Assumption A2:** The `job_id` format (`"job_" + uuid4().hex`) is minted by JOB-002's `create_job_order`, not validated at model level. `JobOrderCreateIn` does not include `job_id` (server-assigned); `JobOrderOut` carries it as a read-only field.
