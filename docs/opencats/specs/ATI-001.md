# ATI-001 — Company & contact ATS field gaps — `key_technologies` / `fein` / `billing_contact_party_id` + contact `title` / `is_hot`

**Type:** Feature | **Priority:** P2 | **Estimate:** 2d  
**Source:** `docs/opencats/ATS_INTEGRATION_TICKETS.md` — ATI-001 section  
**Flags:** `PARTY_CRM_ORG_ACCOUNTS_ENABLED` (Part A — org fields), `PARTY_CRM_ENABLED` (Part B — contact fields). No new flag.

---

## 1. Summary & Goal

OpenCATS stores three company-level ATS fields (`key_technologies`, `fein`, `billing_contact_party_id`) and two contact-level fields (`title`, `is_hot`) that have no equivalent in the planned OFBiz Party/CRM buildout. This ticket closes all five gaps with the minimum delta:

- **Part A** — three additive attributes on `CrmOrgAccountOut`, the PARTY_GROUP META row, and `CrmOrgAccountUpdateIn`; carried by the CCT-001 `PATCH /ui/party/orgs/{id}` endpoint with an extended allow-list. No new endpoint for Part A.
- **Part B** — two additive attributes on `CrmPartyOut` and the PERSON META row; a new `PATCH /ui/party/parties/{party_id}` endpoint backed by a new `update_person` service helper.

No new tables, no new GSIs, no new feature flags.

## 2. Context & Current State

`app/services/party.py` and `app/routers/party.py` do not yet exist (`find app/ -name party.py` returns nothing). All PTY-001..PTY-012 and CCT-001/CCT-003 specs are planned but unimplemented; citations below reference those spec docs.

**Flags** — `grep -n "party_crm" app/core/settings.py` returns nothing. PTY-001 (`docs/ofbiz/specs/PTY-001.md:118–121`) adds `party_crm_enabled` and `party_crm_org_accounts_enabled`; both default `False`. ATI-001 gates on these two flags, no new flag.

**`CrmOrgAccountOut`** — PTY-003 defines seven fields (`docs/ofbiz/specs/PTY-003.md:536–549`). CCT-001 appends five (`docs/suitecrm/specs/CCT-001.md:§4.2`): `industry`, `website`, `phone`, `employee_count`, `annual_revenue_cents`. None of the three ATS fields (`key_technologies`, `fein`, `billing_contact_party_id`) are present.

**`CrmPartyOut`** — PTY-003 defines six fields (`docs/ofbiz/specs/PTY-003.md:489–496`; header at :486, code fence at :488). CCT-003 appends two (`docs/suitecrm/specs/CCT-003.md:§3.4`): `manager_party_id`, `direct_report_count`. Neither `title` nor `is_hot` is present.

**`update_org_account`** — CCT-001 (`docs/suitecrm/specs/CCT-001.md:§4.3`) introduces this function in `app/services/party.py`. It builds a dynamic `UpdateExpression`, uses `model_fields_set` to distinguish explicit-null (REMOVE) from field-absent (no-op) — the same pattern confirmed live at `app/routers/newsfeed.py:3893` — and holds an allow-list `{"industry","website","phone","employee_count","annual_revenue_cents"}`. ATI-001 extends this set by three keys.

**`PATCH /ui/party/orgs/{org_party_id}`** — registered by CCT-001 (`docs/suitecrm/specs/CCT-001.md:§4.6`). No new endpoint needed for Part A; the handler already passes `body.model_dump(include=body.model_fields_set, exclude_unset=True)` to `update_org_account`.

**Person PATCH route collision with PTY-011** — PTY-011 (`docs/ofbiz/specs/PTY-011.md:178,210–215`) already defines `PATCH /parties/{party_id}` (handler `update_party_status`, body `CrmPartyStatusIn`). ATI-001 introduces a second handler at the same path with body `CrmUpdatePersonIn`. FastAPI registers routes by declaration order; registering two `@router.patch("/parties/{party_id}")` handlers means the second silently shadows the first. **Resolution:** the implementer MUST merge both update types into the existing `update_party_status` handler — either by accepting a union body (`CrmPartyStatusIn | CrmUpdatePersonIn`), or by checking `party_type` inside the handler to dispatch, or by moving ATI-001's person fields into a sub-path such as `PATCH /parties/{party_id}/person`. The spec code block below shows the second approach as written; the route path and/or handler strategy must be reconciled with PTY-011 before implementation. CCT-003 adds only `PUT/DELETE/GET` under `/parties/{party_id}/manager` and `/reports-to` (`docs/suitecrm/specs/CCT-003.md:§4.2`); those two-segment-tail endpoints do not conflict.

**`audit_event`** — `app/services/alerts.py:644` (confirmed live). `normalize_phone` — `app/core/normalize.py:66` (confirmed live). `require_ui_session` — `app/services/sessions.py:330` (confirmed live; used at `app/routers/contacts.py:12`).

## 3. Data Model

ATI-001 writes only to the existing `party` table (PTY-002, `docs/ofbiz/specs/PTY-002.md:70–113`). No new tables, GSIs, or `attr_types` entries. The five new fields are plain top-level attributes on existing item rows.

**Part A — PARTY_GROUP META row additions:**

| Attribute | DDB type | Absent-when rule |
|---|---|---|
| `key_technologies` | List (L) of String (S) | Absent when empty or `None` (REMOVE on `[]`) |
| `fein` | String (S) | Absent when `None` |
| `billing_contact_party_id` | String (S) | Absent when `None` |

`key_technologies` tags are deduped, lower-trimmed (strip + lowercase), and stored sorted. Max 50 tags; each tag 1–64 chars after trimming. Example stored value: `["aws", "postgresql", "python"]`.

**Part B — PERSON META row additions:**

| Attribute | DDB type | Absent-when rule |
|---|---|---|
| `title` | String (S) | Absent when `None` |
| `is_hot` | Bool (BOOL) | Absent when `False`; stored only when `true` |

`is_hot=False` is expressed as a REMOVE (absent attribute) rather than Bool `false`. `bool(item.get("is_hot", False))` in the projection yields `False` for both absent and explicitly-`false` stored values — identical externally.

No `attr_types` entries are needed because none of the five fields is a GSI sort key. The `attr_types={"created_at": "N"}` already declared by PTY-002 (`docs/ofbiz/specs/PTY-002.md:110`) is unchanged.

## 4. API / Service Design

### Models — `app/models.py`

```python
# Append to CrmOrgAccountOut (after CCT-001's five fields):
key_technologies:           List[str] = Field(default_factory=list)
fein:                       Optional[str] = None
billing_contact_party_id:   Optional[str] = None

# Append to CrmOrgAccountUpdateIn (CCT-001 model):
key_technologies:           Optional[List[str]] = None   # validator: dedup/lowercase/max-50/max-64
fein:                       Optional[str] = None         # validator: re.match(r"^\d{2}-?\d{7}$", v)
billing_contact_party_id:   Optional[str] = None         # domain-validated at service layer

# Append to CrmPartyOut (after CCT-003's two fields):
title:   Optional[str] = None
is_hot:  bool = False

# New model:
class CrmUpdatePersonIn(BaseModel):
    title:  Optional[str] = Field(default=None, max_length=128)
    is_hot: Optional[bool] = None   # None = absent (no-op); True/False = explicit set
```

`key_technologies` Pydantic validator: strips + lowercases each tag, drops empty strings, deduplicates preserving first-occurrence order, raises `ValueError` for >50 tags or any tag >64 chars.

`fein` Pydantic validator: `re.match(r"^\d{2}-?\d{7}$", v.strip())` — accepts `"12-3456789"` and `"123456789"`. No module-level import needed; `re` already imported at `app/models.py:6`.

### Service — `app/services/party.py`

**`update_org_account` (CCT-001 function, extended):**

Extend the allow-list to include `"key_technologies"`, `"fein"`, `"billing_contact_party_id"`. After the existing ORG_ADMIN check (step 2), insert:

```python
if "billing_contact_party_id" in fields and fields["billing_contact_party_id"] is not None:
    ref = get_party(fields["billing_contact_party_id"])
    if ref is None or ref.get("party_type") != "PERSON":
        raise HTTPException(400, "billing_contact_must_be_person")
```

`key_technologies=[]` or `None` → REMOVE clause. Non-empty list → SET clause (boto3 stores Python list as DynamoDB L). No other changes to the function body.

**New function — `update_person(party_id, actor_party_id, *, fields: dict) -> dict`:**

1. `item = get_party(party_id)`. If absent or `party_type != "PERSON"` → `HTTPException(404, "person_not_found")`.
2. Build `UpdateExpression` from `fields` restricted to allow-list `{"title","is_hot"}`. `v is None` or (`k=="is_hot"` and `v is False`) → REMOVE. Otherwise → SET. Always SET `updated_at = now_ts()`.
3. `T.party.update_item(Key={"PK": f"PARTY#{party_id}", "SK": "META"}, ..., ConditionExpression="attribute_exists(PK)", ReturnValues="ALL_NEW")`. Catch `ConditionalCheckFailedException` → `HTTPException(404)`.
4. `audit_event("party_person_updated", actor_party_id, None, party_id=party_id, updated_fields=list(fields.keys()))`.
5. Return `response["Attributes"]`.

**`_item_to_org_account_out` (PTY-008/CCT-001 helper, extended):**

```python
key_technologies         = list(item.get("key_technologies") or []),
fein                     = item.get("fein"),
billing_contact_party_id = item.get("billing_contact_party_id"),
```

**`_item_to_party_out` (PTY-004/CCT-003 helper, extended):**

```python
title  = item.get("title"),
is_hot = bool(item.get("is_hot", False)),
```

### Router — `app/routers/party.py`

**`PATCH /ui/party/orgs/{org_party_id}`** — CCT-001 endpoint. Handler is unchanged; `CrmOrgAccountUpdateIn` gains three new optional fields.

**New endpoint — `PATCH /ui/party/parties/{party_id}`:**

```python
@router.patch("/parties/{party_id}", response_model=CrmPartyOut)
async def update_person_party(
    party_id: str,
    body: CrmUpdatePersonIn,
    ctx: dict = Depends(require_ui_session),

See the corrected note in §2 for the required resolution. CCT-003's endpoints have two-segment tails (`/manager`, `/reports-to`) and do not conflict.

**Auth:** `require_ui_session` (cookie + CSRF). No admin/root elevation. Status: `200 OK`.

## 5. Detailed Behavior & Edge Cases

**`key_technologies` normalization.** `["Python", "python", " AWS "]` → stored as `["aws", "python"]`. An update setting `key_technologies=[]` sends a REMOVE expression. Tag of 65 chars after trimming → 422. More than 50 tags → 422.

**`fein` format.** `"12-3456789"` and `"123456789"` both accepted. Stored as-is (no canonicalization). `"AB-1234567"` → 422. `"1-2345678"` (first segment must be 2 digits) → 422.

**`billing_contact_party_id` — non-existent or non-PERSON party.** Both map to `HTTPException(400, "billing_contact_must_be_person")`. Setting to `null` in `model_fields_set` → REMOVE. No referential integrity on subsequent party delete; dangling pointer surfaced as the stored string until a future `delete_party` ticket cleans it up.

**`is_hot=False` → REMOVE.** `{"is_hot": true}` stores Bool `true`. `{"is_hot": false}` removes the attribute. Both project as `is_hot: false` and `is_hot: true` respectively via `bool(item.get("is_hot", False))`. Omitting `is_hot` from the PATCH body → no-op.

**`title=null` in `model_fields_set`.** REMOVE expression; attribute absent; subsequent GET returns `title: null`. Empty string `""` is stored as-is (not normalized to `None`).

**Partial update semantics.** Both PATCHes use `model_fields_set` (`app/routers/newsfeed.py:3893` pattern). A body of `{"fein": "12-3456789"}` touches only `fein` + `updated_at`. Concurrent PATCHes are last-writer-wins (no optimistic concurrency counter, consistent with CCT-001 §5.7).

**Flag off.** `PARTY_CRM_ORG_ACCOUNTS_ENABLED=0` → org PATCH 503. `PARTY_CRM_ENABLED=0` → person PATCH 503. No DDB reads or writes occur.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007.** `update_org_account` and `update_person` call `T.party.update_item` identically in dev (DynamoDB Local, `http://localhost:8001` via `.env.local`) and prod (AWS DynamoDB). No `if S.dev_mode:` branch in either function.

**Audit events in both environments.** `audit_event` (`app/services/alerts.py:644`) writes to `T.alerts` in both. Events: `"party_org_account_updated"` on org PATCH; `"party_person_updated"` on person PATCH. Each carries `updated_fields` list.

**`billing_contact_party_id` validation runs in both environments.** The `get_party` call hits `T.party` with no environment conditional.

**Idempotency.** Sending the same PATCH body twice advances `updated_at` on the second call but leaves all field values unchanged. Safe to retry.

**Field allow-listing (defense in depth).** Both service functions silently skip any key not in their respective allow-lists even if a future refactor passes a wider dict. This prevents overwriting `PK`, `SK`, `party_type`, `status`, `created_at`, or GSI keys via crafted input.

**FEIN sensitivity.** Stored as plain String (matches SuiteCRM). DynamoDB server-side encryption at rest covers it. Application-level KMS encryption is deferred.

**No public endpoints.** Both PATCHes require `require_ui_session`; unauthenticated requests return 401 before any service code runs.

## 8. Backward Compatibility & Migration

**All model changes are additive with safe defaults.** `CrmOrgAccountOut` gains three new nullable/empty-list fields; `CrmPartyOut` gains two. Existing callers receive `[]`/`None`/`False` for rows that predate ATI-001. JSON schema gains optional properties only — no required properties change.

**No DynamoDB migration.** Existing PARTY_GROUP META rows lack the three new attributes; `item.get(field)` returns `None`. Existing PERSON META rows lack `title`/`is_hot`; projection defaults apply. No backfill script needed.

**`CrmCreateOrgAccountIn` extension is additive.** Three new optional fields with `None` defaults. Callers that pass only `{"name": "Acme", "owner_user_sub": "usr"}` are unchanged.

**Frontend type stubs (PTY-013).** `CrmOrgAccountOut`, `CrmPartyOut`, and the new `CrmUpdatePersonIn` TypeScript interfaces must be updated. Until then, the JSON serializes correctly; only editor autocomplete is affected.

## 10. Open Questions / Assumptions

1. **`key_technologies` not indexed here.** Skill/tag search is owned by the Tier-2 skill-tags cluster (gap analysis §Tier 2). ATI-001 stores the List attribute only — no GSI, no global tag registry.

2. **FEIN not KMS-encrypted.** Stored as plain String, consistent with SuiteCRM. Application-level encryption via `app/core/crypto.kms_encrypt` (SSH key pattern) deferred to a follow-up if compliance requires it.

3. **`billing_contact_party_id` dangling reference.** No `delete_party` function exists in any planned spec. When deletion is introduced, it should NULL-out `billing_contact_party_id` on referencing orgs. Deferred.

4. **`update_person` has no ownership enforcement.** Any authenticated user can PATCH any PERSON party's `title`/`is_hot` while the flag is on, matching CCT-003's approach. PTY-011 §5.2's record-level ACL will add `_assert_party_access(party_id, ctx["user_sub"])` when it ships.

5. **`is_hot` on Job Orders vs. contacts.** Job Order hotness (a separate `hot` flag) is owned by the JOB cluster. ATI-001 adds `is_hot` only on PERSON parties via the person PATCH endpoint. No `is_hot` is added to `CrmOrgAccountOut`.
