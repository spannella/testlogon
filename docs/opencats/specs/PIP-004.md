# PIP-004 — Candidate rating (1–5) within a pipeline entry

**Ticket type:** Feature
**Priority:** P1
**Estimate:** 1 day
**Master gate:** `S.ats_pipeline_enabled` (`ATS_PIPELINE_ENABLED`, default `false`) — introduced in PIP-001
**Depends on:** PIP-001 (junction table + `rating` attribute + `_require_flag()`), PIP-003 (shares `get_pipeline_entry` + `update_item` helper patterns); ACT-009 (`record_crm_activity`, soft via lazy import)

---

## 1. Summary & Goal

PIP-004 lets a recruiter assign a **1–5 star quality rating** to a candidate within the context of a specific job-order pipeline entry. The rating is per-pipeline, not global — a candidate rated 5 for one job order may be rated 2 for another. Sending `rating=0` explicitly clears a previously set rating back to the unrated baseline.

This is one of the two pieces of per-entry recruiter metadata OpenCATS tracks alongside pipeline status (the other being submit-to-client, PIP-005). It is the simplest stateful mutation in the PIP set: a single `update_item` on the junction row introduced by PIP-001, with an `audit_event` write and a best-effort ACT-009 activity timeline entry.

The feature is fully additive and default-OFF. With `ATS_PIPELINE_ENABLED=false` every service function immediately raises HTTP 503 and no DynamoDB write can occur. With the flag on and `rating=0` (the default on all freshly-created entries per PIP-001), the response is identical to the pre-PIP-004 row shape — no migration needed.

## 2. Context & Current State

**No ATS pipeline exists anywhere in the live tree.** `docs/opencats/OPENCATS_GAP_ANALYSIS.md:69` states "Candidate rating (1–5) within pipeline — **MISSING**." There is no `app/services/ats_pipeline.py`, no `app/routers/ats_pipeline.py`, and no `ats_pipeline` DynamoDB table in the current repository (`app/core/tables.py:68–572` lists every existing handle; `ats_pipeline` is absent).

**PIP-001 reserves the `rating` attribute on the junction row.** `docs/opencats/specs/PIP-001.md §3.1` declares `rating: N` (integer 0–5, default `0`) on the pipeline-entry item and states explicitly: "`rating` — PIP-004 owns writes." PIP-001's `PipelineEntryOut` model already includes `rating: int` (`PIP-001.md §3.2`), so the Pydantic output model requires no change in this ticket.

**PIP-003 establishes the `update_item` mutation pattern on the junction row.** `docs/opencats/specs/PIP-003.md §4.1` shows the standard `T.ats_pipeline.update_item(Key={...}, UpdateExpression="SET #field = :val, updated_at = :ts", ExpressionAttributeNames={...}, ExpressionAttributeValues={...})` form. PIP-004 reuses this identical pattern for `rating` and `updated_at` — no new DDB access pattern is introduced.

**`_FloatSafeTable` coerces integers correctly.** `app/core/tables.py:29–66` defines `_FloatSafeTable._to_decimal`, which coerces Python `float` to `Decimal` on writes. Integer values (such as `rating`) pass through unchanged. All PIP-004 writes go through `T.ats_pipeline` (a `_FloatSafeTable` proxy) — no manual `Decimal` wrapping is needed for the integer rating.

**`audit_event` is the platform audit primitive.** `app/services/alerts.py:644` defines `audit_event(event: str, user_sub: str, request=None, **fields: Any)`. It is fire-and-forget, writes to `T.alerts`, and is called by every service that performs meaningful state changes. PIP-004 calls it once per rating write, recording both the new rating and the previous rating for auditability.

**ACT-009 provides the per-entity timeline primitive.** `docs/suitecrm/specs/ACT-009.md §4.1` specifies `record_crm_activity(entity_type, entity_id, activity_type, activity_id, user_sub, *, summary, metadata)` in `app/services/crm_activity_timeline.py` (ACT-009 deliverable, not yet in the live tree). PIP-004 calls it via a lazy local import inside `try/except` so a missing or disabled ACT-009 module never blocks a rating write — the ordering-independence pattern established in `ACT-009.md §2.3` and already used by PIP-003.

**`require_ui_session` is the auth dependency.** `app/services/sessions.py:330` defines `require_ui_session`. CSRF enforcement on non-GET cookie requests is automatic through this dependency. PIP-004 is a service function; CSRF is enforced by the calling router handler registered in PIP-008.

**`normalize_role` and `Role` enum.** `app/auth/roles.py:48` defines `normalize_role`; `app/auth/roles.py:8` defines `class Role(str, Enum)`. The rating endpoint has no admin gate — it is user-controlled (ownership is enforced by the keyed lookup).

**Ownership-by-key structural authorization.** All pipeline entries are partitioned under `pk=USER#{owner_sub}`. `get_pipeline_entry(owner_sub, job_order_id, candidate_id)` issues `get_item(Key={"pk": f"USER#{owner_sub}", "sk": f"PIPE#{job_order_id}#CAND#{candidate_id}"})`. An attacker substituting a foreign `owner_sub` in the key receives a 404 because the item simply does not exist under their partition — no explicit ACL check is required (OPP-004 §5 structural authorization pattern, `docs/suitecrm/specs/OPP-004.md`).

**`now_ts()` is the timestamp primitive.** `app/core/time.py:2` defines `now_ts() -> int` returning integer Unix seconds. `updated_at` is always set with it; never `time.time()` directly.

## 3. Data Model

### 3.1 DynamoDB table: `ats_pipeline` (no new table, no new GSIs)

PIP-004 introduces **no new DynamoDB tables, item types, or GSIs**. It operates entirely on the `ats_pipeline` table introduced by PIP-001 and reads/writes the `rating` attribute on the existing pipeline-entry junction row.

**Existing pipeline-entry row (PIP-001), attributes mutated by PIP-004:**

| Attribute | DDB type | Description |
|---|---|---|
| `rating` | N | Integer 0–5. `0` = unrated (default). PIP-004 sets this on every call. |
| `updated_at` | N | Integer Unix seconds via `now_ts()`. Updated by every mutation including PIP-003, PIP-004. |

All other attributes (`pk`, `sk`, `pipeline_id`, `job_order_id`, `candidate_id`, `owner_sub`, `status`, `status_rank`, `created_at`) are untouched by PIP-004.

**Key access patterns:**
- Read: `get_item(Key={"pk": "USER#{owner_sub}", "sk": "PIPE#{job_order_id}#CAND#{candidate_id}"})` — primary key lookup; no GSI, no scan.
- Write: `update_item(Key=..., UpdateExpression="SET #r = :r, updated_at = :ts", ExpressionAttributeNames={"#r": "rating"}, ExpressionAttributeValues={":r": rating, ":ts": now_ts()})`.

Because `rating` is a plain item attribute (not a GSI sort key), **no `attr_types` entry** is required in `scripts/local-ddb-init.py`. Only GSI sort keys need `attr_types` declarations to avoid `ValidationException` at query time (CLAUDE.md numeric-GSI gotcha; the `ats_pipeline` `TableDef` in `scripts/local-ddb-init.py` currently has none, matching `PIP-001.md §3.1`).

### 3.2 Pydantic models (`app/models.py`)

Append near the PIP-001/PIP-002/PIP-003 models, in source order:

```python
class PipelineRatingIn(BaseModel):
    rating: int = Field(..., ge=0, le=5,
                        description="1–5 star rating; 0 clears the rating (unrated).")
```

`ge=0` / `le=5` enforces the range at the Pydantic-validation layer, producing an HTTP 422 Unprocessable Entity before the service is reached for any out-of-range value (e.g., `rating=6`, `rating=-1`).

**No new response model.** The existing `PipelineEntryOut` (defined in PIP-001, `models.py`) already carries `rating: int`. The handler returns the updated `PipelineEntryOut` directly from the service, identical to how PIP-003's `change_status` returns the same model.

```python

    job_order_id: str
    candidate_id: str
    owner_sub: str

    status_rank: int
```

## 4. API / Service Design

### 4.1 Service function: `set_rating` in `app/services/ats_pipeline.py`

Add to the existing `app/services/ats_pipeline.py` (created by PIP-001, extended by PIP-002 and PIP-003) without modifying any existing function:

```python
def set_rating(
    owner_sub: str,
    job_order_id: str,
    candidate_id: str,
    rating: int,
) -> "PipelineEntryOut":
    """
    Set or clear the 1–5 star rating on a pipeline entry.
    rating=0 clears a previously set rating.
    Raises HTTP 503 if the flag is off, 404 if the entry is foreign/absent,
    HTTP 400 if rating is out-of-range (defence-in-depth beyond Pydantic layer).
    """
    _require_flag()
    if not (0 <= rating <= 5):
        raise HTTPException(400, detail={"code": "invalid_rating",
                                          "message": "rating must be 0–5"})
    entry = get_pipeline_entry(owner_sub, job_order_id, candidate_id)  # 404 if absent
    # get_pipeline_entry returns PipelineEntryOut (per PIP-001 §4), so use attribute access.
    previous_rating = int(entry.rating)
    entry_pipeline_id = entry.pipeline_id

    T.ats_pipeline.update_item(
        Key={"pk": f"USER#{owner_sub}", "sk": f"PIPE#{job_order_id}#CAND#{candidate_id}"},
        UpdateExpression="SET #r = :r, updated_at = :ts",
        ExpressionAttributeNames={"#r": "rating"},
        ExpressionAttributeValues={":r": rating, ":ts": now_ts()},
    )

    # Always-on audit write (fire-and-forget, never raises)
    try:
        audit_event(
            "pipeline.rated",
            owner_sub,
            None,
            pipeline_id=entry_pipeline_id,
            job_order_id=job_order_id,
            candidate_id=candidate_id,
            rating=rating,
            previous_rating=previous_rating,
        )
    except Exception:
        pass

    # Best-effort ACT-009 timeline write (candidate entity only)
    try:
        from app.services.crm_activity_timeline import record_crm_activity
        import uuid as _uuid
        record_crm_activity(
            entity_type="candidate",
            entity_id=candidate_id,
            activity_type="pipeline_rating",
            activity_id=f"pr_{_uuid.uuid4().hex}",
            user_sub=owner_sub,
            summary=f"Rated {rating}/5" if rating > 0 else "Rating cleared",
            metadata={
                "job_order_id": job_order_id,
                "pipeline_id": entry_pipeline_id,
                "rating": rating,
                "previous_rating": previous_rating,
            },
        )
    except Exception:
        pass

    # Re-fetch and return the updated entry
    updated = get_pipeline_entry(owner_sub, job_order_id, candidate_id)
    return updated  # get_pipeline_entry already returns PipelineEntryOut
```

**Signature (stable public contract):**
```
set_rating(owner_sub: str, job_order_id: str, candidate_id: str, rating: int) -> PipelineEntryOut
```

**No `_entry_to_out` helper.** PIP-001 (`docs/opencats/specs/PIP-001.md §4`) specifies `get_pipeline_entry` returning `PipelineEntryOut(**item)` directly — it does not define a named `_entry_to_out` function. PIP-004 therefore calls `get_pipeline_entry` for the re-fetch and returns its result as-is (a `PipelineEntryOut`). No separate conversion helper is needed or available.

### 4.2 Router endpoint in `app/routers/ats_pipeline.py` (PIP-008 deliverable)

PIP-008 owns the router file and its registration in `app/main.py`. PIP-004 specifies only the one endpoint that PIP-008 must include:

| Method | Path | Auth |
|---|---|---|
| `PUT` | `/ui/ats/pipeline/by-job/{job_order_id}/candidate/{candidate_id}/rating` | `require_ui_session` |

Route declaration (added to `app/routers/ats_pipeline.py` by PIP-008, referencing the service introduced here):

```python
@router.put(
    "/by-job/{job_order_id}/candidate/{candidate_id}/rating",
    response_model=PipelineEntryOut,
)
async def update_pipeline_rating(
    job_order_id: str,
    candidate_id: str,
    body: PipelineRatingIn,
    ctx: Dict = Depends(require_ui_session),
) -> PipelineEntryOut:
    return set_rating(
        owner_sub=ctx["user_sub"],
        job_order_id=job_order_id,
        candidate_id=candidate_id,
        rating=body.rating,
    )
```

**Route-ordering constraint:** this route's path segment `/by-job/{job_order_id}/candidate/{candidate_id}/rating` is a sub-resource route. The router also contains `PATCH .../status` (PIP-003) and `POST .../submit` (PIP-005) and `POST .../placement` (PIP-006) at the same path depth. All are unambiguous because the terminal segment (`/rating`, `/status`, `/submit`, `/placement`) is a literal, not a path parameter. No ordering risk exists between these — FastAPI resolves them deterministically by the literal terminal segment. The ordering constraint from the CLAUDE.md audit-export `/schedules`-before-`/{id}` gotcha applies only when a literal segment could be captured by a sibling dynamic `/{param}` at the same depth; that does not occur here.

**HTTP verb:** `PUT` (idempotent full-replacement semantics — setting rating=4 twice produces exactly the same end state). This is consistent with the PIP-008 route table in `ATS_PIPELINE_TICKETS.md:283`.

**Auth:** `require_ui_session` (`app/services/sessions.py:330`) enforces CSRF automatically on non-GET cookie requests. No additional role gate — the rating operation is user-data-plane, with ownership enforced structurally by the keyed DynamoDB lookup.

**Request body:** `PipelineRatingIn` (section 3.2). Pydantic validation fires before the handler body; `rating=6` never reaches the service.

**Success response:** HTTP 200 with `PipelineEntryOut`, `Content-Type: application/json`.

**Error responses:**

| Status | `detail.code` | Condition |
|---|---|---|
| 422 | (Pydantic validation error) | `rating < 0` or `rating > 5` — model-layer rejection |
| 503 | `ats_pipeline_disabled` | `S.ats_pipeline_enabled == False` |
| 404 | `pipeline_entry_not_found` | Entry absent or foreign owner |
| 400 | `invalid_rating` | Service-layer defence-in-depth (should be unreachable via the model) |

## 5. Detailed Behavior & Edge Cases

### 5.1 Rating semantics

- `rating=1` through `rating=5` sets a star rating (OpenCATS displays 1–5 stars; 5 = best fit).
- `rating=0` is the sentinel for "no rating set." A freshly created pipeline entry (PIP-001) starts at `rating=0`. Submitting `rating=0` is an explicit clear — not a no-op. The service writes `rating=0` and `updated_at=now_ts()`, fires the audit event with `rating=0`, and records a "Rating cleared" timeline summary.
- No distinction is drawn at the service layer between "was already 0, set to 0 again" and "was 4, set back to 0" — both write and audit. (Unlike PIP-003's status-change which has an idempotent same-status no-op shortcut, ratings always write because the intent — explicit clear or explicit set — is always meaningful to the audit log.) If callers want to suppress redundant writes when the rating is unchanged, they must do so in the calling layer (e.g., the FE star control can skip the PATCH if the user clicks the already-selected star).

### 5.2 Concurrent writes

DynamoDB `update_item` is atomic at the single-item level. Two simultaneous `set_rating` calls for the same entry from the same recruiter will each succeed; the last writer wins (last-write-wins). No optimistic locking (`ConditionExpression` on the old value) is applied — last-write-wins is correct for star ratings, which are ephemeral editorial state rather than a ledger. If PIP-009 (FE) adds an optimistic UI update, it should invalidate the React Query cache on 200 rather than relying on the optimistic state to be authoritative.

### 5.3 Ownership boundary

The structural authorization check `get_pipeline_entry(owner_sub, job_order_id, candidate_id)` returns `None` (→ HTTP 404 `pipeline_entry_not_found`) for any of:
- The entry does not exist (has not been added via PIP-001 `add_to_pipeline`).
- The `owner_sub` in the key does not match the authenticated user — the item lives under a different partition and the keyed `get_item` returns nothing.
- The entry was soft-deleted or removed (PIP-001 `remove_from_pipeline`).

There is no separate authorization check. The 404 response is intentionally indistinguishable from "entry does not exist" to avoid leaking the existence of another user's pipeline entry.

### 5.4 Previous-rating capture

The service reads the `previous_rating` from the item fetched by `get_pipeline_entry` before issuing `update_item`. Since `get_pipeline_entry` returns `PipelineEntryOut` (per PIP-001 §4), the read is `entry.rating`. A freshly created entry always carries `rating=0` (PIP-001 sets this at creation), so `entry.rating` is always defined. This value is embedded in the `audit_event` call as `previous_rating=<int>`, giving the audit trail a complete picture of every transition: `{previous_rating: 3, rating: 5}` etc.

### 5.5 ACT-009 timeline: candidate entity only

Unlike PIP-003's `change_status` (which writes two timeline entries — one for the candidate, one for the job-order), PIP-004 writes **one** timeline entry: for the candidate entity only (`entity_type="candidate"`, `entity_id=candidate_id`). The rationale: a rating is a recruiter's assessment of the candidate; the job-order timeline would become very noisy if every rating change on every candidate were recorded there. The `metadata` dict carries `job_order_id` so downstream consumers can reconstruct the job context if needed.

The call is wrapped in `try/except Exception: pass` — a timeline failure never propagates. If ACT-009 has not yet been deployed (`ImportError` on `crm_activity_timeline`), the `except` block catches it silently (ACT-009 §2.3 ordering-independence pattern).

### 5.6 Rating in reporting (PIP-010 / RPT follow-ups)

`rating` is a plain integer attribute on the junction row, visible in any `list_pipeline_for_job` or `list_pipeline_for_candidate` response (PIP-001). Report builder queries (RPT-002/003) can filter or aggregate on it — no additional schema changes are required. No GSI is needed for rating-based sort or filter at the current scale: the pipeline list already returns all entries under a job-order partition and the caller can sort client-side.

### 5.7 Flag-off behavior

When `S.ats_pipeline_enabled == False`:
- `_require_flag()` raises `HTTPException(503, detail={"code": "ats_pipeline_disabled"})`.
- No DDB read is performed. No audit event is emitted. No timeline entry is written.
- The router handler (PIP-008) never mounts the route, so the endpoint returns 404 at the framework level before `_require_flag()` is even reached. The 503 path is exercised only by direct service-function calls in tests.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007: no `if S.dev_mode` business-logic branch

PIP-004 contains zero `if S.dev_mode` or `if S.ats_pipeline_enabled` branches inside the write path. The only env-dependent behaviour is the delivery substrate already abstracted by the reused primitives:

- `T.ats_pipeline` hits in-process moto DynamoDB in dev and real DynamoDB in prod — same boto3 call both ways.
- `audit_event` (`alerts.py:644`) writes to `T.alerts` — same DDB call both ways.
- `record_crm_activity` (ACT-009) writes to `T.crm_activity_timeline` — same DDB call both ways.

There is no email send, no S3 access, and no KMS call in PIP-004. Dev/prod parity is trivially satisfied.

### 7.2 Idempotency

`set_rating(owner_sub, job_order_id, candidate_id, 4)` called twice in succession:
- First call: reads `previous_rating=0`, writes `rating=4`, emits audit `{previous_rating: 0, rating: 4}`.
- Second call: reads `previous_rating=4`, writes `rating=4`, emits audit `{previous_rating: 4, rating: 4}`.

The second call is not a no-op (it writes `updated_at` and emits an audit event). This is intentional: last-write-wins semantics mean the end state is always deterministic, and the audit log records the actual sequence of operations. Callers that wish to suppress redundant round-trips (e.g., the FE star control) should compare the current displayed rating before issuing the request; the service itself has no idempotency guard for same-rating-same-rating.

### 7.3 Structural authorization (no role gate)

The `pk=USER#{owner_sub}` partition key is derived from `ctx["user_sub"]` (the authenticated session identity). No recruiter can rate a pipeline entry they do not own; ownership is enforced by the key shape, not by a runtime permission check. This matches the OPP-004 §5 ownership-by-key pattern.

### 7.4 Input validation layers

| Layer | Mechanism | Out-of-range outcome |
|---|---|---|
| Pydantic | `Field(ge=0, le=5)` on `PipelineRatingIn.rating` | HTTP 422 before handler body |
| Service (defence-in-depth) | `if not (0 <= rating <= 5): raise HTTPException(400, ...)` | HTTP 400 `invalid_rating` |

The service-layer check guards against callers that invoke `set_rating` directly (e.g., in tests or future internal callers) without going through the Pydantic model.

### 7.5 No CSRF special-casing

`require_ui_session` (`sessions.py:330`) automatically enforces CSRF for non-GET cookie-auth requests. `PUT /ui/ats/pipeline/.../rating` is a non-GET, so CSRF is enforced. Bearer-auth callers (API keys, future API-key rollout) bypass CSRF per the platform convention.

## 8. Backward Compatibility & Migration

### 8.1 No existing data to migrate

With `ATS_PIPELINE_ENABLED=false` (the default), the `ats_pipeline` table does not yet exist. When the flag is turned on for the first time, PIP-001's `TableDef` entry in `scripts/local-ddb-init.py` provisions the table on `just restart`. All pipeline entries are created fresh by `add_to_pipeline` (PIP-001) with `rating=0`. There are no pre-existing rows with a missing `rating` attribute to back-fill.

In production, the table will be provisioned via `scripts/local-ddb-init.py` (which runs as part of the first-deploy `just restart` equivalent). Any entries created before PIP-004 is deployed will have `rating=0` from PIP-001's `put_item`. Because PIP-001 always writes `rating=0` at creation, `PipelineEntryOut.rating` will always be `0` for unrated entries — no missing-attribute case exists. The transitional case (`entry.rating` returning `0`) is handled naturally by PIP-001's invariant.

### 8.2 `PipelineEntryOut` is unchanged

`rating: int` is already present in `PipelineEntryOut` (PIP-001). No API version bump, no client-side migration, and no `model_rebuild()` call is required. All existing serialised responses that include `PipelineEntryOut` instances already carry `rating=0` and are byte-for-byte unchanged after PIP-004 ships.

### 8.3 Additive audit events

The new `"pipeline.rated"` audit event type written to `T.alerts` is a net-new string; no existing query filters on `event="pipeline.rated"`, so no existing report or dashboard is affected.

## 10. Open Questions / Assumptions

1. **Rating toggle behavior at the UI layer:** Should clicking the currently-selected star deselect it (sending `rating=0`) or be a no-op? The spec treats `rating=0` as an explicit clear. The FE (PIP-009) should implement toggle-to-clear for the best UX, but the service layer supports either choice. This is a PIP-009 UX decision, not a PIP-004 decision.

2. **Rating visibility to other recruiters:** The current ownership-by-key model means only the owning recruiter can see and modify their own pipeline entries. If a shared-view feature (multiple recruiters collaborating on one job order) is introduced in a future ticket, the rating would be visible to all collaborators with read access. PIP-004 makes no assumption about shared-access — it is a future scope question.

3. **Rating in aggregate statistics:** The gap analysis (§D Reports) mentions pipeline/recruiter reports as a future RPT follow-up. The `rating` field is already present on every `PipelineEntryOut` and is trivially aggregated (average rating per job order, top-rated candidates per pipeline) in RPT-002 report definitions. No schema change is needed when those reports are built.

4. **`get_pipeline_entry` returns `PipelineEntryOut` (not a raw dict):** PIP-001 (`docs/opencats/specs/PIP-001.md §4`) specifies `get_pipeline_entry` returns `PipelineEntryOut(**item)` — a Pydantic model instance. The service code in §4.1 uses `entry.rating` and `entry.pipeline_id` (attribute access, not `entry.get(...)`). If PIP-001's implementation deviates and returns a raw dict, callers must switch to `entry.get("rating", 0)` and `entry.get("pipeline_id")` instead.

5. **No `_entry_to_out` private helper:** PIP-001 does not define a `_entry_to_out` function — it inlines `PipelineEntryOut(**item)` at each return site. PIP-004's `set_rating` returns `get_pipeline_entry(...)` directly (which is already a `PipelineEntryOut`). If the implementation team adds a `_entry_to_out` helper while implementing PIP-001, PIP-004 may use it; otherwise the direct return is correct.
