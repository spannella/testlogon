## 1. Summary & Goal

Add the complete Job Orders frontend: a three-tab list page (Open / Hot / Mine), a detail
page, and a create/edit form. The UI connects exclusively to the REST surface exposed by
JOB-001 through JOB-006. With the feature flags off, the sidebar entry is absent,
the routes do not render, and **every byte of existing platform UI is unchanged**.

OpenCATS's Job Order screen is the recruiter's daily starting point: scan open positions,
identify hot roles, and check their own queue. This ticket delivers that screen using the
project's established conventions — React Query for server state, shadcn/ui primitives,
React Hook Form + Zod for forms, lazy route loading, and a `useInfiniteQuery`-backed list
with cursor pagination — so the implementation integrates naturally with the rest of the
product.

The backend surface this ticket consumes is fully specified in JOB-001 through JOB-006 and
must be deployed before this ticket can be exercised end-to-end. The frontend gate
(`isAtsEnabled()`) is a convenience for hiding nav; the backend remains authoritative.

## 4. API / Service Design

### 4.1 Endpoint wrappers — `frontend/src/api/endpoints/jobOrders.ts`

New file. All calls go through the `api` client (`frontend/src/api/client.ts`) which
attaches the CSRF cookie header (`client.ts:178`) and Bearer token (`client.ts:168-171`)
automatically.

```typescript
import { api } from "@/api/client";
import type {
  AtsFeatureStatus, JobOrder, JobOrderCreateReq, JobOrderListResp,
  JobOrderOpeningsSummary, JobOrderUpdateReq, JobOrderWithLinks,
} from "@/api/types";

const BASE = "/ui/ats/job-orders";

/** No-auth feature flag probe (JOB-003 /feature-status). */
export async function getAtsFeatureStatus(): Promise<AtsFeatureStatus> {
  return api.get<AtsFeatureStatus>(`${BASE}/feature-status`);
}

export async function listOpenJobOrders(params?: {
  cursor?: string; limit?: string; status?: string; company_id?: string;
}): Promise<JobOrderListResp> {
  return api.get<JobOrderListResp>(`${BASE}/open`, params as Record<string, string>);
}

export async function listHotJobOrders(params?: {
  cursor?: string; limit?: string;
}): Promise<JobOrderListResp> {
  return api.get<JobOrderListResp>(`${BASE}/hot`, params as Record<string, string>);
}

export async function listMyJobOrders(params?: {
  cursor?: string; limit?: string;
}): Promise<JobOrderListResp> {
  return api.get<JobOrderListResp>(`${BASE}/mine`, params as Record<string, string>);
}

export async function getJobOrder(
  jobId: string,
  opts?: { expand?: "links" },
): Promise<JobOrderWithLinks> {
  const params = opts?.expand ? { expand: opts.expand } : undefined;
  return api.get<JobOrderWithLinks>(`${BASE}/${jobId}`, params);
}

export async function createJobOrder(req: JobOrderCreateReq): Promise<JobOrder> {
  return api.post<JobOrder>(BASE, req);
}

export async function updateJobOrder(
  jobId: string,
  req: JobOrderUpdateReq,
): Promise<JobOrder> {
  return api.patch<JobOrder>(`${BASE}/${jobId}`, req);
}

export async function setJobOrderStatus(
  jobId: string,
  status: string,
): Promise<JobOrder> {
  return api.post<JobOrder>(`${BASE}/${jobId}/status`, { status });
}

export async function deleteJobOrder(jobId: string): Promise<void> {
  return api.del<void>(`${BASE}/${jobId}`);
}

export async function getOpeningsSummary(
  jobId: string,
): Promise<JobOrderOpeningsSummary> {
  return api.get<JobOrderOpeningsSummary>(`${BASE}/${jobId}/openings`);
}
```

All functions are pure async functions (not hooks) consistent with the existing
`frontend/src/api/endpoints/contacts.ts` pattern — hooks live in pages/components.

### 4.2 React Query key conventions

All query keys are nested under `["ats", "job-orders", ...]` to scope invalidation.

| Query | Key |
|---|---|
| Feature status | `["ats", "feature-status"]` |
| Open list (infinite) | `["ats", "job-orders", "open", statusFilter, companyFilter]` |
| Hot list (infinite) | `["ats", "job-orders", "hot"]` |
| Mine list (infinite) | `["ats", "job-orders", "mine"]` |
| Single job order | `["ats", "job-orders", jobId]` |
| Openings summary | `["ats", "job-orders", jobId, "openings"]` |

## 5. Detailed Behavior & Edge Cases

### 5.1 Feature-flag gating

On mount, `JobOrdersPage`, `JobOrderDetailPage`, and `JobOrderForm` each call
`useQuery(["ats", "feature-status"], getAtsFeatureStatus)`. If `job_orders_enabled`
is `false` (or the fetch fails), the pages render a "Feature not available" placeholder
rather than making further API calls. The sidebar entry is controlled by a separate
`isAtsEnabled()` function (see §6) so the nav is hidden before the user ever navigates
to an ATS page, but the page-level guard is a belt-and-suspenders defense.

The `/feature-status` endpoint requires no authentication (JOB-003 §4.2). The page-level
call uses `useQuery` (not `useInfiniteQuery`) so it fetches once and caches. The stale
time should be 5 minutes (`staleTime: 5 * 60 * 1000`).

### 5.2 JobOrdersPage — tabbed list

**File:** `frontend/src/pages/ats/JobOrdersPage.tsx`

Three tabs backed by `useInfiniteQuery`. Each tab is lazy in the sense that its query is
only enabled when that tab is active (`enabled: activeTab === "open"` etc.) to avoid
unnecessary API calls on initial render.

```
Open tab  → listOpenJobOrders({cursor, limit: "50"})
Hot tab   → listHotJobOrders({cursor, limit: "50"})
Mine tab  → listMyJobOrders({cursor, limit: "50"})
```

Each tab renders a table/card list (shadcn/ui `Table` or `Card` grid) with columns:
- **Title** (link to `/ats/job-orders/:jobId`)
- **Type** (badge: "Hire" / "Contract" / "C2H" / "Referral")
- **Status** (badge, colour-coded — see §5.5)
- **Company** (raw `client_company_id`; full resolution is the detail page concern)
- **Location** (`city`, `state` joined with comma; empty string if both null)
- **Openings** chip: `{openings_remaining} / {openings}` (e.g., "3 / 5")
- **Hot** badge (flame icon, only when `hot === true`)

"New Job Order" button in the page header navigates to `/ats/job-orders/new`.

Infinite scroll: an `IntersectionObserver` sentinel at the list bottom calls
`fetchNextPage()` when `hasNextPage` is true. A "Load more" button is provided as a
fallback for accessibility and as the primary mechanism (matching
`frontend/src/pages/activity/ActivityFeedPage.tsx` which uses a button-only approach —
no `IntersectionObserver` is present in that file; an `IntersectionObserver`-based
sentinel is valid here but has no existing precedent in this codebase to copy from).

Empty states:
- Open tab with no results: "No open job orders" with a "Create one" CTA.
- Hot tab with no results: "No hot job orders. Mark a job order as hot to see it here."
- Mine tab with no results: "You have no assigned job orders."

Loading skeleton: three `Skeleton` rows while the first page loads.

Error state: when the query errors with a non-503, show `toast.error(err.detail)` and an
inline error card with a Retry button.

503 (flags off): render a locked-feature placeholder instead of the list. The 503 JSON
body `{"detail": {"code": "job_orders_disabled"}}` is distinguishable from other errors.

### 5.3 JobOrderDetailPage — single record

**File:** `frontend/src/pages/ats/JobOrderDetailPage.tsx`

Route param: `:jobId`. Fetches `getJobOrder(jobId, { expand: "links" })` via `useQuery`.
Also fetches `getOpeningsSummary(jobId)` via a second `useQuery` (separate cache key so
it can refresh independently when the pipeline later calls `adjust_placed_count`).

**Sections rendered:**

1. **Header** — title, hot badge (if `hot`), public badge (if `public`), type chip,
   status badge with a dropdown control.
2. **Status dropdown** — shows only the legal next statuses. The transition matrix (from
   JOB-002) is mirrored in a client-side helper `ALLOWED_TRANSITIONS: Record<JobOrderStatus, JobOrderStatus[]>`:

   ```typescript
   export const ALLOWED_TRANSITIONS: Record<JobOrderStatus, JobOrderStatus[]> = {
     lead:     ["active"],
     upcoming: ["active"],
     active:   ["on_hold", "full", "closed", "canceled"],
     on_hold:  ["active", "closed", "canceled"],
     full:     ["closed", "canceled"],
     closed:   ["active"],   // only shown when JOB_ORDER_ALLOW_REOPEN (always try; let server 409)
     canceled: [],
   };
   ```

   The dropdown calls `setJobOrderStatus`. On 409 response with
   `{"code": "invalid_status_transition"}`, show a `toast.error` with the server's
   `"from"` and `"to"` fields formatted as "Cannot move from [from] to [to]." The client
   optimistically shows the legal options; if the server rejects, the toast explains why
   and the UI reverts by invalidating the query.

3. **Commercial fields** — pay rate (formatted: `$${(pay_rate_cents/100).toFixed(2)}/hr`
   or "—" if null), bill rate (same format), duration, location (`city, state`).

4. **Openings counter** — large display: `{placed_count} placed / {openings} openings`
   and `{openings_remaining} remaining`. Sourced from `getOpeningsSummary`.

5. **Linked entities** (`links` block from `?expand=links`):
   - Company: show `links.company.name` if resolved, else `{client_company_id}` in muted
     text with an "(unresolved)" label.
   - Contact: show `links.contact.name` + email if resolved, else raw id.
   - Recruiters: list of `display_name` or raw `sub` when unresolved.

6. **Description** — rendered as plain text in a `<pre>`-wrapped block with word-wrap.

7. **Timestamps** — "Created [date]" and "Updated [date]" formatted via `Intl.DateTimeFormat`.

**Action bar** (top-right):
- **Edit** button → navigate to `/ats/job-orders/:jobId/edit`.
- **Delete** button → confirmation dialog (shadcn/ui `AlertDialog`); on confirm calls
  `deleteJobOrder(jobId)`, invalidates both list queries (`["ats","job-orders","open"]`,
  `["ats","job-orders","hot"]`, `["ats","job-orders","mine"]`), navigates to
  `/ats/job-orders`.

Loading state: full-page skeleton with `Skeleton` blocks for each section.
404 response: show `ErrorPage` ("Job order not found").
503 response: show feature-unavailable placeholder (same as §5.2 flag-off case).

Pay/bill rate display convention: fields show dollar amounts (e.g., "25.00"); on submit
multiply by 100 and round to integer before sending to backend.

**Submit flow:**
- Create mode: calls `createJobOrder(values)` via `useMutation`; on success navigates to
  `/ats/job-orders/{job_id}` and calls `queryClient.invalidateQueries(["ats","job-orders","open"])`.
- Edit mode: calls `updateJobOrder(jobId, diff)` where `diff` contains only changed
  fields (computed by comparing form values against the pre-populated baseline).
  On success stays on the form, shows `toast.success("Saved")`, invalidates
  `["ats","job-orders", jobId]` and the list queries.

**Error handling:** Server 422 validation errors are surfaced field-by-field via RHF's
`setError`. Server 409 (optimistic-concurrency conflict from stale `updated_at`) shows
`toast.error("The record was updated by someone else. Please refresh.")` without
navigating away.

### 5.6 Edge cases

- **Soft-deleted orders:** The backend 404s `GET /{job_id}` for soft-deleted items. If
  the user navigates directly to a deleted job's URL, show the 404 `ErrorPage`.
- **Concurrent edit conflict (409):** JOB-002 uses optimistic concurrency
  (`ConditionExpression` on `updated_at`). The `PATCH` endpoint returns 409 when
  `updated_at` is stale. The edit form shows an inline warning rather than silently
  failing.
- **Illegal status transition (409):** `setJobOrderStatus` → `toast.error` with the
  `from`/`to` values extracted from the 409 body. The dropdown returns to the current
  status without a page reload.
- **`recruiter_subs` tag input:** Tags entered as free text (one per Enter keypress or
  comma). In the absence of a user-search API (planned for LED-010), accepts arbitrary
  strings. Renders each as a removable chip.
- **Empty `links` block:** When `?expand=links` is absent (e.g., if the server is an
  older version), the links section is omitted entirely rather than crashing. The
  `JobOrderWithLinks` type makes `links` optional.
- **Currency display for null rates:** When `pay_rate_cents` or `bill_rate_cents` is
  null, display an em dash ("—"), not "$0.00".
- **`openings_remaining` showing 0:** Display a "Full" pill next to the counter if
  `openings_remaining === 0 && status !== "closed" && status !== "canceled"`.
- **Rate limiting (429):** The list endpoints share the backend's global rate limits.
  The `api` client (`client.ts:269-276`) surfaces non-2xx responses as `ApiError`. On
  429, show `toast.error("Too many requests — slow down")` and stop the infinite-scroll
  observer temporarily.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 — no dev_mode branches

The frontend contains no `if (import.meta.env.DEV)` branches in business logic. The
`api` client uses the same `api.get` / `api.post` path in both environments. The
backend already enforces SECOPS-007 across its service layer (JOB-001 through JOB-006).

### 7.2 CSRF

All non-GET calls (`POST`, `PATCH`, `DELETE`) go through `api.post` / `api.patch` /
`api.del` in `frontend/src/api/client.ts`. The client reads the `ui_csrf` cookie
(`client.ts:178`) and attaches `X-CSRF-Token` automatically on every non-GET request.
No manual CSRF handling is needed in the page components.

### 7.3 Authorization

All endpoints require `require_ui_session` (JOB-003). The frontend does not pass raw
user IDs or roles in request bodies. The backend enforces ownership: `list_mine` returns
orders where the calling `user_sub` is in `recruiter_subs`; there is no client-side
filtering. If the session expires mid-flow, the `api` client's 401 handler
(`client.ts:205-248`) refreshes the session once, then redirects to `/login` on failure.

### 7.4 Input sanitization

Zod schemas in `JobOrderForm` enforce maximum lengths (title 255, description 20 000,
etc.) matching the backend Pydantic models (JOB-001). No HTML is rendered from user-
supplied description text — the description is rendered inside a `<pre className="whitespace-pre-wrap">` block, never via `dangerouslySetInnerHTML`.

### 7.5 No sensitive data in URLs

`job_id` values are opaque UUIDs (`job_` + hex). No PII (pay rates, descriptions)
appears in route params or query strings.

### 7.6 Feature flag off — zero data leakage

When `isAtsEnabled()` is `false`, the sidebar entry is absent and the routes still
register but the feature-flag query returns `job_orders_enabled: false`, causing each
page to render a placeholder. The backend independently returns 503 for all data calls
even if a user navigates directly to `/ats/job-orders`.

## 10. Open Questions / Assumptions

1. **Company/contact pickers.** Until PTY-008 (B2B org account) and CCT-003 (contacts
   with reports-to) ship, `client_company_id` and `client_contact_id` are free-text
   inputs. A follow-up ticket (likely an OPP-style "linkage picker" component) will
   replace the text inputs with typeahead selectors once those entities exist.
   **Assumption:** free-text accepted for now; the server stores opaque strings.

2. **Recruiter sub multi-select.** `recruiter_subs` is a list of user `sub` values. The
   current chip input accepts arbitrary strings. User search is implemented in
   `app/services/discovery.py::search_users` and exposed via the aggregated
   `GET /ui/search` endpoint (`app/routers/search.py`); there is no dedicated
   standalone `GET /ui/search/users?q=` endpoint. A dedicated user-search typeahead
   component is not currently surfaced. **Assumption:** plain chip input for P1;
   user-search typeahead backed by the discovery search path is a P2 follow-up.

3. **`JOB_ORDER_ALLOW_REOPEN`.** The backend env var (`JOB_ORDER_ALLOW_REOPEN`, default
   `true`) controls whether `closed → active` is legal. The frontend always shows
   "Active" as an option from `closed` and lets the server 409 if it is disabled.
   The frontend does not need to know the env var value. **Assumption:** attempt and
   surface server rejection; no client-side env-var reading.

4. **Public career portal linkage.** The `public` flag on a job order will eventually
   drive a career portal listing (PORTAL-* tickets). JOB-007 exposes the toggle in the
   form and the badge on the detail page but does not link to any portal URL yet.
   **Assumption:** badge + toggle only; portal link is PORTAL-*'s concern.

5. **i18n coverage.** New `i18nKey` values are added to the nav (`nav.recruiting`,
   `nav.jobOrders`) and the page headings. Whether to add translation strings in this
   ticket or defer to a dedicated i18n sweep is left open. **Assumption:** English
   label strings are sufficient for P1; translation keys are wired but translation
   values are deferred.

6. **Openings counter refresh.** The detail page fetches `getOpeningsSummary` once.
   When PIPE-* ships and pipeline moves update `placed_count`, the counter will be
   stale until page refresh. A future follow-up (or an SSE event) can trigger
   `queryClient.invalidateQueries(["ats","job-orders",jobId,"openings"])`.
   **Assumption:** no live update in this ticket; page-refresh is sufficient for P1.
