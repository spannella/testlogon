# EML-003 — Per-user email account connections (IMAP/SMTP credential storage)

---

## 1. Summary & Goal

EML-003 introduces a **credential vault for personal IMAP and SMTP account registrations**. Each authenticated user can register one or more external email accounts (Gmail, Outlook, corporate Exchange, etc.) and have their passwords stored encrypted at rest. A lightweight connection-verification endpoint checks that the supplied IMAP credentials are reachable before the inbox sync (EML-004) is wired.

This ticket delivers the storage and management layer only. Actual inbox sync, compose/send, threading, archiving, signatures, and the UI are covered by EML-004 through EML-007. The feature is gated behind `EMAIL_CLIENT_ENABLED` (default off) so the existing platform — `send_alert_email`, `T.email_delivery`, `app/routers/admin_email.py` — is byte-for-byte unchanged when the flag is off.

**Scope of this ticket:**
- New DynamoDB table `user_email_accounts`
- New service `app/services/user_email_accounts.py`
- New router `app/routers/user_email_accounts.py` (prefix `/ui/email/accounts`)
- New Pydantic models in `app/models.py`
- Settings key + env var in `app/core/settings.py`
- Table definition in `scripts/local-ddb-init.py` and handle in `app/core/tables.py`
- Registration in `app/main.py`
- Hermetic offline pytest in `tests/test_eml_003_user_email_accounts.py`

## 3. Data Model

### New DynamoDB table: `user_email_accounts`

Single-table design; all account rows for a user share the same partition. A second row-type (`SK=SIGNATURE`) is reserved for EML-006 and must not be created by this ticket.

| Attribute | Type | Notes |
|-----------|------|-------|
| `pk` | S | `USER#{user_sub}` |
| `sk` | S | `ACCT#{account_id}` (UUID4 hex, 32 chars) |
| `account_id` | S | Same as the suffix of `sk`; redundant for convenience |
| `label` | S | Display name, max 100 chars |
| `imap_host` | S | e.g. `imap.gmail.com` |
| `imap_port` | N | Default 993 |
| `imap_use_ssl` | BOOL | Default `true` |
| `smtp_host` | S | e.g. `smtp.gmail.com` |
| `smtp_port` | N | Default 587 |
| `smtp_use_tls` | BOOL | Default `true` |
| `username` | S | Email address used to authenticate |
| `password_ct_b64` | S | KMS-encrypted base-64 ciphertext (never returned to API callers) |
| `is_default` | BOOL | At most one account per user may be `is_default=true` |
| `created_at` | N | `now_ts()` integer Unix seconds |
| `updated_at` | N | `now_ts()` on creation and each update |
| `status` | S | `"unverified"` \| `"active"` \| `"error"` |
| `last_error` | S | Optional; last IMAP connection error message (max 500 chars) |

**Primary key:** `pk` (HASH) + `sk` (RANGE).

**GSI `ByUser`:**
- Partition key: `pk` (S, same as table HASH key)
- Sort key: `created_at` (N)
- Projection: ALL
- `attr_types={"created_at": "N"}` required in `scripts/local-ddb-init.py`

Using the table's own `pk` as the GSI partition key is legal and standard in single-table DDB design. The GSI exists to list all accounts for a user ordered by `created_at` without specifying a specific `sk` prefix.

## 4. API / Service Design

### 4.1 Service: `app/services/user_email_accounts.py`

```python
from __future__ import annotations

import logging
import uuid
from typing import Any

from boto3.dynamodb.conditions import Key

from app.core.crypto import kms_decrypt, kms_encrypt
from app.core.cursor import decode_cursor, encode_cursor
from app.core.tables import T
from app.core.time import now_ts
from app.services.alerts import audit_event

logger = logging.getLogger(__name__)

_MAX_ACCOUNTS_PER_USER = 20
_PASSWORD_FIELD = "password_ct_b64"
_SAFE_FIELDS = {            # fields returned to API callers
    "account_id", "label",
    "imap_host", "imap_port", "imap_use_ssl",
    "smtp_host", "smtp_port", "smtp_use_tls",
    "username", "is_default", "created_at", "updated_at", "status", "last_error",
}

def _strip_password(item: dict) -> dict:
    return {k: v for k, v in item.items() if k in _SAFE_FIELDS}

def create_account(user_sub: str, payload: dict) -> dict:
    ...

def list_accounts(user_sub: str, *, cursor: str | None = None, limit: int = 50) -> tuple[list[dict], str | None]:
    ...

def get_account(user_sub: str, account_id: str) -> dict | None:
    ...

def update_account(user_sub: str, account_id: str, payload: dict) -> dict:
    ...

def delete_account(user_sub: str, account_id: str) -> None:
    ...

def verify_connection(user_sub: str, account_id: str) -> dict:
    ...
```

**`create_account(user_sub, payload) -> dict`**

1. Validate `label` ≤ 100 chars; validate `imap_host` and `smtp_host` are non-empty strings (no IP/port injection: strip leading whitespace, reject values containing `\n` or `\r`).
2. Validate `username` is a syntactically valid email via `app.core.normalize.normalize_email` (raises `ValueError` on failure; caller maps to HTTP 400).
3. Validate `imap_port` ∈ [1, 65535] and `smtp_port` ∈ [1, 65535].
4. Enforce per-user cap: query `ByUser` GSI with `Select=COUNT`; if count ≥ `_MAX_ACCOUNTS_PER_USER`, raise a `LimitExceeded` exception (HTTP 400).
5. Encrypt: `password_ct_b64 = kms_encrypt(payload["password"])`. If `S.kms_key_id` is empty (should not occur in any real environment) raise HTTP 500 "credential encryption is not configured" — same error text as `provider_credentials.py:404`.
6. If `payload.get("is_default")` is `True`, clear any existing `is_default=true` row for this user (update loop over existing accounts — see §5).
7. `T.user_email_accounts.put_item(Item={...})` with `pk`, `sk`, all fields, `status="unverified"`, `created_at=now_ts()`, `updated_at=now_ts()`.
8. Call `audit_event("email_account_created", user_sub, account_id=account_id, label=payload["label"])`.
9. Return `_strip_password(item)`.

**`list_accounts(user_sub, *, cursor, limit) -> (list[dict], cursor | None)`**

Query `ByUser` GSI: `Key("pk").eq(f"USER#{user_sub}")`, `ScanIndexForward=True` (oldest first), `Limit=limit`. Handles `ExclusiveStartKey` via `decode_cursor`/`encode_cursor` from `app/core/cursor.py`. Strips `password_ct_b64` from each item before returning.

**`get_account(user_sub, account_id) -> dict | None`**

`T.user_email_accounts.get_item(Key={"pk": f"USER#{user_sub}", "sk": f"ACCT#{account_id}"})`. Returns `None` if absent. Does NOT strip password (internal use); callers that expose to API must call `_strip_password`.

**`update_account(user_sub, account_id, payload) -> dict`**

1. Load existing item; raise `AccountNotFound` (HTTP 404) if absent.
2. Build `UpdateExpression` dynamically for allowed mutable fields: `label`, `imap_host`, `imap_port`, `imap_use_ssl`, `smtp_host`, `smtp_port`, `smtp_use_tls`, `username`.
3. If `payload` includes `password`, re-encrypt and include `password_ct_b64` in the update.
4. If `payload.get("is_default")` is `True`, first clear any other default (see §5).
5. Always set `updated_at = now_ts()`. Set `status="unverified"` when any of `imap_host`, `smtp_host`, `username`, or `password` changes (credentials may no longer be valid).
6. Emit `audit_event("email_account_updated", user_sub, account_id=account_id)`.
7. Return `_strip_password(updated_item)`.

**`delete_account(user_sub, account_id) -> None`**

1. Load; raise `AccountNotFound` (HTTP 404) if absent.
2. `T.user_email_accounts.delete_item(Key={...})`.
3. Emit `audit_event("email_account_deleted", user_sub, account_id=account_id)`.

**`verify_connection(user_sub, account_id) -> dict`**

1. Load item (raises `AccountNotFound` if absent).
2. Decrypt password: `password = kms_decrypt(item["password_ct_b64"]).decode("utf-8")`.
3. Attempt connection:
   - **Dev mode** (see §6): call `_mock_verify_connection(item)` — always returns `{"ok": True, "detail": "mock"}`.
   - **Prod mode**: call `_live_verify_connection(item, password)` — uses `imaplib.IMAP4_SSL` (or `imaplib.IMAP4` when `imap_use_ssl=False`) to connect to `imap_host:imap_port`, call `.login(username, password)`, then `.logout()`.
4. On success: `update_item` to set `status="active"`, clear `last_error`, `updated_at=now_ts()`. Return `{"ok": True, "status": "active"}`.
5. On failure (IMAP error or socket error): `update_item` to set `status="error"`, `last_error=str(exc)[:500]`, `updated_at=now_ts()`. Return `{"ok": False, "status": "error", "detail": str(exc)[:500]}`. Do NOT re-raise; the HTTP response is 200 with `ok=False`. This matches the non-raising pattern of `email_delivery.record_email_failure`.

Note on SECOPS-007: the IMAP branch is not wrapped in `if S.dev_mode`; instead it is dispatched through a `_get_imap_client(host, port, use_ssl)` factory function that in the real codebase returns `imaplib.IMAP4_SSL(host, port)` but is patchable at import time in tests (see §9).

## 5. Detailed Behavior & Edge Cases

### 5.1 `is_default` uniqueness invariant

At most one account per user may have `is_default=True`. When creating or updating an account with `is_default=True`:

1. Query `ByUser` GSI for all accounts with `is_default=True` (DDB `FilterExpression=Attr("is_default").eq(True)` applied client-side after the query, since DDB's `FilterExpression` on a GSI does not reduce page counts but is safe here given the 20-account cap).
2. For each existing default account (should be at most one, but handle multiple defensively), call `update_item` to set `is_default=False`, `updated_at=now_ts()`.
3. Then proceed with the write that sets the new account's `is_default=True`.

These two writes are NOT in a DDB transaction (cost vs. correctness trade-off acceptable given the 20-account hard cap; a race window is negligible in practice). If consistency is later required, a conditional expression `ConditionExpression=Attr("is_default").eq(True)` can be added.

### 5.2 Connection verification branching (dev vs. prod, SECOPS-007)

`verify_connection` calls a module-level factory:

```python
def _get_imap_client(host: str, port: int, use_ssl: bool):
    import imaplib
    if use_ssl:
        return imaplib.IMAP4_SSL(host, port)
    return imaplib.IMAP4(host, port)
```

In tests, `_get_imap_client` is patched at the module boundary (see §9). There is **no `if S.dev_mode:` branch** anywhere in the service; the same code path runs in both environments. The mock IMAP path is supplied purely by test patching; in the real dev environment the function will attempt a real IMAP connection (which will fail gracefully and update `status="error"`). This satisfies SECOPS-007.

### 5.3 KMS key availability

If `S.kms_key_id` is empty, `kms_encrypt` raises `RuntimeError("KMS_KEY_ID not set")` (`app/core/crypto.py:17-18`). The service catches this and raises `HTTPException(500, "credential encryption is not configured")` — same text as `provider_credentials.py:404`. This makes the error actionable in operator logs.

### 5.4 Ownership enforcement

`get_account(user_sub, account_id)` uses the full primary key `pk=USER#{user_sub}` + `sk=ACCT#{account_id}`. A different user's account is structurally unreachable because the `pk` segment is bound to the authenticated user's `sub`. There is no additional ownership check needed — the DDB key is the ownership boundary.

### 5.5 Password never in API responses

`_strip_password(item)` returns only keys in `_SAFE_FIELDS`. The `password_ct_b64` key is absent from `_SAFE_FIELDS`. Every API handler calls `_strip_password` before returning; the router response model (`EmailAccountOut`) does not include a `password` field, so even if the service accidentally leaked it, Pydantic would drop it on serialization.

### 5.6 Label and host injection

`label` is limited to 100 chars (Pydantic `max_length`). `imap_host` and `smtp_host` are stripped of leading/trailing whitespace and rejected if they contain `\n`, `\r`, or null bytes (service-layer check before encryption). This prevents log injection and IMAP command injection.

### 5.7 Port out of range

`imap_port` and `smtp_port` are validated `ge=1, le=65535` at the Pydantic level. Invalid ports return 422 (Pydantic validation error) before any service code runs.

### 5.8 Large list pagination

`list_accounts` queries the `ByUser` GSI with `Limit=limit` (default 50, max 100). The 20-account hard cap means a single page always covers all accounts in practice, but pagination is implemented correctly for forward-compatibility. The cursor is the DDB `LastEvaluatedKey` encoded by `encode_cursor` from `app/core/cursor.py:94`.

### 5.9 503 when flag is off

`_require_enabled()` is called at the top of every route handler. With `EMAIL_CLIENT_ENABLED=0` (the default), every route returns `HTTP 503 {"detail": "email client is not enabled"}`. The router is still registered in `main.py` so OpenAPI reflects the endpoints, but they are non-functional. This matches the `browser_ssh_terminal_enabled` pattern at `app/core/settings.py:124`.

### 5.10 Audit trail

All five mutating operations emit `audit_event(event_name, user_sub, ...)` from `app/services/alerts.py:644`. The `audit_event` function writes to `T.alerts` and is best-effort (exceptions are swallowed). The event names are:

| Operation | Event name |
|-----------|-----------|
| create | `email_account_created` |
| update | `email_account_updated` |
| delete | `email_account_deleted` |
| verify (success) | `email_account_verified` |
| verify (failure) | `email_account_verify_failed` |

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 compliance

There is no `if S.dev_mode:` branch in `app/services/user_email_accounts.py`. KMS encryption, DDB writes, and the IMAP client factory are identical code paths in both environments. In dev, `scripts/mock_kms_server.py` (port 7999) handles KMS calls — the same `kms_encrypt`/`kms_decrypt` functions work against it without modification. The IMAP factory (`_get_imap_client`) will attempt a real TCP connection in dev; because no mock IMAP server is running, `verify_connection` will return `{"ok": False, "status": "error"}` for any real host in dev — expected behavior, and documented in the E2E test setup.

For E2E tests that need `verify_connection` to succeed in dev, the `POST /{account_id}/verify` endpoint documentation notes that testers must either run a local IMAP server or accept the `"error"` outcome. The unit test patches `_get_imap_client` at module level (see §9).

### Credential encryption

`password_ct_b64` is written by `kms_encrypt` and is the only representation of the password in DDB. The plaintext password exists only:

1. In the HTTP request body (TLS-protected in transit)
2. Transiently in the `create_account`/`update_account` service function stack frame
3. As the `kms_encrypt(...)` call argument

The plaintext is never logged. The `audit_event` call in `create_account` does not include the password argument.

### Idempotency

`create_account` generates a fresh `account_id = uuid.uuid4().hex` on each call; it is not idempotent by design (two calls with the same label create two records). `update_account` and `delete_account` are idempotent in the standard REST sense: applying the same update twice converges to the same state; delete is idempotent (second delete returns 404, not an error in a destructive sense).

`verify_connection` is idempotent: calling it N times produces N `status` updates; the final state is always the result of the last attempt.

### CSRF

All non-GET endpoints require the `x-csrf-token` header (enforced by `get_authenticated_user` for cookie-auth sessions). Bearer-auth callers (API key clients) skip CSRF per the existing platform pattern in `app/auth/deps.py`.

### Password in request body

Pydantic's `EmailAccountCreateIn.password` field is `min_length=1`. FastAPI will log the raw request body at `DEBUG` level only if `access_log=True`; production deployments should ensure debug logging is off. As an additional guard, the service strips the password before calling `audit_event`.

## 8. Backward Compatibility & Migration

### No migration required

This is a net-new table. No existing rows exist. No existing code paths are modified. The `Tables` dataclass gains one new field (`user_email_accounts`) at the end; `dataclass(frozen=True)` is additive.

### Deployment order

1. Deploy `scripts/local-ddb-init.py` changes (runs `create_table` for `user_email_accounts`). In production, this is the DDB table creation step before the binary is deployed.
2. Deploy the new binary. The new table must exist before the binary starts, because `T = Tables(...)` at module import time calls `_safe_table(S.user_email_accounts_table_name)` which calls `ddb.Table(name)` — DDB's `Table()` is lazy (no API call at construction), so the table not existing before the binary starts is technically fine. It is still best practice to create the table first.
3. `EMAIL_CLIENT_ENABLED=0` in prod until EML-004 and EML-005 are also deployed and tested.

### Rollback

Setting `EMAIL_CLIENT_ENABLED=0` makes all routes return 503. The table can be left in place (it is empty). No rollback migration needed.

### Existing `send_alert_email` callers

Zero changes to `send_alert_email` (`alerts.py:459`), `record_email_sent` (`email_delivery.py:33`), or any of the 50+ existing routers. The new router is additive.

## 10. Open Questions / Assumptions

1. **IMAP app passwords vs. OAuth tokens.** Gmail and Outlook now require OAuth 2.0 tokens (not plain IMAP passwords) for new integrations. This ticket stores a password/app-password; proper OAuth-based IMAP authentication (using access tokens from provider_oauth.py) is deferred. Assumption: users will configure app-specific passwords for now; OAuth IMAP is a follow-on to EML-003.

2. **SMTP send path.** The `smtp_*` fields are stored but no send endpoint exists in EML-003. The send functionality is part of EML-004. The SMTP fields are stored here to keep account configuration atomic. The `verify_connection` endpoint only verifies IMAP; SMTP verification is deferred to EML-004.

3. **`_MAX_ACCOUNTS_PER_USER = 20`.** This is a conservative cap. If the limit needs to be raised, it can be made a settings key (`EMAIL_CLIENT_MAX_ACCOUNTS_PER_USER`, default 20).

4. **KMS key selection.** The service uses `S.kms_key_id` (the global platform KMS key, `app/core/settings.py:188`). A dedicated email-credential KMS key (`EMAIL_CREDENTIALS_KMS_KEY_ID`) could be added for key isolation. This is left as a follow-on security hardening item.

5. **Soft delete vs. hard delete.** The spec uses hard delete (`delete_item`). If future EML tickets (e.g., EML-007 archiving) need to reference deleted accounts, a `deleted_at` soft-delete field may be needed. Assumption: hard delete is sufficient for EML-003; EML-007 can re-evaluate.

6. **Rate limiting.** `verify_connection` makes an outbound TCP/TLS connection per call. A per-user rate limit (e.g., 10 verify calls/hour via `T.rate_limits`) is recommended before EML-003 is enabled in production but is out of scope for this ticket.
