# CAS-017 — Ticket analytics — resolution time, volume, agent throughput

**Type:** Feature | **Priority:** P2 | **Estimate:** 2d
**Depends on:** CAS-001 (flag, settings, table scaffolding), CAS-003 (priority field on META rows)
**Consumed by:** Future CAS SLA reporting dashboards

---

## 1. Summary & Goal

Add a dedicated ticket analytics API endpoint that goes well beyond the existing `GET /tickets/admin/summary` (which only returns status-bucket counts, stale count, and unassigned count). The new endpoint computes and returns:

- **Resolution-time distribution**: p50, p90, and mean seconds from ticket creation to `done` status transition, over a configurable time window.
- **Volume by day**: a date-keyed histogram of tickets created within the window (YYYY-MM-DD → count).
- **Per-agent throughput**: for each `assigned_to_sub` that resolved at least one ticket in the window, the total resolved count and average resolution seconds.
- **Open tickets by priority**: a snapshot count of currently open tickets per priority tier (urgent / high / medium / low / unset), useful for capacity planning.

The feature is entirely additive. With `CRM_CASES_ENABLED=0` (the default) the platform is byte-for-byte unchanged: the new route returns 404, the new service method is never called, and all existing tests pass without modification.

## 2. Context & Current State

### Existing tickets infrastructure

`app/services/tickets.py` defines `TicketStore` backed by `T.tickets` (`app/core/tables.py:392`). The existing `get_admin_summary` method (line 694) uses `_query_all_headers_by_index` (line 677) to page through all items on the status GSI (`gsi2pk`=`STATUS#{status}`) and count them. It does **not** compute any time-based metric and has no concept of a query window.

The META row for each ticket (`pk=TICKET#{ticket_id}`, `sk=META`) carries `created_at` (integer Unix seconds, line 458), `assigned_to_sub` (line 455), `status` (line 452), and — once CAS-003 ships — a `priority` attribute. It does **not** store a `resolved_at` timestamp; resolution time must be derived from the activity log.

Each status transition writes an activity row with `sk=ACT#{ts:013d}#{activity_id}`, `activity_type="ticket_status_changed"`, and `status=<new_status>` (line 971). Finding the timestamp at which a ticket entered `done` means querying the activity rows for that ticket (prefix `ACT#`) and selecting the last item with `status="done"`. The sort-key format `ACT#{ts:013d}#{id}` ensures activity rows for a single ticket are returned in chronological order by `ScanIndexForward=True` (explicitly set in `_query_partition_prefix` at `app/services/tickets.py:514`; the `True` value is at line 518).

The existing `GET /tickets/admin/summary` endpoint is registered at:
```
app/routers/tickets.py:887   @router.get("/admin/summary", ...)
```
It is declared **before** the dynamic `/{ticket_id}` route at line 900, following the rule that literal path segments must be declared before parameterized ones (CLAUDE.md gotcha; CAS-017 must follow the same ordering convention).

### Status GSI

The status GSI (`S.tickets_status_index_name`, default `"status-updated_at-index"`) has:
- PK: `gsi2pk` = `STATUS#{status}` (e.g., `STATUS#done`)
- SK: `gsi2sk` = `UPDATED#{updated_at:013d}#TICKET#{ticket_id}` (lexicographic string, **not** a plain integer — `attr_types` not required for this SK)

The GSI is defined in `scripts/local-ddb-init.py:701` (line 700 is the owner GSI entry; the status GSI is the second entry at line 701). Querying `STATUS#done` with `ScanIndexForward=False` gives the most-recently-updated closed tickets. `_query_all_headers_by_index` (line 677) already provides a fully-paginated sweep of any GSI partition, looping via `LastEvaluatedKey` until exhausted — this is the correct primitive to reuse (DDB FilterExpression is not applied until after page reads, so it cannot substitute for paginated sweeps).

### Priority GSI (CAS-003 dependency)

CAS-003 (spec at `docs/suitecrm/specs/CAS-003.md`) adds `gsi_priority_pk` = `PRIORITY#{priority}` on META rows when `S.crm_cases_enabled` is on. The `open_by_priority` metric can query each priority partition on this GSI when the flag is on and CAS-003 has shipped. When the GSI does not yet exist (CAS-003 not shipped), the analytic falls back to scanning the `STATUS#open` partition and reading the `priority` attribute from each header row in Python.

### Auth pattern

Admin-only enforcement in `app/routers/tickets.py` is done inline using the `_is_admin_actor(request, user)` helper (`app/routers/tickets.py:224-225`), which checks `Role.ADMIN | Role.ROOT` (via the internal `_is_admin` helper at line 207-208) or `tickets:admin` API-key scope. There is no `require_admin_session` dependency in this router — the same pattern must be used for the new endpoint.

### Existing `TicketAdminSummary` model

`app/routers/tickets.py:113-122` defines `TicketAdminSummary` and `TicketAdminSummaryEnvelope`. CAS-017 introduces a parallel `TicketAnalyticsOut` / `TicketAnalyticsEnvelope` pair — a new model, not an extension of the summary model, to keep the response shapes orthogonal.

### Frontend recharts

The frontend already depends on `recharts@^3.8.1` (`frontend/package.json:67`). `EarningsPage.tsx` and `AnalyticsPage.tsx` show the established pattern: `AreaChart`/`BarChart` from `recharts` alongside shadcn/ui `Card` primitives. The new `TicketAnalyticsDashboard.tsx` component reuses this pattern without adding a new dependency.

## 3. Data Model

### No new DynamoDB table required

All data lives in the existing `tickets` table (PK=`pk`, SK=`sk`) and the existing `crm_cases_priority_index` GSI introduced by CAS-003. No new tables or attributes beyond those introduced by CAS-001 and CAS-003 need to be created for CAS-017.

### New attribute on ticket META row (no schema change)

No new persistent attribute is needed. Resolution time is computed at query time from existing activity rows. The `priority` attribute on META rows is owned by CAS-003; CAS-017 only reads it.

### `crm_cases_analytics_cache` table (optional pre-computation table — NOT required for MVP)

For the MVP the analytics are computed on-demand from the existing tickets table. If query latency proves unacceptable at scale, a separate cache table can be introduced in a follow-up. The MVP spec does not include this table.

### Summary of DynamoDB access patterns

| Operation | Table/GSI | Access pattern |
|---|---|---|
| Fetch all `done` tickets in window | `tickets` / `status-updated_at-index` (gsi2pk=`STATUS#done`) | Full GSI-partition sweep via `_query_all_headers_by_index`; Python-side filter on `created_at >= window_start` |
| Fetch activity rows per closed ticket | `tickets` base table | `_query_partition_prefix(ticket_id=..., sk_prefix="ACT#")` (existing method, line 514) |
| Fetch open-by-priority snapshot | `tickets` / `crm_cases_priority_index` (one query per priority value) OR `STATUS#open` sweep with Python grouping | Depends on CAS-003 availability |

**Note on `attr_types`**: the existing `gsi2sk` sort key uses a lexicographic `UPDATED#...` string — `attr_types` is not required. The `crm_cases_priority_index` GSI sort key format (defined by CAS-003) also uses the same string pattern. No new numeric GSI sort keys are introduced by CAS-017; therefore no new `attr_types` entries are needed in `scripts/local-ddb-init.py`.

## 4. API / Service Design

### Service layer — `app/services/tickets.py`

Add `TicketStore.get_analytics` as a new method on the existing `TicketStore` class (after `get_admin_summary`, before `_conditional_update_meta`):

```python
def get_analytics(self, *, period_days: int = 30) -> dict[str, Any]:
    """
    Compute ticket analytics for the trailing `period_days` window.

    Returns:
        resolution_time_p50_seconds: int | None
        resolution_time_p90_seconds: int | None
        resolution_time_avg_seconds: float | None
        volume_by_day: dict[str, int]          # YYYY-MM-DD -> count of tickets created
        by_assignee: list[{
            assignee_sub: str,
            resolved_count: int,
            avg_resolution_seconds: float,
        }]
        open_by_priority: dict[str, int]       # priority -> count
    """
```

**Algorithm (all computation in Python after fetching from DDB; no scan):**

1. Compute `window_start = now_ts() - period_days * 86400`.
2. Call `_query_all_headers_by_index(index_name=S.tickets_status_index_name, pk=_status_index_pk("done"), key_expr="gsi2pk = :pk")` to get all META rows with `status=done`. This returns only header rows (no activity rows yet).
3. Filter the list in Python: keep only rows where `int(item.get("created_at", 0)) >= window_start`. This is safe because DDB `FilterExpression` cannot substitute for a `begins_with`-range query on a string SK — the Python-side filter is explicit.
4. For each surviving header, call `_query_partition_prefix(ticket_id=..., sk_prefix="ACT#")` to get activity rows (sorted ascending by `created_at` via `ScanIndexForward=True`). Walk the activity list in reverse and take the `created_at` of the **last** row with `activity_type="ticket_status_changed"` and `status="done"`. This is `resolved_at`. Resolution seconds = `resolved_at - header["created_at"]`. If no such activity row exists (e.g., ticket was seeded directly without a status-change event), skip the ticket from percentile calculations but still count it in `volume_by_day`.
5. Compute `volume_by_day`: for each header in step 3, bucket `created_at` into `datetime.utcfromtimestamp(created_at).strftime("%Y-%m-%d")` and increment the counter.
6. Compute resolution-time metrics: collect `resolution_seconds` values into a sorted list. Percentile `p_k` = `sorted_list[int(len * k / 100)]` with `max(0, ...)` guard. Return `None` for all three values when the list is empty (0 resolved tickets in the window).
7. Compute `by_assignee`: group headers by `assigned_to_sub` (skip rows with `None` assignee). For each group, count members and average their `resolution_seconds`. Rows with no `resolved_at` (activity not found) are excluded from the average but included in the count only if they have a valid `assigned_to_sub`. Return list sorted descending by `resolved_count`.
8. Compute `open_by_priority`:
   - If `S.crm_cases_enabled` and CAS-003 index is available: for each priority value in `("urgent", "high", "medium", "low")`, query `crm_cases_priority_index` with `gsi_priority_pk = PRIORITY#{priority}` filtered to `gsi2pk = STATUS#open` in Python. Also add an `"unset"` bucket for open tickets lacking the `priority` attribute.
   - Fallback (CAS-003 index not yet available or `S.crm_cases_enabled` is off but `open_by_priority` is still requested): sweep `STATUS#open` partition via `_query_all_headers_by_index` and group by `header.get("priority", "unset")` in Python.
   - Since CAS-017 already depends on `CRM_CASES_ENABLED`, in practice the full CAS-003 priority GSI will always be available when this endpoint is callable.

## 5. Detailed Behavior & Edge Cases

### Zero closed tickets in the window

When `_query_all_headers_by_index` on `STATUS#done` returns no rows (or all rows have `created_at < window_start`), `get_analytics` must return:
```python
{
    "resolution_time_p50_seconds": None,
    "resolution_time_p90_seconds": None,
    "resolution_time_avg_seconds": None,
    "volume_by_day": {},
    "by_assignee": [],
    "open_by_priority": { ... },  # still computed from open tickets
}
```
The endpoint must never return 500 in this case. The `TicketAnalyticsOut` model has all resolution-time fields optional (`| None`), so serialization is clean.

### Tickets reopened after `done`

A ticket may transition `done → open → done` multiple times. The algorithm picks the **last** activity row with `activity_type="ticket_status_changed"` and `status="done"`, which gives the most recent resolution time. This is consistent with SuiteCRM's "final resolution time" semantics. Earlier `done` events are silently ignored.

### Activity rows missing `status` field

Legacy tickets created before the `activity_type="ticket_status_changed"` pattern was established (line 971) may have activity rows without a `status` attribute. These are safely skipped by the `status="done"` filter.

### Very large `done` partition

The `STATUS#done` partition can grow unbounded. `_query_all_headers_by_index` already paginates via `LastEvaluatedKey` (line 677-692) up to exhaustion. This is correct behavior but imposes O(n) DDB reads where n = total historical closed tickets. For `period_days=7` on a high-volume installation this may be slow. The Python-side `created_at` filter cannot be pushed down to DDB because the GSI SK encodes `updated_at`, not `created_at`. This is acceptable for the MVP; a dedicated time-partitioned analytics index is a follow-up.

### `assigned_to_sub` vs `assigned_admin_sub`

The META row stores both `assigned_to_sub` and `assigned_admin_sub` (set to the same value by `assign_ticket` at line 815-816). The `by_assignee` metric groups on `assigned_to_sub` to be consistent with the field introduced in CAS-003 and used throughout the ticket list queries. Tickets that were never assigned have `assigned_to_sub=None` and are excluded from the `by_assignee` list but still contribute to `volume_by_day` and resolution-time percentiles.

### `open_by_priority` when CAS-003 is not yet shipped

The `priority` attribute is written on META rows only when `S.crm_cases_enabled=True` and CAS-003 has been deployed. Since CAS-017 is gated on the same flag and depends on CAS-003, in production this situation should not arise. However, in test environments with partial deploys, old META rows may lack `priority`. The Python-side grouping handles this via `header.get("priority", "unset")`, bucketing all legacy rows into `"unset"`.

### `period_days` maximum

`period_days > 90` returns HTTP 422 (FastAPI/Pydantic `le=90` constraint). The ticket source document specifies this constraint explicitly at line 580.

### Concurrent updates during sweep

`_query_all_headers_by_index` reads up to a full DDB partition over potentially many `LastEvaluatedKey` pages. Tickets created or updated during the sweep may be missed or double-counted. This is an accepted eventual-consistency trade-off for an analytics endpoint; no transactional guarantee is required.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007

`get_analytics` performs only DynamoDB reads using the same `T.tickets` table handle used everywhere else in `TicketStore`. There is no `dev_mode` branch. The computation is purely in Python (sorting, percentile math). No S3, KMS, SES, or Cognito calls are made. The code path is identical in dev (DynamoDB Local at port 8001) and production (real DynamoDB).

### Idempotency

`GET /tickets/admin/analytics` is a pure read endpoint. It is trivially idempotent and safe to retry.

### Security

- The endpoint enforces `_is_admin_actor(request, user)` before any DDB access. Non-admin callers receive 403 before data is fetched.
- The `audit_event("ticket_analytics_viewed", ...)` call writes an audit trail entry via `app/services/alerts.audit_event` (`app/services/alerts.py:644`) to `T.alerts` (via `write_alert` → `T.alerts.put_item`, gated on `S.alerts_enabled`), recording the caller's `user_sub`, `outcome`, and `period_days`. This is consistent with all other admin-only analytics endpoints in the codebase.
- No user PII beyond `user_sub` identifiers is returned. `assignee_sub` values in `by_assignee` are the same sub values already exposed by `TicketOut.assigned_to_sub`.
- The endpoint does not cache results and does not accept any write parameters, so there is no injection surface.

## 8. Backward Compatibility & Migration

### No migration required

CAS-017 introduces no new DynamoDB tables, no new attributes on existing rows, and no schema changes to `scripts/local-ddb-init.py`. All attributes it reads (`created_at`, `assigned_to_sub`, `priority`, `activity_type`, `status`) are already present on existing rows (or gracefully absent, in which case defaults apply).

### Additive model changes

`TicketAnalyticsOut`, `TicketAnalyticsEnvelope`, and `AgentThroughputEntry` are new Pydantic models. They do not alter `TicketOut`, `TicketListItemOut`, or `TicketAdminSummary`. Existing API consumers are unaffected.

### Route ordering

The new `@router.get("/admin/analytics", ...)` must be placed in `app/routers/tickets.py` **before** `@router.get("/admin/summary", ...)` at line 887, which is already before `@router.get("/{ticket_id}", ...)` at line 900. Insertion order: `/admin/analytics` → `/admin/summary` → `/{ticket_id}`. FastAPI matches routes in declaration order; placing `/admin/analytics` after `/{ticket_id}` would cause the literal string `analytics` to be captured as `ticket_id`.

### `just restart` compatibility

No new tables means `just restart` requires no schema changes for CAS-017 alone. When CAS-001 has been deployed (the prerequisite), the existing `tickets` table and its GSIs are already present.

## 10. Open Questions / Assumptions

1. **Performance of `STATUS#done` full sweep**: On a production installation with millions of closed tickets, a full-partition sweep of `STATUS#done` to find tickets in a 30-day window could be slow and expensive. The MVP spec accepts this trade-off. A follow-up should add a `created_at`-partitioned GSI (e.g., `DONE#{YYYY-MM-DD}`) so queries can be bounded by date without scanning the entire partition.

2. **`resolved_at` attribute**: Rather than scanning activity rows per ticket, a more efficient approach would be to write `resolved_at` directly onto the META row when status transitions to `done`. This is a CAS-017 follow-up or could be included in CAS-003/CAS-008 SLA work. The MVP derives `resolved_at` from activity rows to avoid modifying `_conditional_update_meta`.

3. **CAS-003 GSI availability**: The `open_by_priority` metric assumes CAS-003 has shipped. If CAS-017 is deployed before CAS-003, the fallback sweep path handles it correctly, but with higher DDB read cost. The fallback is present in the design.

4. **`volume_by_day` timezone**: Currently uses `datetime.utcfromtimestamp`. If the platform gains timezone-aware user settings, this should be configurable. For now UTC is the canonical timezone for all analytics.

5. **Frontend feature flag check**: The `TicketAnalyticsDashboard` should gracefully handle a 404 from the API (feature disabled) by showing a "Contact your administrator" message rather than an error toast. This requires a `isAxiosError` check in the `useQuery` error handler.

6. **Audit event volume**: Every admin page load fires `audit_event("ticket_analytics_viewed", ...)`. For dashboards that auto-refresh, this could create high audit log volume. A future improvement could rate-limit audit writes for read-only analytics views.

## 11. Dependencies

### Hard prerequisites (must ship before CAS-017 can be deployed)

- **CAS-001** (`docs/suitecrm/specs/CAS-001.md`): Provides `S.crm_cases_enabled` flag, `crm_cases_sla_config` table, all sub-flags, and wires `T.crm_cases_*` handles in `app/core/tables.py`. Without CAS-001, the flag check in the route handler references a non-existent `S` attribute and the import fails.
- **CAS-003** (`docs/suitecrm/specs/CAS-003.md`): Provides the `priority` attribute on META rows and the `crm_cases_priority_index` GSI. Without CAS-003, `open_by_priority` falls back to the `STATUS#open` sweep with Python grouping (all items land in `"unset"`), which is functional but less efficient.

### Soft predecessors (provide context; CAS-017 does not block on them)

- **CAS-002** (sequential case numbers): Confirms the `TicketOut` model extension pattern used to add `case_number`. CAS-017 follows the same additive-field approach for new response models.
- **CAS-004** (email notifications): The `audit_event` call pattern for ticket events is established by CAS-004. CAS-017 reuses `audit_event("ticket_analytics_viewed", ...)` in the same style.
- **CAS-008** (SLA management): SLA breach metrics are a natural extension of the resolution-time analytics in CAS-017. CAS-008 may eventually consume `get_analytics` or co-locate SLA computations in the same service method.
- **CAS-009** (escalation): `by_assignee` throughput data is directly useful for identifying agents with escalation bottlenecks — a future CAS-009 escalation dashboard could embed the `TicketAnalyticsDashboard` component.

### Sibling CRM tickets with adjacent concerns

- **PTY-001..PTY-015** (`PARTY_CRM_TICKETS.md`): Party/Contact/Account records. CAS-017's `by_assignee` currently uses raw `user_sub` identifiers. Once PTY ships, the assignee display names can be resolved by joining against Party records. CAS-017 does not block on PTY.
- **MKT (MARKETING_CAMPAIGNS)**, **PRD (CATALOG_DEPTH)**, **OFB (OFBIZ_COMMERCE)**: No direct dependency. CAS-017 is self-contained to the tickets domain.
