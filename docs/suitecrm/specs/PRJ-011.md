# PRJ-011 — Project-to-Account and Project-to-Ticket relationships

**Ticket type:** Feature  
**Priority:** P2  
**Estimate:** 1 day  
**Feature flag:** `CRM_PROJECTS_ENABLED` (shared with all PRJ tickets, default OFF)

---

## 1. Summary & Goal

PRJ-011 adds two lightweight relationship types to the CRM project management system introduced in PRJ-001/PRJ-002:

1. **Project-to-Account**: A CRM project can be associated with exactly one Account (an opaque `party_id` string, eventually resolved by PTY-015's org-account model). The project list endpoint gains an `account_id` query parameter that uses a dedicated GSI for efficient per-account project lookup.

2. **Project-to-Ticket**: A support ticket can be tagged with at most one CRM project. New service functions and three router endpoints allow a project member to link/unlink existing tickets and to list all tickets linked to a given project.

Both features are additive, gated behind the existing `CRM_PROJECTS_ENABLED` flag, and make no changes to any existing table schema or route. They share implementation infrastructure already established by PRJ-001 through PRJ-010 (tables, flag guard, auth access model, audit primitives, cursor pagination).

### File-grouping `projects` table (existing — do not modify)

`app/services/projects_store.py` implements a file-grouping `ProjectModel` (lines 1–605). The PRJ-001 ticket defines four new tables (`crm_pm_projects`, `crm_pm_tasks`, `crm_pm_members`, `crm_pm_templates`), settings keys, and table handles (referenced at `CRM_PROJECTS_GANTT_TICKETS.md:41–116`). None of these files exist yet in the codebase (confirmed: `grep -rn "crm_project" app/` returns empty). PRJ-011 amends the `crm_pm_projects` table definition (adding GSI3) and extends the service and router modules created by those upstream tickets.

`CrmProjectModel` is defined by PRJ-002; the `account_id: Optional[str]` field was declared as a placeholder at `CRM_PROJECTS_GANTT_TICKETS.md:151`. PRJ-011 implements the storage and query path for that field.

### Tickets table (existing — additive extension only)

`app/services/tickets.py` defines `TicketStore` with a `create_ticket` method at line 411. The META item is written to `T.tickets` (handle wired at `app/core/tables.py` via `_safe_table(S.tickets_table_name)`). The META item shape at lines 441–475 already carries `gsi1pk/gsi1sk` (owner), `gsi2pk/gsi2sk` (status), `gsi3pk/gsi3sk` (assignee), and six space-scoped GSI key pairs. The `tickets` DDB table is defined in `scripts/local-ddb-init.py:695–711` with ten GSIs. There is no `project_id` field on the META item today; PRJ-011 adds it as an optional attribute.

The existing `_conditional_update_meta` helper at `tickets.py:723` uses an explicit `UpdateExpression` with aliased attribute names. Adding `project_id` requires extending this method's `set_parts` list and `names` map.

### GSI limit consideration

The `tickets` table already has ten GSIs (`scripts/local-ddb-init.py:700–710`). DynamoDB supports up to 20 GSIs per table. Adding one more (`tickets_project_index`) leaves nine slots free. The index uses a string PK (`gsi_project_pk = "PROJECT#<project_id>"`) and a numeric SK (`gsi_project_sk = updated_at` as an integer). The `attr_types` declaration for this numeric sort key is mandatory (CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha).

### Auth dependency

`app/auth/deps.py` exports `require_ui_session` (via `app/services/sessions.py:330`, referenced in `CRM_PROJECTS_GANTT_TICKETS.md:17`). All CRM project routes use this dependency. The member-role access check `_assert_project_access` (introduced in PRJ-007) gates mutation operations to project `owner` or `member` roles.

### Audit primitive

`app/services/alerts.audit_event` at `alerts.py:644` is the canonical audit write path, accepting `event`, `user_sub`, optional `request`, and arbitrary keyword fields. PRJ-011 emits two audit events: `crm_project.account_linked` and `crm_project.ticket_linked`.

### Cursor pagination

`app/core/cursor.py:94,103` provides `encode_cursor` / `decode_cursor` (HMAC-signed v2 format). All new paginated list responses use these helpers, consistent with the pattern established by PRJ-002.

## 3. Data Model

### 3a. Amendment to `crm_pm_projects` table — add GSI3

The `TableDef` for `crm_pm_projects` defined in PRJ-001 (`CRM_PROJECTS_GANTT_TICKETS.md:53–61`) must be amended to include a third GSI for per-account project lookup. This is declared alongside the existing GSI1 and GSI2 in `scripts/local-ddb-init.py`:

```python
# Addition to the crm_pm_projects TableDef (amends PRJ-001):
TableDef(
    _resolve_table_name(S.crm_pm_projects_table_name, "crm_pm_projects"),
    "PK", "SK",
    gsi=[
        {"index_name": "GSI1", "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "GSI2", "partition_key": "GSI2PK", "sort_key": "GSI2SK"},
        {"index_name": "GSI3", "partition_key": "GSI3PK", "sort_key": "GSI3SK"},  # NEW
    ],
    attr_types={"GSI2SK": "N", "GSI3SK": "N"},  # GSI3SK is also numeric
),
```

**GSI3 key strategy for `crm_pm_projects`:**

| Attribute | Value |
|-----------|-------|
| `GSI3PK`  | `"ACCOUNT#{account_id}"` when `account_id` is set; `"ACCOUNT#NONE"` when null |
| `GSI3SK`  | `created_at` (integer Unix seconds) |

All CRM project items (both new and any created before account assignment) must write `GSI3PK` and `GSI3SK` on create and on every `update_crm_project` call that may change `account_id`. The `"ACCOUNT#NONE"` sentinel allows a full account-null list without a FilterExpression, but callers filtering for a specific account_id will always supply a real `account_id` value.

**Full DDB item shape for a CRM project (updated from PRJ-002):**

```
PK          = "OWNER#{owner_sub}"
SK          = "PROJECT#{project_id}"
GSI1PK      = "PROJECT#{project_id}"
GSI1SK      = "OWNER#{owner_sub}"
GSI2PK      = "STATUS#{status}"
GSI2SK      = created_at          (integer, attr_types N)
GSI3PK      = "ACCOUNT#{account_id}"  or  "ACCOUNT#NONE"
GSI3SK      = created_at          (integer, attr_types N)
entity_type = "crm_project"
account_id  = <str or None>
... (all other PRJ-002 fields)
```

```python
    caller_sub: str,
    account_id: str,
    *,
    limit: int = 50,
    cursor: Optional[str] = None,
) -> dict[str, Any]:

    Query GSI3 on crm_pm_projects for all projects linked to account_id.
    Returns {"items": List[CrmProjectModel], "cursor": Optional[str]}.
    Caller must be authenticated (any valid user_sub) — not restricted to
    project members, since account-level lookup is a CRM read operation.
    Raises HTTP 404 when CRM_PROJECTS_ENABLED is False (via _require_crm_projects()).
    """
```

```python
def set_ticket_project(
    caller_sub: str,
    ticket_id: str,
    project_id: Optional[str],
) -> dict[str, Any]:
    """
    Set or clear the project_id on a ticket META item.
    - Verifies project exists via get_crm_project_by_id() (GSI1 lookup).
    - Verifies caller is a project member with role >= member via
      _assert_project_access(caller_sub, project_id, min_role="member").
    - Verifies ticket exists via STORE.get_ticket(ticket_id); raises 404 if absent.
    - Verifies caller owns the ticket (ticket["owner_sub"] == caller_sub) OR
      caller is a project member (member check already done above) — project
      members may tag any ticket they created.
    - Writes project_id + gsi_project_pk + gsi_project_sk via
      _set_ticket_project_field(ticket_id, project_id, updated_at=now_ts()).
    - Emits audit_event("crm_project.ticket_linked", caller_sub, None,
        project_id=project_id, ticket_id=ticket_id).
    - Returns {"ok": True, "ticket_id": ticket_id, "project_id": project_id}.
    When project_id=None: clears the field + removes GSI keys, emits
      "crm_project.ticket_unlinked".
    """
```

```python
def get_tickets_for_project(
    caller_sub: str,
    project_id: str,
    *,
    limit: int = 50,
    cursor: Optional[str] = None,
) -> dict[str, Any]:
    """
    Query tickets_project_index (gsi_project_pk = "PROJECT#{project_id}")
    for all tickets linked to the project.
    Caller must be a project member (any role) via _assert_project_access().
    Returns {"items": List[dict], "cursor": Optional[str]}, where each item
    is the assembled ticket dict from STORE.get_ticket(ticket_id).
    ScanIndexForward=False → newest updated_at first.
    Uses encode_cursor / decode_cursor from app.core.cursor.
    """
```

Internal helper (private to the module):

```python
def _set_ticket_project_field(

    project_id: Optional[str],

    Directly updates the tickets META item with the project_id field.
    Uses T.tickets.update_item with an UpdateExpression that SETs
```

```python
    account_id: Optional[str] = Query(default=None, max_length=256),
    status: Optional[str] = Query(default=None),
```

## 5. Detailed Behavior & Edge Cases

### Account linking

**Single account per project**: `account_id` is a scalar field on the project item; a project may be linked to at most one account. To switch accounts, the caller PATCHes with a new `account_id`. To clear, PATCH with `account_id: null`.

**GSI3PK sentinel**: Every project item always carries `GSI3PK` and `GSI3SK` (either `"ACCOUNT#{id}"` or `"ACCOUNT#NONE"`). This is set on `create_crm_project` (PRJ-002 is amended) and on every `update_crm_project` call. Omitting the sentinel would leave old items invisible to GSI3 queries after a table rebuild.

**`list_crm_projects_by_account` pagination**: queries `GSI3PK = "ACCOUNT#{account_id}"` with `ScanIndexForward=False` (newest-first). `Limit` is passed directly to DynamoDB; `LastEvaluatedKey` is encoded via `encode_cursor` (app/core/cursor.py:94). The function does not filter by caller ownership — any authenticated user can list projects linked to an account. This matches CRM use-case (sales reps see all org projects for an account).

**Account ID validation**: `account_id` is accepted as an opaque string (max 256 chars). No existence check against PTY party records is performed in PRJ-011. Once PTY-015 ships, a follow-up ticket can add a validation call to `party_service.get_account(account_id)`.

### Ticket linking

**One project per ticket**: `project_id` is a scalar field on the ticket META item. Calling `link_ticket_to_project_route` when the ticket already has a different `project_id` overwrites it (no conflict error). If idempotent behavior is desired, the client should unlink first. This matches SuiteCRM's behavior (a case belongs to one project).

**No version bump**: `_set_ticket_project_field` writes `project_id`, `gsi_project_pk`, `gsi_project_sk` via a direct `update_item` without incrementing `version`. Project linkage is a relationship annotation, not a ticket state transition. This avoids conflicting with concurrent status transitions that use the optimistic-locking pattern in `_conditional_update_meta` (tickets.py:723).

**`get_tickets_for_project` assembly**: the GSI returns ticket META header items. For each header, `STORE.get_ticket(ticket_id)` is called to assemble the full ticket dict (including messages and activity). This is the same `_assemble_headers` pattern used by `list_tickets` at tickets.py:603. For large projects, the caller should use `limit`+`cursor` pagination to bound the number of per-ticket fetches.

**Ticket ownership check for linking**: `set_ticket_project` verifies `ticket["owner_sub"] == caller_sub` OR `caller_sub` is a member of the target project. This prevents a project member from tagging tickets they do not own. If the ticket does not exist, a 404 is raised before any project membership check.

**Clearing the link**: `POST /v1/crm/projects/{project_id}/tickets/{ticket_id}` with the same project already linked is idempotent (returns `{"ok": true}`). `DELETE` on a ticket not linked to any project returns `{"ok": true, "ticket_id": ..., "project_id": null}` (no error).

**GSI key cleanup on ticket deletion**: the existing `TicketStore` does not have a delete endpoint (tickets are status-transitioned to `done`). If a hard-delete path is ever added, it must also remove `gsi_project_pk`/`gsi_project_sk` — this is a future concern noted in the Open Questions section.

**FilterExpression fallback**: the ticket spec (PRJ-011 source text, line 601–607) notes a FilterExpression scan fallback if the GSI cannot be added. Since the `tickets` table has only ten GSIs against a DynamoDB limit of twenty, the new GSI is feasible. The fallback path is not implemented.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

All DDB operations use `T.crm_pm_projects` and `T.tickets` table handles wired in `app/core/tables.py`. In dev, these resolve to DynamoDB Local (port 8001); in prod, they hit real DynamoDB. There is no `if S.dev_mode` branch in the service layer. The `audit_event` call at `alerts.py:644` writes to `T.alerts` in both environments. The `send_alert_email` call (if extended from PRJ-009 completion notifications) writes to a dev log file in dev mode (`alerts.py:462–467`) and sends via SES in prod — the call site in the service layer is identical.

### Idempotency

- `link_ticket_to_project_route` (`POST`): calling with the same `(project_id, ticket_id)` pair twice writes the same values and returns `{"ok": true}` both times. DynamoDB `update_item` without a condition expression is naturally idempotent for scalar sets.
- `unlink_ticket_from_project_route` (`DELETE`): clearing an already-null `project_id` is safe; the REMOVE expression on absent attributes is a no-op in DynamoDB.
- `list_crm_projects_by_account`: pure read, idempotent.

### Security

- **Authorization**: all mutation endpoints verify membership via `_assert_project_access(caller_sub, project_id, min_role="member")` (defined in PRJ-007). Viewers (read-only role) cannot link or unlink tickets. Non-members receive HTTP 403.
- **Ticket ownership**: `set_ticket_project` confirms the caller is either the ticket's `owner_sub` or a project member before modifying the ticket. This prevents cross-user ticket tagging.
- **Input validation**: `account_id` max 256 chars; `ticket_id` and `project_id` path parameters have a maximum implicit length from Pydantic `str`. No SQL or expression injection risk (DynamoDB expressions use positional value maps).
- **Audit trail**: every link/unlink/account-change emits an `audit_event` with the caller's `user_sub`, allowing compliance review.
- **CSRF**: all POST/DELETE routes go through `require_ui_session` which enforces CSRF token validation for cookie-authenticated requests (`app/auth/deps.py`). Bearer-authenticated API clients skip CSRF per the standard platform policy.

## 8. Backward Compatibility & Migration

### Existing data

- **`crm_pm_projects` items created before PRJ-011**: any project items written by PRJ-002 (before GSI3 was declared) will not appear in GSI3 queries because they lack `GSI3PK`/`GSI3SK` attributes. Since PRJ-001 through PRJ-010 have no production data yet (the feature is default-OFF), this is not a concern for the initial rollout. If the flag is enabled after any PRJ-002 data has been written, a one-time backfill script must iterate all `OWNER#` partitions and write `GSI3PK`/`GSI3SK` on each item.

- **`tickets` items existing before PRJ-011**: tickets without `project_id` will not appear in the `tickets_project_index` GSI, which is the correct behavior (they are not linked to any project). No migration is required.

### Additive-only guarantee

- The `ProjectModel` in `app/models.py:1796` is not touched.
- The file-grouping `T.projects` table and `app/services/projects_store.py` are not modified.
- The `TicketOut` response model and `TicketStore.get_ticket()` response dict are extended by the optional `project_id` field only (existing callers that do not read this field are unaffected).
- The existing `_conditional_update_meta` helper at `tickets.py:723` is extended to handle `project_id`/`gsi_project_pk`/`gsi_project_sk` in the same REMOVE-when-None pattern already used for space GSI keys (lines 757–771). The method's call signature is unchanged.

### `scripts/local-ddb-init.py` changes

Two table definition changes:
1. `crm_pm_projects`: add `GSI3` entry and add `"GSI3SK": "N"` to `attr_types`.
2. `tickets`: add the `tickets_project_index` GSI entry and add `"gsi_project_sk": "N"` to `attr_types`.

Both changes are in the init script only; running `just restart` recreates the tables with the new GSIs. ## 10. Open Questions / Assumptions

1. **Account existence validation**: PRJ-011 stores `account_id` as an opaque string without verifying it against a party store. Assumption: PTY-015 has not shipped; once it does, a follow-up PRJ-013 ticket should add a `party_service.get_account(account_id)` validation guard in `update_crm_project`.

2. **Multi-account project support**: the current design allows exactly one `account_id` per project. SuiteCRM similarly uses a single account field. If multi-account linking is needed, the `CrmProjectModel.account_id` scalar must become a list and the GSI3 fan-out must write one row per account. This is deferred; the single-value design is explicitly documented as the chosen path.

3. **Ticket hard-delete GSI cleanup**: there is no ticket hard-delete path today (tickets are archived via status transition). If one is added in a future ticket, the implementer must also remove `gsi_project_pk`/`gsi_project_sk` from the item to avoid leaving stale GSI entries. This is logged as a future concern; no action required in PRJ-011.

4. **GSI3 backfill for existing CRM project data**: if the flag is ever enabled in a staging or production environment that already has `crm_pm_projects` items from PRJ-002 without `GSI3PK`/`GSI3SK`, those items will be invisible to per-account queries. A backfill script should be run before enabling the account-query feature for production users. The init script handles new tables; this is only relevant for table upgrades.

5. **`update_crm_project` version bump on `account_id` change**: the current spec does not bump `version` when only `account_id` changes. If downstream workflows use `version` for change detection (e.g., webhook delivery), a version bump may be warranted. Assumption: `version` tracks structural/status changes; relationship annotations do not increment it.

6. **`get_tickets_for_project` permission scope**: currently any project member (including viewers) can list linked tickets. If ticket visibility should be further restricted (e.g., a viewer should only see tickets they own), a secondary `owner_sub` filter can be added in `get_tickets_for_project`. This is deferred pending requirements.
