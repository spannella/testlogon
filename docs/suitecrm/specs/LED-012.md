# LED-012 — Activity log on Lead / Contact

**Type:** Feature | **Priority:** P1 | **Estimate:** 2d
**Ticket source:** `docs/suitecrm/CRM_LEADS_TICKETS.md`, section "LED-012"
**Sub-flag:** `leads_enabled` (master; no additional sub-flag)
**Depends on:** LED-001, LED-002, LED-003

---

## 1. Summary & Goal

LED-012 delivers a structured, paginated activity log attached to each Lead (and, by extension, each Party/Contact record once PTY lands) so that sales agents can see a chronological audit trail of every note, call, email, and meeting logged against that lead in one place.

The feature has two concerns:

1. **Sparse GSI on `activity_feed`** — add a `ByTarget` GSI to the existing `activity_feed` DynamoDB table so that activity rows tagged with `(target_type, target_id)` can be queried directly without scanning the owner's entire activity stream. This GSI is sparse: only rows that carry both `target_type` and `target_id` project into it.
2. **New service function and two endpoints** — `get_entity_activity_feed(target_type, target_id)` queries the `ByTarget` GSI; `POST /ui/leads/{lead_id}/activities` logs a note/call/email/meeting against the lead; `GET /ui/leads/{lead_id}/activities` retrieves that log newest-first.

Everything is **additive and gated**. When `S.leads_enabled=False` (the default) the two new endpoints return 404 and no existing surface — in particular the existing `GET /ui/activity/feed` endpoint defined in `app/routers/activity_feed.py:83` and the `record_activity` function in `app/services/activity_feed.py:45` — is altered in any way.

## 3. Data Model

### 3.1 Sparse `ByTarget` GSI on `activity_feed`

No new DynamoDB table is created. LED-012 adds one GSI to the existing `activity_feed` table.

**GSI definition** (to add in `scripts/local-ddb-init.py` at the `TableDef` for `activity_feed`):

```
GSI name    : ByTarget
Partition key: GSI_TARGET_PK  (type S)  — composite: "TARGET#{target_type}#{target_id}"
Sort key    : sk               (type S)  — reuses the existing PK/SK "ts#activity_id" value
Projection  : ALL
```

The GSI is **sparse** because `GSI_TARGET_PK` is only written onto rows that represent CRM entity activities (i.e., where `target_type` is non-empty and `target_id` is non-empty). Social activity rows (`follow`, `like`, `comment`, …) written by the existing `record_activity` path never carry `GSI_TARGET_PK` and therefore never appear in the GSI index. This avoids polluting the index with the high-volume social event stream.

**Updated `TableDef` in `scripts/local-ddb-init.py`**:

```python
TableDef(
    _resolve_table_name(S.activity_feed_table_name, "activity_feed"),
    "user_id",
    "sk",
    gsi=[{
        "index_name": "ByTarget",
        "partition_key": "GSI_TARGET_PK",
        "sort_key": "sk",
    }],
    # GSI_TARGET_PK is a string composite key — no attr_types entry needed.
    # "sk" is already declared as the primary sort key (S type).
),
```

`GSI_TARGET_PK` is a string (`S`), so no `attr_types` override is needed — the default `"S"` type is correct.

### 3.2 Activity row shape for CRM entity activities

When `record_activity_for_entity` (§4.1) writes an activity row it sets `GSI_TARGET_PK` in addition to the existing fields. The full item shape:

```
PK (user_id)     : "{lead_id}"              — the lead's own ID used as the "feed owner"
SK (sk)          : "{ts}#{activity_id}"
activity_id      : 16-char hex UUID
actor_id         : caller's user_sub
activity_type    : "note" | "call" | "email" | "meeting"
target_type      : "lead"                   — identifies entity class
target_id        : "{lead_id}"
GSI_TARGET_PK    : "TARGET#lead#{lead_id}"  — sparse GSI partition key
entity_type      : "lead"                   — denormalised for reads
metadata         : {body, subject, duration_seconds, direction, …}
created_at       : now_ts() (integer)
ttl_epoch        : now_ts() + CRM_ACTIVITY_TTL_SECONDS  (see §6)
read             : False
```

The `user_id` PK is set to the `lead_id` string (not a `user_sub`). This is an intentional overload of the `user_id` partition key — the lead record acts as its own "user" for the purpose of owning an activity stream. The existing `get_activity_feed(user_id)` query would therefore also work for leads if called with `lead_id` as the argument, but the entity-targeted `get_entity_activity_feed` path is preferred because it uses the GSI and supports multi-entity fan-out (e.g., Party records).

### 3.3 No changes to the `leads` table schema

Activity rows are stored exclusively in `activity_feed`. The `leads` table (LED-001) is not modified by this ticket.

## 4. API / Service Design

### 4.1 New service function: `record_activity_for_entity`

**Location**: `app/services/activity_feed.py` — new public function appended after the existing `get_unread_count` function.

```python
CRM_ACTIVITY_TYPES = {"note", "call", "email", "meeting"}

def record_activity_for_entity(
    *,
    target_type: str,           # "lead" or "party"
    target_id: str,             # lead_id or party_id
    actor_id: str,              # user_sub of the person logging the activity
    activity_type: str,         # must be in CRM_ACTIVITY_TYPES
    metadata: Optional[Dict[str, Any]] = None,
    ttl_override_seconds: Optional[int] = None,
) -> Dict[str, Any]:
```

**Behavior**:

1. Validates `activity_type in CRM_ACTIVITY_TYPES`; raises `ValueError` for unknown types (caught and re-raised as HTTP 422 at the router layer).
2. Calls `now_ts()` for `ts` and `now_ts() + (ttl_override_seconds or S.crm_activity_ttl_seconds)` for `ttl_epoch`. The default `S.crm_activity_ttl_seconds` comes from `os.environ.get("CRM_ACTIVITY_TTL_SECONDS", str(365 * 86400))` — one year, much longer than the social feed's 30 days.
3. Constructs `sk = f"{ts}#{activity_id}"` (same pattern as `record_activity` at `app/services/activity_feed.py:70`).
4. Writes the item with `GSI_TARGET_PK = f"TARGET#{target_type}#{target_id}"` set unconditionally.
5. Sets `user_id = target_id` so the row lives under the entity's own "feed partition."
6. Returns the stored item dict.

The existing `record_activity` function (`app/services/activity_feed.py:45`) is **not modified**. `record_activity_for_entity` is a new, separate function that calls `T.activity_feed.put_item` directly (no delegation to `record_activity`) so that the GSI key population and the extended TTL are guaranteed.

### 4.2 New service function: `get_entity_activity_feed`

**Location**: `app/services/activity_feed.py` — appended after `record_activity_for_entity`.

```python
def get_entity_activity_feed(
    target_type: str,
    target_id: str,
    *,
    limit: int = 50,
    cursor: Optional[str] = None,
) -> Tuple[List[Dict[str, Any]], Optional[str]]:
```

**Behavior**:

1. Constructs `gsi_pk = f"TARGET#{target_type}#{target_id}"`.
2. Issues a DynamoDB `query` against the `ByTarget` GSI with `IndexName="ByTarget"`, `KeyConditionExpression=Key("GSI_TARGET_PK").eq(gsi_pk)`, `ScanIndexForward=False` (newest first), `Limit=min(limit, 100)`.
3. Decodes `cursor` via `decode_cursor` (`app/core/cursor.py:103`); if non-None, passes as `ExclusiveStartKey`.
4. Encodes `LastEvaluatedKey` via `encode_cursor` (`app/core/cursor.py:94`) for the returned `next_cursor`.
5. Returns `(items, next_cursor)`.

### 4.4 Router endpoints

**File**: `app/routers/leads.py` (introduced by LED-013; LED-012 contributes two endpoint functions that LED-013 includes in the assembled router). The endpoints use `require_ui_session` from `app/services/sessions.py:330` (same dep as `app/routers/contacts.py:14`).

Both endpoints are guarded at the top by:

#### `POST /ui/leads/{lead_id}/activities`

```
Verb   : POST
Path   : /ui/leads/{lead_id}/activities
Auth   : require_ui_session (cookie + CSRF)
Body   : LeadActivityLogIn
Status : 201 Created
Returns: LeadActivityOut
```

**Steps**:

1. Verify the lead exists via `leads.get_lead(lead_id)` → 404 if absent.
2. Verify caller owns or is assigned to the lead (caller's `user_sub` == `lead["created_by"]` or `lead.get("assigned_to")`); admins bypass this check via `ctx["role"] >= Role.ADMIN`. Return 403 otherwise.
3. Call `activity_feed.record_activity_for_entity(target_type="lead", target_id=lead_id, actor_id=caller_sub, activity_type=body.activity_type, metadata={...}, ttl_override_seconds=None)`.
4. Call `alerts.audit_event("lead_activity.logged", caller_sub, lead_id=lead_id, activity_type=body.activity_type)` (`app/services/alerts.py:644`).
5. Return `LeadActivityOut` projected from the stored item.

#### `GET /ui/leads/{lead_id}/activities`

```
Verb   : GET
Path   : /ui/leads/{lead_id}/activities
Auth   : require_ui_session (cookie)
Params : cursor (optional, str), limit (optional, int 1-100, default 20)
Status : 200 OK
Returns: LeadActivityFeedResponse
```

**Steps**:

1. Verify the lead exists → 404 if absent.
2. Verify caller has read access (same ownership check as POST; admins bypass).
3. Call `activity_feed.get_entity_activity_feed("lead", lead_id, limit=limit, cursor=cursor)`.
4. Return `LeadActivityFeedResponse(items=[...], next_cursor=...)`.

## 5. Detailed Behavior & Edge Cases

### 5.1 `activity_type` validation

`LeadActivityLogIn.activity_type` uses a regex pattern `^(note|call|email|meeting)$` enforced by Pydantic before the handler body runs. This produces an HTTP 422 with a clear field error if an unknown type is submitted, without any service-layer code being reached.

The existing `ACTIVITY_TYPES` list at `app/services/activity_feed.py:22` is **not modified**. The CRM types are tracked in the new constant `CRM_ACTIVITY_TYPES` inside `activity_feed.py` (not exported to `ACTIVITY_TYPES`) to avoid breaking existing callers that iterate over `ACTIVITY_TYPES` for notifications or UI rendering.

### 5.2 Lead not found

Both endpoints call `leads.get_lead(lead_id)` first. If the lead does not exist (DDB `get_item` returns `None`) or has `status="dead"`, a 404 is raised. Soft-deleted leads (LED-003 sets `status="dead"`) are not accessible for new activity logging; historical activities remain queryable.

### 5.3 Ownership enforcement

The ownership check uses:
```python
owner = item["created_by"] == caller_sub or item.get("assigned_to") == caller_sub
if not owner and ctx["role"] < Role.ADMIN:
    raise HTTPException(403, "Access denied")
```
`Role` is imported from `app/auth/roles.py`. This mirrors the pattern used in `app/services/kyc_cases.py` where admin role bypasses ownership checks.

### 5.4 Idempotency of `record_activity_for_entity`

Each call generates a fresh `activity_id = uuid.uuid4().hex[:16]` and `ts = now_ts()`, so calls are not idempotent by design — each POST creates a distinct activity row. This is the correct behavior for an activity log (logging the same note twice means it was noted twice). However, the `PUT` semantics are not offered — there is no edit endpoint. Correction is achieved by logging a follow-up note.

### 5.5 ByTarget GSI query ordering

The GSI SK is the same `"{ts}#{activity_id}"` string that serves as the primary SK. Because timestamps are zero-padded as integers and `activity_id` is a hex suffix, lexicographic descending order (`ScanIndexForward=False`) is equivalent to reverse-chronological order within the same second. Ties within the same second are broken by the hex suffix (arbitrary but stable).

### 5.6 Existing `get_activity_feed` unaffected

Rows written by `record_activity_for_entity` set `user_id = target_id` (the lead ID). Since no platform user has a `user_sub` equal to a `lead_id` (lead IDs are prefixed `"lead_"`), these rows never appear in any user's personal social activity feed queried via `get_activity_feed(user_sub)`. The two namespaces are physically separate partitions.

### 5.7 Party / Contact reuse

The `target_type` parameter is not hard-coded to `"lead"`. When PTY-004 delivers Party records, the same `get_entity_activity_feed("party", party_id)` path works without code change because the GSI query is generic. LED-012 must be deployed before PTY tickets that log activity against parties.

### 5.8 Pagination across many activities

The `ByTarget` GSI is queried with `Limit=min(limit, 100)`. A lead with more than 100 activities paginates via the cursor. Because DDB FilterExpression does not reduce the DDB page size (per CLAUDE.md gotcha), no FilterExpression is applied in `get_entity_activity_feed` — the GSI partition is already fully scoped to the target entity.

### 5.9 TTL — CRM activities outlive social activities

Social activity rows carry a 30-day TTL (`_TTL_DAYS = 30` at `app/services/activity_feed.py:32`). CRM activity rows carry a `S.crm_activity_ttl_seconds` TTL (default one year). `record_activity_for_entity` computes `ttl_epoch` independently and does not call the private `_ttl_seconds()` helper (which reads the social TTL setting). DynamoDB honours the `ttl_epoch` attribute name regardless of the value — there is no schema change to the table.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

- **DynamoDB writes** via `T.activity_feed.put_item` go to DynamoDB Local (port 8001) in dev and to AWS DynamoDB in production. The code path is identical — no `S.dev_mode` branch is introduced. SECOPS-007 requires this.
- **Audit events** via `alerts.audit_event` (`app/services/alerts.py:644`) write to `T.alerts` in both environments. In dev this is DynamoDB Local; in prod it is the real DynamoDB `alerts` table. No SES call is made by this function.
- **GSI query** — moto's DynamoDB mock supports GSI queries; the offline hermetic test creates the GSI via `create_table` with `GlobalSecondaryIndexes`.

### 7.2 Ownership enforcement & access control

- Leads are user-owned; a lead is accessible only to its `created_by` user, its `assigned_to` user, and users with `role >= ADMIN`. The same rule applies to both the POST and GET activity endpoints.
- The `lead_id` path parameter is validated to correspond to a real existing lead (404 guard) before any DDB write occurs.
- `activity_type` is restricted to an allowlist via the Pydantic regex pattern. Free-text `body` and `subject` are stored as-is (no HTML, no rendering) with a character cap (`max_length=8000` and `500` respectively).

### 7.3 CSRF

All POST endpoints inherit the platform-wide CSRF enforcement from `require_ui_session`: the `x-csrf-token` header must match both the stored session `csrf_token` and the `ui_csrf` cookie (`app/auth/deps.py` — per CLAUDE.md auth-dependency section).

### 7.4 PII in metadata

`body`, `subject`, and caller-supplied metadata fields may contain PII (names, phone numbers). These are stored in DynamoDB unencrypted, consistent with the rest of the activity feed and tickets system. No additional encryption is required at this tier.

## 8. Backward Compatibility & Migration

### 8.1 `activity_feed` table — GSI addition

The `ByTarget` GSI is additive. Existing rows in `activity_feed` do not carry `GSI_TARGET_PK` and are therefore invisible to the new GSI. The existing primary key queries (PK=`user_id`) and the social-feed endpoints are unaffected.

In a production deployment, adding a GSI to an existing DynamoDB table requires an `UpdateTable` API call. The table enters `UPDATING` state while DynamoDB backfills the GSI (typically minutes for a small table). During backfill, writes continue normally; reads against the new GSI may return partial results until backfill completes. Since the GSI is sparse and only LED-012 writes `GSI_TARGET_PK`, no backfill is needed in practice (pre-existing rows never carry the key). The backfill completes near-instantly.

In dev, `just restart` recreates all tables from scratch via `scripts/local-ddb-init.py`, so the GSI is present from the first start after LED-012 is deployed.

### 8.2 No migration for the `leads` table

LED-012 does not alter the `leads` table schema (LED-001/003) or any of its existing rows.

### 8.3 No existing endpoint changes

`app/services/activity_feed.py:45` (`record_activity`), `app/services/activity_feed.py:101` (`get_activity_feed`), `app/routers/activity_feed.py:83` (`GET /ui/activity/feed`), and all other existing activity-feed entry points are byte-for-byte unchanged.

## 10. Open Questions / Assumptions

1. **Party/Contact support** — The `target_type` parameter is deliberately generic (`"lead"` or `"party"`). The design assumes PTY-004 (Party record creation) will supply a `party_id` value that LED-012 can annotate directly once that ticket ships. Until then, only `target_type="lead"` is exercised. The LED-012 implementation should not special-case `"lead"` — it should treat `target_type` as an opaque string.

2. **Email activity type vs. platform email** — Logging an `activity_type="email"` does not send an email; it records that an email was sent (e.g., via an external mail client). The field name is a CRM concept ("I sent an email to this lead") not a trigger. Actual email delivery remains with `app/services/alerts.send_alert_email` (`app/services/alerts.py:459`) which is unrelated.

3. **Activity edit/delete** — No edit or delete endpoint is specified. If a CRM agent logs a note in error, the recommended workaround is logging a corrective note. Adding edit/delete would require soft-delete semantics on the `activity_feed` table (a `deleted=True` flag) and a FilterExpression on every query; this is deferred to a future CRM-quality-of-life ticket.

4. **`occurred_at` vs. `created_at`** — `occurred_at` in `LeadActivityLogIn` allows back-dating (e.g., "I spoke with this lead yesterday"). It is stored in `metadata` and surfaced in `LeadActivityOut.occurred_at`. The row's `created_at` always reflects the time the activity was *logged* (server-side `now_ts()`). The assumption is that the frontend renders `occurred_at` when present, falling back to `created_at`.

5. **GSI backfill latency in prod** — Adding the `ByTarget` GSI to an already-populated `activity_feed` table in production will take time. Since pre-existing rows carry no `GSI_TARGET_PK`, the backfill is instantaneous (nothing to index). Confirmed by DynamoDB documentation: sparse GSI backfill only indexes items that carry the GSI partition key attribute.
