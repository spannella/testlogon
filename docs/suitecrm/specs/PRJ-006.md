# PRJ-006 — Project templates (clone task structure)

**Type:** Feature | **Priority:** P2 | **Estimate:** 2d  
**Depends on:** PRJ-001, PRJ-002, PRJ-003, PRJ-004  
**Feature flag:** `CRM_PROJECTS_ENABLED` (default `"0"`)

---

## 1. Summary & Goal

Allow users to save a CRM project's task structure as a named, reusable template, and to instantiate new CRM projects from any owned template. The resulting project gets a fresh header with a user-supplied name and start date; every task is cloned with correctly offset dates, and predecessor-to-successor links are re-mapped from template task indices to the newly minted task IDs — so dependency graphs survive cloning intact.

This ticket introduces one new DynamoDB table (`crm_pm_templates`), one new service module (`app/services/crm_project_templates.py`), and six new route handlers appended to the existing `app/routers/crm_projects.py` router. No existing table, service, or router is modified.

## 3. Data Model

### 3.1 `crm_pm_templates` DynamoDB table

**Table definition** (insert in `scripts/local-ddb-init.py` immediately after the `crm_pm_members` TableDef block, which is itself inserted by PRJ-001 after line 277):

```python
# CRM Project Templates (PRJ-006)
# PK=OWNER#{owner_sub}, SK=TEMPLATE#{template_id}
# GSI1: PK=TEMPLATE#{template_id}, SK=OWNER#{owner_sub}  (single-template lookup by id)
TableDef(
    _resolve_table_name(S.crm_pm_templates_table_name, "crm_pm_templates"),
    "PK",
    "SK",
    gsi=[
        {"index_name": "GSI1", "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
    ],
),
```

No numeric GSI sort key here: all GSI keys are strings. No `attr_types` declaration is needed (contrast with the `crm_pm_projects` table where `GSI2SK = created_at` is numeric and requires `attr_types={"GSI2SK": "N"}`).

**Item shape:**

| Attribute | Type | Value |
|---|---|---|
| `PK` | S | `OWNER#{owner_sub}` |
| `SK` | S | `TEMPLATE#{template_id}` |
| `GSI1PK` | S | `TEMPLATE#{template_id}` |
| `GSI1SK` | S | `OWNER#{owner_sub}` |
| `entity_type` | S | `"crm_template"` |
| `template_id` | S | UUID hex |
| `owner_sub` | S | caller's `user_sub` |
| `name` | S | 1–120 chars |
| `description` | S | optional, ≤2000 chars |
| `task_defs` | L | list of task-definition maps (see §3.2) |
| `created_at` | N | `now_ts()` integer |
| `updated_at` | N | `now_ts()` integer |

### 3.2 `task_defs` element shape

Each element of the `task_defs` list is a DynamoDB map capturing the structural (non-transient) fields of a `CrmProjectTaskModel`. Transient runtime fields — `start_date`, `end_date`, `assigned_user_sub`, `percent_complete` — are stripped during capture, as they belong to a specific project instance and are meaningless in a reusable template.

| Field | Type | Notes |
|---|---|---|
| `template_task_id` | S | stable opaque ID assigned at template-save time (UUID hex); used as the predecessor-reference key within this template |
| `name` | S | task display name, 1–200 chars |
| `description` | S | optional, ≤2000 chars |
| `task_order` | N | ascending integer from the source project |
| `duration_days` | N | ≥1, integer |
| `is_milestone` | BOOL | copied from source task |
| `predecessor_template_task_ids` | SS / L | list of `template_task_id` values this task depends on; empty list if none |

`predecessor_task_ids` from the source `CrmProjectTaskModel` are stored here as `predecessor_template_task_ids` referencing the new `template_task_id` values — not the original live task IDs. This re-mapping happens during `create_template_from_project` (§4.2).

### 3.3 No changes to existing tables

This ticket does not add, alter, or remove GSIs or attributes on any of the three other CRM PM tables (`crm_pm_projects`, `crm_pm_tasks`, `crm_pm_members`) defined in PRJ-001 through PRJ-004. It does not touch the legacy `projects` table at `scripts/local-ddb-init.py:270`.

### 4.2 Service layer (`app/services/crm_project_templates.py`)

All functions use `T.crm_pm_templates`. They call `now_ts()` from `app/core/time.py:2`. Template IDs are `uuid4().hex`. Functions raise `HTTPException(404)` for not-found and `HTTPException(400)` for validation failures.

#### `create_template(owner_sub, name, *, description, task_defs) -> CrmProjectTemplateModel`

Validates `name` (strip + length). Assigns a fresh `template_id`. Stores the item with `put_item(ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)")`. Emits `audit_event("crm_template.created", owner_sub, None, template_id=template_id, task_count=len(task_defs))` using `app/services/alerts.audit_event` at `alerts.py:644`. Returns the model.

#### `create_template_from_project(owner_sub, project_id, name, *, description) -> CrmProjectTemplateModel`

1. Calls `get_crm_project(owner_sub, project_id)` (from PRJ-002's `app/services/crm_projects.py`) — raises 404 if project not found or not owned by `owner_sub`.
2. Calls `list_tasks(owner_sub, project_id, limit=500)` (from PRJ-003's `app/services/crm_project_tasks.py`) to collect all task items. The `list_tasks` function paginates via `LastEvaluatedKey`; this function must loop until `cursor` is `None` to handle projects with >500 tasks (loop via `decode_cursor` / `encode_cursor` from `app/core/cursor.py:94,103`).
3. Assigns a fresh `template_task_id` (UUID hex) to each live task; builds a mapping `{live_task_id → template_task_id}`.
4. For each task, constructs a `CrmTemplateTaskDef`: strips `start_date`, `end_date`, `assigned_user_sub`, `percent_complete`; translates `predecessor_task_ids` using the mapping (silently drops predecessor refs that do not map, e.g. predecessor from a different project — defensive; should not occur under normal use).
5. Delegates to `create_template(owner_sub, name, description=description, task_defs=task_defs)`.

#### `get_template(owner_sub, template_id) -> CrmProjectTemplateModel`

Calls `T.crm_pm_templates.get_item(Key={"PK": f"OWNER#{owner_sub}", "SK": f"TEMPLATE#{template_id}"}, ConsistentRead=True)`. Raises 404 if not found or `entity_type != "crm_template"`. Converts the DynamoDB item to `CrmProjectTemplateModel` via `_template_from_item`.

#### `list_templates(owner_sub, *, limit=50, cursor=None) -> {"items": List[CrmProjectTemplateModel], "cursor": Optional[str]}`

Queries `PK = OWNER#{owner_sub}` with `SK begins_with("TEMPLATE#")`, `ScanIndexForward=False` (newest first), respects `limit` (1–200). Passes `decode_cursor(cursor)` as `ExclusiveStartKey`. Returns `encode_cursor(LastEvaluatedKey)` as the next cursor.

#### `delete_template(owner_sub, template_id) -> {"ok": True}`

Calls `T.crm_pm_templates.delete_item(Key=..., ConditionExpression="attribute_exists(PK) AND attribute_exists(SK)")`. Raises 404 on `ConditionalCheckFailedException`. Does not cascade — templates are structurally independent of live projects.

#### `instantiate_from_template(owner_sub, template_id, project_name, *, start_date=None) -> CrmProjectModel`

1. Calls `get_template(owner_sub, template_id)` — 404 if not found.
2. Calls `create_crm_project(owner_sub, project_name)` from PRJ-002 to mint a new `CrmProjectModel` with `status=draft`. Returns a `project_id`.
3. Sorts `task_defs` by `task_order` ascending.
4. Allocates new live `task_id` values (UUID hex) for each task-def; builds a mapping `{template_task_id → new_task_id}`.
5. For each task-def (in `task_order` order):
   - Computes `task_start_date = start_date + offset_days * 86400` where `offset_days` is the cumulative offset from the first task's notional start. The first task (lowest `task_order`) gets `start_date` directly; each subsequent task's offset is computed as `sum of duration_days of all predecessor chain` using the sorted task order (simple sequential offset: `offset_days[i] = sum(duration_days[j] for j in range(i))`). When `start_date` is `None`, `task_start_date` is `None`.
   - Calls `create_task(owner_sub, project_id, name=..., task_id=new_task_id, task_order=task_def.task_order, duration_days=..., start_date=task_start_date, description=..., is_milestone=...)` from PRJ-003.
   - Translates `predecessor_template_task_ids` → `predecessor_task_ids` using the `{template_task_id → new_task_id}` mapping. Passes to `create_task`. Predecessor validation (no-cycle, same-project) from PRJ-004 runs automatically inside `create_task`.
6. Emits `audit_event("crm_template.instantiated", owner_sub, None, template_id=template_id, project_id=project_id, task_count=len(task_defs))`.
7. Returns the newly created `CrmProjectModel`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Template capture from a project with no tasks

`create_template_from_project` succeeds; it stores `task_defs: []`. `instantiate_from_template` on such a template creates a project with no tasks. This is valid — a blank structural template acts as a project header preset.

### 5.2 Predecessor re-mapping correctness

During `create_template_from_project`, a live task whose `predecessor_task_ids` contains a task ID from a different project (an invalid cross-project predecessor, which PRJ-004 should block, but defensively handled here) is silently dropped from `predecessor_template_task_ids` rather than failing. The invariant is maintained: `predecessor_template_task_ids` only ever references `template_task_id` values within the same template.

During `instantiate_from_template`, the reverse mapping `{template_task_id → new_task_id}` is built before any `create_task` call. Every `predecessor_template_task_ids` entry is translated; any entry not found in the map is dropped (defensive, should not occur for well-formed templates). PRJ-004's cycle-detection and date-conflict checks run inside `create_task` on the freshly translated `predecessor_task_ids`, ensuring constraints are re-validated in the new project context.

### 5.3 Date offset computation during instantiation

When `start_date` is provided, dates are computed as a linear sequence:

```
task_defs sorted ascending by task_order
offset_days[0] = 0
offset_days[i] = offset_days[i-1] + task_defs[i-1].duration_days
task_start_date[i] = start_date + offset_days[i] * 86400
```

This is a simple sequential layout rather than critical-path scheduling (which would require resolving the predecessor DAG). The sequential layout is sufficient for template initialization; users can adjust dates after instantiation. The predecessor-date-conflict check in PRJ-004 may fire if the sequential layout does not satisfy the predecessor constraint for non-linear dependency graphs. In that case, `instantiate_from_template` passes `skip_date_validation=True` to `create_task` so that the instantiation always succeeds regardless of the mechanical offset choice. Users then resolve date conflicts via the normal task edit UI.

### 5.4 Large projects (>500 tasks)

`create_template_from_project` loops through `list_tasks` pagination (looping on `LastEvaluatedKey` via `decode_cursor`/`encode_cursor`) until all tasks are collected. DynamoDB `FilterExpression` does not reduce page size (documented in CLAUDE.md), so the loop correctly drains all pages.

### 5.5 Template ownership and access

Templates are strictly per-owner. There is no sharing or team-visibility concept for templates in this ticket (contrast with PRJ-007 project membership). `get_template` and `list_templates` use the caller's `owner_sub` as the DDB partition key — a user cannot access another user's templates by guessing a `template_id`.

### 5.6 Delete does not cascade to live projects

Deleting a template does not affect any project that was previously instantiated from it. Instantiation copies all data at the time of the call; no foreign-key relationship is maintained between the live project and its source template.

### 5.7 Task limit per template

`task_defs` is stored as a DynamoDB List attribute on a single item. DynamoDB single-item size is capped at 400 KB. At roughly 300 bytes per task-def, this supports ~1,300 tasks in a single template. The service does not impose a lower explicit cap, but validation rejects `name` or `description` fields that exceed their declared maximums, keeping individual task-def payloads bounded. If an abnormally large project is converted, the `put_item` call will fail with a `ValidationException` from DynamoDB; the service surfaces this as HTTP 400 `template_too_large`.

### 5.8 Idempotency of `from-project`

`POST /templates/from-project/{project_id}` is not idempotent by design — each call produces a new template with a new `template_id`. Callers that need idempotency should check their template list first.

### 5.9 Empty `name` or whitespace names

The Pydantic `Field(min_length=1)` constraint rejects empty strings at the serialization boundary (422). The service layer additionally strips and re-validates to guard against whitespace-only names that pass the length check.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

There is no `dev_mode` branch in any service or router function in this ticket. All DynamoDB operations use `T.crm_pm_templates` and run against DynamoDB Local (moto in-process for tests, DynamoDB Local process at port 8001 in the dev stack, real DynamoDB in prod) without branching. The `audit_event` call at `app/services/alerts.py:644` writes to `T.alerts` in all environments.

### Idempotency

- `create_template` uses `ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)"` — if the same UUID is generated twice (astronomically unlikely), the second call raises `ConditionalCheckFailedException`, which is surfaced as HTTP 409. The caller should retry with a new ID (the service generates a fresh UUID on each call, so retry from the client is safe).
- `delete_template` uses `ConditionExpression="attribute_exists(PK) AND attribute_exists(SK)"` — deleting an already-deleted template raises 404, which is the correct idempotent behaviour for a DELETE.
- `instantiate_from_template` creates a new project and tasks on every call; it is not idempotent. This is by design — instantiation is a destructive-write operation analogous to `create_project`.

### Security

- **Ownership enforcement at every read/write**: `get_template`, `delete_template`, and `instantiate_from_template` use `PK = OWNER#{owner_sub}` derived from the session's `user_sub` — a user cannot access a template they do not own, even with a valid `template_id`, because the DDB key lookup will return no item.
- **No cross-tenant data leak**: the GSI1 (`TEMPLATE#{template_id}` / `OWNER#{owner_sub}`) is used only internally for canonical item lookup by ID when the owner sub is already known; the router always passes the session `user_sub` as the ownership filter before performing any GSI query.
- **Input size limits**: `task_defs` list is serialized directly to DynamoDB; `name` and `description` fields on each task-def have Pydantic `max_length` constraints (200 and 2000 respectively) to bound item size and prevent DoS via oversized payloads.
- **Audit trail**: every template creation and every instantiation emits an `audit_event` record to `T.alerts`, providing a durable, tamper-evident log of template usage per user.

## 8. Backward Compatibility & Migration

### Zero migration required

This ticket is purely additive:

- No existing DynamoDB table schema is altered.
- No existing service function signature is changed.
- No existing router or endpoint is modified.
- The `crm_pm_templates` table does not exist before this ticket ships; `scripts/local-ddb-init.py` creates it on the next `just restart` or `just up` run.
- In production, the table is created by running the updated `local-ddb-init.py`-equivalent provisioning script (or a CloudFormation/Terraform equivalent) before deploying the new code. Because all routes are behind `CRM_PROJECTS_ENABLED=0` by default, the table can be created in production ahead of the code deploy with zero risk.

### Enabling in production

1. Deploy new code (routes 404 while flag is off).
2. Run table provisioning to create `crm_pm_templates`.
3. Set `CRM_PROJECTS_ENABLED=1` on backend instances (rolling restart or env-var update).
4. All six template routes become live immediately with no data migration.

## 10. Open Questions / Assumptions

1. **Sharing / visibility of templates**: This spec assumes templates are private to the creator (`owner_sub`). A future ticket could add a `visibility: "private" | "org"` field and a GSI on organization scope. Until then, no cross-user template access is possible.

2. **Template update / PATCH**: This spec omits a `PATCH /templates/{template_id}` endpoint. Templates are intended as snapshots; editing them does not retroactively affect any instantiated project. If an update endpoint is later needed, it should use a `replace_all` semantics (overwrite `task_defs`) rather than a partial task-def merge, since `task_defs` is a flat DynamoDB List (not a map keyed by `template_task_id`).

3. **Maximum task-defs per template**: No explicit cap is imposed beyond DynamoDB's 400 KB item limit. If the product team requires a lower cap (e.g. 200 tasks), add `@field_validator("task_defs")` with `len(v) <= 200` to `CrmTemplateCreateIn`.

4. **Sequential vs. CPM date offset**: The instantiation uses simple sequential offsets (`offset_days[i] = sum of prior durations`) rather than Critical Path Method scheduling. This assumption holds when task order == execution order and all tasks are sequential. For parallel or overlapping tasks the resulting dates will be over-estimated. This is documented and acceptable for the initial implementation; critical-path scheduling is a future enhancement.

5. **PRJ-004 date-conflict bypass during instantiation**: `instantiate_from_template` passes `skip_date_validation=True` to `create_task` to prevent mechanical date-offset mismatches from blocking instantiation. This assumes PRJ-003/PRJ-004 expose that optional parameter. If they do not, the alternative is to pass no `start_date` during `create_task` and let users set dates post-instantiation; this spec prefers the skip-validation approach to preserve the UX value of date pre-population.

6. **Audit table name**: `audit_event` writes to `T.alerts` (the shared audit sink). No separate template-specific audit table is warranted for this ticket.
