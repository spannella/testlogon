# LED-002 — Lead entity Pydantic models

**Type:** Feature  **Priority:** P0  **Estimate:** 1 day
**Ticket source:** `docs/suitecrm/CRM_LEADS_TICKETS.md`, section "LED-002"

---

## 1. Summary & Goal

LED-002 delivers all Pydantic request/response models for the Leads and Prospects domain. These models live in `app/models.py` and form the validated wire contract between the HTTP layer and the service layer defined in LED-003. No router, no service, no DynamoDB access, and no frontend code are introduced in this ticket — only model class definitions.

Specifically, this ticket adds:

- `LEAD_STATUSES` and `LEAD_SOURCES` — module-level sentinel sets used for `pattern=` regex validation and service-layer transition guards.
- `LeadCreateIn` — validated request body for creating a lead.
- `LeadUpdateIn` — partial-update body; all fields optional.
- `LeadOut` — full lead representation returned by all read and write endpoints.
- `ProspectCreateIn` and `ProspectOut` — lightweight external-email-only contact (no platform account required), used by LED-007.
- `LeadConversionIn` and `LeadConversionOut` — conversion request/response for LED-006 (lead-to-Party conversion).

With `LEADS_ENABLED=0` (the default established by LED-001) none of the models are reachable through any live endpoint; they are inert Python classes until LED-003 and LED-013 wire them into routers.

## 3. Data Model

LED-002 introduces no DynamoDB tables or GSIs. That work belongs entirely to LED-001 (already specced). This section documents the logical schema that the Pydantic models represent; the DynamoDB mapping is formalized in LED-003.

### 3.1 Lead status state machine

```
LEAD_STATUSES = {"new", "assigned", "in_process", "converted", "recycled", "dead"}
```

Valid transitions (enforced by the service layer in LED-003, not by Pydantic):

```
new       → assigned | in_process | recycled | dead
assigned  → in_process | recycled | dead
in_process→ converted | recycled | dead
recycled  → new | dead
converted → (terminal — no further transitions allowed)
dead      → (terminal)
```

`LeadCreateIn` always initializes status to `"new"` implicitly at the service layer. `LeadUpdateIn.status` accepts any value from `LEAD_STATUSES`; the service rejects invalid transitions, not the model.

### 3.2 Lead source enumeration

```
LEAD_SOURCES = {"web_site", "cold_call", "email", "campaign", "trade_show",
                "word_of_mouth", "other", "internal"}
```

Used as the `pattern=` allowlist on `LeadCreateIn.lead_source`. `"other"` is the default for unknown-origin leads.

## 4. API / Service Design

LED-002 introduces no endpoints and no service functions. All code in this ticket is Pydantic model class definitions in `app/models.py`.

### 4.1 Complete model class definitions

The following classes are inserted at the end of `app/models.py` under a clearly marked section comment.

**Section sentinel sets** (module-level, not classes):

```python
# ── CRM Leads (LED-002) ──────────────────────────────────────────────────────

LEAD_STATUSES: frozenset[str] = frozenset({
    "new", "assigned", "in_process", "converted", "recycled", "dead"
})

LEAD_SOURCES: frozenset[str] = frozenset({
    "web_site", "cold_call", "email", "campaign", "trade_show",
    "word_of_mouth", "other", "internal",
})

_LEAD_SOURCE_PATTERN = (
    r"^(web_site|cold_call|email|campaign|trade_show|word_of_mouth|other|internal)$"
)
```

Using `frozenset` (not `set`) makes the sentinels hashable and avoids accidental mutation by downstream code.

**`LeadCreateIn`** — validated create body:

```python
class LeadCreateIn(BaseModel):
    first_name: str = Field(..., min_length=1, max_length=120)
    last_name: str = Field(..., min_length=1, max_length=120)
    email: str = Field(..., min_length=3, max_length=254)
    phone: Optional[str] = None
    company: Optional[str] = Field(default=None, max_length=200)
    title: Optional[str] = Field(default=None, max_length=200)
    lead_source: str = Field(default="other", pattern=_LEAD_SOURCE_PATTERN)
    description: Optional[str] = Field(default=None, max_length=4000)
    assigned_to: Optional[str] = None
    website: Optional[str] = Field(default=None, max_length=500)
```

`email` carries only length validation here; format and normalization are applied at the service layer by `normalize_email` (same approach as `app/routers/contacts.py:93` which calls `normalize_email` inside the handler, not in the model). `phone` is unrestricted — it is normalized to E.164 by `normalize_phone` at the service layer (same approach as `app/services/profile.py:9`). `lead_source` uses a compiled regex pattern; an unknown value raises `ValidationError` with a clear message before the request reaches the service layer.

**`LeadUpdateIn`** — partial update body, all fields optional:

```python
class LeadUpdateIn(BaseModel):
    first_name: Optional[str] = Field(default=None, min_length=1, max_length=120)
    last_name: Optional[str] = Field(default=None, min_length=1, max_length=120)
    email: Optional[str] = Field(default=None, min_length=3, max_length=254)
    phone: Optional[str] = None
    company: Optional[str] = Field(default=None, max_length=200)
    title: Optional[str] = Field(default=None, max_length=200)
    lead_source: Optional[str] = Field(default=None, pattern=_LEAD_SOURCE_PATTERN)
    description: Optional[str] = Field(default=None, max_length=4000)
    assigned_to: Optional[str] = None
    status: Optional[str] = None  # transition enforced by service layer (LED-003)
    website: Optional[str] = Field(default=None, max_length=500)
    score: Optional[int] = None   # only written by scoring engine (LED-011)
```

`status` carries no `pattern=` constraint at the model layer. This is intentional: the service layer in LED-003 applies the full state-machine transition table, which requires knowing the *current* status before the new value is validated. Validating `status` solely against `LEAD_STATUSES` at the model layer would still allow illegal transitions. The service raises `HTTPException(422)` for invalid values and `HTTPException(409)` for illegal transitions.

## 5. Detailed Behavior & Edge Cases

### 5.1 `lead_source` validation

`LeadCreateIn.lead_source` and `LeadUpdateIn.lead_source` use a `pattern=` regex. Pydantic v2 raises `ValidationError` (which FastAPI translates to HTTP 422) when an unrecognized value is submitted. The pattern is anchored (`^...$`) and covers exactly the eight values in `LEAD_SOURCES`. Callers submitting `lead_source="linkedin"` receive a 422 Unprocessable Entity with a clear field-level error. This aligns with the validation behavior for `CampaignReviewIn.decision` (line 4924) and `AdsApiCampaignCreate.objective` (line 5017).

### 5.2 `status` on create vs. update

`LeadCreateIn` has **no** `status` field: the initial status `"new"` is assigned unconditionally by the LED-003 `create_lead` service function, not by the caller. This prevents a caller from creating a lead directly in `"converted"` state, which would bypass conversion logic. `LeadUpdateIn.status` is an unconstrained `Optional[str]`; the service applies both membership validation (`status not in LEAD_STATUSES → 422`) and transition-graph validation (`current_status → new_status not allowed → 409`).

### 5.3 Email length, not format

`email` fields on all models carry `min_length=3` and `max_length=254` (the RFC 5321 maximum). Format checking (the `@` presence check) is delegated to `normalize_email` at line 60 of `app/core/normalize.py`, which raises `HTTPException(400, "Invalid email")`. This is consistent with the pattern in `app/services/profile.py:9` where `normalize_email` is imported and used in handler code rather than Pydantic validators.

### 5.4 `phone` is an unconstrained optional string

`phone` accepts any string (or `None`). `normalize_phone` at line 66 of `app/core/normalize.py` enforces E.164 format (+digits, 10-digit US, or 11-digit 1NXXNXXXXXX). If `normalize_phone` raises `HTTPException(400)` the request is rejected before any DynamoDB write occurs. The model carries no `pattern=` constraint because phone formats vary widely internationally and a regex that rejects valid non-US numbers would be a source of bugs.

### 5.5 `score` in `LeadUpdateIn`

`score` is present on `LeadUpdateIn` only so that the scoring engine (LED-011) can call the same `update_lead` service path when writing a computed score. It is `Optional[int] = None` (no `ge/le` bounds). The router-layer endpoint for direct lead updates must not expose `score` to normal callers — the LED-013 router will strip `score` from the user-facing `PATCH /ui/leads/{lead_id}` request, passing it only when invoked internally by the scoring engine. This separation is enforced at the router layer, not the model layer, to keep the model simple and reusable.

### 5.6 `converted_party_id` / `converted_org_id` on `LeadOut`

These fields are `Optional[str] = None` on `LeadOut` and remain `None` until the LED-006 conversion endpoint sets them. Existing consumers of `LeadOut` (LED-013 list/get endpoints) serialize these as `null` in JSON, which is backward-compatible when they later become non-null after conversion. No model rebuild (like `ConversationOut.model_rebuild()` documented in CLAUDE.md for the last_message field) is needed — `Optional[str]` with a default already resolves forward references at class definition time.

### 5.7 `LeadConversionIn` field requirements

`create_account=True` without `account_name` is accepted by the model (both are independent fields). The service layer in LED-006 enforces: if `create_account=True` and `S.party_crm_enabled=False` (PTY module absent), then `account_name` must be non-empty to create the inline ORG stub. The model keeps this flexible to avoid premature coupling to the PTY availability check.

### 5.8 `opportunity_amount_cents` ge=0

`ge=0` ensures the amount cannot be negative. A zero-amount opportunity is valid (e.g., relationship tracking with no monetary value). The constraint is on the model rather than the service because it is purely a data-integrity rule that applies regardless of `S.party_crm_enabled` status.

### 5.9 `frozenset` vs `set` for sentinels

`LEAD_STATUSES` and `LEAD_SOURCES` are `frozenset` instances. This makes membership tests (`value in LEAD_STATUSES`) O(1) and prevents accidental mutation by downstream code. Using `frozenset` is consistent with the frozen dataclass pattern already used for `CANONICAL_ADMIN_SCOPES` in `app/auth/roles.py:26`.

## 6. Feature Flag & Config

### 6.1 Flag dependency

LED-002 models are not gated by any flag at the Python class definition level. Pydantic `BaseModel` subclasses are defined unconditionally at import time — gating class definitions on a runtime flag would break FastAPI's OpenAPI schema generation (which inspects models at startup). The flag `S.leads_enabled` is checked by the **router** in LED-013, not by the models themselves.

This is the established pattern: `LeadOut` is inert when `S.leads_enabled=False` because no endpoint returns it; defining it unconditionally has no side-effects on existing routes.

### 6.2 Env vars introduced

None. LED-002 introduces only Python class definitions. All environment variables for the Leads module were introduced by LED-001 (`LEADS_ENABLED`, `DDB_LEADS_TABLE`, sub-flags).

### 6.3 Default-OFF guarantee

With `LEADS_ENABLED=0` (the LED-001 default), no LED-002 model is reachable through any router. The classes exist in memory but are never instantiated by any live request path. Existing `app/models.py` consumers are byte-for-byte unchanged because the new section is appended at the end of the file.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

Pydantic models contain no environment-dependent branching. `LeadCreateIn.model_validate(data)` behaves identically in dev (DynamoDB Local, moto S3) and prod (AWS). No `dev_mode` conditional appears in any model class. This satisfies the SECOPS-007 "same code path dev/prod" constraint from `CRM_LEADS_TICKETS.md` line 13.

### 7.2 Idempotency

Model class definitions are idempotent: importing `app.models` multiple times (as pytest does across test files) produces the same class objects. No side effects occur at definition time.

### 7.3 PII handling

`email`, `first_name`, `last_name`, `phone`, and `company` fields on `LeadOut` and `ProspectOut` are PII. The models themselves do not enforce PII-handling policies (masking, redaction, export suppression) — those are enforced at the service and router layer. The presence of these fields on output models is deliberate: the leads module is a CRM, not a public feed. All lead endpoints (LED-013) require `require_ui_session` authentication, meaning PII is only returned to authenticated users who own the data.

### 7.4 No money-out paths

LED-002 introduces no billing, refund, or ledger logic. `opportunity_amount_cents` on `LeadConversionIn` is a metadata field (integer, ge=0) that the LED-006 service stores on the opportunity stub row; it does not trigger any payment or refund path. If a future Opportunity billing integration is added, it will reuse `refund_payment` / `settle_or_reverse_ledger` per the project constraint — no forking.

### 7.5 Input validation security posture

- `description` max 4000 characters prevents large-payload DoS via a single field.
- `email` max 254 characters enforces RFC 5321 limits before the string reaches `normalize_email`.
- `website` max 500 characters prevents URL-field overflow attacks.
- `lead_source` regex anchor (`^...$`) prevents partial-match injection (e.g., `"campaign\nX-Injected-Header: foo"` would be rejected).
- No HTML injection concern at the model layer: the service layer or frontend template is responsible for escaping on render.

## 8. Backward Compatibility & Migration

### 8.1 Additive-only file change

`app/models.py` is modified by appending a new section at the end. No existing class is modified, renamed, or removed. Python's import system means the new classes are available immediately after the file is saved; they shadow nothing.

### 8.2 No DynamoDB schema change

LED-002 introduces no tables, GSIs, or DynamoDB operations. No migration is required.

### 8.3 OpenAPI schema impact

FastAPI generates OpenAPI schemas lazily from route return types. Because LED-002 models are not yet attached to any route (that happens in LED-013), they do not appear in `GET /openapi.json` until LED-013 ships. No existing API consumers are affected.

### 8.4 Future model extensions

When LED-004 (lead source attribution) adds `attribution_code` and `campaign_id` fields, those are added to `LeadCreateIn` and `LeadOut` as `Optional[str] = None` — backward-compatible because existing callers that omit these fields receive `None` in the response. The same pattern applies to all downstream LED tickets that extend these models.

### 8.5 PTY-dependent fields on `LeadConversionOut`

`converted_party_id` and `converted_org_id` on `LeadConversionOut` are `Optional[str] = None`. When PTY is unavailable (LED-006 inline stub path), the service writes local `PERSON#` / `ORG#` stub IDs to these fields. When PTY ships, it writes real Party IDs. The field type is the same in both cases; no model change is needed when PTY is deployed.

## 10. Open Questions / Assumptions

1. **MKT-003 insert point**: The ticket specification says "after the existing campaign-family models (currently ending around line 4927)". However, `app/models.py` currently has no MKT-series contact list or segment models — those are planned upstream work. This spec inserts the LED-002 block at the end of the file (line 14,633+) rather than at line 4927, because inserting mid-file between existing ADS models and their downstream consumers creates unnecessary diff noise. When MKT-003 ships it can insert its block at its own chosen position. This is safe because Python module imports are not order-sensitive for class definitions.

2. **`score` field writability**: `score` is present on `LeadUpdateIn` so that the scoring engine (LED-011) can reuse the same `update_lead` code path. An alternative design would give the scoring engine a dedicated service function that writes score directly to DynamoDB without going through `LeadUpdateIn`. That approach is cleaner from a data-integrity perspective (preventing users from self-assigning scores via the API) but requires LED-011 to implement its own DDB write path. This spec follows the ticket specification's choice of including `score` on `LeadUpdateIn` and delegates access control to the router layer (LED-013). This assumption should be revisited when LED-011 is designed.

3. **`website` format validation**: `LeadCreateIn.website` accepts any string up to 500 characters with no URL format check. This is consistent with the `cta_url` validator in `CreativeCreateIn` (line 4949) which checks for `http://` or `https://` prefix via `@field_validator`. Adding a similar validator to `website` would be more defensive but would reject valid enterprise URLs (e.g., `ftp://` or bare hostnames). Assumption: no URL format validation on `website` unless the product team requests it.

4. **`ProspectUpdateIn` model**: The ticket specification mentions `ProspectUpdateIn` in LED-007's service signatures but does not include it in LED-002's explicit model list. This spec omits `ProspectUpdateIn` from LED-002 to match the ticket's acceptance criteria exactly. LED-007 can add it as part of its own model additions (which are explicitly permitted to be additive).

5. **`LEAD_STATUSES` and `LEAD_SOURCES` naming**: These are module-level names, not class attributes. They will be importable by service code via `from app.models import LEAD_STATUSES`. This is consistent with `_BID_CPM_MIN` and `_BID_CPM_MAX` at the top of `app/models.py` (private) and `CANONICAL_ADMIN_SCOPES` in `app/auth/roles.py:26` (public). Using `LEAD_SOURCES` as the set name (not `LEAD_SOURCE_VALUES`) follows the convention of `LEAD_STATUSES` from the ticket spec.
