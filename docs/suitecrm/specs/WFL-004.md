# WFL-004 — On-save trigger hook

**Type:** Feature | **Priority:** P1 | **Estimate:** 2d  
**Depends on:** WFL-001 (tables, flag, settings), WFL-002 (WorkflowRuleStore), WFL-003 (condition evaluator)  
**Unblocks:** WFL-005 (background scheduler), WFL-006 (action executor), WFL-009 (admin UI)

---

## 1. Summary & Goal

Introduce `app/services/workflow_hooks.py`, a fire-and-forget hook that fires after any successful record write and propagates matched `on_save` workflow rules into the existing unified scheduler as `crm_workflow` action items ready for immediate dispatch.

The hook is the bridge between the save paths of initial target modules (tickets, contacts) and the rule engine defined by WFL-002/003. Matched rules are not executed inline — they are enqueued as `crm_workflow` rows in `T.scheduled_actions` (PK `USER#system`, `scheduled_at=now_ts()`) so the unified scheduler (WFL-006) executes them asynchronously, preserving the fast write path and isolating rule execution failures from the originating HTTP request.

With `CRM_WORKFLOW_ENABLED=0` (the default), `fire_on_save_hook` is a no-op returning `0`. Every existing code path is unchanged byte-for-byte.

## 2. Context & Current State

**Feature flag (WFL-001):** `S.crm_workflow_enabled` maps to env `CRM_WORKFLOW_ENABLED` (default `"0"`). The pattern follows `unified_scheduler_enabled` at `app/core/settings.py:1933`:
```python
unified_scheduler_enabled: bool = os.environ.get("UNIFIED_SCHEDULER_ENABLED", "1") not in ("0", "false", "False")
```
WFL-001 adds the analogous bool field defaulting to `False`.

**Ticket save paths — two distinct surfaces:**

- `TicketStore.create_ticket` (`app/services/tickets.py:411`): writes a META row plus MSG and ACT sub-rows, returns the full ticket dict from `self.get_ticket(...)` at line 512. The returned dict includes `ticket_id`, `subject`, `owner_sub`, `status="open"`, `created_at`, `labels`, etc.

- `TicketStore._conditional_update_meta` (`app/services/tickets.py:723`): issues a conditional `update_item` with a version check (`expected_version → next_version`). Returns `bool` — `True` on success, `False` on `ConditionalCheckFailedException`. The hook must only fire when the return value is `True` (write succeeded).

**Contact save paths — two router-level functions in `app/routers/contacts.py`:**

- `add_contact` (`app/routers/contacts.py:84`): calls `T.contacts.put_item(Item=item)` at line 110, then returns `_item_to_contact(item)`. The item dict contains `owner_id`, `contact_id`, `display_name`, `is_favorite`, `is_blocked`, `added_at` (ISO string).

- `update_contact` (`app/routers/contacts.py:120`): calls `T.contacts.update_item(...)` with `ReturnValues="ALL_NEW"` at line 144–152, returns `_item_to_contact(resp["Attributes"])`. The returned `ContactEntry` Pydantic model has `owner_id`, `contact_id`, `display_name`, `is_favorite`, `is_blocked`, `added_at`.

**Unified scheduler / scheduled_actions table:**

- `create_action` (`app/services/scheduled_actions.py:91`) persists an action item with:
  - PK: `USER#{user_sub}`, SK: `ACTION#{scheduled_at}#{action_id}`, `GSI_DUE_PK="DUE"`, `GSI_DUE_SK=scheduled_at` (N)
  - Validates `scheduled_at > now + S.scheduled_actions_min_lead_time_seconds` (currently 300 s by default at `app/core/settings.py:1936`)
  - The `scheduled_at` validation means naively passing `now_ts()` will raise `ValueError`. WFL-004 must pass `now_ts() + S.scheduled_actions_min_lead_time_seconds + 1` as the scheduled time to satisfy the lead-time guard, making the action eligible for immediate pickup by the unified scheduler loop.

- `_EXECUTORS` dispatch table (`app/services/unified_scheduler.py:28–32`) currently maps `"post"`, `"file_share"`, `"catalog_sale"`. WFL-006 adds `"crm_workflow"` to this dict. WFL-004 only enqueues — it does not add to `_EXECUTORS`.

**Rule lookup — WFL-002 `WorkflowRuleStore`:** `list_rules_for_module(target_module)` queries the `ByModule` GSI on `T.crm_workflow_rules` (PK `MODULE#{target_module}`, numeric SK `created_at`) and returns only `enabled=True` rules. The hook filters the returned list to `trigger_type == "on_save"`.

**Condition evaluator — WFL-003:** `evaluate_conditions(conditions, record)` is a pure, stateless function with no DDB calls. Returns `(matched: bool, details: list[dict])`. Empty conditions list always returns `(True, [])`.

**Audit events:** `audit_event` (`app/services/alerts.py:644`) writes to `T.alerts` — same code path dev and prod (SECOPS-007). The hook emits one audit event per enqueued action.

**Job registry:** `register_task` / `report_poll` / `report_error` (`app/services/job_registry.py:23`) are in-memory only. The hook itself does not register a background task — it is synchronous and inline with the request.

## 3. Data Model

No new DynamoDB tables are introduced by WFL-004. The hook exclusively writes to two existing tables established by WFL-001 and SCHED-001.

### 3.1 `T.scheduled_actions` (SCHED-001, `scripts/local-ddb-init.py:1319`)

Rows produced by the hook use the existing schema:

| Attribute | Value |
|---|---|
| `pk` (S) | `USER#system` — system-partition so workflow actions do not pollute per-user lists |
| `sk` (S) | `ACTION#{scheduled_at}#{action_id}` |
| `action_id` (S) | `sa_` + uuid4 hex |
| `action_type` (S) | `"crm_workflow"` |
| `status` (S) | `"pending"` |
| `scheduled_at` (N) | `now_ts() + S.scheduled_actions_min_lead_time_seconds + 1` |
| `payload` (M) | `{"rule_id": str, "module": str, "record_id": str, "event": str}` |
| `GSI_DUE_PK` (S) | `"DUE"` |
| `GSI_DUE_SK` (N) | same as `scheduled_at` — makes row visible to `query_due_actions` |
| `GSI_TYPE_PK` (S) | `"USER#system#TYPE#crm_workflow"` — enables per-type querying |
| `GSI_TYPE_SK` (N) | same as `scheduled_at` |
| `ttl_epoch` (N) | `scheduled_at + S.scheduled_actions_ttl_days * 86400` |

No `scripts/local-ddb-init.py` change required — the table and its GSIs (`ByDue`, `ByType`) with `attr_types={"GSI_DUE_SK": "N", "GSI_TYPE_SK": "N"}` were created by SCHED-001 (`scripts/local-ddb-init.py:1319–1328`).

### 3.2 `T.crm_workflow_rules` (WFL-001)

Read-only from the hook via `list_rules_for_module`. No new keys or GSIs. The `ByModule` GSI (PK `GSI_MODULE_PK` S, SK `GSI_MODULE_SK` N = `created_at`) must have `attr_types={"GSI_MODULE_SK": "N"}` in the WFL-001 `TableDef` — this is pre-existing per the WFL-001 spec.

### 3.3 `T.crm_workflow_runs` (WFL-001)

Not written by WFL-004. The run-log row is produced by the action executor in WFL-006. WFL-004 only enqueues; the run outcome is not known at enqueue time.

## 4. API / Service Design

### 4.1 `app/services/workflow_hooks.py` — new file

```python
import logging
from typing import Any

from app.core.settings import S
from app.core.time import now_ts

logger = logging.getLogger(__name__)


def fire_on_save_hook(
    *,
    module: str,
    record: dict[str, Any],
    event: str,          # "create" | "update"
) -> int:
    """Evaluate and enqueue on_save workflow rules for a saved record.

    Must be called AFTER the write commits. Returns the count of rules
    matched and enqueued. Zero is returned immediately when the flag is off
    so the call site is always safe to call unconditionally.

    Never raises — all exceptions are caught and logged as warnings so a bug
    here cannot break the primary write path.
    """
```

Internal flow (see Section 5 for edge cases):

1. `if not S.crm_workflow_enabled: return 0`
2. Import lazily to avoid circular deps at module load time:
   ```python
   from app.services.workflow_rules import list_rules_for_module
   from app.services.workflow_condition_evaluator import evaluate_conditions
   from app.services.scheduled_actions import create_action
   from app.services.alerts import audit_event
   ```
3. `rules = list_rules_for_module(module)` — returns `list[dict]` of enabled rules for the module.
4. Filter: `on_save_rules = [r for r in rules if r.get("trigger_type") == "on_save" and event in (r.get("trigger_config") or {}).get("events", [])]`
5. Resolve `record_id`:
   - `module == "ticket"`: `record.get("ticket_id", "")`
   - `module == "contact"`: `record.get("contact_id", "")`
   - fallback: `record.get("id", record.get("record_id", ""))`
6. For each rule in `on_save_rules`:
   ```python
   matched, details = evaluate_conditions(rule.get("conditions", []), record)
   if not matched:
       continue
   scheduled_at = now_ts() + S.scheduled_actions_min_lead_time_seconds + 1
   create_action(
       user_sub="system",
       action_type="crm_workflow",
       scheduled_at=scheduled_at,
       payload={
           "rule_id": rule["rule_id"],
           "module": module,
           "record_id": record_id,
           "event": event,
       },
       title=f"WFL on_save: {rule.get('name', rule['rule_id'])}",
   )
   audit_event(
       "crm_workflow.on_save_enqueued",
       "system",
       rule_id=rule["rule_id"],
       module=module,
       record_id=record_id,
       event=event,
   )
   enqueued += 1
   ```
7. Return `enqueued`.

The entire body of `fire_on_save_hook` is wrapped in a top-level `try/except Exception` that logs `logger.warning("crm_workflow on_save hook error: %s", exc)` and returns `0` so any DDB error, import error, or logic bug is fully contained.

### 4.2 Wiring call sites

Each call site wraps in its own `try/except Exception: pass` (defence-in-depth; the hook already swallows internally, but the router/service layer must not be affected either way).

**`app/services/tickets.py:TicketStore.create_ticket`** — add after `return self.get_ticket(resolved_ticket_id) or {}` resolves the ticket dict but before the function returns. Specifically, capture the return value, fire the hook, then return:

```python
result = self.get_ticket(resolved_ticket_id) or {}
try:
    from app.services.workflow_hooks import fire_on_save_hook
    fire_on_save_hook(module="ticket", record=result, event="create")
except Exception:
    pass
return result
```

This is after line 512 (`return self.get_ticket(resolved_ticket_id) or {}`).

**`app/services/tickets.py:TicketStore._conditional_update_meta`** — add after the successful `update_item` call and before the function returns `True`. The method currently returns `True`/`False` (bool). The hook only fires on `True`:

```python
# after the update_item try block succeeds and sets `updated = True`
if updated:
    try:
        from app.services.workflow_hooks import fire_on_save_hook
        ticket = self.get_ticket(ticket_id)
        if ticket:
            fire_on_save_hook(module="ticket", record=ticket, event="update")
    except Exception:
        pass
return updated
```

The `get_ticket` re-read is necessary to build a full record dict; the conditional update only receives `values` kwargs, not the full record. The re-read is best-effort — if it fails, the hook is skipped silently.

**`app/routers/contacts.py:add_contact`** — add after `return _item_to_contact(item)` by capturing the result:

```python
contact_out = _item_to_contact(item)
try:
    from app.services.workflow_hooks import fire_on_save_hook
    fire_on_save_hook(module="contact", record=item, event="create")
except Exception:
    pass
return contact_out
```

The raw `item` dict (not the Pydantic model) is passed so the evaluator can access all raw attributes including `owner_id`.

**`app/routers/contacts.py:update_contact`** — add after `return _item_to_contact(resp["Attributes"])`:

```python
raw = resp["Attributes"]
contact_out = _item_to_contact(raw)
try:
    from app.services.workflow_hooks import fire_on_save_hook
    fire_on_save_hook(module="contact", record=raw, event="update")
except Exception:
    pass
return contact_out
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off path
`if not S.crm_workflow_enabled: return 0` — executed first, before any imports. No DDB calls, no imports of WFL-002/003 modules. The platform is byte-for-byte unchanged from the caller's perspective.

### 5.2 `scheduled_at` lead-time constraint
`create_action` at `app/services/scheduled_actions.py:103–105` raises `ValueError` if `scheduled_at <= now + S.scheduled_actions_min_lead_time_seconds` (default 300 s). For immediate on-save dispatch the hook must pass `now_ts() + S.scheduled_actions_min_lead_time_seconds + 1`. The unified scheduler loop polls on `S.unified_scheduler_poll_interval_seconds` (default 15 s), so the effective latency between hook firing and action execution is at most `max(301, poll_interval) ≈ 301 s` under default settings. If tighter latency is required in the future, `SCHEDULED_ACTIONS_MIN_LEAD_TIME_SECONDS` can be reduced — this is a config change only, not a code change.

### 5.3 `max_pending_per_user` limit for "system"
`create_action` checks `_count_pending(user_sub)` against `S.scheduled_actions_max_per_user` (default 100, `app/core/settings.py:1935`). Using `user_sub="system"` means all workflow actions share one "system" partition. In a scenario where many records are saved in a burst, this limit can be hit. Mitigation: the per-user limit should be raised for the system partition via a dedicated `CRM_WORKFLOW_SYSTEM_MAX_PENDING` setting in a follow-up (WFL-005 or WFL-009). For the initial release the hook catches `OverflowError` from `create_action` and logs it as a warning — the primary write is unaffected.

### 5.4 `_conditional_update_meta` return value
`_conditional_update_meta` returns `bool`. The hook reads this return value; if `False` (version conflict, write did not happen), the hook is not called. Callers that invoke `_conditional_update_meta` and ignore the return value today are unaffected.

### 5.5 Record dict shape for condition evaluation
The condition evaluator (WFL-003) operates on a flat dict using `str(record.get(field, ""))`. The shapes passed per module:

- **Ticket record** (from `get_ticket`): includes `ticket_id`, `subject`, `owner_sub`, `status`, `category`, `labels` (list), `created_at` (int), `updated_at` (int), `assigned_to_sub`, `space_id`. List-valued fields (`labels`) are coerced to string by WFL-003's `str()` cast — the `contains` operator will see `"['bug', 'urgent']"` for a labels list. Exact match on list fields requires the `eq` operator to compare the full string representation, which is unusual but acceptable for MVP; complex set-membership operators are a WFL-003 follow-up.

- **Contact record** (raw DDB item from `add_contact`/`update_contact`): includes `owner_id`, `contact_id`, `display_name`, `is_favorite` (bool), `is_blocked` (bool), `added_at` (ISO datetime string). Bool fields are coerced to `"True"`/`"False"` by WFL-003's `str()` cast; rules targeting `is_blocked` should use `operator=eq, value="True"`.

### 5.6 Rule changes between enqueue and execute
A rule may be disabled or deleted after `fire_on_save_hook` enqueues an action but before the unified scheduler executor picks it up. WFL-006 handles this: the executor re-reads the rule at execution time and exits silently if the rule is missing or `enabled=False`. The stale action item is marked `completed` with `actions_fired=[]`.

### 5.7 Duplicate evaluation risk
The on-save hook is fire-and-forget with no deduplication guard. If the caller retries a ticket update due to a version conflict and the second attempt succeeds, the hook fires once (only on `True` return from `_conditional_update_meta`). If caller code mistakenly calls `fire_on_save_hook` twice for the same write, two action rows will be enqueued and the rule will execute twice. The hook itself does not deduplicate. Callers must ensure the hook is called exactly once per successful write.

### 5.8 Thread-safety / async context
`fire_on_save_hook` is synchronous. It is called from both sync FastAPI endpoints (contacts router) and from `TicketStore` service methods (which may be called from async endpoints via `asyncio.to_thread` or directly). Because DynamoDB boto3 calls are synchronous and `create_action` is synchronous, no `await` is needed. If the hook is ever called from an async context, it can be wrapped in `asyncio.to_thread(fire_on_save_hook, ...)` at the call site.

### 5.9 Empty module list
`list_rules_for_module("ticket")` returns `[]` when no rules are defined or all rules are disabled. The for-loop body is never entered; `fire_on_save_hook` returns `0`. This is the expected initial steady-state when the flag is first enabled.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity
`fire_on_save_hook` contains no `if S.dev_mode` branches. All DynamoDB calls (`list_rules_for_module`, `create_action`, `audit_event`) operate against whichever endpoint `T` resolves to — `http://localhost:8001` in dev (moto-intercepted) or real AWS in prod. Same code path both envs.

### 7.2 Idempotency
The hook is not inherently idempotent: two calls with the same arguments produce two action rows. Idempotency is the caller's responsibility (call exactly once per successful write). The action executor (WFL-006) writes a run log per execution; if two actions fire from a duplicate hook call, both will be executed and both run logs written. This is acceptable for an MVP; a per-(rule_id, record_id, write-ts) deduplication key can be added to `T.crm_workflow_runs` in WFL-006.

### 7.3 Security
- The hook uses `user_sub="system"` for all `create_action` calls. This is a non-user-owned partition; `list_actions` filtered by `user_sub="system"` is only accessible to admin/root endpoints (WFL-009). Regular users cannot view or cancel system-owned workflow actions.
- The `payload` stored in `T.scheduled_actions` contains only `rule_id`, `module`, `record_id`, `event` — no PII from the record. PII is re-fetched at execution time by the executor from the source table.
- The hook does not modify the record; it only reads it (plus one DDB GSI query on `T.crm_workflow_rules` and one `put_item` on `T.scheduled_actions` per enqueued action).
- Condition evaluation is pure Python with no eval/exec; field values are compared via string/float cast only — no injection vector.

### 7.4 Audit trail
Each enqueued action emits `audit_event("crm_workflow.on_save_enqueued", "system", rule_id=..., module=..., record_id=..., event=...)` via `app/services/alerts.audit_event` (`app/services/alerts.py:644`). In dev this writes to `T.alerts` (DDB local); in prod same table on real DDB. No SES/SNS email or SMS is triggered by this audit event — it is record-only.

## 8. Backward Compatibility & Migration

### 8.1 No DynamoDB migration required
WFL-004 writes to `T.scheduled_actions` (SCHED-001, already exists) and reads from `T.crm_workflow_rules` (WFL-001). No schema changes to either table.

### 8.2 No modification to existing service files
The only modifications to existing files are additive call sites at the bottom of four functions:
- `TicketStore.create_ticket` (`app/services/tickets.py:411`) — one `try/except` block added before the final `return`.
- `TicketStore._conditional_update_meta` (`app/services/tickets.py:723`) — one `try/except` block added before `return updated`.
- `add_contact` (`app/routers/contacts.py:84`) — capture return value + one `try/except` block.
- `update_contact` (`app/routers/contacts.py:120`) — capture return value + one `try/except` block.

All four are wrapped in `try/except Exception: pass` so the additions are fully inert when the flag is off or when the hook module is not installed.

### 8.3 `just test` green requirement
Existing ticket and contact tests do not set `CRM_WORKFLOW_ENABLED=1` and do not seed `T.crm_workflow_rules`. With the flag off, `fire_on_save_hook` returns immediately — no extra DDB calls, no table references, no imports of WFL-002/003 modules. The `T.crm_workflow_rules` table handle added by WFL-001 is a `_safe_table` call (`app/core/tables.py:354`) which defers the actual table object creation; if the table does not exist in moto the `_safe_table` wrapper still initialises without raising (it raises only at first query time). Since the flag is off, no query is ever issued in existing tests.

### 8.4 Rollout sequencing
WFL-001 through WFL-003 must be deployed before WFL-004. WFL-004 can be deployed before WFL-005 (the background scheduler) and WFL-006 (the executor): with WFL-004 deployed but WFL-006 absent, action rows will accumulate in `T.scheduled_actions` with no executor to claim them. They will eventually TTL-expire (`ttl_epoch` set by `create_action`). Once WFL-006 is deployed and `CRM_WORKFLOW_ENABLED=1` is set, the executor begins processing any accumulated pending rows. This makes the rollout safe in a feature-branch deployment model.

## 10. Open Questions / Assumptions

1. **"system" partition cap**: `create_action` enforces `S.scheduled_actions_max_per_user` (default 100) per partition. Using `user_sub="system"` means all workflow actions globally share a 100-item cap. At medium scale (50 saves/s with 2 matching rules each) this cap is exhausted in 1 second. Assumption: WFL-001 adds a separate `S.crm_workflow_system_max_pending` setting (e.g. default 10 000) and WFL-004 bypasses the per-user guard for the system partition, or `create_action` is extended with a `skip_limit_check` flag. This needs resolution before WFL-004 ships.

2. **Contacts module record_id**: The contacts table (`app/core/tables.py:354`) uses PK `owner_id` and SK `contact_id`. The "record_id" concept for contacts is ambiguous — is it `contact_id` (the person being tracked) or `owner_id` (the user who owns the contact)? This spec assumes `contact_id` is the meaningful identifier for condition evaluation and rule targeting. Confirm with product.

3. **`_conditional_update_meta` re-read overhead**: Fetching the full ticket via `get_ticket(ticket_id)` after a successful conditional update adds one DDB query per update that triggers a matched rule. With `CRM_WORKFLOW_ENABLED=0` this overhead is zero. With the flag on and zero matching rules the overhead is one `ByModule` GSI query returning 0 items. With matching rules it is one GSI query plus one `get_item`. This is acceptable at current scale; if `create_ticket` and `update_ticket` are on the critical hot path, the `get_ticket` re-read can be replaced with constructing a minimal record dict from the `values` argument passed to `_conditional_update_meta`.

4. **Order module**: The ticket description names `"order"` as an initial supported module (`TARGET_MODULES = ["ticket", "contact", "order", ...]`), but WFL-004 does not wire a hook into any order save path. The hook infrastructure is module-agnostic; adding the order module only requires identifying the relevant service function in `app/routers/billing.py` or the cart/checkout service, and calling `fire_on_save_hook(module="order", ...)` there. This is deferred to a follow-up (possibly OFB or FIN tickets).

5. **Synchronous vs async wiring in tickets router**: `TicketStore.create_ticket` and `_conditional_update_meta` are synchronous methods called from async FastAPI handlers. The hook is synchronous, so calling it from a sync method is safe. If in the future the TicketStore is moved to async, the hook must be awaited or wrapped in `asyncio.to_thread`.
