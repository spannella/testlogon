# CAS-012 — Canned responses / reply templates for agents

**Type:** Feature | **Priority:** P2 | **Estimate:** 1 day
**Parent area:** CRM Cases, Customer Support & Customer Portal
**Ticket source:** `docs/suitecrm/CRM_CASES_PORTAL_TICKETS.md`, section "CAS-012"
**Depends on:** CAS-001 (master flag `crm_cases_enabled`, `crm_cases_templates` table, `T.crm_cases_templates` handle)

---

## 1. Summary & Goal

CAS-012 introduces a `TicketResponseTemplate` resource — a reusable pre-written reply (title, body, optional category) — that agents can select from a dropdown in the ticket reply UI instead of composing repetitive text from scratch. Admins manage the template library (create / update / delete); any authenticated user can read templates and filter by category.

> **DESIGN NOTE — visibility scope conflict:** The original ticket source (`docs/suitecrm/CRM_CASES_PORTAL_TICKETS.md:394`) specifies: `GET /tickets/response-templates` — returns "all templates (`admin`) or own templates (`user`)". This implies regular users see only templates they own (i.e. none, since only admins create templates). This spec adopts the simpler "all users see all templates" interpretation (Section 10.1) as more useful for the agent use-case. Implementers should be aware of the discrepancy and choose deliberately.

The feature is strictly additive. With `CRM_CASES_ENABLED=0` (the default) all new routes return 404, no DynamoDB reads or writes occur, and every byte of the existing `app/routers/tickets.py`, `app/services/tickets.py`, and `app/routers/ticket_boards.py` remains unchanged. When the flag is on, a new service module `app/services/ticket_templates.py` is added alongside a thin new router file `app/routers/ticket_templates.py` that is registered in `app/main.py`. `TicketOut` gains no new fields; this ticket touches only the template sub-resource.

## 3. Data Model

### 3.1 `crm_cases_templates` table (from CAS-001)

No new table is introduced. All template data lives in the `crm_cases_templates` table provisioned by CAS-001.

**Primary key:**

| Attribute | Type | Notes |
|---|---|---|
| `template_id` | String (PK) | e.g. `tmpl_<uuid4().hex[:12]>` |
| `sk` | String (SK) | Always the literal string `META` |

**GSI — `ByOwner`:**

| Attribute | Type | Notes |
|---|---|---|
| `owner_sub` | String (GSI PK) | `user_sub` of the admin who created the template |
| `created_at` | Number (GSI SK) | Unix integer timestamp; `attr_types={"created_at": "N"}` — declared by CAS-001 |

**Item attributes (full META row):**

| Attribute | Type | Required | Notes |
|---|---|---|---|
| `template_id` | String | Yes | PK; generated at create time |
| `sk` | String | Yes | Always `"META"` |
| `title` | String | Yes | Max 200 chars; agent-visible display name |
| `body` | String | Yes | Max 8 000 chars; the pre-written reply text |
| `category` | String | No | Optional free-text grouping label (e.g. `"billing"`, `"technical"`, `"general"`); `None` / absent when uncategorized |
| `owner_sub` | String | Yes | GSI PK; `user_sub` of the creating admin |
| `created_at` | Number | Yes | `now_ts()` at create time; GSI SK; declared as `"N"` in `scripts/local-ddb-init.py` via CAS-001 |
| `updated_at` | Number | Yes | `now_ts()` at last update |
| `is_shared` | Boolean | No | CAS-001 (`specs/CAS-001.md:167`) includes `is_shared (bool)` in the canonical item attribute list for this table. CAS-012 does not use this field (all templates are shared by definition per Section 1), but implementers must not write `is_shared=False` by default if it conflicts with a future admission of per-user private templates. Simplest safe choice: omit the attribute; a future CAS ticket can add it. |
| `deleted_at` | Number | No | Unix timestamp of soft-delete; absent on live items |

**Soft-delete convention:** Items are never hard-deleted from DynamoDB. `delete_template` sets `deleted_at = now_ts()`. All reads (`get_template`, `list_templates`) filter out items where `deleted_at` is present. This preserves audit history and avoids races with concurrent reads.

### 3.2 No schema change to `tickets` table

The tickets META row (`pk=TICKET#{id}`, `sk=META`) gains no new attributes. Templates are an independent resource; they are not embedded in or linked to individual tickets. The agent selects a template client-side and its body is inserted into the compose textarea before the reply is submitted — template use is captured only implicitly through the message body sent via `POST /tickets/{id}/messages`.

## 4. API / Service Design

### 4.1 Service: `app/services/ticket_templates.py` (new file)

```python
from __future__ import annotations

import uuid
from dataclasses import dataclass, field
from typing import Any

from app.core.tables import T
from app.core.time import now_ts


class TicketTemplateError(Exception):
    def __init__(self, detail: dict[str, Any]) -> None:
        super().__init__(str(detail.get("code", "template_error")))
        self.detail = detail


@dataclass
class TicketTemplateService:
    _table: Any = field(default_factory=lambda: T.crm_cases_templates)

    def create_template(
        self,
        *,
        owner_sub: str,
        title: str,
        body: str,
        category: str | None = None,
    ) -> dict[str, Any]:
        ...

    def get_template(self, template_id: str) -> dict[str, Any] | None:
        ...

    def update_template(
        self,
        *,
        template_id: str,
        title: str | None = None,
        body: str | None = None,
        category: str | None = None,
    ) -> dict[str, Any]:
        ...

    def delete_template(self, template_id: str) -> None:
        ...

    def list_templates(
        self,
        *,
        category: str | None = None,
        limit: int = 50,
        cursor: str | None = None,
    ) -> dict[str, Any]:
        ...


TEMPLATE_SERVICE = TicketTemplateService()
```

**`create_template` behavior:**
1. Generates `template_id = f"tmpl_{uuid.uuid4().hex[:12]}"`.
2. Writes a DDB item to `self._table` via `put_item` (no `ConditionExpression` needed — `template_id` collision probability is negligible at UUID4 hex).
3. Item: all fields above; `deleted_at` absent; `owner_sub = owner_sub`; `created_at = updated_at = now_ts()`.
4. Returns the item dict.

**`get_template` behavior:**
1. Calls `self._table.get_item(Key={"template_id": template_id, "sk": "META"})`.
2. Returns `item` if found and `deleted_at` not in item, else `None`.

**`update_template` behavior:**
1. `get_template(template_id)` — raises `TicketTemplateError({"code": "template_not_found"})` if `None`.
2. Builds `UpdateExpression` updating only the provided non-None fields plus `updated_at = now_ts()` via `update_item`. Uses `ExpressionAttributeNames` to avoid reserved-word conflicts on `body`.
3. `category` may be set to `None` by passing the sentinel value `""` (empty string) — the service treats `""` as "remove the category attribute" by adding it to the `REMOVE` clause of the `UpdateExpression`. Normal `None` means "do not touch category".
4. Returns `get_template(template_id)`.

**`delete_template` behavior:**
1. `get_template(template_id)` — raises `TicketTemplateError({"code": "template_not_found"})` if `None`.
2. Calls `self._table.update_item(Key=..., UpdateExpression="SET deleted_at = :ts", ...)` with `now_ts()`. Does not remove the GSI keys (they may stay; `list_templates` filters in application code).
3. Returns `None`.

**`list_templates` behavior:**
1. If `category` is provided: performs a `scan` on `self._table` with `FilterExpression="attribute_not_exists(deleted_at) AND #cat = :cat"` using `ExpressionAttributeNames={"#cat": "category"}`. Scans are acceptable here because the template corpus is small (typically < 500 items) and infrequently queried.
2. If `category` is `None`: performs a `scan` with `FilterExpression="attribute_not_exists(deleted_at)"`.
3. Pagination: passes `Limit=limit` and `ExclusiveStartKey=decode_cursor(cursor)` when cursor is provided. Returns `{"templates": [...], "next_cursor": encode_cursor(resp.get("LastEvaluatedKey"))}`.
4. Items are returned sorted by `created_at` descending in application code (slice from scan result).

> **Note on GSI vs scan:** The `ByOwner` GSI is designed for per-owner listing (used when a future "my templates" filter is added). The global `list_templates` (all templates, all owners) does not benefit from a GSI because there is no single GSI PK that covers all owners. A scan over a bounded, rarely-written table is the correct DynamoDB pattern here (same reasoning as `TicketStore.get_admin_summary` which scans all status counts).

from typing import Literal

class CreateTemplateReq(BaseModel):
    title: str = Field(..., min_length=1, max_length=200)
    body: str = Field(..., min_length=1, max_length=8000)
    category: str | None = Field(default=None, max_length=80)

class UpdateTemplateReq(BaseModel):
    title: str | None = Field(default=None, min_length=1, max_length=200)
    body: str | None = Field(default=None, min_length=1, max_length=8000)
    category: str | None = Field(default=None, max_length=80)

class TemplateOut(BaseModel):
    template_id: str
    title: str
    body: str
    category: str | None = None
    owner_sub: str
    created_at: int
    updated_at: int

class TemplateEnvelope(BaseModel):
    template: TemplateOut

class TemplateListEnvelope(BaseModel):
    templates: list[TemplateOut]
    next_cursor: str | None = None

## 5. Detailed Behavior & Edge Cases

### 5.1 Category filtering

The `category` query parameter is an exact-match string filter applied in the DynamoDB `scan` `FilterExpression`. Empty string `""` is treated the same as `null` (no category filter) — the parameter is normalized to `None` in the handler before being passed to the service. Case-sensitivity: categories are stored and matched exactly as provided (no normalization). Convention: lowercase, no spaces (e.g., `"billing"`, `"technical"`) is recommended but not enforced.

### 5.2 Category removal on update

`UpdateTemplateReq.category: str | None = None`. Because `None` is also the default (meaning "do not touch the field"), removing an existing category requires a distinct sentinel. The convention adopted here: pass `category=""` (empty string) to explicitly clear the category. The service detects `category == ""` and issues a `REMOVE category` clause in the `UpdateExpression`. This avoids adding a separate `remove_category: bool` field to the request model.

### 5.3 Soft-delete visibility

`list_templates` and `get_template` both filter out items with `deleted_at` present. A deleted template is invisible to all callers immediately after deletion. The item row remains in DynamoDB for audit purposes (accessible only through a direct DDB scan by an operator, never through the API). There is no `restore_template` endpoint in this spec; one could be added in a follow-up without a schema change.

### 5.4 Concurrent update safety

Templates are not subject to the same optimistic-locking requirement as ticket META rows (which use `_conditional_update_meta` with `version` at tickets.py:723) because templates are low-contention admin-managed objects. Two admins simultaneously updating different fields of the same template could produce a last-write-wins merge — this is acceptable. If stronger guarantees are needed, a `version` field and `ConditionExpression: version = :expected` can be added to `update_template` in a follow-up.

### 5.5 Body length and newlines

`body` allows up to 8 000 characters, which accommodates multi-paragraph responses with markdown or plain text. The backend stores the body as-is (no sanitization). The frontend renders the body as plain text inserted into the textarea (no markdown-to-HTML conversion at the selection step). If the ticket reply area later adopts rich text, the body stored in the template will be treated as the raw content.

### 5.6 No template-use tracking

CAS-012 does not record which templates were used in replies or how many times each was selected. Usage analytics are out of scope. A future `use_count` increment on selection could be added to `update_template` or a separate atomic `ADD` call without a schema change.

### 5.7 Flag-off behavior

When `S.crm_cases_enabled` is `False`:
- All five endpoints return `404 {"error": {"code": "not_found", "message": "not found"}}`.
- `TEMPLATE_SERVICE` is importable but its methods are never called.
- `T.crm_cases_templates` is wired at startup (table object created) but no queries run against it.
- `TicketOut` and `TicketListItemOut` are byte-for-byte unchanged.
- No `audit_event` calls for template events are emitted.

### 5.8 `audit_event` call sites

Four audit event names are introduced: `ticket_template_created`, `ticket_template_updated`, `ticket_template_deleted`, and (read-only, no mutation) no event for `GET` calls.

**`ALERT_EVENT_TYPES` (alerts.py:134–148):** This list is only used by `write_alert_preferences` to validate which event types users can subscribe to (see alerts.py:334 — `allowed = set(ALERT_EVENT_TYPES)`). Since template-CRUD events are admin-internal audit rows that no user subscribes to, these event names do NOT need to be added to `ALERT_EVENT_TYPES`. Adding them would erroneously expose them as subscribable notification events.

**`_NO_ALERT_EVENTS` (alerts.py:117–132):** `audit_event` calls `write_alert` (and `send_push_for_alert`) only when `event not in _NO_ALERT_EVENTS` (alerts.py:710). Since `ticket_template_*` events are NOT in this set, `write_alert` will be called — which is the correct behavior (audit rows should be persisted to `T.alerts`). Adding them to `_NO_ALERT_EVENTS` would suppress the audit row, which is undesirable.

**Email fan-out:** `render_ticket_email_template` (alerts.py:235) guards itself with `if alert_type not in {"ticket_created", "ticket_assigned", "ticket_replied", "ticket_status_changed", "ticket_reopened"}: return None` (alerts.py:236). Template-CRUD event names will not match this guard and will receive `None` — no email is sent. No change to `render_ticket_email_template` is needed.

**Summary:** No changes to `ALERT_EVENT_TYPES`, `_NO_ALERT_EVENTS`, or `render_ticket_email_template` are required. The new event names just work as-is with `audit_event`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/Prod parity

`TicketTemplateService` uses `T.crm_cases_templates` exclusively. There is no `S.dev_mode` branch anywhere in the service or router. In dev, `T.crm_cases_templates` resolves to a DynamoDB Local table (port 8001) seeded by `scripts/local-ddb-init.py` via CAS-001. In prod it resolves to a real DynamoDB table. The `scan` calls, `put_item`, `update_item`, and `get_item` operations are byte-for-byte identical in both environments (SECOPS-007). No mock path, no `if S.dev_mode:` branch.

### 7.2 Idempotency

- **Create:** `create_template` always generates a new `template_id` (UUID4 hex). Two identical `POST` requests produce two separate template rows. This is the correct behavior (admins intending two templates with identical content should get two items). Callers must not retry on success.
- **Update:** `update_template` is idempotent by content — calling it twice with the same field values produces the same stored state (modulo `updated_at` advancing). The `updated_at` timestamp change on each call is safe.
- **Delete:** `delete_template` called twice sets `deleted_at` twice (the second call finds the item already soft-deleted via `get_template` returning `None` and raises `template_not_found`, returning 404). Callers that treat 404 on delete as success achieve effective idempotency.
- **List/Get:** Pure reads; naturally idempotent.

### 7.3 Access control

- **Read** (`GET /tickets/response-templates`, `GET /tickets/response-templates/{id}`): any authenticated user with a valid `ui_session` or Bearer token. Templates are shared platform content; there is no per-user visibility restriction. This follows the principle of least friction — agents need to read templates without having admin privileges.
- **Write** (`POST`, `PUT`, `DELETE`): admin or root only (`user.role in {Role.ADMIN, Role.ROOT}`). This uses the same role check as `set_ticket_status` (router:992) and the escalation endpoint (CAS-009). Scoped admins (AdminProfileType.SCOPED) are treated as full admins for this resource; no fine-grained scope filter is applied (consistent with all other ticket admin operations).

### 7.4 No PII in template rows

Template rows contain only `template_id`, `title`, `body` (pre-written text), `category`, `owner_sub` (a user sub), `created_at`, `updated_at`, and optionally `deleted_at`. No end-user email address, no payment data, no personal information. Audit log entries carry the same minimal fields.

### 7.5 No money movement

CAS-012 performs no billing, refund, or ledger operation. The billing refund path reuse constraint (CLAUDE.md cross-cutting rules) is not applicable.

### 7.6 Injection safety

Template `body` is stored as a plain string and served as JSON. It is never executed or rendered as HTML server-side. Frontend rendering must use `value={template.body}` into a textarea (not `dangerouslySetInnerHTML`) — plain text insertion. XSS risk is at the frontend, not the backend.

## 8. Backward Compatibility & Migration

### 8.1 No change to `TicketOut` or existing routes

`TicketOut` (router:58–73) and `TicketListItemOut` (router:91–110) gain no new fields. Existing callers receive exactly the same response shape as before. The existing `app/routers/tickets.py` and `app/services/tickets.py` are not modified.

### 8.2 No migration required

The `crm_cases_templates` table is created empty by CAS-001's `scripts/local-ddb-init.py` entry. No backfill is needed; templates are authored by admins post-deployment. In production, the table must be created (via `CreateTable`) before the flag is enabled, but it starts empty — there is no pre-existing data to migrate.

### 8.3 Additive router registration

`ticket_templates_router` is registered in `app/main.py` only when `S.crm_cases_enabled` is truthy. On flag-off deployments (the default), `app.include_router(ticket_templates_router)` is never called, so the five routes do not appear in the OpenAPI spec, in route logs, or in the path table. Enabling the flag requires only an environment variable change and a service restart — no code change is needed in production once the feature is shipped.

### 8.4 Frontend graceful degradation

The template dropdown in `TicketsPage.tsx` uses `useQuery` with a query key `["ticket-templates"]`. If the backend returns `404` (flag off) or the array is empty, the dropdown renders as hidden or disabled. No error state is shown to the user; the absence of the dropdown does not impair the existing reply flow.

## 10. Open Questions / Assumptions

1. **Template visibility scope** — This spec makes all templates visible to all authenticated users (shared platform library). An alternative design would restrict `list_templates` to admin users only, with agents seeing only a "use template" surface that doesn't expose the raw body until selected. Assumption: shared visibility is simpler and sufficient for the P2 priority of this ticket.

2. **`owner_sub` immutability** — `update_template` does not allow changing `owner_sub`. Ownership transfer is out of scope. If an admin account is deactivated, their templates remain accessible (soft-delete must be done manually by another admin).

3. **Body character limit** — 8 000 chars is an assumption based on typical support reply lengths. If long-form KB-style templates are needed (CAS-015 knowledge base articles can be much larger), the limit can be raised to 20 000 chars in a follow-up by adjusting the Pydantic validator constant — no DynamoDB schema change is required (DynamoDB strings have no 8 000-char limit).

4. **Assumption: CAS-001 is merged** — `T.crm_cases_templates`, `S.crm_cases_templates_table`, and `S.crm_cases_enabled` must already be present in the codebase. CAS-012 cannot be implemented without CAS-001.

5. **Markdown in template body** — No decision is made here about whether template bodies are plain text or markdown. The backend stores and returns them verbatim. Frontend rendering conventions for the reply textarea are a UX decision; the data model supports either.

6. **Category enumeration** — Categories are free-text strings, not an admin-managed enum. This avoids needing a separate category management endpoint. A future `GET /tickets/response-templates/categories` endpoint could derive distinct category values from a scan.
