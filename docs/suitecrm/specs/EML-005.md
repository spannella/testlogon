# EML-005 — In-app email client UI (inbox, thread view, compose/reply/forward)

---

## 1. Summary & Goal

EML-005 delivers the **full in-app email client frontend** — the user-facing shell that makes the backend APIs from EML-003 (credential storage) and EML-004 (IMAP sync and threading) usable. The new route `/email` presents a three-panel layout: account/folder sidebar, message-list panel, and a combined thread-view / compose panel. Users can read synced emails in threaded form, reply, forward, and compose new messages — all without leaving the platform.

The implementation is **additive and gated default-off** via `S.email_client_enabled` (`EMAIL_CLIENT_ENABLED=0`). With the flag off the entire `/email` route tree and its backend status endpoint are inaccessible; every other surface — `send_alert_email`, `T.email_delivery`, `app/routers/admin_email.py` — is byte-for-byte unchanged. The flag is propagated to the frontend via a new public `GET /ui/email/status` endpoint so the React bundle can conditionally render the feature without a separate Vite env flag.

## 3. Data Model

EML-005 introduces **one new DynamoDB table** (`email_drafts`) and **one new status endpoint** with no table. All heavy storage (accounts, synced messages) lives in the EML-003 / EML-004 tables.

### 3.1 New table: `email_drafts`

Stores compose-pane drafts (auto-saved or explicitly saved). Drafts are ephemeral (30-day TTL) and are never synced to IMAP Drafts folder in this ticket (IMAP Drafts push is a follow-up).

```
PK:  USER#{user_sub}
SK:  DRAFT#{draft_id}          (uuid4().hex, e.g. "DRAFT#a3f1b2...")
draft_id:        str
account_id:      str           which user_email_accounts entry to send from
reply_to_uid:    Optional[int] IMAP UID being replied to (if reply/forward)
thread_id:       Optional[str] copied from parent message thread_id
subject:         str           max 998 chars (RFC 5322)
to_addrs:        list[str]     list of email addresses
cc_addrs:        list[str]
body_html:       str           HTML body (max 64 KB; larger stored to S3)
body_text:       str           plain-text body (max 16 KB)
draft_type:      str           "new" | "reply" | "forward"
created_at:      N             now_ts()
updated_at:      N             now_ts() on every auto-save
ttl_epoch:       N             created_at + 30 * 86400
```

**GSI `ByUser`** — PK=`USER#{user_sub}`, SK=`updated_at N`; enables listing all drafts for a user newest-first.
Declare in `scripts/local-ddb-init.py`:
```python
attr_types={"updated_at": "N"}
```

No other GSIs are needed. `list_drafts` queries this GSI; `get_draft` / `save_draft` / `delete_draft` use the primary key.

### 3.2 Status endpoint (no table)

`GET /ui/email/status` reads `S.email_client_enabled` from the settings singleton and returns `{"enabled": bool}`. No DynamoDB access; no auth required (allows the frontend to check before rendering the nav entry).

### 3.3 Existing tables used (read-only by EML-005 backend additions)

| Table handle | Used for |
|---|---|
| `T.user_email_accounts` (EML-003) | Account selector in `EmailAccountSettings` |
| `T.user_email_messages` (EML-004) | Message list + thread view |

### 4.1 New backend service: `app/services/email_drafts.py`

```python
def save_draft(
```

- `ttl_epoch = created_at + 30 * 86400`.

Prefix `/ui/email/drafts`, tag `email-client`. All endpoints require `Depends(get_authenticated_user)` (cookie or Bearer auth). The router is gated: every handler raises `HTTPException(503, "email client not enabled")` when `not S.email_client_enabled`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Three-panel layout (EmailPage.tsx)

The page is composed of three resizable panes using CSS flexbox (the project has no `ResizablePanelGroup` shadcn component — confirmed by absence from `frontend/src/components/ui/`). The layout uses `flex` with user-adjustable widths stored in `localStorage` under the key `email_panel_widths`.

**Left sidebar** (`FolderTree.tsx`):
- Renders account selector (shadcn `Select`) populated from `GET /ui/email/accounts`.
- Below the selector: folder list — `INBOX`, `Sent`, `Drafts`, `Trash`, plus any folders returned by the sync metadata. Unread count badge (derived from messages with `\Seen` flag absent) is computed client-side from the React Query cache.
- "Add account" link navigates to `EmailAccountSettings.tsx`.
- A "Sync" icon button (`RefreshCw` from lucide-react) triggers `POST /ui/email/accounts/{id}/sync` via a `useMutation`; on success it invalidates `["email", "messages", accountId, folder]`.

**Message list** (`MessageList.tsx`):
- Uses `useInfiniteQuery` (same pattern as `ConversationView.tsx:1594`) with query key `["email", "messages", accountId, folder, limit]`.
- Each row: `EmailMessageRow` — subject (bold if unread), from address, snippet, date formatted via `date-fns`, thread-count badge when `thread_id` groups more than one message.
- Clicking a row sets `selectedThreadId` state; the compose panel switches to thread-view mode.
- Virtualization: the list renders only visible rows using a CSS `overflow-y: auto` scroll container with `@radix-ui/react-scroll-area` (already in `package.json`). Full virtual-scroll library is not needed for typical email counts.

**Thread view** (`ThreadView.tsx`):
- Fetches `GET /ui/email/accounts/{id}/threads/{thread_id}` via `useQuery`.
- Renders messages in ascending `date_ts` order; each is a collapsible card — by default the newest message is expanded.
- HTML body is rendered inside a sandboxed `<iframe srcdoc="..." sandbox="allow-popups">` to isolate CSS and prevent script execution. The `sandbox` attribute blocks `allow-scripts` and `allow-same-origin`. The `srcdoc` value is the `body_html` string from the API; no client-side DOMPurify dependency is added (sandbox isolation is sufficient and avoids adding a new npm package).
- Attachments (when `has_attachments=true`) show a placeholder badge; full attachment download is a follow-up (EML-004 scope).
- "Reply" button opens `ComposePanel` in reply mode; "Forward" opens it in forward mode.

**Compose panel** (`ComposePanel.tsx`):
- Rendered in the right pane replacing `ThreadView` when compose is active.
- Uses a plain `<textarea>` for HTML input in this ticket (no Tiptap rich-text editor — `@tiptap/react` is not in `package.json` and adding it is a follow-up). The textarea accepts raw HTML or plain text; the backend receives it as `body_html`.
- Fields: `to` (comma-separated email addresses — plain `<input>` or shadcn `Input` component; `@radix-ui/react-input` does not exist in this project's `package.json`), `cc` (optional), `subject`, body.
- **New compose** — all fields blank except `subject` pre-filled to empty string.
- **Reply** — `to` pre-filled from the replied-to message `from_addr`; `subject` pre-filled as `Re: {original_subject}` (stripping existing `Re:` prefixes); body blank with a quoted section `\n\n--- Original message ---\n{snippet}`. The `reply_to_uid` is passed to the send endpoint.
- **Forward** — `to` empty; `subject` pre-filled as `Fwd: {original_subject}`; body contains quoted original.
- **Auto-save** — a `useEffect` debounces 2 s after each keystroke and calls `PUT /ui/email/drafts/{draft_id}` (creating on first save). On unmount the final state is flushed synchronously.
- **Send** — calls `POST /ui/email/accounts/{id}/messages/send` (EML-004). On success: deletes the draft via `DELETE /ui/email/drafts/{draft_id}`, closes the compose panel, invalidates `["email", "messages", accountId, "Sent"]`.

### 5.2 Empty state (EmailAccountSetup.tsx)

When `GET /ui/email/accounts` returns an empty list, `EmailPage` renders `EmailAccountSetup` instead of the three-panel layout. The component shows a `Mail` icon (lucide-react), a heading "Connect your email", and a button that navigates to `/email/settings`.

### 5.3 Feature-unavailable notice

When `GET /ui/email/status` returns `{enabled: false}` (polled once on mount via `useQuery`), `EmailPage` renders a centered card: "Email client is not available" with a sub-line "Contact your administrator." The page is still reachable at `/email` — the route is always in the router — but shows this notice. This avoids a hard 404 that would break bookmarks.

### 5.4 Account settings page (EmailAccountSettings.tsx)

Reachable at `/email/settings`. CRUD for IMAP/SMTP accounts using the EML-003 API. Shows each account as a card: label, IMAP host/port, status badge (`active` green, `error` red, `unverified` amber). "Verify" button triggers `POST /ui/email/accounts/{id}/verify` and refreshes the status.

### 5.5 Pagination edge cases

- `MessageList` uses `getNextPageParam: (page) => page.next_cursor ?? undefined` (same pattern as `ConversationView.tsx:1598`). Fetching stops when `next_cursor` is null.
- Switching folder or account resets the infinite query (`queryKey` includes both); stale data is not shown.
- If IMAP sync has never been run, the message list is empty and a "Sync inbox" CTA is shown.

### 5.6 Large HTML bodies

When `GET /ui/email/accounts/{id}/messages/{uid}` returns `body_html_url` (presigned S3 URL) instead of inline `body_html` (body exceeded 64 KB), `ThreadView` fetches the URL via a plain `fetch()` call and injects the result into the `<iframe srcdoc>`. The presigned URL is short-lived (300 s per EML-004 spec); on 403/expired the iframe shows an error message and a "Reload" button that re-fetches the message metadata.

### 5.7 Draft body exceeding 64 KB

`save_draft` in the backend stores the body to S3 at `email-drafts/{user_sub}/{draft_id}.html` and sets `body_html = ""` in DDB with `body_html_s3_key` set to the S3 key. `DraftOut.body_html_url` is a 300 s presigned URL generated at read time. `ComposePanel` checks for `body_html_url` on load and fetches inline content before rendering.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

The service layer has no `if S.dev_mode` branches. `save_draft` always writes to DynamoDB (moto in dev, real DDB in prod). S3 calls for large bodies go through `app.core.aws_clients.s3_client`, which already resolves the endpoint correctly in both environments (moto in-process in dev, real S3 in prod — same pattern used by `kyc_partner_api._store_document_bytes` and the newsfeed image upload). The `/status` endpoint reads `S.email_client_enabled` in both environments identically.

### Idempotency

- `save_draft` with an existing `draft_id` performs a `put_item` (full overwrite). Calling it twice with the same payload produces the same stored state. The auto-save debounce in the UI limits redundant calls.
- `delete_draft` uses `delete_item` unconditionally; a second call is a no-op (DDB returns success for a delete on a non-existent key).
- `GET /ui/email/status` is purely read-only and idempotent.

### Security

- **Auth**: All `/ui/email/drafts/*` endpoints require `get_authenticated_user` (cookie or Bearer). The `GET /ui/email/status` endpoint deliberately has no auth — it returns only a boolean and exposes no user data.
- **Ownership enforcement**: `get_draft` and `delete_draft` load by `PK=USER#{user_sub}` — a user can only access their own drafts. Cross-user access is structurally impossible via the PK access pattern.
- **HTML body isolation**: HTML email bodies are rendered in `<iframe sandbox="allow-popups">` — `allow-scripts` is excluded, blocking JavaScript execution. The `sandbox` attribute also prevents same-origin access to the parent document.
- **No credential exposure**: `DraftOut` never includes `password_ct_b64`; that field lives only in `T.user_email_accounts` (EML-003) and is explicitly excluded from all list/get responses there.
- **S3 draft isolation**: Draft S3 keys are namespaced by `user_sub` (`email-drafts/{user_sub}/{draft_id}.html`). Presigned URLs are scoped to the exact key and expire in 300 s.
- **CSRF**: Non-GET calls from cookie-auth sessions require the `x-csrf-token` header. `get_authenticated_user` (`app/auth/deps.py:199`) does **not** enforce CSRF — CSRF enforcement lives in `require_ui_session` (`app/services/sessions.py:427–436`) and `enforce_cookie_csrf` (`app/auth/policy.py:71`). The email_drafts router must add `Depends(enforce_cookie_csrf)` alongside `Depends(get_authenticated_user)` on non-GET handlers, or use `require_admin_or_root_csrf` (`app/auth/policy.py:100`) for write paths, to achieve CSRF protection for cookie-auth sessions.
- **Input length limits**: `DraftSaveIn.body_html` capped at 65 536 chars; `body_text` at 16 384 chars; `subject` at 998 chars (RFC 5322 limit). Violations return 422.

## 8. Backward Compatibility & Migration

### With flag off (default)

- All `/ui/email/drafts/*` endpoints return 503. The `/ui/email/status` endpoint returns `{"enabled": false}`.
- No DynamoDB table access occurs (the handlers short-circuit before any DDB call).
- The `email_drafts` DDB table is created by `scripts/local-ddb-init.py` on `just restart` regardless of the flag — table creation is not flag-gated (safe: an empty table costs nothing and avoids deployment ordering issues).
- The `email_drafts` handle is registered in `T` unconditionally; accessing a non-existent table returns empty results in moto. In prod the table must be created by infrastructure before deployment.
- The `/email` route in React is always present in the bundle; the `EmailPage` component checks `GET /ui/email/status` and renders the feature-unavailable notice if disabled.

### Migration for existing deployments

No existing data is modified. The `email_drafts` table is net-new. The `user_email_accounts` and `user_email_messages` tables are also net-new (EML-003 / EML-004). No DDB table migrations or backfills are needed.

### Rollback

Setting `EMAIL_CLIENT_ENABLED=0` and redeploying immediately hides all user-facing email surfaces. Drafts already stored in DDB are retained but inaccessible until the flag is re-enabled. The `email_drafts` table can be safely ignored or deleted without affecting any other platform feature.

## 10. Open Questions / Assumptions

1. **Tiptap rich-text editor** — the ticket spec references `@tiptap/react` for the compose body, but `@tiptap/react` is not in `frontend/package.json`. This spec uses a plain `<textarea>` for the body with the assumption that Tiptap is a follow-up feature. If Tiptap is required in scope, it must be added to `package.json` and the `ComposePanel` implementation updated.

2. **ResizablePanelGroup** — the ticket spec references this shadcn/ui component but it is not present in `frontend/src/components/ui/` (confirmed by directory listing). This spec uses CSS flexbox instead. If the shadcn resizable component is needed, it must be added to the project first.

3. **IMAP Drafts folder sync** — saving a draft locally in `email_drafts` does not push to the IMAP server's Drafts folder. This is a known limitation; a follow-up ticket should add `APPEND` to the IMAP Drafts mailbox via the EML-004 sync service.

4. **DOMPurify vs iframe sandbox** — the ticket spec mentions "sandboxed iframe or DOMPurify". This spec chooses `<iframe sandbox>` (no new npm dep). If content-security-policy requirements for the platform mandate DOMPurify over iframe, that can be swapped without affecting the API contract.

5. **Sent folder sync** — after `POST /messages/send` (EML-004), the sent message is delivered via SMTP but may not appear in the IMAP Sent folder until the next sync. The UI shows a "Sending…" state and then invalidates the Sent folder query; the message may not appear immediately.

6. **CSRF enforcement on `GET /ui/email/status`** — this endpoint is intentionally unauthenticated. If the platform's CSRF middleware (which applies only to non-GET cookie-auth requests) is later tightened to require auth on all public routes, the status endpoint should be explicitly exempted.

7. **`email_drafts_table_name` settings key** — assumed to be `"email_drafts"` by default. EML-003's spec already adds `email_client_enabled` to `Settings`; `email_drafts_table_name` is the only new settings key added by EML-005.
