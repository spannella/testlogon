# STU-009 — Admin global search configuration API

**Type:** Feature  **Priority:** P2  **Estimate:** 1 day  
**Ticket source:** `docs/suitecrm/CRM_SECURITY_STUDIO_TICKETS.md`, section "STU-009"  
**Feature flag:** `CRM_STUDIO_ENABLED` (env `CRM_STUDIO_ENABLED`, default `"0"`) — all routes under `/ui/admin/search-config/*` return 404 while the flag is off. The global search endpoint at `/ui/search` is entirely unaffected when the flag is off.

---

## 1. Summary & Goal

The global search aggregator at `app/routers/search.py` determines which domains participate in a fan-out search query using two mechanisms frozen at process start: a hard-coded base set (`ALLOWED_TYPES` at line 43) and a single boolean env-var `GLOBAL_SEARCH_EXTENDED_DOMAINS` (line 41). There is no way for an admin to disable a noisy or malfunctioning domain (e.g., a slow video scan) without a full process restart, and there is no per-domain relevance weight that downstream features (ranked results, CRM full-text search) can use.

STU-009 introduces:

1. **`app/services/search_config_service.py`** — a DynamoDB-backed config store with a 60-second in-memory TTL cache, modelled directly on the `billing_config` pattern (`app/services/billing_config.py:39–50`). Persists per-domain enabled/weight rows in the `search_config` table introduced by STU-001.
2. **`app/routers/admin_search_config.py`** — three admin endpoints (`GET /`, `PATCH /{domain_name}`, `POST /reset`) gated by `CRM_STUDIO_ENABLED` and the existing `require_admin_or_root` / `require_root` auth dependencies from `app/auth/policy.py`.
3. **A one-line integration** in `_search_aggregator` (search.py:645) that replaces the static `ALLOWED_TYPES` filter with the DDB-effective set returned by `get_effective_allowed_types()`.

The change is purely additive and default-OFF. With `CRM_STUDIO_ENABLED=0` the service module is importable but its cache path is never exercised and `_search_aggregator` continues using the module-level `ALLOWED_TYPES` set without any DynamoDB read.

## 2. Context & Current State

### 2.1 Hard-coded domain set in search.py

`app/routers/search.py:41–45` builds `ALLOWED_TYPES` exactly once at module import time:

```python
_EXTENDED_SEARCH = os.environ.get("GLOBAL_SEARCH_EXTENDED_DOMAINS", "true").lower() == "true"

ALLOWED_TYPES = {"users", "posts", "catalog", "files"}
if _EXTENDED_SEARCH:
    ALLOWED_TYPES |= {"messages", "tickets", "contacts", "videos", "calendar"}
```

The nine domain names are: `users`, `posts`, `catalog`, `files`, `messages`, `tickets`, `contacts`, `videos`, `calendar`. Once the process has started, the only way to change the active set is to modify the env-var and restart uvicorn.

### 2.2 The aggregator fan-out at search.py:645–693

`_search_aggregator` at `app/routers/search.py:645` accepts a `types: List[str]` parameter supplied by the caller (the `global_search` endpoint at line 824). The endpoint at line 856 validates the caller's requested types against the module-level `ALLOWED_TYPES`:

invalid = set(requested_types) - ALLOWED_TYPES
if invalid:

The `_search_aggregator` itself builds a `search_fns` dict from the `types` argument (lines 657–674) and fills in empty sections for all types in `ALLOWED_TYPES` not covered (line 689). There is no per-domain weight applied to the returned results; all domains are treated equally.

### 2.5 billing_config cache pattern (canonical model)

`app/services/billing_config.py:46–58` implements the in-memory cache with 60-second TTL that this ticket mirrors exactly:

- Module-level `_config_cache: Optional[Dict[str, Any]] = None` and `_cache_ts: int = 0`.
- `invalidate_cache()` sets both to `None`/`0`.
- Read path checks `(now_ts() - _cache_ts) < _cache_ttl()` before issuing a DDB `get_item`.

### 2.6 Audit event pattern

`app/services/alerts.audit_event` (alerts.py:644) is the canonical fire-and-forget audit hook used across the codebase. It writes to `T.alerts` and does not raise. The search config service calls it on every write. Note: `app/services/billing_config.update_billing_config` does NOT call `alerts.audit_event` — it records change history by writing its own DDB `AUDIT#{ts}#{event_id}` row in the same `billing_config` table (`billing_config.py:374–383`) plus a structured `logger.info("billing_config_updated", ...)` (`billing_config.py:386–395`). STU-009 follows the same dual approach (a `AUDIT#` DDB row in the `search_config` partition, per §4.1) AND additionally fires `alerts.audit_event` so the change flows into the ENTERPRISE-004 audit-export pipeline (the same approach taken by the STU-007 job-config service).

### 2.7 Auth dependencies

`app/auth/policy.py:67` defines `require_admin_or_root` (checks `Role.ADMIN` or `Role.ROOT`). `app/auth/policy.py:63` defines `require_root` (ROOT only). Both return `AuthenticatedUser`. The billing config router at `app/routers/billing_config.py:41–51` is the canonical example: reads use `require_admin_or_root`, destructive writes use `require_root`.

## 3. Data Model

### 3.1 Table: `search_config`

Introduced by STU-001. No changes to the schema are needed beyond what STU-001 defines.

| Attribute | Type | Notes |
|-----------|------|-------|
| `pk` | S | Always `"SEARCH_CONFIG"` for domain rows |
| `sk` | S | `"DOMAIN#{domain_name}"` for per-domain rows; `"AUDIT#{ts}#{event_id}"` for the change log |
| `domain_name` | S | One of the nine allowed domain names |
| `enabled` | BOOL | Whether this domain participates in fan-out |
| `weight` | N (Decimal) | Relevance multiplier 0.0–10.0, default 1.0 |
| `updated_by_sub` | S | Actor sub who last changed this row |
| `updated_at` | N (int) | Unix timestamp of last change |

There is no numeric GSI sort key on this table. The only query pattern is `pk = "SEARCH_CONFIG"` with an optional `sk begins_with "DOMAIN#"` condition (a table query, not a scan). Audit rows share the same partition and are queried with `sk begins_with "AUDIT#"`.

**Why single-partition design:** the config is written rarely (admin actions only) and read frequently (every search fan-out, cached). A single-partition with a 60-second TTL cache is identical to the `billing_config` pattern and has negligible DDB cost. There is no need for a GSI.

**`scripts/local-ddb-init.py` entry** (added by STU-001; reproduced here for completeness):

```python
TableDef(
    _resolve_table_name(S.search_config_table_name, "search_config"),
    "pk",
    "sk",
)
```

No `attr_types` entry is needed because neither `pk` nor `sk` is numeric, and there is no GSI with a numeric sort key on this table.

### 3.2 Allowed domain names

The canonical set matches `ALLOWED_TYPES` in `app/routers/search.py:43–45`:

```python
VALID_DOMAINS = frozenset({
    "users", "posts", "catalog", "files",
    "messages", "tickets", "contacts", "videos", "calendar",
})
```

This constant is defined in `app/services/search_config_service.py` and imported by both the service and the router. The router validates incoming `domain_name` path parameters against it before delegating to the service.

## 4. API / Service Design

### 4.1 Service: `app/services/search_config_service.py` (new file)

```python
VALID_DOMAINS: frozenset[str]         # The nine allowed domain names
_PK = "SEARCH_CONFIG"                 # DynamoDB partition key constant
_CACHE_TTL_SECONDS = 60               # Matches billing_config pattern

# Module-level cache (same pattern as billing_config.py:46–58)
_config_cache: Optional[dict] = None
_cache_ts: int = 0

def invalidate_cache() -> None: ...
    # Sets _config_cache = None, _cache_ts = 0

def get_all_domain_configs() -> dict[str, dict]:
    """Scan pk=SEARCH_CONFIG for sk begins_with DOMAIN# rows.
    Returns {domain_name: {enabled: bool, weight: float, updated_at: int | None,
                           updated_by_sub: str | None}}.
    For domains not present in DDB, falls back to env-var default
    (enabled if in ALLOWED_TYPES from search.py; weight=1.0).
    Uses _config_cache with 60s TTL. Never raises — returns env defaults on DDB error."""

def set_domain_config(
    actor_sub: str,
    domain_name: str,
    enabled: bool | None,
    weight: float | None,
) -> dict:
    """Upsert a per-domain config row. Validates domain_name in VALID_DOMAINS,
    weight in [0.0, 10.0]. Calls invalidate_cache() on success.
    Emits audit_event('search_config.updated', actor_sub, domain=domain_name,
                      enabled=..., weight=...).
    Returns the updated single-domain dict {enabled, weight, updated_at, updated_by_sub}.
    Raises ValueError for invalid domain or out-of-range weight."""

def reset_all_configs(actor_sub: str) -> None:
    """Delete all DOMAIN# rows from the search_config partition (i.e. remove all
    DDB overrides). Calls invalidate_cache(). Emits audit_event('search_config.reset',
    actor_sub). After this, get_all_domain_configs() falls back to env defaults."""

def get_effective_allowed_types() -> set[str]:
    """Return the set of domains that should be included in a search fan-out.
    Algorithm:
      1. Call get_all_domain_configs() to get per-domain state (cached, 60s TTL).
      2. For each domain in VALID_DOMAINS:
         - If a DDB row exists for it: include iff row.enabled == True.
         - If no DDB row: include iff domain is in the module-level ALLOWED_TYPES
           set from app/routers/search.py (i.e. respect the env-var default).
    Returns a subset of VALID_DOMAINS.
    Never raises — falls back to ALLOWED_TYPES on any error."""

def get_domain_weight(domain_name: str) -> float:
    """Return the admin-configured weight for a domain. Default 1.0 if not configured
    or if the domain is not in VALID_DOMAINS. Never raises."""
```

**Implementation notes:**

- `get_all_domain_configs` uses a `Query` with `KeyConditionExpression=Key("pk").eq(_PK) & Key("sk").begins_with("DOMAIN#")` and paginates via `LastEvaluatedKey` (nine rows maximum — pagination will never be needed in practice, but looping is defensive).
- `set_domain_config` uses `T.search_config.put_item` for the config row (full replacement is correct — there are no other attributes to preserve). It writes an audit row at `sk="AUDIT#{ts}#{event_id}"` in the same table, mirroring `billing_config.py:365–382`.
- `reset_all_configs` queries for all `DOMAIN#` rows and deletes them in a loop. It does NOT delete audit rows.
- The `weight` value is stored in DynamoDB as a `Decimal` (using `Decimal(str(round(weight, 4)))`) to avoid float precision issues, consistent with how `billing_config` stores numeric values.
- Import of `ALLOWED_TYPES` from `app.routers.search` is done lazily inside `get_effective_allowed_types` to avoid a circular import (`search.py` will import this service after integration).

### 4.2 Router: `app/routers/admin_search_config.py` (new file)

```
Prefix: /ui/admin/search-config
Tags:   ["admin-search-config"]
```

**Route ordering rule (per cross-cutting constraints):** static paths (`/`, `/reset`) are declared before any dynamic `/{domain_name}` path so the literal string `reset` is not captured as a domain name by FastAPI.

#### `GET /`

```python
@router.get("")
def list_search_config(
    admin: AuthenticatedUser = Depends(require_admin_or_root),
) -> SearchConfigListOut:
```

- Calls `svc.get_all_domain_configs()`.
- Returns `SearchConfigListOut` containing all nine domains with their effective enabled/weight values (DDB override or env default).
- Auth: ADMIN or ROOT.
- 404 returned before auth check when `S.crm_studio_enabled` is False (via a module-level guard function `_require_flag()`).

#### `PATCH /{domain_name}`

```python
@router.patch("/{domain_name}")
def update_domain_config(
    domain_name: str,
    body: SearchConfigUpdateIn,
    request: Request,
    admin: AuthenticatedUser = Depends(require_admin_or_root),
) -> SearchDomainConfigOut:
```

- Validates `domain_name` against `VALID_DOMAINS`; raises `HTTPException(404)` if unknown.
- Validates `body.weight` in `[0.0, 10.0]` if provided; raises `HTTPException(422)` if out of range.
- At least one of `body.enabled` or `body.weight` must be non-None; raises `HTTPException(400)` with `code="no_fields_provided"` otherwise.
- Calls `svc.set_domain_config(admin.sub, domain_name, body.enabled, body.weight)`.
- Returns the updated `SearchDomainConfigOut`.
- Auth: ADMIN or ROOT (consistent with billing-config PATCH, which also accepts ADMIN — search config writes are lower-risk than fee changes).

#### `POST /reset`

```python
@router.post("/reset")
def reset_search_config(
    request: Request,
    admin: AuthenticatedUser = Depends(require_root),
) -> ResetSearchConfigOut:
```

- Calls `svc.reset_all_configs(admin.sub)`.
- Returns `ResetSearchConfigOut(ok=True, message="All domain overrides cleared; env defaults apply.")`.
- Auth: ROOT only (destructive operation affecting all search queries platform-wide).

## 5. Detailed Behavior & Edge Cases

### 5.1 Domain not present in DDB — env default fallback

If an admin has never called `PATCH /{domain_name}` for a given domain, `get_all_domain_configs()` returns an entry derived from the env-var state: `enabled = (domain in ALLOWED_TYPES)` and `weight = 1.0`. This ensures the system behaves identically to the pre-STU-009 state when the flag is on but no config has been written.

### 5.2 Disabling a domain mid-request

Because `_search_aggregator` calls `get_effective_allowed_types()` on every invocation (after the cache check), disabling a domain takes effect within at most 60 seconds (one cache TTL) without a process restart. During the TTL window, in-flight requests that entered the aggregator before the cache invalidation will still fan out to the disabled domain — this is acceptable (the 60s window is deliberate and matches the billing-config precedent).

### 5.3 Cache invalidation on write

`set_domain_config` and `reset_all_configs` both call `invalidate_cache()` before returning. Subsequent calls to `get_all_domain_configs()` will re-read from DDB. Because the service is a module with module-level state, invalidation is process-local. In a multi-worker deployment (not applicable to dev per CLAUDE.md: "Run uvicorn with `--workers 1` in dev mode"), each worker maintains its own cache and convergence happens within one TTL.

### 5.4 Weight semantics — not yet applied to result scoring

`get_domain_weight` is introduced in this ticket as an accessor for future use. The `_search_aggregator` does not currently re-rank results by weight; it only uses `get_effective_allowed_types()` for inclusion/exclusion. The weight is persisted and exposed so that downstream features (e.g., a CRM full-text relevance ranker) can consume it without a schema migration. Applying weights to result ordering is explicitly out of scope for this ticket.

### 5.5 PATCH with no effective change

If an admin sends `PATCH /search-config/posts` with the same `enabled` and `weight` values as already stored in DDB, `set_domain_config` still performs the `put_item` (no optimistic diff like `billing_config.update_billing_config`) and still emits an audit event. This is consistent with simplicity; the admin UI should not call PATCH unnecessarily.

### 5.6 Unknown domain_name in PATCH

The router validates `domain_name` against `VALID_DOMAINS` before passing it to the service. An unknown domain (e.g., a typo) returns `HTTPException(404, detail={"code": "unknown_domain", "domain": domain_name})` without touching DDB.

### 5.7 POST /reset with no rows in DDB

If no domain configs have been written yet, `reset_all_configs` issues a query that returns zero items and deletes nothing. It still calls `invalidate_cache()` and emits an audit event. The response is `{"ok": true, "message": "..."}` with HTTP 200.

### 5.8 Feature flag enforcement

The `_require_flag()` guard at the top of every router handler checks `S.crm_studio_enabled` and raises `HTTPException(404)` if false. This must run before any auth check to avoid leaking the existence of the endpoint to unauthenticated callers. The guard is a plain function (not a `Depends`) called as the first statement in each handler body, consistent with the pattern used in STU-007.

### 5.9 DDB read error handling

`get_all_domain_configs()` wraps its DDB query in a try/except and, on any exception, logs the error and returns a dict of env defaults for all nine domains. This ensures that a DDB outage does not degrade search availability — the system falls back to the static ALLOWED_TYPES set, exactly as it behaved before STU-009. `set_domain_config` and `reset_all_configs` do not catch DDB errors (a write failure should surface as a 500 to the admin caller).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

There is no `dev_mode` branch anywhere in this ticket. The DDB read/write path via `T.search_config` works identically against DynamoDB Local (dev, using moto in tests) and against real DynamoDB (prod). No S3, KMS, SES, or Stripe interaction is needed. This is the simplest SECOPS-007 case: pure DynamoDB, same code path both ways.

### 7.2 Idempotency

- `set_domain_config` uses `put_item` (full replace), so calling it twice with the same values is safe and produces the same DDB state plus two audit rows (acceptable).
- `reset_all_configs` is idempotent: calling it when no rows exist is a no-op that returns success.

### 7.3 Authorization model

- **Read** (`GET /`): ADMIN or ROOT. Knowing which domains are enabled is administrative metadata, not user-sensitive.
- **Write** (`PATCH /{domain_name}`): ADMIN or ROOT. This is slightly more permissive than the billing-config PATCH (ROOT only), justified because disabling a search domain has no financial impact and can be reversed immediately.
- **Destructive reset** (`POST /reset`): ROOT only. Clearing all overrides simultaneously affects all users' search experience and cannot be undone except by re-applying each domain's config.

### 7.4 CSRF

All three endpoints require cookie-based auth to include the `x-csrf-token` header (enforced by `require_admin_or_root` which calls through `get_authenticated_user` → `require_ui_session` for cookie-auth paths). Bearer-token callers bypass CSRF per the existing platform convention.

### 7.5 Input validation / injection

- `domain_name` is validated against a `frozenset` of literal strings before any DDB operation. No concatenation into DDB keys with unvalidated input.
- `weight` is validated as a float in `[0.0, 10.0]` server-side. Pydantic alone is insufficient because the range constraint is domain-specific.
- Audit rows are written with `actor_sub` drawn from the authenticated session, not from the request body.

## 8. Backward Compatibility & Migration

### 8.1 Additive-only, no schema change to existing tables

The `search_config` table is new (introduced by STU-001). No existing table schema is modified. No existing row format is changed.

### 8.2 Zero-downtime deployment

With `CRM_STUDIO_ENABLED=0` (the default), the new code paths are unreachable. The feature can be deployed to production and left dormant. Enabling the flag via env-var change and process restart activates the routes and the aggregator integration atomically from the perspective of the running process.

### 8.3 No migration required on first enable

On first enable with an empty `search_config` table, `get_all_domain_configs()` returns env defaults for all domains (from `ALLOWED_TYPES`). The search experience is byte-for-byte identical to the pre-STU-009 state. Admins can then incrementally write domain configs.

### 8.4 Impact on existing `global_search` endpoint

The existing `GET /ui/search` endpoint (`app/routers/search.py:824`) is unmodified in its signature, request/response shape, rate limiting, or search history behaviour. The only change is the optional narrowing of the `types` list inside `_search_aggregator` when the flag is on. A caller passing `types=messages` when messages is admin-disabled will receive an empty section for messages (same shape as a domain returning no results), not a 400 error — the `invalid` check at search.py:856 still validates against the module-level `ALLOWED_TYPES`, and the aggregator silently drops disabled domains from its `search_fns` map.

## 10. Open Questions / Assumptions

1. **Weight application timing**: This ticket persists weights but does not use them in result scoring. A follow-up ticket (likely in the CRM reporting or full-text ranking work) should consume `get_domain_weight()`. No API contract changes will be needed — the field is already in the response model.

2. **Per-user weight override**: SuiteCRM supports per-user search module preferences. This ticket implements only global admin weights. Per-user overrides can be layered on top in a future ticket using the same `search_config` table with `pk="SEARCH_CONFIG#USER#{user_sub}"`.

3. **Indexing extended domains**: The current `messages`, `tickets`, `contacts`, and `calendar` search modules use in-line scan + filter operations (search.py:401–638). Disabling noisy domains via this API provides operational relief, but true latency reduction for large tables requires dedicated search indexes. That is a separate infrastructure concern.

4. **Assumption — STU-001 is merged first**: This spec assumes `T.search_config`, `S.crm_studio_enabled`, and `S.search_config_table_name` are all present in the codebase. All three are introduced by STU-001. This ticket has a hard dependency on STU-001.

5. **Assumption — `GLOBAL_SEARCH_EXTENDED_DOMAINS` env default remains `true`**: The existing env var continues to control the baseline `ALLOWED_TYPES` used when no DDB override is present. If the operator sets `GLOBAL_SEARCH_EXTENDED_DOMAINS=false`, then extended domains are off by env default even when `CRM_STUDIO_ENABLED=1` and no DDB rows have been written. Admins can re-enable individual domains via `PATCH` to override the env default.
