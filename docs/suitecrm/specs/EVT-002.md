# EVT-002 — CRM Event invitee list management (add/remove/import, invitation email)

**Type:** Feature | **Priority:** P1 | **Estimate:** 3d  
**Source:** `docs/suitecrm/CRM_MISC_TICKETS.md` (section "EVT-002")  
**Dependencies:** EVT-001 (feature flag, DynamoDB scaffolding, guard helper).

---

## 1. Summary & Goal

This ticket introduces invitee management for CRM Events. An event organiser can:

1. Add individual invitees by `user_sub`.
2. Remove an invitee, deleting their row from the `crm_events` table.
3. Bulk-import up to 500 `user_sub` strings in a single API call (idempotent: duplicate subs are skipped).
4. Dispatch invitation emails to all `pending` invitees via `send_alert_email`, advancing their status to `sent`.
5. List the current invitee roster with cursor-paginated results.

The feature is gated behind `S.crm_events_enabled` (introduced by EVT-001; default `False`). With the flag off every route returns HTTP 404 and the `crm_events` table is never written by this code path. All invitation email dispatch reuses `app/services/alerts.send_alert_email` (`app/services/alerts.py:459`) without forking.

## 3. Data Model

All EVT-002 data lives in the `crm_events` table introduced by EVT-001 (PK=`event_id` S, SK=`sk` S). No new tables are created.

### 3.1 META row — `SK = "META"`

Exactly one META row per event.

| Attribute | DDB Type | Required | Description |
|-----------|----------|----------|-------------|
| `event_id` | S (PK) | yes | `uuid.uuid4().hex`; generated at creation |
| `sk` | S (SK) | yes | Literal `"META"` |
| `owner_sub` | S | yes | `user_sub` of the creating user; written once; never updated |
| `name` | S | yes | Human-readable event name; 1–200 chars |
| `description` | S | no | Free-text description; max 5000 chars; defaults to `""` |
| `calendar_event_id` | S | no | Opaque FK to `T.calendar` (format `"{calendar_id}#{event_id}"` — see Open Questions §10.1); absent when not linked |
| `max_attendance` | N | no | Capacity limit used by EVT-004; absent means unlimited |
| `created_at` | N | yes | `now_ts()` (Unix seconds); GSI sort key for `ByOwner` and `ByCalendar` |
| `updated_at` | N | yes | `now_ts()` at last mutation |

`owner_sub` and `created_at` are written once and never mutated by any EVT-002 path. `ByOwner` GSI projects all attributes (`ProjectionType: ALL`).

### 3.2 INVITEE row — `SK = "INVITEE#{invitee_sub}"`

One row per invitee per event. The SK prefix makes it straightforward to query all invitees for a given `event_id` using `begins_with(sk, "INVITEE#")`.

| Attribute | DDB Type | Required | Description |
|-----------|----------|----------|-------------|
| `event_id` | S (PK) | yes | FK to the META row |
| `sk` | S (SK) | yes | `f"INVITEE#{invitee_sub}"` |
| `invitee_sub` | S | yes | Denormalised from SK for easy projection |
| `invite_status` | S | yes | One of `"pending"`, `"sent"`, `"accepted"`, `"declined"`, `"attended"` |
| `invited_at` | N | yes | `now_ts()` when the row was first written |
| `responded_at` | N | no | Set by EVT-003 when invitee accepts or declines |
| `display_name` | S | no | Snapshot of `get_profile_identity(invitee_sub)["display_name"]` at invitation time; nullable |

`invite_status` transitions managed by EVT-002:
- `add_invitee` → writes `"pending"`.
- `send_invitations` → transitions `"pending"` → `"sent"`.
- Transitions to `"accepted"` / `"declined"` / `"attended"` are owned by EVT-003.

No secondary index on the INVITEE rows is needed within EVT-002. Listing all invitees for an event is a `Query` on PK=`event_id` with `KeyConditionExpression: begins_with(sk, "INVITEE#")`.

### 3.3 Single-table co-existence

The `crm_events` table holds both `SK=META` and `SK=INVITEE#*` rows on the same PK (`event_id`). This is the established single-table pattern used throughout the platform (e.g., `T.tickets` with `SK=META`, `SK=MESSAGE#*`, `SK=MEMBER#*`). INVITEE rows do not carry `owner_sub` or `calendar_event_id`, so they are invisible to the `ByOwner` and `ByCalendar` GSIs (sparse projection).

### 3.4 No changes to `crm_event_registrations`

The `crm_event_registrations` table (EVT-001) is not written by EVT-002. Registration and RSVP state is owned by EVT-003.

```python
def create_crm_event(
    owner_sub: str,
    name: str,
    description: str = "",
    calendar_event_id: str | None = None,
    max_attendance: int | None = None,
) -> dict:

    item = {
        "event_id": event_id,

    if max_attendance is not None:

    T.crm_events.put_item(Item=item)
    audit_event("crm_event_created", owner_sub, event_id=event_id, name=name)
    return item
```

#### `add_invitee`

```python
def add_invitee(event_id: str, invitee_sub: str, actor_sub: str) -> dict:
    """
    Write an INVITEE row with invite_status="pending".

    Idempotent: if the row already exists the existing item is returned
    unchanged (conditional put with attribute_not_exists guard).
    Returns the (possibly pre-existing) invitee item.
    """
    sk = f"INVITEE#{invitee_sub}"
    now = now_ts()
    identity = _safe_get_identity(invitee_sub)
    item = {
        "event_id": event_id,
        "sk": sk,
        "invitee_sub": invitee_sub,
        "invite_status": "pending",
        "invited_at": now,
        "display_name": identity.get("display_name"),
    }
    try:
        T.crm_events.put_item(
            Item=item,
            ConditionExpression="attribute_not_exists(sk)",
        )
        audit_event("crm_invitee_added", actor_sub, event_id=event_id, invitee_sub=invitee_sub)
        return item
    except T.crm_events._t.meta.client.exceptions.ConditionalCheckFailedException:
        # Row already exists — return existing item unchanged.
        existing = T.crm_events.get_item(
            Key={"event_id": event_id, "sk": sk}
        ).get("Item", item)
        return existing
```

The `ConditionalCheckFailedException` is caught at the client level. `T.crm_events._t.meta.client.exceptions` is the standard boto3 path for resource-level exception classes. The conditional `attribute_not_exists(sk)` ensures each invitee is added exactly once per event.

#### `remove_invitee`

```python
def remove_invitee(event_id: str, invitee_sub: str, actor_sub: str) -> bool:
    """
    Delete the INVITEE row.

    Returns True when the row existed, False when it was absent
    (caller can decide whether to surface a 404).
    """
    sk = f"INVITEE#{invitee_sub}"
    existing = T.crm_events.get_item(
        Key={"event_id": event_id, "sk": sk}
    ).get("Item")
    if not existing:
        return False
    T.crm_events.delete_item(Key={"event_id": event_id, "sk": sk})
    audit_event("crm_invitee_removed", actor_sub, event_id=event_id, invitee_sub=invitee_sub)
    return True
```

#### `bulk_import_invitees`

```python
def bulk_import_invitees(
    event_id: str,
    user_subs: list[str],
    actor_sub: str,
) -> dict:
    """
    Add multiple invitees. Skips duplicates (idempotent per add_invitee).

    Returns {"added": N, "skipped": M} where skipped = subs already present.
    Limited to 500 subs per call (enforced in the Pydantic model).
    """
    added = 0
    skipped = 0
    seen: set[str] = set()
    for sub in user_subs:
        if sub in seen:
            skipped += 1
            continue
        seen.add(sub)
        result_item = add_invitee(event_id, sub, actor_sub)
        # add_invitee returns the existing item when already present.
        # Distinguish by checking invited_at vs now_ts() is brittle;
        # instead rely on the conditional put: if it raised, add_invitee
        # returned the pre-existing item. We track "was the row written
        # fresh?" by checking invite_status == "pending" and invited_at
        # is very recent (within 2 seconds). This is heuristic — for
        # correctness the counter is best-effort.
        # Simpler approach: count was_added flag returned from add_invitee.
        _ = result_item  # see revised signature below
        added += 1  # conservative: every non-duplicate counts as "added"
    audit_event(
        "crm_bulk_import_invitees",
        actor_sub,
        event_id=event_id,
        total=len(user_subs),
        unique=len(seen),
    )
    return {"added": added, "skipped": skipped}
```

Implementation note: `add_invitee` should return a `(item, was_new: bool)` tuple in the actual implementation to allow accurate `added`/`skipped` counting. The Pydantic response uses `added` + `skipped` as best-effort counters; no transactional correctness guarantee is needed.

#### `send_invitations`

```python
def send_invitations(event_id: str, event_meta: dict, actor_sub: str) -> dict:
    """
    Dispatch invitation emails to all INVITEE rows with invite_status=="pending".

    Transitions each pending invitee to "sent" after a successful email dispatch.
    Leaves status as "pending" on failure (caller may retry).
    Returns {"sent": N, "skipped": M, "failed": K}.
    """
    invitees = _query_all_invitees(event_id)
    sent = skipped = failed = 0

    for invitee in invitees:
        if invitee.get("invite_status") != "pending":
            skipped += 1
            continue

        invitee_sub = invitee["invitee_sub"]
        email = _resolve_email(invitee_sub)
        if not email:
            failed += 1
            continue

        subject, body = _build_invitation_email(event_meta, invitee_sub)
        try:
            send_alert_email([email], subject, body)
            # Advance status to "sent" only after successful dispatch.
            T.crm_events.update_item(
                Key={"event_id": event_id, "sk": f"INVITEE#{invitee_sub}"},
                UpdateExpression="SET invite_status = :s",
                ConditionExpression="invite_status = :p",
                ExpressionAttributeValues={":s": "sent", ":p": "pending"},
            )
            sent += 1
        except Exception:
            logger.warning(
                "crm_send_invitation_failed event_id=%s invitee_sub=%s",
                event_id, invitee_sub, exc_info=True,
            )
            failed += 1

    audit_event(
        "crm_invitations_sent",
        actor_sub,
        event_id=event_id,
        sent=sent,
        skipped=skipped,
        failed=failed,
    )
    return {"sent": sent, "skipped": skipped, "failed": failed}
```

`_build_invitation_email` constructs the subject and body text. Body includes the event name, description, the event organiser's display name, and (when present) the calendar event link (`/calendar?event={calendar_event_id}`). All plain text — no HTML; `send_alert_email` accepts `body_text` only (`app/services/alerts.py:459`).

#### `list_invitees`

```python
def list_invitees(
    event_id: str,
    limit: int = 50,
    cursor: str | None = None,
) -> dict:
    """
    Paginated list of INVITEE rows for an event.

    Returns {"invitees": [...], "cursor": str | None}.
    """
    from boto3.dynamodb.conditions import Key
    kwargs: dict = {
        "KeyConditionExpression": (
            Key("event_id").eq(event_id)
            & Key("sk").begins_with("INVITEE#")
        ),
        "Limit": min(limit, 200),
    }
    lek = decode_cursor(cursor)
    if lek:
        kwargs["ExclusiveStartKey"] = lek

    resp = T.crm_events.query(**kwargs)
    items = resp.get("Items", [])
    next_cursor = encode_cursor(resp.get("LastEvaluatedKey"))
    return {
        "invitees": [_invitee_out(i) for i in items],
        "cursor": next_cursor,
    }
```

`_invitee_out` converts a raw DDB item to the `CrmInviteeOut` shape, casting `invited_at` and `responded_at` from `Decimal` to `int`.

#### Private helpers

```python
def _safe_get_identity(user_sub: str) -> dict:
    """Best-effort profile identity lookup; returns {} on any error."""
    try:
        from app.services.profile import get_profile_identity
        return get_profile_identity(user_sub) or {}
    except Exception:
        return {}

def _resolve_email(user_sub: str) -> str | None:
    """Resolve the displayed_email for a user_sub. Returns None when absent."""
    return (_safe_get_identity(user_sub) or {}).get("email")

def _query_all_invitees(event_id: str) -> list[dict]:
    """Full scan of all INVITEE rows for an event (no Limit)."""
    from boto3.dynamodb.conditions import Key
    items: list[dict] = []
    kwargs: dict = {
        "KeyConditionExpression": (
            Key("event_id").eq(event_id)
            & Key("sk").begins_with("INVITEE#")
        ),
    }
    while True:
        resp = T.crm_events.query(**kwargs)
        items.extend(resp.get("Items", []))
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
    return items
```

`_query_all_invitees` paginates via `LastEvaluatedKey` per the CLAUDE.md DynamoDB gotcha: "DDB FilterExpression doesn't reduce page size — must loop via LastEvaluatedKey." A `begins_with` condition on SK does not use a `FilterExpression`, but the loop is included defensively for events with very large invitee counts.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off: all routes return 404

Every route handler calls `_require_crm_events_enabled()` as its first statement. When `S.crm_events_enabled is False`, every `POST`, `DELETE`, and `GET` under `/ui/crm/events/*` returns HTTP 404, making the entire surface invisible to unauthenticated probing.

### 5.2 Idempotent invitee addition

`add_invitee` uses a DynamoDB conditional `put_item` with `ConditionExpression="attribute_not_exists(sk)"`. If the INVITEE row already exists (because the caller duplicated the request or the bulk import overlapped), the condition fails and the existing item is returned unchanged. The invitee's status is not reset to `"pending"` if they had already advanced to `"sent"` or beyond.

### 5.3 Idempotent invitation dispatch

`send_invitations` queries only rows with `invite_status="pending"`. A subsequent call after a complete send will find all invitees in status `"sent"` and return `{"sent": 0, "skipped": N, "failed": 0}` without dispatching any email. The `update_item` in the send loop uses `ConditionExpression="invite_status = :p"` so a concurrent second call cannot double-send to the same invitee (the second `update_item` will fail silently after the first advances the status, and the email has already been sent by the first call — see §5.9 for the race-condition edge case).

### 5.4 Invitee without a registered email

When `_resolve_email(invitee_sub)` returns `None` (user has no `displayed_email`), the invitee is counted in `failed` and their `invite_status` is left at `"pending"`. This allows a retry once the user has set an email address. The caller's response includes `failed: N` so the organiser knows how many could not be reached.

### 5.5 Bulk import limits

`CrmInviteeBulkImportIn.user_subs` is a list with `max_length=500` (enforced at the Pydantic model level before the service is called). The service loop calls `add_invitee` in a simple Python loop — no DynamoDB batch write is used, because `add_invitee` relies on a conditional put for idempotency. For 500 subs this means up to 500 individual `put_item` calls. In DynamoDB Local (dev) this completes in under 2 seconds. In production, the latency is ~5-10 ms per call × 500 = ~2.5-5 seconds; this is acceptable for a synchronous endpoint. If profiling reveals this is too slow, a follow-up ticket can introduce async batching.

### 5.6 Event ownership enforcement

`_require_owner_or_admin` checks `ctx["user_sub"] == meta["owner_sub"]` first, then falls back to `role_allows_admin_features(normalize_role(ctx["role"]))` (since `Role` is an unordered `str, Enum`, no `>=` comparison is possible). An invitee who is also an admin cannot manage invitations for an event they do not own unless they hold an ADMIN/ROOT role. This follows the same owner-or-admin pattern used elsewhere for mutating operations.

### 5.7 Deletion of a non-existent invitee

`DELETE /{event_id}/invitees/{invitee_sub}` returns 404 when the invitee row is absent. It does not return 204 silently for a missing row, because the caller likely has a bug if they try to remove an invitee that was never added. This decision can be revisited if downstream consumers find the 404 inconvenient for idempotent teardown workflows.

### 5.8 `crm_events` table partition width

A single event's partition holds one META row plus one INVITEE row per invitee. For an event with 5,000 invitees, all rows share PK=`event_id`. DynamoDB's 10 GB per-partition limit is not a concern at this scale; 5,000 items at ~500 bytes each is ~2.5 MB. The separation of registration rows into `crm_event_registrations` (EVT-001 design) keeps the total manageable.

### 5.9 Concurrent `send_invitations` calls

If two concurrent calls hit `send_invitations` for the same event, both will query INVITEE rows with `invite_status="pending"`. Both will attempt to call `send_alert_email` and then `update_item` with `ConditionExpression="invite_status = :p"`. The second `update_item` will fail (`ConditionalCheckFailedException`) because the first already advanced the status. The second call will increment `failed` for those invitees. This is an acceptable trade-off: the worst case is a single duplicate email per concurrent call, which the organiser can explain with "you may receive two invitations." A distributed lock would add complexity disproportionate to the risk for this use case.

### 5.10 `calendar_event_id` validation

EVT-002 does not validate that `calendar_event_id` resolves to a real item in `T.calendar`. The field is stored as an opaque string. If the calendar event was deleted after the CRM event was created, the invitation email body will contain a broken link. A follow-on ticket (EVT-003 or a dedicated validation ticket) can add a lookup via `T.calendar.get_item` to surface this as a 422 at creation time.

### 5.11 `max_attendance` interaction

EVT-002 writes `max_attendance` on the META row but does not enforce it. Invitees can be added in excess of `max_attendance` in EVT-002. Enforcement is owned by EVT-004. This is intentional — the invitee list is a superset of potential attendees; the registration/capacity layer (EVT-003/004) is the enforcement point.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

EVT-002 introduces no `if S.dev_mode` branch anywhere. Every code path (DynamoDB reads/writes, email dispatch, audit events) runs identically in dev and prod. The only behavioural difference is `send_alert_email`'s own internal `if S.dev_mode` branch (pre-existing, `alerts.py:462`), which the EVT-002 service does not replicate. This is the correct SECOPS-007 posture: dev/prod divergence is contained in `alerts.py`, not multiplied across consumers.

### Idempotency

- **Event creation**: `create_crm_event` is not idempotent (each call creates a new event). The router does not perform deduplication. Callers that retry on network failure may create duplicate events; this is consistent with the rest of the platform (e.g., `create_event` in `calendar.py`).
- **Add invitee**: idempotent via conditional `put_item` (§5.2).
- **Bulk import**: idempotent per sub via the same conditional `put_item` path.
- **Send invitations**: idempotent at the status-check level; subsequent calls are no-ops (§5.3).
- **Remove invitee**: not idempotent — second call returns 404 (§5.7).

### CSRF protection

All mutating routes (`POST`, `DELETE`) are reached via `Depends(require_ui_session)`, which enforces CSRF token validation for cookie-auth requests (the `x-csrf-token` header must match the session's `csrf_token` and the `ui_csrf` cookie, per CLAUDE.md auth notes). No special CSRF handling is added in EVT-002.

### Authorisation

- **Create event**: any authenticated user may create an event (no minimum role). The creator becomes `owner_sub`.
- **Add/remove/bulk-import/send/list**: `owner_sub` or `role >= ADMIN`. An ordinary user cannot manage another user's event invitees.
- **Read list**: same guard as mutations. No public endpoint for the invitee list is introduced in EVT-002.

### Audit trail

Every mutation (create, add, remove, bulk import, send invitations) emits an `audit_event` to `T.alerts`. The `audit_event` function (`alerts.py:644`) records `ts`, `event`, `user_sub`, and arbitrary `**fields`. This provides a complete audit trail for compliance without coupling to the session or request object where context is unavailable (e.g., in background-style bulk loops).

### Input validation

- `name` is bounded 1-200 chars; `description` max 5000; `invitee_sub` max 128; `user_subs` max 500 items each max 128 chars. All enforced by Pydantic `Field(...)` constraints before any service code runs.
- `max_attendance` must be `ge=1` when present — an event cannot be created with capacity zero.
- `limit` on list endpoint is clamped server-side to `le=200` regardless of the query parameter value.

### No money-out path

EVT-002 has no billing, payment, or refund paths. The `billing_shared.settle_or_reverse_ledger` and `refund_payment` primitives are not used.

## 10. Open Questions / Assumptions

1. **`calendar_event_id` composite key format.** EVT-002 stores `calendar_event_id` as `"{calendar_id}#{event_id}"` (the `ByCalendar` GSI PK). The `T.calendar` table uses PK=`calendar_id`, SK=`EVENT#{event_id}` (from `_event_key` at `app/routers/calendar.py`). If the frontend ever needs to deep-link to the calendar event, it must split on `#`. **Assumption:** the composite `{calendar_id}#{event_id}` string is sufficient; no lookup into `T.calendar` is performed in EVT-002. Confirm before implementing.

2. **Invitee email fallback when `displayed_email` is private.** `get_profile_identity` returns `{"email": profile.get("displayed_email"), ...}` (`app/services/profile.py:313`). If the user has not set `displayed_email`, the invitation cannot be sent. An alternative would be to look up the user's verified email from `T.email` (the email-device table). **Assumption for EVT-002:** only `displayed_email` is used; users without a displayed email are counted as `failed`. A follow-up ticket can add fallback to the verified email device.

3. **Maximum invitees per event.** No hard cap beyond the 500-per-request bulk import limit. A single event could accumulate thousands of invitees across multiple bulk-import calls. If the event is expected to grow very large, a per-event invitee cap (e.g., `CRM_EVENT_MAX_INVITEES`, default 10,000) should be added. **Assumption:** no cap in EVT-002; deferred to EVT-004 or a dedicated scaling ticket.

4. **`invite_status` transitions from EVT-003.** EVT-003 will add `accept`, `decline`, and `attend` transitions. The INVITEE row is the shared data model. EVT-002 and EVT-003 must agree that EVT-003 never resets a `"sent"` invitee back to `"pending"`. **Assumption:** EVT-003 uses `ConditionExpression="invite_status = :sent"` as a guard on accept/decline transitions.

5. **Bulk import and PTY contact IDs.** Currently invitees are identified by `user_sub`. When PTY-001 ships, the organiser may want to invite a contact by `contact_id` (which resolves to a `user_sub` via the party table). **Assumption:** EVT-002 accepts only `user_sub`. A follow-up ticket extending `CrmInviteeBulkImportIn` to accept `contact_ids` with a resolution step can be added once PTY-001 lands.
