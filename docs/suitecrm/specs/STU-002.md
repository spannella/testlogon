# STU-002 — ACL Role matrix — per-module CRUD permission store & evaluation

**Ticket source**: `docs/suitecrm/CRM_SECURITY_STUDIO_TICKETS.md` lines 96–145  
**Type**: Feature · **Priority**: P1 · **Estimate**: 3 d  
**Feature flag**: `CRM_ACL_ENABLED` (default `"0"`, off)  
**Depends on**: STU-001 (tables + settings scaffolding)

---

## 1. Summary & Goal

Implement the CRM ACL Role entity and its evaluation layer. A ROOT administrator
can create named ACL roles whose `permissions` map grants or denies seven
per-module actions (`create`, `read`, `update`, `delete`, `export`, `import_`,
`mass_update`). Roles are then assigned to individual users. A FastAPI
`Depends`-compatible callable (`require_crm_permission`) integrates with every
CRM router so that, when `CRM_ACL_ENABLED=1`, callers that lack the required
permission on a module receive a 403 before the handler runs.

With `CRM_ACL_ENABLED=0` (the default) the entire enforcement layer is a
no-op: `check_permission` returns `True` unconditionally, the router is never
registered, and the platform is byte-for-byte unchanged.

## 3. Data Model

All rows live in the single `crm_acl_roles` DynamoDB table introduced by STU-001.

### 3.1 Role definition row

```
pk = "ROLE#{role_id}"     (S)
sk = "META"               (S)
```

Additional attributes:

| Attribute | Type | Notes |
|---|---|---|
| `role_id` | S | `uuid4().hex` |
| `name` | S | Human-readable; unique by convention (not enforced in DDB) |
| `description` | S | Free text |
| `permissions` | Map | `{module_name: {create, read, update, delete, export, import_, mass_update}}` — all bool |
| `created_at` | N | `now_ts()` from `app/core/time.py:2` |
| `created_by_sub` | S | `actor_sub` |
| `updated_at` | N | `now_ts()` on each write |
| `updated_by_sub` | S | `actor_sub` on each write |

### 3.2 Per-user assignment row

```
pk = "ROLE#{role_id}"          (S)
sk = "ASSIGNMENT#{user_sub}"   (S)
```

Additional attributes:

| Attribute | Type | Notes |
|---|---|---|
| `user_sub` | S | The assignee |
| `assignee_id` | S | Copy of `user_sub` (projected onto GSI) |
| `role_id` | S | Copy of the parent role_id |
| `assigned_by_sub` | S | Actor |
| `assigned_at` | N | `now_ts()` — GSI sort key; must be `N` |

`assignee_id` is a redundant copy of `user_sub` used as the GSI partition key.
The `by-assignee` GSI (PK=`assignee_id`, SK=`assigned_at`) lets
`get_roles_for_user` retrieve every role assigned to a user in O(log n) without
a table scan.

### 3.3 GSI: `by-assignee`

```
GSI PK  = assignee_id   (S)
GSI SK  = assigned_at   (N)   ← attr_types={"assigned_at": "N"} required
```

Declared in `scripts/local-ddb-init.py` under the `crm_acl_roles` TableDef.
Without `attr_types={"assigned_at": "N"}`, DynamoDB stores the numeric timestamp
as a String and `ValidationException` is thrown at query time (CLAUDE.md gotcha).

### 3.4 No new tables

STU-002 uses only `T.crm_acl_roles` from STU-001 and the existing `T.alerts`
for audit events. No additional DynamoDB tables are created.

## 4. API / Service Design

### 4.1 Service layer — `app/services/crm_acl.py` (new file)

**Module-level cache** (mirrors `billing_config.py:46–58`):

```python
_perm_cache: dict[str, tuple[list[dict], int]] = {}  # user_sub -> (roles, fetched_ts)
_CACHE_TTL = 60  # seconds

def _invalidate_user_cache(user_sub: str) -> None:
    _perm_cache.pop(user_sub, None)
```

**Function signatures:**

```python
def create_acl_role(actor_sub, name, description, permissions: dict[str, dict[str, bool]]) -> dict
def get_acl_role(role_id: str) -> dict              # raises HTTPException(404)
def list_acl_roles(limit=50, cursor=None) -> tuple[list[dict], str | None]
def update_acl_role(actor_sub, role_id, *, name=None, description=None, permissions=None) -> dict
def delete_acl_role(actor_sub, role_id) -> None     # deletes META + all ASSIGNMENT rows
def assign_role_to_user(actor_sub, role_id, user_sub) -> None
def revoke_role_from_user(actor_sub, role_id, user_sub) -> None
def get_roles_for_user(user_sub) -> list[dict]      # queries by-assignee GSI
def list_assignments_for_role(role_id) -> list[dict]
def check_permission(user_sub, module, action) -> bool
def require_crm_permission(module, action)          # FastAPI Depends factory
```

**Key implementation notes:**

- `create_acl_role` generates `role_id = uuid4().hex`, `put_item` the META row,
  calls `audit_event("crm_acl_role.created", actor_sub, role_id=role_id)`.
- `update_acl_role` uses `update_item` with `UpdateExpression` for provided fields
  only; writes `updated_at` + `updated_by_sub`; emits `crm_acl_role.updated`.
- `delete_acl_role` queries `pk=ROLE#{role_id}` for all SK starting with
  `ASSIGNMENT#`, calls `_invalidate_user_cache` per assignee, batch-deletes them,
  then deletes the META row; emits `crm_acl_role.deleted`.
- `assign_role_to_user` upserts the ASSIGNMENT row, emits
  `crm_acl_role.assigned`, invalidates cache for `user_sub`.
- `revoke_role_from_user` deletes the row, emits `crm_acl_role.revoked`,
  invalidates cache.
- `get_roles_for_user` queries the `by-assignee` GSI
  (`Key("assignee_id").eq(user_sub)`), collects `role_id` values, batch-gets META
  rows, returns the list.
- `check_permission` short-circuits to `True` when `_S.crm_acl_enabled is False`
  (lazy import of `S` to avoid circular import). Cache key = `user_sub`; stale
  after `_CACHE_TTL` seconds.
- `require_crm_permission(module, action)` returns a `Depends`-compatible async
  callable that calls `check_permission` and raises `HTTPException(403,
  {"code": "crm_permission_denied", "module": module, "action": action})` on
  denial.

### 4.2 Pydantic models — additions to `app/models.py`

**`CrmAclPermissionMatrix`** — seven bool fields, all default `False`:
`create`, `read`, `update`, `delete`, `export`,
`import_: bool = Field(False, alias="import")` (alias so JSON key is `"import"`,
a Python reserved word; `ConfigDict(populate_by_name=True)`), `mass_update`.

**`CrmAclRoleCreateIn`** — `name: str`, `description: str = ""`,
`permissions: dict[str, CrmAclPermissionMatrix] = {}`.

**`CrmAclRoleUpdateIn`** — same fields, all optional (`str | None`, matrix `| None`).

**`CrmAclRoleOut`** — `role_id`, `name`, `description`, `permissions`,
`created_at: int`, `created_by_sub`, `updated_at: int | None`,
`updated_by_sub: str | None`.

**`CrmAclAssignmentIn`** — `user_sub: str`.

**`CrmAclAssignmentOut`** — `role_id`, `user_sub`, `assigned_by_sub`,
`assigned_at: int`.

**`CrmEffectivePermissionsOut`** — `user_sub: str`,
`permissions: dict[str, CrmAclPermissionMatrix]` (merged union across all
assigned roles).

### 4.3 Router — `app/routers/crm_acl.py` (new file)

Prefix: `/ui/admin/crm/acl-roles`  
Registration: `app/main.py` inside `if S.crm_acl_enabled:` block (see §6).

Route ordering follows the constraint in the file header: static literal segments
(`/my-permissions`) are declared **before** dynamic `/{role_id}` segments.

```
GET   /my-permissions                    → get_my_permissions()
POST  /                                  → create_role()            [ROOT]
GET   /                                  → list_roles()             [ADMIN/ROOT]
GET   /{role_id}                         → get_role()               [ADMIN/ROOT]
PATCH /{role_id}                         → update_role()            [ROOT]
DELETE/{role_id}                         → delete_role()            [ROOT]
GET   /{role_id}/assignments             → list_assignments()       [ADMIN/ROOT]
POST  /{role_id}/assignments             → assign_user()            [ROOT]
DELETE/{role_id}/assignments/{user_sub}  → revoke_user()            [ROOT]
```

Auth dependencies:

| Endpoint | Dependency |
|---|---|
| `GET /my-permissions` | `Depends(get_authenticated_user)` — any authenticated caller |
| `GET /`, `GET /{role_id}`, `GET /{role_id}/assignments` | `Depends(require_admin_or_root)` from `app/auth/policy.py:67` |
| All mutating endpoints (POST, PATCH, DELETE) | `Depends(require_root)` from `app/auth/policy.py:63` |

**Response shapes** (HTTP status codes):

| Operation | Success | Error |
|---|---|---|
| `POST /` | 201 `CrmAclRoleOut` | 422 on validation |
| `GET /` | 200 `{roles: [CrmAclRoleOut], next_cursor: str\|null}` | — |
| `GET /{role_id}` | 200 `CrmAclRoleOut` | 404 not found |
| `PATCH /{role_id}` | 200 `CrmAclRoleOut` | 404 / 422 |
| `DELETE /{role_id}` | 204 | 404 |
| `GET /my-permissions` | 200 `CrmEffectivePermissionsOut` | — |
| `POST /{role_id}/assignments` | 201 `CrmAclAssignmentOut` | 404 role not found / 409 already assigned |
| `DELETE /{role_id}/assignments/{user_sub}` | 204 | 404 |
| `GET /{role_id}/assignments` | 200 `{assignments: [CrmAclAssignmentOut]}` | 404 |

`GET /my-permissions` computes the effective union of all assigned roles for the
caller. When the user has no assigned roles, it returns an empty `permissions`
dict (not a 404 — the caller simply has no grants). The computation matches
`check_permission`: for each module, set a flag to `True` if **any** assigned role
grants it.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off path
`check_permission` returns `True` without any DDB access when `S.crm_acl_enabled
is False`. This holds even if the table has been populated.

### 5.2 Deny-by-default when flag is on
A user with no assigned roles receives `False` for every `check_permission` call.
No CRM access until a ROOT admin assigns a role.

### 5.3 Permission union across roles
Effective permission = `OR` across all assigned roles. Additive only; no
deny-override in STU-002.

### 5.4 Cache invalidation on assignment change
`assign_role_to_user` and `revoke_role_from_user` call `_invalidate_user_cache(
user_sub)` after their DDB write. Cache is process-local; the 60 s TTL bounds
stale-window for cross-process scenarios.

### 5.5 Deleting a role with assignments
`delete_acl_role` queries `pk=ROLE#{role_id}` for all SK with `ASSIGNMENT#`
prefix, invalidates each assignee's cache, batch-deletes rows, then deletes META.
Sequential, not transactional. Orphan ASSIGNMENT rows (process crash mid-delete)
are silently skipped by `get_roles_for_user` (missing META → filtered out).

### 5.6 Duplicate assignment
`assign_role_to_user` upserts unconditionally (idempotent). The 409 router
response is an optional convenience and can be implemented via
`ConditionExpression=attribute_not_exists(sk)` + catch
`ConditionalCheckFailedException`.

### 5.7 Unknown module/action
Unknown module → `False`. Known module but unknown action key → `False`.
Typos in router code silently deny.

### 5.8 ROOT/ADMIN bypass
Recommended: add `if user.role in {Role.ROOT, Role.ADMIN}: return True` in
`check_permission` so operators are never locked out when the flag first activates
without pre-seeded roles. This is optional if seeding is guaranteed.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity
All DynamoDB access goes through `T.crm_acl_roles` — the `_FloatSafeTable` wrapper
(`app/core/tables.py:29`). In dev it points to DynamoDB Local (port 8001); in prod
to real DynamoDB. No `if dev_mode` branch in `app/services/crm_acl.py`. No mock
endpoint.

### 7.2 Idempotency
`create_acl_role` is not idempotent (generates a new `role_id` each call).
`assign_role_to_user` is idempotent (upsert). `revoke_role_from_user` is
idempotent (DDB `delete_item` is a no-op on a missing key). `update_acl_role` is
idempotent. `delete_acl_role` returns 404 on a second call (META row gone).

### 7.3 Security
Mutating endpoints require ROOT via `require_root` (`app/auth/policy.py:63`).
Cookie-auth callers that need CSRF can add `Depends(enforce_cookie_csrf)`
(`app/auth/policy.py:71`) — the base `require_root` dependency does not enforce
CSRF. The Pydantic `CrmAclPermissionMatrix` model silently drops unknown action
keys, preventing injection of arbitrary permission flags. `check_permission` logs
only a `DEBUG` line on cache miss; never logs the full permissions payload.

## 8. Backward Compatibility & Migration

### 8.1 No migration required
`CRM_ACL_ENABLED` defaults to `"0"`. Existing data is unaffected. Activation
sequence: (1) create a "Full Access" role granting all seven actions on all known
modules; (2) assign it to all ROOT/ADMIN users; (3) set `CRM_ACL_ENABLED=1` and
redeploy. Reversing the flag immediately restores open access; DDB rows are
retained and re-activate if the flag is re-enabled.

### 8.2 Downstream router wiring
Sibling CRM routers (PTY contacts, OPP opportunities, etc.) will add
`Depends(require_crm_permission("<module>", "<action>"))` to their handlers once
they are built. Until then, `require_crm_permission` is available but not wired.

### 8.3 STU-003 forward-compatibility
STU-003 replaces `get_roles_for_user` with `get_effective_roles_for_user` (adds
group propagation). `check_permission` is updated in that ticket; the cache
invalidation contract is unchanged.

## 10. Open Questions / Assumptions

1. **ROOT/ADMIN bypass** (§5.8): include bypass in `check_permission` so operators
   are never locked out at flag-activation time. Remove only if a strict
   "ROOT must also have a role" policy is explicitly required.

2. **Module name registry**: no centralized registry of valid module names; a
   follow-on validation enum could be added without changing the DDB schema.

3. **Multi-process cache coherence**: the 60 s cache is process-local. In a
   horizontally-scaled deployment, revocation propagates within 60 s per process.
   DDB Streams-based invalidation or a shorter TTL is a future option.

4. **`import_` alias**: `Field(alias="import")` exposes `"import"` in JSON.
   Rename to `import_permission` before first prod use if the alias causes
   confusion downstream (breaking API change).

5. **Pagination**: most tenants will have <50 roles; `next_cursor` will nearly
   always be `null`.
