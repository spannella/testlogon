# LED-003 — Lead CRUD service

**Type:** Feature  **Priority:** P0  **Estimate:** 2 days
**Ticket source:** `docs/suitecrm/CRM_LEADS_TICKETS.md`, section "LED-003"

---

## 1. Summary & Goal

LED-003 creates `app/services/leads.py`, the DynamoDB data-access and business-logic layer for the `leads` single table delivered by LED-001. It exposes five public functions — `create_lead`, `get_lead`, `list_leads`, `update_lead`, and `delete_lead` — that implement the full CRUD lifecycle for a Lead record, including email normalization, idempotent duplicate detection, status-transition enforcement, GSI fan-out on write, and audit-event emission.

No router, no frontend change, and no existing file is modified when `S.leads_enabled` is False. The service is the stable foundation for every downstream LED ticket (LED-004 through LED-013) and for the full router surface in LED-013.

## 4. API / Service Design

All functions are synchronous (no `async`). They are called from async FastAPI route handlers via `await asyncio.to_thread(...)` at the router layer (LED-013), following the pattern used in `app/routers/google_drive_integration.py`.

### 4.1 `create_lead`

```python
def create_lead(creator_sub: str, data: LeadCreateIn) -> dict:
```

1. Guard: `if not S.leads_enabled: raise HTTPException(503, "Leads module is not enabled")`.
2. Normalize: `email = normalize_email(data.email)` (raises 400 on invalid). `phone = normalize_phone(data.phone) if data.phone else None`.
3. Idempotent duplicate check: query `ByStatus` GSI with `GSI2PK = "STATUS#new"` and `FilterExpression=Attr("email").eq(email)`. If a matching item is returned, return it immediately without writing a new row.
4. Generate: `lead_id = "lead_" + uuid4().hex[:20]`, `ts = now_ts()`.
5. Build item with all fields from `data`, plus `lead_id`, `status="new"`, `score=0`, `created_by=creator_sub`, `created_at=ts`, `updated_at=ts`, and all three GSI attribute pairs.
6. Write: `T.leads.put_item(Item=item)`.
7. Emit: `audit_event("lead.created", creator_sub, lead_id=lead_id, email=email, lead_source=data.lead_source)`.
8. Return the item dict.

### 4.2 `get_lead`

```python
def get_lead(lead_id: str) -> Optional[dict]:
```

1. Guard: `if not S.leads_enabled: raise HTTPException(503, ...)`.
2. `resp = T.leads.get_item(Key={"pk": f"LEAD#{lead_id}", "sk": "META"})`.
3. Return `resp.get("Item")` or `None`.

### 4.3 `list_leads`

```python
def list_leads(
    *,
    owner_sub: str,
    status: Optional[str] = None,
    lead_source: Optional[str] = None,
    assigned_to: Optional[str] = None,
    created_after: Optional[int] = None,
    cursor: Optional[str] = None,
    limit: int = 50,
) -> dict:
    # Returns {"leads": [...], "cursor": Optional[str]}
```

1. Guard: `if not S.leads_enabled: raise HTTPException(503, ...)`.
2. GSI routing (mutually exclusive, checked in order):
   - If `status` is provided: query `ByStatus` GSI with `GSI2PK = "STATUS#{status}"`, `ScanIndexForward=False`.
   - Else if `lead_source` is provided: query `BySource` GSI with `GSI3PK = "SOURCE#{lead_source}"`, `ScanIndexForward=False`.
   - Else: query `ByOwner` GSI with `GSI1PK = "OWNER#{owner_sub}"`, `ScanIndexForward=False`.
3. Apply `created_after` as a `KeyConditionExpression` range filter (`GSI?SK >= created_after`) when the relevant GSI is selected.
4. Apply `assigned_to` as a `FilterExpression` when it is provided (post-filter; not a primary key).
5. Pagination: decode `cursor` via `decode_cursor(cursor)` → `ExclusiveStartKey`. Cap `limit` to 200. After the query, encode the result's `LastEvaluatedKey` via `encode_cursor(...)`.
6. Filter out soft-deleted rows (`Attr("deleted_at").not_exists()`) via `FilterExpression`. Because DynamoDB fetches up to 1 MB before applying `FilterExpression`, the caller may receive fewer than `limit` items in one page; the cursor will continue iteration. This is consistent with existing sparse-filter patterns in the codebase (noted in CLAUDE.md: "DDB FilterExpression doesn't reduce page size").
7. Return `{"leads": [list of item dicts], "cursor": encoded_cursor_or_None}`.

### 4.4 `update_lead`

```python
def update_lead(lead_id: str, actor_sub: str, data: LeadUpdateIn) -> dict:
```

1. Guard: `if not S.leads_enabled: raise HTTPException(503, ...)`.
2. Read current item: `existing = get_lead(lead_id)`. If `None`, raise `HTTPException(404, "Lead not found")`.
3. If `existing.get("deleted_at")` is set, raise `HTTPException(410, "Lead has been deleted")`.
4. Status transition validation: if `data.status` is set and differs from `existing["status"]`, validate the transition against `_LEAD_TRANSITIONS` (defined in the service module — see Section 5.1). Raise `HTTPException(400, "Invalid status transition ...")` on failure. The special case: transitioning to `"converted"` requires `converted_party_id` to be set (either already on the record or passed in `data`).
5. Normalize updated email/phone if provided.
6. Build an `update_expression` that sets only the fields present in `data` (skip `None` values). Always set `updated_at = now_ts()`.
7. If `status` changed, also update `GSI2PK` and `GSI2SK` (status-based GSI key must be rewritten). Because DynamoDB does not support partial key updates in-place for GSI keys, this is implemented as a delete + re-put of the full item (same technique used by any service that changes a GSI partition key). The service reads the item, builds an updated copy, calls `T.leads.delete_item(Key={...})` then `T.leads.put_item(Item=updated_item)`. This is not atomic; the window is acceptable for MVP (a transact_write can be introduced in a follow-up if needed).
8. Emit: `audit_event("lead.updated", actor_sub, lead_id=lead_id, changes=list(data.model_fields_set))`.
9. Return the updated item dict.

### 4.5 `delete_lead`

```python
def delete_lead(lead_id: str, actor_sub: str) -> None:
```

1. Guard: `if not S.leads_enabled: raise HTTPException(503, ...)`.
2. Read current item; raise 404 if not found.
3. If already soft-deleted (`deleted_at` is set), return without error (idempotent).
4. Soft-delete: `update_lead` with `status="dead"` and set `deleted_at = now_ts()` directly via `update_item`.
5. Remove the item from the `ByOwner` and `BySource` GSIs effectively by leaving `GSI1PK` / `GSI2PK` / `GSI3PK` in place; the `deleted_at` filter in `list_leads` will exclude it. This is intentional — a hard GSI removal would require a full item re-write and is unnecessary for a soft-delete, because `list_leads` already applies `FilterExpression(Attr("deleted_at").not_exists())`.
6. Emit: `audit_event("lead.deleted", actor_sub, lead_id=lead_id)`.

### 4.6 Internal helper `find_lead_by_email`

```python
def find_lead_by_email(email: str) -> Optional[dict]:
```

Used by the duplicate check in `create_lead` and by LED-008 bulk import. Queries the `ByStatus` GSI page-by-page for `GSI2PK = "STATUS#new"` with `FilterExpression=Attr("email").eq(normalized_email)`. Returns the first match or `None`. This is the simplest duplicate check available before LED-007 adds the `ByEmail` GSI (GSI4). Once LED-007's GSI4 is in place, this helper can be updated to query that index instead (a transparent internal refactor with no API surface change).

## 5. Detailed Behavior & Edge Cases

### 5.1 Status state machine

```python
LEAD_STATUSES = {"new", "assigned", "in_process", "converted", "recycled", "dead"}

_LEAD_TRANSITIONS: dict[str, tuple[str, ...]] = {
    "new":        ("assigned", "in_process", "recycled", "dead"),
    "assigned":   ("in_process", "recycled", "dead", "new"),
    "in_process": ("converted", "recycled", "dead", "assigned"),
    "recycled":   ("new", "assigned", "dead"),
    "dead":       ("new",),          # re-open only
    "converted":  (),                # terminal: no transitions out
}
```

`update_lead` raises `HTTPException(400, detail={"code": "invalid_status_transition", "from": old, "to": new})` when the requested transition is not in the allowed set. The `"converted"` status is checked as a special pre-condition: `data.status == "converted"` is only allowed when `converted_party_id` is already present on the record (set by LED-006's convert endpoint). If `converted_party_id` is absent and no inline value is supplied, raise `HTTPException(400, "converted_party_id required to transition to converted")`.

### 5.2 Idempotent create (duplicate email)

The duplicate check in `create_lead` uses the `ByStatus` GSI with status `"new"` because duplicate detection is only meaningful for active leads — a dead or converted lead with the same email should not block creation of a new lead for that contact. This means a user can create a new lead for an email address that previously appeared as a `"dead"` or `"converted"` lead.

The duplicate query uses a `FilterExpression` (not a KeyCondition) on the `email` attribute. Because DDB applies filters after fetching 1 MB, if there are more than roughly 500 "new" leads the query must loop via `LastEvaluatedKey`. The helper caps the loop at 10 pages (approx. 5000 leads) before giving up and allowing the write; this avoids an unbounded scan in pathological conditions and is acceptable for MVP.

### 5.3 Email normalization is non-destructive

The raw email string is stored in `email_raw` on the item alongside the normalized `email`. This preserves display fidelity (e.g., `"Alice@Example.COM"` → stored raw; `"alice@example.com"` stored as `email`) and allows future case-sensitive audit queries. The `LeadOut.email` field returns the normalized value.

### 5.4 Phone normalization failure is not a hard error on update

On `update_lead`, if `data.phone` is provided and fails E.164 normalization, `normalize_phone` raises HTTP 400 (`"Invalid phone format; use +E164 or 10-digit"` at `app/core/normalize.py:81`). This propagates to the caller as a 400, not a 500. The phone field is never partially updated.

### 5.5 GSI2PK rewrite on status change

When `update_lead` transitions a lead's status, the `GSI2PK` attribute must change from `"STATUS#{old_status}"` to `"STATUS#{new_status}"`. DynamoDB does not allow updating a GSI partition key in-place with a simple `UpdateExpression`; the attribute that feeds the GSI partition key can be updated, but the change only takes effect in the index after the item is written. The service achieves this by issuing a single `T.leads.put_item(Item=updated_copy)` (a full overwrite), which atomically updates the primary item and all GSI projections in one request. This is the standard single-table approach and is safe for correctness.

### 5.6 `list_leads` with both `status` and `lead_source` provided

If the caller passes both `status` and `lead_source`, the service routes to the `ByStatus` GSI (higher selectivity assumed) and applies `lead_source` as a `FilterExpression`. This is documented behavior: callers who need maximum efficiency should use only one filter dimension at a time.

### 5.7 Soft-delete visibility

Soft-deleted leads (`deleted_at` set, `status="dead"`) remain physically present in DynamoDB and appear in the GSIs. The `list_leads` function always applies a `FilterExpression(Attr("deleted_at").not_exists())`. Admin-level restore is out of scope for LED-003 but can be implemented by calling `update_lead` with `status="new"` and clearing `deleted_at`, provided a new `update_lead` code path permits it (admin-only in LED-013).

### 5.8 `limit` clamping

`list_leads` clamps `limit` to the range `[1, 200]`. Values outside this range are silently clamped rather than rejected with 422, to avoid client breakage if defaults change. The DynamoDB `Limit` parameter is set to the clamped value.

### 5.9 Concurrent create race

Two concurrent `create_lead` calls for the same email (within the same millisecond) may both pass the duplicate check and both write rows. This window is acceptable for MVP. LED-009 (duplicate detection and merge) provides a post-hoc remedy. A conditional write (`ConditionExpression=Attr("pk").not_exists()`) is not sufficient here because the PK is unique by construction (`lead_` + UUID); the uniqueness constraint is on `email`, not `pk`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 — no `dev_mode` branches

`app/services/leads.py` contains zero references to `S.dev_mode`. All DDB operations go through `T.leads` (a `_safe_table` proxy) which targets DynamoDB Local in dev and real DynamoDB in prod. The `audit_event` call writes to `T.alerts` in both environments. There is no mock path, no `if S.dev_mode:` bypass, and no inline data. Dev uses moto; prod uses real AWS — the code path is identical.

### 7.2 Idempotency

`create_lead` with a duplicate normalized email returns the existing record without writing a new row (described in Section 5.2). `delete_lead` on an already-deleted lead is a no-op (returns `None` without error). `update_lead` on an unchanged record still writes `updated_at` and emits an audit event; callers that need true idempotency (no side effect) can compare fields before calling.

### 7.3 Input sanitization

Email normalization (`normalize_email`) rejects inputs without `@` and inputs longer than 254 characters (per RFC 5321). Phone normalization (`normalize_phone`) rejects non-E.164-convertible strings. `lead_source` and `status` are validated against their closed sets (`LEAD_SOURCES`, `LEAD_STATUSES`) at the router layer via Pydantic field patterns (LED-002). The service additionally validates status transitions (Section 5.1).

### 7.4 Actor authorization

LED-003 does not enforce ownership at the service layer; that is the responsibility of the router layer (LED-013). The service accepts `actor_sub` for audit logging only. This is consistent with the `app/services/tickets.py` pattern where the router enforces ownership and the service layer handles DDB access.

### 7.5 PII in audit events

The `audit_event` call for `lead.created` includes `email` (PII). This is intentional — the audit trail must record the lead's email for compliance purposes, consistent with how the KYC modules emit audit events with user-identifiable fields (e.g. `app/services/kyc_risk_scoring.py`, `app/routers/kyc_cases.py`; note `app/services/kyc_cases.py` itself does NOT call `audit_event` directly — the original spec's citation of that file was imprecise). The email is stored in `T.alerts` under the caller's `user_sub`, not broadcast externally.

## 8. Backward Compatibility & Migration

### 8.1 No schema change to existing tables

LED-003 writes only to `T.leads` and `T.alerts` (audit events). It reads only from `T.leads`. No existing DynamoDB table, router, or service file is modified.

### 8.2 `app/models.py` insert point

LED-002 inserts `LeadCreateIn`, `LeadUpdateIn`, and `LeadOut` after the campaign models near line 4927. LED-003 imports these from `app.models` at the top of `app/services/leads.py`. If LED-002 has not shipped, LED-003 cannot compile; this is an explicit prerequisite, not a soft dependency.

### 8.3 Zero DDB migration required

The `leads` table is new. No backfill, no `UpdateTable`, and no index evolution is required. `just restart` recreates the table in dev via `scripts/local-ddb-init.py`. In production the table must be created via `CreateTable` before the flag is turned on; the LED-001 spec covers this as part of its acceptance criteria.

### 8.4 Future GSI additions (LED-007, LED-009)

LED-007 adds a `ByEmail` GSI (GSI4) and LED-009 adds a `ByPhone` GSI (GSI5) to the same `leads` table. These are additive index additions. `find_lead_by_email` (Section 4.6) is written to be refactorable once GSI4 exists: the implementation detail is internal to the service and the function signature does not change.

## 10. Open Questions / Assumptions

1. **`update_lead` ownership enforcement**: The current design delegates authorization to the router layer (LED-013). Should the service also enforce that `actor_sub == existing["created_by"]` or `existing["assigned_to"]`? The ticket is silent on this; the assumption is "no" at the service layer, consistent with `app/services/tickets.py`.

2. **Concurrent duplicate creation window**: The `create_lead` duplicate check is a read-then-write with no DDB conditional on the email attribute. A DDB conditional expression on a GSI attribute is not directly supported. The proposal is to accept the small race window for MVP and rely on LED-009 (merge) to clean up duplicates post-hoc. If this is unacceptable, the only robust solution is a separate `lead_emails` table with a `put_item` conditional on the email primary key (an additional table, out of scope here).

3. **`delete_lead` hard-delete option**: The ticket specifies soft-delete only. If an admin hard-delete is required for GDPR/right-to-erasure, that is a separate ticket. The assumption is that soft-delete with an eventual TTL-expiry mechanism (not specified) is sufficient for MVP.

4. **`list_leads` cross-owner visibility**: `list_leads` currently requires `owner_sub` and queries the `ByOwner` GSI. An admin viewing all leads in the system would need a full scan or a different GSI. The assumption is that admin-level list is out of scope for LED-003 and will be addressed in LED-013's admin endpoints.

5. **`find_lead_by_email` scan depth**: The 10-page cap on the `ByStatus#new` scan (Section 5.2) means duplicate detection can miss leads if there are more than ~5000 "new" leads in the system. This is acceptable for MVP; once LED-007 adds GSI4 (`ByEmail`), `find_lead_by_email` can use a direct keyed query with O(1) pages.
