# OPP-001 — Opportunity data model, DynamoDB table, and feature flag

**Ticket type:** Feature — Infrastructure/Foundation  
**Priority:** P0  
**Estimate:** 2 days  
**Source ticket file:** `docs/suitecrm/CRM_OPPORTUNITIES_TICKETS.md`

---

## 1. Summary & Goal

OPP-001 lays the pure infrastructure foundation that every other ticket in the CRM Opportunities series depends on. No business logic ships here. The deliverables are:

1. A master feature flag `S.sales_pipeline_enabled` (`SALES_PIPELINE_ENABLED`, default `false`) that gates every downstream OPP ticket.
2. Two new DynamoDB table definitions — `sales_opportunities` and `sales_quotas` — added to `scripts/local-ddb-init.py` and wired into the `T` singleton in `app/core/tables.py`.
3. Three Pydantic models — `OpportunityCreateIn`, `OpportunityUpdateIn`, `OpportunityOut` — plus the supporting string-constant tuples `OPPORTUNITY_STAGES` and `LEAD_SOURCE_CHOICES`, added to `app/models.py`.

When `SALES_PIPELINE_ENABLED` is `false` (the default), every existing surface of the platform is byte-for-byte unchanged. The tables exist in DynamoDB Local at dev startup (created by `scripts/local-ddb-init.py`) but no application code reads or writes them until OPP-002 ships the service and router.

### 2.2 DynamoDB table infrastructure

`scripts/local-ddb-init.py` defines a `TableDef` dataclass (`local-ddb-init.py:28-35`) with fields `name`, `partition_key`, `sort_key`, `gsi`, and `attr_types`. Current examples of numeric GSI sort key declarations:

- `scripts/local-ddb-init.py:729`: `BroadcastSessions` — `attr_types={"scheduled_at": "N"}` (TableDef at 721-730)
- `scripts/local-ddb-init.py:758`: `BroadcastHealthSnapshots` — `attr_types={"snapshot_ts": "N"}` (TableDef at 754-758)

The `Contacts` table is a simple two-key table with no GSIs (`local-ddb-init.py:691`; note its keys are `owner_id`/`contact_id`, not `pk`/`sk`, and it is registered with a bare `os.getenv("DDB_CONTACTS_TABLE", "Contacts")` rather than `_resolve_table_name(S.contacts_table_name, ...)`). ## 3. Data Model

### 3.1 `sales_opportunities` table

**Primary key:** `pk` (String) / `sk` (String)  
**Access pattern:** all opportunities for a given owner user are stored under `pk = "USER#{owner_sub}"` with `sk = "OPP#{opp_id}"`.

**Single-table layout:**

| pk | sk | Item type | Description |
|---|---|---|---|
| `USER#{owner_sub}` | `OPP#{opp_id}` | Opportunity META | All opportunity fields |
| `USER#{owner_sub}` | `FORECAST#{period_key}` | Forecast worksheet | Added by OPP-005 |
| `STAGE_CONFIG` | `META` | Stage configuration | Added by OPP-003 |
| `USER#{owner_sub}` | `OPP#{opp_id}#CONTACT#{contact_ref}` | Contact role junction | Added by OPP-004 |

**META row attributes** (OPP-001 defines only this row type):

| Attribute | Type | Notes |
|---|---|---|
| `pk` | String | `USER#{owner_sub}` |
| `sk` | String | `OPP#{opp_id}` |
| `opp_id` | String | `"opp_" + uuid4().hex` |
| `owner_sub` | String | User's Cognito sub; also denormalized for GSI projection |
| `name` | String | 1–255 characters |
| `stage` | String | One of `OPPORTUNITY_STAGES` |
| `amount_cents` | Number | Integer, ≥ 0 |
| `weighted_amount_cents` | Number | `amount_cents * probability // 100`; denormalized |
| `close_date` | Number | Unix timestamp integer (seconds); GSI sort key — MUST be `N` |
| `probability` | Number | Integer 0–100 |
| `lead_source` | String (nullable) | One of `LEAD_SOURCE_CHOICES` or absent |
| `description` | String (nullable) | Max 4096 chars |
| `account_party_id` | String (nullable) | Forward link to a PTY PARTY_GROUP / org account; the org-account service is PTY-008 ("B2B organization account service", `docs/ofbiz/specs/PTY-008.md:1`) and PARTY_GROUP CRUD is PTY-004 (absent until PTY ships) |
| `contact_party_id` | String (nullable) | Forward link to a PTY PERSON; CRUD service is PTY-004 ("Party CRUD service (PERSON / PARTY_GROUP)", `docs/ofbiz/specs/PTY-004.md:1`) (absent until PTY ships) |
| `created_at` | Number | Unix timestamp integer |
| `updated_at` | Number | Unix timestamp integer |
| `deleted_at` | Number (nullable) | Soft-delete timestamp; set by DELETE endpoint in OPP-002 |

**Global Secondary Indexes:**

| GSI name | PK | SK | Purpose |
|---|---|---|---|
| `GSI_BY_USER_CLOSE` | `owner_sub` (S) | `close_date` (N) | List all of a user's opportunities ordered by close date; range-bounded queries for OPP-005 forecast |
| `GSI_BY_STAGE` | `stage` (S) | `close_date` (N) | Admin cross-user funnel report by stage (OPP-006) |
| `GSI_DIRECT` | `opp_id` (S) | — | Direct lookup by opaque `opp_id` without knowing `owner_sub` (admin use, OPP-006) |

**`attr_types` declaration required:** Both `GSI_BY_USER_CLOSE` and `GSI_BY_STAGE` use `close_date` as a numeric sort key. Per the CLAUDE.md gotcha (and existing precedents at `local-ddb-init.py:53,729,758`), the `TableDef` must declare:

```python
attr_types={"close_date": "N", "created_at": "N"}
```

`created_at` is included because it appears as a sort key in the `GSI_DIRECT` projected attributes and may be used for secondary sorting in future tickets; declaring it now prevents a table rebuild later.

**`TableDef` entry in `scripts/local-ddb-init.py`** (positioned after line 691, the `Contacts` entry):

```python
# Sales pipeline — Opportunities (OPP-001)
TableDef(
    _resolve_table_name(S.sales_opportunities_table_name, "sales_opportunities"),
    "pk",
    "sk",
    gsi=[
        {"index_name": "GSI_BY_USER_CLOSE", "partition_key": "owner_sub", "sort_key": "close_date"},
        {"index_name": "GSI_BY_STAGE",      "partition_key": "stage",     "sort_key": "close_date"},
        {"index_name": "GSI_DIRECT",        "partition_key": "opp_id"},
    ],
    attr_types={"close_date": "N", "created_at": "N"},
),
```

`weighted_amount_cents` is a read-only derived field: it is never accepted in `CreateIn` or `UpdateIn`. It is computed server-side on every write (`amount_cents * probability // 100`, integer division) and stored as a denormalized attribute on the DDB row to avoid recomputing on every read.

`deleted_at` is intentionally absent from `OpportunityOut`. Soft-deleted opportunities are not returned by any OPP-002 list or get endpoint; if the item has `deleted_at` set, the get endpoint returns 404. The `deleted_at` attribute lives only in DynamoDB.

## 5. Detailed Behavior & Edge Cases

### 5.1 `close_date` as an integer Unix timestamp

`close_date` in `OpportunityCreateIn` and `OpportunityUpdateIn` is typed `int` representing Unix seconds (not milliseconds). Frontend clients must convert a JavaScript `Date` to `Math.floor(Date.now() / 1000)`. The value is stored as a DynamoDB Number attribute (declared via `attr_types={"close_date": "N"}`). A `close_date` in the past is allowed — a deal may have already closed. The minimum valid value is `0` (epoch); negative values are rejected by DynamoDB's Number type (there is no `ge=0` constraint on `close_date` because historical records may occasionally carry `0`).

### 5.2 `weighted_amount_cents` derivation

`weighted_amount_cents = amount_cents * probability // 100`. At `probability=0`, `weighted_amount_cents=0` regardless of `amount_cents`. At `probability=100`, `weighted_amount_cents=amount_cents`. Integer division is used to avoid fractional cents. This value is stored denormalized on the DDB row, not computed on read, so GSI scans (used by OPP-005 and OPP-006) can project it without fetching the full item.

### 5.3 Validator behavior at the Pydantic layer

Unknown `stage` values raise `ValueError` with a human-readable message listing valid choices. Pydantic v2 wraps these as `422 Unprocessable Entity` responses automatically when the router is wired (OPP-002). At OPP-001's scope (models-only), tests validate the models directly by constructing them and asserting that `ValidationError` is raised for invalid inputs.

`lead_source=None` is valid (optional field). An empty string `""` passes the `Optional[str]` type check but is semantically invalid; the validator does not reject `""` explicitly because it is not in `LEAD_SOURCE_CHOICES`, so `""` will raise `ValueError`. This is the correct behavior.

### 5.4 Account and contact party forward references

`account_party_id` and `contact_party_id` are stored as opaque strings at this stage. The PTY tickets (PTY-004 = "Party CRUD service (PERSON / PARTY_GROUP)", PTY-008 = "B2B organization account service") are **specced** (`docs/ofbiz/specs/PTY-004.md`, `docs/ofbiz/specs/PTY-008.md` exist) but **unbuilt** in the current codebase (confirmed: no `app/services/party*.py` or `app/routers/party*.py` exist). These fields are "nullable forward references" — they accept any string value or `None` without further validation. OPP-004 introduces a structured contact-role junction; OPP-002 documents that these top-level fields are free-text until PTY ships.

### 5.5 Table creation is idempotent

`scripts/local-ddb-init.py` wraps table creation in a `try/except ClientError` that ignores `ResourceInExistsException`. The two new tables follow this same pattern — a second run of `just restart` does not fail.

### 5.6 No DDB reads or writes in OPP-001

The table handles `T.sales_opportunities` and `T.sales_quotas` are initialized at import time by `_safe_table(...)`, which calls `ddb.Table(name)`. In production (and in tests using moto), the `Table` object is lazy — it does not make a network call until the first actual operation. This means that even with `SALES_PIPELINE_ENABLED=false`, the `T` object is fully initialized without error; no DDB round-trip occurs unless a service function (OPP-002+) calls `put_item`, `query`, etc.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No `dev_mode` branching

OPP-001 introduces no business logic and therefore no `if S.dev_mode` branches. The table definitions in `scripts/local-ddb-init.py` and the `T` handles in `app/core/tables.py` use the same code path regardless of environment. In production, `DDB_SALES_OPPORTUNITIES_TABLE` and `DDB_SALES_QUOTAS_TABLE` are set to the actual DynamoDB table ARN suffixes; in dev they default to `"sales_opportunities"` and `"sales_quotas"` against DynamoDB Local at port 8001.

### 7.2 Idempotency

Table creation in `scripts/local-ddb-init.py` is already idempotent (existing tables are skipped). The `T` handle initialization is idempotent (module-level singleton, no side effects on re-import). The Pydantic models have no side effects. Running `just restart` multiple times is safe.

### 7.3 Input security

The `name` field has an explicit `max_length=255` to prevent oversized strings reaching DynamoDB (item size limit is 400KB, but unbounded user input is rejected at the model layer). `description` is bounded at `max_length=4096`. `account_party_id` and `contact_party_id` are opaque strings with no explicit length cap at this stage; OPP-002 should add `max_length=128` to match the UUID-hex format used elsewhere in the codebase (e.g., `opp_id` will be 36 chars, party IDs will be similar).

### 7.4 Ownership enforcement

`OpportunityOut.owner_sub` is set server-side from the authenticated user's session — it is never accepted from the request body. `OpportunityCreateIn` has no `owner_sub` field; the service layer (OPP-002) derives it from `require_ui_session` context.

## 8. Backward Compatibility & Migration

### 8.1 Existing tables unchanged

The `Tables` dataclass is a frozen `@dataclass`. Adding two new fields does not affect existing field access — `T.contacts`, `T.sessions`, etc. are unchanged. The DDB Local instance persists data across backend restarts; the new tables are created on first `just restart` after this ticket lands. Existing data in all other tables is unaffected.

### 8.2 No schema migration needed for existing tables

OPP-001 adds only new tables. No GSIs are added to existing tables. No attribute schema changes touch any existing table. The `Contacts` table definition at `local-ddb-init.py:691` is not modified.

### 8.3 `T` constructor positional safety

The `Tables` dataclass uses a dataclass constructor. All existing callers use keyword arguments (`T.contacts`, `T.billing`, etc.) — there are no positional `Tables(...)` instantiation sites in production code. Adding two fields after `contacts` does not break any existing code.

### 8.4 `app/models.py` import safety

`OPPORTUNITY_STAGES` and `LEAD_SOURCE_CHOICES` are module-level tuples. They do not conflict with any existing name in `app/models.py`. The `OpportunityCreateIn`, `OpportunityUpdateIn`, `OpportunityOut` class names do not conflict with any existing model name (confirmed by searching `models.py` — no `Opportunity*` prefix exists).

### 8.5 Production table provisioning

In a production AWS environment, the two new DynamoDB tables must be provisioned before deploying any code that reads or writes them. Because `SALES_PIPELINE_ENABLED` defaults to `false`, deploying this ticket to production is safe before table creation: the `T.sales_opportunities` and `T.sales_quotas` handles are initialized lazily and never exercised. The recommended sequence is:

1. Deploy OPP-001 code (flag off).
2. Create the DynamoDB tables via Terraform / CloudFormation with the correct GSI definitions and `AttributeDefinitions` for `close_date` (N) and `created_at` (N).
3. Set `SALES_PIPELINE_ENABLED=true` only after tables are confirmed active.

## 10. Open Questions / Assumptions

**Q1: Should `close_date` accept `0` or require a value in the future?**  
Assumption: `0` is allowed because imported/migrated historical deals from SuiteCRM may have `close_date=0` or an unset date. If a "must be in the future" constraint is desired, it should be added in OPP-002 at the service layer (not the model layer) so it can be bypassed by admin data-import operations.

**Q2: Should `OpportunityOut` include `deleted_at`?**  
Assumption: No. Soft-deleted opportunities are treated as non-existent from the API perspective (OPP-002 returns 404 for deleted items). Including `deleted_at` in `OpportunityOut` would leak implementation details to clients. The attribute exists only in DynamoDB storage.

**Q3: Should `OPPORTUNITY_STAGES` be a Python `Enum` rather than a tuple of strings?**  
Assumption: Tuple of strings, matching the precedent of `OPPORTUNITY_STAGES` in the ticket source and the approach used by OPP-003's configurable stage list. An `Enum` would conflict with OPP-003, which stores admin-configured stage keys in DynamoDB that may differ from the compile-time defaults.

**Q4: Where exactly should the new models land in `app/models.py`?**  
Assumption: After any existing Contacts-domain models and before the Broadcast-domain models. The file is ~14,633 lines; the exact line number is not pinned here because it will shift with each merged ticket. The semantic neighborhood (near Contacts) is the stable anchor.

**Q5: GSI projection type for `GSI_DIRECT`?**  
Assumption: `ALL` projection (the DynamoDB Local default when `ProjectionType` is omitted from the `TableDef` creation helper). This matches every other GSI in `scripts/local-ddb-init.py`. For production cost optimization, a `KEYS_ONLY` or `INCLUDE` projection could be used for `GSI_DIRECT` — this is an operational decision, not a functional requirement of OPP-001.

**Q6: Should a `TEAM#{team_id}` shape for the `sales_quotas` table be formally defined now?**  
Assumption: The shape is reserved (noted in the table layout) but no models or service functions are written for team quotas in OPP-001 or OPP-005. Team quotas are a future extension.
