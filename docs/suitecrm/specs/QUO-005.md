# QUO-005 — Standalone invoice lifecycle — draft/sent/paid/overdue/void and manual B2B invoice creation

**Area**: Quotes, Products, Contracts & PDF Templates (AOS)
**Type**: Feature  **Priority**: P2  **Estimate**: 3d
**Flag**: `AOS_STANDALONE_INVOICES_ENABLED` (default `"0"`, off)

---

## 1. Summary & Goal

QUO-005 extends the existing invoice system (`app/services/invoices.py`, `app/routers/invoices.py`) with three complementary capabilities that close the AOS-INV-001 and AOS-INV-VOID gaps from the SuiteCRM gap analysis:

1. **Extended invoice lifecycle**: five meaningful status values — `draft`, `sent`, `paid`, `overdue`, and `void` — added alongside the existing `generated` and `emailed` statuses. A new `update_invoice_status(user_sub, invoice_number, new_status)` service function enforces the allowed transition graph.

2. **Manual B2B invoice creation**: a new admin-only endpoint `POST /ui/admin/invoices/manual` lets sales staff mint a `draft` invoice for any buyer (platform user or external address), with explicit line items, payment terms, and a computed `due_date`. This closes the gap where only auto-generated billing-event invoices existed.

3. **Overdue detection background task**: a periodic checker (`check_overdue_invoices`) queries all `sent` invoices system-wide and marks those whose `due_date` has passed as `overdue`, then optionally emails the buyer. This is disabled by default behind its own sub-flag.

A **void endpoint** (`POST /ui/invoices/{invoice_number}/void`) is accessible to the invoice owner for `draft` and `sent` invoices; admins may void `paid` invoices (triggering a ledger reversal via `billing_shared.new_ledger_entry`).

With `AOS_STANDALONE_INVOICES_ENABLED=0` every new route returns 404, the background task is a no-op, and the existing `create_invoice_safe` path is byte-for-byte unchanged.

## 2. Context & Current State

### Existing invoice infrastructure (all claims grounded in code)

**`create_invoice(...)` signature** (`app/services/invoices.py:272–286`): accepts `user_sub`, `invoice_type` (must be in `VALID_TYPES = {"tip","unlock","subscription","shop","deposit"}` at `invoices.py:33`), `amount_cents`, `line_items`, optional `tax_cents`, `seller_*`, `buyer_*`, `payment_method_summary`, and `currency`. Returns a serialized dict. The `"b2b"` type needed for manual invoices does not yet exist in `VALID_TYPES`; this spec adds it.

**`_next_invoice_number()` counter** (`invoices.py:82–92`): atomic DynamoDB `ADD` on `pk="COUNTER" sk="SEQ"` in `T.invoices`; returns `INV-{year}-{seq:05d}`. Reused unchanged.

**PDF rendering** (`invoices.py:103–143`): `_render_pdf(lines)` produces minimal PDF-1.4 bytes from a list of text strings with no external dependencies. `_render_invoice_lines(record)` at `invoices.py:150–188` formats header, bill-to/seller blocks, a line-item table, subtotal, tax, and total. This spec extends `_render_invoice_lines` to also emit `Due Date:` and `Terms:` lines when those fields are present on the record.

**S3 PDF storage** (`invoices.py:195–209`): `_store_pdf(user_sub, invoice_number, pdf)` uploads via `app.core.aws_clients.s3_client()` to `S.filemgr_bucket`; `_fetch_pdf(s3_key)` retrieves. Both are reused unchanged.

**`_serialize(record)` serializer** (`invoices.py:218–245`): converts a DDB item to a JSON-safe dict matching `InvoiceOut`. The serializer currently projects exactly the fields listed; new fields (`payment_terms_days`, `due_date`, `voided_at`) must be added here.

**`email_invoice(user_sub, invoice_number)` function** (`invoices.py:455–489`): renders the invoice lines as plain text, calls `send_alert_email([to_email], subject, body)` (dev: writes to `S.dev_email_log`; prod: dispatches via SES), then updates `status="emailed"` and `emailed_at`. The void-email and overdue-email paths reuse `send_alert_email` from the same module (`app/services/alerts.py:459`).

**DynamoDB table + GSIs** (`scripts/local-ddb-init.py:2269–2278`): `TableDef` for `invoices` uses `pk/sk`, GSI1 (`GSI1PK=USER#{sub}#TYPE#{type}` / `GSI1SK=created_at`), GSI2 (`GSI2PK=ADMIN_ALL` / `GSI2SK=created_at`), with `attr_types={"GSI1SK":"N","GSI2SK":"N"}`. This spec adds a GSI3 for the overdue checker; see Section 3.

**`T.invoices` handle** (`app/core/tables.py:547`): `invoices=_safe_table(S.invoices_table_name)`. The `_FloatSafeTable` proxy at `tables.py:29` coerces float to Decimal on write; all new write paths go through this handle.

**`admin_list_invoices` admin scan** (`invoices.py:492–522`): queries GSI2 with `GSI2PK="ADMIN_ALL"` and `ScanIndexForward=False`. The overdue checker reuses this scan pattern to find all `sent` invoices.

**Billing ledger** (`app/services/billing_shared.py:224–259`): `new_ledger_entry(*, key_name, key_value, entry_type, amount_cents, state, reason, meta, extra)` mints a ledger row in `T.billing`. **CORRECTION (one-mechanism refund/reversal)**: the canonical platform refund/void pattern is NOT "a single negative-amount `new_ledger_entry`". The reference implementations — `billing.refund_payment` and `returns_rma._refund` (`app/services/returns_rma.py:452-509`) — use the **three-primitive combo**: (1) `new_ledger_entry(entry_type="adjustment", reason="refund"/"void", amount_cents=+amount, state="settled", extra={"provider": ...})` with a **positive** amount and the standard `"adjustment"` type (NOT a bespoke `"invoice_void_reversal"` type or a negative amount); (2) `apply_balance_delta(T.billing, pk, {"payments_settled_cents": -amount}, currency=...)` — this is what actually moves the user's balance and MUST be called (QUO-005's original draft omitted it, leaving balances stale); (3) `settle_or_reverse_ledger(T.billing, "pk", pk, original_ledger_sk, "reversed")` at `billing_shared.py:262` to flip the original entry. QUO-005 void-of-paid must mirror this exact sequence — do not fork. The original ledger sk is looked up from the invoice's `ledger_entry_id`/linkage.

**Audit events** (`app/services/alerts.py:644`): `audit_event(event, user_sub, request=None, **fields)` writes to `T.alerts`. All status transitions emit `audit_event("invoice.status_changed", user_sub, invoice_number=..., old_status=..., new_status=...)`.

**`require_admin_or_root` dependency** (`app/auth/policy.py:67`): raises HTTP 403 for `role < ADMIN`. Used as `Depends(require_admin_or_root)` on `POST /ui/admin/invoices/manual` and the admin-void override path.

**`require_ui_session` dependency** (`app/services/sessions.py:330`): returns `{"user_sub": str, "role": Role, ...}`. Used on all user-facing endpoints.

**Background task pattern** (`app/services/billing_dunning.py:274–302`): `billing_dunning_loop()` is an `async def` function that calls `register_task(name, interval, enabled, description)` from `app/services/job_registry`, then loops with `await asyncio.sleep(interval)`. `start_billing_dunning_task()` creates the asyncio task only when the flag is on; when off, it calls `register_task(..., enabled=False)` for observability. Registered in `app/main.py:650` via `app.add_event_handler("startup", start_billing_dunning_task)`. The overdue checker follows this exact pattern.

**Settings location** (`app/core/settings.py:2567–2569`): `invoices_enabled`, `invoices_table_name`, `invoices_tax_bps` are the last three existing invoice settings. New `aos_standalone_invoices_*` settings are appended immediately after line 2569.

**QUO-003 coordination**: QUO-003 (`docs/suitecrm/specs/QUO-003.md`) also creates `status="draft"` invoices from the `convert-to-invoice` path. Both tickets share the same `status` field extension; QUO-003 must be merged before or alongside QUO-005 to avoid conflicts on the `InvoiceOut` model and `_serialize`.

### What does not yet exist

- Status values `draft`, `sent`, `paid`, `overdue`, and `void` are not in any code path; the only existing statuses set by service code are `"generated"` (at `invoices.py:335`) and `"emailed"` (set in `email_invoice` at `invoices.py:483`, not 481), plus `"refunded"` referenced in `_render_invoice_lines` at `invoices.py:156`.
- `payment_terms_days`, `due_date`, and `voided_at` fields do not exist on DDB items or `InvoiceOut`.
- No endpoint creates invoices from an admin form; all invoices are auto-generated from billing events via `create_invoice_safe`.
- No GSI exists for querying by status; the overdue checker needs one.
- `"b2b"` is not in `VALID_TYPES` at `invoices.py:33`.
- `InvoiceLineItemOut` (`app/models.py:9539–9542`) has `description`, `quantity`, and `amount_cents` but no `unit_price_cents` field. The ticket spec adds it.

## 3. Data Model

### Existing `invoices` table — additive attribute additions only

The DDB table (`pk=USER#{user_sub}`, `sk=INV#{invoice_number}`) at `scripts/local-ddb-init.py:2269` is extended with new optional attributes on the item. No existing attribute is removed or renamed.

**New attributes on invoice items**:

| Attribute | Type | Description |
|---|---|---|
| `payment_terms_days` | N | Payment terms in days (e.g. 30). Present on manual and converted invoices. |
| `due_date` | N | Unix timestamp: `created_at + payment_terms_days * 86400`. Used by overdue checker. |
| `voided_at` | N | Unix timestamp set when invoice is voided. |
| `void_reversal_ledger_sk` | S | The DDB sk of the reversal ledger entry, stored for idempotency on re-void. |
| `GSI3PK` | S | `"STATUS#sent"` / `"STATUS#overdue"` / `"STATUS#draft"` — denormalized for overdue scanner. Set only when `AOS_STANDALONE_INVOICES_ENABLED=1`. Absent on auto-generated `generated`/`emailed` items. |
| `GSI3SK` | N | `due_date` (numeric). Present when `GSI3PK` is set. |

**GSI3 addition to `TableDef`** in `scripts/local-ddb-init.py` (appended to the existing `gsi` list at line 2273):

```python
TableDef(
    _resolve_table_name(S.invoices_table_name, "invoices"),
    "pk",
    "sk",
    gsi=[
        {"index_name": "GSI1", "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "GSI2", "partition_key": "GSI2PK", "sort_key": "GSI2SK"},
        {"index_name": "GSI3", "partition_key": "GSI3PK", "sort_key": "GSI3SK"},
    ],
    attr_types={"GSI1SK": "N", "GSI2SK": "N", "GSI3SK": "N"},
)
```

`attr_types` must include `"GSI3SK": "N"` per the project gotcha ("DynamoDB numeric GSI sort keys") — omitting it causes a `ValidationException` when the overdue checker queries by `due_date` range.

**COUNTER/SEQ row**: unchanged; already exists at `pk="COUNTER" sk="SEQ"`.

**`"b2b"` added to `VALID_TYPES`** (`invoices.py:33`): `VALID_TYPES = {"tip","unlock","subscription","shop","deposit","b2b"}`. This allows `create_invoice(invoice_type="b2b", ...)` to proceed without the early-return at `invoices.py:298`. Existing auto-generated paths never pass `"b2b"`.

### No new tables

All data lives in the existing `invoices` table. The `billing` table is written by `new_ledger_entry` for void reversals but its schema is unchanged.

## 4. API / Service Design

### 4.1 Service layer additions — `app/services/invoices.py`

#### `_require_standalone_enabled() -> None`
```python
def _require_standalone_enabled() -> None:
    from app.core.settings import S
    if not S.aos_standalone_invoices_enabled:
        raise HTTPException(404, "Standalone invoices not enabled")
```
Called at the top of every new endpoint handler in the router (same pattern as `_require_enabled()` at `invoices.py:22`).

#### `STANDALONE_STATUSES` and transition graph
```python
STANDALONE_STATUSES = {"draft", "sent", "paid", "overdue", "void"}

_ALLOWED_TRANSITIONS: Dict[str, Set[str]] = {
    "draft":    {"sent", "void"},
    "sent":     {"paid", "overdue", "void"},
    "overdue":  {"paid", "void"},
    "paid":     set(),          # user cannot transition; admin can void (see below)
    "void":     set(),          # terminal
    "generated": {"void"},      # existing auto-generated invoices may be voided
    "emailed":  {"void"},
}
```

#### `update_invoice_status(user_sub, invoice_number, new_status, *, admin=False, request=None) -> Dict[str, Any]`
```python
def update_invoice_status(
    user_sub: str,
    invoice_number: str,
    new_status: str,
    *,
    admin: bool = False,
    request: Any = None,
) -> Dict[str, Any]:
```
- Reads the raw item via `_get_raw(user_sub, invoice_number)`; raises `HTTPException(404)` if not found.
- Reads `old_status = item.get("status", "generated")`.
- Checks `new_status in _ALLOWED_TRANSITIONS.get(old_status, set())`. If `new_status == "void"` and `old_status == "paid"` and `admin is False`, raises `HTTPException(409, "paid invoices may only be voided by an admin")`.
- **Void reversal** (CORRECTED — reuse the canonical 3-primitive combo from `returns_rma._refund` / `billing.refund_payment`, NOT a single negative entry): if `old_status == "paid"` and `new_status == "void"`:
  1. `led_sk, led_item = billing_shared.new_ledger_entry(key_name="pk", key_value=item["pk"], entry_type="adjustment", amount_cents=_coerce_int(item.get("total_cents")), state="settled", reason="void", meta={"invoice_number": invoice_number}, extra={"provider": item.get("provider",""), "currency": item.get("currency","usd")})` — **positive** amount, `"adjustment"` type.
  2. `billing_shared.ddb_put(T.billing, led_item)`.
  3. `billing_shared.apply_balance_delta(T.billing, item["pk"], {"payments_settled_cents": -_coerce_int(item.get("total_cents"))}, currency=item.get("currency","usd"))` — actually moves the balance.
  4. If the invoice carries an originating `ledger_entry_id`, `billing_shared.settle_or_reverse_ledger(T.billing, "pk", item["pk"], original_ledger_sk, "reversed")`.
  Write `void_reversal_ledger_sk = led_sk` back onto the item for idempotency.
- Builds `UpdateExpression` to set `status`, `updated_at=now_ts()`, `voided_at=now_ts()` (when voiding), and clears `GSI3PK`/`GSI3SK` when transitioning to `void` or `paid` (so voided/paid invoices fall off the overdue scanner's index partition).
- When `new_status == "sent"` and the item has a `due_date` and the invoice was created with `AOS_STANDALONE_INVOICES_ENABLED=1`, writes `GSI3PK="STATUS#sent"` and `GSI3SK=due_date` onto the item to enroll it in the overdue scanner.
- Emits `audit_event("invoice.status_changed", user_sub, invoice_number=invoice_number, old_status=old_status, new_status=new_status)` via `alerts.audit_event`.
- Returns `_serialize(updated_item)` (re-reads after update for accuracy).

#### `create_manual_invoice(*, admin_user_sub, buyer_user_sub, buyer_name, buyer_email, billing_address, line_items, currency, payment_terms_days, notes) -> Dict[str, Any]`
```python
def create_manual_invoice(
    *,
    admin_user_sub: str,
    buyer_user_sub: str,          # may be "" for external buyer
    buyer_name: str,
    buyer_email: str,
    billing_address: Dict[str, str],
    line_items: List[Dict[str, Any]],
    currency: str = "usd",
    payment_terms_days: int = 30,
    notes: str = "",
) -> Dict[str, Any]:
```
- Validates `payment_terms_days >= 1` and `<= 365`.
- Computes `amount_cents = sum(li["unit_price_cents"] * li["quantity"] for li in line_items)`.
- Computes `tax_cents = (amount_cents * max(0, S.invoices_tax_bps)) // 10_000`.
- Calls `_next_invoice_number()` for a new `INV-YYYY-NNNNN`.
- Determines `owner_sub = buyer_user_sub if buyer_user_sub else admin_user_sub` (admin owns the invoice row when buyer is external).
- Builds the DDB item with `status="draft"`, `invoice_type="b2b"`, `payment_terms_days=payment_terms_days`, `due_date=created_at + payment_terms_days * 86400`, `billing_address=billing_address`, `notes=notes`, and `created_by_admin=admin_user_sub`. Sets `GSI1PK=f"USER#{owner_sub}#TYPE#b2b"`, `GSI1SK=created_at`, `GSI2PK="ADMIN_ALL"`, `GSI2SK=created_at`. Does **not** set `GSI3PK`/`GSI3SK` yet — the overdue scanner only picks up `sent` invoices.
- Normalizes `line_items`: each item carries `description`, `quantity`, `unit_price_cents`, `amount_cents=unit_price_cents*quantity`, and `tax_rate_bps`.
- Renders PDF via `_render_pdf(_render_invoice_lines(record))` where `_render_invoice_lines` is extended (see Section 5.1).
- Stores PDF via `_store_pdf(owner_sub, invoice_number, pdf)`.
- Writes item to `T.invoices` via `put_item`.
- Emits `audit_event("invoice.manual_created", admin_user_sub, invoice_number=invoice_number, buyer_email=buyer_email)`.
- Returns `_serialize(record)` (augmented with new fields; see Section 4.3).

#### `check_overdue_invoices() -> int`
```python
def check_overdue_invoices() -> int:
    """Scan GSI3 for sent invoices with due_date < now_ts().

    Returns the count of invoices marked overdue.
    Gated by S.aos_standalone_invoices_enabled; no-op when off.
    """
```
- Short-circuits to `0` if `not S.aos_standalone_invoices_enabled`.
- Queries `T.invoices` on GSI3 with `KeyConditionExpression="GSI3PK = :pk AND GSI3SK < :now"` and `ExpressionAttributeValues={":pk": "STATUS#sent", ":now": now_ts()}`. Loops via `LastEvaluatedKey` until exhausted (DDB FilterExpression does not reduce page size — CLAUDE.md gotcha).
- For each item, calls `update_invoice_status(item["user_sub"], item["invoice_number"], "overdue")`.
- Optionally sends an overdue notification: calls `send_alert_email([buyer_email], f"Invoice {number} is now overdue", body)` where `body` is the plain-text invoice lines extended with an "OVERDUE" banner.
- Returns count of processed items.

#### `start_invoice_overdue_checker_task() -> None`
```python
def start_invoice_overdue_checker_task() -> None:
    from app.services.job_registry import register_task
    if not S.aos_invoice_overdue_checker_enabled:
        register_task("invoice_overdue_checker", 3600, enabled=False,
                      description="Marks sent invoices past due_date as overdue")
        return
    asyncio.create_task(_invoice_overdue_loop())
```

#### `_invoice_overdue_loop() -> None` (async)
Follows the exact pattern of `billing_dunning_loop` (`billing_dunning.py:274`): `register_task(name, interval, enabled=True)`, `while True: check_overdue_invoices(); await asyncio.sleep(interval)`. Interval = `S.aos_invoice_overdue_check_interval_seconds`.

## 5. Detailed Behavior & Edge Cases

### 5.1 `_render_invoice_lines` extension

`_render_invoice_lines(record)` (`invoices.py:150`) is extended after the `Date :` line:
```python
if record.get("payment_terms_days"):
    terms = int(record["payment_terms_days"])
    lines.append(f"Terms   : Net {terms}")
if record.get("due_date"):
    due_str = datetime.fromtimestamp(int(record["due_date"]), tz=timezone.utc).strftime("%B %d, %Y")
    lines.append(f"Due     : {due_str}")
if str(record.get("status")) == "void":
    lines.insert(2, "*** VOIDED ***")
if str(record.get("status")) == "overdue":
    lines.insert(2, "*** OVERDUE ***")
```
This is purely additive — auto-generated invoices never have `payment_terms_days` so these lines are silently skipped.

Also extend line-item loop: each `li` item now emits a `unit_price_cents` column if present.

### 5.2 Transition graph enforcement

Allowed caller-initiated transitions:

| From | To | Actor | Notes |
|---|---|---|---|
| `draft` | `sent` | owner | Emails buyer; enrolls in overdue scanner (GSI3) |
| `draft` | `void` | owner or admin | No ledger entry (never paid) |
| `sent` | `paid` | owner | Writes b2b_invoice_payment ledger entry |
| `sent` | `void` | owner or admin | No ledger entry (never paid) |
| `overdue` | `paid` | owner | Same as sent→paid |
| `overdue` | `void` | owner or admin | No ledger entry |
| `paid` | `void` | admin only | Writes invoice_void_reversal ledger entry (negative amount) |
| `generated` | `void` | owner or admin | Backward-compat: existing auto invoices can be voided |
| `emailed` | `void` | owner or admin | Same |
| any | `overdue` | background checker only | Not callable from the router |

Any other transition returns `HTTP 409 {"code": "invalid_transition", "from": ..., "to": ...}`.

### 5.3 Overdue checker — DDB scan safety

The checker queries GSI3 with a `KeyConditionExpression` range filter. Because DDB applies `FilterExpression` after fetching up to 1 MB (CLAUDE.md gotcha), the checker loops via `LastEvaluatedKey`:
```python
lek = None
while True:
    kwargs = {
        "IndexName": "GSI3",
        "KeyConditionExpression": "GSI3PK = :pk AND GSI3SK < :now",
        "ExpressionAttributeValues": {":pk": "STATUS#sent", ":now": now_ts()},
    }
    if lek:
        kwargs["ExclusiveStartKey"] = lek
    resp = T.invoices.query(**kwargs)
    for item in resp.get("Items", []):
        ...
    lek = resp.get("LastEvaluatedKey")
    if not lek:
        break
```
Already-overdue invoices do not have `GSI3PK="STATUS#sent"` (it was cleared on the `sent→overdue` transition), so they are never re-processed.

### 5.4 Void reversal idempotency

`update_invoice_status(..., "void")` checks for `item.get("void_reversal_ledger_sk")` before writing a new reversal ledger entry. If the field already exists the function skips the `new_ledger_entry` call and proceeds to update `status` / `voided_at`. This makes the void endpoint safe to retry (e.g. network timeout after DDB write but before HTTP response).

### 5.5 External-buyer invoice ownership

When `buyer_user_sub == ""`, the admin's `user_sub` is the DDB `pk` owner. The invoice appears in the admin's own invoice list (`GET /ui/invoices`) with `invoice_type="b2b"`. Buyer-facing delivery is via the emailed PDF. This matches the pattern used by the existing `email_invoice` path which falls back to the user's profile email when `buyer_email` is absent.

### 5.6 `"b2b"` type in `list_invoices` and `admin_list_invoices`

`list_invoices` queries GSI1 when `invoice_type` is provided (`invoices.py:409–412`). Adding `"b2b"` to `VALID_TYPES` means `type=b2b` query params now work correctly for pagination. No other change is needed in the list/admin-list paths.

### 5.7 PDF regeneration on download (cache miss path)

`download_invoice_pdf` at `invoices.py:442` regenerates the PDF from the stored DDB item if the S3 object is missing. Since `_render_invoice_lines` is extended, regenerated PDFs for `draft`/`sent`/`overdue`/`void` invoices will include the new `Due Date:` and status banner lines automatically.

### 5.8 Concurrent send + overdue

If two processes simultaneously transition the same invoice (e.g. `sent→paid` by user and `sent→overdue` by checker), the `update_item` calls race. The last writer wins. This is acceptable: if a payment lands milliseconds before the overdue checker runs, the checker will simply skip the item because `status` will already be `paid` by the time the next check runs — and `GSI3PK` will have been cleared. No conditional locking is needed here, consistent with how `settle_or_reverse_ledger` operates.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity**: No `if S.dev_mode` branch is introduced in `invoices.py`. The `_store_pdf` / `_fetch_pdf` functions call `s3_client()` which is intercepted by moto in dev (the same in-process interception used by all other invoice paths). `send_alert_email` already has its own dev/prod branch at `alerts.py:462` — no additional branching is added. `new_ledger_entry` writes to `T.billing` in both envs; moto intercepts the DDB call in dev. The overdue checker loop runs against moto DDB in dev with `DEV_MODE=1`.

**Idempotency on void**: `void_reversal_ledger_sk` check (Section 5.4) ensures at-most-one ledger reversal per invoice. The `status` update is a plain `update_item` (last-writer-wins); a second `void` call on an already-void invoice returns `HTTP 409` from the transition graph check (`"void" not in _ALLOWED_TRANSITIONS["void"]`).

**Idempotency on manual create**: the manual create path has no `ledger_entry_id` (there is no pre-existing ledger event), so the `_existing_for_ledger` idempotency check at `invoices.py:252` is bypassed. Callers are responsible for not double-submitting. The endpoint is idempotent in the sense that DDB `put_item` is always a new invoice number; if the admin wants to deduplicate they must check the response `invoice_number` and store it.

**CSRF**: `POST /ui/invoices/{number}/void`, `/send`, and `/pay` go through `require_ui_session` which enforces CSRF for cookie-authenticated requests (CLAUDE.md "CSRF" section). `POST /ui/admin/invoices/manual` goes through `require_admin_or_root` which calls `get_authenticated_user` — CSRF is enforced by the same session middleware for cookie-auth admin users. Bearer-token admin clients (e.g. CI scripts) skip CSRF.

**Ownership enforcement**: `update_invoice_status(user_sub, invoice_number, ...)` reads the item via `_get_raw(user_sub, invoice_number)` which queries `pk=USER#{user_sub}`, so a user cannot access another user's invoice by guessing the invoice number. Admin void uses a `user_sub` query parameter and calls the service with that sub — the admin must supply the correct `user_sub` for the invoice row.

**Void of paid invoice**: requires `admin=True`. The router endpoint `POST /ui/admin/invoices/{number}/void` is under `require_admin_or_root` (HTTP 403 for regular users). Regular users hitting `POST /ui/invoices/{number}/void` get `HTTP 409` from the service when `old_status == "paid"`.

## 8. Backward Compatibility & Migration

**Existing auto-generated invoices**: `create_invoice_safe` at `invoices.py:373` and every call site that uses it are unchanged. Existing DDB items have `status="generated"` or `status="emailed"` and no `payment_terms_days`, `due_date`, or `GSI3PK` attributes. The overdue checker queries `GSI3PK="STATUS#sent"` — items lacking `GSI3PK` are never returned by this query (DDB sparse index: only items with the GSI partition key attribute participate in the index). No backfill is needed.

**`InvoiceOut` model**: three new `Optional` fields default to `None`. Any consumer of `GET /ui/invoices` or `GET /ui/admin/invoices` that ignores unknown fields (standard practice) is unaffected. The `InvoiceListOut` wrapper is unchanged.

**`InvoiceLineItemOut`**: adding `unit_price_cents: int = 0` is additive; existing consumers receive `0` for auto-generated items that lack this attribute on DDB.

**GSI3 addition**: adding a new GSI to the table definition in `scripts/local-ddb-init.py` affects only new table creation (dev `just restart` flow). Existing DynamoDB Local data is wiped on restart per the project's clean-wipe workflow. In production, adding a GSI via `UpdateTable` is non-destructive (AWS backfills asynchronously); the overdue checker cannot be enabled (`AOS_INVOICE_OVERDUE_CHECKER_ENABLED=1`) until the GSI backfill completes, which is enforced operationally — not in code.

**QUO-003 merge coordination**: QUO-003 also adds `status="draft"` invoice support. The two specs are compatible: QUO-003 creates draft invoices from a quote conversion and this ticket adds manual creation, the lifecycle transition function, and the background checker. ## 10. Open Questions / Assumptions

1. **`"b2b"` vs `"manual"` type name**: the ticket spec does not name the `invoice_type` value for manual B2B invoices. This spec uses `"b2b"` as the canonical type string. If QUO-003's `convert-to-invoice` path also uses `"b2b"`, there is a naming collision in the GSI1 partition key that conflates converted-quote invoices with admin-created invoices. Alternative: use `"b2b_manual"` for admin-created and `"b2b_converted"` for QUO-003 conversions. Coordinate with QUO-003 author before implementation.

2. **Multi-currency void reversal**: `new_ledger_entry` does not currently carry a `currency` field explicitly (amounts are integers, currency is on the billing row). For B2B invoices in non-USD currency, the reversal entry should carry `extra={"currency": invoice["currency"]}`. Confirm with billing team.

3. **`sent→paid` for admin**: the spec currently limits the `/pay` endpoint to `require_ui_session` (invoice owner). Should admins also be able to record offline payment on behalf of the owner? If yes, add a `POST /ui/admin/invoices/{number}/pay?user_sub=...` endpoint under `require_admin_or_root`.

4. **Email template for overdue notifications**: the current `check_overdue_invoices` sends a plain-text body from `_render_invoice_lines`. If QUO-002 (AOS PDF Template engine) is live, the overdue notification should use an `email_template` with `module="invoice"` merge fields. This is a QUO-002 follow-up; the plain-text path is the safe default.

5. **DDB GSI3 in production**: adding GSI3 to an existing high-volume `invoices` table requires an `UpdateTable` API call followed by an async backfill. The overdue checker must not be enabled (`AOS_INVOICE_OVERDUE_CHECKER_ENABLED=0`) until GSI3 backfill is complete. Backfill status is checked via `DescribeTable`. This is an ops concern, not a code concern — document in the deployment runbook.

6. **`due_date` computation timezone**: `created_at + payment_terms_days * 86400` is timezone-naive (UTC seconds since epoch). DST does not affect Unix timestamps. This is consistent with the rest of the codebase (`now_ts()` returns a UTC integer). No change needed.
