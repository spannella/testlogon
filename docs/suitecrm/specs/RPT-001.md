## 1. Summary & Goal

RPT-001 is pure infrastructure scaffolding: it introduces the top-level `CRM_REPORTS_ENABLED` feature flag, the three new DynamoDB table-name settings, the three new DynamoDB table definitions with correct key schemas and GSIs, and the three new table handles on the `Tables` dataclass. No user-visible behaviour is added. Every subsequent RPT ticket (RPT-002 through RPT-009) declares this ticket as a prerequisite.

With the flag off (the default), the platform is byte-for-byte unchanged at runtime: no routes are registered, no tables are queried, and no background workers run. Only the DynamoDB tables themselves are created at stack-init time — table creation is idempotent (`just restart` calls `local-ddb-init.py` unconditionally).

### 2.3 DynamoDB table definition and creation pattern

`scripts/local-ddb-init.py` holds all table definitions as `TableDef` dataclass instances (line 28–35). The `TableDef` constructor accepts:
- `name` (resolved via `_resolve_table_name(S.<setting>, "<fallback>")`)
- `partition_key` (string; always type `S` unless overridden in `attr_types`)
- `sort_key` (optional)
- `gsi` (list of dicts with `index_name`, `partition_key`, `sort_key`)
- `attr_types` (dict of attribute-name → DynamoDB type code; defaults all to `S`)

`_attribute_definitions` (line 2496) merges declared key names and `attr_types` overrides before passing to `create_table`. Failing to declare a numeric GSI sort key in `attr_types` causes DynamoDB to store it as String, producing a `ValidationException` at query time (CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha). The existing `schedules-due-index` on the `AuditExports` table (line 1500) and the `kyc_risk_scores` table (lines 171–179) demonstrate the correct pattern for numeric `GSI1SK`.

The `_table_defs()` function (line 42) returns a list of all `TableDef` objects. The three new tables are appended at the end of this list, after the `returns` table (lines 2483–2492), which is currently the last entry.

## 3. Data Model

Three new DynamoDB tables are created. All follow single-table design: multiple row types share the same table, distinguished by their `sk` prefix. The `_FloatSafeTable` wrapper is used for all writes, so floats in `updated_at`, `created_at`, or any future numeric field are automatically coerced to `Decimal`.

### 3.1 `crm_reports`

Stores report definitions, their run results, and (in RPT-004) their associated schedules.

| Attribute | Type | Role |
|-----------|------|------|
| `report_id` | S | Partition key (PK) |
| `sk` | S | Sort key |
| `GSI1PK` | S | GSI partition key (`OWNER#{owner_sub}`) |
| `GSI1SK` | **N** | GSI sort key (`created_at`, Unix integer) |

Row types:
- **META row**: `sk = "META"` — full report definition: `name`, `description`, `module`, `fields` (JSON list), `conditions` (JSON list), `owner_sub`, `created_at` (int), `updated_at` (int), plus optional `group_by`, `aggregates`, `chart` added by RPT-003/RPT-005.
- **RUN row**: `sk = "RUN#{run_ts:010d}#{run_id}"` — last execution result: `output_rows` (JSON), `row_count`, `run_at` (int), `status` (`ok`|`error`).
- **SCHEDULE row** (RPT-004): `sk = "META"`, `report_id = "SCHEDULE#{schedule_id}"` — mirrors the `AuditExports` schedule pattern (`app/services/audit_export_schedule.py:10`). `GSI1PK = "RPT_SCHEDULES#ACTIVE"`, `GSI1SK = next_run_at` (numeric) for the `rpt-schedules-due-index` GSI.

GSIs:
- `owner-reports-index`: `GSI1PK` (S) / `GSI1SK` (N) — lists all reports for an owner, newest-created first. **`attr_types={"GSI1SK": "N"}` is mandatory.**
- `rpt-schedules-due-index`: `GSI1PK` (S) / `GSI1SK` (N) — same physical GSI, different `GSI1PK` value prefix (`RPT_SCHEDULES#ACTIVE`). Shared because DynamoDB GSIs are table-wide sparse indexes; schedule rows project into the same GSI with a different PK value, so they are never visible from the owner-reports query (different PK). **Same `attr_types={"GSI1SK": "N"}` covers both uses.**

`TableDef` entry for `scripts/local-ddb-init.py`:
```python
TableDef(
    _resolve_table_name(S.crm_reports_table_name, "crm_reports"),
    "report_id",
    "sk",
    gsi=[
        {"index_name": "owner-reports-index",    "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "rpt-schedules-due-index", "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
    ],
    attr_types={"GSI1SK": "N"},
),
```

Note: DynamoDB does not allow two GSIs on the same physical attribute pair unless they are actually the same index. Because both index names use identical PK/SK attribute names (`GSI1PK` / `GSI1SK`), the local DynamoDB init must declare only one GSI with one of the two names; the second logical access pattern reuses it via a different `GSI1PK` value. **Declare only `owner-reports-index` in the `TableDef`; RPT-004 references this same index under the name `rpt-schedules-due-index`.** Since local DynamoDB Local and the real DynamoDB both accept a single GSI serving both query patterns by virtue of different partition key values, this is correct. The `index_name` passed to `query()` calls must match the declared name — RPT-004's scheduler queries `owner-reports-index` with `GSI1PK = "RPT_SCHEDULES#ACTIVE"`. This is consistent with how the audit export scheduler queries the `schedules-due-index` on the `AuditExports` table.

Revised recommended approach: declare one GSI (`owner-reports-index`) with attributes `GSI1PK`/`GSI1SK`; the RPT-004 scheduler uses the same index. This avoids the DynamoDB constraint that prevents two GSIs with identical key attributes.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off guarantees

When `S.crm_reports_enabled` is `False` (the default), the platform behaviour is byte-for-byte identical to pre-RPT state:
- No CRM routers are registered in `create_app()` (`app/main.py`). The RPT-002 router factory performs the `if not S.crm_reports_enabled: return 404` check at the handler level (per cross-cutting constraint `CRM_REPORTS_TICKETS.md:12`), but since RPT-001 registers no routers, the 404 behavior is achieved by the routes simply not existing.
- `T.crm_reports`, `T.crm_dashboards`, and `T.crm_saved_searches` are created as live boto3 table handles at module import time — this is unavoidable since `T` is a module-level singleton. However, the handles are never accessed unless a downstream service function is called, and no downstream service functions are imported or invoked with the flag off. Boto3 table handles are lightweight client objects; merely holding a reference to `T.crm_reports` does not issue any DynamoDB call.
- No startup tasks are registered by RPT-001.

### 5.2 Table creation idempotency

`scripts/local-ddb-init.py` wraps each `create_table` call with `_retry_transient_ddb_call` (line 2588) and handles `ResourceInExistedException` by logging and continuing. Running `just restart` (which calls `local-ddb-init.py`) on a stack that already has the three tables is a no-op: the existing tables and GSIs are left intact. This is safe because RPT-001 never modifies existing tables — it only adds new ones.

### 5.3 Table-name configurability

All three table names are injected from environment variables with safe defaults. In multi-tenant or multi-environment deployments, operators can set `CRM_REPORTS_TABLE_NAME=prod-crm-reports` etc. without changing code. The `_resolve_table_name(S.crm_reports_table_name, "crm_reports")` pattern in `local-ddb-init.py` ensures the same name is used for both table creation and runtime access.

### 5.4 Numeric GSI sort key correctness

All three new tables carry a `GSI1SK` sort key holding a Unix integer timestamp (`created_at`). All three `TableDef` entries include `attr_types={"GSI1SK": "N"}`. Omitting this causes DynamoDB Local (and AWS DynamoDB) to treat the attribute as type S, which produces a `ValidationException` when querying with an integer `KeyConditionExpression`. This bug is documented in `CLAUDE.md` ("DynamoDB numeric GSI sort keys" gotcha) and is present in the existing `schedules-due-index` on `AuditExports` (line 1500–1502 of `scripts/local-ddb-init.py`).

### 5.5 GSI attribute name collision with existing tables

The attribute names `GSI1PK` and `GSI1SK` are already used by many other tables (e.g., `sticker_collections` at line 83, `delegates` at line 1716). Since DynamoDB attribute names are table-scoped, there is no collision. The same generic `GSI1PK`/`GSI1SK` convention is consistently used across the codebase for single-table GSIs.

### 5.6 `_FloatSafeTable` and `created_at` as `int`

`now_ts()` (`app/core/time.py`) returns a Python `int` (Unix seconds). When written to DynamoDB as the `created_at` attribute, `int` passes through `_to_decimal` unchanged (only `float` is coerced). The `GSI1SK = created_at` sort key will be stored as DynamoDB Number type `N`, consistent with the `attr_types` declaration. No additional coercion is needed.

### 5.7 `just restart` sequence

`just restart` calls `scripts/dev.sh restart`, which:
1. Stops the backend and frontend.
2. Calls `scripts/local-stack-up.sh` (starts DynamoDB Local, moto, Stripe mock, KMS mock).
3. Calls `scripts/local-ddb-init.py` — this is where the three new tables are created.
4. Restarts the backend.
5. Re-seeds E2E sessions.

There is no separate migration step. The three tables exist from the first `just restart` after this ticket lands.

Gating table handle creation on a flag would require conditional dataclass fields or a factory function, neither of which is used elsewhere. Since holding a boto3 Table reference issues no network calls, unconditional creation is safe and consistent.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

All three DynamoDB tables use the same `TableDef` schema in both `local-ddb-init.py` (dev, moto/DynamoDB Local) and the production CloudFormation/Terraform table definitions. There is no `if S.dev_mode` branch anywhere in this ticket. The `_FloatSafeTable` proxy wraps the moto-backed Table resource identically to a real AWS DynamoDB Table resource. This is consistent with SECOPS-007.

### 7.2 Idempotency of table creation

`create_table` calls in `local-ddb-init.py` catch `ResourceInExistedException` and continue. Re-running the init script on a stack with the tables already present is a no-op. This is verified by the existing test suite (`just restart` is called repeatedly in CI).

### 7.3 Security considerations for RPT-001

RPT-001 introduces no endpoints, no data access, and no auth logic. The security surface added by this ticket is zero. The tables are accessible only through the standard AWS IAM credentials (`AWS_ACCESS_KEY_ID=test` in dev, IAM role in prod); there is no public endpoint.

The `crm_reports_enabled` flag defaults to `False`. An operator must explicitly set `CRM_REPORTS_ENABLED=1` to enable any CRM Reports functionality. This prevents accidental exposure of the feature on a production stack before it is ready.

### 7.4 No secrets introduced

No KMS keys, HMAC secrets, or API keys are introduced by this ticket. Downstream tickets (e.g., RPT-004 for email delivery) reuse the existing `alerts.send_alert_email` path, which already has its own secret management.

## 8. Backward Compatibility & Migration

### 8.1 No existing data at risk

The three new tables are created empty. No existing data is read, written, or migrated by this ticket. No existing table schemas are modified.

### 8.2 No router changes

No existing routers in `app/main.py` are modified. No existing route paths conflict with the future `/ui/crm/reports/*` and `/ui/crm/dashboard/*` namespaces.

### 8.3 `Settings` dataclass is frozen

Python `@dataclass(frozen=True)` prevents attribute mutation at runtime. Adding new fields at the end of the dataclass definition is backward-compatible: all existing attribute accesses by name are unaffected. The `Settings` singleton `S` is reconstructed on each `import app.core.settings` (module-level `S = Settings()`), so the new fields are automatically populated from environment variables on the next process restart.

### 8.4 `Tables` dataclass is frozen

Same reasoning applies. Adding three fields to the end of the `Tables` dataclass and the `T = Tables(...)` call is a pure extension. Existing code that accesses `T.tickets`, `T.billing`, etc. is unaffected.

### 8.5 Production deployment sequence

In production:
1. Deploy the new `Settings` and `Tables` code (the table handles are created lazily by boto3; if the DynamoDB tables don't exist yet, the handles are still valid — boto3 only validates the table exists on the first actual DynamoDB call).
2. Run `local-ddb-init.py` equivalent (a `create_table` migration step in CI/CD) to create the three new tables.
3. The `CRM_REPORTS_ENABLED` flag remains `"0"` until all downstream RPT tickets are deployed and tested.

There is no need for a data backfill migration.

## 10. Open Questions / Assumptions

1. **Single GSI for both owner queries and schedule queries** — The ticket text in `CRM_REPORTS_TICKETS.md` (RPT-004, line 207) says the schedule rows use `GSI1PK = "RPT_SCHEDULES#ACTIVE"` and the same `GSI1SK` numeric sort. This spec assumes a single `owner-reports-index` GSI on `crm_reports` serves both access patterns (different `GSI1PK` values isolate the two query types). If DynamoDB Local requires separate GSI names for separate query patterns even with identical key attributes, RPT-001 should declare two GSIs with distinct names but identical key attributes. This is valid DynamoDB (multiple GSIs with different names but same key schema are legal). The implementation team should verify with a DynamoDB Local test.

2. **`just restart` pre-existing table handling** — If a developer's local stack was set up before RPT-001 landed, the first `just restart` after merging will create the three new tables. No manual migration is needed. However, if the developer had previously run a partial migration (e.g., created `crm_reports` manually with a wrong key schema), `just restart` will silently skip creation (idempotent). The developer would need to manually drop the table and re-run init. This is a known limitation of the idempotent init pattern.

3. **Prod table provisioning** — The three new tables are DynamoDB on-demand billing mode (PAY_PER_REQUEST) unless overridden. Confirm with the platform team that PAY_PER_REQUEST is the standard provisioned mode for new tables (consistent with all other tables in the codebase, none of which specify `BillingMode`; DynamoDB Local defaults to PROVISIONED with 5 RCU/WCU, which is correct for local dev).

4. **`crm_reports` table dual-purpose** — Storing both report definitions and schedule rows in the same table (single-table design) follows the `AuditExports` table precedent (`app/services/audit_export_schedule.py:9–10`). If the report schedule access pattern grows complex, a dedicated `crm_report_schedules` table may be warranted. This is a post-RPT-004 concern.
