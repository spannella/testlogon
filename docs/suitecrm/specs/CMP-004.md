# CMP-004 — Unsubscribe / opt-out link embedded in campaign emails

**Type:** Feature  **Priority:** P0  **Estimate:** 2d  
**Area:** Campaigns & Email Marketing  
**Source:** `docs/suitecrm/CRM_CAMPAIGNS_EXTRA_TICKETS.md` § CMP-004

---

## 1. Summary & Goal

CAN-SPAM (15 U.S.C. § 7704) and GDPR (Art. 21) both require that every commercial email carry a clear, working mechanism for the recipient to opt out of future messages. This ticket delivers that mechanism for testlogon's marketing campaign system.

The deliverables are:

1. **`app/services/marketing_unsubscribe.py`** — a new service module that mints HMAC-signed, time-limited, one-time-use unsubscribe tokens and consumes them at redemption time. The signing and consumption schemes are taken directly from the cart-recovery-link pattern (`app/services/cart_reminders.py:150–241`), and the opt-out write reuses the existing `set_reminder_preference` function at `cart_reminders.py:128`. No new DynamoDB table is introduced.

2. **`GET /ui/marketing/optout/{token}`** — a public (no auth), HTML-responding endpoint that verifies the token, writes the global opt-out row, and returns a human-readable confirmation page. The response is always HTTP 200 (never a redirect) to avoid triggering aggressive mail-scanner pre-fetches that would silently unsubscribe users before they click.

3. **Send-path extension** — `_try_send_one` in `app/services/marketing_campaigns.py` (MKT-009) calls `generate_unsubscribe_url(party_id, campaign_id)` and injects the resulting URL into both the plain-text email body and the CMP-002 HTML template merge-vars as `{{unsubscribe_url}}`.

Everything is additive and gated on `S.marketing_campaigns_enabled` (established by MKT-002). With the flag off, no new code path executes and the platform is byte-for-byte unchanged.

**Token consumption rows** (existing schema, no change):

| Attribute | Type | Value |
|-----------|------|-------|
| `pk` | S | `UNSUB#CONSUMED#{jti}` |
| `sk` | S | `META` |
| `consumed_at` | N | Unix timestamp |

The `attribute_not_exists(pk)` conditional-put pattern from `_mark_token_consumed` (cart_reminders.py:198) is replicated verbatim, using the new prefix. ## 4. API / Service Design

### 4.1 New service module: `app/services/marketing_unsubscribe.py`

```python
"""CAN-SPAM / GDPR one-click unsubscribe for marketing campaign emails.

Token scheme: identical to generate_recovery_link
(app/services/cart_reminders.py:150-224) — b64url(JSON_payload).b64url(HMAC-SHA256).
Opt-out write: delegates to set_reminder_preference from cart_reminders.py:128.
Consumption marker: UNSUB#CONSUMED#{jti} in T.cart_reminder_config (same table,
distinct key prefix from RECOVERY#CONSUMED# to avoid namespace collision).
"""
from __future__ import annotations

import hashlib
import hmac
import json
import uuid
from typing import Tuple

from app.core.crypto import b64url, b64url_decode
from app.core.settings import S
from app.core.tables import T
from app.core.time import now_ts

_UNSUB_CONSUMED_PK_PREFIX = "UNSUB#CONSUMED#"


def _unsub_secret() -> bytes:
    """Signing key: MARKETING_UNSUBSCRIBE_SECRET, falling back to
    UI_ACCESS_TOKEN_SECRET. Same fallback chain as cart recovery
    (cart_reminders.py:144–147). Both dev and prod use the same path —
    SECOPS-007 parity."""
    secret = S.marketing_unsubscribe_secret or "dev-unsub-secret"
    return secret.encode("utf-8")


def generate_unsubscribe_url(user_sub: str, campaign_id: str) -> str:
    """Mint a signed, time-limited, one-time-use unsubscribe URL.

    Token payload: {"sub": user_sub, "cid": campaign_id,
                    "exp": now + ttl_days*86400, "iat": now,
                    "jti": uuid4().hex}
    Signed with HMAC-SHA256(_unsub_secret(), JSON_payload_bytes).
    URL: {S.public_base_url}/ui/marketing/optout/{token}

    Mirror of generate_recovery_link at cart_reminders.py:214-224.
    """
    now = now_ts()
    payload = {
        "sub": user_sub,
        "cid": campaign_id,
        "jti": uuid.uuid4().hex,
        "exp": now + S.marketing_unsubscribe_ttl_days * 86400,
        "iat": now,
    }
    raw = json.dumps(payload, separators=(",", ":")).encode("utf-8")
    sig = hmac.new(_unsub_secret(), raw, hashlib.sha256).digest()
    token = f"{b64url(raw)}.{b64url(sig)}"
    base = S.public_base_url.rstrip("/")
    return f"{base}/ui/marketing/optout/{token}"


def verify_unsubscribe_token(token: str) -> Tuple[str, str]:
    """Verify signature, expiry, and one-time-use status.

    Returns (user_sub, campaign_id).
    Raises HTTPException(400) on any failure:
      - malformed token
      - bad signature
      - past exp
      - already consumed jti

    One-time-use is enforced by writing UNSUB#CONSUMED#{jti} to
    T.cart_reminder_config with attribute_not_exists(pk) conditional put,
    mirroring _mark_token_consumed at cart_reminders.py:198-211.
    """
    from fastapi import HTTPException

    try:
        raw_b64, sig_b64 = token.split(".", 1)
        raw = b64url_decode(raw_b64)
        sig = b64url_decode(sig_b64)
        expected = hmac.new(_unsub_secret(), raw, hashlib.sha256).digest()
        if not hmac.compare_digest(sig, expected):
            raise HTTPException(400, "invalid_unsubscribe_token")
        obj = json.loads(raw.decode("utf-8"))
        if not isinstance(obj, dict):
            raise HTTPException(400, "invalid_unsubscribe_token")
        if int(obj.get("exp", 0)) < now_ts():
            raise HTTPException(400, "expired_unsubscribe_token")
    except HTTPException:
        raise
    except Exception:
        raise HTTPException(400, "invalid_unsubscribe_token")

    jti = str(obj.get("jti") or "")
    if not jti:
        raise HTTPException(400, "invalid_unsubscribe_token")

    # One-time-use: atomic consume. Returns False if already consumed.
    try:
        T.cart_reminder_config.put_item(
            Item={
                "pk": f"{_UNSUB_CONSUMED_PK_PREFIX}{jti}",
                "sk": "META",
                "consumed_at": now_ts(),
            },
            ConditionExpression="attribute_not_exists(pk)",
        )
    except Exception:
        # ConditionalCheckFailedException means already consumed.
        # Any other DDB failure is treated the same — fail closed.
        raise HTTPException(400, "unsubscribe_token_already_used")

    return str(obj.get("sub") or ""), str(obj.get("cid") or "")


def opt_out_user(user_sub: str) -> None:
    """Write the global opt-out row using set_reminder_preference.

    Delegates entirely to app.services.cart_reminders.set_reminder_preference
    (cart_reminders.py:128) — a single OPTOUT#USER#{sub}/META row in
    T.cart_reminder_config that is already checked by is_user_opted_out
    (cart_reminders.py:95), which is the shared suppression gate for all
    marketing channels including campaign sends (MKT-009 _try_send_one).
    No per-channel granularity in MVP.
    """
    from app.services.cart_reminders import set_reminder_preference
    set_reminder_preference(user_sub, opted_out=True)
```

### 4.2 Public unsubscribe endpoint

**Router file:** `app/routers/marketing_campaigns.py` (created by MKT-011)  
**Router instance:** the no-auth `public_router` registered in `app/main.py` without a `require_ui_session` dependency (same router that hosts `GET /ui/marketing/t/{code}` from MKT-011 and `GET /ui/marketing/t/{code}/open.gif` from CMP-003)

```
GET /ui/marketing/optout/{token}
```

**Auth:** none — the signed token is the credential, matching the pattern of `GET /ui/shoppingcart/recover/{token}` at `app/routers/shoppingcart.py:268`.

**Response type:** `fastapi.responses.HTMLResponse` always at HTTP 200. Never a redirect. Rationale: mail scanners (Gmail, Outlook Safe Links) pre-fetch URLs in email bodies. A redirect to a confirmation page would cause the scanner to follow the chain and silently unsubscribe the user before they click. Returning a 200 HTML page with the unsubscribe confirmation at the requested URL avoids this.

**Handler logic:**

```python
@public_router.get("/ui/marketing/optout/{token}", response_class=HTMLResponse)
async def ui_marketing_optout(token: str) -> HTMLResponse:
    # 1. Verify token. On failure return soft-error HTML (200 — not 4xx).
    try:
        user_sub, campaign_id = verify_unsubscribe_token(token)
    except HTTPException:
        return HTMLResponse(content=_UNSUB_ERROR_HTML, status_code=200)

    # 2. Write opt-out. Idempotent: already-opted-out users get the
    #    success page; writing opted_out=True again is a no-op.
    try:
        opt_out_user(user_sub)
    except Exception:
        # DDB unavailable — still show success to avoid confusing the user.
        pass

    # 3. Best-effort audit event.
    try:
        from app.services.alerts import audit_event
        audit_event(
            "marketing.unsubscribe",
            user_sub,
            campaign_id=campaign_id,
        )
    except Exception:
        pass

    # 4. Return confirmation page.
    return HTMLResponse(content=_UNSUB_SUCCESS_HTML, status_code=200)
```

**HTML constants** (defined at module top, no external assets, no dependencies):

```python
_UNSUB_SUCCESS_HTML = """\
<!DOCTYPE html><html><head><meta charset="utf-8">
<title>Unsubscribed</title></head><body>
<p>You have been successfully unsubscribed from marketing emails.</p>
<p>This change may take up to 24 hours to take effect for emails already in transit.</p>
</body></html>"""

_UNSUB_ERROR_HTML = """\
<!DOCTYPE html><html><head><meta charset="utf-8">
<title>Link expired</title></head><body>
<p>This unsubscribe link has expired or has already been used.</p>
<p>If you continue to receive unwanted emails please contact support.</p>
</body></html>"""
```

Both pages are intentionally minimal — no CSS, no JavaScript, no external requests — so they render correctly in every mail client webview.

## 5. Detailed Behavior & Edge Cases

### 5.1 Token lifecycle

1. `_try_send_one` calls `generate_unsubscribe_url(party_id, campaign_id)` once per recipient per send attempt.
2. Each call mints a fresh token with a new `jti` (UUID4 hex). Multiple sends of the same campaign to the same recipient each produce a distinct token — preventing replay across campaigns.
3. A token is valid for `S.marketing_unsubscribe_ttl_days` (default 365) days from issuance.
4. On `GET /ui/marketing/optout/{token}`:
   - If the signature is invalid → error HTML (200).
   - If `exp < now_ts()` → error HTML (200).
   - If `UNSUB#CONSUMED#{jti}` already exists → error HTML (200) — idempotent at the HTTP layer, no double-unsubscribe.
   - If DDB `put_item` succeeds → opt-out row written, success HTML (200).
5. A second visit to the same token URL returns error HTML (200) after the `ConditionalCheckFailedException` fires — NOT the success HTML. This is intentional: if the user hits "back" and reloads, they see "link already used" rather than incorrectly implying the action is happening again.

### 5.2 Already opted-out users

When `is_user_opted_out(party_id)` returns `True` at step 4 of `_try_send_one` (MKT-009 spec, `docs/ofbiz/specs/MKT-009.md:315`), the send is suppressed before `generate_unsubscribe_url` is called. No token is minted for opted-out users because no email is sent.

If a user re-subscribes (future feature, not in scope) and a subsequent campaign sends them an email, a fresh token is minted for that send.

### 5.3 Mail-scanner pre-fetch protection

Mail scanners (Gmail Proxy, Outlook Safe Links, etc.) follow all URLs in email HTML bodies when delivering the message to the user's inbox. This would silently consume the one-time-use token before the user ever sees the email.

Mitigation strategy:
- The endpoint returns HTTP 200 HTML at the unsubscribe URL itself (no redirect). Scanners that follow redirects are stopped at the first hop.
- The endpoint does NOT perform the opt-out action unless `verify_unsubscribe_token` succeeds — and that function consumes the `jti`. The scanner's pre-fetch consumes the token without writing the opt-out row... wait: in the design above, `verify_unsubscribe_token` writes the consumption row AND then calls `opt_out_user`. This would silently opt the user out on scanner pre-fetch.

**Resolution (scanner-safe design):** The public endpoint uses a two-step confirmation flow:

- `GET /ui/marketing/optout/{token}` — verifies token validity (signature + expiry) WITHOUT consuming it, and returns a confirmation page with a POST form.
- `POST /ui/marketing/optout/{token}` — verifies AND consumes the token, writes opt-out, returns success HTML.

Mail scanners follow GET requests but never submit forms. This ensures the opt-out only fires on explicit human action.

**Updated endpoint design:**

```
GET  /ui/marketing/optout/{token}   → verify-only, return confirmation form HTML (200)
POST /ui/marketing/optout/{token}   → verify + consume + opt-out, return success HTML (200)
```

`verify_unsubscribe_token_readonly(token)` — a version of the verify function that checks signature + expiry but does NOT write the consumption row. Used by the GET handler to show a valid-looking confirmation page without consuming the token.

```python
def _verify_token_payload(token: str) -> dict:
    """Verify signature and expiry only. Does not consume jti.
    Returns payload dict. Raises HTTPException(400) on failure."""
    # identical to verify_unsubscribe_token up to the consumption step
    ...
```

The GET handler calls `_verify_token_payload` (no consumption). The POST handler calls the full `verify_unsubscribe_token` (with consumption). Both handlers return HTTP 200 HTML always.

### 5.4 Dry-run sends

MKT-009 `_try_send_one` with `dry_run=True` returns early before calling `write_alert` or `send_alert_email` (`docs/ofbiz/specs/MKT-009.md:380`). The `generate_unsubscribe_url` call must also be skipped in dry-run mode, both for performance (no DDB writes needed) and to avoid minting tokens that will never be delivered. Adjust `_try_send_one`:

```python
if dry_run:
    return (True, False)
unsubscribe_url = generate_unsubscribe_url(party_id, campaign_id)
# ... rest of send logic
```

### 5.5 Campaigns without an email address on file

In `_try_send_one`, if `get_profile(party_id)` returns no email, `send_alert_email` is not called (MKT-009 step 7). In this case, `generate_unsubscribe_url` is still called before the profile lookup — it mints a valid token, but the token is never delivered. This is harmless (the minted token expires unused). For efficiency, the call could be moved after the email check; however, keeping it before simplifies the `_build_message_body` call signature (which always receives `unsubscribe_url`). The minor overhead of one UUID generation per no-email recipient is acceptable.

### 5.6 Duplicate `{{unsubscribe_url}}` in HTML template

If the template author includes `{{unsubscribe_url}}` in their HTML template body (CMP-002), the merge-vars substitution replaces it. The footer injection logic (`_build_message_body`) checks `"{{unsubscribe_url}}" in template_item["body_html_template"]` before appending the default footer, so the footer is only injected when the template does not already contain the placeholder. This prevents a double unsubscribe link.

### 5.7 Flag-off behavior

When `S.marketing_campaigns_enabled` is `False`:
- `GET /ui/marketing/optout/{token}` returns HTTP 404 (gated by `_require_enabled()` in MKT-011's public router, matching the `promo_codes.py:40–43` pattern).
- `send_campaign` raises immediately (`docs/ofbiz/specs/MKT-009.md:402`). No tokens are minted.
- `generate_unsubscribe_url` is not called.
- The platform is byte-for-byte unchanged.

**Exception:** The opt-out endpoint should remain accessible even with the flag off, since a user may have received an email before the flag was turned off, and their token is still valid. To handle this, the GET/POST opt-out endpoints are placed on the public router WITHOUT the `_require_enabled()` guard. The token validity (signature + expiry) is the only gate. If the token is valid and the `jti` has not been consumed, the opt-out proceeds regardless of flag state. This matches the CMP-003 open-tracking pixel behavior: `GET /ui/marketing/t/{code}/open.gif` returns the GIF and skips `record_visit` when the flag is off (`docs/suitecrm/CRM_CAMPAIGNS_EXTRA_TICKETS.md:185`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/Prod parity

There are no `if S.dev_mode` branches in `app/services/marketing_unsubscribe.py`. The HMAC signing and DDB writes are identical in both environments. In dev, `opt_out_user` writes to the DDB Local instance at `localhost:8001` via the existing `T.cart_reminder_config` handle. In prod, the same code writes to AWS DynamoDB. This is identical to the pattern used by `generate_recovery_link` / `recover_cart` in `cart_reminders.py` (SECOPS-007).

The only dev-mode difference is in `send_alert_email` (alerts.py:459–468): dev mode logs the email body (including the unsubscribe URL) to `S.dev_email_log` instead of calling SES. This is the existing behavior of that function, not a CMP-004 addition.

### Idempotency

- **Token minting:** `generate_unsubscribe_url` is called once per `_try_send_one` invocation. If the same `(campaign_id, snapshot_ts, party_id)` triple is replayed (MKT-009 dedup hit), `_try_send_one` returns `(False, True)` before reaching the `generate_unsubscribe_url` call. A fresh token is only minted when a new email is actually sent.
- **Opt-out write:** `set_reminder_preference(user_sub, opted_out=True)` is a `put_item` (unconditional overwrite). Calling it twice for the same user writes the same row twice with an updated `updated_at`; this is idempotent at the semantic level (the user remains opted-out).
- **Token consumption:** The `attribute_not_exists(pk)` condition on `UNSUB#CONSUMED#{jti}` ensures that a given token can be consumed at most once, regardless of concurrent requests. The second attempt raises `ConditionalCheckFailedException`, which the handler translates to the error HTML page.

### Security

- **HMAC-SHA256 with compare_digest:** `hmac.compare_digest` (cart_reminders.py:176) prevents timing-oracle attacks on signature verification. CMP-004 uses the same call.
- **`jti` one-time-use:** UUID4 hex is 32 characters with 122 bits of randomness. Brute-force collision probability against the DDB consumption table is negligible.
- **Scanner pre-fetch protection:** The two-step GET/POST confirmation flow (Section 5.3) prevents mail scanners from silently unsubscribing users. Only an explicit POST (form submission) triggers the opt-out.
- **No user enumeration:** The error HTML page says "This link has expired or has already been used" for all failure modes (bad signature, expired, already consumed). It does not distinguish between them, preventing enumeration of valid `user_sub` values.
- **Token payload does not contain PII beyond `user_sub`:** The `user_sub` is already a pseudonymous identifier. The `campaign_id` is not sensitive. The payload is not encrypted (only signed), so its contents are readable by anyone who URL-decodes the token — but this is the same tradeoff made by cart recovery links and is acceptable for a non-financial action.
- **Secret fallback security:** If `MARKETING_UNSUBSCRIBE_SECRET` is unset in production, the fallback to `UI_ACCESS_TOKEN_SECRET` means that a compromise of one secret compromises both token types. Operators are advised to set a distinct `MARKETING_UNSUBSCRIBE_SECRET` in production. This matches the documented behavior of `cart_recovery_link_secret` (`settings.py:826`).

## 10. Open Questions / Assumptions

1. **Re-subscribe flow**: CMP-004 writes a global opt-out row but provides no re-subscribe mechanism. Users who opt out via the unsubscribe link cannot receive future campaign emails until an admin manually deletes their `OPTOUT#USER#{sub}/META` row or a future re-subscribe endpoint (not in scope) writes `opted_out=False`. This is acceptable for CAN-SPAM compliance (opt-out must be honored; re-subscribe is not legally required).

2. **List-level vs. global opt-out**: CMP-004 implements a global opt-out (all campaigns from the platform). SuiteCRM supports per-campaign and per-list opt-out granularity. Implementing per-campaign suppression would require a second DDB table with a composite key `(campaign_id, party_id)`. This is deferred to a future ticket; the single-row global opt-out is sufficient for CAN-SPAM compliance and is the same model used by the existing cart-reminders infrastructure.

3. **One-time-use vs. permanent link**: The spec uses one-time-use tokens following the cart-recovery-link pattern. A permanent token (no `jti`, no consumption) would avoid the "link already used" error on scanner pre-fetch if the GET/POST split (Section 5.3) is not implemented. The one-time-use design is chosen for security (replay prevention); the GET/POST split mitigates the scanner risk. This assumption should be validated with the product team.

4. **Platform name in HTML pages**: The success and error HTML pages say "marketing emails" generically, not the platform's brand name. There is no `S.platform_name` setting in `app/core/settings.py` (verified by `grep`). A future branding pass can add it; for now the generic copy is correct.

5. **Token length**: The JSON payload is approximately 120 bytes. The base64url-encoded token is approximately 200 characters, plus the 43-character HMAC signature. Total URL length: ~280 characters. Well within the 2000-character URL limit of all major email clients.
