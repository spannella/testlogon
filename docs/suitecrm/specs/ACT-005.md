# ACT-005 — Calendar yearly recurrence frequency

## 1. Summary & Goal

ACT-005 adds `YEARLY` as a supported recurrence frequency to the existing calendar event system. The change is a pure code extension: it widens the `RecurrenceRule.freq` enum from three values to four, adds the corresponding expansion branch in `_expand_rrule`, and emits the correct `RRULE:FREQ=YEARLY` property in the iCalendar helper `_build_ics`. No new DynamoDB tables, no background workers, no feature flags, and no new routes are required. The ticket is self-contained within two files (`app/models.py` and `app/routers/calendar.py`) and a new test module.

Goal: a user can create an event with `recurrence_rule: {freq: "YEARLY", interval: 1}`, retrieve that event's occurrences across a multi-year query window, export a standards-compliant `.ics` file that third-party calendars can import, and handle edge cases such as Feb-29 birthday events in non-leap years — all without breaking existing DAILY/WEEKLY/MONTHLY behaviour.

## 2. Context & Current State

### RecurrenceRule model

`app/models.py:1354–1361` defines:

```python
class RecurrenceRule(BaseModel):
    freq: Literal["DAILY", "WEEKLY", "MONTHLY"]
    interval: int = Field(default=1, ge=1)
    until_utc: Optional[str] = None
    count: Optional[int] = Field(default=None, ge=1)
    byday: Optional[List[Literal["MO","TU","WE","TH","FR","SA","SU"]]] = None
    bymonthday: Optional[List[int]] = None
    bysetpos: Optional[List[int]] = None
```

The `freq` field uses `Literal["DAILY", "WEEKLY", "MONTHLY"]`. Any event payload that includes `freq: "YEARLY"` is rejected by Pydantic validation with HTTP 422 before it reaches any router logic.

### `_expand_rrule` function

`app/routers/calendar.py:548–683` implements occurrence expansion. The function signature is:

```python
def _expand_rrule(
    series_start_utc: datetime,
    series_end_utc: datetime,
    rrule: RecurrenceRule,
    window_start: datetime,
    window_end: datetime,
) -> list[tuple[datetime, datetime]]:
```

It handles `DAILY` (lines 561–577), `WEEKLY` (lines 578–611), and `MONTHLY` (lines 612–682). The function terminates each branch either by `break` when the candidate exceeds `window_end` plus a look-ahead margin, or by returning early when `until_utc` or `count` limits are exhausted. An unrecognised `freq` value silently falls through all three `if/elif` blocks and returns the empty `occs` list at line 683.

The MONTHLY branch uses two inner helpers: `month_last_day` (computes the number of days in a given year/month) and `add_months` (does safe calendar-aware month arithmetic to avoid overflow). These helpers are reusable in spirit but are currently defined as closures inside the `MONTHLY` branch; the YEARLY branch cannot call them as-is and will define its own analogous logic.

### `_expand_event_occurrences` caller

`app/routers/calendar.py:686–728` calls `_expand_rrule` and overlays per-occurrence overrides and exdates. The caller is unchanged by this ticket.

### `_build_ics` function

`app/routers/calendar.py:2048–2074` generates an `.ics` file. The current implementation does not emit any `RRULE:` property for any frequency. For YEARLY events this means the exported ICS describes only the first occurrence and gives no recurrence signal to importing calendar applications. Fixing this is in scope for this ticket as it is specified in the acceptance criteria (`ICS download includes RRULE:FREQ=YEARLY`), and the ticket text notes it should match the WEEKLY/MONTHLY `RRULE:FREQ=` lines — those lines are not yet present in the codebase but are called for here. This ticket adds `RRULE` emission for all four frequencies: DAILY, WEEKLY, MONTHLY, and YEARLY.

### `_normalize_recurrence_rule` validator

`app/routers/calendar.py:396–409` validates `until_utc`, `bymonthday`, and `bysetpos` but has no frequency-specific logic. It does not need changes for YEARLY (the existing `until_utc` and `count` guards apply unchanged).

### Where `recurrence_rule` is stored and read

- `create_event` (line 1560–1581): calls `_normalize_recurrence_rule`, stores `recurrence_rule.model_dump()` on the DynamoDB item.
- `update_event` (lines 1774–1817): same pattern.
- `_event_out` (line 1011): reads `item.get("recurrence_rule")` and passes it directly through to `EventOut.recurrence_rule`.

No changes are needed in any of these three locations; they are codec-neutral with respect to `freq` value.

### Leap year handling — current absence

No leap-year logic exists anywhere in `_expand_rrule`. The MONTHLY branch clamps day overflows via `month_last_day` at line 613, but there is no corresponding logic for year advancement. The YEARLY branch must handle the Feb-29 case explicitly (see Section 5).

### Existing tests

`tests/test_calendar_routes.py` calls route handler coroutines directly via `asyncio.run` (the `run_async` helper at line 14), patches `T` via `SimpleNamespace`, and does not use `TestClient`. The new YEARLY test module uses the same pattern.

### 4.1 Model change — `app/models.py:1355`

```python

# After:

```

This is the only change to `app/models.py`. `EventCreateIn.recurrence_rule: RecurrenceRule | None` (line 1269), `EventUpdateIn.recurrence_rule: RecurrenceRule | None` (line 1311), and `EventOut.recurrence_rule: RecurrenceRule | None` (line 1289) all reference `RecurrenceRule` by type; they automatically accept and return `YEARLY` once the Literal is widened. No other model changes are needed.

### 4.2 `_expand_rrule` YEARLY branch — `app/routers/calendar.py`

Insert the following block immediately after the closing of the `MONTHLY` block at line 682 (before the final `return sorted(occs, ...)`):

```python
elif rrule.freq == "YEARLY":
    def _is_leap(year: int) -> bool:
        return year % 4 == 0 and (year % 100 != 0 or year % 400 == 0)

    def _clamp_feb29(year: int, month: int, day: int) -> int:
        """Return day, clamped to Feb-28 when month=2, day=29, and year is not a leap year."""
        if month == 2 and day == 29 and not _is_leap(year):
            return 28
        return day

    dt = series_start_utc
    base_month = series_start_utc.month
    base_day = series_start_utc.day
    while True:
        if until and dt > until:
            break
        if remaining is not None and remaining <= 0:
            break
        occ_start = dt
        occ_end = dt + duration
        if overlap(occ_start, occ_end, window_start, window_end):
            occs.append((occ_start, occ_end))
        if remaining is not None:
            remaining -= 1
        # Advance by interval years, preserving month/day/time
        next_year = dt.year + rrule.interval
        clamped_day = _clamp_feb29(next_year, base_month, base_day)
        dt = dt.replace(year=next_year, month=base_month, day=clamped_day)
        if dt > window_end + timedelta(days=366):
            break
```

**Why `timedelta(days=366)` look-ahead**: the DAILY branch uses `timedelta(days=1)` (line 576) as look-ahead because DAILY intervals are at most 1-day long. YEARLY intervals span up to 366 days (one full year plus leap margin), so the look-ahead must be `366` to prevent premature termination when `interval=1` and the next occurrence falls just outside the nominal window end.

**Why `base_month` / `base_day` variables**: `dt.replace(year=...)` preserves the month and day of `dt` as currently modified, but in the standard YEARLY case the anchor month/day is always the original series start (e.g., "every year on March 15"). Caching `base_month = series_start_utc.month` and `base_day = series_start_utc.day` before entering the loop ensures the anchor is stable even after clamping (e.g., a Feb-29 birthday clamped to Feb-28 in year N should still recur on Feb-29 in leap year N+4, not permanently shift to Feb-28).

### 4.3 `_build_ics` RRULE emission — `app/routers/calendar.py:2048`

The current `_build_ics` implementation (`lines 2048–2074`) writes no `RRULE:` property. This ticket adds RRULE emission for all four frequencies. The change is placed between the `SUMMARY:` line and `END:VEVENT`:

```python
# After line 2070 (the SUMMARY append) and before the final lines list:
rr_data = evt.get("recurrence_rule")
if rr_data:
    freq_val = rr_data.get("freq", "")
    interval_val = int(rr_data.get("interval", 1))
    rrule_parts = [f"FREQ={freq_val}", f"INTERVAL={interval_val}"]
    until_utc = rr_data.get("until_utc")
    if until_utc:
        rrule_parts.append(f"UNTIL={fmt_dt(until_utc)}")
    count_val = rr_data.get("count")
    if count_val:
        rrule_parts.append(f"COUNT={count_val}")
    byday = rr_data.get("byday")
    if byday:
        rrule_parts.append(f"BYDAY={','.join(byday)}")
    lines.append(f"RRULE:{';'.join(rrule_parts)}")
```

This covers all four frequencies in a single code path. It is placed before `END:VEVENT` per RFC 5545. For YEARLY events the emitted line will be, for example:

```
RRULE:FREQ=YEARLY;INTERVAL=1
```

or with a count limit:

```
RRULE:FREQ=YEARLY;INTERVAL=2;COUNT=5
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Standard yearly expansion

For an event starting `2024-03-15T10:00:00Z` with `freq=YEARLY, interval=1`, a query window of `[2024-01-01, 2027-01-01)` returns three occurrences: `2024-03-15`, `2025-03-15`, `2026-03-15`. The same window with `interval=2` returns two: `2024-03-15`, `2026-03-15`.

### 5.2 Feb-29 (leap year birthday) on a non-leap year

An event starting `2024-02-29T12:00:00Z` (2024 is a leap year). When `interval=1`:
- 2025 is not a leap year → `_clamp_feb29(2025, 2, 29)` returns `28` → occurrence is `2025-02-28T12:00:00Z`.
- 2026 is not a leap year → occurrence is `2026-02-28T12:00:00Z`.
- 2027 is not a leap year → occurrence is `2027-02-28T12:00:00Z`.
- 2028 is a leap year → `_clamp_feb29(2028, 2, 29)` returns `29` → occurrence is `2028-02-29T12:00:00Z`.

After a clamped year, the loop restores the canonical anchor (`base_day = 29`) so the next leap-year occurrence is correctly Feb-29, not Feb-28.

### 5.3 `until_utc` termination

When `rrule.until_utc` is set, the branch checks `if until and dt > until: break` before appending or advancing. This is the same guard as the DAILY branch (lines 565–566). The ICS emission also appends `UNTIL={fmt_dt(until_utc)}` so external calendar apps honour the series end.

### 5.4 `count` termination

When `rrule.count` is set, `remaining` is decremented after each occurrence is processed. The branch checks `if remaining is not None and remaining <= 0: break`. Again this mirrors the DAILY branch behaviour (lines 567–568).

### 5.5 Exdate and occurrence overrides

`_expand_event_occurrences` (line 686) is the caller and owns exdate exclusion and override application. The YEARLY branch returns `(occ_start, occ_end)` tuples in the same shape as the other branches, so `_expand_event_occurrences` handles them identically with no change.

### 5.6 Conflict detection

`_ensure_no_conflicts` (line 731) calls `_expand_event_occurrences` which calls `_expand_rrule`. YEARLY events are therefore included in conflict checking with no additional code. A YEARLY event's single occurrence per query window is compared against the requested event time exactly like any other occurrence.

### 5.7 All-day YEARLY events

All-day events use `all_day_date` rather than `start_utc`/`end_utc`. The YEARLY branch operates on `series_start_utc` / `series_end_utc` which are computed by `_event_time_interval` (lines 537–545). For all-day events, `_event_time_interval` converts the `all_day_date` to midnight-to-midnight UTC using the event's `timezone` via `ZoneInfo`. The YEARLY branch receives proper UTC datetimes and does not need to handle the all-day case specially. The `_expand_event_occurrences` caller reconstructs `all_day_date` from the occurrence's UTC start by back-converting through the timezone (lines 708–711), which is correct for YEARLY all-day events.

### 5.8 `window_end` look-ahead safety

The loop terminates when `dt > window_end + timedelta(days=366)`. With `interval=1`, the next candidate after a window-boundary occurrence is at most 366 days ahead (accounting for leap years). With `interval > 1`, candidates are spaced further apart, so this condition also terminates correctly. For extremely large `interval` values (e.g., `interval=100`, field max is unbounded but practically limited to positive integers), the loop makes at most a handful of iterations before the look-ahead condition fires.

### 5.9 Interaction with Google Calendar outbound sync

`create_event` (line 1604) and `update_event` (line 1838) call `enqueue_google_calendar_outbound_sync_job` with `event_snapshot=item`. The `item["recurrence_rule"]` dict now legally contains `freq="YEARLY"`. The Google Calendar outbound sync job (`app/services/google_calendar_outbound_jobs.py`) may not yet handle `YEARLY`; if so it will no-op or log a warning until updated. This is an acceptable gap at the ACT-005 boundary.

### 5.10 Apple CalDAV sync

After this ticket, `_build_ics` emits `RRULE:FREQ=YEARLY` in the ICS body so CalDAV push of YEARLY events sends a standards-compliant rule to iCloud. Pull-import of incoming YEARLY ICS is handled by the Apple CalDAV integration services in `app/services/calendar_integrations/` and is outside this ticket's scope.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity**: The two changed code locations (`_expand_rrule` and `_build_ics`) are pure Python functions with no AWS API calls, no `S.dev_mode` branches, and no mock/real forks. They behave identically in the local dev stack and in production. The YEARLY expansion uses only the Python standard library (`datetime`, `timedelta`, `calendar.isleap`-equivalent inline logic).

**Idempotency**: `_expand_rrule` is a pure deterministic function that writes nothing to storage. `create_event` and `update_event` already use idempotent `put_item` semantics. Re-reading and re-expanding a YEARLY event always produces the same occurrence list.

**Security**: No new endpoints, auth surfaces, or DynamoDB access patterns are introduced. The only new user-controlled input is the string `"YEARLY"` in `freq`, validated by Pydantic's `Literal` constraint before reaching any function. An invalid value (e.g., `"HOURLY"`) is rejected with HTTP 422 before `_expand_rrule` is called.

**Input bounds**: `interval` is already bounded `ge=1` (line 1356); `count` bounded `ge=1` (line 1358); `until_utc` validated by `parse_iso_dt` in `_normalize_recurrence_rule` (line 399). No additional bounds are needed for YEARLY.

## 8. Backward Compatibility & Migration

**Existing events**: All existing events in DynamoDB have `recurrence_rule.freq` values of `"DAILY"`, `"WEEKLY"`, or `"MONTHLY"` (or `null`). They are unaffected. Widening a `Literal` type is backward-compatible; old values remain valid.

**API clients**: Previously `freq="YEARLY"` was rejected with HTTP 422. After this ticket it is accepted. Existing clients sending DAILY/WEEKLY/MONTHLY are unaffected.

**ICS export**: `_build_ics` previously emitted no `RRULE:` property for any frequency. After this ticket it emits `RRULE:` for all four frequencies (RFC 5545 §3.8.5.3 compliant). Integrations that ignored the absent `RRULE` will now correctly expand the series.

**No DynamoDB migration**: No existing rows need to be updated. No `UpdateTable` or GSI backfills are required. `just restart` recreates tables without any new `TableDef` entries.

## 10. Open Questions / Assumptions

1. **`bymonthday` / `byday` / `BYMONTH` + YEARLY**: RFC 5545 supports these modifiers on YEARLY rules. The design implements the common case only: "every N years on the same month and day as the series start." `bymonthday`, `bysetpos`, and `byday` are ignored by the YEARLY branch. A `bymonth` field does not exist on `RecurrenceRule`. All three can be added in a follow-up with no model or API changes.

2. **Google Calendar outbound sync**: The outbound sync job (`app/services/google_calendar_outbound_jobs.py`) may not yet map `freq=YEARLY` to Google Calendar format. The assumption is that the job is resilient to an unknown `freq` (passes through or skips RRULE generation). Fixing that mapping is a follow-up.

3. **Apple CalDAV inbound**: Importing existing YEARLY events from Apple CalDAV is handled by `app/services/calendar_integrations/` and is outside scope. This ticket only affects events created via the internal API.

4. **Timezone/DST edge cases**: `dt.replace(year=...)` preserves wall-clock UTC time. For DST-observing timezones the UTC offset may shift by one hour across DST transitions. This matches the existing DAILY/MONTHLY behaviour and is an accepted P2 limitation.
