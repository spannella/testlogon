# INV-004 — Multi-currency on invoices — currency display and exchange rate on invoice PDF

**Type:** Feature  **Priority:** P2  **Estimate:** 1d  
**Status:** Design spec — not yet implemented  
**Source ticket:** `docs/suitecrm/CRM_INVOICES_CURRENCY_TICKETS.md` § "INV-004"

---

## 1. Summary & Goal

INV-004 surfaces multi-currency information that INV-003 already stores on invoice records into two places where users and admins see it:

1. **Invoice PDF** — when an invoice was issued in a non-USD currency, all line-item and total amounts in the PDF are rendered using the original currency symbol (e.g. `€10.00` instead of `$10.00`), and a USD-equivalent footer block is appended showing the converted total and the locked exchange rate.
2. **Frontend `InvoiceRow` component** — a small currency badge (`€10.00 EUR`) is appended to the amount display when `original_currency` is non-empty and not `"usd"`.

No new DynamoDB table is introduced. No new backend API endpoints are introduced. The entire change is a rendering extension on top of data that INV-003 already persists. With the feature flag `AOS_INVOICE_MULTICURRENCY_DISPLAY_ENABLED` off (the default), the PDF output and the frontend component are byte-for-byte identical to today.

## 4. API / Service Design

### 4.1 Service changes — `app/services/invoices.py`

#### 4.1.1 Updated `_money` helper (line 146)

Replace the single-argument helper with a two-argument version that accepts an optional symbol:

```python
def _money(cents: int, symbol: str = "$") -> str:
    return f"{symbol}{cents / 100:.2f}"
```

The symbol defaults to `"$"` so every existing call site that does not pass a symbol is unchanged. All calls inside `_render_invoice_lines` that render USD amounts continue to produce `$N.NN` without modification.

#### 4.1.2 Updated `_render_invoice_lines` (lines 150–188)

Add a multi-currency rendering branch after the existing header/bill-to block and before `"Thank you for your purchase."`. The new logic is gated on both `S.aos_invoice_multicurrency_display_enabled` and the presence of a non-USD `original_currency` field on the record. If either condition is false the function returns the same lines it does today.

Pseudo-code (exact Python in implementation):

```python
orig_currency = (record.get("original_currency") or "").lower().strip()
usd_eq = _coerce_int(record.get("usd_amount_cents"))
rate_snap = record.get("exchange_rate_snapshot")  # Decimal or float or None
multicurrency = (
    S.aos_invoice_multicurrency_display_enabled
    and orig_currency
    and orig_currency != "usd"
)

# Resolve display symbol — best-effort, never raises
symbol = orig_currency.upper()  # fallback: "EUR", "GBP", etc.
if multicurrency and S.crm_currencies_enabled:
    try:
        from app.services.crm_currencies import get_currency
        cur = get_currency(orig_currency)
        if cur and cur.get("symbol"):
            symbol = str(cur["symbol"])
    except Exception:
        pass  # fail open: use ISO code as symbol

# In the line-item loop and totals block:
# when multicurrency is True, pass symbol to _money(); otherwise pass "$"
money_fn = (lambda c: _money(c, symbol)) if multicurrency else _money
```

Line-item loop change:

```python
for li in record.get("line_items") or []:
    desc = str(li.get("description") or "Item")[:30]
    qty = _coerce_int(li.get("quantity"), 1)
    li_amount = _coerce_int(li.get("amount_cents"))
    lines.append(f"{desc:<32}{qty:>4}{money_fn(li_amount):>12}")
```

Totals block change:

```python
lines.append(f"{'Subtotal':<36}{money_fn(amount):>12}")
lines.append(f"{'Tax':<36}{money_fn(tax):>12}")
total_display = -total if refunded else total
lines.append(f"{'TOTAL':<36}{money_fn(total_display):>12}")
```

USD-equivalent footer block (appended only when `multicurrency` is `True`):

```python
if multicurrency:
    lines.append("")
    lines.append("-" * 48)
    if usd_eq:
        lines.append(f"{'USD equivalent:':<36}{_money(usd_eq):>12}")
    if rate_snap is not None:
        try:
            rate_float = float(rate_snap)
            orig_upper = orig_currency.upper()
            lines.append(f"Rate: 1 {orig_upper} = {rate_float:.6f} USD")
        except (TypeError, ValueError):
            pass
```

The USD equivalent block is placed after the TOTAL line and before `"Thank you for your purchase."`. It uses `_money` (no symbol override — always USD) for the USD equivalent amount.

#### 4.1.3 `download_invoice_pdf` — no change required

`download_invoice_pdf` at `app/services/invoices.py:442` calls `_render_invoice_lines` via `_render_pdf` on S3 cache miss. Because `_render_invoice_lines` is extended in place, regenerated PDFs automatically pick up multi-currency rendering. Existing S3-cached PDFs for USD invoices are untouched.

#### 4.1.4 `_serialize` — no change required

## 5. Detailed Behavior & Edge Cases

### 5.1 USD invoice (flag on or off)

When `original_currency` is `""` or `"usd"` (or absent), `multicurrency = False` and `_render_invoice_lines` follows exactly the same code path it does today. The rendered PDF bytes are byte-for-byte identical. This is the common case for all existing invoices and any new USD invoice.

### 5.2 Non-USD invoice, currency registry populated (INV-002 on)

Example: `original_currency="eur"`, `original_amount_cents=5000`, `usd_amount_cents=5400`, `exchange_rate_snapshot=1.08`, EUR symbol `"€"` in `crm_currencies`.

Expected totals block in PDF:

```
Subtotal                            €50.00
Tax                                  €0.00
TOTAL                               €50.00

------------------------------------------------
USD equivalent:                     $54.00
Rate: 1 EUR = 1.080000 USD
```

Line items are also rendered with `€` prefix.

### 5.3 Non-USD invoice, currency registry absent (INV-002 off or currency not found)

`get_currency("eur")` returns `None` or raises. The symbol fallback is `"EUR"` (ISO code uppercased). Line items render as `EUR50.00`. USD equivalent block still appears if `usd_amount_cents > 0` and `exchange_rate_snapshot` is set (those are stored independently by INV-003 regardless of INV-002's flag state).

### 5.4 Non-USD invoice, INV-003 not yet run (old record without conversion fields)

`original_currency` is absent; `record.get("original_currency")` returns `None`; `multicurrency = False`. The PDF is unchanged (USD path). This is backward compatible — no error, no broken PDF.

### 5.5 `exchange_rate_snapshot` is `None` or conversion failed (INV-003 fail-open)

INV-003 stores `exchange_rate_snapshot = Decimal("1")` as a fallback when the rate lookup fails, so `rate_snap` will be `1.0` rather than `None`. The "Rate: 1 EUR = 1.000000 USD" line appears but is technically inaccurate. This is acceptable; the PDF is not a legal tender document and the rate is clearly labeled. If `rate_snap` is truly `None` (old record), the Rate line is omitted silently (the `if rate_snap is not None` guard).

### 5.6 `usd_amount_cents == 0` (INV-003 fail-open or disabled)

The "USD equivalent:" line is conditionally rendered only when `usd_eq > 0` (`if usd_eq:`). When INV-003 stored `usd_amount_cents=0` (disabled or fail-open), the USD equivalent line is omitted. The non-USD amounts and symbol still render correctly if `original_currency` is set.

### 5.7 PDF regeneration for old invoices

`download_invoice_pdf` regenerates from the stored DDB record on S3 cache miss (line 450). For old invoices created before INV-003, the DDB record lacks `original_currency`; the regenerated PDF is therefore unchanged (USD path). This is correct and safe.

### 5.8 `_money` symbol injection does not affect existing call sites

Only the two call sites inside `_render_invoice_lines` for line items and the TOTAL block receive the symbol override. The USD equivalent line and the `email_invoice` text body (line 472 via `_render_invoice_lines(raw)`) also benefit from correct symbol rendering, because `email_invoice` calls `_render_invoice_lines` directly. No other call site in the codebase calls `_money` directly outside of `invoices.py`.

### 5.9 `decimal_places` from currency registry

SuiteCRM stores `decimal_places` per currency (e.g. 0 for JPY). The current `_money` implementation always divides by 100 and formats to two decimal places. For a complete implementation, `_money(cents, symbol, decimal_places=2)` should format JPY as `¥5000` not `¥50.00`. This is noted as a known limitation and out of scope for the P2 estimate of 1d; INV-004 uses `{cents / 100:.2f}` for all currencies. A follow-up ticket can handle JPY and other zero-decimal currencies.

### 5.10 Thread safety of `_render_invoice_lines`

`_render_invoice_lines` is a pure function (no shared mutable state). The `get_currency` call is also stateless (DDB read). No locking is required.

## 6. Feature Flag & Config

### 6.1 New settings entry

Add immediately after `invoices_tax_bps` at `app/core/settings.py:2569`:

```python
# INV-004: Multi-currency display on invoice PDF and InvoiceRow
# Default OFF. Enable after INV-002 and INV-003 are deployed and currency
# records are populated.
aos_invoice_multicurrency_display_enabled: bool = os.environ.get(
    "AOS_INVOICE_MULTICURRENCY_DISPLAY_ENABLED", "0"
) not in ("0", "false", "False")
```

With env var absent: `"0" not in ("0", "false", "False")` → `False`. Default-off confirmed.  
With `AOS_INVOICE_MULTICURRENCY_DISPLAY_ENABLED=1`: `"1" not in ("0", "false", "False")` → `True`. Enabled.

This follows the established default-OFF flag pattern: the `cart_reminders_enabled` analogy at `app/core/settings.py:821` uses `not in ("0", "false", "False")` with a `"1"` default (making it True by default). Here the default is `"0"` so the flag is False by default.

### 6.2 Environment variable

| Variable | Default | Meaning |
|---|---|---|
| `AOS_INVOICE_MULTICURRENCY_DISPLAY_ENABLED` | `"0"` (off) | Enable multi-currency PDF rendering and `InvoiceRow` badge |

### 6.3 Interaction with sibling flags

| Flag | Required for INV-004 | Notes |
|---|---|---|
| `INVOICES_ENABLED` | Yes (hard gate) | `_require_enabled()` in router already enforces this |
| `CRM_CURRENCIES_ENABLED` (INV-002) | Soft dependency | INV-004 fails open if off; symbol falls back to ISO code |
| `AOS_INVOICE_CURRENCY_CONVERSION_ENABLED` (INV-003) | Soft dependency | INV-004 fails open if off; USD equivalent line is omitted |
| `AOS_INVOICE_MULTICURRENCY_DISPLAY_ENABLED` | This ticket's own flag | Must be explicitly set to `"1"` to activate |

INV-004 does **not** gate on `CRM_CURRENCIES_ENABLED` or `AOS_INVOICE_CURRENCY_CONVERSION_ENABLED` directly. It reads the fields stored by INV-003 from the DDB record; if they are absent it falls back gracefully. This design means INV-004 can be deployed before INV-002 or INV-003 are activated, with no effect.

### 6.4 Frontend flag handling

The `isMultiCurrency` badge in `InvoiceRow.tsx` is controlled purely by the data returned from the API (`invoice.original_currency` non-empty and non-`"usd"`). There is no separate frontend feature flag. When the backend flag is off, `original_currency` will be `""` on all new invoices (INV-003 does not store it when disabled), so the badge never renders.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 dev/prod parity

`_render_invoice_lines` is pure Python with no `if S.dev_mode` branches. The `get_currency` call goes through `T.crm_currencies` (wired by `_safe_table` in `app/core/tables.py:65`), which boto3 intercepts at the botocore layer in dev (moto in-process) exactly as it does in prod (real DynamoDB). The S3 PDF path (`_store_pdf`, `_fetch_pdf`) uses `s3_client()` from `app.core.aws_clients` — same abstraction, moto in dev, real S3 in prod. No AWS service branching exists or is introduced.

### 7.2 Idempotency

PDF generation is deterministic and stateless. Re-downloading the same invoice always produces the same bytes from the same DDB record. If `usd_amount_cents` or `exchange_rate_snapshot` changes on the record (which INV-003 prevents — those are set once at creation), the S3 cache is invalidated only by an explicit `_store_pdf` call. The regeneration path in `download_invoice_pdf` (line 450) correctly re-renders from the current DDB state and re-uploads.

### 7.3 Security

- No new auth surfaces or privilege escalations are introduced. All endpoints that serve PDFs require `require_ui_session` and enforce ownership (`get_invoice` returns `None` for a different user's invoice number, producing 404 — no cross-user data leakage).
- The `get_currency` call inside `_render_invoice_lines` is a **read-only** DDB `get_item`. It cannot write or leak user data. If it raises, the exception is swallowed and the fallback symbol is used.
- The PDF renderer is the existing pure-PostScript text renderer (`app/services/invoices.py:8–10`). No HTML-injection or template-expansion is used; `_pdf_escape` at line 99 sanitizes parentheses in all string content written to the PostScript stream.
- `exchange_rate_snapshot` is serialized as `float(rate_snap)` before formatting. If the stored DDB value is a `Decimal` (as written by INV-003), `float()` converts it safely. A non-numeric stored value (data corruption) is caught by the `except (TypeError, ValueError)` guard and the Rate line is silently omitted.

## 8. Backward Compatibility & Migration

### 8.1 Existing invoices

All invoices created before INV-003 is deployed lack `original_currency`, `usd_amount_cents`, and `exchange_rate_snapshot`. `_render_invoice_lines` reads these via `record.get(...)` with `None` / `0` defaults. With `original_currency` absent or `""`, `multicurrency = False` and the existing USD rendering path executes. No existing invoice is affected.

### 8.2 `InvoiceOut` model backward compatibility

INV-003 adds all three fields to `InvoiceOut` with safe defaults (`str = ""`, `int = 0`, `Optional[float] = None`). Any API consumer that receives an `InvoiceOut` without these fields (serialized from an old DDB item) gets the defaults. No breaking schema change.

### 8.3 `Invoice` TypeScript type

All three new fields are `?` (optional) in the TypeScript interface. Existing components that do not use them compile and run unchanged. `InvoiceRow.tsx` guards `invoice.original_currency` with a truthiness check before rendering the badge.

### 8.4 `_money` signature change

`_money(cents: int, symbol: str = "$") -> str` is backward-compatible: every existing call site in `invoices.py` that passes only `cents` continues to receive `"$N.NN"` output. There is no other file in the codebase that imports `_money` directly (it is a module-private helper prefixed with `_`).

### 8.5 Migration steps

No data migration is required. The feature is purely additive:
1. Deploy INV-002 (currency registry) — optional but improves symbol lookup.
2. Deploy INV-003 (conversion on `create_invoice`) — stores the fields INV-004 reads.
3. Deploy INV-004 (this ticket) — extends the renderer; flag defaults to off.
4. Populate at least one non-USD currency record via `POST /ui/admin/currencies` (INV-002 endpoint).
5. Set `AOS_INVOICE_MULTICURRENCY_DISPLAY_ENABLED=1` in the environment to activate.

Existing PDF S3 objects for USD invoices are never touched. New EUR (or other non-USD) invoices created after step 3+5 will have the correct rendering immediately on first PDF generation.

## 10. Open Questions / Assumptions

1. **JPY and other zero-decimal currencies.** The current `_money` always formats `cents / 100` to two decimal places. For JPY, amounts stored in "yen" (not "yen-cents") would render incorrectly as `¥50.00` when `50` was stored. This ticket assumes all currencies are stored in the smallest unit (e.g. "euro-cents") and displayed divided by 100. The `decimal_places` field in the INV-002 currency record is available for a follow-on fix.

2. **`original_amount_cents` vs `amount_cents` for the TOTAL line.** The spec uses `amount_cents` (the original persisted subtotal) for rendering, which may equal `original_amount_cents` when INV-003 stores it. The TOTAL line uses `total_cents` (which includes tax). This is correct for display but the implementation should confirm that INV-003 stores `total_cents` in original currency units and not USD.

3. **Email body for non-USD invoices.** `email_invoice` at `app/services/invoices.py:455` calls `_render_invoice_lines(raw)` and uses the result as the email body text. With INV-004's extension, the email body will also include EUR symbols and the USD-equivalent footer when the flag is on. This is desirable behavior but should be noted as a change in email content for non-USD invoices.

4. **S3-cached PDFs for non-USD invoices created before INV-004 is deployed.** If INV-003 is live and a EUR invoice's PDF is cached in S3 before INV-004 is deployed, the cached PDF will use `$` symbols. After INV-004 is deployed with the flag on, `download_invoice_pdf` serves the cached S3 PDF without re-rendering. To force re-rendering, the S3 object must be deleted. A one-time admin job or a cache-bust query param is out of scope for 1d estimate; the recommendation is to accept stale S3 PDFs for pre-INV-004 EUR invoices (they still display the correct USD total).

5. **Right-to-left currency symbols.** Some locale conventions place the currency symbol after the amount (e.g. Swedish krona `100,00 kr`). The text-based PDF renderer has no locale awareness; all symbols are prepended. This is a known cosmetic limitation.
