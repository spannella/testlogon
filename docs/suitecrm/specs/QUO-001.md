# QUO-001 — Sales Quote entity — DynamoDB model, service, and REST API

**Area**: Quotes, Products, Contracts & PDF Templates (AOS)
**Type**: Feature **Priority**: P1 **Estimate**: 4d
**Flag**: `AOS_QUOTES_ENABLED` (default `"0"`, off)

---

## 1. Summary & Goal

QUO-001 introduces the core sales-quote entity to the testlogon platform: a DynamoDB table, Pydantic request/response models, a service layer, and a REST router. A quote is a pre-invoice sales proposal with a multi-stage lifecycle (draft → sent → accepted → rejected → expired → converted) and multi-line-item composition.

The goal is to close the SuiteCRM AOS gap for structured quote management — enabling users to compose itemized proposals from catalog products, advance them through an approval cycle, and provide a foundation for QUO-002 (PDF rendering), QUO-003 (quote-to-invoice/contract conversion), and QUO-004 (contract entity). The implementation is additive and default-off: with `AOS_QUOTES_ENABLED=0` the platform is byte-for-byte unchanged.

## 3. Data Model

### `aos_quotes` DynamoDB table

**Environment variable**: `AOS_QUOTES_TABLE_NAME` (default `"aos_quotes"`)

```
Primary key:
  pk  (S) = "USER#{user_sub}"
  sk  (S) = "QUOTE#{quote_id}"          # quote_id = "quo_" + uuid4().hex[:16]

Counter/sequence row (shares the same table, different pk):
  pk  = "COUNTER"
  sk  = "QUOTE_SEQ"
  Mutated with: ADD next_seq :inc — atomic, same as invoices.py:85-91

Item attributes:
  quote_id            str       # "quo_" + uuid4().hex[:16]
  quote_number        str       # "AOS-{seq:05d}", from _next_quote_number()
  title               str       # required, max 255 chars
  stage               str       # draft|sent|accepted|rejected|expired|converted
  valid_until         int|None  # Unix timestamp; null = no expiry
  assigned_user_sub   str       # "" if unassigned
  account_id          str       # "" if no account; future PTY-012 PARTY_GROUP ref
  contact_id          str       # "" if no contact; future PTY-011 PERSON party ref
  currency            str       # ISO 4217 lowercase, default "usd"
  billing_address     dict      # {street, city, state, postal_code, country}
  shipping_address    dict      # same shape
  notes               str       # "" if empty
  line_items          list[dict]
    Each dict:
      catalog_item_id   str     # "" if free-form; else T.catalog SK ref
      description       str     # required even when catalog_item_id set
      qty               int     # ≥ 1
      unit_price_cents  int     # ≥ 0
      discount_bps      int     # basis points off unit price; default 0
      tax_rate_bps      int     # basis points tax on net line; default 0
      line_total_cents  int     # computed: round(qty * unit_price_cents
                                #   * (1 - discount_bps/10000)
                                #   * (1 + tax_rate_bps/10000))
  subtotal_cents      int       # sum of qty*unit_price*(1-discount/10000)
  discount_cents      int       # sum of qty*unit_price*(discount/10000)
  tax_cents           int       # sum of net * tax_rate_bps/10000
  total_cents         int       # subtotal_cents - discount_cents + tax_cents
                                #   (note: discount_cents already excluded
                                #    from subtotal, so total = subtotal + tax)
  created_at          int (N)   # now_ts() at creation
  updated_at          int (N)   # now_ts() at each mutation

GSI attributes (written with each item):
  GSI1PK  = "QUOTES#ALL"
  GSI1SK  = created_at   (N)    # admin cross-user list, newest-first

  GSI2PK  = "USER#{user_sub}#STAGE#{stage}"
  GSI2SK  = created_at   (N)    # per-user stage-filtered list
```

**Clarification on totals arithmetic**: `subtotal_cents` is the pre-discount, pre-tax sum (i.e., `sum(qty * unit_price_cents)` per line). `discount_cents` = `sum(qty * unit_price_cents * discount_bps / 10000)`. Net per line = `qty * unit_price_cents * (1 - discount_bps/10000)`. `tax_cents` = `sum(net_line * tax_rate_bps / 10000)`. `total_cents = subtotal_cents - discount_cents + tax_cents`. Integer truncation via `//` on each step; all stored as `int`. `line_total_cents` = `net_line + tax_on_line` = `net_line * (1 + tax_rate_bps/10000)`.

## 4. API / Service Design

### Service: `app/services/aos_quotes.py`

All public functions begin with:
```python
if not S.aos_quotes_enabled:
    return None   # callers in the router raise 404
```

**`_next_quote_number() -> str`**

Atomically increments `COUNTER/QUOTE_SEQ` using `ADD next_seq :inc` (same call pattern as `invoices.py:85-91`) and returns `f"AOS-{seq:05d}"`. The counter key is isolated to `aos_quotes`, not shared with the invoices counter.

**`_compute_totals(line_items: list[dict]) -> dict`**

Pure function. Returns `{subtotal_cents, discount_cents, tax_cents, total_cents}` and a new list with `line_total_cents` filled in on each item. Called by `create_quote` and `update_quote`. Uses integer arithmetic throughout.

**`create_quote(user_sub: str, title: str, *, valid_until: int | None, assigned_user_sub: str, account_id: str, contact_id: str, currency: str, billing_address: dict, shipping_address: dict, notes: str, line_items: list[dict]) -> dict`**

1. Gate: `if not S.aos_quotes_enabled: return None`.
2. Validate `title` non-empty; `currency` 3-char lowercase; each line item has `qty >= 1`, `unit_price_cents >= 0`, `discount_bps` in [0, 10000], `tax_rate_bps` in [0, 10000].
3. Compute totals via `_compute_totals`.
4. Mint `quote_id = "quo_" + uuid4().hex[:16]`.
5. Call `_next_quote_number()` for `quote_number`.
6. Write DDB item with `stage="draft"`, `created_at=now_ts()`, `updated_at=now_ts()`, GSI1/GSI2 attributes.
7. Call `audit_event("quote.created", user_sub, quote_id=quote_id, quote_number=quote_number)`.
8. Return `_serialize(item)`.

**`get_quote(user_sub: str, quote_id: str) -> dict | None`**

`T.aos_quotes.get_item(Key={"pk": f"USER#{user_sub}", "sk": f"QUOTE#{quote_id}"})`. Returns `_serialize(item)` or `None` if not found or wrong owner.

**`list_quotes(user_sub: str, stage: str | None = None, limit: int = 50, cursor: str | None = None) -> dict`**

- If `stage` is provided: query GSI2 with `GSI2PK = "USER#{user_sub}#STAGE#{stage}"`, `ScanIndexForward=False`, `Limit=limit`, `ExclusiveStartKey=decode_cursor(cursor)`.
- If no stage: query by primary key prefix `pk = "USER#{user_sub}"` with `begins_with(sk, "QUOTE#")`, `ScanIndexForward=False`, `Limit=limit`.
- Returns `{"quotes": [_serialize(item) for item in items], "next_cursor": encode_cursor(lek)}`.

**`update_quote(user_sub: str, quote_id: str, **patch_fields) -> dict | None`**

1. Gate + fetch existing quote; return `None` if not found.
2. Reject mutations on `converted` stage (409 in router).
3. Merge patch fields into item; if `line_items` in patch_fields, recompute totals.
4. If `stage` changes in patch (not via this function — use `transition_stage`): raise `ValueError` ("use transition_stage to change stage").
5. Set `updated_at = now_ts()`; call `T.aos_quotes.put_item(Item=updated)`.
6. If `stage` in patch, update `GSI2PK` to reflect new stage — but this is handled by `transition_stage`, not `update_quote`.
7. Emit `audit_event("quote.updated", user_sub, quote_id=quote_id, changed_fields=list(patch_fields))`.
8. Return `_serialize(updated)`.

**`transition_stage(user_sub: str, quote_id: str, new_stage: str) -> dict | None`**

Allowed transitions:
```
draft     → sent
sent      → accepted | rejected
any       → expired   (system-side expiry sweep; also callable by owner)
accepted  → converted  (only via QUO-003 convert endpoints, not direct API)
```
Any other transition raises `ValueError(f"invalid transition: {current} → {new_stage}")` which the router converts to `400`. Steps:
1. Gate + fetch; return `None` if not found.
2. Validate transition via the table above.
3. Update `stage`, `GSI2PK = f"USER#{user_sub}#STAGE#{new_stage}"`, `updated_at`.
4. Emit `audit_event("quote.stage_changed", user_sub, quote_id=quote_id, from_stage=current, to_stage=new_stage)`.
5. Return `_serialize(updated)`.

**`admin_list_quotes(limit: int = 50, cursor: str | None = None) -> dict`**

Queries GSI1 (`GSI1PK = "QUOTES#ALL"`, `ScanIndexForward=False`). Returns `{"quotes": [...], "next_cursor": ...}`.

## 5. Detailed Behavior & Edge Cases

### Line-item total computation

The computation is pure integer arithmetic. The reference formula per line:
```
net_line_cents = qty * unit_price_cents * (10000 - discount_bps) // 10000
tax_on_line    = net_line_cents * tax_rate_bps // 10000
line_total     = net_line_cents + tax_on_line
```
`subtotal_cents = sum(qty * unit_price_cents for item)` (pre-discount).
`discount_cents = sum(qty * unit_price_cents * discount_bps // 10000 for item)`.
`tax_cents = sum(tax_on_line for item)`.
`total_cents = subtotal_cents - discount_cents + tax_cents`.

Integer truncation (`//`) is applied at each step, not at the final sum, so totals are deterministic and round-trip from DDB without floating-point error.

### Stage transition validation

The `ALLOWED_TRANSITIONS` dict in `aos_quotes.py`:
```python
ALLOWED_TRANSITIONS = {
    "draft":    {"sent", "expired"},
    "sent":     {"accepted", "rejected", "expired"},
    "accepted": {"converted", "expired"},
    "rejected": set(),
    "expired":  set(),
    "converted": set(),
}
```
`rejected`, `expired`, and `converted` are terminal — no further transitions allowed. `converted` can only be reached through the `transition_stage` function called from QUO-003's conversion endpoints (the stage endpoint itself blocks `draft→converted` via the table). If the caller requests `any→expired`, the service allows it unconditionally — this covers both a user manually expiring their own quote and a future expiry sweep.

### `valid_until` expiry semantics

`valid_until` is informational at the model layer (QUO-001 does not run a background sweep). QUO-003 or a future scheduled task can query quotes where `valid_until < now_ts()` and `stage not in ("expired", "converted", "rejected")` and call `transition_stage(..., "expired")`. The field is stored as a numeric Unix timestamp and is `None`/absent when no expiry is set.

### Empty line items

`POST /ui/quotes` with `line_items=[]` is rejected with `422` by Pydantic (`List[QuoteLineItemIn]` has no minimum-length validator added by default). A `@field_validator` on `QuoteCreateIn.line_items` enforces `len(v) >= 1` with a clear message. `QuotePatchIn.line_items` can be `[]` — this is an explicit user action to clear all line items — but `total_cents` would become `0`. This is permitted (drafts may be works-in-progress). If a quote's `total_cents` is `0` and `stage != "draft"`, the router does not block it; business rules around non-zero quotes are left to the UI.

### GSI2 update on stage change

Because `GSI2PK = f"USER#{user_sub}#STAGE#{stage}"` is baked into the item, a stage transition requires a full `put_item` of the updated item (not an `update_item` that only sets `stage`). `transition_stage` fetches the item, mutates stage + GSI2PK + updated_at, and puts the whole item back. The `COUNTER` row has no GSI attributes, so it is never accidentally indexed.

### `PATCH /ui/quotes/{quote_id}` — partial update semantics

`QuotePatchIn` has all-optional fields. The service merges only fields with non-`None` values from the patch over the stored item dict. This follows the exact same pattern as ticket PATCH endpoints in `app/routers/tickets.py`. Fields not present in the patch body are left unchanged. If `line_items` is provided (even as empty list), the totals are fully recomputed.

### Ownership enforcement

`get_quote(user_sub, quote_id)` keys the DDB `get_item` with `pk=USER#{user_sub}`. A caller who supplies a `quote_id` they do not own receives a `404` (the item exists but under a different `pk`). Admin endpoints use `admin_list_quotes()` which queries GSI1 without a user constraint.

### `assigned_user_sub` vs owner `user_sub`

The quote's `pk` encodes the creating user's `user_sub`. `assigned_user_sub` is a separate field (the assigned sales rep). QUO-001 does not enforce that `assigned_user_sub` corresponds to a real user — it is stored as a plain string, consistent with how `assigned_user` is treated in CRM contacts. Future PTY tickets can validate this field once a party/user directory exists.

Add to `app/core/settings.py` immediately after `invoices_enabled` at line 2568:

```python
# QUO-001: Sales Quotes (AOS)
# Default "0" (off) — no routes, no DDB writes when disabled.
# Set AOS_QUOTES_ENABLED=1 to activate.
aos_quotes_enabled: bool = os.environ.get("AOS_QUOTES_ENABLED", "0") not in ("1", "true")
```

**Note on flag polarity**: The ticket source shows `not in ("1", "true")` which evaluates `True` when the env var is absent (defaulting to `"0"`), meaning the feature is OFF by default. This matches the `cart_reminders_enabled` pattern at `app/core/settings.py:821` where `not in ("0", "false", "False")` keeps the flag on by default. The AOS flags use `"0"` as the default, so `not in ("1", "true")` → `True` (enabled) when `AOS_QUOTES_ENABLED=1`. Verify this polarity against the `invoices_enabled` line 2568 pattern (`not in ("0", "false")`) and choose consistently. The correct formulation for a default-OFF flag is:

```python
aos_quotes_enabled: bool = os.environ.get("AOS_QUOTES_ENABLED", "0") in ("1", "true")
```

This means the flag is `False` (off) when the env var is absent or `"0"`, and `True` (on) only when explicitly `"1"` or `"true"`. This is the pattern the ticket source intends.

**`.env.local.example`**: Add `AOS_QUOTES_ENABLED=0` (off by default; developers opt in).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 — no dev_mode branch in service code

`app/services/aos_quotes.py` has zero `if S.dev_mode` branches. All DDB operations go through `T.aos_quotes` which boto3 routes to DynamoDB Local in dev (via `DDB_ENDPOINT_URL`) and real DynamoDB in prod. S3 is accessed via `app.core.aws_clients.s3_client()` — moto intercepts at the botocore layer in dev. No separate code path is needed.

The `audit_event` calls write to `T.alerts` in both environments. `send_alert_email` writes to the dev log file in dev, SES in prod — that branching is already inside `alerts.py:459-479` and requires no changes here.

### Idempotency

`create_quote` does not use a caller-supplied idempotency key (unlike invoices which key on `ledger_entry_id`). Quote creation is not triggered by a payment event, so duplicate-prevention is the caller's responsibility (the UI disables the submit button on first click). If a future integration requires idempotency, a client-supplied `idempotency_key` field can be added to `QuoteCreateIn` with a `put_item` conditional expression `attribute_not_exists(pk)` — this is an additive change deferred to a follow-up ticket.

`transition_stage` is idempotent: if `new_stage == current_stage` the function returns the existing item without writing. This prevents unnecessary GSI2 re-indexing.

`_next_quote_number()` uses a DynamoDB atomic `ADD` — the counter is strictly monotonic and never resets, matching the invoice counter behavior at `invoices.py:85-91`.

### Ownership and authorization

- All user-facing endpoints key on `user_sub` from `require_ui_session` — the session's `user_sub` is trusted (set by the auth layer, not caller-supplied). Callers cannot access quotes owned by other users.
- Admin endpoints use `require_admin_or_root` from `app/auth/policy.py:67`. CSRF is enforced on admin non-GET endpoints via `enforce_cookie_csrf(request)` per `app/auth/policy.py:71-97`.
- `assigned_user_sub` is informational and does not grant access to the quote.

### Input validation

All money fields (`unit_price_cents`, `discount_bps`, `tax_rate_bps`) are validated `>= 0` via Pydantic `Field(ge=0)`. `discount_bps` and `tax_rate_bps` are clamped to `[0, 10000]` (0%–100%). The `currency` field is validated as a 3-character lowercase string; accepted values are not locked to an enum in QUO-001 (multi-currency support is addressed by QUO-005 and the CRM currency module).

## 8. Backward Compatibility & Migration

### With flag off (`AOS_QUOTES_ENABLED=0`, the default)

- `_require_enabled()` raises `HTTPException(404)` at the top of every endpoint. Zero service code executes.
- `T.aos_quotes` is wired in `tables.py` regardless of the flag (lazy boto3 table handle; no DDB call is made until first use). This is the existing pattern for all optional tables.
- `scripts/local-ddb-init.py` creates the `aos_quotes` table unconditionally at stack startup (same as all other optional tables like `audit_exports`, `kyc_cases`, etc.). The table creation is harmless if the flag is off — no data is written.
- All existing endpoints, models, DDB tables, and services are byte-for-byte unchanged.

### With flag on (`AOS_QUOTES_ENABLED=1`)

- The `aos_quotes` table must exist (created by `scripts/local-ddb-init.py` at `just up`/`just restart`).
- In production, a new DynamoDB table `aos_quotes` must be created (via `CreateTable` or IaC) before deploying with the flag on. The COUNTER/SEQ row is auto-created on first `_next_quote_number()` call by the `ADD` expression (DynamoDB creates the item if it doesn't exist when `ADD` is used on a non-existent attribute).
- No migration of existing data is required — the table is new, no existing rows need backfilling.

### Additive model changes

`QuoteOut`, `QuoteListOut`, `QuoteLineItemOut`, `QuoteCreateIn`, `QuotePatchIn`, `QuoteAddressIn` are all new models added to `app/models.py`. No existing model is changed. QUO-003 will add `converted_to_invoice_number: str = ""` and `converted_to_contract_id: str = ""` fields to `QuoteOut` — these are additive and backward-compatible.

## 10. Open Questions & Assumptions

1. **`quote_number` format**: The ticket specifies `"AOS-NNNN"` in the description but `"AOS-00001"` in acceptance criteria. This spec uses `f"AOS-{seq:05d}"` (5 digits, zero-padded) to match the AC and the `INV-YYYY-{seq:05d}` precedent in `invoices.py:83`. If the format needs to include the year (`AOS-2026-00001`), this is a one-line change to `_next_quote_number()`.

2. **`catalog_item_id` validation**: The spec stores `catalog_item_id` as a plain string without performing a `T.catalog.get_item` lookup at write time. This is consistent with how other cross-table FK references work in this codebase (tickets, contacts, projects all store `account_id`/`contact_id` as strings without join validation). If strict FK enforcement is needed, it can be added as a separate validation step in `create_quote` / `update_quote` — but this would add latency and a second DDB read per line item.

3. **Stage endpoint vs PATCH**: The ticket spec separates stage transitions into `POST /ui/quotes/{id}/stage` and field updates into `PATCH /ui/quotes/{id}`. This is by design — it prevents accidental stage changes through a generic PATCH and allows the transition logic to enforce the allowlist. `QuotePatchIn` deliberately excludes `stage` as a patchable field.

4. **`valid_until` expiry sweep**: QUO-001 does not implement a background expiry scheduler. The `valid_until` field is stored and readable, but expired quotes do not automatically transition to `stage="expired"`. A scheduled task or QUO-003 can implement this. The omission is intentional — the background scheduler pattern (like `run_contracts_renewal_check_loop` from QUO-004) is a separate concern.

5. **Multi-currency**: `currency` is stored as a string on the quote. No exchange-rate conversion or currency validation against a registry is performed in QUO-001. The CRM currency module (referenced in the gap analysis) will address multi-currency exchange rates as a separate ticket.

6. **`assigned_user_sub` permission model**: In the current design, only the owner (`user_sub` from session) can read/write their own quotes. There is no "assigned rep can also access" logic. If rep-access is needed, a GSI on `assigned_user_sub` can be added in a follow-up.
