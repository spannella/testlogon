# RPT-009 — Extended CSV export for additional modules

**Type:** Feature | **Priority:** P2 | **Estimate:** 1d  
**Area:** Reports & Dashboards (CRM_REPORTS_TICKETS.md — RPT-009)

---

## 1. Summary & Goal

Extend the existing streaming CSV export endpoint `GET /ui/export/csv` to cover four additional data modules: `tickets`, `subscriptions`, `orders`, and `contacts_crm`. The endpoint infrastructure — rate limiting, streaming `StreamingResponse`, RFC 4180 formatting, UTF-8 BOM, CSV injection sanitization, and the `generate_csv_rows` generator pattern — is entirely unchanged. This ticket adds only new iterator+formatter pairs to `app/services/csv_export.py` and widens the `VALID_SOURCES` set and query-parameter regex in `app/routers/csv_export.py`.

The gap that motivates this ticket: SuiteCRM allows CSV export from any tabular module. The platform today exports `billing_ledger`, `contacts`, and `questionnaire_responses` (the latter requires a `questionnaire_id` parameter). Tickets, subscriptions, orders, and a richer contacts view are absent. The new `contacts_crm` source is a superset of the existing `contacts` source, adding the `notes` and `source` fields that DynamoDB contact items may carry but the current formatter silently drops.

After this ticket, the existing three sources remain byte-for-byte unchanged with `CRM_REPORTS_ENABLED=0`. The four new sources are gated behind `S.crm_reports_enabled` (checked in the router before dispatching to `generate_csv_rows`) so the platform produces no change in observable behavior unless the flag is explicitly enabled.

## 3. Data Model

RPT-009 introduces **no new DynamoDB tables** and **no schema changes**. All four new sources read from existing tables using existing GSIs.

| Source | Table handle | Query key | GSI used |
|--------|-------------|-----------|----------|
| `tickets` | `T.tickets` | `gsi1pk = OWNER#{user_sub}` | `S.tickets_owner_index_name` |
| `tickets` (admin) | `T.tickets` | `gsi2pk = STATUS#{status}` (loop all statuses) | `S.tickets_status_index_name` |
| `subscriptions` | `T.subscriptions` | `pk = SUBSCRIBER#{user_sub}`, `sk begins_with SUB#` | base table (no GSI needed) |
| `orders` | `T.orders` | `GSI_USER` on `user_id = user_sub` | `"GSI_USER"` |
| `contacts_crm` | `T.contacts` | `owner_id = user_sub` | base table (same as `contacts`) |

**No `attr_types` changes needed**: The `GSI_USER` GSI on `T.orders` has `created_at` as its sort key. The DDB init entry at `scripts/local-ddb-init.py:288-294` declares the GSI with `sort_key: "created_at"` but the `attr_types` dict for that `TableDef` is empty (the default `"S"` type), meaning `created_at` is stored as a string there. The iterator does not filter by `created_at` via a GSI key condition — it retrieves all items for the user and sorts in Python — so no schema change is required. Implementors must not add a numeric sort key condition query on this GSI without first verifying the stored type.

```python
def _iter_tickets(
    user_sub: str,
    *,
    is_admin: bool = False,
) -> Generator[Dict[str, Any], None, None]:
    """Paginate over ticket META items for a user (or all, for admin).

    Uses the owner index (gsi1pk = OWNER#{user_sub}) for regular users.
    For admin callers, pages through each known status via the status index
    (gsi2pk = STATUS#{status}) to avoid a full table scan.
    DynamoDB FilterExpression does not reduce page count, so LastEvaluatedKey
    loops are mandatory (CLAUDE.md gotcha).
    """
    from boto3.dynamodb.conditions import Key
    from app.core.settings import S
    from app.services.tickets import _TICKET_STATUSES

    row_count = 0
    if not is_admin:
        # owner-scoped query
        kwargs: Dict[str, Any] = {
            "IndexName": S.tickets_owner_index_name,
            "KeyConditionExpression": "gsi1pk = :pk",
            "ExpressionAttributeValues": {":pk": f"OWNER#{user_sub}"},
            "Limit": 500,
        }
        while row_count < MAX_EXPORT_ROWS:
            resp = T.tickets.query(**kwargs)
            for item in resp.get("Items", []):
                if item.get("sk") == "META":
                    yield item
                    row_count += 1
                    if row_count >= MAX_EXPORT_ROWS:
                        return
            if "LastEvaluatedKey" not in resp:
                break
            kwargs["ExclusiveStartKey"] = resp["LastEvaluatedKey"]
    else:
        # admin: iterate all statuses on the status index
        for status in _TICKET_STATUSES:
            kwargs = {
                "IndexName": S.tickets_status_index_name,
                "KeyConditionExpression": "gsi2pk = :pk",
                "ExpressionAttributeValues": {":pk": f"STATUS#{status}"},
                "Limit": 500,
            }
            while row_count < MAX_EXPORT_ROWS:
                resp = T.tickets.query(**kwargs)
                for item in resp.get("Items", []):
                    if item.get("sk") == "META":
                        yield item
                        row_count += 1
                        if row_count >= MAX_EXPORT_ROWS:
                            return
                if "LastEvaluatedKey" not in resp:
                    break
                kwargs["ExclusiveStartKey"] = resp["LastEvaluatedKey"]
```

```python
def _iter_subscriptions(user_sub: str) -> Generator[Dict[str, Any], None, None]:
    """Paginate over SUBSCRIBER# index rows for the user, then fetch full META
    for each subscription to retrieve period and cancellation fields.
    """
    from boto3.dynamodb.conditions import Key

    kwargs: Dict[str, Any] = {
        "KeyConditionExpression": (
            Key("pk").eq(f"SUBSCRIBER#{user_sub}") & Key("sk").begins_with("SUB#")
        ),
        "Limit": 500,
    }
    row_count = 0
    while row_count < MAX_EXPORT_ROWS:
        resp = T.subscriptions.query(**kwargs)
        for index_row in resp.get("Items", []):
            sub_id = str(index_row.get("subscription_id") or "")
            if sub_id:
                meta_resp = T.subscriptions.get_item(
                    Key={"pk": f"SUBSCRIPTION#{sub_id}", "sk": "META"}
                )
                item = meta_resp.get("Item") or index_row
            else:
                item = index_row
            yield item
            row_count += 1
            if row_count >= MAX_EXPORT_ROWS:
                return
        if "LastEvaluatedKey" not in resp:
            break
        kwargs["ExclusiveStartKey"] = resp["LastEvaluatedKey"]
```

```python
def _iter_orders(user_sub: str) -> Generator[Dict[str, Any], None, None]:
    """Paginate over orders for the user using the GSI_USER index."""
    from boto3.dynamodb.conditions import Key

    kwargs: Dict[str, Any] = {
        "IndexName": "GSI_USER",
        "KeyConditionExpression": Key("user_id").eq(user_sub),
        "Limit": 500,
    }
    row_count = 0
    while row_count < MAX_EXPORT_ROWS:
        resp = T.orders.query(**kwargs)
        for item in resp.get("Items", []):
            yield item
            row_count += 1
            if row_count >= MAX_EXPORT_ROWS:
                return
        if "LastEvaluatedKey" not in resp:
            break
        kwargs["ExclusiveStartKey"] = resp["LastEvaluatedKey"]
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Tickets source

- Regular users receive only their own tickets: `gsi1pk = OWNER#{user_sub}` query on the owner index.
- Admin and root users receive **all** tickets across the platform, iterated by looping through every value in `_TICKET_STATUSES` (13 statuses) via the status index. This avoids a full table scan, which DynamoDB does not support efficiently for export. Each status-partition query loops `LastEvaluatedKey` as required by the CLAUDE.md gotcha on `FilterExpression` and sparse attributes.
- The SK filter `item.get("sk") == "META"` inside the iterator ensures only ticket META items are yielded, not MSG/ACT child rows that share the same partition key.
- `priority` is an optional field; missing values are rendered as an empty string.
- `assigned_admin_sub` and `assigned_to_sub` are both optional. The formatter coalesces them: `assigned_admin_sub or assigned_to_sub or ""`.
- `space_id` is optional; missing renders as empty string.

### 5.2 Subscriptions source

- The two-step lookup (index row → full META item) adds one `get_item` call per subscription. For users with many subscriptions this is unavoidable given the single-table schema. The `MAX_EXPORT_ROWS = 50_000` cap prevents runaway costs.
- If the `subscription_id` backref is absent on the index row (older items or different subscription providers), the index row itself is yielded directly. The formatter is defensive — all fields use `.get(field, default)`.
- `cancelled_at` renders as an empty string for active subscriptions (timestamp is `0` or absent).
- `price_cents` is cast to `int` via `int(item.get("price_cents", 0) or 0)`. DynamoDB may return `Decimal`; the `_FloatSafeTable` wrapper in `app/core/tables.py:29` handles floats on write, but reads may return `Decimal`. The `or 0` guards against `None`.

### 5.3 Orders source

- Queries `GSI_USER` on `user_id = user_sub`. This is a forward index (returns only orders for that user_id), so no server-side filtering is needed.
- Total amount is not included in the base export because `T.order_items` is a separate table requiring secondary queries per order. Including it would require O(N) additional queries. Implementors should add an `include_totals` query parameter in a follow-up if needed.
- `created_at` may be stored as a string in the orders table (GSI declares no `attr_types` numeric override, `scripts/local-ddb-init.py:288`). The `_ts_to_iso` helper safely converts both string and integer timestamps (it calls `int(ts)` and handles `TypeError`/`ValueError` by returning `""`).

### 5.4 `contacts_crm` source

- Reuses `_iter_contacts(user_sub)` verbatim, which queries `T.contacts` by `owner_id = user_sub` (the table's partition key at `scripts/local-ddb-init.py:691`).
- Adds two columns absent from the existing `contacts` source: `notes` (free-text notes field) and `source` (the channel through which the contact was added). Both are optional fields on the DDB item; missing renders as `""`.
- The existing `contacts` source is unchanged. Both sources coexist; users can request either.

### 5.5 Rate limiting

The existing rate limit (`_CSV_EXPORT_MAX = 5` per `_CSV_EXPORT_WINDOW = 60` seconds per user, bucket key `rl#csv_export`) applies uniformly to all seven sources including the four new ones. No source-specific rate limit is added. The rate-limit check fires before the flag gate so an unauthenticated-looking over-limit response does not reveal flag status.

### 5.6 Filename in `Content-Disposition`

The existing pattern `f"{source}_{int(time.time())}.csv"` (line 107) produces meaningful filenames for the new sources automatically, e.g. `tickets_1749600000.csv`.

### 5.7 Empty result sets

An export with zero rows yields only the UTF-8 BOM and header row, producing a valid single-row CSV file. The frontend/browser receives an empty file with correct column headers; this is not an error.

### 5.8 `from_date` / `to_date` filtering

The `from_date` and `to_date` parameters are accepted by the router for all sources but only applied in `_iter_billing_entries`. For the four new sources these parameters are accepted and silently ignored (consistent with the existing `contacts` and `questionnaire_responses` sources which also ignore them). A future ticket may add date filtering per source.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007**: No `if dev_mode` branches exist in any new code. All four new iterators hit `T.tickets`, `T.subscriptions`, `T.orders`, `T.contacts` — DDB-backed handles that run identically against DynamoDB Local (port 8001 in dev) and real DynamoDB in prod. The rate-limit token bucket is backed by `T.sessions` (NOT `T.rate_limits`) via `_bucket_limit` (`app/services/rate_limit.py:60-64`, which reads/writes `T.sessions` rows keyed `{user_sub, session_id="rl#csv_export"}`), same code path both environments.

**Idempotency**: `GET /ui/export/csv` is idempotent by definition — it reads DynamoDB state and streams a response. Repeated calls with the same parameters always reflect current table state; no writes occur.

**CSV injection**: All string fields pass through `_sanitize_csv_field` (line 43 of `app/services/csv_export.py`) before being written to the CSV writer. Formula-injection characters (`=`, `+`, `-`, `@`, `\t`, `\r`) are prefixed with a single quote. Numeric fields (e.g. `price_cents`) are rendered as plain integers and never as formulas.

**Authorization scope**: Regular users receive only their own data. The `is_admin` flag is derived exclusively from the session JWT role via `role_allows_admin_features(normalize_role(ctx["role"]))`. Admin-scoped ticket export is gated on `Role.ADMIN` or `Role.ROOT` (as defined at `app/auth/roles.py:60-61`). There is no way for a regular user to elevate to admin export by manipulating query parameters.

**No money movement**: This ticket introduces no billing writes, refunds, or ledger mutations. The `refund_payment` / `settle_or_reverse_ledger` primitives are not touched.

**No KMS or S3 usage**: Export data streams directly from DynamoDB to the HTTP response; no S3 upload and no KMS encryption are involved.

**Audit event**: Each successful export request (for the four new gated sources) emits an `audit_event("csv_export", user_sub, event_type=source)` call via `app/services/alerts.audit_event` (signature: `audit_event(event: str, user_sub: str, request=None, **fields)` at `app/services/alerts.py:644`). This is best-effort (wrapped in `try/except`); a failure to write the audit event must not abort the export. The existing three sources do not currently emit an audit event and their behavior is unchanged.

## 8. Backward Compatibility & Migration

**Zero schema migration**: No new DynamoDB tables, no GSI additions, no attribute-type changes. All four sources query existing tables with existing indexes.

**Existing sources unchanged**: The `billing_ledger`, `contacts`, and `questionnaire_responses` sources are byte-for-byte unmodified. The `generate_csv_rows` signature change (adding `is_admin=False`) is backward-compatible; existing callers pass no keyword and receive `False`.

**`VALID_SOURCES` set**: Widening the set and extending the regex does not break existing clients. Clients already passing `source=billing_ledger` continue to work. Clients passing an unknown source continue to receive HTTP 422.

**No endpoint change**: The path `GET /ui/export/csv` is unchanged. The new `source` values are only accessible when the flag is enabled.

**Flag-off default**: With `CRM_REPORTS_ENABLED=0` (default), the four new source values return HTTP 404 from the flag gate, so a client unaware of the flag cannot accidentally trigger a new behavior. Existing source values remain unaffected regardless of flag state.

## 10. Open Questions / Assumptions

1. **`contacts_crm` vs `contacts` naming**: The ticket spec uses `contacts_crm` as the new source name to avoid replacing the existing `contacts` behavior. If the product decision is to retire the old `contacts` source in favour of `contacts_crm`, that is a separate breaking-change ticket. This spec preserves both.

2. **Orders total amount**: The `orders` table (`T.orders`) stores order metadata only; line-item totals live in `T.order_items` (separate table, `scripts/local-ddb-init.py:295`). Including totals would require an O(N) secondary query per row. This spec omits totals from the initial implementation. A `?include_totals=true` query parameter enhancement is a reasonable follow-up.

3. **Admin ticket export scale**: The admin path iterates all 13 `_TICKET_STATUSES` partitions. On a platform with millions of tickets, this may be slow. A time-range filter (`from_date`/`to_date` applied to `created_at`) would reduce scope. For now the `MAX_EXPORT_ROWS = 50_000` cap provides an upper bound on rows and DDB read units.

4. **Subscription `pk` pattern variability**: Different subscription subsystems use different PK conventions (`SUBSCRIBER#`, `SUB#`, `SUBSCRIPTION#`). This spec targets the `SUBSCRIBER#` / `SUB#` pattern confirmed in `app/services/syndicate_subscriptions.py:407`. If other subscription types (e.g. fan club, standalone) use different keys, they will not appear in the export. A `SUBSCRIPTION_TYPE` column or separate sources per subscription type is a follow-up consideration.

5. **Date filtering for new sources**: `from_date` / `to_date` are silently ignored for the four new sources. This is consistent with how `contacts` currently behaves. Implementing per-source date filtering requires either a GSI with a numeric sort key (new schema for some tables) or a client-side filter that still reads all pages first. Deferred to a follow-up.

6. **RPT-001 co-landing**: This spec assumes RPT-001 (which defines `S.crm_reports_enabled`) lands in the same release or before. The defensive `getattr(S, "crm_reports_enabled", False)` fallback ensures the code is safe if deployed standalone.
