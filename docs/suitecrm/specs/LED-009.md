# LED-009 — Duplicate detection and merge for Leads

**Type:** Feature  **Priority:** P2  **Estimate:** 2 days  
**Ticket source:** `docs/suitecrm/CRM_LEADS_TICKETS.md`, section "LED-009"

---

## 1. Summary & Goal

LED-009 closes a real-world data-quality gap: Lead records created by multiple channels
(web-to-lead form capture in LED-005, bulk CSV import in LED-008, manual creation in
LED-003) will inevitably produce duplicates for the same person. SuiteCRM's bulk CSV
import includes duplicate detection as a built-in feature; the testlogon leads pipeline
needs the same.

This ticket delivers two capabilities that work together:

1. **Duplicate detection** — `find_duplicates(lead_id)` surfaces all Lead records that
   share the same normalized email address as a given lead, and optionally all records
   that share the same normalized phone number. Results are returned as a list of
   `LeadOut` objects so the caller (API consumer or LED-013's frontend drawer) can
   present a disambiguation UI.

2. **Merge** — `merge_leads(primary_lead_id, secondary_lead_id, actor_sub)` consolidates
   two Lead records into one canonical record. The primary record wins on every field
   conflict; non-null fields from the secondary are back-filled into the primary only
   where the primary field is null or empty. The secondary record is soft-deleted with
   `status="dead"` and a `merged_into` back-pointer. An `ACTIVITY#` row is written to
   the primary lead and an `audit_event` is emitted.

LED-009 is entirely additive. With `LEADS_ENABLED=0` (the default) the platform is
byte-for-byte unchanged: the two new service functions exist in `app/services/leads.py`
but are never invoked, and the two new router endpoints return HTTP 404.

The ByEmail GSI (`GSI4`) required by LED-009 was already introduced by LED-007 for
Prospect deduplication; LED-009 reuses it for Lead rows (same table, same index name,
same key schema). LED-009 also adds a new ByPhone GSI (`GSI5`) for phone-based duplicate
detection, with its corresponding `attr_types` declaration.

LED-007 introduced `GSI4PK = "EMAIL#{normalized_email}"` / `GSI4SK = created_at` (N)

`find_duplicates` can query `ByEmail` without any schema change to existing Lead rows.

However, the `ByEmail` GSI can return rows with `pk` prefixes `LEAD#` *and* `PROSPECT#`
(LED-007 writes Prospect rows to the same index). `find_duplicates` must filter to
`LEAD#` prefixes only (see §5.3).

## 3. Data Model

### 3.1 ByPhone GSI5 — new addition to the `leads` table

LED-009 adds a fifth GSI to the `leads` table established by LED-001 and extended
by LED-007.

| Attribute | GSI5 role | Value written on Lead/Prospect row |
|---|---|---|
| `GSI5PK` | Partition key (string) | `PHONE#{normalized_e164}` |
| `GSI5SK` | Sort key (number) | `{created_at}` (Unix integer) |

Index name: `ByPhone`. Projection: `ALL`.

`GSI5PK` is written on Lead rows when `phone` is present. Rows with no phone field
omit `GSI5PK` entirely — the GSI is sparse and only projects rows that carry
`GSI5PK`. This is the correct pattern for optional attributes: a missing `GSI5PK`
means the lead does not participate in phone-based duplicate detection, not that the
lead has no duplicates.

**Updated `scripts/local-ddb-init.py` `TableDef`** (supersedes LED-001 + LED-007 entries):

```python
TableDef(
    _resolve_table_name(S.leads_table_name, "leads"),
    "pk", "sk",
    gsi=[
        {"index_name": "ByOwner",  "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "ByStatus", "partition_key": "GSI2PK", "sort_key": "GSI2SK"},
        {"index_name": "BySource", "partition_key": "GSI3PK", "sort_key": "GSI3SK"},
        {"index_name": "ByEmail",  "partition_key": "GSI4PK", "sort_key": "GSI4SK"},  # LED-007
        {"index_name": "ByPhone",  "partition_key": "GSI5PK", "sort_key": "GSI5SK"},  # LED-009
    ],
    attr_types={
        "GSI1SK": "N",
        "GSI2SK": "N",
        "GSI3SK": "N",
        "GSI4SK": "N",   # LED-007
        "GSI5SK": "N",   # LED-009 — MUST declare N or DynamoDB raises ValidationException
    },
)
```

Omitting `"GSI5SK": "N"` causes DynamoDB to infer `S` (string) for the sort key,
yielding a `ValidationException` when queried with integer range expressions. This
follows the `attr_types` gotcha documented in CLAUDE.md: "Numeric GSI sort keys
must declare `attr_types={"<key>": "N"}`".

### 3.2 Lead META row additions

LED-009 adds two optional attributes to the Lead META row (written by `merge_leads`
on the secondary record; read-only on the primary):

| Attribute | Type | Notes |
|---|---|---|
| `merged_into` | S (optional) | `lead_id` of the primary when this lead was merged |
| `merged_at` | N (optional) | Unix timestamp when merge occurred |

These attributes are additive: all existing Lead rows continue to work without them.
`merged_into` serves as both a human-readable audit trail and a programmatic signal:
any code that processes Lead records should check `status == "dead"` first (the
standard soft-delete gate) and optionally follow `merged_into` to find the canonical
record.

### 3.3 Merge ACTIVITY row

Written to `T.leads` on the primary lead by `merge_leads`:

| Attribute | Value |
|---|---|
| `pk` | `LEAD#{primary_lead_id}` |
| `sk` | `ACTIVITY#{ts}#{activity_id}` (e.g., `ACTIVITY#1718000000#a3f7c9...`) |
| `activity_type` | `"merged_from"` |
| `actor_id` | `actor_sub` |
| `metadata` | `{"secondary_lead_id": secondary_lead_id, "fields_merged": [...]}` |
| `created_at` | `now_ts()` (integer) |

`ts` is `now_ts()` (integer, not zero-padded). `activity_id` is `uuid4().hex[:16]`.
`fields_merged` is a list of field names that were back-filled from the secondary
(e.g., `["phone", "company"]`). This row is compatible with the LED-012 activity
query interface (`SK=ACTIVITY#...` sort range), so the merge event appears naturally
in the lead's activity log once LED-012 is delivered.

### 3.4 GSI5PK write path

When `create_lead` (LED-003) creates a Lead with a non-null `phone`, it writes
`GSI5PK = "PHONE#{normalized_phone}"` and `GSI5SK = created_at` alongside the existing
GSI attributes. When `update_lead` (LED-003) adds or changes `phone`, it must also
update `GSI5PK` / `GSI5SK`. This is a write-path change to LED-003's functions;
the LED-009 spec makes these an explicit amendment to the LED-003 service rather
than a separate utility, keeping all GSI fan-out logic in one place within
`app/services/leads.py`.

### 4.1 New Pydantic models (`app/models.py`)

#### `find_duplicates(lead_id: str) -> list[dict]`

```python
def find_duplicates(lead_id: str) -> list[dict]:
    """Return all active Lead records that share the same normalized email
    and/or normalized phone as the given lead, excluding the lead itself.

    Algorithm:
    1. Fetch lead META row: get_lead(lead_id) → 404 if not found.
    2. Query ByEmail GSI:
         GSI4PK = "EMAIL#{lead.email}"
         KeyConditionExpression=Key("GSI4PK").eq(email_key)
         Loop via LastEvaluatedKey (FilterExpression does not reduce page size).
         Filter: pk.startswith("LEAD#") AND pk != f"LEAD#{lead_id}"
                 AND status not in {"dead"} (exclude soft-deleted).
    3. If lead.phone is not None:
         Query ByPhone GSI:
           GSI5PK = "PHONE#{lead.phone}"
           Same loop + filter pattern.
         Deduplicate against email results by lead_id.
    4. Collect matched_by dict: {lead_id: set("email"|"phone")} for
       building match_reason in the response.
    5. Return a list of raw item dicts (the router converts to LeadOut
       via the existing _item_to_lead_out helper from LED-003).

    Never raises on an empty result — returns [].
    """
```

Complexity: O(1) GSI lookups (email/phone are high-selectivity keys). In practice
the result list will be 0–5 items for real data; the loop is a safeguard against
theoretical hash collisions (multiple leads with the same email on a large tenant).

---

#### `merge_leads(primary_lead_id: str, secondary_lead_id: str, actor_sub: str) -> dict`

```python
def merge_leads(
    primary_lead_id: str,
    secondary_lead_id: str,
    actor_sub: str,
) -> dict:
    """Merge secondary_lead into primary_lead.

    Ownership check:
      Both leads must have created_by == actor_sub OR actor must be an admin
      (admin check deferred to router layer via require_admin_session; service
      receives actor_sub and trusts the router has already validated scope).

    Idempotency:
      If secondary.status == "dead" AND secondary.merged_into == primary_lead_id:
        return get_lead(primary_lead_id)  # already merged, no-op

    Conflict guard:
      If primary.status == "dead": raise HTTPException(409, "primary lead is deleted")
      If primary_lead_id == secondary_lead_id: raise HTTPException(400, "cannot merge a lead with itself")
      If secondary.status == "dead" AND secondary.merged_into != primary_lead_id:
        raise HTTPException(409, "secondary lead is already dead (merged elsewhere)")

    Field back-fill (primary wins):
      For each nullable field in MERGEABLE_FIELDS:
        if primary[field] is None/empty AND secondary[field] is not None/empty:
          updates[field] = secondary[field]
          fields_merged.append(field)

    Writes (transactional ordering):
      1. update_item on primary: apply updates dict + updated_at = now_ts()
         GSI fan-out: if phone was back-filled, also write GSI5PK/GSI5SK.
      2. update_item on secondary: status="dead", merged_into=primary_lead_id,
         merged_at=now_ts(), GSI2PK="STATUS#dead", GSI2SK=now_ts()
      3. put_item ACTIVITY# row on primary (§3.3).
      4. audit_event("lead.merged", actor_sub, primary_lead_id=primary_lead_id,
                     secondary_lead_id=secondary_lead_id,
                     fields_merged=fields_merged)

    Returns:
      get_lead(primary_lead_id) — the fully updated primary record dict.
    """
```

`MERGEABLE_FIELDS` is a module-level constant in `app/services/leads.py`:

```python
MERGEABLE_FIELDS = [
    "phone", "company", "title", "description", "website",
    "lead_source", "assigned_to", "attribution_code", "campaign_id",
]
```

`first_name`, `last_name`, `email`, `status`, and `score` are intentionally excluded
from back-fill: `email` and `phone` are identity fields (email already matched for
deduplication); `first_name`/`last_name` are identity fields where primary explicitly
wins; `status` is managed by the state machine; `score` is recomputed by LED-011.

**`GET /ui/leads/{lead_id}/duplicates`**

```python
@router.get("/{lead_id}/duplicates", response_model=LeadDuplicatesOut)
async def get_lead_duplicates(
    lead_id: str,
    ctx: dict = Depends(require_ui_session),
):
    _require_leads_enabled()
    dupes = find_duplicates(lead_id)
    return LeadDuplicatesOut(
        lead_id=lead_id,
        duplicates=[_item_to_lead_out(d) for d in dupes],
        match_reason=_compute_match_reason(lead_id, dupes),
    )
```

Response HTTP 200 with `{"lead_id": ..., "duplicates": [...], "match_reason": "email"}`.
Empty `duplicates` list (no duplicates found) is a valid 200 response, not a 404.

**`POST /ui/leads/{lead_id}/merge`**

```python
@router.post("/{lead_id}/merge")
async def merge_lead_endpoint(
    lead_id: str,
    body: MergeLeadsIn,
    ctx: dict = Depends(require_ui_session),
):
    _require_leads_enabled()
    result = merge_leads(
        primary_lead_id=lead_id,
        secondary_lead_id=body.secondary_lead_id,
        actor_sub=ctx["user_sub"],
    )
    return {
        "primary": _item_to_lead_out(result),
        "merge": MergeLeadsOut(
            primary_lead_id=lead_id,
            secondary_lead_id=body.secondary_lead_id,
            merged_at=result.get("updated_at", 0),
            fields_merged=result.get("_fields_merged_tmp", []),
        ),
    }
```

Note: `_fields_merged_tmp` is a transient key that `merge_leads` includes in its
return dict (not persisted to DynamoDB) so the router can populate `MergeLeadsOut`
without a second read. The router strips it before serialization.

CSRF: enforced automatically by `require_ui_session` on the `POST` verb when the
`ui_session` cookie is present (per `app/auth/deps.py`). Bearer-auth requests skip
CSRF.

HTTP status codes:
- `200` — merge succeeded
- `400` — same lead_id in primary and secondary
- `404` — primary lead not found or leads module disabled
- `409` — secondary already dead / primary is dead

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent merge (replay safety)

If `merge_leads(A, B, actor)` is called and then called again with the same arguments:
- After the first call, secondary (B) has `status="dead"` and `merged_into="A"`.
- The second call detects this condition at the top of `merge_leads` and returns
  `get_lead(primary_lead_id)` immediately without any DynamoDB writes.
- This makes the endpoint safe for at-least-once delivery scenarios (e.g., a network
  timeout after the server commits but before the client receives the response).

### 5.2 Merge of an already-merged secondary

If secondary B was previously merged into a *different* primary C (i.e.,
`B.merged_into == "C"` and `B.status == "dead"`), the caller is trying to merge
an already-consumed record. `merge_leads` raises HTTP 409
`"secondary lead is already dead (merged elsewhere)"`. The caller should refresh
their state and, if needed, merge A and C instead.

### 5.3 `ByEmail` GSI mixed Lead/Prospect results

`ByEmail` (GSI4) is shared by Lead rows (`pk = "LEAD#..."`) and Prospect rows
(`pk = "PROSPECT#..."`). `find_duplicates` applies
`FilterExpression=Attr("pk").begins_with("LEAD#")` on the GSI query result to
exclude Prospect rows. This prevents a Prospect from being surfaced as a Lead
duplicate. Per the CLAUDE.md DDB gotcha: the filter is applied server-side after
page fetch, so the loop must continue until `limit` Lead-matching rows are found
or all pages are exhausted.

### 5.4 Phone normalization and GSI5 sparseness

`normalize_phone` raises HTTP 400 for unrecognized formats (line 66,
`app/core/normalize.py`). The ByPhone GSI is sparse: only Lead rows that carry
`GSI5PK` participate. A Lead with no phone is invisible to phone-based duplicate
detection. This is by design — phone is optional and many leads will not have one.

When `phone` is updated via `update_lead` (LED-003):
- If the new phone is non-null: write `GSI5PK = "PHONE#{normalized}"` and
  `GSI5SK = now_ts()` alongside the other update attributes.
- If the new phone is explicitly cleared (empty string): remove `GSI5PK`
  and `GSI5SK` using `REMOVE` expressions in the `UpdateExpression`.

This ensures `ByPhone` stays consistent with the actual `phone` attribute on every
Lead row.

### 5.5 Scope guard — actor can only merge their own leads

`merge_leads` validates that both `primary.created_by == actor_sub` and
`secondary.created_by == actor_sub`. If either check fails, HTTP 403 is raised
(`"actor does not own both leads"`). Admin users bypass this check: the router
can optionally call `merge_leads` with `actor_sub=ctx["user_sub"]` after
`require_admin_session`, but `require_ui_session` (the default dep) does not
elevate scope automatically. The scope guard is a defense-in-depth measure against
cross-tenant data leakage.

### 5.6 Converted leads

A Lead with `status="converted"` has been linked to a Party record (LED-006). Merging
a converted lead requires caution:
- If the **primary** is `converted`: merge is allowed (the secondary's non-null fields
  may still enrich the primary). The converted status and `converted_party_id` are
  preserved on the primary; they are not in `MERGEABLE_FIELDS`.
- If the **secondary** is `converted`: `merge_leads` raises HTTP 409
  (`"cannot merge: secondary lead is already converted — dereference party link first"`).
  A converted secondary has a live PTY party record pointing to it; silently soft-deleting
  it could strand that party record. The caller must unlink the party first (via LED-006's
  conversion service), then re-attempt the merge.

### 5.7 Concurrent merge race

Two concurrent `POST /ui/leads/A/merge` requests with the same `secondary_lead_id=B`
will both read B as active and attempt to write. The second write to B (`status="dead"`)
will succeed silently because DynamoDB `update_item` (without a condition) is last-write-
wins. The result is that both requests complete successfully and the primary A receives
the field back-fill twice (idempotent, since fields_merged only writes fields that are
null on A). This is an acceptable outcome for low-write-rate CRM data. If strict
exactly-once is required in a future iteration, add
`ConditionExpression=Attr("status").ne("dead")` to the secondary's `update_item`.

### 5.8 Empty `fields_merged`

If the primary already has all mergeable fields populated, `fields_merged` is `[]`.
This is a valid successful merge. The secondary is still soft-deleted and an ACTIVITY
row is written — the merge is semantically "de-duplicate without enrichment". The
`MergeLeadsOut.fields_merged` list will be empty.

### 5.9 `lead_source` back-fill conflict

`lead_source` defaults to `"other"` on create (LED-002). Two leads for the same person
may have `lead_source="other"` on the primary and `lead_source="campaign"` on the
secondary. Under the "primary wins" rule, if the primary has `lead_source="other"`,
it does NOT get back-filled from the secondary because `"other"` is not null/empty.
This is by design: the primary record represents the known provenance. If the caller
wants the secondary's `lead_source`, they should instead designate the secondary as
the primary (swap the IDs in the merge request).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No `dev_mode` branch

LED-009 introduces zero `if S.dev_mode` branches. All DynamoDB reads and writes use
`T.leads` via the `_safe_table` proxy. In dev, `T.leads` resolves against DynamoDB
Local on port 8001; in prod, it resolves against real AWS DynamoDB. The code path is
identical (SECOPS-007). The `_safe_table` proxy in `app/core/tables.py` handles
`float`-to-`Decimal` coercion transparently.

### 7.2 Audit trail

`merge_leads` emits `audit_event("lead.merged", actor_sub, primary_lead_id=...,
secondary_lead_id=..., fields_merged=...)` via `app/services/alerts.audit_event` (line 644).
In dev, this writes to DynamoDB Local's `alerts` table. In prod, the same code path
writes to the real `alerts` table. No mock or log-only branch. Audit coverage:

| Event | Function |
|---|---|
| `lead.merged` | `merge_leads` — emitted after all DDB writes succeed |

`find_duplicates` is a read-only operation and does not emit an audit event. The
duplicate list itself is not sensitive; no PII is logged beyond the `lead_id`.

### 7.3 Idempotency

- `find_duplicates`: pure read, no state change, fully idempotent.
- `merge_leads`: idempotent on exact replay (same primary + secondary pair → §5.1).
  Not idempotent if secondary was previously merged into a different primary (§5.2).
- ACTIVITY row write: uses `uuid4().hex[:16]` suffix, so a retry generates a new
  activity ID and a duplicate row. This is acceptable (same as LED-012's `record_activity`
  pattern at `app/services/activity_feed.py:68`). The functional effect (merge outcome)
  is still idempotent.

### 7.4 Security — PII in GSI keys

`GSI4PK = "EMAIL#{normalized_email}"` and `GSI5PK = "PHONE#{normalized_e164}"` store
PII as DynamoDB attribute values (not as DynamoDB table/index names). This is an
established pattern in the codebase (e.g., the billing table uses `pk = "USER#{user_sub}"`).
Access to the `leads` table is controlled by IAM policy in prod. All API endpoints
require a valid session (no unauthenticated access). The ACTIVITY row's `metadata` dict
stores only `secondary_lead_id` and `fields_merged` — no PII.

### 7.5 Scope guard as security invariant

The `created_by == actor_sub` ownership check in `merge_leads` prevents a user from
soft-deleting another user's Lead by designating it as the secondary in a merge
request. This is enforced at the service layer, not just the router layer, so it
holds regardless of which router wraps the service.

### 7.6 No money-out path

LED-009 introduces no billing, payment, refund, or ledger operations. There are no
calls to `refund_payment` or `settle_or_reverse_ledger`. No financial primitives are
involved.

## 8. Backward Compatibility & Migration

### 8.1 GSI5 on an existing `leads` table

The `leads` table is new (introduced by LED-001). If LED-001 through LED-008 have been
deployed before LED-009, the table exists without GSI5:

- **Dev**: `just restart` drops and recreates the table with all five GSIs. No migration
  needed in the dev environment.
- **Prod (Option A, preferred)**: Deploy LED-001 through LED-009 in a single release.
  `scripts/local-ddb-init.py` creates the table with all five GSIs at once. No
  `UpdateTable` needed.
- **Prod (Option B, incremental)**: If the `leads` table exists without GSI5, add a
  one-time migration script `scripts/migrations/add-leads-gsi5.py`:
  ```python
  T.leads.meta.client.update_table(
      TableName=S.leads_table_name,
      AttributeDefinitions=[
          {"AttributeName": "GSI5PK", "AttributeType": "S"},
          {"AttributeName": "GSI5SK", "AttributeType": "N"},
      ],
      GlobalSecondaryIndexUpdates=[{
          "Create": {
              "IndexName": "ByPhone",
              "KeySchema": [
                  {"AttributeName": "GSI5PK", "KeyType": "HASH"},
                  {"AttributeName": "GSI5SK", "KeyType": "RANGE"},
              ],
              "Projection": {"ProjectionType": "ALL"},
          }
      }],
  )
  ```
  GSI backfill is asynchronous (minutes to hours). During backfill, `find_duplicates`
  may miss phone-based matches. Email-based detection is unaffected. `GET /duplicates`
  endpoints should document this transient limitation.

### 8.2 `GSI5PK` on existing Lead rows

Lead rows written by LED-003 before LED-009 ships do not carry `GSI5PK`. This means:
- `find_duplicates` on phone will not find pre-existing duplicate pairs where both
  leads predate LED-009.
- When either lead is updated via `update_lead` (with LED-009 applied), the phone
  update path writes `GSI5PK`, making that lead visible in future phone queries.

A backfill script can optionally scan all `LEAD#` rows with a non-null `phone` and
write `GSI5PK`/`GSI5SK`. This is not required for correctness (duplicate detection
degrades gracefully to email-only for old rows) but may be desired for data completeness.

### 8.3 `merged_into` attribute on existing rows

No existing Lead rows carry `merged_into` or `merged_at`. These attributes are
purely additive; any code that reads Lead rows and does not know about them simply
ignores them. `LeadOut` (LED-002) adds these as optional fields with `None` default.

### 8.4 No existing route conflicts

`GET /ui/leads/{lead_id}/duplicates` and `POST /ui/leads/{lead_id}/merge` are sub-paths
of the existing `/{lead_id}` dynamic route. FastAPI matches the literal sub-paths
`/duplicates` and `/merge` before treating `{lead_id}` as a path parameter — this is
the correct behavior for nested routes. No declaration-order change is needed relative
to the LED-013 router surface.

## 10. Open Questions / Assumptions

### 10.1 Fuzzy name matching

**Assumption**: LED-009 implements exact-match only (normalized email, normalized phone).
Fuzzy name matching ("John Smith" vs "J. Smith") is deferred to PTY-016
(`SUITECRM_GAP_ANALYSIS.md:49`). The LED-009 data model does not preclude adding
fuzzy scoring as a post-filter layer in a future ticket.

### 10.2 Cross-tenant duplicate detection

**Assumption**: `find_duplicates` only surfaces duplicates visible to the actor (via
the ownership scope guard). Two leads with the same email owned by different users are
not considered cross-tenant duplicates by LED-009. A future admin-level deduplication
sweep (if needed) would be a separate admin endpoint.

### 10.3 Merge of a Prospect into a Lead

SuiteCRM supports promoting a Target to a Lead. LED-009's `merge_leads` is scoped to
Lead-to-Lead merges only. Prospect-to-Lead promotion is a distinct operation deferred
to a future LED-007a ticket (`LED-007 spec §10.4`). `merge_leads` raises HTTP 400 if
either ID resolves to a `PROSPECT#` prefix rather than `LEAD#`.

### 10.4 `score` back-fill policy

`score` is excluded from `MERGEABLE_FIELDS` because it is managed by LED-011's scoring
engine. After a merge, `compute_score(primary_lead_id)` from LED-011 should ideally be
called to recompute the enriched lead's score. This best-effort call is out of scope for
LED-009 but could be added as a post-merge hook once LED-011 ships.

### 10.5 Bulk merge from import

LED-008's CSV import calls `create_lead` per row and uses `skip_duplicates=True` to
skip duplicate email rows. LED-009's `merge_leads` is an explicit user/admin action —
import does not auto-merge. An auto-merge-on-import mode could be added as a parameter
to `import_leads_from_csv` in a future enhancement.

### 10.6 GSI5SK vs GSI5PK ordering

The `ByPhone` GSI sort key (`GSI5SK = created_at`) is numeric and must be declared
`attr_types={"GSI5SK": "N"}`. If this declaration is omitted from `scripts/local-ddb-init.py`,
DynamoDB infers `S` (string) and raises `ValidationException` when `find_duplicates`
queries the GSI with a range condition. This is the same gotcha that affected GSI2SK,
GSI3SK, and GSI4SK in earlier LED tickets.
