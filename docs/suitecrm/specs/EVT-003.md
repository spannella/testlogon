# EVT-003 — CRM Event delegate/registration, acceptance/decline, attendance check-in

**Type:** Feature | **Priority:** P1 | **Estimate:** 3d  
**Source:** `docs/suitecrm/CRM_MISC_TICKETS.md` (section "EVT-003")  
**Dependencies:** EVT-002 (invitee management, `app/services/crm_events.py`, `app/routers/crm_events.py` all established there).

---

## 1. Summary & Goal

EVT-003 adds the delegate/registration workflow to the CRM Events module. After this ticket:

- Any platform user who has been invited to a CRM event (or, for open events, any authenticated user) can **self-register** for it. Duplicate registration is rejected with 409.
- A registered user can **accept or decline** their own registration, updating `status` and `responded_at` on the registration row.
- An event organiser (owner) or a user with `role >= ADMIN` can **check in** an attendee, setting `status="attended"` and `checked_in_at`.
- The event owner and admins can **list all registrations** for an event with cursor pagination.

The feature is entirely gated behind the `crm_events_enabled` flag introduced in EVT-001 (default `False`). With the flag off the platform is byte-for-byte identical to its pre-EVT-003 state. All persistence uses the `crm_event_registrations` table scaffolded in EVT-001; no new tables are introduced here. EVT-004 extends these rows with capacity/waitlist logic.

## 2. Context & Current State

### 2.1 crm_event_registrations table (EVT-001)

The `crm_event_registrations` DynamoDB table is declared in `scripts/local-ddb-init.py` by EVT-001 with:

### 2.5 In-app notification primitive

`app/services/alerts.write_alert` (`app/services/alerts.py:356`) writes a DDB item to `T.alerts` and publishes to the SSE stream. Used here to notify the registrant of acceptance/declination outcomes and notify the owner of a new registration.

`app/services/alerts.send_alert_email` (`app/services/alerts.py:459`) — in dev mode writes to the dev email log file; in prod sends via SES. Used in this ticket to notify the event owner when a new registration arrives and to confirm accept/decline to the registrant. ### 2.7 Cursor pagination

`app/core/cursor.encode_cursor` / `decode_cursor` (`app/core/cursor.py:94-131`) implement HMAC-signed opaque pagination cursors over DynamoDB `LastEvaluatedKey`. The `list_registrations` function uses these exactly as other list operations do (e.g., `list_invitees` in EVT-002).

### 2.8 DynamoDB conditional writes

Duplicate-registration rejection (409) uses `ConditionExpression="attribute_not_exists(event_id)"` on `put_item`. This is the same idempotency pattern used by cart recovery token consumption in `app/services/cart_reminders.py` (CLAUDE.md "Cart recovery links" gotcha), and by `app/services/kyc_cases.py` escalation conditional. If the condition fails, `botocore.exceptions.ClientError` with `Error.Code == "ConditionalCheckFailedException"` is raised; the service layer catches this and raises `HTTPException(status_code=409)`.

### 2.9 `now_ts()` for timestamps

`app/core/time.py:2-3` — returns `int(time.time())`. All `registered_at`, `responded_at`, `checked_in_at` fields are integer Unix seconds produced by `now_ts()`.

## 3. Data Model

### 3.1 Registration row in `crm_event_registrations`

Each registration is a single DDB item. **No new table is introduced by this ticket.** The table schema is fixed in EVT-001.

| Attribute | DDB Type | Nullable | Description |
|-----------|----------|----------|-------------|
| `event_id` | S (PK) | No | Stable event identifier (from `crm_events` META row) |
| `registrant_sub` | S (SK) | No | `user_sub` of the registrant |
| `status` | S | No | One of: `registered`, `accepted`, `declined`, `attended`, `waitlisted` |
| `registered_at` | N | No | Unix timestamp when row was first written (`now_ts()`); also the GSI `ByRegistrant` sort key |
| `responded_at` | N | Yes | Unix timestamp set when `respond_to_invitation` is called; absent until user responds |
| `checked_in_at` | N | Yes | Unix timestamp set by `check_in_attendee`; absent until check-in |
| `waitlist_position` | N | Yes | Assigned by EVT-004; absent for direct registrations |
| `invited` | BOOL | Yes | Set to `True` when the registrant also appears in `crm_events` as an `INVITEE#{sub}` row; allows distinguishing open-event walk-ins from explicitly invited delegates |

`registered_at` is declared `"N"` in `attr_types` by EVT-001, so the `ByRegistrant` GSI sort key is correctly typed without further changes to `scripts/local-ddb-init.py`.

**Status state machine:**

```
[new]
  │
  └─► registered  ──► accepted  ──► attended
       │                │
       └─► declined     └─► declined  (re-decision after accept)
       │
       └─► waitlisted  (EVT-004 only; not in this ticket)
```

`check_in_attendee` transitions any status → `attended`. EVT-004 may promote `waitlisted` → `registered`.

### 3.2 crm_events META row (read-only in this ticket)

`crm_events` PK=`event_id`, SK=`META` carries `owner_sub`, `max_attendance` (optional N), `name`, `calendar_event_id`. EVT-003 reads this row to resolve `owner_sub` for authorization and `max_attendance` for open-event check (deferred capacity enforcement to EVT-004). No writes to `crm_events` in this ticket.

### 3.3 No new GSIs

`ByRegistrant` (PK=`registrant_sub`, SK=`registered_at`) already supports "list all events a user registered for" — the only new list access pattern in EVT-003. The `list_registrations` endpoint scans by primary key (`event_id`) which is the table's own hash key — a `Query` on the base table, no GSI needed.

## 4. API / Service Design

### 4.1 Service additions to `app/services/crm_events.py`

All four functions are synchronous (the service has no async I/O). `T.crm_events` and `T.crm_event_registrations` are imported as module-level references from `app.core.tables`.

---

#### `register_for_event`

```python
def register_for_event(event_id: str, registrant_sub: str) -> dict:
    """
    Create a registration row for `registrant_sub` on `event_id`.

    Raises:
        HTTPException(404) if the event META row does not exist.
        HTTPException(409) if the user is already registered.
    Returns:
        The newly created registration item dict.
    """
```

Steps:
1. `get_item(Key={"event_id": event_id, "sk": "META"})` on `T.crm_events` — raises 404 if absent (event does not exist).
2. Set `invited = True` if an `INVITEE#{registrant_sub}` row exists on the same `event_id` partition; else `invited = False`.
3. Build item: `{"event_id": event_id, "registrant_sub": registrant_sub, "status": "registered", "registered_at": now_ts(), "invited": invited}`.
4. `put_item(Item=item, ConditionExpression="attribute_not_exists(event_id) AND attribute_not_exists(registrant_sub)")` — raises `ConditionalCheckFailedException` → caught → `HTTPException(409, "Already registered")`.
5. `audit_event("crm_event_registered", registrant_sub, event_id=event_id)`.
6. Best-effort: call `send_alert_email([owner_email], subject, body)` to notify the event owner of the new registration. Owner email is retrieved from `T.users` via `get_item(Key={"user_sub": owner_sub})` — `email` field. If lookup fails, skip silently.
7. Return the written item.

---

#### `respond_to_invitation`

```python
def respond_to_invitation(
    event_id: str,
    registrant_sub: str,
    new_status: Literal["accepted", "declined"],
    actor_sub: str,
) -> dict:
    """
    Accept or decline a registration.

    `actor_sub` must equal `registrant_sub` OR be the event owner_sub OR
    have role >= ADMIN (checked by the router before calling this function).

    Raises:
        HTTPException(404) if no registration row exists.
        HTTPException(400) if current status is 'attended' (terminal).
    Returns:
        The updated registration item dict.
    """
```

Steps:
1. `get_item(Key={"event_id": event_id, "registrant_sub": registrant_sub})` on `T.crm_event_registrations` — raises 404 if absent.
2. If current `status == "attended"`: raise `HTTPException(400, "Cannot change status after check-in")`.
3. `update_item` — SET `status = :s`, `responded_at = :t` with values `{":s": new_status, ":t": now_ts()}`.
4. `audit_event("crm_event_responded", actor_sub, event_id=event_id, registrant_sub=registrant_sub, new_status=new_status)`.
5. Best-effort `write_alert` for the registrant: title = "Event registration accepted" or "Event registration declined".
6. Return the updated item (re-fetch via `get_item` after update).

---

#### `check_in_attendee`

```python
def check_in_attendee(
    event_id: str,
    registrant_sub: str,
    actor_sub: str,
) -> dict:
    """
    Mark a registrant as attended.

    Authorization: `actor_sub` must be the event owner_sub OR have role >= ADMIN.
    This is checked by the router; the service trusts the caller.

    Raises:
        HTTPException(404) if no registration row exists.
        HTTPException(409) if already checked in.
    Returns:
        The updated registration item dict.
    """
```

Steps:
1. `get_item(Key={"event_id": event_id, "registrant_sub": registrant_sub})` — raises 404 if absent.
2. If current `status == "attended"`: raise `HTTPException(409, "Already checked in")`.
3. `update_item` — SET `status = "attended"`, `checked_in_at = :t` with `ConditionExpression="attribute_exists(event_id)"` (defensive; prevents a race where the row is deleted between get and update — should not occur in practice but guards correctly).
4. `audit_event("crm_event_checked_in", actor_sub, event_id=event_id, registrant_sub=registrant_sub)`.
5. Best-effort `write_alert` for the registrant: title = "You have been checked in to [event name]".
6. Return updated item.

#### `list_registrations`

```python
def list_registrations(
    event_id: str,
    limit: int = 50,
    cursor: str | None = None,
) -> dict:
    """
    Return a paginated list of all registration rows for `event_id`.

    Returns:
        {"registrations": [...], "cursor": str | None}
    """
```

Steps:
1. Build `Query` kwargs: `KeyConditionExpression=Key("event_id").eq(event_id)`, `Limit=limit`, optional `ExclusiveStartKey=decode_cursor(cursor)`.
2. Execute query on `T.crm_event_registrations` (base table, no GSI — `event_id` is the hash key).
3. Return `{"registrations": items, "cursor": encode_cursor(response.get("LastEvaluatedKey"))}`.

Note: `FilterExpression` does not reduce page size (CLAUDE.md DynamoDB gotcha). If status filtering is required by callers, add it as a `FilterExpression` with a loop over `LastEvaluatedKey`. For the initial implementation, no status filter is applied server-side — the response returns all statuses; the frontend filters client-side.

#### PUT `/{event_id}/registrations/{registrant_sub}/respond`

```
PUT /ui/crm/events/{event_id}/registrations/{registrant_sub}/respond
Auth: require_ui_session
Body: CrmRespondIn
Response: 200 CrmRegistrationOut
```

```python
@router.put("/{event_id}/registrations/{registrant_sub}/respond", response_model=CrmRegistrationOut)
async def respond_to_registration(
    event_id: str,
    registrant_sub: str,
    body: CrmRespondIn,
    ctx: dict = Depends(require_ui_session),
):
    _require_crm_events_enabled()
    caller = ctx["user_sub"]
    role = ctx["role"]
    # Resolve event owner for authorization
    meta = _get_event_meta_or_404(event_id)  # helper: get_item on crm_events
    is_owner = (caller == meta["owner_sub"])
    is_admin = role_allows_admin_features(role)
    is_own = (caller == registrant_sub)
    if not (is_own or is_owner or is_admin):
        raise HTTPException(status_code=403, detail="Not authorized to respond on behalf of this registrant")
    return respond_to_invitation(event_id, registrant_sub, body.status, actor_sub=caller)
```

`_get_event_meta_or_404` is a private router helper (or inline code) that calls `T.crm_events.get_item(Key={"event_id": event_id, "sk": "META"})` and raises 404 if absent.

@router.post("/{event_id}/registrations/{registrant_sub}/check-in", response_model=CrmRegistrationOut)

## 5. Detailed Behavior & Edge Cases

### 5.1 Double-registration prevention

`register_for_event` uses a DynamoDB conditional `put_item` with `ConditionExpression="attribute_not_exists(event_id) AND attribute_not_exists(registrant_sub)"`. Because `event_id` is the PK and `registrant_sub` is the SK, both must be absent for the write to succeed. A concurrent duplicate request loses the race and receives `ConditionalCheckFailedException` → HTTP 409. This is the canonical idempotency pattern (CLAUDE.md, "Cart recovery links" one-time-use pattern using the same `attribute_not_exists` conditional on `T.cart_reminder_config`).

### 5.2 Self-registration vs. invitee-only events

The ticket description states "any invitee (or any platform user if the event is open) can register." The current implementation does not enforce an invitee-only gate — any authenticated user may call `POST /{event_id}/register`. The `invited` boolean on the registration row records whether the caller was on the invitee list at registration time. A future ticket (e.g., EVT-004 or a separate access-control ticket) could add a boolean `invite_only` field on the META row and check it here. For EVT-003, the gate is left open to avoid blocking the workflow while access control is designed.

If the event META row does not exist (unknown `event_id`), `register_for_event` raises 404 before writing any registration row, preventing orphaned registrations.

### 5.3 respond_to_invitation authorization matrix

| Caller | Can respond on their own registration | Can respond on others' registrations |
|--------|---------------------------------------|--------------------------------------|
| Registrant (`caller == registrant_sub`) | Yes | No |
| Event owner | Yes (their own) | Yes (for all registrants) |
| ADMIN or ROOT | Yes (their own) | Yes (for all registrants) |
| Other USER | No | No → 403 |

### 5.4 Terminal status after check-in

Once `status == "attended"`, `respond_to_invitation` returns 400 ("Cannot change status after check-in"). This prevents an attendee from declining after being physically checked in. EVT-004's `_promote_from_waitlist` does not affect `attended` registrations.

### 5.5 check_in idempotency

A second check-in call for the same `(event_id, registrant_sub)` pair returns 409 ("Already checked in"). This prevents accidentally double-counting attendance in reporting.

### 5.6 Notification failure is non-blocking

All `write_alert` and `send_alert_email` calls inside service functions are wrapped in `try/except Exception: pass` (best-effort). A failed SES call or missing user email must never roll back a successful registration, response, or check-in.

### 5.7 list_registrations and DynamoDB FilterExpression gotcha

CLAUDE.md documents: "DynamoDB fetches up to 1MB *before* applying `FilterExpression`. Any query that filters a sparse attribute must loop via `LastEvaluatedKey`." The `list_registrations` implementation does not apply a `FilterExpression` in the base version. If a caller needs to filter by `status`, they must receive all pages and filter client-side, or a future ticket can add a paginating filter loop. The current implementation returns a single page with cursor for the next page — this is correct and consistent with all other list endpoints in the codebase.

### 5.8 respond_to_invitation re-decision

A user may call `respond_to_invitation` multiple times (e.g., accept then later decline). The `update_item` overwrites `status` and `responded_at` unconditionally (no condition expression). The audit log records each transition. This is intentional: real-world event management allows last-minute changes. EVT-004 hooks `decline` transitions to trigger waitlist promotion; EVT-003 does not implement that hook — it is explicitly deferred to EVT-004.

### 5.9 Registration of own-event by the owner

The event owner is not prevented from registering themselves. Their self-registration creates a row in `crm_event_registrations` identical to any other registrant's. The owner-authorization check in `check_in` and `list_registrations` uses `meta["owner_sub"]`, not the registrations table, so a self-registered owner is not confused with being "their own registrant."

### 5.10 Concurrency and capacity

EVT-003 does not enforce `max_attendance`. Even if the META row carries `max_attendance`, concurrent registrations beyond capacity are accepted and stored with `status="registered"`. EVT-004 introduces the atomic capacity counter and waitlist assignment. This is documented in `CRM_MISC_TICKETS.md` (EVT-003 calls into "EVT-004 waitlist logic" — meaning the capacity check is implemented in EVT-004 and *called from* `register_for_event`; EVT-003 provides the skeleton and EVT-004 fills in the guard).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007: No dev/prod branches in new code

No `if S.dev_mode:` branch is introduced in any service or router function. The `send_alert_email` call (`app/services/alerts.py:459-491`) handles dev vs. prod internally: dev writes to the log file at `S.dev_email_log`; prod sends via SES. The `write_alert` call (`app/services/alerts.py:356`) writes to DDB (`T.alerts`) identically in both environments. This is the same code path dev (DynamoDB Local) and prod (real DynamoDB) — SECOPS-007 parity is maintained.

### 7.2 Idempotency

| Operation | Idempotency guarantee |
|-----------|----------------------|
| `register_for_event` | Conditional `put_item`; second call → 409 (not a silent no-op, to prevent masking logic errors) |
| `respond_to_invitation` | `update_item` with no condition; calling twice with same `new_status` is a safe no-op (same value written); calling with a different `new_status` re-decides, which is intentional |
| `check_in_attendee` | Second call → 409 explicitly |
| `list_registrations` | Read-only; always idempotent |

### 7.3 Authorization and privilege escalation

Three authorization boundaries are enforced at the router layer before calling service functions:

1. **Registration** (`POST /{event_id}/register`): any authenticated user. No privilege escalation risk — the registrant is always `ctx["user_sub"]`; a caller cannot register another user's `user_sub` via this endpoint.

2. **Respond on behalf** (`PUT .../respond`): `caller == registrant_sub OR owner OR admin`. The `registrant_sub` path parameter is validated against the caller's identity or their role. Without this check, any authenticated user could accept or decline another user's invitation.

3. **Check-in and list** (`POST .../check-in`, `GET .../registrations`): owner or `role >= ADMIN` only. Non-owner users receive 403. The 403 response (not 404) is intentional here — the existence of the event is already disclosed by a successful prior `register` call; hiding the check-in endpoint with 404 would provide no security benefit.

`role_allows_admin_features(role)` from `app/auth/roles.py:60-61` is used for all admin checks. This function returns `True` for `Role.ADMIN` and `Role.ROOT`, consistent with the platform's RBAC model.

### 7.4 Input validation

`CrmRespondIn.status` is `Literal["accepted", "declined"]`. Pydantic rejects any other value before the handler executes. The `registrant_sub` and `event_id` path parameters are validated as non-empty strings by FastAPI's path parameter parsing; no additional length check is required (DDB PK/SK strings are limited to 2KB but platform user subs are short UUIDs/email addresses).

### 7.5 No money paths in this ticket

## 10. Open Questions / Assumptions

1. **Open vs. invite-only events.** EVT-003 allows any authenticated user to register, regardless of whether they were in the invitee list. The `invited` boolean records the distinction. If "invite-only" enforcement is needed, the META row should gain an `invite_only: bool` field and `register_for_event` should check it before writing. **Assumption:** enforcement is deferred to a follow-up ticket; EVT-003 ships with open registration.

2. **Email address resolution for notifications.** `send_alert_email` requires an email address. The service looks up `email` from `T.users` (`get_item(Key={"user_sub": owner_sub})`). The `users` table (`S.users_table_name`, `T.users`, `app/core/tables.py:77`) has a flat PK=`user_sub` with an `email` field. **Assumption:** this field is populated for all platform users by the registration flow. If missing, the email notification is silently skipped.

3. **respond_to_invitation caller resolution.** The current design allows the event owner to respond on behalf of any registrant. In some event management systems, only the registrant themselves can accept/decline (to prevent forged acceptances). **Assumption:** owner-on-behalf is allowed, consistent with the CRM use case of a coordinator managing RSVPs on behalf of corporate delegates. A future access-control ticket can restrict this.

4. **Registrant user existence.** `register_for_event` does not verify that `registrant_sub` is a valid platform user (`T.users` lookup). The only validation is that the event META row exists and the caller is authenticated. **Assumption:** `ctx["user_sub"]` from `require_ui_session` is always a valid, active user — the auth layer guarantees this. No additional user existence check is needed.

5. **`check_in_attendee` race with `respond_to_invitation`.** A concurrent accept and check-in could interleave. The `check_in_attendee` `update_item` does not require `status` to be `accepted` before transitioning — it allows check-in from any status including `registered` directly (walk-in scenario). EVT-004's capacity counter is updated only on `accepted` status, so a `registered → attended` direct transition may undercount capacity. **Assumption:** this edge case is deferred to EVT-004, which owns capacity accounting.

6. **PTY contact_id support.** If PTY-001 ships and invitees are identified by `contact_id` rather than `user_sub`, `register_for_event` needs a resolver. **Assumption:** EVT-003 uses `user_sub` throughout; a PTY bridge can be added in a later EVT ticket without breaking the DDB schema.
