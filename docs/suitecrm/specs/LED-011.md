# LED-011 — Lead scoring engine

**Type:** Feature  **Priority:** P2  **Estimate:** 2 days  
**Ticket source:** `docs/suitecrm/CRM_LEADS_TICKETS.md`, section "LED-011"

---

## 1. Summary & Goal

LED-011 adds a configurable, point-based lead scoring engine to the platform. Each lead record carries a numeric `score` (integer, 0–unbounded) that is recomputed automatically whenever the lead is updated and can be batch-recomputed by an admin. Scores are derived from a set of administrator-defined `ScoringRule` objects stored in the `leads` DynamoDB table. The engine is entirely additive — all new code lives in a new service file, rule storage reuses the existing `leads` table, and no existing route or service is modified when `S.leads_scoring_enabled` is `False`.

The goal is to surface a quick numeric signal that helps sales teams prioritize outreach: leads with complete profiles and high-value sources (e.g., `campaign`, `trade_show`) score higher than sparse records.

## 3. Data Model

### 3.1 Reuse of the `leads` table (LED-001)

All LED-011 rows are stored in the existing `leads` table (`T.leads`, PK=`pk`, SK=`sk`). No new DynamoDB table is required.

#### 3.1.1 Scoring configuration row

```
PK = SCORING_CONFIG
SK = RULES
```

Attributes:

| Attribute | Type | Description |
|-----------|------|-------------|
| `pk` | S | `"SCORING_CONFIG"` |
| `sk` | S | `"RULES"` |
| `rules` | List[Map] | Serialized `ScoringRule` objects (see §4.1) |
| `updated_at` | N | `now_ts()` of last save |
| `updated_by` | S | `user_sub` of saving admin |

This is a single-row config record; `get_item(Key={"pk": "SCORING_CONFIG", "sk": "RULES"})` is the full read. There is only one active rule set per deployment; versioning is tracked via `updated_at` rather than an explicit version counter.

#### 3.1.2 `score` field on lead META row

The `score` attribute is an integer `N` stored directly on the existing `LEAD#{lead_id}/META` row. The engine performs a conditional `update_item` to set `score = :new_score` (and `score_updated_at = :ts`) atomically. No additional row type is introduced.

#### 3.1.3 Score history row (optional, append-only)

To support auditing without a second table, each score recomputation that changes the score appends an `ACTIVITY#` row to the lead (same pattern as the activity rows already described in LED-001):

```
PK = LEAD#{lead_id}
SK = SCORE#{ts:010d}#{score_id}
```

Attributes: `lead_id`, `score_id` (8-char hex), `score` (N), `prev_score` (N), `trigger` (`"update"` | `"manual"` | `"rescore_all"`), `rules_version` (`updated_at` of the config row at compute time), `scored_at` (N).

These rows are written only when `score` changes. The score history is readable via `query(PK=LEAD#{lead_id}, SK begins_with SCORE#)` — no additional GSI needed.

### 3.2 `scripts/local-ddb-init.py` changes

No new `TableDef` is required because all rows share the existing `leads` table. However, the spec must confirm the existing table definition (LED-001) already includes the `leads` table entry. LED-011 adds no `attr_types` beyond those declared in LED-001, because the new `SCORE#...` SK is a string (lexicographic-order prefix, not numeric) and the `SCORING_CONFIG/RULES` row has no GSI projection.

## 4. API / Service Design

### 4.1 Service: `app/services/lead_scoring.py` (new file)

```python
from __future__ import annotations

import logging
from typing import Any, Optional
from uuid import uuid4

from boto3.dynamodb.conditions import Key
from app.core.settings import S
from app.core.tables import T
from app.core.time import now_ts

logger = logging.getLogger(__name__)

SCORING_RULES_PK = "SCORING_CONFIG"
SCORING_RULES_SK = "RULES"

# Supported conditions:
#   "present"  — field is truthy (non-empty, non-null)
#   "eq"       — field == value (string equality)
#   "in"       — field in value (value must be a list)
#   "not_present" — field is falsy / absent
VALID_CONDITIONS = {"present", "eq", "in", "not_present"}

# Fields that rules may reference
SCOREABLE_FIELDS = {
    "company", "phone", "title", "website", "description",
    "lead_source", "assigned_to", "status",
}

class ScoringRule(TypedDict):
    rule_id: str           # stable identifier, uuid4 hex[:8]
    field: str             # one of SCOREABLE_FIELDS
    condition: str         # one of VALID_CONDITIONS
    value: Any             # str, list[str], or None (for present/not_present)
    points: int            # positive (add) or negative (subtract)
    label: str             # human-readable description, max 200 chars


def validate_rules(rules: list[dict]) -> list[dict]:
    """Validate and normalise a list of raw rule dicts.
    Raises ValueError with a descriptive message on the first violation."""
    ...

def get_scoring_rules() -> list[dict]:
    """Read the active rule set from T.leads (SCORING_CONFIG/RULES).
    Returns an empty list if no rules have been saved yet."""
    resp = T.leads.get_item(Key={"pk": SCORING_RULES_PK, "sk": SCORING_RULES_SK})
    return resp.get("Item", {}).get("rules", [])

def save_scoring_rules(rules: list[dict], *, actor_sub: str) -> dict:
    """Validate and persist a new rule set. Admin-only (enforced at router layer).
    Returns the saved config row."""
    ...

def compute_score(lead_id: str, *, trigger: str = "update") -> int:
    """Evaluate active rules against the lead and persist the new score.

    - Reads the lead META row; returns 0 immediately (no write) if not found.
    - Loads the scoring config (SCORING_CONFIG/RULES); returns 0 if none saved.
    - Evaluates each rule independently; per-rule errors are logged and skipped.
    - Computes new_score = max(0, sum of matching rules' points).
    - Writes score + score_updated_at onto the lead META row via update_item
      (conditional on lead existing — ConditionExpression=attribute_exists(pk)).
    - If new_score != prev_score, appends a SCORE# history row.
    - Emits audit_event("lead.score_computed", ...) if score changed.
    - Returns new_score.
    - Is idempotent: calling twice with the same rules and lead fields
      writes the same score both times (no row duplication; the SCORE# row
      is guarded by attribute_not_exists on the SK).
    - Never raises: wrapped in try/except at call sites; returns 0 on error.
    """
    ...

def _evaluate_rule(rule: dict, lead: dict) -> bool:
    """Return True if the rule matches the lead's current field values."""
    ...

async def rescore_all_leads(*, actor_sub: str) -> dict:
    """Fan out compute_score() over all lead META rows.

    Scans T.leads using FilterExpression=begins_with(sk, "META") and
    SK == "META" (via FilterExpression), collecting each LEAD#{id}/META item.
    Processes them sequentially (no concurrent DDB bursts) with await
    asyncio.sleep(0) between batches of 25 to yield the event loop.
    Returns {"queued": N, "actor_sub": actor_sub}.
    """
    ...
```

#### 4.1.1 `compute_score` DDB write details

The score is written via a targeted `update_item`:

```python
T.leads.update_item(
    Key={"pk": f"LEAD#{lead_id}", "sk": "META"},
    ConditionExpression="attribute_exists(pk)",
    UpdateExpression="SET score = :s, score_updated_at = :ts",
    ExpressionAttributeValues={":s": new_score, ":ts": now_ts()},
)
```

The `SCORE#` history row is written only when `new_score != prev_score`. The conditional `attribute_not_exists` on the score history SK prevents duplicates on retry:

```python
T.leads.put_item(
    Item={
        "pk": f"LEAD#{lead_id}",
        "sk": f"SCORE#{ts:010d}#{score_id}",
        "score": new_score,
        "prev_score": prev_score,
        "trigger": trigger,
        "rules_version": config_row.get("updated_at", 0),
        "scored_at": ts,
    },
    ConditionExpression="attribute_not_exists(sk)",
)
```

The history row `put_item` failure (e.g., race on the same-second retry) is caught and logged at DEBUG level — it must not abort the main score write.

## 5. Detailed Behavior & Edge Cases

### 5.1 Rule evaluation semantics

Each `ScoringRule` is evaluated independently against the lead's current fields. Evaluation order is deterministic (list order as saved). The final score is:

```
score = max(0, sum(rule.points for rule in rules if _evaluate_rule(rule, lead)))
```

Scores never go below 0 (the `max(0, ...)` guard).

| Condition | Match logic |
|-----------|-------------|
| `present` | `bool(lead.get(field))` is truthy — non-empty string, non-None |
| `not_present` | `not bool(lead.get(field))` |
| `eq` | `str(lead.get(field, "")) == str(rule["value"])` |
| `in` | `str(lead.get(field, ""))` is a member of `rule["value"]` list |

Unknown `condition` values: `_evaluate_rule` returns `False` and logs a warning — never raises.

### 5.2 Idempotency of `compute_score`

Calling `compute_score(lead_id)` twice with unchanged rules and lead fields produces the same integer and writes the same value via `update_item`. The second `SCORE#` history row `put_item` uses `ConditionExpression="attribute_not_exists(sk)"`. If the SK collides (same-second trigger), the conditional put fails with `ConditionalCheckFailedException`, which is caught and swallowed — idempotency is preserved and no duplicate history row is written.

### 5.3 Flag-off behavior

When `S.leads_scoring_enabled` is `False`:
- `compute_score` returns `0` immediately without reading T.leads.
- The `update_lead` hook (§4.4) is skipped entirely (guarded by `if S.leads_scoring_enabled`).
- All three admin endpoints (`/scoring/rules`, `/rescore-all`) return 404 via a top-level guard in the router: `if not S.leads_scoring_enabled: raise HTTPException(status_code=404)`.
- Existing leads retain whatever `score` they had (unchanged).
- `LeadOut.score` defaults to `0` on new leads.

When `S.leads_enabled` is `False` but `S.leads_scoring_enabled` is `True`, the scoring endpoints also return 404 (the leads router itself is gated on `S.leads_enabled`).

### 5.4 `rescore_all_leads` fan-out behavior

The fan-out coroutine scans `T.leads` with a `FilterExpression` of `SK = :meta` (attribute `sk = "META"`) and collects all `LEAD#...` rows. It processes them in batches of 25, yielding the event loop between batches via `await asyncio.sleep(0)`. The scan loops via `LastEvaluatedKey` (per the CLAUDE.md gotcha: "DDB FilterExpression doesn't reduce page size"). A failed `compute_score` for one lead is caught and counted in a per-run error tally; it does not abort processing of remaining leads.

### 5.5 Save-rules validation

`validate_rules` raises `ValueError` (caught by the router and re-raised as HTTP 422) in these cases:
- Any `field` is not in `SCOREABLE_FIELDS`.
- Any `condition` is not in `VALID_CONDITIONS`.
- A rule with `condition=eq` has `value=None`.
- A rule with `condition=in` has a non-list `value` or an empty list.
- A rule with `condition` in `{present, not_present}` has a non-None `value` (extra strictness — callers should not pass stale values for these conditions).
- `points == 0` (zero-point rules are useless and indicative of a bug).
- Duplicate `rule_id` values within the same batch.
- More than 100 rules total (also enforced by `SaveScoringRulesIn.rules` field max_length).

### 5.6 Score read path — `LeadOut.score`

The `score` field is read directly from the `LEAD#{id}/META` DDB item by `get_lead`. No separate scoring query is needed at read time.

### 5.7 `compute_score` on a newly created lead

`create_lead` (LED-003) does not call `compute_score`. The score starts at `0`. It is first computed when the lead is next `update_lead`-ed (the hook in §4.4 fires). Admins can trigger an immediate rescore via `POST /ui/admin/leads/rescore-all` or by calling the future LED-013 detail UI which may surface a "Rescore" button.

### 5.8 Negative point rules

Rules with `points < 0` reduce the score. The final `max(0, sum(...))` ensures the score never goes negative. A lead scoring below 0 before the clamp is indistinguishable from one that exactly hits 0 — this is intentional (no "negative priority" concept is exposed).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

The scoring engine is DynamoDB-only and has no AWS-service dependency beyond `T.leads`. There is no `dev_mode` branch, no mock code path, and no `if S.dev_mode` conditional anywhere in `app/services/lead_scoring.py`. The same code runs against DynamoDB Local in dev and against real DynamoDB in production.

### 7.2 Idempotency

`compute_score`: idempotent by design (§5.2). `save_scoring_rules`: last-write-wins; there is no optimistic locking on the config row (admin tooling, low contention). `rescore_all_leads`: safe to run multiple times; each invocation re-evaluates from current rules and current lead state.

### 7.3 Access control

- `GET/POST /ui/admin/leads/scoring/rules`: `require_admin_or_root` — role checked via `app/auth/policy.py:67`.
- `POST /ui/admin/leads/rescore-all`: `require_admin_or_root`.
- `GET /ui/leads/{lead_id}/score-history`: `get_authenticated_user`; ownership check (`created_by` or `assigned_to`) before returning data.

CSRF: all non-GET cookie-auth requests enforce CSRF automatically via `require_ui_session` in `app/auth/deps.py`.

### 7.4 Data sensitivity

`ScoringRule` objects contain no PII — they reference field names and literal comparison values (`"campaign"`, `True`, etc.). Score history rows contain only numeric scores and timestamps. No KMS encryption is required.

### 7.5 Score integer overflow

Points per rule are bounded at ±1000 by the Pydantic model (`ge=-1000, le=1000`). With a max of 100 rules all firing at +1000, the ceiling is 100,000 — safely within DynamoDB's Number type range. DynamoDB stores the value as a `Decimal`; `int()` coercion at read time is sufficient.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact with flag off

With `LEADS_SCORING_ENABLED=0` (default), no new code path executes, no new DDB reads/writes occur, and no existing endpoint changes behavior. The `score` field in `LeadOut` continues to read as `0` for all existing leads.

### 8.2 Existing leads after flag-on

When the flag is turned on, existing leads have `score=0` until they are next updated (triggering the `update_lead` hook) or until an admin runs `POST /ui/admin/leads/rescore-all`. There is no automatic backfill at flag-on time. The `rescore-all` endpoint is the recommended migration path.

### 8.3 No table schema changes

The `leads` table schema (defined in LED-001) already includes `PK=pk / SK=sk`. The new `SCORING_CONFIG/RULES` and `SCORE#...` rows use string keys that fit the existing schema without any `UpdateTable` or backfill. The `score` attribute on `META` rows is a numeric attribute added by `update_item`, which DynamoDB accepts without a schema change (schemaless attribute model).

### 8.4 Rule format versioning

Rules are serialized as a plain JSON list on the DDB item. No formal schema version is embedded in the row. If the rule schema needs to evolve (e.g., adding `weight` per rule), a migration script can read and rewrite the `SCORING_CONFIG/RULES` row. The `validate_rules` function acts as the authoritative validator and should be updated in lockstep.

## 10. Open Questions / Assumptions

1. **Score ceiling** — The spec does not define a maximum score. The current design sums all matching rule points (clamped at 0). If a "normalized 0-100" display is desired in the frontend, that is a UI concern and can be implemented as `min(100, score)` in `LeadOut` serialization without changing the underlying storage. **Assumption:** raw unbounded integer is stored; the UI may cap display.

2. **Rule execution order matters for auditing, not correctness** — Rules are evaluated in list order (as saved). Reordering rules does not change the final score (addition is commutative). The order is preserved only for human-readability of `label` strings. **Assumption:** no rule priority / ordering semantics needed.

3. **Behavioral signal fields** — The ticket description mentions "behavioral signals" alongside profile criteria, but the `leads` table as defined in LED-001 through LED-010 contains only profile and status fields, not behavioral events (calls made, emails opened, site visits). **Assumption:** behavioral signals are deferred to a future ticket; LED-011 scores only on the static profile fields available in `SCOREABLE_FIELDS`. If LED-012's `ACTIVITY#` rows are later used as signals, `compute_score` can be extended to query those rows without changing the rule schema.

4. **Score recomputation on `create_lead`** — The hook is wired only in `update_lead`, not `create_lead`. Newly created leads start at `score=0`. **Assumption:** this is acceptable for MVP; if immediate scoring on create is needed it can be added to LED-003's `create_lead` in a follow-on.

5. **`rescore_all_leads` fan-out latency** — On a busy `leads` table with thousands of records, the scan-and-recompute loop may take minutes. The endpoint returns immediately (`status=queued`) and the background coroutine runs non-blocking. **Assumption:** no progress visibility (WebSocket/SSE) is required for MVP.

6. **Rule storage in DDB vs. env var** — Rules are persisted in DynamoDB (not in environment variables or a config file) so they can be changed without a deployment. The admin endpoint is the only write path. **Assumption:** this is the correct choice; if audit-trail-heavy governance is needed, LED-011 history rows and `audit_event` calls provide sufficient traceability.
