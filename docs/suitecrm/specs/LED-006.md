# LED-006 — Lead conversion to Party + Opportunity stub

**Type:** Feature  **Priority:** P1  **Estimate:** 2 days  
**Ticket source:** `docs/suitecrm/CRM_LEADS_TICKETS.md`, section "LED-006"

---

## 1. Summary & Goal

LED-006 implements `POST /ui/leads/{lead_id}/convert`, the one-click conversion flow that promotes a Lead record into the broader CRM graph: a PERSON Party (individual contact) and, optionally, a PARTY_GROUP Party (organizational account), with a lightweight Opportunity stub recording the deal value.

After conversion the lead's `status` transitions to `"converted"` and the lead META row carries back-links (`converted_party_id`, `converted_org_id`, `converted_at`, `opportunity_id`) that allow downstream modules to correlate the origin lead with full CRM entities.

The implementation has two execution paths:

- **PTY path** (when `S.party_crm_enabled` is `True`): delegates to `app/services/party.py` functions delivered by PTY-004 through PTY-008 — `ensure_person_party` (PTY-010), `find_party_by_contact` (PTY-007), and `create_org_account` (PTY-008). This is the production-grade path.
- **Stub path** (when `S.party_crm_enabled` is `False`): writes minimal inline PERSON and ORG child rows directly into the `leads` table. This shim decouples LED-006 delivery from PTY delivery and is documented as removable once PTY ships.

The Opportunity stub is always written into the `leads` table (regardless of PTY availability) as a `LEAD#{lead_id}/OPPORTUNITY#META` child row. No dedicated Opportunity table is required at this stage; the full Opportunity module is reserved for a SALES-001/002 backlog item.

The entire feature is gated by `S.leads_enabled` (LED-001, default `False`). With the flag off, the endpoint returns 404 and no existing code path is touched.

|---|---|---|
| `status` | S | `"converted"` |

`LeadConversionOut` fields mirror what LED-002's `LeadOut` gains (`converted_at`, `converted_party_id`, `converted_org_id`), extended with the opportunity summary and a diagnostic flag `pty_path_used` that callers can use to detect which code path ran.

### 4.2 Service function `convert_lead`

Added to `app/services/leads.py` (the module created by LED-003):

```python
def convert_lead(
    lead_id: str,
    actor_sub: str,
    data: LeadConversionIn,
) -> LeadConversionOut:
```

**Execution steps (all synchronous; called via `asyncio.to_thread` at the router layer):**

1. **Flag guard**: `if not S.leads_enabled: raise HTTPException(503, "Leads module is not enabled")`.
2. **Load lead**: `lead = get_lead(lead_id)`. Raise `HTTPException(404, "Lead not found")` if `None`.
3. **Already-converted guard**: if `lead["status"] == "converted"`, raise `HTTPException(409, "Lead already converted")`. This is idempotency's hard boundary — a second conversion attempt is rejected, not silently replayed, because the caller must confirm intent.
4. **Deleted guard**: if `lead.get("deleted_at")` is set, raise `HTTPException(410, "Lead has been deleted")`.
5. **Branch on PTY availability** (`S.party_crm_enabled`):
   - **PTY path** (`True`): see §4.3.
   - **Stub path** (`False`): see §4.4.
6. **Opportunity stub**: if `data.create_opportunity` is `True`, call `_create_opportunity_stub(lead_id, actor_sub, data)` (§4.5). Store the returned `opportunity_id`.
7. **Update lead META**: call `_finalize_conversion(lead, actor_sub, converted_party_id, converted_org_id, opportunity_id)` which rewrites the lead item via delete+re-put (GSI2PK changes to `"STATUS#converted"`).
8. **Audit**: `audit_event("lead.converted", actor_sub, lead_id=lead_id, converted_party_id=converted_party_id, converted_org_id=converted_org_id, pty_path=S.party_crm_enabled)`.
9. **Return** `LeadConversionOut(...)`.

### 4.3 PTY path (`S.party_crm_enabled=True`)

The following calls use lazy imports (`from app.services import party as _party`) to avoid a hard circular import. Each call is individually wrapped in a `try/except ImportError` so that a missing PTY module at import time causes graceful fallthrough to the stub path rather than a 500:

```python
try:
    from app.services import party as _party_module
    _pty_available = True
except ImportError:
    _pty_available = False

if S.party_crm_enabled and _pty_available:
    # Step A: find or create PERSON party by email
    matches = _party_module.find_party_by_contact("EMAIL", lead["email"])
    if matches:
        person_party_id = matches[0]["party_id"]
    else:
        # create_party("PERSON", correlation_id=f"LED:PERSON:{lead_id}")
        person_dict = _party_module.create_party(
            "PERSON",
            correlation_id=f"LED:PERSON:{lead_id}",
        )
        person_party_id = person_dict["party_id"]
        # back-fill email mech
        _party_module.add_contact_mech(
            person_party_id, "EMAIL", lead["email"],
            purposes=["PRIMARY_EMAIL"],
            correlation_id=f"MECH:EMAIL:LED:{lead_id}",
        )
        if lead.get("phone"):
            _party_module.add_contact_mech(
                person_party_id, "PHONE", lead["phone"],
                purposes=["PRIMARY_PHONE"],
                correlation_id=f"MECH:PHONE:LED:{lead_id}",
            )
    # Step B: org account (optional)
    org_party_id = None
    if data.create_account:
        name = data.account_name or lead.get("company") or f"{lead['first_name']} {lead['last_name']}"
        org_dict = _party_module.create_org_account(
            name,
            owner_user_sub=actor_sub,
            correlation_id=f"LED:ORG:{lead_id}",
        )
        org_party_id = org_dict["party_id"]
```

`find_party_by_contact` returns all parties matching the email (PTY-007 `docs/ofbiz/specs/PTY-007.md:136`). We use the first match if any exist, avoiding duplicate parties for the same email. The `correlation_id` on `create_party` / `add_contact_mech` / `create_org_account` makes these calls idempotent per the deterministic-id pattern established by PTY-004 (`docs/ofbiz/specs/PTY-004.md:§2.3`) and PTY-007.

### 4.5 Opportunity stub creation

```python
def _create_opportunity_stub(
    lead_id: str,
    actor_sub: str,
    data: LeadConversionIn,
    lead: dict,
) -> str:
    opportunity_id = "opp_" + uuid4().hex[:20]
    name = (data.opportunity_name or
            f"Opportunity from {lead['first_name']} {lead['last_name']}")
    T.leads.put_item(Item={
        "pk": f"LEAD#{lead_id}",
        "sk": "OPPORTUNITY#META",
        "opportunity_id": opportunity_id,
        "lead_id": lead_id,
        "name": name,
        "amount_cents": data.opportunity_amount_cents or 0,
        "currency": "USD",
        "stage": "prospecting",
        "created_by": actor_sub,
        "created_at": now_ts(),
        "converted_from_lead_id": lead_id,
    })
    return opportunity_id
```

`put_item` without a condition expression allows idempotent overwrites on retry (the opportunity_id changes each retry since it is random, but the SK `OPPORTUNITY#META` is fixed per lead, so only one opportunity stub can exist per lead). A race condition between two concurrent conversions of the same lead is handled by the step-3 already-converted guard: the first writer to complete step 7 sets `status=converted`; the second hits the 409 guard at step 3.

### 4.6 Lead finalization helper

```python
def _finalize_conversion(
    lead: dict,
    actor_sub: str,
    converted_party_id: str,
    converted_org_id: Optional[str],
    opportunity_id: Optional[str],
) -> dict:
    ts = now_ts()
    updated = {**lead}
    updated["status"] = "converted"
    updated["converted_at"] = ts
    updated["converted_party_id"] = converted_party_id
    updated["updated_at"] = ts
    updated["GSI2PK"] = "STATUS#converted"
    updated["GSI2SK"] = ts
    if converted_org_id:
        updated["converted_org_id"] = converted_org_id
    if opportunity_id:
        updated["opportunity_id"] = opportunity_id
    # GSI2 key has changed: delete old item, re-put updated item
    T.leads.delete_item(Key={"pk": lead["pk"], "sk": "META"})
    T.leads.put_item(Item=updated)
    return updated
```

This is the same delete+re-put pattern used by `update_lead` in LED-003 (`docs/suitecrm/specs/LED-003.md:178`) when the status GSI key changes. It is not atomic, but the conversion flow's already-converted guard provides adequate protection for MVP.

## 5. Detailed Behavior & Edge Cases

### 5.1 Already-converted lead (409)

A lead with `status="converted"` cannot be converted again. The service raises `HTTPException(409, "Lead already converted")` at step 3. This is not idempotent: callers must not retry a conversion without confirming intent. The 409 response body must include `{"detail": "Lead already converted", "lead_id": lead_id, "converted_at": lead["converted_at"]}` so the caller can retrieve the existing conversion result without a separate GET.

### 5.2 Concurrent conversion race

If two requests attempt conversion of the same lead simultaneously, both read `status != "converted"` and proceed to step 7. The delete+re-put in `_finalize_conversion` is not atomic. Both writes succeed (last writer wins on the re-put). Both also create PERSON stubs (or PTY parties), but the PTY `find_party_by_contact` / `create_party` calls use `correlation_id`-based idempotency so a second PTY party is not created. On the stub path, two PERSON stubs with different `person_id` values may be written; the lead's `converted_party_id` reflects whichever writer completed step 7 last. For MVP this race window is acceptable. A future follow-up can add a conditional update with `ConditionExpression="attribute_not_exists(converted_at)"` to make step 7 atomic.

### 5.3 `create_account=True` without `account_name` and no company

The service falls back: `name = data.account_name or lead.get("company") or f"{lead['first_name']} {lead['last_name']}"`. This always produces a non-empty name, so the ORG row is always written. The fallback name may be a person name rather than a company name; the caller is responsible for supplying `account_name` or ensuring the lead has a `company` field.

### 5.4 PTY module import failure

If `S.party_crm_enabled` is `True` but `app.services.party` does not exist (i.e., PTY-004 has not been deployed), the `try/except ImportError` in §4.3 catches the error, sets `_pty_available = False`, and the service falls through to the stub path. The `pty_path_used=False` field in `LeadConversionOut` signals this to the caller. An operator alert should be raised when this mismatch is detected (the stub path sets `pty_path_used=False` while `S.party_crm_enabled` is `True`); monitoring is out of scope for this ticket.

### 5.5 PTY `create_party` / `create_org_account` failure

If the PTY calls succeed partially (e.g., PERSON party created but ORG creation fails), the service propagates the exception from `create_org_account` and the lead remains in its pre-conversion status. No partial conversion state is committed because step 7 (`_finalize_conversion`) has not yet run. The PTY idempotency guarantees that a retry that gets past step 3 will reuse the already-created PERSON party (via `find_party_by_contact` or the `correlation_id` conditional write) without creating a duplicate.

### 5.6 Opportunity stub on a re-put collision

If the same `LEAD#{lead_id}/OPPORTUNITY#META` row already exists (e.g., from a partial prior attempt that failed before step 7), `_create_opportunity_stub` overwrites it. The `opportunity_id` on the overwrite is a new random value, which means the old ID is orphaned. For MVP this is acceptable; a conditional `attribute_not_exists(pk)` can be added as a follow-up.

### 5.7 Flag-off behavior

When `S.leads_enabled=False`, the endpoint handler raises `HTTPException(404)` before calling `convert_lead`. The leads service is never imported by main.py when the flag is off (the router import is conditional, per LED-013 design). No existing table, route, or middleware is affected.

### 5.8 Deleted lead conversion

A lead with `deleted_at` set raises `HTTPException(410, "Lead has been deleted")`. Deleted leads cannot be converted; the caller must restore the lead (update status back to `"new"`) before converting.

### 5.9 `create_opportunity=False` (default)

No opportunity row is written and `LeadConversionOut.opportunity` is `None`. The lead META row gets no `opportunity_id` attribute.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

No `dev_mode` or `S.dev_mode` branch exists in `convert_lead` or its helpers. Both the PTY path and the stub path write to DynamoDB using the same code in dev and prod. The moto in-process mock intercepts DynamoDB calls in dev; the real DynamoDB endpoint is used in prod. The `T.leads` handle (`_safe_table`) and `T.party` handle are the only external dependencies — both are wired identically in all environments.

The stub path is not a dev-only path. It is a valid production fallback for the period before PTY-001 through PTY-010 are deployed. It is documented as removable (not `dev_mode`-gated).

### 7.2 Idempotency guarantees

| Operation | Idempotent? | Mechanism |
|---|---|---|
| Second conversion attempt | No (409) | `status == "converted"` guard |
| PTY PERSON party creation | Yes | `correlation_id=f"LED:PERSON:{lead_id}"` → deterministic ID, conditional put in PTY-004 |
| PTY ORG account creation | Yes | `correlation_id=f"LED:ORG:{lead_id}"` → conditional put in PTY-008 |
| Opportunity stub write | Overwrite (last-write-wins) | `put_item` without condition; MVP acceptable |
| `_finalize_conversion` | Last-write-wins | Delete+re-put; already-converted guard prevents second attempt reaching step 7 |

### 7.3 No money-out operations

LED-006 involves no billing, payment, or refund. No `refund_payment` or `settle_or_reverse_ledger` call is made. No `billing` table is touched.

### 7.4 No S3 or KMS operations

No file upload, no KMS encrypt/decrypt. LED-006 reads and writes DynamoDB only.

### 7.5 Actor isolation

`convert_lead` receives `actor_sub` from the authenticated session (injected by `require_ui_session`). The audit record carries `actor_sub` so the conversion is attributable. The lead's ownership is not enforced by LED-006 itself (a user can convert any lead they can read). Role-scoped access control — restricting conversion to the lead's assigned owner or to admins — is deferred to LED-013's router layer, which can add a role check before calling `convert_lead`.

### 7.6 PII in stub rows

Inline PERSON stub rows store `email`, `first_name`, `last_name`, and optionally `phone` — PII. These rows live in the `leads` table, which should be protected by the same IAM policies as the main `leads` data. The `_stub=True` flag makes them identifiable for future data-minimization or migration workflows. No additional encryption is applied beyond standard DynamoDB server-side encryption.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact when `LEADS_ENABLED=0`

The convert endpoint is registered only when LED-013 imports `app/routers/leads.py`. With `S.leads_enabled=False`, LED-013 (following the pattern of feature-gated routers) either skips the import or the endpoint handler returns 404 immediately. Either way no existing route, table, or behavior changes.

### 8.2 Stub-to-PTY migration

Once PTY-001 through PTY-010 are deployed and `S.party_crm_enabled` is turned on, a one-time migration script should:

1. Scan the `leads` table for items with `SK=META`, `status=converted`, and `converted_party_id` starting with `"PERSON#"`.
2. For each such lead, call `party.find_party_by_contact("EMAIL", lead["email"])`. If found, update the lead's `converted_party_id` to the real PTY `party_id`. If not found, call `party.create_party("PERSON", ...)` + `add_contact_mech(...)` and update the reference.
3. Similarly, scan for `converted_org_id` starting with `"ORG#"` and migrate to real PTY PARTY_GROUP records.
4. After migration, the stub rows (`PK=PERSON#...`, `PK=ORG#...`) can be deleted.

This migration is not part of LED-006. It should be tracked as a follow-up PTY ticket (suggested name: PTY-016 or LED-006-migration).

### 8.3 Opportunity stub migration

The `LEAD#{lead_id}/OPPORTUNITY#META` stub row is forward-compatible with a future SALES-001 Opportunity table. The migration would copy the stub row to the new table and update `opportunity_id` on the lead. No existing behavior depends on the stub row format being stable; it is an append-only new key-space entry.

### 8.4 `LeadOut` backward compatibility

Adding `converted_at`, `converted_party_id`, `converted_org_id` to `LeadOut` (LED-002) is additive. Existing consumers of `LeadOut` that do not read these fields are unaffected. All three fields are `Optional` with `None` default.

## 10. Open Questions / Assumptions

| # | Question | Assumption / Decision |
|---|---|---|
| Q1 | Should `convert_lead` be restricted to the lead's assigned owner, or to admins only? | Not restricted in LED-006; LED-013 router layer can add a role check. Tracked as a follow-up. |
| Q2 | Should a second conversion attempt be idempotent (return the existing result) or conflict (409)? | 409 is chosen. The caller can GET the lead to read the existing `converted_party_id`. Idempotent replay would require deterministic party/org IDs which are only guaranteed on the PTY path. |
| Q3 | What status values can a lead be converted from? | `"new"`, `"assigned"`, `"in_process"`. Converting a `"recycled"` or `"dead"` lead is blocked (state-machine enforcement in `update_lead` / the already-deleted guard). Converting a `"new"` lead directly (skipping `"in_process"`) is allowed. |
| Q4 | Should the Opportunity stub carry a `close_date`? | Deferred to SALES-001/002. The stub only captures name and amount. |
| Q5 | Multi-currency for Opportunity amount | Fixed `"USD"` for MVP. Currency code added as a first-class field so it can be overridden by a future `LeadConversionIn.currency` field. |
| Q6 | Should `find_party_by_contact` return multiple matches and which to use? | First match is used. Operator should investigate duplicates via the PTY dedup tools (PTY-016 / CCT-005). |
| Q7 | Is the delete+re-put in `_finalize_conversion` safe under high load? | Acceptable for MVP. A `TransactWrite` can replace it as a follow-up. |
| Q8 | Do inline PERSON/ORG stub rows need a TTL? | No TTL is set for MVP. They are permanent until the migration script runs. |
