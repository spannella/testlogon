# STU-011 — Studio — custom fields for existing modules

**Type:** Feature  **Priority:** P2  **Estimate:** 3 days
**Ticket source:** `docs/suitecrm/CRM_SECURITY_STUDIO_TICKETS.md`, section "STU-011"
**Feature flag:** `CRM_STUDIO_ENABLED` (env `CRM_STUDIO_ENABLED`, default `"0"`) — all routes under `/ui/admin/studio/*` return 404 while the flag is off. Existing platform behaviour is byte-for-byte identical with the flag off.

---

## 1. Summary & Goal

STU-011 builds the Studio custom-field registry: a DynamoDB-backed store of named field definitions per entity type, a runtime validation layer that callers invoke on create/update payloads, and a set of admin CRUD endpoints exposed under `/ui/admin/studio/fields/{entity_type}`. A companion React component (`FieldEditor.tsx`) lets admins browse, add, edit, and deactivate custom fields without a code deployment.

Custom fields allow product operators to attach domain-specific attributes — for example, a `custom_region` (text) or `custom_tier` (picklist) — to any supported CRM entity (`contact`, `ticket`, `opportunity`, etc.) without touching application source code. The field definitions are stored in DynamoDB; read by service callers at validation time; and, once the STU-012 dropdown editor ships, can reference named option lists for picklist types.

The goal at the end of this ticket is:

1. A root admin can define, update, and deactivate custom fields for any entity type via the REST API.
2. Any service that creates or updates a CRM entity can call `validate_custom_fields(entity_type, payload)` to enforce type constraints and required-field rules declared in the registry.
3. The field registry is invisible — and has zero performance impact — when `CRM_STUDIO_ENABLED=0`.
4. The frontend admin studio page at `/admin/studio/fields` renders a live field table with create/edit/deactivate controls.

## 3. Data Model

### 3.1 Table: `crm_studio_fields` (introduced by STU-001)

**Partition key:** `entity_type` (S) — e.g., `contact`, `ticket`, `opportunity`, `lead`, `case`
**Sort key:** `field_key` (S) — e.g., `custom_region`, `custom_tier`, `custom_score`

**No GSIs** are required. At realistic scale (< 200 custom fields per entity type) a `query(KeyConditionExpression=Key("entity_type").eq(entity_type))` retrieves the full field set in a single page. A `FilterExpression` on `is_active` is applied in-process after fetch rather than via a GSI, per the CLAUDE.md note that `FilterExpression` does not reduce page size.

**TableDef** (already declared by STU-001 in `scripts/local-ddb-init.py`):
```python
TableDef("crm_studio_fields", "entity_type", "field_key")
```
No `attr_types` override needed (both keys are strings).

**Item attributes per field definition row:**

| Attribute | Type | Notes |
|---|---|---|
| `entity_type` | S | PK; one of the registered entity type slugs |
| `field_key` | S | SK; `^[a-z][a-z0-9_]{2,49}$`, unique within entity_type |
| `label` | S | Human-readable display label, 1–255 chars |
| `field_type` | S | `text \| integer \| decimal \| boolean \| date \| picklist \| multi_picklist` |

```python
def validate_custom_fields(entity_type: str, data: dict[str, Any]) -> dict[str, Any]
```
The core validation contract used by CRM entity create/update handlers:
1. Loads active field definitions from cache (TTL-backed) via `_load_fields(entity_type, include_inactive=False)`.
2. Checks each `required=True` field is present in `data` and non-null; collects per-field error dicts.
3. For each key in `data` that starts with `custom_` (convention prefix), looks up the field definition; unknown `custom_` keys raise `ValueError` listing unrecognised fields.
4. Type-coercion and validation per `field_type`:
   - `text`: asserts `isinstance(value, str)`; checks `len(value) <= max_length`.
   - `integer`: asserts `isinstance(value, int)` (not bool); checks `min_value`/`max_value` bounds if set.
   - `decimal`: asserts `isinstance(value, (int, float, Decimal))`; coerces to `Decimal`; checks bounds.
   - `boolean`: asserts `isinstance(value, bool)`.
   - `date`: asserts ISO-8601 date string `YYYY-MM-DD` format via `datetime.date.fromisoformat`.
   - `picklist`: asserts `isinstance(value, str)`; defers active-value membership check to STU-012 integration (see Section 5.4).
   - `multi_picklist`: asserts `isinstance(value, list)`; each element validated as `picklist`.
5. If any error was collected, raises `ValueError` with `{"errors": [...per-field error dicts...]}`.
6. Returns the original `data` dict with `decimal` values coerced to `Decimal` (safe for DDB storage).

## 5. Detailed Behavior & Edge Cases

### 5.1 `field_key` immutability

Once a field is created, `field_key` and `field_type` are immutable. Allowing rename would orphan existing data stored under the old key. Allowing type change would silently corrupt stored values (e.g., an `integer` field repurposed as `text` would leave numeric DDB values behind). The `PATCH` endpoint returns `400` with `code=field_key_immutable` if `field_key` appears in the request body, and `400` with `code=field_type_immutable` if `field_type` is provided.

### 5.2 Duplicate `field_key` prevention

`create_field` uses a DDB conditional `put_item` with `ConditionExpression=attribute_not_exists(field_key)`. A race between two concurrent creates of the same field key results in a `ConditionalCheckFailedException` from boto3, caught and re-raised as `FieldAlreadyExistsError`. The router maps this to `HTTP 409` with `code=field_already_exists`.

### 5.3 Deactivated field behaviour

`delete_field` sets `is_active=False` rather than deleting the item. Consequences:
- `list_fields(include_inactive=False)` (default) excludes the field from results — the cache only stores active fields.
- `validate_custom_fields` ignores deactivated fields: if `data` contains a `custom_` key for a deactivated field, it is passed through without type-checking (it is not treated as an unknown key). This preserves existing stored data in entities that were created while the field was active.
- A deactivated field can be re-activated by calling `PATCH` with `{"is_active": true}` — but only from a ROOT session. `update_field` adds `is_active` as an allowlisted mutable attribute only in the "re-activate" path; the `StudioFieldUpdateIn` model exposes a `reactivate: bool | None = None` field that maps to `is_active=True` on the DDB item. Setting `reactivate=False` via the API is a no-op (use `DELETE` to deactivate).

### 5.4 Picklist validation — STU-012 integration hook

When `field_type` is `picklist` or `multi_picklist`, `validate_custom_fields` needs to verify that submitted values are members of the referenced dropdown's active option list. At the time STU-011 ships, STU-012 (dropdown editor) may not be merged yet. The validation hook is therefore written as an optional integration:

```python
def _get_picklist_active_values(picklist_name: str) -> list[str] | None:
    """Returns None if the dropdown service is not available."""
    try:
        from app.services.crm_studio_dropdowns import get_active_values
        return get_active_values(picklist_name)
    except ImportError:
        return None
```

If `_get_picklist_active_values` returns `None` (STU-012 not yet merged), picklist membership validation is skipped — the submitted value is accepted regardless. Once STU-012 is merged, the import succeeds and validation is fully enforced. This prevents STU-011 tests from failing due to a missing dependency.

### 5.5 Cache invalidation scope

The cache is keyed by `entity_type`. A write to one entity type's fields invalidates only that entity type's cached list. Cache invalidation calls `_invalidate_entity_cache(entity_type)` which deletes `_field_cache[entity_type]` and `_field_cache_ts[entity_type]` from the module-level dicts. Concurrent requests that miss the cache all issue DDB queries and the last writer wins (last stored list replaces earlier in-process), which is correct for a read-through cache.

### 5.6 `validate_custom_fields` is a no-op when `CRM_STUDIO_ENABLED=0`

The function checks `S.crm_studio_enabled` at entry:
```python
def validate_custom_fields(entity_type: str, data: dict[str, Any]) -> dict[str, Any]:
    if not S.crm_studio_enabled:
        return data
    ...
```
This ensures the function is safe to call from entity service code even before the flag is enabled in production. Callers in `app/services/tickets.py` and the contacts router can import and call it unconditionally; with the flag off it is a pure passthrough with no DDB access.

### 5.7 Unknown `custom_` keys handling

Only keys with the `custom_` prefix are subject to custom-field lookup. Keys without this prefix are never validated by `validate_custom_fields` — they belong to the entity's native schema. An incoming payload with `{"custom_foo": "bar"}` where `custom_foo` is not a registered active field for the entity raises `CustomFieldValidationError` with `code=unknown_custom_field`, listing the offending keys. This prevents uncontrolled attribute proliferation in the underlying DDB items.

### 5.8 `default_value` type enforcement

When a field has a non-null `default_value` stored on the field definition, `validate_custom_fields` applies it for missing (not-required) fields: if a `custom_` key is absent from `data` but the field definition has `default_value` set, the returned dict includes `{field_key: default_value}` (coerced to the field's type). This means callers storing the returned dict from `validate_custom_fields` automatically persist defaults without needing explicit handling.

### 5.9 `include_inactive` access gate

`GET /fields/{entity_type}?include_inactive=true` returns deactivated fields, which is a privileged operation useful for auditing what fields were once active. The router enforces: if `include_inactive=True` and the caller is `Role.ADMIN` (not ROOT), return `HTTP 403` with `code=root_required_for_include_inactive`. ROOT can always pass `include_inactive=true`.

### 5.10 Maximum field count per entity

A module-level constant `MAX_FIELDS_PER_ENTITY = 200` guards against runaway schema growth. `create_field` queries the count of active fields for the entity (using the DDB `Select="COUNT"` option) and raises `HTTP 409` with `code=field_limit_reached` when the count is at or above the limit. The count query is issued before the conditional `put_item`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No `dev_mode` branches

The service and router contain no `if S.dev_mode:` branches. The same DDB `put_item`/`update_item`/`query`/`get_item` calls execute in both environments. In dev, `T.crm_studio_fields` resolves to a moto-backed in-process table (via `app/core/dev_s3.py`'s DDB mock path). In prod, it resolves to the real DynamoDB endpoint. The `_FloatSafeTable` proxy handles the boto3 client in both environments identically.

### 7.2 Idempotency of `create_field`

`put_item` with `attribute_not_exists(field_key)` is idempotent in the "already created" direction: a duplicate request raises `FieldAlreadyExistsError` (409), which is the correct idempotent behaviour. Callers that need safe retries should catch `409` and treat it as success.

### 7.3 Idempotency of `delete_field` (soft-delete)

Calling `delete_field` on an already-deactivated field is a no-op update (`is_active=False` is already `False`). The `update_item` sets `is_active=False` unconditionally rather than using a conditional expression — the audit event is emitted even on the no-op (this is intentional: repeated deactivation attempts are worth recording).

### 7.4 Security: entity_type injection

`entity_type` arrives from the URL path parameter. It is validated against `ALLOWED_ENTITY_TYPES` in the service before any DDB access. An attacker cannot probe or write to an arbitrary DDB partition by passing a crafted entity type string. The validation raises `HTTP 400` with `code=invalid_entity_type` for any value not in the allowlist.

### 7.5 Security: `field_key` injection

`field_key` is validated against the regex `^[a-z][a-z0-9_]{2,49}$` before use as a DDB sort key. This prevents whitespace, special characters, or excessively long strings from reaching DynamoDB. The regex allows only lower-case letters, digits, and underscores — sufficient for programmatic keys.

### 7.6 ROOT-only writes

All create/update/delete operations on field definitions require `Role.ROOT`. This prevents ADMIN-level operators from altering the schema that governs data validation, which would be a privilege escalation if an attacker gained ADMIN access. Read access (list/get) is open to all ADMIN/ROOT users.

### 7.7 Audit trail

Every mutating service call emits an `audit_event` via `app/services/alerts.audit_event` (alerts.py:644). Event names:
- `studio.field.created` — `entity_type`, `field_key`, `field_type`, `required`
- `studio.field.updated` — `entity_type`, `field_key`, `changed_attrs` (list of attribute names)
- `studio.field.deactivated` — `entity_type`, `field_key`
- `studio.field.reactivated` — `entity_type`, `field_key`

These events land in `T.alerts` under the actor's `user_sub` and are included in the ENTERPRISE-004 audit export stream via the existing `CrmAuditTrailAdapter` (STU-006).

## 8. Backward Compatibility & Migration

### 8.1 Additive only

No existing table, router, model, or service is modified by STU-011. The `crm_studio_fields` table is a net-new table created by STU-001's `local-ddb-init.py` entry. In prod, the `CreateTable` API call is issued once at stack deploy time; it does not touch existing tables.

### 8.2 Existing entities carry no custom fields

All existing `ticket`, `contact`, and other entity records stored in DynamoDB before STU-011 have no `custom_*` attributes. When `validate_custom_fields` is eventually wired into those write paths, it returns the payload unchanged for entities with no active field definitions (empty field list → no required checks, no type coercion). There is no backfill or migration needed.

### 8.3 Wiring `validate_custom_fields` into existing services

This ticket intentionally does not patch `app/services/tickets.py` or `app/routers/contacts.py` with calls to `validate_custom_fields`. That integration is a follow-up step (one line added to each service's create/update path) that is safe to defer because `validate_custom_fields` is a no-op when `CRM_STUDIO_ENABLED=0`. The spec records the intended call sites:

- `app/services/tickets.py` `create_ticket` — call `validate_custom_fields("ticket", metadata or {})` after the existing label normalization at line ~437.
- `app/services/tickets.py` `update_status` (and any future ticket update functions) — call on the delta payload.
- `app/routers/contacts.py` `update_contact` — call `validate_custom_fields("contact", inp.model_dump(exclude_none=True))` before the DDB `update_item`.

When the integration is added, the entity's DDB item should store the validated custom fields under a `custom_fields` attribute (a DDB map), not scattered at the top level, to keep the native schema clean.

### 8.4 Prod table creation

The `crm_studio_fields` table is created by STU-001's `scripts/local-ddb-init.py` entry in dev. In prod, an `aws dynamodb create-table` call (or Terraform/CloudFormation resource) must be applied before `CRM_STUDIO_ENABLED=1` is set. No `UpdateTable` is required by STU-011 (no GSI additions to an existing table).

## 10. Open Questions / Assumptions

1. **Storage location for custom field data on entities:** This spec assumes custom field values are stored under a `custom_fields` map attribute on the entity's DDB item (e.g., `custom_fields: {"custom_region": "EMEA"}`). An alternative is top-level attribute scattering. The map approach is cleaner for DDB (avoids polluting the top-level attribute namespace with unknown keys). This decision should be confirmed before the service integration step in Section 8.3.

2. **`validate_custom_fields` call timing:** Should validation happen at the router layer (before the service is called) or inside the service? The spec places it inside the service, but router-layer validation (Pydantic `model_validator`) would give cleaner 422 responses. Decision deferred to implementation; either approach satisfies the spec.

3. **`multi_picklist` storage format:** A `multi_picklist` value is a list of strings. When stored in DynamoDB, this becomes a `List` attribute (DDB type `L`). Confirming that `_FloatSafeTable` does not accidentally coerce list elements is needed — `_to_decimal` in `app/core/tables.py:11` recursively processes lists but only coerces `float`, leaving strings unchanged.

4. **Picklist validation without STU-012:** The spec provides a graceful degradation path (skip membership validation if `crm_studio_dropdowns` is not importable). This is a temporary state. Once STU-012 is merged, a follow-up commit should remove the `try/except ImportError` guard and add an integration test.

5. **Frontend entity type list hardcoded vs. API-sourced:** The `FieldEditor.tsx` component uses a static `ALLOWED_ENTITY_TYPES` list. A future enhancement would expose `GET /ui/admin/studio/entity-types` to allow the frontend to dynamically discover registered entity types. Not in scope for STU-011.
