# CAS-010 — Case merge and duplicate detection

## 1. Summary & Goal

CAS-010 adds agent-initiated ticket merging and a duplicate-detection surface to the existing ticket system. When an agent determines that two tickets represent the same issue, they can merge the source (duplicate) into a target (canonical) ticket. After the merge: all `MSG#` and `ATTACH#` sub-items from the source partition are copied into the target partition; the source META row is tombstoned with `merged_into_ticket_id` and transitioned to `status="done"`; subsequent `GET /tickets/{source_id}` calls receive HTTP 301 pointing to the canonical target; and both tickets carry a `ticket_merged` activity record. A lightweight duplicate-detection helper is also exposed so UI and background jobs can surface likely duplicates before an agent manually decides.

The entire feature is additive and gated on the existing `S.crm_cases_enabled` flag (introduced in CAS-001). With the flag off the platform is byte-for-byte unchanged.

## 2. Context & Current State

### Existing ticket storage

`app/services/tickets.py` uses a single DynamoDB table (`T.tickets`, field declared at `app/core/tables.py:140`, wired at `tables.py:392`). All items share a partition key `pk = TICKET#{ticket_id}` and a sort key that encodes item type:

- `sk = "META"` — the header row (`app/services/tickets.py:168–169`)
- `sk = "MSG#{ts:013d}#{message_id}"` — message sub-items (`tickets.py:172–173`)
- `sk = "ACT#{ts:013d}#{activity_id}"` — activity sub-items (`tickets.py:176–177`)
- `sk = "ATTACH#{ts:013d}#{attach_id}"` — attachment sub-items (introduced in CAS-006; **not yet implemented** — `ATTACH#` items do not currently exist in `tickets.py`)

`TicketStore.get_ticket` (`tickets.py:522`) fetches the META row then separately queries `MSG#` and `ACT#` prefixes via `_query_partition_prefix` (`tickets.py:514`).

### Write path and optimistic locking

All META mutations go through `_conditional_update_meta` (`tickets.py:723`), which enforces a `ConditionExpression="#version = :expected_version"` (`tickets.py:782`). `_apply_header_update_once` (`tickets.py:792`) provides the read-modify-write retry wrapper. Any new merge tombstone write must follow this same pattern to prevent lost updates.

### Activity sub-items

`create_ticket` writes the first `ACT#` row with `activity_type="ticket_opened"` (`tickets.py:502–511`). `add_message` writes `activity_type="ticket_message"` or `"ticket_reopened"` activities (`tickets.py:870–880`). CAS-010 adds a new `activity_type="ticket_merged"` row on both source and target partitions.

### Status transitions

`_STATUS_TRANSITIONS` (`tickets.py:30–40`) governs allowed moves. `"done"` is reachable from `open`, `in_progress`, `waiting_on_user`, `code_complete`, `qa_approved` — but is **not** a listed transition from `blocked`, `qa_in_progress`, `deploying`, `deployed`, `investigating`, `analyzing`, or `tickets_created`. The merge operation forces `status="done"` on the source regardless of its current status, **bypassing** `_STATUS_TRANSITIONS` via a direct `_conditional_update_meta` call — this bypass is intentional and is the only place such a bypass is needed.

### Alert and audit primitives

`_emit_ticket_alerts` (`app/routers/tickets.py:362`) iterates a recipient list and calls `audit_event` from `app/services/alerts.py:644`. `audit_event` writes to `T.alerts` and is the canonical audit trail. CAS-010 calls `audit_event("ticket_merged", ...)` directly in the service layer (same pattern as `kyc_risk_scoring.py:588–604` where `audit_event("kyc_auto_escalated", ...)` is called directly after `escalate_case` — note: the `audit_event` call for escalation lives in `kyc_risk_scoring.py`, not inside `kyc_cases.py:escalate_case` itself).

### Duplicate-detection gap

No duplicate detection exists today. `TicketStore` has no subject-similarity search. Prefix-token search is planned for KB articles in CAS-015 (mirroring `build_prefix_tokens` at `app/routers/messaging.py:2743` and `build_message_search_tokens` at `app/routers/messaging.py:2775`; there is no separate `app/services/messaging_search.py` file — the search helpers live in the messaging router directly). CAS-010 introduces a lightweight Jaccard-on-subject-tokens scorer inside the service, using existing DDB queries — no new index required for the detection path.

### CAS-001 scaffolding

CAS-001 introduces `crm_cases_links` (`crm_cases_links_table`, PK=`ticket_id`, SK=`LINK#{related_ticket_id}`) which CAS-011 uses for bidirectional typed links. CAS-010 does **not** use this table — merged-ticket state is stored on the source META row only, so no additional table is needed. **Note:** `S.crm_cases_enabled` and all CAS-001 scaffolding (settings, tables, `T.crm_cases_links`, etc.) do **not yet exist** in `app/core/settings.py` or `app/core/tables.py` — CAS-001 itself must be implemented first.

## 3. Data Model

### No new DynamoDB tables

CAS-010 is purely additive to the existing `tickets` table. The merge tombstone, activity records, and redirect information all live inside the existing single-table structure.

### New attributes on the ticket META row

| Attribute | Type | Description |
|---|---|---|
| `merged_into_ticket_id` | `S` (string) | Present only on a merged (source) ticket. Contains the `ticket_id` of the canonical target. |
| `merged_at` | `N` (number) | Unix timestamp when the merge was executed. |
| `merged_by` | `S` | `user_sub` of the admin who triggered the merge. |
| `merge_note` | `S` | Optional free-text note from the agent explaining why (max 500 chars). |

These four attributes are SET on the source META row via `_conditional_update_meta` in a single `update_item` call. The target META row is untouched except for a new `ACT#` activity row.

### New activity sub-item type

Both source and target partitions receive a new `ACT#` row:

```
pk  = TICKET#{ticket_id}
sk  = ACT#{ts:013d}#{act_id}
entity_type   = "ticket_activity"
activity_type = "ticket_merged"
actor_sub     = <merging agent sub>
merged_source_id  = <source ticket_id>   # on target activity
merged_target_id  = <target ticket_id>   # on source activity
created_at    = <ts>
```

The SK sort prefix `ACT#{ts:013d}` (`tickets.py:176`) means the merge activity sorts naturally in the timeline — no schema change.

### Duplicate-detection index — no new GSI needed

`_query_partition_prefix` (`tickets.py:514`) is used to scan sub-items within a partition. For duplicate detection, the scorer queries `GET /tickets` using the existing status GSI (`gsi2pk = STATUS#open`) to retrieve candidate headers, then scores subject similarity in-process. Subject tokens are short (< 100 chars), so the computation is trivial. No fan-out or secondary index is required for the MVP scoring path.

### scripts/local-ddb-init.py

No new table definitions. The existing tickets table entry at `scripts/local-ddb-init.py:695–711` (`TableDef` starting at line 695) is unchanged. The new `merged_into_ticket_id` / `merged_at` attributes are non-key attributes on an existing table — DynamoDB's schemaless nature means they appear automatically; no migration required.

## 4. API / Service Design

### 4.1 Service layer additions (`app/services/tickets.py`)

#### `TicketStore.merge_ticket`

```python
def merge_ticket(
    self,
    *,
    source_ticket_id: str,
    target_ticket_id: str,
    actor_sub: str,
    merge_note: str | None = None,
) -> dict[str, Any]:
    ...
```

**Steps (all within one logical transaction; no distributed TX — DDB single-table):**

1. Load both tickets with `get_ticket(source_ticket_id)` and `get_ticket(target_ticket_id)`. Raise `TicketStateError({"code": "ticket_not_found", ...})` if either is missing (maps to HTTP 404).
2. Guard: if `source.get("merged_into_ticket_id")` is set, raise `TicketStateError({"code": "ticket_already_merged", "merged_into": source["merged_into_ticket_id"]})` (maps to HTTP 409).
3. Guard: `source_ticket_id == target_ticket_id` → raise `TicketStateError({"code": "ticket_merge_self", ...})` (maps to HTTP 400).
4. Guard: if `target.get("merged_into_ticket_id")` is set, raise `TicketStateError({"code": "ticket_merge_into_merged", ...})` (maps to HTTP 409) — cannot merge into a ticket that is itself already a redirect stub.
5. Copy `MSG#` sub-items: call `_query_partition_prefix(ticket_id=source_ticket_id, sk_prefix="MSG#")` to fetch all source messages. For each item, write a copy into the target partition with `pk = TICKET#{target_ticket_id}`, preserving the original `sk`, `body`, `sender_sub`, `sender_role`, `created_at`, `email_alert_queued_for`, and adding `merged_from_ticket_id = source_ticket_id`. Use `T.tickets.batch_writer()` (the `_FloatSafeTable` wrapper, `tables.py:51–58`) for batched puts.
6. Copy `ATTACH#` sub-items: same batch-write pattern for `sk_prefix="ATTACH#"`. Preserve `s3_key`, `bucket`, `filename`, `content_type`, `size_bytes`, `description`, `uploader_sub`, `created_at`. Add `merged_from_ticket_id`.
7. Write `ACT#` activity on the **target** partition: `activity_type="ticket_merged"`, `merged_source_id=source_ticket_id`.
8. Write `ACT#` activity on the **source** partition: `activity_type="ticket_merged"`, `merged_target_id=target_ticket_id`.
9. Tombstone the source META via `_apply_header_update_once`:
   - Sets `status="done"`, `merged_into_ticket_id`, `merged_at`, `merged_by`, `merge_note`.
   - Updates `gsi2pk = STATUS#done`, `gsi2sk`, `gsi1sk`, `updated_at` as usual.
   - `gsi3pk`/`gsi3sk` (assignee GSI) are **always SET** (never REMOVEd) in `_conditional_update_meta` — they must be passed as `:gsi3pk = _assignee_index_pk("unassigned")` since a merged ticket has no assignee. The REMOVE pattern at `tickets.py:757–771` applies only to the six `gsi_space_*` keys, not to `gsi3pk`/`gsi3sk`.
   - Space GSI keys are REMOVEd if the source ticket had no `space_id`, or SET with the existing space values if it did (handled automatically by `_conditional_update_meta`'s existing REMOVE logic at `tickets.py:757–771`).
10. Emit `audit_event("ticket_merged", actor_sub, ...)` with `source_ticket_id` and `target_ticket_id` fields (same call pattern as `kyc_cases.py:escalate_case`).
11. Return `get_ticket(target_ticket_id)`.

**Failure modes:**
- Step 9 (`_conditional_update_meta`) may fail with `ConditionalCheckFailedException` if concurrent update races the merge. `_apply_header_update_once` raises `TicketStateError({"code": "ticket_update_conflict"})` → HTTP 409. The caller should retry.
- Batch writes in steps 5–6 do not fail atomically; if the process dies mid-copy, a partial copy leaves orphan sub-items in the target. The tombstone has not been set, so the source is still live. The endpoint is idempotent for repeated invocations (same `source_ticket_id` / `target_ticket_id`) — duplicate sub-item puts are no-ops (DDB `put_item` is upsert). A re-run after partial failure is safe.

#### `TicketStore.find_duplicates`

```python
def find_duplicates(
    self,
    *,
    ticket_id: str,
    limit: int = 10,
    status_filter: list[str] | None = None,
) -> list[dict[str, Any]]:
    ...
```

Scoring algorithm (pure Python, no extra DDB index):

1. Load the subject ticket with `get_ticket(ticket_id)`. Return `[]` if not found or if already merged.
2. Tokenise subject: `subject_tokens = set(subject.lower().split())`.
3. Query candidates: for each status in `status_filter or ["open", "in_progress", "waiting_on_user"]`, call `_query_headers_by_index(index_name=S.tickets_status_index_name, pk=_status_index_pk(status), ...)` with `Limit=200`. Deduplicate by `ticket_id`. Exclude `ticket_id` itself and any tickets with `merged_into_ticket_id` set.
4. Score each candidate using Jaccard similarity: `|A ∩ B| / |A ∪ B|` over subject token sets. Also award a 0.15 bonus if both tickets share the same `owner_sub` (same user re-submitting).
5. Return the top `limit` candidates with `score > 0.25`, sorted descending by score. Each result: `{ticket_id, subject, status, owner_sub, score}`.

The 200-candidate cap is deliberate — `_query_headers_by_index` already paginates, and iterating all open tickets for a busy system would be expensive. A future CAS-015 KB token index could replace this with a proper inverted-index lookup if volume warrants.

## 5. Detailed Behavior & Edge Cases

### 5.1 Merge atomicity

DynamoDB does not support cross-partition transactions beyond the 25-item `transactItems` limit. The batch-copy (steps 5–6) is not atomic with the tombstone (step 9). The design handles this with idempotency:

- Sub-item copies are `put_item` upserts; re-running the same merge is safe.
- The tombstone is the authoritative signal (`merged_into_ticket_id` set). If it is not yet set, the source is still live — no inconsistency is visible to API consumers.
- A partial merge (copy done, tombstone not written) will appear as though the merge never happened (the source is still live), allowing a retry. The target accumulates duplicate copies if the batch re-runs, but since `sk` values are preserved from the source, the upsert is idempotent.

### 5.2 Preventing double-redirect

If a consumer follows the 301 to the target and the target is also merged into a third ticket, a second 301 would be issued. To prevent infinite loops: the service guard in step 4 of `merge_ticket` rejects merging into an already-merged target. This means redirect chains are at most one hop deep.

### 5.3 Replies on a merged source

After the source is tombstoned, `add_message` can still be called if the caller has the old `ticket_id`. Because `update_status` checks `_TICKET_STATUSES` (all valid) and the source's `status="done"`, a new message would re-open it via the `_next_status_for_message` path (`tickets.py:235`). To prevent zombie re-opens, the `add_message` method is extended: if `ticket.get("merged_into_ticket_id")`, raise `TicketStateError({"code": "ticket_is_merged", "merged_into": merged_into})` → HTTP 409. This is additive — the check fires only when the new attribute is present.

### 5.4 Watchers and assignee on source

After merge, the source's `status="done"` and it is tombstoned. Watcher notification (CAS-007) on source no longer fires. The target retains its own assignee and watcher list unchanged. Watcher lists are not merged — agents can add watchers to the target separately if needed.

### 5.5 SLA and escalation on the source

CAS-008 `check_breaches` queries by status GSI. After merge, the source moves to `STATUS#done`; the SLA checker will never trigger a breach alert on it again. The `sla_due_at` field on the source is left in place for audit purposes but has no operational effect.

### 5.6 CSAT survey on source

CAS-016 fires a CSAT survey when `set_ticket_status` transitions to `"done"`. `merge_ticket` transitions the source to `"done"` via `_conditional_update_meta` directly, not via the `update_status` router endpoint. Therefore, the CSAT hook in `set_ticket_status` does NOT fire for the source — deliberately, because a merged-in duplicate should not receive a survey. Only the canonical target triggers CSAT when legitimately resolved.

### 5.7 Attachment de-duplication

If the source and target already share an attachment (same `sk` because the file was added to both before merging), the batch-write upsert overwrites with the source's version (which is identical). The `merged_from_ticket_id` field will be set on the copy, making provenance visible.

### 5.8 Duplicate detection score thresholds

A Jaccard score of 0.25 is a practical lower bound for short support-ticket subjects. Subjects with only one common word (e.g., "billing" appearing in both) can easily exceed 0.25, producing false positives. The threshold is env-configurable via `S.crm_cases_merge_dup_min_score` (see section 6). Agents are expected to review suggestions before merging; the API returns candidates, it does not auto-merge.

### 5.9 Pagination of sub-items

`_query_partition_prefix` (`tickets.py:514`) does not loop on `LastEvaluatedKey`. For tickets with very large message histories this could miss items beyond the first DDB page (~1 MB). CAS-010 replaces the direct `_query_partition_prefix` call inside `merge_ticket` with a looping variant that pages until `LastEvaluatedKey` is absent:

```python
def _query_partition_all(self, *, ticket_id: str, sk_prefix: str) -> list[dict]:
    pk = _ticket_pk(ticket_id)
    items, lek = [], None
    while True:
        params = {
            "KeyConditionExpression": "pk = :pk AND begins_with(sk, :pfx)",
            "ExpressionAttributeValues": {":pk": pk, ":pfx": sk_prefix},
            "ScanIndexForward": True,
        }
        if lek:
            params["ExclusiveStartKey"] = lek
        resp = self._table.query(**params)
        items.extend(resp.get("Items", []))
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
    return items
```

`_query_partition_prefix` is left unchanged (used in read paths where the 1 MB limit is acceptable) to avoid any regression.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

All operations are DDB-only (read, batch write, conditional update, audit event to `T.alerts`). There is no S3, SES, or Cognito call in the merge path. The same code executes in dev (DDB local) and prod (real DDB) without any `if S.dev_mode` branch — full parity.

The `audit_event` call (`app/services/alerts.py:644`) writes to `T.alerts` in both environments; in dev this is DDB local, in prod it is the real alerts table. No environment split.

### Idempotency

- `merge_ticket` called twice with the same `(source, target)` pair: the second call hits guard step 2 (`merged_into_ticket_id` is already set) and returns HTTP 409 `ticket_already_merged`. Sub-item copies have already been written (idempotent upserts); no data is duplicated beyond what the first call produced.
- `find_duplicates` is a pure read — fully idempotent.

### Security

- `POST /tickets/{id}/merge` requires admin role or `tickets:admin` API-key scope (`_is_admin_actor(request, user)` check mirrors `set_ticket_status` at `app/routers/tickets.py:999`). Non-admin, non-API-key callers receive 403.
- `GET /tickets/{id}/duplicates` requires `require_ui_session` only. An authenticated user can query duplicate suggestions for any ticket ID. The response contains only `ticket_id`, `subject`, `status`, `owner_sub`, and `score` — no private message bodies or attachments. Ownership check (only the ticket owner or admin can see suggestions) would reduce information leakage; however, `subject` is already surfaced in `TicketListItemOut` for all authenticated users, so the risk is low. If stricter scoping is desired, add `if ticket["owner_sub"] != user.sub and not _is_admin(user): _raise(403, ...)` before the `find_duplicates` call.
- `merge_note` is capped at 500 characters (`Field(max_length=500)`) to prevent oversized write payloads.
- The 301 redirect is server-side (FastAPI `RedirectResponse`) — not an open redirect since the target is always `/tickets/{known_ticket_id}` constructed from trusted DDB state.

## 8. Backward Compatibility & Migration

### Zero-impact with flag off

When `CRM_CASES_ENABLED=0` (the default and current production state), the three new route handlers return 404 before any service code runs. `TicketOut` gains three new `| None = None` fields — existing clients that do not know about these fields will simply ignore them (Pydantic `extra="ignore"` on response serialization).

The `get_ticket` dict returned by the service now conditionally includes `merged_into_ticket_id`, `merged_at`, `merged_by` from the META row. For all existing tickets (which have none of these attributes), `header.get("merged_into_ticket_id")` returns `None`, so the redirect logic in the router is skipped. Existing unit tests and E2E tests are unaffected.

### No DynamoDB migration

No new tables or GSIs are introduced. The new attributes (`merged_into_ticket_id`, `merged_at`, `merged_by`, `merge_note`) are non-key, non-GSI-projected attributes on the existing tickets table. DynamoDB's schemaless design means they appear automatically on first write. No backfill is required in prod.

### add_message guard

The new `add_message` guard (raise on `merged_into_ticket_id`) adds a 404-path for merged tickets. Any client that holds a stale source `ticket_id` and attempts to reply will receive a 409 with `code=ticket_is_merged` and `merged_into` in the detail body, allowing the client to redirect. This is backward compatible — unmerged tickets do not have `merged_into_ticket_id` set, so the guard never fires for existing code paths.

## 10. Open Questions / Assumptions

1. **Message body de-duplication**: if both source and target already contain identical message bodies (e.g., a user copy-pasted the same content into both), the copy produces a duplicate display. The spec assumes agents are aware of this and the merge note provides context. A future improvement could deduplicate on `body` hash before copying.

2. **Watcher merge**: Should the source's watcher list be merged into the target's? This spec deliberately omits it — watchers are per-ticket and the admin can manage them after the merge. CAS-007 should be consulted if this is later desired.

3. **Redirect staleness in cached clients**: HTTP 301 is permanently cached by many HTTP clients. If a merge is later "undone" (which this spec does not support), cached 301s would be stale. The spec assumes merges are irreversible; an undo path is out of scope.

4. **Score threshold calibration**: The default Jaccard threshold of 0.25 is a starting point. Monitoring via the `ticket_merged` audit trail (comparing how often duplicates are found vs manually merged) will inform whether the threshold needs tuning.

5. **Case number surface in merge**: CAS-002 adds `case_number` (e.g., `CASE-0042`) to each ticket. The merge note in the activity record should ideally reference the source case number for human readability in the audit log. The spec includes it as `merged_source_id` (ticket ID), not as case number. Post-merge the agent can look up the source's case number from `get_ticket(source_id)` while it still returns the tombstoned META row.

6. **CAS-011 link creation**: CAS-011 adds typed `duplicate` links via `crm_cases_links`. CAS-010 does not write to that table — the tombstone + 301 is the merge record. Agents may optionally use CAS-011 to create a `duplicate` link before merging, but CAS-010 does not require or produce one automatically.
