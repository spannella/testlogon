# ACT-003 — Calendar event invitation emails with ICS attachment

**Type:** Feature  **Priority:** P1  **Estimate:** 2d  **Area:** Activities & Calendar

---

## 1. Summary & Goal

Wire the existing `create_event` and `update_event` handlers in `app/routers/calendar.py` to dispatch per-attendee invitation emails that include a standards-compliant ICS (iCalendar) attachment. On event deletion, dispatch a cancellation email with `METHOD:CANCEL`. The feature ships as a strictly additive change: with both the master flag (`crm_activities_enabled`) and its sub-flag (`crm_event_reminders_enabled`) off, every existing code path is byte-for-byte unchanged.

The goal is SuiteCRM parity for the attendee invitation workflow: external calendar clients (Google Calendar, Apple Calendar, Outlook) recognise the iTIP `VCALENDAR/METHOD:REQUEST` attachment and offer a one-click "Accept / Decline / Tentative" prompt to the recipient. Cancellation emails carry `METHOD:CANCEL` so those clients remove the event from the attendee's calendar automatically.

## 4. API / Service Design

### 4.1 `_build_ics` extension (`app/routers/calendar.py:2048`)

Add an optional `method` parameter:

```python
def _build_ics(evt: dict, event_id: str, method: str | None = None) -> str:
```

Insert `f"METHOD:{method}"` as the fifth line of the `lines` list, immediately after `"CALSCALE:GREGORIAN"` and before `"BEGIN:VEVENT"`, only when `method is not None`. This makes the output a valid iTIP scheduling object (`RFC 5546`). Valid values for `method` in this ticket are `"REQUEST"` (create/update invites) and `"CANCEL"` (deletion). **The default must be `None`, not `"REQUEST"`** — see the design choice in section 8.2 for the rationale: existing callers `download_public_ical` and `download_event_ical` call `_build_ics(evt, event_id)` without the `method` argument and must produce output identical to the current implementation (no `METHOD:` line).

### 4.2 `send_calendar_invite_email` (`app/services/alerts.py` — new function)

```python
def send_calendar_invite_email(
    to_emails: List[str],
    subject: str,
    body_text: str,
    ics_content: str,
    event_name: str,
) -> None:
```

**Dev mode** (`S.dev_mode`): writes two structured entries to `S.dev_email_log` via `_write_dev_log` — one for the email body and one for the ICS content — so the dev log contains both parts and tests can assert on the ICS. Format:

```
[{ts}] CALENDAR_INVITE TO={addr}
  Subject: {subject}
  Body: {body_text}
  ICS:
{ics_content}
```

**Production** (`not S.dev_mode`): calls `ses.send_raw_email` with a hand-assembled `multipart/mixed` MIME message. The function builds the raw message using only the Python standard library (`email.mime.multipart.MIMEMultipart`, `email.mime.text.MIMEText`, `email.mime.base.MIMEBase`, `email.encoders`), with:

- Part 1: `text/plain` — the invitation body text.
- Part 2: `text/calendar; charset=UTF-8; method={method}` with `Content-Disposition: attachment; filename="invite.ics"` — the ICS content encoded as UTF-8.

The function sends one `send_raw_email` call per recipient (not bulk) to allow per-recipient personalisation in a future ticket. On any `boto3` exception the function logs the error and increments `EMAIL_FAILED` (same guard pattern as `send_alert_email` at `alerts.py:482`). It never raises; failures are best-effort.

Guards: if `not S.alerts_email_enabled or not S.alerts_from_email`, return immediately (same guard as `send_alert_email:469`).

### 4.3 `_dispatch_invite_emails` helper (`app/routers/calendar.py` — new private function)

```python
def _dispatch_invite_emails(
    item: dict,
    event_id: str,
    organizer_sub: str,
    method: str,
) -> None:
```

This function is called fire-and-forget from the three dispatch points. Its contract:

1. Check `S.crm_activities_enabled and S.crm_event_reminders_enabled`; return immediately if either is `False`.
2. Collect `attendees: List[str]` from `item.get("attendees", [])`. Skip the organizer's own `user_sub` (`organizer_sub`) — the organizer does not receive an invite to their own event.
3. Build `ics_content = _build_ics(item, event_id, method=method)`.
4. For each attendee `sub` in `attendees` (up to 50 per call, capped to prevent runaway loops on malformed data):
   a. Call `get_profile_identity(sub)` — imported from `app.services.profile` at the top of `calendar.py`. **`get_profile_identity` is NOT currently imported in `calendar.py`**; it must be added as a new import (e.g. `from app.services.profile import get_profile_identity`). Line 62 imports only `audit_event` from `app.services.alerts`; `app.services.profile` is not imported at all.
   b. If `identity.get("email")` is `None` or empty, skip this attendee silently.
   c. Build a plain-text body:
      ```
      You have been {invited to / notified of a change to / informed of the cancellation of} the event "{event_name}".

      When: {start_utc} – {end_utc} (UTC)
      Where: (omitted — no location field in current EventCreateIn)
      Organizer: {organizer_display_name}

      Open your calendar app to accept, decline, or propose a new time.
      ```
   d. Subject line: `"Invitation: {event_name}"` (create/update) or `"Cancelled: {event_name}"` (cancel).
   e. Call `send_calendar_invite_email([email], subject, body_text, ics_content, event_name)`.
   f. Call `audit_event("calendar_invite_sent", organizer_sub, None, outcome="ok", attendee_sub=sub, event_id=event_id, method=method)`.
5. Entire function body is wrapped in a single `try/except Exception`: on failure log at WARNING level and return. Never raises.

## 5. Detailed Behavior & Edge Cases

**Attendee skip — no email address**: `get_profile_identity` returns `{"email": None, ...}` when the user's `displayed_email` is not set on their profile (`app/services/profile.py:313` — the `"email": profile.get("displayed_email")` entry is at line 313 of the return dict, inside the function defined at line 305). These attendees are silently skipped; no error is raised and no audit event is emitted for them. Behavior is consistent with the ticket specification.

**Organizer skip**: The event organizer (`ctx["user_sub"]`) is excluded from the attendee loop. This prevents the organizer from receiving an invitation to their own event.

**Empty attendee list**: `body.attendees = []` (the default in `EventCreateIn` at `app/models.py:1264`) means the loop body never executes. No emails are sent, no audit events are written. This is the common case for personal events.

**Duplicate attendees**: If `body.attendees` contains the same `user_sub` twice, `_dispatch_invite_emails` will send two emails to that address. The caller (frontend or API) is responsible for deduplication before submission. The service does not deduplicate because the source-of-truth `attendees` list is the one persisted in DynamoDB and must not be silently altered.

**`update_event` with no relevant changes**: If an update changes only the event `name` or `description` and leaves attendees and times unchanged, `_attendees_changed` and `_times_changed` are both `False` and no invitations are sent. This is intentional to avoid inbox spam for cosmetic edits.

**`update_event` new attendee added**: When attendees change from `[alice]` to `[alice, bob]`, both Alice and Bob receive a fresh `METHOD:REQUEST` email. This is the iTIP specification behaviour — `METHOD:REQUEST` is idempotent from the calendar client perspective (receiving a second REQUEST for the same UID updates the existing entry).

**All-day events**: `_build_ics` at `calendar.py:2062` already handles the `all_day` + `all_day_date` case by emitting `DTSTART;VALUE=DATE:` and `DTEND;VALUE=DATE:` lines. The extended `_build_ics` handles this path unchanged — the `method` parameter inserts before `BEGIN:VEVENT`, not inside the datetime block.

**CANCEL for non-existent attendees**: If an attendee's profile was deleted between `create_event` and `delete_event`, `get_profile_identity` returns a profile with `email=None` — it never raises for a missing user because `get_profile` (`profile.py:262`) returns `empty_profile()` when the DynamoDB item is absent. The email is then silently skipped. The delete proceeds normally.

**Rate-limiting**: The `can_send_alert_channel` rate-limiter (`app/services/rate_limit.py:321`) uses `T.sessions` (not `T.alert_prefs`) via `_bucket_limit`. It is applied in the higher-level `send_alert` fan-out function, not in `send_alert_email` directly. `send_calendar_invite_email` does not call through `send_alert_email` or `send_alert`; it calls `ses.send_raw_email` directly and has no per-recipient rate-limiting of its own. In production environments with many attendees this can generate bursts of SES API calls. The 50-attendee cap in `_dispatch_invite_emails` provides a ceiling. If SES throttling is a concern in production, a short `asyncio.sleep(0.05)` between per-recipient calls may be added in a follow-up without changing the public contract.

**Flag transition**: If the feature is enabled (`crm_event_reminders_enabled=True`) and then disabled, no in-flight emails are affected because dispatch is synchronous and inline. Emails already sent are not recalled.

**ICS `UID` field**: `_build_ics` emits `UID:{event_id}@testlogon` (line 2060). The `event_id` is a `uuid4().hex` string (line 1567 in `create_event`), which is globally unique. When `update_event` sends a `METHOD:REQUEST` with the same `UID`, calendar clients correctly identify it as an update to the existing entry rather than a new event.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity**: `send_calendar_invite_email` uses the same `S.dev_mode` branch structure as `send_alert_email` (line 462): in dev mode it writes to `S.dev_email_log` via `_write_dev_log`; in production it calls `ses.send_raw_email`. There is no separate mock implementation. The ICS content, subject, and body are constructed identically in both paths. `_build_ics` is a pure function with no environment branch. Tests run against the dev-mode path but exercise the same ICS-generation and MIME-assembly logic that production uses.

**Idempotency**: `create_event` is not idempotent (each call creates a new `event_id`). `update_event` uses the same `event_id` and the dispatch guard on `_attendees_changed || _times_changed` prevents redundant emails for no-op updates. Retrying a failed `update_event` call (e.g., after a transient error) will re-send the invitation if the condition is still `True`, which is the correct iTIP behaviour — `METHOD:REQUEST` is safe to deliver multiple times (RFC 5546 §3.2.2).

**No secrets in ICS**: The ICS content contains only the event `UID`, `DTSTART`/`DTEND`, `SUMMARY`, `DESCRIPTION`, and the new `METHOD` line. No user `user_sub` values, session tokens, or internal IDs are included in the attachment body.

**Attendee enumeration**: `_dispatch_invite_emails` calls `get_profile_identity` for each attendee `sub`. The function at `app/services/profile.py:305` reads from `T.profile` by primary key; no per-attendee 403 or 404 is raised for deleted/hidden profiles — it returns a dict with `None` email, which is silently skipped. This prevents information leakage about whether a sub exists.

**SES sender spoofing**: `send_calendar_invite_email` uses `S.alerts_from_email` as the MIME `From:` header, the same address used by `send_alert_email`. No caller-controlled `From:` header is accepted.

**MIME injection**: `event_name`, `description`, and `display_name` values sourced from user-supplied `EventCreateIn` fields are placed only in the `text/plain` part body and the ICS `SUMMARY`/`DESCRIPTION` folded lines — never in raw MIME headers. The ICS `DESCRIPTION` folding in `_build_ics` at line 2072 already replaces newlines with `\n` literals (`replace(chr(10), chr(92) + 'n')`). This is sufficient for the text body; no further sanitisation is required for the `text/plain` MIME part.

## 8. Backward Compatibility & Migration

**No DynamoDB schema changes**: existing `T.calendar` items are unmodified. No backfill is needed.

**`_build_ics` signature**: the new `method` parameter has a default of `"REQUEST"`. Both existing call sites — `download_public_ical` (call at `calendar.py:2103`) and `download_event_ical` (call at `calendar.py:2125`; the `@router.get` decorator is at line 2114) — call `_build_ics(evt, event_id)` without a keyword argument and continue to work unchanged. The addition of `METHOD:REQUEST` to previously plain iCal downloads is technically a new field in the output, but it is a valid iCalendar property and all RFC 5545-compliant calendar clients accept it gracefully. The existing `ical` download endpoints for public and authenticated event access are guarded by `S.crm_activities_enabled` — if the master flag is off the `_build_ics` signature change is inert because `method` defaults to `"REQUEST"` but is never actually present in the output without the flag change; see design choice below.

**Design choice — `METHOD` in download endpoints**: The `_build_ics` extension adds `METHOD:{method}` only when the function is called with an explicit `method` argument. Existing download endpoints call `_build_ics(evt, event_id)` and therefore receive the default `method="REQUEST"`. To avoid changing the download ICS output without a flag guard, the implementation should instead default `method=None` and emit the `METHOD:` line only when `method is not None`:

```python
def _build_ics(evt: dict, event_id: str, method: str | None = None) -> str:
    lines = [
        "BEGIN:VCALENDAR",
        "VERSION:2.0",
        "PRODID:-//TestLogon//EN",
        "CALSCALE:GREGORIAN",
    ]
    if method:
        lines.append(f"METHOD:{method}")
    lines += ["BEGIN:VEVENT", ...]
```

This preserves exact backward compatibility for existing callers: `_build_ics(evt, event_id)` produces output identical to the current implementation.

**`send_alert_email` is unchanged**: the new `send_calendar_invite_email` is an additive sibling function in `app/services/alerts.py`. All existing callers of `send_alert_email` are unaffected.

**No migration required**: with both CRM flags off after deployment, no existing functionality changes. Operators enable the feature by setting `CRM_ACTIVITIES_ENABLED=1` and `CRM_EVENT_REMINDERS_ENABLED=1` in `.env.local` (dev) or the production environment and restarting the backend.

## 10. Open Questions / Assumptions

1. **`get_profile_identity` returns `displayed_email`** (line `profile.get("displayed_email")` at `profile.py:313`). If a user's account has a primary email stored under a different key (e.g. `email` vs `displayed_email`), invitations to that user will be silently dropped. Assumption: `displayed_email` is the canonical email field populated during registration. If not, the lookup key needs a follow-up fix in `get_profile_identity`.

2. **Max attendees per event**: `EventCreateIn.attendees` is `List[str]` with no `max_length` constraint (`app/models.py:1264`). The 50-attendee cap in `_dispatch_invite_emails` is a defensive ceiling only. If the platform intends to support large-group events, a separate fan-out queue (SQS or a background task) should replace the inline loop. This is deferred to a follow-up if load testing reveals latency issues.

3. **Organizer display name in email body**: `get_profile_identity(organizer_sub)` is called once to build the body text "Organizer: {name}". This adds one extra DynamoDB read per dispatch call. If this is a concern, the organizer's display name can be omitted from the body in a first iteration.

4. **ICS `ORGANIZER:` field**: RFC 5546 recommends an `ORGANIZER:mailto:{email}` line in iTIP requests. This ticket omits it to keep the first implementation minimal. Calendar clients function without it; the field can be added in ACT-002 or a follow-up once the organizer's email is known.

5. **Recurrence in ICS attachment**: the existing `_build_ics` does not emit `RRULE:` lines (the `YEARLY` extension is in ACT-005). Invitation emails for recurring events will reference only the base event times, not the recurrence rule. This is acceptable for the P1 implementation; `RRULE:` in iTIP invites is a P2 follow-up.

6. **`update_event` dispatches to all attendees, not just new ones**: the current change-detection logic sends `METHOD:REQUEST` to all current attendees when times change, even if a particular attendee's relationship to the event did not change. RFC 5546 recommends this approach (all attendees receive the updated VEVENT). If the platform later tracks per-attendee RSVP state (ACT-002), the dispatch can be scoped to only newly-added attendees for name/description changes.
