# EML-004 — IMAP inbox sync and email threading

**Ticket type:** Feature
**Priority:** P2
**Estimate:** 4d
**Feature flag:** `EMAIL_CLIENT_ENABLED` (default `false`)

---

## 1. Summary & Goal

Implement server-side IMAP inbox synchronisation: fetch message headers and plain-text/HTML bodies from a user's registered IMAP account (provided by EML-003), store them in DynamoDB, derive stable thread identifiers from RFC-2822 `Message-ID` / `In-Reply-To` / `References` headers, and expose list/get/thread endpoints that the in-app email client UI (EML-005) will consume. Large HTML bodies that exceed DynamoDB's practical item-size budget are spilled to S3 and replaced with a presigned download URL at read time.

The entire feature is additive. With `EMAIL_CLIENT_ENABLED=false` (the default) no new code path executes, no IMAP connections are opened, and the existing SES outbound pipeline (`send_alert_email` at `app/services/alerts.py:459`) is byte-for-byte unchanged.

## 3. Data Model

### 3.1 New DynamoDB table: `user_email_messages`

**Primary key:** `PK = USER#{user_sub}#ACCT#{account_id}` (String), `SK = MSG#{uid_str:010d}` (String, UID zero-padded to ten digits for lexicographic sort fidelity).

| Attribute | Type | Notes |
|---|---|---|
| `pk` | S | `USER#{user_sub}#ACCT#{account_id}` |
| `sk` | S | `MSG#{uid:010d}` |
| `uid` | N | IMAP UID (integer) |
| `message_id` | S | RFC-2822 `Message-ID` header value, trimmed of `<>` |
| `in_reply_to` | S | `In-Reply-To` header, absent if not present |
| `references` | L(S) | `References` header parsed into a list of Message-ID strings |
| `thread_id` | S | `sha256(root_message_id)[:16]` — see §5.1 |
| `subject` | S | Decoded subject header, max 500 chars |
| `from_addr` | S | Primary `From` address |
| `to_addrs` | L(S) | `To` header address list |
| `cc_addrs` | L(S) | `Cc` header address list |
| `date_ts` | N | Unix timestamp parsed from `Date` header; falls back to `synced_at` |
| `folder` | S | IMAP folder name e.g. `INBOX`, `Sent`, `Drafts`, `[Gmail]/Trash` |
| `flags` | L(S) | IMAP flags e.g. `["\\Seen", "\\Answered"]` |
| `snippet` | S | First 200 chars of decoded plain-text body |
| `body_text` | S | Plain-text body, up to 32 KB stored inline; truncated with a `…` marker |
| `body_html` | S | HTML body up to 64 KB stored inline; when larger: absent (replaced by `body_html_s3_key`) |
| `body_html_s3_key` | S | S3 key when HTML body exceeds 64 KB; absent otherwise |
| `has_attachments` | BOOL | True when MIME parts with `Content-Disposition: attachment` are found |
| `synced_at` | N | `now_ts()` at time of upsert |
| `ttl_epoch` | N | `synced_at + S.email_messages_ttl_days * 86400`; DynamoDB TTL attribute |

**GSI `ByFolder`:**
- Partition key: `folder_pk` (S) — value `USER#{user_sub}#ACCT#{account_id}#FOLDER#{folder}`
- Sort key: `date_ts` (N)
- Projection: ALL
- Declaration in `scripts/local-ddb-init.py` must include `attr_types={"date_ts": "N"}` per the CLAUDE.md gotcha (numeric GSI sort key).

**GSI `ByThread`:**
- Partition key: `pk` (S) — reuses the primary partition key `USER#{user_sub}#ACCT#{account_id}`
- Sort key: `thread_id` (S) — groups all messages with the same thread root together
- Projection: ALL
- No `attr_types` needed (String SK).

**Sync cursor row** (same table, separate item):

| Attribute | Value |
|---|---|
| `pk` | `USER#{user_sub}#ACCT#{account_id}` |
| `sk` | `SYNC#CURSOR` |
| `folder` | e.g. `INBOX` |
| `last_uid` | N — highest UID successfully synced for this folder |
| `last_synced_at` | N — `now_ts()` |

One `SYNC#CURSOR` row is maintained per `(user, account, folder)` triple. The sync cursor row is exempt from TTL so it is never auto-deleted.

## 5. Detailed Behavior & Edge Cases

### 5.1 Thread-ID derivation

`derive_thread_id` implements the following algorithm:

1. Collect candidates: the full `references` list (oldest first by convention), then `in_reply_to`, then `message_id` itself.
2. For each candidate Message-ID in order, query `T.user_email_messages` with `get_item(Key={"pk": pk, "sk": ...})` where the SK would be `MSG#{uid:010d}` — but since we index by UID, not by `message_id`, we need a secondary approach. The correct path: query `ByThread` GSI with `KeyConditionExpression=Key("pk").eq(pk) & Key("thread_id").eq(candidate_hash)` to check if any message with that thread already exists in the table.
3. If a known thread is found, return that `thread_id`.
4. If none is found (this is the root message), compute `hashlib.sha256(message_id.encode("utf-8")).hexdigest()[:16]` and return it.

This means: the first message in a thread that arrives sets the `thread_id = sha256(its own message_id)[:16]`. All subsequent replies that reference it — directly or transitively — resolve to the same `thread_id` because step 2 will find the existing row.

**Edge cases:**
- `message_id` is empty or missing (malformed MIME): generate a synthetic `message_id = f"<synthetic-{uid}-{account_id}@local>"` and derive `thread_id` from that.
- `References` header lists Message-IDs for messages not yet in the table (out-of-order delivery): treat them as unknown; fall back to `in_reply_to`; if that is also missing, use `message_id` as root. When the referenced root later arrives, it gets a new `thread_id` computed from its own `message_id`, and will not automatically re-thread existing messages. This is an acceptable eventual consistency trade-off; a future re-threading sweep is a follow-up.
- Very long `References` list: cap candidate search at 10 entries.

### 5.2 Idempotent upsert

`sync_inbox` upserts each message using `T.user_email_messages.put_item(Item={...})` unconditionally. Re-running sync for the same folder and UID overwrites the DDB item with the same data. This is safe because: the `sk = MSG#{uid:010d}` key is deterministic per UID, and IMAP UIDs are stable within a folder for the lifetime of a mailbox (RFC-3501 §2.3.1.1). If a message is flagged as `\Seen` between two syncs, the second sync updates the `flags` field in place.

### 5.3 Large HTML body spill to S3

In `_parse_message`, after decoding the HTML part:
- If `len(html_bytes) <= 65536` (64 KB): store inline as `body_html`.
- Else: call `_spill_html_to_s3(user_sub, account_id, uid, html_str)` which calls `s3_client().put_object(Bucket=S.email_bodies_s3_bucket, Key=key, Body=html_bytes, ContentType="text/html; charset=utf-8")`. Store the returned key as `body_html_s3_key`; omit `body_html` from the DDB item.

In `get_message`, when `body_html_s3_key` is present:
- Dev mode: inject `body_html_url = f"/mock/s3/{S.email_bodies_s3_bucket}/{body_html_s3_key}"`.
- Prod: `body_html_url = s3_client().generate_presigned_url("get_object", Params={"Bucket": ..., "Key": ...}, ExpiresIn=300)`.

The `list_messages` endpoint never fetches body fields; `body_html` and `body_text` are set to `None` in the list response.

### 5.4 Sync cursor management

Before each sync run, `sync_inbox` reads the `SYNC#CURSOR` item for `(user_sub, account_id, folder)`:
- `last_uid = item.get("last_uid", 0)` — IMAP SEARCH will use `UID {last_uid+1}:*`.
- After successful upsert of all fetched messages, write back the cursor with `last_uid = max(fetched_uids)` and `last_synced_at = now_ts()`.
- The cursor item does NOT have a `ttl_epoch` so it persists indefinitely. It is only deleted if the EML-003 `delete_account` endpoint is called (which should also purge all messages for that account — a cascade specified in EML-003, not extended here).

If the IMAP server returns no UIDs since `last_uid+1`, return `{"synced": 0, "folder": folder, "last_uid": last_uid}` immediately without writing the cursor.

### 5.5 IMAP connection handling

`_open_imap` behaviour:
1. Call `user_email_accounts.get_account(user_sub, account_id)` to retrieve the account row (includes `imap_host`, `imap_port`, `imap_use_ssl`, `username`, `password_ct_b64`).
2. Decrypt `password_ct_b64` via `kms_decrypt(account["password_ct_b64"]).decode("utf-8")`.
3. If `S.dev_mode` is True: return `_MockImapClient()` regardless of credentials (SECOPS-007 parity — same code path, mock substituted at the boundary).
4. Otherwise: open `imaplib.IMAP4_SSL(host, port)` with a connect timeout of `S.email_imap_timeout_seconds`; call `imap.login(username, password)`. On `imaplib.IMAP4.error` or `socket.timeout`: raise `HTTPException(503, {"code": "imap_connect_failed", "message": str(e)})` and update the account's `status = "error"` and `last_error` via `user_email_accounts.update_account`.

After sync completes: `imap.logout()`. On any exception during fetch (after successful connect): log the error, persist partial results (any messages already upserted), update account `status = "error"`, re-raise as 503.

### 5.6 Plain-text body extraction

`_parse_message` walks the MIME tree using `email.parser.BytesParser().parsebytes(raw)`:
- Plain-text: collect all `text/plain` parts decoded with the charset from `Content-Type` (fallback: `utf-8` with `errors="replace"`). Concatenate, truncate to 32 768 chars. First 200 chars → `snippet`.
- HTML: collect the first `text/html` part (prefer the last in a `multipart/alternative` since RFC-2046 §5.1.4 puts the richest format last). If size > 64 KB, spill to S3.
- Attachments: detect any MIME part where `Content-Disposition` header starts with `attachment` → set `has_attachments = True`.

### 5.7 Concurrency safety

If two sync calls for the same account run concurrently (e.g., two browser tabs), both will read the same `last_uid` cursor, fetch overlapping UIDs, and attempt to `put_item` the same DDB rows. Since `put_item` is unconditional, the last writer wins and the result is correct (both calls fetched the same messages). The cursor update may race; the worst outcome is that one call's `last_uid` overwrites the other's, potentially causing a brief re-fetch on the next sync. This is acceptable — IMAP UIDs are unique and upserts are idempotent.

### 5.8 Ownership enforcement

The `pk` value `USER#{user_sub}#ACCT#{account_id}` is both the DDB partition key and the ownership boundary. A user can never read another user's messages by construction: `list_messages` and `get_message` always construct the `pk` from the authenticated `session.user_sub`, not from a request-supplied value.

| IMAP client | `_MockImapClient` (same module, returned when `S.dev_mode=True` inside `_open_imap`) | `imaplib.IMAP4_SSL` |
| S3 body spill | `s3_client().put_object(...)` — intercepted in-process by moto (no endpoint URL set in dev, per `app/core/aws_clients.py:82`) | Real S3 |
| Presigned URL | `/mock/s3/{bucket}/{key}` | `s3_client().generate_presigned_url(...)` |

| DynamoDB | DynamoDB Local at port 8001 | AWS DynamoDB |

No `if S.dev_mode:` branches exist outside of `_open_imap` (IMAP client selection) and the presigned URL return in `get_message`. Both of these mirrors are already established in the codebase (KYC partner API uses the identical presigned-URL pattern at `app/services/kyc_partner_api.py:630–631`).

### Idempotency

- `sync_inbox` is unconditionally idempotent: re-running it for the same UIDs produces identical DDB items.
- `PUT /sync` is a POST by HTTP convention (triggering a side-effectful action), but calling it twice is safe.
- `get_message` and `list_messages` are pure reads.
- The S3 `put_object` for HTML spill is also idempotent (same key, same content on re-sync).

### Security

- **Password never leaves the server.** `password_ct_b64` is decrypted inside `_open_imap` and the plaintext is discarded after the IMAP `login()` call. It is never logged, returned in API responses, or serialised.
- **Ownership enforced at partition key.** The `pk = USER#{user_sub}#ACCT#{account_id}` construction means a user cannot read another user's messages even if they guess an `account_id`.
- **HTML body isolation.** The S3 key prefix `email-bodies/{user_sub}/{account_id}/` isolates each user's large HTML bodies. S3 bucket-level policies (prod) should deny `s3:GetObject` from other principals; in dev, moto provides in-process isolation by default.
- **No IMAP credentials in logs.** `_open_imap` catches `imaplib.IMAP4.error` and logs only `str(e)` (which IMAP libraries redact passwords from). The `update_account` call stores `last_error = str(e)[:500]`.
- **CSRF protection.** All mutating endpoints (`POST /sync`) inherit the `require_ui_session` CSRF enforcement from EML-003's router. Bearer-auth callers bypass CSRF per the existing `deps.py` design.
- **Audit trail.** `sync_inbox` calls `audit_event("email_inbox_synced", user_sub, account_id=account_id, folder=folder, synced=count)` after a successful sync. This follows the same pattern as `app/services/ssh_key_manager._audit` (fire-and-forget, swallows exceptions).

## 8. Backward Compatibility & Migration

### No existing data to migrate

This is a net-new table and service. There are no pre-existing rows to migrate.

### DynamoDB table creation

The `user_email_messages` table is created by `scripts/local-ddb-init.py` on `just up` / `just restart`. In production, `UpdateTable` + `CreateTable` must be run before deploying the code that references `T.user_email_messages`. The table creation is safe to run before the feature flag is enabled.

### Existing surfaces unchanged

- `T.email_delivery`, `send_alert_email`, `app/routers/admin_email.py`, and `app/services/alerts.py` are untouched.
- The `app/routers/user_email_accounts.py` router is extended (new endpoints appended); the existing EML-003 endpoints at `POST /`, `GET /`, `PATCH /{id}`, `DELETE /{id}`, `POST /{id}/verify` are byte-for-byte unchanged.
- `app/models.py` additions are purely additive (new classes, no changes to existing ones).
- `app/core/settings.py` additions are new fields with defaults; no existing field is changed.

### Rollback

Disabling `EMAIL_CLIENT_ENABLED=0` at runtime causes all new endpoints to return 503 immediately. The `user_email_messages` table can be left in place (data TTLs after `email_messages_ttl_days` days). No compensating DML is required.

## 10. Open Questions / Assumptions

1. **Multi-folder sync.** The spec supports syncing any named folder via the `folder` parameter, but does not implement folder discovery (IMAP `LIST`). EML-005 (UI) should drive folder discovery and call sync per folder. A `GET /{account_id}/folders` endpoint is deferred to EML-005.

2. **Sent/Drafts sync.** `sync_inbox` accepts any folder name including `Sent` and `Drafts`. The same code path handles all; no folder-specific logic is needed.

3. **Message deletion / flag sync.** This ticket only appends new messages (UIDs since `last_uid`). Deleted or expunged messages on the server are not removed from DDB; they TTL-expire after `email_messages_ttl_days` days. A full IMAP EXPUNGE reconciliation is deferred.

4. **OAuth-authenticated IMAP (Gmail/Outlook XOAUTH2).** EML-003 stores password credentials. XOAUTH2 bearer-token authentication (used by Gmail when "less secure apps" are disabled) requires a separate OAuth flow. This is a known gap; assumed out of scope for the EML-004 estimate (4d). A future EML-00X ticket will add OAuth IMAP support.

5. **`EMAIL_BODIES_S3_BUCKET` must exist in prod.** The spec assumes the S3 bucket is created before deployment. In dev, moto's in-process intercept creates the bucket lazily on first `put_object`. A `CreateBucketIfNotExists` guard in `_spill_html_to_s3` for dev bootstrapping is acceptable.

6. **imaplib SSL certificate verification.** `imaplib.IMAP4_SSL` defaults to `ssl.create_default_context()` which enforces certificate verification. Self-signed certs (common in on-prem mail servers) will fail. A per-account `imap_verify_ssl: bool = True` flag is a follow-up; for now the default is strict verification.

7. **Assumed EML-003 is merged first.** The `user_email_accounts` table, service, and router (including the `get_account` and `update_account` functions) must exist before this ticket can be implemented. The `Tables` dataclass field `user_email_accounts` is added by EML-003.
