# EVT-004 — CRM Event capacity limits and waitlist with auto-promotion

**Type:** Feature | **Priority:** P2 | **Estimate:** 2d
**Source:** `docs/suitecrm/CRM_MISC_TICKETS.md` (section "EVT-004")
**Dependencies:** EVT-003 (registration rows, `app/services/crm_events.py`, `app/routers/crm_events.py` all established there).

---

## 1. Summary & Goal

EVT-004 adds enforced capacity limits and an automatic waitlist to CRM events. After this ticket:

- When a CRM event's META row carries a positive `max_attendance` value, new registrations that would exceed capacity are **automatically waitlisted** rather than accepted. The caller receives a `status="waitlisted"` row and an informational notification; no error is returned.
- When a confirmed participant cancels (new `DELETE /{event_id}/registrations/{sub}` endpoint) or declines an existing registration, the topmost waitlisted entrant is **automatically promoted** to `status="registered"` and notified via email and in-app alert.
- A read-only `GET /{event_id}/capacity` endpoint returns live counts: `max_attendance`, `accepted_count`, `waitlisted_count`, and `available_spots`.
- The new `waitlist_position` integer field (already declared as optional on `CrmRegistrationOut` in EVT-003) is populated atomically and decremented on promotion.

The entire feature remains gated behind the `crm_events_enabled` flag from EVT-001 (default `False`). No new feature flag is introduced. With the flag off, the platform is byte-for-byte identical to its pre-EVT-004 state.

## 3. Data Model

### 3.1 No new tables

EVT-004 introduces no new DynamoDB tables. All persistence uses `crm_events` and `crm_event_registrations` scaffolded by EVT-001. No changes to `scripts/local-ddb-init.py` or `app/core/tables.py` are needed.

### 3.2 Registration row additions (`crm_event_registrations`)

The registration row written by EVT-003 gains two new optional attributes, both set only when the registrant is placed on the waitlist:

| Attribute | DDB Type | Nullable | Description |
|-----------|----------|----------|-------------|
| `waitlist_position` | N | Yes (absent for direct registrations) | Monotonically increasing integer, starting at 1 for the first waitlisted registrant. Set at insert time via atomic `ADD` on the META row's `waitlist_counter`. |
| `waitlisted_at` | N | Yes (absent for direct registrations) | Unix timestamp when the row was first placed on the waitlist, set to `now_ts()`. Distinct from `registered_at` (which is always set regardless of path). |

Existing rows written by EVT-003 without `waitlist_position` continue to work: `item.get("waitlist_position")` returns `None`, and `CrmRegistrationOut.waitlist_position` defaults to `None` (already declared optional in EVT-003).

### 3.3 META row addition (`crm_events`)

The META row (`PK=event_id, SK="META"`) gains one new optional attribute used as an atomic waitlist-position counter:

| Attribute | DDB Type | Nullable | Description |
|-----------|----------|----------|-------------|
| `waitlist_counter` | N | Yes (absent until first waitlisted registration) | Monotonically increasing counter. Each new waitlisted registrant atomically increments this via `update_item ADD waitlist_counter :one` and receives the post-increment value as their `waitlist_position`. |

The counter is never decremented on promotion — positions are assigned permanently and are used only for ordering (lowest position = next in line). On promotion the promoted row's `waitlist_position` is retained for audit trail; it is not removed or zeroed.

### 3.4 Status state machine (extended from EVT-003)

```
[new] ──► registered  ──► accepted  ──► attended
  │          │               │
  │          └──► declined   └──► declined
  │
  └──► waitlisted  ──► registered  (on promotion)
            │
            └──► cancelled  (DELETE endpoint)
```

`cancel_registration` (new DELETE endpoint) transitions any non-`attended` status → `cancelled`, then fires `_promote_from_waitlist`. An `attended` registration cannot be cancelled (409).

The `_count_accepted` helper counts `status in {"registered", "accepted", "attended"}`. "Waitlisted" and "cancelled" and "declined" rows do not count against capacity.

### 3.5 GSI changes

No GSI additions or modifications. `_promote_from_waitlist` uses a Scan on the base table (PK=`event_id`) with `FilterExpression="attribute_exists(waitlist_position) AND #s = :waitlisted"` and loops over `LastEvaluatedKey`. A GSI on `waitlist_position` would reduce cost on very large events, but adds schema complexity; it is deferred to a future optimization ticket. On typical CRM event sizes (< 1000 registrants per event, well within 1MB per Query page), a filtered Scan over the single event's rows is acceptable.

An alternative: use `KeyConditionExpression="event_id = :eid"` (base table Query) and apply `FilterExpression` client-side after the Query. This is cheaper than a full-table Scan: it scans only items within the `event_id` partition, not the entire table. The implementation uses this pattern (Query on base PK, not a full Scan).

#### `_count_accepted`

```python
def _count_accepted(event_id: str) -> int:
    """
    Return the number of registrations with status in
    {"registered", "accepted", "attended"} for `event_id`.

    Loops over LastEvaluatedKey because FilterExpression does not reduce
    DynamoDB page size (CLAUDE.md DynamoDB gotcha).
    """
```

Steps:
1. Build a `Query` on `T.crm_event_registrations` base table:
   - `KeyConditionExpression="event_id = :eid"`, `ExpressionAttributeValues={":eid": event_id}`.
   - `FilterExpression="#s IN (:r, :a, :at)"` with `ExpressionAttributeNames={"#s": "status"}` and values for `registered`, `accepted`, `attended`.
   - `Select="COUNT"` — returns only `Count` and `ScannedCount`, no items. Cost is proportional to scanned items but no data is transferred.
2. Loop over `LastEvaluatedKey`, accumulate `Count` from each page.
3. Return total count.

Using `Select="COUNT"` eliminates item deserialization cost; the only returned field per page is `Count`. This is safe because `FilterExpression` is applied server-side before the count is returned, even with `Select="COUNT"`.

#### `_next_waitlist_position`

```python
def _next_waitlist_position(event_id: str) -> int:
    """
    Atomically increment the META row's `waitlist_counter` and return
    the new value. This is the `waitlist_position` for the new waitlisted row.

    Uses DynamoDB ADD expression (atomic increment, no read-modify-write race).
    """
```

Steps:
1. `T.crm_events.update_item`:
   - `Key={"event_id": event_id, "sk": "META"}`.
   - `UpdateExpression="ADD waitlist_counter :one"`.
   - `ExpressionAttributeValues={":one": 1}`.
   - `ReturnValues="UPDATED_NEW"`.
2. Return `int(response["Attributes"]["waitlist_counter"])`.

This is the same `ADD` idiom used by `app/services/rate_limit.py:45` (`UpdateExpression="ADD #cnt :one ..."`) and by DynamoDB-backed atomic counters throughout the codebase.

#### Modified `register_for_event` (extends EVT-003)

The EVT-003 implementation calls `put_item` and always writes `status="registered"`. EVT-004 inserts a capacity check between the META row lookup (step 1) and the `put_item` (step 4 in EVT-003):

```python
def register_for_event(event_id: str, registrant_sub: str) -> dict:
    """
    Create a registration row.

    If `max_attendance` is set on the event META row and
    _count_accepted(event_id) >= max_attendance, the new registration
    is placed on the waitlist (status="waitlisted", waitlist_position assigned).
    Otherwise the row is written with status="registered".

    Raises:
        HTTPException(404) if the event META row does not exist.
        HTTPException(409) if the user is already registered (or waitlisted).
    Returns:
        The newly created registration item dict.
    """
```

Steps (EVT-004 additions in **bold**):
1. `get_item(Key={"event_id": event_id, "sk": "META"})` on `T.crm_events` — raises 404 if absent.
2. Set `invited` flag (existing EVT-003 logic).
3. **Check capacity: `max_attendance = int(meta.get("max_attendance") or 0)`. If `max_attendance > 0` and `_count_accepted(event_id) >= max_attendance`: set `on_waitlist = True`. Otherwise `on_waitlist = False`.**
4. **If `on_waitlist`: call `position = _next_waitlist_position(event_id)`. Build item with `status="waitlisted"`, `waitlist_position=position`, `waitlisted_at=now_ts()`.**
5. **Else: build item with `status="registered"` (existing path, no `waitlist_position`).**
6. `put_item` with `ConditionExpression="attribute_not_exists(event_id) AND attribute_not_exists(registrant_sub)"` — raises 409 on conflict (duplicate registration or duplicate waitlist entry).
7. `audit_event("crm_event_registered", registrant_sub, event_id=event_id, status=item["status"])`.
8. **If `on_waitlist`: best-effort `write_alert` for registrant with title "You have been added to the waitlist for [event name]" and best-effort `send_alert_email` to the registrant.**
9. Best-effort owner notification email (existing EVT-003 logic).
10. Return item.

The race condition between `_count_accepted` and `put_item` is accepted by design: in the narrow window between the count read and the write, another registration could push the event over capacity. At high concurrency this can admit one or two extra direct registrants. The alternative — a DynamoDB transaction — adds significant complexity. For CRM event sizes, the occasional over-admission is preferable to transaction overhead. This is documented as an open question in section 10.

#### `_promote_from_waitlist`

```python
def _promote_from_waitlist(event_id: str) -> dict | None:
    """
    Find the waitlisted registration with the lowest `waitlist_position`
    and promote it to status="registered".

    Sends an email and in-app alert to the promoted registrant.

    Returns the promoted registration item dict, or None if no waitlisted
    registrations exist.

    Called after a cancel or decline transition.
    """
```

Steps:
1. Query `T.crm_event_registrations` base table for all rows in the `event_id` partition:
   - `KeyConditionExpression="event_id = :eid"`.
   - `FilterExpression="attribute_exists(waitlist_position) AND #s = :wl"` with `ExpressionAttributeNames={"#s": "status"}` and `":wl": "waitlisted"`.
   - Loop over `LastEvaluatedKey`; collect all waitlisted items.
2. If no items found: return `None`.
3. Sort collected items by `int(item["waitlist_position"])` ascending; take the first (`min_position`).
4. Promote: `T.crm_event_registrations.update_item`:
   - `Key={"event_id": event_id, "registrant_sub": min_item["registrant_sub"]}`.
   - `UpdateExpression="SET #s = :reg, promoted_at = :t"`.
   - `ConditionExpression="#s = :wl"` — guards against a concurrent promotion racing on the same row; if the condition fails (the row was already promoted by a concurrent request), catch `ConditionalCheckFailedException` and return `None` (promotion already occurred).
   - `ExpressionAttributeNames={"#s": "status"}`.
   - `ExpressionAttributeValues={":reg": "registered", ":wl": "waitlisted", ":t": now_ts()}`.
   - `ReturnValues="ALL_NEW"`.
5. `audit_event("crm_event_waitlist_promoted", min_item["registrant_sub"], event_id=event_id, waitlist_position=min_item["waitlist_position"])`.
6. Resolve registrant email from `T.users` (`get_item(Key={"user_sub": registrant_sub})`); best-effort `send_alert_email` with subject "You have been promoted from the waitlist for [event name]" and body explaining their registration is now confirmed.
7. Best-effort `write_alert` for the promoted registrant: title "Waitlist promotion: your registration for [event name] is confirmed".
8. Return the updated item (from `ReturnValues="ALL_NEW"`).

The conditional `update_item` in step 4 prevents double-promotion: if two cancel/decline operations fire concurrently (race), the first one to execute the `update_item` wins and the second receives `ConditionalCheckFailedException` and returns `None` safely. This is the canonical DynamoDB optimistic-lock pattern, matching the one-time-use cart recovery token pattern documented in CLAUDE.md ("a `RECOVERY#CONSUMED#{jti}` row is written... with a conditional put; second use → 400").

#### `cancel_registration`

```python
def cancel_registration(event_id: str, registrant_sub: str, actor_sub: str) -> dict:
    """
    Cancel a registration. Triggers waitlist promotion.

    Authorization is checked by the router before calling this function.

    Raises:
        HTTPException(404) if the registration row does not exist.
        HTTPException(409) if the registration is already attended (terminal).
    Returns:
        The updated (cancelled) registration item dict.
    """
```

Steps:
1. `get_item(Key={"event_id": event_id, "registrant_sub": registrant_sub})` on `T.crm_event_registrations` — raises 404 if absent.
2. If `status == "attended"`: raise `HTTPException(409, "Cannot cancel a checked-in registration")`.
3. `update_item` SET `status = "cancelled"`, `cancelled_at = now_ts()`. No condition expression (a concurrent double-cancel is safe; the second write is a no-op on an already-cancelled row).
4. `audit_event("crm_event_cancelled", actor_sub, event_id=event_id, registrant_sub=registrant_sub)`.
5. If the cancelled registration had `status in {"registered", "accepted"}` (i.e., it was consuming a capacity slot — checked against the pre-cancel item retrieved in step 1): call `_promote_from_waitlist(event_id)`. A `waitlisted` or `declined` cancellation does not free a capacity slot and does not trigger promotion.
6. Return updated item.

## 5. Detailed Behavior & Edge Cases

### 5.1 Unlimited events (`max_attendance` absent or null)

If the META row has no `max_attendance` field (or it is 0), `register_for_event` always writes `status="registered"` and never calls `_next_waitlist_position`. `get_event_capacity` returns `{"max_attendance": null, "available_spots": null, ...}`. The waitlist feature is fully inert for unlimited events.

### 5.2 Race condition between count and write

Between `_count_accepted(event_id)` and the `put_item`, another concurrent registration may succeed, putting the event over capacity by one. DynamoDB transactions (`TransactWriteItems`) could make this atomic but add significant latency and complexity. Given CRM event sizes and the non-critical nature of a brief over-admission, the eventual-consistency approach is acceptable. The `get_event_capacity` endpoint reflects the true current count immediately after any registration.

### 5.3 `_promote_from_waitlist` called with no waitlisted rows

Returns `None` immediately after the Query returns an empty result set. No `update_item`, no notification. This is not an error — it simply means the waitlist is empty.

### 5.4 Concurrent cancel/decline triggering double-promotion

If two participants cancel simultaneously, both calls execute `_promote_from_waitlist`. The `update_item` condition `#s = :wl` on the top waitlisted row means only one of the two promotions can succeed for any given row. The second concurrent call catches `ConditionalCheckFailedException` and returns `None`. Each cancel/decline call promotes at most one waitlisted registrant; if two capacity slots open simultaneously, the second slot stays open (visible via `get_event_capacity`) and the next registrant receives `status="registered"` directly rather than being waitlisted.

### 5.5 Cancelling a waitlisted registration

If a registrant on the waitlist cancels their spot (`DELETE .../registrations/{sub}` where their `status="waitlisted"`), `cancel_registration` checks the pre-cancel `status`: since `"waitlisted"` is not in `{"registered", "accepted"}`, `_promote_from_waitlist` is **not** called. No capacity slot was held by a waitlisted registrant, so no slot is freed.

### 5.6 Cancelling a `declined` registration

A declined registration (`status="declined"`) similarly did not hold a capacity slot. `cancel_registration` transitions it to `"cancelled"` without triggering promotion.

### 5.7 `waitlist_counter` starting value

The first `ADD :one` on a META row with no existing `waitlist_counter` attribute: DynamoDB's `ADD` semantics treat a missing `N` attribute as 0, so the first increment returns 1. The first waitlisted registrant receives `waitlist_position=1`.

### 5.8 `waitlist_position` ordering stability

`waitlist_position` values are never reused or reassigned after promotion. After a promotion, the promoted registrant's row retains `waitlist_position=1` (for example) in the DDB item, but `status="registered"`. The next time `_promote_from_waitlist` runs, the Query with `FilterExpression="#s = :wl"` excludes it from the result set, so the next-lowest `waitlist_position` among remaining waitlisted rows is correctly selected.

### 5.9 `_count_accepted` and the `waitlisted` status

`"waitlisted"` is explicitly excluded from `_count_accepted`. A waitlisted registrant does not consume a capacity slot. This is correct: their registration is pending, not confirmed.

### 5.10 Capacity endpoint authorization

`GET /{event_id}/capacity` does not require the caller to be the event owner; any authenticated user can read capacity. This is intentional to enable the frontend to display "X spots remaining" before a user decides to register. An admin or owner viewing the management UI sees the same data.

### 5.11 `max_attendance` update after waitlist forms

If an organizer increases `max_attendance` after a waitlist has formed (via an `update_event` call outside this ticket's scope), `_promote_from_waitlist` is not automatically triggered. The waitlisted registrants remain waitlisted until the next cancel/decline event fires the promotion hook. A bulk-promotion endpoint is not in scope for this ticket; it is an open question in section 10.

### 5.12 Notification failure is non-blocking

All `write_alert` and `send_alert_email` calls inside `_promote_from_waitlist` and `register_for_event` are wrapped in `try/except Exception: pass`. A failed SES call must never roll back a successful waitlist write or promotion.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007: No dev/prod branches

No `if S.dev_mode:` branch is introduced in any service or router function in this ticket. The two notification calls (`send_alert_email`, `write_alert`) already branch internally: `send_alert_email` (`app/services/alerts.py:459`) writes to the dev log file in dev mode and dispatches via SES in prod. `write_alert` (`app/services/alerts.py:356`) writes to `T.alerts` identically in both environments (DynamoDB Local in dev, real DynamoDB in prod). The DDB operations (`put_item`, `update_item`, `query`) are identical paths dev (DynamoDB Local at port 8001) and prod (real DynamoDB) — SECOPS-007 parity is fully maintained.

### 7.2 Idempotency

| Operation | Idempotency guarantee |
|-----------|----------------------|
| `register_for_event` (waitlisted) | Conditional `put_item`; second call → 409. `waitlist_counter` is incremented only once per registrant. |
| `_next_waitlist_position` | Each call atomically increments the counter. It is called at most once per registration attempt (after the capacity check confirms waitlisting). |
| `_promote_from_waitlist` | `ConditionExpression="#s = :wl"` on the `update_item` prevents double-promotion. Called from `cancel_registration` and `respond_to_invitation`; both are idempotent at the outer level (the first call changes status to a non-promoting terminal; a second concurrent call sees the changed status and takes the non-promotion path). |
| `cancel_registration` | Second call is safe: the row is already `"cancelled"`, `update_item` overwrites it with the same value. Promotion is not triggered a second time because the first cancel already transitioned the status away from `{"registered", "accepted"}`. |
| `get_event_capacity` | Read-only; always idempotent. |

### 7.3 Authorization boundaries

| Endpoint | Who can call |
|----------|-------------|
| `DELETE /{event_id}/registrations/{sub}` (cancel) | Own registration (`caller == registrant_sub`), or event owner (`caller == meta["owner_sub"]`), or `role >= ADMIN`. Anyone else → 403. |
| `GET /{event_id}/capacity` | Any authenticated user. |

The cancellation authorization rule intentionally mirrors `respond_to_invitation` from EVT-003 (same three principals). The event owner can cancel any registration to free capacity (e.g., a no-show cleanup). An ADMIN can cancel for operational purposes.

### 7.4 No privilege escalation via waitlist position

`waitlist_position` is assigned by the server from an atomic server-side counter, not accepted from the client request. The client has no input into the position; the `POST /{event_id}/register` endpoint takes only `event_id` as a path param and no body fields affect the waitlist assignment.

### 7.5 Capacity race window

As noted in section 5.2, there is a brief consistency window between `_count_accepted` and `put_item`. An adversary cannot exploit this to gain a preferred registration status — the worst case is that one extra registrant is admitted directly instead of being waitlisted. This is an availability improvement for the user, not a security concern.

### 7.6 `waitlist_counter` cannot be reset via API

No endpoint exposes the `waitlist_counter` attribute for write. It is a server-side monotonic counter. The only write path is `_next_waitlist_position` via `ADD :one`. It is surfaced only in the `waitlist_position` field on each registration row (read path), not in any API response.

## 10. Open Questions / Assumptions

1. **Atomicity of capacity check and registration write.** As documented in section 5.2, the count-then-write sequence is not atomic. For CRM event sizes (typical < 1000 registrants, rare concurrent spikes) the race window is milliseconds wide and the consequence (one extra direct registrant) is benign. If strict capacity enforcement is required (e.g., paid ticketed events), a DynamoDB transaction (`TransactWriteItems` combining a conditional read of the counter and the registration write) would be needed. **Assumption:** eventual consistency is acceptable for the CRM use case; strict atomicity is deferred to a future enhancement.

2. **Bulk promotion on `max_attendance` increase.** If an organizer updates `max_attendance` to a larger value after a waitlist forms, existing waitlisted registrants are not automatically promoted. The promotion hook fires only on individual cancel/decline events. A bulk promotion endpoint (`POST /{event_id}/waitlist/promote-bulk`) could drain the waitlist after a capacity increase. **Assumption:** this is out of scope for EVT-004; it can be added as a follow-up without schema changes.

3. **Notification email address resolution.** `send_alert_email` requires a resolved email address. The service calls `T.users.get_item(Key={"user_sub": registrant_sub})` and reads the `email` field. If the user record is missing or has no email, the notification is silently skipped. **Assumption:** all platform users have email addresses populated by the registration flow.

4. **Waitlist depth cap.** There is no server-side limit on the number of waitlisted registrants. For very large events, the `waitlist_counter` could grow without bound. A configurable `crm_events_waitlist_max_per_event` setting could cap this. **Assumption:** unbounded waitlist is acceptable at MVP; a cap can be added later via a new `Settings` field without schema changes.

5. **PTY contact_id support.** EVT-004 uses `user_sub` for registrant identity, consistent with EVT-003. When PTY-001 ships and CRM contacts gain a separate `contact_id`, `register_for_event` may need to accept either a `user_sub` or a `contact_id` (for contacts who are not platform users). The DDB schema accommodates this: `registrant_sub` can hold either kind of identifier; the service's authorization check simply gates on whether the caller is a platform user. **Assumption:** `user_sub` only for MVP; PTY bridge added in a later EVT ticket.

6. **`cancel_registration` vs. `respond_to_invitation(status="declined")`.** These are now two distinct code paths that both free a capacity slot. `decline` transitions `status` to `"declined"` and leaves the row; `cancel` transitions to `"cancelled"` and also leaves the row. Both trigger `_promote_from_waitlist`. This is intentional: the business semantics differ (a user who declines may re-accept; a user who cancels is considered fully out). The state machine in section 3.4 reflects this.

7. **`max_attendance` enforced on all active statuses.** The `_count_accepted` function counts `registered`, `accepted`, and `attended` rows. A user who accepted and was checked in still occupies a capacity slot. This means the event could show 0 available spots even if all attendees are already checked in and the event is live. **Assumption:** this is correct — a seat is occupied from registration through attendance. After the event ends, organizers can use the `DELETE` endpoint to clean up rows if needed.
