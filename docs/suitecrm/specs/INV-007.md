# INV-007 — Invoice-level discount rendering

## 1. Summary & Goal

INV-007 closes the gap identified in the SuiteCRM analysis: the existing
`create_invoice` service has no `discount_cents` parameter, `_render_invoice_lines`
has no discount row, and the platform financial dashboard cannot distinguish
discounted revenue from gross revenue because the ledger entry carries no discount
attribution field.

The goal is to:

1. Accept a `discount_cents` argument in `create_invoice`, cap it safely, persist
   it on the DynamoDB item, and use it in the `total_cents` formula.
2. Render a clearly-labelled negative "Discount" row in the PDF between the
   subtotal and tax lines.
3. Surface `discount_cents` in `InvoiceOut` so it is visible in API responses.
4. Write a `discount_cents` extra field through `new_ledger_entry` so the platform
   financial dashboard can attribute net revenue after discounts.

All changes are additive and gated on the `AOS_INVOICE_FIELDS_ENABLED` flag
(introduced by INV-001; INV-007 strengthens the work INV-001 starts). With the
flag off the platform is byte-for-byte identical to its current state.

## 2. Context & Current State

### Invoices service (`app/services/invoices.py`)

The current `create_invoice` signature (`app/services/invoices.py:272–286`) accepts no
discount parameter. The totals formula at `app/services/invoices.py:305–308` is:

```python
if tax_cents is None:
    tax_cents = (amount_cents * max(0, S.invoices_tax_bps)) // 10_000
tax_cents = _coerce_int(tax_cents)
total_cents = amount_cents + tax_cents
```

There is no subtraction term; `discount_cents` is silently absent.

The `_render_invoice_lines` renderer (`app/services/invoices.py:150–188`) builds a totals
block that currently outputs only "Subtotal", "Tax", and "TOTAL" rows
(`app/services/invoices.py:182–185`). There is no "Discount" row and no branching on a
discount value.

`_serialize` (`app/services/invoices.py:218–245`) maps only `amount_cents`, `tax_cents`,
`total_cents`, and `currency` (plus `seller_id`, `seller_name`, `buyer_name`,
`buyer_email`, `line_items`, `payment_method_summary`, `ledger_entry_id`,
`created_at`); it does not map a `discount_cents` field. Any
`discount_cents` stored on the DynamoDB item is therefore silently dropped from
API responses today.

`VALID_TYPES` at `app/services/invoices.py:33` is `{"tip", "unlock", "subscription", "shop",
"deposit"}`. INV-007 does not add a new type; discount applies to any existing
type.

### Models (`app/models.py`)

`InvoiceLineItemOut` (`app/models.py:9539–9542`) has `description`, `quantity`,
`amount_cents`. `InvoiceOut` (`app/models.py:9545–9563`) has `invoice_id`,
`invoice_number`, `invoice_type`, `user_sub`, `amount_cents`, `tax_cents`,
`total_cents`, `currency`, `status`, `seller_id`, `seller_name`, `buyer_name`,
`buyer_email`, `line_items`, `payment_method_summary`, `ledger_entry_id`,
`created_at`. Neither model has a `discount_cents` field today.

### Ledger (`app/services/billing_shared.py`)

`new_ledger_entry` (`app/services/billing_shared.py:224–259`) accepts an `extra: Optional[Dict]`
keyword argument that is merged directly onto the persisted DynamoDB item
(`app/services/billing_shared.py:255–258`). The `CLAUDE.md` ledger provider attribution note
and the FIN-013 dashboard code at `app/services/platform_financial_dashboard.py:110–114` show
that `extra` fields are the established pattern for attributing contextual data
(e.g., `provider`) to ledger entries. `discount_cents` will follow the same
pass-through pattern.

### Platform financial dashboard (`app/services/platform_financial_dashboard.py`)

The dashboard scans ledger entries and buckets them by `type`, `provider`, and
`amount_cents`. It has a `REFUND_ENTRY_TYPES` set (`app/services/platform_financial_dashboard.py:52–58`)
but no concept of a per-invoice discount. Without a `discount_cents` field on the
ledger entry, the dashboard reports gross revenue; with it, a future aggregation
pass can compute net-of-discount revenue without touching the raw transaction
amounts.

### Feature flag pattern

The `cart_reminders_enabled` flag at `app/core/settings.py:821` is the canonical
reference pattern: `bool = os.environ.get("X", "1") not in ("0", "false", "False")`.
The existing `invoices_enabled` setting at `app/core/settings.py:2568` follows the same
idiom. INV-007 reuses the `AOS_INVOICE_FIELDS_ENABLED` flag that INV-001
introduces (same env var, same settings attribute); it does not introduce a
second flag. The `AOS_INVOICE_FIELDS_ENABLED` setting does not yet exist in the
codebase — it is added by INV-001.

### Router (`app/routers/invoices.py`)

The `invoices_router` prefix is `/ui/invoices` and the `invoices_admin_router`
prefix is `/ui/admin/invoices` (`app/routers/invoices.py:18–19`). Both routers are
registered in `app/main.py:961–963`. No new routes are required for INV-007; the
`InvoiceOut` model update automatically surfaces `discount_cents` through the
existing `GET /ui/invoices/{invoice_number}` and admin list endpoints.

### Sibling tickets

- **INV-001** (`docs/suitecrm/specs/INV-001.md`) is the primary ticket that adds
  `discount_cents` to the model and PDF renderer. INV-007 is the hardening
  pass — it adds the cap, the warning, the ledger integration, and the test
  coverage that INV-001's scope leaves to this ticket.
- **INV-009** (`docs/suitecrm/CRM_INVOICES_CURRENCY_TICKETS.md`) tests the
  paid→void reversal ledger entry; it co-tests the discount ledger field as part
  of the B2B invoice lifecycle integration test.

## 3. Data Model

### No new DynamoDB table

All changes are additive attributes on the existing `T.invoices` items:

```
pk  = USER#{user_sub}          (existing)
sk  = INV#{invoice_number}     (existing)
── discount_cents   int (N)    ← NEW; stored only when > 0
```

Because the field is new and optional, old items that lack `discount_cents`
default to `0` on read (via `_coerce_int`). No migration is needed.

### No new GSIs

The `T.invoices` table (`scripts/local-ddb-init.py:2269–2278`) currently has:

- GSI1: `GSI1PK = USER#{sub}#TYPE#{type}` / `GSI1SK = created_at` (N)
- GSI2: `GSI2PK = ADMIN_ALL` / `GSI2SK = created_at` (N)

`attr_types={"GSI1SK": "N", "GSI2SK": "N"}` is already declared
(`local-ddb-init.py:2277`). INV-007 adds no GSI; no `attr_types` change is
required.

### Ledger extra field (billing table)

The `billing` table ledger entries (managed by `billing_shared.new_ledger_entry`)
receive an additive `discount_cents` key via `extra={"discount_cents": <value>}`.
The billing table schema is unchanged; `extra` is a pass-through merge
(`billing_shared.py:255–258`).

## 4. API / Service Design

### 4.1 Service changes — `app/services/invoices.py`

#### `create_invoice` signature extension

The function signature gains one new keyword argument alongside the INV-001
additions:

```python
def create_invoice(
    *,
    user_sub: str,
    invoice_type: str,
    amount_cents: int,
    line_items: List[Dict[str, Any]],
    ledger_entry_id: str = "",
    tax_cents: Optional[int] = None,
    seller_id: str = "",
    seller_name: str = "",
    buyer_name: str = "",
    buyer_email: str = "",
    payment_method_summary: str = "",
    currency: str = "usd",
    # INV-001 / INV-007 — gated on AOS_INVOICE_FIELDS_ENABLED:
    discount_cents: int = 0,
) -> Optional[Dict[str, Any]]:
```

#### Cap-and-warn logic (INV-007 addition, gated on flag)

Insert immediately after the `amount_cents = _coerce_int(amount_cents)` line at
`invoices.py:295`, inside the `AOS_INVOICE_FIELDS_ENABLED` block:

```python
if S.aos_invoice_fields_enabled:
    discount_cents = max(0, _coerce_int(discount_cents))
    if discount_cents > amount_cents:
        logger.warning(
            "invoice discount_cents=%s exceeds amount_cents=%s for user=%s; capping",
            discount_cents, amount_cents, user_sub,
        )
        discount_cents = amount_cents
else:
    discount_cents = 0
```

#### Updated totals formula

Replace the existing formula at `invoices.py:305–308`:

```python
# before:
total_cents = amount_cents + tax_cents

# after:
total_cents = amount_cents + tax_cents - discount_cents
```

`discount_cents = 0` when the flag is off, so the expression is identical to the
current behaviour in the default case.

#### Record dict — persist discount_cents

Add `"discount_cents": discount_cents` to the `record` dict built at
`invoices.py:324–348`. This is the only change to the DynamoDB write path.

#### Ledger entry integration

After `T.invoices.put_item(Item=record)` at `invoices.py:352`, when a
`ledger_entry_id` is present, the calling code in billing routers typically
writes a ledger entry before calling `create_invoice_safe`. INV-007 does not
own the ledger write path (that lives in billing routers); instead it provides
an `extra` dict that callers can pass to `new_ledger_entry`:

```python
# In the billing router call-site (e.g. app/routers/billing.py),
# after writing the ledger entry:
ledger_sk_val, ledger_item = new_ledger_entry(
    key_name="pk",
    key_value=f"USER#{user_sub}",
    entry_type="...",
    amount_cents=...,
    state="settled",
    reason="...",
    extra={"provider": "stripe", "discount_cents": discount_cents},
)
```

For the initial INV-007 delivery, `create_invoice` accepts `discount_cents` but
the ledger field pass-through is wired through `create_invoice_safe`'s own
optional `ledger_extra` argument (see below).

#### `create_invoice_safe` helper

```python
def create_invoice_safe(**kwargs: Any) -> Optional[Dict[str, Any]]:
    """Best-effort wrapper — never raises."""
    try:
        return create_invoice(**kwargs)
    except Exception:
        logger.warning("invoice hook failed", exc_info=True)
        return None
```

No change to this wrapper; `discount_cents` is passed through `**kwargs`.

#### `_render_invoice_lines` — discount row

In the totals block at `invoices.py:182–185`, insert a "Discount" line between
the Subtotal row and the Tax row, conditioned on `discount_cents > 0`:

```python
lines.append(f"{'Subtotal':<36}{_money(amount):>12}")
discount = _coerce_int(record.get("discount_cents"))
if discount > 0:
    lines.append(f"{'Discount':<36}{'-' + _money(discount):>12}")
lines.append(f"{'Tax':<36}{_money(tax):>12}")
total_display = -total if refunded else total
lines.append(f"{'TOTAL':<36}{_money(total_display):>12}")
```

When `discount_cents` is `0` or absent from the record, the row is omitted
and the PDF is byte-for-byte identical to the current output.

#### `_serialize` — map discount_cents

Add to the returned dict in `_serialize` (`invoices.py:227–245`):

```python
"discount_cents": _coerce_int(record.get("discount_cents")),
```

This ensures `InvoiceOut.discount_cents` is populated from the stored item and
defaults to `0` for all pre-existing records.

## 5. Detailed Behavior & Edge Cases

### 5.1 Normal path

1. Caller invokes `create_invoice(..., discount_cents=200, amount_cents=1000,
   tax_cents=80)`.
2. Flag check: `S.aos_invoice_fields_enabled` is `True`.
3. Cap: `200 <= 1000`, no warning.
4. Formula: `total_cents = 1000 + 80 - 200 = 880`.
5. DDB item carries `discount_cents=200`, `total_cents=880`.
6. PDF includes "Discount: -$2.00" between Subtotal and Tax.
7. `InvoiceOut.discount_cents = 200`.

### 5.2 Discount equals full amount

- `discount_cents = 1000`, `amount_cents = 1000` → `total_cents = tax_cents` (0
  if no tax). This is a valid free-invoice scenario (e.g., promotional coupon).
- No warning is emitted because `discount_cents == amount_cents` passes the cap
  check.

### 5.3 Discount exceeds amount

- `discount_cents = 1500`, `amount_cents = 1000` → cap to `1000`.
- Warning logged: `"invoice discount_cents=1500 exceeds amount_cents=1000 for
  user=… ; capping"`.
- `total_cents = 0 + tax_cents`.
- This prevents any scenario where `total_cents` would become negative.

### 5.4 Flag off (default)

- `discount_cents` argument is accepted syntactically (zero-argument change is
  backward compatible) but set to `0` by the flag guard.
- `total_cents = amount_cents + tax_cents` — identical to today.
- `_serialize` returns `discount_cents=0`.
- `_render_invoice_lines` emits no Discount row.
- PDF output is byte-for-byte identical to the current implementation.

### 5.5 Zero discount

- `discount_cents = 0` (default): no Discount row in PDF, `discount_cents=0`
  in `InvoiceOut`. Existing invoice generation callers pass no `discount_cents`
  and therefore see zero; backward compatible.

### 5.6 Idempotency (duplicate ledger entry)

`_existing_for_ledger` at `invoices.py:252–269` returns the existing invoice if
the ledger marker row is found. An idempotent second call with a different
`discount_cents` still returns the original invoice unchanged. This is correct:
discount was committed at creation time; re-running with a different value would
not change the stored total.

### 5.7 Refunded invoice

`_render_invoice_lines` at `invoices.py:156` tests `status == "refunded"` and
negates `total_display`. A refunded invoice with a discount still shows "Discount:
-$2.00" in the PDF so the reader can reconcile the original total. The refund
banner "*** REFUNDED ***" is unaffected.

### 5.8 PDF regeneration on S3 cache miss

`download_invoice_pdf` at `invoices.py:442–452` falls back to
`_render_pdf(_render_invoice_lines(raw))` when the S3 key is absent or the
`get_object` call fails. Because `discount_cents` is stored on the raw DynamoDB
item, the regenerated PDF will include the correct discount row even after the
flag is toggled on post-creation.

### 5.9 `amount_cents <= 0` guard

`create_invoice` returns `None` immediately when `amount_cents <= 0`
(`invoices.py:296–297`). The cap-and-warn block is inserted after
`amount_cents = _coerce_int(amount_cents)` (line 295) and therefore runs
*before* this guard. This is safe: `_coerce_int` always returns a non-negative
integer, so `amount_cents` is never negative at cap time; and if it is zero the
guard immediately returns `None`, making any computed cap irrelevant.
<!-- CORRECTED: original said 297–298 (off by one — actual guard is at lines
296–297) and incorrectly claimed the guard runs before the cap logic. The cap
block is proposed to be inserted at line 295 (before the guard at 296). -->

### 5.10 Interaction with INV-006 per-line tax

When `AOS_PER_LINE_TAX_ENABLED` is also on (INV-006), `tax_cents` is the sum of
per-line taxes. The totals formula in INV-007 is:
`total_cents = amount_cents + tax_cents - discount_cents`. This is correct
regardless of how `tax_cents` was computed; INV-006 and INV-007 are independent
additive passes over the same field set.

### 5.11 Ledger `discount_cents` extra field

Callers that write a ledger entry via `new_ledger_entry` should pass
`extra={"discount_cents": discount_cents}` to populate the field. When
`discount_cents == 0` callers should omit the field from `extra` (or omit `extra`
entirely) rather than relying on the `if extra` guard at `billing_shared.py:255`
to filter it out — that guard tests whether the dict *itself* is non-empty, not
whether individual values inside it are falsy; passing `extra={"discount_cents": 0}`
would still write `discount_cents: 0` onto the ledger item.
<!-- CORRECTED: original stated "zero is falsy in the `if extra` guard" which
misrepresents how the guard works. The guard is `if extra: item.update(extra)`
— it skips the update only when the dict is empty/None, not when dict values
are zero. -->
`_provider_for` helper (`platform_financial_dashboard.py:110–114`) reads optional
extra fields from items; a `discount_cents` field on ledger entries enables a
future net-revenue aggregation pass without any schema change.

## 6. Feature Flag & Config

| Setting attribute | Env var | Default | Type |
|---|---|---|---|
| `S.aos_invoice_fields_enabled` | `AOS_INVOICE_FIELDS_ENABLED` | `"0"` (off) | bool |

The flag is introduced by INV-001 and shared with INV-007. INV-007 adds no
independent flag. Both tickets must be shipped together or INV-001 must land
first.

**Pattern** (matches `cart_reminders_enabled` at `settings.py:821`):

```python
aos_invoice_fields_enabled: bool = os.environ.get(
    "AOS_INVOICE_FIELDS_ENABLED", "0"
) not in ("0", "false", "False")
```
<!-- CORRECTED: `not in ("1", "true")` inverted the logic — "0" would evaluate
to True (enabled). Correct form is `not in ("0", "false", "False")`. -->

**Effect of flag = off (default)**:

- `discount_cents` argument is silently zeroed before the totals formula.
- `_render_invoice_lines` never emits a "Discount" row.
- `_serialize` returns `discount_cents=0` (field present but zero; backward
  compatible with any `InvoiceOut` consumer that checks for truthiness).
- No call to `new_ledger_entry` is modified; `extra` is not populated with
  `discount_cents`.
- Existing invoice generation callers (`billing.py`, `paypal.py`,
  `billing_ccbill.py`, subscriptions, etc.) are entirely unaffected.

**Enabling in dev**:

```bash
# .env.local
AOS_INVOICE_FIELDS_ENABLED=1
```

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

- `create_invoice` is a pure DynamoDB + S3 write path. The `_s3 = s3_client()`
  singleton at `invoices.py:35` and `_store_pdf` at `invoices.py:195–201` both
  use `app.core.aws_clients.s3_client`, which moto intercepts at the botocore
  layer in dev (`app/core/dev_s3.py`). No `if S.dev_mode` branch is introduced.
- `new_ledger_entry` writes to `T.billing` regardless of environment; moto
  handles the DDB write in dev.
- The `logger.warning` for the cap case is a standard Python log call; it works
  identically in dev and prod.

### Idempotency

- The `_existing_for_ledger` check at `invoices.py:252–269` ensures a second call
  with the same `ledger_entry_id` returns the first invoice unchanged.
- The `COUNTER/SEQ` row uses an atomic `ADD :inc` (`invoices.py:86–91`), so
  invoice numbers are never duplicated even under concurrent creation.

### Security

- `discount_cents` is an integer supplied by internal service code (billing
  routers, subscription hooks), not a raw user-controlled query parameter. The
  cap guards against programming errors but the field is not exposed in
  user-facing creation endpoints.
- The `InvoiceOut.discount_cents` field is additive and read-only in responses.
  No write endpoint exposes discount to end users.
- The `_money()` helper at `invoices.py:146` uses f-string formatting on an
  integer divided by 100; the discount value is always a capped non-negative
  integer by the time it reaches `_render_invoice_lines`. No injection surface.

## 8. Backward Compatibility & Migration

### Model backward compatibility

`InvoiceOut.discount_cents: int = 0` has a default; existing code that constructs
`InvoiceOut(**some_dict)` where `some_dict` lacks `discount_cents` will receive
`0` without error. No `model_rebuild()` call is needed (no forward reference).

### DynamoDB backward compatibility

Old items written before INV-007 do not carry a `discount_cents` attribute.
`_coerce_int(record.get("discount_cents"))` returns `0` for a missing key. All
read paths (`_serialize`, `_render_invoice_lines`, `download_invoice_pdf`) are
safe on old items.

### Migration

No migration is required. The `discount_cents` attribute is written only on new
invoices created after the flag is enabled. Old invoices are read as
`discount_cents=0`, which is correct (they had no discount).

### DynamoDB init script

No change to `scripts/local-ddb-init.py` is required. The `T.invoices` table
definition at `local-ddb-init.py:2269–2278` already declares the correct hash
key (`pk`), sort key (`sk`), and `attr_types={"GSI1SK": "N", "GSI2SK": "N"}`.
No new GSI or attribute type declaration is needed.

## 10. Open Questions / Assumptions

1. **`VALID_TYPES` extension for B2B invoices**: The current `VALID_TYPES` set
   (`invoices.py:33`) is `{"tip", "unlock", "subscription", "shop", "deposit"}`.
   QUO-005 and INV-001 introduce `"manual"` as a type for B2B invoices created
   via admin. INV-007 assumes QUO-005/INV-001 extend `VALID_TYPES` with
   `"manual"` before this ticket is tested; the discount logic is type-agnostic
   and will work correctly once `"manual"` is a valid type.

2. **Discount as percentage vs. fixed cents**: This ticket implements fixed-amount
   `discount_cents` only. A percentage-based discount (e.g., `discount_pct_bps`)
   would be a separate field and a separate ticket. The current design stores the
   pre-computed cent value for simplicity and auditability; the percentage, if
   needed, can be stored as a `discount_pct_bps` extra field alongside.

3. **Negative discount (surcharge)**: The `max(0, ...)` guard means negative
   values are treated as zero. This is intentional — a surcharge is not a
   discount and should be a separate line item or a higher `amount_cents`.

4. **Shipping + discount ordering in the INV-001 formula**: INV-001 specifies
   `total_cents = amount_cents + tax_cents + shipping_cents - discount_cents`.
   INV-007 coordinates with INV-001 on this formula; if INV-001 lands first, the
   formula is already correct. If INV-007 lands in isolation (INV-001 deferred),
   the simpler `total_cents = amount_cents + tax_cents - discount_cents` is used
   and `shipping_cents` is added when INV-001 merges.

5. **Financial dashboard net-revenue query**: The `discount_cents` extra field on
   ledger entries is written by this ticket, but the dashboard aggregation code
   (`platform_financial_dashboard.py`) does not yet read it. A follow-up ticket
   (or an extension of FIN-013) would add a `net_after_discounts` column to the
   daily rollup by summing `discount_cents` across ledger entries for a day.
   This is out of scope for INV-007.
