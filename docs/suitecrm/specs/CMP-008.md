# CMP-008 — Email personalization merge tags end-to-end

**Type:** Feature  **Priority:** P1  **Estimate:** 1d  
**Area:** Campaigns & Email Marketing  
**Source:** `docs/suitecrm/CRM_CAMPAIGNS_EXTRA_TICKETS.md` § CMP-008

---

## 1. Summary & Goal

CMP-002 introduced the `{{merge_field}}` substitution engine for HTML email templates. CMP-003 added open-tracking pixels. CMP-004 injected `{{unsubscribe_url}}`. CMP-005 injected `{{survey_url}}`. CMP-007 added per-variant subject overrides. Each of these tickets wired merge-vars independently inside its own call site, leaving the merge-var assembly scattered across `_build_message_body`, `_try_send_one`, and the HTML template renderer.

CMP-008 consolidates that scattered logic into a single named helper — `_build_merge_vars(party_id, campaign_id)` — callable from both the live send path and a new preview endpoint. It also ensures that all five standard SuiteCRM merge tags (`{{first_name}}`, `{{last_name}}`, `{{email}}`, `{{company}}`, `{{phone}}`) are populated from the recipient's platform profile on every send path: plain-text body fallback, HTML template body, subject line, and A/B variant `subject_override`.

The only new user-facing surface is a single preview endpoint:

```
POST /ui/marketing/campaigns/{id}/preview-email
```

which renders the fully substituted email for a chosen sample recipient — subject, plain-text body, and HTML body — without writing to DynamoDB or sending any message.

Everything is additive, default-off behind `S.marketing_campaigns_enabled`. With the flag off the platform is byte-for-byte unchanged.

## 2. Context & Current State

### Substitution engine (live)

`app/services/notification_templates.py:23` defines:

```python
_VAR_RE = re.compile(r"\{\{\s*([a-zA-Z0-9_]+)\s*\}\}")
```

`app/services/notification_templates.py:245` defines:

```python
def _render(text: Optional[str], sample_vars: Dict[str, str]) -> Tuple[Optional[str], List[str]]:
    """Render a single template string. Returns (rendered, missing_vars)."""
```

`_render` applies `_VAR_RE.sub(repl, text)`. When a placeholder is present in `text` but **absent from `sample_vars` or present with an empty-string value** (`sample_vars[var] == ""`), it leaves `{{var}}` intact and appends `var` to `missing_vars` (lines 251–257; condition at line 253: `if var in sample_vars and sample_vars[var] != ""`). This existing behavior — leave unresolved placeholders in place rather than crash — is the correct contract for the merge-tag feature. Note: empty-string values are treated identically to missing keys and land in `merge_vars_missing`.

### Profile data source (live)

`app/services/profile.get_profile(user_sub)` at `profile.py:262` performs a point lookup on `T.profile` (`Key={"user_sub": user_sub}`) and returns `empty_profile()` on miss. `empty_profile()` at `profile.py:241` defines these keys relevant to merge tags:

| Profile key | CMP-008 merge tag |
|---|---|
| `first_name` | `{{first_name}}` |
| `last_name` | `{{last_name}}` |
| `displayed_email` | `{{email}}` |
| `displayed_telephone_number` | `{{phone}}` |

There is no `company` field in the platform profile model (confirmed: `profile.py:16–33` lists all `PROFILE_FIELDS`; `company` is absent). The `{{company}}` merge tag is therefore populated from the web-lead capture record (when the recipient originated from CMP-006's `web_lead_captures` table) or left as `{{company}}` (unresolved, per `_render` contract) for platform users who have no company attribute.

### Email delivery (live)

`app/services/alerts.send_alert_email(to_emails, subject, body_text)` at `alerts.py:459` accepts only a plain-text body. CMP-002's spec (§4, `docs/suitecrm/specs/CMP-002.md`) extends the signature to:

```python
def send_alert_email(
    to_emails: List[str],
    subject: str,
    body_text: str,
    *,
    body_html: Optional[str] = None,

```

CMP-008 depends on that extension being in place (CMP-002 prerequisite). When `body_html` is provided, the SES `Message["Body"]` dict includes both `Text` and `Html` entries. In dev mode the HTML body is appended to the dev email log at `S.dev_email_log` (`alerts.py:462–468`).

### HTML wrapper (live)

`app/services/alert_email_templates._wrap_html(title, body_html)` at `alert_email_templates.py:16` wraps arbitrary HTML in a minimal responsive email shell. CMP-002 uses this to wrap the campaign template body before passing it to SES. CMP-008 inherits this by going through CMP-002's `render_template` → `_wrap_html` chain.

### Current merge-var assembly (scattered, planned)

As specified in MKT-009 (`docs/ofbiz/specs/MKT-009.md:287–320`), `_try_send_one` currently assembles the recipient email by calling `get_profile(party_id)` once into a local `profile` variable, then extracting `email = profile.get("email") or profile.get("displayed_email")` (MKT-009 §5 step 5 — one call, not two). There is no consolidated `_build_merge_vars` helper. Each of CMP-002 through CMP-007 adds its own ad-hoc vars into the growing dict passed to `render_template`. This works but makes the merge-var contract implicit; CMP-008 makes it explicit.

## 3. Data Model

CMP-008 introduces **no new DynamoDB tables and no new GSIs**. All state lives in tables defined by upstream specs.

### Tables touched (reads only at preview time)

| Table | Access | Purpose |
|---|---|---|
| `MarketingCampaigns` (MKT-002) | `get_item(pk=OWNER#{owner_id}, sk=MKTCAMP#{campaign_id})` | Fetch campaign record: `email_template_id`, `questionnaire_slug`, `variants_json`, `tracking_code`, `promo_code_id`. Key format confirmed by `docs/ofbiz/specs/MKT-004.md:336`. |
| `MarketingEmailTemplates` (CMP-002) | `get_item(pk=TMPL#{id}, sk=META)` | Fetch the HTML template when `email_template_id` is set. |

| `cart_reminder_config` (existing, CMP-004) | Read via `generate_unsubscribe_url` | Mints the HMAC token; writes the `UNSUB#CONSUMED#` row only on redemption, not preview. At preview time, `generate_unsubscribe_url` is called but the URL is never redeemed — the signed token will expire naturally. |

### No new DDB writes on preview

The preview endpoint is read-only. It calls `get_profile`, `get_template`, and `generate_unsubscribe_url` (minting a token is write-free; consumption is what writes). No campaign state is mutated and no email is dispatched. `audit_event` (best-effort, one DDB put to `T.alerts`) is the only write.

## 4. API / Service Design

### 4.1 New service helper: `_build_merge_vars`

**Location:** `app/services/marketing_campaigns.py` (MKT-009 module).

**Signature:**

```python
def _build_merge_vars(
    party_id: str,
    campaign_id: str,
    *,
    campaign: dict,
) -> dict[str, str]:
    """Resolve standard merge tags for one recipient.

    Calls get_profile(party_id) once. Falls back gracefully when the profile
    lookup raises (returns empty strings for all profile-sourced tags).
    The returned dict is passed directly to _render() and render_template().

    Keys guaranteed to be present (value may be empty string):
        first_name, last_name, email, company, phone,
        unsubscribe_url, platform_name, survey_url (when questionnaire linked).

    Never raises — any profile / token / questionnaire lookup failure
    produces empty strings for the affected tags, leaving {{var}} intact
    per the _render() contract.
    """
```

**Resolution logic:**

```python
from app.services.profile import get_profile
from app.services.marketing_unsubscribe import generate_unsubscribe_url  # CMP-004
from app.core.settings import S

def _build_merge_vars(party_id: str, campaign_id: str, *, campaign: dict) -> dict[str, str]:
    # 1. Profile lookup — fail-open
    try:
        profile = get_profile(party_id)
    except Exception:
        profile = {}

    # 2. Standard identity tags
    vars: dict[str, str] = {
        "first_name": str(profile.get("first_name") or ""),
        "last_name": str(profile.get("last_name") or ""),
        "email": str(profile.get("displayed_email") or profile.get("email") or ""),
        "phone": str(profile.get("displayed_telephone_number") or ""),
        "company": str(profile.get("company") or ""),  # empty for platform users
        "platform_name": str(getattr(S, "platform_name", "") or ""),
    }

    # 3. Unsubscribe URL (CMP-004) — fail-open
    try:
        vars["unsubscribe_url"] = generate_unsubscribe_url(party_id, campaign_id)
    except Exception:
        vars["unsubscribe_url"] = ""

    # 4. Survey URL (CMP-005) — present only when questionnaire linked
    # campaign["questionnaire_url"] is NOT stored in DDB — it is computed at API read time.
    # The raw DDB item stores "questionnaire_slug"; build the URL the same way get_campaign does
    # (per docs/suitecrm/specs/CMP-005.md:185, 197-199).
    questionnaire_slug = campaign.get("questionnaire_slug") or ""
    questionnaire_url = (
        f"{S.public_base_url}/questionnaires/published/{questionnaire_slug}"
        if questionnaire_slug
        else ""
    )
    vars["survey_url"] = questionnaire_url

    return vars
```

**Callers after CMP-008:**

- `_try_send_one` in `marketing_campaigns.py` (MKT-009): replaces inline profile lookup + scattered var dict construction.
- `preview_campaign_email` (new function below): called at preview time with `sample_party_id`.

### 4.2 New service function: `preview_campaign_email`

**Location:** `app/services/marketing_campaigns.py`

**Signature:**

```python
def preview_campaign_email(
    campaign_id: str,
    owner_id: str,
    *,
    sample_party_id: Optional[str] = None,
    variant_id: Optional[str] = None,
) -> dict:
    """Render the fully substituted email for one campaign + recipient.

    Returns a dict matching CampaignPreviewOut. Raises HTTPException(404)
    if campaign not found or caller does not own it. Never sends email or
    writes campaign state.
    """
```

**Logic:**

1. Fetch campaign item from `T.marketing_campaigns` using `pk=OWNER#{owner_id}`, `sk=MKTCAMP#{campaign_id}` (the marketing campaign key format per `docs/ofbiz/specs/MKT-004.md:336`, not `CAMPAIGN#`/`META`). On miss → `HTTPException(404)`. Ownership is implicitly enforced by the `OWNER#{owner_id}` partition key — no separate ownership check is needed for the primary access pattern; however, for cross-owner lookups (e.g. `get_campaign_by_id` via GSI `ByCampaignId`), an explicit `campaign["owner_id"] != owner_id` check → `HTTPException(403)` is required.
2. Resolve `effective_party_id = sample_party_id or owner_id`.
3. Call `_build_merge_vars(effective_party_id, campaign_id, campaign=campaign)` → `merge_vars`.
4. Resolve subject and body:
   - If `variant_id` is set, deserialize variants from the raw DDB item: `variants = json.loads(campaign.get("variants_json") or "null") or []` (CMP-007 stores as a JSON string under `variants_json`, not a native list under `variants` — see `docs/suitecrm/specs/CMP-007.md:222`). Locate the matching variant by `variant["variant_id"] == variant_id`. Use variant's `email_template_id` (override) or campaign-level `email_template_id`. Use variant's `subject_override` as the subject template if set; otherwise fall back to `campaign["name"]`.
   - If no variant, use campaign-level `email_template_id` and `campaign["name"]` as subject.
5. Render subject: call `_render(subject_template, merge_vars)` → `(rendered_subject, subject_missing)`.
6. Render plain-text body: call `_build_message_body(campaign, tracking_url=..., promo_code_str=..., merge_vars=merge_vars)` → `(_, body_text)`. Collect missing vars from the body render.
7. Render HTML body (when `email_template_id` is set):
   - Fetch template via `get_template(owner_id, email_template_id)` (CMP-002 service).
   - Call `render_template(template_item, merge_vars)` → `(_, rendered_html)`.
   - Collect missing vars from the HTML render.
8. Consolidate `merge_vars_used` (vars whose value was non-empty and was actually substituted) and `merge_vars_missing` (the union of all missing-var lists from all three renders, deduplicated).
9. Emit `audit_event("marketing.campaign.preview_email", owner_id, campaign_id=campaign_id, sample_party_id=effective_party_id)` — best-effort, `try/except`.
10. Return the dict.

**`_build_message_body` signature extension (additive):**

```python
def _build_message_body(
    campaign: dict,
    *,
    tracking_url: Optional[str],
    promo_code_str: Optional[str],
    merge_vars: Optional[dict[str, str]] = None,   # NEW — default None = no substitution
) -> tuple[str, str]:
```

Note: `campaign.get("questionnaire_slug")` should be read directly inside `_build_message_body` to construct `survey_url` for the plain-text body (matching the CMP-005 pattern at `docs/suitecrm/specs/CMP-005.md:197–201`). The raw DDB item never contains `questionnaire_url`.

When `merge_vars` is provided, apply `_render(body_text, merge_vars)` before returning. When `None`, the existing behavior is preserved (existing MKT-009 callers pass no `merge_vars` until CMP-008's refactor lands).

### 4.3 New Pydantic models

**Location:** `app/models.py` — additive block inside the MKT-003 marketing section (after `MarketingCampaignOut`).

```python
class CampaignPreviewIn(BaseModel):

    )

        description="Which A/B variant to render (CMP-007). "
                    "None = first/only variant or no-variant campaign.",
    )

class CampaignPreviewOut(BaseModel):
    subject: str
    body_text: str
    body_html: Optional[str] = None

```

Both models are additive. No existing model is modified. The `merge_vars_used` list contains the names of placeholders that were present in any template string AND had a non-empty resolved value. `merge_vars_missing` contains placeholder names that were present in any template string but had no resolved value (the `{{var}}` was left intact by `_render`).

## 5. Detailed Behavior & Edge Cases

### 5.1 Merge-var resolution priority

`_build_merge_vars` is the single point where merge vars are assembled. The resolution order is:

1. **Profile-sourced** (`first_name`, `last_name`, `email`, `phone`): from `get_profile(party_id)` at `profile.py:262`. If the profile row is absent `empty_profile()` returns `None` for all keys; each is coerced to `""`.
2. **Platform constant** (`platform_name`): from `S.platform_name` if that setting exists, else `""` (via `getattr(S, "platform_name", "")`). **The setting does not exist in the live codebase and is NOT defined by any MKT or CMP spec** (grep across `docs/ofbiz/specs/MKT-*.md` returns nothing; `app/core/settings.py` has no such attribute). Sibling specs diverge here: CMP-002/CMP-004 leave it as an open branding question, and CMP-006 introduced its own `web_to_lead_platform_name` setting instead. Until the ownership of a platform brand-name setting is decided (see Verification Log row 22 — ESCALATED), the `getattr(..., "")` fallback keeps `{{platform_name}}` rendering as an empty string, which is safe but unbranded.
3. **Campaign-derived** (`unsubscribe_url`, `survey_url`): from CMP-004 token minting and CMP-005 questionnaire URL resolution. `survey_url` is built from `campaign.get("questionnaire_slug")` (the field stored in the DDB item); `campaign.get("questionnaire_url")` is NOT stored in DDB and must not be used.
4. **Not profile-sourced** (`company`): populated from `profile.get("company", "")`. Since `company` is absent from `PROFILE_FIELDS` (`profile.py:16–33`), it will always be `""` for platform users; for web-lead recipients (CMP-006) whose record is in `T.web_lead_captures`, the caller can pass an augmented `merge_vars` dict with `company` pre-filled before calling `render_template`. See §5.4.

### 5.2 Missing merge tags — no crash contract

`_render(text, sample_vars)` at `notification_templates.py:245` leaves `{{var}}` in place when `var` is absent from `sample_vars` (lines 253–257). CMP-008 relies on this contract for all render calls. The preview endpoint surfaces the `merge_vars_missing` list so the campaign author can see exactly which placeholders have no resolved value for a given recipient before sending.

### 5.3 Subject-line personalization

Before CMP-008, `_build_message_body` returns `(subject, body_text)` where `subject` is always `campaign["name"]` — a static string. CMP-008 changes the subject to also pass through `_render`:

```python
subject_template = (
    variant.get("subject_override")   # CMP-007 variant override (highest priority)
    or campaign.get("subject_template")  # campaign-level subject template (new field)
    or campaign.get("name", "")          # legacy fallback
)
rendered_subject, subject_missing = _render(subject_template, merge_vars)
```

A new additive field `subject_template: Optional[str] = None` (max 500 chars) is added to `MarketingCampaignCreateIn` / `MarketingCampaignUpdateIn` / `MarketingCampaignOut` in `app/models.py`. Campaigns without `subject_template` continue to use `name` as the subject (no behavior change for existing records).

### 5.4 Web-lead recipients (CMP-006)

Recipients sourced from `T.web_lead_captures` (CMP-006) are identified by a `capture_id` rather than a platform `user_sub`. For these recipients:

- `get_profile(capture_id)` returns `empty_profile()` (no platform profile exists).
- `_build_merge_vars` is extended to accept an optional `extra_vars: Optional[dict[str, str]] = None` parameter. The caller (`_try_send_one`) passes `extra_vars={"first_name": capture["first_name"], "last_name": capture["last_name"], "company": capture.get("company", ""), "email": capture["email"], "phone": capture.get("phone", "")}` when the recipient's `source` is `"web_lead"`. These values are merged into the dict after the profile lookup, overriding empty profile keys.
- The preview endpoint does not need to handle web-lead recipients because `sample_party_id` is restricted to platform `user_sub` values (the endpoint is authenticated with a session cookie — only platform users can call it).

### 5.5 Variant subject personalization (CMP-007)

When `variant_id` is provided to `preview_campaign_email`:

1. Locate the variant dict in `campaign["variants"]` by matching `variant["variant_id"] == variant_id`. On no match → raise `HTTPException(422, "variant not found")`.
2. Use `variant["subject_override"]` as the subject template (if set). Pass through `_render(subject_override, merge_vars)`.
3. Use `variant["email_template_id"]` (if set) for HTML rendering; otherwise use the campaign-level `email_template_id`.

On the live send path, `_try_send_one` already receives a resolved `(subject, body_text)` pair built by the caller; after CMP-008 it instead receives `merge_vars` and calls `_render`/`_build_message_body` internally. This is a refactor of `_try_send_one`'s internal structure (the external signature of `send_campaign` is unchanged).

### 5.6 Plain-text-only campaigns (no HTML template)

When `campaign.get("email_template_id")` is `None`:

- `_build_merge_vars` is still called → `merge_vars` dict is assembled.
- `_build_message_body(..., merge_vars=merge_vars)` renders the plain-text body with substitution.
- `body_html` in `CampaignPreviewOut` is `None`.
- `merge_vars_missing` contains any unresolved placeholders from the plain-text template.
- `send_alert_email` is called without `body_html` (falls back to the existing text-only SES path).

### 5.7 Preview idempotency and token side-effects

`generate_unsubscribe_url(party_id, campaign_id)` mints a new signed token on every call. Each preview call therefore mints a new token that is valid for `S.marketing_unsubscribe_ttl_days` days (CMP-004 default 365 days) but is never consumed. Over time, repeated previews produce stale unconsumed tokens. This is acceptable because:

- Token minting is write-free (stateless HMAC).
- Token consumption writes `UNSUB#CONSUMED#{jti}` to `T.cart_reminder_config` only when the `/optout/{token}` endpoint is called.
- Unconsumed tokens never appear in DDB; there is no accumulation of stale rows.
- The preview response includes `unsubscribe_url` so the author can verify the URL structure.

### 5.8 `sample_party_id` not owned by caller

The preview endpoint does not validate that the caller owns or administers `sample_party_id`. Any authenticated user can preview their campaign using any other platform user's profile data. This is acceptable because:

- The endpoint only reads profile data (`first_name`, `last_name`, `displayed_email`, `displayed_telephone_number`). Per `PROFILE_FIELD_VISIBILITY` at `profile.py:82–99`: `first_name` and `last_name` are `"member"` visibility, but `displayed_email` and `displayed_telephone_number` are **`"private"`** visibility — not `"member"` as previously stated. This means the preview endpoint can expose private fields of any platform user to the campaign owner. Whether this is acceptable should be revisited; at minimum the claim that these fields are "non-sensitive" and `"member"` visibility is inaccurate.
- The preview renders the email offline; no email is sent and no data is stored for the sample user.
- Admin users (`role >= ADMIN`) may legitimately preview on behalf of any user; regular users can use it to verify their own profile's merge-tag rendering.

If the sample user's profile is hidden or deleted (`discoverability_status == "deleted"`), `get_profile` returns `empty_profile()` (the function at `profile.py:262` catches missing items and returns the empty dict; it does not call `get_profile_for_requester` which would raise 404 on hidden profiles). The preview simply renders with empty profile values.

## 6. Feature Flag & Config

### Flag

CMP-008 uses **no new feature flag**. It is gated entirely on `S.marketing_campaigns_enabled`, inherited from MKT-002.

All new code paths are guarded by the existing `_require_enabled()` helper (defined in `app/routers/marketing_campaigns.py`, established by MKT-011 — the function name in MKT-011 §4.2 is `_require_enabled()`, not `_require_campaigns_enabled()`, following the pattern at `app/routers/promo_codes.py:40`):

def _require_enabled() -> None:

With `S.marketing_campaigns_enabled = False`:
- `POST /ui/marketing/campaigns/{id}/preview-email` → 404.
- `_build_merge_vars` is never called from the send path (the send path itself is guarded by the same flag at `send_campaign` entry).
- `preview_campaign_email` is never reachable from the router; it can be called directly in tests with the flag on.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

`_build_merge_vars` calls only:
- `get_profile(party_id)` — DDB point lookup, identical in dev (DDB Local port 8001) and prod (real DynamoDB). No `if S.dev_mode` branch.
- `generate_unsubscribe_url(...)` — pure HMAC computation, no AWS calls, no branching.

`preview_campaign_email` calls `get_template` (DDB point lookup) and `render_template` (pure Python substitution). Neither branches on `S.dev_mode`.

The `audit_event` call at `alerts.py:644` writes to `T.alerts` in both dev and prod. In dev mode the alert write goes to DDB Local; in prod it goes to real DynamoDB. Same code path.

No `if S.dev_mode` branches are introduced anywhere in CMP-008.

### Idempotency

The preview endpoint is pure read + optional audit write. Calling it N times:
- Mints N HMAC tokens (stateless, write-free).
- Writes N audit rows (each has a unique `alert_id` derived from `uuid4`).
- Reads the profile row, campaign row, and template row N times.
- Does **not** modify any campaign state.

Idempotency in the send path is unchanged from MKT-009: `_build_merge_vars` is a pure function (same input → same output); the idempotency guarantee of `_try_send_one` (conditional put on `send_id`) is unaffected by refactoring the merge-var dict construction.

### Security

**`sample_party_id` scope**: As discussed in §5.8, the merge-var preview reads member-visibility profile fields only. No private fields (mailing address, birthday) are included in the merge-var dict. `_build_merge_vars` does not call `get_profile_for_requester`; it calls `get_profile` directly, which returns the raw profile dict without audience filtering. To prevent leaking private fields: `_build_merge_vars` copies only the specific keys listed in the merge-tag table (§5.1) — it does not pass the entire profile dict to `_render`.

**HMAC token in preview response**: The `unsubscribe_url` in `CampaignPreviewOut` contains a valid signed token for the `sample_party_id`. If the caller previews using another user's `sample_party_id`, the response contains an unsubscribe URL that would opt out that other user if visited. Risk is low (the other user would have to intentionally visit the URL from the preview page), but callers should treat preview responses as internal/non-shareable. Rate limiting on the preview endpoint (see §5.8 — inherits the platform API rate-limiting middleware) prevents bulk token harvesting.

**No PII in logs**: `audit_event` records `campaign_id` and `sample_party_id` (a user_sub UUID, not a name or email). No profile field values are written to the audit log.

**Flag gate**: The preview endpoint is behind `_require_campaigns_enabled()`. In production, this gate ensures the endpoint is not accessible until the marketing campaigns feature is intentionally enabled.

## 8. Backward Compatibility & Migration

### No DDB schema changes

CMP-008 adds no new DynamoDB tables and no new GSIs. `scripts/local-ddb-init.py` requires no changes.

### Additive Pydantic model changes

`CampaignPreviewIn` and `CampaignPreviewOut` are new models. The additive field `subject_template: Optional[str] = None` on `MarketingCampaignCreateIn` / `MarketingCampaignUpdateIn` / `MarketingCampaignOut` defaults to `None` — existing campaign records without `subject_template` continue to use `name` as the subject (no regression). Existing API clients that do not send `subject_template` are unaffected.

### `_build_message_body` signature extension

The new `merge_vars: Optional[dict[str, str]] = None` keyword parameter defaults to `None`. All existing callers of `_build_message_body` (including the existing MKT-009 `send_campaign` code path before CMP-008's refactor lands) pass no `merge_vars` and continue to receive the pre-substitution plain-text body unchanged. The only behavioral change is that the CMP-008 refactored send path now passes `merge_vars`, enabling substitution.

### `_try_send_one` refactor

After CMP-008, `_try_send_one` calls `_build_merge_vars` instead of inline profile lookups. The external behavior — one alert written, one email sent per eligible recipient — is unchanged. The only observable difference is that `{{first_name}}` etc. are now substituted in the message body for recipients who have filled in their profile. This is the desired improvement.

### Migration

No data migration is needed. No existing campaign records, send logs, or contact list rows require changes. The only on-deploy action is ensuring that `S.marketing_campaigns_enabled` (controlled by the `MARKETING_CAMPAIGNS_ENABLED` env var) is set to `False` in prod (the default) until the full MKT + CMP chain is deployed and smoke-tested.

## 10. Open Questions / Assumptions

1. **`platform_name` setting (ESCALATED — open product/design choice)**: The spec injects `platform_name` into every merge-var dict. The live `app/core/settings.py` has no `platform_name` attribute (confirmed by grep), and — contrary to an earlier assumption — **no MKT or CMP spec defines it** (grep across `docs/ofbiz/specs/MKT-*.md` is empty; MKT-002 only adds `marketing_campaigns_enabled`, not a brand name). The sibling specs do not agree on an owner: CMP-002/CMP-004 treat it as an open branding question and supply a literal default; CMP-006 added its own `web_to_lead_platform_name` setting. This needs a product decision: either (a) add a single shared `S.platform_name`/`S.app_name` setting in a dedicated branding ticket that all marketing specs reference, or (b) standardise on a per-feature setting like CMP-006's. Until then CMP-008 uses the safe `getattr(S, "platform_name", "")` fallback, rendering `{{platform_name}}` as an empty string — functionally safe, but the emails are unbranded.

2. **`subject_template` vs. campaign `name`**: This spec adds `subject_template` as a new optional field. The MKT-003 spec (`docs/ofbiz/specs/MKT-003.md`) does not include this field. CMP-008 adds it additively. If MKT-003's implementation has already shipped without `subject_template`, no migration is required (the field defaults to `None` and `name` is used as the fallback).

3. **Web-lead recipient's `user_sub`**: CMP-006's `capture_id` is not a platform `user_sub`; `get_profile(capture_id)` returns `empty_profile()`. This spec introduces the `extra_vars` parameter to `_build_merge_vars` so the caller can supply web-lead fields. This design requires `_try_send_one` to know the recipient's `source` and to fetch the web-lead capture record when `source == "web_lead"`. That lookup is a separate concern best addressed in a CMP-006 follow-up; for CMP-008 the `extra_vars` hook is defined but the CMP-006 send path is expected to populate it.

4. **`company` merge tag**: SuiteCRM includes `{{company}}` in its standard merge-tag set. The testlogon platform has no `company` field in `PROFILE_FIELDS`. Rather than add a new profile field (out of scope for CMP-008), this spec leaves `{{company}}` unresolved (empty string → placeholder left intact) for platform users. Campaign authors who need `{{company}}` should use it only in campaigns targeting web-lead recipients (CMP-006) where the company field is captured at form submission time.

5. **`merge_vars_used` computation**: This spec defines `merge_vars_used` as "vars that were present in the template AND had non-empty resolved values." Implementation: collect all var names matched by `_VAR_RE.findall(template)`, then filter to those present with non-empty values in `merge_vars`. This requires a pre-render scan of the template strings. Simpler alternative: `merge_vars_used = [k for k, v in merge_vars.items() if v != ""]`. The simpler alternative slightly over-reports (includes vars not present in the template), but is acceptable for a diagnostic hint to the campaign author.

6. **Rate limiting the preview endpoint**: The preview endpoint calls `get_profile` + `get_template` + `generate_unsubscribe_url` per request. No per-endpoint rate limit is specified in this ticket. The platform's global API rate-limiting middleware (if implemented) provides baseline protection. If the endpoint is abused for token harvesting (§7 Security), a dedicated rate limit (`_ai_rate_limit_or_429` pattern from MVA) can be added in a follow-up.
