# RPT-007 — Pre-built dashlet catalogue

**Type:** Feature | **Priority:** P2 | **Estimate:** 3d
**Area:** CRM Reports & Dashboards
**Source:** `docs/suitecrm/CRM_REPORTS_TICKETS.md` (RPT-007 section, lines 378–421)

---

## 1. Summary & Goal

RPT-007 implements the backend data providers for the five standard built-in dashlet types and wires them into the frontend dashboard rendered by RPT-006. The deliverable is a single polymorphic data endpoint — `GET /ui/crm/dashboard/dashlets/{dashlet_id}/data` — that reads the calling user's dashlet configuration from `T.crm_dashboards` (provisioned by RPT-001, managed by RPT-006), dispatches to one of five typed providers, and returns a capped, read-only JSON payload. A new service module `app/services/crm_dashlet_data.py` houses all provider logic. Five React components in `frontend/src/pages/reports/dashlets/` render each payload type inside the dashboard grid introduced by RPT-006.

The SuiteCRM gap analysis identifies this capability as DASH-003 "standard dashlet catalogue". testlogon has several hard-coded domain dashboards (creator earnings in `frontend/src/pages/earnings/EarningsPage.tsx`, platform financials in `app/services/platform_financial_dashboard.py`) but no unified, user-configurable dashboard with parameterised tiles. RPT-007 closes the gap for the five most important dashlet types without forking any existing query path.

All new behaviour is inert when `S.crm_reports_enabled` is `False` (default). The platform is byte-for-byte unchanged with the flag off.

## 2. Context & Current State

### 2.1 Existing data surfaces consumed by dashlet providers

**Tickets.** `app/services/tickets.py` defines `TicketStore` (a `@dataclass` with `_table: Any = field(default=T.tickets)` at `app/services/tickets.py:245`). `TicketStore.list_tickets` queries `gsi1pk = OWNER#{owner_sub}` on the `owner_by_updated` GSI to retrieve the calling user's tickets newest-first (`app/services/tickets.py:614`). For admin users it can query the `gsi2pk = STATUS#{status}` partition on the status GSI (`app/services/tickets.py:637`). Ticket items carry `ticket_id`, `subject`, `status`, `created_at`, `updated_at` at a minimum (`app/services/tickets.py:440–475`). The tickets table is `T.tickets = _safe_table(S.tickets_table_name)` (`app/core/tables.py:392`; `app/core/settings.py:421`: default `"tickets"`).

**Calendar.** `app/routers/calendar.py` exposes event listing through `_list_events(calendar_id, start_utc, end_utc, limit, cursor)` (`app/routers/calendar.py:841`), which queries `T.calendar` with `KeyConditionExpression: Key("calendar_id").eq(calendar_id) & Key("sk").begins_with("event#")` and optional date-window filtering (`app/routers/calendar.py:853–879`). The calendar table PK is `calendar_id` (S) / SK `sk` (S); event rows use `sk = "event#{event_id}"` (`app/routers/calendar.py:262`). The user's calendars are found via the access-index pattern at `_load_calendar_access` (`app/routers/calendar.py:806`). `T.calendar = _safe_table(S.calendar_table_name)` (`app/core/tables.py:346`; `app/core/settings.py:466`: default `"calendar"`).

**Contacts.** `app/services/csv_export.py:90` implements `_iter_contacts(user_sub)` which queries `T.contacts` by `Key("owner_id").eq(user_sub)` with `Limit=500` and `LastEvaluatedKey` pagination. Contact items carry `name`, `email`, `phone`, `company`, `tags`, `last_contacted_at` and related fields. `T.contacts = _safe_table(S.contacts_table_name)` (`app/core/tables.py:354`; `app/core/settings.py:498`: default `"Contacts"`).

**Billing ledger.** `app/services/csv_export.py:52` implements `_iter_billing_entries(user_sub, from_date, to_date)` which queries `T.billing` with `pk = USER#{user_sub}` and `begins_with(sk, "LEDGER#")`, paginating via `LastEvaluatedKey` with `Limit=500` (`app/services/csv_export.py:63–87`). Items carry `created_at`, `entry_type`, `amount_cents`, `currency`. `T.billing = _safe_table(S.billing_table_name)` (`app/core/tables.py:333`; `app/core/settings.py:348`: default `"billing"`). The `user_pk` helper lives at `app/services/billing_shared.py:23` and returns `f"USER#{user_id}"`.

**Report run results.** RPT-002 writes RUN rows to `T.crm_reports` with `sk = "RUN#{run_ts:010d}#{run_id}"` and META rows with `sk = "META"`. The service function `run_report(report_id, owner_sub)` and `get_report(report_id, owner_sub)` live in `app/services/crm_reports.py` (introduced by RPT-002). The `ReportRunOut` model (defined in RPT-002 in `app/models.py`) carries `columns: List[str]` and `rows: List[List[Any]]`.

### 2.2 Dashboard storage (RPT-006)

RPT-006 writes dashlet configurations as a `dashlets` list inside the `T.crm_dashboards` META row at PK `dashboard_id = "DASH#{user_sub}#default"`, SK `"META"`. Each element in the list is:

```json
{
  "dashlet_id": "dlt_{uuid8}",
  "dashlet_type": "recent_tickets | calendar_today | my_contacts | billing_summary | report",
  "title": "string",
  "config": {}
}
```

The `config` map carries type-specific configuration:
- `recent_tickets`: optionally `row_limit` (default 10), `status_filter` (default `"open"`)
- `calendar_today`: optionally `calendar_id` (if absent, uses the user's first calendar)
- `my_contacts`: optionally `row_limit` (default 10), `sort_by` (default `"last_contacted_at"`)
- `billing_summary`: optionally `period_days` (default 30, max 365)
- `report`: required `report_id` (string); optional `use_cached` (boolean, default `true`)

`T.crm_dashboards = _safe_table(S.crm_dashboards_table_name)` is added by RPT-001.

### 2.3 No dashlet data service exists yet

No `app/services/crm_dashlet_data.py` exists. No `GET /ui/crm/dashboard/dashlets/{dashlet_id}/data` endpoint exists. The RPT-006 `DashboardPage.tsx` renders tile shells but all provider functions and frontend dashlet components are stubs that RPT-007 fills in.

### 2.4 Route ordering

The file-header constraint (`CRM_REPORTS_TICKETS.md` lines 25–26) requires static path segments before dynamic `{dashlet_id}`. The RPT-006 router (`app/routers/crm_dashboard.py`) already places `/dashlets/reorder` and `/dashlets` before `/{dashlet_id}` (RPT-006 spec). The new `/dashlets/{dashlet_id}/data` route is a sub-path of the existing dynamic segment and carries no ambiguity.

### 2.5 Auth dependency

All `/ui/crm/*` endpoints use `require_ui_session` imported from `app.services.sessions` (confirmed at `app/routers/calendar.py:80`, `app/routers/tickets.py:19`). The dependency returns a dict with at minimum `user_sub`, `role`, `session_id`. RPT-007 follows this pattern throughout.

## 3. Data Model

### 3.1 No new DynamoDB tables

RPT-007 is purely read-only. It reads from five existing tables (`T.crm_dashboards`, `T.tickets`, `T.calendar`, `T.contacts`, `T.billing`) and one RPT-001 table (`T.crm_reports`). No new TableDef entries are required in `scripts/local-ddb-init.py`.

### 3.2 No new DynamoDB writes

Dashlet data is ephemeral: the endpoint computes and returns it; nothing is persisted. The `report` dashlet type optionally reads a previously persisted RUN row from `T.crm_reports` (written by RPT-002's `run_report`).

### 3.3 Response shape per dashlet type

All five providers return a dict under the key `data`, plus metadata (`dashlet_id`, `dashlet_type`, `fetched_at`). The type-specific shapes are:

```
recent_tickets:
  { tickets: [{ticket_id, subject, status, created_at, updated_at}], count: int }

calendar_today:
  { events: [{event_id, title, start_utc, end_utc, all_day}], date_utc: str }

my_contacts:
  { contacts: [{contact_id, name, email, phone, last_contacted_at}], count: int }

billing_summary:
  { total_cents: int, tx_count: int, period_days: int, currency: str }

report:
  { columns: List[str], rows: List[List[Any]], row_count: int, run_at: int, source: "cached" | "fresh" }
```

These shapes are validated via Pydantic models defined in `app/models.py` and returned from the endpoint as `DashletDataOut` (see section 4.3).

## 4. API / Service Design

### 4.1 Service module: `app/services/crm_dashlet_data.py`

All provider logic lives here. The module imports lazily where needed to avoid circular dependencies, following the pattern in `app/services/ssh_bastion.py`.

```python
# app/services/crm_dashlet_data.py

from __future__ import annotations

import logging
from datetime import datetime, timezone, timedelta
from decimal import Decimal
from typing import Any, Dict, List, Optional

from app.core.tables import T
from app.core.time import now_ts
from app.services.billing_shared import user_pk

logger = logging.getLogger(__name__)


def get_dashlet_data(user_sub: str, dashlet_id: str) -> Dict[str, Any]:
    """
    Entry point. Reads the user's dashboard from T.crm_dashboards,
    locates the dashlet by dashlet_id, dispatches to the correct provider.
    Raises ValueError("dashlet_not_found") if dashlet_id is absent.
    Raises ValueError("unknown_dashlet_type") if dashlet_type is unrecognised.
    """
    ...


def _fetch_dashboard_meta(user_sub: str) -> Optional[Dict[str, Any]]:
    """Read DASH#{user_sub}#default / META from T.crm_dashboards."""
    dashboard_id = f"DASH#{user_sub}#default"
    resp = T.crm_dashboards.get_item(Key={"dashboard_id": dashboard_id, "sk": "META"})
    return resp.get("Item")


def _provider_recent_tickets(user_sub: str, config: Dict[str, Any]) -> Dict[str, Any]:
    """
    Queries T.tickets by gsi1pk = OWNER#{user_sub}, ScanIndexForward=False,
    Limit = min(config.get("row_limit", 10), 50).
    Applies optional status_filter as a post-fetch client-side filter
    (mirrors DynamoDB FilterExpression limitation noted in CLAUDE.md).
    Returns {"tickets": [...], "count": int}.
    """
    ...


def _provider_calendar_today(user_sub: str, config: Dict[str, Any]) -> Dict[str, Any]:
    """
    Resolves calendar_id from config or falls back to the user's first calendar
    (queries T.calendar by owner_user_sub via the owner GSI introduced by RPT-001
    or falls back to a scan with FilterExpression on owner_user_sub).
    Builds today's UTC window: start = midnight UTC today, end = midnight UTC tomorrow.
    Calls _list_events(calendar_id, start_utc=start_dt, end_utc=end_dt, limit=20)
    using the same helper imported from app.routers.calendar (local import to
    avoid circular dep at module import time).
    Returns {"events": [...], "date_utc": "YYYY-MM-DD"}.
    """
    ...


def _provider_my_contacts(user_sub: str, config: Dict[str, Any]) -> Dict[str, Any]:
    """
    Calls _iter_contacts(user_sub) from app.services.csv_export (local import).
    Collects up to min(config.get("row_limit", 10), 50) items.
    Sorts by last_contacted_at descending (client-side; DynamoDB contacts table
    is keyed on owner_id with no sort key — app/services/csv_export.py:90).
    Returns {"contacts": [...], "count": int}.
    """
    ...


def _provider_billing_summary(user_sub: str, config: Dict[str, Any]) -> Dict[str, Any]:
    """
    Computes period_days = min(config.get("period_days", 30), 365).
    Calls _iter_billing_entries(user_sub, from_date=cutoff_ts) from
    app.services.csv_export (local import).
    Accumulates total_cents (sum of amount_cents for debit entries) and tx_count.
    Coerces DynamoDB Decimal to int via int(Decimal(...)).
    Returns {"total_cents": int, "tx_count": int, "period_days": int, "currency": "usd"}.
    """
    ...


def _provider_report(user_sub: str, config: Dict[str, Any]) -> Dict[str, Any]:
    """
    report_id = config["report_id"]  # required; raises ValueError if absent
    use_cached = config.get("use_cached", True)

    If use_cached:
      Query T.crm_reports PK=report_id, SK begins_with("RUN#"),
      ScanIndexForward=False, Limit=1 to fetch the most recent RUN row.
      If found: return columns/rows/row_count/run_at with source="cached".
    If not use_cached or no cached run:
      Import crm_reports.run_report (local import) and execute synchronously
      (blocking; caller wraps in asyncio.to_thread — see section 4.2).
      Return with source="fresh".
    Raises ValueError("report_id_required") if report_id absent from config.
    Raises PermissionError if run_report ownership check fails.
    """
    ...
```

All five private functions are unit-testable in isolation (injectable `_table` handles for tests).

### 4.2 Router endpoint: `app/routers/crm_dashboard.py` (extension)

Add one route to the existing `crm_dashboard` router created by RPT-006:

```python
@router.get("/dashboard/dashlets/{dashlet_id}/data")
async def get_dashlet_data_endpoint(
    dashlet_id: str,
    ctx: Dict[str, Any] = Depends(require_ui_session),
):
    if not S.crm_reports_enabled:
        raise HTTPException(status_code=404, detail="not_found")
    user_sub = ctx["user_sub"]
    try:
        result = await asyncio.to_thread(
            crm_dashlet_data.get_dashlet_data, user_sub, dashlet_id
        )
    except ValueError as exc:
        code = str(exc)
        if code == "dashlet_not_found":
            raise HTTPException(status_code=404, detail="dashlet_not_found")
        if code in ("unknown_dashlet_type", "report_id_required"):
            raise HTTPException(status_code=422, detail=code)
        raise HTTPException(status_code=400, detail=code)
    except PermissionError:
        raise HTTPException(status_code=403, detail="forbidden")
    return DashletDataOut(
        dashlet_id=dashlet_id,
        dashlet_type=result["dashlet_type"],
        fetched_at=now_ts(),
        data=result["data"],
    )
```

The route must be declared **before** any pattern that could capture `{dashlet_id}` as a different parameter. In the RPT-006 router the existing routes are:

```
GET    /ui/crm/dashboard
PATCH  /ui/crm/dashboard
POST   /ui/crm/dashboard/dashlets
DELETE /ui/crm/dashboard/dashlets/{dashlet_id}
POST   /ui/crm/dashboard/dashlets/reorder
```

Insert `GET /ui/crm/dashboard/dashlets/{dashlet_id}/data` after the `DELETE` route and before any future catch-all.

## 5. Detailed Behavior & Edge Cases

### 5.1 Dashlet lookup

`get_dashlet_data` reads the user's dashboard META item (PK `DASH#{user_sub}#default` / SK `"META"`) and scans the in-memory `dashlets` list for an element with `dashlet_id == requested_id`. If the dashboard META item does not exist (user never called RPT-006's `GET /ui/crm/dashboard`), treat as empty dashlet list → `ValueError("dashlet_not_found")` → 404. If the dashlet is found but `dashlet_type` is not in the known set, raise `ValueError("unknown_dashlet_type")` → 422. Ownership is implicit: the PK includes `user_sub`, so a user can only retrieve their own dashlets.

### 5.2 `recent_tickets` provider

Query `T.tickets` using `IndexName=S.tickets_owner_index_name` (the `gsi1pk` GSI referenced at `app/services/tickets.py:620`), `KeyConditionExpression: "gsi1pk = :pk"` with `:pk = "OWNER#{user_sub}"`, `ScanIndexForward=False`, `Limit = row_limit` (capped at 50). Apply `status_filter` client-side after fetch because DynamoDB FilterExpression does not reduce the Limit consumption and ticket status is sparse (CLAUDE.md "DDB FilterExpression doesn't reduce page size" gotcha). Project to `{ticket_id, subject, status, created_at, updated_at}`. Coerce `Decimal` timestamps via `int(item.get("created_at", 0))` following the pattern at `app/services/tickets.py:548`.

Admin users (role >= ADMIN) whose dashlets have `config.status_filter = "open"` (or any status) may query the `gsi2pk = STATUS#{status}` partition instead, returning system-wide open tickets (same as the admin summary path at `app/services/tickets.py:637`). Non-admin users always query by `gsi1pk = OWNER#{user_sub}` regardless of `status_filter`.

### 5.3 `calendar_today` provider

Determine today's UTC date window:
```python
now_utc = datetime.now(timezone.utc)
day_start = now_utc.replace(hour=0, minute=0, second=0, microsecond=0)
day_end   = day_start + timedelta(days=1)
```

Resolve `calendar_id` from `config.get("calendar_id")`. If absent, find the user's first calendar by querying `T.calendar` with `FilterExpression: Attr("owner_user_sub").eq(user_sub) & Attr("sk").eq("meta")` and taking the first result. If no calendar exists, return `{"events": [], "date_utc": "YYYY-MM-DD"}`.

Call `_list_events(calendar_id, start_utc=day_start, end_utc=day_end, limit=20)` (imported locally from `app.routers.calendar`). Apply `_expand_event_occurrences` for recurring events using the same idiom as `app/routers/calendar.py:1700–1703`. Return the first 20 results sorted by `start_utc` ascending.

Edge cases: the `_list_events` function returns `(items, next_cursor)` (confirmed at `app/routers/calendar.py:841`); discard the cursor. If the calendar_id from config belongs to a different user, the `T.calendar` `get_item` will return the item regardless (no ownership check in the table itself); ownership is enforced at the dashboard layer: the dashlet config was set by the user through the RPT-006 `add_dashlet` endpoint which already runs `require_ui_session`. However the provider should catch `HTTPException` from `_list_events` and return an empty events list to avoid leaking 404 errors from within the dashlet data response.

### 5.4 `my_contacts` provider

Call `_iter_contacts(user_sub)` (from `app.services.csv_export`, local import). Collect items into a list, stopping at `row_limit` (default 10, max 50). Sort by `last_contacted_at` descending client-side — `Decimal` values from DynamoDB must be converted to `int` before comparison. Project to `{contact_id, name, email, phone, last_contacted_at}` using the pattern in `_format_contacts_row` from `app/services/csv_export.py`. The `contact_id` field is the value of `item.get("contact_id", item.get("sk", ""))`.

### 5.5 `billing_summary` provider

`period_days = min(int(config.get("period_days", 30)), 365)`. Compute `cutoff_ts = now_ts() - period_days * 86400`. Call `_iter_billing_entries(user_sub, from_date=cutoff_ts)`. Accumulate `total_cents` by summing `int(item.get("amount_cents", 0))` for entries where `entry_type` is a debit type (entry_type in `{"charge", "debit", "purchase", "tip_sent"}` — matches the `entry_type` values written by `new_ledger_entry` in `app/services/billing_shared.py`). Count all entries for `tx_count`. Coerce `Decimal` via `int(Decimal(...))` following `app/core/tables.py:11` pattern.

### 5.6 `report` dashlet provider

`report_id = config.get("report_id")` — if absent raise `ValueError("report_id_required")` → 422. `use_cached = config.get("use_cached", True)`.

**Cached path**: Query `T.crm_reports` for `pk = report_id` with `KeyConditionExpression: "report_id = :id AND begins_with(sk, :prefix)"`, `:prefix = "RUN#"`, `ScanIndexForward=False`, `Limit=1`. If an item is found, extract `columns`, `rows`, `row_count`, `run_at` and return with `source="cached"`.

**Fresh path** (use_cached=False or no cached run): import `crm_reports.run_report` locally and call it with `(report_id, user_sub)`. This call is already wrapped in `asyncio.to_thread` at the router layer (section 4.2), so it executes in a thread pool and does not block the event loop. `run_report` raises `PermissionError` if ownership fails — propagated as HTTP 403.

### 5.7 Row caps and DoS prevention

| Provider | Cap | Rationale |
|----------|-----|-----------|
| `recent_tickets` | 50 | dashboard tile, not a full report |
| `calendar_today` | 20 | single-day view |
| `my_contacts` | 50 | card grid |
| `billing_summary` | aggregate only | no row list |
| `report` (cached) | none (inherits RPT-002 cap of 2000) | dashlet shows first 20 rows |

The frontend `ReportDashlet.tsx` displays only the first 20 rows from the `rows` array; the full `ReportRunOut` payload is available for a "View full report" link.

### 5.8 Unknown dashlet type

If `dashlet_type` is not in `{"recent_tickets", "calendar_today", "my_contacts", "billing_summary", "report"}`, raise `ValueError("unknown_dashlet_type")` → HTTP 422 with body `{"detail": "unknown_dashlet_type"}`. This allows RPT-008 to add `"saved_search"` without touching this validation — the RPT-007 endpoint is extended (not forked) by RPT-008.

### 5.9 Partial-failure contract

Individual provider errors (e.g. a transient DynamoDB read failure inside `_provider_calendar_today`) should not propagate as 500s. Wrap each provider call with a `try/except Exception` in `get_dashlet_data`; on failure log the error and re-raise as `ValueError("provider_error")` → HTTP 400 with code `"provider_error"`. This gives the frontend a stable, typed error it can display as "This dashlet is temporarily unavailable" without crashing the dashboard page.

## 6. Feature Flag & Config

### 6.1 Master flag (from RPT-001)

```python
# app/core/settings.py  (added by RPT-001)
crm_reports_enabled: bool = _bool_env("CRM_REPORTS_ENABLED", False)
```

Default: `False` (off). With this flag off, the `GET /ui/crm/dashboard/dashlets/{dashlet_id}/data` endpoint returns HTTP 404. No DynamoDB calls are made. No background tasks are started.

### 6.2 No new flags required by RPT-007

RPT-007 introduces no additional flags. The behaviour of all five providers is controlled entirely by the per-dashlet `config` dict stored in the dashboard META item (itself managed by RPT-006 endpoints). This avoids flag proliferation.

### 6.3 Per-dashlet config parameters (not flags)

These are runtime config values stored in DynamoDB, not environment variables:

| Dashlet type | Config key | Type | Default | Constraint |
|---|---|---|---|---|
| `recent_tickets` | `row_limit` | int | 10 | 1–50 |
| `recent_tickets` | `status_filter` | str | `"open"` | member of `_TICKET_STATUSES` |
| `calendar_today` | `calendar_id` | str | (first calendar) | optional |
| `my_contacts` | `row_limit` | int | 10 | 1–50 |
| `my_contacts` | `sort_by` | str | `"last_contacted_at"` | ignored if not supported |
| `billing_summary` | `period_days` | int | 30 | 1–365 |
| `report` | `report_id` | str | — | required |
| `report` | `use_cached` | bool | `true` | — |

Config validation happens inside each provider function, not at the RPT-006 `add_dashlet` endpoint, so new dashlet types can be added without retroactively updating the `add_dashlet` schema.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

All five providers query DynamoDB directly using the same `T.*` table handles that run against DynamoDB Local (port 8001, `DDB_ENDPOINT_URL=http://localhost:8001`) in dev and against AWS DynamoDB in prod. There are no `if S.dev_mode` branches in `crm_dashlet_data.py`. The `_list_events` function imported from `app.routers.calendar` already follows this pattern (confirmed: no `dev_mode` branch in the event listing logic at `app/routers/calendar.py:841`).

For the `report` dashlet's fresh-run path, `run_report` from RPT-002 executes identically in both environments (same DynamoDB query adapters).

### 7.2 Idempotency

`GET /ui/crm/dashboard/dashlets/{dashlet_id}/data` is a pure read. It never writes to DynamoDB (except indirectly through the `report` fresh-run path, which writes a RUN row to `T.crm_reports` — that write is idempotent with a unique `run_id`). Repeated calls return live data and are safe to retry.

### 7.3 Ownership and access control

The provider dispatch in `get_dashlet_data` reads the dashboard keyed by `DASH#{user_sub}#default` where `user_sub` comes from the verified `require_ui_session` dependency. A user cannot read another user's dashlet data because the PK includes their `user_sub`. Cross-user report access in the `report` provider is blocked by `run_report`'s ownership check in RPT-002 (`get_report` raises `PermissionError` if `owner_sub` mismatches).

No `report_id` from the dashlet config bypasses the ownership check — the provider always passes the authenticated `user_sub` to `run_report`/`get_report`.

### 7.4 No financial writes

The `billing_summary` provider is strictly read-only. It calls `_iter_billing_entries` which issues `T.billing.query(...)` calls only. No calls to `apply_balance_delta`, `new_ledger_entry`, `refund_payment`, or `settle_or_reverse_ledger` are made by any dashlet provider.

### 7.5 Audit events

RPT-007 does not emit audit events for dashlet data reads (they are high-frequency, low-risk GET operations). The underlying `run_report` (fresh path for the `report` dashlet) may emit an audit event per RPT-002's design; that is preserved.

## 8. Backward Compatibility & Migration

### 8.1 Additive only

RPT-007 adds one new endpoint and one new service module. No existing endpoint, service function, model, or DynamoDB table schema is modified. All existing behaviour is unchanged whether `CRM_REPORTS_ENABLED` is `0` (default) or `1`.

### 8.2 No DynamoDB migration

No new tables and no new GSIs. No `scripts/local-ddb-init.py` changes. No `just restart` or table recreation is required beyond what RPT-001 already provisions.

### 8.3 Dashboard META items without dashlets

A `DashboardOut` with an empty `dashlets` list (freshly created by RPT-006's `get_or_create_default_dashboard`) simply means no dashlet IDs are valid; any request to `GET .../data` returns 404 with `detail="dashlet_not_found"`. This is the correct behaviour for a new user.

### 8.4 Forward compatibility for RPT-008

RPT-008 adds the `saved_search` dashlet type. The dispatch in `get_dashlet_data` raises `ValueError("unknown_dashlet_type")` → 422 for unrecognised types. When RPT-008 extends the dispatch dict with a `"saved_search"` entry, existing dashlets of other types are unaffected. The `DashletDataOut.data` field uses `Union[..., Dict[str, Any]]` to accept the new response shape without a model conflict.

## 10. Open Questions / Assumptions

1. **Calendar identity resolution**: the `calendar_today` provider needs to find the user's default calendar when no `calendar_id` is in the config. The current schema stores `owner_user_sub` on the calendar META item (`app/routers/calendar.py:1031`) but there is no GSI on `owner_user_sub` in the existing `calendar` table definition in `scripts/local-ddb-init.py`. **Assumption**: the provider performs a low-cost filtered scan (user typically has 1–3 calendars) or the RPT-006 `add_dashlet` endpoint for `calendar_today` tiles requires `calendar_id` in config (making it non-optional at add time). This needs product decision before implementation. If a GSI is preferred, it requires a `scripts/local-ddb-init.py` change (additive, no migration) with `attr_types={"owner_user_sub": "S"}`.

2. **`recent_tickets` admin path**: the spec allows admin users to query system-wide tickets by status. Should the admin path be gated on a separate config key (`admin_view: true`) to prevent accidental data exposure? **Assumption for now**: admin users only see system-wide data when `config.admin_view = true` is explicitly set on the dashlet.

3. **`report` dashlet fresh-run latency**: calling `run_report` synchronously in a thread pool for a complex report may take multiple seconds. Should the endpoint return immediately with a `"pending"` status and push the result to a polling endpoint? **Assumption**: out of scope for RPT-007; the fresh-run path is only triggered when `use_cached=False` (explicit user intent). A future RPT ticket can add async execution.

4. **`billing_summary` debit types**: the set `{"charge", "debit", "purchase", "tip_sent"}` is assumed from inspection of `new_ledger_entry` callers. This must be verified against the actual `entry_type` values written in `app/routers/billing.py` and `app/routers/paypal.py` before implementation.

5. **Row cap for `report` dashlet in the frontend**: the spec proposes displaying only the first 20 rows from a potentially 2000-row `ReportRunOut`. This is a frontend-only concern; the API always returns the full capped dataset. The "View full report" link navigates to `/crm/reports/:reportId` (introduced by RPT-005).
