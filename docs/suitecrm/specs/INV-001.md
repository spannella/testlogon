# INV-001 — Invoice line items — unit_price_cents, subtotal, discount, and address fields

**Ticket type:** Feature  
**Priority:** P1  
**Estimate:** 2d  
**Feature flag:** `AOS_INVOICE_FIELDS_ENABLED` (default `"0"`, off)

---

## 1. Summary & Goal

Extend the existing invoice data model and PDF renderer to carry the fields that
SuiteCRM's Advanced OpenSales (AOS) Invoice module exposes but testlogon currently
omits:

- `unit_price_cents` on each line item, making every line fully self-describing
  as `qty × unit_price_cents = amount_cents`.
- `discount_cents` and `shipping_cents` on the invoice header, so the total
  formula can reflect real-world discounts and freight.
- `billing_address` and `shipping_address` structs (street, city, state,
  postal_code, country) stored on the invoice and printed on the PDF.

With the flag off the existing `create_invoice` call sites are byte-for-byte
unchanged. No new DynamoDB table is required; all new fields are additive
attributes on the existing `pk=USER#{sub} / sk=INV#{number}` items.

## 3. Data Model

### No new DynamoDB tables or GSIs

All new attributes are stored as additive fields on existing
`pk=USER#{sub} / sk=INV#{number}` items in `T.invoices`. DynamoDB is schema-less
for non-key attributes; no changes to `scripts/local-ddb-init.py` are required
for INV-001.

### New attributes on existing invoice items

| Attribute | Type | Default | Notes |
|---|---|---|---|
| `unit_price_cents` (per line item) | `N` (int) | `0` | Per-unit price; persisted inside the existing `line_items` list attribute |
| `discount_cents` | `N` (int) | `0` | Header-level discount; must be `>= 0` |
| `shipping_cents` | `N` (int) | `0` | Header-level shipping charge; must be `>= 0` |
| `billing_address` | `M` (map) | absent (null) | Nested map: `{street, city, state, postal_code, country}` |
| `shipping_address` | `M` (map) | absent (null) | Same shape as billing_address |

### Updated `total_cents` computation

When `AOS_INVOICE_FIELDS_ENABLED=1`:

```
total_cents = amount_cents + tax_cents + shipping_cents - discount_cents
```

Where:
- `amount_cents` = sum of all `line_item.amount_cents` (unchanged, pre-tax subtotal)
- `tax_cents` = platform-wide `invoices_tax_bps` fallback, or per-line tax from
  INV-006 when that ticket lands
- `shipping_cents` = value passed by caller (default `0`)
- `discount_cents` = value passed by caller (default `0`), capped at `amount_cents`
  (negative totals are rejected — see Section 5)

When `AOS_INVOICE_FIELDS_ENABLED=0` (default): `total_cents = amount_cents + tax_cents`
unchanged from current line 308.

#### Changes to `norm_items` loop (currently line 314)

When `S.aos_invoice_fields_enabled` is `True` and `unit_price_cents_per_item` is


#### Changes to `total_cents` computation (currently line 308)

```python

    tax_cents = (amount_cents * max(0, S.invoices_tax_bps)) // 10_000

    shipping_cents = max(0, _coerce_int(shipping_cents))

    shipping_cents = 0
```

## 5. Detailed Behavior & Edge Cases

### Flag-off invariant

When `AOS_INVOICE_FIELDS_ENABLED=0` (default):

- Calls to `create_invoice` with or without the new keyword args produce an
  identical DDB item and PDF to the current implementation. The new kwargs are
  accepted but silently ignored (early-exit path sets `discount_cents=0`,
  `shipping_cents=0`, and skips address/unit-price persistence).
- `InvoiceOut` fields `discount_cents`, `shipping_cents` default to `0`;
  `billing_address` and `shipping_address` default to `None`. Existing API
  consumers see no new required fields.
- `InvoiceLineItemOut.unit_price_cents` defaults to `0` for all invoices regardless
  of flag.

### Backward compatibility for old DDB items

Old invoice items written before INV-001 was deployed have no `discount_cents`,
`shipping_cents`, `billing_address`, `shipping_address`, or `unit_price_cents` on
their line item dicts. `_serialize` uses `_coerce_int(record.get("field"), 0)` and
`record.get("billing_address") or None`, so they deserialize cleanly with defaults.
`InvoiceOut(**dict)` accepts the `None`/`0` defaults without error.

### Discount cap

`discount_cents` is capped at `amount_cents` in the service layer before
computing `total_cents`. This prevents a discount larger than the subtotal from
producing a negative total. If the caller passes `discount_cents > amount_cents`,
the service silently reduces it to `amount_cents`, resulting in `total_cents =
tax_cents + shipping_cents`. A `logger.warning(...)` is emitted in this case for
observability.

### Negative or zero discount/shipping rejected upstream

`max(0, _coerce_int(discount_cents))` and `max(0, _coerce_int(shipping_cents))`
ensure negative values from callers are treated as zero. The Pydantic model
`InvoiceOut.discount_cents: int = 0` does not enforce non-negativity at the model
layer, since the service already guards it.

### `unit_price_cents` vs. `amount_cents` consistency

The service does not recompute `amount_cents` from `qty × unit_price_cents`. The
caller remains responsible for providing a correct `amount_cents` per line. The
`unit_price_cents` field is advisory/display-only from the service's perspective.
A future ticket may add a consistency check (`qty * unit_price_cents == amount_cents`
within a cent of rounding) as a validation warning.

### Idempotency on `ledger_entry_id`

The existing idempotency path (`_existing_for_ledger`, line 252) checks for a
per-ledger marker row and returns the existing invoice if found. The new fields
are persisted on the original item when the invoice was first created; repeat
calls with the same `ledger_entry_id` return the already-stored serialization
including the new fields. No change to the idempotency mechanism is needed.

### PDF regeneration on S3 cache miss

`download_invoice_pdf` (line 442) calls `_render_invoice_lines(raw)` to regenerate
the PDF when the S3 object is missing. The updated `_render_invoice_lines` uses
`S.aos_invoice_fields_enabled` at render time, not at write time. This means:

- If the flag is off when the PDF is regenerated, discount/address blocks will
  not appear even if they are stored on the item.
- If the flag is on, they will appear.

This is intentional: the flag controls the current platform capability, not a
per-invoice stored preference.

### Address struct validation

`InvoiceAddressIn.country` is validated as a two-character string (ISO 3166-1
alpha-2) at the Pydantic model layer. Callers using the raw `create_invoice`
service function pass a plain `dict`; the service performs a `str()` coercion
but does not validate country code length. Frontend form validation (INV-011 scope)
enforces the constraint on the input side.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

No `if S.dev_mode` branches are introduced. All new DDB writes and reads use
`T.invoices` via the existing `_FloatSafeTable` proxy (`app/core/tables.py:29`),
wired at `app/core/tables.py:547` (`invoices=_safe_table(S.invoices_table_name)`),
which coerces floats to `Decimal` transparently in both dev (moto, in-process) and
prod (real DynamoDB). S3 PDF storage uses `app/core/aws_clients.s3_client`
(`app/services/invoices.py:35`: `_s3 = s3_client()`), already moto-intercepted in
dev via `app/core/dev_s3.py`. No new AWS service is used.

The address map is stored as a DDB `M` (map) attribute. Moto fully supports nested
maps; no dev-only serialization path is needed.

### Idempotency

The idempotency mechanism (`_existing_for_ledger`, ledger marker row with
`ConditionExpression="attribute_not_exists(pk)"`) is unchanged. The new fields are
persisted on the first write only; idempotent replays return the stored item.

### Security

- **No money-out path is introduced.** `discount_cents` reduces `total_cents` but
  does not trigger a payment refund or ledger debit. It is a presentational field
  on the invoice record. Any future discount-ledger integration (INV-007) will use
  `billing_shared.new_ledger_entry` with `extra={"provider": "..."}` as prescribed.
- **Address fields are plaintext strings** stored in DDB. They contain no PII
  beyond what is already on the invoice (`buyer_name`, `buyer_email`). They are
  returned only to the owning user via `require_ui_session` or to admins via
  `require_admin_or_root`; no public endpoint exposes them.
- **Input lengths** are bounded at the Pydantic model layer (`InvoiceAddressIn`
  `max_length` annotations). The service's `str()` coercion truncates only to
  DynamoDB's attribute size limit (400 KB per item, not a practical concern for
  short address strings).
- **`unit_price_cents` is never used to recompute a charge.** It is display data
  only; the authoritative charge amount is `line_item.amount_cents` as before.

All new DDB attributes are additive. No index is added or modified. There is no

### Old invoice items

handles these via `dict.get(key, default)` — old items deserialize to `InvoiceOut`
with `discount_cents=0`, `shipping_cents=0`, `billing_address=None`,
`shipping_address=None`, and `unit_price_cents=0` per line item. The response
shape is unchanged from the client's perspective for pre-existing invoices.

### Callers of `create_invoice`

All current call sites pass keyword args. Adding new optional keyword args with
safe defaults is backward compatible in Python: existing callers that do not pass
`unit_price_cents_per_item`, `discount_cents`, `shipping_cents`, `billing_address`,
or `shipping_address` see exactly the same behavior as before. The `create_invoice_safe`
wrapper (line 373) uses `**kwargs` pass-through, so it forwards new args to
`create_invoice` automatically when callers begin using them.

### QUO-005 coordination

The ticket dependency note in the source document states that QUO-005 also adds
`unit_price_cents` to `InvoiceLineItemOut`. INV-001 and QUO-005 must not conflict
on this field. The safe merge strategy is:

1. If QUO-005 lands first: its `unit_price_cents: int = 0` addition to
   `InvoiceLineItemOut` is identical to INV-001's addition. INV-001's model
   change becomes a no-op and only the service/renderer changes need to be applied.
2. If INV-001 lands first: QUO-005 must not re-add `unit_price_cents` to the
   model but may still reference the field in its own service logic.
3. If both are in flight simultaneously: coordinate on `app/models.py` diff to
   ensure the field is added exactly once with `int = 0` default.

## 10. Open Questions / Assumptions

1. **`VALID_TYPES` and `type="manual"`** — INV-001 does not add `"manual"` to
   `VALID_TYPES` (line 33 of `invoices.py`). Callers creating B2B invoices with
   `unit_price_cents` and addresses will need to use an existing type (e.g.
   `"shop"`) until QUO-005 ships. The INV-001 hermetic tests use `type="shop"`.
   This is documented as a dependency on QUO-005.

2. **`shipping_cents` overlap with INV shipping charge line** — the ticket source
   notes that "Invoice shipping charge line" is PLANNED but not ticketed here.
   `shipping_cents` in INV-001 is a header-level total; there is no separate line
   item for shipping. This is sufficient for MVP rendering. A future ticket may
   convert it to a named line item.

3. **Country code validation depth** — `InvoiceAddressIn.country` uses
   `max_length=2` as a proxy for ISO 3166-1 alpha-2. Full ISO code validation
   (allowlist of known codes) is out of scope for INV-001. The service stores
   whatever two-character string is provided.

4. **`unit_price_cents_per_item` list alignment** — the service aligns
   `unit_price_cents_per_item[idx]` with `line_items[idx]`. If the lists have
   different lengths, missing indices default to `0`. This is an assumption
   documented in code as a comment; the caller is responsible for alignment.
   A future model-layer change may move `unit_price_cents` inside each line item
   dict rather than a parallel list.

5. **`billing_address` dict vs. `InvoiceAddressIn` model** — the service accepts
   `billing_address` as a plain `dict` so the function signature remains
   compatible with programmatic callers (e.g., the billing hooks in
   `billing_shared.py` that call `create_invoice_safe(**kwargs)`). The router
   layer (QUO-005 / INV-011 scope) will accept `InvoiceAddressIn` and call
   `.model_dump()` before passing to the service.
