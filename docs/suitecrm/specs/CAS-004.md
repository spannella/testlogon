# CAS-004 — Case email notifications — transactional SES dispatch

**Type:** Feature  **Priority:** P1  **Estimate:** 1 day  
**Ticket source:** `docs/suitecrm/CRM_CASES_PORTAL_TICKETS.md`, section "CAS-004"

---

## 1. Summary & Goal

CAS-004 closes two concrete gaps in the existing ticket alert pipeline:

1. **HTML email bodies.** `send_alert_email` (`app/services/alerts.py:459`) currently passes only a plain-text `body_text` string to `boto3 ses.send_email`, ignoring `Body.Html`. `render_ticket_email_template` (`alerts.py:235`) returns a `(subject, body_text)` tuple with no HTML variant. CAS-004 extends both so that SES receives a multipart `Text` + `Html` body for every ticket event.

2. **New CRM event types are not email-dispatched.** The future tickets CAS-008 (SLA breach) and CAS-009 (escalation) will emit `ticket_sla_breach` and `ticket_escalated`. CAS-007 will emit `ticket_watcher_added`. CAS-016 will emit `ticket_csat_sent`. None of those event types appear in `ALERT_EVENT_TYPES` (`alerts.py:134`), `ALERT_CATEGORIES` (`alerts.py:32`), or `render_ticket_email_template`'s guard set (`alerts.py:236`) today. CAS-004 registers them so the full email dispatch path is ready before those tickets ship.

3. **Submitter and assigned-agent email lookup is not wired for ticket events.** `_emit_ticket_alerts` (`tickets.py:362`) calls `audit_event` for each recipient, which eventually reaches the `audit_event` email fanout path (`alerts.py:758–810`). That path reads `get_alert_prefs(user_sub)` and only sends if the user has opted `alert_type` into `email_event_types`. For the CRM use-case the platform must send transactional confirmations to both the submitter and the assigned agent _automatically_ when `S.crm_cases_enabled` is on — regardless of personal notification prefs — mirroring SuiteCRM's built-in transactional notifications. This requires a new direct-dispatch call alongside the existing opt-in fanout.

With `CRM_CASES_ENABLED=0` (the default), **zero bytes of existing behavior change.** All additions are additive: new helper functions, new entries in existing sets, a new call site guarded by `if S.crm_cases_enabled`, and extended SES call parameters.

**Location:** `app/services/alerts.py:459`

**New signature:**

```python

    to_emails: List[str],
```

**Behavior change (SES path only):**

```python

    body_block["Html"] = {"Data": html_body[:32000]}
```

### 4.4 New helper — `_send_ticket_transactional_email`

**Location:** `app/services/alerts.py` (new private function, below `render_ticket_email_template`)

This helper performs the **transactional** (non-opt-in) email dispatch used exclusively by the CRM cases path. It is the only way CAS-004 bypasses the `get_alert_prefs` gate.

```python
def _send_ticket_transactional_email(
    user_sub: str,
    *,
    alert_type: str,
    payload: Dict[str, Any],
    outcome: str = "success",
) -> None:
    """Transactional ticket email — sends regardless of user alert prefs.

    Only called when S.crm_cases_enabled is True. Resolves the recipient's
    email address from get_profile_identity (displayed_email field) and
    dispatches via send_alert_email. Best-effort: swallows all exceptions
    so a profile lookup failure or SES error never blocks the ticket operation.
    """
    try:
        identity = get_profile_identity(user_sub)
        email = (identity.get("email") or "").strip()
        if not email:
            return
        template = render_ticket_email_template(
            alert_type=alert_type, payload=payload, outcome=outcome
        )
        if template is None:
            return
        subj, body, html = template
        send_alert_email([email], subj, body, html_body=html)
    except Exception:
        logger.exception(
            "ticket transactional email failed for user_sub=%s event=%s",
            user_sub, alert_type,
        )
```

Key properties:
- **Never raises** — wrapped in `try/except Exception`. A profile lookup or SES error must not roll back the ticket write.
- **No duplicate** — the existing opt-in fanout inside `audit_event` still runs in parallel and sends to any additional addresses the user has configured.
- **No rate-limit gate** — transactional confirmations skip `can_send_alert_channel`. The platform must guarantee delivery of ticket confirmations for compliance (SuiteCRM parity).
- **Flag-gated** — callers wrap in `if S.crm_cases_enabled`.

### 4.5 Wiring in `_emit_ticket_alerts`

**Location:** `app/routers/tickets.py:362`

After the existing `audit_event` loop, add a CRM transactional dispatch block:

```python
def _emit_ticket_alerts(
    event: str,
    *,
    recipients: list[str],
    actor_sub: str,
    request: Request,
    **fields: Any,
) -> None:
    from app.core.settings import S
    principal = _api_key_principal(request)
    api_key_fields: dict[str, Any] = {}
    if principal:
        api_key_fields = {
            "auth_type": "api_key",
            "api_key_id": str(principal.get("api_key_id") or ""),
            "api_key_owner_sub": str(principal.get("user_sub") or ""),
        }
    payload = {**fields, **api_key_fields, "actor_sub": actor_sub}
    for recipient in sorted({item for item in recipients if item}):
        audit_event(event, recipient, request, outcome="success",
                    actor_sub=actor_sub, **api_key_fields, **fields)

    # CRM transactional email — only when CRM cases feature is enabled.
    if S.crm_cases_enabled:
        from app.services.alerts import _send_ticket_transactional_email
        for recipient in sorted({item for item in recipients if item}):
            _send_ticket_transactional_email(
                recipient,
                alert_type=event,
                payload=payload,
                outcome="success",
            )
```

The `_send_ticket_transactional_email` import is local (inside the `if` block) to avoid adding a module-level circular import. The `app.services.alerts` module already imports nothing from `app.routers`; the import direction is safe.

## 5. Detailed Behavior & Edge Cases

### 5.1 Event-to-recipient mapping

| Event | Recipients (current `_emit_ticket_alerts` calls) | Transactional email targets |
|---|---|---|
| `ticket_created` | `[user.sub]` (tickets.py:774) | submitter |
| `ticket_assigned` | `[owner_sub, old_assignee, new_assignee]` (tickets.py:937–944) | submitter + new agent |
| `ticket_replied` | `[owner_sub]` or `[assigned_admin_sub]` (tickets.py:978) | whichever side did not send the reply |
| `ticket_status_changed` | `[owner_sub]` (tickets.py:1008) | submitter |
| `ticket_escalated` | (CAS-009: owner + watchers) | submitter + agent |
| `ticket_sla_breach` | (CAS-008: assignee + watchers) | agent |
| `ticket_watcher_added` | (CAS-007: new watcher) | new watcher |
| `ticket_csat_sent` | (CAS-016: owner) | submitter |

The recipient list passed to `_emit_ticket_alerts` already controls who gets the transactional email. `_send_ticket_transactional_email` fires once per recipient in the list; deduplication is handled by the existing `sorted(set(...))` in `_emit_ticket_alerts`.

### 5.2 Empty or unknown email address

`get_profile_identity` returns `email: None` when the user has not set `displayed_email`. `_send_ticket_transactional_email` silently returns in that case. No error, no retry. For portal/guest submitters (CAS-014), the `owner_sub` will be `"guest:{email}"` — `get_profile_identity` will return `None`; CAS-014 must call `send_alert_email` directly using the known guest email (outside the scope of CAS-004).

### 5.3 Duplicate email delivery

A user who has opted `ticket_created` into their `email_event_types` prefs AND has their profile `displayed_email` set will receive two emails: one from the existing opt-in path (to `prefs["emails"]`) and one from the new transactional path (to `profile.displayed_email`). To prevent this, `_send_ticket_transactional_email` should check whether the transactional address is already in `prefs["emails"]` and skip if so:

```python
prefs = get_alert_prefs(user_sub)
pref_emails = {e.lower() for e in (prefs.get("emails") or [])}
if email.lower() in pref_emails and event in (prefs.get("email_event_types") or []):
    return  # already dispatched via opt-in path
```

This dedup check must itself be wrapped in a `try/except` so a `get_alert_prefs` DDB failure does not suppress the transactional email.

### 5.4 SES HTML escaping

User-supplied fields (`ticket_subject`, display names) are interpolated into the HTML template. All such values must be HTML-escaped before interpolation:

```python
import html as _html
safe_subject = _html.escape(str(ticket_subject))
```

The `_render_ticket_html` helper applies `html.escape` to all user-sourced fields. System-generated fields (`url`, `ticket_id`) are safe by construction.

### 5.5 `case_number` field (CAS-002 dependency)

`render_ticket_email_template` reads `payload.get("case_number")`. When CAS-002 is deployed, `_emit_ticket_alerts` will include `case_number` in `fields`. When CAS-002 is not deployed, `case_number` is `None` and the template falls back to `f"#{ticket_id}"`. No conditional on `crm_cases_enabled` is needed here — the template handles the `None` case.

### 5.6 SES `Body.Html` size limit

AWS SES accepts raw messages up to 40 MB, but the SDK `send_email` action has a 10 MB message limit. The HTML body is capped at 32 000 chars (approximately 32 KB), well within bounds. The plain-text body is capped at 8 000 chars (existing limit at `alerts.py:477`).

### 5.7 `ticket_status_changed` action URL

`_build_action_url` (`alerts.py:65`) already maps `ticket_status_changed` → `/tickets/{ticket_id}`. The four new event types receive the same mapping.

### 5.8 `can_send_alert_channel` rate-limit scope

The transactional path deliberately bypasses `can_send_alert_channel`. The opt-in path respects it. If a spammer opens thousands of tickets, the `ticket_created` transactional emails would fire for each. A secondary guard can be added: if a single `user_sub` has received more than `S.crm_cases_email_transactional_per_hour` (new setting, default 20) ticket emails in the past hour (checked via the same DDB rate-limit table used by `can_send_alert_channel`), suppress additional sends and log a warning. This guard is implementation-detail; the flag controls it.

### 5.9 New event types in future tickets

CAS-007, CAS-008, CAS-009, CAS-016 emit the four new event types. Those tickets must:
- Pass `ticket_id` and `ticket_subject` in their `audit_event` / `_emit_ticket_alerts` `**fields` for `render_ticket_email_template` to produce a valid subject line.
- Pass `case_number` if CAS-002 is deployed.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

`send_alert_email` already enforces parity: the `S.dev_mode` branch (`alerts.py:462–468`) writes to `.logs/dev/emails.log` and returns before any SES call. CAS-004 extends this:

- Dev: `html_body` length is logged as a metadata line (e.g., `Html: 2341 chars`) without writing the full content.
- Prod: `Body.Html.Data` is populated only when `html_body` is non-empty.

No `if S.dev_mode` branch is added inside `render_ticket_email_template` or `_send_ticket_transactional_email`. Both functions behave identically in both environments; only the terminal `send_alert_email` function branches on `dev_mode`.

### 7.2 Idempotency

`send_alert_email` is fire-and-forget with no deduplication. SES itself does not deduplicate. The new transactional path shares this property. For `ticket_created`, the call happens inside `create_ticket` which already uses an idempotent `put_item` guard (`tickets.py:431–433`); a duplicate `create_ticket` call returns the existing ticket without re-running `_emit_ticket_alerts`. For `ticket_assigned`, `assign_ticket` uses `_apply_header_update_once` (`tickets.py:835`) which internally calls `_conditional_update_meta` (`tickets.py:723`) with optimistic locking; a concurrent retry would fail with `TicketStateError` before reaching `_emit_ticket_alerts`. Email idempotency is therefore bounded by the underlying ticket write idempotency.

### 7.3 Security

- **HTML injection**: All user-supplied strings are HTML-escaped via `html.escape` before interpolation into the HTML template.
- **Open redirect**: `_ticket_thread_url` (`alerts.py:228`) produces an absolute URL using `S.public_base_url` (admin-configured) + `/tickets/{ticket_id}` where `ticket_id` is a server-generated opaque string. No user input reaches the URL.
- **Email header injection**: `subject[:120]` (existing cap) prevents multi-line subject injection. No user input is placed in SES `Source` or `Destination` headers.
- **Information disclosure**: The HTML body includes `ticket_subject` (user-provided) and `ticket_id` (server-generated). No internal fields (DDB keys, admin sub-IDs, HMAC tokens) appear in the email body.
- **Rate limiting**: The `crm_cases_email_transactional_per_hour` cap prevents a malicious user from generating thousands of ticket-creation emails to other users by creating tickets that assign them.

## 8. Backward Compatibility & Migration

### 8.1 `render_ticket_email_template` return type change

The return type changes from `Tuple[str, str] | None` to `tuple[str, str, str] | None`. The call site in `app/` (`alerts.py:763–766`) must be updated from `subj, body = ticket_template` to `subj, body, html = ticket_template`. **There is also a second call site in tests: `tests/test_alerts_webhook_retry.py:169` does `subj, body = alerts.render_ticket_email_template(...)` using 2-tuple unpacking; this test must also be updated to unpack three values.** Grep against `app/` code returns two hits — the definition at `alerts.py:235` and the call site at `alerts.py:763` — but a broader `grep -rn "render_ticket_email_template"` returns a third hit in `tests/test_alerts_webhook_retry.py:169`.

### 8.2 `send_alert_email` signature change

`html_body` is keyword-only and defaults to `None`. The three internal `alerts.py` call sites (`alerts.py:766`, `alerts.py:778`, `alerts.py:804`) all use positional form `(emails, subj, body)` and are unaffected. Several external callers in the codebase use **keyword arguments**: `app/services/cart_reminders.py:374` calls `send_alert_email([email], subject=subject, body_text=body_text)` and `app/services/shoppingcart.py:854–858` uses keyword `body_text=`. Since the parameter name `body_text` is unchanged in the new signature, keyword callers remain backward compatible. No existing caller breaks.

### 8.3 `ALERT_EVENT_TYPES` and `ALERT_CATEGORIES` additions

`ALERT_EVENT_TYPES` is read by `set_alert_prefs` (line 334) to filter user-submitted preferences and by the admin email template test suite. Adding new strings is purely additive. `ALERT_CATEGORIES` is read by `get_alert_category` (line 53) which returns `"security"` as a fallback — adding the new types to `"updates"` only improves categorization.

### 8.4 No DynamoDB migration

No new tables, GSIs, or attributes. No backfill required.

### 8.5 No frontend change

The email is sent server-side. No frontend component is added or modified in CAS-004.

## 10. Open Questions / Assumptions

1. **`displayed_email` vs. Cognito email** — `get_profile_identity` returns `profile.get("displayed_email")`. A user who registered via Cognito but never set `displayed_email` gets no transactional email. Should the fallback be the Cognito-verified email from `T.users`? The current design matches the existing `audit_event` fanout path (`alerts.py:669`). Resolution: accepted for CAS-004; a follow-up ticket can add Cognito fallback.

2. **Per-event opt-out for transactional CRM emails** — some deployments may want to allow submitters to silence `ticket_replied` transactional emails. CAS-004 sends unconditionally when the flag is on. A future ticket can add a `crm_cases_email_optout` field to alert prefs. Deferred.

3. **Watcher recipients in `_emit_ticket_alerts`** — the existing `_emit_ticket_alerts` call site for `ticket_replied` (tickets.py:978) passes `recipients=[ticket["owner_sub"]]` or `[assigned_admin_sub]`. CAS-007 (watchers) will extend this to include watcher subs. CAS-004 does not change the recipient list; it only forwards whatever is passed. This is correct — CAS-007 owns the watcher expansion.

4. **`ticket_csat_sent` email dedup** — CAS-016 (`send_csat_survey`) sends a CSAT survey link via `send_alert_email` itself. If CAS-016 also calls `_emit_ticket_alerts("ticket_csat_sent", ...)`, the transactional path would send a second email. CAS-016 must either: (a) not call `_emit_ticket_alerts` for `ticket_csat_sent` and send its own email, or (b) call `_emit_ticket_alerts` and rely on CAS-004 transactional dispatch, suppressing its own direct send. Design decision deferred to CAS-016.

5. **HTML rendering in SES sandbox** — the AWS SES sandbox may reject HTML with certain patterns. The template uses only inline styles and no external URLs, which is safe for SES sandbox.
