## 1. Summary & Goal

PRJ-003 introduces `CrmProjectTask`, the core work-item entity in the CRM project management system. A task belongs to exactly one CRM project (established in PRJ-002) and carries the fields SuiteCRM supports for Gantt-compatible project management: a human name and optional description, an integer ordering position, duration in calendar days, optional start and end dates (with auto-derivation of end from start + duration), a percent-complete tracking field (0–100), a milestone flag (consumed by PRJ-005 and the Gantt component in PRJ-008), an optional assignee (consumed by PRJ-004), and a list of predecessor task IDs for dependency tracking (also consumed by PRJ-004).

The deliverables are:

1. `CrmProjectTaskModel` Pydantic model and associated request/response models in `app/models.py`.
2. Service module `app/services/crm_project_tasks.py` implementing full CRUD plus a reorder operation.
3. Six route handlers added to the existing `app/routers/crm_projects.py` (introduced in PRJ-002) under the path prefix `/v1/crm/projects/{project_id}/tasks`.
4. TypeScript types and API endpoint wrappers in the frontend (consumed fully by PRJ-012).

All behavior is gated behind `S.crm_projects_enabled` (introduced in PRJ-001, default `False`). With the flag off, the platform is byte-for-byte unchanged.

## 3. Data Model

### DynamoDB table: `crm_pm_tasks`

Table handle: `T.crm_pm_tasks` (wired via `_safe_table(S.crm_pm_tasks_table_name)` — declared in PRJ-001).

**Primary key layout:**

```
PK  = "PROJECT#{project_id}"            ← all tasks for a project share the same PK
SK  = "TASK#{task_order:06d}#{task_id}" ← zero-padded 6-digit order enables lexicographic
                                           sort directly from DynamoDB (ScanIndexForward=True)
```

The zero-padded `task_order` prefix in the SK is critical: DynamoDB lexicographic ordering on the SK means `TASK#000001#<id>` sorts before `TASK#000002#<id>` without any post-sort step. The padding of 6 digits allows orders up to 999,999 tasks per project before the sort degrades; practical upper bound is far lower.

**GSI1 — single-task lookup by task ID:**

```
GSI1PK = "TASK#{task_id}"
GSI1SK = "PROJECT#{project_id}"
```

Used by `get_task` and `update_task` to locate a task by its ID alone (without knowing `project_id`), and by PRJ-004 dependency validation to confirm a predecessor lives in the same project.

**GSI2 — per-assignee workload view:**

```
GSI2PK = "ASSIGNEE#{assigned_user_sub}"   (or "ASSIGNEE#unassigned" when null)
GSI2SK = end_date (integer Unix seconds, or 0 when absent)
attr_types = {"GSI2SK": "N"}               ← MUST be declared; omitting causes ValidationException
```

Used by PRJ-004's `get_project_workload` to count tasks per assignee and identify overdue tasks without a full-table scan.

**Full item shape:**

```
PK                  = "PROJECT#{project_id}"
SK                  = "TASK#{task_order:06d}#{task_id}"
GSI1PK              = "TASK#{task_id}"
GSI1SK              = "PROJECT#{project_id}"
GSI2PK              = "ASSIGNEE#{assigned_user_sub}"  | "ASSIGNEE#unassigned"
GSI2SK              = end_date (int)                  | 0
entity_type         = "crm_task"
task_id             = str (uuid4 hex)
project_id          = str
owner_sub           = str  (denormalized for authorization checks without a project lookup)
name                = str
description         = str | absent
task_order          = int
duration_days       = int  (≥1)
start_date          = int | absent
end_date            = int | absent
percent_complete    = int  (0–100)
is_milestone        = bool (default False)
assigned_user_sub   = str | absent
predecessor_task_ids = list[str]  (default [])
created_at          = int
updated_at          = int
```

All absent/null fields are **omitted from the DDB item** (DynamoDB cannot store None as a GSI key; the `_item_to_task` projection uses `.get()` with defaults).

## 4. API / Service Design

### Service module: `app/services/crm_project_tasks.py`

All functions import `T` from `app.core.tables`, `S` from `app.core.settings`, `now_ts` from `app.core.time`, and `audit_event` from `app.services.alerts`. They do **not** import anything from `app.routers` (no circular dependency).

#### `_task_pk(project_id: str) -> str`
Returns `f"PROJECT#{project_id}"`.

#### `_task_sk(task_order: int, task_id: str) -> str`
Returns `f"TASK#{task_order:06d}#{task_id}"`.

#### `_item_to_task(item: Dict[str, Any]) -> CrmProjectTaskModel`
Projects the DDB item dict onto `CrmProjectTaskModel`, coercing `Decimal` numeric fields to `int` (DynamoDB Local and moto return `Decimal` for all numeric attributes). Uses `.get()` with safe defaults for optional fields.

#### `_task_to_item(task: CrmProjectTaskModel) -> Dict[str, Any]`
Builds the full DDB item including GSI keys. Omits keys whose value is `None` (filter via dict comprehension `{k: v for k, v in d.items() if v is not None}`) to avoid writing DynamoDB null attributes to GSI key fields.

#### `_max_task_order(project_id: str) -> int`
Queries `PK=PROJECT#{project_id}` with `SK begins_with("TASK#")`, `ScanIndexForward=False`, `Limit=1` to get the highest existing SK. Parses the zero-padded order from `SK.split("#")[1]`. Returns 0 if no tasks exist.

#### `create_task(owner_sub, project_id, name, *, task_order, duration_days, start_date, description, assigned_user_sub, is_milestone, percent_complete, predecessor_task_ids) -> CrmProjectTaskModel`

1. Calls `get_crm_project(owner_sub, project_id)` from `app.services.crm_projects` — raises 404 if the project does not exist or is not owned by `owner_sub`.
2. If `task_order == 0`, calls `_max_task_order(project_id) + 1` to auto-assign.
3. Derives `end_date = start_date + duration_days * 86400` when `start_date` is provided and `end_date` is absent.
4. Generates `task_id = uuid4().hex`.
5. Sets `created_at = updated_at = now_ts()`.
6. Calls `T.crm_pm_tasks.put_item(Item=_task_to_item(task), ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)")`.
7. Returns the constructed `CrmProjectTaskModel`.

No audit event is emitted on create (reversible, low-risk). Task deletion does emit an audit event.

#### `get_task(owner_sub, task_id) -> CrmProjectTaskModel`

1. Queries `GSI1` with `GSI1PK="TASK#{task_id}"`, `Limit=1`.
2. If no item or `entity_type != "crm_task"`, raises `HTTPException(404)`.
3. Checks `item["owner_sub"] == owner_sub` (ownership via denormalized field); raises 403 if mismatch.
4. Returns `_item_to_task(item)`.

The GSI1 lookup avoids needing the caller to supply `project_id` for every single-task operation.

#### `list_tasks(owner_sub, project_id, *, limit=50, cursor=None) -> Dict[str, Any]`

1. Calls `get_crm_project(owner_sub, project_id)` for authorization.
2. Queries `PK=PROJECT#{project_id}` + `SK begins_with("TASK#")`, `ScanIndexForward=True` (ascending order by zero-padded SK), `Limit=min(limit, 200)`.
3. Loops via `LastEvaluatedKey` until `limit` items collected or no more pages — consistent with the DDB `FilterExpression` pagination note in CLAUDE.md.
4. Decodes `cursor` via `decode_cursor` from `app.core.cursor`; encodes response cursor via `encode_cursor`.
5. Returns `{"items": [CrmProjectTaskModel, ...], "cursor": Optional[str]}`.

#### `update_task(owner_sub, task_id, *, name, description, task_order, duration_days, start_date, end_date, percent_complete, is_milestone, assigned_user_sub, predecessor_task_ids) -> CrmProjectTaskModel`

1. Fetches the existing task via `get_task(owner_sub, task_id)`.
2. Merges provided fields (skips `None` sentinel values — distinguishes "not provided" from explicit `null` via `Optional` with `None` default).
3. Re-derives `end_date` if `start_date` or `duration_days` changed and `end_date` was not explicitly set in this request: `end_date = start_date + duration_days * 86400`.
4. If `task_order` changed: deletes the old item (old SK) and writes the new item (new SK) in a single `transact_write_items` call to avoid a window where neither SK exists — this is critical because the SK encodes the order.
5. Updates `updated_at = now_ts()`.
6. If `percent_complete` transitions to 100 and was previously < 100: calls `audit_event("crm_task.completed", owner_sub, None, task_id=task_id, project_id=existing.project_id)`.
7. Returns the merged `CrmProjectTaskModel`.

**SK rewrite detail for `task_order` change:** The old SK `TASK#{old_order:06d}#{task_id}` and new SK `TASK#{new_order:06d}#{task_id}` are different strings, so a standard `update_item` on the primary key cannot change the SK. The implementation uses `TransactWriteItems` with a `Delete` on the old key and a `Put` (with `ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)"`) for the new key. If the new SK already exists (collision), the transaction fails with `TransactionCanceledException` → raise `HTTPException(409, "task_order_conflict")`.

#### `delete_task(owner_sub, task_id) -> Dict[str, bool]`

1. Fetches task via `get_task(owner_sub, task_id)` (authorization check).
2. `T.crm_pm_tasks.delete_item(Key={"PK": _task_pk(task.project_id), "SK": _task_sk(task.task_order, task.id)}, ConditionExpression="attribute_exists(PK) AND attribute_exists(SK)")`.
3. Calls `audit_event("crm_task.deleted", owner_sub, None, task_id=task_id, project_id=task.project_id, name=task.name)`.
4. Returns `{"ok": True}`.

#### `reorder_tasks(owner_sub, project_id, task_ids: List[str]) -> List[CrmProjectTaskModel]`

Accepts an ordered list of task IDs representing the desired display order. Rewrites each task's SK to reflect the new `task_order`.

1. Authorizes via `get_crm_project(owner_sub, project_id)`.
2. Fetches all current tasks via `list_tasks` (accumulates across all pages to build a complete in-memory map `{task_id: CrmProjectTaskModel}`).
3. Validates that `set(task_ids) == set(existing task IDs)` — returns `HTTPException(400, "reorder_task_ids_mismatch")` if the sets differ (prevents accidental task deletion or duplication via reorder).
4. For each `(new_index, task_id)` pair where `new_index + 1 != existing.task_order`, builds a `TransactWriteItems` batch:
   - `Delete` of old SK.
   - `Put` of new SK with `task_order = new_index + 1`.
   - DynamoDB `TransactWriteItems` accepts up to 100 items per call; if the project has >50 tasks being reordered, split into sequential batches of 50 (25 Delete + 25 Put pairs per transaction).
5. Returns the fully updated task list in new order.

## 5. Detailed Behavior & Edge Cases

### Auto-order assignment

When `task_order = 0` (the default), the service computes `_max_task_order(project_id) + 1`. If the project has no tasks yet, `_max_task_order` returns 0, making the first task's order 1. This avoids `task_order=0` ever appearing in a persisted SK, keeping the lexicographic sort unambiguous (`TASK#000001#` is unambiguously the minimum).

If a caller explicitly supplies `task_order=5` on a project that already has a task at order 5, the `put_item` condition `attribute_not_exists(SK)` will succeed only if the SK for that `task_id` is new — the SK includes the task ID, so two different tasks can share the same `task_order` value and co-exist in the table. In this case, both tasks get the same numeric `task_order` stored on the item but different SKs; the list will return both at adjacent positions (DynamoDB SK sort preserves `TASK#000005#<id_a>` before `TASK#000005#<id_b>` where `id_a < id_b` lexicographically). This is acceptable: the UI-level reorder operation is the canonical way to enforce strict uniqueness of order values. Documentation of this behavior is provided in the OpenAPI description.

### End-date derivation rules

`end_date` is computed from `start_date + duration_days * 86400` when:
- `start_date` is provided and `end_date` is absent in the request body.

`end_date` is **not** recomputed when:
- `end_date` is explicitly set in the request (PATCH) — the caller's explicit value wins.
- `start_date` is absent (no anchor) — `end_date` remains `None`.

On PATCH, if the caller updates `duration_days` but not `start_date` or `end_date`, the service recomputes `end_date` only if `task.start_date` is already set. If `start_date` is not yet set, `duration_days` is just stored and `end_date` remains unset.

|---|---|---|
| `name` | 1–200 chars (Pydantic) | 422 |
| `description` | ≤2000 chars (Pydantic) | 422 |

| `task_id` not owned by caller | `get_task` ownership check | 403 |

### Reorder atomicity

The `reorder_tasks` function issues `TransactWriteItems` calls. DynamoDB transactions are atomic — if any item in a batch fails (e.g., a `ConditionalCheckFailed` on a `Put`), the entire batch is rolled back. This means a partial reorder cannot occur. If the project has more than 50 tasks requiring SK rewrites, the function issues multiple sequential transactions. Between transactions there is a brief window of inconsistency; this is acceptable for a project management system where millisecond consistency is not required. The function does not hold a distributed lock.

### Cascade behavior on project deletion

`delete_crm_project` (PRJ-002) must cascade to task rows. It queries `PK=PROJECT#{project_id}` with `SK begins_with("TASK#")` and batch-deletes all matching items using `batch_write_item`. PRJ-003 documents this dependency but does not own the `delete_crm_project` function — that function is implemented in `app/services/crm_projects.py` (PRJ-002). PRJ-003 should note the expected behavior in comments in the task service so PRJ-002's implementer knows to perform the cascade.


`_require_crm_projects` is a zero-argument function defined in `app/routers/crm_projects.py` (PRJ-001). It does not use `Depends()` — it is a plain function call at the top of each handler body.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

All DDB operations in `app/services/crm_project_tasks.py` go through `T.crm_pm_tasks` — the same `_safe_table` handle used in dev (moto in-process, started by `app/core/dev_s3.py` at app startup) and in prod (real DynamoDB endpoint). There are **no** `if S.dev_mode:` branches in the task service. The `crm_pm_tasks` table is created by `scripts/local-ddb-init.py` in dev exactly as it would be created by an `aws dynamodb create-table` call in prod. SECOPS-007 parity is satisfied.

`send_alert_email` (`app/services/alerts.py:459`) already has an internal dev/prod branch (dev writes to a log file; prod calls SES via boto3) — PRJ-003 does not call `send_alert_email` directly; that is PRJ-009's concern. PRJ-003's only notification primitive is `audit_event`, which is a single DDB `put_item` with no dev/prod branch.

### Idempotency

`create_task` uses `ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)"`. Because the SK encodes a randomly generated `task_id` (uuid4 hex), the probability of a collision is negligible. If a caller retries a failed `create_task` request, a new `task_id` is generated, so the operation is not idempotent by design — this is consistent with the platform's pattern for create operations (same as `create_project` in `app/services/projects_store.py:112`).

`update_task` is idempotent: repeating the same PATCH with the same field values produces the same DDB item. The SK rewrite path uses `TransactWriteItems` with a conditional `Put` — if the new SK already points to the same `task_id`, the condition `attribute_not_exists(SK)` would fail. To handle this edge case (updating `task_order` to the same value it already has), the service short-circuits the SK rewrite when `new_order == existing.task_order`.

### Security

- **Authorization**: Every read/write operation verifies `item["owner_sub"] == caller_sub`. Ownership is denormalized onto each task item at creation time, so a single `get_item` is sufficient for authorization without a separate project lookup (which would be a second DDB call). The denormalized `owner_sub` is never surfaced in update requests — it can only be set at creation time.
- **Path parameter / body divergence**: The `project_id` in the URL path and the `project_id` stored on the task item are authoritative independently. The route handler passes the URL `project_id` to the service. The service queries GSI1 by `task_id` and then validates that `item["GSI1SK"] == f"PROJECT#{project_id}"` to prevent cross-project task enumeration (a caller who knows a `task_id` from project A cannot use it in a request scoped to project B).
- **Input size limits**: All string fields have `max_length` constraints enforced by Pydantic at the HTTP boundary. `predecessor_task_ids` lists are not length-limited by Pydantic but `create_task` / `update_task` validate that each ID is a non-empty string; PRJ-004 adds the cross-project membership validation.

## 8. Backward Compatibility & Migration

### No migration required

PRJ-003 adds a **new DDB table** (`crm_pm_tasks`) and a **new router** (`/v1/crm/projects/{project_id}/tasks`). No existing table schema is altered. No existing endpoint is modified. The existing file-grouping `projects` table and its router are unchanged.

### Forward compatibility for PRJ-004, PRJ-005, PRJ-007, PRJ-008

The task model is designed to carry PRJ-004 fields (`predecessor_task_ids`, `assigned_user_sub`) from day one with sensible defaults (empty list, absent). PRJ-004 adds validation logic to these fields but does not need a schema migration — the fields are already present and stored.

`is_milestone` defaults to `False` and is stored on every new item. PRJ-005 adds the `milestones_only` query filter and a summary endpoint but does not change the item shape.

PRJ-007 (team members and access control) changes the authorization model from owner-only to role-based. The `owner_sub` denormalized field on task items allows PRJ-007's `_assert_project_access` helper to determine whether a non-owner caller is authorized via the members table without changing the task item structure.

### Stack startup

Adding the `crm_pm_tasks` `TableDef` to `scripts/local-ddb-init.py` means `just restart` (which calls `local-ddb-init.py`) creates the table automatically. No manual `aws dynamodb create-table` is needed in dev. In prod, the table must be provisioned before the new code is deployed; PRJ-001's scope covers confirming this sequencing.

17. **delete_task**: Delete task; assert `get_task` raises 404; assert `T.alerts` has `event="crm_task.deleted"`.
18. **delete_task wrong owner**: Delete task owned by user A as user B; assert `403`.

## 10. Open Questions / Assumptions

1. **`task_order` uniqueness enforcement**: This spec allows two tasks to have the same `task_order` value (different SKs because task IDs differ). The reorder endpoint is the canonical tool for strict uniqueness. An alternative is to enforce unique `task_order` per project by adding a conditional expression that checks no existing SK has the same order prefix — but this would require an extra query per create/update. Current assumption: soft uniqueness is acceptable; UI uses drag-reorder which always emits a full ordered list.

2. **TransactWriteItems batch size for large reorders**: The spec caps at 25 Delete + 25 Put pairs per transaction (50 total items, within DynamoDB's 100-item limit). For projects with >50 tasks all being reordered simultaneously, multiple sequential transactions are issued. Assumption: projects rarely exceed 50 tasks; this is acceptable. If needed, a future ticket can introduce an optimistic concurrency token.

3. **Cascade delete scope**: PRJ-003 documents that `delete_crm_project` (PRJ-002) should cascade to task rows. PRJ-003 does not own that function. Assumption: PRJ-002's implementer reads this spec and implements the cascade. A separate integration test in PRJ-002 should cover this.

4. **`project_id` path parameter validation against task ownership**: The spec validates that the task's stored `GSI1SK` matches the URL `project_id`. This adds one comparison after the GSI1 lookup. Assumption: this is the correct security posture; the alternative (trusting only the task_id) would allow a caller to use any project_id in the path when they know the task_id.

5. **Soft delete vs. hard delete for tasks**: This spec uses hard delete (immediate `delete_item`). SuiteCRM supports soft-delete (trash bin). A future PRJ ticket could add a `deleted_at` attribute and a `GET /tasks?include_deleted=true` filter. Assumption: hard delete is sufficient for the initial implementation.
