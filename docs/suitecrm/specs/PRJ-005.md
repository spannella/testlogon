# PRJ-005 — Project milestones

**Ticket type:** Feature
**Priority:** P2
**Estimate:** 1d
**Area:** CRM Projects, Project Tasks & Gantt
**Source:** `docs/suitecrm/CRM_PROJECTS_GANTT_TICKETS.md` § "PRJ-005"

---

## 1. Summary & Goal

PRJ-005 wires the milestone semantics for CRM project tasks. The `is_milestone: bool` field was introduced in PRJ-003 on `CrmProjectTaskModel` (default `False`) and is already stored on every task item in `T.crm_pm_tasks`. This ticket does not touch the data model — it adds the **query filter**, the **summary endpoint**, the **frontend badge**, and the **Gantt prerequisite contract** that downstream PRJ-008 depends on.

Specifically, the four deliverables are:

1. **API filter** — `GET /v1/crm/projects/{project_id}/tasks?milestones_only=true` filters the existing `list_tasks` response to items where `is_milestone=True`.
2. **Milestone summary endpoint** — `GET /v1/crm/projects/{project_id}/milestones` returns each milestone task enriched with computed `on_track` / `overdue` boolean fields derived from `end_date` and `percent_complete` relative to `now_ts()`.
3. **Frontend task-row badge** — The `CrmTaskRow` component (introduced in PRJ-012 but designed here) renders a diamond icon beside the task name when `is_milestone=True`, using `Milestone` from `lucide-react`.
4. **Gantt diamond marker contract** — The milestone flag is already surfaced in the tasks API; PRJ-008 reads `is_milestone` to set `type: "milestone"` in the `gantt-task-react` task shape. PRJ-005 makes this contract explicit and documents the expected field behavior.

All new behavior is gated behind `S.crm_projects_enabled` (env `CRM_PROJECTS_ENABLED`, default `"0"`, introduced in PRJ-001). With the flag off, the platform is byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 Existing file-grouping `projects` surface — not touched

`app/services/projects_store.py` owns the `projects` table (file-grouping layer). Its `ProjectModel` at `app/models.py:1796` carries only `id`, `owner`, `name`, `description`, `tags`, `settings`, `created_at`, `updated_at`. It has no concept of tasks or milestones. The router `app/routers/projects.py` (prefix `/v1/projects`, registered in `app/main.py`) is never modified by any PRJ ticket. The CRM project management system is an entirely separate surface — PRJ-002 introduces `T.crm_pm_projects` and `app/routers/crm_projects.py`; PRJ-003 introduces `T.crm_pm_tasks` and `app/services/crm_project_tasks.py`.

### 2.2 Task model and storage — PRJ-003 prerequisite

PRJ-003's `CrmProjectTaskModel` (added to `app/models.py` after `CrmProjectModel`) carries:

```python
is_milestone: bool = False
end_date: Optional[int] = None   # Unix ts, auto-derived from start_date + duration_days * 86400
percent_complete: int             # 0–100
```

Items are stored in `T.crm_pm_tasks` with:
- `PK = "PROJECT#{project_id}"`
- `SK = "TASK#{task_order:06d}#{task_id}"` — lexicographic ascending order

`is_milestone`, `end_date`, and `percent_complete` are regular DDB attributes on the item (not GSI keys), so filtering on them requires a `FilterExpression` applied after the `KeyConditionExpression` page fetch. The CLAUDE.md note "DDB FilterExpression doesn't reduce page size" means the pagination loop must continue via `LastEvaluatedKey` even when a page yields zero milestone items — see Section 5 for the loop pattern.

`list_tasks(owner_sub, project_id, *, limit, cursor)` in `app/services/crm_project_tasks.py` already queries `PK=PROJECT#{project_id}` with `ScanIndexForward=True` and loops via `LastEvaluatedKey`. PRJ-005 adds an optional `milestones_only: bool = False` parameter to this function; when `True`, a `FilterExpression=Attr("is_milestone").eq(True)` is appended.

### 2.3 Auth and session primitives

`require_ui_session` in `app/services/sessions.py:330` returns `{"user_sub": str, "role": Role, "admin_profile": ..., ...}`. All PRJ route handlers use `Depends(require_ui_session)` following the pattern at `app/routers/projects.py:169`. PRJ-007 (team members) extends the authorization model; until PRJ-007 ships, all task read operations verify `owner_sub == caller_sub` via `get_crm_project(owner_sub, project_id)` in the PRJ-003 service (which raises 404 for non-owners). PRJ-005 inherits this constraint — milestones are readable only by the project owner until PRJ-007 ships.

### 2.4 Timestamp convention

`app/core/time.now_ts()` returns `int(time.time())` — integer Unix seconds — as confirmed at `app/core/time.py:2–3`. The `on_track` / `overdue` computation uses this integer directly: `overdue = (task.end_date is not None) and (task.end_date <= now_ts()) and (task.percent_complete < 100)`.

### 2.5 Audit primitive

`audit_event(event, user_sub, request=None, **fields)` at `app/services/alerts.py:644` writes an audit row to `T.alerts` (via `write_alert`). PRJ-005 calls `audit_event("crm_milestone.summary_viewed", ...)` on each call to the summary endpoint so that milestone progress checks are auditable. This mirrors the PRJ-003 pattern of emitting audit events for significant read/write operations. NOTE (verified `app/services/alerts.py:356-431`): on the persisted item, `event`/`user_sub`/`alert_id` are top-level attributes but the `**fields` (e.g. `project_id`, `page_size`) are nested under the `details` map — tests must assert on `item["details"]["project_id"]`, not a top-level `project_id`. (§2.5 originally cited the event name `crm_milestone.overdue_summary_viewed`; §4.1/§7.3 use `crm_milestone.summary_viewed` — the latter is canonical.)

### 2.6 Pagination primitives

`encode_cursor` and `decode_cursor` at `app/core/cursor.py:94` and `app/core/cursor.py:103` provide HMAC-signed opaque pagination cursors. The milestones summary endpoint also supports cursor-based pagination in case a project has many milestone tasks.

### 2.7 Feature flag guard

`_require_crm_projects()` is a zero-argument helper defined in `app/routers/crm_projects.py` (introduced in PRJ-001) that raises `HTTPException(status_code=404)` when `S.crm_projects_enabled` is `False`. Every route handler added in this ticket calls `_require_crm_projects()` as its first statement.

### 2.8 Frontend component context

`lucide-react` is already in `frontend/package.json` (used throughout the existing UI — e.g., `FolderOpen` in messaging, `FolderKanban` referenced in PRJ-012's sidebar plan). The `Milestone` icon from that package is a diamond shape, matching SuiteCRM's convention for rendering milestone tasks as diamonds on a Gantt chart. The `CrmTaskRow` component described in this spec is the row renderer in PRJ-012's Tasks tab; PRJ-005 defines its milestone badge behavior.

## 3. Data Model

### No new DDB table or schema change

PRJ-005 requires no new DynamoDB table and no new index. The `is_milestone` field is already stored as a regular boolean attribute on task items in `T.crm_pm_tasks` (PRJ-003). The `end_date` and `percent_complete` fields are also already stored as attributes on the same item.

The milestone summary response is a **derived view** computed in the service layer from existing task item fields — it is not persisted anywhere. The `on_track` and `overdue` booleans are computed at request time from `now_ts()` and never written back to DDB.

### New Pydantic response model (add to `app/models.py` after `CrmProjectTaskModel`)

```python
class CrmMilestoneSummaryItem(BaseModel):
    """Single milestone task entry as returned by GET /{project_id}/milestones."""
    id: str
    project_id: str
    name: str
    task_order: int
    start_date: Optional[int] = None
    end_date: Optional[int] = None
    percent_complete: int
    on_track: bool
    overdue: bool
    created_at: int
    updated_at: int

class CrmMilestoneSummaryResp(BaseModel):
    items: List[CrmMilestoneSummaryItem]
    cursor: Optional[str] = None
    total_milestones: int
    overdue_count: int
    on_track_count: int
    no_date_count: int  # milestones with no end_date (cannot determine status)
```

The `total_milestones`, `overdue_count`, `on_track_count`, and `no_date_count` summary counters cover the **current page only** when pagination is in use. This is consistent with the platform's pattern (no separate aggregate queries). If the caller wants full-project counters, they paginate to exhaustion.

### `TableDef` additions

None. All relevant attributes are already on the PRJ-003 `crm_pm_tasks` table (with `attr_types={"GSI2SK": "N"}` for the numeric `end_date` GSI2 sort key). PRJ-005 does not touch `scripts/local-ddb-init.py`.

## 4. API / Service Design

### 4.1 Service changes: `app/services/crm_project_tasks.py`

#### `list_tasks` — extended signature

```python
def list_tasks(
    owner_sub: str,
    project_id: str,
    *,
    limit: int = 50,
    cursor: Optional[Dict[str, Any]] = None,
    milestones_only: bool = False,
) -> Dict[str, Any]:
```

When `milestones_only=True`, the DDB query adds:

```python
from boto3.dynamodb.conditions import Attr
kwargs["FilterExpression"] = Attr("is_milestone").eq(True)
```

The function already loops via `LastEvaluatedKey` to collect `limit` matching items. With `milestones_only=True`, pages that yield zero milestone items after the `FilterExpression` pass do not break the loop — iteration continues until `limit` items are found or no more pages remain. This correctly handles sparse milestone distributions (CLAUDE.md: "DDB FilterExpression doesn't reduce page size").

The return shape is unchanged: `{"items": List[CrmProjectTaskModel], "cursor": Optional[str]}`.

#### New function: `get_milestone_summary`

```python
def get_milestone_summary(
    owner_sub: str,
    project_id: str,
    *,
    limit: int = 50,
    cursor: Optional[Dict[str, Any]] = None,
) -> Dict[str, Any]:
```

1. Calls `get_crm_project(owner_sub, project_id)` from `app.services.crm_projects` — raises 404 if not found, 403 (via PRJ-007's `_assert_project_access` when that ships) if not a member.
2. Calls `list_tasks(owner_sub, project_id, limit=limit, cursor=cursor, milestones_only=True)` to fetch the milestone page.
3. For each returned `CrmProjectTaskModel`, computes:
   ```python
   ts_now = now_ts()
   has_end_date = task.end_date is not None
   on_track = has_end_date and (task.end_date > ts_now)
   overdue = has_end_date and (task.end_date <= ts_now) and (task.percent_complete < 100)
   no_date = not has_end_date
   ```
   Note: a completed milestone (`percent_complete == 100`) is neither `on_track` nor `overdue` regardless of date — it is simply done. The `on_track` flag is only meaningful while the milestone is incomplete (`percent_complete < 100`).
4. Builds `CrmMilestoneSummaryItem` for each task.
5. Computes per-page aggregate counters.
6. Emits `audit_event("crm_milestone.summary_viewed", owner_sub, None, project_id=project_id, page_size=len(items))` — best-effort, wrapped in try/except so an audit failure never blocks the response.
7. Returns `{"items": [...], "cursor": str|None, "total_milestones": int, "overdue_count": int, "on_track_count": int, "no_date_count": int}`.

**Completion semantics:** A milestone with `percent_complete == 100` is considered complete. The summary intentionally does not set `on_track=True` or `overdue=True` for completed milestones — a completed milestone that is past its `end_date` is not "overdue" because the work is done. Callers who want to display completed milestones separately should filter on `percent_complete == 100` client-side.

### 4.2 Router additions to `app/routers/crm_projects.py`

#### Modified route: `GET /v1/crm/projects/{project_id}/tasks`

Add a `milestones_only: bool = Query(default=False)` parameter:

```python
@router.get("/{project_id}/tasks", response_model=CrmProjectTaskListResp)
def list_tasks_route(
    project_id: str,
    limit: int = Query(50, ge=1, le=200),
    cursor: Optional[str] = Query(default=None),

    ctx: Dict = Depends(require_ui_session),

    result = list_tasks(owner_sub, project_id, limit=limit, cursor=decoded_cursor, milestones_only=milestones_only)
    return CrmProjectTaskListResp(
        items=result["items"],
        cursor=encode_cursor(result.get("cursor")),
    )
```

This is a **non-breaking extension** of the existing route (new optional query parameter with a default that preserves existing behavior).

#### New route: `GET /v1/crm/projects/{project_id}/milestones`

```python
@router.get("/{project_id}/milestones", response_model=CrmMilestoneSummaryResp)
def get_milestone_summary_route(
    project_id: str,
    limit: int = Query(50, ge=1, le=200),
    cursor: Optional[str] = Query(default=None),
    ctx: Dict = Depends(require_ui_session),
):
    _require_crm_projects()
    owner_sub = ctx["user_sub"]
    decoded_cursor = decode_cursor(cursor)
    result = get_milestone_summary(owner_sub, project_id, limit=limit, cursor=decoded_cursor)
    return CrmMilestoneSummaryResp(**result)
```

**Route declaration order:** `GET /{project_id}/milestones` must be declared **before** any `/{project_id}/{task_id}`-style catch-all routes in the router file. In `app/routers/crm_projects.py`, the routes are ordered: fixed-suffix routes first, then parameterized sub-resource routes. This prevents FastAPI from matching the literal `milestones` as a `task_id` path parameter. This is the same ordering discipline documented in CLAUDE.md for `/schedules` routes (PRJ-001 cross-cutting constraint).

## 5. Detailed Behavior & Edge Cases

### 5.1 FilterExpression pagination loop (milestones_only)

The core pagination challenge is that `FilterExpression` on `is_milestone` is applied **server-side by DynamoDB after fetching up to 1 MB per page**, so a page of 100 tasks with 0 milestones returns an empty `Items` list but a non-empty `LastEvaluatedKey`. The loop in `list_tasks` must not stop when `Items` is empty for a given page:

```python
while len(items) < limit:
    kwargs = {
        "KeyConditionExpression": Key("PK").eq(f"PROJECT#{project_id}")
            & Key("SK").begins_with("TASK#"),
        "Limit": max(limit * 3, 50),   # over-fetch to reduce round trips for sparse milestones
        "ScanIndexForward": True,
    }
    if milestones_only:
        kwargs["FilterExpression"] = Attr("is_milestone").eq(True)
    if last_key:
        kwargs["ExclusiveStartKey"] = last_key
    resp = T.crm_pm_tasks.query(**kwargs)
    for raw in resp.get("Items", []):
        if raw.get("entity_type") != "crm_task":
            continue
        items.append(_item_to_task(raw))
        if len(items) >= limit:
            break
    last_key = resp.get("LastEvaluatedKey")
    if not last_key:
        break
```

The `Limit` is intentionally set higher than `limit` (e.g., `limit * 3`) when `milestones_only=True` to reduce the number of round trips when milestones are sparse (e.g., 5 milestones among 300 tasks). The multiplier `3` is a reasonable heuristic with no hardcoded assumption; it can be tuned via a `_MILESTONE_SCAN_MULTIPLIER = 3` module constant.

### 5.2 Milestone status computation rules

| `end_date` | `percent_complete` | `on_track` | `overdue` |
|---|---|---|---|
| `None` | any | `False` | `False` |
| > `now_ts()` | 0–99 | `True` | `False` |
| > `now_ts()` | 100 | `False` | `False` |
| <= `now_ts()` | 0–99 | `False` | `True` |
| <= `now_ts()` | 100 | `False` | `False` |

A milestone with `percent_complete=100` is considered **complete** regardless of date. Neither `on_track` nor `overdue` is set for completed milestones. The `no_date` counter (in the summary resp) increments for any milestone where `end_date is None`.

### 5.3 Edge case: empty project

If the project has no tasks at all (or no milestone tasks), `get_milestone_summary` returns:
```json
{
  "items": [],
  "cursor": null,
  "total_milestones": 0,
  "overdue_count": 0,
  "on_track_count": 0,
  "no_date_count": 0
}
```
This is not an error. The response is HTTP 200.

### 5.4 Edge case: `end_date` exactly equals `now_ts()`

The comparison uses `<=`: `overdue = end_date <= now_ts()`. A milestone whose `end_date` is precisely the current second is considered overdue (not on track). This is consistent with the plain-English meaning of "the deadline has passed."

### 5.5 Edge case: project not found or not owned

`get_crm_project(owner_sub, project_id)` raises `HTTPException(404)` if the project does not exist or does not belong to `owner_sub`. Both the `list_tasks` and `get_milestone_summary` paths call this as their first authorization step. Once PRJ-007 (team members) ships, this check is replaced by `_assert_project_access(caller_sub, project_id, min_role="viewer")`, which allows member/viewer access. PRJ-005 documents this evolution point but does not implement PRJ-007's access model.

### 5.6 Flag off behavior

With `S.crm_projects_enabled=False` (the default):
- `GET /v1/crm/projects/{id}/tasks?milestones_only=true` → `_require_crm_projects()` raises `HTTPException(404)` before any DDB call.
- `GET /v1/crm/projects/{id}/milestones` → same.
- The `milestones_only` parameter extension to `list_tasks` in the service layer is inert — the function is never called from the HTTP layer when the flag is off.
- The `CrmMilestoneSummaryResp` Pydantic model is imported but never instantiated.
- The frontend `getCrmProjectMilestones` call returns a 404 which React Query handles as an error; the consuming component renders an empty state or hides the milestones section.

### 5.7 `milestones_only=false` (default) — backward compatibility

When `milestones_only` is absent or `false`, `list_tasks` is called with `milestones_only=False` (the default). The `FilterExpression` is not added. The DDB query is identical to the PRJ-003 implementation. No existing behavior is changed.

### 5.8 Frontend `CrmTaskRow` milestone badge

`CrmTaskRow` is a single-row component within the Tasks tab table of `CrmProjectDetailPage` (PRJ-012). PRJ-005 defines the milestone-badge behavior that PRJ-012 implements:

```tsx
import { Milestone } from "lucide-react";

// Inside CrmTaskRow, beside the task name cell:
{task.is_milestone && (
  <Milestone
    className="inline-block h-4 w-4 text-amber-500 ml-1 shrink-0"
    aria-label="Milestone"
  />
)}
```

The `Milestone` icon from `lucide-react` renders as a diamond shape. The `text-amber-500` color follows the platform's convention for milestone/warning indicators (same color class used for the calendar booking "upcoming" badge). The icon has an `aria-label` for accessibility.

### 5.9 Gantt diamond marker contract (PRJ-008 prerequisite)

PRJ-008 uses `gantt-task-react` to render the Gantt chart. The library's `Task` type accepts `type: "milestone"` to render a diamond marker. PRJ-005 documents the contract that PRJ-008 must implement:

```typescript
// In CrmProjectGanttPage.tsx (PRJ-008):
const ganttTask = {
  id: task.id,
  name: task.name,
  start: task.start_date ? new Date(task.start_date * 1000) : new Date(),
  end: task.end_date ? new Date(task.end_date * 1000) : new Date(),
  progress: task.percent_complete,
  type: task.is_milestone ? "milestone" : "task",   // ← PRJ-005 contract
  dependencies: task.predecessor_task_ids,
};
```

PRJ-005 does not implement the Gantt component itself — that is PRJ-008's scope. PRJ-005 ensures the `is_milestone` field is correctly surfaced in the task API response and documents the exact mapping.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

All DDB operations go through `T.crm_pm_tasks` — the `_safe_table` handle wired in `app/core/tables.py` (PRJ-001). In dev, moto intercepts boto3 calls in-process (started by `app/core/dev_s3.py` at app startup). In prod, calls go to real DynamoDB via the standard `boto3` resource. There are **no** `if S.dev_mode:` branches in `crm_project_tasks.py` or in the new service function `get_milestone_summary`. The `FilterExpression=Attr("is_milestone").eq(True)` is a standard DynamoDB condition that moto implements correctly — no dev-specific workaround is needed.

`audit_event` (`app/services/alerts.py:644`) writes to `T.alerts` via a single `put_item` with no dev/prod branch; it is already SECOPS-007 compliant.

`send_alert_email` (`app/services/alerts.py:459`) has an internal dev/prod branch (dev writes to a log file; prod calls SES). PRJ-005 does **not** call `send_alert_email` — no email notifications are triggered by milestone queries. Email notifications on milestone status are a future enhancement (out of scope for this ticket).

### 7.2 Idempotency

Both new endpoints are read-only (`GET`). They are inherently idempotent — repeated calls with the same parameters return the same result modulo the passage of time (which affects the `on_track` / `overdue` computation). No state mutations occur. The `audit_event` call in `get_milestone_summary` produces a new audit row on every call; this is intentional (audit log completeness) and consistent with the platform's audit-event pattern.

### 7.3 Security

**Authorization:** Both endpoints call `get_crm_project(owner_sub, project_id)` which enforces that the caller is the project owner. Once PRJ-007 ships, the `_assert_project_access` helper replaces this with role-based checks (minimum role: `viewer`). Until then, non-owners get 404.

**Path parameter injection:** `project_id` from the URL path is used only as a DDB key prefix (`f"PROJECT#{project_id}"`). It is not interpolated into any SQL or shell command. There is no injection risk.

**Response data scope:** `CrmMilestoneSummaryItem` exposes only fields from the task item that the caller already owns. No cross-user data is returned. The `owner_sub` field is **omitted** from `CrmMilestoneSummaryItem` deliberately — it is redundant (the caller is the owner) and reduces the blast radius of any future access-control bug.

**`milestones_only` query parameter:** This is a boolean flag validated by FastAPI's query-parameter parsing. Invalid values (e.g., `?milestones_only=banana`) are rejected with a standard FastAPI 422 Unprocessable Entity response before the handler body executes. No manual validation is needed.

**Audit log:** The `audit_event("crm_milestone.summary_viewed", ...)` call records the caller's `user_sub` and `project_id`. This provides a full audit trail for compliance scenarios where milestone progress reviews are sensitive (e.g., client-facing project status checks).

## 8. Backward Compatibility & Migration

### No DDB schema migration required

PRJ-005 adds no new DynamoDB tables, no new GSIs, and no new required attributes on existing items. The `is_milestone`, `end_date`, and `percent_complete` attributes were written to every task item from PRJ-003 onward (with defaults `False`, `None`, and `0` respectively). Pre-PRJ-005 task items are fully compatible with the PRJ-005 query logic.

### No migration for existing items with missing `is_milestone`

Items written before PRJ-003 shipped (i.e., zero items, since the `crm_pm_tasks` table is a new table created by PRJ-001) do not need backfill. There are no "legacy" task rows that predate the `is_milestone` field.

### `list_tasks` API signature is extended, not replaced

The addition of `milestones_only: bool = False` to `list_tasks` is additive with a default of `False`. All existing callers of `list_tasks` (PRJ-003 CRUD routes, PRJ-006 template creation, PRJ-007 workload queries) pass positional or keyword arguments that do not include `milestones_only`. They are unaffected.

The `GET /v1/crm/projects/{id}/tasks` route gains one optional query parameter. Existing clients that do not send `milestones_only` receive the same response shape as before.

### Frontend non-breaking additions

`listCrmProjectTasks` gains an optional `milestones_only` key in its `params` object. TypeScript callers that omit it receive the same behavior. The new `getCrmProjectMilestones` function and `CrmMilestoneSummaryResp` type are additive; no existing component is required to use them.

### Stack startup

No changes to `scripts/local-ddb-init.py` means `just restart` is unchanged. PRJ-005 does not require a stack restart beyond the normal backend restart to pick up the new code.

## 10. Open Questions / Assumptions

1. **`on_track` semantics for milestones without a start_date**: A milestone may have `end_date` set but no `start_date`. The `on_track` computation uses only `end_date` and `now_ts()` — `start_date` is irrelevant. Assumption: this is correct behavior; a deadline is what makes a milestone trackable, not a start date.

2. **`on_track=True` for a completed milestone**: A milestone with `percent_complete=100` whose `end_date` is in the future technically satisfies the `on_track` formula (`end_date > now_ts()`). However, this spec explicitly sets `on_track=False` for completed milestones (the table in Section 5.2 shows this clearly). Rationale: "on track" implies work still in progress; a completed milestone is simply done. If the frontend wants to show "completed early," it should check `percent_complete == 100` directly.

3. **Summary counters are per-page, not whole-project**: With cursor pagination, `total_milestones` reflects only the current page. If all milestones are needed for a progress bar, the caller must paginate to exhaustion or accept an approximate count. A future improvement could add a separate `GET /{project_id}/milestones/count` endpoint that does a count query with `Select="COUNT"`. Assumption: per-page counters are sufficient for the initial UI.

4. **`audit_event` in `get_milestone_summary` — granularity**: Emitting an audit event on every read is verbose for high-traffic scenarios. Assumption: CRM project milestone reviews are infrequent (human-driven, not machine-polling) and the audit trail value outweighs the storage cost. If this assumption proves wrong, the audit call can be removed in a follow-up ticket without any API or schema changes.

5. **`is_milestone` filter uses `FilterExpression` not GSI**: An alternative design would add a sparse GSI (e.g., `MILESTONE#1` partition key) to enable indexed milestone lookups without a full-table `FilterExpression`. This was rejected because milestones are a small fraction of tasks (SuiteCRM projects typically have 1–5 milestone tasks among dozens of regular tasks) and the `FilterExpression` + over-fetch approach is simpler and avoids a table schema change. If projects routinely have hundreds of tasks with many milestones, a GSI can be added as a follow-up without API or frontend changes.

6. **PRJ-007 integration with milestone endpoints**: Once PRJ-007 (team members) ships and replaces the owner-only check with `_assert_project_access(caller_sub, project_id, min_role="viewer")`, non-owner members will be able to call the milestone summary endpoint. PRJ-005 documents this evolution point but does not implement it — that integration is PRJ-007's responsibility.
