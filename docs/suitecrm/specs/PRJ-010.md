# PRJ-010 — Project-to-Contact relationships

**Ticket type:** Feature
**Priority:** P2
**Estimate:** 1d
**Area:** CRM Projects, Project Tasks & Gantt
**Source:** `docs/suitecrm/CRM_PROJECTS_GANTT_TICKETS.md` § "PRJ-010"

---

## 1. Summary & Goal

PRJ-010 allows a CRM project to be linked to one or more external contact party records. SuiteCRM's Projects module exposes project-to-contact relationships as a subpanel on the project detail view, enabling sales and project managers to track which contacts are stakeholders in a given project without those contacts being team members (the membership roster with platform `user_sub` values is handled separately by PRJ-007).

Because the PTY-001..PTY-015 Party/Contact/Account build-out has not yet shipped, this ticket deliberately uses an opaque `linked_entity_type` + `linked_entity_id` pattern (cross-cutting constraint, `CRM_PROJECTS_GANTT_TICKETS.md:24`). The `linked_entity_id` is an arbitrary caller-supplied string — today a free-form contact ID; once PTY-011 ships the same field will hold a real `party_id`. No migration is needed at that point because the value is opaque and never validated against a foreign table.

The feature is entirely additive. With `CRM_PROJECTS_ENABLED=0` (the default) the platform is byte-for-byte identical to its pre-PRJ-010 state.

### 2.4 `T.crm_pm_members` — reuse for contact links

The `crm_pm_members` table (scaffolded by PRJ-001) uses PK `PROJECT#{project_id}` / SK `MEMBER#{user_sub}`. The ticket specification (`CRM_PROJECTS_GANTT_TICKETS.md:547–554`) directs PRJ-010 to store contact-link rows **in the same table** under a different SK prefix:

```
PK  = "PROJECT#{project_id}"
SK  = "CONTACT_LINK#{linked_entity_id}"
```

This single-table co-location means no new DDB table is required. The SK prefix `CONTACT_LINK#` is disjoint from `MEMBER#` (lexicographic ordering guarantees no collision), and a `begins_with(SK, "CONTACT_LINK#")` KeyConditionExpression isolates link rows cleanly.

### 2.5 Auth primitives

`app/services/sessions.require_ui_session` (`app/services/sessions.py:330`) returns a dict with keys `user_sub`, `role`, `session_id`, `ip`, `tenant_id`. All CRM router handlers extract `ctx["user_sub"]` from this dependency. No platform-level admin role is required for project contact-link operations — the gate is project membership via `_assert_project_access` (PRJ-007), not platform `Role`.

### 2.6 Audit primitive

`app/services/alerts.audit_event` (`app/services/alerts.py:644`) accepts `event: str, user_sub: str, request=None, **fields` and writes an item to `T.alerts`. All mutating operations in this ticket call `audit_event` with `request=None` (no IP/user-agent needed for server-side mutations inside the service layer; callers pass `request` from the router handler).

### 2.7 Cursor pagination

`app/core/cursor.encode_cursor` / `decode_cursor` (`app/core/cursor.py:94, 103`) are the HMAC-signed pagination primitives. `encode_cursor` handles `Decimal` from `LastEvaluatedKey` via `_json_default` (`app/core/cursor.py:12`). The list endpoint uses these.

## 3. Data Model

### 3.1 Table: `crm_pm_members` (existing, introduced by PRJ-001)

No new table is introduced. PRJ-010 writes contact-link rows into `T.crm_pm_members` alongside the member rows already written by PRJ-007.

**Contact-link item layout:**

| Attribute | Value | Type | Notes |
|-----------|-------|------|-------|
| `PK` | `PROJECT#{project_id}` | S | Same partition as member rows |
| `SK` | `CONTACT_LINK#{linked_entity_id}` | S | Distinct prefix from `MEMBER#` |
| `entity_type` | `"crm_contact_link"` | S | Discriminator; differs from `"crm_member"` |
| `project_id` | `{project_id}` | S | Denormalized for convenience |
| `linked_entity_type` | `"contact_party"` | S | Literal; extensible once PTY ships |
| `linked_entity_id` | `{linked_entity_id}` | S | Opaque caller-supplied ID |
| `display_name` | `{display_name}` | S (nullable) | Denormalized label, caller-supplied |
| `added_by` | `{caller_sub}` | S | `user_sub` of the adder |
| `added_at` | `{now_ts()}` | N | Unix timestamp integer from `app/core/time.now_ts()` |

**No new GSI is required.** The list operation queries `T.crm_pm_members` with:

```
KeyConditionExpression = "PK = :pk AND begins_with(SK, :prefix)"
ExpressionAttributeValues = {":pk": "PROJECT#{project_id}", ":prefix": "CONTACT_LINK#"}
```

The reverse lookup (which projects reference a given `linked_entity_id`) is out of scope for this ticket and deferred to PTY integration work. If needed later, a GSI with `GSI2PK = "ENTITY#{linked_entity_id}"` could be added as an additive amendment to `crm_pm_members`.

### 3.2 No `attr_types` addition needed

Both `PK`/`SK` are string keys. `added_at` is stored as a plain item attribute, not a GSI sort key, so the numeric-GSI-sort-key `attr_types` rule (CLAUDE.md "DynamoDB numeric GSI sort keys") does not apply. The `crm_pm_members` `TableDef` in `scripts/local-ddb-init.py` (introduced by PRJ-001) requires no modification.

### 3.3 Pydantic model (add to `app/models.py` after `CrmProjectMemberModel`)

```python
class CrmProjectContactLinkModel(BaseModel):
    project_id:          str
    linked_entity_type:  Literal["contact_party"]
    linked_entity_id:    str
    display_name:        Optional[str] = None
    added_by:            str
    added_at:            int   # Unix timestamp integer (now_ts())
```

Place this model after `CrmProjectMemberModel` (which PRJ-007 adds after `CrmProjectModel`). Keep the `Literal["contact_party"]` type for now; once PTY ships additional entity types (e.g. `"org_party"`) the type union can be widened in a follow-up spec without breaking existing stored data.

## 4. API / Service Design

### 4.1 Service: `app/services/crm_project_links.py` (new file)

All functions import `T` from `app/core/tables`, `now_ts` from `app/core/time`, and `audit_event` from `app/services/alerts`. The flag guard (`_require_crm_projects`) lives in the router — the service layer is flag-agnostic.

#### `add_contact_link(caller_sub, project_id, linked_entity_id, display_name) -> CrmProjectContactLinkModel`

```python
def add_contact_link(
    caller_sub: str,
    project_id: str,
    linked_entity_id: str,
    display_name: Optional[str] = None,
) -> CrmProjectContactLinkModel:
```

1. Local-import `_assert_project_access` from `app.services.crm_project_members`; call it with `min_role=CrmProjectMemberRole.member`. Raises `HTTP 403` if the caller is not at least a project member.
2. Validate `linked_entity_id`: strip whitespace; if empty after strip, raise `HTTPException(400, {"code": "invalid_entity_id"})`.
3. Strip `display_name` if provided; coerce empty string to `None`.
4. Call `T.crm_pm_members.put_item` with the item from `_link_item(...)` and `ConditionExpression="attribute_not_exists(SK)"` to enforce idempotent-safe create. If `ConditionalCheckFailedException` is raised (duplicate), fetch the existing item and return it — same semantics as a 200 on repeat add.
5. Call `audit_event("crm_project.contact_link_added", caller_sub, None, project_id=project_id, linked_entity_id=linked_entity_id)`.
6. Return a `CrmProjectContactLinkModel` constructed from the written item.

---

#### `remove_contact_link(caller_sub, project_id, linked_entity_id) -> dict`

```python
def remove_contact_link(
    caller_sub: str,
    project_id: str,
    linked_entity_id: str,
) -> dict:
```

1. Local-import and call `_assert_project_access(caller_sub, project_id, min_role=CrmProjectMemberRole.member)`.
2. Check that the link exists: `T.crm_pm_members.get_item(Key={"PK": ..., "SK": ...})`. If absent (or `entity_type != "crm_contact_link"`), raise `HTTPException(404, {"code": "contact_link_not_found"})`.
3. Call `T.crm_pm_members.delete_item(Key={"PK": ..., "SK": ...})`.
4. Call `audit_event("crm_project.contact_link_removed", caller_sub, None, project_id=project_id, linked_entity_id=linked_entity_id)`.
5. Return `{"ok": True}`.

---

#### `list_contact_links(caller_sub, project_id, *, limit=100, cursor=None) -> dict`

```python
def list_contact_links(
    caller_sub: str,
    project_id: str,
    *,
    limit: int = 100,
    cursor: Optional[str] = None,
) -> dict:
```

1. Local-import and call `_assert_project_access(caller_sub, project_id, min_role=CrmProjectMemberRole.viewer)`. Viewers can read contact links.
2. Decode `cursor` via `decode_cursor(cursor)` from `app/core/cursor` (`app/core/cursor.py:103`).
3. Query `T.crm_pm_members` with:
   ```python
   KeyConditionExpression=Key("PK").eq(f"PROJECT#{project_id}") & Key("SK").begins_with("CONTACT_LINK#")
   ```
   Pass `Limit=min(limit, 200)` and `ExclusiveStartKey=decoded_cursor` (if non-None). `ScanIndexForward=True`.
4. Filter results where `item.get("entity_type") == "crm_contact_link"` (defensive: prevents member rows from leaking if a cursor lands near the SK boundary).
5. Encode `LastEvaluatedKey` via `encode_cursor(response.get("LastEvaluatedKey"))` from `app/core/cursor.py:94`.
6. Return `{"items": [CrmProjectContactLinkModel(**_item_to_link(i)) for i in items], "cursor": next_cursor}`.

Internal helper `_item_to_link(item) -> dict` extracts the fields needed to construct `CrmProjectContactLinkModel`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Duplicate add

If a caller POSTs the same `linked_entity_id` twice for the same project, the `ConditionExpression="attribute_not_exists(SK)"` on `put_item` raises `ConditionalCheckFailedException`. The service catches this, re-fetches the existing item, and returns it with HTTP 200 (not 201). The `display_name` is NOT updated on a duplicate add — it retains the original value. To update `display_name`, the caller must DELETE and re-add.

### 5.2 Non-member caller

Any caller whose `user_sub` has no row in `T.crm_pm_members` (PK `PROJECT#{project_id}`, SK `MEMBER#{caller_sub}`) receives HTTP 403 `{"code": "not_a_project_member"}` from `_assert_project_access`. This applies to all three endpoints. Viewer-role callers may call `GET` but receive 403 on `POST`/`DELETE` because those require `min_role=member`.

### 5.3 Project does not exist

`_assert_project_access` returns 403 for both "project does not exist" and "caller is not a member" cases — it does not distinguish between them for security (no information leakage about project existence to non-members). The 403 body uses `{"code": "not_a_project_member"}` in both cases.

### 5.4 Invalid or empty `linked_entity_id`

`linked_entity_id` after whitespace stripping must be non-empty. The Pydantic field validator (`min_length=1`) on `CrmProjectContactLinkIn` rejects empty strings at the HTTP layer with 422. The service also validates after stripping and raises 400 with `{"code": "invalid_entity_id"}` as a secondary defense.

### 5.5 `linked_entity_id` max length

The field is capped at 256 characters (`max_length=256`) to stay within DDB SK size limits and to prevent abuse. A PTY `party_id` is typically a UUID (36 chars) — 256 is generous headroom.

### 5.6 Pagination cursor validity

An invalid or tampered cursor passed to `list_contact_links_route` is decoded by `decode_cursor`, which returns `None` for any bad input (`app/core/cursor.py:103–131`). When `decoded_cursor` is `None`, the query simply starts from the beginning with no `ExclusiveStartKey`. This is safe and correct behavior.

### 5.7 Concurrent delete + list

DynamoDB does not provide snapshot isolation across a query + delete. A link deleted by another request during a `list` query may or may not appear in the current page — this is acceptable eventual-consistency behavior for a list endpoint. Callers must not rely on list results being point-in-time consistent.

### 5.8 Flag off behavior

When `S.crm_projects_enabled` is `False`, `_require_crm_projects()` raises `HTTPException(404)` before any service call is made. The `T.crm_pm_members` table may not even exist in that configuration (if PRJ-001 scaffolding was not run), so the early exit prevents any DDB call that would fail with a missing-table error.

### 5.9 `display_name` = `None` in responses

`display_name` is `Optional[str]` and may be `None` if the caller did not provide one. Downstream consumers (frontend, integrations) must handle `null` gracefully.

### 5.10 DDB `FilterExpression` not needed

Because the SK prefix `CONTACT_LINK#` is used in the `KeyConditionExpression`, DynamoDB filters at the index level, not with a post-read `FilterExpression`. The entire page of up to `Limit` items is consumed without needing a follow-up scan loop (the CLAUDE.md "DDB FilterExpression doesn't reduce page size" gotcha does not apply here — the key condition is exact).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

All DDB operations use `T.crm_pm_members` via `app/core/tables.T`. In dev, `T.crm_pm_members` is backed by DynamoDB Local (port 8001). In prod it is backed by real DynamoDB. The same code path runs in both environments — there is no `S.dev_mode` branch in `app/services/crm_project_links.py`. Audit events write to `T.alerts` in both environments via `app/services/alerts.audit_event` (`app/services/alerts.py:644`), which has its own dev/prod routing internally. This satisfies the SECOPS-007 requirement.

### 7.2 Idempotency

`add_contact_link` is idempotent: a second call with the same `(project_id, linked_entity_id)` returns the existing item without error rather than raising 409. `remove_contact_link` is idempotent at the network level: a second DELETE for an already-absent link returns 404, which the caller should treat as a successful absence confirmation (the link is not there either way). `list_contact_links` is always read-only and idempotent by nature.

### 7.3 Authorization

- All three endpoints require a valid platform session via `require_ui_session`. Unauthenticated requests receive 401 from the session middleware before the handler runs.
- The project membership check via `_assert_project_access` (PRJ-007) is the authorization boundary. Platform `Role` (admin/root) does not bypass project membership checks — a platform admin who is not in the project's member list is still refused.
- No elevation of privilege is possible: `_assert_project_access` reads directly from `T.crm_pm_members` using a consistent read (`ConsistentRead=True`).
- The `linked_entity_id` is treated as an opaque client-controlled string. It is never resolved against another table in this ticket, so there is no IDOR risk from linking to a non-existent entity. When PTY ships, the PRJ-011 / PTY integration work will add an existence check at that point.
- CSRF: all `POST`/`DELETE` requests from the browser session carry the `x-csrf-token` header, enforced by `require_ui_session` for cookie-based auth (CLAUDE.md "CSRF" section).

### 7.4 Input sanitization

`linked_entity_id` and `display_name` are stored verbatim (after whitespace stripping). They are never evaluated as code or interpolated into DDB condition expressions as raw strings — they are always bound via `ExpressionAttributeValues`. No injection risk.

## 8. Backward Compatibility & Migration

### 8.1 No schema migration

PRJ-010 adds rows with `SK = "CONTACT_LINK#{id}"` to the existing `crm_pm_members` table. Existing `MEMBER#{user_sub}` rows are never touched. Code that queries only `MEMBER#` prefixes (PRJ-007 membership operations) is unaffected. No DDB table schema change (no new attributes on the table definition, no new GSIs) is required.

### 8.2 Removing the flag

If `CRM_PROJECTS_ENABLED` is toggled from `1` to `0` in a running system, existing `CONTACT_LINK#` rows remain in DDB. When the flag is re-enabled, all previously created links are visible again. There is no stale-state issue.

### 8.3 PTY integration path

When PTY-011 ships the party service, the `linked_entity_id` field transparently becomes a real `party_id`. The only change required at that point is to add an optional validation call (existence check against the party service) inside `add_contact_link`. The stored item shape, SK layout, Pydantic model, and API contract are all unchanged.

### 8.4 `display_name` denormalization

`display_name` is stored at write time and is never auto-updated if the party's name changes in a future PTY system. This is acceptable for a V1 relationship; if live name resolution is needed, a downstream read-time enrichment layer (outside this ticket's scope) can overlay it.

## 10. Open Questions / Assumptions

1. **`display_name` update**: The spec intentionally does not provide a PATCH endpoint for `display_name`. Callers must DELETE and re-add to change the label. If the use case for in-place display name updates arises, a `PATCH /v1/crm/projects/{id}/contacts/{entity_id}` endpoint with a `{"display_name": "..."}` body can be added in a follow-up ticket. The DDB item shape supports this with a simple `update_item` expression.

2. **Bulk add**: No bulk endpoint is specified. If UI bulk-import of contacts becomes a requirement, a `POST /v1/crm/projects/{id}/contacts/bulk` accepting `[{linked_entity_id, display_name}]` can be added additively. The service loop would call `add_contact_link` per item and collect partial failures.

3. **Reverse lookup (entity → projects)**: Finding all projects linked to a given `linked_entity_id` requires either a full table scan or a new GSI on `T.crm_pm_members` with `GSI2PK = "ENTITY#{linked_entity_id}"`. This lookup is deferred to PTY integration work. For now, callers discover project-contact relationships by reading a known project's contact list.

4. **Viewer role on `remove`**: This spec grants `remove_contact_link` access at `min_role=member`, not `min_role=owner`. The assumption is that any project member (not just the owner) may manage contact links, consistent with how PRJ-007 assigns member-role write access to project task data. If a stricter policy (owner-only remove) is desired, change the `_assert_project_access` call in `remove_contact_link` to `min_role=CrmProjectMemberRole.owner`.

5. **PTY entity-type extension**: `linked_entity_type` is currently `Literal["contact_party"]`. Once PTY ships organization parties (`PARTY_GROUP`), the value `"org_party"` may need to be added. This is a non-breaking additive change to the `Literal` union and the stored string field. No migration of existing rows is needed.

6. **Soft-delete vs hard-delete**: This spec uses hard delete (`delete_item`). If an audit trail of removed links is needed for compliance, the delete could instead set a `removed_at` attribute and filter it in list queries. This is deferred pending a compliance requirement.
