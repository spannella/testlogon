## 1. Summary & Goal

INV-009 is an integration chore, not a net-new backend feature. QUO-005 specifies and delivers the full invoice status lifecycle (`draft | generated | sent | paid | overdue | void`), the `update_invoice_status` service function, the `POST /ui/invoices/{number}/void` endpoint, the `ManualInvoiceCreateIn` model, payment-terms / due-date fields on `InvoiceOut`, and the overdue background checker. INV-007 depends on the `status="void"` value being present (to avoid applying discounts to voided invoices). Neither INV-001 nor INV-003 call `update_invoice_status` — INV-001 is a pure field-extension chore and INV-003 is creation-time currency conversion. No INV ticket in the current batch calls `update_invoice_status` at merge time except through the integration test authored here.

The goals of this ticket are:

1. **Be the hard dependency gate**: no INV ticket that calls `update_invoice_status` or references the new status values may be merged before QUO-005 lands. This ticket is the blocker.

## 5. Detailed Behavior & Edge Cases

### 5.1 Status lifecycle transitions

The full state machine (enforced by `update_invoice_status` in QUO-005):

```
generated  →  (no transitions; existing auto-generated invoices are immutable)
draft      →  sent | void
sent       →  paid | overdue | void
paid       →  void  (admin-only; triggers ledger reversal)
overdue    →  void  (admin-only; overdue invoices may be written off)
void       →  (terminal; no further transitions)
emailed    →  (legacy; set by email_invoice; not part of the new lifecycle)
```

**`paid→void`** is the only transition that writes a reversal ledger entry. The reversal uses `billing_shared.new_ledger_entry(key_name="pk", key_value=f"USER#{user_sub}", entry_type="invoice_void_reversal", amount_cents=original_total_cents, state="reversed", reason="Invoice voided", extra={"invoice_number": invoice_number})`. **Sign convention (audit A4):** `new_ledger_entry` stores an **unsigned** `amount_cents` (`int(amount_cents)`, `billing_shared.py:249`); direction is derived read-side from the `entry_type` discriminator. The reversal therefore writes a **positive** amount under the `invoice_void_reversal` type (`state="reversed"`) — never a negative amount — consistent with the canonical `refund_payment` convention (`billing.py:1306-1324`). ACC-002 §5 maps `invoice_void_reversal` → credit (+). The ledger SK is stored on the invoice item as `void_reversal_ledger_sk` for traceability. This is the accounting-correct pattern for AR reversals: a credit note (positive credit entry), not a state flip on the original charge row.

**`void` by non-admin** is limited to `draft→void` and `sent→void`. Only admins (via `require_admin_or_root`) may void a `paid` invoice. The void endpoint uses `require_ui_session`, so a non-admin calling it on a `paid` invoice receives 409 ("transition not allowed").

**Ownership check**: the void endpoint at `POST /ui/invoices/{number}/void` loads the raw invoice item and compares `item["user_sub"]` to `ctx["user_sub"]` from the session. Mismatch returns 403.

**Overdue detection**: `check_overdue_invoices()` queries GSI2 (`GSI2PK="ADMIN_ALL"`, `ScanIndexForward=False`) — the same GSI used by `admin_list_invoices` at `app/services/invoices.py:509` — and applies a `FilterExpression: #s = :sent AND due_date < :now`. Because DynamoDB `FilterExpression` does not reduce page size before the 1MB cap (CLAUDE.md gotcha), the function loops via `LastEvaluatedKey` until all pages are consumed. The function skips items where `due_date` is absent (None / 0). Note: QUO-005's description (CRM_QUOTES_CONTRACTS_TICKETS.md:396) ambiguously says "queries GSI1 … (scans ADMIN_ALL GSI2)"; GSI2 is the correct index for cross-user admin scanning — GSI1 is keyed on `USER#{sub}#TYPE#{type}` and cannot scan all users.

**Idempotency of overdue checker**: the `FilterExpression` includes `status = "sent"` so invoices already marked `overdue` are never reprocessed.

### 5.2 Manual invoice creation (QUO-005 endpoint, tested by INV-009)

`POST /ui/admin/invoices/manual` calls `create_invoice(invoice_type="shop", status="draft", ...)` — the status override is only respected when `S.aos_standalone_invoices_enabled` is on; otherwise the endpoint returns 404. `due_date` is computed as `created_at + payment_terms_days * 86400` when `payment_terms_days` is provided. The invoice number is minted by `_next_invoice_number()` using the existing atomic counter (no new counter row needed).

### 5.3 INV-001 field co-testing

The integration test in `tests/test_inv_009_invoice_lifecycle.py` creates a manual invoice with `billing_address`, `discount_cents`, and line items containing `unit_price_cents`. This exercises INV-001 and INV-007 fields in the context of the new lifecycle. The test asserts that `InvoiceOut` carries all fields, that `total_cents = amount_cents + tax_cents + shipping_cents - discount_cents`, and that the PDF bytes (regenerated from the stored record) include the "Billing Address" section header.

### 5.4 Edge cases

**`payment_terms_days=0`**: valid; `due_date = created_at` (invoice is immediately due). The overdue checker will mark it overdue on its next tick.

**Missing `due_date` on old invoices**: `check_overdue_invoices()` skips items where `due_date` is `None` or `0`. Old `generated`/`emailed` invoices are never transitioned to `overdue`.

**Double-void**: calling void on an already-voided invoice returns 409 ("invoice is already voided") without writing a second ledger entry.

**Concurrent void calls**: the `update_invoice_status` implementation uses a conditional `UpdateExpression` with `ConditionExpression="status = :current_status"`. A concurrent void attempt after the first succeeds returns a `ConditionalCheckFailedException` from DynamoDB, which the service translates to 409.

**`create_invoice_safe` bypass**: the `create_invoice_safe` wrapper at `app/services/invoices.py:373` is used inside billing hooks and always creates invoices with the auto-generation path (no `status` override). When `AOS_STANDALONE_INVOICES_ENABLED=0`, the `status` override param in `create_invoice` is silently ignored and status defaults to `"generated"`, preserving existing behavior.

- `POST /ui/invoices/{number}/void` returns 404.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

No `if S.dev_mode` branches in any service code. The `billing_shared.new_ledger_entry` call on `paid→void` writes to the real `T.billing` DynamoDB table in both environments — in dev, moto intercepts the boto3 call in-process (`app/core/dev_s3.py` pattern). The email notification sent by `email_invoice` routes through `alerts.send_alert_email` at `app/services/alerts.py:459`, which in dev writes to the dev email log file (`S.dev_email_log`) rather than SES — the same code path is used, fulfilling SECOPS-007 parity. No `if S.dev_mode` in the lifecycle transition logic.

The `start_invoice_overdue_checker_task` pattern follows `start_compute_billing_timer_task` at `app/services/compute_billing.py:669` (verified — registered in `app/main.py:869` via `app.add_event_handler("startup", start_compute_billing_timer_task)`): `asyncio.ensure_future(run_invoice_overdue_checker_loop())` inside a guard `if S.aos_invoice_overdue_checker_enabled`. Both environments run the same loop.

### Idempotency

- **Void**: protected by a DynamoDB `ConditionExpression` on `status`. Second call → 409 (no double-write of reversal ledger).
- **Overdue checker**: `FilterExpression` filters by `status="sent"`, so already-overdue invoices are never reprocessed.
- **Manual invoice creation**: uses the existing `_existing_for_ledger` idempotency check via the `LEDGERMARK` row when `ledger_entry_id` is provided. Admin-created B2B invoices typically provide no `ledger_entry_id`, so duplicate creation is prevented by the monotonic invoice number (each call mints a new unique number, so a double-POST creates two distinct draft invoices — acceptable for admin manual creation; the admin should not POST twice).

### Security

- **Void ownership check**: `POST /ui/invoices/{number}/void` enforces that `ctx["user_sub"] == item["user_sub"]` before proceeding. This check happens inside the service function before any state mutation.
- **`paid→void` admin-only**: `update_invoice_status` returns 409 if the current status is `paid` and the calling context is not ADMIN/ROOT. The router passes `actor_sub` and `role` from `ctx` to the service.
- **CSRF**: `POST /ui/invoices/{number}/void` is inside `invoices_router` which uses `Depends(require_ui_session)`. As documented in CLAUDE.md, non-GET requests from cookie sessions require `x-csrf-token` header matching both the session's stored `csrf_token` and the `ui_csrf` cookie. Bearer-token callers skip CSRF.
- **Audit trail**: every `update_invoice_status` call emits `audit_event("invoice.status_changed", user_sub, invoice_number=..., from_status=..., to_status=..., actor_sub=...)` via `app/services/alerts.py:644`. The void reversal ledger entry provides an additional financial audit trail.
- **Void reversal ledger** — the positive `invoice_void_reversal` `new_ledger_entry` carries `ledger_date` (written by `billing_shared.ledger_date_for_ts(ts)`) so it appears in the platform financial dashboard aggregations; the read-side derives its credit direction from `entry_type` (ACC-002 §5), correctly reducing net revenue in the period.

### No schema migration required

All new attributes (`payment_terms_days`, `due_date`, `voided_at`, `discount_cents`, `billing_address`) are written only on newly created or newly transitioned invoices. ## 10. Open Questions / Assumptions

1. **`PATCH /ui/invoices/{number}/status` vs. dedicated transition endpoints**: QUO-005 shows two patterns for status transitions — a generic `PATCH /status` body or per-transition endpoints like `POST .../void` and `POST .../send`. This spec assumes QUO-005 delivers both the `POST .../void` endpoint (owned by `invoices_router` with owner-only auth) and at minimum the `POST .../send` verb (owned by admin). If QUO-005 delivers only `POST .../void`, the frontend `patchInvoiceStatus` wrapper should be scoped to the void case only, and a separate `sendInvoice(invoiceNumber)` function should call `POST /ui/invoices/{number}/send`.

2. **`paid→void` admin determination**: the void endpoint uses `require_ui_session` (not `require_admin_or_root`). INV-009 assumes the service function checks `ctx["role"]` to determine whether `paid→void` is allowed. If QUO-005 instead splits void into two endpoints (`POST .../void` for owner, `POST /ui/admin/invoices/{number}/void` for admin), the frontend wrapper and ownership-check logic must be adjusted accordingly.

3. **Reversal ledger table**: `new_ledger_entry` at `app/services/billing_shared.py:224` writes to a `table` parameter that is the caller's billing table. For invoice void reversals, the assumption is that the caller passes `T.billing` (the platform billing table). This must be confirmed when QUO-005 is authored — if QUO-005 writes the reversal to `T.invoices` instead (as a `VOID_REVERSAL#` row), the integration test fixture must create a suitable table.

4. **`discount_cents` ledger integration**: INV-007 specifies writing `discount_cents` as a negative `new_ledger_entry` extra field. If INV-007 is not merged before INV-009, the integration test for `paid→void` will still pass, but the assertion on the financial dashboard reporting negative discount contribution should be deferred to INV-007's test.

5. **Overdue checker GSI scan**: `check_overdue_invoices` is described in QUO-005 as scanning `GSI2` (`ADMIN_ALL`). The `T.invoices` GSI2 includes all invoices. On a production database with millions of invoice records, a full GSI2 scan at each poll interval (default 3600s) may be costly. An optimization — adding a `GSI3` keyed on status for a `STATUS#sent` partition — is deferred to a future ticket. For now the GSI2 full scan with a `FilterExpression` on `status="sent" AND due_date < now` is acceptable for the initial implementation.
