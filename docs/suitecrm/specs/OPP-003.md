# OPP-003 — Sales stage pipeline management and Kanban UI

**Ticket type:** Feature  
**Priority:** P1  
**Estimate:** 3 days  
**Source ticket file:** `docs/suitecrm/CRM_OPPORTUNITIES_TICKETS.md`  
**Master gate:** `S.sales_pipeline_enabled` (`SALES_PIPELINE_ENABLED`, default `false`)

---

## 1. Summary & Goal

OPP-003 adds two things to the sales pipeline feature:

1. **Admin-configurable stage pipeline** — a stored stage configuration that replaces the static `OPPORTUNITY_STAGES` tuple from OPP-001 with a live DynamoDB row admins can reorder, relabel, and extend. SuiteCRM ships a fixed nine-stage pipeline but permits customization; this ticket brings the same capability.

2. **Frontend Kanban board** — a horizontally scrollable opportunity board at `/sales/opportunities` where cards are grouped into stage columns and can be dragged between columns to trigger a stage update. The column list is fetched from the new stages API so the frontend never hard-codes a stage list.

Both surfaces are additive and fully gated behind `S.sales_pipeline_enabled`. With the flag off, every byte of existing platform behavior is unchanged: no new routes are mounted, no DDB writes occur, and the sidebar entry is absent.

This ticket depends on OPP-001 (table, models, and flag) and OPP-002 (CRUD service and router) being merged first.

## 3. Data Model

### 3.1 Stage config row — reuses `T.sales_opportunities`

A single new row type is added to the existing `sales_opportunities` single-table. No new DynamoDB table or GSI is required.

| Attribute | Value | Notes |
|-----------|-------|-------|
| `pk` | `"STAGE_CONFIG"` | Literal string — outside the `USER#` namespace |
| `sk` | `"META"` | Singleton row per deployment (shared across all users) |
| `stages` | JSON list stored as a DynamoDB String | Marshalled in Python; see schema below |
| `updated_at` | integer (Unix seconds) | Set by `audit_event` caller |
| `updated_by_sub` | string | Admin sub who last wrote the config |

The `stages` attribute is persisted as a JSON-encoded string (not a DynamoDB List), sidestepping DynamoDB's lack of ordered-list projection support and keeping the row trivially replaceable with a single `put_item`.

Each element of the decoded list follows this shape:

```python
@dataclass
class StageConfig:
    stage_key: str          # must be in OPPORTUNITY_STAGES or a custom key
    label: str              # display label, max 80 chars
    probability_default: int  # 0..100
    order: int              # sort ascending for column rendering
    is_won: bool            # exactly one stage per config
    is_lost: bool           # exactly one stage per config
    color: Optional[str]    # optional hex color for Kanban column header
```

**Pydantic models** (added to `app/models.py`):

```python
class StageConfigItemIn(BaseModel):
    stage_key: str = Field(..., min_length=1, max_length=80)
    label: str = Field(..., min_length=1, max_length=80)
    probability_default: int = Field(ge=0, le=100, default=0)
    order: int = Field(ge=0)
    is_won: bool = False
    is_lost: bool = False
    color: Optional[str] = Field(None, max_length=7)  # "#RRGGBB"

class StageConfigIn(BaseModel):
    stages: List[StageConfigItemIn]

class StageConfigItemOut(BaseModel):
    stage_key: str
    label: str
    probability_default: int
    order: int
    is_won: bool
    is_lost: bool
    color: Optional[str]

class StageConfigOut(BaseModel):
    stages: List[StageConfigItemOut]
    updated_at: Optional[int]
    updated_by_sub: Optional[str]
```

`StageConfigIn` is validated by a root `@validator` that enforces:
- Exactly one item with `is_won=True`.
- Exactly one item with `is_lost=True`.
- No duplicate `stage_key` values.
- Minimum one and maximum 20 stages.

If these constraints are not satisfied the validator raises `ValueError`, which FastAPI translates to a 422 response. The business-logic layer re-raises as HTTP 400 with a structured `code` field (see Section 4).

### 3.2 Impact on `scripts/local-ddb-init.py`

No new `TableDef` entry is needed. The `STAGE_CONFIG#META` row lives on `sales_opportunities`, which is already declared by OPP-001 with:

```python
attr_types={"close_date": "N", "created_at": "N"}
```

The `pk="STAGE_CONFIG"` row has no numeric GSI keys, so no `attr_types` change is required. The `updated_at` on the config row is stored as an item attribute (not a GSI sort key), so no `attr_types` amendment is needed.

### 3.3 Impact on `app/core/tables.py`

No new table handle is added. `T.sales_opportunities` (introduced by OPP-001) is used directly.

## 4. API / Service Design

### 4.1 Service layer — `app/services/opportunities.py`

All functions are added to the same file introduced by OPP-002. They call `_require_flag()` at entry.

#### `get_stage_config() -> StageConfigOut`

```python
def get_stage_config() -> StageConfigOut:
    _require_flag()
    item = T.sales_opportunities.get_item(
        Key={"pk": "STAGE_CONFIG", "sk": "META"}
    ).get("Item")
    if not item:
        return _default_stage_config()
    stages = json.loads(item["stages"])
    return StageConfigOut(
        stages=[StageConfigItemOut(**s) for s in stages],
        updated_at=int(item.get("updated_at", 0)) or None,
        updated_by_sub=item.get("updated_by_sub"),
    )
```

The fallback `_default_stage_config()` converts `OPPORTUNITY_STAGES` from `app/models.py` into `StageConfigItemOut` objects, assigning sequential `order` values, `probability_default=0`, and setting `is_won=True` for `"closed_won"` and `is_lost=True` for `"closed_lost"`. This ensures `GET /ui/sales/stages` returns a well-formed response even before any admin has saved a config.

#### `set_stage_config(admin_sub: str, data: StageConfigIn) -> StageConfigOut`

```python
def set_stage_config(admin_sub: str, data: StageConfigIn) -> StageConfigOut:
    _require_flag()
    _validate_stage_config(data)   # raises HTTPException(400) on constraint violation
    now = now_ts()
    payload = {
        "pk": "STAGE_CONFIG",
        "sk": "META",
        "stages": json.dumps([s.model_dump() for s in data.stages]),
        "updated_at": now,
        "updated_by_sub": admin_sub,
    }
    T.sales_opportunities.put_item(Item=payload)
    audit_event(
        "sales_stage_config.updated",
        admin_sub,
        None,
        stage_count=len(data.stages),
        won_key=next(s.stage_key for s in data.stages if s.is_won),
        lost_key=next(s.stage_key for s in data.stages if s.is_lost),
    )
    return get_stage_config()
```

`_validate_stage_config(data)` is an internal helper that raises `HTTPException(400, detail={"code": "invalid_stage_config", "reason": "..."})` for:
- `won_count != 1` → `"exactly_one_is_won_required"`
- `lost_count != 1` → `"exactly_one_is_lost_required"`
- Duplicate `stage_key` → `"duplicate_stage_key"`
- `len(data.stages) < 1` → `"stages_empty"` (Pydantic catches this first at the model layer)

#### Stage transition update in `update_opportunity`

The existing `update_opportunity` in OPP-002 checks hard-coded stage names. OPP-003 replaces that with a call to `get_stage_config()` to obtain the current `is_won` and `is_lost` keys:

```python
# Within update_opportunity, when data.stage is being changed:
if data.stage is not None and data.stage != current_stage:
    config = get_stage_config()
    won_key = next((s.stage_key for s in config.stages if s.is_won), "closed_won")
    lost_key = next((s.stage_key for s in config.stages if s.is_lost), "closed_lost")
    terminal_keys = {won_key, lost_key}
    if current_stage in terminal_keys:
        reopen_allowed = S.sales_pipeline_allow_reopen
        if not reopen_allowed:
            raise HTTPException(400, detail={
                "code": "stage_transition_blocked",
                "reason": "opportunity_is_closed",
                "current_stage": current_stage,
            })
        negotiation_key = _reopen_target_stage(config)
        if data.stage != negotiation_key:
            raise HTTPException(400, detail={
                "code": "stage_transition_blocked",
                "reason": "closed_opportunity_may_only_reopen_to_negotiation",
                "allowed_target": negotiation_key,
            })
    audit_event(
        "opportunity.stage_changed",
        owner_sub,
        None,
        opp_id=opp_id,
        from_stage=current_stage,
        to_stage=data.stage,
    )
```

`_reopen_target_stage(config)` returns the `stage_key` with the highest `order` value that is neither `is_won` nor `is_lost` (i.e., the last active stage before closure). For the default config this is `"negotiation_review"`. If no such stage exists it falls back to the first stage in `order` ascending.

`S.sales_pipeline_allow_reopen` is a new boolean setting (see Section 6). When `False`, any update that tries to move a closed opportunity raises `stage_transition_blocked` immediately.

### 4.2 Router additions — `app/routers/opportunities.py`

Two new endpoints are appended to the existing router. Declaration order matters: the `stages` literal path is added **before** any `/{opp_id}` routes to prevent FastAPI capturing the literal word `stages` as an `opp_id` (the same ordering constraint documented for `audit_export.py` schedules in CLAUDE.md).

```python
router_admin = APIRouter(prefix="/ui/admin/sales", tags=["sales-pipeline-admin"])

@router.get("/stages", response_model=StageConfigOut)
async def list_stages(ctx: dict = Depends(require_ui_session)) -> StageConfigOut:
    """Return the active stage list. Requires a valid session; no admin role needed."""
    return get_stage_config()

@router_admin.put("/stages", response_model=StageConfigOut)
async def update_stages(
    body: StageConfigIn,
    ctx: dict = Depends(require_ui_session),
) -> StageConfigOut:
    """Replace the stage list. Admin or root role required."""
    if normalize_role(ctx.get("role")) not in {Role.ADMIN, Role.ROOT}:
        raise HTTPException(403, detail={"code": "admin_role_required"})
    return set_stage_config(ctx["user_sub"], body)
```

Both routers — `router` (already registered by OPP-002) and `router_admin` (new) — are imported and registered in `app/main.py` adjacent to the OPP-002 registration. The `router_admin` `include_router` call is placed immediately after the `opportunities_router` line, inside the same `if _S.sales_pipeline_enabled:` block.

**Full endpoint table for OPP-003:**

| Method | Path | Auth | Body | Response |
|--------|------|------|------|----------|
| `GET` | `/ui/sales/stages` | `require_ui_session` | — | `StageConfigOut` |
| `PUT` | `/ui/admin/sales/stages` | `require_ui_session` + admin role | `StageConfigIn` | `StageConfigOut` |

Plus the `update_opportunity` service change that now emits `opportunity.stage_changed` and validates against the stored config.

## 5. Detailed Behavior & Edge Cases

### 5.1 Default config fallback

`GET /ui/sales/stages` must return a valid `StageConfigOut` even when no admin has ever called `PUT /ui/admin/sales/stages`. `_default_stage_config()` constructs the response from `OPPORTUNITY_STAGES` at runtime. The frontend Kanban must therefore never assume the stages endpoint returns an error when the platform first starts.

### 5.2 Stage validation on opportunity update

When a `PATCH /ui/sales/opportunities/{opp_id}` changes the `stage` field:

1. `get_stage_config()` is called to resolve the current `won_key` and `lost_key`.
2. If the opportunity is already at `won_key` or `lost_key`, and `S.sales_pipeline_allow_reopen` is `False`, the request is rejected with 400 `stage_transition_blocked`.
3. If reopen is allowed, the new stage must equal `_reopen_target_stage(config)`.
4. If the new stage is not present in the current `config.stages` list, the request is rejected with 400 `invalid_stage` (regardless of whether it appears in `OPPORTUNITY_STAGES`).
5. On any stage change, `audit_event("opportunity.stage_changed", ...)` is called.

**Consistency note:** Setting a new stage config can make existing opportunities carry a `stage` value that no longer appears in the config list. The service does not retroactively update opportunity rows; `update_opportunity` only validates the *incoming* stage against the current config. `list_opportunities` and `get_opportunity` return whatever `stage` is stored verbatim. A future "stage cleanup" admin endpoint is out of scope for OPP-003.

### 5.3 PUT /ui/admin/sales/stages — full replacement semantics

`PUT` is idempotent: sending the same list twice produces the same stored state. The entire `stages` list is replaced atomically via `put_item` (not `update_item`). Partial updates are not supported. If an admin wants to rename one stage they must PUT the full list.

### 5.4 Concurrent admin writes

Two admins saving a config simultaneously will race at `put_item`. The last write wins. No optimistic concurrency is added here because stage-config changes are rare, admin-only, and the window for conflict is small. A future `version` attribute can be added if needed (OPP-003 leaves `version` out of scope).

### 5.5 Drag-and-drop on the Kanban

On `dragEnd`, the frontend optimistically moves the card to the target column in local React state before the `PATCH` call completes. If the `PATCH` returns a non-2xx response (e.g., 400 `stage_transition_blocked`), the optimistic update is rolled back via React Query's `onError` callback, which invalidates `["opportunities"]` to trigger a re-fetch. A `toast.error(...)` is shown using the same `sonner` toast pattern as `BoardKanban.tsx`.

### 5.6 Kanban column ordering

Columns are rendered in ascending `order` value as returned by the stages API. The frontend does not sort independently; it trusts the server's ordering. If the server returns stages in an arbitrary order the frontend sorts by `order` ascending before rendering.

### 5.7 Stage-key validation scope

`PUT /ui/admin/sales/stages` does not require `stage_key` values to be members of `OPPORTUNITY_STAGES`. Admins are free to create fully custom stage keys (e.g., `"pilot"`, `"poc"`) as long as the `is_won` / `is_lost` constraints and uniqueness constraints pass. However, when the config is absent, the fallback uses `OPPORTUNITY_STAGES`. Pre-existing opportunity rows that reference a removed stage key are not automatically migrated.

### 5.8 `GET /ui/sales/feature-status` (OPP-006 prerequisite)

This lightweight endpoint (specified more fully in OPP-006) is added in OPP-003 to allow the frontend sidebar to check if the sales pipeline flag is on without importing backend config directly. It is kept minimal here:

```python
@router.get("/feature-status")
async def feature_status() -> dict:
    return {"enabled": S.sales_pipeline_enabled}
```

This endpoint does **not** call `_require_flag()` — it must be reachable when the flag is off so the frontend can determine whether to show or hide the sidebar entry. It uses `require_ui_session` so unauthenticated clients cannot probe the feature flag.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No dev_mode branches

`get_stage_config()` and `set_stage_config()` contain no `if S.dev_mode` branches. In dev, `T.sales_opportunities` is backed by DynamoDB Local (port 8001); in prod, by the real DynamoDB endpoint. The `put_item` and `get_item` calls are identical in both environments. The `_FloatSafeTable` proxy handles the `Decimal` coercion requirement in both.

### 7.2 Idempotency of `PUT /ui/admin/sales/stages`

Two identical `PUT` requests produce identical DynamoDB state. The `put_item` with a full `STAGE_CONFIG#META` row is unconditional (no condition expression), so retrying is safe. `updated_at` will differ between retries but that is acceptable for an admin config operation.

### 7.3 Admin authorization

`PUT /ui/admin/sales/stages` enforces `role in {Role.ADMIN, Role.ROOT}` after `require_ui_session` resolves the caller. The role is sourced from the `ui_access_token` JWT cookie claims (`app/auth/deps.py:109-117` `_extract_role_from_claims`, populating the `AuthenticatedUser.role` field at `:128`), which is server-signed with `UI_ACCESS_TOKEN_SECRET`. It is not sourced from a user-supplied header or the DynamoDB session row directly. This means role elevation requires a new cookie issuance — same guarantee as all other admin endpoints.

### 7.4 Stage config as shared mutable state

The `STAGE_CONFIG#META` row is a single shared row, not per-user. Any admin can overwrite any other admin's config. The `updated_by_sub` and `updated_at` fields provide traceability. The `audit_event` call ensures the change appears in the `T.alerts` audit trail. No row-level isolation is needed because stage config is intentionally a platform-wide setting.

### 7.5 No money movement

OPP-003 involves no payment, refund, or ledger writes. The billing/refund primitives (`app/services/billing_shared.py`, `app/services/invoices.py`) are not used.

### 7.6 CSRF

All mutating endpoints (`PATCH /ui/sales/opportunities/{opp_id}`, `PUT /ui/admin/sales/stages`) are reached via cookie-auth and therefore require the `x-csrf-token` header matching the session's stored `csrf_token` (enforced by `require_ui_session` in `app/services/sessions.py:330`). The frontend `api/client.ts` attaches the CSRF token from the cookie on every non-GET request automatically.

## 8. Backward Compatibility & Migration

### 8.1 Existing opportunity rows

Opportunity rows written before this ticket carry a `stage` field that is one of the nine values in `OPPORTUNITY_STAGES`. After OPP-003 ships, those rows remain valid: `get_stage_config()` falls back to `_default_stage_config()` (built from `OPPORTUNITY_STAGES`) until an admin saves a custom config. If an admin saves a config that omits some of the original nine stage keys, existing rows with the omitted stage are not broken — they simply carry a `stage` value not in the current active list. The API returns them verbatim; the Kanban will place them in an "Unknown" overflow column if their stage is absent from the column list (see Section 5.2).

### 8.2 OPP-001 / OPP-002 compatibility

OPP-003 does not change the DynamoDB table schema, the `T.sales_opportunities` handle, or any of the OPP-002 endpoint paths. It only adds new endpoints and modifies the internals of `update_opportunity`. The validator in `OpportunityCreateIn` and `OpportunityUpdateIn` in `app/models.py` still checks against `OPPORTUNITY_STAGES` for now; OPP-003 does not relax that validation at create time (a follow-up can extend `create_opportunity` to also accept custom stage keys from the config row).

### 8.3 Database migration

No DynamoDB table schema migration is required. The `STAGE_CONFIG#META` row is written on first `PUT /ui/admin/sales/stages` call. Its absence is handled gracefully by the fallback path. `just restart` will re-create the table from scratch in dev (no migration needed there).

### 8.4 `app/main.py` registration ordering

The `opportunities_admin_router` with prefix `/ui/admin/sales` must be registered **after** any generic `/ui/admin` wildcard routers and **before** any future `/ui/admin/sales/{resource_id}` dynamic routes. The current `app/main.py:683` insertion point (adjacent to `contacts_router`) satisfies this.

## 10. Open Questions / Assumptions

**Q1. Should custom `stage_key` values be allowed at opportunity creation?**  
*Assumption:* OPP-003 does not relax `OpportunityCreateIn.stage` validation, which still checks against `OPPORTUNITY_STAGES`. Extending `create_opportunity` to accept custom stage keys from the config row is a follow-up for OPP-004 or later. This keeps OPP-003 focused and avoids a chicken-and-egg: the config might not exist yet when the first opportunity is created.

**Q2. Should the `STAGE_CONFIG#META` row be per-tenant?**  
*Assumption:* No. The platform's multi-tenancy (ENTERPRISE-001) operates at the router level via `TenantMiddleware`; the `sales_opportunities` table is not scoped per tenant in OPP-001's design. If per-tenant stage configs are needed they would require a `pk=TENANT_STAGE_CONFIG#{tenant_id}` row, which is a future follow-up.

**Q3. Should the Kanban show an "Unknown" column for orphaned stage values?**  
*Assumption:* Yes. When an opportunity carries a `stage` value not present in the current config, the Kanban renders an "Unknown" overflow column at the far right. This prevents data loss from being invisible to the rep. The column title is "Unknown" and is not draggable from (but is draggable to).

**Q4. What happens when an admin reduces the stage list and opportunities exist in the removed stages?**  
*Assumption:* The PUT succeeds immediately. Existing opportunities carry the removed stage value indefinitely. The service layer does not migrate them (no background job is added in this ticket). Operators must manually move orphaned opportunities if needed. This is documented in Section 8.1.

**Q5. Should `GET /ui/sales/stages` be accessible without a session (public)?**  
*Assumption:* No. It requires `require_ui_session` so anonymous clients cannot enumerate the platform's sales configuration. This is consistent with similar config endpoints (e.g., `GET /ui/billing/config`) which all require auth.
