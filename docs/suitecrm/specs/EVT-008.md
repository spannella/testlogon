# EVT-008 — Survey distribution — email invitation to contact list or questionnaire link

**Type:** Feature | **Priority:** P1 | **Estimate:** 2d
**Source:** `docs/suitecrm/CRM_MISC_TICKETS.md` (section "EVT-008")
**Dependencies:** EVT-001 (flag pattern). Soft forward dependency on PTY-001 (party/contact-list
segment resolution). `app/routers/questionnaires.py` singleton `REPO` and `_owned_questionnaire_or_404`.

---

## 1. Summary & Goal

EVT-008 adds survey distribution to the existing questionnaire system. A questionnaire owner can
dispatch email invitations that embed the questionnaire's public link to a list of raw email addresses
supplied in the request body. A parallel forward-compatible path accepts an opaque `contact_list_id`
(once MKT-003/PTY-001 ship) from which the service resolves recipient email addresses. A distribution
record is written per recipient so that re-sending is idempotent, duplicate addresses are skipped, and
the owner can retrieve a distribution summary showing sent count, unique respondent count, and response
rate.

The feature is entirely additive: two new endpoints appended to the existing
`app/routers/questionnaires.py`, a new service file
`app/services/crm_survey_distribution.py`, and a new feature flag
`CRM_SURVEY_DISTRIBUTION_ENABLED` (default `false`). With the flag off all new routes return 404 and
the `questionnaires` table is byte-for-byte unchanged.

## 2. Context & Current State

### Questionnaire system (existing)

The `questionnaires` table is a single-table DynamoDB design with composite key
`pk` (S) / `sk` (S) and four GSIs
(`owner-updated-index`, `status-updated-index`, `published_slug-index`,
`response_status-updated-index`). Declared at
`scripts/local-ddb-init.py:127-136`; table handle at `app/core/tables.py:141` and instantiated at
`app/core/tables.py:393` via `_safe_table(S.questionnaire_table_name)`.

The repository class `DynamoQuestionnaireRepository` (default instance `REPO` at
`app/routers/questionnaires.py:24`) owns all DDB access. The PK convention uses the helper
`_q_pk(questionnaire_id) -> "QNR#{questionnaire_id}"` defined at
`app/services/questionnaires_repository.py:686`. Existing SK namespaces under a questionnaire
partition include: `META`, `SECTION#*`, `QUESTION#*`, `VERSION#*`, `RESP#*`, `ANSWER#*`,
`EVENT#RESP#*`, and `PDF#RESP#*`.

Ownership enforcement is centralised in `_owned_questionnaire_or_404(questionnaire_id, user_sub)` at
`app/routers/questionnaires.py:231-237`; it raises `HTTPException(403)` for non-owners and
`HTTPException(404)` for missing questionnaires.

A published questionnaire has a `published_slug` stored on its VERSION row
(`app/services/questionnaires_repository.py:397`), and the published link is accessible at
`GET /questionnaires/published/{published_slug}` (no auth required for `visibility=public`), declared
at `app/routers/questionnaires.py:615`. The public URL takes the form
`{S.public_base_url}/questionnaires/published/{slug}` where `S.public_base_url` is read from
`PUBLIC_BASE_URL` in settings (`app/core/settings.py:349`).

### Email dispatch (existing)

`send_alert_email(to_emails: List[str], subject: str, body_text: str) -> None` at
`app/services/alerts.py:459` is the single canonical email send path. In dev mode it writes to the dev
email log (`S.dev_email_log`). In prod it calls SES via boto3, respects `S.alerts_email_enabled` and
`S.alerts_from_email`, swallows transport errors but increments `EMAIL_FAILED` and calls
`record_email_failure`.

### Rate limiting (existing)

`_bucket_limit(user_sub, sid, max_n, win) -> bool` at `app/services/rate_limit.py:60` is the
general-purpose leaky-bucket limiter backed by `T.sessions`. It is used by other rate-limited send
paths (e.g. `app/routers/csv_export.py:66`). The function returns `False` when the bucket is exhausted,
at which point the caller raises `HTTPException(429)`.

### Audit event (existing)

`audit_event(event: str, user_sub: str, request=None, **fields)` at `app/services/alerts.py:644`
writes audit rows to `T.alerts`. All state-mutating EVT-008 actions emit audit events following the
pattern used throughout the codebase.

### HMAC tokens / public survey links (existing)

`mint_ws_token` / `verify_ws_token` in `app/core/crypto.py:35-61` use HMAC-SHA-256 with
`S.ws_token_secret`. Cart recovery links (`CLAUDE.md` gotcha) use the same scheme for one-time-use
tokens. EVT-008 does not need one-time-use tokens (invite links should remain reusable), so the survey
link is the plain published URL — no extra HMAC wrapping needed. A query-parameter `?ref=inv` is
appended purely for analytics attribution, not security.

### Feature flag pattern (existing)

Flags added to the frozen `Settings` dataclass at `app/core/settings.py:6-8` read environment
variables at import time. Default-false flags use the convention
`os.environ.get("VAR", "false") == "1"` (matching `CRM_EVENTS_ENABLED` described in EVT-001, per

off, following the pattern from `app/routers/group_treasury.py:29` cited in
`docs/suitecrm/specs/EVT-001.md:45`.

## 3. Data Model

### Reuse existing `questionnaires` table — no new table required

Distribution invite records are stored as new rows inside the existing `questionnaires` single-table,
preserving co-locality with the questionnaire they belong to and avoiding an extra DDB round-trip for
ownership checks.

**Invite record row** (new SK namespace):

| Attribute | Type | Value |
|---|---|---|
| `pk` | S | `QNR#{questionnaire_id}` (via `_q_pk()`) |
| `sk` | S | `SURVEY_INVITE#{normalized_email}` |
| `entity_type` | S | `"survey_invite"` |
| `questionnaire_id` | S | questionnaire_id |
| `recipient_email` | S | normalized lowercase email |
| `owner_sub` | S | owner's user sub |
| `status` | S | `"sent"` (only terminal state written at send time) |
| `sent_at` | N | Unix timestamp integer (`now_ts()`) |
| `contact_list_id` | S | opaque ID when dispatched via contact list (nullable/absent) |
| `invite_ref` | S | random hex token appended as `?ref=<invite_ref>` to survey link for per-recipient attribution (16 chars, `uuid4().hex[:16]`) |
| `message` | S | custom message body supplied by owner (nullable/absent) |

**No new GSI is needed** for the distribution summary. `get_distribution_summary` queries the
partition `QNR#{questionnaire_id}` with SK prefix `SURVEY_INVITE#` — a simple SK-prefix query on the
table's primary key, which DynamoDB supports natively without a GSI.

**Idempotency key**: the SK `SURVEY_INVITE#{normalized_email}` is unique per questionnaire per
recipient. A `ConditionExpression="attribute_not_exists(sk)"` conditional put skips already-invited
addresses without raising an error (the caller increments `skipped` rather than `failed`).

**No `attr_types` change needed** because `sent_at` is stored as a numeric value in the item but is
NOT a GSI sort key — the query uses the table's own PK/SK, which are already declared `"S"`. The
`sent_at` column is stored as an integer (`now_ts()` returns `int`) so `_FloatSafeTable` at
`app/core/tables.py:29` will coerce it to `Decimal` automatically on write, and callers must
`int(row["sent_at"])` on read.

**No changes to `scripts/local-ddb-init.py`** — the questionnaires table already exists. No new table
means no new `TableDef`, no new `attr_types` entry, and no new `T.*` handle.

## 4. API / Service Design

### 4.1 New service: `app/services/crm_survey_distribution.py`

```python
from app.core.tables import T
from app.core.time import now_ts
from app.services.alerts import send_alert_email, audit_event
from app.services.questionnaires_repository import _q_pk
from app.core.normalize import normalize_email
```

**`send_survey_invitations`**

```python
def send_survey_invitations(
    *,
    questionnaire_id: str,
    owner_sub: str,
    recipients: list[str],
    subject: str,
    survey_url: str,
    message: str | None = None,
    contact_list_id: str | None = None,
) -> dict[str, int]:
```

Iterates `recipients`, for each address:

1. Normalises via `normalize_email(email)` — raises `HTTPException(400)` on invalid format;
   the router catches this and counts it in `failed`.
2. Mints a 16-char `invite_ref = uuid4().hex[:16]`.
3. Assembles the per-recipient URL: `f"{survey_url}?ref={invite_ref}"`.
4. Assembles `body_text` from `message` (if any) plus a standard footer line with the URL.
5. Attempts a conditional `put_item` with `ConditionExpression="attribute_not_exists(sk)"` to write the
   `SURVEY_INVITE#{normalized_email}` row. If DDB raises `ConditionalCheckFailedException`, increments
   `skipped` and continues without re-sending.
6. Calls `send_alert_email(to_emails=[normalized_email], subject=subject, body_text=body_text)`.
   Any exception from `send_alert_email` increments `failed` and does NOT roll back the DDB record
   (the invite row marks intent, not delivery; dev-mode email writes to log file per
   `app/services/alerts.py:462-468`).
7. Returns `{"sent": N, "skipped": N, "failed": N}` where `sent + skipped + failed == len(recipients)`.

Emits `audit_event("survey_distribution_sent", owner_sub, questionnaire_id=questionnaire_id, sent=sent, skipped=skipped, failed=failed)` after iteration.

**`get_distribution_summary`**

```python
def get_distribution_summary(
    *,
    questionnaire_id: str,
    owner_sub: str,
) -> dict[str, int | float]:
```

1. Queries `T.questionnaires` with `pk = _q_pk(questionnaire_id)` and SK prefix
   `SURVEY_INVITE#`, scanning all pages via `LastEvaluatedKey` loop (the DDB `FilterExpression`
   gotcha from CLAUDE.md: a single query call silently misses items beyond the first 1 MB page).
2. `total_sent = len(invite_rows)`.
3. Loads all response sessions via `T.questionnaires.query(pk=_q_pk(questionnaire_id), sk_prefix="RESP#")`,
   filters to `status == "submitted"`, collects the set of distinct non-null `respondent_id` values.
   Cross-references against the set of `recipient_email` values: a respondent matches if a submitted
   session's `respondent_id` appears in the platform's user record associated with that email. Because
   EVT-008 does not join to the users table (avoiding a cross-table scan), `total_responses` is
   defined as the count of distinct submitted sessions whose `respondent_id` is non-null (regardless
   of whether the respondent was directly invited). This is the same session-count logic used in
   `_compute_questionnaire_analytics` at `app/routers/questionnaires.py:150`.
4. `response_rate = round(total_responses / total_sent * 100, 1) if total_sent > 0 else 0.0`.
5. Returns `{"total_sent": int, "total_responses": int, "response_rate": float}`.

### 4.2 New Pydantic models (in `app/routers/questionnaires.py`)

```python
class DistributeSurveyReq(BaseModel):
    recipients: list[str] = Field(..., min_length=1, max_length=500)
    subject: str = Field(default="You've been invited to complete a survey", max_length=120)
    message: str | None = Field(default=None, max_length=2000)
    contact_list_id: str | None = Field(default=None, min_length=1, max_length=120)

class DistributeSurveyResp(BaseModel):
    sent: int
    skipped: int
    failed: int

class DistributionSummaryResp(BaseModel):
    total_sent: int
    total_responses: int
    response_rate: float
```

`recipients` is a plain `list[str]` rather than `list[EmailStr]` because pydantic's `EmailStr`
depends on `email-validator` which is not in the project's dependency set (`EmailStr` does not appear
anywhere in the codebase per grep). Validation is delegated to `normalize_email()` at
`app/core/normalize.py:60` inside the service.

```python
@router.post(
```

Behaviour:

1. `_require_crm_survey_distribution_enabled()` — returns 404 when flag is off.
2. `_owned_questionnaire_or_404(questionnaire_id, user.sub)` — returns 404/403.

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotency on re-send

The conditional `put_item` with `attribute_not_exists(sk)` on the `SURVEY_INVITE#` row means a
second call to `POST .../distribute` with the same email address silently skips that address
(`skipped += 1`) without re-sending the email or overwriting the original `sent_at`. The owner can
confirm via `GET .../distribution-summary` that the address is already counted in `total_sent`.

To force a re-send to an already-invited address, the caller must first `DELETE
/questionnaires/drafts/{id}/distribution-invites/{email}` (not in this ticket, deferred to a
follow-up) or the admin can purge rows directly via DDB.

### 5.2 Maximum recipients per request

`DistributeSurveyReq.recipients` has `max_length=500`. A single distribute call may target at most
500 addresses. For larger lists the caller makes multiple batched requests; each is subject to the
per-owner rate limit. This ceiling exists to keep Lambda/uvicorn request latency bounded (each
recipient triggers one DDB write and one SES call).

### 5.3 Contact-list resolution path (PTY forward compatibility)

When `body.contact_list_id` is set, the router calls
`_resolve_contact_list_recipients(contact_list_id, user_sub) -> list[str]`. In this ticket the
function is a stub:

```python
def _resolve_contact_list_recipients(contact_list_id: str, user_sub: str) -> list[str]:
    # PTY-001 / MKT-003 not yet shipped — contact-list resolution deferred
    raise HTTPException(
        status_code=501,
        detail={"error": {"code": "contact_list_not_implemented",
                          "message": "contact list resolution requires PTY-001"}},
    )
```

Once PTY-001 ships, this stub is replaced with a call to the Party/Contact-List service (the
interface point is already defined in `docs/suitecrm/CRM_MISC_TICKETS.md:27`).

### 5.4 Questionnaire must be published

`distribute_survey` returns `HTTPException(409, code="questionnaire_not_published")` if the META row
has `status != "published"`. This prevents distributing a link to a questionnaire that cannot accept
responses (`GET /questionnaires/published/{slug}` would 404).

### 5.5 Partial failure semantics

Email delivery errors from `send_alert_email` are swallowed per-recipient; the DDB row remains (the
invite record was written before the email call). The return value tells the owner how many failed.
The total invariant is `sent + skipped + failed == len(input_recipients)`.

### 5.6 Empty recipients + no contact_list_id

`DistributeSurveyReq.recipients` has `min_length=1`, so Pydantic returns 422 before the endpoint body
runs when recipients is an empty list and `contact_list_id` is also absent.

### 5.7 Email normalisation rejects malformed addresses

`normalize_email(email)` at `app/core/normalize.py:60-63` rejects any string that lacks `@` or
exceeds 254 characters, raising `HTTPException(400)`. The service catches this and counts it in
`failed` without aborting the rest of the batch. The error is silently swallowed inside the iteration
loop so one malformed address does not block the others.

### 5.8 Large questionnaire partitions and pagination

`get_distribution_summary` must loop `LastEvaluatedKey` because DDB fetches up to 1 MB before
filtering. A questionnaire with many thousands of invite records may span multiple pages. The loop
accumulates all `SURVEY_INVITE#` rows before computing `total_sent`. DynamoDB Local (port 8001) does
not enforce the 1 MB cap, so tests remain fast; prod readiness is achieved by the pagination loop
without any mock branch (SECOPS-007 parity).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 dev/prod parity

There is no `if S.dev_mode:` branch in the service. The DDB write path is identical in dev
(DynamoDB Local on port 8001) and prod (real DynamoDB). Email dispatch follows the existing
`send_alert_email` contract: dev writes to the dev email log file, prod calls SES — the caller
(EVT-008 service) does not know or care which path is taken.

### Idempotency

The `attribute_not_exists(sk)` conditional put on the invite row is the idempotency guard. A second
POST with the same recipient email is silently a no-op (returns `skipped=1` for that address). There
is no time window or TTL; invites are permanent records unless explicitly deleted.

### Security

- **Ownership enforced at the router level** before the service is called, using the existing
  `_owned_questionnaire_or_404` helper. The service itself also receives `owner_sub` but trusts the
  router to have already validated it.
- **Survey link is the plain public URL** — no secrets are embedded. The `?ref=invite_ref` token
  is a 16-hex-char random value used only for analytics attribution, not access control. Even if
  leaked it grants no extra access beyond what the public questionnaire link already exposes.
- **Rate limiting** prevents bulk abuse of the SES send path by a single owner. The limit uses
  `_bucket_limit` which is backed by `T.sessions`, the same table used by all other rate limiters.
- **Email normalisation** prevents header-injection vectors; `normalize_email` at
  `app/core/normalize.py:60` strips whitespace and lowercases before storing.
- **Maximum recipients per call (500)** limits the blast radius of a single compromised session.
- **Audit trail**: every distribution call writes an audit event to `T.alerts` via `audit_event`.

## 8. Backward Compatibility & Migration

### No schema migration required

New `SURVEY_INVITE#` rows are appended to the existing `questionnaires` table. Existing rows
(`META`, `SECTION#`, `QUESTION#`, `VERSION#`, `RESP#`, `ANSWER#`, `EVENT#RESP#`, `PDF#RESP#`) are
untouched. The `DynamoQuestionnaireRepository` class is not modified; the new service directly calls
`T.questionnaires` (not through the repo class) to avoid coupling the new namespace to the existing
protocol. If the repo class is later refactored to expose a `list_survey_invites` method, that is a
non-breaking additive change.

### Flag-off safety

With `CRM_SURVEY_DISTRIBUTION_ENABLED=0` (the default):

- `_require_crm_survey_distribution_enabled()` raises `HTTPException(404)` before any DDB or email
  call is made.
- `crm_survey_distribution.py` is never imported by the router until the guard passes.
- `T.questionnaires` already exists and is unmodified.
- No new table is created; `just restart` produces exactly the same tables as before.

### Rolling deployment

Because EVT-008 only adds new endpoints and a new SK prefix, there is no window during a rolling
deploy where old and new instances would conflict. An old instance sees no `SURVEY_INVITE#` rows; a
new instance writes them. Both can serve the existing questionnaire endpoints without interference.

### 9.1 Hermetic pytest unit tests: `tests/test_evt_008_survey_distribution.py`

Test isolation follows the canonical form used in `tests/test_questionnaire_draft_routes.py:14-89`

**Test setup:**

```python
import types
from copy import deepcopy
from unittest.mock import patch

import pytest
from app.core import tables as tables_mod
from app.core.time import now_ts
import app.services.crm_survey_distribution as svc

class _FakeTable:
    def __init__(self):
        self.items: dict[tuple[str, str], dict] = {}

    def put_item(self, *, Item, ConditionExpression=None, **kw):
        key = (Item["pk"], Item["sk"])
        if ConditionExpression and key in self.items:
            raise _ConditionalCheckFailed()
        self.items[key] = deepcopy(Item)

    def get_item(self, *, Key):
        return {"Item": deepcopy(self.items.get((Key["pk"], Key["sk"])))}

    def query(self, **kw):
        prefix = kw.get("ExpressionAttributeValues", {}).get(":sk_prefix", "")
        pk = kw.get("ExpressionAttributeValues", {}).get(":pk", "")
        rows = [deepcopy(v) for v in self.items.values()
                if v.get("pk") == pk and v.get("sk", "").startswith(prefix)]
        return {"Items": rows}

class _ConditionalCheckFailed(Exception):
    response = {"Error": {"Code": "ConditionalCheckFailedException"}}

_FAKE = _FakeTable()

    object.__setattr__(tables_mod.T, "questionnaires", _FAKE)
```

## 10. Open Questions / Assumptions

1. **Re-send capability** — this spec defines invite rows as write-once (idempotency guard).
   A future `DELETE /questionnaires/drafts/{id}/distribution-invites/{email}` endpoint would allow
   re-invitation after correction. Not in scope for EVT-008.

2. **Unsubscribe / opt-out link in email body** — CAN-SPAM / GDPR require an opt-out mechanism for
   marketing emails. The current `send_alert_email` signature does not support HTML body or footer
   injection. EVT-008 generates a plain-text email. Adding a proper opt-out footer is deferred to a
   future email-template ticket (see `docs/suitecrm/CRM_EMAIL_TICKETS.md`). The `survey_distribution`
   audit event provides a paper trail in the interim.

3. **`distribution-summary` response count** — the current design counts all submitted sessions
   regardless of whether the respondent was directly invited (no email→user_sub join). This is a
   conservative approximation. A precise count would require looking up `respondent_id` in the users
   table to retrieve email, then cross-referencing with invite rows. This cross-table join is deferred
   until PTY-001 provides a reliable contact→user_sub mapping.

4. **Email from-address / display name** — `send_alert_email` uses `S.alerts_from_email` as the
   sender. No per-questionnaire customisation of from-name is supported in EVT-008. If needed, this
   requires extending `send_alert_email` to accept an optional `from_name` parameter.

5. **`contact_list_id` path is 501** — the contact-list resolution stub intentionally returns 501
   (Not Implemented) rather than 422 to signal "the endpoint exists but this code path is pending a
   dependency", making the integration surface explicit for PTY/MKT teams.
