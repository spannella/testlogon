# CCT-006 — vCard import and export

**Type:** Feature | **Priority:** P2 | **Estimate:** 3d
**Source:** `docs/suitecrm/CRM_CONTACTS_EXTRA_TICKETS.md` — CCT-006 section
**Flag:** `PARTY_CRM_ENABLED` (existing, from PTY-001) — default OFF
**New service file:** `app/services/party_vcard.py`

---

## 1. Summary & Goal

SuiteCRM's Contacts module provides first-class vCard (.vcf) import and export so users can move contacts between standard address-book clients (iOS Contacts, Google Contacts, Outlook, Thunderbird, CardDAV servers) and the CRM. The testlogon platform's existing social-graph contacts surface (`app/routers/contacts.py`) has no address-book interchange capability. The PTY-001..PTY-015 Party/CRM buildout introduces the data model needed to carry this information (parties, contact mechs, relationships), but none of those tickets address vCard serialisation or parsing.

CCT-006 adds vCard 3.0 export and import to the party surface by introducing a new `app/services/party_vcard.py` module — a pure-Python, self-contained implementation following the dependency-free pattern already established by `app/services/receipts.py` and `app/services/audit_export_pipeline.py`. No external library (e.g. `vobject`, `py-vcard`) is added.

**Export goal:** `GET /ui/party/parties/{party_id}/vcard` — produces a standards-compliant vCard 3.0 `.vcf` file from a party's stored data (META row + contact mechs + EMPLOYMENT relationship). Returned as a binary HTTP response with `Content-Type: text/vcard`.

**Import goal:** `POST /ui/party/vcard-import` — accepts a `.vcf` upload (single record or multi-record, up to 500 vCards), idempotently creates or returns `CrmPartyOut` records for each vCard, and wires all `EMAIL`/`TEL`/`ADR` fields as contact mechs.

Both endpoints are gated by `S.party_crm_enabled` (default OFF) and emit audit events. No S3 storage is required — export streams bytes directly; import reads the upload in-memory. The platform is byte-for-byte unchanged with the flag off.

### 3.3 Idempotency key scheme for import

Re-importing the same vCard file must not create duplicate party records. The idempotency key is a deterministic `correlation_id` passed to `create_party` (PTY-004's conditional-put pattern, `docs/ofbiz/specs/PTY-004.md:§2.3`):

```
correlation_id = "VCARD:" + sha256(fn_value + ":" + first_email_or_empty).hexdigest()[:32]
```

where `fn_value` is the normalized (stripped, lowercased) `FN` property value and `first_email_or_empty` is the first `EMAIL` value present (or empty string if none). This matches the `commerce_order_service.py:67` pattern (`hashlib.sha256(corr.encode("utf-8")).hexdigest()[:32]`). On `ConditionalCheckFailedException`, `create_party` returns the existing item — CCT-006 counts it as `existing`.

The same `correlation_id = "VCARD_MECH:" + sha256(party_id + ":" + mech_type + ":" + normalized_value).hexdigest()[:32]` is passed to `add_contact_mech` for each mech, making mech creation idempotent too (PTY-007 `correlation_id` idempotency, `docs/ofbiz/specs/PTY-007.md:§4.1 step 5-7`).

#### `export_party_as_vcard` internals

1. Call `get_party(party_id)` — raises `HTTPException(404, "party_not_found")` if absent.
2. Call `list_contact_mechs(party_id, mech_type=None)` to retrieve all EMAIL, PHONE, POSTAL items.
3. For EMPLOYMENT relationship: call `list_relationships(party_id, direction="from", limit=50)` and filter items with `relationship_type == "EMPLOYMENT"`. If any EMPLOYMENT edge exists, call `get_party(to_party_id)` to fetch the org name.
4. Build vCard 3.0 lines:
   - `BEGIN:VCARD`
   - `VERSION:3.0`
   - `UID:{party_id}`
   - `REV:{updated_at as ISO-8601 UTC}` — formatted via `datetime.fromtimestamp(updated_at, tz=timezone.utc).strftime("%Y%m%dT%H%M%SZ")`
   - For `PERSON`: `FN:{display_name}`, `N:{last};{first};;;` (split on last space; if unsplittable, `N:{display_name};;;;`)
   - For `PARTY_GROUP`: `FN:{display_name}`, `ORG:{display_name}`
   - For each EMAIL mech: `EMAIL;TYPE={purpose_type}:{value}` where `purpose_type` is `WORK` if `WORK_EMAIL` in `purposes`, `HOME` if `HOME_EMAIL` in purposes, else `INTERNET`.
   - For each PHONE mech: `TEL;TYPE={purpose_type}:{e164_value}` where `purpose_type` is `WORK` if `WORK_PHONE` in purposes, `CELL` if `MOBILE_PHONE` in purposes, else `VOICE`.
   - For each POSTAL mech: `ADR;TYPE=WORK:;;{line1};{city};{state};{postal_code};{country}` (vCard 3.0 ADR field order: PO Box; extended; street; city; state; postal; country).
   - If EMPLOYMENT edge present: `ORG:{org_name}` (for PERSON) or second `ORG` line (title, if available).
   - `END:VCARD`
5. Encode all lines as UTF-8, folding any line > 75 characters per RFC 6350 §3.2 (fold by inserting `\r\n ` at character 75).
6. Emit `audit_event("party.vcard_export", actor_sub, party_id=party_id)`.
7. Return `(vcf_bytes, display_name)`.

#### `import_vcard` internals

1. Decode `vcf_bytes` as UTF-8 (fallback: latin-1).
2. Call `_parse_vcards(text)` → list of property dicts.
3. If `len(records) > MAX_VCARDS_PER_IMPORT`: raise `HTTPException(400, "too_many_vcards")`.
4. For each record:
   a. Extract `FN` value (first); if absent, use `ORG` value; if both absent, mark record as skipped (`skipped += 1`), continue.
   b. Determine `party_type`: `PARTY_GROUP` if `ORG` property is present AND `N` property is absent; else `PERSON`.
   c. Compute `correlation_id = "VCARD:" + sha256(fn_normalized + ":" + first_email_or_empty)[:32]`.
   d. Call `create_party(party_type, correlation_id=correlation_id)` — on `ConditionalCheckFailedException` (idempotent replay), retrieve the existing party; increment `existing`; else increment `imported`.
   e. For each `EMAIL` property value:
      - Try `normalize_email(value)` — on exception, skip this EMAIL (do not abort the record).
      - Compute mech `correlation_id = "VCARD_MECH:" + sha256(party_id + ":EMAIL:" + normalized_email)[:32]`.
      - Infer `purposes` from TYPE param: `WORK_EMAIL` if `TYPE=WORK`, `HOME_EMAIL` if `TYPE=HOME`, else `["PRIMARY_EMAIL"]`.
      - Call `add_contact_mech(party_id, "EMAIL", normalized_email, purposes, correlation_id=mech_corr_id)` — idempotent on replay.
   f. For each `TEL` property value:
      - Try `normalize_phone(value)` wrapped in `try/except Exception` — on failure, skip this TEL.
      - Compute mech `correlation_id = "VCARD_MECH:" + sha256(party_id + ":PHONE:" + e164)[:32]`.
      - Infer `purposes` from TYPE param: `WORK_PHONE` if `TYPE=WORK`, `MOBILE_PHONE` if `TYPE=CELL`, else `["PRIMARY_PHONE"]`.
      - Call `add_contact_mech(party_id, "PHONE", e164, purposes, correlation_id=mech_corr_id)`.
   g. For each `ADR` property value:
      - Parse the semicolon-delimited ADR fields into `{line1, city, state, postal_code, country}`.
      - Compute mech `correlation_id = "VCARD_MECH:" + sha256(party_id + ":POSTAL:" + sha256(canonical_json)[:16])[:32]`.
      - Call `add_contact_mech(party_id, "POSTAL", addr_dict, ["GENERAL_CORRESPONDENCE"], correlation_id=mech_corr_id)`.
   h. Emit `audit_event("party.vcard_import", actor_sub, party_id=party_id, source="vcf", was_existing=(record was idempotent replay))`.
5. Return `{"imported": int, "existing": int, "skipped": int, "parties": List[CrmPartyOut]}`.

## 5. Detailed Behavior & Edge Cases

### 5.1 vCard 3.0 vs 4.0

Export always produces vCard **3.0** (`VERSION:3.0`). Import accepts both 3.0 and 4.0 (the parser does not reject on version; it reads properties regardless). Version mismatch in `TYPE` parameter syntax (4.0 drops `TYPE=` prefix) is handled by the parser normalising param values to uppercase and stripping the optional `TYPE=` prefix.

### 5.2 Line folding (RFC 6350 §3.2)

Export folds any logical line exceeding 75 octets by inserting `\r\n ` (CRLF + SP) at byte boundary 75. The fold point must not split a multi-byte UTF-8 sequence — back off to the last safe boundary before byte 75. Import's `_unfold_vcf` joins continuation lines (those starting with SP or HT) before property parsing. Folding/unfolding is the only RFC compliance complexity in the pure-Python parser; all other vCard syntax is straightforward `PROPERTY;PARAM:VALUE` splitting.

### 5.3 Name splitting for PERSON `N` property

vCard `N` property is `familyName;givenName;additionalNames;honorificPrefixes;honorificSuffixes`. CCT-006 uses a simple last-space split: `parts = display_name.rsplit(" ", 1)` → `N:{parts[1]};{parts[0]};;;;` if two parts; `N:{display_name};;;;` if no space. This is the same heuristic used by many address-book clients and is acceptable for Phase 1. A future ticket can add structured name fields to the party META row.

### 5.4 PARTY_GROUP vCard: `ORG` vs `N`

Import decision: `PARTY_GROUP` if an `ORG` property is present AND `N` is absent. If both are present, treat as `PERSON` with an org affiliation (the `ORG` line becomes the EMPLOYMENT target — not created automatically during import since the target org may not exist yet). Exporting a `PARTY_GROUP` emits both `FN` and `ORG` but no `N` property.

### 5.5 Multi-record `.vcf` (vCard book)

A `.vcf` file may contain multiple records separated by `BEGIN:VCARD` / `END:VCARD` boundaries. The parser splits on `BEGIN:VCARD` after unfolding. Each record is processed independently and atomically — a failure on record N (e.g. missing FN) increments `skipped` and does not roll back records 1..N-1 (already written to DynamoDB). The client receives the final `VCardImportResultOut` with per-category counts.

### 5.6 Import idempotency and re-import

A `.vcf` file imported a second time with identical content must produce: `imported=0`, `existing=N` (all N parties matched by `correlation_id`), no duplicate party rows, no duplicate mech rows. This relies on `create_party` and `add_contact_mech` both using `ConditionExpression="attribute_not_exists(PK)"` with deterministic IDs — as specified by PTY-004 (`docs/ofbiz/specs/PTY-004.md:§2.3`) and PTY-007 (`docs/ofbiz/specs/PTY-007.md:§4.1 step 5-7`).

### 5.7 EMAIL field skip vs record skip

A malformed email in a `TEL` or `EMAIL` property is **field-skipped** (the record continues; the field is simply not added as a contact mech). A record with no recoverable `FN` or `ORG` property is **record-skipped** entirely (increments `skipped`, adds nothing to DynamoDB). A vCard file with more than `MAX_VCARDS_PER_IMPORT = 500` records is rejected **before any DynamoDB write** with `HTTP 400 {"detail": "too_many_vcards"}`.

### 5.8 QUOTED-PRINTABLE and BASE64 encoded values

The parser recognises `ENCODING=QUOTED-PRINTABLE` and `ENCODING=BASE64` (vCard 2.1 holdovers sometimes present in Outlook exports). For QUOTED-PRINTABLE, decode using `quopri.decodestring`. For BASE64, decode using `base64.b64decode`. On decode failure, treat as a raw string (passthrough). Photo/binary properties (`PHOTO`, `SOUND`, `KEY`) are silently ignored during import — CCT-006 maps text-representable properties only.

### 5.9 File size limit

Import reads the entire file into memory. A 500-record file with full postal addresses and multiple mechs is under 200 KB in practice. No explicit byte-length limit is enforced beyond the platform's existing request-body size limit (Uvicorn default: 1 MB). If the file cannot be decoded as UTF-8 or latin-1, `import_vcard` raises `HTTPException(400, "invalid_encoding")`.

### 5.10 Actor authorization on export

`require_ui_session` provides `ctx["user_sub"]`. CCT-006 does **not** enforce that `actor_sub == party.user_sub`. Any authenticated user can export any party's vCard (party records are the authenticated user's own contacts in the CRM model). A future ticket may add per-party ACL. For now, the access gate is `require_ui_session` (authenticated = authorized).

### 5.11 Content-Disposition filename sanitization

The `display_name` field from the party META may contain characters illegal in HTTP header values. The filename is sanitised with `re.sub(r'[^\w\- ]', '_', display_name)[:60]` before embedding in the `Content-Disposition` header. This preserves alphanumeric, hyphens, underscores, and spaces; all other characters become `_`.

### 5.12 UTF-8 vCard content

vCard properties containing non-ASCII characters (accented names, CJK characters) are written UTF-8 encoded with `CHARSET=UTF-8` declared on the `VERSION:3.0` line — not per-property (per-property CHARSET params are vCard 2.1 style; vCard 3.0 mandates UTF-8 globally). The `Content-Type: text/vcard; charset=UTF-8` header signals this to the client.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No dev_mode branches

`app/services/party_vcard.py` contains **zero** `if S.dev_mode` conditionals. The vCard formatter and parser are pure-Python with no AWS dependencies. DynamoDB reads/writes go through `app/services/party.py` (which itself has no dev_mode branches per the PTY spec constraints). This ensures identical behaviour in dev (DynamoDB Local / moto) and production (real DynamoDB). The SECOPS-007 parity requirement is met structurally — there is nothing to branch.

### 7.2 S3 not used

Export streams bytes directly to the HTTP response; import reads bytes into memory. No S3 `put_object` or `get_object` call is made. This means no `app.core.aws_clients.s3_client` import is needed — no S3 mock/real divergence exists.

### 7.3 KMS not used

vCard content is not encrypted at rest in CCT-006. Party META and contact mechs are stored as plain DynamoDB attributes (the same as all other party data). If field-level encryption is needed for sensitive contact data, it is a future concern (e.g., CCT-007 or a security hardening ticket).

### 7.4 Idempotency guarantees

**Export:** Pure read — calling `export_party_as_vcard` multiple times for the same `party_id` produces identical byte output (given no DDB updates between calls). Safe to retry.

**Import:** `create_party` and `add_contact_mech` both use deterministic `correlation_id` + `ConditionExpression="attribute_not_exists(PK)"` (PTY-004 `docs/ofbiz/specs/PTY-004.md:§2.3`; PTY-007 `docs/ofbiz/specs/PTY-007.md:§4.1 step 7`). Re-submitting the same `.vcf` is always safe — no duplicate rows are created. The response correctly reflects `existing` vs `imported` counts.

### 7.5 Audit trail

Every successful export emits `audit_event("party.vcard_export", actor_sub, party_id=party_id)`. Every successfully-created-or-matched party during import emits `audit_event("party.vcard_import", actor_sub, party_id=party_id, source="vcf", was_existing=bool)`. Audit events are fire-and-forget (wrapped in `try/except`) — an audit write failure never blocks the response.

### 7.6 Input validation and injection prevention

- `vCard property values` are read-only from trusted DynamoDB data during export; no user-controlled string is interpolated into DynamoDB key expressions.
- During import, all values pass through the respective normalizers (`normalize_email`, `normalize_phone`, `normalize_address_payload`) before reaching DynamoDB. Raw vCard strings are never written to DDB without normalisation.
- The `Content-Disposition` filename is sanitised (§5.11) to prevent header injection.
- The `.vcf` upload is read as raw bytes; no subprocess, `eval`, or `exec` is involved.

## 10. Open Questions / Assumptions

1. **Structured name fields on party META**: CCT-006 assumes `display_name` is the only name field on the party META row (as specified by PTY-003 and PTY-004). Splitting for `N:` property is heuristic (last-space split). If PTY-003 is later extended to store `given_name` / `family_name` separately, the export function should be updated to use those fields.

2. **ORG line on PERSON with EMPLOYMENT**: CCT-006 exports `ORG:{org_name}` for a PERSON who has an `EMPLOYMENT` edge. If the same party has multiple EMPLOYMENT edges (e.g. contractor with two clients), only the first EMPLOYMENT edge's target name is used. This is an acceptable simplification for Phase 1.

3. **Photo / avatar export**: `app/services/profile.py:305-316` (`get_profile_identity`) returns `profile_photo_url`. vCard 3.0 supports `PHOTO` as a URL value (`PHOTO;VALUE=URI:https://...`). This ticket does NOT export photos — the party META row does not store a profile photo in the PTY data model. If PTY-010 (profile-to-party sync) imports profile photos onto party records, a follow-up can add `PHOTO` export.

4. **ADR type on import**: All imported `ADR` values are assigned `purposes=["GENERAL_CORRESPONDENCE"]`. vCard TYPE params (`TYPE=HOME`, `TYPE=WORK`) on `ADR` lines could map to different purposes, but this detail is deferred to a follow-up ticket.

5. **`vcard_import_max_records` setting placement**: The setting is added to `app/core/settings.py`. If the PTY-001 spec specifies a dedicated section for party CRM settings, place `vcard_import_max_records` immediately after the existing `party_crm_enabled` field.

6. **Assumption: `list_relationships` pagination**: CCT-006 calls `list_relationships(party_id, direction="from", limit=50)` to find EMPLOYMENT edges during export. This assumes a party has fewer than 50 outbound relationships. If a party has more (unusual in practice), only the first 50 are inspected. A cursor loop is not implemented — this is an explicit simplification for Phase 1.
