# RPT-005 — Report charts (bar, line, pie)

**Type:** Feature | **Priority:** P2 | **Estimate:** 2d
**Area:** CRM Reports & Dashboards
**Source:** `docs/suitecrm/CRM_REPORTS_TICKETS.md` (RPT-005 section, lines 243–285)

---

## 1. Summary & Goal

RPT-005 attaches an optional chart definition (`ChartConfig`) to a report so that the frontend can render a bar chart, line chart, or pie chart alongside the tabular output of `run_report`. The chart definition travels with the report META row and is echoed unchanged in every `ReportRunOut`; all rendering logic lives in the browser using recharts, which is already a project dependency.

The SuiteCRM gap analysis marks this capability PARTIAL: recharts chart components already exist across several pages — `BarChart`/`Bar` in `frontend/src/pages/affiliates/AffiliateDashboard.tsx:4-12`; `BarChart`/`PieChart`/`Pie`/`Cell`/`ComposedChart`/`Line` in `frontend/src/pages/analytics/AnalyticsPage.tsx:14-30`; `LineChart`/`Line` in `frontend/src/pages/analytics/EngagementRateSection.tsx:14-21`; and `AreaChart`/`Area` (NOT Bar/Line/Pie) in `frontend/src/pages/earnings/EarningsPage.tsx:10-19`. [CORRECTED: EarningsPage imports `AreaChart`/`Area`, not `BarChart`/`LineChart`/`PieChart`; see §2.1 per-file detail.] The gap is that no user-defined report exists to attach a chart to, and there is no shared `ReportRunView` component. RPT-005 closes this gap by adding:

1. A `ChartConfig` Pydantic model and a `chart` field on `ReportCreateIn` (backend, additive).
2. Storage and echo of `chart` on the `crm_reports` META row (service layer, no new table).
3. A React `ReportRunView` component that renders the appropriate recharts chart when `chart` is present.
4. A `ReportsPage` and `ReportBuilderPage` that together form the user-facing report UI introduced by this ticket (the ticket description assigns the frontend shell here).
5. Axios endpoint wrappers and React Query hooks in `frontend/src/api/endpoints/crmReports.ts`.

All new behaviour is inert when `S.crm_reports_enabled` is `False` (the default). No existing file is modified in a breaking way; all additions are purely additive.

## 3. Data Model

### 3.1 No new DynamoDB table

RPT-005 extends the existing `crm_reports` table (created by RPT-001) by persisting a `chart` attribute on the META row. No schema change is needed because the table uses a schemaless item design — `chart` is simply an additional map attribute on the META row.

### 3.2 META row additions

The META row (`pk=report_id`, `sk="META"`) gains one optional attribute:

```
chart: {                        # absent when no chart is configured
  "chart_type": "bar" | "line" | "pie",
  "x_field":   <string>,        # field name for x-axis labels / pie sector names
  "y_field":   <string>         # field name for y-axis values / pie sector sizes
}
```

Constraints:

- `x_field` and `y_field` must be field names present in the report's `fields` list (or a computed aggregate column key of the form `{field}_{FUNC}` produced by RPT-003's `_apply_group_by`). Validation is performed in the service layer at `create_report` and `update_report` time, not at DynamoDB write time.
- When `chart` is absent, `ReportRunOut.chart` is `None` and the frontend renders only the data table.
- `create_report` writes `chart` only when the request payload includes a non-null `chart` block. It is never written as a DynamoDB null.

### 3.3 RUN row — unchanged

The RUN row (`sk="RUN#{run_ts:010d}#{run_id}"`) is written by RPT-002's `run_report` and is not modified by RPT-005. The `chart` config is echoed in `ReportRunOut` by reading it from the META row at run time, not from the RUN row.

### 3.4 attr_types — no change

The numeric GSI sort key (`GSI1SK = created_at`, `attr_types={"GSI1SK": "N"}`) on the `owner-reports-index` was already declared in RPT-001. RPT-005 adds no new keys or indexes.

### 4.2 Service layer additions (`app/services/crm_reports.py`)

**`_validate_chart(chart: Optional[ChartConfig], fields: List[str], aggregates: List[AggregateSpec]) -> None`**

Pure-Python validator, called from `create_report` and `update_report`:

```python
def _validate_chart(chart, fields, aggregates):
    if chart is None:
        return
    # Build the set of valid column names: declared fields + aggregate columns
    agg_columns = {f"{a.field}_{a.function}" for a in (aggregates or [])}
    valid = set(fields) | agg_columns
    if chart.x_field not in valid:
        raise ValueError(f"x_field '{chart.x_field}' is not a declared field or aggregate column")
    if chart.y_field not in valid:
        raise ValueError(f"y_field '{chart.y_field}' is not a declared field or aggregate column")
```

**`create_report(owner_sub, payload)` — additive change**

After existing validation, call `_validate_chart(payload.chart, payload.fields, payload.aggregates)`. If `payload.chart` is non-null, include `"chart": payload.chart.model_dump()` in the META row item written to `T.crm_reports`. Return `ReportOut` with `chart=payload.chart`.

**`update_report(report_id, owner_sub, patch)` — additive change**

If `patch.chart` is explicitly set (not absent from the patch body), call `_validate_chart(patch.chart, effective_fields, effective_aggregates)` where `effective_fields` and `effective_aggregates` are the post-patch values. Write the new `chart` value (or remove the attribute when `patch.chart=None` is explicitly supplied) via the existing `update_item` call. Emit `audit_event("report.chart_config_updated", owner_sub, request, report_id=report_id)` from `app/services/alerts.py:644`.

**`get_report(report_id, owner_sub)` — additive change**

Return `ReportOut` with `chart=ChartConfig(**item["chart"])` when `"chart"` is present on the META row, else `chart=None`.

**`run_report(report_id, owner_sub)` — additive change**

After building `ReportRunOut`, read the `chart` attribute from the META row and populate `run_out.chart`. The chart config is not written into the RUN row; it is sourced from the META row. Return the augmented `ReportRunOut`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Chart type semantics and data shape expected by recharts

**Bar chart (`chart_type="bar"`):** `x_field` is the categorical axis (maps to recharts `dataKey` on `<XAxis>`); `y_field` is the value axis (maps to `dataKey` on `<Bar>`). `ReportRunView` transforms `rows: unknown[][]` into `{ [x_field]: string, [y_field]: number }[]` by zipping each row against the `columns` array. If `y_field` values are strings (e.g. raw DynamoDB output), they must be coerced to `Number(...)` before passing to recharts — a NaN result renders as zero (graceful degradation).

**Line chart (`chart_type="line"`):** Same data shape as bar. `x_field` is typically a date or time column; `y_field` is a numeric metric. Wraps in `<LineChart>` with `<Line type="monotone" dataKey={y_field} />`. Best used with time-series data (e.g. a billing ledger grouped by day).

**Pie chart (`chart_type="pie"`):** `x_field` is the `nameKey` (sector label); `y_field` is the `dataKey` (sector size). recharts `<Pie>` requires `nameKey` + `dataKey` props. Most useful for grouped reports from RPT-003 (e.g. `group_by="status"` with `COUNT` aggregate where `x_field="status"`, `y_field="*_COUNT"`).

### 5.2 Validation failures

- `_validate_chart` raises `ValueError`. The service layer catches this and re-raises as `HTTPException(status_code=422)`. This happens at `create_report` and `update_report` time, before any DynamoDB write.
- If `x_field == y_field`, the chart is technically valid (recharts will render it, albeit meaninglessly). The spec does not prohibit this — it is the user's responsibility to choose meaningful fields.
- A pie chart with more than 50 distinct sectors produces a visually unreadable chart. The backend does not limit sector count; the frontend should display a warning when `chart_type == "pie"` and `row_count > 50`.

### 5.3 PATCH behaviour for chart removal

A `PATCH /ui/crm/reports/{id}` body of `{"chart": null}` explicitly removes the chart config. The service layer detects this by checking `"chart" in patch_dict` (not `patch.chart is not None`). When `chart` is absent from the PATCH body entirely, the existing chart config is preserved. This follows the partial-update semantics already established for other nullable fields in the report definition.

### 5.4 Stale run results and chart config divergence

If a user edits the chart config (via `PATCH`) after a report has already been run, the stale RUN row does not carry the updated chart. `run_report` always reads the chart from the META row (not the RUN row), so the next call to `GET /run` (which returns the last RUN row augmented with the current META chart) will use the updated chart. There is no inconsistency provided the frontend always calls `POST /run` to get a fresh result after editing the definition.

The React Query key `["crm-report-run", reportId]` is invalidated by `ReportBuilderPage` after a successful `PATCH`, prompting a re-run reminder banner (`"Definition changed — re-run to refresh chart data"`).

### 5.5 Grouped report rows and column names

RPT-003's `_apply_group_by` returns group rows with keys of the form `{group_by_field}` and `{agg_field}_{FUNC}` (e.g. `status`, `amount_cents_SUM`, `amount_cents_AVG`, `*_COUNT`). These are valid column names for `x_field` and `y_field`. The `_validate_chart` helper in RPT-005 builds `agg_columns = {f"{a.field}_{a.function}" for a in aggregates}` and accepts these as valid `y_field` values.

### 5.6 Empty result sets

When `run_report` returns `row_count=0`, `ReportRunView` renders the data table as empty and suppresses the chart entirely (renders nothing for the chart pane, with an `"No data to chart"` placeholder). This prevents recharts from receiving an empty `data=[]` array which would otherwise render a blank axes-only chart.

### 5.7 Frontend — report without chart

When `ReportRunOut.chart` is `null` / `undefined`, `ReportRunView` renders only the `DataTable`. No chart toggle or empty chart placeholder is shown, matching SuiteCRM's behaviour for tabular-only reports.

### 5.8 `ReportsPage` — list and run actions

`ReportsPage` lists the user's reports via `listReports()` with infinite scroll (React Query `useQuery` with cursor). Each row shows report name, module, field count, last-run status, and three action buttons: "Run" (triggers `runReport` mutation + navigates to detail view), "Edit" (navigates to `ReportBuilderPage`), "Delete" (mutation with confirmation dialog). The `["crm-reports"]` query is invalidated after any mutation.

### 5.9 `ReportBuilderPage` — chart section

The chart section is collapsed by default, revealed by a "Enable chart" toggle (shadcn `Switch`). When enabled, the user picks chart type (`Select` with options bar/line/pie), then picks `x_field` and `y_field` from a `Select` populated with the report's current `fields` list plus any `aggregates` column names (computed client-side from the aggregates list). The section is disabled (greyed out) when the `fields` list is empty.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 — no dev_mode branch

RPT-005 introduces no `if S.dev_mode` branch. `_validate_chart` is a pure-Python function with no I/O. The DynamoDB write path goes through `_FloatSafeTable` (`app/core/tables.py:29`) and is identical in dev (moto via `DDB_ENDPOINT_URL=http://localhost:8001`) and prod (real DynamoDB). There is no S3, KMS, SES, or Stripe call added by this ticket.

### 7.2 Ownership enforcement

`get_report`, `update_report`, and `run_report` all compare `item["owner_sub"] != owner_sub` and raise `HTTPException(403)` before any write. This is enforced at the data-layer level in `app/services/crm_reports.py` (established by RPT-002). RPT-005 does not weaken or bypass this check.

### 7.3 Input validation

- `ChartConfig.chart_type` is constrained by `Field(..., pattern=r"^(bar|line|pie)$")` — validated by Pydantic before the service layer is entered.
- `x_field` and `y_field` are constrained to `min_length=1, max_length=100` by Pydantic.
- `_validate_chart` confirms both fields exist in the report's own `fields`/aggregates set. An attacker cannot reference fields from another user's report because `get_report` enforces ownership before `_validate_chart` is called.

### 7.4 Audit trail

Every `chart` modification via `PATCH` emits `audit_event("report.chart_config_updated", ...)` to `T.alerts` (`app/services/alerts.py:644`). `create_report` audit event (`report.created`) already includes the full serialised payload including `chart`. No separate audit infrastructure is needed.

### 7.5 Idempotency

`create_report` generates `report_id = "RPT#{uuid4().hex[:12]}"` (established by RPT-002) — each call produces a distinct item. `update_report` uses a conditional `update_item` with `attribute_exists(report_id)` to prevent phantom writes. A duplicate `PATCH` with the same `chart` payload is idempotent at the DynamoDB level (same values written) and emits an audit event each time (acceptable — audit events are write-once append items).

## 8. Backward Compatibility & Migration

### 8.1 Additive fields only

`chart` is `Optional[ChartConfig] = None` on both request and response models. Existing API clients that do not send `chart` will receive `"chart": null` in responses — a JSON null that is safely ignored by any existing consumer. No existing field is renamed, removed, or made required.

### 8.2 Existing META rows

Reports created by RPT-002 / RPT-003 before RPT-005 is deployed will have no `chart` attribute on their META row. `get_report` uses `item.get("chart")` and returns `None` when absent — no migration needed.

### 8.3 Existing RUN rows

RUN rows do not carry `chart`. `run_report` reads chart from the META row at the time of the call. Existing RUN rows are read by RPT-002's last-run-result path; RPT-005 augments this path to append the current META chart before returning. No RUN row backfill is needed.

### 8.4 `just restart` — no schema change

`scripts/local-ddb-init.py` does not need to be modified by RPT-005 (the `crm_reports` table definition was set up by RPT-001). The `chart` attribute is schemaless.

## 10. Open Questions / Assumptions

1. **API client style:** [RESOLVED during verification] `frontend/src/api/client.ts` does NOT export an axios instance — it exports a `fetch`-based `api<T>(path, options)` helper (`client.ts:151`). §4.4 has been rewritten to the real `api<T>()` call style; the original axios snippet was inaccurate.

2. **Frontend feature flag exposure:** [RESOLVED during verification] There is NO `GET /ui/config` endpoint exposing feature flags to the frontend. Frontend flags live in `frontend/src/lib/featureFlags.ts` (Vite `VITE_*` env vars via `toBool`). §6.3 now specifies adding `VITE_CRM_REPORTS_ENABLED` there. The backend API remains the authoritative gate (404 when off).

3. **Re-run reminder after PATCH:** The spec calls for a `"Definition changed — re-run to refresh chart data"` banner in `ReportBuilderPage`. Whether this is implemented as a React state flag or a React Query `isStale` check is left to the implementer. The key requirement is that `["crm-report-run", reportId]` is invalidated after a successful `PATCH`.

4. **`x_field == y_field` validation:** The spec explicitly allows this (Section 5.2). If product decides to prohibit it, a one-line addition to `_validate_chart` suffices.

5. **Pie chart with >50 sectors:** The spec says the frontend "should display a warning" (Section 5.2). This is a UI nicety; the exact threshold (50) is an assumption and may be adjusted.

6. **`*_COUNT` column naming:** `_apply_group_by` in RPT-003 produces the column key `{field}_{FUNC}` for COUNT with `field="*"` as `*_COUNT`. This is the assumed convention; if RPT-003 uses a different key (e.g. `count` or `row_count`), `_validate_chart` must be updated to match.
