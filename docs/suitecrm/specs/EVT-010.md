# EVT-010 — Survey bulk response export (CSV)

**Type:** Feature | **Priority:** P1 | **Estimate:** 1d
**Source:** `docs/suitecrm/CRM_MISC_TICKETS.md` (section "EVT-010")
**Dependencies:** None (extends `app/routers/csv_export.py` + `app/services/csv_export.py`; soft
dependency on EVT-008/EVT-009 for context; no new DynamoDB table required).

---

## 1. Summary & Goal

EVT-010 replaces the current stub implementation of `questionnaire_responses` CSV export with a
complete, per-question-column flat-file export. Today the route `GET /ui/export/csv?source=questionnaire_responses`
is fully wired through routing and ownership validation but the service layer only emits one opaque
`Answers` JSON blob per session row instead of one discrete column per question. This prevents
questionnaire owners from opening the download in spreadsheet software and filtering or pivoting
by individual answers.

After this change, every `status=submitted` session for a questionnaire produces one row in the CSV
where columns for each question ID are individually addressable. Sensitive answers encrypted at rest
via KMS are transparently decrypted by the existing repository method before export. The feature is
additive and gated behind a new flag (`CRM_SURVEY_EXPORT_ENABLED`, default `false`). With the flag
off the endpoint behaves exactly as it does today — the existing stub column schema remains active.

No new DynamoDB tables, no money-movement path, and no background worker are introduced.

## 2. Context & Current State

### 2.1 CSV export router

`app/routers/csv_export.py` exposes `GET /ui/export/csv` at line 27. The `source` query parameter
is validated by an inline regex at line 30 against the set `{"billing_ledger", "contacts",

1. Rejects missing `questionnaire_id` with HTTP 422.
2. Instantiates `DynamoQuestionnaireRepository()` and calls `get_questionnaire(questionnaire_id)`;

Rate limiting is applied before ownership validation: `_bucket_limit(user_sub, "rl#csv_export",

### 2.2 Current service stub

`app/services/csv_export.py` handles `questionnaire_responses` at line 222. The column list is:

```python
QUESTIONNAIRE_COLUMNS = ["Respondent ID", "Started At", "Submitted At", "Status",
                         "Duration (s)", "Version", "Answers"]
```

(line 35). The iterator `_iter_questionnaire_responses` (line 113) calls
`DynamoQuestionnaireRepository().list_response_sessions(questionnaire_id=questionnaire_id)` and
yields each session row directly (line 119). The formatter `_format_questionnaire_row` (line 169)
produces seven columns and places `json.dumps(item.get("answers", {}))` — the session-level

empty JSON object `{}` for all sessions.

### 2.3 Repository methods available

`DynamoQuestionnaireRepository` (defined in `app/services/questionnaires_repository.py`) provides
all required primitives:

- `list_response_sessions(questionnaire_id=...)` (line 492) — queries `SK begins_with "RESP#"`,
  filters `entity_type == "response_session"`, returns sorted by `started_at`. Already used by the
  stub iterator.
- `list_session_answers(questionnaire_id=..., response_session_id=...)` (line 573) — queries
  `SK begins_with "ANSWER#{response_session_id}#"`, assembles `{question_id: value}`. For answers
  where `row.get("value_encrypted") == True` it calls `_decrypt_sensitive_answer` (line 566),
  which calls `kms_decrypt` from `app/core/crypto.py`. This runs against mock KMS in dev and real
  KMS in prod — no dev-mode branch (SECOPS-007 compliant).
- `build_schema_snapshot(questionnaire_id)` (line 312) — returns
  `{questionnaire_id, sections: [{section_id, title, questions: [{question_id, type, label, ...}]}]}`.
  Used by `publish_draft` (line 368) to snapshot the form at publish time.
- `get_version_by_id(questionnaire_id, version_id)` (line 349) — returns the version row carrying
  the `schema_json` snapshot.
- `list_versions(questionnaire_id)` (line 340) — returns all versions sorted by `version_number`.

### 2.4 CSV injection sanitisation

`_sanitize_csv_field` (line 43) prefixes any string that starts with a formula-injection character
(`=`, `+`, `-`, `@`, `\t`, `\r`) with a single-quote. All string fields in the new per-question
columns must pass through this helper before being handed to `csv.writer`.

### 2.5 MAX_EXPORT_ROWS safety cap

`MAX_EXPORT_ROWS = 50_000` (line 28) in `app/services/csv_export.py`. The current stub applies
this cap by slicing `sessions[:MAX_EXPORT_ROWS]` (line 120). The new implementation must apply the
same cap; answers rows do not count separately.

### 2.6 Feature flag

No CRM survey export flag exists in `app/core/settings.py` today (confirmed by grep). The
`crm_events_enabled` family of flags is not yet present in settings either — all EVT-001 through
EVT-009 are also unimplemented in the live settings file. EVT-010 adds its own flag in isolation,
consistent with the cross-cutting constraint that every CRM ticket introduces its own flag.

## 3. Data Model

EVT-010 introduces **no new DynamoDB tables**. It reads entirely from the existing `questionnaires`
table (configured via `S.questionnaire_table_name`, default `"questionnaires"`;
`scripts/local-ddb-init.py:128`).

### 3.1 Relevant existing table structure

```
Table: questionnaires   PK=pk (S)  SK=sk (S)

Key patterns consumed by this ticket (PK prefix is `QNR#`, produced by
`_q_pk` at `app/services/questionnaires_repository.py:686-687`):
  PK=QNR#{questionnaire_id}  SK=META
      → questionnaire row: owner_id, title, status, published_version_id

  PK=QNR#{questionnaire_id}  SK=VERSION#{version_number:06d}
      → version row: version_id, schema_json (sections/questions snapshot)

  PK=QNR#{questionnaire_id}  SK=RESP#{response_session_id}
      → session row: response_session_id, version_id, respondent_id,
                     status, started_at, submitted_at, current_section_index

  PK=QNR#{questionnaire_id}  SK=ANSWER#{response_session_id}#{question_id}
      → answer row: question_id, value | value_enc+value_encrypted
```

GSIs declared in `scripts/local-ddb-init.py:131–136`:
- `owner-updated-index` — PK=`gsi_owner_pk`, SK=`gsi_owner_sk`
- `status-updated-index` — PK=`gsi_status_pk`, SK=`gsi_status_sk`
- `published_slug-index` — PK=`gsi_published_pk`, SK=`gsi_published_sk`
- `response_status-updated-index` — PK=`gsi_response_status_pk`, SK=`gsi_response_status_sk`

None of these GSI sort keys are numeric, so no `attr_types` change is needed for this ticket. The
existing `TableDef` at `scripts/local-ddb-init.py:127–137` remains unchanged.

### 3.2 Schema column derivation

The ordered list of question IDs that become CSV header columns is derived at export time from the
questionnaire's **published version snapshot**, not from live section/question rows. Specifically,
the export reads `schema_json.sections[*].questions[*]` from the version matching
`q["published_version_id"]` (resolved via `get_version_by_id`). This ensures the column order is
stable and reflects what respondents actually answered, even if questions were later reordered or
added to a new draft.

If a questionnaire has never been published (no `published_version_id`), the export falls back to
`build_schema_snapshot(questionnaire_id)`, which reads live section/question rows ordered by
`position`. This covers the case where a questionnaire owner begins collecting responses before
publishing (possible for `visibility=private`).

## 4. API / Service Design

### 4.1 No new endpoints or route changes

The existing endpoint `GET /ui/export/csv` in `app/routers/csv_export.py:27` already accepts
`source=questionnaire_responses` and `questionnaire_id`. No new parameters, no new routes, and no
change to the router are needed. All changes are confined to `app/services/csv_export.py`.

The endpoint signature (for reference):
```
GET /ui/export/csv
  ?source=questionnaire_responses
  &questionnaire_id=<id>
  [&from_date=<unix_ts>]   # filter sessions by submitted_at >= from_date
  [&to_date=<unix_ts>]     # filter sessions by submitted_at <= to_date
Auth: require_ui_session (cookie + CSRF, or Bearer)
Response: StreamingResponse, Content-Type: text/csv; charset=utf-8, UTF-8 BOM
```

The flag guard is enforced inside `generate_csv_rows` (see §4.3) rather than in the router, so
the router's ownership validation still runs and returns 403/404 correctly regardless of flag state.

### 4.2 Updated `QUESTIONNAIRE_COLUMNS` constant

The existing constant in `app/services/csv_export.py:35` becomes a fallback-only constant renamed
`_QUESTIONNAIRE_STATIC_COLUMNS`:

```python
_QUESTIONNAIRE_STATIC_COLUMNS = [
    "session_id", "respondent_id", "started_at", "submitted_at",
    "status", "duration_s", "version_id",
]
```

These seven static columns always appear at the left of the header row. Dynamic question columns
follow in `schema_json` order (see §4.3).

The module-level `QUESTIONNAIRE_COLUMNS` list is **removed** (no external callers reference it —
confirmed by search; it is only used internally in `generate_csv_rows`).

### 4.3 New `_build_questionnaire_export_columns` helper

```python
def _build_questionnaire_export_columns(
    repo: DynamoQuestionnaireRepository,
    questionnaire_id: str,
) -> tuple[list[str], list[tuple[str, str]]]:
    """Return (header_row, question_meta) where question_meta is a list of
    (question_id, question_label) pairs in schema order.
    """
```

Implementation:
1. Load the questionnaire META row via `repo.get_questionnaire(questionnaire_id)`.
2. Resolve `published_version_id`; if set call `repo.get_version_by_id(questionnaire_id,
   published_version_id)` and use its `schema_json`. If not set call
   `repo.build_schema_snapshot(questionnaire_id)`.
3. Walk `schema_json["sections"]` → `section["questions"]` in position order; collect
   `(question["question_id"], question["label"])` pairs.
4. Construct `header = _QUESTIONNAIRE_STATIC_COLUMNS + [q_id for q_id, _ in question_meta]`.
5. Return `(header, question_meta)`.

This function performs purely read operations and raises no exception on an empty schema (returns
an empty `question_meta` list, producing a header with only the seven static columns).

### 4.4 Updated `_iter_questionnaire_responses`

```python
def _iter_questionnaire_responses(
    questionnaire_id: str,
    question_ids: list[str],
    *,
    from_date: int | None = None,
    to_date: int | None = None,
    submitted_only: bool = True,
) -> Generator[dict[str, Any], None, None]:
```

Implementation:
1. Construct `repo = DynamoQuestionnaireRepository()`.
2. Call `repo.list_response_sessions(questionnaire_id=questionnaire_id)` — paginated via the
   existing `LastEvaluatedKey` loop in `list_response_sessions` (line 493). The current
   implementation does not loop (DDB `query` returns up to 1MB); since a questionnaire's sessions
   share a single DDB partition key this is safe for up to ~50K sessions per partition but the cap
   at step 4 provides a hard ceiling.
3. For each session in the returned list (up to `MAX_EXPORT_ROWS`):
   a. If `submitted_only` is True, skip sessions where `session.get("status") != "submitted"`.
   b. Apply `from_date`/`to_date` filters against `int(session.get("submitted_at", 0))`.
   c. Call `repo.list_session_answers(questionnaire_id=questionnaire_id,
      response_session_id=session["response_session_id"])` — returns `{question_id: value}`.
   d. Build a merged dict: `{**session, "answers_map": answers}`.
   e. Yield the merged dict.
4. Stop after yielding `MAX_EXPORT_ROWS` total rows (existing safety cap).

### 4.5 Updated `_format_questionnaire_row`

```python
def _format_questionnaire_row(
    item: dict[str, Any],
    question_ids: list[str],
) -> list[str]:
```

Implementation:
1. Extract static columns:
   - `session_id` = `item.get("response_session_id", "")`
   - `respondent_id` = `item.get("respondent_id", item.get("user_sub", "anonymous")) or "anonymous"`
   - `started_at` = `_ts_to_iso(item.get("started_at", 0))`
   - `submitted_at` = `_ts_to_iso(item.get("submitted_at", 0))`
   - `status` = `item.get("status", "")`
   - `duration_s` — computed as `int(submitted_at) - int(started_at)` if both are present and
     `submitted >= started`, else empty string (same logic as current line 178).
   - `version_id` = `item.get("version_id", "")`
2. For each `q_id` in `question_ids`, look up `item.get("answers_map", {}).get(q_id)`. Coerce to
   string: if the value is a `list` (multiselect) join with `"; "`; if `None` or absent emit `""`.
3. Pass every string value through `_sanitize_csv_field` before appending.
4. Return the flat `list[str]`.

### 4.6 Updated `generate_csv_rows` branch

The `elif source == "questionnaire_responses":` branch in `generate_csv_rows` (currently
lines 222–227) is replaced with:

```python
elif source == "questionnaire_responses":
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Column ordering stability

Question columns follow the order of `schema_json["sections"][*]["questions"]` sorted by
`section.position` then `question.position`. This is the same order used by
`build_schema_snapshot` (line 312–338) and the questionnaire renderer. Consumers who import the
CSV multiple times for the same questionnaire will see a consistent column layout as long as the
published version does not change.

### 5.2 Multi-version questionnaires

A questionnaire can accumulate sessions across multiple published versions, and different versions
may have different question sets. The export is always driven from the **latest published version**
(`published_version_id` on the META row). Sessions answered against an older version may have
answers for question IDs that no longer exist in the latest schema — those answers still appear in
the `answers_map` and will land under their column if the question ID exists in the header, or be
silently dropped if not (because the column enumeration is driven by the latest schema). Sessions
answered against the latest version will have answers for all current question IDs.

This is the simplest behaviour consistent with the SuiteCRM source analogue (which also exports
against the current form structure). An open question (see §10) is whether a per-version export
parameter should be added in a follow-up ticket.

### 5.3 Status filter

By default only `status=submitted` sessions are included (`submitted_only=True`). This matches the
acceptance criterion in the ticket: "Only `status=submitted` sessions are included by default." The
query parameter `status` is not currently exposed by the router endpoint. If an owner wants
`in_progress` sessions (e.g., for debugging partial responses), this is a future extension and is
not in scope for EVT-010.

### 5.4 Date range filters

`from_date` and `to_date` are already accepted by the router (lines 34–43) and passed through to
`generate_csv_rows`. In the new implementation they filter on `submitted_at` (Unix timestamp) of
each session. The comparison is `int(session["submitted_at"]) >= from_date` and
`int(session["submitted_at"]) <= to_date`. Sessions without a `submitted_at` value are excluded
when `submitted_only=True` (they will also lack `status=submitted`).

### 5.5 Sensitive (KMS-encrypted) answers

Answers for `address`, `date`, `time`, and `timezone` question types may be encrypted when
`S.questionnaire_encrypt_sensitive_answers` is true (see `questionnaires_repository.py:553`, 612).
`list_session_answers` already handles decryption transparently via `_decrypt_sensitive_answer`
(line 566). The CSV exporter receives plaintext values and applies `_sanitize_csv_field` before
writing. No additional KMS handling is required in the CSV layer.

If `_decrypt_sensitive_answer` raises (e.g., KMS key unavailable), `list_session_answers` returns
`None` for the affected question. The CSV formatter treats `None` as an empty string.

### 5.6 CSV injection safety

All string values derived from user content (respondent IDs, answer values, question labels in the
header) are passed through `_sanitize_csv_field` (line 43) before being written. The header
question-label columns (e.g., "What is your age?") are also sanitised to prevent a malicious
question label from injecting a formula into the downloaded file when opened by a spreadsheet tool.

### 5.7 Empty questionnaire (no sessions)

If there are no sessions, only the header row and the UTF-8 BOM are emitted. The `StreamingResponse`
completes successfully with an empty body after the header. The download triggers in the browser as
a valid (header-only) CSV file.

### 5.8 Questionnaire with no published version and no questions

`_build_questionnaire_export_columns` falls back to `build_schema_snapshot` which returns
`{"sections": []}` for an empty questionnaire. In this case `question_meta = []` and `columns =
_QUESTIONNAIRE_STATIC_COLUMNS`. The export produces a seven-column CSV with only session metadata.
This is correct and not an error.

### 5.9 MAX_EXPORT_ROWS cap

After `MAX_EXPORT_ROWS = 50_000` rows are yielded the iterator stops. A truncation marker is **not**
added to the CSV (consistent with the behaviour of the `billing_ledger` iterator which also stops
silently). The `Content-Disposition` filename includes a timestamp so repeated exports of the same
questionnaire are distinguishable.

### 5.10 Rate limit interaction

Rate limiting at `_bucket_limit(user_sub, "rl#csv_export", 5, 60)` applies before ownership
validation and before `generate_csv_rows` is called (router line 66). A user who exports the same
large questionnaire 5 times in 60 seconds will receive a 429 on the 6th attempt regardless of
whether the flag is on or off. This prevents DDB read storms caused by repeated `list_session_answers`
calls across thousands of sessions.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 compliance

The entire implementation path runs identically in dev (DynamoDB Local at port 8001, mock KMS at
port 7999) and prod (real DynamoDB, real KMS). There is no `S.dev_mode` branch, no
`if S.dev_mode: return mock_data` block, and no separate code path. The existing
`_decrypt_sensitive_answer` path already uses `kms_decrypt` from `app/core/crypto.py`, which is
itself transparent to the KMS endpoint (mocked in dev, real in prod).

### 7.2 Idempotency

`GET /ui/export/csv` is fully idempotent: repeated calls with the same parameters produce the same
CSV content (assuming no sessions are added between calls). The `_iter_questionnaire_responses`
function is a pure read — it writes nothing to DynamoDB. Retrying a failed export is safe.

### 7.3 Ownership enforcement

Ownership is enforced at the router layer (lines 82–87 of `app/routers/csv_export.py`) before
`generate_csv_rows` is called. The service layer does not re-check ownership. This follows the
existing pattern for `billing_ledger` (which enforces `user_sub` implicitly through the PK) and
`contacts` (which enforces `owner_id == user_sub` through the query).

The router check uses `repo.get_questionnaire(questionnaire_id)` which returns the META row
directly by `{pk, sk}` key — a point read, not a scan. Ownership enforcement adds a single DDB
`get_item` read, negligible in cost.

### 7.4 Answer data privacy

Response data may contain personal information supplied by anonymous respondents (the
`respondent_id` field is nullable; anonymous sessions have `respondent_id=None`). The CSV is
served only to the questionnaire owner (HTTP 403 for all other callers). The response carries
`Cache-Control: no-cache, no-store` and `X-Content-Type-Options: nosniff` (already set by the
router at lines 113–114). The download is transmitted over TLS in prod (platform-wide; no change
required here).

### 7.5 KMS decrypt failure handling

`list_session_answers` calls `_decrypt_sensitive_answer` inside a broad `except Exception: return
None` guard (line 570). If KMS is temporarily unavailable, the affected answer field in the CSV
will be empty (`""`). The export will still complete for all non-encrypted fields. This is
preferable to aborting the entire export. An audit event is not currently emitted by
`_decrypt_sensitive_answer` on failure — this is a pre-existing gap not in scope for EVT-010.

## 8. Backward Compatibility & Migration

### 8.1 Flag-off behaviour is unchanged

With `CRM_SURVEY_EXPORT_ENABLED=0` (the default), `generate_csv_rows` takes the legacy stub path.
The stub path calls `_iter_questionnaire_responses_legacy` and `_format_questionnaire_row_legacy`,
which are renamed copies of the current functions. The emitted CSV is byte-for-byte identical to
the current production output.

### 8.2 No DynamoDB migration

No new tables, no new GSIs, no new attributes are written to DynamoDB by this ticket. Existing
session and answer rows are read-only from the export's perspective. There is nothing to backfill.

### 8.3 Column schema is not versioned

The CSV column set is determined at export time from the published schema. Consumers who parse the
CSV by column name (rather than column index) are unaffected when a new question is added to the
questionnaire and the questionnaire is republished — the new column appears only after republish.
Consumers who parse by column index will see their index mapping break if the question set changes.
This is documented behaviour consistent with SuiteCRM's export model.

### 8.4 Enabling the flag on an existing deployment

Turning `CRM_SURVEY_EXPORT_ENABLED=1` on an existing deployment requires no data migration.
Existing sessions and answers are already stored in the correct format for `list_session_answers`
to consume. The only visible change to callers is the CSV column schema (from 7 columns to 7 +
number-of-questions columns). Callers who download CSVs programmatically should be updated after
the flag is enabled.

## 10. Open Questions / Assumptions

1. **Per-version export parameter**: Should the router accept an optional `version_id` parameter
   to export responses for a specific historical version of the questionnaire? This would allow
   owners to compare cohorts across form revisions. Not in scope for EVT-010; assumed to be a
   follow-up.

2. **In-progress session inclusion**: The ticket's acceptance criteria specify "submitted sessions
   only by default" but do not describe a UI mechanism for requesting in-progress sessions. Assumed
   that a `status_filter` query parameter (default `submitted`) is deferred to a future iteration.

3. **Column header format**: The spec uses raw `question_id` strings (e.g., `q_age_2024`) as column
   headers. An alternative is to use `question_label` (the human-readable label). Using `question_id`
   is safer for programmatic consumers (labels may contain commas or non-ASCII) and is less likely
   to collide. The question label can always be retrieved from a separate schema export. This spec
   assumes `question_id` headers; can be changed to `label` if the product team prefers.

4. **MAX_EXPORT_ROWS truncation notification**: When the export is silently truncated at 50,000
   rows, the caller has no indication that data was omitted. A future enhancement could add a
   `X-Truncated: true` response header or a sentinel final row.

5. **Multiselect serialisation delimiter**: This spec uses `"; "` (semicolon-space) as the
   multiselect join delimiter, consistent with the existing `_format_contacts_row` tag serialisation
   at `csv_export.py:157`. If downstream consumers need a different delimiter, it should be made
   configurable in a follow-up.
