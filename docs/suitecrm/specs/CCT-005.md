# CCT-005 — Contact merge (consolidate two party records)

**Type:** Feature | **Priority:** P1 | **Estimate:** 3d  
**Source:** `docs/suitecrm/CRM_CONTACTS_EXTRA_TICKETS.md` — CCT-005 section  
**Flag:** `PARTY_CRM_ENABLED` (existing, from PTY-001)

---

## 1. Summary & Goal

SuiteCRM's "Merge Duplicates" workflow collapses two party records into a single canonical winner: roles, relationships, and contact mechanisms from both records are unified on the winner, and the losing record is tombstoned (never hard-deleted) so external references continue to resolve.

CCT-005 implements this for the testlogon OFBiz-style party graph by adding `merge_parties(winner_party_id, loser_party_id, *, actor_sub)` to `app/services/party.py` and a single admin-only endpoint `POST /ui/party/parties/merge`. The natural trigger is the duplicate-detection surface introduced in CCT-004: an operator reviews flagged candidates, chooses a winner, and calls this endpoint to collapse the pair.

The feature is entirely additive and default-off. Existing `app/routers/contacts.py`, billing, messaging, calendar, and all other subsystems are byte-for-byte unchanged when `S.party_crm_enabled` is `False`.

## 3. Data Model

### 3.1 No new DynamoDB table or GSI

All writes go to the existing `party` table (PTY-002). The SK namespace after PTY-004 through PTY-007 (`docs/ofbiz/specs/PTY-006.md:220-230`) is: `META`, `ROLE#*`, `REL#*`, `MIRROR#*`, `MECH#*`. CCT-005 writes only to existing SK patterns on the winner's partition, plus one new attribute on the loser's `META` row.

### 3.2 New attribute on loser META row

After merge, the loser's `META` row gains `merged_into_party_id: S = winner_party_id`. Written via:

```python
T.party.update_item(
    Key={"PK": f"PARTY#{loser_party_id}", "SK": "META"},
    UpdateExpression="SET merged_into_party_id = :w",
    ExpressionAttributeValues={":w": winner_party_id},
)
```

No condition expression — the preceding `update_party_status(loser, "MERGED")` already ensures the status is terminal, and the attribute write is safe to repeat.

### 3.3 `scripts/local-ddb-init.py` — no change

The `party` table `TableDef` added by PTY-002 already declares `attr_types={"created_at": "N"}` (`docs/ofbiz/specs/PTY-002.md:88-92`). No new GSI or `attr_types` entry is required.

### 3.4 New Pydantic models in `app/models.py`

**`CrmMergePartyIn`** (new):
```python
class CrmMergePartyIn(BaseModel):
    winner_party_id: str
    loser_party_id:  str

    @model_validator(mode="after")
    def _parties_differ(self) -> "CrmMergePartyIn":
        if self.winner_party_id == self.loser_party_id:
            raise ValueError("winner_party_id and loser_party_id must differ")
        return self
```
The self-merge guard mirrors the `_parties_differ` validator already specified for `CrmRelationshipIn` (`docs/ofbiz/specs/PTY-003.md:425-434`).

**`CrmPartyOut`** (additive extension):
```python
class CrmPartyOut(BaseModel):
    party_id:             str
    party_type:           CrmPartyType
    status:               CrmPartyStatus
    user_sub:             Optional[str] = None
    created_at:           int
    updated_at:           int
    merged_into_party_id: Optional[str] = None  # CCT-005: None on non-merged parties
```
Existing callers receive `None` for the new field — fully backward-compatible.

## 4. API / Service Design

### 4.1 Service function: `merge_parties`

```python
def merge_parties(
    winner_party_id: str,
    loser_party_id: str,
    *,
    actor_sub: str,
) -> Dict[str, Any]:
```

**Steps:**

1. **Validate** — `get_party` both IDs (raise `KeyError` if absent); assert same `party_type` (raise `HTTPException(400, "party_type_mismatch")`); assert `loser["status"] != "MERGED"` (raise `HTTPException(409, "loser_already_merged")`); assert `winner_party_id != loser_party_id` (raise `HTTPException(400, "self_merge")`).

2. **Copy roles** — `list_roles(loser_party_id)` → for each, call `add_role(winner_party_id, role_type)` (idempotent; skips if winner already holds the role).

3. **Copy relationships** — loop with cursor until exhausted:
   - `list_relationships(loser, direction="from")` → for each row where `to_party_id != winner_party_id`, call `create_relationship(winner_party_id, to_party_id, rel_type)`.
   - `list_relationships(loser, direction="to")` → for each row where `from_party_id != winner_party_id`, call `create_relationship(from_party_id, winner_party_id, rel_type)`.
   - Self-loop guard skips edges that would become `winner → winner`.

4. **Copy contact mechs** — `list_contact_mechs(loser_party_id)` → for each mech, call `find_party_by_contact(mech_type, value)` (GSI2); if none of the returned parties is the winner, call `add_contact_mech(winner_party_id, ..., correlation_id=f"MERGE#{loser_party_id}#{mech['mech_id']}")` (idempotent on retry via deterministic correlation_id).

5. **Tombstone loser** — `update_party_status(loser_party_id, "MERGED")` then `T.party.update_item(...)` to write `merged_into_party_id`.

6. **Audit** — `audit_event("party.merged", actor_sub, winner_party_id=winner_party_id, loser_party_id=loser_party_id)`.

7. **Return** — `get_party(winner_party_id)`.

### 4.2 Router endpoint

In `app/routers/party.py`, declared **before** `/{party_id}` routes:

```python
@router.post(
    "/parties/merge",
    response_model=CrmPartyOut,
    status_code=200,
)
def merge_parties_endpoint(
    inp: CrmMergePartyIn,
    actor: AuthenticatedUser = Depends(require_admin_or_root_csrf),
):
    if not S.party_crm_enabled:
        raise HTTPException(503, "party_crm feature not enabled")
    try:
        winner = merge_parties(inp.winner_party_id, inp.loser_party_id, actor_sub=actor.sub)
    except KeyError as exc:
        raise HTTPException(404, str(exc)) from exc
    return winner
```

## 5. Detailed Behavior & Edge Cases

**Idempotency on partial failure**: Every step is idempotent (roles via `ConditionalCheckFailedException`, relationships via structural PK/SK, mechs via `correlation_id`). A mid-execution crash leaves a partial state that is structurally safe; retrying the endpoint fully reconciles. The `update_party_status(loser, "MERGED")` is a no-op when the status is already `MERGED`, and the `merged_into_party_id` write is unconditional.

**Loser already merged (409)**: Prevents merging a tombstone that was already consolidated elsewhere. The caller must resolve to the canonical non-merged party first.

**Party type mismatch (400)**: Merging a `PERSON` into a `PARTY_GROUP` corrupts the relationship graph (e.g., `EMPLOYMENT` connects PERSON → PARTY_GROUP). Rejected before any write.

**Self-merge (422 from model / 400 from service)**: Caught at Pydantic validation time; service-level guard for direct calls.

**Mirror rows on the loser**: After re-pointing inbound edges, the loser's `MIRROR#*` rows remain in place. `list_relationships(loser, direction="to")` still returns them. Callers needing canonical data should filter `status != MERGED`. This is intentional — the tombstone is complete for auditability.

**Chain of merges**: If A → B → C, A's `merged_into_party_id = B`. Callers must walk the chain. A resolution helper is out of scope.

**Large relationship fan-out**: Cursor-looping at `limit=100` per page handles parties with many edges. For extreme datasets a background worker variant can be added later; the synchronous path is acceptable for an infrequent admin operation.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007**: All writes use the same `T.party` handle in dev (DynamoDB Local :8001) and prod (real DynamoDB). `create_relationship`'s `_ddb_lowlevel_client()` inherits its endpoint from the shared `ddb` resource metadata (`app/services/agent_orchestrator.py:38-51`). No `if S.dev_mode` branch anywhere.

**Idempotency**: Covered fully in §5. The audit event is emitted after the tombstone write; a crash before that point means a retry re-emits it — a duplicate audit entry is preferable to a missing one.

**Security**: `require_admin_or_root_csrf` enforces `role >= ADMIN` before any code runs. CSRF is enforced for cookie-auth callers. Audit payload stores only opaque `party_id` values — no email addresses or phone numbers. The loser row is never hard-deleted, preserving compliance history.

## 8. Backward Compatibility & Migration

`CrmPartyOut.merged_into_party_id` is an optional field with `None` default. All non-merged parties return `None` for it — existing callers are unaffected. No new DDB table, GSI, or `attr_types` entry is required. No backfill: CCT-005 introduces an operational capability; existing parties remain `ACTIVE`/`INACTIVE` until an operator explicitly merges them.

## 10. Open Questions / Assumptions

1. **`merged_into_party_id` chain resolution**: If A→B→C, callers must walk the chain manually. A `resolve_canonical_party` helper that follows the chain is out of scope but is a natural CCT-007 candidate.
2. **Loser row cleanup**: Mirror and mech rows on the loser are preserved indefinitely. A retention-period cleanup job is out of scope; add if storage becomes a concern.
3. **`update_party_status` does not accept extra kwargs**: CCT-005 uses a separate `update_item` call for `merged_into_party_id`. If PTY-004 is later extended to accept kwargs on the `MERGED` transition, the two-write pattern can be collapsed.
4. **No money movement**: Billing records referencing `loser_party_id` are not auto-migrated. Billing reconciliation is a future concern.
5. **Assumption — `CrmPartyOut` is a Pydantic `BaseModel` in `app/models.py`**: Verified via PTY-003 spec (`docs/ofbiz/specs/PTY-003.md:489-496`). The additive field appears in the serialized response once the DDB item contains the attribute.
