# STU-005 — Field-level ACL — hide/read-only fields per role

**Type:** Feature  **Priority:** P2  **Estimate:** 2 days  
**Ticket source:** `docs/suitecrm/CRM_SECURITY_STUDIO_TICKETS.md`, section "STU-005"

---

## 1. Summary & Goal

STU-005 introduces a **field-level ACL** layer that allows platform administrators to designate specific fields on CRM entity responses as either `hidden` (completely omitted from API output for restricted callers) or `readonly` (value preserved, but annotated in the response so the UI can prevent editing). Configuration is per-role-per-entity-type-per-field, stored in a dedicated DynamoDB row type on the existing `crm_studio_fields` table (provisioned by STU-001), and applied at response time by a post-processor function that callers invoke explicitly.

The goal mirrors the SuiteCRM Studio field-level ACL feature: an operator can, for example, hide a contact's `internal_notes` field from a `SALES_REP` ACL role while keeping it visible to `ACCOUNT_MANAGER`, or mark a ticket's `internal_cost_estimate` as read-only for all non-ROOT callers.

The feature is entirely default-OFF. With `CRM_ACL_ENABLED=0` the post-processor is a no-op, the configuration endpoints return 404, and the platform behaves byte-for-byte identically to the pre-STU-005 state.

## 3. Data Model

### 3.1 Reusing `crm_studio_fields` — field ACL rows

No new DynamoDB table is introduced. STU-005 stores field ACL configuration as a distinct row type on the `crm_studio_fields` table (PK=`entity_type` S, SK=`field_key` S) provisioned by STU-001.

**ACL config row format:**

| Attribute | DDB type | Value / description |
|-----------|----------|---------------------|
| `entity_type` | S (PK) | Always `"__acl__"` — namespaces ACL rows away from STU-011 field-definition rows |
| `field_key` | S (SK) | `"{role_id}#{entity_type}#{field_name}"` — the composite triple that uniquely identifies one rule |
| `role_id` | S | The ACL role identifier (e.g. `"ROLE#abc123"` or just `"abc123"` from STU-002 creation) |
| `entity_type_name` | S | The CRM entity type this rule applies to, e.g. `"ticket"`, `"contact"`, `"opportunity"` |
| `field_name` | S | The response dict key to restrict, e.g. `"assigned_admin_sub"`, `"internal_notes"` |
| `access` | S | `"hidden"` or `"readonly"` |
| `set_by_sub` | S | `user_sub` of the actor who last wrote this rule |
| `set_at` | N | Unix timestamp (integer) from `now_ts()` (`app/core/time.py:2`) |

**Key composition rationale:** Encoding all three dimensions (`role_id`, `entity_type`, `field_name`) in the SK of a fixed PK `__acl__` allows a single `query` call with `pk = "__acl__"` and an optional `begins_with` filter on SK to enumerate all ACL rules for a given role or entity. The separator `#` cannot appear in valid role IDs, entity type names, or field names (all validated at write time with `^[a-z][a-z0-9_]*$`), preventing SK injection.

### 3.2 `scripts/local-ddb-init.py` changes

The `crm_studio_fields` table `TableDef` is already present from STU-001 with no GSI:

```python
TableDef(
    _resolve_table_name(S.crm_studio_fields_table_name, "crm_studio_fields"),
    "entity_type",
    "field_key",
)
```

STU-005 adds **no new table** and **no GSI** to `scripts/local-ddb-init.py`. The `entity_type = "__acl__"` partition accommodates all field ACL rows, and queries filter by SK prefix `begins_with("field_key", f"{role_id}#")` which is a key-condition (no FilterExpression needed for the common access pattern). The `attr_types` constraint (numeric GSI sort keys must declare `"N"` per CLAUDE.md) is not triggered here since `set_at` is stored as a non-key attribute, not a GSI sort key.

### 3.3 `app/core/tables.py` changes

`T.crm_studio_fields` is already wired by STU-001. No change required.

### 3.4 Row lifecycle

- **Created/updated**: `POST /ui/admin/crm/field-acl/{role_id}/{entity_type}/{field_name}` — upserts the row via `put_item`.
- **Deleted**: `DELETE /ui/admin/crm/field-acl/{role_id}/{entity_type}/{field_name}` — deletes the item via `delete_item(Key={"entity_type": "__acl__", "field_key": f"{role_id}#{entity_type}#{field_name}"})`.
- **Read**: `apply_field_acl` queries by PK `"__acl__"` with SK begins_with filter per role_id per entity_type. The result is cached for 60 seconds in-process.

#### 4.1.1 Module-level cache

```python
_acl_cache: dict[str, tuple[list[dict], int]] = {}
# key: "{role_id}#{entity_type}", value: (rows, fetched_at_ts)
_ACL_CACHE_TTL = 60  # seconds, same as billing_config pattern
```

`_invalidate_cache()` clears `_acl_cache` entirely (same approach as `billing_config.invalidate_cache()` at `app/services/billing_config.py:54`).

#### 4.1.2 `set_field_acl`

```python
def set_field_acl(
    actor_sub: str,
    role_id: str,
    entity_type: str,
    field_name: str,
    access: Literal["hidden", "readonly"],
) -> None:
    """
    Upsert a field ACL rule.

    Validates role_id, entity_type, field_name with ^[a-z][a-z0-9_]*$ (prevents
    SK injection via '#' characters). Writes entity_type="__acl__",
    field_key="{role_id}#{entity_type}#{field_name}" to T.crm_studio_fields.
    Emits audit_event("crm_field_acl.set", actor_sub, ...).
    Invalidates _acl_cache.
    Raises HTTPException(400) on invalid format.
    """
```

Implementation:
1. Validate each of `role_id`, `entity_type`, `field_name` matches `^[a-z0-9][a-z0-9_]{0,98}$` (allows typical identifiers; raises `HTTPException(400, "invalid_format")` on mismatch).
2. Validate `access in ("hidden", "readonly")`.
3. Build `field_key = f"{role_id}#{entity_type}#{field_name}"`.
4. Call `T.crm_studio_fields.put_item(Item={"entity_type": "__acl__", "field_key": field_key, "role_id": role_id, "entity_type_name": entity_type, "field_name": field_name, "access": access, "set_by_sub": actor_sub, "set_at": now_ts()})`.
5. Call `_invalidate_cache()`.
6. Call `audit_event("crm_field_acl.set", actor_sub, role_id=role_id, entity_type=entity_type, field_name=field_name, access=access)`.

#### 4.1.3 `delete_field_acl`

```python
def delete_field_acl(
    actor_sub: str,
    role_id: str,
    entity_type: str,
    field_name: str,
) -> None:
    """
    Delete a field ACL rule. No-op if the rule does not exist.
    Emits audit_event("crm_field_acl.deleted", actor_sub, ...).
    Invalidates _acl_cache.
    """
```

Implementation:
1. `T.crm_studio_fields.delete_item(Key={"entity_type": "__acl__", "field_key": f"{role_id}#{entity_type}#{field_name}"})` — DynamoDB `delete_item` is a no-op on a missing key.
2. Call `_invalidate_cache()`.
3. Call `audit_event("crm_field_acl.deleted", actor_sub, ...)`.

#### 4.1.4 `get_field_acls_for_role`

```python
def get_field_acls_for_role(
    role_id: str,
    entity_type: str,
) -> list[dict]:
    """
    Return all field ACL rules for (role_id, entity_type).

    Queries T.crm_studio_fields with pk="__acl__" and
    begins_with(sk, f"{role_id}#{entity_type}#").
    Loops via LastEvaluatedKey until exhausted (CLAUDE.md pagination requirement).
    Returns list of dicts with keys: role_id, entity_type, field_name, access,
    set_by_sub, set_at.

    Result is cached for _ACL_CACHE_TTL seconds keyed on
    "{role_id}#{entity_type}".
    """
```

Implementation:
1. Cache key: `f"{role_id}#{entity_type}"`.
2. If cached and `now_ts() - fetched_at < _ACL_CACHE_TTL`: return cached rows.
3. Query `T.crm_studio_fields` with `KeyConditionExpression=Key("entity_type").eq("__acl__") & Key("field_key").begins_with(f"{role_id}#{entity_type}#")`.
4. Loop via `LastEvaluatedKey` until exhausted (CLAUDE.md: "DDB FilterExpression doesn't reduce page size — any query that filters a sparse attribute must loop via LastEvaluatedKey").
5. Store result in `_acl_cache[cache_key] = (rows, now_ts())`.
6. Return rows.

#### 4.1.5 `apply_field_acl`

This is the core post-processor function. It is called by service or router code after building a response dict, before serializing to JSON.

```python
def apply_field_acl(
    response_dict: dict,
    entity_type: str,
    user_sub: str,
    admin_profile: AdminProfile,
) -> dict:
    """
    Apply field-level ACL rules to a response dict.

    When S.crm_acl_enabled is False, returns response_dict unmodified (no-op).
    When ROOT or ADMIN role is detected via admin_profile, returns unmodified
    (admins bypass field ACL; see section 5.3).

    For each ACL role the user holds (via get_effective_roles_for_user):
      - Collects all field rules for that (role_id, entity_type) pair.
      - Merges rules across roles: if ANY role grants "hidden", the field is hidden.
        If ANY role grants "readonly" (and none grant "hidden"), the field is readonly.

    Hidden fields: key is deleted from response_dict; field_name is appended to
    _hidden_fields list (debug annotation, stripped in production logging).
    Readonly fields: value is preserved; field_name is appended to _readonly_fields list.

    Returns the modified dict (mutates a shallow copy, not the original).
    Errors in role-loading or cache-read are swallowed (best-effort, never blocks response).
    """
```

Implementation details:
1. If `not S.crm_acl_enabled`: return `response_dict` unchanged.
2. Shallow-copy the dict: `result = dict(response_dict)`.
3. Determine admin bypass: if caller holds `Role.ADMIN` or `Role.ROOT` (obtained from `admin_profile.type == AdminProfileType.GENERAL` when role resolution is available — see section 5.3 for the bypass mechanism), return `result` unchanged.
4. `try/except Exception`: wrap all role-loading and rule-collection in a broad except that logs a warning and returns `result` unchanged on any error (best-effort, never blocks the caller).
5. Call `get_effective_roles_for_user(user_sub, admin_profile)` to get the list of role dicts. Extract `role_id` from each.
6. For each `role_id`, call `get_field_acls_for_role(role_id, entity_type)` and accumulate rules into `hidden_fields: set[str]` and `readonly_fields: set[str]`. Rule precedence: `hidden` wins over `readonly` if a field appears in both sets for different roles (i.e., `hidden_fields` overrides `readonly_fields`).
7. For each `field_name` in `hidden_fields`: `result.pop(field_name, None)`.
8. Append `_hidden_fields: sorted(hidden_fields)` to `result` if non-empty (debug annotation; callers may strip this key before returning to the client in prod logging middleware).
9. Append `_readonly_fields: sorted(readonly_fields - hidden_fields)` to `result` if non-empty.
10. Return `result`.

**Signature:**

```python
def apply_field_acl(
    response_dict: dict,
    entity_type: str,
    user_sub: str,
    admin_profile: "AdminProfile",
) -> dict: ...
```

The `AdminProfile` import is a local import inside the function (or module-level with `TYPE_CHECKING`) to avoid circular dependency since `app/auth/roles.py` does not import any service.

## 5. Detailed Behavior & Edge Cases

### 5.1 Hidden vs. readonly semantics

- **`hidden`**: The field key is removed from the response dict before serialization. The caller's response shape will omit the field entirely — the client sees neither the key nor the value. The field_name is appended to `_hidden_fields: list[str]` in the response dict as a debug annotation (callers may strip this in logging middleware; it is never exposed to the browser client in a well-formed API response because the router should strip `_`-prefixed debug keys).
- **`readonly`**: The field key and value remain in the response dict. The field_name is appended to `_readonly_fields: list[str]`. The UI uses this annotation to disable edit controls for these fields without losing display capability. The backend never enforces read-only at the write path in this ticket (write enforcement is a future concern; the current ticket only restricts GET responses).

### 5.2 Multi-role precedence — `hidden` wins

When a user holds two ACL roles:
- Role A marks `assigned_admin_sub` as `readonly` for entity_type `ticket`.
- Role B marks `assigned_admin_sub` as `hidden` for entity_type `ticket`.

Effective: `assigned_admin_sub` is **hidden** (removed from the response). `hidden` is the more restrictive access level and always wins in a union. This mirrors SuiteCRM's field-level ACL precedence where the most restrictive combined rule applies.

Conversely:
- Role A marks `assigned_admin_sub` as `hidden`.
- Role B has no rule for `assigned_admin_sub`.

Effective: `assigned_admin_sub` is **hidden** (union of restrictions; a permissive role does not override a restrictive one).

### 5.3 Admin and ROOT bypass

ROOT and ADMIN callers bypass all field-level ACL restrictions. The bypass is applied in `apply_field_acl` by inspecting `admin_profile`:

```python
if admin_profile.type == AdminProfileType.GENERAL:
    return result  # ADMIN/ROOT always sees all fields
```

This is consistent with `crm_security_groups.user_can_access_record` (STU-004) which also grants ROOT/ADMIN unconditional access. A SCOPED admin (i.e. `AdminProfileType.SCOPED`) is subject to field ACL rules like a regular user, since scoped admins have limited platform permissions.

Note: the `admin_profile` alone does not convey the platform `Role` enum. The caller must pass the `AuthenticatedUser.admin_profile`; if the route dependency is `require_root_session` or `require_admin_session`, the handler already knows the role and can skip `apply_field_acl` entirely at the call site.

### 5.4 Nested fields and list fields

`apply_field_acl` operates on the **top-level keys** of the response dict only. It does not recursively traverse nested objects (e.g., `messages: list[TicketMessage]`). Hiding or restricting nested fields requires the caller to invoke `apply_field_acl` on each nested dict separately, passing the appropriate `entity_type` for the nested entity. This is a deliberate design constraint for MVP; recursive traversal is a follow-on.

### 5.5 Flag-off guarantees

When `S.crm_acl_enabled` is `False`:
- `apply_field_acl` returns the input dict unchanged on the first line.
- All three router endpoints return 404 (router not registered in `main.py`).
- `get_field_acls_for_role` is never called.
- `T.crm_studio_fields` may have no `__acl__` rows; no effect.
- The `crm_field_acl` module is never imported at module level (conditional import in `main.py`).

### 5.6 `_hidden_fields` and `_readonly_fields` debug keys

The `_hidden_fields` and `_readonly_fields` keys are prefixed with `_` to signal their debug-annotation status. Route handlers that serialize via Pydantic `model_validate` will discard unknown keys automatically if the Pydantic model uses `model_config = ConfigDict(extra="ignore")` (which is the default behavior for Pydantic v2 models unless `extra="allow"` is set). This means: if the route handler wraps the dict in a strongly-typed Pydantic model (like `TicketOut`), these debug keys are silently stripped in the final JSON response. If the handler returns `response_dict` directly (e.g., via `JSONResponse`), the caller sees the debug keys — this is acceptable for admin-tier endpoints and useful for debugging.

### 5.7 Write-path enforcement (out of scope)

STU-005 restricts **read** responses only. It does NOT enforce field-level ACL on write paths (PUT/PATCH). A caller whose role marks `assigned_admin_sub` as `readonly` can still submit a PATCH that changes `assigned_admin_sub` in the request body. Write-path enforcement is a follow-on ticket. This matches SuiteCRM behavior where field-level ACL primarily controls display; write enforcement is a separate Studio permission layer.

### 5.8 Idempotency of `set_field_acl`

`put_item` overwrites an existing row silently. Calling `set_field_acl` twice with the same arguments is safe; only `set_at` and `set_by_sub` change. The cache is invalidated on every call, so the next `apply_field_acl` call reads fresh data within `_ACL_CACHE_TTL` seconds.

### 5.9 Empty rule set

If a user's effective roles have no field ACL rules for a given entity_type, `apply_field_acl` returns the dict unmodified (no `_hidden_fields` or `_readonly_fields` keys added). This is the common case for most users and ensures zero performance overhead beyond the initial cache read.

### 5.10 Unknown field names

`set_field_acl` does not validate that `field_name` corresponds to an actual field on the entity's response model. An ACL rule for a non-existent field (e.g., `field_name="nonexistent_key"`) is stored silently and applied harmlessly — `result.pop("nonexistent_key", None)` is a no-op. This avoids tight coupling between the field ACL store and the Pydantic models; field names can be configured in advance of schema changes.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 — identical code path in dev and prod

All DDB access goes through `T.crm_studio_fields`, a `_FloatSafeTable` wrapping a boto3 Table (`app/core/tables.py:29-66`). In dev, this table is backed by DynamoDB Local on port 8001. In prod, it targets real DynamoDB. No `if S.dev_mode` branch exists in `crm_field_acl.py`. The audit event (`alerts.audit_event`) writes to `T.alerts` in both environments.

`apply_field_acl` calls `get_effective_roles_for_user` from `crm_acl.py` (STU-002/STU-003), which also uses `T.crm_acl_roles` uniformly. There is no mock path.

### 7.2 Audit trail

Every write-path operation (`set_field_acl`, `delete_field_acl`) calls `alerts.audit_event` (`app/services/alerts.py:644`). Event names follow the existing dot-separated convention: `crm_field_acl.set` and `crm_field_acl.deleted`. Audit events fire identically in dev and prod.

### 7.3 SK injection prevention

`role_id`, `entity_type`, and `field_name` are each validated against `^[a-z0-9][a-z0-9_]{0,98}$` at the service layer. The `#` character used as the SK separator cannot appear in any of these values, preventing injection that would corrupt the `__acl__` partition or pollute other SK-prefix namespaces.

### 7.4 Authorization layering

- **`set_field_acl` and `delete_field_acl`**: ROOT only (`require_root_session` — `app/auth/deps.py:308`). Only the platform root can configure field visibility, preventing privilege escalation by ADMIN-tier accounts.
- **`get_field_acls_for_role`** (list endpoint): ADMIN/ROOT — read access is broader.
- **`apply_field_acl`**: internal service call only; no direct public endpoint exposes the raw ACL evaluation result. The post-processor is called from within route handlers that already have a resolved `AuthenticatedUser`.

### 7.5 No money-out path

STU-005 does not touch billing, payments, ledger records, or refunds. The no-fork constraint on `refund_payment` / `settle_or_reverse_ledger` does not apply.

### 7.6 Best-effort application

`apply_field_acl` wraps all role-loading and rule-collection in a `try/except Exception` block that logs a warning and returns the unmodified dict on error. A DynamoDB outage or role-loading failure causes the response to leak restricted fields rather than fail the request. This is a deliberate trade-off: correctness of a configuration feature should not degrade availability of the primary data API. In environments where strict enforcement is required, callers should check the returned `_hidden_fields` list and return 500 if it is absent when rules are expected.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact with flag off

With `CRM_ACL_ENABLED=0` (the default for all existing deployments):
- `apply_field_acl` returns `response_dict` unmodified on line 1 (no DDB reads, no role lookups).
- The `crm_field_acl` router is not registered; its endpoints return 404.
- No existing API behavior is altered.
- The `crm_studio_fields` table may exist with no `__acl__` rows — this is valid.

### 8.2 No DynamoDB schema change

STU-005 adds a new row type (`entity_type = "__acl__"`) to an existing table. DynamoDB is schemaless for non-key attributes; no `UpdateTable` or migration is needed. The new row type coexists with STU-011 field-definition rows (which use `entity_type = "contact"`, `"ticket"`, etc. — never `"__acl__"`).

### 8.3 No changes to existing response models

`TicketOut` (`app/routers/tickets.py:58-72`) and all other existing Pydantic models are unchanged. The `apply_field_acl` call operates on the underlying dict before `model_validate` is called; the Pydantic model strips `_hidden_fields` / `_readonly_fields` debug keys via its default `extra="ignore"` behavior.

### 8.4 Incremental enablement path

When `CRM_ACL_ENABLED=1` is first set in production:
1. No existing rows exist in the `__acl__` partition.
2. All `apply_field_acl` calls return dicts unchanged (empty rule set, section 5.9).
3. Operators configure rules incrementally via the admin API.
4. Rules take effect within the `_ACL_CACHE_TTL` (60 seconds) after being written.

No data migration, backfill, or downtime is required.

## 10. Open Questions / Assumptions

1. **SCOPED admin bypass threshold**: The current design only bypasses field ACL for `AdminProfileType.GENERAL`. A SCOPED admin with `AUTH_SUPPORT` scope but no relevant ACL role assigned is subject to field restrictions. Should all SCOPED admins also bypass? The assumption here is GENERAL = full bypass, SCOPED = subject to rules, consistent with the principle of least privilege. This should be confirmed before STU-005 merges.

2. **Write-path enforcement**: STU-005 does not block write requests for `readonly` fields. A future ticket should add write-path enforcement (reject PATCH/PUT body keys that are `readonly` for the caller's roles). The `readonly` annotation is only advisory in this ticket.

3. **Pydantic model `extra="ignore"` assumption**: The spec assumes that existing Pydantic response models use `extra="ignore"` (Pydantic v2 default), which causes `_hidden_fields` and `_readonly_fields` to be stripped when `model_validate` is called. If any router uses `model_config = ConfigDict(extra="allow")`, these debug keys will leak to the browser client. Audit response model configs before deploying with `CRM_ACL_ENABLED=1`.

4. **`entity_type` namespace collision with STU-011**: STU-011 writes rows to `crm_studio_fields` with `entity_type = "contact"`, `"ticket"`, etc. STU-005 uses `entity_type = "__acl__"`. The double-underscore prefix must be reserved — STU-011 must reject `field_key` requests where `entity_type == "__acl__"`. Add a validation check in STU-011's `create_field` that raises `HTTPException(400)` if `entity_type` starts with `__`.

5. **Performance under many roles**: If a user holds 20+ ACL roles, `apply_field_acl` calls `get_field_acls_for_role` once per role per entity_type. With the 60-second in-process cache this is one DDB query per (role, entity_type) pair per 60-second window. For 20 roles on a frequently-accessed endpoint, this is 20 DDB queries cold. A future optimization could batch all role-ACL rows into a single query against the `__acl__` partition (filtering in application code), reducing cold cost to O(1) DDB queries.

6. **Relationship to STU-013 layout editor**: STU-013 stores per-view field visibility at layout level (which fields appear in the detail/edit view). STU-005 stores per-role field access at ACL level (which fields are hidden from specific roles). These are orthogonal mechanisms: STU-013 is layout-based (all users see the same layout), STU-005 is role-based (different users see different fields). Both can be active simultaneously. Callers should apply STU-005's `apply_field_acl` after building the response dict and before rendering the STU-013 layout.
