# STU-014 — Studio — relationship builder (custom inter-module relationships)

**Type:** Feature | **Priority:** P2 | **Estimate:** 2d  
**Flag:** `CRM_STUDIO_ENABLED` (default `"0"` → `False`)  
**Depends on:** STU-001 (DDB scaffolding + flags), STU-002 (`require_crm_permission`)

---

## 1. Summary & Goal

STU-014 gives administrators the ability to define custom semantic relationships between any two CRM entity types (e.g., "a Contact has many Opportunities", "a Ticket links 1:1 to a Contract") without code changes, and to link and unlink individual record pairs through those relationships at runtime. This is the Studio "Relationship Builder" capability that SuiteCRM provides out of the box.

The deliverable is four integrated layers:

1. **Relationship definition store** — CRUD for `{from_entity, to_entity, rel_name, cardinality}` rows persisted on the existing `crm_studio_modules` table (introduced by STU-001).
2. **Relationship instance store** — link/unlink records persisted on the existing `app_single_table` (the platform's established multi-purpose single table, already holding social follows, newsfeed posts, search history, meeting polls, etc.) under a `REL#` partition namespace. No new DynamoDB table is created.
3. **Service layer** — `app/services/crm_relationships.py` with full CRUD for definitions and instances, cardinality enforcement, and cursor-paginated retrieval.
4. **Router** — `app/routers/crm_relationships.py` with six endpoints under `/ui/admin/studio/relationships`, registered in `app/main.py` behind `if S.crm_studio_enabled`.

A frontend React page (`frontend/src/pages/admin/studio/RelationshipBuilder.tsx`) lets admins manage relationship definitions. Generic relate/unrelate/list endpoints are consumed by other CRM record pages (Contacts, Tickets, Opportunities) as those modules ship.

All code is strictly additive. With `CRM_STUDIO_ENABLED=0` (the default), no routes are registered, no tables are written, and the platform is byte-for-byte identical to its pre-STU-014 state.

## 3. Data Model

### 3.1 Relationship definitions — `crm_studio_modules` table

STU-001 defines this table with `pk` (S) and `sk` (S) as the primary key, no GSIs, in `scripts/local-ddb-init.py`. No modifications are needed.

**Definition row shape:**

| Attribute | Type | Description |
|---|---|---|
| `pk` | S | `MODULE#{from_entity}#{to_entity}` (e.g. `MODULE#contact#opportunity`) |
| `sk` | S | `REL#{rel_name}` (e.g. `REL#opportunities`) |
| `rel_name` | S | Unique slug within the `from_entity`/`to_entity` pair; matches `^[a-z][a-z0-9_]{1,49}$` |
| `from_entity` | S | Source entity type (e.g. `contact`, `ticket`, `opportunity`) |
| `to_entity` | S | Target entity type |
| `cardinality` | S | `one_to_one` \| `one_to_many` \| `many_to_many` |
| `label` | S | Human-readable label from the `from_entity` perspective (e.g. `"Opportunities"`) |
| `reverse_label` | S | Label from the `to_entity` perspective (e.g. `"Contact"`) |
| `created_by_sub` | S | `user_sub` of the admin who created the definition |
| `created_at` | N | Unix timestamp (int) from `now_ts()` |
| `is_active` | BOOL | `True` by default; `False` = soft-deleted |

**Querying all definitions for a given `from_entity`:**

`Query(KeyConditionExpression=Key("pk").begins_with("MODULE#{from_entity}#"), FilterExpression=Attr("sk").begins_with("REL#"))`. DynamoDB `begins_with` on the PK is not directly expressible; instead use `begins_with` on the SK in combination with an exact PK match per `to_entity`, or scan `crm_studio_modules` with a `FilterExpression`. Because the expected number of relationship definitions is small (tens, not millions), a filtered scan of the table is acceptable. Alternatively, `list_relationship_defs(from_entity=None)` does a full scan with `FilterExpression=Attr("sk").begins_with("REL#")` and optionally filters by `from_entity` in Python.

### 3.2 Relationship instances — `app_single_table`

Instance rows live in `app_single_table` (name resolved from `os.environ.get("APP_TABLE", "app_single_table")`). The table already exists with `pk` / `sk` primary key; no changes to `scripts/local-ddb-init.py` are required.

**Instance row shape:**

| Attribute | Type | Description |
|---|---|---|
| `pk` | S | `REL#{from_entity}#{from_id}#{rel_name}` (e.g. `REL#contact#c_abc123#opportunities`) |
| `sk` | S | `TO#{to_entity}#{to_id}` (e.g. `TO#opportunity#o_xyz789`) |
| `from_entity` | S | Denormalized from the PK |
| `from_id` | S | Denormalized from the PK |
| `rel_name` | S | Denormalized for projection |
| `to_entity` | S | Denormalized from the SK |
| `to_id` | S | Denormalized from the SK |
| `created_by_sub` | S | `user_sub` of the actor who created the link |
| `created_at` | N | Unix timestamp (int) from `now_ts()` |

**No new GSI is needed.** All read patterns are:
- Exact PK `REL#{from_entity}#{from_id}#{rel_name}` — fetch all related records from one side (the common case).
- Exact item lookup `pk + sk` — for existence checks before relate/unrelate.

Because `created_at` on instance rows is stored as an item attribute (not a GSI sort key), no `attr_types` declaration is needed. The existing `app_single_table` declaration in `scripts/local-ddb-init.py:397-413` requires no modification.

### 3.3 No new tables or GSI additions required

This ticket introduces zero new DynamoDB tables and zero GSI additions. Both storage surfaces (`crm_studio_modules` and `app_single_table`) are already fully declared by STU-001 and the existing platform scaffold respectively.

### 4.1 Service layer — `app/services/crm_relationships.py`

**Definition management:**

```python
def define_relationship(
    actor_sub: str,
    from_entity: str,
    to_entity: str,
    rel_name: str,
    cardinality: Literal["one_to_one", "one_to_many", "many_to_many"],
    label: str,
    reverse_label: str,
) -> dict:
```
Validates `rel_name` against `^[a-z][a-z0-9_]{1,49}$`. Checks that no active definition already exists for the same `(from_entity, to_entity, rel_name)` triple (raises `ValueError("duplicate_rel_name")` if it does). Writes the definition row to `T.crm_studio_modules` with `is_active=True`, `created_at=now_ts()`. Emits `audit_event("crm_relationship_def.created", actor_sub, from_entity=from_entity, to_entity=to_entity, rel_name=rel_name)`.

```python
def update_relationship_def(
    actor_sub: str,
    from_entity: str,
    to_entity: str,
    rel_name: str,
    *,
    label: str | None = None,
    reverse_label: str | None = None,
) -> dict:
```
Allows updating human-readable labels only (cardinality changes are forbidden once instances exist to avoid orphaned links). Raises `404` if definition not found or `is_active=False`. Emits audit event `crm_relationship_def.updated`.

```python
def delete_relationship_def(
    actor_sub: str,
    from_entity: str,
    to_entity: str,
    rel_name: str,
) -> None:
```
Before soft-deleting, performs an instance count check: queries `_single_tbl` with `pk = "REL#{from_entity}#*##{rel_name}"` using a `FilterExpression=Attr("rel_name").eq(rel_name)` scan bounded by a `Limit=1` to detect any existing instance. If any instance exists, raises `ValueError("instances_exist")` (mapped to HTTP 409). On success, sets `is_active=False` on the definition row (soft delete, not physical removal). Emits `audit_event("crm_relationship_def.deleted", actor_sub, ...)`.

```python
def get_relationship_def(
    from_entity: str,
    to_entity: str,
    rel_name: str,
) -> dict | None:
```
Gets the item from `T.crm_studio_modules`. Returns `None` if absent or `is_active=False`.

```python
def list_relationship_defs(from_entity: str | None = None) -> list[dict]:
```
Scans `T.crm_studio_modules` with `FilterExpression=Attr("sk").begins_with("REL#") & Attr("is_active").eq(True)`. If `from_entity` is given, additionally filters `Attr("from_entity").eq(from_entity)`. Returns all matching items. No cursor pagination (definition count is expected to remain in the dozens).

**Instance management:**

```python
def relate(
    actor_sub: str,
    from_entity: str,
    from_id: str,
    to_entity: str,
    to_id: str,
    rel_name: str,
) -> None:
```
1. Loads the definition via `get_relationship_def(from_entity, to_entity, rel_name)`. Raises `404` if not found.
2. For `cardinality = "one_to_one"`: queries `_single_tbl` with exact PK `REL#{from_entity}#{from_id}#{rel_name}` and `Limit=1`. If any item is found, raises `ValueError("already_related")` (HTTP 409).
3. For `cardinality = "one_to_many"`: no uniqueness check on the from-side (one record can link to many). Does check that the specific `(from_id, to_id)` pair does not already exist (exact get_item lookup) to prevent duplicate links.
4. For `cardinality = "many_to_many"`: same duplicate-pair check only.
5. Writes instance row to `_single_tbl` with `created_at=now_ts()`, `created_by_sub=actor_sub`.
6. Emits `audit_event("crm_relationship.created", actor_sub, from_entity=from_entity, from_id=from_id, to_entity=to_entity, to_id=to_id, rel_name=rel_name)`.

```python
def unrelate(
    actor_sub: str,
    from_entity: str,
    from_id: str,
    to_entity: str,
    to_id: str,
    rel_name: str,
) -> None:
```
Deletes the instance row (exact pk+sk). Raises `404` if the row does not exist. Emits `audit_event("crm_relationship.deleted", ...)`.

```python
def get_related(
    from_entity: str,
    from_id: str,
    rel_name: str,
    limit: int = 50,
    cursor: str | None = None,
) -> tuple[list[dict], str | None]:
```
Queries `_single_tbl` with `KeyConditionExpression=Key("pk").eq(f"REL#{from_entity}#{from_id}#{rel_name}")`. Applies `ScanIndexForward=True`, `Limit=limit`, and `ExclusiveStartKey=decode_cursor(cursor)` if cursor is provided. Returns `(items, encode_cursor(resp.get("LastEvaluatedKey")))`. Each item in the returned list is projected to `{to_entity, to_id, created_by_sub, created_at}`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Duplicate definition prevention

`define_relationship` calls `get_relationship_def(from_entity, to_entity, rel_name)` before writing. If it returns a non-None result (even with `is_active=False`, meaning a previously soft-deleted definition), it raises `ValueError("duplicate_rel_name")` mapped to HTTP 409 with body `{"code": "duplicate_rel_name"}`. This prevents confusion between a re-created definition and any surviving instance rows. If an admin wants to reuse the same `rel_name` after deleting a definition, they must first purge all instances manually (via unrelate) and then re-create.

### 5.2 One-to-one cardinality enforcement

On `relate(...)` with `cardinality = "one_to_one"`, the service queries `_single_tbl` with `KeyConditionExpression=Key("pk").eq(f"REL#{from_entity}#{from_id}#{rel_name}")` and `Limit=1`. If any item is returned, the link already exists and a new `relate` call raises HTTP 409 `{"code": "already_related"}`. This check also applies to the reverse direction: for a true 1:1 relationship, an admin should define two relationship definitions (one in each direction) and the per-direction PK check handles each side independently. If full bidirectional 1:1 enforcement is needed, the service also checks `pk = "REL#{to_entity}#{to_id}#{reverse_rel_name}"` when the definition has a `reverse_rel_name` attribute — this is an open question left for the admin to enforce via workflow, not hardcoded in this ticket (see Section 10).

### 5.3 Many-to-many duplicate link prevention

For all cardinalities, a duplicate `(from_id, to_id, rel_name)` instance is rejected with HTTP 409 `{"code": "already_related"}`. The check is a `get_item(Key={"pk": pk, "sk": sk})` which returns `None` (not present) or the item. If present, `relate` raises 409.

### 5.4 Blocking definition deletion when instances exist

`delete_relationship_def` must not leave orphaned instance rows accessible via `get_related`. Before soft-deleting, it performs a count check: `Query(KeyConditionExpression=Key("pk").begins_with(...))` is not available on a PK expression; instead, the service scans `_single_tbl` with `FilterExpression=Attr("rel_name").eq(rel_name) & Attr("from_entity").eq(from_entity) & Attr("to_entity").eq(to_entity)` and `Limit=1`. If any match is found, return HTTP 409 `{"code": "instances_exist"}`. Because DynamoDB `FilterExpression` does not reduce the scanned page (CLAUDE.md gotcha), the scan uses `Limit=1` at the DynamoDB level and relies on the filter to confirm the match. This is acceptable because the operation is admin-initiated and infrequent.

### 5.5 get_related pagination

DynamoDB `Query` on `pk = "REL#{from_entity}#{from_id}#{rel_name}"` returns items in SK (`TO#{to_entity}#{to_id}`) lexicographic order. The `ScanIndexForward=True` default is used (ascending SK order). `encode_cursor(resp["LastEvaluatedKey"])` produces a signed opaque token; `decode_cursor` on a tampered or expired cursor returns `None`, which the service treats as "start from the beginning" (no `ExclusiveStartKey`).

### 5.6 Instance rows survive definition soft-delete

Soft-deleting a definition sets `is_active=False` on the definition row. Existing instance rows in `app_single_table` are not removed. `get_related` does not validate the definition's `is_active` status — it queries instance rows directly. This is intentional: existing links remain readable for audit/reporting purposes after a definition is retired. `relate` and `unrelate` still validate the definition exists and is active before accepting new changes.

### 5.7 Entity type validation

`from_entity` and `to_entity` must be non-empty strings matching `^[a-z][a-z0-9_]{1,49}$`. The service validates this on `define_relationship`. No registry of valid entity types is maintained — any string is accepted, which allows relationships between not-yet-fully-implemented entity types (e.g., `opportunity` before OPP tickets ship). The calling application is responsible for passing valid entity identifiers.

### 5.8 rel_name scoping

`rel_name` uniqueness is scoped to the `(from_entity, to_entity)` pair. The same slug may be used for different entity pairs (e.g., `contact → opportunity` and `contact → case` can both have `rel_name="primary_ref"`). The PK pattern `REL#{rel_name}` in the SK space of `crm_studio_modules` ensures isolation.

### 5.9 Audit events

Every write path (define, update, delete definition; relate, unrelate instance) calls `audit_event(event_name, actor_sub, ...)` from `app/services/alerts.audit_event` (`alerts.py:644`). Audit events write to `T.alerts`, making them available in the ENTERPRISE-004 audit export. The STU-006 `CrmAuditTrailAdapter` can surface these events in the per-record trail without additional wiring.

### 5.10 CRM ACL permission gating on instances

The `POST /instances` and `DELETE /instances/...` endpoints use `Depends(require_crm_permission(from_entity_value, "update"))`. Because `from_entity` is a path/body parameter (not known at router declaration time), the dependency is constructed inline within the handler rather than at the decorator level:

```python
@router.post("/instances")
async def relate_records(body: CrmRelateIn, user = Depends(get_authenticated_user)):
    await require_crm_permission(body.from_entity, "update")(user)
    ...
```

When `S.crm_acl_enabled=False`, `require_crm_permission` is a no-op and all callers are permitted.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 dev/prod parity

There are no `if S.dev_mode` branches in `app/services/crm_relationships.py` or `app/routers/crm_relationships.py`. Definition rows and instance rows are written to DynamoDB in both dev (moto in-process mock) and prod (real DynamoDB) through the same code path. The `_single_tbl = ddb.Table(os.environ.get("APP_TABLE", "app_single_table"))` pattern is used everywhere in the codebase (e.g., `app/routers/newsfeed.py:65-70`) and works identically against moto and real DynamoDB.

### 7.2 Idempotency

- `relate(...)` on an already-linked pair returns HTTP 409. It is the caller's responsibility to check the response. No silent deduplication.
- `unrelate(...)` on a non-existent instance returns HTTP 404. Callers must handle this for at-least-once delivery scenarios.
- `define_relationship(...)` on a duplicate `rel_name` within the same entity pair returns HTTP 409.
- All DynamoDB writes use `put_item` (unconditional) because optimistic concurrency is not required — the pre-write existence check (via `get_item`) and the subsequent `put_item` are not atomic. In the unlikely case of a concurrent `relate` race, the second writer may overwrite the first's `created_at` and `created_by_sub` but not create a logically incorrect state (the link is still present). A conditional put (`ConditionExpression=attribute_not_exists(pk)`) can be added as a follow-up without changing the API contract.

### 7.3 Security

- **Root-only writes for definitions**: `POST /`, `PATCH /`, and `DELETE /` require `require_root`. This prevents ADMIN-level users from accidentally defining cross-module relationships that bypass security group enforcement.
- **CRM ACL permission on instances**: `POST /instances` and `DELETE /instances/...` require `require_crm_permission(from_entity, "update")`. When `CRM_ACL_ENABLED=0`, this is a no-op (open to all authenticated users), which is the safe default for an initially unconfigured CRM deployment.
- **`from_entity`/`from_id` injection**: Both are taken from user-supplied input. Validation (`^[a-z][a-z0-9_]{1,49}$` for entity types; non-empty for IDs) is applied before constructing DynamoDB key strings. The PK/SK pattern uses `#` as a delimiter; since entity types and rel_names are validated to contain only `[a-z0-9_]`, no injection via delimiter is possible.
- **Audit trail**: Every write path emits an `audit_event` to `T.alerts`. The STU-006 CRM audit trail adapter will surface relationship changes alongside field changes in the ENTERPRISE-004 export.
- **No sensitive data stored**: Relationship instance rows contain only entity type names, record IDs (UUIDs/slugs), and actor metadata. No PII, credentials, or financial data.

## 8. Backward Compatibility & Migration

### 8.1 No schema changes to existing tables

`crm_studio_modules` is a new table (STU-001). `app_single_table` is an existing table with a schemaless `pk`/`sk` design. The `REL#` PK prefix namespace is new and does not collide with any existing prefix in `app_single_table`. A `grep -rn '"REL#"' /home/ubuntu/testlogon/app/` returns no results — the namespace is unoccupied.

### 8.2 Flag-off guarantee

With `CRM_STUDIO_ENABLED=0` (the default), the router is never registered. No `REL#` rows are written. The `app_single_table` remains identical to its pre-STU-014 state. A deployment of this ticket without the flag does not require a DynamoDB `UpdateTable` or backfill — the `crm_studio_modules` table is created at startup by `scripts/local-ddb-init.py` as part of the STU-001 scaffold.

### 8.3 Flag-on migration

No data migration is required. On first startup with `CRM_STUDIO_ENABLED=true`, the `crm_studio_modules` table is empty (no relationship definitions exist). Admins must define relationships explicitly through the Studio UI or the `POST /ui/admin/studio/relationships` API before any instance links can be created. There is no seed data requirement.

### 8.4 Definition deletion is reversible

A soft-deleted definition (`is_active=False`) can be "un-deleted" by an admin calling `PATCH /{from_entity}/{to_entity}/{rel_name}` with no body (returns the existing row) or by a direct DDB write tool. A hard-delete endpoint is intentionally omitted — the `is_active` soft-delete preserves the audit trail of previously-defined relationships without cluttering the active definition list. Existing instance rows under a soft-deleted definition are not removed; they remain readable via `get_related` (see §5.6).

## 10. Open Questions / Assumptions

1. **Bidirectional 1:1 enforcement**: The current design only enforces uniqueness on the `from_entity` side. A true bidirectional 1:1 (e.g., a Contact linked to exactly one Contract) requires a separate reverse definition or a second cardinality check on the `to_entity` side. Assumption: bidirectional enforcement is out of scope for this ticket; it is the admin's responsibility to define a reverse relationship and rely on application-level validation in OPP/CAS/etc. routers.

2. **Reverse definition auto-creation**: SuiteCRM auto-creates a reverse relationship when a relationship is defined. This ticket does not auto-create the reverse row. An admin who wants `opportunity → contact` to also be traversable must define it explicitly. This is a deliberate simplification for the initial implementation.

3. **Instance `to_entity` validation**: The service does not verify that the `to_entity` value matches what was declared in the definition row. It trusts the `rel_name` lookup. If an admin calls `relate("contact", "c1", "invoice", "i1", "opportunities")` but the `opportunities` definition links `contact → opportunity`, the instance row will be written with `to_entity="invoice"`. The `get_related` query returns these rows as-is. Assumption: the frontend always passes the correct `to_entity` as it reads the definition. A validation step can be added in a follow-up.

4. **Pagination strategy for `list_relationship_defs`**: A full scan is used because definition counts are expected to be small (tens). If a deployment accumulates hundreds of definitions, a GSI on `crm_studio_modules` with `pk = "RELDEF_INDEX"` and `sk = from_entity + rel_name` could be added. Assumption: a full scan suffices for now.

5. **`app_single_table` key collision audit**: The `REL#` PK prefix has been verified as unoccupied by `grep -rn '"REL#"'` returning no results. New features that add `REL#` prefixes to `app_single_table` should check this spec before choosing their prefix.

6. **Cardinality change after instances exist**: `update_relationship_def` only allows label changes. Changing cardinality (e.g., from `many_to_many` to `one_to_one`) when instances already exist could leave the table in a state that violates the new cardinality. The safe approach (assumed here) is to forbid cardinality changes altogether after the first instance is created. If cardinality changes are ever needed, the admin must delete all instances, soft-delete the definition, and create a new definition.
