# EVT-013 — Document expiration date and expiry notification alerts

**Type:** Feature | **Priority:** P2 | **Estimate:** 2d
**Source:** `docs/suitecrm/CRM_MISC_TICKETS.md` (section "EVT-013")
**Dependencies:** EVT-011 (flag pattern, file node model); EVT-012 (revision model awareness). Reference pattern: `app/services/license_agreements.py`.

---

## 1. Summary & Goal

This ticket adds an optional expiration timestamp (`doc_expires_at`, Unix integer N) to file-manager file nodes and a background scheduler that fires both an in-app alert and an outbound email alert when a document is approaching expiry (within 30 days). A companion `doc_expiry_alert_sent` boolean guard ensures the alert fires exactly once per file per expiry date.

Two new pieces of surface area are introduced:

1. `PATCH /v1/fs/files/{path:path}/expiry` — sets or clears `doc_expires_at` on a node owned by the caller.
2. `start_document_expiry_checker_task()` — a background asyncio loop registered in `app/main.py`, polling every 3 600 seconds, that scans for approaching-expiry nodes and dispatches alerts.

Everything is gated by a new default-`False` feature flag `crm_document_expiry_enabled`. With the flag off the platform is byte-for-byte identical to today: the new endpoint returns 404, the background loop does not start, and no new DynamoDB GSI is queried.

The implementation reuses without modification:

- `app/services/alerts.write_alert` (`app/services/alerts.py:356`) for in-app alerts.
- `app/services/alerts.send_alert_email` (`app/services/alerts.py:459`) for outbound email.
- `app/services/profile.get_profile` (`app/services/profile.py:305`) to resolve the owner's `displayed_email`.
- `app/core.time.now_ts` (`app/core/time.py:2`) for all timestamp arithmetic.
- The file-manager's `_table()` / `node_key` / `get_node` / `put_node` helpers at `app/services/filemanager.py:104-107`, `446-447`, `450-462`.

## 2. Context & Current State

### File manager storage layer

The file manager persists every file and folder as a single-table DynamoDB item in the table named by `S.filemgr_table_name` (`app/core/settings.py:850`, env `FILEMGR_TABLE`). The `_table()` helper at `app/services/filemanager.py:104-107` acquires a live `boto3.Table` handle and raises HTTP 500 if the setting is empty.

Key layout (unchanged by this ticket):

- `PK = USER#<owner_sub>` — via `pk_user(user)` at `app/services/filemanager.py:438-439`.
- `SK = NODE#<normalised_path>` — via `sk_node(path)` at `app/services/filemanager.py:442-443`.
- Helper `node_key(user, path)` at `app/services/filemanager.py:446-447` produces the primary key dict.

The table is declared in `scripts/local-ddb-init.py:327-335` with exactly two GSIs today:

- `GSI1`: PK=`GSI1PK`, SK=`GSI1SK` — used for name-prefix search.
- `GSI2`: PK=`GSI2PK`, SK=`GSI2SK` — used for child listing by parent path.

Neither GSI uses a numeric sort key; no `attr_types` entry exists for `file_manager` in `local-ddb-init.py`. This ticket adds a **third GSI** (`GSI3`: PK=`GSI3PK`, SK=`GSI3SK`) whose sort key is a numeric Unix timestamp, requiring `attr_types={"GSI3SK": "N"}` (CLAUDE.md gotcha: omitting this causes `ValidationException` at query time).

### Existing file node item shape

When a file is uploaded, `upload_file` at `app/services/filemanager.py:2110-2188` writes a node item. There is currently no `doc_expires_at`, `doc_expiry_alert_sent`, `GSI3PK`, or `GSI3SK` attribute on any node. This ticket adds all four as optional, sparse attributes — nodes without an expiry date carry none of them.

## 3. Data Model

### No new DynamoDB table

All new attributes are stored as sparse additions to the existing `NODE#<path>` item in the `file_manager` table. No new table is needed.

### New attributes on the file-manager node item

| Attribute | DDB type | Nullable | Constraints |
|---|---|---|---|
| `doc_expires_at` | N (integer) | yes | Unix timestamp; must be `> now_ts()` at write time; removed from item (via `REMOVE` expression) when cleared |
| `doc_expiry_alert_sent` | BOOL | yes | absent when no expiry is set; set to `True` by the background checker after the alert fires |
| `GSI3PK` | S | yes | Written only when `doc_expires_at` is set; value `DOC_EXPIRY_MONTH#YYYY-MM` derived from `doc_expires_at` |
| `GSI3SK` | N | yes | Equal to `doc_expires_at`; absent when no expiry is set; **numeric** — requires `attr_types` |

`GSI3PK` / `GSI3SK` are removed (via `REMOVE` expression) when `doc_expires_at` is cleared, keeping the GSI sparse.

### GSI3 addition to the `file_manager` table definition

`scripts/local-ddb-init.py:327-335` currently declares `file_manager` with `GSI1` and `GSI2` and no `attr_types`. After this ticket it becomes:

```python
TableDef(
    _resolve_table_name(S.filemgr_table_name, "file_manager"),
    "PK",
    "SK",
    gsi=[
        {"index_name": "GSI1", "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "GSI2", "partition_key": "GSI2PK", "sort_key": "GSI2SK"},
        {"index_name": "GSI3", "partition_key": "GSI3PK", "sort_key": "GSI3SK"},
    ],
    attr_types={"GSI3SK": "N"},
),
```

`just restart` recreates the table including the new GSI. In production an `UpdateTable` call adds the GSI with an async backfill before this code is deployed (standard DynamoDB GSI addition procedure; no data loss risk since `GSI3PK`/`GSI3SK` are sparse and only written after deploy).

### Month-bucket key helper

```python
# Mirrors app/services/license_agreements.py:93-95
def _doc_expiry_month_pk(expires_at: int) -> str:
    from datetime import datetime, timezone
    dt = datetime.fromtimestamp(int(expires_at), tz=timezone.utc)
    return f"DOC_EXPIRY_MONTH#{dt.strftime('%Y-%m')}"
```

Using a month-bucket PK (identical pattern to `license_agreements._expiry_month_pk`) keeps each GSI partition small and avoids a hot partition. The scanner queries both the current month's bucket and the next month's bucket to cover the full 30-day horizon.

## 4. API / Service Design

### Pydantic models (additions to `app/models.py`)

```python
class FileExpiryIn(BaseModel):
    expires_at: Optional[int] = Field(
        default=None,
        description="Unix timestamp (seconds). Null clears the expiry.",
    )

class FileExpiryOut(BaseModel):
    path: str
    doc_expires_at: Optional[int]
    doc_expiry_alert_sent: bool
```

### Service functions (additions to `app/services/filemanager.py`)

#### `set_file_expiry(owner: str, path: str, expires_at: int | None) -> dict`

```python
def set_file_expiry(owner: str, path: str, expires_at: int | None) -> dict:
    ...
```

Behaviour:

1. Call `get_node(owner, path)` — raises HTTP 404 if node is absent or soft-deleted.
2. If `node["type"] != "file"` raise HTTP 400 `"expiry can only be set on files"`.
3. If `expires_at` is not `None` and `expires_at <= now_ts()`, raise HTTP 422 `"expires_at must be in the future"`.
4. Build `update_item` expression:
   - **Setting** (`expires_at` is not `None`):
     - `SET doc_expires_at = :exp, GSI3PK = :gpk, GSI3SK = :exp, doc_expiry_alert_sent = :f`
     - `:exp = expires_at`, `:gpk = _doc_expiry_month_pk(expires_at)`, `:f = False`
   - **Clearing** (`expires_at` is `None`):
     - `REMOVE doc_expires_at, GSI3PK, GSI3SK, doc_expiry_alert_sent`
5. Execute `_table().update_item(Key=node_key(owner, path), UpdateExpression=..., ExpressionAttributeValues=...)`.
6. Emit `audit_event("doc_expiry_set", owner, path=path, doc_expires_at=expires_at)`.
7. Return `{"path": path, "doc_expires_at": expires_at, "doc_expiry_alert_sent": False}`.

Note: `set_file_expiry` always resets `doc_expiry_alert_sent = False` when setting a new expiry, so a re-set expiry triggers a fresh alert.

#### `check_expiring_documents() -> int`

```python
def check_expiring_documents() -> int:
    ...
```

Behaviour:

1. `now = now_ts()`, `horizon = now + 30 * 86400`.
2. Build the set of month-bucket keys to query: `months = {_doc_expiry_month_pk(now), _doc_expiry_month_pk(horizon)}`.
3. For each `month_pk` in `months`:
   a. Query `_table()` on `GSI3` with `KeyConditionExpression=Key("GSI3PK").eq(month_pk) & Key("GSI3SK").between(now, horizon)`. Follows `LastEvaluatedKey` in a loop (CLAUDE.md: FilterExpression does not reduce page size; the GSI query itself limits to the numeric range, but DynamoDB can still page).
   b. For each item returned:
      - Skip if `item.get("type") != "file"` or `item.get("doc_expiry_alert_sent")`.
      - `owner = item["PK"][len("USER#"):]` (reverse of `pk_user`).
      - `path = item.get("path", "")`.
      - `exp = int(item.get("doc_expires_at", 0))`.
      - `days = max(0, (exp - now) // 86400)`.
      - Resolve the owner's email: `profile = get_profile(owner) or {}; email = profile.get("displayed_email")`.
      - Call `write_alert(owner, event="doc_expiring", outcome="warning", title="Document Expiring Soon", details={"path": path, "name": item.get("name",""), "doc_expires_at": exp, "days_remaining": days}, action_url=f"/files?path={path}")`.
      - If `email`: call `send_alert_email([email], subject=f"Document expiring in {days} days: {item.get('name','')}", body_text=f"Your document '{item.get('name','')}' at {path} expires in {days} day(s).")`.
      - Set `doc_expiry_alert_sent = True` via targeted `update_item`: `UpdateExpression="SET #f = :t", ExpressionAttributeNames={"#f": "doc_expiry_alert_sent"}, ExpressionAttributeValues={":t": True}, Key=node_key(owner, path)`. Use a `ConditionExpression=Attr("doc_expiry_alert_sent").ne(True)` (idempotency guard — see section 5).
      - Catch and log any per-item exception; continue the loop.
      - Increment `sent` counter on success.
4. Return `sent`.

## 5. Detailed Behavior & Edge Cases

### Expiry in the past

`set_file_expiry` validates `expires_at > now_ts()` at write time (mirrors `license_agreements.py:198-199`). Passing `expires_at = now_ts() - 1` raises HTTP 422. Passing `expires_at = None` is always valid (clears the expiry).

### Re-setting expiry on an already-alerted file

`set_file_expiry` always writes `doc_expiry_alert_sent = False` when a non-null `expires_at` is provided. This means that if a user extends a document's expiry after the alert has already fired, the checker will send a fresh alert when the new 30-day window arrives. This is the correct and expected behaviour.

### Horizon spans two calendar months

The checker computes `months = {_doc_expiry_month_pk(now), _doc_expiry_month_pk(horizon)}`. Because the horizon is 30 days out, `now` and `horizon` may fall in the same calendar month or span a month boundary (e.g., checking on 15 June: horizon = 15 July, so both `DOC_EXPIRY_MONTH#2026-06` and `DOC_EXPIRY_MONTH#2026-07` are queried). Items in the overlapping month (within the horizon range) will be returned by the `between(now, horizon)` key condition and correctly processed.

### Duplicate-query of items near a month boundary

An item whose `doc_expires_at` falls exactly in the overlapping bucket is returned by both month queries in the same checker run. The `ConditionExpression=Attr("doc_expiry_alert_sent").ne(True)` on the `update_item` makes the second write a no-op (DynamoDB conditional write fails silently with `ConditionalCheckFailedException`, which is caught and swallowed per the per-item exception handler). The `sent` counter is only incremented on the first success.

### Soft-deleted files

`get_node` (`app/services/filemanager.py:450-457`) raises HTTP 404 for soft-deleted nodes (those with a `deleted_at` attribute). The background checker uses `_table().query(IndexName="GSI3", ...)` directly. A soft-deleted node retains its GSI3 attributes (the soft-delete path at `app/services/filemanager.py:1758-1787` does not clear them today). The checker must explicitly skip items with `item.get("deleted_at")` set — this is added as a skip condition alongside `doc_expiry_alert_sent`.

### Folders

`set_file_expiry` rejects `type != "file"` with HTTP 400. Folders cannot have expiry dates.

### Owner email absent

If `profile.get("displayed_email")` returns `None` or empty string, the `send_alert_email` call is skipped for that item (the `if email:` guard). The in-app `write_alert` still fires. This matches the behaviour of `send_alert_email` itself, which returns early on an empty `to_emails` list (`app/services/alerts.py:460-461`).

### Alert sent field and TTL

`doc_expiry_alert_sent` is set permanently (no TTL). When a document eventually passes its expiry date it remains in DDB (the file manager has a separate purge mechanism for deleted files; expired documents are not auto-deleted by this ticket). A follow-on ticket (e.g., EVT-013b) could implement auto-deletion on expiry; this ticket only alerts.

### Concurrent checker runs

If two instances of the background loop run simultaneously (e.g., during a rolling deploy), the `ConditionExpression` on `update_item` ensures exactly-once alert dispatch — only the first writer succeeds; the second hits `ConditionalCheckFailedException` and the per-item `except` swallows it.

### Empty `filemgr_table_name`

`start_document_expiry_checker_task` checks `S.filemgr_table_name` before starting the loop. If the table name is unset the loop is skipped silently (same guard as `start_filemgr_purge_task` at `app/services/filemanager.py:4337-4338`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

There is no `if S.dev_mode:` branch anywhere in this feature. Both `write_alert` and `send_alert_email` already handle the dev/prod split internally:

- `write_alert` (`app/services/alerts.py:356`) writes to `T.alerts` (DDB local in dev, real DDB in prod) — same code path.
- `send_alert_email` (`app/services/alerts.py:459-480`) writes to `S.dev_email_log` in dev mode, sends SES in prod — the caller (`check_expiring_documents`) has no knowledge of this split.
- `get_profile` (`app/services/profile.py:305`) reads from `T.profile` — same DDB-backed path in both envs.

The new GSI3 on `file_manager` is created identically in dev (via `just restart` → `local-ddb-init.py`) and prod (via `UpdateTable`). No mock/real divergence.

### Idempotency

The `update_item` that sets `doc_expiry_alert_sent = True` uses `ConditionExpression=Attr("doc_expiry_alert_sent").ne(True)`. If the item is already `True` the write fails with `ConditionalCheckFailedException`, which is caught and silently ignored. This makes the alert dispatch idempotent: rerunning the checker (e.g., after a crash mid-run) does not re-send already-sent alerts.

The `set_file_expiry` write is unconditional (last-write-wins). Concurrent `PATCH` requests from the same user for the same file will both succeed; the final state reflects the last writer. This is acceptable for a user-facing metadata field.

### Security

**Owner isolation**: `set_file_expiry` always passes `owner=user` derived from the authenticated session. It cannot be used to set expiry on another user's files — `get_node(owner, path)` keys on `PK=USER#{owner}` and returns HTTP 404 for any path not owned by `owner`.

**Input validation**: `expires_at` is validated as `> now_ts()` before any DDB write. The field is stored as a plain integer (no eval, no deserialization risk).

**No money-out path**: this feature sends informational alerts only; it does not initiate payments, refunds, or billing operations. No `refund_payment` / `settle_or_reverse_ledger` wiring is needed.

**Audit trail**: `audit_event("doc_expiry_set", owner, ...)` is emitted on every `PATCH` call, recording the path, new `expires_at`, and the acting `user_sub`.

## 8. Backward Compatibility & Migration

### Existing file nodes

Existing nodes carry no `doc_expires_at`, `doc_expiry_alert_sent`, `GSI3PK`, or `GSI3SK` attributes. The feature is opt-in: users explicitly call `PATCH .../expiry` to enroll a file. The background checker's GSI3 query returns only nodes that have been enrolled (sparse GSI — unenrolled nodes have no `GSI3PK` attribute and are invisible to the index).

### GSI backfill

Adding `GSI3` to an existing `file_manager` table in production triggers a DynamoDB GSI backfill. During backfill, items that already have `GSI3PK` (none, until callers start setting expiry) would be indexed. Since no existing items carry `GSI3PK`, the backfill is instantaneous in practice. GSI queries during backfill return an eventually-consistent partial view; the 3 600-second checker interval means any brief inconsistency window is irrelevant.

### `just restart` in dev

`local-ddb-init.py` wipes and recreates all tables from scratch on `just restart`. The modified `TableDef` (adding `GSI3` + `attr_types={"GSI3SK": "N"}`) takes effect immediately. No manual migration step is required in dev.

### EVT-011 (CRM document library metadata) and EVT-012 (revision history)

This ticket's new attributes (`doc_expires_at`, `doc_expiry_alert_sent`, `GSI3PK`, `GSI3SK`) coexist with EVT-011's CRM metadata fields (`crm_category`, `crm_description`, `linked_record_type`, `linked_record_id`) and EVT-012's revision rows (`SK=REVISION#...`) without conflict. All are sparse attributes on the same `NODE#<path>` item or distinct SK variants in the same table. No collision.

The background checker queries by `GSI3PK` (month bucket) and filters by `type == "file"` and `not doc_expiry_alert_sent`, so EVT-012 revision rows (SK prefix `REVISION#`) are never enrolled in the GSI and are never processed by the checker.

## 10. Open Questions / Assumptions

1. **Multiple alert thresholds**: The ticket specifies a single 30-day alert. Future tickets could add configurable multi-stage thresholds (e.g., 30 days, 7 days, 1 day). The `doc_expiry_alert_sent` boolean would need to become an array or bitmask. This ticket does not implement multi-stage; the field is boolean for simplicity.

2. **Post-expiry handling**: Once `doc_expires_at` passes the document is not auto-deleted or access-blocked by this ticket. A follow-on EVT-013b could auto-soft-delete expired documents. This ticket only sends an advance warning alert.

3. **Shared / public files**: The file-manager has a file-sharing model (the `shared` attribute on node items, used in `app/routers/filemanager.py:1108-1148`). If a shared file expires, only the owner gets the alert. Recipients of shared files do not receive expiry alerts in this ticket. This is an assumed simplification.

4. **Email subject length vs. long filenames**: `send_alert_email` truncates the `subject` parameter to 120 chars (`app/services/alerts.py:477`). The subject template `"Document expiring in {days} days: {name}"` is truncated automatically. No additional truncation logic is needed in the caller.

5. **Expiry on EVT-012 revision rows**: Revision rows (`SK=REVISION#...`) are not `type="file"` nodes; they are archived snapshots. This ticket does not support setting expiry on individual revision rows. Only the live/current `NODE#<path>` item can have an expiry date.

6. **Assumption — `PATCH` path parameter encoding**: The `/v1/fs/files/{path:path}` path parameter uses FastAPI's greedy `path` type (same as existing file-manager endpoints), which captures slashes. URL-encoding is the caller's responsibility.
