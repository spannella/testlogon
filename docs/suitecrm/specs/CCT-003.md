# CCT-003 — Reports-to hierarchy on Contacts (manager chain)

**Type:** Feature | **Priority:** P2 | **Estimate:** 2d  
**Source:** `docs/suitecrm/CRM_CONTACTS_EXTRA_TICKETS.md` — CCT-003 section  
**Flag:** `PARTY_CRM_ENABLED` (existing, from PTY-001)

---

## 1. Summary & Goal

SuiteCRM's Contacts module supports a "Reports To" field that links a contact to their direct manager, enabling navigation of corporate org-chart relationships between individual contact records. The testlogon platform's existing social-graph contacts surface (`app/routers/contacts.py`) models only friend/block relationships and has no concept of a management hierarchy. The planned OFBiz Party/CRM buildout (PTY-001..PTY-015) establishes a generic relationship graph on the `party` single table, but none of those specs introduce a manager-chain type.

CCT-003 bridges that gap by:

1. Adding `REPORTS_TO` as a new value in the `CrmRelationshipType` enum (`app/models.py`), connecting two `PERSON` parties where `from_party_id` is the direct report and `to_party_id` is the manager.
2. Adding `set_manager` and `get_reports_to_chain` helpers to `app/services/party.py`, reusing the `create_relationship` / `delete_relationship` / `list_relationships` primitives from PTY-006 (`docs/ofbiz/specs/PTY-006.md`).
3. Wiring three new router endpoints to `app/routers/party.py` (PTY-011 scaffold) under `/ui/party/parties/{party_id}`.
4. Extending `CrmPartyOut` with two additive fields (`manager_party_id`, `direct_report_count`) so party-detail responses surface the manager reference inline.

The feature is entirely additive and gated behind `S.party_crm_enabled` (default off). With the flag off, the platform is byte-for-byte unchanged.

## 3. Data Model

### 3.1 No new DynamoDB table or GSI

CCT-003 writes only `REL#REPORTS_TO#…` and `MIRROR#REPORTS_TO#…` rows to the existing `party` table, using the SK namespace already established by PTY-006 (`docs/ofbiz/specs/PTY-006.md:218–229`). The `REPORTS_TO` value is 10 uppercase ASCII characters — safe as a URL segment and as a DynamoDB SK component. No schema change is required in `scripts/local-ddb-init.py`.

The full `party` table GSI layout after PTY-002 (`docs/ofbiz/specs/PTY-002.md:77–112`):

| Index | PK (S) | SK type | Used by CCT-003 |
|---|---|---|---|
| `GSI1` | `GSI1PK` | `GSI1SK` (S) | No |
| `GSI2` | `GSI2PK` | `GSI2SK` (S) | No |
| `GSI3` | `GSI3PK` | `GSI3SK` (S) | Yes — `REL_TO#{to_party_id}` reverse lookup for direct reports |
| `GSI_CREATED` | `type` | `created_at` (N) | No |

`attr_types={"created_at": "N"}` is already declared in `scripts/local-ddb-init.py` by PTY-002 (`docs/ofbiz/specs/PTY-002.md:110`). `GSI3SK` is String — no additional `attr_types` entry is needed.

### 3.2 DynamoDB row shapes written by CCT-003

**Primary row** (written by `set_manager` via `create_relationship`):

```json
{
  "PK":               "PARTY#{direct_report_party_id}",
  "SK":               "REL#REPORTS_TO#{manager_party_id}",
  "from_party_id":    "<direct_report_party_id>",
  "to_party_id":      "<manager_party_id>",
  "relationship_type":"REPORTS_TO",
  "rel_id":           "<uuid4().hex>",
  "created_at":       1749200000
}
```

**Mirror row** (written atomically with the primary by `create_relationship`):

```json
{
  "PK":               "PARTY#{manager_party_id}",
  "SK":               "MIRROR#REPORTS_TO#{direct_report_party_id}",
  "from_party_id":    "<direct_report_party_id>",
  "to_party_id":      "<manager_party_id>",
  "relationship_type":"REPORTS_TO",
  "rel_id":           "<same rel_id>",
  "created_at":       1749200000,
  "GSI3PK":           "REL_TO#{manager_party_id}",
  "GSI3SK":           "REL#REPORTS_TO#{direct_report_party_id}"
}
```

The mirror's `GSI3PK = "REL_TO#{manager_party_id}"` enables `get_reports_to_chain(direction="reports")` to find all direct reports of a given manager via a single GSI3 query with `KeyConditionExpression = Key("GSI3PK").eq(f"REL_TO#{manager_party_id}") & Key("GSI3SK").begins_with("REL#REPORTS_TO#")`.

## 4. API / Service Design

### 4.1 Service helpers in `app/services/party.py`

Both functions are appended to the module after the PTY-006 relationship block. They are unconditionally callable from tests (no flag guard inside the service); the flag is enforced at the router layer.

#### `set_manager`

```python
def set_manager(
    person_party_id: str,
    manager_party_id: str,
    *,
    actor_party_id: str,
) -> Dict[str, Any]:
```

**Contract:**

1. Validate `person_party_id != manager_party_id`; raise `ValueError("self_reports_to_not_allowed")` otherwise.
2. Fetch `get_party(person_party_id)`. If `None` or `party_type != "PERSON"`, raise `ValueError("party_must_be_person")`.
3. Fetch `get_party(manager_party_id)`. If `None` or `party_type != "PERSON"`, raise `ValueError("manager_must_be_person")`.
4. **Circular check:** starting from `manager_party_id`, walk `REPORTS_TO` edges upward (follow each party's `REL#REPORTS_TO#*` row) up to depth 10. If `person_party_id` appears in the chain, raise `ValueError("circular_reports_to")`. If the depth-10 limit is hit without finding a terminus, also raise `ValueError("circular_reports_to")` — a chain that deep is assumed malformed. This matches the CCT-002 contract (`docs/suitecrm/specs/CCT-002.md:339–340`): both tickets raise an error when the depth cap is exceeded, rather than silently allowing the write.
5. **Replace existing manager:** query `T.party` for `PK=PARTY#{person_party_id}`, `SK begins_with "REL#REPORTS_TO#"`. If a row exists, call `delete_relationship(person_party_id, existing_to_party_id, "REPORTS_TO")` first (only one manager allowed per person).
6. Call `create_relationship(person_party_id, manager_party_id, "REPORTS_TO")`.
7. Emit `audit_event("party_manager_set", actor_party_id, None, person_party_id=person_party_id, manager_party_id=manager_party_id)`.
8. Return the primary row dict.

#### `remove_manager`

```python
def remove_manager(
    person_party_id: str,
    *,
    actor_party_id: str,
) -> None:
```

**Contract:**

1. Validate `person_party_id` is a valid non-empty string; length ≤ 64.
2. Query `T.party` for `PK=PARTY#{person_party_id}`, `SK begins_with "REL#REPORTS_TO#"`. If no row, return silently (idempotent, same as `delete_relationship` for a non-existent edge per `docs/ofbiz/specs/PTY-006.md:585–591`).
3. Call `delete_relationship(person_party_id, found_to_party_id, "REPORTS_TO")`.
4. Emit `audit_event("party_manager_removed", actor_party_id, None, person_party_id=person_party_id)`.

#### `get_reports_to_chain`

```python
def get_reports_to_chain(
    person_party_id: str,
    *,
    direction: str = "manager_chain",
) -> Dict[str, Any]:
```

**Contract (two modes):**

**`direction="reports"`** — returns direct reports of `person_party_id`:
- Query `GSI3` with `GSI3PK = "REL_TO#{person_party_id}"` and `GSI3SK begins_with "REL#REPORTS_TO#"`.
- Each item is a mirror row; project to `CrmRelationshipOut`-compatible dict (`from_party_id`, `to_party_id`, `relationship_type`, `created_at`).
- Returns `{"chain": [...], "direction": "reports", "truncated": False}`.
- No pagination (direct reports are expected to be a small set; a single query with `Limit=200` is sufficient for Phase 1).

**`direction="manager_chain"`** — walks the management chain upward from `person_party_id`:
- Step 1: fetch `T.party.get_item(Key={"PK": f"PARTY#{person_party_id}", "SK begins_with REL#REPORTS_TO#"})` — actually `query` with `PK=PARTY#{person_party_id}` + `SK begins_with "REL#REPORTS_TO#"`, take the first item if any.
- Step 2: follow `to_party_id` edges iteratively, collecting each edge into a list. Stop at depth 10 (set `truncated=True`) or when no further `REPORTS_TO` row exists.
- Returns `{"chain": [...], "direction": "manager_chain", "truncated": <bool>}`. Index 0 is the immediate manager edge; last item is the top of the chain.

Both modes return `{"chain": [], "direction": "...", "truncated": False}` when no edges exist — never 404.

### 4.3 `get_party` augmentation

The `get_party(party_id)` service function (PTY-004) and its `_item_to_party_out` helper must be extended to populate the two new `CrmPartyOut` fields. The augmentation is a post-fetch enrichment step:

```python
def _enrich_party_out(item: dict) -> dict:
    """Populate manager_party_id and direct_report_count from the party table."""
    party_id = item["party_id"]
    # Manager: query REL#REPORTS_TO# rows on this party's own partition
    mgr_rows = T.party.query(
        KeyConditionExpression=Key("PK").eq(f"PARTY#{party_id}") & Key("SK").begins_with("REL#REPORTS_TO#"),
        Limit=1,
    ).get("Items", [])
    item["manager_party_id"] = mgr_rows[0]["to_party_id"] if mgr_rows else None

    # Direct reports: count MIRROR#REPORTS_TO# rows on this party's partition
    dr_resp = T.party.query(
        KeyConditionExpression=Key("PK").eq(f"PARTY#{party_id}") & Key("SK").begins_with("MIRROR#REPORTS_TO#"),
        Select="COUNT",
    )
    item["direct_report_count"] = int(dr_resp.get("Count", 0))
    return item
```

This enrichment is only called when `S.party_crm_enabled` is True — the `get_party` code path is already gated at the router layer. To avoid adding two DDB round-trips to every `get_party` call unconditionally, the enrichment is made conditional: only called when the handler explicitly passes `enrich_hierarchy=True` to `_item_to_party_out`, or when `S.party_crm_enabled` is True and the route is a party-detail GET. This keeps the base `get_party` fast for internal callers that do not need hierarchy data.

## 5. Detailed Behavior & Edge Cases

### 5.1 Only PERSON parties may participate

`set_manager` validates both `person_party_id` and `manager_party_id` are `PERSON` parties (not `PARTY_GROUP`). A `PARTY_GROUP` party as either the report or the manager raises `ValueError("party_must_be_person")` or `ValueError("manager_must_be_person")` respectively, which the router converts to HTTP 400. This prevents org-account nodes from appearing in the personal management chain.

### 5.2 Only one direct manager per person

A person may have at most one `REPORTS_TO` edge at any time. `set_manager` queries for any existing `REL#REPORTS_TO#*` row before writing. If found, it calls `delete_relationship` to remove the old edge before writing the new one. The old-then-new sequence is not atomic across two `transact_write_items` calls; the window between delete and create is a brief inconsistency window. In practice:
- A concurrent `set_manager` call from another session would either win the delete or the create, leaving at most one row.
- A read during the window would see zero edges rather than two — a safe transient state.
- For Phase 1 this is acceptable. A full atomic swap could use a single `transact_write_items` with a `ConditionExpression` on the old SK, but that adds complexity not required here.

### 5.3 Circular chain detection

Before writing, `set_manager` walks the manager-chain from `manager_party_id` upward. Implementation:

```python
visited = set()
cursor_id = manager_party_id
depth = 0
while cursor_id and depth < 10:
    if cursor_id == person_party_id:
        raise ValueError("circular_reports_to")
    visited.add(cursor_id)
    rows = T.party.query(
        KeyConditionExpression=Key("PK").eq(f"PARTY#{cursor_id}") & Key("SK").begins_with("REL#REPORTS_TO#"),
        Limit=1,
    ).get("Items", [])
    cursor_id = rows[0]["to_party_id"] if rows else None
    depth += 1
if cursor_id is not None:  # depth cap reached without finding a terminus
    raise ValueError("circular_reports_to")
```

If the depth-10 cap is hit and the chain has not terminated, `cursor_id` will still be non-`None`; the guard after the loop raises `ValueError("circular_reports_to")`. This matches the CCT-002 contract (`docs/suitecrm/specs/CCT-002.md:339–340`): depth-10-exceeded is treated as a cycle error, preventing an unbounded-chain write.

### 5.4 Self-loop rejection

`person_party_id == manager_party_id` is rejected immediately with `ValueError("self_reports_to_not_allowed")` before any DDB access. The same check exists in the `_parties_differ` validator on `CrmRelationshipIn` (PTY-003) — the service adds a second layer for defense-in-depth.

### 5.5 `direction` parameter validation

`GET /reports-to` rejects any `direction` value not in `{"reports", "manager_chain"}` with HTTP 400 before calling the service. This prevents invalid values propagating into the DDB query.

### 5.6 Non-existent `party_id` in GET

`get_reports_to_chain` does not pre-validate that the party exists. A query for a non-existent `PK` returns an empty `Items` list — the endpoint returns `{"chain": [], "direction": "...", "truncated": False}` with HTTP 200. The caller can distinguish a "party exists but no manager" state from a "party does not exist" state via a separate `GET /parties/{party_id}` call. This is acceptable for Phase 1 and consistent with how `list_relationships` behaves for non-existent parties: a DynamoDB `query` on a non-existent `PK` returns `{"Items": []}` silently, so the function returns an empty result rather than 404 (`docs/ofbiz/specs/PTY-006.md:§5.4` describes the analogous no-error behaviour for deletes; the same DDB characteristic applies to queries).

### 5.7 `remove_manager` idempotency

Calling `DELETE /parties/{party_id}/manager` when no `REPORTS_TO` row exists returns 204 without error. `delete_relationship` (PTY-006) is itself a no-op for non-existent rows (`docs/ofbiz/specs/PTY-006.md:585–591`).

### 5.8 `direct_report_count` accuracy

`direct_report_count` is computed by counting `MIRROR#REPORTS_TO#*` rows in the manager's DDB partition. This is consistent because `create_relationship` writes mirror rows atomically with the primary row (`docs/ofbiz/specs/PTY-006.md:304–314`). The count reflects the current number of direct reports without approximation.

### 5.9 Flag-off guarantee

With `S.party_crm_enabled = False` (the default):
- `PUT /parties/{party_id}/manager`, `DELETE /parties/{party_id}/manager`, and `GET /parties/{party_id}/reports-to` all return HTTP 503 `{"detail": "party_crm_disabled"}`.
- `set_manager`, `remove_manager`, and `get_reports_to_chain` are never called through the request path.
- `T.party` is never read or written.
- `app/routers/contacts.py`, all billing, messaging, calendar, and every other subsystem is byte-for-byte unchanged.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

`app/services/party.py` writes to `T.party` — the same DynamoDB table in dev (DynamoDB Local at `http://localhost:8001`, supplied via `.env.local`) and prod (real DynamoDB). There are no `if S.dev_mode:` branches in `set_manager`, `remove_manager`, or `get_reports_to_chain`. The underlying `create_relationship` and `delete_relationship` functions use `transact_write_items` via `_ddb_client()` (the `agent_orchestrator._ddb_lowlevel_client` pattern at `app/services/agent_orchestrator.py:25–51`) which inherits endpoint and credentials from the shared `ddb` resource — identical in both environments.

### 7.2 Idempotency

- `set_manager` replaces any existing manager: it is safe to call twice with the same arguments. The first call deletes the old edge (if any) and writes the new one; the second call finds the same existing edge, calls delete (no-op on the now-correct row), then hits `create_relationship`'s `ConditionalCheckFailedException` path which returns the existing row without re-auditing. Net result: idempotent.
- `remove_manager` is explicitly idempotent (no-op if edge absent).
- `get_reports_to_chain` is a pure read — idempotent by definition.

### 7.3 Security

- **No PII in DynamoDB keys:** All PK/SK values contain only `party_id` (32-char hex), the string `"REPORTS_TO"`, and static prefixes. No email, name, or phone appears in any key.
- **Input length guard:** `CrmSetManagerIn.manager_party_id` is `Field(..., max_length=64)`, bounding SK construction. All generated party IDs are 32-char hex; the 64-char cap provides a safety margin without being gratuitously restrictive.
- **PERSON-only guard:** The service validates both parties are `PERSON` before writing. A `PARTY_GROUP` can never participate in a `REPORTS_TO` edge, preventing org-account nodes from polluting the personal hierarchy.
- **Depth-10 cycle cap:** Prevents a crafted chain from causing an unbounded DDB query loop in `get_reports_to_chain(direction="manager_chain")`.
- **No money-out path:** The manager chain carries no billing data. The billing/GL ledger constraint does not apply.
- **Audit trail:** Every successful `set_manager` and `remove_manager` emits `audit_event` to `T.alerts` via `app/services/alerts.py:644`, maintaining an immutable audit log.
- **Auth:** All three endpoints require `require_ui_session`; unauthenticated requests return 401 before any service code runs.

## 8. Backward Compatibility & Migration

### 8.1 Model changes are additive

`CrmRelationshipType.REPORTS_TO` is a new enum member — it does not change the serialised values of any existing member. Existing DynamoDB rows with `relationship_type` in `{EMPLOYMENT, GROUP_MEMBER, CONTACT_REL, OWNER}` are unaffected.

`CrmPartyOut.manager_party_id` and `CrmPartyOut.direct_report_count` both carry defaults (`None` and `0`). Any code that constructs `CrmPartyOut` without specifying these fields receives the defaults. Any API consumer that does not read these fields sees no change. The OpenAPI schema gains two new optional response fields — backward-compatible per JSON Schema rules.

`CrmSetManagerIn` and `CrmReportingChainOut` are new models. They introduce no collisions with existing models in `app/models.py` (the `Crm`-prefix convention established by PTY-003 at `docs/ofbiz/specs/PTY-003.md:54–75` is followed throughout).

### 8.2 Service function additions are purely additive

`set_manager`, `remove_manager`, and `get_reports_to_chain` are appended to `app/services/party.py` after the PTY-006 block. No existing function signatures are modified. The `_VALID_REL_TYPES` frozenset is the only line that changes in existing service code: `"REPORTS_TO"` is added. This does not break any existing relationship operation — `create_relationship` and `delete_relationship` simply gain a new valid type string.

### 8.3 Router additions do not disturb existing routes

The three new endpoints use the terminal paths `manager` and `reports-to` under `{party_id}`, which are distinct from all existing terminal paths (`roles`, `relationships`, `mechs`, `lookup`). No declaration-order conflict exists (each tail segment is unique).

### 8.4 No data migration

The `party` table is created empty at `just restart` time. In production, `REPORTS_TO` rows simply do not exist before CCT-003 ships — `get_reports_to_chain` returns empty chains for all parties, which is the correct base state.

### 8.5 Rollback

Remove the three new functions from `app/services/party.py`, remove the three endpoints from `app/routers/party.py`, revert the `CrmRelationshipType` enum, and revert the `CrmPartyOut` additions. Any `REL#REPORTS_TO#*` and `MIRROR#REPORTS_TO#*` rows already in DynamoDB will be ignored (no code queries for them with the flag off). A full rollback is safe with no data loss beyond the relationship rows themselves.

## 10. Open Questions / Assumptions

1. **Assumption — PTY-006 `_VALID_REL_TYPES` is an inline frozenset (not a model import).** `docs/ofbiz/specs/PTY-006.md:863–871` recommends using an inline `frozenset({"EMPLOYMENT", ...})` to avoid circular imports between `app/services/party.py` and `app/models.py`. CCT-003 assumes this pattern is in place and that adding `"REPORTS_TO"` to that frozenset is the only service-file change needed to make `create_relationship(..., "REPORTS_TO")` valid.

2. **Assumption — `get_party` enrichment is opt-in.** The spec adds two DDB round-trips (`manager_party_id` lookup and `direct_report_count` count) to the party-detail fetch. If called on every `GET /parties/{party_id}`, this doubles the DDB cost of the endpoint. The design proposes an `enrich_hierarchy=True` parameter to `_item_to_party_out`, defaulting to `False` for internal callers. The E2E spec verifies the fields appear in the GET response; implementors may choose to always enrich (simpler code) or make it conditional (lower latency).

3. **Assumption — `direction="reports"` uses GSI3 query without pagination.** Direct-report counts in a B2B context are expected to be in the tens to hundreds. A single `Limit=200` GSI3 query is sufficient. If a manager has more than 200 direct reports, only the first 200 are returned and a future pagination enhancement (cursor on `GSI3SK`) would be needed. This is out of scope for Phase 1.

4. **Open question — ownership enforcement.** PTY-011 `§5.2` defers ownership enforcement to a later milestone. CCT-003 follows the same deferral: any authenticated user with `S.party_crm_enabled=True` can set or read manager relationships for any party. If ownership enforcement is added by PTY-011 before CCT-003 ships, CCT-003 should call `_assert_party_access(party_id, ctx["user_sub"])` at the top of each handler (same as other `{party_id}` routes per `docs/ofbiz/specs/PTY-011.md:§5.2`).

5. **Open question — cross-org manager chains.** The current design allows a `PERSON` in one org to have a manager who is a `PERSON` in a different org (or in no org). This is intentional (SuiteCRM's "Reports To" is a simple contact-to-contact pointer, not scoped to an organisation). If org-scoped manager chains are required, the `set_manager` validation should be extended to check that both parties belong to the same `PARTY_GROUP` via a shared `GROUP_MEMBER` relationship. Deferred.

6. **Assumption — `remove_manager` uses the actor's `user_sub` as `actor_party_id`.** The audit event logs `actor_party_id=ctx["user_sub"]` (the Cognito sub). This is consistent with how PTY-006 logs relationship creates/deletes (using `from_party_id` as the audit subject). If a different party-scoped actor ID is required, the `CrmSetManagerIn` model could add an optional `actor_party_id` override field.
