# STU-008 — Admin email queue manager

**Type:** Feature  **Priority:** P1  **Estimate:** 2d  
**Ticket source:** `docs/suitecrm/CRM_SECURITY_STUDIO_TICKETS.md`, section "STU-008"

---

## 1. Summary & Goal

STU-008 adds an optional async outbound-email queue layer to the platform. Today every call to `app/services/alerts.send_alert_email` fires synchronously inside the request cycle: if SES is slow or unavailable the caller blocks or silently drops the email. This ticket introduces a `email_queue` DynamoDB table (provisioned by STU-001), a service layer that enqueues, processes, retries, and cancels queued messages, a background worker that drains the queue on a configurable interval, and five admin-only REST endpoints under `/ui/admin/email-queue` for queue inspection and manual intervention.

The feature is entirely additive and default-OFF (`S.email_queue_enabled`, env `EMAIL_QUEUE_ENABLED`, default `"0"`). When the flag is off, `enqueue_email` writes and logs nothing, all five router endpoints return 404, the background worker never starts, and the existing `send_alert_email` synchronous path is completely unchanged — the platform is byte-for-byte identical to its pre-STU-008 state.

## 2. Context & Current State

### 2.1 Existing synchronous send path

`app/services/alerts.send_alert_email` (`app/services/alerts.py:459`) is the platform-wide fire-and-forget email helper. In dev mode (`S.dev_mode`) it writes a text entry to the dev email log file and returns immediately (`alerts.py:462–468`). In production it calls `boto3.client("ses").send_email` synchronously (`alerts.py:472–478`). On SES failure it logs the exception, increments the `EMAIL_FAILED` Prometheus counter, calls `record_email_failure` from `email_delivery.py`, and returns `None` — the caller never learns the email was dropped (`alerts.py:479–491`). There is no retry mechanism, no queue, and no admin visibility into transient failures.

### 2.2 Email delivery tracking (existing)

`app/services/email_delivery.py` provides `record_email_sent`, `record_email_failure`, `record_dev_email`, `record_email_bounce`, `record_email_complaint`, `suppress_email`, `is_suppressed`, `remove_suppression`, and the admin query helpers `list_deliveries`, `list_bounces`, `list_complaints`, `get_delivery_stats`, `get_suppression_list` (`email_delivery.py:33–300`). The table schema is `PK=pk (S), SK=sk (S)` with a `ByStatus` GSI keyed on `(status S, created_at N)` with `attr_types={"created_at": "N"}` (`scripts/local-ddb-init.py:1420–1428`).

### 2.3 Admin email monitoring router (existing)

`app/routers/admin_email.py` provides the existing delivery-monitoring dashboard under the prefix `/ui/admin/email` (`admin_email.py:32`). It is registered in `app/main.py:241, 778`. All endpoints require `Depends(require_admin_or_root)` from `app/auth/policy.py:67`. STU-008's new router uses a sibling prefix `/ui/admin/email-queue` to avoid path collisions and is registered immediately after `admin_email_router` in `main.py`.

Default-OFF boolean settings use the `.lower() == "true"` form: see `inventory_reservations_enabled` at `app/core/settings.py:839` and `returns_rma_enabled` at line 846. ### 2.5 Background worker pattern

`app/services/audit_export_worker.py` (`run_audit_export_worker_loop:79`, `start_audit_export_worker_task:129`) is the canonical pattern for a flag-gated background `asyncio.create_task` worker. The function registers itself via `job_registry.register_task` (`app/services/job_registry.py:23`), loops with `await asyncio.sleep(poll_interval)`, and reports health with `report_poll` / `report_error` (`job_registry.py:58`). The corresponding startup hook is added to `app.add_event_handler("startup", ...)` in `app/main.py:980–981`. STU-008 mirrors this pattern exactly.

### 2.6 Suppression check

Before any message dispatch, `email_delivery.is_suppressed(addr)` (`email_delivery.py:193`) must be consulted per recipient. Any address on the suppression list must be silently skipped and the message marked `sent` only for the surviving recipients; if all recipients are suppressed the item is marked `cancelled` (reason `all_suppressed`) rather than `failed`.

### 2.7 Cursor pagination

All paginated list responses reuse `app/core/cursor.encode_cursor` / `decode_cursor` (`app/core/cursor.py`) — the same pattern as `list_deliveries` in `email_delivery.py:284–300`.

### 2.8 STU-001 dependency

The `email_queue` DynamoDB table, its handle `T.email_queue`, and the settings key `S.email_queue_table_name` are introduced by STU-001 (spec at `docs/suitecrm/specs/STU-001.md`). STU-008 must not re-declare those items; it consumes them as-is. At the time STU-001 is written the settings and table defs listed in the ticket body (`CRM_SECURITY_STUDIO_TICKETS.md:50–66, 79–81`) are treated as implemented by that ticket's acceptance criteria.

## 3. Data Model

### 3.1 `email_queue` table (from STU-001)

The table is already scaffolded by STU-001 with:

```
PK: pk  (S)  — value pattern: EMAIL#{msg_id}
SK: sk  (S)  — always "META"
GSI by-status: PK=status (S), SK=queued_at (N)
attr_types={"queued_at": "N"}   ← required; omitting causes ValidationException
```

The `local-ddb-init.py` entry (introduced by STU-001) is:

```python

    "pk",
    "sk",
    gsi=[{"index_name": "by-status", "partition_key": "status", "sort_key": "queued_at"}],
    attr_types={"queued_at": "N"},
),
```

### 3.2 Item attributes

| Attribute | Type | Description |
|---|---|---|
| `pk` | S | `EMAIL#{msg_id}` |
| `sk` | S | `"META"` (literal) |
| `msg_id` | S | `uuid4().hex` — unique message identifier |
| `to_emails` | SS (StringSet) | One or more recipient addresses |
| `subject` | S | Email subject, truncated to 120 chars on write |
| `body_text` | S | Plain-text body, truncated to 8000 chars on write |
| `body_html` | S | Optional HTML body, truncated to 32000 chars on write |
| `status` | S | One of `queued`, `sending`, `sent`, `failed`, `cancelled` |
| `queued_at` | N | Unix timestamp of initial enqueue (`now_ts()`) — GSI sort key |
| `sent_at` | N | Unix timestamp when status became `sent` (omitted until then) |
| `attempt_count` | N | Number of dispatch attempts; starts at 0, incremented on each `claiming` transition |
| `last_error` | S | Last error message, truncated to 500 chars; cleared on retry |
| `queued_by_sub` | S | `user_sub` of the actor who enqueued; `"system"` for programmatic calls |
| `ttl_epoch` | N | `queued_at + 90 * 86400` — DynamoDB TTL for automatic cleanup |

**Status transition state machine:**

```
queued → sending  (worker claims item; conditional on status=queued)
sending → sent    (SES call succeeded; worker updates)
sending → failed  (SES call raised exception; worker updates + records last_error)
failed  → queued  (admin retry; increments attempt_count, clears last_error)
queued  → cancelled (admin cancel OR all recipients suppressed)
```

The `queued → sending` transition is a conditional `update_item` with `ConditionExpression=Attr("status").eq("queued")`. This prevents double-processing if two worker threads (unlikely with `--workers 1` in dev) race.

```python
def process_queue_batch(max_items: int = 50) -> dict:
    """Query status=queued via by-status GSI (ScanIndexForward=True, FIFO),
    claim each via conditional update (queued→sending), dispatch via
    send_alert_email, update to sent or failed.

    Returns {"processed": int, "sent": int, "failed": int, "skipped_suppressed": int}.
    """
```

```python
def retry_message(actor_sub: str, msg_id: str) -> None:
    """Reset status failed→queued, clear last_error, increment attempt_count.
    Raises HTTPException(404) if msg_id not found.
    Raises HTTPException(409) if current status is not 'failed'.
    Emits audit_event("email_queue.retry", actor_sub, msg_id=msg_id).
    ROOT only (enforced in router; service does not check role).
    """
```

```python

    Raises HTTPException(404) if not found.
    Raises HTTPException(409) if current status is sent, sending, or already cancelled.
```

```python
    register_task("email_queue_worker", poll_interval, enabled=True,
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Suppression check in `process_queue_batch`

Before calling `send_alert_email` for any item, the worker calls `is_suppressed(addr)` (`email_delivery.py:193`) for each address in `to_emails`. Suppressed addresses are silently removed from the dispatch list. If the filtered list is non-empty, `send_alert_email` is called with the filtered list. If the filtered list is empty (all addresses suppressed), the item is updated to `status=cancelled`, `last_error="all_suppressed"` without ever calling `send_alert_email`.

### 5.2 Conditional `queued → sending` claim

`_claim_item` issues a `T.email_queue.update_item` with:
```
ConditionExpression=Attr("status").eq("queued"),
UpdateExpression="SET #s = :sending, attempt_count = attempt_count + :one",
ExpressionAttributeValues={":sending": "sending", ":one": 1, ":queued": "queued"}
```
If DynamoDB raises `ConditionalCheckFailedException`, `_claim_item` returns `False` and the worker silently skips the item. This prevents double-processing without requiring distributed locks.

### 5.3 `status=sending` stuck items

A worker crash between the claim and the send/update can leave items in `status=sending` indefinitely. The worker loop additionally queries `status=sending` items older than `S.email_queue_stale_sending_threshold_seconds` (default 300) and resets them to `status=queued` (incrementing `attempt_count`). This recovery scan runs at the start of each `process_queue_batch` call, before the main processing loop.

### 5.4 Retry limits

If `attempt_count >= S.email_queue_max_attempts` (default 5), the worker does not re-claim the item. Admin-triggered retries via `POST /{msg_id}/retry` bypass this check (ROOT has full override authority) but the count is still incremented so the admin can see how many times the message has been attempted.

### 5.5 `enqueue_email` when flag is off

When `S.email_queue_enabled` is False, `enqueue_email` logs `"email_queue disabled; dropping enqueue for subject=<subject>"` at WARNING level and returns a synthetic `msg_id = "noop-" + uuid4().hex`. This makes the function safe to call from future callers that always enqueue without wrapping in `if S.email_queue_enabled`. The existing `send_alert_email` direct path is unaffected — no existing caller is changed by this ticket.

### 5.6 `process_queue_batch` loop-through for `LastEvaluatedKey`

The GSI query for `status=queued` is paginated server-side by DynamoDB and the in-memory batch is bounded by `max_items`. The function uses a loop: `while len(items) < max_items and last_key` so that a single call fills the batch even if a single GSI page is smaller than `max_items`. This mirrors the pattern in `email_delivery.py:235–248`.

### 5.7 `cancel_message` guard against sent items

`cancel_message` raises `HTTPException(409, detail={"code": "already_sent", "status": current_status})` if the current status is `sent` or `sending`. Status `sending` is treated as uncancellable because the SES call may already be in-flight.

### 5.8 `body_html` size limit

HTML bodies are bounded at 32000 characters on write. SES's `send_email` supports both `Text` and `Html` body parts; the service constructs the SES `Message` dict accordingly when `body_html` is provided. The existing `send_alert_email` function only supports plain text; `process_queue_batch` must call `boto3.client("ses").send_email` directly (the same inline import pattern used in `alerts.py:472–473`) rather than delegating back to `send_alert_email` when HTML is present, because `send_alert_email` has no HTML parameter and must not be changed.

### 6.2 Master gate behaviour

The gate `S.email_queue_enabled` controls:
- Router endpoints: each handler early-exits with `HTTPException(404)` when false.
- Worker startup: `start_email_queue_worker_task` registers the task as `enabled=False` and does not call `asyncio.create_task` when false.

`S.email_queue_worker_enabled` is a sub-flag that allows the table and endpoints to be active (for manual `POST /process` and admin inspection) while the automatic background poller is disabled. Typical dev setup: `EMAIL_QUEUE_ENABLED=true`, `EMAIL_QUEUE_WORKER_ENABLED=false` to test the API without automatic processing.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

There are no `if S.dev_mode` branches in business logic. In dev mode `send_alert_email` (`alerts.py:462`) already writes to the dev log file instead of SES — the queue worker calls it the same way in both environments. The DynamoDB table is backed by DynamoDB Local (port 8001) in dev and real AWS DynamoDB in prod; the boto3 call sites are identical.

### 7.2 Idempotency of retry

`retry_message` uses a conditional `update_item` with `ConditionExpression=Attr("status").eq("failed")`. A duplicate retry call while the item is already `queued` (perhaps from a concurrent admin action) raises `ConditionalCheckFailedException`, which is caught and surfaced as `HTTPException(409, detail={"code": "not_retryable", "current_status": "queued"})`.

### 7.3 Security

- `POST /{msg_id}/retry` is ROOT-only (`Depends(require_root)`). An ADMIN caller receives `403` with `code=role_required` from `app/auth/policy.py:13–22`.
- `body_html` is never returned in list responses (`EmailQueueListOut`). Only `body_text` (truncated) is returned in the single-item response, to limit data exposure.
- `queued_by_sub` is recorded for every enqueue for audit traceability. Admin-initiated enqueues (future: via a `POST /` endpoint not in this ticket) would record the admin's `user_sub`.
- Suppression-list honoring in the worker ensures that addresses the platform has committed not to email (due to hard bounces or complaints at `email_delivery.py:122–124, 152`) are never re-emailed even if a queue item is manually retried by a ROOT admin.
- All state-changing endpoints (`retry`, `cancel`, `process`) emit `audit_event(...)` via `app/services/alerts.audit_event` (`alerts.py:644`) for the existing ENTERPRISE-004 audit trail.

## 8. Backward Compatibility & Migration

### 8.1 Existing call sites unchanged

No existing caller of `send_alert_email` is modified. The synchronous fire-and-forget path in `alerts.py:459` remains the default. Callers that want async queuing must explicitly call `enqueue_email` — this is a future opt-in, not a forced migration.

### 8.2 `email_queue` table in dev

`just restart` recreates all DynamoDB tables including `email_queue` (already present from STU-001). No manual migration is needed in dev. In prod, the table must exist before deploying the router or worker; it is created with the same `TableDef` parameters via `scripts/local-ddb-init.py` (run once against prod DynamoDB before the first deploy).

### 8.3 No schema change to existing tables

`T.email_delivery` is read-only (via `is_suppressed`) from the new service; its schema and all existing write paths are unchanged. The `email_queue` table is new and isolated. No existing index, GSI, or TTL configuration is altered.

### 8.4 Worker registration in job registry

`job_registry.register_task("email_queue_worker", ...)` is called unconditionally at startup (with `enabled=False` when the flag is off). This means the worker always appears in the admin jobs dashboard (STU-007) as disabled when the flag is off, giving operators clear visibility that the feature exists but is not active.

## 10. Open Questions / Assumptions

1. **HTML body support in `send_alert_email`**: The current `send_alert_email` (`alerts.py:477`) passes only `{"Text": {"Data": ...}}` to SES. To support `body_html`, `process_queue_batch` must call SES directly rather than routing through `send_alert_email`. This spec assumes that path is acceptable. If a future ticket refactors `send_alert_email` to accept an optional `body_html` parameter, `process_queue_batch` should be updated to delegate back to it.

2. **Bulk-enqueue endpoint**: The ticket description does not include a `POST /ui/admin/email-queue` endpoint to enqueue from the admin UI. This spec omits it. A future ticket (e.g., a CRM bulk-mailing feature) would add it. The service layer is ready to support it.

3. **Transactional enqueue + existing send**: Some callers may want to offer a "queue it if SES is down, fire it directly otherwise" pattern. That hybrid mode is out of scope for this ticket. STU-008 is a pure async queue; the synchronous path remains separate.

4. **Worker concurrency**: The spec assumes `--workers 1` (dev) and a single-process deployment (prod ECS task). Multiple worker processes would race on the `queued → sending` conditional update — the conditional update protects correctness, but throughput would be capped at one batch per process per poll. Horizontal scaling is safe but not optimized.

5. **`email_queue_table_name` in STU-001 vs STU-008**: The STU-001 ticket body lists `email_queue_table_name` as a setting it introduces. If STU-001 is implemented as written, STU-008 must not re-declare `email_queue_table_name` in `settings.py`. The worker-specific settings (`email_queue_worker_enabled`, `email_queue_worker_poll_interval_seconds`, etc.) are new to STU-008.
