# ACT-004 — Calendar event reminders / alarms (email and in-app)

**Type:** Feature  **Priority:** P1  **Estimate:** 2 days  
**Ticket source:** `docs/suitecrm/CRM_ACTIVITIES_TICKETS.md`, section "ACT-004"

---

## 1. Summary & Goal

ACT-004 delivers per-user, per-event configurable alarms that fire N minutes before an event start. Each alarm can be sent as an email (via the existing SES path), an in-app notification (via the existing `write_alert` path), or both. Users may set up to five reminders per event, each with an independent method and lead time between 1 and 10,080 minutes (one week).

The feature is entirely additive. When the flag `crm_event_reminders_enabled` is off the platform is byte-for-byte identical to its current state: the two new endpoints return 404, the background poller never starts, and the `crm_event_reminders` DynamoDB table (provisioned in ACT-001) remains empty.

The primary goal is parity with SuiteCRM's built-in alarm system: a calendar event owner or attendee can ask the platform to remind them before the event starts, choose the channel, and trust that the reminder fires exactly once even if the background poller restarts or races.

## 3. Data Model

### 3.1 DynamoDB table: `crm_event_reminders`

Provisioned by ACT-001 in `scripts/local-ddb-init.py`. Reproduced here for completeness.

```
Table name : crm_event_reminders  (S.crm_event_reminders_table_name)
PK         : reminder_key  (String) = "{calendar_id}#{event_id}#{user_sub}"
SK         : reminder_id   (String) = "REM#{uuid4().hex}"

GSI DueReminders:
  PK  : GSI1PK  (String)  = constant "DUE"   (present only when fired=False)
  SK  : GSI1SK  (Number)  = fire_at           (Unix epoch seconds)
  attr_types = {"GSI1SK": "N"}                ← required per CLAUDE.md gotcha
  Projection: ALL
```

Item attributes:

| Attribute       | Type    | Notes                                                     |
|-----------------|---------|-----------------------------------------------------------|
| `reminder_key`  | S       | PK composite `{calendar_id}#{event_id}#{user_sub}`        |
| `reminder_id`   | S       | SK, value `REM#{uuid4().hex}`                             |
| `calendar_id`   | S       | Denormalised for easy lookup                              |
| `event_id`      | S       | Denormalised for easy lookup                              |
| `user_sub`      | S       | Owner of this reminder (may be event owner or attendee)   |
| `minutes_before`| N       | Lead time 1–10 080                                        |
| `method`        | S       | `"email"` or `"in_app"`                                   |
| `fire_at`       | N       | `event_start_ts - minutes_before * 60` (Unix seconds)     |
| `fired`         | BOOL    | `False` until dispatch; `True` after                      |
| `GSI1PK`        | S       | `"DUE"` when `fired=False`; **removed** on fire (via `REMOVE GSI1PK, GSI1SK`) |
| `GSI1SK`        | N       | Same value as `fire_at`; removed alongside `GSI1PK`       |
| `event_name`    | S       | Snapshot of `event.name` at set time (avoids a second DDB read at fire time) |
| `event_start_utc`| S      | ISO-8601 UTC snapshot for email body                      |
| `created_at`    | N       | Unix seconds                                              |
| `updated_at`    | N       | Unix seconds                                              |
| `ttl`           | N       | `fire_at + 7 * 86400` (DynamoDB TTL, auto-cleanup)        |

**Key design decisions:**

- `GSI1PK` is only present when `fired=False`. Once fired, `REMOVE GSI1PK, GSI1SK` is issued so the item disappears from the `DueReminders` GSI without being deleted; the historical record (with `fired=True`) is retained until TTL.
- Snapshot attributes (`event_name`, `event_start_utc`) are written at `set_reminders` time. If the event is later updated or deleted the reminder still fires with the information the user saw when they set it.
- No per-user or per-event GSI is needed for the CRUD endpoints: `PUT /reminders` deletes all existing reminders for `reminder_key` before inserting the new set, and `GET /reminders` queries by PK (`reminder_key`) — a simple `query(KeyConditionExpression=Key("reminder_key").eq(...))` scan of the PK.

### 3.2 No changes to existing tables

`T.calendar`, `T.alerts`, `T.scheduled_actions`, and all other existing tables are untouched.

### 4.2 Service: `app/services/crm_event_reminders.py`

New file. All DynamoDB access goes through `T.crm_event_reminders`. No direct boto3 import — uses the `_FloatSafeTable` proxy inherited from `T`.

#### `set_reminders`

```python
def set_reminders(
    calendar_id: str,
    event_id: str,
    user_sub: str,
    reminders: List[EventReminderIn],
    event_start_ts: int,
    event_name: str,
    event_start_utc: str,
) -> List[dict]:
```

Algorithm:
1. Compute `reminder_key = f"{calendar_id}#{event_id}#{user_sub}"`.
2. Delete all existing reminder rows for this `reminder_key` via `query(PK) + batch_writer delete`.
3. For each `EventReminderIn` in `reminders`: compute `fire_at = event_start_ts - r.minutes_before * 60`. If `fire_at <= now_ts()` skip silently (the moment is already past).
4. Write one DDB item per surviving reminder with all attributes including `GSI1PK="DUE"` and `GSI1SK=fire_at`. Use `T.crm_event_reminders.put_item`.
5. Emit `audit_event("crm_reminder_set", user_sub, None, calendar_id=calendar_id, event_id=event_id, count=len(reminders))`.
6. Return the list of written items as dicts.

#### `get_reminders`

```python
def get_reminders(
    calendar_id: str,
    event_id: str,
    user_sub: str,
) -> List[dict]:
```

Query `T.crm_event_reminders` by `PK=reminder_key`, return all items ordered by `fire_at` ascending.

#### `list_due_reminders`

```python
def list_due_reminders(now: int, lookahead: int = 300) -> List[dict]:
```

Query `DueReminders` GSI: `GSI1PK="DUE"` AND `GSI1SK BETWEEN now AND now+lookahead`, `FilterExpression=Attr("fired").eq(False)`. Returns up to 50 items. Uses `ScanIndexForward=True` (ascending by `fire_at`).

Note: DynamoDB does not reduce page size before FilterExpression; loop via `LastEvaluatedKey` until no more pages or 200-item safety cap.

#### `mark_reminder_fired`

```python
def mark_reminder_fired(reminder_key: str, reminder_id: str) -> None:
```

Atomic conditional update:

```python
T.crm_event_reminders.update_item(
    Key={"reminder_key": reminder_key, "reminder_id": reminder_id},
    UpdateExpression="SET fired = :t REMOVE GSI1PK, GSI1SK",
    ConditionExpression="fired = :f",
    ExpressionAttributeValues={":t": True, ":f": False},
)
```

Absorbs `ConditionalCheckFailedException` (already fired — idempotent). On success emits `audit_event("crm_reminder_fired", ...)`.

#### `_resolve_event_start_ts`

```python
def _resolve_event_start_ts(calendar_id: str, event_id: str) -> Optional[int]:
```

Loads the event item from `T.calendar` using `Key={"calendar_id": calendar_id, "sk": f"event#{event_id}"}`. Parses `start_utc` to a Unix timestamp via `datetime.fromisoformat(...).timestamp()`. Returns `None` for all-day events (no `start_utc`) or missing event. Called by the router to provide `event_start_ts` to `set_reminders`.

### 4.3 Background poller: `run_event_reminder_loop` and `start_event_reminder_task`

Both live in `app/services/crm_event_reminders.py`.

```python
async def run_event_reminder_loop() -> None:
    poll_interval = S.crm_event_reminders_poll_interval_seconds  # default 60
    while True:
        try:
            await _fire_due_reminders()
        except Exception:
            logger.exception("crm_event_reminder loop error")
        await asyncio.sleep(poll_interval)

async def _fire_due_reminders() -> None:
    now = now_ts()
    due = list_due_reminders(now=now, lookahead=0)  # only strictly due items
    for item in due:
        try:
            _dispatch_reminder(item)
            mark_reminder_fired(item["reminder_key"], item["reminder_id"])
        except Exception:
            logger.exception("Failed to dispatch reminder %s", item.get("reminder_id"))

def _dispatch_reminder(item: dict) -> None:
    user_sub   = item["user_sub"]
    event_name = item.get("event_name", "")
    event_start_utc = item.get("event_start_utc", "")
    minutes    = int(item.get("minutes_before", 0))
    method     = item.get("method", "in_app")
    title      = f"Reminder: {event_name}"
    body       = (
        f"Your event '{event_name}' starts in {minutes} minute(s)"
        + (f" at {event_start_utc} UTC" if event_start_utc else "")
        + "."
    )
    if method == "in_app":
        write_alert(
            user_sub,
            event="calendar_event_reminder",
            outcome="reminder",
            title=title,
            details={
                "calendar_id": item["calendar_id"],
                "event_id":    item["event_id"],
                "minutes_before": minutes,
            },
            action_url=f"/calendar",
            source_type="calendar_event",
            source_id=item["event_id"],
        )
    else:  # email
        identity = get_profile_identity(user_sub)
        email_addr = identity.get("email")
        if email_addr:
            send_alert_email([email_addr], subject=title, body_text=body)

async def start_event_reminder_task() -> None:
    if S.crm_activities_enabled and S.crm_event_reminders_enabled:
        asyncio.create_task(run_event_reminder_loop())
```

## 5. Detailed Behavior & Edge Cases

### 5.1 `PUT /reminders` is a full replace

`set_reminders` deletes all existing reminder rows for the `(calendar_id, event_id, user_sub)` triplet before inserting the new set. Sending `{"reminders": []}` therefore clears all reminders without inserting new ones. This is intentional and gives the frontend a single idempotent call for any manage-reminders interaction.

### 5.2 Past `fire_at` is silently skipped

If `minutes_before` is so large that `fire_at = event_start_ts - minutes_before*60 <= now_ts()`, that reminder is not written. The API response reflects only the reminders actually persisted. No error is returned for skipped reminders (analogous to how SuiteCRM silently ignores past alarm times).

### 5.3 All-day events

Events with `all_day=True` have no `start_utc` field (`EventCreateIn.start_utc` is `None`, stored verbatim). `_resolve_event_start_ts` returns `None` for these. The `PUT /reminders` endpoint raises 422 to signal that time-based reminders cannot be set on all-day events.

### 5.4 Recurrence

The calendar stores recurring events as a single series item. The `start_utc` on the series item is the first occurrence's start. ACT-004 fires the reminder once, relative to that first-occurrence start. Full per-occurrence reminders (one alarm per recurrence instance) are out of scope for this ticket; they can be addressed in a follow-up by integrating with `_expand_rrule` (line 548 of `calendar.py`).

### 5.5 No double-fire guarantee

`mark_reminder_fired` uses a conditional update (`ConditionExpression="fired = :f"`) that absorbs `ConditionalCheckFailedException`. If two poller instances race (e.g., during a rolling deploy), the second `mark_reminder_fired` call is a no-op and the notification is not sent twice because `_dispatch_reminder` is called before `mark_reminder_fired`. If both instances call `_dispatch_reminder` before either writes `fired=True`, a double notification is theoretically possible. This is acceptable for an alarm system (same trade-off as SuiteCRM). Future hardening could use `claim` (compare-and-swap to `"firing"` state) before dispatch.

### 5.6 Event updated or deleted after reminders are set

If the event is deleted, existing reminder items remain in `crm_event_reminders` until their TTL expires (7 days after `fire_at`). The background poller will call `_dispatch_reminder` with the snapshotted `event_name` and `event_start_utc` without re-fetching the event. The notification will fire even though the event no longer exists.

Mitigation (optional, may be deferred): `delete_event` in `app/routers/calendar.py` (def at line 1851; `T.calendar.delete_item` call at line 1858) can call `clear_reminders_for_event(calendar_id, event_id)` — a service helper that scans all reminder rows for the event PK prefix and marks them fired. This is recommended but may ship in a follow-up ticket.

If the event `start_utc` changes, the existing reminders are not automatically re-calculated. The user must call `PUT /reminders` again to reset them. This is consistent with SuiteCRM behavior where you must explicitly re-save the alarm after editing the event time.

### 5.7 Attendee authorization

An event attendee listed in `event["attendees"]` (the existing flat `List[str]` at `app/models.py:1284`) may set their own reminders. The ACT-002 RSVP table is not consulted — `attendees` is the source of truth for authorization at this ticket's boundary.

### 5.8 User with no email

When `method="email"` and `get_profile_identity` returns `email=None`, the reminder dispatch is silently skipped. No retry or error is recorded. If the user later adds an email to their profile, already-fired reminders will not re-fire.

### 5.9 Rate of poller wakeups

The poller sleeps for `S.crm_event_reminders_poll_interval_seconds` (default 60 s) between cycles. A reminder may fire up to 59 seconds late. This is acceptable for a calendar alarm system. The default can be reduced via env var if tighter precision is needed.

### 5.10 ALERT_CATEGORIES registration

`ALERT_CATEGORIES` is defined at `alerts.py:32`. The new event `calendar_event_reminder` must be added to the `"updates"` category alongside `calendar_event_created` and `calendar_event_updated` (currently at line 40, not 41):

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

There is no `if S.dev_mode:` branch anywhere in the reminder service. All DDB reads and writes use `T.crm_event_reminders`, which resolves to DynamoDB Local in dev and real DynamoDB in prod — the code path is identical. Email dispatch calls `send_alert_email`, which already contains the `S.dev_mode` branch (writing to `S.dev_email_log`) so the reminder service never inspects `dev_mode` directly. In-app alerts use `write_alert` which is already unconditional.

### 7.2 Idempotency

- `PUT /reminders`: Full delete-then-replace semantics mean repeated identical calls produce identical final state.
- `mark_reminder_fired`: Conditional update absorbs double-fire attempts.
- `start_event_reminder_task`: The `asyncio.create_task` is called once at startup; the background loop does not create additional tasks.

### 7.3 Input validation

- `minutes_before`: `Field(ge=1, le=10080)` enforced by Pydantic at deserialization. Values outside this range return 422 before any service code runs.
- Max 5 reminders: `Field(max_length=5)` on `EventRemindersSetIn.reminders`. Exceeding this returns 422.
- `calendar_id`, `event_id`, `user_sub`: URL path parameters; FastAPI validates they are non-empty strings. No additional sanitization needed since these are used only as DynamoDB key components, never in SQL or shell contexts.

### 7.4 Authorization boundary

- The `PUT` and `GET` endpoints verify the caller is the event owner (calendar's `owner_user_sub`) or an event attendee. Non-attendees receive 403. This is checked using the existing `_load_calendar_access` and `event["attendees"]` patterns from `calendar.py`.
- A user can only read and write their own reminders (keyed by `user_sub`). No admin override endpoint is exposed at this ticket's boundary.
- Bearer-auth requests skip CSRF as per `require_ui_session` in `app/auth/deps.py`.

### 7.5 Data exposure

- Reminder items contain `event_name` and `event_start_utc` snapshots. These are event-level fields, not personal data beyond what the user already has access to (they must be the owner or an attendee to set reminders at all).
- `get_profile_identity` is called only inside the background poller, never in API response payloads.

## 8. Backward Compatibility & Migration

### 8.1 Zero migration required

With both flags defaulting to `false`, no existing endpoint, table, or background task is touched. The `crm_event_reminders` DynamoDB table is created by ACT-001's `scripts/local-ddb-init.py` addition, and `just restart` creates it empty. No backfill is needed.

### 8.2 `EventOut` is unchanged

No new field is added to `EventOut` (`app/models.py:1274`). Reminders are a separate resource addressed by the new endpoints. Existing clients that parse `EventOut` see no change.

### 8.3 Enabling the flag

When an operator sets `CRM_ACTIVITIES_ENABLED=true` and `CRM_EVENT_REMINDERS_ENABLED=true` on a running deployment:
1. The background poller starts on the next uvicorn restart.
2. No existing data is disturbed.
3. The `crm_event_reminders` table must exist (created by ACT-001's init script) before the poller starts.

### 8.4 Disabling after use

Setting the flags back to `false` stops the poller loop and returns 404 for all reminder endpoints. Existing reminder rows in DynamoDB remain until their TTL expires; no rows are deleted by the flag-off transition. The `T.crm_event_reminders` table handle remains in `tables.py` regardless of flag state.

## 10. Open Questions / Assumptions

1. **Recurrence per-instance alarms**: ACT-004 fires a reminder once relative to the series `start_utc`. Full per-occurrence alarms require iterating `_expand_rrule` output. Assumed out of scope; deferred to a follow-up ticket.

2. **Event delete cascade**: When an event is deleted, should its reminder rows be proactively cleared? Currently they fire with snapshotted data. The spec recommends calling `clear_reminders_for_event` from `delete_event`, but this is flagged as optional for this ticket to avoid scope creep.

3. **`_load_calendar_access` write flag**: The `PUT /reminders` endpoint calls `_load_calendar_access(calendar_id, ctx["user_sub"], write=False)` because setting reminders does not mutate the event. An attendee (not just the owner) should be allowed to set reminders; the existing helper raises 403 for non-owners when `write=True`. Using `write=False` + a separate attendee check is the correct approach.

4. **Timezone in email body**: `event_start_utc` is stored as ISO-8601 UTC in the snapshot. The email body shows UTC. A future improvement could resolve the calendar's `timezone` field and convert the display time to local time.

5. **Max concurrency of poller**: The poller runs as a single `asyncio.create_task` per uvicorn worker. With `--workers 1` in dev (as documented in CLAUDE.md), there is only one instance. In a multi-worker production deployment, multiple instances would race on the same `DueReminders` GSI items. The `mark_reminder_fired` conditional update prevents double-fire in the normal case, but does not prevent double dispatch when two instances both complete `_dispatch_reminder` before either writes `fired=True`. Assumed acceptable for v1.

6. **Snooze / re-arm**: SuiteCRM supports snoozing alarms. This ticket does not implement snooze. Snoozed re-arming would require writing a new reminder row with an updated `fire_at`. Deferred.
