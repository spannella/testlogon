## 1. Summary & Goal

OPP-006 adds a pipeline funnel report endpoint and a sales dashboard frontend page. The report endpoint aggregates opportunities owned by the caller (or all users for admins) into per-stage metrics — count, total amount, and probability-weighted amount — enabling a sales rep or sales manager to understand deal flow, pipeline health, and conversion shape at a glance. The frontend dashboard renders this data as a horizontal bar chart (via `recharts`, already a declared dependency) and surfaces the rep's forecast worksheet from OPP-005 as a quota-attainment progress bar.

Neither the backend nor the frontend changes any existing surface. The feature is additive and flag-gated: with `SALES_PIPELINE_ENABLED=false` (the default), all new endpoints return HTTP 503, the sidebar entry is absent, and the routes `/sales/dashboard` and `/sales/reports/pipeline` do not render. No data is written to DynamoDB by the report path; it is read-only.

## 2. Context & Current State

### 2.1 Existing opportunity data (OPP-001 through OPP-005)

The `sales_opportunities` DynamoDB table is introduced in OPP-001 (`docs/suitecrm/specs/OPP-001.md`). Its `TableDef` in `scripts/local-ddb-init.py` declares three GSIs:

## 3. Data Model

OPP-006 is a **read-only** feature with respect to DynamoDB. No new tables, GSIs, or item types are introduced. All queries are against tables and GSIs created in OPP-001.

### 3.1 Read paths used by `pipeline_report`

**Per-rep report (`GET /ui/sales/reports/pipeline`):**

Query `GSI_BY_USER_CLOSE` on `T.sales_opportunities`:
- `KeyConditionExpression = Key("owner_sub").eq(owner_sub)`
- Optional date filter: `Key("owner_sub").eq(owner_sub) & Key("close_date").between(close_date_from, close_date_to)`
- `FilterExpression = Attr("sk").begins_with("OPP#")` to exclude non-opportunity rows (e.g., `STAGE_CONFIG`, `FORECAST#`) that share the partition. This filter is applied in Python, not DDB, since `FilterExpression` does not reduce the page-count limit (CLAUDE.md gotcha: "DynamoDB fetches up to 1MB *before* applying FilterExpression — loop via LastEvaluatedKey").
- Pagination loop: continue until `LastEvaluatedKey` is absent.

**Admin cross-user report (`GET /ui/admin/sales/reports/pipeline`):**

Scan `GSI_BY_STAGE` on `T.sales_opportunities`:
- For each stage in the stage config list, query `Key("stage").eq(stage_key)` with optional `close_date` range. Iterate all pages via `LastEvaluatedKey` per stage.
- Aggregate in Python. DDB returns all items for a given `stage` value from this GSI; no user ownership filter is needed on the admin path (the report is explicitly cross-user).

**Stage config read:**

`T.sales_opportunities.get_item(Key={"pk": "STAGE_CONFIG", "sk": "META"})`. If absent, fall back to `OPPORTUNITY_STAGES` tuple. The list is ordered by `order` field ascending. This read adds at most one `GetItem` call per report invocation.

### 3.2 Existing `T.sales_opportunities` schema (owned by OPP-001)

## 4. API / Service Design

### 4.1 New Pydantic models (`app/models.py`)

Append after the existing `ForecastWorksheetOut` model introduced by OPP-005:

```python
from typing import TypedDict  # already imported

class PipelineStageMetric(TypedDict):
    stage: str
    label: str
    count: int
    total_amount_cents: int
    weighted_amount_cents: int
    avg_close_date: Optional[int]   # arithmetic mean of close_date values; None when count=0

class PipelineReportOut(BaseModel):
    stages: List[PipelineStageMetric]
    total_amount_cents: int          # sum of total_amount_cents across all non-terminal stages
    total_weighted_cents: int        # sum of weighted_amount_cents across all non-terminal stages
    generated_at: int                # now_ts() at the time the query ran
```

`PipelineStageMetric` is a `TypedDict` (not `BaseModel`) so it serializes transparently via FastAPI's JSON encoder when embedded in the `stages` list of `PipelineReportOut`. Terminal stages (`is_won=True` or `is_lost=True`) are included in the per-stage list but excluded from the `total_amount_cents` / `total_weighted_cents` rollup totals (those fields represent active pipeline only).

### 4.2 Service functions (`app/services/opportunities.py`)

Append to the existing module after the OPP-005 functions:

```python
def _load_stage_config() -> List[Dict[str, Any]]:
    """Return ordered stage config list; falls back to OPPORTUNITY_STAGES tuple."""
    row = T.sales_opportunities.get_item(
        Key={"pk": "STAGE_CONFIG", "sk": "META"}
    ).get("Item")
    if row and isinstance(row.get("stages"), list):
        return sorted(row["stages"], key=lambda s: s.get("order", 0))
    return [
        {
            "stage_key": s, "label": s.replace("_", " ").title(),
            "order": i, "is_won": s == "closed_won", "is_lost": s == "closed_lost",
        }
        for i, s in enumerate(OPPORTUNITY_STAGES)
    ]


def pipeline_report(
    owner_sub: str,
    close_date_from: Optional[int] = None,
    close_date_to: Optional[int] = None,
) -> PipelineReportOut:
    """Per-rep funnel report. Returns one PipelineStageMetric per configured stage."""
    ...


def pipeline_report_all(
    close_date_from: Optional[int] = None,
    close_date_to: Optional[int] = None,
) -> PipelineReportOut:
    """Admin cross-user funnel report. Aggregates across all reps via GSI_BY_STAGE."""
    ...
```

**`pipeline_report` implementation contract:**

1. Call `_load_stage_config()` to get the ordered stage list.
2. Build the key condition: if both date bounds are provided, use `Key("owner_sub").eq(owner_sub) & Key("close_date").between(close_date_from, close_date_to)`; if only `from` is provided, use `gte`; if only `to`, use `lte`; otherwise omit the sort-key condition.
3. Paginate via `LastEvaluatedKey` accumulating all items from `GSI_BY_USER_CLOSE`.
4. Filter items in Python: `sk.startswith("OPP#")` (drops FORECAST rows and STAGE_CONFIG) and item not soft-deleted (`deleted_at` absent).
5. Group by `item["stage"]`, accumulate `count`, `sum(amount_cents)`, `sum(weighted_amount_cents)`, and `sum(close_date)` for the average.
6. Build a `PipelineStageMetric` for every stage in the stage config list, even if no items exist for that stage (count=0, amounts=0, avg_close_date=None).
7. Compute `total_amount_cents` and `total_weighted_cents` as sums over stages where `is_won=False` and `is_lost=False`.
8. Return `PipelineReportOut(stages=..., total_amount_cents=..., total_weighted_cents=..., generated_at=now_ts())`.

**`pipeline_report_all` implementation contract:**

1. Call `_load_stage_config()`.
2. For each stage in the config, query `GSI_BY_STAGE` with `Key("stage").eq(stage_key)` plus optional `close_date` range on the sort key, paginating all pages.
3. Filter soft-deleted items in Python. Accumulate the same counters.
4. Produce the same `PipelineReportOut` shape. Emit `audit_event("sales_pipeline_report.admin_accessed", admin_sub, None, {"close_date_from": ..., "close_date_to": ...})`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Zero-count stage inclusion

Every configured stage must appear in the `stages` list regardless of whether any opportunities exist for that stage. This is the key invariant that allows the funnel chart to render every column. The implementation builds a result dict keyed by `stage_key` initialized to zero counts before processing DDB results, then maps the stage config list over it.

### 5.2 Date range filter behavior

`close_date_from` and `close_date_to` are inclusive Unix timestamps (integer seconds). The DynamoDB `between` expression is inclusive on both ends. When only one bound is supplied, use `gte` or `lte` on `GSI_BY_USER_CLOSE` / `GSI_BY_STAGE`. When neither is supplied, the sort-key condition is omitted and the query retrieves all opportunities for the owner (or all reps, for the admin variant). Callers should pass sensible fiscal-quarter or fiscal-year bounds to avoid full-partition scans.

### 5.3 Soft-deleted opportunities

OPP-002's `delete_opportunity` sets a `deleted_at` timestamp on the item rather than calling `delete_item`. The report function must filter out items where `deleted_at` is present and non-None. This filter is applied in Python after DDB retrieval, not via `FilterExpression`, to keep the DDB query expression simple.

### 5.4 Admin report audit emission

`pipeline_report_all` writes one `audit_event("sales_pipeline_report.admin_accessed", ...)` per invocation. This is the only audit event OPP-006 emits; the per-rep endpoint is not audited (it reads only the caller's own data, matching the pattern where `list_opportunities` in OPP-002 is also not audited).

### 5.5 Large pipelines and the FilterExpression page-size gotcha

CLAUDE.md states: "DynamoDB fetches up to 1MB *before* applying FilterExpression. Any query that filters a sparse attribute must loop via LastEvaluatedKey — a single query() call silently misses items beyond the first page." The `pipeline_report` queries do not rely on `FilterExpression` for the main data-selection logic (date bounds use a sort-key `KeyConditionExpression` which is applied before the 1MB limit); the Python-side filter for `sk.startswith("OPP#")` and `deleted_at` is applied after all pages are accumulated. The pagination loop must always continue until `LastEvaluatedKey` is absent.

### 5.6 `avg_close_date` for zero-count stages

When `count = 0` for a stage, `avg_close_date` is `None`. When `count >= 1`, `avg_close_date = sum_close_date // count` (integer division, producing an integer Unix timestamp). This is always an integer or `None`; the `TypedDict` declares `Optional[int]`.

### 5.7 `total_amount_cents` rollup semantics

`total_amount_cents` and `total_weighted_cents` sum over stages where `is_won=False AND is_lost=False`. This matches SuiteCRM's convention: "active pipeline" excludes closed deals. Won and lost deals are still shown in the per-stage metrics, allowing the frontend to optionally render them separately (e.g., a separate "Closed Won" stat card).

### 5.8 Feature-status endpoint when flag is off

`GET /ui/sales/feature-status` returns HTTP 200 with `{"enabled": false}` even when the flag is off. It must not call `_require_flag()`. This asymmetry is intentional: the sidebar needs to know the flag state to decide whether to render the "Sales" link; if the endpoint returned 503, the sidebar would have no way to distinguish "flag off" from "server error."

### 5.9 Admin `GSI_BY_STAGE` scan and stage completeness

The admin report queries each stage separately via `GSI_BY_STAGE`. Unknown stage values in DDB items (e.g., from a stale item written before a stage rename) are collected under an `"unknown"` bucket in Python and omitted from the ordered stage list in the response. A future cleanup task can normalize these items, but the report must never fail due to stale stage values.

### 5.10 Concurrency and consistency

The report functions are read-only. DynamoDB eventual consistency is acceptable for a funnel report. No locking or transaction is needed. Multiple concurrent calls may produce slightly different results if an opportunity is being written simultaneously; this is acceptable for a dashboard use case.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

There are no `if S.dev_mode` branches in any OPP-006 code path. The `pipeline_report` and `pipeline_report_all` functions use the same DDB queries in both environments. The `_load_stage_config()` helper reads from `T.sales_opportunities` in both environments. The `GET /ui/sales/feature-status` endpoint reads from `S.sales_pipeline_enabled` in both environments. Moto (used in dev via in-process interception at the botocore layer) handles the DDB queries identically to real DynamoDB.

### 7.2 Idempotency

All report endpoints are GET requests. They are idempotent by definition — same inputs produce the same output for a given DDB state. No state mutation occurs. Re-requests are safe.

### 7.3 Auth and authorization

- **Per-rep endpoint** (`GET /ui/sales/reports/pipeline`): `Depends(require_ui_session)`. The `owner_sub` used in the DDB query is taken exclusively from the session context (`session["user_sub"]`), never from a query parameter. A user cannot request another user's pipeline by passing a different `user_sub` — the query parameter does not exist.
- **Admin endpoint** (`GET /ui/admin/sales/reports/pipeline`): `Depends(require_admin_or_root)` from `app/auth/policy.py:67`. Users with `role=USER` receive HTTP 403. The admin report aggregates across all reps; no per-user filter is applied.
- **Feature status endpoint** (`GET /ui/sales/feature-status`): `Depends(require_ui_session)`. Returns no sensitive data (only a boolean).

### 7.4 No money movement

OPP-006 is read-only. It performs no billing ledger writes, no wallet debits, no Stripe/PayPal/CCBill calls, and no refund operations. The "never fork existing modules — any money-out reuses refund_payment / settle_or_reverse_ledger" constraint applies only to write paths; it is not relevant here.

### 7.5 CSRF

GET endpoints do not require CSRF tokens (the CLAUDE.md auth section states "Cookie-auth non-GET requests require `x-csrf-token` header"). All three OPP-006 endpoints are GET requests; no CSRF header is needed.

## 10. Open Questions / Assumptions

1. **OPP-005 shipped first:** OPP-006 depends on the `FORECAST#{period_key}` row type and the `GET /ui/sales/forecast/{period_key}` endpoint introduced by OPP-005. If OPP-005 is merged after OPP-006, the forecast summary section of the dashboard should degrade gracefully (handle 404 from the forecast endpoint with a "No forecast data" placeholder).

2. **Current period key derivation:** The dashboard page must determine the "current period" to pass to `GET /ui/sales/forecast/{period_key}`. The assumed convention from OPP-005 is ISO-8601 month (`2026-06`) or quarter (`2026-Q2`). The dashboard should compute the current quarter from `new Date()` in the browser and default to the quarterly view. This logic is self-contained in `SalesDashboard.tsx` and does not require a backend change.

3. **Stage label localization:** The `label` field in `PipelineStageMetric` is the raw label from the stage config (or the title-cased `stage_key` fallback). No i18n is applied server-side; localization is deferred to a future ticket if needed.

4. **Report caching:** The report endpoint has no server-side cache. For large pipelines the DDB scan could be slow. A TTL-keyed cache in `T.sales_opportunities` (similar to `T.message_ai_cache`) is a follow-up optimization if response latency becomes a concern in production; it is out of scope for OPP-006.

5. **Decimal serialization:** DynamoDB returns numeric attributes as `Decimal`. The `pipeline_report` service accumulates sums using Python `int()` coercion (`int(item.get("amount_cents", 0))`). The `_json_default` in `app/core/cursor.py:13–18` handles `Decimal` in cursor payloads; FastAPI's Pydantic serialization handles `Decimal` in response models automatically. No explicit `Decimal` coercion is needed in the report aggregation loop beyond `int()` casts.

6. **`isSalesPipelineEnabled` as Vite build-time flag:** The assumption is that operators who want runtime (not build-time) feature gating can use the `GET /ui/sales/feature-status` endpoint and a `useQuery` hook in the sidebar. The Vite env var approach is simpler and matches all other feature flags in the codebase; the runtime API is an opt-in alternative.
