## 1. Summary & Goal

CAS-001 is pure infrastructure scaffolding. It delivers:

- One master feature flag (`crm_cases_enabled`) plus five sub-flags, all defaulting `False`.
- Nine new settings keys for DynamoDB table names, S3 bucket/prefix, and a counter table.
- Six new DynamoDB table definitions with full GSI schemas and correct `attr_types` declarations for every numeric GSI sort key.
- Six new `T.*` table handles wired into `app/core/tables.py`.

No router, no service logic, no background worker, and no UI change is introduced. Every downstream CAS ticket (CAS-002 through CAS-017) depends on this ticket and this ticket alone. When `CRM_CASES_ENABLED=0` (the default), the platform is byte-for-byte identical to today: no new routes exist, no background workers start, and no existing table, service, or endpoint is touched.

### 2.1 Existing feature-flag boolean pattern

`app/core/settings.py` is a frozen `@dataclass` (`Settings`) populated entirely from environment variables at import time. Two canonical default-OFF patterns exist in the file:

**Pattern A** — `not in ("0", "false", "False")` — used when the default env var is `"0"`, which IS in the exclusion set, so the effective default is `False`. The ticket source (`CRM_CASES_PORTAL_TICKETS.md`, line 40) provides the exact expression for the master flag using Pattern A (`not in ("0", "false", "False")`). The implementation below uses Pattern B throughout for consistency with the nearest peers — both patterns are equivalent when default-OFF is required.

## 3. Data Model

CAS-001 provisions six new DynamoDB tables. All follow the single-table `TableDef` pattern from `scripts/local-ddb-init.py`. Every numeric GSI sort key must include `attr_types={"<key>": "N"}`.

### 3.1 `crm_cases_counters`

Stores atomic sequence counters for human-readable case numbers. Used by CAS-002 (`_next_case_number()`).

| Attribute | Value |
|---|---|
| Partition key | `counter_id` (S) — e.g. `"TICKETS"` |
| Sort key | `scope` (S) — e.g. `"GLOBAL"` |

No GSIs. The counter is incremented via `ADD #n :one` with `ReturnValues="UPDATED_NEW"` (same atomic pattern used by any DDB-backed auto-increment). No numeric sort key, so no `attr_types` override needed.

**TableDef:**
```python
TableDef(
    _resolve_table_name(S.crm_cases_counter_table, "crm_cases_counters"),
    "counter_id",
    "scope",
)
```

### 3.2 `crm_cases_links`

Stores directed links between tickets (duplicate, blocks, relates_to). Used by CAS-011 (case linking / duplicate detection).

| Attribute | Value |
|---|---|
| Partition key | `ticket_id` (S) |
| Sort key | `sk` (S) — value: `LINK#{related_ticket_id}` |

**GSI `ByRelated`** — reverse lookup: given a ticket ID, find all tickets that link TO it:

| GSI Attr | Value | Type |
|---|---|---|
| `related_ticket_id` | bare related ticket ID | S |
| `created_at` | Unix epoch seconds | N |

`attr_types={"created_at": "N"}` required.

Item attributes (informational, constrained by CAS-011): `ticket_id`, `related_ticket_id`, `link_type` (`duplicate | blocks | relates_to`), `created_by_sub`, `created_at`.

**TableDef:**
```python
TableDef(
    _resolve_table_name(S.crm_cases_links_table, "crm_cases_links"),
    "ticket_id",
    "sk",
    gsi=[
        {"index_name": "ByRelated", "partition_key": "related_ticket_id", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
)
```

### 3.3 `crm_cases_templates`

Stores canned-response / reply templates for agents. Used by CAS-012.

| Attribute | Value |
|---|---|
| Partition key | `template_id` (S) |
| Sort key | `sk` (S) — constant value `"META"` |

**GSI `ByOwner`** — lists all templates owned by a given admin/agent, ordered by creation time (newest first via descending query):

| GSI Attr | Value | Type |
|---|---|---|
| `owner_sub` | owning admin `user_sub` | S |
| `created_at` | Unix epoch seconds | N |

`attr_types={"created_at": "N"}` required.

Item attributes: `template_id`, `owner_sub`, `title`, `body`, `category`, `is_shared` (bool), `created_at`, `updated_at`.

**TableDef:**
```python
TableDef(
    _resolve_table_name(S.crm_cases_templates_table, "crm_cases_templates"),
    "template_id",
    "sk",
    gsi=[
        {"index_name": "ByOwner", "partition_key": "owner_sub", "sort_key": "created_at"},

```

### 3.5 `crm_cases_sla_config`

Stores per-priority SLA configuration (target response hours, warning threshold, escalation threshold). Used by CAS-008. Analogous to the KYC SLA config pattern from `app/services/kyc_case_assignment.py` (`_DEFAULT_SLA` at lines 50–54, `_sla_sk()` at line 68), but in a dedicated table (the KYC version stores config rows in `T.kyc_cases` — this table is purpose-built for CRM SLA config).

| Attribute | Value |
|---|---|
| Partition key | `config_key` (S) — constant value `"CONFIG"` |
| Sort key | `sk` (S) — value: `SLA#{priority}` where priority is one of `urgent | high | medium | low` |

No GSIs. All four priority tiers are read in a single `query(KeyConditionExpression="config_key = :ck")` call. No numeric keys, so no `attr_types` override needed.

Default values seeded lazily on first read by CAS-008:

| Priority | target_response_hours | warning_pct | escalation_pct |
|---|---|---|---|
| urgent | 4 | 75 | 100 |
| high | 8 | 75 | 100 |
| medium | 24 | 75 | 100 |
| low | 72 | 80 | 100 |

Item attributes: `config_key`, `sk`, `priority`, `target_response_hours`, `warning_pct`, `escalation_pct`, `updated_by_sub`, `updated_at`.

**TableDef:**
```python
TableDef(
    _resolve_table_name(S.crm_cases_sla_config_table, "crm_cases_sla_config"),
    "config_key",
    "sk",
)
```

### 3.6 `crm_kb_articles`

Stores Knowledge Base articles (title, body, category, status, SEO slug). Used by CAS-015 (KB management) and case-deflection suggestions.

| Attribute | Value |
|---|---|
| Partition key | `pk` (S) — value: `ARTICLE#{article_id}` |
| Sort key | `sk` (S) — constant value `"META"` |

**GSI `ByCategory`** — lists published articles within a category, ordered by publish time (newest first via descending query). Used for browsing:

| GSI Attr | Value | Type |
|---|---|---|
| `category` | category slug string | S |
| `published_at` | Unix epoch seconds | N |

**GSI `ByStatus`** — lists all articles of a given status (`draft | published | archived`), ordered by publish time. Used by admin article management queue:

| GSI Attr | Value | Type |
|---|---|---|
| `status` | `draft | published | archived` | S |
| `published_at` | Unix epoch seconds | N |

Both GSIs share the same numeric sort key `published_at`; a single `attr_types={"published_at": "N"}` covers both.

## 5. Detailed Behavior & Edge Cases

Because CAS-001 introduces no runtime logic, this section documents the behavioral invariants that downstream tickets must preserve, derived from the scaffolding design:

### 5.1 Flag evaluation order

Every downstream router guard and service guard must check the master flag first:

```python
if not S.crm_cases_enabled:
    raise HTTPException(status_code=404, detail="Not found")
```

Sub-flags are checked second, e.g.:

```python
if not S.crm_cases_enabled or not S.crm_cases_sla_enabled:
    raise HTTPException(status_code=404, detail="Not found")
```

This two-level guard means an operator can disable all CRM Cases functionality with a single env change (`CRM_CASES_ENABLED=false`) without touching sub-flags. Sub-flags are independently useful for staged rollout.

### 5.2 Tables resolve at import time

Because `T` is constructed at module import time, all six new `_safe_table(...)` calls run on every backend startup regardless of the flag. This is consistent with every other table in `tables.py` (e.g. `T.kyc_cases` resolves even when `SIGNATURE_PDF_ENABLED=0`). The tables must therefore exist in DynamoDB before the backend starts. `scripts/local-ddb-init.py` creates them unconditionally at stack start via `just restart`. In production, the tables must be provisioned via infrastructure-as-code before the new binary is deployed (see Section 8).

### 5.3 Counter atomicity for case numbers

The `crm_cases_counters` table uses `ADD` on a numeric attribute (`#n`) with a DynamoDB `update_item` call — this is the standard atomic counter pattern. There is no `ConditionalExpression`; `ADD` is intrinsically atomic (compare-and-swap is not needed for a monotonic increment). The counter item does not need to be pre-seeded; DynamoDB implicitly starts from 0 on the first `ADD`. CAS-002 will rely on this behavior.

### 5.4 Portal session TTL

`crm_cases_portal_sessions` items carry `expires_at` (set to `now_ts() + S.crm_cases_portal_session_ttl_seconds` — that setting is introduced in CAS-014). CAS-014 will call `_enable_ttl_if_needed(ddb, S.crm_cases_portal_sessions_table)` in `main()`. Items are not deleted programmatically; DynamoDB TTL handles expiry. The `ByEmail` GSI enables rate limiting by scanning recent sessions for a submitter email; expired items may still appear briefly (DynamoDB TTL is eventually consistent), so CAS-014 must filter by `expires_at > now_ts()` in the rate-limit query. NOTE: per the ticket source, CAS-007 is "Ticket watchers / CC list"; the self-service portal is CAS-014.

### 5.5 KB article `published_at` for draft articles

KB articles in `draft` status must not be returned by the `ByCategory` GSI query for public browsing. CAS-015 will set `published_at = 0` on draft articles (so they sort to the bottom) or omit the attribute entirely and rely on a `FilterExpression` on `status`. Both approaches work; the recommendation is to use `published_at = 0` for drafts so the GSI index is always populated, avoiding the DDB FilterExpression-before-page-size trap (CLAUDE.md: "DDB FilterExpression doesn't reduce page size"). NOTE: KB is CAS-015 per the ticket source, not CAS-013.

### 5.6 Link directionality and bidirectional queries

The `crm_cases_links` table stores a directed row: `ticket_id → LINK#{related_ticket_id}`. The `ByRelated` GSI inverts the lookup direction. For display purposes (CAS-011), both directions must be queried: the main table for links originating from a ticket, and the GSI for links pointing to a ticket. The `link_type` (duplicate, blocks, relates_to) is recorded only once on the originator row; the reverse GSI query returns the same `link_type` from the same item via projection.

### 5.7 SLA config key collision safety

The `crm_cases_sla_config` table uses `PK=config_key="CONFIG"` and `SK=SLA#{priority}`. This mirrors the KYC assignment SLA table which uses `PK=CONFIG` and `SK=SLA#{tier}` in `kyc_case_assignment.py` (line 68). Because these are separate physical DynamoDB tables (different `table_name` settings), there is no key collision. If a future operator reuses the same table name by misconfiguring both `CRM_CASES_SLA_CONFIG_TABLE` and a hypothetical KYC SLA table env var to the same value, the items are distinguished only by value semantics, not by key; this is flagged as an assumption (Section 10.1).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

CAS-001 introduces no code paths with conditional dev/prod behavior. All six tables are created unconditionally by `scripts/local-ddb-init.py` in both environments. The `_safe_table` proxy wraps all handles identically in dev and prod. There are no `if S.dev_mode:` branches in this ticket.

For downstream tickets (CAS-002 through CAS-017), the same constraint applies: no `dev_mode` branch in service logic. Email delivery (`send_alert_email`) already handles dev/prod parity internally — in dev mode it logs to `S.dev_email_log`; in prod it uses SES. S3 upload (`app.core.aws_clients.s3_client`) uses the in-process moto interceptor in dev and real S3 in prod. Downstream CAS tickets must reuse these primitives exactly, not fork them.

### 7.2 Idempotency of `local-ddb-init.py`

`local-ddb-init.py` already handles the case where a table already exists: `_ensure_table` (line 2534) wraps `create_table` in a `try/except` that ignores `ResourceInUseException`. The six new tables follow the same pattern automatically. Running `just restart` twice in a row is safe.

### 7.3 Security posture of new tables

- `crm_cases_portal_sessions`: tokens are HMAC-signed (CAS-014 uses `mint_ws_token` / `verify_ws_token` from `app/core/crypto.py` lines 35 and 44). The token IS the primary key; possession of the token is the authorization credential for a portal session. TTL ensures expired sessions are reaped. The table must not be accessible via public API without token verification.
- `crm_cases_templates`: templates may include sensitive language; access is admin-only (CAS-012 endpoints use `require_admin_session`).
- `crm_kb_articles`: public browsing of published articles is intentionally unauthenticated (CAS-015). Draft and archived articles must be filtered at the query layer or by GSI key structure; `ByStatus` GSI with `status="published"` is the correct access pattern for the public endpoint.
- `crm_cases_sla_config`: write access is root-only (CAS-008 `PATCH /ui/admin/crm-cases/sla-config`); read access is admin+.
- `crm_cases_counters` and `crm_cases_links`: no special sensitivity; access is gated by the parent ticket's ownership check in downstream tickets.

### 7.4 No money-out paths

CAS-001 introduces no billing, refund, or ledger operations. When CSAT surveys (CAS-016) or SLA breach penalties are implemented in later tickets, they must reuse `app/services/billing_shared.py` ledger primitives (not fork them).

## 8. Backward Compatibility & Migration

### 8.1 Existing code is unchanged

`app/routers/tickets.py`, `app/services/tickets.py`, and `app/routers/ticket_boards.py` are byte-for-byte unchanged. No existing DDB table is modified. No existing route path changes. The `tickets` table (lines 695–711 in `local-ddb-init.py`, ten GSIs, `PK=pk / SK=sk`) gains no new GSIs or attributes.

### 8.2 Production deployment order

The six new tables must be provisioned (via Terraform / CloudFormation / `aws dynamodb create-table`) before the new binary is deployed. Because `T` is constructed at import time (line 321 in `tables.py`), the backend will fail to start if any `_safe_table(S.<name>)` call cannot resolve its table name. In practice, DynamoDB table access is lazy (boto3 does not validate table existence until the first operation), so the binary will start; the first request that actually touches a new table will fail until the table is created.

Recommended order for zero-downtime prod deployment:

1. Apply infrastructure changes to create all six tables.
2. Deploy the new backend binary.
3. Verify `GET /openapi.json` returns 200 and the new Settings fields are present in the startup log.
4. Enable `CRM_CASES_ENABLED=true` only after CAS-002 through CAS-006 are also merged and tested.

### 8.3 No data migration

CAS-001 is additive only. No existing data is read, written, or transformed. Existing ticket rows in `T.tickets` are unaffected.

### 8.4 Rollback

To roll back CAS-001: revert the three file changes (`settings.py`, `tables.py`, `local-ddb-init.py`). The six new DynamoDB tables can remain (they are empty and incur minimal cost); they do not need to be deleted. Setting `CRM_CASES_ENABLED=false` (the default) is sufficient to make the feature invisible.

## 10. Open Questions / Assumptions

### 10.1 SLA config attribute naming differs from KYC pattern

The KYC SLA config uses `pk: "CONFIG"` (attribute named `pk`) in `T.kyc_cases` (`kyc_case_assignment.py:685`). The CRM SLA config uses `config_key: "CONFIG"` in the dedicated `crm_cases_sla_config` table (attribute named `config_key`). These are intentionally different tables and attribute names — there is no conflict. The note that they share the same "key schema" is only accurate at the value level (`"CONFIG"` partition + `"SLA#{x}"` sort); the table schemas differ. The KYC config uses the `kyc_cases` table (PK `pk`); there is no separate KYC SLA table to collide with.

### 10.2 `crm_kb_articles` full-text search

The `ByCategory` and `ByStatus` GSIs support browsing but not full-text search. CAS-015 (Knowledge Base; per ticket source numbering) will need either a separate search index or a `FilterExpression` scan over the body field. For the initial KB implementation, a DynamoDB `scan` with `FilterExpression` on `body_markdown` CONTAINS is acceptable given low article counts; if volume grows, an OpenSearch index (separate feature) is the path forward. This assumption is flagged here so CAS-015 does not invest in a GSI-based full-text approach.

### 10.3 `crm_cases_portal_sessions` signing secret

CAS-001 introduces the table but not the signing secret setting. CAS-014 (customer self-service portal; per ticket source numbering) will add `crm_cases_portal_token_secret: str = os.environ.get("CRM_CASES_PORTAL_TOKEN_SECRET", "")` and fall back to `S.ui_access_token_secret` if empty (matching the cart recovery link pattern). This is documented here so implementers of CAS-014 know the intended design.

### 10.4 Case attachment bucket vs. file manager

The `crm_cases_attachments_bucket` defaults to `local-uploads`, the same bucket used by file manager uploads, profile photos, and other S3 assets. Distinct prefix (`ticket-attachments/`) ensures namespacing. If a future operator wants attachment isolation, they can configure a separate bucket name via env. No action needed in CAS-001.

### 10.5 `crm_kb_articles` slug uniqueness

The `crm_kb_articles` table has no GSI enforcing slug uniqueness. CAS-015 (KB management) must enforce uniqueness at the application layer (query `ByStatus` GSI + `FilterExpression slug=:slug`, or maintain a separate `SLUG#{slug}` secondary key row). This is a design choice for CAS-015, not a CAS-001 concern; flagged here for awareness.
