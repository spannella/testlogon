# STU-013 — Studio — layout editor (view layouts per module)

**Type:** Feature  **Priority:** P2  **Estimate:** 2 days
**Ticket source:** `docs/suitecrm/CRM_SECURITY_STUDIO_TICKETS.md`, section "STU-013"
**Feature flag:** `CRM_STUDIO_ENABLED` (env `CRM_STUDIO_ENABLED`, default `"false"`) — all routes under `/ui/admin/studio/*` return 404 while the flag is off. Existing platform behaviour is byte-for-byte identical with the flag off.

---

## 1. Summary & Goal

STU-013 builds the Studio layout editor: a DynamoDB-backed store of per-module, per-view layout definitions, a service layer that reads and writes them, and four admin REST endpoints appended to the existing `app/routers/crm_studio.py` router (created by STU-011). A companion React component (`LayoutEditor.tsx`) lets admins drag-and-drop field order within panels and toggle field visibility, then persist the result with a `PUT` call.

A **layout definition** records how the fields of a CRM entity (e.g. `contact`, `ticket`) should be arranged in a specific view mode: `detail` (read-only record card), `edit` (create/update form), `list` (table columns), or `search` (search criteria panel). Each layout is composed of one or more named panels; each panel holds an ordered list of field descriptors (field key, label override, column span, required override, and visibility flag).

The goal of this ticket is:

1. A root admin can define, replace, list, and delete the layout for any `{entity_type}/{view_type}` combination via the REST API.
2. `GET /ui/admin/studio/layouts/{entity_type}/{view_type}` returns `null` when no custom layout has been saved — the frontend uses its own hard-coded default field order in that case, so no migration of existing records is needed.
3. Layout field keys can reference both native entity attributes and custom field keys introduced by STU-011; the service validates that every referenced `field_key` either exists in the native schema constant or is an active custom field in `crm_studio_fields`.
4. The entire feature is invisible — zero DDB access, zero routes — when `CRM_STUDIO_ENABLED=0`.

## 3. Data Model

### 3.1 Table: `crm_studio_layouts` (introduced by STU-001)

**Partition key:** `pk` (S) — value: `LAYOUT#{entity_type}#{view_type}`
**Sort key:** `sk` (S) — value: `META`

**No GSIs.** Layouts are always accessed by exact `{entity_type, view_type}` pair — a single `get_item` call. The list endpoint (`GET /layouts/{entity_type}`) uses a DDB `query` with `KeyConditionExpression=Key("pk").begins_with("LAYOUT#{entity_type}#")`. This is efficient because item counts per entity type are bounded by the number of supported view types (currently four: `detail`, `edit`, `list`, `search`).

**TableDef** (declared by STU-001 in `scripts/local-ddb-init.py`):
```python
TableDef(S.crm_studio_layouts_table_name, "pk", "sk")
```
No `attr_types` override needed (both keys are strings; `updated_at` is stored as a plain integer attribute, not a GSI sort key).

**Item attributes per layout row:**

| Attribute | Type | Notes |
|---|---|---|
| `pk` | S | `LAYOUT#{entity_type}#{view_type}` — DynamoDB partition key |
| `sk` | S | `META` — constant sort key |
| `entity_type` | S | e.g. `contact`, `ticket`, `opportunity`, `lead`, `case`, `project`, `account` |
| `view_type` | S | one of `detail`, `edit`, `list`, `search` |
| `panels` | L | ordered list of panel objects (see below) |
| `updated_by_sub` | S | `user_sub` of the last root admin who saved the layout |
| `updated_at` | N | Unix timestamp (int) from `now_ts()` |

**Panel object structure** (stored as a DDB map inside the `panels` list):

| Field | Type | Notes |
|---|---|---|
| `panel_label` | S | Human-readable panel header (e.g. `"Basic Info"`, `"Address"`) |
| `columns` | N | Number of columns in the panel grid (1 or 2); governs `colspan` layout |
| `fields` | L | ordered list of field descriptor objects |

**Field descriptor object** (stored as a DDB map inside `panel.fields`):

| Field | Type | Notes |
|---|---|---|
| `field_key` | S | Identifies the field — either a native schema attribute name or a `custom_*` key from STU-011 |
| `label` | S | Display label override; empty string means "use field's own label" |
| `colspan` | N | 1 or 2; 2 spans both columns in a 2-column panel |
| `required` | BOOL | Override required flag for this view; default `false` |
| `visible` | BOOL | `false` hides the field in this view without removing it from the layout definition |

## 4. API / Service Design

### 4.1 Service: `app/services/crm_studio_layouts.py` (new file)

**Module-level cache** (mirrors `billing_config.py:46–54`):
```python
_layout_cache: dict[str, dict[str, Any] | None] = {}
_layout_cache_ts: dict[str, int] = {}
_CACHE_TTL_SECONDS: int = 60  # overridable via S.crm_studio_layout_cache_ttl_seconds

def _cache_key(entity_type: str, view_type: str) -> str:
    return f"{entity_type}#{view_type}"

def _invalidate_layout_cache(entity_type: str, view_type: str) -> None:
    key = _cache_key(entity_type, view_type)
    _layout_cache.pop(key, None)
    _layout_cache_ts.pop(key, None)
```

**Public functions:**

```python
def get_layout(entity_type: str, view_type: str) -> dict[str, Any] | None
```
Validates `entity_type` against `ALLOWED_ENTITY_TYPES` and `view_type` against `ALLOWED_VIEW_TYPES` (raises `ValueError` for invalid inputs). Checks the in-memory cache first; on cache miss calls `T.crm_studio_layouts.get_item(Key={"pk": f"LAYOUT#{entity_type}#{view_type}", "sk": "META"})`. Returns the `Item` dict (minus the `pk`/`sk` routing keys) or `None` if no item exists. Stores the result (including `None`) in the cache keyed by `_cache_key(entity_type, view_type)`.

```python
def save_layout(
    actor_sub: str,
    entity_type: str,
    view_type: str,
    panels: list[dict[str, Any]],
) -> dict[str, Any]
```
Validates `entity_type` and `view_type`. Validates `panels` structure (see Section 5.3). Optionally validates that all `field_key` values in the panels exist in `NATIVE_FIELD_KEYS[entity_type]` or are active custom fields (via the STU-011 lazy integration hook). Calls `T.crm_studio_layouts.put_item` to upsert the row (full replace — layouts are not partially updated). Emits `audit_event("studio.layout_saved", actor_sub, entity_type=entity_type, view_type=view_type, panel_count=len(panels))`. Invalidates the cache for `{entity_type, view_type}`. Returns the saved layout dict.

```python
def delete_layout(actor_sub: str, entity_type: str, view_type: str) -> None
```
Validates `entity_type` and `view_type`. Calls `T.crm_studio_layouts.delete_item(Key={"pk": ..., "sk": "META"})` — no-op if the item does not exist (DynamoDB `delete_item` is idempotent). Emits `audit_event("studio.layout_deleted", actor_sub, entity_type=entity_type, view_type=view_type)`. Invalidates cache.

```python
def list_layouts(entity_type: str) -> list[dict[str, Any]]
```
Validates `entity_type`. Calls `T.crm_studio_layouts.query(KeyConditionExpression=Key("pk").begins_with(f"LAYOUT#{entity_type}#"))`. Returns the list of item dicts (minus `pk`/`sk` keys), one per custom layout saved for the entity. Returns an empty list if no layouts exist — this is the expected state for a freshly deployed entity. No cursor pagination is needed: the item count is bounded by `len(ALLOWED_VIEW_TYPES) = 4`.

**Exception classes** (defined in the same module):
```python
class LayoutValidationError(ValueError):
    """Raised when panels structure fails schema validation."""
```

## 5. Detailed Behavior & Edge Cases

### 5.1 `get_layout` returns `null` — frontend default fallback

When no custom layout has been saved for `{entity_type, view_type}`, `get_layout` returns `None` (DDB `get_item` returns no `Item` key). The router serialises this as a JSON `null` body with `Content-Type: application/json`. The frontend detects a `null` response and falls back to its built-in default column order — no error, no empty state. This is the expected state for all entity/view combinations immediately after the feature flag is enabled.

### 5.2 Full-replace PUT semantics

`save_layout` uses `put_item` (not `update_item`), which atomically replaces the entire row. There is no partial-update path. This simplifies the write path: the client always sends the complete desired layout. The downside is that two concurrent admin saves can produce a last-writer-wins outcome, which is acceptable for infrequent admin configuration writes.

### 5.3 Panel structure validation

`save_layout` validates the `panels` argument before writing:

1. At least one panel must be present (`len(panels) >= 1`); raises `LayoutValidationError` with `code=empty_panels`.
2. No more than 20 panels (prevents runaway data growth); raises `LayoutValidationError` with `code=too_many_panels`.
3. Each panel must have at least one field descriptor in its `fields` list; raises `LayoutValidationError` with `code=empty_panel_fields` identifying the offending panel label.
4. `colspan` values must be 1 or 2 (validated at Pydantic level by `StudioFieldDescriptorIn`).
5. A field key must not appear more than once across all panels in the layout; raises `LayoutValidationError` with `code=duplicate_field_key` listing the offending keys.

### 5.4 Field key validation — STU-011 integration

When STU-011 is merged and `CRM_STUDIO_ENABLED=1`, `save_layout` validates that every `field_key` in the panels exists either in `NATIVE_FIELD_KEYS[entity_type]` or as an active custom field. The check uses a lazy import guard:

```python
def _get_active_custom_field_keys(entity_type: str) -> frozenset[str]:
    try:
        from app.services.crm_studio_fields import list_fields
        items, _ = list_fields(entity_type, include_inactive=False)
        return frozenset(item["field_key"] for item in items)
    except ImportError:
        return frozenset()
```

If the import fails (STU-011 not merged), all unknown field keys are accepted without error — the layout is saved as-is. Once STU-011 is present, unknown keys raise `LayoutValidationError` with `code=unknown_field_key` and a list of the offending keys. This matches the graceful-degradation pattern established in STU-011 spec section 5.4.

### 5.5 Cache stores `None` for absent layouts

The cache stores `None` explicitly for layouts that have been queried and found absent:
```python
_layout_cache[cache_key] = item_or_none   # item_or_none may be None
_layout_cache_ts[cache_key] = now_ts()
```
This negative caching prevents repeated DDB reads for layouts that have not been configured. A `delete_layout` call invalidates the cache entry, causing the next read to re-query DDB and re-cache `None`.

### 5.6 `delete_layout` idempotency

`delete_item` on a non-existent DDB item is a no-op in DynamoDB and raises no error. `delete_layout` therefore always returns successfully regardless of whether a layout existed. The audit event is emitted unconditionally (recording the attempt, even if the item was already absent — consistent with the STU-011 soft-delete audit pattern).

### 5.7 `list_layouts` and empty results

`list_layouts` queries with `Key("pk").begins_with(f"LAYOUT#{entity_type}#")`. If no layouts have been saved, this returns an empty list. The router returns `{"entity_type": entity_type, "layouts": []}` — not a 404. Clients must treat an empty layouts list as "all views are using default layout", not as an error.

### 5.8 `view_type` validation in router vs. service

Both the router and the service validate `view_type`. The router maps an invalid `view_type` to `HTTP 400` with `detail={"code": "invalid_view_type", "allowed": list(ALLOWED_VIEW_TYPES)}` before calling the service. The service raises `ValueError` with `code=invalid_view_type` for the same condition — the router catches this and returns the same 400 shape. This double-validation is intentional: the service can be called directly (e.g. from tests) and must be self-defensive.

### 5.9 Maximum panel count constant

`MAX_PANELS_PER_LAYOUT = 20` is a module-level constant read from `S.crm_studio_max_panels_per_layout` (default 20). This limit exists to cap DDB item size: a layout with 20 panels, each with 50 fields, could approach the 400 KB DDB item size limit if label overrides are long. In practice, 3–5 panels with 10–15 fields each is a realistic maximum, but the constant gives operators a safety valve.

### 5.10 `label` field semantics

The `label` field on `StudioFieldDescriptorIn` is an override of the field's own display label. An empty string means "use the field definition's own label". This allows an admin to present a field under a different name in a specific view (e.g. show the `subject` field as "Issue Title" in the ticket detail view) without changing the underlying field definition.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No `dev_mode` branches

The service and router contain no `if S.dev_mode:` branches. The same DDB `put_item` / `delete_item` / `get_item` / `query` calls execute in both environments. In dev, `T.crm_studio_layouts` resolves to a moto-backed in-process table. In prod, it resolves to the real DynamoDB endpoint. No conditional logic diverges between environments. This satisfies SECOPS-007 with no additional effort.

### 7.2 Idempotency of `save_layout`

`put_item` (full replace) is inherently idempotent: calling `save_layout` twice with identical `panels` produces the same DDB state. The only non-idempotent side effects are the audit event emission (one event per call) and the `updated_at` timestamp advancing. Both are acceptable for an admin configuration operation.

### 7.3 Idempotency of `delete_layout`

`delete_item` on a non-existent key is a no-op in DynamoDB. Two concurrent `delete_layout` calls for the same `{entity_type, view_type}` both succeed — the second is a no-op. Consistent with the STU-011 `delete_field` idempotency pattern.

### 7.4 Security: path parameter injection

Both `entity_type` and `view_type` arrive as URL path parameters and are validated against their respective allowlists (`ALLOWED_ENTITY_TYPES`, `ALLOWED_VIEW_TYPES`) before any DDB access. An attacker cannot probe or write to an arbitrary DDB partition by passing crafted path values; the validation raises `HTTP 400` before the DDB key is constructed.

### 7.5 Security: `panels` payload size

The `StudioLayoutSaveIn` model limits panels to 20 (`max_length=20` on the `panels` list) and each `panel_label` / `field.label` to 255 characters. This bounds the payload size before it reaches the service layer. Combined with DynamoDB's 400 KB item size limit, this prevents memory pressure from oversized write payloads.

### 7.6 ROOT-only writes

All create (PUT) and delete operations on layouts require `Role.ROOT`. Read access (list/get) is open to all ADMIN or ROOT users. This prevents scoped ADMIN operators from inadvertently altering the UI schema that governs all users' data entry experience, consistent with the ROOT-only write pattern in STU-011/STU-012.

### 7.7 Audit trail

Every mutating service call emits an `audit_event` via `app/services/alerts.audit_event` (`alerts.py:644`). Event names:
- `studio.layout_saved` — `entity_type`, `view_type`, `panel_count`
- `studio.layout_deleted` — `entity_type`, `view_type`

These events land in `T.alerts` under the actor's `user_sub` and are included in the ENTERPRISE-004 audit export stream via the existing `CrmAuditTrailAdapter` (STU-006).

## 8. Backward Compatibility & Migration

### 8.1 Additive only

No existing table, router, model, or service is modified by STU-013 beyond appending routes to `app/routers/crm_studio.py` and appending Pydantic models to `app/models.py`. The `crm_studio_layouts` table was created by STU-001. In prod, it exists before this ticket is deployed (as part of the STU-001 deployment sequence).

### 8.2 All entity/view combinations start with `null` layout

There is no migration or seed data. Every `{entity_type, view_type}` combination starts with `null` — meaning "use default layout" — until a root admin explicitly saves a custom layout. The frontend must handle `null` gracefully; see Section 5.1.

### 8.3 No breaking change to existing entity service APIs

`app/services/tickets.py`, `app/routers/contacts.py`, and all other existing entity endpoints are not modified by STU-013. The layout definition is purely a metadata store consumed by the frontend; it does not affect which fields are accepted or validated on write paths (that is the domain of STU-011's `validate_custom_fields`).

### 8.4 Router file extension ordering

STU-013 appends routes to the existing `app/routers/crm_studio.py` file created by STU-011 and extended by STU-012. The route declaration order within the file must be preserved: `/fields` block, then `/dropdowns` block, then `/layouts` block. Merging STU-013 before STU-012 (if STU-012 is delayed) is safe — the `/layouts` block can be appended directly after `/fields` without requiring a `/dropdowns` block to exist first.

### 8.5 Prod table creation

The `crm_studio_layouts` table is created by STU-001's `scripts/local-ddb-init.py` entry in dev. In prod, an `aws dynamodb create-table` call must be applied as part of the STU-001 migration (before `CRM_STUDIO_ENABLED=1` is set). No additional `UpdateTable` is required by STU-013 (no new GSIs on an existing table).

## 10. Open Questions / Assumptions

1. **Field key selector in frontend:** The `LayoutEditor.tsx` field selector must know the available fields for each entity type. The spec assumes it calls `GET /ui/admin/studio/fields/{entity_type}` (STU-011) to populate the dropdown. If STU-011 is not yet merged, the selector falls back to the `NATIVE_FIELD_KEYS` constant rendered by a static TypeScript list. This fallback behaviour should be confirmed.

2. **`view_type=list` semantics:** In a list/table view, `colspan` has no meaning (table columns are always single-width). The `colspan` field is accepted for `view_type=list` but ignored by the frontend renderer. An alternative design would reject `colspan > 1` for `list` views at the service layer. The spec currently allows it (no server-side rejection), which is simpler and avoids coupling the service to view-type-specific rendering rules.

3. **Non-custom panel labels for native fields:** The `label` override on field descriptors allows per-view label customisation. However, the native field labels (e.g. "Subject" for `subject`) are defined in the frontend component, not in a DynamoDB metadata table. A future enhancement could expose `GET /ui/admin/studio/native-fields/{entity_type}` to provide label hints from the backend, keeping label management in one place. Not in scope for STU-013.

4. **Concurrent admin saves — last-writer-wins:** The spec accepts last-writer-wins for `put_item`. If two admins edit the same layout simultaneously, one change is silently lost. A `ConditionalExpression=Attr("updated_at").eq(previous_updated_at)` optimistic-lock pattern could prevent this, but it adds retry complexity for a low-concurrency admin operation. Decision deferred to implementation.

5. **Layout validation strictness with `field_key`:** The spec proposes validating `field_key` values against the native schema + active custom fields when STU-011 is present. An alternative is to not validate at all (store whatever the admin provides and let the frontend skip unknown fields). The strict approach is preferred for data quality but must be disabled gracefully when STU-011 is absent.
