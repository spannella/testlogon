# INV-010 — Invoice CRM record linking — account and contact association

**Type:** Feature | **Priority:** P2 | **Estimate:** 2d | **Flag:** `AOS_INVOICE_CRM_LINKING_ENABLED` (default OFF)

---

## 1. Summary & Goal

INV-010 adds optional `account_id` and `contact_id` reference fields to invoice records, establishing the CRM linking layer that SuiteCRM's AOS module provides out of the box. When set, `account_id` identifies a B2B organisation (a future PTY-012 `PARTY_GROUP` party) and `contact_id` identifies an individual buyer (a future PTY-011 `PERSON` party). A new sparse GSI (GSI3) on the invoices table enables an admin to list all invoices for a given account in a single paginated query — the primary day-to-day CRM workflow.

With the feature flag off (`AOS_INVOICE_CRM_LINKING_ENABLED=0`, the default) the platform is byte-for-byte unchanged: no new DDB attributes are written, no new endpoints exist, and `InvoiceOut` returns empty strings for the two new fields. Existing invoice generation, PDF rendering, and ledger hooks are not modified.

**Primary user story:** A sales admin opens the account record for "Acme Corp" and wants to see every invoice ever raised against that account. With INV-010 deployed and the flag on, `GET /ui/admin/invoices/by-account/acct_123` returns a paginated list of all invoices carrying `account_id="acct_123"`, sorted newest-first, without scanning the full invoices table.

## 3. Data Model

### No new DynamoDB table

All new fields are additive attributes on the existing `pk=USER#{sub} / sk=INV#{number}` items in `T.invoices`. The table schema is extended with a third GSI only.

### New attributes on invoice items

| Attribute | Type | Written when |
|-----------|------|-------------|
| `account_id` | String | `account_id` arg is non-empty AND flag is ON |
| `contact_id` | String | `contact_id` arg is non-empty AND flag is ON |
| `GSI3PK` | String `ACCOUNT#{account_id}` | `account_id` is non-empty AND flag is ON |
| `GSI3SK` | Number (Unix timestamp) | Same condition as `GSI3PK` |

The `GSI3PK`/`GSI3SK` attributes are written on the same `put_item` call that writes the invoice record — no separate update is needed. Items without `account_id` never receive `GSI3PK` or `GSI3SK`; DynamoDB automatically excludes them from GSI3 (sparse GSI behaviour). No backfill of pre-existing invoices is required or performed.

### GSI3 definition (additive to existing `invoices` TableDef)

Add to `scripts/local-ddb-init.py:2273–2277`:

```python
TableDef(
    _resolve_table_name(S.invoices_table_name, "invoices"),
    "pk", "sk",
    gsi=[
        {"index_name": "GSI1", "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "GSI2", "partition_key": "GSI2PK", "sort_key": "GSI2SK"},
        {"index_name": "GSI3", "partition_key": "GSI3PK", "sort_key": "GSI3SK"},  # NEW
    ],
    attr_types={"GSI1SK": "N", "GSI2SK": "N", "GSI3SK": "N"},  # GSI3SK added
)
```

`"GSI3SK": "N"` is mandatory — `GSI3SK` is `created_at` (Unix integer). Omitting it causes DynamoDB to treat it as String, and `ScanIndexForward=False` will sort lexicographically (breaking newest-first ordering) while integer comparisons in filter expressions raise `ValidationException`.

After this change `just restart` recreates the table in dev; in production an `UpdateTable` call adds the GSI with a backfill period before the query path is deployed (see §8).

### Key patterns

```
GSI3PK = "ACCOUNT#{account_id}"    e.g. "ACCOUNT#acct_abc123"
GSI3SK = created_at                 e.g. 1748649600  (Unix int)
```

`account_id` values are opaque strings. The format `acct_` + hex is a suggested convention (mirrors `inv_` prefix used for `invoice_id` at `invoices.py:311`) but is not enforced by this ticket — any non-empty string is accepted.

## 5. Detailed Behavior & Edge Cases

### Sparse GSI and items without account_id

DynamoDB only indexes an item in a GSI when the GSI partition key attribute is present on the item. When `account_id` is empty or the flag is off, neither `GSI3PK` nor `GSI3SK` is written. Those items are invisible to GSI3 queries. This is the correct behaviour — the GSI is intentionally sparse.

An `account_id` that contains only whitespace (`"  "`) must be treated as empty: `account_id = account_id.strip() or ""`. Write the GSI attributes only when `account_id` is non-empty after stripping.

### Flag transition: off → on (new invoices)

When the flag is toggled on, all invoices created from that point forward may carry `account_id`/`contact_id`. Pre-existing invoices remain without those attributes and return `account_id=""` from `_serialize`. `list_invoices_for_account` returns only invoices created after the flag was enabled (sparse GSI contains only items with `GSI3PK`). This is the correct and documented behaviour — no backfill.

### Flag transition: on → off (runtime disable)

The flag is checked in the router's `_require_enabled` path and in `list_invoices_for_account`. Disabling the flag causes the endpoint to return 404 immediately. Items already written with `GSI3PK` remain in the GSI but are unreachable via the API. If the flag is re-enabled later, those items become reachable again — the GSI is durable.

### Idempotency

`create_invoice` is already idempotent on `ledger_entry_id` via the `_existing_for_ledger` marker row (line 252–269). When an idempotent duplicate is detected and the existing invoice is returned (line 303), `account_id`/`contact_id` from the second call are silently ignored — the returned value reflects what was stored in the first call. This is consistent with the idempotency contract already in place.

### Large account history (DynamoDB page limits)

`list_invoices_for_account` fetches up to `Limit` items per query call but DynamoDB may return fewer due to the 1 MB per-page cap. The function does not loop — it returns `next_cursor` for the caller to paginate. The router exposes `cursor` as a query parameter. Callers who want all invoices must paginate. This matches the existing `list_invoices` and `admin_list_invoices` patterns (lines 395–439, 492–522).

### contact_id without a GSI

`contact_id` is stored as a plain attribute but not indexed. To list invoices by contact, a caller must scan GSI2 (`ADMIN_ALL`) and apply a `FilterExpression` on `contact_id`, or wait for a future GSI4 ticket. This ticket explicitly does not add GSI4 to keep scope bounded; the field is stored now so no schema migration is needed when that follow-up ships.

### VALID_TYPES guard

`create_invoice` (line 298) returns `None` for unknown `invoice_type` values. This guard is applied before the GSI3 write block, so an invalid type still returns `None` with no DDB write. The `account_id`/`contact_id` logic is never reached.

### Route ordering with QUO-005 and INV-009

QUO-005 adds `POST /ui/admin/invoices/manual` and `POST /ui/invoices/{invoice_number}/void`; INV-009 may add additional `/{invoice_number}` routes. The `by-account` route must be declared in the `invoices_admin_router` (prefix `/ui/admin/invoices`) before any parameterised `/{invoice_number}` route. In the user-facing `invoices_router` (prefix `/ui/invoices`) there is currently `GET /{invoice_number}` (line 53) and `GET /{invoice_number}/pdf` (line 65) — the `by-account` route goes into the admin router (separate prefix), so there is no conflict with user-facing routes.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

There is no `if S.dev_mode` branch anywhere in this ticket. The GSI3 write and the `list_invoices_for_account` query both use `T.invoices` via `boto3`, which is intercepted by moto in-process in dev and hits real DynamoDB in prod. The `s3_client()` factory and `audit_event` calls are also environment-agnostic. This satisfies SECOPS-007: identical code executes in both environments.

The only environment-specific concern is the table recreation sequence: in dev, `just restart` drops and recreates the table with GSI3 (via `scripts/local-ddb-init.py`). In prod the table already exists; see §8.

### Idempotency

`create_invoice` is already idempotent on `ledger_entry_id`. The GSI3 attributes are written as part of the same `put_item` call — there is no separate update step that could create a partial write. If `put_item` fails, neither the invoice record nor the GSI3 attributes are persisted.

The `list_invoices_for_account` function is a pure read — it is inherently idempotent.

### Security

- The `GET /ui/admin/invoices/by-account/{account_id}` endpoint requires `require_admin_or_root`. A `Role.USER` session receives 403 from the dependency before the handler body is reached. There is no user-visible endpoint that exposes account-scoped invoice lists.
- `account_id` is stored as a plain string without server-side validation against an actual account record. This is intentional: PTY-012 is not yet implemented. Validating `account_id` against a non-existent table would require a network call with no benefit until PTY-012 ships. Callers are responsible for passing valid account IDs.
- `contact_id` is stored but never exposed via a search endpoint in this ticket; it cannot be used to enumerate invoices for a contact.
- Audit events are emitted on every invoice creation that carries a non-empty `account_id`, creating a traceable record of CRM-linked invoice creation (`invoice.crm_linked`).
- CSRF: the new `GET` endpoint uses cookie auth; GET requests are CSRF-exempt per the `require_ui_session` implementation (`app/auth/deps.py`). Admin POST endpoints added by QUO-005 require `x-csrf-token`.

## 8. Backward Compatibility & Migration

### Model backward compatibility

`InvoiceOut.account_id` and `InvoiceOut.contact_id` default to `""`. Any consumer of `InvoiceOut` that does not reference these fields sees no change. The `_serialize` function returns `""` for both fields on items that lack the attributes (the `record.get("account_id") or ""` pattern). The `InvoiceListOut` wrapper is unchanged.

### DynamoDB table migration (GSI3)

In dev: `scripts/local-ddb-init.py` change takes effect on next `just restart` (table drop + recreate). No data is lost since dev data is ephemeral.

In production: DynamoDB GSI addition is online and non-disruptive. Run `aws dynamodb update-table` to add GSI3 before deploying the code that writes `GSI3PK`/`GSI3SK`. The GSI backfill is asynchronous; during backfill the index is in `CREATING` status and queries against it return 0 results (not an error). The deployment sequence is:

1. Deploy `scripts/local-ddb-init.py` change to the infra pipeline — triggers `UpdateTable` with GSI3 definition.
2. Wait for GSI3 to reach `ACTIVE` status (typically minutes to hours depending on table size).
3. Deploy the code changes (`invoices.py`, `models.py`, `routers/invoices.py`, `settings.py`).
4. Enable `AOS_INVOICE_CRM_LINKING_ENABLED=1` in the environment.

Pre-existing invoices are not backfilled into GSI3. They will not appear in `list_invoices_for_account` queries. This is the correct and documented behaviour; there is no business requirement to retroactively link historical invoices to accounts.

### `create_invoice` callers

All existing callers of `create_invoice` use keyword arguments. Adding `account_id=""` and `contact_id=""` as keyword-only parameters with default values is fully backward-compatible — no existing call site needs to be updated.

## 10. Open Questions / Assumptions

1. **`account_id` format** — The spec treats `account_id` as an opaque string. When PTY-012 ships, `account_id` values will be `party_` + hex strings. Should INV-010 enforce a format prefix now (e.g. `account_id.startswith("party_")`)? **Assumption:** No format enforcement in INV-010; keep it opaque. Add a Pydantic `Field(max_length=128)` constraint only to prevent oversized DDB attribute values.

2. **Per-contact GSI (GSI4)** — Should INV-010 add GSI4 on `contact_id` now, while the table schema is changing? **Assumption:** Deferred. The `contact_id` attribute is stored for future linking but a GSI for it increases write amplification and cost. A follow-up ticket adds GSI4 when `GET /ui/admin/invoices/by-contact/{contact_id}` is actually needed.

3. **`ManualInvoiceCreateIn` coordination with QUO-005** — QUO-005 defines `ManualInvoiceCreateIn` in `app/models.py`. INV-010 needs to add `account_id` and `contact_id` to that model. **Assumption:** If QUO-005 merges first, INV-010 adds the two fields as a trivial model extension. If INV-010 merges first, it adds a stub `ManualInvoiceCreateIn` with only these two fields; QUO-005 adds the remaining fields in its merge. Either order is safe because both tickets add fields with defaults.

4. **Invoice ownership vs account scope** — An invoice has `pk=USER#{user_sub}`, meaning ownership is per-user. An account may span multiple users (e.g. multiple sales reps create invoices for the same account). GSI3 queries across users by `account_id` regardless of `user_sub`. **Assumption:** This is the correct behaviour — the admin by-account view must be cross-user. The admin auth gate (`require_admin_or_root`) ensures only privileged callers can query the cross-user index.

5. **`invoice_type` for manual B2B invoices** — `VALID_TYPES` (line 33) is `{"tip", "unlock", "subscription", "shop", "deposit"}`. QUO-005 passes `invoice_type="shop"` for manually-created B2B invoices. **Assumption:** No new type is needed in INV-010; `account_id` is orthogonal to `invoice_type`. When the Party module ships, a new `"b2b"` type may be added — that is a QUO-005/PTY-012 concern.
