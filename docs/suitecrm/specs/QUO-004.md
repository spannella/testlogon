# QUO-004 — CRM Contract entity — DynamoDB model, service, and REST API

**Ticket type:** Feature  
**Priority:** P1  
**Estimate:** 3 d  
**Flag:** `AOS_CONTRACTS_ENABLED` (default OFF)

---

## 1. Summary & Goal

Implement the CRM contract entity that SuiteCRM calls its AOS Contracts module. A contract is a formal, time-bounded agreement between the platform and an account (or individual contact) with a monetarily-valued commitment and an explicit lifecycle: `draft → active → expired | terminated | renewed`. Contracts can be created directly by users or produced automatically when an accepted quote is converted (QUO-003). The feature also delivers a background renewal-notification service that sends email alerts before a contract's end date.

The feature is completely additive. With `AOS_CONTRACTS_ENABLED=0` (the default) every new endpoint returns 404, the background loop does not start, and no existing surface is altered by even a single byte.

## 2. Context & Current State

### What already exists and must be reused

**Monotonic counter pattern** — `app/services/invoices.py:82–92` implements `_next_invoice_number()`, which performs an atomic DynamoDB `ADD` on the `Key={"pk": "COUNTER", "sk": "SEQ"}` row of the `invoices` table and formats `INV-{year}-{seq:05d}`. The contract service will replicate this exact pattern on a `Key={"pk": "COUNTER", "sk": "CONTRACT_SEQ"}` row of the new `aos_contracts` table, yielding `CON-{year}-{seq:05d}` numbers.

**Audit event emission** — `app/services/alerts.py:644` exposes `audit_event(event, user_sub, request=None, **fields)` which writes a structured row to `T.alerts` and, when a request object is provided, enriches the payload with IP, user-agent, and impersonation context. All state-changing service functions in this spec call it.

**Email dispatch** — `app/services/alerts.py:459` exposes `send_alert_email(to_emails, subject, body_text)`. In dev mode it writes to a local log file; in prod it calls SES via boto3. The renewal notification background task calls this function directly — no new email path is introduced.

**Background startup pattern** — `app/services/compute_billing.py:669–676` shows `start_compute_billing_timer_task()`, which calls `asyncio.ensure_future(run_compute_billing_timer())` when `S.compute_billing_enabled` is true. The contract renewal checker follows the same structure and is registered via `app.add_event_handler("startup", start_contracts_renewal_check_task)` alongside the compute billing hook at `app/main.py:868–869`.

**Pagination cursors** — `app/core/cursor.py:94,103` provides `encode_cursor` / `decode_cursor`. All list endpoints use these functions to encode `LastEvaluatedKey` from DynamoDB responses.

**Auth dependencies** — `app/auth/policy.py:67` defines `require_admin_or_root`, which raises HTTP 403 when the authenticated user's role is not `ADMIN` or `ROOT` (see `app/auth/roles.py:8`). User-scoped endpoints use `require_ui_session` from `app/auth/deps.py`.

**Settings pattern** — feature flags follow the `cart_reminders_enabled` pattern at `app/core/settings.py:821`: `bool = os.environ.get("FLAG_NAME", "0") not in ("0", "false", "False")`.

**Table definition pattern** — `scripts/local-ddb-init.py:28–36` defines the `TableDef` dataclass. `attr_types` must declare numeric GSI sort keys with `"N"` or DynamoDB stores them as strings, causing `ValidationException` at query time (per CLAUDE.md gotcha). The `sticker_collections` table at line 82 shows the canonical example: `attr_types={"created_at": "N"}`.

**`_FloatSafeTable` proxy** — `app/core/tables.py:29–66` wraps every table handle so `put_item` and `update_item` automatically coerce Python floats to `Decimal`. All integer timestamp fields are already Python `int`; the proxy is transparent for this service.

### What does not yet exist

There is no `aos_contracts` table, no `T.aos_contracts` handle, no `app/services/aos_contracts.py`, no `app/routers/aos_contracts.py`, and no `ContractOut` / `ContractCreateIn` / `ContractPatchIn` / `ContractListOut` Pydantic models. The spec below introduces all of them from scratch.

- **QUO-002** defines the `AosPdfTemplateService`. Once QUO-002 lands, a `module="contract"` template can be registered; `GET /ui/contracts/{contract_id}/pdf` (added in this spec) should prefer an active template over the text-PDF fallback.

## 3. Data Model

### 3.1 DynamoDB table: `aos_contracts`

Environment variable: `AOS_CONTRACTS_TABLE_NAME` (default `"aos_contracts"`).

```
PK  = USER#{user_sub}                       string
SK  = CONTRACT#{contract_id}                string
    contract_id      = "con_" + uuid4().hex[:16]
```

**All item attributes:**

| Attribute | Type | Notes |
|---|---|---|
| `pk` | S | `USER#{user_sub}` |
| `sk` | S | `CONTRACT#{contract_id}` |
| `contract_id` | S | Bare ID without prefix |
| `contract_number` | S | `CON-{year}-{seq:05d}` from atomic counter |
| `user_sub` | S | Denormalized for GSI queries |
| `title` | S | Free-text name of the agreement |
| `stage` | S | `draft` \| `active` \| `expired` \| `terminated` \| `renewed` |
| `account_id` | S | PTY-012 future party_id; `""` when absent |
| `contact_id` | S | PTY-011 future party_id; `""` when absent |
| `aos_quote_id` | S | Back-reference if created via QUO-003; `""` otherwise |
| `start_date` | N | Unix timestamp; required |
| `end_date` | N | Unix timestamp; `None` / absent = open-ended |
| `value_cents` | N | Monetary value in integer cents |
| `currency` | S | ISO 4217 lowercase (default `"usd"`) |
| `description` | S | Extended notes; `""` when absent |
| `renewal_notice_days` | N | Days before `end_date` to trigger notification (default `30`) |
| `renewal_notified_at` | N | Unix timestamp when renewal email was sent; absent = not yet sent |
| `billing_address` | M | `{street, city, state, postal_code, country}` |
| `shipping_address` | M | Same shape; may be empty dict |
| `created_at` | N | Unix timestamp set at creation |
| `updated_at` | N | Unix timestamp updated on every write |

**COUNTER row** (lives in the same `aos_contracts` table):

```
PK = "COUNTER"
SK = "CONTRACT_SEQ"
next_seq: N  (auto-incremented via ADD, same pattern as invoices.py:82)
```

### 3.2 GSIs

**GSI1 — cross-user admin list:**

```
GSI1PK = "CONTRACTS#ALL"              (literal string on every item)
GSI1SK = created_at                   (numeric)
Index name: contracts-all-index
```

Used by `admin_list_contracts()`. Projects all attributes.

**GSI2 — per-user stage + expiry filter:**

```
GSI2PK = USER#{user_sub}#STAGE#{stage}
GSI2SK = end_date                     (numeric; items with end_date=None are absent from this index)
Index name: contracts-by-stage-index
```

Used by `list_contracts(user_sub, stage=...)` and by `check_expiring_contracts()` (scans stage=`active` entries approaching their end_date). Items with no `end_date` do not project a `GSI2SK` value and are sparse in this index — that is intentional; open-ended contracts never expire.

### 3.3 `scripts/local-ddb-init.py` entry

```python
TableDef(
    _resolve_table_name(S.aos_contracts_table_name, "aos_contracts"),
    "pk",
    "sk",
    gsi=[
        {
            "index_name": "contracts-all-index",
            "partition_key": "GSI1PK",
            "sort_key": "GSI1SK",
        },
        {
            "index_name": "contracts-by-stage-index",
            "partition_key": "GSI2PK",
            "sort_key": "GSI2SK",
        },
    ],
    attr_types={"GSI1SK": "N", "GSI2SK": "N"},
),
```

`attr_types` is mandatory. Omitting it stores `created_at` and `end_date` as DynamoDB String values, which causes `ValidationException: Comparators of type N cannot be used with string attribute` when the renewal checker or admin list endpoint queries either GSI with a numeric value.

## 4. API / Service Design

### 4.1 Service layer: `app/services/aos_contracts.py`

All public functions begin with:

```python
if not S.aos_contracts_enabled:
    return None   # or raise HTTPException(status_code=404) in the router layer
```

#### `_next_contract_number() -> str`

Identical to `_next_invoice_number()` at `invoices.py:82` but targets `T.aos_contracts` with `Key={"pk": "COUNTER", "sk": "CONTRACT_SEQ"}`. Returns `f"CON-{year}-{seq:05d}"`.

#### `create_contract(user_sub, *, title, start_date, end_date=None, value_cents, currency="usd", description="", account_id="", contact_id="", aos_quote_id="", renewal_notice_days=30, billing_address=None, shipping_address=None) -> dict`

1. Validates `start_date` is a positive integer. If `end_date` is provided, validates `end_date > start_date`.
2. Calls `_next_contract_number()`.
3. Mints `contract_id = "con_" + uuid4().hex[:16]`.
4. Builds the DDB item with `stage="draft"`, `created_at=now_ts()`, `updated_at=now_ts()`, `GSI1PK="CONTRACTS#ALL"`, `GSI1SK=created_at (int)`.
5. If `end_date` is provided, also sets `GSI2PK=f"USER#{user_sub}#STAGE#draft"`, `GSI2SK=end_date (int)`.
6. Calls `T.aos_contracts.put_item(Item=item)`.
7. Calls `audit_event("contract.created", user_sub, contract_id=contract_id, contract_number=...)` from `app/services/alerts.py:644`.
8. Returns the serialized contract dict.

#### `get_contract(user_sub, contract_id) -> dict | None`

`T.aos_contracts.get_item(Key={"pk": f"USER#{user_sub}", "sk": f"CONTRACT#{contract_id}"})`. Returns `None` if absent or if the item's `user_sub` does not match (ownership check).

#### `list_contracts(user_sub, *, stage=None, limit=50, cursor=None) -> dict`

- When `stage` is given: queries `GSI2` with `KeyConditionExpression=Key("GSI2PK").eq(f"USER#{user_sub}#STAGE#{stage}")`, `ScanIndexForward=False`, `Limit=min(limit, 200)`.
- When `stage` is absent: queries the base table by `Key("pk").eq(f"USER#{user_sub}")`, filtering on `SK.begins_with("CONTRACT#")`, `ScanIndexForward=False`.
- Decodes `cursor` via `decode_cursor` from `app/core/cursor.py:103`; uses result as `ExclusiveStartKey`.
- Encodes `LastEvaluatedKey` via `encode_cursor` from `app/core/cursor.py:94`.
- Returns `{"contracts": [...], "count": int, "next_cursor": str | None}`.

#### `update_contract(user_sub, contract_id, *, title=None, end_date=None, value_cents=None, currency=None, description=None, renewal_notice_days=None, billing_address=None, shipping_address=None) -> dict | None`

1. Calls `get_contract(user_sub, contract_id)` — raises 404 if absent.
2. Builds a partial `UpdateExpression` covering only non-None arguments plus `updated_at=now_ts()`.
3. If `end_date` changes and the contract has a `stage`, rewrites `GSI2SK` and (if stage also has a `GSI2PK`) updates that field.
4. Emits `audit_event("contract.updated", user_sub, ...)`.
5. Returns the updated serialized dict.

#### `transition_stage(user_sub, contract_id, new_stage) -> dict`

Allowed transitions:

| From | To (permitted) |
|---|---|
| `draft` | `active` |
| `active` | `expired`, `terminated`, `renewed` |

Any other transition raises `HTTPException(status_code=400, detail={"code": "invalid_stage_transition", "from": current, "to": new_stage})`.

Implementation:
1. Fetches the current item; validates ownership and that `stage` is not already `new_stage`.
2. Performs a conditional `update_item` with `ConditionExpression="stage = :old"` to prevent concurrent writes from racing through multiple transitions.
3. Updates `GSI2PK` to `f"USER#{user_sub}#STAGE#{new_stage}"` so the stage-filter index stays consistent.
4. Emits `audit_event("contract.stage_changed", user_sub, from_stage=current, to_stage=new_stage, ...)`.
5. Returns the updated dict.

#### `admin_list_contracts(*, limit=50, cursor=None) -> dict`

Queries `GSI1` with `KeyConditionExpression=Key("GSI1PK").eq("CONTRACTS#ALL")`, `ScanIndexForward=False`. Pagination identical to `list_contracts`.

#### `check_expiring_contracts() -> int`

Called by the background renewal loop. Returns the count of notifications sent during the run.

Algorithm:
1. Compute `threshold_ts = now_ts() + max_notice_days_to_scan * 86400` where `max_notice_days_to_scan = 90` (a constant wide enough to cover any realistic `renewal_notice_days`). Query `GSI2` for all `stage=active` items whose `end_date` is between `now_ts()` and `threshold_ts`:
   ```
   IndexName="contracts-by-stage-index"
   KeyConditionExpression=
       Key("GSI2PK").eq("USER#{user_sub}#STAGE#active")
       & Key("GSI2SK").between(now_ts(), threshold_ts)
   ```
   Because this is a cross-user scan the implementation must loop over all users. The practical approach is to scan `GSI1` for stage=`active` contracts and post-filter, or use a separate "all active by expiry" GSI. Given the ticket scope, the implementation scans `GSI1` for `GSI1PK="CONTRACTS#ALL"` with a `FilterExpression=Attr("stage").eq("active") & Attr("end_date").between(now_ts(), threshold_ts)` (per CLAUDE.md, FilterExpression does not reduce page size, so the loop must follow `LastEvaluatedKey`).

2. For each matched item where `renewal_notified_at` is absent and `end_date - now_ts() <= renewal_notice_days * 86400`:
   - Look up the owner's email via `app/services/profile.get_profile_identity(user_sub)` (same helper already used by `audit_event` at `alerts.py:669`).
   - Call `send_alert_email([owner_email], subject, body_text)` from `app/services/alerts.py:459`.
   - Update the item with `renewal_notified_at = now_ts()` via `update_item`.
   - Emit `audit_event("contract.renewal_notified", user_sub, contract_id=..., end_date=...)`.
   - Increment counter.

3. Returns total count of notifications sent.

Gated: returns 0 immediately when `not S.aos_contracts_renewal_notifications_enabled`.

## 5. Detailed Behavior & Edge Cases

### Stage machine enforcement

The full allowed-transition matrix is enforced in `transition_stage()` via an explicit allowlist dict:

```python
_ALLOWED_TRANSITIONS = {
    "draft":  {"active"},
    "active": {"expired", "terminated", "renewed"},
}
```

Terminal stages (`expired`, `terminated`, `renewed`) have no outbound edges. Attempting to transition out of a terminal stage returns HTTP 400 `invalid_stage_transition`. Attempting `draft → expired` (skipping `active`) also returns 400.

### Conditional-write race prevention

`transition_stage` uses a DynamoDB conditional expression:

```python
T.aos_contracts.update_item(
    Key={...},
    UpdateExpression="SET stage = :new, ...",
    ConditionExpression="stage = :old",
    ExpressionAttributeValues={":old": current_stage, ":new": new_stage},
)
```

If a concurrent request wins the race, the loser receives a `ConditionalCheckFailedException` which the service translates to HTTP 409 `concurrent_update`.

### Duplicate conversion guard (QUO-003 integration)

When QUO-003 calls `create_contract(... aos_quote_id=quote_id)` during quote conversion, the quote item is already stamped with `converted_to_contract_id` by QUO-003 before `create_contract` is called. If `create_contract` itself fails after the quote is stamped, QUO-003 rolls back the quote stage. QUO-004 does not need to validate uniqueness of `aos_quote_id` — that idempotency is owned by QUO-003's conditional-put on the quote item.

### Renewal notification idempotency

The `check_expiring_contracts()` function only sends a notification when `renewal_notified_at` is absent on the item. Immediately after sending, it writes `renewal_notified_at = now_ts()`. On the next poll the item will no longer match the "absent" filter and will be skipped. A second notification is never sent for the same contract unless the field is manually cleared (no API for this; admin-only via DDB console if needed).

### Open-ended contracts and GSI2

Contracts with no `end_date` do not write `GSI2SK`. They do not appear in the stage-by-expiry GSI2 index. Listing them requires querying the base table by PK with `begins_with("CONTRACT#")`. `list_contracts` with no `stage` filter uses this path. Open-ended contracts are never candidates for renewal notifications.

### `value_cents = 0`

A zero-value contract (e.g. a free-tier SLA) is valid. `value_cents >= 0` is enforced by Pydantic `ge=0`. There is no billing-ledger interaction for the contract entity itself — the value field is informational. Any monetary movement (deposits, invoicing) goes through existing billing primitives (`billing_shared.new_ledger_entry`) initiated by QUO-005 or external billing flows.

### PDF fallback

When QUO-002 is not yet deployed (or `AOS_PDF_TEMPLATES_ENABLED=0`), `GET /ui/contracts/{id}/pdf` falls back to a text-PDF rendered via `_render_pdf(lines)` at `invoices.py:103`. The `_render_contract_lines(record)` helper follows the same structure as `_render_invoice_lines` at `invoices.py:150`: header block with contract number/date/status, party block (account_id, contact_id), value/currency, start/end dates, renewal notice days.

### Empty address fields

Both `billing_address` and `shipping_address` accept partial or fully-empty dicts. The service stores whatever is provided without validation of individual sub-fields (city, postal code, etc.). PTY-011/012 will eventually provide proper validated address records.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

There is no `if S.dev_mode` branch anywhere in `app/services/aos_contracts.py` or `app/routers/aos_contracts.py`. The DynamoDB calls use `T.aos_contracts`, which in dev resolves to DynamoDB Local via moto (same boto3 path as prod). The `send_alert_email` call in `check_expiring_contracts()` delegates to the existing `alerts.send_alert_email` function, which handles the dev/prod divergence internally at `alerts.py:462–467` (dev writes to a log file; prod calls SES). The contract service sees only one function signature in both environments.

The S3 PDF upload in `get_contract_pdf` uses `app/core/aws_clients.s3_client()` (same factory used by invoices at `invoices.py:35`). In dev this is intercepted by moto's in-process S3 mock.

### Idempotency

`create_contract` is not inherently idempotent (every call mints a new `contract_id` and increments the counter). Callers that need idempotency (e.g. QUO-003's conversion endpoint) must check whether `converted_to_contract_id` is already set on the quote before calling `create_contract`, and return the existing contract if present. This guard lives in QUO-003, not here.

The renewal notification check is idempotent: `renewal_notified_at` is written atomically immediately after the email send. If the process crashes between send and write, the worst case is a duplicate notification on the next poll cycle, which is acceptable for a low-frequency (hourly) notification.

### Authorization

All user-scoped endpoints use `require_ui_session` (cookie + CSRF or Bearer-token). PATCH and POST stage transitions enforce resource ownership by fetching the item by `USER#{user_sub}` PK — a contract owned by another user simply does not exist in that partition and returns 404, leaking no information.

Admin list uses `require_admin_or_root` from `app/auth/policy.py:67`, which checks `role in {Role.ADMIN, Role.ROOT}` per `app/auth/roles.py:8`. No scoped-admin restriction is needed for this read-only list endpoint.

There is no money-out path in the contract entity itself. If a future ticket adds contract termination fees, it must reuse `billing_shared.settle_or_reverse_ledger` at `billing_shared.py:262` — never a custom payment deduction.

## 8. Backward Compatibility & Migration

### Zero-downtime addition

The `aos_contracts` table does not exist before this ticket. `scripts/local-ddb-init.py` is extended with the new `TableDef`. In dev, `just restart` recreates all tables from scratch. In production, the table must be created via `aws dynamodb create-table` (or Terraform) with both GSIs before the new router is deployed; the deployment ordering is: table creation → code deploy. No existing table is modified.

### No existing model changes

No existing Pydantic model is modified. `ContractOut` and its siblings are purely additive entries in `app/models.py`. Existing routes, serializers, and response bodies are unaffected.

### `T` dataclass addition

Adding `aos_contracts: Any` to the `Tables` frozen dataclass in `app/core/tables.py` and initializing it in the `T` singleton is a backward-compatible additive change. No existing field position changes; frozen dataclasses in Python allow new fields at the end.

### QUO-003 forward dependency

QUO-003's `convert-to-contract` endpoint imports `create_contract` from `app/services/aos_contracts.py`. If QUO-004 is not yet deployed when QUO-003 ships, the import will fail at startup. The correct merge order is: QUO-004 merged first (or simultaneously with QUO-003). Both tickets should ship in the same release window.

## 10. Open Questions / Assumptions

1. **`contact_id` / `account_id` validation** — PTY-011 and PTY-012 are not yet delivered. The spec treats both as opaque strings with no FK check. Once PTY delivers its party records, a follow-up ticket should add a validation step in `create_contract` that verifies the caller owns the referenced party record. This is explicitly out of scope for QUO-004.

2. **Multi-currency value** — `value_cents` is stored as an integer in the contract's native `currency`. Exchange-rate conversion for reporting (e.g., a USD dashboard showing the EUR-denominated contract value) is not addressed here. The multi-currency exchange-rate feature is planned under a separate AOS spec; the field is forward-compatible because it already stores `currency` alongside `value_cents`.

3. **Renewal notification email template** — The renewal email body is a hardcoded plaintext string in the initial implementation (subject: `"Contract {contract_number} expires in {days} days"`, body: contract title, start/end dates, value). Once QUO-002 lands, an admin could upload an `module="contract"` notification template; wiring that substitution into the notification path is a follow-up.

4. **Auto-expiry on `end_date` crossing** — The ticket does not auto-transition `active → expired` when the clock passes `end_date`. That would require the renewal-check loop to also perform stage transitions. The assumption is that the stage transition is driven by an admin or by QUO-003/QUO-005 business logic. An auto-expiry enhancement can be added as a follow-up without schema change (the `end_date` field already exists).

5. **Number format year** — `CON-{year}-{seq:05d}` uses the UTC year at creation time. If the counter is shared across years (i.e., not reset per year), year 2026 might yield `CON-2026-00001` and year 2027 might yield `CON-2027-00002`. This matches the existing invoice number behavior at `invoices.py:83–92` and is considered acceptable.

6. **`max_notice_days_to_scan = 90`** — The scan upper bound in `check_expiring_contracts()` is a hardcoded constant. If a contract has `renewal_notice_days > 90`, it will never be notified. An env-configurable `AOS_CONTRACTS_MAX_NOTICE_SCAN_DAYS` setting can be added if operators need longer windows; the default of 90 is consistent with typical contract notice periods and keeps the GSI scan range bounded.
