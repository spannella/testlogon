# STU-004 — CRM Security Groups — record-level access control

**Type:** Feature  **Priority:** P1  **Estimate:** 3 days  
**Ticket source:** `docs/suitecrm/CRM_SECURITY_STUDIO_TICKETS.md`, section "STU-004"

---

## 1. Summary & Goal

STU-004 implements CRM record-level Security Groups: a DynamoDB-backed membership
system that links arbitrary CRM records (tickets, contacts, future party-model
entities) to named groups, and enforces that membership in list/get service
call sites.

When the feature flag is **off** (`CRM_ACL_ENABLED=0`, the default), every
`user_can_access_record` call returns `True` and the management router returns
404. The platform is byte-for-byte unchanged from the caller's perspective.

When the flag is **on**, a record that has at least one security group assigned
is visible only to: (a) authenticated users who are a member of at least one of
those groups, (b) users with `role >= ADMIN`, or (c) ROOT users. Records with
no groups assigned remain accessible to all authenticated users (open access).

This ticket is **distinct** from the compute Security Groups feature at
`app/routers/security_groups.py` (prefix `/ui/compute/security-groups`,
`app/core/settings.py:2297-2300`), which manages EC2/K8s firewall rules. The
CRM Security Groups concept shares the name but has a completely separate
DynamoDB table, router prefix, and service module.

## 3. Data Model

All rows live on the single `crm_security_groups` DynamoDB table introduced by
STU-001. The table schema follows the single-table pattern used throughout the
codebase (e.g. `tickets` table at `app/services/tickets.py:164-169`).

### 3.1 Row types

**Group metadata** (`sk = "META"`):

```
pk           : "GROUP#{group_id}"   (S)
sk           : "META"               (S)
group_id     : str  (uuid4 hex, e.g. "grp_<12 hex>")
name         : str
description  : str
owner_sub    : str  (creator's user_sub)
created_at   : int  (now_ts(), numeric)
is_global    : bool (True → visible to any ADMIN/ROOT in list responses)
```

**Group membership** (`sk = "MEMBER#{user_sub}"`):

```
pk          : "GROUP#{group_id}"    (S)
sk          : "MEMBER#{user_sub}"   (S)
user_sub    : str
added_by_sub: str
added_at    : int  (now_ts(), numeric)
can_edit    : bool (True → member may assign/unassign records for this group)
```

**Record assignment** (`sk = "RECORD#{entity_type}#{record_id}"`):

```
pk              : "GROUP#{group_id}"                   (S)
sk              : "RECORD#{entity_type}#{record_id}"   (S)
entity_type     : str  (e.g. "ticket", "contact")
record_id       : str  (e.g. "tkt_abc123")
record_ref      : str  (f"{entity_type}#{record_id}", GSI PK)
assigned_by_sub : str
created_at      : int  (now_ts(), numeric; GSI SK)
```

### 3.2 GSI: `by-record`

- **PK**: `record_ref` (S) — value `"{entity_type}#{record_id}"`
- **SK**: `created_at` (N)
- **`attr_types`**: `{"created_at": "N"}` — required in the `TableDef` in
  `scripts/local-ddb-init.py` to avoid `ValidationException` at query time
  (see CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha).

This GSI is used by `get_groups_for_record` to find all groups that have a
given record assigned, without scanning the entire table.

### 3.3 Key derivation helpers (in `crm_security_groups.py`)

```python
def _group_pk(group_id: str) -> str:

def _meta_key(group_id: str) -> dict:

def _member_sk(user_sub: str) -> str:

    return f"RECORD#{entity_type}#{record_id}"

def _record_ref(entity_type: str, record_id: str) -> str:
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Group creation

`create_group` generates `group_id = "grp_" + uuid4().hex[:12]`. The META row
is written with a `put_item` conditional on `attribute_not_exists(pk)` to avoid
overwriting a colliding ID (collision probability at `uuid4().hex[:12]` space is
negligible but the guard costs nothing). On success, `audit_event` is called
with `event="crm_sg.group.created"`, `user_sub=actor_sub`,
`group_id=group_id`.

### 5.2 Group deletion cascade

`delete_group` queries the group's full partition (all `sk` values for
`pk = "GROUP#{group_id}"`) and issues a DynamoDB `batch_writer` delete for all
items (META + all MEMBER# + all RECORD# rows). The cascade is idempotent —
deleting a non-existent group raises `GroupNotFound(HTTPException 404)` only
when the META item is absent.

### 5.3 Record assignment — `entity_type` values

Supported `entity_type` strings at this ticket's scope:
- `"ticket"` — record_id is a ticket_id from `app/services/tickets.py` (format
  `"tkt_<12hex>"`, `app/services/tickets.py:430`)
- `"contact"` — record_id is a user_sub string from `T.contacts`
  (`app/core/tables.py:102`)

Future CRM entities (party model from PTY tickets, opportunities from OPP
tickets) will use their own `entity_type` strings. The service layer accepts any
non-empty string for `entity_type` — no allowlist at the service level. The
router validates that `entity_type` is non-empty via the Pydantic model.

### 5.4 `user_can_access_record` — fail-open on DDB error

If `get_groups_for_record` or `get_member_group_ids` raises an exception (e.g.
DDB endpoint unreachable), `user_can_access_record` catches the exception, logs
a warning, and returns `True`. This ensures a DDB degradation does not block all
CRM access. The fail-open behavior is documented in the service module's
docstring.

### 5.5 Open-access rule

A record with zero RECORD# rows in the `crm_security_groups` table — i.e.
`get_groups_for_record` returns `[]` — is accessible to every authenticated
user regardless of group membership. This allows admins to incrementally assign
security groups to sensitive records without a big-bang migration.

### 5.6 ADMIN/ROOT bypass

`user_can_access_record` accepts a `role` parameter. Any call where
`role in {Role.ADMIN, Role.ROOT}` returns `True` immediately without touching
DDB. Route handlers that call the enforcement helper should pass
`role=user.role` where `user` is the `AuthenticatedUser` from their auth dep.

### 5.7 Enforcement injection into tickets

In `app/routers/tickets.py`, the GET single-ticket handler (`get_ticket` at
`app/routers/tickets.py:900`, decorated `@router.get("/{ticket_id}")`, which takes
`_ctx: dict = Depends(require_ui_session)` and `user: AuthenticatedUser =
Depends(get_authenticated_user)` and already performs a `_can_access_ticket(...)`
check) will additionally call:

```python
from app.services.crm_security_groups import user_can_access_record
# user_sub comes from _ctx["user_sub"]; role comes from user.role
if not user_can_access_record(_ctx["user_sub"], "ticket", ticket_id, role=user.role):
    raise HTTPException(403, "Access denied by CRM security group")
```

The list-tickets handler (`list_tickets` at `app/routers/tickets.py:778`,
decorated `@router.get("")`) calls `filter_records_by_access` on the returned list
before serializing to the `TicketEnvelope`/`TicketOut` shape, passing
`record_id_field="ticket_id"`. (Note: there is no GET single-ticket handler near
line 707 — line 707 is the unrelated `replay_admin_kyc_sync_deadletter` admin
handler; the real injection point is line 900.)

Both injection sites are wrapped in `if S.crm_acl_enabled:` guards so they
compile to a single boolean test and are branch-free when the flag is off.

### 5.8 Enforcement injection into contacts

In `app/routers/contacts.py`, `list_contacts` (line 63) applies
`filter_records_by_access(ctx["user_sub"], "contact", contacts,
record_id_field="contact_id")` after fetching. Individual contact GET endpoints
(if any) call `user_can_access_record` directly.

### 5.9 Membership cache invalidation

The 30-second per-user membership cache (`_member_cache: dict[str, tuple[list, int]]`
where the tuple is `(group_ids, fetched_at_ts)`) is invalidated for a specific
`user_sub` by `add_member` and `remove_member`. Invalidation sets the entry to
`([], 0)` which forces a fresh DDB scan on the next `get_member_group_ids` call.
The cache is process-local (not cross-replica). With a 30-second TTL, stale
membership windows are acceptable for CRM access decisions.

### 5.10 `member_count` and `record_count` in `CrmSecurityGroupOut`

The `GET /{group_id}` endpoint's `get_group_with_members` helper queries the
full group partition (all items with `pk = "GROUP#{group_id}"`), counts rows
with `sk.startswith("MEMBER#")` and `sk.startswith("RECORD#")`, and populates
the `member_count` / `record_count` fields. This avoids a separate count query.

### 5.11 `list_groups` scan strategy

`list_groups` performs a DynamoDB scan with a `FilterExpression` of
`sk = :meta` (value `"META"`) to return only group-definition rows and skip
MEMBER# / RECORD# rows. Since `FilterExpression` does not reduce the page size
fetched from DDB (CLAUDE.md gotcha), the scan loops via `LastEvaluatedKey` up
to a hard cap of 2000 items before returning. For the expected number of CRM
security groups (tens to low hundreds), this is not a performance concern.
If `is_global` is provided, an additional Python-side filter is applied on the
returned items.

### 5.12 Route ordering in `app/main.py`

The router registration `app.include_router(crm_security_groups_router)` must
appear after STU-001's settings and table checks but can be in any order
relative to other CRM routers since all live under distinct prefixes.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 dev/prod parity

All DDB operations in `crm_security_groups.py` use `T.crm_security_groups`,
which is the `_FloatSafeTable` proxy (`app/core/tables.py:29-67`) wrapping
either moto (dev) or real DynamoDB (prod). There are **no** `if S.dev_mode`
branches in any business logic path. The `_safe_table` wrapper coerces Python
`float` to `Decimal` before writes, so `created_at` (int) and `added_at` (int)
are stored correctly in both environments.

### 7.2 Idempotency

- `add_member`: `put_item` is unconditional — repeated calls for the same
  `(group_id, user_sub)` overwrite the existing row with the same or updated
  `can_edit` value. This is intentional (supports updating `can_edit`).
- `assign_record`: `put_item` is unconditional — repeated assignments are
  idempotent and harmless.
- `remove_member` / `unassign_record`: `delete_item` on a non-existent key is a
  no-op in DynamoDB. No conditional expression needed.
- `delete_group`: guarded by a `get_item` check for the META row. If the META
  row has already been deleted (concurrent delete), the function raises
  `GroupNotFound` (404).

### 7.3 Security

- All management endpoints require `role >= ADMIN` (create/list/get/add-member/
  assign-record) or `role == ROOT` (delete-group/remove-member). This uses
  `app/auth/policy.require_admin_or_root` and `require_root` directly — no new
  role abstraction is introduced.
- CSRF is enforced on all non-GET mutating endpoints via
  `enforce_cookie_csrf(request)` from `app/auth/policy.py:71`.
- `user_can_access_record` is a pure read operation (no side effects). It does
  not log or audit access denials to avoid high-volume alert noise; enforcement
  silently returns a 403 from the caller's perspective.
- Group IDs use `uuid4().hex[:12]` prefixed with `"grp_"` — not sequentially
  guessable.
- The `record_ref` GSI is queried by entity-type-namespaced compound key
  (`"ticket#tkt_abc123"`) so a user cannot probe group membership by guessing
  record IDs across entity types.
- Audit events are emitted for every mutating operation (create, delete,
  add_member, remove_member, assign_record, unassign_record). The
  `audit_event` call at `app/services/alerts.py:644` writes to `T.alerts`
  via the existing pipeline — no new audit table is required.

## 8. Backward Compatibility & Migration

### 8.1 Zero migration required

With `CRM_ACL_ENABLED=0`, the platform behaves byte-for-byte identically to the
pre-STU-004 state. No existing records in any table are modified. No existing
API contracts change. No frontend changes are required to ship this ticket.

### 8.2 Enabling the flag on an existing deployment

When `CRM_ACL_ENABLED` is flipped to `"true"` on a running system:

1. `just restart` (dev) or a rolling deploy (prod) creates the
   `crm_security_groups` table via `local-ddb-init.py` (dev) or a Terraform/
   CloudFormation table provisioning step (prod).
2. All existing tickets and contacts have zero RECORD# rows → open-access rule
   applies → no users lose access.
3. Admins can then assign records to security groups incrementally. Only records
   that have at least one RECORD# row become restricted.

### 8.3 Existing tests

The enforcement guards in `app/routers/tickets.py` and `app/routers/contacts.py`
are wrapped in `if S.crm_acl_enabled:` guards. All existing pytest test files
run with `S.crm_acl_enabled = False` (the default) and the guards are never
entered. The existing 1070 Playwright E2E tests are similarly unaffected.

## 10. Open Questions / Assumptions

1. **`can_edit` semantics**: The spec defines `can_edit: bool` on membership rows
   (a member who can assign/unassign records for that group) but STU-004 does not
   currently expose a user-facing endpoint for non-admin members to perform
   assignment. The `can_edit` field is stored for future use (a planned follow-up
   that adds a user-scoped `POST /ui/crm/security-groups/{id}/records` endpoint).
   For this ticket, only ADMIN/ROOT can assign records regardless of `can_edit`.

2. **Cross-tenant scoping**: `AuthenticatedUser.tenant_id` (`app/auth/deps.py:133`)
   is available but not used in group membership evaluation. Groups are
   implicitly scoped to the deployment. Multi-tenant isolation (if required by
   an ENTERPRISE ticket) would add a `tenant_id` partition prefix; this is out
   of scope for STU-004.

3. **Performance of `filter_records_by_access` at scale**: Each unique `record_id`
   in a list response triggers one GSI query. For a 100-ticket list, this is up
   to 100 parallel DDB reads. In production with a large group matrix, a bulk
   "check which of these record_refs have groups" query using `batch_get_item`
   could reduce this; that optimization is deferred to a follow-up. For now the
   sequential-query approach is acceptable given typical CRM list sizes.

4. **`is_global` group behavior**: Global groups (`is_global=True`) are visible
   to any ADMIN/ROOT in list responses but are **not** automatically granted
   access to all records. `is_global` is purely a display/discovery property.
   The access-control semantics are unchanged: a user must be an explicit member
   of the group that has the record assigned.

5. **Party model (PTY tickets)**: The STU-004 ticket description references
   "contacts via the party model planned in PTY tickets." Since PTY tickets are
   not yet implemented, the injection point for the party/contact access check
   is currently in `app/routers/contacts.py` (the simple contacts router). When
   PTY tickets ship and introduce a new party service, those service functions
   will call `user_can_access_record` / `filter_records_by_access` using
   `entity_type="contact"` or a new entity type like `"party"`.
