# CMP-006 — Web-to-lead capture form

**Type:** Feature  **Priority:** P1  **Estimate:** 2d  
**Area:** Campaigns & Email Marketing  
**Source:** `docs/suitecrm/CRM_CAMPAIGNS_EXTRA_TICKETS.md` § CMP-006

---

## 1. Summary & Goal

SuiteCRM's web-to-lead feature lets any public website embed an HTML form whose POST creates a Contact/Lead record in the CRM and optionally adds the submitter to a target list for ongoing campaign nurturing. This ticket delivers that capability for testlogon.

The deliverables are:

1. **A new `web_lead_captures` DynamoDB table** — stores each form submission as an independent, externally-originating record. When the LED-001 leads table is deployed (`S.leads_enabled` is on), the capture service writes to `T.leads` using the LED-002 `LeadCreateIn` model; otherwise it falls back to `T.web_lead_captures`. Both paths produce the same `WebLeadCaptureOut` response shape so the caller is unaffected by which backend table was used.

2. **`POST /ui/marketing/leads/capture`** — a fully public (no auth) FastAPI endpoint that accepts a form submission, silently drops bot traffic via a honeypot field, writes the capture, optionally adds the submitter to a contact list (MKT-007 `add_member`), and returns a minimal acknowledgment. Rate-limiting by IP address prevents abuse.

3. **`GET /ui/admin/marketing/leads`** — an admin-only list endpoint for reviewing captured leads, filterable by campaign.

4. **An optional auto-responder email** — when `S.web_to_lead_autoresponder_enabled` is on, the service sends a confirmation email to the submitter using the existing `send_alert_email` primitive (`app/services/alerts.py:459`).

Everything is additive and gated on `S.web_to_lead_enabled` (default `False`). With the flag off every new endpoint returns 404 and all new service functions are dormant. Existing contacts, billing, messaging, and campaign surfaces are byte-for-byte unchanged.

### 4.2 Service module: `app/services/web_lead_capture.py`

New file. All functions are synchronous (no async), consistent with other service files in the project (e.g., `app/services/cart_reminders.py`).

```python
def _require_web_lead_enabled() -> None:
    """Raise HTTPException(404) when S.web_to_lead_enabled is False."""
    if not S.web_to_lead_enabled:
        raise HTTPException(404, "Not found")

def _rate_limit_capture(ip: str) -> None:
    """Apply per-IP rate limit using _bucket_limit.
    
    Imports _bucket_limit from app.services.rate_limit (local import to avoid
    circular dependency). Key: f"ip#{ip}", sid="rl#web_lead_capture",
    max_n=S.web_to_lead_rate_limit_per_ip_per_hour, win=3600.
    Raises HTTPException(429) when limit exceeded.
    """

def create_capture(
    data: WebLeadCaptureIn,
    *,
    source_ip: str = "",
    user_agent: str = "",
) -> WebLeadCaptureOut:
    """Write one web-lead capture row.
    
    1. _require_web_lead_enabled()
    2. Honeypot check: if data.honeypot is non-empty, return a fake
       WebLeadCaptureOut(capture_id="bot", status="received", created_at=0)
       without any DDB write. Response shape is identical to prevent bot
       enumeration.
    3. _rate_limit_capture(source_ip)
    4. Normalise email via normalize_email() (app/core/normalize.py:60).
    5. Generate capture_id = uuid4().hex[:20].
    6. Build item dict.
    7. Write to T.leads if S.leads_enabled, else T.web_lead_captures.
       When writing to T.leads, use LED-002 row schema:
         pk=f"LEAD#{capture_id}", sk="META", lead_source="web_form",
         status="new", and all standard lead fields.
       When writing to T.web_lead_captures, use the schema in §3.1.
    8. If data.contact_list_id and S.marketing_campaigns_enabled:
       best-effort call to add_member(owner_id="system", list_id=...,
       party_id=capture_id) from app.services.marketing_lists
       (lazy import; skip silently if module not available).
    9. If S.web_to_lead_autoresponder_enabled: best-effort call to
       _send_autoresponder(data.email, data.first_name).
   10. best-effort audit_event("web_lead.captured", "anonymous",
         capture_id=capture_id, campaign_id=data.campaign_id or "")
   11. Return WebLeadCaptureOut(capture_id=capture_id,
         status="received", created_at=ts).
    """

def _send_autoresponder(to_email: str, first_name: str) -> None:
    """Send a confirmation email to the submitter.
    
    Renders subject from S.web_to_lead_autoresponder_subject (plain string,
    no merge fields at this stage — CMP-008 personalisation is a future
    extension).
    Renders body using _render() from notification_templates.py:245 with
    vars {"first_name": first_name, "platform_name": get_branding().platform_name}.
    NOTE (decision D6, 2026-06-13): `{{platform_name}}` is sourced from the
    canonical root-admin-configurable branding entity via the cached
    `get_branding()` helper — NOT from a CMP-006-local setting and NOT from
    `S.platform_name` (which does not exist). `get_branding()` resolves the
    `PLATFORM#BRANDING` settings row and falls back to the `PLATFORM_NAME` env
    default, so `{{platform_name}}` always resolves and never raises
    `AttributeError`. The earlier bespoke `web_to_lead_platform_name` setting is
    superseded (§3.3). Import lazily, e.g.
    `from app.services.branding import get_branding` (the helper + entity are
    formalized by a small dedicated branding ticket — see §6).
    Body template:
      "Hi {{first_name}},\n\nThank you for reaching out to {{platform_name}}."
      "\nWe will be in touch shortly.\n"
    Calls send_alert_email([to_email], subject, body_text) from alerts.py:459.
    All exceptions swallowed (best-effort).
    """

def list_captures(
    campaign_id: Optional[str] = None,
    limit: int = 50,
    cursor: Optional[str] = None,
) -> WebLeadListOut:
    """List web-lead captures for admin review.
    
    When campaign_id is provided: query ByCampaignCreatedAt GSI on
    T.web_lead_captures, KeyConditionExpression on GSI1PK=CAMPAIGN#{id},
    ScanIndexForward=False (newest first), Limit=limit.
    When campaign_id is absent: query AllCapturesCreatedAt GSI on
    T.web_lead_captures, KeyConditionExpression on GSI2PK="ALL_CAPTURES",
    ScanIndexForward=False, Limit=limit.
    When S.leads_enabled: query T.leads BySource GSI (LED-001 GSI3PK=
    SOURCE#web_form), ScanIndexForward=False, Limit=limit.
    Cursor encode/decode via app.core.cursor (consistent with other list
    endpoints in the project).
    Returns WebLeadListOut.
    """
```

**Public capture endpoint (no auth):**

```python
@public_router.post(
    "/ui/marketing/leads/capture",
    response_model=WebLeadCaptureOut,
    status_code=200,
)
async def capture_web_lead(
    request: Request,
    body: WebLeadCaptureIn,
) -> WebLeadCaptureOut:
    ip = request.headers.get("x-forwarded-for", "").split(",")[0].strip()
    ua = request.headers.get("user-agent", "")[:256]
    return create_capture(body, source_ip=ip, user_agent=ua)
```

The `public_router` is an `APIRouter` with no `dependencies` argument — this endpoint must be reachable without any auth cookie or token. It is registered in `app/main.py` with `app.include_router(public_router)` (no prefix override; the `/ui/marketing/leads/capture` path is self-contained).

**Admin list endpoint (require admin role):**

```python
@router.get(
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Honeypot bot rejection

The `honeypot` field must be present in the HTML form as a hidden field with `display:none` CSS. A browser user filling out the form will never see or fill it. Bots that blindly fill all fields will populate it, triggering the silent rejection path. The response returned for a non-empty honeypot is structurally identical to a successful capture (`{"capture_id": "bot", "status": "received", "created_at": 0}`) so the bot receives no signal that it was detected. No DDB write is performed for honeypot-triggered requests.

### 5.2 Per-IP rate limiting

`_rate_limit_capture` calls `_bucket_limit(f"ip#{ip}", "rl#web_lead_capture", S.web_to_lead_rate_limit_per_ip_per_hour, 3600)` from `rate_limit.py:60`. The rate bucket lives in `T.sessions`. On limit breach the function raises `HTTPException(429, "Too many requests")`. The bucket is reset each hour (sliding-window semantics). Missing or empty `X-Forwarded-For` falls back to the literal string `"ip#unknown"` — all such requests share one bucket, which is intentional (conservative for anonymous origins).

### 5.3 Email normalisation

`normalize_email(data.email)` (from `app/core/normalize.py:60`) is called before writing. **Important**: the live `normalize_email` implementation raises `HTTPException(400, "Invalid email")` when the input contains no `@` or exceeds 254 characters — it is **not** permissive on failure (see §10, assumption 6). `create_capture` must therefore wrap the call in a `try/except Exception` block and fall back to storing the raw value unchanged when normalisation raises, in order to keep the permissive capture philosophy (never discard a submission due to validation strictness).

### 5.4 Contact list add (MKT-007 integration)

When `data.contact_list_id` is non-empty and `S.marketing_campaigns_enabled` is `True`, `add_member` is called with `owner_id="system"` (the capture is not owned by any specific platform user), `list_id=data.contact_list_id`, and `party_id=capture_id`. `add_member` is idempotent (conditional-put); duplicate submissions for the same email will generate different `capture_id` values but can end up as separate list members. Deduplication by email is a LED-004 concern (duplicate detection via `ByEmail` GSI). The `add_member` call is wrapped in a broad `try/except` — list-add failure never fails the capture.

### 5.5 Auto-responder email

`_send_autoresponder` is called only when `S.web_to_lead_autoresponder_enabled` is `True`. It calls `send_alert_email` at `alerts.py:459` which in dev mode writes to `S.dev_email_log` and in prod sends via SES. The call is wrapped in `try/except` — email failure never fails the capture. The auto-responder does not currently check opt-out state (the submitter has no `user_sub` and therefore no opt-out record); if a future enhancement links a capture to a platform user, `is_user_opted_out` at `cart_reminders.py:95` should be consulted before sending.

### 5.6 `S.leads_enabled` write routing

At write time, `create_capture` checks `S.leads_enabled` once and writes to exactly one table. Reads (admin list endpoint) similarly branch on `S.leads_enabled`. When the flag transitions from `False` to `True`, historic rows in `T.web_lead_captures` are not migrated; the admin list endpoint only queries the active backend. A migration script (`scripts/migrate_web_leads_to_leads_table.py`) is out of scope for this ticket but noted in §10.

### 5.7 Large-volume capture flood

If a single IP exhausts the per-hour bucket and continues posting, every subsequent request hits the 429 branch immediately after the rate-limit check — no DDB write is attempted. The `T.sessions` table rate-limit row acts as the gate; no additional infrastructure (WAF, CloudFront) is required for this ticket.

### 5.8 Missing MKT-007 or LED-001 at runtime

`add_member` is resolved via a lazy import inside `create_capture`:
```python
try:
    from app.services.marketing_lists import add_member as _add_member
    _add_member(...)
except (ImportError, Exception):
    pass
```
If `app/services/marketing_lists.py` does not yet exist (MKT-007 not deployed), the `ImportError` is silently swallowed. Same pattern for `T.leads` — the flag `S.leads_enabled` will be `False` until LED-001 is deployed, so the `T.leads` branch is never reached.

### 5.9 Admin `list_captures` — no `campaign_id` filter

When `campaign_id` is absent and `S.leads_enabled` is `False`, the query falls back to the `AllCapturesCreatedAt` GSI on `T.web_lead_captures` (GSI2PK = constant `"ALL_CAPTURES"`). This is a fan-out anti-pattern for very high volumes but is acceptable for CRM admin review screens; the `limit` cap (max 200) prevents unbounded reads. The `cursor` parameter carries the DynamoDB `LastEvaluatedKey` encoded via `app.core.cursor`.

### 5.10 GDPR / data-minimisation

The `source_ip` field stores the IP with the last octet zeroed for IPv4 (e.g., `"1.2.3.0"`) before writing to DDB. For IPv6 the last 80 bits are zeroed. This anonymises the IP while preserving enough geographic information for abuse analysis. `user_agent` is capped at 256 characters. Both truncations are applied in `create_capture` before DDB write. The `ttl_epoch` field on every capture row ensures automatic DDB TTL expiry after `S.web_lead_captures_ttl_seconds` (default 365 days), satisfying typical GDPR data-retention windows.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

`create_capture` contains no `if S.dev_mode` branch. The email auto-responder delegates entirely to `send_alert_email` at `alerts.py:459`, which already branches internally on `S.dev_mode` to write to the dev email log instead of calling SES. The DDB write uses the same `T.web_lead_captures` handle in both environments — dev resolves to DynamoDB Local (port 8001 via `DDB_ENDPOINT_URL` in `.env.local`); prod resolves to real DynamoDB. SECOPS-007 parity is automatic.

### Idempotency

Each call to `create_capture` generates a fresh `capture_id = uuid4().hex[:20]`. Multiple submissions from the same email address create separate capture rows (by design — each submission is a distinct inbound lead event). Idempotency is not required on the capture path because there is no natural deduplication key provided by the submitter. Deduplication by email address is a LED-007/LED-009 concern: LED-007 adds the `ByEmail` GSI (`GSI4PK=EMAIL#{normalized_email}`) to `T.leads`; LED-009 builds the `find_duplicates` and merge service on top of it.

`add_member` (MKT-007) is idempotent — duplicate calls for the same `(list_id, party_id)` pair use a conditional put and return the existing row without incrementing `member_count` (`docs/ofbiz/specs/MKT-007.md:311`).

### Security

- **No auth on capture endpoint**: intentional — the form is embedded on public websites. Rate limiting by IP (§5.2) and honeypot (§5.1) are the abuse mitigations.
- **No CSRF token requirement**: non-cookie-auth requests skip CSRF validation per the CSRF design at `app/services/sessions.py:429` (`if session_cookie and method.upper() not in ("GET", "HEAD", "OPTIONS"):`). The public capture endpoint carries no cookies, so `session_cookie` is absent and CSRF validation is bypassed. Note: the CSRF guard lives in `app/services/sessions.py`, not `app/auth/deps.py`.
- **Admin list endpoint**: gated on `Role.ADMIN` or `Role.ROOT` using the inline role check consistent with other admin endpoints. CSRF applies because `require_ui_session` is used and the request may carry the `ui_session` cookie.
- **IP anonymisation**: last octet zeroed before DDB write (§5.10). The full IP is never persisted.
- **Email validation**: `normalize_email` is applied but is permissive (stores raw on failure). The `email` field max length is 254 characters (RFC 5321 limit). Overly-long values are rejected by Pydantic validation at the router layer before any service call.
- **`honeypot` field**: never stored in DDB. Never logged. Pydantic max length is intentionally omitted so extremely long values still trigger the honeypot path rather than a 422 validation error that would reveal the field's purpose.
- **Audit trail**: `audit_event("web_lead.captured", "anonymous", ...)` at `alerts.py:644` writes a compliance record to `T.alerts`. The `user_sub="anonymous"` value follows the pattern used in other unauthenticated public endpoints.

## 8. Backward Compatibility & Migration

### Zero-impact with flag off

With `WEB_TO_LEAD_ENABLED=0` (the default):
- The `WebLeadCaptures` table is created by `scripts/local-ddb-init.py` but receives no writes.
- `app/routers/web_lead_capture.py` is registered in `app/main.py` but every handler calls `_require_web_lead_enabled()` first, which raises 404.
- No existing route, service, or model is modified.

### Table creation in production

The `WebLeadCaptures` DynamoDB table must be created before the code that references `T.web_lead_captures` is deployed. Since `S.web_to_lead_enabled` defaults to `False`, the handle is initialised at import time but no DDB calls are made until the flag is turned on. The deployment order is:
1. Deploy code (table handle is lazy, flag is off — safe).
2. Create DDB table via `aws dynamodb create-table` (or CloudFormation).
3. Set `WEB_TO_LEAD_ENABLED=1` in the deployment environment.

### Existing MKT-011 router file

If MKT-011 (`app/routers/marketing_campaigns.py`) has not yet been deployed, CMP-006 creates a standalone `app/routers/web_lead_capture.py`. When MKT-011 later ships, the route handlers in `web_lead_capture.py` should be folded into `marketing_campaigns.py` and the standalone file removed. This consolidation is a one-time, non-breaking migration (the URL paths do not change).

### LED-001 migration path

When LED-001 is deployed and `S.leads_enabled` is set to `True`, new captures are written to `T.leads`. Existing rows in `T.web_lead_captures` are not touched. If admin tooling needs to present a unified view, the `list_captures` function can be extended to query both tables and merge results; that extension is out of scope for this ticket.

## 10. Open Questions / Assumptions

1. **CAPTCHA integration**: `S.web_to_lead_captcha_enabled` is declared but not wired in this ticket. The intended integration is Google reCAPTCHA v3 or hCaptcha: the browser form would send a `captcha_token` alongside the form body, and the backend would verify it against the provider API. This is deferred to a follow-up ticket to keep CMP-006 scoped. The setting name is reserved now to avoid a later rename.

2. **`add_member` owner_id for external captures**: MKT-007 specifies `add_member(owner_id, list_id, party_id)` where `owner_id` is a platform `user_sub`. External captures have no owning user sub. This spec passes `owner_id="system"` as a sentinel. MKT-007's implementation must either accept `"system"` as a valid owner or the contact-list admin must be specified in the capture form config. The MKT-007 spec does not address this case and it should be clarified before implementation.

3. **Deduplication by email**: Multiple submissions from the same email address create distinct capture rows. LED-007 (`docs/suitecrm/CRM_LEADS_TICKETS.md:275`) adds a `ByEmail` GSI (`GSI4PK=EMAIL#{normalized_email}` / `GSI4SK=created_at(N)`) to `T.leads`; LED-009 adds `find_duplicates` / merge service functions that use this GSI. Until those tickets ship, the admin must manually identify duplicates via the list endpoint. Note: LED-004 is "Lead source tracking & attribution field" — it does not introduce the `ByEmail` GSI.

4. **LED-001 `create_lead_from_submission` reuse vs. inline**: LED-005 (`docs/suitecrm/CRM_LEADS_TICKETS.md:218`) specifies `create_lead_from_submission` in `app/services/leads.py` for questionnaire-to-lead capture (not LED-003, which only provides basic CRUD). CMP-006 could call this function instead of inline-writing to `T.leads`. This is preferred if LED-005 ships first; the service design above notes the branch with a comment for the implementer to replace with the LED-005 call. Note: LED-003 (`CRM_LEADS_TICKETS.md:139`) provides `create_lead`, `get_lead`, `list_leads`, `update_lead`, `delete_lead` — it does not define `create_lead_from_submission`.

5. **`notify_owner` on capture**: SuiteCRM sends a notification email to the campaign owner when a new lead is captured. This is not in the current scope; it would require resolving a campaign-owner `user_sub` from `campaign_id` (MKT-004 `get_campaign` lookup) and calling `write_alert` or `send_alert_email`. Deferred to a follow-up.

6. **`normalize_email` raises on failure** (`CORRECTED`): The live implementation at `app/core/normalize.py:60` raises `HTTPException(400, "Invalid email")` when the input lacks `@` or exceeds 254 characters — it is NOT permissive. `create_capture` MUST wrap the call in `try/except Exception` and fall back to the raw value; without this guard, an invalid email will abort the capture with a 400 instead of recording it.

7. **Frontend embed form**: This spec does not include a React page for the capture form. The intended usage is that operators embed the form on an external website. A minimal React component (`frontend/src/pages/marketing/LeadCaptureForm.tsx`) that POSTs to `/ui/marketing/leads/capture` could be added as a follow-up, or operators can write their own HTML form against the API.

### Cross-ticket reconciliation (decision D6, 2026-06-13)

Per `docs/CROSS_TICKET_AUDIT.md §D6`: the canonical source of `platform_name` (and
basic branding) is a root-admin-configurable **`PLATFORM#BRANDING`** settings row
`{name, logo_url, support_email}`, exposed via root-only `GET/PUT /ui/admin/branding`,
with env values (`PLATFORM_NAME`, `PLATFORM_LOGO_URL`, `PLATFORM_SUPPORT_EMAIL`) as
defaults. A cached `get_branding()` helper resolves the row (falling back to env), and
templates read `{{platform_name}}` from `get_branding().platform_name`.

CMP-006 is migrated to consume this canonical helper: the auto-responder body
(`_send_autoresponder`, §4.2) now sources `{{platform_name}}` from
`get_branding().platform_name` instead of the bespoke `web_to_lead_platform_name`
setting, which is **deprecated/removed** (§3.3, §6, verification-log row 30). A small
dedicated branding ticket (e.g. a `PLT-`/`CFG-branding` spec) should formalize the
`PLATFORM#BRANDING` entity and the `/ui/admin/branding` router at build time; until
then `get_branding()` falls back to the `PLATFORM_NAME` env default, so
`{{platform_name}}` always resolves and no `AttributeError` is raised.
