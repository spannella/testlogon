## 1. Summary & Goal

ACT-001 is pure scaffolding. It delivers the master feature flag `crm_activities_enabled`, five module-level sub-flags, five new settings keys for DynamoDB table names, five new DynamoDB table definitions (with all required GSIs and numeric-key `attr_types`), and five new table handles in `app/core/tables.py`. No router, no service logic, no UI is introduced; ACT-001 is the prerequisite every downstream ACT ticket (ACT-002 through ACT-010) depends on.

The goal is that when the flag is off (the default) the platform is byte-for-byte unchanged: no new routes exist, no background workers start, and no existing table, service, or endpoint is touched. When the flag is on, the table handles are available for subsequent tickets to use.

## 3. Data Model

ACT-001 provisions five new DynamoDB tables. All follow the single-table `TableDef` pattern from `scripts/local-ddb-init.py`. Every numeric GSI sort key must include `attr_types={"<key>": "N"}` to avoid `ValidationException` at query time.

### 3.1 `crm_tasks`

Stores standalone CRM task records (subject, status, priority, due date, assignee). Used by ACT-008.

| Layer | Value |
|---|---|
| Partition key | `user_sub` (S) — the owning/creating user |
| Sort key | `sk` (S) — value: `TASK#{inverted_due_ts:013d}#{task_id}` |

**GSI `ByStatus`** — lists all tasks for a given status, ordered by due date ascending:

| Attr | Value | Type |
|---|---|---|
| GSI1PK | `STATUS#{status}` | S |
| GSI1SK | `due_date_ts` (Unix epoch) | N |

`attr_types={"GSI1SK": "N"}` required.

**GSI `ByAssignee`** — lists all tasks assigned to a given user, ordered by due date:

| Attr | Value | Type |
|---|---|---|
| GSI2PK | `ASSIGNEE#{assignee_sub}` | S |
| GSI2SK | `due_date_ts` (Unix epoch) | N |

`attr_types={"GSI2SK": "N"}` required.

Full `attr_types` for this table: `{"GSI1SK": "N", "GSI2SK": "N"}`.

Item attributes (informational for ACT-008, not constrained by this ticket):  
`task_id`, `user_sub`, `subject`, `description`, `status`, `priority`, `due_date_ts`, `assignee_sub`, `linked_entity_type`, `linked_entity_id`, `created_at`, `updated_at`.

### 3.2 `crm_notes`

Stores standalone CRM note records with optional S3 file attachment and optional linked CRM entity. Used by ACT-010.

| Layer | Value |
|---|---|
| Partition key | `user_sub` (S) |
| Sort key | `sk` (S) — value: `NOTE#{inverted_ts:013d}#{note_id}` |

**GSI `ByEntity`** — lists all notes linked to a given CRM entity, ordered by creation time:

| Attr | Value | Type |
|---|---|---|
| GSI1PK | `ENTITY#{linked_entity_type}#{linked_entity_id}` | S |
| GSI1SK | `created_at` (Unix epoch) | N |

`attr_types={"GSI1SK": "N"}` required.

Item attributes: `note_id`, `user_sub`, `body`, `attachment_s3_key`, `attachment_filename`, `attachment_content_type`, `linked_entity_type`, `linked_entity_id`, `created_at`, `updated_at`.

### 3.3 `crm_activity_timeline`

Aggregates cross-module CRM activity events (calls, tasks, notes, calendar events) per CRM entity in a single chronological stream. Used by ACT-009.

| Layer | Value |
|---|---|
| Partition key | `entity_key` (S) — value: `{linked_entity_type}#{linked_entity_id}` |
| Sort key | `sk` (S) — value: `{inverted_ts:013d}#{activity_type}#{activity_id}` |

**GSI `ByType`** — global view of all activity events of a given type:

| Attr | Value | Type |
|---|---|---|
| GSI1PK | `TYPE#{activity_type}` | S |
| GSI1SK | `created_at` (Unix epoch) | N |

`attr_types={"GSI1SK": "N"}` required.

Item attributes: `entity_type`, `entity_id`, `activity_type`, `activity_id`, `user_sub`, `summary`, `metadata` (JSON map), `created_at`.

### 3.4 `crm_event_rsvp`

Stores per-attendee RSVP status for calendar events. Used by ACT-002.

| Layer | Value |
|---|---|
| Partition key | `event_key` (S) — value: `{calendar_id}#{event_id}` |
| Sort key | `attendee_sub` (S) |

**GSI `ByUser`** — all events an attendee has an RSVP on, ordered by response time:

| Attr | Value | Type |
|---|---|---|
| GSI1PK | `USER#{attendee_sub}` | S |
| GSI1SK | `updated_at` (Unix epoch) | N |

`attr_types={"GSI1SK": "N"}` required.

Item attributes: `calendar_id`, `event_id`, `attendee_sub`, `status` (accepted | declined | tentative | no_response), `responded_at`, `updated_at`.

### 3.5 `crm_event_reminders`

Stores per-user, per-event reminder rows that the background poller fires. Used by ACT-004.

| Layer | Value |
|---|---|
| Partition key | `reminder_key` (S) — value: `{calendar_id}#{event_id}#{user_sub}` |
| Sort key | `reminder_id` (S) |

**GSI `DueReminders`** — constant-partition scan for overdue reminders; enables the poller to query `fire_at BETWEEN now AND now+lookahead` without a table scan:

| Attr | Value | Type |
|---|---|---|
| GSI1PK | constant string `"DUE"` | S |
| GSI1SK | `fire_at` (Unix epoch) | N |

`attr_types={"GSI1SK": "N"}` required.

Item attributes: `calendar_id`, `event_id`, `user_sub`, `minutes_before`, `method` (email | in_app), `fire_at`, `fired` (bool), `created_at`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag semantics and evaluation order

`S.crm_activities_enabled` is the master switch. All downstream tickets gate their routers and background tasks on the compound expression `S.crm_activities_enabled and S.<sub_flag>`. This means:

- Disabling the master switch silences all CRM Activities work regardless of sub-flag state.
- Each sub-flag independently controls its module. This lets operators enable Tasks (ACT-008) without enabling Notes (ACT-010) or RSVP tracking (ACT-002).
- With both master and sub-flags off (the default), the platform is byte-for-byte unchanged: the five tables exist in DynamoDB but are never written to or queried from application code. Table existence without traffic has no operational cost.

### 5.2 DynamoDB table creation idempotency

`scripts/local-ddb-init.py` wraps each `create_table` call in a `try/except ClientError` that ignores `ResourceInUseException` (not `ResourceInExistsException` — the actual error code DynamoDB/DynamoDB Local raises for an already-existing table; see `scripts/local-ddb-init.py:2590`). Running `just restart` (which invokes `local-ddb-init.py`) with tables already present is safe — it is a no-op for existing tables.

### 5.3 SK inversion convention

Three of the five tables use an inverted timestamp in the sort key (`TASK#{inverted_due_ts}`, `NOTE#{inverted_ts}`, timeline `{inverted_ts}`). This is the same convention used by `app/services/call_history.py:32` (`9999999999999 - created_at`) and many other services throughout the codebase. The inversion ensures DynamoDB's `ScanIndexForward=False` (the default when descending) is not needed at the application level; a simple ascending query returns records newest-first. The zero-padding length (`013d`) accommodates Unix timestamps up to the year 2286.

### 5.4 GSI sparse writes

GSI attributes (`GSI1PK`, `GSI1SK`, `GSI2PK`, `GSI2SK`) are written by application code in downstream tickets. Items that do not belong to a GSI partition simply omit those attributes; DynamoDB GSIs are automatically sparse. For example, a `crm_tasks` item with no assignee omits `GSI2PK`/`GSI2SK` and does not appear in the `ByAssignee` GSI — no `FilterExpression` needed to exclude unassigned tasks.

### 5.5 Constant-partition anti-pattern for `DueReminders`

The `crm_event_reminders.DueReminders` GSI uses a constant `"DUE"` partition key, which concentrates all writes onto one logical partition. This is acceptable because:
- Event reminders are low-volume (at most a few items per user per event per day).
- The pattern is already established in `app/services/scheduled_actions.py:132` (`"GSI_DUE_PK": "DUE"`) and the `audit_export_schedule` table's `SCHEDULES#ACTIVE` partition (see CLAUDE.md "Scheduled audit export reports").
- The poller window is narrow (`fire_at BETWEEN now AND now+lookahead_seconds`) so the result set is always bounded.

If volume ever grows beyond DynamoDB hot-partition limits, the partition key can be sharded by hour bucket with no change to the item schema — this is an ACT-004 operational concern, not an ACT-001 design constraint.

### 5.6 `crm_event_rsvp` sort key is not a timestamp

Unlike the other four tables, `crm_event_rsvp` uses `attendee_sub` as the sort key (not a timestamp). This allows an O(1) point lookup `GET_ITEM(event_key, attendee_sub)` and an O(attendees) range query `QUERY(PK=event_key)` — both needed by ACT-002. The `ByUser` GSI uses `updated_at` (numeric) as its sort key to enable a user's pending RSVPs ordered by recency.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 compliance

ACT-001 contains no runtime logic — it is pure configuration and schema. There is therefore no `dev_mode` branch to introduce and no parity gap to manage. The DynamoDB tables created by `scripts/local-ddb-init.py` are structurally identical in dev (DynamoDB Local on port 8001) and prod (real AWS DynamoDB). The five `_safe_table` handles use the same `_FloatSafeTable` proxy in both environments (no env-conditional wrapping).

### 7.2 Idempotency

`local-ddb-init.py` is idempotent: re-running it after the tables exist silently succeeds (ResourceInExistsException is swallowed). The settings fields are stateless constants loaded at import time. Adding fields to the frozen `Settings` dataclass does not affect existing field values. Adding fields to the frozen `Tables` dataclass does not affect existing handle references.

### 7.3 Secrets and access control

ACT-001 introduces no new secrets, API keys, encryption keys, or IAM policies. In prod, the five new DynamoDB tables must be added to the IAM policy granting the application's execution role `dynamodb:GetItem`, `dynamodb:PutItem`, `dynamodb:UpdateItem`, `dynamodb:DeleteItem`, `dynamodb:Query`, `dynamodb:Scan` on the new table ARNs and their GSI ARNs. This is an ops/infra concern to address before any downstream ACT ticket is enabled in prod.

### 7.4 Naming collision check

All five table names (`crm_tasks`, `crm_notes`, `crm_activity_timeline`, `crm_event_rsvp`, `crm_event_reminders`) are distinct from all 320+ existing table names currently registered in `T`. The `activity_feed` table (`T.activity_feed`, line 257) and `call_history` table (`T.call_history`, line 259) are separate tables with separate purposes; the CRM tables do not alias or shadow them.

## 8. Backward Compatibility & Migration

### 8.1 Existing tables

No existing table definition in `scripts/local-ddb-init.py` is modified. No existing handle in `app/core/tables.py` is changed. The `@dataclass(frozen=True)` means all existing field accesses via `T.calendar`, `T.call_history`, etc. continue to resolve to exactly the same `_FloatSafeTable` instances they do today.

### 8.2 Existing routes and services

No existing endpoint in any router file is modified. No existing service function is modified. With `CRM_ACTIVITIES_ENABLED` defaulting to `false`, the application startup sequence is byte-for-byte identical to pre-ACT-001 except for five additional `_safe_table(...)` calls during `Tables` construction (which execute unconditionally at import time but are fast and idempotent).

### 8.3 In-flight deployments

Because the five new tables do not yet have any writes directed at them, a rolling deployment that mixes pre-ACT-001 and post-ACT-001 instances is safe: the old instances ignore the new settings fields (they are never read), and the new instances resolve the five handles successfully.

### 8.4 Production table provisioning

In production, the five DynamoDB tables do not exist until explicitly created. `local-ddb-init.py` handles local dev. For prod:
- Tables must be created via IaC (CloudFormation / Terraform) or the AWS CLI before deploying ACT-001 code.
- GSIs must be declared at table creation time (DynamoDB GSIs cannot be added to an existing table without rebuilding it in Local mode, though AddGlobalSecondaryIndex is available on real DynamoDB with async backfill).
- Recommended: create all five tables with all GSIs in a migration PR that targets the same deploy window as ACT-001.
- Tables can exist with zero items and zero capacity consumed; they incur no cost until written to.

## 10. Open Questions / Assumptions

**Q1: Should `crm_event_reminders` reuse `T.scheduled_actions` (the unified scheduler) instead of a dedicated table?**

The unified scheduler (`app/services/scheduled_actions.py:91`) is a general-purpose delayed-action system with retry, status tracking, and a poller (`app/services/unified_scheduler.py:35`). For event reminders, reminders need to be bulk-replaced when an event is rescheduled (delete all user reminders for an event and rewrite them), which is awkward with the scheduler's current key structure. A dedicated table with `PK=reminder_key ({calendar_id}#{event_id}#{user_sub})` makes replace-on-reschedule O(reminders_per_user_per_event) without scanning. **Assumption**: dedicated table is preferable for the access pattern. If the team decides to fold into `scheduled_actions`, ACT-001 can drop the `crm_event_reminders` table and ACT-004 becomes a `create_action` + `mark_reminder_sent` consumer.

**Q2: Are all five tables required in the initial scaffold, or can they be deferred to their respective feature tickets?**

The ticket spec requires all five tables in ACT-001 so that ACT-002 through ACT-010 each have a clean single-ticket dependency (just "ACT-001"). If tables were provisioned per-feature ticket, the dependency graph would grow laterally. **Assumption**: all five tables ship in ACT-001.

**Q3: Should the `crm_activity_timeline` table's partition key be `entity_key` (a composite string) or separate `entity_type` + `entity_id` attributes with a composite condition?**

Using `entity_key = "{type}#{id}"` as the PK is consistent with the RSVP table's `event_key = "{calendar_id}#{event_id}"` pattern and keeps the access pattern a simple `Key("entity_key").eq(...)` query. `entity_type` and `entity_id` are stored as separate attributes for filtering. **Assumption**: composite string PK is the correct choice.

**Q4: Is `inverted_ts` based on `now_ts()` (Unix seconds, 10-digit) or milliseconds?**

All timestamps in the codebase use `now_ts()` from `app/core/time.py:2` which returns `int(time.time())` (Unix seconds). The `call_history.py:32` inversion uses `9999999999999 - ts` (13-digit padding). That constant fits seconds-precision timestamps until year 2286. The `013d` zero-padding format is appropriate for all three inverted-TS sort keys in ACT-001. **Assumption**: seconds precision, 13-digit padding.
