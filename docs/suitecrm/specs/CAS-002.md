# CAS-002 — Sequential human-readable case number

## 1. Summary & Goal

Every support ticket created while `S.crm_cases_enabled` is `True` must carry a
short, human-readable identifier such as `CASE-0042`.  Agents and customers alike
should be able to refer to a ticket by this number in emails, phone calls, and
portal pages without quoting a UUID.

The implementation uses a single DynamoDB atomic counter row (introduced by
CAS-001) and the standard `ADD 1` / `ReturnValues="UPDATED_NEW"` pattern already
used throughout the codebase (e.g. `broadcast_tip_store.py:195–214`).  The counter
row is written once by CAS-001 scaffolding; CAS-002 adds the helper that
increments it and the wiring that attaches the result to every new ticket META
row.

With `CRM_CASES_ENABLED=0` (the default) the platform is **byte-for-byte
unchanged**: no counter is touched, `case_number` is always `None`, and no
existing test can observe a difference.

## 3. Data Model

### 3.1 Counter row (table: `crm_cases_counters`, provisioned by CAS-001)

| Attribute      | Type   | Value                          |
|----------------|--------|-------------------------------|
| `counter_id`   | S (PK) | `"TICKETS"`                   |
| `scope`        | S (SK) | `"GLOBAL"`                    |
| `n`            | N      | monotonically increasing integer (starts at 0, absent until first increment) |

The row need not be seeded explicitly — DynamoDB's `ADD` expression creates the
attribute with value 1 on first call if the attribute does not yet exist
(`if_not_exists` semantics are built into `ADD`).

No GSIs are needed on `crm_cases_counters`.  The table has no secondary-access
patterns for CAS-002.

### 3.2 Ticket META row additions

The existing `tickets` table META row (`pk=TICKET#{ticket_id}`, `sk=META`) gains
one new optional attribute when `S.crm_cases_enabled` is `True`:

| Attribute     | Type | Semantics                                 |
|---------------|------|-------------------------------------------|
| `case_number` | S    | `"CASE-{n:04d}"`, e.g. `"CASE-0042"`.  Absent when flag is off. |

The attribute is set once at creation time and is immutable thereafter.  It is
stored on the same partition as all other ticket sub-items, so no additional GSI
or scan is required to retrieve it.

No new `attr_types` declaration is needed because `case_number` is a String
attribute and is never used as a GSI sort key.

## 4. API / Service Design

### 4.1 New helper: `_next_case_number() -> str`

Location: module-level function in `app/services/tickets.py`, added below the
existing `_complexity_from_labels` helper.

```python
def _next_case_number() -> str:
    """Atomically allocate the next sequential case number.

    Uses DynamoDB ADD on the counter row so concurrent ticket creation
    never produces duplicate numbers.  Returns a zero-padded string such
    as "CASE-0042".  The attribute is auto-initialised to 1 on first call
    (DynamoDB ADD creates missing numeric attributes at 0 then adds :one).
    """
    resp = T.crm_cases_counters.update_item(
        Key={"counter_id": "TICKETS", "scope": "GLOBAL"},
        UpdateExpression="ADD #n :one",
        ExpressionAttributeNames={"#n": "n"},
        ExpressionAttributeValues={":one": 1},
        ReturnValues="UPDATED_NEW",
    )
    n = int(resp["Attributes"]["n"])
    return f"CASE-{n:04d}"
```

`T.crm_cases_counters` is a `_FloatSafeTable` proxy (same wrapper as every
other handle in `app/core/tables.py`), so the `ExpressionAttributeValues`
coercion for `Decimal` is handled transparently.  The integer literal `1` passes
through `_to_decimal` unchanged (`isinstance(1, float)` is `False`).

## 5. Detailed Behavior & Edge Cases

### 5.1 Normal creation path

1. Client calls `POST /tickets` with `subject` + `description`.
2. `create_ticket` generates `resolved_ticket_id`.
3. `get_ticket(resolved_ticket_id)` returns `None` (ticket is new).
4. `_next_case_number()` issues `update_item ADD n :one ReturnValues=UPDATED_NEW`
   against `crm_cases_counters`.  DynamoDB increments `n` atomically and returns
   the new value.
5. `case_number = f"CASE-{n:04d}"` is computed.
6. META row is written with `case_number` field.
7. `TicketOut` returned to client includes `"case_number": "CASE-0001"` (for the
   first ticket).

### 5.2 Idempotent ticket creation (pre-existing ticket_id supplied)

When a caller supplies an explicit `ticket_id` and that ticket already exists,
`create_ticket` returns early at line 431 (`return existing`).  Because the guard
is executed **before** `_next_case_number()` is called, no counter increment
occurs.  The returned ticket carries the `case_number` from the original creation.

### 5.3 Counter starts at 1 automatically

DynamoDB initialises missing numeric attributes to 0 when `ADD` is first applied.
So the first ever call to `_next_case_number()` increments `0 + 1 = 1`, returning
`"CASE-0001"`.  No separate seed step is required.

### 5.4 Counter overflow beyond 9999

When `n` exceeds 9999 the format string `f"CASE-{n:04d}"` still works correctly
— Python's `:04d` is a minimum-width specifier, not a clamp.  The number expands:
`n=10000` yields `"CASE-10000"`.  This is consistent with SuiteCRM behavior
(which also expands) and avoids silent truncation.

### 5.5 DynamoDB `update_item` failure

If `T.crm_cases_counters.update_item` raises a `ClientError` (e.g. table does
not exist because CAS-001 has not been deployed), the exception propagates up
through `create_ticket` and out to the FastAPI exception handler as a `500`.  The
ticket META row is not written.  This is the correct behavior — a partial ticket
without a case number is worse than no ticket.

Operators must deploy CAS-001 before enabling CAS-002 via the flag.

### 5.6 Concurrent creation — no gap guarantee

Two concurrent `POST /tickets` requests may each call `_next_case_number()`
simultaneously.  DynamoDB's `ADD` is serialized at the partition level, so both
receive distinct, consecutive integers.  However, if one of the ticket `put_item`
calls subsequently fails (e.g. a DynamoDB write error after the counter was
already incremented), a gap will appear in the sequence.  This is acceptable:
SuiteCRM similarly does not guarantee gaplessness.

### 5.7 Flag toggled off mid-operation

If `S.crm_cases_enabled` is `False`, `_next_case_number()` is never called.
Tickets created before the flag was enabled retain their `case_number` in DynamoDB
and continue to surface it via `get_ticket` / `TicketOut`.  There is no migration
needed in either direction.

### 5.8 Zero-padded format and human readability

`f"CASE-{n:04d}"` produces `CASE-0001` … `CASE-9999`, then `CASE-10000` onward.
The prefix is uppercase `CASE` (not configurable in this ticket; CAS-017 analytics
may filter by prefix if extended).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No dev/prod branch

`_next_case_number()` issues a real DynamoDB `update_item` call in both dev and
prod.  In dev, this hits DynamoDB Local (port 8001) via the same `T.crm_cases_counters`
handle.  There is no `if S.dev_mode` branch.  This is SECOPS-007 parity: the
counter logic is identical across environments.

### 7.2 Idempotency

The idempotency contract is:
- A given `ticket_id` always maps to exactly one `case_number` (written once, immutable).
- Re-submitting a `POST /tickets` with the same caller-supplied `ticket_id` returns
  the existing ticket (including its original `case_number`) without incrementing
  the counter.
- Re-submitting without a `ticket_id` generates a new UUID and a new case number
  (this is expected behavior for the client, who should use idempotency keys if
  they need deduplication).

### 7.3 Security

`case_number` is a sequential integer-derived identifier and reveals the total
volume of tickets created on the platform.  This is acceptable for an internal
support tool (SuiteCRM exposes the same information).  Operators who require
confidentiality of ticket volume may use a non-sequential scheme — that is an
out-of-scope enhancement for a future ticket.

The counter row has no TTL and is not user-scoped — it is a single global row
manipulated only server-side.  There is no client-controlled input that can
influence the counter value.

### 7.4 Counter row not included in audit exports

The `crm_cases_counters` table does not contain PII or sensitive business logic
and is outside the scope of GDPR data-subject export requests.

## 8. Backward Compatibility & Migration

### 8.1 Existing tickets (flag disabled, then enabled)

Tickets created before `CRM_CASES_ENABLED` is turned on do not have a
`case_number` attribute.  `get_ticket` returns `"case_number": None` for them.
`TicketOut.case_number` defaults to `None`, so these tickets deserialize cleanly.

There is no migration to backfill `case_number` on existing tickets.  Doing so
would require re-numbering them in insertion-time order (expensive scan + sort +
batch update) and would not provide meaningful value — agents already have ticket
UUIDs for pre-flag tickets.  If backfill is required in future, a one-off script
can be written independently of this ticket.

### 8.2 `TicketListItemOut` source field

`TicketListItemOut` has a `source: Literal["internal", "jira"]` field
(`app/routers/tickets.py:108`).  Jira-sourced rows come from
`JiraTicketSyncStore` and not from `TicketStore.create_ticket`, so they never
go through `_next_case_number()`.  Their `case_number` will always be `None`.
This is correct — Jira issues have their own identifier scheme (`external_issue_key`).

### 8.3 No table schema change to `tickets`

`case_number` is a plain string attribute on the META row.  DynamoDB is
schema-less for non-key attributes, so no `UpdateTable` or backfill is required
to write it on new rows while old rows lack it.

## 10. Open Questions / Assumptions

1. **Counter scope**: The spec uses `scope="GLOBAL"` for a single platform-wide
   counter.  If multi-tenancy (per-organization ticket numbering) is added in
   future, a new `scope` value (e.g. `ACCOUNT#{account_id}`) can be introduced
   without altering the table schema.  This is left as a future extension.

2. **Case number prefix**: The prefix `CASE-` is hardcoded.  If operators require
   a custom prefix (e.g. `TICKET-` or `SUP-`) a settings key
   `crm_cases_number_prefix: str = "CASE"` can be added.  Deferred until there is
   an operator request.

3. **Backfill of pre-flag tickets**: No backfill is specified.  Assumption: tickets
   created before the flag is enabled are internal/dev tickets and do not require
   human-readable numbers.  If backfill is needed, it is a separate one-off
   migration script and out of scope for CAS-002.

4. **Atomicity of counter + put_item**: DynamoDB does not support multi-item
   transactions across different tables without using `TransactWriteItems`.  The
   counter increment and the ticket `put_item` are two separate DynamoDB calls.
   A crash between them produces a gap in the sequence.  Gaps are acceptable
   (assumption aligned with SuiteCRM behavior).  If strict no-gap semantics are
   ever required, the counter and the META row must be moved to the same table
   and written in a single `TransactWriteItems` call.

5. **Format width**: `{n:04d}` (4-digit minimum) matches SuiteCRM's default
   display.  At 9999 tickets the format auto-expands.  If a fixed-width 6-digit
   format is preferred, the spec can be updated; no schema change is required.
