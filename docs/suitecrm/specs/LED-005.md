# LED-005 — Web-to-lead form capture (questionnaire integration)

**Type:** Feature  **Priority:** P1  **Estimate:** 2 days
**Ticket source:** `docs/suitecrm/CRM_LEADS_TICKETS.md`, section "LED-005"

---

## 1. Summary & Goal

LED-005 wires the existing questionnaire submission pipeline into the leads system
by adding a `capture_as_lead` flag to questionnaire publish settings. When a
questionnaire carrying that flag is submitted — by an anonymous visitor or an
authenticated user — the system transparently creates a Lead record from the
submitted answers without interrupting the submission flow.

The feature is entirely additive and default-off. With `LEADS_ENABLED=0` (or
`capture_as_lead=False` on the version row) the questionnaire router
(`app/routers/questionnaires.py`) is byte-for-byte unchanged and no Lead is ever
created. A single new helper function, `create_lead_from_submission`, is added to
`app/services/leads.py` (delivered by LED-003); the questionnaire submit handler
gains a best-effort, try/except-wrapped call to it.

**Goal**: enable operators to publish a standard questionnaire (contact form, survey,
intake form) and have every submission automatically land in the leads pipeline for
follow-up by sales or CRM users, without any custom integration code.

## 2. Context & Current State

### 2.1 Questionnaire router — publish and submit paths

`app/routers/questionnaires.py` contains two relevant handler pairs.

**Publish** (`POST /questionnaires/drafts/{questionnaire_id}/publish`, line 580):
delegates to `REPO.publish_draft(...)` (the `DynamoQuestionnaireRepository`
singleton at line 24). The request model is `PublishDraftReq` at line 79, which
currently carries only `published_slug: str | None`. The version row written by
`REPO.publish_draft` (`questionnaires_repository.py:355`) stores computed fields
such as `allow_anonymous` (line 401) and `visibility` (line 400) alongside the
schema snapshot. LED-005 must also store `capture_as_lead` and
`lead_source_override` on this version row so that submit-time logic can read them
without touching the questionnaire META row.

**Submit** (`POST /questionnaires/published/{published_slug}/sessions/{response_session_id}/submit`,
line 772): the critical execution path is:

1. Resolves version from `REPO.get_published_by_slug` (line 779).
2. Resolves session; enforces session ownership (`_enforce_session_access`, line 789).
3. Calls `_enforce_anonymous_submission_controls` (line 790) — this is the last
   gate before the submission is accepted.
4. Validates and saves answers (lines 794-801).
5. Calls `validate_response_session_state` (line 810) — raises 422 if invalid.
6. Calls `REPO.mark_response_submitted` (line 812) — writes `submitted` status.
7. Returns `{"session": submitted, "result": result}`.

The lead capture hook must be injected **after step 6** (after the session is
successfully marked `submitted`) so it only fires for genuinely completed
submissions. It must be wrapped in `try/except` so a lead creation failure never
alters the 200 response already ready.

### 2.5 Leads service — `create_lead` (LED-003 prerequisite)

LED-003 delivers `app/services/leads.py` with `create_lead(creator_sub, data:

### 2.6 Normalization and the anonymous-submission case

`normalize_email` (line 60) raises `HTTPException(400, ...)` when the email is
absent or malformed. Because `create_lead_from_submission` must never raise,
the function must use a plain try/except around normalization and silently return
`None` on any error (see section 5.3).

### 2.7 Answer map layout

Answers are stored in DynamoDB as `ANSWER#{response_session_id}#{question_id}`
rows and returned by `REPO.list_session_answers` as a flat
`dict[question_id, value]` (line 573-590). LED-005 resolves lead fields by
looking up specific `question_id` string keys: `"first_name"`, `"last_name"`,
`"email"`, `"phone"`, `"company"`, `"title"`, `"website"`. These are
**questionnaire author conventions**, not enforced by the schema. If a question
with that exact `question_id` string is absent, the field is treated as missing.

The `submit_response_session` handler already calls `REPO.list_session_answers`
at line 803 and stores the result in `authoritative_answers`. LED-005 passes
this already-fetched dict to `create_lead_from_submission`, avoiding a redundant
DynamoDB query.

### 2.8 Settings flag reference (`app/core/settings.py`)

`S.leads_enabled` will be added by LED-001, following the
`cart_reminders_enabled` pattern at `app/core/settings.py:821`:

```python

```

LED-001 declares `leads_enabled` with default `"0"` (off). LED-005 gates the
capture hook on `S.leads_enabled` at runtime and on `version.get("capture_as_lead")`
from the stored version row.

## 3. Data Model

### 3.1 No new DynamoDB table

LED-005 introduces no new DynamoDB table. Leads created by the capture hook are
written to `T.leads`, the single-table delivered by LED-001 (PK=`pk`, SK=`sk`,
three GSIs: `ByOwner`, `ByStatus`, `BySource`). Refer to the LED-001 and LED-003
specs for the complete `leads` table schema and `attr_types`.

### 3.2 New fields on the questionnaire version row

The version item written by `put_version` in `questionnaires_repository.py:378`
gains two new attributes. These project onto the `gsi_published_pk` index (used
by `get_published_by_slug`) because the index is created with `ProjectionType=ALL`
(confirmed by the `scripts/local-ddb-init.py:127-136` `TableDef` which specifies
no projection, defaulting to ALL).

| Attribute | Type | Default | Notes |
|---|---|---|---|
| `capture_as_lead` | `bool` | `False` | Set at publish time; read at submit time |
| `lead_source_override` | `str \| None` | `None` | Overrides default `"web_site"` source; must be a member of `LEAD_SOURCES` if set |

These attributes are sparse: only version rows published with
`capture_as_lead=True` carry a non-default value. Existing version rows (already
in DDB before LED-005 is deployed) will return `None` / absent on `dict.get`,
which is handled by the `version.get("capture_as_lead", False)` read.

### 3.3 Lead META row written by the capture hook

When `create_lead_from_submission` successfully creates a lead, it writes the
standard `LEAD#{lead_id} / META` row to `T.leads` per the LED-003 schema. The
following fields are populated specifically by the capture path:

| Field | Value |
|---|---|
| `lead_source` | `version.get("lead_source_override") or "web_site"` |
| `created_by` | `user_sub` if authenticated; `"system_web_lead"` if anonymous |
| `origin_questionnaire_id` | `version["questionnaire_id"]` (extra attribution field) |
| `origin_response_session_id` | `response_session_id` passed to the function |

`origin_questionnaire_id` and `origin_response_session_id` are stored as plain
attributes on the META row (no GSI). They are included in `LeadOut` (added by
LED-002) as optional read-only fields, enabling later queries like "which leads
came from form X?".

### 4.6 `create_lead_from_submission` (`app/services/leads.py`)

New function added to the LED-003 service file:

```python
_WELL_KNOWN_QUESTION_IDS = {
    "first_name", "last_name", "email", "phone",
    "company", "title", "website",
}

def create_lead_from_submission(
    version: dict,
    answers: dict,
    *,
    response_session_id: str = "",
    user_sub: Optional[str],
) -> Optional[dict]:
    """Best-effort web-to-lead capture from a questionnaire submission.

    Returns the created lead dict, or None if capture is skipped or fails.
    Never raises.
    """
    try:
        if not getattr(S, "leads_enabled", False):
            return None
        if not version.get("capture_as_lead", False):
            return None

        raw_email = str(answers.get("email") or "").strip()
        if not raw_email:
            return None  # email is the minimum required field

        from app.core.normalize import normalize_email, normalize_phone
        try:
            normalized_email = normalize_email(raw_email)
        except Exception:
            return None  # malformed email; skip silently

        first_name = str(answers.get("first_name") or "").strip()[:120] or "Unknown"
        last_name  = str(answers.get("last_name")  or "").strip()[:120] or "Unknown"
        raw_phone  = str(answers.get("phone")      or "").strip()
        company    = str(answers.get("company")    or "").strip()[:200] or None
        title      = str(answers.get("title")      or "").strip()[:200] or None
        website    = str(answers.get("website")    or "").strip()[:500] or None

        phone: Optional[str] = None
        if raw_phone:
            try:
                phone = normalize_phone(raw_phone)
            except Exception:
                phone = None  # invalid phone; store None

        lead_source = (
            version.get("lead_source_override")
            or "web_site"
        )

        creator_sub = user_sub or "system_web_lead"

        from app.models import LeadCreateIn
        data = LeadCreateIn(
            first_name=first_name,
            last_name=last_name,
            email=normalized_email,
            phone=phone,
            company=company,
            title=title,
            lead_source=lead_source,
            website=website,
        )

        lead = create_lead(
            creator_sub=creator_sub,
            data=data,
            extra={
                "origin_questionnaire_id":   version.get("questionnaire_id", ""),
                "origin_response_session_id": response_session_id,
            },
        )
        return lead
    except Exception:  # pragma: no cover — intentional swallow
        return None
```

`create_lead` (LED-003) is called with an `extra` dict that the service merges
onto the META item (same pattern as `new_ledger_entry(..., extra={...})` in
`billing_shared.py`).

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off path (default)

When `S.leads_enabled` is `False` (the default until the operator sets
`LEADS_ENABLED=1`):

- `PublishDraftReq.capture_as_lead` may still be `True` (the model accepts it),
  but the submit hook short-circuits at the `getattr(S, "leads_enabled", False)`
  check before calling `create_lead_from_submission`.
- No lead row is written to any DynamoDB table.
- The questionnaire router, `questionnaires_repository.py`, and `app/models.py`
  are otherwise byte-for-byte unchanged in observable behavior.

### 5.2 `capture_as_lead=False` (default publish)

When `leads_enabled=True` but `capture_as_lead` is `False` on the version row:

- The hook short-circuits at `version.get("capture_as_lead", False)`.
- No lead is created for submissions of that questionnaire.

### 5.3 Missing or malformed email

`create_lead_from_submission` treats email as the minimum viable field:

- `answers.get("email")` is absent, `None`, or empty string → return `None`.
- `normalize_email` raises (e.g., no `@` sign, length > 254) → catch exception,
  return `None`.
- In both cases the questionnaire submission still returns HTTP 200 and the
  response session is marked `submitted`.

### 5.4 Duplicate email — idempotent create

`create_lead` (LED-003) implements idempotent duplicate detection: it queries the
`ByStatus` GSI for an existing lead with the same normalized email and returns the
existing record if found. A repeated form submission with the same email address
therefore returns the existing lead rather than creating a duplicate row.

### 5.5 Partial answers (first_name/last_name missing)

If `first_name` or `last_name` answers are absent, `create_lead_from_submission`
defaults to `"Unknown"`. These can be corrected later via the Lead CRUD update
endpoint. The intent is to capture the email (for follow-up) even when the form
is partially filled.

### 5.6 `phone` normalization failure

If `normalize_phone` raises (e.g., non-E.164, ambiguous format), the exception is
caught and `phone` is set to `None`. The lead is still created without a phone
number rather than failing silently with no lead at all.

### 5.7 Authenticated vs. anonymous submissions

`user` in the submit handler is `AuthenticatedUser | None` (resolved by
`_maybe_authenticated_user`, line 783). LED-005 passes `user.sub` when
authenticated or `None` when anonymous; `create_lead_from_submission` substitutes
`"system_web_lead"` as the `created_by` value. This sentinel is distinguishable
from a real `user_sub` (real subs come from Cognito and are UUID-format strings).

### 5.8 `version` dict availability

`version` is resolved before the submit handler calls `_enforce_session_access`
(line 780). It is already in scope at line 812 and is passed directly to
`create_lead_from_submission`. No additional DynamoDB read is needed.

### 5.9 `authoritative_answers` availability

`authoritative_answers = REPO.list_session_answers(...)` at line 803 is already
called before submission completes. The dict is passed directly to avoid a
redundant read.

### 5.10 Re-submission attempt (session already submitted)

The handler raises HTTP 409 at line 792 if `session.get("status") != "in_progress"`.
The lead capture hook is placed after `REPO.mark_response_submitted` at line 812,
so it only fires on the first successful submission. A retry on an already-submitted
session is blocked before reaching the hook.

### 5.11 `lead_source_override` validation

The `pattern` field validator on `PublishDraftReq.lead_source_override` (section 4.1)
rejects unknown values at request-parse time with HTTP 422. This means invalid
source strings never reach the service layer. `create_lead_from_submission` still
adds a `LEAD_SOURCES` membership check as a belt-and-suspenders guard, falling
back to `"web_site"` if an unexpected value arrives.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

There is no `dev_mode` branch in LED-005. The `create_lead_from_submission`
function, the `put_version` extension, and the submit hook all execute identically
in development (moto-backed DynamoDB local) and production (real DynamoDB).
`normalize_email` and `normalize_phone` in `app/core/normalize.py` contain no
environment branches. `audit_event` (called internally by `create_lead`) writes to
DynamoDB locally in dev — the same table handle — not to a mock logger. No new
S3 or KMS calls are introduced.

### 7.2 Idempotency

`create_lead` (LED-003) is designed to be idempotent: duplicate email lookup
before write returns the existing record. If the HTTP request is retried (e.g.,
network timeout after the backend writes `submitted` but before the response
reaches the client), the second call to `create_lead_from_submission` will return
the already-existing lead without writing a second row.

`REPO.mark_response_submitted` uses a `ConditionExpression` at
`questionnaires_repository.py:451` (`#status=:in_progress`) — so a retried submit
will fail the condition and return the existing submitted session. The lead capture
hook is placed after `mark_response_submitted`, but the idempotency of `create_lead`
means even if the hook fires twice, only one lead row exists.

### 7.3 Security — anonymous submissions

The lead capture hook fires for anonymous submissions when the questionnaire has
`allow_anonymous=True`. This is intentional: contact capture forms are the primary
use case and are inherently public-facing. Rate limiting is already enforced
against anonymous submissions by `_enforce_anonymous_submission_controls`
(`questionnaires.py:282`), which calls `rate_limit_password_recovery` keyed on
the questionnaire ID and client IP. This rate limit protects the lead table from
bulk-injection via the questionnaire endpoint.

### 7.4 Security — PII in DynamoDB

Email and name data written to `T.leads` is stored in plaintext at rest, encrypted
only by DynamoDB's server-side encryption (standard for all tables on this
platform). Questionnaire answer fields tagged as sensitive types (`address`, `date`,
`time`, `timezone`) are encrypted via `kms_encrypt` in `save_session_answers`
(`questionnaires_repository.py:614-626`). LED-005 reads from `list_session_answers`
which decrypts on the way out (line 586-588) — so answers arrive in plaintext to
`create_lead_from_submission`. No further KMS wrapping is applied to the lead
record; this matches the contacts pattern in `T.contacts` (no field-level
encryption). A future ticket could apply KMS encryption to the `email` field on
`T.leads` following the questionnaire sensitive-answer pattern.

### 7.5 Security — `lead_source_override` injection

A malicious actor submitting to the public questionnaire endpoint cannot supply a
`lead_source_override`; that value is set at **publish time** by the authenticated
questionnaire owner and stored on the server-side version row. The submit handler
reads it from `version` (fetched from DynamoDB), not from the request body. There
is no user-controlled input to the source field.

## 8. Backward Compatibility & Migration

### 8.1 Existing questionnaire version rows

All version rows written before LED-005 is deployed will not carry `capture_as_lead`
or `lead_source_override`. `version.get("capture_as_lead", False)` returns `False`
for those rows, so the hook is never triggered for pre-existing versions. No
DynamoDB migration or backfill is required.

### 8.2 `PublishDraftReq` — backward compatible

The two new fields have `default=False` and `default=None` respectively. Any
existing client sending `{"published_slug": "my-form"}` will parse successfully
with `capture_as_lead=False`. The Pydantic model is additive.

### 8.3 `QuestionnaireRepository` Protocol

The Protocol at `questionnaires_repository.py:25` gains default-value parameters.
Any implementation of the Protocol that does not override `publish_draft` will
inherit the defaults. The `DynamoQuestionnaireRepository` concrete implementation
is the only implementation in the codebase (confirmed: no other class implements
`QuestionnaireRepository`).

### 8.4 Rollback

Rolling back LED-005 (reverting the `questionnaires.py` and
`questionnaires_repository.py` changes) has no effect on previously written lead
rows in `T.leads`. Lead rows created by the capture hook are valid lead records
and are not orphaned. Rolling back LED-005 simply stops future captures; it does
not remove past captures.

## 10. Open Questions / Assumptions

1. **`create_lead` extra fields**: LED-003's `create_lead` signature accepts only
   `creator_sub` and `data: LeadCreateIn`. The spec above proposes an `extra: dict`
   keyword argument to plumb `origin_questionnaire_id` and
   `origin_response_session_id` onto the META item. If the LED-003 implementer
   did not add this parameter, LED-005 can instead call `T.leads.update_item` to
   set those fields after `create_lead` returns, using the returned `lead_id`.
   Either approach is acceptable; the extra-field approach is cleaner.

2. **`first_name`/`last_name` defaulting to `"Unknown"`**: Defaulting to
   `"Unknown"` for missing name fields ensures a valid `LeadCreateIn` (which
   requires `min_length=1`). Operators should be aware that web forms omitting
   those fields will produce leads with placeholder names. An alternative is to
   gate on `first_name` and `last_name` being present (treating them as required
   alongside email). This spec chooses permissiveness to maximize capture rate
   from minimal forms (e.g., newsletter signups that only ask for email).

3. **`normalize_email` raising `HTTPException`**: `app/core/normalize.py:60`
   raises `HTTPException(400, ...)` on invalid email, not a plain Python exception.
   `create_lead_from_submission` catches `Exception` broadly, which includes
   `HTTPException` (a Starlette subclass of `Exception`). This is intentional and
   correct, but worth documenting explicitly so reviewers do not assume only
   `ValueError` needs catching.

4. **Rate limiting for authenticated submissions**: Anonymous submissions are
   rate-limited by `_enforce_anonymous_submission_controls`. Authenticated
   submissions skip that gate (`_enforce_anonymous_submission_controls` returns
   immediately if `user is not None`, line 283). A high-volume authenticated user
   could generate a large number of leads via repeated questionnaire submissions.
   LED-013's router should add a per-user lead-creation rate limit as a follow-up
   (using the `_bucket_limit` pattern from `app/services/rate_limit.py`).

5. **Notification on capture**: SuiteCRM sends an email notification to the
   assigned sales user when a lead is captured via a web form. LED-005 does not
   implement this; the lead is created silently. A follow-up ticket (or LED-010's
   `assign_lead`, which calls `alerts.write_alert`) can add this when assignment
   is wired. LED-005's scope is capture only.

6. **`LEAD_SOURCES` import**: `create_lead_from_submission` validates
   `lead_source_override` against `LEAD_SOURCES` from `app/models.py` (LED-002).
   If LED-002 is not deployed, the import will fail. The function wraps the full
   body in `try/except`, so this would silently return `None`. An alternative is
   to define `LEAD_SOURCES` as a module-level constant in `app/services/leads.py`
   (where it is also needed for `create_lead`) rather than importing from
   `app/models.py`. This is the preferred approach.
