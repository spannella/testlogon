# LED-010 — Lead assignment and round-robin distribution

**Type:** Feature | **Priority:** P2 | **Estimate:** 2d  
**Sub-flag:** `leads_assignment_enabled` (default OFF)  
**Depends on:** LED-001, LED-002, LED-003

---

## 1. Summary & Goal

LED-010 delivers `assigned_to` management for Lead records and an optional round-robin auto-assignment engine keyed on a configurable queue. A queue holds a set of agent user subs and tracks each agent's load; when a new lead is created (or manually dispatched), the round-robin engine picks the agent with the fewest open leads, writes `assigned_to` on the lead META row (promoting the lead's status to `assigned`), and emits an in-app alert to the assignee via the existing `alerts.write_alert` primitive.

With `leads_assignment_enabled=False` (the default) all new endpoints 404, no background work runs, and the `leads` table is byte-for-byte unchanged. With the flag on, three queue-admin endpoints and two lead-level endpoints become live; no existing surface is altered.

### New GSI: `AssignedAgent` (added to the `leads` table `TableDef`)

Round-robin load counting requires a per-agent query of open leads. This mirrors `kyc_cases`'s `assigned-admin-index` GSI.

- **GSI partition key:** `assigned_sub` (String) — top-level denormalized copy of `assigned_to` written by `assign_lead`; absent when a lead is unassigned (sparse index, only assigned leads project in).
- **GSI sort key:** `GSI_ASSIGN_SK` (String) — composite `STATUS#{status}` written simultaneously with `assigned_sub` so we can filter by active status with a sort-key condition.
- **Index name:** `ByAssignedAgent`
- **`attr_types`:** `{}` — both keys are String; no `attr_types` override required.

`scripts/local-ddb-init.py` `TableDef` for `leads` gains one more GSI entry:

```python
{"index_name": "ByAssignedAgent", "partition_key": "assigned_sub", "sort_key": "GSI_ASSIGN_SK"}
```

No `attr_types` extension is needed because both are String. The LED-001 `TableDef` already declares `attr_types={"GSI1SK": "N", "GSI2SK": "N", "GSI3SK": "N"}`; this GSI does not change that.

### Lead META row additions (written by `assign_lead`)

`update_item` adds/removes these top-level attributes on `PK=LEAD#{lead_id}` / `SK=META`:

| Attribute | Type | Notes |
|---|---|---|
| `assigned_to` | String | user_sub of assignee; `REMOVE`d on unassign |
| `assigned_sub` | String | Denormalized copy for `ByAssignedAgent` GSI; `REMOVE`d on unassign |
| `GSI_ASSIGN_SK` | String | `STATUS#{status}`; `REMOVE`d on unassign |
| `assigned_at` | Number | Unix ts; `REMOVE`d on unassign |
| `queue_id` | String | Queue that performed auto-assign; `REMOVE`d on unassign |

`assigned_to` and `assigned_sub` are intentionally redundant: `assigned_to` is the human-readable field in `LeadOut`; `assigned_sub` is the GSI projection key (mirrors the `review.assigned_admin_sub` vs. top-level `assigned_admin_sub` pattern in `kyc_case_assignment.py:566-582`).

## 5. Detailed Behavior & Edge Cases

### `assign_lead` — write path

1. Read `PK=LEAD#{lead_id}` / `SK=META` from `T.leads`. 404 if missing.
2. Validate `assignee_sub` is non-empty. 400 `invalid_assignee` if blank.
3. Build `UpdateExpression`:
   - `SET assigned_to = :a, assigned_sub = :a, GSI_ASSIGN_SK = :sk, assigned_at = :ts, updated_at = :ts`
   - Where `:sk = f"STATUS#{lead.get('status', 'assigned')}"` (reflects the lead's current status so load-counting GSI queries match the correct status bucket).
   - If the lead's current status is `new`, additionally `SET GSI2PK = :s2pk` where `:s2pk = "STATUS#assigned"`, promoting the lead to `assigned` in the `ByStatus` GSI.
4. Write `PK=ASSIGN_AUDIT#{lead_id}` / `SK={ts:013d}#{event_id}` audit row.
5. Call `alerts.write_alert(assignee_sub, event="lead_assigned", outcome="info", title="New lead assigned to you", details={"lead_id": lead_id, "assigned_by": actor_sub})` in a `try/except` — a notification failure never blocks the assignment.
6. Call `alerts.audit_event("lead.assigned", actor_sub, lead_id=lead_id, assignee=assignee_sub)`.
7. Return `LeadAssignmentOut`.

Reassigning a lead that already has `assigned_to` set simply overwrites the value. The audit row captures `from_agent` and `to_agent` for history. This is idempotent: calling `assign_lead` with the same `assignee_sub` twice produces identical state (two audit rows, second is a no-op semantically).

### `unassign_lead` — REMOVE path

Uses `UpdateExpression = "REMOVE assigned_to, assigned_sub, GSI_ASSIGN_SK, assigned_at, queue_id SET updated_at = :ts"`. DynamoDB `REMOVE` on a non-existent attribute is a no-op, so calling unassign on an already-unassigned lead is safe. Writes audit row with `event_type="unassigned"`, `to_agent=None`.

### `auto_assign_round_robin` — selection algorithm

1. Load queue config. `LeadAssignmentError("queue_not_found", status_code=404)` if absent.
2. For each `user_sub` in `queue["agent_subs"]`, load `PK=AGENT#{sub}` / `SK=QUEUE#{queue_id}` to get `on_duty` and `max_leads`. Default `on_duty=True`, `max_leads=S.leads_assignment_max_leads_per_agent` if no availability row exists (new agent, not yet configured).
3. Call `_count_open_leads_for_agent(sub)` for each on-duty agent below capacity. This issues `Select=COUNT` queries on the `ByAssignedAgent` GSI, paginating `LastEvaluatedKey` and summing across `_ACTIVE_STATUS_GSI_KEYS` — exactly mirroring `kyc_case_assignment._count_active_for_admin` (`app/services/kyc_case_assignment.py:266-302`).
4. Filter out agents where `count >= max_leads`. If no eligible agents remain, return `None` (no assignment, no error raised — callers decide what to do with `None`).
5. Sort remaining agents: primary `count ASC`, secondary `last_assigned_at ASC` (None sorts first, so agents who have never been assigned are preferred), tertiary `user_sub ASC` (deterministic tiebreak).
6. Assign to `agents[0]`. Bump `last_assigned_at` on the AVAILABILITY row with `ConditionExpression="attribute_exists(pk)"` (guard against a race where the availability row was deleted between step 2 and step 6 — on `ConditionalCheckFailedException`, swallow the error, the assignment still proceeds).
7. Return `LeadAssignmentOut` with `event_type="auto_assigned"`.

### Flag-off behavior

`_check_assignment_flag()` returns HTTP 404 for all queue and assignment endpoints when `S.leads_assignment_enabled` is `False`. The service layer's `assign_lead` function also checks the flag and returns early (returning `None`) when called from other services (e.g., post-create auto-assign hook in LED-003). No DDB reads or writes occur when the flag is off.

### Empty queue

`auto_assign_round_robin` with a queue whose `agent_subs` list is empty returns `None` without writing any row and without raising an exception. Callers (e.g., an auto-assign-on-create hook) log a warning but do not fail the parent operation.

### Concurrent assignment race

Two simultaneous `assign_lead` calls for the same `lead_id` both succeed — DynamoDB `update_item` is not conditional on the current `assigned_to` value, so the second write wins. This is intentional; the audit log records both events. If stricter serialization is required in future, a `ConditionExpression="assigned_to = :current OR attribute_not_exists(assigned_to)"` can be added as a follow-up.

### Alert `lead_assigned` event registration

`alerts.write_alert` uses `ALERT_CATEGORIES` (`app/services/alerts.py:32`) to categorize events. The `"lead_assigned"` event is not currently in any category, so it falls through to the `"security"` default bucket in `get_alert_category` (`app/services/alerts.py:53-55`). LED-010 registers `"lead_assigned"` in the `"updates"` category by adding it to `ALERT_CATEGORIES["updates"]` (`app/services/alerts.py:40`) — additive, no existing entry is modified.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

- **DDB writes:** All queue config, agent availability, and audit rows go to `T.leads` (DynamoDB Local in dev, real DynamoDB in prod). No `S.dev_mode` branch exists; the same code path runs in both environments.
- **Alert delivery:** `alerts.write_alert` writes to `T.alerts` in both environments. `alerts.send_alert_email` writes to a dev log file in dev (`S.dev_mode=True` branch at `app/services/alerts.py:462`) and calls SES in prod — this is the existing parity mechanism, not a new branch in LED-010.
- **`audit_event`:** Writes to `T.alerts` in both environments without any `dev_mode` conditional.

### Idempotency

- `create_queue` is idempotent within a single run (duplicate name is allowed; a new `queue_id` is always minted on each call). Callers that want deduplication should call `list_queues` first.
- `assign_lead` called twice with the same `assignee_sub` produces identical DDB state (second `update_item` overwrites the same values). Two audit rows are written.
- `auto_assign_round_robin` called on an already-assigned lead reassigns it (no guard), producing a `reassigned` event type.
- `unassign_lead` on an already-unassigned lead is a no-op at the DDB layer (REMOVE of absent attributes succeeds silently); one audit row is still written.

### Security

- **Ownership enforcement:** `assign_lead` and `unassign_lead` read the lead META row and verify that `created_by == actor_sub` OR `actor_sub` has ADMIN/ROOT role before writing. Attempting to assign someone else's lead returns 403 `forbidden`.
- **Queue admin gates:** All queue CRUD and agent availability endpoints enforce `Role.ADMIN` or `Role.ROOT` via the `require_roles` pattern from `app/auth/policy.py:49`. Non-admin users receive 403.
- **`assignee_sub` validation:** The service validates that `assignee_sub` is a non-empty string but does not verify it maps to a real platform user (no cross-table lookup). This is consistent with the existing ticket assignment pattern where `assigned_to` is stored as-is.
- **Audit trail:** Every assignment event writes an immutable `ASSIGN_AUDIT#` row. These rows are never deleted.
- **CSRF:** All non-GET endpoints inherit CSRF enforcement from `require_ui_session` (`app/auth/deps.py` enforces `x-csrf-token` header for cookie-auth non-GET requests as noted in CLAUDE.md).

## 8. Backward Compatibility & Migration

### No table migration required

LED-010 adds columns (`assigned_sub`, `GSI_ASSIGN_SK`) and a new GSI (`ByAssignedAgent`) to the existing `leads` table. In dev, `just restart` recreates the table with the new `TableDef`. In production, `UpdateTable` must be called to add the GSI before LED-010 is deployed; DynamoDB populates the GSI asynchronously from existing items. During the backfill window:

- Newly assigned leads appear in `ByAssignedAgent` immediately (they carry `assigned_sub`).
- Pre-existing leads that have `assigned_to` but lack `assigned_sub` (from LED-003's stub `assign_lead`) do not appear in the GSI until they are touched. `_count_open_leads_for_agent` may under-count during the backfill window. This is acceptable — the system will self-correct as leads are reassigned.

### LED-003 stub compatibility

LED-003's `assign_lead` stub writes only `assigned_to` on the lead META row (no `assigned_sub`, no `GSI_ASSIGN_SK`). After LED-010 ships, `app/services/leads.py` `assign_lead` is replaced by a delegating call to `LeadAssignmentService().assign_lead(...)`. The LED-003 function signature is preserved (`assign_lead(lead_id, assignee_sub, actor_sub)`) so existing callers compile without changes.

### Flag rollout sequence

Recommended production rollout:
1. Deploy LED-010 code with `LEADS_ASSIGNMENT_ENABLED=0` (flag off).
2. Run `UpdateTable` to add `ByAssignedAgent` GSI. Wait for `ACTIVE` status.
3. Set `LEADS_ASSIGNMENT_ENABLED=1` to activate endpoints.

## 10. Open Questions / Assumptions

1. **Auto-assign on create:** LED-003's `create_lead` accepts an `assigned_to` field; if set, it calls `assign_lead` directly. Should `create_lead` also support an `auto_assign_queue_id` parameter that triggers `auto_assign_round_robin`? **Assumption:** Yes, as an optional `auto_assign_queue_id` field on `LeadCreateIn`; when present and the assignment flag is on, `create_lead` calls `auto_assign_round_robin` after writing the lead META row (best-effort, never blocks create).

2. **Cross-queue assignment:** Can a lead be assigned via a queue that the agent is not a member of? **Assumption:** No — `auto_assign_round_robin` only considers agents in the queue's `agent_subs` list. Manual `assign_lead` does not enforce queue membership.

3. **Notification content:** The alert sent to the assignee contains `lead_id`. Should it also include the lead's name and company? **Assumption:** Yes — add `first_name`, `last_name`, `company` (truncated to 100 chars) to the `details` dict in `write_alert`. These are already on the lead META row.

4. **Agent `user_sub` validation:** Should `set_agent_availability` verify that the `user_sub` maps to a real platform user via `T.users`? **Assumption:** No for MVP — consistent with how the KYC assignment service stores availability rows without cross-table user validation. The admin is responsible for providing valid subs.

5. **Queue deletion with active assignments:** Deleting a queue that has active assigned leads — should assigned leads be unassigned? **Assumption:** No — `delete_queue` soft-deletes the queue config row (sets `deleted_at`) but leaves `queue_id` on existing lead META rows as a historic reference. Leads remain assigned; they are not auto-unassigned.
