# EVT-005 — Geocode contact and account addresses, store lat/lng

**Type:** Feature | **Priority:** P2 | **Estimate:** 2d
**Source:** `docs/suitecrm/CRM_MISC_TICKETS.md` (section "EVT-005")
**Dependencies:** EVT-001 (flag pattern + `_require_crm_events_enabled` guard convention). PTY-001 is a soft
prerequisite: the lat/lng write to `T.party` is conditional on that table's existence (see §5).

---

## 1. Summary & Goal

EVT-005 extends the deterministic mock geocoding pattern already present in
`app/services/kyc_address_verification._geocode` (lines 210–224) to the general CRM surface: user address
book entries (the existing `addresses` table), and — once PTY-001 ships — party/contact/account records.
The ticket delivers:

1. A new service `app/services/crm_geocoding.py` that encapsulates address-to-lat/lng logic behind a single
   new feature flag `crm_geocoding_enabled` (default OFF).
2. Best-effort background geocoding wired into the address creation and update endpoints in
   `app/services/addresses.py` / `app/routers/addresses.py`.
3. A `PATCH /ui/addresses/{address_id}/geocode` endpoint that allows an explicit, on-demand re-geocode of
   a single saved address.
4. A `GET /ui/addresses/geocoded` endpoint that lists all of the caller's addresses that carry `lat`/`lng`.
5. Additive `lat`, `lng`, `geocoded_at` attributes written onto rows in the existing `addresses` DDB table
   (PK=`user_sub`, SK=`address_id`). No new table is required.
6. A forward-compatibility write path to `T.party` (when the table is available) so EVT-006 (proximity
   search) and EVT-007 (map view) can consume coordinates from the Party model once PTY-001 merges.

With `CRM_GEOCODING_ENABLED=0` (the default) every new code path is a no-op and the platform is
byte-for-byte identical to its pre-EVT-005 state.

## 2. Context & Current State

### 2.1 Existing geocoding pattern (KYC)

`app/services/kyc_address_verification._geocode` (lines 210–224) already implements a deterministic,
flag-gated mock geocoder:

```
# app/services/kyc_address_verification.py:210-224
def _geocode(address: dict[str, Any]) -> dict[str, float] | None:
    if not S.kyc_address_geocoding_enabled:
        return None
    fp = _address_fingerprint(address)
    digest = hashlib.sha256(fp.encode("utf-8")).digest()
    lat_raw = int.from_bytes(digest[0:4], "big")
    lng_raw = int.from_bytes(digest[4:8], "big")
    lat = round((lat_raw % 180_000_000) / 1_000_000.0 - 90.0, 6)
    lng = round((lng_raw % 360_000_000) / 1_000_000.0 - 180.0, 6)
    return {"lat": lat, "lng": lng}
```

The helper `_address_fingerprint` (lines 192–202) normalises six fields (`line_1`/`line1`, `line_2`/`line2`,
`city`, `state`, `postal_code`, `country`) into a pipe-delimited string and is used as the SHA-256 pre-image.
The KYC geocoding flag is at `app/core/settings.py:1455–1457` (`KYC_ADDRESS_GEOCODING_ENABLED`, default
`"true"`). EVT-005 introduces a separate flag so the two concerns are independently controlled.

### 2.2 Address service and table

`app/services/addresses.py` manages the `addresses` DDB table (PK=`user_sub`, SK=`address_id`, declared at
`scripts/local-ddb-init.py:98`). Key functions:
- `create_address(user_sub, payload)` — normalises via `normalize_address_payload`, writes via
  `T.addresses.put_item` (line 88).
- `update_address(user_sub, address_id, payload)` — read-modify-write via `T.addresses.put_item` (line 102).
- `get_address(user_sub, address_id)` — `get_item` returning the raw DDB item (line 69, not 70; raises `HTTPException(404)` when absent).

Neither function currently writes `lat`, `lng`, or `geocoded_at`; these fields are absent from all existing
items. The `normalize_address_payload` function (line 39) strips `None` values before persisting, so any
additive float fields introduced by EVT-005 will simply not appear in pre-existing rows.

### 2.3 Contacts router

`app/routers/contacts.py` (prefix `/ui/contacts`, registered at `app/main.py:683`) manages
`T.contacts` (PK=`owner_id`, SK=`contact_id`, declared at `scripts/local-ddb-init.py:691`). Contact items
store an opaque `contact_id` equalling the target user's `user_sub` together with `display_name` and
`profile_photo_url`; they do **not** store a postal address. Consequently EVT-005 does not hook directly into
the contacts router — the canonical address surface for a platform user is the `addresses` table managed by
`app/services/addresses.py`.

### 2.4 Party table (PTY prerequisite)

`T.party` does not exist in `app/core/tables.py` at the time this spec is written. (Verification
correction: the canonical PTY spec is `docs/ofbiz/specs/PTY-001.md`; there is no
`docs/suitecrm/PARTY_CRM_TICKETS.md`.) Per `docs/ofbiz/specs/PTY-001.md:1,10,73,98`, PTY-001 introduces
ONLY the `party_table_name` setting (`DDB_PARTY_TABLE`, default `"party"`), the `party_crm_enabled` flag,
and the `Tables.party` handle (`party=_safe_table(S.party_table_name)`) — it does **not** define the
`party` `TableDef`/KeySchema (that is PTY-002's scope). The party **PK/SK** (assumed `user_sub`/`party_id`
in this spec) is therefore NOT yet fixed by PTY-001 and remains an assumption (see §10 Open Question #5);
`geocode_party_address` must read the actual key schema once PTY-002 lands. The helper in §4 skips its
write when the `T.party` handle is absent, making the dependency soft.

### 2.5 Settings and flag conventions

`app/core/settings.py` is a frozen `@dataclass` (line 6). New default-OFF boolean flags follow the
`os.environ.get("VAR", "false").lower() in ("1", "true", "yes", "on")` pattern (e.g.
`newsfeed_recsys_enabled` at line 2014). EVT-001 adds `crm_events_enabled` with this same convention.
EVT-005 adds `crm_geocoding_enabled` alongside it.

### 2.6 Audit and alert primitives

`app/services/alerts.audit_event` (line 644) is the canonical audit write. `send_alert_email` (line 459)
is the canonical transactional email dispatch. Neither is needed on the geocoding hot-path (geocoding is
transparent to the end user) but `audit_event` is emitted once per explicit re-geocode request so that
address coordinate changes appear in the audit log.

## 3. Data Model

### 3.1 No new DynamoDB table

EVT-005 writes three additive attributes onto items in the **existing** `addresses` table
(`app/core/tables.py:345`, `scripts/local-ddb-init.py:98`):

| Attribute | DDB type | Description |
|-----------|----------|-------------|
| `lat` | N (stored as Python `Decimal` via boto3) | Latitude in \[-90, 90\], 6 decimal places |
| `lng` | N | Longitude in \[-180, 180\], 6 decimal places |
| `geocoded_at` | N | Unix timestamp (`now_ts()`) of last geocoding attempt |

These attributes are **sparse**: rows created before EVT-005 or with `CRM_GEOCODING_ENABLED=0` carry none of
them. Existing queries against the table (`list_addresses`, `get_address`, `search_addresses`) silently skip
these unknown fields, so no migration is required.

No new GSI is introduced in this ticket. EVT-006 (proximity search) will perform a full scan of geocoded
addresses and apply Haversine filtering in Python; a GSI on `lat`/`lng` would not accelerate that query
pattern and would add unnecessary write overhead.

### 3.2 Party forward-compatibility (soft write)

When `T.party` exists (post-PTY-001) the service writes the same three attributes onto the party item via
`update_item` with `SET lat = :lat, lng = :lng, geocoded_at = :ts`. The write is wrapped in `try/except`
and never raises. No `attr_types` change is needed in `scripts/local-ddb-init.py` because the party table's
`TableDef` is declared by PTY-002 (PTY-001 ships only the `T.party` handle + `party_table_name` setting —
see §2.4 verification correction).

### 3.3 Settings additions (`app/core/settings.py`)

```python
crm_geocoding_enabled: bool = os.environ.get(
    "CRM_GEOCODING_ENABLED", "false"
).lower() in ("1", "true", "yes", "on")

crm_geocoding_provider_url: str = os.environ.get("CRM_GEOCODING_PROVIDER_URL", "")
# Empty string = use the deterministic mock (dev + any env without a real provider).
# Non-empty = call the external Nominatim/Google Maps REST endpoint (prod).

crm_geocoding_batch_limit: int = int(os.environ.get("CRM_GEOCODING_BATCH_LIMIT", "100"))
# Max addresses processed per background re-geocode sweep.
```

## 4. API / Service Design

### 4.1 New service: `app/services/crm_geocoding.py`

```python
def _address_fingerprint_crm(address: dict) -> str:
    """
    Same normalisation as kyc_address_verification._address_fingerprint (lines
    192-202) but imported from a shared internal helper to avoid duplication.
    Accepts both line1/line2 and line_1/line_2 variants.
    """

def geocode_address(address: dict) -> dict[str, float] | None:
    """
    Returns {"lat": float, "lng": float} or None.

    Dev / no-provider path (S.crm_geocoding_provider_url == ""):
      Deterministic SHA-256 mock identical to kyc_address_verification._geocode
      (lines 218-223). Same byte-for-byte mapping: lat in [-90, 90],
      lng in [-180, 180], 6 decimal places.

    Prod path (S.crm_geocoding_provider_url != ""):
      HTTP GET to S.crm_geocoding_provider_url with query params derived from
      the address fields; parses first result's lat/lng; returns None on
      non-200 or empty result set. Uses requests.get with a 5-second timeout.
      Both paths run in dev and prod — there is NO dev_mode branch. The mock
      path is activated by the absence of a provider URL, not by S.dev_mode.

    Returns None (never raises) when S.crm_geocoding_enabled is False.
    """

def apply_geocode_to_address(user_sub: str, address_id: str) -> dict | None:
    """
    Reads the address item from T.addresses, calls geocode_address on it,
    and — if a result is returned — writes lat/lng/geocoded_at back via
    update_item. Returns the updated item dict or None if geocoding returned
    no result.

    Emits audit_event("crm_address_geocoded", user_sub, address_id=address_id,
    lat=lat, lng=lng) on success.
    Raises nothing — all DDB and network errors are caught and logged.
    """

def geocode_party_address(party_id: str, address: dict) -> None:
    """
    Soft write to T.party when the table handle is available.
    Calls geocode_address(address); if a result is returned, calls
    T.party.update_item(Key={"party_id": party_id}, ...) with lat/lng/geocoded_at.
    Skips entirely (no-op, no exception) if:
      - S.crm_geocoding_enabled is False, or
      - T.party attribute is None / missing on the Tables dataclass, or
      - geocode_address returns None (empty address), or
      - any DDB exception occurs.
    """

def list_geocoded_addresses(user_sub: str) -> list[dict]:
    """
    Queries T.addresses for all items belonging to user_sub, returns only
    those that carry both 'lat' and 'lng' attributes.

    NOTE (verification correction): the existing list_addresses
    (app/services/addresses.py:64-67) does a SINGLE query() call with no
    LastEvaluatedKey loop — it does NOT paginate. list_geocoded_addresses
    must therefore IMPLEMENT its own LastEvaluatedKey loop (per the CLAUDE.md
    DDB 1MB/FilterExpression gotcha) rather than "reuse the same pagination
    loop as list_addresses" — there is no such loop to reuse.
    """
```

### 4.2 New router: `app/routers/crm_geocoding.py`

Prefix: `/ui/crm/geocoding`
Tags: `["crm_geocoding"]`
All endpoints: `Depends(require_ui_session)` + inline flag guard (raises `HTTPException(404)` when
`S.crm_geocoding_enabled` is `False`).

#### 4.2.1 `PATCH /ui/crm/geocoding/addresses/{address_id}`

Explicit on-demand re-geocode of a single saved address.

```
Request:  no body (address data read from T.addresses)
Response: GeocodedAddressOut
Errors:
  404 — feature flag off
  404 — address not found or not owned by caller
  422 — address has no geocodable fields (all blank)
```

**Pydantic models** (added to `app/models.py`):

```python
class GeocodedAddressOut(BaseModel):
    address_id: str
    lat: float
    lng: float
    geocoded_at: int
    line1: Optional[str] = None
    city: Optional[str] = None
    state: Optional[str] = None
    postal_code: Optional[str] = None
    country: Optional[str] = None
```

**Behavior:**
1. Guard: raise 404 if flag off.
2. `get_address(user_sub, address_id)` — raise 404 if not found.
3. `apply_geocode_to_address(user_sub, address_id)` — returns updated item.
4. If updated item has no `lat` (geocoder returned None), raise 422 "Address could not be geocoded".
5. Return `GeocodedAddressOut` built from the updated item.

#### 4.2.2 `GET /ui/crm/geocoding/addresses`

Returns all of the caller's addresses that have been geocoded.

```
Response: GeocodedAddressListOut
  {
    "addresses": list[GeocodedAddressOut],
    "count": int
  }
Errors:
  404 — feature flag off
```

### 4.3 Hooks into existing address endpoints

In `app/services/addresses.py`, `create_address` and `update_address` are extended with a best-effort
background geocoding call. Because `app/routers/addresses.py` uses synchronous FastAPI handlers (no
`BackgroundTasks` currently), the pattern follows `app/routers/privacy.py:80` which passes a
`BackgroundTasks` parameter to its handler and calls `background_tasks.add_task(...)`.

**Changes to `app/routers/addresses.py`** (the router file that calls `create_address` and
`update_address`):
- Import `BackgroundTasks` from `fastapi`.
- Add `background_tasks: BackgroundTasks` parameter to the `POST /ui/addresses` (create) and
  `PATCH /ui/addresses/{address_id}` (update) handlers.
- After the service call succeeds, add:
  ```python
  if S.crm_geocoding_enabled:
      background_tasks.add_task(
          apply_geocode_to_address, user_sub, item["address_id"]
      )
  ```

This pattern keeps geocoding off the request path: the HTTP response is returned immediately and geocoding
runs after the response is flushed, exactly as the privacy export (`app/routers/privacy.py:80`) does.

The `app/services/addresses.py` functions themselves are not modified — the hook lives in the router layer.

### 4.4 Router registration in `app/main.py`

```python

# ...
app.include_router(crm_geocoding_router)
```

No startup task is registered by this ticket. EVT-006 may add a batch re-geocode sweep later.

## 5. Detailed Behavior & Edge Cases

### 5.1 Mock vs real provider selection

The mock path is selected when `S.crm_geocoding_provider_url == ""` (the default). This is orthogonal to
`S.dev_mode`. An operator can configure a real Nominatim endpoint in dev, or keep the mock in a restricted
prod environment. There is no `if S.dev_mode` branch in `crm_geocoding.py`.

### 5.2 Determinism of mock output

For a fixed address, `geocode_address` always returns the same `lat`/`lng`. The SHA-256 pre-image is
`_address_fingerprint_crm(address)` — the same pipe-delimited normalised string used by
`kyc_address_verification._address_fingerprint` (lines 192–202). Two calls with the same field values
(regardless of key casing `line1` vs `line_1`) produce identical coordinates. This makes unit tests
deterministic without mocking the function.

### 5.3 Partial / empty addresses

`geocode_address` returns `None` when the fingerprint is entirely blank (all six normalised parts are
empty strings). `apply_geocode_to_address` treats a `None` result as "no coordinates available" and does not
write `lat`/`lng`/`geocoded_at`. Existing items that had no geocodable data remain unchanged.

### 5.4 Re-geocoding an already-geocoded address

`apply_geocode_to_address` always overwrites `lat`/`lng`/`geocoded_at` if the geocoder returns a result.
This is intentional: an address that was previously geocoded with the mock should be upgradeable to real
coordinates by toggling the provider URL without any data migration.

### 5.5 `PATCH .../geocode` on a non-existent or foreign address

`get_address(user_sub, address_id)` raises `HTTPException(404)` when the item is absent or owned by a
different `user_sub` (because the DDB `get_item` uses `Key={"user_sub": user_sub, "address_id": address_id}`
— the partition key enforces ownership). The router propagates the 404.

### 5.6 Background geocoding failure

If `apply_geocode_to_address` throws (DDB write failure, network error to real provider), it catches the
exception, logs it at WARNING level, and returns `None`. The `background_tasks.add_task` wrapper means this
never surfaces as an HTTP error to the caller. The address item remains unchanged (no partial writes).

### 5.7 `geocode_party_address` with missing T.party

Until PTY-001 ships, `T.party` is not a field on the `Tables` dataclass. The implementation checks
`hasattr(T, "party") and T.party is not None` before attempting any DDB operation. The function is
designed to be called from EVT-002 / PTY-001 once those tables exist; in the meantime it is a no-op.

### 5.8 Prod provider HTTP call

In the real-provider path, `geocode_address` issues a synchronous `requests.get(url, params=..., timeout=5)`.
It parses Nominatim's JSON response shape (`[{"lat": "...", "lon": "..."}]`). A non-200 response, an empty
array, or a `requests.exceptions.RequestException` all return `None` (best-effort). The call is made inside
`apply_geocode_to_address` which always runs in a `BackgroundTasks` worker thread (or the explicit PATCH
handler), never on the asyncio event loop — so blocking I/O is acceptable.

### 5.9 Rate limiting the PATCH endpoint

The explicit re-geocode PATCH endpoint uses the existing `_bucket_limit` helper from
`app/services/rate_limit.py` (signature `_bucket_limit(user_sub, sid, max_n, win)` at `rate_limit.py:60`).
The canonical call is `_bucket_limit(user_sub, "rl#geocode", 20, 60)` — the second arg is a string bucket
label (matching the established `"rl#csv_export"` / `"rl#verify_email"` idiom at `csv_export.py:66` /
`rate_limit.py:316`), NOT a `geocode:{user_sub}` composite. Window 60 s, limit 20 calls. This prevents
a client from hammering the real geocoding provider through the API. The background-triggered geocoding
(from create/update) is not rate-limited since it fires at most once per address write.

### 5.10 `list_geocoded_addresses` pagination

The function issues one `query()` per page using `LastEvaluatedKey` and collects all items before
filtering. NOTE (verification correction): `list_addresses` (`addresses.py:64–67`) does NOT loop —
it is a single `query()` call — so `list_geocoded_addresses` must add its own `LastEvaluatedKey`
loop, it cannot "reuse" a loop that does not exist. DDB's `FilterExpression` cannot be used
efficiently here because `lat`/`lng` are sparse; the Python-side filter is applied after full retrieval,
consistent with the CLAUDE.md DDB gotcha: "DynamoDB fetches up to 1MB before applying FilterExpression".

## 6. Feature Flag & Config

| Settings key | Env var | Default | Purpose |
|---|---|---|---|
| `crm_geocoding_enabled` | `CRM_GEOCODING_ENABLED` | `false` | Master gate: all EVT-005 routes return 404 and all background hooks are no-ops when off |
| `crm_geocoding_provider_url` | `CRM_GEOCODING_PROVIDER_URL` | `""` | Empty = deterministic mock; non-empty = external Nominatim/Google Maps REST endpoint |
| `crm_geocoding_batch_limit` | `CRM_GEOCODING_BATCH_LIMIT` | `100` | Max addresses per future background sweep (EVT-006) |

All three fields are added to `app/core/settings.py` in the `Settings` frozen dataclass.

The flag is checked in three places:
1. `geocode_address()` — returns `None` immediately if flag is off.
2. Router-layer guard in `app/routers/crm_geocoding.py` — raises `HTTPException(404)`.
3. Background-task conditional in `app/routers/addresses.py` — skips `background_tasks.add_task`.

This triple-gate ensures that with the flag off there is zero execution overhead: no DDB reads, no network
calls, no task queuing.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

The same `geocode_address` function runs in dev and prod. The only difference is the value of
`S.crm_geocoding_provider_url`:

- **Dev** (`CRM_GEOCODING_PROVIDER_URL` unset): deterministic SHA-256 mock, no network calls, fully offline.
- **Prod** (`CRM_GEOCODING_PROVIDER_URL` set to a real endpoint): HTTP request to external service.

There is no `if S.dev_mode` branch. The mock is activated by the empty URL, not by dev mode. This means
integration tests that set `CRM_GEOCODING_PROVIDER_URL` to a test server get the same real HTTP code path
as production.

### 7.2 Idempotency

`apply_geocode_to_address` is idempotent: re-running it on an already-geocoded address overwrites `lat`,
`lng`, `geocoded_at` with the same values (mock) or updated values (real provider). No conditional write is
needed because overwriting coordinates is always safe.

The PATCH endpoint is idempotent (calling it twice on the same address produces the same final state).

### 7.3 Security

- **Ownership enforcement**: `get_address(user_sub, address_id)` uses a composite DDB key
  `{user_sub, address_id}`, so one user cannot geocode another user's address. The partition key is always
  the authenticated caller's `user_sub`.
- **No PII in provider request**: the geocoding provider request contains only address fields (line1, city,
  state, postal_code, country) — no user identity, session token, or internal IDs.
- **Provider URL validation**: `S.crm_geocoding_provider_url` is read from env at startup. The value is
  used as a URL prefix for `requests.get`; it must be an `https://` URL in prod (enforced by documentation
  and ops runbooks, not in code — same pattern as `S.public_base_url`).
- **Stored coordinates**: `lat`/`lng` are floating-point values derived from the address itself; they do not
  reveal any information not already present in the address. No KMS encryption is applied (addresses are
  already stored in plaintext).
- **Rate limiting**: the PATCH endpoint is rate-limited (§5.9) to prevent provider abuse.

## 8. Backward Compatibility & Migration

### 8.1 Existing address items

Pre-existing rows in the `addresses` table have no `lat`, `lng`, or `geocoded_at` attributes. This is
correct: sparse attributes in DDB single-table design are intentional. The `AddressOut` Pydantic model
in `app/models.py` does not declare these fields, so existing API consumers see no change. The
`GeocodedAddressOut` model (new, EVT-005-only) adds them.

No backfill migration is required for this ticket. A future admin-sweep endpoint (potentially in EVT-006
or as a standalone task) can iterate all addresses and geocode those lacking coordinates.

### 8.2 `app/services/addresses.py` functions

`create_address` and `update_address` are **not modified**. All new logic is in the router layer
(`app/routers/addresses.py`) via `BackgroundTasks`, keeping the service layer pure and testable without
mocking geocoding.

### 8.3 `normalize_address_payload` filter

`normalize_address_payload` (addresses.py:39) strips `None` values via `{k: v for k, v in out.items() if
v is not None}`. It only normalises the nine explicitly listed keys and does not touch `lat`, `lng`, or
`geocoded_at`. An `update_address` call therefore cannot accidentally overwrite or delete these geocoded
attributes.

### 8.4 `just restart` impact

`scripts/local-ddb-init.py` does not need to be changed by this ticket (no new table, no new GSI). Running
`just restart` after merging EVT-005 leaves all existing tables intact and simply deploys the new flag
and service code.

## 10. Open Questions / Assumptions

1. **Nominatim rate limits**: The Nominatim public API requires a `User-Agent` header and enforces 1
   request/second. The `crm_geocoding_provider_url` configuration should point to a self-hosted or
   licensed Nominatim instance in production, not `nominatim.openstreetmap.org`. This is an ops
   concern, not a code concern; the service does not enforce any specific URL.

2. **`_address_fingerprint_crm` vs re-import**: The fingerprint logic in
   `kyc_address_verification._address_fingerprint` (lines 192–202) is a private function. `crm_geocoding.py`
   should duplicate the 10-line implementation rather than import from `kyc_address_verification` to avoid
   creating a KYC-to-CRM import dependency. The duplicated code is small and the normalisation rules are
   stable.

3. **`AddressOut` model extension**: This spec does not add `lat`/`lng` to `AddressOut` (defined at
   `app/models.py:1427`). Adding them would break clients that do not expect these fields if the flag is on.
   The separate `GeocodedAddressOut` model keeps the surfaces cleanly separated. If the team decides to
   surface coordinates in the main address list, that is a follow-on scope change.

4. **Batch backfill**: No backfill endpoint is specified in this ticket. All existing address items will
   lack coordinates until the user updates their address or calls the PATCH endpoint. A background admin
   sweep can be added in EVT-006 or a separate INFRA ticket.

5. **Assumption — party table schema**: This spec assumes PK=`user_sub` and SK=`party_id`. Verification
   note: PTY-001 (`docs/ofbiz/specs/PTY-001.md`) does NOT define the party `TableDef`/KeySchema — it only
   ships the `T.party` handle and `party_table_name` setting; the table definition (and thus its real PK/SK)
   is **PTY-002's** scope. So this PK/SK is unconfirmed and `geocode_party_address` must be adjusted to the
   actual schema once PTY-002 merges.
