# LED-007 — Prospect (Target) record — external email-only contact

**Type:** Feature  **Priority:** P1  **Estimate:** 2 days
**Ticket source:** `docs/suitecrm/CRM_LEADS_TICKETS.md`, section "LED-007"

---

## 1. Summary & Goal

LED-007 delivers the Prospect (Target) entity — a lightweight record for external
email-only contacts that have no platform user account. Prospects are the CRM
counterpart of SuiteCRM's "Target" object: they represent real people who are known
only by an email address (and optionally a name, phone, and company), who are
candidates for marketing outreach or nurture sequences but are not yet in the
leads pipeline.

The Prospect entity is stored in the same `leads` DynamoDB table delivered by
LED-001 using a distinct `PK=PROSPECT#{prospect_id}` namespace, reusing all
infrastructure already in place. LED-007 adds:

- A **ByEmail GSI** (`GSI4`) on the `leads` table for O(1) duplicate lookup by
  normalized email — the primary uniqueness constraint for external contacts.
- A **`ProspectUpdateIn`** Pydantic model (additive; `ProspectCreateIn` and
  `ProspectOut` are already added by LED-002).
- Five service functions in `app/services/leads.py`: `create_prospect`,
  `get_prospect`, `list_prospects`, `update_prospect`, `delete_prospect`.
- A helper `find_prospect_by_email` for internal deduplication use.
- A soft dependency on MKT-007 via `add_prospect_to_contact_list`, wrapped in a
  `try/except ImportError` shim so deployment order does not matter.
- Five REST endpoints registered in the `app/routers/leads.py` router (delivered
  fully by LED-013; LED-007 may define endpoints now or defer to LED-013 per team
  preference — this spec covers both paths).

With `LEADS_ENABLED=0` (the default), the platform is byte-for-byte unchanged:
no new routes exist, no background work runs, and no existing file is modified.

## 3. Data Model

### 3.1 GSI4 — ByEmail (new; added to the `leads` table)

LED-007 adds a fourth GSI to the single `leads` table established by LED-001.

| Attribute | GSI4 role | Value written on Prospect row |
|---|---|---|
| `GSI4PK` | Partition key (string) | `EMAIL#{normalized_email}` |
| `GSI4SK` | Sort key (number) | `{created_at}` (Unix integer) |

Index name: `ByEmail`. Projection: `ALL`.

This GSI enables O(1) duplicate lookup: `query(IndexName="ByEmail", KeyConditionExpression=Key("GSI4PK").eq(f"EMAIL#{norm_email}"))` without a table scan. The same GSI is reused by LED-009 (`find_duplicates`) for email-based duplicate detection on Leads (LED-009 adds `ByEmail` usage independently; LED-007 is the GSI's origin).

**`attr_types` update** — the existing LED-001 `TableDef` entry must be extended:

```python
# scripts/local-ddb-init.py
TableDef(
    _resolve_table_name(S.leads_table_name, "leads"),
    "pk", "sk",
    gsi=[
        {"index_name": "ByOwner",  "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "ByStatus", "partition_key": "GSI2PK", "sort_key": "GSI2SK"},
        {"index_name": "BySource", "partition_key": "GSI3PK", "sort_key": "GSI3SK"},
        {"index_name": "ByEmail",  "partition_key": "GSI4PK", "sort_key": "GSI4SK"},  # LED-007
    ],
    attr_types={
        "GSI1SK": "N", "GSI2SK": "N", "GSI3SK": "N",
        "GSI4SK": "N",   # LED-007 — numeric, must declare or ValidationException
    },
)
```

Omitting `"GSI4SK": "N"` causes DynamoDB to treat it as a string, yielding
`ValidationException` when queried with integer range conditions.

### 3.2 Prospect META row schema

Every Prospect is a single DynamoDB item in the `leads` table:

| Attribute | Type | Value |
|---|---|---|
| `pk` | S | `PROSPECT#{prospect_id}` |
| `sk` | S | `META` |
| `prospect_id` | S | `"pros_" + uuid4().hex[:20]` |
| `owner_sub` | S | `user_sub` of the creator |
| `email` | S | Normalized (lowercase, stripped) |
| `first_name` | S or absent | Optional |
| `last_name` | S or absent | Optional |
| `phone` | S or absent | Normalized E.164, optional |
| `company` | S or absent | Optional, max 200 chars |
| `suppressed` | BOOL | `True` if opted out at create time |
| `created_at` | N | `now_ts()` |
| `updated_at` | N | `now_ts()` at last write |
| `deleted_at` | N or absent | Soft-delete timestamp |
| `GSI1PK` | S | `OWNER#{owner_sub}` |
| `GSI1SK` | N | `created_at` |
| `GSI2PK` | S | `STATUS#prospect` |
| `GSI2SK` | N | `created_at` |
| `GSI4PK` | S | `EMAIL#{normalized_email}` |
| `GSI4SK` | N | `created_at` |

`GSI3PK` / `GSI3SK` (BySource) are intentionally omitted — Prospects have no
`lead_source` field. The ByOwner and ByStatus GSIs project Prospects into the same
index as Leads, enabling a future unified list query. `STATUS#prospect` is a
sentinel partition key value that keeps Prospect rows queryable separately from
any `LEAD_STATUS` value (which are `STATUS#new`, `STATUS#assigned`, etc.).

### 3.3 Uniqueness constraint

Email uniqueness is enforced at the service layer (not a DynamoDB condition):
`create_prospect` calls `find_prospect_by_email(normalized_email)` which queries
`ByEmail` GSI. If a row is found and `deleted_at` is absent (active record), the
existing item is returned without writing a duplicate. Soft-deleted rows (have
`deleted_at`) are ignored — a new Prospect can be created for the same email after
soft-deletion.

### 3.4 Soft delete

`delete_prospect` writes `deleted_at = now_ts()` and `GSI2PK = "STATUS#deleted"`
via `update_item`. The `ByEmail` GSI entry (`GSI4PK`) is retained so that a
subsequent `create_prospect` for the same email correctly ignores the deleted row
(checks `deleted_at` presence) and creates a fresh record.

## 4. API / Service Design

### 4.1 New Pydantic model: `ProspectUpdateIn`

Add to `app/models.py` immediately after `ProspectOut` (LED-002 block, around
line 4927 region):

```python
class ProspectUpdateIn(BaseModel):
    first_name: Optional[str] = Field(default=None, max_length=120)
    last_name: Optional[str] = Field(default=None, max_length=120)
    phone: Optional[str] = None
    company: Optional[str] = Field(default=None, max_length=200)
    # email is intentionally absent — changing an email creates a new identity;
    # callers must delete and re-create if they need to change the email.
```

Email is immutable after creation. Changing email would break GSI4 (the ByEmail
key is written at create time and DynamoDB has no "move key" primitive — it would
require a delete + re-write, which is semantically a new Prospect). If a caller
needs to correct an email, they must `delete_prospect` and `create_prospect`.

### 4.2 Service functions (`app/services/leads.py`)

All functions are guarded by a `if not S.leads_enabled: raise HTTPException(404)`
check at the router layer (not the service layer) consistent with the flag-off
contract: the service functions themselves are always importable.

```python
def find_prospect_by_email(normalized_email: str) -> Optional[dict]:
    """Query ByEmail GSI (GSI4PK=EMAIL#{normalized_email}), return first active row.

    Returns None if not found or if found row has deleted_at set.
    Paginates if multiple rows exist (e.g., after re-create cycles).
    Uses Key("GSI4PK").eq(f"EMAIL#{normalized_email}").
    """

def create_prospect(owner_sub: str, data: ProspectCreateIn) -> dict:
    """Idempotent: returns existing active Prospect if email already present.

    Steps:
    1. normalize_email(data.email) → raises HTTP 400 on invalid format.
    2. normalize_phone(data.phone) if data.phone is not None → raises HTTP 400
       on invalid format. If phone is absent, skip normalization silently.
    3. find_prospect_by_email(norm_email) → if found (active), return existing item.
    4. Opt-out check: try/except wraps is_user_opted_out(norm_email); suppressed=True
       if opted out, suppressed=False on any error (fail-open).
    5. prospect_id = "pros_" + uuid4().hex[:20]; ts = now_ts().
    6. put_item with all attributes from §3.2 schema.
    7. audit_event("prospect.created", owner_sub, prospect_id=prospect_id,
                   email=norm_email) via app/services/alerts.audit_event (line 644).
    8. Return the written item dict.
    """

def get_prospect(prospect_id: str) -> Optional[dict]:
    """get_item(Key={"pk": f"PROSPECT#{prospect_id}", "sk": "META"}).
    Returns None if not found or if deleted_at is set.
    """

def list_prospects(
    owner_sub: str,
    *,
    cursor: Optional[str] = None,
    limit: int = 50,
    include_suppressed: bool = True,
    include_deleted: bool = False,
) -> dict:
    """Query ByOwner GSI (GSI1PK=OWNER#{owner_sub}) with a FilterExpression to
    keep only PROSPECT# pk values (FilterExpression=Attr("pk").begins_with("PROSPECT#")).
    Also filters out deleted rows unless include_deleted=True.
    Also filters out suppressed rows when include_suppressed=False.

    Note: FilterExpression does not reduce DDB page size (CLAUDE.md gotcha).
    Must loop via LastEvaluatedKey until `limit` results are collected or
    no more pages remain.

    Pagination via encode_cursor(last_evaluated_key) / decode_cursor(cursor).
    Returns {"prospects": [list of item dicts], "cursor": Optional[str], "count": int}.
    """

def update_prospect(
    prospect_id: str,
    actor_sub: str,
    data: ProspectUpdateIn,
) -> dict:
    """Fetch the existing Prospect (404 if absent or deleted).
    Build an update_item UpdateExpression for non-None fields in data.
    Always update updated_at = now_ts().
    Phone: if data.phone is not None, normalize via normalize_phone (HTTP 400 on
    invalid); if data.phone is explicitly None, do not unset (callers send
    ProspectUpdateIn with phone=None to leave unchanged; to clear a phone number
    they must supply phone="").
    Emit audit_event("prospect.updated", actor_sub, prospect_id=prospect_id).
    Returns updated item dict.
    """

def delete_prospect(prospect_id: str, actor_sub: str) -> None:
    """Soft-delete: update_item sets deleted_at=now_ts(), GSI2PK="STATUS#deleted".
    Idempotent: if already deleted, returns silently.
    Emit audit_event("prospect.deleted", actor_sub, prospect_id=prospect_id).
    Does NOT remove GSI4PK/GSI4SK — the email slot remains queryable so
    find_prospect_by_email can detect and skip soft-deleted rows.
    """

def add_prospect_to_contact_list(prospect_id: str, list_id: str) -> None:
    """Soft dependency on MKT-007 marketing_lists.add_member().

    try:
        from app.services.marketing_lists import add_member
        prospect = get_prospect(prospect_id)
        if not prospect:
            raise ValueError(f"Prospect {prospect_id} not found")
        add_member(list_id=list_id, email=prospect["email"],
                   suppressed=prospect.get("suppressed", False))
    except ImportError:
        pass   # MKT-007 not yet deployed; silently skip
    """
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent create / deduplication

`create_prospect` must never write two active rows for the same normalized email.
The lookup via `find_prospect_by_email` uses `ByEmail` GSI (a read, not a
conditional write). This means there is a small TOCTOU window under concurrent
creates with the same email. Mitigation: the GSI query runs with
`ConsistentRead=False` (GSIs do not support consistent reads in DynamoDB), so
two concurrent creates could both see "not found" and both write. To close this,
the `put_item` uses a `ConditionExpression=Attr("pk").not_exists()` guard. If the
condition fails (409 from DynamoDB), the service catches `ConditionalCheckFailedException`
and falls back to `find_prospect_by_email` to return the just-written row.

### 5.2 `include_suppressed` in list

By default `list_prospects` returns suppressed Prospects (`include_suppressed=True`).
Campaign senders (via MKT integration) must filter `suppressed=True` records at
their layer. The `GET /ui/leads/prospects?include_suppressed=false` query param
surfaces a pre-filtered list for convenience (implemented as
`FilterExpression=Attr("suppressed").eq(False)` inside the DDB loop).

### 5.3 Opt-out check timing and re-check

The opt-out check runs at `create_prospect` time and sets `suppressed` persistently
on the row. It does not re-run on subsequent `list_prospects` calls. If a Prospect
later opts out (via MKT or cart-reminder unsubscribe), MKT-007's `add_member` call
is responsible for updating the `suppressed` flag on existing Prospect rows. This
is out of scope for LED-007; the spec records the assumption as an open question
(§10.2).

### 5.4 Phone normalization on optional field

`normalize_phone` (line 66 of `app/core/normalize.py`) raises HTTP 400 for
unrecognized formats. For an optional phone field, the behavior is:
- `phone` absent in `ProspectCreateIn` → no normalization, no storage.
- `phone` present but empty string → treated as absent (coerced to `None`).
- `phone` present and non-empty → normalized; HTTP 400 on failure.

### 5.5 Soft-delete and re-create

After soft-deletion, `find_prospect_by_email` may return the deleted row. The
function checks `"deleted_at" in item` and returns `None` when the row is soft-
deleted, treating it as absent. A re-create for the same email writes a new row
with a new `prospect_id` without modifying or overwriting the deleted row.

### 5.6 `ByOwner` GSI FilterExpression pagination

The ByOwner GSI (`GSI1PK=OWNER#{sub}`) is shared by both Leads and Prospects.
`list_prospects` applies `FilterExpression=Attr("pk").begins_with("PROSPECT#")`.
Per the CLAUDE.md "DDB FilterExpression doesn't reduce page size" gotcha, DynamoDB
fetches up to 1MB per page *before* applying the filter. On a busy owner with many
leads, the loop must continue via `LastEvaluatedKey` until `limit` Prospect rows
are collected or all pages are exhausted.

### 5.7 Deletion of already-deleted Prospect

`delete_prospect` must be idempotent. If `deleted_at` is already set, return
silently (do not raise 404 or 409). This ensures retry-safe delete semantics.

### 5.8 `add_prospect_to_contact_list` and MKT-007 unavailability

When `app.services.marketing_lists` cannot be imported (MKT-007 not deployed),
the function silences `ImportError` and returns. It also silences any other
exception from `add_member` to prevent a marketing-list failure from surfacing
as an error to the Prospect API caller. The endpoint returns `{"ok": True}`
regardless.

### 5.9 Email length and format guard

`normalize_email` (line 60) strips and lowercases, then raises HTTP 400 if `@`
is absent or the result exceeds 254 characters. This validation applies at service
entry, before the GSI lookup, so malformed emails are rejected before any DDB read.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No dev_mode branch

LED-007 introduces zero `if S.dev_mode` branches. All DynamoDB reads and writes
use the same `T.leads` table handle regardless of environment. In dev, `T.leads`
resolves against DynamoDB Local (port 8001); in prod, it resolves against real
AWS DynamoDB. The `_safe_table` proxy in `app/core/tables.py:29-62` handles the
float-to-Decimal coercion transparently in both environments. This is identical
to every other table in the codebase (SECOPS-007 parity).

### 7.2 Audit trail

Every mutating operation (`create_prospect`, `update_prospect`, `delete_prospect`,
`add_prospect_to_contact_list`) emits an `audit_event` via
`app/services/alerts.audit_event` (line 644). In dev, this writes to
DynamoDB Local's `alerts` table. In prod, the same code path writes to the real
`alerts` table. No mock or log-only branch.

### 7.3 Idempotency

- `create_prospect`: idempotent — duplicate email returns the existing row.
  The conditional `put_item` + fallback ensures exactly-once semantics under
  concurrent create.
- `delete_prospect`: idempotent — re-deleting an already-deleted Prospect is
  a no-op.
- `update_prospect`: last-write-wins; no versioning required at this stage
  (prospects are lightweight and not contended).
- `add_prospect_to_contact_list`: delegates idempotency to MKT-007's
  `add_member`.

### 7.4 PII handling

`email`, `first_name`, `last_name`, `phone`, and `company` are PII. All endpoints
require `require_ui_session` authentication — no unauthenticated read of Prospect
data is possible. The ByEmail GSI stores the normalized email as a DynamoDB
attribute key (`GSI4PK=EMAIL#{email}`); this is acceptable because the `leads`
table is an internal CRM table, not a publicly accessible resource. Audit events
log `email` for traceability.

No Prospect data is returned to anonymous callers. The `/ui/leads/prospects/*`
path prefix requires a valid session cookie or Bearer token per the auth dependency
chain at `app/services/sessions.py:330`.

### 7.5 No money-out path

LED-007 introduces no billing, payment, refund, or ledger operations. There is
nothing to settle or reverse.

### 7.6 CSRF

CSRF enforcement is automatic: `require_ui_session` enforces `x-csrf-token`
matching `ui_csrf` cookie on all non-GET cookie-auth requests. The endpoint
table in §4.3 marks which verbs require CSRF. Bearer-auth requests (API clients)
bypass CSRF per the existing dep chain.

## 8. Backward Compatibility & Migration

### 8.1 Additive-only table change

The `leads` DynamoDB table does not yet exist in any deployed environment when
LED-001 is first applied (it is new). Adding GSI4 at LED-007 time requires either:

- **Option A (preferred)**: Apply LED-001 and LED-007 together in the same
  deployment (both add to `scripts/local-ddb-init.py`; `just restart` creates
  the table with all four GSIs at once).
- **Option B (incremental)**: If LED-001 has already been deployed without GSI4,
  an `UpdateTable` call is needed to add GSI4. Add a one-time migration script
  `scripts/migrations/add-leads-gsi4.py` that calls
  `T.leads.meta.client.update_table(...)` with the new GSI definition. GSI
  backfill is asynchronous in real DynamoDB (minutes to hours depending on table
  size); query callers must not assume GSI4 is immediately consistent after the
  migration.

In the local dev environment, `just restart` always drops and recreates the
table from `scripts/local-ddb-init.py`, so Option A is effectively the dev path.
For production, Option B documentation must accompany the LED-007 deployment.

### 8.2 No existing Prospect rows

There are no Prospect rows to backfill. LED-007 is a green-field feature.
`suppressed` defaults to `False`; there is no retroactive opt-out check needed.

### 8.3 LED-009 ByEmail GSI reuse

LED-009 (`duplicate detection and merge`) queries `ByEmail` GSI for Lead rows
in addition to Prospect rows. The GSI4 introduced here is shared — LED-009 must
be aware that `ByEmail` results can contain both `LEAD#` and `PROSPECT#` pk
prefixes and filter accordingly.

### 8.4 No model deprecations

`ProspectCreateIn` and `ProspectOut` are additive to `app/models.py`. No existing
model is modified. Adding `ProspectUpdateIn` (§4.1) is purely additive.

## 10. Open Questions / Assumptions

### 10.1 GSI4 on existing LED-001 table

**Assumption**: LED-001 and LED-007 ship together or LED-001 has not yet been
deployed to production when LED-007 is merged. If LED-001 was deployed first,
the `UpdateTable` migration path (Option B, §8.1) must be followed.

### 10.2 Opt-out re-sync

**Open question**: If a Prospect opts out of cart-reminder emails after being
created (via `PUT /ui/shoppingcart/reminders/preferences`), the `suppressed`
flag on the existing Prospect row is not automatically updated. Should
`update_prospect` re-run the opt-out check and update `suppressed`? Or should
MKT-007's `add_member` be responsible for syncing `suppressed` when it processes
the list membership?

**Current assumption**: LED-007 sets `suppressed` at create time only. MKT-007
is responsible for re-checking opt-out at campaign-send time. This is consistent
with SuiteCRM's behavior where Target records store a static suppression flag and
campaign sends do a final opt-out check at send time.

### 10.3 `ProspectUpdateIn` email immutability UX

**Assumption**: callers who need to correct an email must `DELETE` the old
Prospect and `POST` a new one. This is documented in §4.1. The UI (LED-013) should
surface this constraint clearly.

### 10.4 Prospect-to-Lead promotion

SuiteCRM supports promoting a Target to a Lead. This is out of scope for LED-007.
A future ticket (e.g., LED-007a) could add `POST /ui/leads/prospects/{id}/promote`
that calls `create_lead` with data from the Prospect and then soft-deletes the
Prospect row. No structural changes to LED-007's data model are required to support
this future path.

### 10.5 `STATUS#prospect` vs per-owner GSI2

Using `GSI2PK=STATUS#prospect` means the ByStatus GSI returns all Prospects
system-wide in that partition, not scoped to the caller's ownership. A malicious
admin-level caller who knows the GSI key could list all Prospects. This is
acceptable because (a) the ByStatus GSI is only queried by service-layer code,
not exposed directly in a public endpoint, and (b) all prospect endpoints require
authentication. If a scoped ByStatus query per owner becomes necessary, the value
could be changed to `STATUS#prospect#OWNER#{owner_sub}` — this is an open design
decision deferred to LED-013.

### 11.4 Relationship to PTY / MKT CRM family

LED-007 Prospects are the lightweight pre-CRM form of what PTY-004 will model as
a `PERSON` party with an `EMAIL` contact mechanism. When PTY is deployed, a
Prospect can be promoted to a PERSON party (LED-007a future ticket). Until PTY
ships, Prospects remain self-contained in the `leads` table and require no party
infrastructure.

MKT-001 through MKT-014 (`docs/ofbiz/specs/MKT-*.md`) deliver `ContactLists`,
`PartySegments`, and campaign-send infrastructure. LED-007's
`add_prospect_to_contact_list` is the integration point: it delegates to
MKT-007's `add_member` and is silently a no-op until MKT-007 ships. No MKT
ticket needs to be deployed before LED-007 goes live.
