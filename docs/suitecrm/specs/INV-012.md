## 1. Summary & Goal

INV-012 authors the Playwright end-to-end test file `frontend/e2e/invoices-crm.spec.ts` that exercises the full AOS invoice feature set delivered by INV-001 through INV-011. The goal is CI-verifiable coverage that each INV ticket's backend endpoints and the admin invoice UI behave correctly against the live dev stack (DynamoDB Local + moto + uvicorn). The existing `frontend/e2e/invoices.spec.ts` (sections 539–543) covers FIN-001 auto-generated invoices; this new file covers the CRM-extended surface — manual B2B invoice creation, multi-currency, per-line tax, branding, lifecycle, CRM linking, and the admin UI.

No new backend code is introduced. Every test in this file is additive and flag-gated at the `.env.local` level: the CI job that runs `invoices-crm.spec.ts` must set the seven feature flags listed in Section 6. With all flags off the platform is byte-for-byte unchanged.

## 5. Detailed Behavior & Edge Cases

### 5.1 Unique timestamps for test isolation

All created record names and identifiers include a `TS = Date.now()` suffix, identical to the pattern in `catalog-subscriptions.spec.ts:33`. Currency ISO codes are constructed as `String(TS % 100).padStart(2, "0")` prepended with `"t"` — always exactly 3 chars (e.g. `"t42"`, `"t09"`, `"t99"`). ⚠ CORRECTED: the formula `"t${TS % 1000}".padStart(3, "x")` stated in earlier drafts is wrong — `TS % 1000` can yield a 3-digit number like `123`, producing a 4-char string `"t123"` that violates INV-002's 3-char ISO code constraint. Use `TS % 100` (range 0–99) to stay within 3 chars. Tax rate names use `E2E VAT ${TS}`.

### 5.2 Section independence

Each `test.describe` block declares its own `beforeAll`/`afterAll` that creates and cleans up its records. No section reads state written by another section. The `charlie` ADMIN page is created fresh per section via `newAdminPage(browser, "charlie")`.

### 5.3 PDF content assertions

PDF bytes are fetched via `apiGet(charliePage, "/ui/invoices/{number}/pdf")` (admin reads the invoice owner's PDF — admin has cross-user read access via `admin_list_invoices`). The PDF is asserted with:
```typescript
const buf = await resp.body();
expect(buf.slice(0, 4).toString()).toBe("%PDF");
expect(buf.toString("latin1")).toContain("Test Corp INV012");
```
The PDF renderer (`invoices.py:103–143`) encodes content as UTF-8 inside a PostScript stream. [VERIFIED: `app/services/invoices.py:103`; `_render_pdf` uses `content.encode("utf-8")` at line 110, streams it into the PDF content object] String content embedded between `(...)Tj` operators is readable as ASCII/Latin-1 in the raw bytes.

### 5.4 Currency conversion math assertion

When EUR is created with `rate_to_usd=1.08` and an invoice is created for `amount_cents=10000` EUR, the expected `usd_amount_cents` is `round(10000 * 1.08) = 10800`. The test asserts `usd_amount_cents > 0` rather than the exact value to avoid floating-point rounding sensitivity across moto versions.

### 5.5 Tax arithmetic assertion

For a single line item with `amount_cents=10000` and `tax_rate_bps=2000`, `line_tax = (10000 * 2000) // 10000 = 2000`. The test asserts `inv.tax_cents === inv.line_items.reduce((s,l) => s + l.tax_cents, 0)` — verifying per-line summation rather than hardcoded expected values.

### 5.6 Discount total formula

For `amount_cents=5000`, `discount_cents=500`, `tax_cents=0` (no tax configured), `shipping_cents=0`: `total_cents = 5000 + 0 + 0 - 500 = 4500`. Test asserts exact equality.

### 5.7 Account GSI3 sparse behavior

An invoice created without `account_id` must NOT appear in `GET /ui/admin/invoices/by-account/{id}`. The test creates two invoices in the same section — one with `account_id="acct_e2e_{TS}"`, one without — and asserts only the linked one appears in the by-account query.

### 5.8 Lifecycle 403 guard

Section 708 creates a `draft` invoice under Alice, then tests that Bob (a different user) cannot void it — expect `403`. Charlie (ADMIN) CAN void it. After void, a second void attempt returns `409` (already void). These auth boundary tests validate the ownership check added in INV-009.

### 5.9 Flag-off branches are NOT tested in E2E

Per the ticket definition in the source file (line 704–706): "Feature-flag-off sections (covered by unit tests, not E2E): when `CRM_CURRENCIES_ENABLED=0`, currency endpoints return 404 — validated in hermetic unit tests (INV-002), not E2E." This spec follows that principle for all seven flags. The E2E CI job sets all flags to `1`; the unit test suite covers flag-off invariants in isolation.

### 5.10 Branding teardown

Section 707 must reset branding to empty values in `afterAll` so subsequent test runs do not have a stale company_name in PDFs. The teardown `PATCH` sends `{ company_name: "", footer_text: "" }`.

### 5.11 Admin page identity mismatch

Admin endpoints (`/ui/admin/invoices/manual`, `/ui/admin/currencies`, `/ui/admin/tax-rates`, `/ui/admin/invoices/branding`) require `role >= ADMIN`. The `charlie` identity created by `e2e_admin_session_setup.py` carries `role=admin` in the HS256 `ui_access_token` cookie. The `alice` identity (role=user) must receive `403` on these endpoints — validated in Sections 702 and 704 as negative access-control tests.

### 5.12 Route ordering for literal-segment routes

`GET /ui/admin/invoices/by-account/{account_id}` (INV-010) must be declared before `/{invoice_number}` in the router. The E2E tests do NOT test route ordering directly (that is a unit test concern per INV-010's acceptance criteria), but Section 709 provides end-to-end confirmation that the route resolves correctly.

### 5.13 UI section (Section 710) — React Query invalidation

After the Void button is clicked in `AdminInvoicesPage.tsx`, the test waits for `page.waitForResponse(r => r.url().includes("/ui/admin/invoices") && r.status() === 200)` before asserting the status badge. This avoids the `waitForLoadState("networkidle")` issue documented in CLAUDE.md (Vite HMR + presence polling keep network active).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/Prod parity

INV-012 is a test file and contains no service code. It exercises backend code from INV-001–INV-011, all of which follow SECOPS-007 (no `if S.dev_mode` branches in service code; moto intercepts boto3 at the botocore layer identically to real AWS). The test assertions are the same against dev and prod because the same code path runs in both environments.

### Test idempotency

Each section uses `TS = Date.now()` to generate unique identifiers. The `beforeAll`/`afterAll` teardown removes records created by that section. A second run of the same section after teardown produces no residual state. The `ensureInvoicesTable()` helper (carried from `invoices.spec.ts:84–103`) is not needed here because the CRM tables are created by `local-ddb-init.py` on `just restart`.

### Session idempotency

`getAdminSessions()` calls `python3 e2e_admin_session_setup.py` only once per Playwright worker process (module-level `_adminSessions` variable), matching the pattern in `invoices.spec.ts:54–63`. The admin session script is idempotent — it uses `put_item` unconditionally, so multiple runs produce the same session state.

### CSRF

All non-GET requests to `/ui/admin/*` and `/ui/invoices/*` include the `x-csrf-token` header from the session's `csrf_token` field, following the documented pattern in CLAUDE.md "CSRF validation" section.

### No secrets in test output

Payment method injection (for Section 708 lifecycle) uses the inline `execSync` Python snippet pattern from `invoices.spec.ts:105–113`. The PM ID is a fixed test string `pm_inv_crm_test_4242` — not a real Stripe key.

## 8. Backward Compatibility & Migration

### No new tables

INV-012 does not add DDB tables. The tables it exercises (`invoices` with GSI3, `crm_currencies`, `crm_tax_rates`) are added by INV-001–INV-010. After merging those tickets, run `just restart` to recreate DDB tables with the updated schema. Existing `invoices` rows that predate INV-001 have no `billing_address` / `discount_cents` / `account_id` attributes; `InvoiceOut` defaults all new fields to `""` / `0` / `None` so serialization is backward-compatible.

### Existing `invoices.spec.ts` is untouched

Sections 539–543 test FIN-001 auto-generated invoices only. INV-012's `invoices-crm.spec.ts` adds new section numbers (701–710) and uses a separate file. The two files can run in parallel (`npx playwright test invoices`) because they use isolated browser contexts and do not share DDB state (except the `COUNTER/SEQ` row, which is append-only and commutative).

### Frontend `Invoice` type extension

`frontend/src/api/types.ts:8784` `Invoice` gains the INV-001/INV-003/INV-009/INV-010 fields as optional additions. Existing usages (`InvoicesPage.tsx`, `InvoiceRow.tsx`) access only FIN-001 fields, so they continue to compile and render correctly when new fields are absent.

## 10. Open Questions / Assumptions

1. **QUO-005 hard dependency for Section 708**: The lifecycle endpoints (`POST .../send`, `POST .../void`, overdue checker) are delivered by QUO-005. Section 708 is conditionally skipped (`test.skip`) if QUO-005 is not yet merged. The skip condition is detected by attempting `POST /ui/admin/invoices/manual` and checking if the response carries a `status` field; if `status` is not in the response the section exits early with a warning.

2. **INV-011 hard dependency for Section 710**: `AdminInvoicesPage.tsx`, `ManualInvoiceForm.tsx`, and the `/admin/invoices` route must exist for Section 710 to run. If INV-011 is not merged, Section 710 will fail at `page.goto("/admin/invoices")`. Like Section 708, Section 710 should be conditionally skipped if the route returns a 404 or redirect-to-login.

3. **`VALID_TYPES` for manual invoices**: The existing `VALID_TYPES = {"tip", "unlock", "subscription", "shop", "deposit"}` at `invoices.py:33` does not include a `"manual"` type. QUO-005 either adds `"manual"` to `VALID_TYPES` or the manual invoice endpoint bypasses the guard. The test uses `invoice_type: "shop"` as a safe fallback that is guaranteed to be in `VALID_TYPES` if QUO-005 is not yet merged.

4. **3-char ISO code uniqueness**: The generated ISO code `t${TS % 1000}` is padded to 3 chars. In a rapid-succession CI run the `TS % 1000` values could collide across parallel workers. The spec uses Playwright's single-worker mode (`workers: 1` in `playwright.config.ts`) so this is not a concern in practice. In multi-worker mode a UUID-based 3-char hex suffix would be needed.

5. **Branding persistence across test runs**: Section 707's `afterAll` resets branding to empty strings. If the test is interrupted (Ctrl-C) the teardown does not run, leaving a stale `company_name` in DDB that would appear in Section 539–543 PDFs. A `beforeAll` in Section 707 also resets branding before the test runs to guard against this.
