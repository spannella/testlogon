# CCT-004 — Duplicate contact detection

**Type:** Feature | **Priority:** P1 | **Estimate:** 3d  
**Source:** `docs/suitecrm/CRM_CONTACTS_EXTRA_TICKETS.md` — CCT-004 section  
**Flag:** `PARTY_CRM_ENABLED` (existing, from PTY-001) — default OFF  
**New sub-flag:** `PARTY_DEDUP_ENABLED` (default OFF, sub-gated)

---

## 1. Summary & Goal

SuiteCRM's Contacts module includes automatic duplicate detection: when a new contact is created, or when a user runs an explicit deduplication sweep, the system compares parties against each other using email/phone exact match and name fuzzy match, then surfaces high-scoring candidate pairs for human review or automated merge. The testlogon platform's existing social-graph contacts surface (`app/routers/contacts.py`) has no duplicate detection whatsoever.

CCT-004 introduces a new `app/services/party_dedup.py` module that:

1. Scores any party against its potential duplicates using two complementary signals — exact contact-mechanism (email/phone) match and fuzzy normalized-name comparison — reusing existing primitives with zero code forking.
2. Exposes a per-party duplicate query for authenticated users and a system-wide paginated admin sweep.
3. Emits an audit event on every admin sweep call.
4. Is fully additive and gated default-off; with all flags off the platform is byte-for-byte unchanged.

CCT-004 is the natural prerequisite for CCT-005 (contact merge), which resolves the duplicate pairs that this ticket surfaces.

## 3. Data Model

### 3.1 No new DynamoDB table required

CCT-004 is entirely read-side: it queries the existing `party` table via `GSI2` (contact-mech reverse lookup) and `GSI_CREATED` (sequential scan for name matching), and reads META rows. No new rows are written by the deduplication service itself. Duplicate candidates are returned as transient in-memory objects — they are not persisted to DynamoDB.

This is correct because duplicate candidates can go stale (parties get merged, contact mechs added/removed), making a cached result set more misleading than helpful. Stale persistence would also require a TTL cleanup strategy; avoiding it keeps the service stateless and simple.

### 3.2 Existing `party` table — access patterns used by CCT-004

| Access pattern | GSI / key | Used by |
|---|---|---|
| Exact EMAIL match for party X's email | `GSI2` — `GSI2PK = "EMAIL#{norm}"` | `find_duplicates_for_party` |
| Exact PHONE match for party X's phone | `GSI2` — `GSI2PK = "PHONE#{e164}"` | `find_duplicates_for_party` |
| Scan all PERSON parties (name match candidates) | `GSI_CREATED` — `type = "TYPE#PERSON"` | `find_duplicates_for_party`, `list_all_duplicate_candidates` |
| Scan all PARTY_GROUP parties | `GSI_CREATED` — `type = "TYPE#PARTY_GROUP"` | `list_all_duplicate_candidates` |
| Fetch party META row | Primary `PK = "PARTY#{id}" / SK = "META"` | score computation; `get_party()` reuse |
| List contact mechs for a party | `PK = "PARTY#{id}" / SK begins_with "MECH#"` | gather EMAIL/PHONE for comparison |

All of these access patterns are already supported by the PTY-002 table definition (`docs/ofbiz/specs/PTY-002.md:§3.1`). No new GSIs or attribute changes are required.

### 3.3 Pydantic models — additions to `app/models.py`

```python
class DuplicateCandidateOut(BaseModel):
    party_a_id:    str
    party_b_id:    str
    score:         float          # 0.0–1.0; capped at 1.0
    match_signals: List[str]      # e.g. ["email_exact", "name_fuzzy:0.91"]

class DuplicateCandidateListOut(BaseModel):
    candidates: List[DuplicateCandidateOut]
    count:      int
    cursor:     Optional[str] = None
```

`DuplicateCandidateOut` is the sole new model. `match_signals` is a human-readable list of the signals that contributed to the score — useful for the UI and for operators reviewing candidates before merging.

## 4. API / Service Design

### 4.1 New service module — `app/services/party_dedup.py`

All deduplication logic lives in a single new file. It imports only stdlib, existing platform primitives, and `T.party`.

#### Module-level constants

```python
# Scoring weights
_EMAIL_EXACT_SCORE  = 0.90
_PHONE_EXACT_SCORE  = 0.80
_NAME_FUZZY_WEIGHT  = 0.70   # name_ratio × 0.70
_NAME_RATIO_FLOOR   = 0.85   # minimum SequenceMatcher ratio to contribute

# Candidate scan cap for name-based matching
_NAME_SCAN_LIMIT    = 200    # max parties read from GSI_CREATED per call
```

#### `_normalize_name(value: str | None) -> str`

Local copy of the normalization pattern from `app/services/kyc_sanctions_screening.py:205-211`. Lowercase, strip diacritics via `unicodedata.normalize("NFKD")` + `unicodedata.combining` filter, collapse non-alphanumeric to single spaces.

#### `_score_pair(party_a: dict, party_b: dict, mechs_a: list[dict], mechs_b: dict) -> tuple[float, list[str]]`

Internal scoring function. Returns `(score, signals)`.

Algorithm:
1. **Email exact match**: for each EMAIL mech in `mechs_a`, call `find_party_by_contact("EMAIL", value)` (PTY-007) which queries `GSI2`. If party_b's `party_id` appears in results, add `_EMAIL_EXACT_SCORE` to candidates and append `"email_exact"` to signals.
2. **Phone exact match**: same pattern with PHONE mechs; score `_PHONE_EXACT_SCORE`, signal `"phone_exact"`.
3. **Name fuzzy match**: compute `ratio = difflib.SequenceMatcher(None, _normalize_name(a_name), _normalize_name(b_name)).ratio()`. If `ratio >= _NAME_RATIO_FLOOR`, add `ratio * _NAME_FUZZY_WEIGHT` to candidates and append `f"name_fuzzy:{ratio:.2f}"` to signals.
4. **Final score**: `min(1.0, max(candidates))` — the maximum single-signal score, capped at 1.0. Signals from all contributing channels are included (not just the max-scoring one) to give reviewers full context.

The function avoids calling `find_party_by_contact` inside the inner loop of bulk operations; instead the caller pre-fetches mechs for party_a and passes them in, so the GSI2 queries are batched at the outer level.

#### `find_duplicates_for_party(party_id: str, *, actor_sub: str) -> List[DuplicateCandidateOut]`

Signature:
```python
def find_duplicates_for_party(
    party_id: str,
    *,
    actor_sub: str,
) -> List[DuplicateCandidateOut]:
```

Steps:
1. `party_a = get_party(party_id)` (PTY-004). Raise `HTTPException(404, "party not found")` if None.
2. `mechs_a = list_contact_mechs(party_id)` (PTY-007). Returns all `MECH#*` rows.
3. Collect candidate party_ids via **two sources**:
   - **Contact-mech source**: for each EMAIL and PHONE mech in `mechs_a`, query `GSI2` directly (`T.party.query(IndexName="GSI2", KeyConditionExpression=Key("GSI2PK").eq(gsi2_pk))`) to get all parties sharing that contact value. Collect the `party_id` from each `GSI2SK = "PARTY#{party_id}"` item.
   - **Name source**: query `GSI_CREATED` with `PK = "TYPE#{party_a['party_type']}"`, `ScanIndexForward=False`, `Limit=_NAME_SCAN_LIMIT`. Collect `party_id` from each META row.
4. Deduplicate the candidate set; exclude `party_id` itself; exclude parties with `status == "MERGED"`.
5. For each candidate, call `_score_pair`. Collect pairs where `score >= S.party_dedup_match_threshold`.
6. Return sorted by score descending.

No audit event is emitted by `find_duplicates_for_party` (it is a user-facing read that may be called frequently; admin sweeps are audited separately).

#### `list_all_duplicate_candidates(actor_sub: str, cursor: Optional[str] = None, limit: int = 50) -> tuple[List[DuplicateCandidateOut], Optional[str]]`

Signature:
```python
def list_all_duplicate_candidates(
    actor_sub: str,
    cursor: Optional[str] = None,
    limit: int = 50,
) -> tuple[List[DuplicateCandidateOut], Optional[str]]:
```

Steps:
1. Emit `audit_event("party.duplicate_scan", actor_sub, cursor=cursor, limit=limit)` via `app.services.alerts.audit_event` (`alerts.py:644`). Fire-and-forget (no `await`; synchronous).
2. Decode cursor via `decode_cursor(cursor)` (`app/core/cursor.py:103`). If invalid, treat as `None` (start from beginning).
3. Query `GSI_CREATED` with `type = "TYPE#PERSON"` for up to `limit * 3` items (over-fetch to account for pairs that score below threshold), starting from `ExclusiveStartKey` if cursor is set.
4. For each fetched PERSON party, call `find_duplicates_for_party(party_id, actor_sub=actor_sub)` and collect results.
5. Deduplicate across calls (a pair A/B should appear once, not once from A's perspective and once from B's). Canonical form: `(min(party_a_id, party_b_id), max(party_a_id, party_b_id))` as the dedup key.
6. If `GSI_CREATED` query returns a `LastEvaluatedKey`, encode it with `encode_cursor` (`cursor.py:94`) and return it as the next cursor. Otherwise return `None`.
7. Return `(candidates[:limit], next_cursor)`.

The sweep covers PERSON parties in this pass. PARTY_GROUP deduplication follows the identical pattern using `type = "TYPE#PARTY_GROUP"` — the same function handles both types because the scoring algorithm is type-agnostic.

#### `GET /ui/party/parties/{party_id}/duplicates`

```python
@router.get(

    response_model=DuplicateCandidateListOut,

The `/duplicates` suffix is a static literal after the path parameter, so no declaration-order concern arises here (FastAPI only needs the static-before-dynamic rule at the same depth level).

```python

## 5. Detailed Behavior & Edge Cases

### 5.1 Self-exclusion

`find_duplicates_for_party` excludes the input `party_id` from the candidate set before scoring (step 4 above). This prevents a party from appearing as its own duplicate when a contact-mech query returns the same party.

### 5.2 MERGED party exclusion

Parties with `status == "MERGED"` (the terminal state defined in PTY-003 `docs/ofbiz/specs/PTY-003.md:189-196`) are excluded from both the candidate set and from the subject party check. If `get_party(party_id)` returns a MERGED party, `find_duplicates_for_party` raises `HTTPException(409, "party_already_merged")` rather than silently returning zero results — this informs callers that they are querying a tombstone.

### 5.3 Scoring is the maximum single-signal score, not a sum

A party pair can score on multiple signals (e.g., both email exact and name fuzzy). The final score is `max(all_signal_scores)`, not the sum. This prevents inflation — a pair with identical email already scores 0.90; adding a fuzzy name match that would score 0.78 does not push the total above 0.90. The `match_signals` list retains all contributing signals for transparency.

### 5.4 Threshold configuration

`S.party_dedup_match_threshold` (float, default `0.70`, env `PARTY_DEDUP_MATCH_THRESHOLD`) is read from `app/core/settings.py` and applied in both `find_duplicates_for_party` and `list_all_duplicate_candidates`. Setting the threshold to `1.0` effectively disables results (only perfect email/phone matches survive). Setting it below `0.70` may produce excessive noise.

### 5.5 Empty contact mechs

If `mechs_a` is empty (party has no EMAIL or PHONE mechs), the contact-mech signal produces zero candidates. Name-source candidates are still generated and scored. A party with no mechs and a unique name returns an empty candidate list — this is correct behavior, not a bug.

### 5.6 Name-source scan limit

The `_NAME_SCAN_LIMIT = 200` cap on `GSI_CREATED` reads is a performance guard for `find_duplicates_for_party`. For large datasets, not all parties are compared by name — only the 200 most recently created parties of the same type. This is documented in the `DuplicateCandidateListOut` response; the admin sweep operates in pages precisely to handle scale.

### 5.7 GSI2 returns multiple parties for the same mech value

When two parties legitimately share an email (e.g., a family sharing a single address), both are returned by `find_party_by_contact`. The scoring correctly marks them as high-confidence duplicates (0.90). It is then the human reviewer's or admin's responsibility to decide whether to merge. The dedup service surfaces candidates; it never merges automatically.

### 5.8 DynamoDB `FilterExpression` does not reduce page size

As noted in CLAUDE.md, DynamoDB fetches up to 1 MB _before_ applying `FilterExpression`. The name-source scan of `GSI_CREATED` excludes MERGED parties via post-processing in Python (not a DDB filter) to avoid silent missing results across page boundaries. The `Limit=_NAME_SCAN_LIMIT` applies to the DDB read; the Python-level merged-party filter is applied afterward.

### 5.9 Pair dedup in `list_all_duplicate_candidates`

Because the sweep calls `find_duplicates_for_party` for each party, pairs are encountered twice (once from each side). A `seen_pairs: set[frozenset]` accumulator ensures each canonical `{party_a_id, party_b_id}` pair appears in the output exactly once. The `party_a_id` / `party_b_id` assignment in the output canonically places the lexicographically smaller ID in `party_a_id`.

### 5.10 `normalize_phone` raises `HTTPException` inside service layer

`normalize_phone` at `app/core/normalize.py:66` raises `HTTPException(400, ...)`. When called from a service function (not from a Pydantic validator), this propagates cleanly to the router as a 400 response — this is the expected behavior for invalid phone numbers encountered during mech scoring. The service wraps the call in a `try/except HTTPException` and skips that mech rather than aborting the entire dedup scan.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No dev_mode branches

`app/services/party_dedup.py` contains no `if S.dev_mode` or `_mock_enabled()` branches. All code paths run identically in dev (DynamoDB Local) and prod (real DynamoDB). This satisfies SECOPS-007 as enforced by the file-header constraint in `docs/suitecrm/CRM_CONTACTS_EXTRA_TICKETS.md`.

### 7.2 Idempotency

`find_duplicates_for_party` and `list_all_duplicate_candidates` are pure read operations. They can be called any number of times with the same arguments and produce the same result (modulo data changes in DynamoDB). No writes occur in the dedup service; there is nothing to make idempotent on the write path.

### 7.3 Audit trail

Every call to `list_all_duplicate_candidates` (admin sweep) emits `audit_event("party.duplicate_scan", actor_sub, ...)` to `T.alerts` via `app.services.alerts.audit_event` (`alerts.py:644`). This creates a searchable trail of who ran bulk duplicate scans and when, consistent with how other admin data-access operations are audited in this codebase (e.g., `"party.merged"` in CCT-005, `"party.contact_mech.add"` in PTY-007).

### 7.4 Authorization

- **Per-party endpoint** (`GET /ui/party/parties/{party_id}/duplicates`): gated by `require_ui_session`. Any authenticated user can scan for duplicates of any party. This is intentionally permissive at the query layer — the party details returned are already visible to any authenticated user via `GET /ui/party/parties/{party_id}` (PTY-011). Restricting dedup reads to party owners would add complexity without meaningful security benefit.
- **Admin sweep** (`GET /ui/admin/party/duplicate-candidates`): gated by `require_admin_or_root` (`app/auth/policy.py:67`). Only ADMIN or ROOT roles can trigger a system-wide scan. This is a data-access operation (reads all party names and contact mechs in aggregate), so it requires elevated privilege.

### 7.5 No PII in audit payload

`audit_event` kwargs must not include normalized email addresses or phone numbers — those are PII. The audit event records only `actor_sub`, `cursor`, and `limit` for the sweep, and `party_id` for the per-party scan.

### 7.6 Normalized contact values in GSI2

Email addresses and phone numbers stored in `GSI2PK` are already normalized (lowercased email, E.164 phone). The dedup service re-normalizes on each comparison, so a stale pre-normalization value in an old row cannot cause a false negative. `normalize_email` and `normalize_phone` are called on every mech value before querying `GSI2` (`app/core/normalize.py:60-81`).

## 8. Backward Compatibility & Migration

### 8.1 No schema changes

CCT-004 adds no new DynamoDB tables, no new GSIs, and no new attributes on existing rows. It reads from the `party` table using access patterns already defined by PTY-002 and PTY-007. There is nothing to migrate.

### 8.2 Flag off = zero change

With `PARTY_CRM_ENABLED=0` or `PARTY_DEDUP_ENABLED=0`, both router endpoints return HTTP 503 immediately. No DynamoDB reads occur, no settings values are read beyond the flag check, and all other subsystems are entirely unaffected.

### 8.3 Additive Pydantic models

`DuplicateCandidateOut` and `DuplicateCandidateListOut` are new models with no overlap with any existing model in `app/models.py`. The `Crm`-prefix naming convention for CRM models (established in PTY-003 at `docs/ofbiz/specs/PTY-003.md:64-76` — the "Name collision" section §2.2) does not apply here because these models are output-only and not part of the core party graph — they represent a computed view, not a persisted entity. The `DuplicateCandidate` prefix is unambiguous.

### 8.4 Router registration order

`admin_party_router` is registered in `app/main.py` after `party_router` (which is itself registered after `contacts_router`). The admin router carries a distinct prefix (`/ui/admin/party`) so there is no URL collision with the existing party router (`/ui/party`).

## 10. Open Questions / Assumptions

1. **Name-source scan limit for large data sets**: `_NAME_SCAN_LIMIT = 200` was chosen to keep per-request latency bounded. For deployments with tens of thousands of parties, the admin sweep is the correct tool (it pages through all parties). If the per-party endpoint must also reach all parties, `_NAME_SCAN_LIMIT` should be raised or a separate background scoring pass should be introduced. **Assumption**: 200 candidates per call is sufficient for Phase 1 scale.

2. **POSTAL mech deduplication**: The ticket description does not call for POSTAL-address scoring. POSTAL hashing via `GSI2` (PTY-007) is complex (hash-of-canonical-JSON) and postal addresses change frequently. **Assumption**: POSTAL signal is excluded from Phase 1 scoring; email and phone exact match plus name fuzzy match are sufficient for the CCT-005 merge workflow.

3. **Async vs sync service functions**: All party service functions in PTY-004..PTY-007 are synchronous (no `async`). `find_duplicates_for_party` and `list_all_duplicate_candidates` are also synchronous and run in the FastAPI thread pool (no `await`). If DynamoDB calls in PTY service functions are ever converted to async, the dedup service will need to match. **Assumption**: sync for Phase 1.

4. **Cross-type deduplication**: A PERSON party and a PARTY_GROUP party with the same email are never considered duplicates because CCT-005 (merge) requires both parties to share `party_type`. The name-source scan is already gated on `type` from `GSI_CREATED`. **Assumption**: cross-type dedup is out of scope.

5. **Real-time vs batch**: `find_duplicates_for_party` is designed to be called on demand (e.g., "check for duplicates before saving a new contact"). It is not a background batch job. A background dedup job (e.g., cron that runs `list_all_duplicate_candidates` and stores results) is a natural follow-up but is not in scope for CCT-004.
