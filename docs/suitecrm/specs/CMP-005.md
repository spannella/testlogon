# CMP-005 — Survey / questionnaire linked to campaign

**Type:** Feature  **Priority:** P2  **Estimate:** 1d  
**Source:** `docs/suitecrm/CRM_CAMPAIGNS_EXTRA_TICKETS.md` (CMP-005 section)

---

## 1. Summary & Goal

CMP-005 allows a marketing campaign owner to attach a published questionnaire to a campaign so that every send email includes a survey URL for the recipient. This mirrors the SuiteCRM Campaigns module's "Survey" link field, which associates a survey with a campaign and embeds the survey link in outgoing emails.

The scope is intentionally narrow: no new DynamoDB table, no new service module, and no new questionnaire behavior. The entire change is additive fields on the campaign model (`questionnaire_id`, `questionnaire_url`) plus three small service-layer additions wired into existing functions that are already defined by MKT-004 (`create_campaign`, `update_campaign`, `get_campaign`) and MKT-009 (`_build_message_body`). The feature is entirely invisible with the flag off and does not affect any questionnaire, email, or billing behavior.

Goals:
1. Let a campaign reference a questionnaire at create/update time, with server-side validation that the referenced questionnaire is published.
2. Surface the resolved `questionnaire_url` on `GET /ui/marketing/campaigns/{id}`.
3. Inject the survey URL into both plain-text and HTML campaign email bodies at send time, as an additional merge-field `{{survey_url}}` consumed by the CMP-002 template engine.
4. Emit an audit event when a campaign is linked to or de-linked from a questionnaire.

## 3. Data Model

CMP-005 introduces **no new DynamoDB table**. All state is stored as new attributes on the existing `MarketingCampaigns` campaign META item. No GSI changes are required.

### Attribute additions to the MarketingCampaigns META row

| Attribute | Type | Description |
|---|---|---|
| `questionnaire_id` | `S` (optional, absent if not linked) | The `questionnaire_id` of the linked questionnaire. |
| `questionnaire_slug` | `S` (optional, absent if not linked) | The `published_slug` of the questionnaire at link time, cached so `get_campaign` can build the URL without a second DDB call. |

Both attributes are written by `create_campaign` and `update_campaign` when `questionnaire_id` is present in the input. They are omitted entirely (not stored as `null`) when no questionnaire is linked, following the standard DynamoDB sparse attribute pattern used throughout the codebase (for example, `assigned_admin_sub` on KYC case items at `scripts/local-ddb-init.py:156`).

**No `scripts/local-ddb-init.py` change is required.** The `MarketingCampaigns` table already exists (MKT-002). Sparse string attributes require no GSI declaration. Numeric GSI sort keys are the only attributes requiring `attr_types` declarations per the CLAUDE.md gotcha; `questionnaire_id` and `questionnaire_slug` are plain non-indexed strings.

### 4.1 Pydantic model changes (`app/models.py`)

All additions are in the MKT-003 block (after the existing `CampaignReviewIn` at line 4924, before line 4929). They are additive fields with `Optional[str] = None` defaults so existing serialized campaign items remain round-trippable without migration.

```python

# Additive fields on MarketingCampaignUpdateIn (MKT-003 block):
```

### 4.2 Service changes (`app/services/marketing_campaigns.py`)

#### `_validate_questionnaire_link(questionnaire_id: str) -> dict`

A new private helper, defined once, called from both `create_campaign` and `update_campaign`.

```python
def _validate_questionnaire_link(questionnaire_id: str) -> dict:
    """Verify questionnaire_id refers to a published questionnaire.

    Returns the questionnaire item dict on success.
    Raises HTTPException(422, "questionnaire_not_found_or_not_published")
    if the id does not resolve or the questionnaire status != "published".

    Reads T.questionnaires via DynamoQuestionnaireRepository (same table handle
    already used by app/routers/questionnaires.py).
    Uses get_questionnaire(questionnaire_id) for an O(1) point lookup.
    Never calls get_published_by_slug — the id is already known.
    """
    from app.services.questionnaires_repository import DynamoQuestionnaireRepository
    repo = DynamoQuestionnaireRepository()
    item = repo.get_questionnaire(questionnaire_id)
    if not item or item.get("status") != "published":
        raise HTTPException(
            status_code=422,
            detail="questionnaire_not_found_or_not_published",
        )
    return item
```

The local import inside the helper avoids circular-import risk (same pattern as `_record_timeline` in `app/services/ec2_launcher.py:24` per CLAUDE.md — note: `_record_timeline` lives in `ec2_launcher.py`, not `instance_monitoring.py`; the CLAUDE.md note describes it as a helper in `ec2_launcher.py` that lazy-imports from `instance_monitoring.py` to avoid a circular import) since `marketing_campaigns.py` and `questionnaires_repository.py` are peer modules.

The META item carries `published_version_id` (a version-id string like `"ver_abc123"`, NOT the slug) but does not carry `published_slug` directly (`questionnaires_repository.py:116` — only `published_version_id: None` is initialised on META; `published_slug` is written only to the VERSION row at line 397). A second lookup is needed to resolve the slug.

> **CORRECTION (first code block below was wrong)**: The initial draft called `repo.get_published_by_slug(item.get("published_version_id") ...)` but `get_published_by_slug` accepts a *slug* string, not a version_id. Passing `published_version_id` (e.g. `"ver_abc123"`) would construct `gsi_published_pk = PUBLISHED#ver_abc123` which would never match. The corrected approach below uses `questionnaire_id` as the slug candidate, leveraging the `publish_draft:367` default (`slug = (published_slug or draft.get("questionnaire_id") or questionnaire_id).strip()`).

```python
# Corrected slug resolution:
# published_version_id is NOT a slug — it is a "ver_<hex>" string.
# The default slug set by publish_draft (questionnaires_repository.py:367) is:
#   slug = (published_slug or draft.get("questionnaire_id") or questionnaire_id).strip()
# so for questionnaires without a custom slug, the slug == questionnaire_id.
slug_candidate = item.get("questionnaire_id", questionnaire_id)
slug_row = repo.get_published_by_slug(slug_candidate)
if slug_row:
    slug = slug_row.get("published_slug", slug_candidate)
else:
    slug = slug_candidate  # best-effort fallback (custom-slug case — see OQ-1)
return item, slug
```

`_validate_questionnaire_link` returns `(questionnaire_item, resolved_slug)`.

#### `create_campaign` (MKT-004 extension)

When `data.questionnaire_id` is non-None and non-empty, call `_validate_questionnaire_link(data.questionnaire_id)` before the DDB put. On success, persist `questionnaire_id` and `questionnaire_slug` on the item dict. Emit audit event `"marketing.campaign.questionnaire_linked"` with `campaign_id` and `questionnaire_id` (best-effort). When `data.questionnaire_id` is `None` the create proceeds unchanged.

#### `update_campaign` (MKT-004 extension)

The update path handles three cases for the `questionnaire_id` field in `data`:
- `None` (absent/not provided): no change to existing link.
- `""` (empty string): remove the link — delete `questionnaire_id` and `questionnaire_slug` attributes from the DDB item using `REMOVE questionnaire_id, questionnaire_slug` in the UpdateExpression. Emit audit event `"marketing.campaign.questionnaire_unlinked"`.
- Non-empty string: validate via `_validate_questionnaire_link`, then upsert the two attributes. Emit audit event `"marketing.campaign.questionnaire_linked"`.

#### `get_campaign` (MKT-004 extension)

After fetching the item, if `item.get("questionnaire_slug")` is non-empty, populate:

This is set on the `MarketingCampaignOut` response only, never stored in DDB. When `questionnaire_slug` is absent, `questionnaire_url` remains `None`.

## 5. Detailed Behavior & Edge Cases

### Validation sequence in `create_campaign`

1. Pydantic model validation (field types, lengths). `questionnaire_id` is `Optional[str]`, no format constraint.
2. If `questionnaire_id` is non-empty: call `_validate_questionnaire_link`. This makes **two DDB reads** (META point lookup + GSI slug lookup). Both are reads on `T.questionnaires`, which is a separate table from `T.marketing_campaigns` — no conflict.
3. If the questionnaire is not found or not `status="published"`: raise `HTTPException(422, "questionnaire_not_found_or_not_published")`. The campaign is NOT created.
4. If validation passes: proceed with the existing deterministic-id `put_item` (conditional put, MKT-004 pattern).
5. Best-effort audit event.

### Questionnaire unpublished after campaign creation

Once a campaign references a questionnaire by `questionnaire_id`, the campaign item stores the `questionnaire_slug` at create/update time. If the questionnaire is subsequently archived, the stored slug is stale but the campaign item is unchanged — CMP-005 does not add a poll or live-check on questionnaire status at send time. This is intentional and consistent with the SuiteCRM model: the campaign owns the survey URL string, not a live reference. The recipient will reach a "survey not found" page if the questionnaire owner archives the published questionnaire after the campaign was sent. Operators should be warned of this via UI copy (MKT-013 frontend — outside this ticket's scope). The `get_campaign` read path does NOT re-validate the slug is still active; it returns the cached slug unconditionally.

### `questionnaire_id` is a plain opaque string

No format enforcement (e.g. UUID) is applied at the model level. The validation is entirely by existence in `T.questionnaires`. Supplying a valid questionnaire_id belonging to a different owner is accepted — questionnaires may be intentionally shared (visibility="public"). The only invariant is `status="published"`.

### Re-linking to a different questionnaire

`update_campaign` with a new non-empty `questionnaire_id` replaces both stored attributes. The old link is silently overwritten. The audit event records both old and new ids: `"marketing.campaign.questionnaire_linked"` with `{"old_questionnaire_id": ..., "new_questionnaire_id": ...}` (read the existing item first to populate `old_questionnaire_id` if any; default `None`).

### Campaign in `active` or `completed` status

`update_campaign` applies the questionnaire link regardless of campaign status. The MKT-006 state machine governs status transitions; CMP-005 does not impose additional restrictions on when a link can be changed. In practice, updating a completed campaign's survey link does not re-send emails; the link change only affects future sends.

### Idempotent create

The MKT-004 deterministic-id scheme means that a retried `create_campaign` with the same `(owner_id, name, created_bucket)` returns the existing item. If the first call included a `questionnaire_id` and the retry does not, the retry returns the existing item unchanged (conditional put short-circuits on existing pk). Callers should not rely on the retry path to de-link a questionnaire.

### Plain-text body URL injection

The survey URL line is appended after the unsubscribe URL line added by CMP-004:
```
...
To unsubscribe: <unsubscribe_url>
Please complete our survey: <survey_url>
```
The ordering is: main body → promo code → tracking URL → unsubscribe link → survey link.

### HTML template with no `{{survey_url}}`

If an HTML template does not contain `{{survey_url}}` but the campaign has a linked questionnaire, the survey URL is included in plain-text bodies but NOT automatically appended to the HTML body (unlike CMP-004's unsubscribe footer, which CMP-004 explicitly appends as a fallback footer). Campaign owners who use HTML templates are expected to include `{{survey_url}}` in their template if they want it in the HTML body. This keeps the HTML template system composable and predictable.

### `_try_send_one` opt-out guard

The existing MKT-009 opt-out guard (`is_user_opted_out` from `app/services/cart_reminders.py:95`) runs before `_build_message_body` is called. Opted-out recipients never receive the survey URL; no special handling needed.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 — no `if S.dev_mode` branch

`_validate_questionnaire_link` calls `T.questionnaires` through `DynamoQuestionnaireRepository`, which in dev reads from DynamoDB Local (port 8001) and in prod reads from real DynamoDB. The endpoint path and table schema are identical in both environments. No mock or stub branch exists.

`get_campaign` computes `questionnaire_url` using `S.public_base_url`, which resolves to `http://localhost:8000` in dev and the production HTTPS domain in prod — the same code path both ways, as confirmed by `app/core/settings.py:349`.

### Idempotency

`create_campaign` is idempotent via MKT-004's conditional put. CMP-005 does not break this: the validation call to `_validate_questionnaire_link` is read-only. If the conditional put fails (campaign already exists), no audit event is emitted and no DDB write is attempted. `update_campaign` uses a `UpdateExpression` SET/REMOVE, which is inherently idempotent for the same input.

### Security

- **Ownership**: a campaign owner can only link questionnaires that are published. No ownership check is enforced on the questionnaire — published questionnaires are accessible by definition. If a questionnaire owner restricts visibility to `"private"` before publishing, the `publish_draft` flow itself would determine reachability; CMP-005 does not modify access control on questionnaires.
- **CSRF**: the create/update endpoints use `require_ui_session`, which enforces CSRF for all non-GET cookie-auth requests per `app/auth/deps.py` (CLAUDE.md auth section). No bypass is introduced.
- **No PII in audit**: `audit_event("marketing.campaign.questionnaire_linked", owner_sub, campaign_id=..., questionnaire_id=...)` writes only IDs, not questionnaire content or recipient data.
- **Slug stability**: the `questionnaire_slug` cached on the campaign item is the slug at link time. If the questionnaire owner later re-publishes with a different slug, the campaign retains the old slug (which will resolve to 404 at the public URL). This is a known trade-off; no automatic re-sync is performed. Operators should treat the link as a snapshot reference.

## 8. Backward Compatibility & Migration

### No data migration

Existing campaign items in `T.marketing_campaigns` have no `questionnaire_id` or `questionnaire_slug` attributes. `MarketingCampaignOut` defaults both to `None` via Pydantic field defaults. `get_campaign` reads `item.get("questionnaire_slug")` which returns `None` for pre-existing items — `questionnaire_url` will be `None` on existing campaigns. No backfill or schema change is required.

### Model backward compatibility

`MarketingCampaignCreateIn` and `MarketingCampaignUpdateIn` gain `Optional[str] = None` fields. Existing callers that do not send `questionnaire_id` in the request body receive `None` by default — behavior is unchanged. This is purely additive.

### MKT-009 `_build_message_body` extension

The `merge_vars` dict gains a conditional `survey_url` key. The `_render` function at `app/services/notification_templates.py:245–259` already handles unknown keys silently and unknown `{{var}}` placeholders in templates by leaving them intact. Pre-existing templates without `{{survey_url}}` are unaffected.

### CMP-002 dependency

CMP-005 depends on CMP-002 for HTML template merge-var injection (`survey_url` in `merge_vars`). If CMP-002 is not yet deployed, the `merge_vars` dict key is still populated by `_build_message_body`, but it is simply unused in plain-text bodies. There is no crash — the CMP-002 `render_template` function will substitute `{{survey_url}}` if present in the template; with CMP-002 absent, the plain-text path works standalone.

## 10. Open Questions & Assumptions

**OQ-1: Questionnaire slug resolution from the META item.**
The META item (`questionnaires_repository.py:103–127`) stores `pk`, `sk`, `questionnaire_id`, `status`, `published_version_id`, etc., but NOT `published_slug` directly. The `published_slug` lives on the VERSION row. This spec proposes calling `get_published_by_slug(questionnaire_id)` as a second read using the default-slug assumption (`publish_draft:367` shows the slug defaults to `questionnaire_id`). If a questionnaire owner provided a custom slug at publish time, this second lookup may miss. A safer approach would be for `_validate_questionnaire_link` to query `list_versions(questionnaire_id)` and extract `published_slug` from the most recent version row. The implementation team should confirm which path is more reliable given the data model.

**Assumption A-1:** Custom publish slugs are rare; defaulting to `questionnaire_id` as the slug covers the vast majority of cases, and the `get_published_by_slug` fallback provides correctness for the default case.

**OQ-2: Questionnaire visibility check.**
A questionnaire with `visibility="private"` but `status="published"` is accessible to authenticated users but not necessarily to anonymous email recipients who click the survey URL. CMP-005 does not add a visibility guard on `_validate_questionnaire_link` — only `status="published"` is checked. The assumption is that if an operator links a private questionnaire to a campaign, they accept the consequence that recipients cannot fill it in anonymously. A future improvement (out of scope here) could warn the operator in the UI if `visibility != "public"` when linking.

**Assumption A-2:** CMP-005 validates only `status="published"`. Visibility enforcement is the questionnaire system's responsibility.

**OQ-3: Response attribution.**
When a recipient follows the survey URL embedded in the campaign email, their questionnaire response session is anonymous (or linked to their platform account if they are logged in). There is no mechanism in this ticket to attribute a questionnaire response to a specific campaign send or recipient. Tracking-code integration (via a query parameter on the survey URL, e.g., `?utm_campaign={campaign_id}`) is a future enhancement for CMP-007/CMP-008. For now, the URL is a plain public URL with no tracking parameters.

**OQ-4: Rate of questionnaire lookup at send time.**
`_build_message_body` reads `campaign.get("questionnaire_slug")` from the in-memory campaign dict loaded by `send_campaign`. The slug is cached on the campaign item, so there is zero additional DDB reads at send time — only at create/update. This is the correct design; this note documents the confirmation.
