# LED-004 — Lead source tracking & attribution field

**Type:** Feature  **Priority:** P1  **Estimate:** 1 day  
**Ticket source:** `docs/suitecrm/CRM_LEADS_TICKETS.md`, section "LED-004"

---

## 1. Summary & Goal

LED-004 extends the Lead CRUD service from LED-003 with two new attributes — `attribution_code` and `campaign_id` — and delivers a read-only admin summary endpoint that returns a count breakdown of leads by `lead_source`.

The two new fields let every lead carry the marketing "entry path" that produced it. When a lead is created with an `attribution_code`, the service fires a best-effort call to `app/services/tracking_codes.record_visit` (delivered by MKT-010) so that the tracking-code analytics gain a `referrer="lead_create"` visit event. If MKT-010 has not yet shipped, the call is silenced via `ImportError` wrapping — lead creation is never blocked.

The admin endpoint `GET /ui/leads/sources/summary` uses the `BySource` GSI that LED-001 already provisions to count leads per source value with one `Select=COUNT` query per source. No new DynamoDB table, GSI, or index is required.

With `S.leads_enabled = False` (the default), all new behaviour is a complete no-op: the `attribution_code` and `campaign_id` fields are never written, the summary endpoint returns 404, and the `record_visit` hook is never reached.

## 3. Data Model

### 3.1 New Lead META attributes

LED-004 adds two optional attributes to every Lead META row written by `create_lead`. Both are stored directly on the same `PK=LEAD#{lead_id}/SK=META` item.

| DynamoDB attribute | Python type | Notes |
|---|---|---|
| `attribution_code` | `str \| None` | The raw tracking code slug supplied by the caller. Stored verbatim (not normalized). Absent when not provided. |
| `campaign_id` | `str \| None` | Opaque campaign identifier from the MKT module. Stored verbatim. Absent when not provided. |

Neither attribute is a GSI key. Neither requires an `attr_types` declaration. No new GSI, no new table, no `UpdateTable` is needed.

### 3.2 No new DynamoDB table or GSI

The `BySource` GSI (`GSI3PK=SOURCE#{lead_source}` / `GSI3SK=created_at`) is already provisioned by LED-001. The summary endpoint queries it with `Select="COUNT"` — it reads no item data, only the count returned by DynamoDB.

### 3.3 `LEAD_SOURCES` set (defined in LED-002, used by summary endpoint)

```python
LEAD_SOURCES = {
    "web_site", "cold_call", "email", "campaign",
    "trade_show", "word_of_mouth", "other", "internal"
}
```

The summary endpoint iterates over this set, issuing one `Select=COUNT` query per value against `BySource`. Eight queries total per summary request.

### 4.3 `app/services/leads.py` — `get_lead_source_counts` (new function)

```python
def get_lead_source_counts() -> list[dict]:
    """
    Return a count breakdown of Lead META rows grouped by lead_source.

    Issues one Select=COUNT query per value in LEAD_SOURCES against the
    BySource GSI (GSI3PK / GSI3SK). Paginates each per-source query via
    LastEvaluatedKey to ensure accuracy on large datasets.

    Returns:
        [{"lead_source": str, "count": int}, ...]  sorted by lead_source asc.
    """
    if not S.leads_enabled:
        raise HTTPException(503, "Leads module is not enabled")

    results = []
    for source in sorted(LEAD_SOURCES):
        total = 0
        exclusive_start_key = None
        while True:
            kwargs: dict = {
                "IndexName": "BySource",
                "KeyConditionExpression": Key("GSI3PK").eq(f"SOURCE#{source}"),
                "Select": "COUNT",
            }
            if exclusive_start_key:
                kwargs["ExclusiveStartKey"] = exclusive_start_key
            resp = T.leads.query(**kwargs)
            total += resp.get("Count", 0)
            exclusive_start_key = resp.get("LastEvaluatedKey")
            if not exclusive_start_key:
                break
        results.append({"lead_source": source, "count": total})
    return results
```

The function name `get_lead_source_counts` is intentionally distinct from the router endpoint path to make the service layer independently testable.

## 5. Detailed Behavior & Edge Cases

### 5.1 `attribution_code` is stored verbatim, not validated against MKT-010

LED-004 does not validate that `attribution_code` refers to a real tracking code in the `tracking_codes` table. The value is stored as-is on the lead. This is intentional: it allows leads to be created before MKT-010 ships (the MKT module is a soft dependency), and it avoids adding a cross-service read to the lead creation hot path. If validation is later required, it can be added to `create_lead` behind a separate feature flag.

### 5.2 `record_visit` is best-effort and fire-and-forget — no retry

The `record_visit` call in step 6.5 of `create_lead` is wrapped in a broad `except (ImportError, Exception)` block. A DynamoDB error inside MKT-010, a network timeout, or a `ModuleNotFoundError` all result in a silent pass. The lead is written successfully regardless. No retry queue, no background task, and no dead-letter mechanism is introduced at this ticket's scope. If attribution fidelity is critical, a follow-up ticket can add an asynchronous retry via the existing background task pattern in `app/services/audit_export_worker.py`.

### 5.3 `campaign_id` field has no FK constraint

`campaign_id` is an opaque string. There is no check that it corresponds to a real campaign in `T.mass_message_campaigns` or any other campaign table. Foreign-key enforcement is the responsibility of the calling client or a future validation layer (MKT-013 or LED-013 UX form validation).

### 5.4 Idempotent `create_lead` preserves attribution fields

The duplicate-detection path in `create_lead` (LED-003 §5.2 — returns the existing lead when a matching email is found under `STATUS#new`) returns the existing item without modification. If the first creation had `attribution_code="X"` and the idempotent second creation has `attribution_code="Y"`, the existing item is returned unchanged and `"Y"` is discarded. This is intentional: the first attribution wins (consistent with last-write-wins being undesirable for attribution).

The `record_visit` call is also skipped on the idempotent return path because the guard runs only after a successful `put_item`. If the idempotent branch fires before the `put_item`, `record_visit` is never called.

### 5.5 Summary endpoint count accuracy

The `Select=COUNT` query counts every item that projects into the `BySource` GSI with the given `GSI3PK` value, including soft-deleted leads (`deleted_at` set). This is intentional for the summary view — an admin wants to see total pipeline volume by source, not just active leads. If active-only counts are required, a `FilterExpression(Attr("deleted_at").not_exists())` can be added to each query; however, DDB applies `FilterExpression` after fetching items, so it reduces the returned count but not the scanned pages. For MVP, the simpler all-inclusive count is used.

### 5.6 Summary endpoint pagination per source

Each per-source `Select=COUNT` query paginates via `LastEvaluatedKey`. This mirrors the `_count_active_for_admin` pattern in `app/services/kyc_case_assignment.py:266-303`, which also loops via `LastEvaluatedKey` to get an exact count. The loop terminates when `resp.get("LastEvaluatedKey")` is `None`. A hard cap of 1000 pages per source is applied to prevent runaway loops in pathological conditions:

```python
page = 0
while page < 1000:
    ...
    page += 1
    if not exclusive_start_key:
        break
```

For any realistic lead volume the cap will never be reached.

### 5.7 `attribution_code` max length

`attribution_code` is capped at 200 characters via the Pydantic `Field(max_length=200)` annotation. Tracking code slugs in MKT-010 are expected to be short (human-readable, URL-safe strings), so 200 characters is a generous upper bound. Values that exceed this are rejected by Pydantic before reaching the service layer.

### 5.8 Summary endpoint is read-only — no CSRF required

`GET /ui/leads/sources/summary` is an HTTP GET. The `require_ui_session` dependency does not enforce the `x-csrf-token` header on GET requests (confirmed by `app/auth/deps.py` — CSRF is checked only for non-GET methods). No client-side CSRF token header is required.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No `dev_mode` branch

`app/services/leads.py` contains zero references to `S.dev_mode`. The `attribution_code` persistence, the `record_visit` fire-and-forget, and the `get_lead_source_counts` function all use `T.leads` (a `_safe_table` proxy targeting DynamoDB Local in dev, real DynamoDB in prod). The `audit_event` call writes to `T.alerts` in both environments. There is no mock path, no inline stub data, and no `if S.dev_mode:` bypass anywhere in LED-004's scope.

### 7.2 `record_visit` does not create a prod/dev parity issue

`app/services/tracking_codes.record_visit` (MKT-010) is itself written with SECOPS-007 parity — it uses `T.tracking_codes` unconditionally in both dev and prod. LED-004 calls it through a `try/except` which suppresses `ImportError` (MKT-010 not present) and all `Exception` subclasses (transient DDB errors). The suppression is identical in dev and prod — there is no env-specific mock.

### 7.3 Idempotency on `create_lead`

The idempotent duplicate path (LED-003 §5.2) returns the existing item without calling `put_item` again. If `attribution_code` was present on the original creation and is different on the idempotent replay, the original value is preserved. The `record_visit` hook is not fired on the idempotent path. These are consistent, deterministic behaviors independent of environment.

### 7.4 PII handling in attribution fields

`attribution_code` and `campaign_id` are not PII themselves. They are marketing metadata. They are included in the `audit_event("lead.created", ...)` call as non-PII extra fields, which is consistent with how `app/services/kyc_cases.py` includes case-metadata (not user PII) in audit events.

### 7.5 Injection safety

`attribution_code` and `campaign_id` are stored as DynamoDB String attributes. DynamoDB has no SQL injection surface. The values are not interpolated into any query expression — they are stored as item attributes and compared only via DynamoDB `Attr()` conditions (not present in LED-004's own query paths). CSV export safety via `_sanitize_csv_field` (per `app/services/csv_export.py:43`) must be applied by any future CSV export path that includes these fields, consistent with how all other string fields are handled there.

### 7.6 Authorization

The summary endpoint checks `ctx["role"] in (Role.ADMIN, Role.ROOT)` inside the handler. This is the same inline role-check pattern used throughout `app/routers/admin_roles.py`. Non-admin callers (USER role) receive HTTP 403 with the detail `"Admin access required"`. The route is not accessible to unauthenticated callers because `require_ui_session` raises HTTP 401/403 before the handler body is reached.

## 8. Backward Compatibility & Migration

### 8.1 Additive model fields — no breaking change

`attribution_code` and `campaign_id` are both `Optional[str] = None` on `LeadCreateIn` and `LeadOut`. Existing API clients that do not send these fields receive `None` in responses — the absence of the fields does not change any existing behavior. No existing `LeadCreateIn` caller is required to supply them.

### 8.2 No DynamoDB schema migration

The two new attributes are stored on existing Lead META rows only when present. Old rows (written before LED-004 ships) simply lack `attribution_code` and `campaign_id` attributes; DynamoDB returns them as absent, and `LeadOut` renders them as `None`. No backfill, no `UpdateTable`, and no index evolution is needed.

### 8.3 `create_lead` extension is backward-compatible

The `create_lead(creator_sub, data)` function signature is unchanged. `LeadCreateIn` is a Pydantic model; adding optional fields with defaults is non-breaking for existing callers that construct it directly.

### 8.4 `get_lead_source_counts` is a new function

No existing function is modified. `get_lead_source_counts` is an additive new function in `app/services/leads.py`. It is not called by any existing code path.

### 8.5 Summary endpoint is a new route

`GET /ui/leads/sources/summary` is a new FastAPI route registered in `app/routers/leads.py` (LED-013). It does not modify any existing route. The route is declared before `/{lead_id}` in the router file (see Section 4.4) so the literal segment `sources` is not captured by the dynamic parameter.

## 10. Open Questions / Assumptions

1. **Should `record_visit` be called on idempotent `create_lead` (duplicate email path)?** The current design skips it because the lead row is not written. An alternative is to always call `record_visit` when `attribution_code` is present, even if the lead already exists, to capture repeat visits from the same source. This is not done because it would inflate `visit_count` on the tracking code without a corresponding new lead. Assumed: call `record_visit` only on actual new lead creation.

2. **Should `attribution_code` be updatable via `PATCH /ui/leads/{id}`?** The current design makes it immutable post-creation. This matches the typical first-touch attribution model. If last-touch or multi-touch attribution is required, a separate spec is needed. Assumed: immutable at LED-004 scope.

3. **Should the summary endpoint include soft-deleted leads?** The current design counts all GSI rows, including soft-deleted ones (no `FilterExpression` on `deleted_at`). This gives a total pipeline-volume view. If active-only counts are required for the UI, the endpoint should accept a `?active_only=true` query param that adds the `FilterExpression`. Assumed: total-volume counts for MVP.

4. **Are `attribution_code` and `campaign_id` returned in `LeadOut` when absent?** Yes — `Optional[str] = None` means absent DDB attributes serialize to `null` in the JSON response, not omitted. Clients must handle `null` for these fields. Assumed: consistent with every other optional field in `LeadOut`.

5. **Should `record_visit` receive the lead's `party_id` once PTY-007 ships?** MKT-010's `record_visit` accepts `party_id` to associate the visit with a Party entity. LED-004 currently passes `party_id=None` (anonymous). Once PTY-007 delivers `find_party_by_contact(email)`, a follow-up change to `create_lead` can pass `party_id=converted_party_id` if one exists. Assumed: out of scope for LED-004; the field defaults to `None` and is documented as a known gap.
