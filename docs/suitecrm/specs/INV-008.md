# INV-008 — Invoice PDF branding — admin-configurable logo, company name, and footer

**Type:** Feature | **Priority:** P2 | **Estimate:** 2d | **Flag:** `AOS_INVOICE_BRANDING_ENABLED` (default OFF)

---

## 1. Summary & Goal

INV-008 gives platform admins a runtime-editable branding configuration that is injected into every generated invoice PDF: a company name that replaces the bare `"INVOICE"` header, an optional multi-line address block, a footer line, and an S3-stored logo whose key is embedded as a placeholder for downstream template engines (see §11, QUO-002). When the feature flag is off the existing PDF output is byte-for-byte unchanged.

**Primary user story:** An admin navigates to the Admin Invoice Branding panel, uploads a PNG logo, sets `company_name = "Acme Corp"` and `footer_text = "Payment terms: Net 30"`, and the next invoice PDF downloaded by any user reads `"Acme Corp INVOICE"` in the header and `"Payment terms: Net 30"` at the foot — with no re-deploy required.

## 3. Data Model

### Reuse: existing `billing_config` table — no new table

INV-008 **does not introduce a new DynamoDB table**. Branding is stored as a single row in the existing `T.billing_config` table (same table used by `app/services/billing_config.py`):

```
pk  = "INVOICE_BRANDING"           # fixed string, distinct from "BILLING_CONFIG"
sk  = "CURRENT"                    # single config row
─────────────────────────────────────────────────────────
company_name            str         # e.g. "Acme Corp"
company_address_lines   list[str]   # up to 5 lines; stored as a DynamoDB List
footer_text             str         # e.g. "Payment terms: Net 30"
logo_s3_key             str         # "invoice-branding/logo.{ext}" or ""
logo_bucket             str         # S.filemgr_bucket value at upload time, or ""
updated_at              int (N)     # now_ts() at last write
updated_by              str         # admin_sub
```

**No GSI is required** — branding is always read by its exact primary key `("INVOICE_BRANDING", "CURRENT")` and written in full on every update.

**No `scripts/local-ddb-init.py` change is needed** — `T.billing_config` is already declared at line 78 as `TableDef(..., "pk", "sk")` with no GSIs. No numeric sort keys, no `attr_types` changes.

**Why single-table reuse:** The `billing_config` table's design — a single partition keyed by a short string constant, a `CURRENT` row, and an `AUDIT#` history — is exactly the pattern needed here. Writing branding under `pk="INVOICE_BRANDING"` is invisible to `get_billing_config()` (which only reads `pk="BILLING_CONFIG"`) and cannot interfere with existing billing configuration logic.

## 4. API / Service Design

### New service: `app/services/invoice_branding.py`

```python
# Module-level cache (mirrors billing_config.py:46–58)
_branding_cache: Optional[Dict[str, Any]] = None
_cache_ts: int = 0

def _cache_ttl() -> int:
    return int(getattr(S, "invoice_branding_cache_ttl_seconds", 60) or 60)

def invalidate_cache() -> None:
    global _branding_cache, _cache_ts
    _branding_cache = None
    _cache_ts = 0

def _defaults() -> Dict[str, Any]:
    return {
        "company_name": "",
        "company_address_lines": [],
        "footer_text": "",
        "logo_s3_key": "",
        "logo_bucket": "",
        "updated_at": None,
        "updated_by": None,
    }

def get_branding() -> Dict[str, Any]:
    """Read pk='INVOICE_BRANDING'/sk='CURRENT' from T.billing_config.
    Caches for S.invoice_branding_cache_ttl_seconds (default 60s).
    Returns defaults on cache miss or DDB error (never raises).
    Gated on S.aos_invoice_branding_enabled; returns defaults when off.
    """

def update_branding(
    admin_sub: str,
    *,
    company_name: Optional[str] = None,
    company_address_lines: Optional[List[str]] = None,
    footer_text: Optional[str] = None,
) -> Dict[str, Any]:
    """Merge-write non-None fields onto the CURRENT row; invalidate cache;
    emit audit_event("invoice_branding.updated", admin_sub, fields={...}).
    Returns the updated branding dict.
    Raises ValueError if company_address_lines has more than 5 entries.
    Raises ValueError if any address line exceeds 120 characters.
    """

def upload_logo(
    admin_sub: str,
    image_bytes: bytes,
    content_type: str,       # "image/png" or "image/jpeg"
) -> str:
    """Store logo at 'invoice-branding/logo.{ext}' in S.filemgr_bucket
    via app.core.aws_clients.s3_client(); write logo_s3_key + logo_bucket
    to the CURRENT row; invalidate cache; emit audit_event("invoice_branding.logo_uploaded", ...).
    Returns the S3 key string.
    Raises ValueError for unsupported content_type.
    """

def get_logo_bytes() -> Optional[bytes]:
    """Fetch logo from S3 using the stored logo_s3_key / logo_bucket.
    Returns None when no logo is configured or on S3 ClientError.
    Never raises.
    """
```

**Validation rules:**
- `company_name`: max 120 characters; empty string is valid (disables company name branding).
- `company_address_lines`: max 5 entries; each entry max 120 characters.
- `footer_text`: max 250 characters; empty string is valid (disables footer).
- `content_type`: must be one of `{"image/png", "image/jpeg"}` — other types raise `ValueError("unsupported logo content type")`.

**S3 key scheme for logos:** `invoice-branding/logo.png` or `invoice-branding/logo.jpg` — a single overwrite key per platform (not per user). Re-uploading replaces the previous logo. This keeps storage simple and avoids orphaned keys.

**Merge semantics for `update_branding`:** Only fields supplied as non-None are changed. Supplying `company_name=""` explicitly clears the company name. `logo_s3_key` is not writable via `update_branding`; it is only set by `upload_logo`.

    branding: Dict[str, Any] = {}
    if S.aos_invoice_branding_enabled:

            from app.services import invoice_branding as _ib
            branding = _ib.get_branding()

    address_lines = branding.get("company_address_lines") or []
    footer_text = branding.get("footer_text") or ""
    logo_s3_key = branding.get("logo_s3_key") or ""

    if company_name:

    for addr_line in address_lines:
        lines.append(addr_line)
    if company_name or address_lines:
        lines.append("-" * 48)

    # Logo placeholder (only when logo_s3_key set)
    if logo_s3_key:
        lines.append(f"[Logo: {logo_s3_key}]")

    # ... existing invoice number / date / type / payment / BILL TO / SELLER blocks unchanged ...
    # ... existing line-item table unchanged ...
    # ... existing subtotal / tax / total block unchanged ...

    lines.append("")
    # Footer text (new, only when non-empty)

    lines.append("Thank you for your purchase.")

## 5. Detailed Behavior & Edge Cases

### Cache invalidation on update

`invalidate_cache()` is called immediately inside both `update_branding` and `upload_logo`, before returning. The next call to `get_branding()` — even on the same worker — will hit DynamoDB. Since the service is designed for a single-worker dev environment (`uvicorn --workers 1`, per CLAUDE.md), no cross-process cache invalidation is needed. In a multi-worker prod deployment the 60-second TTL (configurable via `INVOICE_BRANDING_CACHE_TTL_SECONDS`) is the eventual-consistency window; admins are told in the UI that branding updates take up to 60 seconds to propagate.

### Invoice regeneration on S3 cache miss

`download_invoice_pdf` (invoices.py line 442–452) falls back to re-rendering from the stored DDB record when the S3 key is missing. After an admin updates branding, previously generated PDFs cached in S3 will return stale bytes — because the S3 key still resolves. This is intentional and acceptable: historical invoices retain their original branding. If the admin wants historical invoices re-branded, they must delete the S3 objects manually (out of scope for this ticket).

### Logo embedding limitation

The `_render_pdf` function (invoices.py line 103) is a pure-PostScript text renderer with no image embedding capability — its objects array has no XObject or image stream type. A logo `[Logo: ...]` placeholder line is written as text so that QUO-002's AOS PDF template engine (when deployed) can replace the text-based renderer and inject a real image from the same S3 key recorded in branding. This approach avoids introducing new binary dependencies (no `fpdf2`, `Pillow`, etc.) in line with the project's "pure-Python, no system deps" renderer philosophy (invoices.py line 8–10).

### Concurrent admin updates (last-write-wins)

`update_branding` does a full `put_item` on `("INVOICE_BRANDING", "CURRENT")` with no optimistic concurrency. Two simultaneous admin PATCH calls may interleave. Given the infrequency of branding changes and single-admin nature of the setting, last-write-wins is sufficient. If stronger consistency is later needed, a `ConditionExpression` on `updated_at` can be added without schema changes.

### Empty / partial branding

Admins may partially configure branding. Only non-empty fields affect the rendered PDF:
- `company_name = ""` (default): header stays `"INVOICE"`, no address block.
- `footer_text = ""` (default): no footer line above "Thank you for your purchase."
- `logo_s3_key = ""` (default): no `[Logo: ...]` line.

This means a partial config (e.g., footer only) works correctly without requiring all fields to be set.

### Address line validation

`company_address_lines` is validated in `update_branding` before writing to DDB:
- More than 5 entries → `ValueError("company_address_lines: max 5 lines")` → 400 from the router.
- Any line longer than 120 characters → `ValueError(...)` → 400 from the router.

### Logo size limit

The `/branding/logo` endpoint checks `len(contents) > 2_000_000` before calling the service and returns HTTP 413 with `{"code": "logo_too_large", "max_bytes": 2000000}`. This prevents DDB writes of large keys and S3 throughput spikes.

### Flag-off behavior

When `AOS_INVOICE_BRANDING_ENABLED=0`:
- `GET /ui/admin/invoices/branding` → 404.
- `PATCH /ui/admin/invoices/branding` → 404.
- `POST /ui/admin/invoices/branding/logo` → 404.
- `get_branding()` called from `_render_invoice_lines` returns `{}` immediately (short-circuit before any DDB call).
- Invoice PDFs are byte-for-byte identical to today.

### Route ordering

The three new admin-router endpoints (`/branding`, `/branding`, `/branding/logo`) are registered before any future `/{invoice_number}` segment on `invoices_admin_router`. The existing admin router has only `GET ""` and `GET /` (lines 97–98 of invoices.py); there is no existing dynamic segment. However, explicit ordering is enforced in the code to guard against future additions.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 dev/prod parity

There are no `if S.dev_mode` branches anywhere in the new code. The branding row is stored in DynamoDB (moto-intercepted in dev, real DynamoDB in prod) using the same code path. S3 logo uploads go through `app.core.aws_clients.s3_client()` (moto-intercepted in dev, real S3 in prod) — same as `_store_pdf` in invoices.py:198. No mock-only branches.

### Idempotency

- `update_branding` is a full `put_item` on a fixed key: calling it twice with the same values writes the same row twice. The second call is a no-op from a data perspective (identical item written). The `invalidate_cache()` call on the second write is harmless.
- `upload_logo` overwrites the same S3 key (`invoice-branding/logo.{ext}`) on every call. A re-upload with the same bytes produces the same content at the same key.

### Security

- **Role enforcement:** The GET endpoint uses `require_admin_or_root` (app/auth/policy.py:67); the two mutating endpoints (`PATCH /branding`, `POST /branding/logo`) must use `require_admin_or_root_csrf` (app/auth/policy.py:100) to enforce CSRF for cookie-authenticated callers. Standard users receive 403.
- **Logo content-type validation:** The endpoint accepts only `image/png` and `image/jpeg`. Other MIME types are rejected 400 before any bytes are stored.
- **Logo size cap:** 2 MB hard limit at the endpoint layer prevents DoS via oversized uploads.
- **Audit trail:** Every `update_branding` and `upload_logo` call emits `audit_event(...)` to `T.alerts`. Admin identity (`admin_sub`) is recorded on the DDB branding row itself (`updated_by` field).
- **S3 key namespacing:** Logo is stored under `invoice-branding/` prefix — distinct from user file manager objects (`files/`), invoice PDFs (`invoices/`), KYC documents (`kyc/`). Standard S3 bucket-policy permission boundaries are unaffected.
- **No PII in the logo S3 key:** The key `invoice-branding/logo.png` contains no user sub or identifying data; it is the same fixed key for all uploads.
- **CSRF:** `require_admin_or_root` (policy.py:67) calls `get_authenticated_user` which does NOT enforce CSRF. For cookie-authenticated write requests, the endpoints must use `require_admin_or_root_csrf` (policy.py:100), which wraps `enforce_cookie_csrf` + `require_admin_or_root`. The GET endpoint may keep `require_admin_or_root` since GET is CSRF-exempt. <!-- CORRECTED: original falsely claimed require_admin_or_root enforces CSRF. It does not. The CSRF-enforcing variant is require_admin_or_root_csrf. -->

### Zero migration required

- No new DynamoDB table is created.
- The `billing_config` table requires no schema change — `pk="INVOICE_BRANDING"` is a new partition that does not conflict with `pk="BILLING_CONFIG"`.

- Existing invoices already stored in S3 are not affected. Their cached PDF bytes remain at their S3 keys and are served unchanged.
- All existing E2E tests remain valid: with the flag off (default), `_render_invoice_lines` produces identical output.

### Deployment sequence

1. Deploy backend code with `AOS_INVOICE_BRANDING_ENABLED=0` (the default). No migration needed.
2. Admin configures branding via the new endpoints.
3. Set `AOS_INVOICE_BRANDING_ENABLED=1` in environment.
4. From the next invoice generation (or PDF re-render on cache miss) onward, branding is applied.

## 10. Open Questions & Assumptions

**Q1: Should historical invoice PDFs be re-rendered on branding update?**
Assumed NO for INV-008 — historical PDFs are frozen at their S3 key and served as-is. Re-rendering all existing PDFs on branding update would require a background sweep of all `INV#` keys per user, which is a separate ticket. Admins can force a single invoice to regenerate by deleting its S3 object (the `download_invoice_pdf` S3-miss path at invoices.py:450 will re-render with current branding).

**Q2: Per-user or per-platform branding?**
Assumed **platform-wide** (single `INVOICE_BRANDING/CURRENT` row). SuiteCRM supports multi-company branding per account, but that requires an Accounts module (INV-010 / PTY-012) not yet built. Per-account branding is deferred to a future INV-0xx ticket once Account records exist.

**Q3: Logo image embedding in PDF?**
Assumed **deferred** — the current `_render_pdf` renderer (invoices.py:103) is a text-only PostScript writer with no XObject support. A `[Logo: ...]` placeholder line is written so QUO-002's template engine can substitute a real image. Full image embedding would require either introducing a PDF library dependency or significantly extending `_render_pdf` — both are out of scope for a 2d estimate.

**Q4: Multipart upload size limit — where to enforce?**
The 2 MB cap is enforced at the endpoint layer (before `await file.read()`) by checking the `Content-Length` request header. If `Content-Length` is missing (chunked encoding), the cap is checked after `await file.read()`. This is consistent with how the KYC partner API handles uploads (kyc_partner_api.py:203).

**Q5: What happens if `T.billing_config` is unavailable at PDF render time?**
`get_branding()` wraps the DDB read in a broad `try/except` and returns `_defaults()` on error. PDF generation is never blocked by a branding DDB failure — it degrades to the unbranded layout transparently.
