# CAS-011 — Case-to-case relationship links

**Type:** Feature | **Priority:** P2 | **Estimate:** 1 day
**Parent area:** CRM Cases, Customer Support & Customer Portal
**Ticket source:** `docs/suitecrm/CRM_CASES_PORTAL_TICKETS.md`, section "CAS-011"
**Depends on:** CAS-001 (master flag `crm_cases_enabled`, `crm_cases_links` table, `T.crm_cases_links` handle)

---

## 1. Summary & Goal

CAS-011 introduces typed bidirectional links between support tickets. A link captures that two tickets are related in a structured way: one is a `duplicate` of another, one `blocks` another, or one `relates_to` another. Agents and administrators can create and remove links; owners can read the link list for their own tickets.

The feature is strictly additive. With `CRM_CASES_ENABLED=0` (the default) all new routes return 404, no DynamoDB writes occur, and the existing `app/routers/tickets.py` and `app/services/tickets.py` are byte-for-byte unchanged. When the flag is on, three new endpoints are appended to the tickets router and a new service module `app/services/ticket_links.py` is added. `TicketOut` gains an additive `links` field that defaults to `[]` so existing callers see no change in shape until they read a ticket whose links have been populated.

### 2.5 Sibling CAS context

The `crm_cases_links` table is separate from the `tickets` table. Its write path does not touch `_conditional_update_meta` (`tickets.py:723`) and has no interaction with ticket optimistic locking.

## 3. Data Model

### 3.1 `crm_cases_links` table (from CAS-001)

No new table is introduced. All link data lives in the `crm_cases_links` table provisioned by CAS-001.

**Primary key:**
| Attribute | Type | Notes |
|---|---|---|
| `ticket_id` | String (PK) | The originating ticket, e.g. `tkt_abc123` |
| `sk` | String (SK) | `LINK#{related_ticket_id}` |

**GSI — `ByRelated`:**
| Attribute | Type | Notes |
|---|---|---|
| `related_ticket_id` | String (GSI PK) | Enables reverse-lookup: "all tickets that link to X" |
| `created_at` | Number (GSI SK) | Unix timestamp; `attr_types={"created_at": "N"}` in `scripts/local-ddb-init.py` — **already declared by CAS-001** |

**Item attributes (per link row):**

| Attribute | Type | Notes |
|---|---|---|
| `ticket_id` | String | Partition key |
| `sk` | String | `LINK#{related_ticket_id}` |
| `related_ticket_id` | String | Plain ticket id |
| `link_type` | String | One of `duplicate`, `blocks`, `relates_to` |
| `direction` | String | `source` or `target` — records which end of the link this row represents |
| `created_at` | Number | `now_ts()` at write time |
| `created_by` | String | `user_sub` of the admin who created the link |

### 3.2 Bidirectional write pattern

For every logical link A→B, two rows are written via a DynamoDB `transact_write_items` call (NOT `batch_writer`):

1. `PK=ticket_id_A`, `SK=LINK#{ticket_id_B}`, `direction="source"`, `link_type=<type>`
2. `PK=ticket_id_B`, `SK=LINK#{ticket_id_A}`, `direction="target"`, `link_type=<type>`

For `relates_to` links the distinction between `source` and `target` is cosmetic (the relationship is symmetric). For `duplicate` and `blocks` the directionality is meaningful: A `blocks` B means A is the blocker; A is the `duplicate` of B means A is the newer/lower-priority one.

For delete, both rows are removed via a `transact_write_items` call of two `Delete` actions. **Important**: DynamoDB `batch_writer` (BatchWriteItem) does NOT provide atomicity — it is a best-effort operation that can partially succeed. Use `transact_write_items` (TransactWriteItems) for all-or-nothing guarantees, matching the pattern used by `app/services/group_treasury.py` and `app/services/content_reports_store.py`. The `_FloatSafeTable` proxy does not wrap `transact_write_items`; call it via `T.crm_cases_links.meta.client.transact_write_items(TransactItems=[...])` using fully-qualified low-level item dicts (same pattern as `app/services/refund_requests.py:292`).

### 3.3 No schema change to `tickets` table

The tickets META row (`pk=TICKET#{id}`, `sk=META`) gains no new attributes. Links are a separate concern in their own table. `get_ticket` continues to read from `T.tickets` only; `TicketLinkService.list_links` is called by the router when assembling the enriched `TicketOut` that includes a `links` list.

## 4. API / Service Design

### 4.1 Service: `app/services/ticket_links.py` (new file)

```python
_VALID_LINK_TYPES = frozenset({"duplicate", "blocks", "relates_to"})

class TicketLinkError(Exception):
    def __init__(self, detail: dict): ...

@dataclass
class TicketLinkService:
    _table: Any = field(default_factory=lambda: T.crm_cases_links)

    def add_link(self, *, ticket_id, related_ticket_id, link_type, created_by) -> list[dict]: ...
    def remove_link(self, *, ticket_id, related_ticket_id) -> None: ...
    def list_links(self, ticket_id: str) -> list[dict]: ...

LINK_SERVICE = TicketLinkService()
```

**`add_link`**: validates `link_type in _VALID_LINK_TYPES` (→ `invalid_link_type`); rejects self-links (→ `self_link_forbidden`); `get_item` existence check (→ `link_already_exists` if present); writes both directional rows via `transact_write_items` (two `Put` actions) with `created_at=now_ts()`; returns `list_links(ticket_id)`. Use `self._table.meta.client.transact_write_items(TransactItems=[{"Put": {"TableName": ..., "Item": ...}}, ...])` — the `_FloatSafeTable` proxy does not wrap `transact_write_items`.

**`remove_link`**: `get_item` existence check (→ `link_not_found` if absent); removes both directional rows via `transact_write_items` (two `Delete` actions).

**`list_links`**: queries `KeyCondition="ticket_id = :pk AND begins_with(sk, 'LINK#')"`, `ScanIndexForward=True`; returns raw items for the router to serialize.

### 4.2 Pydantic models (added to `app/routers/tickets.py`)

```python
from typing import Literal as _Lit

class TicketLinkOut(BaseModel):
    ticket_id: str
    related_ticket_id: str
    link_type: _Lit["duplicate", "blocks", "relates_to"]
    direction: _Lit["source", "target"]
    created_at: int
    created_by: str

class TicketLinksEnvelope(BaseModel):
    links: list[TicketLinkOut]

class AddTicketLinkReq(BaseModel):
    related_ticket_id: str = Field(..., min_length=1, max_length=64)
    link_type: _Lit["duplicate", "blocks", "relates_to"]
```

**`TicketOut` addition** (additive, backward-compatible):
```python
class TicketOut(BaseModel):
    ...  # existing fields unchanged
    links: list[TicketLinkOut] = []
```

`TicketOut.links` is populated only when the caller uses `GET /tickets/{ticket_id}` with `CRM_CASES_ENABLED=1`. When the flag is off, the `get_ticket` handler does not call `LINK_SERVICE.list_links` and the field stays at its default `[]`.

### 4.3 Endpoints (added to `app/routers/tickets.py`)

All three endpoints are declared **before** `@router.get("/{ticket_id}", ...)` at `router:900` to prevent path-parameter capture.

---

#### `GET /tickets/{ticket_id}/links`

**Auth:** `require_ui_session` + `get_authenticated_user`. Caller must pass `_can_access_ticket` (owner or admin).
**Gate:** `if not S.crm_cases_enabled: _raise(404, ...)`.
**Logic:** `_ticket_or_404(ticket_id)` → access check → `LINK_SERVICE.list_links(ticket_id)` → return `TicketLinksEnvelope`.
**Response:** `200 TicketLinksEnvelope`.

---

#### `POST /tickets/{ticket_id}/links`

**Auth:** `require_ui_session` + `get_authenticated_user`. `_is_admin_actor` only.
**Gate:** `if not S.crm_cases_enabled: _raise(404, ...)`.
**Request body:** `AddTicketLinkReq`.
**Logic:** `_is_admin_actor` check → `_ticket_or_404(ticket_id)` → `_ticket_or_404(related_ticket_id)` → `LINK_SERVICE.add_link(...)`. Map `TicketLinkError` codes to HTTP: `link_already_exists`→409, `self_link_forbidden`→400. On success: `audit_event("ticket_link_added", ...)`, return `201 TicketLinksEnvelope`.

---

#### `DELETE /tickets/{ticket_id}/links/{related_ticket_id}`

**Auth:** `require_ui_session` + `get_authenticated_user`. Admin actor only.
**Gate:** `if not S.crm_cases_enabled: _raise(404, ...)`.
**Logic:** `_is_admin_actor` check → `_ticket_or_404(ticket_id)` → `LINK_SERVICE.remove_link(...)`. Map `link_not_found`→404. On success: `audit_event("ticket_link_removed", ...)`, return `204 No Content`.

### 4.4 `get_ticket` enrichment

The existing `get_ticket` handler at `router:900` is extended with a flag-gated call:

```python
@router.get("/{ticket_id}", response_model=TicketEnvelope, ...)
def get_ticket(ticket_id: str, request: Request, _ctx=Depends(require_ui_session), user=Depends(get_authenticated_user)):
    ticket = _ticket_or_404(ticket_id)
    if not _can_access_ticket(request, user, ticket):
        _raise(403, ...)
    if S.crm_cases_enabled:
        ticket = {**ticket, "links": LINK_SERVICE.list_links(ticket_id)}
    return _wrap_ticket(ticket)
```

`_wrap_ticket` calls `TicketOut.model_validate(ticket)` (`router:232–233`). Because `TicketOut.links` defaults to `[]`, callers on a flag-off deployment receive `"links": []` transparently.

## 5. Detailed Behavior & Edge Cases

### 5.1 Non-existent target ticket

`POST /tickets/{id}/links` verifies that the `related_ticket_id` resolves via `_ticket_or_404` before writing any row. This prevents orphan link rows where one end points to a deleted or never-created ticket.

If a target ticket is deleted after a link is created, the link row remains but the related ticket will 404 on navigation. `list_links` does not filter or validate the remote side; the caller (UI or API consumer) is responsible for handling 404 when navigating to a linked ticket. A future cleanup sweep (out of scope here) could prune dangling links.

### 5.2 Duplicate-link prevention

`add_link` performs a `get_item` existence check before writing. If the row already exists, it raises `TicketLinkError(code="link_already_exists")` which the router converts to 409. Because simultaneous duplicate-link creation is unlikely (agents rarely race on the same pair), a read-then-write without a conditional expression is sufficient.

### 5.3 Self-links

`add_link` rejects `ticket_id == related_ticket_id` before touching DynamoDB (400, `self_link_forbidden`).

### 5.4 Direction semantics

Each logical link A→B writes two rows: the source row (`PK=A`, `SK=LINK#B`, `direction="source"`) and the target row (`PK=B`, `SK=LINK#A`, `direction="target"`). Both rows carry the same `link_type`. For `relates_to` the direction is cosmetic (symmetric relationship); for `blocks` and `duplicate` it is meaningful.

### 5.5 `list_links` returns both perspectives

`list_links(ticket_id)` queries `PK=ticket_id, begins_with(SK, "LINK#")`. This returns both outgoing rows (where `ticket_id` is the source) and incoming rows (where it is the target), giving the full link neighborhood in a single query.

### 5.6 Link type validation

Pydantic `Literal["duplicate", "blocks", "relates_to"]` on `AddTicketLinkReq.link_type` fires 422 before the handler body. The service-layer `_VALID_LINK_TYPES` frozenset is a belt-and-suspenders guard for direct service callers.

### 5.7 Terminal ticket status

No restriction is placed on ticket status for link creation or removal. A `done` ticket may still be linked. A future policy check can be added to `add_link` without a schema change.

### 5.8 No notification email

Link events generate `audit_event` calls only. The event names `ticket_link_added` and `ticket_link_removed` are added to `ALERT_EVENT_TYPES` (`alerts.py:134–148`) and to `_NO_ALERT_EVENTS` (`alerts.py:117`) so the audit trail writes to `T.alerts` without triggering push or email fan-out. `render_ticket_email_template` (`alerts.py:235`) is not extended.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/Prod parity

`TicketLinkService` uses `T.crm_cases_links` exclusively with no `S.dev_mode` branch. In dev the table is DynamoDB Local; in prod it is a real DynamoDB table. Same `transact_write_items` and `query` calls both ways (SECOPS-007).

### 7.2 Idempotency

Repeat `add_link` with the same pair returns 409. Repeat `remove_link` after deletion returns 404. Callers may treat both as "already in desired state" if appropriate.

### 7.3 Access control

Read (`GET .../links`): ticket owner or admin, matching `_can_access_ticket` (`router:339`). Write (`POST`, `DELETE`): admin actor only (`_is_admin_actor`), consistent with CAS-009's escalation endpoint.

### 7.4 No PII, no money movement

Link rows contain only ticket IDs, `link_type`, `direction`, `created_at`, and `created_by` (a user sub). No billing, refund, or ledger operation occurs.

## 10. Open Questions / Assumptions

1. **Link count limit** — No hard cap is imposed. A future `CRM_CASES_MAX_LINKS_PER_TICKET` guard can be added to `add_link` without a schema change.

2. **Cascade on ticket delete** — No ticket hard-delete exists today. If one is introduced, its implementer must call a future `LINK_SERVICE.remove_all_links(ticket_id)` helper to prune dangling rows.

3. **`relates_to` directionality** — `direction` is recorded for completeness but is semantically neutral for `relates_to`. The UI should render it symmetrically.

4. **CAS-001 assumed merged** — `T.crm_cases_links`, `S.crm_cases_links_table`, and `S.crm_cases_enabled` must exist before CAS-011 can be implemented.

5. **`link_type` extensibility** — Additional types (e.g. `caused_by`) can be added by extending the `Literal` union and `_VALID_LINK_TYPES`, with no DynamoDB schema change.
