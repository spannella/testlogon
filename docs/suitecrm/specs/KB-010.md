# KB-010 — Article revision history / versioning

**Type:** Feature  **Priority:** P2  **Estimate:** 2 days  
**Ticket source:** `docs/suitecrm/CRM_KNOWLEDGE_BASE_TICKETS.md`, section "KB-010"

---

## 1. Summary & Goal

KB-010 adds a revision history system to KB articles: every time an admin saves an update that changes the article title or body, a snapshot of the pre-update state is written to DynamoDB. Admins can list past revisions, inspect individual snapshots, and restore a prior version (which itself snapshots the current state before overwriting).

Concrete deliverables:

1. A `REVISION#{article_id}` / `REV#{ts:012d}#{revision_id}` DDB row schema on the existing `crm_kb_articles` table — no new table.
2. An atomic `rev_counter` increment on the article META row (pattern from `app/services/invoices.py:85`) so every revision has a stable monotonic `rev_number`.
3. Three private service helpers: `_snapshot_revision`, `list_revisions`, `get_revision`, and `restore_revision` on `KbArticleService` (`app/services/kb_articles.py`).
4. Three admin-only router endpoints on `app/routers/kb_articles.py`: list revisions, get a single revision, and restore a revision.
5. Pydantic models `KbRevisionOut` and `KbRestoreReq` in `app/models.py`.

With `KNOWLEDGE_BASE_ENABLED=0` the platform is byte-for-byte unchanged: no revision rows are ever written, and all three endpoints return 404.

## 2. Context & Current State

### 2.1 `KbArticleService` and `update_article` (after CAS-015 through KB-009)

`app/services/kb_articles.py` is created by CAS-015 and extended by KB-002 through KB-009. At the time KB-010 ships, `KbArticleService.update_article(article_id, admin_sub, *, title, body_html, edit_note="", **fields)` exists but does not snapshot the pre-update state. KB-010 inserts a `_snapshot_revision` call at the top of `update_article`, before the `update_item` call, whenever `title` or `body_html` change from their stored values.

### 2.2 Atomic counter pattern

`app/services/invoices.py:85` shows the project-standard pattern for atomic monotonic counters:

```python
result = T.invoices.update_item(
    Key={"pk": "COUNTER", "sk": "SEQ"},
    UpdateExpression="ADD next_seq :inc",
    ExpressionAttributeValues={":inc": 1},
    ReturnValues="UPDATED_NEW",
)
seq = int(result["Attributes"]["next_seq"])
```

KB-010 reuses the same `ADD` expression on the article META row itself (`PK=ARTICLE#{article_id}`, `SK=META`) to increment a `rev_counter` field. This avoids a separate counter row and keeps all article state co-located.

### 2.3 Revision snapshot pattern (collaborations.py)

`app/services/collaborations.py:399` defines `_save_revision(collab, revision_number)` which writes a `sk=REV#{revision_number:04d}` snapshot row on the same PK. KB-010 adapts this pattern with a time-prefixed SK (`REV#{ts:012d}#{revision_id}`) so DynamoDB's native sort order returns revisions newest-first without a client-side sort.

### 2.4 crm_kb_articles table (after KB-001)

KB-001 (`docs/suitecrm/specs/KB-001.md`) declares `crm_kb_articles` in `scripts/local-ddb-init.py` with:
- PK = `pk` (String, HASH), SK = `sk` (String, RANGE) — **lowercase** per KB-001 (`docs/suitecrm/specs/KB-001.md:409–410`). All Key/Item dicts below use `pk`/`sk`, NOT the uppercase `PK`/`SK` that would mismatch the actual key schema.
- GSIs: `ByCategory`, `ByStatus`, `ByAuthor`, `ByTag`.
- `attr_types={"created_at": "N", "published_at": "N"}`.

Revision rows use `PK=REVISION#{article_id}` with `SK=REV#{ts:012d}#{revision_id}`. The `{ts:012d}` zero-padding ensures lexicographic sort on the string SK is equivalent to chronological sort — newest revisions have lexicographically larger SKs and are returned first by `ScanIndexForward=False`. No additional GSI is needed; revisions are always accessed by article PK.

`app/core/tables.py:29` wraps every table in `_FloatSafeTable` which coerces Python `float` to `Decimal` in `put_item` and `update_item`. All numeric fields in revision rows (`created_at`, `rev_number`) are plain `int` values and require no special handling.

## 3. Data Model

### 3.1 Revision rows (new, on existing `crm_kb_articles` table)

```
pk  = "REVISION#{article_id}"                          (String)
sk  = "REV#{created_at:012d}#{revision_id}"            (String)

Fields:
  revision_id          String    — UUID hex (e.g. "rev_" + uuid4().hex)
  article_id           String    — FK back to the article
  rev_number           Number    — monotonic integer (1-based); never reused
  title_snapshot       String    — article title at snapshot time
  body_html_snapshot   String    — full article body_html at snapshot time
  tags_snapshot        List[str] — article tags at snapshot time (empty list if no tags)
  edited_by            String    — user_sub of the admin who triggered the update
  edit_note            String    — optional free-text note supplied by the admin
  created_at           Number    — integer Unix timestamp (now_ts())
```

**SK format rationale.** `REV#{created_at:012d}#{revision_id}` zero-pads the timestamp to 12 decimal digits, giving correct lexicographic ordering until year 33658 CE. The `#{revision_id}` suffix guarantees uniqueness in the (astronomically unlikely) case of two concurrent updates at the same second.

**No GSI.** Revisions are always queried via `PK=REVISION#{article_id}`. DynamoDB range queries on the SK prefix are sufficient; no cross-article revision lookup is needed. This is consistent with the attachment row design in KB-003 (`ATTACHMENT#{id}`) and the rating row design in KB-005 (`RATING#{user}`).

### 3.2 Article META row additions (on existing META row)

The existing article META row (`PK=ARTICLE#{article_id}`, `SK=META`) gains one new field:

```
rev_counter   Number   — monotonic revision sequence; starts at 0, incremented
                         atomically via ADD on every snapshot write
```

`rev_counter` is initialized to `0` at article creation (KB-001 / CAS-015). The first snapshot write increments it to `1` and the snapshot is stored with `rev_number=1`.

### 3.3 scripts/local-ddb-init.py additions

No new `TableDef` entry is required. The existing `crm_kb_articles` `TableDef` (added by KB-001) already has `attr_types={"created_at": "N", "published_at": "N"}`. Revision rows do not introduce any new **GSI sort keys** that need `attr_types` declarations because revision rows carry no GSI attributes — they are only accessed through the table's primary key.

The `rev_counter` field on the META row is a plain numeric attribute, not a GSI key, so it also requires no `attr_types` addition.

## 4. API / Service Design

### 4.1 Service additions (`app/services/kb_articles.py`)

#### `KbArticleService._snapshot_revision(article_id, current_item, edited_by, edit_note) -> int`

Private helper. Called before applying any update that changes `title` or `body_html`.

```python
def _snapshot_revision(
    self,
    article_id: str,
    current_item: Dict[str, Any],
    edited_by: str,
    edit_note: str = "",
) -> int:
    """Write a REVISION# snapshot row; return the new rev_number."""
    # 1. Atomically increment rev_counter on META row.
    result = T.kb_articles.update_item(
        Key={"pk": f"ARTICLE#{article_id}", "sk": "META"},
        UpdateExpression="ADD rev_counter :one",
        ExpressionAttributeValues={":one": 1},
        ReturnValues="UPDATED_NEW",
    )
    rev_number = int(result["Attributes"]["rev_counter"])

    # 2. Write the snapshot row.
    ts = now_ts()
    revision_id = "rev_" + uuid.uuid4().hex
    item = {
        "pk": f"REVISION#{article_id}",
        "sk": f"REV#{ts:012d}#{revision_id}",
        "revision_id": revision_id,
        "article_id": article_id,
        "rev_number": rev_number,
        "title_snapshot": current_item.get("title", ""),
        "body_html_snapshot": current_item.get("body_html", ""),
        "tags_snapshot": list(current_item.get("tags") or []),
        "edited_by": edited_by,
        "edit_note": edit_note,
        "created_at": ts,
    }
    T.kb_articles.put_item(Item=item)

    # 3. Emit audit event (best-effort).
    try:
        from app.services.alerts import audit_event
        audit_event(
            "kb.article.revision_created",
            edited_by,
            article_id=article_id,
            rev_number=rev_number,
        )
    except Exception:
        logger.exception("Failed to emit revision audit event for %s", article_id)

    return rev_number
```

The `ADD rev_counter :one` expression is idempotent in the sense that a crash after the DDB write but before the `put_item` leaves the META row incremented but with no matching snapshot row. The resulting gap in `rev_number` is harmless — `rev_number` is informational only (list sorting is by timestamp SK, not `rev_number`).

#### `KbArticleService.update_article(article_id, admin_sub, *, title, body_html, edit_note="", **fields)` — modified

The existing `update_article` is modified to call `_snapshot_revision` when either `title` or `body_html` changes:

```python
def update_article(
    self,
    article_id: str,
    admin_sub: str,
    *,
    title: Optional[str] = None,
    body_html: Optional[str] = None,
    edit_note: str = "",
    **fields,
) -> Dict[str, Any]:
    if not S.knowledge_base_enabled:
        raise HTTPException(status_code=404)
    # 1. Fetch current item.
    current = self.get_article(article_id)  # raises 404 if not found
    # 2. Determine if a snapshot is needed.
    needs_snapshot = (
        (title is not None and title != current.get("title")) or
        (body_html is not None and body_html != current.get("body_html"))
    )
    if needs_snapshot:
        self._snapshot_revision(article_id, current, edited_by=admin_sub, edit_note=edit_note)
    # 3. Apply update (existing logic unchanged below).
    ...
```

If neither `title` nor `body_html` changes (e.g. only `category_id` or `tags` are updated), no snapshot is written and `rev_counter` is not incremented — consistent with the acceptance criterion "No revision written when body/title are unchanged."

#### `KbArticleService.list_revisions(article_id, limit=20, cursor=None) -> Tuple[List[Dict], Optional[str]]`

```python
def list_revisions(
    self,
    article_id: str,
    limit: int = 20,
    cursor: Optional[str] = None,
) -> Tuple[List[Dict[str, Any]], Optional[str]]:
    if not S.knowledge_base_enabled:
        raise HTTPException(status_code=404)
    kwargs: Dict[str, Any] = {
        "KeyConditionExpression": Key("pk").eq(f"REVISION#{article_id}"),
        "ScanIndexForward": False,   # newest SK (largest ts) first
        "Limit": min(limit, 50),
    }
    if cursor:
        lek = decode_cursor(cursor)
        if lek:
            kwargs["ExclusiveStartKey"] = lek
    resp = T.kb_articles.query(**kwargs)
    items = resp.get("Items", [])
    next_cursor = encode_cursor(resp.get("LastEvaluatedKey"))
    return items, next_cursor
```

`ScanIndexForward=False` returns items in descending SK order. Because `SK=REV#{ts:012d}#{uuid}` is padded, newer revisions always have a lexicographically larger SK and appear first — no client-side sort needed.

#### `KbArticleService.get_revision(article_id, revision_id) -> Dict[str, Any]`

```python
def get_revision(
    self,
    article_id: str,
    revision_id: str,
) -> Dict[str, Any]:
    if not S.knowledge_base_enabled:
        raise HTTPException(status_code=404)
    # Query the REVISION# partition and filter by revision_id attribute.
    resp = T.kb_articles.query(
        KeyConditionExpression=Key("pk").eq(f"REVISION#{article_id}"),
        FilterExpression=Attr("revision_id").eq(revision_id),
        Limit=200,
    )
    items = resp.get("Items", [])
    if not items:
        raise HTTPException(status_code=404, detail="Revision not found")
    return items[0]
```

A direct `get_item` is not possible because the SK includes the timestamp, which is not known to the caller (the caller knows only `revision_id`). The query uses a `FilterExpression` on the `revision_id` attribute. Because `FilterExpression` does not reduce the page count (CLAUDE.md "DDB FilterExpression doesn't reduce page size"), a `Limit=200` per-page loop is used. In practice an article will rarely have more than 200 revisions, but a loop on `LastEvaluatedKey` should be added for correctness.

#### `KbArticleService.restore_revision(article_id, revision_id, admin_sub, *, edit_note="") -> Dict[str, Any]`

```python
def restore_revision(
    self,
    article_id: str,
    revision_id: str,
    admin_sub: str,
    edit_note: str = "",
) -> Dict[str, Any]:
    if not S.knowledge_base_enabled:
        raise HTTPException(status_code=404)
    # 1. Fetch the revision to restore.
    rev = self.get_revision(article_id, revision_id)
    # 2. Fetch current META (snapshot it before overwriting).
    current = self.get_article(article_id)
    self._snapshot_revision(
        article_id,
        current,
        edited_by=admin_sub,
        edit_note=f"[pre-restore] {edit_note}".strip(),
    )
    # 3. Overwrite META with snapshot values.
    now = now_ts()
    T.kb_articles.update_item(
        Key={"pk": f"ARTICLE#{article_id}", "sk": "META"},
        UpdateExpression=(
            "SET title = :t, body_html = :b, tags = :tg, updated_at = :now, "
            "last_edited_by = :who, last_edit_note = :note"
        ),
        ExpressionAttributeValues={
            ":t": rev["title_snapshot"],
            ":b": rev["body_html_snapshot"],
            ":tg": rev.get("tags_snapshot") or [],
            ":now": now,
            ":who": admin_sub,
            ":note": edit_note or "",
        },
    )
    # 4. Rebuild search index for the restored title (KB-009).
    try:
        published_at = int(current.get("published_at") or 0)
        status = current.get("status", "draft")
        _delete_kb_search_index(article_id, current.get("title", ""))
        _write_kb_search_index(article_id, rev["title_snapshot"], published_at, status)
    except Exception:
        logger.exception("Search index rebuild failed on restore for %s", article_id)
    # 5. Rebuild tag index if tags changed (KB-007).
    old_tags = list(current.get("tags") or [])
    new_tags = list(rev.get("tags_snapshot") or [])
    if set(old_tags) != set(new_tags):
        try:
            _delete_kb_tag_index(article_id, old_tags)
            # KB-007 signature is _write_kb_tag_index(article_id, tags, published_at, status, title)
            _write_kb_tag_index(
                article_id,
                new_tags,
                int(current.get("published_at") or 0),
                current.get("status", "draft"),
                rev["title_snapshot"],
            )
        except Exception:
            logger.exception("Tag index rebuild failed on restore for %s", article_id)
    # 6. Audit event.
    try:
        from app.services.alerts import audit_event
        audit_event(
            "kb.article.revision_restored",
            admin_sub,
            article_id=article_id,
            restored_rev_number=int(rev.get("rev_number", 0)),
        )
    except Exception:
        logger.exception("Audit event failed on restore for %s", article_id)
    return self.get_article(article_id)
```

Steps 4 and 5 are best-effort (`try/except`) — a search or tag index failure must never block the restore.

## 5. Detailed Behavior & Edge Cases

### 5.1 Snapshot only on content change

`_snapshot_revision` is called only when `title` or `body_html` change. If an admin updates only `category_id`, `tags`, `expires_at`, or any other metadata field, no snapshot is written and `rev_counter` is unchanged. This matches the acceptance criterion and avoids cluttering the revision history with administrative metadata changes.

### 5.2 First update on a new article

A newly created article has no `rev_counter` attribute. The `ADD rev_counter :one` expression initializes it to `1` on first call (DynamoDB treats a missing numeric attribute as `0` for `ADD`). No special initialization is needed at article creation time.

### 5.3 Concurrent updates (race condition)

If two admin requests call `update_article` for the same article simultaneously:
- Both issue `ADD rev_counter :one` — DynamoDB's atomic `ADD` guarantees they receive distinct `rev_number` values (e.g., `1` and `2`).
- Both write `REVISION#` rows with distinct `revision_id` and distinct `created_at` (at second resolution, the SKs may collide on the timestamp portion, but the `#{revision_id}` UUID suffix guarantees SK uniqueness).
- The final META row reflects the last writer's content; both snapshots are preserved. The history is complete.

### 5.4 Restore of a revision that references a deleted article body

If an article's body has been updated multiple times and the oldest revision is restored, the body content is restored verbatim from `body_html_snapshot`. No sanitization is re-applied at restore time (the content was sanitized at original save time). If the platform's HTML sanitization rules change between the original edit and the restore, the restored content may contain patterns that would be rejected on a fresh create — this is acceptable for admin-only operations where the admin bears responsibility for the content.

### 5.5 Restore while article is published

`restore_revision` does not change `status`. If the article is currently `published`, it remains published after restore with the new (older) body. The search index is rebuilt for the restored title (Step 4 in the service method), so search results will reflect the restored title immediately. Tag index is also rebuilt if tags changed (Step 5).

### 5.6 Restore records pre-restore state as a new revision

Before overwriting the META row, `restore_revision` calls `_snapshot_revision` on the current state with `edit_note="[pre-restore] {edit_note}"`. This means a restore operation produces two changes to the revision list: one new row snapshotting the pre-restore state, and then the META row is updated to match the target revision. The history is therefore fully reversible: a restore can itself be reversed by restoring the pre-restore snapshot.

### 5.7 Revision body size limit

`body_html_snapshot` stores the full article body. DynamoDB item size limit is 400 KB. For articles with very large bodies, a snapshot row may approach or exceed this limit. The service should enforce a maximum body size at `update_article` time (e.g., 250 KB plain bytes) — this constraint is already appropriate for a KB article body and keeps snapshot rows comfortably within DDB limits. If a snapshot would exceed 390 KB (leaving headroom for other fields), log a warning and truncate `body_html_snapshot` to `[TRUNCATED — body exceeded snapshot size limit]`. This truncation is a last resort; in practice KB article bodies should be kept well under 100 KB.

### 5.8 Pagination of revision list

`list_revisions` uses `ScanIndexForward=False` with a DDB `Limit` parameter and cursor-based pagination via `encode_cursor` / `decode_cursor`. Because `Limit` reduces the number of items DynamoDB scans (not just returns) on a `query` with no `FilterExpression`, the page size matches exactly the `Limit` value — no client-side looping is needed for the list endpoint. Pagination is needed only when an article has more than `limit` revisions.

### 5.9 Maximum revision count

No hard maximum is enforced at the application layer. DynamoDB has no practical limit on the number of items per partition. Articles that are updated very frequently will accumulate many revision rows. A future maintenance task could prune revisions older than N days or beyond the Nth most recent, but that is out of scope for this ticket. The list endpoint's `limit=50` cap keeps individual page fetches bounded.

### 5.10 `edit_note` on `update_article`

The `edit_note` parameter on `update_article` is optional and defaults to `""`. If supplied, it is stored on the revision row as `edit_note`. If not supplied, `edit_note` is an empty string. The admin UI (KB-012) may surface this as a "save with comment" text field.

### 5.11 Flag-off behavior

With `S.knowledge_base_enabled = False`:
- `GET /kb/articles/{id}/revisions` → 404.
- `GET /kb/articles/{id}/revisions/{rev_id}` → 404.
- `POST /kb/articles/{id}/revisions/{rev_id}/restore` → 404.
- `KbArticleService.update_article` raises 404 at entry before any snapshot attempt.
- `_snapshot_revision` is never reached.
- No `REVISION#` rows are written.

## 6. Feature Flag & Config

### 6.1 Primary flag

```
KNOWLEDGE_BASE_ENABLED=0    (default — no revision rows written, all endpoints 404)
KNOWLEDGE_BASE_ENABLED=1    (revision history fully active)
```

Follows the bool-env pattern at `app/core/settings.py:1875`:

```python
knowledge_base_enabled: bool = os.environ.get("KNOWLEDGE_BASE_ENABLED", "0") not in ("0", "false", "False")
```

KB-010 introduces no new settings keys beyond those already added by KB-001.

### 6.2 `rev_counter` initialization

No settings key. `rev_counter` is initialized lazily on the first `ADD` call (DynamoDB treats missing numeric attributes as `0` for `ADD`). No migration or pre-seeding is required.

### 6.3 Snapshot body truncation threshold

Module-level constant in `app/services/kb_articles.py`:

```python
_KB_REVISION_BODY_MAX_BYTES: int = 390_000  # 390 KB; leave headroom to 400 KB DDB item limit
```

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Single code path (SECOPS-007)

There is no `if S.dev_mode:` branch anywhere in KB-010. All DDB operations (`update_item` for `rev_counter`, `put_item` for the snapshot row, `query` for list/get, `update_item` for restore) run against the same `T.kb_articles` handle. In dev this resolves to DynamoDB Local (`DDB_ENDPOINT_URL=http://localhost:8001`); in prod it resolves to real DynamoDB. The boto3 client is chosen by `app/core/aws.py` based on `DDB_ENDPOINT_URL` — no code divergence.

### 7.2 Idempotency

- `_snapshot_revision` increments `rev_counter` atomically and writes a snapshot row. It is not idempotent in isolation: if called twice for the same state, it writes two snapshot rows. This is intentional — the snapshot is of a transient pre-update state that will be overwritten; duplicates are harmless but wasteful. The caller (`update_article`) gates the call on a content-change check, so duplicate snapshot writes cannot occur from normal usage.
- `restore_revision` is idempotent with respect to the final META state: calling it twice with the same `revision_id` produces the same final META row (same title, body, tags). Each call also produces a new pre-restore snapshot row, so the revision history grows with each call. This is acceptable behavior.
- `list_revisions` and `get_revision` are read-only and trivially idempotent.

### 7.3 Authentication and authorization

- All three endpoints require `Depends(require_admin_or_root)` (`app/auth/policy.py:67`). Unauthenticated requests receive 401; authenticated non-admin users receive 403.
- Revision content (`title_snapshot`, `body_html_snapshot`) is admin-only readable. There is no public endpoint that exposes revision data — historical body content may contain drafts or withdrawn information that should not be publicly visible.
- `edited_by` stores the `user_sub` of the admin who performed the update. This is adequate for accountability; the display name can be resolved from `T.users` by the admin UI (KB-012) at render time.

### 7.4 Input validation

- `edit_note` is capped at 500 characters in the Pydantic model (`max_length=500`). Longer notes are rejected with 422.
- `limit` is bounded at 50 via `Query(ge=1, le=50)`.
- `revision_id` is a plain string path parameter; no regex enforcement. The service raises 404 if no matching revision exists.

### 7.5 Sensitive data in snapshots

`body_html_snapshot` stores the full article body at snapshot time, including any embedded data the admin had entered (e.g., support phone numbers, internal pricing notes in draft articles). Access is restricted to `admin` and `root` roles; no public exposure. Audit events for snapshot creation include only `article_id` and `rev_number` — not the body content — so the audit log does not contain duplicated large payloads.

## 8. Backward Compatibility & Migration

### 8.1 Flag-off default

With `KNOWLEDGE_BASE_ENABLED=0` (the default), no revision rows are written and `rev_counter` is never set on any article META row. Enabling the flag later causes `rev_counter` to start from `0` for all articles (lazily initialized on first `ADD`) and revision history to accumulate from that point forward. Pre-flag-on updates are not retroactively snapshotted — this is expected and documented.

### 8.2 Articles created before KB-010 ships

Articles created while the flag was on (KB-001 through KB-009 already deployed) but before KB-010 ships have no `rev_counter` field. The `ADD rev_counter :one` expression initializes it on first use. No migration is needed.

### 8.3 Articles with no revisions

`GET /kb/articles/{id}/revisions` returns `{"items": [], "cursor": null, "article_id": "..."}` for articles that have never been updated (or were only updated with metadata-only changes). The empty list is a valid response; no 404 is raised.

### 8.4 No changes to existing tables or GSIs

KB-010 adds only new rows to `crm_kb_articles` (under the `REVISION#` PK prefix and the `rev_counter` attribute on META rows). All existing queries (`ByStatus`, `ByCategory`, `ByAuthor`, `ByTag` GSIs; direct `ARTICLE#` / `META` gets; `RATING#` rows; `ATTACHMENT#` rows; etc.) are completely unaffected. The `REVISION#` PK prefix is distinct from all other PK prefixes used in the table.

### 8.5 `update_article` signature extension

The `edit_note` parameter is added to the existing `update_article` signature as `edit_note: str = ""`. All existing callers that do not supply `edit_note` continue to work without modification (the parameter is keyword-only with a default). The function signature change is backward-compatible at the Python call site and at the API level (the router adds `edit_note` as an optional field in the request body via `KbArticleUpdateReq`).

## 10. Open Questions / Assumptions

1. **Maximum revision retention** — should old revisions be pruned after N days or after exceeding M total revisions per article? No pruning is implemented in this ticket. A follow-on ticket (KB-013 or a maintenance task) can add a DDB TTL on revision rows or a cleanup worker. For now, revision rows accumulate indefinitely.

2. **Partial update signature** — the design assumes `update_article` accepts `title` and `body_html` as keyword-only optional parameters. If the CAS-015 implementation uses a different signature (e.g., a Pydantic model as the only argument), the snapshot logic needs to extract `title` and `body_html` from the model and compare against the stored values. The principle is unchanged; only the extraction pattern differs.

3. **Concurrent restore operations** — if two admins call `restore_revision` for the same article at the same time, both will read the current META, snapshot it, and then both will call `update_item` to overwrite META. The last writer wins on the META row. Both pre-restore snapshots are preserved in the revision history. This is acceptable for an admin-only low-frequency operation; a conditional expression (`ConditionExpression=Attr("rev_counter").eq(expected)`) could make the restore atomic if needed in a future iteration.

4. **`tags_snapshot` type** — DynamoDB StringSets (`SS`) and plain Lists behave differently. If `tags` on the META row is stored as a DDB StringSet (`SS`) by KB-007, `get_item` returns a Python `set`, not a `list`. The snapshot row stores `tags_snapshot` as a DDB List (`L`) for deterministic ordering and serialization. The `restore_revision` method converts back to the appropriate type when calling `_write_kb_tag_index`. This conversion is assumed; the exact type depends on KB-007's implementation.

5. **`edit_note` in `KbArticleUpdateReq`** — the existing `KbArticleUpdateReq` Pydantic model (defined by CAS-015) may not have an `edit_note` field. KB-010 adds it as `edit_note: str = ""`. If the CAS-015 model is immutable (e.g., generated from an OpenAPI spec), a new `KbArticleUpdateV2Req` model can be defined without breaking existing clients.
