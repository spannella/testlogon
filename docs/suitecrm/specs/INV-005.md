# INV-005 — Named tax groups and jurisdiction tax rate registry

**Ticket type:** Feature
**Priority:** P1
**Estimate:** 3d
**Feature flag:** `CRM_TAX_RATES_ENABLED` (default `"0"`, off)

---

## 1. Summary & Goal

Build a configurable, admin-managed tax rate registry so the platform can
define named tax groups (e.g., "CA Sales Tax 9.5%", "VAT EU Standard 20%")
each carrying a jurisdiction label, a rate expressed in basis points, and an
active/inactive toggle. Tax groups are then referenced at line-item level by
INV-006 (per-line tax assignment). This ticket delivers the data model, service
layer, and admin CRUD REST endpoints; it does NOT yet wire tax groups into
invoice creation (that is INV-006's scope).

The goal is to close the SuiteCRM AOS gap item "configurable tax-group registry
with jurisdiction labels." The existing platform carries only a single, flat
`invoices_tax_bps` setting at `app/core/settings.py:2569` — a global integer
applied uniformly to every invoice. There is no per-jurisdiction differentiation,
no named group concept, and no admin UI to manage rates without an env-var
restart.

With `CRM_TAX_RATES_ENABLED=0` (the default) the platform is byte-for-byte
unchanged: all new routes return 404, no DDB calls are made, and no new
background work runs. Existing invoice generation continues to use
`invoices_tax_bps` exactly as before.

## 3. Data Model

### New DynamoDB table: `crm_tax_rates`

**Environment variable**: `CRM_TAX_RATES_TABLE_NAME` (default `"crm_tax_rates"`)

**Primary key**: `PK = TAXRATE#{tax_rate_id}`, `SK = META`

`tax_rate_id` is `"tr_" + uuid4().hex[:12]` (generated at creation time;
same pattern as other platform IDs).

**Item attributes**:

| Attribute     | Type    | Notes                                                          |
|---------------|---------|----------------------------------------------------------------|
| `pk`          | S       | `TAXRATE#{tax_rate_id}`                                        |
| `sk`          | S       | `META`                                                         |
| `tax_rate_id` | S       | Same value as in `pk`; denormalized for convenience            |
| `name`        | S       | Human-readable name, e.g. `"CA Sales Tax"`                     |
| `rate_bps`    | N       | Basis points, integer in `[0, 10000]`; 950 = 9.5%             |
| `jurisdiction`| S       | ISO 3166-1 alpha-2 (`"US"`, `"DE"`) or subdivision (`"US-CA"`) |
| `description` | S       | Optional free text; default `""`                               |
| `is_active`   | BOOL    | Default `True`; `False` = deactivated, excluded from lookups   |
| `created_by`  | S       | `user_sub` of the admin who created the record                 |
| `created_at`  | N       | Unix epoch seconds (`now_ts()`)                                |
| `updated_at`  | N       | Unix epoch seconds; set on every `update_tax_rate` call        |
| `GSI1PK`      | S       | `"TAXRATES#ACTIVE"` when `is_active=True`; omitted when `False`|
| `GSI1SK`      | S       | `name` — enables alphabetical listing of active rates          |
| `GSI2PK`      | S       | `"JURISDICTION#{jurisdiction}"` always                         |
| `GSI2SK`      | S       | `name` — enables listing all rates for a jurisdiction by name  |

**GSI definitions**:

- **GSI1** (`taxrates-active-index`): `GSI1PK` (S) / `GSI1SK` (S) — returns
  all active tax rates, alphabetically by name. Sparse: inactive items omit
  `GSI1PK` so they never appear in the active query.
- **GSI2** (`taxrates-jurisdiction-index`): `GSI2PK` (S) / `GSI2SK` (S) —
  returns all tax rates (active and inactive) for a jurisdiction, alphabetically
  by name.

**`attr_types` note**: Both GSI sort keys (`GSI1SK` and `GSI2SK`) are string
(`name`), so **no numeric `attr_types` declaration is needed** for either GSI.
The `created_at` and `updated_at` attributes are numeric but are not used as GSI
sort keys, so they require no `attr_types` entry. This table introduces no new
`attr_types` entries.

**`scripts/local-ddb-init.py` addition** (added to `_table_defs()` after the
`invoices` TableDef at line 2278):

**Active/inactive sparse GSI pattern**: When `update_tax_rate` deactivates a
rate (`is_active=False`) it removes `GSI1PK` from the item via a
`REMOVE GSI1PK` `UpdateExpression`. This keeps the item in the table but
removes it from the active-rates GSI, matching the `SCHEDULES#DISABLED`
pattern used in audit export schedules (CLAUDE.md, "Scheduled audit export
reports" section).

## 4. API / Service Design

### 4.1 Service layer: `app/services/crm_tax_rates.py`

All public functions begin with a gate:

```python
def _require_enabled() -> None:
    if not S.crm_tax_rates_enabled:
        raise ValueError("crm_tax_rates is not enabled")
```

**`create_tax_rate`**:

```python
def create_tax_rate(
    *,
    name: str,
    rate_bps: int,
    jurisdiction: str,
    description: str = "",
    created_by: str = "",
) -> dict:
```

Validates `0 <= rate_bps <= 10000`; raises `ValueError` with code
`invalid_rate_bps` otherwise. Normalizes `jurisdiction` to uppercase. Generates
`tax_rate_id = "tr_" + uuid4().hex[:12]`, sets `created_at = updated_at = now_ts()`,
`is_active = True`. Writes item with `GSI1PK = "TAXRATES#ACTIVE"`,
`GSI1SK = name`, `GSI2PK = f"JURISDICTION#{jurisdiction}"`, `GSI2SK = name`.
Emits `audit_event("tax_rate.created", created_by, tax_rate_id=tax_rate_id, name=name, rate_bps=rate_bps, jurisdiction=jurisdiction)`.
Returns the serialized dict.

**`update_tax_rate`**:

```python
def update_tax_rate(
    tax_rate_id: str,
    *,
    name: str | None = None,
    rate_bps: int | None = None,
    jurisdiction: str | None = None,
    description: str | None = None,
    is_active: bool | None = None,
    updated_by: str = "",
) -> dict:
```

Reads the existing item; raises `KeyError` (404) if not found. Validates
`rate_bps` when provided. Builds `UpdateExpression` from non-None fields.
When `is_active` transitions to `False`, adds `REMOVE GSI1PK` to the
expression so the item falls out of the active-rates GSI. When `is_active`
transitions to `True`, adds `SET GSI1PK = :active_pk` (value
`"TAXRATES#ACTIVE"`). When `name` or `jurisdiction` changes, updates
`GSI1SK` and `GSI2PK`/`GSI2SK` accordingly. Sets `updated_at = now_ts()`.
Emits `audit_event("tax_rate.updated", updated_by, tax_rate_id=tax_rate_id, **changed_fields)`.
Returns serialized dict of the updated item.

**`get_tax_rate`**:

```python
def get_tax_rate(tax_rate_id: str) -> dict | None:
```

`T.crm_tax_rates.get_item(Key={"pk": f"TAXRATE#{tax_rate_id}", "sk": "META"})`.
Returns `_serialize(item)` or `None`. Does NOT enforce `is_active`; the caller
(INV-006) checks `is_active` to decide whether to apply the rate.

**`list_tax_rates`**:

```python
def list_tax_rates(
    jurisdiction: str | None = None,
    active_only: bool = True,
    limit: int = 200,
    cursor: str | None = None,
) -> dict:
```

When `jurisdiction` is provided: queries `GSI2` with
`KeyConditionExpression = "GSI2PK = :pk"` (value `f"JURISDICTION#{jurisdiction.upper()}"`);
`active_only` is then applied as a `FilterExpression` (`is_active = :true`) on
that result set, since GSI2 contains both active and inactive items. When
`jurisdiction` is `None` and `active_only=True`: queries `GSI1` with
`GSI1PK = "TAXRATES#ACTIVE"` (returns only active items by construction).
When `jurisdiction` is `None` and `active_only=False`: performs a table scan
with a `FilterExpression` ensuring `begins_with(pk, "TAXRATE#")` to exclude
`COUNTER` rows. Pagination via `encode_cursor` / `decode_cursor` (same pattern
as `app/services/invoices.py:437–438`). Returns
`{"tax_rates": [TaxRateOut dict, ...], "next_cursor": str | None}`.

**`get_tax_rate_by_name`**:

```python
def get_tax_rate_by_name(name: str) -> dict | None:
```

Queries `GSI1` with `KeyConditionExpression = "GSI1PK = :pk AND GSI1SK = :name"`.
Returns the first active match, or `None`. Used by INV-006 to resolve a
human-readable name to `rate_bps` without knowing the `tax_rate_id`.

**`_serialize`** (internal):

```python
def _serialize(item: dict) -> dict:

        "tax_rate_id": str(item.get("tax_rate_id") or ""),
        "name": str(item.get("name") or ""),

        "jurisdiction": str(item.get("jurisdiction") or ""),
        "description": str(item.get("description") or ""),
        "is_active": bool(item.get("is_active", True)),
        "created_by": str(item.get("created_by") or ""),
        "created_at": int(item.get("created_at") or 0),
        "updated_at": int(item.get("updated_at") or 0),
    }
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Rate basis points validation

`rate_bps` must be in `[0, 10000]` (0% to 100%). A value of 0 is valid: it
models a zero-rate jurisdiction (explicitly tax-exempt). Values above 10000
are rejected by Pydantic at the request boundary (HTTP 422) so the service
layer never sees them. The service-layer `create_tax_rate` also validates
independently to guard against direct service calls (raises `ValueError`).

### 5.2 Deactivation vs. deletion

There is no DELETE endpoint. Admins deactivate rates by `PATCH`-ing
`is_active=false`. This is a soft-deactivation: the item remains in DDB
(preserving audit history and existing `tax_rate_id` references in
line-item data from INV-006), but it is removed from the active-rates GSI1
via a `REMOVE GSI1PK` expression. Reactivating (`is_active=true`) restores
the `GSI1PK` attribute.

If a future deactivation is applied to a rate already referenced by an
existing invoice line item (INV-006 data), that invoice record retains the
snapshot `tax_rate_bps` value that was baked in at creation time — the rate
registry is not re-queried for historical invoices.

### 5.3 Name collisions

Names are not enforced as unique at the DDB layer. Two tax rates can share
the same `name` in different jurisdictions. `get_tax_rate_by_name` returns
the first alphabetical match (GSI1 scan by name). INV-006 prefers referencing
by `tax_rate_id` (exact) over `name` (first-match); the by-name path is
provided as a convenience for admin tooling.

### 5.4 Jurisdiction format

`jurisdiction` is stored as-provided but normalized to uppercase by the
service. Accepted formats: ISO 3166-1 alpha-2 country codes (`"US"`, `"DE"`,
`"GB"`) or ISO 3166-2 subdivision codes (`"US-CA"`, `"US-NY"`, `"DE-BY"`).
The service does not validate against an authoritative code list (out of scope);
the admin UI (INV-011) should provide a dropdown or validated text field.

### 5.5 GSI filter on inactive rates within jurisdiction query

When `jurisdiction` is provided with `active_only=True`, the query targets
GSI2 (which holds all jurisdiction items), and a `FilterExpression` of
`is_active = :true` is added. Note per the DDB gotcha in CLAUDE.md:
"DDB FilterExpression doesn't reduce page size" — the query loops via
`LastEvaluatedKey` until `limit` active items are accumulated or there are
no more pages. This avoids silent truncation on jurisdictions with many
inactive rates.

### 5.6 Concurrent deactivation and active-list cache

There is no in-memory cache on tax rate lookups (unlike `billing_config.py`).
The registry is read at invoice-creation time by INV-006 via a direct DDB
`get_item` call; the additional per-request latency (~1ms for DDB Local,
~2–5ms for DDB in prod) is acceptable for an infrequent admin operation.
If the rate lookup in INV-006 returns an inactive rate, it is silently ignored
and falls back to `rate_bps=0` for that line (not an error). This prevents a
deactivated rate from hard-blocking invoice creation.

### 5.7 Flag guard in service functions

Every public service function checks `S.crm_tax_rates_enabled` at entry and
raises `ValueError("crm_tax_rates is not enabled")` when `False`. The router
`_require_enabled()` guard converts this to HTTP 404 before the service is
called. This double-guard (router + service) prevents accidental service-layer
calls from internal callers (e.g., INV-006) when the flag is off.

### 5.8 `audit_event` fields

Both mutation functions emit audit events to `T.alerts` via
`app/services/alerts.audit_event` (line 644). Event names:
- `"tax_rate.created"` — on successful `create_tax_rate`.
- `"tax_rate.updated"` — on successful `update_tax_rate`.
- `"tax_rate.deactivated"` — emitted as a second distinct event when
  `update_tax_rate` sets `is_active=False` (in addition to `.updated`), to
  make deactivation events searchable in the audit log.

Fields always included: `tax_rate_id`, `name`, `jurisdiction`, `rate_bps`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

There is no `if S.dev_mode` branch anywhere in `crm_tax_rates.py`. DDB calls
use the same `T.crm_tax_rates` table handle in both environments; in dev,
boto3 is redirected to DynamoDB Local on port 8001 via `DDB_ENDPOINT_URL`
(set in `.env.local`), and real DynamoDB is used in prod. No mock path,
no conditional logic. This satisfies SECOPS-007.

### Idempotency

`create_tax_rate` does not carry an idempotency key. Admins who double-click
the "Create" button will create two records with distinct `tax_rate_id`s but
the same `name`. The admin UI (INV-011) should disable the submit button after
the first click and display the returned `tax_rate_id` to prevent confusion.
`update_tax_rate` is idempotent: applying the same patch twice yields the same
item (only `updated_at` changes).

### Security

- All endpoints require `ADMIN` or `ROOT` role (`app/auth/policy.py:67–68`).
  `USER`-role callers receive HTTP 403 with `code=role_required`.
- CSRF protection: the `require_admin_or_root` dependency resolves via
  `get_authenticated_user` → `require_ui_session`; cookie-auth non-GET
  requests enforce the `x-csrf-token` header matching the session's stored
  `csrf_token` and the `ui_csrf` cookie.
- `name` and `description` fields are stored as raw strings. They appear only
  in admin-facing API responses and the invoice PDF; they are PDF-escaped via
  `_pdf_escape` in `app/services/invoices.py:99–100` before rendering.
  No HTML rendering path exists, so XSS via these fields is not a concern.
- `rate_bps` is constrained to `[0, 10000]`; values are always `int` in the
  service and Pydantic enforces bounds, preventing arithmetic overflow or
  negative-tax exploits.
- Audit trail: every mutation emits `audit_event` to `T.alerts` with the
  acting admin's `user_sub`, timestamp, and changed fields.

## 8. Backward Compatibility & Migration

### Zero impact with flag off

With `CRM_TAX_RATES_ENABLED=0` (the default), no new table is accessed, no
existing model is changed, no existing endpoint is modified, and no existing
service call is altered. The `crm_tax_rates` table in DDB can be created by
`scripts/local-ddb-init.py` and will sit empty without any effect on the
platform.

### DDB init change requires `just restart`

Adding the `crm_tax_rates` `TableDef` to `scripts/local-ddb-init.py` is a
one-time schema change. In dev: `just restart` recreates all tables including
the new one. The new table is empty after restart; no data migration is needed.
In prod: `local-ddb-init.py` runs during deployment; `CreateTable` is
idempotent (existing tables are not touched).

### `app/models.py` additions are additive

New models (`TaxRateCreateIn`, `TaxRatePatchIn`, `TaxRateOut`,
`TaxRateListOut`) are appended to `app/models.py`. No existing model is
modified by this ticket. INV-006 will later add `tax_rate_id: str = ""`
and `tax_rate_bps: int = 0` to `InvoiceLineItemOut` and `tax_breakdown` to
`InvoiceOut`; those changes belong to INV-006, not here.

### `app/core/tables.py` addition is safe

Adding `crm_tax_rates: Any` to the `Tables` dataclass and the corresponding
initializer call follows the existing `_safe_table` pattern: if the DDB table
does not exist (e.g., during a cold `uvicorn` start before `local-ddb-init.py`
runs), `_safe_table` returns a non-None resource handle that will fail on first
use. The handle is never called when the flag is off, so there is no startup
failure in the flag-off state.

### No ledger, no billing change

This ticket does not touch `billing_shared.new_ledger_entry`, the invoice
`VALID_TYPES` set, or any payment path. Tax registry operations are
administrative metadata management only.

## 10. Open Questions / Assumptions

1. **Name uniqueness enforcement**: The current design does not enforce unique names
   within a jurisdiction at the DDB level. Should there be a conditional-put guard?
   The existing `crm_currencies` pattern (INV-002) does enforce uniqueness on the ISO
   code PK; tax rates have no natural unique key other than their generated ID. Assumption:
   no uniqueness enforcement; admin UI should display a warning when a name already exists.

2. **Soft-delete vs. hard-delete**: The design uses soft-deactivation only. If an admin
   needs to permanently delete a rate (e.g., created by mistake), they currently cannot.
   Assumption: the admin UI can filter to `active_only=false` to see all rates; a future
   hard-delete endpoint can be added if needed without changing the core data model.

3. **Maximum rates per jurisdiction**: DDB query performance degrades when a partition
   returns thousands of items. Assumption: the number of named tax rates is small (< 100
   total across all jurisdictions); no secondary pagination optimization is needed beyond
   the standard cursor pattern.

4. **INV-011 admin UI**: The `ManualInvoiceForm.tsx` in INV-011 includes a tax-rate
   `<select>` populated by `GET /ui/admin/tax-rates`. It is assumed that `CRM_TAX_RATES_ENABLED`
   must be on for the tax-rate select to populate; when the flag is off, the select shows
   empty and the form falls back to the platform `invoices_tax_bps`.

5. **`crm_currencies` and `crm_tax_rates` flag independence**: The two feature flags
   (`CRM_CURRENCIES_ENABLED` and `CRM_TAX_RATES_ENABLED`) are independent. Either can be
   enabled without the other. INV-006 (per-line tax) has its own flag
   (`AOS_PER_LINE_TAX_ENABLED`) and only calls `crm_tax_rates.get_tax_rate` when
   `CRM_TAX_RATES_ENABLED` is on.
