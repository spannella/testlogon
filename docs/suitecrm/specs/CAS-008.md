# CAS-008 — SLA management — tiers, breach detection, and escalation alerts

**Type:** Feature | **Priority:** P1 | **Estimate:** 3d  
**Parent area:** CRM Cases, Customer Support & Customer Portal  
**Source ticket:** `docs/suitecrm/CRM_CASES_PORTAL_TICKETS.md` §CAS-008

---

## 1. Summary & Goal

Add first-class SLA (Service Level Agreement) enforcement to the existing ticket store. Each ticket receives a `sla_due_at` Unix timestamp computed from its priority tier at creation time. A background checker runs every 5 minutes (configurable), detects breached tickets, marks them `sla_breached`, sends in-app and email alerts to the assignee and watcher list (from CAS-007), and optionally auto-escalates via the CAS-009 hook. Admins can read and hot-update per-priority SLA config through two new endpoints. Everything is additive and off by default (`CRM_CASES_SLA_ENABLED=0`); the platform is byte-for-byte unchanged when the flag is off.

## 2. Context & Current State

### Ticket store — what already exists

`app/services/tickets.py` defines `TicketStore` (`app/services/tickets.py:244`) with a single DynamoDB table (`T.tickets`, wired at `app/core/tables.py:140`). The table (`scripts/local-ddb-init.py:695–711`) has **ten GSIs** (owner, status, assignee, space, space-status, space-assignee, member-spaces, jira-workspace, jira-issue, jira-sync-state) including `status-updated_at-index` (keys `gsi2pk`/`gsi2sk`) used by `get_admin_summary` to scan all statuses (`app/services/tickets.py:694–707`). Note: `get_admin_summary` scans **all** statuses in `_TICKET_STATUSES` (13 values), not only open tickets. `_query_all_headers_by_index` (`app/services/tickets.py:677`) drives full-partition iteration with `LastEvaluatedKey` loop — this is the pattern the SLA checker must reuse.

The META row written by `create_ticket` (`app/services/tickets.py:440–476`) does not yet carry `priority`, `sla_due_at`, `sla_breached`, or `breach_alerted_at`. CAS-003 adds `priority` as a prerequisite; CAS-008 depends on that field being present.

All writes to the META row go through `_conditional_update_meta` (`app/services/tickets.py:723`) using optimistic version locking. Any new attributes appended by CAS-008 must be added to the SET block inside that method.

### KYC SLA — the canonical pattern to mirror

`app/services/kyc_case_assignment.py` implements a near-identical pattern:

- `SLA_TIERS` tuple + `_DEFAULT_SLA` dict (`app/services/kyc_case_assignment.py:40–53`) define default target hours, warning %, and escalation %.
- `_sla_sk(tier)` (`app/services/kyc_case_assignment.py:68`) produces the DynamoDB SK `SLA#{tier}` for config rows stored under `pk="CONFIG"` in `T.kyc_cases` (attribute name is `pk` in the KYC table; the CRM SLA table uses `config_key` instead — see §3.2).
- `get_sla_config()` (`app/services/kyc_case_assignment.py:658`) queries `KeyConditionExpression="pk = :pk AND begins_with(sk, :s)"` and merges stored overrides with `_DEFAULT_SLA` defaults.
- `update_sla_config()` (`app/services/kyc_case_assignment.py:680`) is a `put_item` under `pk="CONFIG"`, `sk="SLA#{tier}"`.
- `check_sla_compliance()` (`app/services/kyc_case_assignment.py:707`) iterates active cases, compares `sla_due_at` vs `now_ts()`, and returns breached rows sorted by `hours_overdue` descending.
- `run_sla_escalation_sweep()` (`app/services/kyc_case_assignment.py:807`) is the loop body: calls `check_sla_compliance()` then `escalate_case()` per breach.
- `kyc_sla_checker_loop()` (`app/services/kyc_case_assignment.py:831`) is an `async` loop with `asyncio.sleep`.
- `start_kyc_sla_checker_task()` (`app/services/kyc_case_assignment.py:844`) is registered in `app/main.py:663` via `app.add_event_handler("startup", ...)`. Note: `start_kyc_sla_checker_task` calls `kyc_sla_checker_loop()` **without passing** a configurable interval — the loop uses its default `interval_seconds=300`. CAS-008 deviates from this by passing `S.crm_cases_sla_check_interval_seconds`.

CAS-008 follows this structure, adapted for ticket priorities instead of KYC risk tiers. The key schema difference is the `config_key` vs `pk` partition key attribute name in the SLA config table (see §3.2).

### Alert and email primitives

`app/services/alerts.py` provides:

## 3. Data Model

### 3.1 New attributes on existing `tickets` META row

No new table or GSI is needed for the core SLA stamps. The three new attributes are plain non-key fields appended to the existing META item (`pk=TICKET#{id}`, `sk=META`):

| Attribute | Type | Notes |
|---|---|---|
| `sla_due_at` | Number (Unix s) | Set on creation when flag is on and `priority` is known. `None` / absent when flag is off. |
| `sla_breached` | Boolean | Set to `true` by `check_breaches` when `now_ts() > sla_due_at`. Never reset to `false` (append-only audit semantic). |
| `breach_alerted_at` | Number (Unix s) | Timestamp of the first breach alert dispatch. Used for idempotency — `check_breaches` skips tickets where this is already set. |

Because these are non-key attributes the existing `tickets` table definition in `scripts/local-ddb-init.py:696–711` requires no change. The `attr_types` clause on that `TableDef` is not affected.

### 3.2 SLA config table — reuse `crm_cases_sla_config`

CAS-001 (`docs/suitecrm/specs/CAS-001.md` §3.5) defines `crm_cases_sla_config` with partition key `config_key` (not `pk`) and sort key `sk`. The constant PK value is still `"CONFIG"` but the DynamoDB attribute name is `config_key`. CAS-008 writes and reads from this table. One row per priority level:

| Field | Type | Notes |
|---|---|---|
| `config_key` | S | Always `"CONFIG"` — **attribute name is `config_key`, not `pk`** (CAS-001 §3.5) |
| `sk` | S | `"SLA#{priority}"` — e.g. `SLA#urgent` |
| `entity_type` | S | `"ticket_sla_config"` |
| `priority` | S | `urgent \| high \| medium \| low` |
| `target_response_hours` | N | Hours from `created_at` until first-response SLA fires — **field is `target_response_hours`, not `first_response_hours`** (CAS-001 §3.5) |
| `resolution_hours` | N | Hours from `created_at` until resolution SLA fires |
| `warning_pct` | N | % of `target_response_hours` at which a warning alert fires |
| `escalation_pct` | N | % threshold at which escalation fires (always 100 for now — CAS-001 §3.5) |
| `updated_at` | N | Unix timestamp |
| `updated_by_sub` | S | `user_sub` of the admin who last changed the config — **field is `updated_by_sub`, not `updated_by`** (CAS-001 §3.5) |

No GSI is required on this table — config is fetched with a single `query(KeyConditionExpression="config_key = :ck")` call (CAS-001 §3.5 note: the table uses `config_key` as PK, so the `begins_with` variant from the KYC pattern is not needed; a plain `pk = :pk` query suffices). This differs from the KYC pattern at `kyc_case_assignment.get_sla_config()` (`app/services/kyc_case_assignment.py:658–678`) which queries `T.kyc_cases` with `pk = :pk AND begins_with(sk, :s)` using attribute name `pk`.

## 4. API / Service Design

### 4.1 New service file: `app/services/ticket_sla.py`

```python
_TICKET_PRIORITIES: tuple[str, ...] = ("urgent", "high", "medium", "low")

# Default values align with CAS-001 §3.5 seeded defaults.
# NOTE: the DynamoDB field name is target_response_hours (not first_response_hours).
# warning_pct defaults from CAS-001 §3.5: 75 for urgent/high/medium, 80 for low.
# resolution_hours is CAS-008's own additional field (CAS-001 does not define it).
# The specific resolution_hours values below are product-level choices for CAS-008.
_DEFAULT_SLA_CONFIG: dict[str, dict[str, int]] = {
    "urgent": {"target_response_hours": 4,  "resolution_hours": 16,  "warning_pct": 75, "escalation_pct": 100},
    "high":   {"target_response_hours": 8,  "resolution_hours": 32,  "warning_pct": 75, "escalation_pct": 100},
    "medium": {"target_response_hours": 24, "resolution_hours": 96,  "warning_pct": 75, "escalation_pct": 100},
    "low":    {"target_response_hours": 72, "resolution_hours": 288, "warning_pct": 80, "escalation_pct": 100},
}

def _sla_sk(priority: str) -> str:
    return f"SLA#{priority}"

@dataclass
class TicketSlaService:
    _sla_table: Any = field(default_factory=lambda: T.crm_cases_sla_config)
    _tickets_store: Any = field(default_factory=lambda: STORE)   # TicketStore singleton

    def get_sla_config(self) -> dict[str, dict[str, int]]:
        """Read all priority rows from crm_cases_sla_config; merge with defaults.
        Query uses config_key = :ck (not pk) per CAS-001 table schema.
        """

    def update_sla_config(
        self, *, priority: str, target_response_hours: int,
        resolution_hours: int, warning_pct: int, actor_sub: str,
    ) -> dict[str, Any]:
        """put_item under config_key='CONFIG', sk='SLA#{priority}'.
        Stores target_response_hours (not first_response_hours) and
        updated_by_sub (not updated_by) per CAS-001 §3.5 item schema.
        """

    def compute_sla_due_at(self, ticket: dict[str, Any]) -> int | None:
        """Return created_at + target_response_hours * 3600, or None if priority unknown."""

    def check_breaches(self) -> dict[str, Any]:
        """
        Scan open/in_progress/waiting_on_user tickets via status GSI.
        For each: if sla_due_at < now_ts() and breach_alerted_at is not set:
          - mark sla_breached=True and breach_alerted_at=now on the META row
          - call _dispatch_breach_alerts(ticket)
        Returns {"checked": N, "breached": M, "alerted": K}.
        """

    def _dispatch_breach_alerts(self, ticket: dict[str, Any]) -> None:
        """
        Fire write_alert + send_alert_email for the assignee and all watchers.
        Best-effort: swallows all exceptions — a notification failure must not
        block the breach-marking write.
        """

# Module-level singleton
SLA_SERVICE = TicketSlaService()

async def ticket_sla_checker_loop(interval_seconds: int = 300) -> None:
    while True:
        try:
            SLA_SERVICE.check_breaches()
        except Exception:
            logger.exception("ticket_sla.checker_error")
        await asyncio.sleep(max(5, int(interval_seconds)))

def start_ticket_sla_checker_task() -> None:
    import asyncio
    if S.crm_cases_sla_enabled:
        asyncio.ensure_future(
            ticket_sla_checker_loop(S.crm_cases_sla_check_interval_seconds)
        )
```

## 5. Detailed Behavior & Edge Cases

### 5.1 `compute_sla_due_at` — priority-to-deadline mapping

1. Read `priority` from `ticket["priority"]` (set by CAS-003; `None` when CAS-003 is off or caller did not supply it).
2. If `priority` is `None` or not in `_TICKET_PRIORITIES`, return `None` — no SLA deadline is set.
3. Call `self.get_sla_config()` to read live config (merges stored overrides with `_DEFAULT_SLA_CONFIG`).
4. Return `ticket["created_at"] + config[priority]["target_response_hours"] * 3600`.
5. `sla_due_at` is stored once at creation and is **immutable** — it is not recalculated if priority is later changed by an admin. Priority update (CAS-003 `PATCH /tickets/{id}/priority`) must call `compute_sla_due_at` and re-persist `sla_due_at` via a direct `update_item` (not through `_conditional_update_meta` which requires version bump).

### 5.2 `check_breaches` — idempotent breach detection

```
for status in ("open", "in_progress", "waiting_on_user"):
    for header in _query_all_headers_by_index(status_index, gsi2pk=STATUS#{status}):
        if header does not have sla_due_at → skip
        if header.sla_breached is True → skip (already processed)
        if header.breach_alerted_at is set → skip (already alerted)
        if now_ts() < int(header.sla_due_at) → skip (not yet due)
        # --- breach confirmed ---
        mark_breached(ticket_id, now)      # unconditional update_item
        _dispatch_breach_alerts(ticket)    # best-effort, try/except
```

The `mark_breached` write is a plain `update_item` (not version-locked):
```python
T.tickets.update_item(
    Key=_meta_item_key(ticket_id),
    UpdateExpression="SET sla_breached = :t, breach_alerted_at = :now",
    ConditionExpression="attribute_not_exists(breach_alerted_at)",
    ExpressionAttributeValues={":t": True, ":now": now_ts()},
)
```
The `ConditionExpression="attribute_not_exists(breach_alerted_at)"` provides the idempotency guard — if two checker instances run concurrently (unlikely but defensive), only one write succeeds; the other gets `ConditionalCheckFailedException` which is swallowed.

### 5.3 `_dispatch_breach_alerts` — recipients and message

Recipients = deduplicated list of:
- `ticket["assigned_admin_sub"]` (may be `None` — skip if so)
- `ticket["assigned_to_sub"]` (may duplicate `assigned_admin_sub` — deduplicate)
- `ticket.get("watchers", [])` (added by CAS-007; empty list if CAS-007 not yet shipped)

Per recipient:
1. `write_alert(recipient, event="ticket_sla_breach", outcome="warning", title="SLA breached", details={ticket_id, priority, sla_due_at, hours_overdue})` (`alerts.py:356`)
2. Resolve the recipient's email via `app.services.profile.get_profile_identity(recipient)["email"]` (wrapped in try/except — missing profile → skip email for that recipient).
3. Call `send_alert_email([email], subject, body_text)` with the rendered template from `render_ticket_email_template`.

All three calls are inside a single `try/except Exception: logger.warning(...)` per recipient — a broken email config must not abort the breach sweep.

### 5.4 CAS-009 auto-escalation hook

When `S.crm_cases_sla_enabled` is true and the breach is confirmed in `check_breaches`, after `_dispatch_breach_alerts`, call:
```python
if int(ticket.get("escalation_level") or 0) == 0:
    from app.services.tickets import STORE as _STORE
    try:
        _STORE.escalate_ticket(
            ticket_id=ticket_id,
            actor_sub="system_sla_escalation",
            reason=f"SLA breach auto-escalation ({hours_overdue:.1f}h overdue)",
        )
    except Exception:
        logger.warning("ticket_sla.auto_escalate_failed ticket_id=%s", ticket_id)
```
This hook is inert if CAS-009 has not shipped yet (`escalate_ticket` will not exist) — the `ImportError`/`AttributeError` is caught by the outer `except`. When CAS-009 does ship, the hook activates without any CAS-008 code change (lazy import at call time).

### 5.5 Warning alerts (pre-breach)

When `now_ts() >= ticket["created_at"] + target_response_hours * warning_pct/100 * 3600` and `sla_breached` is not yet set, the checker fires a `ticket_sla_warning` in-app alert. This does NOT set `breach_alerted_at` (that field is reserved for the final breach). Warning alerts use the same `write_alert` call with `event="ticket_sla_warning"` and `outcome="info"`. Since warnings may fire on every checker pass until breach, use a separate `warning_alerted_at` field (stored on the META row, non-key) guarded by the same `attribute_not_exists` conditional write pattern.

### 5.6 Closed and terminal tickets

The status GSI query uses `STATUS#open`, `STATUS#in_progress`, `STATUS#waiting_on_user` — tickets in `done`, `deployed`, `qa_approved`, etc. are never returned by the breach scan. SLA breach on a closed ticket is a non-event.

### 5.7 Tickets without `sla_due_at` (flag was off at creation)

If `sla_due_at` is absent on a ticket that pre-dates the flag being enabled, `check_breaches` skips it (the `if header does not have sla_due_at → skip` guard). No retroactive backfill.

### 5.8 Concurrent checker runs

The startup task uses `asyncio.ensure_future` (same as `start_kyc_sla_checker_task`, `kyc_case_assignment.py:849`). With `--workers 1` in dev (CLAUDE.md gotcha), only one task runs. In prod (multiple uvicorn workers), concurrent breaches are handled idempotently by the `attribute_not_exists(breach_alerted_at)` conditional write.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

- `send_alert_email` (`app/services/alerts.py:459`) already handles parity internally: it branches on `if S.dev_mode:` to write to `S.dev_email_log`; in prod it calls SES. Call sites in `ticket_sla.py` need no additional branching — the function is the single dev/prod seam.
- `write_alert` (`alerts.py:356`) writes to `T.alerts` (DynamoDB Local in dev, real DynamoDB in prod) — same code path.
- `T.crm_cases_sla_config` points to DynamoDB Local in dev and real DynamoDB in prod via the same `S.crm_cases_sla_config_table` table name. No mock/real branching.
- The background loop uses `asyncio.sleep` — no `time.sleep` blocking — consistent across dev and prod.

### Idempotency

- `check_breaches` skips any ticket with `breach_alerted_at` set (field-level check before the write).
- The `update_item` breach-marking write uses `ConditionExpression="attribute_not_exists(breach_alerted_at)"` — concurrent runs produce `ConditionalCheckFailedException` (swallowed, not re-raised) so alerts are dispatched at most once per ticket.
- `update_sla_config` is idempotent: repeated `put_item` with the same values is a no-op from the caller's perspective.

### Security

- `GET /tickets/admin/sla-config` requires `_is_admin` (`Role.ADMIN | Role.ROOT`), consistent with all admin read endpoints in `tickets.py` (e.g. `tickets.py:593`).
- `PATCH /tickets/admin/sla-config/{priority}` requires `_is_root` — SLA config is a platform-level policy change that should require the highest privilege, matching how KYC SLA config updates are gated (root-level) in `app/routers/kyc_cases.py`.
- `breach_alerted_at` is never surfaced to non-admin callers (it is an internal operational field) but it is included in `TicketOut` for admin audit visibility.
- Alert dispatch resolves recipient emails via `get_profile_identity` server-side — email addresses are never passed in from client requests.
- No new secrets, no KMS usage, no S3 access.

## 8. Backward Compatibility & Migration

### Flag-off invariant

With `CRM_CASES_SLA_ENABLED=0` (default):
- `TicketOut` fields `sla_due_at`, `sla_breached`, `breach_alerted_at` are `None` / `False` (Pydantic defaults) — no client breakage.
- `create_ticket` skips the `update_item` SLA stamp entirely — existing tests pass unchanged.
- `_conditional_update_meta` only extends the `SET` clause when callers supply the new key-value pairs — passing nothing for SLA attrs is identical to today.
- The startup hook is a no-op (returns immediately).
- The two new endpoints return 404.

### Pre-existing tickets (retroactive enablement)

When an operator enables the flag on a live system, tickets created before the flag was on will have no `sla_due_at`. The breach checker skips them permanently (no retroactive SLA assignment). This is intentional — setting a retroactive deadline on tickets that are already past their hypothetical due date would produce a wave of spurious breach alerts.

Operators who want to apply SLA to pre-existing open tickets must call `PATCH /tickets/{id}/priority` (CAS-003) which, per §5.1, triggers a `sla_due_at` recalculation.

### Database migration

None required. DynamoDB's schemaless nature allows the new attributes to appear on new items without a table migration. No `just restart` is required; the new attributes simply absent on old items.

## 10. Open Questions / Assumptions

1. **Resolution vs first-response deadline**: The spec stores only `target_response_hours` as the basis for `sla_due_at`. SuiteCRM tracks both first-response and resolution SLA separately. If the product wants separate clocks, two fields (`sla_first_response_at`, `sla_resolution_at`) should be introduced. This spec implements one `sla_due_at` mapped to `target_response_hours` as the primary breach trigger; `resolution_hours` is stored in config but a second breach field can be added in a follow-up without a schema change.

2. **SLA clock paused during `waiting_on_user`**: SuiteCRM pauses the SLA clock when a case is waiting on the customer. The current design does not implement pause/resume; `sla_due_at` is a fixed timestamp computed at creation. Pause/resume requires storing a `sla_paused_seconds` accumulator, which is a separate follow-up.

3. **Priority changed after creation**: §5.1 states that changing priority (CAS-003) recalculates `sla_due_at`. This is the expected behavior but requires CAS-003's `update_priority` method to call `TicketSlaService().compute_sla_due_at` and persist the new value. This coordination is noted as a CAS-003 dependency detail; CAS-008 does not own that change.

4. **Watcher email resolution**: `_dispatch_breach_alerts` calls `get_profile_identity` per recipient. If a watcher is a portal guest (CAS-011, no internal `user_sub`), the email is resolved differently. For now, the implementation skips recipients where `get_profile_identity` returns no email; portal guest notification is deferred to CAS-011.

5. **Multi-worker deploy**: With `uvicorn --workers N` (prod), each worker runs its own `asyncio.ensure_future(ticket_sla_checker_loop())`. The `attribute_not_exists(breach_alerted_at)` conditional write prevents duplicate alerts but generates redundant DDB reads. A distributed lock (e.g. DDB conditional heartbeat) is out of scope for this ticket.
