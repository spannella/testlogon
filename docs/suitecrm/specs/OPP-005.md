# OPP-005 — Sales quota management and forecast worksheets

**Ticket type:** Feature
**Priority:** P1
**Estimate:** 3 days
**Source ticket file:** `docs/suitecrm/CRM_OPPORTUNITIES_TICKETS.md` (lines 338–447)
**Master gate:** `S.sales_pipeline_enabled` (`SALES_PIPELINE_ENABLED`, default `false`)
**Depends on:** OPP-001 (table, models, flag), OPP-002 (opportunity CRUD for `closed_cents` aggregation)

---

## 1. Summary & Goal

OPP-005 adds two tightly coupled forecast capabilities that together give sales managers and reps a complete picture of quota attainment for any calendar period:

1. **Admin-managed sales quotas** — admins set a target revenue amount (in cents) per rep per period (monthly, quarterly, or annual). Quotas are stored in the dedicated `sales_quotas` table introduced by OPP-001 and are never editable by the rep whose quota it is.

2. **Per-rep forecast worksheets** — each sales rep fills in a self-assessed forecast for a period: a committed amount, a best-case amount, and a pipeline amount. The worksheet also surfaces a read-only `closed_cents` field auto-computed by aggregating `closed_won` opportunity records whose `close_date` falls within the period, and a `quota_cents` field joined from the quota table. Together these yield `attainment_pct`, the ratio of actual closed revenue to target.

Both surfaces are additive and fully gated behind `S.sales_pipeline_enabled`. With the flag off, every existing platform byte is unchanged: the two tables already exist (created by OPP-001), but no new routes are mounted and no reads or writes occur.

The intended audience for quotas is sales managers with `Role.ADMIN` or `Role.ROOT`. The forecast worksheet is self-service for any authenticated user who is active in the sales pipeline.

### 2.8 Period key format

`period_key` is a caller-supplied string such as `"2026-Q2"` (quarterly), `"2026-06"` (monthly), or `"2026"` (annual). OPP-005 defines a pure-Python `_parse_period_key(period_key)` helper (no external dependency) that returns `(ts_from: int, ts_to: int)` Unix-second boundaries used for the `close_date` range scan. The spec for parsing is:
- Monthly: `"YYYY-MM"` — first second of that month to last second of that month (handles month length correctly via `calendar.monthrange`).
- Quarterly: `"YYYY-Q{1-4}"` — maps to the three-month range (Q1=Jan–Mar, Q2=Apr–Jun, Q3=Jul–Sep, Q4=Oct–Dec).
- Annual: `"YYYY"` — first second of January 1 to last second of December 31.
- Invalid format raises `HTTPException(400, detail={"code": "invalid_period_key"})`.

The helper uses only the Python standard library (`calendar`, `datetime`) — no third-party dependency.

## 3. Data Model

### 3.1 `T.sales_quotas` — quota rows

Table: `sales_quotas` (introduced OPP-001, simple two-key, no GSIs)

| `pk` | `sk` | Description |
|------|------|-------------|
| `USER#{user_sub}` | `QUOTA#{period_key}` | Per-rep per-period quota |
| `TEAM#{team_id}` | `QUOTA#{period_key}` | Team quota row (reserved for future; never written by OPP-005) |

Attributes on the `USER#…` quota row:

| Attribute | Type | Notes |
|-----------|------|-------|
| `pk` | S | `USER#{user_sub}` |
| `sk` | S | `QUOTA#{period_key}` e.g. `QUOTA#2026-Q2` |
| `user_sub` | S | Denormalized for response projection |
| `period_type` | S | `monthly` \| `quarterly` \| `annual` |
| `period_key` | S | e.g. `2026-Q2` |
| `target_amount_cents` | N | Quota target in integer cents, `>= 0` |
| `set_by_sub` | S | `user_sub` of the admin who last wrote the row |
| `created_at` | N | Unix integer seconds (`now_ts()`) |
| `updated_at` | N | Unix integer seconds (`now_ts()`), same value as `created_at` on first write |

`set_quota` uses `put_item` (upsert semantics) — the entire quota row is replaced on each write. There is no versioning or history; only the current quota for a period is stored. Idempotent: calling `set_quota` twice with the same values produces the same stored row.

**No new `TableDef` or GSI changes are required.** The simple base-table query `pk=USER#{user_sub}` with `sk` begins-with `QUOTA#` is sufficient for `list_quotas_for_user`. A `get_quota(user_sub, period_key)` is a single `get_item` lookup.

### 3.2 `T.sales_opportunities` — forecast worksheet rows

The forecast worksheet is stored in the **same** `sales_opportunities` table as opportunities (single-table pattern), using a distinct `sk` prefix.

| `pk` | `sk` | Description |
|------|------|-------------|
| `USER#{user_sub}` | `FORECAST#{period_key}` | Forecast worksheet row |

Attributes:

| Attribute | Type | Notes |
|-----------|------|-------|
| `pk` | S | `USER#{user_sub}` |
| `sk` | S | `FORECAST#{period_key}` e.g. `FORECAST#2026-Q2` |
| `user_sub` | S | Denormalized |
| `period_key` | S | |
| `committed_cents` | N | Rep's committed forecast, integer cents `>= 0` |
| `best_case_cents` | N | Rep's best-case forecast, integer cents `>= 0` |
| `pipeline_cents` | N | Rep's total pipeline forecast, integer cents `>= 0` |
| `notes` | S | Free-text notes, optional, max 4096 chars |
| `created_at` | N | Unix integer seconds, set only on first write |
| `updated_at` | N | Unix integer seconds, always updated on upsert |

`closed_cents`, `quota_cents`, and `attainment_pct` are **computed at read time** and never stored. This avoids stale data: every `get_forecast` call re-aggregates closed opportunities from `GSI_BY_USER_CLOSE` and re-fetches the quota from `T.sales_quotas`. The worksheet row itself is only the three rep-entered fields plus notes and timestamps.

**No new GSIs** are needed on `T.sales_opportunities`. Forecast rows are keyed `FORECAST#{period_key}` and fetched via `get_item(pk, sk)`. The `GSI_BY_USER_CLOSE` index (already declared in OPP-001 with `attr_types={"close_date": "N"}`) is the aggregation path for `closed_cents`.

The existing `attr_types={"close_date": "N", "created_at": "N"}` on `sales_opportunities` ensures the `GSI_BY_USER_CLOSE` range scan on `close_date` (integer) works without `ValidationException`.

## 4. API / Service Design

### 4.1 Service functions (`app/services/opportunities.py`)

All functions call `_require_flag()` as their first statement. All DDB writes go through `T.sales_quotas` or `T.sales_opportunities`, both `_FloatSafeTable` proxies (`app/core/tables.py:29–66`).

```python
# ── Period helper ──────────────────────────────────────────────────────────

def _parse_period_key(period_key: str) -> Tuple[int, int]:
    """Return (ts_from, ts_to) Unix-second boundaries for the period.

    Raises HTTPException(400, code=invalid_period_key) on unrecognized format.
    Uses only stdlib: calendar, datetime, timezone.
    """

# ── Quota functions ────────────────────────────────────────────────────────

def set_quota(admin_sub: str, data: SalesQuotaIn) -> SalesQuotaOut:
    """Upsert a quota row. admin_sub must have ADMIN or ROOT role (enforced by
    the router dependency; service trusts the caller). Emits audit_event
    "quota.set". Returns the persisted SalesQuotaOut."""

def get_quota(user_sub: str, period_key: str) -> Optional[SalesQuotaOut]:
    """Fetch a single quota row or return None. No 404; absence = no quota."""

def list_quotas_for_user(
    user_sub: str,
    cursor: Optional[str] = None,
    limit: int = 50,
) -> Tuple[List[SalesQuotaOut], Optional[str]]:
    """Query pk=USER#{user_sub}, sk begins_with QUOTA#. Paginate with cursor."""

# ── Forecast worksheet functions ───────────────────────────────────────────

def _compute_closed_cents(user_sub: str, ts_from: int, ts_to: int) -> int:
    """Aggregate amount_cents of closed_won opportunities via GSI_BY_USER_CLOSE
    where close_date BETWEEN ts_from AND ts_to. Loops LastEvaluatedKey to handle
    FilterExpression sparsity. Returns integer cents sum."""

def upsert_forecast(user_sub: str, data: ForecastWorksheetIn) -> ForecastWorksheetOut:
    """Upsert a forecast worksheet row. Reads closed_cents from opportunities
    (via _compute_closed_cents), reads quota_cents from T.sales_quotas, computes
    attainment_pct, and returns the enriched ForecastWorksheetOut. Emits
    audit_event "forecast.upserted"."""

def get_forecast(user_sub: str, period_key: str) -> ForecastWorksheetOut:
    """Fetch the worksheet row and enrich with live closed_cents + quota_cents +
    attainment_pct. Returns 404 (code=forecast_not_found) if no worksheet row
    exists for the period."""
```

#### `set_quota` implementation notes

Uses `T.sales_quotas.put_item(Item={...})`. There is no conditional — full replacement is intentional (last-writer-wins per period). Sets `created_at` on first write by issuing a `get_item` check first (read-before-write) only when the caller needs the original `created_at` to be stable; simpler: always write both `created_at=now_ts()` and `updated_at=now_ts()` on upsert. The distinction matters only if the admin updates an existing quota; in that case `created_at` is reset. Given the simple operational model (quota is set at the start of a period and rarely changed), this trade-off is acceptable. A future refinement can use `update_item` with `if_not_exists(created_at)` to preserve the original timestamp.

Emits: `audit_event("quota.set", admin_sub, None, user_sub=data.user_sub, period_key=data.period_key, target_amount_cents=data.target_amount_cents)`.

#### `_compute_closed_cents` implementation notes

Queries `GSI_BY_USER_CLOSE` with:
```python
KeyConditionExpression = Key("owner_sub").eq(user_sub) & Key("close_date").between(ts_from, ts_to)
FilterExpression = Attr("stage").eq("closed_won") & Attr("sk").begins_with("OPP#")
```
The `sk.begins_with("OPP#")` guard excludes any non-opportunity rows (e.g. `FORECAST#` rows) that might share `owner_sub` in a GSI projection. Per the CLAUDE.md `FilterExpression` gotcha, the implementation loops via `LastEvaluatedKey` until exhausted, accumulating the integer `amount_cents` sum. Returns `0` when no `closed_won` rows exist.

#### `upsert_forecast` implementation notes

1. Validate `period_key` via `_parse_period_key` (raises 400 on bad format).
2. Call `_compute_closed_cents(user_sub, ts_from, ts_to)`.
3. Call `get_quota(user_sub, period_key)` — returns `None` → `quota_cents = 0`.
4. Compute `attainment_pct = (closed_cents * 100 // quota_cents) if quota_cents > 0 else 0`.
5. Issue `T.sales_opportunities.put_item(Item={...})` — full replacement. `created_at` is preserved by issuing a `get_item` first to carry the existing `created_at` forward if the row already exists; on first write, `created_at = updated_at = now_ts()`.
6. Emit `audit_event("forecast.upserted", user_sub, None, period_key=data.period_key)`.
7. Return `ForecastWorksheetOut` with computed fields populated.

## 5. Detailed Behavior & Edge Cases

### 5.1 Period key parsing

`_parse_period_key` must handle exactly three formats and reject all others:

| Input | `ts_from` | `ts_to` |
|-------|-----------|---------|
| `"2026-06"` | `datetime(2026,6,1,0,0,0,tzinfo=UTC)` as Unix int | `datetime(2026,6,30,23,59,59,tzinfo=UTC)` as Unix int |
| `"2026-Q2"` | `datetime(2026,4,1,0,0,0,tzinfo=UTC)` as Unix int | `datetime(2026,6,30,23,59,59,tzinfo=UTC)` as Unix int |
| `"2026"` | `datetime(2026,1,1,0,0,0,tzinfo=UTC)` as Unix int | `datetime(2026,12,31,23,59,59,tzinfo=UTC)` as Unix int |
| Anything else | raises `HTTPException(400, detail={"code": "invalid_period_key"})` | — |

The regex guards are: monthly = `r"^\d{4}-(0[1-9]|1[0-2])$"`, quarterly = `r"^\d{4}-Q[1-4]$"`, annual = `r"^\d{4}$"`. End-of-month day is derived via `calendar.monthrange(year, month)[1]` so February is handled correctly in both leap and non-leap years.

### 5.2 `closed_cents` aggregation loop

Because `FilterExpression` does not reduce DDB page size (CLAUDE.md gotcha), a rep with hundreds of opportunities could require multiple round trips. The loop is bounded by DynamoDB's own 1MB page limit. No additional application-level page cap is applied — the aggregation reads all matching pages. In production, a rep's closed opportunities for a single quarter is expected to be in the dozens, making multi-page scans rare in practice. Nonetheless the loop is required for correctness. Pseudocode:

```python
closed_cents = 0
lek = None
while True:
    kwargs = {
        "IndexName": "GSI_BY_USER_CLOSE",
        "KeyConditionExpression": Key("owner_sub").eq(user_sub)
            & Key("close_date").between(ts_from, ts_to),
        "FilterExpression": Attr("stage").eq("closed_won") & Attr("sk").begins_with("OPP#"),
    }
    if lek:
        kwargs["ExclusiveStartKey"] = lek
    resp = T.sales_opportunities.query(**kwargs)
    for item in resp.get("Items", []):
        closed_cents += int(item.get("amount_cents", 0))
    lek = resp.get("LastEvaluatedKey")
    if not lek:
        break
return closed_cents
```

### 5.3 Quota absence

`get_quota` returns `None` when no quota row exists. `upsert_forecast` and `get_forecast` treat absence as `quota_cents = 0` and `attainment_pct = 0`. This is a deliberate UX choice: a rep can create a forecast worksheet before an admin has set their quota; the worksheet shows `quota_cents: 0` rather than blocking.

### 5.4 `attainment_pct` overflow guard

Integer division `closed_cents * 100 // quota_cents` can exceed 100 if the rep over-attains. The field is typed `int` with no upper cap — values above 100 (e.g. 127 for 127% attainment) are valid and meaningful. The frontend is responsible for display formatting.

### 5.5 Quota ownership isolation

`POST /ui/admin/sales/quotas` body contains `user_sub` (the rep being assigned the quota). The admin may set a quota for any `user_sub`. There is no check that the target `user_sub` is a real user in DynamoDB — orphaned quota rows (quota for a deleted user) are benign; they just never appear in a forecast. A future ticket can add user-existence validation.

`GET /ui/admin/sales/quotas/{user_sub}` is admin-only; a rep cannot fetch another rep's quota list. A rep can only see their own `quota_cents` through the forecast worksheet enrichment, not as a standalone endpoint.

### 5.6 Forecast worksheet ownership isolation

`PUT /ui/sales/forecast/{period_key}` always uses `user.sub` from the authenticated session as `user_sub`. A rep cannot write or read another rep's worksheet. There is no admin override endpoint for writing a rep's worksheet (admins have the quota endpoint; worksheet is rep self-service only).

### 5.7 `period_key` in path vs. body

`PUT /ui/sales/forecast/{period_key}` takes `period_key` from the URL path parameter. The `ForecastWorksheetIn` body model does not include `period_key` — it is supplied solely by the path parameter. This avoids ambiguity when path and body disagree. The router handler sets `data.period_key = period_key` on the service call explicitly (or the service function signature takes `period_key` as a separate argument).

### 5.8 Concurrent worksheet upserts

Two concurrent `PUT` requests for the same `(user_sub, period_key)` can produce a race on `created_at`. The implementation uses `get_item` + `put_item` (not a conditional `update_item`). In the worst case both writes succeed and the later one wins. Given that worksheets are entered manually by a single rep, concurrent writes are not an operational concern. Optimistic concurrency (`ConditionExpression` on `updated_at`) is not applied here (unlike `update_opportunity` in OPP-002) because the risk is negligible and the simpler `put_item` keeps the code consistent with `set_quota`.

### 5.9 `SalesQuotaIn.period_key` / `ForecastWorksheetIn.period_key` validation mismatch

`SalesQuotaIn` accepts any `period_key` string (validated for format in the service, not the Pydantic model). The `@validator("period_type")` on `SalesQuotaIn` checks that `period_type` matches the three choices but does NOT cross-validate that the `period_key` string is consistent with `period_type` (e.g. a caller could POST `period_type=monthly` with `period_key=2026-Q1`). The service does not enforce this cross-field consistency — `period_type` is stored as supplied and used only for display; `period_key` alone drives the date computation. A future validator could enforce consistency, but it is not required for correctness.

**Default-off guarantee:** With `SALES_PIPELINE_ENABLED` absent or set to any value not in `{"1","true","yes","on"}`, `S.sales_pipeline_enabled` is `False`. The `_require_flag()` guard at the top of every handler raises `HTTP 503 {"code": "sales_pipeline_disabled"}` before touching any DDB table. Existing routes, tables, and behaviors are completely unaffected.

**Local dev activation:**

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No `if S.dev_mode` branches

All service functions in this ticket use the same DDB-backed code path in both environments. There is no mock/stub branch. In dev, `T.sales_quotas` and `T.sales_opportunities` are backed by DynamoDB Local on port 8001; in prod they are backed by real DynamoDB. The `_FloatSafeTable` proxy handles `float→Decimal` coercion identically in both environments. This is SECOPS-007 parity.

### 7.2 No money-out operations

OPP-005 stores and reads integer cent values but does **not** initiate any payment, refund, or ledger entry. `quota_cents` is purely informational — it is never debited from a wallet, never sent to Stripe/PayPal/CCBill. There is no need to call `refund_payment` or `settle_or_reverse_ledger`. The existing billing primitives (`app/services/billing_shared.py`) are not touched.

### 7.3 Idempotency

`set_quota` is idempotent by design: posting the same `(user_sub, period_key, target_amount_cents)` twice produces identical stored state (full `put_item` replacement). `upsert_forecast` is idempotent for the same reason.

The audit events emitted are not idempotent (each call emits a new row to `T.alerts`), but that is the established platform convention — `alerts.audit_event` is a fire-and-forget log, not a deduplicating ledger.

### 7.4 Authorization boundaries

- Only `Role.ADMIN` or `Role.ROOT` can write or read quota rows via the admin endpoints. `require_admin_or_root` (`app/auth/policy.py:67`) is the sole enforcer; the service layer trusts the router dependency.
- Any authenticated user can write and read their own forecast worksheet. There is no cross-user worksheet access.
- No endpoint exposes quota amounts to the rep directly (only `quota_cents` is surfaced in the rep's own forecast worksheet).

### 7.5 Input validation and injection

`period_key` is validated by regex in `_parse_period_key` before being used in any DDB key expression. It is never interpolated into raw strings that could form an injection vector — DynamoDB key expressions use parameterized boto3 `Key()` / `Attr()` condition objects.

`notes` is stored as-is (no HTML escaping); the frontend is responsible for sanitization on display, consistent with the existing `description` field on `OpportunityCreateIn`.

### 9.1 Hermetic pytest unit tests (`tests/test_opp_005_quota_forecast.py`)

All tests are offline and hermetic following the patterns in `tests/test_gap_0262_0264_kyc_template_endpoints.py` and `tests/test_gap_0265_0266_kyc_risk_scoring.py`:

- **No `@mock_aws` / no moto bootstrapping at module level.** Instead, bind a fresh moto in-memory DynamoDB table to `T.sales_quotas` and `T.sales_opportunities` via `object.__setattr__(T, "sales_quotas", ...)` and `object.__setattr__(T, "sales_opportunities", ...)` in a `setup_module` fixture, and restore originals in `teardown_module`.

Test cases:

**Period parsing (`_parse_period_key`):**
- Monthly: `"2026-06"` → correct `(ts_from, ts_to)` spanning June 2026 (30 days).
- Quarterly: `"2026-Q2"` → April 1 – June 30 2026.
- Annual: `"2026"` → January 1 – December 31 2026.
- Leap year February: `"2024-02"` → 29 days.
- Invalid: `"2026-13"`, `"2026-Q5"`, `"foo"`, `""`, `"2026-06-01"` → all raise 400 `invalid_period_key`.

- `list_quotas_for_user` with three quota rows across different periods → returns all three; cursor pagination works for limit=1.
- `list_quotas_for_user` for a user with no quotas → returns empty list.

**Forecast worksheet:**
- `upsert_forecast` with zero closed_won opps → `closed_cents=0`, `attainment_pct=0`.

- `upsert_forecast` when no quota → `quota_cents=0`, `attainment_pct=0`.
- `get_forecast` for an existing worksheet → returns enriched `ForecastWorksheetOut`.
- `get_forecast` for a non-existent period → raises 404 `forecast_not_found`.
- `upsert_forecast` called twice → second call updates `updated_at`; `created_at` preserved from first write.
- Over-attainment: `closed_cents=150_00`, `quota_cents=100_00` → `attainment_pct=150`.

**Flag enforcement:**
- With `S.sales_pipeline_enabled=False`, all four handler functions raise 503 `sales_pipeline_disabled`.

**Authorization (router-level tests):**
- `POST /ui/admin/sales/quotas` with `Role.USER` → `require_admin_or_root` raises 403.

- `GET /ui/admin/sales/quotas/{user_sub}` with `Role.USER` → 403.

## 10. Open Questions / Assumptions

1. **Cross-rep forecast read for admins.** OPP-005 does not add an admin endpoint to read a specific rep's forecast worksheet. Admin cross-rep visibility is deferred to OPP-006 (the pipeline funnel dashboard). Assumption: OPP-006 will add `GET /ui/admin/sales/forecast/{user_sub}/{period_key}` using the same `get_forecast` service function with `user_sub` taken from the path rather than from `user.sub`.

2. **Team quotas.** The `TEAM#{team_id}` / `QUOTA#{period_key}` row shape is reserved in the table layout but no service function writes or reads it in this ticket. Team quota aggregation (summing individual quotas, setting a team-level target) is deferred. Assumption: a future ticket (OPP-007 or similar) adds team quota management without any schema migration.

3. **`period_type` cross-validation.** The spec does not enforce that `period_type=quarterly` is accompanied by a `period_key` matching `YYYY-Q{1-4}`. Assumption: this is acceptable for V1; the `period_key` alone drives the date computation and `period_type` is purely informational metadata for display filtering.

4. **`created_at` preservation on upsert.** The simple `put_item` approach resets `created_at` on every write. If audit trail fidelity of "when was this forecast first submitted" is required, a `update_item` with `if_not_exists(created_at, :now)` should be used instead. Assumption: first-submission timestamp is not a hard requirement for V1; the simpler `put_item` is acceptable.

5. **Quota visibility to reps.** Reps currently see their quota only via `quota_cents` in their own forecast worksheet. There is no `GET /ui/sales/my-quota/{period_key}` self-service endpoint. Assumption: the forecast worksheet is the correct UX entry point and a dedicated quota-read endpoint is not required for V1.

6. **`closed_cents` reflects close_date, not stage-change date.** If a rep closes a deal in Q1 but the `close_date` field was set to Q2, that deal is counted in Q2's `closed_cents`. Assumption: `close_date` is the canonical attainment date for quota purposes, consistent with SuiteCRM's convention.
