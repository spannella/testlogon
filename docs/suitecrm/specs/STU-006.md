# STU-006 — CRM field-change audit trail

## 1. Summary & Goal

Implement a per-record, per-field change audit trail for CRM entities that captures old and new values on every mutation. Each write to a CRM record produces a `field_changes` row in a dedicated DynamoDB table keyed by entity type and record ID, queryable by either the record itself or the actor who made the change. The trail is surfaced through two admin read endpoints appended to the existing ENTERPRISE-004 audit export router, and the trail events are wired into the ENTERPRISE-004 bulk export pipeline through a new `CrmAuditTrailAdapter`.

The entire feature is additive and default-off, controlled by `S.crm_studio_enabled` (`CRM_STUDIO_ENABLED`, default `"0"`). With the flag off the new router endpoints return 404 and the write-path hook is a no-op, leaving the platform byte-for-byte identical to its current state.

## 2. Context & Current State

**Existing audit infrastructure (ENTERPRISE-004)**

The project already has a unified audit export system. `app/services/audit_export.py` defines `UnifiedAuditEvent` (lines 10-27), a dataclass with fields `event_id`, `event_type`, `event_action`, `timestamp`, `timestamp_unix`, `actor_user_id`, `actor_role`, `target_resource_type`, `target_resource_id`, `outcome`, `metadata`, `source_table`, and `impersonation_context`. `app/services/audit_adapters.py` defines `BaseAuditAdapter` (line 19) with the abstract `query()` method and the `ADAPTERS` registry (line 441) currently containing five categories: `auth`, `moderation`, `broadcast`, `admin`, `billing`. `VALID_CATEGORIES` (line 449) is derived from the registry keys and is what `POST /ui/admin/audit-exports` validates against. New adapters are registered by adding an entry to `ADAPTERS`.

**Audit event helper**

`app/services/alerts.audit_event` (line 644) is the standard fire-and-forget hook: `audit_event(event: str, user_sub: str, request=None, **fields)`. It writes to `T.alerts`. This is used for access/role/billing events but is not the right storage target for CRM field changes — field changes are high-cardinality, record-scoped events that need to be queryable by `(entity_type, record_id)` without scanning the full alerts table. STU-006 uses a dedicated `crm_audit_trail` table instead.

**Ticket service — write paths that will be hooked**

`app/services/tickets.py` exposes the `TicketStore` class (line 244) backed by `T.tickets`. The mutating methods that change user-visible CRM fields are:

- `create_ticket` (implicitly called from the router; not hooked — creation is recorded as a dedicated `ticket_opened` activity, not a field change).
- `assign_ticket` (line 807) — changes `assigned_admin_sub`, `assigned_to_sub`, `assigned_by`, `assigned_at`, `status` (potentially). After calling `_apply_header_update_once` it writes a `ticket_assigned` activity row.
- `update_status` (line 913) — changes `status`. After calling `_apply_header_update_once` it writes a `ticket_status_changed` activity row.
- `add_message` (line 851) — changes `status` implicitly via `_next_status_for_message` (line 235). The status side-effect qualifies as a field change.

No PATCH/PUT endpoint exists in `app/routers/tickets.py` (confirmed: the router has `POST`, `GET`, `DELETE` variants and `POST /{id}/assign`, `POST /{id}/messages`, `POST /{id}/status` — no general field update path). Future subject/description edits would be added as part of downstream CRM tickets and would similarly call `_emit_field_changes`.

**`crm_audit_trail` DynamoDB table**

Introduced by STU-001 (scaffolding ticket). The table is declared in `scripts/local-ddb-init.py` under `TableDef` (line 29 pattern) with:

```
PK: pk (S)  — e.g. ENTITY#ticket#tkt_abc123
SK: sk (S)  — e.g. CHANGE#0001748563210#evt_hex16
GSI by-actor: PK=actor_sub (S), SK=changed_at (N)
attr_types={"changed_at": "N"}
```

The `attr_types={"changed_at": "N"}` declaration is mandatory; omitting it causes a DynamoDB `ValidationException` at GSI query time because the sort key would be stored as String and queried as Number (CLAUDE.md numeric GSI gotcha).

The table handle `T.crm_audit_trail` is added to `app/core/tables.py` in STU-001 following the `_safe_table(S.crm_audit_trail_table_name)` pattern (tables.py line 65-66).

**Cursor pagination**

`app/core/cursor.py` exposes `encode_cursor(last_evaluated_key)` (line 94) and `decode_cursor(cursor)` (line 103). All pagination in this spec uses these functions, matching the pattern used by every other paginated service.

**Settings / flag pattern**

`app/core/settings.py` uses the pattern `field: bool = os.environ.get("VAR", "0") not in ("0", "false", "False")` (observed at lines 51, 56, 61 for feature flags). The `crm_studio_enabled` and `crm_audit_trail_table_name` settings are added by STU-001.

**Auth dependencies**

`app/auth/policy.py` provides `require_root` (line 63) and `require_admin_or_root` (line 67), both returning `AuthenticatedUser`. These are the standard Depends-compatible callables used across admin routers (e.g., `app/routers/refund_requests.py:118`, `app/routers/job_dashboard.py:37`).

**No existing field-change trail**

There is no current mechanism that records old/new field values on ticket or contact mutations. The `ticket_activity` rows written by `assign_ticket` and `update_status` record the *new* value (e.g., `"status": requested_status` at `tickets.py:973`) but not the previous value, making them insufficient for a full audit trail. The `alerts` table (used by `audit_event`) stores structured events but is not keyed for efficient per-record lookup.

## 3. Data Model

### 3.1 `crm_audit_trail` table (introduced by STU-001)

All rows share the schema below. One row is written per mutation call (a single `record_field_changes` invocation captures all fields changed in that operation as a list).

| Attribute | Type | Notes |
|-----------|------|-------|
| `pk` | S | `ENTITY#{entity_type}#{record_id}` e.g. `ENTITY#ticket#tkt_abc` |
| `sk` | S | `CHANGE#{ts:010d}#{event_id}` e.g. `CHANGE#1748563210#evt_4f8a3c2b1d6e9f0a` |
| `event_id` | S | `uuid4().hex` — 32 hex chars |
| `entity_type` | S | e.g. `ticket`, `contact`, `opportunity` |
| `record_id` | S | e.g. `tkt_abc123` |
| `actor_sub` | S | user_sub of the mutating actor; also the GSI partition key |
| `changed_at` | N | Unix timestamp integer (`now_ts()`); also the GSI sort key |
| `field_changes` | L | List of `{field_name: str, old_value: str|null, new_value: str|null}` |
| `source` | S | `api` \| `workflow` \| `import` \| `system` |

**GSI `by-actor`**: PK=`actor_sub` (S), SK=`changed_at` (N)

`attr_types` declaration in `scripts/local-ddb-init.py`:
```python
TableDef(
    _resolve_table_name(S.crm_audit_trail_table_name, "crm_audit_trail"),
    "pk",
    "sk",
    gsi=[{
        "index_name": "by-actor",
        "partition_key": "actor_sub",
        "sort_key": "changed_at",
    }],
    attr_types={"changed_at": "N"},
)
```

### 3.2 No new tables

STU-006 does not introduce any tables beyond `crm_audit_trail` (which is STU-001's responsibility). All reads and writes are against this single table.

### 3.3 Value serialization

`old_value` and `new_value` are serialized as strings: primitives use `str()`, lists use `json.dumps(sorted(list))`, dicts use `json.dumps(dict, sort_keys=True)`. `None` is stored as DynamoDB NULL (Python `None`) and returned as JSON `null`. Truncation: values longer than 1 024 characters are truncated to 1 021 chars with `"..."` appended to prevent runaway storage from large text fields. The truncation is noted in a sibling attribute `field_changes[i]["truncated"] = true` when applied.

## 4. API / Service Design

### 4.1 Service: `app/services/crm_audit_trail.py` (new file)

```python
from __future__ import annotations
from uuid import uuid4
from typing import Any
from app.core.tables import T
from app.core.time import now_ts
from app.core.cursor import encode_cursor, decode_cursor
from app.core.settings import S

def record_field_changes(
    actor_sub: str,
    entity_type: str,
    record_id: str,
    changes: list[dict],   # [{field_name, old_value, new_value}]
    source: str = "api",
) -> None:
    """Best-effort write; never raises; never blocks the write path."""

def get_record_audit_trail(
    entity_type: str,
    record_id: str,
    limit: int = 50,
    cursor: str | None = None,
) -> tuple[list[dict], str | None]:
    """Query by PK, SK descending. Returns (items, next_cursor)."""

def get_actor_audit_trail(
    actor_sub: str,
    limit: int = 50,
    cursor: str | None = None,
) -> tuple[list[dict], str | None]:
    """Query by-actor GSI, changed_at descending. Returns (items, next_cursor)."""
```

**`record_field_changes` implementation detail**: The entire function body is wrapped in `try/except Exception`. When `S.crm_studio_enabled` is `False` the function returns immediately without any DDB call. When enabled it calls `T.crm_audit_trail.put_item(Item={...})`. The `pk` is `f"ENTITY#{entity_type}#{record_id}"`, the `sk` is `f"CHANGE#{now_ts():010d}#{uuid4().hex[:16]}"`. The value serialization described in section 3.3 is applied before writing.

**`get_record_audit_trail`**: Calls `T.crm_audit_trail.query(KeyConditionExpression=Key("pk").eq(pk), ScanIndexForward=False, Limit=limit, ...)`. Uses `decode_cursor(cursor)` for `ExclusiveStartKey` and `encode_cursor(resp["LastEvaluatedKey"])` for `next_cursor`.

**`get_actor_audit_trail`**: Queries the `by-actor` GSI: `IndexName="by-actor"`, `KeyConditionExpression=Key("actor_sub").eq(actor_sub)`, `ScanIndexForward=False`. Note: the GSI sort key `changed_at` is type `N`, so `ExclusiveStartKey` for pagination must include `{"actor_sub": actor_sub, "changed_at": Decimal(ts), "pk": ..., "sk": ...}`. The cursor encodes the full `LastEvaluatedKey` dict via `encode_cursor`, which uses `_json_default` to serialize `Decimal` as `int` (cursor.py:12).

### 4.2 Write-path helper: `_emit_field_changes`

```python
def _emit_field_changes(
    actor_sub: str,
    entity_type: str,
    record_id: str,
    before: dict,
    after: dict,
    source: str = "api",
) -> None:
    """Diff before/after dicts and call record_field_changes. Best-effort."""
```

This function lives in `app/services/crm_audit_trail.py`. It compares `before` and `after` key by key, collecting `{field_name, old_value, new_value}` for every key whose value differs. Only the fields listed in `_AUDITED_FIELDS_BY_ENTITY` (a module-level dict) are diffed — auditing every key including internal GSI attributes would be noisy and wasteful:

```python
_AUDITED_FIELDS_BY_ENTITY: dict[str, frozenset[str]] = {
    "ticket": frozenset({
        "subject", "status", "assigned_to_sub", "assigned_admin_sub",
        "assigned_by", "priority", "labels", "complexity",
        "estimated_effort_hours", "space_id",
    }),
    # future entities added here as CRM tickets ship
}
```

If `entity_type` is not in the dict all top-level non-GSI keys are diffed (fallback for forward compatibility). The function calls `record_field_changes(...)` and swallows all exceptions.

### 4.4 Audit adapter: `CrmAuditTrailAdapter`

Added to `app/services/audit_adapters.py`:

```python
class CrmAuditTrailAdapter(BaseAuditAdapter):
    source_table = "crm_audit_trail"
    event_type = "crm_field_change"

    def query(
        self,
        from_ts: int,
        to_ts: int,
        actor: Optional[str] = None,
        target: Optional[str] = None,
        event_actions: Optional[list[str]] = None,
        limit: int = 1000,
    ) -> Iterator[UnifiedAuditEvent]:
        ...

    def _item_to_event(self, item: dict) -> Optional[UnifiedAuditEvent]:
        ...
```

Registered in `ADAPTERS` at `audit_adapters.py:441`:
```python
ADAPTERS: dict[str, BaseAuditAdapter] = {
    "auth": AlertsAdapter(),
    "moderation": ModerationAuditAdapter(),
    "broadcast": BroadcastAuditAdapter(),
    "admin": RoleAuditAdapter(),
    "billing": BillingLedgerAdapter(),
    "crm_field_change": CrmAuditTrailAdapter(),   # STU-006
}
```

`VALID_CATEGORIES` derives automatically (line 449: `set(ADAPTERS.keys())`), so `POST /ui/admin/audit-exports` immediately accepts `"crm_field_change"` as a category with no other changes.

**`query` implementation**: When `actor` is provided, query the `by-actor` GSI with `Key("actor_sub").eq(actor)` and a `FilterExpression` on `changed_at` between `from_ts` and `to_ts`. When `actor` is absent, perform a `scan` with `FilterExpression=Attr("changed_at").between(from_ts, to_ts)`. Both paths use `_paginate_query` / `_paginate_scan` (inherited from `BaseAuditAdapter`, lines 56-74). When `target` is supplied, additionally filter `Attr("pk").begins_with(f"ENTITY#{target}")` — this targets by entity_type/record_id prefix; pass as `entity_type#record_id` in the `target` field.

**`_item_to_event` implementation**: Maps one DDB row to a `UnifiedAuditEvent`:

```
event_id       = item["event_id"]
event_type     = "crm_field_change"
event_action   = f"crm.{item['entity_type']}.field_changed"
timestamp      = _ts_to_iso(item["changed_at"])
timestamp_unix = int(item["changed_at"])
actor_user_id  = item["actor_sub"]
actor_role     = "user"          # callers may be user or admin; conservative default
target_resource_type = item["entity_type"]
target_resource_id   = item["record_id"]
outcome        = "success"
metadata       = {
    "field_changes": item.get("field_changes", []),
    "source": item.get("source", "api"),
}
source_table   = "crm_audit_trail"
```

## 5. Detailed Behavior & Edge Cases

**No changes diffed**: If `before` and `after` are identical for all audited fields (e.g., a no-op update), `_emit_field_changes` detects an empty `changes` list and skips the `record_field_changes` call entirely. No row is written.

**First assignment (None → value)**: `old_value` will be `None` (serialized as JSON `null`). This is a valid and expected state — the first `assign_ticket` call on a newly created ticket will produce `old_value: null, new_value: "some_user_sub"` for `assigned_to_sub`.

**Status coercion**: `tickets.py:_coerce_status` (line 228) normalizes `"reopened"` → `"open"`. The audit trail captures the *coerced* value (post-normalization), not the raw input, ensuring consistency with what is actually stored.

**Concurrent update conflict**: `_apply_header_update_once` uses optimistic locking (line 792-804). If the conditional update fails (`TicketStateError` with code `ticket_update_conflict`), the exception propagates before the hook call site is reached — no field-change row is written for a failed update. This is correct: only committed changes are audited.

**Rollback / eventual consistency**: DynamoDB does not support multi-item transactions across tables with conditional expressions. The audit write is a separate `put_item` on `crm_audit_trail` that happens *after* the successful update to `T.tickets`. The brief window between the two writes is acceptable: if the audit write fails (network error, capacity), the `try/except` in `record_field_changes` swallows it. The ticket mutation is not rolled back. Operators can detect missing audit rows by comparing the gap between activity timestamps and trail timestamps.

**Large `labels` lists**: Serialized as `json.dumps(sorted(list))`. If the diff is too long (> 1 024 chars) truncation applies; `truncated: true` is set.

**`source` field**: The ticket router `app/routers/tickets.py` always goes through `TicketStore` methods which call `_emit_field_changes(source="api")`. Future import or workflow-engine callers pass `source="import"` or `source="workflow"` respectively at the call site.

**Entity types not yet fully implemented**: The hook is wired into `tickets.py` now. Future CRM entity services (contacts/party under PTY tickets, opportunities under OPP tickets) add their own hook calls when those services ship. The `crm_audit_trail` table is shared across all entity types — the `entity_type` field disambiguates rows.

**Pagination boundary with concurrent writes**: New rows inserted between pagination calls may cause a row to be missed or duplicated when iterating with cursors. This is standard DynamoDB behavior. The trail is an append-only log; duplicates cannot occur (each row has a unique event_id). Skipped rows during concurrent paging are acceptable for an audit UI and do not affect the correctness of the data that was written.

**Maximum `limit` cap**: Both service functions and endpoints cap `limit` at 200 to prevent unbounded reads. The adapter's `query` method uses its own `limit` parameter (default 1000, passed by the export pipeline) and does not impose the 200 cap since the pipeline controls its own budget.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**No dev_mode branch**: `record_field_changes` uses the same DDB `put_item` path in dev (moto in-process) and prod (real DynamoDB). There is no `if S.dev_mode` conditional in the service. This is identical to the pattern used in `app/services/instance_monitoring.py`, `app/services/ssh_session_recording.py`, and `app/services/kyc_cases.py`.

**Idempotency**: Each row has a unique `event_id = uuid4().hex` embedded in the SK. Duplicate calls to `record_field_changes` with the same arguments produce independent rows with distinct `event_id`s — there is no conditional-put idempotency guard. This is intentional: retried API requests that re-call `_emit_field_changes` should not de-duplicate (the underlying ticket mutation was also re-applied). In practice the ticket's optimistic locking prevents double-application of mutations, so double-write of audit rows cannot occur through normal paths.

**No PII in old/new values by default**: The `_AUDITED_FIELDS_BY_ENTITY` allowlist deliberately excludes free-text body fields (`description`, message `body`) and sensitive personal data fields. Only structural/state fields are captured (status, assignment, labels). Operators who need full-text diffs may extend the allowlist at deploy time (feature flag + config change, not a code change).

**Access control**:
- Record trail (`GET /crm-trail/{entity_type}/{record_id}`): ADMIN or ROOT. Scoped admins cannot reach audit trails without being assigned `require_admin_or_root`.
- Actor trail (`GET /crm-trail/actor/{actor_sub}`): ROOT only. This endpoint reveals every record an actor has ever touched; ROOT-only constraint prevents admins from querying each other's activity.
- `CrmAuditTrailAdapter` in bulk exports: ROOT-only (enforced by `_require_root` in `create_audit_export` at `audit_export.py:34-38`).

**Write-path security**: `record_field_changes` is never called from unauthenticated endpoints. Every call site goes through a `require_ui_session` or `require_root_session` dep chain before reaching `TicketStore`. The `actor_sub` passed is always the authenticated user's `sub` from the session context.

**Value truncation prevents DynamoDB item size attacks**: Individual field values are capped at `S.crm_audit_trail_value_max_length` (default 1 024). A single DDB item is bounded to approximately `len(field_changes) * 2 * 1024 + fixed_overhead`. With a reasonable maximum of 20 fields per change event, the maximum item size is well under DynamoDB's 400 KB per-item limit.

## 8. Backward Compatibility & Migration

**Zero migration required for existing data**: The `crm_audit_trail` table is empty at introduction. No existing DDB rows are modified. No existing APIs change their response shape.

**`VALID_CATEGORIES` expansion**: Adding `"crm_field_change"` to `ADAPTERS` expands the set of valid categories in the audit export API. This is a purely additive change — existing export jobs created without this category are unaffected. Clients that enumerate `/ui/admin/audit-exports` categories will see the new entry only when `CRM_STUDIO_ENABLED=1`.

**Ticket router compatibility**: The three hook insertions in `tickets.py` add a `try/except`-wrapped call after already-successful DDB writes. If `crm_audit_trail` does not exist in a legacy environment (before STU-001 ran), the `put_item` raises a `ResourceNotFoundException` which the `try/except` silently swallows. This means the ticket operation succeeds and no audit row is written — acceptable degraded behavior.

**Table creation**: `just restart` recreates all tables from `scripts/local-ddb-init.py`. In production, adding the `crm_audit_trail` `TableDef` entry and running `scripts/local-ddb-init.py` (or the equivalent `aws dynamodb create-table` command) before deploying the new backend binary is sufficient. No backfill is needed or possible (historical field changes are not reconstructable).

## 10. Open Questions / Assumptions

1. **Party/contact hook wiring timing**: STU-006 wires hooks only into `tickets.py`. Contact and account hooks will be added when the PTY (party model) tickets ship. The `crm_audit_trail` table and adapter are ready to accept those events without schema changes.

2. **`actor_role` field in `UnifiedAuditEvent`**: Currently hardcoded to `"user"` in `_item_to_event`. In practice the actor may be ADMIN or ROOT. The role is not stored in the trail row. A future improvement could pass the role at `record_field_changes` call time and persist it. For now `"user"` is a conservative default.

3. **Bulk export date-range queries against `crm_audit_trail`**: The adapter's scan path uses `FilterExpression` on `changed_at`. DynamoDB applies filters post-read, so large date ranges on a busy table will perform full table scans. A future GSI `by-date` (PK=`date_bucket` rounded to day, SK=`changed_at`) could optimize this for production workloads. Deferred until table volume justifies it.

4. **`_AUDITED_FIELDS_BY_ENTITY` extensibility**: The allowlist is currently hardcoded in `crm_audit_trail.py`. A future STU-011 (Studio custom fields) integration could merge the custom field list into the allowlist dynamically at call time. For now, custom field changes on `entity_type=ticket` fall through to the fallback (all non-GSI keys diffed), which may produce noisy output. Operators should extend the allowlist explicitly.

5. **`source="workflow"` path**: No workflow engine exists yet. The `source` field is forward-looking for when automation / import pipelines ship.

6. **Assumption — `T.crm_audit_trail` exists**: STU-006 depends on STU-001 for the DDB table and handle. If deployed before STU-001, `record_field_changes` will hit a `ResourceNotFoundException`, which the `try/except` swallows. The ticket operation will still succeed.
