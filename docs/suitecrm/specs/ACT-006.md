# ACT-006 — CRM Call Logging — extend call record with subject, description, direction, outcome

**Ticket type:** Feature  
**Priority:** P1  
**Estimate:** 2d  
**Flag:** `crm_activities_enabled` (default OFF) — sourced from ACT-001

---

## 1. Summary & Goal

ACT-006 extends the existing `call_history` DynamoDB table and its associated service/router with a CRM-grade call log concept. The platform already records telephony events via `record_call` in `app/services/call_history.py` (CALL-004), but those records are generated by the signaling layer and expose only `caller_id`, `callee_id`, `call_type`, `duration_seconds`, `status`, and `direction`. They are not user-authored and carry no contextual metadata.

This ticket introduces a second, user-authored call log entry type within the same `call_history` table (distinguished by a different SK prefix) that exposes the four missing CRM fields: `subject` (brief label for the call), `description` (freeform notes), `direction` (inbound/outbound — caller-specified rather than system-inferred), and `outcome` (connected, not_connected, left_message, wrong_number, busy). A full CRUD API is provided at `/ui/calls/logs`, gated by the `crm_activities_enabled` flag introduced in ACT-001. All existing platform call routes (`/ui/calls/history`, `/ui/calls/record`, `/ui/calls/stats`) remain byte-for-byte unchanged when the flag is off.

## 3. Data Model

### 3.1 DynamoDB: `call_history` table (no schema change)

ACT-006 reuses the existing `call_history` table (PK `user_id` / SK `sk`). CRM call log items are distinguished from platform call records by a different SK prefix: `CALLLOG#` instead of `CALL#`. This avoids any collision with the two-item-per-call records written by `record_call`.

**CRM call log SK pattern**:

```
CALLLOG#{inverted_ts:013d}#{call_id}
```

Using the same `9999999999999 - created_at` inversion already implemented in `_make_sk` (`call_history.py:28–32`), so the helper can be reused directly.

**No new DynamoDB table is needed.** No change to `scripts/local-ddb-init.py` is required.

### 3.2 DDB item shape

Each CRM call log item stored on the `call_history` table:

| Attribute | DDB type | Notes |
|-----------|----------|-------|
| `user_id` | S | PK — the owning user's `user_sub` |
| `sk` | S | `CALLLOG#{inverted_ts:013d}#{call_id}` |
| `call_id` | S | `uuid4().hex` |
| `subject` | S | max 200 chars |
| `description` | S | max 5000 chars; stored as empty string if omitted |
| `direction` | S | `"inbound"` or `"outbound"` |
| `duration_seconds` | N | integer ≥ 0 |
| `outcome` | S | one of the `CallOutcome` enum values |
| `call_type` | S | `"audio"`, `"video"`, or `"phone"` |
| `contact_user_sub` | S | optional; absent if not provided |
| `created_at` | N | Unix epoch seconds from `now_ts()` |
| `updated_at` | N | Unix epoch seconds; set on creation and on each PATCH |

The `CALLLOG#` prefix ensures `list_call_history` (which queries `begins_with(sk, "CALL#")`) continues to return only platform telephony records. The new `list_crm_call_logs` queries `begins_with(sk, "CALLLOG#")`.

### 3.3 New Pydantic models (`app/models.py`)

Add after `app/models.py:6125` (after `CallStatsOut`), in a new `# ─── CRM Call Logging (ACT-006) ─` section:

- **`CallOutcome(str, Enum)`**: `connected`, `not_connected`, `left_message`, `wrong_number`, `busy`.
- **`CallLogCreateIn(BaseModel)`**: `subject: str = Field(default="", max_length=200)`, `description: str = Field(default="", max_length=5000)`, `direction: Literal["inbound","outbound"] = "outbound"`, `duration_seconds: int = Field(ge=0, default=0)`, `outcome: CallOutcome = CallOutcome.connected`, `call_type: Literal["audio","video","phone"] = "phone"`, `contact_user_sub: Optional[str] = None`.
- **`CallLogUpdateIn(BaseModel)`**: `subject: Optional[str] = Field(default=None, max_length=200)`, `description: Optional[str]`, `outcome: Optional[CallOutcome]`. `direction`, `duration_seconds`, `call_type`, `contact_user_sub` are intentionally absent — immutable after creation.
- **`CallLogOut(BaseModel)`**: all fields of `CallLogCreateIn` plus `call_id: str`, `user_sub: str`, `created_at: int`, `updated_at: int`.
- **`CallLogListResponse(BaseModel)`**: `items: List[CallLogOut]`, `next_cursor: Optional[str]`.

## 4. API / Service Design

### 4.1 Service additions (`app/services/call_history.py`)

All new functions are appended to the existing file. They share the module-level `T.call_history` table handle and `now_ts` / `encode_cursor` / `decode_cursor` imports already present at `call_history.py:19–21`.

**`_CALLLOG_PREFIX = "CALLLOG#"`** — module-level constant distinguishing CRM items from platform `CALL#` items.

**`_make_calllog_sk(created_at, call_id) -> str`** — mirrors `_make_sk` at `call_history.py:28–32`. Returns `f"CALLLOG#{9999999999999 - created_at:013d}#{call_id}"`.

**`_calllog_item_to_out(item) -> dict`** — projects a DDB item to `CallLogOut` shape; uses `.get()` with safe defaults for all optional attributes.

**`create_crm_call_log(user_sub, body: CallLogCreateIn) -> dict`** — generates `uuid4().hex` call_id, calls `now_ts()` for `created_at`/`updated_at`, writes a single item to `T.call_history` with `PK=user_sub / SK=CALLLOG#{...}`, then calls `audit_event("crm_call_log_created", user_sub, call_id=call_id)` via a deferred local import (mirrors the pattern at `alerts.py:644`).

**`list_crm_call_logs(user_sub, cursor, limit) -> dict`** — queries `T.call_history` with `KeyConditionExpression="user_id = :uid AND begins_with(sk, :prefix)"` (prefix = `"CALLLOG#"`), `Limit=min(limit, 100)`, `ScanIndexForward=True` (inverted SK gives newest-first). Returns `{items, next_cursor}` using `encode_cursor` / `decode_cursor` (`cursor.py:94–131`).

**`get_crm_call_log(user_sub, call_id) -> Optional[dict]`** — same query plus `FilterExpression="call_id = :cid"`. Returns `None` if not found or if the item belongs to another user (PK ownership enforces this).

**`update_crm_call_log(user_sub, call_id, updates: CallLogUpdateIn) -> Optional[dict]`** — two-phase read-then-write: query by PK + prefix + `call_id` filter to resolve the SK; then `update_item` with a dynamic `SET` expression covering only `subject`, `description`, `outcome`, and `updated_at`. Returns `None` if not found. Calls `audit_event("crm_call_log_updated", ...)`.

**`delete_crm_call_log(user_sub, call_id) -> bool`** — same query to resolve SK; `delete_item` by `Key={user_id, sk}`; returns `True` if deleted, `False` if not found. Calls `audit_event("crm_call_log_deleted", ...)`.

### 4.2 Router additions (`app/routers/call_history.py`)

Five new route handlers are appended to the existing file. They use the same `router` instance (`APIRouter(prefix="/ui/calls", tags=["call-history"])` at `call_history.py:20`) and the same `require_ui_session` import (`call_history.py:18`).

**Guard helper** (module-level constant in the router file):

```python
def _require_crm_flag() -> None:
    from app.core.settings import S
    if not S.crm_activities_enabled:
        raise HTTPException(status_code=404, detail="Not found")
```

**Endpoints**:

| Verb | Path | Auth | Request body | Response |
|------|------|------|--------------|----------|
| POST | `/ui/calls/logs` | `require_ui_session` | `CallLogCreateIn` | `CallLogOut` 201 |
| GET  | `/ui/calls/logs` | `require_ui_session` | query params: `cursor`, `limit` | `CallLogListResponse` 200 |
| GET  | `/ui/calls/logs/{call_id}` | `require_ui_session` | — | `CallLogOut` 200 |
| PATCH | `/ui/calls/logs/{call_id}` | `require_ui_session` | `CallLogUpdateIn` | `CallLogOut` 200 |
| DELETE | `/ui/calls/logs/{call_id}` | `require_ui_session` | — | `{"ok": True}` 200 |

Declaration order matters: all `/logs` routes must be declared **before** any future `/{call_id}` wildcard to prevent FastAPI matching `"logs"` as a path param. In this router the existing routes use `/history/{call_id}` and `/stats`, so there is no collision with the new `/logs` prefix, but the `GET /logs/{call_id}` must be declared before `GET /logs` when using the same prefix — in practice FastAPI resolves static vs. parameterized segments correctly as long as `/logs` (list) is declared before `/logs/{call_id}` (detail).

Each handler calls `_require_crm_flag()` at the top, delegates to the corresponding service function, and raises `HTTPException(404)` on a `None` return from `get_crm_call_log`, `update_crm_call_log`, or `delete_crm_call_log`. The POST handler returns HTTP 201.

## 5. Detailed Behavior & Edge Cases

### 5.1 SK uniqueness and collision avoidance

`record_call` writes items with `SK = CALL#{...}`. The new items use `SK = CALLLOG#{...}`. The prefixes are distinct: `CALLLOG#` does **not** begin with `CALL#` — the fifth character of `CALLLOG#` is `L`, whereas `CALL#` has `#` as its fifth character. DynamoDB `begins_with(sk, "CALL#")` therefore does **not** match `CALLLOG#` items (verified: `"CALLLOG#...".startswith("CALL#")` is `False`). No `FilterExpression` change to `list_call_history` is required; the existing query at `call_history.py:80–81` already excludes CRM log items by virtue of the distinct prefix characters.

### 5.2 Input defaults and immutability

`subject` and `description` default to `""` and are always stored; `_calllog_item_to_out` uses `.get(..., "")` so items survive future schema extensions. `direction`, `duration_seconds`, `call_type`, and `contact_user_sub` are immutable after creation (absent from `CallLogUpdateIn`). `contact_user_sub` is stored opaquely — FK validation against the `users` table is deferred to ACT-007.

### 5.3 Concurrency, pagination, and IDOR

PATCH uses a two-phase query-then-`update_item`; last writer wins on concurrent requests. `list_crm_call_logs` sets `Limit` with no post-query filter so the effective page size matches exactly. All queries anchor on `user_id = :uid` (the authenticated sub from `require_ui_session`) — cross-user probing returns 404 without confirming record existence (IDOR prevention matching the pattern in `get_call_detail` at `call_history.py:99–114`).

## 6. Feature Flag & Config

### 6.1 Flag

`crm_activities_enabled` is declared in ACT-001 (`docs/suitecrm/specs/ACT-001.md`). The exact form used in that spec differs from the `CART_REMINDERS_ENABLED` pattern at `app/core/settings.py:821`; ACT-001 specifies:

```python
crm_activities_enabled: bool = os.environ.get(
    "CRM_ACTIVITIES_ENABLED", "false"
).lower() == "true"
```

Note: this differs from the `not in ("0","false","False")` idiom used for `CART_REMINDERS_ENABLED` — with the ACT-001 form, `"1"` evaluates to `False` (only `"true"` / `"True"` activates the flag). Implementors must use the ACT-001 form exactly.

**Default: OFF.** The existing `/ui/calls/history`, `/ui/calls/record`, `/ui/calls/stats` routes are not touched by this flag — they remain unconditionally registered and operational.

### 6.2 Environment variable

| Variable | Default | Effect |
|----------|---------|--------|
| `CRM_ACTIVITIES_ENABLED` | `"0"` | `"1"` enables all CRM activity endpoints including the five new `/ui/calls/logs` routes |

No additional sub-flag is required for ACT-006; the ticket spec designates only the top-level `crm_activities_enabled` gate. Sub-flags (`crm_tasks_enabled`, `crm_notes_enabled`, etc.) from ACT-001 are for modules introduced in later tickets.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 compliance

No `if S.dev_mode` branch exists in any new code. All DynamoDB writes go through `T.call_history` (DynamoDB Local in dev, real DynamoDB in prod — same code path). `audit_event` writes to `T.alerts` regardless of environment. No mock S3 or email paths are involved.

### 7.2 Idempotency

`create_crm_call_log` generates a fresh `call_id` + `created_at` on every POST — not idempotent by design. `delete_crm_call_log` is effect-idempotent (item gone after first call) but returns 404 on retry (standard REST).

### 7.3 Ownership and audit

All service functions anchor on `user_id = :uid` from `ctx["user_sub"]` — cross-user access returns 404 (IDOR parity with `get_call_detail` at `call_history.py:103`). Each mutating path emits a distinct audit event (`crm_call_log_created`, `crm_call_log_updated`, `crm_call_log_deleted`) via `audit_event` (`alerts.py:644`) with `call_id` in `**fields`. The import is deferred (local) to avoid circular-import risk.

### 8.1 Table schema

No new DynamoDB table is created. No GSIs or attribute definitions are added to the existing `call_history` table. `scripts/local-ddb-init.py:1955–1960` is unchanged.

Existing `CALL#` prefix items in `call_history` are never touched by the new code paths. `list_call_history` queries `begins_with(sk, "CALL#")` at `call_history.py:80–81`. ### 8.3 Frontend

No existing frontend page is modified. The CRM call log UI is a net-new page under `frontend/src/pages/crm-calls/` (§9.3 below). The `/ui/calls/history` page continues to show platform telephony records only.

Because the flag defaults OFF and no table schema changes are needed, ACT-006 can be deployed in any order relative to other in-flight changes. Enabling `CRM_ACTIVITIES_ENABLED=1` in `.env.local` activates the new endpoints with no restart-and-reseed required (the flag is read from `S` at request time, not at startup).
