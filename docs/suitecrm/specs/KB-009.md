# KB-009 — Full-text search token index + global search integration

**Type:** Feature  **Priority:** P1  **Estimate:** 2 days  
**Ticket source:** `docs/suitecrm/CRM_KNOWLEDGE_BASE_TICKETS.md`, section "KB-009"

---

## 1. Summary & Goal

KB-009 replaces the naive DynamoDB `scan + contains` approach for searching Knowledge Base articles with an inverted-token index stored on the `crm_kb_articles` table, and wires KB article results into the platform's global search aggregator at `app/routers/search.py`.

With this ticket deployed and `KNOWLEDGE_BASE_ENABLED=1`, the following become possible:

1. **Dedicated public KB search endpoint** — `GET /public/kb/search?q=<query>` returns published articles whose titles match the query using the token index (no table scan).
2. **Global search integration** — `GET /ui/search?q=<query>&types=kb` fans out to KB alongside the existing nine search modules (`users`, `posts`, `catalog`, `files`, `messages`, `tickets`, `contacts`, `videos`, `calendar`).
3. **Automatic index maintenance** — token rows are written on article create/update (title change) and deleted on expire/archive, keeping the index coherent without any manual rebuild step.

The entire feature is gated behind `S.knowledge_base_enabled`. With the flag off the platform is byte-for-byte unchanged: the dedicated search endpoint returns 404, `_search_kb` returns `_empty_section()`, and `ALLOWED_TYPES` in the global search does not include `"kb"`.

## 3. Data Model

### 3.1 Token index rows (new, on `crm_kb_articles` table)

```
PK  = "SEARCH_TOKEN#{token}"      (String)
SK  = "ARTICLE#{article_id}"      (String)

Fields:
  article_id      String   — the article's UUID
  title_snippet   String   — first 80 characters of the article title (snapshot at index time)
  published_at    Number   — integer Unix timestamp; 0 if not yet published
  status          String   — "draft" | "published" | "expired"
  updated_at      Number   — integer Unix timestamp of index write
```

No GSI is required. The query pattern is always `PK = "SEARCH_TOKEN#{token}"` using the table's primary hash key. DynamoDB returns all articles whose title contains `token` as a prefix substring, sorted by SK (ARTICLE# prefix + article_id UUID) — caller sorts in memory by `published_at` desc.

**Single-table reasoning.** Token rows coexist on `crm_kb_articles` alongside `ARTICLE#{id}/META`, `CATEGORY#{id}/META`, `RELATED#{id}/ARTICLE#{id}`, `TAG#{tag}/ARTICLE#{id}`, `RATING#{user}/META`, etc. The `SEARCH_TOKEN#` PK prefix is distinct from all other prefixes in use by KB-001 through KB-008.

### 3.2 scripts/local-ddb-init.py additions

No new `TableDef` is needed. The `crm_kb_articles` table definition (added by KB-001) already has `attr_types={"created_at": "N", "published_at": "N"}`. Token index rows do **not** introduce any new numeric GSI sort keys, so no additional `attr_types` entries are required here.

The spec does not change the table definition — KB-009 is purely additive at the row level on the existing table.

### 3.3 Token generation rules

Given an article title `t`:
1. Lowercase the entire string.
2. Extract word tokens via `re.findall(r"[a-z0-9-]+", t.lower())` — keeps hyphens within words (e.g. `"self-service"` yields `["self", "service"]` after the split; alternatively keep it as a single token if desired — see Open Questions).
3. For each word token `w` whose length is ≥ 3 characters, generate all prefix strings of length 3 through `min(len(w), 8)` — the `_KB_SEARCH_MAX_PREFIX_LEN = 8` constant. The full word itself is included as a "prefix of length `len(w)`" (no special casing).
4. Deduplicate tokens with `dict.fromkeys(...)`.
5. Cap at 60 distinct token strings per article (drop excess tokens if the title is unusually long). This prevents a single article from consuming hundreds of DDB writes.

Tokens shorter than 3 characters are skipped to avoid over-broad matches on common English stop words (`"a"`, `"to"`, `"in"`, `"of"`, `"is"`, `"it"`) that would make the index enormous and degrade precision.

Example: title `"How to reset your password"` →
- words (after lowercasing, filtering 2-char stopwords): `["how", "reset", "your", "password"]`
- tokens: `"how"`, `"res"`, `"rese"`, `"reset"`, `"you"`, `"your"`, `"pas"`, `"pass"`, `"passw"`, `"passwo"`, `"passwor"`, `"password"`

## 4. API / Service Design

### 4.1 Service additions (`app/services/kb_articles.py`)

#### `_KB_SEARCH_MAX_PREFIX_LEN: int = 8`

Module-level constant mirroring `_MSG_SEARCH_MAX_PREFIX_LEN` in `app/routers/messaging.py:2786`. Governs both index writes and query prefix generation; the two must always match.

#### `_build_kb_search_tokens(title: str) -> list[str]`

```python
def _build_kb_search_tokens(title: str) -> list[str]:
    words = re.findall(r"[a-z0-9]+", (title or "").lower())
    out: list[str] = []
    for word in words:
        if len(word) < 3:
            continue
        for length in range(3, min(len(word), _KB_SEARCH_MAX_PREFIX_LEN) + 1):
            out.append(word[:length])
    return list(dict.fromkeys(out))[:60]
```

Pure function; no I/O. Tested directly in unit tests.

#### `_write_kb_search_index(article_id: str, title: str, published_at: int, status: str) -> None`

```python
def _write_kb_search_index(
    article_id: str,
    title: str,
    published_at: int,
    status: str,
) -> None:
    tokens = _build_kb_search_tokens(title)
    if not tokens:
        return
    title_snippet = (title or "")[:80]
    ts = now_ts()
    with T.kb_articles.batch_writer() as batch:
        for token in tokens:
            batch.put_item(Item={
                "PK": f"SEARCH_TOKEN#{token}",
                "SK": f"ARTICLE#{article_id}",
                "article_id": article_id,
                "title_snippet": title_snippet,
                "published_at": published_at,
                "status": status,
                "updated_at": ts,
            })
```

Uses `T.kb_articles.batch_writer()` (mirrors `_write_tag_index` in `newsfeed.py:444`). Best-effort: exceptions are logged, not raised — a failed index write must never block article creation or publishing.

#### `_delete_kb_search_index(article_id: str, old_title: str) -> None`

```python
def _delete_kb_search_index(article_id: str, old_title: str) -> None:
    tokens = _build_kb_search_tokens(old_title)
    if not tokens:
        return
    with T.kb_articles.batch_writer() as batch:
        for token in tokens:
            batch.delete_item(Key={
                "PK": f"SEARCH_TOKEN#{token}",
                "SK": f"ARTICLE#{article_id}",
            })
```

Called on expire and archive. Also called at the start of `update_article` when the title changes (old title tokens deleted, new title tokens written).

#### `KbArticleService.search_articles(q: str, limit: int = 25, *, published_only: bool = True) -> list[KbSearchResultItem]`

**Replaces the CAS-015 scan stub.** Full algorithm:

1. Normalize `q`: lowercase, `re.findall(r"[a-z0-9]+", ...)`, filter words shorter than 3 chars. Split into at most 3 tokens (take the first 3 to bound DDB read amplification).
2. If no tokens remain, return `[]` immediately.
3. Query primary token: `T.kb_articles.query(KeyConditionExpression=Key("PK").eq(f"SEARCH_TOKEN#{tokens[0][:_KB_SEARCH_MAX_PREFIX_LEN]}"))`. Use `Limit=200` per query page; loop on `LastEvaluatedKey` until exhausted (DDB `FilterExpression doesn't reduce page size` caveat from CLAUDE.md applies here — the token rows are sparse so all pages must be consumed). Collect candidate `(article_id, title_snippet, published_at, status)` tuples.
4. For each additional token (tokens[1], tokens[2] if present): query its index similarly and intersect `article_id` sets client-side — only keep articles present in **all** token result sets (AND semantics).
5. Filter: if `published_only=True`, discard items where `status != "published"`.
6. Sort remaining candidates by `published_at` descending.
7. Take the first `limit` article IDs. Fetch full META rows via `T.kb_articles.meta.client.batch_get_item(RequestItems={S.kb_articles_table: {"Keys": [...], "ProjectionExpression": "..."}})` — project only the fields needed for `KbSearchResultItem` to minimize read cost.
8. Build and return `list[KbSearchResultItem]`.

The `published_only=False` path is used by an admin preview endpoint (KB-011) and by the global aggregator when the caller is an authenticated admin. The flag defaults to `True` for the public portal.

#### Wire `_write_kb_search_index` into existing lifecycle methods

- `KbArticleService.create_article(...)` — after successful `put_item`, call `_write_kb_search_index(article_id, title, published_at=0, status="draft")` wrapped in `try/except`.
- `KbArticleService.update_article(article_id, ...)` — if title changes: call `_delete_kb_search_index(article_id, old_title)` then `_write_kb_search_index(article_id, new_title, ...)`.
- `KbArticleService.publish_article(article_id, admin_sub)` — after updating `status` and `published_at`: call `_write_kb_search_index(article_id, title, published_at, status="published")` (updates all token rows to reflect the new `published_at` and `status`).
- `KbArticleService.expire_article(article_id, ...)` and `archive_article(article_id, ...)` — call `_delete_kb_search_index(article_id, title)` after successfully updating status.

Wire point for KB-010 (`restore_revision`) is also noted: `restore_revision` already calls `_write_kb_search_index` per the KB-010 spec (`docs/suitecrm/specs/KB-010.md`).

**Handler:**

```python
@router.get("/public/kb/search", response_model=KbSearchOut)
def public_kb_search(
    q: str = Query(..., min_length=2, max_length=100),
    limit: int = Query(default=10, ge=1, le=25),
    request: Request = None,
):
    if not S.knowledge_base_enabled:
        raise HTTPException(status_code=404, detail="Knowledge base not enabled")
    # Per-IP rate limit (fail-open)
    client_ip = (request.client.host if request and request.client else "unknown")

    svc = KbArticleService()
    items = svc.search_articles(q, limit=limit, published_only=True)
    return KbSearchOut(
        items=items,
        query=q,
        total_estimate=len(items),
        has_more=len(items) >= limit,
    )
```

Route ordering: `GET /public/kb/search` must be declared **before** any dynamic `/{article_id}` routes in `kb_articles.py` (constraint from ticket file header) so the literal segment `search` is not captured as an article ID.

## 5. Detailed Behavior & Edge Cases

### 5.1 Index write on create vs. publish

Articles are created in `draft` status. Token rows are written at create time with `status="draft"` and `published_at=0`. When `publish_article` is called, the same token rows are overwritten with `status="published"` and the real `published_at` timestamp. This two-phase approach means:
- A draft article's token rows exist but are never returned by `search_articles(published_only=True)`.
- Admin tools can call `search_articles(published_only=False)` to find draft articles by title.
- The overwrite at publish time is safe because `batch_writer().put_item` is a full replacement of the item.

### 5.2 Title update — old token cleanup

When `update_article` is called and `new_title != old_title`:

1. Read the current `old_title` from the META row before applying the update.
2. Call `_delete_kb_search_index(article_id, old_title)` — deletes all token rows derived from the old title.
3. Apply the DDB `update_item` to write the new title.
4. Call `_write_kb_search_index(article_id, new_title, published_at, status)` — writes token rows for the new title.

If the title is unchanged (only description, body, or tags are updated), neither delete nor write is called — no unnecessary DDB writes.

### 5.3 Stale token rows after expire/archive

`expire_article` and `archive_article` call `_delete_kb_search_index`. If the delete call fails (DDB unavailable, partial batch failure), stale `SEARCH_TOKEN#` rows remain in the table. The query step in `search_articles` fetches `status` from the token row snapshot and filters out `status != "published"` — so stale rows for expired articles are silently excluded from results without needing a secondary read. The `status` field on the token row is therefore a safety net against stale index rows.

### 5.4 Public endpoint per-IP rate limit

`GET /public/kb/search` is unauthenticated. To prevent abuse, a per-IP soft cap of 20 requests per 60 seconds is applied using `_bucket_limit` from `app/services/rate_limit.py`. The call uses **fail-open semantics**: if `_bucket_limit` raises (DDB unavailable), the request is served anyway. The cap is intentionally lenient (20 rpm) since the endpoint is cheap (token index query, not a scan). This differs from the global search endpoint which hard-enforces its cap and returns 429.

### 5.5 AND vs OR semantics for multi-token queries

`search_articles` splits the query into up to 3 tokens and performs AND intersection: an article must appear in **all** per-token result sets. This provides higher precision than OR at the cost of recall. A query like `"reset password"` returns only articles whose titles contain both `"reset"` and `"password"` as substrings, not articles that match only one word. This matches the behavior of `_search_tickets` at `search.py:404` which also applies AND logic.

### 5.6 Empty query normalization

If after lowercasing and tokenizing the query `q` produces zero tokens of length ≥ 3, `search_articles` returns `[]` immediately without querying DDB. Example: `q="a to"` → both words are < 3 chars → empty result. The endpoint's `min_length=2` constraint on `q` prevents trivially empty string inputs from reaching the service layer, but single-character and two-character queries are still possible (`q="ab"`) — these are handled gracefully.

### 5.7 batch_get_item size limit

DDB `batch_get_item` is limited to 100 keys per call. Since `search_articles` caps results at `limit ≤ 25` (public endpoint) or `≤ 20` (global search), the batch_get_item call for article META rows will never exceed 25 keys — well within the DDB limit.

### 5.8 Global search `types` parameter validation

The global search endpoint at `search.py:855` raises 400 for unknown types:

```python
invalid = set(requested_types) - ALLOWED_TYPES
if invalid:
    raise HTTPException(status_code=400, ...)
```

Because `"kb"` is only added to `ALLOWED_TYPES` when `S.knowledge_base_enabled` is true, a caller that sends `types=kb` with the flag off will receive a 400 `"Invalid search types: kb"` error. This is by design — it prevents silent no-op queries and makes the flag state detectable by API clients. The public-facing documentation for KB-012 should note this behavior.

### 5.9 ThreadPoolExecutor worker exhaustion

The global search fan-out at `search.py:676` caps `max_workers = min(len(search_fns), 8)`. With `"kb"` added, the maximum is 10 modules (9 existing + 1 KB). The `min(..., 8)` cap means KB may share a worker thread with another module. This is acceptable: token index queries are fast DDB primary-key lookups (~5ms p99), well within the 2-second per-future timeout.

### 5.10 Concurrent index writes

If two concurrent requests call `publish_article` for the same article (e.g. an admin double-click), both will call `_write_kb_search_index` with the same token set. DDB `put_item` is idempotent (last writer wins for the same PK+SK). No conditional expression is needed — duplicate writes are harmless.


### 6.2 Token index tuning constants

These are module-level constants in `app/services/kb_articles.py` — not env-var driven (same approach as `_MSG_SEARCH_MAX_PREFIX_LEN` in `messaging.py:2786`). They are not exposed as settings because changing them requires an index rebuild:


### 6.3 Search result limit

The public endpoint caps `limit ≤ 25`. The global aggregator calls `search_articles(q, limit=limit)` where the caller-supplied `limit` is already bounded to `[1, 20]` by the global search endpoint's `Query(default=5, ge=1, le=20)` at `search.py:828`. These constraints are enforced at the router layer; `KbArticleService.search_articles` accepts any positive integer.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Single code path (SECOPS-007)

There is no `if S.dev_mode:` branch in KB-009. All code paths — token writes, token queries, batch_get_item for article META — run against the same DDB client (`T.kb_articles`) regardless of whether the environment uses DynamoDB Local (`http://localhost:8001`) or production DynamoDB. The `AWS_ACCESS_KEY_ID=test` / `DDB_ENDPOINT_URL` values in `.env.local` make the boto3 calls target DynamoDB Local transparently without any code divergence.

### 7.2 Idempotency

All index write operations are idempotent:
- `_write_kb_search_index`: `batch_writer().put_item` is a full overwrite of the token row. Repeating the call with the same inputs produces identical DDB items.
- `_delete_kb_search_index`: `batch_writer().delete_item` is a no-op if the item doesn't exist.
- `search_articles` is a read-only operation with no side effects.

### 7.3 Authentication and authorization

- `GET /public/kb/search` — no authentication. Only `status="published"` articles are returned. The handler enforces `published_only=True` unconditionally.
- `GET /ui/search?types=kb` — requires `require_ui_session` (cookie or Bearer token). Returns published articles only (same `published_only=True` call path via `_search_kb`). An authenticated admin who wants draft-article search uses the dedicated admin endpoint (KB-012 admin UI, not this ticket).
- The token index itself stores no sensitive data — only `article_id`, `title_snippet` (first 80 chars of title), `published_at`, and `status`. No user PII, no body content.

### 7.4 Input sanitization

Query input goes through `_sanitize_query` in `search.py:52` (for the global aggregator path) which normalizes Unicode, strips control characters, and collapses whitespace. The public endpoint handler should apply an equivalent normalization before passing `q` to `search_articles`:

```python
q = re.sub(r"\s+", " ", q.strip().lower())
```

The service layer's `_build_kb_search_tokens` applies `re.findall(r"[a-z0-9]+", ...)` which already strips any residual punctuation or injection attempt.

### 7.5 Index row exposure

Token rows (`PK=SEARCH_TOKEN#*`) are DDB-internal only. They are never exposed via any API endpoint. A query for `GET /public/kb/articles/SEARCH_TOKEN#password` would fail with 404 because the article existence check in `get_article` looks up `PK=ARTICLE#{article_id}` / `SK=META` — the SEARCH_TOKEN# PK pattern never matches.

## 8. Backward Compatibility & Migration

### 8.1 Flag-off state

With `KNOWLEDGE_BASE_ENABLED=0` (the default):
- No token rows are ever written (every KB service method checks the flag at entry).
- `GET /public/kb/search` returns 404.
- `_search_kb` in `search.py` returns `_empty_section()`.
- `"kb"` is not in `ALLOWED_TYPES`; a caller explicitly requesting `types=kb` receives 400.
- The existing `app/routers/search.py`, `app/services/filemanager.py`, and all other platform files are byte-for-byte unchanged.

### 8.2 Cold-start index population

When KB-009 is deployed with `KNOWLEDGE_BASE_ENABLED=1` for the first time against a production DynamoDB table that already has articles (created via KB-001 through KB-007), no token rows exist. To populate the index, a one-time migration is needed:

`KbArticleService.rebuild_search_index()` — new method (used only from `scripts/rootctl` or an admin endpoint outside this ticket's scope):

```python
def rebuild_search_index(self) -> int:
    """Scan all ARTICLE# META rows and rewrite their token index rows. Returns count."""
    count = 0
    last_key = None
    while True:
        kwargs = {
            "FilterExpression": "begins_with(#pk, :prefix) AND #sk = :meta",
            "ExpressionAttributeNames": {"#pk": "PK", "#sk": "SK"},
            "ExpressionAttributeValues": {":prefix": "ARTICLE#", ":meta": "META"},
            "Limit": 100,
        }
        if last_key:
            kwargs["ExclusiveStartKey"] = last_key
        resp = T.kb_articles.scan(**kwargs)
        for item in resp.get("Items", []):
            article_id = item.get("article_id", "")
            title = item.get("title", "")
            published_at = int(item.get("published_at") or 0)
            status = item.get("status", "draft")
            _write_kb_search_index(article_id, title, published_at, status)
            count += 1
        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break
    return count
```

This is a migration utility, not part of the normal application path. In dev, `just restart` recreates the DDB table from scratch so no backfill is needed in development. In production, the operator runs the rebuild once via `scripts/rootctl` before enabling public search.

### 8.3 No schema changes to existing tables

The `crm_kb_articles` table receives new rows but no schema changes (no new GSIs, no new `attr_types`). All existing queries (`ByStatus`, `ByCategory`, `ByAuthor`, `ByTag` GSIs) continue to work identically because they filter by PK prefixes (`ARTICLE#`, `CATEGORY#`, `TAG#`) that never collide with `SEARCH_TOKEN#`.

## 10. Open Questions / Assumptions

1. **Hyphen handling in titles** — the token extractor uses `r"[a-z0-9]+"` which splits on hyphens. A title `"Self-service portal"` yields tokens for `"sel"`, `"self"`, `"ser"`, `"serv"`, ..., `"portal"` — it does not index the compound `"self-service"`. This is acceptable for MVP (consistent with `_search_tokens` in `filemanager.py:966`), but a query for `"self-service"` returns articles containing both `"self"` and `"service"` independently. If compound-word search is needed in a future iteration, the tokenizer can be extended with an ngram or bigram step without a breaking API change.

2. **Body-text indexing** — this ticket indexes the **title only**. SuiteCRM's AOS KB supports full-text search over the article body. Indexing the body would require significantly more token rows (bodies can be thousands of words) and a separate token table or careful row-count management. Body search is deferred to a follow-on ticket (KB-009b or KB-013). The `excerpt` field in `KbSearchResultItem` is derived from the body at query time (fetched via `batch_get_item`) but not indexed.

3. **Index rebuild endpoint** — `rebuild_search_index()` is defined as a service method. Whether it should be exposed as a root-only `POST /admin/kb/search/rebuild` endpoint is out of scope for this ticket. The method is sufficient for a `scripts/rootctl` CLI invocation.

4. **`published_only=False` for admin global search** — the global aggregator at `_search_kb` uses `published_only=True` unconditionally. An authenticated admin who wants to search draft articles via the global search bar will not see them. A follow-on ticket (or KB-012) can add an `include_drafts` query param to `GET /ui/search` for admin callers.

5. **`GLOBAL_SEARCH_EXTENDED_DOMAINS` interaction** — if `GLOBAL_SEARCH_EXTENDED_DOMAINS=false` but `KNOWLEDGE_BASE_ENABLED=1`, the `"kb"` type is added to `ALLOWED_TYPES` regardless (KB's addition is independent of the messaging/ticket/contacts/videos/calendar block). This is intentional: the KB flag controls KB availability; the extended search flag controls the messaging/ticket/etc. domains.
