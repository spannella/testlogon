# EVT-006 — Contact/account proximity search (Haversine radius endpoint)

**Type:** Feature | **Priority:** P2 | **Estimate:** 2d
**Source:** `docs/suitecrm/CRM_MISC_TICKETS.md` (section "EVT-006")
**Dependencies:** EVT-005 (geocoded lat/lng on address items). EVT-001 (flag scaffolding pattern).

---

## 1. Summary & Goal

EVT-006 adds a server-side proximity search endpoint that returns platform addresses — and, once PTY-001
ships, party/contact/account records — within a caller-specified kilometre radius of a given lat/lng centre
point. Distance is computed in pure Python via the Haversine formula applied against the `lat`/`lng`
attributes written onto DynamoDB items by EVT-005 (`app/services/crm_geocoding.py`).

The ticket delivers:

1. A `haversine_km(lat1, lng1, lat2, lng2) -> float` pure-Python helper added to
   `app/services/crm_geocoding.py`.
2. A `proximity_search(...)` service function that scans geocoded address items, applies Haversine
   filtering in Python (post-DDB-fetch), and returns results sorted by ascending distance.
3. A new read endpoint `GET /ui/crm/maps/contacts/proximity` exposed from a new router
   `app/routers/crm_maps.py`, prefix `/ui/crm/maps`.
4. A rate-limit guard keyed per calling user using the existing `_bucket_limit` helper
   (`app/services/rate_limit.py:60`).
5. A `crm_proximity_search_enabled` sub-flag (off by default, requires `crm_geocoding_enabled` to also
   be true).

With both flags off the platform is byte-for-byte identical to its pre-EVT-006 state; all new routes
return 404 and no DDB reads are issued.

## 2. Context & Current State

### 2.1 Geocoded address data written by EVT-005

EVT-005 (`docs/suitecrm/specs/EVT-005.md`) adds `lat` (N), `lng` (N), and `geocoded_at` (N) as sparse
attributes onto items in the existing `addresses` DynamoDB table (PK=`user_sub`, SK=`address_id`,
declared at `scripts/local-ddb-init.py:98`, settings key `ADDRESSES_TABLE_NAME` at
`app/core/settings.py:463`). The service `app/services/crm_geocoding.py` (EVT-005) exposes
`list_geocoded_addresses(user_sub) -> list[dict]` which returns all of a user's address items that
carry both `lat` and `lng`. No GSI on these numeric fields exists; the scan-then-filter approach is
correct and consistent with the CLAUDE.md DDB gotcha: "DynamoDB fetches up to 1MB *before* applying
FilterExpression."

EVT-005 also defines `geocode_address(address: dict) -> dict[str, float] | None` (the same SHA-256
deterministic mock first implemented in `app/services/kyc_address_verification._geocode` at lines
210–224) and the `crm_geocoding_enabled` / `CRM_GEOCODING_ENABLED` flag (default `false`) in
`app/core/settings.py`.

### 2.2 Current contacts surface (no lat/lng)

`app/routers/contacts.py` (prefix `/ui/contacts`, registered in `app/main.py`) manages `T.contacts`
(PK=`owner_id`, SK=`contact_id`, declared at `scripts/local-ddb-init.py:691`, table name
`DDB_CONTACTS_TABLE` defaulting to `"Contacts"`). Contact items store `contact_id` (the target user's
`user_sub`), `display_name`, `profile_photo_url`, `is_favorite`, `is_blocked`, and `added_at`. They do
**not** store a postal address or `lat`/`lng` (`app/routers/contacts.py:101-109`). There is no proximity
query capability today.

### 2.3 No party table yet

`T.party` does not exist in `app/core/tables.py` at the time of writing (grep confirms no `party` field
beyond `watch_party_participants`). PTY-001 (`docs/ofbiz/specs/PTY-001.md`) will introduce it — that
ticket adds `party: Any` to the `Tables` dataclass and `party=_safe_table(S.party_table_name)` to the
`T` instantiation (PTY-001 §3; the `party` `TableDef` itself is PTY-002's scope). EVT-006 handles
this by operating on the `addresses` table today and accepting an opaque `entity_type` query parameter
whose `"party"` value is a no-op until PTY ships (see §5.4).

### 2.4 Haversine: no existing implementation

A search across `app/` finds no existing Haversine or great-circle distance implementation. The formula
is self-contained pure Python (6 lines; no third-party library required), consistent with the project's
preference for dependency-free helpers (see `app/services/receipts.py` and `audit_export_pipeline.py`
for the pure-Python PDF renderer precedent).

### 2.5 Rate limiting primitive

`app/services/rate_limit._bucket_limit(user_sub, sid, max_n, win) -> bool` (line 60) provides
sliding-window DDB-backed rate limiting using `T.sessions`. Returns `False` when the caller has
exceeded `max_n` calls within `win` seconds. Used by KYC partner API (`rate_limit_kyc_partner_api`,
line 385) and other callers. EVT-006 adds a thin wrapper `rate_limit_proximity_search(user_sub)` that
calls `_bucket_limit` with configurable caps.

### 2.6 Cursor pagination

`app/core/cursor.encode_cursor` / `decode_cursor` (lines 94, 103) provide HMAC-signed, tamper-resistant
DynamoDB `LastEvaluatedKey` pagination. The proximity search result set is assembled entirely in Python
after a full DDB scan (no native DDB pagination boundary corresponds to a radius cut-off), so the
cursor is applied at the Python level — the first page of results (up to `limit`) is returned and the
remaining results are held in-memory only for the duration of that request. This is safe because the
address table is per-user and bounded in size.

### 2.7 Auth dependencies

`app/services/sessions.require_ui_session` (line 330 of `app/services/sessions.py`) is the standard
auth dependency that returns `{"user_sub": str, "role": Role, ...}`. All EVT-006 endpoints use it.
`app/auth/roles.Role` enum is available for future admin-only elevation but is not needed in this
ticket's public search path.

### 2.8 Audit primitive

`app/services/alerts.audit_event(event, user_sub, request=None, **fields)` (line 644) is the canonical
audit write. EVT-006 emits one audit event per proximity search call (best-effort, fire-and-forget in a
`try/except`).

EVT-006 reads from the existing `addresses` table written by EVT-005 and, once PTY-001 ships, from the

#### 4.1.1 `haversine_km`

```python
import math

def haversine_km(lat1: float, lng1: float, lat2: float, lng2: float) -> float:
    """
    Returns the great-circle distance in kilometres between two points
    given as (latitude, longitude) pairs in decimal degrees.

    Uses the Haversine formula:
      a = sin²(Δlat/2) + cos(lat1)·cos(lat2)·sin²(Δlng/2)
      c = 2·atan2(√a, √(1−a))
      d = R·c   where R = 6371.0 km (mean Earth radius, IUGG)

    Precision: suitable for distances from < 1 m to > 10 000 km.
    Pure Python, no third-party dependencies.
    """
    R = 6371.0
    phi1 = math.radians(lat1)
    phi2 = math.radians(lat2)
    dphi = math.radians(lat2 - lat1)
    dlambda = math.radians(lng2 - lng1)
    a = math.sin(dphi / 2) ** 2 + math.cos(phi1) * math.cos(phi2) * math.sin(dlambda / 2) ** 2
    return R * 2 * math.atan2(math.sqrt(a), math.sqrt(1 - a))
```

#### 4.1.3 `proximity_search`

```python
def proximity_search(
    user_sub: str,
    center_lat: float,
    center_lng: float,
    radius_km: float,
    limit: int = 50,
    entity_type: str = "address",
) -> list[dict]:
    """
    Returns items within radius_km of (center_lat, center_lng), sorted
    by distance ascending, up to `limit` results.

    entity_type="address" (default, always available):
      Queries T.addresses keyed on user_sub, collects items that have
      both 'lat' and 'lng', applies haversine_km filter, sorts, slices.

    entity_type="party" (post-PTY-001):
      Operates on T.party when the table handle is present; skips and
      returns [] when T.party is absent (hasattr guard, same pattern as
      geocode_party_address in EVT-005).

    Returns list of dicts with keys:
      - entity_type: str            ("address" or "party")
      - entity_id: str              (address_id or party_id)
      - name: str                   (label/display_name; address line1 for addresses)
      - lat: float
      - lng: float
      - distance_km: float          (rounded to 3 decimal places)
      - address_id: str | None      (present for entity_type="address")
      - city: str | None
      - country: str | None

    Raises ValueError for invalid entity_type.
    Returns [] when S.crm_proximity_search_enabled or
    S.crm_geocoding_enabled is False (callers should check the flag
    before calling, but defensive check here too).
    """
```

**Internal flow for `entity_type="address"`**:

1. Guard: return `[]` if `not S.crm_proximity_search_enabled or not S.crm_geocoding_enabled`.
2. Validate `0 <= radius_km <= S.crm_proximity_search_max_radius_km`; raise `ValueError` otherwise.
3. Fetch all address items for the user via a paginated `query` loop on `T.addresses` (PK=`user_sub`),
   same pattern as `list_geocoded_addresses` from EVT-005. Collect all pages (no DDB-level filter on
   coordinates, per CLAUDE.md gotcha on `FilterExpression`).
4. Filter: retain only items where `"lat" in item and "lng" in item`.
5. Compute `distance_km = haversine_km(center_lat, center_lng, float(item["lat"]), float(item["lng"]))`.
6. Filter: retain only items where `distance_km <= radius_km`.
7. Sort ascending by `distance_km`.
8. Slice to `limit` items.
9. Return list of result dicts as specified above.

**Pydantic models** (added to `app/models.py`):

```python
class ProximityResultItem(BaseModel):
    entity_type: str
    entity_id: str
    name: str
    lat: float
    lng: float
    distance_km: float
    address_id: Optional[str] = None
    city: Optional[str] = None
    country: Optional[str] = None

class ProximitySearchOut(BaseModel):
    results: list[ProximityResultItem]
    count: int
    center_lat: float
    center_lng: float
    radius_km: float
    entity_type: str
```

**Handler behaviour**:

1. Call `_require_proximity_enabled()`.
2. Validate `lat` in `[-90, 90]` and `lng` in `[-180, 180]`; raise `HTTPException(400)` otherwise.
3. Validate `0 < radius_km <= S.crm_proximity_search_max_radius_km`; raise `HTTPException(400)` otherwise.
4. Clamp `limit` to `[1, 200]`.
5. Call `rate_limit_proximity_search(user_sub)`.
6. Call `proximity_search(user_sub, lat, lng, radius_km, limit, entity_type)`. Catch `ValueError`
   (invalid `entity_type`) and re-raise as `HTTPException(400)`.
7. Best-effort audit: `try: audit_event("crm_proximity_search", user_sub, request=request, lat=lat, lng=lng, radius_km=radius_km, result_count=len(results)) except Exception: pass`.
8. Return `ProximitySearchOut(results=results, count=len(results), ...)`.

## 5. Detailed Behavior & Edge Cases

### 5.1 `radius_km=0` returns empty list

The filter `distance_km <= radius_km` with `radius_km=0` passes only points at the exact centre
(distance=0.0). In practice the mock geocoding rounds to 6 decimal places so the chance of an exact
match is negligible; the result will be `[]`. The endpoint returns 200 with `count=0` rather than a
special status code.

### 5.2 `radius_km=20000` returns all geocoded addresses

20 000 km exceeds the Earth's maximum great-circle distance (~20 015 km). With the default
`CRM_PROXIMITY_SEARCH_MAX_RADIUS_KM=20000.0`, a caller can retrieve all geocoded addresses by passing
`radius_km=20000`. The result set is bounded by `limit` (max 200) and the number of geocoded addresses
the user has, not by an arbitrary scan limit.

### 5.3 No geocoded addresses

If the user has no addresses with `lat`/`lng` (EVT-005 geocoding never ran, or the feature was off
when addresses were created), `proximity_search` returns `[]` (200, `count=0`). No error.

### 5.4 `entity_type="party"` before PTY-001 ships

When `entity_type="party"` is requested and `T.party` is not present (i.e., `not hasattr(T, "party")
or T.party is None`), `proximity_search` returns `[]`. This matches EVT-005's `geocode_party_address`
soft-dependency pattern and avoids a hard failure that would block EVT-007 testing in the interim.
Once PTY-001 merges and `T.party` is populated with geocoded party items, the same code path returns
real results without modification.

### 5.5 Unsupported `entity_type` values

Any `entity_type` value other than `"address"` or `"party"` causes `proximity_search` to raise
`ValueError("Unknown entity_type: {entity_type}")`. The handler catches this and raises
`HTTPException(400, detail=str(e))`. Future entity types (e.g., `"account"`, `"lead"`) are added by
extending the `if/elif` chain in `proximity_search` — no schema migration required.

### 5.6 Haversine at antipodal points

For two points exactly opposite each other on the Earth (distance ≈ 20 015 km), `a = 1.0` exactly,
`math.sqrt(1 - a) = 0.0`, and `math.atan2(1.0, 0.0) = π/2`. The result is `6371.0 * π ≈ 20 015 km`.
This is numerically stable because `atan2` is defined for `(1, 0)`.

### 5.7 Float precision and `Decimal` conversion

Items returned by boto3 from a DynamoDB table carry `lat`/`lng` as `decimal.Decimal`. The service
casts `float(item["lat"])` and `float(item["lng"])` before calling `haversine_km`. Python's `float`
is IEEE 754 double (64-bit), which provides ~7 significant decimal digits of latitude precision —
adequate for sub-metre accuracy. The `_FloatSafeTable` wrapper (`app/core/tables.py:29–62`) coerces
Python `float` to `Decimal` on writes, but reads return `Decimal` from DDB; the explicit `float()`
cast in the service is the correct read-side conversion.

### 5.8 Performance: per-user address scan

The `addresses` table is keyed on `user_sub`. A query for one user returns only that user's items.
Platform users typically have a small number of addresses (1–10). Even at 1000 addresses the full scan
per request completes in milliseconds. A GSI on `lat`/`lng` would not help because DynamoDB cannot
express radius queries natively; the full fetch + Python filter is the correct approach. The `limit`
parameter (max 200) caps the response size, not the DDB scan.

### 5.9 Rate limiting details

The `_bucket_limit` helper (`app/services/rate_limit.py:60`) writes a sliding-window counter to
`T.sessions` using a synthetic `session_id = f"prox_search:{user_sub}"`. Defaults: 30 calls per 60 s.
Both values are env-configurable. When `T.sessions` is unavailable (e.g., DDB local not running),
`_bucket_limit` returns `True` (allow), consistent with its `_sessions_table_enabled()` guard at line
61.

### 5.10 Audit event

The audit call uses best-effort `try/except` so a DDB write failure in the `alerts` table never
surfaces as a 500 to the caller. The event name is `"crm_proximity_search"` with fields `lat`, `lng`,
`radius_km`, `result_count`. This is consistent with how EVT-005 emits `"crm_address_geocoded"` via
`audit_event` (`app/services/alerts.py:644`).

### 5.11 `limit` boundary clamping

`limit` values below 1 are clamped to 1; values above 200 are clamped to 200. The clamp happens in the
handler (not in the service) so that the service function is usable by internal callers with larger
limits. The handler's 200-item cap prevents response payloads from becoming unwieldy before EVT-007's
map view adds its own pagination.

## 6. Feature Flag & Config

| Settings key | Env var | Default | Purpose |
|---|---|---|---|
| `crm_proximity_search_enabled` | `CRM_PROXIMITY_SEARCH_ENABLED` | `false` | Master gate for this ticket; routes return 404 when off |
| `crm_geocoding_enabled` | `CRM_GEOCODING_ENABLED` | `false` | Also required; owned by EVT-005 |

The flag is checked in two places:

1. `_require_proximity_enabled()` in `app/routers/crm_maps.py` — raises `HTTPException(404)` on the
   first line of every handler. With `CRM_PROXIMITY_SEARCH_ENABLED=0` no DDB reads, no Haversine
   arithmetic, and no audit writes occur.
2. Defensive check at the top of `proximity_search()` in the service — returns `[]` immediately. This
   allows internal callers to call the service safely even before checking the flag themselves.

When `CRM_PROXIMITY_SEARCH_ENABLED=1` but `CRM_GEOCODING_ENABLED=0`, the guard also returns 404 because
no `lat`/`lng` data exists to search over. Both flags must be `1` for the feature to be active.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007: same code path in all environments

There are no `if S.dev_mode` branches in EVT-006. The mock geocoding introduced by EVT-005 is
activated by `S.crm_geocoding_provider_url == ""` (i.e., the absence of a real provider URL), not by
`S.dev_mode`. Consequently the Haversine arithmetic, DDB query, rate-limit write, and audit write all
execute identically in dev (against DynamoDB Local on port 8001) and in production (against real
DynamoDB). This is consistent with how the KYC partner-API proximity-adjacent work (`GAP-0286`) and
the newsfeed recsys (`NRS-001..010`) avoid dev-mode branches.

### 7.2 Idempotency

`GET /ui/crm/maps/contacts/proximity` is a read-only endpoint. Repeated calls with the same parameters
return the same result set (deterministic because EVT-005's mock geocoder is deterministic). The only
side effects are the rate-limit counter increment and the best-effort audit write, both of which are
intentionally not idempotent. The read itself has no mutating side effects.

### 7.3 Ownership and data isolation

The `proximity_search` function queries `T.addresses` with `KeyConditionExpression: Key("user_sub").eq(user_sub)`
where `user_sub` is the authenticated caller's subject. DynamoDB's partition key enforces strict
per-user isolation — a caller cannot retrieve another user's address coordinates. The `entity_type="party"`
path (post-PTY-001) must apply the same ownership filter when it queries `T.party`.

### 7.4 Coordinate leakage prevention

The response includes `lat`, `lng`, and `distance_km` for items the caller already owns (their own
address book). No cross-user coordinate data is ever exposed. The `entity_type="party"` path must
be similarly scoped: only parties owned by or visible to `user_sub` (enforced by the PTY layer's access
control) should be returned.

### 7.5 Unbounded radius protection

`S.crm_proximity_search_max_radius_km` (default 20 000 km, env-configurable) caps the `radius_km`
parameter. An operator who wants to prevent global scans can lower this to e.g. 500 km. Values above
the cap return 400, not a full table scan.

### 7.6 Input sanitisation

`lat` and `lng` query parameters are typed `float` by FastAPI's query-param validation. Out-of-range
values (`lat > 90`, `lat < -90`, `lng > 180`, `lng < -180`) are rejected with 400 before any DDB
interaction. Non-numeric strings are rejected by FastAPI's type coercion with 422.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact when flags are off

With `CRM_PROXIMITY_SEARCH_ENABLED=0` (the default), no new routes exist at the HTTP layer (all return
404), no DDB reads occur, and no changes to existing service functions are made. The platform is
byte-for-byte identical to its pre-EVT-006 state.

### 8.2 Additive service extension only

EVT-006 adds two new functions (`haversine_km`, `proximity_search`) and one wrapper
(`rate_limit_proximity_search`) to the existing `app/services/crm_geocoding.py`. No existing function
in that file is modified. The two new Pydantic models (`ProximityResultItem`, `ProximitySearchOut`)
are added to `app/models.py` without touching any existing model.

### 8.3 No DynamoDB schema changes

No new tables, no new GSIs, no `attr_types` changes to `scripts/local-ddb-init.py`. Running
`just restart` after merging EVT-006 leaves all existing tables intact. The new settings fields in
`app/core/settings.py` all have safe defaults (the feature is off).

### 8.4 EVT-007 compatibility

EVT-007 (Map view frontend) consumes `GET /ui/crm/maps/contacts/proximity`. The response shape
`ProximitySearchOut.results[*]` is designed to be stable: the required fields (`entity_id`, `name`,
`lat`, `lng`, `distance_km`) are present for both `"address"` and `"party"` entity types, so the
Leaflet pin-rendering code in EVT-007 does not need to branch on entity type. Additional optional
fields (`address_id`, `city`, `country`) are surfaced in the `Popup` component.

### 8.5 PTY-001 forward compatibility

When PTY-001 ships and `T.party` becomes available, `proximity_search` with `entity_type="party"`
automatically becomes functional with no code change — the `hasattr(T, "party")` guard evaluates to
`True` and the existing `elif entity_type == "party"` branch executes. No migration or feature-flag
bump is needed.

## 10. Open Questions / Assumptions

1. **Admin visibility of all users' contacts**: The current design scopes each proximity search to the
   authenticated caller's own address book. A future admin-level endpoint (ADMIN or ROOT role) could
   scan across all users' geocoded addresses — for example, to find all platform users near a given
   event venue. That is explicitly out of scope for EVT-006 and should be a separate ticket with
   appropriate security review.

2. **`entity_type="contact"` vs `entity_type="address"`**: The ticket source says "contacts/accounts"
   but the platform's contacts (`T.contacts`) store only `user_sub` opaque IDs with no address fields
   (`app/routers/contacts.py:101-109`). The queryable geocoded data today lives in `T.addresses`.
   This spec uses `entity_type="address"` for the live path and reserves `"party"` for PTY. If the
   team wants the URL to say `/contacts/proximity` but the underlying data to be addresses, the path
   segment is cosmetic; the response correctly labels results as `entity_type="address"`.

3. **Cross-user proximity**: The current design only searches the caller's own geocoded addresses.
   SuiteCRM's Maps module searches all geocoded contacts/accounts regardless of owner. A multi-user
   search would require a GSI on the `addresses` table (or a global scan) and raises PII concerns.
   Deferred to a follow-on ticket.

4. **Assumption — `addresses` table column names**: This spec assumes the `addresses` table item
   shape used by `app/services/addresses.py` (PK=`user_sub`, SK=`address_id`, fields include `line1`,
   `city`, `state`, `postal_code`, `country` — verified at `app/services/addresses.py:42,44-47`; the
   field is `line1` with **no** underscore). The `name` field projection in `proximity_search` uses
   `item.get("line1") or item.get("address_id")`.

5. **Nominatim / real provider**: EVT-005 notes that Nominatim requires a self-hosted or licensed
   instance for production. EVT-006 inherits this assumption unchanged. The proximity search itself
   is purely computational (no external calls) — only the upstream geocoding write (EVT-005) touches
   an external API.
