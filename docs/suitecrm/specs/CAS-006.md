# CAS-006 — Case file attachment upload and download

## 1. Summary & Goal

Add first-class file attachment support to the support-ticket lifecycle. Agents and ticket owners can attach arbitrary files to a ticket (screenshots, logs, PDFs, archives) via a multipart upload endpoint. Uploaded files are persisted to S3 and their metadata written as sub-items inside the existing `tickets` DynamoDB table. Callers can retrieve per-ticket attachment lists with time-limited presigned URLs for download, and admin-only soft-delete hides attachments without removing the S3 object (preserving the audit trail).

When the master feature flag `S.crm_cases_enabled` is off (the default), all new endpoints return 404 and no new DynamoDB sub-items are written. The existing `tickets` table, all pre-existing routes, and every non-flag-gated service path remain byte-for-byte unchanged.

## 2. Context & Current State

**Tickets table and partition key scheme** (`app/services/tickets.py:164-177`): every ticket lives in a single DynamoDB partition keyed `pk = "TICKET#{ticket_id}"`. Sub-items carry different SK prefixes: messages use `MSG#{ts:013d}#{message_id}` (line 172), activities use `ACT#{ts:013d}#{activity_id}` (line 176), and the META header uses SK `"META"` (line 168). There is no `ATTACH#` prefix today; this ticket introduces it.

**`TicketStore.get_ticket`** (`app/services/tickets.py:522-566`): reads the META header via `get_item`, then two prefix scans for `MSG#` and `ACT#` via `_query_partition_prefix` (line 514). It returns a plain dict with `messages` and `activity` list fields. There is no `attachments` key today.

**`TicketStore.create_ticket`** (`app/services/tickets.py:411-512`): writes at minimum three items on creation (META, one `MSG#` item for the description, one `ACT#` activity), plus one additional label-index sub-item per label in the `labels` list (`entity_type="ticket_label_index"`). The META row carries six GSI projections for owner/status/assignee/space indexes (plus space-status and space-assignee). No attachment-related keys are present.

**`_conditional_update_meta`** (`app/services/tickets.py:723-790`): the optimistic-locking update path for ticket headers. Attachment sub-items do not go through this path; they are written with independent `put_item` calls (same pattern as `MSG#` and `ACT#` sub-items), so they never interfere with version-gated header updates.

**Auth helpers** (`app/routers/tickets.py:207-341`): `_is_admin(user)` (line 207) checks `Role.ADMIN` or `Role.ROOT`; `_is_admin_actor(request, user)` (line 224) additionally accepts `tickets:admin` API-key scope; `_can_access_ticket(request, user, ticket)` (line 339) allows owner **or** admin. All require `Depends(require_ui_session)` from `app/services/sessions` (line 19). These helpers are reused unchanged for the new attachment endpoints.

**S3 upload pattern** (`app/services/kyc_partner_api.py:468-509`): `_store_document_bytes` calls `app.core.aws_clients.s3_client().put_object(...)` (line 497) via a lazy import inside a `try/except`, making the call best-effort for transient failures. In dev mode it returns a `/mock/s3/{bucket}/{key}` URL (line 508). In prod the same code path runs against real S3 with no `dev_mode` branch (SECOPS-007 parity). This is the canonical S3-upload primitive to reuse verbatim.

**Presigned URL generation** (`app/services/kyc_partner_api.py:583-640`): `get_document_download` uses `s3_client().generate_presigned_url("get_object", Params=..., ExpiresIn=300)` (line 636) in prod, and returns the `/mock/s3/...` URL in dev (line 631). Same 300-second TTL is appropriate here.

**`s3_client()` factory** (`app/core/aws_clients.py:114-122`): returns a boto3 S3 client with dev-mode-aware endpoint resolution (moto in-process when `S.dev_mode`, real S3 otherwise). No new client factory is needed.

**Audit events** (`app/services/alerts.py:644`): `audit_event(event, user_sub, request, **fields)` writes to the alerts DDB table. `_emit_ticket_alerts` (`app/routers/tickets.py:362`) wraps this for ticket-specific calls in the router layer. NOTE: `app/services/tickets.py` does not currently import `audit_event`; the new `add_attachment` and `delete_attachment` service methods must add `from app.services.alerts import audit_event` to use it directly (same pattern as other service files). The router-layer `_emit_ticket_alerts` is not appropriate for service-layer calls.

**Settings scaffolding** (CAS-001): `S.crm_cases_enabled`, `S.crm_cases_attachments_bucket` (default `"local-uploads"`), and `S.crm_cases_attachments_s3_prefix` (default `"ticket-attachments/"`) are defined in CAS-001. At the time CAS-006 ships, if CAS-001 has not yet landed, these three settings must be added here (they are non-breaking additions).

**Existing file size pattern** (`app/routers/bulk_payout_tools.py:163-164`): `if len(file_bytes) > _CSV_MAX_BYTES: raise HTTPException(status_code=413, ...)`. The same inline read-then-size-check pattern is used throughout the codebase; it is replicated for attachments with a 10 MB limit.

**No attachment sub-items exist today**: searching `app/services/tickets.py` and `app/routers/tickets.py` for `ATTACH#` returns zero results. The `TicketOut` Pydantic model (`app/routers/tickets.py:58-72`) has no `attachments` field. The `Ticket` TypeScript interface (`frontend/src/api/endpoints/tickets.ts:23-38`) has no attachment fields.

**`FilePickerDialog` component** (`frontend/src/pages/messages/FilePickerDialog.tsx`): a shared file-picker dialog used by `ComposeBar` (line 30 of `ComposeBar.tsx`) and `CreatePost` (`frontend/src/pages/feed/CreatePost.tsx:26`). CAS-006 does not need to use this component; it adds a simpler native `<input type="file">` in the ticket detail panel since tickets attach arbitrary binary files rather than picking from the in-app file manager.

## 3. Data Model

### DynamoDB — `tickets` table (existing, reused)

CAS-006 adds a new SK-prefix family to the existing `tickets` table. No new table is required. The table is defined in `scripts/local-ddb-init.py` at line 695 (`TableDef(_resolve_table_name(S.tickets_table_name, "tickets"), "pk", "sk", gsi=[...])`).

**New sub-item type: attachment**

| Attribute | Type | Description |
|-----------|------|-------------|
| `pk` | S | `TICKET#{ticket_id}` — same partition as the ticket header |
| `sk` | S | `ATTACH#{ts:013d}#{attach_id}` — zero-padded 13-digit ms epoch + unique ID enables lexicographic time-ordering and prefix queries |
| `entity_type` | S | `"ticket_attachment"` |
| `ticket_id` | S | Bare ticket ID (de-normalised for easier projection) |
| `attach_id` | S | `att_{uuid4().hex[:16]}` |
| `s3_key` | S | Full S3 object key written by `_store_attachment_bytes` |
| `bucket` | S | S3 bucket name (from `S.crm_cases_attachments_bucket`) |
| `filename` | S | Sanitised original filename (`re.sub(r"[^A-Za-z0-9._-]", "_", ...)`) |
| `content_type` | S | MIME type from `UploadFile.content_type` (default `application/octet-stream`) |
| `size_bytes` | N | Byte length of uploaded content |
| `description` | S | Optional caller-supplied description (max 500 chars) |
| `uploader_sub` | S | `user.sub` of the uploading principal |
| `created_at` | N | `now_ts()` integer Unix seconds |
| `deleted_at` | N | Set on soft-delete; absent otherwise |

**SK format rationale**: `ATTACH#{ts:013d}#{attach_id}` mirrors the existing `MSG#` and `ACT#` patterns at `app/services/tickets.py:172-177`. The `{ts:013d}` format zero-pads a `now_ts()` Unix-**second** integer (≈10 digits today) to 13 characters, matching `_msg_sk` and `_act_sk` exactly. This provides correct lexicographic sort without a GSI. NOTE: `now_ts()` returns seconds (`app/core/time.py:3`), not milliseconds — the value is not "Unix seconds × 1000"; the zero-padding merely aligns future-proof capacity to 13 chars.

**No new GSI is required.** Attachments are always fetched by ticket partition (`pk = TICKET#{ticket_id}`, `sk begins_with ATTACH#`), which is a base-table key-condition query — the same pattern as `_query_partition_prefix` at line 514 of `app/services/tickets.py`.

**`scripts/local-ddb-init.py`**: No changes required. The `tickets` table already exists with its 10 GSIs. New attachment sub-items fit within the existing partition; no new attributes require GSI registration. The `created_at` attribute is already numeric on the `MSG#` and `ACT#` sub-items, so no new `attr_types` entry is needed.

**S3 object key format**:
```
{S.crm_cases_attachments_s3_prefix}{ticket_id}/{attach_id}/{safe_filename}
```
Example: `ticket-attachments/tkt_abc123/att_def456xyz/screenshot_001.png`

## 4. API / Service Design

### Service layer (`app/services/tickets.py` additions)

**Helper `_attach_sk(ts: int, attach_id: str) -> str`**
```python
def _attach_sk(ts: int, attach_id: str) -> str:
    return f"ATTACH#{ts:013d}#{attach_id}"
```
Mirrors `_msg_sk` and `_act_sk` at lines 172 and 176.

**Helper `_store_attachment_bytes(...) -> dict[str, Any]`**
```python
def _store_attachment_bytes(
    *,
    ticket_id: str,
    attach_id: str,
    filename: str,
    content_type: str,
    contents: bytes,
) -> dict[str, Any]:
```
Verbatim port of `kyc_partner_api._store_document_bytes` (`app/services/kyc_partner_api.py:468-509`), substituting `S.crm_cases_attachments_bucket` and `S.crm_cases_attachments_s3_prefix`. Returns `{"s3_key": str, "bucket": str}` plus a dev-mode `"url"` key. Lazy-imports `app.core.aws_clients.s3_client` inside a `try/except` (best-effort on transient S3 failures).

**`TicketStore.add_attachment`**
```python
def add_attachment(
    self,
    *,
    ticket_id: str,
    uploader_sub: str,
    filename: str,
    content_type: str,
    size_bytes: int,
    contents: bytes,
    description: str | None = None,
) -> dict[str, Any]:
```
Raises `HTTPException(404)` if `self.get_ticket(ticket_id)` returns `None`. Generates `attach_id = f"att_{uuid.uuid4().hex[:16]}"`, calls `_store_attachment_bytes(...)`, writes the DDB sub-item via `self._table.put_item(...)`, emits `audit_event("ticket_attachment_uploaded", uploader_sub, ...)`. Returns the sub-item dict.

**`TicketStore.list_attachments`**
```python
def list_attachments(self, ticket_id: str, *, include_deleted: bool = False) -> list[dict[str, Any]]:
```
Calls `_query_partition_prefix(ticket_id=ticket_id, sk_prefix="ATTACH#")`. Filters out items where `deleted_at` is set unless `include_deleted=True`. Returns list ordered by `created_at` ascending (sub-items already arrive in SK lexicographic order from `_query_partition_prefix`'s `ScanIndexForward=True`).

**`TicketStore.delete_attachment`**
```python
def delete_attachment(self, ticket_id: str, attach_id: str, *, actor_sub: str) -> bool:
```
Resolves the full SK prefix by scanning `list_attachments(ticket_id, include_deleted=True)` for an item with `attach_id == attach_id`. If not found returns `False`. Uses `update_item` with `SET deleted_at = :ts` (no conditional needed since soft-delete is idempotent). Emits `audit_event("ticket_attachment_deleted", actor_sub, ...)`. Returns `True`.

**`TicketStore.get_ticket` extension** (line 522): after fetching `messages` and `activities`, add:
```python
attachments_raw = self._query_partition_prefix(ticket_id=ticket_id, sk_prefix="ATTACH#")
```
Filter out soft-deleted items (`item.get("deleted_at")` is truthy). Map each to an `AttachmentOut`-compatible dict including a `url` field — dev: `/mock/s3/{bucket}/{s3_key}`; prod: 300-second presigned URL via `s3_client().generate_presigned_url(...)`. Include the list in the returned dict under key `"attachments"`. This is guarded: `if not S.crm_cases_enabled: return []` so no query runs with the flag off.

## 5. Detailed Behavior & Edge Cases

**File size enforcement**: The backend reads the full multipart body with `await file.read()` and then checks `len(contents) > S.crm_cases_attachment_max_bytes`. If exceeded: `raise HTTPException(status_code=413, detail={"code": "attachment_too_large", "message": f"File exceeds maximum size of {S.crm_cases_attachment_max_bytes} bytes"})`. The frontend performs an identical check before issuing the request and shows a `toast.error` without making a network call.

**Filename sanitisation**: `safe_filename = re.sub(r"[^A-Za-z0-9._-]", "_", filename or "upload.bin")` (mirrors `kyc_partner_api._store_document_bytes:489`). An empty `filename` field from `UploadFile.filename` defaults to `"upload.bin"`.

**Content-type**: taken from `file.content_type or "application/octet-stream"`. The platform does not restrict MIME types; any file type is accepted.

**Duplicate filenames**: not rejected. Each attachment gets a unique `attach_id`, so `ticket_id/attach_id/filename` S3 keys are always distinct even if the same filename is uploaded twice.

**S3 write failure**: the `try/except` in `_store_attachment_bytes` logs a warning and continues. The DDB sub-item is still written with `s3_key` set (the key that would have been used), preserving referential integrity. A follow-up admin tool or retry can re-upload to that key. This matches the behavior of `kyc_partner_api._store_document_bytes:503-504`.

**Soft delete and audit trail**: `DELETE /tickets/{id}/attachments/{attach_id}` sets `deleted_at` on the DDB item and does **not** call `s3_client().delete_object(...)`. The S3 object is retained forever for compliance. Only items with `deleted_at` absent are returned by `list_attachments` and included in `get_ticket`. Admin calls `list_attachments(include_deleted=True)` via a separate internal helper (not exposed as an endpoint in this ticket).

**Presigned URL TTL**: 300 seconds, matching the KYC partner API pattern (`kyc_partner_api.py:636`). The frontend should not cache URLs beyond 240 seconds; React Query's `staleTime` for the attachments query should be set to `200_000` ms.

**Race condition on ticket deletion**: if a ticket is soft-deleted or merged (CAS-010) while an upload is in flight, `add_attachment` calls `self.get_ticket(ticket_id)` first. If `get_ticket` returns `None` the method raises 404 before touching S3. If the ticket is deleted between the check and the S3/DDB write, the orphaned S3 object is unreachable but harmless (S3 lifecycle rules can clean it up).

**`get_ticket` performance**: the new `_query_partition_prefix(sk_prefix="ATTACH#")` call runs only when `S.crm_cases_enabled` is `True`. Each prefix scan is a key-condition query (no FilterExpression), so it is O(items in partition with that prefix) — acceptable for the expected volume per ticket. The three sub-queries (MSG#, ACT#, ATTACH#) are sequential; a future optimisation could batch them but is out of scope.

**Uploader permission**: `_can_access_ticket(request, user, ticket)` allows both the ticket owner and any admin to upload. Arbitrary third-party users cannot upload to tickets they do not own. This mirrors the add-message permission check at `app/routers/tickets.py:958`.

**Zero-byte files**: `size_bytes=0` is stored and `len(contents) == 0` is allowed (no lower-bound check). `put_object` with an empty body is valid S3.

**Flag-off guard on `get_ticket`**: the `attachments` sub-query is wrapped: `if not S.crm_cases_enabled: return []`. This means with the flag off, `TicketOut.attachments` is always `[]` and no `ATTACH#` prefix scan is issued.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity**: the single code path for S3 writes and reads (`_store_attachment_bytes`, presigned URL generation) uses the `app.core.aws_clients.s3_client()` factory, which transparently points to the in-process moto mock in dev (`app/core/aws_clients.py:79-83`: when `S.dev_mode` is true the S3 endpoint URL is `None`, so botocore's moto intercept activates) and to real S3 in prod. There is no `if S.dev_mode` branch in the service layer — only a dev-mode `url` shortcut in the response projection (same pattern as `kyc_partner_api.py:630-631`).

**Idempotency**: attachment uploads are not idempotent by design — repeated uploads of the same file create additional sub-items (same as multiple messages). Each `attach_id` is a freshly generated `uuid4` hex, so retrying a failed upload creates a second item. The frontend should display a spinner during upload and disable the upload button until the mutation settles.

**Ownership enforcement**: `_can_access_ticket` gates upload on owner or admin. The list and delete endpoints separately enforce the same check. An attacker who knows a `ticket_id` but is not the owner and is not an admin will receive 403 on all three endpoints.

**S3 path traversal prevention**: `safe_filename = re.sub(r"[^A-Za-z0-9._-]", "_", ...)` strips all characters except alphanumerics, dots, hyphens, and underscores. Combined with the `ticket_id/attach_id/` prefix, the resulting S3 key cannot traverse outside the ticket's prefix.

**No signed-URL leakage**: presigned URLs are generated on-demand per `GET /tickets/{id}/attachments` call and never persisted to DynamoDB. TTL is 300 seconds, matching the KYC precedent.

**Content-type sniffing**: the stored `content_type` comes from the client-supplied `UploadFile.content_type`. In prod, S3 serves the stored `ContentType` header; there is no server-side content sniffing. The frontend renders download links that open in a new tab (`target="_blank"`), so even an incorrectly declared content type does not execute scripts in the platform origin.

**Audit trail**: every upload and soft-delete emits an `audit_event` via `app/services/alerts.audit_event` (`alerts.py:644`). The event payload includes `ticket_id`, `attach_id`, `filename`, `size_bytes`, `uploader_sub` (or `actor_sub` for delete). These are written to the alerts DDB table and survive the 300-second presigned URL TTL.

## 8. Backward Compatibility & Migration

**No data migration required.** The `tickets` table exists and the new `ATTACH#` sub-items fit within the existing partition scheme without any schema change or `UpdateTable` call. `scripts/local-ddb-init.py` is unchanged.

**`TicketOut.attachments` is additive.** The new field carries a default of `[]`. All existing JSON consumers that deserialise `TicketOut` will receive an empty list and ignore it unless they opt in. No existing Pydantic validator or TypeScript interface breaks.

**Rollback**: disabling `CRM_CASES_ENABLED` after some attachments have been uploaded leaves `ATTACH#` rows in DynamoDB and objects in S3. These are inert — no existing code path reads or touches them. Re-enabling the flag makes them visible again. Physical cleanup of orphaned rows (if desired) can be performed offline with a one-off DDB scan filtered to `entity_type = "ticket_attachment"`.

**CAS-010 (merge)**: when CAS-010 ships, `TicketStore.merge_ticket` must copy `ATTACH#` sub-items from the source partition to the target partition via batch writes. The sub-item schema documented in Section 3 provides all the fields needed for that copy. CAS-010 already lists CAS-006 as a dependency.

## 10. Open Questions / Assumptions

1. **Multi-file upload**: the spec's POST endpoint accepts one `UploadFile` per request, matching the KYC partner API and the ticket description. If multiple simultaneous uploads are needed, the frontend calls the endpoint once per file (parallel requests). A multi-file batch endpoint is a follow-up.

2. **CAS-001 landing order**: CAS-006 depends on `S.crm_cases_enabled`, `S.crm_cases_attachments_bucket`, and `S.crm_cases_attachments_s3_prefix` from CAS-001. If CAS-001 has not yet merged, CAS-006's PR must add those three settings inline; they are fully non-breaking additions. The spec assumes CAS-001 is merged first (listed as a hard dependency).

3. **`local-uploads` bucket in dev**: the dev moto environment creates `local-uploads` in `app/core/dev_s3.py` at startup. CAS-006 reuses this bucket for dev without any additional bucket-creation step. In prod, `CRM_CASES_ATTACHMENTS_BUCKET` must be set to a pre-existing bucket.

4. **Attachment count limit**: the ticket description does not impose a maximum number of attachments per ticket. A future hardening step could add a configurable cap (e.g., 50 per ticket) to prevent runaway storage, but it is not required for MVP.

5. **Content-type allow-list**: the spec does not restrict MIME types. If the security team requires blocking executables (`.exe`, `.sh`) this can be added as a `content_type_denylist` setting in a follow-up.

6. **S3 lifecycle / retention**: S3 object retention policy (e.g., 7-year audit hold) is an infrastructure concern outside this ticket. The service never calls `delete_object`.
