# CAS-009 — Case escalation — manual and rule-based

**Type:** Feature | **Priority:** P1 | **Estimate:** 2d
**Parent area:** CRM Cases, Customer Support & Customer Portal
**Depends on:** CAS-001 (flag + `crm_cases_sla_config` table), CAS-007 (watcher list for alert fan-out), CAS-008 (SLA breach hook that triggers auto-escalation)

---

## 1. Summary & Goal

Add a case escalation capability to the support ticket system. Escalation elevates a ticket to a higher-priority handling tier and notifies relevant parties. Two paths are supported:

- **Manual escalation** — an admin calls `POST /tickets/{ticket_id}/escalate` with a reason and an optional reassignment target. `escalation_level` increments by 1 and relevant parties are notified.
- **Auto-escalation** — when `TicketSlaService.check_breaches` (introduced by CAS-008) detects a ticket has breached its SLA deadline and `escalation_level == 0`, it calls `TicketStore.escalate_ticket` with `actor_sub="system_sla_escalation"`. Subsequent SLA ticks (while the ticket remains open and breached) increment the level further, enabling a configurable escalation chain up to `CRM_CASES_MAX_ESCALATION_LEVEL` (default 3).

The feature is strictly additive. With `CRM_CASES_ENABLED=0` (the default) the platform is byte-for-byte unchanged: no new routes are registered, no new DynamoDB attributes are written, and the SLA breach hook is a no-op.

## 3. Data Model

### No new DynamoDB tables

CAS-009 stores all escalation state as additive attributes on the existing `tickets` table (PK=`TICKET#{ticket_id}`, SK=`META`). No new tables, no new GSIs, no `scripts/local-ddb-init.py` changes.

### New META row attributes

| Attribute | DDB Type | Default | Description |
|-----------|----------|---------|-------------|
| `escalation_level` | N | 0 (absent = 0) | Counter incremented on each escalation. |
| `escalated_at` | N | absent | Unix timestamp of the most recent escalation. |
| `escalated_by` | S | absent | `user_sub` or `"system_sla_escalation"` of the actor who most recently escalated. |
| `escalated_to_sub` | S | absent | Optional; the `user_sub` the ticket was reassigned to on manual escalation. |
| `escalation_reason` | S | absent | Human-readable reason string from the most recent escalation. |
| `breach_alerted_at` | N | absent | Unix timestamp of the last SLA-breach alert (written by CAS-008's `check_breaches`). Consumed by `escalate_ticket` to enforce the once-per-breach idempotency guard. |

**Initialization**: None of these attributes are written at `create_ticket` time. `get_ticket` reads them with `header.get("escalation_level", 0)` (int coercion) and `header.get(field)` for the optional string/timestamp fields.

**Write pattern**: `escalate_ticket` issues a single `update_item` with `ADD escalation_level :one` plus `SET escalated_at, escalated_by, escalated_to_sub, escalation_reason, updated_at`. The ADD expression increments the counter atomically — no read-modify-write is needed and no `version` bump occurs (escalation is an administrative annotation, not a versioned state transition, as described in the `kyc_cases.escalate_case` docstring at `kyc_cases.py:750-761` and confirmed by the absence of a `version` field in its `UpdateExpression` at `kyc_cases.py:782`).

**Conditional expression**: The `ConditionExpression` on `escalate_ticket` asserts the ticket is in an active status (`open | in_progress | waiting_on_user`) and that `escalation_level < :max_level`. This prevents:
1. Escalating a closed or terminal ticket.
2. Escalating beyond the configured maximum level.

**`ConditionalCheckFailedException` handling**: Swallowed gracefully — the method re-reads and returns the current ticket (same as `kyc_cases.escalate_case:796-803`).

**Activity sub-item**: Each successful escalation writes an `ACT#` activity row with `activity_type="ticket_escalated"` to the same partition, mirroring the existing pattern in `assign_ticket` (`tickets.py:838-848`) and `update_status` (`tickets.py:964-976`).

## 4. API / Service Design

### 4.1 Service additions (`app/services/tickets.py`)

```python
def escalate_ticket(
    self,
    *,
    ticket_id: str,
    actor_sub: str,
    reason: str,
    new_assignee_sub: str | None = None,
) -> dict[str, Any] | None:
    """
    Increment escalation_level by 1 on the ticket META row.

    - Returns None if the ticket does not exist.
    - Returns the existing (unchanged) ticket if current status is terminal
      (not in open | in_progress | waiting_on_user).
    - Returns the existing ticket (no error) if escalation_level >= max level
      (ConditionalCheckFailedException is swallowed).
    - Writes an ACT# activity row with activity_type="ticket_escalated".
    - If new_assignee_sub is provided, calls assign_ticket() AFTER the
      escalation write (separate operation, separate version bump).
    - Emits audit_event("ticket_escalated", ...) to T.alerts.
    """
```

The method signature and behavior mirrors `kyc_cases.escalate_case` (`kyc_cases.py:742`) while adapting for the ticket data model (top-level attributes instead of `review` sub-object).

**Implementation sketch**:
```python
def escalate_ticket(self, *, ticket_id, actor_sub, reason, new_assignee_sub=None):
    existing = self.get_ticket(ticket_id)
    if not existing:
        return None
    if existing.get("status", "open") not in {"open", "in_progress", "waiting_on_user"}:
        return existing  # terminal — no-op, no error

    ts = now_ts()
    max_level = S.crm_cases_max_escalation_level   # default 3
    try:
        self._table.update_item(
            Key=_meta_item_key(ticket_id),
            UpdateExpression=(
                "ADD escalation_level :one "
                "SET escalated_at = :ts, escalated_by = :actor, "
                "    escalation_reason = :reason, updated_at = :ts"
            ),
            ConditionExpression=(
                "attribute_exists(pk) AND #status IN (:s1, :s2, :s3) AND "
                "(attribute_not_exists(escalation_level) OR escalation_level < :max)"
            ),
            ExpressionAttributeNames={"#status": "status"},
            ExpressionAttributeValues={
                ":one": 1, ":ts": ts, ":actor": actor_sub,
                ":reason": reason,
                ":s1": "open", ":s2": "in_progress", ":s3": "waiting_on_user",
                ":max": max_level,
            },
        )
    except ClientError as exc:
        if exc.response.get("Error", {}).get("Code") == "ConditionalCheckFailedException":
            return self.get_ticket(ticket_id)
        raise

    # Optional: write escalated_to_sub as a separate SET if provided
    if new_assignee_sub:
        self._table.update_item(
            Key=_meta_item_key(ticket_id),
            UpdateExpression="SET escalated_to_sub = :sub",
            ExpressionAttributeValues={":sub": new_assignee_sub},
        )

    # Activity sub-item
    act_id = f"act_{uuid.uuid4().hex[:12]}"
    self._table.put_item(Item={
        "pk": _ticket_pk(ticket_id), "sk": _act_sk(ts, act_id),
        "entity_type": "ticket_activity", "ticket_id": ticket_id,
        "activity_id": act_id, "activity_type": "ticket_escalated",
        "actor_sub": actor_sub, "reason": reason,
        "escalated_to_sub": new_assignee_sub,
        "created_at": ts,
    })
    return self.get_ticket(ticket_id)
```

**`POST /tickets/{ticket_id}/escalate`**

**Handler sketch**:
```python
@router.post("/{ticket_id}/escalate",
             response_model=EscalateTicketEnvelope,
             responses=_error_responses())
def escalate_ticket(
    ticket_id: str,
    body: EscalateTicketReq,
    request: Request,
    _ctx: dict[str, str] = Depends(require_ui_session),
    user: AuthenticatedUser = Depends(get_authenticated_user),
):
    if not S.crm_cases_enabled:
        _raise(404, "feature_disabled", "crm_cases feature is not enabled")
    if not _is_admin_actor(request, user):
        _raise(403, "admin_role_required", "admin role required")

    ticket = _ticket_or_404(ticket_id)
    if ticket.get("status") not in {"open", "in_progress", "waiting_on_user"}:
        _raise(409, "ticket_terminal_status",
               "cannot escalate a ticket in a terminal or closed status",
               details={"status": ticket.get("status")})

    # Validate optional reassignment target
    if body.new_assignee_sub and not _is_assignable_admin(body.new_assignee_sub):
        _raise(400, "invalid_assignee_role",
               "new_assignee_sub must be an admin or root user",
               details={"new_assignee_sub": body.new_assignee_sub})

    updated = STORE.escalate_ticket(
        ticket_id=ticket_id,
        actor_sub=user.sub,
        reason=body.reason.strip(),
        new_assignee_sub=(body.new_assignee_sub or "").strip() or None,
    )
    if not updated:
        _raise(404, "ticket_not_found", "ticket not found",
               details={"ticket_id": ticket_id})

    # If escalation hit the max level (level unchanged), surface 409
    if int(updated.get("escalation_level") or 0) == int(ticket.get("escalation_level") or 0):
        _raise(409, "ticket_max_escalation_level",
               "ticket has already reached the maximum escalation level",
               details={"escalation_level": updated.get("escalation_level"),
                        "max_level": S.crm_cases_max_escalation_level})

    # If reassignment requested, delegate to existing assign path
    if body.new_assignee_sub:
        try:
            updated = STORE.assign_ticket(
                ticket_id=ticket_id,
                actor_sub=user.sub,
                assignee_sub=body.new_assignee_sub.strip(),
            ) or updated
        except TicketStateError:
            pass  # assignment conflict: escalation was still recorded; surface updated ticket

    # Alert recipients: owner + current watchers (CAS-007) + optional new assignee
    watchers = list(updated.get("watchers") or []) if S.crm_cases_enabled else []
    recipients = list({
        updated.get("owner_sub") or "",
        updated.get("assigned_admin_sub") or "",
        body.new_assignee_sub or "",
        *watchers,
    })
    _emit_ticket_alerts(
        "ticket_escalated",
        recipients=recipients,
        actor_sub=user.sub,
        request=request,
        ticket_id=ticket_id,
        ticket_subject=updated.get("subject", ""),
        escalation_level=updated.get("escalation_level"),
        reason=body.reason.strip(),
    )
    return EscalateTicketEnvelope(ticket=TicketOut.model_validate(updated))
```

**Route ordering**: `/{ticket_id}/escalate` is a sub-path of the existing `/{ticket_id}` route. FastAPI matches more-specific routes first by declaration order. Declare `escalate` before the bare `/{ticket_id}` GET — the existing admin-summary and kyc-sync-deadletter routes already demonstrate this pattern (those appear before the `/{ticket_id}` GET at `router:900`). Insert the `escalate` route immediately after the other sub-resource routes (`/assign`, `/messages`, `/status`) which are already declared before `/{ticket_id}/escalate` would live.

## 5. Detailed Behavior & Edge Cases

### Manual escalation

- **Active statuses only**: Only tickets in `open`, `in_progress`, or `waiting_on_user` can be escalated. A ticket in `done`, `blocked`, `code_complete`, `qa_in_progress`, `qa_approved`, `deploying`, `deployed`, `investigating`, `analyzing`, or `tickets_created` returns 409 `ticket_terminal_status`. The endpoint checks this before calling `STORE.escalate_ticket` so the DynamoDB write is never attempted for clearly ineligible tickets.

- **Maximum escalation level**: `S.crm_cases_max_escalation_level` (default 3) caps the counter. If the ticket is already at level 3, the `ConditionExpression` in `escalate_ticket` (ADD is rejected when `escalation_level >= max`) causes `ConditionalCheckFailedException`, which is swallowed and the unchanged ticket is returned. The endpoint detects the unchanged level and raises 409 `ticket_max_escalation_level`. The max level can be raised by increasing the env var without a code deploy.

- **Optional reassignment**: If `new_assignee_sub` is provided, the endpoint validates the target is an admin/root (same check as `assign_ticket` at `router:927-928`). The reassignment is performed via the existing `STORE.assign_ticket` call AFTER the escalation write — ensuring the escalation counter is always recorded even if the assignment step conflicts.

- **Concurrent mutations**: The `ADD escalation_level :one` DynamoDB expression is atomic. A concurrent admin escalation and a user reply cannot corrupt the counter. The `_conditional_update_meta` optimistic-lock path (used by replies and status changes) does not reference `escalation_level`, so there is no cross-write conflict.

- **Idempotency**: Calling `POST /tickets/{id}/escalate` twice in rapid succession from two concurrent admin sessions will both succeed — the first increments level 0 → 1, the second increments 1 → 2 (unless the max is 1). This is intentional: each escalation is distinct and auditable via the ACT# activity log. If true idempotency-per-actor is required, a `dedupe_key` field can be added as a follow-up.

### Auto-escalation (SLA breach path)

- **Level 0 first breach**: When `check_breaches` detects a fresh breach and `escalation_level == 0`, it calls `escalate_ticket` with `actor_sub="system_sla_escalation"`. Level becomes 1.

- **Subsequent breaches (level > 0)**: CAS-008's `check_breaches` uses a `breach_alerted_at` field on the META row to prevent re-alerting on the same breach. On each checker tick after the initial breach, if the ticket is still breached AND `breach_alerted_at` was set more than one alert interval ago, the checker fires again and increments `escalation_level` to 2, then 3 (up to max). This provides a graduated escalation chain: Level 1 at first breach, Level 2 at second tick, Level 3 at third tick. Once max level is reached, the `ConditionalCheckFailedException` path is a no-op — no further escalations.

- **Ticket resolved between checker ticks**: If the ticket moves to `done` between SLA ticks, the `ConditionExpression` asserts the status is still active and fails silently. The escalation is skipped.

- **`S.crm_cases_sla_enabled` required**: Auto-escalation is only triggered when the SLA sub-flag is on. `S.crm_cases_enabled` alone does not enable the SLA checker loop — both flags must be on.

### Alert delivery

- `_emit_ticket_alerts` (`router:362-372`) calls `audit_event` per recipient, which calls `write_alert` to write the in-app alert to `T.alerts` and publish via SSE. For `ticket_escalated`, the call also reaches `render_ticket_email_template` (after CAS-004's extension), generating an email to all recipients.

- Recipients: `{owner_sub, assigned_admin_sub, new_assignee_sub (if provided), *watchers}`. The set comprehension in `_emit_ticket_alerts` deduplicates and drops empty strings.

- For auto-escalation from `check_breaches`, email targets are derived by re-reading the ticket after escalation. The CAS-008 breach checker constructs the recipient list from the same `get_ticket` result it uses for breach detection. This is acceptable: the one-second window between the breach-checker read and the email construction is unlikely to produce stale watchers. A full re-read after `escalate_ticket` provides the freshest state.

### Activity log

Every escalation — manual or auto — writes an `ACT#` activity sub-item with `activity_type="ticket_escalated"`. This provides a complete audit trail in `get_ticket(id).activity`, including the actor (`actor_sub`), timestamp, and reason for each level.

### Flag-off guarantee

- `POST /tickets/{id}/escalate` returns 404 immediately (no service call, no DDB write).

- No `ticket_escalated` entries appear in `ALERT_EVENT_TYPES` processing (the dispatch gate in `render_ticket_email_template` is flag-agnostic but the event is never emitted while the flag is off).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

All writes target `T.tickets` (DynamoDB Local in dev, AWS DynamoDB in prod — same boto3 call path). There are no `if S.dev_mode` branches in the service layer for escalation. Alert delivery via `send_alert_email` (`alerts.py:459-468`) already handles dev (log to file) vs prod (SES) internally without any escalation-specific branching.

### Idempotency

- The `ADD :one` DynamoDB expression is not idempotent by itself — repeated calls increment the counter. However, the `ConditionExpression` (`escalation_level < :max`) provides a natural ceiling. The POST endpoint is not idempotent by design: each call represents a distinct escalation event and is fully auditable in the ACT log. If a network retry causes a double-increment, the activity log records both entries and both recipients receive notifications. Callers should apply standard HTTP idempotency keys if they require exactly-once semantics — this is acceptable for an infrequently called admin action.
- Auto-escalation from `check_breaches` is bounded by `breach_alerted_at` (CAS-008's de-dup field): the checker only fires the escalation once per breach detection cycle. A crash-restart of the server between checker ticks would re-detect the breach and fire again, but the max-level condition prevents unbounded growth.

### Security

- **Authorization**: The `POST /tickets/{id}/escalate` endpoint requires `_is_admin_actor` (`_is_admin(user) or _has_api_key_scope(request, "tickets:admin")`), matching the pattern for `set_ticket_status` (`router:999-1000`). Regular users cannot escalate.
- **New assignee validation**: `new_assignee_sub` is validated via `_is_assignable_admin(sub)` (same as `assign_ticket` at `router:927-928`), which reads `T.users` and checks the role is `ADMIN` or `ROOT`. This prevents privilege escalation through the reassignment field.
- **CSRF**: `require_ui_session` enforces CSRF on all non-GET requests (`app/auth/deps.py`). Bearer-auth API key requests bypass CSRF but must carry the `tickets:admin` capability scope.
- **Auto-escalation actor**: `actor_sub="system_sla_escalation"` is a synthetic sub that does not correspond to any real user. It is stored in `escalated_by` and the ACT activity row verbatim for auditability. It will not be found in `T.users` lookups; no code attempts to resolve it to a user profile.

## 8. Backward Compatibility & Migration

### Zero-downtime, no migration required

The five new attributes (`escalation_level`, `escalated_at`, `escalated_by`, `escalated_to_sub`, `escalation_reason`) are never written while the flag is off. Existing ticket rows do not carry these attributes. `get_ticket` reads them with `header.get(field, 0)` / `header.get(field)`, returning safe defaults for rows that predate this feature.

`TicketOut` additions are all optional with explicit defaults. Any existing client that parses the response model will simply receive extra zero/null fields that can be safely ignored.

`_conditional_update_meta` (`tickets.py:723-790`) does not reference any of the new fields; its `SET` expressions will not clear or corrupt escalation state even when called concurrently. The version counter it manages is separate from `escalation_level`.

### Rollback

If the feature is rolled back (flag turned off), escalation data written to DynamoDB is inert — `get_ticket` returns the attributes but the endpoint is 404 and no new escalations fire. The data can be left in place without operational impact.

## 10. Open Questions / Assumptions

1. **Escalation level vs. priority**: CAS-003 introduces a `priority` field. Escalation and priority are orthogonal — a low-priority ticket can be escalated multiple times without changing its priority. If the business process requires escalation to auto-raise priority (e.g., Level 2 escalation → priority becomes "urgent"), that logic should be added as a follow-up within CAS-009's `escalate_ticket` method as an optional behavior gated by a new flag (`crm_cases_escalation_auto_raise_priority`, default off).

2. **Escalation notifications to specific admin tiers**: SuiteCRM's escalation rules can route to a specific named supervisor or role tier (e.g., "L2 support queue"). CAS-009 implements the counter and reassignment mechanism; routing to a specific admin from a queue is a follow-up concern addressed by CAS-008's workload management patterns (mirrored from `kyc_case_assignment.py`).

3. **Per-ticket escalation config override**: Currently the max escalation level is global. A per-space or per-priority override could be useful. Assumed out of scope for MVP.

4. **Watcher dependency**: CAS-009 sends alerts to `ticket.get("watchers")`. If CAS-007 has not been deployed, this returns an empty list — the behavior is correct (no watchers → no extra alerts). CAS-009 does not hard-require CAS-007 at runtime.

5. **Email notification for auto-escalation**: The auto-escalation path in `check_breaches` fires `audit_event` for each recipient, which triggers `write_alert` / `send_alert_email` per the `ALERT_EVENT_TYPES` set. This means recipients receive an email on every SLA-checker tick that results in escalation. If this is too frequent, a `crm_cases_escalation_email_enabled` sub-flag (default true) can suppress the email path for auto-escalations while keeping in-app alerts.

6. **`breach_alerted_at` de-dup field ownership**: CAS-008 writes `breach_alerted_at`. CAS-009 reads it implicitly (via the `check_breaches` loop flow). If CAS-008 is not deployed, the auto-escalation hook is never triggered (the SLA checker loop does not exist). This is the correct dependency ordering.
