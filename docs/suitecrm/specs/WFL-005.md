# WFL-005 — On-schedule & time-elapsed triggers (background worker)

**Type:** Feature | **Priority:** P1 | **Estimate:** 2d  
**Depends on:** WFL-001, WFL-002, WFL-003, WFL-004  
**Flag:** `CRM_WORKFLOW_ENABLED` (default `"0"`)

---

## 1. Summary & Goal

WFL-005 introduces the background scheduler that drives two of the three workflow trigger modes defined in WFL-002:

- **`on_schedule`** — fire all matching records once per cron cadence (e.g. every Monday at 09:00 in a given timezone).
- **`on_time_elapsed`** — fire for each record whose watched timestamp field crossed the `offset_hours` boundary during the current poll window (e.g. 24 hours after `closed_at`).

The worker is additive: when `CRM_WORKFLOW_ENABLED=0` (the default) it registers itself as disabled in the job registry and immediately returns without creating any DDB rows, scheduled actions, or background tasks. The rest of the platform is byte-for-byte unchanged.

The scheduler does not execute rule actions itself. Instead it enqueues `crm_workflow` items into `T.scheduled_actions` — the same table used by the unified scheduler (WFL-004 does the same for `on_save`). The `crm_workflow` executor registered in WFL-006 will drain those items. This ticket owns only the _enqueue_ side.

## 2. Context & Current State

### Existing scheduler infrastructure

`app/services/unified_scheduler.py` already implements the poll-execute loop pattern:

- `_EXECUTORS` is a dict (`unified_scheduler.py:28`) with three entries today (`post`, `file_share`, `catalog_sale`). WFL-006 will add `crm_workflow` to this dict; WFL-005 does not touch it.
- `start_unified_scheduler_task()` (`unified_scheduler.py:185`) is registered via `app.add_event_handler("startup", start_unified_scheduler_task)` in `app/main.py:973` (CORRECTED: `app/main.py:229` is the *import* of `start_unified_scheduler_task`, not the registration).

The analogous background loop for audit-export schedules (`run_audit_export_scheduler_loop` at `audit_export_schedule.py:295`) provides the exact structural template: `while True: try: run_due(); except: logger.exception(); await asyncio.sleep(interval)`.

### Cron parsing

`app/services/bot_scheduler.py:77` (`_parse_cron`) and `bot_scheduler.py:101` (`_next_run_from_cron`) are a self-contained, no-dependency 5-field cron parser + next-occurrence calculator. They support `*`, `*/step`, `a-b`, `a-b/step`, and comma-separated lists per field. Frequencies above once-per-hour are rejected at `bot_scheduler.py:88–90`. The implementation uses `zoneinfo.ZoneInfo` for IANA timezone support. WFL-005 reuses these two functions directly via import — no fork, no re-implementation.

### Scheduled-action enqueue

`app/services/scheduled_actions.create_action` (`scheduled_actions.py:91`) writes a `pending` item to `T.scheduled_actions` (PK `USER#{user_sub}`, SK `ACTION#{scheduled_at}#{action_id}`) with GSI keys `GSI_DUE_PK="DUE"` and `GSI_DUE_SK=scheduled_at` (N). It validates minimum lead time (`S.scheduled_actions_min_lead_time_seconds`) and the per-user pending cap (`S.scheduled_actions_max_per_user`). Because the workflow worker enqueues under `user_sub="system"`, it lives in its own DDB partition and never interferes with user quotas.

### Rule storage (WFL-001/002)

`T.crm_workflow_rules` stores rule META rows at `PK=RULE#{rule_id}, SK=META`. The `ByModule` GSI (`GSI_MODULE_PK=MODULE#{target_module}`, `GSI_MODULE_SK=created_at N`) lets `list_rules_for_module(module)` fetch all enabled rules for a module efficiently. The `next_run_at` (N) field on each META row tracks when an `on_schedule` rule should next fire — written by WFL-005 after each successful tick.

### Run-dedup store (WFL-001)

`T.crm_workflow_runs` records execution history at `PK=RULE#{rule_id}, SK=RUN#{ts:010d}#{run_id}`. The `ByRecord` GSI (`GSI_RECORD_PK={module}#{record_id}`, `GSI_RECORD_SK=started_at N`) enables per-record deduplication queries. WFL-005 writes lightweight `outcome="enqueued"` sentinel rows before enqueuing so the time-elapsed tick never double-enqueues the same `(rule_id, record_id)` within the same poll window.

### Job registry

`app/services/job_registry.register_task` (`job_registry.py:23`) and `report_poll` / `report_error` maintain an in-memory health dict read by the admin jobs dashboard (`app/routers/admin_jobs.py`). The unified scheduler calls these on every poll cycle (`unified_scheduler.py:37–45`, `unified_scheduler.py:77–78`).

### Record fetching

`app/services/tickets.TicketStore.list_tickets` (`tickets.py:614`) returns paginated ticket headers. `app/routers/contacts.list_contacts` (`contacts.py:63`) queries `T.contacts` by `owner_id`. Both are the existing primitives WFL-005 wraps in `workflow_record_fetcher.py`.

## 3. Data Model

### No new tables

WFL-005 reuses the two tables established in WFL-001: `T.crm_workflow_rules` and `T.crm_workflow_runs`. No new DynamoDB tables are needed in this ticket. No changes to `scripts/local-ddb-init.py` beyond what WFL-001 already specifies.

### Rule META row — `next_run_at` field (on_schedule rules only)

Added to `T.crm_workflow_rules` items at `PK=RULE#{rule_id}, SK=META`:

| Attribute | Type | Notes |
|-----------|------|-------|
| `next_run_at` | N | Unix timestamp of next scheduled fire. Written by WFL-005 `_advance_next_run(rule_id, cron_expression, timezone)` after each successful tick. Absent on new rules until the first tick initialises it. |

The `ByModule` GSI key `GSI_MODULE_SK=created_at` is numeric and already declared with `attr_types={"GSI_MODULE_SK": "N"}` in WFL-001 — no additional `attr_types` required.

### Run sentinel row — dedup guard (on_time_elapsed rules)

Written to `T.crm_workflow_runs` before enqueuing an `on_time_elapsed` match, using the standard key scheme from WFL-001:

| Attribute | Value |
|-----------|-------|
| `pk` | `RULE#{rule_id}` |
| `sk` | `RUN#{started_at:010d}#{run_id}` |
| `outcome` | `"enqueued"` |
| `trigger_type` | `"on_time_elapsed"` |
| `target_module` | e.g. `"ticket"` |
| `record_id` | the record's primary key |
| `started_at` | N — Unix timestamp |
| `GSI_RECORD_PK` | `{target_module}#{record_id}` |
| `GSI_RECORD_SK` | `started_at` (N) |
| `dedup_window_start` | N — floor of the poll window (for audit inspection) |
| `dedup_window_end` | N — ceiling of the poll window |

The sentinel is written with a conditional `attribute_not_exists(pk)` guard keyed on a deterministic `run_id = sha256(rule_id + record_id + str(window_start))[:16]`. If the conditional put fails (i.e. the sentinel already exists), the enqueue is skipped — this is the primary idempotency mechanism for double-poll scenarios.

## 5. Detailed Behavior & Edge Cases

### `_tick_scheduled_rules(now)` — full flow

1. Guard: `if not S.crm_workflow_enabled: return 0`.
2. `rules = workflow_rules.list_rules_for_module_all()` — fetches every enabled rule across all modules whose `trigger_type == "on_schedule"`. Internally queries `T.crm_workflow_rules` via a Scan with `FilterExpression=Attr("enabled").eq(True) & Attr("trigger_type").eq("on_schedule")`. This is acceptable because the rules table is small (capped at `S.crm_workflow_max_rules_per_module * len(TARGET_MODULES)` rows).
3. For each rule:
   a. Read `next_run_at` from rule dict. If absent (new rule), compute it via `_next_run_from_cron(rule["trigger_config"]["cron_expression"], rule["trigger_config"].get("timezone", "UTC"))` and persist it — then skip this tick (fire on the next due cycle).
   b. If `next_run_at > now`, skip (not due yet).
   c. Fetch records: `fetch_module_records(rule["target_module"], limit=100)`.
   d. For each record: `matched, _ = evaluate_conditions(rule["conditions"], record)`. If matched and not already enqueued (`_is_already_enqueued`), call `_enqueue_workflow_action`.
   e. Advance: `_advance_next_run(rule_id, cron_expression, timezone)` — updates `next_run_at` on the META row via `update_item` and returns the next timestamp.
4. Return total count enqueued.

**Edge case — rule disabled mid-tick**: `list_rules_for_module_all` fetches a snapshot. A rule disabled between fetch and enqueue will still be enqueued; the executor (WFL-006) re-checks `rule["enabled"]` at execution time and no-ops silently.

**Edge case — cron parse failure**: If `_parse_cron` returns `None` for the stored expression (corrupted rule), the tick logs a warning with `rule_id` and skips that rule. It does not raise, so subsequent rules in the batch still fire.

**Edge case — worker restart / missed tick**: If the process restarts and `next_run_at` is in the past, the rule fires immediately on the next poll. This is the standard "catch-up" behaviour mirrored by `run_due_schedules()` in `audit_export_schedule.py:256` (CORRECTED from `:258`).

### `_tick_time_elapsed_rules(now)` — full flow

1. Guard: `if not S.crm_workflow_enabled: return 0`.
2. Compute `poll_window = S.crm_workflow_poll_interval_seconds` (default 60 seconds). This defines the dedup window: `window_start = now - offset_seconds - poll_window`, `window_end = now - offset_seconds`.
3. Fetch all enabled `on_time_elapsed` rules (same Scan as above, filtered to `trigger_type`).
4. For each rule:
   a. Parse `field = rule["trigger_config"]["field"]` and `offset_hours = int(rule["trigger_config"]["offset_hours"])`. Compute `offset_seconds = offset_hours * 3600`.
   b. `elapsed_window = (now - offset_seconds - poll_window, now - offset_seconds)`.
   c. Fetch records: `fetch_module_records(rule["target_module"], limit=100)`.
   d. For each record: check `record.get(field)`. If the field value (integer Unix timestamp or ISO-8601 string, coerced to int) falls within `elapsed_window` — i.e. `window_start <= field_ts <= window_end` — then evaluate conditions.
   e. If matched: call `_write_enqueue_sentinel(rule_id, module, record_id, now, window_start, window_end)`. If the conditional put succeeds (returns True), call `_enqueue_workflow_action`. If it fails (duplicate), log at DEBUG and skip.
5. Return total count enqueued.

**Edge case — field missing on record**: If `record.get(field)` is absent or None, the record does not match the time-elapsed window — it is skipped silently. This mirrors the `is_empty` operator semantics in WFL-003.

**Edge case — field is ISO-8601 string**: Coerce to Unix int via `int(datetime.fromisoformat(field_value).timestamp())`. If coercion fails (bad data), skip the record with a DEBUG log.

**Edge case — large offset (e.g. 720 hours = 30 days)**: The window arithmetic is the same regardless of magnitude. The fetcher still returns at most 100 records per tick; the caller filters in-process. For modules with high cardinality, the 100-record cap means some elapsed records may be missed in a given tick — they will appear in the next tick's window only if they remain within the `±poll_window` band. This is acceptable for the initial release (see Open Questions).

**Edge case — `offset_hours=0`**: Rejected at rule-creation time by WFL-002 (`offset_hours` must be `>= 1`). The scheduler assumes the field is always non-zero.

### Enqueue function `_enqueue_workflow_action`

Calls `scheduled_actions.create_action(user_sub="system", action_type="crm_workflow", scheduled_at=now_ts(), payload={"rule_id": rule_id, "module": module, "record_id": record_id, "trigger_type": trigger_type})`. The lead-time check in `create_action` (`scheduled_actions.py:103–105`) requires `scheduled_at > now + S.scheduled_actions_min_lead_time_seconds`. To satisfy this, WFL-005 passes `scheduled_at = now_ts() + S.scheduled_actions_min_lead_time_seconds + 1` so items are immediately eligible on the next unified-scheduler poll without violating the invariant.

### Loop structure

```
run_workflow_scheduler_loop():
  if not S.crm_workflow_enabled:
      register_task("crm_workflow_scheduler", interval, enabled=False, ...)
      return                            # exits immediately; no asyncio.sleep loop
  register_task("crm_workflow_scheduler", interval, enabled=True, ...)
  while True:
      t0 = perf_counter()
      enqueued_sched = enqueued_elapsed = 0
      try:
          now = now_ts()
          enqueued_sched  = _tick_scheduled_rules(now)
          enqueued_elapsed = _tick_time_elapsed_rules(now)
          report_poll("crm_workflow_scheduler",
                      items_processed=enqueued_sched + enqueued_elapsed,
                      duration_ms=(perf_counter()-t0)*1000)
      except Exception:
          report_error("crm_workflow_scheduler", str(exc))
          logger.exception("crm_workflow_scheduler_loop_error")
      await asyncio.sleep(S.crm_workflow_poll_interval_seconds)
```

This mirrors `run_unified_scheduler_loop` (`unified_scheduler.py:35–87`) exactly, including the `report_poll` / `report_error` calls that feed the admin jobs dashboard.

### Cron constraint (inherited from `bot_scheduler.py:88–90`)

`_parse_cron` rejects expressions where `parts[0] == "*" and parts[1] == "*"` (every-minute frequency). Admins attempting to store such expressions receive a 400 from the WFL-002 `create_rule` validation. The scheduler itself does not re-validate — it trusts that persisted rules are valid.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

There are no `if S.dev_mode` branches in `workflow_scheduler.py` or `workflow_record_fetcher.py`. The scheduler uses only DynamoDB (`T.crm_workflow_rules`, `T.crm_workflow_runs`, `T.scheduled_actions`) and the existing `_next_run_from_cron` helper — all of which run identically against DynamoDB Local (moto port 8001) in dev and real DynamoDB in prod.

`send_alert_email` (called indirectly via WFL-006/007, not WFL-005) already branches on `S.dev_mode` at `alerts.py:462` — WFL-005 does not call it.

### Idempotency

**On-schedule**: `next_run_at` is advanced atomically via `update_item` after each successful tick. If the process crashes between the enqueue and the `_advance_next_run` call, the rule fires again on the next poll. The executor (WFL-006) checks the run log before acting, providing end-to-end idempotency. Within a single tick, `query_due_actions` in the unified scheduler uses `claim_action` (`scheduled_actions.py:377`) with a conditional update on `status=pending` — two worker instances cannot both execute the same action.

**On-time-elapsed**: The conditional-put sentinel (`_write_enqueue_sentinel`) is the primary dedup guard. Its `run_id` is a deterministic hash of `rule_id + record_id + str(window_start)`, so two concurrent poll cycles with the same window produce the same `run_id` and only one put succeeds.

### Security

- All enqueues use `user_sub="system"` — there is no user impersonation and no user quota consumed.
- The scheduler reads rule definitions from `T.crm_workflow_rules` which is admin-write-only (WFL-009 requires `require_admin_or_root_csrf`). A regular user cannot inject a rule.
- `fetch_module_records` performs system-level queries. It must not expose PII in logs. The tick functions log only `rule_id`, `record_id`, and counts — never record field values.
- Cron expressions are stored and evaluated server-side; they do not execute arbitrary code. The `_parse_cron` function returns `None` (invalid) for any expression that does not match the allowed field grammar, making injection impossible.

## 8. Backward Compatibility & Migration

### Zero impact when flag is off

`start_workflow_scheduler_task` returns `None` immediately when `S.crm_workflow_enabled` is `False`. No DDB tables, no background task, no `asyncio.Task` is created. The `app/main.py` registration line itself is additive (one new `add_event_handler` call) and causes no side effects.

### Migration for existing deployments

No data migration is required. The two new DynamoDB tables (`crm_workflow_rules`, `crm_workflow_runs`) are created at stack startup by `scripts/local-ddb-init.py` (WFL-001). In production, the tables should be provisioned before deploying the code — empty tables cause no harm. Once deployed with the flag off, operators can enable the feature by setting `CRM_WORKFLOW_ENABLED=1` and restarting uvicorn.

### Existing table compatibility

`T.scheduled_actions` gains `crm_workflow` action items at `pk=USER#system`. The unified scheduler's `query_due_actions` queries `GSI_DUE_PK="DUE"` — it will pick up these items and attempt to dispatch them via `_EXECUTORS.get("crm_workflow")`. Until WFL-006 adds the executor, `_EXECUTORS.get("crm_workflow")` returns `None`, and `_process_action` calls `mark_action_failed` (`unified_scheduler.py:137–138`). This is safe: the items TTL out after `S.scheduled_actions_ttl_days` days. **Deployment order must therefore be: WFL-006 before WFL-005 is enabled in production.** WFL-005 can be deployed (flag off) before WFL-006 with no risk.

## 9. Test Plan

### Hermetic pytest tests (`tests/test_wfl_005_workflow_scheduler.py`)

All tests use moto-backed DynamoDB. `T.crm_workflow_rules`, `T.crm_workflow_runs`, and `T.scheduled_actions` are bound via `object.__setattr__` on the frozen `T` singleton (canonical pattern from `tests/test_gap_0220_0221_ssh_stored_key.py`). `S.crm_workflow_enabled` and `S.crm_workflow_poll_interval_seconds` are toggled via `object.__setattr__` on the frozen `S` singleton. `now_ts` is monkeypatched to return a fixed integer. `_next_run_from_cron` is NOT patched — it is pure and self-contained.

**Test cases:**

1. **Flag-off short-circuit**: With `S.crm_workflow_enabled=False`, `_tick_scheduled_rules(now)` returns 0 and makes zero DDB calls (assert via monkeypatched `T.crm_workflow_rules.scan` that raises if called).

2. **On-schedule: no due rules**: Insert a rule with `next_run_at = now + 3600`. Assert `_tick_scheduled_rules(now)` returns 0 and `T.scheduled_actions` has no new items.

3. **On-schedule: rule is due**: Insert a rule with `next_run_at = now - 1`. Insert two ticket records. Assert `_tick_scheduled_rules(now)` returns 2 (both tickets matched, no conditions), `T.scheduled_actions` has 2 items with `action_type="crm_workflow"`, and the rule's `next_run_at` is updated to a future timestamp.

4. **On-schedule: condition filters records**: Insert a rule with `conditions=[{"field": "status", "operator": "eq", "value": "open"}]`. Insert 3 tickets: 2 open, 1 closed. Assert 2 items enqueued.

5. **On-schedule: `next_run_at` absent (new rule)**: Insert a rule with no `next_run_at`. Assert the tick initialises `next_run_at` but does NOT enqueue (fires on next due cycle), and the field is now present on the rule META.

6. **On-schedule: `next_run_at` advanced correctly**: After a successful tick, assert `next_run_at` is the strictly-next cron occurrence after `now` using the same `_next_run_from_cron` logic.

7. **On-schedule: cron parse failure**: Insert a rule with `cron_expression="invalid"`. Assert the tick logs a warning, skips the rule, and returns 0 — does not raise.

8. **On-time-elapsed: record in window**: Insert a rule with `offset_hours=24`. Insert a ticket with `closed_at = now - 86400` (exactly 24h ago). Poll window is 60s, so `window_start = now - 86400 - 60`, `window_end = now - 86400`. Assert 1 item enqueued and sentinel row written.

9. **On-time-elapsed: record outside window**: Same setup but `closed_at = now - 86400 - 3600` (25h ago). Assert 0 enqueued.

10. **On-time-elapsed: dedup — second tick does not re-enqueue**: Run `_tick_time_elapsed_rules(now)` twice with the same `now`. Assert `T.scheduled_actions` still has exactly 1 item (conditional-put guard on sentinel blocks the second write).

11. **On-time-elapsed: missing field skipped**: Insert ticket without `closed_at`. Assert 0 enqueued, no exception raised.

12. **On-time-elapsed: ISO-8601 field coercion**: Insert a contact with `updated_at` as an ISO-8601 string in the elapsed window. Assert 1 item enqueued.

13. **Flag disabled stops loop**: `start_workflow_scheduler_task` called with `S.crm_workflow_enabled=False` does not create an `asyncio.Task`. Assert via `asyncio.all_tasks()` count.

14. **Job registry registration**: With flag on, `run_workflow_scheduler_loop` calls `register_task("crm_workflow_scheduler", ...)`. Assert `job_registry._tasks["crm_workflow_scheduler"]["enabled"]` is True after one loop iteration (loop broken by monkeypatching `asyncio.sleep` to raise `StopIteration`).

15. **`report_poll` called on success**: After a successful tick, `report_poll` is called with `items_processed >= 0`. Assert via spy on `job_registry.report_poll`.

16. **`report_error` called on exception**: If `_tick_scheduled_rules` raises unexpectedly, `report_error` is called. Assert via monkeypatching `_tick_scheduled_rules` to raise and spying on `report_error`.

## 10. Open Questions / Assumptions

1. **Record fetch cap at 100**: The initial `fetch_module_records` cap is 100 records per module per tick. For deployments with many thousands of contacts or tickets, some elapsed records will fall outside the polling window before being seen. A follow-on ticket should add a DDB GSI on the relevant timestamp fields (e.g. `closed_at`, `updated_at`) to enable range queries instead of full fetches. Assumption for WFL-005: record counts per module are low enough that 100 is sufficient for the initial release.

2. **`on_time_elapsed` window drift**: The dedup window is defined as `±poll_interval_seconds` around the target elapsed time. If the poll interval is increased in production (e.g. from 60s to 300s), the window widens and more records qualify per tick. Operators should be aware that changing `CRM_WORKFLOW_POLL_INTERVAL_SECONDS` affects both cadence and time-elapsed precision.

3. **Cross-user ticket scans**: `_fetch_tickets` uses `TicketStore.list_tickets(status=None)` which queries the status GSI for all statuses. This is a system-level operation not scoped to any user. Assumption: this is acceptable for an admin-only background worker; the `crm_workflow_rules` table is admin-write-only.

4. **`user_sub="system"` action quota**: `create_action` checks `_count_pending(user_sub)` against `S.scheduled_actions_max_per_user` (default 100, `settings.py:1935`). Under high rule + record volumes, the `system` partition could hit this cap. The threshold should be raised via env var for deployments with many workflow rules, or a separate bypass for the system user should be added in a follow-on ticket. Assumption: 100 pending actions per poll cycle is sufficient for the initial release.

5. **Timezone for `_advance_next_run`**: The `trigger_config.timezone` field is validated at rule-creation time (WFL-002). If an invalid timezone somehow reaches the scheduler, `_next_run_from_cron` raises `ValueError`. The tick function catches this and logs a warning, skipping the advance — `next_run_at` remains stale. The rule fires again on every subsequent poll until manually corrected by an admin.
