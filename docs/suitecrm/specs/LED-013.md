# LED-013 — Lead / Prospect search, filter, and router surface

**Type:** Feature  **Priority:** P1  **Estimate:** 3 days  
**Ticket source:** `docs/suitecrm/CRM_LEADS_TICKETS.md`, section "LED-013"

---

## 1. Summary & Goal

LED-013 delivers the complete, flag-gated HTTP surface for the Leads module: a single FastAPI router (`app/routers/leads.py`), all attendant Pydantic request/response wrappers in `app/models.py`, TypeScript API bindings, a React page, and a Playwright E2E spec. It is the integration layer that stitches LED-003 through LED-012 together behind a consistent `require_ui_session` auth boundary and a DynamoDB-native search/filter mechanism.

The goal is threefold. First, expose every lead and prospect operation from a single URL namespace (`/ui/leads`) with correct declaration ordering so that static sub-paths (`/prospects`, `/import/csv`, `/sources/summary`) are never captured by the dynamic `/{lead_id}` segment. Second, add a query-param-driven filter and text-search capability that works without a separate search index for MVP. Third, wire a flag-gated frontend entry point (nav item + lazy-loaded page) that is completely invisible when `LEADS_ENABLED=0`.

With `S.leads_enabled = False` (the default), no new endpoint is reachable, the nav item is absent, and every existing code path is byte-for-byte unchanged. The flag can be toggled per deployment without a code change.

### Cross-ticket reconciliation (audit 2026-06-13)

Per `docs/CROSS_TICKET_AUDIT.md` (Part C #11): the admin route prefix is canonically `/ui/admin/leads` (matching the established `/ui/admin/audit-exports` convention). LED-011's score-history endpoint and any other Leads admin surfaces resolve to this prefix.

### 2.1 Auth pattern: `require_ui_session`

The canonical auth dependency for UI-facing endpoints is `require_ui_session` from `app/services/sessions.py:330`. It is consumed at `app/routers/contacts.py:14` with `router = APIRouter(prefix="/ui/contacts", tags=["contacts"])` and used in every contact endpoint as `Depends(require_ui_session)` (e.g., `app/routers/contacts.py:63`). ### 2.3 FastAPI declaration-order constraint

Per the "Common gotchas" note in CLAUDE.md and the implementation of `app/routers/kyc_cases.py:1–50`, FastAPI matches route handlers in declaration order. A dynamic segment `/{lead_id}` declared before `/prospects` or `/import/csv` would capture those literal strings as path parameters. LED-013 must declare all static routes before dynamic ones.

## 3. Data Model

### 3.1 Reuse of the `leads` table (LED-001)

LED-013 introduces no new DynamoDB tables. All reads and writes go through `T.leads`, `T.activity_feed`, and `T.alerts` — all defined by prerequisite tickets. The table `T.leads` is a single-table design with `PK=pk`, `SK=sk`, and the following row types written by LED-003 through LED-012:

| Row type | PK | SK |
|----------|----|----|
| Lead META | `LEAD#{lead_id}` | `META` |
| Lead activity | `LEAD#{lead_id}` | `ACTIVITY#{ts}#{id}` |
| Lead score history | `LEAD#{lead_id}` | `SCORE#{ts}#{id}` |
| Prospect META | `PROSPECT#{prospect_id}` | `META` |
| Assignment queue config | `QUEUE#{queue_id}` | `CONFIG` |
| Scoring rules config | `SCORING_CONFIG` | `RULES` |

### 3.2 GSIs (all defined in LED-001, LED-007, LED-009)

| GSI name | PK attribute | SK attribute | attr_types (numeric SK) |
|----------|-------------|-------------|-------------------------|
| `ByOwner` | `GSI1PK` = `OWNER#{sub}` | `GSI1SK` = `created_at` (N) | `"GSI1SK": "N"` |
| `ByStatus` | `GSI2PK` = `STATUS#{status}` | `GSI2SK` = `created_at` (N) | `"GSI2SK": "N"` |
| `BySource` | `GSI3PK` = `SOURCE#{source}` | `GSI3SK` = `created_at` (N) | `"GSI3SK": "N"` |
| `ByEmail` | `GSI4PK` = `EMAIL#{normalized_email}` | `GSI4SK` = `created_at` (N) | `"GSI4SK": "N"` |
| `ByPhone` | `GSI5PK` = `PHONE#{normalized_e164}` | `GSI5SK` = `created_at` (N) | `"GSI5SK": "N"` |

All five GSIs are declared in the single `TableDef` entry for `leads` in `scripts/local-ddb-init.py`, with the full `attr_types` dict:

```python
TableDef(
    _resolve_table_name(S.leads_table_name, "leads"),
    "pk",
    "sk",
    gsi=[
        {"index_name": "ByOwner",  "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "ByStatus", "partition_key": "GSI2PK", "sort_key": "GSI2SK"},
        {"index_name": "BySource", "partition_key": "GSI3PK", "sort_key": "GSI3SK"},
        {"index_name": "ByEmail",  "partition_key": "GSI4PK", "sort_key": "GSI4SK"},
        {"index_name": "ByPhone",  "partition_key": "GSI5PK", "sort_key": "GSI5SK"},
    ],
    attr_types={
        "GSI1SK": "N", "GSI2SK": "N", "GSI3SK": "N",
        "GSI4SK": "N", "GSI5SK": "N",
    },
)
```

Omitting any `attr_types` entry for a numeric GSI sort key causes `ValidationException` at runtime, per the CLAUDE.md DynamoDB gotcha.

### 3.3 `scripts/local-ddb-init.py` changes

LED-013 itself adds no new `TableDef` entries. It relies on LED-001's `leads` table entry (updated by LED-007 and LED-009 to add the `ByEmail` and `ByPhone` GSIs). The only change this ticket makes to `local-ddb-init.py` is confirming the consolidated `TableDef` above is present. If any prior LED ticket has not yet been merged, the implementer must add the missing GSI entries at the same time as LED-013.

#### `GET /ui/leads` — list leads with filter and search

```python
@router.get("", response_model=LeadListOut)
async def list_leads_endpoint(
    status: Optional[str] = Query(default=None),
    lead_source: Optional[str] = Query(default=None),
    assigned_to: Optional[str] = Query(default=None),
    created_after: Optional[int] = Query(default=None),
    q: Optional[str] = Query(default=None, max_length=200),
    cursor: Optional[str] = Query(default=None),
    limit: int = Query(default=50, ge=1, le=200),
    ctx: dict = Depends(require_ui_session),
):
    _require_leads_enabled()
    result = leads.list_leads(
        owner_sub=ctx["user_sub"],
        status=status,
        lead_source=lead_source,
        assigned_to=assigned_to,
        created_after=created_after,
        cursor=cursor,
        limit=limit,
    )
    items = result["leads"]
    if q:
        q_lower = q.strip().lower()
        items = [
            ld for ld in items
            if q_lower in (ld.get("first_name") or "").lower()
            or q_lower in (ld.get("last_name") or "").lower()
            or q_lower in (ld.get("email") or "").lower()
            or q_lower in (ld.get("company") or "").lower()
        ]
    return {"leads": [LeadOut(**ld) for ld in items], "cursor": result.get("cursor")}
```

The `q` filter is applied in Python after the DynamoDB query returns. This is appropriate for MVP on a small-to-medium result set. If the caller provides both `q` and `status` or `lead_source`, the GSI query narrows the result set before Python filtering, which bounds memory usage. A `TODO` comment in the code documents that a dedicated search index (e.g., OpenSearch) is the production-scale replacement.

#### `GET /ui/leads/{lead_id}` — get single lead


## 5. Detailed Behavior & Edge Cases

### 5.1 Declaration order verification

The router must declare routes in this exact order in `app/routers/leads.py`:

1. `POST /import/csv`
2. `GET /prospects`, `POST /prospects`
3. `GET /prospects/{prospect_id}`, `PATCH /prospects/{prospect_id}`, `DELETE /prospects/{prospect_id}`
4. `GET /sources/summary`
5. `POST ""` (create lead at `/ui/leads`)
6. `GET ""` (list leads at `/ui/leads`)
7. `GET /{lead_id}`, `PATCH /{lead_id}`, `DELETE /{lead_id}`
8. `POST /{lead_id}/convert`, `GET /{lead_id}/duplicates`, `POST /{lead_id}/merge`, `POST /{lead_id}/assign`
9. `GET /{lead_id}/activities`, `POST /{lead_id}/activities`
10. `GET /{lead_id}/score-history` (LED-011, sub-flag gated)

A FastAPI integration test (in the hermetic pytest) must assert that `GET /ui/leads/prospects` does not match the `/{lead_id}` handler by verifying `response["lead_id"] != "prospects"`.

### 5.2 `q` search filter semantics

The `q` parameter matches any lead where the lowercase query string is a substring of at least one of: `first_name`, `last_name`, `email`, `company`. Matching is case-insensitive (`q_lower in field.lower()`). `q` is applied after the DynamoDB query, so it does not affect which GSI is used or what `cursor` is returned. Consequence: when `q` is present, the response may have fewer items than `limit` even when a `cursor` is returned. Clients must follow the cursor until it is absent to ensure completeness. A `TODO` comment documents this known limitation.

### 5.3 Flag guard behavior

`_require_leads_enabled()` raises `HTTPException(status_code=404)` when `S.leads_enabled` is `False`. This is raised before any auth check, so unauthenticated requests also receive 404 (no information leakage about route existence). The sub-flag for assignment (`S.leads_assignment_enabled`) is checked at the `POST /{lead_id}/assign` handler level — this endpoint returns 404 even when `S.leads_enabled` is `True` but `S.leads_assignment_enabled` is `False`. Similarly, `GET /{lead_id}/score-history` checks `S.leads_scoring_enabled`.

### 5.4 Ownership enforcement

`_assert_ownership(lead, caller_sub, role)` logic:

- If `role == Role.ROOT` or `role == Role.ADMIN`: full access, no 403.
- If `caller_sub == lead["created_by"]`: access allowed.
- If `caller_sub == lead["assigned_to"]`: access allowed.
- Otherwise: `raise HTTPException(403, "lead_access_denied")`.

Prospects are owned by their `owner_sub` field; the same helper is used.

### 5.5 CSV import size and row cap

The multipart upload handler reads the file with `await file.read()`. If `file.size` is available and exceeds 10 MB, a 422 is raised before reading. If `file.size` is `None` (some clients omit Content-Length), the bytes are read and checked post-read. `leads_import.import_leads_from_csv` hard-caps at 5000 rows (LED-008). Rows beyond the cap are silently dropped, and the result object reports `{"imported": N, "skipped": M, "errors": [...], "capped": True}`.

### 5.6 Concurrent `list_leads` with `q` and filter

When both `status` and `q` are provided, the service routes to the `ByStatus` GSI (narrower result set) and Python-filters by `q`. When only `q` is provided (no status or source filter), the service falls back to the `ByOwner` GSI so only the caller's own leads are scanned. A scan of the entire `leads` table is never performed in the list-leads path — the caller's `user_sub` always bounds the query.

### 5.7 Duplicate route guard for `/import/csv` vs. `/{lead_id}`

FastAPI's route matching is order-sensitive. Because `POST /import/csv` is declared first, the string `"import"` will never be treated as a `lead_id`. However, `lead_id` values must never start with reserved strings (`"import"`, `"prospects"`, `"sources"`). LED-003's `create_lead` generates IDs as `"lead_" + uuid4().hex[:20]`, which always starts with `lead_` and never collides with these prefixes. LED-007's `create_prospect` generates `"prospect_" + uuid4().hex[:20]`. No additional runtime guard is needed.

### 5.8 Audit trail for bulk import

`import_leads_from_csv` (LED-008) emits a single `audit_event("lead.bulk_import", owner_sub, imported=N, skipped=M, errors=len(errors))` at the end of a successful import run. Individual row-level events are not emitted to avoid flooding the audit table on large imports. The router wraps the import call with a try/except that converts service-layer errors to HTTP 422 with the error list in the response body.

### 5.9 Score-history endpoint (LED-011 integration)

`GET /ui/leads/{lead_id}/score-history` returns the `SCORE#{ts}#{id}` rows for a lead, newest-first, via a `query(KeyConditionExpression=pk=LEAD#{id} AND sk begins_with SCORE#)` call. This query uses the base table (no GSI), so it is always consistent. The endpoint is gated on `S.leads_scoring_enabled` as a secondary guard after the `S.leads_enabled` flag guard.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

The router has no `if S.dev_mode` branch, no mock DynamoDB path, and no inline fixture data. It calls the same service functions in dev (against DynamoDB Local on port 8001) and in prod (against real DynamoDB). The only environment difference is the `DDB_ENDPOINT_URL` in `app/core/settings.py`. The CSV import uses `io.BytesIO` in both environments — no tmp-file writes. Audit events go to `T.alerts` in both environments. All of this is consistent with the SECOPS-007 mandate: "same code path both ways, no AWS divergence."

### 7.2 CSRF enforcement

`require_ui_session` (at `app/services/sessions.py:330`) enforces CSRF for non-GET cookie-auth requests automatically. No per-route CSRF header or token logic is needed in `app/routers/leads.py`. Bearer-auth requests (API key or Cognito JWT) bypass CSRF, consistent with the platform-wide policy documented in CLAUDE.md.

### 7.3 Idempotency

- `POST /ui/leads` — idempotent by email: LED-003's `create_lead` returns the existing lead if the normalized email already exists (same status). A second identical POST returns HTTP 200 with the existing lead (not 201).
- `POST /ui/leads/{lead_id}/convert` — LED-006 returns HTTP 409 if status is already `"converted"`. The router passes this through unchanged.
- `POST /ui/leads/{lead_id}/merge` — LED-009 is idempotent: merging a lead that is already `"dead"` and `merged_into=primary_lead_id` is a no-op returning the primary lead.
- `POST /ui/leads/import/csv` — not idempotent (a second upload of the same file with `skip_duplicates=True` skips all rows and returns `{imported: 0, skipped: N}`). Clients should use `skip_duplicates=True` (the default) for safe retries.

### 7.4 Access control summary

| Endpoint group | Auth dep | Role requirement |
|----------------|----------|-----------------|
| All `/ui/leads/*` (read/write) | `require_ui_session` | Authenticated user; ownership checked per-resource |
| `GET /ui/leads/sources/summary` | `require_ui_session` + `require_admin_or_root` | ADMIN or ROOT |
| `GET/POST /ui/admin/leads/scoring/rules` | `require_ui_session` + `require_admin_or_root` | ADMIN or ROOT |
| `POST /ui/admin/leads/rescore-all` | `require_ui_session` + `require_admin_or_root` | ADMIN or ROOT |
| Queue config CRUD (LED-010) | `require_ui_session` + `require_admin_or_root` | ADMIN or ROOT |

### 7.5 Input sanitization

- `email` is normalized via `normalize_email` from `app/core/normalize.py:60` in the service layer (not the router). [VERIFIED-CORRECTED: `app/routers/contacts.py` does NOT call `normalize_email`/`normalize_phone` (no such reference exists in that file), so the "consistent with `app/routers/contacts.py:96`" citation is removed. `normalize_email`/`normalize_phone` are consumed elsewhere in the platform; LED-013 introduces the service-layer call in `app/services/leads.py`.]
- `phone` is normalized via `normalize_phone` from `app/core/normalize.py:66`.
- CSV field values are passed through `_sanitize_csv_field` from `app/services/csv_export.py:43` during import to prevent formula injection.
- `lead_id` path parameters are not validated beyond being non-empty strings. The service layer returns `None` on miss, which the router converts to HTTP 404.

### 7.6 PII handling

Lead records contain PII (name, email, phone). They are stored in DynamoDB without KMS encryption at the field level (consistent with the contacts table pattern — no field-level encryption in the existing contacts surface). Audit events in `T.alerts` do not include PII fields; they include only identifiers (`lead_id`, `user_sub`). This is consistent with the KYC audit pattern at `app/services/alerts.py:644`.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact with flag off

With `LEADS_ENABLED=0` (the default), `app/routers/leads.py` is imported into `app/main.py` but all handlers return 404 immediately. No DynamoDB reads or writes occur. No existing table is modified. No existing endpoint is affected. The contacts router (`app/routers/contacts.py`), activity feed (`app/services/activity_feed.py`), questionnaires (`app/routers/questionnaires.py`), and all other existing surfaces are byte-for-byte unchanged.

### 8.2 Progressive flag enablement

The recommended deployment sequence is:

1. Deploy with `LEADS_ENABLED=0` (no user impact).
2. Run `just restart` (or equivalent) in dev to create the `leads` DynamoDB table via `scripts/local-ddb-init.py`.
3. In prod: run `CreateTable` for `leads` via the migration script before setting `LEADS_ENABLED=1`.
4. Set `LEADS_ENABLED=1` — endpoints become live, nav item appears.
5. Optionally set `LEADS_SCORING_ENABLED=1` and `LEADS_ASSIGNMENT_ENABLED=1` to activate sub-features.

There is no data migration step because the `leads` table starts empty. Existing users see no change until they navigate to the Leads page.

### 8.3 Activity feed backward compatibility

LED-012 does **not** modify the existing `ACTIVITY_TYPES` list at `app/services/activity_feed.py:22` (which is `["follow","like","comment","post","mention","share","tip"]`). Instead it introduces a separate `CRM_ACTIVITY_TYPES = {"note","call","email","meeting"}` constant and a new `record_activity_for_entity(...)` function — leaving all existing callers that iterate `ACTIVITY_TYPES` untouched (LED-012 §5.1). LED-013's `log_lead_activity` handler must therefore call `activity_feed.record_activity_for_entity(target_type="lead", target_id=lead_id, actor_id=..., activity_type=..., ...)` so the sparse `GSI_TARGET_PK` is populated and `get_entity_activity_feed` (the GSI query) returns the row. [VERIFIED-CORRECTED: (1) `ACTIVITY_TYPES` is unchanged by LED-012 — the new CRM types live in a separate `CRM_ACTIVITY_TYPES` set, and `"lead"`/`"party"` are `target_type` values, not `activity_type` entries; (2) the §4.3 sketch of `log_lead_activity` calling plain `record_activity` would NOT set `GSI_TARGET_PK`, so it must use `record_activity_for_entity` per LED-012 §4.1.] The existing `get_activity_feed` (which queries by `user_id`) is not affected — it never returns lead-activity rows in a user's social feed because those rows are stored with `user_id=lead_id` (not a platform user's sub). There is no cross-contamination between the social activity feed and the CRM lead activity log.

### 8.4 OpenAPI schema

The leads router is tagged `"leads"`. Because it is imported unconditionally in `app/main.py`, the OpenAPI schema at `GET /openapi.json` includes all lead endpoints regardless of the flag. This is consistent with how other flag-gated routers (e.g., the KYC routers) behave — the schema describes the surface; the runtime flag controls access. Clients should treat 404 responses from leads endpoints as "feature not enabled" rather than "endpoint does not exist."

## 10. Open Questions / Assumptions

1. **`q` filter cursor semantics** — When `q` is combined with pagination, the cursor points to the DynamoDB position in the unfiltered result set. Clients advancing through pages with `q` may see fewer results per page than `limit`. This is documented in the handler as a known limitation. The assumption is that this is acceptable for MVP; a production-scale text search would require a separate index.

2. **Prospect opt-out integration** — LED-007's `create_prospect` calls `cart_reminders.is_user_opted_out` to set a `suppressed` flag. The `GET /ui/leads/prospects` list endpoint should surface this `suppressed` field in `ProspectOut`. The assumption is that `suppressed` is a read-only flag computed at create/update time, not re-checked on every list call.

3. **Admin route prefix** — The admin scoring endpoints are placed at `/ui/admin/leads/...` rather than `/ui/leads/admin/...`. The assumption is that all admin routes share the `/ui/admin/` prefix (consistent with `/ui/admin/audit-exports`, `/ui/admin/audit-exports/schedules`). If the platform conventions change, the prefix must be updated here and in `app/main.py`.

4. **`LeadOut.score` on list** — Every `list_leads` call returns `score` from the `META` row. When scoring is disabled, `score` is always `0`. If a lead was scored before `leads_scoring_enabled` was turned off, the stored score is still returned. The assumption is that consumers ignore `score=0` when the scoring flag is off (no special null vs. 0 distinction needed).

5. **Duplicate lead return code** — LED-003's `create_lead` returns the existing lead on a duplicate email create. The router returns HTTP 200 (not 201) in this case. The assumption is that callers treat the response identically regardless of status code. If strict 201-only semantics are needed by a client, a `created: bool` field can be added to `LeadOut` to distinguish the two cases.

6. **Activity feed GSI (LED-012)** — LED-012 adds a `ByTarget` sparse GSI to the `activity_feed` table. If LED-012 has not yet been merged when LED-013 is deployed, `get_entity_activity_feed` will fall back to a scan (or return empty results). The router handles this gracefully via the service layer's `try/except` wrapper.

7. **PTY integration in conversion** — LED-006's `convert_lead` checks `S.party_crm_enabled`. When the PTY module is not deployed, conversion falls back to inline stubs. LED-013's router is agnostic to this — it calls `leads.convert_lead` and returns `LeadConversionOut`. No router-level PTY check is needed.
