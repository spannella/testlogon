# INV-006 — Per-line-item tax rate assignment on invoices

**Ticket type:** Feature  
**Priority:** P1  
**Estimate:** 2d  
**Feature flag:** `AOS_PER_LINE_TAX_ENABLED` (default `"0"`, off)

---

## 1. Summary & Goal

Allow each invoice line item to carry its own tax rate — expressed as either a
raw basis-points integer (`tax_rate_bps`) or a reference to a named tax group
from the INV-005 registry (`tax_rate_id`). The per-line tax is computed at
invoice creation time, accumulated into the existing `tax_cents` field on the
invoice, and rendered in the PDF as a dedicated per-line tax column with an
itemized breakdown footer.

When the flag is off the existing single platform-wide `invoices_tax_bps` rate
continues to apply unchanged and no new fields are surfaced. When the flag is
on, invoices that supply at least one non-zero per-line rate compute their own
tax total and bypass the platform-wide fallback; invoices that supply only
zero-rated lines fall back to the platform rate as before.

The primary motivation is parity with SuiteCRM's Advanced OpenSales (AOS)
Invoice module, which assigns tax groups from a jurisdiction-labelled registry
at the line-item level rather than applying a single global rate to the invoice
total.

## 3. Data Model

### No new DynamoDB table

All changes are additive attributes on existing `pk=USER#{sub} / sk=INV#{number}`
items in `T.invoices`. No schema changes to `scripts/local-ddb-init.py` are
required for this ticket because the new per-line fields (`tax_rate_bps`,
`tax_cents` on each line-item dict) are stored inside a DynamoDB List attribute
(`line_items`), not as top-level attributes with independent GSI projections. The
`tax_breakdown` field is similarly stored as a List attribute on the top-level
item.

### Per-line-item attribute additions

Each dict inside the `line_items` List attribute gains two new keys when
`AOS_PER_LINE_TAX_ENABLED` is on:

| Attribute | Type | Description |
|-----------|------|-------------|
| `tax_rate_bps` | `int` | Basis points applied to this line's `amount_cents`. 0 = untaxed. |
| `tax_cents` | `int` | Computed: `(amount_cents * tax_rate_bps) // 10_000`. Integer cents. |

Old items written before this ticket have no `tax_rate_bps` or `tax_cents` keys
in their line-item dicts. `_serialize` returns `0` as the default for both via
`_coerce_int`.

### Top-level invoice item addition

| Attribute | Type | Description |
|-----------|------|-------------|
| `tax_breakdown` | `List[dict]` | One entry per distinct `tax_rate_bps` value across all lines: `{name: str, rate_bps: int, tax_cents: int}`. Empty list for invoices where all lines have `tax_rate_bps=0`. |

`name` in the breakdown comes from the tax group's `name` field when the line
was resolved via `tax_rate_id`; otherwise it is auto-derived as
`f"{rate_bps / 100:.2f}% Tax"`.

### Invariants

- `sum(item["tax_cents"] for item in norm_items) == invoice["tax_cents"]` when
  any per-line rate is non-zero.
- When all per-line rates are zero: `invoice["tax_cents"]` equals the
  platform-wide fallback `(amount_cents * S.invoices_tax_bps) // 10_000`.
- `tax_breakdown` is written to the DDB item only when non-empty; old items
  without it return `[]` via `_serialize`.

## 4. API / Service Design

### Service layer: `app/services/invoices.py`

#### Extended `create_invoice` signature

```python
def create_invoice(
    *,
    user_sub: str,
    invoice_type: str,
    amount_cents: int,
    line_items: List[Dict[str, Any]],
    ledger_entry_id: str = "",
    tax_cents: Optional[int] = None,
    seller_id: str = "",
    seller_name: str = "",
    buyer_name: str = "",
    buyer_email: str = "",
    payment_method_summary: str = "",
    currency: str = "usd",
    # INV-006 additions (ignored when AOS_PER_LINE_TAX_ENABLED is off):
    per_line_tax: bool = False,       # opt-in to per-line tax computation
) -> Optional[Dict[str, Any]]:
```

`per_line_tax=True` is the only new parameter on the public signature. The
actual per-line rate values arrive inside the existing `line_items` list as
`tax_rate_bps` (int) and/or `tax_rate_id` (str) keys on each dict.

The boolean opt-in keeps backward compatibility: existing callers that pass
`line_items` without tax keys continue to follow the platform-wide fallback
path regardless of the flag.

#### Line-item normalisation loop (replaces `invoices.py:314–322`)

```python
norm_items: List[Dict[str, Any]] = []
per_line_tax_active = S.aos_per_line_tax_enabled and per_line_tax
total_line_tax = 0
tax_accumulator: Dict[int, Dict[str, Any]] = {}   # rate_bps → {name, tax_cents}

for li in line_items or []:
    desc = str(li.get("description") or "Item")
    qty = _coerce_int(li.get("quantity"), 1)
    line_amount = _coerce_int(li.get("amount_cents"))

    raw_bps = 0
    tax_name = ""
    if per_line_tax_active:
        raw_bps = _coerce_int(li.get("tax_rate_bps"))
        tax_rate_id = str(li.get("tax_rate_id") or "")
        if not raw_bps and tax_rate_id and S.crm_tax_rates_enabled:
            try:
                from app.services.crm_tax_rates import get_tax_rate
                tr = get_tax_rate(tax_rate_id)
                if tr and tr.get("is_active"):
                    raw_bps = _coerce_int(tr.get("rate_bps"))
                    tax_name = str(tr.get("name") or "")
            except Exception:
                pass   # fail-open: treat as 0% if lookup errors
    if not tax_name and raw_bps:
        tax_name = f"{raw_bps / 100:.2f}% Tax"
    line_tax = (line_amount * raw_bps) // 10_000

    norm_item = {
        "description": desc,
        "quantity": qty,
        "amount_cents": line_amount,
        "tax_rate_bps": raw_bps,
        "tax_cents": line_tax,
    }
    norm_items.append(norm_item)
    if raw_bps:
        total_line_tax += line_tax
        bucket = tax_accumulator.setdefault(raw_bps, {"name": tax_name, "rate_bps": raw_bps, "tax_cents": 0})
        bucket["tax_cents"] += line_tax

if not norm_items:
    norm_items = [{"description": invoice_type.title(), "quantity": 1,
                   "amount_cents": amount_cents, "tax_rate_bps": 0, "tax_cents": 0}]
```

#### Tax total resolution

```python
if per_line_tax_active and total_line_tax > 0:
    # Per-line tax overrides the platform-wide fallback.
    if tax_cents is None:
        tax_cents = total_line_tax
    # If caller also supplied an explicit tax_cents it is honoured as-is (rare;
    # used by quote-to-invoice conversion that already summed line taxes).
else:
    # Existing fallback path (invoices.py:305–308) — unchanged:
    if tax_cents is None:
        tax_cents = (amount_cents * max(0, S.invoices_tax_bps)) // 10_000
tax_cents = _coerce_int(tax_cents)
```

#### `tax_breakdown` persistence

```python
tax_breakdown = list(tax_accumulator.values()) if tax_accumulator else []
```

This list is stored on the `record` dict and written to DynamoDB.

#### `_render_invoice_lines` additions (`invoices.py:150–188`)

When `any(li.get("tax_rate_bps", 0) for li in record.get("line_items") or [])`:

1. The line-item table header changes from:
   ```
   Description                     Qty      Amount
   ```
   to:
   ```
   Description                     Qty  Tax Rate      Amount
   ```
   Column widths: Description 28 chars, Qty 4, Tax Rate 9, Amount 12.

2. Each line-item row appends the formatted rate:
   ```python
   rate_str = f"{raw_bps / 100:.1f}%"   # e.g. "9.5%"
   lines.append(f"{desc:<28}{qty:>4}{rate_str:>9}{_money(li_amount):>12}")
   ```

3. In the totals block, after the existing `Tax` row, the `tax_breakdown` list
   is rendered as individual rows:
   ```
   CA Sales Tax (9.5%)            $0.95
   EU VAT (20.0%)                 $2.00
   ```
   When `tax_breakdown` is empty the totals block is unchanged.

4. When no line item has a non-zero `tax_rate_bps` the entire layout is
   identical to today (no extra column, no breakdown rows).

## 5. Detailed Behavior & Edge Cases

### Flag-off invariant

When `S.aos_per_line_tax_enabled` is `False` (the default):
- `per_line_tax_active` is `False` in the normalisation loop.
- All per-line tax processing is skipped; `tax_rate_bps`, `tax_rate_id` keys in
  incoming `line_items` dicts are silently ignored.
- `norm_items` contains `tax_rate_bps=0, tax_cents=0` on every item.
- `tax_breakdown` is an empty list.
- `tax_cents` computation falls through to the existing platform fallback at
  `(amount_cents * max(0, S.invoices_tax_bps)) // 10_000`.
- `_render_invoice_lines` detects no non-zero `tax_rate_bps` and renders the
  existing column layout byte-for-byte.
- Existing `InvoiceLineItemOut` consumers see `tax_rate_bps=0` and `tax_cents=0`
  (from the model defaults), which is backward-compatible with any code that only
  reads `amount_cents`.

### Fallback when all per-line rates are zero

When the flag is on (`per_line_tax_active=True`) but every line item has
`tax_rate_bps=0` and no `tax_rate_id`:
- `total_line_tax` remains `0`.
- The condition `per_line_tax_active and total_line_tax > 0` is `False`.
- The platform fallback applies as before.
- This means callers that opt in via `per_line_tax=True` but forget to set rates
  gracefully degrade rather than zeroing out all tax.

### `tax_rate_id` resolution failure (fail-open)

If `get_tax_rate(tax_rate_id)` raises an exception or returns `None` (unknown
ID, inactive rate, or `CRM_TAX_RATES_ENABLED=0`):
- The `except Exception: pass` block runs.
- `raw_bps` remains `0` for that line.
- The invoice is still created; a warning is NOT logged for inactive rates, but a
  `logger.debug` call is appropriate. A lookup exception does warrant
  `logger.warning`.
- This fail-open matches the pattern used in INV-003 currency conversion
  (`CRM_INVOICES_CURRENCY_TICKETS.md`, INV-003 service changes block).

### Mixed-rate invoices

A single invoice can have lines at different rates (e.g. 0%, 9.5%, 20%). The
`tax_accumulator` dict groups them by `rate_bps` so the breakdown shows:
```
CA Sales Tax (9.5%)    $0.95
EU VAT (20.0%)         $2.00
```
Lines at `rate_bps=0` contribute nothing to `tax_breakdown`.

### Explicit `tax_cents` override from caller

A caller (e.g. QUO-003 quote-to-invoice conversion) may supply an explicit
`tax_cents` keyword argument. When `per_line_tax_active` is on and
`total_line_tax > 0` but `tax_cents` is also supplied, the explicit value is
honoured and replaces the computed sum. This prevents double-counting when the
upstream conversion has already summed the line taxes. The `tax_breakdown` is
still populated from the per-line computation regardless.

### Idempotency via ledger marker

The idempotency path (`_existing_for_ledger` at `invoices.py:252–269`) returns
the serialized existing record on duplicate `ledger_entry_id`. Because the new
fields are included in `_serialize`, a duplicate call returns the same
`tax_breakdown` as the original. No additional idempotency logic is required.

### PDF S3 cache

The PDF stored in S3 reflects the `tax_rate_bps` values at invoice-creation
time. If an invoice is regenerated on cache miss (`invoices.py:449–451`),
`_render_invoice_lines` reads the DDB record and renders the same per-line data,
so the regenerated PDF is identical to the originally stored one.

### `invoice_type="b2b_manual"` (QUO-005 future)

QUO-005 adds a `b2b_manual` invoice type and extends `VALID_TYPES`. When that
ships, manually-created B2B invoices will arrive via
`POST /ui/admin/invoices/manual` with per-line tax data from the
`ManualInvoiceForm` (INV-011). The normalisation loop handles them identically
to auto-generated invoices. No special-casing is needed in INV-006.

### QUO-001 quote line items

QUO-001 (`docs/suitecrm/CRM_QUOTES_CONTRACTS_TICKETS.md`) carries `tax_rate_bps`
on quote line items. The QUO-003 quote-to-invoice conversion passes those values
through as `tax_rate_bps` keys in the `line_items` dicts passed to
`create_invoice`. Since `tax_rate_id` is optional, and `tax_rate_bps` is a raw
int, no INV-005 lookup is needed on the quote-to-invoice path. The conversion
sets `per_line_tax=True` and supplies the already-computed `tax_cents` explicitly
to prevent the fallback rate from overriding the quote's tax.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### No `dev_mode` branches

The entire per-line tax computation runs against the same DynamoDB path in dev
(moto in-process) and prod (real DynamoDB). `app/core/tables.py:547` wires
`T.invoices` from `S.invoices_table_name` in both environments. `crm_tax_rates`
is accessed via its own table handle (`T.crm_tax_rates`, from INV-005) which
is similarly environment-agnostic. There are no `if S.dev_mode` branches in the
service layer. SECOPS-007 parity is preserved.

### Idempotency

Per-line tax data is written to DynamoDB at creation time and never recomputed.
The ledger-marker idempotency path (`invoices.py:252–269`) returns the
serialized stored record including `tax_breakdown`. A second call with the same
`ledger_entry_id` returns the original invoice unchanged.

### Input validation

- `tax_rate_bps` values are coerced via `_coerce_int` before the integer floor
  division. Non-integer or missing values produce `0`.
- `tax_rate_bps` is not separately range-validated in the service; it is the
  caller's responsibility to supply a value in `[0, 10000]` (enforced by
  INV-005's `TaxRateCreateIn` model if the rate comes from the registry, and
  by the `ManualInvoiceForm` Zod schema for manual entry).
- A malicious caller supplying `tax_rate_bps > 10_000` would result in a
  `line_tax` that exceeds `line_amount`, producing an inflated `tax_cents`.
  Since `create_invoice` is an internal service function (not directly called by
  untrusted user input — it is invoked from billing hooks and admin endpoints),
  this is an acceptable trust boundary. Adding a `min(raw_bps, 10_000)` clamp
  inside the loop is low-cost and is RECOMMENDED.
- `tax_rate_id` is an opaque string resolved via DDB lookup; an unknown ID fails
  open to 0% rather than raising.

### Audit trail

The existing `logger.info` at `invoices.py:366–369` already logs
`invoice_number`, `user_sub`, `invoice_type`, and `total_cents`. No separate
`audit_event` call is required for per-line tax (it is an attribute of the
invoice, not a standalone action). If the invoice is created via an admin
manual-creation endpoint (QUO-005 / INV-011), that endpoint emits its own audit
event.

### Security: tax-rate ID ownership

`get_tax_rate` (INV-005) looks up by `TAXRATE#{id}` — globally scoped, not
per-user. Any authenticated user whose billing flow leads to `create_invoice`
could theoretically supply a `tax_rate_id` referencing another tenant's tax
group (in a multi-tenant future). Since tax groups are admin-created platform
resources (not user-owned secrets), this is acceptable. The resolved `rate_bps`
is a public rate; no private data leaks.

## 8. Backward Compatibility & Migration

### Existing invoice items

Items already in `T.invoices` have `line_items` lists without `tax_rate_bps` or
`tax_cents` keys. `_serialize` uses `_coerce_int(li.get("tax_rate_bps"))` which
returns `0` when the key is absent. `InvoiceLineItemOut.tax_rate_bps` and
`tax_cents` default to `0`. `InvoiceOut.tax_breakdown` defaults to `[]`. No
migration script is required.

### Existing callers of `create_invoice`

All existing call sites (billing hooks, test code) use positional keyword
arguments and do not pass `per_line_tax`. The new parameter defaults to `False`,
so all existing callers follow the fallback path without any change.

### `download_invoice_pdf` cache miss regeneration

For existing S3-stored PDFs, a cache miss triggers regeneration from the DDB
record. Old records have no `tax_rate_bps` in their line-item dicts, so `any(li.get("tax_rate_bps", 0) ...)` is `False`, and the regenerated PDF uses the
existing column layout. The regenerated PDF is byte-for-byte equivalent to the
original for untaxed-per-line invoices.

### `just restart` not required

No changes to `scripts/local-ddb-init.py` — the `T.invoices` table definition
is unchanged. A dev-stack restart is not needed to pick up INV-006.

### Forward compatibility with INV-001 and INV-007

When `AOS_INVOICE_FIELDS_ENABLED` (INV-001) is also on:
- `total_cents = amount_cents + tax_cents + shipping_cents - discount_cents`
- `tax_cents` is now the per-line sum when INV-006 is also on.
- The two flags commute: enabling one does not break the other.

## 10. Open Questions / Assumptions

1. **`per_line_tax` opt-in boolean vs always-on when flag is set**: The current
   design requires callers to pass `per_line_tax=True` in addition to enabling
   the flag. An alternative is to auto-detect: if any incoming `line_items` dict
   contains a non-zero `tax_rate_bps` or a `tax_rate_id`, treat it as per-line.
   Auto-detection is simpler for call sites but risks silently activating the
   feature for stale callers that happen to include those keys for other reasons.
   The explicit opt-in is conservative and preferred.

2. **`tax_rate_bps` upper-bound clamp**: The spec recommends a
   `min(raw_bps, 10_000)` clamp inside the loop. Whether this is enforced in the
   service (silently capping) or in a Pydantic model upstream (validation error)
   is left to the implementer. Silent capping is consistent with the
   `_coerce_int` fail-soft pattern in the rest of the file.

3. **PDF column layout overflow**: The current ASCII PDF renderer uses fixed
   character widths. Adding a "Tax Rate" column (9 chars) reduces the Description
   column from 32 to 28 chars. Long descriptions will be truncated at 28 chars
   instead of 30 (existing: `str(li.get("description") or "Item")[:30]`).
   Whether this is acceptable or whether the column widths need adjustment to
   maintain total line width at 48 chars is left to the implementer. The spec
   above uses 28+4+9+12=53, which slightly exceeds the current 48-char ruler.
   Adjust Description to 23 chars (23+4+9+12=48) to stay within the page width.

4. **Tax breakdown deduplication by rate vs by `tax_rate_id`**: The current spec
   groups by `rate_bps` (numeric value). Two different named tax groups with the
   same basis points (e.g. "CA Sales Tax 9.5%" and "NY Sales Tax 9.5%") would
   be merged into a single breakdown entry. Grouping by `tax_rate_id` instead
   would preserve distinct names. For the initial implementation, grouping by
   `rate_bps` is acceptable; INV-005 generally assigns unique rates per
   jurisdiction.

5. **QUO-003 coordination**: The QUO-003 quote-to-invoice conversion is assumed
   to pass `per_line_tax=True` and supply line-level `tax_rate_bps` values that
   were set when the quote was created (QUO-001). The exact call-site wiring in
   QUO-003 is out of scope for INV-006 but must be coordinated at merge time.

## 11. Dependencies

### Hard prerequisites

- **INV-005** (`docs/suitecrm/CRM_INVOICES_CURRENCY_TICKETS.md`, `INV-005`):
  delivers `app/services/crm_tax_rates.py` and `get_tax_rate(tax_rate_id)`.
  INV-006 has a soft dependency on this: per-line tax via raw `tax_rate_bps`
  works without INV-005 being enabled, but `tax_rate_id` resolution requires the
  INV-005 service to be present. When `CRM_TAX_RATES_ENABLED=0`, INV-005's
  `get_tax_rate` raises `ValueError("crm_tax_rates is not enabled")` — the
  `except Exception: pass` block in the normalisation loop catches this and
  treats the line as 0%-taxed (fail-open). INV-005 should ship before or
  alongside INV-006 to avoid import errors if `crm_tax_rates_enabled=True`.

- **QUO-005** (`docs/suitecrm/CRM_QUOTES_CONTRACTS_TICKETS.md`): delivers the
  `b2b_manual` invoice type, `POST /ui/admin/invoices/manual` endpoint, and the
  invoice status lifecycle. INV-006 is independent of QUO-005 for the existing
  auto-generated invoice types (`tip`, `unlock`, `subscription`, `shop`,
  `deposit`), but the INV-012 E2E Section 5 tests use the manual creation
  endpoint delivered by QUO-005.

### Soft / co-development dependencies

- **INV-001** (`CRM_INVOICES_CURRENCY_TICKETS.md`, `INV-001`): adds
  `unit_price_cents`, `discount_cents`, `shipping_cents`, and address fields.
  INV-001 and INV-006 both modify `create_invoice`, `_render_invoice_lines`, and
  `_serialize`. They must be merged without conflict: INV-001 changes the totals
  formula and renderer header/footer; INV-006 changes the line-item loop and
  table column layout. The merge order is INV-001 first, INV-006 second.

- **INV-011** (`CRM_INVOICES_CURRENCY_TICKETS.md`, `INV-011`): delivers
  `ManualInvoiceForm.tsx` with a per-line tax-rate select populated from

  prerequisite for the per-line tax UI in INV-011.

  `tax_rate_bps` on quote line items. The same bps value flows through QUO-003
  quote-to-invoice conversion into `create_invoice`, eliminating the need for a
  `tax_rate_id` lookup on that path.

  Playwright E2E suite including Section 705 for this ticket.
