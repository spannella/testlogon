# CAS-003 — Case priority field (Urgent / High / Medium / Low)

**Type:** Feature | **Priority:** P1 | **Estimate:** 1d  
**Depends on:** CAS-001 (scaffolding, settings, `crm_cases_sla_config` table), CAS-002 (confirms `TicketOut` model change pattern)  
**Consumed by:** CAS-005, CAS-008, CAS-009, CAS-017

---

## 1. Summary & Goal

Introduce a first-class `priority` field (enum `urgent | high | medium | low`) on every ticket record, replacing the current workaround where agents embed priority intent as ad-hoc `complexity:*` labels. Priority is set at creation time by any authenticated user (defaulting to `medium`), updateable at any time by admin/root actors, and exposed as a dedicated GSI so callers can list tickets filtered by a single priority tier without a full-table scan.

With `CRM_CASES_ENABLED=0` (the default) the platform is **byte-for-byte unchanged**: no new GSI rows are written, no new request fields are validated, and all existing tests pass without modification.

### Existing GSI layout on the tickets table

`scripts/local-ddb-init.py:695-710` shows the tickets table has ten GSIs: owner (`gsi1pk/gsi1sk`), status (`gsi2pk/gsi2sk`), assignee (`gsi3pk/gsi3sk`), space, space+status, space+assignee, member-spaces, jira-workspace, jira-issue, jira-sync-state. None carries a priority partition key. Sorting within each GSI is on `gsi_*sk` which uses the `_updated_index_sk(updated_at, ticket_id)` pattern (`app/services/tickets.py:192-193`):

```python

    return f"UPDATED#{updated_at:013d}#TICKET#{ticket_id}"
```

The sort key value is a lexicographic string, **not** a plain integer, so `attr_types` is not required for it — this is consistent with all existing GSI sort keys in the tickets table.

### Optimistic-locking write path

All updates to the META row must go through `TicketStore._conditional_update_meta` (`app/services/tickets.py:723`) or `_apply_header_update_once` (`app/services/tickets.py:792`), which enforces optimistic concurrency via a `version` counter. The new `update_priority` method must follow this pattern.

**Important**: `_apply_header_update_once` does **not** contain a retry loop — on a version conflict it raises `TicketStateError({"code": "ticket_update_conflict", ...})` and returns immediately (lines 799–804). The `while True:` loop visible at line 680 belongs to `_query_all_headers_by_index`, a different method. Any caller of `update_priority` that needs retry-on-conflict must implement the loop externally (e.g. the HTTP handler catches `TicketStateError` and the client retries).

### 4.4 New `TicketStore.update_priority` method

```python
def update_priority(
    self,
    *,
    ticket_id: str,
    new_priority: str,
    actor_sub: str,
) -> dict[str, Any] | None:
    """Update the priority field via optimistic-locking. Returns None if ticket not found."""
    if new_priority not in _PRIORITY_VALUES:
        raise ValueError(f"invalid priority: {new_priority!r}")

    def build_values(cur: dict[str, Any]) -> dict[str, Any]:
        ts = now_ts()
        tid = cur["ticket_id"]
        return {
            ":status": cur["status"],
            ":assigned_admin_sub": cur.get("assigned_admin_sub"),
            ":assigned_to_sub": cur.get("assigned_to_sub"),
            ":assigned_by": cur.get("assigned_by"),
            ":assigned_at": cur.get("assigned_at"),
            ":updated_at": ts,
            ":last_message_at": cur.get("last_message_at", ts),
            ":last_message_by_role": cur.get("last_message_by_role", "user"),
            ":gsi1sk": _updated_index_sk(ts, tid),
            ":gsi2pk": _status_index_pk(cur["status"]),
            ":gsi2sk": _updated_index_sk(ts, tid),
            ":gsi3pk": _assignee_index_pk(cur.get("assigned_to_sub") or "unassigned"),
            ":gsi3sk": _updated_index_sk(ts, tid),
            # space GSI keys (may be None → handled by _conditional_update_meta REMOVE logic)
            ":gsi_space_pk": _space_index_pk(cur["space_id"]) if cur.get("space_id") else None,
            ":gsi_space_sk": _updated_index_sk(ts, tid) if cur.get("space_id") else None,
            ":gsi_space_status_pk": _space_status_index_pk(cur["space_id"], cur["status"]) if cur.get("space_id") else None,
            ":gsi_space_status_sk": _updated_index_sk(ts, tid) if cur.get("space_id") else None,
            ":gsi_space_assignee_pk": _space_assignee_index_pk(cur["space_id"], cur.get("assigned_to_sub") or "unassigned") if cur.get("space_id") else None,
            ":gsi_space_assignee_sk": _updated_index_sk(ts, tid) if cur.get("space_id") else None,
        }

    result = self._apply_header_update_once(ticket_id=ticket_id, build_values=build_values)
    if result is None:
        return None

    # Write the priority attribute separately via a simple update_item (not version-gated).
    # Rationale: priority is an annotation, not a state transition; same pattern as
    # kyc_cases.py:escalate_case which writes escalation fields without bumping version.
    # The _conditional_update_meta call above already bumped version + gsi keys.
    ts = now_ts()
    self._table.update_item(
        Key={"pk": _ticket_pk(ticket_id), "sk": "META"},
        UpdateExpression=(
            "SET priority = :priority, gsi_priority_pk = :gpk, gsi_priority_sk = :gsk"
        ),
        ExpressionAttributeValues={
            ":priority": new_priority,
            ":gpk": _priority_index_pk(new_priority),
            ":gsk": _updated_index_sk(ts, ticket_id),
        },
    )
    return self.get_ticket(ticket_id)
```

**Design note**: `update_priority` calls `_apply_header_update_once` first (to bump `updated_at` and all existing GSI sort keys in one atomic conditional write), then writes the `priority` / `gsi_priority_*` attributes in a second unconditional `update_item`. This mirrors the pattern in `kyc_cases.escalate_case` (KYC-008/GAP-0265), which writes `review.escalated*` fields after the version-bumped state write. The two-step approach is safe here because: (a) the version bump already happened, preventing a concurrent conflicting update from also changing priority; (b) `gsi_priority_pk` / `gsi_priority_sk` are not part of `_conditional_update_meta`'s fixed SET clause, so they cannot be inadvertently cleared.

**Conflict behaviour**: `_apply_header_update_once` raises `TicketStateError` on a version conflict; it does NOT silently retry. The `update_ticket_priority` HTTP handler should catch `TicketStateError` and return a 409 `ticket_update_conflict` response (mirroring `set_ticket_status` at `app/routers/tickets.py:1005`). The client (or admin tooling) is responsible for re-reading the ticket and retrying if desired.

## 5. Detailed Behavior & Edge Cases

### Priority on creation
- Any authenticated user can supply `priority` in `CreateTicketReq`. The field is optional and defaults to `"medium"`.
- An unrecognized value (not in the Literal union) returns HTTP 422 from Pydantic before reaching the service layer.
- When `S.crm_cases_enabled` is `False`, `priority` in the request body is parsed but silently discarded; the META row is not written with a `priority` attribute.

### Priority on update
- Only admin/root/`tickets:admin`-key actors may call `PATCH /tickets/{id}/priority`.
- Non-admin callers → 403 `admin_role_required`.
- Unknown `ticket_id` → 404 `ticket_not_found`.
- Flag off → 404 (endpoint does not exist from the caller's perspective).
- Valid call on a ticket that was created with `S.crm_cases_enabled=False` (no `priority` attribute): the two-step write sets `priority` for the first time — this is additive and safe.
- Concurrent priority updates: each `update_priority` call starts by calling `_apply_header_update_once`, which uses `_conditional_update_meta` with a version check. If two concurrent requests race, one will fail the condition check and `_apply_header_update_once` will raise `TicketStateError` (it does **not** retry — see note in Section 2). The `update_ticket_priority` HTTP handler must catch `TicketStateError` and return 409 so clients can retry. The result is last-write-wins within a short window; this is acceptable for an annotation field.

### Priority filtering in `GET /tickets`
- `?priority=urgent` with `S.crm_cases_enabled=True` queries `crm_cases_priority_index` via `gsi_priority_pk = PRIORITY#urgent`.
- `?priority=urgent` with `S.crm_cases_enabled=False` silently falls back to the default status-based path (returns open tickets regardless of priority, since no priority GSI rows exist).
- An unrecognized priority value is rejected by Pydantic as a `Literal` violation → 422.
- `priority` and `status` filters are mutually exclusive in the service: if `priority` is present and `S.crm_cases_enabled`, it takes precedence (consistent with how `owner_sub` short-circuits `assignee_sub`).
- `priority` and `owner_sub` are compatible: caller supplies both → service uses `owner_sub` (its branch runs first). If a caller needs "all urgent tickets for a specific owner", that is a cross-filter not natively supported by this GSI; callers should query by priority and filter client-side, or use the owner GSI and filter client-side. This limitation is intentional to avoid adding a composite GSI in the first iteration.

### `gsi_priority_sk` on updates
- Any call to `_apply_header_update_once` (e.g. via `update_status`, `assign_ticket`, `add_message`) bumps `updated_at`. It does **not** know about `gsi_priority_sk`. Therefore, after a status change, `gsi_priority_sk` may become stale (pointing to an old `updated_at`).
- To keep the priority GSI sort order fresh after every metadata update, the second `update_item` in `update_priority` already refreshes `gsi_priority_sk`. However, for updates made via other paths (status change, assignment), `gsi_priority_sk` is not refreshed — the priority index sort order reflects last-priority-change time, not last-update time. This is acceptable for the P1 iteration; a later ticket may add `gsi_priority_sk` refresh to `_conditional_update_meta` if precise recency sort within a priority bucket becomes important.

### Audit event
- `ticket_priority_changed` is emitted via `_emit_ticket_alerts` for `owner_sub`. It is passed to `audit_event` from `app/services/alerts.py:644`.
- `ticket_priority_changed` is **not** added to the inline event-type set inside `render_ticket_email_template` (`app/services/alerts.py:236`) in CAS-003 — priority changes are operational signals, not customer-facing events. CAS-004 may promote it to an email event if needed.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 — no dev_mode branch
All code paths (flag check, DynamoDB write, GSI query) are identical in dev and prod. There is no `if S.dev_mode` branch in any CAS-003 code. The moto-backed DynamoDB local instance in dev runs the same `query` call against the same GSI name.

### Idempotency
- `create_ticket` is already idempotent via `get_ticket` guard at `app/services/tickets.py:431-433`: if a `ticket_id` is supplied and already exists, the existing ticket is returned without incrementing counters or writing priority again.
- `update_priority` is effectively idempotent: calling it twice with the same priority value writes the same DynamoDB attributes. Note that each call also bumps `version` via `_apply_header_update_once`, so calling it twice on an unchanged ticket increments `version` twice — this is the same behaviour as any other update path and is acceptable for an annotation field.

### Auth hardening
- `PATCH /{ticket_id}/priority` is admin-only. The check uses `_is_admin_actor(request, user)` (`app/routers/tickets.py:224`), which covers `Role.ADMIN`, `Role.ROOT`, and `tickets:admin` API-key scope — consistent with `set_ticket_status` (`app/routers/tickets.py:992`; admin gate at line 999) and `assign_ticket` (`app/routers/tickets.py:914`).
- Non-admin users who supply `priority` in `CreateTicketReq` are **allowed** — priority is a public creation field. If the platform wants to restrict creation-time priority to admins, that is a future policy change; the default is permissive (SuiteCRM allows submitters to self-select priority).
- The `priority` Literal constraint prevents injection of arbitrary strings at the Pydantic validation layer before the service is reached.

### GSI write safety
`gsi_priority_pk` and `gsi_priority_sk` are only written when `S.crm_cases_enabled`. When the flag is off, these attributes are absent from the DynamoDB item entirely, so the `crm_cases_priority_index` GSI (which may not exist yet until CAS-001 is applied) is never projected. This is safe because DynamoDB Local and real DynamoDB silently omit items from a GSI when the projected key attributes are absent.

## 8. Backward Compatibility & Migration

### Existing tickets (created before CAS-003 is deployed)
All pre-existing tickets have no `priority` attribute on their META rows. After deployment:
- `get_ticket` returns `priority: None` for these rows. `TicketOut.priority` is `str | None` — clients must handle `None`.
- `PATCH /tickets/{id}/priority` on a pre-existing ticket works correctly: the unconditional `update_item` sets `priority` for the first time.
- `GET /tickets?priority=medium` does **not** return pre-existing tickets because they have no `gsi_priority_pk` attribute → they are absent from the `crm_cases_priority_index`.
- Operators who want existing open tickets to appear in priority queries should run a one-off backfill script (not in scope for CAS-003 but described in Open Questions).

### Clients (`TicketOut` / `TicketListItemOut` schema)
`priority: str | None = None` is additive. Existing clients that don't read `priority` continue to work. The frontend `Ticket` interface in `frontend/src/api/endpoints/tickets.ts:23-38` gains `priority?: string | null` (optional field).

### `CreateTicketReq` is backward-compatible
`priority` defaults to `"medium"` and is optional. Existing API clients that POST without `priority` continue to work.

### Existing GSI layout
No existing GSI is modified. One new GSI entry is added to the `tickets` table definition in `scripts/local-ddb-init.py`. In dev, `just restart` recreates all tables and picks up the new GSI. In production, an `UpdateTable` call must add the new GSI before deploying code that writes `gsi_priority_pk` — the code is safe to deploy first (it writes the attribute only when flag is on, and an absent GSI means the attribute is simply not indexed; it doesn't cause an error).

## 10. Open Questions / Assumptions

1. **Backfill existing tickets**: Pre-existing ticket META rows have no `priority` attribute. Should a one-off migration script set them to `"medium"` so `GET /tickets?priority=medium` returns all legacy tickets? Recommendation: defer to a CAS-003-backfill task run on opt-in by the operator. Default assumption is that legacy tickets remain `null` until explicitly updated.

2. **Submitter-controlled priority**: The current design allows any authenticated user to set priority at creation time (defaulting to `medium`). SuiteCRM allows submitters to self-select. If the product team decides creation-time priority should be admin-only, add an `if not S.crm_cases_enabled or _is_admin(user):` guard in the `create_ticket` endpoint and ignore the field for regular users.

3. **`gsi_priority_sk` freshness on non-priority updates**: After a status or assignment change, `gsi_priority_sk` is not refreshed (it retains the `updated_at` from the last priority write, or the `created_at` if priority was never changed). Items within a priority bucket are therefore sorted by "last priority change" rather than "last activity". This may be surprising to CAS-017 analytics. Resolution: CAS-003 leaves this as-is; CAS-017 can add a `gsi_priority_sk` refresh to `_conditional_update_meta` if recency sort within priority buckets is required.

4. **`priority` in `TicketAdminSummary`**: CAS-017 plans a `open_by_priority` breakdown (line 568 of the source ticket). That metric can be derived from the `crm_cases_priority_index` GSI added here. No change to `TicketAdminSummary` is needed in CAS-003.

5. **Enum casing**: The ticket uses lowercase enum values (`urgent`, `high`, `medium`, `low`) matching SuiteCRM's internal representation. The frontend should display them as capitalized labels (`Urgent`, `High`, `Medium`, `Low`) using a simple `priority.charAt(0).toUpperCase() + priority.slice(1)` transform or a lookup map — this is a frontend concern and not part of the backend spec.
