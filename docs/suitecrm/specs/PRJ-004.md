# PRJ-004 — Task dependencies and resource assignment

**Ticket type:** Feature
**Priority:** P1
**Estimate:** 2 days
**Area:** CRM Projects, Project Tasks & Gantt
**Source:** `docs/suitecrm/CRM_PROJECTS_GANTT_TICKETS.md` § "PRJ-004"

---

## 1. Summary & Goal

PRJ-004 extends the CRM project task entity (introduced in PRJ-003) in two tightly coupled directions:

1. **Task dependencies** — a task can declare one or more predecessor tasks (finish-to-start links). The service validates that: all predecessors belong to the same project; no circular dependency exists across the full task graph; and if the task has an explicit `start_date`, that date is no earlier than the latest `end_date` of any direct predecessor.

2. **Resource assignment** — each task can be assigned to a single platform user (`assigned_user_sub`) or, in anticipation of the future PTY party model, to a CRM contact party (`linked_contact_id`). A new `project_resource_type` field (`"user"` | `"contact"`) distinguishes the two. A new read endpoint, `GET /{project_id}/workload`, aggregates per-assignee task counts and overdue counts for the project.

When `CRM_PROJECTS_ENABLED=0` (the default) the platform is byte-for-byte unchanged. All new logic extends the existing `crm_pm_tasks` table and `app/services/crm_project_tasks.py` service module introduced in PRJ-003; no new DynamoDB tables are required.

## 4. API / Service Design

### 4.1 Core validation helpers — `app/services/crm_project_tasks.py`

Two new private helpers power the dependency contract:

#### `_load_all_project_tasks(project_id: str) -> Dict[str, dict]`

Queries `T.crm_pm_tasks` with `PK = "PROJECT#{project_id}"`, `SK begins_with("TASK#")`, no limit (loop via `LastEvaluatedKey` per the CLAUDE.md "DDB FilterExpression doesn't reduce page size" guidance). Returns a dict keyed by `task_id` → raw DDB item. Called once per `create_task` / `update_task` invocation when `predecessor_task_ids` is non-empty.

**Note on page size**: each loop iteration passes `Limit=1000` and accumulates until `LastEvaluatedKey` is absent. A project with thousands of tasks is pathological for an MVP — the workload is bounded in practice to a few hundred tasks. No pagination is exposed to the caller; this is an internal helper.

#### `_detect_cycle(task_id: str, new_predecessors: List[str], all_tasks: Dict[str, dict]) -> Optional[str]`

Builds a directed adjacency graph from `all_tasks` where each edge is `predecessor → successor`. The subject task's edges are replaced (not merged) with `new_predecessors` for the purpose of this check. Runs iterative DFS from `task_id` following predecessor links (reverse direction, i.e. can I reach `task_id` starting from any of `new_predecessors`?). Returns the ID of the task that forms the cycle root if one is found, or `None` if the graph is acyclic.

Implementation uses an explicit stack (not recursion) to avoid Python's default 1000-frame stack limit on deep dependency chains:

```python
def _detect_cycle(
    task_id: str,
    new_predecessors: List[str],
    all_tasks: Dict[str, dict],
) -> Optional[str]:
    # Build predecessor map: task_id → set of its predecessor IDs
    pred_map: Dict[str, List[str]] = {}
    for tid, item in all_tasks.items():
        preds = item.get("predecessor_task_ids") or []
        pred_map[tid] = list(preds)
    # Override the subject task's predecessors with the proposed new set
    pred_map[task_id] = list(new_predecessors)

    # DFS: starting from each proposed predecessor, can we reach task_id?
    # If yes, adding task_id → predecessor would create a cycle.
    for start in new_predecessors:
        visited: set = set()
        stack = [start]
        while stack:
            current = stack.pop()
            if current == task_id:
                return start   # cycle root
            if current in visited:
                continue
            visited.add(current)
            stack.extend(pred_map.get(current) or [])
    return None
```

#### `_max_predecessor_end_date(predecessor_ids: List[str], all_tasks: Dict[str, dict]) -> Optional[int]`

Returns the maximum `end_date` (integer Unix seconds) across all listed predecessors, or `None` if no predecessor has an `end_date` set. Used by the date conflict check.

### 4.2 Service function modifications — `app/services/crm_project_tasks.py`

#### `create_task` (extend PRJ-003 implementation)

After the basic field validation and before the DynamoDB `put_item`, when `predecessor_task_ids` is non-empty:

1. **Same-project check**: call `_load_all_project_tasks(project_id)`. For each ID in `predecessor_task_ids`, assert it exists in the returned dict. Missing ID → `HTTPException(400, {"code": "predecessor_not_found", "task_id": missing_id})`.

2. **Cycle check**: call `_detect_cycle(new_task_id, predecessor_task_ids, all_tasks)`. Cycle detected → `HTTPException(400, {"code": "circular_dependency", "cycle_root": cycle_root_id})`.

3. **Date conflict check**: if `start_date` is provided, call `_max_predecessor_end_date(predecessor_task_ids, all_tasks)`. If `max_end_date` is not `None` and `start_date < max_end_date` → `HTTPException(400, {"code": "predecessor_date_conflict", "blocking_task_id": id_of_max_end_date_task})`.

After validation, set `project_resource_type` on the item:
- If `linked_contact_id` is provided and `project_resource_type` is absent or `"contact"`, set `project_resource_type = "contact"`.
- Otherwise default to `"user"`.

Set `GSI2PK` based on the resolved resource type (see §3.1).

Emit audit event on successful creation when a non-empty assignment exists:
```python
audit_event("crm_task.assigned", owner_sub, None,
            project_id=project_id, task_id=task_id,
            resource_type=project_resource_type, assigned_id=assigned_id)
```

#### `update_task` (extend PRJ-003 implementation)

When `predecessor_task_ids` is in `updates.model_fields_set` and is non-empty:

1. **Same-project check**: load all tasks via `_load_all_project_tasks(project_id)`. Cross-project predecessors → 400 `predecessor_not_found`.

2. **Cycle check**: call `_detect_cycle(task_id, new_predecessors, all_tasks)`. Cycle → 400 `circular_dependency`.

3. **Date conflict check**: use the _merged_ `start_date` (new value if supplied in `updates`, else existing value from DDB). If merged `start_date` is not `None` and `start_date < max(predecessors' end_dates)` → 400 `predecessor_date_conflict`.

When `predecessor_task_ids` is set to an empty list (`[]`), it clears all predecessors. The DDB `UpdateExpression` sets the attribute to an empty List rather than using `REMOVE` so that the absence-vs-empty distinction is explicit.

When `assigned_user_sub`, `linked_contact_id`, or `project_resource_type` change, rewrite `GSI2PK` in the same `update_item` call to keep the workload index consistent.

Emit `crm_task.dependency_set` audit event when `predecessor_task_ids` changes (non-empty→new set or clear):
```python
audit_event("crm_task.dependency_set", owner_sub, None,
            project_id=project_id, task_id=task_id,
            predecessor_count=len(new_predecessors))
```

All audit calls are wrapped in `try/except Exception: pass` — audit failure must never block the task write.

#### `get_project_workload` (new function)

```python
def get_project_workload(
    owner_sub: str,
    project_id: str,
) -> CrmProjectWorkloadResp:
```

1. Calls `get_crm_project(owner_sub, project_id)` to assert ownership (or PRJ-007 member access).
2. Calls `_load_all_project_tasks(project_id)` to retrieve every task item.
3. Groups items by `GSI2PK`. For each distinct `GSI2PK` value:
   - Parses `resource_type` and `assigned_id` from the prefix: `"ASSIGNEE#{user_sub}"` → `resource_type="user"`, `assigned_id=user_sub`; `"ASSIGNEE#contact#{contact_id}"` → `resource_type="contact"`, `assigned_id=contact_id`; `"ASSIGNEE#unassigned"` → skip (unassigned tasks are not included in workload entries).
   - `task_count`: number of tasks in the group.
   - `overdue_count`: tasks where `end_date is not None`, `end_date <= now_ts()`, and `percent_complete < 100`.
4. Returns `CrmProjectWorkloadResp(project_id=project_id, entries=[...])` sorted by `task_count` descending.

## 5. Detailed Behavior & Edge Cases

### 5.1 Same-project predecessor enforcement

`predecessor_task_ids` contains task IDs. The service does not accept task IDs from other projects — it queries `_load_all_project_tasks(project_id)` and verifies each listed predecessor exists in the result. A task ID that belongs to a different project is indistinguishable from a non-existent task from the caller's perspective; both return `400 predecessor_not_found`.

### 5.2 Circular dependency detection

A cycle `A → B → A` is detected when: task A is being updated with `predecessor_task_ids = [B]`, and the existing task B already has `predecessor_task_ids` containing A (directly or transitively). The DFS in `_detect_cycle` covers both direct and transitive cycles. The error response includes `cycle_root` — the first predecessor that creates the loop — to give the frontend actionable feedback.

A self-referential predecessor (`task_id` in its own `predecessor_task_ids`) is a degenerate cycle detected in O(1) before the DFS: the ID is found in `new_predecessors`, so the DFS immediately encounters `task_id == task_id`.

### 5.3 Predecessor date conflict — partial date scenarios

The date conflict check (`start_date < max(predecessor end_dates)`) applies only when all three conditions hold:
- The subject task's resolved `start_date` (after merge) is not `None`.
- At least one predecessor has a non-`None` `end_date`.
- `start_date < max_predecessor_end_date`.

Predecessors with `end_date = None` do not contribute to `max_predecessor_end_date`. This is intentional: unscheduled predecessors do not constrain the successor's start date.

The `blocking_task_id` in the error response is the ID of the predecessor with the maximum `end_date` — the one most directly constraining the schedule.

### 5.4 Resource type mutual exclusion

When both `assigned_user_sub` and `linked_contact_id` are provided in the same request:
- If `project_resource_type = "user"`: `linked_contact_id` is ignored and not stored.
- If `project_resource_type = "contact"`: `assigned_user_sub` is stored as-is for display purposes (the task history) but `GSI2PK` is set to the contact prefix so the workload index reflects the contact assignment.
- If `project_resource_type` is absent: `linked_contact_id` takes precedence when present (`resource_type="contact"`); otherwise `assigned_user_sub` drives `resource_type="user"`.

### 5.5 Clearing predecessors

Setting `predecessor_task_ids = []` explicitly clears all predecessors. An absent `predecessor_task_ids` in a `PATCH` request (not in `model_fields_set`) leaves the existing list unchanged. These two behaviors must be distinct in the `update_task` implementation.

### 5.6 Unassigned tasks in workload

Tasks with `GSI2PK = "ASSIGNEE#unassigned"` are not included in `CrmProjectWorkloadResp.entries`. The caller can infer the unassigned count from `total_tasks - sum(entry.task_count for entry in entries)`, where `total_tasks` is available from the task list endpoint.

### 5.7 Concurrent updates and predecessor integrity

Two concurrent `PATCH` requests to task B and task C both adding each other as predecessors could create a cycle if the cycle check reads a stale state. PRJ-004 does not implement transactional cycle detection (DynamoDB transactions would require a `TransactWriteItems` across all task items). The race window is small in practice (cycle detection reads the full task graph before the write). A follow-up ticket can add DDB conditional expressions on `version` counters if cycle races are observed.

### 5.8 `linked_contact_id` — PTY soft dependency

`linked_contact_id` is stored and returned as an opaque string. No lookup is performed against PTY party records in PRJ-004 because PTY-001..PTY-015 have not shipped. The field is reserved for future resolution. Once PTY ships, a validation layer can be added without changing the DDB schema.

### 5.9 Flag-off behavior

When `CRM_PROJECTS_ENABLED=0`, `_require_crm_projects()` raises `HTTPException(404)` before any service code runs. No DynamoDB calls are made, no audit events are emitted, and no cycle detection executes.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 — no dev_mode branches

There are no `if S.dev_mode:` branches in `app/services/crm_project_tasks.py` for any PRJ-004 logic. The cycle-detection algorithm, date conflict check, and workload aggregation run identically in dev (moto-backed DynamoDB Local port 8001) and prod (real DynamoDB). The `T.crm_pm_tasks` handle transparently resolves to the correct endpoint through the `_safe_table(S.crm_pm_tasks_table_name)` wiring. `audit_event` at `app/services/alerts.py:644` already implements parity (dev writes to local log; prod writes to DDB + optional SES).

### 7.2 Idempotency

`create_task` uses a `ConditionExpression="attribute_not_exists(PK)"` guard (inherited from PRJ-003). A retried create with the same generated `task_id` raises `ConditionalCheckFailedException`, which the service converts to `HTTP 409 Conflict` — correct, since a retry would be creating a second task, not replaying the first.

`update_task` uses `ConditionExpression="attribute_exists(PK)"` to guard against writing to a deleted task. Replaying the same PATCH with the same `predecessor_task_ids` is idempotent: the cycle detection will pass (the existing graph already includes these predecessors, no new cycle is introduced), and the DDB `update_item` writes the same values.

### 7.3 Ownership and access control

`create_task` and `update_task` assert project ownership by calling `get_crm_project(owner_sub, project_id)` (PRJ-002), which raises 404 if `item["owner_sub"] != owner_sub`. This means a non-owner cannot set dependencies even if they know both task IDs. PRJ-007 will extend this to member-role access by replacing the ownership assertion with `_assert_project_access(caller_sub, project_id, min_role="member")`.

`get_project_workload` performs the same ownership assertion. The workload endpoint does not reveal task counts for projects the caller does not own.

### 7.4 Predecessor enumeration as IDOR vector

The `predecessor_not_found` error (400) is returned when a task ID belongs to a different project, not 404. This prevents an attacker from using the dependency endpoint to probe whether arbitrary task IDs exist in other users' projects by distinguishing "task exists but belongs to another project" vs "task does not exist." Both cases return the same `predecessor_not_found` code.

### 7.5 Input size limits

`predecessor_task_ids` is capped at 50 entries per task (enforced by Pydantic `max_items=50`). Longer lists would cause `_load_all_project_tasks` + `_detect_cycle` to be called unnecessarily and risk a large DFS. The 50-predecessor cap is generous for real-world project management use.

## 8. Backward Compatibility & Migration

### 8.1 Existing task items

PRJ-003 task items stored before PRJ-004 ships lack `project_resource_type` and `linked_contact_id`. The service reads these fields with `.get("project_resource_type", "user")` and `.get("linked_contact_id")` — absent fields default to `"user"` and `None` respectively. No backfill or migration script is required.

Existing `predecessor_task_ids` values (which PRJ-003 stores as-is with no validation) are trusted as-is by the cycle detector. Since PRJ-003 stores only caller-supplied values with no validation, a corrupted predecessor set could theoretically contain cross-project IDs. PRJ-004 treats such stale data conservatively: `_load_all_project_tasks` returns only same-project tasks, so any cross-project IDs from PRJ-003 are treated as missing predecessors and excluded from cycle detection without error.

### 8.2 `GSI2PK` for pre-existing items

Existing task items written by PRJ-003 have `GSI2PK = "ASSIGNEE#{user_sub}"` (or `"ASSIGNEE#unassigned"`). The new `"ASSIGNEE#contact#{contact_id}"` prefix is additive. Workload aggregation in `get_project_workload` strips prefixes from `GSI2PK` values; existing string-form entries are parsed correctly by the `user` branch of the parser.

### 8.3 PRJ-007 extension contract

When PRJ-007 ships, the ownership assertion in `create_task`, `update_task`, and `get_project_workload` is replaced with `_assert_project_access(caller_sub, project_id, min_role="member")`. The dependency validation logic, cycle detection, and workload aggregation are unchanged. PRJ-004 does not need to anticipate or stub this replacement.

### 8.4 PRJ-008 (Gantt) consumption

The Gantt chart component in PRJ-008 reads `predecessor_task_ids` from task items to render dependency arrows. PRJ-004 ensures these IDs are always valid same-project IDs (or an empty list), which simplifies the Gantt renderer: it can trust the array without defensive filtering.

## 10. Open Questions / Assumptions

1. **Finish-to-start only**: PRJ-004 implements only finish-to-start dependency links (predecessor must complete before successor can start). SuiteCRM supports additional dependency types (start-to-start, finish-to-finish, start-to-finish). These are deferred; the `predecessor_task_ids` list is the authoritative representation and can be extended with a `dependency_type` attribute per link in a follow-up.

2. **Date conflict is advisory**: The spec raises HTTP 400 on date conflicts. An alternative is to auto-push `start_date` to match the latest predecessor `end_date`. This ticket chooses the strict 400 to keep scheduling intent explicit — the user should consciously resolve conflicts. The auto-push behavior can be added as a query parameter (`?auto_adjust_dates=true`) later.

3. **Graph load on every mutation**: `_load_all_project_tasks` fetches all tasks in the project on every `create_task` / `update_task` with non-empty `predecessor_task_ids`. For projects with hundreds of tasks this adds a DDB query on every mutation. A future optimization could maintain a separate dependency-graph summary item or use DDB Streams to maintain an adjacency cache, but this is not warranted at MVP scale (sub-100 tasks per project).

4. **`linked_contact_id` namespace collision**: Using `"ASSIGNEE#contact#{contact_id}"` as `GSI2PK` avoids collision with user subs only if PTY contact IDs do not contain `#` characters. The assumption is that PTY `party_id` values are UUID hex strings. If PTY uses a different format, the GSI prefix must be adjusted when PTY integration ships (PRJ-010 / PRJ-011).

5. **Workload endpoint caller is always owner**: PRJ-004 enforces ownership via `get_crm_project(owner_sub, ...)`. Once PRJ-007 ships, `viewer`-role members should also be able to call `GET /workload`. The workload endpoint does not modify data, so `min_role="viewer"` is the correct access level. This will require a one-line change in PRJ-007's `_assert_project_access` call.
