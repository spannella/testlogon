# KB-012 — Admin KB Management UI (React Frontend)

**Type:** Feature | **Priority:** P2 | **Estimate:** 3d  
**Ticket source:** `docs/suitecrm/CRM_KNOWLEDGE_BASE_TICKETS.md` §KB-012

---

## 1. Summary & Goal

KB-012 delivers the complete React frontend layer for the Knowledge Base system introduced by KB-001 through KB-011. The deliverable is twofold:

1. **Admin management UI** — a role-gated set of pages under `/admin/knowledge` that allow users with `role >= admin` to create, edit, publish, expire, delete, tag, relate, and manage revisions for KB articles, as well as manage the category tree.
2. **Public-facing Help Center** — unauthenticated pages at `/knowledge` and `/knowledge/:articleId` that let any visitor browse published articles by category or tag, search by keyword, and submit helpful/not-helpful ratings.

Both surfaces are **entirely additive and default-off**. The flag `VITE_KNOWLEDGE_BASE_ENABLED=1` (or `KNOWLEDGE_BASE_ENABLED=1` for the backend, already gating all API endpoints to 404) must be set for any of the new pages to become navigable. With the flag off the React routes still exist in the bundle but the pages immediately render a "Feature not available" notice; the nav links are hidden entirely.

## 3. Data Model

KB-012 is a pure frontend ticket. It consumes the DynamoDB-backed backend APIs defined in KB-001 through KB-011 and introduces no new tables, GSIs, or DynamoDB rows of its own.

The relevant backend table is `crm_kb_articles` (provisioned by KB-001 in `scripts/local-ddb-init.py`), accessed exclusively through the API endpoints defined in KB-002 through KB-011. The frontend never writes to DynamoDB directly.

For completeness the consumed DDB row shapes are:

| Row type | PK | SK | Purpose |
|---|---|---|---|
| Article META | `ARTICLE#{id}` | `META` | Core article fields |
| Attachment | `ARTICLE#{id}` | `ATTACHMENT#{att_id}` | KB-003 |
| Category | `CATEGORY#{id}` | `META` | KB-004 |
| Rating | `ARTICLE#{id}` | `RATING#{user_sub}` | KB-005 |
| Tag index | `TAG#{tag}` | `ARTICLE#{id}` | KB-007 |
| Related link | `RELATED#{id}` | `ARTICLE#{rel_id}` | KB-008 |

| Revision | `REVISION#{id}` | `REV#{ts}#{rev_id}` | KB-010 |

The `attr_types` requirement (numeric GSI sort keys declared in `scripts/local-ddb-init.py`) is satisfied by KB-001; KB-012 adds nothing to that file.

## 5. Detailed Behavior & Edge Cases

### 5.1 New pages — directory: `frontend/src/pages/knowledge/`

All six new page components live here.

#### `KbPublicPage.tsx` — route `/knowledge`

Renders the public Help Center. Uses `publicListArticles` and `publicSearch` from `kb.ts`. Layout:

- Search bar at top. `onChange` debounced 300 ms; on input longer than 1 character calls `publicSearch(q)` and replaces the article list with search results. On clear, reverts to the category-filtered or all-articles list.
- Left sidebar: category tree built by nesting the flat `listCategories()` result on `parent_id`. Clicking a category sets a `categoryId` state param and refetches `publicListArticles({ category_id })`. "All articles" breadcrumb clears the filter.
- Article cards: title (link to `/knowledge/{id}`), excerpt, tag chips, `view_count`, helpful/not-helpful ratio bar. No auth required to view cards.
- Infinite scroll: `useInfiniteQuery` with `cursor` param. `getNextPageParam` returns `cursor` from each page response; `undefined` cursor ends the list.
- When the flag is off (`isKnowledgeBaseEnabled() === false`) renders a `<Card>` with text "The Help Center is not currently available." and no API calls are made.

#### `KbArticlePage.tsx` — route `/knowledge/:articleId`

Individual article view. Uses `publicGetArticle(articleId)`. No auth required.

- Renders `article.body_html` via `dangerouslySetInnerHTML` inside a `prose` Tailwind class container. The backend already sanitizes HTML via `render_markdown_sanitized_html` before storing, so raw insertion is safe.
- Attachment list rendered as download links using `<a href={att.url} target="_blank" download>` for each `KbAttachmentOut` in `article.attachments`.
- Related articles panel calls `GET /public/kb/articles/{id}/related` (not in the main `kb.ts` endpoint list — add `listRelated(articleId)` making a `GET /public/kb/articles/{articleId}/related` call returning `KbArticleSummary[]`). Related cards are click-through links.
- Helpful/not-helpful buttons call `rateArticle(articleId, helpful)` via `useMutation`. Requires session: if `!isAuthenticated` the buttons are disabled with tooltip "Sign in to rate this article." On success, `queryClient.invalidateQueries(["kb", "public", "article", articleId])` refreshes counts. Optimistic update: immediately flip the local count.
- Back-to-search breadcrumb: if the user arrived from `/knowledge` with a search query preserved in `location.state.q`, the breadcrumb reads "Back to search results for '{q}'".

#### `KbAdminPage.tsx` — route `/admin/knowledge`

Admin article list and management dashboard. Gated: if `role` is not `admin` or `root`, renders `<Navigate to="/knowledge" replace />`.

Layout follows `TicketsPage.tsx` master–detail split pattern (`frontend/src/pages/tickets/TicketsPage.tsx:40`): left panel is a sortable, filterable table of all articles (draft, published, expired); right panel shows the selected article's metadata with action buttons.

Table columns: Title (link to editor), Status badge (Draft=secondary, Published=default/green, Expired=destructive), Category, Published At (formatted), View Count, Helpful/Not Helpful counts.

Toolbar: "New Article" button → navigates to `/admin/knowledge/articles/new`. Status filter dropdown (All, Draft, Published, Expired). Full-text search box triggers `listArticles({ q, status })`.

Per-row actions (kebab menu):
- **Edit** → `/admin/knowledge/articles/{id}/edit`
- **Publish** → calls `publishArticle(id)` via `useMutation`; disabled if already published.
- **Expire** → opens `KbExpireDialog` (inline Dialog component with a reason `<Textarea>`); calls `expireArticle(id, reason)`.
- **Unpublish** → calls `unpublishArticle(id)`; only visible on published articles.
- **Delete** → confirmation dialog; calls `deleteArticle(id)`. Returns 400 if article has published dependents (backend validates); show `toast.error` from the error message.

All mutations call `queryClient.invalidateQueries(["kb", "articles"])` on success.

#### `KbArticleEditorPage.tsx` — routes `/admin/knowledge/articles/new` and `/admin/knowledge/articles/:articleId/edit`

Form for creating and editing articles. Uses `useParams` to detect create vs. edit mode. On edit, `useQuery(["kb", "article", articleId])` pre-populates the form.

Fields:
- **Title** — `<Input>` — required, max 300 chars.
- **Category** — `<Select>` populated from `listCategories()`. Options rendered with indentation proportional to `path` depth (count of `>` separators). Inline "Create new category" link opens `KbInlineCategoryForm` (see below).
- **Tags** — comma-separated `<Input>`. On blur, normalize each entry client-side (lowercase, strip `#`, filter non-`[a-z0-9_-]`), display as tag chips with `×` remove button.
- **Expires at** — `<Input type="date">` optional. Converted to Unix timestamp before submission.
- **Body** — `<Textarea>` with minimum height 400px for MVP. A "Preview" toggle tab renders the body as HTML in a `prose` div. The backend stores the body as `body_html`; the frontend sends whatever the admin types directly as `body_html`. A future ticket may upgrade this to a rich-text editor (noted in Open Questions).
- **Edit note** (edit mode only) — short `<Input>` describing the change; passed as `edit_note` to `updateArticle`.

Buttons:
- **Save as Draft** — `POST /kb/articles` (create) or `PUT /kb/articles/{id}` (update). Always saves with current `status` unchanged (or `draft` on create).
- **Publish** — save then `POST .../publish`. Disabled if form is dirty (must save first) or if already published.
- **Attachments panel** — collapsible `<Accordion>` item. Lists `listAttachments(articleId)` results. Upload button → `<input type="file" multiple>` hidden input triggered on click. Each selected file is uploaded via `uploadAttachment(articleId, file)` serially. File size validated client-side against a 20 MB cap before upload attempt.
- **Related articles panel** — collapsible `<Accordion>` item. Shows `listRelated(articleId)` results with unlink buttons. "Add related article" input with autocomplete from `listArticles({ q })`.
- **View revision history** — button that opens `KbRevisionDrawer`.

On create success, navigate to `/admin/knowledge/articles/{newId}/edit` (so the URL updates and subsequent saves use PUT).

#### `KbCategoryAdminPage.tsx` — route `/admin/knowledge/categories`

Category tree management. Fetches `listCategories()` and builds a tree by nesting on `parent_id`. Renders as a `<ul>` tree with drag-handle icons for reorder (MVP: up/down arrow buttons only; drag-and-drop is a future enhancement).

Per-node actions: Rename (inline `<Input>`), Add child (opens inline create form below the node), Delete (disabled if node has child categories or articles assigned — backend returns 409; surface as `toast.error`).

"Add root category" button at top appends a new top-level node.

Create/rename calls `createCategory` / `updateCategory` via `useMutation`. Delete calls `deleteCategory`. All invalidate `["kb", "categories"]`.

#### `KbRevisionDrawer.tsx` — used by `KbArticleEditorPage`

`<Sheet>` component (from `components/ui/sheet`) opens from the right. Triggered by the "View revision history" button in the editor.

Header: "Revision history for {article.title}".

Body: chronological list of `KbRevision` items from `listRevisions(articleId)`, newest first. Each row shows `rev_number`, formatted `created_at`, `edited_by`, `edit_note` (truncated). Clicking a row expands a diff-style preview: two `<pre>` blocks side-by-side showing `title_snapshot` and `body_html_snapshot` vs. current article values (simple text diff — highlight lines added/removed using background color).

"Restore this revision" button opens a confirmation dialog with an edit note input, then calls `restoreRevision(articleId, revisionId, editNote)`. On success closes the drawer and invalidates `["kb", "article", articleId]`.

### 5.4 Edge cases

**Concurrent edit:** If two admins edit the same article simultaneously, the second `PUT /kb/articles/{id}` overwrites the first silently (backend has no optimistic locking on the content fields). This is acceptable for MVP; revision history preserves all snapshots. A future ticket can add `version` CAS.

**Flag toggled at runtime:** If `KNOWLEDGE_BASE_ENABLED` is flipped on the backend while the frontend is loaded, API calls return 404 until the user reloads. The `ApiError` handler in `client.ts:269` surfaces these as toast errors. Navigating to `/knowledge` shows "Feature not available."

**Empty category tree:** `publicListArticles` with `category_id` of a deleted category returns an empty list (not 404). The frontend shows "No articles found in this category."

**Article body rendering:** `dangerouslySetInnerHTML` is safe here because the backend stores only sanitized HTML (via `render_markdown_sanitized_html` at `app/routers/newsfeed.py:1186`). Attachment URLs rendered inside body HTML are already `/mock/s3/...` in dev and presigned URLs in prod (KB-003).

**Large article list:** The admin `listArticles` endpoint returns cursor-paginated results. `KbAdminPage` uses `useInfiniteQuery` with a "Load more" button (not auto-scroll) to avoid accidentally loading thousands of articles.

**Attachment upload progress:** For MVP, show a spinner while `uploadAttachment` is pending. The `api.upload` call is a single `fetch` with no `XMLHttpRequest` progress events; a true progress bar requires switching to `XMLHttpRequest` or the Fetch API stream, which is a future enhancement.

**Rate limiting:** The backend imposes per-user rate limits on AI-backed operations but not on ratings or views. If the backend ever returns 429, the `ApiError` handler in `client.ts:269` shows a toast with the error detail (which for KB includes `Retry-After` in the response body).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

KB-012 is a pure React frontend. It makes no direct DynamoDB, S3, or KMS calls. All backend operations run through the existing KB-001–KB-011 service layer, which already achieves SECOPS-007 parity (same DynamoDB code path in dev with moto and prod with real DynamoDB). The frontend adds no new `dev_mode` branches.

### 7.2 Idempotency of mutations

- `publishArticle`, `expireArticle`, `unpublishArticle`: idempotent per KB-002 (backend validates current status before transition and returns 400 on invalid transition; frontend disables the button for the current state so double-clicks produce no second API call after the mutation resolves).
- `uploadAttachment`: NOT idempotent by nature (creates a new S3 object each call). The upload button is disabled while the mutation is pending to prevent duplicate uploads.
- `addRelated`: idempotent on the backend (KB-008 uses `attribute_not_exists(pk)` conditional put). Frontend allows re-linking gracefully.
- `rateArticle`: idempotent per KB-005 (`already_rated=true` response). Frontend shows "already rated" state after first submission.

### 7.3 Security

**XSS:** `dangerouslySetInnerHTML` in `KbArticlePage` renders `body_html` from the backend. The backend stores only sanitized HTML (via `render_markdown_sanitized_html` at `app/routers/newsfeed.py:1186`), so no raw user-supplied HTML reaches this path. The admin editor sends whatever the admin types as `body_html`; admins are already trusted operators (role >= admin as verified server-side by `require_admin_or_root` at `app/auth/policy.py:67` — note there is NO `require_admin_session` function in the codebase; KB admin endpoints use `require_admin_or_root`, and the tickets domain uses `require_ui_session` + inline `_is_admin`).

**CSRF:** All non-GET mutations send the CSRF header automatically via `api/client.ts:179`. The backend's `require_ui_session` enforces CSRF on all non-GET cookie-auth requests (CLAUDE.md, auth dependency section). Public endpoints (`/public/kb/*`) require no auth and no CSRF.

**Role gate enforcement:** Role gating in the frontend is advisory (UX convenience). The authoritative gate is `Depends(require_admin_or_root)` (`app/auth/policy.py:67`) on every admin-only KB backend endpoint (KB-002–KB-010). An attacker cannot bypass the frontend gate to perform admin actions.

**Attachment downloads:** The `GET /kb/articles/{id}/attachments/{att_id}` endpoint returns a presigned URL in prod (300-second TTL) or a `/mock/s3/...` redirect in dev. The URL expires before it can be meaningfully shared.

KB-012 is purely additive. No existing page, route, component, endpoint file, or nav group entry is modified. Specifically:

No DynamoDB migration is needed. No existing API endpoint is changed. Existing E2E specs are unaffected.

## 10. Open Questions / Assumptions

1. **Rich text editor:** The ticket spec says `<textarea>` for MVP body editing with a preview pane. A future ticket should evaluate `@tiptap/react` or `@uiw/react-md-editor` as a drop-in rich-text upgrade. For now, the body is raw HTML input by the admin.

2. **Markdown vs. HTML input format:** The backend stores `body_html`. Should admins write Markdown (converted client-side before saving) or raw HTML? Assumed HTML for MVP to match the CAS-015 backend contract; a Markdown-to-HTML conversion step could be added to the editor's `onSubmit` without changing the API.

3. **Attachment upload progress:** `api.upload` uses a single `fetch` call with no progress events. A proper progress bar requires `XMLHttpRequest` or `fetch` with a `ReadableStream` body. Deferred to a follow-up.

4. **Drag-and-drop category reorder:** `KbCategoryAdminPage` uses up/down arrow buttons for MVP sort order. A full drag-and-drop tree requires a library such as `@dnd-kit/sortable`. Deferred.

5. **Category creation from article editor:** The inline "Create new category" link in `KbArticleEditorPage` opens a lightweight modal form. Assumed it uses a `<Dialog>` containing a minimal `name` + `parent_id` form that calls `createCategory` and then re-fetches the category list to update the `<Select>`.

6. **`isKnowledgeBaseEnabled` client-side resolution:** The flag is evaluated at Vite build time from `VITE_KNOWLEDGE_BASE_ENABLED`. If the flag needs to be toggled without a frontend rebuild (e.g., via a server-side feature flag API), a `GET /ui/feature-flags` endpoint would be needed. This is out of scope for KB-012.

7. **Pagination in KbAdminPage:** It is assumed the admin article list uses cursor-based infinite scroll via `useInfiniteQuery` with a "Load more" button, consistent with how `TicketsPage` handles pagination (`TicketsPage.tsx:60`).
