# KB-006 — Article view counter (atomic increment on GET)

**Type:** Feature  **Priority:** P2  **Estimate:** 0.5 day  
**Ticket source:** `docs/suitecrm/CRM_KNOWLEDGE_BASE_TICKETS.md`, section "KB-006"

---

## 1. Summary & Goal

KB-006 wires the view counter that CAS-015 stubbed but left disconnected from the router.
Specifically it:

1. Completes `KbArticleService.increment_view_count` so it performs a real atomic DDB `ADD`
   on `view_count` — the same `UpdateExpression="ADD view_count :one"` idiom already in
   production at `app/services/stories.py:160`.
2. Adds `KbArticleService.record_view(article_id, viewer_id)` which deduplicates increments
   within a 24-hour window using a `VIEW#{viewer_id}` sub-item with a DDB TTL, and calls
   `increment_view_count` only when no existing dedup row exists (conditional `put_item` +
   `ConditionalCheckFailedException` guard).
3. Wires `record_view` as a fire-and-forget `BackgroundTasks` call inside the two public GET
   endpoints already declared by CAS-015: the unauthenticated `GET /public/kb/articles/{id}`
   (uses client IP as `viewer_id`) and the authenticated `GET /kb/articles/{id}` (uses
   `user_sub`).

After this ticket, repeated visits from the same IP or authenticated user within 24 hours
register exactly one increment; view-count failures never block article delivery; and
`view_count` is exposed in every `KbArticleSummaryOut` / `KbArticleOut` response that
CAS-015 already defines.

All behavior is additive and gated on `S.knowledge_base_enabled` (KB-001). With the flag
off the platform is byte-for-byte identical to its pre-KB-006 state.

## 2. Context & Current State

### 2.1 Stub already defined by CAS-015

`CAS-015` (`docs/suitecrm/CRM_CASES_PORTAL_TICKETS.md:492`) specifies:

```
KbArticleService: … increment_view_count, …
```

The spec at `docs/suitecrm/specs/CAS-015.md:230–233` shows the stub signature:

```python
def increment_view_count(self, article_id: str) -> None:
    # DDB ADD view_count :one — fire-and-forget, no version check.
    ...
```

That method is defined but intentionally left as a pass-through (no DDB write) in CAS-015's
scope. CAS-015 also does NOT call it from either GET endpoint (`docs/suitecrm/specs/
CAS-015.md:274`: "Get one article; increments `view_count` atomically" is listed as
intended behavior but the wiring is deferred to KB-006). This ticket closes that gap.

### 2.2 `view_count` field on the article META row

`docs/suitecrm/specs/CAS-015.md:101` defines `view_count` as a DDB Number attribute on
every `ARTICLE#{id}/META` item, initialized to `0` at `create_article` time. The field is
already included in `KbArticleSummaryOut.view_count` and `KbArticleOut.view_count`
(`docs/suitecrm/specs/CAS-015.md:298+`). No schema change is required.

### 2.3 Atomic ADD pattern — `app/services/stories.py:156–164`

The canonical atomic increment is in `app/services/stories.py:156–164`:

```python
try:
    tbl.update_item(
        Key={"pk": f"STORY#{story_id}", "sk": "META"},
        UpdateExpression="ADD view_count :one",
        ExpressionAttributeValues={":one": 1},
    )
except ClientError:
    logger.exception("Failed to increment view count for story %s", story_id)
```

The `ADD` operator is idempotent with respect to concurrent writers — DDB serializes it
server-side — and is safe even if the item's `view_count` attribute does not yet exist (DDB
treats a missing numeric attribute as 0 before adding). The `try/except ClientError` ensures
the calling request is never blocked by a transient DDB error. KB-006 replicates this
pattern exactly, substituting `ARTICLE#` for `STORY#`.

### 2.4 Deduplication pattern — `app/services/stories.py:143–154`

`stories.record_view` (line 137–166) checks for an existing `STORYVIEW#{story_id}/
VIEWER#{viewer_id}` item with a `get_item` call before writing a new view row and
incrementing the counter. That pattern works but requires two round-trips (get, then
put + update). KB-006 uses a more efficient one-round-trip variant: a `put_item` with
`ConditionExpression=Attr("pk").not_exists()` catches the duplicate on the first write
attempt and avoids the preliminary read, consistent with the conditional-put guard used
throughout the codebase (e.g. `app/services/newsfeed_fanout.py:138`). The stories pattern
uses `ttl_epoch` for TTL; KB-006 uses `ttl` (the field name used by the `message_ai_cache`
table at `scripts/local-ddb-init.py:1708`). Both field names are recognized by DDB TTL;
the choice is table-local and must match what `_enable_ttl_if_needed` is called with for
`crm_kb_articles`.

### 2.5 Client IP extraction — `app/routers/signature_public.py:47–51`

For unauthenticated callers the `viewer_id` is the client IP. The canonical helper in the
codebase respects `X-Forwarded-For` so load-balancer deployments get the real IP:

```python
def _client_ip(request: Request) -> str:
    fwd = request.headers.get("x-forwarded-for") or ""
    if fwd:
        return fwd.split(",")[0].strip()
    return request.client.host if request.client else ""
```

The X-Forwarded-For-aware form of this helper exists at `app/routers/signature_public.py:47–51`.
(`app/routers/delegation_api.py:32–35` also defines a private `_client_ip`, but its simpler
variant — `return req.client.host if req.client else ""` — does NOT consult `X-Forwarded-For`;
KB-006 follows the `signature_public.py` XFF-aware version.) KB-006 replicates the XFF helper
as a private `_client_ip` at the top of `app/routers/kb_articles.py` (not imported from another
module, to avoid coupling, consistent with how both existing files define their own copy).

### 2.6 Fire-and-forget via `BackgroundTasks`

`app/routers/privacy.py:55–80` demonstrates the approved FastAPI pattern for running a
task after the response is sent without blocking:

```python
async def request_data_export(
    background_tasks: BackgroundTasks,
    …
) -> DataRequestOut:
    …
    background_tasks.add_task(_run_export_safe, user_sub, item["request_id"], categories)
    return DataRequestOut(…)
```

KB-006 follows this exact pattern. `record_view` is wrapped in a `_record_view_safe`
function that swallows all exceptions (so a DDB hiccup during view recording never surfaces
as a 500 to the caller). `background_tasks.add_task(_record_view_safe, article_id,
viewer_id)` is appended to both GET endpoints before `return article`.

### 2.7 TTL on `crm_kb_articles`

`scripts/local-ddb-init.py:2639–2661` shows `_enable_ttl_if_needed` applies TTL to a
named attribute on a named table. The `crm_kb_articles` table (CAS-001) does not currently
enable TTL. KB-006 adds a call `_enable_ttl_if_needed(ddb, S.kb_articles_table)` to the
`main()` function in `scripts/local-ddb-init.py` (after the table is created), using the
default TTL attribute name `"ttl"` rather than `"ttl_epoch"` (consistent with the
`message_ai_cache` pattern at line 1708 where `attr_types={"ttl": "N"}` is declared).
The TTL name must be declared in `attr_types` on the `TableDef`.

### 2.8 Existing `T.kb_articles` handle (KB-001)

KB-001 (`docs/suitecrm/specs/KB-001.md`) wires `T.kb_articles` in `app/core/tables.py`
alongside `T.tickets` (line 392). All service-layer DDB calls in KB-006 go through
`self._table` (set to `T.kb_articles` by default), allowing tests to inject a moto-backed
table via `KbArticleService(table=moto_table)` or via `object.__setattr__(T, "kb_articles",
moto_table)`.

### 2.9 `now_ts()` — `app/core/time.py`

`now_ts()` returns `int(time.time())`. All Unix integer timestamps in KB-006 use this
helper. The dedup TTL expiry is `now_ts() + 86400` (24 hours, same window as the stories
viewer TTL at `app/services/stories.py:152`).

## 3. Data Model

### 3.1 No new tables

KB-006 adds one new sub-item kind to `crm_kb_articles`. No new DynamoDB table is required.

### 3.2 View deduplication row

Written to the existing `crm_kb_articles` table (CAS-001):

```
PK = ARTICLE#{article_id}
SK = VIEW#{viewer_id}
```

| Field | DDB Type | Notes |
|-------|----------|-------|
| `pk` | S | `ARTICLE#{article_id}` |
| `sk` | S | `VIEW#{viewer_id}` |
| `viewer_id` | S | IP string for anonymous callers; `user_sub` for authenticated callers |
| `viewed_at` | N | Unix int (`now_ts()`) |
| `ttl` | N | `now_ts() + 86400`; DDB TTL deletes this row after 24 h |

The `viewer_id` for anonymous callers is the client IP from `_client_ip(request)`. For
IPv4 callers behind a load balancer this is the real IP from `X-Forwarded-For`. The value
is used only as a deduplication key; it is never returned in any API response.

**No GSI is needed** — rows are always accessed as a conditional write keyed by
`(ARTICLE#{id}, VIEW#{viewer_id})`. There is no query that needs to enumerate all views
for an article; the aggregate is already maintained as `view_count` on the META row.

### 3.3 `crm_kb_articles` TableDef change (scripts/local-ddb-init.py)

The existing CAS-001 `TableDef` for `crm_kb_articles` must be extended to declare `"ttl":
"N"` in `attr_types` so `_enable_ttl_if_needed` can configure DDB TTL against a numeric
attribute:

```python
TableDef(
    _resolve_table_name(S.kb_articles_table, "crm_kb_articles"),
    "pk",
    "sk",
    gsi=[
        {"index_name": "ByCategory",   "partition_key": "category",   "sort_key": "published_at"},
        {"index_name": "ByStatus",     "partition_key": "status",     "sort_key": "published_at"},
        # KB-001 additions:
        {"index_name": "ByAuthor",     "partition_key": "author_sub", "sort_key": "created_at"},
        {"index_name": "ByTag",        "partition_key": "tag",        "sort_key": "created_at"},
    ],
    attr_types={"published_at": "N", "created_at": "N", "ttl": "N"},
)
```

Note: `"ttl": "N"` is the only change relative to what KB-001 already specifies. The
`ttl` attribute on `VIEW#` rows is a numeric Unix timestamp. DDB Local (port 8001) does not
actively expire rows based on TTL, but the attribute is present so the real DynamoDB table
will expire them automatically; tests assert the attribute value rather than actual deletion.

Additionally, `_enable_ttl_if_needed(ddb, _resolve_table_name(S.kb_articles_table,
"crm_kb_articles"))` must be called in `main()` after the table is created/confirmed,
using the default TTL attribute `"ttl"`:

```python
_enable_ttl_if_needed(ddb, _resolve_table_name(S.kb_articles_table, "crm_kb_articles"))
```

The `_enable_ttl_if_needed` helper at line 2639 reads `getattr(S, "ddb_ttl_attr",
"ttl_epoch") or "ttl_epoch"`. Because KB-006 uses the attribute name `"ttl"` (not
`"ttl_epoch"`), the `update_time_to_live` call must pass `AttributeName="ttl"` explicitly
rather than delegating to `_enable_ttl_if_needed`. A thin wrapper suffices:

```python
def _enable_kb_ttl(ddb, table_name: str) -> None:
    """Enable TTL on the crm_kb_articles view dedup rows (attribute name: "ttl")."""
    if not table_name:
        return
    client = ddb.meta.client
    try:
        client.update_time_to_live(
            TableName=table_name,
            TimeToLiveSpecification={"Enabled": True, "AttributeName": "ttl"},
        )
    except Exception:
        pass  # DynamoDB Local may not support this; safe to ignore
```

Called as `_enable_kb_ttl(ddb, _resolve_table_name(S.kb_articles_table, "crm_kb_articles"))`
in `main()`.

## 4. API / Service Design

### 4.1 Service additions to `app/services/kb_articles.py`

#### 4.1.1 `increment_view_count`

CAS-015 defined this as a stub. KB-006 fills it in:

```python
def increment_view_count(self, article_id: str) -> None:
    """Atomically increment view_count on the article META row.

    Pattern: app/services/stories.py:156–164.
    Wrapped in try/except — a DDB failure must never block article delivery.
    """
    try:
        self._table.update_item(
            Key={"pk": f"ARTICLE#{article_id}", "sk": "META"},
            UpdateExpression="ADD view_count :one",
            ExpressionAttributeValues={":one": 1},
        )
    except ClientError:
        logger.exception(
            "kb.view_count: failed to increment for article %s", article_id
        )
```

`ClientError` is imported from `botocore.exceptions` (already imported in
`app/services/stories.py:15`).

#### 4.1.2 `record_view`

```python
def record_view(self, article_id: str, viewer_id: str) -> None:
    """Write a VIEW# dedup row and increment view_count if the viewer is new
    within the 24-hour TTL window.

    Uses a conditional put_item (attribute_not_exists(pk)) so a single
    round-trip handles the check-and-insert atomically. On
    ConditionalCheckFailedException the row already exists; skip increment.

    Pattern: app/services/newsfeed_fanout.py:138 (conditional put idempotency).
    TTL pattern: app/services/stories.py:152 (now_ts() + 86400).
    """
    if not viewer_id:
        return
    view_item = {
        "pk": f"ARTICLE#{article_id}",
        "sk": f"VIEW#{viewer_id}",
        "viewer_id": viewer_id,
        "viewed_at": now_ts(),
        "ttl": now_ts() + 86400,
    }
    try:
        self._table.put_item(
            Item=view_item,
            ConditionExpression="attribute_not_exists(pk)",
        )
    except ClientError as exc:
        code = exc.response.get("Error", {}).get("Code", "")
        if code == "ConditionalCheckFailedException":
            # Viewer already registered within the 24 h window — skip increment.
            return
        # Unexpected error — log but do not raise; view counting is best-effort.
        logger.exception(
            "kb.record_view: unexpected error for article %s viewer %s",
            article_id, viewer_id,
        )
        return
    # Row inserted successfully — this is a new view.
    self.increment_view_count(article_id)
```

The `ConditionExpression="attribute_not_exists(pk)"` fires when the `VIEW#` row does not
yet exist. Because `pk` is the DDB partition key it is always present on stored items, so
the condition is equivalent to "this item has never been written." This is the same guard
used at `app/services/newsfeed_fanout.py:138`.

#### 4.1.3 `_record_view_safe` wrapper (used by router)

```python
def _record_view_safe(svc: "KbArticleService", article_id: str, viewer_id: str) -> None:
    """Top-level fire-and-forget wrapper; swallows all exceptions."""
    try:
        svc.record_view(article_id, viewer_id)
    except Exception:
        logger.exception(
            "kb.record_view_safe: unhandled error article=%s viewer=%s",
            article_id, viewer_id,
        )
```

This is a module-level function (not a method) so `BackgroundTasks.add_task` can reference
it by name without capturing `self`. It receives the `KbArticleService` instance as its
first argument.

async def get_public_article(

## 5. Detailed Behavior & Edge Cases

### 5.1 Normal flow — first view

1. Client sends `GET /public/kb/articles/kb_abc123`.
2. Router calls `svc.get_article("kb_abc123")` — synchronous; article returned.
3. `_client_ip(request)` extracts IP (e.g. `"203.0.113.42"`).
4. `background_tasks.add_task(_record_view_safe, svc, "kb_abc123", "203.0.113.42")` is
   registered.
5. `KbArticleOut` response is returned to the client immediately.
6. FastAPI runs the background task after the response is sent:
   - `record_view` calls `put_item(Item={pk="ARTICLE#kb_abc123", sk="VIEW#203.0.113.42",
     ttl=now+86400, …}, ConditionExpression="attribute_not_exists(pk)")`.
   - Condition passes (first visit) — item is written.
   - `increment_view_count` runs `update_item(ADD view_count :one)`.
   - `view_count` on the META row goes from 0 to 1.

### 5.2 Repeated view within 24 hours (deduplication)

On the second visit from the same IP within 24 hours:
- `put_item` raises `ConditionalCheckFailedException` (the `VIEW#` row already exists with
  `ttl` still in the future).
- `record_view` catches the exception, logs nothing (this is the expected path), and
  returns without calling `increment_view_count`.
- `view_count` remains at 1.

### 5.3 View after 24 hours (TTL expiry)

DDB TTL deletes the `VIEW#{viewer_id}` row after the `ttl` timestamp passes (eventually
consistent, may take up to 48 h in production DynamoDB SLA). Once the row is gone the next
visit from the same IP will succeed the conditional put and increment the counter again.
In dev (DDB Local) TTL is not enforced at the data layer; tests simulate this by deleting
the row manually before re-running the view scenario.

### 5.4 DDB increment failure (transient error)

If `increment_view_count` throws `ClientError` (network blip, throttling, DDB Local
restart):
- The `VIEW#` row was already written successfully (it preceded the update).
- `view_count` is not incremented for this request.
- The `ClientError` is caught and logged via `logger.exception`.
- The response has already been sent to the client — no 500 is raised.
- The `VIEW#` row remains and blocks future increments for 24 h (conservative: one lost
  increment is better than unbounded double-counting).

### 5.5 `record_view` called for non-existent article

`record_view` does not check whether the article META row exists. If called with a
fabricated `article_id` (e.g., via a stale cache), the `put_item` writes a `VIEW#` orphan
row and `increment_view_count` runs `ADD view_count :one` on a non-existent META row.
DDB's `ADD` against a missing item does nothing (the item must already exist for the key;
the attribute is added to it only if the item exists). Since the GET handler verifies
article existence and status before registering the background task, this scenario cannot
occur from normal traffic. No defensive guard is needed in `record_view` itself — the
existing GET-level 404 is the single authority.

### 5.6 Empty `viewer_id` (no client IP)

`_client_ip` returns `""` when `request.client is None` and no `X-Forwarded-For` header
is present. `record_view` short-circuits with an early `return` when `viewer_id` is falsy
(line shown in §4.1.2 signature). This means the view is not counted for callers with no
detectable IP (e.g., unit tests with a mocked request that provides no client). This is
acceptable — an unidentifiable caller cannot be deduplicated anyway.

### 5.7 Anonymous vs. authenticated views of the same article

An unauthenticated view from IP `203.0.113.42` writes `VIEW#203.0.113.42`. The same
user, now logged in, hits `GET /kb/articles/{id}` and is identified as `user_sub=alice123`,
writing `VIEW#alice123`. These are distinct dedup keys, so both increment `view_count`.
This is the expected behavior — a user browsing the portal anonymously then logging in to
rate an article legitimately counts as two views.

### 5.8 Concurrent requests (race condition safety)

Two concurrent first-time requests from the same IP race to `put_item` with
`attribute_not_exists(pk)`. DDB guarantees that exactly one will succeed; the other will
receive `ConditionalCheckFailedException`. The `increment_view_count` is only called by
the winner. `view_count` is atomically incremented by 1, not 2. No distributed lock is
needed.

### 5.9 `knowledge_base_enabled` flag-off behavior

When `S.knowledge_base_enabled is False`, both GET endpoints return HTTP 404 before any
article fetch or background task registration. `record_view` is never called. The DDB
table may not even exist in that environment. No error is raised because the 404 guard
runs first.

### 5.10 Admin-only article preview (authenticated GET)

`GET /kb/articles/{article_id}` does not enforce `status="published"` — it returns the
article regardless of status so an admin can preview a draft. View counting still fires
for admins, so internal previews inflate `view_count` slightly. This is acceptable for an
MVP; a future ticket could add `?preview=1` to suppress counting for admin callers.

### 6.1 Master flag

knowledge_base_enabled: bool = os.environ.get("KNOWLEDGE_BASE_ENABLED", "0") not in ("0", "false", "False")

KB-006 introduces no additional flags beyond `S.knowledge_base_enabled`. View counting is

disable view counting while keeping article reads active.

The 24-hour dedup window is hard-coded as `86400` seconds. A future ticket could expose
`KB_VIEW_DEDUP_WINDOW_SECONDS: int = int(os.environ.get("KB_VIEW_DEDUP_WINDOW_SECONDS",
"86400"))` in settings if operators need a different window. KB-006 does not introduce this
setting.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 — single code path dev and prod

`increment_view_count` and `record_view` use `self._table` which resolves to
`T.kb_articles` — the same boto3 `Table` proxy in both dev (pointing at DDB Local on port
8001) and prod (pointing at real DynamoDB). There is no `if S.dev_mode` branch anywhere
in the view-count path. In dev, DDB Local does not enforce TTL expiry but the rows are
written with the correct `ttl` value; prod DynamoDB will expire them. The `try/except
ClientError` guard and the `ConditionalCheckFailedException` catch are identical in both
environments.

### 7.2 Idempotency

`record_view` is idempotent at the "per-viewer per-24h" granularity: calling it N times
with the same `(article_id, viewer_id)` within the TTL window produces exactly one
`VIEW#` row and one increment. After TTL expiry the cycle resets. This is the correct
business semantic for "unique daily views."

`increment_view_count` on its own is NOT idempotent — each call unconditionally adds 1.
It should only ever be called from within `record_view`, guarded by the conditional put.
No other code path calls `increment_view_count` directly; see §8.2 for the CAS-015 stub
contract.

### 7.3 Security

- **No new authentication surface**: Both endpoints already existed (CAS-015); KB-006
  adds no new routes or auth dependencies.
- **IP-based dedup is a weak proxy**: IPv4 shared NAT or IPv6 prefix rotation means
  multiple users may share a `viewer_id`, leading to under-counting. This is acceptable
  for an analytics counter; KB is not a billing or access-control mechanism.
- **viewer_id never appears in responses**: The `VIEW#` sub-item is a pure internal
  dedup token. `KbArticleOut` and `KbArticleSummaryOut` expose `view_count` (the
  aggregate integer) but not any per-viewer data. No PII is leaked.
- **No rate-limiting needed on the view path**: `record_view` is fire-and-forget and DDB
  conditional puts are cheap. The article GET itself may be rate-limited at the API
  gateway layer (outside the scope of this ticket); that is sufficient.
- **DDB TTL data**: The `VIEW#` rows contain `viewer_id` (an IP or `user_sub`). DDB
  encrypts at rest (real DynamoDB) and DDB Local is not accessible outside the dev host.
  No additional encryption is required for this low-sensitivity dedup token.

## 8. Backward Compatibility & Migration

### 8.1 Zero changes to existing articles

The `VIEW#` sub-item lives under `PK=ARTICLE#{id}` in the same table. Existing article
META rows (`SK=META`), rating rows (`SK=RATING#{user_sub}`, KB-005), and attachment rows
(`SK=ATTACHMENT#{id}`, KB-003) are unaffected. A `query(PK="ARTICLE#{id}")` that does not
filter by SK will now return `VIEW#` rows alongside other sub-items; callers that do a
`get_item(PK, SK=META)` are entirely unaffected. Service methods that process sub-items
(e.g., `list_attachments`) filter by `SK begins_with "ATTACHMENT#"` and will silently
skip `VIEW#` rows.

### 8.2 CAS-015 stub replacement

CAS-015 defines `increment_view_count` as a stub (body is `pass` or a comment). KB-006
fills in the body. No callers in CAS-015 call `increment_view_count` directly — CAS-015
describes the GET endpoint as "increments view_count atomically" but defers wiring to
KB-006. The only behavioral change to existing CAS-015 code is that `view_count` on the
META row now increases over time. This is the expected outcome and breaks no tests.

### 8.3 `attr_types` addition to `crm_kb_articles` TableDef

Adding `"ttl": "N"` to `attr_types` on an already-existing table definition in
`scripts/local-ddb-init.py` causes `just restart` to recreate the table in dev (the init
script drops-and-recreates tables when `TableDef` changes). In prod, the table already
exists; the `attr_types` change in the init script is dev-only scaffolding. The TTL
attribute change is handled separately via `_enable_kb_ttl(ddb, table_name)` which calls
`update_time_to_live` — that is an in-place update to an existing table and does not
require a migration or downtime.

### 8.4 `just restart` on a clean dev environment

After KB-006 merges, a developer running `just restart` will:
1. Recreate `crm_kb_articles` with `"ttl": "N"` in `attr_types`.
2. Call `_enable_kb_ttl` — DDB Local may silently ignore this; no error.
3. All new `VIEW#` rows written during the session will carry the `ttl` attribute even if
   DDB Local does not act on it.

No manual migration steps are needed for dev environments. Production TTL enablement is a
one-time `update_time_to_live` API call executed by running the updated
`scripts/local-ddb-init.py` against the production table (safe — `update_time_to_live`
is idempotent once TTL is already enabled).

## 10. Open Questions / Assumptions

**OQ-1: Should `view_count` include admin preview views?**
Currently yes — the authenticated `GET /kb/articles/{id}` endpoint fires `record_view`
regardless of the caller's role. If product wants admin previews excluded, a `?preview=1`
query param or a check on `ctx["role"] >= ADMIN` before registering the background task
would suffice. Deferred to a follow-up; the current behavior is simpler and consistent
with how story views work.

**OQ-2: What happens if a `VIEW#` row's `ttl` attribute overflows?**
`now_ts() + 86400` will overflow a 32-bit integer in 2038 if stored as a 32-bit type. DDB
stores Number as a variable-precision decimal; Python's `int` is arbitrary precision;
boto3 serializes it as a DDB `N` string. No overflow risk in practice.

**OQ-3: Should unauthenticated views be distinguished from authenticated views in the count?**
Not in this ticket. `view_count` is a single aggregate. If separate `anonymous_view_count`
/ `authenticated_view_count` metrics are needed, that is a KB-006 follow-up.

**OQ-4: Privacy — is storing client IPs in DDB a GDPR concern?**
Potentially yes in EU deployments. The `viewer_id` for anonymous callers is an IP address,
which may be personal data under GDPR. Mitigations: (a) hash the IP before storing
(`hashlib.sha256(ip.encode()).hexdigest()[:16]`), (b) use a shorter TTL, or (c) only count
authenticated views. The current spec stores the raw IP, which is consistent with how
`app/routers/billing.py:141` stores IPs for fraud detection. A future privacy ticket can
add IP hashing; KB-006 does not block on this.

**Assumption A**: CAS-015 has shipped with `increment_view_count` as a stub (body `pass`).
If CAS-015 shipped with the increment already wired but without deduplication, KB-006's
scope is reduced to adding the `record_view` dedup layer and changing the router to call
`record_view` instead of `increment_view_count` directly.

**Assumption B**: `T.kb_articles` is the DDB table object (i.e., `kb_articles_table` is
the correct settings key, introduced by KB-001). `app/core/tables.py` must expose
`T.kb_articles` (confirmed by KB-001 spec at `docs/suitecrm/specs/KB-001.md:14`).
