# RPT-002 — Custom report builder — definition CRUD

**Type:** Feature | **Priority:** P1 | **Estimate:** 3d
**Area:** CRM Reports & Dashboards
**Source:** `docs/suitecrm/CRM_REPORTS_TICKETS.md` (RPT-002 section, lines 77–158)

---

## 1. Summary & Goal

RPT-002 implements the metadata-driven custom report builder: users compose a report definition by selecting a target data module, choosing which fields to project, and specifying filter conditions. The report is persisted as a DynamoDB item; results are computed on demand against live data from the platform's existing service tables and cached in a companion RUN row. The ticket covers the complete backend service layer, router, and Pydantic models; the frontend UI shell is delivered by RPT-005.

The goal is parity with SuiteCRM's Advanced OpenReports (AOR) "basic tabular report" capability. After this ticket a user can `POST` a report definition, `GET` it back, list all their reports, `PATCH` or `DELETE` it, and trigger a `POST …/run` that evaluates the definition against live data and returns up to 2 000 rows. All behaviour is inert when `S.crm_reports_enabled` is `False` (the default).

## 3. Data Model

### 3.1 Table: `crm_reports` (created by RPT-001)

All RPT-002 data is single-table in `T.crm_reports`.

| Attribute | Type | Notes |
|---|---|---|
| `report_id` | S | Hash key; value `RPT#{12-hex-char uuid4 fragment}` |
| `sk` | S | Range key; see row types below |
| `GSI1PK` | S | `OWNER#{owner_sub}` — written on every META row |
| `GSI1SK` | N | `created_at` (Unix integer seconds) — written on every META row |

**META row** (`sk = "META"`): stores the full report definition. All fields except keys are plain string/number/list DynamoDB attributes; nested structures (`conditions`, `fields`) are stored as DynamoDB Lists / Maps.

```
report_id:    "RPT#a3f8c219b204"
sk:           "META"
GSI1PK:       "OWNER#alice@example.com"
GSI1SK:       1718000000          ← created_at (numeric — attr_types={"GSI1SK":"N"} in RPT-001)
name:         "Open Tickets This Week"
description:  "..."               ← optional, max 1 000 chars
module:       "tickets"
fields:       ["subject", "status", "created_at"]
conditions:   [{"field":"status","operator":"eq","value":"open"}]
owner_sub:    "alice@example.com"
created_at:   1718000000
updated_at:   1718000000
```

**RUN row** (`sk = "RUN#{run_ts:010d}#{run_id}"`): stores the most-recent cached execution result. The sort key encodes the run timestamp so that a `query(pk=report_id, begins_with(sk, "RUN#"), ScanIndexForward=False, Limit=1)` retrieves the latest run without a scan.

```
report_id:    "RPT#a3f8c219b204"
sk:           "RUN#1718001000#7f3a"
run_id:       "7f3a"
run_at:       1718001000
status:       "ok"                ← "ok" | "error"
row_count:    42
columns:      ["subject", "status", "created_at"]
rows:         [[...], [...]]      ← List of Lists; capped at 2 000
error_msg:    null                ← present only when status="error"
```

Old RUN rows are not proactively deleted. The router only reads the latest RUN row; old ones age naturally. Implementors may add a TTL attribute (`ttl_epoch`) of `run_at + 7*86400` to keep the table tidy, using the existing `with_ttl` helper from `app/services/ttl.py`.

### 3.2 GSI: `owner-reports-index`

Defined in RPT-001's `TableDef` with `attr_types={"GSI1SK": "N"}`.

- Partition key: `GSI1PK` (S) → value `OWNER#{owner_sub}`
- Sort key: `GSI1SK` (N) → value `created_at` (integer Unix seconds)
- Projection: `ALL`

`list_reports` queries this GSI with `GSI1PK = :pk`, `ScanIndexForward=False` (newest-first), `Limit` capped at 50 per page.

**Important**: only META rows carry `GSI1PK`/`GSI1SK`. RUN rows do **not** carry these attributes so they are invisible to the GSI query. This avoids mixing row types in the listing.

## 4. API / Service Design

### 4.1 Pydantic models (`app/models.py`)

```python
class ReportCondition(BaseModel):
    field: str = Field(..., min_length=1, max_length=100)
    operator: str = Field(
        ...,
        pattern=r"^(eq|neq|contains|gt|lt|gte|lte|is_empty|not_empty)$"
    )
    value: Optional[str] = Field(None, max_length=500)

class ReportCreateIn(BaseModel):
    name: str = Field(..., min_length=1, max_length=200)
    description: Optional[str] = Field(None, max_length=1000)
    module: str = Field(
        ...,
        pattern=r"^(tickets|contacts|billing_ledger|orders|subscriptions|questionnaire_responses)$"
    )
    fields: List[str] = Field(..., min_length=1, max_length=20)
    conditions: List[ReportCondition] = Field(default_factory=list)

class ReportUpdateIn(BaseModel):
    name: Optional[str] = Field(None, min_length=1, max_length=200)
    description: Optional[str] = Field(None, max_length=1000)
    fields: Optional[List[str]] = Field(None, min_length=1, max_length=20)
    conditions: Optional[List[ReportCondition]] = None

class ReportOut(BaseModel):
    report_id: str
    name: str
    description: Optional[str]
    module: str
    fields: List[str]
    conditions: List[ReportCondition]
    owner_sub: str
    created_at: int
    updated_at: int

class ReportRunOut(BaseModel):
    report_id: str
    run_id: str
    run_at: int
    status: str        # "ok" | "error"
    row_count: int
    columns: List[str]
    rows: List[List[Any]]   # capped at 2 000; each inner list matches `columns`
    error_msg: Optional[str] = None
```

`ReportOut` is both the create-response and the get/list-item shape. `ReportRunOut` is the run-response shape. Neither model needs `model_rebuild()` because neither contains forward references.

`_iter_tickets` is a new thin function in `crm_reports.py` that mirrors the `_iter_billing_entries` pattern: it queries `T.tickets` via the owner GSI and loops over `LastEvaluatedKey` pages, yielding each raw item dict. It does **not** import from `app/services/tickets.py` directly to avoid a circular dependency; it queries `T.tickets` and the GSI name directly.

**`_eval_condition` operator semantics**:

| Operator | Semantics |
|---|---|
| `eq` | `str(field_val) == value` (or exact typed match) |
| `neq` | `str(field_val) != value` |
| `contains` | `value.lower() in str(field_val).lower()` (substring, case-insensitive) |
| `gt` | `float(field_val) > float(value)` |
| `lt` | `float(field_val) < float(value)` |
| `gte` | `float(field_val) >= float(value)` |
| `lte` | `float(field_val) <= float(value)` |
| `is_empty` | `field_val is None or str(field_val).strip() == ""` |
| `not_empty` | inverse of `is_empty` |

For numeric operators, `Decimal` values from DynamoDB are first coerced to `float` (same pattern as `app/core/tables.py:11`). A `ValueError` or `TypeError` during coercion is treated as `False` (the item does not satisfy the condition) and logged at `DEBUG` level — it never raises to the caller.

## 5. Detailed Behavior & Edge Cases

### 5.1 `create_report`

1. Validate payload (Pydantic, field count 1–20, conditions list 0–20 items).
2. Generate `report_id = f"RPT#{uuid4().hex[:12]}"`.
3. Set `created_at = updated_at = now_ts()`.
4. Write META row to `T.crm_reports` with `put_item`. No conditional expression needed on create (IDs are UUIDs; collision probability is negligible).
5. Emit `audit_event("report.created", user_sub, request, report_id=report_id, module=payload.module)`.
6. Return `ReportOut`.

### 5.2 `get_report`

1. `T.crm_reports.get_item(Key={"report_id": report_id, "sk": "META"})`.
2. If `Item` absent → `HTTPException(404, "Report not found")`.
3. If `item["owner_sub"] != owner_sub` → `HTTPException(403, "Forbidden")`.
4. Return `ReportOut` built from item.

### 5.3 `list_reports`

1. Build `ExclusiveStartKey` from `decode_cursor(cursor)` (returns `None` for absent or invalid cursors — no error, just starts from the beginning).
2. Query `owner-reports-index` with `KeyConditionExpression="GSI1PK = :pk"`, `ExpressionAttributeValues={":pk": f"OWNER#{owner_sub}"}`, `ScanIndexForward=False`, `Limit=min(limit, 50)`.
3. Build `next_cursor = encode_cursor(resp.get("LastEvaluatedKey"))`.
4. Return `{"reports": [ReportOut(...) for item in items], "next_cursor": next_cursor}`.

### 5.4 `update_report`

1. Read META row (ownership check via `get_report`).
2. Build `UpdateExpression` / `ExpressionAttributeValues` from non-None patch fields.
3. Always update `updated_at = now_ts()`.
4. Call `T.crm_reports.update_item` with `ConditionExpression="owner_sub = :sub"` to enforce ownership at the DynamoDB layer (prevents TOCTOU between read and write).
5. Emit `audit_event("report.updated", user_sub, request, report_id=report_id)`.
6. Re-read and return updated `ReportOut`.

**Fields that cannot be updated via PATCH**: `module` and `report_id`. If `module` is present in `ReportUpdateIn` it is silently ignored (the field is not on the model).

### 5.5 `delete_report`

1. Read META row (ownership check).
2. Query all RUN rows: `T.crm_reports.query(KeyConditionExpression="report_id = :id AND begins_with(sk, :prefix)", ...)`.
3. Delete META + all RUN rows in a single `batch_writer` context. DynamoDB `batch_writer` handles batching into groups of 25 automatically.
4. Emit `audit_event("report.deleted", user_sub, request, report_id=report_id)`.
5. Return `204 No Content`.

**Concurrency**: If a concurrent `run_report` writes a new RUN row after step 2's query but before step 3's batch delete, that orphan RUN row is left behind. This is acceptable because orphan RUN rows don't appear in any listing and are cleaned up by TTL. A compensating full re-scan is not worth the added complexity.

### 5.6 `run_report` (the query engine)

1. `get_report(report_id, owner_sub)` — ensures ownership and existence.
2. Set `run_id = uuid4().hex[:4]`, `run_at = now_ts()`.
3. Call `_fetch_and_filter(module, owner_sub, fields, conditions)` inside `asyncio.to_thread`.
4. On success: write RUN row with `status="ok"`, `columns=columns`, `rows=rows`, `row_count=len(rows)`.
5. On exception: write RUN row with `status="error"`, `error_msg=str(exc)[:500]`, `row_count=0`, `columns=[]`, `rows=[]`. Re-raise as `HTTPException(500, "Report execution failed")`.
6. Emit `audit_event("report.run", user_sub, request, report_id=report_id, row_count=row_count, status=status)`.
7. Return `ReportRunOut`.

**`questionnaire_responses` module**: The `questionnaire_id` must be supplied as a condition with `field="questionnaire_id"` and `operator="eq"`. If absent, `_fetch_and_filter` raises `ValueError("questionnaire_id condition required for questionnaire_responses module")` which the router converts to `HTTPException(422, ...)`.

**Row cap**: `_fetch_and_filter` stops iterating and returns early once it has accumulated `MAX_REPORT_ROWS = 2000` rows after filtering. This mirrors the `MAX_EXPORT_ROWS = 50_000` guard in `app/services/csv_export.py:28` but at a much tighter cap because rows are held in memory and returned as JSON.

**Field projection**: The `fields` list in the report definition drives which columns are returned. If `fields = ["subject", "status"]` then `columns = ["subject", "status"]` and each row is `[item.get("subject"), item.get("status")]`. Unknown or missing fields return `None` in that column position.

**All-fields wildcard**: `fields = ["*"]` is explicitly disallowed by the Pydantic model — each element must match `^[a-zA-Z_][a-zA-Z0-9_.]{0,99}$` (to be validated). This forces callers to enumerate the fields they want, which keeps row payloads predictable.

### 5.7 Additional edge cases

- **Empty result set**: `run_report` with a filter that matches nothing returns `row_count=0`, `rows=[]`, `status="ok"`. Not an error.
- **`is_empty` / `not_empty` on absent fields**: `item.get(field)` returns `None`; `is_empty` evaluates `True`; `not_empty` evaluates `False`. Consistent and deterministic.
- **Concurrent `delete` + `run`**: If a report is deleted while a `run` is in flight, the `run` will still write a RUN row (the `report_id` PK is not removed atomically until the batch finishes). The orphan RUN row is harmless and ages out via TTL.
- **`PATCH` on a nonexistent report**: `update_report` calls `get_report` first, so it returns `404` before attempting the update.
- **User with many reports (> 50)**: The list endpoint is paginated; the frontend must follow `next_cursor` to retrieve subsequent pages.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

There are no `if S.dev_mode` branches in `app/services/crm_reports.py` or `app/routers/crm_reports.py`. All code paths — DynamoDB reads/writes, condition evaluation, row capping, audit emission — are identical in dev (DynamoDB Local at `http://localhost:8001`, moto-backed in tests) and prod (real DynamoDB). The `_bucket_limit` rate limiter uses `T.sessions` which is DynamoDB-backed in both environments.

### 7.2 Ownership enforcement

Ownership is enforced at two layers:

1. **Service layer** (`get_report`, `update_report`, `delete_report`, `run_report`): each reads the META row and compares `item["owner_sub"]` to the caller's `user_sub`. A mismatch raises `HTTPException(403)`.
2. **DynamoDB conditional expression** (update only): `ConditionExpression="owner_sub = :sub"` on `update_item` prevents a TOCTOU race between the read-check and the write.

There is no admin bypass at this stage (RPT-002 is user-scoped). Admin visibility across all users' reports is a post-RPT-002 follow-up if needed.

### 7.3 Input validation

- `module` is validated by Pydantic regex to the exact allowed set (`tickets|contacts|billing_ledger|orders|subscriptions|questionnaire_responses`). An unknown module never reaches the iterator dispatch.
- `operator` is validated by Pydantic regex to the exact allowed set. Unknown operators never reach `_eval_condition`.
- `fields` elements are validated to `^[a-zA-Z_][a-zA-Z0-9_.]{0,99}$` — no shell injection vector, no DynamoDB expression injection.
- All string fields have `max_length` limits to prevent oversized items.

### 7.4 CSV injection prevention

`_project_row` returns raw values from DynamoDB items. These values are returned as JSON in `ReportRunOut`; they are not passed through `_sanitize_csv_field` at this stage. The RPT-004 scheduler, when serialising rows to CSV for email delivery, must pass each cell through `app/services/csv_export._sanitize_csv_field` (or inline the same `_DANGEROUS_PREFIXES` check).

### 7.5 Idempotency

- `create_report` is not idempotent (each call generates a new UUID). The client must not retry on timeout without checking whether the first attempt succeeded.
- `run_report` is idempotent in effect: running the same report twice produces two RUN rows; only the latest is returned by subsequent queries. There is no `condition_not_exists` guard on RUN row creation.
- `delete_report` is idempotent: if called twice (e.g., network retry), the second call returns `404` at the `get_report` step.

## 10. Open Questions / Assumptions

1. **Admin cross-user report access**: RPT-002 is user-scoped only. If an admin needs to view or run another user's reports (e.g., for audit purposes), a separate admin endpoint is required. Assumption: deferred post-RPT-002; not in scope.

2. **`questionnaire_responses` ownership**: The `_iter_questionnaire_responses` iterator in `csv_export.py:113` takes a `questionnaire_id` and does not filter by `owner_sub`. For reports, the caller must supply a `field="questionnaire_id", operator="eq"` condition. The service validates that the caller's `owner_sub` matches the questionnaire's `owner_id` by calling `DynamoQuestionnaireRepository().get_questionnaire(qid)` before executing — matching the ownership check in `app/routers/csv_export.py:81-87`.

3. **`orders` and `subscriptions` access patterns** [RESOLVED during verification]: `subscriptions` uses `pk = _pk_subscriber(owner_sub)` + `begins_with(sk, "SUB#")` — VERIFIED at `app/services/subscription_access.py:58`. `orders` does NOT use an `ORDER#` SK prefix: the `orders` table key is PK `order_id` (no SK) with a `GSI_USER` GSI on `user_id`/`created_at` (`scripts/local-ddb-init.py:288`), so the orders iterator must query the `GSI_USER` index with `user_id = owner_sub`. The §4.2 dispatch table has been corrected accordingly.

4. **Row serialisation of nested DDB structures**: Some DDB items contain nested Maps or Sets (e.g., `answers` in questionnaire responses, `tags` in contacts). `_project_row` uses `item.get(field)` which returns the raw boto3-deserialised Python object (dict, set, Decimal). For JSON serialisation, `ReportRunOut.rows` is typed `List[List[Any]]`. The Pydantic `model_dump(mode="json")` call on the response will fail on `Decimal` and `set` objects. The router must pass `rows` through a `_json_safe(val)` helper that converts `Decimal → float/int`, `set → list`, recursively — identical to the pattern in `app/core/cursor.py:12`.

5. **RUN row size limit**: DynamoDB items are capped at 400 KB. With 2 000 rows and multiple string columns, this limit is reachable. If a run result exceeds ~300 KB, the `put_item` will raise a `ClientError(ValidationException)`. RPT-002 should catch this error and retry with a halved row cap, writing `status="ok"`, `row_count=N`, and a `truncated=True` flag. This retry path is listed as a post-implementation hardening task.
