# WFL-007 — Action executor — send-email action

**Type:** Feature | **Priority:** P1 | **Estimate:** 1d
**Depends on:** WFL-001, WFL-002, WFL-003, WFL-006
**Flag:** `CRM_WORKFLOW_ENABLED` (default `"0"`)

---

## 1. Summary & Goal

WFL-007 extends the action executor introduced in WFL-006 (`app/services/workflow_action_executor.py`) with a third action type: `send_email`. When a workflow rule fires and one of its ordered action steps carries `action_type: "send_email"`, the executor resolves the recipient email address from the triggering record, renders a stored notification template against a variable context built from that record, and dispatches the email through the existing `send_alert_email` infrastructure. An audit event is emitted on success.

The action is intentionally non-blocking: if the recipient address cannot be resolved, the template does not exist, or the template is inactive, the step is marked `skipped` in the run log and execution continues with the next action in the rule. This matches the fault-isolation contract established in WFL-006 for `modify_field` and `create_record`.

With `CRM_WORKFLOW_ENABLED=0` (the default) the flag guard at the top of `execute_crm_workflow_action` (WFL-006) short-circuits before any action step is evaluated, so this ticket adds zero net behaviour to the platform in the default-off state.

## 2. Context & Current State

### 2.1 Action executor skeleton (WFL-006)

WFL-006 introduces `app/services/workflow_action_executor.py` and registers `"crm_workflow": execute_crm_workflow_action` in `_EXECUTORS` at `app/services/unified_scheduler.py:28`. The top-level function iterates `rule["actions"]` and delegates each step to `_execute_action(action, module, record_id)`. WFL-006 implements the `modify_field` and `create_record` branches of that dispatch; WFL-007 adds the `send_email` branch to the same `_execute_action` function — no new files are created.

The run log is written by `_write_run` (WFL-006) to `T.crm_workflow_runs` at `PK=RULE#{rule_id}`, `SK=RUN#{started_at:010d}#{run_id}`. The `actions_fired` list within the run row accumulates per-step result dicts of the form `{"action_type": str, "result": str | dict}`.

### 2.2 Notification template service

`app/services/notification_templates.py` owns all CRUD and rendering for stored email/SMS templates.

- Templates live in `T.admin_messaging_templates` (`app/core/tables.py:460`) with `PK=TEMPLATE#{template_id}`, `SK=META` (`notification_templates.py:6`).
- `get_template(template_id) -> Optional[dict]` (`notification_templates.py:171`) performs a single `get_item` and returns a normalised dict with keys `template_id`, `channel`, `name`, `subject`, `body`, `variables`, `active`, `updated_at`, `updated_by`. Returns `None` when the item is missing.
- `preview_template(template_id, *, sample_vars)` (`notification_templates.py:263`) calls the private `_render(text, sample_vars)` function (`notification_templates.py:245`) which applies the `{{ variable }}` regex `_VAR_RE = re.compile(r"\{\{\s*([a-zA-Z0-9_]+)\s*\}\}")` (`notification_templates.py:23`). This is the correct renderer to use for templates stored in `admin_messaging_templates` — it uses double-brace `{{ }}` syntax, not the single-brace `{var}` syntax of `bot_template.resolve_variables` (`bot_template.py:215`, `bot_template.py:24`: `_VAR_RE = re.compile(r"\{(\w+)\}")`). WFL-007 **must** use `notification_templates._render` (or `preview_template` directly) rather than `bot_template.resolve_variables` because the two regex patterns are incompatible.

### 2.3 Email dispatch

`send_alert_email(to_emails: List[str], subject: str, body_text: str)` lives at `app/services/alerts.py:459`. In dev mode it appends to the dev email log (`S.dev_email_log`) rather than calling SES — no `if dev_mode` branch is needed in WFL-007 itself because `send_alert_email` already handles the divergence transparently (SECOPS-007 parity without any new branches).

The function is fire-and-hold: exceptions from boto3 SES are caught internally, logged, and counted via `EMAIL_FAILED` metric + `record_email_failure` (`alerts.py:480–491`). WFL-007 callers do not need to catch SES errors; they only guard against a `None` / unresolvable address upstream.

### 2.4 Profile email resolution

`app/services/profile.get_profile(user_sub) -> dict` (`profile.py:262`) returns the profile dict from `T.profile`. The email field is `profile["displayed_email"]` (`profile.py:252`). The higher-level `get_profile_identity(user_sub)` (`profile.py:305`) returns `{"email": profile.get("displayed_email"), ...}` (`profile.py:313`) and is the correct function to call when the action config specifies `to_field: "owner_sub"` — resolve the `user_sub` string in the record to a real email address.

### 2.5 Audit events

`app/services/alerts.audit_event(event, user_sub, request=None, **fields)` (`alerts.py:644`) is the standard audit path. WFL-007 calls it with `user_sub="system"` (no HTTP request context), matching the `create_record` pattern established in WFL-006.

### 2.6 Existing tables — no new table needed

`T.admin_messaging_templates` is already defined at `app/core/tables.py:460` and provisioned by `scripts/local-ddb-init.py`. WFL-007 reads from it but does not write to it. `T.crm_workflow_runs` (defined in WFL-001) already stores per-run action results; WFL-007 contributes entries to the `actions_fired` list within the run row that WFL-006 writes.

## 3. Data Model

### 3.1 No new DynamoDB tables

WFL-007 introduces no new tables. All persistent state flows through tables established before this ticket:

| Table handle | Owner ticket | WFL-007 access |
|---|---|---|
| `T.crm_workflow_rules` | WFL-001 | Read — fetch rule and its `actions` list |
| `T.crm_workflow_runs` | WFL-001 | Write — via WFL-006's `_write_run` helper |
| `T.admin_messaging_templates` | ADMIN-002 (pre-existing) | Read — `get_template(template_id)` |
| `T.profile` | pre-existing | Read — `get_profile(user_sub)` when `to_field="owner_sub"` |

### 3.2 Run log `actions_fired` entry shape

Each `send_email` step appends one dict to the `actions_fired` list in the `crm_workflow_runs` item. The shape reuses the WFL-006 convention:

```python
{
    "action_type": "send_email",
    "result": "sent",            # or "skipped"
    "skip_reason": str | None,   # e.g. "to_address_unresolvable", "template_not_found",
                                 #       "template_inactive", "channel_mismatch"
    "template_id": str,
    "to_address": str | None,    # populated even on skip when address was resolved
}
```

`result` is always one of `"sent"` or `"skipped"`. The step never raises — any exception during resolution or dispatch is caught, logged, and mapped to `result="skipped"` with `skip_reason="unexpected_error"`.

### 3.3 `send_email` action config schema

The `config` dict stored in the rule's `actions` list item for a `send_email` step:

| Field | Type | Required | Notes |
|---|---|---|---|
| `template_id` | string | yes | Must match a `TEMPLATE#{id}` row in `T.admin_messaging_templates` |
| `to_field` | string | yes | Name of a field in the record dict that holds the recipient address, or the literal `"owner_sub"` to trigger profile lookup |
| `extra_vars` | dict[str, str] | no | Additional `{{ key }}: value` substitution pairs merged over the record-derived context |

No changes to `app/models.py` `WorkflowActionIn` are required beyond what WFL-002 already defines (`action_type: str`, `config: dict`) — the `send_email` config is validated lazily at execution time rather than at rule-creation time, consistent with the WFL-006 approach for `modify_field` and `create_record`.

## 4. API / Service Design

### 4.1 Files modified (no new files)

WFL-007 touches exactly one file: `app/services/workflow_action_executor.py` (created by WFL-006). No new modules, no router changes, no `app/main.py` changes.

### 4.2 New private helper: `_execute_send_email`

Added to `app/services/workflow_action_executor.py`:

```python
def _execute_send_email(
    action: dict,
    *,
    module: str,
    record: dict,
) -> dict:
    """Execute a send_email action step.

    Returns an actions_fired entry dict with keys:
      action_type, result, skip_reason, template_id, to_address.
    Never raises — all error paths produce result="skipped".

    Args:
        action:  The full action dict from the rule, with action["config"]
                 holding template_id, to_field, and optional extra_vars.
        module:  The target module string (e.g. "ticket", "contact").
        record:  The full record dict as fetched by the executor.
    """
```

### 4.3 Internal flow

```
_execute_send_email(action, module=module, record=record)
│
├─ 1. Parse config
│     config        = action.get("config") or {}
│     template_id   = config.get("template_id")
│     to_field      = config.get("to_field")
│     extra_vars    = config.get("extra_vars") or {}
│     → if template_id or to_field is missing/empty: return skipped("bad_config")
│
├─ 2. Resolve to_address
│     if to_field == "owner_sub":
│         owner_sub = record.get("owner_sub") or record.get("user_sub")
│         if not owner_sub: return skipped("to_address_unresolvable")
│         identity  = profile.get_profile_identity(owner_sub)   # profile.py:305
│         to_address = identity.get("email")
│     else:
│         to_address = record.get(to_field)
│     → if not to_address: return skipped("to_address_unresolvable")
│
├─ 3. Load and validate template
│     tpl = notification_templates.get_template(template_id)    # notification_templates.py:171
│     → if tpl is None: return skipped("template_not_found")
│     → if not tpl.get("active", True): return skipped("template_inactive")
│     → if tpl["channel"] != "email": return skipped("channel_mismatch")
│
├─ 4. Build variable context and render
│     context = {str(k): str(v) for k, v in record.items() if v is not None}
│     context.update({str(k): str(v) for k, v in extra_vars.items()})
│     rendered_subject, _ = notification_templates._render(tpl.get("subject") or "", context)
│     rendered_body,    _ = notification_templates._render(tpl.get("body")    or "", context)
│     # Unresolved {{ vars }} are left in place (notification_templates._render semantics)
│
├─ 5. Dispatch
│     alerts.send_alert_email(                                   # alerts.py:459
│         to_emails=[to_address],
│         subject=rendered_subject or "",
│         body_text=rendered_body or "",
│     )
│
└─ 6. Audit + return
      alerts.audit_event(                                        # alerts.py:644
          "crm_workflow.send_email",
          "system",
          template_id=template_id,
          module=module,
          record_id=record.get(f"{module}_id") or record.get("id", ""),
          to=to_address,
      )
      return {"action_type": "send_email", "result": "sent",
              "skip_reason": None, "template_id": template_id,
              "to_address": to_address}
```

### 4.4 Integration point in `_execute_action`

In WFL-006's `_execute_action` dispatch block, add the `send_email` branch before the final `else` (unknown action type) arm:

```python
elif action_type == "send_email":
    result = _execute_send_email(action, module=module, record=record)
    return result
```

The surrounding `try/except` in `execute_crm_workflow_action` is already in place (WFL-006); `_execute_send_email` itself also wraps its body in a broad `try/except Exception` so that an unexpected error (e.g. `T.profile` unavailable) produces `result="skipped"` rather than propagating to the executor level and causing the entire rule run to be marked `"error"`.

### 4.5 Record hydration

WFL-006's `_execute_action` currently receives only `module` and `record_id`. WFL-007 fetches the full record inside `_execute_send_email` using `workflow_record_fetcher.fetch_module_records` (WFL-005), extended with an optional `record_id` filter for single-item fetch. If the record no longer exists at execution time, `record={}` causes address resolution to fail and the step is skipped with `skip_reason="record_not_found"`. This keeps `_execute_action`'s call signature unchanged.

### 4.6 No new HTTP endpoints

WFL-007 is a pure background-execution enhancement. No routes are added or modified. The admin run-history view (`GET /ui/admin/crm/workflow/rules/{rule_id}/runs`, defined in WFL-009) will surface the enriched `actions_fired` entries written by this ticket.

## 5. Detailed Behavior & Edge Cases

### 5.1 `to_field` resolution

| Scenario | Outcome |
|---|---|
| `to_field = "email"` and `record["email"] = "alice@example.com"` | Address resolved; email dispatched |
| `to_field = "email"` and `"email"` absent from record | `skipped("to_address_unresolvable")` |
| `to_field = "email"` and `record["email"] = ""` (empty string) | Treated as absent; `skipped("to_address_unresolvable")` |
| `to_field = "owner_sub"` and profile has `displayed_email` | Email resolved from profile; dispatched |
| `to_field = "owner_sub"` and profile `displayed_email` is `None` | `skipped("to_address_unresolvable")` |
| `to_field = "owner_sub"` and `T.profile` raises | Caught; `skipped("unexpected_error")` |
| `to_field = "assignee_sub"` (any valid `owner_sub`-style field) | Same profile-lookup path applies if the value looks like a Cognito sub (not an email address itself) — **Note:** WFL-007 does not auto-detect; callers must use `"owner_sub"` as the `to_field` value explicitly to trigger profile lookup. Any other `to_field` value is treated as a literal email address field on the record. |

### 5.2 Template lifecycle

- **Template deleted after rule was saved**: `get_template` returns `None` → `skipped("template_not_found")`. The rule is not automatically disabled; the run log records the skip for admin visibility.
- **Template deactivated** (`active=False`): `skipped("template_inactive")`. Same non-fatal outcome.
- **SMS template used in email action** (`channel="sms"`): `skipped("channel_mismatch")`. The `subject` field is `None` on SMS templates; dispatching via `send_alert_email` would produce an empty subject, which is misleading. The channel guard prevents this.
- **Template subject is `None`** (valid for SMS; should not occur for email templates): `rendered_subject` becomes `""` after the `or ""` guard; `send_alert_email` truncates to 120 chars (`alerts.py:477`), so an empty subject is accepted.

### 5.3 Variable rendering

`notification_templates._render` uses `{{ variable }}` double-brace syntax (`notification_templates.py:23`). Unresolved placeholders are left verbatim — the email may contain raw `{{ record_id }}` text if a variable is missing from the context. The record context is built as `{str(k): str(v) for k, v in record.items() if v is not None}`. DynamoDB `Decimal` values are coerced to `str` by Python's `str()`. `extra_vars` from the action config are merged after, allowing overrides (e.g. injecting `platform_name`, `action_url`).

### 5.4 Ordering and fault isolation

Actions execute sequentially (WFL-006's `for action in rule["actions"]` loop). A `send_email` step that returns `result="skipped"` does not halt the loop; subsequent `modify_field`, `create_record`, or other `send_email` steps continue. `_execute_send_email` wraps its entire body in `try/except`, so no exception escapes to the executor level.

### 5.5 `send_alert_email` guarantees

`send_alert_email` (`alerts.py:459`) never raises. SES errors are caught internally and counted via `EMAIL_FAILED` metric (`alerts.py:483`). WFL-007 records `result="sent"` regardless of SES delivery outcome — this is the existing platform contract for all alert-email callers (best-effort notification, not transactional guarantee).

### 5.6 Idempotency of re-runs

The unified scheduler retries failed `crm_workflow` actions via `schedule_retry` (`unified_scheduler.py:148`). If a retry occurs after `send_alert_email` was called but before `mark_action_completed`, a duplicate email may be sent. WFL-007 does not add additional dedup at the dispatch level; deduplication is provided by `claim_action`'s conditional-put (`scheduled_actions.py:377`) and the WFL-005 enqueue sentinel. Duplicate emails on retry are accepted as the same risk borne by all other `send_alert_email` callers.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

`send_alert_email` (`alerts.py:459`) handles dev/prod divergence internally: `alerts.py:462` writes to the dev email log in dev mode; the prod path calls SES. WFL-007 adds no `if dev_mode` branch — the same code path runs in both environments (SECOPS-007). `notification_templates.get_template`, `_render`, and `profile.get_profile` have no dev/prod branching either.

### 7.2 Idempotency

At-most-once delivery is provided by the unified scheduler's `claim_action` conditional put (`scheduled_actions.py:377`). Once an action is in `executing` status, subsequent scheduler iterations skip it. A crash between email dispatch and `mark_action_completed` can produce at-most one duplicate send (the action would be retried). This is documented in §5.6 and is acceptable for non-transactional workflow notifications.

### 7.3 Security

**Email address exposure**: `to_address` is stored in `T.crm_workflow_runs` (admin-only via WFL-009 router with `Depends(require_admin_or_root_csrf)`); never exposed in user-facing API responses.

**Template injection**: `extra_vars` is admin-authored. Template rendering via `notification_templates._render` substitutes into a stored text body; SES `body_text` is plain text capped at 8000 chars (`alerts.py:477`) — no HTML injection risk.

**Profile lookup authorization**: `profile.get_profile(user_sub)` (`profile.py:262`) is an unchecked DynamoDB `get_item`, appropriate here because the executor runs as `user_sub="system"` (same as `audit_event` at `alerts.py:644`).

**Rate limiting**: No per-rule send quota. High-cardinality `on_schedule` rules can dispatch many `send_alert_email` calls in one tick. Operators must manage SES limits; per-rule quotas are a follow-up.
