# EVT-014 — Outbound SMS from contact record (individual send from UI)

**Type:** Feature | **Priority:** P1 | **Estimate:** 2d
**Source ticket:** `docs/suitecrm/CRM_MISC_TICKETS.md` § EVT-014
**Dependencies:** EVT-001 (flag + guard pattern). Soft dependency on PTY-001.

---

## 1. Summary & Goal

This ticket surfaces the platform's already-complete outbound SMS infrastructure at the CRM layer by adding a "Send SMS" action on a contact record in the frontend. A user clicks an SMS button on any contact row in `ContactsPage`, types a message body (up to 1600 chars), and submits; the backend resolves the contact's phone number, validates it through `normalize_phone`, and hands off to `send_sms` in `app/services/sms_delivery.py` — which already handles dev-mode logging, SNS dispatch, suppression-list enforcement, per-number daily rate limiting, and global cost-cap enforcement.

No new SMS infrastructure is introduced. This ticket is a thin CRM adapter: a dedicated service file (`app/services/crm_contact_sms.py`), a dedicated router (`app/routers/crm_contact_sms.py`), and a minimal frontend compose dialog. The entire feature is gated behind a new default-off flag `CRM_CONTACT_SMS_ENABLED`; with the flag off the platform is byte-for-byte unchanged.

The `contacts` table (`T.contacts`) stores `contact_id` as the sort key and resolves phone from the `profile` table (`T.profile`) via `get_profile_identity`. A new `crm_contact_sms_log` DynamoDB table records a per-contact send history that can be displayed in the UI and is kept separate from the low-level `sms_delivery` tracking already present.

## 2. Context & Current State

### 2.1 SMS delivery infrastructure

`app/services/sms_delivery.send_sms` (`sms_delivery.py:207`) is the single, consolidated outbound SMS pipeline. Its behaviour:

- **Dev mode** (`S.dev_mode`): writes to `S.dev_sms_log` (default `.logs/dev/sms.log`) via `_write_dev_log`, records a `dev_logged` row in `T.sms_delivery`, and returns `{"status": "dev_logged"}`. Never hits AWS SNS.
- **Suppression check** (`sms_delivery.py:233`): calls `is_sms_suppressed(phone)` against `T.sms_delivery` PK `SMS_SUPPRESS#{phone}`; returns `{"status": "suppressed"}` when on the list. Runs in dev and prod identically.
- **Per-number daily rate limit** (`sms_delivery.py:243`): calls `sms_daily_limit_exceeded(phone)` which reads `DAILY#{phone}` / `DAY#{day_key}` in `T.sms_delivery`; returns `{"status": "rate_limited"}` when exceeded. Controlled by `S.sms_daily_limit_per_number` (default 10, `app/core/settings.py:211`).
- **Global cost cap** (`sms_delivery.py:255`): guarded by `S.sms_daily_cost_cap_usd` (default 0 = disabled, `settings.py:218`); returns `{"status": "rate_limited"}` when the estimated daily spend would exceed the cap.
- **Production gate** (`sms_delivery.py:283`): `S.alerts_sms_enabled` (default off, `settings.py:202`). When disabled, returns `{"status": "disabled"}`.
- **SNS send** (`sms_delivery.py:287`): calls `sns_client().publish(...)` with `MessageAttributes` from `_build_sms_attributes()` (respects `S.sms_sender_id`, `S.sms_origination_number`, `S.sms_message_type`).
- Returns `{number, message_id, status}` in all paths.

`send_sms_bulk` (`sms_delivery.py:308`) iterates a list calling `send_sms` per number; EVT-014 does not use it (individual send only). Bulk broadcast from a contact list is in scope for a future MKT-* ticket (see section 11).

### 2.2 Phone normalization

`app/core/normalize.normalize_phone` (`normalize.py:66`) accepts freeform phone strings (E.164, NANP 10-digit, 11-digit US), strips separators, normalises to `+E164`. Raises `HTTPException(400, ...)` on invalid input. This is the canonical validator already used by `app/services/profile.py:216`.

### 2.3 Contacts table and phone resolution

`T.contacts` is a `_FloatSafeTable` handle (`app/core/tables.py:102`, `354`) wrapping the `Contacts` DynamoDB table (env `DDB_CONTACTS_TABLE`, default `"Contacts"`, `settings.py:498`). The table is declared in `scripts/local-ddb-init.py:691` with `PK=owner_id` (S), `SK=contact_id` (S) and no GSIs.

The contacts router (`app/routers/contacts.py`) stores items with the key `{owner_id: user_sub, contact_id: inp.user_id}` (`contacts.py:101-110`). Currently stored fields are: `display_name`, `profile_photo_url`, `is_favorite`, `is_blocked`, `added_at`. There is **no `phone` field** on the contacts item itself.

Phone is resolved through `get_profile_identity(user_sub)` in `app/services/profile.py:305`, which reads `T.profile` and returns `{"display_name", "email", "phone", "profile_photo_url"}` where `phone` maps to `displayed_telephone_number` (`profile.py:314`). The contact's phone is therefore `get_profile_identity(contact_id)["phone"]`. This call may return `None` if the contact has not set a public phone number.

### 2.4 `ContactEntry` model and frontend

`ContactEntry` in `frontend/src/api/types.ts:3143` has no `phone` field. `ContactsPage.tsx` imports `getContacts`, `addContact`, `removeContact`, `updateContact` from `api/endpoints/contacts.ts`; it renders a `DropdownMenu` per contact row (`ContactsPage.tsx:185-207`) with Message, File Share, Calendar Share, and Remove actions. An SMS action is not present.

### 2.5 Audit primitives

`audit_event(event, user_sub, request=None, **fields)` (`app/services/alerts.py:644`) writes a payload to `T.alerts`. It is used throughout the platform (e.g., `"filemgr_file_uploaded"`) and is the canonical audit mechanism for CRM-layer events.

### 2.6 Flag and guard conventions

The default-off flag convention uses `os.environ.get("VAR", "false").lower() in ("1", "true", "yes", "on")` (confirmed in EVT-001 spec and `app/core/settings.py` for `newsfeed_recsys_enabled` and `legal_export_enabled`). Guard helpers raise `HTTPException(status_code=404, ...)` when the flag is off, matching the pattern in `app/routers/group_treasury.py:29`.

EVT-001 already specifies `crm_events_enabled` and the `_require_crm_events_enabled()` guard. EVT-014 introduces a **separate** flag `crm_contact_sms_enabled` with its own guard `_require_crm_contact_sms_enabled()`, so the SMS feature can be enabled independently of the broader CRM Events module.

### 2.7 Per-sender rate limiting

`_bucket_limit(user_sub, sid, max_n, win)` (`app/services/rate_limit.py:60`) provides a sliding-window bucket stored in `T.sessions`. For this feature a dedicated session key `"rl#crm_sms"` is used, controlled by two new settings `CRM_CONTACT_SMS_RATE_MAX` (default 20) and `CRM_CONTACT_SMS_RATE_WINDOW_SECONDS` (default 3600), so operators can independently cap CRM SMS sends per user per hour without touching the MFA or alert limits.

## 3. Data Model

### 3.1 No schema change to existing tables

`T.contacts` (PK=`owner_id`, SK=`contact_id`) and `T.sms_delivery` are used as-is. No columns are added to either.

### 3.2 New table: `crm_contact_sms_log`

A new CRM-layer table stores one row per individual send, giving a per-contact outbound SMS history. It is separate from the low-level `sms_delivery` table (which tracks raw delivery status) and contains CRM context (sender, contact, message body preview, outcome).

**Table name setting**: `crm_contact_sms_log_table_name: str = os.environ.get("CRM_CONTACT_SMS_LOG_TABLE", "crm_contact_sms_log")` added to `app/core/settings.py`.

**Primary key**: `PK = sender_sub` (S), `SK = LOG#{sent_at_ts:010d}#{sms_id}` (S) — lexicographically newest-first when scanned with `ScanIndexForward=False`.

**GSI `ByContact`**: `PK = contact_id` (S), `SK = sent_at_ts` (N). Allows fetching all SMS sent to a specific contact regardless of sender. Must declare `attr_types={"sent_at_ts": "N"}` (CLAUDE.md gotcha: numeric GSI sort keys stored as String cause `ValidationException` at query time).

**GSI `ByStatus`**: `PK = status` (S), `SK = sent_at_ts` (N). Allows admin visibility into failed/suppressed sends. Reuses the same numeric sort key — same `attr_types` declaration covers both GSIs.

**Item attributes**:

| Attribute | Type | Notes |
|---|---|---|
| `sender_sub` | S | PK — the authenticated user who sent |
| `sk` | S | `LOG#{sent_at_ts:010d}#{sms_id}` |
| `sms_id` | S | `uuid4().hex` generated at send time |
| `contact_id` | S | Opaque contact identifier (sort key of `T.contacts`) |
| `contact_phone` | S | Normalised E.164 phone at time of send (denormalised for history) |
| `body_preview` | S | First 160 chars of message body |
| `segments` | N | Estimated SMS segment count |
| `status` | S | `sent` / `dev_logged` / `suppressed` / `rate_limited` / `failed` / `disabled` |
| `message_id` | S | SNS `MessageId` on success; empty string otherwise |
| `sent_at_ts` | N | Unix integer timestamp (`now_ts()`) — GSI sort key |
| `ttl_epoch` | N | `sent_at_ts + 365 * 86400` — 1-year TTL |

**`scripts/local-ddb-init.py` entry** (to be added before the closing `]` of `_table_defs()`):

## 4. API / Service Design

### 4.1 Service: `app/services/crm_contact_sms.py` (new file)

```python
def send_contact_sms(
    *,
    sender_sub: str,
    contact_id: str,
    body: str,
) -> dict:
    """
    Validate + resolve + dispatch a single outbound SMS to a contact.

    Steps:
    1. Validate body length (1–1600 chars; enforced by Pydantic before call).
    2. Resolve contact record from T.contacts (Key={owner_id: sender_sub, contact_id}).
       Raises HTTPException(404) if missing.
    3. Resolve phone via get_profile_identity(contact_id)["phone"].
       Raises HTTPException(404, "contact has no phone number") if None.
    4. Normalise phone via normalize_phone() — raises HTTPException(400) on bad format.
    5. Call send_sms(phone, body) from sms_delivery — returns {number, message_id, status}.
    6. Write one row to T.crm_contact_sms_log.
    7. Call audit_event("crm_contact_sms_sent", sender_sub, contact_id=..., status=...).
    8. Return {ok: True, sms_id, message_id, status, contact_phone (masked)}.
    """


def list_contact_sms_log(
    *,
    sender_sub: str,
    contact_id: str | None = None,
    limit: int = 50,
    cursor: str | None = None,
) -> dict:
    """
    Paginated list of outbound SMS for the authenticated user.

    - If contact_id is given: queries GSI ByContact (PK=contact_id),
      filtered client-side to sender_sub for isolation.
    - Otherwise: queries table directly (PK=sender_sub), SK prefix "LOG#",
      ScanIndexForward=False.
    Returns {items: [...], cursor: str | None}.
    """
```

**Phone masking**: `contact_phone` in the API response is masked to show only the last 4 digits (`+*******1234`). The full E.164 number is stored in `T.crm_contact_sms_log` for admin audit and retry use. This prevents phone number leakage through the API response.

**Log write** (best-effort, never raises): wrapped in `try/except` so a DDB write failure does not block the send. The `sms_delivery` table already has the canonical delivery record; the CRM log is a UX convenience layer.

### 4.2 Router: `app/routers/crm_contact_sms.py` (new file)

```python
router = APIRouter(prefix="/ui/crm/contacts/{contact_id}/sms", tags=["crm_contact_sms"])

class ContactSmsIn(BaseModel):
    body: str = Field(..., min_length=1, max_length=1600)

class ContactSmsOut(BaseModel):
    ok: bool
    sms_id: str
    message_id: str | None
    status: str            # sent | dev_logged | suppressed | rate_limited | failed | disabled
    contact_phone: str     # masked: +*******1234

class ContactSmsLogItem(BaseModel):
    sms_id: str
    contact_id: str
    contact_phone: str     # masked
    body_preview: str
    segments: int
    status: str
    message_id: str | None
    sent_at_ts: int

class ContactSmsLogOut(BaseModel):
    items: list[ContactSmsLogItem]
    cursor: str | None
```

**Endpoints**:

| Verb | Path | Auth | Description |
|---|---|---|---|
| `POST` | `/ui/crm/contacts/{contact_id}/sms` | `require_ui_session` | Send SMS to contact |
| `GET` | `/ui/crm/contacts/{contact_id}/sms` | `require_ui_session` | List send history for contact |
| `GET` | `/ui/crm/sms/log` | `require_ui_session` | List all sends by this sender |

The three endpoints share one guard invocation: `_require_crm_contact_sms_enabled()` raises `HTTPException(404)` when `S.crm_contact_sms_enabled` is `False`.

**`POST /ui/crm/contacts/{contact_id}/sms`** (send):
1. Call `_require_crm_contact_sms_enabled()`.
2. Call `rate_limit_crm_sms(user_sub)` (see below) — raises 429 on breach.
3. Call `send_contact_sms(sender_sub=user_sub, contact_id=contact_id, body=inp.body)`.
4. Return `ContactSmsOut`.

**`GET /ui/crm/contacts/{contact_id}/sms`** (history for one contact):
1. Call `_require_crm_contact_sms_enabled()`.
2. Call `list_contact_sms_log(sender_sub=user_sub, contact_id=contact_id, limit=..., cursor=...)`.
3. Return `ContactSmsLogOut`.

**`GET /ui/crm/sms/log`** (all sends by authenticated user):
1. Call `_require_crm_contact_sms_enabled()`.
2. Call `list_contact_sms_log(sender_sub=user_sub, limit=..., cursor=...)`.
3. Return `ContactSmsLogOut`.

**Route registration**: `app/main.py` gains:
```python

```

### 4.3 Rate-limit helper: `rate_limit_crm_sms` in `app/services/rate_limit.py`

```python
def rate_limit_crm_sms(user_sub: str) -> None:
    """Raise HTTPException(429) if user exceeds CRM SMS send rate."""
    if not _bucket_limit(
        user_sub,
        "rl#crm_sms",
        S.crm_contact_sms_rate_max,
        S.crm_contact_sms_rate_window_seconds,
    ):
        raise HTTPException(429, "SMS rate limit exceeded; try again shortly")
```

Uses the existing `_bucket_limit` helper (`rate_limit.py:60`), which stores bucket state in `T.sessions`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Send flow happy path

`POST /ui/crm/contacts/alice123/sms` with `{"body": "Hi from CRM"}` by user `sender_sub`:
1. Guard passes (`crm_contact_sms_enabled=true`).
2. Rate-limit bucket checked; count incremented.
3. `T.contacts.get_item(Key={owner_id: sender_sub, contact_id: "alice123"})` — item found.
4. `get_profile_identity("alice123")["phone"]` returns `"+15551234567"`.
5. `normalize_phone("+15551234567")` returns `"+15551234567"` (already valid E.164).
6. `send_sms("+15551234567", "Hi from CRM")` — in dev returns `{status: "dev_logged", message_id: "dev-1234567890"}`.
7. Log row written to `T.crm_contact_sms_log`.
8. `audit_event("crm_contact_sms_sent", sender_sub, contact_id="alice123", status="dev_logged")` called.
9. Response: `{ok: true, sms_id: "abc123", message_id: "dev-1234567890", status: "dev_logged", contact_phone: "+*******4567"}`.

### 5.2 No phone number

`get_profile_identity(contact_id)["phone"]` returns `None`. Service raises `HTTPException(404, "contact has no phone number")`. The log row is **not** written. The audit event is **not** emitted. Frontend shows a toast: "This contact has no phone number on their profile."

### 5.3 Contact not found

`T.contacts.get_item(...)` returns no `Item`. Service raises `HTTPException(404, "contact not found")`. No log write. No audit.

### 5.4 Suppressed number

`is_sms_suppressed(phone)` returns `True`. `send_sms` returns `{status: "suppressed"}`. Log row is written with `status="suppressed"`. Audit event `crm_contact_sms_sent` emitted with `status="suppressed"`. API returns 200 with `{ok: true, status: "suppressed"}` — the send is not an error; the caller should surface a UI message "This number has opted out of SMS."

### 5.5 Per-number daily limit exceeded

`sms_daily_limit_exceeded(phone)` returns `True`. `send_sms` returns `{status: "rate_limited"}`. Log row written. Audit emitted. API returns 200 with `status="rate_limited"`.

### 5.6 Sender rate limit (CRM-layer)

`_bucket_limit(user_sub, "rl#crm_sms", ...)` returns `False`. Router raises `HTTPException(429)` **before** calling the service. No `send_sms` call, no log write, no audit. Frontend shows a toast: "SMS rate limit reached. Please try again later."

### 5.7 SNS failure

`send_sms` catches the `Exception` from `sns.publish`, calls `record_sms_failure`, and returns `{status: "failed"}`. Service writes log row with `status="failed"` (best-effort). Service **does not re-raise** — returns `{ok: true, status: "failed"}` to the caller. Frontend shows a warning toast indicating failure.

### 5.8 Body length

Pydantic `Field(min_length=1, max_length=1600)` enforces bounds before the handler runs; FastAPI returns 422 automatically. `sms_delivery._estimate_segments` caps at segment-based accounting; `send_sms` itself truncates to 1400 chars before SNS publish (`sms_delivery.py:295`).

### 5.9 Invalid phone format on profile

If `get_profile_identity` returns a phone that fails `normalize_phone` (e.g., a free-text string that was saved before normalization was enforced), the service catches the resulting `HTTPException(400)` and re-raises it as `HTTPException(400, "contact phone number is not valid")`. Log not written.

### 5.10 SMS disabled in production

`S.alerts_sms_enabled=false` (default). `send_sms` returns `{status: "disabled"}`. Log row written with `status="disabled"`. API returns 200. No error — operator must explicitly enable SMS.

### 5.11 Flag off

`S.crm_contact_sms_enabled=false`. All three endpoints return `404`. Existing contact routes (`/ui/contacts`) are untouched. `T.crm_contact_sms_log` exists in DynamoDB but receives no writes.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

There is **no `dev_mode` branch** in `crm_contact_sms.py`. The service calls `send_sms(phone, body)` unconditionally; `sms_delivery.send_sms:268` already short-circuits to `record_sms_dev_logged` in dev mode and never hits SNS. The suppression check, daily rate limit, and global cost-cap check run identically in both environments. DynamoDB writes to `T.crm_contact_sms_log` are the same in dev (DynamoDB Local on port 8001) and prod (real DynamoDB) — the `_FloatSafeTable` proxy handles numeric coercion in both.

### 7.2 Phone number security

- The `contact_phone` field returned in API responses is **masked** (last 4 digits visible).
- The full E.164 value is stored only in `T.crm_contact_sms_log` (server-side) and in `T.sms_delivery` (existing, unchanged). It is never returned to the frontend.
- `audit_event` includes `contact_phone` in the audit payload but the audit log is accessible only to ROOT-role principals.

### 7.3 Ownership enforcement

The contact lookup uses `Key={owner_id: user_sub, contact_id: contact_id}` — a sender can only SMS their own contacts. A contact belonging to a different user returns 404 (item simply not found under the caller's `owner_id`). No additional ownership predicate is required.

### 7.4 Idempotency

Each send generates a fresh `sms_id = uuid4().hex`. There is no idempotency key on the SMS send itself (the UI button should be disabled after submission). The `T.crm_contact_sms_log` write is a blind `put_item` with a unique SK; concurrent duplicate submits may produce two log rows, but only one SNS `publish` call reaches the carrier because the frontend blocks re-submission via React `useMutation` `isPending` state.

### 7.5 CSRF

The `POST` endpoint uses `require_ui_session` which enforces CSRF for cookie-auth requests (`x-csrf-token` header). Bearer-auth calls (API clients) bypass CSRF per the existing auth architecture (`app/auth/deps.py`).

### 7.6 Input sanitisation

Message body is a plain string; no HTML or Markdown is accepted. Pydantic `Field(max_length=1600)` truncates at the model layer. `sms_delivery.send_sms` further caps at 1400 chars before SNS publish (`sms_delivery.py:295`). No injection risk for SMS bodies.

## 8. Backward Compatibility & Migration

### 8.1 Existing endpoints unchanged

`/ui/contacts` (list, add, remove, update) — no modification. `T.contacts` schema is unchanged. `ContactEntry` in `frontend/src/api/types.ts` is unchanged (no `phone` field added to the public type). There is no migration of existing contact records.

### 8.2 `T.crm_contact_sms_log` table creation

`just restart` (which runs `scripts/local-ddb-init.py` via `scripts/local-stack-up.sh`) creates the new table with both GSIs. In production a one-time `CreateTable` AWS CLI or CloudFormation call is required before the flag is enabled. The table starts empty; no backfill is needed.

### 8.3 No changes to `T.sms_delivery` or `T.contacts`

The `sms_delivery` table already tracks delivery events. `crm_contact_sms_log` adds a CRM-context overlay; the two tables are independent. If the CRM log table is absent (e.g., forgotten in prod), the write fails silently (best-effort `try/except`) and the SMS still sends.

### 8.4 Profile `displayed_telephone_number` field

This field is already present in `T.profile` items for users who have set it. Its absence for a given contact is an expected state and is handled by the 404 response described in section 5.2. No profile schema migration is required.

## 10. Open Questions / Assumptions

1. **Phone source for PTY contacts**: Currently `get_profile_identity(contact_id)` reads `T.profile`. After PTY-001 ships, the enriched Party record may be the authoritative phone source. This implementation treats the `T.profile` path as the definitive source (consistent with `app/services/profile.py:314`); PTY integration will require a separate adapter update.

2. **Phone visibility gating**: `displayed_telephone_number` visibility is controlled by the profile visibility setting (`profile.py:93` — default `"private"`). A contact's phone may be `None` even if set, if they have it marked private. This is treated as "no phone" (404) — **assumption**: the 404 message text "This contact has no phone number" is acceptable even when the real reason is privacy settings. An alternative message ("phone number unavailable") is more accurate but requires a visibility-check code path.

3. **Log retention**: TTL is set to 1 year (`sent_at_ts + 365 * 86400`). This is the same order of magnitude as `sms_delivery` (90 days) but longer because the CRM log is a user-visible history, not just an infrastructure trace. Operators may reduce via the `CRM_CONTACT_SMS_LOG_TABLE` TTL configuration or a separate setting if needed.

4. **Character encoding warning**: `_estimate_segments` in `sms_delivery.py:150` uses an ASCII heuristic; non-ASCII content counts as UCS-2 (70 chars/segment). The frontend textarea does not currently warn the user about segment count. A future UX improvement would add a live segment counter, but this is out of scope for EVT-014.

5. **Opt-out handling**: The platform's `is_sms_suppressed` check (`sms_delivery.py:336`) guards the send. There is no CRM-layer UI to show whether a contact is suppressed before composing. An operator who needs this should query the suppression list via the existing admin SMS dashboard (`GET /ui/admin/sms/suppression-list`, gated by `require_admin_session`).

6. **Concurrent sends to the same number**: Two users can both have the same person as a contact. The per-number daily limit in `sms_delivery` is phone-keyed and shared across all callers, which is correct behaviour (the carrier cap is per-number regardless of who sends).
