# ACT-002 — Calendar RSVP — attendee RSVP status tracking

---

## 1. Summary & Goal

ACT-002 upgrades the flat `attendees: List[str]` field on calendar events to carry per-attendee RSVP state (accepted / declined / tentative / no_response). The RSVP data lives in its own DDB table (`crm_event_rsvp`) introduced by ACT-001, keeping the primary event item in `T.calendar` byte-for-byte unchanged. Two new authenticated endpoints are added — one for an attendee to record their response, one to read the enriched attendee list — both gated behind a dedicated feature sub-flag so the change is fully invisible when disabled.

The goal is to match SuiteCRM's attendee/RSVP workflow (accept, decline, tentative, no-response) described in `docs/suitecrm/CRM_ACTIVITIES_TICKETS.md` lines 7–8, while reusing the existing calendar primitives, audit infrastructure, and pagination utilities already present in the codebase.

---

## 2. Context & Current State

**Event storage** — Calendar events are stored in `T.calendar` (the single `calendar` DynamoDB table, handle wired at `app/core/tables.py:346`). Each event item has `PK=calendar_id` / `SK=event#{event_id}`. The item carries `"attendees": [list_of_user_sub_strings]` which is written verbatim by `create_event` (`app/routers/calendar.py:1551`) and `update_event` (`app/routers/calendar.py:1766`). The `_event_out` helper (function definition at `app/routers/calendar.py:979`, `return EventOut(...)` block at `app/routers/calendar.py:996–1018`) reads this field directly:

```python
attendees=item.get("attendees", []),   # calendar.py:1006
```

`EventOut.attendees` is declared `List[str]` in `app/models.py:1284`. There is no RSVP status anywhere in the existing data model.

**Access control** — Calendar owner and calendar-share checks are performed by `_load_calendar_access` (`app/routers/calendar.py:806`), which returns the calendar meta item if the caller is the owner or has a share record. Write operations additionally require `write` permission (line 817). This function is the canonical gate for all calendar endpoint guards.

**Audit infrastructure** — `app/services/alerts.audit_event` (`app/services/alerts.py:644`) writes a timestamped audit record to `T.alerts`. The existing event endpoints already emit `calendar_event_create` and `calendar_event_update` audit events (lines 1589, 1823).

**In-app alerts** — `app/services/alerts.write_alert` (`app/services/alerts.py:356`) writes a per-user in-app notification row. Used by several notification paths in the codebase; ACT-002 reuses it to notify the calendar owner when an attendee responds.

**Email delivery** — `app/services/alerts.send_alert_email` (`app/services/alerts.py:459`) sends a plain-text email via SES in prod and writes to the dev email log (`S.dev_email_log`) in dev mode (line 462). This is the single reusable email primitive mandated by the cross-cutting constraint at `CRM_ACTIVITIES_TICKETS.md:15`.

**Attendee email lookup** — `app/services/profile.get_profile_identity(user_sub)` (`app/services/profile.py:305`) returns `{"email": ..., "display_name": ...}` for a given user sub. Used here to resolve attendee display names in notification payloads.

**Pagination** — `app/core/cursor.encode_cursor` / `decode_cursor` (`app/core/cursor.py:94`, `103`) produce HMAC-signed v2 cursors. The `ByUser` GSI query on `crm_event_rsvp` uses this for the `list_user_rsvps` path.

**Settings flag pattern** — The `cart_reminders_enabled` bool at `app/core/settings.py:821` is the canonical pattern for default-off flags: `os.environ.get("KEY", "0") not in ("0", "false", "False")`. ACT-001 adds `S.crm_activities_enabled` and `S.crm_event_rsvp_enabled` following this pattern.

**New DDB table** — ACT-001 scaffolds the `crm_event_rsvp` table (key scheme described in `CRM_ACTIVITIES_TICKETS.md:60–64`) and wires its handle as `T.crm_event_rsvp` in `app/core/tables.py` (next to `T.calendar` at line 346). ACT-002 depends on that table existing.

**What does NOT exist yet** — There is no `EventAttendeeOut`, no `EventRsvpUpdateIn`, no `crm_event_rsvp` service module, and no RSVP endpoint anywhere in `app/routers/calendar.py`. The `_event_out` function has no RSVP enrichment path.

## 3. Data Model

### 3.1 `crm_event_rsvp` table (provisioned by ACT-001)

| Attribute | Type | Role |
|---|---|---|
| `event_key` | S (PK) | `{calendar_id}#{event_id}` |
| `attendee_sub` | S (SK) | The attending user's `user_sub` |
| `status` | S | `accepted` \| `declined` \| `tentative` \| `no_response` |
| `responded_at` | N | Unix epoch seconds; `None` when status is `no_response` |
| `updated_at` | N | Unix epoch seconds, always set |
| `user_sub` | S | Denormalized copy of `attendee_sub` (for GSI projection) |
| `calendar_id` | S | Denormalized for lookup convenience |
| `event_id` | S | Denormalized for lookup convenience |

**GSI `ByUser`** — PK = `GSI1PK` (value `USER#{attendee_sub}`), SK = `GSI1SK` (value = `updated_at`, integer). Enables `list_user_rsvps`. Declared with `attr_types={"GSI1SK": "N"}` in `scripts/local-ddb-init.py` per the CLAUDE.md gotcha ("Missing this causes DynamoDB to store it as String → `ValidationException` when queried with integer values").

The table definition added in ACT-001 (shown verbatim in `CRM_ACTIVITIES_TICKETS.md:60–64`) is not duplicated here; ACT-002 uses it exactly as specified.

### 3.2 No changes to the `calendar` table

The `attendees: List[str]` field on event items is left exactly as written by `create_event` and `update_event`. ACT-002 is purely additive: RSVP state lives only in `crm_event_rsvp`; the calendar item is not touched.

### 3.3 Pydantic additions (`app/models.py`)

```python
class EventAttendeeRsvpStatus(str, Enum):
    accepted    = "accepted"
    declined    = "declined"
    tentative   = "tentative"
    no_response = "no_response"

class EventAttendeeOut(BaseModel):
    user_sub: str
    rsvp_status: EventAttendeeRsvpStatus = EventAttendeeRsvpStatus.no_response
    responded_at: Optional[int] = None   # Unix epoch; None when no_response

class EventRsvpUpdateIn(BaseModel):
    status: EventAttendeeRsvpStatus

class EventAttendeeListOut(BaseModel):
    attendees: List[EventAttendeeOut]

class UserRsvpListOut(BaseModel):
    items: List[dict]           # raw rsvp rows enriched with event_key
    next_cursor: Optional[str] = None
```

`EventAttendeeOut` is the enriched form used only by the two new endpoints. `EventOut.attendees` remains `List[str]` — backward compatibility is preserved by never touching `_event_out`.

## 4. API / Service Design

### 4.1 Service layer — `app/services/crm_event_rsvp.py` (new file)

All functions import `T.crm_event_rsvp`, `now_ts`, `encode_cursor`, `decode_cursor`, and `audit_event` from existing codebase modules. No novel dependencies.

```python
def upsert_rsvp(
    calendar_id: str,
    event_id: str,
    attendee_sub: str,
    status: str,          # EventAttendeeRsvpStatus value
) -> dict:
```
Writes one item to `T.crm_event_rsvp` with `PK={calendar_id}#{event_id}`, `SK={attendee_sub}`. Sets `responded_at=now_ts()` when status is not `no_response`; sets `responded_at=None` (removes attribute) when status reverts to `no_response`. Sets `updated_at=now_ts()` always. Sets `GSI1PK=USER#{attendee_sub}`, `GSI1SK=updated_at`. Uses `put_item` (unconditional upsert — last write wins, idempotent). Emits `audit_event("calendar_event_rsvp", attendee_sub, None, calendar_id=..., event_id=..., status=...)` after the write.

```python
def get_rsvp(
    calendar_id: str,
    event_id: str,
    attendee_sub: str,
) -> Optional[dict]:
```
`T.crm_event_rsvp.get_item(Key={"event_key": f"{calendar_id}#{event_id}", "attendee_sub": attendee_sub})`. Returns `None` when item absent.

```python
def list_rsvps(
    calendar_id: str,
    event_id: str,
) -> List[dict]:
```
`T.crm_event_rsvp.query(KeyConditionExpression=Key("event_key").eq(f"{calendar_id}#{event_id}"))`. Paginates with `LastEvaluatedKey` loop if result set exceeds one page (per CLAUDE.md: "DDB FilterExpression doesn't reduce page size" — even plain queries can span pages on busy tables). Returns a plain list; no cursor needed for the per-event attendee list since event attendee counts are bounded.

```python
def list_user_rsvps(
    attendee_sub: str,
    limit: int = 20,
    cursor: Optional[str] = None,
) -> dict:
```
Queries `ByUser` GSI: `PK=USER#{attendee_sub}`, sorted by `GSI1SK` descending (`ScanIndexForward=False`). Applies `ExclusiveStartKey=decode_cursor(cursor)` when cursor present. Returns `{"items": [...], "next_cursor": encode_cursor(last_evaluated_key)}`.

```python
def _enrich_attendees(
    calendar_id: str,
    event_id: str,
    attendees: List[str],
) -> List[EventAttendeeOut]:
```
Calls `list_rsvps(calendar_id, event_id)` once to build a `{attendee_sub: rsvp_row}` map. For each `user_sub` in the plain `attendees` list, returns an `EventAttendeeOut` using the RSVP row if found, or defaulting to `rsvp_status=no_response, responded_at=None`. Any `user_sub` present in the RSVP table but absent from `attendees` is silently omitted (the event item is the source of truth for membership).

### 4.2 Router additions (`app/routers/calendar.py`)

Both routes are added at the bottom of `router` (the authenticated `APIRouter` already defined in the file). Both are gated with an early 404 guard:

```python
if not S.crm_activities_enabled or not S.crm_event_rsvp_enabled:
    raise HTTPException(status_code=404, detail="Not found")
```

#### PUT `/ui/calendars/{calendar_id}/events/{event_id}/rsvp`

```python
@router.put(
    "/calendars/{calendar_id}/events/{event_id}/rsvp",
    response_model=EventAttendeeOut,
)
async def update_event_rsvp(
    calendar_id: str,
    event_id: str,
    body: EventRsvpUpdateIn,
    ctx: Dict[str, str] = Depends(require_ui_session),
) -> EventAttendeeOut:
```

Steps:
1. Flag gate (404 when disabled).
2. Load event item: `T.calendar.get_item(Key={"calendar_id": calendar_id, "sk": f"event#{event_id}"})`. 404 if absent.
3. Verify caller is in `item.get("attendees", [])`. Raise `HTTPException(403, "Not an attendee")` otherwise.
4. Call `upsert_rsvp(calendar_id, event_id, ctx["user_sub"], body.status.value)`.
5. Optionally notify the calendar owner: load calendar meta (`T.calendar.get_item(Key=_calendar_keys(calendar_id))`); if owner is not the attendee, call `write_alert` with `event="calendar_rsvp_received"`, `title=f"{identity['display_name']} {body.status.value} your event: {item['name']}"`. Best-effort, wrapped in `try/except`.
6. Return `EventAttendeeOut(user_sub=ctx["user_sub"], rsvp_status=body.status, responded_at=row["responded_at"])`.

Auth: `require_ui_session` (cookie or Bearer). CSRF enforced automatically for cookie sessions (see `app/auth/deps.py` CSRF check). No admin role required.

#### GET `/ui/calendars/{calendar_id}/events/{event_id}/attendees`

```python
@router.get(
    "/calendars/{calendar_id}/events/{event_id}/attendees",
    response_model=EventAttendeeListOut,
)
async def list_event_attendees(
    calendar_id: str,
    event_id: str,
    ctx: Dict[str, str] = Depends(require_ui_session),

```

Steps:
1. Flag gate.
2. Load event item; 404 if absent.
3. Verify caller is either calendar owner (`_load_calendar_access` — tolerates share-access) OR in `item.get("attendees", [])`. Raise 403 if neither.
4. Call `_enrich_attendees(calendar_id, event_id, item.get("attendees", []))`.
5. Return `EventAttendeeListOut(attendees=enriched)`.

#### GET `/ui/calendars/{calendar_id}/events/{event_id}/rsvp` (self-query convenience)

```python

    "/calendars/{calendar_id}/events/{event_id}/rsvp",

```

Steps:
1. Flag gate.
2. Load event item; 404 if absent.
3. Verify caller is in `item.get("attendees", [])`. Raise 403 otherwise.
4. Call `get_rsvp(calendar_id, event_id, ctx["user_sub"])`. If None, return default `EventAttendeeOut(user_sub=ctx["user_sub"], rsvp_status="no_response")`.
5. Return `EventAttendeeOut` populated from row.


## 5. Detailed Behavior & Edge Cases

**Attendee membership check** — The `attendees: List[str]` on the event item is the authoritative membership list. A `user_sub` that appears in `crm_event_rsvp` but was subsequently removed from `attendees` must NOT be returned by `list_event_attendees` (the `_enrich_attendees` helper iterates `attendees`, not RSVP rows). Stale RSVP rows for removed attendees are invisible and harmless; they are not deleted (no tombstone needed).

**Re-RSVP (status change)** — `upsert_rsvp` is an unconditional `put_item`. Calling `PUT /rsvp` twice with different statuses always results in the last status winning. `responded_at` is refreshed on each non-`no_response` write. This is correct: a user may change their mind until the event passes.

**Reverting to `no_response`** — When the caller sends `status=no_response`, the service sets `responded_at` to `None`. `put_item` with a `None` value for a numeric attribute would store a NULL; to avoid this, the service implementation explicitly removes the key from the item dict before writing when `responded_at is None` (consistent with how DynamoDB handles absent optional numeric attributes throughout the codebase).

**Calendar owner updating RSVP** — The calendar owner appears in `attendees` (they may invite themselves). The 403 guard checks membership, not ownership; an owner who is also an attendee may PUT their own RSVP. Owner-only writes are not blocked.

**Non-attendee read access** — `list_event_attendees` is accessible to the calendar owner and to all calendar-share holders (via `_load_calendar_access`), as well as to attendees listed in `item["attendees"]`. A non-attendee, non-owner, non-share-holder gets 403. This is consistent with the access model of existing calendar endpoints (lines 806–818 in `app/routers/calendar.py`).

**Event not found vs. calendar not found** — The PUT endpoint loads the event directly from `T.calendar` without going through `_load_calendar_access` first; a 404 is returned for both a missing event and a missing calendar. This is acceptable because the RSVP action does not require write permission on the calendar itself — an attendee may not have calendar write access.

**All-day events** — `responded_at` semantics are identical for all-day events. The RSVP table stores no time information beyond the timestamp of the response.

**Recurrence instances** — A single `event_id` in `T.calendar` represents the entire series. RSVP status is per `event_id`, not per occurrence. Per-occurrence RSVP tracking is out of scope for this ticket. The spec records this as an open question (see §10).

**DDB pagination in `list_rsvps`** — Attendee lists for real-world meetings are small (< 100), but the implementation must still loop `LastEvaluatedKey` to be correct (CLAUDE.md: "DDB FilterExpression doesn't reduce page size"). The loop uses no filter expression so each page is fully used; in practice a single page covers all attendees.

**`ByUser` GSI and `no_response` rows** — The GSI is written on every `upsert_rsvp`, including `no_response` reverts. This means `list_user_rsvps` returns all events the user has been invited to and explicitly touched, even those where they reverted to `no_response`. Callers may filter client-side. An alternative design (delete the GSI row on `no_response`) is noted as an open question.

**Notification on RSVP** — The owner in-app notification is best-effort (`try/except`). `write_alert` is called only when `owner_sub != attendee_sub` to avoid self-notifications when the owner RSVPs their own event.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity** — The RSVP service uses `T.crm_event_rsvp` for all reads and writes in both environments. There is no `if S.dev_mode` branch. DynamoDB Local (`port 8001`) and real DynamoDB share the same `boto3` path through `_FloatSafeTable` (`app/core/tables.py:29`). The owner notification calls `write_alert` which writes to DDB local in dev and to the production `alerts` table in prod — same code path both ways.

**Idempotency** — `upsert_rsvp` uses an unconditional `put_item`. Sending the same `PUT /rsvp` twice with the same status is a no-op from the caller's perspective (returns the same `EventAttendeeOut`). The `audit_event` call fires on every request; this is consistent with the pattern across the codebase (e.g., `calendar_event_create` fires on every `create_event` call including retries).

**CSRF** — The `PUT /rsvp` endpoint uses `require_ui_session`. For cookie-authenticated requests, CSRF validation is enforced by the dependency (`app/auth/deps.py`): the request must carry `x-csrf-token` header matching `session.csrf_token` and the `ui_csrf` cookie. Bearer-authenticated requests bypass CSRF (same rule as all other `require_ui_session` endpoints).

**Authorization** — The attendee membership check is enforced server-side. A user who knows a `calendar_id` and `event_id` but is not listed in `item["attendees"]` receives 403. This prevents an attacker from injecting spurious RSVP rows for events they have no access to. The 403 does not leak whether the calendar or event exists (the 404 is returned first when the item is genuinely absent).

**No money movement** — This ticket involves no billing, refunds, or ledger operations. The refund/ledger constraint in the cross-cutting rules (`CRM_ACTIVITIES_TICKETS.md:14`) is therefore not applicable.

**Input validation** — `EventRsvpUpdateIn.status` is a `str`-based `Enum`; FastAPI/Pydantic will reject any value not in the four-element set before the handler runs, returning a 422 with no DDB interaction.

**Audit trail** — Every successful `upsert_rsvp` call emits an `audit_event("calendar_event_rsvp", ...)` to `T.alerts` (via `app/services/alerts.audit_event`, `alerts.py:644`). Fields: `calendar_id`, `event_id`, `attendee_sub`, `status`, `ts`. This provides a tamper-evident log of all RSVP state changes.

## 8. Backward Compatibility & Migration

**Zero-migration required** — Existing event items in `T.calendar` are not modified. The `crm_event_rsvp` table starts empty. All existing callers of `EventOut` receive the unchanged `attendees: List[str]` field, because `_event_out` (`calendar.py:996`) is not altered. The new `EventAttendeeOut` type is used exclusively by the four new endpoints.

**API versioning** — All four new routes use new URL paths distinct from existing calendar routes. There is no ambiguity with existing routes. In particular, `GET /calendars/{id}/events/{eid}/attendees` and `PUT .../rsvp` are new paths with no prior existence in the router.

**Gradual enablement** — Teams can enable `CRM_EVENT_RSVP_ENABLED=1` on any existing deployment without backfilling RSVP rows. All existing event attendees appear in `list_event_attendees` with `rsvp_status=no_response` and `responded_at=None` — the default state that correctly reflects "never responded."

**Flag-off rollback** — Setting `CRM_EVENT_RSVP_ENABLED=0` at any time restores pre-ACT-002 behavior completely. RSVP rows in DDB are not deleted (they remain dark until the flag is re-enabled). No destructive migration is ever needed.

**`EventOut.attendees` type stability** — The field remains `List[str]` in `EventOut`. No existing frontend or API client that reads `EventOut.attendees` needs modification. The enriched `EventAttendeeOut` type is only returned by the two new GET endpoints and the PUT endpoint.

## 10. Open Questions / Assumptions

1. **Per-occurrence RSVP for recurring events** — The current design tracks RSVP at the `event_id` level (entire series). SuiteCRM supports per-occurrence RSVP (`VEVENT` instances have distinct UIDs). This ticket defers per-occurrence support; a follow-on ticket may extend `SK` to `{attendee_sub}#{occurrence_date}` if needed. The current DDB key scheme does not prevent this extension.

2. **Delete-on-no-response vs. keep-the-row** — The current design keeps the RSVP row when status reverts to `no_response`, making `list_user_rsvps` return events where the user explicitly de-responded. An alternative is to delete the row on `no_response`. This spec chooses keep-the-row because it preserves audit history and because `_enrich_attendees` handles absent rows identically to `no_response` rows. The behavior should be confirmed before implementation.

3. **RSVP cleanup on attendee removal** — When `update_event` removes a `user_sub` from `attendees`, the corresponding RSVP row in `crm_event_rsvp` is not deleted. The stale row is invisible to callers (guarded by `_enrich_attendees` membership check) but occupies DDB storage. ACT-003 or a follow-on maintenance ticket may add cleanup.

4. **RSVP cleanup on event delete** — Similarly, deleting an event does not delete RSVP rows. These are considered orphaned rows. A TTL attribute could be added to `crm_event_rsvp` rows (set to event `end_utc + 30 days`); this is deferred.

5. **Bulk initial RSVP seeding** — When an event is created with attendees, no RSVP rows are written (all attendees implicitly have `no_response`). This is intentional (lazy initialization). If ACT-003 (invitation emails) needs a "sent" state, a `invited` status value could be added; this is deferred to ACT-003.

6. **Admin visibility** — There is no admin endpoint to view RSVP data. An admin may call `GET /ui/calendars/{id}/events/{eid}/attendees` only if they are the calendar owner or an attendee. This is consistent with the general principle that admin access to user calendar data requires impersonation. If broader admin visibility is needed, it is out of scope here.
