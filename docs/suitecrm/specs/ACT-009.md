## 1. Summary & Goal

ACT-009 delivers the CRM Activity History Timeline: a single chronological feed that aggregates any CRM activity (call, task, note, calendar event, email) linked to a Contact, Lead, Account, or Opportunity, regardless of which module recorded it. The service is the central write target for all sibling ACT modules and exposes one paginated read endpoint per entity.

Concretely this ticket delivers:

- `app/services/crm_activity_timeline.py` — the write primitive (`record_crm_activity`) and read/delete functions (`list_entity_activities`, `delete_entity_activity`).
- `app/routers/crm_activity_timeline.py` — one `GET` endpoint per entity returning a `CrmActivityTimelineOut` payload; one `DELETE` endpoint for hard-removing a stale row.
- Pydantic models `CrmActivityOut` and `CrmActivityTimelineOut` appended to `app/models.py`.
- Registration of the router in `app/main.py`.
- `scripts/local-ddb-init.py` entry for the `crm_activity_timeline` table (provisioned by ACT-001; this ticket only asserts the entry exists and documents the shape).

With `CRM_ACTIVITIES_ENABLED=0` (default) or `CRM_ACTIVITY_TIMELINE_ENABLED=0` the platform is byte-for-byte unchanged: the router returns 404 on all routes and `record_crm_activity` is a no-op guard that returns immediately.

## 3. Data Model

### 3.1 DynamoDB: `crm_activity_timeline` table

This table is provisioned by ACT-001. ACT-009 documents the full item shape and access patterns.

**Primary key**

| Attribute | Type | Value |
|-----------|------|-------|
| `entity_key` | S (PK) | `"{entity_type}#{entity_id}"` e.g. `"contact#party_abc"` |
| `sk` | S (SK) | `"{inverted_ts:013d}#{activity_type}#{activity_id}"` |

The inverted timestamp uses `9_999_999_999_999 - created_at` (matching the `_make_sk` pattern in `app/services/call_history.py:31`) so that `ScanIndexForward=False` is not needed; natural lexicographic order yields newest-first without a sort direction parameter.

**Item attributes**

| Attribute | Type | Notes |
|-----------|------|-------|
| `entity_key` | S | PK; redundant store for readback |
| `sk` | S | SK as above |
| `entity_type` | S | `contact`, `lead`, `account`, `opportunity` |
| `entity_id` | S | Opaque string — PTY record id once PTY ships |
| `activity_type` | S | `call`, `task`, `note`, `calendar_event`, `email` |
| `activity_id` | S | ID of the source record in its owning table |
| `user_sub` | S | The user who performed or owns the activity |
| `summary` | S | Short human-readable description (≤ 200 chars) |
| `metadata` | M (map) | Arbitrary JSON sub-fields; caller-supplied |
| `created_at` | N | Unix epoch seconds (integer) |
| `GSI1PK` | S | `"TYPE#{activity_type}"` |
| `GSI1SK` | N | Same value as `created_at` |

`GSI1SK` is a numeric sort key, so `scripts/local-ddb-init.py` must include `attr_types={"GSI1SK": "N"}` in the `TableDef` for `crm_activity_timeline` (ACT-001 is responsible; this spec repeats the requirement for clarity).

**GSI: `ByType`**

| Attribute | Value |
|-----------|-------|
| PK | `GSI1PK` = `"TYPE#{activity_type}"` |
| SK | `GSI1SK` = `created_at` (N) |

Used by `list_entity_activities` when filtering by `activity_type`. Because DynamoDB applies `FilterExpression` after reading up to 1 MB (CLAUDE.md gotcha), the `ByType` GSI avoids full-partition scans when the caller wants only calls or only notes for a high-volume entity.

## 4. API / Service Design

### 4.1 Service: `app/services/crm_activity_timeline.py`

```python
from __future__ import annotations

import logging
import uuid
from typing import Any, Dict, List, Optional

from boto3.dynamodb.conditions import Attr, Key

from app.core.settings import S
from app.core.tables import T
from app.core.time import now_ts
from app.core.cursor import decode_cursor, encode_cursor

logger = logging.getLogger(__name__)

_INVERTED_TS_MAX = 9_999_999_999_999


def _guard() -> bool:
    """Return True when the timeline feature is active; no-op otherwise."""
    return S.crm_activities_enabled and S.crm_activity_timeline_enabled


def _make_sk(created_at: int, activity_type: str, activity_id: str) -> str:
    inverted = _INVERTED_TS_MAX - created_at
    return f"{inverted:013d}#{activity_type}#{activity_id}"


def _item_to_out(item: Dict[str, Any]) -> Dict[str, Any]:
    return {
        "activity_id": item["activity_id"],
        "entity_type": item["entity_type"],
        "entity_id": item["entity_id"],
        "activity_type": item["activity_type"],
        "user_sub": item["user_sub"],
        "summary": item.get("summary", ""),
        "metadata": item.get("metadata") or {},
        "created_at": int(item["created_at"]),
    }


def record_crm_activity(
    entity_type: str,
    entity_id: str,
    activity_type: str,
    activity_id: str,
    user_sub: str,
    *,
    summary: str = "",
    metadata: Optional[Dict[str, Any]] = None,
) -> Optional[Dict[str, Any]]:
    """Write one timeline row. Returns the stored item or None when flag is off."""
    if not _guard():
        return None
    ts = now_ts()
    entity_key = f"{entity_type}#{entity_id}"
    sk = _make_sk(ts, activity_type, activity_id)
    item: Dict[str, Any] = {
        "entity_key": entity_key,
        "sk": sk,
        "entity_type": entity_type,
        "entity_id": entity_id,
        "activity_type": activity_type,
        "activity_id": activity_id,
        "user_sub": user_sub,
        "summary": summary[:200],
        "metadata": metadata or {},
        "created_at": ts,
        "GSI1PK": f"TYPE#{activity_type}",
        "GSI1SK": ts,
    }
    T.crm_activity_timeline.put_item(Item=item)
    logger.debug(
        "crm_activity_timeline: recorded entity=%s type=%s id=%s",
        entity_key, activity_type, activity_id,
    )
    return item


def list_entity_activities(
    entity_type: str,
    entity_id: str,
    *,
    activity_type: Optional[str] = None,
    cursor: Optional[str] = None,
    limit: int = 20,
) -> Dict[str, Any]:
    """Return paginated timeline for one CRM entity, newest-first."""
    if not _guard():
        return {"items": [], "next_cursor": None, "total_hint": 0}

    entity_key = f"{entity_type}#{entity_id}"
    limit = max(1, min(limit, 100))
    kwargs: Dict[str, Any] = {
        "KeyConditionExpression": Key("entity_key").eq(entity_key),
        "ScanIndexForward": True,   # SK is already inverted, so ascending = newest first
        "Limit": limit,
    }
    if activity_type:
        kwargs["FilterExpression"] = Attr("activity_type").eq(activity_type)
        # Use ByType GSI when filtering by type to avoid full-partition reads
        kwargs = {
            "IndexName": "ByType",
            "KeyConditionExpression": (
                Key("GSI1PK").eq(f"TYPE#{activity_type}")
            ),
            "FilterExpression": Attr("entity_key").eq(entity_key),
            "ScanIndexForward": False,  # GSI1SK = created_at; descending = newest first
            "Limit": limit,
        }

    eks = decode_cursor(cursor)
    if eks:
        kwargs["ExclusiveStartKey"] = eks

    # Loop to handle sparse FilterExpression pages (CLAUDE.md gotcha)
    collected: List[Dict[str, Any]] = []
    last_key = None
    max_pages = 5

    for _ in range(max_pages):
        resp = T.crm_activity_timeline.query(**kwargs)
        collected.extend(resp.get("Items", []))
        last_key = resp.get("LastEvaluatedKey")
        if len(collected) >= limit or not last_key:
            break
        kwargs["ExclusiveStartKey"] = last_key

    items = collected[:limit]
    next_cursor = encode_cursor(last_key) if last_key and len(collected) >= limit else None
    total_hint = len(items) if not last_key else None

    return {
        "items": [_item_to_out(i) for i in items],
        "next_cursor": next_cursor,
        "total_hint": total_hint,
    }


def delete_entity_activity(
    entity_type: str,
    entity_id: str,
    sk: str,
) -> bool:
    """Hard-delete a single timeline row. Returns True if the row existed."""
    if not _guard():
        return False
    entity_key = f"{entity_type}#{entity_id}"
    resp = T.crm_activity_timeline.delete_item(
        Key={"entity_key": entity_key, "sk": sk},
        ReturnValues="ALL_OLD",
    )
    return bool(resp.get("Attributes"))
```

## 5. Detailed Behavior & Edge Cases

### 5.1 `record_crm_activity` idempotency

`put_item` is not conditional; a second call with the same `(entity_type, entity_id, activity_type, activity_id)` at a different wall-clock timestamp produces a **different SK** (because `now_ts()` changes) and thus a **second timeline row**. Callers that retry on transient failures may write duplicate rows.

To prevent this, callers should wrap `record_crm_activity` in a `try/except` with no retry (best-effort fire-and-forget, per `CRM_ACTIVITIES_TICKETS.md:526`). A conditional `attribute_not_exists(entity_key)` write is intentionally not used because the SK already encodes the timestamp, making exact-SK collisions practically impossible. If a caller writes the same logical event twice (e.g., a retried task completion), the timeline will show two entries a few seconds apart. This is acceptable: the timeline is an activity log, not a state machine.

### 5.2 Filtering by `activity_type` — GSI vs. FilterExpression trade-off

When `activity_type` is supplied, the service switches to the `ByType` GSI (`GSI1PK = "TYPE#{activity_type}"`). This is more efficient for high-volume entities but returns results across **all entities** for that type unless `FilterExpression` narrows to the specific `entity_key`. The `FilterExpression` does not reduce DDB read cost but does reduce network payload. For entities with many activities of a single type, the multi-page loop (capped at 5 pages) ensures completeness despite DynamoDB's 1 MB page limit (CLAUDE.md: "DDB FilterExpression doesn't reduce page size").

For unfiltered queries (all activity types), the service queries directly by PK (`entity_key`) without the GSI; the inverted-timestamp SK ensures newest-first ordering without `ScanIndexForward=False`.

### 5.3 Access control — current boundary

The ticket source (`CRM_ACTIVITIES_TICKETS.md:516`) states: "user must own or be assigned at least one activity row for the entity (no additional party-level auth at this ticket's boundary — full record-level ACL deferred to the Security Suite area)."

Concretely: the `require_ui_session` dependency authenticates the user. No ownership check is enforced at the entity level in ACT-009 — any authenticated user who knows the `entity_type` and `entity_id` can read the timeline. Full entity-level ACL is a PTY-area concern and will be added once PTY-011 ships.

Security implication: the `entity_id` is an opaque string. Before PTY ships, valid entity IDs are not discoverable via public enumeration (no `GET /ui/crm/entities` list endpoint exists), so exposure is limited to users who already know the ID (typically obtained from a call log or task record they own).

### 5.4 `DELETE` authorization

Any authenticated user can currently call `DELETE /activities/{sk}`. Admin-only delete is deferred to the Security Suite area. For auditing purposes, every successful delete emits an `audit_event("crm_activity_deleted", ...)` to `T.alerts` (via `alerts.py:644`), so removals are traceable in the audit log.

### 5.5 Unknown `entity_type` values

`_VALID_ENTITY_TYPES = {"contact", "lead", "account", "opportunity"}` is enforced at the router level (422). The service layer does not validate `entity_type` to allow internal callers (e.g., a future `deal` type) to write rows without router-level constraints. Router validation is the public API contract; service-level validation would be duplicated and more fragile.

### 5.6 `summary` truncation

`record_crm_activity` truncates `summary` to 200 characters at write time (`summary[:200]`). Callers that pass longer strings are silently truncated; no error is raised. This matches the `send_alert_email` body truncation pattern at `alerts.py:477` (`body_text[:8000]`).

### 5.7 `metadata` constraints

`metadata` is stored as a DynamoDB `Map` attribute. It must contain only JSON-serialisable values; the `_FloatSafeTable` proxy converts `float` to `Decimal` automatically. Callers must not pass nested structures deeper than 5 levels (DynamoDB map depth limit) or total items exceeding 400 KB (single-item limit). These constraints are not validated at the Python level but are documented for callers.

### 5.8 Pagination cursor validity

Cursors are HMAC-signed (`app/core/cursor.py:94–101`). An invalid or tampered cursor causes `decode_cursor` to return `None`, which is interpreted as "start from the beginning" — no error is raised. This matches the behavior in `app/services/activity_feed.py:118`. <!-- CORRECTED: decode_cursor is called at line 118, not 119 -->

### 5.9 Flag-off no-op behavior

When `S.crm_activities_enabled` is `False` or `S.crm_activity_timeline_enabled` is `False`:

- `record_crm_activity` returns `None` immediately (no DDB write, no import of `T.crm_activity_timeline`).
- `list_entity_activities` returns `{"items": [], "next_cursor": None, "total_hint": 0}`.
- `delete_entity_activity` returns `False`.
- Router endpoints all raise `HTTPException(404)` via `_gate()`.

The `T.crm_activity_timeline` table handle is still resolved at import time (frozen `Tables` dataclass), but the underlying DynamoDB table does not need to exist when the flag is off — the handles are never called.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 compliance

ACT-009 contains **no `dev_mode` branch**. `record_crm_activity`, `list_entity_activities`, and `delete_entity_activity` all use `T.crm_activity_timeline` directly. In dev, this resolves to the DynamoDB Local instance (port 8001) via the `DDB_ENDPOINT_URL=http://localhost:8001` env var; in prod it resolves to real DynamoDB. The code path is identical. There is no `S.dev_mode` conditional anywhere in the service or router.

This mirrors the audit export approach documented in CLAUDE.md ("Dev/prod parity: both paths run against moto in-process S3 in dev with `DEV_MODE=0`").

### 7.2 Idempotency

`record_crm_activity` is not idempotent for the same logical event called twice (see §5.1). Callers are responsible for best-effort fire-and-forget (no retry). The `list_entity_activities` and `delete_entity_activity` functions are idempotent: re-listing returns the same result set (cursor-consistent), and re-deleting an already-deleted SK returns `False` (no error).

### 7.3 Security: no money-out

ACT-009 has no payment operations. There is nothing to route through `refund_payment` or `settle_or_reverse_ledger`.

### 7.4 Security: input validation

- `entity_type` is validated against `_VALID_ENTITY_TYPES` at the router layer (§5.5); unknown values return 422.
- `activity_type` query parameter is validated against `_VALID_ACTIVITY_TYPES` at the router layer; unknown values return 422.
- `summary` is truncated at 200 characters at the service layer.
- `sk` path parameter in the DELETE endpoint is used directly as a DynamoDB key value; it is not parsed or executed. Injection is not possible via DynamoDB `Key=` lookups.
- `cursor` is HMAC-verified; tampered cursors silently fall back to the start of the result set.

### 7.5 Security: no KMS or S3

ACT-009 stores only structured metadata strings in DynamoDB. No file content, no cryptographic secrets. `app/core/crypto.kms_encrypt` / `kms_decrypt` are not used.

### 7.6 Audit trail

Deletes are logged via `audit_event("crm_activity_deleted", user_sub, ...)` to `T.alerts` (`alerts.py:644`). Write operations (`record_crm_activity`) are logged at `DEBUG` level only; they are not individually audited because they are called as fire-and-forget from other services that already audit their own primary operations.

## 8. Backward Compatibility & Migration

### 8.1 Existing tables and routes unchanged

ACT-009 introduces one new service file, one new router file, two new Pydantic models, one router registration in `main.py`, and zero changes to any existing file (other than `main.py`'s router include and the `app/models.py` model append). Existing endpoints, services, and DDB tables are untouched.

### 8.2 No data migration

The `crm_activity_timeline` table starts empty. There is no historical call, task, or note data to backfill because the ACT-006/ACT-008/ACT-010 callers only start writing rows once their own features are enabled. No backfill script is required.

### 8.3 Additive model fields

`CrmActivityOut` and `CrmActivityTimelineOut` are new types added to `app/models.py`. They do not alter any existing model. No `model_rebuild()` call is needed.

### 8.4 `total_hint` is advisory

Clients must treat `total_hint` as informational. When pagination is in progress (`next_cursor` is non-null), `total_hint` is `None`. Clients must not rely on it for accurate counts.
