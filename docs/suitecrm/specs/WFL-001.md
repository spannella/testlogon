# WFL-001 — Feature flag, settings & DynamoDB scaffolding

**Type:** Chore | **Priority:** P0 | **Estimate:** 1d | **Blocks:** WFL-002 through WFL-009

---

## 1. Summary & Goal

Introduce the `CRM_WORKFLOW_ENABLED` feature flag, seven new `Settings` fields, two new
DynamoDB tables (`crm_workflow_rules`, `crm_workflow_runs`), and two new table handles in
`T` — providing the exclusive scaffolding required by every subsequent WFL ticket. When
the flag is off (the default), the platform is byte-for-byte identical to the current
state: no routes are registered, no background loops start, and existing service files are
untouched.

This ticket has no user-visible behaviour. It only lays the infrastructure foundation so
that WFL-002 through WFL-009 can be merged in any order, always against a stable, tested
foundation.

## 3. Data Model

### 3.1 `crm_workflow_rules` table

Stores rule definitions and their enabled/disabled state.

**Primary key:**

| Attribute | Type | Role |
|---|---|---|
| `pk` | S | Hash key — value: `RULE#{rule_id}` |
| `sk` | S | Range key — value: `META` for the rule META row; `DRIP#{sequence_id}` for drip sequence rows (WFL-008 single-table reuse) |

**META item fields** (written at rule creation, patched on update):

| Field | Type | Notes |
|---|---|---|
| `rule_id` | S | UUID hex, generated at creation |
| `name` | S | Human-readable label |
| `description` | S | Optional free text |
| `target_module` | S | `ticket`, `contact`, `order`, `subscription`, `lead` |
| `trigger_type` | S | `on_save`, `on_schedule`, `on_time_elapsed` |
| `trigger_config` | M (map) | See WFL-002 for sub-fields per trigger type |
| `conditions` | L (list) | Each: `{field, operator, value}` |
| `actions` | L (list) | Each: `{action_type, config}` |
| `enabled` | BOOL | Default `true` at creation |
| `created_by` | S | `user_sub` of creating admin |
| `created_at` | N | Unix timestamp integer |
| `updated_at` | N | Unix timestamp integer |
| `next_run_at` | N | (optional) For `on_schedule` rules: next due epoch; written by WFL-005 |

**GSI — `ByModule`:**

| Attribute | Type | Purpose |
|---|---|---|
| `GSI_MODULE_PK` | S | `MODULE#{target_module}` |
| `GSI_MODULE_SK` | N | `created_at` — enables newest-first listing per module |

`attr_types` required: `{"GSI_MODULE_SK": "N"}` — omitting this causes `ValidationException` at `ScanIndexForward=False` query time (CLAUDE.md gotcha confirmed by `scheduled_actions` at `scripts/local-ddb-init.py:1327`).

### 3.2 `crm_workflow_runs` table

Append-only execution log. Every rule evaluation that produces an outcome (matched,
skipped, or error) writes one run row. This table is write-heavy and read occasionally
(admin run-history view in WFL-009).

**Primary key:**

| Attribute | Type | Role |
|---|---|---|
| `pk` | S | `RULE#{rule_id}` |
| `sk` | S | `RUN#{started_at:010d}#{run_id}` — zero-padded epoch enables time-ordered range scan without GSI |

**Item fields:**

| Field | Type | Notes |
|---|---|---|
| `run_id` | S | UUID hex |
| `rule_id` | S | Denormalized for convenience |
| `target_module` | S | Module that was evaluated |
| `record_id` | S | PK of the evaluated record |
| `trigger_type` | S | `on_save`, `on_schedule`, `on_time_elapsed` |
| `outcome` | S | `matched`, `skipped`, `error` |
| `actions_fired` | L | `[{action_type, result}]` |
| `started_at` | N | Unix epoch integer |
| `finished_at` | N | Unix epoch integer |
| `error_message` | S | Set only when `outcome=error` |

**GSI — `ByRecord`:**

| Attribute | Type | Purpose |
|---|---|---|
| `GSI_RECORD_PK` | S | `{target_module}#{record_id}` |
| `GSI_RECORD_SK` | N | `started_at` — per-record run history newest-first |

`attr_types` required: `{"GSI_RECORD_SK": "N"}`.

### 3.3 Single-table reuse note

`crm_workflow_rules` serves double duty for WFL-008 drip sequence definitions: rows with
`pk=DRIP#{sequence_id}`, `sk=META` (sequence metadata) and `pk=ENROL#{sequence_id}`,
`sk=RECORD#{module}#{record_id}` (enrolment state) live in the same table. No schema
change is needed — the `pk`/`sk` key space is already partitioned by the prefix. This
mirrors the single-table pattern used by `AuditExports` (which stores both export jobs
and schedules) at `scripts/local-ddb-init.py:1491–1503`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off behavior (default state)

With `CRM_WORKFLOW_ENABLED=0` (the default):

- `S.crm_workflow_enabled` evaluates to `False`.
- No WFL routes exist at all (they are registered conditionally in WFL-009).
- `T.crm_workflow_rules` and `T.crm_workflow_runs` are valid table handles pointing to
  DynamoDB tables that exist but receive no reads or writes from application code.
- The tables are created by `scripts/local-ddb-init.py` regardless of the flag (DDB
  init always creates all declared tables; flag-gating is an application-layer concern).

### 5.2 Flag-on behavior

With `CRM_WORKFLOW_ENABLED=1`:

- `S.crm_workflow_enabled` evaluates to `True`.
- Subsequent WFL tickets guard their logic with `if not S.crm_workflow_enabled: ...`.
- No behaviour change in WFL-001 itself — only future tickets observe the flag.

### 5.3 Table creation idempotency

`_ensure_table` in `scripts/local-ddb-init.py` wraps table creation in
`_retry_transient_ddb_call` and catches `ResourceInUseException` silently (table already
exists). Running `just up` or `just restart` multiple times is safe.

### 5.4 Table-name override

`CRM_WORKFLOW_RULES_TABLE_NAME` and `CRM_WORKFLOW_RUNS_TABLE_NAME` allow renaming tables
in multi-tenant or blue/green deployments. `_resolve_table_name(S.crm_workflow_rules_table_name, "crm_workflow_rules")` honors this override the same way all other tables do.

### 5.5 `_FloatSafeTable` write coercion

`T.crm_workflow_rules` and `T.crm_workflow_runs` go through `_FloatSafeTable`, which
recursively converts Python `float` to `Decimal` before any `put_item` or `update_item`
call. This guarantees that numeric timestamps written as `int(time.time())` (from
`now_ts()`) never trigger boto3's float rejection. WFL-002+ service code need not wrap
timestamps explicitly.

### 5.6 Numeric GSI sort key declaration

`GSI_MODULE_SK` and `GSI_RECORD_SK` must appear in `attr_types` as `"N"`. DynamoDB Local
creates attribute definitions at table-creation time; if declared as String (the default
when omitted), integer query values produce `ValidationException: Type mismatch for key
GSI_MODULE_SK expected: S actual: N`. This is confirmed by the identical pattern at
`scripts/local-ddb-init.py:1327` (`scheduled_actions` ByDue GSI).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

No `if S.dev_mode` branches exist or will be introduced by this ticket. The two DynamoDB
tables use the same `TableDef` pattern as every other table; in dev they are created in
DynamoDB Local (port 8001); in prod they are created via `UpdateTable`/`CreateTable` on
the real AWS DynamoDB endpoint. The application code is identical in both environments
(`DDB_ENDPOINT_URL` routing is handled by `app/core/aws.py` transparently).

### 7.2 Idempotency

`_ensure_table` is idempotent by construction — it catches `ResourceInUseException`.
`just restart` can be run any number of times without error.

`S` is a frozen dataclass (`@dataclass(frozen=True)`, `app/core/settings.py:6`); new
fields added to it are also frozen. The `T` singleton is likewise frozen. Tests patch
handles via `object.__setattr__` on frozen instances (canonical pattern:
`tests/test_gap_0220_0221_ssh_stored_key.py:108`).

### 7.3 Security

WFL-001 introduces no auth-guarded endpoints, no PII processing, and no credential
exposure. The table handles are server-side only. There are no secrets referenced.

Admin access to the tables (via WFL-009 endpoints) will require
`Depends(require_admin_or_root_csrf)` — enforced in that ticket, not here.

### 7.4 Table-handle initialization ordering

`T` is constructed at module import time in `app/core/tables.py`. The `_safe_table()`
calls resolve table handles lazily via boto3 `ddb.Table(name)` (the Table object is a
client stub; no network call happens until the first DDB operation). If the tables do not
yet exist at startup (e.g., first run before `local-ddb-init.py`), the handles are still
valid Python objects — operations on them will fail at DDB call time, not at import.

## 8. Backward Compatibility & Migration

### 8.1 Existing tests

No existing service file is modified. `just test` must remain green. The additions are:

1. Seven new fields on `Settings` — existing code that references `S` is unaffected.
2. Two new fields on `Tables` — existing code that accesses `T` is unaffected (frozen
   dataclass fields are additive).
3. Two new `TableDef` entries in `_table_defs()` — `main()` creates tables
   alphabetically; order does not matter for correctness.

### 8.2 Prod migration

In production, the new tables must be created before deploying any WFL-002+ code. The
recommended approach is to run `scripts/local-ddb-init.py` (or its production
equivalent) in a pre-deploy migration step with `CRM_WORKFLOW_ENABLED=0` so that the
tables exist but no application code activates them.

The `GSI_MODULE_SK` and `GSI_RECORD_SK` numeric GSI sort key declarations require the
`AttributeDefinitions` to list those attribute names with `AttributeType: N`. DynamoDB
only validates these when a GSI is first created; updating an existing table to add a GSI
with the wrong type requires a table rebuild. The `TableDef` declares them correctly —
ensure this is the version that reaches prod before any data is written.

### 8.3 No data migration

Both tables start empty. There is no existing workflow-rule data to migrate.

## 10. Open Questions / Assumptions

1. **Table TTL**: The `crm_workflow_runs` table will accumulate one row per rule
   evaluation. Should a TTL (`ttl_epoch`) be declared now or deferred to WFL-006 when the
   writer is first implemented? Recommendation: defer TTL enablement to WFL-006 so it can
   be configured alongside `S.crm_workflow_runs_retention_days`. WFL-001 does not call
   `_enable_ttl_if_needed` for either table.

2. **GSI projection type**: The `TableDef` helper uses `KEYS_ONLY` or `ALL` projection
   depending on whether an explicit projection is passed. The ticket spec does not specify
   projection for `ByModule` or `ByRecord`. Recommendation: use `ALL` (the default) so
   that WFL-002 `list_rules_for_module` and WFL-009 run-history queries can project all
   fields from the GSI without a second `get_item` round-trip. This is consistent with
   how `ByModule`/`ByType` on `scheduled_actions` works.

3. **`crm_workflow_rules` for drip sequences (WFL-008)**: The single-table reuse
   (`DRIP#` and `ENROL#` PK prefixes) assumes no additional GSIs are needed on those
   row types beyond the primary key. If WFL-008 requires listing all sequences or all
   active enrolments, an additional GSI may need to be backfilled — a prod
   `UpdateTable` operation. This is accepted risk for the MVP; the spec calls it out as
   a future concern.

4. **`crm_workflow_max_rules_per_module`**: The limit is checked at rule-creation time
   by WFL-002. It requires a `count` query on the `ByModule` GSI before writing. This
   query is per-module, not global, so it is cheap. Assumption: the limit is per-module
   (50 rules per target module), not per-tenant.

### 11.3 Sibling CRM ticket families (extend, do not duplicate)

The WFL series sits alongside several other CRM ticket families already partially
specified in `docs/suitecrm/specs/`:

- **CAS-001..CAS-017** (Cases/Tickets) — `app/services/tickets.py` `TicketStore` is the
  primary record target for `module="ticket"` rules in WFL-004 and WFL-006.
- **ACT-001..ACT-010** (Activities/Tasks) — Activity feed (`app/services/activity_feed.py`,
  `T.activity_feed`) is a candidate emission point for `crm_workflow.create_record`
  actions; WFL-006 should emit activity entries when creating ticket or contact records.
- **OPP-001..OPP-006** (Opportunities/Leads) — `module="lead"` and `module="order"` in
  the WFL target-module list depend on lead and order services defined in those tickets.
- **EML-001..EML-010** (Email) — WFL-007's `send_email` action reuses
  `T.admin_messaging_templates` (`app/services/notification_templates.py`), which is
  specified by EML. New template IDs created by EML are immediately usable in WFL-007
  rules without any WFL change.
- **PRJ-001..PRJ-012** (Projects) — Not a target module in the initial WFL set, but
  `app/services/projects_store.py` follows the same DDB key conventions; adding
  `module="project"` in a future WFL-002 patch would be straightforward.

### 11.4 PTY / MKT / PRD / OFB cross-references

- **PTY (PARTY_CRM)**: Contact and account data models defined there are the schema
  source for `module="contact"` field names referenced in WFL-003 conditions and
  WFL-006 `modify_field`.
- **MKT (MARKETING_CAMPAIGNS)**: The `drip_sequence` action in WFL-008 generalises the
  cart-abandonment pattern from `app/services/cart_reminders.py`. If MKT introduces
  campaign-specific drip sequences, they should reuse the WFL-008 `DRIP#` row type in
  `T.crm_workflow_rules` rather than forking another stage-config table.
- **PRD (CATALOG_DEPTH)**: `module="order"` in WFL-004 on-save hooks depends on the
  order service from PRD/OFB. Until those tickets are merged, order-module rules can be
  defined but the on-save hook has no wiring point; WFL-004 documents this as a
  deferred integration.
- **OFB (OFBIZ_COMMERCE)**: Same as PRD; the `T.orders` handle already exists
  (`app/core/tables.py:381`) and the order service is partially implemented, making
  order-module wiring feasible in WFL-004.
