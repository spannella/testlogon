# KB-005 — Article ratings (helpful / not helpful aggregate)

**Type:** Feature  **Priority:** P2  **Estimate:** 1 day  
**Ticket source:** `docs/suitecrm/CRM_KNOWLEDGE_BASE_TICKETS.md`, section "KB-005"

---

## 1. Summary & Goal

KB-005 completes the article rating contract that CAS-015 left as a stub. The goal is to allow any authenticated user to mark a published KB article as **helpful** or **not helpful**, persist a per-user rating record so the same user cannot double-vote, and maintain atomic aggregate counters (`helpful_count`, `not_helpful_count`) on the article's META row. Vote-changing (flipping from helpful to not-helpful or vice versa) must also be handled correctly: the old counter is decremented and the new counter is incremented in the same DynamoDB update, and the rating row is replaced.

Concrete deliverables:

1. A `RATING#{user_sub}` sub-item stored under the article's partition key in `crm_kb_articles`, enabling per-user deduplication.
2. `KbArticleService.rate_article(article_id, user_sub, helpful)` rewritten to read the existing rating row, branch on first-vote / same-vote / vote-change, issue the correct atomic `ADD` expression(s), and return current aggregate counts.
3. `POST /kb/articles/{article_id}/rate` endpoint in `app/routers/kb_articles.py` wired to `require_ui_session`.
4. Two Pydantic models — `KbRateReq` and `KbRateOut` — added to `app/models.py`.
5. An `audit_event("kb.article.rated", ...)` emitted on every successful new vote or vote change.

With `KNOWLEDGE_BASE_ENABLED=0` (the default), the endpoint returns 404 and the service is never invoked. The platform is byte-for-byte identical to its pre-KB-005 state when the flag is off.

## 2. Context & Current State

### 2.1 CAS-015 rating stub

CAS-015 (`docs/suitecrm/specs/CAS-015.md`, §4.1) defines `KbArticleService.rate_article` with this docstring:

```
ADD helpful_count :one or not_helpful_count :one.
Idempotency: a per-user rating row at pk="RATE#{article_id}", sk="USER#{user_sub}"
with attribute_not_exists guard prevents double-voting. Returns updated counts.
```

The CAS-015 spec further states in §5.5 that a second vote by the same user raises 409 `already_rated`, and that changing a vote is **not supported** in that version. KB-005 supersedes this stub: the 409-on-repeat behaviour is replaced with idempotent return of current counts, and vote-changing is fully supported.

### 2.2 Atomic ADD pattern

`app/services/stories.py:156–164` shows the canonical `ADD view_count :one` update expression:

```python
tbl.update_item(
    Key={"pk": f"STORY#{story_id}", "sk": "META"},
    UpdateExpression="ADD view_count :one",
    ExpressionAttributeValues={":one": 1},
)
```

KB-005 extends this pattern to issue a single `update_item` call that can apply up to two `ADD` clauses in one expression when a vote is being changed (e.g. `"ADD helpful_count :neg, not_helpful_count :pos"`), avoiding race conditions that would exist if two separate update calls were issued.

`app/services/social.py:552–575` demonstrates `ADD <field> :neg_one` with a clamp-at-zero `ConditionalCheckFailedException` guard. KB-005 borrows the same negative-delta technique. The clamp guard is applied so that a decrement never pushes a counter below zero (which could happen if, for example, the rating row exists but the article's counter was reset by an admin).

### 2.3 Per-user deduplication row layout

CAS-015 §5.5 specifies the rating row as:

```
pk="RATE#{article_id}"  sk="USER#{user_sub}"  helpful=<bool>  created_at=<ts>
```

KB-005 inherits this layout and adds one field: `updated_at` (integer Unix timestamp) set on every vote change to track when the flip occurred. The `helpful` field stores the **current** vote direction after any update.

### 2.4 Article META counters

CAS-015 §3.1 specifies `helpful_count: N` and `not_helpful_count: N` fields on the article META item (`PK=ARTICLE#{article_id}`, `SK=META`) in `crm_kb_articles`. Both fields are initialized to `0` by `create_article`. These are the counters that KB-005 maintains atomically. The `crm_kb_articles` table is declared by CAS-001 in `scripts/local-ddb-init.py`; no new table, GSI, or schema change is introduced by KB-005.

### 2.5 `require_ui_session` dependency

`app/services/sessions.py:330` defines `require_ui_session` as an async FastAPI dependency. It returns a `dict` with at least `{"user_sub": str, "role": str, ...}`. The `user_sub` value from this dict is what KB-005 uses as the voter identity for rating rows. Unauthenticated requests are rejected with HTTP 401 before the handler body runs.

### 2.6 `audit_event` primitive

`app/services/alerts.py:644` defines `audit_event(event: str, user_sub: str, request=None, **fields)`. It writes a row to `T.alerts` and publishes an SSE alert — same code path in dev and prod (`S.dev_mode` does not alter this path). KB-005 calls it for every successful first vote or vote change but not for idempotent repeat-same-vote calls.

### 2.7 Flag gating pattern

KB-001 (`docs/suitecrm/specs/KB-001.md`, §2.1) establishes the top-level flag `S.knowledge_base_enabled`. The helper `_require_kb_enabled()` (defined in `app/routers/kb_articles.py` by KB-001/CAS-015) raises `HTTPException(404)` when the flag is off. KB-005 reuses this helper at the top of the `rate` endpoint with no modification.

### 2.8 Existing `KbArticleOut` model

CAS-015 §4.3 defines `KbArticleOut` with `helpful_count: int = 0` and `not_helpful_count: int = 0`. The `KbRateOut` response model introduced by KB-005 echoes these two counters alongside `ok` and `already_rated` so the client can update its local state without a separate article GET.

## 3. Data Model

### 3.1 No new DynamoDB table

KB-005 writes exclusively to the existing `crm_kb_articles` table (CAS-001). No new table, new GSI, or change to `scripts/local-ddb-init.py` is required. The rating rows are sub-items on the same partition as the article META row.

### 3.2 Rating sub-item

```
Table:   crm_kb_articles
PK:      ARTICLE#{article_id}
SK:      RATING#{user_sub}
```

| Field | DDB Type | Notes |
|-------|----------|-------|
| `pk` | S | `ARTICLE#{article_id}` — matches article META partition |
| `sk` | S | `RATING#{user_sub}` — one row per user per article |
| `article_id` | S | Denormalized for convenience |
| `user_sub` | S | Voter's identity, sourced from `require_ui_session` |
| `helpful` | BOOL | Current vote direction (`True` = helpful, `False` = not helpful) |
| `rated_at` | N | Unix int via `now_ts()` — set on first vote |
| `updated_at` | N | Unix int — set on vote change; absent (not written) on first vote |

No GSI is needed. The only query pattern is a point-lookup `get_item(PK, SK)` to check whether the user has already voted. The `PK=ARTICLE#{article_id}` partition already holds the META row and any `ATTACHMENT#`, `VIEW#`, and `RELATED#` rows added by sibling tickets; rating rows co-exist on the same partition without conflict because DynamoDB partitions are addressed by full `(PK, SK)` primary key.

### 3.3 Article META counter fields (pre-existing, CAS-001)

`helpful_count` and `not_helpful_count` are numeric (`N`) fields already present on the article META item from CAS-015. They are maintained by `ADD` update expressions. No attribute-type change or GSI projection is needed. Because these fields are not sort keys on any GSI, no `attr_types` entry is required (they are not declared as primary or sort key attributes; DynamoDB infers their type from write values).

### 3.4 `scripts/local-ddb-init.py` — no change

The `crm_kb_articles` `TableDef` already carries `attr_types={"published_at": "N", "created_at": "N"}` from KB-001. The new `rated_at` and `updated_at` fields on rating rows are not index keys, so no `attr_types` addition is needed and `scripts/local-ddb-init.py` is not touched by KB-005.

## 4. API / Service Design

### 4.1 Service method: `KbArticleService.rate_article`

Location: `app/services/kb_articles.py` (introduced by CAS-015; KB-005 replaces the stub body).

```python
def rate_article(
    self,
    article_id: str,
    user_sub: str,
    helpful: bool,
) -> dict[str, Any]:
    """
    Rate an article helpful or not-helpful.

    Returns:
        {
            "ok": True,
            "helpful_count": int,
            "not_helpful_count": int,
            "already_rated": bool,   # True when same-direction repeat vote
            "changed": bool,         # True when vote direction was flipped
        }

    Raises:
        KbArticleNotFoundError  — article does not exist or is not published
    """
```

**Algorithm (step-by-step):**

Step 1 — Verify the article exists and is published:

```python
article = self.get_article(article_id)
if article is None or article.get("status") != "published":
    raise KbArticleNotFoundError(article_id)
```

Ratings are only accepted on published articles. Admins wishing to test ratings on drafts must publish first.

Step 2 — Read existing rating row (point lookup, no scan):

```python
rating_key = {
    "pk": f"ARTICLE#{article_id}",
    "sk": f"RATING#{user_sub}",
}
existing = self._table.get_item(Key=rating_key).get("Item")
```

Step 3 — Branch on vote state:

**Branch A — No prior vote (first-time vote):**

```python
# Write rating row
self._table.put_item(Item={
    **rating_key,
    "article_id": article_id,
    "user_sub": user_sub,
    "helpful": helpful,
    "rated_at": now_ts(),
})

# Atomic ADD on the article META row
count_field = "helpful_count" if helpful else "not_helpful_count"
result = self._table.update_item(
    Key={"pk": f"ARTICLE#{article_id}", "sk": "META"},
    UpdateExpression=f"ADD {count_field} :one",
    ExpressionAttributeValues={":one": 1},
    ReturnValues="ALL_NEW",
)
attrs = result["Attributes"]
audit_event("kb.article.rated", user_sub,
            article_id=article_id, helpful=helpful, action="new")
return {
    "ok": True,
    "helpful_count": int(attrs.get("helpful_count", 0)),
    "not_helpful_count": int(attrs.get("not_helpful_count", 0)),
    "already_rated": False,
    "changed": False,
}
```

**Branch B — Repeat vote, same direction (idempotent):**

```python
if existing.get("helpful") == helpful:
    # No DDB write. Return current counts from article META.
    article = self.get_article(article_id)  # fresh read for current counts
    return {
        "ok": True,
        "helpful_count": int(article.get("helpful_count", 0)),
        "not_helpful_count": int(article.get("not_helpful_count", 0)),
        "already_rated": True,
        "changed": False,
    }
```

No audit event is emitted for idempotent repeats. No DynamoDB write occurs.

**Branch C — Vote change (flip direction):**

```python
old_helpful = existing["helpful"]
old_field = "helpful_count" if old_helpful else "not_helpful_count"
new_field = "helpful_count" if helpful else "not_helpful_count"

# Decrement old counter (clamp at zero) then increment new counter
# in a single update_item to minimize race window.
try:
    result = self._table.update_item(
        Key={"pk": f"ARTICLE#{article_id}", "sk": "META"},
        UpdateExpression=f"ADD {old_field} :neg, {new_field} :pos",
        ConditionExpression=f"{old_field} > :zero",
        ExpressionAttributeValues={":neg": -1, ":pos": 1, ":zero": 0},
        ReturnValues="ALL_NEW",
    )
    attrs = result["Attributes"]
except ClientError as exc:
    if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
        # old counter is already 0; just increment new field
        result = self._table.update_item(
            Key={"pk": f"ARTICLE#{article_id}", "sk": "META"},
            UpdateExpression=f"ADD {new_field} :pos",
            ExpressionAttributeValues={":pos": 1},
            ReturnValues="ALL_NEW",
        )
        attrs = result["Attributes"]
    else:
        raise

# Replace rating row (overwrite with new direction)
ts = now_ts()
self._table.put_item(Item={
    **rating_key,
    "article_id": article_id,
    "user_sub": user_sub,
    "helpful": helpful,
    "rated_at": existing.get("rated_at", ts),
    "updated_at": ts,
})
audit_event("kb.article.rated", user_sub,
            article_id=article_id, helpful=helpful, action="changed",
            previous_helpful=old_helpful)
return {
    "ok": True,
    "helpful_count": int(attrs.get("helpful_count", 0)),
    "not_helpful_count": int(attrs.get("not_helpful_count", 0)),
    "already_rated": False,
    "changed": True,
}
```

The combined `ADD old_field :neg, new_field :pos` expression is a single atomic update, not two sequential updates, eliminating the window where counts would be temporarily inconsistent. The `ConditionalCheckFailedException` guard on `old_field > :zero` is borrowed directly from `app/services/social.py:557–575`.

### 4.2 Router endpoint

Location: `app/routers/kb_articles.py` (introduced by CAS-015/KB-001).

```python
@router.post("/kb/articles/{article_id}/rate")
async def rate_article(
    article_id: str,
    body: KbRateReq,
    session: dict = Depends(require_ui_session),
) -> KbRateOut:
    _require_kb_enabled()
    svc = KbArticleService()
    result = svc.rate_article(
        article_id=article_id,
        user_sub=session["user_sub"],
        helpful=body.helpful,
    )
    return KbRateOut(**result)
```

**Route placement:** This route is declared after the `/kb/articles/{article_id}/publish`, `/kb/articles/{article_id}/archive`, and `/kb/articles/{article_id}/related` routes (per the CAS-015 router layout). The segment `/rate` is a static suffix on a dynamic `{article_id}` prefix; FastAPI resolves this correctly because the full path is unique. The route does NOT appear under `/public/kb/` because authentication is required.

**Verb:** `POST` (not `PUT`) because a rating is an action/event, not a full resource replacement. Consistent with `POST /posts/{id}/tip` and `POST /posts/{id}/reactions` in `app/routers/newsfeed_posts.py`.

**Auth:** `Depends(require_ui_session)` — requires a valid `ui_session` cookie or Bearer token. Unauthenticated callers receive HTTP 401 before the handler body executes.

**CSRF:** Non-GET requests made via cookie auth require `x-csrf-token` header matching the session's stored `csrf_token` and the `ui_csrf` cookie value. This is enforced transparently by `require_ui_session` (`app/services/sessions.py:330`). Bearer-auth clients (e.g. API key callers) bypass CSRF.

## 5. Detailed Behavior & Edge Cases

### 5.1 Article must be published

`rate_article` rejects ratings on draft and archived articles with HTTP 404. This is a deliberate UX choice: publishing gating means users only encounter rating prompts on live articles. Admins cannot rate their own unpublished drafts via this endpoint (they can still observe counts through the admin article view).

### 5.2 Idempotent same-direction repeat

Calling `POST /kb/articles/{id}/rate` with `{"helpful": true}` twice in a row from the same session returns `{"ok": true, "already_rated": true, "changed": false}` on the second call, with unchanged aggregate counts. No DynamoDB write is performed on the second call. This allows the frontend to safely retry on network failure without inflating counters.

### 5.3 Vote change atomicity

Changing a vote from `helpful=true` to `helpful=false` issues a single `update_item` call with `UpdateExpression="ADD helpful_count :neg, not_helpful_count :pos"`. This is atomic at the DDB level — an observer reading the article META row will never see a state where the decrement has applied but the increment has not (or vice versa). The `ConditionalCheckFailedException` fallback (§4.1 Branch C) handles the edge case where `helpful_count` was already 0, applying only the increment.

### 5.4 Rating row replacement on vote change

On a vote change, the existing `RATING#{user_sub}` row is overwritten via `put_item` (not `update_item`). The original `rated_at` value is preserved so the record shows when the article was first rated; `updated_at` records the flip timestamp. This provides a complete audit trail without a separate event log table.

### 5.5 Concurrent vote from same user

Two simultaneous `POST .../rate` requests from the same user for the same article (e.g. from two browser tabs) can both pass the `get_item` check (both see no existing row), and both attempt `put_item`. The second `put_item` overwrites the first without error. The `update_item` ADD calls both fire, potentially incrementing the counter twice. This is a known limitation at the DDB level without using a transaction. The impact is one extra count unit. Corrective options (DDB TransactWrite or an optimistic lock on the rating row) are tracked as an open question (§10.1). At expected KB rating volume, the probability of a true simultaneous double-vote from the same user is negligible.

### 5.6 Counter floor at zero

The `ConditionExpression={old_field} > :zero` in Branch C ensures a decrement never produces a negative counter. If the condition fails (counter is already 0 — possible if an admin manually reset counts or historical data is inconsistent), the service falls back to incrementing only the new counter, which leaves `old_field` at 0 rather than -1. The fallback path still writes the rating row and emits an audit event.

### 5.7 Non-existent article ID

`self.get_article(article_id)` queries DDB for `PK=ARTICLE#{article_id}`, `SK=META`. If the item is absent, `get_article` returns `None` and `rate_article` raises `KbArticleNotFoundError` (HTTP 404). The rating row is never written.

### 5.8 Deleted article ratings

When an article is deleted (hard delete by an admin), the `ARTICLE#{article_id}` partition is removed from DDB. Any `RATING#{user_sub}` rows in that partition are co-deleted if the admin uses DDB batch delete scoped to the partition, or they become orphaned if only the META row is removed. This is an admin-path concern; the rating endpoint never queries orphaned rows because the `get_article` check at Step 1 returns 404 before the rating lookup.

### 5.9 Rate-limit on the rating endpoint

`POST /kb/articles/{id}/rate` is an authenticated endpoint, so per-user abuse (spam voting across many articles) is possible. The existing `_bucket_limit` helper in `app/services/rate_limit.py` (pattern from GAP-0286 / `app/services/kyc_partner_api.py`) is applied per `user_sub`, category `"kb_rate"`, with a cap of `S.kb_rate_limit_per_hour` (default 60) requests per hour. The limit is fail-open: if the rate-limit table is unavailable, the request proceeds normally.

### 5.10 Response counts are from `ReturnValues="ALL_NEW"`

In Branch A and Branch C, `update_item` uses `ReturnValues="ALL_NEW"` to obtain the post-update counter values in the same round-trip, avoiding a separate `get_item` read. In Branch B (idempotent repeat), a fresh `get_article` read returns current counts. This means `KbRateOut.helpful_count` and `not_helpful_count` always reflect the state immediately after the operation, consistent with what the frontend needs to update its displayed totals without a separate refetch.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No `S.dev_mode` branch

`rate_article` issues standard DDB `get_item`, `put_item`, and `update_item` calls via `self._table` (which resolves to `T.kb_articles`, i.e. `T.crm_kb_articles`). In dev, this is DynamoDB Local at `http://localhost:8001`; in prod, it is real DynamoDB — same Python code path in both environments. No `if S.dev_mode` guard is introduced anywhere in KB-005. This satisfies SECOPS-007.

`audit_event` (`app/services/alerts.py:644`) writes to `T.alerts` in both dev and prod — also no `dev_mode` branch (confirmed at `app/services/alerts.py:644–695`).

The rate-limit helper `_bucket_limit` (`app/services/rate_limit.py`) uses DDB-backed token buckets in both environments. No mock path exists or is added.

### 7.2 Idempotency

| Scenario | Result | DDB writes |
|----------|--------|------------|
| First vote | `already_rated=false`, counter incremented | rating row written, META updated |
| Repeat same vote | `already_rated=true`, counts unchanged | none |
| Vote change | `changed=true`, counters updated atomically | rating row overwritten, META updated |
| Network retry of first vote after server-side success | Rating row already exists → Branch B, idempotent | none |
| Network retry of vote change after success | Rating row already reflects new direction → Branch B | none |

The "network retry of vote change" path is safe because after the first successful execution the rating row's `helpful` field equals the new direction; a retry reads this row and lands in Branch B.

### 7.3 Authentication and authorization

- **Authentication:** `Depends(require_ui_session)` at `app/services/sessions.py:330` enforces a valid cookie or Bearer session. HTTP 401 is returned before the handler body for unauthenticated requests.
- **Authorization:** Any authenticated user (role USER, ADMIN, or ROOT) may rate any published article. There is no role-based restriction on the rating action itself. Admins rating their own articles is permitted (no self-rating restriction) — this is consistent with the SuiteCRM behaviour the ticket models.
- **CSRF:** Cookie-authenticated POST requests must include `x-csrf-token` header matching `ui_csrf` cookie and session `csrf_token`. Bearer-authenticated requests skip CSRF (standard platform rule, CLAUDE.md).

### 7.4 Audit trail

`audit_event("kb.article.rated", user_sub, article_id=article_id, helpful=helpful, action=action)` is called:

- On first vote: `action="new"`
- On vote change: `action="changed"`, `previous_helpful=<old_bool>`
- Not on idempotent same-direction repeat (no state change)

The event string `"kb.article.rated"` must be present in `ALERT_EVENT_TYPES` in `app/services/alerts.py:134` (additive string-list append, no existing entries changed).

### 7.5 Input validation

`KbRateReq.helpful: bool` — Pydantic validates that the field is a boolean (`true`/`false` in JSON). A string value like `"yes"` results in HTTP 422. No other input fields exist on the request body.

`article_id` is a path parameter (string). The service validates existence via `get_article`; no additional format constraint is imposed at the router level beyond `str`.

### 7.6 No money movement

KB-005 involves no billing, no refunds, and no wallet operations. `refund_payment`, `settle_or_reverse_ledger`, and all billing service functions are untouched.

## 8. Backward Compatibility & Migration

### 8.1 CAS-015 stub replacement

CAS-015 defines `rate_article` as a stub that:
1. Issues a single `ADD helpful_count :one` or `ADD not_helpful_count :one` with no existing-vote check.
2. Returns 409 `already_rated` on second vote (via `attribute_not_exists` condition on the rating row, raising on failure).

KB-005 replaces this body entirely. The method signature `rate_article(self, article_id, *, helpful, user_sub)` is preserved. Callers of the method see improved behaviour (idempotent repeats, vote changes) with no signature break.

The router endpoint `POST /kb/articles/{article_id}/rate` defined by CAS-015 now returns `KbRateOut` (which adds `changed: bool` to the fields CAS-015 already specified in `RateArticleReq` / implied response). The new `changed` field is additive; existing API consumers that ignore unknown fields are unaffected.

### 8.2 `KbRateOut` vs CAS-015 stub response

CAS-015 §4.3 specifies the stub response as `{ok, helpful_count, not_helpful_count, already_rated}`. KB-005 adds `changed: bool` to this shape. This is a pure addition — no existing field is renamed, removed, or type-changed. API clients can safely ignore `changed` until they are updated to use it.

### 8.3 No table schema change

The `RATING#{user_sub}` sub-item schema was already specified by CAS-015 §5.5. KB-005 adds `updated_at` as an optional field written only on vote changes. DynamoDB's schemaless nature means rows without `updated_at` (written by the CAS-015 stub before KB-005 ships) are read without error: `existing.get("updated_at")` returns `None`, which is handled correctly by Branch B (same-direction idempotent check) and Branch C (vote change, which preserves the original `rated_at` and sets a fresh `updated_at`).

### 8.4 Existing `RATE#` rows from CAS-015 stub

If the CAS-015 stub deployed to an environment before KB-005 ships, rating rows with the old layout (no `updated_at`) exist. KB-005 reads them in `get_item` → Branch B or Branch C. Both branches handle missing `updated_at` gracefully. Counters on the article META may be slightly inaccurate if the CAS-015 stub had a defect (e.g. double-increments), but KB-005 does not attempt backfill — counter accuracy is best-effort and the impact is cosmetic.

### 8.5 `app/main.py` — no change

The KB router is already registered by CAS-015/KB-001. KB-005 adds a route to the existing router; no `app/main.py` modification is needed.

## 10. Open Questions / Assumptions

**10.1 Concurrent same-user double-vote (race condition):** Two simultaneous requests from the same session can both pass the `get_item` check before either writes the rating row, resulting in the counter being incremented twice. The fix is a DDB `TransactWrite` that atomically checks `attribute_not_exists(sk)` and writes both the rating row and the META counter update. This adds latency and cost. At expected KB rating volume, the probability is negligible, but it should be addressed before public launch. Tracked as a follow-up to KB-005.

**10.2 Admin counter reset / audit:** There is currently no admin endpoint to reset or adjust `helpful_count` / `not_helpful_count` (e.g. to correct data corrupted by the CAS-015 stub). If needed, this can be added as a low-priority follow-up (`PATCH /kb/admin/articles/{id}/rating-counts`). Until then, DynamoDB console access is the only correction path.

**10.3 Anonymous ratings:** The current design requires authentication. An operator may want to allow unauthenticated portal visitors to rate articles (like many public knowledge bases do). The challenge is preventing multiple votes per visitor without a login. A cookie-based single-vote pattern (write a `__kb_rated_{article_id}` browser cookie; no server-side per-visitor record) is the lightest-weight option but is trivially defeated. Deferred — requires a product decision on the trust model.

**10.4 Rating visibility in article responses:** `KbArticleOut` (CAS-015) already includes `helpful_count` and `not_helpful_count`. However, it does not expose whether the *current authenticated user* has already rated the article (and in which direction). A `my_rating: bool | null` field on `KbArticleOut` would allow the frontend to display the "You rated this helpful" state without a separate API call. Deferred to a follow-up patch.

**10.5 Assumption — CAS-015 is merged:** KB-005 assumes `KbArticleService`, `KbArticleNotFoundError`, `T.kb_articles`, and `S.knowledge_base_enabled` are already present from CAS-015 and KB-001. If those tickets are not yet merged, those symbols must be added inline in this PR.

**10.6 Assumption — `RATE#` SK prefix:** CAS-015 §5.5 specifies `sk="USER#{user_sub}"` under `pk="RATE#{article_id}"`. KB-005 adopts `pk="ARTICLE#{article_id}"`, `sk="RATING#{user_sub}"` (matching the KB-005 ticket source text at `CRM_KNOWLEDGE_BASE_TICKETS.md:204`). The prefix `RATING#` rather than `USER#` avoids collision with any future `USER#` sub-items on the article partition (e.g. a "view history" item). If CAS-015 already shipped with `sk="USER#{user_sub}"`, the service must be updated to use the `RATING#` prefix consistently, and existing `USER#` rows must be migrated or the service must handle both prefixes during a transition window.
