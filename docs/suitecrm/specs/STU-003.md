# STU-003 — ACL Role multi-role assignment & user-group propagation

**Type:** Feature  **Priority:** P1  **Estimate:** 2 days  
**Ticket source:** `docs/suitecrm/CRM_SECURITY_STUDIO_TICKETS.md`, section "STU-003"

---

## 1. Summary & Goal

STU-003 extends the ACL role assignment model introduced in STU-002 along two dimensions:

1. **Multi-role semantics**: A single user may hold N ACL roles simultaneously. Permission evaluation merges all assigned roles by union — if any role grants an action, the user has that action. STU-002 already stores one row per assignment (`ASSIGNMENT#{user_sub}` under a role partition), so the DynamoDB structure already supports multi-role; this ticket verifies the evaluation path correctly unions permissions across all rows returned by `get_roles_for_user` and adds explicit test coverage for the union semantics.

2. **User-group propagation**: Platform admin groups — the four `AdminScope` values defined in `app/auth/roles.py:14-19` (`AUTH_SUPPORT`, `BILLING_SUPPORT`, `CONTENT_MODERATION`, `CONTENT_MODERATION_SENIOR`) plus any named string group key — can be assigned an ACL role. All members of the group inherit that role automatically at permission-evaluation time without requiring individual ASSIGNMENT rows. This is implemented by a new `GROUP_ASSIGNMENT#{group_key}` row type on the same `crm_acl_roles` table established in STU-001, and by updating `check_permission` to call a new `get_effective_roles_for_user` function that unions direct and group-propagated assignments.

With `CRM_ACL_ENABLED=0` (the default), both functions degrade gracefully: `check_permission` returns `True` unconditionally, and the new router endpoints return 404.

## 3. Data Model

### 3.1 New row type on `crm_acl_roles` (no new table)

STU-003 adds a single new row type to the existing `crm_acl_roles` table (created by STU-001). No new DynamoDB table is needed.

**Group assignment row:**

| Attribute | Type | Value |
|-----------|------|-------|
| `pk` | S | `ROLE#{role_id}` |
| `sk` | S | `GROUP_ASSIGNMENT#{group_key}` |
| `group_key` | S | e.g. `auth_support`, `billing_support`, `content_moderation`, `content_moderation_senior`, or any custom string |
| `assigned_by_sub` | S | actor user_sub |
| `assigned_at` | N | Unix timestamp integer from `now_ts()` |

`group_key` is a plain string: either an `AdminScope` value or an arbitrary named group (for forward compatibility with PTY-series group constructs). The `by-assignee` GSI does NOT index group assignment rows (those rows use `sk = GROUP_ASSIGNMENT#...`, not `sk = ASSIGNMENT#...`) and are not projected through the existing GSI. Group assignments are queried directly by PK with an SK prefix condition.

### 3.2 No changes to `scripts/local-ddb-init.py`

The `crm_acl_roles` `TableDef` and its `by-assignee` GSI with `attr_types={"assigned_at":"N"}` are already declared in STU-001. No new tables or GSIs are required by STU-003.

### 3.3 No changes to `app/core/tables.py`

`T.crm_acl_roles` is already wired in STU-001.

### 3.4 Row lifecycle

- **Group assignment created**: `POST /{role_id}/group-assignments` → writes `GROUP_ASSIGNMENT#{group_key}` row via `put_item`.
- **Group assignment deleted**: `DELETE /{role_id}/group-assignments/{group_key}` → calls `delete_item(Key={"pk": f"ROLE#{role_id}", "sk": f"GROUP_ASSIGNMENT#{group_key}"})`.
- **Propagation is read-time only**: No fan-out writes to individual user assignment rows. Group membership is resolved at permission evaluation time by reading the caller's `AdminProfile.scopes` from the JWT and looking up matching `GROUP_ASSIGNMENT#` rows.

## 4. API / Service Design

### 4.1 Service changes to `app/services/crm_acl.py`

All functions below are additions or replacements within the `crm_acl.py` module introduced by STU-002.

#### 4.1.1 `assign_role_to_group`

```python
def assign_role_to_group(
    actor_sub: str,
    role_id: str,
    group_key: str,
) -> None:
    """
    Assign an ACL role to a platform group.

    Writes pk=ROLE#{role_id}, sk=GROUP_ASSIGNMENT#{group_key}.
    Emits audit_event("crm_acl_role.group_assigned", actor_sub, ...).
    Idempotent: put_item overwrites if the row already exists.
    """
```

- Validates `role_id` exists by reading the META row; raises `HTTPException(404)` if absent.
- Validates `group_key` is non-empty and contains only `[a-z0-9_]` characters (prevents SK injection).
- Writes the row with `assigned_at = now_ts()` (`app/core/time.now_ts`).
- Calls `audit_event("crm_acl_role.group_assigned", actor_sub, role_id=role_id, group_key=group_key)` (`app/services/alerts.py:644`).
- Calls `_invalidate_permission_cache()` (same module-level cache invalidation used by `assign_role_to_user`).

#### 4.1.2 `revoke_role_from_group`

```python
def revoke_role_from_group(
    actor_sub: str,
    role_id: str,
    group_key: str,
) -> None:
    """
    Revoke an ACL role from a platform group.

    Deletes pk=ROLE#{role_id}, sk=GROUP_ASSIGNMENT#{group_key}.
    Emits audit_event("crm_acl_role.group_revoked", actor_sub, ...).
    No-op if the row does not exist.
    """
```

- Deletes the row unconditionally (DynamoDB `delete_item` is a no-op on missing keys).
- Calls `audit_event("crm_acl_role.group_revoked", ...)`.
- Calls `_invalidate_permission_cache()`.

#### 4.1.3 `get_effective_roles_for_user`

```python
def get_effective_roles_for_user(
    user_sub: str,
    admin_profile: AdminProfile,
) -> list[dict]:
    """
    Return all ACL role definition dicts applicable to this user.

    Combines:
    (a) Direct ASSIGNMENT rows from the by-assignee GSI (same as get_roles_for_user).
    (b) GROUP_ASSIGNMENT rows for each scope in admin_profile.scopes (SCOPED profile)
        or all GROUP_ASSIGNMENT rows if admin_profile.type is GENERAL.
    For each group_key found, fetches the corresponding META row to get the
    permissions dict.

    Returns a deduplicated list of role dicts (by role_id).
    """
```

Implementation notes:

- Call `get_roles_for_user(user_sub)` to get direct roles (GSI query on `by-assignee`).
- Determine group keys to check:
  - If `admin_profile.type == AdminProfileType.GENERAL`: query `pk = ROLE#{role_id}` with `SK begins_with "GROUP_ASSIGNMENT#"` for ALL known role IDs, OR (more efficiently) query all `GROUP_ASSIGNMENT#` rows on-demand. The simpler approach: for each `scope` in `CANONICAL_ADMIN_SCOPES` (`app/auth/roles.py:26-31`), check if a role has `GROUP_ASSIGNMENT#{scope}`.
  - If `admin_profile.type == AdminProfileType.SCOPED`: use `admin_profile.scopes` directly.
- For each scope in the resolved group_key set: query `T.crm_acl_roles` with `Key={"pk": f"ROLE#*"}` is expensive; instead, for each role already known (from a `scan` of META rows, which is small in practice given low role counts), check if `GROUP_ASSIGNMENT#{group_key}` exists via `get_item`. Alternatively — and preferably — maintain an inverted index via a second GSI. However, since the ticket spec does not add a second GSI for GROUP_ASSIGNMENT rows, the implementation must query by role_id. Since role counts are small (typically <100), a scan of all META rows followed by per-role `get_item` checks per group_key is acceptable.
- Deduplicate by `role_id` across direct and group-propagated roles.
- Cache the result for 60 seconds keyed on `(user_sub, hash(tuple(sorted(admin_profile.scopes))))` — same TTL as STU-002's existing permission cache.

#### 4.1.4 `check_permission` (updated)

Replace the call to `get_roles_for_user(user_sub)` with `get_effective_roles_for_user(user_sub, admin_profile)`. The calling convention changes to:

`admin_profile` defaults to `AdminProfile()` (general, no scopes) for callers that only pass `user_sub`. When called from route handlers that have an `AuthenticatedUser`, pass `user.admin_profile`.

#### 4.1.5 `require_crm_permission` (updated)

The `Depends`-compatible callable from STU-002 must be updated to extract `admin_profile` from the `AuthenticatedUser` and pass it to `check_permission`. Since `require_crm_permission(module, action)` is a factory returning a dependency function, the inner function receives the full `AuthenticatedUser` via `Depends(get_authenticated_user)` and passes `user.admin_profile`.

#### 4.1.6 `list_role_assignments`

```python
def list_role_assignments(role_id: str) -> dict:
    """
    Return all direct user assignments and group assignments for a role.

    Returns:
    {
        "user_assignments": [{"user_sub": ..., "assigned_by_sub": ..., "assigned_at": ...}],
        "group_assignments": [{"group_key": ..., "assigned_by_sub": ..., "assigned_at": ...}],
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Union semantics for multi-role

When a user holds roles R1 and R2:
- R1 grants `contacts.read = True`, `contacts.export = False`.
- R2 grants `contacts.read = False`, `contacts.export = True`.
- Effective permissions: `contacts.read = True` AND `contacts.export = True`.

The union is computed by `OR`-ing each boolean field across all role permission matrices. This mirrors SuiteCRM's behavior where a user with multiple roles receives the most permissive combination.

### 5.2 Group propagation priority

Group assignments are additive to direct assignments. A user with direct role R1 and group role R2 (via `AUTH_SUPPORT`) has the union of R1 and R2. There is no "override" or "deny" semantics — the model is purely permissive union.

### 5.3 GENERAL admin profile and group propagation

An admin with `AdminProfileType.GENERAL` has all scopes implicitly (`admin_profile_has_scope` at `app/auth/roles.py:118` returns `True` for GENERAL profiles). For permission evaluation, GENERAL admins receive all group-assigned roles for all four canonical scopes. This means a GENERAL admin who holds no direct ACL role assignments may still inherit permissions via group assignments to any scope.

### 5.4 `CRM_ACL_ENABLED=0` — zero impact

When `S.crm_acl_enabled` is `False`:
- `check_permission` returns `True` immediately (no DDB reads).
- All three new router endpoints return 404 (router not registered).
- `get_effective_roles_for_user` is never called.
- The `crm_acl_roles` table may be empty; no effect.

### 5.5 Idempotency of assignment

`assign_role_to_group` uses `put_item` which overwrites silently. Calling it twice with the same `(role_id, group_key)` is safe; the second call updates `assigned_at` and `assigned_by_sub` but otherwise has no side effect. The audit event fires on every call.

`revoke_role_from_group` uses `delete_item` which is a no-op on a non-existent key. Calling it when the row is already deleted emits the audit event but does not raise an error.

### 5.6 Cache invalidation correctness

The permission cache is keyed on `(user_sub, hash(admin_profile_scopes))`. Because group assignments are not user-specific in the cache key, when a group assignment changes, the entire cache must be invalidated (not just one user's entry). `_invalidate_permission_cache()` must clear the entire dict, not a single entry. This is the same behavior as `billing_config.invalidate_cache()` (`app/services/billing_config.py:54`) which also drops the entire cache on write.

### 5.7 Role deletion cascades

When a role is deleted (STU-002's `delete_acl_role`), it must also delete all `GROUP_ASSIGNMENT#` rows for that role. The existing pattern scans `sk` prefixed `ASSIGNMENT#`; it must be extended to also scan `GROUP_ASSIGNMENT#`. Both loops use `FilterExpression` with `Key("pk").eq(f"ROLE#{role_id}")` and `begins_with("sk", "ASSIGNMENT#")` / `begins_with("sk", "GROUP_ASSIGNMENT#")` respectively.

### 5.8 Unknown group_key values

`group_key` is not validated against `CANONICAL_ADMIN_SCOPES` at write time. This is intentional: the system must be forward-compatible with custom group names (e.g., PTY-series contact group keys). At permission evaluation time, `get_effective_roles_for_user` only activates group roles when the user's `admin_profile.scopes` contains the group key. An assignment to a non-existent group key is harmless — no user will ever have that scope, so the role is never propagated.

### 5.9 Race condition on cache and assignment

There is a TOCTOU window: a group assignment may be written between a user's JWT issuance and their next permission check. The 60-second TTL cache means a newly assigned group role becomes effective within 60 seconds. For revocation, the same 60-second window applies. This matches the existing behavior of direct user assignment and is acceptable for an admin-tier configuration change.

### 5.10 `assigned_at` precision

`now_ts()` returns integer Unix seconds (`app/core/time.py:2`). The `assigned_at` field in GROUP_ASSIGNMENT rows is stored as `N` type. Since DynamoDB does not enforce uniqueness on `sk` values that differ (each `GROUP_ASSIGNMENT#{group_key}` SK is unique per role), there is no collision risk from timestamp precision.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

All service functions use `T.crm_acl_roles` (a `_FloatSafeTable` wrapping a boto3 DynamoDB resource, `app/core/tables.py:29-66`). In dev, this table is backed by DynamoDB Local (port 8001). In prod, it points to real DynamoDB. No `if S.dev_mode` branch exists in the service. The `_safe_table` wrapper handles float-to-Decimal coercion on writes for both environments transparently.

### 7.2 Audit trail

Every write-path operation (`assign_role_to_group`, `revoke_role_from_group`) calls `alerts.audit_event` (`app/services/alerts.py:644`), writing an immutable row to `T.alerts`. Audit events are emitted unconditionally — they fire in dev and prod identically. Event names follow the existing convention: `crm_acl_role.group_assigned` and `crm_acl_role.group_revoked`.

### 7.3 Authorization layering

- Group assignment and revocation: ROOT only (`require_root`, `app/auth/policy.py:63`). Only the platform root can grant ACL roles to groups, preventing privilege escalation by ADMIN-tier accounts.
- Listing assignments: ADMIN or ROOT (`require_admin_or_root`, `app/auth/policy.py:67`). Read access is broader.
- `check_permission` / `get_effective_roles_for_user`: internal service calls only; no direct public endpoint exposes the raw role list for arbitrary users.

### 7.4 SK injection prevention

`group_key` is validated against the regex `^[a-z][a-z0-9_]*$` before any DDB write. This prevents injection of SK separator characters (`#`, `:`, etc.) that could corrupt the single-table DDB key space.

### 7.5 Idempotency

`assign_role_to_group` uses `put_item` (last-write-wins). `revoke_role_from_group` uses `delete_item` (no-op on missing). Both are safe to retry on network failure without manual deduplication.

### 7.6 No money-out path

STU-003 does not touch billing, payments, or ledger records. The no-fork constraint on `refund_payment` / `settle_or_reverse_ledger` does not apply here.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact with flag off

With `CRM_ACL_ENABLED=0` (the default for all existing deployments), the `crm_acl` router is not registered, the service functions are never called, and `check_permission` short-circuits to `True`. No existing behavior is altered.

### 8.2 No DynamoDB schema change

STU-003 adds a new SK prefix (`GROUP_ASSIGNMENT#`) to an existing table. DynamoDB is schemaless for non-key attributes; no table update or migration is needed. The new row type coexists with `META` and `ASSIGNMENT#` rows under the same `pk`.

### 8.3 STU-002 `check_permission` signature change

The signature of `check_permission` gains an optional `admin_profile` parameter (default `AdminProfile()`). All existing callers that pass only `(user_sub, module, action)` continue to work — they get the GENERAL-profile path, which includes all canonical scope group assignments. This is a widening change: existing callers may newly pick up group-propagated roles after STU-003 is deployed with `CRM_ACL_ENABLED=1`. No existing callers exist in prod before STU-002 is deployed, so this is only relevant in the flag-on state.

### 8.4 STU-002 `delete_acl_role` change

The function must be updated to also purge `GROUP_ASSIGNMENT#` rows. This is a non-breaking internal change with no effect on the public API shape. The behavior with `CRM_ACL_ENABLED=0` is unchanged (delete is never called).

### 8.5 No data migration required

All existing `crm_acl_roles` rows remain valid. The new `GROUP_ASSIGNMENT#` rows are written only when `assign_role_to_group` is called; no backfill is needed for existing deployments.

## 10. Open Questions / Assumptions

1. **Custom group_key namespace**: The spec allows arbitrary string group keys beyond the four canonical `AdminScope` values. The assumption is forward-compatibility with PTY-series contact groups. If the intended scope is strictly the four `AdminScope` values, the `assign_role_to_group` validator should be tightened to `CANONICAL_ADMIN_SCOPES`. This decision should be made before STU-003 merges.

2. **Group assignment visibility to GENERAL admins**: The current design has GENERAL admins inherit ALL group-assigned roles for all canonical scopes. This may be undesirable if a GENERAL admin should not automatically inherit billing-support ACL roles. An alternative: only propagate group roles when the user has an explicit scope match, and require ROOT to set `AdminProfileType.SCOPED` to get group roles. The spec follows the ticket description which states GENERAL admins have all scopes.

3. **Pagination of `list_role_assignments`**: The current design returns all assignments in a single response. For large deployments with many users assigned to a single role, this could be expensive. If role membership can reach thousands, cursor pagination should be added. For the MVP, a single non-paginated response with a 1000-item cap is acceptable.

4. **`get_effective_roles_for_user` performance**: For GENERAL admins, this function queries `GROUP_ASSIGNMENT#` existence for all canonical scopes across all role IDs. With O(roles × scopes) DDB reads, this could be 400 reads for 100 roles × 4 scopes. The 60-second in-process cache mitigates this; however, a second GSI indexed on `sk` prefix would make this O(4) queries. Adding a GSI for GROUP_ASSIGNMENT rows is flagged as a potential follow-on optimization under `STU-003b` if performance becomes an issue.

5. **JWT-derived `AdminProfile` staleness**: If an admin's group membership changes (e.g., their `AdminProfile.scopes` is updated), the change is reflected only after their next JWT refresh (typically on next login). The permission cache also adds up to 60 seconds of lag. This is a known limitation and matches the behavior described in CLAUDE.md for cookie-based session auth.
