# CAS-005 — Case linked to Contact and Account

**Type:** Feature  **Priority:** P1  **Estimate:** 1 day  
**Ticket source:** `docs/suitecrm/CRM_CASES_PORTAL_TICKETS.md`, section "CAS-005"

---

## 1. Summary & Goal

CAS-005 adds two optional foreign-key fields — `contact_id` and `account_id` — to the ticket data model. These are opaque string identifiers today; once PTY-001..PTY-015 (Party/Contact/Account CRM) ships they will resolve to live Party records. The feature enables:

1. Linking any support ticket to a Contact (an individual person record, e.g. a B2C customer) and/or an Account (an organisational record, e.g. a B2B company).
2. Listing all tickets associated with a given contact or account — two new admin-only query paths backed by dedicated GSIs on the existing `tickets` table.
3. Updating the contact/account link after creation via the existing `_conditional_update_meta` optimistic-lock path.

Everything is additive and gated on `S.crm_cases_enabled` (introduced by CAS-001). With the flag off the platform is byte-for-byte unchanged: the two new fields are never written, the two new GSIs receive no data, and no existing route, service, or test is affected.

## 2. Context & Current State

### 2.1 Ticket store write path

`app/services/tickets.py:411` contains `TicketStore.create_ticket`. It builds a `header` dict and calls `self._table.put_item(Item={k: v for k, v in header.items() if v is not None})` at `app/services/tickets.py:476`. The filter strips `None` values, so new optional keys that are `None` are automatically omitted — no DynamoDB NULL is stored, no GSI row is written. This is the correct pattern for optional GSI attributes.

The optimistic-lock update path is `TicketStore._conditional_update_meta` at `app/services/tickets.py:723`. It constructs a `SET ... REMOVE ...` expression. Space GSI keys follow the SET-if-non-None / REMOVE-if-None pattern starting at `app/services/tickets.py:757`: each GSI attribute is SEt when its placeholder value is not `None`, and REMOVEd otherwise. This prevents writing `NULL` into DynamoDB GSI hash/range key attributes (a DynamoDB constraint that causes `ValidationException`). Contact and account GSI keys must follow the same pattern.

### 2.2 Existing GSI key conventions

The `tickets` table (declared at `scripts/local-ddb-init.py:695-711`) uses composite GSI keys of the form `gsi<N>pk` / `gsi<N>sk` for the core owner/status/assignee indexes, and `gsi_<qualifier>_pk` / `gsi_<qualifier>_sk` for domain-specific indexes (`gsi_space_pk`, `gsi_space_status_pk`, `gsi_space_assignee_pk`). The GSI sort key is always `_updated_index_sk(updated_at, ticket_id)` which is `f"UPDATED#{updated_at:013d}#TICKET#{ticket_id}"` (`app/services/tickets.py:192-193`) — a string prefixed with a zero-padded numeric timestamp. Because this key is declared as type `S` (string) in the existing table definition it does NOT require `attr_types={"...", "N"}`. The new contact/account GSI sort keys must follow the same string-SK convention to be consistent.

The existing `tickets` table definition at `scripts/local-ddb-init.py:695-711` already registers 10 GSIs (`scripts/local-ddb-init.py:700-709`, confirmed by inspection). DynamoDB Local supports up to 20 GSIs per table. Adding two more (contact and account) brings the total to 12, well within the 20-GSI limit.

It currently has no `contact_id`, `account_id`, `case_number`, or `priority` fields — these are added by CAS-002 and CAS-003 respectively (confirmed: `app/routers/tickets.py:58-73` — fields are `ticket_id`, `subject`, `owner_sub`, `status`, `space_id`, `assigned_*`, `created_at`, `updated_at`, `version`, `messages`, `activity` only). ## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off isolation

When `S.crm_cases_enabled` is `False` (the default):

- `CreateTicketReq.contact_id` and `account_id` are accepted at parse time (Pydantic does not reject them) but silently discarded inside `create_ticket` — the `if S.crm_cases_enabled` guard means neither value nor GSI key is written to DynamoDB.
- `PATCH /{ticket_id}/contact-account` returns 404 `crm_cases_disabled`.
- `GET /tickets?contact_id=X` and `GET /tickets?account_id=X` behave as if the parameters were absent (the new `list_tickets` branches are not entered when the index names resolve to the existing `tickets` table which has no such GSIs registered — the query would fail, so the branches are guarded by `if S.crm_cases_enabled` before dispatching).
- `TicketOut.contact_id` and `TicketOut.account_id` will be `None` for all existing tickets (the fields are not present in their META rows).
- No existing test exercises the new code paths.

### 5.2 Partial linkage (contact only or account only)

Either field may be supplied independently. A ticket may have `contact_id` set and `account_id` absent (or vice versa). No business rule requires both to be present simultaneously. The SET/REMOVE logic in `_conditional_update_meta` handles each independently.

### 5.3 Clearing a link

Sending `PATCH /{ticket_id}/contact-account` with `{"contact_id": null}` removes the `contact_id` (and its two GSI keys) from the META row via the REMOVE path. The ticket will no longer appear in `GET /tickets?contact_id=<old_id>` queries after the next update propagates to the GSI (DynamoDB GSI eventual consistency, typically sub-second).

### 5.4 Changing a link

Sending a new `contact_id` (different from the current value) replaces the GSI key atomically via the `_conditional_update_meta` update expression. Because the update sets both the `gsi_contact_pk` (to the new partition prefix) and `gsi_contact_sk` atomically, there is no window where a ticket appears under both the old and new contact GSI partitions.

### 5.5 Concurrent update conflict

`_apply_header_update_once` (`app/services/tickets.py:792`) performs one read-then-conditional-write cycle with version check. On concurrent update, `_conditional_update_meta` returns `False` (DynamoDB `ConditionalCheckFailedException` caught at `app/services/tickets.py:788`), and `_apply_header_update_once` raises `TicketStateError` with code `ticket_update_conflict` (`app/services/tickets.py:800-804`). The `update_ticket_contact_account` endpoint catches this and returns HTTP 409 (following the existing `_ticket_state_http_status` helper at `app/routers/tickets.py:348-351`).

The ticket source does not specify a retry loop for this endpoint. The caller is expected to retry with the latest version.

### 5.6 Whitespace and empty-string normalisation

`body.contact_id` is normalised to `None` via `(body.contact_id or "").strip() or None` at every call site. This prevents a ticket with `contact_id=""` (empty string) from writing a `gsi_contact_pk = "CONTACT#"` GSI key that would pollute the contact index partition.

### 5.7 `_assemble_headers` N+1 pattern

`_assemble_headers` at `app/services/tickets.py:603` calls `get_ticket` once per header row returned by the GSI query. This is the same pattern used by the owner/assignee/status list paths and is consistent across all list endpoints. No new N+1 penalty is introduced.

### 5.8 Audit events

On successful creation with a non-null `contact_id` or `account_id`, `audit_event("ticket_contact_linked", ...)` / `audit_event("ticket_account_linked", ...)` is emitted inside `update_contact_account`. On creation these are emitted from the create path via a helper. Both audit event names must be added to `ALERT_EVENT_TYPES` in `app/services/alerts.py:134` (confirmed: `app/services/alerts.py:134-148`; currently the ticket event names at `app/services/alerts.py:140` are `ticket_created`, `ticket_assigned`, `ticket_replied`, `ticket_status_changed`, `ticket_reopened`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

There are no `dev_mode` branches in this ticket. All DynamoDB operations use `T.tickets` regardless of environment (`app/core/tables.py:392`). The `_FloatSafeTable` proxy at `app/core/tables.py:29-62` (instantiated via `_safe_table` at `app/core/tables.py:65-66`) ensures `Decimal` coercion on writes. No S3, KMS, SES, or mock service is involved. Code is identical in dev (DynamoDB Local on port 8001) and production (AWS DynamoDB).

### 7.2 Idempotency

- `create_ticket` already has an idempotent guard at `app/services/tickets.py:431`: `existing = self.get_ticket(resolved_ticket_id); if existing: return existing`. This guard fires before the new contact/account fields are written, so a duplicate create with different `contact_id`/`account_id` values returns the already-stored ticket unchanged. Callers must use `PATCH /{ticket_id}/contact-account` to update the link post-creation.
- `update_contact_account` is idempotent: calling it twice with the same values produces no visible state change (version increments each time, but the field values remain the same).

### 7.3 Security

- **Admin-only queries**: `GET /tickets?contact_id=X` and `GET /tickets?account_id=X` are admin-only. A regular user can only see their own tickets via the `owner_sub` branch (which uses the caller's own `user.sub`). A non-admin cannot enumerate tickets linked to an arbitrary contact or account.
- **PATCH is admin-only**: `PATCH /{ticket_id}/contact-account` requires `_is_admin_actor(request, user)`. A ticket owner (non-admin user) cannot modify the CRM linkage.
- **Field-length validation**: `max_length=128` on `contact_id` and `account_id` in `CreateTicketReq` and `UpdateContactAccountReq` prevents oversized strings from reaching DynamoDB.
- **No FK resolution at this stage**: No query against a contacts or accounts table is performed. The opaque string is stored as-is, so there is no IDOR risk introduced at this layer. PTY validation will be added once PTY ships.
- **CSRF**: All mutating endpoints (`POST /tickets`, `PATCH /tickets/{id}/contact-account`) use `Depends(require_ui_session)` which enforces CSRF token validation for cookie-auth requests (CLAUDE.md auth section).

## 8. Backward Compatibility & Migration

### 8.1 Existing tickets

Existing META rows have no `contact_id`, `account_id`, or associated GSI attributes. `get_ticket` uses `header.get("contact_id")` / `header.get("account_id")` with no fallback — both return `None` for pre-existing rows. `TicketOut` declares both fields as `str | None = None`, so Pydantic validation succeeds for all existing tickets.

### 8.2 Existing callers of `_conditional_update_meta`

All three callers of `_apply_header_update_once` — `assign_ticket` (call at `app/services/tickets.py:835`; method at line 807), `add_message` (call at `app/services/tickets.py:908`; method at line 851), `update_status` (call at `app/services/tickets.py:962`; method at line 913) — construct their `values` dict inside `build_values` closures. Each closure must be extended to pass the new GSI placeholder values with `None` (REMOVE semantics) so that tickets without a contact/account link do not accidentally have stale GSI attributes injected during unrelated updates.

Concretely, each `_values` closure must include:

```python
":gsi_contact_pk": cur.get("contact_id") and _contact_index_pk(cur.get("contact_id")) or None,
":gsi_contact_sk": _updated_index_sk(ts, ticket_id) if cur.get("contact_id") else None,
":gsi_account_pk": cur.get("account_id") and _account_index_pk(cur.get("account_id")) or None,
":gsi_account_sk": _updated_index_sk(ts, ticket_id) if cur.get("account_id") else None,
```

This preserves existing GSI data (re-written on every update) for tickets that have the fields set, and generates REMOVE operations for tickets that do not. This is identical to the treatment of space GSI keys at `app/services/tickets.py:827-832`.

### 8.3 No DynamoDB table migration required

New GSIs are declared in `scripts/local-ddb-init.py` and created at `just restart` time in dev. In production, adding GSIs to an existing table requires an `UpdateTable` call followed by an async backfill by AWS. GSI items only appear when a write occurs after the index is active — pre-existing ticket rows with no `gsi_contact_pk` / `gsi_account_pk` are simply absent from the new indexes, which is the correct behaviour (they have no contact/account link).

The production deployment procedure must therefore:
1. Deploy the `UpdateTable` request to add the two new GSIs to the live `tickets` table.
2. Wait for `IndexStatus=ACTIVE` (typically minutes to hours depending on table size).
3. Deploy the application code.

This is a standard additive-index migration with no data transformation needed.

### 8.4 `.env.local` changes

Two new env vars (`TICKETS_CONTACT_INDEX_NAME`, `TICKETS_ACCOUNT_INDEX_NAME`) default to safe values; no `.env.local` change is required for dev work with the defaults.

## 10. Open Questions / Assumptions

1. **PTY ID format**: PTY-001..PTY-015 may produce `contact_id` and `account_id` values with a specific prefix (e.g. `pty_cnt_...`). The current `max_length=128` is generous; adjust once PTY specifies its ID format. No structural change to the DynamoDB row or GSI key format will be needed.

2. **Validation of existence**: Should `POST /tickets` with an unknown `contact_id` return 404 (fail-fast) or silently store the opaque ID? The current design stores silently (soft dependency on PTY). This is consistent with the ticket source: "PTY dependency soft: fields are stored and returned even without a live PTY module." If PTY ships before CAS-005 is deployed, a validation hook can be added without changing this spec.

3. **Bulk re-linking**: No batch endpoint for linking all tickets of an old contact to a new merged-contact record is specified. CAS-005 covers the single-ticket operation only; bulk re-linking is a follow-up.

4. **Index name collisions**: The chosen default index names (`contact-updated_at-index`, `account-updated_at-index`) must not collide with any existing index name on the `tickets` table. The existing 10 index names are confirmed distinct from these two defaults.

5. **`_conditional_update_meta` signature stability**: CAS-003 (priority field) also adds new GSI keys to this method. CAS-005 assumes CAS-003 is merged first (per the dependency chain: CAS-001 → CAS-002 → CAS-003 → CAS-005). If merging out-of-order, the `_conditional_update_meta` changes from both tickets must be combined in a single merge.
