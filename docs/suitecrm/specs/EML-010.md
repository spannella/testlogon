## 1. Summary & Goal

EML-010 adds a comprehensive test harness — one Playwright E2E spec file and one hermetic pytest module — that validates the full surface area introduced by EML-001 through EML-009. Its goal is to prevent regressions in every new capability: HTML email delivery (EML-001), admin email settings (EML-002), per-user IMAP/SMTP account management (EML-003), inbox sync and threading (EML-004), the in-app email client UI (EML-005), personal email signatures (EML-006), email archiving to CRM records (EML-007), inbound group mailbox auto-ticket creation (EML-008), and campaign HTML template management (EML-009).

No new production service code is introduced by this ticket. All test code is strictly additive; removing the spec files leaves the platform byte-for-byte unchanged in production.

## 4. API / Service Design

EML-010 adds no new production endpoints. It validates the APIs introduced by EML-001 through EML-009. The test-only admin endpoint `POST /ui/admin/email/mailboxes/test-inbound` (introduced by EML-008, `app/routers/admin_email.py`, after the mailbox CRUD routes) is the primary inbound-path E2E entrypoint. This endpoint:

```python
@router.post("/ui/admin/email/mailboxes/test-inbound")
async def test_inbound_email(
    payload: TestInboundIn,        # {raw_mime: str}
    actor: AuthenticatedUser = Depends(require_admin_or_root),
) -> dict:
    if not S.inbound_mailbox_enabled:
        raise HTTPException(status_code=503, detail="inbound_mailbox_disabled")
    result = await asyncio.to_thread(
        inbound_email.process_inbound_message, payload.raw_mime.encode()
    )
    return result
    # Full return shapes (EML-008:233–238):
    #   {"action": "created",  "ticket_id": str, "mailbox_id": str}
    #   {"action": "threaded", "ticket_id": str, "mailbox_id": str}
    #   {"action": "ignored",  "reason": str}
    #   {"action": "error",    "reason": str}   ← on MIME parse failures
```
<!-- CORRECTED: original return-shape comment showed only `{action: "created"|"threaded"|"ignored", ticket_id?: str}`. EML-008:233–238 specifies four possible actions including "error", and created/threaded responses also carry `mailbox_id`. -->

This mirrors the security-equivalent prod path (same `process_inbound_message` call, same return shape) without requiring real SNS infrastructure.

### 5.2 Pytest unit test module (`tests/test_eml_email_client.py`)

#### `test_account_kms_encryption`

- Creates a moto DynamoDB `user_email_accounts` table; patches `T.user_email_accounts` via `object.__setattr__`.
- Patches `app.services.user_email_accounts.kms_encrypt` with a deterministic identity stub: `lambda pt: base64.b64encode(("FAKE_CT:" + pt).encode()).decode()`.
- Patches `app.services.user_email_accounts.kms_decrypt` with the inverse.
- Calls `create_account(user_sub="test_sub", payload=AccountCreatePayload(..., password="secret123"))`.
- Asserts DDB item `password_ct_b64` differs from `"secret123"` (encryption happened).
- Asserts `list_accounts("test_sub")` returns the account without `password_ct_b64` in any returned dict.
- Asserts `verify_connection("test_sub", account_id)` returns `{"ok": True, "status": "active"}` (dev mock; `S.dev_mode=True` via `object.__setattr__`).

#### `test_thread_id_consistency`

- Creates a moto `user_email_messages` table; patches `T.user_email_messages` via `object.__setattr__`.
- Calls `sync_inbox` twice with the mock client returning two messages: message A with `Message-ID: <root@example.com>`, message B with `In-Reply-To: <root@example.com>`.
- Asserts both stored items share the same `thread_id` (`sha256("<root@example.com>")[:16]`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

Per the `CRM_EMAIL_TICKETS.md:13` constraint, no `dev_mode` branches are permitted that skip logic. The only dev-mode divergences are:

- `send_alert_email` in `app/services/alerts.py:462`: dev mode writes to `S.dev_email_log` instead of calling SES. This existing branch is not modified; the new `html_body` parameter is written to the dev log as a length annotation. Tests that need to assert SES payload structure set `S.dev_mode=False` via `object.__setattr__`.
- `verify_connection` in `app/services/user_email_accounts.py`: in dev mode returns `{"ok": True, "status": "active"}` without opening a real IMAP connection. The `_MockImapClient` stub (used by `sync_inbox`) is selected when `S.dev_mode=True`. No logic is skipped; the stub path exercises the same code paths as the real IMAP path (same return shape, same DDB writes). Production uses `imaplib.IMAP4_SSL`. Both paths go through the same `create_account` / `list_accounts` / `get_account` functions.

### Idempotency

- **IMAP sync** (`sync_inbox`): re-sync with the same UIDs issues `put_item` calls with the same PK/SK; DynamoDB `put_item` is last-writer-wins, so duplicate syncs are safe. The last-sync cursor row (`SYNC#CURSOR`, SK literal; PK encodes the folder as `USER#{sub}#ACCT#{id}#FOLDER#{folder}`) is only advanced after all `put_item` calls succeed. On partial failure the cursor is not advanced, so the next sync re-fetches the same UIDs. <!-- CORRECTED: original said "SYNC#{account_id}"; EML-004:102 specifies SK="SYNC#CURSOR" and per-folder PK. -->
- **Email archive** (`archive_email`): the SK encodes `date_ts` and `message_id_hash`, which are derived from immutable MIME headers, so re-archiving the same message to the same entity produces the same SK and overwrites with identical data.
- **Inbound ticket creation** (`process_inbound_message`): the `Message-ID` header is checked against an index (`ByMessageId` or a conditional put on the ticket itself) to prevent duplicate ticket creation for retried SNS deliveries.

### Security

- **Password encryption at rest**: `password_ct_b64` is stored as KMS ciphertext (`kms_encrypt` from `app/core/crypto.py:16`). The service layer (`user_email_accounts.py`) never returns `password_ct_b64` from `list_accounts` or `get_account`; only `verify_connection` decrypts it server-side and never surfaces the plaintext to any API response.
- **SNS signature verification**: the inbound endpoint reuses the exact `verify_sns_message` call and `S.ses_sns_signature_verification_enabled` gate from `app/routers/ses_notifications.py:47`. The SSRF guard on `SigningCertURL` (enforced by `app/services/sns_signature.py`) applies identically.
- **Signature HTML sanitisation**: `upsert_signature` (EML-006, `user_email_accounts.py`) strips `<script>`, `<iframe>`, `<object>`, `<embed>`, `<form>`, and event-handler attributes before storing, using a regex-based `_sanitize_signature_html` function (EML-006:137). **No `bleach` or other third-party HTML-sanitisation library is used or required** — EML-006 explicitly adopts a pure-regex approach consistent with `app/services/text_sanitizer.py` and `app/services/audit_export_pipeline.py`, and `bleach` is absent from `requirements.txt`. <!-- CORRECTED: original said "The service uses `bleach` or an equivalent dependency already present in `requirements.txt`." EML-006:43,599 and requirements.txt confirm no bleach dependency; the sanitiser is regex-only. --> Server-side sanitisation is the authoritative gate; the compose panel may also apply `DOMPurify` client-side but this is not a security boundary.
- **Archive ownership**: `archive_email` and `unarchive_email` validate entity ownership (ticket `owner_sub` or admin, contact `owner_id == user_sub`) before writing or deleting. A user cannot archive an email against another user's ticket by guessing the `entity_id`.
- **Campaign template injection**: `render_campaign_body` substitutes only the exact keys listed in `merge_fields`. HTML output is passed directly to `send_alert_email(..., html_body=...)` (EML-001); SES truncates at 50,000 chars. No `eval` or Jinja autoescape risk — substitution uses `_VAR_RE` from `notification_templates.py:23` with `re.sub`, which is safe for user-controlled template bodies authored by admins only (`require_admin_or_root`).
