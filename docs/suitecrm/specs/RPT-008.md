# RPT-008 — Saved searches as dashlets

**Ticket area**: Reports & Dashboards (AOR + dashlets)
**Type**: Feature  **Priority**: P2  **Estimate**: 2d
**Depends on**: RPT-001 (tables + flag), RPT-006 (dashboard CRUD), RPT-007 (dashlet data dispatch)
**Source**: `docs/suitecrm/CRM_REPORTS_TICKETS.md` lines 424–465

---

## 1. Summary & Goal

RPT-008 implements the SuiteCRM DASH-002 "Saved Searches as Dashlets" capability. A user may save a named filter — a `(module, conditions)` pair — as a persistent Saved Search record, then pin that record as a `saved_search` dashlet tile on their home dashboard (RPT-006). When the dashlet is rendered, it executes the saved search live against the appropriate DynamoDB table and returns a capped result set.

The end state is:

1. **Backend** — `app/services/crm_saved_searches.py` (CRUD + run); `app/routers/crm_saved_searches.py` (5 endpoints); an additive `saved_search` branch inside `app/services/crm_dashlet_data.py` (RPT-007).
2. **Frontend** — `frontend/src/pages/reports/SavedSearchesPage.tsx`; an `SavedSearchDashlet.tsx` renderer; React Query wiring.
3. **Data** — the `crm_saved_searches` DynamoDB table introduced by RPT-001 (no new tables required here).

With `CRM_REPORTS_ENABLED=0` (the default) every endpoint introduced by this ticket returns 404, the frontend page is unreachable, and the dashlet dispatch branch is never entered. The rest of the platform is byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 Feature flag

`S.crm_reports_enabled` is the single gate for all CRM Reports & Dashboards tickets. It is introduced by RPT-001 following the boolean env-var pattern at `app/core/settings.py:81`:

```python
crm_reports_enabled: bool = os.environ.get("CRM_REPORTS_ENABLED", "0") not in ("0", "false", "False")
```

With the flag off, no existing file is altered — the guard is checked at the router boundary only.

### 2.2 crm_saved_searches table

RPT-001 declares the `crm_saved_searches` table in `scripts/local-ddb-init.py` with:

- PK `saved_search_id` (S), SK `sk` (S)
- GSI `owner-searches-index`: `GSI1PK=OWNER#{owner_sub}`, `GSI1SK=created_at` (numeric)
- `attr_types={"GSI1SK": "N"}` — required because `created_at` is an integer Unix timestamp; omitting this causes a DynamoDB `ValidationException` at query time (CLAUDE.md gotcha, `scripts/local-ddb-init.py:34`).

The table handle is exposed as `T.crm_saved_searches` (added to `app/core/tables.py` by RPT-001, following the `_safe_table` / `_FloatSafeTable` proxy pattern at `app/core/tables.py:65`).

### 2.3 Dashboard dashlet model (RPT-006)

RPT-006 introduces `T.crm_dashboards` (PK `dashboard_id`, SK `sk`). A dashlet within the layout list has shape `{dashlet_id, dashlet_type, title, config}` where `config` is a free-form `Dict[str, Any]`. For `dashlet_type="saved_search"`, `config` must carry `{"saved_search_id": "<SS#...>"}`. The service at `app/services/crm_dashboard.py` stores and retrieves this layout without inspecting `config` — interpretation is delegated to the dashlet data layer.

### 2.4 Dashlet data dispatch (RPT-007)

`app/services/crm_dashlet_data.py` (RPT-007) exposes `get_dashlet_data(user_sub, dashlet)` which dispatches on `dashlet["dashlet_type"]`. It currently handles `recent_tickets`, `calendar_today`, `my_contacts`, `billing_summary`, and `report`. RPT-008 adds one new branch: `saved_search`. No existing branches are modified.

### 2.5 Module data access primitives

The saved search executor must iterate live DynamoDB data for each supported module. The same iteration patterns already exist in `app/services/csv_export.py`:

- `tickets` — `T.tickets` (handle at `app/core/tables.py:392`; access pattern from `app/services/tickets.py`)
- `contacts` — `_iter_contacts(user_sub)` at `app/services/csv_export.py:90`
- `billing_ledger` — `_iter_billing_entries(user_sub)` at `app/services/csv_export.py:52`

- `subscriptions` — `T.subscriptions` (handle at `app/core/tables.py:352`)
- `questionnaire_responses` — `_iter_questionnaire_responses` at `app/services/csv_export.py:113`

RPT-008 extracts a shared `_fetch_and_filter(module, conditions, owner_sub)` helper from the RPT-002 `run_report` implementation (or, if RPT-002 is not yet merged, implements the same logic inline and moves it to a shared helper simultaneously). This helper is the single code path that both `run_report` (RPT-002) and `run_saved_search` (this ticket) call.

### 2.6 Condition evaluation

RPT-002 introduces `_eval_condition(item, condition)` — a pure-Python evaluator supporting operators `eq`, `neq`, `contains`, `gt`, `lt`, `gte`, `lte`, `is_empty`, `not_empty`. RPT-008 reuses this function unchanged; conditions in a saved search follow exactly the same `ReportCondition` model.

### 2.7 Auth

All endpoints use `require_ui_session` (defined at `app/services/sessions.py:330`), which returns a dict carrying at minimum `user_sub: str`, `role`, and `session_id` (cookie-auth sessions also carry `admin_profile`). Cookie-based sessions include CSRF enforcement on non-GET methods (CLAUDE.md auth section). Ownership is enforced at the service layer — a `saved_search_id` owned by another user returns 403, not 404, to avoid oracle leakage.

### 2.8 Pagination

Cursor-based pagination reuses `encode_cursor` / `decode_cursor` from `app/core/cursor.py:94`. The cursor is an HMAC-signed v2 envelope; `Decimal` values in `LastEvaluatedKey` are serialised safely via `_json_default` at `app/core/cursor.py:12`.

### 2.9 Audit events

`audit_event(event, user_sub, ...)` at `app/services/alerts.py:644` is the single audit write path. RPT-008 emits audit events for create, delete, and run operations to `T.alerts`, consistent with the pattern used by KYC, SSH key manager, and other services.

## 3. Data Model

### 3.1 crm_saved_searches table (created by RPT-001)

No schema changes are required in RPT-008. The table definition established by RPT-001 is:

```
Table name : crm_saved_searches   (S.crm_saved_searches_table_name)
PK         : saved_search_id  (S)
SK         : sk               (S)
GSI        : owner-searches-index
             GSI1PK = OWNER#{owner_sub}   (S)
             GSI1SK = created_at          (N)   ← attr_types={"GSI1SK": "N"} required
```

#### META row (sk = "META")

| Attribute        | Type | Notes |
|------------------|------|-------|
| `saved_search_id`| S    | `"SS#{uuid4().hex[:12]}"` — stable opaque ID |
| `sk`             | S    | `"META"` |
| `GSI1PK`         | S    | `"OWNER#{owner_sub}"` |
| `GSI1SK`         | N    | `created_at` (Unix epoch int) |
| `owner_sub`      | S    | Sub of the creating user |
| `name`           | S    | User-supplied display name, 1–200 chars |
| `module`         | S    | One of the six supported modules (see §4.1) |
| `filters`        | L    | JSON-serialised list of `ReportCondition`-shaped dicts |
| `created_at`     | N    | Unix epoch int |
| `updated_at`     | N    | Unix epoch int |

#### No additional rows

Saved searches have no run-result row (unlike reports in RPT-002). Results are computed on-demand at `/run` time and never persisted — this keeps the table small and avoids stale cache management.

### 3.2 crm_dashboards table interaction (RPT-006 schema, no change)

When a saved search is pinned as a dashlet, the config payload written into the `dashlets` list on `T.crm_dashboards` is:

```json
{
  "dashlet_id": "dlt_{uuid8}",
  "dashlet_type": "saved_search",
  "title": "<user-supplied or saved search name>",
  "config": { "saved_search_id": "SS#{12hex}" }
}
```

No change to the `crm_dashboards` schema or service is required.

## 4. API / Service Design

### 4.1 Pydantic models (add to `app/models.py`)

```python
class SavedSearchCreateIn(BaseModel):
    name: str = Field(..., min_length=1, max_length=200)
    module: str = Field(
        ...,
        pattern=r"^(tickets|contacts|billing_ledger|orders|subscriptions|questionnaire_responses)$"
    )
    filters: List[ReportCondition] = Field(default_factory=list, max_items=20)

class SavedSearchUpdateIn(BaseModel):
    name: Optional[str] = Field(None, min_length=1, max_length=200)
    filters: Optional[List[ReportCondition]] = Field(None, max_items=20)

class SavedSearchOut(BaseModel):
    saved_search_id: str
    name: str
    module: str
    filters: List[ReportCondition]
    owner_sub: str
    created_at: int
    updated_at: int

class SavedSearchRunOut(BaseModel):
    saved_search_id: str
    module: str
    columns: List[str]      # ordered field names present in result rows
    rows: List[Dict[str, Any]]  # capped at 500 rows; values are str/int/None
    row_count: int
    ran_at: int             # Unix epoch of this execution
```

`ReportCondition` is defined by RPT-002 in `app/models.py`. It must be declared before `SavedSearchCreateIn` in the file — if RPT-002 has not been merged, include the definition here in full:

```python
class ReportCondition(BaseModel):
    field: str
    operator: str  # eq | neq | contains | gt | lt | gte | lte | is_empty | not_empty
    value: Optional[str] = None
```

### 4.2 Service layer (`app/services/crm_saved_searches.py`)

#### `create_saved_search(owner_sub, payload: SavedSearchCreateIn) -> SavedSearchOut`

1. Generate `saved_search_id = f"SS#{uuid4().hex[:12]}"`.
2. Set `now = now_ts()`.
3. Build item: all `SavedSearchOut` fields plus `GSI1PK = f"OWNER#{owner_sub}"`, `GSI1SK = now`.
4. `T.crm_saved_searches.put_item(Item=item)` — unconditional; IDs are UUID-derived and collision probability is negligible.
5. Emit `audit_event("saved_search.created", owner_sub, saved_search_id=saved_search_id, module=payload.module)`.
6. Return `SavedSearchOut`.

#### `list_saved_searches(owner_sub, cursor: Optional[str] = None) -> Tuple[List[SavedSearchOut], Optional[str]]`

1. Build GSI query: `IndexName="owner-searches-index"`, `KeyConditionExpression=Key("GSI1PK").eq(f"OWNER#{owner_sub}")`, `ScanIndexForward=False` (newest first), `Limit=50`.
2. Apply `ExclusiveStartKey=decode_cursor(cursor)` if cursor is non-None.
3. Return `(items, encode_cursor(resp.get("LastEvaluatedKey")))`.

#### `get_saved_search(saved_search_id, owner_sub) -> SavedSearchOut`

1. `T.crm_saved_searches.get_item(Key={"saved_search_id": saved_search_id, "sk": "META"})`.
2. If item missing → raise `HTTPException(404)`.
3. If `item["owner_sub"] != owner_sub` → raise `HTTPException(403)`.
4. Return `SavedSearchOut`.

#### `update_saved_search(saved_search_id, owner_sub, patch: SavedSearchUpdateIn) -> SavedSearchOut`

1. Read item (with ownership check as above).
2. Build `UpdateExpression` and `ExpressionAttributeValues` for whichever fields are non-None in `patch`, always including `updated_at = now_ts()`.
3. `T.crm_saved_searches.update_item(Key=..., UpdateExpression=..., ConditionExpression="owner_sub = :sub", ...)` to prevent TOCTOU race.
4. Return updated `SavedSearchOut`.

#### `delete_saved_search(saved_search_id, owner_sub) -> None`

1. Read item (with ownership check).
2. `T.crm_saved_searches.delete_item(Key={"saved_search_id": saved_search_id, "sk": "META"}, ConditionExpression="owner_sub = :sub", ExpressionAttributeValues={":sub": owner_sub})`.
3. Emit `audit_event("saved_search.deleted", owner_sub, saved_search_id=saved_search_id)`.

#### `run_saved_search(saved_search_id, owner_sub) -> SavedSearchRunOut`

1. `get_saved_search(saved_search_id, owner_sub)` — ownership check included.
2. Call `_fetch_and_filter(module=ss.module, conditions=ss.filters, owner_sub=owner_sub)` (shared helper, see §4.3). The call runs inside `asyncio.to_thread` to avoid blocking the event loop during DynamoDB pagination.
3. Cap result at 500 rows (saved searches display in dashlets; a tighter cap than RPT-002's 2000-row report cap keeps dashlet responses snappy).
4. Derive `columns` from the union of keys across all returned rows, sorted alphabetically.
5. Emit `audit_event("saved_search.run", owner_sub, saved_search_id=saved_search_id, row_count=len(rows))`.
6. Return `SavedSearchRunOut`.

### 4.3 Shared `_fetch_and_filter` helper

This function is extracted from (or introduced alongside) `crm_reports.run_report` so that both reports and saved searches share one code path:

```python
# app/services/crm_reports.py  (or crm_saved_searches.py if RPT-002 not yet merged)

def _fetch_and_filter(
    module: str,
    conditions: List[ReportCondition],
    owner_sub: str,
    max_rows: int = 2000,
) -> List[Dict[str, Any]]:
    """Iterate all items for `module` accessible by `owner_sub`,
    apply client-side condition filtering, and return up to `max_rows` dicts."""
    ...
```

Module dispatch (all using `LastEvaluatedKey` pagination loops per the CLAUDE.md gotcha):

| module | Iterator |
|--------|----------|
| `tickets` | `T.tickets.query(IndexName=S.tickets_owner_index_name, KeyConditionExpression=Key("gsi1pk").eq(f"OWNER#{owner_sub}"), ...)` — the tickets table PK is `ticket_id`; per-owner access is via the `gsi1pk` owner GSI (`app/services/tickets.py:620`), NOT a `pk=OWNER#` partition |
| `contacts` | `_iter_contacts(owner_sub)` from `app/services/csv_export.py:90` |
| `billing_ledger` | `_iter_billing_entries(owner_sub)` from `app/services/csv_export.py:52` |
| `orders` | `T.orders.query(IndexName="GSI_USER", KeyConditionExpression=Key("user_id").eq(owner_sub), ...)` — the orders table PK is `order_id` with no `pk` attribute; per-user access is via the `GSI_USER` index keyed on `user_id` (`scripts/local-ddb-init.py:291`), NOT a `pk=USER#` partition |
| `subscriptions` | The subscriptions table PK is `pk`/`sk` but per-subscriber rows use `pk=SUBSCRIBER#{owner_sub}` (e.g. `app/services/syndicate_subscriptions.py:218`), NOT `pk=USER#{owner_sub}`. The helper must query `KeyConditionExpression=Key("pk").eq(f"SUBSCRIBER#{owner_sub}")` (the exact subscriber-row key prefix to use is the canonical one for the subscription surface RPT-008 targets and must be confirmed against the chosen subscription store at implementation time) |
| `questionnaire_responses` | `_iter_questionnaire_responses(questionnaire_id)` — requires `questionnaire_id` in conditions; see §5.3 |

Condition evaluation reuses `_eval_condition(item, condition)` from RPT-002. `_fetch_and_filter` applies it as a client-side post-scan filter (mirrors DynamoDB FilterExpression semantics; works on all field types without requiring a GSI per field).

## 5. Detailed Behavior & Edge Cases

### 5.1 Ownership enforcement

`get_saved_search`, `update_saved_search`, `delete_saved_search`, and `run_saved_search` all read the item first and compare `item["owner_sub"]` against the session `user_sub`. On mismatch they raise `HTTPException(403, "forbidden")`. This pattern matches the ownership check in RPT-002's `get_report`. The 403 (not 404) response is intentional: returning 404 for existing but unowned resources would leak the ID namespace.

Admin and root users (`role in {Role.ADMIN, Role.ROOT}` per `app/auth/roles.py:61`) do not bypass the ownership check for saved searches — unlike certain admin-scoped billing or KYC endpoints, saved searches are personal data with no cross-user admin use case in this ticket. If a future admin override is needed it should be a separate endpoint.

### 5.2 Row cap and performance

`run_saved_search` caps output at 500 rows (passed as `max_rows=500` to `_fetch_and_filter`). The underlying iteration loops via `LastEvaluatedKey` until this cap is reached or DynamoDB returns no further pages. This cap is deliberately lower than the RPT-002 report cap (2000) because saved search results are rendered inside a dashlet tile — not a full-page data table — and excessive rows would degrade frontend performance without adding value.

The cap applies after filtering. A table with 10,000 rows but a highly selective filter may require scanning many pages before accumulating 500 matching rows. `_fetch_and_filter` exits as soon as `len(results) >= max_rows` to bound DynamoDB read consumption.

### 5.3 Module `questionnaire_responses`

This module requires a `questionnaire_id` to be specified — it cannot enumerate responses across all questionnaires for a user. Callers must include a condition `{field: "questionnaire_id", operator: "eq", value: "<id>"}`. If no such condition is present, `_fetch_and_filter` raises `HTTPException(422, "questionnaire_responses module requires a questionnaire_id eq condition")`. This is consistent with the DynamoDB access pattern for `T.questionnaires` which is keyed by `questionnaire_id`.

### 5.4 Empty filter list

A saved search with `filters=[]` is valid; it returns all accessible rows for the module up to the 500-row cap. This is the "list all open tickets" style dashlet (combined with a single condition) as well as a "show me everything" debug view. No special handling needed — `_fetch_and_filter` with an empty conditions list simply returns all scanned rows.

### 5.5 Dashlet data ownership

When the RPT-007 `GET /ui/crm/dashboard/dashlets/{dashlet_id}/data` endpoint dispatches to the `saved_search` branch, it passes the authenticated `user_sub` to `run_saved_search`. If the `saved_search_id` in the dashlet config belongs to a different user (which should not occur through normal UI flows but could via direct API manipulation), `run_saved_search` returns 403. The dashlet renders an error state rather than crashing.

### 5.6 Saved search deleted while pinned as dashlet

When a saved search is deleted via `DELETE /ui/crm/saved-searches/{id}`, any dashlets that reference it are NOT automatically removed from dashboard layouts. This is intentional: RPT-008 is a P2 feature and the cross-table cleanup adds complexity. Instead, on the next dashlet data fetch, `get_saved_search` returns 404, which surfaces as an error state in the dashlet renderer. The frontend `SavedSearchDashlet.tsx` must handle this case by displaying a "Search not found — remove this dashlet" message. The user manually removes the stale dashlet via the RPT-006 remove endpoint.

### 5.7 Update semantics

`PATCH /ui/crm/saved-searches/{id}` supports partial updates: `name` and/or `filters` independently. The `module` field is immutable after creation — changing the module would invalidate the semantics of stored conditions. If a caller needs a different module, they must delete and recreate. The handler returns 422 if `module` appears in the PATCH body.

### 5.8 Concurrent modifications

`update_saved_search` uses a conditional `update_item` with `ConditionExpression="owner_sub = :sub"`. This guards against two concurrent PATCH requests racing on the same item (last writer wins within a single attribute, conditional prevents cross-owner write). There is no optimistic-locking version counter for saved searches; the simpler ownership condition suffices for the access patterns expected at this tier.

### 5.9 Condition field name validation

The `field` in each `ReportCondition` is not validated against a schema for the named module at write time. Validation is deferred to run time: if a condition references a non-existent field (e.g., `field="nonexistent_attr"`), `_eval_condition` simply evaluates the condition to False for all items (treating a missing key as an empty/null value), so the result is an empty result set rather than an error. This matches SuiteCRM AOR behavior and is noted in the `run` response by `row_count: 0`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

All DynamoDB operations use `T.crm_saved_searches` through the `_FloatSafeTable` proxy (`app/core/tables.py:29`), which is backed by DynamoDB Local (port 8001) in dev and real DynamoDB in prod — the boto3 endpoint is resolved from `S.ddb_endpoint_url`. There are no `if S.dev_mode` branches in the service layer. Audit events written to `T.alerts` via `audit_event` follow the same dev-log / prod-DDB path established by that function at `app/services/alerts.py:644`.

### 7.2 Idempotency

- `create_saved_search` is not idempotent by design (each call produces a new `saved_search_id`). Callers must use `list_saved_searches` to discover duplicates.
- `delete_saved_search` uses a conditional `delete_item`; a second call on an already-deleted item raises a `ConditionalCheckFailedException` which the handler converts to 404.
- `run_saved_search` is fully idempotent — it reads live data and returns a fresh result each time without side effects (no result row is written).

### 7.3 Security

**Ownership enforcement**: Every mutating and read operation checks `item["owner_sub"] == user_sub` before proceeding. The check is at the service layer so it cannot be bypassed by alternative router paths.

**CSRF**: `POST`, `PATCH`, and `DELETE` requests via cookie auth require the `x-csrf-token` header matching the session's stored `csrf_token` and the `ui_csrf` cookie. This is enforced by `require_ui_session` at `app/services/sessions.py:330`; no additional code is needed in the router.

**CSV injection**: The `_fetch_and_filter` helper returns raw DynamoDB item dicts. The `/run` endpoint serialises these as JSON (not CSV). No CSV injection risk at the API layer. If a downstream feature exposes saved search results as CSV (e.g., via RPT-009), it must pass values through `_sanitize_csv_field` from `app/services/csv_export.py:43`.

**Filter value injection**: Condition `value` strings are used only in client-side `_eval_condition` comparisons against DynamoDB item attributes — they are never interpolated into DynamoDB `FilterExpression` strings or raw queries. There is no injection vector.

**Module allowlist**: The `module` field is validated by a Pydantic `pattern` regex on `SavedSearchCreateIn` — only the six enumerated values are accepted. Unknown modules return 422 before any DynamoDB access occurs.

**Audit trail**: `saved_search.created`, `saved_search.deleted`, and `saved_search.run` events are written to `T.alerts` via `audit_event`. This provides a complete trail for compliance review and correlates with the saved-search `saved_search_id` in the `fields` dict.

## 8. Backward Compatibility & Migration

### 8.1 Additive only

RPT-008 introduces new files (`app/services/crm_saved_searches.py`, `app/routers/crm_saved_searches.py`) and appends a branch to `app/services/crm_dashlet_data.py`. No existing file has lines removed or semantics changed. With `CRM_REPORTS_ENABLED=0` the platform is byte-for-byte equivalent to the pre-RPT-008 state at runtime.

### 8.2 DynamoDB tables

The `crm_saved_searches` table is created by RPT-001's `scripts/local-ddb-init.py` additions. In dev, `just restart` recreates all tables from scratch; no migration is needed. In production, the table must be created via `aws dynamodb create-table` before the RPT-008 code is deployed. The RPT-001 spec describes this as a one-time pre-deployment step; RPT-008 adds no additional table schema changes.

### 8.3 `app/models.py` additions

`SavedSearchCreateIn`, `SavedSearchUpdateIn`, `SavedSearchOut`, and `SavedSearchRunOut` are new models. If `ReportCondition` is already present from RPT-002, it is reused unchanged. If RPT-002 is not yet merged, `ReportCondition` is declared here and must be deduplicated when RPT-002 lands (move declaration above all callers; both classes reference the same definition).

### 8.4 `crm_dashlet_data.py` extension

The `saved_search` branch is guarded by `elif dashlet_type == "saved_search":` with a local import of `run_saved_search`. The local import avoids a circular dependency (the dashlet data module is imported by the dashboard router, and the saved searches module should not import the dashboard module). If RPT-007 has not yet been merged, this extension is deferred until RPT-007 is available.

## 10. Open Questions / Assumptions

1. **RPT-007 merge order**: This spec assumes RPT-007 (`crm_dashlet_data.py`) is merged before RPT-008 ships. If the two are developed in parallel, the `saved_search` branch should be guarded by a `hasattr` check or the file created fresh by RPT-008 with only the `saved_search` branch, to be merged with the other branches when RPT-007 lands.

2. **`_fetch_and_filter` ownership**: The spec places this helper in `app/services/crm_reports.py` (RPT-002 domain). If RPT-002 is not yet merged when RPT-008 is implemented, the helper should live temporarily in `app/services/crm_saved_searches.py` and be moved (not copied) to `crm_reports.py` when RPT-002 lands. Never fork — one canonical implementation.

3. **Admin cross-user access**: The spec deliberately excludes admin-role bypass for ownership. If a compliance use case emerges (e.g., root administrator auditing user-defined saved searches), a separate admin endpoint should be proposed rather than relaxing the ownership check on user-facing endpoints.

4. **Stale dashlet UX**: §5.6 describes the broken-reference behavior when a saved search is deleted while pinned. The exact error UX (error message text, icon, action button) is deferred to the frontend implementation. The API contract is fixed: 404 from `/run`.

5. **Field enumeration**: `SavedSearchRunOut.columns` is derived from the union of keys in the returned rows. If different rows have different sparse attributes (common in DynamoDB), the column list may vary across runs. This is noted in the API response — callers must not assume a fixed schema per module.

6. **Rate limiting**: This spec does not add per-user rate limiting on `/run`. RPT-007's catalogue dashlets are also unrated. If DashboardPage renders all dashlet tiles simultaneously and each calls `/run`, a user with 20 `saved_search` dashlets would issue 20 DDB scans on page load. A follow-up ticket should add `_bucket_limit` (from `app/services/rate_limit.py:60`) on `/run` — recommended: 30 runs per user per 60 seconds. This is not a blocker for the P2 RPT-008 release.
