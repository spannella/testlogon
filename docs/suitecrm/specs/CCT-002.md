# CCT-002 — Account hierarchy (parent account / member organizations)

**Type:** Feature | **Priority:** P1 | **Estimate:** 2 days
**Milestone:** CRM Contacts & Accounts — Batch 1
**Depends on:** CCT-001, PTY-003, PTY-006, PTY-008, PTY-011, PTY-012
**Flag:** `PARTY_CRM_ORG_ACCOUNTS_ENABLED` (same flag as CCT-001; default OFF)

---

## 1. Summary & Goal

CCT-002 adds a SuiteCRM-style **account hierarchy** to the party/CRM surface: any
`PARTY_GROUP` account can designate exactly one other `PARTY_GROUP` as its parent
organization. The resulting tree (up to 10 levels deep) is navigable in both directions —
ancestor chain upward and immediate children downward — without introducing any new DynamoDB
tables or GSIs. The feature reuses the existing `PARENT_ORG` relationship type (added to
`CrmRelationshipType` by this ticket), the `create_relationship` / `delete_relationship`
primitives from PTY-006, and the `_assert_org_admin` guard from PTY-008.

On the read side, `CrmOrgAccountOut` (defined in PTY-003 at
`docs/ofbiz/specs/PTY-003.md:537-545` and extended by CCT-001) gains two additive fields —
`parent_org_party_id` and `child_org_count` — so the existing `GET /ui/party/orgs/{id}`
endpoint surfaces hierarchy information without a separate call.

Three new HTTP endpoints are added under the existing `/ui/party/orgs/{org_party_id}` group
established by PTY-012:

- `PUT  /ui/party/orgs/{org_party_id}/parent`  — set (or replace) parent
- `DELETE /ui/party/orgs/{org_party_id}/parent` — remove parent link
- `GET  /ui/party/orgs/{org_party_id}/hierarchy` — read ancestor chain and/or child list

With `PARTY_CRM_ORG_ACCOUNTS_ENABLED` off (the default), all three routes return HTTP 503
and the platform is byte-for-byte unchanged.

### 2.4 Relationship storage — PTY-006 primitives

PTY-006 establishes the full relationship-edge pattern on the `party` single table
(`docs/ofbiz/specs/PTY-006.md:147-210`):

- **Primary row:** `PK=PARTY#{from_party_id}`, `SK=REL#{rel_type}#{to_party_id}`
- **Mirror row:** `PK=PARTY#{to_party_id}`, `SK=MIRROR#{rel_type}#{from_party_id}`,
  `GSI3PK=REL_TO#{to_party_id}`, `GSI3SK=REL#{rel_type}#{from_party_id}`

Both rows are written and deleted atomically via `transact_write_items`
(`docs/ofbiz/specs/PTY-006.md:267-313`). The `PARENT_ORG` relationship slots directly into
this pattern — `from_party_id` = child org, `to_party_id` = parent org — with no schema
change.

For `PARENT_ORG`, the GSI3 mirror row means:
- **Listing children of a parent** — query `GSI3PK=REL_TO#{parent_org_id}` and filter for
  `SK begins_with "MIRROR#PARENT_ORG#"` (base-table query under the parent's partition).
- **Finding the parent of a child** — single `get_item` on the child's primary row
  `PK=PARTY#{child_id}`, `SK=REL#PARENT_ORG#{parent_id}` (one row; only one parent allowed).

## 4. API / Service Design

### 4.1 Service functions — `app/services/party.py`

Two new public functions appended after the PTY-008 org-account functions. Neither function
modifies existing function signatures.

#### `set_parent_org`

```python
def set_parent_org(
    child_org_id: str,
    parent_org_id: str,
    *,
    actor_party_id: str,
) -> Dict[str, Any]:
    """Set or replace the parent org for child_org_id.

    Validates both parties are PARTY_GROUP, validates no circular chain
    (walks PARENT_ORG edges upward to depth 10), removes any existing
    PARENT_ORG edge, then writes a new one via create_relationship.

    Returns the primary relationship row dict.
    Raises HTTPException(400, "circular_hierarchy") if a cycle is detected.
    Raises HTTPException(403) if actor is not ORG_ADMIN on child_org_id.
    Raises HTTPException(404, "org_not_found") if either org is absent.
    Raises HTTPException(422, "party_type_not_group") if either party
        is not PARTY_GROUP.
    """
```

Step-by-step contract:

1. **Assert actor is ORG_ADMIN on child org:** call
   `_assert_org_admin(child_org_id, actor_party_id)` — raises `HTTPException(403)` if not.

2. **Resolve both orgs:** `get_party(child_org_id)` and `get_party(parent_org_id)` — raise
   `HTTPException(404, "org_not_found")` if either is absent or has `status=MERGED`.

3. **Validate both are `PARTY_GROUP`:** inspect the `party_type` attribute on each META row.
   Raise `HTTPException(422, "party_type_not_group")` if either is not `PARTY_GROUP`.

4. **Reject self-loop:** if `child_org_id == parent_org_id`, raise
   `HTTPException(400, "circular_hierarchy")` (a one-node loop is the degenerate case).

5. **Circular-chain check** (walk up to depth 10 from `parent_org_id`):

   ```python
   visited = {child_org_id}
   cursor_id = parent_org_id
   for _ in range(10):
       resp = T.party.get_item(
           Key={
               "PK": f"PARTY#{cursor_id}",
               "SK": f"REL#PARENT_ORG#*",   # see note below
           }
       )
   ```

   Because the exact `to_party_id` of the parent's own parent is not known in advance, this
   walk uses a `query` rather than `get_item`. For each `cursor_id`, query:

   ```python
   resp = T.party.query(
       KeyConditionExpression=Key("PK").eq(f"PARTY#{cursor_id}") &
                              Key("SK").begins_with("REL#PARENT_ORG#"),
       Limit=1,
   )
   items = resp.get("Items", [])
   ```

   If the query returns no item, the chain terminates (no further ancestor). If it returns an
   item, extract `to_party_id` as `next_id`. If `next_id in visited`, raise
   `HTTPException(400, "circular_hierarchy")`. Add `cursor_id` to `visited` and advance
   `cursor_id = next_id`. After 10 iterations without finding a cycle or terminus, raise
   `HTTPException(400, "circular_hierarchy")` (depth-limit exceeded).

6. **Remove any existing parent:** query the child's existing `PARENT_ORG` primary row:

   ```python
   resp = T.party.query(
       KeyConditionExpression=Key("PK").eq(f"PARTY#{child_org_id}") &
                              Key("SK").begins_with("REL#PARENT_ORG#"),
       Limit=1,
   )
   ```

   If found, call `delete_relationship(child_org_id, existing_to_party_id, "PARENT_ORG")`.

7. **Write new edge:** call
   `create_relationship(child_org_id, parent_org_id, "PARENT_ORG",
   correlation_id=f"PARENT_ORG:{child_org_id}:{parent_org_id}")`.
   The `correlation_id` makes the write idempotent on retry.

8. **Emit audit event:**

   ```python
   audit_event(
       "party_parent_org_set",
       actor_party_id,
       None,
       child_org_id=child_org_id,
       parent_org_id=parent_org_id,
   )
   ```

9. **Return** the primary relationship row dict.

#### `get_org_hierarchy`

```python
def get_org_hierarchy(
    org_party_id: str,
    *,
    direction: str = "both",   # "children" | "ancestors" | "both"
) -> Dict[str, Any]:
    """Return ancestor chain and/or immediate children for org_party_id.

    direction="ancestors"  — walks PARENT_ORG primary rows upward; max depth 10.
    direction="children"   — queries MIRROR rows under org_party_id's partition
                             for SK begins_with "MIRROR#PARENT_ORG#"; O(n children).
    direction="both"       — returns both; two sequential queries.

    Returns:
        {
          "ancestors": List[CrmRelationshipOut-compatible dict],
          "children":  List[CrmRelationshipOut-compatible dict],
        }
    Both lists are empty lists when direction excludes that side.
    """
```

**Ancestor walk** (for `direction in ("ancestors", "both")`):
- Initialize `ancestors = []`, `cursor_id = org_party_id`.
- Repeat up to 10 times: query `PK=PARTY#{cursor_id}` + `SK begins_with "REL#PARENT_ORG#"`,
  `Limit=1`. If no row, stop. Else append the item (coerced to `CrmRelationshipOut`-compatible
  dict) to `ancestors` and set `cursor_id = item["to_party_id"]`.
- Returns list in order from immediate parent to most-distant ancestor.

**Children query** (for `direction in ("children", "both")`):
- Query the base table: `PK=PARTY#{org_party_id}` + `SK begins_with "MIRROR#PARENT_ORG#"`.
- Loop via `LastEvaluatedKey` until exhausted (DynamoDB FilterExpression does not reduce page
  size per CLAUDE.md; base-table query with no filter is exact).
- For each mirror row, reconstruct the outbound edge shape using `from_party_id` (= child)
  and `to_party_id` (= this org) from the stored attributes.
- Returns list of `CrmRelationshipOut`-compatible dicts (all immediate children, unordered).

**Note on the children query:** the mirror row shape from PTY-006 §3.2 stores `from_party_id`
and `to_party_id` on the mirror item, so the child's `party_id` can be read directly as
`item["from_party_id"]` without a secondary lookup.

#### Projection helpers — `get_org_account` update

The existing `get_org_account(org_party_id) -> dict` function (added by PTY-008) is extended
to populate the two new CCT-002 fields on `CrmOrgAccountOut`:

- **`parent_org_party_id`:** query the org's own partition for `SK begins_with
  "REL#PARENT_ORG#"`, `Limit=1`. If found, take `item["to_party_id"]`. If absent, `None`.
- **`child_org_count`:** query the org's own partition for `SK begins_with
  "MIRROR#PARENT_ORG#"` and count the results (loop until `LastEvaluatedKey` is exhausted).

Both lookups are added as two additional DynamoDB queries within `get_org_account`. They are
gated on `S.party_crm_org_accounts_enabled` being true (the existing flag gate on the org
endpoint covers them). When the flag is off the endpoint never fires and these queries never
run.

#### `PUT /ui/party/orgs/{org_party_id}/parent`

```python
@router.put("/orgs/{org_party_id}/parent", status_code=200)
async def set_parent_org_endpoint(
    org_party_id: str,
    body: CrmSetParentOrgIn,
    ctx: dict = Depends(require_ui_session),
) -> CrmRelationshipOut:
    _check_org_accounts_flag()
    actor_party_id = _resolve_person_party(ctx["user_sub"])   # PTY-012 helper
    try:
        item = party_svc.set_parent_org(
            child_org_id=org_party_id,
            parent_org_id=body.parent_org_party_id,
            actor_party_id=actor_party_id,
        )
    except ValueError as exc:
        raise HTTPException(422, str(exc)) from exc
    return _item_to_rel_out(item)
```

Returns `CrmRelationshipOut` for the new `PARENT_ORG` edge. HTTP 200 (not 201) because the
operation is idempotent (PUT semantics; the edge may be replacing an existing one). If the
child had no prior parent this is a first-time write; if it did the old edge is atomically
replaced. Either way the new edge state is fully represented by the 200 response.

#### `DELETE /ui/party/orgs/{org_party_id}/parent`

```python
@router.delete("/orgs/{org_party_id}/parent", status_code=204)
async def delete_parent_org_endpoint(
    org_party_id: str,
    ctx: dict = Depends(require_ui_session),
):
    _check_org_accounts_flag()
    actor_party_id = _resolve_person_party(ctx["user_sub"])
    _assert_org_admin(org_party_id, actor_party_id)
    # Find existing parent row
    resp = T.party.query(
        KeyConditionExpression=Key("PK").eq(f"PARTY#{org_party_id}") &
                               Key("SK").begins_with("REL#PARENT_ORG#"),
        Limit=1,
    )
    items = resp.get("Items", [])
    if not items:
        return  # Already absent — idempotent 204
    parent_id = items[0]["to_party_id"]
    party_svc.delete_relationship(org_party_id, parent_id, "PARENT_ORG")
    audit_event(
        "party_parent_org_deleted",
        actor_party_id,
        None,
        child_org_id=org_party_id,
        parent_org_id=parent_id,
    )
```

No request body. Returns 204 No Content on success. Idempotent: if no parent link exists,
returns 204 silently (matches `delete_relationship`'s own no-op-on-absent semantics from
PTY-006 §5.4). The router imports `audit_event` directly from
`app.services.alerts` for the extra event; `delete_relationship` also emits its own
`"party_relationship_deleted"` audit event, so the DELETE path produces two audit events —
the low-level one from PTY-006 and the CCT-002-specific semantic one.

#### `GET /ui/party/orgs/{org_party_id}/hierarchy`

```python
@router.get("/orgs/{org_party_id}/hierarchy")
async def get_org_hierarchy_endpoint(
    org_party_id: str,
    direction: str = "both",    # "children" | "ancestors" | "both"
    ctx: dict = Depends(require_ui_session),
) -> CrmOrgHierarchyOut:
    _check_org_accounts_flag()
    if direction not in ("children", "ancestors", "both"):
        raise HTTPException(422, "direction must be 'children', 'ancestors', or 'both'")
    result = party_svc.get_org_hierarchy(org_party_id, direction=direction)
    return CrmOrgHierarchyOut(
        org_party_id=org_party_id,
        direction=direction,
        ancestors=[_item_to_rel_out(r) for r in result["ancestors"]],
        children=[_item_to_rel_out(r) for r in result["children"]],
    )
```

Any authenticated party member may call `GET /hierarchy` — no ORG_ADMIN requirement. The
hierarchy graph is not PII and visibility matches the existing `GET /orgs/{id}` endpoint.

## 5. Detailed Behavior & Edge Cases

### 5.1 One parent at a time

A `PARTY_GROUP` may have at most one `PARENT_ORG` edge. This is enforced structurally: a
`query` on `PK=PARTY#{child}` + `SK begins_with "REL#PARENT_ORG#"` returns at most one row
(because the SK encodes the parent's `party_id` and only one parent is allowed). Step 6 of
`set_parent_org` deletes any existing edge before writing the new one. The delete and the
create are two separate DynamoDB operations (not a single transaction), but the ordering is
safe because:
- After the delete and before the create, no parent exists — a window of no-parent is
  acceptable (the operation is initiated by ORG_ADMIN, not by external users).
- If the service crashes between delete and create, a retry of `set_parent_org` will find
  no existing edge (step 6 is a no-op) and proceed to step 7 (create), converging correctly.

### 5.2 Circular hierarchy detection

The depth-10 walk in `set_parent_org` step 5 prevents directed cycles. Consider three orgs:
A, B, C where the current state is A → B → C (A is child of B, B is child of C). Attempting
to set C's parent to A would walk: start at A (the new proposed parent), find A's parent = B,
find B's parent = C, find `child_org_id` = C in `visited` → raise
`HTTPException(400, "circular_hierarchy")`.

The depth limit of 10 also prevents arbitrarily deep chains from consuming unbounded DynamoDB
read capacity. If an org's hierarchy is already 10 levels deep, adding an 11th level is
rejected. This is a conscious product constraint matching SuiteCRM's default hierarchy depth.

### 5.3 `delete_relationship` + `create_relationship` are individually idempotent

If `set_parent_org` is retried after partial failure:
- If the delete completed but the create did not: step 6 finds no existing edge and skips;
  step 7 calls `create_relationship` which writes the new edge.
- If the delete did not complete: step 6 finds the old edge and deletes it (correct).
- If both completed: step 6 finds a `REL#PARENT_ORG#{new_parent}` row (the new edge from
  the previous attempt); the `correlation_id` makes the `create_relationship` call in step
  7 idempotent (returns the existing row without a second write).

### 5.4 `child_org_count` is computed at read time

`child_org_count` in `CrmOrgAccountOut` is derived by counting `MIRROR#PARENT_ORG#*` rows
under the org's partition at GET time, not stored as a pre-aggregated counter. This means it
is always accurate but involves a full partition scan for that SK prefix. For orgs with
hundreds of children (large enterprise hierarchies) this may read multiple DynamoDB pages;
the loop over `LastEvaluatedKey` ensures completeness. If this becomes a performance concern
in a future milestone, a denormalized counter can be added to the META row — that optimization
is out of scope for CCT-002.

### 5.5 Non-PARTY_GROUP parties rejected at service layer

`set_parent_org` validates `party_type == "PARTY_GROUP"` for both parties. `PERSON` parties
cannot be in a parent-child org relationship. Attempting to set a `PERSON` party as either
child or parent raises `HTTPException(422, "party_type_not_group")`. This is enforced in the
service layer (step 3) not by the Pydantic model, matching the PTY-006 approach for
`relationship_type` validation (inline set constant, no circular import).

### 5.6 Missing parent in `get_org_hierarchy` ancestors walk

If the stored `to_party_id` on a `PARENT_ORG` edge does not correspond to an existing META
row (e.g. the parent was deleted or status=MERGED), the ancestor walk still includes the
edge's `from_party_id` / `to_party_id` fields from the relationship row itself. The walk
continues up by querying `PK=PARTY#{to_party_id}` for a further `PARENT_ORG` edge — if none
is found the walk terminates normally. The caller receives edges that may reference an absent
org; the caller is responsible for resolving party details separately. This "dead edge"
scenario is rare (CCT-005 merge marks losers as MERGED but does not delete relationship rows)
and is acceptable for Phase 1.

### 5.7 Flag-off behaviour

When either `S.party_crm_enabled` or `S.party_crm_org_accounts_enabled` is `False`:
- All three CCT-002 endpoints return `HTTP 503`.
- The two CCT-002 service functions (`set_parent_org`, `get_org_hierarchy`) are importable
  but never called via the normal request path.
- `get_org_account` (PTY-008) skips the two new `parent_org_party_id` / `child_org_count`
  queries (it is also gated by the same flag).
- Zero DynamoDB reads or writes are triggered.
- All other subsystems — contacts, billing, messages, calendar — are byte-for-byte unchanged.

### 5.8 ORG_ADMIN check on DELETE

The DELETE endpoint calls `_assert_org_admin` directly in the router before querying for the
existing parent edge. This means a non-admin caller receives `403` immediately, without the
overhead of a parent-edge lookup.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

`set_parent_org` and `get_org_hierarchy` contain no `S.dev_mode` branch. Every DynamoDB
operation goes through `T.party` (the `_FloatSafeTable` resource wrapper) or the low-level
`transact_write_items` client pattern from PTY-006 — both of which already resolve to
`http://localhost:8001` (DynamoDB Local) in dev and real AWS DynamoDB in prod via the shared
`ddb` resource's endpoint metadata (`app/core/aws.py:6`: `ddb = ddb_resource()`). The
`_ddb_client()` helper from PTY-006 (`docs/ofbiz/specs/PTY-006.md:388-414`) is inherited
without modification. This is full SECOPS-007 parity: same code path in both environments.

### 7.2 Idempotency

- **`set_parent_org`:** idempotent on retry. The delete of the old edge is silent-no-op if
  absent; the `create_relationship` call uses a `correlation_id` so the structural PK/SK
  conditional put is idempotent. A repeated PUT with the same `parent_org_party_id` for a
  child that already has that parent will: find the existing edge in step 6 (but the existing
  edge matches the new desired parent, so there is nothing to delete), then call
  `create_relationship` which returns the existing row without writing. Net effect: no-op.
- **`DELETE /parent`:** idempotent; 204 returned whether a parent existed or not.
- **`GET /hierarchy`:** read-only; trivially idempotent.

### 7.3 Security

- **No PII in DynamoDB keys:** all PK/SK values contain only `party_id` (opaque 32-char hex),
  the string `PARENT_ORG`, and static prefixes. No email, phone, or name appears in any key.
- **Authorization enforcement:** mutating endpoints (PUT, DELETE) require ORG_ADMIN on the
  child org (enforced by `_assert_org_admin` from PTY-008, `docs/ofbiz/specs/PTY-008.md:340`).
  A non-admin authenticated session receives `403`. Unauthenticated requests receive `401`
  from `require_ui_session` before any handler logic runs.
- **No cross-org privilege escalation:** the `org_party_id` path parameter is always the
  child (the org the actor administers). An actor cannot set the parent for an org they do
  not administer.
- **No money-out path:** parent-org relationships carry no billing data. No ledger entry, no
  refund, no Stripe/PayPal/CCBill call is involved in this feature.
- **Input length guards:** `party_id` values in the request body are treated as opaque
  identifiers. The `create_relationship` service function caps them at 64 chars
  (`docs/ofbiz/specs/PTY-006.md:268-271`) before constructing SK values, preventing unbounded
  key injection.
- **Depth limit prevents DoS:** the 10-iteration limit on both the circular-check walk and
  the ancestor walk bounds DynamoDB read consumption to at most 10 `query` calls per request.
- **Audit trail:** `set_parent_org` emits `"party_parent_org_set"` and the underlying
  `create_relationship` emits `"party_relationship_created"` (both via
  `app/services/alerts.py:644`). DELETE emits `"party_parent_org_deleted"` and
  `"party_relationship_deleted"`. All four events land in `T.alerts` for operational
  visibility.

## 8. Backward Compatibility & Migration

### 8.1 Existing surfaces unchanged

`app/routers/contacts.py` and the `Contacts` DynamoDB table (`scripts/local-ddb-init.py:691`)
are byte-for-byte unchanged. The `party` table's `GSI3` index was provisioned by PTY-002; CCT-002
writes `PARENT_ORG` mirror rows with `GSI3PK=REL_TO#{parent_id}` using the same established
pattern as `GROUP_MEMBER` and `OWNER` edges — no index schema change.

### 8.2 `CrmRelationshipType` enum extension

Adding `PARENT_ORG` to `CrmRelationshipType` is a backward-compatible enum extension in Pydantic
v2. Existing callers that only produce or consume the four prior values (`EMPLOYMENT`,
`GROUP_MEMBER`, `CONTACT_REL`, `OWNER`) are unaffected. Code paths that switch/match on this
enum will receive unknown-value errors only if they explicitly `case` the new value without a
default — a compile-time issue surfaced at code review, not a runtime regression.

`delete_relationship` and `list_relationships` in PTY-006 validate `relationship_type` against
`_VALID_REL_TYPES` (an inline plain set defined in `app/services/party.py` per
`docs/ofbiz/specs/PTY-006.md:593-606` — definition at line 597). CCT-002 must update this set to
include `"PARENT_ORG"`:

```python
_VALID_REL_TYPES = {
    "EMPLOYMENT", "GROUP_MEMBER", "CONTACT_REL", "OWNER", "PARENT_ORG"
}
```

### 8.3 `CrmOrgAccountOut` extension

Adding `parent_org_party_id: Optional[str] = None` and `child_org_count: int = 0` to
`CrmOrgAccountOut` is backward-compatible: existing deserialization code (PTY-013 TypeScript
types, PTY-014 frontend page) receives these fields as `null` / `0` for any org that has no
parent and no children, which matches the pre-CCT-002 state of every org.

### 8.4 No data migration

There are no pre-existing `PARENT_ORG` rows in any table (the `party` table itself does not
exist until PTY-002 is deployed). No backfill or migration script is required.

## 10. Open Questions / Assumptions

1. **CCT-001 merged before CCT-002.** This spec assumes `CrmOrgAccountOut` already carries
   the five CCT-001 business-metadata fields when CCT-002 is implemented. If CCT-001 is
   delayed, CCT-002 can still be merged independently — the two new fields
   (`parent_org_party_id`, `child_org_count`) are added to the same model without conflicting
   with the CCT-001 fields.

2. **`_VALID_REL_TYPES` frozenset in `app/services/party.py`.** PTY-006 defines this constant
   inline to avoid circular imports (`docs/ofbiz/specs/PTY-006.md:600-607`). CCT-002 adds
   `"PARENT_ORG"` to this set. The implementer must locate this constant (not a model import)
   and extend it. If PTY-006 is not yet merged, CCT-002 introduces the frozenset at that time.

3. **`get_org_account` is owned by PTY-008.** Adding the parent/child projection queries
   to that function is a modification of PTY-008's code. The implementer must coordinate
   or land both in the same PR to avoid conflicts.

4. **Child count is eventually consistent with parent-set operations.** Between the delete
   of the old parent edge (step 6) and the creation of the new one (step 7), a concurrent
   `GET /ui/party/orgs/{parent}` would see a stale `child_org_count`. This is acceptable for
   Phase 1 (the window is sub-millisecond in practice).

5. **`_resolve_person_party` helper.** This helper is defined by PTY-012
   (`docs/ofbiz/specs/PTY-012.md:80-85`). CCT-002 calls it in the PUT and DELETE endpoints
   without redefining it. If PTY-012 has not yet merged, CCT-002 must include this helper.

6. **`direction` parameter default of `"both"`.** Returning both ancestors and children in
   a single call means up to 11 DynamoDB queries (10-level walk + 1 children query with
   possible multi-page loop). For orgs with shallow hierarchies (the common case) this is
   2-3 queries total. A depth-limited ancestor walk cap of 10 bounds the maximum.

7. **`get_org_hierarchy` is not paginated.** The children list is returned in full. If an
   org has hundreds of immediate children (e.g. a large franchisor), the children query loops
   over all pages and returns the full list. A `cursor`-paginated variant can be added in a
   future milestone using the `encode_cursor` / `decode_cursor` pattern from
   `app/core/cursor.py:94,103`.
