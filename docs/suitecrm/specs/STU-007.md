# STU-007 — Admin scheduler/cron-job management — enable/disable/trigger API

**Type:** Feature  **Priority:** P1  **Estimate:** 2 days  
**Ticket source:** `docs/suitecrm/CRM_SECURITY_STUDIO_TICKETS.md`, section "STU-007"  
**Feature flag:** `CRM_STUDIO_ENABLED` (default `"0"`) — routes 404 while flag is off

---

## 1. Summary & Goal

STU-007 closes the operational gap identified in the CRM gap analysis: the platform has no way for an admin to durably disable or immediately trigger a background scheduler without restarting the process. Today every background task is wired at startup unconditionally (or via a single dedicated env-var flag) and there is no central API surface for enable/disable toggles or manual runs that survive a process restart.

This ticket adds:

1. **`app/services/job_config.py`** — a thin DynamoDB overlay on top of the existing in-memory `job_registry` (`app/services/job_registry.py`). Persists per-job enable/disable state under the `billing_config` table's single-table design pattern, keyed `pk="JOB_CONFIG"`, `sk="JOB#{task_name}"`.
2. **Three new endpoints in `app/routers/admin_jobs.py`** — `POST /enable`, `POST /trigger`, and `GET /config` — all auth-gated and all returning 404 when `CRM_STUDIO_ENABLED` is off.
3. **A `KNOWN_JOBS` extension** — `app/services/job_dashboard.py:KNOWN_JOBS` (line 54) is extended to include the jobs registered by background-task modules (e.g. `audit_export_worker`, `audit_export_scheduler`, `compute_billing_timer`, `newsfeed_recsys_refresh`).
4. **A reference startup integration** in `app/services/audit_export_worker.py:start_audit_export_worker_task` (lines 129–139) that consults `is_job_enabled("audit_export_worker")` before starting the loop.

The change is purely additive and default-OFF. With `CRM_STUDIO_ENABLED=0`, the platform is byte-for-byte identical in behaviour to its pre-ticket state.

## 2. Context & Current State

### 2.1 In-memory job registry (no persistence)

`app/services/job_registry.py` is a pure in-memory registry backed by a module-level `_tasks: Dict[str, Dict]` dict protected by a `threading.Lock` (lines 19–21). `register_task(name, poll_interval_seconds, enabled, description)` writes an initial entry (lines 23–55); `report_poll` and `report_error` update counters (lines 58–107); `get_all_tasks` adds staleness detection (lines 110–137). There is no DynamoDB write, no persistence across restarts, and no enable/disable API. The registry rebuilds from scratch on every process start — by design (per the file's docstring, lines 1–10).

### 2.2 Existing admin jobs router

`app/routers/admin_jobs.py` (lines 1–108) exposes:
- `GET /ui/admin/jobs/status` — in-memory health snapshot + scheduled-action queue depths (line 22).
- `GET /ui/admin/jobs/task/{task_name}` — single-task detail (line 65).
- `GET /ui/admin/jobs/failed` — failed scheduled actions (line 76).
- `POST /ui/admin/jobs/retry/{action_id}` — reschedule a failed action (line 90).

Auth is enforced via a local `_require_admin` helper at line 15 that checks `ctx["role"]` for `"root"` or `"admin"`. This helper is not using `app/auth/policy.require_admin_or_root` (which returns an `AuthenticatedUser`). The new endpoints added in this ticket will use `app/auth/policy.require_admin_or_root` and `app/auth/policy.require_root` (defined at `app/auth/policy.py:67` and `app/auth/policy.py:63`) for consistency with the rest of the codebase.

### 2.3 Job dashboard and KNOWN_JOBS

`app/services/job_dashboard.py` (line 54) defines `KNOWN_JOBS`: a static dict mapping job names to metadata including `run_now_safe` and `run_now` (a dotted import path). `app/routers/job_dashboard.py` already exposes `POST /ui/admin/jobs/run-now/{job_name}` (line 85) gated by `require_root`, which calls `svc.trigger_run_now` (line 92). That path only works for jobs in `KNOWN_JOBS` with `run_now_safe: True`. The new `POST /trigger` endpoint in this ticket is a complementary path that invokes the per-task registered callback (not the `run_now` dotted-path pattern), making it work for tasks not yet in `KNOWN_JOBS`.

### 2.4 Startup task hooks and the inconsistency they create

Background tasks follow two patterns today:

**Pattern A — env-var flag only** (`app/services/audit_export_worker.py:129–139`):
```python
async def start_audit_export_worker_task() -> None:
    if S.audit_export_worker_enabled:
        asyncio.create_task(run_audit_export_worker_loop())
    else:
        register_task("audit_export_worker", ..., enabled=False, ...)
```
The env-var check is frozen at startup; disabling requires a redeploy.

**Pattern B — no flag at all** (e.g. `app/services/compute_billing.py:669–677`):
```python
def start_compute_billing_timer_task() -> None:
    if S.compute_billing_enabled:
        asyncio.ensure_future(run_compute_billing_timer())
```
Same problem: no runtime toggle, no per-task DDB override.

After this ticket, both patterns gain a DDB consultation step: `is_job_enabled(task_name)` is evaluated before the existing env-var flag, giving admins a live override that persists across restarts.

### 2.5 Billing config as the pattern to replicate

`app/services/billing_config.py` (lines 38–54) uses `billing_config` table (`T.billing_config`) with `pk="BILLING_CONFIG"`, `sk="CURRENT"` for live config and `sk="AUDIT#..."` for change history. It keeps a module-level `_config_cache` / `_cache_ts` with a 60-second TTL and an `invalidate_cache()` function (lines 46–57). The `job_config` service follows this same pattern, sharing the same `billing_config` table by using a distinct partition key `pk="JOB_CONFIG"` (the table is a general-purpose single-partition config store, PK=`pk`, SK=`sk`; see `scripts/local-ddb-init.py:78`).

**No new DynamoDB table is required for STU-007.** The existing `billing_config` table at `T.billing_config` (`app/core/tables.py:334`) is reused under the `JOB_CONFIG` partition. This follows the ticket specification and the single-table design principle applied throughout the codebase (e.g. `app_single_table` hosts search history, poll state, relationship instances, etc.).

### 2.6 Manual trigger: existing vs. new

`app/routers/job_dashboard.py:85` (`POST /ui/admin/jobs/run-now/{job_name}`) already handles manual triggers for jobs in `KNOWN_JOBS` with `run_now_safe: True`, using a dotted-path import. The new `POST /ui/admin/jobs/task/{task_name}/trigger` endpoint in this ticket uses a separate callback registry (a module-level dict in `job_config.py`) populated at startup by each background-task module. This second mechanism is intentional: it fires the actual polling function (or a wrapped one-shot version) for tasks that may not yet be listed in `KNOWN_JOBS`, without requiring a `run_now` entry in the static dict. Both mechanisms remain in place; they are additive, not replacements.

## 3. Data Model

### 3.1 Reuse: `billing_config` table

No new DynamoDB table. All job config rows live in the existing `billing_config` table (`T.billing_config`, `app/core/tables.py:334`), whose `TableDef` is at `scripts/local-ddb-init.py:78`:

```
Table: billing_config
  PK: pk (S)
  SK: sk (S)
  (no GSIs; single-partition config store)
```

### 3.2 Job config row

One row per job under the `JOB_CONFIG` partition:

```
pk  = "JOB_CONFIG"          (string, partition constant)
sk  = "JOB#{task_name}"     (string, e.g. "JOB#audit_export_worker")

task_name    : str           — matches the key used in register_task()
enabled      : bool          — false = disabled
updated_by_sub : str         — actor sub who last changed the row
updated_at   : int (N)       — Unix timestamp of last change
```

`updated_at` is a plain item attribute stored as a DynamoDB Number (`Decimal`). No GSI is needed for this table because jobs are looked up by exact `pk`+`sk` (`get_item`), and the full scan of all `JOB#` rows on `GET /config` uses a `begins_with("JOB#")` key-condition query on the partition.

### 3.3 Audit rows

Each enable/disable toggle also writes an audit row under the same partition:

```
pk  = "JOB_CONFIG"
sk  = "AUDIT#{ts:010d}#{event_id}"  (string, same pattern as billing_config.py:377)

admin_sub    : str
task_name    : str
enabled      : bool
created_at   : int (N)
```

These rows are never read by the service layer; they exist for compliance and for future admin-audit-trail queries (mirrors `billing_config.py:364–382`).

## 4. API / Service Design

### 4.1 Service: `app/services/job_config.py` (new file)

```python
# Storage constants
_PK = "JOB_CONFIG"
_SK_CURRENT = lambda name: f"JOB#{name}"

# In-memory TTL cache (60 s, same as billing_config)
_config_cache: dict[str, dict] | None = None
_cache_ts: int = 0

def _cache_ttl() -> int: ...          # reads S.job_config_cache_ttl_seconds (default 60)
def invalidate_cache() -> None: ...   # sets _config_cache = None, _cache_ts = 0
```

**Functions:**

```python
def get_job_config(task_name: str) -> dict | None:
    """
    Read the DDB row for one job.
    Returns None if absent (treat as enabled=True, no override).
    Uses T.billing_config.get_item(Key={"pk": _PK, "sk": _SK_CURRENT(task_name)}).
    """

def set_job_enabled(actor_sub: str, task_name: str, enabled: bool) -> None:
    """
    Upsert the JOB# config row + write an AUDIT# row.
    Calls invalidate_cache().
    Emits audit_event("admin_job.toggled", actor_sub, task_name=task_name, enabled=enabled)
    via app.services.alerts.audit_event (alerts.py:644).
    Raises ValueError if task_name is not in job_registry._tasks OR in KNOWN_JOBS —
    unknown job names are rejected to prevent silent typos.
    """

def get_all_job_configs() -> dict[str, dict]:
    """
    Queries T.billing_config with
      KeyConditionExpression=Key("pk").eq(_PK) & Key("sk").begins_with("JOB#")
    Returns {task_name: {enabled, updated_by_sub, updated_at}} for all stored rows.
    Uses the in-memory cache (returns cached copy if within TTL).
    """

def is_job_enabled(task_name: str) -> bool:
    """
    Returns the DDB-persisted enabled flag if a row exists for task_name.
    Falls back to True if no row is present (absence = enabled).
    Called at startup from background-task startup hooks.
    Implementation: get_job_config(task_name), check "enabled" key.
    """
```

**Trigger callback registry:**

```python
_trigger_callbacks: dict[str, Callable[[], None]] = {}

def register_trigger_callback(task_name: str, fn: Callable[[], None]) -> None:
    """
    Register a one-shot callable for a task. Called once at task startup.
    fn() should run a single iteration of the task's work (not the full loop).
    """

def get_trigger_callback(task_name: str) -> Callable[[], None] | None:
    """Return the registered callable or None if not registered."""
```

### 4.2 Router additions: `app/routers/admin_jobs.py`

All three endpoints are appended to the existing `router` (APIRouter at line 12). They return 404 when `not S.crm_studio_enabled`. FastAPI matches routes in declaration order: the static path segments `/config` and `/task/{task_name}/enable` and `/task/{task_name}/trigger` must be declared before any existing dynamic `/{task_name}` pattern. The current file has `GET /task/{task_name}` at line 65, so the three new routes are declared **before** that endpoint or placed immediately after the router header but before line 65.

```
POST  /ui/admin/jobs/task/{task_name}/enable
      Auth: Depends(require_admin_or_root) from app.auth.policy
      Body: JobToggleIn  { enabled: bool }
      On success: 200 { ok: true, task_name, enabled, updated_at }
      On unknown task_name: 404

POST  /ui/admin/jobs/task/{task_name}/trigger
      Auth: Depends(require_root) from app.auth.policy
      Body: none
      On success: 200 { ok: true, task_name, triggered_at: int }
      On not registered (no callback): 404
      On not run_now_safe in KNOWN_JOBS but callback present: allowed (callback overrides)

GET   /ui/admin/jobs/config
      Auth: Depends(require_admin_or_root)
      Returns: JobConfigOut — merged view of in-memory registry + DDB overrides
```

**Handler pseudocode for `POST .../enable`:**

```python
@router.post("/ui/admin/jobs/task/{task_name}/enable")
async def enable_job(
    task_name: str,
    body: JobToggleIn,
    user: AuthenticatedUser = Depends(require_admin_or_root),
):
    if not S.crm_studio_enabled:
        raise HTTPException(404)
    try:
        job_config.set_job_enabled(user.sub, task_name, body.enabled)
    except ValueError as e:
        raise HTTPException(404, detail=str(e))
    return {"ok": True, "task_name": task_name, "enabled": body.enabled,
            "updated_at": now_ts()}
```

**Handler pseudocode for `POST .../trigger`:**

```python
@router.post("/ui/admin/jobs/task/{task_name}/trigger")
async def trigger_job(
    task_name: str,
    user: AuthenticatedUser = Depends(require_root),
):
    if not S.crm_studio_enabled:
        raise HTTPException(404)
    fn = job_config.get_trigger_callback(task_name)
    if fn is None:
        raise HTTPException(404, detail=f"No trigger registered for '{task_name}'")
    loop = asyncio.get_event_loop()
    await loop.run_in_executor(None, fn)
    return {"ok": True, "task_name": task_name, "triggered_at": now_ts()}
```

**Handler pseudocode for `GET /config`:**

```python
@router.get("/ui/admin/jobs/config")
async def get_job_config_merged(
    _user: AuthenticatedUser = Depends(require_admin_or_root),
):
    if not S.crm_studio_enabled:
        raise HTTPException(404)
    in_memory = job_registry.get_all_tasks()           # keyed by task_name
    ddb_overrides = job_config.get_all_job_configs()   # keyed by task_name
    known = job_dashboard.list_known_jobs()            # from KNOWN_JOBS

    merged = {}
    # Start from in-memory registry
    for name, task in in_memory.items():
        merged[name] = {**task, "ddb_enabled": None, "ddb_updated_by": None,
                        "ddb_updated_at": None, "trigger_registered": False}
    # Layer in KNOWN_JOBS metadata
    for entry in known:
        name = entry["name"]
        if name not in merged:
            merged[name] = {"name": name, "enabled": False, "status": "not_running",
                            "ddb_enabled": None, "ddb_updated_by": None,
                            "ddb_updated_at": None, "trigger_registered": False}
        merged[name].update({"label": entry["label"], "run_now_safe": entry["run_now_safe"]})
    # Layer in DDB overrides
    for name, cfg in ddb_overrides.items():
        if name not in merged:
            merged[name] = {"name": name, "status": "config_only",
                            "trigger_registered": False}
        merged[name].update({"ddb_enabled": cfg["enabled"],
                             "ddb_updated_by": cfg.get("updated_by_sub"),
                             "ddb_updated_at": cfg.get("updated_at")})
    # Mark trigger availability
    for name in merged:
        merged[name]["trigger_registered"] = (
            job_config.get_trigger_callback(name) is not None
        )
    return {"jobs": list(merged.values()), "timestamp": now_ts()}
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Enable/disable toggle

- **Unknown task name**: `set_job_enabled` raises `ValueError` if `task_name` is not in `job_registry._tasks` AND not in `job_dashboard.KNOWN_JOBS`. The router converts this to HTTP 404. This prevents silent config for tasks that do not exist.
- **Toggle does not restart a running loop**: The DDB config row changes what `is_job_enabled` returns for subsequent calls, but it does not signal a running `asyncio.Task` to stop. To make the toggle take effect immediately, the admin must also restart the process (or the startup hook must be re-consulted). A `note` field in the response states this explicitly: `"note": "Change will take full effect on next process restart unless the task polls is_job_enabled periodically"`.
- **No-op toggle**: Writing `enabled=True` when the job already has a stored `enabled=True` still writes the DDB row (updates `updated_by_sub` and `updated_at`) but the audit row reflects no net change. This differs from `billing_config.update_billing_config` which skips the write on no-op (line 351). The rationale: for job config, always recording who last touched the row is more operationally valuable than skipping it.

### 5.2 Manual trigger

- **run_in_executor**: The callback is invoked via `asyncio.get_event_loop().run_in_executor(None, fn)` so the async endpoint does not block the event loop. If the callback raises, the 500 propagates to the caller.
- **No re-entrancy guard**: If a job is currently running its normal loop, `trigger` fires an extra iteration. Background loops are expected to be safe against concurrent calls (they use compare-and-swap on DynamoDB for ownership; e.g. `audit_export_worker._claim_job` at `audit_export_worker.py:49`). A caller warning is included in the 200 response: `"note": "Trigger may run concurrently with the scheduled loop if it is active"`.
- **ROOT only**: Manual triggers carry operational risk (running a billing reconcile or dunning job out of schedule could double-charge). The `require_root` dependency gates this.
- **`run_now_safe` is advisory**: The `trigger` endpoint does not check `KNOWN_JOBS["run_now_safe"]`; it fires if a callback is registered. Only jobs that explicitly register a callback via `register_trigger_callback` are triggerable. Jobs with `run_now_safe: False` in KNOWN_JOBS should not register a callback.

### 5.3 `GET /config` merged view

- In-memory tasks not in DDB get `ddb_enabled: null` in the response (meaning "no override; env-var default applies").
- DDB rows for task names that no longer appear in the in-memory registry (stale config from a deleted or renamed task) appear with `status: "config_only"`.
- The response is cached for up to 1 second at the router layer (no separate cache — `get_all_job_configs` already has a 60-second TTL). Repeated GET requests within the TTL window return the same DDB view.

### 5.4 Cache invalidation

`invalidate_cache()` is called synchronously inside `set_job_enabled` before the function returns, so a subsequent `GET /config` (or a startup hook's `is_job_enabled` call) will read fresh data from DDB. The 60-second TTL only applies to passive reads.

### 5.5 Interaction with existing env-var flags

The startup hook integration introduced as a reference in `start_audit_export_worker_task` uses:

```python
if S.audit_export_worker_enabled and is_job_enabled("audit_export_worker"):
    asyncio.create_task(run_audit_export_worker_loop())
```

The env-var flag is checked first. If `AUDIT_EXPORT_WORKER_ENABLED=0`, the task never starts regardless of the DDB row. The DDB row provides a finer-grained override only within the space where the env-var permits the task to run. This layering prevents the DDB toggle from inadvertently re-enabling a task that has been hard-disabled at the infrastructure level.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

`app/services/job_config.py` contains no `if S.dev_mode` branches. All DDB reads and writes go through `T.billing_config` using the standard boto3 Table API. In dev, this points to the moto in-process mock (same endpoint URL as every other table). In prod it points to real DynamoDB. The code path is identical — SECOPS-007 is satisfied.

### 7.2 Idempotency

- `set_job_enabled` is idempotent with respect to the desired state: calling it twice with the same `(task_name, enabled)` writes the same DDB item twice (with updated `updated_at`). No conditional puts are used for the config row; the last writer wins. Audit rows are append-only (unique SK via `now_ts()` + `uuid4().hex[:8]`), so repeated calls produce distinct audit entries.
- `GET /config` is a pure read; it is safe to call repeatedly.
- `POST /trigger` is not idempotent; it fires the task callback each time it is called.

### 7.3 Security

- **Role gating**: Enable/disable requires ADMIN or ROOT (`require_admin_or_root`). Manual trigger requires ROOT (`require_root`). Auth is enforced by FastAPI dependency injection — no local role check at the handler body.
- **CSRF**: Because these endpoints are under `/ui/`, the standard cookie-auth CSRF flow applies. Bearer-token callers (API keys) bypass CSRF as usual.
- **Task name injection**: `task_name` is a path parameter passed to `set_job_enabled`, which validates it against the in-memory registry and `KNOWN_JOBS` before writing to DDB. This prevents an attacker from writing arbitrary keys to the `JOB_CONFIG` partition.
- **Audit trail**: Every enable/disable toggle emits an `audit_event("admin_job.toggled", ...)` via `app/services/alerts.audit_event` (`alerts.py:644`) and also writes an `AUDIT#` row to DDB. Audit events are picked up by the ENTERPRISE-004 audit export pipeline (`app/services/audit_export_pipeline.py`).

## 8. Backward Compatibility & Migration

### 8.1 Existing endpoints unchanged

`GET /ui/admin/jobs/status` (line 22), `GET /ui/admin/jobs/task/{task_name}` (line 65), `GET /ui/admin/jobs/failed` (line 76), and `POST /ui/admin/jobs/retry/{action_id}` (line 90) are unchanged. All new routes use the `/task/{task_name}/enable` and `/task/{task_name}/trigger` path shapes, which do not conflict with the existing `/{action_id}` path at line 90 because the `task/` prefix is unambiguous.

### 8.2 Existing startup hooks

The reference integration in `start_audit_export_worker_task` is the only startup hook modified in this ticket. All other background tasks (`compute_billing`, `newsfeed_recsys`, `audit_export_scheduler`, `webhook_dispatcher`, `unified_scheduler`, etc.) continue to start unconditionally from their env-var flags. Integrating those hooks with `is_job_enabled` is deferred to follow-up work; the reference implementation demonstrates the pattern.

### 8.3 No DynamoDB schema change

The `billing_config` table already exists with PK=`pk`, SK=`sk` (declared at `scripts/local-ddb-init.py:78`). Adding `JOB_CONFIG` partition rows requires no schema migration: DynamoDB's schema-less model allows new partition key values without table changes.

### 8.4 Rollback

To roll back, set `CRM_STUDIO_ENABLED=0` (the default). The three endpoints return 404. DDB rows under `JOB_CONFIG` remain but are never read by existing code. Reverting the `start_audit_export_worker_task` change restores the prior startup logic.

## 10. Open Questions / Assumptions

1. **Live loop termination**: This spec does not deliver a mechanism to stop a running asyncio loop mid-flight. The assumption is that `is_job_enabled` being called at the top of each poll iteration is sufficient for well-behaved loops. Do any loops need an explicit cancellation signal? Deferred to follow-up.

2. **`KNOWN_JOBS` as the canonical task list for validation**: `set_job_enabled` validates `task_name` against `job_registry._tasks` union `KNOWN_JOBS`. This means a task registered only at startup (and not in `KNOWN_JOBS`) is valid only while the process is running. After restart, before the task registers itself, DDB config for it is not writeable via the API. The assumption is that tasks always call `register_task` at startup before any admin request arrives. If not, a two-phase approach (allow writing config for any previously-seen task stored in DDB) would be needed.

3. **Multi-worker processes**: The spec notes moto requires `--workers 1` in dev (CLAUDE.md). In a theoretical multi-worker prod deployment, each worker has its own in-memory `_tasks` dict. The DDB overlay applies uniformly across all workers (they all call `is_job_enabled` at startup). The in-memory registry on each worker is per-process; a trigger fires only in the worker that received the HTTP request. This is acceptable for a 1-worker dev config and documented for prod.

4. **Trigger callback naming**: The `register_trigger_callback` function must be called by each background task module. The audit_export_worker reference integration registers `lambda: asyncio.run(run_audit_export_worker_loop.__wrapped__())` or a dedicated one-shot function. The exact one-shot function signature is an implementation decision left to the implementer.

5. **Whether to extend `job_dashboard.KNOWN_JOBS`**: The ticket requests adding the async-startup tasks (`audit_export_worker`, `audit_export_scheduler`, `compute_billing_timer`, `newsfeed_recsys_refresh`) to `KNOWN_JOBS`. This is a `job_dashboard.py` change. The spec defers the specific `run_now` callable paths for those tasks to the implementer, as calling an async loop function from a sync one-shot wrapper requires care (same pattern as `trigger_run_now` in `job_dashboard.py:410`).
