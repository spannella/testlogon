# KB-004 — KB category tree (hierarchical categories with parent/child nesting)

**Type:** Feature  **Priority:** P1  **Estimate:** 2 days  
**Ticket source:** `docs/suitecrm/CRM_KNOWLEDGE_BASE_TICKETS.md`, section "KB-004"

---

## 1. Summary & Goal

KB-004 formalizes the Knowledge Base category system from a raw string field into a
full hierarchical tree stored in DynamoDB. Categories carry a `parent_id` reference
enabling unlimited depth nesting, a materialized `path` string (e.g. `"Support > Billing
> Refunds"`) for breadcrumbs, and a `sort_order` integer for display sequencing within
a level. Articles already carry a `category` field (introduced by CAS-015); this ticket
upgrades that field to a foreign-key reference to a managed `CATEGORY#` item, adds
`category_id` as the canonical FK attribute, and ensures cascade path recomputation
when a category is reparented.

Concrete deliverables:

1. Five new `KbArticleService` methods in `app/services/kb_articles.py` covering
   create/update/delete/get/list of `CATEGORY#` items.
2. Five new router endpoints in `app/routers/kb_articles.py` — two public (no auth)
   and three admin-only — all declared before the existing `/{article_id}` segment to
   prevent path-capture.
3. Two new Pydantic models in `app/models.py`: `KbCategoryIn` and `KbCategoryOut`.
4. `audit_event` emission on every mutating category operation.

All behavior is additive and gated on `S.knowledge_base_enabled` (default `False`).
With the flag off the platform is byte-for-byte identical to its pre-KB-004 state: no
new routes exist, no new items are written, and every existing file outside
`app/services/kb_articles.py`, `app/routers/kb_articles.py`, and `app/models.py` is
unchanged.

### 2.2 Table handle `T.kb_articles`

KB-001 wires `T.kb_articles` in `app/core/tables.py` using `_safe_table(S.kb_articles_table)`

The `_FloatSafeTable` proxy coerces `float` to `Decimal` on every `put_item`,

### 2.3 CAS-015 base service and article `category` field

CAS-015 introduces `app/services/kb_articles.py` (`KbArticleService`) and stores
`category` on the article META item as a raw string. The CAS-015 spec
(`docs/suitecrm/specs/CAS-015.md:17–18`) notes that CAS-015 manages categories as
items under `PK=CATEGORY#{category_id}` / `SK=META` in the same single table, but does
not deliver the full CRUD surface. KB-004 extends that file to provide the complete
category management layer. Articles already carry a `category` string field; KB-004
treats `category_id` as the canonical FK without mandating a migration of legacy rows
(see Section 8).

### 2.4 Single-table layout precedent

The `crm_kb_articles` table uses composite key `pk` / `sk` (both String) as declared
in `scripts/local-ddb-init.py` by CAS-001. Multiple item types coexist under distinct
`ARTICLE#`, `CATEGORY#`, and future `ATTACHMENT#` / `REVISION#` / `TAG#` prefixes —
the same single-table pattern used in `T.tickets` (ticket items, space items, label
fan-out rows under `LABELIDX#` per `app/services/tickets.py:45`) and `T.billing`
(ledger entries, payment-method rows, balance rows under distinct SK prefixes). DynamoDB
`FilterExpression` does not reduce consumed page size before the 1MB limit, so any
scan over `CATEGORY#` items must paginate via `LastEvaluatedKey` (CLAUDE.md gotcha,
`app/core/cursor.py` encodes these keys).

### 2.5 No new GSI for categories

The ticket source (`docs/suitecrm/CRM_KNOWLEDGE_BASE_TICKETS.md:162`) specifies that
categories need no dedicated GSI: the tree is small (typically < 200 nodes), so a
table scan with `FilterExpression: begins_with(pk, "CATEGORY#")` is acceptable.
`list_categories` always fetches the full set into memory and applies parent-level
filtering client-side. This mirrors the pattern in `app/services/tickets.py` where
label fan-out rows are queried by partition key directly rather than via a GSI.

## 3. Data Model

### 3.1 Existing table: `crm_kb_articles`

No new table is introduced. Category items are stored as additional item types in the
existing `crm_kb_articles` table alongside `ARTICLE#` and future `ATTACHMENT#` rows. The
table declaration in `scripts/local-ddb-init.py` (added by CAS-001, extended by KB-001)
retains:

```
PK (hash key):  pk   — String
SK (range key): sk   — String
attr_types: {"published_at": "N", "created_at": "N"}
GSI ByCategory: PK=category, SK=published_at (N)
GSI ByStatus:   PK=status,   SK=published_at (N)
GSI ByAuthor:   PK=author_sub, SK=created_at (N)   [added by KB-001]
GSI ByTag:      PK=tag,        SK=created_at (N)    [added by KB-001]
```

KB-004 adds no new GSIs to `scripts/local-ddb-init.py`.

### 3.2 Category item layout

Each managed category is stored as a single DynamoDB item:

| Attribute    | Type    | Notes |
|---|---|---|
| `pk`         | String  | `CATEGORY#{category_id}` |
| `sk`         | String  | `META` |
| `category_id`| String  | UUID (hex, no dashes) |
| `name`       | String  | Display label, max 120 chars |
| `slug`       | String  | URL-safe identifier, `[a-z0-9_-]+`, max 80 chars, unique across all categories |
| `parent_id`  | String  | `""` (empty string) for root-level categories; `{category_id}` for children |
| `path`       | String  | Materialized label path, e.g. `"Support > Billing > Refunds"` |
| `description`| String  | Optional free-text, max 500 chars, default `""` |
| `sort_order` | Number  | Integer, default `0`, used to sequence siblings in the UI |
| `created_by` | String  | `user_sub` of the admin who created the category |
| `created_at` | Number  | Integer Unix timestamp from `now_ts()` |
| `updated_at` | Number  | Integer Unix timestamp, set on every mutating write |
| `deleted_at` | Number  | Integer Unix timestamp; present only on soft-deleted items |

No new `attr_types` declaration is needed in `scripts/local-ddb-init.py` because
`created_at` is already declared `"N"` by KB-001.

### 3.3 Article FK alignment

Articles already store a `category` string field (CAS-015). KB-004 adds a parallel
`category_id` attribute to article META items when a category is created or when
`update_article` receives a `category_id` parameter. The legacy `category` string
remains on existing items for backward compatibility; new articles and category-aware
updates write `category_id` alongside it. `KbCategoryOut` includes both `category_id`
and `slug` so callers can build either FK or slug-based URLs.

### 3.4 Slug uniqueness enforcement

Slug uniqueness is enforced application-side: `create_category` scans all `CATEGORY#`
items, collects existing slugs, and raises `KbCategorySlugConflictError` (HTTP 409)
before writing if the new slug is already taken by a non-deleted item. The scan is
acceptable at category-tree scale (< 200 nodes); no DDB conditional expression is
needed for this check.

## 4. API / Service Design

### 4.1 Service additions (`app/services/kb_articles.py`)

All five methods are added to the existing `KbArticleService` class introduced by
CAS-015. The service imports `T` from `app/core/tables` and `now_ts` from
`app/core/time`.

#### 4.1.1 Exception classes (new, defined at module level)

```python
class KbCategoryNotFoundError(Exception):
    """Raised when a category_id does not resolve to a live CATEGORY# item."""

class KbCategoryNotEmptyError(Exception):
    """Raised when delete_category is called while articles reference this category."""

class KbCategorySlugConflictError(Exception):
    """Raised when the requested slug is already in use by another live category."""

class KbCategoryCircularError(Exception):
    """Raised when an update_category reparent would create a cycle."""
```

#### 4.1.2 `create_category`

```python
def create_category(
    self,
    *,
    name: str,
    slug: str,
    parent_id: str = "",
    description: str = "",
    sort_order: int = 0,
    created_by: str,
) -> dict:
```

Steps:
1. Normalize `slug`: lowercase, strip, replace spaces with `-`, drop chars outside
   `[a-z0-9_-]`, truncate to 80 chars.
2. If `parent_id` is non-empty: call `get_category(parent_id)` — raises
   `KbCategoryNotFoundError` if absent or soft-deleted. Ensures the parent exists before
   writing.
3. Scan all live `CATEGORY#` items (see Section 4.1.5) and check slug uniqueness; raise
   `KbCategorySlugConflictError` if collision found.
4. Compute `path`:
   - If `parent_id == ""`: `path = name`.
   - Else: `path = f"{parent.path} > {name}"` where `parent = get_category(parent_id)`.
5. Generate `category_id = uuid4().hex`.
6. Call `T.kb_articles.put_item(Item={...})` with all fields above.
7. Emit `audit_event("kb.category.created", created_by, category_id=category_id)`.
8. Return the full category dict.

#### 4.1.3 `get_category`

```python
def get_category(self, category_id: str) -> dict:
```

Steps:
1. `T.kb_articles.get_item(Key={"pk": f"CATEGORY#{category_id}", "sk": "META"})`.
2. If absent or `deleted_at` present: raise `KbCategoryNotFoundError`.
3. Return the item.

#### 4.1.4 `list_categories`

```python
def list_categories(self, parent_id: str | None = None) -> list[dict]:
```

Steps:
1. Scan `T.kb_articles` with `FilterExpression=Attr("pk").begins_with("CATEGORY#") &
   Attr("deleted_at").not_exists()`, looping over `LastEvaluatedKey` until exhausted
   (per CLAUDE.md DDB FilterExpression gotcha — scan loops are mandatory).
2. If `parent_id is not None`: client-side filter to items where `item["parent_id"] == parent_id`.
3. Sort by `sort_order` ascending, then `name` ascending as tie-breaker.
4. Return list of dicts (caller builds tree from the flat list).

This method always fetches the entire live category set into memory; at tree scale
(< 200 nodes) this is well within DynamoDB scan limits.

#### 4.1.5 `update_category`

```python
def update_category(
    self,
    category_id: str,
    *,
    admin_sub: str,
    name: str | None = None,
    slug: str | None = None,
    parent_id: str | None = None,
    description: str | None = None,
    sort_order: int | None = None,
) -> dict:
```

Steps:
1. `get_category(category_id)` — raises `KbCategoryNotFoundError` if absent.
2. If `slug` is changing: normalize and slug-uniqueness check (same as create, excluding
   `category_id` itself from the conflict scan).
3. If `parent_id` is changing (new value differs from current `item["parent_id"]`):
   - If new `parent_id` is non-empty: call `get_category(parent_id)` to assert it exists.
   - Cycle detection: walk the ancestor chain of the new `parent_id` via repeated
     `get_category` calls; raise `KbCategoryCircularError` if `category_id` is encountered
     in the chain (i.e., you would be making a node its own descendant).
4. Recompute `path`:
   - If `parent_id` is being changed or `name` is being changed: rebuild path from
     `parent.path + " > " + (new_name or item["name"])`.
   - Cascade recomputation: call `list_categories(parent_id=category_id)` to get direct
     children, then recursively call `update_category` on each child passing only
     `parent_id=category_id` (no-op field change triggers path recomputation via
     `_recompute_path` internal helper). This recursion terminates because the tree is
     acyclic (cycle check above) and bounded (< 200 nodes).
5. Build a DynamoDB `UpdateExpression` for only the changed fields plus `updated_at`.
   Use `SET` expressions; never rewrite unchanged attributes.
6. `T.kb_articles.update_item(...)`.
7. Emit `audit_event("kb.category.updated", admin_sub, category_id=category_id)`.
8. Return the updated category dict via `get_category(category_id)`.

#### 4.1.6 `delete_category`

```python
def delete_category(self, category_id: str, admin_sub: str) -> None:
```

Steps:
1. `get_category(category_id)` — raises `KbCategoryNotFoundError` if absent.
2. Check for assigned articles: scan `T.kb_articles` with
   `FilterExpression=Attr("pk").begins_with("ARTICLE#") & Attr("sk").eq("META") &
   Attr("category_id").eq(category_id) & Attr("deleted_at").not_exists()`, loop over
   `LastEvaluatedKey`. If any result has a count > 0: raise `KbCategoryNotEmptyError`.
3. Check for child categories: call `list_categories(parent_id=category_id)`. If non-empty:
   raise `KbCategoryNotEmptyError` (message distinguishes "has children" from "has articles").
4. Soft-delete: `T.kb_articles.update_item(Key=..., UpdateExpression="SET deleted_at = :ts",
   ExpressionAttributeValues={":ts": now_ts()})`.
5. Emit `audit_event("kb.category.deleted", admin_sub, category_id=category_id)`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Path materialization

`path` is computed eagerly at write time, not at read time, to avoid repeated ancestor
lookups on every GET. The separator `" > "` (space–greater-than–space) is fixed. A root
category with `name="Support"` has `path="Support"`. A child with `name="Billing"` and
`parent_id=<support_id>` has `path="Support > Billing"`. A grandchild `name="Refunds"`
has `path="Support > Billing > Refunds"`.

### 5.2 Cascade path recomputation on reparent

When `update_category` changes `parent_id` or `name`, all descendant categories must
have their `path` refreshed. The implementation performs a depth-first recursive cascade:
1. Fetch direct children via `list_categories(parent_id=category_id)`.
2. For each child, compute the new `path = updated_parent.path + " > " + child["name"]`
   and write it via a targeted `update_item` (only `path` and `updated_at` change — no
   `audit_event` is emitted for the cascade children, only for the explicitly updated
   category).
3. Recurse into each child's children.

At tree scale (< 200 nodes, typical depth ≤ 5) this is at most ~200 DDB writes in the
pathological full-tree reparent case. This is acceptable for an infrequent admin
operation. A `_cascade_path_update(category_id, new_parent_path)` private helper
encapsulates this logic to keep `update_category` readable.

### 5.3 Delete blocked by non-empty category

`delete_category` raises `KbCategoryNotEmptyError` if any of the following are true:
- At least one live `ARTICLE#` META item has `category_id` equal to the target.
- At least one live `CATEGORY#` item has `parent_id` equal to the target (i.e. direct
  children exist).

The error message distinguishes between the two cases: `"Category has assigned articles"` vs
`"Category has child categories"`. The router returns HTTP 409 in both cases.

Soft-deleted articles (those with a `deleted_at` attribute) and soft-deleted child
categories are excluded from the non-empty check.

### 5.4 Slug uniqueness scope

Slugs are globally unique across all live categories — not scoped per-level. `"billing"`
as a root slug and `"billing"` as a child of `"Support"` are a conflict. This matches
SuiteCRM's behavior and simplifies URL routing for KB-011's public portal (`/kb/c/{slug}`).

### 5.5 Cycle detection

`update_category` with a new `parent_id` must not allow a node to become its own
ancestor. The cycle check walks the ancestor chain of the *proposed* parent:
```
ancestors = set()
cursor = proposed_parent_id
while cursor != "":
    if cursor == category_id:
        raise KbCategoryCircularError(...)
    ancestors.add(cursor)
    cursor = get_category(cursor)["parent_id"]
```
For a tree of depth D, this is at most D `get_item` calls (at most 10–20 in practice).

### 5.6 Concurrent slug conflict

Because slug uniqueness is enforced by scan-then-write (not a DDB conditional
expression), a narrow race window exists between the scan and the `put_item`. At category
management scale (admin-only, infrequent writes) this race is acceptable. If two
concurrent `create_category` calls with the same slug both pass the scan, both items are
written and the second write wins (no data corruption, only a duplicate slug). A
follow-up could add a `SLUG_LOCK#{slug}` sentinel item with a DDB conditional put if this
proves problematic, but it is not required for MVP.

### 5.7 `parent_id` serialized as empty string, not null

DynamoDB does not support `NULL` as a GSI key value, and absent-attribute lookups
behave differently from empty-string lookups. `parent_id` is stored as `""` (empty
string) for root categories throughout: in `put_item`, `update_item`, and all
`FilterExpression` comparisons. Callers passing `None` for `parent_id` in Pydantic
models are coerced to `""` in the service layer.

### 5.8 `list_categories` pagination loop

DynamoDB scan with `FilterExpression` does not reduce page size before the 1MB limit.
`list_categories` must loop via `LastEvaluatedKey` until exhausted:
```python
items = []
kwargs = {"FilterExpression": ...}
while True:
    resp = T.kb_articles.scan(**kwargs)
    items.extend(resp.get("Items", []))
    lek = resp.get("LastEvaluatedKey")
    if not lek:
        break
    kwargs["ExclusiveStartKey"] = lek
```
This is the same pattern required by the CLAUDE.md gotcha on `DDB FilterExpression`.

### 5.9 Ordering of response items

`list_categories` returns items sorted by `sort_order` ascending, then `name` ascending.
The sort is applied client-side after all pages are collected, since DynamoDB scan
returns items in undefined order.

### 5.10 Article `category_id` alignment on category rename

When a category's `name` changes, articles referencing that category via `category_id`
continue to resolve correctly because they store the opaque `category_id`, not the
display name. The materialized `path` on the category item is updated by KB-004 itself.
Articles do not cache the category `name` or `path` — they always fetch the category
separately. (KB-011's `KbArticleOut` may embed a `category_name` projection field,
but that projection is populated at query time, not stored on the article.)

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

All DynamoDB operations use `T.kb_articles` (backed by `_safe_table` →
`_FloatSafeTable` → boto3 `Table`). In dev, `T.kb_articles` points at DynamoDB Local
(`DDB_ENDPOINT_URL=http://localhost:8001`). In prod it points at real DynamoDB. The code
path is identical — no `S.dev_mode` branch exists in KB-004. No mock-only paths are
introduced. `audit_event` writes to `T.alerts` via `now_ts()` in both dev and prod.
There is no S3 interaction in KB-004 (S3 is introduced for attachments in KB-003).

### 7.2 Idempotency

- `create_category` uses `put_item` unconditionally after UUID generation, so two
  concurrent calls with the same `name`+`slug` (but different UUIDs) each succeed and
  produce distinct items. Slug conflict is caught pre-write.
- `update_category` uses `update_item` targeting the fixed `PK/SK`, so repeated calls
  with the same payload are idempotent in effect.
- `delete_category` is idempotent: a second call finds `deleted_at` already set, meaning
  `get_category` raises `KbCategoryNotFoundError` → HTTP 404. No double-delete fault.

### 7.3 Security

- All write endpoints (`POST /kb/categories`, `PUT /kb/categories/{id}`,
  `DELETE /kb/categories/{id}`) require `Depends(require_ui_session)` and an inline
  admin-role check (`Role.ADMIN` or `Role.ROOT`). A `USER`-role session receives HTTP 403.
- Public endpoints (`GET /public/kb/categories`, `GET /public/kb/categories/{id}`) require
  no authentication, consistent with SuiteCRM's public KB portal surface.
- No user-supplied content is evaluated as code. Category `name`, `description`, and
  `slug` are stored and returned as plain strings; HTML sanitization is the responsibility
  of the rendering layer (KB-012 frontend).
- CSRF: write endpoints use cookie-based `require_ui_session` and therefore enforce the
  `x-csrf-token` header check implemented in `app/auth/deps.py`.
- No money-out path, billing ledger write, or refund call is involved in KB-004.

## 8. Backward Compatibility & Migration

### 8.1 Existing article items

Pre-KB-004 article items in `crm_kb_articles` carry a `category` string (raw display
name, set by CAS-015). They do not carry `category_id`. KB-004 does not run any
migration sweep. Post-KB-004, new articles and any article updated via
`update_article(category_id=...)` carry both `category` (human label) and `category_id`
(FK). Legacy items without `category_id` are treated as uncategorized by `list_categories`
queries and KB-011 public browse (the `ByCategory` GSI returns `ARTICLE#` items where
`category` equals the string value, not the UUID FK — this coexistence is stable until
a background migration is run in a later ticket).

### 8.2 No new DDB table; no `just restart` impact

KB-004 adds no new `TableDef` to `scripts/local-ddb-init.py`. It adds no new GSIs to
the `crm_kb_articles` table (those were added by KB-001). `just restart` behavior is
unchanged by KB-004: the `crm_kb_articles` table is recreated with the KB-001 GSI set,
and any `CATEGORY#` items written in the previous dev session are wiped along with
`ARTICLE#` items.

### 8.3 `T.kb_articles` handle

`T.kb_articles` is introduced by KB-001 and must be present before KB-004 can run. If
KB-001 has not shipped, KB-004 will fail at import time with an `AttributeError` on
`T.kb_articles`. This is an expected hard dependency, not a compatibility issue.

### 8.4 Router file ordering

When KB-004's five endpoints are integrated into the KB router alongside future KB-007
(`/public/kb/tags`) and KB-009 (`/public/kb/search`) endpoints, the ordering constraint
must be preserved: all static-segment routes before `/{article_id}`. KB-004 endpoint
declarations belong in a `# --- Category routes ---` block placed at the top of the
router file, above both the article CRUD routes and the existing public list/get routes
from CAS-015.

## 10. Open Questions / Assumptions

1. **Maximum tree depth** — The spec assumes < 200 total nodes and depth ≤ 5. If the
   platform expects deep taxonomies (10+ levels), the recursive cascade in
   `update_category` should be replaced with a non-recursive `_cascade_path_update`
   helper that uses an iterative BFS/DFS queue to avoid Python call-stack depth limits.
   Assumed safe for MVP.

2. **Article `category` vs `category_id` field** — Pre-KB-004 articles carry `category`
   (string name); KB-004 introduces `category_id` (UUID FK). The two fields coexist without
   a migration. The assumption is that KB-012's article editor will write `category_id` on
   any edit, and a background migration script can backfill `category_id` on legacy items
   in a later release. Confirmed acceptable per ticket source (CAS-015 category field is
   a raw string today).

3. **Slug immutability after publication** — The spec allows slug changes at any time via
   `PUT /kb/categories/{id}`. If permalinks in KB-011 are slug-based (e.g.,
   `/kb/c/{slug}`), changing a slug breaks existing URLs. A follow-up hardening could
   store a `previous_slug` list and issue redirects. Not in scope for KB-004.

4. **Concurrent reparent writes** — The cascade path update is not atomic. A concurrent
   read of a child category during the cascade may see an inconsistent (partially updated)
   `path`. At admin-only write frequency this is acceptable. A DDB transaction would
   require the TransactWriteItems limit (25 items). Assumed safe for MVP given tree scale.

5. **`KbCategoryUpdateIn.parent_id = None` semantics** — `None` means "do not change
   `parent_id`", while `""` means "reparent to root". The router must distinguish these.
   The Pydantic model uses `parent_id: str | None = None` where `None` signals "no
   change" and `""` signals "promote to root". This behavior must be documented in the
   OpenAPI description of the field.
