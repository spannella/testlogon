# PRJ-002 — Project header CRUD with status, dates, and priority

**Ticket type:** Feature  
**Priority:** P1  
**Estimate:** 2 days  
**Source ticket file:** `docs/suitecrm/CRM_PROJECTS_GANTT_TICKETS.md`

---

## 1. Summary & Goal

PRJ-002 introduces the CRM project _header_ entity: the top-level record that identifies a project by name, describes its current status (draft / in_review / underway / completed / deferred), holds scheduling dates (start and end), carries a numeric priority level, and optionally references an assigned user and an account organisation. It is the smallest useful unit of the Projects module — every subsequent PRJ ticket (tasks, members, Gantt, templates, relationships) builds on top of this record.

The deliverables for this ticket are:

1. Two new Pydantic models in `app/models.py` — `CrmProjectStatus` (enum) and `CrmProjectModel` — plus request/response variants `CrmProjectCreateIn`, `CrmProjectUpdateIn`, `CrmProjectOut`, and `CrmProjectListResp`.
2. A new service module `app/services/crm_projects.py` with five public functions: `create_crm_project`, `get_crm_project`, `update_crm_project`, `delete_crm_project`, and `list_crm_projects`.
3. A new router `app/routers/crm_projects.py` exposing five REST endpoints under the prefix `/v1/crm/projects`, all gated by the `CRM_PROJECTS_ENABLED` flag introduced in PRJ-001.
4. Frontend type declarations in `frontend/src/api/types.ts` and endpoint wrappers in `frontend/src/api/endpoints/crmProjects.ts`.

When `CRM_PROJECTS_ENABLED=0` (the default) every new surface returns HTTP 404 and the platform byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 Existing "projects" surface — file-grouping layer, not CRM

The platform already has a projects concept, but it serves an entirely different purpose: it groups cloud-provider files by project name. Its Pydantic model lives at `app/models.py:1796` (`ProjectModel`) with fields `id`, `owner`, `name`, `description`, `tags`, `settings`, `created_at`, `updated_at` — no status, no dates, no priority. The corresponding service is `app/services/projects_store.py` and the router is `app/routers/projects.py` (prefix `/v1/projects`), registered in `app/main.py:682`. The cross-cutting constraint in `docs/suitecrm/CRM_PROJECTS_GANTT_TICKETS.md` (header section) is explicit: **the existing file-grouping layer must never be modified**. CRM project management lives in a completely separate DDB table (`crm_pm_projects`) and a separate router.

### 2.2 DynamoDB table scaffold — PRJ-001 prerequisite

PRJ-001 (pure infrastructure scaffold) defines the `crm_pm_projects` DynamoDB table in `scripts/local-ddb-init.py` and wires four table handles into `app/core/tables.py`. The relevant definition for this ticket (verbatim from the ticket file, section PRJ-001) is:

```
TableDef(
    _resolve_table_name(S.crm_pm_projects_table_name, "crm_pm_projects"),
    "PK", "SK",
    gsi=[
        {"index_name": "GSI1", "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "GSI2", "partition_key": "GSI2PK", "sort_key": "GSI2SK"},
    ],
    attr_types={"GSI2SK": "N"},

```

`GSI2SK` is the integer `created_at` timestamp, which is a numeric sort key — `attr_types={"GSI2SK": "N"}` is **mandatory** per the CLAUDE.md gotcha ("DynamoDB numeric GSI sort keys" section): omitting it causes a `ValidationException` when querying with integer values. The table handle `T.crm_pm_projects` is already accessible once PRJ-001 ships.

PRJ-001 adds `crm_projects_enabled: bool` to `app/core/settings.py` following the exact same pattern as `cart_reminders_enabled` at `app/core/settings.py:821`. The guard helper `_require_crm_projects()` (in `app/routers/crm_projects.py`) raises `HTTPException(404)` when `S.crm_projects_enabled is False`.

All new endpoints use `Depends(require_ui_session)` from `app/services/sessions.py:330`, which returns `{"user_sub": str, "role": str, ...}`. The same shim is replicated in the new CRM router.

### 2.5 Audit and email primitives

- `audit_event(event, user_sub, request, **fields)` lives at `app/services/alerts.py:644`. It writes to the `T.alerts` table via `write_alert` and optionally enriches the payload with identity fields. Any **kwargs become top-level fields on the DDB item and are safe to use for filtering.
- `send_alert_email(to_emails, subject, body_text)` lives at `app/services/alerts.py:459`. In `dev_mode` it writes to a local log file instead of calling SES — full dev/prod parity (SECOPS-007).

`app/core/cursor.py:94` (`encode_cursor`) and `:103` (`decode_cursor`) provide HMAC-signed, version-tagged cursors for DynamoDB `LastEvaluatedKey` pagination. All list endpoints in this ticket use these helpers rather than the un-signed base64 approach used in the legacy projects router at `app/routers/projects.py:173`.

The legacy `ProjectModel` stores `created_at` as an ISO string (`app/models.py:1803`); `CrmProjectModel` uses `int` throughout to align with every other modern service in the codebase (tickets, billing, etc.).

## 3. Data Model

### 3.1 DynamoDB item shape — `crm_pm_projects`

Every CRM project is a single DynamoDB item in `T.crm_pm_projects`:

| Attribute | Type | Value |
|-----------|------|-------|
| `PK` | S | `OWNER#{owner_sub}` |
| `SK` | S | `PROJECT#{project_id}` |
| `GSI1PK` | S | `PROJECT#{project_id}` |
| `GSI1SK` | S | `OWNER#{owner_sub}` |
| `GSI2PK` | S | `STATUS#{status}` (e.g. `STATUS#draft`) |
| `GSI2SK` | **N** | `created_at` (integer Unix seconds) |
| `entity_type` | S | `"crm_project"` |
| `project_id` | S | UUID hex (`uuid4().hex`) |
| `owner_sub` | S | caller's `user_sub` |
| `name` | S | 1–120 chars |
| `description` | S (nullable) | ≤ 2000 chars |
| `status` | S | one of `CrmProjectStatus` values |
| `priority` | N | 0–4 integer |
| `start_date` | N (nullable) | Unix timestamp int |
| `end_date` | N (nullable) | Unix timestamp int |
| `assigned_user_sub` | S (nullable) | any platform `user_sub` |
| `account_id` | S (nullable) | opaque party_id (PTY integration, PRJ-011) |
| `created_at` | N | `now_ts()` at creation |
| `updated_at` | N | `now_ts()` at every write |

**GSI1 (owned-project lookup)**: `GSI1PK=PROJECT#{id}` / `GSI1SK=OWNER#{sub}` — used by `get_crm_project` for O(1) single-item fetch by project ID without needing the owner in the caller (e.g. future member-access path in PRJ-007). The `GSI1SK` value is a string, so no `attr_types` entry is needed for this index.

**GSI2 (status-filtered list)**: `GSI2PK=STATUS#{status}` / `GSI2SK=created_at (int)` — used by `list_crm_projects` when `status_filter` is set. Requires `attr_types={"GSI2SK": "N"}` in the PRJ-001 `TableDef` (already specified there). A query against GSI2 with `KeyConditionExpression = Key("GSI2PK").eq("STATUS#underway") & Key("GSI2SK").gte(0)` returns all `underway` projects in ascending creation order.

**Nullable attributes**: DynamoDB cannot store `None`/`NULL` as a GSI key. `GSI2PK` is always set (every project has a status). `start_date`, `end_date`, `assigned_user_sub`, and `account_id` are stored only when non-null — omit the key entirely on put/update rather than writing `None`.

## 4. API / Service Design

### 4.1 Service — `app/services/crm_projects.py`

All functions import `T` from `app/core/tables` and `S` from `app/core/settings`. Timestamps from `app/core/time.now_ts()`. Cursors from `app/core/cursor.encode_cursor` / `decode_cursor`.

```python
def create_crm_project(
    owner_sub: str,
    name: str,
    *,
    description: Optional[str] = None,
    status: CrmProjectStatus = CrmProjectStatus.draft,
    priority: int = 0,
    start_date: Optional[int] = None,
    end_date: Optional[int] = None,
    assigned_user_sub: Optional[str] = None,
    account_id: Optional[str] = None,
) -> CrmProjectOut:
    ...
```

Raises `HTTPException(400, {"code": "end_before_start"})` when both dates are supplied and `end_date < start_date`. Generates `project_id = uuid4().hex`. Calls `T.crm_pm_projects.put_item(Item=item, ConditionExpression="attribute_not_exists(PK)")` — idempotent guard on accidental double-submit. Returns `CrmProjectOut`.

```python
def get_crm_project(owner_sub: str, project_id: str) -> CrmProjectOut:
    ...
```

Queries GSI1: `Key("GSI1PK").eq(f"PROJECT#{project_id}")`. If no item found or `item["owner_sub"] != owner_sub`, raises `HTTPException(404)`. Ownership is enforced here; PRJ-007 will extend this with shared-member access.

```python
def update_crm_project(
    owner_sub: str,
    project_id: str,
    updates: CrmProjectUpdateIn,
) -> CrmProjectOut:
    ...
```

Fetches the existing item via `get_crm_project` to enforce ownership. Validates `end_before_start` against the _merged_ dates (new value or existing). Builds a DynamoDB `UpdateExpression` from `updates.model_fields_set`. When `status` changes, emits `audit_event("crm_project.updated", owner_sub, None, project_id=project_id, field="status", old_value=old_status, new_value=new_status)` using `app/services/alerts.audit_event:644`. Updates `GSI2PK` when status changes (the partition key must change). Sets `updated_at = now_ts()` unconditionally. Returns refreshed `CrmProjectOut`.

```python
def delete_crm_project(owner_sub: str, project_id: str) -> dict:
    ...
```

Fetches item via GSI1, enforces ownership, calls `T.crm_pm_projects.delete_item(Key={"PK": pk, "SK": sk})`. Returns `{"ok": True}`. **Note**: cascade deletion of task rows (in `T.crm_pm_tasks`, keyed `PK=PROJECT#{project_id}`) is deferred to PRJ-003, which owns the tasks table. PRJ-002 documents the cascade contract but does not implement it — tasks will be orphaned in the `crm_pm_tasks` table until PRJ-003 ships. PRJ-003's `delete_crm_project` wrapper must query `T.crm_pm_tasks` and batch-delete all rows before the project header is deleted.

```python
def list_crm_projects(
    owner_sub: str,
    *,
    limit: int = 20,
    cursor: Optional[str] = None,
    status_filter: Optional[CrmProjectStatus] = None,
    name_query: Optional[str] = None,
) -> CrmProjectListResp:
    ...
```

Two code paths:

- **Primary path** (no `status_filter`): queries on `PK = OWNER#{owner_sub}`, `SK begins_with("PROJECT#")`, `ScanIndexForward=False` (newest first), `Limit=limit`. Decoded cursor from `decode_cursor` is passed as `ExclusiveStartKey`.
- **Status-filter path** (`status_filter` set): queries GSI2 with `Key("GSI2PK").eq(f"STATUS#{status_filter.value}")` and `FilterExpression=Attr("owner_sub").eq(owner_sub)`. GSI2 is a global index across all owners, so the `FilterExpression` restricts to the caller's projects. As noted in CLAUDE.md ("DDB FilterExpression doesn't reduce page size"), the loop must follow `LastEvaluatedKey` until the requested `limit` is satisfied.

When `name_query` is set, an additional `FilterExpression=Attr("name").contains(name_query)` is applied in the primary path only (substring search, case-sensitive; full-text search integration is a PRJ-012 follow-up).

`limit` is clamped to `max(1, min(limit, 100))`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Date validation

- `end_date < start_date` on both `POST` and `PATCH` returns `HTTP 400 {"code": "end_before_start"}`.
- On `PATCH`, the validation is run against the _merged_ state: if only `end_date` is being updated, it is compared against the existing `start_date` already stored in DynamoDB, not against None.
- Either date can be supplied without the other (a project may have only a start date or only an end date).
- Dates are Unix epoch seconds. No timezone conversion is performed server-side — the frontend is responsible for converting display dates to epoch integers before sending them.

### 5.2 Priority semantics

`priority` is an integer `0–4` with no business logic applied at the service layer. Display labels (None / Low / Medium / High / Urgent) are purely a frontend concern. Out-of-range values return `HTTP 422` from Pydantic's `ge=0, le=4` constraint.

### 5.3 Status field on create

Status defaults to `draft` if omitted. All five statuses are accepted on `POST` — a user may create a project directly in `underway` status. Status transition enforcement (restricting which transitions are valid) is intentionally deferred to PRJ-009 to keep this ticket focused on CRUD. PRJ-002 accepts any valid `CrmProjectStatus` value on `PATCH` without transition validation.

### 5.4 GSI2PK update on status change

When `update_crm_project` changes the `status` field, the DynamoDB `UpdateExpression` must include setting the new `GSI2PK = STATUS#{new_status}` alongside the changed `status` attribute. Failing to update `GSI2PK` silently corrupts the status-filter index — the item remains queryable under the old status bucket. The implementation must set both in a single `update_item` call.

### 5.5 Partial update via PATCH

Only attributes present in `updates.model_fields_set` are written. Fields absent from the PATCH body are left at their existing DynamoDB values. To explicitly clear an optional field (e.g. remove `assigned_user_sub`), the client sends `"assigned_user_sub": null`. The service uses DynamoDB's `REMOVE` action in the `UpdateExpression` for null-valued explicit sets.

### 5.6 Concurrent updates

No optimistic concurrency (version counter) is implemented in PRJ-002. A `ConditionExpression="attribute_exists(PK)"` guard on `update_item` ensures the item has not been deleted between the fetch and the write. Full version-checked optimistic concurrency (used in the tickets service at `app/services/tickets.py:466` via `version` attribute) can be added in a later ticket if contention is observed in practice.

### 5.7 Delete and cascade contract

`delete_crm_project` deletes only the project header item. The downstream cascade contract (delete all tasks in `T.crm_pm_tasks` for this project) is owned by PRJ-003. The two-ticket contract is:

1. PRJ-002 ships: `delete_crm_project` deletes the header; tasks are not yet implemented.
2. PRJ-003 ships: PRJ-003 imports `delete_crm_project` and wraps it — first batch-deletes all tasks, then calls the PRJ-002 header delete. The signature of `delete_crm_project` is unchanged.

### 5.8 Unknown status value

Sending `status: "invalid_value"` on `POST` or `PATCH` returns `HTTP 422 Unprocessable Entity` from Pydantic's enum validation before the service layer is reached.

### 5.9 Flag-off behavior

When `CRM_PROJECTS_ENABLED=0`, `_require_crm_projects()` raises `HTTPException(status_code=404)`. No service logic executes, no DynamoDB calls are made, and no audit events are emitted. The frontend is expected to catch the 404 from the list endpoint and render a graceful "coming soon" notice rather than an error page.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

There are no `dev_mode` branches in `app/services/crm_projects.py`. All DynamoDB reads and writes go through the same `T.crm_pm_projects` table handle in both environments. The table handle resolves to DynamoDB Local (port 8001) in dev and to real DynamoDB in prod, transparently, through the same `_safe_table(S.crm_pm_projects_table_name)` wiring established in PRJ-001. `send_alert_email` already provides dev/prod parity at `app/services/alerts.py:459–491` (dev writes to a local log file; prod calls SES).

### 7.2 Idempotency

`create_crm_project` uses a `ConditionExpression="attribute_not_exists(PK)"` guard. A retry of the same request with the same auto-generated `project_id` (UUID) would fail with `ConditionalCheckFailedException` — this is correct behaviour because the retry would be creating a second project, not replaying the first. There is no client-supplied idempotency key for project creation in PRJ-002. If idempotency keys are required (e.g. for mobile offline-sync), a `client_idempotency_key` field can be added in a follow-up.

`update_crm_project` uses `ConditionExpression="attribute_exists(PK)"` to guard against writing to a deleted project. Replaying the same PATCH is safe — DynamoDB's conditional update is idempotent if the field values are identical.

### 7.3 Ownership enforcement

`get_crm_project` fetches by project ID via GSI1 and asserts `item["owner_sub"] == owner_sub`. This is the **only** authorization check in PRJ-002. PRJ-007 extends this to shared members by replacing the strict equality with a `_assert_project_access` call. Until PRJ-007 ships, no other user can read or modify a project they do not own.

### 7.4 Input sanitization

- `name` and `description` are stripped of leading/trailing whitespace in the Pydantic model validator (mirrors the pattern at `app/models.py:1806`).
- `name` of length 0 after strip returns `HTTP 422`.
- `account_id` and `assigned_user_sub` are accepted as opaque strings with no server-side validation. No DynamoDB lookup is performed to confirm they point to real entities in PRJ-002.

### 7.5 Audit events

Every call to `update_crm_project` that changes the `status` field emits an `audit_event` at `app/services/alerts.py:644`. The audit event is best-effort (no transaction guarantee) — audit failure must not roll back the status update. The recommended pattern is:

```python
try:
```

## 8. Backward Compatibility & Migration

### 8.1 No migration required

PRJ-002 writes only to `T.crm_pm_projects`, a new table with no existing data. There is no schema migration for existing tables.

### 8.2 Non-interference with file-grouping projects

The `T.projects` table (file-grouping layer, PK=`OWNER#{user}`, SK=`PROJECT#{id}`) is **never touched** by PRJ-002. The CRM projects table uses the same key naming pattern but is a completely separate physical DynamoDB table. There is zero risk of cross-contamination.

### 8.3 PRJ-001 prerequisite on a running stack

If `scripts/local-ddb-init.py` is run before PRJ-001 ships (i.e. the `crm_pm_projects` table definition is absent), the router will fail with a DynamoDB `ResourceNotFoundException` on the first request. The solution is to run `just restart` after PRJ-001 merges, which recreates all tables via `local-ddb-init.py`. In production, PRJ-001 must be deployed (table creation via Terraform/CloudFormation) before PRJ-002 is deployed.

### 8.4 Future extension points

- `account_id` is stored as an opaque string now and will be resolved to real PTY party records in PRJ-011 without changing the DDB schema.
- `assigned_user_sub` is stored as-is; PRJ-004 will extend this with a `project_resource_type` field.
- The delete endpoint is additive — PRJ-003 wraps it rather than replacing it.

## 10. Open Questions / Assumptions

1. **Search integration**: `list_crm_projects` with `name_query` performs a DynamoDB `Attr("name").contains(...)` filter which is a full-table per-owner scan for that user's projects. For users with thousands of projects this will be slow. A proper solution (integrate with `app/services/search.py`) is deferred to PRJ-012. The current implementation is acceptable for MVP volumes.

2. **Email notification on status change**: PRJ-009 specifies that completing a project sends an email via `send_alert_email`. PRJ-002 emits only an audit event (not an email) on status changes because no email template for generic status changes has been defined. The email requirement is explicitly owned by PRJ-009.

3. **`account_id` validation**: The field is accepted as an opaque string with no validation against real party records. This is correct for PRJ-002 but assumes PTY party IDs are globally unique (not namespaced). If PTY uses `PARTY_GROUP#{id}` as its canonical identifier, the `account_id` field contract should be revisited in PRJ-011.

4. **`assigned_user_sub` validation**: No lookup is performed to confirm the sub belongs to an active platform user. A malformed or deleted `user_sub` will be stored silently. Server-side validation (confirm user exists in `T.users`) can be added in PRJ-007 when the full member model is built.

5. **Project ID format**: Using `uuid4().hex` (32-char lowercase hex, no hyphens). This is consistent with most IDs in the codebase (e.g. ticket IDs at `app/services/tickets.py:434`). If the PRJ-006 template instantiation path needs stable, predictable IDs (e.g. for idempotent instantiation), a `client_project_id` parameter can be added.

6. **Concurrency model**: PRJ-002 does not implement version-based optimistic locking. Concurrent PATCH requests to the same project will last-write-win. This is acceptable for V1 but should be revisited before multi-member concurrent editing is enabled (PRJ-007).
