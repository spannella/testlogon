# INV-003 — Currency conversion at transaction / charge time

**Ticket type:** Feature
**Priority:** P1
**Estimate:** 2d
**Feature flag:** `AOS_INVOICE_CURRENCY_CONVERSION_ENABLED` (default `"0"`, off)

---

## 1. Summary & Goal

When an invoice is created in a non-USD currency, record both the original
currency amount and the USD equivalent computed using the live exchange rate
from the INV-002 currency registry. The USD equivalent and the exchange rate
used are stored on the invoice DDB item at creation time ("snapshot at
transaction time"), satisfying the SuiteCRM AOS gap item "Currency conversion
at transaction/charge time."

This allows accurate financial reporting in a single base currency (USD) while
preserving the multi-currency display amounts for the buyer. No rounding or
conversion is applied to the existing `amount_cents` / `total_cents` fields —
those remain in the invoice's original currency, preserving backward
compatibility for all existing callers and for invoices created when the flag is
off.

With `AOS_INVOICE_CURRENCY_CONVERSION_ENABLED=0` (default) the `create_invoice`
function is byte-for-byte unchanged. No new DynamoDB table is introduced; the
four new fields are additive attributes on the existing
`pk=USER#{sub} / sk=INV#{number}` items.

## 3. Data Model

### No new DynamoDB table

All changes are additive scalar attributes on existing
`pk=USER#{sub} / sk=INV#{number}` items in `T.invoices`. DynamoDB's
schema-less attribute model allows adding these fields without any
`UpdateTable` call.

### New item attributes (all optional / nullable)

| Attribute | Type | Default when absent | Description |
|---|---|---|---|
| `original_currency` | String | `""` | ISO 4217 code of the invoice currency (e.g. `"eur"`). Populated even for USD invoices when the flag is on (`"usd"`). |
| `original_amount_cents` | Number (int) | `0` | Invoice `amount_cents` in the original currency, captured at creation time. |
| `usd_amount_cents` | Number (int) | `0` | USD equivalent of `original_amount_cents`, computed via `convert_amount` at creation time. For USD invoices this equals `original_amount_cents`. |
| `exchange_rate_snapshot` | Number (Decimal) | `null` | `rate_to_usd` used at conversion time (e.g. `1.08` for EUR). Stored for audit reproducibility. Stored as DynamoDB Number; `_FloatSafeTable` at `app/core/tables.py:29` coerces Python `Decimal`/`float` to `Decimal` on write, so no explicit coercion is required at the write site. |

### No `scripts/local-ddb-init.py` change required

The `invoices` TableDef at `scripts/local-ddb-init.py:2269` already carries the
correct GSIs and `attr_types`. The four new attributes are plain scalars — no new
GSI sort key, so no new `attr_types` entry is needed.

### `crm_currencies` table (owned by INV-002)

INV-003 reads from `T.crm_currencies` only through the service-layer functions
`get_exchange_rate` and `convert_amount`. This table is defined, wired, and
tested by INV-002; INV-003 treats it as an opaque dependency.

## 4. API / Service Design

### Service layer — `app/services/invoices.py`

#### `create_invoice` extension

The existing signature at `app/services/invoices.py:272`:

```python
def create_invoice(
    *,
    user_sub: str,
    invoice_type: str,
    amount_cents: int,
    line_items: List[Dict[str, Any]],
    ledger_entry_id: str = "",
    tax_cents: Optional[int] = None,
    seller_id: str = "",
    seller_name: str = "",
    buyer_name: str = "",
    buyer_email: str = "",
    payment_method_summary: str = "",
    currency: str = "usd",
) -> Optional[Dict[str, Any]]:
```

No new parameters are added. The conversion is applied automatically when the
currency is non-USD and both flags are enabled; callers pass `currency="eur"`
exactly as they do today and the conversion is transparent.

Insertion point: after `total_cents = amount_cents + tax_cents` (line 308) and
before `invoice_number = _next_invoice_number()` (line 310). Logic:

```python
# INV-003: snapshot the USD equivalent at transaction time.
_original_currency = (currency or "usd").lower().strip()
_original_amount = amount_cents  # in the invoice currency
_usd_amount = amount_cents       # default: 1:1 (USD or flag off)
_rate_snapshot = None            # Decimal | None

if (
    S.crm_currencies_enabled
    and S.aos_invoice_currency_conversion_enabled
    and _original_currency != "usd"
):
    try:
        from app.services.crm_currencies import convert_amount as _cvt
        from app.services.crm_currencies import get_exchange_rate as _rate
        _rate_snapshot = _rate(_original_currency, "usd")
        _usd_amount = _cvt(amount_cents, _original_currency, "usd")
    except Exception:
        logger.warning(
            "currency conversion failed for %s invoice=%s currency=%s",
            user_sub, invoice_type, _original_currency, exc_info=True,
        )
        # Fail-open: store amount_cents as-is in both fields.
        _rate_snapshot = None
        _usd_amount = amount_cents
```

These four local variables are then added to the `record` dict before
`T.invoices.put_item`:

```python
record["original_currency"] = _original_currency
record["original_amount_cents"] = _original_amount
record["usd_amount_cents"] = _usd_amount
if _rate_snapshot is not None:
    record["exchange_rate_snapshot"] = _rate_snapshot
    # _FloatSafeTable coerces Decimal; no explicit str() conversion needed.
```

#### `_serialize` extension

In `app/services/invoices.py:218`, add the four fields to the returned dict:

```python

"original_amount_cents": _coerce_int(record.get("original_amount_cents")),
```

## 5. Detailed Behavior & Edge Cases

### Normal path (flag on, non-USD currency, known rate)

1. Caller invokes `create_invoice(..., currency="eur", amount_cents=10000)`.
2. `S.crm_currencies_enabled` is `True`, `S.aos_invoice_currency_conversion_enabled`
   is `True`, `_original_currency != "usd"`.
3. `get_exchange_rate("eur", "usd")` returns `Decimal("0.925926...")` (if EUR
   `rate_to_usd = 1.08`; the cross-rate is `1 / 1.08`).
   Wait — the INV-002 spec defines `rate_to_usd` as "1 EUR = 1.08 USD", so
   `convert_amount(10000, "eur", "usd")` applies `10000 × (rate_eur_to_usd /
   rate_usd_to_usd)` = `10000 × (1.08 / 1.0)` = `10800` cents = $108.00 USD.
   `exchange_rate_snapshot = Decimal("1.08")`.
4. `record["original_currency"] = "eur"`, `record["original_amount_cents"] = 10000`,
   `record["usd_amount_cents"] = 10800`, `record["exchange_rate_snapshot"] = Decimal("1.08")`.
5. `_serialize` returns `original_currency="eur"`, `original_amount_cents=10000`,
   `usd_amount_cents=10800`, `exchange_rate_snapshot=1.08`.

### USD invoice (flag on, currency == "usd")

The `if ... and _original_currency != "usd"` guard short-circuits the conversion
block. Record attributes: `original_currency="usd"`,
`original_amount_cents=amount_cents`, `usd_amount_cents=amount_cents`,
`exchange_rate_snapshot=None`. Both amounts are identical; `InvoiceOut` reflects
this correctly.

### Flag off (either flag)

If `S.aos_invoice_currency_conversion_enabled` is `False` (default) or
`S.crm_currencies_enabled` is `False`, the conversion block is not entered.
The four new attributes are still written to `record` with their default values
(`_original_currency = (currency or "usd").lower()`, `_usd_amount = amount_cents`,
`_rate_snapshot = None`). This keeps `_serialize` and `InvoiceOut` consistent
across flag states without a conditional in `_serialize`.

### Unknown / inactive currency (conversion failure, fail-open)

`get_exchange_rate` raises `ValueError` if the currency is not found in
`T.crm_currencies` or if the currency is inactive. The `except Exception` block:

- Logs a warning with `exc_info=True` (for ops visibility).
- Sets `_usd_amount = amount_cents` (no conversion; USD equivalent is treated as
  1:1 with the original).
- Sets `_rate_snapshot = None`.
- Does NOT abort invoice creation; the invoice is persisted normally.

This fail-open design ensures that a missing currency registry entry or DDB
timeout never blocks a payment flow.

### DDB unavailability during `get_exchange_rate`

Same path as unknown currency — the `except Exception` catches `ClientError` and
any other exception from the DDB read inside `crm_currencies`. Fail-open.

### Idempotency

The existing idempotency mechanism (per-ledger marker at
`USER#{sub}#LEDGERMARK / LEDGER#{entry_id}`) fires at `app/services/invoices.py:301`
before the conversion block. A duplicate call with the same `ledger_entry_id`
returns the existing invoice's `_serialize` output, which includes the already-
stored conversion fields. The conversion code is never re-executed on a
duplicate.

### `create_invoice_safe` callers

`create_invoice_safe` (`app/services/invoices.py:373`) is a pass-through wrapper
used by `app/routers/billing.py` and other payment hooks. It gains the new
behavior automatically since it delegates to `create_invoice`. No changes needed
at call sites.

### PDF rendering

This ticket does not modify `_render_invoice_lines`. INV-004 (the sibling
ticket) adds the "USD equivalent:" and "Rate:" lines to the PDF. INV-003 only
stores the data; INV-004 renders it. With INV-003 merged but INV-004 not yet
merged, PDFs are unchanged from today.

### Integer rounding

`convert_amount` in INV-002 returns `int` (rounded to the nearest cent using
Python's `round()`). No fractional cents are stored. `_usd_amount` is always an
`int`; `usd_amount_cents` stored in DDB is a Number attribute.

### Very large amounts

For amounts in currencies with `decimal_places=0` (e.g. JPY), `amount_cents`
is actually whole-yen (no fractional unit). `convert_amount` handles this
uniformly via integer arithmetic; INV-003 imposes no additional constraint.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

There is no `if S.dev_mode` branch in the conversion logic. Both dev (moto
in-process S3/DDB) and prod (real DynamoDB) execute identical code. `T.invoices`
and `T.crm_currencies` are intercepted by moto in dev at the botocore layer; no
mock-vs-real fork is introduced. The `_FloatSafeTable` proxy
(`app/core/tables.py:29`) coerces `Decimal` writes in both environments.

### Idempotency

The ledger-marker idempotency check at `app/services/invoices.py:301` fires
before the conversion block. Duplicate calls with the same `ledger_entry_id`
return the stored invoice without re-computing the exchange rate. The stored
`exchange_rate_snapshot` is the authoritative, immutable record of the rate used
at transaction time — re-running the function would produce a different snapshot
if the rate has since changed, which is exactly what must be avoided.

### Security considerations

- **Exchange-rate immutability**: `exchange_rate_snapshot` is written once at
  creation time and never updated. Subsequent admin changes to the EUR/USD rate
  in `T.crm_currencies` do not retroactively alter existing invoices.
- **No money-out path**: This ticket only stores data. No new charge, refund, or
  ledger-debit operation is introduced. If a future ticket needs to issue a
  refund in a non-USD currency, it must re-read `exchange_rate_snapshot` from
  the invoice and apply `settle_or_reverse_ledger` / `refund_payment` using that
  stored rate — not recompute from the current live rate.
- **Fail-open audit trail**: When conversion fails and the flag is on, a
  `WARNING` log line is emitted with `exc_info=True`. This gives ops visibility
  without blocking the payment. An explicit audit event is not written for
  conversion failures (they are warnings, not security events); anomalies in the
  financial dashboard (INV-004 / platform_financial_dashboard) will surface
  invoices where `usd_amount_cents == original_amount_cents` despite a non-USD
  `original_currency` as a data-quality signal.
- **No new network calls**: The conversion path calls into `T.crm_currencies`
  (DynamoDB), which is the same infrastructure as all other DDB access. There is
  no outbound HTTP call to an external exchange-rate feed (that is in-scope for
  the planned "Admin: live rate fetch" ticket, not INV-003).
- **Decimal precision**: `exchange_rate_snapshot` is stored as a DynamoDB Number
  (arbitrary precision) and serialized to `float` in the API response only for
  JSON display. The DDB item preserves full precision for future audit queries.

## 8. Backward Compatibility & Migration

### Existing invoices (no `original_currency` attribute)

Old DDB items written before INV-003 have no `original_currency`,
`original_amount_cents`, `usd_amount_cents`, or `exchange_rate_snapshot`
attributes. `_serialize` calls `record.get("original_currency")` which returns
`None`; `str(None or "")` yields `""`. Similarly `_coerce_int(None)` yields `0`.
`InvoiceOut` defaults (`original_currency=""`, `original_amount_cents=0`,
`usd_amount_cents=0`, `exchange_rate_snapshot=None`) match exactly. No migration
of existing items is required; no backfill job is needed.

### API clients

The four new fields on `InvoiceOut` have safe defaults and are additive.
Existing API clients that ignore unknown fields (standard JSON deserialization
practice) are unaffected. Clients that use strict-shape deserialization must
add the four optional fields to their type definitions; this is a non-breaking
additive change.

### `create_invoice` callers

All existing callers (`create_invoice_safe`, billing routers, subscription
hooks) pass `currency="usd"` implicitly (the default). With the flag off the
conversion block is skipped entirely. With the flag on and `currency="usd"`,
the `!= "usd"` guard short-circuits and the result is identical to flag-off
behavior.

### DynamoDB table — no schema change

No `UpdateTable` is required in production. The `attr_types` declaration in
`scripts/local-ddb-init.py:2277` already covers the existing numeric GSI sort
keys (`GSI1SK`, `GSI2SK`). The four new plain scalar attributes require no
`attr_types` entry. Running `just restart` in dev will recreate the table
cleanly; in prod, deploying the new code is sufficient — existing items remain
valid, and new items will carry the four additional attributes.

## 10. Open Questions / Assumptions

1. **`convert_amount` direction for non-USD source**: INV-002 defines
   `get_exchange_rate(from_iso, to_iso)` as `from_rate_to_usd / to_rate_to_usd`.
   For `from_iso="eur"`, `to_iso="usd"`: `rate_eur_to_usd / rate_usd_to_usd` =
   `1.08 / 1.0` = `1.08`. So `convert_amount(10000, "eur", "usd")` = `10800`.
   This interpretation must be confirmed with INV-002's implementation before
   shipping. If INV-002's semantics differ, the INV-003 call site is the only
   change needed.

2. **Default platform currency**: The ticket and the ticket file assume USD is
   the platform base currency (`rate_to_usd` on every currency row means
   "how many USD is one unit of this currency"). If the platform's default
   currency is changed by a future Admin ticket, `usd_amount_cents` would need
   renaming to `base_currency_amount_cents`. For now, "USD" is treated as the
   fixed base currency per the INV-002 spec.

3. **`exchange_rate_snapshot` precision for display**: The `InvoiceOut` model
   serializes `exchange_rate_snapshot` as `Optional[float]`. For financial
   audit purposes the raw DDB Number (arbitrary-precision Decimal) should be
   queryable. A future admin-audit endpoint that needs exact precision should
   use `_get_raw` rather than `get_invoice` / `_serialize`.

4. **`total_cents` remains in invoice currency**: This ticket does not change
   the `total_cents` formula; it remains `amount_cents + tax_cents` in the
   invoice currency. If a future ticket needs a `usd_total_cents` (including
   USD-equivalent tax), it can add that field following the same pattern.

5. **INV-002 must land first or concurrently**: If INV-002 is merged after
   INV-003, the `get_exchange_rate` import inside the try/except will simply
   raise `ImportError` (or `ValueError` from the flag check), which is caught
   and triggers the fail-open path. INV-003 is therefore safe to deploy before
   INV-002 is active, with the flag off.

6. **Multi-hop: what if the invoice currency is GBP and the buyer's display
   currency is EUR?** That is a display-layer concern (INV-004) and out of scope
   for INV-003. INV-003 always converts to USD regardless of the buyer's locale.
