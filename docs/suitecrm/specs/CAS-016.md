# CAS-016 — CSAT survey on ticket closure

**Type:** Feature  **Priority:** P2  **Estimate:** 2 days  
**Ticket source:** `docs/suitecrm/CRM_CASES_PORTAL_TICKETS.md`, section "CAS-016"

---

## 1. Summary & Goal

When an agent closes a support ticket (status transition to `"done"`), the platform automatically sends the ticket owner a Customer Satisfaction (CSAT) survey link. The survey is delivered by email and, on completion, its score and optional comment are surfaced on the `TicketOut` response model.

The implementation reuses the existing questionnaire infrastructure — `DynamoQuestionnaireRepository` (`app/services/questionnaires_repository.py`) — for session management and answer storage, `send_alert_email` (`app/services/alerts.py:459`) for delivery, and `audit_event` (`app/services/alerts.py:644`) for the audit trail. No new survey engine is introduced.

With `CRM_CASES_CSAT_ENABLED=0` (the default), the platform is byte-for-byte unchanged: the existing `set_ticket_status` endpoint returns immediately after the status update with no survey side-effect, and the two new `TicketOut` fields (`csat_score`, `csat_comment`) are `None`.

## 3. Data Model

### 3.1 Reuse: `T.questionnaires` (existing table, no schema change)

All CSAT session/answer rows are stored in the existing `questionnaires` DynamoDB table using the existing single-table key scheme.

| Row kind | PK | SK | Key fields |
|---|---|---|---|
| Questionnaire META (admin-created once) | `Q#{questionnaire_id}` | `META` | `status`, `published_version_id` |
| Questionnaire version | `Q#{questionnaire_id}` | `VERSION#{n:06d}` | `version_id`, `schema_json`, `published_slug` |
| CSAT response session | `Q#{questionnaire_id}` | `RESP#{response_session_id}` | `respondent_id`, `status` (`in_progress`/`submitted`), `ref_ticket_id` (new extra field), `started_at` |
| CSAT answers | `Q#{questionnaire_id}` | `ANSWER#{response_session_id}#{question_id}` | `value`, `question_id` |
| Response event | `Q#{questionnaire_id}` | `EVENT#RESP#{response_session_id}#...` | `event_type`, `payload` |

`ref_ticket_id` is an additional field written during `put_response_session`; because DynamoDB items are schema-free it requires no table migration. It is used by `get_csat_result` to look up the session given only a ticket ID.

### 3.2 Additive sub-item in `T.tickets` (no GSI)

A `CSAT#` sub-item is written to the ticket partition once the survey link is dispatched, and updated once the session is submitted.

| Row | PK | SK | Key fields |
|---|---|---|---|
| CSAT dispatch record | `TICKET#{ticket_id}` | `CSAT#META` | `response_session_id`, `questionnaire_id`, `version_id`, `sent_at`, `sent_to_sub`, `survey_url` |

No GSI is needed: `get_ticket` queries the full partition (already fetches `MSG#` and `ACT#` with `begins_with`) so `CSAT#META` is returned in the same query. The SK prefix `"CSAT#"` sorts between `"ACT#"` and `"META"` lexicographically, posing no conflict.

When the survey is submitted the `CSAT#META` row is updated with `csat_score: int`, `csat_comment: str | None`, `completed_at: int`.

### 3.3 `scripts/local-ddb-init.py` — no new table required

No new DDB tables are introduced. The existing `questionnaires` table and `tickets` table are unchanged in schema. No `attr_types` addition is needed because no new numeric GSI sort key is added.

## 4. API / Service Design

### 4.1 New service file: `app/services/ticket_csat.py`

```python
CSAT_SURVEY_TOKEN_TTL_SECONDS: int = 14 * 24 * 3600  # 14 days default; env-overridable

def _csat_secret() -> str:
    """Signing secret: CRM_CASES_CSAT_TOKEN_SECRET → UI_ACCESS_TOKEN_SECRET fallback."""

def _mint_csat_token(ticket_id: str, response_session_id: str, ttl: int) -> str:
    """Produce a signed URL token embedding ticket_id, response_session_id, exp."""

def _verify_csat_token(token: str) -> dict[str, Any] | None:
    """Return payload dict or None if invalid/expired."""

def send_csat_survey(
    ticket_id: str,
    owner_sub: str,
    *,
    repo: DynamoQuestionnaireRepository | None = None,
) -> dict[str, Any] | None:
    """
    1. Guard: S.crm_cases_csat_enabled and S.crm_cases_csat_questionnaire_id set.
    2. Resolve published version_id from repo.get_questionnaire / list_versions.
    3. Mint response_session_id = f"csat_{uuid4().hex[:16]}".
    4. Call repo.put_response_session(..., respondent_id=owner_sub, ref_ticket_id=ticket_id).
    5. Mint signed CSAT URL token (mint_csat_token).
    6. Build survey_url = f"{S.public_base_url}/q/{slug}?session_id={response_session_id}&ref=ticket:{ticket_id}&token={token}".
    7. Write T.tickets CSAT#META sub-item.
    8. Look up owner email via get_profile_identity(owner_sub).
    9. Call send_alert_email([email], subject, body) with survey link.
    10. Emit audit_event("ticket_csat_sent", owner_sub, ...).
    11. Return {"response_session_id": ..., "survey_url": ...} or None.
    """

def get_csat_result(ticket_id: str) -> dict[str, Any] | None:
    """
    1. Read CSAT#META sub-item from T.tickets for ticket_id.
    2. If not present or session_id absent, return None.
    3. Read repo.list_session_answers(questionnaire_id, response_session_id).
    4. Extract rating from answers (question_id = S.crm_cases_csat_rating_question_id).
    5. Extract comment if present.
    6. Return {"csat_score": int|None, "csat_comment": str|None, "completed_at": int|None}.
    """
```

`repo` parameter allows injection of a pre-built `DynamoQuestionnaireRepository` for test isolation.

### 4.6 New webhook endpoint: `POST /public/csat/submit`

A publicly accessible submission endpoint that accepts the signed token, validates it, writes answers to the questionnaire session, and marks it submitted. This avoids requiring the user to have an authenticated session when clicking the survey link in email.

```
POST /public/csat/submit
Auth: none (token in request body)
Gate: if not S.crm_cases_csat_enabled: raise HTTP 404
```

Request model:
```python
class CsatSubmitReq(BaseModel):
    token: str  # signed CSAT token from survey URL
    rating: int = Field(..., ge=1, le=5)
    comment: str | None = Field(default=None, max_length=1000)
```

Handler logic:
1. `_verify_csat_token(req.token)` → payload with `ticket_id`, `response_session_id`, `exp`. Returns 401 `csat_token_invalid` if invalid or expired.
2. Check CSAT#META row exists for `ticket_id` and `response_session_id` matches. Returns 404 `ticket_csat_not_found` if missing.
3. Check session not already `submitted` (idempotent: if already submitted, return 200 with existing score).
4. `repo.save_session_answers(questionnaire_id, response_session_id, {S.crm_cases_csat_rating_question_id: req.rating, S.crm_cases_csat_comment_question_id: req.comment})`.
5. `repo.mark_response_submitted(questionnaire_id, response_session_id, actor_sub=None)`.
6. Update `T.tickets CSAT#META` row: set `csat_score`, `csat_comment`, `completed_at`.
7. `audit_event("ticket_csat_received", payload["owner_sub"], ...)`.
8. Return `{"ok": True, "ticket_id": ticket_id, "csat_score": req.rating}`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Survey not sent when CSAT questionnaire is unconfigured

If `S.crm_cases_csat_questionnaire_id` is empty string or the questionnaire does not exist in DDB, `send_csat_survey` returns `None` immediately after the guard check. No DDB write, no email, no error propagation. The admin must create and publish the questionnaire before CSAT surveys are dispatched.

### 5.2 Owner has no email address

`get_profile_identity(owner_sub).get("email")` (`app/services/profile.py:313`) can be `None` if the user has not set `displayed_email`. In that case `send_alert_email` is not called (no-op: the `to_emails` guard at `app/services/alerts.py:460` returns immediately on empty list). The CSAT#META sub-item is still written, recording `sent_at` and `response_session_id`. The admin can retrieve the survey URL from `GET /tickets/{id}/csat`.

### 5.3 Idempotency — ticket closed twice

If the status is changed from `"done"` back to `"open"` and then to `"done"` again, `send_csat_survey` is called a second time. Guard: before writing a new `CSAT#META` row, check whether one already exists (`self._table.get_item(Key={"pk": _ticket_pk(ticket_id), "sk": "CSAT#META"})` inside `send_csat_survey`). If a row exists and `completed_at` is set (survey already submitted), return `None` silently. If a row exists but `completed_at` is absent (survey still pending), return the existing `response_session_id` without re-sending the email.

### 5.4 Questionnaire `status != "published"`

`send_csat_survey` calls `repo.get_questionnaire(S.crm_cases_csat_questionnaire_id)` and checks `item.get("status") == "published"` and `item.get("published_version_id")`. If the questionnaire is a draft or archived, it returns `None` (no survey sent). This prevents accidental dispatch against an unpublished form.

### 5.5 Concurrent status changes (version conflict)

`set_ticket_status` uses `_apply_header_update_once` / `_conditional_update_meta` for optimistic locking (`app/services/tickets.py:792–805`). The CSAT send happens **after** the status update commits. If two concurrent requests both set `status="done"`, only one succeeds; the second receives `TicketStateError(ticket_update_conflict)` → HTTP 409, and the CSAT hook is never reached for that request.

### 5.6 Survey token expiry

The default token TTL is 14 days (`crm_cases_csat_token_ttl_days`). After expiry, `POST /public/csat/submit` returns 401 `csat_token_expired`. The admin can issue a new survey link via `POST /ui/tickets/{id}/csat/resend` (admin-only endpoint, see section 4 — optional extension for a follow-up ticket).

### 5.7 Portal-submitted tickets (CAS-014)

Tickets created via the portal have `owner_sub` of the form `guest:{email}`. `get_profile_identity("guest:alice@example.com")` will return `None` for `email` (no profile record). In this case, extract the email from the `owner_sub` directly: `if owner_sub.startswith("guest:"): email = owner_sub.removeprefix("guest:")`. This preserves CAS-014 compatibility without needing profile records for guest submitters.

### 5.8 Rating scale validation

`csat_rating` must be integer 1–5. The `POST /public/csat/submit` handler enforces this via Pydantic `ge=1, le=5`. If the CSAT questionnaire's schema also uses a `slider` question type with `min=1, max=1, step=1`, the questionnaire validation path will enforce it redundantly; but the public endpoint enforces it directly without invoking the full questionnaire validation pipeline.

### 5.9 Comment optional, CSAT score mandatory

The `POST /public/csat/submit` handler requires `rating` (no default); `comment` is optional. This ensures `csat_score` is always populated on completion.

### 5.10 `TicketOut` backward compatibility

`csat_score: int | None = None`, `csat_comment: str | None = None`, `csat_sent_at: int | None = None` all default to `None`. Clients that do not expect them will silently ignore the extra fields (Pydantic will serialize them; JSON consumers must tolerate additional keys).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

`send_alert_email` (`app/services/alerts.py:459–491`) already branches on `S.dev_mode`: in dev it writes to `S.dev_email_log`; in prod it calls `boto3 SES`. CAS-016 calls `send_alert_email` with no additional branching. The CSAT#META DDB write uses the standard `T.tickets` handle — the same moto-backed table in dev, real DDB in prod. No `if S.dev_mode` branch is added by CAS-016.

### 7.2 Token security

The CSAT survey token uses `hmac.new(secret, payload, sha256)` — the same scheme as `mint_ws_token` / `verify_ws_token` at `app/core/crypto.py:35`. The payload embeds `ticket_id`, `response_session_id`, and `exp`. The `verify_csat_token` function uses `hmac.compare_digest` for constant-time comparison to prevent timing attacks (`app/core/crypto.py:52`).

The token is included in the email body URL only, never in a cookie or response header. Survey URLs are single-use at the business level: `POST /public/csat/submit` checks whether the session is already `"submitted"` (idempotent re-submission returns existing score) but does not cryptographically burn the token, because CSAT surveys should be accessible for the full TTL window so the customer can fill them in after re-opening the email.

### 7.3 No PII in audit payload

`audit_event("ticket_csat_sent", owner_sub, ...)` records only `ticket_id`, `response_session_id`, and `sent_at`. The survey URL (which contains the signed token) is **not** included in the audit payload.

### 7.4 Survey answer privacy

CSAT answers are stored in the existing `questionnaires` table under the questionnaire owner's partition (admin-created questionnaire). They are readable via `GET /questionnaires/{id}/sessions` (admin only, `app/routers/questionnaires.py`). The submitter is identified by `respondent_id = owner_sub` on the session row.

The `GET /tickets/{ticket_id}/csat` endpoint reads only `csat_score` and `csat_comment` from the CSAT#META ticket sub-item (written at submission time) — it does not re-query the questionnaire table on every call, minimizing cross-table joins.

### 7.5 Idempotency of `send_csat_survey`

The function reads the existing `CSAT#META` sub-item before writing. If already present (any re-close after re-open), it is a no-op. This makes the hook safe to call multiple times for the same ticket without generating duplicate sessions or emails.

## 8. Backward Compatibility & Migration

### 8.1 `TicketOut` — additive fields only

`csat_score: int | None = None`, `csat_comment: str | None = None`, `csat_sent_at: int | None = None` are added with `None` defaults. Existing clients receive these as `null` in JSON and must not break. No existing field is renamed or removed.

### 8.2 `TicketStore.get_ticket` — one extra `get_item` per call

The new `get_item(Key={"pk": ..., "sk": "CSAT#META"})` call is a single-key lookup (no scan, no GSI). It is issued only when the ticket is fetched; with `CRM_CASES_CSAT_ENABLED=0` the `send_csat_survey` path is never executed so `CSAT#META` rows are never written and the lookup always returns `{"Item": None}` (empty result). This is a negligible overhead and requires no migration.

### 8.3 No DynamoDB table schema change

No new tables, no GSI additions, no `attr_types` changes. The `questionnaires` table and `tickets` table store schema-free items.

### 8.4 Existing questionnaire E2E tests unaffected

CAS-016 adds `CSAT#` SK-prefixed items to the `tickets` table and `RESP#` items to the `questionnaires` table, but only under the ticket partition and the CSAT questionnaire partition. Existing E2E tests that query ticket or questionnaire partitions are unaffected because:
- `get_ticket` queries only `MSG#` and `ACT#` prefixes in the existing implementation; the new `get_item("CSAT#META")` is an additive key lookup.
- The CSAT questionnaire ID is a distinct questionnaire not touched by any pre-existing test.

## 10. Open Questions / Assumptions

1. **Single vs. multiple CSAT templates**: This spec assumes one global CSAT questionnaire (`crm_cases_csat_questionnaire_id`). If per-space or per-category templates are needed, that is a follow-up extension. The current design stores only the global questionnaire ID in settings.

2. **Re-close behaviour (re-survey)**: The idempotency rule (section 5.3) is to not re-send if a session already exists. The assumption is that a second closure after re-opening should not pester the customer with a new survey. If the business wants a fresh survey on each closure, the rule should be inverted and the existing session ID should be replaced.

3. **CSAT questionnaire question IDs**: The spec assumes `S.crm_cases_csat_rating_question_id` (default `"csat_rating"`) and `S.crm_cases_csat_comment_question_id` (default `"csat_comment"`) match the `question_id` values in the admin-created questionnaire. If they diverge, `get_csat_result` will return `csat_score: None`. Documentation for admins must make this pairing explicit.

4. **Rating scale**: 1–5 integer is assumed. The questionnaire schema should use `type=slider, min=1, max=5, step=1`. The public submit endpoint enforces `ge=1, le=5` independently.

5. **`displayed_email` vs. Cognito email**: `get_profile_identity` reads `displayed_email` from `T.profile` (`app/services/profile.py:313`). In dev mode with Cognito enabled, a newly registered user may not have `displayed_email` set. Admins must ensure users have this field populated for survey delivery.

6. **Frontend star-badge implementation**: The frontend work (star rating badge in `frontend/src/pages/tickets/TicketsPage.tsx`) is mentioned in the ticket source but not sized here. CAS-016 backend is self-contained; the frontend badge is a follow-up.

## 11. Dependencies

### Hard prerequisites
- **CAS-001** — Scaffolds `S.crm_cases_csat_enabled` and `S.crm_cases_csat_questionnaire_id` settings; without CAS-001 there is no flag to gate on.
- **CAS-004** — Registers `ticket_csat_sent` in `ALERT_EVENT_TYPES` (`alerts.py:134`), in `ALERT_CATEGORIES["updates"]` (`alerts.py:32`), and in `render_ticket_email_template`'s dispatch set (`alerts.py:236`). Without CAS-004, the email template function silently returns `None` for `ticket_csat_sent` events and the HTML email body extension is absent.

### Soft prerequisites (no hard dependency, but improves completeness)
- **CAS-007** (watchers) — If watchers should also receive CSAT results, CAS-016 can extend the `send_csat_survey` call to notify `ticket["watchers"]` with the score. Not in scope for CAS-016.
- **CAS-014** (portal tickets) — Guest tickets (`owner_sub="guest:{email}"`) need the email-extraction fallback (section 5.7). CAS-016 includes this logic; CAS-014 is not a prerequisite but ships this edge case correctly when both are enabled.
- **CAS-002** (case number) — `TicketOut.case_number` would enrich the CSAT email body (`[CASE-0042] How was your support experience?`). CAS-016 uses `ticket_id` in the email subject if `case_number` is absent.

### Sibling CRM tickets that extend the same primitives
- **CAS-008** (SLA), **CAS-009** (escalation) — Both use `_emit_ticket_alerts` and `write_alert`; CAS-016 reuses the same alert dispatch without conflict.
- **CAS-017** (analytics) — May add `csat_score` to the analytics aggregation output. CAS-016 populates the raw `csat_score` on the ticket; CAS-017 can read it from the status-GSI scan.

### Upstream platform primitives reused (no changes needed)
- `DynamoQuestionnaireRepository` (`app/services/questionnaires_repository.py`) — reused verbatim.
- `send_alert_email` / `render_ticket_email_template` (`app/services/alerts.py:459, 235`) — extended by CAS-004 (spec, not yet implemented); CAS-016 depends on CAS-004 being implemented first or must itself register `ticket_csat_sent` in `ALERT_EVENT_TYPES`, `ALERT_CATEGORIES["updates"]`, and `render_ticket_email_template`'s guard set.
- `mint_ws_token` / `verify_ws_token` scheme (`app/core/crypto.py:35`) — adapted as `_mint_csat_token` / `_verify_csat_token`.
- `get_profile_identity` (`app/services/profile.py:305`) — used verbatim for email lookup.
- `audit_event` (`app/services/alerts.py:644`) — used verbatim.
- `TicketStore._conditional_update_meta` + `_apply_header_update_once` (`app/services/tickets.py:723, 792`) — not modified; CSAT#META sub-item writes are plain `put_item`/`update_item` outside the optimistic-lock flow (CSAT data is non-versioned).
