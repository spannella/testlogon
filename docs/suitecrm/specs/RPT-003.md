# RPT-003 — Report grouping (GROUP BY) and aggregate functions

**Type:** Feature | **Priority:** P1 | **Estimate:** 2d
**Area:** CRM Reports & Dashboards
**Source:** `docs/suitecrm/CRM_REPORTS_TICKETS.md` (RPT-003 section, lines 161–193)

---

## 1. Summary & Goal

RPT-003 extends the report execution engine introduced in RPT-002 to support GROUP BY semantics with five standard aggregate functions: COUNT, SUM, AVG, MIN, and MAX. A user can optionally specify a `group_by` field on any report definition; when present, `run_report` groups the post-filter row set by the distinct values of that field and computes the requested aggregates per group rather than returning the raw row list.

This is the AOR "Grouped Report" capability from SuiteCRM. It enables, for example, a tickets report grouped by `status` with a COUNT of rows per status, or a billing ledger report grouped by `type` with SUM and AVG of `amount_cents` per entry type. The grouping and aggregation are pure-Python in-memory operations applied after data retrieval and condition filtering; no DynamoDB schema changes are needed beyond what RPT-001 already provisions.

The goal is to give users quantitative summaries across any supported module without requiring SQL or a warehouse — the data volume per user is bounded (RPT-002 caps raw rows at 2000 before capping grouped output at 2000 groups), and the computation runs in `asyncio.to_thread` so the event loop is never blocked.

## 2. Context & Current State

### 2.1 The RPT-002 run_report pipeline (the surface this ticket extends)

RPT-002 establishes the `run_report(report_id, owner_sub)` function in `app/services/crm_reports.py`. Its execution pipeline is:

1. Load the META row from `T.crm_reports` (`report_id` / `sk="META"`).
2. Verify `owner_sub` matches.
3. Dispatch to a module-specific data adapter (`_fetch_and_filter(module, conditions)`) that iterates the relevant DynamoDB table, applies condition filtering client-side, and yields raw item dicts.
4. Project each dict to the requested `fields` list, coercing values to strings.
5. Cap the row list at 2000 rows.
6. Write a `RUN#` row back to `T.crm_reports` with `output_rows` (JSON), `row_count`, `run_at`, `status`.
7. Return a `ReportRunOut`.

RPT-003 inserts a new step 4.5 between projection and capping: if `group_by` is non-None on the report definition, call `_apply_group_by(projected_rows, group_by_field, aggregates)` and replace the row list with group rows before capping.

### 2.2 Data adapter iteration and the Decimal coercion pattern

All six module data adapters in RPT-002 yield raw DynamoDB item dicts. DynamoDB returns numeric attributes as Python `Decimal` (boto3 numeric type). The `_to_decimal` helper in `app/core/tables.py:11` converts `float → Decimal` on writes; the mirror problem on reads is that `Decimal("150.00")` must be coerced to `float` before arithmetic (averaging, summing). The canonical safe coercion pattern used throughout the codebase is `float(Decimal(...))` or equivalently the `_to_decimal`-safe round-trip. RPT-003 must apply this coercion in `_apply_group_by` before any arithmetic aggregate.

### 2.3 The billing ledger's amount_cents field

The billing ledger rows fetched by `_iter_billing_entries` in `app/services/csv_export.py:52` carry `amount_cents` (integer cents). The `_format_billing_row` formatter at `app/services/csv_export.py:138` reads it as `int(item.get("amount_cents", 0))`. In DynamoDB the stored type is `N`; boto3 deserialises it as `Decimal`. The `_apply_group_by` function must call `int(item.get("amount_cents", 0) or 0)` (with a `Decimal`-safe coercion) before summing. The RPT-002 adapter projects raw item fields to strings for the output row, but `_apply_group_by` operates on the pre-projection dicts, so numeric fields are still in their raw `Decimal` form at that stage.

## 3. Data Model

### 3.1 No new DynamoDB tables

RPT-003 introduces no new tables. All storage uses `T.crm_reports`, which was provisioned by RPT-001 with:

- PK `report_id` (S), SK `sk` (S)
- META row (`sk="META"`) — the report definition
- RUN row (`sk="RUN#{run_ts:010d}#{run_id}"`) — the last execution result
- `owner-reports-index` GSI: `GSI1PK=OWNER#{owner_sub}` / `GSI1SK=created_at` (N)

RPT-003 adds two fields to the META row, persisted as part of the report definition:

| Field | DDB type | Description |
|---|---|---|
| `group_by` | S (nullable / absent) | Field name to group on; absent means ungrouped |
| `aggregates` | S (JSON-encoded list) | Serialised `List[AggregateSpec]`; absent means `[]` |

These are stored as JSON strings within the META item using the same `json.dumps` / `json.loads` pattern used for `fields` and `conditions` in RPT-002. No additional GSIs or `attr_types` changes are needed.

### 3.2 RUN row output shape for grouped reports

When `group_by` is set, the RUN row's `output_rows` JSON contains group rows rather than raw projected rows. Each group row is a flat dict:

```json
{
  "status": "open",
  "status_COUNT": 14,
  "amount_cents_SUM": 284500,
  "amount_cents_AVG": 20321.4
}
```

The `columns` list in `ReportRunOut` is constructed from the group-row keys in a deterministic order: `[group_by_field] + [f"{agg.field}_{agg.function}" for agg in aggregates]`.

The `row_count` in the RUN row reflects the number of groups (distinct values of the `group_by` field), not the number of raw rows scanned.

### 3.3 COUNT on wildcard field

When `AggregateSpec.field = "*"` and `function = "COUNT"`, the aggregate counts the number of rows in the group regardless of any field's value. The column name in the output is `*_COUNT`. This matches SuiteCRM AOR convention for row-count aggregates.

### 4.2 Service additions (`app/services/crm_reports.py`)

#### 4.2.1 `_coerce_numeric(value: Any) -> float`

A small private helper that safely coerces a DynamoDB numeric value (which may arrive as `Decimal`, `int`, `float`, or `str`) to a Python `float` for arithmetic:

```python
from decimal import Decimal

def _coerce_numeric(value: Any) -> float:
    if value is None:
        return 0.0
    if isinstance(value, Decimal):
        return float(value)
    try:
        return float(value)
    except (TypeError, ValueError):
        return 0.0
```

This mirrors the pattern used in `app/services/csv_export.py:138` (`int(item.get("amount_cents", 0))`) and in `app/services/platform_financial_dashboard.py` where raw DynamoDB amounts are cast before summing.

#### 4.2.2 `_apply_group_by(rows, group_by_field, aggregates) -> List[Dict[str, Any]]`

Pure Python, no DynamoDB calls. Takes the pre-projection raw item dicts (still carrying `Decimal` numeric fields), groups them, and returns a list of group-summary dicts.

```python
import collections

def _apply_group_by(
    rows: List[Dict[str, Any]],
    group_by_field: str,
    aggregates: List["AggregateSpec"],
) -> List[Dict[str, Any]]:
    """Group rows by group_by_field and compute aggregate functions per group.

    Operates on raw DynamoDB item dicts (Decimal numeric values).
    Returns a list of group-summary dicts with keys:
      {group_by_field: value, "<field>_<FUNC>": value, ...}

    The group key is the string representation of the group_by_field value
    (or the empty string "" for missing/None values).
    """
    groups: Dict[str, List[Dict[str, Any]]] = collections.defaultdict(list)
    for row in rows:
        key = str(row.get(group_by_field, "") or "")
        groups[key].append(row)

    result = []
    for group_key, group_rows in groups.items():
        summary: Dict[str, Any] = {group_by_field: group_key}
        for agg in aggregates:
            col_name = f"{agg.field}_{agg.function}"
            if agg.function == "COUNT":
                if agg.field == "*":
                    summary[col_name] = len(group_rows)
                else:
                    # COUNT non-null values of a specific field
                    summary[col_name] = sum(
                        1 for r in group_rows if r.get(agg.field) is not None
                    )
            else:
                numeric_vals = [
                    _coerce_numeric(r.get(agg.field))
                    for r in group_rows
                    if r.get(agg.field) is not None
                ]
                if not numeric_vals:
                    summary[col_name] = None
                elif agg.function == "SUM":
                    summary[col_name] = sum(numeric_vals)
                elif agg.function == "AVG":
                    summary[col_name] = sum(numeric_vals) / len(numeric_vals)
                elif agg.function == "MIN":
                    summary[col_name] = min(numeric_vals)
                elif agg.function == "MAX":
                    summary[col_name] = max(numeric_vals)
        result.append(summary)
    return result
```

Key design choices:
- Missing `group_by_field` values are bucketed under the empty string `""`, not silently dropped. This is consistent with SQL `GROUP BY` treating NULL as a distinct group.
- `None` values for the aggregate field are excluded from numeric computations (not counted as zero), consistent with SQL aggregate semantics (`SUM` of no rows is `NULL`, not 0). The output is `None` rather than `0` for empty numeric sets.
- The function is deterministic: group order is `dict` insertion order (Python 3.7+), which is the order groups are first encountered as rows are iterated. This matches the output of the raw row scan (scan order from DynamoDB).
- No sorting of groups is performed. If the caller wants sorted output (e.g., by count descending), that is a future RPT-005 chart concern.

#### 4.2.3 `run_report` integration

The existing `run_report` function in RPT-002 is modified to call `_apply_group_by` after filtering and before capping. The change is a single conditional block inserted between the condition-filter step and the 2000-row cap:

```python
# --- After _fetch_and_filter returns filtered raw rows ---
raw_rows: List[Dict[str, Any]] = list(filtered_rows)

if definition.get("group_by"):
    group_by_field = definition["group_by"]
    aggregates_data = json.loads(definition.get("aggregates", "[]"))
    aggregates = [AggregateSpec(**a) for a in aggregates_data]
    grouped = _apply_group_by(raw_rows, group_by_field, aggregates)
    # Columns for grouped output: [group_by_field] + [f.field_FUNC for f in aggregates]
    columns = [group_by_field] + [f"{a.field}_{a.function}" for a in aggregates]
    output_rows = grouped[:2000]   # cap at 2000 groups
    row_count = len(output_rows)
else:
    # Ungrouped path (RPT-002 unchanged)
    columns = definition["fields"]
    output_rows = [_project_row(r, columns) for r in raw_rows[:2000]]
    row_count = len(output_rows)
```

`_project_row` is the RPT-002 helper that projects a raw item dict to a list of string values matching the requested `fields` list. It is not called for grouped output because grouped rows are already structured dicts with aggregate column names as keys — the frontend renders them via the `columns` list.

## 5. Detailed Behavior & Edge Cases

### 5.1 Ungrouped reports are byte-for-byte unchanged

If `group_by` is `None` (the field is absent from the META row or explicitly `null`), `run_report` takes the existing RPT-002 code path without modification. The `aggregates` list is ignored in this case (the model validator prevents a non-empty `aggregates` without `group_by`). All existing RPT-002 tests remain green.

### 5.2 COUNT(*) semantics

`AggregateSpec(field="*", function="COUNT")` counts all rows in the group regardless of field presence. The output column is `*_COUNT`. The `"*"` sentinel is validated by the `field` pattern in `AggregateSpec` (no pattern restriction is applied to `field`; the `function` field carries the `^(SUM|AVG|COUNT|MIN|MAX)$` pattern constraint).

### 5.3 COUNT on a named field

`AggregateSpec(field="amount_cents", function="COUNT")` counts the number of rows where `amount_cents` is not `None`. This matches SQL `COUNT(column)` semantics (excludes NULLs). The output column is `amount_cents_COUNT`.

### 5.4 SUM/AVG/MIN/MAX on a missing field

If `group_by_field` is `"status"` and `aggregates=[AggregateSpec(field="nonexistent_field", function="SUM")]`, all rows in every group will have `r.get("nonexistent_field") is None`, so `numeric_vals` is empty and the output for that column is `None` (not 0). This is the correct SQL-equivalent behaviour.

### 5.5 Mixed-type field values

If a field contains both numeric and non-numeric values (e.g., `amount_cents` is sometimes a string in legacy data), `_coerce_numeric` swallows `ValueError` and returns `0.0` for the non-coercible values. This prevents a single bad row from crashing the entire aggregate. The behaviour mirrors `app/services/csv_export.py:248` which wraps each formatter call in `try/except` with a `logger.warning`.

### 5.6 Empty group_by field values (NULL/missing)

Rows where the `group_by_field` attribute is absent or `None` are bucketed under the group key `""` (empty string). This group appears in the output with the key `{group_by_field: ""}`. Callers (dashboard, chart renderer) should handle empty-string group keys by displaying them as "(none)" or similar.

### 5.7 Group count cap

The 2000-row cap applies to groups, not raw rows. A report with 50,000 tickets and 12 distinct status values produces 12 group rows, well within the cap. A pathological report grouping on a high-cardinality field (e.g., `ticket_id`) could produce up to 2000 groups before truncation. No warning is emitted at the cap boundary in this ticket; a `truncated: bool` field on `ReportRunOut` is an RPT-005 follow-up.

### 5.8 AVG precision

`sum(numeric_vals) / len(numeric_vals)` returns a Python `float`. When written to the RUN row's `output_rows` JSON via `json.dumps`, Python floats serialize as standard JSON numbers. When written to DynamoDB via `T.crm_reports.put_item`, the `_FloatSafeTable._to_decimal` coercion (`app/core/tables.py:20`) converts the `float` to `Decimal(str(value))`, which stores as a DynamoDB Number with up to 38 significant digits. On read-back, the `Decimal` is coerced back to `float` by the frontend JSON serialiser. No precision loss beyond standard IEEE 754 double is introduced.

### 5.9 Duplicate aggregate column names

If the caller submits two `AggregateSpec` with the same `field` and `function` (e.g., `[{"field":"amount_cents","function":"SUM"},{"field":"amount_cents","function":"SUM"}]`), the output dict will have duplicate keys, with the second write overwriting the first. A `@model_validator` deduplication check on `aggregates` is recommended: raise `ValueError` if any `(field, function)` pair appears more than once. This is enforced at model validation time before any DynamoDB writes.

### 5.10 `group_by` field not in `fields` list

The `fields` list controls which fields are returned for ungrouped rows. For grouped reports, the `fields` list is ignored entirely — the output columns are `[group_by_field] + [agg cols]`. A `group_by` value that is not in `fields` is therefore valid. However, if the `group_by_field` does not exist on any raw item (e.g., typo), all rows bucket under `""` and the report returns a single group with key `""`. No 422 is raised; the data simply shows a single empty-key group.

### 5.11 Thread safety of `_apply_group_by`

`_apply_group_by` is a pure function with no shared state. It creates local `defaultdict` and list objects. It is safe to call from `asyncio.to_thread` (multiple concurrent run requests each get their own call with independent locals).

### 5.12 Interaction with RPT-004 (scheduled delivery)

RPT-004's `run_due_report_schedules` calls `crm_reports.run_report(report_id, owner_sub)` and serialises the result to CSV. For grouped reports, `ReportRunOut.columns` and `ReportRunOut.rows` carry the grouped output. The `generate_csv_rows` generator in `app/services/csv_export.py:194` is extended by RPT-009 to support new sources; RPT-004 will use a direct `csv.writer` over `columns` + `rows` rather than the module-specific `generate_csv_rows` dispatcher. This is consistent with RPT-004's design note: "serialises result to CSV using the same `generate_csv_rows` pattern."

### 5.13 Interaction with RPT-005 (charts)

Grouped reports are the primary input for pie and bar charts. When `chart_type="pie"`, the `x_field` is typically the `group_by_field` (e.g., `"status"`) and the `y_field` is an aggregate column (e.g., `"*_COUNT"`). RPT-005 persists these in `ChartConfig` and the frontend maps them to recharts data keys. RPT-003 does not implement charts; it provides the structured output that RPT-005 consumes.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No dev_mode branches

`_apply_group_by` is pure Python with no DynamoDB calls, no network calls, and no AWS SDK usage. It runs identically in dev (moto-backed DynamoDB Local) and production. There is no `if S.dev_mode` branch in this ticket. The RPT-002 data adapters that supply the raw rows already run identically across environments (`_iter_billing_entries` uses `T.billing` which is a `_FloatSafeTable` backed by DynamoDB Local in dev and real DynamoDB in prod).

### 7.2 Idempotency of run_report

Running the same grouped report twice writes two `RUN#` rows (with different `run_ts` and `run_id` suffixes in the SK). Each run is a fresh full scan + group computation. The latest RUN row is not identified by any unique constraint — the service returns the most recent by querying `sk begins_with "RUN#"` and taking the lexicographically last SK (which sorts by `run_ts`). This is the same idempotency model as RPT-002.

### 7.3 Ownership enforcement

Ownership is enforced in `get_report` before `run_report` reads the definition: a `PermissionError` is raised (mapped to HTTP 403 by the router) if `owner_sub` does not match the META row's `owner_sub`. There is no admin bypass for report execution — an ADMIN or ROOT user running a report they do not own receives a 403. This is intentional: reports may contain sensitive user-scoped data, and ownership is the correct isolation boundary. An admin inspection path (if needed) is a future security-review item.

### 7.4 Aggregate function injection safety

The `function` field of `AggregateSpec` is validated by the Pydantic `pattern=r"^(SUM|AVG|COUNT|MIN|MAX)$"` constraint before reaching `_apply_group_by`. The `field` and `group_by_field` values are used as dict keys (`r.get(field)`) and string prefixes in column names — they never appear in a DynamoDB expression string, so there is no expression injection risk. The `group_by_field` string is included in the output JSON column names; it is bounded to 100 characters by the `max_length=100` field validator.

### 7.5 Output row JSON size

The RUN row stores `output_rows` as a JSON string. A grouped report produces at most 2000 group rows, each with at most 11 keys (1 group-by key + 10 aggregate keys). DynamoDB item size limit is 400 KB. A conservative estimate: 2000 groups × 11 keys × 50 bytes/key ≈ 1.1 MB, which exceeds the limit if all groups are wide. To stay within the 400 KB DynamoDB item limit, the 2000-group cap combined with a 10-aggregate cap should be verified empirically. If needed, a follow-up can store `output_rows` in S3 (mirroring the `_process_export_s3` path in `app/services/audit_export_pipeline.py`) and store only the S3 key on the RUN row. For this ticket, the 2000 × 11 ceiling is an accepted risk noted in Open Questions.

### 7.6 Audit logging

`run_report` calls `audit_event("crm_report.run", owner_sub, report_id=report_id, row_count=row_count, grouped=bool(group_by_field))` via `app/services/alerts.audit_event` (`app/services/alerts.py:644`). This is fire-and-forget (best-effort, `try/except`). The `grouped=True` flag makes it easy to filter grouped report executions in the audit log.

## 8. Backward Compatibility & Migration

### 8.1 Existing reports are unaffected

Reports created before RPT-003 land have no `group_by` or `aggregates` fields in their META rows. When `get_report` reads them, `definition.get("group_by")` returns `None` and `definition.get("aggregates", "[]")` returns `"[]"`. The `run_report` function takes the ungrouped path. `ReportOut.group_by` defaults to `None` and `ReportOut.aggregates` defaults to `[]`. No migration is required.

### 8.2 Model backward compatibility

`ReportCreateIn.group_by` defaults to `None` and `ReportCreateIn.aggregates` defaults to `[]`. Existing callers that do not supply these fields receive responses identical to pre-RPT-003 behaviour. The OpenAPI schema gains two new optional fields; no breaking change to existing API consumers.

### 8.3 `update_report` on existing reports

An existing report can be upgraded to a grouped report by sending a `PATCH` with `group_by` and `aggregates` set. This writes the new fields to the META row and future `run_report` calls produce grouped output. Conversely, patching `group_by=null` with `aggregates=[]` removes grouping from a previously grouped report. The model validator enforces the `group_by` ↔ `aggregates` mutual-presence constraint on every update.

### 8.4 RUN rows from before RPT-003

RUN rows written by RPT-002 (before grouping was introduced) have `output_rows` containing projected row lists (not group-row dicts). The router reads the most recent RUN row; if the most recent run was created before RPT-003, its `columns` reflects the raw `fields` list and its `rows` are projected row arrays. After RPT-003 lands, the first `POST /{id}/run` on a now-grouped report writes a new RUN row with grouped output; the old rows are superseded. No migration of old RUN rows is needed.

## 10. Open Questions / Assumptions

1. **DynamoDB RUN row size limit (400 KB)**: A grouped report with 2000 groups and 10 aggregates may approach the 400 KB DynamoDB item limit. The current design stores `output_rows` as JSON in the RUN row item. If the sum of all group-row JSON exceeds ~380 KB, `put_item` will fail with `ValidationException: Item size has exceeded the maximum allowed size`. A safe fallback (not in scope for this ticket) is to store oversized results in S3 (key under `crm-report-runs/{report_id}/{run_id}.json`) and write only the S3 key in the RUN row, mirroring `_process_export_s3` in `app/services/audit_export_pipeline.py`. This is deferred to a follow-up ticket. For this ticket we accept the 400 KB risk for large grouped outputs.

2. **Group ordering**: Groups are returned in iteration-encounter order (the order rows come back from DynamoDB scan/query). For tickets grouped by `status`, the ordering is non-deterministic across runs (DynamoDB scan order is not guaranteed). If stable ordering is required (e.g., for frontend chart consistency), a `sort_groups_by` field (defaulting to `group_key_asc`) can be added in a follow-up. This ticket makes no ordering guarantee.

3. **`group_by_field` must match a field returned by the module adapter**: The `group_by` value is not validated against the module's known fields at report creation time (that would require a field registry). If `group_by="nonexistent"`, the report runs successfully but all rows bucket under `""`. A future field-registry validation could catch typos at creation time.

4. **Whether `fields` is meaningful for grouped reports**: For grouped output, the `fields` list is currently ignored — the output columns are computed from `group_by` + `aggregates`. Should `fields` still be required (`min_length=1`)? The current spec retains the requirement (from RPT-002) so the report definition is always valid for both grouped and ungrouped use. A follow-up could relax `min_length` to 0 for grouped-only reports.

5. **COUNT named-field semantics for non-null check**: The spec defines `COUNT(field)` as counting non-null values. Some implementations treat `COUNT(field)` as `COUNT(*)` when the field is non-null in the vast majority of rows. Confirm with the product team that the SQL-standard non-null semantics are the expected behaviour for the CRM audience.

6. **Interaction with RPT-009 CSV export of grouped reports**: RPT-009 extends `GET /ui/export/csv` for new module sources. Grouped report output (produced by `run_report` and returned as `ReportRunOut`) is not a new CSV source in RPT-009's scope — it is served by `POST /{id}/run`. A "download grouped report as CSV" path should be specified in RPT-004 (scheduled delivery) or a separate export sub-ticket.
