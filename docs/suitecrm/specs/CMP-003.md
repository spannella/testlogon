# CMP-003 — Email open-tracking pixel

## 1. Summary & Goal

CMP-003 adds a CAN-SPAM/GDPR-standard 1×1 transparent GIF open-tracking pixel to the campaign email infrastructure. Every outgoing campaign HTML email body gets a pixel `<img>` tag appended automatically at send time. When a recipient's mail client loads the image, the platform's public GIF endpoint records an open event in DynamoDB using the existing MKT-010 `TrackingCodes` table, making the open event indistinguishable from a click-visit for attribution rollup purposes (distinguished only by the `event_type="open"` attribute on the VISIT row).

The primary goals are:

1. **Open-rate visibility**: operators can measure the percentage of recipients who opened a campaign email, feeding into the per-variant A/B analysis in CMP-007.
2. **Reuse, not duplication**: no new DynamoDB table; VISIT rows are appended to the existing `T.tracking_codes` table via an additive `event_type` attribute on `record_visit`.
3. **Zero footprint when flag is off**: with `S.marketing_campaigns_enabled=False` the pixel endpoint still returns the GIF (to prevent broken-image icons in already-sent emails) but skips all DDB writes. The campaign send path is unchanged — no pixel injection occurs when the flag is off.

## 3. Data Model

### No new DynamoDB table

CMP-003 appends VISIT rows to the existing `T.tracking_codes` table defined by MKT-002/MKT-010. No new table, no new GSI, no `scripts/local-ddb-init.py` change.

### VISIT row — additive `event_type` attribute

CMP-003 extends the VISIT row schema (MKT-010) with a single additive attribute:

| Attribute | Type | New in CMP-003 | Notes |
|-----------|------|----------------|-------|
| `pk` | S | No | `TRACK#{code_slug}` |
| `sk` | S | No | `VISIT#{ts:010d}#{nonce}` |
| `code_slug` | S | No | Denormalized for `ByCodeTs` GSI |
| `ts` | N | No | Unix timestamp; `ByCodeTs` GSI sort key |
| `party_id` | S | No | `"anon"` for pixel fetches (no session) |
| `referrer` | S | No | Optional; truncated to 500 chars |
| `event_type` | S | **Yes** | `"click"` or `"open"`. Absent on pre-CMP-003 rows. |
| `ip_address` | S | **Yes** | Client IP from request (for spam/bot detection). Absent on pre-CMP-003 click rows (additive). |
| `user_agent` | S | **Yes** | `User-Agent` header, truncated to 256 chars. Absent on pre-CMP-003 click rows (additive). |

The existing MKT-010 `visit_count` counter on the META row is incremented for **both** click-visits and open-visits. When the CMP-005/CMP-007 attribution rollup (MKT-005) needs to separate opens from clicks, it queries `VISIT#` rows by SK prefix and filters on `event_type`. This is a post-query application filter — because `event_type` is not a GSI key, filtering is done in Python after the `query()` call and must loop via `LastEvaluatedKey` (per CLAUDE.md "DDB FilterExpression doesn't reduce page size").

The `ByCodeTs` GSI (PK=`code_slug`, SK=`ts` N) already covers time-series queries over all VISIT rows for a code. No new GSI is required.

### `scripts/local-ddb-init.py` — no change required

The `TrackingCodes` `TableDef` (MKT-002) already declares `attr_types={"created_at": "N", "ts": "N"}`. The new `event_type`, `ip_address`, and `user_agent` attributes are plain string attributes on VISIT rows — not key attributes — so no `attr_types` entry is needed. No `TableDef` modification is required by CMP-003.

### `app/core/tables.py` — no change required

`T.tracking_codes` is added by MKT-002. CMP-003 reads and writes to this handle without adding a new field to the `Tables` dataclass.

### `app/core/settings.py` — additive settings (Section 6)

Two new settings are added (detailed in Section 6): `marketing_open_tracking_enabled` and `marketing_open_tracking_bot_ignore_uas`. Both are read-only at runtime after startup.

### 4.1 Public GIF endpoint (no auth)

**Location**: `app/routers/marketing_campaigns.py` (MKT-011 public router, registered in `app/main.py` without `require_ui_session`).

**Declaration must appear BEFORE the existing MKT-011 campaign path-parameter routes** to prevent FastAPI capturing the literal path segment `t` as a `campaign_id` path parameter. The MKT-011 spec already notes that public routes are declared before dynamic routes.

```python
GET /ui/marketing/t/{code_slug}/open.gif
```

**Parameters**:
- `code_slug: str` — path parameter, the tracking code slug.
- `request: Request` — FastAPI `Request` object for IP and User-Agent extraction.

**Response**: `Response(content=_TRANSPARENT_GIF, media_type="image/gif")` with additional headers:
- `Cache-Control: no-store, no-cache`
- `Pragma: no-cache`
- `X-Content-Type-Options: nosniff`

**Handler logic**:

```python
@router.get("/t/{code_slug}/open.gif", include_in_schema=False)
async def campaign_open_pixel(code_slug: str, request: Request) -> Response:
    if S.marketing_campaigns_enabled and S.marketing_open_tracking_enabled:
        ua = request.headers.get("user-agent", "")[:256]
        if not _is_bot_ua(ua):
            ip = _client_ip(request)
            await anyio.to_thread.run_sync(
                lambda: _record_open_safe(code_slug, ip, ua)
            )
    return Response(
        content=_TRANSPARENT_GIF,
        media_type="image/gif",
        headers={
            "Cache-Control": "no-store, no-cache",
            "Pragma": "no-cache",
            "X-Content-Type-Options": "nosniff",
        },
    )
```

The `_record_open_safe` helper wraps `record_visit` in a `try/except` so a DDB failure never prevents the GIF from being returned:

```python
def _record_open_safe(code_slug: str, ip: str, ua: str) -> None:
    try:
        from app.services.tracking_codes import record_visit
        record_visit(
            code_slug,
            party_id="anon",
            event_type="open",
            ip_address=ip,
            user_agent=ua,
        )
    except Exception:
        logger.debug("open-pixel record_visit failed for code=%s", code_slug)
```

`_client_ip` extracts the real IP using `X-Forwarded-For` / `X-Real-IP` headers. The `anyio.to_thread.run_sync` call keeps the async endpoint non-blocking while the synchronous `record_visit` (which calls DDB) runs in a thread pool. [CORRECTED: the spec claims this pattern is "used throughout `app/routers/browser_ssh_terminal.py`" but `browser_ssh_terminal.py` does NOT use `anyio` — it uses `asyncio.wait_for` / `asyncio.TimeoutError` (`browser_ssh_terminal.py:838–941`). `anyio.to_thread.run_sync` IS used in `app/routers/messaging.py:13132` and `app/routers/broadcast.py:1915`. ### 4.2 `record_visit` extension (`app/services/tracking_codes.py` — MKT-010)

The existing MKT-010 signature:

```python
def record_visit(
    code_slug: str,
```

CMP-003 extends it with additive keyword-only parameters:

```python

    code_slug: str,
    *,
    party_id: str = "anon",
    referrer: Optional[str] = None,
    event_type: str = "click",          # NEW — "click" | "open"

    user_agent: Optional[str] = None,   # NEW

```

The implementation change is minimal: the `Item` dict passed to `T.tracking_codes.put_item` for the VISIT row gains three conditional attributes:

```python
visit_item = {
    "pk": f"TRACK#{code_slug}",
    "sk": f"VISIT#{ts:010d}#{nonce}",
    "code_slug": code_slug,
    "ts": ts,
    "party_id": party_id,
}

    visit_item["referrer"] = referrer[:500]
if event_type != "click":          # omit the attribute on click rows (backward compat)
    visit_item["event_type"] = event_type
```

The decision to omit `event_type` on click rows (leaving the attribute absent rather than writing `"click"`) ensures pre-CMP-003 and post-CMP-003 click rows are handled uniformly by the attribution rollup: rows without `event_type` are treated as `"click"` via `item.get("event_type", "click")`.

### 4.3 `_build_message_body` extension (`app/services/marketing_campaigns.py` — MKT-009)

The MKT-009 `_build_message_body` function builds the email body from either a plain-text template or a CMP-002 HTML template. CMP-003 adds pixel injection at the end of the HTML path:

```python
def _build_message_body(
    campaign: dict,
    merge_vars: dict,
    *,
    owner_id: str,
) -> tuple[str, Optional[str]]:
    """Returns (body_text, body_html | None).
    body_html is None when no HTML template is linked.
    """
    # ... existing MKT-009 + CMP-002 logic ...

    # CMP-003: append open-tracking pixel to HTML body only
    if body_html is not None and S.marketing_open_tracking_enabled:
        code_slug = campaign.get("tracking_code")
        if not code_slug:
            # Create a synthetic per-campaign open-tracking code on first use
            code_slug = _ensure_open_tracking_code(campaign, owner_id)
        if code_slug:
            pixel_url = (
                f"{S.public_base_url}/ui/marketing/t/{code_slug}/open.gif"
            )
            pixel_tag = (
                f'<img src="{pixel_url}" width="1" height="1" '
                f'alt="" style="display:none" />'
            )
            # Inject before closing </div></div></body></html> of _wrap_html output
            body_html = body_html.replace(
                "</div></div>\n</body>", f"{pixel_tag}\n</div></div>\n</body>", 1
            )

    return body_text, body_html
```

The `str.replace(..., 1)` (count=1, replace first occurrence only) is safe because `_wrap_html` (`alert_email_templates.py:16`) produces exactly one `</div></div>\n</body>` sequence. [VERIFIED: `app/services/alert_email_templates.py:37` — actual HTML closing sequence is `</div></div>\n</body>\n</html>` (line 37 is `</div></div>`, line 38 is `</body>`, line 39 closes with `</html>"`). The f-string uses Python `"""\` multi-line — there is NO `\n` between `</div></div>` and `</body>`; they are on adjacent lines in the f-string which Python renders as a literal newline. The `str.replace` target `"</div></div>\n</body>"` is therefore correct.] If the structure changes this replacement silently appends at the end of `body_html` via a fallback:

```python
if "</div></div>" in body_html:
    body_html = body_html.replace("</div></div>\n</body>", f"{pixel_tag}\n</div></div>\n</body>", 1)
else:
    body_html = body_html + pixel_tag
```

**Plain-text bodies receive no pixel**: `body_html is None` means the campaign has no CMP-002 HTML template and the send path sends a plain-text email. Pixels require an `<img>` rendered by an HTML-capable mail client; injecting a raw URL string into plain text would be meaningless. CMP-003 never modifies `body_text`.

### 4.4 `_ensure_open_tracking_code` helper (new, in `marketing_campaigns.py`)

When a campaign has no `tracking_code` attribute, CMP-003 creates a synthetic code so open events can still be attributed to the campaign:

```python
def _ensure_open_tracking_code(campaign: dict, owner_id: str) -> Optional[str]:
    """Create (or return cached) a synthetic open-tracking code for a campaign.

    The slug is deterministic: sha256(campaign_id + "|open")[:16].
    Uses attribute_not_exists conditional put — safe to call concurrently
    (only the first caller creates; subsequent callers see ConditionalCheckFailed
    and query the existing row).
    Returns the slug, or None if creation fails (best-effort).
    """
    try:
        from app.services.tracking_codes import create_tracking_code
        campaign_id = campaign["campaign_id"]
        slug = hashlib.sha256(
            (campaign_id + "|open").encode()
        ).hexdigest()[:16]
        destination_url = f"{S.public_base_url}/ui/marketing/campaigns/{campaign_id}"
        create_tracking_code(
            owner_id,
            {
                "code_slug": slug,
                "campaign_id": campaign_id,
                "destination_url": destination_url,
            },
        )
        # Back-write slug onto campaign item so future sends skip this step
        T.marketing_campaigns.update_item(
            Key={"pk": f"OWNER#{owner_id}", "sk": f"MKTCAMP#{campaign_id}"},
            UpdateExpression="SET tracking_code = :s",
            ExpressionAttributeValues={":s": slug},
        )
        return slug
    except Exception:
        logger.debug("_ensure_open_tracking_code failed for %s", campaign.get("campaign_id"))
        return None
```

The back-write ensures the synthetic code is reused on subsequent sends of the same campaign without calling `create_tracking_code` again (which would get `ConditionalCheckFailedException` anyway — idempotent). The `create_tracking_code` conditional put (`attribute_not_exists(pk)`) handles concurrent calls safely.

## 5. Detailed Behavior & Edge Cases

### 5.1 Multiple opens from the same recipient

Mail clients sometimes pre-fetch images (image prefetching in iOS Mail, Gmail, Outlook). Each prefetch results in a separate `GET /ui/marketing/t/{code}/open.gif` request, which writes a separate VISIT row. There is no deduplication at the VISIT level — every request increments `visit_count`. This matches SuiteCRM's behavior (unique opens vs. total opens are computed at the analytics layer by counting distinct `party_id` values, but `party_id` is always `"anon"` for pixel requests since no session cookie is present). Operators viewing open rates should understand these are raw open counts, not unique-recipient counts.

An optional `open_unique_count` (distinct `ip_address` values) can be computed at attribution rollup time but is out of scope for CMP-003.

### 5.2 Bot and scanner traffic

Mail security scanners (e.g., Proofpoint, Google Safe Browsing, Barracuda) frequently pre-scan links and images in emails, inflating open counts. CMP-003 filters known scanner User-Agent strings via `_is_bot_ua(ua)`. The bot UA list is configurable via `S.marketing_open_tracking_bot_ignore_uas` (see Section 6). Requests matching a bot UA return the GIF but skip `record_visit`.

IP-based filtering (e.g., known Google scanner CIDR blocks) is deferred as a follow-up. The `ip_address` attribute stored on VISIT rows enables post-hoc filtering by analysts even if real-time filtering is not implemented.

### 5.3 Campaign with `campaign_type != "email"`

The pixel injection block in `_build_message_body` is gated on `body_html is not None`. Non-email campaigns (CMP-001 types: phone, mail, fax, sms) never have an HTML body, so the pixel is never injected. This gate requires no explicit `campaign_type` check.

### 5.4 Campaign with no HTML template

If `campaign_type == "email"` but no `email_template_id` is set (no CMP-002 template linked), `body_html` will be `None` and no pixel is injected. Open tracking only works for campaigns that use CMP-002 HTML templates. This is by design: plain-text emails cannot embed tracking images.

### 5.5 `record_visit` called for unknown code

[CORRECTED] If `code_slug` does not correspond to an existing META row in `T.tracking_codes`, `record_visit` as specified in MKT-010 (`docs/ofbiz/specs/MKT-010.md:344–345`) **silently returns without writing anything** — it performs a `get_tracking_code(code_slug)` lookup first and short-circuits on `None`. No VISIT row is written, no META row is created, no orphan row is produced. The original claim that "the VISIT `put_item` call succeeds unconditionally" and creates an orphan META row is wrong: it describes raw DDB behavior but not MKT-010's `record_visit` implementation, which explicitly guards against unknown codes.

For synthetic codes generated by `_ensure_open_tracking_code`, the META row is always written by `create_tracking_code` before any send occurs — this point is still correct.

For spoofed/mistyped `code_slug` values in requests to the pixel endpoint: `record_visit` silently returns, so no storage is consumed. This is better than the "orphan write" the previous version described.

### 5.6 Pixel URL in forwarded emails

When a recipient forwards an email, the `<img>` tag travels with it. Opens by the forwarded-to recipient also hit the original campaign's tracking code. This is standard SuiteCRM behavior and cannot be distinguished from genuine opens without recipient-specific pixel URLs. Recipient-specific pixel tokens are a CMP-003 follow-up; the current design uses a single per-campaign code.

### 5.7 Cache-control headers and CDN caching

The `Cache-Control: no-store, no-cache` and `Pragma: no-cache` headers ensure proxy servers, CDNs, and mail clients do not cache the GIF and serve it from cache on repeated opens (which would suppress the `GET` request and prevent the VISIT row from being written). Email client behavior varies: some iOS Mail versions ignore `Cache-Control` from `<img>` tags. This is an inherent limitation of pixel tracking and is not addressable at the server level without JavaScript.

### 5.8 Idempotency of `_ensure_open_tracking_code`

`create_tracking_code` uses `ConditionExpression="attribute_not_exists(pk)"` — exactly the pattern at `app/services/cart_reminders.py:198–211` (`_mark_token_consumed`). [VERIFIED: `app/services/cart_reminders.py:198` — `_mark_token_consumed` function starts at line 198; `ConditionExpression="attribute_not_exists(pk)"` confirmed at line 207.] If two workers call `_ensure_open_tracking_code` concurrently for the same campaign, one succeeds and the other gets `ConditionalCheckFailedException`, which is caught and silently ignored. Both workers proceed to the back-write (`update_item`), which is a last-writer-wins `SET` — idempotent. The same slug is written both times, so no conflict.

### 5.9 `visit_count` counter and open vs click separation

The `visit_count` counter on the META row accumulates both opens and clicks. The MKT-005 attribution rollup must query VISIT rows to separate them. CMP-003 adds a `open_count` convenience attribute (denormalized counter, incremented separately):

```python
# Separate counter on META row for opens:
T.tracking_codes.update_item(
    Key={"pk": f"TRACK#{code_slug}", "sk": "META"},
    UpdateExpression=(
        "SET visit_count = if_not_exists(visit_count, :z) + :one, "
        "    open_count = if_not_exists(open_count, :z) + :one, "
        "    updated_at = :ts"
    ) if event_type == "open" else (
        "SET visit_count = if_not_exists(visit_count, :z) + :one, "
        "    updated_at = :ts"
    ),
    ExpressionAttributeValues={":one": 1, ":z": 0, ":ts": ts},
)
```

`open_count` is absent on pre-CMP-003 META rows; consumers use `item.get("open_count", 0)`. This avoids a full VISIT row scan just to compute `open_rate`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 — no `dev_mode` branch

CMP-003 introduces zero `if S.dev_mode` branches. The dev/prod split for email delivery is already inside `send_alert_email` at `app/services/alerts.py:462–468` (dev writes to `S.dev_email_log`; prod calls SES). [VERIFIED: `app/services/alerts.py:462` — `if S.dev_mode:` branch confirmed; dev log writes at line 467, function ends at 492.] The pixel endpoint and `record_visit` use `T.tracking_codes` (DynamoDB Local in dev, real DynamoDB in prod) without any environment check. `S.public_base_url` (`settings.py:349`) is `http://localhost:8000` in dev and the production HTTPS URL in prod — the pixel URL in HTML emails sent during dev testing hits localhost, which is correct and testable.

### Idempotency

The VISIT row SK `VISIT#{ts:010d}#{nonce}` uses an 8-hex-char nonce from `secrets.token_hex(4)`, giving 4 billion possible values per second. Collision probability per second per code is negligible. Each `GET /ui/marketing/t/{code}/open.gif` call produces a new nonce — the endpoint is intentionally non-idempotent (each pixel load = one open event). The `_ensure_open_tracking_code` back-write is idempotent (`SET` expression, last-writer-wins).

### Security considerations

1. **No session or authentication on pixel endpoint**: The pixel endpoint is public and unauthenticated by design (the mail client fetching the image has no user session). The only data recorded is IP address, User-Agent, timestamp, and code slug — all of which are available in any web server access log. No PII beyond IP is recorded.

2. **IP address storage**: IP addresses are PII under GDPR. They are stored on VISIT rows with the 90-day TTL on the `T.tracking_codes` table (to be defined by MKT-002; if not defined, no TTL is set by CMP-003 — a follow-up should confirm TTL policy for VISIT rows). Operators in EU regions should ensure `MARKETING_OPEN_TRACKING_ENABLED=0` until a compliant consent flow is in place.

3. **Pixel URL non-guessability**: The tracking code slug is a caller-supplied string (MKT-010) or a deterministic SHA-256 prefix (CMP-003 synthetic codes). The synthetic slug `sha256(campaign_id + "|open")[:16]` is 16 hex chars = 64 bits of entropy. Brute-forcing the slug to inflate a competitor's open count is infeasible. The `campaign_id` is itself a 24-char SHA-256 prefix (MKT-004 scheme), so the combined entropy is high.

4. **`display:none` style**: The pixel tag includes `style="display:none"` as defense-in-depth against webmail clients that render the `<img>` as a visible broken image when the GIF fails to load. The `alt=""` attribute suppresses screen-reader announcements.

5. **`include_in_schema=False`**: The endpoint is excluded from the OpenAPI schema to avoid advertising it as a callable API endpoint. It exists solely as a mail-client image target.

6. **Response size**: The GIF is exactly 43 bytes. The endpoint never serves user-supplied content and cannot be used as an open redirect or SSRF vector.

## 8. Backward Compatibility & Migration

### Existing click-visit VISIT rows

Pre-CMP-003 VISIT rows have no `event_type` attribute. All consumers of VISIT rows must use `item.get("event_type", "click")` to treat absent-attribute rows as click visits. This default is specified in `record_visit`'s parameter default (`event_type: str = "click"`) and in `list_visits_for_code`'s filter logic.

### Existing `record_visit` callers

The MKT-011 public click-redirect endpoint calls `record_visit(code_slug, party_id=party_id, referrer=referrer)` (no `event_type` argument). Because `event_type` defaults to `"click"` and the attribute is omitted from the Item dict when `event_type == "click"`, existing call sites are completely unaffected — same DDB write shape as before, no migration needed.

### `visit_count` on META rows

The `visit_count` counter was already incremented for click visits. CMP-003 continues to increment it for open visits as well (both contribute to the total engagement count). The new `open_count` counter starts at 0 for all existing codes (absent attribute read as 0). There is no data migration; the counters diverge forward from the CMP-003 deployment date.

### `CampaignAttributionOut` new fields

`open_count: int = 0` and `open_rate: float = 0.0` are additive fields with zero defaults. Frontend consumers that deserialize `CampaignAttributionOut` will receive `0` for campaigns that were sent before CMP-003 was deployed or that used plain-text emails. No breaking change.

### No new router, no re-registration

The pixel endpoint is added to the existing MKT-011 `app/routers/marketing_campaigns.py` router. It uses the same router prefix and registration in `app/main.py`. No new `include_router` call is needed.

## 10. Open Questions / Assumptions

1. **TTL policy for VISIT rows**: MKT-002 may define a TTL on VISIT rows in the `TrackingCodes` table. CMP-003 does not set a `ttl_epoch` on VISIT rows because the MKT-010 spec does not reference one. A follow-up should define whether open events should expire (privacy-driven TTL) and, if so, what the retention window is. GDPR Article 5(1)(e) requires data minimization; storing IP addresses for opens beyond 90–180 days may require justification.

2. **Recipient-specific pixel tokens**: The current design uses a per-campaign code, making it impossible to identify which specific recipient opened an email. SuiteCRM supports per-contact open tracking. A future CMP-003 extension could append a recipient identifier to the pixel URL (e.g., `open.gif?r=<hmac_signed_party_id>`) to enable unique-open tracking. This is deferred because it adds PII-handling complexity and may require explicit consent disclosures.

3. **`_wrap_html` structure stability**: The pixel injection uses `str.replace` on the HTML string produced by `_wrap_html`. If `_wrap_html` is refactored (e.g., to use a templating engine), the replacement pattern may break silently. A more robust approach would have `_wrap_html` accept an optional `footer_html` parameter. This is flagged as a low-priority follow-up.

4. **Alignment of `open_count` denormalized counter vs. VISIT row query**: Both mechanisms compute opens. The denormalized counter is always at least as fast to read but may be inconsistent if a `record_visit` call writes the VISIT row but fails on the subsequent counter `update_item`. The probability of split is low (both calls target the same DDB table with a single-digit ms gap). For precision attribution, MKT-005 should prefer querying VISIT rows over the denormalized counter.

5. **`display:none` CSS compatibility**: Some email clients (notably Lotus Notes, older Outlook) ignore `display:none` or render empty alt text differently. This is an inherent limitation and not addressable server-side.

6. **`anyio.to_thread.run_sync` dependency**: The pixel endpoint uses `anyio` for thread dispatch. `anyio` is already a FastAPI / Starlette transitive dependency (confirmed by inspecting other async endpoints in `app/routers/messaging.py:13132` and `app/routers/broadcast.py:1915` which use `anyio.to_thread.run_sync`). [CORRECTED: the original claim cited `app/routers/browser_ssh_terminal.py` as the analogue, but `browser_ssh_terminal.py` does NOT use `anyio` — it uses `asyncio.wait_for` / `asyncio.TimeoutError`. The correct analogues are `messaging.py:13132` and `broadcast.py:1915`.] No new dependency is added.
