# CAS-007 — Ticket watchers / CC list

**Type:** Feature | **Priority:** P1 | **Estimate:** 1d  
**Parent area:** CRM Cases, Customer Support & Customer Portal  
**Depends on:** CAS-001 (feature flag + `T.tickets` table handle scaffolding)

---

## 1. Summary & Goal

Add a watcher (CC) list to support tickets so that users other than the ticket owner and assignee can subscribe to ticket activity. Each watcher receives the same in-app alert and email notification as the primary parties on every reply and status change. A watcher can be added or removed by the ticket owner or any admin. Watchers cannot self-add unless they are the owner (owner is always implicitly included).

The feature is entirely additive: with `S.crm_cases_enabled = False` (the default) the platform is byte-for-byte unchanged — no new routes are registered, no service methods run, no new DynamoDB attributes are written.

## 2. Context & Current State

### Existing ticket infrastructure

**`app/services/tickets.py`** contains `TicketStore`, a dataclass with `_table: Any = field(default=T.tickets)` (`tickets.py:244-245`). The `create_ticket` method (`tickets.py:411-512`) builds and writes the META item with `pk=TICKET#{ticket_id}`, `sk=META`. There is no `watchers` attribute on newly created tickets today; `header` dict at `tickets.py:440-475` has no `watchers` key.

`get_ticket` (`tickets.py:522-566`) assembles the ticket dict by reading the META item and querying `MSG#` and `ACT#` prefixes. It does not surface a `watchers` field in the returned dict.

`_conditional_update_meta` (`tickets.py:723-790`) is the write path for all META changes and uses optimistic locking via a `version` condition expression. It sets a fixed set of attributes and performs `REMOVE` for nullable space GSI keys. **Any mutation of `watchers` must bypass this method** and use a dedicated `update_item` with `ADD`/`DELETE` on a DynamoDB StringSet — avoiding a read-modify-write race condition.

`_apply_header_update_once` (`tickets.py:792-805`) calls `_conditional_update_meta` once and raises `TicketStateError({"code": "ticket_update_conflict"})` if the version condition fails — it is a **fail-fast** wrapper, not a retry-on-conflict loop. Watcher add/remove does not need version locking because DynamoDB StringSet `ADD`/`DELETE` is inherently atomic.

**`app/routers/tickets.py`** contains `_emit_ticket_alerts` (`tickets.py router:362-372`), which iterates `sorted({item for item in recipients if item})` and calls `audit_event` per recipient. The `add_ticket_message` handler (`router:949-988`) currently builds `recipients` as only the owner (if sender is admin) or the assigned admin (if sender is user) — watchers are not included.

`set_ticket_status` (`router:991-1010`) emits `ticket_status_changed` with `recipients=[ticket["owner_sub"]]` — again watchers are absent.

**`app/routers/ticket_boards.py`** already anticipates the `watchers` field. `_board_ticket_participants` (`ticket_boards.py:237-243`) iterates `ticket.get("watchers", [])` when building participant lists. `assign_board_ticket` (`ticket_boards.py:434`) passes `*updated.get("watchers", [])` into the `recipients` list. These references are already in production and return empty lists today because the attribute is never written.

**`TicketOut`** Pydantic model (`router:58-73`) does not have a `watchers` field. `TicketListItemOut` (`router:91-110`) likewise has no `watchers` field.

**Alert primitives:**
- `write_alert` (`app/services/alerts.py:356`): writes in-app alert to `T.alerts` and publishes SSE.
- `send_alert_email` (`app/services/alerts.py:459`): dev-mode log / prod SES send.

## 3. Data Model

### No new DynamoDB tables required

CAS-007 stores watcher state entirely on the existing `tickets` table (PK=`TICKET#{ticket_id}`, SK=`META`), using a DynamoDB **StringSet** attribute named `watchers`.

### META row additions

A new optional attribute is added to the ticket META item:

| Attribute | DDB Type | Description |
|-----------|----------|-------------|
| `watchers` | SS (StringSet) | Set of `user_sub` strings who watch this ticket. Absent when empty (DynamoDB does not permit empty sets). |

**Initialization:** `create_ticket` does **not** write `watchers` at creation time, because DynamoDB rejects empty sets. The attribute is omitted from the initial `put_item` call. `get_ticket` returns `list(header.get("watchers") or [])` — yielding `[]` when the attribute is absent.

**Atomic add:** `T.tickets.update_item(Key=..., UpdateExpression="ADD watchers :ws", ExpressionAttributeValues={":ws": {"SS": [watcher_sub]}})` — no condition expression needed; idempotent by definition (sets ignore duplicate elements).

**Atomic remove:** `T.tickets.update_item(Key=..., UpdateExpression="DELETE watchers :ws", ExpressionAttributeValues={":ws": {"SS": [watcher_sub]}})` — also idempotent; DynamoDB silently ignores removal of a member not present.

**No new GSIs.** Watchers are surfaced only through the existing per-ticket `get_ticket` path; there is no requirement to query "all tickets watched by user X" in this ticket. If that is needed later, a GSI on a fan-out row can be introduced as a follow-up (see Section 10).

**No `attr_types` entry needed** because `watchers` is a StringSet, not a numeric GSI sort key; the CLAUDE.md gotcha about `attr_types` applies only to numeric GSI keys.

## 4. API / Service Design

### 4.1 Service additions (`app/services/tickets.py`)

```python
def add_watcher(self, *, ticket_id: str, watcher_sub: str) -> dict[str, Any] | None:
    """
    Atomically add watcher_sub to the ticket's `watchers` StringSet.
    Returns the refreshed ticket dict, or None if the ticket does not exist.
    Raises TicketStateError with code="ticket_not_found" if missing.
    """

def remove_watcher(self, *, ticket_id: str, watcher_sub: str) -> dict[str, Any] | None:
    """
    Atomically remove watcher_sub from the `watchers` StringSet.
    Returns the refreshed ticket dict, or None if the ticket does not exist.
    Raises TicketStateError with code="ticket_owner_cannot_be_removed"
    if watcher_sub == ticket["owner_sub"].
    """
```

Both methods call `T.tickets.update_item` directly with `Key=_meta_item_key(ticket_id)` (the same helper used throughout `tickets.py`), bypassing `_conditional_update_meta` to avoid a needless version bump and read-modify-write.

**`get_ticket` update** (`tickets.py:522-566`): Add `watchers` to the assembled dict:

```python
"watchers": sorted(list(header.get("watchers") or [])),
```

Sorting ensures stable ordering for deterministic test assertions and API consumers.

**`create_ticket` update** (`tickets.py:411-512`): No change — the `watchers` attribute is intentionally absent at creation time.

### 4.2 Pydantic model additions (`app/routers/tickets.py`)

```python
class TicketOut(BaseModel):
    # ... existing fields ...
    watchers: list[str] = []          # NEW: additive, default empty

class TicketListItemOut(BaseModel):
    # ... existing fields ...
    watchers: list[str] = []          # NEW: additive, default empty

class AddWatcherReq(BaseModel):
    watcher_sub: str = Field(..., min_length=1, max_length=128)

```

`TicketOut.model_validate(ticket)` already handles extra dict keys gracefully (Pydantic ignores unknown keys by default). Adding `watchers: list[str] = []` is non-breaking for existing callers — they receive an extra empty list.

### 4.3 New endpoints (`app/routers/tickets.py`)

All new endpoints are gated at the router level with an early return:

```python
if not S.crm_cases_enabled:
    _raise(404, "feature_disabled", "crm_cases feature is not enabled")
```

**`POST /tickets/{ticket_id}/watchers`**

```
POST /tickets/{ticket_id}/watchers
Auth: require_ui_session + get_authenticated_user
Body: AddWatcherReq { watcher_sub: str }
Response 200: WatcherEnvelope (TicketOut with updated watchers list)
Errors: 404 (feature off or ticket not found), 403 (not owner/admin), 400 (watcher_sub empty), 409 (watcher already present — optional, currently a silent no-op)
```

Authorization: caller must be the ticket owner (`user.sub == ticket["owner_sub"]`) or an admin/root (`_is_admin_actor(request, user)`).

**`DELETE /tickets/{ticket_id}/watchers/{watcher_sub}`**

```
DELETE /tickets/{ticket_id}/watchers/{watcher_sub}
Auth: require_ui_session + get_authenticated_user
Response 200: WatcherEnvelope (TicketOut with updated watchers list)
Errors: 404 (feature off or ticket not found), 403 (not owner/admin), 400 (attempt to remove ticket owner)
```

Authorization: same as add. Owner cannot be removed as a watcher (the owner is always an implicit recipient; the `watchers` list is an explicit CC, not a replacement for the owner notification).

**`GET /tickets/{ticket_id}/watchers`**

```
GET /tickets/{ticket_id}/watchers
Auth: require_ui_session + get_authenticated_user
Response 200: { "watchers": list[str], "ticket_id": str }
Errors: 404 (feature off or ticket not found), 403 (no access)
```

This endpoint is a convenience read; the watchers list is also embedded in `GET /tickets/{ticket_id}` via `TicketOut.watchers`. It allows lightweight polling without fetching the full ticket.

### 4.4 Alert emission changes (`app/routers/tickets.py`)

**`add_ticket_message` handler** (`router:949-988`) — update the `recipients` list construction:

```python
# Before (line 977):
recipients = [ticket["owner_sub"]] if sender_role == "admin" else [ticket.get("assigned_admin_sub") or ""]

# After:
watchers = ticket.get("watchers") or []
if sender_role == "admin":
    recipients = [ticket["owner_sub"], *watchers]
else:
    recipients = [ticket.get("assigned_admin_sub") or "", *watchers]
```

The `_emit_ticket_alerts` helper already deduplicates via `sorted({item for item in recipients if item})`, so no extra dedup is needed.

**`set_ticket_status` handler** (`router:991-1010`) — update similarly:

```python
# Before (line 1008):
_emit_ticket_alerts("ticket_status_changed", recipients=[ticket["owner_sub"]], ...)

# After:
watchers = ticket.get("watchers") or []
_emit_ticket_alerts("ticket_status_changed", recipients=[ticket["owner_sub"], *watchers], ...)
```

Both changes are gated on `S.crm_cases_enabled`. With the flag off, the handler code remains the original single-recipient path — implemented via an inline conditional:

```python

recipients = [ticket["owner_sub"], *extra_recipients]
```

This pattern avoids any code-path divergence in tests when the flag is off.

## 5. Detailed Behavior & Edge Cases

### Watcher identity and deduplication
- The `watchers` StringSet is keyed by `user_sub` (the Cognito sub string). Platform user existence is not validated at the service layer — validation is the caller's responsibility (the endpoint verifies the requesting user exists via the session; the target `watcher_sub` is accepted as an opaque string and will simply not receive alerts if they have no user record or no registered alert email).
- Adding a user who is already a watcher is a no-op at the DynamoDB level (StringSet ADD is idempotent). The endpoint returns 200 with the current watchers list.
- The ticket owner (`owner_sub`) should never appear in the explicit `watchers` StringSet — the owner is already an implicit primary recipient. The `add_watcher` service method should check `if watcher_sub == ticket["owner_sub"]: return self.get_ticket(ticket_id)` (silent no-op, not an error) to avoid redundant notification.

### Alert delivery
- In-app alerts (`write_alert`) are fired for `ticket_replied` and `ticket_status_changed`. No new event types are introduced; the existing `render_ticket_email_template` at `alerts.py:235` handles both.
- Each watcher receives their own independent `write_alert` call (the existing fan-out in `_emit_ticket_alerts` already iterates per recipient). If `T.alerts.put_item` raises for one watcher, the exception is swallowed by `write_alert` (see `alerts.py:424-428`), so one bad sub does not block others.
- `send_alert_email` is not called in `_emit_ticket_alerts` today — that helper only calls `audit_event`. Email delivery for watchers follows the same pattern as the existing `email_alert_queued_for` field on message rows: the service stores the targets and the transport layer picks them up. For CAS-007, the `email_targets` list passed to `STORE.add_message` (`router:972`) should be extended to include watchers when the flag is on.

### Self-watch opt-in / opt-out
- Any authenticated user who can access the ticket (owner or admin) may add themselves as a watcher. Users cannot add themselves to tickets they cannot read — the access guard (`_can_access_ticket`) is checked before calling `add_watcher`.
- A non-owner admin who adds themselves as a watcher will receive notifications on future replies to that ticket.
- Watchers added before the flag is turned off remain persisted in DynamoDB but receive no alerts while the flag is off (the emission code paths are flag-gated).

### Watcher list in `TicketListItemOut`
- The listing endpoints (`list_tickets`) call `_assemble_headers` which calls `get_ticket` per header row. Because `get_ticket` now returns `watchers`, the list endpoint also surfaces the watcher list. This is acceptable: the watchers list is typically small (< 20 subs). If list performance becomes a concern, a follow-up may add a `include_watchers: bool = True` query param.

### Removal guard
- `remove_watcher` raises `TicketStateError({"code": "ticket_owner_cannot_be_removed"})` if `watcher_sub == ticket["owner_sub"]`. The DELETE endpoint maps this to HTTP 400.
- Removing a sub that is not in the set is a silent no-op (DynamoDB StringSet DELETE is idempotent).

### Ticket board participants
- `_board_ticket_participants` in `app/routers/ticket_boards.py:237-243` already iterates `ticket.get("watchers", [])`. Once CAS-007 is deployed and the flag is on, board ticket events (assign, reply, status change) will automatically fan-out to watchers with no further code change. This is the intended behavior noted in the ticket description and confirmed by `ticket_boards.py:434`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity
All watcher operations target the `tickets` DynamoDB table, which is shared by dev and prod. There are no `if S.dev_mode` branches in the service layer. In dev the table is DynamoDB Local (port 8001); in prod it is AWS DynamoDB — the same boto3 call path is exercised in both environments. `_FloatSafeTable` is used in both environments via `T.tickets`.

Alert dispatch (`write_alert`, `send_alert_email`) is already environment-aware at `alerts.py:459-468`: dev writes to a local log file (`S.dev_email_log`), prod sends via SES. No new divergence is introduced.

### Idempotency
- **Add:** StringSet `ADD` is inherently idempotent — adding the same `user_sub` twice produces the same single-element set. The endpoint returns 200 on both the first add and subsequent redundant adds.
- **Remove:** StringSet `DELETE` is inherently idempotent — removing an absent element is a no-op. The endpoint returns 200 in both cases.
- **No version increment:** Watcher mutations do not bump the META `version` field because they use a separate `update_item` expression targeting only `watchers`. This means two concurrent watcher-add requests do not conflict with each other or with an in-flight `_conditional_update_meta` call (which only conditions on `version`). The result is last-writer-wins on the set membership — the correct semantic for a CC list.

### Security
- **Authorization:** Both add and remove require the caller to be the ticket owner or an admin/root. A non-owner regular user cannot add or remove watchers on another user's ticket.
- **Watcher sub validation:** The `watcher_sub` in `AddWatcherReq` is validated as `min_length=1, max_length=128` (matching other sub fields in the codebase). No user existence check is enforced at the API layer — the frontend is responsible for resolving valid user subs (e.g., via an admin user-lookup endpoint). This is consistent with how `assignee_admin_sub` is handled in `assign_ticket` (`router:927-928`), where a role check is done but no separate user existence check is performed beyond querying `T.users`.
- **No PII leakage:** `TicketOut.watchers` returns a list of `user_sub` strings, not email addresses or display names. Resolving display names is a frontend concern using the existing `/users/{sub}` profile endpoints.
- **CSRF:** All mutating endpoints use `require_ui_session` which enforces CSRF token validation on non-GET requests (`app/services/sessions.py:330` and CLAUDE.md auth section).

## 8. Backward Compatibility & Migration

### Zero-downtime, no migration required
- The `watchers` StringSet attribute is never written on existing ticket rows. `get_ticket` uses `header.get("watchers") or []`, which returns `[]` for any row that lacks the attribute. This is safe with or without a deploy.
- `TicketOut.watchers: list[str] = []` is additive — existing API clients that do not expect the field will ignore it. No existing API response is modified in a breaking way.
- The `_conditional_update_meta` / `_apply_header_update_once` methods are not changed; their `SET` expressions do not reference `watchers`, so they do not clear or overwrite the StringSet.

### `ticket_boards.py` already compatible
- `_board_ticket_participants` at `ticket_boards.py:241` uses `ticket.get("watchers", [])`. Once CAS-007 ships and watchers are persisted, board events will start notifying them. This is an intentional behavior change that is opt-in via `CRM_CASES_ENABLED=1`.

### Rollback
- If CAS-007 is rolled back (flag turned off), watcher data already written to DynamoDB is inert — the attribute is read by `get_ticket` and surfaced in responses, but the emission code is flag-gated so no notifications fire. The data can be left in place without impact.
- If the `TicketOut.watchers` field needs to be hidden on rollback, a temporary `exclude_unset=True` serialization or a response model without the field can be used. This is unlikely to be necessary.

## 10. Open Questions / Assumptions

1. **Watcher cap:** Should there be a max number of watchers per ticket (e.g., 50)? Not specified in the ticket. Assumption: no cap for MVP; a guard can be added in `add_watcher` with a DynamoDB condition expression (`size(watchers) < 50`) if abuse is observed.

2. **Watcher notifications on ticket creation:** The source ticket does not mention notifying watchers when a ticket is created (they would not exist yet). This spec matches that: no change to the `ticket_created` emission path.

3. **Watcher self-service (non-owner add):** The ticket says "Auth: owner or admin." Non-owner regular users cannot add themselves as watchers on other users' tickets. If a use case arises for public "follow this ticket" functionality, a separate `POST /tickets/{id}/watch` endpoint (no body, always adds `user.sub`) can be added in a follow-up.

4. **Fan-out index (GSI for "tickets watched by user"):** Not required by CAS-007. If a "my watched tickets" view is needed, a fan-out approach (one row per watcher per ticket in the `tickets` table under `pk=WATCHER#{user_sub}`, `sk=TICKET#{ticket_id}`) can be added as a follow-up with a new GSI, without changing the StringSet design.

5. **External watcher emails (non-platform users):** The ticket scopes watchers to platform `user_sub` values. SuiteCRM's CC list supports arbitrary email addresses. If external email CC is needed, a separate `cc_emails: list[str]` attribute can be added alongside `watchers` in a CAS-007-ext ticket.

6. **`email_alert_queued_for` on message rows:** The spec extends the `email_targets` list passed to `add_message` to include watchers. This persists watcher subs in the message row's `email_alert_queued_for` field. The existing email delivery background worker (if any) will pick these up. If no worker currently processes this field for ticket emails, the write is a no-op for email delivery but adds audit value.
