## 1. Summary & Goal

OPP-002 implements the full create/read/update/delete service layer and REST router for the Opportunity entity introduced as infrastructure in OPP-001. When this ticket ships, authenticated users can manage their own sales pipeline opportunities via five REST endpoints. All mutations emit structured audit events. The entire feature is additive and gated behind `S.sales_pipeline_enabled`; the rest of the platform is byte-for-byte unchanged with the flag off.

The goal is a production-quality service that later tickets (OPP-003 stage pipeline UI, OPP-004 contact-role junction, OPP-005 quota/forecast, OPP-006 funnel report) can build directly on top of without modification to this layer.

## 3. Data Model

### DynamoDB single-table layout on `T.sales_opportunities`

All rows for a user live under `pk = USER#{owner_sub}`.

| pk | sk | Row type | Description |
|---|---|---|---|
| `USER#{owner_sub}` | `OPP#{opp_id}` | META | Opportunity record (all fields) |

There are no additional row types in this ticket. OPP-004 will add `OPP#{opp_id}#CONTACT#{contact_ref}` rows to the same table; OPP-005 will add `FORECAST#{period_key}` rows.

### Attributes on the META row

| Attribute | Type | Notes |
|---|---|---|
| `pk` | S | `USER#{owner_sub}` |
| `sk` | S | `OPP#{opp_id}` |
| `opp_id` | S | Denormalized; used by `GSI_DIRECT` |
| `owner_sub` | S | Denormalized; GSI_BY_USER_CLOSE partition key |
| `name` | S | |
| `stage` | S | Member of `OPPORTUNITY_STAGES`; GSI_BY_STAGE partition key |
| `amount_cents` | N | Integer; `ge=0` |
| `weighted_amount_cents` | N | `amount_cents * probability // 100`; recomputed on every write |
| `close_date` | N | Unix timestamp integer; GSI sort key — must be numeric |
| `probability` | N | 0–100 |
| `lead_source` | S | Nullable; member of `LEAD_SOURCE_CHOICES` or absent |
| `description` | S | Nullable; max 4096 chars |
| `account_party_id` | S | Nullable; forward reference to PTY-008 Party Group |
| `contact_party_id` | S | Nullable; forward reference to PTY-004 Person |
| `created_at` | N | Unix timestamp integer |
| `updated_at` | N | Unix timestamp integer; used as optimistic-lock version |
| `deleted_at` | N | Unix timestamp integer; absent means not deleted (soft-delete) |

### GSIs (defined in OPP-001, consumed here)

| GSI name | Partition key | Sort key | Purpose |
|---|---|---|---|
| `GSI_BY_USER_CLOSE` | `owner_sub` (S) | `close_date` (N) | List all opps for a user, sorted by close date — primary query path |
| `GSI_BY_STAGE` | `stage` (S) | `close_date` (N) | Cross-user stage queries (OPP-006 admin report) |
| `GSI_DIRECT` | `opp_id` (S) | — | Direct lookup by ID without knowing owner (admin use; not required in OPP-002) |

`attr_types={"close_date": "N", "created_at": "N"}` is set in the OPP-001 `TableDef`. Both GSI sort keys are numeric; the `attr_types` declaration is the only way to tell DynamoDB Local to treat them as `N` rather than `S`.

### Why single-table

The `sales_opportunities` table is the single table for all CRM sales objects. Junction rows (contact roles, forecast worksheets) share the same `pk/sk` namespace with distinct `sk` prefixes. This mirrors the pattern used in `tickets` (`app/services/tickets.py`) and `billing` (`app/services/billing_shared.py`).

## 4. API / Service Design

### 4.1 Service layer — `app/services/opportunities.py`

New file. All functions are synchronous (same as `app/services/tickets.py`). All DDB operations go through `T.sales_opportunities` (a `_FloatSafeTable` proxy).

```python
from __future__ import annotations

from typing import List, Optional, Tuple
from uuid import uuid4

from boto3.dynamodb.conditions import Attr, Key
from fastapi import HTTPException

from app.core.cursor import decode_cursor, encode_cursor
from app.core.settings import S
from app.core.tables import T
from app.core.time import now_ts
from app.models import (
    LEAD_SOURCE_CHOICES,
    OPPORTUNITY_STAGES,
    OpportunityCreateIn,
    OpportunityOut,
    OpportunityUpdateIn,
)
from app.services.alerts import audit_event


def _require_flag() -> None:
    """Raise 503 when the sales pipeline feature is disabled."""
    if not S.sales_pipeline_enabled:
        raise HTTPException(503, detail={"code": "sales_pipeline_disabled"})


def _item_to_out(item: dict) -> OpportunityOut:
    """Convert a raw DDB item to OpportunityOut, skipping soft-deleted rows."""
    if item.get("deleted_at"):
        raise HTTPException(404, detail={"code": "opportunity_not_found"})
    return OpportunityOut(
        opp_id=item["opp_id"],
        owner_sub=item["owner_sub"],
        name=item["name"],
        stage=item["stage"],
        amount_cents=int(item["amount_cents"]),
        weighted_amount_cents=int(item["weighted_amount_cents"]),
        close_date=int(item["close_date"]),
        probability=int(item["probability"]),
        lead_source=item.get("lead_source"),
        description=item.get("description"),
        account_party_id=item.get("account_party_id"),
        contact_party_id=item.get("contact_party_id"),
        created_at=int(item["created_at"]),
        updated_at=int(item["updated_at"]),
    )


def create_opportunity(
    owner_sub: str,
    data: OpportunityCreateIn,
    request=None,
) -> OpportunityOut:
    _require_flag()
    # Validation is enforced by OpportunityCreateIn validators (OPP-001),
    # but double-check stage here for defence-in-depth.
    if data.stage not in OPPORTUNITY_STAGES:
        raise HTTPException(400, detail={"code": "invalid_stage", "stage": data.stage})
    if data.lead_source is not None and data.lead_source not in LEAD_SOURCE_CHOICES:
        raise HTTPException(400, detail={"code": "invalid_lead_source"})

    opp_id = "opp_" + uuid4().hex
    ts = now_ts()
    weighted = data.amount_cents * data.probability // 100
    item = {
        "pk": f"USER#{owner_sub}",
        "sk": f"OPP#{opp_id}",
        "opp_id": opp_id,
        "owner_sub": owner_sub,
        "name": data.name,
        "stage": data.stage,
        "amount_cents": data.amount_cents,
        "weighted_amount_cents": weighted,
        "close_date": data.close_date,
        "probability": data.probability,
        "lead_source": data.lead_source,
        "description": data.description,
        "account_party_id": data.account_party_id,
        "contact_party_id": data.contact_party_id,
        "created_at": ts,
        "updated_at": ts,
    }
    # Strip None values — DynamoDB cannot store NULL as a GSI key attribute.
    item = {k: v for k, v in item.items() if v is not None}
    T.sales_opportunities.put_item(Item=item)
    audit_event("opportunity.created", owner_sub, request, opp_id=opp_id, stage=data.stage)
    return _item_to_out(item)


def get_opportunity(owner_sub: str, opp_id: str) -> OpportunityOut:
    _require_flag()
    resp = T.sales_opportunities.get_item(
        Key={"pk": f"USER#{owner_sub}", "sk": f"OPP#{opp_id}"}
    )
    item = resp.get("Item")
    if not item:
        raise HTTPException(404, detail={"code": "opportunity_not_found"})
    return _item_to_out(item)


def update_opportunity(
    owner_sub: str,
    opp_id: str,
    data: OpportunityUpdateIn,
    request=None,
) -> OpportunityOut:
    _require_flag()
    current = get_opportunity(owner_sub, opp_id)

    if data.stage is not None and data.stage not in OPPORTUNITY_STAGES:
        raise HTTPException(400, detail={"code": "invalid_stage"})
    if data.lead_source is not None and data.lead_source not in LEAD_SOURCE_CHOICES:
        raise HTTPException(400, detail={"code": "invalid_lead_source"})

    ts = now_ts()
    new_amount = data.amount_cents if data.amount_cents is not None else current.amount_cents
    new_prob = data.probability if data.probability is not None else current.probability
    new_weighted = new_amount * new_prob // 100

    # Build UpdateExpression dynamically from non-None fields.
    set_parts = ["#updated_at = :updated_at", "weighted_amount_cents = :weighted"]
    expr_names = {"#updated_at": "updated_at"}
    expr_values = {
        ":updated_at": ts,
        ":weighted": new_weighted,
        ":current_updated_at": current.updated_at,
    }
    field_map = {
        "name": data.name,
        "stage": data.stage,
        "amount_cents": data.amount_cents,
        "close_date": data.close_date,
        "probability": data.probability,
        "lead_source": data.lead_source,
        "description": data.description,
        "account_party_id": data.account_party_id,
        "contact_party_id": data.contact_party_id,
    }
    for attr, val in field_map.items():
        if val is not None:
            safe_name = f"#{attr}"
            set_parts.append(f"{safe_name} = :{attr}")
            expr_names[safe_name] = attr
            expr_values[f":{attr}"] = val

    T.sales_opportunities.update_item(
        Key={"pk": f"USER#{owner_sub}", "sk": f"OPP#{opp_id}"},
        UpdateExpression="SET " + ", ".join(set_parts),
        ConditionExpression=Attr("updated_at").eq(current.updated_at),
        ExpressionAttributeNames=expr_names,
        ExpressionAttributeValues=expr_values,
    )
    audit_event("opportunity.updated", owner_sub, request, opp_id=opp_id)
    return get_opportunity(owner_sub, opp_id)


def delete_opportunity(owner_sub: str, opp_id: str, request=None) -> None:
    _require_flag()
    get_opportunity(owner_sub, opp_id)  # 404 if missing or wrong owner
    ts = now_ts()
    T.sales_opportunities.update_item(
        Key={"pk": f"USER#{owner_sub}", "sk": f"OPP#{opp_id}"},
        UpdateExpression="SET deleted_at = :ts",
        ExpressionAttributeValues={":ts": ts},
    )
    audit_event("opportunity.deleted", owner_sub, request, opp_id=opp_id)


def list_opportunities(
    owner_sub: str,
    stage: Optional[str] = None,
    cursor: Optional[str] = None,
    limit: int = 50,
) -> Tuple[List[OpportunityOut], Optional[str]]:
    _require_flag()
    limit = max(1, min(limit, 200))
    exclusive_start = decode_cursor(cursor)

    items: List[dict] = []
    last_key = exclusive_start
    # Loop via LastEvaluatedKey: FilterExpression (stage + not-deleted) does not
    # reduce the DDB page size, so a single query() call can return 0 matching
    # items even when matching rows exist beyond the first page.
    while True:
        kwargs: dict = {
            "IndexName": "GSI_BY_USER_CLOSE",
            "KeyConditionExpression": Key("owner_sub").eq(owner_sub),
            "FilterExpression": Attr("deleted_at").not_exists(),
            "Limit": limit * 4,  # over-fetch to counteract filter sparsity
        }
        if stage:
            kwargs["FilterExpression"] = (
                Attr("deleted_at").not_exists() & Attr("stage").eq(stage)
            )
        if last_key:
            kwargs["ExclusiveStartKey"] = last_key

        resp = T.sales_opportunities.query(**kwargs)
        items.extend(resp.get("Items", []))
        last_key = resp.get("LastEvaluatedKey")

        if len(items) >= limit or not last_key:
            break

    result_items = items[:limit]
    # If we gathered exactly `limit` items and there are more in DDB, encode a
    # cursor pointing to the last item returned so the next page starts there.
    next_cursor: Optional[str] = None
    if len(items) > limit or last_key:
        # Build a synthetic LastEvaluatedKey from the last returned item.
        last_item = result_items[-1] if result_items else None
        if last_item:
            lek = {
                "pk": last_item["pk"],
                "sk": last_item["sk"],
                "owner_sub": last_item["owner_sub"],
                "close_date": last_item["close_date"],
            }
            next_cursor = encode_cursor(lek)

    return [_item_to_out(i) for i in result_items], next_cursor
```

## 5. Detailed Behavior & Edge Cases

### 5.1 `create_opportunity`

- Generates `opp_id = "opp_" + uuid4().hex` (32-hex suffix; same pattern as `"opp_" + uuid4().hex` used by tickets for `ticket_id`).
- `weighted_amount_cents = amount_cents * probability // 100` (integer division; no floats stored in DDB).
- `close_date` is accepted as a Unix timestamp integer. The caller is responsible for passing a valid future or past date; the service does not enforce minimum date. OPP-003 may add a `close_date >= now` validator on the frontend.
- `None`-valued optional fields are stripped before `put_item` to avoid DynamoDB `NULL` values on GSI key attributes. This mirrors the approach in `app/services/tickets.py` which filters None values from the `gsi*pk` attrs.
- On success emits `audit_event("opportunity.created", owner_sub, request, opp_id=opp_id, stage=data.stage)`.

### 5.2 `get_opportunity`

- Issues a `get_item` on `pk=USER#{owner_sub}`, `sk=OPP#{opp_id}`. Because `owner_sub` is part of the primary key, a user fetching another user's opportunity will always get a `None` item → 404. Ownership is enforced at the data-access level, not via a secondary check.
- Soft-deleted items (those with `deleted_at` set) are treated as 404 by `_item_to_out`.

### 5.3 `update_opportunity`

- Reads the current item first via `get_opportunity` to obtain `current.updated_at` for the optimistic-lock `ConditionExpression=Attr("updated_at").eq(current.updated_at)`. If a concurrent update races ahead, the `ConditionalCheckFailedException` from DDB propagates as an unhandled 500. Callers should retry on 500 after a short back-off. A future iteration can catch `ClientError` with code `ConditionalCheckFailedException` and return 409.
- `weighted_amount_cents` is always recomputed using the merged (new or existing) `amount_cents` and `probability`, even if neither changes explicitly. This ensures the stored value is always consistent.
- Audit event `"opportunity.updated"` is emitted after the successful `update_item`.
- Fields not included in `OpportunityUpdateIn` (e.g., `created_at`, `opp_id`, `owner_sub`) are never modified by this function.

### 5.4 `delete_opportunity`

- Soft-delete only: writes `deleted_at = now_ts()` via `update_item`. The row remains in DDB for historical queries and as a tombstone for OPP-005 `closed_cents` computation (which must ignore deleted opportunities).
- A hard-delete function is not provided in this ticket. If needed in the future it should be a separate admin endpoint.
- Emits `audit_event("opportunity.deleted", ...)` after the soft-delete write.

### 5.5 `list_opportunities` — pagination and filter

- Uses `GSI_BY_USER_CLOSE` with `KeyConditionExpression=Key("owner_sub").eq(owner_sub)` and a `FilterExpression` for `deleted_at.not_exists()` plus an optional stage equality filter.
- Because `FilterExpression` is evaluated post-fetch (CLAUDE.md gotcha), the function loops via `LastEvaluatedKey` until it has accumulated `limit` non-deleted matching items or the index is exhausted.
- The over-fetch multiplier of `4` in the `Limit` kwarg reduces the number of loop iterations in practice but is not a strict bound; the loop continues until the condition is met.
- The cursor encodes the composite GSI+primary key needed for `ExclusiveStartKey` on `GSI_BY_USER_CLOSE` (requires `pk`, `sk`, `owner_sub`, `close_date`). `encode_cursor` handles `Decimal` serialization via its `_json_default` helper (`cursor.py:13–18`), which is essential because DDB returns numeric attrs as `Decimal`.
- `limit` is clamped to `[1, 200]`; values outside this range are silently coerced.
- Results are ordered by `close_date` ascending (DynamoDB GSI default scan direction with `ScanIndexForward=True`, which is the boto3 default). OPP-003 may expose a `sort_dir` parameter.

### 5.6 Flag-off behavior

`_require_flag()` is the first call in every exported service function. When `S.sales_pipeline_enabled` is `False`, every endpoint returns:
```json
{ "detail": { "code": "sales_pipeline_disabled" } }
```
with HTTP 503. No DDB operations are executed.

### 5.7 Input validation errors

Invalid `stage` or `lead_source` values return HTTP 400 with a structured detail body (`{"code": "invalid_stage", "stage": <value>}`). This is defence-in-depth; the Pydantic `@validator` in OPP-001 models will have already caught these at the request-parsing layer with 422, but service-level checks guard against programmatic service calls that bypass the router.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

There are no `if S.dev_mode` branches anywhere in `app/services/opportunities.py` or `app/routers/opportunities.py`. The same DDB access path runs in dev (DynamoDB Local at port 8001) and in prod (real AWS DynamoDB). This follows the SECOPS-007 mandate documented in `CRM_OPPORTUNITIES_TICKETS.md` line 13 and enforced across the codebase (e.g., `app/services/audit_export_worker.py`, `app/services/ssh_session_recording.py`).

### Idempotency

- `create_opportunity` is not idempotent by design (each call generates a new `opp_id`). Callers should not retry on success. Network-level retries that reach the service after a successful write will create duplicate records; this is standard REST behavior for `POST`.
- `update_opportunity` uses optimistic concurrency (`ConditionExpression` on `updated_at`). A retry after a successful update will fail the condition check, returning 500 (see Section 5.3 for retry guidance). A future improvement is to return 409 on `ConditionalCheckFailedException`.
- `delete_opportunity` (soft-delete) is idempotent: a second call on an already-deleted item will succeed (writes `deleted_at` again with the new timestamp). `get_opportunity` returns 404 for deleted items, so the second `delete_opportunity` call will itself return 404 before touching DDB.

### Security

- **Ownership enforcement at the data-access layer.** `get_opportunity` uses a composite primary-key lookup (`pk=USER#{owner_sub}`, `sk=OPP#{opp_id}`). A user who supplies another user's `opp_id` but their own `owner_sub` will find no item → 404. There is no separate ownership check; the DDB access pattern enforces it.
- **No cross-user listing.** `list_opportunities` queries `GSI_BY_USER_CLOSE` with a strict `owner_sub` equality condition. A user can never see another user's opportunities through this endpoint.
- **No admin cross-user list in this ticket.** An admin-level cross-user view is deferred to OPP-006 (`GET /ui/admin/sales/reports/pipeline`), which will use `Depends(require_admin_or_root)` from `app/auth/policy.py:67`.
- **CSRF.** All mutating endpoints (`POST`, `PATCH`, `DELETE`) use `require_ui_session` which enforces CSRF validation for cookie-authenticated sessions (the check is inside `require_ui_session` at `app/services/sessions.py:330`). Bearer-auth clients skip CSRF per the standard platform policy.
- **Input size limits.** `name` is capped at 255 chars; `description` at 4096 chars (from OPP-001 Pydantic models). `lead_source` and `stage` are validated against closed enums; unknown values return 400/422.
- **Audit trail.** Every mutation emits `audit_event` with the `opp_id` recorded. This provides a per-opportunity event log in `T.alerts` without any separate audit table.

## 10. Open Questions / Assumptions

1. **Optimistic concurrency on lost-update race (409 vs 500).** The spec uses `ConditionExpression` to prevent lost updates but lets `ConditionalCheckFailedException` surface as an unhandled 500. The ticket text does not specify a 409 response. This is left as a follow-up improvement; the current implementation is correct and safe but the error UX is poor under high concurrency.

2. **`close_date` validation.** The service accepts any integer for `close_date` (past or future). Should `create_opportunity` reject a `close_date` in the past? Deferred to OPP-003 (which introduces a configurable pipeline UI where the semantics of close date are more visible). For now, no minimum date validation.

3. **`deleted_at` in `OpportunityOut`.** The current `OpportunityOut` model (from OPP-001) does not expose `deleted_at`. This is intentional — deleted opportunities return 404. If soft-deleted records ever need to be surfaced (e.g., for admin audit), an admin-only `include_deleted=true` query param and a corresponding `deleted_at` field in the output model can be added without breaking the existing API.

4. **`contact_party_id` / `account_party_id` resolution.** These fields are stored as opaque strings. Resolution to a Party record requires PTY-004/PTY-008, which are unbuilt. Until those tickets ship, the fields are free-text identifiers with no FK enforcement. The service does not validate that the referenced party IDs exist.

5. **`record_activity` integration.** `app/services/activity_feed.py:45` exposes `record_activity(user_id, actor_id, activity_type, ...)`. Opportunity creation could emit an activity feed event so managers see "Alice created a new opportunity: Deal X". This is not in scope for OPP-002 (no corresponding ticket exists yet) but the `record_activity` call point is natural inside `create_opportunity`.

6. **Assumption: OPP-001 filters `None` values from `put_item` items.** The spec above filters `None` values before `put_item` to prevent DynamoDB `NULL` attribute storage on GSI key columns. If OPP-001's models initialize optional fields to `None` (likely), the service must strip them at write time; this is verified by analogy with `app/services/tickets.py` which does the same for GSI partition key attributes.
