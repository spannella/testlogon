# STU-012 — Studio — dropdown editor for picklist fields

**Type:** Feature | **Priority:** P2 | **Estimate:** 2d  
**Flag:** `CRM_STUDIO_ENABLED` (default `"0"` → `False`)  
**Depends on:** STU-001 (DDB scaffolding), STU-011 (custom fields + `validate_custom_fields`)

---

## 1. Summary & Goal

STU-012 builds a named-dropdown (picklist option list) management service that backs the `picklist` and `multi_picklist` field types introduced by STU-011. Admins define reusable named lists of `{value, label, sort_order, is_active}` tuples. Custom field definitions reference a list by `picklist_name`; the validation layer resolves the active values at runtime.

The deliverable is:

1. A service layer (`app/services/crm_studio_dropdowns.py`) with full CRUD plus an `get_active_values` query used by the validation integration.
2. Five REST endpoints appended to the STU-011 router (`app/routers/crm_studio.py`) under the `/ui/admin/studio/dropdowns` prefix.
3. A React page (`frontend/src/pages/admin/studio/DropdownEditor.tsx`) reachable at `/admin/studio/dropdowns` that lets admins manage dropdown lists including inline reordering.
4. An integration hook in `app/services/crm_studio_fields.py:validate_custom_fields` (STU-011) that rejects picklist values not in the active set.

All code is additive and gated behind `S.crm_studio_enabled`. With the flag off, every endpoint returns 404 and `validate_custom_fields` cannot be called through any live code path because the router is not registered.

## 3. Data Model

### 3.1 DynamoDB table: `crm_studio_dropdowns`

Introduced by STU-001. No schema changes needed in this ticket; STU-012 only writes and reads from it.

| Attribute | Type | Notes |
|---|---|---|
| `pk` | S | `DROPDOWN#{list_name}` — e.g. `DROPDOWN#regions` |
| `sk` | S | `META` (only one row per dropdown) |
| `list_name` | S | Slug, validated `^[a-z][a-z0-9_]{1,63}$` |
| `label` | S | Human-readable display name |
| `options` | L | Ordered list of option maps (see below) |
| `created_by_sub` | S | `user_sub` of creator |
| `updated_by_sub` | S | `user_sub` of last editor |
| `created_at` | N | Unix seconds (`now_ts()`) |
| `updated_at` | N | Unix seconds (`now_ts()`) |
| `is_active` | BOOL | `True` — soft-delete sets to `False`, keeps row for audit |

Each element of `options` is a DynamoDB map:

| Sub-attribute | Type | Constraints |
|---|---|---|
| `value` | S | Unique within the list; `^[A-Za-z0-9_\-]{1,100}$` |
| `label` | S | Max 200 chars |
| `sort_order` | N | Integer 0-based; determines render order |
| `is_active` | BOOL | Inactive options are excluded from validation |

No GSI is required — list scans and point reads are both by the `pk + sk` primary key. The total number of dropdown lists per deployment is expected to be small (under 500), so a full table scan for `list_dropdowns` is acceptable.

## 4. API / Service Design

### 4.1 Service: `app/services/crm_studio_dropdowns.py`

All functions are synchronous (no async/await); called from async FastAPI handlers via direct invocation (same pattern as `app/services/billing_config.py`).

```python
# Module-level cache (mirrors billing_config.py:46-58)
_dropdown_cache: dict[str, dict] = {}   # list_name -> item
_cache_ts: int = 0
_CACHE_TTL_SECONDS: int = 60

def invalidate_cache() -> None: ...

def _guard_enabled() -> None:
    """Raise HTTPException(404) when crm_studio_enabled is False."""
    if not S.crm_studio_enabled:
        raise HTTPException(404, "Studio not enabled")
```

#### `create_dropdown`

```python
def create_dropdown(
    actor_sub: str,
    list_name: str,
    label: str,
    options: list[dict],
) -> dict:
```

- Validates `list_name` against `^[a-z][a-z0-9_]{1,63}$`; raises `HTTPException(422, "invalid list_name")` on failure.
- Validates each option: `value` matches `^[A-Za-z0-9_\-]{1,100}$`; `label` is non-empty string; `sort_order` is non-negative int; `is_active` is bool. Raises `HTTPException(422)` listing per-option errors.
- Checks uniqueness: if a row with `pk=DROPDOWN#{list_name}`, `sk=META` already exists (including soft-deleted ones where `is_active=False`), raises `HTTPException(409, "dropdown already exists")`.
- Writes the item via `T.crm_studio_dropdowns.put_item(Item={...}, ConditionExpression=Attr("pk").not_exists())`.
- Calls `audit_event("studio.dropdown.created", actor_sub, list_name=list_name, option_count=len(options))`.
- Invalidates cache; returns the written item dict.

#### `update_dropdown`

```python
def update_dropdown(
    actor_sub: str,
    list_name: str,
    *,
    label: str | None = None,
    options: list[dict] | None = None,
) -> dict:
```

- Raises `HTTPException(404)` if the row is absent or `is_active=False`.
- `options`, when supplied, replaces the entire options list (client owns ordering). Validates same rules as create. Deduplication: if two options share the same `value`, raises `HTTPException(422, "duplicate option value")`.
- Updates `updated_by_sub`, `updated_at = now_ts()`.
- Uses `T.crm_studio_dropdowns.update_item` with an `UpdateExpression` that sets only provided fields (label, options, updated_by_sub, updated_at).
- Emits `audit_event("studio.dropdown.updated", actor_sub, list_name=list_name, changed_fields=[...])`.
- Invalidates cache; returns updated item.

#### `delete_dropdown`

```python
def delete_dropdown(actor_sub: str, list_name: str) -> None:
```

- Raises `HTTPException(404)` if absent or already soft-deleted.
- Checks `crm_studio_fields` for active fields with `picklist_name = list_name`. If any found, raises `HTTPException(409, "dropdown in use by active fields", detail={"field_count": N})`.
- Soft-deletes: sets `is_active=False`, `updated_by_sub`, `updated_at`.
- Emits `audit_event("studio.dropdown.deleted", actor_sub, list_name=list_name)`.
- Invalidates cache.

#### `get_dropdown`

```python
def get_dropdown(list_name: str) -> dict | None:
```

- Point-reads `pk=DROPDOWN#{list_name}`, `sk=META`.
- Returns the item dict or `None` if absent. Does not filter by `is_active` (callers check themselves).

#### `list_dropdowns`

```python
def list_dropdowns(include_inactive: bool = False) -> list[dict]:
```

- Scans `crm_studio_dropdowns` table. With `include_inactive=False` (default), applies `FilterExpression=Attr("is_active").eq(True)`.
- Returns items sorted by `list_name` ascending.
- No cursor pagination needed (record count is administratively bounded).

#### `get_active_values`

```python
def get_active_values(list_name: str) -> list[str]:
```

- Used by STU-011 `validate_custom_fields`; called on the hot validation path so it uses the module-level cache.
- Cache key: `list_name`. Cache invalidated by any write to this dropdown.
- If the list does not exist or is soft-deleted, returns `[]` (validation is then effectively open; callers may choose to treat empty as "list not found" and emit a warning).
- Returns `[opt["value"] for opt in item["options"] if opt.get("is_active", True)]` in `sort_order` ascending order.

#### `reorder_options`

```python
def reorder_options(
    actor_sub: str,
    list_name: str,
    ordered_values: list[str],
) -> dict:
```

- Receives a complete list of `value` strings in the desired display order.
- Validates that `set(ordered_values) == set(existing active values)`. Raises `HTTPException(422)` if any values are missing or unknown.
- Reassigns `sort_order` as `enumerate(ordered_values)`.
- Writes via `update_item`; emits audit `studio.dropdown.reordered`.
- Invalidates cache; returns updated item.

This is a separate endpoint from `update_dropdown` so the frontend can issue a cheap reorder-only call from the drag-and-drop handler without transmitting full label strings.

## 5. Detailed Behavior & Edge Cases

### 5.1 Option uniqueness

Within a single dropdown, `value` must be unique (case-sensitive). `create_dropdown` and `update_dropdown` both validate this before writing. The service rejects payloads where two options share the same `value` with `HTTPException(422, "duplicate option value", detail={"duplicate": value})`.

### 5.2 In-use deletion block

`delete_dropdown("regions")` is blocked when any row in `crm_studio_fields` has `is_active=True` and `picklist_name="regions"`. The scan uses `FilterExpression` after a full table scan (acceptable for small field counts, per CLAUDE.md gotcha: "DDB FilterExpression doesn't reduce page size" — the scan must loop via `LastEvaluatedKey` if the fields table grows large). The 409 response body includes `{"code": "dropdown_in_use", "field_count": N}` so the frontend can display a helpful message listing the blocking fields.

Soft-deleted dropdowns (`is_active=False`) are not returned by `list_dropdowns` (default `include_inactive=False`) and are never eligible as `picklist_name` targets when creating new custom fields. The STU-011 field creation path validates that the referenced `picklist_name` resolves to an active dropdown.

### 5.3 Option deactivation vs. deletion

`update_dropdown` accepts `is_active: false` on individual options. Inactive options are excluded from `get_active_values` and therefore from picklist validation. Existing entity records that hold a now-inactive value are not retroactively invalidated — the validation layer only fires on new writes. This is the correct SuiteCRM-parity behavior: retiring an option does not corrupt historical data.

### 5.4 Reorder endpoint atomicity

`reorder_options` does a read-then-write (read current options, reassign `sort_order`, write back). It is not transactional. Concurrent reorders on the same list could produce an ordering from one writer clobbered by another. For a low-frequency admin operation this is acceptable. The frontend should optimistically update the displayed order after a successful 200 response.

### 5.5 Empty options list

`create_dropdown` accepts `options: []`. This creates a valid but empty dropdown. `get_active_values` returns `[]` for it. Picklist fields referencing an empty dropdown will reject any non-null value for the field. This is intentional: an admin can scaffold the dropdown before populating it.

### 5.6 `list_name` slug immutability

`list_name` is the DynamoDB partition key. It is immutable after creation. The `update_dropdown` endpoint does not accept `list_name` as a patchable field. If a rename is needed, the admin must create a new dropdown and re-point all referencing fields via the STU-011 field `PATCH` endpoint.

### 5.7 `validate_custom_fields` integration (STU-011 service)

In `app/services/crm_studio_fields.py`, the `validate_custom_fields(entity_type, data)` function iterates over active fields for the entity. For each field where `field_type in ("picklist", "multi_picklist")`:

```python
from app.services.crm_studio_dropdowns import get_active_values  # lazy import

active = get_active_values(field["picklist_name"])
if field["field_type"] == "picklist":
    if data.get(field["field_key"]) not in active:
        errors.append({field["field_key"]: f"value must be one of {active}"})
elif field["field_type"] == "multi_picklist":
    submitted = data.get(field["field_key"], [])
    invalid = [v for v in submitted if v not in active]
    if invalid:
        errors.append({field["field_key"]: f"invalid values: {invalid}"})
```

If `active` is `[]` (dropdown not found or empty), all values are rejected. This strictness is intentional and surfaces misconfigured field definitions early.

### 5.8 `multi_picklist` serialization

Multi-picklist values are stored on CRM entity records as a `StringSet` (DynamoDB `SS` type) or a `List` — this spec does not own the entity storage layer, but the validation layer accepts a Python `list[str]` from the incoming JSON payload.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

The service layer contains no `if S.dev_mode` branches. All DynamoDB writes and reads use `T.crm_studio_dropdowns` (resolved from `S.crm_studio_dropdowns_table_name`), which points to DynamoDB Local (port 8001) in dev and real DynamoDB in prod via the same `_safe_table` / `botocore` endpoint-URL override path. The `_FloatSafeTable` proxy (`app/core/tables.py:29`) handles the `float → Decimal` coercion transparently in both environments.

### 7.2 Idempotency

`create_dropdown` uses `ConditionExpression=Attr("pk").not_exists()`. A second identical POST returns 409 rather than silently overwriting. `update_dropdown` is idempotent for the same payload (writing the same values produces the same item; `updated_at` advances but this is expected).

`delete_dropdown` is idempotent for already-deleted items: it returns 404 (not 409) on a second call, matching the standard soft-delete convention used throughout the platform.

### 7.3 Input validation

`list_name` slugs are validated by both the Pydantic model (`Field(..., pattern=...)`) and the service layer (`_VALID_LIST_NAME_RE = re.compile(r"^[a-z][a-z0-9_]{1,63}$")`). Option `value` strings are validated by both layers. Double validation ensures defensive behavior even if service functions are called from non-HTTP paths (e.g., tests, admin scripts).

### 7.4 Auth enforcement

All write endpoints require ROOT (not ADMIN). This matches the SuiteCRM model where Studio DDL changes are reserved for super-admins. ADMIN users can read dropdown definitions for display purposes (e.g., when configuring field layouts in STU-013) but cannot mutate them.

### 7.5 Audit trail

Every mutating service call emits `audit_event(...)` via `app/services/alerts.audit_event` (`alerts.py:644`). Event names: `studio.dropdown.created`, `studio.dropdown.updated`, `studio.dropdown.deleted`, `studio.dropdown.reordered`. All events include `list_name` in the extra fields. These writes go to `T.alerts` (the platform-wide audit sink) and are therefore included in ENTERPRISE-004 audit exports (`app/routers/audit_export.py`) without any additional wiring.

### 7.6 No money-out paths

This ticket involves no financial operations and therefore does not invoke `refund_payment`, `settle_or_reverse_ledger`, or any billing primitives.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact with flag off

When `CRM_STUDIO_ENABLED=0` (the default), the `crm_studio` router is not imported or registered in `app/main.py`. All routes under `/ui/admin/studio/*` return 404. No new DynamoDB table is queried. The `T.crm_studio_dropdowns` handle is instantiated at startup (because `app/core/tables.py` unconditionally instantiates all handles), but the underlying table need not exist if the flag is off — boto3 raises on the first actual operation, not at handle construction time.

### 8.2 `just restart` creates the table

Running `just restart` executes `scripts/local-ddb-init.py`, which creates all tables including `crm_studio_dropdowns` even when the flag is off. This is intentional: pre-creating the table allows flipping the flag on without a restart.

### 8.3 Pre-existing CRM entity records

CRM entity records created before STU-012 was deployed do not have picklist custom fields. Once a picklist field is added (STU-011) and a dropdown is defined, all new writes to that entity type are validated against the dropdown. Existing records that do not pass through the validation layer (e.g., read-only views) are unaffected.

### 8.4 STU-011 dependency

If STU-011 has not been deployed, the `validate_custom_fields` integration hook described in Section 5.7 will not have a caller. STU-012 can be deployed independently without STU-011 (the dropdown CRUD endpoints are standalone), but the picklist validation integration only becomes active when STU-011 calls it. There is no runtime error when STU-011 is absent.

## 10. Open Questions / Assumptions

1. **STU-011 not yet implemented.** This spec assumes `app/services/crm_studio_fields.py` and `validate_custom_fields` will be implemented as part of STU-011 before the integration hook in Section 5.7 is wired. If STU-012 ships first, the integration hook can be left as a stub comment.

2. **Scan-based in-use check.** The "block delete when referenced" check uses a full table scan of `crm_studio_fields`. If that table grows large (thousands of custom field definitions), this scan could become slow. A targeted GSI on `crm_studio_fields` keyed on `picklist_name` would make the lookup O(1), but is deferred to avoid scope creep. A table with under 500 field definitions (typical CRM deployment) takes milliseconds to scan.

3. **Hard delete vs. soft delete.** This spec chooses soft delete (`is_active=False`) to preserve historical integrity. If a "purge" operation (hard delete) is needed later, it can be added as a separate ROOT-only endpoint (`DELETE /ui/admin/studio/dropdowns/{list_name}?hard=true`) with an explicit confirmation token.

4. **Pagination for `list_dropdowns`.** No cursor pagination is specified because a typical deployment has a small number of named dropdown lists. If deployments with hundreds of lists emerge, a `GET /ui/admin/studio/dropdowns?cursor=...&limit=50` cursor-based variant using `encode_cursor` / `decode_cursor` (`app/core/cursor.py:94`) should be added.

5. **Multi-tenancy.** The current data model has no `tenant_id` scoping on dropdown rows. If multi-tenant Studio isolation is required (e.g., different tenants with different dropdown lists), the `pk` scheme must change to `DROPDOWN#{tenant_id}#{list_name}`. This is deferred until STU tickets explicitly address tenancy.

6. **Relationship to STU-013 (layout editor).** Layout panels may reference picklist fields by `field_key`. The layout editor (STU-013) does not need to know the dropdown's option list — that is a field concern, not a layout concern. No direct dependency from STU-013 to STU-012 exists beyond the field definition.
