# CMP-001 — Non-email campaign types (phone / mail / fax / SMS)

## 1. Summary & Goal

SuiteCRM's Campaigns module supports five outreach channel types: `email`, `phone`, `mail`, `fax`, and `sms`. The planned `MarketingCampaignCreateIn` model in MKT-003 (`docs/ofbiz/specs/MKT-003.md:99–115`) has no `campaign_type` field — it implicitly treats all campaigns as email. This ticket adds an explicit `campaign_type` field to the MKT-003 model block and extends the MKT-009 `send_campaign` path to branch on channel type, ensuring that non-email campaigns produce the correct delivery behavior without regressing email campaigns.

The goal is SuiteCRM parity for the channel-type concept: operators can create phone, mail, fax, or SMS campaigns in the platform, filter the campaign list by type, and have the send path behave correctly for each channel. Email campaigns behave exactly as MKT-009 specifies. SMS campaigns leverage the existing `send_alert_sms` / `send_sms_bulk` production pipeline at `app/services/alerts.py:494–507` and `app/services/sms_delivery.py:207–310`. Phone, mail, and fax campaigns produce in-app alerts only (no electronic delivery infrastructure exists for those physical channels; delivery is out-of-band).

Everything is additive and gated on `S.marketing_campaigns_enabled` (established by MKT-002). With the flag off, the entire marketing surface is unchanged.

## 3. Data Model

### No new DynamoDB tables

CMP-001 does not introduce any new table. The `MarketingCampaigns` table (MKT-002) stores `campaign_type` as a plain string attribute on the existing item. The `MarketingCampaignSendLog` table (MKT-009) gains two additive attributes on each send-log row: `channel` (S) and `sms_sent` (BOOL). Both are sparse attributes — absent on rows written before CMP-001 deploys, present on rows written after. DynamoDB's schemaless model handles this without migration.

### `MarketingCampaigns` table (MKT-002, `T.marketing_campaigns`)

Default table name: `MarketingCampaigns` (env `DDB_MARKETING_CAMPAIGNS`).

Existing schema per MKT-002: PK=`OWNER#{owner_id}` (S), SK=`MKTCAMP#{campaign_id}` (S). GSIs: `ByOwnerCreatedAt` (PK=`owner_id`, SK=`created_at` N), `ByStatusCreatedAt` (PK=`status`, SK=`created_at` N).

CMP-001 additive attribute on the campaign item:

| Attribute | Type | Notes |
|-----------|------|-------|
| `campaign_type` | S | `"email"` \| `"phone"` \| `"mail"` \| `"fax"` \| `"sms"`. Defaults to `"email"` at read time via `item.get("campaign_type", "email")`. |

Adding a GSI on `campaign_type` is deferred — for MVP, `list_campaigns` applies a `FilterExpression` on the attribute after the primary `ByOwnerCreatedAt` GSI query. Expected result sets per owner are small enough that post-query filtering is acceptable; a `ByTypeCreatedAt` GSI can be added in a future follow-up ticket if analytics queries require it.

### `MarketingCampaignSendLog` table (MKT-009, `T.marketing_send_log`)

Default table name: `MarketingCampaignSendLog` (env `DDB_MARKETING_SEND_LOG`). Schema per MKT-009: PK=`CAMP#{campaign_id}` (S), SK=`SEND#{send_id}` (S). GSI `ByCampaignSentAt`: PK=`campaign_id` (S), SK=`sent_at` (N), `attr_types={"sent_at": "N"}`.

CMP-001 additive attributes on send-log rows:

| Attribute | Type | Notes |
|-----------|------|-------|
| `channel` | S | Value of `campaign_type` at send time. Absent on pre-CMP-001 rows; read back as `item.get("channel", "email")`. |
| `sms_sent` | BOOL | `True` if `send_alert_sms` was called and returned at least one non-`"failed"` status. Absent on email/phone/mail/fax rows. |
| `sms_number` | S | Redacted phone: last 4 digits only, e.g. `"***1234"`. Written only when `channel="sms"`. |

No `scripts/local-ddb-init.py` change is needed because neither attribute is a primary key, GSI key, or GSI sort key. The `attr_types={"sent_at": "N"}` declaration already exists in the MKT-009 `TableDef` block.

#### `send_campaign` / `_try_send_one` (MKT-009)

The central extension point is `_try_send_one`. The MKT-009 spec defines it to unconditionally call `write_alert` and `send_alert_email`. CMP-001 adds a channel-dispatch block:

```python
def _try_send_one(
    *,
    campaign_id: str,
    campaign_type: str,   # NEW — passed through from send_campaign
    party_id: str,
    source: str,
    source_id: str,
    snapshot_ts: int,
    subject: str,
    body_text: str,
    dry_run: bool,
    now: int,
) -> tuple[bool, bool]:
```

Channel-dispatch logic (inserted after step 5 of MKT-009 spec, after profile lookup):

```
if campaign_type == "email":
    # Existing MKT-009 path — unchanged
    write_alert(...)                           # in-app
    if email: send_alert_email([email], ...)  # SES / dev-log

elif campaign_type == "sms":
    # SMS path
    write_alert(..., event="marketing.campaign.sms")   # in-app
    phone = profile.get("displayed_telephone_number")
    if phone:
        results = send_alert_sms([phone], body_text)   # SNS / dev-log
        sms_ok = any(r.get("status") not in ("failed",) for r in results)
    else:
        sms_ok = False

else:  # "phone", "mail", "fax"
    # In-app alert only; physical channel is out-of-band
    write_alert(..., event=f"marketing.campaign.{campaign_type}")

```

`send_alert_sms` is imported from `app.services.alerts` (it is already defined there at line 494). No new module is imported; no new infrastructure is created.

The send-log row written by `_try_send_one` gains `channel=campaign_type`, `sms_sent=sms_ok` (when `campaign_type=="sms"`), and `sms_number=_redact_phone(phone)` (last 4 digits). `_redact_phone` is a one-line helper: `f"***{phone[-4:]}" if phone and len(phone) >= 4 else "***"`.

`send_campaign` passes `campaign_type=campaign.get("campaign_type", "email")` into each `_try_send_one` call.

## 5. Detailed Behavior & Edge Cases

### Channel dispatch rules

| `campaign_type` | `write_alert` called | `send_alert_email` called | `send_alert_sms` called | Notes |
|-----------------|---------------------|--------------------------|------------------------|-------|
| `"email"` | Yes | Yes (if profile has email) | No | MKT-009 behavior unchanged |
| `"sms"` | Yes | No | Yes (if profile has phone) | Uses existing `send_alert_sms` pipeline |
| `"phone"` | Yes | No | No | In-app alert only; note in details: `"channel": "phone"` |
| `"mail"` | Yes | No | No | In-app alert only; note in details: `"channel": "mail"` |
| `"fax"` | Yes | No | No | In-app alert only; note in details: `"channel": "fax"` |

### SMS channel edge cases

- **Missing phone number**: if `profile.get("displayed_telephone_number")` is `None` or empty, the SMS send is skipped. The in-app alert is still written. The send-log row records `sms_sent=False`. This is not counted as an error — it is counted as a partial send (`total_sent` incremented for the alert, but `sms_sent=False` on the log row).
- **Suppressed number**: `send_sms` (called by `send_alert_sms`) checks `is_sms_suppressed(phone)` at `app/services/sms_delivery.py:233–239` and returns `status="suppressed"`. The send-log row records `sms_sent=False`.
- **Rate-limited number**: `send_sms` returns `status="rate_limited"` when the per-number daily limit is exceeded (line 242–248). Same handling: `sms_sent=False` on log row.
- **Global cost cap**: `S.sms_daily_cost_cap_usd` at `app/core/settings.py:218` when non-zero halts all outbound SMS system-wide. `send_sms` returns `status="rate_limited"`. `_try_send_one` records this but does not abort the loop — remaining recipients continue to be processed (the cap applies per number, not per campaign).
- **`dry_run=True`**: the SMS send is not attempted. `_try_send_one` returns `(True, False)` at step 2 before reaching the dispatch block.

### Phone/mail/fax campaigns

The in-app alert for these channels uses `details={"campaign_id": campaign_id, "channel": campaign_type, "note": "Delivery via physical channel; complete outreach out-of-band."}`. This gives operators a checklist item in their notification feed for each contact. No external system is called; no telephone, print, or fax API is invoked (none exists in the codebase).

### Backward compatibility for `campaign_type="email"`

`send_campaign` on a campaign with `campaign_type="email"` (including legacy campaigns without the attribute, which default to `"email"` via `item.get("campaign_type", "email")`) follows the MKT-009 `_try_send_one` path exactly. No regression is possible because the dispatch block for `"email"` is structurally identical to the pre-CMP-001 code path.

### `list_campaigns` with `campaign_type` filter

When `campaign_type` is provided, the `FilterExpression` is applied. Because `FilterExpression` does not reduce the DDB 1MB page scan (per CLAUDE.md), `list_campaigns` must loop via `LastEvaluatedKey` until the requested `limit` of matching items is accumulated or the table is exhausted. The loop cap is 20 pages (≈ 10,000 items scanned) to prevent unbounded scans on large tables; if the cap is hit the function returns the accumulated results with a `cursor` pointing to the last evaluated key.

### Campaign status guard for `campaign_type` updates

Changing `campaign_type` is only allowed when the campaign is in `draft` status. An attempt to update `campaign_type` on an `active` or `completed` campaign raises `HTTPException(409, "campaign_type cannot be changed after activation")`. This check runs in `update_campaign` before the DDB `update_item` call, mirroring the MKT-006 status-machine guard for other immutable fields.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

No `if S.dev_mode` branch is introduced by CMP-001. The dev/prod split for email is already inside `send_alert_email` at `app/services/alerts.py:462–468` <!-- VERIFIED: alerts.py:462 `if S.dev_mode`, 467 `_write_dev_log(S.dev_email_log, ...)`, 468 `return` --> (dev logs to `S.dev_email_log`, prod calls SES). The dev/prod split for SMS is already inside `send_sms` at `app/services/sms_delivery.py:268+` <!-- VERIFIED: sms_delivery.py:268 `if S.dev_mode`, dev path → dev_sms_log (settings.py:302) --> (dev logs to `S.dev_sms_log`, prod calls SNS). CMP-001 calls those existing functions unconditionally; the parity boundary stays inside the primitives.

### Idempotency

Send idempotency is inherited entirely from MKT-009's `_try_send_one` design: `ConditionExpression="attribute_not_exists(pk)"` on the send-log put (MKT-009 spec step 3) ensures a `(campaign_id, snapshot_ts, party_id)` triple is processed exactly once. CMP-001 adds `channel` to the log row after the conditional put — this is a best-effort `update_item`; if it fails the dedup guarantee is unaffected because the conditional put already succeeded.

### Phone number privacy

The `sms_number` attribute on the send-log row stores only the last 4 digits (`"***1234"`). The full phone number is never written to DynamoDB by the campaign send path. This mirrors the suppression table PK pattern in `app/services/sms_delivery.py:5` (`SMS#{phone}`) which does store the full number in the suppression table — but that table is for suppression management, not campaign analytics.

### Input validation

`campaign_type` is validated at the Pydantic layer with `pattern=r"^(email|phone|mail|fax|sms)$"`. No SQL injection or DDB injection risk — the value is only written as a string attribute and never used as a key expression.

The `campaign_type` query parameter on `GET /ui/marketing/campaigns` is validated against `CAMPAIGN_TYPES` before reaching the service layer, raising `HTTPException(422)` for unknown values. This prevents unexpected `FilterExpression` values from being passed to DynamoDB.

### SMS opt-out

`send_sms` at `app/services/sms_delivery.py:233–239` <!-- VERIFIED: sms_delivery.py:233 --> checks the SMS suppression table before any delivery attempt. The `S.sms_suppression_enabled` flag (`app/core/settings.py:212` <!-- VERIFIED: settings.py:212 -->) controls whether this check runs. In addition, the platform-wide marketing opt-out check (`is_user_opted_out` at `app/services/cart_reminders.py:95–107` <!-- VERIFIED: cart_reminders.py:95–107 -->) runs in `_try_send_one` at step 4 (MKT-009 spec) for all channel types including SMS — a user who opts out of marketing communications is excluded from SMS campaigns as well as email campaigns.

## 8. Backward Compatibility & Migration

### Existing campaign items

Campaigns created before CMP-001 is deployed have no `campaign_type` attribute on their DDB item. All read paths (`get_campaign`, `list_campaigns`, `_try_send_one`) use `item.get("campaign_type", "email")` to default to `"email"`. No backfill is needed.

### Existing `MarketingCampaignOut` consumers

The `campaign_type: str = "email"` field on `MarketingCampaignOut` has a default value. Any consumer that deserializes the response (e.g., the MKT-012 frontend API wrappers) will receive `"email"` for legacy campaigns without explicit type, and the correct type for new campaigns. No breaking change.

### Send-log rows

Pre-CMP-001 send-log rows lack `channel`, `sms_sent`, and `sms_number` attributes. Any analytics query that reads these fields must use `item.get("channel", "email")` and `item.get("sms_sent", False)`. Attribution queries in MKT-005 read `email_sent` from the send-log; they are unaffected by the new attributes.

### `list_campaigns` signature change

Adding `campaign_type: Optional[str] = None` to `list_campaigns` is additive (default `None` = no filter). All existing callers that omit the parameter continue to receive all campaigns.

## 10. Open Questions / Assumptions

1. **Phone/mail/fax out-of-band delivery**: This spec assumes no third-party phone-call, print-mail, or fax API is available or planned. The in-app alert serves as a "to-do" notification for the operator. If a fax or mail delivery vendor (e.g., ClickSend, Lob) is added in a future ticket, the `else` branch in `_try_send_one` can be extended to call that vendor's service. The `channel` attribute on the send-log row is designed to support that extension without table migration.

2. **SMS type requires `S.alerts_sms_enabled=1` in production**: The ticket enables the channel type; actual SMS delivery also requires the SNS plumbing to be configured (`ALERTS_SMS_ENABLED=1`, `S.sms_origination_number` or `S.sms_sender_id`). Dev environments get dev-log behavior from `send_sms` without any SNS configuration.

3. **`list_campaigns` filter — GSI vs. scan**: filtering by `campaign_type` using `FilterExpression` is sufficient for small per-owner lists. If the platform expects campaigns in the thousands per owner for a given type, a `ByTypeCreatedAt` GSI should be added. This is deferred to a follow-up.

4. **`displayed_telephone_number` privacy**: the profile field is marked `"private"` visibility at `app/services/profile.py:93`. `_try_send_one` calls `get_profile(party_id)` which returns the owner's full profile (no audience filtering, since this is a server-to-server call, not a cross-user read). This is correct — campaign sends run on behalf of the campaign owner who by definition has permission to contact their own list members.

5. **`campaign_type` update guard timing**: the spec blocks type changes for `active` campaigns. The exact status set that permits changes (`draft` only, or also `scheduled`/`paused`) should align with the MKT-006 status-machine definition. This spec assumes `draft`-only; if MKT-006 allows field edits in `paused` state, the guard should be updated accordingly.
