# ACT-007 — CRM Call Logging — link call log to CRM entity

**Ticket type:** Feature
**Priority:** P2
**Estimate:** 1d
**Flag:** `crm_activities_enabled` (default OFF) — sourced from ACT-001

---

## 1. Summary & Goal

ACT-007 extends the user-authored CRM call log introduced in ACT-006 with optional entity-linking fields so that a call record can be associated with a Contact, Lead, Account, or Opportunity. It also introduces a dedicated by-entity query endpoint and wires the call log into the CRM Activity Timeline (ACT-009) via a fire-and-forget call so that linked calls appear in the per-entity chronological feed once ACT-009 ships.

The scope is deliberately narrow: two optional fields (`linked_entity_type`, `linked_entity_id`) are added to the create and output models, a new `list_crm_call_logs_for_entity` service function is added, a single new router endpoint (`GET /ui/calls/logs/by-entity`) is declared, and the create path gains a best-effort `record_crm_activity` call. No new DynamoDB table is required. The Party/Contact/Account module (PTY-001..PTY-015) is a soft prerequisite: `linked_entity_id` is stored as an opaque string at this ticket boundary, so ACT-007 ships and provides value before PTY records exist.

With `CRM_ACTIVITIES_ENABLED=0` (the default) the platform is byte-for-byte unchanged: no new routes exist, no DDB writes occur, no background work runs.

## 2. Context & Current State

### 2.1 Existing call log shape (ACT-006)

ACT-006 (`docs/suitecrm/specs/ACT-006.md`) introduced `create_crm_call_log`, `list_crm_call_logs`, `get_crm_call_log`, `update_crm_call_log`, and `delete_crm_call_log` in `app/services/call_history.py`. These functions write and query items on the existing `call_history` DynamoDB table (PK `user_id` / SK `CALLLOG#{inverted_ts:013d}#{call_id}`) using the `CALLLOG#` prefix to avoid collision with platform telephony records (`CALL#` prefix).

The ACT-006 DDB item shape (grounded in `app/services/call_history.py:52–68`) carries: `user_id`, `sk`, `call_id`, `subject`, `description`, `direction`, `duration_seconds`, `outcome`, `call_type`, `contact_user_sub`, `created_at`, `updated_at`. It does **not** carry `linked_entity_type` or `linked_entity_id`.

The `_item_to_out` function at `call_history.py:178–188` is the existing platform projection function (platform calls only). ACT-006 introduces `_calllog_item_to_out`, the CRM-log projection that mirrors it. ACT-007 extends `_calllog_item_to_out` to include the two new entity-link fields.

### 2.2 ACT-006 Pydantic models (current state in `app/models.py`)

ACT-006 appended the following models after `CallStatsOut` (`app/models.py:6121`):

- `CallOutcome` — enum: `connected`, `not_connected`, `left_message`, `wrong_number`, `busy`.
- `CallLogCreateIn` — `subject`, `description`, `direction`, `duration_seconds`, `outcome`, `call_type`, `contact_user_sub`. No entity-link fields.
- `CallLogUpdateIn` — `subject`, `description`, `outcome`. Immutable fields intentionally omitted.

### 2.3 Existing router (`app/routers/call_history.py`)

The router file (`call_history.py:1–76`) uses `APIRouter(prefix="/ui/calls", tags=["call-history"])` and imports `require_ui_session` from `app.services.sessions` (`call_history.py:18`). ACT-006 appended five routes under `/ui/calls/logs`. ACT-007 appends a sixth: `GET /ui/calls/logs/by-entity`.

ACT-007 calls this function from `create_crm_call_log` when `linked_entity_type` is set. Because ACT-009 may ship after ACT-007, the call is wrapped in `try/except` and uses a lazy local import:

### 2.5 DynamoDB query strategy for by-entity

The ACT-007 ticket source (`CRM_ACTIVITIES_TICKETS.md:359`) states: "queries `T.call_history` using a `FilterExpression` on `linked_entity_type` + `linked_entity_id` (no new GSI needed at this volume; add GSI if query latency becomes an issue once PTY ships)."

`app/services/call_history.py:73–96` shows `list_call_history` already uses a `ScanIndexForward=True` / `begins_with` pattern. The same pattern applies to `list_crm_call_logs_for_entity`: query by PK (`user_sub`) with `begins_with(sk, "CALLLOG#")`, then apply `FilterExpression` on `linked_entity_type` and `linked_entity_id`. Because DynamoDB applies `FilterExpression` after fetching up to 1 MB per page (CLAUDE.md gotcha: "DDB FilterExpression doesn't reduce page size"), the function must loop via `LastEvaluatedKey` until either the limit is met or pages are exhausted.

- `app/core/cursor.encode_cursor` / `decode_cursor` (`cursor.py:94–131`) — used by `list_crm_call_logs`; reused identically by `list_crm_call_logs_for_entity`.

#### 4.1.3 New `list_crm_call_logs_for_entity`

```python
def list_crm_call_logs_for_entity(
    user_sub: str,
    entity_type: str,
    entity_id: str,
    cursor: Optional[str] = None,
    limit: int = 20,
) -> Dict[str, Any]:
    """Return call logs owned by user_sub linked to the given entity.

    Queries by PK (user_sub) + CALLLOG# prefix, then applies FilterExpression.
    Loops via LastEvaluatedKey because DynamoDB evaluates FilterExpression after
    the 1MB page fetch — a single query call may return 0 items even when
    matching items exist beyond the first page.
    """
    from boto3.dynamodb.conditions import Key, Attr

    max_items = min(limit, 100)
    exclusive_start = decode_cursor(cursor)
    collected: list = []
    last_key = exclusive_start

    while len(collected) < max_items:
        kwargs: Dict[str, Any] = {
            "KeyConditionExpression": (
                Key("user_id").eq(user_sub) & Key("sk").begins_with(_CALLLOG_PREFIX)
            ),
            "FilterExpression": (
                Attr("linked_entity_type").eq(entity_type)
                & Attr("linked_entity_id").eq(entity_id)
            ),
            "Limit": max_items * 4,   # over-fetch to compensate for sparse filter
            "ScanIndexForward": True,
        }
        if last_key:
            kwargs["ExclusiveStartKey"] = last_key

        resp = T.call_history.query(**kwargs)
        collected.extend(resp.get("Items", []))
        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break

    page = collected[:max_items]
    # Build next cursor from last processed item's key if more items remain
    next_key = None
    if len(collected) > max_items and page:
        last_item = page[-1]
        next_key = {"user_id": last_item["user_id"], "sk": last_item["sk"]}

    return {
        "items":       [_calllog_item_to_out(it) for it in page],
        "next_cursor": encode_cursor(next_key),
    }
```

Note: the `Limit` over-fetch factor (4×) is a pragmatic heuristic; callers with very sparse entity links may need multiple round-trips, which the loop handles. This matches the approach used in `app/services/kyc_cases.py` (CLAUDE.md: "DDB FilterExpression doesn't reduce page size — must loop via LastEvaluatedKey").

## 5. Detailed Behavior & Edge Cases

### 5.1 Partial entity link (one field set, the other absent)

`linked_entity_type` and `linked_entity_id` are a semantic pair. Providing one without the other is a caller error. `create_crm_call_log` enforces this at the service layer:

```python
if bool(body.linked_entity_type) != bool(body.linked_entity_id):
    raise ValueError(
        "linked_entity_type and linked_entity_id must both be provided or both omitted"
    )
```

The router handler converts `ValueError` from the service into `HTTPException(422)`. This is consistent with how `record_call` in the same file raises `ValueError` for invalid `call_type` (line 43) and the router at line 67–75 wraps it as `HTTPException(422)`.

### 5.2 `linked_entity_type=opportunity` before Opportunity module ships

The ticket source explicitly states: "`linked_entity_type=opportunity` is accepted without error even before an Opportunity module exists." The `Literal` constraint in `CallLogCreateIn` accepts all four values. There is no FK check against any PTY or Opportunity table. The stored value is an opaque string. `list_crm_call_logs_for_entity?entity_type=opportunity&entity_id=opp_xyz` returns only calls linked to that ID — an empty list if none exist, not a 404.

### 5.3 Entity reassignment is not allowed after creation

`CallLogUpdateIn` does not include `linked_entity_type` or `linked_entity_id`. A PATCH request cannot change the entity link. This is an intentional audit-integrity decision (same rationale as `direction`, `duration_seconds`, `call_type` being immutable in ACT-006 §3.3). Callers who need to re-link a call must delete and re-create it.

### 5.4 FilterExpression performance and the DynamoDB 1MB page boundary

`list_crm_call_logs_for_entity` may issue multiple DynamoDB queries per call if `CALLLOG#` items for the user are plentiful but sparsely linked to the target entity. The loop terminates when either:
- `len(collected) >= max_items` (enough results found), or
- `LastEvaluatedKey` is absent (all pages exhausted).

The `Limit=max_items * 4` per-request over-fetch is a conservative heuristic. When PTY-shipped entity IDs are widely used, the query density will increase and the filter will be selective, making single-page results common. If the over-fetch factor proves insufficient on large user logs, a `ByEntity` GSI can be added to `call_history` via an `UpdateTable` migration without any application-layer changes beyond updating the query in `list_crm_call_logs_for_entity`. This is noted as a deferred optimization in §10.

### 5.5 Timeline write failure does not block the primary operation

If `crm_activity_timeline.record_crm_activity` raises any exception (including `ImportError` before ACT-009 ships, or any DynamoDB error), the `except Exception` block logs a warning at DEBUG level and the `create_crm_call_log` function returns the newly created call log item normally. The caller receives HTTP 201 with the call log data. The timeline entry is simply absent until the call is re-linked or a backfill runs. This mirrors the `_record_timeline` lazy-import pattern documented in CLAUDE.md ("Best-effort: swallows exceptions").

### 5.6 Existing call logs created by ACT-006 (no entity link)

Items in `call_history` written by ACT-006 (before ACT-007 ships) lack `linked_entity_type` and `linked_entity_id`. `_calllog_item_to_out` uses `.get("linked_entity_type")` → `None`, `.get("linked_entity_id")` → `None`. These items are correctly projected as `CallLogOut` with both entity fields as `None`. `list_crm_call_logs_for_entity` never returns these items because the `FilterExpression` requires both attributes to match a specific value; items missing the attribute do not satisfy `Attr("linked_entity_type").eq(...)`.

### 5.7 `entity_type` query parameter validation

The `GET /ui/calls/logs/by-entity` endpoint validates `entity_type` via FastAPI `Query(..., pattern="^(contact|lead|account|opportunity)$")`. An unknown entity type (e.g. `entity_type=invoice`) returns HTTP 422 immediately without issuing a DynamoDB query. `entity_id` has `min_length=1, max_length=200` to prevent empty-string or oversized queries.

### 5.8 Concurrent creates with the same entity link

Two simultaneous `POST /ui/calls/logs` calls with the same `linked_entity_type` and `linked_entity_id` each write distinct items (different `call_id`, different SK). DynamoDB PK uniqueness is at the `(user_id, sk)` level; because each SK includes a UUID, there is no collision. Both calls may fire `record_crm_activity`; the timeline table (ACT-009) is keyed by `(entity_key, sk)` where the SK includes the `activity_id` (call_id), so both timeline entries are distinct.

### 5.9 User sub vs. entity ID scope

`list_crm_call_logs_for_entity` queries by `user_sub` (PK) first, then filters by entity. This means a call log is visible in a by-entity query only to the user who created it. There is no cross-user entity view in this ticket — an admin CRM entity detail page would require a separate admin-scoped endpoint querying a GSI rather than by user PK. That is deferred to a future admin CRM module.

## 6. Feature Flag & Config

### 6.1 Flag inheritance

ACT-007 does not introduce any new flag. It is entirely gated on `crm_activities_enabled`, the master flag introduced by ACT-001:

```python
crm_activities_enabled: bool = os.environ.get(
    "CRM_ACTIVITIES_ENABLED", "false"
).lower() == "true"
```

This flag is checked at the top of every route handler via `_require_crm_flag()` (introduced by ACT-006). With the flag off:
- All `/ui/calls/logs` routes return `404 Not Found`.
- `create_crm_call_log` is never called from the router.
- The timeline fire-and-forget block inside `create_crm_call_log` never executes.
- The existing platform call routes (`/ui/calls/history`, `/ui/calls/record`, `/ui/calls/stats`) are completely unaffected.

ACT-006 and ACT-007 are both extensions of the call log functionality and use only the top-level `crm_activities_enabled` gate — consistent with the ticket source specification.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No dev_mode branch

There is no `if S.dev_mode` branch in any new code. All DynamoDB reads and writes go through `T.call_history`, which resolves to DynamoDB Local (port 8001) in dev and real DynamoDB in prod. The `audit_event` call writes to `T.alerts` in both environments. The fire-and-forget `record_crm_activity` call writes to `T.crm_activity_timeline` (when ACT-009 is available) — the same table in both environments. No mock code paths are introduced.

### 7.2 Idempotency

`create_crm_call_log` generates a new UUID `call_id` on every invocation. It is not designed to be idempotent — two POSTs with the same body produce two distinct items. Callers must use `GET /ui/calls/logs` to detect duplicates before posting. The by-entity query endpoint is fully idempotent (read-only). DELETE follows standard REST semantics (200 on first delete, 404 on retry).

### 7.3 Ownership enforcement and IDOR prevention

All service functions anchor DynamoDB queries on `user_id = :uid` (the authenticated `user_sub` from `require_ui_session`). `list_crm_call_logs_for_entity` queries by the calling user's sub; it returns only that user's records. It is not possible to enumerate another user's linked calls by supplying a different `entity_id` — the PK scope prevents cross-user reads. The router returns 404 rather than 403 for any missing or unauthorized resource (does not confirm existence of other users' records).

### 7.4 Input validation

- `linked_entity_type`: validated by Pydantic `Literal` in `CallLogCreateIn`; unknown values return 422.
- `linked_entity_id`: `Optional[str]` with no max-length constraint in the model (matches the ACT-008 task spec which also stores it as an opaque string). The router's `Query(..., max_length=200)` cap on the GET endpoint prevents oversized filter values; the POST body has no explicit max-length on `linked_entity_id` to allow future PTY IDs of any format. If a max-length is desired at POST time, `Field(max_length=500)` can be added without breaking backward compatibility.
- Partial link guard (§5.1) catches the one-field-without-other case and returns 422 before DDB write.

### 7.5 Audit trail

The `audit_event` call in `create_crm_call_log` includes `linked_entity_type` and `linked_entity_id` as kwargs so auditors can query the alerts table for all calls linked to a specific entity. The three existing audit event names from ACT-006 (`crm_call_log_created`, `crm_call_log_updated`, `crm_call_log_deleted`) are unchanged. `crm_call_log_created` is enriched with the two new fields.

### 7.6 No money-out paths

This ticket involves no payment, refund, or ledger operations. The billing primitive reuse requirement (CLAUDE.md: "any money-out reuses refund_payment / settle_or_reverse_ledger") is not applicable.

### 8.1 DDB table schema

## 10. Open Questions / Assumptions

1. **GSI deferral trigger**: The ticket source says "add GSI if query latency becomes an issue once PTY ships." A concrete threshold should be defined: if P99 `list_crm_call_logs_for_entity` latency exceeds 500 ms under production load, add a `ByEntity` GSI (`GSI1PK = ENTITY#{linked_entity_type}#{linked_entity_id}`, `GSI1SK = created_at`, `attr_types={"GSI1SK": "N"}`). Adding the GSI requires an `UpdateTable` + async backfill in prod and a `scripts/local-ddb-init.py` update in dev. The application query in `list_crm_call_logs_for_entity` would switch to the GSI and remove the FilterExpression loop.

2. **Cross-user entity queries (admin CRM view)**: The current design scopes all by-entity queries to the authenticated user's own records. A CRM admin or manager role that needs to see all calls linked to a given contact (regardless of which team member logged them) requires a separate admin endpoint that queries the potential GSI or scans with a different PK strategy. This is deferred to a future admin CRM module.

3. **`linked_entity_id` format contract**: Currently opaque. Once PTY-001..PTY-015 ship, the format of PTY party IDs will be known. The call log stores whatever string the caller provides. If PTY IDs have a known prefix (e.g. `PARTY#` or a UUID format), the service could validate format at create time. Deferred until PTY ships.

4. **Backfill of ACT-006 items**: Calls created by ACT-006 before ACT-007 ships have no entity link. If users want to retroactively link them, they must delete and re-create (entity reassignment is intentionally blocked via immutable-field policy). A separate "re-link" endpoint could be added if this becomes a significant UX friction point.

5. **`_timeline_record` wrapper naming**: The spec proposes a module-level `_timeline_record(...)` helper in `app/services/call_history.py` to make the timeline call monkeypatchable in tests. This is an internal implementation detail; the function is not exported. Alternative approach: monkeypatch `app.services.crm_activity_timeline` in `sys.modules` before import (same pattern as `tests/test_gap_0235_0236_ssh_bastion_multihop.py`). Either approach satisfies the hermetic test requirement.
