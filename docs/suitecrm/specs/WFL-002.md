# WFL-002 — Workflow rule data model & CRUD service

**Type:** Feature | **Priority:** P0 | **Estimate:** 2d

**Unblocks:** WFL-003, WFL-004, WFL-005, WFL-006, WFL-007, WFL-008, WFL-009

## 1. Summary & Goal

Implement `app/services/workflow_rules.py` — the authoritative data-layer service for persisting, retrieving, and mutating CRM workflow rule definitions in DynamoDB. This ticket is **pure data layer**: no router, no executor, no background worker. Every subsequent WFL ticket imports and calls these service functions rather than touching the table directly.

The service provides seven typed CRUD functions (`create_rule`, `get_rule`, `list_rules`, `update_rule`, `delete_rule`, `enable_rule`, `disable_rule`) plus one internal bulk-fetch helper (`list_rules_for_module`) consumed by the on-save hook (WFL-004) and the scheduler worker (WFL-005).

Matching Pydantic request/response models are added to `app/models.py` following the `ScheduledActionCreateIn` / `ScheduledActionOut` pattern at `app/models.py:3319–3362`.

## 3. Data Model

### 3.1 DynamoDB table: `crm_workflow_rules`

Provisioned by WFL-001 in `scripts/local-ddb-init.py`. Spec repeated here for completeness.

```
TableDef(
    _resolve_table_name(S.crm_workflow_rules_table_name, "crm_workflow_rules"),
    "pk",          # PK (S)
    "sk",          # SK (S)
    gsi=[{
        "index_name": "ByModule",
        "partition_key": "GSI_MODULE_PK",   # S — "MODULE#{target_module}"
        "sort_key": "GSI_MODULE_SK",        # N — created_at Unix timestamp
    }],
    attr_types={"GSI_MODULE_SK": "N"},      # REQUIRED — prevents ValidationException
)
```

**Row schema (META row for a rule definition):**

| Attribute | Type | Value |
|-----------|------|-------|
| `pk` | S | `RULE#{rule_id}` |
| `sk` | S | `META` |
| `rule_id` | S | `wfl_` + 12-char hex UUID |
| `name` | S | human-readable label |
| `description` | S | optional |
| `target_module` | S | one of `TARGET_MODULES` |
| `trigger_type` | S | one of `TRIGGER_TYPES` |
| `trigger_config` | M | varies by trigger_type (see §4.1) |
| `conditions` | L | list of condition dicts |
| `actions` | L | list of action dicts (ordered) |
| `enabled` | BOOL | `True` at creation |
| `created_by` | S | user_sub of creating admin |
| `created_at` | N | Unix timestamp (`now_ts()`) |
| `updated_at` | N | Unix timestamp |
| `GSI_MODULE_PK` | S | `MODULE#{target_module}` |
| `GSI_MODULE_SK` | N | `created_at` |

`GSI_MODULE_SK` carries `created_at` so `list_rules_for_module` can return rules in stable insertion order without a post-query sort.

No TTL attribute on rule definitions — rules persist until explicitly deleted.

### 3.2 Constants

```python
TRIGGER_TYPES = ["on_save", "on_schedule", "on_time_elapsed"]

TARGET_MODULES = ["ticket", "contact", "order", "subscription", "lead"]

TRIGGER_CONFIG_SCHEMA = {
    "on_save":         {"events": list},          # subset of ["create", "update"]
    "on_schedule":     {"cron_expression": str,   # e.g. "0 9 * * 1"
                        "timezone": str},          # e.g. "UTC"
    "on_time_elapsed": {"field": str,             # record attribute name
                        "offset_hours": int},      # fire N hours after field value
}
```

### 3.3 Condition dict (stored inline in the `conditions` list)

```python
{
    "field":    str,               # record attribute name
    "operator": str,               # eq|neq|contains|gt|lt|is_empty|is_not_empty
    "value":    str | None,        # None only for is_empty / is_not_empty
}
```

An empty `conditions` list means "always match" (evaluated by WFL-003's `evaluate_conditions([], record) → (True, [])`).

### 3.4 Action dict (stored inline in the `actions` list)

```python
{
    "action_type": str,   # modify_field|create_record|send_email|drip_sequence
    "config":      dict,  # type-specific (validated by executor, not here)
}
```

WFL-002 stores and returns these opaque dicts without validating `config` internals — executor tickets (WFL-006, WFL-007, WFL-008) own config validation.

## 4. API / Service Design

### 4.1 Service functions (`app/services/workflow_rules.py`)

All functions guard on `S.crm_workflow_enabled` at the top of the module via a module-level helper:

```python
def _require_flag() -> None:
    if not S.crm_workflow_enabled:
        raise RuntimeError("crm_workflow is disabled")
```

Internal callers (e.g. `list_rules_for_module` called from the on-save hook) instead check the flag with an early `if not S.crm_workflow_enabled: return []` to avoid raising exceptions in fire-and-forget hook paths.

---

#### `create_rule`

```python
def create_rule(
    *,
    created_by: str,
    name: str,
    description: str = "",
    target_module: str,
    trigger_type: str,
    trigger_config: dict,
    conditions: list[dict],
    actions: list[dict],
    enabled: bool = True,
) -> dict:
```

1. `_require_flag()`
2. Validate `target_module in TARGET_MODULES` — raises `ValueError("invalid_target_module")` if not.
3. Validate `trigger_type in TRIGGER_TYPES` — raises `ValueError("invalid_trigger_type")`.
4. `len(conditions) > S.crm_workflow_max_conditions_per_rule` — raises `OverflowError`.
5. `len(actions) > S.crm_workflow_max_actions_per_rule` — raises `OverflowError`.
6. Generate `rule_id = "wfl_" + uuid.uuid4().hex[:12]`.
7. Build item with `pk=f"RULE#{rule_id}"`, `sk="META"`, `GSI_MODULE_PK=f"MODULE#{target_module}"`, `GSI_MODULE_SK=created_at` (numeric).
8. `T.crm_workflow_rules.put_item(Item=item)`.
9. `audit_event("crm_workflow_rule.created", created_by, rule_id=rule_id, name=name, target_module=target_module)`.
10. Return `get_rule(rule_id)`.

---

#### `get_rule`

```python
def get_rule(rule_id: str) -> dict | None:
```

`T.crm_workflow_rules.get_item(Key={"pk": f"RULE#{rule_id}", "sk": "META"})` — returns `None` if item absent.

---

#### `list_rules`

```python
def list_rules(
    *,
    target_module: str | None = None,
    enabled_only: bool = False,
    limit: int = 25,
    cursor: str | None = None,
) -> dict:   # {"rules": [...], "cursor": str | None}
```

- When `target_module` is supplied: queries `ByModule` GSI with `GSI_MODULE_PK = "MODULE#{target_module}"`, `ScanIndexForward=True` (ascending `created_at`), `Limit=limit`, `ExclusiveStartKey=decode_cursor(cursor)`.
- When `target_module` is `None`: uses `T.crm_workflow_rules.scan(Limit=limit, ExclusiveStartKey=...)` — acceptable because `crm_workflow_rules` is an admin-only, low-cardinality table bounded by `S.crm_workflow_max_rules_per_module * len(TARGET_MODULES)`.
- If `enabled_only=True`: adds a `FilterExpression=Attr("enabled").eq(True)`. As per CLAUDE.md, DynamoDB's `FilterExpression` is applied post-page; callers must not assume `limit` items are always returned.
- Returns `{"rules": [_rule_out(item) for item in items], "cursor": encode_cursor(last_evaluated_key)}`.

---

#### `update_rule`

```python
def update_rule(
    rule_id: str,
    *,
    updated_by: str,
    name: str | None = None,
    description: str | None = None,
    trigger_config: dict | None = None,
    conditions: list[dict] | None = None,
    actions: list[dict] | None = None,
    enabled: bool | None = None,
) -> dict | None:
```

Builds a partial `UpdateExpression` for only the supplied (non-None) fields. Always sets `updated_at = now_ts()`. Returns `None` if rule does not exist. Emits `audit_event("crm_workflow_rule.updated", updated_by, rule_id=rule_id, changed_fields=[...])`.

Immutable fields (`rule_id`, `target_module`, `trigger_type`, `created_by`, `created_at`) are never included in the update expression. Changing `target_module` or `trigger_type` requires a delete-and-recreate.

---

#### `delete_rule`

```python
def delete_rule(rule_id: str, *, deleted_by: str) -> bool:
```

Hard-deletes the META row. Returns `False` if the rule was not found. Emits `audit_event("crm_workflow_rule.deleted", deleted_by, rule_id=rule_id)`. Does **not** purge run history from `T.crm_workflow_runs` — runs are append-only and may be referenced for audit queries after deletion.

---

#### `enable_rule` / `disable_rule`

```python
def enable_rule(rule_id: str, *, actor: str) -> dict | None:
def disable_rule(rule_id: str, *, actor: str) -> dict | None:
```

Each issues a targeted `UpdateExpression SET enabled = :val, updated_at = :ts`. Returns the updated rule dict or `None` if not found. Emits `crm_workflow_rule.enabled` / `crm_workflow_rule.disabled` audit events.

---

#### `list_rules_for_module`

```python
def list_rules_for_module(target_module: str) -> list[dict]:
```

Used internally by the on-save hook (WFL-004) and scheduler (WFL-005). **Not** exposed via the HTTP API.

1. `if not S.crm_workflow_enabled: return []` — guard, never raises.
2. Queries `ByModule` GSI: `GSI_MODULE_PK = "MODULE#{target_module}"`, `FilterExpression=Attr("enabled").eq(True)`, pages via `LastEvaluatedKey` loop until exhausted (rule counts bounded by `S.crm_workflow_max_rules_per_module`, so no more than 2 pages in practice).
3. Returns list of rule dicts sorted ascending by `created_at` (GSI already in this order, but post-filter ordering is confirmed in-process).

## 5. Detailed Behavior & Edge Cases

**Validation order in `create_rule`:**  
`target_module` → `trigger_type` → conditions count → actions count. This order ensures the caller receives the most specific error first and never writes a partial item.

**`conditions=[]` semantics:**  
An empty conditions list is stored as-is and means "fire for every record". The executor (WFL-003/006) evaluates `evaluate_conditions([], record) → (True, [])`. `list_rules_for_module` returns such rules; they should not be filtered out.

**`enabled` flag at creation:**  
Default is `True`. Callers wishing to create a rule in draft state pass `enabled=False`. The `ByModule` GSI always indexes both enabled and disabled rules; `list_rules_for_module` applies a `FilterExpression` to exclude disabled rules at read time.

**`trigger_config` is stored opaque:**  
WFL-002 does not validate the internal shape of `trigger_config` beyond confirming `trigger_type` is in `TRIGGER_TYPES`. Structural validation of `trigger_config` contents (e.g. `cron_expression` syntax) is the responsibility of WFL-005 (scheduler) or WFL-009 (router-level Pydantic sub-models in a follow-up). This keeps WFL-002 decoupled.

**Decimal coercion from DynamoDB:**  
`GSI_MODULE_SK` and `created_at` / `updated_at` are stored as DynamoDB Number (N) attributes. `get_item` returns them as `Decimal`. `_rule_out(item)` must cast these with `int(item["created_at"])` to avoid Pydantic/JSON serialization errors — mirrors `_action_out` in `app/services/scheduled_actions.py:50–84`.

**`list_rules` with `enabled_only=True` and page boundary:**  
Because DynamoDB applies `FilterExpression` after fetching up to `Limit` items, a page of `limit=25` may return fewer than 25 results if many rules are disabled. Callers must follow `cursor` until `cursor is None` to enumerate all matching rules. This is the same behavior documented in CLAUDE.md for sparse-attribute filters.

**Concurrent `enable_rule` / `disable_rule`:**  
Last-writer-wins; no version check needed. Enabling an already-enabled rule is a no-op that still emits an audit event. WFL-006 checks `rule["enabled"]` at execution time to handle the race between disable and execution.

**`delete_rule` does not cascade to `crm_workflow_runs`:**  
Run history is append-only and preserved for audit. WFL-006 handles the "rule deleted after enqueue" case by calling `get_rule(rule_id)` and exiting early if `None`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**No `if S.dev_mode` branches in business logic.** All DDB writes use `T.crm_workflow_rules` which resolves to `DDB_ENDPOINT_URL=http://localhost:8001` in dev and the real AWS DynamoDB endpoint in prod. The table name is env-configurable (`CRM_WORKFLOW_RULES_TABLE_NAME`) so dev and prod use the same code path with different table names — identical to the `scheduled_actions` pattern (`app/core/settings.py:1932`).

**Idempotency of `create_rule`:** Each call generates a fresh `rule_id = "wfl_" + uuid.uuid4().hex[:12]`, so retried POSTs produce duplicate rules. The router (WFL-009) is responsible for idempotency keys if needed. The service layer does not deduplicate by name.

**Audit trail:** Every mutating service function calls `audit_event(...)` from `app/services/alerts.py:644`. In dev this writes a dev-log entry; in prod it writes to `T.alerts` (DDB) and optionally fires webhooks — same code path, no branch.

**Input bounds:** `S.crm_workflow_max_conditions_per_rule` and `S.crm_workflow_max_actions_per_rule` (both default 10) prevent DDB item size exhaustion from unbounded list growth. `name` is limited to 200 characters by the Pydantic model (`max_length=200`); `description` to 2000. `trigger_config`, `conditions`, and `actions` are stored as DDB Maps/Lists; DDB's 400KB item limit provides a hard ceiling even if application limits are relaxed.

**No PII stored in rule definitions.** `created_by` is a user_sub (opaque identifier), not an email address — consistent with the `audit_event` signature at `app/services/alerts.py:644`.

## 10. Open Questions / Assumptions

1. **`max_rules_per_module` enforcement.** `create_rule` queries the `ByModule` GSI with `Select="COUNT"` before writing and raises `OverflowError` if the count meets `S.crm_workflow_max_rules_per_module`. Implementer should confirm exact vs approximate is acceptable; at the default cap of 50, an exact count query is fine.

2. **`trigger_config` validation depth.** `cron_expression` syntax validation is deferred to WFL-005 (scheduler). WFL-009 (router) may add a `_validate_trigger_config` call before `create_rule` for user-friendly API errors without changing the service contract.

3. **GSI eventual consistency.** `list_rules_for_module` reads a GSI; a rule created milliseconds earlier may not yet appear. For the on-save hook (WFL-004) this is acceptable. For the admin UI (WFL-009) a base-table `Scan` with `ConsistentRead=True` is an option but adds cost and is not required at this volume.

4. **Rule name uniqueness.** Not enforced at the DDB layer. Duplicate names are permitted; the admin UI (WFL-009) may surface a warning.
