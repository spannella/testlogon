# EVT-011 — Document library — category, description, and record-link fields on file nodes

**Type:** Feature | **Priority:** P2 | **Estimate:** 2d
**Source:** `docs/suitecrm/CRM_MISC_TICKETS.md` (section "EVT-011")
**Dependencies:** EVT-001 (flag pattern). Soft dependency on PTY-001 for `account`/`contact` record types.

---

## 1. Summary & Goal

This ticket adds three additive CRM metadata attributes to existing file-manager file nodes in the `file_manager` DynamoDB table:

- `crm_category` — an optional free-text string categorising the document (e.g. "Contracts", "Marketing", "Technical").
- `crm_description` — an optional long-form description up to 2 000 characters.
- `linked_record_type` / `linked_record_id` — an optional pair that associates a file node with a CRM record (contact, ticket, account, or party).

All three are additive attributes written on to the existing `NODE#<path>` item in the `file_manager` table via a targeted `update_item` call. No existing column is modified, and no new DynamoDB table is required.

Two new endpoints are added to `app/routers/filemanager.py` under the existing `/v1/fs` router:

- `PATCH /v1/fs/crm-metadata` — write or clear the three metadata fields on a node owned by the caller.
- `GET /v1/fs/crm-search` — return the caller's file nodes that match a given `linked_record_type` + `linked_record_id` pair, with full `LastEvaluatedKey` pagination.

Both endpoints are gated by a new `crm_document_library_enabled` flag (default `False`). With the flag off the platform is byte-for-byte identical to today.

## 2. Context & Current State

### File manager storage layer

The file manager persists every file and folder as a single-table DynamoDB item in the table named by `S.filemgr_table_name` (`app/core/settings.py:850`, read from env `FILEMGR_TABLE`, default `""`). The `_table()` helper at `app/services/filemanager.py:104-107` acquires a live boto3 `Table` handle (raising HTTP 500 if the setting is empty). Key layout:

- `PK = USER#<owner_sub>` (via `pk_user`, `app/services/filemanager.py:438-439`)
- `SK = NODE#<normalised_path>` (via `sk_node`, `app/services/filemanager.py:442-443`)
- Helper `node_key(user, path)` returns `{"PK": ..., "SK": ...}` (`app/services/filemanager.py:446-447`)

The table is declared in `scripts/local-ddb-init.py:327-335` with two existing GSIs: `GSI1` (PK=`GSI1PK`, SK=`GSI1SK`) and `GSI2` (PK=`GSI2PK`, SK=`GSI2SK`). Neither GSI uses a numeric sort key, so no `attr_types` entry is needed for the new CRM attributes — the new fields are written only to the item body, not into any GSI projection key.

### File node item shape

When a file is uploaded, `upload_file` (`app/services/filemanager.py:2110-2188`) writes a node item containing at minimum: `PK`, `SK`, `type`, `path`, `name`, `name_lc`, `parent`, `created_at`, `updated_at`, `upload_at`, `upload_by`, `size`, `content_type`, `s3_bucket`, `s3_key`, `etag`, `is_encrypted`, `enc_metadata`, `GSI1PK`, `GSI1SK`, `GSI2PK`, `GSI2SK`. There is no `crm_category`, `crm_description`, `linked_record_type`, or `linked_record_id` field today.

### GET /info response

The `file_info` endpoint at `app/routers/filemanager.py:1107-1148` returns a projection that explicitly enumerates fields (`path`, `type`, `name`, `parent`, `created_at`, `updated_at`, `upload_at`, `upload_by`, `last_download_at`, `last_download_by`, `size`, `duration_seconds`, `thumbnail`, `content_type`, `shared`, plus `encryption_info` and `preview_info` spreads). Because the CRM fields are not in this projection they remain invisible to existing consumers — satisfying the "additive only" acceptance criterion.

### Auth pattern in this router

`app/routers/filemanager.py:165` registers the router with prefix `/v1/fs`. Per-endpoint auth resolves the caller's `user_sub` through `_current_user` (defined at `app/routers/filemanager.py:249-255`), which calls `require_ui_session` from `app/services/sessions.py:330` and falls back to `get_authenticated_user` from `app/auth/deps.py:199`. The dependency returns a plain `str` (the `user_sub`), unlike admin routes that receive the full session context dict.

### Existing update_item pattern

The service already updates node items in place using `tbl.update_item(Key=node_key(owner, path), UpdateExpression=..., ExpressionAttributeValues=...)` — for example the media preview writer at `app/services/filemanager.py:1573-1586` and the soft-delete writer at `app/services/filemanager.py:1780-1787`. This ticket follows the identical pattern.

### Existing scan + FilterExpression pattern

`app/services/filemanager.py:4283-4287` shows the canonical paginated `scan` with `FilterExpression=Attr(...).begins_with(...) & Attr(...).exists()` and `LastEvaluatedKey` cursor loop. The crm-search endpoint follows this pattern. The CLAUDE.md "DDB FilterExpression doesn't reduce page size" gotcha applies: the scan loop must always follow `LastEvaluatedKey` until exhausted and collect up to the requested limit.

### Audit infrastructure

`app/services/alerts.py:644` defines `audit_event(event: str, user_sub: str, request=None, **fields)`. The file manager router already calls `audit_event(...)` for folder creation (`app/routers/filemanager.py:1802`). The new PATCH endpoint must also call `audit_event` to maintain the audit trail.

### Feature flag convention

`app/core/settings.py:850` shows the file-manager section. The default-false flag convention mirrors `legal_export_enabled` and `newsfeed_recsys_enabled`: `os.environ.get("CRM_DOCUMENT_LIBRARY_ENABLED", "0") == "1"`. See EVT-001 spec for the full pattern.

## 3. Data Model

### No new DynamoDB table

All three metadata attributes are stored as additional attributes on the existing `NODE#<path>` item in the `file_manager` table. No new table, GSI, or `attr_types` declaration is required in `scripts/local-ddb-init.py`.

### New attributes written to the existing item

| Attribute | DynamoDB type | Nullable | Constraints |
|---|---|---|---|
| `crm_category` | S | yes | max 200 chars; removed from item when set to `None` via `REMOVE` expression |
| `crm_description` | S | yes | max 2 000 chars; removed from item when set to `None` |
| `linked_record_type` | S | yes | when set, must be one of `{"contact","ticket","account","party"}`; removed when `None` |
| `linked_record_id` | S | yes | 1–200 chars; required when `linked_record_type` is set; removed when `None` |
| `crm_metadata_updated_at` | S | no (written on every PATCH) | ISO-8601 UTC timestamp (from `now_iso()`) |

`linked_record_type` and `linked_record_id` are treated as an atomic pair: both must be supplied together or both must be absent. Supplying one without the other is a 400.

### Key layout (unchanged)

```
PK  = USER#<owner_sub>      (existing)
SK  = NODE#<normalised_path> (existing)
```

No new GSI is introduced for the crm-search query path. The search is implemented as a paginated `scan` with `FilterExpression`, scoped to the caller's `PK`. This is acceptable for the document library use case: a user's node count is bounded (quotas enforced by `_enforce_upload_and_storage_quotas`), and the search is user-scoped so it never performs a global full-table scan. An administrative cross-user search is out of scope for this ticket.

## 4. API / Service Design

### 4.1 Service additions — `app/services/filemanager.py`

#### `_LINKED_RECORD_TYPES`

A module-level frozenset constant:

```python
_LINKED_RECORD_TYPES: frozenset[str] = frozenset({"contact", "ticket", "account", "party"})
```

Validated in `update_crm_metadata` before any DDB call.

#### `update_crm_metadata`

```python
def update_crm_metadata(
    owner: str,
    path: str,
    *,
    crm_category: str | None,
    crm_description: str | None,
    linked_record_type: str | None,
    linked_record_id: str | None,
) -> dict[str, Any]:
```

Steps:

1. Normalise `path` via `norm_path(path, is_folder=False)`.
2. Assert the node exists and is not deleted via `get_node(owner, path)` (raises HTTP 404 if absent or soft-deleted, `app/services/filemanager.py:450-457`).
3. Validate `crm_category` length ≤ 200; raise HTTP 400 if exceeded.
4. Validate `crm_description` length ≤ 2 000; raise HTTP 400 if exceeded.
5. Validate the `linked_record_type` / `linked_record_id` atomic pair:
   - If `linked_record_type` is set and not in `_LINKED_RECORD_TYPES`, raise HTTP 400 `{"code": "invalid_linked_record_type"}`.
   - If exactly one of the pair is set (and the other is `None`), raise HTTP 400 `{"code": "linked_record_pair_required"}`.
6. Build a DynamoDB `update_item` expression:
   - Fields with non-`None` values are written via `SET` clause.
   - Fields explicitly passed as `None` are removed via `REMOVE` clause (so the attribute is fully absent from the item rather than stored as a DDB NULL).
   - `crm_metadata_updated_at` is always set to `now_iso()`.
7. Call `_table().update_item(Key=node_key(owner, path), UpdateExpression=..., ExpressionAttributeValues=..., ExpressionAttributeNames=...)`.
8. Return the refreshed node dict from `get_node(owner, path)`.

The `SET`/`REMOVE` split must be built dynamically because all fields are optional. Example construction:

```python
set_parts, remove_parts, eav, ean = [], [], {":ts": now_iso()}, {}
set_parts.append("crm_metadata_updated_at=:ts")
for attr, val in [
    ("crm_category", crm_category),
    ("crm_description", crm_description),
    ("linked_record_type", linked_record_type),
    ("linked_record_id", linked_record_id),
]:
    if val is not None:
        placeholder = f":{attr}"
        eav[placeholder] = val
        set_parts.append(f"{attr}={placeholder}")
    else:
        remove_parts.append(attr)
update_expr = "SET " + ", ".join(set_parts)
if remove_parts:
    update_expr += " REMOVE " + ", ".join(remove_parts)
_table().update_item(Key=node_key(owner, path), UpdateExpression=update_expr, ExpressionAttributeValues=eav)
```

#### `search_by_linked_record`

```python
def search_by_linked_record(
    owner: str,
    linked_record_type: str,
    linked_record_id: str,
    *,
    limit: int = 50,
    cursor: Optional[dict[str, Any]] = None,
) -> tuple[list[dict[str, Any]], Optional[dict[str, Any]]]:
```

Steps:

1. Validate `linked_record_type in _LINKED_RECORD_TYPES`; raise HTTP 400 if not.
2. Cap `limit = max(1, min(limit, 200))`.
3. Build a `FilterExpression`:
   ```python
   Attr("PK").eq(pk_user(owner))
   & Attr("SK").begins_with("NODE#")
   & Attr("linked_record_type").eq(linked_record_type)
   & Attr("linked_record_id").eq(linked_record_id)
   ```
4. Loop via `LastEvaluatedKey` following the canonical pattern in the service (`app/services/filemanager.py:4284-4299`), collecting items until `len(results) >= limit` or no more pages remain.
5. Strip internal DynamoDB keys (`PK`, `SK`, `GSI1PK`, `GSI1SK`, `GSI2PK`, `GSI2SK`) from each result item before returning.
6. Return `(results[:limit], last_evaluated_key)` where `last_evaluated_key` is the raw DDB key dict for the next page, or `None` if exhausted.

```python
        crm_description=node.get("crm_description"),
        linked_record_type=node.get("linked_record_type"),
```

#### GET /v1/fs/crm-search

```python
@router.get("/crm-search")
def crm_search_endpoint(
    linked_record_type: str = Query(...),
    linked_record_id: str = Query(...),
    limit: int = Query(50, ge=1, le=200),
    cursor: Optional[str] = Query(default=None),
    user: str = Depends(_current_user),
) -> CrmSearchOut:
    _require_crm_document_library_enabled()
    cursor_payload = _decode_cursor(cursor)
    items, next_key = search_by_linked_record(
        user,
        linked_record_type,
        linked_record_id,
        limit=limit,
        cursor=cursor_payload,
    )
    next_cursor = _encode_cursor(next_key) if next_key else None
    return CrmSearchOut(
        items=[
            CrmMetadataOut(
                path=it["path"],
                crm_category=it.get("crm_category"),
                crm_description=it.get("crm_description"),
                linked_record_type=it.get("linked_record_type"),
                linked_record_id=it.get("linked_record_id"),
                crm_metadata_updated_at=it.get("crm_metadata_updated_at"),
            )
            for it in items
        ],
        cursor=next_cursor,
        count=len(items),
    )
```

## 5. Detailed Behavior & Edge Cases

### Partial updates and null semantics

`CrmMetadataIn` passes all four fields as keyword arguments to `update_crm_metadata`. Any field the client omits from the JSON body defaults to Pydantic `None`. The service distinguishes "omit from body" from "explicitly null": both map to Python `None` and both cause the attribute to be REMOVEd from the DynamoDB item. This is intentional — the PATCH semantics for this endpoint are "write exactly what you send; omit means clear". Clients that want to update only `crm_description` without touching the record link must re-send the full desired state of all four fields.

This avoids an upsert-merge ambiguity and keeps the `UpdateExpression` logic simple and testable.

### Linked record pair atomicity

Validation in `update_crm_metadata` (step 5) fires before any DDB write. If `linked_record_type="contact"` is sent with `linked_record_id=None`, the service raises HTTP 400 with `{"code": "linked_record_pair_required"}` before touching the table. The existing node is unchanged.

### SFTP-mounted paths

`_enforce_sftp_mount_flags_for_path(path, operation="write")` is called by the PATCH endpoint. If the path falls under an SFTP mount, it will raise an appropriate error (`app/routers/filemanager.py:426-436`). The GET crm-search endpoint does not call this guard because it is read-only and the search is filtered to the caller's local nodes (SFTP-mounted items live in a separate backend and are not stored as `NODE#` items in the `file_manager` table, so they can never appear in a `FilterExpression` scan of that table).

### Node not found / soft-deleted

`get_node` at `app/services/filemanager.py:450-457` raises HTTP 404 for a missing or soft-deleted node. The PATCH endpoint propagates this directly. A client that attempts to set CRM metadata on a non-existent or deleted file receives 404.

### Folder nodes

The `norm_path(path, is_folder=False)` call in `update_crm_metadata` normalises the path treating it as a file (no trailing slash). If a caller passes a folder path with a trailing slash, `norm_path` will strip it and the resulting path will not match the folder's `NODE#/folder/` SK. This means CRM metadata can only be written to file nodes, not folders. This is consistent with the SuiteCRM document library model (documents, not directories, carry metadata).

If the design is later extended to support folder metadata, `is_folder` would need to change to `None` and additional validation added; that is out of scope here.

### crm-search scan performance

DynamoDB evaluates `FilterExpression` after reading each page (up to 1 MB) from the `file_manager` table. For a user with many file nodes, multiple scan rounds may be needed to collect `limit` matching items. The loop cap of 30 scan rounds (matching the `admin_search_metadata` pattern at `app/services/filemanager.py:128-130`) prevents runaway scan loops. If the cap is hit before `limit` results are found, the partial list is returned with a `cursor` pointing to `LastEvaluatedKey` so the client can page.

### Existing GET /info not modified

`file_info` at `app/routers/filemanager.py:1130-1148` returns an explicit projection. The four new attributes are not added to that projection by this ticket, satisfying the acceptance criterion that "fields do not appear in existing GET /files list response". The `CrmMetadataOut` type is returned only by the two new endpoints.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

Both service functions call only:
- `_table()` → `ddb.Table(S.filemgr_table_name)` — same in dev (DynamoDB Local) and prod (real DynamoDB).
- `get_node` / `update_item` / `scan` — standard boto3 table operations; no `dev_mode` branch exists and none is introduced.
- `now_iso()` — deterministic UTC ISO string, no dev/prod divergence.

No `if S.dev_mode` branches are introduced in this ticket. The feature is 100% DynamoDB-backed in both environments.

### Idempotency

`update_crm_metadata` uses `update_item` (not `put_item`), so calling it twice with the same payload produces the same final item state (second write is a no-op except for `crm_metadata_updated_at` advancing). The endpoint is safely retryable by clients.

`search_by_linked_record` is a read-only scan with no side effects. It is naturally idempotent.

### Ownership enforcement

`update_crm_metadata` resolves the node via `get_node(owner, path)` where `owner = user_sub` from the authenticated session. A user can only write CRM metadata to nodes they own. There is no cross-user write path.

`search_by_linked_record` scopes the `FilterExpression` to `Attr("PK").eq(pk_user(owner))` so the scan never reads another user's items.

### Input sanitisation

- `crm_category` max length 200 enforced by Pydantic `Field(max_length=200)` before the service is called.
- `crm_description` max length 2 000 enforced by `Field(max_length=2000)`.
- `linked_record_type` is validated against the closed enum `_LINKED_RECORD_TYPES` in the service; an unknown value is rejected with 400.
- `linked_record_id` max length 200 enforced by `Field(max_length=200)`.
- DynamoDB attribute names are hardcoded strings, not user input; no injection surface exists.

### Audit trail

Every successful PATCH call emits `audit_event("filemgr_crm_metadata_updated", user_sub, request, ...)` to `T.alerts`. The GET search endpoint does not emit an audit event (read-only, low-value for audit purposes, consistent with the existing `file_info` and search endpoints which also do not audit).

## 8. Backward Compatibility & Migration

### Zero migration required

The three new attributes are additive to items that already exist in the `file_manager` table. Pre-existing nodes simply lack these keys; `item.get("crm_category")` returns `None`, which the `CrmMetadataOut` model handles correctly as `Optional[str]`.

No `UpdateTable` or backfill script is needed.

### No schema change to `scripts/local-ddb-init.py`

The `file_manager` table `TableDef` at `scripts/local-ddb-init.py:327-335` is unchanged. The two new CRM attributes are not GSI projection keys, so no `attr_types` entry is needed.

### `just restart` safety

Because no new table is created and no existing table schema changes, `just restart` continues to work without modification.

### Downstream tickets

EVT-012 (document revision history) and EVT-013 (document expiration) both cite this ticket as a dependency. They depend on the `file_manager` item structure established here and on the flag-gating pattern, but neither depends on any specific new DynamoDB attribute introduced by EVT-011. The CRM metadata attributes written by this ticket will be preserved across the revision snapshots that EVT-012 introduces, because EVT-012 copies the full existing item when archiving a revision.

## 9. Test Plan

### 9.1 Hermetic pytest — `tests/test_evt_011_crm_document_metadata.py`

The test file uses the canonical offline pattern: moto in-memory DynamoDB, frozen `T` and `S` patched via `object.__setattr__`, no real AWS or network calls. The `filemgr` table is created inline in `setUp`; the exact frozen `_table()` function handle in `app.services.filemanager` is monkey-patched to return the moto-backed table.

Because `_table()` dynamically calls `ddb.Table(S.filemgr_table_name)` rather than reading a `T.*` handle, the test must either:

(a) Override `S.filemgr_table_name` via `object.__setattr__(S, "filemgr_table_name", "test_file_manager")` so that `_table()` resolves to the moto table by name, OR

(b) Patch `app.services.filemanager._table` directly with a lambda returning the moto table.

Option (a) is preferred — it exercises the real `_table()` code path and requires no mock.

```python
@mock_aws
```

## 10. Open Questions / Assumptions

1. **`linked_record_id` format**: This ticket treats `linked_record_id` as an opaque string (max 200 chars). It does not validate that the referenced record actually exists in `T.contacts`, `T.tickets`, or the not-yet-built `party` table. Resolution of dangling links is out of scope; the field is a best-effort association. A follow-on ticket (or EVT-012/EVT-013) can add existence validation once the PTY tables are live.

2. **`party` record type**: The `_LINKED_RECORD_TYPES` set includes `"party"` as a forward-compatible value in anticipation of PTY-001. Until PTY-001 ships, `linked_record_id` values with `linked_record_type="party"` are accepted but unvalidated. This avoids a data migration later.

3. **Folder node support**: The current design explicitly targets file nodes only (using `norm_path(path, is_folder=False)`). If document-library folders (e.g. a "Contracts" folder linked to an account) are needed, that is a separate ticket.

4. **Category taxonomy**: `crm_category` is a free-text string, not a controlled vocabulary. A predefined category list (admin-managed) would be a UI enhancement outside this ticket's scope.

5. **Search scope**: The `GET /v1/fs/crm-search` endpoint is scoped to the calling user's nodes. An admin/root cross-user search (e.g. "all files linked to contact X across all users") is not implemented here. That would require either a new GSI or an admin-only scan, and is deferred.

6. **`_encode_cursor` / `_decode_cursor`**: The router already defines these helpers at `app/routers/filemanager.py:232-247` using `app/core/cursor.encode_cursor` / `decode_cursor`. The `GET /v1/fs/crm-search` endpoint reuses them directly.

## 11. Dependencies

### Hard dependencies

- **EVT-001** — supplies the flag-gating pattern (`_require_crm_events_enabled()` convention) and the default-false flag convention used here. Without EVT-001's established pattern in the codebase, this ticket implements the same pattern independently for `crm_document_library_enabled`.

Note: EVT-001 is technically a dependency only for the pattern. Since EVT-011 introduces its own flag and its own guard helper (`_require_crm_document_library_enabled`), it can ship independently of EVT-001 if EVT-001 has not yet landed. The two flags are completely independent settings.

### Soft / forward-compatible dependencies

- **PTY-001** (`PARTY_CRM_TICKETS.md`) — delivers the `party` table and `contact`/`account` record types as structured CRM data. EVT-011 accepts `linked_record_type="party"` and `"contact"` and `"account"` as valid values now, with no existence validation, so EVT-011 can ship before PTY-001 without any breaking change.

### Downstream dependents

- **EVT-012** (document revision history) — cites EVT-011 as a dependency because it relies on the `file_manager` node shape established here. The revision snapshot written by EVT-012 on overwrite copies the entire existing item dict, which will include the four CRM attributes if they have been set.
- **EVT-013** (document expiration) — similarly cites EVT-011 for the file node model. The `expires_at` field added by EVT-013 is orthogonal to the CRM attributes added here; both can coexist on the same node item.
