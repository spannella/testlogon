# EML-001 — HTML email body in system notification templates

**Type:** Feature · **Priority:** P0 · **Estimate:** 1 day  
**Status:** Design spec (ready for implementation)

---

## 1. Summary & Goal

`send_alert_email` at `app/services/alerts.py:459` currently constructs an SES `Message.Body` that contains only a `Text` key, silently discarding the HTML string that `render_alert_email_template` (`app/services/alert_email_templates.py`) already returns.  The goal is a minimal, backwards-compatible extension that threads an optional `html_body` parameter from each call site through to the SES `send_email` call so that email clients capable of rendering HTML receive the styled notification rather than the raw plain-text dump.

This is a self-contained one-file change to `app/services/alerts.py`, with three targeted call-site updates in the same file.  No new DynamoDB tables, no new routes, no new feature flags beyond those already gating the HTML template path (`NOTIFICATION_EMAIL_TEMPLATES_ENABLED`).  The change is purely additive: callers that do not pass `html_body` continue to receive text-only SES messages, byte-for-byte identical to today.

## 4. API / Service Design

### 4.1 `send_alert_email` — new signature

```python
def send_alert_email(
    to_emails: List[str],
    subject: str,
    body_text: str,
    *,
    html_body: str | None = None,
) -> None:
```

`html_body` is keyword-only (after `*`) so no positional call site can accidentally supply it as the fourth argument.  This is a strict backwards-compatible extension.

### 4.2 SES `Message.Body` construction

```python
body_dict: dict = {"Text": {"Data": body_text[:8000]}}
if html_body:
    body_dict["Html"] = {"Data": html_body[:50000]}

ses.send_email(
    Source=S.alerts_from_email,
    Destination={"ToAddresses": to_emails},
    Message={
        "Subject": {"Data": subject[:120]},
        "Body": body_dict,
    },
)
```

Truncation limits:
- `body_text`: `[:8000]` — unchanged from current behaviour.
- `html_body`: `[:50000]` — well within SES's 10 MB message limit; prevents accidental oversized template strings from failing the API call.

The `Html` key is added **only when `html_body` is truthy** (non-None, non-empty string).  An explicit `html_body=""` is treated as absent, identical to `html_body=None`.

### 4.3 Dev-mode log extension

```python
if S.dev_mode:
    ts = datetime.now(timezone.utc).strftime("%Y-%m-%dT%H:%M:%SZ")
    for addr in to_emails:
        html_note = f"  HTML: {len(html_body)} chars\n" if html_body else ""
        entry = (
            f"[{ts}] ALERT_EMAIL TO={addr}\n"
            f"  Subject: {subject}\n"
            f"  Body: {body_text}\n"
            f"{html_note}\n"
        )
        _write_dev_log(S.dev_email_log, entry)
    return
```

The `HTML: N chars` line is appended **only** when `html_body` is truthy, so existing log-parsing scripts that do not expect it will not break (the line is inserted before the blank-line separator, not replacing existing lines).

### 4.4 `record_email_sent` call (delivery tracking fix)

After a successful `ses.send_email(...)`, capture the `MessageId` from the response and call `record_email_sent`:

```python
response = ses.send_email(...)
message_id = response.get("MessageId", "")
record_email_sent(to_emails, subject, message_id)
# Also stamp has_html on each row:
if html_body and message_id:
    _stamp_html_flag(to_emails, subject, message_id)
```

`_stamp_html_flag` is a small private helper (5 lines) that calls `T.email_delivery.update_item` with `SET has_html = :v` for each `EMAIL#{addr}` / `SENT#{ts}#{message_id}` row.  It is wrapped in a `try/except` and failure does not abort delivery.

Import `record_email_sent` at the module top of `alerts.py` alongside the existing `record_email_failure` import (`app/services/alerts.py:22`).

### 4.5 Updated call sites inside `alerts.py`

| Current line | Branch | New call |
|---|---|---|
| 766 | ticket template | `send_alert_email(emails, subj, body)` → unchanged (no `html_body`) |
| 778 | HTML template (flag on) | `send_alert_email(emails, subj, body, html_body=body)` |
| 804 | plain-text fallback | `send_alert_email(emails, subj, "\n".join(lines))` → unchanged |

At line 778 the variable `body` already holds the `<!DOCTYPE html>...` string returned by `render_alert_email_template`.  Passing it as both `body_text` and `html_body` is intentional: SES multipart clients that prefer text will receive the raw HTML as text (degraded but legible), and clients that prefer HTML will receive the properly rendered message.

A cleaner approach would be to extract a plain-text version from the rendered HTML; however this ticket is explicitly scoped to the minimal fix described in the source ticket (`CRM_EMAIL_TICKETS.md:28`).  A follow-up improvement (strip HTML tags for the text part) is logged in §10.

### 4.6 No model changes

`send_alert_email` is a service function, not an API endpoint.  No Pydantic model changes are needed in `app/models.py`.

## 5. Detailed Behavior & Edge Cases

**E1 — `html_body=None` (default):** Behaviour is byte-for-byte identical to the current implementation.  SES receives only `Body.Text`.  No regression for any existing caller.

**E2 — `html_body=""` (empty string):** Treated as absent (`if html_body:` is falsy for empty string).  SES receives only `Body.Text`.

**E3 — `html_body` longer than 50 000 chars:** Silently truncated with `[:50000]`.  No exception raised; `body_text` is truncated separately with the existing `[:8000]`.  Both truncations happen before the SES call so the dict construction cannot raise.

**E4 — SES `send_email` raises:** The existing `except Exception as exc` block at `app/services/alerts.py:479` continues to handle this.  `record_email_failure` is called.  `record_email_sent` is only called on the success path (after the response object exists), so partial-failure double-recording cannot occur.

**E5 — `record_email_sent` or `_stamp_html_flag` raises:** Each is wrapped in its own `try/except`.  Delivery-tracking failure must never interrupt the send pipeline.  The function returns normally.

**E6 — dev mode:** The function returns after writing to the dev log.  SES is never called.  `record_email_sent` is not called (dev has no SES `MessageId`).  The `html_body` length note appears in the log only if `html_body` is truthy, so the dev log remains valid for log-parsing tests in the existing test suite.

**E7 — `S.alerts_email_enabled` is false or `S.alerts_from_email` is empty:** The function returns early at `app/services/alerts.py:469` before constructing `body_dict`.  No change to this path.

**E8 — HTML template flag off (`NOTIFICATION_EMAIL_TEMPLATES_ENABLED=0`):** Line 770 gates the `html_template` branch.  When the flag is off, `html_template` remains `None`, and execution falls through to the plain-text fallback at line 804.  `html_body` is never passed to `send_alert_email`.  Full text-only behaviour preserved.

**E9 — Concurrent sends:** `send_alert_email` is stateless and synchronous.  No shared mutable state.  Thread-safe.

**E10 — Recipient list with suppressed addresses:** The existing suppression list lives in `email_delivery` and is checked by the admin dashboard but not currently enforced inside `send_alert_email` at send time.  This is a pre-existing gap outside EML-001 scope.

**E11 — `render_ticket_email_template` returns a plain-text tuple:** Line 764–766 assigns `subj, body = ticket_template` and calls `send_alert_email(emails, subj, body)` without `html_body`.  This branch is unaffected.

## 6. Feature Flag & Config

EML-001 does **not** introduce a new feature flag.

The HTML body is threaded to SES only when `render_alert_email_template` returns a non-None result, which is already gated by `S.notification_email_templates_enabled` (`app/core/settings.py:2044`, env `NOTIFICATION_EMAIL_TEMPLATES_ENABLED`, default `"1"` → on).

With `NOTIFICATION_EMAIL_TEMPLATES_ENABLED=0`:
- Line 770 short-circuits to the plain-text fallback.
- `html_body` is never supplied to `send_alert_email`.
- SES `Message.Body` contains only `Text`.
- Platform behaviour is byte-for-byte identical to the pre-EML-001 state.

No `.env.local.example` change is needed; the flag already exists.

If a future operator wishes to force HTML-off even while the template flag is on, that concern is out of scope for this ticket and should be addressed as a separate `EMAIL_HTML_BODY_ENABLED` flag in EML-002 or a follow-up.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity:** The dev-mode branch returns early before SES construction.  The new `html_body` parameter and truncation logic are evaluated identically in both environments.  In dev mode the log note records whether HTML was present; in prod the SES payload carries the HTML key.  There is no `if S.dev_mode` branch that skips logic — the early return is the existing pre-EML-001 pattern at line 462.

**Idempotency:** `send_alert_email` is fire-and-forget.  Retries are handled by the caller (the email fanout block at line 758 does not retry).  `record_email_sent` uses a timestamped SK (`SENT#{ts}#{message_id}`) so repeated calls with the same `message_id` produce duplicate rows rather than a conditional-put conflict — this is the same behaviour as before EML-001 and is a pre-existing design decision.

**HTML injection / XSS:** The HTML body originates exclusively from `render_alert_email_template`, which constructs templates from Python f-strings using trusted server-side data (alert event type, amount_cents, display names from profile).  No user-supplied HTML is accepted as input to `send_alert_email`.  Caller-supplied display names are interpolated without escaping; this is a pre-existing design decision shared with the plain-text path.  A full XSS-safe template engine (Jinja2 autoescaping) is a follow-up concern outside EML-001 scope.

**Character encoding:** SES `Body.Html.Data` is UTF-8 by default.  The `_wrap_html` wrapper at `alert_email_templates.py:18` already includes `<meta charset="utf-8">`.

**Email header injection:** `subject[:120]` truncation is unchanged.  No new header field is introduced.

**SES send limit:** `html_body[:50000]` plus `body_text[:8000]` plus headers stays well within SES's 10 MB raw message limit and 64 KB body limit for the API path.

## 8. Backward Compatibility & Migration

**Zero-downtime deployment:** The change is additive.  Old callers passing three positional arguments continue to work.  No caller passes a fourth positional argument; `html_body` is keyword-only.

**No DynamoDB migration:** The `has_html` attribute on `email_delivery` rows is optional.  Existing rows without it are valid.  The admin email dashboard (`app/routers/admin_email.py`) does not currently surface `has_html`; adding it to the delivery list response is a UI-only concern deferred to EML-002.

**No frontend change:** There is no frontend component for outbound SES messages.  The change is entirely backend.

**Rollback:** Setting `NOTIFICATION_EMAIL_TEMPLATES_ENABLED=0` immediately disables all HTML body generation without a code rollback, reverting to the pre-EML-001 text-only path.

**Existing tests:** Existing pytest tests that mock `boto3.client("ses")` and check `Message.Body` will continue to pass for calls without `html_body` because the `Html` key is added only when `html_body` is truthy.  Test files that call `send_alert_email` without `html_body` are unaffected.

## 10. Open Questions / Assumptions

**OQ-1 — Plain-text part of HTML templates.**  Currently at line 778, `body_text` receives the same raw `<!DOCTYPE html>...` string as `html_body`.  This means text-only email clients see unrendered HTML markup.  The ticket source does not require stripping; this spec preserves the current behaviour.  A follow-up should strip HTML tags for the `body_text` argument (using stdlib `html.parser` — no new dependency).

**OQ-2 — Ticket template HTML upgrade.**  `render_ticket_email_template` (`alerts.py:235`) currently returns a plain-text tuple.  Giving it an HTML variant is outside EML-001 scope.  A follow-up can mirror the `_wrap_html` pattern from `alert_email_templates.py`.

**OQ-3 — External caller HTML bodies.**  Cart reminders (`cart_reminders.py:374`), invoice emails (`invoices.py:473`), signature reminders (`signature_packet_reminders.py:162`), and others pass plain-text `body_text`.  Passing `html_body` from those callers is outside EML-001 scope and will be addressed in per-feature follow-up tickets (e.g., EML-009 for campaign templates).

**OQ-4 — `record_email_sent` currently absent.**  The current `send_alert_email` does not call `record_email_sent` even though the infrastructure exists.  This spec adds the call.  The assumption is that adding delivery tracking is unambiguously correct and within scope for a P0 fix; if stakeholders disagree, the `record_email_sent` addition can be deferred to EML-002.

**OQ-5 — SES `charset` field.**  SES `send_email` accepts an optional `Charset` field in `Body.Html`.  The default is `UTF-8`, which matches `_wrap_html`'s `<meta charset="utf-8">`.  No explicit `Charset` field is needed.

**Assumption A1:** All callers of `send_alert_email` outside `alerts.py` use positional arguments for `(to_emails, subject, body_text)` only and do not pass a fourth argument.  Verified by grep — confirmed correct (see §2.4).

**Assumption A2:** `render_alert_email_template` returns a complete `<!DOCTYPE html>` document, not a fragment, for all event types it handles.  Confirmed by reading `_wrap_html` at `alert_email_templates.py:16–39`.
