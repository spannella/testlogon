# RPT-004 — Scheduled report email delivery

**Ticket area**: Reports & Dashboards (AOR)
**Type**: Feature  **Priority**: P1  **Estimate**: 2d
**Depends on**: RPT-001 (tables + flag), RPT-002 (run_report engine)

---

## 1. Summary & Goal

RPT-004 adds recurring, cron-cadenced email delivery of custom reports to the
platform's CRM report system. A user who owns a report (created via RPT-002) can
attach one or more named schedules to it, each specifying a cadence
(daily/weekly/monthly), a list of recipient email addresses, and a serialisation
format (csv or json). A background loop polls for due schedules, executes the
underlying report, serialises the result, and dispatches it by email. Between
runs the schedule is dormant; its `GSI1SK = next_run_at` numeric key advances by
one cadence offset after each successful dispatch.

This mirrors the existing scheduled audit-export capability
(`app/services/audit_export_schedule.py`) precisely, reusing the same
`CADENCE_OFFSETS` table, the same `GSI1PK`/`GSI1SK` active-index pattern, the
same `send_alert_email` email dispatch path (`app/services/alerts.py:459`), and
the same asyncio background-loop startup registration pattern already present in
`app/main.py` for the audit-export scheduler. No existing files are modified
beyond the additive changes described here unless noted explicitly.

## 2. Context & Current State

### 2.1 Feature flag and report tables (RPT-001)

RPT-001 adds `S.crm_reports_enabled` (env `CRM_REPORTS_ENABLED`, default `"0"`)
to `app/core/settings.py`, following the `bool_env` pattern at
`app/core/settings.py:81` (`alerts_enabled`, same expression). It also creates
the `crm_reports` DynamoDB table in `scripts/local-ddb-init.py` and exposes the
handle as `T.crm_reports` in `app/core/tables.py`. RPT-004 does **not** create a
new table; schedules are stored as additional rows on the same `crm_reports`
table (single-table design).

### 2.2 Report execution engine (RPT-002)

RPT-002 provides `crm_reports.run_report(report_id, owner_sub) -> ReportRunOut`.
`ReportRunOut` contains: `report_id`, `run_id`, `run_at`, `status`, `row_count`,
`columns: List[str]`, `rows: List[List[Any]]` (capped at 2000). RPT-004's
background runner calls this function directly.

### 2.3 Audit export scheduler — the reference implementation

`app/services/audit_export_schedule.py` is the canonical precedent. Key details:

- `CADENCE_OFFSETS` (`audit_export_schedule.py:40`): `{"daily":86400,
  "weekly":604800, "monthly":2592000}`. RPT-004 copies this dict verbatim.
- Schedule records use `pk=SCHEDULE#{schedule_id}` / `sk=META` co-located in the
  same DynamoDB table as the primary entity records.
- Active schedules carry `GSI1PK="SCHEDULES#ACTIVE"`, `GSI1SK=next_run_at`
  (numeric). Disabling a schedule switches `GSI1PK` to `"SCHEDULES#DISABLED"` so
  the runner query never returns it (`audit_export_schedule.py:170-171`).
- `get_due_schedules(now)` queries `IndexName=SCHEDULE_INDEX_NAME` with
  `Key("GSI1PK").eq(SCHEDULES_ACTIVE_PK) & Key("GSI1SK").lte(ts)`, returning all
  due items in ascending `next_run_at` order (`audit_export_schedule.py:193-202`).
- `_advance_schedule` increments `GSI1SK` + `next_run_at` and records
  `last_run_at` + `last_export_id` atomically (`audit_export_schedule.py:205-219`).
- `_notify_recipients` calls `send_alert_email` inside a `try/except`; failures
  are logged but never re-raised (`audit_export_schedule.py:222-253`).
- The background loop is `run_audit_export_scheduler_loop` / started by
  `start_audit_export_scheduler_task` (`audit_export_schedule.py:295-309`),
  registered as a FastAPI startup hook in `app/main.py`.
- `GSI1SK` being numeric requires `attr_types={"GSI1SK":"N"}` in the TableDef
  for `AuditExports` (`scripts/local-ddb-init.py:1502`) — omitting causes a
  DynamoDB `ValidationException` at query time (CLAUDE.md gotcha).

### 2.4 Email dispatch

`app/services/alerts.send_alert_email(to_emails, subject, body_text)`
(`alerts.py:459`) is the single platform email path. In dev mode
(`S.dev_mode=True`) it writes to `S.dev_email_log` (a filesystem log). In prod it
calls `boto3.client("ses").send_email`. There is no in-line `if dev_mode` branch
in any caller — the branch lives entirely inside `send_alert_email` itself, which
satisfies SECOPS-007.

### 2.5 CSV generation

`app/services/csv_export.generate_csv_rows(source, user_sub, ...)` (`csv_export.py:194`)
is a generator that yields RFC 4180 UTF-8-BOM CSV strings, one row at a time. For
a scheduled delivery the caller must materialise the generator to a single string
(or `io.StringIO`) so it can be included as an email body or attachment. The same
three module sources from RPT-002 (`tickets`, `contacts`, `billing_ledger`,
`orders`, `subscriptions`, `questionnaire_responses`) are available as report data
sources; the CSV serialisation in RPT-004 derives columns and rows directly from
`ReportRunOut.columns` + `ReportRunOut.rows` rather than re-querying DynamoDB, so
it is not constrained to the `VALID_SOURCES` set in `csv_export.py:20`.

### 2.6 Cursor pagination

`app/core/cursor.encode_cursor` / `decode_cursor` (`cursor.py:94`, `cursor.py:103`)
provide HMAC-signed opaque pagination cursors. `list_report_schedules` uses these
for the paginated GET endpoint.

### 2.7 Rate limiting

`app/services/rate_limit._bucket_limit(user_sub, key, max, window)` is the
DDB-backed token-bucket primitive reused at `app/routers/csv_export.py:66`. It is
applied to schedule-create to prevent users from creating an unbounded number of
schedules per minute.

### 2.8 Audit events

`app/services/alerts.audit_event(event, user_sub, request, **fields)`
(`alerts.py:644`) writes structured audit rows to `T.alerts`. RPT-004 emits
`crm_report_schedule.created`, `crm_report_schedule.updated`,
`crm_report_schedule.deleted`, and `crm_report_schedule.dispatched` events.

## 3. Data Model

### 3.1 Table: `crm_reports` (created by RPT-001)

Schedule records live in the same table as report META and RUN rows (single-table
design, identical to the audit-export pattern). The table key schema is:

| Attribute | Type | Role |
|-----------|------|------|
| `report_id` | S | Partition key (table) |
| `sk` | S | Sort key (table) |
| `GSI1PK` | S | GSI partition key |
| `GSI1SK` | N | GSI sort key — **numeric; requires `attr_types={"GSI1SK":"N"}`** |

#### 3.2 GSI addition: `rpt-schedules-due-index`

This GSI must be declared in the `crm_reports` TableDef in
`scripts/local-ddb-init.py`. RPT-001 creates the table with a `owner-reports-index`
GSI (`GSI1PK=OWNER#{owner_sub}` / `GSI1SK=created_at`); RPT-004 adds a **second**
GSI to the same TableDef:

```python
TableDef(
    _resolve_table_name(S.crm_reports_table_name, "crm_reports"),
    "report_id",
    "sk",
    gsi=[
        # Declared by RPT-001
        {
            "index_name": "owner-reports-index",
            "partition_key": "GSI1PK",
            "sort_key": "GSI1SK",
        },
        # Added by RPT-004
        {
            "index_name": "rpt-schedules-due-index",
            "partition_key": "GSI2PK",
            "sort_key": "GSI2SK",
        },
    ],
    attr_types={"GSI1SK": "N", "GSI2SK": "N"},
)
```

The schedule rows use `GSI2PK` / `GSI2SK` to avoid colliding with the
owner-reports index used by report META rows (which also set `GSI1PK`/`GSI1SK`).
This is the cleanest single-table approach: report META rows write `GSI1PK`,
schedule rows write `GSI2PK`.

#### 3.3 Schedule row schema

```
PK  report_id = "SCHEDULE#{schedule_id}"
SK  sk        = "META"

GSI2PK  = "RPT_SCHEDULES#ACTIVE"   (or "RPT_SCHEDULES#DISABLED" when disabled)
GSI2SK  = next_run_at              (int, Unix seconds — numeric N type)

schedule_id:   str   e.g. "rptsched_{uuid8}"
report_id:     str   FK to the owning report's META row PK
owner_sub:     str   user_sub of the schedule creator (must own the report)
cadence:       str   "daily" | "weekly" | "monthly"
recipients:    list  [email strings]
format:        str   "csv" | "json"
enabled:       bool
created_at:    int   Unix seconds
next_run_at:   int   Unix seconds — first run = created_at + CADENCE_OFFSETS[cadence]
last_run_at:   int | None
last_run_id:   str | None   run_id from the last ReportRunOut
```

No new attributes are added to existing report META rows; schedules are
independently queryable rows co-located in the same table.

## 4. API / Service Design

### 4.1 Service: `app/services/crm_report_scheduler.py` (new file)

```python
from app.core.settings import S
from app.core.tables import T
from app.core.time import now_ts
import asyncio, logging, uuid
from typing import Any, Dict, List, Optional

SCHEDULE_INDEX   = "rpt-schedules-due-index"
SCHEDULES_ACTIVE = "RPT_SCHEDULES#ACTIVE"
CADENCE_OFFSETS  = {"daily": 86400, "weekly": 604800, "monthly": 2592000}
VALID_FORMATS    = ("csv", "json")

def _schedule_pk(schedule_id: str) -> str:
    return f"SCHEDULE#{schedule_id}"

def create_report_schedule(
    *,
    owner_sub: str,
    report_id: str,
    cadence: str,
    recipients: List[str],
    format: str,
) -> Dict[str, Any]: ...

def get_report_schedule(
    schedule_id: str,
    owner_sub: str,
) -> Optional[Dict[str, Any]]: ...

def list_report_schedules(
    owner_sub: str,
    report_id: Optional[str] = None,
    cursor: Optional[str] = None,
) -> Dict[str, Any]: ...   # {"schedules": [...], "cursor": str|None}

def update_report_schedule(
    schedule_id: str,
    owner_sub: str,
    *,
    cadence: Optional[str] = None,
    recipients: Optional[List[str]] = None,
    format: Optional[str] = None,
    enabled: Optional[bool] = None,
) -> Dict[str, Any]: ...

def delete_report_schedule(schedule_id: str, owner_sub: str) -> None: ...

def get_due_report_schedules(now: Optional[int] = None) -> List[Dict[str, Any]]: ...

def run_due_report_schedules() -> int: ...

async def run_report_scheduler_loop() -> None: ...

async def start_report_scheduler_task() -> None: ...
```

**`create_report_schedule`**: validates `cadence in CADENCE_OFFSETS`, `format in
VALID_FORMATS`, and that `report_id` is owned by `owner_sub` (calls
`crm_reports.get_report(report_id, owner_sub)` — raises 403 if not owned). Generates
`schedule_id = f"rptsched_{uuid.uuid4().hex[:12]}"`. Computes
`next_run_at = now_ts() + CADENCE_OFFSETS[cadence]`. Writes the schedule row with
`GSI2PK=SCHEDULES_ACTIVE`, `GSI2SK=next_run_at`. Calls
`audit_event("crm_report_schedule.created", owner_sub, ...)`. Returns the item.

**`list_report_schedules`**: queries `T.crm_reports` by `report_id` with SK prefix
`SCHEDULE#` (standard `begins_with` key condition), or scans by `owner_sub`
as a FilterExpression when `report_id` is None. Applies `encode_cursor` /
`decode_cursor` (`cursor.py:94`) for pagination. Returns
`{"schedules": [item, ...], "cursor": next_cursor_or_none}`.

**`update_report_schedule`**: fetches the row; raises 403 if `owner_sub` mismatches.
Builds a partial `UpdateExpression` from provided kwargs (same SET-parts accumulator
pattern as `audit_export_schedule.update_schedule`, `audit_export_schedule.py:128-184`).
When `enabled=False`, sets `GSI2PK="RPT_SCHEDULES#DISABLED"`; when `enabled=True`,
restores `GSI2PK=SCHEDULES_ACTIVE`. When `cadence` changes, recomputes `next_run_at`.
Emits `audit_event("crm_report_schedule.updated", ...)`.

**`delete_report_schedule`**: enforces ownership; calls `T.crm_reports.delete_item`.
Emits `audit_event("crm_report_schedule.deleted", ...)`.

**`get_due_report_schedules`**: mirrors `audit_export_schedule.get_due_schedules`
(`audit_export_schedule.py:192-202`) exactly:

```python
def get_due_report_schedules(now=None):
    ts = now if now is not None else now_ts()
    resp = T.crm_reports.query(
        IndexName=SCHEDULE_INDEX,
        KeyConditionExpression=(
            Key("GSI2PK").eq(SCHEDULES_ACTIVE) & Key("GSI2SK").lte(ts)
        ),
        ScanIndexForward=True,
    )
    return resp.get("Items", [])
```

**`run_due_report_schedules`**: iterates due schedules; for each:
1. Calls `crm_reports.run_report(report_id, owner_sub)` in `asyncio.to_thread`
   (same pattern RPT-002 uses to avoid blocking the event loop).
2. Serialises result to the requested `format`:
   - `csv`: materialises `generate_csv_rows` using the `ReportRunOut.columns` and
     `ReportRunOut.rows` fields (writes header + data rows via `csv.writer` into
     an `io.StringIO`, then `.getvalue()`); calls `_sanitize_csv_field`
     (`csv_export.py:43`) on each cell.
   - `json`: `json.dumps({"columns": ..., "rows": ..., "row_count": ...})`.
3. Calls `send_alert_email(recipients, subject, body_text)` (`alerts.py:459`).
   Subject: `f"Scheduled report: {report_name} ({cadence})"`.
   Body: human-readable header (schedule ID, report ID, cadence, run ID, row count,
   generated at ISO timestamp) followed by the serialised content inline for small
   results (`row_count <= 100`) or a note that the full data exceeds inline size
   for larger ones. This matches the body pattern of `_notify_recipients`
   (`audit_export_schedule.py:228-251`).
4. Calls `_advance_schedule(schedule_id, cadence, run_id)` to bump `next_run_at`.
5. Emits `audit_event("crm_report_schedule.dispatched", owner_sub, ...)`.
6. Any per-schedule exception is caught and logged; the loop continues with the
   next due schedule (mirrors `audit_export_schedule.run_due_schedules:283-289`).
7. Returns count of schedules dispatched.

**`start_report_scheduler_task`**: gated on `S.crm_reports_enabled and
S.crm_reports_scheduler_enabled`. Creates an asyncio task wrapping
`run_report_scheduler_loop`. The loop sleeps
`S.crm_reports_scheduler_poll_interval` seconds between ticks
(mirrors `audit_export_schedule.run_audit_export_scheduler_loop:296-303`).

## 5. Detailed Behavior & Edge Cases

### 5.1 Schedule creation constraints
- A user may attach at most 10 active schedules per report. A `create_report_schedule`
  call that would exceed this limit returns HTTP 422
  (`"Maximum 10 schedules per report"`).
- `recipients` entries are validated as email addresses via `pydantic.EmailStr`.
  Duplicates are de-duplicated by the service before writing.
- The `report_id` path parameter is validated against the report META row; a
  non-existent report returns 404. A report owned by another user returns 403.

### 5.2 First-run timing
- `next_run_at = created_at + CADENCE_OFFSETS[cadence]` — the first dispatch
  occurs at least one full cadence from schedule creation. This matches the audit
  export scheduler behaviour (`audit_export_schedule.py:78`).

### 5.3 Runner dispatch logic
- The `run_due_report_schedules` loop does NOT use a compare-and-swap on `enabled`
  status. Instead, the design relies on `GSI2PK` toggling:
  disabled/deleted schedules no longer appear in the GSI query, so they are never
  selected. This is exactly the audit export approach.
- If `run_report` raises an exception for a specific schedule (e.g. the report was
  deleted between schedule creation and dispatch), the runner logs the error with
  `schedule_id` and continues to the next due item. It does NOT advance
  `next_run_at` for failed dispatches, so the schedule will be retried on the next
  polling tick.
- If `send_alert_email` fails (e.g. SES unavailable in prod), the failure is
  logged. `next_run_at` is still advanced so the schedule does not produce an
  infinite retry storm.

### 5.4 Report deletion and orphaned schedules
- When RPT-002's `delete_report` deletes a report (META row + all RUN rows), it
  must also delete any `SCHEDULE#*` rows for that `report_id`. RPT-002's
  `delete_report` implementation uses `batch_writer` to delete META + RUN rows.
  RPT-004 extends this: before the batch delete, it queries all schedule rows
  (`begins_with(sk, "SCHEDULE#")`) and includes them in the batch. This is the
  only change to existing RPT-002 code.
- Alternatively, the runner's per-schedule `try/except` absorbs a 404 from
  `run_report` for a deleted report and logs it without crashing.

### 5.5 Cadence update
- When `cadence` changes via PATCH, `next_run_at` is recomputed as
  `now_ts() + CADENCE_OFFSETS[new_cadence]`, resetting the clock. This matches the
  behaviour in `audit_export_schedule.update_schedule:133-145`.

### 5.6 Re-enable
- PATCH with `enabled=True` on a previously disabled schedule restores `GSI2PK` to
  `RPT_SCHEDULES#ACTIVE` and recomputes `next_run_at = now_ts() + CADENCE_OFFSETS[cadence]`
  so the schedule does not fire immediately after re-enabling.

### 5.7 Row cap and large results
- `run_report` caps its output at 2000 rows (RPT-002 specification). When `format=csv`,
  the inline email body is truncated to 100 rows with a footer note:
  `"(showing 100 of {row_count} rows — run report interactively for full results)"`.
  This avoids overrunning SES's 10 MB message limit.
- `format=json` is similarly capped to 100 rows inline in the email body; the full
  row_count is reported.

### 5.8 Empty result
- If `run_report` returns `row_count=0` the email is still sent, with body noting
  "No rows matched the report criteria for this period." This allows recipients to
  confirm the schedule ran even when there are no results.

### 5.9 Idempotency
- There is no idempotency key on schedule creation; each POST creates a new
  distinct schedule row with a fresh UUID. Users who accidentally double-POST can
  delete the duplicate via the DELETE endpoint.

- `start_report_scheduler_task` is a no-op (guard at the top of the function).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

The `send_alert_email` path (`alerts.py:459-491`) already handles dev/prod
branching internally: dev writes to `S.dev_email_log`, prod dispatches via SES.
`crm_report_scheduler.run_due_report_schedules` calls it without any `if S.dev_mode`
branch — full parity. The same is true of `audit_event` (`alerts.py:644`) and
`T.crm_reports` DynamoDB operations (moto in dev, real DDB in prod — same boto3 call).

There is no S3 attachment upload in this ticket (CSV/JSON is inlined in the email
body). If future work adds S3 uploads, they must follow the
`app.core.aws_clients.s3_client` factory pattern (used in `kyc_partner_api` and
audit export S3 path) so dev (moto in-process) and prod (real S3) share the same
code.

### 7.2 Recipient validation and SSRF

`recipients` are email addresses validated by `pydantic.EmailStr` at the API
layer. `send_alert_email` does not follow URLs; it only calls
`ses.send_email`, so there is no SSRF surface in the delivery path.

### 7.3 Ownership enforcement

Every service function that mutates or reads a schedule checks `owner_sub`
against the item's stored `owner_sub` and raises `PermissionError` on mismatch.
The router translates `PermissionError` to HTTP 403. Additionally, the
`report_id` path parameter is validated against the owning report before a
schedule is created, preventing a user from scheduling delivery of another user's
report.

### 7.4 Audit trail

Every schedule lifecycle event emits an `audit_event` to `T.alerts`:
- `crm_report_schedule.created` — on successful creation
- `crm_report_schedule.updated` — on any PATCH
- `crm_report_schedule.deleted` — on DELETE
- `crm_report_schedule.dispatched` — per successful runner dispatch, including
  `run_id`, `row_count`, `recipient_count` fields

### 7.5 Rate limiting on schedule creation

`POST /schedules` calls `_bucket_limit(user_sub, "rl#rpt_schedule_create", 10, 60)`
before writing. This mirrors the CSV export rate limit at `csv_export.py:66`.
A 429 is returned with `Retry-After: 60`.

### 7.6 CSV injection

All cell values written to the CSV body pass through `_sanitize_csv_field`
(`csv_export.py:43`) to prepend a `'` before any cell that starts with
`=`, `+`, `-`, `@`, `\t`, or `\r`.

## 8. Backward Compatibility & Migration

### 8.1 No schema migration for existing tables

No existing DynamoDB table schemas change. The `crm_reports` table is new (created
by RPT-001); adding a second GSI (`rpt-schedules-due-index`) to it in
`scripts/local-ddb-init.py` requires only a `just restart` in dev (the init script
drops and recreates all tables). In production, the table is also new (RPT-001
must ship first), so the GSI is declared at table-creation time — no
`UpdateTable` + async backfill is needed.

### 8.2 RPT-001 TableDef amendment

The TableDef for `crm_reports` defined in RPT-001 must be updated to include the
second GSI. The change is in `scripts/local-ddb-init.py` only — no DDB data
migration and no code change beyond the init script and `crm_report_scheduler.py`.

### 8.3 RPT-002 `delete_report` extension

The single code change to an RPT-002 function (`delete_report` extended to also
delete schedule rows) is additive: it queries new rows that did not exist before
RPT-004 ships. With `CRM_REPORTS_ENABLED=0` the router endpoints never call
`delete_report`, so there is no risk to existing behaviour.

### 8.4 Rollback

Because all schedule rows use `PK=SCHEDULE#{id}` / `SK=META`, they are cleanly
separated from report META rows and RUN rows in the same table. Rolling back
RPT-004 (by disabling `CRM_REPORTS_SCHEDULER_ENABLED`) leaves orphaned schedule
rows in DynamoDB but they are never queried and do not affect any live paths.

## 10. Open Questions / Assumptions

1. **Email attachment vs. inline body**: The current design inlines the CSV/JSON
   in the email body (truncated to 100 rows). SuiteCRM's AOR scheduler attaches
   the report as a file. Future work could use `email.mime.multipart` to produce
   a proper multipart/mixed attachment, but this requires the SES
   `send_raw_email` API rather than the simpler `send_email`. This is deferred to
   avoid complicating the `send_alert_email` primitive.

2. **Timezone for cadence alignment**: The current implementation advances
   `next_run_at` by a fixed offset in Unix seconds (same as the audit export
   scheduler). There is no "run at 08:00 in user's timezone" concept. If
   timezone-aligned scheduling is needed, it is a follow-up ticket.

3. **Maximum schedules per user (cross-report)**: The spec caps schedules per
   report at 10. A global per-user cap (e.g. 50 across all reports) is not
   implemented. If abuse becomes a concern it can be enforced by a separate
   GSI query on `owner_sub`.

4. **Retry on email failure**: Currently `next_run_at` is advanced even when
   `send_alert_email` fails. An alternative is to leave `next_run_at` unchanged on
   email failure so the next poll retries delivery. The current choice (advance
   regardless) prevents email failure storms; the audit export scheduler makes the
   same choice.

5. **Report run caching**: Each scheduled dispatch calls `run_report`, which
   re-queries DynamoDB. If the report is expensive, this could be optimised by
   returning the most recent RUN row if it is within some freshness window.
   Deferred to a follow-up.
