# PRJ-012 — Projects frontend pages (list, detail, tasks, members)

**Type:** Feature | **Priority:** P1 | **Estimate:** 3d  
**Flag:** `CRM_PROJECTS_ENABLED` (default OFF)  
**Depends on:** PRJ-001 through PRJ-008 (backend scaffold, CRUD, tasks, dependencies, milestones, templates, members, Gantt)

---

## 1. Summary & Goal

Deliver the complete React/TypeScript frontend for CRM project management under `frontend/src/pages/crmProjects/`. When `CRM_PROJECTS_ENABLED=0` (default) the platform renders an empty-state or "coming soon" notice — every API call catches the 404 guard response and the rest of the application is byte-for-byte unchanged.

When the flag is on, users get:

- A **project list page** (`CrmProjectsPage`) with status-filtered cards and a "New Project" dialog.
- A **project detail page** (`CrmProjectDetailPage`) with four tabs: Overview, Tasks, Members, Gantt.
- A **shared form dialog** (`CrmProjectFormDialog`) reused by list and detail.
- Full TypeScript typings for the CRM project, task, and member API surface.
- A "Projects" sidebar entry under a new "CRM" section (using the already-imported `FolderKanban` icon).
- Three React Router routes wired in `App.tsx`, all lazy-loaded.

No new DynamoDB tables or backend endpoints are introduced by this ticket; it is purely frontend work consuming the APIs from PRJ-001 through PRJ-008. The Gantt component tab (PRJ-008) is embedded, not re-implemented.

### 4.2 Frontend endpoint module — `frontend/src/api/endpoints/crmProjects.ts`

```typescript
import { api } from "@/api/client";
import type {
  CrmProject, CrmProjectCreateReq, CrmProjectUpdateReq, CrmProjectListResp,
  CrmProjectTask, CrmProjectTaskCreateReq, CrmProjectTaskUpdateReq,
  CrmProjectTaskListResp, CrmProjectMember,
} from "@/api/types";

// ── Projects ──────────────────────────────────────────────────────
export const listCrmProjects = (opts?: {
  limit?: number; cursor?: string;
  status?: string; nameQuery?: string; accountId?: string;
}) => {
  const params: Record<string, string> = {};
  if (opts?.limit)     params.limit      = String(opts.limit);
  if (opts?.cursor)    params.cursor     = opts.cursor;
  if (opts?.status)    params.status     = opts.status;
  if (opts?.nameQuery) params.name_query = opts.nameQuery;
  if (opts?.accountId) params.account_id = opts.accountId;
  return api.get<CrmProjectListResp>("/v1/crm/projects", params);
};

export const createCrmProject = (body: CrmProjectCreateReq) =>
  api.post<CrmProject>("/v1/crm/projects", body);

export const getCrmProject = (projectId: string) =>
  api.get<CrmProject>(`/v1/crm/projects/${projectId}`);

export const updateCrmProject = (projectId: string, body: CrmProjectUpdateReq) =>
  api.patch<CrmProject>(`/v1/crm/projects/${projectId}`, body);

export const deleteCrmProject = (projectId: string) =>
  api.del<{ ok: boolean }>(`/v1/crm/projects/${projectId}`);

// ── Tasks ─────────────────────────────────────────────────────────
export const listCrmProjectTasks = (
  projectId: string,
  opts?: { limit?: number; cursor?: string; milestonesOnly?: boolean }
) => {
  const params: Record<string, string> = {};
  if (opts?.limit)          params.limit           = String(opts.limit);
  if (opts?.cursor)         params.cursor          = opts.cursor;
  if (opts?.milestonesOnly) params.milestones_only = "true";
  return api.get<CrmProjectTaskListResp>(`/v1/crm/projects/${projectId}/tasks`, params);
};

export const createCrmProjectTask = (
  projectId: string, body: CrmProjectTaskCreateReq
) => api.post<CrmProjectTask>(`/v1/crm/projects/${projectId}/tasks`, body);

export const updateCrmProjectTask = (
  projectId: string, taskId: string, body: CrmProjectTaskUpdateReq
) => api.patch<CrmProjectTask>(`/v1/crm/projects/${projectId}/tasks/${taskId}`, body);

export const deleteCrmProjectTask = (projectId: string, taskId: string) =>
  api.del<{ ok: boolean }>(`/v1/crm/projects/${projectId}/tasks/${taskId}`);

export const reorderCrmProjectTasks = (projectId: string, taskIds: string[]) =>
  api.put<CrmProjectTask[]>(`/v1/crm/projects/${projectId}/tasks/order`, { task_ids: taskIds });

// ── Members ───────────────────────────────────────────────────────
export const listCrmProjectMembers = (projectId: string) =>
  api.get<CrmProjectMember[]>(`/v1/crm/projects/${projectId}/members`);

export const addCrmProjectMember = (
  projectId: string, body: { user_sub: string; role: string }
) => api.post<CrmProjectMember>(`/v1/crm/projects/${projectId}/members`, body);

export const updateCrmProjectMemberRole = (
  projectId: string, userSub: string, role: string
) => api.patch<CrmProjectMember>(
  `/v1/crm/projects/${projectId}/members/${userSub}`, { role }
);

export const removeCrmProjectMember = (projectId: string, userSub: string) =>
  api.del<{ ok: boolean }>(`/v1/crm/projects/${projectId}/members/${userSub}`);
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Feature flag off — graceful degradation

When `isCrmProjectsEnabled()` returns false (default):

- The "CRM" `NavGroup` is not rendered in `Sidebar.tsx` — no dead link visible in navigation.
- The routes `/crm/projects` and `/crm/projects/:projectId` still exist in the router (removing them would break deep-links on re-enable) but their lazy-loaded components detect the disabled state on mount and render an `<EmptyState>` with title "CRM Projects" and message "This feature is not enabled on your account." No API call is made.
- If a user navigates directly to `/crm/projects` and the backend returns HTTP 404 (the `_require_crm_projects()` guard), the React Query error handler catches the `AxiosError` and the same empty-state is displayed. The error is not rethrown to an error boundary.

### 5.2 CrmProjectsPage — project list

**Mount behavior:** `useQuery(["crm-projects", statusFilter, nameQuery], () => listCrmProjects({status: statusFilter, nameQuery}))`. The query key includes the active filter values so React Query caches each filter separately.

**Status filter dropdown:** Uses `shadcn/ui Select` with options: All (empty string), Draft, In Review, Underway, Completed, Deferred. When "All" is selected, `status` param is omitted from the API call.

**Project cards:** Each card (`shadcn/ui Card`) shows:
- Name (CardTitle)
- Status badge (`shadcn/ui Badge` with color variant: `secondary` for draft, `outline` for in_review, `default` for underway, `success` for completed, `destructive` for deferred — using the existing badge variant system).
- Priority icon: no icon for 0, `ArrowDown` for 1 (low), `Minus` for 2 (medium), `ArrowUp` for 3 (high), `AlertTriangle` for 4 (urgent) — all from `lucide-react`.
- Start/end date formatted as locale date string (`new Date(ts * 1000).toLocaleDateString()`). Empty dates show "—".
- Two buttons: "Open" links to `/crm/projects/{id}`, "Gantt" links to `/crm/projects/{id}/gantt`.

**Pagination:** A "Load more" button appears when the list response includes a non-null `cursor`. Clicking appends the next page to the in-memory items array. Uses `useInfiniteQuery` with `getNextPageParam: (page) => page.cursor ?? undefined`.

**New Project dialog:** `CrmProjectFormDialog` in create mode. On submit: `useMutation(createCrmProject)` → on success calls `queryClient.invalidateQueries(["crm-projects"])` and closes the dialog.

**Empty state:** When `items.length === 0` and `!isLoading`, render `<EmptyState>` with `FolderKanban` icon, title "No projects yet", and a "Create your first project" button that opens the dialog.

**Name search:** A debounced (300 ms) text input filters by `name_query`. The debounce uses `React.useCallback` + `setTimeout` — no external dep required.

### 5.3 CrmProjectFormDialog — shared create/edit dialog

Props: `mode: "create" | "edit"`, `initialValues?: Partial<CrmProjectUpdateReq>`, `onSuccess: (project: CrmProject) => void`, `open: boolean`, `onOpenChange: (open: boolean) => void`.

Uses React Hook Form with Zod schema:

```typescript
const schema = z.object({
  name: z.string().min(1).max(120),
  description: z.string().max(2000).optional(),
  status: z.enum(["draft","in_review","underway","completed","deferred"]).default("draft"),
  priority: z.coerce.number().int().min(0).max(4).default(0),
  start_date: z.number().int().optional(),
  end_date: z.number().int().optional(),
  assigned_user_sub: z.string().optional(),
  account_id: z.string().optional(),
}).refine(
  (v) => !v.start_date || !v.end_date || v.end_date >= v.start_date,
  { message: "End date must be after start date", path: ["end_date"] }
);
```

Dates are captured via `<input type="date">` and converted to Unix timestamps (`Math.floor(new Date(value).getTime() / 1000)`) before submission. `Zod.refine` on `end_date >= start_date` mirrors the backend 400 `end_before_start` check client-side.

### 5.4 CrmProjectDetailPage — tabbed detail

Route: `/crm/projects/:projectId`. Uses `useParams<{ projectId: string }>()`.

**Data loading:** Two parallel queries on mount:
- `useQuery(["crm-project", projectId], () => getCrmProject(projectId))`
- `useQuery(["crm-project-members", projectId], () => listCrmProjectMembers(projectId))`

Loading skeleton: `<Loader2 className="animate-spin">` centered in a min-h-48 div.

Error state: `<Alert variant="destructive">` — for the 404 case (flag off or project not found) shows the empty-state component.

**Tab navigation:** `shadcn/ui Tabs` with values `overview | tasks | members | gantt`. The active tab is synced to the URL search param `?tab=overview` (default) so deep-links work and browser back/forward navigate between tabs. `useSearchParams` from react-router-dom.

#### 5.4.1 Overview tab

Displays all project header fields in a two-column grid. Each field is editable inline via a toggle: clicking a field value shows an input/select in place; pressing Enter or clicking "Save" triggers `useMutation(updateCrmProject)`. On mutation success the query cache for `["crm-project", projectId]` is invalidated.

Status field uses a `<Select>` constrained to the valid transition targets. The full validation of allowed transitions is server-side (PRJ-009); the client shows all options but displays the server 400 `invalid_status_transition` error as a toast: `toast.error("Invalid status transition: " + err.response?.data?.detail)`.

**Status history link:** A "View history" button below the status field navigates to `?tab=overview&showHistory=true` and renders a collapsible list of status-change audit entries fetched from `GET /{id}/status-history`.

#### 5.4.2 Tasks tab

Component: `CrmTaskList` (co-located in `frontend/src/pages/crmProjects/CrmTaskList.tsx`).

**Query:** `useQuery(["crm-project-tasks", projectId], () => listCrmProjectTasks(projectId, { limit: 200 }))`.

**Table columns:**
- Order (drag handle icon `GripVertical` from lucide-react)
- Name (milestone tasks show a `Diamond` icon from lucide-react beside the name when `is_milestone === true`)
- Assignee (`assigned_user_sub` truncated to 12 chars or "—")
- Start date (locale date string)
- End date (locale date string)
- % Complete (inline editable `<Input type="number" min="0" max="100">` — blur calls `updateCrmProjectTask` with `{ percent_complete: value }`)
- Dependency count (number of `predecessor_task_ids`, shown as a badge)
- Delete button (trash icon, owner-only)

**Drag-to-reorder:** Uses `@dnd-kit/sortable` (`SortableContext`, `useSortable`, `DndContext` with `PointerSensor`). On drag end, the `onDragEnd` handler derives the new ordered `task_ids` array and calls `reorderCrmProjectTasks(projectId, taskIds)`. The mutation optimistically reorders the local `items` array and invalidates `["crm-project-tasks", projectId]` on settle. If the sortable library import is unavailable (pre-PRJ-008 state), fall back to up/down arrow buttons that shift task position.

**Add Task inline form:** A row at the bottom of the table with `name`, `duration_days`, `start_date` inputs and an "Add" button. On submit calls `createCrmProjectTask`. Controlled by `React.useState` local form state (not React Hook Form, for minimal complexity).

**Milestone filter toggle:** A `<Switch>` labeled "Milestones only" above the table. When on, re-fetches with `milestonesOnly: true` by updating the query key.

#### 5.4.3 Members tab

Query: `useQuery(["crm-project-members", projectId], () => listCrmProjectMembers(projectId))` (already loaded by `CrmProjectDetailPage`, passed as prop or read from cache by the same query key).

**Member list:** Table with columns: User sub (truncated), Role (badge: `owner`=blue, `member`=gray, `viewer`=outline), Added date, Remove button.

**Remove button visibility:** Compare `member.user_sub` against the current user's `user_sub` from `useAuthStore`. Only show the remove button when the current user's role is `owner` AND the target member is not the owner row itself (`role !== "owner"`).

**Role badge color map:**

```typescript
const roleVariant: Record<CrmProjectMemberRole, BadgeVariant> = {
  owner: "default",
  member: "secondary",
  viewer: "outline",
};
```

**Add Member dialog:** A `<Dialog>` containing a `user_sub` text input and a `<Select>` for role (member/viewer; owner not selectable in add flow). Submit calls `addCrmProjectMember` and invalidates `["crm-project-members", projectId]`.

**Role update:** Clicking a non-owner role badge opens an inline `<Select>` (same pattern as inline edit in Overview tab). On change calls `updateCrmProjectMemberRole` and invalidates the members query.

#### 5.4.4 Gantt tab

Renders `<CrmProjectGanttPage projectId={projectId} embedded />` where `CrmProjectGanttPage` is delivered by PRJ-008. If PRJ-008 has not yet landed, the tab shows:

```tsx
<Alert>
  <AlertDescription>Gantt chart coming soon.</AlertDescription>
</Alert>
```

The `embedded` prop (boolean) suppresses the standalone page chrome (header, back button) so the component fits inside the detail page's tab panel.

### 5.5 Route ordering in App.tsx

The new routes must be added inside the `<AppShell>` / `<ProtectedRoute>` wrapper. Declaration order matters for React Router v6 — more specific paths first:

```tsx
<Route path="/crm/projects/:projectId/gantt" element={<CrmProjectGanttPage />} />
<Route path="/crm/projects/:projectId"       element={<CrmProjectDetailPage />} />
<Route path="/crm/projects"                  element={<CrmProjectsPage />} />
```

### 5.6 Error handling — flag-off 404

When the CRM flag is off, every `GET /v1/crm/projects*` call returns `404`. React Query surfaces this as a failed query. The pages use `isError` and inspect `error.response?.status === 404` to render the empty-state rather than a generic error. This prevents false "something went wrong" messages when the feature is simply disabled.

```typescript
if (isError && (error as AxiosError).response?.status === 404) {
  return <CrmFeatureDisabledState />;
}
```

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007:** The frontend consumes the API via the standard Vite proxy (`/v1/crm/projects` → `http://localhost:8000`). There is no dev-mode branch in any frontend component — all API calls go through the same `api/client.ts` axios instance in both environments. The axios instance at `frontend/src/api/client.ts` attaches CSRF cookie headers and handles 401 → logout uniformly. No mock data, no `import.meta.env.DEV` conditional.

**CSRF:** All mutating calls (`POST`, `PATCH`, `PUT`, `DELETE`) go through `api.post/patch/put/del` which attach `x-csrf-token` from the cookie store. Cookie-auth sessions enforce CSRF per `app/auth/deps.py`; Bearer-auth API keys skip CSRF. The frontend uses the same cookie-auth path as all other pages.

**Idempotency on reorder:** `PUT /tasks/order` is idempotent — sending the same list twice produces the same result. The frontend optimistic update is reverted if the mutation fails, preventing stale UI state.

**Authorization display:** The "Remove member" button and the "Add member" dialog are gated by the current user's role. The backend enforces authorization independently (`_assert_project_access`); the frontend gate is a UX affordance only and never a security boundary. A viewer who tampers with the request will receive a 403 from the backend.

**No money-out paths:** This ticket introduces no billing, refund, or payment logic. The `refund_payment` / `settle_or_reverse_ledger` primitives are not touched.

**No S3/KMS:** No file upload, encryption, or KMS interaction in this ticket.

## 10. Open Questions / Assumptions

1. **PRJ-008 Gantt component landing:** PRJ-012 assumes PRJ-008 delivers `CrmProjectGanttPage` accepting an `embedded` prop. If the prop interface differs, the Gantt tab integration point in `CrmProjectDetailPage` must be updated. Until PRJ-008 lands, the tab shows a placeholder.

2. **`gantt-task-react` npm install:** PRJ-008 is responsible for adding this package to `frontend/package.json`. PRJ-012 does not run `npm install gantt-task-react` — that is PRJ-008's responsibility.

3. **User display name for assignee/member columns:** The current task model stores only `assigned_user_sub`. The Tasks tab displays the truncated sub string. A richer "assigned user display name" requires a profile lookup endpoint. Deferred to a follow-up ticket — this spec shows the sub as-is.

4. **`account_id` field:** Rendered as a plain text input in `CrmProjectFormDialog`. Once PTY-015 (org accounts) ships, this should become a searchable dropdown of account records. For now it accepts any opaque string.

5. **Optimistic reorder vs. server race:** The optimistic reorder in the Tasks tab could conflict with concurrent edits. Accepted risk for the 3-day estimate — no distributed lock is added. The backend reorder is idempotent and the query invalidation on settle restores consistency.

6. **`@dnd-kit/sortable` version:** `package.json` declares `^10.0.0`. The `useSortable` / `SortableContext` API is stable across v7+. No version-specific workaround is anticipated.

7. **Inline date inputs:** `<input type="date">` returns ISO string (`"YYYY-MM-DD"`), converted to Unix via `new Date(value).getTime() / 1000`. Timezone: `new Date("2025-01-01")` is interpreted as midnight UTC, which is consistent across environments. Accepted.
