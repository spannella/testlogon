## 1. Summary & Goal

LED-001 is pure scaffolding. It delivers:

- One master feature flag `S.leads_enabled` (default OFF).
- Three module-level sub-flags `S.leads_scoring_enabled`, `S.leads_drip_enabled`, `S.leads_assignment_enabled` (all default OFF).
- Two settings keys for DynamoDB table name and base configuration.
- One new DynamoDB single table `leads` with PK=`pk` / SK=`sk` and three GSIs (`ByOwner`, `ByStatus`, `BySource`) with correctly-declared numeric `attr_types`.
- One new table handle `T.leads` in `app/core/tables.py`.

No router, no service logic, no Pydantic models, and no frontend code are introduced. LED-001 is the zero-risk prerequisite for every downstream LED ticket (LED-002 through LED-013). When the flag is off — the default — the platform is byte-for-byte unchanged: no new routes, no background tasks, no existing table or endpoint is modified.

## 2. Context & Current State

### 2.1 Feature-flag pattern in `app/core/settings.py`

`app/core/settings.py` defines a frozen `Settings` dataclass (~2772 lines) whose fields are populated entirely from environment variables at process start. There are two established styles for default-OFF boolean flags:

**Style A** — `.lower() == "true"` (used by `inventory_reservations_enabled` at line 839 and `returns_rma_enabled` at line 846):
```python
inventory_reservations_enabled: bool = os.environ.get("INVENTORY_RESERVATIONS_ENABLED", "false").lower() == "true"
```

**Style B** — `not in ("0", "false", "False")` (used by `cart_reminders_enabled` at line 821, which defaults ON):
```python
cart_reminders_enabled: bool = os.environ.get("CART_REMINDERS_ENABLED", "1") not in ("0", "false", "False")
```

The LED ticket specification (`CRM_LEADS_TICKETS.md` line 28) explicitly prescribes Style B but with a `"0"` default, which evaluates to `False` and is therefore default-OFF. The exact form to follow is:

```python
leads_enabled: bool = os.environ.get("LEADS_ENABLED", "0") not in ("0", "false", "False")
```

This matches the `cart_reminders_enabled` structure at line 821 with a `"0"` sentinel to ensure default-OFF behavior. The three sub-flags use the same form.

### 2.2 Table-name settings pattern

Every DynamoDB table name is stored as a string setting. Examples: `contacts_table_name` at line 498 (`os.environ.get("DDB_CONTACTS_TABLE", "Contacts")`), `activity_feed_table_name` at line 2335 (`os.environ.get("ACTIVITY_FEED_TABLE_NAME", "activity_feed")`), `cart_reminder_config_table_name` at line 822. ```

### 2.3 `Tables` dataclass and `_safe_table` in `app/core/tables.py`

`app/core/tables.py` defines a `@dataclass(frozen=True)` called `Tables` (line 69) with one `Any`-typed field per logical table. The singleton `T = Tables(...)` is constructed at module import time (line 321). Every handle uses `_safe_table(S.<setting_name>)` (lines 65–66), which returns a `_FloatSafeTable` proxy (lines 29–62) that coerces Python `float` to `Decimal` on every `put_item` and `update_item` call. The current last entry is `returns=_safe_table(S.returns_table_name)` (line 571).

The field for `T.leads` must be added to the `Tables` dataclass body and wired in the `T = Tables(...)` constructor call, following the same position (after `T.contacts` at line 354 in the constructor and line 102 in the dataclass, per the ticket's instruction to wire it "next to `T.contacts`").

### 2.4 `TableDef` and `_table_defs()` in `scripts/local-ddb-init.py`

`scripts/local-ddb-init.py` defines `TableDef` (lines 28–35), a frozen dataclass with fields `name`, `partition_key`, `sort_key`, `gsi`, and `attr_types`. The `_table_defs()` function (line 42) returns the full list; `main()` (line 2664) iterates it and calls `_ensure_table` for each. GSIs are expressed as dicts with keys `index_name`, `partition_key`, and `sort_key`.

The critical CLAUDE.md gotcha: if a GSI sort key is numeric, it **must** appear in `attr_types` with value `"N"`. Omitting it causes DynamoDB to treat the attribute as a string, yielding `ValidationException` at query time. Examples of correctly-declared numeric GSI keys in the codebase:

- `sticker_collections` (line 84): `attr_types={"created_at": "N"}`
- `kyc_review_schedule` (line 196): `attr_types={"next_review_date": "N"}`
- `kyc_documents` (line 217): `attr_types={"created_at": "N"}`
- `kyc_risk_scores` (line 178): `attr_types={"timestamp": "N"}`

All three GSI sort keys in the `leads` table (`GSI1SK`, `GSI2SK`, `GSI3SK`) are numeric timestamps and must each be declared in `attr_types`.

## 3. Data Model

### 3.1 Single-table schema

LED-001 creates one DynamoDB table named `leads` (or the value of `DDB_LEADS_TABLE`). The table uses a composite key `pk` (string, hash) and `sk` (string, range), consistent with the single-table pattern already used by `billing` (`pk`/`sk`), `questionnaires` (`pk`/`sk`), `kyc_cases` (`pk`/`sk`), and `shopping_cart` (`PK`/`SK`).

All item types coexist in this single table:

| Row type | `pk` value | `sk` value | Notes |
|---|---|---|---|
| Lead META | `LEAD#{lead_id}` | `META` | Primary lead record |
| Lead ACTIVITY | `LEAD#{lead_id}` | `ACTIVITY#{ts}#{uuid}` | Per-lead activity log rows (LED-012) |
| Prospect META | `PROSPECT#{prospect_id}` | `META` | Lightweight external contact (LED-007) |
| Scoring rules | `SCORING_CONFIG` | `RULES` | Global scoring rule set (LED-011) |
| Assignment queue | `QUEUE#{queue_id}` | `CONFIG` | Round-robin queue config (LED-010) |
| Agent availability | `AGENT#{user_sub}` | `QUEUE#{queue_id}` | Queue membership (LED-010) |
| Opportunity stub | `LEAD#{lead_id}` | `OPPORTUNITY#META` | Inline opp record (LED-006) |

LED-001 only provisions the table. The row types beyond Lead META are documented here for completeness and will be written by downstream tickets.

### 3.2 GSI definitions

Three GSIs are required at table creation. All three use `created_at` (integer Unix seconds from `app/core/time.now_ts()`) as their sort key, which is a numeric attribute and **must** be declared in `attr_types`.

**GSI1 — ByOwner**
- Partition key: `GSI1PK` (string) — value: `OWNER#{user_sub}`
- Sort key: `GSI1SK` (number) — value: `{created_at}`
- Purpose: list all leads belonging to a given user, sorted newest-first.

**GSI2 — ByStatus**
- Partition key: `GSI2PK` (string) — value: `STATUS#{status}`
- Sort key: `GSI2SK` (number) — value: `{created_at}`
- Purpose: list all leads in a given status (e.g., `STATUS#new`, `STATUS#assigned`), sorted newest-first.

**GSI3 — BySource**
- Partition key: `GSI3PK` (string) — value: `SOURCE#{lead_source}`
- Sort key: `GSI3SK` (number) — value: `{created_at}`
- Purpose: list all leads from a given source (e.g., `SOURCE#campaign`), sorted newest-first; also powers the lead-source summary endpoint in LED-004.

### 3.3 `attr_types` declaration

```python
attr_types={"GSI1SK": "N", "GSI2SK": "N", "GSI3SK": "N"}
```

All three numeric sort keys are named distinctly (`GSI1SK`, `GSI2SK`, `GSI3SK`) rather than all sharing `created_at`, which avoids DynamoDB attribute-type conflicts when the same attribute name might carry different types across item types in a single-table design. The `GSI_PK` attributes (`GSI1PK`, `GSI2PK`, `GSI3PK`) default to string type and require no `attr_types` entry.

### 3.4 Future GSIs (not in LED-001)

LED-007 (Prospects) adds a `ByEmail` GSI (GSI4) with `attr_types={"GSI4SK": "N"}`. LED-009 (Duplicate detection) adds a `ByPhone` GSI (GSI5) with `attr_types={"GSI5SK": "N"}`. These are additive DynamoDB `UpdateTable` operations applied by those tickets' own `TableDef` changes; LED-001 does not pre-provision them.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off guarantees

When `LEADS_ENABLED` is absent or set to `"0"`, `"false"`, or `"False"`:
- `S.leads_enabled` evaluates to `False`.
- All sub-flags also evaluate to `False` independently (they are not gated on the master flag at the settings level; each downstream ticket's router guard checks its own flag).
- `T.leads` is still constructed at import time as a `_FloatSafeTable` proxy pointing at the `"leads"` DynamoDB table. This is intentional and safe: the proxy is a lazy reference — no network call occurs until a method (`put_item`, `query`, etc.) is invoked. If the table does not exist in DynamoDB, any such call will raise a `ResourceNotFoundException`, but no code path invokes `T.leads` unless `S.leads_enabled` is checked first by a router guard.
- No existing endpoint, table, or background task is affected in any way.

### 5.2 Sub-flag independence

The sub-flags (`leads_scoring_enabled`, `leads_drip_enabled`, `leads_assignment_enabled`) are evaluated independently of `S.leads_enabled`. Downstream tickets that implement those features must check both the master flag and the relevant sub-flag:

```python
if not S.leads_enabled:
    raise HTTPException(404)
if not S.leads_assignment_enabled:
    raise HTTPException(404)
```

This two-level check mirrors the layered sub-flag gating used by the voice-message AI endpoints: `messaging_transcription_enabled` (`app/routers/messaging.py:15007`) and `messaging_tts_enabled` combined with `voice_message_enabled` (`app/routers/messaging.py:15080`). Note there is no `messaging_enabled` master flag in `app/core/settings.py`; those endpoints gate on their own (and an adjacent) sub-flag directly. LED's own two-level master+sub-flag check is therefore a new convention for the Leads module, not a copy of an existing master-flag chain.

### 5.3 `T.leads` access before table creation

If `just restart` has not been run after deploying LED-001, the `leads` table does not yet exist. Any premature call to `T.leads.<method>()` will raise `botocore.exceptions.ClientError` with `ResourceNotFoundException`. The correct pattern for all downstream services is a guard check on `S.leads_enabled` before touching `T.leads`. Smoke tests will catch any missing guard by asserting that the table handle exists and resolves correctly against a moto-backed table.

### 5.4 `DDB_LEADS_TABLE` override in non-default environments

Some environments (e.g., staging with table-name prefixes) set `DDB_LEADS_TABLE=staging-leads`. The `_resolve_table_name(S.leads_table_name, "leads")` call in `local-ddb-init.py` correctly defers to the setting, so the same `TableDef` works in all environments. The fallback `"leads"` is only reached if `S.leads_table_name` is an empty string, which cannot happen because `os.environ.get("DDB_LEADS_TABLE", "leads")` always returns a non-empty string.

### 5.5 `_FloatSafeTable` proxy and frozen `T`

`Tables` is `@dataclass(frozen=True)`: once `T` is constructed at module import, its fields cannot be reassigned. Hermetic tests that need to swap in a moto-backed table handle do so via `object.__setattr__(T, "leads", moto_table_handle)`, the canonical pattern used by `tests/test_gap_0220_0221_ssh_stored_key.py` and many others. The `_FloatSafeTable` wrapper should be preserved in the override (i.e., wrap the moto resource table in `_FloatSafeTable`) or tests should patch at the service layer. Both approaches are valid; the test plan below describes the recommended form.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

LED-001 introduces no `dev_mode` branching. The `_safe_table` proxy, the `TableDef` creation path, and the flag evaluation are identical in dev (DynamoDB Local on port 8001 via `DDB_ENDPOINT_URL=http://localhost:8001`) and prod (AWS DynamoDB via standard boto3 endpoint resolution). There is no dev-only fallback or mock path. This satisfies the SECOPS-007 constraint from `CRM_LEADS_TICKETS.md` line 13.

### 7.2 Idempotency of table creation

`_ensure_table` in `scripts/local-ddb-init.py` (called by `main()` at line 2669) performs a `CreateTable` call and swallows `ResourceInUseException` (table already exists). Running `just restart` or `local-ddb-init.py` multiple times is safe; GSIs are declared at creation time and are not modified by repeated runs.

### 7.3 Security posture

LED-001 has no auth, no PII, and no money-movement logic. The only security consideration is that `T.leads` must not be reachable through any code path when `S.leads_enabled` is `False`. Because LED-001 introduces no router and no service, this is guaranteed at this stage. Downstream tickets (LED-002 onward) are responsible for gating their own endpoints.

### 7.4 No PII in settings or table creation

The settings keys added by LED-001 (`leads_enabled`, `leads_table_name`, and sub-flags) contain no PII. The DynamoDB table definition contains no data — it is a schema-only operation.

## 8. Backward Compatibility & Migration

### 8.1 No migration required

LED-001 is entirely additive:
- New `Settings` fields default to their env-var values; missing env var produces the default. No existing code reads these new fields, so no existing behavior changes.
- Adding a new `leads: Any` field to `Tables` and a new `leads=...` entry to `T = Tables(...)` is backward-compatible in Python. No existing import, test, or service references `T.leads` before this ticket.
- The new `TableDef` in `_table_defs()` only adds a table; no existing table definition is modified.

### 8.2 No data backfill

The `leads` table starts empty. There is no historical data to migrate.

### 8.3 `just restart` creates the table

After merging LED-001, running `just restart` (which calls `scripts/local-ddb-init.py`) creates the `leads` table with all three GSIs. No manual DynamoDB operation is required in any environment.

### 8.4 Production deployment order

In production, `scripts/local-ddb-init.py` (or its production equivalent) must be run before the backend process starts, so that `T.leads` resolves to an existing table the moment the first request arrives. Because no endpoint currently reads `T.leads`, deploying the code before running the init script is also safe — `T.leads` will just be an unresolvable table handle until the script runs.

## 10. Open Questions / Assumptions

Existing tables are inconsistent — `Contacts` uses PascalCase (`DDB_CONTACTS_TABLE` defaults to `"Contacts"` at settings.py line 498) while `activity_feed` (line 2335) and `kyc_cases` use snake_case. This spec follows the ticket spec's lower-case `"leads"` and notes that the default can be overridden via `DDB_LEADS_TABLE` for any environment that needs a different name or prefix.

2. **Sub-flag `leads_drip_enabled`**: No LED ticket in `CRM_LEADS_TICKETS.md` currently implements drip nurturing sequences. The flag is added now (as the ticket specification directs) so that future work can be gated without a settings change. It is assumed to remain permanently `False` until a drip-sequencing ticket is filed.

3. **PTY-001 flag reference**: The ticket specification mentions following the sub-flag pattern from `party_crm_contacts_migration_enabled` in `docs/ofbiz/specs/PTY-001.md` (the upstream `CRM_LEADS_TICKETS.md` line 34 cites a non-existent `PARTY_CRM_TICKETS.md:PTY-001`; the real PTY specs live at `docs/ofbiz/specs/PTY-*.md`). The PTY-001 spec exists and defines `party_crm_enabled` / `party_crm_contacts_migration_enabled` (PTY-001.md:95–96), but **neither flag yet exists in `app/core/settings.py`** (confirmed: no `party_crm` references appear in settings.py — PTY-001 is not yet implemented). This spec therefore bases the sub-flag pattern on the existing `inventory_reservations_enabled` / `returns_rma_enabled` / `cart_reminders_enabled` family, which achieves the same structural goal. When PTY-001 is implemented it will follow the same pattern.

4. **`leads_table_name` vs `leads_enabled` consistency**: A valid question is whether `T.leads` should be conditionally constructed only when `S.leads_enabled` is `True`. The existing pattern (used by `T.returns`, `T.inventory`, `T.reservations`, all for default-OFF flags) is to always construct the handle at import time and rely on the router guard to prevent actual calls. This spec follows that pattern to avoid complicating the frozen `Tables` dataclass with optional fields.
