# WFL-009 — Admin CRUD router & frontend UI

**Type:** Feature | **Priority:** P2 | **Estimate:** 3d
**Flag:** `CRM_WORKFLOW_ENABLED` (default `"0"`)
**Depends on:** WFL-001, WFL-002, WFL-003, WFL-004, WFL-005, WFL-006, WFL-007, WFL-008

---

## 1. Summary & Goal

WFL-009 is the final ticket in the CRM Workflow series. It surfaces the rule engine built in WFL-001 through WFL-008 via a REST API and a React admin page so that general admins and root operators can create, edit, enable/disable, delete, and monitor workflow rules without writing code or touching DynamoDB directly.

**What this ticket delivers:**

1. A FastAPI router (`app/routers/workflow_rules.py`) with thirteen endpoints covering rule CRUD, enable/disable toggles, per-rule run history, and drip-sequence definition CRUD — all gated by the `CRM_WORKFLOW_ENABLED` flag and `require_admin_or_root_csrf` auth.
2. A React admin page (`frontend/src/pages/admin/workflow/WorkflowRulesPage.tsx`) listing all rules in a data table with inline enable/disable toggles and a slide-in editor drawer (`WorkflowRuleEditor.tsx`) for creating and editing rules.
3. TypeScript types and an API endpoint module (`frontend/src/api/endpoints/workflowRules.ts`) mirroring the backend models.
4. A route entry in `frontend/src/App.tsx` and a sidebar nav item in `frontend/src/components/layout/Sidebar.tsx` under the Admin section, guarded by `canAccessGeneralAdminControls`.

With `CRM_WORKFLOW_ENABLED=0` (the default), the backend returns 404 for every endpoint in this router, the frontend nav item is not rendered, and the platform is byte-for-byte unchanged from today.

### 4.3 Flag gate

Every endpoint must check `S.crm_workflow_enabled` as the first statement and raise `HTTPException(404)` when false. This keeps the router free of conditional `include_router` logic in `main.py` while ensuring the platform is unchanged when the flag is off:

```python
def _require_flag() -> None:
    if not S.crm_workflow_enabled:
        raise HTTPException(status_code=404, detail="crm_workflow not enabled")
```

Each handler calls `_require_flag()` before touching any service. This is identical to the pattern used for the Stripe provider gate in `app/routers/billing.py` and is consistent with the cross-cutting constraint in `CRM_WORKFLOW_TICKETS.md`.

async def list_rule_runs(rule_id: str, limit: int = Query(25, ge=1, le=100),
                         cursor: Optional[str] = None,
                         _actor: AuthenticatedUser = Depends(require_admin_or_root)):
    _require_flag()
    from app.core.tables import T
    from app.core.cursor import encode_cursor, decode_cursor
    exclusive_start = decode_cursor(cursor)
    kwargs = dict(
        KeyConditionExpression=Key("pk").eq(f"RULE#{rule_id}") & Key("sk").begins_with("RUN#"),
        ScanIndexForward=False,
        Limit=limit,
    )
    if exclusive_start:
        kwargs["ExclusiveStartKey"] = exclusive_start
    resp = T.crm_workflow_runs.query(**kwargs)
    runs = [_run_to_out(item) for item in resp.get("Items", [])]
    return WorkflowRunListOut(runs=runs, cursor=encode_cursor(resp.get("LastEvaluatedKey")))

## 5. Detailed Behavior & Edge Cases

### 5.1 Rule creation validation

`POST /ui/admin/crm/workflow/rules` delegates to `workflow_rules.create_rule`, which:
1. Validates `target_module` against `TARGET_MODULES` — raises `ValueError` → 422.
2. Validates `trigger_type` against `TRIGGER_TYPES` — raises `ValueError` → 422.
3. Checks `len(conditions) <= S.crm_workflow_max_conditions_per_rule` — raises `OverflowError` → 507 (Insufficient Storage, indicating a configuration limit).
4. Checks `len(actions) <= S.crm_workflow_max_actions_per_rule` — raises `OverflowError` → 507.
5. Writes rule to DDB, emits `audit_event("crm_workflow_rule.created", actor.sub, rule_id=...)`.

The router translates `ValueError` → 422 and `OverflowError` → 507. Other exceptions propagate as 500.

### 5.2 Partial update (PATCH)

`WorkflowRuleUpdateIn` uses `model_dump(exclude_unset=True)` to produce only the fields the caller supplied. The router passes these as `**fields` to `workflow_rules.update_rule(rule_id, updated_by=actor.sub, **fields)`. Fields not supplied are unchanged in DDB. If the caller supplies an empty dict (all fields optional and none sent), a 422 is raised with `detail="No fields to update"`.

### 5.3 Enable / disable idempotency

`POST /rules/{rule_id}/enable` calls `enable_rule(rule_id, actor=actor.sub)`. The service performs an unconditional `update_item` setting `enabled=True` — calling it on an already-enabled rule is a no-op (returns the current item unchanged). No error is raised. The audit event is emitted regardless so the admin audit trail reflects every intent.

### 5.4 Delete while rules are actively firing

`DELETE /rules/{rule_id}` is a hard-delete (removes the DDB item). The action executor (`app/services/workflow_action_executor.py`) checks `if not rule or not rule["enabled"]` at the top of `execute_crm_workflow_action` — if the rule has been deleted between enqueue and execution, `get_rule` returns `None` and the executor exits silently, logging a `rule_deleted_mid_execution` warning. No error is surfaced to the caller. This is the same graceful degradation used by the audit export worker when a schedule is deleted mid-run.

### 5.5 Run history pagination

`GET /rules/{rule_id}/runs` uses `ScanIndexForward=False` so items are returned newest-first. The SK structure `RUN#{started_at:010d}#{run_id}` guarantees that lexicographic descending order equals reverse-chronological order because `started_at` is zero-padded to 10 digits (covers timestamps up to year 2286). The cursor encodes the DDB `LastEvaluatedKey` opaquely via `encode_cursor` (`app/core/cursor.py:94`) and is validated on decode via HMAC (`decode_cursor`, `app/core/cursor.py:103`). A tampered or expired cursor decodes to `None`, causing the query to restart from the beginning (safe degradation).

### 5.6 Drip sequence deletion with active enrolments

`DELETE /drip-sequences/{sequence_id}` removes the sequence definition row. Enrolment rows (`ENROL#{sequence_id}`) are not cascade-deleted. The stage executor checks `enrolment["stopped"]` before sending each email; once the definition row is gone, `get_sequence` returns `None`, and the stage executor exits with `skipped` rather than `error`. Administrators should disable a sequence's parent rule before deleting a drip sequence definition — this is documented in the Open Questions section (§10).

### 5.7 Flag-off behaviour

When `CRM_WORKFLOW_ENABLED=0` (or when the router is not included):
- All 13 endpoints return 404.
- Frontend nav item is hidden (Sidebar filter returns `false` for the workflow path).
- No background workers start (WFL-005 `start_workflow_scheduler_task` self-gates).
- No DDB reads or writes occur from this router.
- Existing service files (`tickets.py`, `contacts.py`) are unmodified; on-save hooks installed by WFL-004 check `S.crm_workflow_enabled` at the top and return 0 without any DDB call.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No dev_mode branch in business logic

The router and service layer contain zero `if S.dev_mode` branches. DDB reads and writes work identically against DynamoDB Local (port 8001) and production DynamoDB. Email dispatch called from action executors (not directly from this router) goes through `alerts.send_alert_email` (`app/services/alerts.py:459`) which already handles dev-mode (writes to `S.dev_email_log`) vs prod (SES) transparently. This router does not call `send_alert_email` directly.

### 7.2 CSRF enforcement

All mutating endpoints (`POST`, `PATCH`, `DELETE`) use `Depends(require_admin_or_root_csrf)` (`app/auth/policy.py:100`). This enforces CSRF for cookie-auth (browser) sessions while leaving Bearer-auth API clients unaffected, matching the pattern at `app/routers/admin_notifications.py:54`.

### 7.3 Audit trail

Every state-changing operation emits an `audit_event` via `app/services/alerts.audit_event` (`app/services/alerts.py:644`). The actor's `user_sub` (from `AuthenticatedUser.sub`) is recorded on every create, update, delete, enable, and disable action. Audit events are written to `T.alerts` with `event` strings in the `crm_workflow_rule.*` namespace. This matches the pattern used by `app/services/workflow_rules.py` (WFL-002) — the router passes `actor.sub` as `created_by` / `updated_by` / `deleted_by` / `actor` to the service functions which in turn call `audit_event`.

### 7.4 Input validation

`WorkflowRuleCreateIn.name` is `max_length=200`; `description` is `max_length=2000`. `trigger_config`, `conditions`, and `actions` are validated structurally by `workflow_rules.create_rule` (WFL-002). The router performs no extra sanitisation — Pydantic handles all field-level validation. DDB's 400KB item size limit provides a hard backstop for `conditions` and `actions` list growth above the configurable limits.

### 7.5 Authorisation scope

Only ADMIN (with `admin_profile.type == "general"`) and ROOT roles can access these endpoints. Scoped admins (`type == "scoped"`) are denied because `require_admin_or_root` calls `require_roles(user, {Role.ADMIN, Role.ROOT})` which checks the role value only (`app/auth/policy.py:67`). The frontend additionally guards the nav item with `canAccessGeneralAdminControls` (`frontend/src/lib/adminCapabilities.ts:47`) which requires `profile.type === "general"`.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact when flag is off

When `CRM_WORKFLOW_ENABLED=0` (the default for all existing deployments), `app/main.py` does not call `app.include_router(workflow_rules_router)`. No routes are registered, the OpenAPI schema is unchanged, and no background loops start. Existing E2E tests, unit tests, and API consumers are unaffected.

### 8.2 No schema changes to existing tables

WFL-009 reads from and writes to `crm_workflow_rules` and `crm_workflow_runs` — both tables are new (WFL-001) and contain no existing data in production. No `UpdateTable` or data migration is required. In dev, `just restart` recreates both tables from scratch via `scripts/local-ddb-init.py`.

### 8.3 Frontend backward compatibility

The lazy-loaded `WorkflowRulesPage` and `WorkflowRuleEditor` components are only imported when the user navigates to `/admin/workflow/rules`. Non-admin users never see the route or the nav item. No existing page imports are modified.

### 8.4 Enabling in production

Deployment order:
1. Deploy the backend with `CRM_WORKFLOW_ENABLED=0` (no-op).
2. Verify WFL-001 DDB table creation has run in the new deployment (check `crm_workflow_rules` and `crm_workflow_runs` exist via AWS console or `describe_table`).
3. Set `CRM_WORKFLOW_ENABLED=1` in the environment and restart the backend.

No data backfill is required. No existing workflows will fire until an admin creates the first rule.

## 10. Open Questions / Assumptions

1. **Scoped-admin access.** The spec assumes workflow rule management requires a `general` admin profile (not scoped). If a `workflow_admin` scope is added later, `require_admin_or_root_csrf` can be swapped for a scoped variant without changing the service layer. For now `general` admin is the minimum.

2. **Drip sequence deletion with active enrolments.** No cascade-delete is specified. The current design leaves orphaned enrolment rows (`ENROL#`) in `T.crm_workflow_rules`; the stage executor handles missing sequences gracefully by exiting with `skipped`. A separate cleanup job is out of scope for this ticket. Admins should disable the parent rule before deleting a drip sequence. This should be surfaced as a UI warning in the editor.

3. **`actions` config textarea vs structured input.** The ticket specifies a JSON `config` textarea for MVP. This means the frontend does zero validation on the per-action config dict. Invalid configs will be caught by the action executor at runtime and logged as `skipped` or `error` in the run log. A structured UI for each action type (e.g., a field-picker for `modify_field`) is a follow-up, out of scope here.

4. **Run log retention.** `T.crm_workflow_runs` items currently have no TTL attribute. High-frequency `on_save` rules against busy modules (e.g., every ticket update) could produce millions of run rows. A TTL field (`expires_at`) should be added in WFL-001 or a follow-up ticket. This spec assumes run rows are retained indefinitely for MVP.

5. **Run history for deleted rules.** After `DELETE /rules/{rule_id}`, the run history rows remain in `T.crm_workflow_runs` under `PK=RULE#{rule_id}`. The `GET /rules/{rule_id}/runs` endpoint returns 404 when the rule is gone (the router checks `get_rule` before querying runs). A separate "orphaned run history" query is out of scope.

6. **`CRM_WORKFLOW_ENABLED=1` in E2E test environment.** The E2E test suite assumes the flag is enabled. The setup scripts (`e2e_admin_session_setup.py`) may need a corresponding env-var override. If the backend is started with the flag off, section 70–73 tests will all fail with 404. This is a known pre-condition.

### 11.2 Sibling CRM tickets (context only, no code dependency)

This ticket does not directly extend the following but interacts conceptually:

- **PARTY_CRM (PTY) tickets** — the `contact` and `lead` modules targeted by workflow rules overlap with the Party/CRM contact data model. Rule conditions that reference contact fields (e.g., `field="email_domain"`) depend on the field schema established by PTY tickets.

- **PRD (Catalog Depth) tickets** — the `order` module target for workflow rules depends on PRD's order data model. `on_save` hooks on orders (WFL-004) are not implemented until the PRD order service exposes the required write paths.
- **OFB (OfBiz Commerce) tickets** — same dependency as PRD for order-module workflow triggers.
