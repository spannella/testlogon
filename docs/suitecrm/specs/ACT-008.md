# ACT-008 — CRM Tasks module — standalone task management

**Ticket type:** Feature
**Priority:** P1
**Estimate:** 3d
**Sub-flag:** `crm_tasks_enabled` (default OFF) — requires parent `crm_activities_enabled` from ACT-001

---

## 1. Summary & Goal

ACT-008 introduces a standalone CRM Tasks module: a dedicated CRUD service and router for user-authored task records carrying subject, a five-state status state machine, priority tier, due date, optional assignee delegation, and an optional opaque link to a future CRM entity (contact, lead, account, opportunity). Tasks are the direct analog of SuiteCRM's Tasks module as described in `docs/suitecrm/CRM_ACTIVITIES_TICKETS.md` lines 6–8.

The deliverable is:

- A new `app/services/crm_tasks.py` service against the `crm_tasks` DynamoDB table (scaffolded by ACT-001).
- A new `app/routers/crm_tasks.py` router mounted at `/ui/crm/tasks`, gated by `S.crm_activities_enabled and S.crm_tasks_enabled`.
- Pydantic models `CrmTaskCreateIn`, `CrmTaskUpdateIn`, `CrmTaskOut` added to `app/models.py`.
- A React frontend page at `frontend/src/pages/crm-tasks/` with status filter tabs, create/edit dialog, priority badge, and due date display.
- A `GET /ui/crm/tasks/by-entity` endpoint for entity-linked task retrieval (needed by ACT-009 timeline callers).

With both flags off the platform is byte-for-byte unchanged: no new routes answer, no DynamoDB writes occur, and no startup tasks are registered.

## 3. Data Model

### 3.1 DynamoDB table: `crm_tasks`

Provisioned by ACT-001. ACT-008 reads and writes it; it does not alter the table definition.

```
Table name : S.crm_tasks_table_name  (default "crm_tasks")
PK         : user_sub  (S) — the task owner / creator
SK         : sk        (S) — value TASK#{inverted_due_ts:013d}#{task_id}
```

Inverted sort key formula: `9999999999999 - due_date_ts` when `due_date_ts` is set; otherwise `9999999999999 - created_at`. This produces the same reverse-chronological default ordering used in `call_history.py:30–31`.

**GSI ByStatus** — for listing all tasks across all users in a given status, ordered by due date ascending:

```
GSI1PK : STATUS#{status}   (S)
GSI1SK : due_date_ts       (N)   ← attr_types={"GSI1SK": "N"} required (ACT-001)
```

**GSI ByAssignee** — for listing all tasks assigned to a given user, ordered by due date ascending:

```
GSI2PK : ASSIGNEE#{assignee_sub}  (S)
GSI2SK : due_date_ts              (N)   ← attr_types={"GSI2SK": "N"} required (ACT-001)
```

Both GSIs are sparse: rows without `due_date_ts` use `created_at` as the fallback numeric value for the GSI sort key so every row always participates in the index.

**`create_task` behavior:**

1. Generate `task_id = uuid.uuid4().hex`; `ts = now_ts()`.
2. Compute `sort_ts = body.due_date_ts if body.due_date_ts else ts`.
3. Build item with all fields; set `GSI1PK = _gsi1_pk(body.status.value)`, `GSI1SK = sort_ts`.
4. If `body.assignee_sub` is set: also write `GSI2PK = _gsi2_pk(body.assignee_sub)`, `GSI2SK = sort_ts`. Best-effort validate the assignee exists via `get_profile_identity(body.assignee_sub)` — if the profile lookup raises, still write the task (opaque sub acceptable; PTY-level validation is a follow-up).
5. `T.crm_tasks.put_item(Item=item)`.
6. If `body.assignee_sub and body.assignee_sub != user_sub`: call `write_alert(body.assignee_sub, event="crm_task_assigned", outcome="info", title=f"New task assigned: {body.subject[:60]}", details={"task_id": task_id, "assigned_by": user_sub})` wrapped in `try/except`.
7. If `body.linked_entity_type`: call `_maybe_record_timeline(entity_type, entity_id, "task", task_id, user_sub, f"Task created: {body.subject[:80]}")` (see below).
8. Return `_item_to_out(item)`.

**`get_task` behavior:**

1. Query `T.crm_tasks` on `PK=user_sub`, `FilterExpression=Attr("task_id").eq(task_id)`, `Limit=100`. (A GSI on `task_id` is not necessary at this volume — the SK already encodes `task_id` so a single-page query with a filter is acceptable. If a direct key lookup is preferred, the SK can be reconstructed by scanning for the SK prefix `TASK#` and filtering on `task_id`.)
2. Return first matching item after `_item_to_out`, or `None`.

**Alternative get by direct key** (preferred for production efficiency): store a second forward-index row `PK=TASKIDX#{task_id}`, `SK=META` pointing to `(user_sub, sk)` — query that row to resolve the primary key, then do a direct `get_item`. Whether to implement the index row is left as an implementation choice; the acceptance criteria only require correctness, not a specific lookup strategy. This spec recommends the simpler filter approach for the initial implementation.

**`update_task` behavior:**

1. Call `get_task(user_sub, task_id)` — return `None` (→ 404) if missing.
2. Apply only the non-`None` fields from `updates`.
3. Validate status transition: if `updates.status` is set and differs from current status, assert the transition is in `_VALID_TRANSITIONS[current_status]`; raise `ValueError("Invalid status transition")` (→ 400) if not.
4. Recompute `sk` and GSI keys if `due_date_ts` changes (requires `delete_item` of the old SK then `put_item` with the new SK — a two-step atomic-ish write; see Section 5 for edge cases).
5. Update `updated_at = now_ts()`.
6. If status changed: call `audit_event("crm_task_status_changed", user_sub, request, task_id=task_id, old_status=old, new_status=new_status)`.
7. If status changed to `completed` and `linked_entity_type` is set: call `_maybe_record_timeline(entity_type, entity_id, "task", task_id, user_sub, f"Task completed: {subject[:80]}")`.
8. If `assignee_sub` changed: notify new assignee via `write_alert` as in `create_task`.

**`delete_task` behavior:**

1. `get_task(user_sub, task_id)` — 404 if missing.
2. `T.crm_tasks.delete_item(Key={"user_sub": user_sub, "sk": item["sk"]})`.
3. Return `True`.

**`list_tasks` routing logic:**

- If `assignee_sub` is provided: query `ByAssignee` GSI with `KeyConditionExpression=Key("GSI2PK").eq(_gsi2_pk(assignee_sub))`. The caller can be the assignee themselves or a user listing their own assignments — no additional auth check at the service layer.
- Else if `status` is provided: query `ByStatus` GSI with `KeyConditionExpression=Key("GSI1PK").eq(_gsi1_pk(status))`.
- Else: query primary key `Key("user_sub").eq(user_sub)` with `begins_with(sk, "TASK#")`.
- All paths use `Limit=limit`, `ExclusiveStartKey=decode_cursor(cursor)`, and return `{"items": [...], "next_cursor": encode_cursor(resp.get("LastEvaluatedKey"))}`.

**`list_tasks_for_entity` behavior:**

- Query primary key `Key("user_sub").eq(user_sub)` with `begins_with(sk, "TASK#")` and `FilterExpression=Attr("linked_entity_type").eq(entity_type) & Attr("linked_entity_id").eq(entity_id)`.
- Important: DynamoDB `FilterExpression` does not reduce the page size before consuming `Limit` capacity (CLAUDE.md gotcha). Use a loop over `LastEvaluatedKey` — continue fetching pages until `limit` results are accumulated or pages are exhausted. Cap total pages at 20 to avoid unbounded scans.

## 5. Detailed Behavior & Edge Cases

### 5.1 Status state machine enforcement

The five-state machine is:

```
not_started ──→ in_progress, deferred, waiting, completed
in_progress ──→ not_started, completed, deferred, waiting
completed   ──→ not_started, in_progress
deferred    ──→ not_started, in_progress
waiting     ──→ not_started, in_progress
```

`create_task` accepts any initial status — the state machine only constrains `update_task` transitions. A `400` with body `{"code": "invalid_status_transition", "from": "...", "to": "..."}` is returned on an illegal move. The forbidden transition `completed → deferred` (for example) is intentional: a completed task must be reopened to `not_started` or `in_progress` before it can be deferred.

### 5.2 SK rebuild on due_date_ts change

The SK encodes the inverted due date for DynamoDB sort order. If `updates.due_date_ts` changes the sort position, the old item must be deleted and a new item written at the new SK. This is a two-step operation:

1. `T.crm_tasks.delete_item(Key={"user_sub": user_sub, "sk": old_sk})`.
2. Compute `new_sk = _make_sk(_inverted(new_due_date_ts), task_id)`.
3. `T.crm_tasks.put_item(Item={...new item with new_sk...})`.

A crash between steps 1 and 2 would lose the item. To mitigate: perform step 2 first (put at new SK), then step 3 (delete old SK). A crash between the two writes results in a duplicate (two SK values for the same `task_id`), which `get_task` must handle by returning the item with the later `updated_at`. The `list_tasks` endpoint's filter on `task_id` would return both; callers should de-duplicate by `task_id`. This is an acceptable eventual-consistency window given DynamoDB local's non-distributed nature.

If `due_date_ts` is unchanged, no SK rebuild is needed — a simple `update_item` expression on the non-key attributes suffices.

### 5.3 Assignee validation

`assignee_sub` is accepted as any non-empty string without hard-enforcing that the user exists in `T.users`. The `get_profile_identity` call in `create_task` is advisory: if it raises (user not found), the task is still created with the opaque `assignee_sub` and no notification is sent. This mirrors the `linked_entity_id` opaqueness design and avoids a hard cross-domain dependency before PTY ships.

### 5.4 `list_tasks_for_entity` and FilterExpression page exhaustion

As noted in CLAUDE.md: DynamoDB applies `FilterExpression` after consuming `Limit` capacity. A table with 1000 tasks for `user_sub` of which only 3 link to `entity_id=X` may require many pages to retrieve all 3. The implementation must loop via `LastEvaluatedKey` and cap at 20 pages (returning whatever has been collected at that point with no `next_cursor`). A future ACT-007-style GSI on `linked_entity_type#linked_entity_id` can replace the scan once entity volume grows.

### 5.5 Missing due_date_ts

When `due_date_ts` is not provided, the GSI sort keys (`GSI1SK`, `GSI2SK`) use `created_at` as the fallback. This ensures every row participates in the GSIs — a sparse GSI that excludes tasks without due dates would cause `ByStatus` listing to silently omit them.

### 5.6 Assignee GSI cleanup on assignee removal

If `update_task` sets `assignee_sub=None` (clearing the assignee), the `GSI2PK` and `GSI2SK` attributes must be removed from the item using DynamoDB `REMOVE` expressions. Failure to do this leaves a stale GSI entry that makes the task appear in `list_tasks(assignee_sub=...)` for the old assignee.

### 5.7 Due date in the past

The API does not reject past due dates. A task can legitimately be created after the fact (e.g., logging a completed call-follow-up task retroactively). The frontend MAY show an "Overdue" badge when `due_date_ts < now()` and status is not `completed`.

### 5.8 Pagination on ByStatus / ByAssignee GSIs

Both GSIs include tasks from all users in the system, not just the authenticated user. When listing by `status` or `assignee_sub`, the caller receives tasks they may not own. This is intentional — CRM task delegation requires that a manager can list all tasks assigned to a report. Row-level ownership enforcement (only the owner or assignee can view a task) is a security hardening concern deferred to a future access-control ticket; this ticket applies only creator-side ownership checks on `update_task` and `delete_task` (the `user_sub` must match the item's `user_sub`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 dev/prod parity

There is no `dev_mode` branch anywhere in `crm_tasks.py` or `crm_tasks.py` router. All DynamoDB reads and writes go through the same `T.crm_tasks` handle (`_FloatSafeTable` proxy from `app/core/tables.py:29–66`) regardless of environment. The same table, same GSIs, same key expressions operate in both local DynamoDB (port 8001) and production DynamoDB. No mock path is introduced.

Email notifications via `write_alert` and `send_alert_email` already implement their own dev/prod split internally (`alerts.py:459–468`): dev mode writes to `S.dev_email_log`; prod sends SES. ACT-008 calls these primitives and inherits their parity without adding any branch.

### 7.2 Idempotency

`create_task` is not idempotent (each call produces a new `task_id`). Callers that need idempotency should check for an existing task by `subject` + `due_date_ts` before creating. `update_task` and `delete_task` are idempotent on repeated calls with the same input: PATCH with the same status returns the same item; DELETE of an already-deleted task returns 404 (not an error in idempotent retry semantics, but not a 200 either — callers should tolerate 404 on delete retry).

### 7.3 Ownership enforcement

`update_task` and `delete_task` call `get_task(user_sub, task_id)` which queries `PK=user_sub`. If `task_id` belongs to a different owner it will not be found (404) without any additional auth check — the primary key naturally enforces ownership. Assignees can view tasks via the `ByAssignee` GSI but cannot modify or delete them without the owner's `user_sub` match. This is sufficient for the initial implementation.

### 7.4 Input sanitization

`subject` is capped at 200 chars; `description` at 5000 chars. Both are stored as plain strings — no HTML/Markdown rendering at the service layer. If the frontend renders description as Markdown in the future, server-side sanitization would be required; that is out of scope for this ticket.

### 7.5 No money-out paths

This ticket introduces no financial operations. No calls to `refund_payment`, `settle_or_reverse_ledger`, or `new_ledger_entry` are made. The CRM task lifecycle does not touch billing.

## 10. Open Questions / Assumptions

**OQ-1: `get_task` lookup strategy.** The spec describes a scan-with-filter approach because the SK encodes the inverted due date, making direct lookup by `task_id` alone impossible without a reverse index. A forward-index row (`PK=TASKIDX#{task_id}`, `SK=META`) adds one extra write per create/delete but enables O(1) lookup. Decision deferred to implementer. Recommendation: use the forward-index approach for any deployment with >10k tasks per user.

**OQ-2: Cross-user task visibility via ByStatus GSI.** Currently `list_tasks(status=...)` returns tasks from all users globally (since the GSI PK is just `STATUS#{status}`). This may be undesirable if task privacy is required. Mitigation: add a `user_sub` FilterExpression to the GSI query when the caller wants their own tasks only. Alternatively, scope the GSI PK to `STATUS#{status}#{user_sub}` at the cost of losing the cross-user admin view. Assumed acceptable for the initial implementation given the flag-default-off state and CRM's typically single-tenant deployment.

**OQ-3: Conflict on SK rebuild.** The two-step write (put new SK, delete old SK) is not atomic. Implementing a DynamoDB Transaction (`transact_write_items`) would make it atomic at the cost of one extra DDB API call. Assumed acceptable tradeoff to defer transactions.

**OQ-4: PTY-level entity validation.** `linked_entity_id` is accepted as an opaque string. Once PTY-011 ships, the task service should optionally validate the entity exists in the Party CRM table. This is a soft dependency to be revisited when the PTY sprint lands.

**Assumption A-1:** ACT-001 is merged before ACT-008 is deployed. ACT-008 will fail at startup with a `ValidationException` if the `crm_tasks` table does not exist or lacks the GSI `attr_types={"GSI1SK": "N", "GSI2SK": "N"}` declarations.

**Assumption A-2:** `require_ui_session` from `app.services.sessions` (not from `app.auth.deps`) is the correct auth primitive for this router, matching the pattern in `app/routers/tickets.py:19`. The two are functionally equivalent for cookie-based UI sessions; `require_ui_session` from sessions.py returns `Dict[str, str]` while `get_authenticated_user` from deps.py returns `AuthenticatedUser`. The former is used consistently in the existing CRM-adjacent routers.

**Assumption A-3:** ACT-006 is NOT a hard prerequisite of ACT-008. `CallLogOut` (cited as the insertion anchor in Section 4.1) does not yet exist in `app/models.py` (grep confirmed zero matches). If ACT-006 is unmerged when ACT-008 ships, the new Pydantic models should be appended at the end of `app/models.py`.
