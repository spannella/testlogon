# KB-007 — Article tags / keywords (tag index + tag-scoped browse)

**Type:** Feature  **Priority:** P2  **Estimate:** 1 day  
**Ticket source:** `docs/suitecrm/CRM_KNOWLEDGE_BASE_TICKETS.md`, section "KB-007"

---

## 1. Summary & Goal

KB-007 adds a normalized keyword-tag system to the Knowledge Base. Admins assign a list of tags to any article; those tags are indexed so that the public portal can browse articles by tag and list the platform's most-popular tags. The implementation reuses the `TAG#{tag}` index pattern that already exists in `app/routers/newsfeed.py:440` (`_write_tag_index`) and the `TAG_STATS` counter row at `app/routers/newsfeed.py:456`.

Concrete deliverables:

1. Three private helpers on `app/services/kb_articles.py` — `_normalize_tag`, `_write_kb_tag_index`, and `_delete_kb_tag_index` — that write and delete `TAG#{tag}` index rows and maintain `KB_TAG_STATS` counters in `crm_kb_articles`.
2. Three public methods on `KbArticleService` — `set_tags`, `list_articles_by_tag`, and `list_popular_tags`.
3. Three endpoints on `app/routers/kb_articles.py`:
   - `PUT /kb/articles/{article_id}/tags` (admin-only, replace tag set)
   - `GET /public/kb/tags` (no auth, popular tags list)
   - `GET /public/kb/tags/{tag}/articles` (no auth, cursor-paginated articles for a tag)
4. Two Pydantic models in `app/models.py`: `KbSetTagsReq` and `KbTagOut`.
5. Three entries in `API_KEY_ROUTE_EXEMPTIONS` for the public routes.

With `KNOWLEDGE_BASE_ENABLED=0` (the default), all three endpoints return 404 and the service is never invoked. The platform is byte-for-byte identical to its pre-KB-007 state when the flag is off. No existing table, file, or endpoint is modified.

## 2. Context & Current State

### 2.1 Tag index pattern in newsfeed

`app/routers/newsfeed.py:440–462` defines the canonical tag-indexing primitives used across the platform. Two key structures are written per tagged entity:

**Per-entity tag row** (one per tag per post):
```python
{"pk": f"TAG#{tag}", "sk": f"{created_at}#POST#{post_id}", "post_id": post_id, "author_id": user_id, "created_at": created_at}
```
Written via `batch_writer()` on the application table.

**TAG_STATS counter row** (one per unique tag):
```python
Key={"pk": "TAG_STATS", "sk": f"TAG#{tag}"},
UpdateExpression="SET #n = if_not_exists(#n, :z) + :one, last_used_at = :now",
ExpressionAttributeNames={"#n": "count"},
ExpressionAttributeValues={":one": 1, ":z": 0, ":now": created_at},
```
At `app/routers/newsfeed.py:455–462`.

KB-007 replicates this pattern on `crm_kb_articles` with an `ARTICLE#`-prefixed SK and a separate `KB_TAG_STATS` partition key so that KB tag rows never collide with newsfeed `TAG#` rows (which live on a different DynamoDB table: `app/services/newsfeed_feed.tbl`).

### 2.2 Tag normalization pattern

`app/routers/newsfeed.py:414` defines:
```python
_TAG_VALID_RE = re.compile(r"^[a-z][a-z0-9_]{0,49}$")
```
And `app/routers/newsfeed.py:430–437` implements `_normalize_tags`: lowercase, strip leading `#`, filter by regex. KB-007 adapts this but with a more permissive character set (`[a-z0-9_-]`) to also allow hyphens, which are common in technical KB keywords such as `two-factor`, `sign-in`, etc. The max tag length is 50 characters and the max tag count per article is 20 — matching the newsfeed `_MAX_TAGS_PER_POST = 20` at `app/routers/newsfeed.py:415`.

### 2.3 Cursor pagination primitive

`app/core/cursor.py:94–101` provides `encode_cursor(last_evaluated_key)` → opaque HMAC-signed string; `app/core/cursor.py:103–131` provides `decode_cursor(cursor)` → `LastEvaluatedKey | None`. These are used throughout the platform (e.g., `app/routers/tickets.py`) for DynamoDB-backed pagination. KB-007 uses them on `list_articles_by_tag` to pass `ExclusiveStartKey` through between pages.

### 2.4 Atomic ADD pattern

`app/services/stories.py:158–162` demonstrates the canonical `ADD view_count :one` update expression used throughout the platform for atomic counter increments:
```python
tbl.update_item(
    Key={"pk": f"STORY#{story_id}", "sk": "META"},
    UpdateExpression="ADD view_count :one",
    ExpressionAttributeValues={":one": 1},
)
```
The `KB_TAG_STATS` counter rows use the same `ADD` expression.

### 2.5 Auth dependency pattern

`app/services/sessions.py:330` defines `require_ui_session`, the standard cookie+CSRF session dependency used by all authenticated endpoints. Admin-only enforcement follows the pattern at `app/routers/tickets.py:207–208`:
```python
def _is_admin(user: AuthenticatedUser) -> bool:
    return normalize_role(user.role) in {Role.ADMIN, Role.ROOT}
```
raising `HTTPException(403)` when the caller is not ADMIN or ROOT.

### 2.6 API key route exemptions

`app/services/api_key_route_scope_registry.py:70` defines `API_KEY_ROUTE_EXEMPTIONS`, a dict of route-id strings → exemption metadata. Public KB portal routes are unauthenticated and must be listed here so they are not challenged for an API key when called outside a session.

### 2.7 Single-table DynamoDB layout for crm_kb_articles

CAS-001 (`docs/suitecrm/CRM_CASES_PORTAL_TICKETS.md`) created the `crm_kb_articles` table with `PK` (S) / `SK` (S) as the primary key. KB-001 added a `ByTag` GSI (`PK=tag`, `SK=created_at` N) to this same table. The tag index rows from KB-007 are direct primary-key items (`PK=TAG#{tag}`, `SK=ARTICLE#{article_id}`), not rows that belong to the `ByTag` GSI — the GSI is designed for a different query (articles projected by tag onto GSI), while the direct `PK=TAG#{tag}` rows use the table's native hash key so a standard DynamoDB `query` with `KeyConditionExpression=pk = :tag_pk` retrieves all articles for a tag efficiently without a GSI scan.

### 2.8 CAS-015 tags field stub

CAS-015 (`docs/suitecrm/specs/CAS-015.md`) specifies that each article META row carries a `tags` field (DynamoDB `StringSet`). KB-007 reads and replaces this field via `set_tags`. It does not write the raw `tags` field elsewhere — all tag state is dual-written: once to the `tags` StringSet on the META row (for article-level retrieval), and once as inverted index rows (`PK=TAG#{tag}`, `SK=ARTICLE#{article_id}`) for tag-scoped browse.

## 3. Data Model

All rows live in the `crm_kb_articles` table (`T.kb_articles`; handle wired by KB-001 via `app/core/tables.py`).

### 3.1 Tag index row (one per article per tag)

```
PK  = "TAG#{normalized_tag}"      (String)
SK  = "ARTICLE#{article_id}"      (String)
```

Projected fields stored on the row:
| Attribute | Type | Description |
|---|---|---|
| `article_id` | S | Article UUID — used to batch-fetch META rows |
| `tag` | S | Normalized tag string |
| `published_at` | N | Copy of the article's `published_at` timestamp (integer Unix seconds) — allows `ScanIndexForward=False` ordering |
| `status` | S | Copy of article `status` — used for client-side `published` filter when querying by tag |
| `title_snippet` | S | First 120 characters of article title — avoids extra `GetItem` for list rendering |
| `created_at` | N | Unix seconds when the tag row was written |

These rows use the table's native PK so `query(KeyConditionExpression=Key("pk").eq(f"TAG#{tag}"))` retrieves all articles for a tag with a single request. They are NOT projected onto the `ByTag` GSI (that GSI is reserved for article META rows that carry a `tag` attribute, added by KB-001 for a different access pattern).

### 3.2 KB_TAG_STATS counter row (one per unique tag)

```
PK  = "KB_TAG_STATS"    (String)
SK  = "TAG#{tag}"       (String)
```

| Attribute | Type | Description |
|---|---|---|
| `tag` | S | Normalized tag string |
| `count` | N | Total number of articles currently carrying this tag (atomic ADD/subtract) |
| `last_used_at` | N | Unix seconds of most recent tag assignment |

Queried with `query(KeyConditionExpression=Key("pk").eq("KB_TAG_STATS"))` to list all popular tags, then sorted client-side by `count` desc (tag count is small — typically < 500 unique tags).

### 3.3 No new DynamoDB table; no new GSI

KB-007 adds no new tables and no new GSIs. Tag index rows are standard primary-key items on the existing `crm_kb_articles` table. The `ByTag` GSI (PK=`tag`, SK=`created_at` N) introduced by KB-001 is not used by this ticket's query paths (it exists for a future KB-001 extension); KB-007 relies on the table's native hash-key query.

### 3.4 scripts/local-ddb-init.py

No change is required to `scripts/local-ddb-init.py` for this ticket. KB-001 already added the `ByTag` GSI with `attr_types={"created_at": "N", "published_at": "N"}` to the `crm_kb_articles` `TableDef`. The new tag index rows (`published_at` is N) and `KB_TAG_STATS` rows are primary-key items that do not project onto any new GSI, so no additional `attr_types` declaration is needed. Implementors must verify KB-001 has run before deploying KB-007.

## 4. API / Service Design

### 4.1 Service helpers (`app/services/kb_articles.py`)

#### `_normalize_tag(raw: str) -> str | None`

```python
_KB_TAG_RE = re.compile(r"^[a-z0-9][a-z0-9_-]{0,49}$")

def _normalize_tag(raw: str) -> str | None:
    tag = raw.lower().lstrip("#").strip()
    tag = re.sub(r"[^a-z0-9_-]", "-", tag).strip("-")
    if not _KB_TAG_RE.match(tag):
        return None
    return tag[:50]
```

Differences from `_normalize_tags` at `app/routers/newsfeed.py:430`: hyphens are allowed (common in KB keywords); leading digits are allowed (`2fa`, `3ds`); invalid characters are replaced with `-` rather than silently dropped (more predictable for admins). Returns `None` for strings that reduce to empty after normalization — those are silently dropped. Maximum normalized length 50 characters.

#### `_write_kb_tag_index(article_id: str, tags: list[str], published_at: int, status: str, title: str) -> None`

Batch-writes one `TAG#{tag}` / `ARTICLE#{article_id}` row per tag to `T.kb_articles` and increments each tag's `KB_TAG_STATS` counter. Uses `T.kb_articles.batch_writer()` for the row puts (mirrors `app/routers/newsfeed.py:444`). The `count` increment uses `ADD count :one` with `if_not_exists` initializer — identical to the `TAG_STATS` update at `app/routers/newsfeed.py:456–461`. Wrapped in a module-level `try/except` for the stats update; a stats failure must not prevent the index rows from being written.

Signature:
```python
def _write_kb_tag_index(
    article_id: str,
    tags: list[str],
    published_at: int,
    status: str,
    title: str,
) -> None: ...
```

#### `_delete_kb_tag_index(article_id: str, old_tags: list[str]) -> None`

Batch-deletes `TAG#{tag}` / `ARTICLE#{article_id}` rows for each tag in `old_tags`. Decrements `KB_TAG_STATS` counters via `ADD count :-1`, clamped to 0 with `ConditionExpression=Attr("count").gt(0)` (catches `ConditionalCheckFailedException` and ignores it — count already at zero). Wrapped in `try/except`; a stats failure must not prevent the index rows from being deleted.

Signature:
```python
def _delete_kb_tag_index(article_id: str, old_tags: list[str]) -> None: ...
```

### 4.2 KbArticleService public methods (`app/services/kb_articles.py`)

#### `KbArticleService.set_tags(article_id: str, tags: list[str], admin_sub: str) -> dict`

```python
def set_tags(
    self,
    article_id: str,
    tags: list[str],
    admin_sub: str,
) -> dict:
```

1. Fetches the article META row (`PK=ARTICLE#{article_id}`, `SK=META`). Raises `KbArticleNotFoundError` (404) if absent.
2. Normalizes each tag via `_normalize_tag`; silently drops `None` results; deduplicates; truncates list to 20 tags.
3. Reads current `tags` StringSet from the META row (default `[]`).
4. Diffs: `added = new_set - old_set`, `removed = old_set - new_set`.
5. For `added` tags: calls `_write_kb_tag_index(article_id, list(added), item["published_at"], item["status"], item["title"])`.
6. For `removed` tags: calls `_delete_kb_tag_index(article_id, list(removed))`.
7. Updates the META row's `tags` attribute to the new StringSet (or removes the attribute if the new set is empty, because DynamoDB does not store empty sets):
   ```python
   if new_tags:
       T.kb_articles.update_item(
           Key={"pk": f"ARTICLE#{article_id}", "sk": "META"},
           UpdateExpression="SET tags = :t, updated_at = :now",
           ExpressionAttributeValues={":t": new_tags_set, ":now": now_ts()},
       )
   else:
       T.kb_articles.update_item(
           Key={"pk": f"ARTICLE#{article_id}", "sk": "META"},
           UpdateExpression="REMOVE tags SET updated_at = :now",
           ExpressionAttributeValues={":now": now_ts()},
       )
   ```
8. Emits `audit_event("kb.article.tags_set", admin_sub, article_id=article_id, tags=list(new_tags_set))` via `app/services/alerts.audit_event` (`app/services/alerts.py:644`).
9. Returns `{"ok": True, "article_id": article_id, "tags": sorted(new_tags_set)}`.

Idempotent: calling `set_tags` with the same tag list twice leaves the article and index unchanged (the diff is empty on the second call).

#### `KbArticleService.list_articles_by_tag(tag: str, limit: int = 25, cursor: str | None = None) -> dict`

```python
def list_articles_by_tag(
    self,
    tag: str,
    limit: int = 25,
    cursor: str | None = None,
) -> dict:
```

1. Normalizes `tag` via `_normalize_tag`. Returns `{"items": [], "cursor": None}` if normalization yields `None` (unknown tag format → empty, not error).
2. Decodes `cursor` via `app/core/cursor.decode_cursor` (`app/core/cursor.py:103`). Returns 400 if cursor is non-empty and cannot be decoded.
3. Queries `T.kb_articles`:
   ```python
   kwargs = {
       "KeyConditionExpression": Key("pk").eq(f"TAG#{normalized_tag}"),
       "Limit": min(limit, 50),
       "ScanIndexForward": False,  # newest published_at first (SK is ARTICLE#..., so DDB sorts lexicographically; use FilterExpression + client sort for ordering)
   }
   if exclusive_start_key:
       kwargs["ExclusiveStartKey"] = exclusive_start_key
   resp = T.kb_articles.query(**kwargs)
   ```
   Note: because SK is `ARTICLE#{article_id}` (a UUID string), `ScanIndexForward=False` gives lexicographic reverse-UUID order, not `published_at` order. Client-side sort by `published_at` desc from the projected field on each tag row is therefore applied after the query. This is acceptable for the tag-browse use case where `limit` is at most 50. Operators who need strict `published_at`-sorted pagination across many pages should use the `ByTag` GSI (KB-001) in a future enhancement.
4. Client-side filters `status == "published"` (tag rows may point to articles that were later expired or unpublished). Only published articles are returned to the public portal.
5. Returns:
   ```python
   {
       "items": [KbArticleSummaryOut-compatible dicts from tag row projected fields],
       "cursor": encode_cursor(resp.get("LastEvaluatedKey")),
   }
   ```

#### `KbArticleService.list_popular_tags(limit: int = 50) -> list[dict]`

```python
def list_popular_tags(self, limit: int = 50) -> list[dict]:
```

1. Queries `T.kb_articles` with `KeyConditionExpression=Key("pk").eq("KB_TAG_STATS")`, no limit (tag count is expected to be < 500). Does not paginate — the stats partition is bounded.
2. Returns items sorted by `count` desc, truncated to `limit`, each as `{"tag": str, "count": int, "last_used_at": int}`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Tag normalization edge cases

| Input | Output | Reason |
|---|---|---|
| `"  #Billing  "` | `"billing"` | Strip whitespace, strip `#`, lowercase |
| `"two-factor"` | `"two-factor"` | Hyphen retained |
| `"3ds"` | `"3ds"` | Leading digit allowed |
| `"RESET PASSWORD"` | `"reset-password"` | Space replaced with `-` |
| `"_internal"` | `None` → dropped | Must start with `[a-z0-9]` |
| `""` | `None` → dropped | Empty string |
| `"a" * 60` | `"a" * 50` | Truncated to 50 chars |
| `"billing!!!"` | `"billing---"` then strip trailing `-` → `"billing"` | Non-alphanumeric/hyphen/underscore replaced; trailing hyphens stripped |

After normalization any tag that does not match `_KB_TAG_RE` is silently dropped. The endpoint never raises 422 for individual bad tags — it normalizes what it can and ignores the rest.

### 5.2 Empty-set call (`tags: []`)

`set_tags` with `tags=[]` removes all existing tags. The full `old_set` goes into `removed`; `_delete_kb_tag_index` is called for all of them; the META row's `tags` attribute is `REMOVE`d. `list_articles_by_tag` for any of those tags will return an empty `items` list after the tag rows are deleted.

### 5.3 Idempotent re-tag

Calling `set_tags` with exactly the same set of (post-normalization) tags that the article already carries produces an empty diff. Neither `_write_kb_tag_index` nor `_delete_kb_tag_index` is called. The META row's `updated_at` is still refreshed. The audit event is still emitted (admin intent to confirm the tags is auditable).

### 5.4 Article expiry / status change interaction

`set_tags` writes the article's current `status` onto each tag index row as a projected field. When KB-002's `expire_article` is called, it does NOT automatically call `_delete_kb_tag_index` — KB-007 does not modify KB-002. Instead, `list_articles_by_tag` client-side filters `status == "published"` on the projected `status` field of each tag row, so expired articles are silently omitted from tag-browse results without any index cleanup.

An admin who wants to clean up tag index rows for expired articles should call `set_tags(article_id, [], admin_sub)` explicitly; this is an operational hygiene step, not a correctness requirement.

Future tickets (such as KB-002 revision or a dedicated tag-cleanup task) may wire `_delete_kb_tag_index` into the expiry path; this ticket leaves that to a follow-up.

### 5.5 Projected field staleness

The `title_snippet` and `published_at` copied onto tag index rows may become stale if the article's title or publish timestamp changes after tagging. `set_tags` refreshes the tag rows for the tags in `added` (i.e., newly added tags) but not for unchanged tags. Callers who update an article title should call `set_tags` again with the same tag list to refresh projections. The `KbArticleService.update_article` method (KB-010) should be extended to call `_write_kb_tag_index` with the new title when the title changes; that wire-up is out of scope for KB-007 and should be tracked as a follow-up.

### 5.6 `KB_TAG_STATS` count accuracy

`KB_TAG_STATS` counts are best-effort. The `_delete_kb_tag_index` decrement uses a `ConditionExpression=Attr("count").gt(0)` guard and swallows `ConditionalCheckFailedException` so the count never goes negative, but it can drift if tag index rows are deleted outside the normal `set_tags` flow (e.g., direct DynamoDB repair). `list_popular_tags` returns whatever is stored; no correctness guarantee is provided. This matches the approach used by the newsfeed `TAG_STATS` at `app/routers/newsfeed.py:453–462`.

### 5.7 Pagination correctness for `list_articles_by_tag`

DynamoDB's `Limit` applies before `FilterExpression` (CLAUDE.md gotcha: "DDB FilterExpression doesn't reduce page size"). Because KB-007 applies a client-side `status == "published"` filter after fetching (not a DDB FilterExpression), the effective number of returned items per page may be less than `limit` even when more pages exist. Callers must continue paginating as long as `cursor` is non-null, regardless of how few items are in the current page. The router's max `limit` is capped at 50 to bound per-request DDB reads.

### 5.8 Route ordering constraint

`GET /public/kb/tags` and `GET /public/kb/tags/{tag}/articles` must be declared before `GET /public/kb/articles/{article_id}` and before any other `/{article_id}` route in the FastAPI router, and `PUT /kb/articles/{article_id}/tags` must be declared before any generic `PUT /kb/articles/{article_id}` route if one exists. This prevents FastAPI's declaration-order path matching from treating the literal word `tags` as an article ID (per `CRM_KNOWLEDGE_BASE_TICKETS.md:27`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

KB-007 contains no `if S.dev_mode:` branch. The code path for `_write_kb_tag_index`, `_delete_kb_tag_index`, `set_tags`, `list_articles_by_tag`, and `list_popular_tags` is identical in development (moto-backed DynamoDB Local on `http://localhost:8001`) and production (real DynamoDB). The `T.kb_articles` handle is wired from `S.kb_articles_table` at startup in both environments (`app/core/tables.py`; KB-001 pattern mirrors `T.tickets` at `app/core/tables.py:140`).

### 7.2 Idempotency

`set_tags` is idempotent: calling it twice with identical (post-normalization) tag lists produces no DynamoDB writes beyond the `updated_at` timestamp refresh on the META row. `_write_kb_tag_index` can be called multiple times for the same `(tag, article_id)` pair — each call overwrites the existing tag row via `put_item` (no conditional, so repeated puts are safe). `_delete_kb_tag_index` is also idempotent: deleting a non-existent row is a no-op in DynamoDB.

### 7.3 Security

**Admin-only write**: `PUT /kb/articles/{article_id}/tags` requires `role in {ADMIN, ROOT}`. Any other caller receives HTTP 403. Role enforcement follows `app/auth/roles.py:60–61` (`role_allows_admin_features`).

**No PII in tag index rows**: Tag index rows contain only `article_id`, `tag`, `published_at`, `status`, `title_snippet`, and `created_at`. No user-sub or session data is stored.

**Tag content**: Normalized tags contain only `[a-z0-9_-]` characters, so they are safe for use as DynamoDB key attributes and in URL path segments without additional encoding. SQL injection and XSS via tag strings are not applicable (DynamoDB, and tags are displayed escaped by the React frontend).

**Public route**: `GET /public/kb/tags` and `GET /public/kb/tags/{tag}/articles` require no authentication and return only published article metadata. The `status == "published"` filter is applied server-side, so draft or expired articles are never exposed to unauthenticated callers even if their tag rows remain in the index.

**`audit_event` on every admin write**: `set_tags` calls `app/services/alerts.audit_event("kb.article.tags_set", admin_sub, article_id=..., tags=...)` (`app/services/alerts.py:644`) for every call, including no-op re-tags (admin intent is auditable regardless).

## 8. Backward Compatibility & Migration

### 8.1 Zero impact when flag is off

With `KNOWLEDGE_BASE_ENABLED=0` (the default), no routes are registered, no service code runs, and no DynamoDB reads or writes are attempted. Existing articles in `crm_kb_articles` (from CAS-015 / KB-001 through KB-006) are untouched. The `tags` StringSet field on article META rows may already be set by CAS-015's `create_article` or `update_article`; KB-007 reads and manages it but does not require it to exist (a missing `tags` attribute is treated as an empty set).

### 8.2 Existing articles have no tag index rows

When `KNOWLEDGE_BASE_ENABLED` is first enabled, existing published articles have `tags` fields (potentially set by admins directly via earlier KB operations) but no corresponding `TAG#{tag}` index rows or `KB_TAG_STATS` entries. Tag-browse queries will return zero results for those tags until an admin re-saves tags via `PUT /kb/articles/{article_id}/tags`. This is acceptable for a P2 feature at initial rollout. A backfill script (`scripts/kb_tag_backfill.py`) is out of scope for KB-007 but should be added as a follow-up if the platform has a significant existing KB article corpus at launch.

### 8.3 crm_kb_articles table schema

No schema change is required. The new tag index rows (`PK=TAG#{tag}`) and `KB_TAG_STATS` rows use only the existing `pk` (S) / `sk` (S) primary key. No new GSI is added. `just restart` is not required after deploying KB-007.

## 10. Open Questions / Assumptions

1. **Tag row ordering**: The spec uses client-side sort by `published_at` from the projected field on tag rows, rather than a DynamoDB-native sort, because the tag row SK is `ARTICLE#{uuid}` (lexicographic, not numeric). This is acceptable for `limit ≤ 50` pages but would not scale to tag-browse lists requiring strict chronological pagination across hundreds of results. If strict ordering becomes a requirement, the tag row SK should be changed to `{published_at:012d}#{article_id}` — a breaking schema change that would require a backfill. This is captured here as a known trade-off.

2. **Tag index staleness on article update**: When an article's title changes (KB-010 `update_article`), the `title_snippet` on existing tag rows becomes stale. KB-007 does not wire `_write_kb_tag_index` into KB-010's `update_article`. The assumption is that title snippet staleness is tolerable in v1 (it does not affect correctness — a full article fetch is needed for rendering). A KB-010 follow-up should call `_write_kb_tag_index` for the current tag set when title changes.

3. **`ByTag` GSI (KB-001) vs. direct PK query**: KB-001 added a `ByTag` GSI (PK=`tag`, SK=`created_at` N) to `crm_kb_articles`, presumably for article META rows that carry a `tag` attribute. KB-007 does not use this GSI; it uses direct table queries on `PK=TAG#{tag}`. This avoids the GSI attribute projection complexity and keeps the index pattern consistent with newsfeed. The GSI can be used in a future enhancement for ordered, paginated tag-scoped queries with native DynamoDB sort.

4. **Tag normalization contract**: The `_KB_TAG_RE` regex `^[a-z0-9][a-z0-9_-]{0,49}$` is slightly more permissive than the newsfeed `_TAG_VALID_RE` `^[a-z][a-z0-9_]{0,49}$`. This is intentional for KB use cases but may create UX inconsistency if the frontend offers a shared tag-input component. Assumed acceptable because KB and newsfeed are distinct surfaces.

5. **Backfill for existing articles**: Assumed not required at initial deployment — the tag system is new and no articles will have stale tag index rows unless someone set the `tags` field on article META rows before KB-007 was deployed (possible via direct DDB writes during development). The backfill is a follow-up item.
