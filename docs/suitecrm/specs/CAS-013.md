## 1. Summary & Goal

CAS-013 wires inbound email into the ticket system. An email sent to the configured support address (e.g. `support@example.com`) is routed by AWS SES to an SNS topic, which delivers an HTTPS POST to `POST /internal/ses/inbound` on the platform backend. The handler parses the raw RFC-2822 email, creates or threads a ticket, and fires the standard ticket notification path — all with no code changes to the existing `app/routers/tickets.py` or `app/services/tickets.py`.

Three creation scenarios are covered:

1. **Known sender** — submitter email matches a platform user via a `T.users` GSI lookup; ticket is created under that `user_sub`.
2. **Unknown/guest sender** — no matching platform user; ticket is created under a synthetic owner key `guest:{email}` with `submitter_email` persisted on the META row for later portal link delivery (CAS-014 follow-up).
3. **Reply threading** — the email carries an `In-Reply-To` header matching a previously-stored `email_message_id` on a ticket; the handler calls `STORE.add_message` instead of creating a new ticket.

A companion `POST /mock/ses/inbound` endpoint is provided for dev/E2E use. The entire feature is gated by `S.crm_cases_email_inbound_enabled` (default `False`). With the flag off, every new route returns 404 and the existing platform is byte-for-byte unchanged.

## 4. API / Service Design

### 4.1 New service module: `app/services/inbound_email_parser.py`

Pure parsing logic with no DynamoDB dependencies — trivially testable.

```python
from __future__ import annotations
import email.policy
import re
from email.parser import BytesParser
from typing import Any

def parse_raw_email(raw_bytes: bytes) -> dict[str, Any]:
    """Parse raw RFC-2822 bytes. Returns normalised dict.

    Keys:
      from_address (str): first address from the From header, lower-cased.
      subject (str): decoded Subject, max 500 chars, stripped.
      body_text (str): plain-text part (text/plain preferred; fallback to
          text/html with tags stripped); max 10_000 chars.
      message_id (str): Message-ID header, angle brackets stripped, lower-cased.
          Empty string if missing.
      in_reply_to (str): In-Reply-To header, first token, same normalisation.
          Empty string if missing.
    """
    ...

def _strip_html_tags(html: str) -> str:
    """Remove all HTML tags via stdlib re — no external dependency."""
    return re.sub(r"<[^>]+>", " ", html)
```

The parser uses `email.parser.BytesParser(policy=email.policy.SMTP)` from the Python standard library — no third-party dependency. `from_address` is extracted using `email.headerregistry.Address` to handle encoded headers (`=?utf-8?...?=`). Subject line decoded via `email.header.decode_header`.

### 4.2 New service helper: `app/services/inbound_email_resolver.py`

Resolves a sender email address to a platform `user_sub`.

```python
def resolve_user_by_email(email_address: str) -> str | None:
    """Query the users ByEmail GSI. Returns user_sub or None."""
    resp = T.users.query(
        IndexName=S.users_email_index_name,
        KeyConditionExpression="email = :e",
        ExpressionAttributeValues={":e": email_address.lower().strip()},
        Limit=1,
    )
    items = resp.get("Items", [])
    if items:
        return str(items[0].get("user_sub", "")).strip() or None
    return None

def find_ticket_by_email_message_id(message_id: str) -> str | None:
    """Query the tickets ByEmailMessageId GSI. Returns ticket_id or None."""
    resp = T.tickets.query(
        IndexName=S.tickets_email_message_id_index_name,
        KeyConditionExpression="email_message_id = :mid",
        ExpressionAttributeValues={":mid": message_id},
        Limit=1,
    )
    items = resp.get("Items", [])
    if items:
        return str(items[0].get("ticket_id", "")).strip() or None
    return None
```

**`_process_inbound_notification(body)` logic:**

```python
def _process_inbound_notification(body: dict) -> None:
    sns_message_id = body.get("MessageId", "")
    # 1. Idempotency check
    if sns_message_id:
        existing = T.crm_cases_email_inbound.get_item(
            Key={"sns_message_id": sns_message_id, "sk": "META"}
        ).get("Item")
        if existing:
            logger.info("ses/inbound: duplicate SNS message %s, skipping", sns_message_id)
            return

    # 2. Decode raw email from SNS message content field
    message_str = body.get("Message", "")
    # SES inbound rule stores the raw email as the SNS message body (or base64)
    raw_bytes = _decode_message_content(message_str)

    # 3. Parse
    parsed = parse_raw_email(raw_bytes)

    # 4. Resolve sender
    user_sub = resolve_user_by_email(parsed["from_address"])
    owner_sub = user_sub or f"guest:{parsed['from_address']}"

    # 5. Thread or create
    ticket_id = None
    if parsed["in_reply_to"]:
        ticket_id = find_ticket_by_email_message_id(parsed["in_reply_to"])

    if ticket_id:
        _add_email_reply(
            ticket_id=ticket_id,
            owner_sub=owner_sub,
            body=parsed["body_text"],
            from_address=parsed["from_address"],
        )
    else:
        _create_email_ticket(
            owner_sub=owner_sub,
            subject=parsed["subject"] or "(no subject)",
            description=parsed["body_text"],
            from_address=parsed["from_address"],
            email_message_id=parsed["message_id"],
        )

    # 6. Write idempotency record
    if sns_message_id:
        ttl = now_ts() + 72 * 3600
        T.crm_cases_email_inbound.put_item(Item={
            "sns_message_id": sns_message_id,
            "sk": "META",
            "ticket_id": ticket_id or "",
            "created_at": now_ts(),
            "ttl": ttl,
        })
```

## 5. Detailed Behavior & Edge Cases

### 5.1 SES inbound raw-email delivery format

AWS SES inbound rules can deliver raw email via SNS in one of two forms: (a) the entire raw MIME message as the SNS `Message` field (for small emails, up to ~150KB); (b) an S3 pointer in the SNS `Message` for larger emails. CAS-013 Phase 1 handles only form (a) — the raw MIME string. The `_decode_message_content` helper must detect whether `Message` is a raw MIME string (begins with `Received:`, `From:`, etc.) or a JSON object with an `s3` key, and return `None` for the S3 case (resulting in a no-op log + 200 response).

### 5.2 Sender normalisation

`from_address` is normalised via `app/core/normalize.normalize_email` (normalize.py) before GSI lookup and before persistence. If the `From` header contains a display name (`Alice Smith <alice@example.com>`), the raw address is extracted first. Malformed `From` headers (no `@`) result in a guest ticket with `owner_sub="guest:MALFORMED#{sha256[:8]}"` so the row is still created but the address is not stored as `submitter_email`.

### 5.3 Empty or missing subject

If the `Subject` header is absent or blank after decoding, `subject` defaults to `"(no subject)"`. The 500-char truncation applies.

### 5.4 Multipart email body extraction

`parse_raw_email` iterates MIME parts and selects the **first** `text/plain` part as the body. If none exists, it falls back to the first `text/html` part with `_strip_html_tags` applied. If neither exists (e.g., the email is entirely `text/calendar` or `application/octet-stream`), `body_text` is set to `""` and the ticket is created with a description of `"(email body not extracted)"`.

### 5.5 Reply threading: `In-Reply-To` vs `References`

`In-Reply-To` is the canonical RFC-2822 threading header. `References` (the full thread chain) is considered only if `In-Reply-To` is absent and `References` is present — in that case, the **last** token in `References` is used as the effective `in_reply_to` value. This covers MUA behaviour that omits `In-Reply-To` but populates `References`.

If the resolved ticket via `find_ticket_by_email_message_id` is in `status="done"`, `add_message` will reopen it to `"open"` via the existing `_next_status_for_message` logic (tickets.py:856) — no special handling required.

### 5.6 Guest ticket vs authenticated ticket — post-creation link

For guest tickets (`owner_sub` starts with `"guest:"`), a ticket-view URL cannot be constructed via normal UI session auth. CAS-014 (portal) will deliver a portal link email on ticket creation. CAS-013 fires the portal-link email path **only if** `S.crm_cases_portal_enabled` is also `True`; otherwise the ticket is created silently (agents see it in the admin queue, the sender receives no acknowledgement until CAS-014 ships).

### 5.7 Rate limiting per sender

To prevent email flooding, a per-`from_address` rate limit is enforced in `_process_inbound_notification` before calling `_create_email_ticket`. The helper `app/services/rate_limit.can_send_alert_channel` (already used in alerts.py:23) is not directly applicable here; instead, `T.crm_cases_email_inbound` is queried via the `ByFromAddress` projection (added below) to count tickets created in the last hour for this sender. If the count exceeds `S.crm_cases_inbound_max_per_sender_per_hour` (default 20), the message is silently accepted (HTTP 200 to SNS) but no ticket is created. An `audit_event("ticket_email_inbound_rate_limited", ...)` is emitted.

### 5.8 Subject sanitisation

Before creating the ticket, the subject is passed through a basic sanitisation step that strips ASCII control characters (0x00–0x1F except 0x09, 0x0A, 0x0D) and truncates to 500 characters. This prevents crafted email subjects from injecting unexpected characters into DynamoDB string values or notification bodies.

### 5.9 Attachment handling

CAS-013 does not process attachments. MIME parts with `Content-Disposition: attachment` are silently skipped. Attachment handling is deferred to CAS-006 (file/attachment upload per case), which already specifies S3 storage via `app.core.aws_clients.s3_client`. (CAS-010 is case merge/duplicate detection, not attachment upload.) The body extraction in Section 5.4 ignores all non-text MIME parts.

### 5.10 SNS payload size limit

SNS `Message` field is capped at 256KB. Raw emails larger than ~200KB may be truncated when delivered as the SNS body. The `_decode_message_content` helper detects a truncated MIME payload (malformed final boundary) and creates a ticket with the partial body plus an appended notice: `"[message truncated by SNS size limit]"`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

There is no `if S.dev_mode` branch inside the ticket-creation or email-parsing logic. The only dev-mode divergence is the existence of the `/mock/ses/inbound` endpoint (registered only when `S.dev_mode`), and the skipping of real SNS signature verification (controlled by `S.ses_sns_signature_verification_enabled`, default `True` in both envs — same as `ses_notifications.py:47`).

In dev, `send_alert_email` writes to `S.dev_email_log` (alerts.py:462–467) — no SES call. This is the existing behaviour of the entire alert email stack and requires no special casing here.

DynamoDB operations run against DynamoDB Local (port 8001) in dev and real DynamoDB in prod — the boto3 client configuration in `app/core/aws.py` already handles this via `S.ddb_endpoint_url`.

### 7.2 Idempotency

The `crm_cases_email_inbound` table row keyed on `sns_message_id` provides idempotency against SNS at-least-once delivery. A `get_item` check (point-read, not a conditional put) at the top of `_process_inbound_notification` short-circuits on duplicates. The write of the idempotency record happens **after** ticket creation succeeds. This means a crash between creation and idempotency write would result in a duplicate ticket on SNS retry — acceptable for support tickets (agents can merge via CAS-011). A stricter two-phase approach using a conditional `put_item` with `attribute_not_exists(sns_message_id)` can be added in a follow-up.

### 7.3 SSRF protection

The `confirm_subscription` call for `SubscriptionConfirmation` payloads is already SSRF-guarded inside `app/services/sns_signature.confirm_subscription` — which validates that `SubscribeURL` matches `https://sns.<region>.amazonaws.com/...` before making any outbound HTTP request. CAS-013 reuses this function unchanged.

### 7.4 SNS signature verification

All `Notification` and `SubscriptionConfirmation` payloads are verified via `verify_sns_message(body)` when `S.ses_sns_signature_verification_enabled=True` (the production default). This prevents unauthenticated callers from forging ticket creation by POST-ing to `/internal/ses/inbound`. **Note:** The `/internal` path prefix IS proxied by the Vite dev server (`frontend/vite.config.ts:123`: `"/internal": "http://localhost:8000"`), so in dev mode a browser can reach `/internal/ses/inbound` via the Vite proxy. In production there is no Vite proxy — raw traffic goes directly to port 8000, and `/internal/` routes are only reachable by services on the same network (SNS delivery). The SNS signature verification (`verify_sns_message`) is the authoritative authentication gate in both environments; there is no IP-allow-list guard at the route level.

### 7.5 Input bounds

- `subject`: truncated to 500 chars, control characters stripped.
- `body_text`: truncated to 10,000 chars.
- `from_address`: normalised via `normalize_email`; malformed addresses result in a guest key, not a hard failure.
- `email_message_id`: truncated to 1,000 chars (RFC 2822 Message-ID is typically <128 chars).

## 8. Backward Compatibility & Migration

### 8.1 Additive-only changes

- `TicketStore.create_ticket`: two new keyword-only parameters with `None` defaults. All existing callers pass neither parameter; their behavior is unchanged.
- `TicketOut` in `app/routers/tickets.py`: two new nullable fields. Existing API clients that deserialise `TicketOut` ignore unknown fields. Frontend TypeScript types (`frontend/src/api/types.ts`) gain two optional fields.
- `users` table `TableDef`: adding a GSI to an existing table requires an AWS DDB `UpdateTable` call in prod. In dev, `just restart` recreates the table including the new GSI. For production deployment, a GSI `UpdateTable` must be issued before the new code is deployed (GSI creation is eventually consistent, taking minutes on large tables; the inbound endpoint guards against the GSI being missing by catching `ClientError` from the query and falling back to `None` for `user_sub`).
- `tickets` table `TableDef`: same as above — `UpdateTable` for the new GSI required before deploy. Same ClientError fallback guard.

### 8.2 No existing data migration

Existing tickets have neither `submitter_email` nor `email_message_id`. The nullable fields in `TicketOut` correctly project as `None` for all pre-existing tickets. The new `email_message_id` GSI is sparse and picks up only newly-created email-inbound tickets.

### 8.3 `just restart` coverage

`just restart` wipes and recreates all DynamoDB tables via `scripts/local-ddb-init.py`. The two new GSIs (on `users` and `tickets`) and the new `crm_cases_email_inbound` table will be created correctly on the next `just restart`.

## 10. Open Questions / Assumptions

1. **S3-backed SES inbound for large emails**: CAS-013 only handles the inline MIME payload. Emails exceeding the SNS 256KB limit are silently dropped. A follow-up task should add S3-pointer handling (`app.core.aws_clients.s3_client` fetch), mirroring the pattern in `app/services/kyc_partner_api._store_document_bytes`. Until then, operators should configure a SES rule byte-size filter (`<= 150KB`) to avoid truncation.

2. **Email-to-user matching via `email` field**: The `users` table stores `email` at the top-level item (evidenced by `sessions.py:211` `T.users.get_item` returning items with an `email` key). However, not all users may have a top-level `email` attribute (some auth paths may store it only in the `profile` table). The GSI is sparse; if `resolve_user_by_email` returns `None` for a known user, the ticket will be created as guest. A follow-up can add a fallback lookup against `T.profile` (keyed on `displayed_email`). For now, the behaviour is safe and documented.

3. **From-address as owner_sub for reply messages**: When a guest sends an email reply, `owner_sub = "guest:{email}"`. The `add_message` `sender_sub` will be this synthetic sub, which will not resolve to a real user profile. Agents viewing the ticket will see a raw `sender_sub` string. CAS-014 (portal) will introduce a proper portal identity; until then this is acceptable for the agent-side admin view.

4. **Notification to agent on new email ticket**: CAS-013 calls `_notify_ticket_created` which sends email via `send_alert_email`. The recipient list is currently fixed to `[S.crm_cases_inbound_email_address]`. A more flexible admin notification subscription model is out of scope for this ticket.

5. **Multi-value `From` headers**: RFC-2822 allows multiple addresses in `From`. CAS-013 uses only the first address. This is consistent with SES behaviour (SES also uses the first `From` address for routing rule matching).
