# RPT-006 — Per-user configurable home dashboard with dashlets

**Ticket area**: Reports & Dashboards (AOR + dashlets)
**Type**: Feature  **Priority**: P1  **Estimate**: 3d
**Depends on**: RPT-001 (tables + flag)
**Source**: `docs/suitecrm/CRM_REPORTS_TICKETS.md` lines 288–375

---

## 1. Summary & Goal

RPT-006 implements a per-user configurable home dashboard for the CRM surface.
Each user gets exactly one default dashboard — created lazily on first access —
whose layout is an ordered list of up to 20 dashlet tiles. Users can add, remove,
and reorder tiles; each tile carries a `dashlet_type` that governs how it is
rendered on the frontend. The complete layout is persisted in a single DynamoDB
item on `T.crm_dashboards` (created by RPT-001); no additional tables are
required.

This closes the SuiteCRM Home Dashboard / DASH-001 gap: the platform already
has several hardcoded domain dashboards (`frontend/src/pages/Dashboard.tsx`,
`frontend/src/pages/earnings/EarningsPage.tsx`, the financial dashboard at
`app/services/platform_financial_dashboard.py`) but has no mechanism for a user
to compose and persist a personal layout of mixed data tiles. With the flag off
(`CRM_REPORTS_ENABLED=0`, the default) the five new endpoints return 404 and the
new `DashboardPage` component is never reachable; the rest of the platform is
byte-for-byte unchanged.

## 3. Data Model

### 3.1 Single DynamoDB item per user (default dashboard)

All dashboard state for a user lives in a single item on `T.crm_dashboards`:

```
PK  = "DASH#{user_sub}#default"
SK  = "META"

GSI attributes (for owner listing):
  GSI1PK  = "OWNER#{user_sub}"   (S)
  GSI1SK  = <created_at>          (N)  ← must be declared in attr_types

Payload attributes:
  owner_sub  : str   — user sub, denormalised for ownership checks
  name       : str   — display name, default "Home"
  dashlets   : list  — ordered list of dashlet config dicts (see 3.2)
  created_at : int   — Unix timestamp (now_ts())
  updated_at : int   — Unix timestamp, updated on every mutation
```

The `dashboard_id` encodes user identity directly (`DASH#{user_sub}#default`),
so ownership is also enforced at the key level — no scan or GSI is required to
resolve the calling user's default dashboard.

### 3.2 Dashlet config schema (embedded list element)

Each element of the `dashlets` list is a dict:

```
{
  "dashlet_id"   : "dlt_{8-char hex}",   # stable per-dashlet UUID; assigned on add
  "dashlet_type" : str,                  # one of the five types + "report" + "saved_search"
  "title"        : str,                  # user-facing tile title (max 120 chars)
  "config"       : {}                    # type-specific config dict (see 3.3)
}
```

The `dashlet_id` is generated as `"dlt_" + uuid4().hex[:8]` on each `add_dashlet`
call. IDs are stable across `update_dashboard` PATCH calls by matching on
position in the incoming list (existing IDs are preserved; new elements get new
IDs).

### 3.3 Type-specific config keys

| `dashlet_type`    | Mandatory config keys              | Notes                           |
|-------------------|------------------------------------|----------------------------------|
| `recent_tickets`  | `row_limit` (int, default 10)      | Provided by RPT-007              |
| `calendar_today`  | none                               | Provided by RPT-007              |
| `my_contacts`     | `row_limit` (int, default 10)      | Provided by RPT-007              |
| `billing_summary` | `period_days` (int, default 30)    | Provided by RPT-007              |
| `report`          | `report_id` (str, required)        | Provided by RPT-007; requires RPT-002 |
| `saved_search`    | `saved_search_id` (str, required)  | Provided by RPT-008              |

The `dashlet_type` field is validated against this set in the service layer;
unknown types return 422.

### 3.4 DDB table definition additions (RPT-001 owns this; documented here for completeness)

In `scripts/local-ddb-init.py`, the `crm_dashboards` table `TableDef` must
include:

```python
TableDef(
    _resolve_table_name(S.crm_dashboards_table_name, "crm_dashboards"),
    "dashboard_id",
    "sk",
    gsi=[{
        "index_name": "owner-dashboards-index",
        "partition_key": "GSI1PK",
        "sort_key": "GSI1SK",
    }],
    attr_types={"GSI1SK": "N"},    # ← required; omitting causes ValidationException
)
```

The `attr_types={"GSI1SK": "N"}` declaration is non-negotiable: numeric GSI sort
keys without an explicit `N` type declaration are stored as String by DynamoDB
Local and moto, causing `ValidationException` when queried with integer
`KeyConditionExpression` values (CLAUDE.md gotcha at line 98).

## 4. API / Service Design

### 4.1 Pydantic models (additions to `app/models.py`)

```python
VALID_DASHLET_TYPES = frozenset({
    "recent_tickets", "calendar_today", "my_contacts",
    "billing_summary", "report", "saved_search",
})

class DashletConfig(BaseModel):
    dashlet_type: str = Field(..., pattern=r"^(recent_tickets|calendar_today|my_contacts|billing_summary|report|saved_search)$")
    title: str = Field(..., min_length=1, max_length=120)
    config: Dict[str, Any] = Field(default_factory=dict)

class DashletConfigOut(DashletConfig):
    dashlet_id: str

class DashboardOut(BaseModel):
    dashboard_id: str
    name: str
    owner_sub: str
    dashlets: List[DashletConfigOut]
    created_at: int
    updated_at: int

class DashboardUpdateIn(BaseModel):
    name: Optional[str] = Field(None, min_length=1, max_length=200)
    dashlets: Optional[List[DashletConfig]] = None   # full replacement list

class DashletAddIn(BaseModel):
    dashlet_type: str = Field(..., pattern=r"^(recent_tickets|calendar_today|my_contacts|billing_summary|report|saved_search)$")
    title: str = Field(..., min_length=1, max_length=120)
    config: Dict[str, Any] = Field(default_factory=dict)

class DashletReorderIn(BaseModel):
    dashlet_ids: List[str] = Field(..., min_items=1)
```

All models live in `app/models.py` alongside existing models — no new file
required.

### 4.2 Service layer (`app/services/crm_dashboard.py`)

New file. All functions are synchronous and interact with `T.crm_dashboards`
directly (DynamoDB boto3 resource).

```python
def _dashboard_id(user_sub: str) -> str:
    return f"DASH#{user_sub}#default"

def _item_to_out(item: dict) -> DashboardOut:
    """Convert a DynamoDB item dict to DashboardOut.
    Coerces Decimal created_at / updated_at to int."""
    ...

def get_or_create_default_dashboard(user_sub: str) -> DashboardOut:
    """Read DASH#{user_sub}#default / META.
    On first call (item missing), write an empty dashboard with created_at=now_ts()
    and return it. Uses a conditional put (attribute_not_exists(dashboard_id)) to
    be idempotent under concurrent first-time requests."""
    ...

def update_dashboard(user_sub: str, patch: DashboardUpdateIn) -> DashboardOut:
    """Partial update: name and/or full dashlets list replacement.
    When patch.dashlets is provided, existing dashlet_ids are preserved by
    positional index (element 0 keeps its old dashlet_id if present; new
    positions get a freshly minted dlt_XXXXXXXX id). Enforces ≤ 20 dashlet
    limit. Raises HTTPException(422) if limit is exceeded."""
    ...

def add_dashlet(user_sub: str, payload: DashletAddIn) -> DashboardOut:
    """Append a new dashlet to the dashboard.
    Generates dashlet_id = 'dlt_' + uuid4().hex[:8].
    Raises HTTPException(422) if the dashboard already has 20 dashlets.
    Writes updated_at = now_ts() and the new dashlets list atomically with
    update_item. Calls audit_event('crm_dashboard.dashlet_added', user_sub)."""
    ...

def remove_dashlet(user_sub: str, dashlet_id: str) -> DashboardOut:
    """Filter the dashlet with the given dashlet_id out of the list.
    Raises HTTPException(404) if dashlet_id is not found.
    Calls audit_event('crm_dashboard.dashlet_removed', user_sub)."""
    ...

def reorder_dashlets(user_sub: str, ordered_dashlet_ids: List[str]) -> DashboardOut:
    """Replace the dashlets list with elements in the order specified by
    ordered_dashlet_ids. Raises HTTPException(422) if the provided IDs do not
    exactly match the current set of dashlet_ids (same count, same members, no
    duplicates). Calls audit_event('crm_dashboard.reordered', user_sub)."""
    ...
```

All mutating functions read the current dashboard item first (to get the current
`dashlets` list), compute the new list in Python, then write the full list back
with `update_item`. The write uses `UpdateExpression` with
`ExpressionAttributeValues` so that float values in `config` dicts pass through
`_FloatSafeTable._to_decimal` correctly (`app/core/tables.py:11`).

`audit_event` calls import `from app.services.alerts import audit_event` at the
top of the service file — the same pattern used in `app/services/ssh_key_manager.py`.

### 4.3 Router (`app/routers/crm_dashboard.py`)

New file. All five endpoints share a single `APIRouter(prefix="")`:

```
GET    /ui/crm/dashboard
        → get_or_create_default_dashboard(session["user_sub"])
        → 200 DashboardOut

PATCH  /ui/crm/dashboard
        body: DashboardUpdateIn
        → update_dashboard(session["user_sub"], body)
        → 200 DashboardOut

POST   /ui/crm/dashboard/dashlets          ← declared before /{dashlet_id}
        body: DashletAddIn
        → add_dashlet(session["user_sub"], body)
        → 200 DashboardOut

POST   /ui/crm/dashboard/dashlets/reorder  ← declared before /{dashlet_id}
        body: DashletReorderIn
        → reorder_dashlets(session["user_sub"], body.dashlet_ids)
        → 200 DashboardOut

DELETE /ui/crm/dashboard/dashlets/{dashlet_id}
        → remove_dashlet(session["user_sub"], dashlet_id)
        → 200 DashboardOut
```

Route declaration order is critical: `/dashlets` (POST add) and
`/dashlets/reorder` (POST reorder) **must** be declared before
`/dashlets/{dashlet_id}` (DELETE). FastAPI matches routes in declaration order;
a dynamic `{dashlet_id}` segment declared first would capture the literal string
`"reorder"` as a path parameter (CRM_REPORTS_TICKETS.md cross-cutting constraint,
line 25).

Each handler begins with:

```python
if not S.crm_reports_enabled:
    raise HTTPException(status_code=404)
```

Auth dependency: `session: dict = Depends(require_ui_session)`. CSRF is enforced
automatically on all non-GET requests by `require_ui_session` when the request
arrives via cookie auth (`app/auth/deps.py` cookie-auth path).

Add to `app/main.py` (alongside sibling CRM routers registered by other RPT

## 5. Detailed Behavior & Edge Cases

### 5.1 Lazy creation with idempotent conditional put

`get_or_create_default_dashboard` first attempts a `get_item` on
`DASH#{user_sub}#default` / `"META"`. If the item is absent, it calls
`put_item` with `ConditionExpression=Attr("dashboard_id").not_exists()`. If a
concurrent request wins the race, the `ConditionalCheckFailedException` is
caught and a second `get_item` is issued to return the item created by the racing
request. This two-phase approach guarantees that the function always returns a
valid `DashboardOut` without a unique constraint violation.

The empty dashboard has: `name = "Home"`, `dashlets = []`,
`created_at = updated_at = now_ts()`.

### 5.2 Dashlet limit enforcement

The maximum of 20 dashlets is enforced before writing in both `add_dashlet` and
`update_dashboard` (when `patch.dashlets` is provided). The check is:
`if len(new_dashlets) > 20: raise HTTPException(status_code=422, detail="Maximum 20 dashlets per dashboard")`.

### 5.3 Dashlet ID stability across PATCH

When `PATCH /ui/crm/dashboard` supplies a `dashlets` list, each element is
matched to the existing list by index (not by `dashlet_type` or `title`). This
means:

- Existing element at position 0 keeps its old `dashlet_id` if the list
  length stays the same or grows.
- Truncation (fewer elements in the patch than currently exist) discards the
  excess elements along with their IDs.
- New elements appended at the end receive fresh `dlt_XXXXXXXX` IDs.

The frontend is responsible for including only known dashlet types when calling
PATCH. This avoids accidental ID reassignment and keeps dashlet data links
(e.g., `config.report_id` references) stable.

### 5.4 Reorder validation

`reorder_dashlets` validates that `ordered_dashlet_ids`:
1. Has the same length as the current `dashlets` list.
2. Contains exactly the same set of IDs as the current list (no additions,
   no omissions, no duplicates — checked via `set` comparison).

If either check fails, the function raises
`HTTPException(status_code=422, detail="dashlet_ids must be a permutation of the current dashlet IDs")`.

No partial reorder is supported; the client always sends the full ordered set.

### 5.5 Unknown `dashlet_type` at write time

Although the `DashletConfig.dashlet_type` field has a regex pattern validator in
Pydantic, service-layer code also rejects unknown types explicitly:

```python
if payload.dashlet_type not in VALID_DASHLET_TYPES:
    raise HTTPException(status_code=422, detail=f"Unknown dashlet_type: {payload.dashlet_type}")
```

This double-validation ensures the constraint holds even when the service is
called directly from tests or other services (not through the FastAPI request
pipeline).

### 5.6 Dashboard name update without dashlets

`PATCH /ui/crm/dashboard` with `{"name": "My CRM Home"}` and no `dashlets` key
updates only the `name` and `updated_at` attributes on the DDB item. The
`dashlets` list is untouched. This is implemented with an `update_item`
`UpdateExpression` that conditionally includes only the supplied non-None fields.

### 5.7 Concurrent modifications

Dashboard mutations are infrequent enough that optimistic locking via a version
counter is not required for RPT-006. The read-modify-write cycle (get → compute
→ update_item) is sufficient for single-user personal layouts. If a concurrent
write race occurs, the second writer wins (last-writer-wins semantics), which is
acceptable for a personal UI preference store.

### 5.8 DashletConfigOut serialisation

`DashletConfigOut` extends `DashletConfig` by adding `dashlet_id`. When
converting a DDB item's `dashlets` list to `DashboardOut`, each element dict is
coerced to `DashletConfigOut`. Any `Decimal` values embedded in `config` dicts
(e.g., a `row_limit` stored as `Decimal(10)`) must be cast to `int` or `float`
before constructing the Pydantic model; use the `_to_decimal`-safe reverse
pattern from `app/core/tables.py:11`.

### 5.9 Empty dashboard on first render

When `GET /ui/crm/dashboard` returns `dashlets: []`, the frontend renders an
empty grid with only an "Add Dashlet" prompt visible. This is the cold-start
state; no error or placeholder data is needed on the backend.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

All DynamoDB access goes through `T.crm_dashboards`, which is a `_FloatSafeTable`
wrapping a standard `boto3.resource("dynamodb").Table(...)` regardless of
environment. In dev this resolves to DynamoDB Local at
`DDB_ENDPOINT_URL=http://localhost:8001`; in prod it resolves to real DynamoDB.
There is no `if S.dev_mode` branch in `app/services/crm_dashboard.py`. The
entire code path is identical in both environments.

### 7.2 Ownership enforcement

The `dashboard_id` key `DASH#{user_sub}#default` is constructed from the
authenticated `user_sub` (extracted from the session token, not from the request
body). A user cannot access or mutate another user's dashboard because they
cannot supply a different `user_sub` — the key is always derived from the
verified session.

The service functions never accept a `dashboard_id` from the request;
`_dashboard_id(user_sub)` is called with the session sub exclusively. This is the
same pattern used in `app/services/billing_shared.py` (`user_pk(user_sub)`).

### 7.3 CSRF protection

All non-GET requests (`PATCH`, `POST`, `DELETE`) carry CSRF enforcement via
`require_ui_session` when the request arrives via cookie auth. The CSRF token
must be present in the `x-csrf-token` header and match both the session's stored
`csrf_token` and the `ui_csrf` cookie (`app/auth/deps.py` cookie-auth path).
Bearer-token callers skip CSRF automatically.

### 7.4 Audit trail

Every mutating operation (`add_dashlet`, `remove_dashlet`, `reorder_dashlets`,
`update_dashboard`) calls `audit_event(event_name, user_sub, request=None)`
which writes to `T.alerts` (`app/services/alerts.py:644`). Event names:
`crm_dashboard.dashlet_added`, `crm_dashboard.dashlet_removed`,
`crm_dashboard.reordered`, `crm_dashboard.updated`. Fields include `dashboard_id`
and, where applicable, `dashlet_id` and `dashlet_type`.

### 7.5 Input size limits

- `title`: max 120 chars (validated by Pydantic).
- `config` dict: no explicit size limit at the model level. The DynamoDB item
  size limit (400 KB) provides a hard upper bound. With 20 dashlets and typical
  config payloads (< 200 bytes each), total item size is well under 10 KB.
- `name`: max 200 chars (validated by Pydantic).

### 7.6 Idempotency

`GET /ui/crm/dashboard` is idempotent by construction (the conditional put for
creation uses `attribute_not_exists`). The PATCH, POST, and DELETE endpoints are
not idempotent (repeated calls produce different states), which is standard for
state-mutation endpoints.

## 8. Backward Compatibility & Migration

### 8.1 No schema migration required

With `CRM_REPORTS_ENABLED=0` (the default), no code path touches `T.crm_dashboards`
at runtime. Deploying the flag-off code to production is a no-op for existing
users. Enabling the flag later requires only that the `crm_dashboards` DynamoDB
table has been created (by the RPT-001 `local-ddb-init.py` changes deployed at or
before flag-on time). There is no data to migrate.

### 8.2 Existing Dashboard.tsx is not modified

`frontend/src/pages/Dashboard.tsx` (the existing post-login landing page) is
not touched by RPT-006. The new `DashboardPage.tsx` at
`frontend/src/pages/reports/DashboardPage.tsx` is a completely new component
accessible only via the `/crm/dashboard` route, which does not conflict with any
existing route.

### 8.3 Future multi-dashboard support

The `dashboard_id` key space (`DASH#{user_sub}#default`) is designed to
accommodate future named dashboards (`DASH#{user_sub}#{dashboard_slug}`) without
a schema change. The `owner-dashboards-index` GSI already supports listing all
dashboards owned by a user. RPT-006 exposes only the default dashboard; the
multi-dashboard CRUD surface is deferred to a future ticket.

### 8.4 Rolling deploys

The `crm_dashboards` DynamoDB table must be created (by deploying RPT-001) before
`CRM_REPORTS_ENABLED=1` is set in any environment. The table creation is
idempotent (`just restart` calls `local-ddb-init.py` which uses
`create_table` wrapped in a `ResourceInUseException` guard). In production,
table creation should precede the flag-on deployment by at least one release
train to ensure availability during a rolling restart.

## 10. Open Questions / Assumptions

1. **`dashlet_type` registry is closed**: The valid type set
   (`recent_tickets | calendar_today | my_contacts | billing_summary | report |
   saved_search`) is defined in RPT-006 and relied upon by RPT-007/RPT-008. If
   a new built-in dashlet type is added later (e.g., `open_opportunities` from
   OPP tickets, `pipeline` from a future CRM ticket), the validator pattern in
   `DashletConfig.dashlet_type` and the `VALID_DASHLET_TYPES` constant must be
   updated in the same commit. This is intentional — open-registry types would
   allow storing arbitrary unvalidated type strings.

2. **One default dashboard per user**: RPT-006 creates exactly one default
   dashboard per user. Multiple named dashboards are out of scope for this ticket.
   The key design (`DASH#{user_sub}#default`) is forward-compatible with named
   dashboards but does not expose multi-dashboard management.

3. **`report` and `saved_search` dashlet types are stubs in RPT-006**: The
   `add_dashlet` endpoint accepts these types and stores their config, but the
   data-fetching backend (RPT-007/RPT-008) is not yet wired. Tiles of type
   `report` or `saved_search` render a "Coming soon" placeholder on the frontend
   until RPT-007/RPT-008 are deployed.

4. **Drag-and-drop vs. up/down arrows for reorder**: The ticket description leaves
   the reorder UX unspecified ("drag-and-drop reorder (or up/down arrow buttons
   for simpler implementation)"). The recommended initial implementation is
   up/down arrow buttons per tile, which avoids the complexity of a DnD library.
   The backend `POST /dashlets/reorder` endpoint supports both approaches
   identically.

5. **No pagination on dashlets list**: With a maximum of 20 dashlets, the full
   list fits in a single DynamoDB item and a single API response. No pagination
   cursor is needed for the dashlets array within `DashboardOut`.

6. **`config` dict is schema-free on the backend**: The backend stores and
   returns `config` as a freeform `Dict[str, Any]`. Structural validation of
   type-specific config keys (e.g., `report_id` for the `report` type) is left
   to RPT-007, which owns the data-provider layer. RPT-006 only validates the
   `dashlet_type` string itself.

7. **Assumption — `T.crm_dashboards` handle exists**: RPT-006 assumes RPT-001
   has been merged and that `T.crm_dashboards` is present in `app/core/tables.py`
   before this ticket's code is deployed. If RPT-001 is merged alongside RPT-006
   in the same release, the deployment ordering within the release does not matter
   (both go through `app/main.py` import, which imports `app/core/tables.py` at
   load time).

## 11. Dependencies

### 11.1 Hard prerequisites

- **RPT-001** — Provides `S.crm_reports_enabled`, `S.crm_dashboards_table_name`,
  `T.crm_dashboards` table handle, and the `crm_dashboards` DynamoDB table
  definition with `owner-dashboards-index` GSI and `attr_types={"GSI1SK": "N"}`.
  RPT-006 cannot be deployed without RPT-001.

### 11.2 Soft / peer dependencies (RPT-006 does not block on these)

- **RPT-002** — Provides `run_report` and `ReportRunOut` needed when a `report`
  dashlet type is resolved for data in RPT-007. RPT-006 accepts `report` dashlet
  configs without validating that the referenced `report_id` exists.
- **RPT-005** — Provides the recharts chart rendering components reused in
  `ReportDashlet.tsx` (RPT-007 frontend). Not needed for RPT-006's `DashboardPage`
  scaffold.
- **RPT-007** — Provides the `GET /ui/crm/dashboard/dashlets/{dashlet_id}/data`
  endpoint and all five built-in dashlet data providers. RPT-006 provides the
  layout management layer; RPT-007 provides the data layer. They must both be
  deployed for fully functional dashlets.
- **RPT-008** — Provides the `saved_search` dashlet data provider and the
  `crm_saved_searches` service. Until RPT-008 is deployed, `saved_search` tiles
  are storage-only stubs.

### 11.3 Related sibling CRM tickets

- **CRM_ACTIVITIES_TICKETS (ACT series)** — Activity feed data could become a
  `recent_activities` dashlet type in a future extension. The `T.activity_feed`
  table and `app/services/activity_feed.py` service (uses `encode_cursor` /
  `decode_cursor` from `app/core/cursor.py:94`) are already in place.
- **CRM_CONTACTS_EXTRA_TICKETS (CCT series)** — The `my_contacts` dashlet type
  in RPT-007 reuses the `_iter_contacts` iterator from
  `app/services/csv_export.py:90` which queries `T.contacts`.
- **CRM_OPPORTUNITIES_TICKETS (OPP series)** — A `pipeline` or
  `open_opportunities` dashlet type is a natural extension once OPP-001 lands.
  The `dashlet_type` validator pattern in `DashletConfig` would need to be
  extended at that point.
- **CRM_PROJECTS_GANTT_TICKETS (PRJ series)** — A `my_projects` dashlet type
  could query `T.projects` via the existing `app/services/projects_store.py`
  service; out of scope for RPT-006.
