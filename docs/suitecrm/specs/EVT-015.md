# EVT-015 — Global activity audit log — paginated admin browse endpoint

## 1. Summary & Goal

EVT-015 delivers a **live, paginated admin browse endpoint** for the cross-module audit log, enabling ROOT operators to browse all platform audit events in real time without spawning a background export job. This complements the existing job-based path (`POST /ui/admin/audit-exports` from `app/routers/audit_export.py:66`) by providing an **interactive, low-latency query interface** rather than an asynchronous pipeline.

The core ask from the SuiteCRM gap analysis is: "The Admin panel has a live global activity audit log for real-time cross-module browsing." The existing ENTERPRISE-004 export system (`app/routers/audit_export.py`) handles bulk offline exports; EVT-015 handles the interactive, scrollable, operator dashboard use case.

**Goals:**
- A single `GET /ui/admin/audit-log` endpoint usable by React's `useInfiniteQuery` for real-time browsing.
- Filter by time window, actor (`user_sub`), and audit event category (reusing `VALID_CATEGORIES` from `app/services/audit_adapters.py:449`).
- Cursor-based pagination via the existing `encode_cursor`/`decode_cursor` primitives in `app/core/cursor.py`.
- A React admin page (`AuditLogBrowsePage.tsx`) with date pickers, filter dropdowns, and infinite scroll.
- Default-off feature flag; zero behaviour change with the flag off.

**Out of scope:** New data ingestion, new DynamoDB tables, or duplicating the export worker logic. This ticket is purely a read-path over already-written audit data.

## 2. Context & Current State

### Existing audit infrastructure

The platform already has a mature, multi-source audit export system (ENTERPRISE-004):

- **`app/routers/audit_export.py`** (line 1): all audit-export endpoints at `/ui/admin/audit-exports`. ROOT-only guard `_require_root` at line 34 checks `ctx["role"] != Role.ROOT` and raises HTTP 403.
- **`app/services/audit_adapters.py`** (line 1): the `BaseAuditAdapter` abstract class (line 19) and five concrete adapters — `AlertsAdapter` (line 77, reads `T.alerts`), `ModerationAuditAdapter` (line 181, reads `T.moderation_audit_log`), `BroadcastAuditAdapter` (line 238, reads `T.broadcast_action_audit`), `RoleAuditAdapter` (line 300, reads `T.role_audit`), `BillingLedgerAdapter` (line 353, reads `T.billing`).
- **`ADAPTERS` registry** and **`VALID_CATEGORIES`** (`app/services/audit_adapters.py:441-449`): maps category names (`"auth"`, `"moderation"`, `"broadcast"`, `"admin"`, `"billing"`) to adapter instances. EVT-015 reuses this registry wholesale.
- **`UnifiedAuditEvent`** dataclass (`app/services/audit_export.py:10`): the normalised event schema with fields `event_id`, `event_type`, `event_action`, `timestamp`, `timestamp_unix`, `actor_user_id`, `actor_role`, `actor_ip`, `actor_user_agent`, `target_user_id`, `target_resource_type`, `target_resource_id`, `outcome`, `metadata`, `source_table`, `impersonation_context`.
- **`app/services/audit_export_pipeline.py`**: `create_export_job` and the full async processing pipeline. EVT-015 does **not** use the pipeline — it drives adapters directly.

### T.alerts table layout

`T.alerts` is defined at `scripts/local-ddb-init.py:61` as `PK=user_sub (S)`, `SK=alert_id (S)`. The `alert_id` is formatted `f"{ts:010d}#{uuid.uuid4().hex}"` (line 370 of `app/services/alerts.py`), embedding a zero-padded Unix timestamp as the leading component. This means per-user queries with `ScanIndexForward=False` return events newest-first naturally. The item written at `app/services/alerts.py:405-416` includes: `user_sub`, `alert_id`, `ts` (N), `event` (S), `outcome` (S), `title` (S), `details` (M), `read` (B), `read_at` (N), `priority` (S), `category` (S).

Critically, the `alerts` table has **no GSI** on `ts` or `category` as of `scripts/local-ddb-init.py:61`. Cross-user (admin) queries currently scan with `FilterExpression=Attr("ts").between(...)` (as done in `AlertsAdapter.query`, line 130–137). This is the same strategy EVT-015 uses; no new GSI is required.

### Pagination primitives

`app/core/cursor.py` exposes `encode_cursor(last_evaluated_key)` (line 94) and `decode_cursor(cursor)` (line 103). Cursors are HMAC-signed with `CURSOR_SIGNING_SECRET` (v2 format: `v2.<payload_b64>.<hmac_sha256>`). The `_json_default` helper (line 12) handles DynamoDB `Decimal` in `LastEvaluatedKey`, making cursor encoding float-safe for numeric sort keys.

### Role / auth system

`app/auth/roles.py:9` defines `Role.ROOT = "root"`. `_require_root` in `app/routers/audit_export.py:34` is the established pattern for ROOT-only access — it checks `ctx.get("role") != Role.ROOT` and raises HTTP 403. The `ctx` dict is supplied by `Depends(require_ui_session)` from `app/services/sessions.py`.

### Rate limiting

`app/services/rate_limit.py:60` defines `_bucket_limit(user_sub, sid, max_n, win) -> bool`, backed by `T.sessions`. This is the same primitive used by `app/routers/csv_export.py:66` for export rate limiting and by `app/services/kyc_partner_api.py` for per-key caps. EVT-015 applies it to the browse endpoint.

### No existing browse endpoint

There is currently no `GET /ui/admin/audit-log` route anywhere in the codebase. The `app/routers/audit_export.py` router has: `POST ""` (create job), `GET ""` (list jobs), `GET /{export_id}`, `GET /{export_id}/download`, and scheduled export CRUD under `/schedules`. No synchronous read-path exists.

## 3. Data Model

EVT-015 **does not create any new DynamoDB tables**. It reads exclusively from existing tables already owned by the five audit adapters:

| Source Table | Adapter | Key Shape |
|---|---|---|
| `alerts` (`T.alerts`) | `AlertsAdapter` | PK=`user_sub`, SK=`alert_id` (`{ts:010d}#...`) |
| `moderation_audit_log` | `ModerationAuditAdapter` | scanned by `created_at` string |
| `broadcast_action_audit` | `BroadcastAuditAdapter` | GSI `ByCreatedAt` PK=`scope`, SK=`created_at` |
| `role_audit` | `RoleAuditAdapter` | scanned by `timestamp` N |
| `billing` (LEDGER# rows) | `BillingLedgerAdapter` | PK=`USER#{sub}`, SK=`LEDGER#...` |

### No schema changes required

Because EVT-015 is purely a read-path driven by the existing adapters, `scripts/local-ddb-init.py` requires **no additions**. No new table, no new GSI, no `attr_types` change.

### Pagination state

The endpoint returns an HMAC-signed opaque cursor (from `encode_cursor`) encoding the `LastEvaluatedKey` from the last DynamoDB page returned for the active query. Because EVT-015 queries a **single adapter per request** (caller selects one `category`), the cursor is per-adapter and round-trips cleanly. Multi-category fan-out (like the export pipeline's `_merge_sorted_events`) is explicitly out of scope for the interactive browse path — callers issue separate requests per category.

## 4. API / Service Design

### 4.1 New service: `app/services/audit_log_browse.py`

```python
from __future__ import annotations

from typing import Any, Optional
from boto3.dynamodb.conditions import Attr, Key

from app.core.cursor import decode_cursor, encode_cursor
from app.core.settings import S
from app.services.audit_adapters import ADAPTERS, VALID_CATEGORIES
from app.services.audit_export import UnifiedAuditEvent


_BROWSE_MAX_LIMIT = 200       # hard cap per page, regardless of caller input
_BROWSE_DEFAULT_LIMIT = 50


def browse_audit_log(
    *,
    category: str,
    from_ts: int,
    to_ts: int,
    user_sub_filter: Optional[str] = None,
    event_type_filter: Optional[str] = None,
    limit: int = _BROWSE_DEFAULT_LIMIT,
    cursor: Optional[str] = None,
) -> dict[str, Any]:
    """
    Paginated synchronous browse of a single audit category.

    Returns:
        {
            "items": list[dict],          # UnifiedAuditEvent.to_ndjson_dict() each
            "cursor": str | None,         # next-page opaque cursor; None = last page
            "total_scanned": int,         # DynamoDB items examined in this call
            "category": str,
        }
    Raises:
        ValueError: if category not in VALID_CATEGORIES, or from_ts > to_ts,
                    or date range exceeds S.audit_export_max_date_range_days.
    """
```

**Implementation notes:**

- Validates `category in VALID_CATEGORIES`; raises `ValueError` otherwise.
- Validates `from_ts <= to_ts`; raises `ValueError` if not.
- Validates `(to_ts - from_ts) <= S.audit_export_max_date_range_days * 86400`; reuses the same cap as the export pipeline (`app/core/settings.py:2133`, default 90 days).
- Clamps `limit` to `min(limit, _BROWSE_MAX_LIMIT)`.
- Decodes cursor via `decode_cursor(cursor)` (returns `None` for invalid/expired cursors, which is treated as start-of-query).
- Calls `ADAPTERS[category].query(from_ts, to_ts, actor=user_sub_filter, event_actions=[event_type_filter] if event_type_filter else None, limit=limit)` to drive the existing adapter. The adapter handles its own `LastEvaluatedKey` pagination loop internally via `_paginate_query`/`_paginate_scan` (lines 56–74 of `audit_adapters.py`).
- Because the adapters iterate fully until `limit` is reached or exhausted, this service must wrap the adapter call to stop after `limit` items and capture the adapter's DynamoDB `LastEvaluatedKey` at the stop point. This requires a **single-page** DynamoDB call path rather than the full `_paginate_*` iterator. See detailed behaviour in Section 5.
- Returns events as `UnifiedAuditEvent.to_ndjson_dict()` dicts.
- Emits `audit_event("crm_audit_log_browse", actor_sub, ...)` (best-effort) via `app.services.alerts.audit_event` so the browse action itself is audited.

## 5. Detailed Behavior & Edge Cases

### 5.1 Single-page adapter call strategy

The existing `BaseAuditAdapter._paginate_query` and `_paginate_scan` helpers (`audit_adapters.py:56–74`) loop until exhausted. For the browse endpoint, the service needs to stop after `limit` items **and return the DynamoDB `LastEvaluatedKey`** so the client can continue with a cursor. The browse service therefore drives DynamoDB directly for adapters that support it:

- For **`AlertsAdapter`** (T.alerts, PK=`user_sub`): when `user_sub_filter` is set, issue a single `query(KeyConditionExpression=..., FilterExpression=..., Limit=limit*3, ScanIndexForward=False, ExclusiveStartKey=decoded_cursor)` call and collect up to `limit` items from the response, then call `encode_cursor(resp.get("LastEvaluatedKey"))`. The `Limit=limit*3` multiplier accounts for the `ts.between` FilterExpression not reducing the DynamoDB page size (per CLAUDE.md DDB FilterExpression gotcha). When `user_sub_filter` is absent, issue a `scan(FilterExpression=..., Limit=limit*5, ExclusiveStartKey=decoded_cursor)`.
- For **`BroadcastAuditAdapter`** (GSI `ByCreatedAt`): issue a single `query(IndexName="ByCreatedAt", ..., Limit=limit*3, ExclusiveStartKey=decoded_cursor)`.
- For **`ModerationAuditAdapter`** and **`RoleAuditAdapter`** (scan-only): issue a single `scan(FilterExpression=..., Limit=limit*5, ExclusiveStartKey=decoded_cursor)`.
- For **`BillingLedgerAdapter`**: when `user_sub_filter` is set, issue a single `query(KeyConditionExpression=Key("pk").eq(f"USER#{user_sub_filter}") & Key("sk").begins_with("LEDGER#"), FilterExpression=..., Limit=limit*3, ExclusiveStartKey=decoded_cursor)`.

`total_scanned` in the response is the count of DynamoDB items the call examined (i.e., the raw `Count` or `ScannedCount` from the response, not just the items returned after FilterExpression application).

### 5.2 Cursor validity

Invalid or tampered cursors (`decode_cursor` returns `None`) are silently treated as a fresh query from the beginning (no 400 error). This is consistent with the existing cursor usage across the codebase and avoids surfacing internal key shapes.

### 5.3 Date range validation

- `from_ts > to_ts` → HTTP 400: `"from_ts must be <= to_ts"`.
- `to_ts - from_ts > S.audit_export_max_date_range_days * 86400` → HTTP 400: `"Date range exceeds maximum of N days"`. The same setting (`audit_export_max_date_range_days`, default 90) used by `_validate_date_range` in `audit_export.py:51` is reused — no new config key.
- `from_ts == 0 and to_ts == 0` → HTTP 400: `"Date range is empty"` (mirrors `audit_export.py:54`).

### 5.4 Unknown category

`category` not in `VALID_CATEGORIES` → HTTP 400: `"Unknown category: X. Valid: auth, admin, billing, broadcast, moderation"`.

### 5.5 Empty result set

Returns `{"items": [], "cursor": null, "total_scanned": N, ...}` — not a 404.

### 5.6 Self-audit of browse action

Every successful call to `browse_audit_log_endpoint` triggers `audit_event("crm_audit_log_browse", ctx["user_sub"], category=category, from_ts=from_ts, to_ts=to_ts, ...)` via `app.services.alerts.audit_event` (line 644 of `app/services/alerts.py`). This is best-effort (`try/except`), never blocking the response. The browse action itself becomes visible in subsequent `category=auth` queries.

### 5.7 Rate limiting

`_bucket_limit` (line 60 of `app/services/rate_limit.py`) uses `T.sessions` keyed `{user_sub, "rl#audit_log_browse"}`. On breach, the endpoint raises HTTP 429 with a plain JSON error body. The 60/min cap is intentionally generous — ROOT users are few — but prevents runaway polling loops.

### 5.8 Frontend infinite scroll

`AuditLogBrowsePage.tsx` uses `useInfiniteQuery` with `getNextPageParam = (last) => last.cursor ?? undefined`. When `cursor` is `undefined`, React Query does not fetch the next page. The table renders rows from all pages in order (newest-first within each page, matching DynamoDB `ScanIndexForward=False` for the `auth` category).

### 5.9 DynamoDB FilterExpression and sparse pages

Per the CLAUDE.md gotcha: DynamoDB fetches up to 1MB before applying `FilterExpression`. Sparse attributes (e.g. events from a narrow time window on a large `alerts` table) may return fewer items than `Limit`. The multiplier strategy (section 5.1) mitigates this; the caller simply paginates further if items < requested limit and cursor is non-null.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

There is **no `dev_mode` branch** anywhere in the service or router. Both environments:
- Read from the same DynamoDB tables (DDB Local in dev, real DDB in prod).
- Use the same `T.alerts` / `T.role_audit` / `T.moderation_audit_log` / `T.broadcast_action_audit` / `T.billing` handles.
- Apply the same `_require_root` guard.
- Apply the same date-range cap.

The `AlertsAdapter` in dev mode reads from DDB Local (seeded by E2E sessions). The same code path runs in both environments.

### Idempotency

`GET` endpoint — inherently idempotent. No state is mutated by a browse call. The self-audit `audit_event(...)` write is best-effort and silently discarded on error, so repeated requests do not compound side effects.

### Security

- **ROOT-only**: Only `role == ROOT` can reach the endpoint (HTTP 403 otherwise). ROOT credentials require break-glass auth and MFA (per `docs/root-admin-login-plan.md`).
- **Cursor tamper protection**: `decode_cursor` performs HMAC-SHA256 verification. A tampered cursor returns `None` and is treated as a fresh query — no exception is surfaced to the caller (no oracle for HMAC).
- **No PII in cursor**: The cursor encodes DynamoDB's `LastEvaluatedKey` (key attributes only — `user_sub` and `alert_id`). Because `alert_id = f"{ts:010d}#{uuid}"`, the cursor contains the user's sub for per-user queries. This is acceptable since the endpoint is ROOT-only and the transport is HTTPS.
- **Input sanitisation**: `user_sub_filter` and `event_type_filter` are passed as `FilterExpression` attribute values, never interpolated into expression strings. No injection risk.
- **Rate limiting**: 60/min per ROOT caller prevents enumeration attacks and runaway scripts.
- **Self-audit trail**: Browse activity is itself audited, satisfying compliance requirements for "who accessed the audit log".

## 8. Backward Compatibility & Migration

### Zero breaking changes

- No existing DynamoDB tables are modified.
- No existing routes are changed (`GET /ui/admin/audit-exports` and its sub-routes are untouched).
- `browse_router` is a new independent router instance; it does not modify the existing `router` in `audit_export.py`.
- With `CRM_AUDIT_LOG_BROWSE_ENABLED=0` (the default), `app/main.py` still registers the router but the endpoint returns HTTP 404 immediately. The Vite proxy and OpenAPI spec gain a new route, which is additive and non-breaking.

### Migration

No DynamoDB `UpdateTable` required. No data backfill. No schema change. Deploying the code with the flag off is safe on any running instance.

**Enabling in production** is a one-line env change (`CRM_AUDIT_LOG_BROWSE_ENABLED=1`), which can be toggled without a deployment.

### Existing audit export schedules / jobs

EVT-015 does not interact with `T.audit_exports` (the job table). Running browse queries does not create export jobs. The two systems are fully independent read-paths over the same source tables.

## 10. Open Questions / Assumptions

1. **Multi-category fan-out in browse**: The current design requires callers to select one category per request. An alternative would be to fan-out across all adapters and merge by `timestamp_unix`. This is deferred to a follow-up: the merge logic in `audit_export_pipeline._merge_sorted_events` is iterator-based and designed for the offline pipeline, not real-time pagination. Multi-category browse would need a distinct merge strategy with stable cursors per source.

2. **Soft-deleted / TTL'd alerts**: Alert items have a DynamoDB TTL (`alerts_ttl_days`, via `with_ttl` in `app/services/alerts.py:426`). Items past their TTL are lazily deleted by DynamoDB. The browse endpoint may see recently-expired items during the TTL eviction window. This is acceptable for an admin audit interface.

3. **`alerts` table scan performance at scale**: With `user_sub_filter` absent and a narrow time window, the scan FilterExpression still reads all items in the table before filtering on `ts`. For large deployments, a `ByTimestamp` GSI (PK=`category`, SK=`ts`) on the `alerts` table would make this efficient. Adding such a GSI is deferred — it requires a DynamoDB `UpdateTable` + backfill in production, a non-trivial migration. For the interactive browse use case, operators always filter by `user_sub` or use narrow time windows, making scans acceptable initially.

4. **`event_type_filter` semantics**: The filter parameter is passed as `event_actions` to the adapter. In `AlertsAdapter`, this maps to `Attr("event").is_in([event_type_filter])` (the query-branch at line 116, scan-branch at line 132). For `BillingLedgerAdapter`, it maps to `Attr("reason").is_in([event_type_filter])` (line 373). The field names differ by adapter; this is the existing adapter design. The frontend should clarify in the UI that `event_type` semantics vary by category.

5. **Audit trail of browse access**: Each `GET /ui/admin/audit-log` call writes an `audit_event("crm_audit_log_browse", ...)`. This means heavy interactive browsing generates audit records in `T.alerts` that themselves appear in subsequent `category=auth` browse queries. This is intentional (chain of custody) and mirrors the behaviour of export job creation.

EVT-015 is built entirely on top of ENTERPRISE-004:
- `app/services/audit_adapters.py` — `ADAPTERS`, `VALID_CATEGORIES`, `BaseAuditAdapter`, all five concrete adapters.
- `app/services/audit_export.py` — `UnifiedAuditEvent` dataclass.

### No dependency on sibling CRM tickets

EVT-015 reads existing audit data; it does not generate new CRM-specific audit events. However, once EVT-002 through EVT-014 are implemented and their respective `audit_event(...)` calls are in place, their events (`crm_event_register`, `crm_contact_sms_sent`, etc.) become visible via the `auth` category browse (since `audit_event` writes to `T.alerts`). No code changes in EVT-015 are needed to accommodate those — the data is already there.

### Sibling tickets this extends (read-path consumers)

- **EVT-002 through EVT-014**: CRM event/contact/document/SMS `audit_event(...)` calls will appear under `category=auth` in the browse view once those tickets ship.
- **PTY-001..PTY-015** (PTY family referenced across CRM docs; no dedicated source file checked in yet — forward reference): Party/contact/account operations will produce their own `audit_event` writes visible in this browse interface.
- **MKT-003, MKT-009** (`MARKETING_CAMPAIGNS`): Campaign dispatch events will appear under `category=auth` browse.

EVT-015 does not directly extend or depend on any PRD (`CATALOG_DEPTH`), OFB (`OFBIZ_COMMERCE`), or other non-audit CRM ticket families.
