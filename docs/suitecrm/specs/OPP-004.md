# OPP-004 — Opportunity–Contact role junction

**Ticket type:** Feature
**Priority:** P1
**Estimate:** 2 days
**Master gate:** `S.sales_pipeline_enabled` (`SALES_PIPELINE_ENABLED`, default `false`)
**Depends on:** OPP-001 (table, models, flag), OPP-002 (opportunity CRUD service)

---

## 1. Summary & Goal

OPP-004 implements the contact-role junction: the ability to associate one or more contacts with a sales opportunity, each tagged with a role such as "Decision Maker" or "Evaluator". This mirrors SuiteCRM's Opportunity–Contact relationship, which is one of the most operationally important parts of a B2B deal record — knowing who at the prospect organization is involved, and in what capacity, directly shapes outreach and close strategy.

The junction is implemented as a new item type stored inside the existing `sales_opportunities` DynamoDB table (introduced in OPP-001), keyed under the opportunity owner's partition. Three sub-resource REST endpoints expose the junction: add, list, and remove. The `GET /ui/sales/opportunities/{opp_id}` endpoint (OPP-002) gains an opt-in `include_contacts=true` query parameter that embeds the contact-role list in-line.

All changes are fully additive. With `SALES_PIPELINE_ENABLED=false` the new endpoints return 503 and the `OpportunityOut` model is byte-for-byte unchanged (the `contact_roles` field defaults to an empty list and is only populated when the flag is on and `include_contacts=true` is requested).

## 2. Context & Current State

**No opportunity or contact-role surface exists today.** The `CRM_OPPORTUNITIES_TICKETS.md` header (line 6) states: "The testlogon platform has zero of these capabilities today." No `app/services/opportunities.py`, no `app/routers/opportunities.py`, no `sales_opportunities` table.

**OPP-001 and OPP-002 are prerequisites.** OPP-001 (`docs/suitecrm/specs/OPP-001.md`) introduces the `sales_opportunities` DynamoDB table on `T.sales_opportunities`, the `S.sales_pipeline_enabled` flag, and the Pydantic models (`OpportunityCreateIn`, `OpportunityUpdateIn`, `OpportunityOut`). OPP-002 (`docs/suitecrm/specs/OPP-002.md`) implements the service functions `create_opportunity`, `get_opportunity`, `update_opportunity`, `delete_opportunity`, `list_opportunities` in `app/services/opportunities.py` and the five CRUD endpoints in `app/routers/opportunities.py`. OPP-004 adds to both files without modifying their existing surfaces.

**DynamoDB single-table pattern already established.** The `sales_opportunities` table uses `pk` / `sk` as primary keys. OPP-002 stores opportunity META rows as `pk=USER#{owner_sub}`, `sk=OPP#{opp_id}`. OPP-004 adds a new item type under the same partition using an extended sort key — `sk=OPP#{opp_id}#CONTACT#{contact_ref}` — so all rows for an opportunity are co-located under one partition and queryable with a `begins_with` prefix. This pattern is used throughout the codebase; for example the tickets service (`app/services/tickets.py:1–60`) uses `pk=TICKET#{ticket_id}` composite sort keys for activity and message sub-items.

**`_FloatSafeTable` and `_safe_table` are the required DDB write proxies.** `app/core/tables.py:29–66` defines `_FloatSafeTable`, a proxy that coerces Python floats to `Decimal` on every `put_item` and `update_item`. `T.sales_opportunities` is wired through `_safe_table(name)` (line 66) in OPP-001. All OPP-004 writes go through this proxy.

**Cursor-based pagination is the platform standard.** `app/core/cursor.encode_cursor` / `decode_cursor` (`app/core/cursor.py:94–131`) produce HMAC-signed v2 cursors and handle `Decimal` values in `LastEvaluatedKey` via `_json_default` (`cursor.py:13–18`). The `list_contact_roles` function is paginated with this mechanism.

**`audit_event` is the platform audit primitive.** `app/services/alerts.audit_event(event, user_sub, request, **fields)` (`app/services/alerts.py:644`) is fire-and-forget, writes to `T.alerts`, and is called by every service that performs meaningful state changes (e.g., opportunity create/delete in OPP-002, ticket create/update in `app/services/tickets.py`).

**`require_ui_session` is the standard user-facing auth dependency.** `app/services/sessions.py:330` defines `require_ui_session`; it is used by every non-admin endpoint including tickets (`app/routers/tickets.py:19`) and contacts (`app/routers/contacts.py:63, 85, 115, 121`). All three OPP-004 endpoints use it.

**`require_admin_or_root` for admin guards.** `app/auth/policy.py:67` defines `async def require_admin_or_root(user: AuthenticatedUser = Depends(get_authenticated_user))`. This is the standard enforcer for admin-only endpoints (used in `app/routers/license_agreements.py:24`, `app/routers/kyc_document_templates.py:18`, etc.). OPP-004 does not introduce any new admin endpoints — the junction is entirely user-controlled — but the pattern is available if future tickets require admin inspection.

**Contacts router as structural reference.** `app/routers/contacts.py:63–121` shows the pattern for simple sub-resource CRUD (list / add / remove) with `require_ui_session`. OPP-004 follows the same structure.

**PTY-004 is an acknowledged future dependency.** The ticket file (`CRM_OPPORTUNITIES_TICKETS.md`, OPP-004 section, line 321) notes that once PTY-004 (party CRUD) and PTY-006 (contact mechanisms) ship, `contact_ref` can be resolved to a `CrmPartyOut`. In this ticket, `contact_ref` is stored as a free-text identifier (a platform `user_sub`, a party UUID once PTY ships, or any display string). The resolution step is a follow-up extension.

**Route ordering constraint.** `CRM_OPPORTUNITIES_TICKETS.md` line 434 (OPP-005 section) documents a FastAPI route ordering issue: static path segments declared after dynamic `/{opp_id}` segments get captured incorrectly. OPP-004's three sub-resource routes all include `/{opp_id}/contacts` and are free of this issue as long as the `GET /ui/sales/opportunities` list and `GET /ui/sales/opportunities/{opp_id}` single-get routes from OPP-002 remain above them. The `include_contacts` query param on the single-get is additive to the existing route — no ordering change is required.

## 4. API / Service Design

### Service functions (`app/services/opportunities.py` additions)

These three functions are appended to the existing `opportunities.py` file introduced in OPP-002 without changing existing functions:

```python
def add_contact_role(
    owner_sub: str,
    opp_id: str,
    data: OppContactRoleIn,
) -> OppContactRoleOut:
    """Add a contact-role row to the opportunity.

    Validates opportunity ownership via get_opportunity() (raises 404 if not found
    or not owned by owner_sub). Validates contact_role against CONTACT_ROLES.
    Uses conditional put_item to prevent duplicate contact_ref on the same opp.
    Emits audit_event on success.
    """
    ...

def list_contact_roles(
    owner_sub: str,
    opp_id: str,
) -> List[OppContactRoleOut]:
    """Return all contact-role rows for the opportunity.

    Verifies ownership via get_opportunity() first (raises 404 if not owned).
    Queries pk=USER#{owner_sub} with sk.begins_with(f"OPP#{opp_id}#CONTACT#").
    Returns list sorted by created_at ascending.
    """
    ...

def remove_contact_role(
    owner_sub: str,
    opp_id: str,
    contact_ref: str,
) -> None:
    """Delete a contact-role row.

    Verifies ownership via get_opportunity() first (raises 404 if not owned).
    Raises 404 if the contact-role row itself does not exist.
    Emits audit_event on success.
    """
    ...
```

**`add_contact_role` implementation detail:**

1. Call `get_opportunity(owner_sub, opp_id)` — raises `HTTPException(404)` if missing or wrong owner. This is an ownership gate, not just an existence check.
2. Validate `data.contact_role` against `CONTACT_ROLES` (model validator runs first, so this is already enforced at the Pydantic layer; the service re-validates as defence-in-depth).
3. Build `sk = f"OPP#{opp_id}#CONTACT#{data.contact_ref}"`.
4. Call `T.sales_opportunities.put_item(Item={...}, ConditionExpression=Attr("sk").not_exists())`. If the condition fails (item already exists), boto3 raises `ClientError` with `ConditionalCheckFailedException` — catch and raise `HTTPException(409, detail={"code": "contact_role_exists"})`.
5. Call `audit_event("opportunity.contact_role_added", owner_sub, None, opp_id=opp_id, contact_ref=data.contact_ref, contact_role=data.contact_role)`.
6. Return `OppContactRoleOut(...)`.

**`list_contact_roles` implementation detail:**

1. Call `get_opportunity(owner_sub, opp_id)` to enforce ownership (raises 404).
2. Query: `T.sales_opportunities.query(KeyConditionExpression=Key("pk").eq(f"USER#{owner_sub}") & Key("sk").begins_with(f"OPP#{opp_id}#CONTACT#"))`. Loop via `LastEvaluatedKey` until exhausted (per the CLAUDE.md `FilterExpression` / pagination gotcha — even without a FilterExpression, DynamoDB paginates at 1MB; the loop is defensive).
3. Convert each item to `OppContactRoleOut`. Sort results by `created_at` ascending before returning.

**`remove_contact_role` implementation detail:**

1. Call `get_opportunity(owner_sub, opp_id)` to enforce ownership (raises 404 if opportunity not found or wrong owner).
2. Build `sk = f"OPP#{opp_id}#CONTACT#{contact_ref}"`.
3. Fetch the item with `get_item(Key={"pk": f"USER#{owner_sub}", "sk": sk})`. If absent, raise `HTTPException(404, detail={"code": "contact_role_not_found"})`.
4. Call `delete_item(Key={"pk": ..., "sk": ...})`.
5. Call `audit_event("opportunity.contact_role_removed", owner_sub, None, opp_id=opp_id, contact_ref=contact_ref)`.

## 5. Detailed Behavior & Edge Cases

### Ownership enforcement

`add_contact_role`, `list_contact_roles`, and `remove_contact_role` all begin with `get_opportunity(owner_sub, opp_id)`. That function (OPP-002) does `T.sales_opportunities.get_item(Key={"pk": f"USER#{owner_sub}", "sk": f"OPP#{opp_id}"})` and raises 404 if the item is missing. Because the DDB key includes `owner_sub`, an attacker passing another user's `opp_id` will get a 404 (the item simply doesn't exist under their `USER#` partition). This is structural authorization — no explicit authz check is needed beyond the keyed DDB lookup.

### Duplicate prevention

`add_contact_role` uses `put_item` with `ConditionExpression=Attr("sk").not_exists()`. If the same `contact_ref` is submitted twice for the same `opp_id`, the conditional fails and a 409 is returned. The duplicate check is keyed on `(owner_sub, opp_id, contact_ref)` — the same contact can hold different roles in different opportunities, and the role can be changed by removing the existing row and re-adding with a new role.

### Role update (no PATCH endpoint)

There is no PATCH on a contact-role row. To change a contact's role: DELETE the existing row, then POST a new one with the updated role. This matches the SuiteCRM UX pattern and keeps the service surface minimal. A future PATCH can be added as a non-breaking extension.

### `contact_ref` format

`contact_ref` is stored as a free-text string (max 255 chars). The service does not validate that it refers to an existing platform user or party. This is intentional: the PTY party buildout is unbuilt; the field is designed for forward compatibility. When PTY-004 ships, a follow-up ticket can add a `party.get_party(contact_ref)` lookup and surface enriched contact info.

### `contact_ref` URL-safety

The `DELETE /ui/sales/opportunities/{opp_id}/contacts/{contact_ref}` path captures `contact_ref` as a path segment. If `contact_ref` contains special characters (e.g., `@`, `/`), callers must percent-encode them in the URL. The FastAPI path parameter will decode the value before it reaches the service. The router and service do no additional encoding/decoding; the raw decoded value is used as-is for the DDB key.

### Cascade delete on opportunity delete

When an opportunity is deleted (OPP-002 `DELETE /ui/sales/opportunities/{opp_id}`), associated contact-role rows are **not** automatically removed in this ticket. The rows become orphaned under the same partition. This is acceptable because:

1. They share the same partition key as the (now-soft-deleted) META row and are invisible via the `get_opportunity` ownership gate.
2. Opportunity delete in OPP-002 is a soft delete (sets `deleted_at`); the rows remain co-located for potential restore.

If hard-delete or explicit cleanup is required (e.g., for GDPR erasure), a follow-up ticket should add a `purge_contact_roles(owner_sub, opp_id)` helper that queries `begins_with(f"OPP#{opp_id}#CONTACT#")` and batch-deletes all rows. This is documented as an open question in Section 10.

### `include_contacts=true` on single-get

The `GET /{opp_id}?include_contacts=true` path makes two DDB calls: one for the META row (`get_item`) and one for the contact-role rows (`query`). Both are under the same `USER#{owner_sub}` partition. The second call is only made when `include_contacts=true`; the default `false` means zero additional DDB cost for existing callers.

### Pagination on `list_contact_roles`

While most opportunities have a small number of contacts (SuiteCRM rarely exceeds 20 per opportunity in practice), the list loop uses `LastEvaluatedKey` unconditionally as a correctness guarantee. The endpoint returns the full list in one response with no cursor; pagination is only internal (DDB 1MB page boundary). If an opportunity ever has hundreds of contacts, a `cursor` / `limit` query parameter can be added as a non-breaking extension.

### Audit trail

Every state change emits a structured `audit_event` call via `app/services/alerts.audit_event` (`app/services/alerts.py:644`):

- Add: `audit_event("opportunity.contact_role_added", owner_sub, None, opp_id=..., contact_ref=..., contact_role=...)`
- Remove: `audit_event("opportunity.contact_role_removed", owner_sub, None, opp_id=..., contact_ref=...)`

These calls are synchronous and fire-and-forget (the function catches all exceptions internally). They do not pass a `request` object because the service layer does not take `Request` as a parameter (consistent with OPP-002's audit calls and the pattern in `app/services/tickets.py`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

There are no `if S.dev_mode` or `if S.dev_mode else` branches anywhere in OPP-004's code path. DynamoDB writes use `T.sales_opportunities` which is wired through `_safe_table` in OPP-001 — the same code path in both dev (DynamoDB Local on port 8001) and prod (real DynamoDB). The moto mock used in tests intercepts at the botocore layer, meaning the service code is identical between the test runner and production.

No S3, KMS, SES, or Stripe calls are made. No mock-specific code paths exist.

### Idempotency

- `add_contact_role`: **Not idempotent.** A duplicate `(opp_id, contact_ref)` pair returns 409. Callers that need idempotent upsert should DELETE then POST.
- `list_contact_roles`: **Fully idempotent.** Read-only.
- `remove_contact_role`: **Idempotent with caution.** A second DELETE on the same key returns 404 (not 204). This is intentional — callers should not silently swallow 404 on remove, as it may indicate a logic error.

### Security

**Authorization:** All three endpoints use `require_ui_session`. The DDB key structure (`pk=USER#{owner_sub}`) structurally enforces ownership — no explicit authz check is needed beyond the keyed lookup described in Section 5.

**Input validation:** `contact_ref` is validated as a non-empty string of max 255 chars. `contact_role` is validated against the `CONTACT_ROLES` tuple at the Pydantic layer (field validator on `OppContactRoleIn`) and again in the service as defence-in-depth. Unknown values produce a Pydantic 422 before any DDB call is made.

**No money-out path:** OPP-004 has no billing, refund, or ledger involvement. The billing primitives (`billing_shared.py`, `refund_payment`, `settle_or_reverse_ledger`) are not touched.

**No KMS or sensitive data:** `contact_ref` is stored in plaintext. It is expected to be an opaque user-controlled identifier (a `user_sub`, a party UUID, or a display name). If PII storage constraints arise for a specific deployment, the follow-up PTY integration can apply KMS encryption to the resolved party record, not to this junction row.

**CSRF:** `require_ui_session` enforces CSRF on non-GET requests when the cookie auth path is active (`app/services/sessions.py:330`). The `POST` and `DELETE` endpoints are therefore CSRF-protected automatically via the session dependency.

## 8. Backward Compatibility & Migration

### Wire compatibility

`OpportunityOut` gains a new field `contact_roles: List[OppContactRoleOut] = Field(default_factory=list)`. Because it defaults to `[]`, all existing OPP-002 callers (list, GET single, PATCH, create responses) continue to receive the same shape with an additional empty list. JSON clients that parse strictly by field name (not positional) are unaffected. Clients that strip unknown fields are unaffected. The change is additive-only.

### DynamoDB schema migration

No new tables, no new GSIs. The new contact-role rows use the existing `pk`/`sk` primary key with an extended sort key prefix. DynamoDB Local and real DynamoDB accept new item shapes in an existing table without schema changes. No migration step is required.

## 10. Open Questions / Assumptions

1. **Cascade delete on opportunity hard-delete.** OPP-004 does not clean up contact-role rows when an opportunity is deleted. OPP-002's delete is a soft delete, so orphaned rows are harmless for now. If a hard-delete or GDPR erasure path is added in a future ticket, it must call `purge_contact_roles(owner_sub, opp_id)` before removing the META row. **Assumption:** defer to the GDPR/erasure ticket.

2. **`contact_ref` URL encoding.** If callers use `user_sub` values that contain characters outside URL path-safe characters (e.g., `@`), the DELETE endpoint requires percent-encoding. The current platform `user_sub` values are UUID-hex strings (`usr_` prefix + hex), so this is not an immediate concern. **Assumption:** document in OpenAPI description; no server-side workaround needed.

3. **Admin visibility of contact roles.** Admins cannot currently list or modify contact roles for other users' opportunities via this ticket. If admin support is needed (e.g., for CRM data quality audits), a future ticket should add `GET /ui/admin/sales/opportunities/{opp_id}/contacts` using `require_admin_or_root` (`app/auth/policy.py:67`). **Assumption:** out of scope for OPP-004.

4. **Contact role deduplication semantics.** The current design prevents duplicate `(opp_id, contact_ref)` pairs — a given contact can appear only once per opportunity. If multi-role-per-contact is a future requirement (e.g., someone is both Decision Maker and Executive Sponsor), the SK scheme would need to change to `OPP#{opp_id}#CONTACT#{contact_ref}#{role}`. **Assumption:** one role per contact per opportunity is sufficient for SuiteCRM parity.

5. **`contact_ref` resolution enrichment.** Once PTY-004 (party CRUD) ships, `OppContactRoleOut` should include resolved party name/email. The follow-up ticket should add an optional `contact_party: Optional[CrmPartyOut]` field and lazy-resolve it when PTY is available. **Assumption:** OPP-004 stores the raw `contact_ref` only; PTY resolution is a separate ticket.

6. **Pagination on list endpoint.** The current `list_contact_roles` returns all contacts in one response. This is acceptable given expected cardinality (SuiteCRM practice shows <20 contacts per opportunity). **Assumption:** no pagination cursor needed on the public response; the internal loop via `LastEvaluatedKey` is sufficient.

### Platform extension points (future)

- **PTY-004 / PTY-006** (`docs/ofbiz/specs/` — Party CRUD and contact mechanisms). Once these ship, `contact_ref` can be resolved to a `CrmPartyOut`. OPP-004 is designed for forward compatibility: the `contact_ref` field is opaque, stored as-is, and the `OppContactRoleOut` model has a clear extension point for a future `contact_party` field.

- **MARKETING_CAMPAIGNS (MKT)** — Campaign contact targeting could read `contact_ref` values from opportunity-contact junctions to build campaign audiences. OPP-004's `list_contact_roles` function is the natural read surface for this.

- **PARTY_CRM (PTY)** — The full PTY buildout (party groups, org accounts, person contacts) is the long-term owner of the `contact_ref` namespace. OPP-004 is deliberately PTY-agnostic to avoid a blocking dependency.
