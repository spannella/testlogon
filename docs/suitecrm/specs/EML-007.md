# EML-007 — Email archiving — relate email to CRM record

**Ticket:** EML-007  
**Type:** Feature  
**Priority:** P2  
**Estimate:** 2d  
**Feature flag:** `EMAIL_ARCHIVING_ENABLED` (default `false`)

---

## 1. Summary & Goal

EML-007 allows a user to associate a synced email message (stored in `user_email_messages` by EML-004) with a CRM record — currently a support ticket (`ticket`) or a personal contact (`contact`), with org-account (`org_account`) deferred until the PTY (Party CRM) tickets ship. Once archived, any authorised viewer of that CRM record can see a chronological list of all related email threads directly on the record.

This mirrors the SuiteCRM "Relate to" button on the Emails module. The gap analysis in `docs/suitecrm/CRM_EMAIL_TICKETS.md` (header, lines 1–16) identifies this as the primary missing "email-to-CRM linkage" capability. The feature is entirely additive: with `EMAIL_ARCHIVING_ENABLED=0` the platform is byte-for-byte unchanged.

## 3. Data Model

### 3.1 New DynamoDB table: `email_archive`

This is a new table dedicated to the archive link records. It does **not** reuse `user_email_messages` or `tickets` because the access pattern is entity-centric (list all emails for a ticket) rather than user+account-centric.

**Table name setting:** add `email_archive_table_name: str = os.environ.get("EMAIL_ARCHIVE_TABLE_NAME", "email_archive")` to `Settings` in `app/core/settings.py`.

**Primary key:**

| Attribute | Type | Value pattern |
|-----------|------|---------------|
| `pk` | S | `ENTITY#{entity_type}#{entity_id}` — e.g. `ENTITY#ticket#tkt_abc123` |
| `sk` | S | `EMAIL#{date_ts:010d}#{message_id_hash}` — zero-padded Unix timestamp + first 16 hex chars of `sha256(message_id)` |

The composite `sk` format sorts archived emails by message date ascending under each entity partition. `sha256(message_id)[:16]` is the collision-resistant disambiguation suffix for same-second messages; it is also the handle used in the `DELETE` path.

**Item attributes:**

```
entity_type:     str    "contact" | "ticket"   (org_account deferred until PTY ships)
entity_id:       str    ticket_id or contact_id
user_sub:        str    who performed the archive action
account_id:      str    which EML-003 IMAP account the message belongs to
uid:             int    IMAP UID in user_email_messages (integer, stored as N via _FloatSafeTable)
message_id:      str    RFC-2822 Message-ID header value (full, untruncated)
message_id_hash: str    sha256(message_id)[:16] — stable identifier for DELETE
subject:         str    copied from user_email_messages at archive time (max 500 chars)
from_addr:       str    copied from user_email_messages (max 320 chars)
snippet:         str    first 200 chars of plain-text body, copied from source message
date_ts:         N      Unix timestamp from message Date header
archived_at:     N      now_ts() — when the user clicked "Relate to"
```

**GSI — `ByUser`:**

| Attribute | Type | Value |
|-----------|------|-------|
| GSI PK | S | `USER#{user_sub}` |
| GSI SK | N | `archived_at` |

This lets users view their own archiving history ("what have I linked?") independently of entity. `attr_types={"archived_at": "N"}` required in `scripts/local-ddb-init.py` (CLAUDE.md DynamoDB gotcha — numeric GSI sort keys must be declared).

`date_ts` is a numeric attribute but it appears only in the base-table SK (as the zero-padded string `date_ts:010d`), so it does not need a separate numeric `attr_types` declaration. If a future GSI on `date_ts` is added, `attr_types={"date_ts": "N"}` must be declared.

### 3.2 Registration in app/core/tables.py

Add `email_archive: Any` to the `Tables` dataclass (after existing `email_delivery`, before next alphabetical entry) and wire it in the `T` constructor:

```python
email_archive=_safe_table(S.email_archive_table_name),
```

`_safe_table` wraps the boto3 table in `_FloatSafeTable` (lines 65–66 of `app/core/tables.py`). `_FloatSafeTable._to_decimal` converts Python `float` → `Decimal` only (lines 20–21 of `app/core/tables.py`); Python `int` values such as `uid`, `archived_at`, and `date_ts` are passed through unchanged — boto3 accepts `int` natively and serialises them to DynamoDB `N` type without requiring `Decimal`. No manual `Decimal()` wrapping is needed for integer fields in the archive item.

### 3.3 DynamoDB init (scripts/local-ddb-init.py)

Add the following `TableDef` entry inside `_table_defs()`, after the existing `email_delivery` entry:

```python

    _resolve_table_name(S.email_archive_table_name, "email_archive"),
    "pk",
    "sk",
    gsi=[{
        "index_name": "ByUser",
        "partition_key": "gsi_user_pk",
```

The GSI partition key attribute is named `gsi_user_pk` (value `USER#{user_sub}`) rather than re-using the overloaded `pk` column, following the pattern used by the tickets table (lines 700–710 of `local-ddb-init.py`).

## 4. API / Service Design

### 4.1 Service: app/services/email_archive.py

New file. All public functions check `S.email_archiving_enabled` at call time via a shared guard that raises `HTTPException(503, {"code": "feature_disabled"})` when the flag is off.

```python
def _require_enabled() -> None:
    if not S.email_archiving_enabled:
        raise HTTPException(503, {"code": "feature_disabled", "feature": "email_archiving"})
```

**`archive_email(user_sub: str, account_id: str, uid: int, entity_type: str, entity_id: str) -> dict`**

1. Calls `_require_enabled()`.
2. Validates `entity_type in {"contact", "ticket"}` — raises 400 `invalid_entity_type` otherwise. (`org_account` is not yet supported.)
3. Resolves the source message: `T.user_email_messages.get_item(Key={"pk": f"USER#{user_sub}#ACCT#{account_id}", "sk": f"MSG#{uid:010d}"})` — raises 404 `message_not_found` if absent.
4. Validates entity ownership:
   - `ticket`: calls `STORE.get_ticket(entity_id)` (imported from `app.services.tickets`); raises 404 if absent. Raises 403 `access_forbidden` if `ticket["owner_sub"] != user_sub` and the caller is not admin/root. (The service accepts an optional `is_admin: bool = False` parameter; the router passes `user.role in {Role.ADMIN, Role.ROOT}` — the codebase pattern from `app/auth/roles.py:61` (`role_allows_admin_features`) and `app/routers/tickets.py:207–208` (`_is_admin`). Do NOT use `user.role >= Role.ADMIN`; `Role` is a `str` enum and string ordering is lexicographic, not semantic.)
   - `contact`: calls `T.contacts.get_item(Key={"owner_id": user_sub, "contact_id": entity_id})` — raises 404 if absent (contacts are per-owner, so a missing item already implies no access).
5. Computes `message_id_hash = hashlib.sha256(message["message_id"].encode()).hexdigest()[:16]`.
6. Constructs `sk = f"EMAIL#{message['date_ts']:010d}#{message_id_hash}"`.
7. Calls `T.email_archive.put_item(Item={...}, ConditionExpression=Attr("pk").not_exists() | ...)` using an unconditional put (idempotent: repeated archiving of the same message to the same entity overwrites with identical data — acceptable because all fields are deterministic from source).
8. Calls `audit_event("email_archived", user_sub, request=None, entity_type=entity_type, entity_id=entity_id, message_id=message["message_id"], account_id=account_id)`.
9. Returns the newly-written item as a dict.

**`list_archived_emails(entity_type: str, entity_id: str, *, limit: int = 25, cursor: str | None = None) -> tuple[list[dict], str | None]`**

1. Calls `_require_enabled()`.
2. Queries the base table: `KeyConditionExpression=Key("pk").eq(f"ENTITY#{entity_type}#{entity_id}")`, `ScanIndexForward=True` (chronological), `Limit=limit`, `ExclusiveStartKey=decode_cursor(cursor)` when cursor is non-None.
3. Returns `(items, encode_cursor(resp.get("LastEvaluatedKey")))`.

**`get_archive_entry(entity_type: str, entity_id: str, sk: str) -> dict | None`**

Helper for unarchive; fetches a single item by its full PK+SK. Used internally; not exposed directly as an endpoint.

**`unarchive_email(user_sub: str, entity_type: str, entity_id: str, message_id_hash: str, *, is_admin: bool = False) -> None`**

1. Calls `_require_enabled()`.
2. Scans for the item by querying `pk = f"ENTITY#{entity_type}#{entity_id}"` with a begins-with filter on SK `EMAIL#%#{message_id_hash}` to locate the full SK. (Alternatively, the DELETE endpoint accepts the full `date_ts` to reconstruct the SK directly — see §4.2.)
3. Checks `item["user_sub"] == user_sub or is_admin`. Raises 403 `unarchive_forbidden` if neither.
4. Calls `T.email_archive.delete_item(Key={"pk": ..., "sk": ...})`.
5. Calls `audit_event("email_unarchived", user_sub, entity_type=entity_type, entity_id=entity_id, message_id_hash=message_id_hash)`.

### 4.2 Router: app/routers/email_archive.py

New file. Prefix `/ui/email/archive`, tag `email-archiving`. Registered in `app/main.py` after `admin_email_router` (line 778).

Auth: all endpoints use `Depends(get_authenticated_user)` for the `AuthenticatedUser` object (from `app.auth.deps`) plus `Depends(require_ui_session)` for the session context dict (`user_sub`). Cookie + CSRF path for browser use; Bearer path for API clients (skips CSRF per CLAUDE.md auth section).

**`POST /ui/email/archive`**

- Body: `ArchiveEmailIn`
- Auth: `require_ui_session`
- Response: `ArchivedEmailOut` (201)
- Calls `email_archive.archive_email(user_sub, payload.account_id, payload.uid, payload.entity_type, payload.entity_id, is_admin=user.role in {Role.ADMIN, Role.ROOT})`.

**`GET /ui/email/archive/entity/{entity_type}/{entity_id}`**

- Auth: `require_ui_session` (ticket owner or admin; contact owner implied by lookup logic)
- Query params: `limit: int = Query(25, ge=1, le=100)`, `cursor: str | None = None`
- Response: `{"items": list[ArchivedEmailOut], "next_cursor": str | None}`
- Performs its own entity access check before calling `list_archived_emails`: for tickets, loads `STORE.get_ticket(entity_id)` and checks `ticket["owner_sub"] == user_sub or user.role in {Role.ADMIN, Role.ROOT}`; for contacts, checks `T.contacts.get_item(owner_id=user_sub, contact_id=entity_id)` exists.

**`DELETE /ui/email/archive/entity/{entity_type}/{entity_id}/{message_id_hash}`**

- Auth: `require_ui_session`
- Response: `{"ok": True}` (200) or 403/404
- Path param `message_id_hash` is the 16-char hash from the `sk` (also stored as `item["message_id_hash"]`).
- The router reconstructs the SK by querying with `begins_with` on the hash suffix (or by accepting `date_ts` as an additional query param `?date_ts=1234567890` to allow exact key reconstruction: `sk = f"EMAIL#{date_ts:010d}#{message_id_hash}"`).
- Calls `email_archive.unarchive_email(user_sub, entity_type, entity_id, message_id_hash, is_admin=user.role in {Role.ADMIN, Role.ROOT})`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Duplicate archive (idempotency)

Archiving the same `(account_id, uid)` pair to the same `(entity_type, entity_id)` a second time produces an identical `pk`/`sk` and calls `put_item` unconditionally. DynamoDB replaces the existing item with byte-for-byte identical data (all fields are deterministic). No error is raised; the endpoint returns the item as if it were new. This is correct: the client may retry on network error.

### 5.2 Archiving to multiple entities

The same email can be archived to multiple entities (e.g., a ticket AND a contact) by calling `POST /ui/email/archive` twice with different `entity_type`/`entity_id` values. Each creates a separate row under a different `pk`, so there is no conflict. This is the intended SuiteCRM "Relate to multiple records" behaviour.

### 5.3 Message deleted from user_email_messages (EML-004 purge)

If a user later removes the source message from `user_email_messages` (EML-004 provides no explicit delete endpoint in the current spec, but message expiry via TTL is planned), existing archive rows become dangling references. The archive row retains the copied subject/snippet/from_addr, so the read path continues to return useful display data. The `uid` field is no longer resolvable to the live message but this is acceptable — the archived metadata itself has historical value. A future cleanup sweep can be added if needed.

### 5.4 Ticket deleted after archiving

If `STORE.get_ticket(entity_id)` returns `None` during a `GET /ui/email/archive/entity/ticket/{id}` call, the router raises 404 `ticket_not_found`. Existing archive rows are not cascade-deleted (no DDB streams in this design). A tombstone clean-up can be added as a follow-up.

### 5.5 Contact ownership edge case

A contact with `contact_id=X` owned by user A cannot be accessed by user B, even if user B's tickets reference user X. The `T.contacts.get_item(Key={"owner_id": user_sub, "contact_id": entity_id})` lookup inherently enforces this because the composite key includes `owner_id`.

### 5.6 Admin access to entity archives

An ADMIN or ROOT actor can call `GET /ui/email/archive/entity/{type}/{id}` for any entity (the entity-ownership check is skipped when `user.role >= Role.ADMIN`). Admins cannot archive emails on behalf of another user; `user_sub` in the archive row always records the requesting actor.

### 5.7 entity_type = org_account (deferred)

Any request with `entity_type="org_account"` receives `400 invalid_entity_type` with body `{"code": "entity_type_not_supported", "detail": "org_account support requires PTY tickets"}`. This is explicitly gated in `_require_entity_type_supported()` inside the service. When PTY ships and `T.organizations` is available, this gate is lifted and a new validation branch is added.

### 5.8 Large entity archives (DynamoDB page size)

A support ticket that has received thousands of emails will accumulate many archive rows under the same partition. `list_archived_emails` uses `Limit=limit` (max 100 per call) and returns a `next_cursor`; callers must paginate. DynamoDB's `FilterExpression` is not used (all rows in the partition are valid archive entries), so the `Limit` directly controls page size without the silent-miss hazard described in CLAUDE.md.

### 5.9 Rate limiting

No dedicated rate limit is added for EML-007 beyond the existing session-auth rate limiting already applied to all `/ui/` endpoints. If abuse becomes a concern, the existing `app/services/rate_limit.py` `_bucket_limit` primitive can be wired to `POST /ui/email/archive` in a follow-up.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 — no dev_mode branches

The `email_archive` service has no `if S.dev_mode` branch. DynamoDB access goes through `T.email_archive` in both environments — moto intercepts boto3 calls in dev, real DynamoDB in prod. The service does not call IMAP/SMTP or SES; it only reads from `T.user_email_messages` and writes to `T.email_archive`. There is no mock path to maintain separately.

The `audit_event` call at `app/services/alerts.py:644` is already dev-mode-aware (it writes to the dev email log in dev, fires SNS in prod) without any branching in EML-007's code.

### 7.2 Idempotency

The `archive_email` function uses an unconditional `put_item` (DynamoDB's natural idempotency for full-item overwrites). Because all archive item fields are derived deterministically from the source message and the request parameters, a retry of a successful archive produces an identical DynamoDB write with no observable side effect beyond a second `audit_event` entry. This is acceptable. If strict once-only audit is required, a `ConditionExpression=Attr("pk").not_exists()` can be added as a follow-up; for now the simplicity of unconditional put is preferred.

### 7.3 Security

**Data isolation:** The `list_archived_emails` service function does not enforce entity ownership — it returns all rows for the given PK. Ownership enforcement is the router's responsibility: the router performs the entity access check before calling the service. Tests must cover the 403 paths.

**CSRF:** Cookie-auth POST/DELETE requests to `/ui/email/archive` go through the standard `require_ui_session` path which validates the `x-csrf-token` header against the session's stored `csrf_token` and the `ui_csrf` cookie (CLAUDE.md auth section). Bearer-auth requests skip CSRF validation.

**Input validation:** `entity_type` is validated to the allow-list `{"contact", "ticket"}` before any DynamoDB reads. `uid` is typed as `int` in the Pydantic model; Pydantic rejects non-integer values at parse time. `account_id` is a string that is used only as part of a DynamoDB key — no SQL injection risk.

**Snippet truncation:** The `snippet` field is populated from `user_email_messages["snippet"]` which EML-004 already truncates to 200 characters at sync time. No additional truncation is needed here, but the service caps it defensively at 200 chars before writing.

**No credentials stored:** EML-007 does not store IMAP/SMTP credentials. It copies only non-sensitive message metadata (subject, snippet, from address). KMS encryption is not required.

## 8. Backward Compatibility & Migration

### 8.1 Additive only

With `EMAIL_ARCHIVING_ENABLED=0` (the default):
- The new `T.email_archive` table handle is wired at startup but never accessed.
- The `email_archive` router is registered but all endpoints immediately return 503 via `_require_enabled()`.
- No existing endpoint, table, model, or middleware is modified.
- The `Settings` dataclass gains one new field with a default — frozen dataclass addition is backwards-compatible in Python.

### 8.2 Table creation

The `email_archive` table is created at stack startup by `scripts/local-ddb-init.py`. In dev, `just restart` recreates the table. In prod, the table must be created via `CreateTable` API call before `EMAIL_ARCHIVING_ENABLED=1` is set; there is no data backfill required (the table starts empty).

### 8.3 EML-003 / EML-004 dependency

EML-007 reads from `T.user_email_messages` which is created by EML-004. `T.user_email_messages` must be present and populated before any archive operation makes sense. At the API level, if the source message does not exist, `archive_email` returns 404 — no crash. The feature flag guard ensures that even if the table exists but `EMAIL_CLIENT_ENABLED=0`, the EML-004 sync endpoints that populate it are unavailable, making archive creation impossible in practice. `EMAIL_ARCHIVING_ENABLED` should only be set to `1` after `EMAIL_CLIENT_ENABLED=1` and accounts/sync are functional.

### 8.4 tables.py / settings.py extension

Adding new fields to the frozen `Settings` dataclass and the `Tables` dataclass follows the existing pattern used throughout the codebase (verified by checking the hundreds of existing fields). No migration is needed.

## 10. Open Questions / Assumptions

1. **`org_account` entity type**: This spec defers `org_account` support until the PTY (Party CRM) tickets provide the `T.organizations` table and ownership model. The deferral is enforced by a named error code (`entity_type_not_supported`) rather than a silent failure, so the frontend can display an informative message.

2. **Message deletion / dangling archive rows**: EML-004 does not yet define a message-deletion or TTL-expiry endpoint. When it does, a DynamoDB stream or a periodic cleanup sweep should be added to remove archive rows whose source messages have been purged. This spec leaves those rows in place (they retain the copied metadata) until that design decision is made.

3. **Thread-level archiving**: SuiteCRM's "Relate to" links a full email thread to a record, not just a single message. This spec archives individual messages. Thread-level archiving (linking all messages sharing a `thread_id` in one operation) is a follow-up; the data model supports it by calling `archive_email` for each message in the thread.

4. **Bidirectional UI surface**: This spec defines the backend only. The frontend CRM record views (ticket detail page, contact detail page) need an "Archived Emails" tab calling `GET /ui/email/archive/entity/{type}/{id}`. That UI work is deferred to EML-005 or a follow-up frontend ticket.

5. **`date_ts` timezone**: The `date_ts` field is stored as a Unix timestamp (seconds since epoch, UTC). Message headers may contain timezone-aware dates. The EML-004 sync service is responsible for converting the `Date:` header to UTC Unix time before writing to `user_email_messages`. EML-007 copies the value verbatim.

6. **Snippet content vs. sensitivity**: Email snippets may contain personal information. The archive row copies up to 200 characters of the message body. Admins with `GET entity/{type}/{id}` access can read snippets for tickets they administer. This is acceptable for a support ticket context but should be reviewed against data-minimisation requirements before enabling in regulated environments.
