# CAS-014 — Customer self-service portal (guest ticket submission)

**Type:** Feature  **Priority:** P2  **Estimate:** 3 days
**Ticket source:** `docs/suitecrm/CRM_CASES_PORTAL_TICKETS.md`, section "CAS-014"

---

## 1. Summary & Goal

CAS-014 adds a **public, account-free case-submission flow** that lets external users (customers who have no platform account) file a support ticket using only their email address. The flow mirrors SuiteCRM's Joomla-style customer portal: the submitter provides an email, receives a one-time verification link, confirms ownership, and is then issued a short-lived portal token that authorizes ticket creation and read-back — all without a session cookie or Cognito account.

Concrete deliverables:

1. Four new public endpoints under `/public/cases/` (start, verify, submit, read).
2. A new `PortalSessionService` in `app/services/portal_sessions.py` that mints, verifies, and consumes HMAC-signed portal tokens backed by `T.crm_cases_portal_sessions` (scaffolded by CAS-001).
3. Extension of `TicketStore.create_ticket` to accept `owner_sub=f"guest:{email}"` and persist `submitter_email` without modifying any existing caller.
4. Two new frontend pages (`/support/new`, `/support/tickets/:ticketId`) under `frontend/src/pages/tickets/PortalPage.tsx`.
5. Extension of `render_ticket_email_template` (CAS-004) to cover the new `portal_ticket_created` event type.

With `CRM_CASES_PORTAL_ENABLED=0` (the default), the platform is byte-for-byte identical to today. All four endpoints return 404, no background worker starts, and `TicketStore` behavior is unchanged.

## 2. Context & Current State

### 2.1 Existing ticket creation path

`TicketStore.create_ticket` (`app/services/tickets.py:411–512`) accepts `owner_sub: str` and writes the META row at `pk=TICKET#{ticket_id} / sk=META` with a hard `status="open"`. The idempotency guard at line 431 (`existing = self.get_ticket(resolved_ticket_id); if existing: return existing`) means the method is safe to call with a deterministic `ticket_id`. No field in the current signature or META item stores a `submitter_email` or differentiates guest vs authenticated ownership; both fields are absent from `TicketOut` (`app/routers/tickets.py:58–73`) and `TicketListItemOut` (line 91–110). No existing caller passes a `guest:` prefix — the owner column is always a Cognito `user_sub` UUID today.

### 2.2 Existing `TicketOut` and `CreateTicketReq` models

`CreateTicketReq` (`app/routers/tickets.py:173`) currently accepts only `subject` and `description`. `TicketOut` (line 58) exposes `ticket_id`, `subject`, `owner_sub`, `status`, `space_id`, `assigned_admin_sub`, `assigned_to_sub`, `assigned_by`, `assigned_at`, `created_at`, `updated_at`, `version`, and `messages`/`activity` lists — **no GSI key columns** (gsi* attributes are internal DDB storage columns, absent from `TicketOut`), no `case_number` (CAS-002), no `submitter_email`, and no `public_ticket_url`. Adding `submitter_email: str | None = None` and `case_number: str | None = None` (already defined by CAS-002) to `TicketOut` is purely additive and backward-compatible — existing deserialization is unaffected because both fields default to `None`.

### 2.3 HMAC token scheme

`app/core/crypto.py:35–61` provides `mint_ws_token(user_sub, ttl_seconds) -> str` (line 35) and `verify_ws_token(token) -> dict | None` (line 44). Both use the module-level pattern: `b64url(JSON payload).b64url(HMAC-SHA256 sig)`, keyed on `S.ws_token_secret`. Cart recovery (`app/services/cart_reminders.py:150–211`) uses the identical approach with a `jti` claim plus a `RECOVERY#CONSUMED#{jti}` row in DDB for single-use enforcement via `ConditionExpression="attribute_not_exists(pk)"` (line 207). CAS-014 reuses the same mint/verify/consume triple — NOT by calling `mint_ws_token` directly (which is keyed on `S.ws_token_secret`) but by replicating the signing pattern with its own HMAC, keyed on `S.crm_cases_portal_signing_secret` falling back to `S.ui_access_token_secret`. The secret resolution pattern follows `_recovery_secret()` at `app/services/cart_reminders.py:144–147` (the function that resolves `S.cart_recovery_link_secret or "dev-cart-recovery-secret"`); `S.cart_recovery_link_secret` itself resolves via `app/core/settings.py:826–829` (`os.environ.get("CART_RECOVERY_LINK_SECRET") or os.environ.get("UI_ACCESS_TOKEN_SECRET", "")`). Note: `app/services/cart_reminders.py:165` is the HMAC signing call, not the secret resolution function. CAS-014 stores consumption markers in `T.crm_cases_portal_sessions`.

### 2.4 `send_alert_email` and `render_ticket_email_template`

`send_alert_email` (`app/services/alerts.py:459`) sends plain-text email in production via `boto3 ses.send_email` and writes to a dev log file when `S.dev_mode` is `True` (line 462–468). `render_ticket_email_template` (line 235) handles exactly five event types: `ticket_created`, `ticket_assigned`, `ticket_replied`, `ticket_status_changed`, `ticket_reopened`. A sixth type `portal_ticket_created` is not yet present. CAS-004 (spec `docs/suitecrm/specs/CAS-004.md`) has already extended this template function to add HTML bodies and new event types; CAS-014 depends on CAS-004 to wire the new event type into the same facility.

## 3. Data Model

### 3.1 `crm_cases_portal_sessions` (existing table, CAS-001)

This table already exists per CAS-001 scaffolding. CAS-014 defines its item schema:

| Attribute | Type | Notes |
|---|---|---|
| `token` | S (PK) | Opaque HMAC token string (the `b64url(payload)` portion only — not the full `payload.sig` compound; the sig is stored separately). |
| `sk` | S (SK) | Always `"META"` |
| `submitter_email` | S | Email provided in `POST /public/cases/start` |
| `subject` | S | Ticket subject carried through the flow |
| `description` | S | Ticket description (up to 4000 chars) |
| `state` | S | Enum: `"pending_verification"`, `"verified"`, `"submitted"` |
| `created_at` | N | Unix timestamp (`now_ts()`); GSI `ByEmail` sort key — **must be numeric (`attr_types={"created_at": "N"}`)**. Already declared in CAS-001. |
| `expires_at` | N | TTL attribute (`now_ts() + 3600`). DDB TTL is enabled on this attribute so stale unverified sessions are auto-purged. |
| `verified_at` | N | Set when `state` transitions to `"verified"` |
| `portal_token_hash` | S | SHA-256 hex of the issued `portal_token` (the full `payload.sig` compound); the raw portal token is **never stored** — only its hash |
| `portal_token_expires_at` | N | `now_ts() + 900` (15 min) |
| `consumed_at` | N | Set during the atomic submit conditional-write; `attribute_not_exists(consumed_at)` guards single-use |
| `ticket_id` | S | Populated after successful submit |

**GSI** — `ByEmail` (already declared by CAS-001):
- Partition key: `submitter_email` (S)
- Sort key: `created_at` (N)
- Purpose: list a submitter's historical portal sessions by email

**DDB TTL**: enable TTL on `expires_at` in `scripts/local-ddb-init.py` for the `crm_cases_portal_sessions` table. No schema change needed — DDB TTL is configured at the table level via `TimeToLiveSpecification` in the `TableDef` factory (already supported by the codebase pattern).

### 3.2 `tickets` table — additive fields on the META item

No new GSIs are needed. Two new attributes are written to existing META rows **only when `S.crm_cases_portal_enabled`** is on and `create_ticket` is called from the portal path:

| Attribute | Type | Notes |
|---|---|---|
| `submitter_email` | S | Raw email of the portal guest |
| `is_portal_ticket` | BOOL | `True` for portal-originated tickets; allows admin filtering |

These attributes are absent from all non-portal ticket rows — DDB sparse attributes, never queried by existing GSIs. `get_ticket` (`app/services/tickets.py:522`) already returns `header.get(key)` for any attribute, so no structural change is needed to surface these fields.

## 4. API / Service Design

### 4.1 Service: `app/services/portal_sessions.py` (new file)

```python
class PortalSessionService:
    def __init__(self) -> None:
        self._table = T.crm_cases_portal_sessions

    def _portal_secret(self) -> str: ...  # fallback to S.ui_access_token_secret

    def mint_verification_token(
        self, *, submitter_email: str, subject: str, description: str
    ) -> tuple[str, str]:
        """
        Returns (token_key, full_token) where:
          - token_key = b64url(payload) — used as PK in DDB
          - full_token = b64url(payload).b64url(sig) — embedded in email link
        Writes 'pending_verification' session row with TTL.
        """

    def verify_token(self, full_token: str) -> dict[str, Any]:
        """
        Validates HMAC + expiry. Transitions state to 'verified'.
        Issues a short-lived portal_token (15 min), stores only its SHA-256 hash.
        Returns {'portal_token': str, 'submitter_email': str, 'subject': str, 'description': str}.
        Raises HTTPException 401 portal_token_invalid on bad/expired token.
        Raises HTTPException 409 portal_token_already_used if state != 'pending_verification'.
        """

    def validate_portal_token(self, portal_token: str) -> dict[str, Any]:
        """
        Looks up session by SHA-256(portal_token) via table scan on hash attr, or
        structured lookup via token_key stored in the portal_token payload.
        Returns session dict if valid and not consumed.
        Raises HTTPException 401 portal_token_invalid on any failure.
        """

    def submit_ticket(
        self, portal_token: str, ticket_id: str
    ) -> bool:
        """
        Atomically marks session consumed via conditional update_item
        with ConditionExpression='attribute_not_exists(consumed_at)'.
        Writes consumed_at + ticket_id to the session row.
        Returns True on success, False if already consumed (idempotent replay).
        """

    def get_session_for_ticket(self, ticket_id: str, portal_token: str) -> dict[str, Any]:
        """
        Validates portal_token, returns session.
        Asserts session.ticket_id == ticket_id (ownership check).
        """
```

The `validate_portal_token` lookup avoids a full table scan: the minted `portal_token` payload carries `token_key` (the DDB PK) so the lookup is a direct `get_item` on `T.crm_cases_portal_sessions` with `Key={"token": token_key, "sk": "META"}`, then SHA-256 of the submitted full token is compared against the stored `portal_token_hash`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Email-first verification flow

1. Client `POST /public/cases/start {email, subject, description}`.
2. Server mints a verification token whose payload contains `{token_key, email_hash, exp, iat, jti}` (no PII in the token itself; `email_hash` = `sha256(email)` for binding without leaking the address).
3. Session row written: `{token: token_key, sk: "META", submitter_email: email, subject, description, state: "pending_verification", created_at, expires_at: now+3600}`.
4. Email sent to the address with link `{S.public_base_url}/public/cases/verify/{full_token}`.
5. Client clicks link → `GET /public/cases/verify/{full_token}`.
6. Server: HMAC verify → OK; check `state == "pending_verification"` → OK; mint `portal_token` (TTL 15 min); hash it; update session row `{state: "verified", verified_at, portal_token_hash, portal_token_expires_at}`; redirect to `/support/new?portal_token={portal_token}`.
7. Frontend receives `portal_token` from the URL query param and stores it in `sessionStorage` (not `localStorage` — tab-scoped only).
8. Client `POST /public/cases/submit {subject, description}` with `X-Portal-Token` header.
9. Server: validate portal token; lookup session by `token_key`; compare `sha256(portal_token)` vs stored hash; check `portal_token_expires_at > now`; check `consumed_at` absent; call `STORE.create_ticket`; atomically mark consumed.
10. Response: `{ticket_id, case_number, public_ticket_url}`.

### 5.2 Double-submit / replay protection

`submit_ticket` uses a DDB conditional update: `ConditionExpression="attribute_not_exists(consumed_at)"`. If the condition fails (token already consumed), the handler catches `ConditionalCheckFailedException` and checks whether a `ticket_id` is already stored on the session. If yes, it returns the stored ticket's data (idempotent replay). If no `ticket_id` is found despite consumed_at being set, it returns HTTP 409 `portal_submit_already_consumed`. This mirrors the cart recovery one-time-use pattern at `app/services/cart_reminders.py:198–211`.

### 5.3 Expired verification link

`GET /public/cases/verify/{full_token}` with an expired token: `verify_ws_token` returns `None` because `exp < now`. Server redirects to `/support/error?code=portal_token_expired`. The frontend renders a user-friendly message with a "Start again" button that navigates to `/support/new`.

### 5.4 Expired portal token during submit

`portal_token_expires_at` is checked in `validate_portal_token`. If expired: 401 `portal_token_expired`. The frontend shows a banner "Your session has expired. Please verify your email again." with a link to `/support/new`.

### 5.5 Rate limiting

`POST /public/cases/start` is on the public internet. Rate limit: 5 start requests per `(IP, email)` pair per hour, using the existing DDB-backed `_bucket_limit` primitive (same pattern as `app/services/kyc_partner_api.py:rate_limit_kyc_partner_api`). Bucket key: `portal_start:{sha256(email)[:16]}`. Exceeded: 429 with `Retry-After: 3600`.

### 5.6 Agent replies visible to portal user

When an agent replies to a portal ticket via the existing `POST /tickets/{ticket_id}/reply` endpoint (authenticated), the `MSG#` sub-item is written to the tickets table in the normal way. `GET /public/cases/{ticket_id}` reads the same sub-items from `STORE.get_ticket(ticket_id).messages` and projects them into `PortalTicketMessageOut`. The portal user sees agent messages in real time on the next page reload (no SSE; polling is handled by the frontend `useQuery` with `refetchInterval`).

### 5.7 `owner_sub` format for guest tickets

Portal tickets carry `owner_sub=f"guest:{email}"`. This value does not match any Cognito `user_sub` and will not satisfy `T.users.get_item` lookups. Callers that currently do a user lookup on `owner_sub` (e.g., `_emit_ticket_alerts` at `app/routers/tickets.py:362`) must guard against the `"guest:"` prefix. The `_emit_ticket_alerts` function loops over `recipients`; a `"guest:email@..."` recipient is skipped for in-app alerts (no platform session) but its email is extracted for `send_alert_email`. A helper `_is_guest_owner(owner_sub: str) -> bool` (returns `owner_sub.startswith("guest:")`) and `_guest_email(owner_sub: str) -> str` (returns `owner_sub[6:]`) are added in `app/routers/portal_cases.py`.

### 5.8 `GET /public/cases/{ticket_id}` ownership

The portal token's `token_key` maps to a session row that stores `ticket_id`. The handler asserts `session["ticket_id"] == path_ticket_id`. A mismatch → 403 `portal_access_denied` (prevents guessing ticket IDs with a valid but unrelated portal token).

### 5.9 `send_alert_email` for verification and confirmation

Two new template branches are added in `render_ticket_email_template` (`app/services/alerts.py:235`):

- `portal_ticket_verification`: subject `"Please verify your email to submit a support ticket"`, body includes the verification link.
- `portal_ticket_created`: subject `"[CASE-{case_number}] Your ticket has been received"`, body includes the `public_ticket_url` for read-back.

Both follow the existing `(subject, body_text)` tuple return type. CAS-004's HTML extension also applies here through the same render function.

### 5.10 Security: no internal fields in portal response

`PortalTicketOut` strips `assigned_admin_sub`, `assigned_to_sub`, `space_id`, all `gsi*` attributes, `owner_sub`, and internal metadata keys. It only exposes `ticket_id`, `subject`, `status`, `case_number`, `created_at`, `updated_at`, and `messages`. `sender_sub` in messages is replaced by `sender_role` (`"user"` or `"agent"`) so no internal `user_sub` UUID is exposed to the unauthenticated portal user.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

`send_alert_email` already bifurcates on `S.dev_mode` (line 462–468): in dev it writes to `S.dev_email_log`; in prod it calls SES. CAS-014 uses the same call site — no new `if S.dev_mode` branch is introduced in the portal service or router. Token minting and verification use `app/core/crypto.b64url` / `hmac.new` with no environment dependency. DDB writes are identical in dev (DynamoDB Local) and prod (AWS DynamoDB). S3 is not used by CAS-014 (attachments are CAS-006). KMS is not used (portal tokens are HMAC, not KMS-encrypted — same rationale as cart recovery tokens).

### 7.2 Idempotency

- `POST /public/cases/start` with the same email+subject+description within the TTL window creates a new session row each time (different `jti`/`token_key`). Repeated clicks generate multiple pending sessions; only the most recently clicked verification link can be used (earlier tokens still verify but point to separate sessions). This is acceptable behavior; rate limiting (§5.5) caps abuse.
- `POST /public/cases/submit` with the same portal token after a successful first submit returns the stored `ticket_id` (idempotent replay; see §5.2).
- Verification link clicks are idempotent after the first: `state` is already `"verified"` → 409 `portal_token_already_used`.

### 7.3 HMAC token security

Tokens are signed with HMAC-SHA256. Secret is `S.crm_cases_portal_signing_secret` falling back to `S.ui_access_token_secret` — **must be non-empty in prod**. `verify_ws_token` (`app/core/crypto.py:44`) uses `hmac.compare_digest` (constant-time comparison) preventing timing attacks. The `jti` claim in the verification token is a UUIDv4 hex — unguessable. The `token_key` (DDB PK) is the base64-encoded payload only; the signature half is never stored (same as cart recovery). An attacker who reads the DDB row cannot reconstruct a valid full token without the signing secret.

### 7.4 Portal token scope

A portal token is scoped to one (email, session) pair. Reuse across ticket IDs is blocked by `get_session_for_ticket`'s `session["ticket_id"] == path_ticket_id` check. A portal token cannot be used to read a ticket it did not create.

### 7.5 No open redirect

The verification endpoint redirects to `{S.public_base_url}/support/new?portal_token=...`. `S.public_base_url` is a server-side setting (`app/core/settings.py:349`); it is never taken from user input. The redirect target is constructed from this controlled value only — no `next=` or similar query-param redirect is introduced.

### 8.1 No existing table changes

`TicketStore.create_ticket` gains two new keyword arguments `submitter_email: str | None = None` and `is_portal_ticket: bool = False` with defaults that preserve existing call-site behavior byte-for-byte. All existing callers in `app/routers/tickets.py` pass neither; they are unaffected.

`submitter_email` and `is_portal_ticket` are only written to portal-originated ticket META rows. The absence of these attributes from all existing ticket rows does not affect any existing query, GSI, or `FilterExpression` — DynamoDB sparse attributes are transparent.

### 8.6 No DynamoDB migration

`crm_cases_portal_sessions` is a new table with no existing data. `tickets` gains sparse attributes only. No backfill, no `UpdateTable`, no existing row mutation.

## 10. Open Questions / Assumptions

1. **Email uniqueness across sessions**: The design allows multiple simultaneous pending sessions for the same email address. If a submitter clicks "Start" twice, they get two separate sessions. Only the one they verify creates a portal token. Is there a business requirement to cancel older unverified sessions for the same email on a new Start request? The current design does not invalidate prior sessions (they expire naturally after 1h). A future CAS follow-up could add a `ByEmail` GSI query on Start to expire old pending sessions.

2. **Agent reply notifications to portal users**: When an agent replies to a portal ticket, `_emit_ticket_alerts` fires `ticket_replied`. The portal user (owner `guest:email@...`) has no in-app alert subscription. The spec assumes a best-effort outbound email is sent to `submitter_email` via `send_alert_email`. The exact hook (whether it lives in `_emit_ticket_alerts` in `app/routers/tickets.py` or in a separate `portal_notify` helper) is an implementation decision deferred to CAS-004 integration work.

3. **Portal token storage on the frontend**: The spec recommends `sessionStorage` (tab-scoped, cleared on tab close). If the user navigates away mid-flow and returns via the verification link in a new tab, the portal token from the redirect URL is available in the URL query param and can be re-extracted. An alternative is to store it in a session cookie via a server-issued `Set-Cookie`. Session cookie approach is simpler for the E2E tests but introduces cookie-auth into what is otherwise a stateless portal.

4. **CAS-002 dependency (`case_number`)**: The spec assumes CAS-002 has shipped and `_next_case_number()` is available. If CAS-014 ships before CAS-002, `case_number` will be `None` in the submit response. The spec recommends merging CAS-002 first (it is P1 vs CAS-014's P2).

5. **Attachment support for portal tickets**: CAS-006 adds file attachment endpoints guarded by `require_ui_session`. Portal users cannot upload files through those endpoints. A future follow-up (CAS-014b) could add `POST /public/cases/{ticket_id}/attachments` gated by `X-Portal-Token` and consuming the same S3 + `TicketStore.add_attachment` primitives as CAS-006.
