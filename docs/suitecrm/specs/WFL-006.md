# WFL-006 — Action executor — modify-field & create-record

**Type:** Feature | **Priority:** P1 | **Estimate:** 2d
**Depends on:** WFL-001, WFL-002, WFL-003, WFL-004, WFL-005
**Unblocks:** WFL-007 (send-email action), WFL-008 (drip sequence), WFL-009 (admin UI)

---

## 1. Summary & Goal

This ticket delivers `app/services/workflow_action_executor.py`, the action execution core of the CRM workflow rule engine. It wires a new `"crm_workflow"` executor into the existing unified scheduler's `_EXECUTORS` dispatch table (`app/services/unified_scheduler.py:28`), so that `crm_workflow` action rows enqueued by WFL-004 and WFL-005 are automatically picked up, executed, and logged.

The two action types in scope are:

- **`modify_field`**: mutates a named field on the target record by calling the existing service-layer write path (never raw DDB). For `ticket` module: `TicketStore.update_status` or `TicketStore.assign_ticket`. For `contact` module: the contacts router's `update_contact` logic.
- **`create_record`**: creates a new record in the named module via its existing service constructor. For `ticket` module: `TicketStore.create_ticket` with `owner_sub="system"`.

Every execution is logged as a run row in `T.crm_workflow_runs` (introduced by WFL-001). Downstream tickets (WFL-007, WFL-008) extend the same executor file with additional action types — this ticket establishes the pluggable `_execute_action` dispatch pattern they will follow.

With `CRM_WORKFLOW_ENABLED=0` (the default) the entire code path is unreachable: `create_action` in WFL-004/WFL-005 is never called, so no `crm_workflow` rows are ever enqueued, and the executor is never invoked by the scheduler. The platform is byte-for-byte unchanged.

## 5. Detailed Behavior & Edge Cases

### 5.1 Top-level executor flow

```
execute_crm_workflow_action(user_sub="system", payload={"rule_id", "module", "record_id", "event"})
  1. Guard: if not S.crm_workflow_enabled → return  (safety net)
  2. rule = workflow_rules.get_rule(payload["rule_id"])
     if not rule or not rule["enabled"] → return silently
     (rule deleted/disabled after enqueue — idempotent skip, no run log)
  3. run_id = _new_run_id(); started_at = now_ts(); actions_fired = []
  4. for action in rule["actions"]:
       result = await _execute_action(action, module=payload["module"],
                                      record_id=payload["record_id"])
       actions_fired.append({
           "action_type": action["action_type"],
           "result": result,
       })
  5. finished_at = now_ts()
     _write_run(..., outcome="matched", ...)
     audit_event("crm_workflow.execute", "system", rule_id=..., module=..., record_id=...)
  except Exception as exc:
     finished_at = now_ts()
     _write_run(..., outcome="error", error_message=str(exc), ...)
     raise  # re-raise so unified_scheduler.py:146 can apply retry logic
```

Re-raising on unhandled exception is deliberate: the unified scheduler's retry-then-fail logic (`schedule_retry` / `mark_action_failed` at `app/services/unified_scheduler.py:146-154`) handles backoff and eventual permanent failure, consistent with `execute_scheduled_post` and other executors in `app/services/schedule_executors.py`.

### 5.2 `_execute_action` dispatcher

```python
async def _execute_action(action, *, module, record_id) -> str:
    action_type = action.get("action_type", "")
    config = action.get("config") or {}
    if action_type == "modify_field":
        return _dispatch_modify_field(module, record_id, config)
    elif action_type == "create_record":
        return _dispatch_create_record(config)
    else:
        # Unknown action type — future types (send_email, drip_sequence) handled by WFL-007/008
        logger.warning("crm_workflow: unknown action_type=%r — skipping", action_type)
        return "skipped"
```

Unknown action types produce `"skipped"` in `actions_fired` and do not raise. This ensures partial-support scenarios (e.g., a rule with both `modify_field` and `send_email` actions deployed before WFL-007) do not block the known action steps.

### 5.3 `modify_field` — ticket module

Supported fields and their dispatch:

| `config.field` | Method called | Notes |
|---|---|---|
| `status` | `STORE.update_status(ticket_id=record_id, actor_sub="system", status=value)` | Raises `TicketStateError` for invalid status or disallowed transition — caught and returned as `"error:<msg>"` |
| `assignee_sub` | `STORE.assign_ticket(ticket_id=record_id, actor_sub="system", assignee_sub=value)` | `value=None` or empty string → skip |
| `priority` | `T.tickets.update_item(Key=..., UpdateExpression="SET priority = :v", ...)` | `priority` is a free-form string attribute; no `TicketStore` helper exists — raw `update_item` |
| `title` / `subject` | `T.tickets.update_item(Key=..., UpdateExpression="SET subject = :v", ...)` | Stored as `subject` in DDB (see `app/services/tickets.py:447`) |

For `status` and `assignee_sub`, the `TicketStore` methods are preferred over raw DDB because they maintain all GSI key attributes (`gsi2pk`, `gsi3pk`, etc.) and write activity rows. For `priority` and `subject`, which have no dedicated `TicketStore` method, a targeted `update_item` on the META row is used (Key `{"pk": f"TICKET#{record_id}", "sk": "META"}`).

When the ticket does not exist (`STORE.update_status` returns `None`), the action returns `"skipped"` and emits a warning log. It does not raise.

`TicketStateError` for invalid transitions is caught and returns `"error:invalid_ticket_status_transition"`. The run log records this in `actions_fired[i].result`. The overall `outcome` is still `"matched"` (partial execution is not a fatal executor error).

`audit_event("crm_workflow.modify_field", "system", module="ticket", record_id=record_id, field=field, value=value)` is emitted after a successful write.

### 5.4 `modify_field` — contact module

The contacts table PK is `owner_id`, SK `contact_id` (`app/routers/contacts.py:69`). To reach a contact by `record_id` alone (which is the `contact_id`), the executor must resolve `owner_id`. The payload written by WFL-004 must include `owner_id` alongside `record_id` — or `record_id` must encode both (e.g., `{owner_sub}#{contact_id}`).

**Design decision**: the payload written to `T.scheduled_actions` by `fire_on_save_hook` for contact events includes `owner_sub` in the payload dict. The executor reads `payload.get("owner_sub")` as the `owner_id` for the contacts table key.

Supported fields for contacts:

| `config.field` | `update_item` expression |
|---|---|
| `is_favorite` | `SET is_favorite = :v` (bool coercion) |
| `is_blocked` | `SET is_blocked = :v` (bool coercion) |

Other fields are logged as `"skipped"` with `reason="unsupported_contact_field"`.

`audit_event("crm_workflow.modify_field", "system", module="contact", record_id=record_id, field=field)` on success.

### 5.5 `create_record` — ticket module

```python
def _create_record_ticket(fields: dict) -> str:
    subject = fields.get("subject") or fields.get("title") or ""
    if not subject:
        return "skipped:missing_subject"
    description = fields.get("description", "")
    space_id = fields.get("space_id") or None
    labels = fields.get("labels") or []
    new_ticket = STORE.create_ticket(
        owner_sub="system",
        subject=subject,
        description=description,
        space_id=space_id,
        labels=labels,
    )
    audit_event(
        "crm_workflow.create_record",
        "system",
        module="ticket",
        new_record_id=new_ticket["ticket_id"],
        triggered_by_field=fields.get("_triggered_by_record_id", ""),
    )
    return f"ok:ticket_id={new_ticket['ticket_id']}"
```

`STORE` is imported at module level from `app.services.tickets` (the same singleton at `app/services/tickets.py:979`). `create_ticket` is idempotent when a `ticket_id` is provided (it calls `get_ticket` first and returns the existing row). For system-created tickets no `ticket_id` is passed, so a fresh one is always generated.

`create_record` for modules other than `ticket` returns `"skipped:unsupported_module"` and logs a warning.

### 5.6 Run log idempotency

`_write_run` uses `T.crm_workflow_runs.put_item(Item=item)`. If the same `run_id` is written twice (e.g., due to a retry that re-enters after a transient DDB failure), the second write is a no-op overwrite of identical data. The `run_id` is generated once at the start of `execute_crm_workflow_action` so retries produce a new `run_id` each time (since the action is re-dispatched by the scheduler's retry path which creates a fresh invocation).

### 5.7 Empty actions list

A rule with `actions=[]` is valid (conditions-only monitoring rule). `execute_crm_workflow_action` iterates zero steps, writes a run log with `outcome="matched"` and `actions_fired=[]`.

### 5.8 Action step ordering

Actions in `rule["actions"]` are executed sequentially in list order. A failure in step N (caught and recorded as `"error:..."` in `actions_fired[N]`) does not prevent steps N+1 onward from executing — only an unhandled exception escaping `_execute_action` halts the loop.

### 5.9 Record no longer exists

If `record_id` refers to a deleted ticket (`STORE.update_status` returns `None`) or a deleted contact (DDB `update_item` returns no matching item), the action is marked `"skipped:record_not_found"`. No exception is raised; the run log records `outcome="matched"` (the rule fired; the record was gone by execution time).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

No `if S.dev_mode` branches exist in the executor. All DDB writes go through `T.crm_workflow_rules`, `T.crm_workflow_runs`, `T.tickets`, and `T.contacts`. In dev these tables are backed by DynamoDB Local (port 8001, `DDB_ENDPOINT_URL=http://localhost:8001`); in prod they are real DynamoDB tables. Boto3 client selection is handled transparently by `app/core/aws.py`. The executor is entirely DDB-only — no S3, KMS, SES, or external HTTP calls in this ticket.

`audit_event` at `app/services/alerts.py:644` writes to `T.alerts` in both dev and prod; in dev no SES call is made. No divergent behavior.

### 7.2 Idempotency

The unified scheduler's claim step (`claim_action` at `app/services/scheduled_actions.py:377`) uses a conditional-put `status=pending → executing`. Only one scheduler instance can execute a given action. If the process crashes after `claim_action` but before `mark_action_completed`, the action is left in `executing` status and not retried (this is the existing scheduler's behavior for all action types). The run log row may be absent for crashed executions — this is acceptable; WFL-009's run history UI can surface `executing` rows as in-progress.

### 7.3 Security

`execute_crm_workflow_action` runs as `user_sub="system"`, not as any real user. `TicketStore.update_status` and `assign_ticket` accept any `actor_sub`; passing `"system"` is valid and produces activity rows with `actor_sub="system"` that are visible in the ticket audit trail.

The `create_record` action creates tickets with `owner_sub="system"`. Such tickets are visible to admins but not attributed to any user. If a future requirement is to create tickets on behalf of the record's owner, the executor can read `owner_sub` from the payload.

`config.fields` in `create_record` is not sanitized beyond the `TicketStore.create_ticket` validation (subject required, labels normalized). Admins who define workflow rules control the `fields` dict content; the endpoint that creates rules (WFL-009) requires `require_admin_or_root_csrf` (`app/routers/admin_notifications.py:13`), so only admins can define what `create_record` puts in the `fields` dict.

The `modify_field` action on contacts reads `owner_sub` from the executor payload, which was written by `fire_on_save_hook` in WFL-004. The hook sources `owner_sub` from the authenticated session's `user_sub` at save time. No privilege escalation is possible: the executor only writes to the contact row that the original user owned.

## 8. Backward Compatibility & Migration

### 8.1 Zero-migration deployment

No existing DynamoDB table schemas change. `T.crm_workflow_rules` and `T.crm_workflow_runs` are new tables (WFL-001); they are created by `scripts/local-ddb-init.py` on `just restart` and will be created in prod via a one-time `CreateTable` call before deployment. They are empty at deploy time; the executor simply finds no rows to process until the first rule is defined.

`_EXECUTORS` in `app/services/unified_scheduler.py` gains one new key. If a `"crm_workflow"` action row somehow existed in `T.scheduled_actions` before this deployment (impossible in practice; no code writes them when the flag is off), it would have been marked `failed` with `"Unknown action_type: crm_workflow"` by the existing `mark_action_failed` branch at line 137. After deployment those rows would be retried if within `max_retries` — not a concern in practice.

### 8.2 Rollback

Disabling `CRM_WORKFLOW_ENABLED` after enabling it stops new rules from firing. In-flight `crm_workflow` rows in `T.scheduled_actions` with `status=pending` will be dispatched by the executor (which will immediately return on the flag guard). To hard-stop: set `status=cancelled` on those rows directly (DDB console / rootctl). No data in `T.tickets` or `T.contacts` is modified by the rollback itself.

## 10. Open Questions / Assumptions

1. **Min-lead-time bypass for system enqueue**: `create_action` enforces `scheduled_at > now + min_lead_time_seconds` (default 300 s). WFL-004/005 enqueue with `scheduled_at=now_ts()` for immediate execution. The WFL-004 spec calls `T.scheduled_actions.put_item` directly (bypassing the user-facing API guard). This ticket **assumes** that approach is in place and does not attempt to call `create_action` from within the executor. If WFL-004/005 are changed to use `create_action`, the min-lead-time must be set to 0 for system enqueues (via a `_system_create_action` helper that skips the lead-time check). **Assumption**: WFL-004 uses direct `put_item`.

2. **Contact `record_id` encoding**: The executor payload for contact events must contain both `record_id` (the `contact_id`) and `owner_sub`. This is assumed to be the case per the WFL-004 spec. If the payload format differs (e.g., `record_id = f"{owner_sub}#{contact_id}"`), the contact dispatch must be adjusted accordingly.

3. **Status transition bypass for workflow rules**: `update_status` enforces `_STATUS_TRANSITIONS`. A `modify_field` action attempting an invalid transition (e.g., `done → blocked`) will be caught and logged as an error. This is intentional — workflow rules are not given elevated permission to bypass transition guards. If admins need to force-set status regardless of transition rules, a separate `force_status` field could be introduced in a follow-up.

4. **`priority` field not yet in `_TICKET_STATUSES` or any dedicated service method**: The raw `update_item` approach for `priority` and `subject` is chosen because `TicketStore` has no helper for these. A future `TicketStore.update_fields` generic helper could replace the raw DDB call — deferred to avoid scope creep.

5. **No `create_record` for contacts**: Creating a contact requires a profile lookup (`get_profile_identity`) and there is no standalone "create contact" service call — contacts are always created from the router with an authenticated session. System-created contacts are therefore out of scope. `create_record` for `module="contact"` returns `"skipped:unsupported_module"`.
