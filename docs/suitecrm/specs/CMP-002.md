# CMP-002 — HTML email templates for campaigns with merge-field substitution

## 1. Summary & Goal

CMP-002 introduces a `MarketingEmailTemplate` resource that lets campaign owners author reusable HTML email templates containing `{{merge_field}}` placeholders. At campaign-send time those placeholders are substituted per-recipient from profile data, producing a fully personalized HTML email delivered via the existing SES path.

The goal is to bring testlogon's campaign module to parity with SuiteCRM's HTML template system while reusing every relevant existing primitive: the `{{var}}` substitution engine at `app/services/notification_templates.py:23,245`, the HTML wrapper at `app/services/alert_email_templates.py:16`, and the email-delivery function at `app/services/alerts.py:459`. No new email-delivery mechanism is introduced; the only additions are a new DynamoDB table, a new service module, additive fields on existing models, and an extension of `send_alert_email` to accept an optional `body_html` parameter.

The entire feature is default-off behind `S.marketing_campaigns_enabled` (MKT-002 flag). With the flag off the platform is byte-for-byte unchanged.

**Item schema**:

| Attribute | Type | Notes |
|---|---|---|
| `pk` | S (HASH) | `TMPL#{template_id}` |
| `sk` | S (RANGE) | `META` |
| `template_id` | S | `sha256(owner_id + "\|" + name)[:16]` — deterministic, duplicate-proof |
| `owner_id` | S | GSI partition key (`ByOwnerCreatedAt`) |
| `name` | S | Human-readable template name |
| `subject_template` | S | Subject line with `{{merge_field}}` placeholders |
| `body_html_template` | S | HTML body with `{{merge_field}}` placeholders, up to 50 000 chars |
| `variables` | SS / List | Variable names extracted from `subject_template + body_html_template` at save time |
| `status` | S | `"draft"` or `"active"` |
| `created_at` | N | `now_ts()` — GSI sort key |
| `updated_at` | N | `now_ts()` on every write |

**GSI ByOwnerCreatedAt**: partition key `owner_id (S)`, sort key `created_at (N)`. Supports `list_templates(owner_id, ...)` with `ScanIndexForward=False` for newest-first ordering. `attr_types={"created_at": "N"}` is mandatory in `scripts/local-ddb-init.py` — omitting it stores the number as a String type and causes `ValidationException` on numeric range queries at runtime (CLAUDE.md gotcha).

## 4. API / Service Design

### New service: `app/services/marketing_email_templates.py`

#### `create_template(owner_id: str, data: MarketingEmailTemplateCreateIn) -> Dict[str, Any]`

1. Compute `template_id = hashlib.sha256((owner_id + "|" + data.name).encode()).hexdigest()[:16]`.
2. Parse all variable names from subject and body: `variables = sorted(set(_VAR_RE.findall(data.subject_template + data.body_html_template)))`.
3. Build item with `pk=f"TMPL#{template_id}"`, `sk="META"`, `owner_id`, `name`, `subject_template`, `body_html_template`, `variables`, `status="draft"`, `created_at=now_ts()`, `updated_at=now_ts()`.
4. `T.marketing_email_templates.put_item(Item=item, ConditionExpression="attribute_not_exists(pk)")`. On `ConditionalCheckFailedException` raise `HTTPException(409, "template name already exists for this owner")`.
5. Emit `audit_event("marketing.template.created", owner_id, template_id=template_id)` best-effort.
6. Return item dict.

#### `get_template(owner_id: str, template_id: str) -> Dict[str, Any]`

Point lookup: `T.marketing_email_templates.get_item(Key={"pk": f"TMPL#{template_id}", "sk": "META"}).get("Item")`. Returns `None` when not found. Raises `HTTPException(403)` when `item["owner_id"] != owner_id` — ownership enforced (404 preferred for external callers; 403 reserved for explicit mismatches detected post-lookup, following the pattern from `app/routers/ads.py:67–83`).

#### `list_templates(owner_id: str, limit: int = 20, cursor: Optional[str] = None) -> Dict[str, Any]`

Query `ByOwnerCreatedAt` GSI: `KeyConditionExpression=Key("owner_id").eq(owner_id)`, `Limit=limit`, `ScanIndexForward=False`. Pagination via `app/core/cursor.py:encode_cursor / decode_cursor` (the same pattern used by `list_tracking_codes_for_campaign` in MKT-010). Returns `{"templates": [MarketingEmailTemplateOut, ...], "cursor": str|None, "count": int}`.

#### `update_template(owner_id: str, template_id: str, data: MarketingEmailTemplateUpdateIn) -> Dict[str, Any]`

Fetch item, verify ownership. Build `UpdateExpression` for each non-`None` field in `data`. Re-extract `variables` when `subject_template` or `body_html_template` changes. Set `updated_at=now_ts()`. Use `update_item` (not `put_item`) to preserve `created_at`. Emit `audit_event("marketing.template.updated", ...)`.

#### `delete_template(owner_id: str, template_id: str) -> None`

Fetch item, verify ownership, check `reference_count` (see edge cases). `T.marketing_email_templates.delete_item(Key=...)`. Emit `audit_event("marketing.template.deleted", ...)`.

#### `render_template(template_item: Dict[str, Any], merge_vars: Dict[str, str]) -> Tuple[str, str]`

Delegates entirely to the existing substitution engine. No new rendering logic:

```python
from app.services.notification_templates import _render, _VAR_RE
from app.services.alert_email_templates import _wrap_html

def render_template(template_item, merge_vars):
    rendered_subject, _ = _render(template_item["subject_template"], merge_vars)
    rendered_body, _    = _render(template_item["body_html_template"], merge_vars)
    wrapped = _wrap_html(rendered_subject or "", rendered_body or "")
    return rendered_subject or "", wrapped
```

Missing merge vars are left as `{{var}}` placeholders (the existing `_render` contract at `notification_templates.py:251–256`). The function never raises on missing vars.

### Extension to MKT-009 `_build_message_body` in `app/services/marketing_campaigns.py`

MKT-009's `_build_message_body(campaign, merge_vars)` produces the plain-text body inside `send_campaign`, where the loaded `campaign` dict is in scope. MKT-009's `_try_send_one` (`docs/ofbiz/specs/MKT-009.md:290–301`) is **keyword-only** and receives `campaign_id: str` plus `subject`/`body_text` — NOT a `campaign` dict. So the HTML rendering must happen in the `send_campaign` outer scope (which already holds the `campaign` dict and loops over recipients), and the rendered `html_body` is threaded down to `send_alert_email`. CMP-002 adds an additive keyword-only `body_html` parameter to `_try_send_one` and computes `html_body` once per send (template render is per-campaign, not per-recipient):

```python
# In send_campaign(), after the campaign dict is loaded and before the recipient loop:
html_body: Optional[str] = None
if campaign.get("email_template_id") and campaign.get("campaign_type", "email") == "email":
    try:
        from app.services.marketing_email_templates import get_template, render_template
        tmpl = get_template(campaign["owner_id"], campaign["email_template_id"])
        if tmpl:
            _, html_body = render_template(tmpl, merge_vars)
    except Exception:
        html_body = None  # best-effort: fall back to plain text

# _try_send_one gains an additive keyword-only `body_html=None`; it forwards it:
# send_alert_email([recipient_email], subject, body_text, body_html=body_html)
```

The `get_template` call uses a best-effort `try/except` — a missing or corrupted template falls back to `html_body=None` (plain text only) without aborting the send. The existing MKT-009 plain-text body and opt-out check are not altered.

## 5. Detailed Behavior & Edge Cases

### Variable extraction at save time

`_VAR_RE.findall(subject_template + body_html_template)` returns a flat list of all variable names found in both fields. The stored `variables` list is `sorted(set(...))` — deduplicated and sorted for deterministic output. On update, if `subject_template` or `body_html_template` changes, `variables` is re-extracted from the new combined text; unchanged fields use their stored values in the re-extraction pass.

### Duplicate template name per owner

`create_template` uses a conditional `attribute_not_exists(pk)` put on the deterministic `template_id = sha256(owner_id + "|" + name)[:16]`. Because `template_id` is deterministic from `(owner_id, name)`, two creates with the same owner + name collide on the same pk and the second raises 409. Changing the name produces a different `template_id` and succeeds.

### Missing merge vars at render time

`_render` (at `notification_templates.py:251–257`) substitutes a var only when `var in sample_vars and sample_vars[var] != ""` (lines 253–254). Unresolvable vars (`{{company}}` when no company is set) are left as the original match string via `return match.group(0)` (line 257), so `{{company}}` appears literally in the rendered output. The campaign send never raises on missing vars. The preview endpoint returns `missing_vars` so template authors can see which vars need values.

### `email_template_id` referencing a non-existent template at campaign create/update

In `create_campaign` and `update_campaign` (MKT-004): when `email_template_id` is provided, call `get_template(owner_id, email_template_id)`. If `None` is returned, raise `HTTPException(422, "email_template_id does not exist or does not belong to this owner")`. Validation happens at campaign write time, not at send time, to fail fast.

### Template deleted while referenced by a campaign

`delete_template` checks whether any `MarketingCampaigns` items reference `email_template_id`. Implement as a point-check: query `ByOwnerCreatedAt` GSI for the owner, scan results for `email_template_id == template_id`, and raise `HTTPException(409, "template is referenced by one or more campaigns")` when found. This is a best-effort guard; race conditions are handled at send time by the `try/except` fallback in `send_campaign`'s template-render block (plain-text fallback on missing template, see §HTML body extension above).

### HTML body size limit in SES

AWS SES limits the total raw MIME message to 10 MB. The `body_html_template` field cap of 50 000 characters and the `_wrap_html` wrapper add roughly 1 500 characters of chrome, giving a total HTML body well under the SES limit. Subject is truncated to 120 chars at `send_alert_email` level (existing behavior at `alerts.py:477`).

### `campaign_type` guard

The HTML template is only rendered when `campaign_type == "email"` (field added by CMP-001). For `phone`, `mail`, `fax`, or `sms` campaigns, `html_body` is always `None` regardless of `email_template_id`. This guard lives in `send_campaign`'s template-render block (in the campaign-dict scope) before the template fetch.

### Preview endpoint — no side effects

`POST /ui/marketing/email-templates/{id}/preview` calls `render_template(tmpl, body.sample_vars)` and returns the rendered output. It does not write to any DDB table, does not send email, and does not record audit events. The `missing_vars` field in the response lists all `{{var}}` placeholders that had no value in `sample_vars`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

The `send_alert_email` extension uses the existing `S.dev_mode` branch at `app/services/alerts.py:462`. When `body_html` is provided in dev mode, the function logs to `S.dev_email_log` as today; it does not call SES. In prod it constructs the `Html` body for SES. Same code path — no `if S.dev_mode` branch in the new `marketing_email_templates.py` service. The DDB table is created by `scripts/local-ddb-init.py` in exactly the same way as in prod (moto in-process in dev, real DynamoDB in prod — SECOPS-007 parity).

### Idempotency

`create_template` is idempotent per `(owner_id, name)` pair via the conditional put on a deterministic `template_id`. A duplicate create with the same owner + name returns 409 (not a silent no-op), consistent with the CMP-002 ticket spec. `render_template` is purely functional (no writes). The `send_campaign` integration inherits MKT-009's send-dedup via the `CampaignSendLog` conditional put — duplicate sends to the same `(campaign_id, snapshot_ts, party_id)` are suppressed before `render_template` is ever called.

### Security

- **Ownership enforcement**: every service function that reads or writes a template verifies `item["owner_id"] == owner_id`. A user cannot read, update, delete, or preview another owner's template.
- **HTML injection in templates**: `body_html_template` is stored and rendered as-is. Campaign owners author the HTML; recipients receive exactly what the owner wrote. This is by design (same as SuiteCRM). Admin review of templates should be a future ADMIN-gate concern (out of scope here).
- **Input size limits**: `body_html_template` is capped at 50 000 chars by Pydantic validation, well under DynamoDB's 400 KB item limit and SES's 10 MB message limit.
- **CSRF**: all mutating endpoints use `Depends(require_ui_session)` which enforces the `x-csrf-token` header for cookie-auth requests (per `app/auth/deps.py` CSRF logic).
- **Template variable names**: `_VAR_RE` restricts variable names to `[a-zA-Z0-9_]+` — no shell-injection or XSS via variable names.
- **Audit trail**: `create_template`, `update_template`, `delete_template` each emit an `audit_event` to `T.alerts` (best-effort `try/except`).

## 8. Backward Compatibility & Migration

### Existing callers of `send_alert_email`

All existing callers pass two positional arguments (`to_emails`, `subject`) and one positional `body_text`. The new `body_html` parameter is keyword-only with default `None`, so all existing call sites compile and behave identically without any changes — the `body_html=None` branch produces `{"Text": {"Data": body_text[:8000]}}`, identical to the current SES message.

### Existing `MarketingCampaignCreateIn` / `MarketingCampaignUpdateIn`

`email_template_id: Optional[str] = None` is added as an optional field with a default, so all existing model round-trips and test payloads that omit this field remain valid.

### Existing `MarketingCampaigns` DDB items

Items written before CMP-002 lack `email_template_id`. The send path reads `campaign.get("email_template_id")` which returns `None`, activating the existing MKT-009 plain-text fallback path — zero impact on campaigns created before this ticket landed.

### DynamoDB table creation

The `MarketingEmailTemplates` table is created at stack startup by `scripts/local-ddb-init.py`. In dev: `just restart` recreates tables cleanly. In prod: the table must be created via `aws dynamodb create-table` (or Terraform) before the service binary is deployed. The binary tolerates the table not existing at import time (table handles are lazy boto3 references) but will raise on first DDB call. Recommended deployment order: (1) apply table DDL, (2) deploy binary.

## 10. Open Questions / Assumptions

1. **`platform_name` merge var source**: The `notification_templates.py` default templates reference `{{platform_name}}` (line 38) but there is no `S.platform_name` or `S.app_name` setting in `app/core/settings.py`. CMP-002 will supply `platform_name` in `merge_vars` from a hard-coded default `"testlogon"` (or from a future `S.platform_name` setting) until that setting is added. This is consistent with how the notification templates currently handle it (sample vars must supply it).

2. **Max HTML body size in DynamoDB**: A single DynamoDB item is capped at 400 KB. The 50 000 char limit on `body_html_template` is conservative (50 000 UTF-8 bytes plus all other attributes stays well under 400 KB). If future templates need richer content, the design could store the body in S3 with a DDB pointer (outside this ticket's scope).

3. **Admin visibility**: Template CRUD is currently owner-scoped only. An admin "view all templates" endpoint is not included. If moderation or compliance requires it, a `GET /ui/admin/marketing/email-templates` endpoint (behind `require_admin_session`) should be added in a follow-up.

4. **Template versioning**: This ticket stores a single live version per template. If a template is edited while a campaign send is in progress, in-flight sends for some recipients may use the old body and later recipients the new body. Full versioning (immutable version rows keyed by `version_id`) is a future concern; for MVP the spec requires no version locking.

5. **`_render` is a private symbol**: `from app.services.notification_templates import _render, _VAR_RE` imports a module-private function. This is acceptable for internal services but should be documented as a coupling point. A future refactor could add a public `render_template_vars(text, vars)` wrapper to `notification_templates.py`.
