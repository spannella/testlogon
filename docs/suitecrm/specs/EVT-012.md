# EVT-012 — Document revision history (version on overwrite, download prior versions)

**Type:** Feature | **Priority:** P2 | **Estimate:** 3d  
**Source ticket:** `docs/suitecrm/CRM_MISC_TICKETS.md` § EVT-012

---

## 1. Summary & Goal

When a user overwrites an existing file node with a new upload (same path, new binary content), the current design destroys the prior S3 object. EVT-012 archives the prior file metadata as a revision row in the same DynamoDB table before the overwrite completes. Users can then list all historical revisions for a path and download any prior version by revision number. The feature is entirely additive and gated behind a default-off flag; every existing upload and download code path is byte-for-byte unchanged when the flag is off.

The goal mirrors what SuiteCRM's Documents module provides (see `docs/suitecrm/CRM_MISC_TICKETS.md` header): a versioned document library with revision history accessible to the document owner.

## 2. Context & Current State

### File manager table layout

The file manager uses a single DynamoDB table whose name comes from `S.filemgr_table_name` (`app/services/filemanager.py:105`). Every file node is stored as:

- `PK = USER#{owner}` (constructed by `pk_user`, line 438)
- `SK = NODE#{normalized_path}` (constructed by `sk_node`, line 442)

`node_key(owner, path)` (`filemanager.py:446`) returns both parts. `get_node` (`line 450`) reads a single node, raising 404 if absent or soft-deleted. `put_node` (`line 460`) writes unconditionally via `tbl.put_item`. The table is wired in `scripts/local-ddb-init.py:328` with two GSIs: `GSI1` (PK=`GSI1PK`, SK=`GSI1SK`) and `GSI2` (PK=`GSI2PK`, SK=`GSI2SK`). Neither GSI SK is numeric, so no `attr_types` entry is currently needed for the existing file-node GSIs.

### Overwrite path today

`upload_file_dispatched` (`filemanager.py:1953`) accepts an `overwrite: bool` flag. When `overwrite=True` and a local node already exists (lines 1976–1986):

```
existing = get_node(owner, norm_path(path, is_folder=False))
if existing.get("type") != "file":
    raise HTTPException(409, "already exists")
remove_file(owner, path)        # soft-deletes node + schedules S3 purge
```

Then `upload_file` (`line 2110`) writes a brand-new item at the same `PK`/`SK`, uploading new bytes to S3 at `{owner}/objects/{new_uuid}`. The prior S3 object key (`existing["s3_key"]`) is carried only on the soft-deleted node and will be garbage-collected by the existing purge worker. There is no revision trail.

`require_not_exists` (`line 940`) raises 409 if the node already exists; `upload_file` calls it, so without `overwrite=True` a re-upload fails.

The upload router endpoint (`app/routers/filemanager.py:1806`) exposes `overwrite: bool = Query(False)`.

### Download path today

`download_file` (`filemanager.py:2609`) reads the live node, fetches the S3 object via `_s3.get_object`, and the router (`filemanager.py:2352`) streams the body as `StreamingResponse`. There is no path that fetches a revision-keyed S3 object.

### Audit events

`audit_event` from `app/services/alerts.py:644` is already called by the upload router (`filemanager.py router:1866`) as `"filemgr_file_uploaded"` and by the download router (`filemanager.py router:2390`) as `"filemgr_file_downloaded"`. Revision-specific events will follow the same convention.

### `now_iso()` and `now_ts()`

`now_iso()` (`filemanager.py:177`) returns an ISO 8601 UTC string. `now_ts()` (`app/core/time.py:2`) returns a Unix integer timestamp. Revision rows will store a numeric `superseded_at_ts` for GSI sort and an ISO string `superseded_at_iso` for human display.

### EVT-011 dependency

EVT-011 adds `crm_category`, `crm_description`, `linked_record_type`, and `linked_record_id` as additive attributes on file nodes (same `PK`/`SK` pattern). This spec is purely additive on top of the same node structure; the two features are independent and can be deployed in any order. EVT-012 carries the same flag-check convention established in EVT-001 and used by EVT-011.

## 3. Data Model

### Reuse: existing `file_manager` DynamoDB table

No new DynamoDB table is created. Revision rows are stored as additional items in the same table that already holds file nodes and upload tickets (`S.filemgr_table_name`). The single-table pattern is consistent with how upload tickets are stored (`SK=TICKET#{ticket_id}`, `filemanager.py:2243`) in the same table.

### Revision row key scheme

```
PK  = USER#{owner}                         (same pk_user pattern, line 438)
SK  = REVISION#{path}#{revision_number:08d}
```

`revision_number` is zero-padded to eight digits so lexicographic `begins_with` + `ScanIndexForward=False` returns revisions newest-first without a secondary index. Example:

```
PK  = USER#alice-sub-123
SK  = REVISION#/docs/contract.pdf#00000001
```

A helper constructor mirrors `sk_node`:

```python
def sk_revision(path: str, revision_number: int) -> str:
    return f"REVISION#{path}#{revision_number:08d}"
```

### Revision row attributes

| Attribute | Type | Notes |
|---|---|---|
| `PK` | S | `USER#{owner}` |
| `SK` | S | `REVISION#{path}#{n:08d}` |
| `type` | S | Fixed value `"revision"` |
| `path` | S | Normalized file path (same as current live node) |
| `name` | S | Filename at time of archival |
| `revision_number` | N | Monotonically increasing integer, starts at 1 |
| `superseded_at_ts` | N | Unix timestamp (integer) when the revision was archived — used as **GSI3 sort key** |
| `superseded_at_iso` | S | ISO 8601 string of the same moment, for display |
| `superseded_by_sub` | S | `user_sub` of the user who performed the overwrite |
| `s3_bucket` | S | Bucket that holds the archived object |
| `s3_key` | S | S3 object key of the archived content (the prior `s3_key` from the live node) |
| `size` | N | File size in bytes at archival time |
| `content_type` | S | MIME type at archival time |
| `etag` | S | S3 ETag at archival time |
| `is_encrypted` | BOOL | Whether the archived content was encrypted |
| `enc_metadata` | M | Encryption envelope map, if `is_encrypted=True`, else absent |
| `original_created_at` | S | `created_at` from the live node (ISO) — when the file was first uploaded |
| `original_upload_by` | S | `upload_by` from the live node |
| `GSI3PK` | S | `REVISIONS#{owner}#{path}` — enables listing all revisions of one file |
| `GSI3SK` | N | Same value as `superseded_at_ts` — numeric, requires `attr_types` entry |

### New GSI: `GSI3` on the existing `file_manager` table

```
GSI3:
  index_name: "GSI3"
  partition_key: "GSI3PK"   (S)
  sort_key:      "GSI3SK"   (N)
```

Add to `scripts/local-ddb-init.py` inside the existing `file_manager` TableDef's `gsi` list:

```python
{"index_name": "GSI3", "partition_key": "GSI3PK", "sort_key": "GSI3SK"},
```

And add `attr_types` for the new numeric sort key (this is mandatory per the CLAUDE.md gotcha — omitting it causes `ValidationException` at query time):

```python
attr_types={"GSI3SK": "N"},
```

The existing `GSI1`/`GSI2` GSI sort keys are strings, so they require no `attr_types` entry.

### Revision number allocation

The next revision number for a given `(owner, path)` is derived by querying `GSI3`:

```python
resp = tbl.query(
    IndexName="GSI3",
    KeyConditionExpression=Key("GSI3PK").eq(f"REVISIONS#{owner}#{path}"),
    Select="COUNT",
)
next_revision = resp["Count"] + 1
```

This is a point-in-time count; concurrent overwrites could theoretically produce a collision. The write uses a conditional expression (`attribute_not_exists(SK)`) to make the revision write idempotent — a collision causes a retry with an incremented number (max 3 retries before raising 500).

### S3 object lifecycle for revision content

Revision rows reference the *prior* S3 key (`existing["s3_key"]`). The existing `_soft_delete_node` and purge worker (`filemanager.py:1755`) must NOT delete the S3 object if the key is referenced by any revision row. To achieve this without changing the purge worker:

- The `remove_file` call inside `upload_file_dispatched` is **skipped** when `crm_document_revisions_enabled`. Instead, the live node item is overwritten in place (by the subsequent `upload_file` call's `put_node`) after the revision row is written. The old S3 key is preserved in the revision row and remains accessible. The live node's `purge_status`/`deleted_at` are never set for the archived content; only the live node item is replaced.
- Revision S3 objects are deleted only when a revision row is explicitly deleted or when the `purge_all_revisions` service function is called (see §5).

## 4. API / Service Design

### 4.1 Service additions (`app/services/filemanager.py`)

#### `_archive_revision(owner: str, existing_node: dict, *, superseded_by: str) -> int`

Internal helper called by `upload_file_dispatched` when `crm_document_revisions_enabled` is on and an existing file is being overwritten. Allocates the next revision number, writes the revision row, and returns the allocated `revision_number`. Does NOT remove or soft-delete the live node — callers must not call `remove_file` for this path.

```python
def _archive_revision(
    owner: str,
    existing_node: dict,
    *,
    superseded_by: str,
) -> int:
    """Archive the current live node as a revision row before overwrite.

    Returns the revision_number assigned to the archived content.
    Raises HTTPException(500) if revision allocation fails after 3 retries.
    """
```

#### `list_revisions(owner: str, path: str, *, limit: int = 50, cursor: str | None = None) -> dict`

```python
def list_revisions(
    owner: str,
    path: str,
    *,
    limit: int = 50,
    cursor: str | None = None,
) -> dict:
    """Return revision rows for path, newest-first.

    Returns: {"revisions": list[dict], "cursor": str | None, "total": int}
    Each dict contains: revision_number, superseded_at_iso, superseded_at_ts,
    superseded_by_sub, size, content_type, is_encrypted, original_created_at.
    The s3_key and s3_bucket are NOT returned to callers (they are resolved
    internally by download_revision).
    """
```

Queries `GSI3` with `ScanIndexForward=False` (newest first). Paginates via `encode_cursor`/`decode_cursor` from `app/core/cursor.py`. Raises 404 if no live node exists at path (confirms ownership before listing).

#### `download_revision(owner: str, path: str, revision_number: int) -> dict`

```python
def download_revision(
    owner: str,
    path: str,
    revision_number: int,
) -> dict:
    """Resolve the archived S3 object for a specific revision.

    Returns: {"node": revision_row_dict, "object": s3_get_object_response}
    Raises 404 if the live file node does not exist (ownership check).
    Raises 404 if the revision row does not exist.
    """
```

Reads the revision row directly via `tbl.get_item(Key={"PK": pk_user(owner), "SK": sk_revision(path, revision_number)})`. Fetches the S3 object via `_s3.get_object(Bucket=..., Key=...)`. The same `ClientError` wrapping used in `download_file` (`filemanager.py:2617`) applies.

#### `purge_all_revisions(owner: str, path: str) -> int`

```python
def purge_all_revisions(owner: str, path: str) -> int:
    """Hard-delete all revision rows and their S3 objects for a given path.

    Called when the live node is permanently deleted (purge, not soft-delete).
    Returns the number of revisions purged.
    Not exposed as an API endpoint; called internally from the purge worker path.
    """
```

Queries `GSI3` for all revisions, deletes each S3 object and DDB row. Uses a DDB `batch_writer` for efficiency. Swallows S3 `NoSuchKey` errors (idempotent).

### 4.2 Modification to `upload_file_dispatched`

The change is confined to the `overwrite=True` + `dispatch["kind"] == "local"` branch (`filemanager.py:1976–1986`). Current code:

```python
# Current (lines 1977–1986)
existing = get_node(owner, norm_path(path, is_folder=False))
...
remove_file(owner, path)   # <-- soft-deletes and schedules S3 purge
```

Proposed replacement (flag-gated):

```python
existing = get_node(owner, norm_path(path, is_folder=False))
if existing.get("type") != "file":
    raise HTTPException(409, "already exists")
if getattr(S, "crm_document_revisions_enabled", False):
    _archive_revision(owner, existing, superseded_by=owner)
```

When the flag is off, the behaviour is identical to today (soft-delete then re-upload). When the flag is on, the prior node is archived and then overwritten; `upload_file` calls `put_node` which unconditionally replaces the item (`tbl.put_item`), so the live node SK is reused with fresh attributes.

## 5. Detailed Behavior & Edge Cases

### First overwrite — revision number 1

When a file has never been overwritten, `list_revisions` returns `[]` (no GSI3 rows). On first overwrite with flag on, `_archive_revision` allocates `revision_number=1`, writes the row, and the new upload becomes the live node (no revision number on the live node itself — the live node is always "current").

### Revision number allocation under concurrency

The count-based allocation is susceptible to concurrent overwrites. The conditional-write retry loop in `_archive_revision` handles this:

1. Query `GSI3` for count → derive candidate `revision_number = count + 1`.
2. `tbl.put_item(Item=..., ConditionExpression=Attr("SK").not_exists())`.
3. If `ConditionalCheckFailedException`, retry up to 3 times with `revision_number += 1`.
4. After 3 failures, raise `HTTPException(500, "revision allocation conflict")`.

In practice, concurrent overwrites of the same path are rare (the upload itself is sequential per S3 key), so one retry is almost never needed.

### Encrypted files

Revision rows preserve `is_encrypted=True` and `enc_metadata` from the live node. When a caller downloads a revision of an encrypted file, the raw ciphertext is streamed identically to the unencrypted path — the client is responsible for decryption using the stored `enc_metadata`. No decryption is performed server-side for file-manager content.

### Revision of a revision is not a concept

Revision rows (`type="revision"`) are never overwritten — their SK includes the revision number, so a new upload always creates a new `NODE#` item (the live node) and archives the prior `NODE#` item. There is no nested revision chain.

### Large number of revisions

`list_revisions` applies `Limit=limit` at the DDB query level (against GSI3). For high-churn files this prevents unbounded scans. The cursor mechanism (`encode_cursor`/`decode_cursor`) allows clients to page through all revisions.

### Permanent deletion carries through to revisions

When a file is permanently purged (not soft-deleted — specifically the purge worker processing `purge_status="pending"` nodes), the purge worker calls `purge_all_revisions(owner, path)` as a best-effort step before deleting the live S3 object. This ensures no orphaned revision S3 objects remain. The purge worker is in `app/services/filemanager.py`; the call is wrapped in `try/except` so a revision-purge failure does not block the node purge.

The soft-delete path (`_soft_delete_node`) does NOT call `purge_all_revisions` — revisions remain accessible even after the live node is soft-deleted, until the purge TTL fires.

### Overwrite with `overwrite=False`

`require_not_exists` raises 409 before `upload_file_dispatched` reaches the overwrite branch. Revision archival is never triggered. Behaviour unchanged.

### Mount provider paths

The `upload_file_dispatched` overwrite branch for mounted providers (`dispatch["kind"] == "mount"`) is not affected. Revision archival applies only to the `dispatch["kind"] == "local"` branch. Mount providers (S3 mounts, SFTP mounts, Google Drive mounts) manage their own versioning. A flag-check guard is added to the local branch only.

### Storage quota accounting

When the flag is on, `remove_file` is skipped, so `record_storage_delta(user, p, -prior_size, ...)` is NOT called for the prior file. The prior S3 bytes are retained for revision storage. A future ticket (EVT-013 or a quota extension) should account for revision bytes in quota calculations. For now, revision bytes are not debited from the user's quota, matching SuiteCRM's behaviour (it does not charge revision storage against quota).

### GSI3 and existing nodes

All existing file nodes pre-date the GSI3 index. They have no `GSI3PK`/`GSI3SK` attributes. DynamoDB sparse index semantics mean pre-existing nodes are simply absent from GSI3 — no migration is needed. When a pre-existing file is first overwritten with the flag on, the new revision row carries `GSI3PK`/`GSI3SK` and appears in the index normally.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/Prod parity

There is no `dev_mode` branch in the new code. Both revision-write and revision-download paths use the same `_table()` function (`filemanager.py:104`) and `s3_client` factory (`app/core/aws_clients.s3_client`). In dev, `_table()` points at DynamoDB Local (port 8001) and `s3_client` talks to the in-process moto mock — exactly as the existing upload/download paths do. In prod, both point at real AWS. No mock-only or dev-only branches exist.

The presigned-URL logic for `download_file` wraps `_s3.get_object` directly — not `generate_presigned_url` — and streams the body through the router. `download_revision` follows the same pattern, so there is no presigned URL involved and no dev/prod divergence.

### Idempotency

The conditional `attribute_not_exists(SK)` write in `_archive_revision` ensures that if the same revision number is attempted twice (e.g., retry after a network timeout), the second attempt either succeeds (first attempt did not commit) or raises `ConditionalCheckFailedException` (first attempt committed — treat as success and skip). The overarching upload flow does not have a standard idempotency key for the revision archival step; callers that retry a failed overwrite may create a duplicate revision. This is acceptable: the revision number is allocated fresh on each attempt, and a partial revision row is never left in an inconsistent state because the `put_item` is atomic.

### Ownership enforcement

Both new endpoints call `get_node(user, p)` before doing anything else. `get_node` raises 404 if the node does not exist or is soft-deleted, and the `PK=USER#{user}` key means a user can only access nodes under their own partition. No cross-user access is possible via these endpoints.

### S3 key secrecy

`list_revisions` never returns `s3_key` or `s3_bucket` to callers. Only `download_revision` (which verifies ownership) accesses those fields internally. This matches the existing `download_file` pattern.

### Encrypted-file revisions

When downloading a revision of an encrypted file, the raw ciphertext bytes are streamed unchanged. The encryption envelope is preserved in the revision row's `enc_metadata` field and returned in the `revisions` list response so the client can decrypt. Server-side decryption of file-manager content is never performed (same constraint as live download).

### Audit trail

Every revision list and download emits an `audit_event` to `T.alerts` via `app/services/alerts.audit_event` (`alerts.py:644`). The archive step also emits `"filemgr_revision_archived"` with `path`, `revision_number`, and `prior_s3_key` (the archived S3 key — logged for forensics, not returned to users).

## 8. Backward Compatibility & Migration

### No schema migration required

Adding `GSI3` to an existing DynamoDB table requires an `UpdateTable` call in production, which DynamoDB processes asynchronously (typically minutes). The index is sparse: only revision rows carry `GSI3PK`/`GSI3SK`. During the `UpdateTable` backfill period, `list_revisions` may return an incomplete set of recently written revision rows; this is acceptable because the feature is new and default-off.

In dev, `just restart` recreates all tables from scratch via `scripts/local-ddb-init.py`, so the new GSI appears immediately after the first restart with the updated script.

### `scripts/local-ddb-init.py` change

The existing `file_manager` `TableDef` block at line 328 gains one entry in its `gsi` list and an `attr_types` dict:

```python
TableDef(
    _resolve_table_name(S.filemgr_table_name, "file_manager"),
    "PK",
    "SK",
    gsi=[
        {"index_name": "GSI1", "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "GSI2", "partition_key": "GSI2PK", "sort_key": "GSI2SK"},
        {"index_name": "GSI3", "partition_key": "GSI3PK", "sort_key": "GSI3SK"},   # NEW
    ],
    attr_types={"GSI3SK": "N"},   # NEW — numeric sort key, required or ValidationException
),
```

### Existing data

All existing file-node items are unaffected. The new `type="revision"` SK prefix (`REVISION#...`) does not collide with `NODE#...` (live nodes) or `TICKET#...` (upload tickets). `list_children_page` and `search_prefix` query by `GSI1PK`/`GSI1SK` or `SK.begins_with("NODE#")`, so they never surface revision rows.

### Rollback

If the flag is turned off after revision rows have been written, the upload path silently resumes soft-deleting prior nodes. Existing revision rows remain in the table; `list_revisions` and `download_revision` return 404 (flag guard). The revision rows and their S3 objects are not automatically purged on flag disable — an operator must run a cleanup script if permanent removal is desired.

## 10. Open Questions / Assumptions

1. **Quota for revision bytes**: This spec does not debit revision bytes against the user's storage quota. Should revision bytes count toward quota? If so, `_archive_revision` should call `record_storage_delta` for the archived size (positive, since the S3 object is now "extra" bytes). Deferred to a future quota-extension ticket.

2. **Maximum revision count per file**: No cap is imposed today. A heavily overwritten file could accumulate thousands of revision rows. A `max_revisions_per_file` setting (e.g., default 100) could be added, with `_archive_revision` pruning the oldest revision (deleting its S3 object and DDB row) when the cap is reached. Deferred.

3. **Restore-from-revision endpoint**: EVT-012 specifies download only. A future `POST /files/revisions/restore?path=...&revision_number=N` that promotes a revision back to the live node would complement this feature. Deferred.

4. **Cross-owner admin access to revisions**: Should ROOT/ADMIN users be able to list and download revisions for any user? The current design enforces strict owner-only access via `PK=USER#{user}`. Admin access would require a separate `admin_list_revisions(owner_sub, path)` function with `require_admin_session`. Deferred.

5. **Revision archival for presigned-upload path**: The presigned-upload flow (`register_presigned_upload` + `complete_upload`) also supports overwrite via a ticket mechanism (`filemanager.py:2264`). This spec targets the direct-upload `upload_file_dispatched` path only. Revision archival for presigned uploads is assumed deferred to a follow-up.

6. **Assumption — `put_node` on overwrite**: When `crm_document_revisions_enabled` is on, `upload_file` calls `require_not_exists` then `put_node`. Since `remove_file` is skipped, the live node still exists when `require_not_exists` runs, causing a 409. Resolution: when the flag is on and overwrite=True, skip the `require_not_exists` call inside `upload_file` or call `put_node` directly instead of `upload_file`. The implementation uses a private `_upload_file_no_require_exists(owner, path, file, ...)` variant that omits the `require_not_exists` check and is called only from the `upload_file_dispatched` overwrite branch when the flag is on.

## 11. Dependencies

### Hard dependencies

- **EVT-001** (`CRM_MISC_TICKETS.md` § EVT-001) — establishes the flag convention and `_require_crm_events_enabled` guard pattern. EVT-012 follows the identical pattern for its own `_require_doc_revisions_enabled`.
- **EVT-011** (`CRM_MISC_TICKETS.md` § EVT-011) — adds `crm_category` / `crm_description` / `linked_record_type` / `linked_record_id` to the same file nodes. EVT-012 must not overwrite those additive fields when writing the live-node replacement after archiving a revision. Concretely: `upload_file` (`filemanager.py:2160`) writes a fresh item dict without EVT-011 fields; when both features are on, the replacement node loses CRM metadata. Mitigation: carry EVT-011 fields forward by copying them from `existing_node` into the new item. This requires EVT-011 to ship first or the two tickets to be merged. **EVT-011 is a hard dependency.**

### Soft dependencies

- **PTY-001..PTY-015** (`docs/PARTY_CRM_TICKETS.md`) — deliver Party/Contact/Account. EVT-012 does not directly depend on party data, but the `linked_record_id` field introduced by EVT-011 (and carried forward by EVT-012) will resolve to party records once PTY ships.
- **MKT-003/MKT-009** (`docs/MARKETING_CAMPAIGNS_TICKETS.md`) — marketing campaign/contact-list layer. No direct dependency.
- **EVT-013** (`CRM_MISC_TICKETS.md` § EVT-013) — document expiry. Both EVT-012 and EVT-013 add attributes to file nodes additively and independently. If both are enabled, the `expires_at` field from EVT-013 should also be copied forward on overwrite (same "carry-forward" pattern noted in the EVT-011 dependency above).
- **PRD (CATALOG_DEPTH)** / **OFB (OFBIZ_COMMERCE)** — no dependency.
