# EML-006 — User personal email signature

**Ticket type:** Feature
**Priority:** P2
**Estimate:** 1d
**Feature flag:** `EMAIL_SIGNATURES_ENABLED` (default `false`)

---

## 1. Summary & Goal

EML-006 allows each authenticated user to create, update, retrieve, and delete a personal email signature — an HTML block with a plain-text fallback — that is automatically appended when they compose or send an email via the in-app client (EML-005).

The signature is stored as a new row type on the existing `user_email_accounts` table introduced by EML-003, so no new DynamoDB table is required. Three service functions and three REST endpoints are added. The compose panel (EML-005 `ComposePanel.tsx`) fetches the signature on mount and appends it to outgoing messages. The outbound send service (EML-004's `send_message`) appends the signature server-side so it is included even in API or CLI sends that bypass the UI.

All changes are fully additive. With `EMAIL_SIGNATURES_ENABLED=false` (the default) every new endpoint returns 503, the compose panel never fetches the signature, and the outbound send path skips the signature entirely. The existing `send_alert_email` pipeline at `app/services/alerts.py:459`, the `T.email_delivery` table, and `app/routers/admin_email.py` are byte-for-byte unchanged.

### 2.3 HTML sanitisation precedents

The codebase contains two relevant sanitisation patterns:

1. `app/services/text_sanitizer.py:6-21` — `sanitize_user_text(value, *, max_length)` strips `<script>` and `<style>` blocks via `_SCRIPT_STYLE_RE` (line 6), then strips all remaining tags via `_TAG_RE` (line 7). This is too aggressive for a signature that must retain formatting HTML.
2. `app/models.py:9167-9173` — `_strip_script_tags` validator used by notification template models; uses `re.sub(r"<script[^>]*>.*?</script>", "", v, flags=re.DOTALL|re.IGNORECASE)` to remove `<script>` blocks while preserving other HTML. This is the correct precedent for EML-006: strip executable/dangerous elements only, leaving presentation markup intact.

EML-006 adopts an extended version of the `_strip_script_tags` regex pattern that also removes `<iframe>`, `<object>`, `<embed>`, `<form>`, and event attributes (`on\w+="..."`), applied server-side inside the `upsert_signature` service function. No third-party dependency (`bleach`) is required.

## 3. Data Model

### 3.1 Storage: new row type on `user_email_accounts` table

EML-006 adds a single new row type to the existing `user_email_accounts` table. No new table, no new GSI, no change to `scripts/local-ddb-init.py`.

| Attribute | DDB Type | Notes |
|---|---|---|
| `pk` | S | `USER#{user_sub}` — same partition as account rows |
| `sk` | S | `SIGNATURE` — literal string; one row per user maximum |
| `signature_html` | S | HTML body of the signature; max 10 240 bytes (10 KB) after sanitisation |
| `signature_text` | S | Plain-text fallback, used for the text part of outbound MIME; max 2 048 bytes |
| `updated_at` | N | `now_ts()` — integer Unix seconds; updated on every upsert |

**Key invariants:**
- `pk = USER#{user_sub}` / `sk = SIGNATURE` forms an unambiguous partition-level singleton: one row per user, enforced by unconditional `put_item` in `upsert_signature` (last-write wins; no conditional needed because a user's signature is not a shared resource with concurrent-write contention from multiple parties).
- The `SIGNATURE` row deliberately has no `created_at` attribute, so it does not appear in the `ByUser` GSI (which partitions on `pk` and sorts on `created_at`). It is invisible to account-listing queries.
- No TTL is set on the signature row; signatures persist until the user deletes them or the account is purged by a data-deletion workflow.

## 4. API / Service Design

### 4.1 Service additions: `app/services/user_email_accounts.py`

Three functions are appended to the existing service module created by EML-003.

#### HTML sanitiser helper (module-private)

```python
import re

# Strip dangerous/executable elements and event-handler attributes from HTML.
# Preserves presentation tags (<b>, <i>, <a>, <p>, <br>, <img>, <table>, etc.).
_DANGEROUS_TAGS_RE = re.compile(
    r"<\s*(script|iframe|object|embed|form|base)\b[^>]*>.*?<\s*/\s*\1\s*>",
    re.IGNORECASE | re.DOTALL,
)
_VOID_DANGEROUS_RE = re.compile(
    r"<\s*(script|iframe|object|embed|form|base)\b[^>]*/?>",
    re.IGNORECASE,
)
_EVENT_ATTR_RE = re.compile(
    r'\s+on\w+\s*=\s*(?:"[^"]*"|\'[^\']*\'|[^\s>]+)',
    re.IGNORECASE,
)
_JAVASCRIPT_HREF_RE = re.compile(
    r'(href\s*=\s*["\'])javascript:[^"\']*(["\'])',
    re.IGNORECASE,
)


def _sanitize_signature_html(raw: str) -> str:
    """Strip executable elements and event handlers; preserve presentation HTML."""
    s = _DANGEROUS_TAGS_RE.sub("", raw)
    s = _VOID_DANGEROUS_RE.sub("", s)
    s = _EVENT_ATTR_RE.sub("", s)
    s = _JAVASCRIPT_HREF_RE.sub(r"\g<1>#\g<2>", s)
    return s.strip()
```

This mirrors the `_strip_script_tags` pattern at `app/models.py:9167` but extends coverage to `<iframe>`, `<object>`, `<embed>`, `<form>`, `<base>`, all `on*` event attributes, and `javascript:` href values — the full set of XSS vectors in an HTML signature context. No external dependency is needed.

#### `get_signature(user_sub: str) -> dict | None`

```python
def get_signature(user_sub: str) -> dict | None:
    resp = T.user_email_accounts.get_item(
        Key={"pk": f"USER#{user_sub}", "sk": "SIGNATURE"}
    )
    return resp.get("Item") or None
```

Returns the raw DDB item (containing `signature_html`, `signature_text`, `updated_at`) or `None` when no row exists.

#### `upsert_signature(user_sub: str, html: str, text: str) -> dict`

```python
def upsert_signature(user_sub: str, html: str, text: str) -> dict:
    sanitized_html = _sanitize_signature_html(html)
    if len(sanitized_html.encode("utf-8")) > 10_240:
        raise ValueError("signature_html exceeds 10 KB limit after sanitisation")
    if len(text.encode("utf-8")) > 2_048:
        raise ValueError("signature_text exceeds 2 KB limit")
    ts = now_ts()
    item = {
        "pk": f"USER#{user_sub}",
        "sk": "SIGNATURE",
        "signature_html": sanitized_html,
        "signature_text": text.strip(),
        "updated_at": ts,
    }
    T.user_email_accounts.put_item(Item=item)
    audit_event("email_signature_upserted", user_sub, signature_html_bytes=len(sanitized_html.encode("utf-8")))
    return item
```

`put_item` is unconditional: last write wins. The HTML sanitiser runs before the size check so the limit applies to the sanitised output, not the raw input.

#### `delete_signature(user_sub: str) -> None`

```python
def delete_signature(user_sub: str) -> None:
    existing = get_signature(user_sub)
    if existing is None:
        raise KeyError("no_signature")
    T.user_email_accounts.delete_item(
        Key={"pk": f"USER#{user_sub}", "sk": "SIGNATURE"}
    )
    audit_event("email_signature_deleted", user_sub)
```

Raises `KeyError("no_signature")` when the row does not exist; the router translates this to a 404.

### 4.2 Pydantic models (`app/models.py`)

Append after existing EML-003 models:

```python
class SignatureIn(BaseModel):
    signature_html: str = Field(..., max_length=40_000,
        description="Raw HTML (sanitised server-side; max 40 KB input, 10 KB after sanitisation)")
    signature_text: str = Field(..., max_length=2_048,
        description="Plain-text fallback, max 2 KB")

    @field_validator("signature_html", mode="before")
    @classmethod
    def _not_empty(cls, v: str) -> str:
        if not isinstance(v, str) or not v.strip():
            raise ValueError("signature_html must not be empty")
        return v


class SignatureOut(BaseModel):
    signature_html: str
    signature_text: str
    updated_at: int
```

`max_length=40_000` on the raw input bound prevents extremely large payloads before sanitisation; the service re-enforces 10 240 bytes on the sanitised result.

### 4.3 Router additions (`app/routers/user_email_accounts.py`)

Three endpoints appended to the EML-003 router (prefix `/ui/email/accounts`). All are gated by `S.email_signatures_enabled`; a 503 guard function at the top of each handler is the standard pattern used throughout the codebase (e.g., `app/routers/call_recording.py:39-41`):

```python
def _require_signatures_enabled() -> None:

        raise HTTPException(503, detail={"code": "email_signatures_disabled"})
```

#### `GET /ui/email/signature`

```python
@router.get("/signature", response_model=SignatureOut)
async def get_email_signature(
    actor: AuthenticatedUser = Depends(get_authenticated_user),
) -> SignatureOut:
    _require_signatures_enabled()
    row = get_signature(actor.sub)
    if row is None:
        raise HTTPException(404, detail={"code": "no_signature"})
    return SignatureOut(**row)
```

- Auth: `get_authenticated_user` (any authenticated user).
- CSRF: GET — exempt.
- Returns: `SignatureOut` with `signature_html`, `signature_text`, `updated_at`.
- 404 when no signature exists.

#### `PUT /ui/email/signature`

```python
@router.put("/signature", response_model=SignatureOut)
async def put_email_signature(
    payload: SignatureIn,
    actor: AuthenticatedUser = Depends(get_authenticated_user),
    _csrf: None = Depends(enforce_cookie_csrf),
) -> SignatureOut:
    _require_signatures_enabled()
    try:
        row = upsert_signature(actor.sub, payload.signature_html, payload.signature_text)
    except ValueError as exc:
        raise HTTPException(422, detail={"code": "signature_too_large", "detail": str(exc)})
    return SignatureOut(**row)
```

- Auth: `get_authenticated_user` + CSRF enforcement via `enforce_cookie_csrf` (from `app/auth/policy.py:71`).
- Body: `SignatureIn`.
- Returns: `SignatureOut` with sanitised `signature_html`.
- 422 when post-sanitisation size exceeds limit.

#### `DELETE /ui/email/signature`

```python
@router.delete("/signature", status_code=204)
async def delete_email_signature(
    actor: AuthenticatedUser = Depends(get_authenticated_user),
    _csrf: None = Depends(enforce_cookie_csrf),
) -> None:
    _require_signatures_enabled()
    try:
        delete_signature(actor.sub)
    except KeyError:
        raise HTTPException(404, detail={"code": "no_signature"})
```

- Auth: `get_authenticated_user` + CSRF.
- Returns: HTTP 204 No Content on success.
- 404 when no signature exists (idempotent from the client's perspective: calling DELETE on a non-existent signature is an error, not a silent no-op, to help callers detect stale state).

### 4.4 EML-004 send integration

In `app/services/email_sync.py` (EML-004), `send_message(user_sub, account_id, payload)` builds the outbound MIME message. After building the base `MIMEMultipart("alternative")` with text and HTML parts, it calls:

```python
from app.services.user_email_accounts import get_signature as _get_sig

sig = None
if S.email_signatures_enabled:
    try:
        sig = _get_sig(user_sub)
    except Exception:
        pass  # never block send on signature failure

if sig:
    text_part = text_body + "\n\n--\n" + sig["signature_text"]
    html_part = html_body + "\n<br><hr style='border:none;border-top:1px solid #ccc;margin:12px 0'>\n" + sig["signature_html"]
else:
    text_part = text_body
    html_part = html_body
```

The separator between the message body and signature follows RFC-3676 conventions: `--\n` prefix in text, a light `<hr>` in HTML. The call is wrapped in `try/except` so a DynamoDB read failure never interrupts the send.

## 5. Detailed Behavior & Edge Cases

### 5.1 HTML sanitisation correctness

The sanitiser `_sanitize_signature_html` is applied server-side inside `upsert_signature` before storage. Key rules:

- **Stripped entirely:** `<script>`, `<iframe>`, `<object>`, `<embed>`, `<form>`, `<base>` — both paired tags and self-closing void forms.
- **Attribute removal:** All `on*` event-handler attributes (`onclick`, `onmouseover`, `onload`, etc.) are stripped from any element.
- **`javascript:` hrefs:** Rewritten to `#` to prevent execution.
- **Preserved:** All presentation and structural tags (`<b>`, `<strong>`, `<em>`, `<i>`, `<a>`, `<p>`, `<br>`, `<hr>`, `<ul>`, `<li>`, `<img>`, `<table>`, `<tr>`, `<td>`, `<span>`, `<div>`, `<h1>`-`<h6>`, etc.).
- The `GET /ui/email/signature` endpoint returns the already-sanitised HTML from DDB; the client-side TipTap editor also sanitises on render, but the server is the authoritative sanitisation boundary.

### 5.2 Size limits and truncation

| Field | Input limit (Pydantic) | Storage limit (service) | Rationale |
|---|---|---|---|
| `signature_html` raw input | 40 000 chars (`max_length` on model field) | 10 240 bytes UTF-8 after sanitisation | 10 KB comfortably fits in a DDB item; leaves room for the rest of the item |
| `signature_text` | 2 048 chars (`max_length`) | 2 048 bytes UTF-8 | RFC-3676 convention; plain-text sigs are short |

When sanitisation reduces the raw HTML below 10 KB, the stripped result is stored. If the result still exceeds 10 KB, `upsert_signature` raises `ValueError` and the router returns 422 with `code=signature_too_large`.

### 5.3 Idempotency of upsert

`upsert_signature` uses unconditional DDB `put_item`. Calling `PUT /ui/email/signature` twice with the same payload produces the same stored state (modulo `updated_at`). There is no versioning or optimistic-lock on the signature row.

### 5.4 Concurrent PUT

Two simultaneous PUT requests from the same user (e.g., two open browser tabs) will result in the last write winning. This is acceptable for a per-user singleton like a signature; no coordination mechanism is needed.

### 5.5 Flag-off behaviour

When `S.email_signatures_enabled` is `False`:
- `GET /ui/email/signature` → 503 `{"code": "email_signatures_disabled"}`.
- `PUT /ui/email/signature` → 503.
- `DELETE /ui/email/signature` → 503.
- The compose panel checks the flag before issuing the GET (via a feature status endpoint or a config query); if the flag is off it initialises the draft with an empty body and never calls the signature API.
- `send_message` in EML-004 skips the `get_signature` call entirely; the `if S.email_signatures_enabled:` guard short-circuits without a DDB read.

### 5.6 Interaction with EML-004 send

The `send_message` function calls `get_signature` lazily and wraps the call in `try/except`. A DDB timeout or `user_email_accounts` table outage never propagates to the send path. The signature is a best-effort decoration; the email is sent without it on any fetch failure. This mirrors the `send_alert_email` error-swallowing pattern at `app/services/alerts.py:479-491`.

### 5.7 `DELETE` returns 404 for non-existent row

Unlike some idempotent DELETE designs, EML-006's DELETE raises 404 when no signature exists. This is intentional: it gives the frontend accurate feedback that the user has no signature to delete, preventing misleading "deleted successfully" toasts. The frontend must handle 404 on DELETE gracefully (show "no signature to delete").

### 5.8 No multi-account disambiguation

The signature is per-user, not per-account. A user with multiple IMAP accounts (EML-003) uses the same signature across all of them. If per-account signatures are needed in the future they would use `SK=SIGNATURE#ACCT#{account_id}` on the same table; that extension does not require a schema migration — it merely adds new row types.

### 5.9 Audit trail

Every `upsert_signature` call writes an `"email_signature_upserted"` audit event to `T.alerts` via `audit_event`. Every `delete_signature` call writes `"email_signature_deleted"`. These appear in the existing audit export infrastructure. No new audit table or model is required.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

There is no `dev_mode` branch in any EML-006 code path. The three service functions write to and read from `T.user_email_accounts` in both dev (DynamoDB Local on port 8001) and prod (real DynamoDB). The `audit_event` call writes to `T.alerts` in both environments. The `email_signatures_enabled` flag is the sole gate; when it is on, the code path is identical in both environments.

This satisfies the SECOPS-007 requirement: the same sanitisation, size enforcement, audit emission, and 503 guard execute in dev and prod without any conditional branch on `S.dev_mode`.

### 7.2 Input sanitisation as a security boundary

The `_sanitize_signature_html` function runs server-side before storage. The stored `signature_html` value is already sanitised; the `GET` endpoint returns it verbatim. The frontend TipTap editor's own sanitisation is defence-in-depth, not the primary boundary. This means:

- A malicious API client that bypasses the UI cannot inject `<script>` or event handlers by constructing a raw PUT request.
- A future admin feature that renders signatures in a different context (e.g., an admin review page) will always receive pre-sanitised HTML.

### 7.3 CSRF enforcement

`PUT` and `DELETE` are non-safe methods that modify user state. Both endpoints include `_csrf: None = Depends(enforce_cookie_csrf)`. Cookie-authenticated browser clients must supply the `x-csrf-token` header matching the `ui_csrf` cookie value, per `app/auth/policy.py:71-97`. Note that `enforce_cookie_csrf` performs a 2-way check (header == cookie value) — it does NOT additionally verify against the session-stored `csrf_token` (that 3-way check is only in `require_ui_session` at `app/services/sessions.py:427-436`). Bearer-token clients (including E2E tests using `page.request` with the global `request` fixture) skip CSRF enforcement per the existing policy. `GET /ui/email/signature` is a safe method and does not require CSRF.

### 7.4 Ownership enforcement

The `pk = USER#{actor.sub}` key is computed from the authenticated `actor.sub` resolved by `get_authenticated_user`. A user can only read, write, or delete their own signature — there is no admin endpoint to manage another user's signature in this ticket.

### 7.5 No secrets stored

Signatures are presentation content, not credentials. They are stored in plaintext DynamoDB (no KMS encryption needed). The `password_ct_b64` field on account rows remains the only KMS-encrypted field on the `user_email_accounts` table.

## 8. Backward Compatibility & Migration

### 8.1 No data migration

The `SIGNATURE` row type is new; no existing `user_email_accounts` rows use `sk = SIGNATURE`. Adding the new row type is zero-downtime: old code ignores rows it does not recognise, and the EML-003 account listing queries (`ByUser` GSI) only return rows with `ACCT#` prefix skips because `created_at` is absent on the `SIGNATURE` row.

### 8.2 No schema changes to `scripts/local-ddb-init.py`

The `user_email_accounts` table definition remains unchanged. After running `just restart` (which wipes and recreates all DynamoDB Local tables), the table exists with its original schema and the signature row type is ready to be created on first PUT.

### 8.3 Additive models

`SignatureIn` and `SignatureOut` are new Pydantic classes appended to `app/models.py`. No existing model is modified. No existing serialisation is affected.

### 8.4 Router is append-only

The three signature endpoints are appended to the end of `app/routers/user_email_accounts.py`. No existing endpoint is reordered or modified. FastAPI matches routes in declaration order; since `GET /signature`, `PUT /signature`, and `DELETE /signature` use a static path segment (`signature`) rather than a dynamic capture (`{account_id}`), there is no risk of path-parameter shadowing. The literal `signature` endpoint must be declared before any future catch-all `/{account_id}/...` sub-routes if such are added; the current EML-003/EML-004 route order places static paths (e.g., `POST /{account_id}/verify`, `POST /{account_id}/sync`) after the account CRUD routes, so the three `/signature` endpoints (which share the same path prefix but no `{account_id}`) are safely distinct.

### 8.5 Settings backward compatibility

`email_signatures_enabled` defaults to `false`. No existing deployment is affected. No `.env.local.example` change is strictly required (the feature is off), but the example file should document the new key with a comment for discoverability.

## 10. Open Questions / Assumptions

1. **Per-account signatures (future):** This design uses a single per-user signature. If per-account signatures are ever needed (e.g., different signature for work vs. personal IMAP account), the row key `sk=SIGNATURE#ACCT#{account_id}` can be added without a schema change. Assumed out of scope for EML-006.

2. **Image hosting in signatures:** HTML signatures often contain `<img src="...">` pointing to external URLs. EML-006 stores those URLs verbatim — it does not proxy, re-host, or validate them. If external image tracking or privacy concerns arise (e.g., images loading from attacker-controlled servers revealing the recipient's IP), a future ticket can strip or proxy `<img src>` attributes. Assumed acceptable for P2 initial delivery.

3. **Signature versioning / history:** No history is maintained; each PUT overwrites. If audit-quality signature history is needed (e.g., to understand what signature was included in a particular sent email), the approach would be to snapshot the signature at send time into the `user_email_messages` item. Assumed out of scope.

4. **Admin management of user signatures:** No admin endpoint is provided to view or delete another user's signature. If a ROOT-level compliance action is needed (e.g., sanitising a malicious signature already stored), it would be handled via the `rootctl` CLI writing directly to DDB. Assumed acceptable.

5. **`bleach` dependency:** The spec uses a regex-based sanitiser to avoid adding a new third-party dependency. This is consistent with the pattern in `app/models.py:9167` and `app/services/audit_export_pipeline.py` (no `reportlab`). If a future security review determines regex-based sanitisation is insufficient, `bleach` or `nh3` can be substituted in `_sanitize_signature_html` without changing the API or data model.

6. **Assumption: EML-003 ships first.** This spec assumes the `user_email_accounts` table, `T.user_email_accounts` handle, and `S.user_email_accounts_table_name` / `S.email_client_enabled` settings already exist from EML-003 implementation. EML-006 cannot be implemented before EML-003.

7. **Assumption: EML-004's `send_message` is the only outbound send path.** System-level transactional emails via `send_alert_email` are not modified to include user signatures — they are platform-to-user notifications, not user-composed emails.
