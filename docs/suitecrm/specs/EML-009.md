# EML-009 — Campaign email HTML template library

**Type:** Feature | **Priority:** P1 | **Estimate:** 2d  
**Flag:** `CAMPAIGN_EMAIL_TEMPLATES_ENABLED` (default OFF)

---

## 1. Summary & Goal

EML-009 adds a campaign-specific HTML email template resource that allows
marketing campaign sends (MKT-009) to use a custom per-campaign HTML body
with recipient merge fields, rather than always falling back to the generic
plain-text `send_alert_email` path. The feature extends the existing
`admin_messaging_templates` DynamoDB table (used by `app/services/notification_templates.py`)
with a new `channel="campaign"` row type, adds `campaign_id` and `merge_fields`
attributes, and exposes five new admin endpoints appended to
`app/routers/admin_email.py`.

The render path — `render_campaign_body(template_id, recipient_vars)` — is the
contract point for MKT-009: when a campaign has a linked `template_id` the
send function calls `render_campaign_body` and passes the resulting `html_body`
to `send_alert_email(..., html_body=html_body)` (EML-001). Without EML-001's
`html_body` parameter, campaign HTML would be silently discarded.

With `CAMPAIGN_EMAIL_TEMPLATES_ENABLED=0` (default) the entire new surface
is gated: all five new endpoints return 503, `render_campaign_body` is never
called, and MKT-009 falls back to its existing plain-text body. The rest of the
platform — including every existing endpoint in `admin_email.py` and every row
in `admin_messaging_templates` with `channel` other than `"campaign"` — is
byte-for-byte unchanged.

## 3. Data Model

### 3.1 Reuse of `admin_messaging_templates` table

No new DynamoDB table is created. Campaign templates live as rows in the
existing `admin_messaging_templates` table (PK `TEMPLATE#{template_id}`,
SK `META`) with two additive attributes:

| Attribute | Type | Notes |
|---|---|---|
| `campaign_id` | S | Optional link to a `MarketingCampaign`; stored as empty string `""` when absent |
| `merge_fields` | L (list of S) | Caller-declared `{{variable}}` names beyond the standard set |

All existing attributes (`template_id`, `channel`, `name`, `subject`, `body`,
`variables`, `active`, `updated_at`, `updated_by`) are preserved unchanged.
The `channel` attribute is set to `"campaign"` for rows created by EML-009.

**Standard merge fields** available to every campaign template regardless of
`merge_fields` declaration:

| Variable | Source |
|---|---|
| `{{first_name}}` | recipient profile `display_name` first token |
| `{{email}}` | recipient email address |
| `{{unsubscribe_url}}` | `{S.public_base_url}/ui/preferences/unsubscribe?token=...` |
| `{{platform_name}}` | Caller-supplied string — `S.platform_name` does **not** exist in `app/core/settings.py`; MKT-009 must resolve the platform name from a local constant or a different settings key and inject it into `recipient_vars` |
| `{{campaign_name}}` | campaign `name` field |

`merge_fields` on the template item lists *additional* variables the template
author expects callers to supply. The renderer does not enforce presence; missing
vars are left as-is (inheriting `_render`'s existing behaviour at
`notification_templates.py:256–257`).

### 3.2 `scripts/local-ddb-init.py`

No new `TableDef` entry is required. The `admin_messaging_templates` table is
already declared at `scripts/local-ddb-init.py:1430–1434` with no GSIs.
Campaign templates are retrieved via the same full-table scan used by
`list_templates(channel="campaign")`, which is already paginated.

If, at a later milestone, the volume of campaign templates makes scanning
expensive, an `ByChannel` GSI (`partition_key="channel"`, `sort_key="updated_at"` N,
`attr_types={"updated_at": "N"}`) can be added to the `TableDef` without any
table-schema migration. This ticket does not add that GSI — the scan path
suffices for typical deployments with O(100) templates.

### 4.1 Service layer — `app/services/notification_templates.py`

---

#### `create_campaign_template(actor_sub: str, payload: dict) -> dict`

```python
def create_campaign_template(actor_sub: str, payload: dict) -> dict:
    """Create a new campaign-channel template.

    payload keys: name (str), subject (str), body (str),
                  campaign_id (str | None), merge_fields (list[str])
    Returns the stored item dict in _to_out shape, extended with
    campaign_id and merge_fields.
    Calls audit_event("campaign_template_created", actor_sub, ...).
    """
```

Implementation notes:
- Generates `template_id = "campaign_" + uuid4().hex[:12]` to avoid collisions
  with existing `email_*` / `sms_*` seeded IDs.
- Sets `channel="campaign"`, `active=True`, `updated_at=now_ts()`,
  `updated_by=actor_sub`.
- Strips `<script>` tags from `body` using the same `re.sub` already applied by
  `NotificationTemplateUpdate._strip_script_tags` at `app/models.py:9166–9173`.
- Calls `T.admin_messaging_templates.put_item(Item={...})`.
- Calls `audit_event("campaign_template_created", actor_sub, template_id=template_id)`.
- Returns `_campaign_to_out(item)` (see §4.5).

---

#### `render_campaign_body(template_id: str, recipient_vars: dict) -> tuple[str, str]`

```python
def render_campaign_body(
    template_id: str,
    recipient_vars: dict,
) -> tuple[str, str]:
    """Render subject and HTML body for a campaign send.

    Returns (subject, html_body). On any error (missing template, inactive
    template) logs a warning and returns ("", "") so MKT-009 can fall back
    to plain-text without raising.
    """
```

Implementation notes:
- Calls `get_template(template_id)`.
- If the template is absent or `active=False`, logs a warning and returns
  `("", "")`.
- Calls `_render(tpl["subject"], recipient_vars)` and
  `_render(tpl["body"], recipient_vars)` — same `_render` helper at lines 245–260.
- Drops the `missing_vars` list from the return value (caller does not need it;
  missing vars appear literally in output so admins can detect them).
- Returns `(rendered_subject or "", rendered_body or "")`.
- This function never raises; exceptions are caught and logged.

---

#### `list_campaign_templates() -> list[dict]`

```python
def list_campaign_templates() -> list[dict]:
    """Return all active + inactive campaign-channel templates."""
```

Delegates to the existing `list_templates(channel="campaign")` at line 145.
Returns items in `_campaign_to_out` shape.

---

#### `_campaign_to_out(item: dict) -> dict`

Private helper extending `_to_out` with campaign-specific fields:

```python
def _campaign_to_out(item: dict) -> dict:
    base = _to_out(item)
    base["campaign_id"] = item.get("campaign_id") or None
    base["merge_fields"] = list(item.get("merge_fields") or [])
    return base
```

## 5. Detailed Behavior & Edge Cases

### 5.1 `render_campaign_body` — unknown variables

Following `_render`'s existing contract at `notification_templates.py:257`,
an unknown `{{var}}` token in the template body is **left as-is** in the rendered
output. MKT-009 passes rendered HTML to the recipient regardless. Admins can
detect the issue by checking the preview endpoint's `missing_vars` field (also
returned by `preview_template`).

### 5.2 `render_campaign_body` — inactive template

If the template row has `active=False`, `render_campaign_body` logs
`WARNING: campaign template {template_id} inactive; skipping html` and returns
`("", "")`. MKT-009 must treat an empty `html_body` return as a signal to fall
back to its existing plain-text body and not pass `html_body=""` to
`send_alert_email` (an empty string is falsy in Python and EML-001 only passes
`Html` to SES when `html_body` is truthy).

### 5.3 `render_campaign_body` — missing template

Same as inactive: logs `WARNING` and returns `("", "")`. Never raises.

### 5.4 PATCH channel guard

`PATCH /campaign-templates/{template_id}` verifies `item["channel"] == "campaign"`
before applying changes. If an admin supplies a `template_id` that belongs to
an `email` or `sms` channel template, the endpoint returns 404 with
`detail="Template not found or not a campaign template"`. This prevents
accidentally overwriting notification templates through the campaign endpoint.

### 5.5 DELETE is a soft delete

`DELETE /campaign-templates/{template_id}` sets `active=False` via the
existing `update_template` path. The row remains in DynamoDB. If MKT-009
holds a reference to the `template_id` in a campaign record, `render_campaign_body`
silently falls back to plain text rather than failing the send job.

### 5.6 Concurrent create idempotency

`create_campaign_template` does not use `ConditionExpression="attribute_not_exists(pk)"`.
Template IDs include a 12-hex uuid fragment and are not user-supplied, making
collisions negligible. If duplicate creation is a concern, a conditional put
can be added in a follow-up without API-contract change.

### 5.7 `body` size limit

`CampaignEmailTemplateCreate.body` is capped at 50,000 characters (the SES
`Body.Html.Data` safe limit cited in EML-001). Bodies over 50,000 characters
fail model validation with a `max_length` error before any DDB write.

### 5.8 `merge_fields` validation

Each entry must match `[a-zA-Z0-9_]{1,64}`. This mirrors the `_VAR_RE` pattern
(`[a-zA-Z0-9_]+`) and prevents injection of whitespace or special characters
that could confuse downstream processors. Validation happens in the Pydantic
`field_validator` on `CampaignEmailTemplateCreate`; the stored list is trusted
on read.

### 5.9 Flag off — MKT-009 fallback path

When `S.campaign_email_templates_enabled = False`:
- All five new admin endpoints return 503.
- MKT-009 must not call `render_campaign_body` (gating is in MKT-009's send
  function, not here). The guard in MKT-009 is:
  `if campaign.get("template_id") and S.campaign_email_templates_enabled`.
- Existing `GET /ui/admin/notifications/templates` (prefix `/ui/admin/notifications`)
  is unaffected; it still lists `email` and `sms` channel templates.

### 5.10 Preview endpoint with empty `sample_vars`

`POST .../preview` with `{}` as `sample_vars` returns the template body with
all `{{var}}` tokens left as-is and `missing_vars` listing every declared
variable. This is useful for quickly auditing which variables the template
expects.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No dev_mode branch

`create_campaign_template`, `render_campaign_body`, and
`list_campaign_templates` contain no `if S.dev_mode` branches. The same
DynamoDB read/write path runs in both environments. Dev mode only affects
`send_alert_email` (which has its own dev-log path already in place at
`alerts.py:462–468`); EML-009 does not call `send_alert_email`.

### 7.2 CSRF on mutating endpoints

`POST /campaign-templates`, `PATCH /campaign-templates/{id}`, and
`DELETE /campaign-templates/{id}` all use `require_admin_or_root_csrf`
(app/auth/policy.py:100), which enforces both role (`ADMIN` or `ROOT`) and
CSRF token matching. `GET` and `POST .../preview` use `require_admin_or_root`
(read-only role check, no CSRF required).

### 7.3 Script injection prevention

`body` is sanitised at the model layer (`CampaignEmailTemplateCreate` and
`CampaignEmailTemplateUpdate` both strip `<script>…</script>` tags). This
mirrors the identical validator at `app/models.py:9165–9173`. The sanitisation
happens before DDB write and before any render call, so stored bodies are
always script-clean. Other potentially dangerous tags (`<iframe>`, `<object>`,
`onload=`) are left to SES's recipient mail client — this is consistent with
the existing `NotificationTemplateUpdate` behaviour (same scope, same risk
surface).

### 7.4 Authorization

All five endpoints require `ADMIN` or `ROOT` role. Non-admin users get 403 from
`require_admin_or_root` before the flag guard fires. There is no user-facing
exposure of campaign templates.

### 7.5 Audit trail

Create, update, and delete operations emit `audit_event(...)` to `T.alerts`
via the existing `app/services/alerts.audit_event` path (line 644). Audit rows
carry `template_id`, `actor_sub`, and timestamp. Retrieving the audit trail uses
the existing admin alert log endpoints already available in the platform.

### 7.6 Template-to-campaign linkage is advisory

`campaign_id` on the template is a soft reference. There is no foreign-key
constraint enforced at the DDB level. MKT-009 must resolve the `template_id`
from the campaign record (not the other way around). Deleting a campaign does
not cascade to deactivate its template; deleting a template does not fail if
a campaign still references it (send falls back to plain text per §5.2).

## 8. Backward Compatibility & Migration

### 8.1 Zero migration path

The `admin_messaging_templates` table already exists in every deployment. No
`UpdateTable` call, no backfill, and no new table are required. Campaign
templates are simply new rows with `channel="campaign"` in the existing table.
Existing `email` and `sms` rows are untouched.

### 8.2 `list_templates` scan unchanged

The existing `list_templates()` scan at `notification_templates.py:145–168`
returns all rows with `sk=META`, then filters by `channel` if supplied.
Without the `channel` filter it returns campaign templates too — this is
intentional and backwards-compatible: the `channel` field has always been
present and callers that care about channel already filter. The admin
notifications router at `admin_notifications.py:30–35` calls
`list_templates(channel=channel)`, so querying with `channel="email"` or
`channel="sms"` continues to exclude campaign templates.

### 8.3 `NotificationTemplateOut` unchanged

`CampaignEmailTemplateOut` is a subclass that adds two optional fields.
Clients that call `GET /ui/admin/notifications/templates` (the sibling router)
continue to receive `NotificationTemplateOut` shapes with no extra fields.
Clients that call `GET /ui/admin/email/campaign-templates` receive the extended
`CampaignEmailTemplateOut`. There is no version bump or content-type change.

### 8.4 Enabling the flag on an existing deployment

Setting `CAMPAIGN_EMAIL_TEMPLATES_ENABLED=1` immediately activates the five
new endpoints. No DDB changes or seed scripts are needed because the table
already exists. Disabling the flag again does not remove existing campaign
template rows — they are simply unreachable until the flag is re-enabled.
