# CAS-015 — Knowledge Base — articles, categories, search, case deflection

**Type:** Feature  **Priority:** P2  **Estimate:** 4 days  
**Ticket source:** `docs/suitecrm/CRM_CASES_PORTAL_TICKETS.md`, section "CAS-015"

---

## 1. Summary & Goal

CAS-015 adds a **Knowledge Base (KB)** module to the platform: a publicly readable article library with hierarchical categories, full-text prefix search, agent-managed article lifecycle (draft → published → archived), per-article helpful/not-helpful ratings, and a **case deflection hook** that attaches the top three matching KB articles to every newly created ticket so users can self-serve before an agent responds.

Concrete deliverables:

1. A new `KbArticleService` in `app/services/kb_articles.py` backed by the `crm_kb_articles` DynamoDB table (scaffolded by CAS-001).
2. A new router `app/routers/kb_articles.py` with public read endpoints, authenticated rating endpoints, and admin CRUD/lifecycle endpoints.
3. Category item management (stored in the same single table under `CATEGORY#` SK prefix).
4. Token-prefix search on article titles, stored as a `search_tokens` DDB StringSet at write time; queried with a DDB `FilterExpression` `contains` scan across the published-article GSI.
5. Case deflection: `create_ticket` (`app/routers/tickets.py:766`) calls `KbArticleService().search_articles(q)` when `S.crm_cases_kb_enabled` and attaches the top-3 results to `TicketOut.suggested_articles`.
6. Two new frontend components: `KbPage.tsx` (public article browser) and a suggestion panel inside the existing `TicketsPage.tsx` ticket-creation form.

With `CRM_CASES_KB_ENABLED=0` (default), the platform is byte-for-byte identical to today: all new endpoints return 404, no search is performed on ticket creation, and `TicketOut.suggested_articles` is always `None`.

### 2.5 Prefix search pattern

`build_prefix_tokens` (`app/routers/messaging.py:2743`) and `build_message_search_tokens` (line 2775) define the project-standard prefix tokenization. Note that `build_prefix_tokens` uses the regex `r"[a-z0-9@._-]+"` (includes dots, dashes, @ etc.) while `build_message_search_tokens` includes stemming via snowball. For KB article title search, a simpler variant is appropriate: lowercase word extraction via `re.findall(r"[a-z0-9]+", text.lower())` (alphanumeric only, no punctuation), then for each word emit all prefixes of length 1 through `min(len(word), 8)` (capped at 8 to mirror `_MSG_SEARCH_MAX_PREFIX_LEN = 8` at line 2786 — index tokens and query tokens must use the same cap). This is stored in a `search_tokens` DDB StringSet on the article item. The `contains(search_tokens, :token)` FilterExpression approach is sufficient at KB scale (hundreds to low thousands of articles). A fan-out SEARCH_TOKEN index can be adopted later if volume warrants.

The file manager uses an analogous inline `_search_tokens` helper (`app/services/filemanager.py:966`) and queries with `all(token in haystack for token in tokens)` (`app/services/filemanager.py:984`) — the same "all-token-must-match" conjunction semantics apply here.

### 3.3 Search token construction

At write time (`create_article`, `update_article`, `publish_article`):

```python
_KB_SEARCH_MAX_PREFIX = 8

def _build_search_tokens(title: str) -> set[str]:
    tokens: set[str] = set()
    for word in re.findall(r"[a-z0-9]+", title.lower()):
        for i in range(1, min(len(word), _KB_SEARCH_MAX_PREFIX) + 1):
            tokens.add(word[:i])
    return tokens  # stored as a DDB StringSet
```

At query time, `search_articles(q)` extracts the longest unique word from `q` (after the same normalization) and calls:

```python
T.crm_kb_articles.query(
    IndexName="ByStatus",
    KeyConditionExpression="status = :pub",
    FilterExpression="contains(search_tokens, :token)",
    ExpressionAttributeValues={":pub": "published", ":token": query_token},
)
```

Multiple words: the query is run for the first (longest) non-trivial token; the result set is then filtered in Python to require all remaining tokens to appear in `title.lower()`. This avoids N serial queries while still matching multi-word queries.

## 5. Detailed Behavior & Edge Cases

### 5.1 Article lifecycle state machine

```
draft → published  (via publish_article)
published → archived  (via archive_article)
archived → draft  (via re-draft endpoint, POST /kb/articles/{id}/redraft — admin only)
draft → deleted  (via delete_article)
archived → deleted  (via delete_article)
published → deleted  (BLOCKED — 409 "cannot_delete_published_article"; archive first)
```

`publish_article` rebuilds `search_tokens` from the current `title` at publish time so that any pre-publish title edits are reflected in the live search index immediately.

### 5.2 Category constraints

- `delete_category` returns 409 `category_has_articles` if any article (any status) references `category_id`. Agents must re-categorize or delete articles first.
- `category` on an article is a free-form string stored verbatim; the service validates that a `CATEGORY#{category}` item exists at write time (returns 404 `category_not_found` otherwise). This enforces referential integrity without a foreign-key mechanism.
- `parent_category_id` is validated to exist as a category item. Circular parent references (A → B → A) are prevented by a two-hop depth check: a category whose `parent_category_id` is already non-null may not itself be used as `parent_category_id` (enforced in `create_category` / `update_category` — two-level hierarchy maximum, matching the ticket's description of "hierarchical categories").

### 5.3 Search behavior

- Empty or single-character `q` returns 422 (validated in router via `Query(min_length=2)`).
- The `ByStatus` GSI query uses `ScanIndexForward=False` so the most recently published articles appear first in the raw result. Results are then re-ranked by `helpful_count desc` in Python before slicing to `limit`.
- The DDB `FilterExpression` `contains(search_tokens, :token)` requires an exact prefix token match; partial suffix matches are not supported (consistent with the messaging search design). This is expected behavior documented in the UI.
- Search is **published articles only**. Drafts and archived articles never appear in `GET /public/kb/search` or the case deflection hook.

### 5.4 View count atomicity

`GET /public/kb/articles/{article_id}` calls `increment_view_count` using a DDB `ADD view_count :one` update expression with no condition check. This is a best-effort counter — slight over/under-counting under concurrent load is acceptable.

### 5.5 Rating idempotency

Each `POST /kb/articles/{article_id}/rate` writes a de-duplicate row:

```
pk="RATE#{article_id}"  sk="USER#{user_sub}"  helpful=<bool>  created_at=<ts>
```

with `ConditionExpression="attribute_not_exists(pk)"`. On a second vote by the same user, the condition fails and the service returns 409 `already_rated`. Changing a vote (e.g., switching from helpful to not-helpful) is not supported in this version — this is an open question (see §10).

### 5.6 Case deflection — empty results

If no KB articles match, `suggested_articles` is set to `[]` (empty list), not `None`, so the frontend can distinguish "KB feature active but no matches" from "KB feature off". The handler sets `suggested_articles = []` when `S.crm_cases_kb_enabled=True` and the search returns zero items.

### 5.7 HTML sanitization

`body_html` is stored as-is by the service layer. The router enforces a 64 KB size cap (Pydantic `max_length=65536`). HTML sanitization (stripping `<script>`, `<iframe>`, etc.) is the responsibility of the frontend display layer using a library such as DOMPurify. A future hardening pass may add server-side sanitization using `bleach` or `lxml.html.clean` — tracked as a follow-up in §10.

### 5.8 Slug uniqueness

`create_category` checks for an existing `CATEGORY#` item by `slug` using a `Scan` with `FilterExpression="slug = :slug AND begins_with(pk, :pfx)"` before writing. On collision, returns 409 `slug_already_exists`. This scan is acceptable because category count is bounded (tens to hundreds at most).

### 5.9 Large `body_html` and DynamoDB 400 KB item limit

A single DDB item is capped at 400 KB. With `body_html` up to 64 KB and all other fields, this is well within the limit. If a future version requires larger bodies, the body can be offloaded to S3 (the presigned URL pattern from `kyc_partner_api.py:636` applies) and stored as `body_s3_key`. This is tracked as an open question (§10).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

No `S.dev_mode` branch is introduced anywhere in CAS-015. DynamoDB access uses `T.crm_kb_articles` uniformly. The `search_articles` DDB query and the `increment_view_count` DDB update run identically against DynamoDB Local (dev) and real DynamoDB (prod). S3 usage (future image upload extension) would use `app.core.aws_clients.s3_client()` — moto in-process in dev, real S3 in prod — with no code fork.

### 7.2 Idempotency

- `create_article` uses `put_item` with `ConditionExpression="attribute_not_exists(pk)"`. Callers must generate a fresh `article_id` per attempt; the service provides `article_id` to the caller so re-POST of the same body creates a new article (no idempotency key is exposed at the API level — this is intentional for CRUD).
- `publish_article` is idempotent: calling it on an already-published article returns the current item unchanged (status is already `published`, no DB write).
- `rate_article` is single-use per user per article (§5.5).
- `increment_view_count` is not idempotent by design (view counter).

### 7.3 Auth and access control

- Public endpoints (`/public/kb/*`) carry no authentication. They return only `status=published` items.
- `rate_article` requires a valid `ui_session` cookie to prevent anonymous spam voting.
- Admin endpoints require `_is_admin(user)` (`app/routers/tickets.py:207`), i.e. `Role.ADMIN` or `Role.ROOT`. Non-admin receives 403.
- CSRF: all non-GET authenticated endpoints enforce CSRF via `require_ui_session` (cookie auth) or skip CSRF for Bearer-auth API clients (consistent with CLAUDE.md CSRF rules).
- Article body HTML is not executed server-side. XSS mitigation is frontend DOMPurify (noted as a follow-up, §10).

### 7.4 Audit trail

Every article lifecycle transition emits `audit_event(event, author_sub, request, ...)` to `T.alerts`:
- `kb_article.created` — on `create_article`
- `kb_article.published` — on `publish_article`
- `kb_article.archived` — on `archive_article`
- `kb_article.deleted` — on `delete_article`
- `kb_article.rated` — on `rate_article`
- `kb_category.created` / `kb_category.updated` / `kb_category.deleted` — on category mutations

These event strings must be added to `ALERT_EVENT_TYPES` in `app/services/alerts.py:134` (additive; the list is already long and accepts arbitrary new strings).

### 7.5 Rate limiting

The public search endpoint `GET /public/kb/search` does not require auth and could be called in a tight loop. The existing rate-limit infrastructure in `app/services/rate_limit.py` (pattern: `_bucket_limit`, keyed by IP or `api_key_id`) should be applied per client IP: `rate_limit_kb_search(ip, category="read")` with a cap of 100 req/min (`CRM_KB_SEARCH_RL_READ`, default 100). This mirrors the KYC partner API rate-limit approach (`app/services/kyc_partner_api.py`, GAP-0286). Rate-limit enforcement is best-effort (fail-open).

## 8. Backward Compatibility & Migration

### 8.1 No schema changes to existing tables

CAS-015 writes only to `T.crm_kb_articles` (a CAS-001 table). `T.tickets`, `T.alerts`, `T.alert_prefs`, and all other existing tables are read-only from CAS-015's perspective, or written only via pre-existing, well-tested service methods (`audit_event`).

### 8.2 `TicketOut` model change

Adding `suggested_articles: list[KbArticleSummaryOut] | None = None` to `TicketOut` (`app/routers/tickets.py:58`) is backward-compatible: existing API consumers that do not read this field are unaffected. Consumers that do read it receive `null` when the flag is off or no match is found.

### 8.3 `app/main.py` router registration

`app.include_router(kb_router, prefix="/ui")` is added once at the bottom of the router registration block in `app/main.py`. No existing router is modified or displaced.

### 8.4 Migration on flag enable

When `CRM_CASES_KB_ENABLED` is toggled from `0` to `1` in a live environment, the `crm_kb_articles` table already exists (CAS-001 created it on deploy). No backfill is required — the table starts empty and agents populate it on first use. Existing ticket history is not retroactively augmented with `suggested_articles`.

## 10. Open Questions / Assumptions

1. **HTML sanitization server-side**: Currently deferred to frontend DOMPurify. A server-side pass using `bleach` (Python) would harden against stored XSS if the KB admin role is ever delegated to less-trusted users. Recommendation: add to a CAS-015b hardening ticket.

2. **Article rating — vote change**: Current design allows only one vote per user per article (no update). If users want to change a rating, the `RATE#` de-duplicate row must be read and the old counter decremented atomically — a two-step operation that requires a transaction. Deferred to a follow-up.

3. **Search ranking**: Currently re-ranked by `helpful_count desc` in Python after a DDB query. For higher volume (thousands of articles), a dedicated search token fan-out table (pattern: `SEARCH_TOKEN#{token}` / `ARTICLE#{article_id}`) would allow index-only lookups without `FilterExpression` scans. Deferred — the current approach handles hundreds of articles without issue.

4. **Body offload to S3**: If articles require >64 KB bodies (e.g., embedded base64 images), `body_html` would exceed practical DDB item size before hitting the 400 KB hard limit. In that case, store the body in S3 at `{S.crm_kb_articles_body_s3_prefix}{article_id}/body.html` and a `body_s3_key` pointer in DDB. The public `GET /public/kb/articles/{id}` endpoint would fetch and return the body inline. Deferred for now.

5. **Category item count**: `list_categories` currently does a full Scan of `CATEGORY#*` items. If category count exceeds ~100, a dedicated `ByCategory` list query (GSI or dedicated table) would be more efficient. At current scale, the scan is acceptable.

6. **Assumption — CAS-001 is merged**: CAS-015 assumes `T.crm_kb_articles`, `S.crm_cases_kb_enabled`, and `S.crm_kb_articles_table` are already wired from CAS-001. If CAS-001 is not yet merged, those four items must be added inline as part of this ticket's PR.

7. **`suggested_articles` on list endpoints**: Currently, `GET /tickets` (list) does not populate `suggested_articles`. Only `POST /tickets` (create) returns suggestions. This is intentional — the deflection hook fires only at creation time. If agents need to see suggestions on existing tickets, a separate `GET /tickets/{id}/suggestions` endpoint would be the right shape.
