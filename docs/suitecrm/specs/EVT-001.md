# EVT-001 — Feature flag, settings & DynamoDB scaffolding for CRM Events

**Type:** Chore | **Priority:** P1 | **Estimate:** 1d  
**Source:** `docs/suitecrm/CRM_MISC_TICKETS.md` (section "EVT-001")  
**Dependencies:** None — this is the foundation ticket for all EVT-* work.

---

## 1. Summary & Goal

This ticket introduces the minimal, additive scaffolding required before any CRM Events feature can ship:

1. A single feature flag `crm_events_enabled` in `app/core/settings.py`, default `False`, that gates all subsequent EVT-* routes and workers.
2. Two new DynamoDB tables (`crm_events`, `crm_event_registrations`) declared via the `TableDef` pattern in `scripts/local-ddb-init.py`, with correct numeric `attr_types` for every GSI sort key.
3. Two corresponding `_FloatSafeTable` handles added to the `Tables` dataclass and `T` singleton in `app/core/tables.py`.
4. A single guard helper `_require_crm_events_enabled()` that every subsequent EVT router calls as its first action.

With this ticket merged and the flag off (the default), the platform is byte-for-byte unchanged: no new routes exist, no background workers run, and the two new DynamoDB tables are created empty at `just restart` time without affecting any existing table.

## 2. Context & Current State

### Feature flag pattern

`app/core/settings.py` uses a frozen `@dataclass` `Settings` with one field per config value, all read from environment variables at import time (`app/core/settings.py:6-8`). Boolean flags follow two conventions:

- **Default-true**: `os.environ.get("VAR", "1") not in ("0", "false", "False")` — for example `compute_billing_enabled` at `app/core/settings.py:2385`.
- **Default-false**: `os.environ.get("VAR", "false").lower() in ("1", "true", "yes", "on")` — for example `newsfeed_recsys_enabled` at `app/core/settings.py:2014`; or equivalently `os.environ.get("VAR", "0").lower() in ("1", "true", "yes", "on")` — for example `legal_export_enabled` near the end of the file.

`crm_events_enabled` must use the **default-false** convention, matching `legal_export_enabled` (which has an explicit comment explaining the default-off contract).

A companion table-name setting is also needed so the table name can be overridden in integration environments without code changes (same pattern as every other table: `calendar_table_name` at `app/core/settings.py:466`, `contacts_table_name` at `app/core/settings.py:498`).

### Guard helper pattern

`app/routers/webhooks.py:51-53` shows the canonical inline guard:

```python
def _require_webhooks_enabled():
    if not S.webhooks_enabled:
        raise HTTPException(status_code=403, detail="Webhooks feature is disabled")
```

The `CRM_MISC_TICKETS.md` header constraint (line 11) specifies that routes should return **404** when the flag is off, not 403. This matches how `app/routers/group_treasury.py:27-29` handles its flag (the helper is named `_check_enabled`, not `_require_*`): `raise HTTPException(status_code=404, detail="Group treasury is not enabled")` (the raise is at `app/routers/group_treasury.py:29`). The guard for CRM Events follows the 404 convention.

### DynamoDB `TableDef` pattern

`scripts/local-ddb-init.py:28-35` defines `TableDef` with fields `name`, `partition_key`, `sort_key`, `gsi`, and `attr_types`. The `_attribute_definitions` function at line 2496 applies `attr_types` overrides on top of the default `"S"` type. **Numeric GSI sort keys must appear in `attr_types`** or DynamoDB Local stores them as String, causing `ValidationException` at query time (CLAUDE.md gotcha, confirmed at `scripts/local-ddb-init.py:34` comment).

Several existing tables demonstrate the correct numeric GSI sort key pattern:

- `sticker_collections` at `scripts/local-ddb-init.py:80-85`: `attr_types={"created_at": "N"}`.
- `kyc_risk_scores` at lines 170-178: `attr_types={"timestamp": "N"}`.
- `returns` at lines 2483-2492: `attr_types={"created_at": "N"}` shared by two GSIs.

### `Tables` dataclass and `T` singleton

`app/core/tables.py:68-572` defines the frozen `Tables` dataclass and the module-level `T = Tables(...)` singleton. Every new table requires:

1. A typed `Any` field in the `Tables` dataclass body (lines 69-319).
2. A corresponding `_safe_table(S.<table_name_setting>)` call in the `T = Tables(...)` constructor (lines 321-572).

The `_FloatSafeTable` proxy (`app/core/tables.py:29-66`) wraps every `put_item` and `update_item` call to coerce `float` to `Decimal`, making numeric DDB writes float-safe across all callers without per-call wrapping.

### Existing calendar table (reuse relationship)

`T.calendar` (`app/core/tables.py:94`) uses PK=`calendar_id`, SK=`sk` and is registered at `S.calendar_table_name` (`app/core/settings.py:466`, default `"calendar"`). The `crm_events` table **links** to this table via a `calendar_event_id` foreign key (an opaque string reference to an item in `T.calendar`) but does not share the table. EVT-002 will write invitee rows into `crm_events`; the calendar item itself is never written by EVT code.

### `app/main.py` startup registration

`app/main.py` registers routers via `app.include_router(...)` imports (lines 1-300+). There is currently no `crm_events` router import. This ticket does not add a router — the router is introduced in EVT-002 — but subsequent tickets must add their import and `app.include_router(crm_events_router, ...)` call here. No startup task is needed for this ticket.

### Hermetic test pattern

All new `pytest` files in this project bind moto-backed DynamoDB table objects to the frozen `T` and `S` handles via `object.__setattr__` (canonical example: `tests/test_gap_0220_0221_ssh_stored_key.py`). `TestClient` is broken; route handlers must be called directly on a fresh `asyncio` event loop.

## 3. Data Model

### 3.1 `crm_events` table

Single-table pattern. All item types share the same PK/SK space.

| Attribute | Type | Purpose |
|-----------|------|---------|
| `event_id` | S (PK) | UUID hex; stable identifier for a CRM event |
| `sk` | S (SK) | Row type discriminator: `META`, `INVITEE#{invitee_sub}` (EVT-002), etc. |
| `owner_sub` | S | User who created the event; written on META row |
| `calendar_event_id` | S | FK to a `T.calendar` item (`calendar_id#event_id`) written on META row; nullable (event may not have a calendar anchor) |
| `created_at` | N | Unix timestamp (`now_ts()`); written on META row; GSI sort key |
| `name` | S | Human-readable event name |
| `description` | S | Free-text description |
| `max_attendance` | N | Optional capacity limit; absent means unlimited |

**GSIs:**

| Index | PK | SK | Usage |
|-------|----|----|-------|
| `ByOwner` | `owner_sub` (S) | `created_at` (N) | List all events for a user, newest-first |
| `ByCalendar` | `calendar_event_id` (S) | `created_at` (N) | Look up CRM events linked to a calendar event |

Both GSIs share the numeric `created_at` sort key, so `attr_types={"created_at": "N"}` is required.

**`TableDef` entry** (to be added to `scripts/local-ddb-init.py` inside `_table_defs()`, after the `returns` entry at line 2492):

```python
TableDef(
    _resolve_table_name(S.crm_events_table_name, "crm_events"),
    "event_id",
    "sk",
    gsi=[
        {"index_name": "ByOwner", "partition_key": "owner_sub", "sort_key": "created_at"},
        {"index_name": "ByCalendar", "partition_key": "calendar_event_id", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
),
```

### 3.2 `crm_event_registrations` table

Separate table for registration records to avoid hot-partition issues (large events may have thousands of registrants; keeping them separate from the event metadata table keeps `crm_events` queries cheap).

| Attribute | Type | Purpose |
|-----------|------|---------|
| `event_id` | S (PK) | FK to `crm_events` event_id |
| `registrant_sub` | S (SK) | User sub of the registrant |
| `status` | S | One of `registered`, `accepted`, `declined`, `attended`, `waitlisted` (EVT-003/004) |
| `registered_at` | N | Unix timestamp; GSI sort key |
| `responded_at` | N | Unix timestamp; nullable until accept/decline |
| `checked_in_at` | N | Unix timestamp; nullable until check-in |
| `waitlist_position` | N | Nullable; set by EVT-004 when at capacity |

**GSIs:**

| Index | PK | SK | Usage |
|-------|----|----|-------|
| `ByRegistrant` | `registrant_sub` (S) | `registered_at` (N) | List all events a user is registered for |

`attr_types={"registered_at": "N"}` required.

**`TableDef` entry:**

```python
TableDef(
    _resolve_table_name(S.crm_event_registrations_table_name, "crm_event_registrations"),
    "event_id",
    "registrant_sub",
    gsi=[
        {"index_name": "ByRegistrant", "partition_key": "registrant_sub", "sort_key": "registered_at"},
    ],
    attr_types={"registered_at": "N"},
),
```

### 3.3 Rationale for separate tables

A single-table design combining events and registrations would use PK=`event_id`, SK=`REGISTRATION#{registrant_sub}` alongside `SK=META` and `SK=INVITEE#*` rows. That works for low-cardinality events but creates a very wide partition for large events (e.g., 5,000 registrants × 3 GSI projections). DynamoDB Local does not enforce the 10 GB per-partition limit, but production does. Separate tables give each registration its own partition.

The trade-off is that capacity counting (EVT-004) requires a `Query` on `crm_event_registrations` rather than a key-condition within one partition — acceptable given that capacity checks occur only at registration time, not on every read.

### 4.3 Guard helper

The guard lives in `app/routers/crm_events.py` (the new router file introduced by EVT-002). Its signature is defined here so all EVT tickets implement it identically:

```python
from fastapi import HTTPException
from app.core.settings import S

def _require_crm_events_enabled() -> None:
    """Raise HTTP 404 when the CRM Events feature flag is off.

    Must be called as the first statement in every EVT-* route handler.
    Returns None (does not raise) when S.crm_events_enabled is True.
    """
    if not S.crm_events_enabled:
        raise HTTPException(status_code=404, detail="CRM Events feature is not enabled")
```

The 404 status code is required by the `CRM_MISC_TICKETS.md` header constraint (line 11): "With the flag off all new routes return 404". This differs from `_require_webhooks_enabled()` in `app/routers/webhooks.py:51-53`, which uses 403. The 404 convention prevents feature discovery by probing status codes.

Usage in every subsequent EVT route handler:

```python
@router.post("/", status_code=201)
async def create_crm_event(
    body: CrmEventCreateIn,
    ctx: AuthenticatedUser = Depends(require_ui_session),
):
    _require_crm_events_enabled()
    # ... handler body
```

The guard is a plain function, not a FastAPI `Depends` dependency, because it reads only `S` (module-level singleton) and needs no injected context. This matches the `_require_webhooks_enabled()` pattern.

### 4.4 No `app/main.py` changes in this ticket

EVT-001 does not introduce a router. `app/main.py` is not modified. EVT-002 will add:

```python

# ...
app.include_router(crm_events_router)
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off behavior

With `CRM_EVENTS_ENABLED` unset or set to any value other than `"1"`, `"true"`, `"yes"`, or `"on"`:

- `S.crm_events_enabled` evaluates to `False` at import time (frozen dataclass; value is fixed for the lifetime of the process).
- No routes exist (EVT-002+ introduces them; they always call `_require_crm_events_enabled()` first).
- `T.crm_events` and `T.crm_event_registrations` are valid boto3 table proxies pointing to real DynamoDB tables — they just hold no items.
- `just restart` creates both tables (DynamoDB `CreateTable` is idempotent; the existing-table error — `ResourceInUseException` — is swallowed by `_ensure_table` at `scripts/local-ddb-init.py:2534-2592`).

There is no code path that writes to these tables when the flag is off because all write paths originate from route handlers that begin with `_require_crm_events_enabled()`.

### 5.2 Flag-on behavior

With `CRM_EVENTS_ENABLED=1`:

- EVT-002 route handlers proceed past the guard.
- All reads and writes use `T.crm_events` and `T.crm_event_registrations` via `_FloatSafeTable`, which coerces floats on write.
- Downstream EVT tickets may query the `ByOwner` GSI (PK=`owner_sub`, SK=`created_at` numeric) or `ByRegistrant` GSI (PK=`registrant_sub`, SK=`registered_at` numeric). Because `attr_types` is declared correctly, DynamoDB stores and queries these as `N` type from the first write.

### 5.3 `_safe_table` wrapping and float coercion

The `_FloatSafeTable.update_item` path (`app/core/tables.py:47-49`) coerces only `ExpressionAttributeValues`. When EVT-002+ service code uses `update_item` with numeric expression attribute values (e.g., `":ts": now_ts()`), `now_ts()` returns `int` (`app/core/time.py:2`), which DynamoDB's boto3 serializer accepts directly. The `_to_decimal` function (`app/core/tables.py:11-26`) only converts `float`; `int` values pass through unchanged.

### 5.4 `attr_types` propagation in `_attribute_definitions`

`scripts/local-ddb-init.py:2496-2506` shows that `_attribute_definitions` starts from the PK/SK types (both `"S"` by default), then iterates GSI keys (also defaulting to `"S"`), then applies `attr_types` overrides. This means:

- `crm_events`: `created_at` appears as a sort key in two GSIs. Without `attr_types={"created_at": "N"}`, it would be created as `"S"`, and queries using `KeyConditionExpression` with an integer value would fail with `ValidationException`.
- `crm_event_registrations`: `registered_at` appears as the sort key in `ByRegistrant`. Same reasoning.

Both `TableDef` entries include the correct `attr_types` dict.

### 5.5 `_resolve_table_name` call

Every `TableDef` in `_table_defs()` uses `_resolve_table_name(S.<name>, "<fallback>")` (defined at `scripts/local-ddb-init.py:38-39`). The fallback string is used only when the settings value is empty, which cannot happen with the defaults defined in 4.1. The explicit fallback is defensive convention.

### 5.6 Table name collision risk

`"crm_events"` and `"crm_event_registrations"` are new names not present in any existing `Settings` field or `TableDef`. A grep of `app/core/settings.py` and `scripts/local-ddb-init.py` confirms no existing table uses either name. The DynamoDB Local instance (port 8001) persists data across backend restarts (`CLAUDE.md` dev stack table); a `just restart` (clean-wipe) recreates all tables, so stale data from a previous schema iteration is not a concern.

Those flags are not part of this ticket; EVT-001 introduces only `crm_events_enabled`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

This ticket introduces no dev-mode branches. The `Settings` dataclass reads from the environment identically in dev and prod. The `TableDef` entries in `scripts/local-ddb-init.py` create tables against DynamoDB Local (dev) and real DynamoDB (prod) using the same code path — `_ensure_table` calls `create_table` and swallows `ResourceInUseException` in both environments.

There is no `if S.dev_mode:` branch anywhere in this ticket. The flag reads the same env var in both environments; the only difference is that prod sets it via a secrets/parameter store rather than `.env.local`.

### Table creation idempotency

`_ensure_table` (`scripts/local-ddb-init.py:2534-2592`) catches `ResourceInUseException` from DynamoDB and returns, making `just restart` safe to run repeatedly. The `_wait_for_tables` call (`scripts/local-ddb-init.py:2613`) polls until tables reach `ACTIVE` status before returning, so the backend never starts against a `CREATING` table.

### Security surface of this ticket

This ticket introduces no routes, no user data writes, and no authentication changes. The only security-relevant decision is the **default-off** flag, which ensures:

1. No new attack surface is exposed until an operator explicitly opts in.
2. A misconfigured deploy that omits `CRM_EVENTS_ENABLED=1` cannot accidentally expose the CRM Events API.

The `_require_crm_events_enabled()` guard raises 404 (not 403 or 401), preventing enumeration of disabled features by unauthenticated callers.

### `T` handle immutability

`Tables` is a `@dataclass(frozen=True)` (`app/core/tables.py:68`). Test code binds moto tables onto the frozen `T` via `object.__setattr__` (bypassing the dataclass freeze), which is the established pattern. This works because `frozen=True` only blocks `__setattr__` on the dataclass instance; `object.__setattr__` skips the descriptor protocol.

## 8. Backward Compatibility & Migration

### Additive-only changes

This ticket touches three files:

1. `app/core/settings.py` — adds three new fields to the frozen `Settings` dataclass. Because `Settings` is instantiated once at module level (`S = Settings()` at end of file), adding fields with defaults never breaks callers that reference existing fields.

2. `app/core/tables.py` — adds two fields to the `Tables` dataclass and two entries to the `T = Tables(...)` constructor. The constructor uses positional-by-name keyword arguments (all arguments are named in the `Tables(...)` call), so adding new fields at the end does not shift existing arguments.

3. `scripts/local-ddb-init.py` — appends two `TableDef` entries. `_table_defs()` returns a list; appending to it is safe.

No existing field, route, test, or migration is modified.

### Schema migration in production

Neither table exists in production before this ticket ships. The `_ensure_table` call creates them on first run of `scripts/local-ddb-init.py` (or its prod equivalent). There is no data to migrate, no GSI backfill, and no `UpdateTable` required.

If a later ticket (e.g., EVT-002) needs a new GSI on `crm_events`, that ticket's spec will document the `UpdateTable` + backfill procedure. For this ticket, the two GSIs (`ByOwner`, `ByCalendar` on `crm_events`; `ByRegistrant` on `crm_event_registrations`) are declared from the first `CreateTable` call, so no backfill is ever needed for these indexes.

### `.env.local.example` update

`CRM_EVENTS_ENABLED=0` should be appended to `.env.local.example` with a comment:

```
# CRM Events module (EVT-001). Default off; set to 1 to enable.
CRM_EVENTS_ENABLED=0
```

This follows the convention used by other feature flags in that file.

## 10. Open Questions / Assumptions

1. **`calendar_event_id` foreign key format.** The `crm_events` META row stores `calendar_event_id` as an opaque string. `T.calendar` uses PK=`calendar_id`, SK=`event_id` (separate fields). The FK could be stored as `"{calendar_id}#{event_id}"` (composite) or just `event_id` (assuming a single calendar). The composite form is assumed here to allow CRM events to span multiple user calendars. EVT-002 should confirm this with the calendar service owner.

2. **`ByCalendar` GSI sparseness.** Items with `sk != "META"` (e.g., invitee rows from EVT-002) will not carry `calendar_event_id`, so the GSI is sparse. This is intentional and correct: DynamoDB only projects items that carry both GSI key attributes. Invitee rows without `calendar_event_id` are invisible to `ByCalendar` queries.

3. **PTY contact resolution.** EVT-002 adds invitees identified by `user_sub`. Once PTY-001 ships, invitees may be identified by `contact_id` or `account_id` instead. The `crm_events` and `crm_event_registrations` tables use `user_sub` strings throughout, which are platform-native identifiers. PTY FKs can be stored as additional optional attributes without a schema change. This assumption should be confirmed before EVT-002 starts.

4. **Multi-tenant isolation.** `T.crm_events` items carry `owner_sub` but no `tenant_id`. The `T.calendar` table similarly uses `calendar_id`-scoped partitions without cross-tenant isolation at the DDB level. If the tenant middleware (`ENTERPRISE-001`) is active, queries must filter by `owner_sub` (which is tenant-scoped via the session). A `ByTenant` GSI may be needed later if admin-level cross-user queries are required. Deferred to a future ticket.

5. **`_require_crm_events_enabled` location.** The guard is defined in `app/routers/crm_events.py` (EVT-002). If future EVT tickets introduce separate router files (e.g., `app/routers/crm_geocoding.py` for EVT-005), they will define their own `_require_crm_geocoding_enabled()` guard rather than importing from `crm_events.py`, keeping coupling minimal.
