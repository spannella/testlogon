# QUO-003 — Quote-to-invoice and quote-to-contract conversion

**Type:** Feature  **Priority:** P1  **Estimate:** 3d  
**Flag:** `AOS_QUOTES_ENABLED` (shared with QUO-001; default `"0"` / off)  
**Depends on:** QUO-001 (quote entity), QUO-004 (contract entity)

---

## 1. Summary & Goal

QUO-003 closes the "quote lifecycle terminal transitions" gap identified in the SuiteCRM gap analysis (section "[T2] Quotes, Products, Contracts & PDF Templates (AOS)"). It adds two endpoints that advance an accepted sales quote to either a draft invoice record or a draft contract record:

- `POST /ui/quotes/{quote_id}/convert-to-invoice` — copies the quote's financial data into a new invoice row in the existing `invoices` table, transitions the quote stage to `converted`, and stamps `converted_to_invoice_number` on the quote.
- `POST /ui/quotes/{quote_id}/convert-to-contract` — creates a new row in the `aos_contracts` table (QUO-004), transitions the quote stage to `converted`, and stamps `converted_to_contract_id`.

Both operations are atomic from the caller's perspective: the quote stage update and the downstream entity creation share a "check-and-update" pattern on the quote item using a DynamoDB conditional expression so that a retry of either endpoint is idempotent.

The feature is entirely additive: with `AOS_QUOTES_ENABLED=0` the two new endpoints return 404 and no existing code path changes.

## 3. Data Model

### No new DynamoDB tables

QUO-003 is purely additive to two existing tables (`invoices` from FIN-001, `aos_quotes` from QUO-001) and one dependency table (`aos_contracts` from QUO-004). No new `TableDef` entries are required in `scripts/local-ddb-init.py`.

### Changes to the `aos_quotes` table (QUO-001)

Two new optional string attributes are added to the quote item in-place. They are written atomically during conversion via a conditional `update_item`:

| Attribute | Type | Description |
|---|---|---|
| `converted_to_invoice_number` | S (string) | Set when `convert-to-invoice` succeeds; e.g. `"INV-2026-00042"`. Absent until conversion. |
| `converted_to_contract_id` | S (string) | Set when `convert-to-contract` succeeds; e.g. `"con_abc123..."`. Absent until conversion. |
| `stage` (existing) | S | Transitioned to `"converted"` atomically with the above write. |

These fields are sparse — they do not exist on unconverted quotes and DynamoDB never stores NULL for absent attributes. No new GSI is required; the existing GSI2 (per-user stage filter) already handles queries for `stage=converted` quotes.

No `attr_types` changes are needed since neither new attribute is a GSI key.

### Changes to the `invoices` table (FIN-001, no schema change)

The existing `create_invoice` at `invoices.py:272` accepts arbitrary extra kwargs which are passed through onto the persisted item via the `extra` pattern (same mechanism as `provider` attribution described in CLAUDE.md). QUO-003 adds `aos_quote_id` as one such extra field. The table schema itself is unchanged; the attribute is simply stored as an additional string on the item.

The `_serialize` function at `invoices.py:218` must be extended to surface `aos_quote_id` in its output (see Section 4). The `InvoiceOut` Pydantic model at `models.py:9545` gains `aos_quote_id: str = ""` as an additive optional field.

### Changes to the `aos_contracts` table (QUO-004)

`create_contract` from QUO-004 accepts `aos_quote_id` as a first-class field at item creation time. No QUO-003-specific schema change is needed here; QUO-003 simply passes the quote's `quote_id` to QUO-004's service.

## 4. API / Service Design

### New endpoints in `app/routers/aos_quotes.py`

Both endpoints are appended after the existing `POST /ui/quotes/{quote_id}/stage` endpoint defined by QUO-001.

#### `POST /ui/quotes/{quote_id}/convert-to-invoice`

```python
@aos_quotes_router.post(
    "/{quote_id}/convert-to-invoice",
    response_model=InvoiceOut,
    status_code=201,

def convert_quote_to_invoice(
    quote_id: str,
    ctx: Dict[str, Any] = Depends(require_ui_session),
    request: Request = None,

    _require_enabled()          # raises 404 if AOS_QUOTES_ENABLED=0
    result = quote_conversion_service.convert_to_invoice(
        user_sub=ctx["user_sub"],
        quote_id=quote_id,
        request=request,
    )
    return InvoiceOut(**result)
```

#### `POST /ui/quotes/{quote_id}/convert-to-contract`

```python
@aos_quotes_router.post(
    "/{quote_id}/convert-to-contract",
    response_model=ContractOut,

)
def convert_quote_to_contract(
    quote_id: str,
    ctx: Dict[str, Any] = Depends(require_ui_session),

```

`_require_enabled()` is the same guard function from QUO-001's router, checking `S.aos_quotes_enabled`.

### New service module: `app/services/aos_quote_conversion.py`

Keeping conversion logic in its own module avoids circular imports between `aos_quotes.py` (which owns CRUD) and `invoices.py` / `aos_contracts.py` (which own their respective entity creation). It also makes the single-responsibility boundary clear.

#### `convert_to_invoice(user_sub, quote_id, request=None) -> dict`

```python
def convert_to_invoice(
    *,
    user_sub: str,
    quote_id: str,
    request=None,
) -> Dict[str, Any]:
    """Convert an accepted quote to a draft invoice.

    Steps:
    1. Fetch and ownership-validate the quote.
    2. Assert stage == "accepted"; raise 400 otherwise.
    3. Assert converted_to_invoice_number not set; raise 409 if already converted.
    4. Call create_invoice(...) from app.services.invoices.
    5. Atomically update the quote via conditional update_item:
       - SET stage = "converted"
       - SET converted_to_invoice_number = <invoice_number>
       - ConditionExpression: attribute_not_exists(converted_to_invoice_number)
       raises 409 on ConditionCheckFailedException (concurrent duplicate).
    6. Emit audit_event("quote.converted", user_sub, ...).
    7. Record activity via record_activity(...).
    8. Return the InvoiceOut-shaped dict from create_invoice.
    """
```

Key implementation notes:

- `create_invoice` is called with `invoice_type="shop"` (the closest match in `VALID_TYPES` at `invoices.py:33`; QUO-005 will add `"quote"` as a proper type). The `aos_quote_id` is threaded as an extra dict field: `extra={"aos_quote_id": quote_id}`. This matches the `provider` attribution pattern at `billing.py:1134`.
- `amount_cents` = quote `subtotal_cents` (the pre-tax subtotal). `tax_cents` = quote `tax_cents`. The invoice `total_cents` is computed by `create_invoice` as `amount_cents + tax_cents`.
- `line_items` is mapped from the quote's `line_items` list: each entry `{description, qty, unit_price_cents, ...}` becomes `{"description": li["description"], "quantity": li["qty"], "amount_cents": li["line_total_cents"]}` matching the `InvoiceLineItemOut` shape at `models.py:9539`.
- `buyer_name` and `buyer_email` are sourced from the quote's `contact_id` if set (via `get_profile_identity` from `app/services/profile.py`); otherwise fall back to the authenticated user's profile. Both can be empty strings; `create_invoice` handles empty gracefully (renders "Customer" as fallback at `invoices.py:168`).
- `currency` passes through from the quote directly.
- `ledger_entry_id` is left as `""` (no pre-existing ledger entry; the invoice is a proposal, not a settled payment).
- The invoice is created with the default `status="generated"` from `create_invoice`. QUO-005 will later extend the status lifecycle to `"draft"` for quote-originated invoices; for now `"generated"` is acceptable and backward-compatible.
- The step-5 conditional `update_item` uses:
  ```
  UpdateExpression="SET #stage = :converted, converted_to_invoice_number = :inv_num"
  ConditionExpression="attribute_not_exists(converted_to_invoice_number)"
  ExpressionAttributeNames={"#stage": "stage"}
  ExpressionAttributeValues={":converted": "converted", ":inv_num": invoice_number}
  ```
  A `ConditionalCheckFailedException` from botocore (`ClientError` with code `ConditionalCheckFailedException`) means a concurrent call already converted this quote; raise `HTTPException(409, {"code": "quote_already_converted"})`.

#### `convert_to_contract(user_sub, quote_id, request=None) -> dict`

```python
def convert_to_contract(
    *,
    user_sub: str,
    quote_id: str,
    request=None,
) -> Dict[str, Any]:
    """Convert an accepted quote to a draft contract.

    Steps:
    1. Fetch and ownership-validate the quote.
    2. Assert stage == "accepted"; raise 400 otherwise.
    3. Assert converted_to_contract_id not set; raise 409 if already converted.
    4. Call create_contract(...) from app.services.aos_contracts (QUO-004).
    5. Atomically update the quote:
       - SET stage = "converted"
       - SET converted_to_contract_id = <contract_id>
       - ConditionExpression: attribute_not_exists(converted_to_contract_id)
    6. Emit audit_event("quote.converted", user_sub, ...).
    7. Record activity via record_activity(...).
    8. Return the ContractOut-shaped dict from create_contract.
    """
```

`create_contract` is called with:
- `user_sub` = quote `user_sub` (owner, not necessarily the authenticated user — quotes can be converted by an admin on behalf of the owner; see Section 5).
- `title` = `f"Contract from {quote['quote_number']}"` as a sensible default; caller can `PATCH /ui/contracts/{id}` afterward.
- `value_cents` = quote `total_cents`.
- `currency` = quote `currency`.
- `account_id` = quote `account_id` (empty string if unset).
- `contact_id` = quote `contact_id` (empty string if unset).
- `aos_quote_id` = `quote_id`.
- `start_date` = `now_ts()`.
- `end_date` = `None` (open-ended; caller sets via PATCH).
- `renewal_notice_days` = default 30 (from QUO-004 service default).

## 5. Detailed Behavior & Edge Cases

### Stage pre-condition

Both endpoints enforce `stage == "accepted"` before performing any write. The full set of error responses:

| Condition | HTTP | Code |
|---|---|---|
| Quote not found or not owned by `user_sub` | 404 | `quote_not_found` |
| Quote stage is not `accepted` | 400 | `quote_must_be_accepted` |
| Quote already has `converted_to_invoice_number` set | 409 | `quote_already_converted` |
| Quote already has `converted_to_contract_id` set | 409 | `quote_already_converted` |
| Concurrent duplicate (conditional check failure) | 409 | `quote_already_converted` |
| `AOS_QUOTES_ENABLED=0` | 404 | (plain "not enabled") |

### Double-conversion guard

A quote can only be converted once to a single target type. Attempting to call `convert-to-invoice` on a quote that already has `converted_to_invoice_number` set returns 409 before touching the invoices table. Similarly for `convert-to-contract`. Calling `convert-to-invoice` on a quote that was already `convert-to-contract`-ed also returns 409 (stage is `converted`; the check on `stage == "accepted"` catches this). This means a quote cannot produce both an invoice and a contract — it is a single terminal conversion, matching SuiteCRM AOS behavior.

### Partial failure recovery

`convert_to_invoice` calls `create_invoice` first (step 4), then performs the conditional `update_item` on the quote (step 5). If step 5 fails (e.g. network error), the invoice exists but the quote is still in `accepted` stage with no `converted_to_invoice_number`. On retry, step 4 is called again, and since `ledger_entry_id=""`, `create_invoice` does NOT use its ledger-based idempotency guard and will mint a second invoice number. To prevent orphaned duplicates, the service checks for an existing `converted_to_invoice_number` (set in step 5) before calling `create_invoice`:

```python
# Idempotency check before creating invoice
existing = quote.get("converted_to_invoice_number")
if existing:
    raise HTTPException(409, {"code": "quote_already_converted"})
# ... proceed to create_invoice ...
```

Because `create_invoice` is called before the conditional update, there is a narrow TOCTOU window between the initial check and the `create_invoice` call where two concurrent requests could both pass the pre-check and both call `create_invoice`. The subsequent conditional `update_item` (step 5) with `attribute_not_exists(converted_to_invoice_number)` acts as the final arbiter: only one request will succeed; the other will receive `ConditionalCheckFailedException` → 409. The winning invoice number is stamped on the quote; the losing invoice number is an orphan. Orphaned invoices (created but never stamped on a quote) are a known acceptable outcome — they exist in the `invoices` table with `invoice_type="shop"` and `aos_quote_id` set, queryable by admin via `GET /ui/admin/invoices`. They do not affect billing ledger state since no ledger entry exists for them.

### Admin-owned quotes

When an admin performs a conversion on a quote owned by another user, `ctx["user_sub"]` is the admin's sub but the quote's `user_sub` belongs to the original creator. The service always looks up the quote using the path parameter `quote_id` and verifies ownership against `quote["user_sub"]`. If the authenticated user is not the owner, the service checks `role >= ADMIN` (via `normalize_role(ctx["role"]) in {Role.ADMIN, Role.ROOT}`); if not, it raises 404 (not 403, to avoid revealing existence of other users' quotes). The resulting invoice is owned by `quote["user_sub"]`, not the admin's sub.

### Currency passthrough

Quote `currency` is passed directly to `create_invoice`. The invoices system stores it as-is; no exchange-rate conversion is performed. Multi-currency support (exchange rates) is deferred to a later PRD/OFBiz milestone.

### Line-item mapping

Quote line items use `line_total_cents` (the per-row net total after quantity × unit_price × discount). Invoice `amount_cents` is set to the quote's `subtotal_cents` (sum of all `line_total_cents` before tax). Each line item on the invoice has `amount_cents = li["line_total_cents"]` and `quantity = li["qty"]`. The `unit_price_cents` field is not yet in `InvoiceLineItemOut` (that addition belongs to QUO-005); for QUO-003 it is omitted.

### Audit and activity

Both conversions emit two side-effect calls (best-effort, wrapped in `try/except` so they never block the response):

1. `audit_event("quote.converted", user_sub, request=request, quote_id=quote_id, conversion_target="invoice"|"contract", target_id=<invoice_number_or_contract_id>)` — writes to `T.alerts` via `alerts.py:644`.
2. `record_activity(user_id=user_sub, actor_id=ctx_user_sub, activity_type="quote_converted", target_type="invoice"|"contract", target_id=<id>)` — writes to `T.activity_feed` via `activity_feed.py:45`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 dev/prod parity

There is no `if S.dev_mode` branch anywhere in `aos_quote_conversion.py`. The moto S3/DynamoDB mock intercepts boto3 at the botocore layer (configured by `app/core/dev_s3.py` at startup), so `create_invoice`'s `_store_pdf` and `_s3.put_object` calls work identically in dev and prod. The `_render_pdf` PDF renderer is pure Python with no system dependencies (same pattern as `receipts.py` and `invoices.py:103`). No dev-only stubs or mock branches are introduced.

### Idempotency

- **Invoice conversion**: The `attribute_not_exists(converted_to_invoice_number)` conditional on the `update_item` acts as the idempotency key. A retry after the conditional write has succeeded returns 409 (the quote already has the field set), which is the correct safe behavior.
- **Contract conversion**: Same pattern with `attribute_not_exists(converted_to_contract_id)`.
- **Invoice creation idempotency**: `create_invoice` supports `ledger_entry_id`-based idempotency but QUO-003 does not use it (no pre-existing ledger entry). The orphan-handling in Section 5 is the mitigation.

### Ownership enforcement

- Quote lookup uses `T.aos_quotes.get_item(Key={"pk": f"USER#{user_sub}", "sk": f"QUOTE#{quote_id}"})`. A quote belonging to a different user is never returned (DynamoDB key isolation). Admins pass an explicit `target_user_sub` if operating on behalf of another user (see Section 5 admin path).
- Invoice ownership: `create_invoice` writes under `USER#{owner_sub}`, not `USER#{admin_sub}`.

### Input validation

- `quote_id` path parameter is validated to be non-empty (FastAPI 422 if missing).
- No free-text fields are accepted from the request body; all input is sourced from the authenticated quote record.
- `currency` is passed through verbatim from the quote; no injection risk (stored as string attribute).

### No money movement

Neither conversion endpoint touches the billing ledger (`billing_shared.new_ledger_entry` is not called). Invoice conversion creates a record-keeping document, not a charge. The charge path belongs to QUO-005's `pay_invoice` feature.

## 8. Backward Compatibility & Migration

### Zero impact when flag is off

With `AOS_QUOTES_ENABLED=0` (the default): the two new endpoints are never registered in FastAPI's route table (the `_require_enabled()` guard is called at handler entry, so from FastAPI's perspective the routes exist but return 404 immediately). The `invoices` table, `InvoiceOut` model, and `_serialize` function are each modified additively:

- `InvoiceOut.aos_quote_id` defaults to `""` — existing `InvoiceOut(**data)` calls succeed unchanged since `data` dicts from existing `_serialize` calls never contain `aos_quote_id`, so Pydantic uses the default.
- `_serialize` addition of `"aos_quote_id": str(record.get("aos_quote_id") or "")` is always safe since `dict.get` returns `None` for absent keys, coerced to `""`.

### Table migration

- `aos_quotes` table: the two new attributes (`converted_to_invoice_number`, `converted_to_contract_id`) are sparse and DynamoDB is schema-less for non-key attributes. Existing quote items simply lack these attributes; the service reads them with `quote.get("converted_to_invoice_number")` defaulting to `None`/falsy. No table migration, backfill, or `UpdateTable` call is needed.
- `invoices` table: `aos_quote_id` is a non-key attribute added to new items only. Existing invoice items are untouched.
- No new DynamoDB tables; no `local-ddb-init.py` changes.

### Merge order

QUO-003 must be merged after QUO-001 (quote entity and `transition_stage`) and after QUO-004 (contract entity and `create_contract`). The `convert-to-invoice` path has no QUO-004 dependency, but `convert-to-contract` imports from `app.services.aos_contracts`. If merging QUO-003 before QUO-004, the `convert-to-contract` endpoint can be commented out or guarded by `if not S.aos_contracts_enabled: raise HTTPException(501)` until QUO-004 lands.

QUO-003 and QUO-005 share the `InvoiceOut` model: QUO-005 adds `payment_terms_days`, `due_date`, `voided_at`, and `unit_price_cents` to `InvoiceLineItemOut`. QUO-003 adds `aos_quote_id`. Both are additive fields with defaults; they can be merged in either order without conflict.

## 10. Open Questions / Assumptions

1. **`invoice_type` for quote-originated invoices**: The spec uses `invoice_type="shop"` since `VALID_TYPES` at `invoices.py:33` does not include `"quote"`. QUO-005 is the natural place to extend `VALID_TYPES` with `"quote"`. Until then, `"shop"` is the closest semantic match (a sales transaction). Implementors should coordinate with QUO-005 and change `invoice_type="quote"` once QUO-005 adds it to `VALID_TYPES`.

2. **Invoice `status` for quote-originated invoices**: `create_invoice` hardcodes `status="generated"` at `invoices.py:335`. QUO-005 introduces a `"draft"` status for manually-created invoices. Quote-originated invoices arguably should start as `"draft"` (not yet sent to the buyer). This requires QUO-005's status enum extension to land first. For QUO-003, `status="generated"` is used as-is; QUO-005 implementation note: add `status_override` param to `create_invoice` for this use case.

3. **Buyer name/email resolution priority**: The spec resolves `buyer_name`/`buyer_email` from `contact_id` if set, then falls back to the owner's profile. If neither is available, `create_invoice` renders "Customer" (see `invoices.py:168`). If CRM contact/account records (from PTY-011/PTY-012) are not yet deployed, the fallback to profile identity is acceptable.

4. **Orphan invoice cleanup**: Invoices created in the TOCTOU window (see Section 5) are orphaned — they have `aos_quote_id` set and `invoice_type="shop"` but no corresponding quote reference. A future admin cleanup endpoint or a scheduled reconciliation job could identify them. No immediate action required for QUO-003.

5. **`convert-to-contract` requires QUO-004 to be deployed first**: If QUO-003 is shipped before QUO-004, the `convert-to-contract` endpoint returns 409 (`contracts_not_enabled`). This is by design.

6. **Multi-conversion**: SuiteCRM allows a quote to be converted to both an invoice and a contract. This spec implements a single-terminal-conversion model (converted quote cannot be converted again). If the business requires dual-path conversion, the guard conditions must be separated: `converted_to_invoice_number` and `converted_to_contract_id` are independent attributes, and only a `stage == "accepted"` check (not `stage == "converted"`) would block the second conversion. This decision should be made before implementation.
