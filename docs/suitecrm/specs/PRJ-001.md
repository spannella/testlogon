# PRJ-001 — Feature flag, settings keys, and DynamoDB table scaffold

**Ticket type:** Chore  
**Priority:** P0  
**Estimate:** 1d  
**Area:** CRM Projects, Project Tasks & Gantt  
**Source:** `docs/suitecrm/CRM_PROJECTS_GANTT_TICKETS.md` § "PRJ-001"

## 1. Summary & Goal

PRJ-001 is the pure scaffolding ticket for the entire CRM project-management feature family (PRJ-001 through PRJ-012). It delivers exactly four things, none of which are user-visible:

1. A single top-level feature flag `CRM_PROJECTS_ENABLED` that gates all downstream PRJ work at the HTTP boundary, leaving every byte of existing platform behavior unchanged when the flag is off (default).
2. Four settings keys on `app/core/settings.Settings` — one boolean flag and four string table-name keys — following the existing `bool = os.environ.get(...) not in ("0","false","False")` pattern already used for flags such as `cart_reminders_enabled` (`app/core/settings.py:821`).
3. Four DynamoDB table definitions in `scripts/local-ddb-init.py`, inserted after the existing `projects` table block at line 277, with correct `attr_types` for every numeric GSI sort key.
4. Four corresponding table handles declared in `app/core/tables.Tables` and wired via `_safe_table(...)` in the frozen `T` singleton, appended after the `returns=_safe_table(S.returns_table_name)` entry at line 571.

No router, no service module, no Pydantic model, and no frontend change ships in this ticket. The only observable outcome is that `scripts/local-ddb-init.py` creates four additional DynamoDB tables on a clean stack start, and that `T.crm_pm_projects`, `T.crm_pm_tasks`, `T.crm_pm_members`, and `T.crm_pm_templates` are importable from any service module without error.

## 2. Context & Current State

### Existing file-grouping `projects` table — do not touch

The platform already has a `projects` table used by `app/routers/projects.py` and `app/services/projects_store.py`. The existing `ProjectModel` at `app/models.py:1796` carries only `id`, `owner`, `name`, `description`, `tags`, `settings`, `created_at`, and `updated_at` — these are cloud file-grouping fields, not CRM project-management fields. The `projects` router is imported in `app/main.py:81` as `projects_router` and registered via `app.include_router(projects_router)` at `app/main.py:682`. The `projects` table `TableDef` at `scripts/local-ddb-init.py:269–277` uses `PK`/`SK` keys with two GSIs (`GSI1`, `GSI2`) but no `attr_types` override (all keys are strings).

**None of the above files are modified by this ticket.** CRM project management lives in entirely separate tables and a new router file that does not exist yet.

### Settings singleton pattern

`app/core/settings.Settings` (`class Settings` at `app/core/settings.py:7`; `@dataclass` decorator at line 6) is a frozen `@dataclass` where every field is a class-level default pulled from `os.environ.get(...)`. The module-level singleton `S = Settings()` is assigned at `app/core/settings.py:2772`. Because the dataclass is frozen, all runtime mutations go through `object.__setattr__` (tests only).

The canonical pattern for a **default-off boolean flag** is seen at:
- `cart_reminders_enabled` (`app/core/settings.py:821`): `bool = os.environ.get("CART_REMINDERS_ENABLED", "1") not in ("0", "false", "False")` — this one defaults ON.
- `returns_rma_enabled` (`app/core/settings.py:846`): `bool = os.environ.get("RETURNS_RMA_ENABLED", "false").lower() == "true"` — this one defaults OFF.
- `inventory_reservations_enabled` (`app/core/settings.py:839`): `bool = os.environ.get("INVENTORY_RESERVATIONS_ENABLED", "false").lower() == "true"` — another default-OFF.

PRJ-001 follows the `returns_rma_enabled` / `inventory_reservations_enabled` pattern: default env value is `"0"` (falsy), resulting in `False`.

The canonical pattern for **table-name string keys** is seen throughout the file, e.g. `returns_table_name` (`app/core/settings.py:847`): `str = os.environ.get("RETURNS_TABLE_NAME", "returns")`.

### Table handle pattern

`app/core/tables.py` defines `_safe_table(name: str) -> Any` at line 65 (return annotation is `Any`, not `_FloatSafeTable`), which wraps `ddb.Table(name)` with a proxy that coerces Python `float` to `Decimal` on every `put_item` / `update_item` call. The frozen `Tables` dataclass (line 69; field list begins line 70) lists every table as `Any`. The singleton `T = Tables(...)` constructor opens at line 321 and is constructed by passing `_safe_table(S.<name>_table_name)` for each field. The last entry before the closing `)` (line 572) is `returns=_safe_table(S.returns_table_name)` at line 571.

### DynamoDB table definition pattern

`scripts/local-ddb-init.py` defines `TableDef` at line 29 (`@dataclass(frozen=True)` decorator at line 28):

```python
@dataclass(frozen=True)
class TableDef:
    name: str
    partition_key: str
    sort_key: Optional[str] = None
    gsi: List[Dict[str, str]] = field(default_factory=list)
    attr_types: Dict[str, str] = field(default_factory=dict)
```

The `attr_types` dict overrides attribute types for keys that are not strings. The CLAUDE.md "DynamoDB numeric GSI sort keys" note and the existing `kyc_proof_of_funds` entry (`scripts/local-ddb-init.py:260–268`, `attr_types={"created_at": "N"}`) confirm that numeric GSI sort keys **must** be declared here or DynamoDB raises `ValidationException` at query time.

The helper `_resolve_table_name(name: str, fallback: str) -> str` at `scripts/local-ddb-init.py:38` returns `name or fallback`. All new tables use it so that the env var override takes effect.

### Guard helper pattern

Several feature families expose a `_require_<feature>()` helper at the top of their router that raises `HTTPException(status_code=404)` when the feature flag is off. This ticket introduces the file `app/routers/crm_projects.py` containing only this guard (plus the `APIRouter` stub). All downstream PRJ route handlers will call `_require_crm_projects()` as their first statement, before auth resolution.

## 3. Data Model

### Overview

Four DynamoDB tables are created. All follow the platform's single-table `PK`/`SK` design with `GSI` projections. Table names are configurable via env vars and stored as strings on `Settings`; the default names are fixed strings that cannot collide with existing tables.

### 3.1 `crm_pm_projects` — CRM project header records (PRJ-002+)

```
Hash key  : PK  (S)
Range key : SK  (S)
GSI1      : GSI1PK (S)  /  GSI1SK (S)   — owned-project lookup by project_id
GSI2      : GSI2PK (S)  /  GSI2SK (N)   — status-filtered list, sorted by created_at
attr_types: {"GSI2SK": "N"}
```

**Future item shape** (established in PRJ-002, not stored yet in this ticket):

| Attribute | Value |
|-----------|-------|
| `PK` | `OWNER#{owner_sub}` |
| `SK` | `PROJECT#{project_id}` |
| `GSI1PK` | `PROJECT#{project_id}` |
| `GSI1SK` | `OWNER#{owner_sub}` |
| `GSI2PK` | `STATUS#{status}` |
| `GSI2SK` | `created_at` (integer Unix seconds, `attr_types="N"`) |
| `entity_type` | `"crm_project"` |

GSI2 enables `GET /v1/crm/projects?status=underway` to query `GSI2PK="STATUS#underway"` with numeric range conditions on `GSI2SK` without a full-table scan.

### 3.2 `crm_pm_tasks` — Project task rows (PRJ-003+)

```
Hash key  : PK  (S)
Range key : SK  (S)
GSI1      : GSI1PK (S)  /  GSI1SK (S)   — single-task lookup by task_id
GSI2      : GSI2PK (S)  /  GSI2SK (N)   — per-assignee workload, sorted by due_date
attr_types: {"GSI2SK": "N"}
```

**Future item shape** (PRJ-003):

| Attribute | Value |
|-----------|-------|
| `PK` | `PROJECT#{project_id}` |
| `SK` | `TASK#{task_order:06d}#{task_id}` |
| `GSI1PK` | `TASK#{task_id}` |
| `GSI1SK` | `PROJECT#{project_id}` |
| `GSI2PK` | `ASSIGNEE#{user_sub}` or `ASSIGNEE#unassigned` |
| `GSI2SK` | `end_date` integer (or 0 when unset) |
| `entity_type` | `"crm_task"` |

The zero-padded `task_order` in the sort key (`TASK#{task_order:06d}#{task_id}`) means `ScanIndexForward=True` on the primary index returns tasks in ascending display order without a secondary sort step, up to 999,999 tasks per project.

### 3.3 `crm_pm_members` — Project membership roster (PRJ-007+)

```
Hash key  : PK  (S)
Range key : SK  (S)
GSI1      : GSI1PK (S)  /  GSI1SK (S)   — per-user project membership list
(no numeric GSI sort keys — no attr_types override needed)
```

**Future item shape** (PRJ-007):

| Attribute | Value |
|-----------|-------|
| `PK` | `PROJECT#{project_id}` |
| `SK` | `MEMBER#{user_sub}` |
| `GSI1PK` | `MEMBER#{user_sub}` |
| `GSI1SK` | `PROJECT#{project_id}` |
| `entity_type` | `"crm_project_member"` |

### 3.4 `crm_pm_templates` — Project templates (PRJ-006+)

```
Hash key  : PK  (S)
Range key : SK  (S)
GSI1      : GSI1PK (S)  /  GSI1SK (S)   — template lookup by template_id
(no numeric GSI sort keys)
```

**Future item shape** (PRJ-006):

| Attribute | Value |
|-----------|-------|
| `PK` | `OWNER#{owner_sub}` |
| `SK` | `TEMPLATE#{template_id}` |
| `GSI1PK` | `TEMPLATE#{template_id}` |
| `GSI1SK` | `OWNER#{owner_sub}` |
| `entity_type` | `"crm_project_template"` |

## 4. API / Service Design

PRJ-001 ships **no endpoints and no service functions**. The only code artifact is the stub router file `app/routers/crm_projects.py` containing the guard helper and an empty `APIRouter`. This file is the home for all downstream PRJ route handlers (PRJ-002 through PRJ-012).

### 4.1 Guard helper

```python
# app/routers/crm_projects.py
from fastapi import APIRouter, HTTPException
from app.core.settings import S

router = APIRouter(prefix="/v1/crm/projects", tags=["crm-projects"])

def _require_crm_projects() -> None:
    """Raise HTTP 404 when the CRM Projects feature flag is off.

    Called as the first statement in every route handler in this module and
    all sibling CRM-projects routers (tasks, members, templates, Gantt).
    Keeps flag enforcement co-located with the feature rather than in a
    middleware layer, so it is exercisable in offline hermetic tests without
    spinning up the full FastAPI app.
    """
    if not S.crm_projects_enabled:
        raise HTTPException(status_code=404, detail="crm_projects_not_enabled")
```

### 4.2 Router registration

```python
# app/main.py — append alongside existing router imports
from app.routers.crm_projects import router as crm_projects_router

# In create_app() or the module-level app.include_router() block:
app.include_router(crm_projects_router)
```

No `prefix` override is needed at registration because the router carries its own `prefix="/v1/crm/projects"`.

### 4.3 Settings additions

```python
# app/core/settings.py — append before the final `S = Settings()` line (2772)
# CRM Project Management (PRJ-001)
crm_projects_enabled: bool = (
    os.environ.get("CRM_PROJECTS_ENABLED", "0") not in ("0", "false", "False")
)
crm_pm_projects_table_name: str  = os.environ.get("DDB_CRM_PM_PROJECTS_TABLE",  "crm_pm_projects")
crm_pm_tasks_table_name: str     = os.environ.get("DDB_CRM_PM_TASKS_TABLE",     "crm_pm_tasks")
crm_pm_members_table_name: str   = os.environ.get("DDB_CRM_PM_MEMBERS_TABLE",   "crm_pm_members")
crm_pm_templates_table_name: str = os.environ.get("DDB_CRM_PM_TEMPLATES_TABLE", "crm_pm_templates")
```

The flag expression `not in ("0", "false", "False")` matches the `cart_reminders_enabled` style exactly (`app/core/settings.py:821`), avoiding the `.lower()` variant used by `returns_rma_enabled` to keep consistency within the same codebase. Because the default env value is `"0"`, `crm_projects_enabled` evaluates to `False` on every deployment unless the operator explicitly sets `CRM_PROJECTS_ENABLED=1` (or `true`).

### 4.4 Table handle additions

```python
# app/core/tables.py — in the Tables dataclass body, after existing `returns: Any` field
crm_pm_projects:   Any
crm_pm_tasks:      Any
crm_pm_members:    Any
crm_pm_templates:  Any

# In the T = Tables(...) constructor, after returns=_safe_table(S.returns_table_name)
crm_pm_projects   = _safe_table(S.crm_pm_projects_table_name),
crm_pm_tasks      = _safe_table(S.crm_pm_tasks_table_name),
crm_pm_members    = _safe_table(S.crm_pm_members_table_name),
crm_pm_templates  = _safe_table(S.crm_pm_templates_table_name),
```

Because `Tables` is a frozen dataclass, the four new fields have `Any` type annotations (consistent with every existing field; the dataclass field block spans `app/core/tables.py:70–319`, and the `T = Tables(...)` constructor keyword block spans 322–571). The `_safe_table` wrapper ensures float-to-Decimal coercion on writes, identical to all other table handles.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off behavior

When `CRM_PROJECTS_ENABLED` is unset or set to `"0"` / `"false"` / `"False"`:

- `S.crm_projects_enabled` is `False`.
- Every call to `_require_crm_projects()` raises `HTTPException(status_code=404, detail="crm_projects_not_enabled")`.
- The four new DynamoDB tables exist in DynamoDB Local (they are always created by `scripts/local-ddb-init.py`), but no application code reads from or writes to them.
- `T.crm_pm_projects`, `T.crm_pm_tasks`, `T.crm_pm_members`, and `T.crm_pm_templates` are live `_FloatSafeTable` wrappers — they do not fail on import even when the flag is off. They simply go unused.
- The existing `app/routers/projects.py` router (imported `app/main.py:81`, registered `app/main.py:682`) and `app/services/projects_store.py` are byte-for-byte unchanged.

### 5.2 Table name collision avoidance

The four default table names (`crm_pm_projects`, `crm_pm_tasks`, `crm_pm_members`, `crm_pm_templates`) do not collide with any existing name in `scripts/local-ddb-init.py`. The existing file-grouping table is named `projects` (line 270). The `project_sprints` and `project_reports` tables wired at `app/core/tables.py:536–537` are analytics/agent tables unrelated to CRM. No rename is needed.

### 5.3 `_table_defs()` insertion point

The four `TableDef` calls are inserted into `_table_defs()` in `scripts/local-ddb-init.py` immediately **after** the existing `projects` `TableDef` closing `)` at line 277. This keeps the CRM family co-located in the file and avoids disrupting the ordering of existing table creation calls (DynamoDB Local creates tables in definition order; ordering is not load-bearing but eases code review).

### 5.4 `T` singleton field ordering

The four new fields are appended at the tail of both the `Tables` dataclass body and the `T = Tables(...)` constructor call, after `returns`. Appending to the end ensures no existing positional argument shifts (the constructor uses keyword arguments, so ordering does not matter functionally, but keeping changes minimal reduces merge conflicts with sibling branches).

### 5.5 Router file and import

`app/routers/crm_projects.py` is created with only the `APIRouter` stub and `_require_crm_projects()`. The router is registered unconditionally in `app/main.py` (same as all other feature routers). The guard is invoked at handler call time, not at import or registration time, so import of the module never raises even when the flag is off.

### 5.6 Stack restart behavior

`scripts/local-ddb-init.py` calls `create_table` inside a `try/except ClientError` that swallows `ResourceInUseException` (already-exists). After the first clean creation the four tables persist across backend-only restarts. A `just restart` (which wipes DynamoDB Local data) will recreate them cleanly.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

There is no service logic in this ticket — only settings, table definitions, table handles, and a guard helper. All four of these are identical in dev and prod:

- `Settings` reads from `os.environ` in both environments; the dataclass has no `dev_mode` branch.
- `_safe_table(name)` wraps `ddb.Table(name)` — `ddb` is `boto3.resource("dynamodb", ...)` wired to the local endpoint in dev and to real AWS in prod via `app/core/aws.py`. No `dev_mode` branch.
- `scripts/local-ddb-init.py` is a dev tool only; prod table creation goes through Terraform/CloudFormation/CDK with the same attribute definitions.
- `_require_crm_projects()` evaluates `S.crm_projects_enabled` — same code, same env-var source in both environments.

No `if S.dev_mode:` branches are introduced. SECOPS-007 compliance is trivially satisfied by the absence of any service logic.

### Idempotency

`scripts/local-ddb-init.py` already wraps every `create_table` call in a `try/except ClientError` that suppresses `ResourceInUseException`. The four new tables follow the same pattern. Running `local-ddb-init.py` repeatedly (or after a backend-only restart that does not wipe DynamoDB Local data) is safe and produces no duplicate tables.

### Security

This ticket introduces no auth surface. The guard helper raises `404` (not `403`) to avoid leaking feature existence to unauthenticated probers — a convention followed by other feature flags in the codebase (e.g. `returns_rma_enabled` gating returns endpoints with 404). Four empty DynamoDB tables with no data have no security impact; they are created with `BillingMode="PAY_PER_REQUEST"` (the platform standard) and no data is readable without knowing a valid `PK` value.

## 8. Backward Compatibility & Migration

### Zero impact when flag is off

With `CRM_PROJECTS_ENABLED=0` (the shipped default):

- No existing API response changes.
- No existing DynamoDB read/write path changes.
- The `app/routers/projects.py` file-grouping router is untouched.
- The `ProjectModel` at `app/models.py:1796` is untouched.
- The `T.projects` handle at `app/core/tables.py:353` is untouched.
- The four new `T.*` handles are live wrappers around empty tables — they add ~4 `ddb.Table(name)` constructor calls at process startup, which is negligible.

### Production deployment sequence

Because the flag defaults to `"0"`, the correct production deployment sequence is:

1. Deploy backend code (settings + table handles + guard + empty router).
2. Run `local-ddb-init.py` equivalent (or Terraform) to create the four tables in prod DynamoDB.
3. Enable the flag (`CRM_PROJECTS_ENABLED=1`) only after PRJ-002+ service code has been deployed and verified.

Steps 1 and 2 are safe to deploy to production before PRJ-002 code exists, because no endpoints are exposed until the flag is on.

### No data migration

This ticket creates four empty tables. There is no existing CRM project data to migrate. No backfill, no schema evolution, and no GSI `UpdateTable` is needed.

## 10. Open Questions / Assumptions

1. **`crm_pm_projects` GSI2 query cardinality**: `GSI2PK` will be `"STATUS#{status}"` with five possible statuses (`draft`, `in_review`, `underway`, `completed`, `deferred`). On a large multi-tenant deployment, querying `STATUS#underway` could fan out across all owners. PRJ-002 will need to decide whether the status GSI is scoped per-owner (e.g. `GSI2PK = "STATUS#{status}#OWNER#{owner_sub}"`) or whether an admin-only status list is acceptable at the cost of wider scans. **Assumption here**: the five-status partition is acceptable for initial release; a composite key can be introduced in a later ticket if GSI hot-partition issues arise.

2. **Table retention policy**: The four new tables have no TTL column defined at this stage. Long-term retention and archival (e.g. soft-delete + purge of completed projects older than N days) is deferred to a future operations ticket.

3. **Multi-tenancy / `owner` scoping**: All four tables scope data under `OWNER#{user_sub}` or `PROJECT#{project_id}` partition keys. Cross-user admin access to CRM project data (e.g. a ROOT admin listing all projects) is not addressed in PRJ-001 and will need a system-wide scan path or a separate `ADMIN#` GSI in PRJ-002+.

4. **Cursor signing secret**: The four tables will use paginated list queries in downstream tickets. `encode_cursor` / `decode_cursor` from `app/core/cursor.py:94,103` use HMAC-signed v2 cursors (keyed by `CURSOR_SIGNING_SECRET` env var). No new secret is needed; this is assumed to be set in prod already.

5. **`_safe_table` and `T` constructor syntax**: The `T = Tables(...)` constructor at `app/core/tables.py:321` is a multi-line keyword-argument call. The implementer must verify the exact line of the closing `)` before appending the four new entries to avoid a `SyntaxError`. At time of verification, the closing `)` is at line 572 (one line after `returns=_safe_table(S.returns_table_name)` at line 571).
