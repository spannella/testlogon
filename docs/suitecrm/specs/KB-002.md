# KB-002 — Article status lifecycle — Draft / Published / Expired transitions

**Type:** Feature  **Priority:** P1  **Estimate:** 1 day  
**Ticket source:** `docs/suitecrm/CRM_KNOWLEDGE_BASE_TICKETS.md`, section "KB-002"

---

## 1. Summary & Goal

KB-002 delivers the three-state article lifecycle (`draft → published → expired`) for the Knowledge Base module introduced by KB-001 and CAS-015. When an article is first created it lands in `draft`; an admin explicitly publishes it, making it visible on the public portal; an admin (or the background expiry checker) expires it, removing it from public visibility without deleting the record.

The specific deliverables are:

- Three new transition methods on `KbArticleService` (`publish_article`, `expire_article`, `unpublish_to_draft`), each with validated state-machine guards and `audit_event` emission.
- An `expires_at` field on the article item so time-limited articles expire automatically.
- A background loop (`run_kb_expiry_checker_loop` / `start_kb_expiry_checker_task`) that polls the `ByStatus` GSI every 3 600 seconds, finds published articles whose `expires_at` has passed, and calls `expire_article` for each.
- Three new admin-only router endpoints exposing those transitions.
- A `KbArticleStateError` exception class for invalid transitions.

All behaviour is additive and gated on `S.knowledge_base_enabled` (introduced by KB-001, default `False`). With the flag off the platform is byte-for-byte identical to its current state: no new routes exist, no workers start, and no existing file is modified.

### 2.8 Status values and `ByStatus` GSI query

The `ByStatus` GSI on `crm_kb_articles` has PK=`status` (String) and SK=`published_at` (Number). A query for all published articles uses:

```python

    IndexName="ByStatus",
    KeyConditionExpression=Key("status").eq("published"),

```

With `ScanIndexForward=True` this returns articles sorted by `published_at` ascending. The expiry checker filters client-side on `expires_at <= now_ts()` after fetching all published articles. For tables with large numbers of published articles a two-stage approach (filter `expires_at` server-side via `FilterExpression`) is preferable; see Section 5.3 below.

## 4. API / Service Design

### 4.1 `app/services/kb_articles.py` — service additions

All methods below are added to the existing `KbArticleService` class.

**Exception class** (defined at module level, before `KbArticleService`):

```python
class KbArticleStateError(Exception):
    """Raised when a lifecycle transition is invalid for the article's current status."""
    def __init__(self, current_status: str, attempted: str) -> None:
        super().__init__(f"Cannot transition from '{current_status}' to '{attempted}'")
        self.current_status = current_status
        self.attempted = attempted
```

**`publish_article(article_id: str, admin_sub: str) -> dict`**

1. Calls `self.get_article(article_id)` — raises 404 if missing.
2. Reads `current_status = item["status"]`. If `current_status != "draft"` raises `KbArticleStateError(current_status, "published")`.
3. Calls `T.kb_articles.update_item` with:
   - `UpdateExpression = "SET #status = :published, published_at = :ts REMOVE expired_at, expiry_reason"`
   - `ConditionExpression = "#status = :draft"`
   - `ExpressionAttributeNames = {"#status": "status"}`
   - `ExpressionAttributeValues = {":published": "published", ":draft": "draft", ":ts": now_ts()}`
4. Catches `ClientError` where `Code == "ConditionalCheckFailedException"` — raises `KbArticleStateError` (concurrent modification safety net).
5. Calls `audit_event("kb.article.published", admin_sub, article_id=article_id)`.
6. Returns the updated item via `self.get_article(article_id)`.

**`expire_article(article_id: str, admin_sub: str, *, reason: str = "") -> dict`**

1. Calls `self.get_article(article_id)`.
2. Reads `current_status`. If `current_status != "published"` raises `KbArticleStateError(current_status, "expired")`.
3. Calls `T.kb_articles.update_item` with:
   - `UpdateExpression = "SET #status = :expired, expired_at = :ts" + (", expiry_reason = :reason" if reason else "")`
   - `ConditionExpression = "#status = :published"`
   - `ExpressionAttributeValues` include `":expired": "expired"`, `":published": "published"`, `":ts": now_ts()`, and `":reason": reason` if provided.
4. Catches `ConditionalCheckFailedException` → raises `KbArticleStateError`.
5. Calls `audit_event("kb.article.expired", admin_sub, article_id=article_id, reason=reason)`.
6. Returns updated item.

**`unpublish_to_draft(article_id: str, admin_sub: str) -> dict`**

1. Calls `self.get_article(article_id)`.
2. Reads `current_status`. If `current_status != "published"` raises `KbArticleStateError(current_status, "draft")`.
3. Calls `T.kb_articles.update_item` with:
   - `UpdateExpression = "SET #status = :draft REMOVE published_at"`
   - `ConditionExpression = "#status = :published"`
4. Calls `audit_event("kb.article.unpublished", admin_sub, article_id=article_id)`.
5. Returns updated item.

**Signature summary:**

```python
def publish_article(self, article_id: str, admin_sub: str) -> dict: ...
def expire_article(self, article_id: str, admin_sub: str, *, reason: str = "") -> dict: ...
def unpublish_to_draft(self, article_id: str, admin_sub: str) -> dict: ...
```

### 4.2 Background expiry checker — `app/services/kb_articles.py`

```python
async def run_kb_expiry_checker_loop() -> None:
    if not S.knowledge_base_enabled:
        logger.info("KB expiry checker disabled (flag off)")
        return
    interval = max(60, S.kb_expiry_checker_interval_seconds)  # default 3600
    logger.info("KB expiry checker started (interval=%ds)", interval)
    while True:
        try:
            _run_kb_expiry_check_once()
        except Exception:
            logger.exception("KB expiry checker error")
        await asyncio.sleep(interval)

def _run_kb_expiry_check_once() -> int:
    """Query published articles with expires_at <= now; expire each. Returns count."""
    ts = now_ts()
    svc = KbArticleService()
    expired_count = 0
    last_key = None
    while True:
        kwargs: dict = {
            "IndexName": "ByStatus",
            "KeyConditionExpression": Key("status").eq("published"),
            "FilterExpression": Attr("expires_at").lte(ts) & Attr("expires_at").exists(),
        }
        if last_key:
            kwargs["ExclusiveStartKey"] = last_key
        resp = T.kb_articles.query(**kwargs)
        for item in resp.get("Items", []):
            try:
                svc.expire_article(item["article_id"], "system_kb_expiry")
                expired_count += 1
            except KbArticleStateError:
                pass  # already transitioned by concurrent admin action — harmless
            except Exception:
                logger.exception("KB expiry: failed to expire article %s", item.get("article_id"))
        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break
    if expired_count:
        logger.info("KB expiry checker: expired %d article(s)", expired_count)
    return expired_count

def start_kb_expiry_checker_task() -> None:
    if not S.knowledge_base_enabled:
        return
    try:
        asyncio.get_event_loop().create_task(run_kb_expiry_checker_loop())
    except RuntimeError:
        asyncio.ensure_future(run_kb_expiry_checker_loop())
```

The `FilterExpression` uses `Attr("expires_at").exists()` to exclude articles that have no `expires_at` set (i.e. articles that never auto-expire). This avoids scanning articles that should remain published indefinitely. Pagination via `LastEvaluatedKey` is mandatory — DynamoDB applies `FilterExpression` after fetching up to 1 MB, so a single query call will silently miss items on a busy table (CLAUDE.md gotcha).

## 5. Detailed Behavior & Edge Cases

### 5.1 Valid and invalid transitions

| From | To | Method | Allowed |
|---|---|---|---|
| `draft` | `published` | `publish_article` | Yes |
| `published` | `expired` | `expire_article` | Yes |
| `published` | `draft` | `unpublish_to_draft` | Yes |
| `draft` | `expired` | — | No — raises `KbArticleStateError` |
| `expired` | `published` | — | No |
| `expired` | `draft` | — | No |
| `draft` | `draft` | — | No-op / `KbArticleStateError` |

There is intentionally no `expired → draft` or `expired → published` re-activation path. If an expired article must be re-published, the admin must create a new article or the platform team must directly update the DDB item. This keeps the state machine simple and the audit trail clean.

### 5.2 `expires_at` semantics

`expires_at` is an optional integer Unix timestamp set by the admin on `create_article` or `update_article` (these endpoints are CAS-015 scope; KB-002 documents the field contract). When `expires_at` is `None` or not present, the article never auto-expires. When `expires_at <= now_ts()` at the time the expiry checker runs, `expire_article` is called. The checker passes `reason="auto_expiry"` (a well-known sentinel) so the `expiry_reason` field on the item is populated and the audit event payload is self-describing.

### 5.3 Pagination in the expiry checker

The DynamoDB query on `ByStatus` with `FilterExpression` fetches up to 1 MB before filtering. For the `"published"` status bucket on a platform with thousands of published articles, a single `query()` call will silently miss items beyond the first page. `_run_kb_expiry_check_once` loops via `LastEvaluatedKey` until exhausted (see Section 4.2). This matches the guidance in CLAUDE.md: "DDB FilterExpression doesn't reduce page size."

### 5.4 Concurrent transition safety

If two admin users simultaneously call `POST .../publish` for the same article, both read `status=draft`, both attempt the `update_item` with `ConditionExpression="#status = :draft"`. The second write will hit `ConditionalCheckFailedException` because the first write already set `status=published`. The handler converts this to a `KbArticleStateError`, which the router maps to HTTP 409. This is correct behavior — the article is already published, so no data is lost.

The expiry checker uses the same conditional guard in `expire_article`, which means that if an admin manually expires an article at the same time the checker runs, one of the two will get a harmless `KbArticleStateError` that is swallowed by the `except KbArticleStateError: pass` clause in `_run_kb_expiry_check_once`.

### 5.5 Expiry checker and `expires_at` in the future

The `FilterExpression` condition is `Attr("expires_at").lte(ts) & Attr("expires_at").exists()`. An article with `expires_at = now_ts() + 7200` passes the `exists()` check but fails the `lte(ts)` check, so it is not expired until the checker's next tick at or after that timestamp. The maximum latency between the `expires_at` timestamp and actual expiry is equal to the `kb_expiry_checker_interval_seconds` setting (default 3 600 s = 1 hour). This is acceptable for a KB article lifecycle.

### 5.6 Public visibility contract

The CAS-015 `GET /public/kb/articles` and `GET /public/kb/articles/{article_id}` endpoints only return articles where `status == "published"`. After `expire_article` transitions `status` to `"expired"`, the article will no longer appear in the public list on the next query and the direct-GET will return 404. No caching invalidation is required at this layer because the public endpoints query DynamoDB directly.

### 5.7 `publish_article` clears `expired_at` and `expiry_reason`

The `UpdateExpression` for `publish_article` includes `REMOVE expired_at, expiry_reason`. This ensures that if an article is somehow in an `expired` state and an admin attempts to re-publish via a direct DDB edit (not via the lifecycle API), the stale `expired_at` does not linger. However, since the state machine does not support `expired → published`, this `REMOVE` clause is a belt-and-suspenders measure and will only execute on the `draft → published` transition in practice.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

There is no `dev_mode` branch in any KB-002 code path. The DynamoDB `update_item` calls go through `T.kb_articles`, which resolves to either DynamoDB Local (dev) or production DynamoDB depending on `DDB_ENDPOINT_URL`. The `audit_event` call writes to `T.alerts` regardless of environment; in dev this is DynamoDB Local, in prod it is the production alerts table. The `send_alert_email` path in `app/services/alerts.py:459` already handles dev vs prod (dev writes to the file log, prod sends via SES) but KB-002 does not invoke `send_alert_email` — only `audit_event`.

### 7.2 Idempotency

- Calling `publish_article` on an already-published article raises `KbArticleStateError` (HTTP 409) because the `ConditionExpression` check fails.
- Calling `expire_article` on an already-expired article raises `KbArticleStateError` (HTTP 409).
- The expiry checker calls `expire_article` inside `try/except KbArticleStateError: pass`, so the checker is idempotent across ticks.

### 7.3 Authentication and authorisation

- All three transition endpoints require `require_ui_session` (cookie auth with CSRF) and an authenticated user with `Role.ADMIN` or `Role.ROOT` (`role_allows_admin_features` at `app/auth/roles.py:60`).
- The public `GET /public/kb/articles/{id}` endpoint (CAS-015) never returns `draft` or `expired` articles — only `published` ones. No auth is required to read published articles.
- Unauthenticated or user-role callers calling `POST .../publish` receive HTTP 403.

### 7.4 Sensitive data

No sensitive data (PII, payment info, KMS-encrypted fields) is touched by KB-002. The `expiry_reason` field is an admin-supplied free-text label stored in plaintext in DynamoDB.

## 8. Backward Compatibility & Migration

### 8.1 Existing articles

The `crm_kb_articles` table (created by CAS-001) may already contain rows from integration testing. All existing `ARTICLE#` rows have `status="draft"` (as set by `create_article` in CAS-015). The KB-002 lifecycle methods are additive: no existing row is modified, no existing field is removed. Articles without `expires_at` behave identically — the expiry checker's `Attr("expires_at").exists()` filter skips them.

### 8.2 `published_at` attribute type

CAS-001 declares `published_at` as `N` in the `ByStatus` GSI `attr_types`. The KB-002 `publish_article` method sets `published_at = now_ts()` (an integer), which is consistent with the declared type. Writing a string to a numeric GSI sort key would cause `ValidationException` at query time (CLAUDE.md DynamoDB gotcha). The `update_item` `ExpressionAttributeValues` must pass `now_ts()` as a Python `int`, not a string.

### 8.3 `just restart` compatibility

`just restart` wipes and re-creates all DynamoDB tables via `scripts/local-ddb-init.py`. KB-002 adds no new tables and no new GSIs, so no `local-ddb-init.py` change is required beyond what KB-001 already specifies. The `kb_expiry_checker_interval_seconds` setting has no DynamoDB impact.

## 10. Open Questions / Assumptions

1. **Re-activation path (expired → published):** The current design intentionally omits this transition. If the product team requires it (e.g. for seasonal articles that are re-published annually), a `reactivate_article` method can be added as a subsequent ticket. The state machine deliberately excludes this for now to keep the audit trail unambiguous.

2. **Expiry notification email:** The ticket source does not require an email to admins when an article auto-expires. If this is needed (e.g. "Article X expired automatically") it should be a separate ticket that wires `send_alert_email` into `expire_article` when `admin_sub == "system_kb_expiry"`. KB-002 does not include this.

3. **`expires_at` set by `create_article` or `update_article`:** Both CAS-015 methods must accept and persist `expires_at` as an optional integer field. This spec assumes CAS-015 already stores it as-is on the META row. If CAS-015 does not persist `expires_at`, KB-002 must add the field to the `update_article` call path. This should be confirmed when CAS-015 is implemented.

4. **Expiry checker interval in tests:** The default 3 600 s interval means the background loop is not exercised by unit tests. `_run_kb_expiry_check_once` is the unit-testable function; `run_kb_expiry_checker_loop` is tested only indirectly via startup registration assertions (pattern: `tests/test_compute_billing_timer_gap0228.py`).

5. **`ByStatus` GSI `published_at` sort key and `expires_at` filter:** Since `expires_at` is not a GSI key, the query fetches all published articles and filters in memory or via `FilterExpression`. If the platform ever has more than tens of thousands of published articles, a dedicated `ByExpiry` GSI (PK=`status`, SK=`expires_at`) would be more efficient. This is a future optimization; at current scale the `FilterExpression` approach is acceptable.
