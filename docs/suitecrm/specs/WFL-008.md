**Type:** Feature | **Priority:** P2 | **Estimate:** 2d
**Depends on:** WFL-001, WFL-002, WFL-003, WFL-006, WFL-007
**Unblocks:** WFL-009 (admin UI — exposes drip-sequence CRUD endpoints)

## 1. Summary & Goal

This ticket extends `app/services/workflow_action_executor.py` (introduced by WFL-006) with the `drip_sequence` action type, and adds the companion service module `app/services/workflow_drip_sequences.py` that owns the sequence definition CRUD and enrolment state.

A drip sequence is a configurable, multi-stage campaign that fires a series of templated emails against a single record at specified time offsets. When the workflow action executor encounters a `drip_sequence` action step, it:

1. Creates or retrieves an enrolment row that tracks the record's position in the sequence.
2. Schedules stage 1 as a new `crm_workflow_drip_stage` action in `T.scheduled_actions`.

Each stage executor sends its email (reusing the `_send_email_for_action` shared helper introduced by WFL-007), advances the enrolment pointer, and schedules the next stage until the sequence is complete or the enrolment is stopped.

The design generalises the cart-abandonment drip pattern (`app/services/cart_reminders.py` — `_get_stages` / `_send_stage_reminder` / `process_abandoned_carts`) into the user-configurable workflow rule engine. All sequence definitions live in the existing `T.crm_workflow_rules` table under dedicated `DRIP#` partition keys — no new DynamoDB table is required. Enrolment state is stored in the same table under `ENROL#` partition keys.

With `CRM_WORKFLOW_ENABLED=0` (the default), no drip-sequence rows are ever enqueued and the platform is byte-for-byte unchanged.

### 3.1 Sequence definition rows (reuse `T.crm_workflow_rules`)

| Attribute | Type | Notes |
|---|---|---|
| `pk` | S | `DRIP#{sequence_id}` |
| `sk` | S | `META` |
| `sequence_id` | S | UUID, `drip_` prefix, e.g. `drip_a1b2c3...` |
| `name` | S | Human-readable name |
| `description` | S | Optional |
| `stages` | L | Ordered list — see stage schema below |
| `created_by` | S | `user_sub` of admin who created it |
| `created_at` | N | Unix timestamp |
| `updated_at` | N | Unix timestamp |

**Stage schema** (each element of `stages`):

| Field | Type | Notes |
|---|---|---|
| `stage_number` | N | 1-based, must be unique within a sequence |
| `delay_hours` | N | Hours after enrolment (stage 1) or after previous stage send (stages 2+) |

**No new GSI is required** for sequence definitions — admin list operations do a scan of PK prefix `DRIP#` across the table (the table is small; rules are bounded by `S.crm_workflow_max_rules_per_module`). If list performance becomes an issue post-launch, a GSI can be added without a migration.

```python
async def _execute_drip_sequence(
    config: dict,
    *,
    module: str,
    record_id: str,
) -> dict:
    """Enrol a record in a drip sequence and schedule stage 1."""
    if not S.crm_workflow_enabled:
        return {"status": "skipped", "reason": "flag_off"}
    sequence_id = config.get("sequence_id", "")
    seq = workflow_drip_sequences.get_sequence(sequence_id)
    if not seq:
        logger.warning("drip_sequence: sequence_id=%s not found", sequence_id)
        return {"status": "skipped", "reason": "sequence_not_found"}
    stages = seq.get("stages") or []
    if not stages:
        return {"status": "skipped", "reason": "sequence_has_no_stages"}
    now = now_ts()
    enrolment = workflow_drip_sequences.enrol_record(
        sequence_id, module, record_id, enrolled_at=now
    )
    if enrolment.get("current_stage", 0) > 0:
        # Already enrolled and progressing — idempotent, do not re-schedule
        return {"status": "already_enrolled", "sequence_id": sequence_id}
    stage = stages[0]  # sorted by stage_number, 1-based
    _schedule_drip_stage(seq, stage, module=module, record_id=record_id, enrolled_at=now)
    audit_event(
        "crm_workflow.drip_enrolled", "system",
        sequence_id=sequence_id, module=module, record_id=record_id,
    )
    return {"status": "enrolled", "sequence_id": sequence_id, "stage_scheduled": stage["stage_number"]}
```

**`_schedule_drip_stage` (internal helper)**:

```python
def _schedule_drip_stage(
    seq: dict,
    stage: dict,
    *,
    module: str,
    record_id: str,
    enrolled_at: int,
) -> None:
    """Write one crm_workflow_drip_stage row directly to T.scheduled_actions.

    Bypasses create_action() min-lead-time guard (as per WFL-004 pattern)
    by calling T.scheduled_actions.put_item directly. Uses user_sub="system".
    scheduled_at = enrolled_at + stage["delay_hours"] * 3600 (stage 1)
    or last_stage_sent_at + stage["delay_hours"] * 3600 (stages 2+).
    """
    action_id = "sa_" + uuid.uuid4().hex
    scheduled_at = enrolled_at + int(stage.get("delay_hours", 0)) * 3600
    now = now_ts()
    item = {
        "pk": "USER#system",
        "sk": f"ACTION#{scheduled_at}#{action_id}",
        "action_id": action_id,
        "user_sub": "system",
        "action_type": "crm_workflow_drip_stage",
        "status": "pending",
        "scheduled_at": scheduled_at,
        "created_at": now,
        "updated_at": now,
        "title": f"Drip {seq['name']} stage {stage['stage_number']}",
        "payload": {
            "sequence_id": seq["sequence_id"],
            "stage_number": stage["stage_number"],
            "module": module,
            "record_id": record_id,
            "template_id": stage["template_id"],
            "to_field": stage["to_field"],
            "enrolled_at": enrolled_at,
        },
        "GSI_DUE_PK": "DUE",
        "GSI_DUE_SK": scheduled_at,
        "GSI_TYPE_PK": f"USER#system#TYPE#crm_workflow_drip_stage",
        "GSI_TYPE_SK": scheduled_at,
        "ttl_epoch": scheduled_at + S.scheduled_actions_ttl_days * 86400,
        "retry_count": 0,
        "max_retries": S.scheduled_actions_max_retries,
        "reminder_sent": False,
        "notify_before_seconds": 0,
    }
    T.scheduled_actions.put_item(Item=item)
```

### 4.3 New executor: `execute_drip_stage_action` (in `workflow_action_executor.py`)

Registered into `_EXECUTORS` in `unified_scheduler.py` as `"crm_workflow_drip_stage"`.

```python
async def execute_drip_stage_action(user_sub: str, payload: dict) -> None:
    sequence_id = payload["sequence_id"]
    stage_number = int(payload["stage_number"])
    module = payload["module"]
    record_id = payload["record_id"]
    template_id = payload["template_id"]
    to_field = payload["to_field"]
    enrolled_at = int(payload.get("enrolled_at", 0))

    # 1. Guard: check enrolment is active
    enrolment = workflow_drip_sequences.get_enrolment(sequence_id, module, record_id)
    if not enrolment or enrolment.get("stopped"):
        logger.info("drip_stage: skipping stopped/missing enrolment seq=%s record=%s", sequence_id, record_id)
        return

    # 2. Fetch the live record so template variables are up to date
    record = _fetch_record(module, record_id)
    if record is None:
        logger.warning("drip_stage: record not found module=%s record_id=%s", module, record_id)
        return

    # 3. Send email using shared WFL-007 helper
    result = _send_email_for_action(
        template_id=template_id,
        to_field=to_field,
        record=record,
        module=module,
        extra_vars={},
    )
    if result.get("status") == "skipped":
        logger.warning("drip_stage: email skipped seq=%s stage=%d reason=%s",
                       sequence_id, stage_number, result.get("reason"))

    now = now_ts()
    audit_event(
        "crm_workflow.drip_stage_sent", "system",
        sequence_id=sequence_id, stage_number=stage_number,
        module=module, record_id=record_id, result=result.get("status"),
    )

    # 4. Advance enrolment pointer
    workflow_drip_sequences.advance_enrolment(
        sequence_id, module, record_id, stage_number=stage_number, now=now
    )

    # 5. Schedule next stage or complete
    seq = workflow_drip_sequences.get_sequence(sequence_id)
    if not seq:
        # Sequence deleted after enrolment — mark complete and exit
        workflow_drip_sequences.complete_enrolment(sequence_id, module, record_id, now=now)
        return

    stages = sorted(seq.get("stages") or [], key=lambda s: int(s["stage_number"]))
    next_stages = [s for s in stages if int(s["stage_number"]) > stage_number]
    if next_stages:
        next_stage = next_stages[0]
        _schedule_drip_stage(seq, next_stage, module=module, record_id=record_id, enrolled_at=now)
    else:
        workflow_drip_sequences.complete_enrolment(sequence_id, module, record_id, now=now)
        audit_event(
            "crm_workflow.drip_completed", "system",
            sequence_id=sequence_id, module=module, record_id=record_id,
        )
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent enrolment (duplicate fire guard)

`enrol_record` uses a DDB conditional put (`attribute_not_exists(pk)`) on the enrolment row. If the WFL-004/005 scheduler fires the same rule against the same record twice in the same poll window (e.g., due to a retry or a bug), the second `enrol_record` call fails the condition, the existing enrolment is returned unchanged, and `_execute_drip_sequence` detects `current_stage > 0` or `enrolled_at` matches and returns `"already_enrolled"` without scheduling a duplicate stage. This is the same one-time-use conditional-put pattern used by cart recovery token consumption at `app/services/cart_reminders.py:201–211`.

### 5.2 Stopped flag — stage executor guard

Before sending any email, `execute_drip_stage_action` calls `get_enrolment` and checks `stopped`. If the flag is set, the executor returns immediately without sending or advancing the stage pointer. Any already-pending stage rows in `T.scheduled_actions` will similarly be claimed by the scheduler and silently dropped by the guard — they are not cancelled from the queue, but they become no-ops.

### 5.3 Sequence deleted after enrolment

If an admin deletes a sequence definition (`delete_sequence`) while records are still enrolled, `execute_drip_stage_action` calls `get_sequence` after a send and receives `None`. It marks the enrolment `completed=True` and exits — the remaining pending stage rows in `T.scheduled_actions` are claimed and silently dropped via the same path (the `get_sequence` guard fires at the start of each stage).

### 5.4 Record deleted between enrolment and stage fire

`_fetch_record(module, record_id)` returns `None` if the record no longer exists. The stage executor logs a warning and returns without sending or advancing the pointer. Subsequent stages remain pending but will hit the same guard. This is safe — no email is sent to a non-existent record.

### 5.5 Template not found at send time

`_send_email_for_action` (WFL-007 helper) returns `{"status": "skipped", "reason": "template_not_found"}` when the template no longer exists. The drip stage executor logs the skip but still advances `current_stage` and schedules the next stage. The sequence completes normally; the missing stage is logged as `skipped` in the audit trail. This is consistent with WFL-007's guard on the `send_email` action type.

### 5.6 Zero-delay stage 1

`delay_hours=0` is valid. `scheduled_at = enrolled_at + 0` means the stage is immediately due when the unified scheduler next polls (within `S.unified_scheduler_poll_interval_seconds`, default 15 s). Stage 1 is always written via `put_item` directly (bypassing the 300-second min-lead-time guard in `create_action`), so zero-delay sequences fire near-instantly.

### 5.7 Re-enrolment after completion

`completed=True` on the enrolment row does NOT prevent a new enrolment. If the same workflow rule fires against the same record again (e.g., on a second on-save event), `enrol_record` uses a conditional put that will fail because the row already exists. `_execute_drip_sequence` detects `current_stage > 0` (or `completed=True`) and returns `"already_enrolled"`. If the business requirement is to re-enrol completed records, a calling path must first call `stop_drip_sequence` (which sets `stopped=True`) and then delete the enrolment row before re-enrolling — but this is out of scope for this ticket.

### 5.8 Stage-number gaps in sequence definition

`create_sequence` validates that `stage_number` values in the supplied `stages` list are contiguous starting from 1 (i.e., [1, 2, 3, ...] with no gaps). A gap would cause `next_stages` in the stage executor to skip intermediate stage numbers, potentially sending emails out of order. The validator raises `ValueError("stage_number values must be contiguous starting from 1")` if violated.

### 5.9 `delay_hours` for stages 2+

The ticket description says "delay from previous stage send". `_schedule_drip_stage` for stages 2+ receives `enrolled_at=now` (the `now` timestamp at the moment the previous stage fires), so each inter-stage gap is `delay_hours` relative to when the preceding stage was actually sent — not relative to enrolment. This matches the cart reminders pattern (`reference_ts = last_reminder_at` for stage > 1 at `app/services/cart_reminders.py:306`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity**: All code paths use `T.scheduled_actions`, `T.crm_workflow_rules`, and `T.admin_messaging_templates` — the same DynamoDB tables in both environments. `send_alert_email` (`app/services/alerts.py:459`) already handles the dev/prod split internally: in dev mode it writes to the dev email log file; in prod it calls SES. No `if dev_mode` branch is added in `workflow_drip_sequences.py` or the executor extensions.

**Idempotency**: The conditional put in `enrol_record` is the primary idempotency guard. The unified scheduler's `claim_action` (`app/services/scheduled_actions.py:377`) performs an atomic status transition `pending → executing` via a DDB conditional update, so concurrent scheduler workers cannot double-execute the same stage. `mark_action_completed` writes `status=completed` so a replayed action is a no-op.

**Security**: Drip sequence definitions and enrolment rows live in `T.crm_workflow_rules` — the same table as rule definitions introduced by WFL-002. The existing `require_admin_or_root_csrf` guard (to be added in WFL-009) will protect all CRUD endpoints. Enrolment rows are internal system data, never exposed directly to end-users. The `to_field` value in a stage definition is resolved from the record dict at send time; it does not accept arbitrary Python attribute access — only a top-level dict key lookup. Template rendering uses `bot_template.resolve_variables` (`app/services/bot_template.py:215`), which is a regex-based `{variable}` substitution with no `eval` path, safe from injection.

**No money-out path**: Drip sequences only send emails; no payment or refund primitives are involved.

## 10. Open Questions / Assumptions

1. **Re-enrolment policy**: The current design treats completed enrolments as permanent — a record cannot be re-enrolled without first deleting the enrolment row. If the product team requires automatic re-enrolment (e.g., a contact can restart a nurture sequence when they become a lead again), a `allow_reenrolment: bool` flag on the sequence definition would replace the conditional-put guard with an upsert. Assumed: re-enrolment is not needed at this tier.

2. **Per-sequence enrolment cap**: There is no cap on how many records can be enrolled in a single sequence simultaneously. On a large platform with many contacts matching an on-save rule, thousands of drip enrolments could be created in a single scheduler tick. A follow-up could add `crm_workflow_max_drip_enrolments_per_sequence` as a safety valve. Assumed: acceptable at P2 scope.

3. **Stage email skip vs. abort**: Currently a `template_not_found` skip advances the stage pointer and schedules the next stage (best-effort delivery). An alternative is to abort the entire enrolment on a skip. The current behaviour is chosen for resilience — a missing template does not cascade into blocking later (potentially more important) stages. This assumption should be confirmed with the product team.

4. **`to_field = "owner_sub"` resolution**: The stage executor calls `_fetch_record` to get the record dict. For the `ticket` module, `owner_sub` is a field on the ticket dict. However the email address requires a profile lookup via `profile.get_profile(owner_sub)`. The `_send_email_for_action` helper (WFL-007) already handles `owner_sub` → profile lookup. This ticket assumes the WFL-007 helper is in place and handles this case correctly.

5. **`delay_hours` granularity**: Only integer hours are supported (matching the cart reminders pattern). Sub-hour precision (e.g., `delay_minutes`) is not in scope for this ticket.

6. **Sequence update while records are enrolled**: Updating a sequence's `stages` list after enrolments exist does NOT retroactively change pending stage rows already written to `T.scheduled_actions`. The stage payload is a snapshot captured at schedule time (`template_id`, `to_field`). This is intentional — in-flight stages are immutable. Assumed acceptable for P2 scope.
