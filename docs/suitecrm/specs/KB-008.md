# KB-008 — Related articles linking

**Type:** Feature  **Priority:** P2  **Estimate:** 1 day  
**Ticket source:** `docs/suitecrm/CRM_KNOWLEDGE_BASE_TICKETS.md`, section "KB-008"

---

## 1. Summary & Goal

KB-008 adds bidirectional "related articles" linking to the Knowledge Base. An admin links any two articles; the link is surfaced on the public article view so readers can navigate to adjacent content. Links are stored in the existing `crm_kb_articles` DynamoDB table under a `RELATED#` PK prefix — zero new tables. The feature is default-off behind `S.knowledge_base_enabled` (KB-001).

Deliverables: three service methods (`add_related`, `remove_related`, `list_related`) on `KbArticleService`; three endpoints (`POST`, `DELETE`, `GET`) on the KB router; two Pydantic models; one `API_KEY_ROUTE_EXEMPTIONS` entry; hermetic pytest.

## 3. Data Model

### 3.1 Link rows (no new table, no new GSI)

All link data lives in `crm_kb_articles` under a `RELATED#` PK prefix. For a link between articles A and B, two rows are written:

| Field | Forward row | Reverse row |
|-------|-------------|-------------|
| `pk` | `RELATED#A` | `RELATED#B` |
| `sk` | `ARTICLE#B` | `ARTICLE#A` |
| `source_id` | `A` | `B` |
| `target_id` | `B` | `A` |
| `linked_by` | admin `user_sub` | admin `user_sub` |
| `created_at` | `now_ts()` (int) | same value |

`created_at` is stored on the item but is **not** a GSI sort key, so no new `attr_types` entry is required beyond what KB-001 already declares (`attr_types={"created_at": "N", "published_at": "N"}`). No changes to `scripts/local-ddb-init.py`.

The `RELATED#` prefix is distinct from every other prefix in the table (`ARTICLE#`, `CATEGORY#`, `TAG#`, `KB_TAG_STATS`, `SEARCH_TOKEN#`, `ATTACHMENT#`, `REVISION#`, `RATING#`, `VIEW#`) — no collision is possible.

Links are always accessed by source article PK (`query(PK="RELATED#{id}")`), so no GSI is needed.

### 3.2 Pydantic models (`app/models.py`)

```python
class KbAddRelatedReq(BaseModel):
    related_article_id: str  # min_length=1

class KbRelatedArticlesOut(BaseModel):
    items: list[KbArticleSummaryOut]  # reuses CAS-015 summary model
    count: int
```

`KbArticleSummaryOut` in its **expanded form** — `article_id`, `title`, `status`, `category_id`, `tags`, `view_count`, `helpful_count`, `not_helpful_count`, `published_at`, and `excerpt` — is defined by **KB-011** (`docs/suitecrm/specs/KB-011.md:269–279`), which supersedes CAS-015's minimal version (CAS-015 `KbArticleSummaryOut` at `docs/suitecrm/specs/CAS-015.md:326–331` carries only `article_id`, `title`, `category`, `helpful_count`, `published_at`). KB-008 therefore depends on the **KB-011** model shape, not the CAS-015 one. No new summary shape is needed.

## 4. API / Service Design

### 4.1 Service methods (`app/services/kb_articles.py`)

```python
def add_related(self, article_id: str, related_id: str, *, linked_by: str) -> dict[str, Any]:
    # 1. Raise KbArticleRelatedSelfError (400) if article_id == related_id.
    # 2. self.get_article(article_id) — raises KbArticleNotFoundError (404) if absent.
    # 3. self.get_article(related_id) — same.
    # 4. Build forward + reverse item dicts (created_at=now_ts()).
    # 5. batch_writer().put_item() for both — unconditional overwrite (idempotent, last-write-wins).
    # 6. audit_event("kb.related.added", linked_by, source_id=article_id, target_id=related_id)  # best-effort
    # Returns forward item dict.

def remove_related(self, article_id: str, related_id: str, *, admin_sub: str) -> None:
    # 1. T.kb_articles.delete_item(Key={"pk": f"RELATED#{article_id}", "sk": f"ARTICLE#{related_id}"})
    # 2. T.kb_articles.delete_item(Key={"pk": f"RELATED#{related_id}", "sk": f"ARTICLE#{article_id}"})
    # delete_item on a missing key is a no-op — inherently idempotent.
    # 3. audit_event("kb.related.removed", admin_sub, ...)  # best-effort

def list_related(self, article_id: str, *, limit: int = 10) -> list[dict[str, Any]]:
    # 1. query(PK="RELATED#{article_id}", Limit=limit) → link rows.
    # 2. batch_get_item(Keys=[{pk: "ARTICLE#{r['target_id']}", sk: "META"}]) chunked at 25,
    #    retry UnprocessedKeys up to 8 times (pattern: app/services/group_feed.py:357).
    # 3. Filter out missing items (orphan links) and items with status=="archived" or "draft".
    # 4. Sort by published_at desc (None last); return list of article item dicts.
```

The `batch_get_item` call uses `ddb` from `app.core.aws` (local import to avoid circular dep), unwrapping the `_FloatSafeTable` proxy to get the raw table name via `self._table._t.name`.

## 5. Detailed Behavior & Edge Cases

**Self-link** (`article_id == related_article_id`): `KbArticleRelatedSelfError` (HTTP 400, `code="self_link_not_allowed"`) raised before any DDB read.

**Missing articles**: `get_article` raises `KbArticleNotFoundError` (HTTP 404). Both articles are validated before any write.

**Bidirectionality**: Both `RELATED#A/ARTICLE#B` and `RELATED#B/ARTICLE#A` are written in a single `batch_writer` call. The `batch_writer` context manager retries `UnprocessedItems` automatically, so partial-failure windows are handled by the SDK.

**Orphan links**: When an article is deleted (`delete_article`, CAS-015), its `RELATED#` rows are not cleaned up. `list_related` silently omits targets whose `ARTICLE#{id}/META` item is absent in `batch_get_item`. No `list_related` call errors on orphans.

**Archived/draft filtering**: `list_related` filters items with `status != "published"` from public responses, preventing exposure of non-public content via the unauthenticated endpoint.

**Link count cap**: No cap is enforced in this ticket. Adding a cap later requires only a `query(..., Select="COUNT")` pre-check in `add_related`; no schema change.

**Concurrent writes**: DynamoDB `put_item` for link rows is LWW. Two admins simultaneously linking A→B results in both row pairs being written — harmlessly idempotent.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

All DynamoDB access uses `T.kb_articles` (a `_FloatSafeTable` wrapping `ddb.Table(S.kb_articles_table)`). In dev, `S.ddb_endpoint_url = "http://localhost:8001"`; in prod the SDK resolves the real endpoint. No `S.dev_mode` branch exists anywhere in this implementation — identical bytes execute in both environments (SECOPS-007 parity, matching the rest of the KB surface per `docs/suitecrm/specs/CAS-015.md:485`).

`add_related`: idempotent — `batch_writer` overwrites with same key values; last-write-wins on `linked_by`/`created_at` is safe for an admin-only linking action.

`remove_related`: inherently idempotent — DynamoDB `delete_item` on a non-existent key is a no-op.

Admin endpoints require `Role.ADMIN` or `Role.ROOT` enforced via `_is_admin(user)` (same helper as `app/routers/tickets.py:207`). A `Role.USER` caller receives HTTP 403.

`audit_event` calls are wrapped in `try/except` — failure never blocks the primary operation.

## 8. Backward Compatibility & Migration

KB-008 is purely additive. No existing rows are modified. No existing endpoints are modified. No existing Pydantic models are modified. `RELATED#` rows begin appearing in `crm_kb_articles` only after the first `add_related` call with `KNOWLEDGE_BASE_ENABLED=1`. Rolling the flag back to `0` hides all three endpoints with no data cleanup requirement.

`delete_article` (CAS-015) does not cascade-delete `RELATED#` rows; orphan rows are silently omitted at read time (§5, orphan handling). This matches the project norm for sparse cleanup of index rows.

## 10. Open Questions / Assumptions

1. **Max links per article**: No cap defined. If product sets a limit (e.g., 20), add a `query(..., Select="COUNT")` pre-check in `add_related`; no schema change needed.
2. **Link visibility on status change**: When linked article B transitions to `archived`, it disappears from A's related list automatically (filtered at read time). Link row is retained and would reappear if B is re-published. Product should confirm this is the intended UX.
3. **Cascade delete on article removal**: `delete_article` does not clean up `RELATED#` rows. Orphans are silently omitted at read time. Eager cleanup can be added as a follow-up (`query(PK="RELATED#{id}")` + batch delete) if storage hygiene is required.
4. **Assumption — KB-001 merged**: `T.kb_articles` and `S.knowledge_base_enabled` must be wired before this ticket's PR can be reviewed. If KB-001 is delayed, both must be added inline in this PR.
5. **Assumption — `KbArticleSummaryOut` defined**: `KbRelatedArticlesOut.items` uses the **expanded** `KbArticleSummaryOut` defined by **KB-011** (`docs/suitecrm/specs/KB-011.md:269`), not the minimal CAS-015 version. If KB-011 is not yet merged, KB-008 must include the expanded definition inline.
