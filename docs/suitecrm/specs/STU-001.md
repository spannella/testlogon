# STU-001 — Feature flag, settings & DynamoDB scaffolding

**Type:** Chore  **Priority:** P0  **Estimate:** 1 day  
**Ticket source:** `docs/suitecrm/CRM_SECURITY_STUDIO_TICKETS.md`, section "STU-001"

---

## 1. Summary & Goal

STU-001 is pure scaffolding. It delivers the two master feature flags (`crm_acl_enabled`, `crm_studio_enabled`), twelve settings keys for DynamoDB table names, ten new DynamoDB table definitions with all required GSIs and `attr_types` for numeric sort keys, and ten new table handles in `app/core/tables.py`. No router, no service logic, and no frontend UI is introduced.

The goal is that with both flags off (the default), the platform is byte-for-byte identical to its state before this ticket: no new routes are registered, no background workers start, and no existing table, service, or endpoint is altered. When either flag is set to `"true"` in the environment, the corresponding table handles become available for use by downstream STU tickets (STU-002 through STU-014) and the companion ACT/CAS/EML/RPT series.

STU-001 is the hard prerequisite for every subsequent STU ticket. Nothing in the CRM Security Suite, Studio, or Admin area can be built until this scaffolding is in place.

## 2. Context & Current State

### 2.1 Existing flag pattern

`app/core/settings.py` is a frozen `@dataclass` (`Settings`) populated entirely from environment variables (lines 6–7). The canonical default-OFF bool pattern used by the inventory and returns flags (lines 839, 846) is:

```python
inventory_reservations_enabled: bool = os.environ.get("INVENTORY_RESERVATIONS_ENABLED", "false").lower() == "true"
returns_rma_enabled: bool = os.environ.get("RETURNS_RMA_ENABLED", "false").lower() == "true"
```

This form is preferred for default-OFF flags over the `not in ("0", "false", "False")` form (used for default-ON flags such as `messaging_translation_enabled` at line 1875). The two new CRM flags must default OFF, so the `.lower() == "true"` form is the correct choice, matching the precedent at lines 839 and 846.

An alternative equivalent form (`"false".lower() in ("1", "true", "yes", "on")`) is used by `newsfeed_recsys_enabled` at line 2014. Either is acceptable, but `.lower() == "true"` is the most concise and aligns with the majority of default-OFF flags in the file.

The settings file ends at line 2772 with `S = Settings()`. New entries must be appended before the sentinel `S = Settings()` line at the end.

Every table name follows the same idiom (e.g., `billing_config_table_name` at line 2625):

### 2.3 Existing table handle pattern

`app/core/tables.py` defines a frozen `@dataclass` named `Tables` (line 69) whose fields are `Any`-typed. Every field is initialised via `_safe_table(S.<table_name_setting>)` (line 65), which wraps a boto3 Table in a `_FloatSafeTable` proxy (lines 29–66) that coerces Python floats to `Decimal` on every `put_item` / `update_item` / `batch_writer.put_item` call. The `T` singleton is instantiated at line 321.

The frozen dataclass means `T` cannot accept attribute assignment at runtime; tests use `object.__setattr__(T, "attr_name", moto_table)` to inject test doubles without touching the live singleton.

Ten new fields and ten new `_safe_table(...)` initialisers must be added following the pattern established throughout lines 69–572.

### 2.4 Existing TableDef / local-ddb-init.py pattern

`scripts/local-ddb-init.py` defines a `TableDef` dataclass at line 28:

```python
@dataclass(frozen=True)
class TableDef:
    name: str
    partition_key: str
    sort_key: Optional[str] = None
    gsi: List[Dict[str, str]] = field(default_factory=list)
    attr_types: Dict[str, str] = field(default_factory=dict)
```

The comment at line 34 states that numeric keys must be declared: "Use for numeric keys, e.g. `{'created_at': 'N'}`". This requirement is also documented in CLAUDE.md under "DynamoDB numeric GSI sort keys". Omitting `attr_types` for a numeric GSI sort key causes a `ValidationException` at query time.

Table definitions are returned by `_table_defs()` starting at line 42. The billing table at lines 67–77 shows the GSI plus `attr_types` pattern in full. All four tables in STU-001 that carry numeric GSI sort keys (`crm_acl_roles`, `crm_security_groups`, `crm_audit_trail`, and `email_queue`) require `attr_types` entries.

### 2.5 No existing CRM Security Suite / Studio infrastructure

A search of `app/core/settings.py` for `crm_acl_enabled`, `crm_studio_enabled`, and all 10 table-name keys returns no results. None of the 10 DynamoDB tables exist in `_table_defs()`. None of the 10 handles exist in the `Tables` dataclass or the `T` singleton. This ticket creates them all from scratch.

### 2.6 Cross-cutting constraints (from ticket file header)

All CRM Security Suite and Studio tickets are gated by `S.crm_studio_enabled` (env `CRM_STUDIO_ENABLED`) and `S.crm_acl_enabled` (env `CRM_ACL_ENABLED`), both defaulting to `"0"` / `false`. ## 3. Data Model

STU-001 introduces ten DynamoDB tables. Six of them are used directly by STU-002 through STU-010; the remaining four are used by STU-011 through STU-014. All follow the `TableDef` pattern in `scripts/local-ddb-init.py:28`.

### 3.1 Table definitions

#### `crm_acl_roles`
- **PK** `pk` (S) — values: `ROLE#{role_id}`
- **SK** `sk` (S) — values: `META`, `ASSIGNMENT#{user_sub}`, `GROUP_ASSIGNMENT#{group_key}`
- **GSI `by-assignee`**: PK=`assignee_id` (S), SK=`assigned_at` (N)
  - Purpose: retrieve all role-assignment rows for a given user sub (STU-002 `get_roles_for_user`).
  - `attr_types={"assigned_at": "N"}` required.

#### `crm_security_groups`
- **PK** `pk` (S) — values: `GROUP#{group_id}`
- **SK** `sk` (S) — values: `META`, `MEMBER#{user_sub}`, `RECORD#{entity_type}#{record_id}`
- **GSI `by-record`**: PK=`record_ref` (S), SK=`created_at` (N)
  - Purpose: fast lookup of all groups a CRM record belongs to (STU-004 `get_groups_for_record`). `record_ref` is written as `"{entity_type}#{record_id}"`.
  - `attr_types={"created_at": "N"}` required.

#### `crm_studio_fields`
- **PK** `entity_type` (S) — e.g. `contact`, `ticket`, `opportunity`, or the reserved value `__acl__` for field-level ACL metadata (STU-005).
- **SK** `field_key` (S) — e.g. `custom_region`, or `{role_id}#{entity_type}#{field_name}` for ACL rows.
- No GSI needed. Item counts per entity type are low (typically <200 custom fields), so a per-PK query on `entity_type` is always O(fields) and within DDB read capacity.

#### `crm_studio_modules`
- **PK** `pk` (S) — values: `MODULE#{module_key}`, or `MODULE#{from_entity}#{to_entity}` for relationship definitions (STU-014).
- **SK** `sk` (S) — values: `META`, `REL#{rel_name}`
- No GSI. The number of module and relationship definitions is small and bounded by admin activity.

#### `crm_studio_layouts`
- **PK** `pk` (S) — value: `LAYOUT#{entity_type}#{view_type}` (e.g. `LAYOUT#contact#detail`)
- **SK** `sk` (S) — value: `META`
- No GSI. Layout definitions are read by exact PK; there is no cross-entity scan requirement at this ticket level.

#### `crm_studio_dropdowns`
- **PK** `pk` (S) — value: `DROPDOWN#{list_name}`
- **SK** `sk` (S) — value: `META`
- No GSI. Dropdown definitions are read by exact PK or listed via full-partition scan (acceptable given the bounded admin-defined item count).

#### `crm_audit_trail`
- **PK** `pk` (S) — value: `ENTITY#{entity_type}#{record_id}`
- **SK** `sk` (S) — value: `CHANGE#{ts:010d}#{event_id}` (zero-padded timestamp enables chronological SK sort, newest-first with `ScanIndexForward=False`).
- **GSI `by-actor`**: PK=`actor_sub` (S), SK=`changed_at` (N)
  - Purpose: actor-scoped audit trail queries (STU-006 `get_actor_audit_trail`).
  - `attr_types={"changed_at": "N"}` required.

#### `currencies`
- **PK** `pk` (S) — values: `CURRENCY#{code}` (e.g. `CURRENCY#USD`), or `CURRENCY_CONFIG` for the global config row.
- **SK** `sk` (S) — value: `META` for currency rows; `CURRENT` for the config row (mirrors the `billing_config` single-partition pattern at `app/services/billing_config.py:39–41`).
- No GSI. All currency rows share the same PK prefix and are listed with a `begins_with` query.

#### `search_config`
- **PK** `pk` (S) — value: `SEARCH_CONFIG`
- **SK** `sk` (S) — value: `DOMAIN#{domain_name}` (e.g. `DOMAIN#videos`, `DOMAIN#catalog`)
- No GSI. The domain config set is small (<20 items) and always read as a full partition scan.

#### `email_queue`
- **PK** `pk` (S) — value: `EMAIL#{msg_id}` (msg_id = `uuid4().hex`)
- **SK** `sk` (S) — value: `META`
- **GSI `by-status`**: PK=`status` (S), SK=`queued_at` (N)
  - Purpose: worker queries `status=queued` in FIFO order to dequeue messages (STU-008 `process_queue_batch`). Also enables admin list-by-status filtering.
  - `attr_types={"queued_at": "N"}` required.

### 3.2 Summary of `attr_types` requirements

| Table | GSI name | Numeric SK | `attr_types` entry |
|---|---|---|---|
| `crm_acl_roles` | `by-assignee` | `assigned_at` | `{"assigned_at": "N"}` |
| `crm_security_groups` | `by-record` | `created_at` | `{"created_at": "N"}` |
| `crm_audit_trail` | `by-actor` | `changed_at` | `{"changed_at": "N"}` |
| `email_queue` | `by-status` | `queued_at` | `{"queued_at": "N"}` |

The remaining six tables have no numeric GSI sort keys and require no `attr_types` entries.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag isolation

With both `CRM_ACL_ENABLED` and `CRM_STUDIO_ENABLED` absent from the environment, `S.crm_acl_enabled` and `S.crm_studio_enabled` both evaluate to `False`. No downstream STU router is imported or registered in `app/main.py` when these flags are off. The 10 new table handles in `T` are initialised on process startup regardless of flag state (they are just boto3 Table proxies with no network activity at construction time), but they are never accessed by any code path when the flags are off.

This means the handles can be safely created even in tests that do not set up the CRM tables — as long as no service code reads from them. Tests for downstream tickets will inject moto-backed tables via `object.__setattr__` and will enable the flags via `object.__setattr__` on `S`, exactly as done throughout the test suite (e.g. `tests/test_gap_0265_0266_kyc_risk_scoring.py`).

### 5.2 Table name collision avoidance

The names `crm_acl_roles`, `crm_security_groups`, `crm_studio_fields`, `crm_studio_modules`, `crm_studio_layouts`, `crm_studio_dropdowns`, `crm_audit_trail` are not used anywhere in the existing codebase. The name `currencies` is not used as a DynamoDB table name (the existing billing table uses a different name). The name `search_config` does not conflict with the existing `app/routers/search.py` or `app/services/search.py` files, which use no single dedicated table. The name `email_queue` does not conflict with `email_delivery` (used by `app/services/email_delivery.py`).

### 5.3 `crm_security_groups` naming collision awareness

The name `crm_security_groups` must not be confused with the existing compute security groups table, whose handle is `T.security_groups` (line 255 of `app/core/tables.py`; the `security_groups=_safe_table(...)` initialiser is at line 507) and whose table name setting is `S.security_groups_table_name`. These are entirely separate concepts: `T.security_groups` holds EC2/K8s firewall rules managed by `app/services/security_groups.py` and `app/routers/security_groups.py`; `T.crm_security_groups` will hold CRM record-level access control memberships managed by the future `app/services/crm_security_groups.py` (STU-004). The distinct handle names prevent any ambiguity in service imports.

### 5.4 `currencies` GSI absence rationale

The `currencies` table has no GSI. All access patterns are exact-key reads (`get_item(Key={"pk": "CURRENCY#USD", "sk": "META"})`) or partition scans (`query(KeyConditionExpression=Key("pk").begins_with("CURRENCY#"))`) with a bounded item count (tens of currencies, never thousands). A scan or bounded query on a table with tens of items is always under 1 KB and never requires pagination or a GSI. This is the same rationale applied to `crm_studio_dropdowns` and `crm_studio_layouts`.

### 5.5 `crm_studio_fields` PK design — reuse for field-ACL rows

The `crm_studio_fields` table is shared between two distinct row types:

1. Custom field definitions: `entity_type = "contact"`, `field_key = "custom_region"` (STU-011).
2. Field-level ACL metadata: `entity_type = "__acl__"`, `field_key = "{role_id}#{entity_type}#{field_name}"` (STU-005).

The reserved PK value `__acl__` is guaranteed not to conflict with real entity types because entity type names follow snake_case and never start with double underscores. This single-table design avoids introducing a dedicated `crm_field_acl` table.

### 5.6 `crm_studio_modules` PK design — reuse for relationship definitions

Similarly, `crm_studio_modules` stores both module metadata (`pk = "MODULE#{module_key}"`, `sk = "META"`) and relationship definitions (`pk = "MODULE#{from_entity}#{to_entity}"`, `sk = "REL#{rel_name}"`). The two access patterns never conflict because module metadata SK is always `"META"` and relationship definition SKs always begin with `"REL#"`.

### 5.7 `just restart` and table creation

`just restart` calls `scripts/local-ddb-init.py` which invokes `_table_defs()` and creates each table if it does not already exist (using `CreateTable` with a `ResourceInUseException` guard). The 10 new tables will be created on the first restart after this ticket lands. There is no destructive operation on existing tables.

### 6.2 Default-OFF semantics

The `.lower() == "true"` form (as opposed to `not in ("0", "false", "False")`) means:
- Empty string `""` → `False` (safe).
- `"0"` → `False` (safe).
- `"false"` → `False` (safe, case-insensitive).
- `"true"` → `True`.
- `"1"` → `False` (unlike the `not in` form, `"1"` does NOT enable the flag with this pattern).

If the team prefers `"1"` to enable flags (a common convention for feature flags), the form `os.environ.get("CRM_ACL_ENABLED", "false").lower() in ("1", "true", "yes", "on")` should be used instead. This is the form used by `newsfeed_recsys_enabled` (line 2014). The ticket specification uses the `.lower() == "true"` form — this should be confirmed with the team before implementation. Whichever form is chosen, it must be applied consistently to both `crm_acl_enabled` and `crm_studio_enabled`.

### 6.3 Table-name settings

All 10 table-name settings follow the identical idiom:

```python
<name>_table_name: str = os.environ.get("<ENV_VAR>", "<default_name>")
```

The default table names become the DynamoDB table names created by `scripts/local-ddb-init.py` in development. In production, a deployment can override any name via the corresponding env var.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

STU-001 introduces no business logic, no network calls, and no conditional branching on `S.dev_mode`. The three files it modifies (`settings.py`, `tables.py`, `local-ddb-init.py`) run identically in dev (moto-backed DDB) and prod (real DynamoDB). The `_safe_table` wrapper's float-to-Decimal coercion is DDB-agnostic and applies in both environments. This satisfies SECOPS-007 with no additional effort.

### 7.2 Idempotency

`scripts/local-ddb-init.py`'s `CreateTable` calls are wrapped in a `ResourceInUseException` guard (existing pattern in the script). Running `just restart` multiple times will not duplicate or corrupt tables.

The `Settings` dataclass is frozen (`@dataclass(frozen=True)`) and populated at import time. There is no runtime mutation. The `Tables` dataclass is also frozen; all 10 new handles are set once at module load and never changed outside of tests.

### 7.3 Security

STU-001 introduces no new endpoints, no new auth checks, and no new data access paths. The flags `crm_acl_enabled` and `crm_studio_enabled` are read-only env-var booleans; they cannot be toggled at runtime by an API caller. The table handles are inert boto3 proxies that perform no operations until called by service code in downstream tickets.

The `crm_acl_roles` and `crm_security_groups` tables are sensitive (they will store access control data in downstream tickets). Their DynamoDB resource policies in production must follow the principle of least privilege — only the backend process role should have read/write access. This is a deployment/IAM concern outside the scope of STU-001 code changes.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact on existing tables and services

No existing table definition in `_table_defs()` is modified. No existing handle in `T` is changed. No existing settings key is altered. No existing router or service file is touched.

### 8.2 New table creation is additive

The 10 new DynamoDB tables are created by `scripts/local-ddb-init.py` on `just restart`. In production, a migration step must create these tables before deploying any code from downstream STU tickets (STU-002+). STU-001 alone does not require any production migration because its code changes are confined to the Python source files — no new routes or data access occur until a downstream ticket is deployed alongside a set `CRM_ACL_ENABLED` or `CRM_STUDIO_ENABLED` flag.

The recommended production rollout sequence is:
1. Deploy the STU-001 code change (settings + tables + handles).
2. Run the DynamoDB `CreateTable` migration for all 10 tables (same parameters as `_table_defs()` entries above).
3. Validate that all tables exist and GSIs are ACTIVE.
4. Deploy downstream STU tickets with flags still off.
5. Enable `CRM_ACL_ENABLED=true` and/or `CRM_STUDIO_ENABLED=true` to activate routes.

### 8.3 Table name availability in production

## 10. Open Questions / Assumptions

1. **Flag activation convention (`"1"` vs `"true"`)**: The ticket spec shows `_bool_env("CRM_ACL_ENABLED", False)` (a helper not present in `app/core/settings.py`), but the existing file uses inline `os.environ.get(...).lower() == "true"` or `not in (...)`. The spec assumes the `.lower() == "true"` form (matching `inventory_reservations_enabled`). If the team adopts `"1"` as the preferred enable value, the `in ("1", "true", "yes", "on")` form should be used instead. This must be decided before implementation.

2. **`currencies` table name collision**: The default name `"currencies"` must not conflict with any existing production DynamoDB table. A search of the codebase reveals no existing table with this name, but production accounts should be checked before migration.

3. **GSI billing**: DynamoDB charges per GSI per table. The four tables with GSIs (`crm_acl_roles`, `crm_security_groups`, `crm_audit_trail`, `email_queue`) each add one GSI. This is low cost but should be noted for capacity planning.

4. **`crm_studio_fields` shared with field-ACL rows**: The ticket spec places STU-005's field-ACL metadata on `crm_studio_fields` using `entity_type="__acl__"`. This is confirmed as intentional by the ticket file. However, if STU-005 is never implemented, the table still exists with no wasted rows. If STU-005 is implemented but a separate table is preferred, `crm_field_acl` can be introduced at that time as a STU-005 amendment.

5. **`crm_studio_modules` shared with relationship definitions**: The ticket spec places STU-014's relationship definition rows on `crm_studio_modules`. Same rationale as above — this is intentional per the ticket file and avoids a dedicated relationship table.

6. **Production IAM policies**: STU-001 does not include IAM policy changes. Downstream tickets that add service code reading/writing these tables must ensure the backend execution role has appropriate DynamoDB permissions before deployment.

STU-001 does not directly import from, modify, or extend any of these series. The dependency is directional: those series consume the tables and flags that STU-001 introduces.
