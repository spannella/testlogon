# EVT-009 — Survey analytics — per-question answer frequency distribution

**Type:** Feature | **Priority:** P1 | **Estimate:** 2d
**Source:** `docs/suitecrm/CRM_MISC_TICKETS.md` (section "EVT-009")
**Dependencies:** None (extends existing `_compute_questionnaire_analytics` in
`app/routers/questionnaires.py:150`).

---

## 1. Summary & Goal

EVT-009 extends the existing questionnaire analytics endpoint to add per-question answer-frequency
distributions for `select`, `multiselect`, and `radio` question types. Today the endpoint
(`GET /questionnaires/drafts/{questionnaire_id}/analytics`) reports funnel metrics, drop-off
points, and validation hotspots but contains no aggregation of what respondents actually answered.
This ticket surfaces the missing breakdown so questionnaire owners can see, for example, that 42 %
of respondents chose "Strongly agree" on a given Likert-scale radio question.

The deliverable is additive and flag-gated (`SURVEY_ANALYTICS_ENABLED`, default `false`). With
the flag off the endpoint returns exactly the same payload it does today — no existing field is
modified or removed. With the flag on, a new `question_frequencies` array is appended to the
response object. No new DynamoDB table, no new route, and no money-movement path is involved.

`questionnaires_repository.py:573–590`. It queries SK prefix
`ANSWER#{response_session_id}#` on the questionnaires single table and returns a

- A `str` for `select` and `radio` answers (validated at
  `questionnaire_validation.py:306–314` — `value not in options` where `options` is a
  `list[str]`).
- A `list[str]` for `multiselect` answers (validated at
  `questionnaire_validation.py:317–334` — `any(v not in options for v in value)`).

  `value_encrypted=True`, just as `list_session_answers` already decrypts them internally; since

  ciphertext — but `select`/`radio`/`multiselect` are **not** in the sensitive-type set

### 4.3 Helper: `_compute_question_frequencies`

**File:** `app/routers/questionnaires.py` (module-level, below
`_compute_questionnaire_analytics`)

```python
_FREQ_TYPES = frozenset({"select", "multiselect", "radio"})

def _compute_question_frequencies(
    *,
    questionnaire_id: str,
    versions: list[dict[str, Any]],
    sessions: list[dict[str, Any]],
) -> list[dict[str, Any]]:
    ...
```

**Signature rationale:** `sessions` is passed in from `_compute_questionnaire_analytics` (which
already fetches them at line 151) to avoid a redundant DynamoDB call. `versions` is likewise
already in scope. The helper is pure computation; it calls
`REPO.list_session_answers(questionnaire_id=..., response_session_id=...)` for each submitted
session.

**Algorithm (per version):**

1. For each published version:
   a. Extract all questions where `type in _FREQ_TYPES` from
      `version["schema_json"]["sections"][*]["questions"]`.
   b. Build `question_meta: dict[question_id, {label, type, options: list[str]}]`.
   c. Filter `sessions` to those where `version_id == version["version_id"]`
      and `status == "submitted"`.
   d. For each submitted session, call
      `REPO.list_session_answers(questionnaire_id=questionnaire_id, response_session_id=sid)`.
   e. For `select`/`radio` questions: if the answer is a `str` and present in `options`,
      increment `freq[question_id][answer_str]`. Count denominator = number of submitted
      sessions for this version (`total_submitted`); `total_answered` = sessions that provided
      a non-null answer for this question.
   f. For `multiselect` questions: if the answer is a `list`, iterate each element; if element
      is in `options`, increment `freq[question_id][element]`. Count denominator for `pct`
      = total submitted sessions (`total_submitted`, NOT total answer occurrences, so percentages
      sum to more than 100 % when multi-selections are common — this is the correct survey
      semantics; `total_answered` = sessions with at least one valid choice).
   g. Build the `options` list ordered by the canonical option order from `config_json.options`
      (not by count — preserves survey scale order). Unknown answer values (options removed
      after publish) are accumulated into a synthetic `{"value": "__other__", "label":
      "(other / removed option)"}` bucket if count > 0.
   h. Compute `pct = round(count / total_submitted * 100, 1)` when `total_submitted > 0`,
      else `0.0`.

2. Aggregate across versions by `question_id`: merge frequency dicts, summing counts, and
   recompute `pct` against the combined `total_submitted`. This gives the cross-version
   totals that mirror how `all_dropoffs` / `all_hotspots` are built at lines 155–156.

**Return value:**

```python
[
    {
        "question_id": "q_satisfaction",
        "question_label": "Overall satisfaction",
        "type": "radio",
        "total_submitted": 87,
        "total_answered": 82,
        "options": [
            {"value": "Very satisfied", "label": "Very satisfied", "count": 34, "pct": 39.1},
            {"value": "Satisfied",      "label": "Satisfied",      "count": 28, "pct": 32.2},
            ...
        ],
    },
    ...
]
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Questionnaire with no submitted sessions

`_compute_question_frequencies` returns `[]`. No call to `list_session_answers` is made. The
`question_frequencies` key is an empty list in the response (not omitted) — this prevents
frontend null-guards from needing special-casing.

### 5.2 Multi-version questionnaires

For questionnaires with multiple published versions, options may differ (a question could be
removed or a new option added). The function accumulates per-version first, then merges.
Questions present only in some versions are included only in those version aggregations.
The cross-version totals use `total_submitted` from all versions combined.

### 5.3 Answer value not in current options list

If a respondent submitted an answer whose value no longer appears in the version's `options`
list (e.g., an option was renamed after a bug fix by republishing), the value is counted in the
`__other__` synthetic bucket. This prevents silent data loss while keeping the canonical option
rows clean.

### 5.4 `multiselect` percentage semantics

`pct` for a multiselect option is `count / total_submitted * 100`, not `count / total_answers`.
Example: 10 submitted sessions, 6 chose option A, 8 chose option B — pct for A = 60.0,
pct for B = 80.0. The sum across options exceeds 100 %; the `type` field signals this to the
frontend. This matches standard survey analysis practice. `total_answered` is the count of
sessions that selected at least one option.

### 5.5 Encrypted answers

`list_session_answers` transparently decrypts KMS-encrypted values (lines 586–588). Because
`select`/`radio`/`multiselect` question types are not in the sensitive-type set
(`_sensitive_question_ids_for_version` at line 553: `sensitive_types = {"address", "date",
"time", "timezone"}`), frequency aggregation never encounters encrypted data in practice. The
helper must still handle a `value_encrypted=True` row defensively (skip it) in case of future
type changes, relying on the decrypted dict returned by `list_session_answers`.

### 5.6 DynamoDB pagination for sessions

`list_response_sessions` at `questionnaires_repository.py:492` uses a single `query()` call
with no `Limit` — it returns all `RESP#` rows for the questionnaire. Per the CLAUDE.md
`FilterExpression` gotcha, `query()` fetches up to 1 MB before filtering. For questionnaires
with very large response volumes (> ~4000 sessions on an active table), this may miss sessions
beyond the first DynamoDB page. EVT-009 does not fix this existing limitation; it is noted as
an open question (see §10). The existing analytics function already has this behaviour.

### 5.7 `pct` precision

`round(count / total_submitted * 100, 1)` uses Python's built-in banker's rounding. Percentages
for all options of a question should nominally sum to ~100 % for single-select types (rounding
error up to ±0.1 × number_of_options is acceptable and standard).

### 5.8 Performance

For a typical questionnaire with 100 submitted sessions and 10 questions, the helper makes
100 calls to `list_session_answers` (one per session). Each call does a DynamoDB query with
a narrow SK prefix. At O(100) queries this is acceptable for a synchronous analytics endpoint.
For questionnaires with > 1000 sessions a caching / background-compute approach should be
considered (tracked in §10); EVT-009 does not address it.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

EVT-009 introduces no `if S.dev_mode` branching. The `_compute_question_frequencies` helper
calls `REPO.list_session_answers` which reads from `T.questionnaires` — the same DynamoDB path
in both dev (DynamoDB Local) and prod (real DynamoDB). The flag check
`getattr(S, "survey_analytics_enabled", False)` is a pure boolean gate; it does not alter data
reads or writes. This satisfies the SECOPS-007 requirement of identical code paths.

### 7.2 Idempotency

The endpoint is a `GET` (pure read). Calling it N times with the same inputs returns the same
result (within the DynamoDB eventual-consistency window). No state is written. The function is
fully idempotent.

### 7.3 Owner-only access

`_owned_questionnaire_or_404` at `questionnaires.py:231` enforces that only the questionnaire
owner can access analytics. The frequency distribution data — which reveals respondents'
aggregated choices — is visible only to the owner. Individual `respondent_id` values are not
included in `question_frequencies`; the aggregation is non-PII at the output level.

### 7.4 No money movement

EVT-009 is a read-only analytics extension. No billing, refund, or ledger primitives are
involved. `settle_or_reverse_ledger` and `refund_payment` are not referenced.

### 7.5 Audit

An `audit_event("survey_analytics_viewed", user_sub, questionnaire_id=questionnaire_id)` call
(via `app/services/alerts.audit_event` at `alerts.py:644`) is placed in the existing endpoint
handler at `questionnaires.py:612`, alongside the existing `_owned_questionnaire_or_404` check.
This fires regardless of whether the flag is on (viewing any analytics is an auditable action),
consistent with the existing pattern where KYC and admin analytics endpoints emit audit events
on access.

## 8. Backward Compatibility & Migration

### 8.1 No breaking change to existing response

The `question_frequencies` key is absent when `SURVEY_ANALYTICS_ENABLED=0`. When the flag is
on, it is a **new additive key** in the `analytics` dict. JSON consumers that do not
recognise the key ignore it (RFC 7159 §4). No existing field is renamed or removed.

### 8.2 Frontend defensive rendering

`QuestionnaireAnalyticsTab.tsx` guards on `analytics.question_frequencies?.length > 0` before
rendering the frequency section. If the backend is deployed with the flag off and the frontend
is deployed with the new component, no new UI appears. This is the standard feature-flag
dual-deployment safety pattern.

### 8.3 No DynamoDB schema migration

No new table, GSI, or attribute type is introduced. `just restart` requires no schema change.
Existing questionnaire data (sessions, answers, versions) is consumed as-is.

### 8.4 No rolling-migration window

Because the change is a pure read-only extension with an additive JSON key, it can be deployed
to prod without a coordination window. The flag can be toggled at runtime via env-var update +
process restart without data migration.

## 10. Open Questions / Assumptions

1. **DynamoDB page size for large questionnaires**: `list_response_sessions` and
   `list_session_answers` both use unbounded `query()` calls. For questionnaires with > ~4000
   sessions the first DynamoDB page (1 MB cap) may be silently truncated. EVT-009 accepts this
   limitation (consistent with the existing analytics function) and defers a
   `LastEvaluatedKey`-looping upgrade to a follow-up ticket.

2. **Performance budget for N answer reads**: For questionnaires with > 500 submitted
   sessions, the helper makes > 500 sequential DynamoDB calls. A future caching layer
   (background pre-computation storing a frequency snapshot row, similar to the newsfeed
   recsys `RECO#` row pattern) is recommended but out of scope for this 2d ticket.

3. **Option structure is `list[str]`**: The spec assumes `config_json.options` is always a
   flat `list[str]` (both identity and label are the same string). If a future ticket
   introduces rich options (`[{"value": "...", "label": "..."}]`), the aggregation key must
   switch from `str` to `option["value"]` and the label from `str` to `option["label"]`.

4. **`question_frequencies` placement: per-version vs. totals-only**: The ticket description
   says "return as `question_frequencies`" without specifying whether it lives inside each
   version row or only in the top-level `totals` block. This spec places it at the top-level
   `analytics` object (alongside `versions` and `totals`) as a cross-version aggregate. A
   per-version breakdown is tracked as a follow-up if needed.

5. **Audit event on every analytics GET**: Some operators may prefer the audit event to fire
   only when `question_frequencies` data is actually returned (flag on). This spec fires it
   unconditionally. If audit volume is a concern the guard can be added without changing the
   public contract.
