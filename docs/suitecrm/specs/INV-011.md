# INV-011 — Invoice frontend — admin invoice management UI

**Type:** Feature | **Priority:** P2 | **Estimate:** 2d  
**Flag:** `AOS_STANDALONE_INVOICES_ENABLED` (default `"0"`, off)  
**Dependencies:** INV-001, INV-002, INV-004, INV-005, INV-009, INV-010, QUO-005

---

## 1. Summary & Goal

Build an admin-facing invoice management UI that allows sales reps and general
admins to create B2B invoices manually, browse all invoices across users,
filter by status and date, and perform lifecycle actions (send, void). The
existing user-facing `InvoicesPage.tsx` (at
`frontend/src/pages/billing/InvoicesPage.tsx`) is unchanged. No new backend
DynamoDB tables are introduced; this ticket is a pure frontend layer that wires
together the backend endpoints delivered by INV-001 through INV-010 and
QUO-005.

The goal matches the SuiteCRM AOS Invoice module's administrative surface:
admins can see invoices across all buyers, create manual B2B invoices with
structured line items and addresses, and drive the status lifecycle from the
UI. With `AOS_STANDALONE_INVOICES_ENABLED=0` (the default), the platform is
byte-for-byte unchanged — no new routes exist, no new JS bundle chunks are
loaded, no existing pages are modified.

## 4. API / Service Design

### 4.1 New API endpoint wrappers (`frontend/src/api/endpoints/invoices.ts`)

All wrappers use the existing `api` client instance from
`frontend/src/api/client.ts`. The wrappers are only imported by the new admin
pages, so they are never executed when `AOS_STANDALONE_INVOICES_ENABLED=0`.

```typescript
export interface AdminInvoiceListParams {
  user_sub?: string;
  status?: string;        // "draft" | "sent" | "paid" | "overdue" | "void" | "all"
  date_from?: number;
  date_to?: number;
  account_id?: string;
  limit?: number;
  cursor?: string;
}

/** GET /ui/admin/invoices — requires ADMIN or ROOT role */
export const adminListInvoices = (params: AdminInvoiceListParams = {}) => {
  const qp: Record<string, string> = {};
  if (params.user_sub)    qp.user_sub  = params.user_sub;
  if (params.status && params.status !== "all") qp.status = params.status;
  if (params.date_from != null) qp.date_from = String(params.date_from);
  if (params.date_to   != null) qp.date_to   = String(params.date_to);
  if (params.account_id) qp.account_id = params.account_id;
  if (params.limit != null) qp.limit = String(params.limit);
  if (params.cursor)    qp.cursor = params.cursor;
  return api.get<InvoiceList>("/ui/admin/invoices", qp);
};

/** POST /ui/admin/invoices/manual — QUO-005 endpoint */
export const createManualInvoice = (body: ManualInvoiceCreateIn) =>
  api.post<Invoice>("/ui/admin/invoices/manual", body);

/** POST /ui/invoices/{number}/send — QUO-005 / INV-009
 * CONFIRMED: QUO-005 defines this endpoint at docs/suitecrm/specs/QUO-005.md:242
 * (require_ui_session, empty body; calls update_invoice_status(...,"sent") then a
 * best-effort email_invoice). This wrapper is correct as written — no fallback to
 * patchInvoiceStatus is needed.
 */
export const sendInvoice = (invoiceNumber: string) =>
  api.post<Invoice>(`/ui/invoices/${encodeURIComponent(invoiceNumber)}/send`);

/** POST /ui/invoices/{number}/void — QUO-005 / INV-009
 * NOTE: INV-009.md:242-246 also exports voidInvoice with identical signature.
 * Do not re-declare; import the symbol added by INV-009 instead.
 */
export const voidInvoice = (invoiceNumber: string) =>
  api.post<Invoice>(`/ui/invoices/${encodeURIComponent(invoiceNumber)}/void`);

/** GET /ui/admin/currencies — INV-002 */
export const listCurrencies = (activeOnly = true) =>
  api.get<{ currencies: Currency[] }>("/ui/admin/currencies", {
    active_only: String(activeOnly),
  });

/** GET /ui/admin/tax-rates — INV-005 */
export const listTaxRates = (activeOnly = true) =>
  api.get<{ tax_rates: TaxRate[] }>("/ui/admin/tax-rates", {
    active_only: String(activeOnly),
  });
```

No new backend service functions or FastAPI endpoints are added by INV-011
itself — it only wires the frontend to endpoints owned by sibling tickets.

### 4.2 Backend admin list — status filter extension

The existing `admin_list_invoices` in `app/services/invoices.py:492` accepts
`target_user_sub` and `invoice_type` but not `status`. To support the admin
UI's status filter, the function signature is extended:

```python
def admin_list_invoices(
    *,
    target_user_sub: Optional[str] = None,
    invoice_type: Optional[str] = None,
    status: Optional[str] = None,          # new
    date_from: Optional[int] = None,       # new
    date_to: Optional[int] = None,         # new
    limit: int = 100,
    cursor: Optional[str] = None,
) -> Dict[str, Any]:
```

When `status` is provided and not `"all"`, a `FilterExpression` is appended
to the GSI2 query: `Attr("status").eq(status)`. Because DynamoDB applies
`FilterExpression` after fetching up to the 1-MB page limit (CLAUDE.md:
"DDB FilterExpression doesn't reduce page size"), the service loops via
`LastEvaluatedKey` until either `limit` items pass the filter or the
response has no `LastEvaluatedKey`. Maximum loop iterations: 10 (safety cap).

`date_from` / `date_to` are post-fetch filters applied in Python on the
`created_at` attribute (matching the existing pattern in `list_invoices:426-431`
at `app/services/invoices.py`).

The admin router `GET /ui/admin/invoices` (`app/routers/invoices.py:99`) gains
two new `Query` parameters:

```python
status:    Optional[str] = Query(default=None)
date_from: Optional[int] = Query(default=None)
date_to:   Optional[int] = Query(default=None)
```

These are passed through to `admin_list_invoices`. The route path and auth
dependency (`require_admin_or_root`) are unchanged.

## 5. Detailed Behavior & Edge Cases

### 5.1 `AdminInvoicesPage.tsx`

Located at `frontend/src/pages/billing/AdminInvoicesPage.tsx` (new file).

**Filters (controlled state)**:
- `filterStatus` — `<Select>` with options: All / Draft / Sent / Paid /
  Overdue / Void. Default `"all"`.
- `filterUserSub` — `<Input>` free-text for user sub search. Default `""`.
- `filterDateFrom` / `filterDateTo` — `<Input type="date">`.
- `filterAccountId` — `<Input>` for account_id (INV-010). Default `""`.

**Data fetching**:
```tsx
const query = useQuery({
  queryKey: ["admin-invoices", filterStatus, filterUserSub, filterDateFrom,
             filterDateTo, filterAccountId],
  queryFn: () => adminListInvoices({
    status: filterStatus,
    user_sub: filterUserSub || undefined,
    date_from: toEpoch(filterDateFrom),
    date_to: toEpoch(dateTo),
    account_id: filterAccountId || undefined,
    limit: 100,
  }),
  enabled: true,   // always fetches; admin sees all invoices by default
});
```

`toEpoch` is the same helper already used in `InvoicesPage.tsx:30-35`.

**Table columns**: invoice_number (mono font), buyer_name, total_cents with
currency badge (calls `formatCents(inv.total_cents, inv.currency)` from
`InvoiceRow.tsx:10-19`; when `inv.original_currency` is non-empty and != `"usd"`,
renders a secondary badge `"{original_currency.toUpperCase()}"` drawn from
INV-004 display logic), status badge with semantic colors (draft=secondary,
sent=blue, paid=green, overdue=destructive, void=outline), due_date column
(formatted `formatDate(inv.due_date)` — blank when absent), account_id column
(blank when absent), and an Actions column.

**Actions column** (per-row `<DropdownMenu>`):
- "Download PDF" — calls `downloadInvoicePdf(inv.invoice_number)` (existing
  wrapper).
- "Email" — calls `emailInvoice(inv.invoice_number)` then invalidates
  `["admin-invoices", ...]`.
- "Send" — visible only when `inv.status === "draft"`. Calls `sendInvoice`.
  On success: toast "Invoice sent" and `queryClient.invalidateQueries(["admin-invoices"])`.
- "Void" — visible only when `inv.status === "draft" || inv.status === "sent"`.
  Opens a `<AlertDialog>` confirmation ("Void invoice {number}?"). On confirm:
  calls `voidInvoice`. On success: toast "Invoice voided" and invalidates the
  query key.

**"Create Invoice" button** — opens `<ManualInvoiceForm>` in a `<Dialog>`.

**Empty state** — `<EmptyState>` with `FileText` icon when `invoices.length === 0`
and query is not loading.

**Loading state** — three `<Skeleton className="h-20 w-full">` placeholders,
matching the pattern in `InvoicesPage.tsx:111-116`.

### 5.2 `ManualInvoiceForm.tsx`

Located at `frontend/src/pages/billing/ManualInvoiceForm.tsx` (new file).

Uses React Hook Form with Zod schema validation. The form is rendered inside a
`<DialogContent>` opened from `AdminInvoicesPage` via a controlled `open`/
`onOpenChange` prop pair.

**Zod schema**:
```typescript
const lineItemSchema = z.object({
  description: z.string().min(1),
  quantity: z.number().int().min(1),
  unit_price_cents: z.number().int().min(0),
  tax_rate_id: z.string().optional(),
});

const manualInvoiceSchema = z.object({
  buyer_name:        z.string().min(1),
  buyer_email:       z.string().email(),
  payment_terms_days: z.number().int().min(0).optional().default(30),
  currency:          z.string().length(3).optional().default("usd"),
  discount_cents:    z.number().int().min(0).optional().default(0),
  billing_address:   z.object({
    street: z.string().min(1),
    city:   z.string().min(1),
    state:  z.string().optional().default(""),
    postal_code: z.string().min(1),
    country: z.string().min(2),
  }).optional(),
  line_items: z.array(lineItemSchema).min(1),
});
```

**Currency select**: populated from `useQuery(["admin-currencies"], listCurrencies)`.
When INV-002 flag is off the query returns 404 (API error); the form falls back
to a plain text input for `currency` displaying `"usd"` as default. The
`listCurrencies` call uses `api.get` so ApiError is caught and the select is
hidden (not shown in error state) — the field defaults to `"usd"`.

**Tax rate select** (per line item): populated from `useQuery(["admin-tax-rates"],
listTaxRates)`. Same 404-fallback: when INV-005 flag is off, the select column
is omitted from the line-items table. The select is a `<Select>` per row
showing `"{name} ({rate_bps / 100}%)"`.

**Dynamic line items**: managed with React Hook Form's `useFieldArray`.
"Add line" appends a blank row; "Remove" button (trash icon) on each row
removes it. At least one line item is required (enforced by Zod `min(1)`).

**Subtotal preview**: computed client-side as a read-only `<p>` element:
```
subtotal = sum(qty * unit_price_cents)
discount = form.watch("discount_cents") || 0
net = subtotal - discount
```
This is informational only; the backend recomputes authoritatively.

**Submit mutation**:
```typescript
const mutation = useMutation({
  mutationFn: createManualInvoice,
  onSuccess: (inv) => {
    toast.success(`Invoice ${inv.invoice_number} created`);
    queryClient.invalidateQueries({ queryKey: ["admin-invoices"] });
    onOpenChange(false);
  },
  onError: (err) => toast.error(err.message),

```

### 5.4 Edge cases

**INV-002 / INV-005 flags off**: `listCurrencies()` and `listTaxRates()` both
return 404. The `useQuery` hooks enter error state. The form renders without
the currency select and without the tax rate column. The text input for
`currency` defaults to `"usd"`. This is handled with `onError: () => {}`
(silent) in the query options so no toast fires for an expected 404.

**INV-009 / QUO-005 not yet merged**: `sendInvoice` and `voidInvoice` return
404. The action buttons call the endpoint; on ApiError (404), the error toast
reads "Invoice not found or action not available." The buttons are always
visible for eligible statuses regardless of whether QUO-005 is merged; the
backend is the source of truth.

**Status field missing on old invoices**: Old items from before QUO-005 carry
`status="generated"` or `status="emailed"`. The "Send" / "Void" buttons are
not shown for these statuses (only `draft` / `sent`) so no incorrect action
button appears.

**Large invoice lists with status filter**: The backend loops via
`LastEvaluatedKey` (up to 10 pages) to fill the status filter. Frontend
receives a normal `InvoiceList` response; pagination via `next_cursor` is
surfaced as a "Load more" button. The frontend does not call infinite query
for the admin list (keeping implementation simple given the 2d estimate).

**Currency badge overflow**: `formatCents` in `InvoiceRow.tsx:10-19` uses
`Intl.NumberFormat` which handles unknown currency codes by falling back to
the `try/catch` branch returning `"$N.NN"`. The admin table reuses
`formatCents` directly.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**No `if S.dev_mode` branches in any code added by this ticket.** The sole
backend change (the `status` / `date_from` / `date_to` filter extension on
`admin_list_invoices`) uses DynamoDB `FilterExpression` and Python-level
post-filtering; both work identically against DynamoDB Local (dev) and
DynamoDB (prod) via the same boto3 call path.

**Auth**: All admin endpoints use `require_admin_or_root` from
`app/auth/policy.py:67`, which enforces `Role.ADMIN` or `Role.ROOT`. The
frontend `api` client at `frontend/src/api/client.ts:174-177` includes the
impersonation token header when active. No new auth dependency is introduced.

**CSRF**: The `api.post` / `api.patch` helpers in `client.ts:293-313`
automatically attach the `x-csrf-token` header from the `ui_csrf` cookie.
Admin mutation endpoints require this header (enforced by
`require_admin_or_root` in conjunction with `enforce_cookie_csrf` from
`app/auth/policy.py:100-106`). No additional CSRF handling needed in the new
wrappers.

**Void idempotency**: `voidInvoice` calls `POST /ui/invoices/{number}/void`
(QUO-005). QUO-005 specifies that voiding an already-void invoice returns a
consistent 200 or 409 response; the frontend handles both: on 2xx the query is
invalidated; on `ApiError` the toast shows the error message. No special
dedup logic is needed in this ticket.

**S3 / PDF**: INV-011 does not upload or generate PDFs; it only calls
`downloadInvoicePdf` (existing wrapper using `fetch` with `credentials: "include"`
at `invoices.ts:32-49`).

**Audit**: The backend `admin_list_invoices` endpoint does not emit audit
events (read-only). `createManualInvoice` (QUO-005) calls
`app/services/alerts.audit_event("invoice.manual_created", ...)` — owned by
QUO-005, not duplicated here. `sendInvoice` and `voidInvoice` emit their own
audit events (QUO-005 / INV-009). No new audit calls are needed in INV-011.

**Input sanitization**: Zod schema in `ManualInvoiceForm` enforces email
format (`z.string().email()`), min-length for string fields, and non-negative
integers for cents/quantity. The backend Pydantic models (QUO-005) perform
server-side validation independently; the Zod schema is defense-in-depth.

## 10. Open Questions / Assumptions

1. **QUO-005 merge order**: INV-011 depends on `POST /ui/admin/invoices/manual`,
   `POST /ui/invoices/{n}/send`, and `POST /ui/invoices/{n}/void` all being
   available. If QUO-005 is not yet merged when INV-011 ships, the "Create"
   and "Send" / "Void" buttons will return 404 at runtime. The frontend
   degrades gracefully (toast error). The feature flag
   `AOS_STANDALONE_INVOICES_ENABLED` should remain off in production until
   QUO-005 is merged.

2. **Sidebar navigation**: No sidebar link to `/admin/invoices` is specified.
   Assumed to be added as part of an admin nav consolidation ticket, or
   discovered via `/admin/financials`. An admin can reach the page via direct
   URL or from the FinancialDashboard (`admin/financials`) with a link added
   in a future UX pass.

3. **Infinite scroll vs. "Load more"**: The spec chooses a simple "Load more"
   button (single `useQuery` with explicit `cursor` state) over
   `useInfiniteQuery` to stay within the 2d estimate and because the admin
   table already shows up to 100 items per page (sufficient for typical
   admin workflows). If the platform accumulates large invoice histories,
   a follow-up can migrate to `useInfiniteQuery`.

4. **`ManualInvoiceForm` billing_address fields**: The spec marks
   `billing_address` as optional at the Zod level. INV-001 requires the address
   struct when passed but does not mandate it. If QUO-005's
   `POST /ui/admin/invoices/manual` makes `billing_address` required on the
   backend, the Zod schema must be tightened to `z.object({...})` (non-optional)
   and the form must show required field indicators.

5. **`account_id` search filter**: The `filterAccountId` input sends
   `account_id` to `adminListInvoices`. The backend `admin_list_invoices`
   passes it through to `list_invoices_for_account` (INV-010) when set. If
   INV-010 is not yet merged, this filter silently returns an empty list
   (GSI3 does not exist → DynamoDB raises a `ResourceNotFoundException` which
   the backend catches and returns `{"invoices": [], "next_cursor": null}`).
   This is acceptable degradation.
