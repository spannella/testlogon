# CMP-007 — A/B (split) test for campaign email content

**Type:** Feature  **Priority:** P2  **Estimate:** 2d  
**Area:** Campaigns & Email Marketing  
**Source:** `docs/suitecrm/CRM_CAMPAIGNS_EXTRA_TICKETS.md` § CMP-007

---

## 1. Summary & Goal

CMP-007 brings SuiteCRM-parity split testing to testlogon's marketing campaign module. Campaign owners can attach 2–5 named variants to a single campaign, each with its own HTML email template and/or subject line. When the campaign is sent, the audience is deterministically divided across variants by weighted round-robin; each send-log row records which variant a recipient received. The per-variant engagement counters (opens from CMP-003 tracking-pixel VISIT rows, clicks from MKT-010 VISIT rows) are surfaced via a new `GET .../ab-results` endpoint that returns raw rates plus a two-proportion Z-test significance result reusing `ab_test_significance` already implemented at `app/services/ad_optimization.py:253`.

Goals:
1. **Additive variant metadata** — a `variants` list on the campaign model; 2–5 variants; default `None` means no A/B test (existing behavior is unchanged).
2. **Deterministic audience split** — each resolved party is assigned to exactly one variant using `hash(campaign_id + "\x00" + party_id) % total_weight`; the assignment is stable across replays.
3. **Variant-scoped tracking** — per-variant tracking sub-codes `{code_slug}_v{idx}` are provisioned on first send via MKT-010's `create_tracking_code`; all open-pixel and click-redirect hits land on the correct per-variant counter.
4. **Statistical reporting** — `GET /ui/marketing/campaigns/{id}/ab-results` returns `variant_stats` (sent, opens, clicks, rates) and a significance block from the reused Z-test utility.
5. **Zero footprint when flag off** — `S.marketing_campaigns_enabled` gates all new paths; existing sends, attribution, and models are byte-for-byte unchanged when the feature is absent or variants is `None`.

## 2. Context & Current State

### A/B test significance utility (existing, in production)

`app/services/ad_optimization.py:253–308` defines:

```python
def ab_test_significance(
    *,
    variant_a: Dict[str, int],
    variant_b: Dict[str, int],
    confidence_level: float = 0.95,
) -> Dict[str, Any]:
    """Two-proportion Z-test between two creatives."""
```

It accepts `{"impressions": int, "clicks": int}` dicts, runs a pooled two-proportion Z-test, and returns `{"variant_a_ctr", "variant_b_ctr", "lift_percent", "z_score", "p_value", "significant": bool, "confidence_level", "winner": "a"|"b"|None, "sample_size_sufficient": bool}`. The `min_sample = 100` guard at line 266 returns `significant=False` and `sample_size_sufficient=False` when either arm has fewer than 100 observations. This function is pure Python with no external dependencies, making it trivially testable offline. CMP-007 calls it with `impressions=variant.sent` and `clicks=variant.opens` (open-rate significance) as the primary metric, and a separate call with `clicks=variant.clicks` (click-rate significance) as a secondary metric. The pairwise loop over 2–5 variants is described in Section 4.

## 3. Data Model

### No new DynamoDB table for variant metadata

Variant definitions are stored as a JSON list in the `variants` attribute on the existing campaign META row in `T.marketing_campaigns`. This avoids a new table for what is fundamentally a compound attribute of the campaign itself. The list is small (2–5 entries, each ≤ 500 bytes) and always fetched with the campaign, so no GSI is needed for variant lookup.

### `T.marketing_send_log` — additive GSI and attribute

The `MarketingCampaignSendLog` table (created by MKT-009, `scripts/local-ddb-init.py`) receives one additive change:

- **New attribute**: `variant_id: str` — present on rows written when `campaign.get("variants")` is non-empty; absent on all pre-existing rows (backward-compatible absence).
- **New GSI `ByCampaignVariant`**: partition key `campaign_id` (S), sort key `variant_id` (S). This is a string sort key; no `attr_types` declaration is needed. The GSI enables a `query(KeyConditionExpression=Key("campaign_id").eq(cid) & Key("variant_id").eq(vid))` to count sent rows per variant directly, without loading and filtering all send-log rows for the campaign.

Updated `TableDef` in `scripts/local-ddb-init.py` (replaces the existing MKT-009 block):

```python
TableDef(
    _resolve_table_name(S.marketing_send_log_table_name, "MarketingCampaignSendLog"),
    "pk",
    "sk",
    gsi=[
        {
            "index_name": "ByCampaignSentAt",
            "partition_key": "campaign_id",
            "sort_key": "sent_at",
        },
        {
            "index_name": "ByCampaignVariant",
```

`variant_id` is a string GSI sort key; `attr_types` is only required for numeric sort keys per the CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha. The `sent_at` numeric declaration from MKT-009 is preserved.

### Settings additions (`app/core/settings.py`)

No new settings are required. `S.marketing_campaigns_enabled` (MKT-002) is the sole flag. The variant-count limits and confidence level are hardcoded constants in the service (not env-tunable at MVP).

### No changes to `T.tracking_codes` schema

Per-variant sub-codes are distinct rows in the existing `T.tracking_codes` table (PK `TRACK#{code_slug}_v{idx}` / SK `META`). The `ByCampaignCreatedAt` GSI on that table already allows listing all codes for a campaign by `campaign_id`; the `_v{idx}` suffix on the slug makes them identifiable as variant sub-codes. The visit/open rows live under these sub-codes, following the existing `VISIT#{ts}#{nonce}` SK pattern.

#### `send_campaign` extension — variant assignment

Inside `_resolve_audience` (MKT-009), add variant assignment:

```python
def _assign_variant(
    campaign_id: str,
    party_id: str,
    variants: List[dict],
) -> dict:
    """Deterministically assign a party to a variant using weighted round-robin.

    Algorithm:
      total_weight = sum(v["weight"] for v in variants)
      bucket = int(hashlib.sha256(
          (campaign_id + "\\x00" + party_id).encode("utf-8")
      ).hexdigest(), 16) % total_weight

      Walk variants in order, subtracting each weight; the variant whose
      cumulative weight range contains bucket is selected.

    This is purely deterministic — replaying send_campaign with the same
    audience and variants always assigns the same party to the same variant.
    The sha256 is computed once per party in O(1) with no DDB reads.
    """
```

`_try_send_one` gains an additional `variant: Optional[dict] = None` parameter. When `variant` is not None:
1. The `subject` argument is overridden by `variant["subject_override"]` (if set, rendered through `_render(variant["subject_override"], merge_vars)` from CMP-008's `_build_merge_vars`).
2. The `email_template_id` used by `_build_message_body` is `variant.get("email_template_id") or campaign.get("email_template_id")`.
3. The tracking URL is `f"{S.public_base_url}/ui/marketing/t/{tracking_code}_v{variant_index}"` (where `variant_index` is the zero-based position in the variants list).
4. The send-log row written to `T.marketing_send_log` includes `variant_id=variant["variant_id"]`.

#### `compute_ab_results` — new service function

```python
def compute_ab_results(
    campaign_id: str,
    owner_id: str,
) -> CampaignABResultsOut:
    """Compute per-variant engagement stats and significance tests.

    1. Fetch the campaign item; raise 404 if not found or not owned by owner_id.
    2. If campaign has no variants, raise HTTPException(400, "no A/B variants configured").
    3. For each variant:
       a. Count sent rows via ByCampaignVariant GSI:
          T.marketing_send_log.query(
              IndexName="ByCampaignVariant",
              KeyConditionExpression=Key("campaign_id").eq(cid) & Key("variant_id").eq(vid),
              Select="COUNT",
          )
       b. Count open VISIT rows for the variant tracking code (if provisioned):
          T.tracking_codes.query(
              KeyConditionExpression=Key("pk").eq(f"TRACK#{slug}_v{idx}") & Key("sk").begins_with("VISIT#"),
              FilterExpression=Attr("event_type").eq("open"),
              Select="COUNT",
          )
          DDB FilterExpression does not reduce page count; the query must loop via
          LastEvaluatedKey until exhausted. For MVP, cap at 10 000 visits per
          variant and return a `capped: True` flag if the limit is hit.
       c. Count click VISIT rows (event_type="click" or event_type absent) similarly.
       d. Compute open_rate = opens / sent (or 0.0), click_rate = clicks / sent (or 0.0).
    4. Build significance results for every ordered pair (i, j) where i < j, for both
       "open_rate" (impressions=sent_i, clicks=opens_i vs impressions=sent_j, clicks=opens_j)
       and "click_rate" (impressions=sent_i, clicks=clicks_i).
       Call ab_test_significance() from app/services/ad_optimization.py:253 for each pair+metric.
       Map winner "a"|"b"|None to the corresponding variant_id.
    5. Emit audit_event("marketing.ab_test.results_queried", owner_id, campaign_id=campaign_id).
    6. Return CampaignABResultsOut.
    """
```

## 5. Detailed Behavior & Edge Cases

### Variant assignment determinism and replay safety

`_assign_variant` uses `sha256(campaign_id + "\x00" + party_id)` with a null-byte separator to prevent prefix-collision attacks (following the MKT-004 pattern cited at `docs/ofbiz/specs/MKT-004.md:57`). The assignment is stateless — no DDB read is required. If `send_campaign` is replayed with the same campaign and the same variants list, every party is assigned to the same variant. The `_try_send_one` dedup (`ConditionExpression="attribute_not_exists(pk)"` on the send-log row) already prevents double-delivery on replay; the variant_id on the row records which variant was actually sent.

### Variant weight normalization

Weights are not normalized to sum to 100; they are relative. Equal-weight two-variant tests use `weight=1` on both. A `weight=[3,1]` split sends 75% of recipients to variant A and 25% to variant B. The `total_weight` is recomputed at send time from the persisted variant rows, so updating weights between sends (via `update_campaign`) affects subsequent sends immediately.

### Unequal audience size

If the campaign audience is very small (e.g., 3 recipients with a 2-variant equal-weight split), some variants may receive 0 recipients. `compute_ab_results` must handle `sent=0` without division-by-zero: `open_rate = opens / sent if sent > 0 else 0.0`. The significance function's `min_sample=100` guard (`ad_optimization.py:266`) will return `significant=False, sample_size_sufficient=False` for any variant with fewer than 100 sends.

### 3–5 variant pairwise comparisons

For 3 variants, there are 3 pairwise comparisons (0v1, 0v2, 1v2), each yielding two `ABSignificanceOut` entries (open_rate + click_rate) for a total of 6 significance objects. For 5 variants the maximum is 10 pairs × 2 metrics = 20 objects. All are returned in a flat `significance` list. The caller UI is responsible for presenting them appropriately.

### No tracking code on the campaign

When `campaign.get("tracking_code")` is absent or `None`, `_ensure_variant_tracking_code` is never called. Open rates will be `0` for all variants (no pixel to fire), but click rates are also unavailable because there are no sub-codes to embed in the email body. The `VariantStatOut` will show `opens=0, clicks=0` for all variants. The significance test will return `sample_size_sufficient=False`. This is documented behavior, not an error.

### Variant with no email_template_id (plain-text fallback)

When both `variant.email_template_id` and `campaign.email_template_id` are `None`, `_build_message_body` falls back to the plain-text body template (MKT-009 default). The variant's `subject_override` is still applied to the subject line. The open-tracking pixel (CMP-003) is not appended when there is no HTML body — this is the same behavior as non-variant sends and requires no special handling.

### `update_campaign` with a changed variants list

If an owner calls `PATCH /ui/marketing/campaigns/{id}` and changes the `variants` list, the new list is validated and written to `variants_json`. Subsequent sends use the new list. Previously sent rows in `T.marketing_send_log` retain the old `variant_id` values; the `compute_ab_results` query against `ByCampaignVariant` may return rows for old variant_ids that no longer exist in the current variants list. The service handles this by including only variant_ids present in the current campaign `variants_json` when building `variant_stats`; orphaned send-log rows are silently excluded from the results.

### Concurrent sends

If two `send_campaign` calls run concurrently (e.g., via duplicate POST requests), the `_ensure_variant_tracking_code` idempotency (attribute_not_exists conditional put on the tracking code) prevents duplicate sub-code creation. The per-party send dedup (`_try_send_one` conditional put on `T.marketing_send_log`) prevents double-delivery. The variant assignment function is stateless and produces the same variant for any (campaign_id, party_id) pair regardless of concurrency.

## 6. Feature Flag & Config

### Gate

All CMP-007 paths are gated on `S.marketing_campaigns_enabled` (added by MKT-002, `app/core/settings.py`, env `MARKETING_CAMPAIGNS_ENABLED`, default `"0"` → `False`). Following the pattern at `app/core/settings.py:821`:

```python
marketing_campaigns_enabled: bool = os.environ.get(
    "MARKETING_CAMPAIGNS_ENABLED", "0"
) not in ("0", "false", "False")
```

With the flag off:
- `POST /ui/marketing/campaigns` with `variants` set → the field is accepted and stored (model validation still runs) but `_require_enabled()` raises HTTP 404 before the service is called, so no DDB write occurs.
- `GET /ui/marketing/campaigns/{id}/ab-results` → 404.
- `send_campaign` → raises HTTP 403 immediately (MKT-009 guard); no variant assignment or sub-code provisioning occurs.
- No variant_id is written to any send-log row.
- `compute_ab_results` → 404 (never reached).

### No additional feature flags

Split testing is a structural sub-feature of campaign sends, not a separately togglable behavior. Adding a `campaign_ab_test_enabled` flag would create a two-flag dependency that is harder to reason about than the single master flag.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

No `if S.dev_mode` branch exists anywhere in this ticket. The two behaviors that differ between dev and prod are:
1. Email delivery — `send_alert_email` at `app/services/alerts.py:459–492` handles dev vs. prod internally. CMP-007 calls `_try_send_one` the same way as MKT-009.
2. DynamoDB — the same `T.marketing_send_log` and `T.tracking_codes` handles are used in dev (DynamoDB Local on port 8001) and prod (real DynamoDB). Moto provides the offline test equivalent. No in-memory mock branches are introduced.

### Send idempotency

Inherits MKT-009's `attribute_not_exists(pk)` conditional put on `T.marketing_send_log` keyed on `send_id = sha256(campaign_id + "\x00" + str(snapshot_ts) + "\x00" + party_id)[:24]`. A replayed `send_campaign` call never re-delivers to a party that already received a message in that snapshot. The variant assignment for a replayed party is identical (deterministic hash), but the dedup fires before any variant-specific send path executes.

### Sub-code provisioning idempotency

`_ensure_variant_tracking_code` uses `create_tracking_code` from MKT-010 which internally uses `ConditionExpression="attribute_not_exists(pk)"` on the tracking code META row. A second call with the same slug is silently idempotent (returns the slug without re-writing the row).

### Ownership enforcement

`_require_campaign_owner` (from MKT-011) enforces that the campaign belongs to `ctx["user_sub"]` before any read or write. The `GET .../ab-results` endpoint also enforces ownership. There is no public endpoint for A/B results.

### No money movement

CMP-007 introduces no billing writes, no refunds, and no ledger entries. Attribution is purely read-only aggregation of existing `T.tracking_codes` VISIT rows and `T.marketing_send_log` send rows. The `billing_shared.new_ledger_entry` and `refund_payment` / `settle_or_reverse_ledger` primitives are not called anywhere in this ticket.

### Input validation

- `variants` list must have 2–5 entries; validated in `_validate_and_assign_variants`.
- Each `variant.name` is `min_length=1, max_length=80` (Pydantic model).
- Each `variant.email_template_id`, when provided, is verified against DDB at campaign create/update time.
- `variant.weight` is `ge=1, le=100` (Pydantic model); zero weights are rejected to prevent division-by-zero in the assignment hash.
- `variant_id` on input is ignored (server-assigned); Pydantic default `""` is replaced by the server before persistence.

## 8. Backward Compatibility & Migration

### Existing campaigns (no variants)

Campaigns created before CMP-007 have no `variants_json` attribute. `get_campaign` returns `variants=[]` for such items (via `json.loads(item.get("variants_json") or "null") or []`). `send_campaign` on a campaign with no variants follows the pre-existing single-path logic exactly. `GET .../ab-results` returns HTTP 400 `"no A/B variants configured"`. No DDB migration is required.

### Existing send-log rows (no variant_id)

Pre-existing `T.marketing_send_log` rows lack `variant_id`. The `ByCampaignVariant` GSI is an additive GSI on the existing table; DynamoDB adds pre-existing items to the GSI only if they carry the GSI key attributes. Items without `variant_id` are simply absent from the GSI (sparse GSI behavior). Queries against `ByCampaignVariant` for a campaign with pre-CMP-007 send rows correctly return zero rows for any variant — consistent with "no A/B test was active for those sends."

### Adding the GSI in production

Adding `ByCampaignVariant` to `MarketingCampaignSendLog` in production requires an `UpdateTable` call followed by DynamoDB's async backfill. Since `variant_id` was absent on all pre-existing rows, the backfill results in an empty GSI. No service downtime is required; DynamoDB adds the GSI asynchronously and the service continues to write new rows (which will include `variant_id` for new A/B sends) concurrently. In local dev, `just restart` recreates the table with both GSIs via `scripts/local-ddb-init.py`.

## 10. Open Questions / Assumptions

1. **Multi-variant (3–5) front-end display**: The spec returns all pairwise significance comparisons. The UI design for presenting 3+ variant comparisons is deferred to MKT-013 and CMP-007's frontend ticket. The backend API is complete regardless.

2. **Variant-level unsubscribe opt-out tracking**: CMP-004's `opt_out_user` writes a global opt-out row (not per-campaign or per-variant). This means a recipient who unsubscribes via a variant B email is suppressed from all future campaign sends, not just variant B. This is intentional (CAN-SPAM compliance) and requires no CMP-007 changes.

3. **Historical re-analysis**: If a campaign is re-sent against a new audience snapshot, old send-log rows (with old variant_ids) coexist with new rows. `compute_ab_results` aggregates all rows across all snapshots. If this causes misleading statistics (e.g., the variant weight changed between sends), the owner can use the `snapshot_ts` field on send-log rows to filter manually. A per-snapshot breakdown is a future enhancement.

4. **A/B winner auto-promotion**: SuiteCRM allows automatically declaring a winner and continuing the remainder of the send with the winning variant. This is not implemented in CMP-007. It is tracked as a future P3 feature.

5. **Assumption: `ab_test_significance` pairwise-only**: The `ab_test_significance` function at `app/services/ad_optimization.py:253` accepts exactly two variants. Multi-arm Bayesian approaches or ANOVA are out of scope. For 3–5 variants, all pairwise Z-tests are computed; multiple-comparison correction (Bonferroni) is noted in the significance response metadata as a future enhancement.

6. **Assumption: CMP-003 is deployed before CMP-007 in production**: Without CMP-003, all `opens` counts will be 0 (no pixel to fire). The open-rate significance test will return `sample_size_sufficient=False` for all variants. The click-rate test will still function if CMP-003 variant tracking codes are provisioned. The service handles the CMP-003-absent case gracefully (zero opens is a valid state).
