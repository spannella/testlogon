# LED-008 — Bulk CSV import for Leads and Prospects

**Type:** Feature  **Priority:** P1  **Estimate:** 2 days  
**Ticket source:** `docs/suitecrm/CRM_LEADS_TICKETS.md`, section "LED-008"

---

## 1. Summary & Goal

LED-008 adds `POST /ui/leads/import/csv` — a multipart file-upload endpoint that accepts a UTF-8 CSV, validates each row, performs per-row duplicate detection, and bulk-creates Lead or Prospect records in the `leads` DynamoDB table.

The endpoint returns a structured result object summarising how many rows were imported, how many were skipped as duplicates, and a per-row error list for any rows that failed validation. The import is additive: on success each row calls the existing `create_lead` or `create_prospect` service functions from LED-003 and LED-007 respectively, so all business rules (normalization, audit events, GSI fan-out) are inherited automatically and never duplicated.

The entire feature is gated by `S.leads_enabled` (LED-001, default `False`). With the flag off the endpoint returns 404 and the platform is byte-for-byte unchanged.

### 3.3 Import result shape (in-memory, not persisted)

The import result is an ephemeral Python dict returned in the HTTP response body. It is never written to DynamoDB. For large imports where the caller needs to poll status, a future ticket (LED-008-async, not in scope here) could persist this dict; for the MVP synchronous path it is purely in-memory.

```
{
  "imported": int,      # rows successfully created
  "skipped":  int,      # rows skipped (duplicate or record already exists)
  "errors":   [         # rows that raised a validation error
    {"row": int, "reason": str}
  ]
}
```

## 4. API / Service Design

### 4.1 Service: `app/services/leads_import.py`

New file created from scratch. All functions are synchronous (no `async`). Called from the async route handler via `await asyncio.to_thread(import_leads_from_csv, ...)` following the pattern used in `app/routers/google_drive_integration.py`.

#### 4.1.1 Constants

```python
LEAD_CSV_COLUMNS = [
    "first_name", "last_name", "email", "phone",
    "company", "title", "lead_source", "description", "website",
]
MAX_IMPORT_ROWS = 5000
_MAX_CSV_BYTES = 10 * 1024 * 1024   # 10 MB; also enforced at router layer
```

#### 4.1.2 `import_leads_from_csv`

```python
def import_leads_from_csv(
    owner_sub: str,
    csv_bytes: bytes,
    *,
    record_type: str = "lead",        # "lead" or "prospect"
    skip_duplicates: bool = True,
) -> dict:
    """
    Parse csv_bytes as UTF-8 CSV, validate each row, and bulk-create
    Lead or Prospect records.

    Returns:
        {"imported": int, "skipped": int, "errors": [{"row": int, "reason": str}]}
    """
```

Implementation steps (in order):

1. **Flag guard**: `if not S.leads_enabled: raise HTTPException(503, "Leads module is not enabled")`.
2. **record_type validation**: raise `HTTPException(422, "record_type must be 'lead' or 'prospect'")` for unknown values.
3. **Decode**: `text = csv_bytes.decode("utf-8", errors="replace")`. Replace-mode prevents a single malformed byte from aborting the whole import.
4. **Parse**: `reader = csv.DictReader(io.StringIO(text))`. The `DictReader` uses the first row as field names.
5. **Header validation**: `missing = set(["email"]) - set(reader.fieldnames or [])`. If `email` is absent, raise `HTTPException(422, "CSV must contain an 'email' column")`. Other columns are optional; absent optional columns produce `None` in the row dict.
6. **Row iteration loop** (up to `MAX_IMPORT_ROWS`):
   a. Strip every field: `row = {k: (v or "").strip() for k, v in raw_row.items()}`.
   b. Sanitize every string value via `_sanitize_csv_field` (imported from `app/services.csv_export`) to prevent CSV injection from user-supplied data being reflected in downstream string storage.
   c. **Required field check**: if `row.get("email")` is empty, append `{"row": row_num, "reason": "missing required field: email"}` to errors and `continue`.
   d. **Email pre-validation**: call `normalize_email(row["email"])` in a `try/except HTTPException`. On failure, append error and `continue`. Store the normalized email as `norm_email`.
   e. **Duplicate check**: call `find_lead_by_email(norm_email)` (for `record_type="lead"`) or `find_prospect_by_email(norm_email)` (for `record_type="prospect"`). If a match is found and `skip_duplicates=True`, increment `skipped` and `continue`. If `skip_duplicates=False`, proceed to create (the service-layer idempotent create will return the existing record without writing a duplicate).
   f. **Build model input**:
      - For `"lead"`: construct `LeadCreateIn(first_name=..., last_name=..., email=..., phone=..., company=..., title=..., lead_source=..., description=..., website=...)`. Use `lead_source = row.get("lead_source") or "other"`.
      - For `"prospect"`: construct `ProspectCreateIn(email=..., first_name=..., last_name=..., phone=..., company=...)`.
   g. **Pydantic validation**: wrap `LeadCreateIn(...)` / `ProspectCreateIn(...)` in `try/except ValidationError`. On failure, append `{"row": row_num, "reason": str(exc.errors()[0]["msg"])}` and `continue`.
   h. **Create record**: call `create_lead(owner_sub, model)` or `create_prospect(owner_sub, model)` inside a `try/except Exception`. On success increment `imported`. On `HTTPException` with status 409 (duplicate from service layer), increment `skipped`. On any other exception, append error and `continue`.
7. **Hard cap**: after the loop, if the reader still has rows (i.e., `row_count == MAX_IMPORT_ROWS`), append a synthetic error `{"row": MAX_IMPORT_ROWS + 1, "reason": "import truncated at 5000-row limit"}`.
8. **Audit event**: `audit_event("lead_import.completed", owner_sub, imported=imported, skipped=skipped, error_count=len(errors), record_type=record_type)`.
9. Return `{"imported": imported, "skipped": skipped, "errors": errors}`.

#### 4.1.3 `_sanitize_csv_field` (imported, not copied)

LED-008 imports `_sanitize_csv_field` from `app.services.csv_export` (which defines it at `app/services/csv_export.py:43`). It is not copied or forked. Importing a private symbol from a sibling service is intentional here because the function is tightly scoped to CSV field safety and has no meaningful public alternative.

### 4.2 Router endpoint: `app/routers/leads.py`

LED-013 owns the full router file. LED-008 specifies only the import endpoint; LED-013 will integrate it into the complete router surface.

```python
from fastapi import APIRouter, Depends, File, Form, HTTPException, Query, UploadFile
from app.services.sessions import require_ui_session
from app.core.settings import S

router = APIRouter(prefix="/ui/leads", tags=["leads"])

_MAX_CSV_BYTES = 10 * 1024 * 1024  # 10 MB

# IMPORTANT: declared BEFORE /{lead_id} per FastAPI declaration-order rule
@router.post("/import/csv", status_code=200)
async def import_csv(
    file: UploadFile = File(...),
    record_type: str = Form(default="lead"),
    skip_duplicates: bool = Form(default=True),
    ctx: dict = Depends(require_ui_session),
):
    if not S.leads_enabled:
        raise HTTPException(404, "Not found")
    csv_bytes = await file.read()
    if len(csv_bytes) > _MAX_CSV_BYTES:
        raise HTTPException(422, "CSV file must be under 10 MB")
    import asyncio
    from app.services.leads_import import import_leads_from_csv
    result = await asyncio.to_thread(
        import_leads_from_csv,
        ctx["user_sub"],
        csv_bytes,
        record_type=record_type,
        skip_duplicates=skip_duplicates,
    )
    return result
```

**HTTP verb**: `POST` with `multipart/form-data`.
**Auth**: `require_ui_session` (cookie + CSRF enforced automatically for non-GET requests).
**Status codes**:
- `200 OK` — import ran; check `errors` in response body for per-row failures.
- `422 Unprocessable Entity` — file exceeds 10 MB, unknown `record_type`, or missing `email` header column.
- `503 Service Unavailable` — `S.leads_enabled` is False (also surfaces as 404 at the route guard for cleaner UX; see Section 6).
- `404 Not Found` — `S.leads_enabled` is False (per flag-off convention used across the CRM tickets).

### 4.3 Pydantic response model: `LeadImportResultOut`

Added to `app/models.py` after the existing `LeadOut` / `ProspectOut` family (LED-002):

```python
class LeadImportRowError(BaseModel):

class LeadImportResultOut(BaseModel):

```

## 5. Detailed Behavior & Edge Cases

### 5.1 Column header matching

`csv.DictReader` uses the first row as field names. Header matching is case-sensitive: `email` must appear exactly as `email`, not `Email` or `EMAIL`. The spec does not require case-insensitive matching for MVP; if a caller supplies `Email`, the row dict will have `Email` not `email`, and the required-field check will flag every row. A future enhancement could call `.lower()` on all fieldnames during parsing.

If the CSV has extra columns beyond `LEAD_CSV_COLUMNS`, `DictReader` includes them in the row dict. They are silently ignored (not stored).

### 5.2 `lead_source` validation

`LeadCreateIn.lead_source` has a Pydantic regex constraint accepting only the eight valid values (`web_site`, `cold_call`, `email`, `campaign`, `trade_show`, `word_of_mouth`, `other`, `internal`). If `row.get("lead_source")` is an unknown value, Pydantic validation will raise `ValidationError`. The import service catches this at step 4.1.2(g) and records a per-row error, then continues with the next row.

If `lead_source` is absent from the CSV (no column) or blank, the service substitutes `"other"` before constructing `LeadCreateIn`, so missing source is never an error.

### 5.3 Phone normalization failures

`normalize_phone` at `app/core/normalize.py:66` raises `HTTPException(400, "Invalid phone format; ...")`. Unlike `normalize_email`, a bad phone should not abort the row — phone is an optional field. The service must catch `HTTPException` from phone normalization, store `phone=None` for that row, and continue. The row is still imported; a warning is not written to `errors` (the phone data is simply dropped). This is consistent with the "best-effort optional field" pattern used throughout the codebase.

### 5.4 Duplicate detection semantics

`find_lead_by_email` queries the `ByEmail` GSI4 (after LED-007) with `GSI4PK = "EMAIL#{norm_email}"`. The GSI4 covers both `LEAD#` and `PROSPECT#` rows (they share the same `leads` table). For `record_type="lead"`, the helper filters for rows whose `pk` begins with `"LEAD#"`. For `record_type="prospect"`, it filters for `"PROSPECT#"`. This means a CSV imported as `record_type="lead"` will not skip a row just because a Prospect with the same email exists, and vice versa. The duplicate check is type-scoped.

If `skip_duplicates=False`, the service calls `create_lead` / `create_prospect` unconditionally. Those functions implement idempotent create: if the email already exists in the same record type, they return the existing record without writing a new row. The `imported` counter is incremented (the call "succeeded"), not the `skipped` counter, to reflect that the caller explicitly opted out of duplicate skipping. This is intentional: with `skip_duplicates=False` the caller expects all rows to be "processed" even if the underlying create is a no-op.

### 5.5 Encoding and BOM handling

The service decodes with `errors="replace"` to handle files with isolated encoding issues. The UTF-8 BOM (`﻿`) that Excel emits when saving as CSV is handled by Python's `csv.DictReader` transparently when the file is decoded as `"utf-8-sig"`. To be safe, the service should use `csv_bytes.decode("utf-8-sig", errors="replace")` — the `"utf-8-sig"` codec strips the BOM if present and behaves identically to `"utf-8"` if the BOM is absent. This is a one-character change from the earlier `"utf-8"` proposal and prevents the `﻿` character prepending the first column name (`﻿email` instead of `email`), which would make the required-field check fail silently.

### 5.6 Empty file and header-only file

- Zero bytes: `csv.DictReader` yields no rows; `fieldnames` is `None`. The required-field check (`missing = {"email"} - set(reader.fieldnames or [])`) detects the absent `email` column and raises `HTTPException(422, "CSV must contain an 'email' column")`.
- Header row only (no data rows): the loop iterates zero times and returns `{"imported": 0, "skipped": 0, "errors": []}`. This is valid and not an error.

### 5.7 Row count cap and partial import

The cap is enforced by a `row_count` counter inside the loop. When `row_count == MAX_IMPORT_ROWS`, the loop breaks and a synthetic error entry is appended. All rows up to and including row 5000 are processed normally; row 5001 onward is silently dropped (only the synthetic error notes the truncation). The HTTP response is still `200 OK` — truncation is not a hard error; the caller can re-upload a continuation file starting from the next batch.

### 5.8 Partial failure semantics

LED-008 does not implement transactional batch writes. Each row is created independently. If rows 1–50 succeed and row 51 fails validation, rows 1–50 are already committed to DynamoDB. There is no rollback. This is consistent with the row-level error collection design in the ticket description and matches industry-standard CSV import UX (Salesforce, HubSpot, and SuiteCRM all use the same partial-success model).

### 5.9 Large batch performance

`import_leads_from_csv` runs in `asyncio.to_thread`, keeping the event loop unblocked. Each row is a separate synchronous `T.leads.put_item` call (via `create_lead`/`create_prospect`). For 5000 rows this is approximately 5000 sequential DynamoDB writes. In a production environment with a well-provisioned `leads` table this completes in under 30 seconds. The endpoint has no explicit timeout guard beyond the standard uvicorn request timeout. A future improvement could batch writes using `T.leads.batch_writer()` inside the service; however, batching bypasses `create_lead`'s idempotent duplicate check and audit-event emission, so it requires careful design and is deferred to a follow-up.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 dev/prod parity

LED-008 contains no `dev_mode` branches and no conditional logic that diverges between local and production environments. The service reads and writes `T.leads` exclusively through the `create_lead` / `create_prospect` functions, which are DynamoDB-only operations — the same code path executes against DynamoDB Local (port 8001) in dev and against real DynamoDB in prod. The `audit_event` call writes to `T.alerts`, which is also DynamoDB-only. There is no S3 upload, no SES/email send, no Cognito call, and no external service dependency. SECOPS-007 parity is satisfied structurally.

### 7.2 Idempotency

**Upload-level**: the import endpoint is not natively idempotent. Submitting the same CSV twice with `skip_duplicates=True` (the default) results in 0 new records on the second call and all rows counted as `skipped`. With `skip_duplicates=False`, a second submission creates duplicate records (by design — the caller opted out of deduplication).

**Row-level**: each row is idempotent with `skip_duplicates=True` because `find_lead_by_email` is called before `create_lead`. The `create_lead` service function also has its own idempotent-create guard (returns existing record on email collision); LED-008's pre-check adds a `skipped` counter entry so the result is accurate.

There is no `Idempotency-Key` header for the upload endpoint. This differs from `app/routers/kyc_partner_api.py:187` which requires an `Idempotency-Key`. CSV bulk import is not a financial or legally sensitive operation, so this omission is acceptable for MVP.

### 7.3 CSV injection prevention

All string values read from the CSV are passed through `_sanitize_csv_field` (from `app/services/csv_export.py:43`) before being stored. This prevents `=CMD(...)`, `+SUM(...)`, and similar payloads from being stored verbatim and later re-exported in a way that would execute in spreadsheet software. The sanitization prepends `'` to any value beginning with `=`, `+`, `-`, `@`, `\t`, or `\r`.

Additionally, Pydantic model validation enforces max-length constraints on all string fields (`first_name` max 120, `email` max 254, `description` max 4000, etc.), preventing excessively large payloads from reaching DynamoDB.

### 7.4 Authentication and authorization

The endpoint requires a valid `ui_session` cookie (cookie-based auth) or Bearer token. CSRF is enforced automatically by `require_ui_session` (`app/services/sessions.py:330`) for all `POST` requests using cookie auth. Bearer-token requests bypass CSRF per the CLAUDE.md auth pattern.

There is no additional RBAC check beyond `require_ui_session`: any authenticated user can import leads into their own account. Admin-scoped import (importing on behalf of another user) is not in scope for LED-008.

### 7.5 Rate limiting

LED-008 does not introduce per-endpoint rate limiting. The standard platform rate-limit middleware (if present) applies. A future ticket could add a per-user import-count rate limit to prevent abuse of the 5000-row-per-call allowance.

### 7.6 File content validation

The endpoint accepts any content type for the uploaded file (FastAPI does not enforce `Content-Type: text/csv`). The parser will simply fail at the `DictReader` stage if the content is not valid CSV, producing a `422` from the header validation step. Binary content (e.g., Excel `.xlsx`) will decode with replacement characters and likely fail the `email` column check. This is acceptable behavior; a future improvement could check `file.content_type.startswith("text/")` or detect the BOM of an XLSX file and return a clearer error.

## 8. Backward Compatibility & Migration

### 8.1 Existing endpoints

LED-008 introduces one new route (`POST /ui/leads/import/csv`). No existing route, Pydantic model, DynamoDB table, service function, or frontend component is modified. When `LEADS_ENABLED=0` (the default), the route returns 404 and is invisible to all existing callers.

### 8.2 DynamoDB schema

No new table, GSI, or attribute type is introduced by LED-008. The `leads` table's `ByEmail` GSI (GSI4) is introduced by LED-007 and is a prerequisite for LED-008's duplicate detection. No `scripts/local-ddb-init.py` change is required in LED-008 itself.

### 8.3 `app/models.py`

`LeadImportRowError` and `LeadImportResultOut` are additive new model classes. No existing model class is modified. They are inserted after the `LeadOut` / `ProspectOut` family (from LED-002) and before the next non-leads section. Per the LED project constraint: "No existing `app/models.py` model is modified."

### 8.4 Migration

There is no data migration. The import endpoint writes new records into the `leads` table in the same format as `create_lead`; all existing lead records are unaffected. Enabling `LEADS_ENABLED=1` on a live instance with an existing `leads` table is safe.

## 9. Test Plan

### 9.1 Hermetic pytest — `tests/test_led_008_bulk_csv_import.py`

All tests use the canonical offline isolation pattern from `tests/test_gap_0220_0221_ssh_stored_key.py`:
- `@mock_aws` decorates the test class; `moto` creates an in-memory DynamoDB resource.
- `object.__setattr__(T, "leads", moto_table)` patches the frozen `T` handle; `addCleanup` restores it.

- Route handlers are called directly (not via `TestClient`), passing mock `ctx` dicts.
- No real AWS, no network, no subprocess.

**Test cases:**

1. **Happy path — lead import**: 5-row CSV with all required and optional fields. Assert `imported=5`, `skipped=0`, `errors=[]`. Assert 5 `LEAD#` items exist in the moto table.

2. **Happy path — prospect import**: Same CSV with `record_type="prospect"`. Assert 5 `PROSPECT#` items exist, no `LEAD#` items.

3. **Missing email column**: CSV with columns `[first_name, last_name]` (no `email`). Assert `HTTPException(422)` is raised with the `"CSV must contain an 'email' column"` message.

4. **Row with empty email**: CSV where one row has `email=""`. Assert that row appears in `errors` with `reason` containing `"missing required field: email"`, and all other valid rows are imported.

5. **Invalid email format**: Row with `email="not-an-email"`. Assert row appears in `errors`; other rows imported.

6. **Duplicate email with `skip_duplicates=True`** (default): Pre-insert one lead with `email="dup@example.com"` into the moto table. Submit CSV containing that email. Assert `skipped=1`, `imported=N-1`.

7. **Duplicate email with `skip_duplicates=False`**: Same setup. Assert `imported=N` (all rows processed including duplicate; service-layer idempotent create returns existing record, no new row).

8. **Row cap at 5001 rows**: Construct a CSV with 5001 data rows in memory. Assert `imported=5000`, `errors` contains the truncation entry at `row=5001`.

9. **File exceeds 10 MB**: Call `import_leads_from_csv` with `len(csv_bytes) > 10*1024*1024`. Assert `HTTPException(422)` from the router guard. (Test the router guard by constructing a large bytes object without a real HTTP call.)

10. **Flag off**: `object.__setattr__(S, "leads_enabled", False)`. Call `import_leads_from_csv` directly. Assert `HTTPException(503)`.

11. **Invalid `record_type`**: Call with `record_type="opportunity"`. Assert `HTTPException(422)`.

12. **Invalid `lead_source`**: Row with `lead_source="unknown_value"`. Assert row appears in `errors` with a Pydantic validation reason; other rows imported.

13. **Bad phone normalization**: Row with `phone="not-a-phone"`. Assert the row is still imported (phone stored as `None`), no error entry for this row, `imported` incremented.

14. **UTF-8 BOM handling**: Prepend `b"\xef\xbb\xbf"` to an otherwise valid CSV. Assert the import succeeds and the `email` column is correctly identified (BOM stripped by `"utf-8-sig"` codec).

15. **Audit event emitted**: Patch `app.services.leads_import.audit_event` with a mock. Run a successful import. Assert it was called once with `event="lead_import.completed"`, `imported > 0`.

16. **CSV injection sanitization**: Row with `email="normal@x.com"`, `first_name="=CMD(whoami)"`. Assert the stored `first_name` is `"'=CMD(whoami)"` (prefixed apostrophe).

## 10. Open Questions / Assumptions

1. **`find_prospect_by_email` function name and GSI scope**: LED-007's spec defines `find_prospect_by_email` as a separate helper that queries GSI4 filtered to `PROSPECT#` rows. This spec assumes that function exists and is importable from `app/services/leads`. If LED-007 merges `find_lead_by_email` and `find_prospect_by_email` into a single helper with a `record_type` param, LED-008's duplicate-detection block must be adjusted accordingly.

2. **Async vs. sync `create_lead` call path**: The current spec uses `await asyncio.to_thread(import_leads_from_csv, ...)` so that the entire import loop runs on a thread pool thread, keeping the event loop unblocked. This means `create_lead` is called synchronously from within the thread. If a future refactor makes `create_lead` itself async (e.g., to use `aioboto3`), the thread-dispatch pattern would need to be replaced with a direct `await create_lead(...)` chain.

3. **Partial-success HTTP status**: The spec returns `200 OK` even when some rows failed. An alternative is `207 Multi-Status` (used by WebDAV). The project has no existing 207 usage; `200 OK` with a structured `errors` list matches the pattern used by similar bulk endpoints in SuiteCRM and Salesforce. This is assumed acceptable but can be changed by the implementing engineer without spec impact.

4. **`_sanitize_csv_field` import visibility**: `_sanitize_csv_field` is a private function (underscore prefix) in `app/services/csv_export.py`. Importing a private symbol across service files is a code smell. If the implementing engineer prefers, they can copy the 5-line function verbatim into `leads_import.py` with a comment citing the source. The key constraint is no forking of logic — if the original function changes, `leads_import.py` should update accordingly. A clean alternative is to move `_sanitize_csv_field` to a `app/core/csv_utils.py` utility module, but that requires an additional small refactor outside LED-008's scope.

5. **Column name case sensitivity**: The spec requires exact lowercase column names. If ops teams report Excel-generated CSVs failing because Excel capitalizes headers (`Email`, `First_Name`), a case-fold normalization of `reader.fieldnames` is a one-line fix. This is deferred to a bug-fix ticket rather than baked into the MVP spec.
