# EML-002 — Admin outbound email settings (from-address, SES/SMTP config, audit log)

**Ticket type:** Feature  
**Priority:** P1  
**Estimate:** 2d  
**Feature flag:** `ADMIN_EMAIL_SETTINGS_ENABLED` (default `false`)

---

## 1. Summary & Goal

Add a runtime-editable, ROOT-only admin endpoint for global outbound email settings so that operators can update the sender address, toggle SES, and reserve an SMTP slot — all without a redeploy. The effective `from_email` used by `send_alert_email` is determined at call time by reading a single-row DynamoDB config item; when no override row exists the platform falls back to `S.alerts_from_email` / `S.alerts_email_enabled` exactly as today. All existing callers and behaviour are byte-for-byte unchanged with the feature flag off.

The design mirrors the `billing_config` pattern already in production: a `CONFIG` / `GLOBAL` single-item table that is read on demand, cached in process for a short TTL, and written only by privileged roles with a full audit trail. The only new externally visible surfaces are three endpoints appended to the existing `app/routers/admin_email.py` router plus a thin service module and one DynamoDB table.

## 3. Data Model

### New DynamoDB table: `email_settings`

**Table name:** `email_settings` (controlled by new settings field `email_settings_table_name`, default `"email_settings"`).

**Key schema:** PK=`pk` (S), SK=`sk` (S). No GSIs — this is a single-row global config table. No `attr_types` overrides needed because there are no numeric GSI sort keys.

**Single config row:**

| Attribute | Type | Notes |
|-----------|------|-------|
| `pk` | S | Always `"CONFIG"` |
| `sk` | S | Always `"GLOBAL"` |
| `from_email` | S | Validated via `normalize_email`; overrides `S.alerts_from_email` when set |
| `reply_to_email` | S (optional) | Raw RFC-5321 address; set to `""` to clear |
| `ses_enabled` | BOOL | Overrides `S.alerts_email_enabled` when row exists |
| `smtp_enabled` | BOOL | Reserved; not yet wired to outbound path; stored for EML-003 SMTP future work |
| `updated_at` | N | `now_ts()` integer Unix seconds |
| `updated_by` | S | `actor.sub` (ROOT user who performed the PATCH) |

**DynamoDB table definition** (to be added to `scripts/local-ddb-init.py` after the `billing_config` entry at line 78):


No `attr_types` override is needed because `updated_at` is only stored as a plain attribute, not a GSI sort key.

**Tables dataclass** (`app/core/tables.py`): add field `email_settings: Any` to the `Tables` dataclass after `billing_config` (line 82), and wire it in the `T = Tables(...)` constructor after line 334:

## 4. API / Service Design

### 4.1 New service: `app/services/email_settings.py`

```python
def get_email_settings() -> dict:
    """
    Return effective email settings.
    Reads CONFIG/GLOBAL from T.email_settings.
    Falls back to S.alerts_from_email / S.alerts_email_enabled when row absent
    or on any DDB error (best-effort; never raises).
    Returns a dict matching EmailSettingsOut field names.
    """

def update_email_settings(
    actor_sub: str,
    *,
    from_email: str | None = None,
    reply_to_email: str | None = None,
    ses_enabled: bool | None = None,
    smtp_enabled: bool | None = None,
) -> dict:
    """
    Merge-patch CONFIG/GLOBAL in T.email_settings, then call
    audit_event("email_settings_updated", actor_sub, from_email=..., ses_enabled=...).
    Returns the updated EmailSettingsOut dict.
    Raises HTTPException(400) if from_email is present and fails normalize_email.
    """
```

**In-process cache:** `get_email_settings` maintains a module-level `_CACHE: dict | None = None` and `_CACHE_TS: int = 0`. Cached for `S.email_settings_cache_ttl_seconds` (default 60 s). Cache is invalidated eagerly in `update_email_settings` by setting `_CACHE = None`. This mirrors the `billing_config` service's per-process caching strategy and avoids a DDB round-trip on every outbound email.

**Wiring into `send_alert_email`** (`app/services/alerts.py:459`): after the `if S.dev_mode` branch (line 462) and before the `if not S.alerts_email_enabled` guard (line 469), insert a best-effort read:

```python
# EML-002: read runtime override (best-effort; fall back to S on error)
_from_email = S.alerts_from_email
_ses_enabled = S.alerts_email_enabled
if S.admin_email_settings_enabled:
    try:
        from app.services.email_settings import get_email_settings as _ges
        _cfg = _ges()
        if _cfg.get("from_email"):
            _from_email = _cfg["from_email"]
        _ses_enabled = _cfg.get("ses_enabled", _ses_enabled)
    except Exception:
        pass
if not _ses_enabled or not _from_email:
    return
# ... rest of SES send using _from_email instead of S.alerts_from_email
```

The import is a lazy local import to avoid a circular dependency at module load time (same pattern as `app/services/instance_monitoring.py`'s `_record_timeline` helper documented in CLAUDE.md).

### 4.2 New Pydantic models (add to `app/models.py`)

```python
class EmailSettingsOut(BaseModel):
    from_email: str
    reply_to_email: Optional[str] = None
    ses_enabled: bool
    smtp_enabled: bool
    updated_at: Optional[int] = None
    updated_by: Optional[str] = None
    source: str  # "ddb_override" | "env_fallback"

class EmailSettingsUpdate(BaseModel):
    from_email: Optional[str] = None
    reply_to_email: Optional[str] = None
    ses_enabled: Optional[bool] = None
    smtp_enabled: Optional[bool] = None
```

The `source` field in `EmailSettingsOut` is informational only — it tells callers whether the returned values come from the DDB override row or from the env-var defaults. It is never stored in DDB.

### 4.3 New endpoints (append to `app/routers/admin_email.py` after line 203)

All three endpoints are gated by `S.admin_email_settings_enabled`; when the flag is off they raise `HTTPException(503, "Email settings management not enabled")`.

---

**`GET /ui/admin/email/settings`**

```
Auth:    require_admin_or_root
Returns: EmailSettingsOut
```

Calls `email_settings.get_email_settings()`. Returns the cached effective config (from DDB or env fallback). Non-admin callers receive 403 via `require_admin_or_root`.

---

**`PATCH /ui/admin/email/settings`**

```
Auth:    require_root   (ROOT only — writing SES config is privileged)
Body:    EmailSettingsUpdate  (all fields optional; absent = no change)
Returns: EmailSettingsOut
```

Calls `email_settings.update_email_settings(actor.sub, **payload.model_dump(exclude_none=True))`. Validates `from_email` via `normalize_email` inside the service (returns 400 on invalid format). Non-root admins receive 403. CSRF must be enforced explicitly: use `require_root_csrf` (or `Depends(enforce_cookie_csrf)` alongside `Depends(require_root)`) — there is no global CSRF middleware; enforcement is per-endpoint via the `enforce_cookie_csrf` dependency function (`app/auth/policy.py:71`). Other write endpoints in the codebase use `require_admin_or_root_csrf` for the same purpose (e.g. `app/routers/admin_notifications.py`).

---

**`GET /ui/admin/email/settings/audit`**

```
Auth:    require_admin_or_root
Query:   limit: int = Query(default=50, ge=1, le=200)
Returns: {"items": list[dict], "count": int}
```

Queries `T.alerts` for the sentinel actor `user_sub = "system_email_settings"` (the actor sub written by `audit_event` in `update_email_settings`). Uses `T.alerts.query(KeyConditionExpression=Key("user_sub").eq("system_email_settings"), ScanIndexForward=False, Limit=limit)` to return the most recent audit events newest-first. Items include `from_email`, `ses_enabled`, `updated_by`, and `ts` from the alert's `details` map.

Rationale for sentinel sub: `audit_event` stores rows keyed on `user_sub`. Using a fixed sentinel `"system_email_settings"` rather than the actor's own sub allows querying a bounded set of rows without scanning the whole alerts table. `updated_by` in the details map preserves the actual actor identity for display.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag off — complete isolation

When `S.admin_email_settings_enabled` is `false` (default):
- The three new endpoints return 503.
- The lazy `get_email_settings` import inside `send_alert_email` is never reached; the outer `if S.admin_email_settings_enabled:` guard prevents the import.
- `T.email_settings` is still registered in `Tables` and the table is created by `local-ddb-init.py` unconditionally (same as other tables), but no data is read or written.
- The existing `S.alerts_from_email` / `S.alerts_email_enabled` env-var behaviour is unchanged byte-for-byte.

### 5.2 DDB row absent (first run)

`get_email_settings` calls `T.email_settings.get_item(Key={"pk": "CONFIG", "sk": "GLOBAL"})`. When `"Item"` is absent the function returns:

```python
{
    "from_email": S.alerts_from_email,
    "reply_to_email": None,
    "ses_enabled": S.alerts_email_enabled,
    "smtp_enabled": False,
    "updated_at": None,
    "updated_by": None,
    "source": "env_fallback",
}
```

This means `GET /ui/admin/email/settings` is immediately usable on a fresh deployment without any PATCH having been called first.

### 5.3 DDB error during send

`send_alert_email` wraps the `get_email_settings` call in `try/except Exception`. On any DDB error (table missing, network timeout, throttle) the function falls back silently to `S.alerts_from_email`. This is a deliberate best-effort design: a config-table outage must never prevent alert emails from being sent.

### 5.4 Partial PATCH

`EmailSettingsUpdate` uses `Optional` for every field. `update_email_settings` performs a read-modify-write: it calls `get_email_settings()` to fetch the current row (or env defaults), merges only the non-None fields from the incoming update, then calls `T.email_settings.put_item` with the complete merged item. This avoids DDB `UpdateExpression` complexity and ensures the row is always well-formed.

### 5.5 `from_email` validation

`normalize_email` (normalize.py:60) strips and lowercases the string and raises `HTTPException(400, "Invalid email")` if `@` is absent or length exceeds 254. This HTTPException propagates unchanged to the caller (FastAPI serialises it as a 400 JSON response). No additional domain or MX validation is performed, consistent with how the rest of the platform handles email input.

### 5.6 Clearing `reply_to_email`

To clear a previously set `reply_to_email`, the operator sends `PATCH` with `{"reply_to_email": ""}`. The service stores `""` in DDB and `get_email_settings` returns `reply_to_email: None` when the stored value is `""` (coerced to `None` on read for API cleanliness). When the SES `send_email` call is extended to honour `reply_to_email`, it should skip the `ReplyToAddresses` key when the value is falsy.

### 5.7 `smtp_enabled` reservation

`smtp_enabled` is stored but not yet wired into `send_alert_email`. It is reserved for the EML-003 per-user SMTP account path and exposed in the API now so that EML-003 implementors can read it without a schema migration. A value of `true` with no corresponding SMTP config has no effect.

### 5.8 `ses_enabled` override semantics

The DDB `ses_enabled` field is an override, not a pure replacement. The logic in `send_alert_email` is:
- If the DDB row is present: use `row["ses_enabled"]`.
- If the DDB row is absent (env fallback): use `S.alerts_email_enabled`.

Setting `ses_enabled = false` via PATCH disables SES outbound globally at runtime without needing to change the env var.

### 5.9 Audit event contents

`audit_event("email_settings_updated", "system_email_settings", from_email=..., ses_enabled=..., smtp_enabled=..., reply_to_email=..., updated_by=actor_sub)` is called after every successful `put_item`. The `from_email` value is stored in the audit payload as-is (already validated). No credentials are ever stored in audit rows.

### 5.10 Concurrency / last-write-wins

The PATCH endpoint uses `put_item` (overwrite). There is no optimistic locking. Concurrent writes from two ROOT sessions resolve by last-write-wins. This is acceptable because only ROOT users can PATCH (≤ 2 concurrent principals in practice) and the config changes are infrequent administrative operations. Future iterations can add a `version` conditional if needed.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**No dev-mode branch.** The service reads and writes the `email_settings` DDB table identically in dev (DynamoDB Local on port 8001) and prod (real DynamoDB). The existing dev-mode check in `send_alert_email` (line 462) returns before the EML-002 override read is reached, so in dev mode no DDB read occurs — preserving the dev email log path unchanged. This is not a code divergence; it is the natural result of the early-return dev-mode guard already present.

**Idempotency.** `PATCH` with the same payload twice produces the same DDB row and the same audit event (two rows in `T.alerts`, one per call). `GET` is naturally idempotent.

**Auth chain.** `PATCH` requires `require_root` (policy.py:63) — the strictest auth level. `GET /settings` and `GET /settings/audit` require `require_admin_or_root` (policy.py:67) — read-only ops visible to ADMIN+. CSRF enforcement applies to all cookie-auth non-GET requests via the standard middleware path.

**Sensitive data.** The `from_email` value is a non-secret address; no credentials are stored in this table. There is no KMS encryption requirement (unlike EML-003 SMTP passwords).

**Input length limits.** `from_email` is validated by `normalize_email` (max 254 chars). `reply_to_email` is stored at most 254 chars (the service truncates to 254 before storing). No other fields are user-supplied text.

## 8. Backward Compatibility & Migration

### Zero migration required

- With `ADMIN_EMAIL_SETTINGS_ENABLED=0` (default), no code path is changed. The `email_settings` DDB table is created empty by `local-ddb-init.py` but never read or written.
- Existing `S.alerts_from_email` / `S.alerts_email_enabled` env-vars continue to function as the sole source of truth until an operator explicitly calls `PATCH /ui/admin/email/settings`.
- All existing callers of `send_alert_email` — `app/services/cart_reminders.py`, the alert fanout loop at `alerts.py:766/778/804`, and the planned `MKT-009` send path — continue to receive the effective from-address transparently. No call-site changes needed.

### Enabling the flag in production

1. Deploy the code (flag still off).
2. `local-ddb-init.py` is re-run at deploy time; it creates the `email_settings` table (idempotent — `_ensure_table` at `scripts/local-ddb-init.py:2534` already handles pre-existing tables by checking `list_tables` before creating).
3. Set `ADMIN_EMAIL_SETTINGS_ENABLED=1` in the env and restart.
4. The config table starts empty; `GET /ui/admin/email/settings` returns `source: "env_fallback"` until an operator issues the first PATCH.

### Rollback

Setting `ADMIN_EMAIL_SETTINGS_ENABLED=0` and restarting immediately reverts to pure env-var behaviour. The `email_settings` DDB row is not deleted; it is simply ignored.

## 10. Open Questions / Assumptions

1. **`reply_to_email` in SES call.** The current `send_alert_email` (alerts.py:474-477) does not pass `ReplyToAddresses` to SES. Wiring `reply_to_email` into the SES call is deferred until EML-001 (which also modifies the SES call for HTML body) lands first, per the EML-002 dependency note. The field is stored and returned in `EmailSettingsOut` as a signal to operators that it is intended for future use.

2. **Multi-process cache invalidation.** The in-process `_CACHE` is per-worker. With `--workers 1` in dev (CLAUDE.md note), this is a non-issue. In prod with multiple workers, a PATCH on worker A does not invalidate worker B's cache until the TTL expires (up to 60 s). This is accepted as a known limitation for an administrative config endpoint with infrequent writes. If sub-minute consistency is required in a future iteration, the cache can be backed by a DDB conditional-read with `ConsistentRead=True` on every call.

3. **Table name override in tests.** Tests use `object.__setattr__(S, "email_settings_table_name", moto_table_name)` to point `T.email_settings` at the moto-created table. This is the same pattern used across all INFRA-related tests documented in CLAUDE.md.

4. **`smtp_enabled` wiring.** When EML-003 (per-user SMTP) is implemented, the `smtp_enabled` flag should be read by the send path to determine whether user-level SMTP is permissible as an alternative to platform SES. The schema is intentionally reserved here but not wired.

5. **Assumption:** `require_root` is already exported from `app/auth/policy.py` (confirmed at policy.py:63). No new auth dependency needs to be introduced.
