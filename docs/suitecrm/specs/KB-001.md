## 1. Summary & Goal

KB-001 is pure infrastructure scaffolding for the Knowledge Base (KB) module. It delivers three things and nothing else:

1. A top-level feature flag `S.knowledge_base_enabled` (env `KNOWLEDGE_BASE_ENABLED`, default `False`) that gates every downstream KB ticket.
2. Four new settings keys for table names, S3 bucket, S3 prefix, and max attachment size.
3. Two additional GSIs (`ByAuthor` and `ByTag`) appended to the `crm_kb_articles` table definition that CAS-001 introduced, plus a `T.kb_articles` table handle wired into `app/core/tables.py`.

No router, service, background worker, model, or UI change is introduced. When `KNOWLEDGE_BASE_ENABLED` is absent or `"0"`, the platform is byte-for-byte identical to today: no new routes exist, no workers start, and no existing table, service, or endpoint is touched. Every downstream KB ticket (KB-002 through KB-012) depends on this ticket.

## 3. Data Model

### 3.1 Existing crm_kb_articles table (created by CAS-001)

```
Table: crm_kb_articles   (CAS-001 creates this)
  Hash key:  pk   (S)   — "ARTICLE#{article_id}" for article META rows
  Sort key:  sk   (S)   — "META" for article META rows; other SK prefixes
                           used by later tickets (ATTACHMENT#, RATING#, etc.)
  GSI ByCategory: PK=category (S), SK=published_at (N)
  GSI ByStatus:   PK=status   (S), SK=published_at (N)
  attr_types: {"published_at": "N"}
```

### 3.2 Additional GSIs added by KB-001

KB-001 appends two GSIs to the same `crm_kb_articles` `TableDef`:

```
GSI ByAuthor:
  partition_key: author_sub  (S)
  sort_key:      created_at  (N)
  Purpose: admin listing of own articles, e.g. GET /kb/my-articles

GSI ByTag:
  partition_key: tag         (S)
  sort_key:      created_at  (N)
  Purpose: tag-indexed article queries (KB-007 writes TAG#{tag}/ARTICLE#{id}
           rows; ByTag is not the primary access path for those but enables
           sorted tag-scoped scans)
```

Both `created_at` and `published_at` are integer Unix timestamps produced by `now_ts()` (`app/core/time.py`). Per the CLAUDE.md gotcha: "If a GSI sort key is a number, the `TableDef` in `scripts/local-ddb-init.py` must include `attr_types={"<key>": "N"}`." The combined `attr_types` declaration for the table is:

```python
attr_types={"published_at": "N", "created_at": "N"}
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off guarantees

When `KNOWLEDGE_BASE_ENABLED` is unset or `"0"`:
- `S.knowledge_base_enabled` evaluates to `False`.
- No KB routes are registered (they are added by KB-002 through KB-012, each of which checks the flag before registering).
- No KB background workers start (same pattern: each worker guards itself with `if not S.knowledge_base_enabled: return`).
- `T.kb_articles` is initialized at module import but is never called because no code path leads to it when the flag is off.
- `app/routers/tickets.py`, `app/services/tickets.py`, and all other existing files are byte-for-byte unchanged.

### 5.2 T.kb_articles is always initialized (even when flag is off)

Like every other `T.*` handle, `T.kb_articles` is initialized unconditionally at import time by `_safe_table(S.kb_articles_table)`. This is intentional: the `_safe_table` call does not make a network request; it only wraps the boto3 `Table` object with the `_FloatSafeTable` proxy (`app/core/tables.py:65–66`). The actual DynamoDB connection is lazy. This means smoke tests that import `T` will not fail even if the table does not yet exist in DynamoDB Local.

### 5.3 CAS-001 prerequisite: migration order matters

`scripts/local-ddb-init.py` is idempotent: it calls `create_table` on first run and ignores `ResourceInUseException` on subsequent runs (the script handles both `create_table` and `update_table` paths). However, the `ByAuthor` and `ByTag` GSIs can only be added to a table that already exists. In a fresh environment, `just restart` runs `local-ddb-init.py` from scratch and creates the table with all four GSIs in a single `create_table` call — no ordering issue. In an environment where CAS-001 was applied first and the table already exists with only two GSIs, `local-ddb-init.py` must issue `update_table` calls to add the two new GSIs. The script's `_ensure_table` helper (or equivalent) must handle this additive GSI update idempotently.

> **KNOWN BUG — `_ensure_table` update path ignores `attr_types`** (`scripts/local-ddb-init.py:2544–2548`):  
> When `_ensure_table` adds a missing GSI via `update_table`, it builds the `AttributeDefinitions` array by hardcoding `"AttributeType": "S"` for every new attribute (lines 2546 and 2548), without consulting `table.attr_types`. For `ByAuthor` (SK=`created_at`, N) and `ByTag` (SK=`created_at`, N), if `created_at` is not already registered on the table, `_ensure_table` will declare it as String — causing `ValidationException` on any range query against these GSIs in a persistent dev environment. The `create_table` path (fresh restart) is correct because it uses `_attribute_definitions()` which does apply `attr_types`. **Workaround**: always use `just restart` (cold-start DynamoDB Local) rather than incremental table updates when adding these GSIs. **Fix (out of KB-001 scope)**: the `_ensure_table` update loop should resolve the `AttributeType` from `table.attr_types.get(key, "S")` instead of hardcoding `"S"`.

### 5.4 attr_types must cover all numeric GSI sort keys

Per CLAUDE.md: "If a GSI sort key is a number, the `TableDef` must include `attr_types={"<key>": "N"}`." Both `published_at` (CAS-001) and `created_at` (KB-001) are integer Unix timestamps. The final `attr_types` dict must contain both: `{"published_at": "N", "created_at": "N"}`. Omitting either will cause `ValidationException: Type mismatch for key published_at` (or `created_at`) at query time when later tickets query those GSIs.

### 5.5 kb_articles_table vs crm_kb_articles_table

Two settings now point to the same physical table: `S.crm_kb_articles_table` (CAS-001, used by CAS-015's case-deflection hook in `app/routers/tickets.py`) and `S.kb_articles_table` (KB-001, used by all KB-002..KB-012 service code). They share the same default value (`"crm_kb_articles"`). Operators who want to point them at different tables (e.g., isolated test environments) can do so via env vars. The `T.kb_articles` handle uses `S.kb_articles_table`; any CAS-015 code that already uses `S.crm_kb_articles_table` is not changed.

### 5.6 S3 settings are declaration-only

`S.kb_attachments_bucket`, `S.kb_attachments_s3_prefix`, and `S.kb_attachment_max_bytes` are declared in KB-001 but not consumed until KB-003 adds the attachment upload/download endpoints. Their presence in settings has no runtime effect until KB-003 is merged. The defaults (`"local-uploads"`, `"kb-attachments/"`, `20 MiB`) match the S3 mock bucket already created for the dev stack (`app/core/dev_s3.py`) and the KYC partner API attachment pattern (`app/routers/kyc_partner_api.py`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

KB-001 is pure configuration scaffolding — there is no business logic, no network call, and no conditional branching on `S.dev_mode`. The three file changes (settings, DDB init, tables.py) are identical in dev and prod. No `if S.dev_mode` branch is introduced.

The S3 defaults (`"local-uploads"` bucket, `"kb-attachments/"` prefix) are intentionally identical in dev (in-process moto S3 via `app/core/dev_s3.py`) and prod (real S3). KB-003 will use the same `s3_client()` factory (`app/core/aws_clients.s3_client`) in both environments, following the precedent set by `app/services/kyc_partner_api.py:_store_document_bytes`.

### 7.2 Idempotency

`scripts/local-ddb-init.py` handles both first-run (table does not exist → `create_table` with all GSIs) and subsequent runs (table exists → `update_table` to add missing GSIs). The `_ensure_table` helper will not error if the GSI already exists — the `missing` list computation at line 2542 skips already-present GSIs.

Because `attr_types` is a map, not a list, adding `"created_at": "N"` to an existing table that already has a `"published_at": "N"` declaration is additive and safe at the `TableDef` level.

> **Partial idempotency gap**: The `create_table` path (fresh restart) is fully correct. The `update_table` path (persistent env) has the type-loss bug documented in §5.3 — new numeric GSI sort keys are registered as String. This does not affect fresh-restart (CI/CD) environments. See §5.3 for the workaround.

### 7.3 Security: flag is read-only at runtime

`S` is a frozen dataclass (`@dataclass(frozen=True)` at `app/core/settings.py:6`). `knowledge_base_enabled` cannot be mutated at runtime. Toggling the flag requires a process restart, which is the correct and safe behavior for a feature flag of this kind.

### 7.4 No new attack surface

KB-001 introduces no endpoints, no authentication paths, and no data flows. The only change visible to an attacker is the addition of two GSI definitions to a DynamoDB table — these are server-internal structures with no external exposure.

## 8. Backward Compatibility & Migration

### 8.1 Existing tables unchanged

`T.tickets` (`app/core/tables.py:392`) and all other existing table handles are unchanged. The `crm_kb_articles` table definition is extended (two new GSIs added), not replaced.

### 8.2 Zero-downtime GSI addition

Adding a GSI to an existing DynamoDB table is a non-blocking, additive operation. In prod, DynamoDB will backfill the GSI asynchronously; queries against the new GSI must not be issued until the GSI reaches `ACTIVE` status. All code that uses `ByAuthor` and `ByTag` is introduced in later tickets (KB-007 and KB-010), at which point the GSIs will have long been active. No migration script is required.

### 8.3 No data migration

No existing rows in `crm_kb_articles` need to be backfilled. The `author_sub` and `created_at` fields referenced by the new GSIs are already written by CAS-015's `create_article` function on every new article row. DynamoDB will project existing rows into the new GSIs automatically during backfill.

### 8.4 Settings backward compatibility

Adding new fields to the `Settings` frozen dataclass is additive. Existing code that imports `S` and does not reference the new fields is unaffected. No `.env.local.example` changes are strictly required for the flag to remain off (the default is `"0"`), but adding `KNOWLEDGE_BASE_ENABLED=0` to `.env.local.example` with a comment is good practice.

### 8.5 crm_kb_articles_table vs kb_articles_table coexistence

CAS-015 service code that was written to use `S.crm_kb_articles_table` continues to work unchanged. KB-001 does not rename or remove that setting. The dual-setting situation (two env vars, same default table name) is intentional and matches precedent: for example, `S.ddb_sessions_table` and `S.ui_session_cookie_name` both exist independently even though they're conceptually related.

## 10. Open Questions / Assumptions

1. **CAS-001 applied first**: This spec assumes CAS-001 has been applied and the `crm_kb_articles` table and `S.crm_kb_articles_table` setting exist. If KB-001 is applied to a repo where CAS-001 has not yet merged, `scripts/local-ddb-init.py` must include the full CAS-001 `TableDef` inline (with all four GSIs from the start). The safest approach is to merge CAS-001 before KB-001, as prescribed by the ticket source.

2. **CAS-015 applied first**: CAS-015 creates `app/services/kb_articles.py` and `app/routers/kb_articles.py`. KB-001 does not create or modify these files. If KB-001 is applied before CAS-015, the `T.kb_articles` handle exists but nothing imports it — which is fine (the handle is inert until consumed).

3. **`kb_articles_table` vs `crm_kb_articles_table`**: Two settings pointing to the same default table is a deliberate design choice documented in Section 8.5. If the team prefers a single canonical setting, `kb_articles_table` could simply alias `S.crm_kb_articles_table` — but that would require CAS-015 code to be updated to use the new alias, adding scope to CAS-015 retroactively. The dual-setting approach is cleaner as a forward-only migration.

4. **`ByTag` GSI vs direct query on TAG# PK**: KB-007 stores tag index rows as `PK=TAG#{tag}`, `SK=ARTICLE#{article_id}`. Because `TAG#{tag}` is the primary hash key of the table (not a GSI attribute), queries on it use the table's primary index directly — the `ByTag` GSI is not strictly needed for KB-007's main access pattern. The `ByTag` GSI is retained per the ticket source for sorted tag-scoped scans (ordered by `created_at`). If it proves unnecessary after KB-007 is implemented, it can be removed in a follow-up chore without affecting the primary data.

5. **`just restart` recreation vs additive update**: In a CI environment where DynamoDB Local is cold-started from scratch, `create_table` with all four GSIs succeeds in one call. In a persistent dev environment, `update_table` must be called twice (once per new GSI) because DynamoDB Local does not support adding multiple GSIs in a single `update_table` call. The `_ensure_table` helper in `scripts/local-ddb-init.py` should handle this by adding GSIs one at a time.
