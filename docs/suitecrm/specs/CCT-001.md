# CCT-001 — Account industry and business metadata fields

**Type:** Feature | **Priority:** P1 | **Estimate:** 2d  
**Source:** `docs/suitecrm/CRM_CONTACTS_EXTRA_TICKETS.md` — CCT-001 section  
**Flag:** `PARTY_CRM_ORG_ACCOUNTS_ENABLED` (existing, from PTY-001)

---

## 1. Summary & Goal

SuiteCRM's Accounts module stores rich business metadata on organisation records: industry vertical, website URL, primary phone, employee headcount, and annual revenue. The testlogon platform has a planned B2B org-account surface (PTY-001 through PTY-012) that currently models an organisation as little more than a name and status. This ticket bridges that gap by adding five additive fields to the `CrmOrgAccountOut` response model and the underlying DynamoDB META row, and introducing a `PATCH /ui/party/orgs/{org_party_id}` endpoint that lets an ORG_ADMIN actor update any subset of those fields.

The goal is exact SuiteCRM parity for the five standard Account business-profile fields — `industry`, `website`, `phone`, `employee_count`, `annual_revenue_cents` — while remaining byte-for-byte backward-compatible when the flag is off and making zero changes to the existing party-table schema or any other subsystem.

## 3. Data Model

### 3.1 DynamoDB table — no schema changes

CCT-001 writes **only to the existing** `party` table (defined by PTY-002 at `docs/ofbiz/specs/PTY-002.md:70–113`). No new tables, no new GSIs, no changes to `scripts/local-ddb-init.py`, and no new `attr_types` entries are required.

The five new fields are stored as plain top-level attributes on the PARTY_GROUP META row:

| Attribute | DynamoDB type | Constraints |
|---|---|---|
| `industry` | String (S) | Value from `INDUSTRY_CHOICES`; absent when `None` |
| `website` | String (S) | max 2048 chars; absent when `None` |
| `phone` | String (S) | E.164 normalized; absent when `None` |
| `employee_count` | Number (N) | non-negative integer; absent when `None` |
| `annual_revenue_cents` | Number (N) | non-negative integer (cents); absent when `None` |

**Absent-when-None rule:** Optional fields with value `None` are never written to DynamoDB (no `NULL` attribute type is stored). The `update_org_account` function uses a dynamic `UpdateExpression` that only sets attributes present in the caller's payload. Removing a field (setting it to `null` in the request) sends an explicit `REMOVE` expression for that attribute. This keeps item sizes minimal and avoids `NULL` entries that complicate GSI projections.

### 3.2 Extended PARTY_GROUP META row shape

After CCT-001, a fully-populated META row contains all existing PTY-008 attributes plus the five new ones:

```json
{
  "PK":                   "PARTY#{org_party_id}",
  "SK":                   "META",
  "party_id":             "{org_party_id}",
  "party_type":           "PARTY_GROUP",
  "status":               "ACTIVE",
  "name":                 "Acme Corp",
  "industry":             "Technology",
  "website":              "https://acme.example.com",
  "phone":                "+14155551234",
  "employee_count":       250,
  "annual_revenue_cents": 5000000000,
  "created_at":           1749200000,
  "updated_at":           1749200000,
  "type":                 "TYPE#PARTY_GROUP",
  "GSI_CREATED":          "TYPE#PARTY_GROUP"
}
```

No existing attribute is modified or renamed. The `type` and `GSI_CREATED` keys used by the `GSI_CREATED` index remain untouched; `created_at` (numeric) retains the `attr_types={"created_at": "N"}` declaration added by PTY-002.

#### `CrmOrgAccountUpdateIn` — new model for the PATCH endpoint

```python
class CrmOrgAccountUpdateIn(BaseModel):
    """PATCH body for updating org account business metadata (CCT-001).
    All fields are optional. Only supplied fields are written; omitted fields
    are left unchanged. Explicitly passing null removes the stored value.
    """
    industry:             Optional[str] = None
    website:              Optional[str] = Field(default=None, max_length=2048)
    phone:                Optional[str] = None
    employee_count:       Optional[int] = Field(default=None, ge=0)
    annual_revenue_cents: Optional[int] = Field(default=None, ge=0)

    @field_validator("industry")
    @classmethod
    def _validate_industry(cls, v: Optional[str]) -> Optional[str]:
        if v is None:
            return None
        from app.services.party import INDUSTRY_CHOICES  # local import avoids circular dep
        if v not in INDUSTRY_CHOICES:
            raise ValueError(f"Unknown industry '{v}'. Valid choices: {sorted(INDUSTRY_CHOICES)}")
        return v

    @field_validator("website")
    @classmethod
    def _validate_website(cls, v: Optional[str]) -> Optional[str]:
        if v is None:
            return None
        if not re.match(r"^https?://", v):
            raise ValueError("website must start with http:// or https://")
        return v

    @field_validator("phone")
    @classmethod
    def _validate_phone(cls, v: Optional[str]) -> Optional[str]:
        if v is None:
            return None
        cleaned = v.strip()
        if not cleaned:
            return None
        try:
            return normalize_phone(cleaned)   # normalize_phone imported at app/models.py:21
        except Exception as exc:
            raise ValueError("Invalid phone") from exc
```

Note: `normalize_phone` is already imported at `app/models.py:21`; no new import is needed. The `INDUSTRY_CHOICES` local import avoids a module-level circular dependency (models → party → models). The same validator logic is applied to the `industry`, `website`, and `phone` fields on `CrmCreateOrgAccountIn` by the same three `field_validator` methods (added to that class as well).

**PATCH semantics — field presence discrimination:** Because all fields are optional and `None` can mean either "caller did not mention this field" (no-op) or "caller wants to clear this field" (REMOVE), the router uses a raw-dict check before Pydantic validation: it inspects `body.model_fields_set` to distinguish supplied-as-null (explicit clear) from absent (no-op). This is the same approach used by the Pydantic v2 partial-update pattern; `model_fields_set` returns the set of keys explicitly provided by the caller even when their value is `None`.

### 4.3 New service function `update_org_account`

Location: `app/services/party.py`, appended after `list_members` (PTY-008's last function).

```python
def update_org_account(
    org_party_id: str,
    actor_party_id: str,
    *,
    fields: dict,  # key → new value; value=None means REMOVE the attribute
) -> dict:
    """
    Update business metadata on a PARTY_GROUP META row.

    Args:
        org_party_id:  PK identity of the target org.
        actor_party_id: PERSON party of the calling user (resolved by router).
        fields:        Dict of field names → new values; a None value removes the attribute.

    Returns:
        The updated META row as a dict.

    Raises:
        HTTPException(404) if the org does not exist.
        HTTPException(403) if actor_party_id is not ORG_ADMIN on this org.
        HTTPException(400) if any field value fails domain validation.
    """
```

Step-by-step contract:

1. **Validate org exists:** `item = get_party(org_party_id)`. Raise `HTTPException(404, "org_not_found")` if absent or if `item["party_type"] != "PARTY_GROUP"`.

2. **Assert ORG_ADMIN:** call `_assert_org_admin(org_party_id, actor_party_id)`. Raises `HTTPException(403, "not_org_admin")` if the actor does not hold an owner/admin org_role on the target org.

3. **Build UpdateExpression:** iterate over `fields`. For each `(k, v)`:
   - If `v is not None`: append `#alias = :alias` to the SET clause.
   - If `v is None`: append `#alias` to the REMOVE clause.
   - Skip keys not in the allowed set `{"industry", "website", "phone", "employee_count", "annual_revenue_cents"}` (defense in depth; the router enforces the same).

4. **Always SET `updated_at`:** append `updated_at = :now` to the SET clause with `now = now_ts()`.

5. **Execute `T.party.update_item`:**
   ```python
   T.party.update_item(
       Key={"PK": f"PARTY#{org_party_id}", "SK": "META"},
       UpdateExpression=update_expr,
       ExpressionAttributeNames=name_map,
       ExpressionAttributeValues=val_map,
       ConditionExpression="attribute_exists(PK)",  # prevents phantom write
       ReturnValues="ALL_NEW",
   )
   ```
   The `ConditionExpression="attribute_exists(PK)"` guard is a safety net: if the org was deleted between step 1 and the write, `ConditionalCheckFailedException` is caught and re-raised as `HTTPException(404, "org_not_found")`.

6. **Emit audit event:**
   ```python
   audit_event(
       "party_org_account_updated",
       actor_party_id,
       None,
       org_party_id=org_party_id,
       updated_fields=list(fields.keys()),
   )
   ```

7. **Return** the `Attributes` dict from `ReturnValues="ALL_NEW"`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Unknown `industry` value

The `industry` field is validated against `INDUSTRY_CHOICES` by the `CrmOrgAccountUpdateIn._validate_industry` Pydantic validator. Pydantic raises `ValidationError` on an unknown string, which FastAPI converts to a `422 Unprocessable Entity` response with a body listing the valid choices. The service layer additionally checks `industry not in INDUSTRY_CHOICES` and raises `HTTPException(400, "unknown_industry")` as a defense-in-depth guard for direct service calls from tests. The router path sees only the Pydantic 422.

### 5.2 Malformed website

`_validate_website` checks `re.match(r"^https?://", v)`. Examples of rejection: `"acme.com"` (no scheme), `"ftp://acme.com"` (non-HTTP scheme), `""` (empty — accepted as `None` after the `if v is None` check, but the router should normalize an explicit empty string to `None` before passing to the model). The `max_length=2048` Field constraint prevents excessively long URLs before the regex runs.

### 5.3 Phone normalization

`normalize_phone` (`app/core/normalize.py:66–81`) normalizes to E.164: 10-digit US numbers gain a `+1` prefix; 11-digit numbers starting with `1` gain `+`; numbers already starting with `+` strip punctuation. An input like `"(415) 555-1234"` becomes `"+14155551234"`. Inputs that cannot be parsed (e.g. `"not-a-phone"`) cause the `try/except` wrapper to raise `ValueError("Invalid phone")`, returned to the caller as `422 Unprocessable Entity`.

### 5.4 Partial update — fields_set discrimination

`CrmOrgAccountUpdateIn` uses `model_fields_set` to distinguish `{"industry": null}` (explicit clear, REMOVE the attribute) from `{}` (field omitted entirely, no-op for `industry`). A PATCH body of `{"employee_count": 500}` updates only `employee_count` and `updated_at`; all other fields remain exactly as stored. A PATCH body of `{"industry": null}` removes the `industry` attribute from DynamoDB.

### 5.5 Non-ORG_ADMIN caller

`_assert_org_admin` reads the caller's `REL#GROUP_MEMBER#{org_party_id}` row first; if absent, falls back to `REL#OWNER#{org_party_id}`, and checks `org_role in {"org_admin", "owner"}` (`"admin"` is **not** a valid org_role here — corrected from earlier draft). A plain `member` role returns `HTTPException(403, "org_admin role required")`. An authenticated user with no relationship to the org at all also gets 403 (not 404) — the org's existence is confirmed before the role check, so the 403 reveals that the org exists; this is acceptable because the caller already knows the `org_party_id` from the URL they are patching.

### 5.6 Flag-off behavior

When `S.party_crm_org_accounts_enabled` is `False` (the default), `_check_org_flag()` raises `HTTPException(503, "party_crm_org_accounts feature not enabled")`. The DynamoDB table is never read or written. The `update_org_account` service function is never called. The five new fields remain `None` on any `CrmOrgAccountOut` returned by a flag-on read after a flag-off write (they were never stored).

### 5.7 Idempotent re-PATCH

Two concurrent PATCH requests for the same org apply their `update_item` calls in DynamoDB's last-writer-wins order. There is no version counter or optimistic concurrency on the META row for these metadata fields (the PTY-004 design does not add one). This is acceptable because the five fields are mutable business metadata, not state-machine status transitions that require conditional writes.

### 5.8 Decimal coercion from DynamoDB

boto3 returns DynamoDB Number attributes as `decimal.Decimal`. The projection helper (`§4.5`) coerces `employee_count` and `annual_revenue_cents` to `int` via explicit `int()` calls. `Decimal` values that are not integral (e.g. `Decimal("500.5")`) would be truncated; this is acceptable because these fields are only ever written as integers by the service layer.

### 5.9 `create_org_account` with no metadata

Calling `create_org_account("Acme Corp", owner_user_sub="usr_abc")` without any of the five fields is identical to the PTY-008 behavior. The five fields are absent from the DynamoDB item; the returned `CrmOrgAccountOut` carries `None` for all five. Existing PTY-012 tests are unaffected.

### 5.10 `employee_count` and `annual_revenue_cents` zero values

Both fields accept `ge=0` (Pydantic `Field`). `employee_count=0` (e.g. a pre-revenue startup with no headcount recorded) and `annual_revenue_cents=0` are stored as DynamoDB Number `0`, not removed. Callers must explicitly set these to `null` to remove them.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**No `dev_mode` branch.** The `update_org_account` service function performs the same `T.party.update_item` in both environments. In dev, `T.party` points to DynamoDB Local at `http://localhost:8001`; in prod, `T.party` points to AWS DynamoDB via the boto3 client. The code path is identical — no conditional on `S.dev_mode` is introduced.

**Phone normalization in both environments.** `normalize_phone` (`app/core/normalize.py:66–81`) runs identically in dev and prod. E.164 is a universal format with no environment-specific behavior.

**Audit events in both environments.** `audit_event` (`app/services/alerts.py:644`) writes to `T.alerts`. In dev, `T.alerts` is DynamoDB Local; in prod, it is AWS DynamoDB. No environment-conditional behavior.

**Idempotency.** The PATCH endpoint is idempotent: sending the same body twice updates `updated_at` on the second call but leaves all field values unchanged. The `ConditionExpression="attribute_exists(PK)"` guard prevents writing to a deleted org. No duplicate audit events are a concern (each PATCH emits exactly one audit event; there is no compare-and-swap that would suppress a second identical audit event, which is the correct behavior for mutable metadata updates).

**Security — privilege check ordering.** The service function validates org existence (step 1) before checking ORG_ADMIN (step 2). This ensures the 403 response does not inadvertently leak "org does not exist" vs "org exists but you are not admin". Since the PATCH URL already reveals the `org_party_id`, this ordering is acceptable; it matches the PTY-008 `add_member` ordering (`docs/ofbiz/specs/PTY-008.md:455–462`).

**Security — field allow-listing.** `update_org_account` ignores any key in `fields` that is not in the allowed set `{"industry", "website", "phone", "employee_count", "annual_revenue_cents"}`. This prevents a malicious caller from overwriting `name`, `status`, `party_type`, `created_at`, or GSI projection keys via a crafted PATCH body, even if a future refactor inadvertently passes a wider dict.

**Security — URL max-length.** `website` is bounded by `Field(max_length=2048)` to prevent oversized payloads from being persisted, consistent with the 2048-char DynamoDB String limit that becomes relevant for indexed projection keys. The `website` field is not indexed (no GSI), but the length cap protects against storage bloat.

**Additive only.** All five new fields carry `Optional[…] = None` defaults in `CrmOrgAccountOut`. Clients that parse the response today (PTY-012 consumers, E2E tests, frontend type stubs) will see five additional nullable JSON properties in the response. No previously present property is renamed, re-typed, or removed.

**`CrmCreateOrgAccountIn` extension.** The five new fields are added as optional with `None` defaults. Any caller that currently passes `{"name": "Acme Corp"}` continues to work unchanged; the new fields default to `None` and are omitted from the `put_item` via `if v is not None` filtering.

**PTY-012 router contract.** The `GET /ui/party/orgs/{id}` endpoint defined by PTY-012 returns `CrmOrgAccountOut`. After CCT-001, the same endpoint returns the same model with five additional nullable fields. No HTTP status code, URL, or header changes.

**Frontend type stubs.** PTY-013 adds TypeScript types for `CrmOrgAccountOut`. CCT-001 requires PTY-013 to be updated (or a CCT-001 frontend companion ticket created) to add the five optional fields to the TypeScript interface. The existing frontend code will not break — TypeScript optional fields with undefined values are safe — but editors will not suggest auto-complete for the new fields until the stubs are updated.

## 10. Open Questions / Assumptions

1. **`industry` picklist extensibility.** The `INDUSTRY_CHOICES` constant is a hardcoded `frozenset`. If operators need to define custom industries, a future ticket would need to either move the picklist to a DynamoDB config row or add an `OTHER` free-text escape hatch. For now, `"Other"` is included in the set.

2. **`annual_revenue_cents` display currency.** The field stores raw cents (integer) with no currency code. SuiteCRM stores revenue as a float with a separate currency field. A future ticket (likely a CCT follow-on) could add `annual_revenue_currency: Optional[str] = "USD"`. For CCT-001, USD-cents integer is sufficient and avoids floating-point representation hazards.

3. **`website` uniqueness.** No uniqueness constraint is enforced across org accounts. If two orgs claim the same website URL, both are allowed. Deduplication would be handled by CCT-004 (duplicate detection) which can include `website` as a signal.

4. **Phone on org vs. contact mech.** The PTY-007 contact-mech model already supports `PHONE` type contact mechs on any party. Storing `phone` as a flat attribute on the META row (as SuiteCRM does) is a convenience denormalization. Future tickets may need to decide whether the META `phone` and the contact-mech `PHONE` rows are kept in sync or treated as independent data.

5. **`_validate_industry` local import.** `CrmOrgAccountUpdateIn._validate_industry` uses a local import `from app.services.party import INDUSTRY_CHOICES` to avoid a module-level circular dependency (models → party imports models). If PTY-003 introduces the models before PTY-008 defines `INDUSTRY_CHOICES`, the local import defers the resolution to call time — which is correct. An alternative is to move `INDUSTRY_CHOICES` to a separate constants module (e.g. `app/services/party_constants.py`) to eliminate the deferred import; this is left as an implementation decision.
