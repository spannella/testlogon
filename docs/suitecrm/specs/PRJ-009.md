# PRJ-009 — Project status workflow with audit trail

**Type:** Feature  **Priority:** P1  **Estimate:** 1d  
**Area:** CRM Projects — `app/routers/crm_projects.py`, `app/services/crm_projects.py`  
**Flag:** `CRM_PROJECTS_ENABLED` (default `"0"`)

---

## 1. Summary & Goal

PRJ-009 enforces a typed status-transition graph on CRM projects, persists every
transition in the existing `alerts` audit table, exposes a `GET
/{project_id}/status-history` endpoint for inspecting the transition log, and sends
a best-effort completion email to the project owner(s) when a project reaches
`completed`.

Before this ticket, `update_crm_project` (PRJ-002) accepts any free-form `status`
string that passes Pydantic validation without enforcing legal state-machine
progressions. There is no audit record that captures who changed a status or when.
PRJ-009 closes both gaps without introducing any new DynamoDB table — it reuses
`T.alerts` (PK=`user_sub`, SK=`alert_id`, `scripts/local-ddb-init.py:61`) as the
audit store, and `send_alert_email` (`app/services/alerts.py:459`) as the email
transport.

## 3. Data Model

### 3.1 No new DynamoDB table

PRJ-009 stores audit records in the existing `alerts` table (PK=`user_sub`,
SK=`alert_id` where `alert_id = f"{ts:010d}#{uuid4().hex}"`).
`scripts/local-ddb-init.py:61`:

```
TableDef(_resolve_table_name(S.alerts_table_name, "alerts"), "user_sub", "alert_id")
```

The `event` field and the `details` map fields (`project_id`, `from_status`,
`to_status`) are stored as attributes on each row. No GSI is needed for the
status-history endpoint because the query key `user_sub = owner_sub` combined with a
`FilterExpression` on `event = "crm_project.status_changed" AND project_id = <id>`
is sufficient for the expected cardinality (a user will have at most hundreds of
project audit events, not millions). This matches the
`DDB FilterExpression doesn't reduce page size` guidance in CLAUDE.md by looping
`LastEvaluatedKey` until the page is full.

### 3.2 `CrmProjectStatus` and transition graph

These are defined in `app/models.py` (PRJ-002). PRJ-009 adds a new module-level
constant in `app/services/crm_projects.py`:

```python
_CRM_PROJECT_TRANSITIONS: dict[str, tuple[str, ...]] = {
    "draft":      ("in_review", "underway", "deferred"),
    "in_review":  ("underway", "draft", "deferred"),
    "underway":   ("completed", "in_review", "deferred"),
    "completed":  ("underway",),   # reopen only
    "deferred":   ("draft", "underway"),
}
```

### 3.3 Alert row schema for status-change events

Each status transition audit row written by `audit_event` has this shape in
`T.alerts`:

| Field          | Type   | Value                                      |
|----------------|--------|--------------------------------------------|
| `user_sub`     | S      | `owner_sub` of the project                 |
| `alert_id`     | S      | `"{ts:010d}#{uuid4().hex}"`                |
| `ts`           | N      | `now_ts()` (Unix seconds)                  |
| `event`        | S      | `"crm_project.status_changed"`             |
| `outcome`      | S      | `"info"`                                   |
| `title`        | S      | `"Project status changed"`                 |
| `details`      | M      | `{project_id, from_status, to_status, changed_by, project_name}` |

The `details` map is serialized by `write_alert` (`app/services/alerts.py:373–380`).
All values fit within the 512-char per-field cap.

**Modified function** — `update_crm_project`:

```python
def update_crm_project(
    owner_sub: str,
    project_id: str,
    *,
    name: Optional[str] = None,
    description: Optional[str] = None,
    status: Optional[str] = None,
    priority: Optional[int] = None,
    start_date: Optional[int] = None,
    end_date: Optional[int] = None,
    assigned_user_sub: Optional[str] = None,
    account_id: Optional[str] = None,
    changed_by: Optional[str] = None,

    ...
```

When `status` is provided and differs from the current value:
1. Fetch the current project via `get_crm_project(owner_sub, project_id)` — raises
   404 if not found.
2. Look up `allowed = _CRM_PROJECT_TRANSITIONS.get(current.status, ())`. If
   `status not in allowed`, raise `HTTPException(400, detail={"code":
   "invalid_status_transition", "from": current.status.value, "to": status})`.
3. Write the updated item to `T.crm_pm_projects` (same `update_item` pattern as
   PRJ-002).
4. Call `audit_event("crm_project.status_changed", owner_sub, None,
   project_id=project_id, from_status=current.status.value, to_status=status,
   changed_by=changed_by or owner_sub, project_name=current.name)` — reusing
   `app/services/alerts.audit_event` (`app/services/alerts.py:644`).
5. If `status == "completed"`, call `_notify_project_completed(owner_sub, project_id,
   current.name)` in a `try/except` block — failure must not roll back the status
   update.

**New helper** — `_notify_project_completed`:

```python
def _notify_project_completed(
    owner_sub: str,
    project_id: str,
    project_name: str,
) -> None:
    """Send completion email to all project members with role='owner'.
    Best-effort — any exception is swallowed."""
    from app.services.alerts import send_alert_email

    owner_emails: list[str] = _collect_owner_emails(owner_sub, project_id)
    if not owner_emails:
        return
    send_alert_email(
        owner_emails,
        subject=f"Project completed: {project_name}",
        body_text=(
            f"The project \"{project_name}\" has been marked as completed.\n\n"
            f"Project ID: {project_id}"
        ),
    )
```

**New helper** — `_collect_owner_emails`:

```python
def _collect_owner_emails(owner_sub: str, project_id: str) -> list[str]:
    """Query T.crm_pm_members for role='owner' rows and resolve email addresses.

    Returns a de-duplicated list of email strings. Never raises — returns []
    on any error.
    """
    from app.core.tables import T
    from boto3.dynamodb.conditions import Key, Attr
    try:
        resp = T.crm_pm_members.query(
            KeyConditionExpression=Key("PK").eq(f"PROJECT#{project_id}"),
            FilterExpression=Attr("role").eq("owner"),
        )
        subs = [item["user_sub"] for item in resp.get("Items", []) if item.get("user_sub")]
    except Exception:
        return []
    emails: list[str] = []
    for sub in subs:
        try:
            from app.services.alerts import get_profile_identity
            identity = get_profile_identity(sub)
            email = (identity or {}).get("email", "")
            if email and email not in emails:
                emails.append(email)
        except Exception:
            continue
    return emails
```

**New function** — `list_project_status_history`:

```python
def list_project_status_history(
    owner_sub: str,
    project_id: str,
    *,
    limit: int = 50,
    cursor: Optional[str] = None,
) -> dict:
    """Return status-change audit records for a project in reverse
    chronological order (newest first).

    Queries T.alerts PK=owner_sub with ScanIndexForward=False, looping
    LastEvaluatedKey until `limit` matching rows are found or the table
    is exhausted.  Matching criterion: event="crm_project.status_changed"
    AND details.project_id=project_id.
    """
    from app.core.tables import T
    from app.core.cursor import decode_cursor, encode_cursor
    from boto3.dynamodb.conditions import Key, Attr

    lek = decode_cursor(cursor)
    results: list[dict] = []
    last_key: Optional[dict] = lek

    while len(results) < limit:
        kwargs: dict = {
            "KeyConditionExpression": Key("user_sub").eq(owner_sub),
            "FilterExpression": (
                Attr("event").eq("crm_project.status_changed")
                & Attr("details.project_id").eq(project_id)
            ),
            "ScanIndexForward": False,
            "Limit": max(limit * 4, 200),  # over-fetch to compensate for filter
        }
        if last_key:
            kwargs["ExclusiveStartKey"] = last_key

        resp = T.alerts.query(**kwargs)
        for item in resp.get("Items", []):
            det = item.get("details") or {}
            results.append({
                "from_status":  det.get("from_status"),
                "to_status":    det.get("to_status"),
                "changed_by":   det.get("changed_by"),
                "project_name": det.get("project_name"),
                "changed_at":   item.get("ts"),
                "alert_id":     item.get("alert_id"),
            })
            if len(results) >= limit:
                break

        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break

    return {
        "items": results[:limit],
        "cursor": encode_cursor(last_key) if last_key and len(results) >= limit else None,
    }
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Allowed transitions

| From        | Allowed `to`                      | Notes                                     |
|-------------|-----------------------------------|-------------------------------------------|
| `draft`     | `in_review`, `underway`, `deferred` | Cannot jump directly to `completed`       |
| `in_review` | `underway`, `draft`, `deferred`   | Can revert to `draft` (reviewer rejected) |
| `underway`  | `completed`, `in_review`, `deferred` | Forward to done, back to review, or park |
| `completed` | `underway`                        | Reopen only — no direct `draft` regression |
| `deferred`  | `draft`, `underway`               | Resume from parking                       |

Any other pair returns `HTTP 400 {"code": "invalid_status_transition", "from": "...", "to": "..."}`.

### 5.2 No-op transition (same status)

If the caller sends `PATCH` with `status` equal to the current value, the transition
guard treats it as a no-op: the condition `status not in allowed` is False for the
identity transition since we explicitly handle `requested == current` as a pass-through
(same logic as `app/services/tickets.py:928`: `if requested_status not in allowed_next
and requested_status != current_status`). No audit event is emitted for a no-op.

### 5.3 Concurrent PATCH (optimistic concurrency)

`update_crm_project` uses the `ConditionExpression=Attr("updated_at").eq(old_updated_at)`
pattern (standard DDB optimistic lock). If the condition fails, a `ConditionalCheckFailedException`
is raised and surfaces as `HTTP 409 {"code": "conflict"}`. The caller should re-fetch
and retry.

### 5.4 Completion email failure

`_notify_project_completed` is called inside a `try/except Exception`. If
`_collect_owner_emails` returns an empty list (e.g., PRJ-007 has not yet run,
`T.crm_pm_members` has no rows), the email is silently skipped. If `send_alert_email`
raises, the exception is swallowed and the status update has already been committed.
This matches the KYC risk-scoring submission hook pattern
(`app/services/kyc_risk_scoring.py`, GAP-0265 in CLAUDE.md).

### 5.5 `changed_by` attribution

The `changed_by` field is populated from `session["user_sub"]` in the router handler
and passed down to `update_crm_project(changed_by=...)`. When the update is performed
by an impersonating admin, the router reads `session.get("actor_sub") or session["user_sub"]`
so the audit row accurately captures the acting identity.

### 5.6 Status-history pagination

`list_project_status_history` loops `LastEvaluatedKey` until `limit` matching rows
are accumulated or the table is exhausted. The over-fetch multiplier (`limit * 4`,
minimum 200) compensates for the sparse filter (CLAUDE.md: "DDB FilterExpression
doesn't reduce page size"). The returned `cursor` is `None` when no more rows exist
or when the current page is not full. A non-null `cursor` does not guarantee more
matching rows exist — callers must handle an empty `items` list on the next page.

### 5.7 Members not found at completion time

If PRJ-007 (`crm_pm_members`) is not yet implemented at the time PRJ-009 ships,
`_collect_owner_emails` catches the `ResourceNotFoundException` from DynamoDB and
returns `[]`, silently skipping the email. The status transition itself is unaffected.

### 5.8 Project ownership check for history endpoint

`get_project_status_history_route` calls `get_crm_project(session["user_sub"],
project_id)` first to enforce ownership (404 if not owner or not found) before
querying the alerts table. This ensures a non-owner cannot enumerate another user's
audit events.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

`audit_event` / `write_alert` writes to the real `T.alerts` DDB table in both dev
(moto in-process) and prod (real DynamoDB). No `S.dev_mode` branch is introduced.
`send_alert_email` self-selects the transport based on `S.dev_mode` at
`app/services/alerts.py:462–467` — the service layer is unchanged. This preserves
the existing SECOPS-007 guarantee: the production code path is exercised in dev.

### 7.2 Idempotency

`audit_event` generates a new `alert_id = f"{ts:010d}#{uuid4().hex}"` on each call
(`app/services/alerts.py:370`). Two identical PATCH requests sent at the same
millisecond produce two distinct audit rows. This is intentional — audit trails must
not suppress duplicate transitions caused by retries. The transition guard prevents
a no-op transition from emitting a spurious event.

### 7.3 Security

- The `status-history` endpoint enforces project ownership via `get_crm_project` before
  querying `T.alerts`. A caller cannot retrieve another user's alert rows by supplying
  an arbitrary `project_id`.
- The `changed_by` field records the actor's `user_sub` (not the impersonated subject)
  when the session carries an admin impersonation context. This is consistent with
  the audit attribution pattern throughout the codebase.
- Status values are Pydantic-enum-validated before reaching the service; invalid
  strings fail at 422 before any DDB write occurs.

## 8. Backward Compatibility & Migration

### 8.1 No breaking changes to existing APIs

`PATCH /v1/crm/projects/{project_id}` acquires an additional validation step but its
request/response shape is unchanged from PRJ-002. Existing callers that only update
non-`status` fields (name, description, priority, dates) are unaffected — the
transition guard short-circuits when `status` is `None` or unchanged.

### 8.2 Existing project rows

CRM project items written by PRJ-002 before PRJ-009 ships all carry `status="draft"`
(the default). The transition guard allows forward transitions from `draft`, so no
migration is needed.

### 8.3 Alert table growth

Each status transition adds one row to `T.alerts`. The alerts table has a TTL
(`S.alerts_ttl_days`, default 90 days, `app/services/alerts.py:371`). Status history
rows are therefore pruned automatically. The `status-history` endpoint's reverse-scan
loop gracefully handles expired rows by finding fewer results — the cursor correctly
reflects the exhaustion.

### 8.4 Route ordering safety

The `GET /{project_id}/status-history` path segment is concrete (`status-history`)
and does not conflict with any parameter capture in the router. FastAPI's declaration
order is safe as long as `/status-history` is declared before a potential catch-all
`/{project_id}/{sub_resource}` route (none exists yet in the PRJ series).

## 10. Open Questions / Assumptions

1. **`changed_by` in PATCH request**: The router derives `changed_by` from
   `session["user_sub"]` (or `actor_sub` for impersonation). No `changed_by` field
   is exposed in the `CrmProjectUpdateIn` request body — it is always server-derived
   for security.

2. **All project members vs owner-only for completion email**: PRJ-009 spec
   (`CRM_PROJECTS_GANTT_TICKETS.md:515`) says "all project `owner` members". This
   spec follows that literally — only members with `role="owner"` receive the email.
   If the product team wants all members notified, the `_collect_owner_emails` helper
   is extended to drop the `FilterExpression` on role.

3. **Status history accessible to project members (PRJ-007)**: For now the ownership
   check uses `get_crm_project(owner_sub, ...)`, which 404s for non-owners. Once
   PRJ-007's `_assert_project_access` helper ships, the history endpoint should be
   widened to allow `role >= viewer`. This is a safe follow-up — being more
   restrictive initially cannot break callers.

4. **Alert TTL vs. long-lived audit requirement**: `alerts_ttl_days` (default 90) will
   prune status history. If compliance requires a longer retention window, the
   `crm_project.status_changed` event can be excluded from TTL pruning by adding it
   to a future `_NO_TTL_EVENTS` set in `write_alert`. Out of scope for PRJ-009.

5. **Assumption — `T.crm_pm_projects` GSI2SK is numeric**: The `attr_types={"GSI2SK": "N"}`
   declaration in the PRJ-001 `TableDef` is required (CLAUDE.md: "DynamoDB numeric GSI
   sort keys"). The status-history endpoint does not use GSI2 — it queries the `alerts`
   table on its primary key — so this assumption has no direct impact on PRJ-009 but
   is documented for PRJ-001 completeness.
