# PRJ-007 — Project team members (owner/member/viewer roles)

**Ticket type:** Feature
**Priority:** P1
**Estimate:** 2d
**Area:** CRM Projects, Project Tasks & Gantt
**Source:** `docs/suitecrm/CRM_PROJECTS_GANTT_TICKETS.md` § "PRJ-007"

---

## 1. Summary & Goal

PRJ-007 introduces a multi-user membership roster for CRM projects. Before this ticket, every CRM project endpoint checks that `caller_sub == project.owner_sub`; no other user can read or write a project they do not own. After this ticket, three distinct roles control access:

- **owner** — full control: edit the project header and tasks, manage the member roster, and delete the project. There is exactly one owner per project at any time, and the owner row cannot be removed.
- **member** — read + write on project data (header, tasks), but cannot add/remove other members, delete the project, or change membership roles.
- **viewer** — read-only on the project header, task list, milestone list, and member roster. Cannot create, update, or delete tasks or the project header.

The gate function `_assert_project_access(caller_sub, project_id, min_role)` replaces the existing `owner_sub == project.owner_sub` checks across the CRM project service layer. Membership records live in the dedicated `T.crm_pm_members` table scaffolded by PRJ-001.

All behavior is gated behind `S.crm_projects_enabled` (env `CRM_PROJECTS_ENABLED`, default `"0"`, introduced in PRJ-001). With the flag off, the platform is byte-for-byte unchanged.

## 3. Data Model

### 3.1 Table: `crm_pm_members` (introduced in PRJ-001)

This table is already scaffolded by PRJ-001. PRJ-007 is the first ticket to write to it.

**Primary key layout:**

| Attribute | Value | Notes |
|-----------|-------|-------|
| `PK` | `PROJECT#{project_id}` | All members of a project |
| `SK` | `MEMBER#{user_sub}` | One row per member |
| `GSI1PK` | `MEMBER#{user_sub}` | Inverse index: projects for a user |
| `GSI1SK` | `PROJECT#{project_id}` | Sorted by project ID string |

**Item attributes:**

| Attribute | Type | Description |
|-----------|------|-------------|
| `project_id` | S | Denormalized for convenience |
| `user_sub` | S | Member's platform user sub |
| `role` | S | `"owner"` \| `"member"` \| `"viewer"` |
| `added_by` | S | `user_sub` of the user who created this row |
| `added_at` | N | Unix timestamp (integer, `now_ts()`) |
| `entity_type` | S | `"crm_member"` (entity discriminator) |

**No `attr_types` entry is needed** — both `PK`/`SK` and `GSI1PK`/`GSI1SK` are string attributes. The `added_at` field is stored as a plain item attribute, not as a GSI key, so the DDB `ValidationException` for numeric GSI sort keys does not apply here.

### 3.2 Owner bootstrap row

When a project is first created in PRJ-002, `create_crm_project` must also write an owner member row to `T.crm_pm_members`:

```
PK      = "PROJECT#{project_id}"
SK      = "MEMBER#{owner_sub}"
role    = "owner"
added_by = owner_sub
added_at = now_ts()
entity_type = "crm_member"
GSI1PK  = "MEMBER#{owner_sub}"
GSI1SK  = "PROJECT#{project_id}"
```

This write happens inside `create_crm_project` in `app/services/crm_projects.py` (PRJ-002 code). PRJ-007 introduces the helper `_bootstrap_owner_member(project_id, owner_sub)` in `app/services/crm_project_members.py` which `create_crm_project` calls via a lazy import. The bootstrap uses `put_item` with `ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)"` so that a replay of a failed create never double-writes.

#### `_assert_project_access(caller_sub: str, project_id: str, min_role: CrmProjectMemberRole) -> CrmProjectMemberRole`

```python
def _assert_project_access(
    caller_sub: str,
    project_id: str,
    min_role: CrmProjectMemberRole,
) -> CrmProjectMemberRole:
```

1. Calls `T.crm_pm_members.get_item(Key={"PK": f"PROJECT#{project_id}", "SK": f"MEMBER#{caller_sub}"}, ConsistentRead=True)`.
2. If item is absent or `entity_type != "crm_member"`, raises `HTTPException(403, {"code": "not_a_project_member"})`.
3. Parses `role` from item. The role ordering is `owner > member > viewer` encoded as ordinal values `{owner: 3, member: 2, viewer: 1}`.
4. If caller role ordinal < `min_role` ordinal, raises `HTTPException(403, {"code": "insufficient_project_role", "required": min_role.value, "actual": caller_role.value})`.
5. Returns the caller's `CrmProjectMemberRole`.

This helper replaces the `owner_sub == project.owner_sub` pattern in PRJ-002 and PRJ-003 service functions. Each of those functions is amended to call `_assert_project_access(caller_sub, project_id, min_role=CrmProjectMemberRole.member)` for write operations and `min_role=CrmProjectMemberRole.viewer` for read operations, **instead of** calling `get_crm_project(owner_sub, project_id)` with the caller acting as `owner_sub`. The PRJ-002/PRJ-003 `get_crm_project` call must still happen to retrieve the project object — but the authorization is now done by the membership check, not by the ownership field comparison. The `get_crm_project` signature in PRJ-002 is amended to accept `caller_sub` separately from `owner_sub` so it can load the project by `GSI1PK = PROJECT#{project_id}` rather than requiring the caller to be the owner.

---

#### `add_member(caller_sub, project_id, target_sub, role) -> CrmProjectMemberModel`

```python
def add_member(
    caller_sub: str,
    project_id: str,
    target_sub: str,
    role: CrmProjectMemberRole,
) -> CrmProjectMemberModel:
```

1. Calls `_assert_project_access(caller_sub, project_id, min_role=CrmProjectMemberRole.owner)` — only owners may add members.
2. Rejects `role == CrmProjectMemberRole.owner` for new additions: there can only be one owner row per project. Raises `HTTPException(400, {"code": "cannot_assign_owner_role"})`. Ownership transfer is not supported in this ticket.
3. Writes the member item with `ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)"`. If item already exists (idempotent re-add of same user) catches `ConditionalCheckFailedException` and returns the existing row as-is.
4. Calls `audit_event("crm_project.member_added", caller_sub, None, project_id=project_id, target_sub=target_sub, role=role.value)`.
5. Returns `CrmProjectMemberModel`.

---

#### `update_member_role(caller_sub, project_id, target_sub, new_role) -> CrmProjectMemberModel`

```python
def update_member_role(
    caller_sub: str,
    project_id: str,
    target_sub: str,
    new_role: CrmProjectMemberRole,
) -> CrmProjectMemberModel:
```

1. Calls `_assert_project_access(caller_sub, project_id, min_role=CrmProjectMemberRole.owner)`.
2. Prevents changing the owner row's role: if `target_sub` is the project owner, raises `HTTPException(400, {"code": "cannot_change_owner_role"})`. The owner row is identified by `item["role"] == "owner"`.
3. Prevents demoting to `owner` (same constraint as `add_member`): `new_role == CrmProjectMemberRole.owner` raises `HTTPException(400, {"code": "cannot_assign_owner_role"})`.
4. Uses `update_item` with `UpdateExpression="SET #role = :role, added_at = :ts"` (reusing `added_at` as `updated_at` for simplicity; an explicit `updated_at` attribute may be added without schema change).
5. Calls `audit_event("crm_project.member_role_updated", ...)`.
6. Returns the updated `CrmProjectMemberModel`.

---

#### `remove_member(caller_sub, project_id, target_sub) -> dict`

```python
def remove_member(
    caller_sub: str,
    project_id: str,
    target_sub: str,
) -> dict:
```

1. Calls `_assert_project_access(caller_sub, project_id, min_role=CrmProjectMemberRole.owner)`.
2. Retrieves the target member row. If absent, returns `{"ok": True}` (idempotent).
3. If `target_sub == project.owner_sub` (identified by `item["role"] == "owner"`), raises `HTTPException(400, {"code": "cannot_remove_owner"})`.
4. Calls `T.crm_pm_members.delete_item(Key={...})`.
5. Calls `audit_event("crm_project.member_removed", caller_sub, None, project_id=project_id, target_sub=target_sub)`.
6. Returns `{"ok": True}`.

---

#### `list_members(caller_sub, project_id) -> List[CrmProjectMemberModel]`

```python
def list_members(
    caller_sub: str,
    project_id: str,
) -> List[CrmProjectMemberModel]:
```

1. Calls `_assert_project_access(caller_sub, project_id, min_role=CrmProjectMemberRole.viewer)` — viewers may list members.
2. Queries `T.crm_pm_members` with `KeyConditionExpression = Key("PK").eq(f"PROJECT#{project_id}") & Key("SK").begins_with("MEMBER#")`, `ScanIndexForward=True`.
3. Filters items where `entity_type == "crm_member"` (skips any `CONTACT_LINK#` rows stored on the same PK by PRJ-010).
4. Returns list of `CrmProjectMemberModel` sorted alphabetically by `user_sub` (natural DDB ordering with `MEMBER#` SK prefix).
5. No cursor pagination: membership lists are expected to be small (fewer than 100 members per project). If a project exceeds 100 members in production, a follow-up ticket (PRJ-013) should add cursor pagination here.

---

#### `get_member_role(caller_sub, project_id) -> Optional[CrmProjectMemberRole]`

Returns the caller's role in a project, or `None` if not a member. Never raises. Used by the frontend to conditionally render owner-only controls without requiring a full `list_members` call.

---

#### `list_projects_for_member(user_sub, *, limit, cursor) -> dict`

```python
def list_projects_for_member(
    user_sub: str,
    *,
    limit: int = 50,
    cursor: Optional[Dict] = None,
) -> dict:
```

Queries `T.crm_pm_members` on **GSI1** with `KeyConditionExpression = Key("GSI1PK").eq(f"MEMBER#{user_sub}")`. This returns all projects the user is a member of (including as owner), regardless of who owns the project. Returns `{items: List[CrmProjectMemberModel], cursor: Optional[str]}`. This function is used by the PRJ-012 frontend list page to show all projects accessible to the user, not just ones they own.

## 5. Detailed Behavior & Edge Cases

### 5.1 Project creation bootstraps the owner row

`create_crm_project` (PRJ-002) must atomically bootstrap the owner member row. Because DDB does not support cross-table transactions between `crm_pm_projects` and `crm_pm_members`, the bootstrap is a **two-step sequential write** in the service layer:

1. `T.crm_pm_projects.put_item(...)` — creates the project header (ConditionExpression: attribute_not_exists).
2. `_bootstrap_owner_member(project_id, owner_sub)` — writes the owner member row (ConditionExpression: attribute_not_exists).

If step 2 fails (e.g., network error), the project exists without a member row. A subsequent retry of `create_crm_project` with the same `project_id` will fail at step 1 (conditional check). The caller must treat the orphaned project as unusable and create a new one. There is no compensating transaction. This is acceptable given the low-probability failure scenario; a production-hardening follow-up could use DDB TransactWriteItems across both tables once AWS supports cross-table transactions with distinct partition keys (not currently available).

### 5.2 Non-member callers receive 403, not 404

When `_assert_project_access` is called for a project that exists but the caller has no membership row, the function raises `HTTPException(403, {"code": "not_a_project_member"})`. This is intentional: returning 404 would allow callers to infer project existence by probing IDs. An ADMIN or ROOT platform role (as defined in `app/auth/roles.py:8`) does not bypass this check — CRM project ownership is a separate authorization layer from platform admin roles.

Exception: an ADMIN/ROOT-protected admin endpoint may be added in a future ticket to allow platform admins to view any project for audit purposes. This ticket does not introduce such an endpoint.

### 5.3 Viewer role restrictions

A caller with `role=viewer` on a project:
- May call `GET /v1/crm/projects/{id}` (get header), `GET /v1/crm/projects/{id}/tasks`, `GET /v1/crm/projects/{id}/tasks/{task_id}`, `GET /v1/crm/projects/{id}/milestones` (PRJ-005), `GET /v1/crm/projects/{id}/members`.
- May NOT call `PATCH /v1/crm/projects/{id}` (update header), `POST/PATCH/DELETE /v1/crm/projects/{id}/tasks/...`, `GET /v1/crm/projects/{id}/workload` (PRJ-004) — the workload endpoint requires `member` role since it exposes per-user assignment data. Wait, workload is read-only. Reconsider: `viewer` may call `GET /workload` (PRJ-004) — it is a read-only aggregation. Set `min_role=viewer` for workload.
- May NOT call any `POST/PATCH/DELETE /v1/crm/projects/{id}/members/...`.

### 5.4 Cannot remove the last owner

The owner row (`role="owner"`) cannot be deleted. There is exactly one owner per project. If the owner wants to transfer ownership, a future ticket (PRJ-013) should introduce an explicit ownership-transfer endpoint that atomically: (a) writes a new owner row for the transferee, and (b) demotes the previous owner to `member`. This ticket explicitly does NOT implement ownership transfer; attempting to `PATCH` the owner's role or `DELETE` the owner member row returns `HTTP 400 {"code": "cannot_remove_owner"}` or `{"code": "cannot_change_owner_role"}` respectively.

### 5.5 Duplicate add_member calls are idempotent

If a caller adds a user who is already a member, `add_member` catches `ConditionalCheckFailedException` (the attribute_not_exists condition fails on the second write) and returns the existing member row unchanged. The HTTP status is still `201`. The role is **not** updated by an idempotent re-add; to change roles, the caller must use `PATCH /{project_id}/members/{user_sub}`.

### 5.6 Project deletion cascades member rows

`delete_crm_project(caller_sub, project_id)` (PRJ-002, amended here) must also delete all member rows from `T.crm_pm_members`. Because DDB delete-item requires the exact key, the cascade is:

1. Query `T.crm_pm_members` with `KeyConditionExpression = Key("PK").eq(f"PROJECT#{project_id}")`, collecting all items.
2. Loop and `delete_item` each row (batch_writer preferred if >10 items).

This cascade is performed inside `delete_crm_project` (the service function), not in the router. The caller must have `owner` role (enforced by `_assert_project_access` before deletion proceeds).

### 5.7 `list_members` does not paginate

The `list_members` function queries the full `MEMBER#` prefix in one DDB call (max 1 MB / ~16 KB per item = ~60,000 items before hitting the scan limit). For practical project sizes (fewer than a few hundred members), a single query is sufficient. If a project ever accumulates enough member rows to exceed 1 MB in a single query page, `list_members` will silently return a truncated list. A follow-up ticket adds `LastEvaluatedKey` loop logic. For PRJ-007 the simplified single-page approach is acceptable.

### 5.8 GSI1 query for `list_projects_for_member`

`list_projects_for_member` queries `GSI1PK = MEMBER#{user_sub}` across all projects. The GSI1SK value is the string `PROJECT#{project_id}` so results are sorted alphabetically by project ID. The caller receives `CrmProjectMemberModel` items (containing `project_id` and `role`) and must issue individual `get_crm_project` calls to hydrate project headers, or the frontend can call `list_crm_projects` (own projects) + `list_projects_for_member` (member-of projects) and deduplicate by `project_id`. The PRJ-012 frontend implementation deduplicates by rendering both sets.

### 5.9 In-app notification on member addition

When a member is added (`add_member` succeeds), a best-effort in-app alert is written to the new member:

```python
try:
    write_alert(
        target_sub,
        event="crm_project.member_added",
        outcome="info",
        title=f"You were added to project {project_id}",
        details={"project_id": project_id, "role": role.value, "added_by": caller_sub},
    )
except Exception:
    pass
```

`write_alert` is `app/services/alerts.write_alert` (`app/services/alerts.py:356`). The call is wrapped in `try/except` so a notification failure never blocks the membership write. No email notification is sent for member additions in this ticket (PRJ-009 introduces email for project completions as the precedent pattern).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

All DDB reads and writes in `app/services/crm_project_members.py` use `T.crm_pm_members`, which resolves to the moto in-process mock in dev and the real DynamoDB table in prod. There is no `if S.dev_mode` branch anywhere in the service layer. `audit_event` writes to `T.alerts` regardless of environment. `write_alert` writes to `T.alerts` in both environments. This satisfies the SECOPS-007 single-code-path requirement.

### 7.2 Idempotency

- `add_member` uses `attribute_not_exists` conditional put — safe to retry; second call returns existing row.
- `_bootstrap_owner_member` uses `attribute_not_exists` — safe to call multiple times; subsequent calls are no-ops.
- `remove_member` returns `{"ok": True}` even when the item is already absent.
- `update_member_role` is naturally idempotent when called with the same role value.
- `delete_crm_project` cascade: `delete_item` on a nonexistent key is a no-op in DDB (no ConditionExpression needed for deletes).

### 7.3 Security

**Authorization model**: membership is enforced by `_assert_project_access` at the service layer, called before any data read or mutation. The router layer has no access-control logic — it delegates entirely to the service. This ensures authorization cannot be bypassed by adding a new handler that forgets to call the flag guard.

**Privilege escalation prevention**: `add_member` and `update_member_role` both reject `role == owner`. The only way to have `role=owner` is via `_bootstrap_owner_member` which is called only from `create_crm_project`.

**Cross-user information disclosure**: `list_members` requires at least `viewer` role. Unauthenticated or non-member callers receive HTTP 403 (not 404) and learn nothing about the project's membership list. Project IDs are UUIDs (opaque), so enumeration is not feasible.

**CSRF**: All mutating endpoints (POST, PATCH, DELETE) go through `require_ui_session` which validates the `x-csrf-token` header for cookie-based sessions (documented in CLAUDE.md "CSRF" section). Bearer-auth requests skip CSRF.

**Input validation**: `AddMemberIn.user_sub` has `min_length=1, max_length=256`. The `role` field is a typed `CrmProjectMemberRole` enum — unknown values return HTTP 422 from Pydantic validation.

**Audit trail**: every mutating operation (`add_member`, `update_member_role`, `remove_member`) calls `audit_event` with the platform's standard signature (`app/services/alerts.py:644`). This ensures membership changes are visible in the admin audit log.

## 8. Backward Compatibility & Migration

### 8.1 Flag-off behavior

With `CRM_PROJECTS_ENABLED=0` (the default), every route in `app/routers/crm_projects.py` returns HTTP 404 via `_require_crm_projects()`. No DDB tables are read or written. No existing routes are affected. The `T.projects` table (file-grouping layer) and `app/routers/projects.py` are untouched.

### 8.2 PRJ-002/PRJ-003 function signature change

The change from `owner_sub` to `caller_sub` in the service function signatures (§4.3) is a rename inside the CRM layer. Since `app/routers/crm_projects.py` is the only caller of these functions (no external callers exist), this is not a breaking change to any public API. The HTTP response shapes are unchanged.

### 8.3 DDB table lifecycle

`T.crm_pm_members` is created by `scripts/local-ddb-init.py` on `just up` / `just restart`. Because `CRM_PROJECTS_ENABLED` defaults to `"0"`, no items are written to this table in production until the flag is explicitly enabled. There is no migration of existing data — the table starts empty and is populated only when the flag is on and users create CRM projects.

### 8.4 Owner row bootstrap for existing PRJ-002 projects

If PRJ-002 was deployed before PRJ-007 (i.e., projects exist in `T.crm_pm_projects` but no owner rows exist in `T.crm_pm_members`), the amended PRJ-002 `get_crm_project` (which now calls `_assert_project_access`) would return 403 for the project owner themselves. To prevent this, a **lazy bootstrap** is implemented: inside `_assert_project_access`, if no member row is found for the caller AND the project's `owner_sub == caller_sub`, the function auto-creates the owner row and proceeds. This covers the migration window between PRJ-002 deployment and PRJ-007 deployment. Once PRJ-007 is deployed, all new project creations bootstrap the owner row immediately; the lazy path handles only the pre-existing orphaned rows.

## 10. Open Questions / Assumptions

1. **Ownership transfer**: SuiteCRM supports reassigning the project to a different user. PRJ-007 deliberately defers ownership transfer to avoid complexity. If needed, a follow-up ticket (PRJ-013) should add `POST /{project_id}/transfer-ownership` that uses a DDB TransactWriteItems to atomically swap owner and demote the previous owner to `member`. Assumption: not required for initial launch.

2. **Cross-tenant member invitation**: If the platform has tenant isolation enabled (ENTERPRISE-001, `TenantMiddleware`), a project owner in tenant A could attempt to add a user_sub from tenant B. PRJ-007 does not validate that `target_sub` belongs to the same tenant as `caller_sub`. This validation is deferred; the assumption is that `user_sub` is globally unique across tenants in the current implementation and cross-tenant membership is considered an edge case for a later security hardening pass.

3. **Email notification on member addition**: PRJ-009 uses `send_alert_email` for project completion. PRJ-007 uses only `write_alert` (in-app notification) for member additions — no email. Assumption: email for membership changes is lower priority than in-app alerts.

4. **Batch member operations**: `add_member` accepts one member at a time. SuiteCRM supports bulk import of team members. A bulk endpoint is deferred. Assumption: single-user add is sufficient for the initial PRJ-012 UI.

5. **Member list size assumption**: `list_members` does not paginate. This is safe assuming a project has fewer than ~1,000 members (fitting within the 1 MB DDB query page limit). If a future use case requires larger teams, PRJ-013 adds pagination. Assumption holds for the typical CRM project team size.
