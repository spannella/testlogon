# EVT-007 — Map view — frontend page with geocoded pin-drop rendering

**Type:** Feature | **Priority:** P2 | **Estimate:** 3d
**Source:** `docs/suitecrm/CRM_MISC_TICKETS.md` (section "EVT-007")
**Dependencies:** EVT-006 (proximity search endpoint), which itself depends on EVT-005 (geocoding service)
and EVT-001 (flag scaffolding).

---

## 1. Summary & Goal

EVT-007 delivers a map view page at `/crm/maps` that renders geocoded contact pins on an interactive
Leaflet map. The page is the visual counterpart to the EVT-006 proximity search endpoint: the user selects
a centre point (either by clicking the map or entering an address), adjusts a radius slider, and the
page re-fetches `GET /ui/crm/maps/contacts/proximity` to show matching contacts as drop pins with popup
cards.

Three concrete deliverables:

1. **A thin backend addition** — a `GET /ui/crm/maps/feature-flags` endpoint that exposes the
   `crm_geocoding_enabled` flag to the frontend without embedding backend environment details in the
   build. This is the only new backend code in this ticket; all geocoding and search logic lives in
   EVT-005 / EVT-006.
2. **Frontend API wrapper** — `frontend/src/api/endpoints/crmMaps.ts` with typed axios calls.
3. **Frontend map page** — `frontend/src/pages/crm/maps/CrmMapsPage.tsx` using `react-leaflet`
   (`MapContainer`, `TileLayer`, `Marker`, `Popup`) and React Query.

With `CRM_GEOCODING_ENABLED=0` (the default) the feature-flags endpoint returns `{"crm_geocoding_enabled":
false}`, the sidebar link is hidden, and navigating directly to `/crm/maps` shows a disabled-feature
placeholder. The rest of the platform is byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 Geocoding infrastructure (EVT-005)

`app/services/kyc_address_verification._geocode` (`app/services/kyc_address_verification.py:210–224`)
is the authoritative deterministic mock geocoder. It derives `lat` in `[-90, 90]` and `lng` in
`[-180, 180]` from a SHA-256 of a normalised address fingerprint; the guard
`if not S.kyc_address_geocoding_enabled: return None` (line 216) makes it flag-safe.

EVT-005 introduces `app/services/crm_geocoding.py` (new file, not yet present in the repo), which
re-implements the same logic behind the separate flag `S.crm_geocoding_enabled`
(`app/core/settings.py` — flag not yet added; EVT-001 / EVT-005 add it). The `geocode_address` and
`apply_geocode_to_address` functions write `lat`, `lng`, `geocoded_at` onto rows in the existing
`addresses` table (`app/core/tables.py:345`, `scripts/local-ddb-init.py:98`, PK=`user_sub`,
SK=`address_id`). No new table is introduced by EVT-005.

### 2.2 Proximity search endpoint (EVT-006)

EVT-006 adds `proximity_search(user_sub, center_lat, center_lng, radius_km, limit=50)` to
`app/services/crm_geocoding.py` (Haversine-filtered scan of geocoded addresses) and exposes
`GET /ui/crm/maps/contacts/proximity?lat=&lng=&radius_km=&limit=` in a new router
`app/routers/crm_geocoding.py` (prefix `/ui/crm/maps`). Each result carries
`{party_id, name, lat, lng, distance_km}`. This is the data source EVT-007 consumes.

### 2.3 No existing CRM map/geocoding routers or pages

No file matching `app/routers/crm*.py` or `app/services/crm*.py` exists yet
(confirmed: `ls app/routers/crm*.py` returns nothing; `ls app/services/crm*.py` returns nothing).
No `frontend/src/pages/crm/` directory exists. No `frontend/src/api/endpoints/crmMaps.ts` exists.

### 2.4 Frontend feature-flag pattern

`frontend/src/lib/featureFlags.ts` (line 1) reads from `import.meta.env` (Vite-injected). Boolean flags
follow the `toBool(env.VITE_<NAME>, <default>)` helper pattern (e.g. `inventoryReservationsEnabled` at
line 161, default `false`). Sidebar entries can be conditionally rendered by importing the flag function
and adding a guard in `NAV_GROUPS` construction
(`frontend/src/components/layout/Sidebar.tsx:81–82` imports flag functions and applies them in the
component body — e.g. `showInventoryAdmin = isInventoryReservationsEnabled() && ...` at line 263).

However, for CRM map view the feature is gated server-side by `CRM_GEOCODING_ENABLED` (a backend env
var, not a Vite build-time var). The Vite build must not encode a server-side flag directly, so
EVT-007 exposes a lightweight `GET /ui/crm/maps/feature-flags` endpoint (see §4.1) and the frontend
queries it on mount via React Query to decide whether to render the full map or a disabled placeholder.
This is the same pattern that the moderation admin UI uses for its feature-flag probe endpoint at
`app/routers/admin_moderation.py:513` (`GET /admin/moderation/feature-flags`).

### 2.5 React Router and lazy-loading

`frontend/src/App.tsx:1` uses `React.lazy` for all page components (e.g. `CalendarPage` at line 40,
`ContactsPage` at line 75). A new `<Route>` for `/crm/maps` is added inside the `<AppShell>` guarded
routes block, wrapped in `<Suspense>` like all other lazy routes.

### 2.6 Contacts table shape

`app/routers/contacts.py` (prefix `/ui/contacts`, import at `app/main.py:82`, registered at
`app/main.py:683`) stores contact items in `T.contacts` (PK=`owner_id`, SK=`contact_id`). Items carry
`display_name`, `profile_photo_url`, `is_favorite`, `is_blocked`, `added_at`. Notably, contact items
do **not** store a postal address or lat/lng directly — those live in the `addresses` table managed by
`app/services/addresses.py`. EVT-006's `proximity_search` returns results derived from the `addresses`
table (geocoded saved addresses), identifying each by a `party_id` (or `address_id` until PTY-001
ships). EVT-007 renders these as map pins using the `name` and `distance_km` fields from the proximity
response; it does not need to re-query the contacts table.

### 2.7 Audit primitives

`app/services/alerts.audit_event` (line 644) is the canonical audit write. EVT-007 emits a single
`audit_event("crm_map_viewed", user_sub)` on page load (routed through the feature-flags endpoint
response handling, see §4.1) to record that a user opened the map view. No money moves; no billing,
refund, or ledger primitives are needed.

### 2.8 No Leaflet package yet

The repo does not currently ship `react-leaflet` or `leaflet`. These are added as runtime dependencies
in `frontend/package.json`. The Leaflet CSS (`leaflet/dist/leaflet.css`) must be imported in
`CrmMapsPage.tsx` (or in `main.tsx`) to prevent missing tile/marker icon styles. Marker icons require
a one-time icon-URL fix (standard react-leaflet pattern using `L.Icon.Default.mergeOptions`) because
Webpack/Vite asset hashing breaks the default icon path resolution.

## 4. API / Service Design

### 4.1 New endpoint: `GET /ui/crm/maps/feature-flags`

Added to the existing EVT-006 router `app/routers/crm_geocoding.py` (prefix `/ui/crm/maps`).

**Auth:** `Depends(require_ui_session)` (imported from `app.services.sessions`, consistent with
`app/routers/contacts.py:12`).

**Guard:** None — this endpoint must return `{"crm_geocoding_enabled": false, ...}` even when the flag
is off, so the frontend knows to show the disabled placeholder. Do not apply
`_require_crm_events_enabled()` or the geocoding flag guard here.

**Request:** `GET /ui/crm/maps/feature-flags` — no query parameters, no body.

**Response model** (inline in the router file or added to `app/models.py`):

```python
class CrmMapFeatureFlagsOut(BaseModel):
    crm_geocoding_enabled: bool
    default_lat: float
    default_lng: float
    default_radius_km: float
    max_radius_km: float
    max_pins: int
```

**Handler logic:**

```python
@router.get("/feature-flags", response_model=CrmMapFeatureFlagsOut)
def get_crm_map_feature_flags(
    _user: AuthenticatedUser = Depends(get_authenticated_user),
) -> CrmMapFeatureFlagsOut:
    audit_event("crm_map_viewed", _user.sub)   # best-effort, fire-and-forget
    return CrmMapFeatureFlagsOut(
        crm_geocoding_enabled=S.crm_geocoding_enabled,
        default_lat=S.crm_map_default_lat,
        default_lng=S.crm_map_default_lng,
        default_radius_km=S.crm_map_default_radius_km,
        max_radius_km=S.crm_map_max_radius_km,
        max_pins=S.crm_map_max_pins,
    )
```

`audit_event` is imported from `app.services.alerts` (line 644). The call is wrapped in `try/except`
so an audit write failure never breaks the feature-flags response.

The EVT-006 proximity endpoint (`GET /ui/crm/maps/contacts/proximity`) is unchanged by EVT-007 but is
the other backend surface consumed by the frontend.

**Route ordering note:** `/feature-flags` is a literal path segment; it must be declared **before**
any `/{something}` catch-all in the router file to avoid FastAPI matching it as a path parameter
(same rule applied to `/ui/admin/audit-exports/schedules` in `CLAUDE.md`).

### 4.2 Frontend API wrapper: `frontend/src/api/endpoints/crmMaps.ts`

```typescript
import { api } from "@/api/client";
import type { CrmMapFeatureFlags, ProximityResult } from "@/api/types";

const BASE = "/ui/crm/maps";

export async function getCrmMapFeatureFlags(): Promise<CrmMapFeatureFlags> {
  return api.get<CrmMapFeatureFlags>(`${BASE}/feature-flags`);
}

export async function getProximityContacts(params: {
  lat: number;
  lng: number;
  radius_km: number;
  limit?: number;
}): Promise<ProximityResult[]> {
  return api.get<ProximityResult[]>(`${BASE}/contacts/proximity`, { params });
}
```

The `api` object is the existing axios wrapper at `frontend/src/api/client.ts` (imported at line 1 of
`frontend/src/api/endpoints/contacts.ts`).

### 4.4 Frontend page: `frontend/src/pages/crm/maps/CrmMapsPage.tsx`

Single-file component. Key structure:

```typescript
// 1. Query feature flags on mount (staleTime: Infinity — flags don't change at runtime)
const { data: flags, isLoading: flagsLoading } = useQuery({
  queryKey: ["crm", "map-feature-flags"],
  queryFn: getCrmMapFeatureFlags,
  staleTime: Infinity,
});

// 2. Local state: centre lat/lng and radius
const [centre, setCentre] = useState<[number, number] | null>(null);
const [radiusKm, setRadiusKm] = useState<number>(flags?.default_radius_km ?? 50);

// 3. Query proximity contacts (enabled only when flag is on and centre is set)
const { data: pins = [], isFetching } = useQuery({
  queryKey: ["crm", "proximity", centre, radiusKm],
  queryFn: () =>
    getProximityContacts({
      lat: centre![0],
      lng: centre![1],
      radius_km: radiusKm,
      limit: flags?.max_pins,
    }),
  enabled: !!flags?.crm_geocoding_enabled && centre !== null,
  staleTime: 30_000,
});
```

**Map initialisation:**

- `MapContainer` centred on `[flags.default_lat, flags.default_lng]`, zoom 10.
- `TileLayer` with OpenStreetMap URL `https://{s}.tile.openstreetmap.org/{z}/{x}/{y}.png` and
  attribution string `© OpenStreetMap contributors`.
- One `Marker` per `ProximityResult` entry, positioned at `[pin.lat, pin.lng]`.
- Each `Marker` wraps a `Popup` showing: the contact name, the formatted distance
  (`${pin.distance_km.toFixed(1)} km away`), and a "View Contact" link navigating to
  `/contacts?highlight=${pin.party_id}`.

**Centre selection — `<MapClickHandler>` inner component:**

A small child component that calls `useMapEvents({ click: (e) => onCentreChange([e.latlng.lat, e.latlng.lng]) })` from `react-leaflet`. A distinct `CircleMarker` (blue, no popup) marks the chosen centre point so the user can see what they clicked.

**Radius slider:** A shadcn/ui `Slider` component bound to `radiusKm`, min `1`, max
`flags.max_radius_km`, step `5`. Changing the slider triggers React Query re-fetch (the `queryKey`
includes `radiusKm`). A `Circle` overlay from `react-leaflet` is drawn at the centre with
`radius={radiusKm * 1000}` (metres) so the search area is visible on the map.

**Disabled-feature state:**

When `flags?.crm_geocoding_enabled === false`, the page renders a full-height placeholder:

```tsx
<div className="flex flex-col items-center justify-center h-full gap-4 text-muted-foreground">
  <MapPin className="h-12 w-12" />
  <p className="text-lg font-medium">Map view is not enabled</p>
  <p className="text-sm">Ask your administrator to enable CRM_GEOCODING_ENABLED.</p>
</div>
```

**Empty-results state:**

When the flag is on, a centre is set, the query is not loading, and `pins.length === 0`, a `toast.info`
is shown: "No geocoded contacts found within [N] km." The map remains interactive.

**Loading state:**

While `isFetching` is true, a `<Loader2>` spinner is overlaid in the top-right corner of the map
container (absolute-positioned, z-index above the map tiles) using Tailwind `absolute top-2 right-2`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Initial load sequence

1. `CrmMapsPage` mounts; React Query fires `GET /ui/crm/maps/feature-flags`.
2. While the flags query is loading (`flagsLoading === true`), render a centered `<Loader2>` spinner
   (no map yet — `leaflet` requires a non-zero sized DOM node to initialise, and the flags determine
   the centre coordinates).
3. On flags response: if `crm_geocoding_enabled === false`, render the disabled placeholder (§4.4).
4. If enabled, render the `MapContainer` centred at `[default_lat, default_lng]`. No proximity query
   fires yet because `centre === null`.
5. User clicks the map or uses the "Use my location" button (§5.5); `centre` is set, proximity query
   fires.

### 5.2 Centre-change and re-fetch

Each map click calls `setCentre([lat, lng])`. React Query's `queryKey` is
`["crm", "proximity", centre, radiusKm]`, so each new `centre` or `radiusKm` value triggers a fresh
fetch. Previous results are replaced (not merged). The `staleTime: 30_000` prevents a re-fetch if the
user clicks the same pixel twice within 30 seconds.

### 5.3 `radius_km=0` guard

The frontend prevents a `radius_km=0` query by clamping the slider minimum to `1`. If somehow a `0`
reaches the backend, EVT-006's `proximity_search` returns an empty list (Haversine distance > 0 for
all points); the frontend shows the "no results" toast.

### 5.4 `limit` cap and overflow notice

The frontend passes `limit: flags.max_pins` (server-provided, default 200). When the response length
equals `max_pins`, a warning banner is shown: "Showing the nearest [N] contacts — zoom in or reduce
the radius to see all results." This prevents silent truncation.

### 5.5 "Use my location" button

A `<Button>` labelled "Use my location" calls `navigator.geolocation.getCurrentPosition`. On success,
calls `setCentre([coords.latitude, coords.longitude])` and pans the map via the `useMap()` hook. On
error or denial, shows a `toast.error("Location access denied.")`. The button is rendered outside the
`MapContainer` (above the map, in the page header row) to avoid z-index conflicts with Leaflet.

### 5.6 Marker icon fix

react-leaflet's default marker icons break in Vite because asset hashing changes the file paths.
`CrmMapsPage.tsx` calls the following once at module level:

```typescript
import L from "leaflet";
import markerIcon2x from "leaflet/dist/images/marker-icon-2x.png";
import markerIcon from "leaflet/dist/images/marker-icon.png";
import markerShadow from "leaflet/dist/images/marker-shadow.png";

delete (L.Icon.Default.prototype as any)._getIconUrl;
L.Icon.Default.mergeOptions({ iconUrl: markerIcon, iconRetinaUrl: markerIcon2x,
                               shadowUrl: markerShadow });
```

This is a standard one-time fix and has no runtime side effects.

### 5.7 `party_id` vs `address_id` (PTY-001 soft dependency)

Until PTY-001 ships, EVT-006's `proximity_search` returns items from the `addresses` table where
`party_id` is actually the `address_id` string. The frontend uses this field opaquely as the map pin
key and in the "View Contact" link. Once PTY-001 ships and `proximity_search` is updated to query the
party GSI, the same field carries the real `party_id` — no frontend change is needed.

### 5.8 Duplicate pins at the same location

The deterministic mock geocoder (§2.1) maps distinct addresses to distinct lat/lng values with very
high probability (SHA-256 collisions are negligible). Two contacts at the exact same postal address
will receive the exact same mock lat/lng. Leaflet stacks markers at identical coordinates; since the
dataset is small (≤200 pins) and this is a CRM internal tool, no clustering library is required in
this ticket. EVT-007 can note this as an open question (§10).

### 5.9 Backend 404 when flag is off

`GET /ui/crm/maps/contacts/proximity` (EVT-006) returns 404 when `S.crm_geocoding_enabled` is false.
The proximity `useQuery` is only `enabled` when `flags?.crm_geocoding_enabled === true`, so this 404
is never reached under normal conditions. If it is somehow reached (e.g. flag turned off while the
page is open), React Query surfaces the error as a `toast.error` via the global error handler in
`frontend/src/api/client.ts`.

### 5.10 Map height and responsive layout

`MapContainer` must have an explicit height. The component wraps it in a `div` with
`className="h-[calc(100vh-8rem)] w-full"` (subtracting the AppShell header height). On mobile viewports
the same class collapses gracefully. The radius slider and header row live above the map in a `flex
flex-col` container, so the total page height fits within the viewport without a scrollbar.

### 5.11 No server-side rendering

`CrmMapsPage` is a client-side-only lazy chunk. `leaflet` and `react-leaflet` do not support SSR;
the lazy import ensures they are never evaluated in a non-browser context.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

The `GET /ui/crm/maps/feature-flags` endpoint reads only from `app/core/settings.py` (the `S`
singleton). There is no `if S.dev_mode:` branch. The same handler runs in both environments.

The proximity endpoint (EVT-006) uses `geocode_address` from `app/services/crm_geocoding.py`, which
switches between the deterministic SHA-256 mock and a real HTTP provider based solely on whether
`S.crm_geocoding_provider_url` is empty — not on `S.dev_mode`. This preserves SECOPS-007 parity.

Leaflet tiles are fetched client-side from `tile.openstreetmap.org`. In production, a self-hosted or
CDN-backed tile server URL can be substituted via a `VITE_CRM_MAP_TILE_URL` build variable without any
backend change.

### 7.2 Idempotency

The feature-flags endpoint is idempotent (read-only). Multiple concurrent calls from the same user
return the same payload. The `audit_event` call in the handler is best-effort and wrapped in
`try/except`; a double-call records two audit rows (acceptable — the event is informational only).

The proximity endpoint (EVT-006) is read-only and idempotent; React Query deduplicates concurrent
requests with the same `queryKey`.

### 7.3 Authentication & CSRF

Both backend endpoints use `Depends(require_ui_session)` (imported from `app.services.sessions`,
consistent with `app/routers/contacts.py:12`). The `require_ui_session` dependency enforces CSRF
tokens for non-GET requests (`app/auth/deps.py:330`); both `/feature-flags` and
`/contacts/proximity` are GET requests and therefore skip CSRF validation. Bearer-token callers
(Playwright E2E, API keys) bypass CSRF identically.

### 7.4 No PII in URLs

Lat/lng coordinates are passed as query parameters. These are floating-point numbers with no direct
PII. The audit log records `crm_map_viewed` with `user_sub` only — no coordinates are written to the
audit table. Proximity results returned to the browser contain only names and distances, not raw postal
addresses.

### 7.5 Tile URL and privacy

OpenStreetMap tiles are fetched by the user's browser from a third-party CDN. No contact data is sent
to OpenStreetMap; only tile coordinates (zoom/x/y) are transmitted. This is standard Leaflet behaviour
and equivalent to any other map-embedded web application.

## 8. Backward Compatibility & Migration

### 8.1 No DynamoDB changes

EVT-007 introduces no new tables, no new GSIs, no new attribute writes. The `scripts/local-ddb-init.py`
file is unchanged by this ticket.

### 8.2 No changes to existing endpoints

The feature-flags endpoint is a new route added to the existing EVT-006 router
(`app/routers/crm_geocoding.py`). It does not modify any existing endpoint signature or response
shape.

### 8.3 `app/main.py` router registration

The EVT-006 router (`crm_geocoding_router`) is already registered in `app/main.py` alongside the
contacts router (`app/main.py:683`). EVT-007 adds no new `include_router` call — the `/feature-flags`
route is part of the same router file.

### 8.4 Frontend backward compatibility

The lazy-loaded `CrmMapsPage` is tree-shaken from builds that do not route to `/crm/maps`. The new
`CrmMapFeatureFlags` and `ProximityResult` types in `api/types.ts` are purely additive. The new import
of `isCrmGeocodingEnabled` in `Sidebar.tsx` defaults to `false`, so the nav link is invisible until
explicitly enabled — no existing sidebar entries are affected.

### 8.5 `react-leaflet` / `leaflet` package addition

Adding `react-leaflet` and `leaflet` to `frontend/package.json` increases the build size by
approximately 150 KB (minified+gzip). These packages are loaded only when the user navigates to
`/crm/maps` (lazy split). No existing pages are affected.

## 10. Open Questions / Assumptions

1. **Marker clustering:** With `max_pins=200` and the mock geocoder producing deterministic but
   globally-distributed coordinates, the map will show up to 200 scattered pins. Whether to add a
   clustering library (e.g. `react-leaflet-cluster`) is deferred to a follow-up ticket.

2. **Real tile server:** The spec uses the public OpenStreetMap tile CDN. Production deployments with
   privacy requirements should use a self-hosted tile server. A `VITE_CRM_MAP_TILE_URL` env var is
   reserved for this substitution.

3. **PTY-001 `party_id` semantics:** Until PTY-001 ships, the "View Contact" link in each pin popup
   uses `party_id` which is currently an `address_id`. The link target `/contacts?highlight=<id>` will
   not highlight anything in the current contacts page. This is acceptable for a P2 ticket in the
   pre-PTY state; a follow-up CRM ticket should wire the deep-link properly once PTY ships.

4. **Geolocation permission UX:** `navigator.geolocation` prompts the user for permission. The current
   spec shows a `toast.error` on denial. A more polished empty-state prompt ("Allow location to centre
   the map, or click to choose a point") is out of scope for this ticket.

5. **Accessibility of the map:** Leaflet maps are notoriously difficult to make fully keyboard-navigable.
   For EVT-007, the map is supplementary to the existing contacts list — all geocoded contacts are
   still accessible via the text-based `/contacts` page. Full a11y compliance for the map is deferred.

6. **Default centre coordinates:** The default `37.7749, -122.4194` (San Francisco) is a neutral
   placeholder. Operators deploying in other regions should override `CRM_MAP_DEFAULT_LAT/LNG`. The
   "Use my location" button is the primary UX for self-locating.
