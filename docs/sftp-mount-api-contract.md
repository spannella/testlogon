# SFTP Mount Product/API Contract (SFTP-001)

This document finalizes SFTP-001 by defining:
- canonical mounted path namespace and path resolution rules,
- canonical mount state model,
- deterministic backend behavior for mounted paths across list/download/upload/delete/move,
- backward-compatibility constraints for existing non-mounted paths.

---

## 1) Canonical mounted path namespace

### 1.1 Namespace shape
Mounted SFTP files are represented as virtual file-manager paths under:

- `/mounts/{mount_id}/`

Where:
- `mount_id` is an opaque stable identifier generated by backend mount-create API.
- `{mount_id}` segment is required and case-sensitive.
- Everything after `/mounts/{mount_id}/` is interpreted as the mount-relative path.

Examples:
- Mount root folder: `/mounts/mnt_01HXYZABCDEF/`
- Child folder: `/mounts/mnt_01HXYZABCDEF/projects/`
- File: `/mounts/mnt_01HXYZABCDEF/projects/spec.pdf`

### 1.2 Reserved namespace rules
- `/mounts/` is reserved for external mounts and cannot be created/renamed/deleted as a normal user-managed folder.
- Existing user-managed folders/files outside `/mounts/` are unaffected.

### 1.3 Path normalization
Requests are normalized using existing file-manager path semantics plus mount-specific rules:
- Multiple slashes collapse to single slash.
- Paths must start with `/`.
- `.` segments are ignored.
- `..` segments are rejected.
- Folder APIs require trailing `/`; file APIs reject trailing `/` where applicable.
- For mounted paths, normalized mount-relative path must never escape configured `remote_root`.

If normalization fails, backend returns `400 invalid_path`.

---

## 2) Path resolution algorithm

Given input `path`:
1. Normalize path using existing `norm_path` semantics.
2. If path does **not** start with `/mounts/`, route to native provider behavior (current S3-backed path).
3. If path starts with `/mounts/`, parse `mount_id` as second segment.
4. Look up mount metadata by `{owner_user, mount_id}`.
5. Verify mount is accessible to requester (owner/admin policy + route authorization).
6. Resolve mount-relative path and map to remote SFTP absolute path under `remote_root`.
7. Dispatch operation through `SFTPProvider`.

Deterministic error mapping:
- Unknown mount id: `404 mount_not_found`
- Unauthorized mount access: `403 mount_forbidden`
- Mount disabled: `409 mount_disabled`
- Invalid mounted path escape attempt: `400 invalid_mount_path`

## 3) Canonical mount state model

Allowed state values:
- `healthy`
- `degraded`
- `auth_failed`
- `unreachable`
- `disabled`

### 3.1 State semantics
- `healthy`: recent probe and/or operation succeeded; mount can service requests.
- `degraded`: intermittent failures observed; operations may still succeed.
- `auth_failed`: credential or host-key validation failure; data operations blocked.
- `unreachable`: remote host/network unavailable or timed out; operations fail fast with retriable signal.
- `disabled`: mount administratively or user disabled; all data operations blocked.

### 3.2 State transition rules
- `disabled` is set explicitly by lifecycle APIs (disable/delete/revoke flow).
- `auth_failed` set on deterministic auth/host-key failures.
- `unreachable` set on transport/connectivity failures beyond retry budget.
- `degraded` set on repeated transient failures that do not fully block operations.
- Successful probe/operation can transition `degraded|unreachable|auth_failed` back to `healthy` only when auth + transport checks pass.

## 4) Backend behavior by operation

The table below defines deterministic behavior for mounted paths.

| Operation | Mounted path behavior | Native path behavior |
| --- | --- | --- |
| List (`/v1/fs/list`) | Resolve mount and execute `SFTPProvider.list_dir` for mount-relative folder. | Existing behavior unchanged. |
| Download (`/v1/fs/download`) | Resolve mount and stream bytes via `SFTPProvider.read_stream`. | Existing behavior unchanged. |
| Upload (`/v1/fs/upload`, `complete-upload` path) | For mounted destination paths, write via `SFTPProvider.write_stream` (direct pass-through mode). | Existing behavior unchanged. |
| Delete (`/v1/fs/delete`) | For mounted file/folder targets, call `SFTPProvider.delete` subject to mount policy. | Existing behavior unchanged. |
| Move (`/v1/fs/move`) | Mounted↔mounted move allowed only within same mount unless cross-mount copy policy is explicitly implemented. Mounted↔native move is rejected in v1 with explicit error. | Existing behavior unchanged for native↔native. |
| Share (`/v1/fs/share`, `/v1/fs/unshare`, `/v1/fs/shared-with`) | **Not supported in initial policy** for mounted paths. Return explicit policy error for any mounted path share attempt. | Existing behavior unchanged. |

### 4.1 Move constraints in v1
- Allowed: same-mount rename/move.
- Rejected: cross-mount move.
- Rejected: mounted path to native path move.
- Rejected: native path to mounted path move.

Recommended error code for rejected move classes: `409 unsupported_move_boundary`.

### 4.2 Mount state gate behavior by operation
For mounted operations:
- `healthy`: allow.
- `degraded`: allow with normal retries/timeouts.
- `auth_failed`: reject write/read/list/delete/move with `409 mount_auth_failed`.
- `unreachable`: reject with `503 mount_unreachable`.
- `disabled`: reject with `409 mount_disabled`.


### 4.3 Share policy in v1
- Mounted SFTP content sharing is disabled by policy in the initial rollout.
- API calls that attempt to share/unshare/query sharing on mounted paths return `403 sftp_mount_share_not_allowed`.
- This policy is deterministic and independent of mount read/write settings.

## 5) API contract additions

### 5.1 Mount object shape (returned by mount APIs)
Minimum required fields:
- `id: string`
- `type: "sftp"`
- `protocol: "sftp" | "scp" | "ftp"`
- `display_name: string`
- `path_prefix: string` (always `/mounts/{id}/`)
- `remote_root: string`
- `status: "healthy" | "degraded" | "auth_failed" | "unreachable" | "disabled"`
- `read_only: boolean`
- `last_tested_at: string|null` (ISO-8601)
- `last_error_code: string|null`
- `last_error_message: string|null` (sanitized, no secrets)
- `created_at: string`
- `updated_at: string`

### 5.2 Transport protocol notes
- Initial supported mount protocol values: `sftp`, `scp`, `ftp`.
- `scp` mounts reuse SSH transport semantics with file operations routed through the mounted provider abstraction.
- `ftp` mounts are password-auth only and do not use SSH host-key verification.

### 5.3 Error code contract
Stable mount-related error codes introduced by SFTP-001:
- `invalid_path`
- `invalid_mount_path`
- `mount_not_found`
- `mount_forbidden`
- `mount_disabled`
- `mount_auth_failed`
- `mount_unreachable`
- `unsupported_move_boundary`
- `sftp_mount_share_not_allowed`

---

## 6) Backward compatibility guarantees

SFTP-001 requires the following compatibility guarantees:
1. Any path not under `/mounts/{mount_id}/` continues through existing native file-manager behavior.
2. Existing request/response fields for non-mounted operations are unchanged.
3. Existing clients that do not use mount APIs are unaffected by feature rollout.
4. SFTP functionality remains behind feature flag until explicitly enabled.

---

## 6.1 Dev inspection endpoint contract (`GET /v1/fs/mounts/{mount_id}/mock-files`)

This endpoint is only for local development while `FILEMGR_SFTP_BACKEND=mock` is enabled.

Query parameters:
- `path` (default `/`)
- `limit` (default `200`, min `1`, max `1000`)
- `cursor` (opaque pagination cursor)

Success response:
- `mount_id`, `owner`, `backend`, `path`
- `items: Array<{name,path,type,size,modified_at}>`
- `limit: number`
- `cursor: string|null` (null when there are no more entries)

Stable error codes for UI handling:
- `sftp_mock_backend_disabled`
- `mock_path_invalid`
- `mock_path_not_found`
- `mock_path_not_directory`
- `mock_path_invalid_cursor`
- `mock_path_invalid_limit`

## Audit event taxonomy

All SFTP mount and credential flows emit mount-specific audit events. Audit payloads **must never include raw credential material** (`password`, `private_key`, `private_key_passphrase`, ciphertext blobs).

### Event names

- Mount lifecycle:
  - `filemgr_sftp_mount_created`
  - `filemgr_sftp_mount_updated`
  - `filemgr_sftp_mount_deleted`
  - `filemgr_sftp_mount_tested`
  - `filemgr_sftp_mount_revoked`
  - `filemgr_sftp_mount_credential_rotated`
  - `filemgr_sftp_mount_health_refresh`
- Credential lifecycle:
  - `filemgr_sftp_credential_upserted`
  - `filemgr_sftp_credential_accessed`
  - `filemgr_sftp_credential_deleted`
- Data operations on mounted paths:
  - `filemgr_sftp_data_listed`
  - `filemgr_sftp_data_read`
  - `filemgr_sftp_data_written`
  - `filemgr_sftp_data_deleted`
  - `filemgr_sftp_data_moved`

### Expected payload shape (fields)

- Common:
  - `owner` (string, target user)
  - `mount_id` (string, when available)
  - `storage_backend` (`sftp`)
  - `path` (string, when operation is path-scoped)
  - `outcome` (`success|failure|fallback` depending on route)
- Status/health:
  - `status`, `previous_status`, `status_changed`
  - `last_error_code` (stable error code)
- Data operation-specific:
  - `src`, `dst` for move/rename
  - `bytes_written` for write
  - `bytes_requested` for download/read
  - `item_count` for list
  - `deleted_count` for folder delete
- Credential auditing:
  - `auth_mode`, `operation`, `secret_redacted=true`

### Redaction rules

- Never emit or log secret fields or encrypted blobs.
- Only emit non-sensitive credential metadata (`auth_mode`, owner/mount context).
- Use stable error codes/messages; do not include raw private key or password parsing artifacts.
