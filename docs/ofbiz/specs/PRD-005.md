# PRD-005 — Category-tree router endpoints

**Type:** Feature | **Priority:** P0 | **Estimate:** 2 days
**Milestone:** 2 — Category Trees

---

## 1. Summary & Goal

PRD-005 exposes the category-tree operations implemented in `app/services/product_categories.py` (PRD-004) as four new HTTP endpoints added to the existing catalog router (`app/routers/catalog.py`, prefix `/ui/catalog`). All four endpoints are gated behind `S.product_depth_enabled`: when the flag is off they return 404, making them invisible to existing clients. No existing `/categories` route is modified.

The four new endpoints are:

| Method | Path | Purpose |
|--------|------|---------|
| `POST` | `/categories/{category_id}/children` | Create a child category under a parent |
| `PATCH` | `/categories/{category_id}/move` | Re-parent a category (move it in the tree) |
| `GET` | `/categories/{category_id}/tree` | Return a category's full subtree (recursive descendants) |
| `GET` | `/categories/{category_id}/breadcrumb` | Return the ancestry path from root to the category |

The router is already registered in `app/main.py` at `:671` (`app.include_router(catalog_router)`); no new registration is needed — the four functions are appended to the existing `router` object defined at `app/routers/catalog.py:42`.

## 2. Context & Current State

### 2.1 Existing catalog router and ownership guard

`app/routers/catalog.py` defines a single `APIRouter` at `:42`:

```python
# app/routers/catalog.py:42
router = APIRouter(
    prefix="/ui/catalog",
    tags=["catalog"],
    dependencies=[Depends(maybe_enforce_api_key_route_policy)],
)
```

This router is imported and registered in `app/main.py:72,671`. Every new endpoint appended to `router` in the same file inherits the `/ui/catalog` prefix and the `maybe_enforce_api_key_route_policy` dependency automatically.

The ownership guard at `app/routers/catalog.py:247` is:

```python
# app/routers/catalog.py:247–252
def _require_category_owner(category_id: str, user_id: str) -> Dict[str, Any]:
    item = _get_category_meta(category_id)
    creator_id = item.get("creator_id")
    if creator_id and creator_id != user_id:
        raise HTTPException(status_code=403, detail="Not authorized to manage this category.")
    return item
```

All four new endpoints delegate ownership enforcement to this function, just as `create_item` (`:352–353`), `delete_category` (`:324–325`), and `update_item` (`:519–520`) already do.

### 2.2 Pagination helpers

`app/routers/catalog.py:158–175` defines `encode_next_token` / `decode_next_token` — base64-URL encode/decode over a JSON-serialized DynamoDB `LastEvaluatedKey`. The `GET /categories/{id}/tree` endpoint uses these to support cursor-based pagination over a wide subtree. The `GET /categories/{id}/breadcrumb` does not paginate (depth is bounded by `S.product_depth_max_category_depth`, an int setting from PRD-002 defaulting to 10).

### 2.3 Category storage on T.catalog (current flat model)

Today a category is one row: `PK=CAT#{id}`, `SK=META`, with `entity="category"`, `GSI1PK="CATS"`, `GSI1SK="{name.lower()}#{id}"` (written at `app/routers/catalog.py:260–283`). There is no `parent_category_id`, no `path`, no `position` on these rows today.

PRD-004's service (`app/services/product_categories.py`) writes a separate `TREE` row on `T.product_depth` (PK=`CAT#{category_id}`, SK=`TREE`, `GSI_PARENT_PK`/`GSI_PARENT_SK` for the `ByParent` GSI). The `META` row on `T.catalog` is **not modified** — tree-structural fields (`parent_category_id`, `path`, `position`, `depth`) live exclusively on the `TREE` row in `T.product_depth`. See PRD-004 §3.2 for confirmation. `T.product_depth` handle is wired in `app/core/tables.py` by PRD-002 (not yet in codebase).

### 2.4 Feature flag pattern

The canonical pattern for default-off feature gating in router endpoints comes from the returns-RMA router: a private `_require_enabled()` helper raises `HTTPException(404)` when the flag is off. This ticket adds an identical helper:

```python
def _require_depth_enabled() -> None:
    if not getattr(S, "product_depth_enabled", False):
        raise HTTPException(status_code=404, detail="Product depth is not enabled.")
```

This matches `app/services/inventory.py:54–56` (verified; `_require_enabled` raises 404 when `inventory_reservations_enabled` is off) and `app/routers/catalog.py:591–592` (`_catalog_upload_unavailable` raises 501 for missing multipart) as the established not-enabled pattern.

### 2.5 Audit event plumbing

`app/routers/catalog.py:682` already shows the lazy-import pattern for `app.services.alerts.write_alert`. PRD-005 instead uses the richer `audit_event` function (`app/services/alerts.py:644`) — signature `audit_event(event: str, user_sub: str, request=None, **fields: Any)` — which writes to `T.alerts` and accepts arbitrary keyword fields. Note: `request` is the third positional parameter (pass `None` in the router helper). The `add_child` and `move_category` mutations emit best-effort audit events; read endpoints (`tree`, `breadcrumb`) do not.

### 2.6 Route ordering constraint

FastAPI matches routes in declaration order (`app/routers/catalog.py` currently has 1000 lines; the last route decorator is at `:954`). The four new routes use paths prefixed with `/categories/{category_id}/` which is unambiguous because the existing routes under the same prefix are:
- `POST /categories/{category_id}/items` (`:352`)
- `GET /categories/{category_id}/items` (`:394`)
- `PATCH /categories/{category_id}/items/{item_id}` (`:519`)
- `POST /categories/{category_id}/items/{item_id}/images/upload` (`:596`)

The new sub-paths (`/children`, `/move`, `/tree`, `/breadcrumb`) are new literal segments — there is no ambiguity with existing patterns. They must be appended at the end of the file (after line 1000), after the `bulk-update` route at `:954`.

## 3. Data Model

PRD-005 is a router-only ticket; all DynamoDB schema changes were specified in PRD-002 and implemented by PRD-004. This section describes only what rows the new endpoints read/write and which indexes they use.

### 3.1 Rows written by POST /categories/{id}/children

`POST /categories/{id}/children` attaches an **existing** flat category (identified by `child_category_id` in the request body) into the tree under the given parent. The service function `product_categories.add_child(*, parent_category_id, child_category_id, user_sub, position)` (PRD-004 §4.1.2):

1. Does **not** create a new `T.catalog` META row — the child category must already exist (created via the existing `POST /categories` endpoint). The META row is read but never written.
2. Writes one new `TREE` row to `T.product_depth`: `PK=CAT#{child_category_id}`, `SK=TREE`, carrying `parent_category_id`, `path`, `depth`, `position`, `creator_id`, `GSI_PARENT_PK="PARENT#{parent_category_id}"` (or `"PARENT#root"` for root-level), `GSI_PARENT_SK=<position int>`. A `ConditionalCheckFailedException` on this write → 409 `"Category is already in the tree"`.

**Implication for the router**: The request body (`CategoryChildCreateIn`) must carry the `child_category_id` of the existing category to attach, not a `name`/`description` for a new one. The `name` / `description` / `category_id` fields in `CategoryChildCreateIn` (§4.1) must be replaced with a single required `child_category_id: str` field. The router calls `add_child(parent_category_id=category_id, child_category_id=body.child_category_id, user_sub=ctx["user_sub"], position=body.position)` — ownership of the child is checked by the service itself (PRD-004 §4.1.2 step 3), so a separate `_require_category_owner` call on the child is redundant but harmless; the parent `category_id` path parameter is verified to exist via `_get_category_meta` before the service call.

### 3.2 Rows touched by PATCH /categories/{id}/move

`PATCH /categories/{id}/move` delegates to `product_categories.move_category(*, category_id, new_parent_category_id, user_sub, position)` (PRD-004 §4.1.3). That service function:

1. Reads the category's existing `TREE` row from `T.product_depth` (404 if not in the tree yet).
2. Overwrites the `TREE` row for `category_id` with the new `parent_category_id`, `path`, and `depth`. The `T.catalog` META row is **not touched**.
3. BFS-traverses all descendants via `list_children` and updates each descendant's `TREE` row in-place (`update_item` per row). No scan of `T.catalog` is done.
4. **Cycle check**: raises 422 `"Re-parenting would create a cycle"` if `new_parent_row["path"]` starts with `category_row["path"]` (path-prefix check, not breadcrumb walk — PRD-004 §4.1.3 step 5b).

### 3.3 GSI access pattern for GET /categories/{id}/tree

`GET /categories/{id}/tree` calls `product_categories.list_descendants(category_id, *, max_results=500)` (PRD-004 §4.1.7). This function does **not** accept a `start_key` / cursor parameter — it performs an internal BFS using repeated `list_children` calls bounded by `max_results`, returning `List[Dict[str, Any]]` (not a `(list, lek)` tuple). Each `list_children` call queries the `ByParent` GSI:

```
IndexName = "ByParent"
KeyConditionExpression = GSI_PARENT_PK = "PARENT#{category_id}"
ScanIndexForward = True   # ascending position
Limit = 200 (per list_children call)
```

Because `list_descendants` returns a flat list rather than a paginated cursor, `CategoryTreeOut.next_token` is always `null`. The `page_size` / `next_token` query parameters in the endpoint signature (§4.2) are **removed**; callers receive all descendants (up to `max_results=500`) in one response. The router returns `CategoryTreeNodeOut` objects built from `TREE` rows — fields `parent_category_id`, `depth`, `position`, `path` come from `T.product_depth`; `name` and `description` must be fetched from `T.catalog` META rows (one `get_item` per node, or the router can skip them and return `name=None` from the `TREE` row since the `TREE` row does not store `name`). **Design note**: the `TREE` row carries `category_id`, `creator_id`, `parent_category_id`, `path`, `depth`, `position`, `created_at` but NOT `name`/`description` (those live only on the META row). Either the router calls `_get_category_meta` per node for names, or `CategoryTreeNodeOut.name` is made `Optional[str]` and populated only when desired.

### 3.4 Access pattern for GET /categories/{id}/breadcrumb

`GET /categories/{id}/breadcrumb` calls `product_categories.get_breadcrumb(category_id)` (PRD-004 §4.1.6). This function reads the `TREE` row from `T.product_depth`, parses the materialized `path` to extract ancestor IDs, then performs one `T.catalog.get_item(PK=CAT#{id}, SK=META)` per ancestor to fetch the display `name`. It returns `List[{"category_id": str, "name": str}]` (minimal dict, not a full category item). No GSI is needed; traversal uses the materialized path string and O(depth) point lookups. If `category_id` has no `TREE` row (not yet placed in the tree), `_require_tree_row` raises 404 before returning any crumbs — the router's `if not crumbs` check in §4.2 therefore also fires on 404, but the service raises first.

## 4. API / Service Design

### 4.1 Request / Response models

All new models are appended to `app/models.py` alongside the existing catalog models (after `CatalogCategoryListOut` at `:534`):

```python
# app/models.py — new models for PRD-005

class CategoryChildCreateIn(BaseModel):
    """Request body for POST /categories/{id}/children.
    Attaches an existing flat category into the tree under the given parent.
    The category identified by child_category_id must already exist (created via
    POST /categories). The router's category_id path param is the parent.
    """
    child_category_id: str = Field(min_length=1, max_length=200,
                                   description="category_id of the existing flat category to attach.")
    position: Optional[int] = Field(default=None, ge=0, le=10_000_000)


class CategoryMoveIn(BaseModel):
    """Request body for PATCH /categories/{id}/move."""
    new_parent_category_id: Optional[str] = Field(
        default=None,
        description="Target parent category_id; null/absent means move to root."
    )
    position: Optional[int] = Field(default=None, ge=0, le=10_000_000)


class CategoryTreeNodeOut(BaseModel):
    """One node in the tree or breadcrumb response."""
    category_id: str
    name: str
    description: Optional[str] = None
    creator_id: Optional[str] = None
    parent_category_id: Optional[str] = None
    position: Optional[int] = None
    path: Optional[str] = None          # materialized ancestry, e.g. "root/a/b/c"
    depth: int = 0                       # 0 = root, 1 = immediate child of root, …
    created_at: str
    child_count: int = 0                 # direct children (best-effort from index)


class CategoryTreeOut(BaseModel):
    """Response for GET /categories/{id}/tree.
    No pagination: list_descendants (PRD-004 §4.1.7) returns a bounded flat list
    (max_results=500); next_token is always null.
    """
    root: CategoryTreeNodeOut           # the requested node itself (META row)
    nodes: List[CategoryTreeNodeOut]    # flat list of ALL descendants (TREE rows, up to 500)


class CategoryBreadcrumbOut(BaseModel):
    """Response for GET /categories/{id}/breadcrumb."""
    crumbs: List[CategoryTreeNodeOut]   # ordered root → leaf (the requested node last)
```

`CatalogPageOut` (`:516`) is **not** used for `CategoryTreeOut` — `list_descendants` returns a plain list with no cursor, so extending `CatalogPageOut` would add a misleading `next_token` field.

### 4.2 Endpoint signatures

All four endpoints live in `app/routers/catalog.py`, appended after the existing routes.

#### POST /categories/{category_id}/children

```python
@router.post(
    "/categories/{category_id}/children",
    response_model=CategoryTreeNodeOut,
    status_code=201,
)
async def add_child_category(
    category_id: str,
    body: CategoryChildCreateIn,
    ctx=Depends(require_ui_session),
) -> CategoryTreeNodeOut:
    _require_depth_enabled()
    _get_category_meta(category_id)   # 404 if parent not found; no ownership check here
    # Ownership of child_category_id is enforced inside the service (PRD-004 §4.1.2 step 3)
    from app.services import product_categories
    node = product_categories.add_child(
        parent_category_id=category_id,
        child_category_id=body.child_category_id,
        user_sub=ctx["user_sub"],
        position=body.position,
    )
    _audit_depth("catalog.category.child_added", ctx["user_sub"],
                 parent_category_id=category_id, child_category_id=body.child_category_id)
    return _category_node_out(node)
```

**Auth:** `require_ui_session` (cookie or Bearer). Ownership of `child_category_id` enforced inside the service (403 if caller does not own the child). Parent `category_id` existence checked via `_get_category_meta` (404 if absent). Flag gate: 404 when off.

#### PATCH /categories/{category_id}/move

```python
@router.patch(
    "/categories/{category_id}/move",
    response_model=CategoryTreeNodeOut,
)
async def move_category(
    category_id: str,
    body: CategoryMoveIn,
    ctx=Depends(require_ui_session),
) -> CategoryTreeNodeOut:
    _require_depth_enabled()
    # Ownership of category_id is enforced inside the service (PRD-004 §4.1.3 step 3)
    from app.services import product_categories
    node = product_categories.move_category(
        category_id=category_id,
        new_parent_category_id=body.new_parent_category_id,
        user_sub=ctx["user_sub"],
        position=body.position,
    )
    _audit_depth("catalog.category.moved", ctx["user_sub"],
                 category_id=category_id, new_parent_category_id=body.new_parent_category_id)
    return _category_node_out(node)
```

**Auth:** `require_ui_session`. Ownership of `category_id` enforced inside the service (403 if caller does not own it). Flag gate: 404 when off.

#### GET /categories/{category_id}/tree

```python
@router.get(
    "/categories/{category_id}/tree",
    response_model=CategoryTreeOut,
)
async def get_category_tree(
    category_id: str,
    ctx=Depends(require_ui_session),
    max_results: int = Query(default=100, ge=1, le=500),
) -> CategoryTreeOut:
    _require_depth_enabled()
    root_meta = _get_category_meta(category_id)   # 404 if META row not found
    from app.services import product_categories
    # list_descendants returns List[dict] (TREE rows), not a (list, lek) tuple
    descendants = product_categories.list_descendants(
        category_id=category_id,
        max_results=max_results,
    )
    return CategoryTreeOut(
        root=_category_node_out(root_meta),
        nodes=[_category_node_out(d) for d in descendants],
    )
```

**Auth:** `require_ui_session`. No ownership check — reading a tree is not destructive; any authenticated user may browse. Flag gate: 404 when off. Note: `TREE` rows do not contain `name`/`description`; `_category_node_out` must tolerate absent name (or the router must join with META rows per node for display names).

#### GET /categories/{category_id}/breadcrumb

```python
@router.get(
    "/categories/{category_id}/breadcrumb",
    response_model=CategoryBreadcrumbOut,
)
async def get_category_breadcrumb(
    category_id: str,
    ctx=Depends(require_ui_session),
) -> CategoryBreadcrumbOut:
    _require_depth_enabled()
    from app.services import product_categories
    # get_breadcrumb calls _require_tree_row internally → raises 404 if category not in tree.
    # Returns List[{"category_id": str, "name": str}] (minimal dicts, not full TREE rows).
    crumbs = product_categories.get_breadcrumb(category_id)
    return CategoryBreadcrumbOut(crumbs=[_category_node_out(c) for c in crumbs])
```

**Auth:** `require_ui_session`. No ownership check. Flag gate: 404 when off. Note: `get_breadcrumb` raises 404 internally for a missing or not-yet-tree-placed category; the `if not crumbs` guard is therefore not reached for a missing category but is still safe as a defensive empty-list guard.

## 5. Detailed Behavior & Edge Cases

### 5.1 POST /categories/{id}/children — normal flow

1. Flag check → 404 if `product_depth_enabled` is False.
2. `_require_category_owner(category_id, user_sub)` → 404 if parent not found; 403 if owned by another user.
3. If `position` is not supplied, the service assigns `position = current_max_child_position + 1` (queried from `ByParent` GSI) to append the new child.
4. Service writes child META row to `T.catalog` and child-index row to `T.product_depth` in a non-transactional sequence (the index write is best-effort; partial failure leaves an orphaned META row without a `ByParent` entry — the repair path is a re-index from the META row's `parent_category_id` field).
5. Returns `CategoryTreeNodeOut` with `status_code=201`.

### 5.2 POST /categories/{id}/children — 409 already in tree

If `child_category_id` already has a `TREE` row on `T.product_depth`, the service raises `409 Conflict` (`"Category is already in the tree"`) via a `ConditionalCheckFailedException` on the `put_item` call (PRD-004 §4.1.2 step 10). The router propagates this without catching it. The 409 pattern mirrors `create_category` at `app/routers/catalog.py:276–283`.

### 5.3 PATCH /categories/{id}/move — cycle detection

The service (`product_categories.move_category`) performs a cycle check before writing using a path-prefix comparison (PRD-004 §4.1.3 step 5b): if `new_parent_row["path"]` starts with `category_row["path"] + "/"` or equals `category_row["path"]`, the move would create a cycle. The service raises `HTTPException(422, "Re-parenting would create a cycle")`. The router propagates this. The cycle check does **not** use `get_breadcrumb` — it uses the materialized `path` field for O(1) detection without additional DDB reads.

### 5.4 PATCH /categories/{id}/move — moving to root

`body.new_parent_category_id = null` (or absent) moves the category to the root level. The service sets `parent_category_id = None`, `path = "root/{category_id}"`, depth=1, and sets `GSI_PARENT_PK="PARENT#root"` on the `TREE` row (PRD-004 §4.1.3 step 6).

### 5.5 PATCH /categories/{id}/move — cross-owner move

A category may only be moved by its owner. The service enforces ownership of `category_id` via `_require_catalog_meta` + `creator_id` check (PRD-004 §4.1.3 step 3). The `new_parent_category_id` target is not owner-checked: the move does not transfer ownership. If `new_parent_category_id` does not have a `TREE` row, the service raises 404 `"Category ... is not in the tree"`.

### 5.6 GET /categories/{id}/tree — no cursor pagination

`list_descendants` (PRD-004 §4.1.7) performs an internal BFS and returns all descendants up to `max_results` in a single call. There is no cursor/`next_token` — the response either contains up to `max_results` nodes or all descendants, whichever is smaller. To retrieve a subtree larger than `max_results`, clients must query sub-trees recursively via their own `/tree` endpoints.

`CategoryTreeOut.root` always returns the requested category's node (even when `nodes` is empty — the category exists but has no children in the tree yet).

### 5.7 GET /categories/{id}/tree — 404

If `category_id` does not map to a `CAT#` / `META` row in `T.catalog`, `_get_category_meta` raises `HTTPException(404)` at `app/routers/catalog.py:243`.

### 5.8 GET /categories/{id}/breadcrumb — depth limit

`get_breadcrumb` parses the materialized `path` string (e.g. `"root/abc/def/ghi"`) to derive ancestor IDs, bounded naturally by `S.product_depth_max_category_depth` (the tree enforces this during `add_child`). No runtime truncation occurs — the path cannot have more segments than `_max_depth()` since the service rejected deeper inserts. The response `crumbs` list is ordered root-first, leaf last.

### 5.9 GET /categories/{id}/breadcrumb — flat category (no TREE row)

A category created via `POST /categories` but never attached to the tree via `POST /children` has no `TREE` row on `T.product_depth`. `get_breadcrumb` calls `_require_tree_row` which raises `HTTPException(404, "Category ... is not in the tree")`. The endpoint returns 404 — this is intentional; breadcrumb is only available for tree-placed categories.

### 5.10 Non-owner reads tree/breadcrumb

`GET /tree` and `GET /breadcrumb` are read-only. Any authenticated session may read any category's tree or breadcrumb, regardless of whether they own the category. This matches the behavior of `GET /categories` (`:293`) and `GET /categories/{id}/items` (`:394`), which also do not require ownership for read access.

### 5.11 Items in a category are unaffected by tree operations

Moving a category does not move its items. Items remain on `T.catalog` with their original `PK=CAT#{id}` / `SK=ITEM#{item_id}` rows. The items' `category_id` attribute stays the same. This is intentional: the category tree is a logical grouping layer; item resolution always goes through `CAT#{category_id}` as the DynamoDB partition key regardless of where that category sits in the tree.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

All four endpoints read/write `T.catalog` (the existing `shopping_catalog` DynamoDB table, pointing to DynamoDB Local on port 8001 in dev, real DynamoDB in prod) and `T.product_depth` (the new `product_depth` table, same endpoint routing). No in-process mock, no `dev_mode` branch, no `if S.dev_mode` conditional in any of the four route handlers. The same code path runs in both environments.

Audit events are emitted via `app.services.alerts.audit_event` — which writes to `T.alerts`. In dev this is DynamoDB Local; in prod it is real DynamoDB. No divergence.

### 7.2 Idempotency of POST /categories/{id}/children

`add_child` uses a conditional `put_item` with `attribute_not_exists(PK) AND attribute_not_exists(SK)` on the `TREE` row in `T.product_depth` (PRD-004 §4.1.2 step 10). A second call with the same `child_category_id` returns 409 `"Category is already in the tree"`. The call is naturally idempotent on retry-after-409: simply return the existing `TREE` row. The `child_category_id` is always supplied by the caller (it identifies an existing flat category), so no UUID generation occurs and idempotency is deterministic.

### 7.3 Idempotency of PATCH /categories/{id}/move

`move_category` is idempotent: re-calling with the same `new_parent_category_id` when the category is already there is a no-op at the service level — the overwrite `put_item` is unconditional (PRD-004 §4.1.3 step 8), so repeating the same move writes the same values.

### 7.4 Security: cycle injection

The cycle detection in `move_category` uses a materialized-path prefix check (O(1), no DDB reads for cycle detection itself). An adversarial deep tree cannot cause unbounded DynamoDB reads from the cycle check. The subsequent `_bulk_update_paths` BFS is bounded by `max_results` (500) via `list_children`. The router never bypasses the service-level cycle check.

### 7.5 Security: ownership on mutations

`POST /children` checks ownership of `child_category_id` inside the service (PRD-004 §4.1.2). `PATCH /move` checks ownership of `category_id` inside the service (PRD-004 §4.1.3). The router does not duplicate these checks (the service is authoritative), but `_get_category_meta` is called for the parent `category_id` in `POST /children` to give a friendly 404 before the service is called. Read endpoints (`/tree`, `/breadcrumb`) intentionally skip ownership.

### 7.6 CSRF

All four endpoints are under `require_ui_session`. Cookie-authenticated non-GET requests (POST, PATCH) require `x-csrf-token` header matching the session's stored `csrf_token` and the `ui_csrf` cookie value, as documented in CLAUDE.md. Bearer-authenticated requests skip CSRF. This is inherited from the existing auth infrastructure with no special handling needed.

## 8. Backward Compatibility & Migration

### 8.1 Zero change to existing routes

The four new routes use distinct path suffixes (`/children`, `/move`, `/tree`, `/breadcrumb`) that do not conflict with any existing path in the catalog router. FastAPI's declaration-order matching is not affected: the new routes are appended at the end of `app/routers/catalog.py` (after `:954`, the current last route `POST /items/bulk-update`).

### 8.2 Existing flat categories

Categories created via `POST /categories` before being tree-placed have no `TREE` row on `T.product_depth`. The new endpoints handle this:

- `GET /breadcrumb` for a flat category returns **404** `"Category ... is not in the tree"` — breadcrumb requires a `TREE` row (§5.9).
- `GET /tree` for a flat category: `_get_category_meta` succeeds (returns META row), but `list_descendants` returns `[]` (no children in `T.product_depth`). Response: `{ root: <node>, nodes: [] }`.
- `POST /children` targeting a flat category as parent: `_get_category_meta` succeeds; `add_child` then calls `_require_tree_row(parent_category_id)` → 404 `"Category ... is not in the tree"`. The parent must be placed in the tree before children can be added to it.
- `PATCH /move` on a flat category: the service calls `_require_tree_row(category_id)` → 404. The category must be placed in the tree first.

### 8.3 No DynamoDB schema migration required

`T.catalog`'s `shopping_catalog` table schema is unchanged — confirmed: `scripts/local-ddb-init.py:117–125` shows `PK`/`SK`/`GSI1`/`ByItemId` only; no new columns on the existing table. The `T.product_depth` `product_depth` table is added by PRD-002 to `scripts/local-ddb-init.py` and created at `just restart`; in production it must be created before `PRODUCT_DEPTH_ENABLED` is set to `true`.

### 8.4 CatalogCategoryOut unchanged

The existing `CatalogCategoryOut` model (`app/models.py:526`) does not gain any tree fields — that is PRD-003's responsibility (`CategoryTreeNodeOut` is a separate, additive model). `GET /categories` continues returning `CatalogCategoryOut` objects. Clients that do not know about the tree API are unaffected.

## 10. Open Questions / Assumptions

1. **CONFIRMED** (from PRD-004 spec): Service function signatures are:
   - `add_child(*, parent_category_id, child_category_id, user_sub, position) → Dict[str, Any]`
   - `move_category(*, category_id, new_parent_category_id, user_sub, position) → Dict[str, Any]`
   - `list_descendants(category_id, *, max_results=500) → List[Dict[str, Any]]` (no cursor)
   - `get_breadcrumb(category_id) → List[{"category_id": str, "name": str}]`
   These are definitively specified in PRD-004 §4. The router delegation calls use these exact signatures.

2. **CONFIRMED** (from PRD-004 §2.4): `S.product_depth_max_category_depth` is introduced by PRD-004 (not just PRD-002) adjacent to `S.product_depth_enabled`. `getattr(S, "product_depth_max_category_depth", 10)` is the safe defensive read pattern in the service.

3. **CONFIRMED prerequisite**: `T.product_depth` and `S.product_depth_enabled` are **not yet present** in `app/core/tables.py` or `app/core/settings.py` (PRD-002 not yet shipped). PRD-005 must ship after PRD-002 and PRD-004.

4. **RESOLVED**: `GET /tree` returns a flat list (BFS, up to `max_results=500`). No cursor pagination — PRD-004 §4.1.7 is definitive. Clients reconstruct tree shape locally using `depth`/`parent_category_id` fields.

5. **Open question**: Should `GET /tree` and `GET /breadcrumb` require subscription-gated access (matching the `can_access_creator` check in `GET /categories/{id}/items` at `:404`)? Current design skips the subscription check. Confirm with product team.

6. **RESOLVED**: `CategoryChildCreateIn` carries `child_category_id: str` (required — identifies the existing flat category to attach). No `category_id` generation. Previous spec wrongly assumed this endpoint creates a new category.

7. **Open question**: `PATCH /move` only requires ownership of the category being moved, not ownership of `new_parent_category_id`. A user may move their own category under any other category. Confirm intended ACL model with product team.

8. **Open question**: `list_descendants` returns `TREE` rows which do NOT include `name`/`description` (those are on META rows in `T.catalog`). The router must either: (a) call `_get_category_meta` per node to populate `name` (O(N) reads), or (b) make `CategoryTreeNodeOut.name` optional and omit it from `/tree` results. Confirm with frontend team which is acceptable.
