# FAC-007 — Receiving (inbound goods → on-hand)

## 1. Summary & Goal

FAC-007 delivers `app/services/receiving.py`, the inbound-goods layer of the OFBiz Facility application. Its single core responsibility is: **receive a shipment of physical goods at a facility location, land every line item into on-hand inventory, and record an auditable receipt document**.

Concretely the ticket ships:

1. **`receive_shipment(...)`** — the primary entry point that writes a receipt header + per-line rows to `T.receipts`, then calls `inventory.adjust(sku, +qty, reason="receipt", location_id=...)` (`app/services/inventory.py:209`) once per line, using the create-on-adjust path (`app/services/inventory.py:225`) for SKUs that have never been stocked at that location.
2. **Deterministic-id idempotency** — `receipt_id = sha256(correlation_id)[:32]` (same pattern as `app/services/commerce_order_service.py:67`) so a re-submitted receipt is a no-op and on-hand is not double-incremented.
3. **Optional PO linkage** — when `po_id` is supplied the receipt records `received_qty` per line and computes a `receipt_status` of `complete` / `partial` / `over` relative to PO-ordered quantities. A standalone receipt (no `po_id`) is fully supported.
4. **Inventory-flag guard** — when `S.inventory_reservations_enabled` is `False`, `receive_shipment` still writes the receipt header and lines (durable record of what arrived) but **skips the `inventory.adjust` calls**, mirroring the guard in `app/services/returns_rma.py:424`.
5. **Audit trail** — every receipt emits `alerts.audit_event("receiving.received", ...)` via the best-effort `_audit()` wrapper.

Everything is **additive and flag-gated** behind `S.facility_fulfillment_enabled` (default `False`). The existing shop, cart, orders, billing, inventory, reservations, and returns paths are byte-for-byte unchanged when the flag is off.

### 3.4 Access patterns

| Query | Mechanism |
|---|---|
| Fetch a receipt (header + lines) | `T.receipts.query(KeyConditionExpression=Key("receipt_id").eq(rid))` — returns META + all LINE rows in a single call |
| Receipts at a facility (newest-first) | `GSI_FACILITY` query: `Key={"facility_id": fid}`, `ScanIndexForward=False` — META rows only (LINE rows don't carry `facility_id` GSI key) |
| Receipts for a PO (newest-first) | `GSI_PO` query: `Key={"po_id": po_id}`, `ScanIndexForward=False` — META rows only |
| Admin receipt queue by status | `GSI_STATUS` query: `Key={"receipt_status": status}`, `ScanIndexForward=False` |

**Projection note**: LINE rows carry `receipt_id` and `sk` (prefixed `LINE#`) but not `facility_id`, `po_id`, or `receipt_status`. GSI queries therefore only project META rows. This is the same single-table fan-out pattern used in `app/services/returns_rma.py:280–295` `list_returns_for_order` (function at line 280, META-only filter comment at line 293 ✓).


### 4.3 Primary entry point

```python
def receive_shipment(
    *,
    facility_id: str,
    location_id: str,
    lines: List[Dict[str, Any]],
    received_by: str,
    correlation_id: str,
    po_id: Optional[str] = None,
    po_lines: Optional[Dict[str, int]] = None,  # {sku: ordered_qty}
) -> Dict[str, Any]:
```

**Arguments**:

- `facility_id` — the FAC-004 facility ID. Validated to be non-empty; existence check is caller's responsibility (the router verifies it via `facilities.get_facility`).
- `location_id` — the bare location string passed directly to `inventory.adjust(..., location_id=location_id)`.
- `lines` — list of `{"sku": str, "quantity": int}` dicts. Each `sku` must be non-empty; `quantity` must be ≥ 1.
- `received_by` — `user_sub` of the actor (stamped on the receipt for audit).
- `correlation_id` — caller-supplied idempotency key (non-empty string, max 256 chars).
- `po_id` — optional; links the receipt to a purchase order. When supplied, PO reconciliation is computed.
- `po_lines` — optional dict of `{sku: ordered_qty}` sourced from the PO (the Purchasing module provides this; it is not fetched here). When `po_id` is set and `po_lines` is `None`, `ordered_qty` is left unset on each line and `receipt_status` defaults to `"standalone"` (the PO owner hasn't provided quantities yet).

**Returns**: `_receipt_out(header, lines)` — see §4.5.

**Raises**:

- `HTTPException(404)` — flag off.
- `HTTPException(422)` — `lines` empty, any `sku` empty, any `quantity < 1`, `correlation_id` empty, or duplicate SKU within `lines`.
- `HTTPException(409)` — a concurrent mutation conflict on the inventory row (surfaced from `inventory.adjust`; callers should retry).

## 5. Detailed Behavior & Edge Cases

### 5.1 `receive_shipment` — step-by-step

1. **Flag gate**: call `_require_enabled()`. Raises 404 when `S.facility_fulfillment_enabled` is `False`.
2. **Input validation**:
   - `correlation_id` must be non-empty.
   - `lines` must be non-empty (at least one line).
   - Each line: `sku` non-empty, `quantity >= 1`.
   - Duplicate SKUs within a single receipt are rejected (422 "Duplicate SKU in receipt lines") — same pattern as `app/services/returns_rma.py:209–210` which rejects duplicate `item_id` with `HTTPException(422)`.
3. **Derive receipt_id**: `receipt_id = _receipt_id_for(correlation_id)`.
4. **Derive per-line status** (when `po_id` is set and `po_lines` is provided):
   - `quantity == ordered_qty` → `"complete"`
   - `quantity < ordered_qty` → `"partial"`
   - `quantity > ordered_qty` → `"over"`
   - `po_lines` is `None` or SKU not in `po_lines` → `"standalone"` (no PO quantity known)
5. **Derive header `receipt_status`**:
   - `po_id` is `None` → `"standalone"`
   - All lines `"complete"` → `"complete"`
   - Any line `"over"` → `"over"`
   - Otherwise → `"partial"`
6. **Write header row** via conditional `put_item(Item=header, ConditionExpression="attribute_not_exists(receipt_id)")`:
   - On success: proceed to step 7.
   - On `ConditionalCheckFailedException`: this `correlation_id` was already received. Load and return the existing receipt without touching inventory (idempotent replay path).
7. **Write line rows** (one `put_item` per line, `sk = f"LINE#{idx}"`). Line rows are not conditional — a partial write followed by a crash would produce incomplete line rows. To recover, the idempotency guard at step 6 fires on the second attempt, preventing double inventory adjustments. Implementors MAY add a `line_rows_written` attribute to the header and only write lines when it is absent (more robust), but the base FAC-007 spec does not require it.
8. **Adjust on-hand** (guarded by `S.inventory_reservations_enabled`):
   ```python
   if bool(getattr(S, "inventory_reservations_enabled", False)):
       try:
           from app.services import inventory as inv
           for ln in resolved_lines:
               inv.adjust(ln["sku"], ln["quantity"], reason="receipt",
                          location_id=location_id, user_sub=received_by)
       except Exception:
           pass  # inventory error must not roll back the receipt header
   ```
   The `try/except` wraps the entire loop — a single failing `adjust` (e.g. a concurrent `ConditionalCheckFailedException` that exhausted retries) is swallowed. The receipt header is already persisted at this point; the discrepancy is visible in the audit log.
9. **Emit audit event**:
   ```python
   _audit("receiving.received", received_by,
          receipt_id=receipt_id, facility_id=facility_id,
          location_id=location_id, line_count=len(resolved_lines),
          po_id=po_id, receipt_status=header["receipt_status"])
   ```
10. **Return** `_receipt_out(header, line_rows)`.

### 5.2 Idempotency invariants

- **Same `correlation_id`, same lines**: second call returns the existing receipt, on-hand unchanged. This is the primary idempotency path.
- **Same `correlation_id`, different lines**: the conditional `put_item` fires with the existing `receipt_id`; the second call returns the original receipt unchanged and the new lines are **not** written. Callers must use a distinct `correlation_id` for a distinct physical delivery.
- **Different `correlation_id`, same SKU**: two separate receipts are created; `inventory.adjust` is called twice, correctly double-incrementing on-hand.

### 5.3 PO reconciliation (no PO entity ownership)

FAC-007 **does not own or store PO entities**. The Purchasing module (`PUR`) owns POs. The contract this ticket defines for the `PUR` module to consume:

- After `receive_shipment` the `GSI_PO` index allows `list_receipts_for_po(po_id)` to enumerate all receipts against a PO.
- Each META row carries `receipt_status` and each LINE row carries `line_status` and `quantity`, so the PUR module can compute total received qty per SKU as `sum(ln["quantity"] for ln in all_receipts_for_po if ln["sku"] == target_sku)`.
- FAC-007 does not update any PO record; the PUR module queries the `receipts` table for its own state.

### 5.4 Inventory-disabled skip

When `S.inventory_reservations_enabled` is `False`:

- The receipt header and line rows are written normally (the inbound goods record is complete).
- No `inventory.adjust` call is made.
- `receipt_status` is still computed from PO quantities (when supplied).
- The `ReceiptOut` returned is identical in shape to the inventory-enabled path.
- This mirrors the pattern at `app/services/returns_rma.py:424` exactly.

### 5.5 Over-receipt

Over-receipt (`quantity > ordered_qty` on a PO line) is **allowed** by FAC-007 — the line is recorded with `line_status = "over"` and the full received quantity is adjusted into on-hand. The business decision to reject or quarantine over-received goods belongs to the Purchasing/Warehouse operator, surfaced via the `receipt_status = "over"` signal. FAC-007 does not raise an error for over-receipt.

### 5.6 Empty-location receiving

A location may receive its very first unit of a SKU at any time. `inventory.adjust` at `app/services/inventory.py:225–251` handles this via the create-on-adjust branch: `put_item` with `ConditionExpression="attribute_not_exists(sku)"`. If a concurrent receive of the same SKU wins the race, the function recurses once to the update path. FAC-007 does not need special handling for this case — it delegates entirely to `inventory.adjust`.

### 5.7 Partial write crash recovery

If the process crashes after writing the header but before all LINE rows are written, the receipt is in an inconsistent state (header exists, fewer lines than `line_count`). A re-submission with the **same `correlation_id`** hits the idempotency guard and returns the partially-written receipt as-is (the `ConditionalCheckFailedException` fires on the header). The missing lines will not be re-written. Operators can detect this by comparing `line_count` against the actual number of `LINE#n` rows in the receipt. A future hardening ticket may add per-line idempotency, but it is out of FAC-007 scope.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

`app/services/receiving.py` contains **no** `if S.dev_mode` branch. The same DynamoDB `put_item` / `update_item` / `query` calls run identically against moto local DDB (dev) and real DynamoDB (prod). The `inventory.adjust` call itself is also branchless (`app/services/inventory.py:209`).

### Idempotency

Two layers:

1. **Receipt-level**: `ConditionExpression="attribute_not_exists(receipt_id)"` on the header write. A replayed `correlation_id` is caught here; on-hand is never incremented a second time.
2. **Inventory-level**: Each `inventory.adjust` within the loop is itself concurrency-safe via the optimistic conditional at `app/services/inventory.py:261–286` (✓ verified: comment at 261–263, `update_item` try block at 264–286), but it is NOT individually idempotent (it does increment on every successful call). The receipt-level guard is therefore the definitive idempotency boundary.

### Security

- **Authorization**: mutations (`POST /ui/receiving/receipts`) require `require_admin_or_root_csrf` (`app/auth/policy.py:100` ✓; same as `inventory.set_on_hand` at `app/routers/inventory.py:46–48` ✓). An unprivileged user cannot land inventory into on-hand.
- **Ownership of facility**: the router validates that the `facility_id` in `ReceiveIn` belongs to a facility that exists and is active before calling `receive_shipment`. The service itself trusts the caller (same pattern as `returns_rma.request_return` trusting the order lookup result).
- **Audit trail**: every successful receipt emits `alerts.audit_event("receiving.received", ...)`. Audit events are best-effort (wrapped in `try/except`) but failures are logged by the alerts module. On-hand changes also emit `inventory.adjust` audit events from `app/services/inventory.py:289–298` (✓ verified).
- **Correlation ID as user input**: the `correlation_id` is stored verbatim as an opaque string (max 256 chars). It is hashed before use as `receipt_id`; no SQL injection or partition-key collision risk. The hash is 32-hex-char, same as `commerce_order_service`.

## 10. Open Questions / Assumptions

1. **Assumption**: FAC-002 has been implemented before FAC-007. `T.receipts`, `S.receipts_table_name`, and `S.facility_fulfillment_enabled` are assumed to exist in `app/core/tables.py` and `app/core/settings.py` when FAC-007 is implemented.

2. **Assumption**: FAC-003 has been implemented before FAC-007. `ReceiveIn`, `ReceiveLineIn`, and `ReceiptOut` Pydantic models are assumed to be in `app/models.py`.

3. **Open question — per-line location override**: The data model includes `location_id` on each line row (denormalised from the header). FAC-007 spec requires all lines to share the header `location_id`. A future FAC-014 extension may allow per-line location (e.g., bulk goods received to `"receiving-dock"` then transferred to bin locations). This is noted in the schema but not implemented here.

4. **Assumption — PO validation**: FAC-007 does not validate that `po_id` resolves to an existing PO record. The Purchasing module (`PUR`) owns PO entities; FAC-007 simply stores the `po_id` string and computes reconciliation from `po_lines` if supplied. If `po_id` is set but `po_lines` is `None`, all lines get `line_status = "standalone"`. The PUR module is responsible for providing `po_lines` at call time.

5. **Open question — `adjust` failure handling**: The current spec wraps the entire `adjust` loop in `try/except` (mirroring the RMA restock guard). If one line's `adjust` fails (e.g., concurrent conflict exhausts retries), the failure is swallowed and the receipt header is persisted with the stated quantities. On-hand will be inconsistent with the receipt. A hardened design would write a `line_adjust_status` attribute per line row. This is flagged as a potential follow-up hardening ticket.

6. **Assumption — receipt header is immutable after creation**: There is no `update_receipt` function in this spec. A receipt may not be amended. Corrections are made by receiving a new shipment (new `correlation_id`). This mirrors how `commerce_order_service` treats order records.

7. **Open question — over-receipt policy**: The spec allows over-receipt (records and increments on-hand). Some warehouse operations want to quarantine over-received goods. This could be a flag (`S.receiving_allow_over_receipt`, default `True`) in a future follow-up. For FAC-007, over-receipt is always allowed.

8. **Assumption — `facility_id` existence validation**: The router (FAC-011) is responsible for calling `facilities.get_facility(facility_id)` before invoking `receive_shipment`. The service function itself does not validate facility existence (same pattern: `returns_rma.receive_return` does not re-validate order existence from within the service layer once the header has been read by the caller).
