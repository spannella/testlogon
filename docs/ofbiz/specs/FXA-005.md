# FXA-005 — Fixed-asset register service (CRUD)

## 1. Summary & Goal

FXA-005 creates `app/services/fixed_assets.py` — the service layer for the fixed-asset register. It implements five public functions (`create_asset`, `get_asset`, `list_assets`, `update_asset`, `dispose_asset`) that perform all DynamoDB I/O against `T.fixed_assets`, plus the internal `_audit` helper used by every mutating call. A sixth helper, `_asset_pk`, standardizes PK formatting throughout the service and for downstream callers (FXA-006 depreciation schedule, FXA-007 router).

The design contract this ticket must honor:

- **Additive + flag-gated.** `FIXED_ASSETS_ENABLED` (wired by FXA-002) gates every live call. With the flag off the module is importable but dormant; existing shop, cart, orders, billing, and inventory paths are byte-for-byte unchanged.
- **Deterministic-id idempotency.** Re-issuing `create_asset` with the same `correlation_id` returns the existing asset without writing a duplicate row. The `asset_id` is derived as `hashlib.sha256(correlation_id.encode()).hexdigest()[:32]`, matching the pattern established by `app/services/commerce_order_service.py:67` (`order_id = hashlib.sha256(corr.encode()).hexdigest()[:32]`).
- **Audit on every mutation.** Create, update, and dispose each emit one `app/services/alerts.audit_event` call (best-effort, via the `_audit` wrapper). Update emits a before/after snapshot.
- **No parallel billing mechanism.** Disposal proceeds — when present — flow through the existing `refund_payment` / `settle_or_reverse_ledger` path (`app/routers/billing.py:1287` and `app/services/billing_shared.py:262`). The fixed-assets service never mints its own payment path.
- **SECOPS-007 parity.** Identical code in dev (moto + DynamoDB Local) and prod (real DynamoDB); no `if S.dev_mode` branch in any business logic function.

### 3.2 `fixed_asset_schedule` and `maintenance_orders` (read-only context for FXA-005)

FXA-005 does not write to these tables. No foreign-key enforcement at the DDB level — DynamoDB has none; the service enforces it procedurally.

## 5. Detailed Behavior & Edge Cases

### 5.1 `create_asset` — deterministic-id idempotency

```
1. _require_enabled()
2. Derive correlation key:
       corr = req.correlation_id or f"asset:{owner_sub}:{uuid.uuid4().hex}"
   asset_id = hashlib.sha256(corr.encode("utf-8")).hexdigest()[:32]
3. Build the DDB item dict:
       pk = _asset_pk(asset_id)
       sk = "META"
       ts = now_ts()
       item = {pk, sk, asset_id, owner_sub, name, asset_class,
               acquisition_cost_cents, salvage_value_cents, useful_life_months,
               acquired_at=req.acquired_at, depreciation_method="straight_line",
               status="active", accumulated_depreciation_cents=0,
               gl_*_account_id (when present), correlation_id=corr,
               created_at=ts, updated_at=ts}
4. Conditional put:
       try:
           ddb_put(T.fixed_assets, item,
                   condition_expression="attribute_not_exists(pk)")
       except ClientError as exc:
           if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
               # Idempotent: return existing row without writing
               existing = T.fixed_assets.get_item(
                   Key={"pk": pk, "sk": "META"}
               ).get("Item") or {}
               _audit("fixed_asset.create.idempotent", owner_sub,
                      asset_id=asset_id, correlation_id=corr)
               return _item_to_out(existing)
           raise
5. _audit("fixed_asset.created", owner_sub, asset_id=asset_id,
           name=req.name, asset_class=req.asset_class,
           acquisition_cost_cents=req.acquisition_cost_cents,
           correlation_id=corr, outcome="success")
6. return _item_to_out(item)
```

**Why conditional-put instead of get-then-put:** a conditional put is atomic and requires only one DDB round-trip in the common (non-duplicate) path, matching the pattern at `app/services/refund_requests.py:160`. <!-- VERIFIED: refund_requests.py:159–164 --> Two concurrent creates with the same `correlation_id` resolve deterministically: exactly one wins, the other catches `ConditionalCheckFailedException` and fetches + returns the winner's row.

**When `correlation_id` is omitted:** a random UUID is embedded in `corr` so each call without a client correlation ID creates a fresh asset. The caller cannot create an idempotent duplicate without supplying the same correlation_id.

### 5.2 `get_asset` — ownership check

```
1. item = T.fixed_assets.get_item(Key={"pk": _asset_pk(asset_id), "sk": "META"}).get("Item")
2. if not item: return None  (router returns 404)
3. if item["owner_sub"] != owner_sub: raise HTTPException(404, ...)
   (ownership failure → 404, not 403, to avoid leaking existence)
4. return _item_to_out(item)
```

The service returns `None` for missing assets; the router maps this to HTTP 404. Ownership mismatch also returns `None`-equivalent (raises 404) to prevent oracle attacks.

### 5.3 `list_assets` — GSI pagination

Two query modes, selected by the `status` parameter:

**Without status filter (list all for owner):** query `GSI_OWNER` with `owner_sub` as the partition key, `acquired_at` descending.

**With status filter:** query `GSI_STATUS` with `status` as partition key and `ScanIndexForward=False` to get most-recently-acquired first, then apply a `FilterExpression` for `owner_sub`. Because `GSI_STATUS` does not include `owner_sub` in the key schema, filtering is post-DDB; the DDB `Limit` applies *before* the filter, so the service must loop over `LastEvaluatedKey` until it has gathered `limit` items or exhausted the index.

```python
def list_assets(owner_sub, *, status=None, limit=25, cursor=None):
    _require_enabled()
    if status and status not in ("active", "fully_depreciated", "disposed"):
        raise HTTPException(400, "invalid status filter")

    if status:
        index_name = "GSI_STATUS"
        key_cond = Key("status").eq(status)
        filter_expr = "owner_sub = :os"
        expr_attr_vals = {":os": owner_sub}
    else:
        index_name = "GSI_OWNER"
        key_cond = Key("owner_sub").eq(owner_sub)
        filter_expr = None
        expr_attr_vals = {}

    kwargs = {
        "IndexName": index_name,
        "KeyConditionExpression": key_cond,
        "ScanIndexForward": False,
        "Limit": limit,
    }
    if filter_expr:
        kwargs["FilterExpression"] = filter_expr
        kwargs["ExpressionAttributeValues"] = expr_attr_vals
    if cursor:
        kwargs["ExclusiveStartKey"] = decode_cursor(cursor)

    resp = T.fixed_assets.query(**kwargs)
    items = [_item_to_out(i) for i in resp.get("Items", [])]

    result = {"items": items, "count": len(items)}
    if resp.get("LastEvaluatedKey"):
        result["cursor"] = encode_cursor(resp["LastEvaluatedKey"])
    return result
```

**FilterExpression and page size gotcha** (from CLAUDE.md): `GSI_STATUS` queries with `FilterExpression` for `owner_sub` can return fewer than `limit` items even when more exist on subsequent pages. For the admin-owned asset register this is unlikely to be a problem in practice (an admin registers assets, not millions of users), but the caller must respect the `cursor` field and issue successive requests if they need a complete list. The service does not loop internally; that complexity is deferred to FXA-007 if needed.

### 5.4 `list_assets` — `GSI_OWNER` vs `GSI_STATUS` choice

When `status` is not supplied, `GSI_OWNER` is the canonical listing index: it returns exactly this owner's assets with `acquired_at` as the sort key. The `status` filter variant uses `GSI_STATUS` because no composite `(owner_sub, status)` GSI exists — adding one is deferred to FXA-003 follow-up if query performance demands it. For a typical asset register (dozens to hundreds of assets per deployment), the post-filter approach is adequate.

### 5.5 `update_asset` — partial update, immutable fields enforced

```
1. item = fetch (same ownership check as get_asset, raises 404 on miss/wrong owner)
2. if item["status"] == "disposed": raise HTTPException(409, "cannot_update_disposed_asset")
3. before_snapshot = {name, asset_class, gl_*_account_id}
4. build UpdateExpression from non-None fields on patch:
       SET #name = :name, asset_class = :ac, updated_at = :ts, ...
   Only fields present on FixedAssetPatchIn are writable:
       name, asset_class, gl_asset_account_id, gl_accum_depr_account_id,
       gl_depr_expense_account_id, gl_gain_loss_account_id
5. T.fixed_assets.update_item(
       Key={"pk": pk, "sk": "META"},
       UpdateExpression=...,
       ExpressionAttributeValues=...,
       ConditionExpression="attribute_exists(pk)",
   )
6. re-fetch updated item
7. after_snapshot = {same fields}
8. _audit("fixed_asset.updated", owner_sub, asset_id=asset_id,
           before=before_snapshot, after=after_snapshot, outcome="success")
9. return _item_to_out(updated_item)
```

`acquisition_cost_cents`, `salvage_value_cents`, `useful_life_months`, `acquired_at`, and `depreciation_method` are **not** in the `UpdateExpression` even if somehow supplied by the caller — they are not fields on `FixedAssetPatchIn` (FXA-004 section 4.2), so FastAPI will reject them before service code runs.

### 5.6 `dispose_asset` — status transition + audit

```
1. item = fetch with ownership check
2. if item["status"] == "disposed": raise HTTPException(409, "already_disposed")
3. ts = now_ts()
4. T.fixed_assets.update_item(
       Key={"pk": pk, "sk": "META"},
       UpdateExpression="SET #status = :s, disposed_at = :ts, updated_at = :ts"
                        + (" , disposal_reason = :dr" if req.disposal_reason else ""),
       ExpressionAttributeNames={"#status": "status"},
       ExpressionAttributeValues={":s": "disposed", ":ts": ts, ...},
       ConditionExpression="#status <> :disposed_val",
       ExpressionAttributeValues includes ":disposed_val": "disposed",
   )
5. re-fetch updated item
6. _audit("fixed_asset.disposed", owner_sub, asset_id=asset_id,
           status_before=item["status"],
           disposal_reason=req.disposal_reason,
           proceeds_amount_cents=req.proceeds_amount_cents,
           outcome="success")
7. return _item_to_out(updated_item)
```

**Proceeds money-out is NOT handled by this service.** If `req.proceeds_payment_intent_id` is set, the *router* (FXA-007) calls `refund_payment` / `settle_or_reverse_ledger` (from `app/routers/billing.py:1287` and `app/services/billing_shared.py:262`) *after* `dispose_asset` returns successfully. <!-- VERIFIED: billing.py:1287, billing_shared.py:262 --> The service is responsible only for the status transition and audit. This keeps the service free of billing imports and honors the "no parallel money mechanism" constraint.

**`ConditionExpression` on the disposal update** prevents double-disposal under concurrent requests: the second concurrent dispose raises `ConditionalCheckFailedException`, which the service maps to HTTP 409 "already_disposed".

### 5.7 Status transition table

| From status | `update_asset` allowed? | `dispose_asset` allowed? |
|---|---|---|
| `active` | yes | yes |
| `fully_depreciated` | yes | yes |
| `disposed` | no (409) | no (409) |

The `fully_depreciated` status is set by the depreciation poster (FXA-009), not by this service. The service does not validate transition from `active` to `fully_depreciated` — that transition is an internal FXA-009 concern.

### 5.8 `_item_to_out` and `net_book_value_cents`

`_item_to_out` constructs `FixedAssetOut(..., net_book_value_cents=0, ...)`. The `model_validator(mode="after")` on `FixedAssetOut` (FXA-004 section 4.3) overwrites `net_book_value_cents` with `max(salvage_value_cents, acquisition_cost_cents - accumulated_depreciation_cents)`. The service never writes `net_book_value_cents` to DynamoDB — it is always derived at serialization time.

### 5.9 Edge cases summary

| Scenario | Behavior |
|---|---|
| `create_asset` with duplicate `correlation_id` (same owner) | Returns existing asset, no write, audit event `fixed_asset.create.idempotent` |
| `create_asset` with duplicate `correlation_id` (different `owner_sub`) | Same asset_id derived; conditional put fails; returns existing asset regardless of `owner_sub` on the existing row — the router's ownership check will then return 404 to the second caller |
| `get_asset` with unknown `asset_id` | Returns `None` → router 404 |
| `get_asset` with wrong `owner_sub` | Raises HTTPException 404 (ownership leak prevention) |
| `update_asset` on disposed asset | 409 `cannot_update_disposed_asset` |

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

No `if S.dev_mode` branch exists anywhere in `app/services/fixed_assets.py`. DynamoDB Local (port 8001) and real DynamoDB both accept `attribute_not_exists(pk)` conditional expressions identically. moto's in-process DDB mock used in tests also supports this expression. The `encode_cursor` / `decode_cursor` functions in `app/core/cursor.py` handle DDB `Decimal` from both environments via `_json_default` (`app/core/cursor.py:12–19`). <!-- VERIFIED: cursor.py:12–19 -->

### 7.2 Idempotency contract

`create_asset` is idempotent per `correlation_id`: the same input yields the same `asset_id` and returns the same `FixedAssetOut` on re-issue. The conditional put plus get-on-conflict pattern guarantees at-most-one write for any given `asset_id`.

`update_asset` and `dispose_asset` are idempotent in the sense that repeating a disposal or update with the same payload produces the same final state. The `ConditionExpression` on `dispose_asset` means a concurrent second call raises 409 rather than silently double-applying.

### 7.3 Security

- **Ownership enforcement.** Every mutating operation fetches the existing item and verifies `item["owner_sub"] == owner_sub` before proceeding. Mismatches return HTTP 404 (not 403) to avoid confirming asset existence to unauthorized callers.
- **Admin-only access.** The router (FXA-007) enforces `Role.ADMIN | Role.ROOT`. Non-admin users receive 403 before any service function is called. No ordinary user can register, view, or dispose assets.
- **No PII beyond `owner_sub`.** Asset fields are financial record data (cost, GL accounts, dates). None contain personal identifiers beyond the opaque Cognito sub.
- **Correlation ID stored, not secret.** `correlation_id` is stored in DynamoDB and returned in `FixedAssetOut.correlation_id`. It is a client-supplied idempotency key, not a secret token. The SHA-256 derivation of `asset_id` is one-way from the caller's perspective, but the `correlation_id` itself is retained on the item for audit purposes.
- **Input length caps** on string fields (`name: max_length=200`, `asset_class: max_length=50`) are enforced by `FixedAssetIn` (FXA-004), preventing oversized DDB attribute writes.

## 10. Open Questions / Assumptions

1. **Cross-owner `correlation_id` collision.** If two different `owner_sub` values both submit `correlation_id="invoice-2025-01"`, they derive the same `asset_id` and the second create hits `ConditionalCheckFailedException`. The service returns the first owner's asset to the second owner; the router's ownership check then returns 404 to the second caller. This is arguably correct but surprising. A safer `corr` derivation is `f"{owner_sub}:{correlation_id}"` — this namespaces the idempotency key per owner, preventing cross-owner collisions. The spec assumes the `owner_sub`-prefixed form. This assumption must be verified against the FXA-001 design note before implementation.

2. **`list_assets` with `status` filter — loop vs. single page.** The spec's `list_assets` implementation issues a single DDB page (honoring `Limit`) and lets the caller iterate. For a sparse `GSI_STATUS` (e.g., only a few disposed assets), the DDB-level `Limit` applies before `FilterExpression`, so the page may contain fewer than `limit` items despite more existing. The assumption is that this is acceptable for an admin-only register with a small dataset. If the team requires that each response page always contains exactly `limit` owner-matching items, a looping implementation is needed — defer to FXA-007 review.

3. **`dispose_asset` proceeds responsibility.** The spec assigns disposal-proceeds GL posting to FXA-007 (the router layer calls `settle_or_reverse_ledger` after `dispose_asset` returns). An alternative is to have `dispose_asset` accept a `billing_table` collaborator and post the ledger entry itself, keeping all disposal logic in one place. The spec assumes the router-layer pattern to keep the service free of billing imports. This assumption should be confirmed against the FXA-001 design note (which explicitly references `app/routers/billing.py:1287`).

4. **`accumulated_depreciation_cents` update path.** FXA-005 initializes `accumulated_depreciation_cents=0` on create. FXA-009 (depreciation posting) increments this field via `update_item`. This ticket does not need an `increment_depreciation(asset_id, amount)` helper — that belongs to FXA-009. The assumption is that FXA-009 will import and call `get_asset` for read and `T.fixed_assets.update_item` directly for write. If the team prefers FXA-005 to own all `fixed_assets` table I/O (service-layer encapsulation), add a `record_depreciation_posted(asset_id, amount_cents)` function to FXA-005 and update this assumption.

5. **`list_assets` sort direction.** The spec uses `ScanIndexForward=False` (newest-acquired-first) as the default sort order. If the team prefers oldest-first or a caller-supplied `sort` parameter, that is a one-line change. The assumption follows the `license_agreements` pattern (`ScanIndexForward: False` at `app/services/license_agreements.py:265`). <!-- VERIFIED: license_agreements.py:265 -->

6. **Disposal sets `status="disposed"` directly without passing through `fully_depreciated`.** An asset may be disposed from `active` (written off early) or from `fully_depreciated`. No intermediate status is required. The spec treats disposal as a terminal transition from any non-disposed status. This matches the FXA-004 status enum (`active` | `fully_depreciated` | `disposed`).

7. **GL account IDs optional on create.** `FixedAssetIn` declares all four `gl_*_account_id` fields as `Optional[str] = None`. If OFB-013 is not yet deployed (the GL chart of accounts does not exist), assets can be registered without GL account linkage; the depreciation poster (FXA-009) must then handle missing GL account IDs gracefully. The spec assumes this is acceptable and defers GL account defaulting to FXA-008 (if scoped).
