# POS-008 — Void & in-person refund reusing refund_payment

**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days

---

## 1. Summary & Goal

POS-008 adds two money-reversing operations to `app/services/pos_tender.py` (created
by POS-006, extended by POS-007):

1. **`void_transaction(txn_id, cashier_sub)`** — cancels a transaction that has not
   yet been settled (status `"draft"` or `"open"`). No money has moved so no ledger
   entry is reversed; the bound cart and any inventory reservations are released.
   Voiding a settled transaction (`status="tendered"`) is a 409 — the caller must
   use `refund_transaction` instead.

2. **`refund_transaction(txn_id, cashier_sub, line_refs, reason)`** — issues a
   post-settlement refund against a `"tendered"` transaction. Refund money-out
   reuses the platform's single refund mechanism exactly as `returns_rma.refund_return`
   does (`app/services/returns_rma.py:444`): one `type="adjustment", reason="refund"`
   ledger entry per tender leg, written via `billing_shared.new_ledger_entry` with the
   original `provider` attribution; the original ledger row reversed via
   `billing_shared.settle_or_reverse_ledger`; balance delta applied via
   `billing_shared.apply_balance_delta`. Card tenders are additionally reversed at
   the Stripe layer (same as `app/routers/billing.py:1287` `refund_payment`). Cash
   refunds record a negative cash tender and reduce the session's `expected_cash_cents`.
   Wallet refunds credit back via `apply_wallet_delta`.

3. **Inventory restock** — when `S.inventory_reservations_enabled` is `True`, each
   returned line item calls `inventory.adjust(sku, +qty, reason="pos_refund_restock")`
   mirroring the `rma_restock` path at `app/services/returns_rma.py:423–435`
   (`inv.adjust` call at `:432`). This call is wrapped in `try/except` and never
   blocks the refund.

The entire feature is behind the existing default-off `S.pos_enabled` flag. No bytes
in the existing shop/cart/orders/billing/inventory stacks change when the flag is off.

### 2.2 `refund_payment` — the canonical card refund path
(`app/routers/billing.py:1287`)

`refund_payment` is the only card-refund mechanism in the platform:

1. Loads the payment record from `T.billing` via `ddb_get(T.billing, pk, pay_sk(pi_id))` (`:1292`).
2. Calls `stripe.Refund.create(payment_intent=pi_id, amount=amount, reason=reason)` (`:1300`).
3. Writes a refund ledger entry via `new_ledger_entry(entry_type="adjustment", reason="refund", extra={"stripe_payment_intent_id": ..., "stripe_refund_id": ..., "provider": "stripe"})` (`:1306`).
4. Calls `apply_balance_delta(T.billing, pk, {"payments_settled_cents": -amount})` (`:1321`) — conditional on payment status; pending payments use `payments_pending_cents` at `:1319`.
5. Calls `settle_or_reverse_ledger(T.billing, "pk", pk, pay["ledger_sk"], "reversed")` (`:1324`).
6. Calls `update_payment_status(user_id, pi_id, "refunded")` (`:1326`).
7. Optionally calls `mark_reverted(user_id, purchase_txn_id, reason)` (`:1330`).

POS-008 does **not** call `refund_payment` as an HTTP handler (it has
`ctx=Depends(require_ui_session)` and `actor=Depends(get_authenticated_user)`
kwargs assuming HTTP context). Instead it calls the same underlying primitives
directly in service code, following the same sequence. This mirrors how
`returns_rma.refund_return` (`:444`) calls `new_ledger_entry`, `apply_balance_delta`,
and `settle_or_reverse_ledger` directly rather than routing through the billing router.

### 2.7 Session float counter mutation (cash void and cash refund)

POS-004 (`app/services/pos_register.py`) computes `expected_cash_cents` at
`close_session`:

```
expected_cash_cents = opening_float_cents + cash_in_cents − change_out_cents
```

POS-006 atomically increments `cash_in_cents` and `change_out_cents` on the
`SESSION#{session_id}/META` row after a cash tender. POS-008 must perform the
inverse:
- **Cash void (pre-settlement)**: No cash was accepted; `cash_in_cents` and
  `change_out_cents` have NOT been incremented (the tender never settled). No
  session float update needed.
- **Cash refund (post-settlement)**: Cash was accepted. The refund pays out cash.
  Atomically decrement `cash_in_cents` by `refund_amount_cents` (reducing the
  till's expected in-flow) using `ADD cash_in_cents :-refund_amt` on the session
  row.

### 2.8 `purchase_cart` idempotency (cart release on void)

`purchase_cart` at `app/services/shoppingcart.py:474` detects an already-purchased
cart and returns early (`483–491`: status `"PURCHASED"` early-return). POS-008 void
must NOT call `purchase_cart`; instead it must expire the bound cart (set cart
`status="EXPIRED"` via a direct `update_item` on the shopping_cart table, matching
the `"EXPIRED"` status written by `expire_abandoned_carts` at
`shoppingcart.py:945`). The `"ABANDONED"` string is **not** a valid cart status in
the codebase — valid terminal statuses are `"PURCHASED"` and `"EXPIRED"`. Setting
`status="EXPIRED"` releases the cart's catalog items without creating an order or
decrementing stock.

## 3. Data Model

### 3.1 No new tables

POS-008 writes only to the existing `T.pos` and `T.billing` tables. No new
`TableDef` entries are required in `scripts/local-ddb-init.py`.

### 3.2 TXN row — additional status values

The `TXN#{txn_id}/META` row from POS-005/006/007 gains two new `status` values:

| Status | Written by | Meaning |
|---|---|---|
| `"draft"` | POS-005 | Cart bound, no tenders yet |
| `"open"` | POS-007 | One or more partial tenders; not fully settled |
| `"tendered"` | POS-006/007 | Fully settled; order created |
| `"voided"` | **POS-008** | Pre-settlement cancel; cart abandoned |
| `"refunded"` | **POS-008** | Post-settlement full refund issued |
| `"partial_refund"` | **POS-008** | Post-settlement partial refund; some lines refunded |

Transition rules (enforced by POS-008):
- `"draft"` → `"voided"`: allowed (no money moved; cart abandoned).
- `"open"` → `"voided"`: allowed (partial tender legs must each be reversed before
  void can succeed; see §5.4).
- `"tendered"` → `"refunded"` or `"partial_refund"`: allowed.
- `"voided"` → any: 409 (terminal state).
- `"refunded"` → any: 409 (terminal state).
- `"tendered"` → `"voided"`: **409** — caller must use `refund_transaction` instead.

### 3.3 New attributes on TXN row

| Attribute | DDB type | Written by | Description |
|---|---|---|---|
| `voided_at` | N | `void_transaction` | `now_ts()` at void time |
| `void_reason` | S | `void_transaction` | Caller-supplied reason string |
| `refund_ledger_sks` | L | `refund_transaction` | List of billing SK strings for each refund ledger entry |
| `refunded_line_refs` | L | `refund_transaction` | List of `{sku, qty}` maps for auditing |
| `refund_amount_cents` | N | `refund_transaction` | Total refund issued |
| `refunded_at` | N | `refund_transaction` | `now_ts()` at first refund |

All new attributes use DynamoDB's sparse model — rows written by earlier tickets
without these fields are treated as absent (not an error).

### 3.4 REFUND tender row (new row kind written by POS-008)

Cash refunds write a new tender row to record the outflow for the Z-report:

```
pos_pk = "SESSION#{session_id}"
pos_sk = "REFUND#{txn_id}#{seq:04d}"
```

| Attribute | Type | Description |
|---|---|---|
| `pos_pk` | S | `"SESSION#{session_id}"` |
| `pos_sk` | S | `"REFUND#{txn_id}#{seq:04d}"` |
| `txn_id` | S | Original settled txn |
| `session_id` | S | Register session |
| `cashier_sub` | S | Cashier who processed the refund |
| `kind` | S | `"cash_refund"` / `"card_refund"` / `"wallet_refund"` |
| `amount_cents` | N | Refund amount (positive integer) |
| `reason` | S | Caller-supplied reason string |
| `ledger_sk` | S | Billing refund ledger SK back-ref |
| `created_at` | N | `now_ts()` — numeric, appears in `GSI_SESSION_TXN` |
| `idempotency_key` | S | Deterministic id used for the conditional put |

`REFUND#` rows appear in `GSI_SESSION_TXN` (partition_key `session_id`, sort_key
`created_at` numeric) because they carry both top-level attributes. POS-010 (X/Z
report) queries this GSI to aggregate by-tender totals including refunds. No new
GSI is required; `attr_types={"created_at": "N"}` was already declared by POS-003.

## 4. API / Service Design

### 4.1 `void_transaction`

```python
def void_transaction(
    txn_id: str,
    cashier_sub: str,
    *,
    reason: str = "void",
) -> Dict[str, Any]:
```

**Steps:**

1. `_require_pos_enabled()` — `HTTPException(404)` if `S.pos_enabled` is False.
2. Load TXN row: `T.pos.get_item(Key={"pos_pk": f"TXN#{txn_id}", "pos_sk": "META"})`.
   Raises `HTTPException(404, "Transaction not found")` if absent.
3. Ownership check: `txn["cashier_sub"] == cashier_sub`; raises
   `HTTPException(403, "Not your transaction")` if mismatched.
4. Status guard:
   - `status in ("voided", "refunded", "partial_refund")` → `HTTPException(409, "Transaction is already in terminal state")`
   - `status == "tendered"` → `HTTPException(409, "Transaction is settled; use refund_transaction instead")`
   - `status in ("draft", "open")` → proceed.
5. **Pre-settlement tender reversal** (status `"open"` only): For each tender row
   under `SESSION#{session_id}/TENDER#{txn_id}#*` (queried via
   `begins_with("TENDER#{txn_id}#")`):
   - If `kind == "card"`: call `stripe.Refund.create(payment_intent=tender["pi_id"], amount=tender["amount_cents"])` and write a reversal ledger entry via `new_ledger_entry(entry_type="adjustment", reason="refund", state="settled", extra={"provider": "stripe", "pos_txn_id": txn_id})` + `ddb_put(T.billing, ...)` + `settle_or_reverse_ledger(T.billing, "pk", pk, tender["ledger_sk"], "reversed")`.
   - If `kind == "wallet"`: call `apply_wallet_delta(T.billing, pk, +tender["amount_cents"])` and write a reversal ledger entry with `extra={"provider": "wallet"}` + reverse original ledger row.
   - If `kind == "cash"`: no ledger was written before full settlement (POS-006 only writes the ledger entry after `purchase_cart` succeeds). If `cash_in_cents` was already incremented (edge: cash tender committed before cart purchase), reverse it via `ADD cash_in_cents :-amount` on the session row.
6. **Expire the bound cart**: Call
   `T.shopping_cart.update_item(Key={"PK": f"USER#{cashier_sub}", "SK": f"CART#{cart_id}"}, UpdateExpression="SET #s = :s", ExpressionAttributeNames={"#s": "status"}, ExpressionAttributeValues={":s": "EXPIRED"})` so the cart is not re-used or billed.
   (`shoppingcart.py:945` — `"EXPIRED"` is the only non-purchased terminal cart status; `"ABANDONED"` does not exist as a status value.)
7. **Write TXN void**: Conditional `update_item` on `TXN#{txn_id}/META`:
   ```python
   T.pos.update_item(
       Key={"pos_pk": f"TXN#{txn_id}", "pos_sk": "META"},
       UpdateExpression="SET #st = :v, voided_at = :now, void_reason = :r",
       ConditionExpression="#st IN (:draft, :open)",
       ExpressionAttributeNames={"#st": "status"},
       ExpressionAttributeValues={":v": "voided", ":now": now_ts(), ":r": reason,
                                   ":draft": "draft", ":open": "open"},
   )
   ```
   On `ConditionalCheckFailedException` (concurrent void or status changed): reload
   and return the current TXN row (idempotent).
8. Emit `audit_event("pos_void", cashier_sub, None, pos_txn_id=txn_id, reason=reason)`
   (best-effort `try/except`).
9. Return the updated TXN dict.

### 4.2 `refund_transaction`

```python
def refund_transaction(
    txn_id: str,
    cashier_sub: str,
    line_refs: List[Dict[str, Any]],   # [{sku, qty}] — empty list = full refund
    *,
    reason: str = "refund",
    idempotency_key: str,
) -> Dict[str, Any]:
```

`line_refs` is a list of `{"sku": str, "qty": int}` maps identifying which line
items to refund. An empty `line_refs` list means a full refund of all lines at
their original quantities. `qty` must be ≥ 1 and ≤ the original purchased quantity
for that SKU (validated against the TXN's `line_snapshot`, written by POS-005/006).

**Steps:**

1. `_require_pos_enabled()`.
2. Load TXN row; raise `HTTPException(404)` if absent.
3. Ownership check (`cashier_sub` must match `txn["cashier_sub"]`).
4. Status guard: `status != "tendered"` → `HTTPException(409, f"Cannot refund from status {status}")`.
   (Already-voided, already-fully-refunded, or draft transactions all fail here.)
5. **Idempotency gate**: compute
   `refund_id = hashlib.sha256(f"pos_refund:{txn_id}:{idempotency_key}".encode()).hexdigest()[:32]`.
   Attempt a conditional `put_item` on a new `REFUND_LOCK#{refund_id}/META` row with
   `ConditionExpression="attribute_not_exists(pos_pk)"`. On
   `ConditionalCheckFailedException`: reload TXN and return idempotently (double-refund
   prevented).
6. **Resolve line_refs**: if `line_refs` is empty, expand it from
   `txn["line_snapshot"]` (written by POS-005 as `[{sku, qty, unit_price_cents}]`).
   Validate each `{sku, qty}` against the snapshot: unknown SKU → 422; qty exceeds
   purchased qty → 422; qty 0 → 422.
7. **Compute `refund_amount_cents`**: prorate by `unit_price_cents`:
   `sum(snap["unit_price_cents"] * ref["qty"] for ref in resolved_refs)`.
   For a full refund, `refund_amount_cents == txn["total_cents"]`.
8. **Determine refund mode** from `txn["tender_kinds"]` (the list written by
   POS-006/007 once settled). For each original tender leg in order:
   - **Card leg** (`kind="card"`): Call `stripe.Refund.create(payment_intent=tender["pi_id"], amount=leg_refund_cents, reason="requested_by_customer")`. Write one refund ledger entry via `new_ledger_entry(entry_type="adjustment", reason="refund", amount_cents=leg_refund_cents, state="settled", meta={"pos_txn_id": txn_id, "reason": reason}, extra={"provider": "stripe", "stripe_payment_intent_id": tender["pi_id"]})` + `ddb_put(T.billing, ...)`. Call `settle_or_reverse_ledger(T.billing, "pk", pk, tender["ledger_sk"], "reversed")`. Call `apply_balance_delta(T.billing, pk, {"payments_settled_cents": -leg_refund_cents})`.
   - **Wallet leg** (`kind="wallet"`): Call `apply_wallet_delta(T.billing, pk, +leg_refund_cents)`. Write refund ledger entry with `extra={"provider": "wallet"}` + reverse original ledger row + apply balance delta.
   - **Cash leg** (`kind="cash"`): Write a negative-amount cash tender (a `REFUND#` row with `kind="cash_refund"`, `amount_cents=leg_refund_cents`, `reason=reason`). Write refund ledger entry with `extra={"provider": "pos_cash"}` + reverse original ledger row + apply balance delta. Atomically decrement session `cash_in_cents`:
     ```python
     T.pos.update_item(
         Key={"pos_pk": f"SESSION#{session_id}", "pos_sk": "META"},
         UpdateExpression="ADD cash_in_cents :neg",
         ExpressionAttributeValues={":neg": -leg_refund_cents},
     )
     ```
   Proration across multiple tender legs: distribute `refund_amount_cents`
   proportionally to each leg's original `amount_cents` (largest-remainder method
   for integer cents). Full refunds refund each leg in full.
9. **Restock inventory** (best-effort): if `S.inventory_reservations_enabled`:
   ```python
   try:
       from app.services import inventory as inv
       for ref in resolved_refs:
           if ref.get("sku") and ref.get("qty", 0) > 0:
               inv.adjust(ref["sku"], ref["qty"], reason="pos_refund_restock", user_sub="system")
   except Exception:
       pass
   ```
10. **Update TXN status**: determine if fully or partially refunded:
    - `total_refunded_qty == total_original_qty` → `status="refunded"`
    - else → `status="partial_refund"` (append to `refunded_line_refs`; update
      `refund_amount_cents` via `ADD`)
    - Conditional `update_item` on TXN row; append `refund_ledger_sks`.
11. Emit `audit_event("pos_refund", cashier_sub, None, pos_txn_id=txn_id, refund_amount_cents=refund_amount_cents, reason=reason)` (best-effort).
12. Return updated TXN dict.

## 5. Detailed Behavior & Edge Cases

### 5.1 Void of a draft transaction (status `"draft"`, no tenders)

The simplest path: no tender rows exist, no money has moved. `void_transaction`
skips the tender-reversal loop (step 5 finds zero rows), abandons the bound cart
(step 6), and writes `status="voided"`. One ledger-entry-free operation.

### 5.2 Void of a partially-tendered transaction (status `"open"`)

The transaction has one or more `TENDER#` rows but `purchase_cart` has not been
called. Each unsettled tender leg must be reversed before the cart is abandoned:
- Card leg: Stripe refund + ledger reversal.
- Wallet leg: wallet credit + ledger reversal.
- Cash leg: If POS-006's cash tender committed the ledger entry before `purchase_cart`
  (the design where ledger is written as each leg lands), decrement `cash_in_cents`
  and reverse the ledger row. If POS-006 only writes the cash ledger at full settlement,
  no cash ledger reversal is needed.

**Assumption**: per POS-006 spec §4.1 step 9, the cash ledger entry IS written
immediately when `tender_cash` is called (before the full-settlement check). This
means a cash leg in an `"open"` transaction has a live ledger entry that must be
reversed by `void_transaction`.

### 5.3 Void of a settled transaction — 409

`status == "tendered"` → `HTTPException(409, "Transaction is settled; use refund_transaction instead")`. This is enforced at step 4 before any writes.

### 5.4 Full cash refund — till adjustment

A full cash refund (`line_refs=[]`) refunds the entire `total_cents` via cash.
The session `cash_in_cents` is decremented by `total_cents` (step 8 cash path).
At close, `expected_cash_cents = opening_float + cash_in_cents − change_out_cents`
will be reduced by the refund amount, matching the physical till which now has
`total_cents` less cash.

### 5.5 Partial-quantity refund — proration

`line_refs=[{"sku": "SKU1", "qty": 2}]` on a transaction with 5 units of SKU1
at $3.00/unit: `refund_amount_cents = 2 * 300 = 600`. The prorated refund across
tender legs uses the largest-remainder method to avoid rounding loss:

```python
total = refund_amount_cents   # 600
legs = sorted(tender_legs, key=lambda t: t["amount_cents"], reverse=True)
total_tendered = sum(t["amount_cents"] for t in legs)
leg_shares = [round(total * t["amount_cents"] / total_tendered) for t in legs]
# Fix rounding drift on the first (largest) leg:
leg_shares[0] += total - sum(leg_shares)
```

Each leg receives `leg_shares[i]` cents of the refund.

### 5.6 Double-refund prevention (idempotency)

The `REFUND_LOCK#{refund_id}/META` conditional put (step 5 of `refund_transaction`)
prevents two concurrent refunds with the same `idempotency_key`. The `refund_id` is
`sha256(f"pos_refund:{txn_id}:{idempotency_key}")[:32]` — deterministic from the
caller's key.

A second call with the same `idempotency_key` hits `ConditionalCheckFailedException`
on the lock row, reloads the TXN, and returns the already-recorded refund state.
No second Stripe call is made, no second ledger entry is written, no second
`cash_in_cents` decrement occurs.

### 5.7 Partial refund followed by another partial refund

POS-008 supports multiple partial refunds up to the original transaction total. Each
call is idempotent on its own `idempotency_key`. The TXN row's
`refunded_line_refs` accumulates all refunded `{sku, qty}` entries (via
`list_append`) and `refund_amount_cents` is incremented via `ADD`. When cumulative
`refund_amount_cents == total_cents`, `status` transitions to `"refunded"`. A
further refund attempt on a `"refunded"` TXN returns 409.

### 5.8 Stripe refund failure on card void/refund

If `stripe.Refund.create` raises a Stripe exception during a card leg reversal:
- Log the error as an audit event.
- Raise `HTTPException(502, "Card refund failed: {details}")`.
- No ledger entry is written.
- No TXN status update is written (the `REFUND_LOCK` row was not yet committed;
  or if it was, the lock prevents double-retry but the refund state is incomplete).
- The cashier must retry.

This differs from inventory restock errors (which are swallowed). Card refund
failures are surfaced because money-out to the card network is a critical operation.

### 5.9 Mixed-tender split (card + cash) refund

For a split-tender settled txn (`ledger_sks=[card_ledger_sk, cash_ledger_sk]`):
- `refund_transaction` distributes `refund_amount_cents` proportionally across
  the card and cash legs.
- Card portion: Stripe refund + ledger reversal.
- Cash portion: negative cash tender row + `cash_in_cents` decrement + ledger reversal.
- Both reversals happen in sequence within the same service call. If the card
  refund succeeds but the subsequent session counter update fails, the session
  float is inconsistent. This is mitigated by writing the session counter update
  last and wrapping it in `try/except` — the till reconciliation (POS-010) will
  show the discrepancy in the over/short calculation.

### 5.10 Inventory restock is best-effort and idempotent at the inventory layer

`inventory.adjust(sku, +qty, reason="pos_refund_restock")` at
`app/services/inventory.py:209` is always wrapped in `try/except` and never blocks
the refund. If the inventory service is unavailable or the SKU has no inventory
record, the refund still succeeds. The `pos_refund_restock` reason string appears
in the inventory audit log (`_audit("inventory.adjust", ...)` at `:250`), making
it traceable independently of the refund ledger.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

All DDB writes use the same code path in dev (DynamoDB Local port 8001) and prod
(real DynamoDB). There is no `if S.dev_mode` branch in `pos_tender.py`. The Stripe
mock (stripe-mock binary on port 12111 in dev, set via `S.stripe_api_base`) is
used transparently through the `stripe.Refund.create` call — identical code in
both envs. `inventory.adjust` reads from the local DynamoDB inventory table in
dev; prod uses the same table. No AWS divergence.

### 7.2 Idempotency

- **`void_transaction`**: The conditional `update_item` with
  `ConditionExpression="#st IN (:draft, :open)"` is the atomicity gate. A
  concurrent second void call catches `ConditionalCheckFailedException` and returns
  the already-voided TXN. The per-leg tender reversals (Stripe, wallet, cash) are
  each guarded by the tender row's existing `ledger_sk` back-ref — on retry the
  service can check whether the original ledger entry is already `"reversed"` before
  issuing another Stripe/wallet call.
- **`refund_transaction`**: `sha256(f"pos_refund:{txn_id}:{idempotency_key}")[:32]`
  is the deterministic lock key. The `REFUND_LOCK` conditional put is the primary
  gate. Stripe's `idempotency_key` parameter on `Refund.create` provides a secondary
  layer.

### 7.3 Security

- `cashier_sub` is always sourced from `ctx["user_sub"]` (authenticated session),
  never from the request body.
- Ownership check at step 3 of both functions prevents a cashier from voiding or
  refunding another cashier's transaction.
- CSRF enforced by `require_ui_session` for all non-GET POS endpoints (cookie-auth
  path), consistent with all other POS and billing endpoints.
- Integer-cents arithmetic throughout; `_FloatSafeTable` at `app/core/tables.py:29`
  coerces any stray `float` to `Decimal` on write.
- The `refund_id` lock prevents partial-state replays from triggering duplicate
  money-out events.

### 7.4 Audit trail

Both `void_transaction` and `refund_transaction` emit `audit_event(...)` via
`app/services/alerts.py:644`, wrapped in best-effort `try/except`. Fields include:
`pos_txn_id`, `session_id`, `cashier_sub`, `reason`, and for refunds:
`refund_amount_cents`, `provider(s)`. This mirrors the audit coverage in
`returns_rma.refund_return` at `:532–540`.

## 10. Open Questions / Assumptions

1. **Assumption: `line_snapshot` on TXN row**. `refund_transaction` resolves qty and
   unit prices from a `line_snapshot: [{sku, qty, unit_price_cents}]` attribute on
   the TXN row. POS-005 (cart binding) must write this snapshot at settlement time
   (alongside `subtotal_cents`). If POS-005 does not write `line_snapshot`, the refund
   service must query the linked `order_id`'s order items table instead. This spec
   assumes POS-005/006 write the snapshot.

2. **Assumption: `tender_kinds`, `pi_ids`, and `ledger_sks` lists on TXN row**.
   POS-007 spec (§3.3) states `ledger_sks: list[str]` is written at settlement.
   This spec extends that to `tender_kinds: list[str]` and `pi_ids: list[str]` so
   `refund_transaction` can dispatch per-leg without re-querying all `TENDER#` rows.
   If POS-007 does not write these lists, `refund_transaction` must query
   `begins_with("TENDER#{txn_id}#")` to reconstruct the per-leg data.

3. **Assumption: partial void not supported.** `void_transaction` cancels the entire
   transaction. There is no "partial void" (removing a single line item from an
   `"open"` transaction). Removing a line item before settlement uses the existing
   POS-005 `remove_line_item` path. If partial-void support is later desired, a new
   endpoint is needed.

4. **Assumption: cash tender rows in `"open"` transactions have a committed ledger entry**.
   POS-006 spec §4.1 shows the ledger entry is written when `tender_cash` is called,
   even before full settlement on a split-tender transaction. If POS-006 defers the
   ledger write until full settlement, the `"open"` void path has no ledger entry to
   reverse for the cash leg, simplifying step 5 of `void_transaction`.

5. **Assumption: `REFUND_LOCK` rows are never cleaned up.** The lock row at
   `REFUND_LOCK#{refund_id}/META` persists indefinitely in the `pos` table. This is
   intentional (same pattern as `RECOVERY#CONSUMED#` rows in cart recovery). A
   DynamoDB TTL of 90 days on these rows is a reasonable enhancement but is out of
   scope for POS-008.

6. **Question: should a full refund mark the linked order as `"refunded"`?** The
   `commerce_order_service` has no "refunded" order status in the existing codebase.
   `mark_reverted` in `app/services/purchase_history.py:469` transitions the purchase
   transaction to `"REVERTED"`. Should `refund_transaction` call `mark_reverted` for
   the linked purchase transaction? This spec assumes yes for full refunds
   (`refund_amount_cents == total_cents`), mirroring `refund_payment` at `:1330`.

7. **Question: void of an `"open"` transaction — should partial card/wallet ledger
   entries be reversed via Stripe refund or via auth cancellation?** For a card
   leg that settled via `off_session=True, confirm=True` PaymentIntent, no "auth
   cancellation" is possible; a full Stripe refund is required. This spec assumes
   the `"open"` state implies the PaymentIntent has already been confirmed (charged),
   so `stripe.Refund.create` is the only reversal path.
