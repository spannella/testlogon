# PRD-015 — Catalog-depth admin UI (variants, features, bundles, tree)

## 1. Summary & Goal

PRD-015 delivers the frontend half of the OFBiz-style product-depth system. The backend services and router endpoints were shipped in PRD-004 through PRD-013; PRD-014 added the TypeScript types and axios endpoint wrappers. This ticket wires those wrappers into a set of admin UI panels embedded within the existing shop admin shell.

The concrete deliverables are:

- **`CatalogDepthAdmin.tsx`** — a top-level page component (`frontend/src/pages/shop/admin/`) rendered in a five-tab layout (Tree, Features, Variants, Bundles, Associations, Prices). Composed from five focused sub-panels, each a separate file in the same directory.
- **`CategoryTreePanel.tsx`** — category-tree manager: indented tree with breadcrumb path, drag-reorder via `SortableList`, add-child dialog, move-to-parent dialog.
- **`FeaturesPanel.tsx`** — feature-category/value editor: create/delete feature categories, add feature values with optional `price_delta_cents` and `position`, reorder via drag.
- **`VariantMatrixPanel.tsx`** — variant matrix builder: selects an item, shows the Cartesian grid of feature-value combinations as rows, each row displaying SKU, selected feature values, and live effective price (parent `price_cents` + Σ delta). Create and delete individual variant rows.
- **`BundlesPanel.tsx`** — bundle/kit composer: pick a bundle/kit item, add component items with quantities, show `expand_bundle` output (flattened lines + computed price), distinguish kit vs bundle pricing.
- **`AssociationsPanel.tsx`** — associations panel: pick a source item, add/remove SUBSTITUTE/COMPLEMENT/UPGRADE/MANUF associations with hydrated target summaries.
- **`PriceComponentsPanel.tsx`** — price-components editor: dated rows per `price_type`, create/edit/delete, resolved effective price display for a chosen `as_of` date.
- A `GET /ui/catalog/depth-config` endpoint on the existing `catalog.router` that returns `{ product_depth_enabled: bool }`, consumed by a `useQuery` in the depth-admin entry point to gate the entire surface at runtime.
- A lazy-loaded route at `admin/catalog-depth` in `frontend/src/App.tsx`, and a nav entry shown only when `product_depth_enabled` is true.

With `PRODUCT_DEPTH_ENABLED=false` (the default), the backend endpoint returns `{ product_depth_enabled: false }`, the route still mounts but immediately renders an "unavailable" banner, and the sidebar nav link is hidden. Every existing catalog/cart/billing/orders path is byte-for-byte unchanged.

### 4.6 VariantMatrixPanel

**`frontend/src/pages/shop/admin/VariantMatrixPanel.tsx`**

State: `selectedItemId: string | null`.

Queries:
- Item picker (same as FeaturesPanel).
- `useQuery(["catalog", "feature-categories", selectedItemId], () => getItemFeatures(selectedItemId!), { enabled: !!selectedItemId })`.
- `useQuery(["catalog", "variants", selectedItemId], () => getItemVariants(selectedItemId!), { enabled: !!selectedItemId })` — calls `GET /ui/catalog/items/{id}/variants`.

The parent item data (specifically `price_cents`) is obtained from the item picker query or a `GET /ui/catalog/items/{itemId}` call, stored in local state alongside the item ID.

Matrix logic (pure, client-side):

```
function cartesianProduct(featureCategories: FeatureCategory[]): FeatureValue[][]
```

Returns the full Cartesian product of all feature-value arrays. Each row corresponds to one combination. For each row, the effective price is:

```
effectivePrice = parentPriceCents + sum(row.map(v => v.price_delta_cents ?? 0))
```

This mirrors the server-side formula in `app/services/product_variants.py` (PRD-007) so the display is live without a round-trip.

Mutations:
- `createVariantMutation`: `POST /ui/catalog/items/{id}/variants` with `{ feature_value_ids: [...], sku?: string }`. On success: invalidate `["catalog", "variants", selectedItemId]`.
- `deleteVariantMutation`: `DELETE /ui/catalog/items/{id}/variants/{variantId}`. On success: invalidate same.

Layout: a `Table` with columns:

| Feature 1 | Feature 2 | … | SKU | Effective Price | Exists | Actions |
|---|---|---|---|---|---|---|

Each row represents one combination. The "Exists" column shows a green checkmark `Badge` if a variant already exists for this combination (matched by deterministic variant id or by comparing `feature_value_ids`), otherwise a "Create" `Button`. The "Actions" column shows a "Delete" button (only if the variant exists). A row whose variant exists is highlighted with a `bg-muted/40` row class. A "Generate All" `Button` above the table creates all missing combinations in sequence (mutations fired in series to avoid DynamoDB write conflicts), with a `Loader2` spinner and disabled state while running.

## 5. Detailed Behavior & Edge Cases

### Flag-off state

`GET /ui/catalog/depth-config` returns `{ product_depth_enabled: false }` when `S.product_depth_enabled` is `False`. The `CatalogDepthAdmin` page renders a centered `EmptyState` with the message "Product depth is not enabled on this instance." No tab structure, no queries to depth endpoints. The sidebar nav link for "Catalog Depth" is hidden (conditional on `depthConfig?.product_depth_enabled`).

All PRD-005/008/011/013 endpoints return `404` or `501` when the flag is off. If somehow a depth endpoint is called with the flag off (e.g. a cached stale flag value), the axios error handler surfaces the error as a `toast.error` message — no crash.

### Item picker pattern (shared)

Each panel that requires an item selection uses a two-step picker: first a `Select` populated from `getCategories()` to choose a category, then a second `Select` populated from `getCategoryItems(catId)` to choose an item. The item `Select` is disabled until a category is selected. Both lists are loaded with `useQuery` and cached under their standard keys (`["catalog", "categories"]` and `["catalog", "admin-items", catId]`) — re-used across panels, no redundant fetches.

### Variant matrix — handling zero feature categories

If the selected item has no feature categories attached, the matrix table shows an `EmptyState` with the message "Attach at least one feature category to generate variants." The "Generate All" button is hidden.

### Variant matrix — "Generate All" sequencing

Mutations are fired one at a time (await each before the next) to avoid optimistic collision. If any individual create fails with `409 Conflict` (the combination already exists — duplicate deterministic id), that row is silently skipped (the variant is already present); the remaining rows continue. After all mutations complete, the variants query is invalidated once.

### Bundle expansion vs. components edit

The expansion preview calls `GET /items/{id}/expand` which is a read-only computed view. It is automatically re-fetched (`staleTime: 0`) whenever the `setComponentsMutation` succeeds. Kit vs. bundle distinction is shown to the user: a "KIT" badge means the total is the sum of component prices; a "BUNDLE" badge means the total is the item's fixed `price_cents`. The distinction comes from the `product_type` field on the item returned by the item picker.

### Move category — cycle prevention

The Move dialog's target `Select` excludes the node being moved and all of its descendants (computed from the loaded tree). The exclusion list is computed client-side from the `getCategoryTree` response before rendering the Select options. If the backend also rejects the move with `400 Conflict` (cycle detected), the mutation `onError` handler calls `toast.error("Cannot move: would create a cycle.")`.

### Price component date overlap

The backend (PRD-012) resolves the most-recent active component for a given `as_of`. The frontend does not enforce non-overlapping date windows; it simply posts what the admin enters and relies on the backend's resolution logic. The effective-price display makes the active component obvious.

### Pagination

All item pickers use `page_size=200` to keep the selector populated without multi-page UX. Category lists are similarly bounded. If a catalog has more than 200 items per category, a warning `Badge` ("Large catalog — showing first 200") is rendered below the picker; full pagination is out of scope for this ticket.

### Loading and error states

Every `useQuery` result that is loading shows a `Loader2` spinner in place of the panel content. Every `useQuery` error shows an `Alert` with the error message and a "Retry" `Button` that calls `query.refetch()`. Mutations follow the existing pattern (`onError: () => toast.error("...")`, `onSuccess: () => toast.success("...")`).

### CSRF

All mutating calls go through the axios instance in `frontend/src/api/client.ts`, which auto-attaches the `x-csrf-token` header from the `ui_csrf` cookie. No per-panel CSRF handling is needed.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

`GET /ui/catalog/depth-config` reads `S.product_depth_enabled` — the same singleton used by all depth endpoints. No `dev_mode` branch. With `DEV_MODE=1` and `PRODUCT_DEPTH_ENABLED=0`, the UI shows the disabled state; with both on, the full UI is available. No mocked responses or `S.dev_mode` conditionals in this endpoint.

### Security

- All depth write endpoints (PRD-005/008/011/013) require `require_ui_session` + `_require_category_owner` ownership check. Non-owners receive `403`. The frontend does not re-implement this check — it is enforced server-side.
- The depth-config endpoint (`GET /ui/catalog/depth-config`) requires `require_ui_session` but no ownership; it returns a global flag value.
- No new auth roles or scopes are introduced. The frontend admin gating (showing the tab in the sidebar) is a UX convenience only, not a security boundary — the backend endpoints enforce ownership.
- XSS: all user-supplied strings (category names, feature names, item names) are rendered via React's JSX escaping. No `dangerouslySetInnerHTML`.

### Idempotency

All idempotency guarantees live in the backend service layer (PRD-004 through PRD-013):
- Variant creation uses `sha256(parent_id + sorted feature-value tuple)` for deterministic IDs. A second "Create" click returns `409` which the UI silently ignores (the variant already exists).
- Association creation uses `sha256(from + type + to)`. Duplicate `POST` returns `409`; the UI treats this as success (already present).
- Price component upsert uses `PUT` semantics — backend overwrites if exists.

The frontend's "Generate All" logic (§5) exploits these backend idempotency guarantees.

## 10. Open Questions / Assumptions

1. **PRD-014 endpoint wrapper naming.** This spec assumes `catalogDepth.ts` exposes functions named `getCatalogDepthConfig`, `getCategoryTree`, `getCategoryBreadcrumb`, `addCategoryChild`, `moveCategory`, `getItemFeatures`, `createFeatureCategory`, `attachFeatureCategory`, `addFeatureValue`, `getItemVariants`, `createVariant`, `deleteVariant`, `getBundleComponents`, `setComponents`, `expandBundle`, `getItemAssociations`, `addAssociation`, `removeAssociation`, `getItemPriceComponents`, `upsertPriceComponent`, `getEffectivePrice`. If PRD-014 uses different names, the implementer must reconcile.

2. **`CatalogItem.product_type` field availability.** The spec assumes PRD-014/PRD-003 added `product_type?: string` to `CatalogItemOut` and the TypeScript `CatalogItem` interface. The BundlesPanel and VariantMatrixPanel use this field to show the correct type badge. If absent, fall back to reading a `product_type` field from the item's `attributes` map.

3. **`FeatureCategory` type shape.** Assumed to be `{ fc_id: string; name: string; values: FeatureValue[] }` where `FeatureValue` is `{ fv_id: string; name: string; price_delta_cents?: number; position?: number }`. If PRD-014 uses a different shape, adapt accordingly.

4. **Tree endpoint response.** Assumed `GET /categories/{id}/tree` returns `{ children: CategoryTreeNode[] }` where `CategoryTreeNode` is `{ category_id: string; name: string; path: string; position?: number; children?: CategoryTreeNode[] }`. The recursive tree render handles arbitrary depth.

5. **Drag-reorder for tree children.** The spec calls for `SortableList` within a single parent's children list. This requires a `PATCH /categories/{id}/reorder` or similar endpoint (not explicitly specified in PRD-005). If no reorder endpoint exists, drag-reorder within a subtree is omitted from the CategoryTreePanel in v1 and replaced with up/down arrow buttons that fire individual `move` calls.

6. **Admin navigation.** The spec assumes the sidebar navigation component (likely in `frontend/src/components/layout/`) has a pattern for conditionally showing nav links based on a runtime query. If the sidebar is static, the "Catalog Depth" link may need to always render but navigate to the page where the EmptyState appears. The implementer should check the sidebar implementation and align.

7. **`api.get<T>` with query params pattern.** `api.get<T>(path, params)` where `params` is `Record<string, string>` (all values must be strings — no `number` values) per `frontend/src/api/client.ts:290`. <!-- CORRECTED: client.ts:290 defines params as Record<string,string>, not Record<string,string|number> --> Consistent with `getCategoryItems` at line 69 of `cart.ts` <!-- CORRECTED: function is at cart.ts:69, not line 73 --> which stringifies `pageSize` via `String(pageSize)` before passing.

8. **Move-category destination list.** Loading the full flat category list for the Move dialog may include hundreds of entries on large catalogs. If `getCategories()` is paginated, the dialog may need a search-based `Select` (command palette pattern) rather than a plain `Select`. For v1, cap at 200 with a note; upgrade to command palette if performance is an issue.

9. **`just restart` not required for this ticket.** No DDB table changes. Implementers should confirm that the backend does not require a restart to pick up the new `GET /ui/catalog/depth-config` endpoint after a code-only hot reload. Since uvicorn is run with `--reload` in dev, no restart is needed during development; a clean deploy picks up the endpoint automatically.
