# FXA-010 — Depreciation poster background loop

## 1. Summary & Goal

FXA-010 wires the background automation layer that makes depreciation actually post without manual intervention. The two prior tickets — FXA-006 (schedule generation) and FXA-009 (per-period journal posting) — produce and consume individual schedule rows. This ticket adds the scheduler that drives them continuously:

1. **`run_depreciation_poster_loop()`** — an `async` loop that queries `fixed_asset_schedule.GSI_DUE` for `schedule_status="scheduled"` rows whose `period_end_ts <= now_ts()`, calls `post_depreciation_period(asset_id, period)` for each, and sleeps for `S.fixed_assets_depreciation_poll_interval` seconds (default 86 400 s, i.e. once per day).
2. **`start_depreciation_poster_task()`** — the FastAPI startup hook: registers the loop as a background coroutine when both `S.fixed_assets_enabled` and `S.fixed_assets_depreciation_posting_enabled` are true; is a documented no-op otherwise.
3. **Registration** in `app/main.py` next to `start_compute_billing_timer_task` / `start_k8s_ttl_checker_task`.

With either flag off, not a single line of FXA-010 code executes at runtime. With both flags on, every depreciation period whose `period_end_ts` has passed is posted within one poll cycle, idempotently across restarts, and periods not yet due are silently skipped.

## 2. Context & Current State

### 2.1 The `fixed_asset_schedule` table and `GSI_DUE`

`docs/ofbiz/specs/FXA-003.md` and `FIXED_ASSETS_TICKETS.md:55` define:

- **PK**: `pk` (S) = `"ASSET#{asset_id}"`
- **SK**: `sk` (S) = `"PERIOD#{period:07d}"`, one row per straight-line period
- **GSI `GSI_DUE`**: partition key `schedule_status` (S), sort key `period_end_ts` (N)
- `attr_types={"period_end_ts": "N"}` in `scripts/local-ddb-init.py` (per the CLAUDE.md numeric-GSI-gotcha; compare `scripts/local-ddb-init.py:2475` where `GSI_EXPIRY` is defined for the reservations table, with `attr_types={"created_at": "N", "expires_at": "N"}` at `:2477`)

This GSI is the single index the poster uses. A query with `schedule_status="scheduled" AND period_end_ts <= now_ts()` returns every period that has fallen due but has not yet been posted, across all assets, system-wide.

### 2.2 `post_depreciation_period` (FXA-009 deliverable)

`FIXED_ASSETS_TICKETS.md:181–182` defines `post_depreciation_period(asset_id: str, period: int)` in `app/services/fixed_assets.py`. This function:

- Posts a balanced non-cash GL journal entry (Dr Depreciation Expense / Cr Accumulated Depreciation) via `app/services/gl_posting.py`.
- Is idempotent: deterministic `journal_id = sha256(f"{asset_id}:period:{period}")[:32]` (`docs/ofbiz/specs/FXA-009.md:8`); early return when schedule row already has `schedule_status="posted"` (`FXA-009.md:13`); the `post_journal_entry` call in `gl_posting.py` also guards the GL write via `attribute_not_exists` on the journal table. Re-calling it for an already-posted period is a confirmed no-op.
- On success flips the schedule row to `schedule_status="posted"` and increments `accumulated_depreciation_cents` on the asset row.
- When the final period posts, flips the asset `status="fully_depreciated"`.

FXA-010 calls `post_depreciation_period` exactly as specified — it owns zero posting logic itself. The only new code in FXA-010 is the query loop, the startup gating, and the registration.

### 2.6 Pagination requirement — `LastEvaluatedKey` exhaustion

CLAUDE.md documents: "DDB FilterExpression doesn't reduce page size — DynamoDB fetches up to 1MB before applying FilterExpression. Any query that filters a sparse attribute must loop via LastEvaluatedKey." `GSI_DUE` is a direct KeyConditionExpression on the index — not a FilterExpression — so each page is fully filtered. However, the index can still return multiple pages of due periods when many assets reach their period end on the same day. The query loop must consume all pages before sleeping. Compare `app/services/compute_billing.py:507–522` (VERIFIED: `_scan_all_running_instances` defined at `:507`, `LastEvaluatedKey` loop at `:515–521`) where `_scan_all_running_instances` loops over `LastEvaluatedKey`.

## 4. API / Service Design

FXA-010 lives entirely in `app/services/fixed_assets.py`. It adds two public functions and one private query helper, with a thin registration line in `app/main.py`.

### 4.1 `_query_due_periods(now: int) -> list[dict]`

```python
def _query_due_periods(now: int) -> list[dict[str, Any]]:
    """Query GSI_DUE for all scheduled periods whose period_end_ts <= now.

    Exhausts LastEvaluatedKey pages so a busy index never silently drops
    due periods (CLAUDE.md "FilterExpression doesn't reduce page size" note —
    applies equally to multi-page GSI query results).
    """
    from boto3.dynamodb.conditions import Key

    items: list[dict[str, Any]] = []
    kwargs: dict[str, Any] = {
        "IndexName": "GSI_DUE",
        "KeyConditionExpression": (
            Key("schedule_status").eq("scheduled") & Key("period_end_ts").lte(now)
        ),
        "ScanIndexForward": True,  # oldest-due-first, natural posting order
    }
    while True:
        resp = T.fixed_asset_schedule.query(**kwargs)
        items.extend(resp.get("Items", []))
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
    return items
```

**Why `ScanIndexForward=True`**: posting periods in chronological order (oldest due first) is correct for accounting — it ensures accumulated depreciation increments in period order, which matches the conditional-update logic in FXA-009.

### 4.2 `run_depreciation_poster_loop(*, poll_interval: int | None = None) -> None`

```python
async def run_depreciation_poster_loop(
    *, poll_interval: int | None = None
) -> None:
    """Background task: post all due depreciation periods once per day.

    Queries GSI_DUE for schedule_status="scheduled" rows with
    period_end_ts <= now_ts(), calls post_depreciation_period for each,
    then sleeps for poll_interval seconds (default S.fixed_assets_depreciation_poll_interval).

    Idempotent across restarts: post_depreciation_period uses a conditional
    put (attribute_not_exists) so re-posting an already-posted period is a
    confirmed no-op (FXA-009).

    No dev_mode branch — same DDB code path in dev (moto) and prod (SECOPS-007).
    """
    interval = (
        poll_interval
        if poll_interval is not None
        else S.fixed_assets_depreciation_poll_interval
    )
    while True:
        try:
            _post_all_due_periods()
        except Exception:
            logger.exception("depreciation_poster_loop error")
        await asyncio.sleep(interval)
```

### 4.3 `_post_all_due_periods() -> int`

This is a synchronous helper extracted from the loop body to make it directly testable without an event loop.

```python
def _post_all_due_periods() -> int:
    """Post every due-but-unposted depreciation period.

    Returns the count of periods posted on this run (0 on a clean system
    or when all due periods were already posted on a prior run).
    """
    now = now_ts()
    due = _query_due_periods(now)
    posted = 0
    for item in due:
        # Extract asset_id from PK "ASSET#{asset_id}"
        pk = item.get("pk", "")
        asset_id = pk.removeprefix("ASSET#") if pk.startswith("ASSET#") else pk
        period = int(item.get("period", 0))
        if not asset_id or not period:
            logger.warning(
                "depreciation_poster_skip_malformed pk=%s period=%s", pk, period
            )
            continue
        try:
            post_depreciation_period(asset_id, period)
            posted += 1
            logger.info(
                "depreciation_posted asset_id=%s period=%d", asset_id, period
            )
        except Exception:
            logger.exception(
                "depreciation_post_failed asset_id=%s period=%d", asset_id, period
            )
    logger.info("depreciation_poster_tick posted=%d due=%d", posted, len(due))
    return posted
```

Per-period exceptions are caught and logged but never re-raised, so a posting failure on one asset does not abort the batch for other assets. This mirrors the pattern in `app/services/compute_billing.py:616–649` where `_tick_all_running_resources` continues through `InsufficientBalanceError` per-resource.

### 4.4 `start_depreciation_poster_task() -> None`

```python

    Both FIXED_ASSETS_ENABLED and FIXED_ASSETS_DEPRECIATION_POSTING_ENABLED

```

## 5. Detailed Behavior & Edge Cases

### 5.1 Due-period detection

The loop queries `schedule_status="scheduled" AND period_end_ts <= now_ts()`. The `period_end_ts` for period `n` is set by FXA-006 as approximately `acquired_at + n * seconds_per_month`. A period becomes due when `now_ts()` crosses its `period_end_ts`. Periods in the future (`period_end_ts > now`) are excluded by the `lte(now)` KeyConditionExpression and are never touched.

### 5.2 Idempotency across restarts

FXA-009's `post_depreciation_period` uses a DDB conditional put with `attribute_not_exists(journal_entry_id)` and immediately flips `schedule_status` to `"posted"`. Once `schedule_status="posted"`, the `GSI_DUE` query on `schedule_status="scheduled"` no longer returns that row. If the process crashes mid-batch, the partially-posted periods were already flipped, and the un-flipped ones will be re-queried and re-posted on the next wake cycle — `post_depreciation_period` handles the re-post as a no-op. There is no double-counting risk.

### 5.3 Empty batch (already caught up)

When all due periods have been posted by a prior run, `_query_due_periods(now)` returns an empty list. `_post_all_due_periods` returns `0` immediately. The loop logs `depreciation_poster_tick posted=0 due=0` and sleeps. This is the normal steady-state between daily wake cycles.

### 5.4 Large batches and pagination

If many assets have periods due on the same day, `GSI_DUE` may return multiple DynamoDB pages. `_query_due_periods` loops over `LastEvaluatedKey` until exhausted before returning the full list. The per-period exception handler in `_post_all_due_periods` ensures individual failures do not truncate the batch.

### 5.5 Period not yet due

A period with `period_end_ts > now` is excluded by the GSI KeyConditionExpression. The loop wakes once per `S.fixed_assets_depreciation_poll_interval`. With the default 86 400 s interval, a period that falls due at midnight will be posted on the following day's wake cycle, creating at most a one-day posting lag. This is standard accounting practice for automated day-end batch runs.

### 5.6 Asset in `fully_depreciated` or `disposed` status

FXA-009 flips the final period row to `schedule_status="posted"` and the asset status to `"fully_depreciated"`. The GSI query on `schedule_status="scheduled"` naturally excludes already-posted periods, so there is nothing for the loop to do for a fully-depreciated asset. Disposed assets (FXA-011) cancel remaining scheduled periods by flipping them to `schedule_status="cancelled"`, which likewise removes them from the `GSI_DUE` query result. FXA-010 does not need to inspect asset status directly.

### 5.7 Malformed rows

If a `GSI_DUE` result row is missing `pk` or `period` (e.g. a corrupt write or an integration test artefact), `_post_all_due_periods` logs a `WARNING` and `continue`s rather than crashing. This guards against stray test data on a shared dev stack.

### 5.8 `post_depreciation_period` failure modes

`post_depreciation_period` may raise for reasons including: asset row missing (race with disposal), GL journal store unavailable, or a concurrent update conflict. All such exceptions are caught per-item and logged at `ERROR` level. The batch continues for all other due periods. The failing item remains in `schedule_status="scheduled"` and will be retried on the next poll cycle.

### 5.9 Dual-flag gate

Both `S.fixed_assets_enabled` (master kill-switch for the entire module) and `S.fixed_assets_depreciation_posting_enabled` (poster-specific kill-switch) must be true. This allows operators to run the asset register and schedule generation without enabling automated posting — useful during initial data migration or audit freeze periods.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007: identical code paths

`_post_all_due_periods` and `_query_due_periods` perform DynamoDB reads and write through `T.fixed_asset_schedule` and `T.fixed_assets` (indirectly via `post_depreciation_period`). Both tables resolve to DynamoDB Local (moto-backed) in dev and real DynamoDB in prod. There is no `if S.dev_mode` branch anywhere in the poster code. The GL posting done by `post_depreciation_period` (via `app/services/gl_posting.py`) likewise uses the same table handles in both environments.

### 7.2 Idempotency

The poster achieves idempotency at three levels:

1. **GSI query** — `schedule_status="scheduled"` rows are the only target. Once `post_depreciation_period` succeeds, it flips the row to `"posted"`, removing it from future query results.
2. **Conditional put inside `post_depreciation_period`** — `attribute_not_exists(journal_entry_id)` on the GL journal entry write ensures only one journal entry per `(asset_id, period)` ever persists, even under restart mid-batch.
3. **DDB `attribute_not_exists` on schedule-row flip** — FXA-009 uses a conditional update on the schedule row itself so a concurrent re-post cannot double-increment `accumulated_depreciation_cents`.

A full restart during a posting batch therefore converges cleanly on the next wake cycle.

### 7.3 Security considerations

The poster runs under the process identity of the FastAPI application with no per-user authorization. It posts journal entries attributed to a system actor (no `user_sub` = no human). FXA-009's audit event for each posted period should record `user_sub="system_depreciation_poster"` to make these machine-generated entries distinguishable in audit logs. FXA-010 passes no credentials and never receives HTTP requests — its attack surface is limited to the DynamoDB read/write performed by `post_depreciation_period` plus the `_query_due_periods` query.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact with flags off

With `FIXED_ASSETS_ENABLED=false` (the default), `start_depreciation_poster_task` is imported by `app/main.py` but the `asyncio.ensure_future` line inside it is never reached. No background task is created. The DynamoDB table handles exist (FXA-002 wires them as `_safe_table(...)` which is a no-op-safe lazy reference) but are never read or written. All existing shop, cart, orders, billing, inventory, and GL paths are byte-for-byte unchanged.

### 8.2 Schema migration

`scripts/local-ddb-init.py` creates the `fixed_asset_schedule` table with `GSI_DUE` at stack startup (`just restart`). In production, the table must be created (or the GSI added) via `CreateTable` / `UpdateTable` before `FIXED_ASSETS_DEPRECIATION_POSTING_ENABLED` is turned on. The poster will query an empty index on first run and post nothing — correct behavior.

### 8.3 Brownfield data

If the stack has existing schedule rows from manual testing with `schedule_status="scheduled"` and old `period_end_ts` values, turning on the poster will post all historical due periods in the first wake cycle. This is intentional — it "catches up" a backlog. In production, a pre-cutover audit of the schedule table is advisable before enabling the flag.

### 8.4 Disabling mid-run

Disabling `FIXED_ASSETS_DEPRECIATION_POSTING_ENABLED` after the poster has been running stops future posting immediately (the loop will not be started on the next application restart). In-flight `post_depreciation_period` calls (already dispatched before the flag change) complete normally. No rollback is required.

## 10. Open Questions / Assumptions

1. **`post_depreciation_period` signature** — This spec assumes the FXA-009 deliverable exposes `post_depreciation_period(asset_id: str, period: int)` as a module-level function in `app/services/fixed_assets.py`. If FXA-009 instead returns a boolean or raises a specific typed exception for "already posted", `_post_all_due_periods` must handle that exception shape. The current spec treats any exception as a "retry next cycle" scenario.

2. **`asyncio.ensure_future` vs `asyncio.create_task`** — The spec follows the `compute_billing` / `k8s_launcher` precedent of `asyncio.ensure_future`. If the project decides to standardize all background tasks on `asyncio.create_task` (the pattern used by `audit_export_worker`), this is a trivial one-line change. Both are equivalent for the use case here.

3. **`job_registry` instrumentation** — The audit export worker uses `register_task` / `report_poll` / `report_error` from `app/services/job_registry` to surface the task in the dev-tools monitoring UI (`app/main.py:980–981`). FXA-010 intentionally omits this for simplicity (the depreciation poster is low-frequency and the audit is sufficient via logs). If visibility in the monitoring dashboard is desired, the pattern from `app/services/audit_export_worker.py:82–87` should be followed — this is an additive enhancement.

4. **`ScanIndexForward` ordering** — The spec uses `ScanIndexForward=True` (ascending `period_end_ts`) for natural posting order. FXA-009's idempotency does not depend on ordering, so reversing this is safe. Confirm with the FXA-009 implementer that the conditional update on `accumulated_depreciation_cents` uses a `+= amount_cents` expression rather than an absolute-value set, so posting order truly does not matter.

5. **Cancelled periods (FXA-011 disposal)** — FXA-011 is specified to flip remaining scheduled periods to `schedule_status="cancelled"`. This spec assumes `"cancelled"` rows are excluded from the `GSI_DUE` query because the partition key is `schedule_status` and the query is scoped to `schedule_status="scheduled"`. If FXA-011 instead leaves rows in `"scheduled"` and sets a separate `cancelled_at` attribute, `_post_all_due_periods` would attempt to post disposed-asset periods. This assumption must be verified with FXA-011's implementer.

6. **System-actor attribution** — `post_depreciation_period` (FXA-009) emits an audit event. The spec assumes the audit event records `user_sub="system_depreciation_poster"` or a similar sentinel. FXA-010 does not pass a `user_sub` to `post_depreciation_period`. Confirm FXA-009 has a default for headless/system callers.

7. **Concurrent instances** — In a multi-worker deployment (multiple uvicorn processes), each worker would start its own copy of the poster loop. Since `post_depreciation_period` is idempotent via conditional put, concurrent postings produce no duplication — the second conditional put raises `ConditionalCheckFailedException` and FXA-009 handles it as a no-op. No additional distributed-lock mechanism is needed at the FXA-010 level.
