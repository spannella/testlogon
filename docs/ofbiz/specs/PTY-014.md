## 1. Summary & Goal

PTY-014 introduces the Party/CRM frontend: a lazy-loaded React page at
`frontend/src/pages/party/PartyPage.tsx`, a React Router route at `/party` registered in
`frontend/src/App.tsx`, and a flag-gated nav entry in
`frontend/src/components/layout/Sidebar.tsx` adjacent to the existing "Contacts" item.

The page is the primary UI surface for the party graph built in PTY-001 through PTY-013. It
provides three distinct views to authenticated users:

- **Party list** — paginated table of all parties with type indicator and role badges; searchable
  by name/ID.
- **Party detail drawer** — a right-aligned `Sheet` that slides in when a row is clicked,
  showing roles, relationships, and contact mechanisms, with inline add/edit actions for each
  sub-resource.
- **Organizations tab** — a separate tab on the main page for `PARTY_GROUP` records, supporting
  create-org and manage-members workflows.

The nav entry and the `/party` route are conditionally rendered based on a single
`isPartyCrmEnabled()` flag helper in `frontend/src/lib/featureFlags.ts` (backed by
`VITE_PARTY_CRM_ENABLED`). With the flag off, neither the route nor the nav link is visible and
the browser receives a React Router 404 for direct `/party` navigation — the existing Contacts
page at `/contacts` is untouched.

## 3. Data Model

PTY-014 is a pure frontend ticket. It reads and writes data through the HTTP API exposed by
PTY-011/PTY-012 and typed by PTY-013. There are no new DynamoDB tables, GSIs, or settings keys
introduced in this ticket.

The DynamoDB schema (single `party` table) was fully specified in PTY-002:

| PK | SK | Purpose |
|----|-----|---------|
| `PARTY#{party_id}` | `META` | Party item (type, status, user_sub, created_at) |
| `PARTY#{party_id}` | `ROLE#{role_type}` | Role membership row |
| `PARTY#{from}` | `REL#{type}#{to}` | Outbound relationship edge |
| `PARTY#{party_id}` | `MECH#{type}#{mech_id}` | Contact mechanism |

GSIs used by the frontend-consumed API:

| GSI | PK | SK | Used for |
|-----|----|----|---------|
| `GSI1` | `ROLE#{role_type}` | `PARTY#{party_id}` | `parties_with_role` (role filter) |
| `GSI2` | `EMAIL#{norm}` / `PHONE#{e164}` / `POSTAL#{hash}` | `PARTY#{party_id}` | `/parties/lookup` |
| `GSI3` | `REL_TO#{to}` | `REL#{type}#{from}` | Inbound relationship queries |
| `GSI_CREATED` | `TYPE#{party_type}` | `created_at` (N) | Newest-first party listing |

These are the tables and indexes served through PTY-011/PTY-012 endpoints that the frontend
consumes — no additional schema work is required here.

## 4. API / Service Design

PTY-014 consumes API endpoints; it does not add any. The relevant API surface (from PTY-011
and PTY-012 specs) that the page calls:

### 4.1 Endpoint wrappers consumed from PTY-013

```ts
// Parties
getParties(params?: { party_type?: string; cursor?: string }): Promise<PartyListResp>
getParty(partyId: string): Promise<PartyOut>
createParty(req: CreatePartyIn): Promise<PartyOut>
updatePartyStatus(partyId: string, status: string): Promise<PartyOut>

// Roles
addRole(partyId: string, req: AddRoleIn): Promise<PartyRole>
removeRole(partyId: string, roleType: string): Promise<void>
listRoles(partyId: string): Promise<PartyRole[]>

// Relationships
createRelationship(partyId: string, req: CreateRelationshipIn): Promise<PartyRelationship>
deleteRelationship(partyId: string, relType: string, toPartyId: string): Promise<void>
listRelationships(partyId: string, direction?: "from" | "to" | "both"): Promise<PartyRelationship[]>

// Contact mechs
addContactMech(partyId: string, req: AddContactMechIn): Promise<ContactMechOut>
updateContactMech(partyId: string, mechId: string, req: Partial<AddContactMechIn>): Promise<ContactMechOut>
removeContactMech(partyId: string, mechId: string): Promise<void>
listContactMechs(partyId: string, mechType?: string): Promise<ContactMechOut[]>

// Orgs
createOrg(req: CreateOrgIn): Promise<OrgAccountOut>
listOrgs(): Promise<OrgAccountOut[]>
getOrg(orgPartyId: string): Promise<OrgAccountOut>
addOrgMember(orgPartyId: string, req: AddMemberIn): Promise<void>
removeOrgMember(orgPartyId: string, memberPartyId: string): Promise<void>
listOrgMembers(orgPartyId: string): Promise<OrgMemberOut[]>
```

### 4.2 React Query key structure

```ts
// Party list (both types together and filtered)
["party", "list"]                         // all parties
["party", "list", { party_type }]         // filtered by PERSON | PARTY_GROUP
["party", "detail", partyId]              // single party
["party", "roles", partyId]               // roles for a party
["party", "rels", partyId]                // relationships for a party
["party", "mechs", partyId]               // mechs for a party
["party", "orgs"]                         // org list
["party", "org", orgPartyId]              // single org detail
["party", "org-members", orgPartyId]      // org member list
```

`invalidateQueries({ queryKey: ["party"] })` (root key) is called after mutations that affect
multiple sub-resources (e.g., creating an org touches both `["party", "list"]` and
`["party", "orgs"]`). More targeted keys are used where only one resource changes.

## 5. Detailed Behavior & Edge Cases

### 5.1 PartyPage top-level structure

The page is split into two tabs rendered by `@/components/ui/tabs`:

- **People** (`PERSON` parties) — shows the party list table with role badges.
- **Organizations** (`PARTY_GROUP` parties) — shows org cards with member counts and an
  "Add Organization" action.

The default tab is "People". Both tabs share a search input that filters the visible list
client-side (for small lists) or drives a server-side `party_type`-filtered query.

### 5.2 Party list table (People tab)

- Columns: Avatar placeholder (initials from `party_id` prefix), Party ID (truncated), Type
  badge, Status chip, Roles (up to 3 badges then "+N more"), Created date.
- Clicking any row opens the `PartyDetailSheet` for that `party_id`.
- An "Add Party" button in the header opens a `Dialog` with a controlled form (`party_type`
  radio — PERSON or PARTY_GROUP, optional `correlation_id` for idempotency).
- Pagination: uses `cursor` from `PartyListResp` and an "Load more" button at the bottom
  (append-on-demand, not infinite scroll, matching the project's established pattern for
  paginated lists).

### 5.3 PartyDetailSheet

A right-side `Sheet` (width `sm:max-w-lg`) that renders on `open={selectedPartyId !== null}`.
The sheet is populated with three collapsible sections:

#### 5.3.1 Roles section

- `useQuery(["party", "roles", partyId], () => listRoles(partyId))`
- Shows a badge list of current roles. An inline "Add role" `Popover` with a `Select`
  component constrained to `PartyRoleType` enum values invokes `addRole`.
- Each role badge has an `×` delete button that calls `removeRole`.
- Duplicate-add is a no-op on the backend (PTY-005); the UI optimistically adds and then
  reconciles on re-query.

#### 5.3.2 Relationships section

- `useQuery(["party", "rels", partyId], () => listRelationships(partyId, "both"))`
- Table rows: direction arrow (→ / ←), relationship type, other party ID (clickable — opens
  that party's detail sheet).
- "Add relationship" inline form: `to_party_id` text input, `relationship_type` select,
  Submit. Calls `createRelationship`; self-relationship (`from === to`) is blocked on the
  backend (PTY-006) and the UI validates this client-side too (inline error).
- Delete button per row calls `deleteRelationship`.

#### 5.3.3 Contact mechanisms section

- `useQuery(["party", "mechs", partyId], () => listContactMechs(partyId))`
- Table with columns: Type badge (`EMAIL` / `PHONE` / `POSTAL`), Value (email/phone/address
  summary), Purposes (comma-joined), Verified chip.
- "Add mech" button opens a sub-`Dialog` with `mech_type` select, `value` text input, and a
  purposes multi-select. Calls `addContactMech`.
- Pencil icon per row opens the same dialog pre-filled; calls `updateContactMech`.
- Trash icon calls `removeContactMech`.
- POSTAL mechs render the address summary as `line1, city, state postal_code, country`.
- Validation mirrors the backend: EMAIL must match RFC-like pattern, PHONE must be dialable
  (E.164 intent, client leaves normalization to backend), POSTAL requires `line1`.

#### 5.3.4 Sheet invalidation

On any mutation inside the sheet, `queryClient.invalidateQueries({ queryKey: ["party",
"detail", partyId] })` is called plus the specific sub-key (`roles`, `rels`, `mechs`).
The party list is NOT re-fetched for contact mech changes; it IS re-fetched for status changes
(which affect the status chip).

### 5.4 Organizations tab

- `useQuery(["party", "orgs"], listOrgs)` returns a list of `OrgAccountOut`.
- Each org is rendered as a `Card` showing org name, member count, and owner party ID.
- Clicking a card opens `OrgDetailSheet` (same `Sheet` component, different content):
  - Members list rendered from `useQuery(["party", "org-members", orgPartyId], () => listOrgMembers(orgPartyId))`.
  - "Add member" form: `member_party_id` text input + `role_type` select (limited to
    `GROUP_MEMBER`, `ORG_ADMIN`). Calls `addOrgMember`. Non-admin callers will receive 403
    from the backend; the UI surfaces this as a `toast.error` (the same pattern used by
    `frontend/src/pages/contacts/ContactsPage.tsx:243` `onError: () => toast.error(...)`).
  - Remove member button (visible only for members with fewer privileges than the viewer).
  - The viewer's own membership is not removable via UI (prevented by backend 403, but the
    button is also hidden client-side when `member_party_id === viewer_party_id`).
- "Create Organization" button in the tab header opens a `Dialog` with `name` text input and
  an optional `correlation_id` field (hidden by default, shown in a "Advanced" disclosure).
  Calls `createOrg`; on success adds the new org to the list via cache invalidation.

### 5.5 Edge cases

- **Flag on, backend party_crm_enabled off**: Every API call returns 503 (the PTY-011
  per-handler guard). The page renders an empty state with a "Party CRM is currently
  disabled by the server" message and no mutations are possible. The `isLoading` / `isError`
  states from React Query are handled uniformly.
- **Flag off entirely**: The `/party` route is not registered in `App.tsx` (the `lazy()`
  import is inside an `isPartyCrmEnabled()` guard). Direct navigation to `/party` hits
  React Router's catch-all and renders the platform's 404 component. The nav entry is absent
  from the sidebar.
- **Empty party list**: The People tab renders an empty state with a "No parties yet" message
  and an "Add Party" CTA, mirroring `frontend/src/pages/contacts/ContactsPage.tsx:407-412`.
- **Unknown party in relationship "other" click**: If the linked party does not exist on the
  backend (deleted out of band), the sheet opens but the detail query returns 404. The detail
  sheet shows an error state ("Party not found") without crashing.
- **Stale list after sheet mutations**: Any mutation in the sheet (add role, remove mech, etc.)
  calls `invalidateQueries` so the party list badge count stays accurate without a full
  page reload.
- **B2B org creation race**: Creating an org is idempotent on the backend via `correlation_id`.
  If the user double-clicks Submit, the second call is a no-op server-side. The Submit button
  is disabled while the mutation is pending (`useMutation`'s `isPending` state).
- **ORG_ADMIN gate**: Add/remove member calls are rejected 403 when the caller is not an
  `ORG_ADMIN`. The UI surfaces these as `toast.error`; the member list is not mutated
  optimistically for these operations (pessimistic mutation to avoid UI thrash on 403).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

PTY-014 is a pure frontend ticket. All DynamoDB access, normalization, and authorization logic
lives in the backend (PTY-004 through PTY-012). The frontend calls the same HTTP endpoints in
both dev and prod environments — there is no frontend code path that branches on `dev_mode`.

### 7.2 CSRF

The `api` client in `frontend/src/api/client.ts:179-181` reads the `ui_csrf` cookie and sets
`X-CSRF-Token` on **every request** (GET and non-GET alike); the backend at
`app/core/settings.py:101` (`ui_csrf_header_name = "x-csrf-token"`) only validates this header
on non-GET requests, so all party mutations (POST, PATCH, DELETE) carry the required CSRF
header. <!-- corrected: client sets header unconditionally, not only on non-GET -->

### 7.3 Idempotency in UI

- **Create party / create org**: The form includes an optional `correlation_id` input (advanced
  section, defaults to a client-generated `crypto.randomUUID()` inserted at form-init time).
  The backend's `attribute_not_exists(PK)` conditional put (PTY-004) makes replay safe.
  The UI disables the Submit button while `isPending` to prevent double-post.
- **Add role**: Backend is idempotent per PTY-005. No client-side de-dup is needed.
- **Add mech**: `mech_id` is backend-generated; duplicate adds are distinct items. The UI
  does not attempt to prevent them — the user must explicitly remove duplicates.

### 7.4 Authorization surface in the UI

- The party detail sheet's "Add" / edit / delete buttons are shown to all authenticated users.
  Authorization enforcement is entirely server-side.
- For org member mutations: the "Add member" / "Remove" buttons are displayed to any user who
  can open the `OrgDetailSheet`. The backend enforces `ORG_ADMIN` and returns 403 if the caller
  lacks it. The UI handles 403 via `toast.error` (no special pre-check).
- PII in contact mechs (email, phone, postal address) is served from the backend and displayed
  directly; the frontend never stores or caches it beyond React Query's in-memory cache.

### 7.5 No money-out paths

PTY-014 has no billing, payment, or refund touch points. The billing ledger
(`app/services/billing_shared.new_ledger_entry`) and the `refund_payment` path are not called
or referenced anywhere in this ticket.

## 10. Open Questions / Assumptions

1. **PTY-013 API shape assumption**: This spec assumes PTY-013 delivers
   `PartyListResp = { parties: PartyOut[]; cursor?: string }` as the list response shape.
   If the backend returns a different envelope (e.g., top-level `items`), the `getParties`
   wrapper and pagination logic in the page must be adjusted.

2. **`ensure_person_party` for the current user**: The spec assumes the party detail sheet
   does not auto-link the viewing user's `user_sub` to the party being displayed. If PTY-010's
   `ensure_person_party` is called during session init, the party for the current user may
   already exist and could be displayed in the list. This is desirable behavior, but whether
   PTY-010 wires its hook into the session startup is determined by that ticket's implementation
   and has no impact on the UI design here.

3. **Inline party creation vs. `UserSearch`**: The "Add Party" dialog on the People tab uses a
   free-form `party_type` select + optional `correlation_id`. It does not use the existing
   `UserSearch` component (which searches registered platform users). The assumption is that
   a party represents any real-world entity, not necessarily a platform user — consistent with
   the OFBiz model. If the product decision changes (e.g., "PERSON parties must always link
   to a `user_sub`"), the form needs a `UserSearch` integration similar to
   `frontend/src/pages/contacts/ContactsPage.tsx:433-436`.

4. **Org name source**: `OrgAccountOut` is assumed to carry a `name` field populated from the
   PERSON party's `display_name` or a separate `org_name` attribute set during `create_org`.
   The exact field name depends on PTY-008's service design; the page renders `org.name` and
   falls back to `org.party_id` if absent.

5. **Pagination strategy**: The spec uses cursor-based "Load more" (append-on-demand). If the
   product requirement is infinite scroll, `useInfiniteQuery` should replace `useQuery` and
   an `IntersectionObserver` trigger should be added. This change is backward-compatible with
   the backend cursor API.

6. **Mobile nav**: `frontend/src/components/layout/MobileNav.tsx` exists and has its own
   independent nav items list (`MobileNav.tsx:67-99`). Unlike `Sidebar.tsx`, the mobile nav
   does NOT include a "Contacts" item and has no feature-flag filter comparable to
   `Sidebar.tsx:307-329`. Adding a Party/CRM entry to MobileNav is therefore a distinct
   implementation step, not a side-effect of the Sidebar change — it must be explicitly added
   with its own `isPartyCrmEnabled()` guard. This spec defers that to PTY-015 if tests reveal
   a gap, but the implementer should assume it requires a code touch to MobileNav.

7. **POSTAL mech address sub-form**: The spec notes that POSTAL mechs require a full address
   shape. Rather than building a full address form inline, PTY-014 may render a multi-field
   sub-section (line1, line2, city, state, postal_code, country). The exact field set should
   match `normalize_address_payload`'s expected keys in `app/services/addresses.py:39`.
