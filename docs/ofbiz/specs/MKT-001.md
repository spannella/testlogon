# MKT-001 — Marketing module scoping spike & data-model delta

## 1. Summary & Goal

MKT-001 is a scoping spike whose output is this written design note. It maps every relevant OFBiz Marketing entity onto the testlogon codebase, decides what is in scope for the MVP marketing-campaigns module, and produces the authoritative data-model delta (DynamoDB tables, Pydantic models, settings keys, feature flag) that every downstream MKT ticket (MKT-002 through MKT-015) must reference rather than re-derive.

No code is written in this ticket. The deliverable is a decision record that resolves four questions:

1. Which OFBiz entities map to existing testlogon primitives, and which require new tables?
2. What is the additive surface (marketing campaign as umbrella, contact list, party segment, tracking code)?
3. What deterministic-id scheme keeps every new write path idempotent?
4. How is the GL/billing layer kept untouched — marketing spend attribution reads ledger rows, never writes money?

## 3. Data Model

All four tables use the same PK/SK composite key format as `AdCampaigns` and `PromoCodes`. Numeric GSI sort keys are declared with `attr_types={"<key>": "N"}` following the pattern at `scripts/local-ddb-init.py:1112` <!-- AdAccounts attr_types, verified --> and `1123` <!-- AdCampaigns attr_types, verified -->.

### Table: MarketingCampaigns

Stores the umbrella marketing campaign rows and their linkage metadata.

| Attribute | Type | Notes |
|-----------|------|-------|
| `pk` | S | `OWNER#{owner_id}` |
| `sk` | S | `MKTCAMP#{campaign_id}` for the META row |
| `campaign_id` | S | 24-char hex prefix of `sha256(owner_id\|name\|created_bucket)` |
| `owner_id` | S | user_sub of the creator |
| `name` | S | display name |
| `objective` | S | `awareness \| traffic \| conversions` |
| `status` | S | state machine literal (see Section 4) |
| `ad_campaign_id` | S | optional reference to `AdCampaigns` row |
| `promo_code_ids` | L | list of promo code ids (references, not owned) |
| `contact_list_ids` | L | list of `ContactLists` list_ids |
| `segment_ids` | L | list of `PartySegments` segment_ids |
| `tracking_code` | S | slug of the primary `TrackingCodes` row |
| `budget_cents` | N | total campaign budget in cents |
| `start_date` | N | Unix timestamp (optional) |
| `end_date` | N | Unix timestamp (optional) |
| `created_at` | N | Unix timestamp (numeric — requires `attr_types`) |
| `updated_at` | N | Unix timestamp |

**GSIs:**

- `ByOwnerCreatedAt`: PK=`owner_id` (S), SK=`created_at` (N) — paginated list for the owner dashboard.
- `ByStatusCreatedAt`: PK=`status` (S), SK=`created_at` (N) — admin campaign queue.

`attr_types={"created_at": "N"}` required.

### Table: ContactLists

Stores both list META rows and per-member rows in a single table (single-table pattern).

| Row type | PK | SK |
|----------|----|----|
| List META | `OWNER#{owner_id}` | `LIST#{list_id}` |
| Member | `LIST#{list_id}` | `PARTY#{party_id}` |

Attributes on META row: `list_id`, `owner_id`, `name`, `description`, `member_count` (denormalized), `created_at` (N), `updated_at` (N).

Attributes on member row: `list_id`, `party_id`, `joined_at` (N), `suppressed` (BOOL — true when `is_user_opted_out` returns true at join time).

**GSIs:**

- `ByOwnerCreatedAt`: PK=`owner_id` (S), SK=`created_at` (N) — on META rows only.
- `ByListJoinedAt`: PK=`list_id` (S), SK=`joined_at` (N) — on member rows; pagination for send resolution.

`attr_types={"created_at": "N", "joined_at": "N"}` required.

Default table name: `ContactLists` (env `DDB_CONTACT_LISTS`).

### Table: PartySegments

Stores segment META and snapshot-membership rows.

| Row type | PK | SK |
|----------|----|----|
| Segment META | `OWNER#{owner_id}` | `SEGMENT#{segment_id}` |
| Snapshot member | `SEGMENT#{segment_id}` | `SNAP#{snap_ts:010d}#{party_id}` |

Attributes on META: `segment_id`, `owner_id`, `name`, `predicates` (L of `{attribute, operator, value}` maps), `created_at` (N), `updated_at` (N).

Attributes on snapshot-member: `segment_id`, `snap_ts` (N), `party_id`, `suppressed` (BOOL).

**GSIs:**

- `ByOwnerCreatedAt`: PK=`owner_id` (S), SK=`created_at` (N) — segment listing.
- `BySegmentSnapTs`: PK=`segment_id` (S), SK=`snap_ts` (N) — latest snapshot resolution.

`attr_types={"created_at": "N", "snap_ts": "N"}` required.

Default table name: `PartySegments` (env `DDB_PARTY_SEGMENTS`).

### Table: TrackingCodes

Stores tracking-code slugs and their visit/order attribution rows (single-table).

| Row type | PK | SK |
|----------|----|----|
| Code META | `TRACK#{code_slug}` | `META` |
| Visit | `TRACK#{code_slug}` | `VISIT#{ts:010d}#{nonce}` |
| Order | `TRACK#{code_slug}` | `ORDER#{order_id}` |

Attributes on META: `code_slug`, `campaign_id`, `owner_id`, `created_at` (N), `visit_count` (N, denormalized), `order_count` (N, denormalized).

Attributes on VISIT: `ts` (N), `party_id` (S, optional — anonymous visits have `"anon"`), `referrer` (S, optional).

Attributes on ORDER: `order_id`, `attributed_at` (N), `campaign_id`.

**GSIs:**

- `ByCampaignCreatedAt`: PK=`campaign_id` (S), SK=`created_at` (N) — all codes for a campaign.
- `ByCodeTs`: PK=`code_slug` (S), SK=`ts` (N) — time-ordered visit/order scan.

`attr_types={"created_at": "N", "ts": "N"}` required.

Default table name: `TrackingCodes` (env `DDB_TRACKING_CODES`).

## 5. Detailed Behavior & Edge Cases

### OFBiz entity mapping and in/out decisions

| OFBiz Entity | testlogon Mapping | Decision |
|-------------|-------------------|----------|
| `MarketingCampaign` | New `MarketingCampaigns` table, umbrella row | **IN** |
| `ContactList` | New `ContactLists` table, static membership | **IN** |
| `ContactListParty` | Member rows in `ContactLists` table | **IN** |
| `SegmentGroup` | New `PartySegments` table, rule-based | **IN** |
| `SegmentGroupClassification` | Predicate set serialized as JSON in META row | **IN** (simplified — no separate classification rows) |
| `TrackingCode` | New `TrackingCodes` table, META row | **IN** |
| `TrackingCodeVisit` | VISIT child rows in `TrackingCodes` | **IN** |
| `TrackingCodeOrder` | ORDER child rows in `TrackingCodes` | **IN** |
| `MarketingCampaignNote` | Not built — no note model exists for the ads campaign either | **DEFERRED** |
| `CampaignRole` / party-role wiring | OFBiz party-role system has no analog in testlogon RBAC | **DEFERRED** |
| `MarketingCampaignPrice` / dynamic discount rules | Covered by existing promo codes — no new discount engine | **OUT (use promo_codes)** |
| `MarketingCampaignPromoCode` (join entity) | Represented as `promo_code_ids: list[str]` on the campaign row | **IN (denormalized)** |

### Deterministic campaign ID

```
created_bucket = now_ts() // 3600          # collapses retries within one hour
seed = f"{owner_id}|{name}|{created_bucket}".encode("utf-8")
campaign_id = "mktcamp_" + hashlib.sha256(seed).hexdigest()[:24]
```

A second `create_campaign` call with the same `owner_id` and `name` within the same hour window produces the same `campaign_id`. The `put_item` uses `ConditionExpression="attribute_not_exists(pk)"`. If the condition fails (`ConditionalCheckFailedException`), the service re-fetches and returns the existing item — identical to the pattern at `app/services/mass_message_campaigns.py:130–134`.

### State machine for marketing campaigns

```
draft → scheduled → active → paused → active (re-activate)
active → completed
active / paused / scheduled → archived
archived → (terminal)
```

Transition to `active` validates: (a) any linked promo codes exist and have `active=True`, (b) if `end_date` is set it must be in the future, (c) if `start_date` is set it must not be in the past by more than one hour. Failed validation raises `HTTP 422`; no state change is written.

On any successful transition, `app/services/alerts.audit_event` (line 644 of `app/services/alerts.py` <!-- verified -->) is called with `event="marketing_campaign.transition"`.

### Opt-out signal

`cart_reminders.is_user_opted_out(party_id)` from `app/services/cart_reminders.py:95` <!-- verified --> is the shared do-not-contact gate. It reads the `cart_reminder_config` table key `OPTOUT#USER#{sub}` / `META` <!-- verified: app/services/cart_reminders.py:37,98-99 -->. Contact-list member addition marks `suppressed=True` when this returns `True`. `list_members` for send resolution always filters `suppressed=True` entries from the output unless `include_suppressed=True` is passed.

### Tracking code visit endpoint

`GET /ui/marketing/t/{code_slug}` is declared **before** any `/{campaign_id}` dynamic route in the router to avoid FastAPI capturing the literal `t` as a campaign_id. It calls `record_visit` (appending the VISIT row), then returns `RedirectResponse(url=S.public_base_url + "/", status_code=302)`. When a `redirect_to` query parameter is present and its value begins with `S.public_base_url`, the redirect goes there instead (open-redirect guard).

### Attribution read path

`compute_attribution` never queries the billing table directly. It:

1. Reads `ad_campaigns.get_campaign(account_id, ad_campaign_id)["lifetime_spent_cents"]` if `ad_campaign_id` is set.
2. For each `promo_code_id`, calls `promo_codes.get_promo_stats(code_id)` and sums `total_discount_cents` and `total_redemptions` — read-only, no writes to ledger.
3. Counts VISIT and ORDER child rows under each of the campaign's tracking codes via `T.tracking_codes.query(KeyConditionExpression=Key("pk").eq(f"TRACK#{slug}"))`.

The returned `CampaignAttributionOut.ad_spend_cents` matches `ads.lifetime_spent_cents` exactly (cents-for-cents parity requirement from MKT-001 acceptance criteria).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity**: all four service files use `T.<table>` from `app/core/tables.py` without any `if S.dev_mode` branching — moto in-process (dev) and real DynamoDB (prod) exercise the same code path. No mock-only routes are introduced. Visit recording (`record_visit`) is synchronous — no background worker divergence.

**Idempotency**:

- `create_campaign`: `attribute_not_exists(pk)` conditional put + sha256 deterministic id.
- `add_member`: `attribute_not_exists(sk)` conditional put (no-op on duplicate).
- `snapshot_segment`: each snapshot writes a new `SNAP#{snap_ts}#...` prefix; prior snapshots are immutable (reads by exact `snap_ts` are stable forever).
- `record_order`: `attribute_not_exists(sk)` on `ORDER#{order_id}` row prevents double-counting.
- `create_tracking_code`: `attribute_not_exists(pk)` on `TRACK#{code_slug}#META`; slug collision returns HTTP 409 (not idempotent — different campaign could claim the same slug).

**Security**:

- Owner isolation: all service functions accept `owner_id` and construct `PK=OWNER#{owner_id}` queries. Foreign-owner access returns `HTTP 404` (not 403) to avoid information leakage. Note: the existing `app/routers/ads.py:83` raises HTTP 403 for campaign ownership mismatch — the marketing module intentionally diverges here and returns 404 uniformly (the service layer at `app/services/ad_campaigns.py:66–70` returns `None` and the router raises 404).
- Tracking-code visit endpoint: no authentication required (public), but the redirect target is validated against `S.public_base_url` to prevent open-redirect.
- Budget cents are non-negative integers; zero-budget campaigns are allowed (awareness campaigns with no spend cap). No money-out path exists in this module.
- Segment evaluation reads subscription, profile, and ledger tables but never writes them. Predicate attribute names and operators are validated against explicit allowlists (`VALID_SEGMENT_ATTRIBUTES`, `VALID_OPERATORS`) — unknown values raise `HTTP 422`.

## 10. Open Questions / Assumptions

1. **Assumption**: `owner_id` for a marketing campaign is always a `user_sub` (not an `account_id` as used by the ads module). This keeps the marketing module independent of the ad-account hierarchy. If a user needs to manage campaigns from an ads account, a `source_account_id` field can be added additively.

2. **Assumption**: The opt-out signal from `cart_reminders.is_user_opted_out` is sufficient as the sole do-not-contact gate. If a separate marketing-specific opt-out is needed (e.g., "unsubscribe from marketing emails only"), it would require a new preference row — recorded here as a deferred follow-up.

3. **Open question**: Should `MarketingCampaigns` be a separate DDB table from `AdCampaigns`, or should it be a new row type in the existing `AdCampaigns` table (using a different SK prefix like `MKTCAMP#` instead of `CAMPAIGN#`)? This spec assumes a separate table for isolation. If co-location is preferred, MKT-002 must be updated.

4. **Assumption**: Visit recording in `record_visit` is synchronous (inline DDB write). For high-traffic tracking URLs this may add latency. Async fire-and-forget (similar to `_audit()` in `app/services/ssh_key_manager.py`) is an acceptable follow-up optimization but is not required for MVP.

5. **Open question**: The `send_campaign` function (MKT-009) re-uses `write_alert` + `send_alert_email`. If campaign sends should also be recorded as ledger-style audit rows (for campaign-send audit trail), where do those rows live? Proposed: a send-log row in `MarketingCampaigns` table with SK `SEND#{snap_ts}#{party_id}`, no separate table. Needs confirmation before MKT-009 implementation.

6. **Assumption**: Segment evaluation (`evaluate_segment`) does a full scan over the `users` table filtered by predicates. This is acceptable for MVP (dev + small prod). Large-scale evaluation needs a GSI-backed approach; recorded as a performance follow-up.

7. **Open question**: `MarketingCampaignNote` and `CampaignRole` are explicitly deferred. Are there any other OFBiz Marketing entities (`DataSource`, `MarketingCampaignCost`, `SegmentGroupGeo`) that stakeholders consider P0?

8. **Assumption**: The `tracking_code` field on a marketing campaign stores a single primary slug. A campaign may have multiple tracking codes (e.g., per-channel), each queried via the `ByCampaignCreatedAt` GSI on `TrackingCodes`. The single `tracking_code` field is the "default" code embedded in campaign send links.
