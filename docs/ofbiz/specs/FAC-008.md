# FAC-008 — Picklist generation & pick confirmation

## 1. Summary & Goal

FAC-008 delivers `app/services/picking.py`, the pick-work engine of the OFBiz Facility application. Its responsibility is to bridge a commerce order that is ready to fulfill to the physical warehouse: generate a structured picklist from the order's line items, allow warehouse workers to confirm each line as physically collected, and — when every line is confirmed — commit the underlying soft reservations to reduce on-hand inventory exactly once.

Concretely the ticket ships:

1. **`generate_picklist(order_id, facility_id, *, user_sub)`** — reads the order header and all line items from `T.orders`/`T.order_items`, for each line resolves or creates a soft reservation on the relevant inventory location, and writes a picklist header (`META` row) plus one `LINE#{n}` row per order line to `T.picklists`.
2. **`confirm_pick(picklist_id, line_no, picked_qty, *, user_sub)`** — marks a single `LINE#{n}` row as `picked` (with `line_status = "picked"` or `"short"` on under-pick) using the `_close_reservation`-style conditional-status guard from `app/services/inventory.py:434–453` so confirming a line twice is a no-op.
3. **Full-pick completion** — when all lines reach a terminal pick status (`picked` or `short`), the picklist header transitions from `in_pick` to `picked` and each line's `reservation_id` is committed via `inventory.commit_reservation(...)` (or, when no reservation exists, an `inventory.adjust(sku, -qty, reason="pick")` is issued as fallback). The commit block runs exactly once under the same conditional idempotency guard.
4. **Short/backorder handling** — lines where `picked_qty < quantity` surface as `short` rather than silently overdrawing stock; `available` stock is released back when a reservation is cancelled on short-pick.
5. **Audit trail** — every state transition emits `alerts.audit_event` via the best-effort `_audit()` wrapper (copied verbatim from `app/services/inventory.py:92–98`).

Everything is **additive and flag-gated** behind `S.facility_fulfillment_enabled` (default `False`). With the flag off, `app/services/picking.py` is dormant and all existing shop, cart, order, billing, inventory, reservation, and returns code paths are byte-for-byte unchanged.

### Inventory service (the foundation FAC-008 calls into)

`app/services/inventory.py` establishes every primitive this ticket reuses:

## 3. Data Model

FAC-008 writes to `T.picklists` (defined by FAC-002) and reads from `T.orders`, `T.order_items`, and `T.reservations`. No new tables are introduced by this ticket.

### 3.1 Table: `picklists` (wired by FAC-002, extended by FAC-008)

**Primary key**: `picklist_id` (S, hash) / `sk` (S, range)

**GSIs** (defined by FAC-002):

| Index | Hash key | Range key | `attr_types` note |
|---|---|---|---|
| `GSI_ORDER` | `order_id` (S) | `created_at` (N) | `"N"` — integer Unix timestamp; already declared in FAC-002 `TableDef` |
| `GSI_STATUS` | `status` (S) | `created_at` (N) | `"N"` — same |

**No new tables or GSIs** are added by FAC-008; the `TableDef` in `scripts/local-ddb-init.py` is owned by FAC-002 and is not touched here.

### 3.2 Picklist header row (`sk = "META"`)

| Attribute | DDB type | Notes |
|---|---|---|
| `picklist_id` | S | PK. `uuid4().hex` — one per `generate_picklist` call. Non-deterministic because one order may have multiple picklist generations (e.g., after a partial cancel). |
| `sk` | S | Literal `"META"` |
| `order_id` | S | Commerce order — GSI_ORDER PK. Keyed identically to `T.orders` PK and `T.order_items` PK (`app/services/commerce_order_service.py:73`, `:90`). |
| `facility_id` | S | Warehouse where the pick is performed. Supplied by the caller; must be an active facility record (FAC-004). |
| `status` | S | `open` → `in_pick` → `picked` / `cancelled`. GSI_STATUS PK. `open` on creation; `in_pick` on first `confirm_pick`; `picked` when all lines reach a terminal pick status; `cancelled` via explicit cancel. |
| `created_by` | S | `user_sub` of the actor who generated the picklist. |
| `line_count` | N | Number of `LINE#{n}` child rows; used by the full-pick-detection loop. |
| `created_at` | N | Immutable integer Unix timestamp (`now_ts()`). GSI_ORDER and GSI_STATUS sort key. |
| `updated_at` | N | Updated on every header mutation. |

### 3.3 Picklist line row (`sk = "LINE#{n}"`)

`n` is the 1-based integer `item_id` from `T.order_items`. For `item_id = "3"`, the SK is `"LINE#3"`.

| Attribute | DDB type | Notes |
|---|---|---|
| `picklist_id` | S | PK — same as header |
| `sk` | S | `"LINE#{n}"` |
| `order_line_id` | S | The source `item_id` from `T.order_items` (e.g. `"1"`, `"2"`). Enables cross-reference back to the order. |
| `sku` | S | Stock-keeping unit. Copied from the `T.order_items` row. |
| `location_id` | S | Bin to pick from. Resolved by `_resolve_pick_location(facility_id, sku)` — see §5. |
| `quantity` | N | Qty to pick. Copied from `T.order_items.quantity`. |
| `picked_qty` | N | Qty confirmed by `confirm_pick`. `0` until confirmed. Updated in-place by `confirm_pick`. |
| `reservation_id` | S | Optional. The `reservation_id` from `inventory.reserve(...)` issued during `generate_picklist`. Empty string `""` when no reservation was created (inventory flag off or `reserve` not called for this line). |
| `line_status` | S | `open` / `picked` / `short` / `cancelled`. |
| `created_at` | N | Same timestamp as the header. |

### 3.4 Access patterns

| Query | Mechanism |
|---|---|
| Fetch a picklist (header + lines) | `T.picklists.query(KeyConditionExpression=Key("picklist_id").eq(pid))` — returns META + all LINE rows |
| All picklists for an order | `GSI_ORDER` query: `Key={"order_id": oid}`, `ScanIndexForward=False` |
| Warehouse work queue by status | `GSI_STATUS` query: `Key={"status": "open"}`, `ScanIndexForward=False` with optional filter on `facility_id` |
| Fetch order line items | `T.order_items.query(KeyConditionExpression=Key("order_id").eq(oid))` — all lines in one call |

**Projection note**: LINE rows carry `picklist_id` and `sk` but not `order_id`, `facility_id`, or `status`. GSI queries therefore project only META rows. This is the same single-table fan-out pattern used in `app/services/returns_rma.py:293`.

### 4.3 `generate_picklist(order_id, facility_id, *, user_sub) -> Dict`

**Signature:**

```python
def generate_picklist(
    order_id: str,
    facility_id: str,
    *,
    user_sub: str = "system",
    location_id: Optional[str] = None,   # override: use this location for all lines
) -> Dict[str, Any]:
```

**Steps:**

1. `_require_enabled()`
2. Verify the order exists: `T.orders.get_item(Key={"order_id": order_id})` — raise `HTTPException(404)` if missing.
3. Query all order lines: `T.order_items.query(KeyConditionExpression=Key("order_id").eq(order_id))` — raise `HTTPException(422, "Order has no line items")` if empty.
4. Determine pick location per line: `_resolve_pick_location(facility_id, sku, override=location_id)` (see §5.1).
5. For each line, if `S.inventory_reservations_enabled` is `True`, call `inventory.reserve(sku, quantity, location_id=resolved_location, user_sub=user_sub, cart_id=f"picklist:{order_id}")`. If `reserve` raises `HTTPException(409)` (out of stock), record the line with `line_status="short"` and `reservation_id=""` rather than aborting the whole picklist — this surfaces a backorder state.
6. Assign `picklist_id = uuid.uuid4().hex`.
7. Write all `LINE#{n}` rows first (ensures line rows exist before the header is visible to queries), then write the `META` header with `status="open"`.
8. Emit `_audit("picking.generated", user_sub, picklist_id=picklist_id, order_id=order_id, facility_id=facility_id, line_count=N)`.
9. Return `_picklist_out(picklist_id)`.

**Atomicity note:** DynamoDB does not offer multi-item transactions in the basic API. Lines are written sequentially; the header is written last. If the process crashes between line writes, the partial state is cleaned up on the next call to `generate_picklist` for the same order (which checks `GSI_ORDER` for an existing `open` picklist and returns it rather than creating a duplicate). A future FAC enhancement may use `TransactWriteItems` but that is out of scope here.

### 4.4 `confirm_pick(picklist_id, line_no, picked_qty, *, user_sub) -> Dict`

**Signature:**

```python
def confirm_pick(
    picklist_id: str,
    line_no: int,              # 1-based; "LINE#{line_no}"
    picked_qty: int,
    *,
    user_sub: str = "system",
) -> Dict[str, Any]:
```

**Steps:**

1. `_require_enabled()`
2. Fetch the header (`META`) and the specific line (`LINE#{line_no}`): `T.picklists.query(KeyConditionExpression=Key("picklist_id").eq(picklist_id) & Key("sk").begins_with(""))` — or two targeted `get_item` calls.
3. Raise `HTTPException(404)` if the picklist or line is missing.
4. Raise `HTTPException(409, "Picklist is not open for picking")` if `header.status` is `picked`, `packed`, or `cancelled`.
5. Raise `HTTPException(422)` if `picked_qty < 0` or `picked_qty > line.quantity`.
6. **Idempotency guard on the line**: attempt `_confirm_line(picklist_id, line_no, picked_qty)`:

```python
def _confirm_line(picklist_id: str, line_no: int, picked_qty: int) -> Optional[Dict]:
    new_status = "picked" if picked_qty >= line.quantity else "short"
    try:
        resp = T.picklists.update_item(
            Key={"picklist_id": picklist_id, "sk": f"LINE#{line_no}"},
            UpdateExpression="SET picked_qty = :pq, line_status = :ls",
            ConditionExpression="line_status = :open",
            ExpressionAttributeValues={":pq": picked_qty, ":ls": new_status, ":open": "open"},
            ReturnValues="ALL_OLD",
        )
        return resp.get("Attributes")
    except ClientError as exc:
        if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
            return None  # already confirmed — no-op
        raise
```

7. If `_confirm_line` returns `None` (already confirmed): return current picklist state unchanged (idempotent no-op).
8. **Short-pick reservation release**: if the old line had a `reservation_id` and `new_status == "short"` and `S.inventory_reservations_enabled`:
   - Call `inventory.release_reservation(reservation_id, reason="short_pick", user_sub=user_sub)` to return unfulfilled qty to available stock.
   - Set `reservation_id = ""` on the line (via a second `update_item` — no condition needed).
9. **Header transition to `in_pick`**: if the header is still `open`, flip it to `in_pick` using `_transition_header(picklist_id, "open", "in_pick")`. If the header is already `in_pick` this is a no-op.
10. **Check full-pick completion**: call `_check_all_lines_terminal(picklist_id)` — queries all `LINE#*` rows and returns `True` if every line has `line_status` in `{"picked", "short", "cancelled"}`.
11. If all lines are terminal: call `_finalize_picklist(picklist_id, user_sub=user_sub)` (see §4.5).
12. Emit `_audit("picking.line_confirmed", user_sub, picklist_id=picklist_id, line_no=line_no, picked_qty=picked_qty, new_status=new_status)`.
13. Return `_picklist_out(picklist_id)`.

### 4.5 `_finalize_picklist(picklist_id, *, user_sub)` (internal)

Called only by `confirm_pick` when all lines are terminal. Performs the header `in_pick → picked` transition with a reservation-commit block that runs exactly once.

```python
def _finalize_picklist(picklist_id: str, *, user_sub: str) -> None:
    old = _transition_header(picklist_id, "in_pick", "picked",
                             extra_set={"picked_at": now_ts()})
    if old is None:
        return  # already picked — idempotent no-op
    # Commit reservations exactly once (old.status was "in_pick").
    lines = _get_lines(picklist_id)
    if bool(getattr(S, "inventory_reservations_enabled", False)):
        try:
            from app.services import inventory as inv
            for ln in lines:
                res_id = ln.get("reservation_id") or ""
                sku = ln.get("sku")
                qty = int(ln.get("picked_qty") or 0)
                ls = ln.get("line_status")
                if ls == "picked" and res_id:
                    inv.commit_reservation(res_id, user_sub=user_sub)
                elif ls == "picked" and not res_id and sku and qty > 0:
                    # No reservation (flag was off at generate time or direct sale).
                    inv.adjust(sku, -qty, reason="pick", user_sub=user_sub)
                # "short" lines: reservation already released in confirm_pick step 8.
                # "cancelled" lines: released in cancel_picklist.
        except Exception:
            # Inventory failure must not block the header transition.
            pass
    _audit("picking.picked", user_sub, picklist_id=picklist_id, order_id=old.get("order_id"))
```

`_transition_header(picklist_id, from_status, to_status, *, extra_set=None)` replicates the `_transition` pattern from `app/services/returns_rma.py:319–354` applied to `T.picklists` with `Key={"picklist_id": picklist_id, "sk": "META"}`.

### 4.8 `cancel_picklist(picklist_id, *, user_sub) -> Dict`

```python
def cancel_picklist(picklist_id: str, *, user_sub: str = "system") -> Dict[str, Any]:
    _require_enabled()
    old = _transition_header(picklist_id, "open", "cancelled")
    if old is None:
        old = _transition_header(picklist_id, "in_pick", "cancelled")
    if old is None:
        return _picklist_out(picklist_id)  # already terminal — no-op
    # Release all active reservations.
    lines = _get_lines(picklist_id)
    if bool(getattr(S, "inventory_reservations_enabled", False)):
        try:
            from app.services import inventory as inv
            for ln in lines:
                res_id = ln.get("reservation_id") or ""
                if res_id and ln.get("line_status") == "open":
                    inv.release_reservation(res_id, reason="picklist_cancelled", user_sub=user_sub)
        except Exception:
            pass
    _audit("picking.cancelled", user_sub, picklist_id=picklist_id)
    return _picklist_out(picklist_id)
```

## 5. Detailed Behavior & Edge Cases

### 5.1 `_resolve_pick_location(facility_id, sku, *, override)`

Returns the `location_id` string to use for a pick line. Priority:

1. If `override` is non-empty, use it directly (caller-supplied blanket override for the whole picklist).
2. Query `T.inventory` (via `inventory.get_inventory(sku, location_id=<each location at facility>)`) for the location within the facility that has the highest `available` qty. In practice, this is simplified to: look up the facility's default location from `T.facilities` (`facility_id` / `LOC#default`), fall back to `DEFAULT_LOCATION = "warehouse"` if no facility record is found.
3. Return the resolved `location_id` string. This is the same value passed to `inventory.reserve(...)` and stored on the `LINE#{n}` row.

**Implementation note**: a full bin-level slot allocation algorithm is a stretch goal for FAC-014. For FAC-008, a single location per facility (the default or override) is sufficient to pass acceptance criteria.

### 5.2 Duplicate picklist prevention

`generate_picklist` queries `GSI_ORDER` for existing picklists with `order_id = order_id` before writing. If an `open` or `in_pick` picklist already exists, it is returned without creating a second one (idempotent). If a `picked` or `packed` picklist exists, `HTTPException(409, "Order already has a completed picklist")` is raised. This guards against duplicate API calls without requiring a deterministic `picklist_id` (non-deterministic UUIDs are appropriate here because multiple picklists per order — e.g., for re-shipment after a partial cancel — is a valid future use case).

### 5.3 Partial (short) pick and backorder

When `picked_qty < line.quantity`:
- `line_status` is set to `"short"`.
- If a `reservation_id` exists, `inventory.release_reservation(reservation_id, reason="short_pick")` is called immediately to return the unfulfilled units to available stock. This prevents stock from being locked in a reservation for units the warehouse cannot physically fulfill.
- The picklist can still transition to `picked` (all lines terminal) with some `short` lines; downstream FAC-009 (pack) must reconcile picked vs. requested quantities.

### 5.4 Insufficient stock at `generate_picklist` time (out-of-stock line)

When `inventory.reserve(...)` raises `HTTPException(409)` for a line, the service writes the line with `reservation_id=""` and `line_status="short"`. It does **not** abort the entire picklist. This surfaces a backorder state: the warehouse knows immediately which lines have no stock allocated. Callers may choose to cancel and re-generate once stock is replenished, or proceed to pack with the available lines.

### 5.5 Inventory flag off — no-reservation fallback

When `S.inventory_reservations_enabled` is `False`:
- `generate_picklist` skips all `inventory.reserve(...)` calls; `reservation_id = ""` on every line.
- `confirm_pick` skips `release_reservation` on short lines.
- `_finalize_picklist` uses `inventory.adjust(sku, -qty, reason="pick")` for `status="picked"` lines instead of `commit_reservation`. If `adjust` raises `409` (would go negative), it is swallowed and the picklist still flips to `picked` — the caller must reconcile stock manually. This mirrors the RMA restock guard at `app/services/returns_rma.py:423–435`.

### 5.6 Confirm replay (idempotency)

If `confirm_pick(picklist_id, line_no, picked_qty)` is called a second time with the same arguments:
- `_confirm_line` returns `None` because `line_status != "open"` (already `"picked"` or `"short"`).
- The function returns the current picklist state without touching inventory or emitting a duplicate audit event.
- If called with a **different** `picked_qty` on an already-confirmed line, the same no-op applies (the condition guards on `line_status = "open"` only). If the business requires re-confirmation with a corrected quantity, the line must first be explicitly reopened — this is a future FAC enhancement and out of scope for FAC-008.

### 5.7 `_finalize_picklist` called twice (full-pick replay)

`_transition_header(picklist_id, "in_pick", "picked")` conditions on `status = "in_pick"`. A second call returns `None`, and the entire commit block is skipped. This is the single-writer idempotency guarantee for the inventory decrement.

### 5.8 Cancel while lines are in `picked` status

`cancel_picklist` transitions from `open` or `in_pick` only. A picklist that has already reached `picked` cannot be cancelled via this function (the function's two `_transition_header` calls both return `None`); the current state is returned as a no-op. Post-`picked` cancellation (e.g., for a customer order cancel after picking) is the responsibility of FAC-010 (ship cancellation) which calls `inventory.release_reservation` on committed lines.

### 5.9 Race between concurrent `confirm_pick` calls

Two concurrent calls to `confirm_pick` for the same line will race on `_confirm_line`. Only one wins the `ConditionalCheckFailedException`-guarded update; the loser returns `None` (idempotent no-op). Both calls then inspect line completion. Only one call will win the `_transition_header("in_pick", "picked")` guard if all lines are terminal; the other will get `None` and return the already-`picked` picklist. No duplicate inventory operations occur.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

`app/services/picking.py` contains zero `S.dev_mode` branches. All DynamoDB operations (`put_item`, `update_item`, `query`, `get_item`) run against the same DDB endpoint in dev (DynamoDB Local at port 8001) and in prod (DynamoDB AWS). The inventory calls (`reserve`, `commit_reservation`, `adjust`) are similarly uniform — no mock path exists in `inventory.py` beyond the `S.inventory_reservations_enabled` flag gate. This is identical to the approach used in `app/services/returns_rma.py` (SECOPS-007 parity).

### Idempotency summary

| Operation | Guard mechanism | Replay outcome |
|---|---|---|
| `generate_picklist` for an already-open order | `GSI_ORDER` pre-check | Returns existing `open` picklist, no new reservations |
| `confirm_pick` for an already-confirmed line | `ConditionExpression="line_status = :open"` | Returns current state, no inventory mutation |
| `_finalize_picklist` (full-pick commit) | `ConditionExpression="status = :in_pick"` | Returns `None`, commit block skipped |
| `commit_reservation` inside finalize | `_close_reservation` conditions on `status = active` | Returns existing record, no double-decrement |
| `cancel_picklist` on already-cancelled | `_transition_header` returns `None` | Returns current state, no inventory mutation |

### Security

- All mutating endpoints (`POST /ui/fulfillment/picklists`, `POST .../confirm`, `DELETE`) require `require_admin_or_root_csrf` (same policy as `app/routers/inventory.py:48`). Warehouse workers are admin-role users.
- `picklist_id` is a `uuid4().hex` — 32 hex characters, unguessable. Order enumeration via `GSI_ORDER` is restricted to admin role.
- Reservation `cart_id` is set to `f"picklist:{order_id}"` to distinguish picklist-driven reservations from cart-driven reservations in audit logs.
- Audit events (`picking.generated`, `picking.line_confirmed`, `picking.picked`, `picking.cancelled`) are emitted best-effort via `_audit()` to `T.alerts`, the same table used by all other OFBiz modules.

## 8. Backward Compatibility & Migration

### Flag-off guarantee

With `FACILITY_FULFILLMENT_ENABLED=false` (the default):
- `app/services/picking.py` is importable but all public functions raise `HTTPException(404)` immediately.

### Forward compatibility

- The `LINE#{n}` sort key uses the same `item_id` as `T.order_items`. This 1:1 mapping is stable; future FAC-013+ lot/serial tracking can add a `lot_id` attribute to each line row without changing the key schema.

- The `shipment_id` attribute on the header `META` row (defined in FAC-002's data model) is not written by FAC-008; it is written by FAC-009 when the picklist is packed.

## 10. Open Questions / Assumptions

1. **Assumption**: FAC-002, FAC-003, FAC-004, FAC-006, and FAC-007 are complete and merged before FAC-008 is implemented. Specifically: `T.picklists`, `T.orders`, `T.order_items`, and `T.reservations` are all wired in `app/core/tables.py`; `S.facility_fulfillment_enabled` and `S.picklists_table_name` exist in `app/core/settings.py`; `PicklistOut`, `PickLineOut`, `PicklistGenerateIn`, and `PickConfirmIn` are defined in `app/models.py`.

2. **Assumption**: `T.orders` PK is a bare `order_id` string (no prefix), as confirmed by `app/services/commerce_order_service.py:73` and `scripts/local-ddb-init.py:288–294`. The `get_item` call in `generate_picklist` uses `Key={"order_id": order_id}` with no sort key.

3. **Assumption**: `T.order_items` SK is `item_id` which is a 1-based integer string (`"1"`, `"2"`, …), confirmed at `app/services/commerce_order_service.py:88–91`. The `LINE#{n}` SK on picklist rows uses the same integer (e.g., `"LINE#1"` for `item_id="1"`). Alphabetic sort of `LINE#*` keys may not match numeric sort on large orders (e.g., `LINE#10` sorts before `LINE#2`). To guarantee correct numeric ordering, the service returns lines sorted by `int(sk.split("#")[1])` after the `query` response.

4. **Open question**: Should `generate_picklist` be idempotent via a deterministic `picklist_id = sha256(order_id|facility_id)` (as used in `commerce_order_service.py:67`) or should it allow multiple picklists per order? This spec assumes a `GSI_ORDER` pre-check for an existing `open`/`in_pick` picklist as the idempotency gate, with `uuid4()` picklist IDs to permit future re-generation. If strict single-picklist-per-order semantics are required, the deterministic-ID pattern should be used instead.

5. **Open question**: What is the precise set of order `status` values that are eligible for picklist generation? This spec does not check order status (any order can have a picklist generated). A stricter design would reject picklist generation if `order.status` is not `"processing"` or equivalent. The order lifecycle state machine is owned by the ORD module and is out of scope here.

6. **Assumption**: The `_resolve_pick_location` function for FAC-008 uses the facility's default location (i.e., the `LOC#default` row from `T.facilities`, if present, else `DEFAULT_LOCATION = "warehouse"`). A full bin-slotting algorithm that picks the optimal bin per SKU is deferred to FAC-014.

7. **Open question**: Should `confirm_pick` allow `picked_qty = 0` to explicitly mark a line as fully short (zero units available)? This spec accepts `picked_qty >= 0` (`Field(ge=0, ...)`). A `picked_qty = 0` is treated as a 100% short.

8. **Assumption**: The `fulfillment_router` was introduced by FAC-005/006/007 as a shared router in `app/routers/fulfillment.py`. FAC-008 appends to this router rather than creating a new file. If FAC-005–007 each created separate routers, FAC-008 may need to create or extend the appropriate file.
