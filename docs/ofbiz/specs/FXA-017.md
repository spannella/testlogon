# FXA-017 — Hermetic offline unit + E2E tests

## 1. Summary & Goal

FXA-017 is the capstone test milestone for the Fixed Assets module. It delivers four hermetic offline pytest suites and one Playwright E2E spec that together prove correctness of everything FXA-005 through FXA-016 built. No production code changes. No new services. No new endpoints. Pure test coverage.

The four unit suites target the most business-critical invariants:

- **`tests/test_fxa_register.py`** — asset CRUD + idempotent creation.
- **`tests/test_fxa_depreciation.py`** — schedule math, balanced journal posting, idempotent posting (no double-increment), fully-depreciated transition, NBV == salvage floor at end, trial-balance integrity against an in-memory GL.
- **`tests/test_fxa_disposal.py`** — balanced closing journal, gain/loss plug arithmetic, disposal proceeds reuse the `refund_payment` path (no forked billing), disposal idempotency.
- **`tests/test_fxa_work_orders.py`** — lifecycle transitions, illegal-transition 409 rejection, disposed-asset rejection.

The E2E spec (`frontend/e2e/fixed-assets.spec.ts`) exercises the full stack against a running dev environment: register an asset via the admin UI, view the generated depreciation schedule, trigger a manual period post, and create and complete a work order.

A fifth acceptance criterion cuts across all suites: with `FIXED_ASSETS_ENABLED=false`, a regression test asserts the depreciation poster background task never starts and every FXA endpoint returns 503.

### 2.2 Hermetic test isolation pattern (canonical)

Every hermetic offline test in this repo follows the pattern established by `tests/test_gap_0223_0224_ec2_host_inventory.py` and `tests/test_compute_billing_timer_gap0228.py`:

- **moto in-process DynamoDB**: `from moto import mock_aws`; activate with `ExitStack` + `stack.enter_context(mock_aws())` in `setUp`. Create tables in-memory — never connect to real DynamoDB Local on port 8001.
- **Frozen `T` patched via `patch.object`**: the `Tables` dataclass (`app/core/tables.py:68–69`) is frozen. Each test patches the module-level `T` in the service module under test using `patch.object(module, "T", SimpleNamespace(...))` (see `tests/test_gap_0223_0224_ec2_host_inventory.py:94–99`) with the moto-backed in-memory table objects. Do NOT use `object.__setattr__` on `T` — use `patch.object` with `SimpleNamespace` via `ExitStack.enter_context` so cleanup is automatic. <!-- CORRECTED: original text incorrectly said "object.__setattr__" for T patching; the canonical pattern uses patch.object+SimpleNamespace -->
- **Frozen `S` patched via `object.__setattr__`**: `Settings` is also a frozen dataclass (`app/core/settings.py`). Tests flip individual flags with `object.__setattr__(module.S, "fixed_assets_enabled", True)` and restore them in `addCleanup` / `finally`.
- **No FastAPI TestClient**: the TestClient is broken in this environment per the CLAUDE.md notes and confirmed by the pattern across all ~40 hermetic tests. Route-handler coroutines are called directly by driving service functions (or, for async handlers, on a fresh `asyncio.new_event_loop()` per the pattern in `tests/test_gap_0220_0221_ssh_stored_key.py`).
- **`@unittest.skipIf(mock_aws is None, "moto is not installed")`**: guard all test classes so the suite skips cleanly if moto is absent.

### 2.3 In-memory GL for depreciation tests

`tests/test_fxa_depreciation.py` needs a minimal in-memory GL that `post_depreciation_period` (FXA-009) writes journal entries into, so the trial-balance assertion is meaningful. The OFB-014 `gl_posting.post_journal_entry` function and the `gl_journal` DDB table are dependencies of FXA-009 but are not themselves under test here. The approach is:

- Create a moto-backed `gl_journal` table in the test setUp alongside the `fixed_assets` and `fixed_asset_schedule` tables.
- Bind `T.gl_journal` on the patched `T` namespace.
- Call `post_depreciation_period` normally — it drives `gl_posting.post_journal_entry` which writes to the moto-backed `T.gl_journal`.
- After posting, scan the `gl_journal` table and assert Σdebits == Σcredits (balanced) and that no duplicate journal entry rows exist.

This is intentionally a black-box assertion over the GL table content; the test does not reach into `gl_posting.py` internals.

### 2.4 Refund-path reuse assertion in disposal tests

## 3. Data Model

FXA-017 does not modify the data model. It creates in-memory moto replicas of the tables established by FXA-003. The table shapes the tests must replicate are documented in `docs/ofbiz/specs/FXA-003.md` and `FIXED_ASSETS_TICKETS.md:53–57`:

### 3.1 `fixed_assets` table (test replica)

```
PK: pk (S) = "ASSET#{asset_id}"
SK: sk (S) = "META"
GSI GSI_OWNER: pk=owner_sub (S), sk=acquired_at (N)
GSI GSI_STATUS: pk=status (S), sk=acquired_at (N)
attr_types: {"acquired_at": "N"}
```

### 3.2 `fixed_asset_schedule` table (test replica)

```
PK: pk (S) = "ASSET#{asset_id}"
SK: sk (S) = "PERIOD#{period:07d}"
GSI GSI_DUE: pk=schedule_status (S), sk=period_end_ts (N)
attr_types: {"period_end_ts": "N"}
```

### 3.3 `maintenance_orders` table (test replica)

```
PK: pk (S) = "ASSET#{asset_id}"
SK: sk (S) = "WO#{work_order_id}"
GSI GSI_WO_STATUS: pk=wo_status (S), sk=created_at (N)
GSI GSI_WO_ASSIGNEE: pk=assignee_sub (S), sk=created_at (N)
attr_types: {"created_at": "N"}
```

### 3.4 `gl_journal` table (test replica — for depreciation balance assertion)

<!-- CORRECTED: ADR-001 (line 296) uses PK="JE#{journal_id}" / SK="META"|"LINE#{n}", which is also quoted by FXA-009.
     OFB-002 spec (lines 116–129) and OFB-014 spec (lines 114–139) supersede the ADR and define the implemented schema as
     PK="JE#GLOBAL" (constant) / SK="JE#{journal_entry_id}" (header) or "JL#{journal_entry_id}#{seq:04d}" (line).
     FXA-017 unit tests must mirror whichever schema OFB-014 actually implements. The OFB-002/OFB-014 shape is authoritative
     for the implemented table. Both GSI names in OFB-002 are GSI_SOURCE and GSI_DATE. -->

Per OFB-002 (`docs/ofbiz/specs/OFB-002.md:116–129`) and OFB-014 (`docs/ofbiz/specs/OFB-014.md:104–176`):

```
PK: pk (S) = "JE#GLOBAL"                        (constant — single partition)
SK: sk (S) = "JE#{journal_entry_id}"             (header row)
          | "JL#{journal_entry_id}#{seq:04d}"    (line rows, seq=0001,0002,…)
GSI GSI_SOURCE: pk=source_entry_id (S), sk=posted_at (N)   (idempotency lookup)
GSI GSI_DATE:   pk=gl_date (S), sk=posted_at (N)           (date-range queries)
attr_types: {"posted_at": "N"}
```

**RISK**: ADR-001 (line 296) and FXA-009 spec both use the older `PK="JE#{journal_id}"` / `SK="META"|"LINE#{n}"` shape. When OFB-014 lands, the actual `gl_posting.post_journal_entry` implementation will define the canonical schema. FXA-017 tests must be written against whatever OFB-014 emits. The OFB-002/OFB-014 shape shown above is the most recently specced version and is what `local-ddb-init.py` will create.

Note: the `attr_types` declarations are required when creating the tables via the moto `create_table` helper for the same reason they are required in `scripts/local-ddb-init.py` — DynamoDB (including moto's DynamoDB implementation) must know which attributes are numeric so it can range-query them correctly with integer values.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity in the test suite

The service functions under test use the same DDB code path in dev and prod — there are no `if S.dev_mode` branches in `fixed_assets.py` or `asset_maintenance.py` (per `docs/ofbiz/specs/FXA-005.md:14`: "SECOPS-007 parity. Identical code in dev…and prod; no `if S.dev_mode` branch in any business logic function."). The moto in-process DynamoDB is a faithful enough mock for these tests — exactly the same pattern used by `tests/test_gap_0223_0224_ec2_host_inventory.py` (which similarly tests code that runs in both dev and prod without a dev branch).

### 7.2 Idempotency assertions

Three idempotency invariants have explicit test coverage:

1. **Asset creation**: same `correlation_id` → same `asset_id` → `attribute_not_exists(pk)` conditional put fails on retry → existing row returned, no new row written. Test: `test_create_idempotent_same_correlation_id` (count rows via `T.fixed_assets.scan()`).

2. **Depreciation posting**: deterministic `journal_id = sha256(f"{asset_id}:period:{period}")[:32]` + `attribute_not_exists(pk)` on `T.gl_journal` → second post call writes nothing to `T.gl_journal` and does not call `T.fixed_assets.update_item` a second time. Test: `test_posting_idempotent_no_double_increment`.

3. **Disposal**: `ConditionExpression="#status <> :disposed_val"` on the asset `update_item` call fails on a second `dispose_asset` call → raises HTTP 409. Test: `test_disposal_idempotent`.

### 7.3 No forked billing

`test_disposal_with_proceeds_reuses_refund_path` is the critical security/correctness gate: it patches `refund_payment` at the module level (`patch.object(billing_module, "refund_payment", ...)`) and asserts it is called exactly once. A separate assertion (via `T.billing` not being bound in the test namespace, or by asserting `T.billing.put_item.call_count == 0` if bound as a `MagicMock`) confirms no out-of-band `new_ledger_entry` call from within the disposal path.

### 7.4 Balanced GL invariant

`test_post_period_writes_balanced_journal` and `test_trial_balance_stays_balanced_after_posting` both assert Σdebits == Σcredits. An implementation that writes an unbalanced journal (e.g. only the debit leg) will fail these tests before production data can be corrupted.

## 10. Open Questions / Assumptions

1. **`gl_posting.post_journal_entry` interface**: FXA-017 assumes `post_journal_entry` accepts a `journal_id` parameter (deterministic, passed by the caller) and validates Σdr == Σcr before writing. If OFB-014 instead generates journal IDs internally, FXA-009's idempotency mechanism must use a lookup-by-source-id pattern instead of a deterministic-id put. The test setup for `test_posting_idempotent_no_double_increment` must be adjusted accordingly.

2. **`dispose_asset` imports `refund_payment` directly or via module reference**: Assumed `from app.routers.billing import refund_payment` import style. If the actual implementation uses a lazy import or a service-level wrapper, the patch target in `test_fxa_disposal.py` must change.

3. **`T.gl_journal` namespace binding**: The test creates a moto-backed gl_journal table and binds it on the patched `T` namespace for `fixed_assets` module. This assumes `post_depreciation_period` (FXA-009) references `T.gl_journal` through the same `T` import. If `gl_posting.py` has its own `T` import, an additional `patch.object(gl_posting_module, "T", ...)` is needed.

4. **Work-order poster scanning vs. query**: FXA-010's poster loop queries `GSI_DUE` on `T.fixed_asset_schedule`. The `test_poster_loop_posts_due_periods` test must construct a moto table with the GSI pre-populated. If moto's GSI implementation does not support range key conditions on numeric sort keys, the test must fall back to patching the query function directly.

5. **FXA-007 router endpoint name for manual period posting**: The ticket description references posting a period via a router endpoint (Section 71 of E2E). FXA-013 (`docs/ofbiz/specs/FXA-013.md`) or FXA-007 may not expose a `POST /{asset_id}/depreciation/post-period` endpoint explicitly — this may be admin-only from the background poster only. If no HTTP endpoint for manual posting exists, Section 71 must call `post_depreciation_period` via a direct DDB seed + background-poster trigger, or the E2E spec must omit the explicit period-post step and instead assert the schedule shows at least the initial scheduled state.

6. **`charlie_admin` can register assets**: FXA-007 uses `require_admin_or_root_csrf` (defined at `app/auth/policy.py:100`) for all state-mutating endpoints. `charlie_admin` has `role=admin` per `e2e_admin_session_setup.py:244`. This assumption holds unless FXA-007 narrows to ROOT-only — the tickets do not indicate that. <!-- VERIFIED: require_admin_or_root_csrf exists at app/auth/policy.py:100; charlie_admin role=admin confirmed -->

7. **E2E flag detection**: The spec guard calls `GET /ui/fixed-assets` and checks for 503 to detect whether `FIXED_ASSETS_ENABLED` is set in the running stack. This requires the FXA-007 router to be registered in `app/main.py` and the flag guard to fire at the router/service level (not at import time). <!-- FORWARD_DEP: FXA-007 spec §4.5 defines the main.py include_router call; resolves when FXA-007 is built -->
