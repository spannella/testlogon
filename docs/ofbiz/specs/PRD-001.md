# PRD-001 — Product-depth scoping spike & single-table key design

**Type:** Spike | **Priority:** P0 | **Estimate:** 3 days
**Milestone:** 1 — Scaffolding & Data Model

---

## 1. Summary & Goal

PRD-001 is the design gate for the entire OFBiz Catalog/Product-depth workstream (PRD-002 through PRD-016). It maps OFBiz catalog entities — `Product` with `productTypeId` VIRTUAL/VARIANT/FINISHED_GOOD/DIGITAL_GOOD, `ProductCategory`/`ProductCategoryRollup` tree, `ProductFeature`/`ProductFeatureCategory`/`ProductFeatureAppl`, `ProductAssoc` (PRODUCT_VARIANT / MANUF / SUBSTITUTE / COMPLEMENT), configurable `ProductConfig`/`ProductConfigOption`, and `ProductPrice` components — onto the existing testlogon catalog model and prescribes the DynamoDB key design every downstream ticket will implement.

The **primary deliverable** is this design document. No code ships in PRD-001 itself. The outcomes that subsequent tickets depend on are:

1. **Table decision**: whether new depth-entities go onto `T.catalog` (the existing `shopping_catalog` table) or a dedicated `T.product_depth` table. This spec recommends a dedicated table (see §3 for rationale).
2. **PK/SK/GSI layout** for every new entity type, with `attr_types` annotations for any numeric sort key.
3. **Idempotency strategy**: deterministic entity IDs based on content hashes so re-submitting the same creation request is a no-op.
4. **Variant↔inventory-SKU mapping**: how a chosen feature-value tuple selects a specific inventory SKU in `T.inventory`/`T.reservations`.
5. **Back-compat statement**: how the scalar catalog item at `app/routers/catalog.py` and `app/services/shoppingcart.py` are byte-for-byte unchanged when `PRODUCT_DEPTH_ENABLED` is off.

## 2. Context & Current State

### 2.1 The existing scalar catalog model

The live catalog lives on a single DynamoDB table named `shopping_catalog` (configured via `S.catalog_table_name`, `app/core/settings.py:832`; table handle `T.catalog`, `app/core/tables.py:99`). Two primary entity shapes exist on the table:

**Category rows** — `PK=CAT#{category_id}`, `SK=META`, `entity="category"`. Created at `app/routers/catalog.py:261`. Each category row carries `GSI1PK="CATS"`, `GSI1SK=f"{name.lower()}#{category_id}"` so that `GET /ui/catalog/categories` can list all categories with a `GSI1` query (`app/routers/catalog.py:199`). The fallback for tables where `GSI1` was not yet provisioned is a full-table scan filtered by `entity == "category"` (`app/routers/catalog.py:211–217`).

**Item rows** — `PK=CAT#{category_id}`, `SK=ITEM#{item_id}`, `entity="item"`. Created at `app/routers/catalog.py:353`. The `ByItemId` GSI (`scripts/local-ddb-init.py:123`) is a single-attribute GSI keyed on the `item_id` attribute that already exists on the item row — there is **no** second projection row. `_find_item_by_id` (`app/routers/catalog.py:702`) queries this GSI with a FilterExpression `entity = "item"` to exclude review rows that also carry `item_id`.

The table schema in `scripts/local-ddb-init.py:117–125`:
```python
TableDef(
    _resolve_table_name(S.catalog_table_name, "shopping_catalog"),
    "PK", "SK",
    gsi=[
        {"index_name": "GSI1", "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "ByItemId", "partition_key": "item_id"},
    ],
)
```
Note that `GSI1SK` is a string (category-name prefix), so no `attr_types` entry is needed here.

### 2.2 The catalog item output shape

`_catalog_item_out` at `app/routers/catalog.py:107` produces a `CatalogItemOut` (`app/models.py:672`). The current fields are: `category_id`, `item_id`, `name`, `description`, `price_cents`, `currency`, `image_urls`, `attributes`, `creator_id`, `created_at`, `updated_at`, `stock_count`, `stock_status`, `low_stock_threshold`, `stock_updated_at`, `position`. None of these are product-type-aware; the item is always treated as a standalone (FINISHED_GOOD / DIGITAL_GOOD) product.

`_compute_stock_status` at `app/routers/catalog.py:94` reads `stock_count` from the item row directly, using `S.catalog_default_low_stock_threshold` (`app/core/settings.py:833`) as the default.

### 2.3 The cart integration point

`add_catalog_item` at `app/services/shoppingcart.py:370` adds a catalog item to a cart. It reads the item directly from `T.catalog` (`app/services/shoppingcart.py:381`), asserts `entity == "item"`, and creates a cart line with `sku=f"catalog:{item_id}"` and `unit_price_cents=int(item["price_cents"])` (`app/services/shoppingcart.py:391–394`). This is the integration seam that PRD-007 / PRD-009 will extend — variants and bundle expansions must produce a cart line in a shape this function already understands, without modifying it.

### 2.4 The billing / ledger integration point

All money-out paths (refunds, returns, cancellations) reuse `refund_payment` at `app/routers/billing.py:1287`, which calls the stripe SDK then calls `new_ledger_entry` (`app/services/billing_shared.py:224`) to write the adjustment row. The general ledger (GL) derives from this single-entry ledger pattern; PRD-012's price-component layer is **read-only enrichment** only — it does not introduce a new charge path. Cart/checkout continues to call `new_ledger_entry` via the existing `purchase_transactions` flow; price components only change the value of `unit_price_cents` resolved before the cart is populated, not after.

### 2.5 The `catalog_products` table (pre-existing, unrelated)

`T.catalog_products` (`app/core/tables.py:127`, `app/core/settings.py:1122`) is used by `file_bundle_checkout.py` and `api_package_catalog.py` for `entity="file_bundle_sku"` / `entity="api_package_sku"` rows — an entirely different concept from OFBiz product variants. Its `GSI_PRODUCT_TYPE` GSI (`scripts/local-ddb-init.py:283`) is keyed on `GSI_PRODUCT_TYPE_PK` / `GSI_PRODUCT_TYPE_SK`. **PRD-001 does not modify this table.** The new depth work lives on a separate `T.product_depth` table to avoid collision.

### 2.6 Existing pattern for default-off feature flags

The canonical default-off pattern in `app/core/settings.py` (following `inventory_reservations_enabled` at `:839` and `returns_rma_enabled` at `:846`):
```python
product_depth_enabled: bool = os.environ.get("PRODUCT_DEPTH_ENABLED", "false").lower() == "true"
```
Services gate on this flag via a `_flag_on()` / `_require_enabled()` helper pair (see `app/services/inventory.py:50–56` as the canonical model).

## 3. Data Model

### 3.1 Table decision: dedicated `product_depth` table

**Recommendation: dedicated table, not co-resident on `T.catalog`.**

Rationale:
- The existing `ByItemId` GSI on `T.catalog` is a single-attribute projection keyed on `item_id`. Mixing depth rows (variants, features, associations, price components) would require adding multiple new GSIs to `T.catalog`, which risks `ValidationException` on existing data that lacks the new GSI key attrs and complicates the table's access patterns.
- The entity-scan filter `item.get("entity") != "item"` at `app/routers/catalog.py:485` already relies on all non-item entities on `T.catalog` being category rows; adding variant/feature/bundle rows would widen the filter surface.
- A dedicated table keeps the scope of `PRODUCT_DEPTH_ENABLED=off` trivially verifiable: if the table handle is never referenced, behavior is unchanged.
- Precedent: `T.inventory` and `T.reservations` were created as dedicated tables for OFB-003/004 rather than extending the catalog table.

**Table name**: `product_depth` (env `PRODUCT_DEPTH_TABLE_NAME`, default `"product_depth"`).
**Primary key**: `PK` (String) / `SK` (String).

### 3.2 Entity layout on `T.product_depth`

Every row carries `entity` (a discriminator string) and `creator_id` (the owning user sub, for access-control checks).

#### 3.2.1 Product-type marker

Maps to OFBiz `Product.productTypeId`. Rather than duplicating the full scalar item on `T.product_depth`, a thin marker row is written when a scalar catalog item is promoted to a product type.

| Attribute | Value |
|---|---|
| `PK` | `ITEM#{item_id}` |
| `SK` | `TYPE` |
| `entity` | `"product_type"` |
| `product_type` | `"virtual"` / `"variant"` / `"standalone"` / `"bundle"` / `"kit"` / `"digital"` |
| `creator_id` | `{user_sub}` |
| `created_at` | Unix int |
| `updated_at` | Unix int |

`standalone` is the default (semantically equivalent to OFBiz `FINISHED_GOOD`/`DIGITAL_GOOD`); for existing scalar items with no marker row the type resolves as `standalone`.

#### 3.2.2 Category-tree rows

Extends the flat `CAT#{id}/META` rows on `T.catalog` with depth-specific metadata. The scalar category row on `T.catalog` remains unchanged; a companion depth row adds tree position.

| Attribute | Value |
|---|---|
| `PK` | `CAT#{category_id}` |
| `SK` | `TREE` |
| `entity` | `"category_tree"` |
| `parent_category_id` | `{parent_id}` or absent for root |
| `path` | `"root/parent/.../category_id"` (materialized ancestry, `/`-delimited) |
| `position` | Integer — ordering within parent (numeric, must be in `attr_types`) |
| `depth` | Integer — nesting depth (0 = root) |
| `GSI_PARENT_PK` | `PARENT#{parent_category_id}` (or `"PARENT#root"` for roots) |
| `GSI_PARENT_SK` | Integer `position` (numeric sort — allows ordered child listing) |
| `creator_id` | `{user_sub}` |

**GSI: `ByParent`** — `GSI_PARENT_PK` (S) / `GSI_PARENT_SK` (N). `attr_types={"GSI_PARENT_SK": "N"}`.
Allows `list_children(parent_id)` in O(1) without scanning.

#### 3.2.3 Feature-category rows

Maps to OFBiz `ProductFeatureCategory`. One row per logical feature axis (e.g. "Color", "Size").

| Attribute | Value |
|---|---|
| `PK` | `FTCAT#{feature_category_id}` |
| `SK` | `META` |
| `entity` | `"feature_category"` |
| `name` | `"Color"` |
| `description` | Optional string |
| `creator_id` | `{user_sub}` |
| `created_at` | Unix int |

**Feature-value rows** (OFBiz `ProductFeature`):

| Attribute | Value |
|---|---|
| `PK` | `FTCAT#{feature_category_id}` |
| `SK` | `FTVAL#{feature_value_id}` |
| `entity` | `"feature_value"` |
| `name` | `"Red"` |
| `price_delta_cents` | Signed integer (0 = no delta) |
| `position` | Integer (ordered display — numeric, in `attr_types`) |
| `GSI_FTCAT_PK` | `FTCAT#{feature_category_id}` |
| `GSI_FTCAT_SK` | Integer `position` |

**GSI: `ByFeatureCategory`** — `GSI_FTCAT_PK` (S) / `GSI_FTCAT_SK` (N). `attr_types={"GSI_FTCAT_SK": "N"}`.

#### 3.2.4 Feature-application rows (product ↔ feature-category binding)

Maps to OFBiz `ProductFeatureAppl`. Associates a feature category with a product, making that axis selectable for this product.

| Attribute | Value |
|---|---|
| `PK` | `ITEM#{item_id}` |
| `SK` | `FTAPPL#{feature_category_id}` |
| `entity` | `"feature_appl"` |
| `feature_category_id` | string |
| `sequence_num` | Integer — axis ordering on the product (numeric, in `attr_types`) |
| `creator_id` | `{user_sub}` |

No new GSI needed; listing a product's feature applications is a SK-prefix query `begins_with("FTAPPL#")` on `PK=ITEM#{item_id}`.

#### 3.2.5 Variant rows

Maps to OFBiz `Product` (type=VARIANT) + `ProductAssoc` (type=PRODUCT_VARIANT). Each variant is a distinct SKU mapping to a unique feature-value combination.

| Attribute | Value |
|---|---|
| `PK` | `ITEM#{parent_item_id}` |
| `SK` | `VAR#{variant_id}` |
| `entity` | `"variant"` |
| `variant_id` | `sha256(parent_item_id + sorted_feature_value_tuple)[:16]` — deterministic |
| `parent_item_id` | string |
| `sku` | `"variant:{parent_item_id}:{variant_id}"` — inventory key |
| `feature_values` | `{"feature_category_id": "feature_value_id", ...}` |
| `price_delta_cents` | Integer (signed; Σ of feature value deltas) |
| `effective_price_cents` | Integer (parent price + price_delta_cents; denormalized for cart speed) |
| `creator_id` | `{user_sub}` |
| `created_at` | Unix int |
| `GSI_VIRT_PK` | `VIRTUAL#{parent_item_id}` |
| `GSI_VIRT_SK` | `{created_at}` — chronological listing (numeric, in `attr_types`) |

**GSI: `ByVirtualParent`** — `GSI_VIRT_PK` (S) / `GSI_VIRT_SK` (N). `attr_types={"GSI_VIRT_SK": "N"}`.
Allows `list_variants(parent_item_id)` in one GSI query without scanning.

**Inventory-SKU mapping**: `variant.sku` is the SKU key used in `T.inventory` (`app/services/inventory.py`) and `T.reservations`. When the cart calls `add_catalog_item`, the caller first resolves the variant SKU via `list_variants`, then calls `add_item` directly with that SKU — bypassing the `f"catalog:{item_id}"` default, so the inventory-reservation path from OFB-004 tracks the correct variant stock. This does not modify `add_catalog_item` itself.

#### 3.2.6 Bundle/kit component rows

Maps to OFBiz `ProductAssoc` (type=PRODUCT_COMPONENT).

| Attribute | Value |
|---|---|
| `PK` | `ITEM#{bundle_item_id}` |
| `SK` | `COMP#{component_item_id}` |
| `entity` | `"bundle_component"` |
| `bundle_item_id` | string |
| `component_item_id` | string |
| `quantity` | Integer (ge=1) |
| `sequence_num` | Integer — display order (numeric, in `attr_types`) |
| `creator_id` | `{user_sub}` |

No new GSI required; components are retrieved with a SK-prefix scan `begins_with("COMP#")` on `PK=ITEM#{bundle_item_id}`.

#### 3.2.7 Product-association rows

Maps to OFBiz `ProductAssoc` types SUBSTITUTE, COMPLEMENT/cross-sell, UPGRADE/upsell, MANUF.

| Attribute | Value |
|---|---|
| `PK` | `ITEM#{from_item_id}` |
| `SK` | `ASSOC#{assoc_type}#{assoc_id}` |
| `entity` | `"product_assoc"` |
| `assoc_id` | `sha256(from_item_id + assoc_type + to_item_id)[:16]` — deterministic |
| `assoc_type` | `"substitute"` / `"complement"` / `"upgrade"` / `"manuf"` |
| `from_item_id` | string |
| `to_item_id` | string |
| `creator_id` | `{user_sub}` |
| `created_at` | Unix int |
| `GSI_ASSOC_PK` | `ASSOC_SRC#{from_item_id}` |
| `GSI_ASSOC_SK` | `{assoc_type}#{assoc_id}` — string, no `attr_types` needed |

**GSI: `ByAssocSource`** — `GSI_ASSOC_PK` (S) / `GSI_ASSOC_SK` (S). Allows `list_associations(item_id)` and `list_associations(item_id, assoc_type=X)` with a SK-begins-with filter.

#### 3.2.8 Price-component rows

Maps to OFBiz `ProductPrice`. Per-product price components by type, date-effective.

| Attribute | Value |
|---|---|
| `PK` | `ITEM#{item_id}` |
| `SK` | `PRICE#{price_type}#{effective_at}` where `effective_at` is zero-padded 10-digit Unix int |
| `entity` | `"price_component"` |
| `price_type` | `"LIST"` / `"DEFAULT"` / `"PROMO"` / `"COMPETITIVE"` / `"MINIMUM"` / `"AVERAGE_COST"` |
| `amount_cents` | Integer |
| `currency` | `"USD"` |
| `effective_at` | Unix int (numeric for `attr_types`) |
| `expires_at` | Unix int or absent |
| `creator_id` | `{user_sub}` |
| `GSI_PRICE_PK` | `PRICE#{item_id}#{price_type}` |
| `GSI_PRICE_SK` | Integer `effective_at` — newest-first by negating? No — scan with ScanIndexForward=False |

**GSI: `ByItemPrice`** — `GSI_PRICE_PK` (S) / `GSI_PRICE_SK` (N). `attr_types={"GSI_PRICE_SK": "N", "effective_at": "N"}`.
Allows `resolve_effective_price(item_id, price_type, as_of)` with a ranged query (`GSI_PRICE_SK <= as_of`, `ScanIndexForward=False`, `Limit=1`) to find the newest price effective at `as_of`.

### 3.3 Summary: all GSIs and their `attr_types`

The `TableDef` for `product_depth` in `scripts/local-ddb-init.py` requires:

```python
TableDef(
    _resolve_table_name(S.product_depth_table_name, "product_depth"),
    "PK", "SK",
    gsi=[
        {"index_name": "ByParent",         "partition_key": "GSI_PARENT_PK", "sort_key": "GSI_PARENT_SK"},
        {"index_name": "ByFeatureCategory","partition_key": "GSI_FTCAT_PK",  "sort_key": "GSI_FTCAT_SK"},
        {"index_name": "ByVirtualParent",  "partition_key": "GSI_VIRT_PK",   "sort_key": "GSI_VIRT_SK"},
        {"index_name": "ByAssocSource",    "partition_key": "GSI_ASSOC_PK",  "sort_key": "GSI_ASSOC_SK"},
        {"index_name": "ByItemPrice",      "partition_key": "GSI_PRICE_PK",  "sort_key": "GSI_PRICE_SK"},
    ],
    attr_types={
        "GSI_PARENT_SK": "N",   # category position (int)
        "GSI_FTCAT_SK":  "N",   # feature-value position (int)
        "GSI_VIRT_SK":   "N",   # variant created_at (int)
        "GSI_PRICE_SK":  "N",   # price effective_at (int)
    },
)
```

`GSI_ASSOC_SK` is a String (`"{assoc_type}#{assoc_id}"`), so no `attr_types` entry is needed for that index.

### 4.4 Variant service (`app/services/product_variants.py`) — PRD-007

```python
def compute_variant_id(parent_item_id: str, feature_values: Dict[str, str]) -> str: ...
# sha256(parent_item_id + "|" + "|".join(sorted(f"{k}={v}" for k,v in feature_values.items())))[:16]

def compute_variant_price(
    parent_price_cents: int,
    feature_values: Dict[str, str],
    feature_value_deltas: Dict[str, int],   # {feature_value_id: price_delta_cents}
) -> int: ...
# parent_price_cents + sum(feature_value_deltas.get(v, 0) for v in feature_values.values())

def create_variant(
    user_sub: str,
    parent_item_id: str,
    feature_values: Dict[str, str],         # {feature_category_id: feature_value_id}
) -> Dict: ...
# Fetches parent from T.catalog; resolves feature value deltas from T.product_depth.
# Writes PK=ITEM#{parent}, SK=VAR#{variant_id} on T.product_depth.
# Idempotent: duplicate variant_id -> 409 with stable message.
# Marks parent as product_type="virtual" if not already.

def list_variants(parent_item_id: str) -> List[Dict]: ...
# GSI query on ByVirtualParent (GSI_VIRT_PK=VIRTUAL#{parent_item_id}), ScanIndexForward=True.

def delete_variant(user_sub: str, parent_item_id: str, variant_id: str) -> None: ...
```

**Variant SKU → inventory mapping**: `variant.sku = f"variant:{parent_item_id}:{variant_id}"`. The caller (cart integration, PRD-008 endpoint) passes this SKU to `inventory.reserve(sku=variant.sku, ...)` from OFB-004 (`app/services/inventory.py:339`). No modification to `add_catalog_item` is required because the depth-aware cart path (PRD-011) calls `add_item` directly with the pre-resolved variant SKU and `unit_price_cents=variant["effective_price_cents"]`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Standalone items when flag is on

A scalar catalog item with no `ITEM#{id}/TYPE` row on `T.product_depth` is treated identically to today. `_catalog_item_out` is called unchanged; the new additive fields (`product_type`, `variant_count`, `has_features`, `bundle_component_count`) default to `None` / `0` / `False` / `0` respectively (PRD-003 will add them as `Optional` with defaults). Calling `GET /items/{id}/variants` returns `{"variants": [], "count": 0}`.

### 5.2 Virtual product with no variants

A product marked `product_type="virtual"` but with no variant rows is in an "incomplete" state. The cart must reject adding a virtual product directly (`add_catalog_item` raises 409 "Product requires variant selection") when a TYPE row with `product_type="virtual"` exists. This is the only modification to the `add_catalog_item` call path and it is gated on `_flag_on()`.

### 5.3 Variant price computation (pure function, unit-testable)

```
effective_price_cents = parent.price_cents + sum(
    feature_value_delta(fv_id)
    for fv_id in feature_values.values()
)
```

This must be a pure function (`compute_variant_price` in §4.4) callable without DynamoDB access so it can be unit-tested in isolation. The denormalized `effective_price_cents` on the variant row is written at creation time; it is **not** recomputed on every cart read. A price change to the parent item or a feature-value delta triggers a re-materialization job (a future ticket; PRD-001 documents this as a known limitation — stale `effective_price_cents` after parent price edit).

### 5.4 Deterministic IDs and idempotency

Two entity types use content-hash IDs:

- **Variant**: `sha256(parent_item_id + "|" + sorted_feature_value_key)[:16]`. Two creates with the same parent + feature combination hit the same SK → conditional put `attribute_not_exists(PK) AND attribute_not_exists(SK)` → 409 with message "Variant already exists for this feature combination".
- **Product association**: `sha256(from_item_id + "|" + assoc_type + "|" + to_item_id)[:16]`. Same pattern.

Feature values and feature categories use `ulid_like()` (time-prefixed UUID, `app/routers/catalog.py:51`) since they are not content-addressed — the caller always provides a `name` that may be duplicated intentionally.

Category-tree rows use the existing `category_id` from the scalar row on `T.catalog`.

### 5.5 Cycle detection

**Category tree**: before `move_category(C, new_parent=P)`, assert `C not in list_descendants(P)`. Max depth enforced by `S.product_depth_max_category_depth` (default 10).

**Bundle**: before `set_components(B, components=[C, ...])`, for each component C assert `B not in list_components(C)` (1-level check). Full transitive cycle detection is bounded to 2 recursion levels per the bundle spec (deeper circular structures are not expected in practice).

### 5.6 Price-component fallback chain

`resolve_effective_price(item_id, price_type="DEFAULT", as_of=T)`:
1. Query `T.product_depth` on `ByItemPrice` GSI for the most recent component with `GSI_PRICE_SK <= T`.
2. If component's `expires_at` is set and `T > expires_at`, skip and continue to next.
3. If no valid component found, fall back to scalar `item["price_cents"]` from `T.catalog.get_item`.
4. Return the resolved int.

The cart (`add_catalog_item`) does NOT call `resolve_effective_price` by default — it reads `price_cents` directly. The depth-aware cart path (PRD-011) calls it before constructing the cart line. With flag off, the direct `price_cents` path is taken.

### 5.7 Bundle expansion and cart

`expand_bundle` returns component lines. Each line is `{item_id, sku, quantity, unit_price_cents}`. The cart's `add_item` (accepting free-form `sku` + `unit_price_cents`) is called once per line. For kit pricing, `unit_price_cents` is the component's resolved price; for bundle pricing, `unit_price_cents` is `bundle_override / component_count` rounded down (remainder applied to the first line). Reservations are made per-line via `inventory.reserve(sku=line.sku, quantity=..., user_sub=...)` (`app/services/inventory.py:339`) if `S.inventory_reservations_enabled`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

All reads/writes on `T.product_depth` use the same DynamoDB boto3 API in both dev (DynamoDB Local on port 8001) and prod (AWS DynamoDB). There is no `S.dev_mode` branch in any depth service. The `_safe_table` wrapper (`app/core/tables.py:65`) handles `Decimal` coercion transparently. The table is created by `scripts/local-ddb-init.py` in dev and by `aws dynamodb create-table` / Terraform in prod.

### 7.2 Idempotency

- **Category-tree `add_child`**: conditional put `attribute_not_exists(PK) AND attribute_not_exists(SK)` on `T.product_depth`. Re-submitting with the same child/parent is a 409 (already added).
- **`move_category`**: unconditional `put_item` overwrite on the TREE row. Idempotent.
- **`mark_product_type`**: unconditional `put_item`. Idempotent.
- **Variant creation**: deterministic `variant_id`; conditional put → 409 on duplicate.
- **Association creation**: deterministic `assoc_id`; conditional put → 409 on duplicate.
- **Feature attachment**: conditional put → 409 if already attached.
- **Price component**: `SK=PRICE#{type}#{effective_at:010d}` — multiple components for the same type at different effective dates coexist. Overwriting the same `(type, effective_at)` pair is an unconditional `put_item` (intentional upsert for corrections).

### 7.3 Security

- **Ownership enforcement**: every write endpoint resolves the `item_id` via `_find_item_by_id` and passes `creator_id` to `_require_category_owner` (existing helper, `app/routers/catalog.py:247`). A user cannot mutate another creator's product depth.
- **Feature category ownership**: feature categories are creator-scoped (`creator_id` on the `FTCAT` row). Attaching a feature category to an item verifies both the feature category's creator and the item's owner are the same user. Cross-creator feature sharing is out of scope for PRD-001 through PRD-013.
- **Price component writes are admin/creator only**: `PUT /items/{id}/price-components` requires the caller to be the item's `creator_id` (via `_require_category_owner`). No public price-mutation path exists.
- **No PII on `T.product_depth`**: depth rows carry only structural data (ids, types, prices). No personal data requiring encryption or access audit.

## 8. Backward Compatibility & Migration

### 8.1 With `PRODUCT_DEPTH_ENABLED=false` (the default)

- **Zero schema changes** to `T.catalog`. The `shopping_catalog` table, its GSIs, and its item/category rows are byte-for-byte unchanged.
- **Zero API changes**: every existing endpoint in `app/routers/catalog.py` returns identical responses. The `CatalogItemOut` model (PRD-003 will extend it) uses `Optional` fields with defaults so a deserializer expecting the old shape sees no difference.
- **Zero cart/checkout changes**: `add_catalog_item` at `app/services/shoppingcart.py:370` reads `T.catalog` directly; the only change when the flag is on is the pre-check for `product_type="virtual"` (§5.2), which is never reached when the flag is off.
- **Zero billing changes**: `new_ledger_entry` is never called from any depth service. Price components are read-only.

### 8.2 Enabling the flag on existing data

Existing catalog items have no TYPE row on `T.product_depth`, so `get_product_type(item_id)` returns `"standalone"` and the item behaves identically. The additive `product_type` field in `CatalogItemOut` will be `None` (or `"standalone"` if populated by the PRD-003 enrichment path), which is backward-compatible for API clients that don't check the field.

### 8.3 `T.product_depth` table creation

The table must exist before the flag is enabled. `scripts/local-ddb-init.py` creates it at startup; in prod, it must be provisioned (via Terraform or `aws dynamodb create-table`) before `PRODUCT_DEPTH_ENABLED=true` is deployed. The table is empty at creation; no backfill of existing catalog items is required.

## 10. Open Questions / Assumptions

1. **Assumption**: The `catalog_products` table (`T.catalog_products`) is unrelated to OFBiz product depth and will not be extended in the PRD series. It exists for file-bundle and API-package SKUs and its `entity` discriminator (`"file_bundle_sku"`, `"api_package_sku"`) does not conflict. **Verify** with the team that `catalog_products` ownership is stable before PRD-002.

2. **Assumption**: Virtual product → variant children do NOT get their own `ITEM#` rows on `T.catalog`. Each variant is purely a depth row on `T.product_depth`. This means a variant is not directly addressable as a `CatalogItemOut` — callers must fetch the parent and then the variant list. **Verify** this is the intended UX for PRD-003/008.

3. **Assumption**: `effective_price_cents` on the variant row is denormalized at creation time and is NOT recomputed when the parent's `price_cents` changes. This means a parent price edit silently stalens all variant prices until a re-materialization is triggered. A re-materialization job is deferred to a future ticket. **Decision needed**: should variant creation be rejected if the parent price is 0, or is this acceptable?

4. **Open question**: Should feature categories be global (any creator can reuse "Color") or per-creator? This spec assumes per-creator (scoped by `creator_id` on the `FTCAT` row). A global feature-category model would require a `GSI_FTCAT_PK="GLOBAL"` query pattern and admin governance. **Decide before PRD-006.**

5. **Assumption**: Price components of type `MINIMUM_PRICE` and `AVERAGE_COST` are stored but not enforced by the cart (they are informational). Only `DEFAULT_PRICE` is used by `resolve_effective_price` in the add-to-cart path. If enforcement is wanted, that is a future pricing-rules ticket.

6. **Assumption**: The `product_depth` table uses the same DynamoDB endpoint and IAM credentials as all other tables (`S.ddb_endpoint_url`, `AWS_ACCESS_KEY_ID=test` in dev). No separate provisioning path.

7. **Open question**: The CATALOG_DEPTH_TICKETS.md mentions the existing `ByItemId` GSI at `scripts/local-ddb-init.py:123` for resolving an item from a bare `item_id`. Depth rows on `T.product_depth` use `PK=ITEM#{item_id}` but do NOT propagate to the `ByItemId` GSI on `T.catalog`. Is this intentional? The recommendation is yes — depth rows are looked up by service functions that already know `item_id`; the `ByItemId` GSI is only needed for the `_find_item_by_id` helper on `T.catalog`.

8. **Assumption**: Bundle price distribution across component lines (remainder to first line, §5.7) is acceptable for display purposes. If accounting requires integer allocation, Bresenham rounding may be needed.
