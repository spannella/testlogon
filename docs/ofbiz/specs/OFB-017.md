# OFB-017 — Accounting admin UI

## 1. Summary & Goal

OFB-017 delivers the **ROOT-only accounting section** of the admin UI. It surfaces all four of the upstream GL services (OFB-013 chart of accounts, OFB-014 double-entry journal, OFB-015 AR/AP subledgers, OFB-016 financial statements) through a cohesive React interface, and wires the existing QuickBooks/Xero export mapper (`app/services/audit_export_accounting.py`) into a one-click export action.

**Acceptance criteria from the ticket:**
- ROOT can view the chart of accounts, journal entry browser, AR/AP aging, and the three financial statements; non-ROOT receives 403.
- Journal rows drill through to their source billing ledger entry (linking back to `T.billing` via `source_sk`/`source_pk`).
- Export downloads a QuickBooks or Xero-format CSV via the existing `create_export_job` pipeline (`app/services/audit_export_pipeline.py:304`).

**Non-goals:** This ticket adds no new DynamoDB state of its own. Every GL data-access function is owned by OFB-013..016. OFB-017 provides only the read-layer API router that aggregates those services, and the React pages that call it.

## 4. API / Service Design

### 4.1 New router: `app/routers/accounting_ui.py`

```python
"""Accounting admin UI read-aggregation router (OFB-017).

Read-only over GL services. All endpoints require ROOT.
Mounted at /ui/admin/accounting. Gated by S.accounting_ui_enabled.
"""
from fastapi import APIRouter, Depends, HTTPException, Query
from app.auth.policy import require_root
from app.auth.deps import AuthenticatedUser
from app.core.settings import S

accounting_ui_router = APIRouter(
    prefix="/ui/admin/accounting",
    tags=["accounting-ui"],
)

def _check_enabled() -> None:
    if not S.accounting_ui_enabled:
        raise HTTPException(status_code=404, detail="Accounting UI disabled")
```

#### Function signatures

```python
@accounting_ui_router.get("/accounts", response_model=AccountingChartOut)
async def list_chart_of_accounts(
    account_class: Optional[str] = Query(None),
    active_only: bool = Query(True),
    user: AuthenticatedUser = Depends(require_root),
) -> AccountingChartOut:
    _check_enabled()
    from app.services import gl_accounts as svc
    accounts = svc.list_accounts(account_class=account_class, active_only=active_only)
    return AccountingChartOut(accounts=[_account_out(a) for a in accounts])


@accounting_ui_router.get("/journal", response_model=AccountingJournalPageOut)
async def list_journal_entries(
    start_date: str = Query(...),
    end_date: str = Query(...),
    cursor: Optional[str] = Query(None),
    limit: int = Query(50, ge=1, le=200),
    user: AuthenticatedUser = Depends(require_root),
) -> AccountingJournalPageOut:
    _check_enabled()
    from app.services import gl_posting as svc
    # NOTE (pass 3): OFB-014 does not yet define list_journal_entries at the
    # service layer (only router-level list_entries exists). OFB-014 must add
    # this service-level helper, or OFB-017 must query T.gl_journal directly.
    # See §10 item 3 and §13 for the resolution plan.
    result = svc.list_journal_entries(start_date=start_date, end_date=end_date,
                                      cursor=cursor, limit=limit)
    return AccountingJournalPageOut(**result)


@accounting_ui_router.get("/journal/{journal_entry_id}/source",
                          response_model=AccountingSourceLedgerOut)
async def get_source_ledger_entry(
    journal_entry_id: str,
    user: AuthenticatedUser = Depends(require_root),
) -> AccountingSourceLedgerOut:
    _check_enabled()
    from app.services import gl_posting as svc
    from app.core.tables import T
    # NOTE (pass 3): get_journal_entry_header not defined in OFB-014 service;
    # same PLAN_GAP as list_journal_entries above. See §13.
    header = svc.get_journal_entry_header(journal_entry_id)
    if not header:
        raise HTTPException(404, "Journal entry not found")
    source_pk = header.get("source_pk", "")
    source_sk = header.get("source_sk", "")
    if not source_pk or not source_sk:
        raise HTTPException(404, "Source ledger reference missing")
    row = T.billing.get_item(Key={"pk": source_pk, "sk": source_sk}).get("Item")
    if not row:
        raise HTTPException(404, "Source billing ledger row not found")
    return AccountingSourceLedgerOut(**_ledger_row_out(row))


@accounting_ui_router.post("/export", response_model=AccountingExportOut, status_code=202)
async def trigger_accounting_export(
    body: AccountingExportIn,
    user: AuthenticatedUser = Depends(require_root),
) -> AccountingExportOut:
    _check_enabled()
    from app.services.audit_export_pipeline import create_export_job
    job = create_export_job(
        categories=["billing"],

        from_ts=body.from_ts,
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Chart of accounts (`/accounts`)

- Calls `gl_accounts.list_accounts(account_class=..., active_only=...)` from OFB-013.
- `account_class` query parameter is optional; omitting it returns all classes.
- `active_only=true` (default) excludes disabled accounts. UI always passes `active_only=false` for the admin chart view so disabled accounts appear with a visual indicator.
- If `GL_DOUBLE_ENTRY_ENABLED=false` (upstream flag off), `gl_accounts.list_accounts()` returns `[]` (service is dormant) — the UI renders an empty state with an explanatory message.

### 5.2 Journal entry browser (`/journal`)

- Queries `gl_posting.list_journal_entries` which pages via `ENTRIES_BY_DATE` GSI on `gl_journal` (per OFB-014 spec: `PK=ledger_date, SK=posted_at (N)`).
- Date range is validated: `start_date <= end_date`, both in `YYYY-MM-DD` format. Empty range (no posted entries) returns `entries=[], count=0, cursor=null` — not an error.
- `limit` is capped at 200. The backend loops via `LastEvaluatedKey` until it has `limit` headers or exhausts the day's results (per the CLAUDE.md `DDB FilterExpression doesn't reduce page size` gotcha).
- Lines are fetched via a separate query on `SK.begins_with("JL#{journal_entry_id}#")` in the same `JE#GLOBAL` partition. The full-entry endpoint (`/journal/{id}`) always returns lines; the list endpoint returns headers only (no lines) to keep payloads small.

### 5.3 Drill-through to source billing ledger (`/journal/{id}/source`)

- Reads the header row to get `source_pk` and `source_sk`.
- Does a single `T.billing.get_item(Key={"pk": source_pk, "sk": source_sk})`.
- Returns 404 if the billing row was deleted (possible after a long retention window).
- Returns 404 if the journal entry itself doesn't exist.
- Never mutates `T.billing`.
- The frontend journal table renders a "View source" link/button on each row. Clicking it opens an inline detail panel (slide-over) showing the raw billing ledger fields — same data as the user's billing history, but accessed via the ROOT-only drill-through path.

### 5.4 AR/AP aging (`/ar-aging`, `/ap-aging`)

- Delegates to `ar_subledger.compute_ar_aging()` and `ap_subledger.compute_ap_aging()` (OFB-015 services; see §13 correction — OFB-015 §4.1/§4.2 define `compute_ar_aging`/`compute_ap_aging`, not `get_ar_aging`/`get_ap_aging`).
- These are always recomputed live on demand (no snapshot read for real-time accuracy). The `ar_ap_snapshots` table is used internally by OFB-015 for trend history — OFB-017 does not expose snapshots directly.
- `variance_cents` = `abs(sum(open items) - GL control account balance)`. The UI highlights non-zero variance in amber (warning, not error) — a non-zero variance may be normal lag between ledger posting and GL posting.
- If `AR_AP_SUBLEDGERS_ENABLED=false` (OFB-015 flag off), calls to the subledger service return empty results. The UI renders an "AR/AP subledgers not enabled" placeholder.

### 5.5 Financial statements (`/statements/*`)

- `trial-balance`: requires `start_date` and `end_date`. Calls `gl_statements.get_trial_balance(start_date, end_date)` (OFB-016). If `is_balanced=false`, the API still returns 200 with `is_balanced: false` — the out-of-balance condition is a data integrity signal surfaced to the ROOT user, not a server error.
- `income`: requires `start_date` and `end_date`. Calls `gl_statements.get_income_statement`. Also calls `platform_financial_dashboard.get_kpis` (existing service at `app/services/platform_financial_dashboard.py:367`) for the same period to compute `variance_cents = abs(net_revenue_cents - dashboard_net_revenue_cents)`.
- `balance-sheet`: requires `as_of_date` (single date). Calls `gl_statements.get_balance_sheet(as_of_date)`. `is_balanced=false` is surfaced to the user without masking.

### 5.6 Export (`/export`)

- Accepts `column_format: "quickbooks" | "xero"`, `from_ts` (Unix ts), `to_ts` (Unix ts).
- Calls `create_export_job(categories=["billing"], format="csv", from_ts=..., to_ts=..., created_by=user.sub, column_format=...)`.
- In dev mode (`S.dev_mode=True`), `create_export_job` processes synchronously and the job is immediately `"completed"` (`audit_export_pipeline.py:349–355`).
- In prod, the job is `"pending"` and processed asynchronously by the audit export worker (`S.audit_export_worker_enabled`).
- The response is `202 Accepted` with `{export_id, status}`. The frontend polls `GET /ui/admin/audit-exports/{export_id}` (existing endpoint at `app/routers/audit_export.py:265`) and downloads via `GET /ui/admin/audit-exports/{export_id}/download` when status is `"completed"`.
- The export file name suffix is auto-computed by the download endpoint (`audit_export.py:313–314`): it appends `-quickbooks` or `-xero` to distinguish formats.

### 5.7 Rate limiting and performance

- All GL read endpoints are ROOT-only and expected to have very low call frequency (one ROOT user at most). No rate limiting beyond the existing platform-wide per-user rate limits.
- `list_journal_entries` for a wide date range could be expensive. The router enforces `limit <= 200` and relies on cursor-based pagination. Do not add a server-side scan-all path.
- `/ar-aging` and `/ap-aging` are live-computed and may take several seconds on a busy DDB. The frontend should show a loading skeleton.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

The accounting router reads from `T.gl_accounts`, `T.gl_journal`, `T.ar_ap_snapshots`, and `T.billing` — all DynamoDB tables accessed identically in dev (moto-backed local DDB on port 8001) and prod (real DynamoDB). There is no `S.dev_mode` branch inside the router. The export path calls `create_export_job` which has an existing dev/prod fork in `audit_export_pipeline.py:349` — that fork is owned by the pipeline, not by OFB-017, so the router is parity-clean.

### Idempotency

- Read endpoints are idempotent by definition (no state mutation).
- The `POST /export` endpoint calls `create_export_job` which writes a new `audit_exports` row each time. This is intentional — each export request produces a distinct job with its own `export_id`. The frontend debounces the Export button to prevent rapid double-submissions.

### Security

- **Authorization**: Every endpoint in `accounting_ui_router` uses `require_root` (from `app/auth/policy.py:63`). A non-ROOT user (admin or regular user) receives 403. This is strictly more restrictive than the existing `FinancialDashboard` which allows admin-or-root (`platform_financial_dashboard_router` at `app/routers/platform_financial_dashboard.py:68`).
- **No secrets exposure**: The drill-through endpoint returns the raw billing ledger row. Sensitive fields like payment method tokens are stored in `T.billing` under `PM#` SKs, not `LEDGER#` SKs, so the drill-through can only ever return ledger rows — no payment method data leaks.
- **CSRF**: Cookie-auth `POST /export` requires `x-csrf-token` header (enforced by `require_ui_session` via the session check in `app/auth/deps.py`). The frontend `api/client.ts` attaches this automatically.
- **Audit event**: Each `POST /export` call emits a best-effort `audit_event("accounting_export_created", user.sub, ...)` so ROOT export actions are traceable.

## 8. Backward Compatibility & Migration

**Zero breaking changes.** With `ACCOUNTING_UI_ENABLED=false` (the default), the new router is registered but all its endpoints return 404. No existing router, service, or table is modified. The `billing` table, `audit_exports` table, and all existing billing endpoints are unchanged.

**Migration path for enabling the feature:**

1. Ensure OFB-013 (`GL_DOUBLE_ENTRY_ENABLED=true`, `gl_accounts` table created) is deployed and the chart is seeded.
2. Ensure OFB-014 (`gl_journal` table created, posting worker running) has posted at least one billing period.
3. Ensure OFB-015 (`AR_AP_SUBLEDGERS_ENABLED=true`, `ar_ap_snapshots` table created) is deployed.
4. Ensure OFB-016 (`gl_statements.py` service available) is deployed.
5. Set `ACCOUNTING_UI_ENABLED=true` and `VITE_ACCOUNTING_UI_ENABLED=true` and redeploy.

Steps 1–4 can be done in any order independently; step 5 activates the UI. There is no DynamoDB backfill or schema migration for the UI layer itself.

## 10. Open Questions / Assumptions

1. **Assumption**: OFB-016 will deliver `app/services/gl_statements.py` with the public functions `get_trial_balance(start_date, end_date)`, `get_income_statement(start_date, end_date)`, and `get_balance_sheet(as_of_date)`. OFB-017 imports these by name; if the OFB-016 spec defines different names, this router must update its imports.

2. **CORRECTED (pass 3)**: OFB-015 (§4.1, §4.2) defines `compute_ar_aging()` in `ar_subledger.py` and `compute_ap_aging()` in `ap_subledger.py` — not `get_ar_aging()`/`get_ap_aging()`. OFB-017's router must call `compute_ar_aging()` and `compute_ap_aging()`. All inline references updated.

3. **PLAN GAP (pass 3)**: OFB-014 (§4.1 service + §4.3 router) does NOT define service-level functions named `list_journal_entries` or `get_journal_entry_header`. OFB-014's service layer defines only `post_ledger_entry`, `post_date`, `post_date_range`, `run_gl_posting_loop`, and `start_gl_posting_task`; its router defines handler functions `list_entries` and `get_entry`. OFB-017 requires two new service-level helpers — either OFB-014 must add them, or OFB-017 must query `T.gl_journal` directly. The OFB-014 spec must be updated to add `list_journal_entries(start_date, end_date, cursor, limit)` and `get_journal_entry_header(journal_entry_id)` as public service functions, or OFB-017 must own the direct DDB queries. See §13 item for the plan-gap decision.

4. **Open question**: The `IncomeStatementOut.variance_cents` compares `net_revenue_cents` (from GL) to `dashboard_net_revenue_cents` (from `platform_financial_dashboard.get_kpis`). What is the acceptable tolerance threshold? The ticket says "reconcile within an explicit tolerance" (OFB-016 acceptance criteria). OFB-017 surfaces the raw `variance_cents` to ROOT without applying a threshold — the ROOT user decides if the variance is acceptable. A threshold-based warning UI label (e.g. amber if `variance_cents > 100`) can be added in a follow-up.

5. **Open question**: The `POST /export` endpoint returns a `202 Accepted` with an `export_id`. The frontend must poll the existing `GET /ui/admin/audit-exports/{id}` endpoint to detect completion. Is a WebSocket/SSE push notification for export completion desired? Assumed no for this ticket — the AuditExportPage (`frontend/src/pages/admin/AuditExportPage.tsx:43–48`) already uses polling via React Query, and the accounting export can reuse that pattern.

6. **Assumption**: The `/journal/{id}/source` drill-through returns the raw billing ledger row fields (type, reason, amount_cents, state, etc.). If some billing ledger rows were created before the `ledger_date` denorm was added (FIN-013 / GAP-0202), those rows will have no `ledger_date`. The `AccountingSourceLedgerOut` model makes `ledger_date` a required field — for pre-denorm rows this should fall back to `""` not crash. The helper `_ledger_row_out` should use `.get("ledger_date", "")`.

7. **Assumption**: The `ACCOUNTING_UI_ENABLED` backend flag and `VITE_ACCOUNTING_UI_ENABLED` frontend flag are separate env vars that must be set in sync. In dev, both default `false`. If only the backend flag is set to `true` without the frontend flag, the nav item is hidden but the API endpoints are live — this is an acceptable inconsistency and does not need a startup check.
