# POS-002 — POS data model (models.py)

## 1. Summary & Goal

POS-002 adds all Pydantic shapes that the Point-of-Sale module needs to `app/models.py`, immediately after the existing Returns / RMA block (currently ending at `app/models.py:670`). No router, no service, no DynamoDB table, and no settings key are added by this ticket — those are POS-003 through POS-005. The deliverable is a self-contained set of validated models that import cleanly, enforce the same integer-cents / `now_ts()` conventions used everywhere else in the codebase, and include a cross-field validator that checks whether a tender request's sum covers a transaction total.

The models reflect the reuse contract established by POS-001: every POS sale resolves to a `purchase_cart` / `create_order_from_line_items` call; money flows through `new_ledger_entry` (`app/services/billing_shared.py:224`) / `refund_return` (`app/services/returns_rma.py:444`); POS introduces only the register, session, transaction-wrapper, and tender concepts that do not yet exist.

## 2. Context & Current State

### 2.1 Money conventions

All monetary amounts in the codebase are integer cents. The canonical pattern is:

- `CatalogItemCreateIn.price_cents: int = Field(ge=0, le=10_000_000_00)` (`app/models.py:542`)
- `ShoppingCartItemIn.unit_price_cents: conint(ge=0, le=100000000)` (`app/models.py:939`)
- `ApiPackageSkuCreateIn.amount_cents: conint(ge=0, le=100000000)` (`app/models.py:823`)

POS models follow these bounds. `conint` and `Field(ge=0)` are both in use; this spec uses `Field(ge=0, le=...)` for new models because it produces clearer validation error messages, matching the trend in the OFBiz models added after line 581.

### 2.2 Quantity conventions

`ShoppingCartItemIn.quantity: conint(ge=1, le=1000)` (`app/models.py:938`) and `InventoryReserveIn.quantity: int = Field(ge=1, le=10_000_000)` (`app/models.py:612`) both enforce `ge=1`. POS line-item quantities follow `ge=1`.

### 2.3 Timestamp conventions

`now_ts()` from `app/core/time.py:2` returns an integer Unix second timestamp. All output models that expose timestamps use `int` (e.g. `ReservationOut.created_at: int = 0` at `app/models.py:626`). Timestamps are never ISO strings in the OFBiz model family.

### 2.4 Enum / Literal conventions

Closed-value fields use `Literal` rather than `Enum` throughout the OFBiz model block, e.g. `ReservationOut.status: str  # active | committed | released | expired` (`app/models.py:623`) and `ReturnOut.status: str  # requested | approved | ...` (`app/models.py:659`). The `Literal` approach is used for `In` models where the value is constrained at the boundary, while `Out` models sometimes use plain `str` with an inline comment. POS follows the same convention: `Literal` on `In` models, plain `str` with comment on `Out` models.

### 2.5 model_validator usage

`@model_validator(mode="after")` is the established cross-field validation mechanism (e.g. `CatalogStockAdjustIn.exactly_one_mode` at `app/models.py:566`). The tender-sum validator follows exactly this pattern.

### 2.6 Existing commerce chain (reuse, not fork)

The POS models must reference — but never replicate — the following existing shapes:

- `ShoppingCartItemsOut` / `ShoppingCartPurchaseOut` (`app/models.py:973`, `993`) — cart output the POS session will piggyback
- `ReturnRequestIn` / `ReturnOut` (`app/models.py:638`, `655`) — refund/void path reuses the RMA model
- `ReceiptLinkOut` (`app/models.py:509`) — receipt surface is unchanged; the POS transaction points to a `receipt_id` that resolves via the existing receipt service

`purchase_cart` (`app/services/shoppingcart.py:474`) accepts `idempotency_key: str | None`; the POS tender request threads its `idempotency_key` down to this call. `new_ledger_entry` (`app/services/billing_shared.py:224`) accepts `extra={"provider": "pos_cash"}` or `extra={"provider": "pos_card"}` so the platform financial dashboard (FIN-013) buckets in-person sales correctly.

### 2.7 Insertion point

The new block is placed after the Returns / RMA section that ends at `app/models.py:670`, before the `CatalogItemOut` block at line 672. This keeps all OFBiz-adjacent commerce models contiguous.

### 4.2 Request (In) models

```python
class OpenSessionIn(BaseModel):
    register_id: str = Field(min_length=1, max_length=128)
    opening_float_cents: int = Field(default=0, ge=0, le=100_000_000)


class CloseSessionIn(BaseModel):
    counted_cash_cents: int = Field(ge=0, le=100_000_000)


class AddLineItemIn(BaseModel):
    # Exactly one of sku, item_id must be provided; category_id required when item_id is used
    sku: Optional[str] = Field(default=None, min_length=1, max_length=128)
    category_id: Optional[str] = Field(default=None, min_length=1, max_length=128)
    item_id: Optional[str] = Field(default=None, min_length=1, max_length=128)
    quantity: int = Field(default=1, ge=1, le=1000)

    @model_validator(mode="after")
    def sku_or_item_id(self) -> "AddLineItemIn":
        has_sku = bool(self.sku)
        has_item = bool(self.item_id)
        if has_sku == has_item:  # both set or neither
            raise ValueError("Provide exactly one of 'sku' or 'item_id'")
        if has_item and not self.category_id:
            raise ValueError("'category_id' is required when 'item_id' is provided")
        return self


class TenderIn(BaseModel):
    kind: Literal["cash", "card", "wallet"]
    amount_cents: int = Field(ge=0, le=100_000_000)
    change_due_cents: int = Field(default=0, ge=0, le=100_000_000)
    payment_method_id: Optional[str] = Field(default=None, max_length=256)
    card_ref: Optional[str] = Field(default=None, max_length=256)

    @model_validator(mode="after")
    def card_wallet_needs_pm(self) -> "TenderIn":
        if self.kind in ("card", "wallet") and not self.payment_method_id:
            raise ValueError("'payment_method_id' is required for card/wallet tenders")
        return self


class TenderRequestIn(BaseModel):
    tenders: List[TenderIn] = Field(min_length=1)
    idempotency_key: str = Field(min_length=1, max_length=256)

    def total_tendered_cents(self) -> int:
        """Sum of all tender amounts minus change given back."""
        return sum(t.amount_cents - t.change_due_cents for t in self.tenders)

    def validates_against_total(self, transaction_total_cents: int) -> bool:
        """Returns True iff net tender covers (equals) the transaction total."""
        return self.total_tendered_cents() == transaction_total_cents


class RefundTxnIn(BaseModel):
    txn_id: str = Field(min_length=1, max_length=128)
    lines: List[ReturnLineIn] = Field(min_length=1)  # reuse existing ReturnLineIn
    reason: str = Field(min_length=1, max_length=500)
```

Note: `ReturnLineIn` is already defined at `app/models.py:633` and is reused directly by `RefundTxnIn`. The POS refund path calls `refund_payment` (via the RMA service) rather than implementing a new money-out path.

## 5. Detailed Behavior & Edge Cases

### 5.1 Tender sum validation

`TenderRequestIn.validates_against_total(transaction_total_cents)` is the single source of truth for the "tenders cover the total" check. The service layer calls this before writing any DDB row. Net tendered = `Σ(amount_cents) − Σ(change_due_cents)`. Cash over-tender is valid (cashier gives change); change is embedded in `TenderIn.change_due_cents`. Under-tender is rejected with HTTP 422 at the router level, not silently accepted.

### 5.2 `change_due_cents` semantics

`change_due_cents` is only meaningful for `kind="cash"`. For `kind="card"` or `kind="wallet"` the model validator `card_wallet_needs_pm` already enforces the payment method; the service layer must additionally reject non-zero `change_due_cents` on card/wallet tenders with HTTP 422 ("change cannot be given on card/wallet tender").

### 5.3 `AddLineItemIn` mutual exclusivity

Exactly one of `sku` or `item_id` must be provided. If `item_id` is given, `category_id` is required (because the catalog key in `app/services/shoppingcart.py:506` is `_catalog_item_key(cat_id, ci_item_id)`, a composite of both fields). A POS terminal scanning a barcode resolves it to `sku`; one using the catalog picker resolves to `category_id` + `item_id`.

### 5.4 `TenderKind` enum vs Literal

`TenderIn.kind` uses `Literal["cash", "card", "wallet"]` (matching the existing `ShoppingCartItemIn.product_type` pattern at `app/models.py:943`). `TenderOut.kind` is plain `str` with an inline comment (matching `ReservationOut.status: str  # active | committed ...` at `app/models.py:623`) so deserialization from DDB does not require the Literal constraint on reads. The enum class `TenderKind` is defined alongside the models for use by service-layer comparisons (`if tender.kind == TenderKind.cash`).

### 5.5 `RegisterConfig` creation vs output

The creation request is `RegisterConfig` with `register_id=None` (omitted), `created_at=0`, `updated_at=0`, `created_by=None`. The router fills those in from `now_ts()` and the session's `user_sub`. The same shape is used for both creation and output — `register_id` is `Optional[str] = None` on the model, and the router validates its presence on reads. This avoids a separate `RegisterConfigCreateIn`.

### 5.6 `RefundTxnIn` and the RMA reuse contract

`RefundTxnIn.lines` is `List[ReturnLineIn]` — the existing type at `app/models.py:633`. The POS refund service will call `request_return` (`app/services/returns_rma.py:174`) with a `reason` string that encodes `source_system=pos`, then immediately call `approve_return` (`app/services/returns_rma.py:371`) / `receive_return` (`app/services/returns_rma.py:409`) / `refund_return` (`app/services/returns_rma.py:444`), short-circuiting the async approval workflow for in-person voids. Note: `request_return` has no `source_system` or `metadata` parameter; the POS channel is recorded in the `reason` string until POS-004/POS-005 extends the signature. Cash refunds are issued via `new_ledger_entry(extra={"provider": "pos_cash"})` so the ledger reason is always `pos_cash_refund`.

### 5.7 `idempotency_key` on TenderRequestIn

The service layer derives `txn_id = "txn_" + sha256(idempotency_key.encode()).hexdigest()[:12]`. A second `POST /tender` with the same key returns the existing `PosTransactionOut` without re-executing (mirrors the `purchase_cart` idempotency at `app/services/shoppingcart.py:542–543`). The key is validated as non-empty (`min_length=1`) at the model level.

### 5.8 Monetary limits

`opening_float_cents` and `counted_cash_cents` are capped at `100_000_000` (one million dollars) matching `ShoppingCartItemIn.unit_price_cents`. Individual tender `amount_cents` has the same cap. `total_cents` on `PosTransactionOut` is `int` with no explicit cap because it is an output field computed by the service, not user-supplied.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity**: The Pydantic models are pure Python with no `dev_mode` branch. There is nothing to diverge. The one area that requires care in downstream tickets is the `provider` field passed to `new_ledger_entry`: both dev (moto-backed DDB) and prod (real DDB) must receive `extra={"provider": "pos_cash"}` or `extra={"provider": "pos_card"}` — the field is never conditionally omitted.

**Idempotency**: `TenderRequestIn.idempotency_key` (caller-supplied, validated non-empty) is the idempotency anchor. The service derives `txn_id` deterministically from it (`sha256(key)[:12]`) using the same SHA-256-truncation pattern as `app/services/commerce_order_service.py:67` (which truncates to `[:32]` for `order_id`; POS uses `[:12]` to fit the `txn_` prefix convention). A duplicate tender request returns the existing row without re-tendering.

**Security**: No PII is stored in `TenderOut`. `card_ref` is an opaque processor reference, never a raw PAN. `payment_method_id` references the existing `billing` table PM record (owned by the authenticated user); the service layer must verify ownership before using it (`T.billing.get_item(Key={pk, sk})` where `pk = user_pk(cashier_sub)`). The `register_id` → location mapping is a non-secret configuration row; no access-control concern there.

**Input bounds**: All `amount_cents` fields are `ge=0` (no negative charges at model level; credit notes are handled via `refund_return` at `app/services/returns_rma.py:444`). All `quantity` fields are `ge=1` (zero-quantity lines are rejected before touching inventory).

## 8. Backward Compatibility & Migration

POS-002 is purely additive. The new classes are appended after `app/models.py:670` and do not modify any existing class. No existing import is changed. No DynamoDB schema change is made (that is POS-003).

The insertion of a `TenderKind` enum class introduces the only potential namespace collision: `TenderKind` is a new name in `app/models.py`. A `grep -rn "TenderKind" app/` before merging confirms there is no existing use.

The `RefundTxnIn` model reuses `ReturnLineIn` by reference; if `ReturnLineIn` is modified in the future (e.g. adding an optional `unit_price_cents` for re-invoicing), `RefundTxnIn` inherits the change without a separate ticket. This is the intended behavior.

## 10. Open Questions / Assumptions

1. **Assumption**: `source_system="pos"` will be added to the `normalized_source` allowlist in `app/services/commerce_order_service.py:58` by POS-004/POS-005. Currently only `{"shopping_cart", "commercial_direct", "subscription_cycle"}` are accepted (`app/services/commerce_order_service.py:58`); POS orders must identify their channel.

2. **Assumption**: The receipt service (`app/services/receipts.py`) can generate a receipt given an `order_id` and a list of `TenderOut` dicts. The `receipt_id` on `PosTransactionOut` is the key returned by that service. The exact receipt service integration is POS-005 scope.

3. **Assumption**: `TenderIn.card_ref` is opaque (max 256 chars) and is sufficient to store a Stripe `PaymentIntent.id` or a mock reference in dev. If a real card-present terminal is integrated in a future ticket, this field may need to be widened or a separate `card_present_ref` added. This is deferred.

4. **Open question**: Should `RegisterConfig` carry `is_active: bool` for soft-deletion? The current design omits it; registers are deleted by removing the DDB row. If registers accumulate historical sessions that must remain visible after decommissioning, a soft-delete flag is needed. Assume no soft-delete for MVP; add in a follow-up if required.

5. **Assumption**: Tax calculation (`tax_cents` on `PosTransactionOut`) is caller-provided (the frontend or POS terminal computes it from the jurisdiction rate and passes it to the tender endpoint). The backend stores and sums it but does not recompute it. This avoids a tax-engine dependency in MVP.

6. **Assumption**: `over_short_cents` can be negative (cashier is short). The field is `Optional[int]` with no bound — negative values are valid and expected.

7. **Open question**: Does `CloseSessionIn` need to accept an `override_reason` for supervisory override of a large over/short discrepancy? Assume no override flow for MVP; add a `reason: Optional[str]` field in a follow-up if an audit log of discrepancy explanations is needed.
