# FXA-016 — Route + navigation (flag-gated)

## 1. Summary & Goal

FXA-016 wires the fixed-assets admin page (built by FXA-015) into the React SPA's routing and navigation surfaces. The deliverable is entirely additive: three targeted edits across four files in the frontend, all behind the `VITE_FIXED_ASSETS_ENABLED` build-time flag. With the flag absent or set to any falsy value the entire fixed-assets route and nav entry are invisible — the existing router tree, sidebar, and mobile nav are byte-for-byte equivalent to today's state.

The specific changes are:

1. **`frontend/src/lib/featureFlags.ts`** — confirm the `fixedAssetsEnabled` / `isFixedAssetsEnabled()` pair is present (FXA-014 is its owner; FXA-016 declares a read-only dependency on it and must not re-declare it).
2. **`frontend/src/App.tsx`** — lazy-import `FixedAssetsPage` and render the `/fixed-assets` route conditionally behind `showFixedAssets`.
3. **`frontend/src/components/layout/Sidebar.tsx`** — add a `"Fixed Assets"` nav entry in the admin section of `NAV_GROUPS`, import `isFixedAssetsEnabled` and `canAccessGeneralAdminControls`, and extend the per-path filter to hide that item when either the flag is off or the viewer is not admin/root.
4. **`frontend/src/components/layout/AppShell.tsx` (MobileSidebar)** — mirror the same entry and filter logic in `MOBILE_NAV_GROUPS` so the drawer on mobile surfaces the page only when the flag is on.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag off — complete absence

When `VITE_FIXED_ASSETS_ENABLED` is absent, `"0"`, `"false"`, `"no"`, or `"off"` (any value `toBool` normalizes to `false`), the following must hold:

- `isFixedAssetsEnabled()` returns `false` at module load time (evaluated once; the `env` object is frozen at Vite build time).
- `showFixedAssets` in `App()` is `false`; the `{showFixedAssets && <Route .../>}` expression evaluates to `false` and React renders nothing — no `<Route>` node exists in the router tree for `/fixed-assets`.
- Navigating directly to `/fixed-assets` (e.g. via address bar or a bookmark) hits the catch-all `<Route path="*" element={<ErrorPage status={404} />} />` at `App.tsx:558` [`frontend/src/App.tsx:558`]. The user sees a 404 page.
- The `Sidebar` filter returns `false` for the fixed-assets path item; `items.length` for that group is unchanged (the entry is never added to `NAV_GROUPS` conditionally — it is always in the static array but filtered out at render time). The sidebar renders identically to before FXA-016.
- The `MobileSidebar` filter returns `false` for the same item; the drawer renders identically to before FXA-016.
- No import of `FixedAssetsAdmin` is ever executed: `lazy()` wraps an arrow function, which is only called when the `<Route>` element is actually rendered. Since the `<Route>` is never mounted, the dynamic `import("@/pages/shop/admin/FixedAssetsAdmin")` never fires.
- No network request for the chunk is made. The Vite build includes the chunk (it is in the module graph) but the browser never requests it.

### 5.2 Flag on, user is USER role

`showFixedAssets` is `true`; the `<Route>` exists. However `canAccessGeneralAdminControls(accessToken)` returns `false` for a plain `USER` token. The sidebar filter evaluates `isFixedAssetsEnabled() && canAccessGeneralAdminControls(accessToken)` to `false`, so the nav entry is hidden.

Direct navigation to `/fixed-assets` is possible (the route exists and the page loads). The page itself (FXA-015) is responsible for enforcing the admin-only display — it should show a 403/forbidden state or redirect using a role check against `useAuthStore`. The backend will enforce 403 on every API call regardless.

This is consistent with the `admin/inventory` route which has no React Router-level role guard and relies on the page + backend to enforce access.

### 5.3 Flag on, user is ADMIN (scoped)

`canAccessGeneralAdminControls(accessToken)` returns `false` for scoped admins (profile type `"scoped"`, per `adminCapabilities.ts:47–52`). The nav entry is hidden. Direct URL access hits the page which renders a forbidden state.

### 5.4 Flag on, user is ADMIN (general) or ROOT

Both `isFixedAssetsEnabled()` and `canAccessGeneralAdminControls(accessToken)` are `true`. The nav entry appears in the sidebar and mobile drawer. Clicking it navigates to `/fixed-assets`; the lazy chunk loads, and the page renders.

### 5.5 Sidebar group remains visible when other items filter out

The `Account` group in `NAV_GROUPS` contains many items. Even if the fixed-assets entry is the only filtered-out item, the group still has many visible items and `items.length === 0` is never triggered for that group. No group-level collapse occurs.

### 5.6 Active state and `isActive`

`Sidebar.tsx:276` [`frontend/src/components/layout/Sidebar.tsx:276`] defines `isActive = (path) => path === "/" ? ... : location.pathname.startsWith(path)`. For `/fixed-assets`, any path starting with `/fixed-assets` (including sub-paths if the page introduces nested client routing) will highlight the nav entry as active. This is the correct default.

### 5.7 `lazy()` module-not-found error

If `frontend/src/pages/shop/admin/FixedAssetsAdmin.tsx` does not exist when a user navigates to `/fixed-assets`, the `Suspense` boundary catches the rejected import promise and re-throws it, causing the nearest `ErrorBoundary` to display (the `<ErrorPage status={404} />` fallback in the outermost route catch-all is not an error boundary — a real error boundary around `<Suspense>` is needed). This is a build-time / deployment sequencing concern: FXA-015 must land before or with FXA-016 in any merged branch.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

FXA-016 is purely a frontend concern. There is no server-side logic, no DynamoDB access, and no conditional behavior based on `S.dev_mode`. The `VITE_FIXED_ASSETS_ENABLED` variable is injected at Vite build time, making it the same code in dev and prod builds — the only difference is the environment variable value. No `import.meta.env.DEV` branch is introduced.

### 7.2 Idempotency

React Router's `<Routes>` component renders exactly the first matching `<Route>`. Because the fixed-assets route is rendered behind a flag condition, at most one `<Route path="fixed-assets" ...>` element can exist in the tree at any given time. There is no duplication risk.

### 7.3 Security

The route and nav entry are the user-facing presentation layer only. They provide no access control guarantees. All authorization enforcement lives at two deeper layers:

1. **Page layer (FXA-015)**: The `FixedAssetsAdmin` component checks the viewer's role via `useAuthStore` and renders a 403/redirect for non-admin users.
2. **API layer (FXA-007, FXA-013)**: Every `/ui/fixed-assets/*` endpoint uses `require_admin_or_root` (defined at `app/auth/policy.py:67` [`app/auth/policy.py:67`]) as its auth dependency, returning 403 for USER-role callers and 503 when `S.fixed_assets_enabled` is false. Note: `require_admin_session` does not exist in the codebase — the correct dependency is `require_admin_or_root` from `app/auth/policy.py`.

Hiding the route and nav entry when the flag is off is defense-in-depth UX polish, not a security boundary.

### 7.4 No sensitive data in the router

The lazy import path (`@/pages/shop/admin/FixedAssetsAdmin`) is a source-code string visible in the JS bundle regardless of the flag value. This is expected and harmless — the bundle structure is not a secret.

## 10. Open Questions / Assumptions

1. **Route path `/fixed-assets` vs `/admin/fixed-assets`**: This spec uses `/fixed-assets` (no `/admin/` prefix) to match the flat naming used by many existing admin features (e.g. the page is implicitly admin because of the nav filter and backend 403). If the product team standardizes all admin-only pages under `/admin/*`, the path changes to `/admin/fixed-assets` in one place each in `App.tsx`, `Sidebar.tsx`, and `AppShell.tsx`. This is a trivial change confined to FXA-016. **Assumption: `/fixed-assets` is acceptable; no change needed unless a naming convention PR is in flight.**

2. **`FixedAssetsAdmin.tsx` exact filename and export** (RESOLVED in pass 3): FXA-015 spec §1 and §4.1 define the file as `frontend/src/pages/shop/admin/FixedAssetsAdmin.tsx` with default export `FixedAssetsAdmin`. FXA-016's lazy import has been updated to match. **Assumption resolved: FXA-016 uses `FixedAssetsAdmin.tsx` / `FixedAssetsAdmin` (not `FixedAssetsPage.tsx`).**

3. **`VITE_FIXED_ASSETS_ENABLED` constant already declared in FXA-014**: FXA-016 reads `isFixedAssetsEnabled()` but does not re-declare it. This spec assumes FXA-014 has already added the constant pair to `frontend/src/lib/featureFlags.ts`. If FXA-014 has not landed, FXA-016 is blocked on that dependency. **Assumption: FXA-014 lands before or with FXA-016.**

4. **Nav group placement**: This spec places the fixed-assets entry in the existing `Account` group of `NAV_GROUPS` (line 189 in `Sidebar.tsx`), near `admin/inventory` (line 237). An alternative is to introduce a new "Operations" or "Assets" group. **Assumption: placing it in `Account` near the other admin entries is sufficient for the initial release; a nav-group refactor is a separate concern.**

5. **MobileNav bottom-tab bar vs MobileSidebar drawer**: `MobileNav.tsx` (the bottom tab bar, `frontend/src/components/layout/MobileNav.tsx`) shows only a small subset of pinned tabs and does not include admin items. FXA-016 targets only `MobileSidebar` (the Sheet drawer rendered inside `AppShell.tsx`). The bottom tab bar requires no change. **Assumption confirmed by reading `MobileNav.tsx`: it has no `admin/inventory` entry and no existing flag-gated admin items.**

6. **`Boxes` icon for fixed assets**: `Sidebar.tsx:58` [`frontend/src/components/layout/Sidebar.tsx:58`] already imports `Boxes` from `lucide-react` (used for the inventory nav item at line 237). The lucide `Landmark` icon (typically associated with fixed/real assets or financial institutions) is a reasonable choice for fixed assets — it is available in the installed lucide-react version (confirmed used at `frontend/src/pages/payouts/PayoutDashboard.tsx:14`) but is NOT currently imported in `Sidebar.tsx`. Alternative options already imported in `Sidebar.tsx`: `Wrench` (line 33, used for maintenance contexts [`frontend/src/components/layout/Sidebar.tsx:33`]) or `Boxes` (line 58). **Assumption: `Landmark` from lucide-react is used; must be added to the lucide import block in `Sidebar.tsx`. The exact icon choice is a cosmetic decision for the implementer.**

7. **`i18nKey` for the nav label**: All nav items have optional `i18nKey` fields following the `"nav.<camelCase>"` convention. The new entry should use `i18nKey: "nav.fixedAssets"`. If the i18n JSON files do not include this key, the label falls back to the `label` string (`"Fixed Assets"`). **Assumption: the fallback string display is acceptable for initial release; translations are a follow-up.**
