# FAC-003 — Facility/fulfillment Pydantic models

## 1. Summary & Goal

FAC-003 lands all the request/response Pydantic shapes that FAC-005 through FAC-011 route handlers will reference as `response_model=` and request-body types. Its scope is purely `app/models.py`: no service, router, DynamoDB table definition, or settings key is touched here. The ticket is a prerequisite for every downstream FAC router ticket because FastAPI schema generation runs at import time and requires all `response_model` types to be importable before any router is mounted.

The new models cover five sub-domains:

1. Facilities and their locations (`FacilityIn` / `FacilityOut` / `FacilityLocationIn` / `FacilityLocationOut`)
2. Stock transfers between locations (`TransferIn` / `TransferItemIn` / `TransferOut` / `TransferItemOut`)
3. Inbound receiving against purchase orders (`ReceiveIn` / `ReceiveLineIn` / `ReceiptOut` / `ReceiptLineOut`)
4. Pick / pack / ship (`PicklistOut` / `PickLineOut` / `PackageIn` / `PackageLineIn` / `ShipmentIn` / `ShipmentOut` / `PackageOut`)
5. Optional lot / serial tracking (`LotOut` / `SerialOut`)

Two cross-cutting constraints apply:

- DynamoDB stores numbers as `Decimal`. Every `Out` model that reads numeric DynamoDB attributes (`quantity`, `qty`, timestamps, counts) must coerce `Decimal` → `int` via `@field_validator(..., mode="before")` or a catch-all `@model_validator(mode="before")`, following the established project pattern (`app/models.py:2912–2918`, `app/models.py:3713–3721`).
- All models must be importable with no external dependencies so that `GET /openapi.json` succeeds when `FACILITY_FULFILLMENT_ENABLED` is off.

## 5. Detailed Behavior & Edge Cases

### 5.1 `Decimal` → `int` coercion

DynamoDB Local returns numeric attributes as Python `Decimal` objects (not `int` or `float`). The `_FloatSafeTable` class in `app/core/tables.py:29–62` coerces floats→Decimal on **writes** only (via `put_item`/`update_item`); it does NOT coerce Decimal→int on **reads** — reads return the raw boto3 response. Therefore every `Out` model's `@field_validator(mode="before")` must call `int(v)` rather than assuming `v` is already an `int`. The factory `_safe_table` is at `app/core/tables.py:65–66`. The guard `return 0 if v is None else int(v)` is copied verbatim from `app/models.py:2914–2918`.

### 5.2 `Optional[int]` timestamp fields

Fields such as `completed_at`, `shipped_at`, `delivered_at`, and `expires_at` are absent from the DDB item until the event occurs. They must be typed `Optional[int]` with a `None` default. The `@field_validator` for these fields must also return `None` for `None` input (not `0`) so callers can distinguish "not yet occurred" from "occurred at Unix epoch 0". Adjust the guard:

```python
return None if v is None else int(v)
```

For required timestamp fields like `created_at` the existing `return 0 if v is None else int(v)` pattern is correct.

### 5.3 `PackageIn` re-use in `ShipmentIn` and `PackageOut`

`PackageIn` is the input shape for packing (FAC-009) and appears as `ShipmentIn.packages`. `PackageOut` is the read shape. They are separate classes because `PackageOut` adds `package_id` (assigned by the service) and uses `int = 0` defaults for optional dimensions (DDB read path).

`PackageOut.contents` is typed `List[PackageLineIn]` — reusing the input line type for the embedded contents list. This is intentional: a package line has no server-assigned fields beyond what the caller provides, so a separate `PackageLineOut` class would be pure boilerplate. If a server-assigned field (e.g., a `line_status`) is added later, a separate `PackageLineOut` should be introduced.

### 5.4 `TransferItemOut.picked_quantity`

`picked_quantity` tracks how many units of a line have been physically moved in partial-transfer scenarios. It is distinct from `quantity` (the requested amount). On initial creation `picked_quantity = 0`; on `complete_transfer` the service sets `picked_quantity = quantity`. Callers comparing the two can detect in-progress partial transfers.

### 5.5 `ReceiptLineOut.receipt_status` vs `ReceiptOut.status`

The line-level `receipt_status` is derived per-line at read time:
- `received` — `received_quantity == ordered_quantity` (or `ordered_quantity == 0` for non-PO lines)
- `short` — `received_quantity < ordered_quantity`
- `over` — `received_quantity > ordered_quantity`

The header `ReceiptOut.status` is derived from all lines:
- `partial` — any line is `short`
- `over` — any line is `over` (and none is `short`)
- `received` — all lines are `received`

Deriving these values is the service layer's responsibility (FAC-007). The Pydantic models store the pre-computed strings.

### 5.6 Schema validation at startup with flag off

All new classes are importable unconditionally (no `if S.facility_fulfillment_enabled` guard in models.py). FastAPI schema generation runs the moment the router is mounted; since the router (FAC-005 / FAC-011) calls `_require_enabled()` at handler runtime, not import time, the schemas are always registered in OpenAPI but the handlers 404 when the flag is off. This matches the existing inventory router pattern at `app/routers/inventory.py:32–33`.

### 5.7 `FacilityIn.idempotency_key` vs service-computed `facility_id`

`FacilityIn` carries an optional `idempotency_key`. The FAC-004 service computes `facility_id = sha256(owner_sub + "|" + name)[:32]` when `idempotency_key` is absent, falling back to `sha256(idempotency_key)[:32]` when present. The model does not enforce uniqueness — that is a service-layer concern.

### 5.8 `ReceiveIn.correlation_id` is required, not optional

Unlike `TransferIn.idempotency_key` (optional, falls back to a UUID), `ReceiveIn.correlation_id` is **required**. This enforces that callers always provide an idempotency key for receiving, since double-receipts increment on-hand and are difficult to reverse without a write-off ledger entry. Callers without a natural key must generate one (e.g., `uuid4().hex`) and persist it for potential replay.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity:** `app/models.py` contains no `dev_mode` branches. Pydantic validation and Decimal coercion run identically against DynamoDB Local (moto / DDB Local on port 8001) and real DynamoDB in production. No mock paths.

**Idempotency at model layer:** Models are stateless value objects. Idempotency is enforced by service-layer conditional writes (FAC-004/006/007/008/010); the models carry the idempotency keys (`idempotency_key`, `correlation_id`) transparently.

**Input validation:**
- `FacilityIn.facility_type`, `FacilityLocationIn.location_type`, `ShipmentIn.carrier` / `tracking_number` have `Field(pattern=...)` or `min_length` constraints that reject empty strings and unknown enum values before any DDB write.
- `TransferItemIn.quantity`, `ReceiveLineIn.quantity`, `PackageLineIn.quantity` use `ge=1` to prevent zero-quantity lines.
- `ShipmentIn.packages: List[PackageIn] = Field(min_length=1)` prevents creating a shipment with no packages.

**No money fields in FAC-003 models:** `ReceiveLineIn.unit_cost_cents` is an informational cost field for inventory valuation; it does NOT trigger a billing ledger entry. Money-out paths (write-offs, damaged stock) use `billing_shared.new_ledger_entry` in the service layer (FAC-007 / FAC-010), never forking billing.

**No PII in models:** `owner_sub` / `received_by` / `created_by` are user subject identifiers (not names or emails), consistent with the audit trail pattern across all other `Out` models.

## 10. Open Questions / Assumptions

1. **`receipts` table vs reusing `transfers` table for receipt rows.** FAC-001/002 define a separate `receipts` table (not `transfers`). This spec assumes a dedicated `receipts` (or `receiving`) table with PK=`receipt_id`, SK=`META` | `LINE#{n}`. If FAC-002 instead reuses the `transfers` table with a `record_type="receipt"` discriminator, `ReceiptOut.receipt_id` maps to `transfer_id` and the service layer changes but the Pydantic model fields are unaffected.

2. **`PackageOut.package_id` format.** The DDB sort key is `PKG#{n}` (e.g., `PKG#1`). This spec leaves `package_id` as the raw string. The service layer (FAC-009) may strip the `PKG#` prefix before populating `PackageOut.package_id`, or keep the full key. Either is valid from the model's perspective. The spec recommends stripping the prefix (return `"1"`, not `"PKG#1"`) for a cleaner API surface.

3. **`FacilityLocationListOut` cursor.** FAC-003 defines `FacilityLocationListOut` without a `next_cursor` field (a facility is expected to have O(100) locations, not millions). If FAC-004 finds that paginating locations is necessary, a `next_cursor: Optional[str] = None` field can be added to `FacilityLocationListOut` without breaking existing callers.

4. **`PicklistOut` embedded `lines` vs separate endpoint.** This spec embeds `lines: List[PickLineOut]` in `PicklistOut`. If FAC-008 finds that large orders produce too many lines to embed, a separate `GET /ui/fulfillment/picklists/{id}/lines` endpoint returning `List[PickLineOut]` can be added; the `PicklistOut` can then carry `line_count: int = 0` instead of the embedded list.

5. **`LotOut` / `SerialOut` — FAC-014 only.** These models are included in FAC-003 per the ticket description but they are gated behind `FACILITY_LOT_SERIAL_ENABLED` at the service layer (FAC-014). Defining the shapes now prevents a second `app/models.py` PR in Milestone 5. If FAC-014 is de-scoped, these two classes are dead code but cause no harm.

6. **`ReceiveIn.lines[n].serials` as `List[str]`.** Serial numbers in `ReceiveLineIn.serials` are plain strings. The `max_length=10_000` cap prevents pathological payloads. If serial numbers must be unique per SKU, that uniqueness constraint is enforced by the service layer (FAC-007) via a conditional put on `T.lot_serial`, not by Pydantic.

7. **Currency on `ShipmentIn`.** No `currency` field is defined on `ShipmentIn` or `ShipmentOut`. Shipping costs are not tracked in FAC-010 scope; if a shipping-cost ledger entry is added in a follow-up, `currency: str = "usd"` can be added to `ShipmentOut` without a breaking change.
