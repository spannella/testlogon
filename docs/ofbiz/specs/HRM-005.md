# HRM-005 — Position / job-title service

**Type:** Feature | **Priority:** P0 | **Estimate:** 2 days
**Milestone:** 2 — Employee & Position Service Core

---

## 1. Summary & Goal

HRM-005 extends `app/services/hr.py` (created by HRM-004) with the full CRUD and lifecycle service layer for **Position** records — the OFBiz-style job openings / filled roles that gate the Employment service in HRM-006. The deliverable is four service functions (`create_position`, `get_position`, `list_positions`, `update_position_status`) plus a custom exception class (`PositionInvalidTransitionError`) and the allowed-transition table that the router (HRM-009) maps to HTTP 409.

Positions are stored in the `hr` single-table (defined by HRM-002) under `PK=POSITION#{position_id}` / `SK=META`. Two GSIs serve different query shapes:

- **GSI1** (`GSI1PK` / `GSI1SK`) — status-filtered listing without a full-table scan.
- **GSI_CREATED** (`entity_type` / `created_at` numeric) — newest-first listing across all statuses.

No money moves in this ticket; no ledger is touched. The existing billing, cart, orders, and shop surfaces are byte-for-byte unchanged when `S.hr_enabled` is `False` (the default).

## 3. Data Model

HRM-005 introduces no new DynamoDB tables or GSIs — the `hr` table and all its indexes are defined in HRM-002. This section documents the exact item shapes HRM-005 reads and writes.

### 3.1 Position META item

Stored at `PK=POSITION#{position_id}` / `SK=META`.

| Attribute | DynamoDB type | Value |
|---|---|---|
| `PK` | S | `"POSITION#{position_id}"` |
| `SK` | S | `"META"` |
| `position_id` | S | `"POS_{sha256_hex_32}"` (deterministic) or `"POS_{uuid4_hex}"` (random) |
| `title` | S | Free text, max 200 chars |
| `department` | S (optional) | Free text, max 100 chars; absent when `None` |
| `status` | S | `"OPEN"`, `"FILLED"`, or `"CLOSED"` |
| `created_at` | N | Unix epoch seconds from `now_ts()` |
| `updated_at` | N | Unix epoch seconds from `now_ts()` |
| `GSI1PK` | S | `"POSITION#{status}"` e.g. `"POSITION#OPEN"` |
| `GSI1SK` | S | `"POSITION#{position_id}"` — lexicographically sortable for cursor pagination |
| `entity_type` | S | `"POSITION"` — GSI_CREATED partition key |
| `correlation_id` | S (optional) | Stored for auditability; absent when no correlation id was supplied |

**Rationale for `GSI1SK` being `POSITION#{position_id}` rather than a timestamp:** The ticket descriptor specifies `GSI1SK=POSITION#{position_id}` explicitly (HR_TICKETS.md:103). This enables pagination via `encode_cursor` on `GSI1SK`; since `GSI1` is queried for exact-status listings, the sort is stable and cursor-safe. The GSI_CREATED index (sorted by `created_at`) serves the newest-first listing use case separately.

**`created_at` as numeric (`N`):** Declared via `attr_types={"created_at": "N"}` in the `GSI_CREATED` TableDef (HRM-002). Without this, DynamoDB Local stores it as `S` and any integer comparison raises `ValidationException` (CLAUDE.md gotcha; confirmed pattern at `scripts/local-ddb-init.py:84`).

### 3.2 Status transition table

```python
_POSITION_ALLOWED_TRANSITIONS: Dict[str, Set[str]] = {
    "OPEN":   {"FILLED", "CLOSED"},
    "FILLED": {"CLOSED"},
    "CLOSED": set(),          # terminal state
}
```

Allowed paths: `OPEN→FILLED`, `OPEN→CLOSED`, `FILLED→CLOSED`. Attempting any other transition (including `CLOSED→*`, `FILLED→OPEN`) raises `PositionInvalidTransitionError`.

The router (HRM-009) maps `PositionInvalidTransitionError` → HTTP 409 with `code="position_invalid_transition"`.

## 4. API / Service Design

### 4.1 Service functions (`app/services/hr.py`)

All four functions are added to the existing `hr.py` created by HRM-004. They import `T` from `app.core.tables`, `now_ts` from `app.core.time`, `encode_cursor` / `decode_cursor` from `app.core.cursor`, and `audit_event` from `app.services.alerts`. They also use `hashlib` and `uuid` from the standard library.

---

#### `create_position`

```python
def create_position(
    title: str,
    department: Optional[str] = None,
    *,
    actor_sub: str,
    correlation_id: Optional[str] = None,
) -> Dict[str, Any]:
```

**Parameters:**
- `title` — job title string (1–200 chars; validated upstream by `CreatePositionIn`).
- `department` — optional org unit string (max 100 chars).
- `actor_sub` — `user_sub` of the admin performing the create; written to audit event.
- `correlation_id` — optional caller-supplied idempotency key; when present, `position_id = "POS_" + hashlib.sha256(correlation_id.encode()).hexdigest()[:32]`; when absent, `position_id = "POS_" + uuid4().hex`.

**Behaviour:**
1. Derive `position_id` from `correlation_id` (deterministic) or `uuid4()` (random).
2. Compute `ts = now_ts()`.
3. Build the full DDB item (all attributes from §3.1, `status="OPEN"` always on create).
4. Call `T.hr.put_item(Item=item, ConditionExpression="attribute_not_exists(PK)")`.
   - On `ClientError` with code `"ConditionalCheckFailedException"`: the `correlation_id` was already used — fetch and return the existing item via `get_position(position_id)` (idempotent replay).
5. Call `audit_event("position.created", actor_sub, position_id=position_id, title=title)` best-effort (wrapped in `try/except`).
6. Return the item dict.

**Returns:** `Dict[str, Any]` matching the `Position` schema.

---

#### `get_position`

```python
def get_position(position_id: str) -> Optional[Dict[str, Any]]:
```

**Behaviour:**
1. `resp = T.hr.get_item(Key={"PK": f"POSITION#{position_id}", "SK": "META"})`.
2. Return `resp.get("Item")` or `None` if not found.

**Returns:** `Dict[str, Any]` or `None`.

#### `list_positions`

```python
def list_positions(
    status: Optional[str] = None,
    *,
    cursor: Optional[str] = None,
    limit: int = 50,
) -> Dict[str, Any]:
```

**Parameters:**
- `status` — when supplied, query GSI1 with `KeyConditionExpression=Key("GSI1PK").eq(f"POSITION#{status}")`. When `None`, query GSI_CREATED with `KeyConditionExpression=Key("entity_type").eq("POSITION")`, `ScanIndexForward=False` for newest-first.
- `cursor` — opaque pagination cursor from a prior call; decoded via `decode_cursor(cursor)` into `ExclusiveStartKey`.
- `limit` — page size, default 50, caller may override.

**Behaviour:**

When `status` is supplied (status-filtered path):
```python
kwargs = {
    "IndexName": "GSI1",
    "KeyConditionExpression": Key("GSI1PK").eq(f"POSITION#{status}"),
    "Limit": limit,
}
if cursor:
    kwargs["ExclusiveStartKey"] = decode_cursor(cursor)
resp = T.hr.query(**kwargs)
```

When `status` is `None` (newest-first path):
```python
kwargs = {
    "IndexName": "GSI_CREATED",
    "KeyConditionExpression": Key("entity_type").eq("POSITION"),
    "ScanIndexForward": False,
    "Limit": limit,
}
if cursor:
    kwargs["ExclusiveStartKey"] = decode_cursor(cursor)
resp = T.hr.query(**kwargs)
```

Both paths build the result as:
```python
result = {"items": resp.get("Items", [])}
if resp.get("LastEvaluatedKey"):
    result["next_cursor"] = encode_cursor(resp["LastEvaluatedKey"])
return result
```

**IMPORTANT:** DynamoDB's `FilterExpression` does not reduce the page size before applying the limit (CLAUDE.md "DDB FilterExpression doesn't reduce page size" gotcha). The `status` filtering is done via GSI key condition (not `FilterExpression`), so this is not an issue here — the page size is honest.

**Returns:** `{"items": List[Dict], "next_cursor": Optional[str]}`.

---

#### `update_position_status`

```python
def update_position_status(
    position_id: str,
    new_status: str,
    *,
    actor_sub: str,
) -> Dict[str, Any]:
```

**Behaviour:**
1. Fetch existing item via `get_position(position_id)`. If `None`, raise `LookupError("position_not_found")` (router maps to 404).
2. `current_status = item["status"]`.
3. Validate: if `new_status not in _POSITION_ALLOWED_TRANSITIONS.get(current_status, set())`, raise `PositionInvalidTransitionError(f"{current_status}→{new_status}")`.
4. `ts = now_ts()`.
5. `T.hr.update_item(Key={"PK": f"POSITION#{position_id}", "SK": "META"}, UpdateExpression="SET #status = :status, updated_at = :ts, GSI1PK = :gsi1pk", ExpressionAttributeNames={"#status": "status"}, ExpressionAttributeValues={":status": new_status, ":ts": ts, ":gsi1pk": f"POSITION#{new_status}"})`.
   - Note: `GSI1PK` must be updated atomically with `status` so the GSI index stays consistent; a two-step approach would leave GSI1 stale between writes.
6. Call `audit_event("position.status_updated", actor_sub, position_id=position_id, old_status=current_status, new_status=new_status)` best-effort.
7. Fetch and return the updated item via `get_position(position_id)`.

**Returns:** Updated `Dict[str, Any]` matching the `Position` schema.

### 4.2 Router endpoints (HRM-009's scope, specified here for clarity)

HRM-009 creates `app/routers/hr.py` with `APIRouter(prefix="/ui/hr", tags=["hr"])`. The position-related endpoints are:

| Method | Path | Auth | Body | Response |
|---|---|---|---|---|
| `POST` | `/positions` | `require_admin_or_root` | `CreatePositionIn` | `PositionOut` (201) |
| `GET` | `/positions` | `require_admin_or_root` | query: `status`, `cursor`, `limit` | `{"items": List[PositionOut], "next_cursor": Optional[str]}` |
| `GET` | `/positions/{position_id}` | `require_admin_or_root` | — | `PositionOut` (404 if not found) |
| `PATCH` | `/positions/{position_id}` | `require_admin_or_root` | `UpdatePositionStatusIn` | `PositionOut` (409 on invalid transition) |

**Declaration order:** Static path `/positions` is declared before dynamic `/positions/{position_id}` in the router, following the CLAUDE.md gotcha about FastAPI declaration-order matching (the `/schedules` before `/{export_id}` example). The `POST /positions` and `GET /positions` decorators must appear before `GET /positions/{position_id}`.

**Error mapping in the router:**
```python
@hr_router.patch("/positions/{position_id}", response_model=PositionOut)
async def update_position_status_endpoint(
    position_id: str,
    body: UpdatePositionStatusIn,
    user: AuthenticatedUser = Depends(require_admin_or_root),
):
    _require_hr()
    try:
        item = hr_svc.update_position_status(
            position_id, body.status, actor_sub=user.sub
        )
    except LookupError:
        raise HTTPException(status_code=404, detail="position_not_found")
    except PositionInvalidTransitionError as exc:
        raise HTTPException(status_code=409, detail={"code": "position_invalid_transition", "message": str(exc)})
    return PositionOut(**item)
```

Auth: `require_admin_or_root` (imported from `app.auth.policy`, as used by `app/routers/job_dashboard.py:21`) enforces `Role.ADMIN` or `Role.ROOT` per `app/auth/roles.py:60`. Non-admin callers receive HTTP 403.

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent create (deterministic id replay)

When `correlation_id="create-cto-role-v1"` is supplied:
- `position_id = "POS_" + sha256("create-cto-role-v1").hexdigest()[:32]`
- First call: `put_item` succeeds → position created.
- Second call with identical `correlation_id`: `put_item` raises `ConditionalCheckFailedException` → service fetches the existing item and returns it unchanged. The router returns HTTP 200 (not 201) on the second call; the response body is the original position.

When `correlation_id` is omitted, each call produces a fresh `uuid4`-based `position_id` — no idempotency. This is the expected case for ad-hoc position creation.

### 5.2 Status transition DAG

```
         OPEN
        /    \
     FILLED  CLOSED
        \
        CLOSED
```

- `OPEN → FILLED`: position is assigned to a hire (called by HRM-006's `create_employment` via `update_position_status(position_id, "FILLED", actor_sub=...)`).
- `OPEN → CLOSED`: position cancelled before anyone was hired.
- `FILLED → CLOSED`: position closed after employment termination (HRM-006 calls this on terminate, best-effort, flag-gated — see §5.3).
- `CLOSED → *`: always illegal. `CLOSED` is the terminal state.
- `FILLED → OPEN`: illegal. A filled position cannot be re-opened; a new position must be created.

Any attempt to re-open a closed or filled position raises `PositionInvalidTransitionError`.

### 5.3 Position→FILLED side-effect (HRM-006 concern, documented here)

HRM-006's `create_employment` calls `update_position_status(position_id, "FILLED", ...)` after writing the employment record. This call is wrapped in `try/except` — if it fails (e.g. the position doesn't exist, or the position is already `CLOSED`), the employment is still created; the position status flip is best-effort and never blocks the primary employment write. HRM-005's `update_position_status` never calls back into HRM-006.

### 5.4 `None` department attribute

When `department=None` the DDB item does not store a `department` key at all (absent, not `None`/NULL). DynamoDB cannot store NULL as a string attribute for a GSI key, and `department` is not a GSI key — but the pattern of omitting absent optional fields prevents DynamoDB NULL-type surprises. The `get_position` return dict will lack a `department` key; the Pydantic `Position` model handles missing optional fields via `Optional[str] = None`.

### 5.5 Concurrent status update

Two admin users simultaneously calling `PATCH /positions/{id}` with `status=CLOSED` from `status=OPEN` is safe: DynamoDB's `update_item` is atomic at the item level. Both calls will succeed and the result is `CLOSED`. There is no optimistic-lock version check in HRM-005 (unlike `kyc_cases.py:252` which has an explicit `version` field). If the product requires conflict detection, a `version` field can be added in a follow-on ticket.

### 5.6 Large position lists

When a table grows beyond a few hundred positions the `limit` parameter caps each DynamoDB page. The `GSI1` query for status-filtered listing is honest (no `FilterExpression`), so DynamoDB returns exactly `limit` items per page. The `GSI_CREATED` query is likewise a direct key-condition with no post-filter, so pagination is reliable.

### 5.7 Flag-off behaviour

With `S.hr_enabled=False`, the router's `_require_hr()` guard fires before any service call. The service functions themselves are never invoked; `T.hr` is never called; no DynamoDB I/O occurs. The billing, catalog, orders, and messaging surfaces are byte-for-byte unchanged.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007: no dev/prod code branches

HRM-005 introduces no `if S.dev_mode:` branches, no mock paths, and no conditional imports. The four service functions behave identically in dev (DynamoDB Local on port 8001) and production (real DynamoDB). The only difference is that DynamoDB Local is started by `scripts/local-stack-up.sh` and real DynamoDB is reached via IAM credentials — transparent to the service layer.

### 7.2 Idempotency

- **Create**: `ConditionExpression="attribute_not_exists(PK)"` + `ConditionalCheckFailedException` → fetch-and-return. The same `correlation_id` from any caller (including a retry after a network timeout) produces the same `position_id` and the same response body.
- **Status update**: `update_position_status` is idempotent in the sense that calling it twice with the same `new_status` when the position is already in that status raises `PositionInvalidTransitionError` (because `FILLED → FILLED` is not in the transition table). This is intentional: callers should not re-apply the same status; if they need idempotency on status updates, they can check `get_position` first.

### 7.3 Security

- All endpoints are `require_admin_or_root` — regular users cannot create or modify positions. A non-admin caller receives HTTP 403 before any service code runs.
- `audit_event` is called on create and on every status change, creating an immutable trail in `T.alerts` (the audit log table).
- `position_id` is never user-supplied — it is derived from `sha256(correlation_id)` or `uuid4()`. Callers cannot inject a `position_id` that collides with another entity type (e.g. `EMPLOYMENT#...`) because the `PK` namespace prefix `POSITION#` is applied by the service, not the caller.
- `title` and `department` are persisted verbatim; they are free-text fields with no HTML rendering in the current admin UI (plain text in the React table). If the UI ever renders them as HTML, an XSS sanitisation step should be added in the router before they reach the service.

## 8. Backward Compatibility & Migration

### 8.1 Zero-change guarantee

With `HR_ENABLED=0` (the default), this ticket is byte-for-byte additive:

- `app/services/hr.py` gains new functions, but they are dead code when the router is inert.
- No existing DynamoDB table schema is changed.
- No existing service or router file is modified.
- No existing model in `app/models.py` is changed.
- No billing, cart, orders, or messaging code is touched.

### 8.2 Migration

There is no data migration in HRM-005. The `hr` DynamoDB table is created fresh by HRM-002 / `scripts/local-ddb-init.py` when `just restart` runs. Any deployment that has already created the `hr` table (from HRM-002) can immediately start calling `create_position` — there are no schema changes.

### 8.3 `GSI1SK` format commitment

The `GSI1SK` value `"POSITION#{position_id}"` is part of the cursor encoding. Once a cursor has been issued to a client, the `GSI1SK` format cannot change without invalidating existing cursors. HRM-005 establishes this format; future tickets must preserve it. The `position_id` prefix `"POS_"` is a convention (not enforced by DynamoDB) — changing it would require a migration.

## 10. Open Questions / Assumptions

1. **Assumption: `app/services/hr.py` is created by HRM-004.** HRM-005 appends to it. If HRM-004 is not merged when HRM-005 is implemented, `hr.py` must be created first (or HRM-005 creates it). The HRM-004 spec confirms the file is created there; this assumption tracks that dependency.

2. **Assumption: `T.hr` is the exact attribute name on the frozen `Tables` dataclass.** HRM-002 spec at §2.4 confirms `hr: Any` is added next to `contacts: Any` at `app/core/tables.py:102`. Tests must bind via `object.__setattr__(tables_mod.T, "hr", hr_tbl)` using this exact name.

3. **Assumption: `PositionInvalidTransitionError` is the only exception class needed from HRM-005.** The `LookupError` for "not found" is a stdlib exception; the router catches it and raises 404. If a separate `PositionNotFoundError(LookupError)` is preferred for clarity, that is a minor refactor with no behavioural change.

4. **Assumption: `position_id = "POS_" + sha256[:32]` format is final.** HRM-006 references `position_id` as a foreign key. Changing the prefix after any employments are created requires a migration. The `"POS_"` prefix is a convention — nothing enforces it at the DynamoDB layer.

5. **Assumption: concurrent `PATCH` status updates do not require optimistic locking.** The transition table is a DAG with a single terminal state. The worst case (two admins concurrently transitioning `OPEN→FILLED` and `OPEN→CLOSED`) results in one write winning and the other seeing an already-`FILLED` or already-`CLOSED` position on their next read. If the product requires "exactly one fill per position", a `ConditionExpression` on the current `status` attribute should be added to `update_item` in `update_position_status`. This is not specified by the ticket; it is flagged as an open question.

6. **Assumption: `actor_sub` is the admin's `user.sub` extracted from the `AuthenticatedUser` by the router.** All other audit-event callers in the codebase pass the session's `user_sub`; HRM-009 will pass `user.sub` from the `Depends(require_admin_or_root)` dependency.

7. **Open question: should `list_positions` with no `status` filter use GSI_CREATED (newest-first, unfiltered) or a paginated full scan?** The ticket specifies GSI_CREATED for newest-first listing. A full scan is avoided because it does not scale; the GSI_CREATED query is O(N_positions) but at least uses an index. This is the correct design; recorded here as an explicit choice.

8. **Open question: should the `PATCH /positions/{id}` endpoint be `PUT` (full replacement) or `PATCH` (partial update)?** HRM-009 specifies `PATCH` (only `status` changes). A future ticket could add `PATCH` support for `title` and `department` updates without changing the status semantics. Using `PATCH` now is the correct choice.
