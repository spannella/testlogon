# SHP-013 — Carrier-tracking poller integration for shipments

## 1. Summary & Goal

SHP-013 extends the existing carrier-tracking background poller
(`app/services/carrier_tracking_poller.py`) to also poll active `shipments` rows,
not just `purchase_transactions` rows. It reuses the **identical loop, cadence, and
batch-size settings** already in place for orders — no second timer, no new background
task, no new flag. It also adds a single on-demand admin endpoint,
`POST /ui/shop/tracking/shipments/{shipment_id}/poll`, that mirrors the existing
per-transaction endpoint at
`POST /ui/shop/tracking/transactions/{txn_id}/poll`
(`app/routers/carrier_tracking_poller.py:55`).

The result: a shipment whose carrier status has advanced (e.g. from `in_transit` to
`out_for_delivery`) will be updated in DynamoDB on the next poll cycle, and an admin
can force an immediate refresh for a specific shipment via the on-demand endpoint.
All carrier normalization, idempotency, and delivery-alert logic continues to flow
through the shared `app/services/carrier_tracking.py` helpers — nothing is
reimplemented.

Scope: changes are confined to `app/services/carrier_tracking_poller.py` (three new
functions) and `app/routers/carrier_tracking_poller.py` (one new endpoint). Nothing
else in the codebase is modified.

### 2.5 `T.shipments` table structure

Defined by SHP-002 (`docs/ofbiz/specs/SHP-002.md:§3.2`) and wired in
`app/core/tables.py`. Key attributes for the polling path:

| Attribute | Type | Notes |
|---|---|---|
| `shipment_id` (PK) | String | Hash key |
| `status` | String | State machine value; compared against `ACTIVE_TRACKING_STATUSES` |
| `tracking_number` | String | Top-level scalar; written by `transition_shipment → shipped`; must exist for polling |
| `carrier` | String | Lowercase carrier code written by the `→ shipped` transition (SHP-010 stores `carrier`, not `carrier_code` — see OQ-5) |

`tracking_number` is stored at the top level of the row (not inside a sub-map),
mirroring how `purchase_history.py:413–418` promotes it for the `TrackingIndex` GSI
[VERIFIED: `app/services/purchase_history.py:413–418`].
This means a simple `attribute_exists(tracking_number)` FilterExpression works on a
`T.shipments` scan — the same pattern used in
`get_pollable_orders` (`:139–141`).

### 2.6 `poll_all` and `carrier_polling_loop` must cover both tables

`carrier_polling_loop` (`:186`) calls `poll_all()` in its `while True` body.
SHP-013 extends `poll_all` to call both `get_pollable_orders` (existing) and
`get_pollable_shipments` (new). There is no second loop — the cadence, batch-size
setting, and error handling are identical for both populations.

The combined batch is split by a configurable ceiling: up to
`carrier_tracking_poll_batch_size` entries in total, distributed
`floor(cap / 2)` to orders and `floor(cap / 2)` to shipments (if both are
non-empty), with the remainder available for whichever collection returns fewer than
its half-cap. This prevents one large table from starving the other. The default
`carrier_tracking_poll_batch_size` of 50 means up to 25 orders + 25 shipments per
cycle. If shipping is not yet enabled (`S.shipping_enabled is False`),
`get_pollable_shipments` returns an empty list immediately, and `poll_all`'s
existing order-polling behavior is byte-for-byte unchanged.

## 3. Data Model

SHP-013 introduces **no new DynamoDB tables, no new settings keys beyond what
SHP-002 and the existing carrier poller already define, and no schema changes to
`scripts/local-ddb-init.py`**.

All tables consumed are:

| Table handle | Source ticket | Used by |
|---|---|---|
| `T.purchase_transactions` | pre-existing | `get_pollable_orders` (unchanged) |
| `T.shipments` | SHP-002 | `get_pollable_shipments` (new) |

The `shipments` table key schema and GSIs are reproduced from `SHP-002.md:§3.2`:

```
PK: shipment_id (String)
GSI_ORDER: order_id (S) / created_at (N)   ← attr_types={"created_at":"N"}
GSI_STATUS: status (S) / created_at (N)    ← same numeric sort key
```

`get_pollable_shipments` does a **scan** with `FilterExpression =
"attribute_exists(tracking_number)"`, not a GSI query. This mirrors
`get_pollable_orders` (`:139`) exactly. The GSI_STATUS index is not used here
because the active-status filter spans multiple status values and would require
separate queries per status (five values in `ACTIVE_TRACKING_STATUSES`) — the scan
with client-side status filter is the established pattern for this batch operation.

The on-demand poll endpoint fetches one shipment by `T.shipments.get_item(Key=
{"shipment_id": shipment_id})`, not by tracking number. This is a direct hash-key
lookup — O(1), no GSI required.

## 4. API / Service Design

### 4.1 New service functions in `app/services/carrier_tracking_poller.py`

#### 4.1.1 `get_pollable_shipments(limit: int) -> List[Dict[str, Any]]`

```python
def get_pollable_shipments(limit: int) -> List[Dict[str, Any]]:
    """Scan for shipments that have a tracking number and are still in flight.

    Short-circuits to [] when shipping is disabled so the scan is skipped
    entirely with the feature flag off.

    Mirrors get_pollable_orders — sparse scan for rows with a top-level
    ``tracking_number`` attribute, filtered client-side to active statuses.
    """
    from app.core.settings import S as _S
    if not getattr(_S, "shipping_enabled", False):
        return []

    shipments: List[Dict[str, Any]] = []
    scan_kwargs: Dict[str, Any] = {
        "FilterExpression": "attribute_exists(tracking_number)",
    }
    last_key = None
    while True:
        if last_key:
            scan_kwargs["ExclusiveStartKey"] = last_key
        resp = T.shipments.scan(**scan_kwargs)
        for item in resp.get("Items", []):
            status = (item.get("status") or "").strip()
            if status and status not in ACTIVE_TRACKING_STATUSES:
                continue
            shipments.append(item)
            if len(shipments) >= limit:
                return shipments
        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break
    return shipments
```

Key differences from `get_pollable_orders`:
- Reads from `T.shipments` (not `T.purchase_transactions`).
- The status field is a top-level scalar `item["status"]`, not nested under
  `item["shipping"]["status"]`.
- Guarded by `S.shipping_enabled` so that the scan is skipped when shipping is off,
  preventing a `ResourceNotFoundException` if `T.shipments` doesn't exist yet.

#### 4.1.2 `poll_shipment(shipment: Dict[str, Any]) -> Dict[str, Any]`

```python
def poll_shipment(shipment: Dict[str, Any]) -> Dict[str, Any]:
    """Poll the carrier for a single shipment and apply any status change.

    Returns the same result shape as poll_order:
        {
            "shipment_id": str,
            "polled": bool,
            "updated": bool,
            "old_status": str | None,
            "new_status": str | None,
            "reason": str,
        }
    Delegates the actual status-machine update to SHP-012's
    apply_tracking_result_to_shipment; this function only resolves the
    carrier state and normalises it.
    """
    from app.services.carrier_tracking import apply_tracking_result_to_shipment

    shipment_id = str(shipment.get("shipment_id") or "")
    carrier = (shipment.get("carrier") or "").lower().strip()
    tracking_number = (shipment.get("tracking_number") or "").strip()
    old_status = (shipment.get("status") or "").strip() or None

    base = {
        "shipment_id": shipment_id,
        "polled": False,
        "updated": False,
        "old_status": old_status,
        "new_status": old_status,
    }

    if not carrier or not tracking_number:
        return {**base, "reason": "no_tracking_info"}

    state = _lookup_carrier_state(carrier, tracking_number)
    if not state:
        return {**base, "reason": "no_carrier_data"}

    raw_status = state.get("status") or state.get("status_description") or ""
    normalized = map_carrier_status(carrier, raw_status)
    if (state.get("status") or "") in (
        ACTIVE_TRACKING_STATUSES | {"delivered", "exception", "returned"}
    ):
        normalized = state["status"]

    result = {
        "status": normalized,
        "status_description": state.get("status_description"),
        "estimated_delivery": state.get("estimated_delivery"),
        "delivered_at": state.get("delivered_at"),
        "events": state.get("events"),
    }

    info = apply_tracking_result_to_shipment(shipment, result)
    new_status = normalized
    if info is None:
        return {
            **base,
            "polled": True,
            "updated": False,
            "new_status": new_status,
            "reason": "unchanged",
        }

    return {
        "shipment_id": shipment_id,
        "polled": True,
        "updated": True,
        "old_status": old_status,
        "new_status": new_status,
        "reason": "updated",
    }
```

This mirrors `poll_order` (`:48`) line-for-line except:
- Keys into `shipment["status"]` (scalar) instead of `order["shipping"]["status"]`.
- Returns `shipment_id` as the identifier, not `txn_id`.
- Calls `apply_tracking_result_to_shipment` (SHP-012) instead of
  `apply_tracking_result`.

#### 4.1.3 Modified `poll_all`

The existing `poll_all(limit)` (`:160`) is extended in-place. The new version:

```python
def poll_all(limit: Optional[int] = None) -> Dict[str, Any]:
    """Poll a batch of in-flight orders AND shipments.

    Splits the batch budget evenly between orders and shipments; if either
    population returns fewer rows than its half-cap the remainder is available
    to the other. Shipment polling is a no-op (returns []) when
    S.shipping_enabled is False, preserving exact existing behaviour.
    """
    cap = limit or int(S.carrier_tracking_poll_batch_size)
    half = max(1, cap // 2)

    orders = get_pollable_orders(half)
    # Shipment slots: up to (cap - len(orders)) to consume any leftover budget.
    shipment_cap = max(0, cap - len(orders))
    shipments_batch = get_pollable_shipments(shipment_cap) if shipment_cap else []

    results: List[Dict[str, Any]] = []
    updated = 0

    for order in orders:
        try:
            res = poll_order(order)
        except Exception:
            logger.exception("Error polling order %s", order.get("txn_id"))
            continue
        results.append(res)
        if res.get("updated"):
            updated += 1

    for shipment in shipments_batch:
        try:
            res = poll_shipment(shipment)
        except Exception:
            logger.exception("Error polling shipment %s", shipment.get("shipment_id"))
            continue
        results.append(res)
        if res.get("updated"):
            updated += 1

    return {
        "checked": len(orders) + len(shipments_batch),
        "orders_checked": len(orders),
        "shipments_checked": len(shipments_batch),
        "updated": updated,
        "results": results,
    }
```

**Backward-compatibility note**: the `poll_all` response gains two additive keys
(`orders_checked`, `shipments_checked`). The existing `checked` and `updated` keys
and `results` list are byte-for-byte compatible. The admin endpoint at
`POST /poll-now` returns this dict directly; any consumer that only reads `checked`
/ `updated` / `results` is unaffected.

### 4.2 New router endpoint in `app/routers/carrier_tracking_poller.py`

#### On-demand per-shipment poll

```python
@carrier_tracking_poller_router.post("/shipments/{shipment_id}/poll")
async def ui_poll_shipment(
    shipment_id: str,
    user=Depends(require_admin_or_root),
) -> Dict[str, Any]:
    """Admin/root: poll the carrier for one shipment and apply any status change.

    Returns the poll outcome plus the refreshed shipment tracking view.
    """
    from app.core.settings import S as _S
    if not getattr(_S, "shipping_enabled", False):
        raise HTTPException(503, {"code": "feature_disabled",
                                   "message": "Shipping is not enabled"})

    item = T.shipments.get_item(Key={"shipment_id": shipment_id}).get("Item")
    if not item:
        raise HTTPException(404, "Shipment not found")

    poll = poll_shipment(item)

    # Re-fetch after potential update for the refreshed tracking view.
    refreshed = T.shipments.get_item(Key={"shipment_id": shipment_id}).get("Item") or item
    from app.services.carrier_tracking import build_tracking_url
    carrier = refreshed.get("carrier")
    tn = refreshed.get("tracking_number")
    tracking_view = {
        "shipment_id": shipment_id,
        "carrier": carrier,
        "tracking_number": tn,
        "tracking_url": build_tracking_url(carrier, tn) if carrier and tn else None,
        "status": refreshed.get("status"),
        "status_description": refreshed.get("status_description"),
        "estimated_delivery": refreshed.get("estimated_delivery"),
        "delivered_at": refreshed.get("delivered_at"),
        "carrier_events": refreshed.get("carrier_events"),
        "last_carrier_check": refreshed.get("last_carrier_check"),
    }
    return {"poll": poll, "tracking": tracking_view}
```

**Auth**: `require_admin_or_root` (same as `POST /poll-now`). This is an admin-only
operation — buyers can view tracking via the buyer read path on `shipments_router`
(SHP-011) but cannot trigger a force-refresh.

**No CSRF on this endpoint**: The endpoint is idempotent in the sense that repeated
calls are harmless (the carrier state and shipment state converge). More importantly,
it matches the existing `/transactions/{txn_id}/poll` which uses only
`require_ui_session` (not `require_admin_or_root_csrf`). The SHP-013 endpoint uses
`require_admin_or_root` (not `_csrf`) consistent with the `/poll-now` pattern —
Bearer-token API clients and E2E tests using the global `request` fixture call it
without CSRF headers.

**Route ordering**: The new path `/shipments/{shipment_id}/poll` uses the literal
segment `shipments` followed by a path parameter. Within the
`carrier_tracking_poller_router` (prefix `/ui/shop/tracking`) this does not conflict
with any existing route (`/transactions/{txn_id}/poll` and `/poll-now` are
orthogonal). No declaration-order guard is needed.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag off: shipping not enabled

When `S.shipping_enabled is False`:
- `get_pollable_shipments` returns `[]` immediately (the scan is skipped).
- `poll_all` processes zero shipments; its order-side behavior is byte-for-byte
  unchanged (same as before SHP-013 merged).
- `POST /shipments/{shipment_id}/poll` returns HTTP 503.

The existing `POST /transactions/{txn_id}/poll` and `POST /poll-now` are unaffected.

### 5.2 Flag off: carrier polling not enabled

When `S.carrier_tracking_poll_enabled is False`, `start_carrier_polling_task`
returns without creating the background task (`:207`). The `POST /poll-now` and
`POST /shipments/{id}/poll` endpoints still work on-demand — they do not check
`carrier_tracking_poll_enabled`. This mirrors the existing behavior where the admin
can call `POST /poll-now` even when the background loop is disabled.

### 5.3 Idempotency of `poll_shipment`

`apply_tracking_result_to_shipment` (SHP-012) short-circuits with `return None`
when `new_status == old_status` (same contract as `apply_tracking_result` at
`carrier_tracking.py:166–168`). A second `poll_shipment` call with no carrier-state
change returns `{updated: False, reason: "unchanged"}` and does not write to DDB.

### 5.4 Delivery alert exactly once

`apply_tracking_result_to_shipment` (SHP-012) calls `send_delivery_alert` only on
the `old_status != "delivered" → new_status == "delivered"` transition, matching
the behavior of `apply_tracking_result` at `carrier_tracking.py:192–194`. A second
poll of an already-delivered shipment returns `updated=False` before reaching the
alert logic.

### 5.5 Terminal shipment statuses

Shipments in `"delivered"`, `"returned"`, or `"cancelled"` are not in
`ACTIVE_TRACKING_STATUSES`. `get_pollable_shipments` filters them out client-side —
they are never passed to `poll_shipment`. The on-demand endpoint `POST
/shipments/{id}/poll` can still be called for terminal shipments (no guard at the
router level), but `poll_shipment` will find carrier data and call
`apply_tracking_result_to_shipment`, which itself checks whether the transition is
legal via `transition_shipment` — if already delivered, the status is unchanged and
the function returns `None` → `updated=False, reason="unchanged"`.

### 5.6 Shipment with no carrier data seeded

If the mock `_TRACKING_STATE` has no entry for `(carrier, tracking_number)`,
`_lookup_carrier_state` returns `None` and `poll_shipment` returns
`{polled: False, reason: "no_carrier_data"}`. This is not an error — it means the
carrier has not yet provided an update. The row is not touched.

### 5.7 Shipment with `carrier` field absent

A shipment that has `tracking_number` stored but no `carrier` (e.g. created before
the auto-detect fix landed) returns `{polled: False, reason: "no_tracking_info"}`.
`get_pollable_shipments` will include it in the batch (it has `tracking_number`),
but `poll_shipment` exits before touching DDB.

### 5.8 Error isolation per shipment

Each `poll_shipment` call is wrapped in `try/except Exception` inside the
`poll_all` loop, mirroring the order loop at `:173–175`. An exception in one
shipment's poll (e.g. a transient DDB error) is logged and skipped; subsequent
shipments in the batch are unaffected.

### 5.9 `T.shipments` not yet created

If SHP-002 has not been deployed and `T.shipments` doesn't exist,
`get_pollable_shipments` will raise a `ResourceNotFoundException` on the scan call.
The `S.shipping_enabled` guard prevents this: when the flag is off (the default with
SHP-002 not yet deployed), the scan is never attempted. Deploying SHP-002 first and
keeping `SHIPPING_ENABLED=false` until ready is the safe rollout sequence (see §8).

### 5.10 `poll_all` return-value change is additive

The two new keys `orders_checked` and `shipments_checked` are added to the
`poll_all` return dict. The existing admin endpoint `POST /poll-now` returns this
dict directly and will now include those keys. No existing client is expected to
break on extra response fields (FastAPI does not validate response shapes by default
unless a strict `response_model` is set, and the `/poll-now` handler returns a raw
`Dict[str, Any]`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No `dev_mode` branches

Neither `get_pollable_shipments`, `poll_shipment`, nor the new router endpoint
contains `if S.dev_mode:` conditional logic. The carrier mock state
(`_TRACKING_STATE` in `carrier_tracking_mock.py`) is already used by the existing
`poll_order` path in dev; `poll_shipment` reads from the same source via
`_lookup_carrier_state`. In prod, `_TRACKING_STATE` is always empty so
`_lookup_carrier_state` always returns `None` — the real carrier webhook path
(outside scope) would populate tracking status directly. Dev and prod code paths are
identical.

### 7.2 Idempotency

- **Background loop**: Each cycle calls `poll_all` which calls
  `apply_tracking_result_to_shipment` per shipment. Because
  `apply_tracking_result_to_shipment` short-circuits on `new_status == old_status`,
  repeated cycles with unchanged carrier state produce zero DDB writes.
- **On-demand endpoint**: Repeated POST calls to `/shipments/{id}/poll` with no
  carrier-state change return `updated=False` without writing. The response is stable.
- **Delivery alert deduplication**: `apply_tracking_result_to_shipment` (SHP-012)
  tracks `delivered_already = (old_status == "delivered")` before calling
  `transition_shipment` and skips `send_delivery_alert` on replay — same contract
  as the order path at `carrier_tracking.py:192–194`.

### 7.3 Security

- **Admin-only write path**: the on-demand `/shipments/{id}/poll` endpoint is gated
  by `require_admin_or_root` (`app/auth/policy.py:67` [VERIFIED]). A USER-role
  caller receives HTTP 403 before any DDB access.
- **Ownership not required**: unlike the transaction poll (`/transactions/{txn_id}/poll`
  which uses `require_ui_session` and is accessible to the owning buyer), the
  shipment poll is admin-only. Buyers do not have a polling path for shipments.
- **No PII in poll results**: `poll_shipment` returns `{shipment_id, polled, updated,
  old_status, new_status, reason}`. No address, customer name, or payment data is
  included. The `tracking_view` in the response contains `tracking_number` (not PII)
  and carrier event descriptions from the mock.
- **No CSRF**: Bearer-token admin callers are unaffected; cookie-based callers do not
  need CSRF for this endpoint because it uses `require_admin_or_root` (not `_csrf`),
  consistent with the existing `/poll-now` endpoint.

### 7.4 Billing ledger

No calls to `billing_shared.new_ledger_entry` or `refund_payment`. This ticket has
no money movement. Carrier status updates are purely informational.

## 8. Backward Compatibility & Migration

### 8.1 Existing order poller behavior unchanged with flag off

With `SHIPPING_ENABLED=false` (the current production default while SHP-001 through
SHP-012 are being deployed):

- `get_pollable_shipments` returns `[]` immediately.
- `poll_all` calls `get_pollable_orders(cap // 2)` as before (the cap is the same
  integer value — only split semantics changed, but `cap // 2` rounds to the same
  effective limit for most values of `CARRIER_TRACKING_POLL_BATCH_SIZE`).
- The `results` list in `poll_all` contains only order results. The new
  `orders_checked` / `shipments_checked` keys appear in the response but do not
  break existing consumers.

**Caution on batch size**: the existing `poll_all` used `cap` (the full batch size)
for orders. SHP-013 uses `cap // 2` for orders when both populations are active.
With `SHIPPING_ENABLED=false` (no shipments), `shipment_cap = cap - 0 = cap`, so
orders still receive `cap` slots. The order-side throughput only decreases when
shipping is enabled and shipments are present, which is intentional and expected.
If the order batch size must remain at `cap` even with shipping on, the operator
should double `CARRIER_TRACKING_POLL_BATCH_SIZE` (100 instead of 50).

### 8.2 Schema: no new tables, no new GSIs

`T.shipments` and its GSIs are defined entirely by SHP-002. SHP-013 adds no new
`TableDef` entries to `scripts/local-ddb-init.py` and no new table handles to
`app/core/tables.py` or fields to `app/core/settings.py`.

### 8.3 `poll_all` response shape

Two additive keys added (`orders_checked`, `shipments_checked`). The `POST /poll-now`
endpoint's raw dict response now includes these. Strictly additive — no existing key
removed or renamed.

### 8.4 Safe deployment sequence

1. Merge SHP-002 through SHP-012 with `SHIPPING_ENABLED=false`.
2. Merge SHP-013 with `SHIPPING_ENABLED=false` — order polling is byte-for-byte
   unchanged; `T.shipments` scan is never attempted.
3. Set `SHIPPING_ENABLED=true`. Shipment polling is now active on the next cycle.
4. Optionally set `CARRIER_TRACKING_POLL_ENABLED=true` to start the background loop.

## 10. Open Questions / Assumptions

**OQ-1 (`apply_tracking_result_to_shipment` signature)**: This spec assumes SHP-012
adds `apply_tracking_result_to_shipment(shipment: Dict, result: Dict) -> Optional[Dict]`
to `app/services/carrier_tracking.py` (or `app/services/shipments.py`). The function
must:
- Accept a `shipments` DDB item (keyed by `shipment_id`, not `user_sub`/`txn_id`).
- Apply the status change via `transition_shipment` (SHP-010).
- Return `None` on idempotent no-op (same status).
- Call `send_delivery_alert` once on `→ delivered`.

If SHP-012 uses a different name or module location, only the import statement in
`poll_shipment` needs to change.

**OQ-2 (Import location for `apply_tracking_result_to_shipment`)**: It may live in
`app/services/carrier_tracking.py` (alongside the order path) or in
`app/services/shipments.py` (closer to the state machine). This spec imports it as
`from app.services.carrier_tracking import apply_tracking_result_to_shipment` on the
assumption SHP-012 keeps carrier-tracking logic in the carrier_tracking module.
Adjust the import if SHP-012 places it in `shipments.py`.

**OQ-3 (Batch split semantics)**: The `cap // 2` split reduces the order batch to
half when shipping is enabled. If the team decides orders should retain priority
(e.g. always up to `cap` orders, shipments only if spare slots remain), replace the
split with:
```python
orders = get_pollable_orders(cap)
shipment_cap = max(0, cap - len(orders))
shipments_batch = get_pollable_shipments(shipment_cap)
```
This is actually the simpler version shown in the modified `poll_all` above — order
polling retains its full budget and shipments fill any remaining capacity. The spec
describes this as the default, but the exact split policy should be confirmed before
implementation.

**OQ-4 (`T.shipments` import in `carrier_tracking_poller.py`)**: Currently the
module imports `T` at the top level for `T.purchase_transactions`. Adding
`T.shipments` is a one-line addition (no new import needed). However, if `T.shipments`
is `None` (because SHP-002 hasn't been deployed), the `scan` call raises
`AttributeError`. The `S.shipping_enabled` guard in `get_pollable_shipments` prevents
this — `T.shipments` is never accessed when the flag is off.

**OQ-5 (Carrier field name: `carrier` vs `carrier_code`)**: SHP-002
(`docs/ofbiz/specs/SHP-002.md:§3.2`) uses `carrier_code` for the carrier identifier
on the `shipments` row. SHP-010 (`docs/ofbiz/specs/SHP-010.md:§3.2`) mentions
storing `carrier` (no `_code` suffix) on the `→ shipped` transition. This spec uses
`shipment.get("carrier")` to read the carrier value from the shipment item. If the
stored attribute name is `carrier_code`, the call should be
`shipment.get("carrier_code")`. Verify the actual stored attribute name in SHP-010's
implementation before coding `poll_shipment`.

**OQ-6 (`last_carrier_check` written by SHP-012 or SHP-013)**: The order path in
`apply_tracking_result` (`:179`) sets `shipping["last_carrier_check"] = now_ts()`.
The tracking view in the new endpoint includes `last_carrier_check`. This spec
assumes SHP-012's `apply_tracking_result_to_shipment` similarly writes
`last_carrier_check` to the shipment row. If it doesn't, the field will always be
`None` in the on-demand endpoint response — functional but missing the "last checked"
timestamp. Confirm with SHP-012 implementor.
