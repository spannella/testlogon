# MKT-014 — Marketing module tests (hermetic pytest + E2E)

## 1. Summary & Goal

MKT-014 is the test-completeness ticket for the entire OFBiz Marketing Campaigns module (MKT-001 through MKT-013). It delivers two layers of verification:

1. **Hermetic offline pytest suites** (`tests/test_mkt_campaigns.py`, `tests/test_mkt_lists.py`, `tests/test_mkt_segments.py`, `tests/test_mkt_tracking.py`, `tests/test_mkt_send.py`, `tests/test_mkt_flag_off.py`) — unit/integration tests that run without any real AWS, network, or dev stack. Each suite binds moto in-memory DynamoDB tables to the frozen `T` handles via `object.__setattr__` and calls service/router handler coroutines directly (never through `TestClient`).

2. **A Playwright E2E spec** (`frontend/e2e/marketing-campaigns.spec.ts`) — a browser-level regression suite covering the full end-to-end marketing workflow: campaign create → promo link → list/segment build → tracking-code mint → public visit redirect → send → attribution; with admin review as the root identity. The spec follows the session/CSRF/auth conventions established by `frontend/e2e/ads-accounts-campaigns.spec.ts`.

The tests assert all the correctness properties the ticket backlog specifies: idempotent create, state-machine legality, opt-out suppression, segment-snapshot immutability, tracking-code slug uniqueness, send dedup/replay safety, attribution rollup accuracy, and flag-off parity. Nothing in the existing ads/promo/cart-reminders/billing codepaths is touched.

## 5. Detailed Behavior & Edge Cases

### 5.1 Campaign CRUD and deterministic idempotency (`test_mkt_campaigns.py`)

**Normal create → get → list → update round-trip.** Create with a new `(owner_id, name, created_bucket)` produces a campaign_id `= sha256(owner_id + "\x00" + name + "\x00" + str(bucket))[:24]` and status `"draft"`. `get_campaign` returns the same item. `list_campaigns` returns it in the `ByOwnerCreatedAt` GSI order. `update_campaign` with non-status fields (`name`, `budget_cents`, `objective`) updates the row and advances `updated_at`.

**Idempotent re-create.** A second `create_campaign` call with the same owner, name, and within the same hourly bucket must return the existing item unchanged — specifically: the returned `campaign_id` equals the first call's value and DDB contains exactly one row for that PK/SK. This is the `attribute_not_exists(pk)` / `ConditionalCheckFailedException` → fallback-get path (`app/services/cart_reminders.py:198–211` pattern).

**Cross-owner isolation.** `get_campaign("bob_sub", alice_campaign_id)` returns `None`; `list_campaigns("bob_sub")` returns an empty list even when Alice's campaigns exist.

**Linked-entity validation.** Creating with a non-existent `ad_campaign_id` raises `HTTPException(422)`. Creating with a non-existent promo `code_id` in `promo_code_ids` raises `HTTPException(422)`. Creating with both valid and one invalid promo id raises `HTTPException(422)` (all-or-nothing validation).

**Attribution tie-out.** Seed an ad campaign in `T.ad_campaigns` with `lifetime_spent_cents=500`, `spent_today_cents=100`. Seed a promo code in `T.promo_codes` with two `REDEEM#` rows totalling 300 discount cents. Seed a tracking-code META with `visit_count=7`, `order_count=2`. Link all three to a marketing campaign. `compute_attribution` must return `{"ad_spend_lifetime_cents": 500, "ad_spend_today_cents": 100, "promo_total_discount_cents": 300, "promo_total_redemptions": 2, "visit_count": 7, "order_count": 2}` — cents-for-cents, no re-derivation. This is the attribution tie-out asserted by the MKT-005 spec.

### 5.2 State machine (`test_mkt_campaigns.py` — lifecycle section)

The marketing-campaign SM (MKT-006) is:
```
draft → scheduled → active → paused/completed → archived
draft → archived
scheduled → archived
paused → active
active → paused, completed, archived
completed → archived
```

Tests must cover:
- Every legal transition succeeds, writes the new status, and emits exactly one audit event.
- `draft → active` is illegal (must skip `scheduled`); expect `ValueError` / HTTP 409.
- `active → scheduled` is illegal; expect `ValueError` / HTTP 409.
- `archived → draft` is illegal (terminal status).
- Transitioning `draft → scheduled → active` with a linked promo code that has `active=False` or `expires_at < now` raises `HTTPException(422)`.
- Transitioning to `active` when `start_date > now` raises `HTTPException(422)`.
- Illegal transition leaves status unchanged — the item in DDB is re-read to confirm no write occurred.

### 5.3 Contact list membership and opt-out suppression (`test_mkt_lists.py`)

**Duplicate add is idempotent.** `add_member` twice with the same `party_id` leaves exactly one member row in `T.contact_lists`; `list_members` returns the party once.

**Opt-out suppression.** Seed an opt-out row for `party_b` in `T.cart_reminder_config` at `pk=OPTOUT#USER#party_b` / `sk=META` (prefix constant `_OPTOUT_PK_PREFIX = "OPTOUT#USER#"` at `app/services/cart_reminders.py:37` ✓) with `opted_out=True`. `list_members` returns both `party_a` and `party_b` (with `party_b.suppressed=True`). `list_members_for_send` returns only `party_a`. This is the shared "do-not-contact" gate from `cart_reminders.is_user_opted_out` (`app/services/cart_reminders.py:95` ✓).

**Contacts import dedup.** Seed three contacts for `owner` in `T.contacts`. Call `seed_from_contacts(owner, list_id)` twice. After the second call, `list_members` still returns exactly three rows (dedup on `party_id`).

**Remove.** After `add_member` then `remove_member`, `list_members` returns an empty list.

### 5.4 Segment evaluation and snapshot immutability (`test_mkt_segments.py`)

**Predicate matching.** Create a segment with one rule `{attribute: "order_count", operator: "gte", value: 2}`. Seed users in `T.orders` (via `GSI_USER` index): `alice` with 3 orders, `bob` with 1 order. `evaluate_segment` returns `[{"party_id": "alice", "opted_out": False}]`. `bob` is excluded.

**Unknown attribute → 422.** Creating a segment with `{attribute: "nonexistent_field"}` raises `HTTPException(422)`.

**Snapshot immutability.** `snapshot_segment` at `snap_ts_1` writes rows for `alice`. Later, `bob` gains 3 orders and a second `snapshot_segment` runs at `snap_ts_2`. `resolve_snapshot_members(segment_id, snap_ts_1)` still returns only `alice`; `resolve_snapshot_members(segment_id, snap_ts_2)` returns both `alice` and `bob`. The first snapshot is immutable.

**Opt-out in snapshot.** Seed `alice` as opted-out before snapshotting. `snapshot_segment` writes an `alice` row with `opted_out=True`. `resolve_snapshot_members` returns `alice` with `opted_out=True`; `send_campaign` (MKT-009) will suppress her.

### 5.5 Tracking code uniqueness and order idempotency (`test_mkt_tracking.py`)

**Slug uniqueness.** Create a tracking code with slug `"SUMMER2026"`. A second `create_tracking_code` with the same slug (different campaign_id) raises `HTTPException(409)`.

**Identical retry is idempotent.** A second `create_tracking_code` with the same slug AND same campaign_id returns the existing item (the `attribute_not_exists` + fallback-get path).

**Visit append.** `record_visit("SUMMER2026", party_id="alice", referrer=None)` appends a `VISIT#...` row. `record_visit` a second time appends a second row; `get_tracking_code` shows `visit_count=2`.

**Order idempotency.** `record_order("SUMMER2026", "order_001", campaign_id)` → `True`. A second call with the same `order_id` → `False` (silent no-op); `get_tracking_code` shows `order_count=1` (not 2).

**Promo reconciliation.** Seed two `REDEEM#alice#...` rows in `T.promo_codes` for promo `"pc_abc"`. After `link_promo_redemption("SUMMER2026", "pc_abc", "alice")`, `get_promo_stats("pc_abc")["total_redemptions"]` still returns 2 (unchanged). The linkage row exists in `T.tracking_codes` but `T.promo_codes` is unchanged.

**Public URL.** `get_tracking_url("SUMMER2026")` returns `f"{S.public_base_url}/ui/marketing/t/SUMMER2026"`.

### 5.6 Send dedup/replay (`test_mkt_send.py`)

**Recipient set.** Create a campaign with one contact list (members: `alice`, `bob`) and one segment snapshot (members: `alice`, `carol`). After dedup, the effective audience is `{alice, bob, carol}`. With `bob` opted out, `send_campaign` delivers to `{alice, carol}`. Patching `write_alert` (`app/services/alerts.py:356` ✓) and `send_alert_email` (`app/services/alerts.py:459` ✓) with recording mocks, assert exactly 2 write_alert calls and 2 send_alert_email calls — `bob` is excluded.

**Dedup of list + segment overlap.** `alice` appears in both the list and the segment snapshot; she should receive exactly one delivery, not two. Assert `write_alert` called once for `alice`.

**Replay idempotency.** Run `send_campaign` twice with the same snapshot_ts (simulating a cron retry). After the second run, `write_alert` is still called exactly 2 times total (not 4). The send-dedup rows in `T.marketing_campaigns` (using `attribute_not_exists(pk)` conditional puts keyed on `sha256(campaign_id + "\x00" + str(snap_ts) + "\x00" + party_id)[:24]`) prevent double delivery.

**Tracking link embedded.** When the campaign has a `tracking_code` set, the body passed to `send_alert_email` contains the string `"/ui/marketing/t/{code_slug}"`. When the campaign has a linked promo code, the body contains the promo code's `code` string (e.g., `"SAVE20"`). These assertions are made on the `body_text` captured by the mock.

**Flag off.** With `S.marketing_campaigns_enabled = False`, `send_campaign` raises `HTTPException(404)` (invisible-surface convention) and neither `write_alert` nor `send_alert_email` is called.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity in tests.** Every tested service function follows the same code path in dev and prod (no `if S.dev_mode` branch is added to marketing services). Tests confirm this by running with `S.dev_mode = False` (or with moto mocking the calls in both cases). There is no `_dev_path` vs `_prod_path` fork to test around.

**Billing neutrality.** `compute_attribution` and the attribution tests assert that `billing_shared.new_ledger_entry` (`app/services/billing_shared.py:224` ✓) is never called. A recording `side_effect` patch on `new_ledger_entry` (imported into `marketing_campaigns`) confirms zero invocations across all attribution-path tests.

**Money read-only assertion.** `attach_promo_code` / `detach_promo_code` tests assert `T.promo_codes.put_item` and `T.promo_codes.update_item` are never called. Only `T.marketing_campaigns.update_item` may be called. This is the "references but never owns" invariant.

**Idempotency proof.** Idempotency is not just documented — it is mechanically asserted: before and after a duplicate `create_campaign` or duplicate `record_order`, a `scan` of the relevant table must return exactly one item matching the key, not two.

**Opt-out as security invariant.** `list_members_for_send` and the `send_campaign` audience-resolution path are tested with an opted-out party: the party must not appear in the delivery set even if they are in both the contact list and the segment snapshot. This invariant is tested in `test_mkt_send.py` and `test_mkt_lists.py` independently.
