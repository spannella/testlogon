# ECM-011 — Cart UI — reservation & pricing-breakdown surfacing

## 1. Summary & Goal

ECM-011 updates two frontend pages — `frontend/src/pages/shop/Cart.tsx` and
`frontend/src/pages/shop/Checkout.tsx` — to consume the richer response shapes
delivered by ECM-009 and ECM-008:

1. **Pricing breakdown** — bind the cart total display to the full
   `CartPricingBreakdownOut` shape (subtotal, per-rule discount lines with rule
   names, final total) returned by `GET /ui/shoppingcart/carts/{id}/total` so
   that applied rule names and savings are visible in both the cart summary and
   the checkout order-review panel.

2. **Reservation & availability indicators** — per cart line item, surface a
   soft "Reserved for you" badge when ECM-008 has placed an active soft
   reservation, and a "Only N left" / "Selling fast" warning when live
   availability from ECM-005 drops to a low-stock threshold.

Both additions are gated on the same `STORE_INTEGRATION_ENABLED` master flag
used by every other ECM ticket. With it off (the default), `Cart.tsx` and
`Checkout.tsx` render byte-for-byte identically to today: the total card shows
a single scalar, no reservation badges appear, and no new API calls are made.

No new backend endpoints are introduced by this ticket; it is a pure frontend
change that adapts to the widened response models from ECM-009 (backend) and
ECM-013 (TypeScript types / wrappers), and consumes the new
`GET /ui/shoppingcart/carts/{id}/line-availability` endpoint introduced by
ECM-008/ECM-005 to surface per-SKU reservation + availability status.

## 4. API / Service Design

ECM-011 is frontend-only. This section documents the backend contract it
consumes and the new frontend wrappers it depends on (delivered by ECM-013).

### 4.1 Backend endpoint consumed: `GET /ui/shoppingcart/carts/{cart_id}/total`

**Delivered by**: ECM-009 (current endpoint: `app/routers/shoppingcart.py:169`,
function `ui_cart_total`, response_model currently `ShoppingCartTotalOut`
(`app/models.py:982`); ECM-009 widens this to `CartPricingBreakdownOut`).

**Response model** (ECM-003 / ECM-009):

```python
class AppliedRuleLineOut(BaseModel):
    rule_id: str
    rule_name: str
    discount_cents: int

class CartPricingBreakdownOut(BaseModel):
    cart_id: str
    subtotal_cents: int
    rule_discount_cents: int = 0
    applied_rules: list[AppliedRuleLineOut] = []
    promo_discount_cents: int = 0
    promo_code_id: Optional[str] = None
    final_total_cents: int
    currency: str = "USD"
    # backward-compat alias — total_cents == final_total_cents
    total_cents: int   # property or validator in ECM-009
```

When `STORE_APPLY_PRICING_RULES` is off, `applied_rules = []`,
`rule_discount_cents = 0`, `final_total_cents == subtotal_cents`,
`total_cents == final_total_cents` — identical to today's `ShoppingCartTotalOut`.

**Auth**: `require_ui_session` (`app/services/sessions.py:330`, imported by shoppingcart router), unchanged.

### 4.2 Backend endpoint consumed: `GET /ui/shoppingcart/carts/{cart_id}/line-availability`

**Delivered by**: ECM-008.

**Response** (when flag on):

```python
{
  "cart_id": str,
  "lines": [
    {
      "sku": str,
      "reservation_id": Optional[str],   # active reservation id for this cart+sku
      "reserved_qty": int,               # qty currently reserved
      "expires_at": int,                 # Unix ts; 0 if no reservation
      "available": int,                  # inventory.available post-reservation
      "on_hand": int,
      "low_stock": bool,                 # available <= reorder_point
      "status": str,                     # in_stock | low_stock | out_of_stock
    }
  ]
}
```

When `STORE_SHOW_LIVE_AVAILABILITY` is off, returns `{ cart_id, lines: [] }`.
Any inventory-service error degrades to `{ cart_id, lines: [] }` (no 500).

**Auth**: `require_ui_session` (`app/services/sessions.py:330`), unchanged.

### 4.3 Backend endpoint consumed: `GET /ui/store/config`

**Delivered by**: ECM-013 (or ECM-002).

**Response**:

{
  store_integration_enabled: boolean;
  store_apply_pricing_rules: boolean;

All fields default `false`. ECM-011 uses this to decide at runtime whether to

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off path — exact today's behavior

When `store_integration_enabled` is `false` (the default):

- `getStoreConfig` returns all flags as `false`.
- The `["cart-line-availability", cartId]` query is never enabled.
- `Cart.tsx` and `Checkout.tsx` render using only `total_cents` from
  `totalQuery.data`. The `applied_rules` field, if present on the wire, is
  ignored by the rendering code (conditional renders gated on
  `storeConfig.store_apply_pricing_rules`).
- No reservation badges, no availability warnings, no rule discount rows.
- The visual output is byte-for-byte identical to today.

### 5.2 Pricing breakdown display — Cart.tsx

When `storeConfig.store_apply_pricing_rules` is `true` and `totalQuery.data`
carries a non-empty `applied_rules` list:

**Total card** (replaces the current single `total_cents` line at
`Cart.tsx:325–343`):

```
Subtotal                          $xx.xx
  ─ [rule_name] discount          −$yy.yy    (one row per applied_rules entry)
  ─ Promo (CODE)                  −$zz.zz    (only if promo_discount_cents > 0)
Total                             $TT.TT
```

When `applied_rules` is empty and `rule_discount_cents == 0` (flag on but no
rule matched), the breakdown collapses: only "Total" is shown (same as today).
The layout shift is zero for flag-off and for carts with no matching rules.

When there are multiple rule lines, each is shown as a separate row with the
`rule_name` string from `AppliedRuleLineOut` and the per-rule `discount_cents`.
Green text and a `Tag` icon (already imported in `Checkout.tsx:10`) distinguish
discount rows from subtotal/total rows.

### 5.3 Pricing breakdown display — Checkout.tsx

The existing "Order Summary" card (`Checkout.tsx:248–278`) already renders a
promo-discount row at line 264. ECM-011 inserts rule-discount rows immediately
above the promo row (rules first, then promo, matching the stacking order from
ECM-009 §5.3):

```tsx
{storeConfig.store_apply_pricing_rules &&
  (total as CartPricingBreakdown)?.applied_rules?.map((rule) => (
    <div key={rule.rule_id} className="flex items-center justify-between text-sm text-green-600">
      <span><Tag className="inline h-3 w-3 mr-1" />{rule.rule_name}</span>
      <span>-{formatCents(rule.discount_cents)}</span>
    </div>
  ))}
```

The existing promo row (`Checkout.tsx:263–268`) is untouched. The "Total" row
at `Checkout.tsx:269` already uses `effectiveTotal`; ECM-011 extends that
computation:

```ts
const effectiveTotal = promoResult
  ? promoResult.final_price_cents
  : (storeConfig.store_apply_pricing_rules
      ? (total as CartPricingBreakdown)?.final_total_cents
      : total?.total_cents) ?? 0;
```

This ensures the total shown in the checkout confirm dialog and the "Place
Order" button label matches `CartPricingBreakdownOut.final_total_cents`, which
is the same value `purchase_cart` will charge (no client/server drift,
ECM-009's hard acceptance criterion).

### 5.4 Reservation badge — Cart.tsx per-line

When `storeConfig.store_cart_reservations_enabled` is `true`, each cart-line
row checks the `lineAvail` map for its SKU:

```ts
const lineAvail = lineAvailQuery.data?.lines ?? [];
const avail = lineAvail.find((l) => l.sku === item.sku);
```

**Cases**:

| Condition | Badge |
|---|---|
| `avail?.reservation_id` is set and `avail.expires_at > now` | Amber clock icon + "Reserved for you" text (subtle, below item name) |
| `avail?.low_stock === true` and `avail.available > 0` | Orange "Only {avail.available} left" badge (same style as `Catalog.tsx:181`) |
| `avail?.status === "out_of_stock"` | Red "Out of Stock" badge; qty +/− buttons disabled |
| No `avail` entry, or flag off | No badge (today's behavior) |

The reservation badge shows a countdown: `expires_at - Date.now()/1000` seconds
formatted as `"Reserved for {m}m {s}s"`. When the countdown reaches zero the
badge changes to "Reservation expired — item may sell out" in muted-foreground
styling. The expiry countdown updates via `setInterval` every 10 seconds (not
every second — avoids excessive re-renders for a long TTL).

### 5.5 Availability warning — Cart.tsx per-line

Low-stock and out-of-stock warnings reuse the exact same `Badge` variants and
color tokens used in `Catalog.tsx:180–189` and `ProductDetail.tsx:209–218` so
the visual language is consistent:

- `low_stock`: `variant="outline"` with `border-orange-500 text-orange-600`
  class (identical to `Catalog.tsx:181`, `ProductDetail.tsx:210`).
- `out_of_stock`: `variant="destructive"` (identical to `Catalog.tsx:186`,
  `ProductDetail.tsx:215`).

When `status === "out_of_stock"`, the quantity +/− stepper is disabled and the
"Proceed to Checkout" button gets a tooltip: "One or more items are out of
stock". The button remains enabled for `low_stock` (availability > 0 but
scarce).

### 5.6 Line-availability polling interval

The `["cart-line-availability", cartId]` query uses
`refetchInterval: 60_000` (60 seconds) when on the Cart page, so users see
availability changes without manual refresh. On the Checkout page the interval
is `30_000` (30 seconds, tighter because the user is closer to purchase). Both
use `staleTime: 0` so a manual refetch (e.g., after qty change) is always
fresh.

After a successful `updateQtyMutation` or `removeMutation`, `queryClient.
invalidateQueries({ queryKey: ["cart-line-availability", cartId] })` is called
alongside the existing `cart-items` and `cart-total` invalidations. This
ensures the reservation badge reflects the adjusted quantity immediately.

### 5.7 `getStoreConfig` error handling

If `GET /ui/store/config` fails (e.g., ECM-013 not yet deployed), the
`useQuery` error path sets `storeConfig` to a default-all-false object:

```ts
const storeConfig = storeConfigQuery.data ?? {
  store_integration_enabled: false,
  store_apply_pricing_rules: false,
  store_show_live_availability: false,
  store_cart_reservations_enabled: false,
};
```

This means the Cart/Checkout pages degrade gracefully to today's behavior when
the config endpoint is unavailable — no visible error, no broken UI.

### 5.8 `getCartLineAvailability` error handling

If the endpoint returns a network error or `lines: []`, the `lineAvail` map is
treated as empty: no badges are rendered, no availability checks block checkout.
This mirrors the `_safe_upstream` pattern used in backend ECM specs.

### 5.9 Checkout "Place Order" button and total drift prevention

The `purchaseMutation` at `Checkout.tsx:133` (verified) calls `purchaseCart(cartId, ...)`.
The `purchase_cart` backend re-computes the breakdown server-side (ECM-009),
so the charged total is always authoritative. The frontend total shown in the
confirm dialog is `effectiveTotal` (§5.3 formula) which matches
`CartPricingBreakdownOut.final_total_cents` — no drift. If the user adds/removes
items between viewing the total and clicking "Place Order", the backend
re-computes and the `purchased_total_cents` in the success state may differ from
what was shown; a "Total may have changed" note in the success card handles
this edge case (below the order ID line).

### 5.10 Checkout promo code + rules co-existence

The existing promo-code UI in `Checkout.tsx:281–344` (verified) is untouched. The `effectiveTotal`
formula (§5.3) stacks rule and promo discounts in the correct order:
`subtotal → rule discount → promo discount`. The "Apply" and "Remove" promo
buttons work as today. When a promo is applied after rules have already been
computed in `totalQuery.data`, the UI shows both discount rows:

```
Subtotal                      $100.00
  ─ Volume Discount           −$10.00    (rule)
  ─ Promo (SAVE10)            −$9.00     (promo on $90)
Total                          $81.00
```

The promo `final_price_cents` from `validatePromoCode` already takes
`item_price_cents = total?.total_cents` as its base (`Checkout.tsx:109`); that field is now
`final_total_cents` (post-rule). The existing `effectiveTotal` override at
`Checkout.tsx:96–98` is updated to use `final_total_cents` when rules are enabled (§5.3).

### 5.11 Mobile layout

The pricing breakdown rows in the total card use `flex items-center
justify-between` with `text-sm`, consistent with the existing promo row at
`Checkout.tsx:264`. On narrow viewports the rule name truncates with
`truncate max-w-[180px]`; a `Tooltip` wraps the name to show the full string.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity**: ECM-011 is pure frontend; it makes no `S.dev_mode`
conditional renders. The flag-gated behavior is uniform across dev and prod —
flags `false` in dev produce today's behavior in both environments. When flags
are `true` in dev (for E2E testing), the UI renders identically to prod.

**No billing fork**: ECM-011 never calls `new_ledger_entry` or any billing
service. The total it shows is derived from `CartPricingBreakdownOut` which is
itself derived from the existing single-entry ledger model (ECM-009 §7). The
ECM-009 backend is the authoritative source; the UI only mirrors the
server-computed value.

**Idempotency**: The `getCartLineAvailability` query is read-only. The
`useQuery` hook may call it multiple times (refetchInterval); each response
replaces the previous one in the React Query cache with no side effects. No
write path in ECM-011 is idempotency-sensitive.

**Session ownership**: All new endpoints (`line-availability`, `store/config`,
`/total`) are gated by `require_ui_session` on the backend. The frontend only
reads `cartId` from URL params (already checked by existing Cart/Checkout
logic) — no user can see another user's cart availability data.

**XSS / injection**: `rule_name` from `AppliedRuleLineOut` is rendered as
React text content (not `dangerouslySetInnerHTML`), so rule names with HTML
characters are escaped automatically by React.

**Expiry countdown timer**: Uses `setInterval` in a `useEffect` with proper
cleanup on unmount to avoid memory leaks. The interval fires every 10 seconds;
no performance concern for a short cart session.

## 8. Backward Compatibility & Migration

**Zero backend migration**: ECM-011 is a frontend-only ticket. No DynamoDB
tables, backend models, or settings keys change.

**Zero frontend migration**: All new rendering blocks are inside
`storeConfig.store_apply_pricing_rules ? ... : null` and
`storeConfig.store_cart_reservations_enabled ? ... : null` conditionals. With
flags off, the JSX evaluates to `null` and React renders nothing additional.
The existing `total_cents` read (`Cart.tsx:333`) continues to work because
`CartPricingBreakdownOut` (ECM-009) exposes `total_cents` as a backward-compat
alias for `final_total_cents`.

**Type widening is additive**: ECM-013 extends `CartTotal` with optional fields
(`applied_rules?: AppliedRuleLineOut[]`, `subtotal_cents?: number`, etc.). The
`getCartTotal` wrapper's return type becomes `CartPricingBreakdown` (a superset
of `CartTotal`). Existing callers that only read `total_cents` see no change.

**`just restart` safe**: Restarting with both new flags `false` (the default)
produces no behavioral change in cart or checkout. No DDB backfill required.

## 10. Open Questions / Assumptions

1. **Assumption: ECM-013 delivers `CartPricingBreakdown`, `LineAvailability`,
   `CartLineAvailabilityResp`, and `StoreConfig` TypeScript interfaces in
   `frontend/src/api/types.ts` before ECM-011 merges.** If ECM-013 is not yet
   merged, ECM-011 must either inline the type definitions temporarily or open a
   blocking dependency.

2. **Assumption: ECM-013 adds `getCartLineAvailability` and `getStoreConfig`
   wrappers to `frontend/src/api/endpoints/cart.ts`.** ECM-011 imports them
   from there; if they land in a different file, the import paths must be
   updated.

3. **Assumption: `CartPricingBreakdownOut.total_cents` (ECM-009) is a
   backward-compat alias for `final_total_cents`.** If ECM-009 does not
   include this alias, `Cart.tsx:333`'s existing `total.total_cents` read will
   break even with flags off. ECM-011 implementation must guard:
   `total.total_cents ?? total.final_total_cents`.

4. **Open question: Should the expiry countdown in the reservation badge
   be a live countdown (every second) or a rough indicator (every 10 seconds)?**
   This spec assumes 10-second polling for performance. If the product team
   wants a live per-second countdown, the `setInterval` interval is changed to
   `1000` ms; no other change required.

5. **Open question: Should the "Only N left" badge on Cart.tsx show the
   reservation-adjusted `available` count (post-reservation) or the raw
   `on_hand`?** This spec uses `avail.available` (post-reservation) from
   `line-availability`, which is the more accurate figure for the buyer:
   it reflects how many units remain after their own and others' active
   reservations. If product decides `on_hand` is less confusing, the badge
   reads `avail.on_hand` instead.

6. **Assumption: `GET /ui/store/config` is lightweight (no DDB calls,
   pure settings read).** If the endpoint performs any DDB I/O, a
   `staleTime: 5 * 60 * 1000` + `refetchOnWindowFocus: false` strategy is
   still appropriate.

7. **Open question: Does the "Proceed to Checkout" button need to be
   completely disabled when one item is out of stock, or only show a warning?**
   This spec disables the button and shows a tooltip. If the product team wants
   to allow checkout with a mix of in-stock and out-of-stock items (letting
   `purchase_cart` 409 server-side), the button should remain enabled and the
   badge is informational only.

8. **Assumption: The `line-availability` endpoint returns one entry per
   cart-item SKU (not per quantity).** If a SKU appears multiple times in the
   cart (different product_types but same sku string), the first matching entry
   is used. This is expected to be rare; file a follow-up if multi-line same-SKU
   carts become a real use case.
