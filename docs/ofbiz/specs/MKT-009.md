# MKT-009 — Segment/list-targeted campaign send via existing channels

## 1. Summary & Goal

MKT-009 delivers `send_campaign(campaign_id, owner_id, *, now)` in `app/services/marketing_campaigns.py`. Calling this function resolves the full recipient audience for a marketing campaign (union of all linked contact-list members and the latest segment snapshots for all linked segments), applies opt-out suppression, then delivers one alert and one email per eligible recipient using the identical plumbing already used by cart abandonment reminders: `alerts.write_alert` and `alerts.send_alert_email` (imported together at `app/services/cart_reminders.py:32`). Each delivery is idempotent per `(campaign_id, snapshot_ts, party_id)` — a tuple that produces a deterministic send-record ID — so replaying a send over the same snapshot never double-sends.

The campaign's linked tracking code (MKT-010) is embedded as a tagged URL in the message body. If a promo code is linked, its code string is included in the body so recipients can copy-paste it; redemption still flows through the unchanged `promo_codes.redeem_promo_code` path.

Everything is gated on `S.marketing_campaigns_enabled`. With the flag off `send_campaign` raises immediately and writes nothing.

### Send idempotency requirement

The ticket requires replay safety: "a re-run of the same snapshot does not double-send." The deterministic-id scheme from MKT-004 (`sha256(...)[:24]`) is extended to send records: `send_id = sha256(campaign_id + "\x00" + str(snapshot_ts) + "\x00" + party_id)[:24]`. A `ConditionExpression="attribute_not_exists(pk)"` put (same pattern as `_mark_token_consumed` at `app/services/cart_reminders.py:198–211`) enforces exactly-once delivery per triple.

### Audience resolution: contact-list members

`app/services/marketing_lists.py` (MKT-007) exposes `list_members_for_send(list_id)` — a paginated cursor over `T.contact_lists` using the `ByListJoinedAt` GSI (sort key `joined_at` numeric, declared `attr_types={"joined_at": "N"}` per MKT-002 spec `docs/ofbiz/specs/MKT-002.md:144`). This function already filters suppressed (opted-out) parties and returns only active members. MKT-009 calls it for each `contact_list_id` in the campaign.

### Audience resolution: segment snapshots

`app/services/party_segments.py` (MKT-008) exposes two functions for snapshot resolution:

- `list_snapshots(segment_id, owner_id, ...)` — queries `BySegmentSnapTs` GSI (PK=`segment_id`, SK=`snap_ts` N, `ScanIndexForward=False`) to find the latest `snap_ts` and its `snap_id` (`docs/ofbiz/specs/MKT-008.md:337–348`). MKT-009 calls this to get the most recent `(snap_ts, snap_id)` pair for each linked segment.
- `list_snapshot_members(segment_id, snap_id, owner_id, include_opted_out=False, ...)` — queries `PK=SEGMENT#{segment_id}#SNAP#{snap_id}` / `SK begins_with PARTY#` with optional `FilterExpression(opted_out=False)` (`docs/ofbiz/specs/MKT-008.md:350–366`). Returns `{"members": [SegmentMemberOut, ...], "cursor": str|None}`. MKT-009 calls this with `include_opted_out=False` for each segment.

**GSI name verified consistent**: Both MKT-002 (`docs/ofbiz/specs/MKT-002.md:160,269`) and MKT-008 (`docs/ofbiz/specs/MKT-008.md:106,118,348,566`) use `BySegmentSnapTs` for this GSI. The earlier claim that MKT-008 renamed it `BySnapshotTs` was incorrect; all references in the MKT-008 spec use `BySegmentSnapTs`. MKT-009 must use `BySegmentSnapTs`. RISK-1 (§12) is resolved: no conflict exists. (Pass 3 correction.)

`attr_types={"snap_ts": "N"}` declared per MKT-002 spec `docs/ofbiz/specs/MKT-002.md:162`.

## 3. Data Model

### No changes to existing tables

`T.alerts`, `T.cart_reminder_config`, `T.billing`, and `T.promo_codes` are read-only from MKT-009's perspective. The marketing campaigns, contact-lists, and party-segments tables (owned by MKT-002) are also read-only; MKT-009 reads `contact_list_ids`, `segment_ids`, `tracking_code`, `promo_code_ids` from the campaign item.

### New table: `MarketingCampaignSendLog`

Stores one row per `(campaign_id, snapshot_ts, party_id)` triple. Acts as a deduplication ledger for replay safety and as an audit trail.

Default table name: `MarketingCampaignSendLog` (env `DDB_MARKETING_SEND_LOG`).

| Row type | PK (S) | SK (S) | Notes |
|----------|--------|--------|-------|
| Send record | `CAMP#{campaign_id}` | `SEND#{send_id}` | One row per sent party |

Where `send_id = sha256(campaign_id + "\x00" + str(snapshot_ts) + "\x00" + party_id)[:24]`.

GSIs:

| Index name | PK (S) | SK (N) | Notes |
|------------|--------|--------|-------|
| `ByCampaignSentAt` | `campaign_id` | `sent_at` | All send records for a campaign, time-ordered |

`attr_types={"sent_at": "N"}` — `sent_at` is a numeric Unix timestamp used as the GSI sort key; without this declaration DynamoDB would store it as String, causing `ValidationException` on range queries (CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha).

Send record attributes:

```
pk            : "CAMP#{campaign_id}"
sk            : "SEND#{send_id}"
send_id       : str   — sha256[:24] of (campaign_id, snapshot_ts, party_id)
campaign_id   : str
party_id      : str   — the recipient's user_sub
snapshot_ts   : int   — Unix ts; 0 for list-only members (no snapshot)
source        : str   — "list" | "segment"
list_id       : str | absent   — when source="list"
segment_id    : str | absent   — when source="segment"
sent_at       : int   — now_ts() at send time; GSI ByCampaignSentAt sort key
alert_id      : str | absent   — returned by write_alert
email_sent    : bool  — True if send_alert_email was called for this party
```

### `_resolve_audience` internal helper

```python
def _resolve_audience(
    campaign: dict,
    snapshot_ts: int,
) -> Iterator[tuple[str, str, str]]:
    """Yield (party_id, source, source_id) for all non-suppressed recipients.

    Deduplication across lists and segments is enforced by a seen set so
    the same party_id is yielded at most once regardless of how many
    lists/segments they appear in.
    """
```

Iteration order:
1. For each `list_id` in `campaign["contact_list_ids"]`: paginate `list_members_for_send(list_id)` — yields `(party_id, "list", list_id)`.
2. For each `segment_id` in `campaign["segment_ids"]`: call `list_snapshots(segment_id, owner_id=owner_id, limit=1)` to get the latest snapshot's `(snap_ts, snap_id)`, then paginate `list_snapshot_members(segment_id, snap_id, owner_id=owner_id, include_opted_out=False)` — yields `(party_id, "segment", segment_id)`. Per `docs/ofbiz/specs/MKT-008.md:350–366`, each page returns `{"members": [...], "cursor": ...}`; pagination loops until `cursor` is `None`.

The cross-source `seen: set[str]` is maintained in `_resolve_audience`. If a `party_id` appears in both a list and a segment, the first source wins and the duplicate is counted under `total_skipped`.

### `_try_send_one` internal helper

```python
def _try_send_one(
    *,
    campaign_id: str,
    party_id: str,
    source: str,
    source_id: str,
    snapshot_ts: int,
    subject: str,
    body_text: str,
    dry_run: bool,
    now: int,
) -> tuple[bool, bool]:
    """Attempt idempotent send to one party.

    Returns (sent, skipped).
    sent=True means a new alert+email was delivered.
    skipped=True means already sent (dedup hit) or opted-out.
    Raises on hard errors (DDB unavailable).
    """
```

Logic:
1. Compute `send_id = sha256(campaign_id + "\x00" + str(snapshot_ts) + "\x00" + party_id)[:24]`.
2. If `dry_run`: return `(True, False)` without any writes.
3. Attempt `T.marketing_send_log.put_item(Item={...}, ConditionExpression="attribute_not_exists(pk)")`. On `ConditionalCheckFailedException` → `return (False, True)` (already sent).
4. Opt-out check: `is_user_opted_out(party_id)` — if True → delete the send-log row just written and `return (False, True)`. (Delete on opt-out instead of checking before put avoids a race where the user opts-out between the opt-out check and the put.)
5. Look up email: `profile = get_profile(party_id)`. Extract `email = profile.get("email") or profile.get("displayed_email")`.
6. Call `write_alert(party_id, event="marketing.campaign.send", outcome="sent", title=subject, details={"campaign_id": campaign_id, "source": source, ...}, action_url=tracking_url)`.
7. If `email`: call `send_alert_email([email], subject=subject, body_text=body_text)`.
8. Update the send-log row: `SET alert_id = :aid, email_sent = :sent`.
9. Return `(True, False)`.

## 5. Detailed Behavior & Edge Cases

### Campaign status guard

`send_campaign` raises `HTTPException(409, "campaign must be active to send")` if `campaign["status"]` is not `"active"`. This prevents sending from `draft`, `paused`, `completed`, or `archived` campaigns. The check mirrors the "activated promo" guard in MKT-006 (`transition_status` validates `promo_codes.get_promo_code(...)[" active"]` before `→ active`).

### Empty audience

When the campaign has no `contact_list_ids` and no `segment_ids`, `_resolve_audience` yields nothing. The function returns `CampaignSendResult(total_resolved=0, total_sent=0, ...)` without error. This is normal for a newly-assembled campaign being validated.

### Segment with no snapshot yet

If `list_snapshots(segment_id, owner_id, limit=1)` returns an empty `snapshots` list (no snapshot materialized by MKT-008 yet), MKT-009 skips that segment and adds a per-segment warning to the send result's `details` (surfaced as a structured list `skipped_segments: list[str]` on `CampaignSendResult`). The send is not aborted — other lists/segments still proceed. This ensures partial audience availability does not block the entire send.

### `snapshot_ts` value for list-only sends

When the campaign has contact lists but no segments, there is no single `snap_ts` from a segment materialization. MKT-009 sets `snapshot_ts = now` (the `now` parameter passed into `send_campaign`, defaulting to `now_ts()`). This makes the idempotency key `(campaign_id, now, party_id)` which is unique per send invocation. Callers who want strict replay safety for list-only campaigns must pass the same `now` value on the retry; the endpoint sets `now = now_ts()` at request time and surfaces `snapshot_ts` in `CampaignSendResult` so the caller can record it.

When segments are present, `snapshot_ts` is the minimum `snap_ts` across all linked segments (the oldest materialized snapshot timestamp). This ensures the dedup key is stable across retries as long as no new snapshot is materialized between the original send and the retry. If a new snapshot is materialized mid-send, the next call will use a different `snapshot_ts` and re-send to the updated membership — which is the desired behavior.

### Opted-out party after list membership

`list_members_for_send` (MKT-007) already filters suppressed parties using `is_user_opted_out` at list-build time. MKT-009 re-checks opt-out inside `_try_send_one` after the dedup put to close the race where a party opts out between the audience scan and the per-party send. The second check adds at most one extra DDB read per recipient; its cost is acceptable.

### Alert write failure

`write_alert` wraps the DDB `put_item` in `try/except Exception: pass` (`app/services/alerts.py:425–428`), so a table-unavailable error is silently swallowed and the function **still returns `{"alert_id": ..., "ts": ...}`**. The only case where `write_alert` returns `None` is when `S.alerts_enabled` is `False` (early return at `app/services/alerts.py:367–368`). `_try_send_one` treats `write_alert` returning `None` (alerts disabled) as a soft failure: it still attempts `send_alert_email` (email is independent of in-app alerts), increments `total_errors`, and leaves the send-log row in place (so a replay does not retry). This matches the cart-reminder pattern where email is sent regardless of whether the in-app alert write succeeded.

### Email address absent

If `profile.get("email")` and `profile.get("displayed_email")` are both absent/falsy, `send_alert_email` is skipped. The send-log row is still written with `email_sent=False`. The in-app alert is the primary channel; email is best-effort.

### No promo code in body when multiple promo codes are linked

MKT-009 embeds only the first promo code (`promo_code_ids[0]`) in the message body. If multiple promo codes are linked, the others are silently ignored for body construction. This is a known limitation recorded in Section 10 (Open Questions).

### `dry_run=True` semantics

With `dry_run=True`, `_resolve_audience` is still called (so audience counts are accurate), but no `put_item` to `T.marketing_send_log` is executed, no `write_alert` is called, and no `send_alert_email` is called. `CampaignSendResult.dry_run` is set to `True`. Useful for the frontend to preview the audience size before committing to a send.

### Cross-list deduplication

The `seen: set[str]` in `_resolve_audience` is held in memory for the duration of a single `send_campaign` call. For a campaign with millions of recipients this set grows proportionally — estimated 50 bytes per UUID, so 1 million recipients ≈ 50 MB. This is acceptable for current scale. A DDB-based dedup set is noted in Section 10 as a future consideration.

### Pagination and the DDB FilterExpression caveat

Both `list_members_for_send` (MKT-007) and `resolve_snapshot_members` (MKT-008) must paginate via `LastEvaluatedKey`. Per CLAUDE.md: "DDB FilterExpression doesn't reduce page size — DynamoDB fetches up to 1 MB before applying FilterExpression." Both callers loop over `LastEvaluatedKey` to avoid silently missing recipients beyond the first page.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

`write_alert` and `send_alert_email` both already branch on `S.dev_mode` internally (`send_alert_email` writes to `S.dev_email_log` in dev, calls SES in prod — `app/services/alerts.py:462–468`). MKT-009 calls these functions without any `S.dev_mode` branch of its own. The send-log DDB writes go to DynamoDB Local in dev and real DynamoDB in prod — the same client path, no divergence (SECOPS-007 parity).

`is_user_opted_out` reads `T.cart_reminder_config` with `get_item` — identical behavior dev and prod.

`get_tracking_url` (MKT-010) builds the URL from `S.public_base_url` (`app/core/settings.py:349`) which is `http://localhost:8000` in dev and the public HTTPS domain in prod. No dev branch needed.

### Idempotency

Idempotency is enforced at three levels:

1. **Per-recipient dedup**: `T.marketing_send_log.put_item(..., ConditionExpression="attribute_not_exists(pk)")`. A second call with the same `send_id` fails the condition and returns `(False, True)` (skipped). The key is `sha256(campaign_id + "\x00" + str(snapshot_ts) + "\x00" + party_id)[:24]` — deterministic given the same inputs.

2. **Snapshot stability**: Segment snapshots are immutable once written (MKT-008: "re-snapshotting creates a new immutable snapshot"). Replaying a send over the same `snapshot_ts` sees the same segment membership.

3. **Audit idempotency**: `audit_event` in `app/services/alerts.py:644` writes a new row every time it is called (no dedup). This is intentional — audit events are append-only logs. Replaying a send produces a second audit event, which is correct (it records that a retry occurred).

### Security

- **Ownership enforcement**: `send_campaign` verifies `campaign["pk"] == f"OWNER#{owner_id}"` before reading any audience data. A call with a mismatched `owner_id` surfaces as 404 from the router's `_require_campaign_owner` helper (the same pattern as `ads.py:67–78`).
- **CSRF**: The `POST /ui/marketing/campaigns/{id}/send` endpoint uses `Depends(require_ui_session)` which enforces CSRF for cookie-auth non-GET requests (CLAUDE.md "CSRF" section). Bearer-auth callers skip CSRF (existing framework behavior).
- **Opt-out enforcement**: `is_user_opted_out` is called inside `_try_send_one` after every dedup put, so a user who opts out between audience scan and send does not receive a message.
- **No money writes**: MKT-009 never calls `new_ledger_entry` or any payment function. Marketing spend is attribution-only (read via `compute_attribution` in MKT-005). The GL is untouched.
- **Profile email access**: `get_profile` is called for each recipient to obtain their email address. This is the same access pattern as `_send_stage_reminder` at `app/services/cart_reminders.py:371`. The email address is used transiently within the function and is not persisted to the send-log.

## 8. Backward Compatibility & Migration

### No existing behavior changes

All changes are additive:
- One new DDB table (`MarketingCampaignSendLog`).
- One new settings key (`marketing_send_log_table_name`).
- One new table handle (`T.marketing_send_log`).
- New function `send_campaign` in `app/services/marketing_campaigns.py`.
- New Pydantic models `CampaignSendIn` and `CampaignSendResult` in `app/models.py`.
- One `message_body_template` optional field on `MarketingCampaignCreateIn` / `MarketingCampaignUpdateIn` — additive, defaults to `None`; existing campaign items without this attribute are handled by `campaign.get("message_body_template")` returning `None`, which triggers the default body template.

No existing routers, services, or DDB tables are modified. With `MARKETING_CAMPAIGNS_ENABLED=0` (the default on a fresh deployment) the new send-log table is created (it is always in `_table_defs()`) but never written to.

### DynamoDB table creation

`just restart` recreates all tables from `_table_defs()`. The new `MarketingCampaignSendLog` `TableDef` is picked up automatically. In production, a new `CreateTable` call must precede the code deployment; the table can be created with zero capacity-unit impact since it starts empty.

### `message_body_template` on existing campaigns

Existing campaigns have no `message_body_template` attribute. The `campaign.get("message_body_template")` call returns `None`, which falls through to the default body template in `_build_message_body`. No migration or backfill is needed.

## 10. Open Questions / Assumptions

1. **Assumption**: `message_body_template` field is added to `MarketingCampaignCreateIn`/`UpdateIn` as part of MKT-009 (since it is only needed for send). If MKT-003 is already merged without it, a targeted `UpdateIn` extension is needed. This is a minor additive change and does not affect MKT-003 round-trips.

2. **Assumption**: MKT-008's `party_segments.py` exposes `list_snapshots(segment_id, owner_id, ...)` (returning newest-first pagination with `snap_ts`/`snap_id` per row) and `list_snapshot_members(segment_id, snap_id, owner_id, include_opted_out=False, ...)` (returning `{"members": [...], "cursor": ...}`). Per `docs/ofbiz/specs/MKT-008.md:337–366`, these are the frozen interfaces. MKT-009 must use `snap_id` (not `snap_ts`) as the key to `list_snapshot_members`.

3. **Assumption**: MKT-007's `marketing_lists.py` exposes `list_members_for_send(list_id) -> Iterator[str]` (yields `party_id` strings, not `ContactListMemberOut` objects) that already filters opted-out parties live. Per `docs/ofbiz/specs/MKT-007.md:218–225`, this is the frozen interface. MKT-009 consumes `party_id` strings directly from this iterator.

4. **Corrected (pass 3)**: MKT-010's `tracking_codes.py` does NOT expose `get_tracking_url(code_slug)`. MKT-010 only exposes `get_tracking_code(code_slug)` (returns item dict or None). The tracking URL is built inline by MKT-009: `f"{S.public_base_url}/ui/marketing/t/{tracking_code}"`. No import of a URL-builder from `tracking_codes` is needed; a guard on `if campaign.get("tracking_code"):` is sufficient.

5. **Multiple promo codes**: Only the first `promo_code_ids[0]` is embedded in the message body. If the use-case demands multiple codes, the body template should be updated. This is deferred to a follow-up (MKT-009b or product decision).

6. **Large audiences and in-memory dedup**: The `seen: set[str]` approach works for campaigns up to ~1 million unique recipients. For larger audiences, a DDB-backed bloom filter or sorted-set approach would be needed. Current customer-base scale makes this a future concern.

7. **Send concurrency**: No distributed lock is taken before `send_campaign`. Two simultaneous calls with the same `snapshot_ts` will both attempt the per-party dedup puts and the second will get `ConditionalCheckFailedException` for each recipient that the first already wrote. This is correct behavior (idempotency holds), but the second call will report `total_sent == 0, total_skipped == N` which may confuse callers. A campaign-level lock row (or a `ConditionExpression` on the campaign status) is a follow-up consideration.

8. **Rate limiting on `write_alert`**: `write_alert` calls `sse_publish_alert` internally which is a best-effort fire-and-forget. Sending to 10,000 recipients triggers 10,000 SSE publishes. This is consistent with how cart reminders work at scale. If this becomes a bottleneck, a batch-publish path is a backend concern outside MKT-009.

9. **`snapshot_ts` for list-only campaigns and replay**: The spec sets `snapshot_ts = now` for list-only sends, making the dedup key time-dependent. A true list-only replay requires the caller to pass the original `now` value. The frontend send-log endpoint (`GET /ui/marketing/campaigns/{id}/send-log`) should surface `snapshot_ts` from the first send so the admin can pass it on a targeted retry. This endpoint is designed in MKT-011.
