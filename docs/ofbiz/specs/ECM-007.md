# ECM-007 — Storefront variant picker & live-availability UI

**Type:** Feature | **Priority:** P1 | **Estimate:** 4 days
**Dependencies:** ECM-006 (catalog router enrichment), ECM-013 (TS types & endpoint wrappers)

---

## 1. Summary & Goal

ECM-007 updates the storefront React pages to consume the variant topology and live-availability data that the backend integration layer (ECM-004 through ECM-006) exposes, when `STORE_INTEGRATION_ENABLED` and `STORE_VARIANT_SELECTION_ENABLED` are on.

The four concrete deliverables are:

1. **Variant picker** (`frontend/src/pages/shop/ProductDetail.tsx`) — a set of option-group selectors (one per feature category) that resolves the current combination to a `StorefrontVariant`. Selecting a variant updates the displayed price, the availability badge, and the SKU sent in the `addToCartMutation` payload. When no variant is yet selected, the Add-to-Cart button is disabled.

2. **Live-availability badges** — the card badge in `Catalog.tsx:180–192` <!-- VERIFIED --> and the detail badge in `ProductDetail.tsx:209–218` <!-- VERIFIED --> bind to `item.availability.stock_status` (when the `availability` field is non-null) instead of the scalar `item.stock_status`. The disabled state of the Add-to-Cart button at `ProductDetail.tsx:267` <!-- VERIFIED --> is extended to also disable when the resolved variant's availability `available` is 0.

3. **Flag guard** — all new UI is conditional on the integration flag read from a new `VITE_STORE_INTEGRATION_ENABLED` env var (mirroring the `VITE_INVENTORY_RESERVATIONS_ENABLED` pattern at `frontend/src/lib/featureFlags.ts:161`). With the flag off, `ProductDetail.tsx` and `Catalog.tsx` render exactly as they do today — no picker, no extra badge logic, no new API calls.

4. **TS types** (ECM-013 dependency) — `CatalogItem` in `frontend/src/api/types.ts:2135` gains two optional additive fields; `CartItemIn` at `types.ts:2061` gains an optional `variant_id` field; new `StorefrontVariant` and `StorefrontAvailability` interfaces are added. These changes are additive and backward-compatible with all existing callers.

### 4.4 Variant picker — option-group UI

The picker renders one row per unique feature-category name, derived from the `variants` list. No new shadcn component is needed; the existing `Badge` component (currently rendering attribute badges at `ProductDetail.tsx:225–233`) is reused for option value buttons. The option-group selector uses the existing shadcn `Button` component in a `flex-wrap gap-2` container.

Algorithm to derive option groups from variant list:

```ts
function buildOptionGroups(variants: StorefrontVariant[]): Record<string, string[]> {
  const groups: Record<string, Set<string>> = {};
  for (const v of variants) {
    for (const [key, val] of Object.entries(v.option_selections)) {
      if (!groups[key]) groups[key] = new Set();
      groups[key].add(val);
    }
  }
  return Object.fromEntries(
    Object.entries(groups).map(([k, s]) => [k, Array.from(s)])
  );
}
```

Current selections are stored as `selectedOptions: Record<string, string>` in component state alongside `selectedVariantId`. Selecting a combination calls `resolveVariant(variants, selectedOptions)` to find a matching variant. The picker resets `selectedVariantId` and `selectedOptions` when `item` changes (i.e., when the user navigates between products without leaving the page — `useEffect([itemId])`).

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag off — zero behavioral change

When `VITE_STORE_INTEGRATION_ENABLED` is `false` (the compile-time default):

- `variants` is always `null`; the picker section renders nothing.
- `displayPrice`, `displayStockStatus`, `displayStockCount` fall through to the existing `item.*` scalar fields.
- The Add-to-Cart button uses `item.stock_status === "out_of_stock"` exactly as today (`ProductDetail.tsx:267`).
- `Catalog.tsx` badges bind to `item.stock_status` and `item.stock_count` exactly as today (`Catalog.tsx:180–192`).
- No new state variables are allocated; the `selectedVariantId` and `selectedOptions` state declarations are inside a conditional branch `if (isStoreVariantPickerEnabled())` so they are compile-dead when the flag is off.

### 5.2 Integration on but no variants (non-virtual product)

When the backend returns `item.variants === null` (a flat/standalone product), the picker section is skipped: `variants` is `null`, so the picker block does not render. The `displayPrice` / `displayStockStatus` fall through to the scalar fields. The Add-to-Cart button works as today, sending `sku: item.item_id`.

This case handles all pre-existing catalog items (which have no `product_type="virtual"` marker), ensuring ECM-007 is completely inert for them even with the integration flag on.

### 5.3 Virtual product — partially selected options

When the user has selected some option groups but not all (e.g., selected "Color=Red" but not "Size"), `resolveVariant` returns `null` because no variant matches an incomplete selection. `selectedVariant` is `null`:

- The price displayed is `item.price_cents` (parent base price — a "from" price).
- The availability badge shows `item.availability` (parent-level availability when `STORE_SHOW_LIVE_AVAILABILITY` is on, else the scalar badge).
- The Add-to-Cart button is **disabled** with `title="Select all options to add to cart"` — this is a new disable condition added alongside the existing `out_of_stock` disable.

This ensures the cart never receives a bare `item_id` SKU for a virtual product (which has no inventory row), preventing a downstream 400 from ECM-008's reservation call.

### 5.4 Virtual product — variant out-of-stock

When `selectedVariant.availability.available === 0` (live availability at zero):

- The Add-to-Cart button is disabled with the existing `"out_of_stock"` label.
- The detail availability badge shows "Out of Stock" (`displayStockStatus === "out_of_stock"`).

This extends the existing disable check at `ProductDetail.tsx:267`. The implementation:

```ts
const isOutOfStock =
  (selectedVariant?.availability != null && selectedVariant.availability.available <= 0)
  || (!selectedVariant && displayStockStatus === "out_of_stock");
```

When `selectedVariant.availability` is `null` (ECM-005 not on or degrade), the oversell guard falls back to the scalar `stock_status === "out_of_stock"` check — same as today.

### 5.5 Variant selection resets on item navigation

The query `itemsQuery` is keyed on `["catalog", "items", categoryId]` (`ProductDetail.tsx:63`). When the user navigates to a different `itemId` within the same category (e.g., via browser back/forward), `item` changes but `categoryId` does not, so `itemsQuery` may not re-run and `selectedVariantId` / `selectedOptions` retain stale values. A `useEffect` resets these:

```ts
useEffect(() => {
  setSelectedVariantId(null);
  setSelectedOptions({});
}, [itemId]);
```

### 5.6 Availability for variant vs. parent-level

ECM-005 / ECM-006 populate `availability` at two levels:

- `item.availability` — reflects the parent item's aggregate availability (sum across all variants, or the flat item's availability if non-virtual). Always present when `STORE_SHOW_LIVE_AVAILABILITY` is on.
- `selectedVariant.availability` — reflects the *selected variant's* SKU-specific availability. Present only when `STORE_SHOW_LIVE_AVAILABILITY` is on AND ECM-006 runs the per-variant availability pass.

The priority order for the badge in ProductDetail is: `selectedVariant.availability` > `item.availability` > scalar `item.stock_status`. The Catalog grid only has `item.availability` (no variant picker on the grid).

### 5.7 Catalog browse grid — availability badge

In `Catalog.tsx`, the badge at line 180 renders `item.stock_status`. ECM-007 extends this to:

```tsx
const badgeStatus = (isStoreIntegrationEnabled() && item.availability != null)
  ? item.availability.stock_status
  : item.stock_status;
const badgeCount = (isStoreIntegrationEnabled() && item.availability != null)
  ? item.availability.available
  : item.stock_count;
```

The badge JSX structure is unchanged; only the data source changes. This is a one-line substitution per badge condition, not a structural change.

### 5.8 Price display — "from" vs. variant-specific

When variants are present and none is selected, the displayed price is `item.price_cents` (the parent base price). A "From" prefix is conditionally rendered:

```tsx
<p className="mt-1 text-2xl font-semibold text-primary">
  {hasVariants && !selectedVariant && (
    <span className="text-sm font-normal text-muted-foreground mr-1">From</span>
  )}
  {formatPrice(displayPrice, displayCurrency)}
</p>
```

`hasVariants` is `true` when `variants !== null && variants.length > 0`.

### 5.9 option_selections ordering

Feature category keys are extracted from `Object.entries(v.option_selections)`. JavaScript `Object.entries` preserves insertion order for string keys in modern engines, and DynamoDB stores maps as unordered attribute sets — the order of entries may differ across variants. ECM-007 presents option groups in the stable order they first appear across the variant list (via the `buildOptionGroups` loop). This ensures the "Color" row always appears before the "Size" row across renders, even if different variants have different insertion orders in their DynamoDB rows.

### 5.10 Variant with `availability: null` when flag partially on

If `STORE_VARIANT_SELECTION_ENABLED` is on but `STORE_SHOW_LIVE_AVAILABILITY` is off, the backend returns variants with `availability: null` on each `StorefrontVariant`. The `displayStockStatus` then falls through to `item.stock_status` (the scalar). The Add-to-Cart button is enabled unless `item.stock_status === "out_of_stock"`. This is correct: the variant picker works (correct SKU and price), but availability reflects only the static scalar — acceptable degraded state.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 dev/prod parity

ECM-007 introduces no `if (import.meta.env.DEV)` branches. The compile-time `VITE_*` flags are the only mechanism; they are environment-variable driven and apply consistently to any build target (local, staging, prod). The picker and badge logic reads the same `item.variants` / `item.availability` fields regardless of environment.

The backend `/ui/catalog/integration-config` endpoint reads `S.*` singleton values via `getattr(S, ..., False)` — the same pattern as `_integration_enabled` in ECM-002. It does not fork on `S.dev_mode`. The response shape is identical in dev (moto-backed DynamoDB) and prod.

### 7.2 Idempotency

ECM-007 makes no write paths. The only write is the existing `addCartItem` call, which ECM-007 modifies to send `sku: selectedVariant.sku` instead of `sku: item.item_id`. Cart item upsert idempotency (re-adding the same SKU increments quantity) is already handled by `add_item` in `shoppingcart.py:316–337` — unchanged.

No new DynamoDB writes, no billing ledger entries, no reservation calls in this ticket. Those belong to ECM-008.

### 7.3 Security: server-authoritative price

The `unit_price_cents` sent in the `addCartItem` payload comes from `selectedVariant.price_cents` — a server-computed value derived from `parent.price_cents + variant.price_delta_cents` (see ECM-004 `_build_storefront_variant`). The cart service stores `unit_price_cents` verbatim from the payload at `shoppingcart.py:347`; it does not re-validate against the catalog at add-time.

This is the same trust model as the current code — the frontend sends `item.price_cents` which it also received from the server. The price is authoritative at purchase-time: ECM-009 (pricing rules) re-computes the total server-side at `purchase_cart`, making the stored `unit_price_cents` advisory rather than binding for billing. Until ECM-009 lands, the risk profile is identical to the current store: a client could manipulate `unit_price_cents` in the add-cart request. This pre-existing risk is documented in ECM-001 section 2.7 and is out of scope for ECM-007.

### 7.4 No PII exposure

`StorefrontAvailabilityOut.available` / `on_hand` / `reserved` are aggregate counts. As confirmed in ECM-003 §7.3, per-user reservation breakdowns are not exposed. The `StorefrontVariant` shape carries no user-specific fields.

Adding `variants?: StorefrontVariant[] | null` and `availability?: StorefrontAvailability | null` to the `CatalogItem` interface at `frontend/src/api/types.ts:2135` is backward-compatible. TypeScript optional fields (`?`) do not require callers to handle them. All existing component code that destructures or accesses `CatalogItem` fields by name continues to compile and run unchanged.

### 8.2 CartItemIn TypeScript interface is additive

Adding `variant_id?: string` to `CartItemIn` at `types.ts:2061` <!-- VERIFIED --> is backward-compatible. The existing `addCartItem` call at `ProductDetail.tsx:91–99` <!-- VERIFIED: payload construction at lines 91–99 --> does not pass `variant_id` today and will not be modified when the flag is off.

### 8.3 ShoppingCartItemIn Pydantic model is additive

Adding `variant_id: Optional[str] = None` to `app/models.py:948` (appended after the existing `entitlement_template_metadata` field at line 947) is backward-compatible. Existing POST requests that omit `variant_id` continue to validate (Pydantic treats missing optional fields as their default). No migration of existing cart item DDB rows is required — old rows simply lack the `variant_id` attribute, and the new conditional block in `_item_from_item` (`shoppingcart.py:79`) will not include it in the output when absent.

### 8.4 No DDB schema migration

The cart item DDB schema is open-ended: `add_item` stores optional keys conditionally at lines 357–364 (`image_url`, `category_id`, `item_id`, `creator_user_id`). Adding `variant_id` follows the same pattern with one new `if payload.get("variant_id")` block. No `scripts/local-ddb-init.py` change is needed.

### 8.5 Existing E2E and unit tests

- `frontend/e2e/catalog-subscriptions.spec.ts` (37 tests, sections 59–64) asserts catalog item shapes. The new optional `variants` / `availability` keys (present as `null`) are invisible to existing assertions that check only for known fields.
- `tests/test_shoppingcart_*.py` and similar cart tests do not assert the absence of `variant_id` on the request model, so the additive Pydantic field is safe.
- If any existing test uses `response_model_exclude_none=False` and asserts a precise JSON serialisation, the `"variants": null` and `"availability": null` keys that ECM-003 adds may surface. The ECM-003 spec (§5.1) documents this and recommends the catalog router use `exclude_none=True` on the enriched path if this is undesirable.

## 10. Open Questions / Assumptions

1. **Assumption: `item.availability` (parent-level) is populated by ECM-006 even for virtual products.** If ECM-005/006 only populates `availability` on flat items (since virtual parents hold no inventory row), then the Catalog grid badge cannot show availability for virtual items at browse time. The fallback is the scalar `stock_status`. This spec assumes ECM-006 uses the first variant's availability as the parent-level indicator when the item is virtual; if not, the Catalog grid simply shows the scalar badge for virtual items (acceptable degraded state).

2. **Assumption: `variants` list order is stable across requests.** The picker renders options in the order they arrive from the API. If the variant list order is non-deterministic (e.g., varies by DynamoDB GSI scan), the option groups could reorder on re-render. ECM-004 spec (§5.7) assumes `list_variants` returns variants ordered by `sequence_num`; ECM-007 trusts this. If not, the `buildOptionGroups` output is still correct (all values are present), but the button ordering within a group may flicker.

3. **Assumption: option-group feature category names are user-facing strings (not internal IDs).** The picker renders `Object.keys(option_selections)` directly as group headings. If PRD-003 stores internal IDs as keys (e.g., `feat_cat_001: "Red"` instead of `Color: "Red"`), the headings will be ugly. This spec assumes PRD-003 stores human-readable names as keys per the `option_selections: Dict[str, str]` shape in ECM-003 §3.1.

4. **Open: Should selecting a variant also swap the product image?** The current `activeImageIndex` state controls which image is shown from `item.image_urls`. If variants have per-variant images, ECM-007 would need `StorefrontVariant` to carry an `image_url: Optional[str]` field (not in ECM-003 today). **Assumption for this ticket:** variant images are not supported; the image gallery shows the parent item images regardless of variant selection. This can be added as ECM-007b if needed.

5. **Open: Maximum number of option values per group.** If a "Color" option has 50+ values, the button grid overflows the page. ECM-007 renders all values as buttons with `flex-wrap`. A `max(20)` truncation with a "show more" disclosure could be added but is not scoped here. PRD-003 should enforce a per-feature-category value count limit.

6. **Assumption: `VITE_*` compile-time flags match the backend `S.*` runtime flags in the deployed environment.** If they diverge (e.g., backend flag off but frontend flag on), the frontend renders a picker but the API returns `variants: null`. The picker code handles this cleanly: `variants` resolves to `null`, the picker does not render, and the add-to-cart mutation falls back to `item.item_id`. No error or blank page.

7. **Assumption: `CartItemIn.variant_id` is not validated server-side in ECM-007.** The backend simply stores whatever string is passed. Validation that `variant_id` matches a real PRD-007 variant record is deferred to ECM-008 (reserve-on-add), which can do the lookup as part of the reservation call.
