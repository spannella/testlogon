# ECM-015 — Hermetic offline pytest + storefront E2E suite

**Type:** Chore | **Priority:** P1 | **Estimate:** 4 days
**Dependencies:** ECM-007 (variant picker UI), ECM-011 (cart UI), ECM-014 (order tracking page + fulfillment endpoint)

## 1. Summary & Goal

ECM-015 delivers the test coverage that validates the full ECM integration surface end-to-end. It has two deliverables:

1. **`tests/test_ecm_store_integration.py`** — a hermetic offline pytest suite that calls service-layer and route-handler functions directly (no `TestClient`, no real AWS, no network) against moto-backed DynamoDB tables bound to the frozen `T` handles via `object.__setattr__`. It covers each integrated surface from ECM-004 through ECM-012 and asserts that **flag-off always yields byte-for-byte parity with the legacy `shoppingcart`/`catalog` responses**.

2. **`frontend/e2e/store-integration.spec.ts`** — a Playwright E2E spec that drives the full variant→reserve→price→checkout→track happy path through the real running stack, using the same session/CSRF/idempotency patterns as `frontend/e2e/shopping-cart.spec.ts`. It also asserts a flag-off smoke path: with `STORE_INTEGRATION_ENABLED=false` (the default), legacy endpoints return the legacy shape.

Neither file introduces new production code. Both files are the authoritative regression lock-in for the ECM milestone. CI must pass both suites green before the milestone is closed.

### 2.2 Existing hermetic test patterns in the repo

The repo's established pattern for hermetic tests is exemplified by `tests/test_gap_0343_shop_promo_checkout.py` and `tests/test_gap_0347_0348_catalog_stock.py`:

- `@mock_aws` (moto) activates in `setUp`; `ExitStack` manages cleanup (`tests/test_gap_0343_shop_promo_checkout.py:107–128`).
- moto DynamoDB tables are created in-memory mirroring the schemas from `scripts/local-ddb-init.py`.
- The frozen `T` handle for each module is replaced using `patch.object(module, "T", SimpleNamespace(...))` or `object.__setattr__(T, "attr", moto_table)`, and the original is restored via `addCleanup` (`tests/test_gap_0347_0348_catalog_stock.py:90–92`).
- **`TestClient` is not used** — the repo README and existing tests confirm it is broken in this environment. Service functions and route handler coroutines are called directly.
- Route handler coroutines (async) are driven on a fresh `asyncio.new_event_loop()` (pattern from `tests/test_gap_0233_0234_ssh_session_recording.py:290`).
- Commerce side effects (order creation, entitlement orchestration, purchase ledger) are stubbed via `patch.object` so no Stripe / real AWS is needed (`tests/test_gap_0343_shop_promo_checkout.py:131–159`).
- Settings flags are toggled by `object.__setattr__(S, "flag_name", True/False)` with `addCleanup` restoring the original (`tests/test_gap_0347_0348_catalog_stock.py:161–164`).

## 5. Detailed Behavior & Edge Cases

### 5.1 pytest — ECM-004 variant-aware catalog read

**Test: `test_virtual_item_returns_variants`**
Seed a catalog item with `product_type="virtual"` in the moto `shopping_catalog` table. `enrich_catalog_item` is called with `STORE_VARIANT_SELECTION_ENABLED=true`. Assert the returned `CatalogItemOut` has `variants` populated with `[FAKE_VARIANT_A, FAKE_VARIANT_B]` from the stub and that all scalar fields (`item_id`, `price_cents`, `stock_status`, etc.) are unchanged.

**Test: `test_flat_item_returns_unchanged`**
Seed a flat catalog item (no `product_type`). Assert `enrich_catalog_item` returns the same scalar `CatalogItemOut` that `_catalog_item_out(item)` would return (`app/routers/catalog.py:107` — verified ✓), with `variants=None`. Specifically compare the `dict` representation to ensure byte-for-byte parity.

**Test: `test_flag_off_returns_legacy`**
Set `STORE_VARIANT_SELECTION_ENABLED=false`. Even with a virtual item, assert the output is the legacy scalar `CatalogItemOut` with `variants=None` and no PRD-007 stub call was made (assert the stub was not called).

**Test: `test_upstream_error_degrades_to_legacy`**
Replace the variant stub with a side effect that raises `Exception("PRD unavailable")`. Assert `enrich_catalog_item` returns the legacy scalar item and does not raise.

### 5.2 pytest — ECM-005 live availability projection

**Test: `test_reserved_reduces_available`**
Seed inventory: `on_hand=10, reserved=3, available=7` for `SKU_A` in the moto `inventory` table. Call `availability_for_skus(["SKU_A"])`. Assert `available=7`, `on_hand=10`, `reserved=3`, `low_stock=False`.

**Test: `test_low_stock_threshold`**
Seed inventory: `available=2, reorder_point=5`. Assert `low_stock=True` in the returned `StorefrontAvailabilityOut`.

**Test: `test_flag_off_uses_scalar_stock_count`**
Set `STORE_SHOW_LIVE_AVAILABILITY=false`. Call the catalog `list_items` endpoint (route handler directly). Assert the response items have `stock_status` derived from `_compute_stock_status` on the raw `stock_count` scalar (`app/routers/catalog.py:94` — verified ✓), not from the inventory table. Assert `T.inventory` was never queried (patch the table's `batch_get_item` to a spy and assert `call_count == 0`).

**Test: `test_inventory_unavailable_degrades`**
Replace `T.inventory` with an object whose `batch_get_item` raises `ClientError`. Assert `availability_for_skus` returns an empty dict and `_apply_live_availability` falls through to the scalar `stock_count`.

### 5.3 pytest — ECM-008 reserve-on-add / release

**Test: `test_add_item_places_reservation`**
Seed inventory `on_hand=5, reserved=0, available=5` for `SKU_A`. Seed an OPEN cart. Set `INVENTORY_RESERVATIONS_ENABLED=true` and `STORE_SHOW_LIVE_AVAILABILITY=true`. Call `add_item(user_sub, cart_id, {sku: "SKU_A", quantity: 2, ...})`. Assert: (1) the `reservations` table has one active row for `SKU_A` with `quantity=2`; (2) `T.inventory` now shows `reserved=2, available=3`.

**Test: `test_re_add_same_sku_is_idempotent`**
Call `add_item` twice for the same `{cart_id, sku}`. Assert only one reservation row exists (not two). The deterministic reservation ID (`sha256("{cart_id}#{sku}")[:16]`) must deduplicate. NOTE: the current `inventory.reserve` (`app/services/inventory.py:383`) uses `uuid4().hex` — ECM-008 must add a `correlation_id` parameter; see Open Question 6.

**Test: `test_delete_cart_releases_reservation`**
After reserving, call `delete_cart(user_sub, cart_id)`. Assert the reservation row has `status="released"` and `T.inventory` shows `reserved=0, available=5`.

**Test: `test_reservation_failure_does_not_block_add`**
Seed inventory with `available=0` for `SKU_A` (out of stock). Set flag on. Call `add_item`. Assert: (1) no `HTTPException` is raised; (2) the cart item is added (the legacy no-inventory-check path); (3) no reservation row exists for `SKU_A`.

### 5.4 pytest — ECM-009 pricing rule total

**Test: `test_pricing_rule_applied_to_total`**
The `_apply_pricing_rules` stub returns `FAKE_PRICING_BREAKDOWN = {subtotal_cents: 10000, rule_discount_cents: 1500, final_total_cents: 8500, applied_rules: [{rule_id: "RULE1", discount_cents: 1500}]}`. **Test: `test_purchase_uses_same_total_as_preview`**

**Test: `test_flag_off_returns_plain_total`**
Set `STORE_APPLY_PRICING_RULES=false`. Call `cart_total_cents`. Assert it returns a plain `int` (specifically the sum of `line_total_cents`). Assert `_apply_pricing_rules` stub was not called.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity**: The tests assert the same code path runs in both dev (moto DynamoDB) and prod (real DynamoDB). The test suite uses `@mock_aws` to intercept DDB calls at the botocore layer — the same boto3 client code runs in both environments. No `dev_mode` branch is tested differently.

**Idempotency**:
- `purchase_cart` idempotency is tested explicitly (section 5.5): a second call on an already-`PURCHASED` cart returns the same result without re-committing the reservation. The CAS at `app/services/shoppingcart.py:628–642` (`except ClientError` block checking `ConditionalCheckFailedException`) is the idempotency guard; `commit_reservation` at `app/services/inventory.py:456` is its own idempotent guard via `_close_reservation`'s `ConditionExpression="#status = :active"` at `app/services/inventory.py:444` (verified ✓).
- Reservation dedup: the deterministic ID (`sha256("{cart_id}#{sku}")[:16]`, per ECM-008) is tested by the idempotent re-add test case (section 5.3).
- Order ID determinism: `sha256(corr.encode("utf-8")).hexdigest()[:32]` (`app/services/commerce_order_service.py:67` — verified ✓) means the same correlation_id always produces the same `order_id`, making the test's assertions stable across reruns.

**Security**: The tests assert ownership enforcement in `order_fulfillment_status` (section 5.6: foreign `user_sub` gets 403). No billing write paths are exercised; money never moves in the test suite. The flag-off smoke (E2E section 94) asserts that a caller without the feature enabled cannot observe any integration-surface data in responses.

## 9. Test Plan

### 9.1 pytest suite — `tests/test_ecm_store_integration.py`

**Isolation constraints** (from CLAUDE.md hermetic-test pattern):
- `@unittest.skipIf(mock_aws is None, "moto not installed")` guards every class.
- Each `setUp` calls `ExitStack.__enter__` on `mock_aws()` and creates four fresh moto tables; each `tearDown` closes the stack.
- Every module-level `T` binding is replaced with `patch.object(module, "T", SimpleNamespace(...))`, not `object.__setattr__(T, ...)`, because `store_integration`, `shoppingcart`, and `inventory` each import `T` from `app.core.tables` at module load time and hold their own reference. `patch.object` replaces the name in each module's namespace for the duration of the test.
- `S` flag overrides use `object.__setattr__(S, attr, value)` with `addCleanup` restore (not `patch.object(S, ...)` — `S` is a frozen dataclass; `object.__setattr__` bypasses the frozen guard, consistent with every other test in the repo).
- Route handler coroutines (for ECM-006/012 endpoint tests) are called via `asyncio.new_event_loop().run_until_complete(handler(...))`, never via `TestClient`.

**Complete test matrix**:

| Test class | Test method | Flag(s) on | Assert |
|---|---|---|---|
| `TestVariantAwareCatalogRead` | `test_virtual_item_returns_variants` | `store_variant_selection_enabled` | `variants` populated |
| | `test_flat_item_returns_unchanged` | on | `variants=None`, scalar unchanged |
| | `test_flag_off_returns_legacy` | off | `variants=None`, stub not called |

## 10. Open Questions / Assumptions

1. **Assumption: `store_integration.py` exists before ECM-015 merges.** ECM-002 creates it; ECM-015 depends on ECM-007 and ECM-011 (which depend on ECM-006, ECM-008, ECM-009, ECM-010, ECM-002/003/004/005). If any upstream spec is incomplete, the corresponding ECM-015 test class should be skipped with `@unittest.skip("ECM-00X not yet implemented")` rather than blocking CI.

2. **Assumption: `app/services/pricing_rules.py` (OFB-019) exists with an `apply_rules(items, viewer_sub)` function.** ECM-009 spec references `OFB-019/OFB-020`. If OFB-019 is not yet implemented, the `TestPricingRuleTotal` class stubs `_apply_pricing_rules` at the `store_integration` module level and tests the glue logic without requiring the real rules engine.

3. **Assumption: `app/services/product_variants.py` (PRD-007) exists with a `get_variants_for_item(item_id)` function.** ECM-004 spec specifies it. The `TestVariantAwareCatalogRead` class stubs it; PRD-007 not being merged does not block this test class.

4. **Assumption: The E2E sections 801–803 run against a stack where the upstream PRD/OFB/ORD/SHP modules have been seeded with test data** (variant definitions, inventory records, pricing rules, order lifecycle rows). If the upstream data is absent, sections 801–803 degrade gracefully (flags are on but no upstream data → no enrichment). Sections 801–803 are therefore conditional on the full stack being seeded; CI should mark them as expected-to-skip if the upstream flags (`PRODUCT_DEPTH_ENABLED`, `INVENTORY_RESERVATIONS_ENABLED`, etc.) are off.

5. **Open question: Should section 804 (flag-off smoke) run in a separate CI job from sections 801–803 (flag-on)?** The flag-on tests require a backend restart with env vars set. The current Playwright config (`frontend/playwright.config.ts`) uses a single worker, so both groups could run serially with backend restarts between groups — but this adds 20–30 seconds per restart. Alternatively, the flag-off smoke could be a standalone spec file. Decision deferred to the implementer.

6. **Open question: Reservation dedup key format.** ECM-008 spec states `sha256("{cart_id}#{sku}")[:16]`. The `reserve` function in `inventory.py:383` currently generates `uuid4().hex`. ECM-008's implementer must add a `correlation_id` parameter to `reserve` to allow the caller to pass a deterministic ID. The pytest tests for ECM-008 behavior (`test_re_add_same_sku_is_idempotent`) depend on this. If `reserve` does not yet accept `correlation_id`, the idempotency test must stub the reservation table put to verify dedup behavior at the `shoppingcart.add_item` level rather than at the inventory level.

7. **Assumption: The `orders` table is an existing moto table in tests.** The base class stubs `create_order_from_line_items` to return `{"order_id": "ord_ecm015"}`, so the `orders` table is never actually written in the pytest tests. For `TestFulfillmentStatusRead`, the `orders` row is written directly to the moto table in `setUp` to provide the ownership check.
