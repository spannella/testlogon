# HRM-003 — HR Pydantic models (employee / position / employment / payroll)

## 1. Summary & Goal

HRM-003 defines the complete Pydantic model surface for the HR module: domain objects (`Position`, `Employment`, `PayrollRun`, `PayrollLine`) plus their IO counterparts (`CreatePositionIn`, `PositionOut`, `UpdatePositionStatusIn`, `CreateEmploymentIn`, `EmploymentOut`, `TerminateEmploymentIn`, `CreatePayrollRunIn`, `PayrollRunOut`, `PayrollLineOut`). All models live in `app/models.py` alongside the 14 000+ lines of existing models. No router, service, or DynamoDB table is created here; those belong to HRM-004 through HRM-009. The models constitute the contract that every downstream HRM ticket implements against and that `tests/test_hrm_003_models.py` validates in isolation (no DynamoDB, no network).

Money fields use integer cents plus a `currency` string — the same convention established by `billing_shared.new_ledger_entry` at `app/services/billing_shared.py:248` (`"amount_cents": int(amount_cents)`). Enum values are expressed as `Literal[...]` union types, matching the dominant pattern in the file (e.g. `app/models.py:1853`, `:2278`). Cross-field validation (e.g. `end_date < start_date`) is enforced by `@model_validator(mode="after")` — the same pattern used by `RegisterStartReq` at `app/models.py:171`.

## 5. Detailed Behavior & Edge Cases

### 5.1 `end_date < start_date` rejection

`CreateEmploymentIn` uses `@model_validator(mode="after")`. If `end_date` is `None` the check is skipped (the common case: hire with no end date). If `end_date` is set and strictly less than `start_date`, a `ValueError("end_date must be >= start_date")` is raised, which Pydantic wraps into a `ValidationError` with a `"value_error"` type. FastAPI will translate this to a 422 Unprocessable Entity response — no special handler needed.

The same check applies to `CreatePayrollRunIn.period_end < period_start`.

### 5.2 Negative money rejection

`pay_rate_cents: int = Field(..., ge=0)` and `gross_cents: int = Field(..., ge=0)` reject negative values at Pydantic validation time (before any service code runs). A pay rate of zero is deliberately allowed — unpaid positions (internships, volunteer roles) are valid HR records.

### 5.3 Currency normalisation

`currency` is typed `str` with `min_length=3, max_length=3`. No uppercase-enforcement validator is added at the model layer — the service layer (HRM-006, HRM-008) normalises to uppercase before persistence (following the pattern in `billing_shared.py` where `"usd"` is used as a lowercase default). The `min_length=max_length=3` constraint prevents empty strings and longer freetext while keeping the model thin. If a caller passes `"eur"`, the model accepts it; the service uppercases to `"EUR"` before writing to DDB.

### 5.4 Unknown `status` / `pay_period` rejection

`Literal` type annotations cause Pydantic to raise `ValidationError` for any value not in the literal set. For example `pay_period="FORTNIGHTLY"` → 422. There is no `else: raise` clause needed in service code — the model rejects it before reaching the service. This is a strict improvement over an open `str` field with a service-layer check because the error fires as early as FastAPI's request body parsing.

### 5.5 `PositionOut` vs `Position`

The ticket specifies separate `PositionOut` and `Position` classes. Because both have identical fields, `PositionOut` is implemented as a direct alias:
```python
PositionOut = Position
```
This matches the approach used for other passthrough output models in the codebase (e.g. `PurchaseTransactionSummary` serves as both the base and the list-item response). If future HRM tickets add computed fields (e.g. `active_employment_count`) to `PositionOut`, `PositionOut` should be promoted to an independent subclass at that time without breaking existing callers.

### 5.6 `PayrollRun.lines` as embedded list

`PayrollRun.lines: List[PayrollLine] = Field(default_factory=list)` — the lines are embedded in the run object, not returned by a separate endpoint. HRM-007 populates this list during the compute phase. DynamoDB stores them as a JSON-serialised list on the `PAYROLL_RUN#` item (single-table, no separate `PayrollLine` DDB rows). This avoids a secondary query when fetching a run for review or approval.

### 5.7 `approved_by` and `posted_at` lifecycle

`approved_by: Optional[str] = None` is `None` when the run is `DRAFT`; set to the approving user's `user_sub` when the run transitions to `APPROVED` (HRM-007 service). `posted_at: Optional[int] = None` is `None` until the GL posting hook (HRM-010) runs and transitions the run to `POSTED`. These are output-only fields — neither `CreatePayrollRunIn` nor any patch model accepts them as input.

### 5.8 `correlation_id` passthrough

`correlation_id` is accepted on `CreatePositionIn`, `CreateEmploymentIn`, and `CreatePayrollRunIn` but is **not** returned in any `Out` model — it is a write-path idempotency key used only by the service layer (HRM-005/006/007). This follows the `entitlements_service.py:132` pattern where the correlation key `stable_src` is consumed during `sha256` id-derivation and not stored as a user-visible field.

### 5.9 `Employment.status` transitions (model vs service)

The model allows direct assignment of any valid `EmploymentStatus` literal. Transition enforcement (`ACTIVE`→`TERMINATED`, `ACTIVE`→`ON_LEAVE`, `ON_LEAVE`→`ACTIVE`) belongs to the service (HRM-006) via a `ConditionalCheckFailedException` on DynamoDB `UpdateItem` — identical to the pattern used in `update_position_status` (HRM-005). The model does not encode transition logic.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007

HRM-003 is pure Python model code with no AWS calls, no `dev_mode` branches, and no mock paths. The same `app/models.py` file is used in both dev and prod — there is no divergence. The models parse identically on `uvicorn` started via `scripts/run_local_mock_backend.sh` (dev) and on the production app server.

### Idempotency at the model layer

HRM-003 itself has no write paths, so idempotency is not applicable here. The `correlation_id` fields on `CreatePositionIn`, `CreateEmploymentIn`, and `CreatePayrollRunIn` are the vehicle for write-path idempotency in HRM-005/006/007 — they are `Optional[str]` here, with no validation beyond `max_length=64`. The service layer (HRM-005) derives `position_id = hashlib.sha256(correlation_id.encode()).hexdigest()[:32]` when the field is set, following `app/services/api_usage_metering.py:142` (`digest = hashlib.sha256(idempotency_key.encode("utf-8")).hexdigest()[:32]`).

### Security

- No secrets, tokens, or sensitive data in model fields.
- `pay_rate_cents` is a compensation field. Access control is enforced at the router/auth layer (HRM-009) — employees may view their own employment records; HR admins may view all. The model itself does not gate visibility.
- `currency` is constrained to exactly 3 characters, preventing injection of oversized strings into DynamoDB.
- `party_id` and `org_party_id` are plain strings — ownership validation (does this `party_id` belong to the calling user or are they an HR admin?) is enforced in the service (HRM-004/006), not at the model layer.

## 8. Backward Compatibility & Migration

### Zero-change guarantee

With `HR_ENABLED=0` (the default), HRM-003's only change to the running system is the addition of new classes to `app/models.py`. Because:

1. No existing class is modified.
2. No existing import is changed.
3. No router registration or DynamoDB table creation happens.

…existing shop/cart/orders/billing/inventory surfaces are byte-for-byte unchanged at runtime. The `S = Settings()` singleton and all existing `T.*` table handles are unaffected.

### Migration

No DynamoDB migration is needed. The `hr` table is created by HRM-002 (`scripts/local-ddb-init.py`). HRM-003 only touches `app/models.py`. No `just restart` is required after merging this ticket on its own; however, `just restart` is required before running HRM-004+ service code (which writes to `T.hr`).

### Python module import order

`app/models.py` is imported by essentially every router and service in the app at startup. Adding classes at the end of the file does not affect startup time measurably (class definition is ~O(1) per class). There are no circular imports because the HR models reference only `str`, `int`, `Optional`, `List`, `Literal`, `Field`, `BaseModel`, `model_validator`, and `field_validator` — all already imported in the file's import block (`app/models.py:1–19`).

## 10. Open Questions / Assumptions

1. **Assumption: `PositionOut = Position` (alias) is sufficient for HRM-003.** If HRM-005/009 require additional computed fields on the response (e.g. `active_employment_count`), `PositionOut` should be promoted to a subclass at that point without breaking the model contract established here.

2. **Assumption: timestamps are Unix epoch integers throughout.** `start_date`, `end_date`, `period_start`, `period_end`, `created_at`, `updated_at`, `posted_at` are all `int` (Unix seconds from `now_ts()`). The codebase uniformly uses this convention (e.g. `app/models.py:461`). ISO-8601 string dates are not used. Callers must convert to epoch before calling.

3. **Assumption: currency is validated at model layer only for length (3 chars), not for ISO-4217 membership.** Validating the full ISO-4217 list requires a static table import or regex. The existing codebase does not do this for any currency field (e.g. `app/models.py:429` `Field(..., min_length=3, max_length=10)`). HRM-003 tightens to `max_length=3` but does not validate membership. If a future audit requires strict ISO-4217 validation, a `@field_validator` can be added without breaking existing data.

4. **Assumption: `correlation_id` max length of 64 is sufficient.** UUIDs are 36 chars; SHA-256 hex digests are 64 chars. The 64-char limit accommodates both. If callers use longer opaque keys, the limit should be raised to 128.

5. **Assumption: `PayrollRun.lines` is embedded (not a separate DDB entity).** This is convenient for read performance but means a run with hundreds of employees will have a large DDB item. The DynamoDB item size limit is 400 KB. A run with 1000 employees × ~200 bytes per `PayrollLine` ≈ 200 KB — within limits for realistic org sizes. If line counts exceed ~1500, HRM-007 should paginate lines into overflow items. This is a HRM-007 concern, not a model concern, but the model's `lines: List[PayrollLine]` does not artificially cap the list.

6. **Assumption: `org_party_id` is always the platform's own PARTY_GROUP.** In a multi-tenant deployment, different tenants have different org parties. `org_party_id` is accepted as a caller-supplied value (no hardcoded default) so that HRM-004's `ensure_employee_party` can supply the correct org party for the tenant context. The model does not validate that `org_party_id` refers to a real PARTY_GROUP — that is a service-layer concern (HRM-004/006).

7. **Assumption: `TerminateEmploymentIn` does not accept `status` directly.** Only `end_date` (and an optional `note`) are accepted. The service (HRM-006) sets `status = "TERMINATED"` based on the action being called, not on a request field. This prevents callers from setting arbitrary statuses via the terminate endpoint.

8. **Open question: should `PayrollLine.party_id` be included in the model or derived on-the-fly?** Including `party_id` in `PayrollLine` denormalises data from `Employment` for display convenience. If HRM-007's compute step materialises lines from Employment rows, embedding `party_id` saves a join at read time. If future refactoring removes the denormalisation, the field becomes dead weight. Assumed here: include it for display convenience, consistent with how the billing ledger denormalises `user_sub` onto each row (`billing_shared.py:244`).
