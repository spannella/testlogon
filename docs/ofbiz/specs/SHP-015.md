# SHP-015 — Refund of paid shipping via existing billing

## 1. Summary & Goal

SHP-015 adds a `refund_shipping_charge` service function to `app/services/shipments.py` that is
called automatically whenever a shipment enters the terminal side-states `cancelled` or `returned`
(driven by the SHP-010 state machine). When shipping was charged at label-creation time, exactly
one money-out ledger entry of `type="adjustment"`, `reason="shipping_refund"` is written through
the existing `new_ledger_entry` + `apply_balance_delta` + `settle_or_reverse_ledger` path in
`app/services/billing_shared.py` — the same primitives used by `app/routers/billing.py:refund_payment`
and `app/services/returns_rma.py:refund_return`. No new refund code path is introduced; no direct GL
write bypasses the ledger. The refund is idempotent per shipment: a deterministic idempotency key
(`sha256("shipping_refund:{shipment_id}")[:32]`, mirroring the `order_id` derivation at
`app/services/commerce_order_service.py:67`) ensures a replayed cancel cannot double-refund.

The entire feature is gated behind `S.shipping_enabled` (the master flag from SHP-002, env
`SHIPPING_ENABLED`, default `false`). With the flag off, `refund_shipping_charge` is never called
and the billing table is untouched.

## 2. Context & Current State

### 2.1 Billing ledger primitives

All money-out flows in the platform converge on three functions in
`app/services/billing_shared.py`:

- `new_ledger_entry(*, key_name, key_value, entry_type, amount_cents, state, reason, meta, extra)`
  (`billing_shared.py:224`) — mints a `LEDGER#{ts}#{entry_id}` SK row. The `extra` dict is
  pass-through onto the DynamoDB item; callers must pass `extra={"provider": "stripe"|"paypal"|"ccbill"}`
  for FIN-013 provider attribution (`billing_shared.py:235–238`).
- `apply_balance_delta(table, pk, delta, *, currency)` (`billing_shared.py:83`) — atomic
  add-or-create on the `BALANCE` row.
- `settle_or_reverse_ledger(table, key_name, key_value, ledger_sk_value, new_state)`
  (`billing_shared.py:262`) — flips the `state` field on a specific ledger row to `"reversed"`.

`app/routers/billing.py:refund_payment` (`billing.py:1287`) calls exactly these three functions when
processing a Stripe refund: it writes a new `type="adjustment", reason="refund"` entry, adjusts the
balance, and reverses the original charge row. `app/services/returns_rma.py:refund_return`
(`returns_rma.py:444`) follows the same pattern for RMA money-out, using a conditional status-flip
(`_transition`) as a single-writer guard to prevent double-posting.

### 2.2 Platform financial dashboard dependency

`app/services/platform_financial_dashboard.py` queries ledger entries via `GSI_LEDGER_DATE`
(`platform_financial_dashboard.py:148`). Provider attribution is resolved by `_provider_for`
(`platform_financial_dashboard.py:110`) reading the `provider` field on each ledger item. Any
shipping refund that omits `provider` would be bucketed as `"unknown"` in the breakdown —
preserving attribution requires `extra={"provider": "<original_provider>"}` on every
`new_ledger_entry` call.

### 2.3 Shipment state machine (SHP-010)

`app/services/shipments.py` (delivered by SHP-008/009/010, not yet on disk) implements the lifecycle:

```
created → packed → label_created → shipped → in_transit → out_for_delivery → delivered
                                ↘ cancelled
                shipped/in_transit/out_for_delivery ↘ returned/exception
```

The `label_created` transition is the point at which shipping is charged: the ship method's
computed rate (`amount_cents`, from SHP-006/007) is recorded on the shipment row as
`shipping_charge_cents` and `shipping_ledger_sk` (the billing ledger SK of the debit entry posted
at charge time). Both fields are written by `charge_shipping` (a new internal function in
`app/services/shipments.py`, spec'd below) called from the `label_created` transition handler.
SHP-015 depends on both being present before refund can occur.

### 2.4 Single-writer idempotency pattern

`returns_rma._transition` (`returns_rma.py:319`) uses a `ConditionExpression="#s = :from"` DynamoDB
conditional update returning `ALL_OLD`. If the item is already in the target state, the condition
fails and the function returns `None` — the caller then skips the ledger write. SHP-015 uses the
same pattern: a dedicated idempotency row (`SK = "SHIPPING_REFUND_LOCK"` on the `shipments` table)
written with `attribute_not_exists(sk)` guards the first-and-only ledger write.

### 2.5 Existing tables (already declared)

The `billing` table (PK `pk`, SK `sk`) is declared at `scripts/local-ddb-init.py:67` with
`GSI_LEDGER_DATE`. The `shipments` table (PK `shipment_id`, SK `sk`) is declared by SHP-002. No new
table is required for SHP-015.

### 2.6 What does NOT yet exist

- `app/services/shipments.py` (landing in SHP-008 through SHP-010).
- `S.shipping_enabled` and associated table settings (landing in SHP-002).
- `T.shipments`, `T.shipment_items`, `T.shipment_packages`, `T.shipping_carriers` (landing in SHP-002).
- `shipping_charge_cents` / `shipping_ledger_sk` / `shipping_payment_intent_id` fields on the
  shipment row (populated by `charge_shipping`, called from the `label_created` transition in SHP-010).

## 3. Data Model

### 3.1 Shipment row additions (no new table; `shipments` table from SHP-002)

SHP-015 reads and writes the following fields on the shipment header row
(`PK = shipment_id, SK = "META"`):

| Field | Type | Written by | Purpose |
|---|---|---|---|
| `shipping_charge_cents` | `int` | `charge_shipping` (label_created transition, SHP-010) | Amount charged for shipping; `0` if free |
| `shipping_ledger_sk` | `str` | `charge_shipping` | `LEDGER#{ts}#{entry_id}` of the debit entry to reverse |
| `shipping_payment_intent_id` | `str \| None` | `charge_shipping` | Stripe PI id (if Stripe was used), for traceability |
| `shipping_provider` | `str` | `charge_shipping` | `"stripe"` / `"paypal"` / `"ccbill"` for FIN-013 |
| `shipping_refund_ledger_sk` | `str \| None` | `refund_shipping_charge` | Set after successful refund; presence blocks replay |
| `shipping_refund_idempotency_key` | `str` | `refund_shipping_charge` | `sha256("shipping_refund:{shipment_id}")[:32]`; stored for audit trail |

### 3.2 Idempotency row (`shipments` table)

A one-time-write sentinel is inserted alongside the shipment header:

```
PK  = <shipment_id>
SK  = "SHIPPING_REFUND_LOCK"
idempotency_key = sha256("shipping_refund:{shipment_id}")[:32]
created_at      = <unix timestamp int>
actor_sub       = <admin or system sub>
```

Written with `ConditionExpression="attribute_not_exists(sk)"`. A second call (replay) hits
`ConditionalCheckFailedException`, which `refund_shipping_charge` catches and treats as a no-op
(returns the current shipment row unchanged). No second ledger entry is ever written.

### 3.3 Billing table rows written by SHP-015

All writes target `T.billing` (existing table), PK `pk = USER#{user_sub}`:

**Refund ledger entry** (one per shipment, idempotent):
```
pk              = USER#{buyer_user_sub}
sk              = LEDGER#{ts}#{entry_id}         # via new_ledger_entry → ledger_sk()
entry_id        = ulidish()
ts              = now_ts()
type            = "adjustment"
amount_cents    = <shipping_charge_cents>
state           = "settled"
reason          = "shipping_refund"
ledger_date     = YYYY-MM-DD (UTC)               # FIN-013 / GSI_LEDGER_DATE
provider        = <shipping_provider>             # GAP-0203 / FIN-013 attribution
meta            = {"shipment_id": "...", "order_id": "...", "reason": "shipping_cancelled|returned"}
```

**Balance delta** (via `apply_balance_delta`): `payments_settled_cents -= shipping_charge_cents`.

**Original shipping debit** (via `settle_or_reverse_ledger`): `shipping_ledger_sk` row state →
`"reversed"`.

### 3.4 No schema changes to existing tables

`orders`, `order_items`, `billing`, `purchase_transactions` — all unchanged. The `shipments` table
receives new optional attributes on the `META` row only; existing rows without these fields are
treated as `shipping_charge_cents = 0` (nothing to refund).

## 4. API / Service Design

### 4.1 New internal function: `charge_shipping` (called from SHP-010)

```python
# app/services/shipments.py

def charge_shipping(
    shipment_id: str,
    *,
    user_sub: str,
    amount_cents: int,
    currency: str = "usd",
    provider: str = "stripe",
    payment_intent_id: Optional[str] = None,
) -> str:
    """Record a shipping charge against the buyer's billing ledger.

    Called by the label_created transition handler in SHP-010. Returns the
    ledger SK for storage on the shipment row.
    Raises HTTPException(400) if amount_cents <= 0 (caller passes 0 for free shipping).
    """
```

This writes one `type="charge", reason="shipping_charge"` ledger entry via `new_ledger_entry`
and adjusts `payments_settled_cents` upward. It then back-writes `shipping_charge_cents`,
`shipping_ledger_sk`, `shipping_payment_intent_id`, and `shipping_provider` onto the shipment's
`META` row via `update_item`. Not called for `amount_cents == 0` (free shipping).

### 4.2 New internal function: `refund_shipping_charge`

```python
# app/services/shipments.py

def refund_shipping_charge(
    shipment_id: str,
    *,
    actor_sub: str,
    reason: str = "cancelled",   # "cancelled" | "returned"
) -> Dict[str, Any]:
    """Refund the shipping charge for a cancelled or returned shipment.

    Idempotent: a second call with the same shipment_id is a no-op (returns
    the current shipment dict without a second ledger write).

    Returns the current shipment META dict.

    Raises:
        HTTPException(404) if shipment not found.
        HTTPException(422) if shipping_charge_cents is missing or <= 0
                            (nothing to refund).
    """
```

Full logic:

1. Load `META` row from `T.shipments`. Raise 404 if absent.
2. Read `shipping_charge_cents`. If `0` or absent: return current row (no-op, not an error — free
   shipping is valid).
3. Attempt idempotency row insert:
   ```python
   T.shipments.put_item(
       Item={
           "shipment_id": shipment_id,
           "sk": "SHIPPING_REFUND_LOCK",
           "idempotency_key": idem_key,   # sha256("shipping_refund:{shipment_id}")[:32]
           "created_at": now_ts(),
           "actor_sub": actor_sub,
       },
       ConditionExpression="attribute_not_exists(sk)",
   )
   ```
   On `ConditionalCheckFailedException`: idempotent replay — return current META row unchanged.
4. Load `shipping_provider`, `shipping_ledger_sk`, `user_sub`, `order_id`, `currency` from META.
5. Call `new_ledger_entry(key_name="pk", key_value=user_pk(user_sub), entry_type="adjustment",
   amount_cents=int(shipping_charge_cents), state="settled", reason="shipping_refund",
   meta={"shipment_id": shipment_id, "order_id": order_id, "reason": reason},
   extra={"provider": shipping_provider, "shipment_id": shipment_id})`.
6. `ddb_put(T.billing, led_item)`.
7. `apply_balance_delta(T.billing, user_pk(user_sub), {"payments_settled_cents": -int(shipping_charge_cents)}, currency=currency)`.
8. If `shipping_ledger_sk` is set: `settle_or_reverse_ledger(T.billing, "pk", user_pk(user_sub), shipping_ledger_sk, "reversed")`.
9. Back-write `shipping_refund_ledger_sk` and `shipping_refund_idempotency_key` onto the shipment's
   `META` row (best-effort `update_item`; failure is non-fatal — the ledger entry already exists).
10. `_audit("shipping.refunded", actor_sub, shipment_id=shipment_id, amount_cents=..., provider=..., order_id=..., reason=reason)`.
11. Return refreshed `META` dict.

All imports from `billing_shared` are local (lazy) to avoid circular dependencies, matching the
pattern in `returns_rma.refund_return` (`returns_rma.py:459–465`).

### 4.3 Wiring into the SHP-010 state machine (`app/services/shipments.py`)

The `transition_shipment` function (from SHP-010) gains a post-transition hook:

```python
# After a successful version-guarded conditional update:
if to_status in ("cancelled", "returned"):
    try:
        refund_shipping_charge(shipment_id, actor_sub=actor_sub, reason=to_status)
    except HTTPException as exc:
        if exc.status_code == 422:
            pass   # free shipping: nothing to refund, not an error
        else:
            raise
    except Exception:
        pass       # best-effort: refund failure does not abort the transition
```

The try/except ensures the state transition always succeeds even if the billing system is
temporarily unavailable, consistent with the "best-effort" pattern in `returns_rma.py:521–530`.
However, `ConditionalCheckFailedException` inside `refund_shipping_charge` is swallowed internally
(step 3 above), so the caller only sees a clean no-op return.

### 4.4 New admin endpoint: `POST /ui/shop/shipments/{shipment_id}/refund-shipping`

This endpoint allows an admin to manually trigger a shipping refund outside the automatic
cancel/return flow (e.g. goodwill refund after partial loss). It delegates entirely to
`refund_shipping_charge`.

```python
# app/routers/shipments.py  (from SHP-011)

@shipments_router.post(
    "/{shipment_id}/refund-shipping",
    response_model=ShipmentRefundOut,
    summary="Manually refund the shipping charge for a shipment",
)
async def admin_refund_shipping(
    shipment_id: str,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> ShipmentRefundOut:
    _require_shipping_enabled()
    result = refund_shipping_charge(shipment_id, actor_sub=user.sub, reason="admin_manual")
    return ShipmentRefundOut(
        shipment_id=shipment_id,
        refunded_cents=int(result.get("shipping_charge_cents", 0)),
        refund_ledger_sk=result.get("shipping_refund_ledger_sk"),
    )
```

Auth: `require_admin_or_root_csrf` (same as `returns_rma_router` admin endpoints at
`app/routers/returns_rma.py:61`). CSRF enforced for non-GET cookie-session calls per repo
convention.

## 5. Detailed Behavior & Edge Cases

### 5.1 Free shipping (no charge)

`shipping_charge_cents` is `0` or absent on the shipment META row. `refund_shipping_charge` detects
this at step 2, returns the current row immediately, and writes neither a ledger entry nor the
idempotency lock row. The caller (transition hook) sees a clean return; the admin endpoint responds
with `refunded_cents: 0`. This is not an error.

### 5.2 Double-cancel / idempotent replay

A replayed cancel (e.g. webhook fires twice) calls `transition_shipment` a second time. The
SHP-010 version guard (`ConditionExpression="version = :v"`) blocks the second transition. Even if
it were to reach `refund_shipping_charge`, the idempotency lock row already exists and the
`put_item` with `attribute_not_exists(sk)` raises `ConditionalCheckFailedException`, which is
caught and returned as a no-op. Exactly one ledger entry is ever written per shipment.

### 5.3 Partial refunds

SHP-015 does not support partial shipping refunds. The full `shipping_charge_cents` is refunded.
If business logic requires partial refunds (e.g. partial delivery), that is a separate ticket.

### 5.4 `charge_shipping` never called (no payment recorded)

If `shipping_charge_cents` and `shipping_ledger_sk` are absent (the shipment was created before
`charge_shipping` was wired, or the charge never went through), step 2 returns a no-op. The admin
endpoint will respond with `refunded_cents: 0`. No 500 is thrown.

### 5.5 `settle_or_reverse_ledger` on an already-reversed row

DynamoDB `update_item` with `SET #s = :s` is unconditional — setting `state = "reversed"` on a row
already in `"reversed"` is idempotent and raises no error (`billing_shared.py:268–274`).

### 5.6 Provider attribution

`shipping_provider` is stored on the shipment META row by `charge_shipping` at the time of the
debit. If for any reason it is absent at refund time, `refund_shipping_charge` defaults to
`"stripe"` (the most common provider), logs a warning, and proceeds. This avoids `"unknown"` in the
financial dashboard while noting the data gap in logs.

### 5.7 Order linkage for traceability

`order_id` is stored on the shipment META row by SHP-008 (`create_shipment`). The refund ledger
entry's `meta` dict carries both `shipment_id` and `order_id`, enabling the financial dashboard to
trace a refund back to its originating order without a separate lookup.

### 5.8 Currency mismatch

`apply_balance_delta` requires a `currency` parameter. `refund_shipping_charge` reads `currency`
from the shipment META row (set by `charge_shipping` from the ship method's `currency` field).
If absent, it defaults to `"usd"` (consistent with `apply_balance_delta`'s signature default at
`billing_shared.py:83` and `returns_rma.py:478`).

### 5.9 Flag off at refund time

If `S.shipping_enabled` is toggled off after shipments exist, `refund_shipping_charge` is never
called (the state-machine hook checks `_require_shipping_enabled()` before calling it). The admin
endpoint also gates on the flag and returns 404.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007

All billing-ledger writes go through `new_ledger_entry` / `apply_balance_delta` /
`settle_or_reverse_ledger` from `app/services/billing_shared.py` — the same functions used in
production by `app/routers/billing.py:refund_payment`. There is no `dev_mode` branch in
`refund_shipping_charge`. DynamoDB local (moto in tests, DynamoDB Local in dev) handles all writes;
no mock path diverges from the production code flow.

### 7.2 Idempotency

Two-layer idempotency:

1. SHP-010 version guard (optimistic concurrency, `ConditionExpression="version = :v"`) prevents
   the `cancelled`/`returned` transition from firing twice.
2. `SHIPPING_REFUND_LOCK` sentinel row (`attribute_not_exists(sk)`) prevents a second ledger write
   even if the hook fires more than once (e.g. due to crash-recovery retry).

The idempotency key `sha256("shipping_refund:{shipment_id}")[:32]` is deterministic across
processes and restarts, mirroring `commerce_order_service.py:67`.

### 7.3 Security

- Admin-only write path: `require_admin_or_root_csrf` on the manual-refund endpoint; the automatic
  path in the state machine is server-internal (no direct API surface).
- Buyers cannot trigger a shipping refund directly; they can only cancel a shipment if SHP-011
  exposes a buyer-cancel endpoint (which would require admin approval per the lifecycle design in
  SHP-010).
- `user_sub` used for the billing ledger PK is read from the shipment's own `user_sub` field (set
  at creation time by `create_shipment`), never from the API caller. A malicious admin cannot
  redirect the refund to an arbitrary account.
- `amount_cents` is read from the stored `shipping_charge_cents` field (set at charge time), never
  from the API request body. Overflow is impossible.

### 7.4 Audit trail

Every call to `refund_shipping_charge` (both automatic and manual) emits
`audit_event("shipping.refunded", actor_sub, ...)` with `shipment_id`, `amount_cents`,
`provider`, `order_id`, and `reason` fields. Best-effort fire-and-forget (swallows exceptions),
matching the pattern in `returns_rma.py:532–541`.

## 8. Backward Compatibility & Migration

### 8.1 Existing billing table

No schema change. `new_ledger_entry` writes new rows; existing rows are never mutated except for
the targeted `settle_or_reverse_ledger` call on `shipping_ledger_sk`. The `GSI_LEDGER_DATE` index
(`scripts/local-ddb-init.py:67`) covers the new rows automatically because `ledger_date` is
populated by `new_ledger_entry` (`billing_shared.py:253`).

### 8.2 Existing shipments table

The new `shipping_charge_cents`, `shipping_ledger_sk`, `shipping_refund_ledger_sk`, and
`shipping_refund_idempotency_key` fields are additive. Shipments created before this feature is
deployed will have these fields absent; `refund_shipping_charge` treats absent fields as `0` (no-op).

### 8.3 Existing order/billing/RMA flows

With `SHIPPING_ENABLED=false` (the default), no code path added by SHP-015 is reachable. The
billing table, orders table, and returns table are byte-for-byte unchanged.

### 8.4 `just restart` (local dev)

No new DynamoDB table is introduced by SHP-015. The `shipments` table with the
`SHIPPING_REFUND_LOCK` SK is already served by the `shipments` table from SHP-002. `just restart`
suffices; no manual `UpdateTable` is required.

### 8.5 Production deployment

1. Deploy backend with `SHIPPING_ENABLED=false` (default). No refund path is reachable.
2. Enable `SHIPPING_ENABLED=true` only after SHP-008 through SHP-014 are live and validated.
3. No backfill is required: legacy shipment records without `shipping_charge_cents` are handled
   as free-shipping (no-op) by `refund_shipping_charge`.

## 10. Open Questions / Assumptions

1. **Assumption**: `charge_shipping` (the companion function that records the original debit at
   `label_created` time) is delivered as part of SHP-010 (or SHP-011), not SHP-015. SHP-015 only
   reads the fields it writes. If SHP-010 does not write `shipping_charge_cents` /
   `shipping_ledger_sk`, the refund will be a no-op (free-shipping case) until those fields exist.

2. **Assumption**: A single provider covers the entire shipping charge. Split-provider charging (e.g.
   part Stripe, part wallet) is not supported in this ticket. `shipping_provider` is a single string.

3. **Open**: Does `transition_shipment` (SHP-010) expose a synchronous or async interface? The
   refund hook design above assumes synchronous. If `app/services/shipments.py` uses `async def`,
   `refund_shipping_charge` must also be `async` and be awaited inside the hook.

4. **Open**: The admin manual-refund endpoint (`POST /ui/shop/shipments/{id}/refund-shipping`)
   should it be callable even when the shipment is in `delivered` state (goodwill refund)? Current
   design: yes — `refund_shipping_charge` does not check the shipment's current lifecycle state;
   only the idempotency lock prevents double-refund. Verify with product.

5. **Assumption**: `user_sub` on the shipment row is the buyer's sub (set by `create_shipment` from
   the order's `user_id`). If SHP-008 uses a different field name, the PK derivation in
   `refund_shipping_charge` must be updated to match.

6. **Open**: Should a `shipping_refund` ledger entry's `amount_cents` be positive (money-out,
   matching the `refund_payment` convention at `billing.py:1306`) or negative? Convention in the
   existing codebase is that refunds write a positive `amount_cents` with `type="adjustment"` and
   `state="settled"`, while the sign is implied by the reason. `returns_rma.py:496–505` writes
   positive `amount_cents` for refunds. SHP-015 follows the same convention.

7. **Assumption**: The `shipments` table primary key is `PK = shipment_id` (string) and `SK = sk`
   (string), consistent with SHP-002's `TableDef` spec. The `META` SK value for the header row is
   the string literal `"META"`, following the RMA pattern (`returns_rma.py:343`).
