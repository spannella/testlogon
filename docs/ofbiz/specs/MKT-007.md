# MKT-007 — Contact lists (static membership)

## 1. Summary & Goal

MKT-007 delivers the contact-list feature of the OFBiz Marketing module: a list owner can create named lists, add and remove party members, and query membership for campaign-send purposes. Lists are static — membership is written explicitly, not derived from a predicate. This distinguishes them from party segments (MKT-008, rule-based dynamic membership).

Three distinct capabilities land in this ticket:

1. **List CRUD** — `create_list`, `get_list`, `list_lists`, `update_list`, `delete_list` in `app/services/marketing_lists.py`. All mutating calls are gated on `S.marketing_campaigns_enabled`.
2. **Member management** — `add_member`, `remove_member`, `list_members`, and `list_members_for_send` (opt-out-suppressed view) in the same service file. Duplicate `add_member` is idempotent. `list_members_for_send` is the send-resolution cursor used by MKT-009; it filters suppressed parties but still shows them to the owner via `list_members`.
3. **Contacts import** — `seed_from_contacts(owner_id, list_id)` reads `T.contacts` (the existing contacts table at `app/core/tables.py:354`) and adds each contact's `contact_id` to the list additively, deduplicating by `party_id`.

No existing service, router, or DDB table outside the marketing module is modified. With `MARKETING_CAMPAIGNS_ENABLED=0` (the default), the contacts system, cart reminders, and billing paths are byte-for-byte unchanged.

### Deterministic `list_id` scheme (MKT-004 pattern)

MKT-004's spec (Section 4) established the sha256-based deterministic-id pattern for marketing objects: `sha256(owner_id + "\x00" + name + "\x00" + created_bucket)[:24]`. MKT-007 applies the same scheme to `list_id`: `sha256(owner_id + "\x00" + name + "\x00" + created_bucket)[:24]`, where `created_bucket = (now_ts() // 3600) * 3600`. A retry within the same hour with the same `owner_id` and `name` produces the same `list_id` and the conditional put fails with `ConditionalCheckFailedException`, at which point the existing item is returned (idempotent create).

## 3. Data Model

MKT-007 uses the `ContactLists` DDB table established by MKT-002. No new DDB tables are introduced.

### Table: ContactLists (single-table, two row types)

Default name: `ContactLists` (env `DDB_CONTACT_LISTS`). Handle: `T.contact_lists`.

**PK/SK schema** (from MKT-002 spec, Section 3):

| Row type | PK | SK | Key attributes |
|----------|----|----|----------------|
| List META | `OWNER#{owner_id}` | `LIST#{list_id}` | `owner_id` (S), `created_at` (N), `list_id` (S), `name`, `description`, `member_count` (N), `updated_at` (N) |
| Member | `LIST#{list_id}` | `PARTY#{party_id}` | `list_id` (S), `joined_at` (N), `suppressed` (Bool), `display_name` (S) |

**GSIs** (declared in `scripts/local-ddb-init.py` by MKT-002 with `attr_types={"created_at": "N", "joined_at": "N"}`):

| Index name | Partition key | Sort key | Used by |
|------------|---------------|----------|---------|
| `ByOwnerCreatedAt` | `owner_id` (S) | `created_at` (N) | `list_lists` — all lists for an owner, newest first |
| `ByListJoinedAt` | `list_id` (S) | `joined_at` (N) | `list_members` / `list_members_for_send` — paginated member enumeration |

**Why two `pk` prefixes in one table**: the `OWNER#{owner_id}` prefix scopes META rows to a partition per owner (owner may have many lists). The `LIST#{list_id}` prefix scopes member rows to a partition per list (a list may have many members). DynamoDB FilterExpression on the `sk` prefix (`begins_with("LIST#")` vs `begins_with("PARTY#")`) further disambiguates row types within each partition — though in practice the two pk namespaces are disjoint so no cross-contamination is possible.

**`suppressed` on member rows**: stored as a `bool` at write time (`is_user_opted_out(party_id)` called during `add_member`). This snapshot value is returned to the owner. Send-resolution (`list_members_for_send`) re-evaluates opt-out at query time (live call to `is_user_opted_out`) rather than relying on the stored value, because opt-out state can change between list population and actual send. The stored value is for display; the live call is for send safety.

**Function signatures**:

```python
def _list_id(owner_id: str, name: str, ts: int) -> str:
    """Deterministic list_id: sha256(owner_id|name|created_bucket)[:24]."""
    created_bucket = (ts // 3600) * 3600
    raw = f"{owner_id}\x00{name}\x00{created_bucket}".encode("utf-8")
    return hashlib.sha256(raw).hexdigest()[:24]

def create_list(owner_id: str, data: ContactListCreateIn) -> ContactListOut:
    """
    Idempotent create. Conditional put with attribute_not_exists(pk).
    On ConditionalCheckFailedException reads back and returns existing item.
    Emits audit_event("contact_list.created", ...).
    Raises HTTPException(403) if flag off.
    """

def get_list(owner_id: str, list_id: str) -> Optional[ContactListOut]:
    """
    Reads pk=OWNER#{owner_id} / sk=LIST#{list_id}.
    Returns None when the item is absent (caller raises 404).
    No flag check — reads pre-existing data.
    """

def list_lists(owner_id: str, limit: int = 50, cursor: Optional[str] = None
               ) -> dict[str, Any]:
    """
    Queries ByOwnerCreatedAt GSI: pk=owner_id, ScanIndexForward=False.
    Returns {"lists": [ContactListOut, ...], "cursor": str|None}.
    No flag check.
    """

def update_list(owner_id: str, list_id: str, name: Optional[str],
                description: Optional[str]) -> ContactListOut:
    """
    Updates name/description/updated_at on the META row.
    Raises 404 if list not found.
    Emits audit_event("contact_list.updated", ...).
    Raises HTTPException(403) if flag off.
    """

def delete_list(owner_id: str, list_id: str) -> None:
    """
    Deletes the META row (pk=OWNER#{owner_id} / sk=LIST#{list_id}).
    Member rows are NOT eagerly deleted (they become orphaned; purge is a
    background-cleanup concern outside this ticket's scope).
    Emits audit_event("contact_list.deleted", ...).
    Raises HTTPException(403) if flag off.
    """

def add_member(owner_id: str, list_id: str, party_id: str
               ) -> ContactListMemberOut:
    """
    1. _require_flag()
    2. _assert_list_owner(owner_id, list_id)  — 404 if META row missing
    3. get_profile_identity(party_id)  — 404 if party absent
    4. suppressed = is_user_opted_out(party_id)
    5. Conditional put pk=LIST#{list_id} / sk=PARTY#{party_id}
       ConditionExpression="attribute_not_exists(pk)"
       On ConditionalCheckFailedException: read back existing row (no-op dedup)
    6. On fresh write: increment META member_count by +1
    7. Emits audit_event("contact_list.member_added", ...) on fresh write only
    Returns ContactListMemberOut.
    """

def remove_member(owner_id: str, list_id: str, party_id: str) -> None:
    """
    1. _require_flag()
    2. _assert_list_owner(owner_id, list_id)  — 404 if META row missing
    3. delete_item pk=LIST#{list_id} / sk=PARTY#{party_id}
       ConditionExpression="attribute_exists(pk)" to detect missing member
       On ConditionalCheckFailedException: 404
    4. Decrement META member_count by -1 (floor at 0 via MAX expression)
    5. Emits audit_event("contact_list.member_removed", ...)
    """

def list_members(owner_id: str, list_id: str, limit: int = 100,
                 cursor: Optional[str] = None,
                 include_suppressed: bool = True) -> dict[str, Any]:
    """
    Queries ByListJoinedAt GSI: pk=list_id, ScanIndexForward=False.
    include_suppressed=True: returns all members with stored suppressed flag.
    include_suppressed=False: filters out members where suppressed=True
      (snapshot value; callers who need live opt-out check use list_members_for_send).
    Returns {"members": [ContactListMemberOut, ...], "cursor": str|None, "total": int}.
    No flag check.
    """

def list_members_for_send(list_id: str) -> Iterator[str]:
    """
    Generator. Paginates ByListJoinedAt GSI (all members).
    For each member, calls is_user_opted_out(party_id) live.
    Yields party_id only when opted-out returns False.
    Callers (MKT-009) consume this iterator for send-resolution.
    No flag check (reads are always safe).
    """

def seed_from_contacts(owner_id: str, list_id: str) -> dict[str, int]:
    """
    1. _require_flag()
    2. _assert_list_owner(owner_id, list_id)
    3. Query T.contacts KeyConditionExpression=Key("owner_id").eq(owner_id)
       Paginate with Limit=500 until no LastEvaluatedKey (mirrors contacts.py:67-78)
    4. For each contact item, call add_member(owner_id, list_id, contact["contact_id"])
       Dedup is handled by add_member's conditional put.
    5. Return {"added": N, "already_present": M, "total_contacts": P}
    Emits one audit_event("contact_list.seeded_from_contacts", ...) after all adds.
    """
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent `create_list`

`create_list` uses a conditional put with `ConditionExpression="attribute_not_exists(pk)"`. The `pk` value is `OWNER#{owner_id}` and the `sk` is `LIST#{list_id}`. Since `list_id` is deterministic (sha256 of `owner_id|name|created_bucket`), two calls within the same hour with the same `owner_id` and `name` produce the same `list_id` and the same `pk`/`sk`. The second call hits `ConditionalCheckFailedException`, at which point the service reads back the existing item and returns it as a `ContactListOut`. The caller sees HTTP 200 (not 201) on the retry — distinct status codes are not exposed; `get_item` is used for the read-back, not an additional put.

### 5.2 Idempotent `add_member` (duplicate no-op)

The member row uses `pk=LIST#{list_id}`, `sk=PARTY#{party_id}`. The conditional put uses `ConditionExpression="attribute_not_exists(pk)"`. On `ConditionalCheckFailedException`, the service reads the existing member row and returns it without incrementing `member_count`. This means a client that calls `add_member` twice for the same `(list_id, party_id)` pair receives a valid `ContactListMemberOut` both times, and `member_count` on the META row stays accurate.

**Important**: on fresh write the `suppressed` value stored in the member row is the snapshot at add-time. If the party opts out after being added, the stored `suppressed=False` becomes stale. `list_members_for_send` always re-evaluates `is_user_opted_out(party_id)` live; `list_members` (owner view) returns the stored snapshot. This is intentional: the owner sees membership without live opt-out status on every page load (one DDB page-query, no N fan-out calls). Send resolution (MKT-009) always uses the live check via `list_members_for_send`.

### 5.3 `remove_member` guards on existence

`delete_item` with `ConditionExpression="attribute_exists(pk)"` raises `ConditionalCheckFailedException` when the member row does not exist. The service catches this and raises `HTTPException(404, "Member not found")`. Attempting to remove a member who was never added is explicitly a 404, not a silent no-op, to surface integration bugs in callers.

### 5.4 `member_count` floor at zero

If a remove races with a concurrent import that already decremented the count, `member_count` could theoretically go negative. The `remove_member` update expression uses:

```python
UpdateExpression="SET member_count = if_not_exists(member_count, :zero) + :neg_one, updated_at = :ts",
ExpressionAttributeValues={":neg_one": -1, ":zero": 0, ":ts": now_ts()}
```

If DDB atomic arithmetic would produce a negative result, DynamoDB does not enforce a floor automatically; the service must handle reconciliation separately. A background reconciliation pass (COUNT query on `ByListJoinedAt` GSI + update META row) is out of scope for this ticket and recorded in Section 10 as an open question.

### 5.5 `seed_from_contacts` — large contact books

The contacts query uses `Limit=500` per page with `LastEvaluatedKey` pagination (matching `app/routers/contacts.py:67-78`). Each contact's `add_member` call is a separate conditional put; there is no batch write path. For a contact book of N contacts, `seed_from_contacts` makes O(N) DDB write calls. This is acceptable for expected contact-book sizes (typically < 5000 contacts). Very large contact books should be handled by background workers in a future enhancement.

### 5.6 Opt-out display to list owner

`ContactListMemberOut.suppressed=True` informs the list owner that a specific `party_id` has opted out. This exposes opt-out state indirectly (the owner learns a user is opted out without the user having explicitly told the owner). This is an accepted trade-off for the campaign-management use case, where suppressions are mandatory to honor. The privacy impact and any legal-compliance requirements (GDPR/CAN-SPAM) must be confirmed; see Section 10 Open Question 6 (carried from MKT-003 spec).

### 5.7 `delete_list` does not cascade to member rows

Eagerly deleting all member rows on list deletion requires a full GSI scan of `LIST#{list_id}` followed by individual `delete_item` calls — potentially thousands of calls for a large list. This ticket scopes deletion to the META row only. Orphaned member rows (`LIST#{list_id}` / `PARTY#{party_id}` with no corresponding META row) are benign — any future query for a deleted list will 404 at the META check before reaching member rows. A background cleanup job for orphaned members is a follow-up outside this ticket's scope.

### 5.8 Ownership enforcement

The service always passes `owner_id` derived from the authenticated session's `user_sub`. `_assert_list_owner` validates that the META row exists at `OWNER#{owner_id} / LIST#{list_id}`. A request for a list owned by a different user will 404 (the owner prefix differs, so the item is not found). No separate authorization check beyond the existence gate is needed, because the PK encodes ownership.

### 5.9 Profile existence check on `add_member`

`get_profile_identity(party_id)` (imported from `app/services/profile.py:305`) is called before writing the member row. **Important**: `get_profile_identity` does NOT raise an exception for a missing profile — it calls `get_profile()` (line 262), which returns `empty_profile()` (an empty dict with all-`None` values) when the DDB item is absent. To prevent phantom member rows for non-existent users, `add_member` must check whether the returned identity is empty (e.g. `all(v is None for v in identity.values())`) and raise `HTTPException(404, "Party not found")` explicitly. The `add_contact` handler in `app/routers/contacts.py:92-98` demonstrates the pattern of wrapping `get_profile_identity` in `try/except`, but it falls back gracefully rather than rejecting — `add_member` must instead reject. In `seed_from_contacts`, this check is an implicit belt-and-suspenders guard; contacts were validated at `add_contact` time but the check still applies.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity**: `T.contact_lists` resolves to DynamoDB Local at port 8001 in dev (sourced from `DDB_ENDPOINT_URL` in `.env.local`) and to real DynamoDB in prod. No `if S.dev_mode` branch exists in `marketing_lists.py`. `is_user_opted_out` calls the same `T.cart_reminder_config` handle in both environments. `get_profile_identity` calls `T.profile` in both environments. There is no mock/stub path — SECOPS-007 compliance is automatic.

**Idempotency**: Every mutating path has a defined idempotency contract:
- `create_list`: same `(owner_id, name)` within the same hour → same `list_id`, conditional put fails, existing item returned.
- `add_member`: same `(list_id, party_id)` → conditional put fails, existing member row returned, `member_count` unchanged.
- `seed_from_contacts`: calls `add_member` for each contact; each call is individually idempotent; re-running seed never writes duplicate rows or double-counts `member_count`.
- `remove_member`: removing a non-existent member → 404. Removing an already-removed member is not silently idempotent; callers should treat 404 as "already removed" if necessary.
- `delete_list`: deleting a non-existent list → 404 from `_assert_list_owner`. Callers should treat this 404 as "already deleted".

**Security**:
- Ownership is enforced by PK prefix. The authenticated `user_sub` is the `owner_id` in every call; cross-owner access is structurally impossible with the current PK scheme.
- `ContactListMemberIn.party_id` has `min_length=1` (from MKT-003 spec, `app/models.py`), preventing the empty-string `PARTY#` suffix edge case.
- `get_profile_identity` validates party existence before write, preventing phantom rows.
- Opt-out is re-evaluated live at send time (`list_members_for_send`), so a delayed opt-out is always honored before any message leaves the platform.
- `audit_event` writes a record to `T.alerts` for every mutating operation — list creation, member add/remove, delete, seed — enabling audit trail reconstruction.
- No PII is stored in the member row beyond `party_id` (a `user_sub`, not email/name). `display_name` is stored as a convenience cache (from `get_profile_identity`) but is not used for auth or billing decisions.

## 10. Open Questions / Assumptions

1. **Assumption**: `marketing_lists.py` is the service file name (a sibling to `marketing_campaigns.py`), as suggested by the ticket description's parenthetical "or a sibling `app/services/marketing_lists.py`". The alternative of putting list logic directly in `marketing_campaigns.py` would make that file very large. This spec chooses the sibling file.

2. **Assumption**: `ContactListUpdateIn` is added to `app/models.py` as part of this ticket (MKT-003 only defines `ContactListCreateIn`). If the team prefers to add it in MKT-003's file changes, MKT-007 would just import it — either approach is valid.

3. **Open question**: `delete_list` leaves orphaned member rows. A `DELETE /ui/marketing/lists/{id}` endpoint that returns 204 is clean from the API perspective, but production DDB accumulation of orphaned `LIST#{id}/PARTY#{id}` rows could be significant for lists with many members. Options: (a) eager deletion in a loop (slow, unbounded), (b) background cleanup job keyed on a `deleted_at` marker, (c) accept the orphan (storage is cheap, rows are never read after list deletion). Option (c) is assumed here; confirm with the team.

4. **Open question**: `remove_member` with `ConditionExpression="attribute_exists(pk)"` returns 404 for non-existent members. Some callers (e.g., a sync loop removing many members) may prefer a silent no-op on 404. Should `remove_member` be idempotent-silent or 404-explicit? This spec chooses 404-explicit to surface double-remove bugs. Confirm with API consumers.

5. **Assumption**: `member_count` can theoretically go negative if a `remove_member` call races with a separate process that also decremented it. The spec documents this as a known drift risk and defers reconciliation to a background job. The counter is a display hint, not an authoritative membership count — actual membership is always queryable via `list_members`.

6. **Open question (privacy — from MKT-003 spec Section 10 Q6)**: `ContactListMemberOut.suppressed=True` reveals to the list owner that a specific `party_id` has opted out of marketing communications. Legal review (GDPR Article 6, CAN-SPAM) is required before shipping to confirm this disclosure is permissible. An alternative is to never surface `suppressed=True` to the owner and simply omit suppressed parties from all list-member API responses — trading owner visibility for privacy. Needs PM/legal sign-off.

7. **Assumption**: the `ByListJoinedAt` GSI on `ContactLists` is keyed on `list_id` (S) / `joined_at` (N). Member rows write `list_id` as a top-level attribute (distinct from the PK value `LIST#{list_id}`). This means the member row must explicitly set `list_id = <bare_id>` (without the `LIST#` prefix) as a projected attribute. META rows do not write `list_id` and therefore do not appear in this GSI (sparse index behavior). Implementers must ensure member rows always write the bare `list_id` attribute.

8. **Assumption**: `list_members_for_send` makes a live `is_user_opted_out(party_id)` call per member. For a list with N members, this is N synchronous DDB `get_item` calls. For large lists (>10,000 members), this is slow. MKT-009 (campaign send) will need to run `list_members_for_send` in a background task, not in a synchronous request path. This constraint is noted here; MKT-009 is responsible for the async execution pattern.

9. **Assumption**: `seed_from_contacts` runs synchronously in the request-response cycle. For users with large contact books (>1000 contacts), this may exceed the default FastAPI request timeout. A background-task version (`BackgroundTasks.add_task(seed_from_contacts, ...)`) should be considered when the feature is production-tested. This is a follow-up outside this ticket's scope.
