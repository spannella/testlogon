# OFB-012 — Returns/RMA E2E tests

## 1. Summary & Goal

OFB-012 adds `frontend/e2e/returns-rma.spec.ts`, a Playwright E2E spec that exercises the full Returns/RMA lifecycle end-to-end against the running dev stack. The suite covers:

1. **Full lifecycle** — `requested → approved → received → refunded → closed` driven entirely through the HTTP API layer.
2. **Reject path** — admin rejects at both the `requested` and `approved` states; illegal transition is caught as 409.
3. **Restock verification** — after `received`, the inventory on-hand count has increased by the returned quantity (visible via the inventory API).
4. **Refund-idempotency** — a second call to `POST /ui/returns/admin/{id}/refund` is a no-op: status stays `refunded` and the billing ledger contains exactly one refund entry.
5. **Customer-ownership guard** — Bob cannot read or act on Alice's return (404).
6. **Flag-off guard** — all endpoints 404 when `RETURNS_RMA_ENABLED=false` (but the flag is ON for this spec since we are testing live behavior).
7. **Admin-role guard** — Alice (role=USER) receives 403 on admin endpoints.
8. **My-Returns list** — `GET /ui/returns` (added in OFB-011) lists only the caller's own returns.

The spec is purely API-driven (no UI navigation) except for two UI smoke-tests that verify the `My Returns` and `RMA Queue` pages render when the flag is on. It uses the standard `e2e_admin_session_setup.py` session bootstrap, matches the Playwright config in `frontend/playwright.config.ts` (1 worker, 1 retry, Chromium, 30 s timeout), and follows the auth/CSRF/DDB helper patterns established in `frontend/e2e/cart-abandonment.spec.ts` and `frontend/e2e/inventory.spec.ts`.

## 3. Data Model

OFB-012 creates no new DynamoDB tables and makes no schema changes. It depends on the tables established by OFB-008 through OFB-011:

### `returns` table (established by OFB-008, extended by OFB-011)

```
PK  return_id  (S)
SK  sk         (S)   "META" | "ITEM#{n}"
```

GSIs (as defined in `scripts/local-ddb-init.py:2483–2492`, to be extended by OFB-011):

| Index       | Partition key | Sort key     | Notes                            |
|-------------|--------------|--------------|----------------------------------|
| `GSI_ORDER` | `order_id`   | `created_at` | Used by `list_returns_for_order` (`returns_rma.py:280`) |
| `GSI_STATUS`| `status`     | `created_at` | Used by `list_returns_by_status` (admin queue, `returns_rma.py:298`) |
| `GSI_USER`  | `user_sub`   | `created_at` | **Not yet in codebase** — added by OFB-011 for `list_returns_by_user` |

`attr_types={"created_at": "N"}` — declared at `local-ddb-init.py:2491`, covers all three GSI sort keys.

> **Note**: `GSI_USER` (pk=`user_sub`) does NOT yet exist in `scripts/local-ddb-init.py` for the `returns` table (only GSI_ORDER and GSI_STATUS are present at line 2488–2489). A `GSI_USER` named index exists on the `orders` table (`local-ddb-init.py:291`) but with pk=`user_id`, not `user_sub`. The `returns` table `GSI_USER` is an OFB-011 deliverable.

### `orders` and `order_items` tables (pre-existing)

The spec seeds order records directly via the DynamoDB helper (Python inline script), because the cart-purchase flow creates orders whose `order_id` is a deterministic SHA-256 of the correlation ID — using the actual purchase API would require a full catalog-item and cart setup and would re-test OFB-002 scope. A direct DDB seed is simpler and test-isolated.

### `inventory` table (pre-existing)

PK=`sku`, SK=`location_sk`. The spec seeds an initial `on_hand` count via `inventory.adjust` (called through the inventory API `PATCH /ui/catalog/items/{itemId}/stock` or directly via DDB) so that restock assertions have a known baseline.

### `billing` table (pre-existing)

PK=`pk` (user-scoped, `USER#{sub}`), SK=`sk`. The spec reads ledger entries via `GET /ui/billing/ledger` filtered to `reason=refund` to count refund rows.

## 5. Detailed Behavior & Edge Cases

### Section 1 — Customer request flow (API)

**Before-all**: seed an order for Alice (`seedOrder(aliceSub, {sku: "ERMA01", qty: 3, unitCents: 400})`). Seed inventory: 10 on-hand for `ERMA01` via `setOnHand`. All tests share one `alicePage` and one `charliePage` (admin).

**Tests**:

1.1 `POST /ui/returns` creates a return in `requested` state; response has `return_id`, `status=requested`, `lines[0].quantity=2`, `lines[0].amount_cents=800` (proration: 400 * 2).

1.2 `GET /ui/returns/{return_id}` returns the same record; ownership is correct.

1.3 `GET /ui/returns` (list-my-returns) includes the new return in the list; `status=requested`.

1.4 Duplicate open return → 409 with message containing "open return already exists".

1.5 Over-quantity request → 422.

1.6 Unknown `item_id` → 422.

1.7 Unknown `order_id` → 404.

1.8 Bob's `GET /ui/returns/{alice_return_id}` → 404 (ownership).

### Section 2 — Admin approve + receive + restock (API)

**Continues with the return from Section 1** (state=`requested`).

2.1 `GET /ui/returns/admin/queue?status=requested` includes Alice's return.

2.2 Admin (charlie) `POST /ui/returns/admin/{id}/approve` → `status=approved`, `decided_by=charlie_sub`.

2.3 Admin `GET /ui/returns/admin/queue?status=requested` no longer contains the return.

2.4 Admin `GET /ui/returns/admin/queue?status=approved` contains the return.

2.5 `POST /ui/returns/admin/{id}/receive` → `status=received`; inventory on-hand for `ERMA01` is now `10 + 2 = 12` (verified via `getOnHand`).

2.6 Replay of receive (same endpoint called a second time): returns 200 with `status=received`; on-hand is still `12` (no double-restock).

### Section 3 — Refund + close (API)

**Continues with the return from Section 2** (state=`received`).

3.1 `POST /ui/returns/admin/{id}/refund` → `status=refunded`, `refund_amount_cents=800`, `provider=stripe`, `refund_ledger_sk` is non-empty.

3.2 Billing ledger has exactly one entry with `reason=refund` for Alice (`countRefundLedgerEntries(alicePage)` = 1).

3.3 Replay refund (double-refund idempotency): returns 200 with `status=refunded`; ledger count is still 1.

3.4 `POST /ui/returns/admin/{id}/close` → `status=closed`.

3.5 Attempting `approve` on a `closed` return → 409 (illegal transition).

3.6 `GET /ui/returns/{id}` for Alice shows `status=closed`.

### Section 4 — Reject path (API)

**New return seeded in before-all** (separate order to avoid duplicate-open conflict).

4.1 Admin rejects from `requested` state with note "not eligible" → `status=rejected`, `decision_note="not eligible"`.

4.2 Attempting `receive` on a `rejected` return → 409.

4.3 `GET /ui/returns/admin/queue?status=rejected` includes the return.

4.4 New return on another order; admin approves it → `status=approved`; then rejects from `approved` → `status=rejected`. (OFB-009 defines that `approved → rejected` is valid per `_VALID_TRANSITIONS` at `returns_rma.py:53–60`.)

4.5 Admin rejects an already-rejected return: returns 200 idempotently (the `_require_transition` function at `returns_rma.py:357–365` treats `current == target` as a no-op).

### Section 5 — Role + flag guards (API)

5.1 Alice (USER role) calling `GET /ui/returns/admin/queue` → 403.

5.2 Alice calling `POST /ui/returns/admin/{id}/approve` → 403.

5.3 Unauthenticated `POST /ui/returns` (no cookies) → 401 or redirect to login (handled by `require_ui_session`).

5.4 Admin calling `POST /ui/returns` → 200 (admin is also a valid session user and can file a return on their own orders — no restriction in the service layer).

### Section 6 — My-Returns list via GSI_USER (API)

6.1 Alice has at least two returns (from Sections 1 and 4). `GET /ui/returns` returns an array containing both, ordered newest-first.

6.2 Bob has no returns. `GET /ui/returns` as Bob returns an empty array (not 404).

6.3 Each entry in the list has `return_id`, `status`, `order_id`, `refund_amount_cents` but `lines: []` (list view omits line detail — per the `list_returns_by_user` design in OFB-011).

### Section 7 — Partial-quantity proration (API)

7.1 Alice files a return on a 4-item order requesting only 1 unit (`qty=1, unitCents=250`). After approve/receive/refund, `refund_amount_cents=250`.

7.2 Alice files a return on the same order for 3 units. The duplicate-open guard fires with 409 (the prior return from step 7.1 is still open until closed). Close it first, then the second request succeeds with `refund_amount_cents=750`.

### Section 8 — UI smoke tests (browser navigation)

**Requires OFB-011 UI to be built; test is marked as `test.skip` if `VITE_RETURNS_RMA_ENABLED` is not set in the frontend env. The section is included in the spec as specified by OFB-012's AC — "Suite passes under the standard Playwright config" — with a guard that makes it conditional.**

8.1 Alice navigates to `/my-returns`; page renders a heading matching `/my returns/i` and a "Request a Return" button (or equivalent trigger).

8.2 Admin navigates to `/admin/rma-queue`; page renders a heading matching `/rma queue/i` and a status filter.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

`app/services/returns_rma.py:36–37` explicitly documents the parity contract: "identical code in dev (moto / local DDB) and prod (real DDB); no `dev_mode` branch in the business logic." The E2E suite runs against the exact same code path that production uses.

The billing side-effect (`new_ledger_entry` / `apply_balance_delta` / `settle_or_reverse_ledger`) is the same code used by `billing.refund_payment` (`app/routers/billing.py:1287`). No parallel refund mechanism exists.

### Idempotency

Two idempotency properties are verified by the spec:

1. **Receive-restock idempotency** (Section 2.6): the single-writer conditional `_transition("approved" → "received")` at `app/services/returns_rma.py:420` means a second `receive` call finds the row already in `received` state, the condition fails silently (`_transition` returns `None`), and the service returns the current state without triggering a second `inventory.adjust`.

2. **Refund idempotency** (Section 3.3): the conditional `_transition("received" → "refunded")` at `app/services/returns_rma.py:481–489` means a second refund call returns `None` from `_transition`, skipping the `new_ledger_entry` / `apply_balance_delta` calls. Exactly one ledger row is posted across unlimited replays.

### Security — CSRF

All non-GET requests include an `x-csrf-token` header matching the session's stored `csrf_token` value (fetched from the admin session dict). Omitting it → 403. This is tested implicitly (the spec's helpers always include it) and explicitly in Section 5.3.

### Security — ownership

`app/routers/returns_rma.py:49–52`: `GET /ui/returns/{return_id}` returns 404 (not 403) for a foreign return, to avoid information leak. The spec verifies this (Section 1.8). Admin endpoints bypass this check by design (admins see all returns via the queue).

## 8. Backward Compatibility & Migration

OFB-012 is a pure test addition. It writes no production code. Existing tests (`test_ofb_returns_rma.py`, shop/cart/billing E2E specs) are entirely unaffected: the RMA router is additive, the billing table schema is unchanged, and the orders/inventory tables receive only reads during RMA tests.

## 10. Open Questions / Assumptions

1. **`GET /ui/inventory/items/{sku}` exists**: Verified — `app/routers/inventory.py:36` exposes `GET /ui/inventory/items/{sku}` (not `/ui/inventory/{sku}` — the `/items/` segment is required). Returns `InventoryRecordOut` with `on_hand` field (`app/models.py:587`). RESOLVED.

2. **`GSI_USER` present before spec runs**: OFB-011 is a hard dependency. The `GET /ui/returns` list endpoint will not exist and the test will fail with 404/405 if OFB-011 has not landed. The spec notes this dependency in its file-header comment.

3. **`INVENTORY_RESERVATIONS_ENABLED` must be ON**: Restock tests (Section 2.5–2.6) require this flag. The spec includes a before-all canary for it — if the inventory flag is off the restock sub-tests skip rather than fail (since the RMA still succeeds without restock).

4. **Billing ledger API shape**: Verified — `GET /ui/billing/ledger` (`app/routers/billing.py:2448–2454`) returns `{"items": [{sk, reason, type, amount_cents, state, ts, ...}]}`. The response key is `items`, not `entries`. The `reason` field is written by `new_ledger_entry` (`billing_shared.py:250`) and will be `"refund"` for RMA refund entries. RESOLVED.

5. **Deterministic order_id across retries**: The seed helper uses `SHA-256(TS + userSub + sku)` as the order ID, which is stable for one `TS` value (module load time). On Playwright retry the same worker is reused (no module re-load in `workers:1`), so the same `orderId` is produced. This is intentional — DDB `put_item` on retry silently overwrites the identical seed rows.

6. **Admin cannot read Alice's individual return via `GET /ui/returns/{id}`**: The router's ownership check (`returns_rma.py:49`) compares `rec.user_sub` to `session.user_sub`. An admin whose `user_sub != alice_sub` will get 404 on the customer endpoint. Admin reads go through `GET /ui/returns/admin/queue` instead. This is tested in Section 5.

7. **`order_id` in `order_items` PK/SK**: The existing unit test seeds `T.order_items.put_item(Item={"order_id": order_id, "item_id": "1", ...})` (`tests/test_ofb_returns_rma.py:142–148`) — verifying that `order_items` has composite key `(order_id, item_id)`. Confirmed by `app/core/tables.py:130` (`T.order_items`) and `app/core/settings.py:1125` (`order_items_table_name`). The DDB seed helper in the E2E spec uses the same key shape.

8. **`on_hand` field name in inventory response**: Verified — `InventoryRecordOut.on_hand` (`app/models.py:587`) is the serialized field name. RESOLVED.

9. **Section 8 UI smoke tests**: These require the OFB-011 React pages to be built and the Vite dev server running with `VITE_RETURNS_RMA_ENABLED=true`. The section is always included in the spec file but wrapped in a `test.skip` condition that checks `process.env.VITE_RETURNS_RMA_ENABLED`. This satisfies the AC ("Suite passes under the standard Playwright config") because skipped tests are not failures.

10. **Partial-quantity second return (Section 7.2)**: The spec closes the first return before requesting a second on the same order, relying on `close_return` going from `refunded` to `closed`. The `_OPEN_STATUSES = {"requested", "approved", "received"}` set (`app/services/returns_rma.py:61`) means a `closed` return does not block a new one. This logic is confirmed in `request_return`'s open-return guard (`app/services/returns_rma.py:197–199`).
