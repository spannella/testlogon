## 1. Summary & Goal

OFB-007 extends `frontend/e2e/inventory.spec.ts` (which currently covers Sections 1–5, the SHOP-001 `stock_count` scalar path) with **Sections 6–9** that validate the **OFB-004 reservation lifecycle** and the **OFB-006 admin inventory page** end-to-end under real backend conditions.

The four new sections are:

| Section | Scope | Test count (target) |
|---------|-------|---------------------|
| 6 — Reservation lifecycle API | reserve → commit, release, expire; oversell 409 | 7 |
| 7 — Checkout: reservation-on-checkout happy path | add-to-cart reserves; purchase commits | 4 |
| 8 — Low-stock alert surfacing | admin `/low-stock` status list (8.1–8.3); `inventory.low_stock` alert stream (8.4 — `test.fixme`, OFB-005 not yet wired) | 4 |
| 9 — Admin Inventory UI | `/admin/inventory` page: look up SKU, set on-hand, inline adjust, low-stock table | 5 |

**Total new tests:** 20. Combined with the existing 21 tests in Sections 1–5, the file grows to ~41 tests. All must pass under the standard 1-worker Playwright config (`frontend/playwright.config.ts`).

The sections exercise the endpoints exposed by `app/routers/inventory.py` (mounted at `/ui/inventory`, `app/main.py:877`) and the `InventoryAdmin` React component (`frontend/src/pages/shop/admin/InventoryAdmin.tsx`). With `INVENTORY_RESERVATIONS_ENABLED=false` (the default) every `/ui/inventory` handler returns 404 (`app/services/inventory.py:54–56`); the new sections are therefore only meaningful when the flag is on and must be skipped (or expected to return 404) otherwise. The spec handles this via a compile-time env-var check mirroring the existing `isInventoryReservationsEnabled()` pattern in the frontend.

## 5. Detailed Behavior & Edge Cases

### Section 6 — Reservation lifecycle API (7 tests)

**Setup:** `beforeAll` creates a catalog item with `stock_count=10` (for catalog compatibility) via `catPost`, then seeds the inventory record for the same SKU via `PUT /ui/inventory/items` with `on_hand=10, reorder_point=3` using Charlie's admin session. The SKU used is `catalog:{item_id}` — the same format that `shoppingcart.py` uses when building `sku` values from cart line items.

**6.1 Reserve reduces available without changing on_hand**
- `POST /ui/inventory/reservations` with `sku, quantity=4` from Bob's session → expect 200, `status="active"`, `quantity=4`.
- `GET /ui/inventory/items/{sku}` → `on_hand=10`, `reserved=4`, `available=6`.

**6.2 Commit converts reservation to on-hand decrement**
- Extending 6.1's reservation: directly call commit via the router. Note: there is no HTTP endpoint for commit (OFB-004 design: commit is called internally by `purchase_cart`). The test covers this indirectly via Section 7 (checkout). For the API section, the test verifies `commit_reservation` state via a Python helper script called via `execSync` that invokes the service function directly, OR — simpler — Section 6 only tests reserve and release via HTTP, and leaves commit to Section 7. Recommended approach: Section 6 covers reserve/release/expire; Section 7 covers commit via purchase.

**6.3 Release reservation restores available**
- Reserve 4 units → release via `POST /ui/inventory/reservations/{id}/release` → `GET /ui/inventory/items/{sku}` → `available=10`, `reserved=0`.

**6.4 Double-release is idempotent (200 on second release attempt)**
- Reserve → release → release again → second `POST .../release` returns **200** with the existing terminal reservation object (status=`"released"`). The router (`app/routers/inventory.py:117–126`) passes any non-missing reservation to `inv.release_reservation`; the service's `_close_reservation` (`app/services/inventory.py:434–453`) returns `None` (idempotent no-op) when the reservation is already terminal, and `release_reservation` then returns the existing record via `get_reservation` (`app/services/inventory.py:501–505`). A 404 is only returned if the reservation row is entirely missing.

**6.5 Oversell prevention: 409 on insufficient available**
- Seed SKU with `on_hand=2`. Bob reserves 2 → 200. Bob tries to reserve 1 more → 409 with detail containing "out of stock" (`app/services/inventory.py:371` ✓: `detail=f"Item '{sku}' is out of stock"`).

**6.6 Foreign reservation returns 404**
- Bob reserves a unit → Alice tries to release Bob's reservation → 404 (ownership check at `app/routers/inventory.py:123–124` ✓).

**6.7 Reserve on nonexistent inventory row → 409**
- Call `POST /ui/inventory/reservations` with a SKU that has no inventory row (never seeded) → 409 with detail `"No inventory for SKU '{sku}'"` (`app/services/inventory.py:359` ✓).

### Section 7 — Checkout reservation-on-checkout happy path (4 tests)

These tests confirm the OFB-004 integration between `shoppingcart.purchase_cart` and the reservation service when the flag is on. They require that OFB-004's wiring of `purchase_cart` is complete (see §11 dependency note). With the flag off these tests skip.

**Setup:** Seed `on_hand=5`, `reorder_point=1` for a catalog item. Bob creates a cart and adds 2 units.

**7.1 add-to-cart creates a reservation**
- After `POST /ui/shoppingcart/carts/{id}/items`, call `GET /ui/inventory/items/{sku}` → `reserved=2`, `available=3`. This verifies that `add_catalog_item` calls `inventory.reserve(...)` when the flag is on.

**7.2 Purchase commits reservation → on_hand decremented**
- After purchasing the cart: `GET /ui/inventory/items/{sku}` → `on_hand=3`, `reserved=0`, `available=3`. The reservation row should be `status="committed"`.

**7.3 Cart deletion releases reservation**
- Bob creates a cart, adds 2 units (reservation created), then `DELETE /ui/shoppingcart/carts/{id}` → `GET /ui/inventory/items/{sku}` → `available=5` (restored).

**7.4 Oversell at purchase time: two buyers race for the last unit**
- Seed `on_hand=1`. Alice and Bob each create a cart and add 1 unit. The first to `add_catalog_item` gets the reservation; the second's `add_catalog_item` returns 409. Only one cart purchase succeeds.

### Section 8 — Low-stock alert surfacing (4 tests)

**Setup:** Seed `on_hand=10`, `reorder_point=5` for a fresh SKU using Charlie's admin session.

**8.1 Crossing threshold emits low-stock status**
- `POST /ui/inventory/items/adjust` with `delta=-6` → `available=4` (`4 <= 5` → `low_stock`). `GET /ui/inventory/items/{sku}` → `status="low_stock"`.

**8.2 Low-stock list includes the SKU**
- `GET /ui/inventory/low-stock` from Charlie's session → response `{"items": [...]}` contains the SKU with `status="low_stock"`.

**8.3 Recovery removes SKU from low-stock list**
- After 8.1: `POST /ui/inventory/items/adjust` with `delta=+10` → `available=14` (`14 > 5` → `in_stock`). `GET /ui/inventory/low-stock` → SKU no longer present (or `status` is `in_stock`).

**8.4 Low-stock alert appears in alert stream (OFB-005 not yet wired — `test.fixme`)**
- After crossing down: `GET /ui/alerts` from Alice's session (catalog item owner) → check for an alert with the correct SKU in `details`. **Always mark `test.fixme`**: OFB-005 injection into `app/services/inventory.py`'s `adjust()` is not yet implemented; no `inventory.low_stock` event is emitted by the OFBiz inventory path. (The existing `catalog.low_stock` alert emitted by `app/routers/catalog.py:643` is unrelated — it fires only from `PATCH /ui/catalog/items/{id}/stock` on the legacy `stock_count` path, and only when `CATALOG_STOCK_ALERTS_ENABLED` is on.) The alert surfacing via `GET /ui/inventory/low-stock` (test 8.2) confirms the data model regardless of alert plumbing.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No dev_mode branches in tested code

`app/services/inventory.py` contains no `S.dev_mode` branch — the same conditional-update logic runs against DynamoDB Local in dev and real DynamoDB in prod. The E2E tests therefore validate the exact prod code path (SECOPS-007 parity).

### 7.2 Idempotency validated in tests

Section 6.4 (double-release) and 7.4 (oversell race) explicitly cover the idempotency and single-writer guarantees of `_close_reservation` (`app/services/inventory.py:434–453` ✓). The conditional update `ConditionExpression="#status = :active"` (`app/services/inventory.py:444`) ensures a second release/commit/expire on a terminal reservation is an idempotent 200 (returns existing terminal record), not a double-count or an error.

### 7.3 CSRF enforcement

All state-changing test requests include the `x-csrf-token` header from the seeded session (mirroring the CLAUDE.md pattern for cookie-auth non-GET requests). The router uses `require_admin_or_root_csrf` for admin mutations (`app/routers/inventory.py:48, 65`) and `require_ui_session` for customer reservations (`app/routers/inventory.py:37, 92, 107, 118`).

### 7.4 Ownership isolation (Section 6.6)

The foreign-reservation test (6.6) confirms that `get_reservation` and `release_reservation` enforce ownership via the `user_sub` check at `app/routers/inventory.py:112–113` (GET handler) and `app/routers/inventory.py:123–124` (release handler). A customer cannot release another user's reservation.

### 7.5 Test data isolation

Each section `beforeAll` creates uniquely-named SKUs using `Date.now()` as a suffix (consistent with the existing `TS = Date.now()` pattern in the file). This prevents cross-section SKU collisions on a long-running DynamoDB Local instance. Sections do not share SKUs across section boundaries.

## 10. Open Questions / Assumptions

1. **OFB-004 `purchase_cart` wiring status** — Section 7 assumes that OFB-004's hook of `reserve` into `add_catalog_item` and `commit_reservation` into `purchase_cart` is complete. If `shoppingcart.py` has not yet been updated to call the reservation service (a search for `reserve` in `shoppingcart.py` currently returns zero hits), Section 7 tests will see `reserved=0` after add-to-cart and the section must be marked `test.fixme` until the wiring lands. This must be verified against the current branch before running.

2. **SKU namespace for inventory vs catalog** — The tests use `sku = "catalog:{item_id}"` to match the cart's SKU convention for catalog items (`shoppingcart.py` builds `sku = f"catalog:{item_id}"` for line items). The OFB-003 inventory service accepts any string SKU; the test must ensure the SKU passed to `invSetOnHand` matches exactly the SKU that `purchase_cart` would pass to `inventory.reserve`. This assumption should be verified in the OFB-004 wiring code.

3. **Admin session for mutations** — `PUT /ui/inventory/items` and `POST /ui/inventory/items/adjust` require `require_admin_or_root_csrf`. Sections 6–8 use Charlie's admin session from `e2e_admin_session_setup.py`. If the admin session's `role` is not wired to `ADMIN` or `ROOT` in the JWT cookie (per `e2e_admin_session_setup.py:244`), these calls will 403. The session setup must be verified.

4. **Section 8.4 OFB-005 alert wiring** — The `inventory.low_stock` alert is emitted by `_audit("inventory.low_stock", ...)` inside `_maybe_emit_low_stock_alert` (OFB-005). If OFB-005 injection points in `adjust()` / `reserve()` are not yet present in `inventory.py`, `GET /ui/alerts` will not contain the alert. Test 8.4 is marked `test.fixme` by default; it is only activated once OFB-005 injection is confirmed.

5. **`checkInventoryEnabled` probe distinguishes flag-off from missing record** — The probe calls `GET /ui/inventory/items/__probe__` and checks whether the 404 body contains `"not enabled"`. This assumes the router returns `detail="Inventory reservations are not enabled"` when the flag is off (`inventory.py:56`) and `detail="No inventory record for SKU"` otherwise. Both paths return HTTP 404, so the probe must parse the detail string; this logic is correct as of the current router implementation but fragile if the detail messages change.

6. **Playwright `page.request` carries cookies** — Following the CLAUDE.md pattern, all `page.request.post/put/get` calls in the new sections carry the page's cookie context (including `ui_session` and `ui_csrf`). The CSRF header must be sent explicitly for all non-GET mutations. The `invSetOnHand`, `invAdjust`, and `invRelease` helpers must include `"x-csrf-token": session.csrf_token`.

7. **`test.setTimeout` vs `test(title, {timeout}, fn)`** — Section 9 UI tests that wait for React Query invalidation after mutations may exceed the default 30s timeout. Per CLAUDE.md, `test.setTimeout(N)` inside the test body is used (not the `{ timeout }` option on the `test()` call, which is not reliably honored).
