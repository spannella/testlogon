# MFG-003 — Pydantic models for BOM, routing, work orders & MRP

**Type:** Feature | **Priority:** P0 | **Estimate:** 2 days  
**Milestone:** 1 — Scaffolding & Data Model

---

## 1. Summary & Goal

Add all Pydantic request/response models required by the manufacturing/MRP subsystem to `app/models.py`. These models cover four domains:

1. **Bills of Materials (BOM)** — finished-goods recipes (components, quantities, scrap)
2. **Work Centers** — production stations with capacity and cost rates
3. **Work Orders** — production-run lifecycle (create → release → complete → cancel)
4. **MRP Requirements** — lite-MRP output rows (net requirement, suggested action)

The models are purely additive: with `MANUFACTURING_MRP_ENABLED=false` (the default) they exist in the module namespace but no endpoint exposes them. The inventory/catalog/billing shapes at `app/models.py:584–629` are byte-for-byte unchanged.

## 4. API / Service Design

MFG-003 delivers **only models** — no service functions or router endpoints. The endpoint surface is defined by MFG-011; service logic by MFG-004/007/010. This section describes each model's fields, validators, and intended usage.

### 4.1 BOM models

All model classes are appended to `app/models.py` in a new section after the returns block (currently ending at line 669), preceded by a comment:

```python
# ── OFBiz Manufacturing/MRP (MFG-003) ──────────────────────────────────────
```

#### `BomComponentIn`

```python
class BomComponentIn(BaseModel):
    component_sku: str = Field(min_length=1, max_length=256)
    quantity_per: float = Field(gt=0, le=1_000_000)
    scrap_pct: float = Field(default=0.0, ge=0.0, lt=1.0)
    seq: int = Field(default=0, ge=0, le=9999)
    unit_of_measure: str = Field(default="each", max_length=32)
```

- `quantity_per` is `float` (not `int`) because sub-unit ratios occur in manufacturing (e.g. 0.5 kg of resin per unit). The `gt=0` validator enforces the acceptance criterion "reject ≤ 0".
- `scrap_pct` is in [0, 1) — 5% scrap = 0.05. Upper bound `lt=1.0` prevents 100%-scrap nonsense.
- `seq` controls explosion and display order. Default 0; caller should number them 10, 20, 30, … leaving gaps for insertion.
- `unit_of_measure` is a free-form string (e.g. `"each"`, `"kg"`, `"L"`). Default `"each"`. Added per MFG-004 §3.1 which stores `unit_of_measure` on component rows.

#### `BomComponentOut`

```python
class BomComponentOut(BaseModel):
    component_sku: str
    quantity_per: float
    scrap_pct: float
    seq: int
    bom_id: str
    updated_at: int = 0
```

Returned from BOM component list/read. `bom_id` is denormalized for convenience so a client holding a component row knows its parent.

#### `BomHeaderIn`

```python
class BomHeaderIn(BaseModel):
    product_sku: str = Field(min_length=1, max_length=256)
    name: str = Field(min_length=1, max_length=256)
    output_quantity: int = Field(default=1, gt=0, le=100_000)
    status: Literal["active", "inactive", "draft"] = "draft"
    components: List[BomComponentIn] = Field(default_factory=list)
    correlation_id: Optional[str] = Field(default=None, max_length=128)
```

- `output_quantity` is `int` (whole units per BOM run); `gt=0` satisfies the acceptance criterion.
- `components` list may be empty at create time; components can be added via PATCH later.
- `status` is a `Literal` — the acceptance criterion specifically calls for constrained literals on MRP output; applying the same pattern here keeps the codebase consistent and catches typos at parse time.
- `correlation_id` is the idempotency key used by `create_bom` to derive a deterministic `bom_id = sha256(correlation_id)[:32]` (MFG-004 §2.5). Added per ESCALATIONS §A row 17.

#### `BomOut`

```python
class BomOut(BaseModel):
    bom_id: str
    product_sku: str
    name: str
    output_quantity: int
    status: Literal["active", "inactive", "draft"]
    components: List[BomComponentOut] = Field(default_factory=list)
    created_at: int = 0
    updated_at: int = 0
    created_by: str = ""
```

Assembled by the BOM service by fetching the META row + all `COMP#` rows in a single `query(KeyConditionExpression=Key("bom_id").eq(...))`.

`created_by` reflects the `user_sub` stored on the DDB header row (see MFG-004 §3.1). Defaults to `""` for pre-existing rows that lack the field. Added per ESCALATIONS §A row 17.

#### `BomUpdateIn`

```python
class BomUpdateIn(BaseModel):
    name: Optional[str] = Field(default=None, min_length=1, max_length=256)
    status: Optional[Literal["active", "inactive", "draft"]] = None
```

Used by `PATCH /ui/manufacturing/boms/{bom_id}` to update name and/or status. Both fields are optional; an empty patch is a no-op. `status` is constrained to the same `Literal` set as `BomHeaderIn` to prevent invalid transitions at parse time (service layer enforces allowed-transition rules; see MFG-004 §5.9). Added per ESCALATIONS §A row 17.

#### `ExplodedComponentOut`

```python
class ExplodedComponentOut(BaseModel):
    component_sku: str
    required_qty: float
    depth: int
```

Returned by `GET /ui/manufacturing/boms/{bom_id}/explode`. Each entry represents a leaf raw-material requirement after full multi-level BOM explosion. `required_qty = ceil(quantity_per / output_quantity × build_qty × (1 + scrap_pct))` (from MFG-004 §5.7). `depth` is 1-based (direct component of the top BOM is depth 1). Added per ESCALATIONS §A row 17.

### 4.3 Work Order models

#### `WorkOrderCreateIn`

```python
class WorkOrderCreateIn(BaseModel):
    product_sku: str = Field(min_length=1, max_length=256)
    quantity: int = Field(gt=0, le=10_000_000)
    bom_id: Optional[str] = Field(default=None, max_length=256)
    work_center_id: Optional[str] = Field(default=None, max_length=256)
    correlation_id: Optional[str] = Field(default=None, max_length=256)
```

- `bom_id` is optional; if absent the service resolves the active BOM via `get_active_bom(product_sku)`.
- `correlation_id` is the seed for deterministic `work_order_id = sha256(correlation_id)`. If absent the service generates a UUID as the correlation value — still deterministic for the life of that call, but not re-runnable by the caller without receiving the resulting `work_order_id` back.

#### `WorkOrderIssueOut`

```python
class WorkOrderIssueOut(BaseModel):
    seq: int
    component_sku: str
    required_qty: float
    issued_qty: float
    status: Literal["pending", "issued", "failed"]
    issued_at: int = 0
```

One row per component that was (or should be) issued. Returned embedded in `WorkOrderOut.issues`. A `failed` status row means the `inventory.adjust` call raised a 409 (insufficient stock) and was rolled back — the work-order release itself will have been blocked in that case, so this row appears only on a partial-failure read.

#### `MrpRequirementOut`

```python
class MrpRequirementOut(BaseModel):
    sku: str
    gross_requirement: int
    on_hand_available: int
    scheduled_receipts: int
    net_requirement: int        # may be negative (surplus)
    suggested_action: Literal["produce", "purchase", "none"]
    suggested_quantity: int = Field(ge=0)   # always ≥ 0 even when net_req < 0
```

- `net_requirement = gross_requirement - on_hand_available - scheduled_receipts`. Negative values mean surplus inventory; the acceptance criterion explicitly allows negative here.
- `suggested_quantity = max(0, net_requirement)`.
- `suggested_action` is a `Literal["produce", "purchase", "none"]` — satisfies the acceptance criterion "constrained literal".

## 5. Detailed Behavior & Edge Cases

### Validation rules (enforced at parse time by Pydantic)

| Model | Field | Constraint | Error |
|---|---|---|---|
| `BomComponentIn` | `quantity_per` | `gt=0` | 422 "Input should be greater than 0" |
| `BomComponentIn` | `scrap_pct` | `ge=0, lt=1.0` | 422 |
| `BomHeaderIn` | `output_quantity` | `gt=0` | 422 "Input should be greater than 0" |
| `WorkCenterIn` | `capacity_per_hour` | `gt=0` | 422 |
| `WorkCenterIn` | `cost_per_hour_cents` | `ge=0` | 422 |
| `WorkOrderCreateIn` | `quantity` | `gt=0` | 422 |
| `WorkOrderIssueOut` | `status` | Literal | 422 if not in set |
| `MrpRequirementOut` | `suggested_quantity` | `ge=0` | 422 — surplus is communicated via negative `net_requirement`, not negative `suggested_quantity` |

### Decimal coercion

DynamoDB returns numeric attributes as `decimal.Decimal` via boto3. Pydantic v2 does not coerce `Decimal` to `int`/`float` by default in strict mode. The existing inventory models handle this silently because `app/core/tables.py:11–26` (`_to_decimal`) only affects writes; reads come back as `Decimal`. Following the pattern set by `MessageEncryptionEnvelope` (`@model_validator(mode="before")` at `app/routers/messaging.py:1810` — **not** in `app/models.py`), if a service layer passes raw DynamoDB items directly to these models, each `int`/`float` field receiving a `Decimal` will coerce correctly in Pydantic v2's lax mode (the default). No explicit `model_validator` is required unless a field is typed as `Literal` — `Literal` types do not coerce, so status fields should be stored/read as strings.

### `BomOut.components` ordering

The service fetching a BOM must order the component rows by `seq` before constructing `BomOut`. The model itself imposes no ordering constraint — ordering is a service concern (MFG-004). The `seq` field on `BomComponentOut` enables the client to re-sort if needed.

### `WorkOrderOut.issues` on list vs. detail

List endpoints returning `List[WorkOrderOut]` SHOULD omit the `issues` list (return the default empty list) to keep payloads manageable. The detail endpoint `GET /ui/manufacturing/work-orders/{id}` SHOULD populate `issues` by fetching all `ISSUE#` rows from `T.mfg_work_orders`. The model supports both paths without schema change.

### `MrpRequirementOut` surplus handling

When `net_requirement < 0` (on-hand exceeds demand), `suggested_action = "none"` and `suggested_quantity = 0`. The negative `net_requirement` value is preserved in the response so the admin UI can communicate "X units surplus" without needing a separate field.

### `correlation_id` and deterministic IDs

`WorkOrderCreateIn.correlation_id` and `MrpRunIn.correlation_id` are optional strings that the service layer hashes to derive a stable `work_order_id` / `mrp_run_id`. The model accepts any non-empty string ≤ 256 chars; the sha256 computation happens in the service (MFG-007, MFG-010), not in the model. If `correlation_id` is absent, the service generates a random UUID to use as the seed — the resulting ID is still deterministic for that call instance but unknown to the caller before the call.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

The models are plain Python dataclasses — no `dev_mode` branch is possible or needed. The same schema is used in both environments. The service-level `_require_enabled()` guard (not in this ticket) ensures the models are only reachable in prod when the flag is explicitly enabled.

### Idempotency at the model level

The `correlation_id` fields in `WorkOrderCreateIn` and `MrpRunIn` are the hooks for service-level idempotency. The models make them `Optional` so existing API clients without idempotency requirements work unmodified; the service will accept a missing `correlation_id` by generating a random one, which means the caller loses the ability to replay safely — this is explicitly documented in acceptance criteria for MFG-007.

### Security

No auth logic lives in models. Role enforcement is entirely at the router level (MFG-011 uses `require_admin_or_root_csrf` — defined at `app/auth/policy.py:100`, used at `app/routers/inventory.py:48` — for all write paths). The models do not contain `user_sub` in any `*In` request body — the service always derives `user_sub` from the authenticated session, never from caller-supplied data.

`BomComponentIn.component_sku` and `WorkOrderCreateIn.product_sku` accept any string ≤ 256 characters. SKU existence validation is a service concern (MFG-004 reads `inventory.get_or_zero` at `app/services/inventory.py:158` to confirm the SKU exists before persisting a BOM component). The models themselves apply only length bounds.

## 8. Backward Compatibility & Migration

### Zero impact when flag is off

- `app/models.py` is imported at startup unconditionally; appending new classes after the returns block (line 669) is purely additive. Existing models at lines 584–669 are not touched.
- No `__init__.py` wildcard export exists for `app/models.py` — downstream code imports specific class names. The new classes do not conflict with any existing name.
- The four new DynamoDB tables (MFG-002) are created by `scripts/local-ddb-init.py`; existing tables are unaffected. `just restart` recreates all tables from scratch in dev.

### Migration in prod

No data migration is needed because all four tables are brand-new. The only prod migration step is a `CreateTable` API call (via the DDB init script or CDK) for each of the four tables — no backfill, no schema alteration of existing tables.

### `app/models.py` import stability

MFG-004, MFG-005, MFG-007, MFG-010, and MFG-011 will import specific model classes by name from `app.models`. The import paths are stable from this ticket onward:


## 10. Open Questions / Assumptions

1. **`quantity_per` type: `float` vs `int`** — The ticket text says "integer quantities throughout, matching the inventory record shapes at `app/services/inventory.py:101`". However, manufacturing often requires fractional per-unit quantities (e.g. 0.25 kg of material per widget). This spec uses `float`. If the platform restricts quantities to whole units (e.g. discrete components only), change to `int` with `gt=0`.

2. **`BomComponentOut.bom_id` denormalization** — Assumed useful for REST clients that need to know the parent BOM when iterating components. If the API never returns components without their parent header, this field can be dropped.

3. **`WorkOrderOut.correlation_id` in response** — Assumed the caller needs the correlation ID echoed back so they can confirm which request produced which work order (especially useful for retry scenarios). If this is security-sensitive (could leak intent), it can be omitted.

4. **`MrpRunIn.location_id` scope** — Assumed the MRP run is scoped to a single inventory location (matching `inventory.get_inventory(sku, location_id)` at `app/services/inventory.py:150`). Multi-location MRP is deferred. If the platform decides all MRP is always warehouse-scoped, remove `location_id` from `MrpRunIn`.

5. **`WorkOrderIssueOut.required_qty` vs. `issued_qty`** — `required_qty` is the exploded requirement (from BOM explosion); `issued_qty` is what was actually taken from inventory (may differ if partial issue is allowed). This spec assumes partial issue is not supported in Phase 1 — a failed issue blocks the release entirely — so `required_qty == issued_qty` always on a fully released order. The field is kept separate to accommodate MFG-007's "optional un-issue on cancel" path.

6. **`BomHeaderIn.status` on create** — Defaulting to `"draft"` means new BOMs are not immediately active. The service (MFG-004) must provide a PATCH endpoint to transition `draft → active`. If the platform wants new BOMs to be immediately active (simpler), change the default to `"active"`.

7. **`WorkOrderOut.produced_qty` type** — Used `int` matching inventory convention. If fractional production quantities are ever needed (yield < 100%), this would need to be `float`. For Phase 1 this is `int`.

8. **Scrap pct range** — `scrap_pct < 1.0` enforced (lt=1.0). This means 99.9% scrap is valid (unusual). A tighter bound like `le=0.5` might be more appropriate for the platform's use case.
