## 1. Summary & Goal

PUR-017 is the dedicated test milestone for the entire Purchasing/SCM module.  It delivers two
categories of tests:

1. **Four hermetic offline pytest suites** that verify the service and router layers in isolation —
   no real AWS, no network, moto in-memory DynamoDB tables bound to the frozen `T` handles via
   `object.__setattr__`, route-handler coroutines called directly (no `TestClient`).  Each suite
   focuses on one slice:
   - `tests/test_pur_suppliers.py` — supplier + supplier-product CRUD, cheapest-supplier ordering,
     create idempotency.
   - `tests/test_pur_purchase_orders.py` — PO creation / subtotal math / idempotency, and the full
     lifecycle state machine including every illegal transition (409) and replay idempotency.
   - `tests/test_pur_receiving.py` — full/partial receive, over-receive 422, receipt replay
     idempotency, inventory-disabled path, AP payable flow via a stubbed `new_ledger_entry`.
   - `tests/test_pur_reorder.py` — suggestion math, supplier selection, no-supplier warning,
     convert-to-PO idempotency.

2. **One Playwright E2E spec** (`frontend/e2e/purchasing-scm.spec.ts`) that drives the full
   admin-UI lifecycle — create-supplier → create-PO → approve → receive → inventory increment, plus
   a reorder-suggestion → draft-PO flow — against the running dev stack, using admin sessions from
   `e2e_admin_session_setup.py` with CSRF per the established pattern.

A cross-cutting **flag-off contract** test asserts that with `purchasing_scm_enabled=false` every
purchasing endpoint returns 404 and existing shop/cart/orders/billing/inventory pytest and E2E
suites are unaffected.

No new DynamoDB tables, settings keys, Pydantic models, services, or router endpoints are
introduced by this ticket.  All DynamoDB schemas, service functions, and endpoints are supplied by
PUR-002 through PUR-016.

## 5. Detailed Behavior & Edge Cases

### 5.1 `test_pur_suppliers.py`

**Happy path**
- `create_supplier("ACME", email="acme@test.local", payment_terms_days=30)` writes a `META` row
  under `supplier_id = sha256("supplier:{user_sub}:ACME")[:32]`.
- Calling `create_supplier` again with the same name returns the same `supplier_id` without
  duplicating the DDB row (idempotency via deterministic id + `put_item` with no condition — the
  sha256 collision produces the same PK, so the second call overwrites with identical data).
- `update_supplier(supplier_id, payment_terms_days=45)` updates the `META` row.
- `set_supplier_status(supplier_id, "inactive")` moves the row to `status="inactive"` and is no
  longer returned by `list_suppliers(status="active")`.

**Supplier-product**
- `upsert_supplier_product(supplier_id, "SKU-A", unit_cost_cents=1000, lead_time_days=7, min_order_qty=10)` writes a `SKU#SKU-A` row.
- `list_suppliers_for_sku("SKU-A")` with two suppliers at costs 1500 and 800 returns them ordered
  [800, 1500] (ascending by `unit_cost_cents` via `GSI_SKU`).
- Re-upserting with `unit_cost_cents=750` updates in place; `list_suppliers_for_sku` still returns
  one item at 750.

**Flag-off**
- `object.__setattr__(S, "purchasing_scm_enabled", False)` → `create_supplier(...)` raises
  `HTTPException(404)`.

### 5.2 `test_pur_purchase_orders.py`

**Creation and subtotal**
- `create_purchase_order(supplier_id, lines=[{sku:"SKU-A", quantity_ordered:5, unit_cost_cents:200}], correlation_id="corr-1", created_by="admin-sub")` writes one `META` row with `subtotal_cents=1000` and one `LINE#1` row.
- `get_purchase_order(po_id)` returns `{header: {...}, lines: [{...}]}`.
- Calling `create_purchase_order` again with `correlation_id="corr-1"` returns the same `po_id`
  and does not write duplicate `LINE#n` rows (idempotency: `po_id = sha256("corr-1")[:32]` is
  stable; header/line `put_item` calls are re-entrant or conditional-on-absent).

**State machine — happy path**
```
draft → submit(actor) → submitted → approve(admin) → approved → receive(lines) → received → closed
```
Each transition asserts: status field on META row changes; `updated_at` advances; audit event
emitted (verified via a `_audit` mock).

**Illegal transitions (each → 409)**
- `approved → submitted` (backward)
- `received → approved` (backward past terminal)
- `cancelled → submitted` (from terminal)
- `closed → approved` (from terminal)
- Cancel after any quantity received: `receive_po` partial, then `transition_po(cancel)` → 409.

**Replay idempotency**
- `transition_po(po_id, "approved", actor)` twice in a row: the second call returns the current
  state without error (ConditionExpression `#status = :expected` fails on second call → caught,
  current state read and returned; not a 409 storm).

### 5.3 `test_pur_receiving.py`

**Full receive**
- PO with two lines (SKU-A qty=10, SKU-B qty=5) in `approved` status.
- `receive_po(po_id, [{line_no:1, quantity:10}, {line_no:2, quantity:5}], actor, receipt_correlation_id="rcpt-1")` →
  - Writes `RECEIPT#sha256("rcpt-1")[:32]` row in `po_receipts`.
  - Calls `inventory.adjust("SKU-A", +10, "po_receipt")` and `inventory.adjust("SKU-B", +5, "po_receipt")` (verified via direct inventory query on the moto table).
  - PO header status becomes `received` then auto-transitions to `closed`.

**Partial receive**
- Same PO; receive line 1 only (qty=8 of 10).  `quantity_received[line 1] = 8`.  Status → `partially_received`.
- Second call (qty=2 of line 1 + qty=5 of line 2).  Status → `received` → `closed`.

**Over-receive**
- `receive_po(..., [{line_no:1, quantity:11}])` when `quantity_ordered=10` → `HTTPException(422)`.
- DDB row and inventory unchanged.

**Replay idempotency**
- `receive_po(..., receipt_correlation_id="rcpt-1")` twice: second call detects the existing
  `RECEIPT#sha256("rcpt-1")[:32]` row (read via `GSI_RECEIPT`) and returns the existing receipt
  without re-incrementing inventory.

**Inventory-disabled path**
- `object.__setattr__(S, "inventory_reservations_enabled", False)` with `purchasing_scm_enabled=True`.
- `receive_po` records the receipt row, updates `quantity_received`, but does NOT call
  `inventory.adjust`.  Verified by asserting the `inventory` table remains empty.

**AP payable via stubbed ledger**
- `new_ledger_entry` patched on `po_receiving` module namespace; the stub returns `("LEDGER#fake#1", {})`.
  Because `new_ledger_entry` only constructs the item (it does NOT write), the test must also patch
  the `ddb_put` call that `po_receiving.py` makes after it, or confirm the stub return value is
  never persisted (since `T.billing` is not mounted in this test's setUp — see assumption 5).
- Full receive that transitions PO to `received`: stub is called exactly once with
  `entry_type="ap_payable"`, `amount_cents=po_subtotal_cents`, `reason="supplier_payment"`.
- Second call (replay) does not call the stub a second time (`receipt_correlation_id` is same →
  early return after finding existing receipt).

### 5.4 `test_pur_reorder.py`

**Suggestion math**
- Inventory: SKU-X on_hand=3, reorder_point=10, reserved=0 → `available=3`, `status="low_stock"`.
- Supplier product: `unit_cost_cents=500, min_order_qty=5`.
- `generate_suggestions()` → suggestion for SKU-X: `suggested_qty = max(10-3, 5) = 7` rounded to next MOQ multiple of 5 → `10`.

**Supplier selection**
- Two suppliers for SKU-Y: costs 1200 (supplier B) and 800 (supplier A).
- Suggestion picks supplier A (cheapest, or `preferred=True` wins over cheapest).

**No-supplier warning**
- SKU-Z is `low_stock` but has no supplier-product record.
- `generate_suggestions()` returns `warnings=[{"sku": "SKU-Z", "reason": "no_supplier"}]` and
  does NOT raise.

**Convert-to-PO idempotency**
- `create_purchase_order_from_suggestion("supplier-A", ["SKU-X"])` → creates draft PO with
  deterministic `correlation_id = sha256(f"reorder:{supplier_id}:{sku_list_hash}")[:32]`.
- Calling again: same `po_id` returned, no new LINE rows.

### 5.5 Flag-off contract test (shared across all suites)

A dedicated `test_flag_off_*` method in each suite:
1. `object.__setattr__(S, "purchasing_scm_enabled", False)`
2. Assert `create_supplier / create_purchase_order / receive_po / generate_suggestions` all raise
   `HTTPException(404)`.
3. Import and call `inv.set_on_hand("SKU-SAFE", 5)` with `S.inventory_reservations_enabled=True`:
   assert it succeeds (existing inventory service is unaffected).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity**: All service modules under test use the existing DDB primitives (`T.*`) with
no `if dev_mode` branch.  The `inventory.adjust` call in `po_receiving.py` uses the same code path
in dev (moto in-process) and prod (real DynamoDB) — there is no mock branch.  `new_ledger_entry`
in `billing_shared.py:224` constructs the ledger item (it does NOT perform the DDB write itself —
see section 2.3); `po_receiving.py` must call `ddb_put(T.billing, led_item)` after it.  Tests stub
`new_ledger_entry` at the module-import level rather than branching the production code.

**Idempotency invariants asserted in tests**:
- `create_supplier` same name → same `supplier_id`, no duplicate DDB row.
- `create_purchase_order` same `correlation_id` → same `po_id`, no duplicate LINE rows.
- `receive_po` same `receipt_correlation_id` → second call returns early; inventory not
  double-incremented; `new_ledger_entry` not called twice.
- `transition_po` replay of an already-applied transition → no-op, not 409.
- `create_purchase_order_from_suggestion` same suggestion → same `po_id`.

Each idempotency assertion is verified by inspecting DDB row counts (e.g. `scan(TableName=...)`
comparing item count before and after second call).

**Security**: All purchasing endpoints require at minimum `require_ui_session` (for submit) or
`require_admin_or_root_csrf` (for all mutations).  E2E tests call the endpoints using the
`charlie_admin` admin identity (role=ADMIN) seeded by `e2e_admin_session_setup.py`.  Non-admin
(alice, USER role) is tested via `apiPost(alicePage, ...)` expecting HTTP 403.  The flag-off 404
contract is verified independently in unit tests.

## 8. Backward Compatibility & Migration

PUR-017 adds only test files.  No migration or compatibility concern for production data.

For the local dev stack, the four new DynamoDB tables (`suppliers`, `supplier_products`,
`purchase_orders`, `po_receipts`) must exist before the E2E suite runs.  They are created by
`scripts/local-ddb-init.py` (PUR-002) and are present after any `just restart` or `just up`.  The
E2E spec does not attempt to create its own tables and will fail with a `ResourceNotFoundException`
if the tables are absent (surfaced as a `500` from the backend during the first `POST /ui/purchasing/suppliers` call).

The E2E suite seeds all its own data in `beforeAll` blocks (per the CLAUDE.md pattern) and is
therefore self-contained: it does not depend on DDB state from previous runs.  All created
suppliers, POs, and receipts use a `Date.now()` timestamp suffix in names (`"E2E Supplier ${TS}"`)
so multiple runs do not collide.

## 10. Open Questions / Assumptions

1. **Assumption**: `create_supplier` uses `put_item` without `ConditionExpression`, so a second
   call with the same `supplier_id` silently overwrites with identical data.  This is the same
   pattern used in `commerce_order_service.py:85` for the order header (verified: `self.orders.put_item(Item=order_record)` at `:85`).  If PUR-003 uses
   `attribute_not_exists(supplier_id)` instead, idempotency tests must be adapted to expect
   either a no-op return (early-exit on pre-existing id) or an overwrite — needs confirmation
   from the PUR-003 implementer.

2. **Assumption**: `transition_po` replay (already-in-target-state) catches
   `ConditionalCheckFailedException`, reads the current item, and returns it without raising —
   mirroring `_close_reservation` at `app/services/inventory.py:434–454`.  If it raises 409 on
   replay, the "replay idempotency" tests in section 9.2 must be removed or changed to expect 409.

3. **Assumption**: AP payable (`new_ledger_entry`) is called inside `receive_po` in
   `po_receiving.py` (PUR-009 wired into PUR-008) rather than as a separate post-receive step.
   If PUR-009 wires the payable via a separate `post_ap_payable(po_id)` function that the caller
   must invoke explicitly, the receiving test must call both.  Needs PUR-009 implementer
   confirmation.

4. **Assumption**: `create_purchase_order_from_suggestion` in `reorder_suggestions.py` keys the
   deterministic correlation id on `f"reorder:{supplier_id}:{sorted_sku_fingerprint}"`.  The exact
   key format must be confirmed so the idempotency test uses the same input.

5. **Assumption**: The `billing` table is **not** needed in `test_pur_receiving.py` because
   `new_ledger_entry` is fully stubbed at the module level.  If `po_receiving.py` calls
   `T.billing.put_item` directly (outside `billing_shared.new_ledger_entry`), a `billing` moto
   table must also be added to setUp.

6. **Open question**: Does the reorder suggestion background task (`start_reorder_suggestion_task`,
   PUR-012) need a smoke test in `test_pur_reorder.py`?  The ticket description says "Verify the
   flag-off contract" for endpoints; the background task is flag-gated by the sub-flag and
   registered in `app/main.py`.  Recommend adding a `test_background_task_not_registered_when_flag_off`
   test that asserts `start_reorder_suggestion_task` is in `create_app().router.on_startup` iff
   `purchase_order_reorder_suggestions_enabled=True`, mirroring `tests/test_compute_billing_timer_gap0228.py`.

7. **Open question**: The `GSI_RECEIPT` on `po_receipts` has no sort key.  Idempotent lookup
   (`receive_po` checking for an existing receipt by `receipt_id`) uses a `query` on this GSI.
   In moto, a GSI without a sort key is a valid hash-only index.  Confirm the moto version in use
   supports this pattern (it does as of moto 4.x).

8. **RISK**: E2E section 73 (inventory increment) requires the inventory table to be
   pre-populated with a record for `SKU-E2E-A`.  The test seeds it via
   `PUT /ui/inventory/items` (admin endpoint from `app/routers/inventory.py:46`).  That
   endpoint calls `_require_enabled()` which gates on `inventory_reservations_enabled`.
   **`INVENTORY_RESERVATIONS_ENABLED` is NOT present in `.env.local.example`** (verified —
   `settings.py:839` defaults it to `false`).  The running dev stack must therefore explicitly
   set `INVENTORY_RESERVATIONS_ENABLED=true` in `.env.local`, or the seeding `PUT` will return
   404 and the inventory increment assertion will be meaningless.  Add this variable to
   `.env.local.example` (PUR-002 or environment setup responsibility).
