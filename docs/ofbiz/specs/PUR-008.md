# PUR-008 — Receiving against PO → inventory increment

**Type:** Feature | **Priority:** P0 | **Estimate:** 5 days  
**Milestone:** 3 — Purchase Orders & Approval  
**Depends on:** PUR-007 (state machine), PUR-002 (scaffolding), OFB-003 (`app/services/inventory.py`)

---

## 1. Summary & Goal

PUR-008 delivers `app/services/po_receiving.py`, the "goods receipt" step of the buy-side purchasing
lifecycle. When warehouse staff confirm that supplier goods have physically arrived, they call
`receive_po(...)` with the PO identifier, a per-line received-quantity list, the receiving actor,
and a caller-supplied `receipt_correlation_id`. The service:

1. **Guards** that the PO is in a receivable status (`approved`, `ordered`, or `partially_received`);
   any other status → 409.
2. **Records a receipt row** in `po_receipts` (PK=`po_id`, SK=`RECEIPT#{receipt_id}`) with
   `receipt_id = sha256(receipt_correlation_id)[:32]` so replaying the same correlation id is
   idempotent — no double-increment.
3. **Per received line** validates that `quantity_received + new_qty ≤ quantity_ordered` (over-receive
   → 422) and atomically increments `quantity_received` on the PO line row.
4. **Increments on-hand stock** for each line via the existing `inventory.adjust(sku, +qty,
   reason="po_receipt", user_sub=actor_sub)` — this is the only stock-mutation path (no parallel
   writes).
5. **The inventory increment is guarded** by `S.inventory_reservations_enabled`: with the flag off,
   the receipt is still recorded and `quantity_received` still advances (the financial/receiving record
   is complete), but the stock mutation is skipped — mirroring the OFB-009 restock guard in
   `app/services/returns_rma.py:424`.
6. **Recomputes the PO header status** after all lines are updated: all lines fully received →
   `received`; at least one line partially received → `partially_received`. A newly `received` PO is
   then automatically advanced to `closed` via PUR-007's `transition_po`.
7. **Emits an audit event** (`purchase_order_received`) best-effort.

The service does not add router endpoints (those are added by PUR-010) and does not post the AP
payable (that is PUR-009). With `PURCHASING_SCM_ENABLED=false` (the default) every function raises
`HTTPException(404)` and all existing code is byte-for-byte unchanged.

### 2.6 State machine source constraints (PUR-007)

Receivable statuses (the PO must be in one of these, else 409):
- `approved` — PO approved by an admin; goods may now arrive.
- `ordered` — PO explicitly "placed" with the supplier; goods in transit.
- `partially_received` — at least one prior receipt exists; more goods still to arrive.

Post-receive header status logic:
- All lines: `quantity_received == quantity_ordered` → advance header to `received`, then
  `transition_po(po_id, "closed", actor_sub)` (auto-close per PUR-007 policy).
- At least one line: `quantity_received < quantity_ordered` → advance header to
  `partially_received`.

```python
"""PO receiving service (PUR-008).

Records a goods-receipt row, conditionally increments quantity_received per
PO line, recomputes header status, and — when inventory is enabled — adjusts
on-hand stock through the existing inventory.adjust primitive.

Flag-gated: purchasing_scm_enabled (PURCHASING_SCM_ENABLED, default false).
With the flag off every function raises HTTPException(404). With inventory
disabled (INVENTORY_RESERVATIONS_ENABLED=false) receiving still records the
receipt and advances quantity_received but skips the on-hand increment
(mirrors returns_rma.receive_return OFB-009 guard).
"""

import hashlib
from typing import Any, Dict, List, Optional

from botocore.exceptions import ClientError
from fastapi import HTTPException

from app.core.settings import S
from app.core.tables import T
from app.core.time import now_ts
```

#### 4.1.1 Private helpers

```python
def _flag_on() -> bool:
    return bool(getattr(S, "purchasing_scm_enabled", False))

def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="Purchasing/SCM is not enabled")

def _audit(event: str, actor_sub: str, **fields: Any) -> None:
    try:
        from app.services.alerts import audit_event
        audit_event(event, actor_sub or "system", None, **fields)
    except Exception:
        pass

def _to_int(value: Any, default: int = 0) -> int:
    try:
        return int(value) if value is not None else default
    except (TypeError, ValueError):
        return default

def _load_po(po_id: str) -> tuple[Optional[Dict], List[Dict]]:
    """Load header + all line rows for a PO (full query, handles pagination)."""
    from boto3.dynamodb.conditions import Key
    kwargs: Dict[str, Any] = {"KeyConditionExpression": Key("po_id").eq(po_id)}
    header: Optional[Dict] = None
    lines: List[Dict] = []
    while True:
        r = T.purchase_orders.query(**kwargs)
        for it in r.get("Items", []):
            if it.get("sk") == "META":
                header = it
            elif str(it.get("sk", "")).startswith("LINE#"):
                lines.append(it)
        lek = r.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
    return header, lines
```

#### 4.1.2 Public function: `receive_po`

```python
def receive_po(
    po_id: str,
    *,
    lines: List[Dict[str, Any]],   # [{line_no: int, quantity: int}, ...]
    actor_sub: str,
    receipt_correlation_id: str,
) -> Dict[str, Any]:
    """Record a goods receipt and increment on-hand stock.

    Parameters
    ----------
    po_id : str
        The target purchase order.
    lines : list of {line_no: int, quantity: int}
        Quantities received per line in this receipt. Only lines present in
        this list are updated; omitted lines are unchanged.
    actor_sub : str
        Sub of the user performing the receiving action (written to receipt
        row and audit event).
    receipt_correlation_id : str
        Caller-supplied idempotency key. sha256[:32] of this string becomes
        the receipt_id. Replaying the same value is a no-op.

    Returns
    -------
    dict with keys ``receipt``, ``po`` (updated header + lines snapshot).

    Raises
    ------
    HTTPException 404  — flag is off
    HTTPException 404  — PO not found
    HTTPException 409  — PO status not receivable
    HTTPException 422  — over-receive on any line
    """
```

**Detailed logic** (see §5 for edge cases):

1. `_require_enabled()`
2. `receipt_id = hashlib.sha256(receipt_correlation_id.encode("utf-8")).hexdigest()[:32]`
3. Idempotency check: `T.po_receipts.get_item(Key={"po_id": po_id, "sk": f"RECEIPT#{receipt_id}"})`.
   If `Item` exists, reload and return `{"receipt": existing_item, "po": get_purchase_order(po_id)}`.
4. `header, existing_lines = _load_po(po_id)`; if `header is None` → 404.
5. Guard receivable status: `header["status"] not in {"approved", "ordered", "partially_received"}`
   → `HTTPException(409, detail="PO is not in a receivable status")`.
6. Build `line_map = {it["sk"]: it for it in existing_lines}` (keyed by `LINE#N`).
7. For each input `{line_no, quantity}`:
   - sk = `f"LINE#{line_no}"`. If not in `line_map` → `HTTPException(422, detail="Line not found")`.
   - `qty_ordered = _to_int(line_map[sk]["quantity_ordered"])`.
   - `qty_already = _to_int(line_map[sk].get("quantity_received", 0))`.
   - `new_total = qty_already + quantity`. If `new_total > qty_ordered` → `HTTPException(422,
     detail=f"Over-receive on line {line_no}: would receive {new_total} > ordered {qty_ordered}")`.
8. Write the receipt row:
   ```python
   T.po_receipts.put_item(
       Item={
           "po_id": po_id, "sk": f"RECEIPT#{receipt_id}",
           "receipt_id": receipt_id, "receipt_correlation_id": receipt_correlation_id,
           "actor_sub": actor_sub, "received_at": now_ts(),
           "lines": [{"line_no": ln["line_no"], "sku": line_map[f"LINE#{ln['line_no']}"]["sku"],
                      "quantity_received_this_receipt": ln["quantity"]} for ln in lines],
       },
       ConditionExpression="attribute_not_exists(po_id)",
   )
   ```
   If `ConditionalCheckFailedException` → the receipt already exists (race with another thread
   using the same correlation id); reload and return existing receipt.
9. For each input line, conditional increment:
   ```python
   T.purchase_orders.update_item(
       Key={"po_id": po_id, "sk": f"LINE#{line_no}"},
       UpdateExpression="SET quantity_received = quantity_received + :d, updated_at = :now",
       ConditionExpression="quantity_received + :d <= quantity_ordered",
       ExpressionAttributeValues={":d": quantity, ":now": now_ts()},
   )
   ```
   `ConditionalCheckFailedException` → `HTTPException(422, "Over-receive (concurrent update)")`.
10. Inventory increment (gated):
    ```python
    if bool(getattr(S, "inventory_reservations_enabled", False)):
        try:
            from app.services import inventory as inv
            for ln in lines:
                sku = line_map[f"LINE#{ln['line_no']}"]["sku"]
                qty = ln["quantity"]
                if sku and qty > 0:
                    inv.adjust(sku, qty, reason="po_receipt", user_sub=actor_sub)
        except Exception:
            pass  # stock failure must not roll back the receipt
    ```
11. Reload all lines to compute new header status (re-query `T.purchase_orders`).
12. `all_full = all(_to_int(l.get("quantity_received")) >= _to_int(l.get("quantity_ordered")) for l in reloaded_lines)`
    - `all_full` → new status `"received"`; then call `transition_po(po_id, "closed", actor_sub)`.
    - Otherwise → new status `"partially_received"`.
    - `T.purchase_orders.update_item(Key={"po_id": po_id, "sk": "META"}, UpdateExpression="SET #s = :s, updated_at = :now", ExpressionAttributeNames={"#s": "status"}, ExpressionAttributeValues={":s": new_status, ":now": now_ts()})`.
13. `_audit("purchase_order_received", actor_sub, po_id=po_id, receipt_id=receipt_id, new_status=new_status)`.
14. Return `{"receipt": receipt_item, "po": get_purchase_order(po_id)}`.

#### 4.1.3 Public function: `get_receipt`

```python
def get_receipt(po_id: str, receipt_id: str) -> Optional[Dict[str, Any]]:
    """Return a single receipt row, or None if not found."""
    _require_enabled()
    resp = T.po_receipts.get_item(Key={"po_id": po_id, "sk": f"RECEIPT#{receipt_id}"})
    return resp.get("Item")

def list_receipts(po_id: str) -> List[Dict[str, Any]]:
    """Return all receipt rows for a PO, newest-first by received_at."""
    _require_enabled()
    from boto3.dynamodb.conditions import Key
    items: List[Dict] = []
    kwargs: Dict[str, Any] = {
        "KeyConditionExpression": Key("po_id").eq(po_id) & Key("sk").begins_with("RECEIPT#"),
    }
    while True:
        r = T.po_receipts.query(**kwargs)
        items.extend(r.get("Items", []))
        lek = r.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
    items.sort(key=lambda x: _to_int(x.get("received_at")), reverse=True)
    return items
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotency under replay

The receipt SK is deterministic: `po_id` + `RECEIPT#{sha256(receipt_correlation_id)[:32]}`. The
`put_item` with `ConditionExpression="attribute_not_exists(po_id)"` is the single-writer guard.

On the first call: the condition succeeds, the receipt row is written, line updates and stock
adjustments proceed.

On replay (same `receipt_correlation_id`): `get_item` in step 3 finds the existing row and returns
early — no `put_item`, no line update, no stock increment. The return value is the original receipt
+ the current PO snapshot (which already reflects the first call's changes).

On a concurrent race (two threads with identical correlation id arrive simultaneously): the `put_item`
condition will fail on the loser. The loser catches `ConditionalCheckFailedException`, loads the
winner's receipt row, and returns it — same as a sequential replay. No double-increment is possible.

### 5.2 Over-receive protection — two layers

**Layer 1 (pre-flight check in step 7):** Before writing any receipt row, the service reads every
affected line and checks `qty_already + new_qty ≤ qty_ordered`. If any line fails, the entire call
is rejected (422) without writing anything — the PO is untouched.

**Layer 2 (conditional DDB update in step 9):** The `update_item`
`ConditionExpression="quantity_received + :d <= quantity_ordered"` enforces the cap atomically at
the DynamoDB level. This protects against a concurrent partial-receive that arrived between the
pre-flight read and the update — if the condition fires, the service raises 422 with
`"Over-receive (concurrent update)"`.

These two layers together mean over-receiving is impossible even under concurrent load.

### 5.3 Stock increment failure does not roll back receipt

The inventory `try/except Exception: pass` wrapper (mirroring `returns_rma.py:433`) ensures that a
DynamoDB contention error or a `NoCredentialsError` in CI never unwinds `quantity_received`. The
goods-receipt financial record is complete regardless of stock state. Monitoring must reconcile
`quantity_received` changes against `inventory.on_hand` separately if stock mutations fail.

### 5.4 Partial vs. full receipt sequencing

A typical 3-step flow:
1. Receipt 1: 4 of 10 units on line 1 → `quantity_received=4`, header → `partially_received`.
2. Receipt 2: 3 more of 10 units on line 1 → `quantity_received=7`, header stays `partially_received`.
3. Receipt 3: final 3 units → `quantity_received=10 == quantity_ordered=10`, header → `received` →
   auto-transition → `closed`.

Each receipt is a separate call with a distinct `receipt_correlation_id`; all three records are
preserved in `po_receipts`.

### 5.5 PO status not receivable

A PO in `draft`, `submitted`, `rejected`, `cancelled`, `received`, or `closed` returns 409:
`"PO is not in a receivable status"`. `received` and `closed` are already terminal; the over-receive
check (§5.2) would also catch these as 422 since `quantity_received == quantity_ordered`, but the
explicit 409 guard fires first (step 5 precedes step 7).

### 5.6 Auto-close after full receipt

When `all_full` is true, `transition_po(po_id, "closed", actor_sub)` is called immediately. If the
PO was just set to `received` by this call's `update_item` in step 12, the `transition_po`
conditional `status = "received"` will succeed. If a concurrent call also advanced it to `received`
(unlikely given the per-line update guards), `transition_po` is designed (PUR-007) to be idempotent
— the loser's `ConditionalCheckFailedException` is swallowed as a no-op.

### 5.7 Lines not included in the request

Only lines listed in the input `lines` array are updated. Lines with `line_no` absent from the input
are unchanged. This allows granular receiving: e.g., only line 1 arrives today; line 2 arrives
tomorrow in a separate receipt.

### 5.8 Empty `lines` input

`PoReceiveIn.lines` is validated with `min_length=1` (Pydantic), so an empty list is rejected with
HTTP 422 at the validation layer before reaching the service.

### 5.9 Large POs (>1 page of lines)

`_load_po` uses a `while True` pagination loop identical to `_load_return` in
`app/services/returns_rma.py:153–168`. DynamoDB returns at most 1MB per query page; pagination via
`LastEvaluatedKey` handles large POs (hundreds of lines).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

There is no `dev_mode` branch anywhere in `po_receiving.py`. The `T.purchase_orders` and
`T.po_receipts` table handles point to DynamoDB Local (port 8001) in dev and to real DynamoDB in
prod; the service code is identical. The `inventory.adjust` call goes through the same `T.inventory`
handle in both environments.

This mirrors `app/services/inventory.py:27–28`'s explicit declaration: "SECOPS-007 parity: identical
code in dev (moto / local DDB) and prod (real DDB); no `dev_mode` branch in the business logic."

### Idempotency

Every write is deterministic-id guarded:
- Receipt row: `put_item` + `attribute_not_exists(po_id)` on the deterministic SK.
- Line update: DDB `ConditionExpression` prevents over-increments atomically.
- Header status update: no conditional needed (it is a monotone advance — `partially_received`
  can overwrite `partially_received` safely; `received` is set only when all lines are full).

### Security

- **Auth**: `receive_po` is called only from the `require_admin_session`-gated endpoint (PUR-010).
  Non-admin users cannot trigger a receiving action.
- **Ownership**: PO ownership is not per-user-sub (POs are org-wide admin objects); the auth guard
  is role-based, not sub-based. An admin can receive any PO.
- **Over-receive**: Two independent guards (pre-flight + DDB conditional) prevent stock inflation.
- **Audit**: Every successful receive emits `purchase_order_received` to `T.alerts` for the audit
  trail; the `inventory.adjust` call independently emits `inventory.adjust`.
- **No sensitive data in receipt rows**: `receipt_correlation_id` is a caller-supplied key (e.g.,
  a delivery reference number); no PII is expected.

## 8. Backward Compatibility & Migration

### With `PURCHASING_SCM_ENABLED=false` (the default)

Every new function in `po_receiving.py` immediately raises `HTTPException(404)`. No DynamoDB
writes occur. No changes to `T.inventory`, `T.billing`, `T.purchase_orders`, or any existing table.
Existing shop/cart/orders/billing/inventory E2E tests are unaffected — they run with the flag off
and never touch the new code paths.

### Table creation is non-destructive

`scripts/local-ddb-init.py` creates tables idempotently (wraps each `create_table` with
`ResourceInUseException` handling at `_ensure_table`). Adding `po_receipts` to the list is safe;
it does not modify any existing table.

### `app/core/tables.py` and `app/core/settings.py` additions

Appending new fields to the `Tables` dataclass and new keys to `Settings` is additive. The frozen
dataclass pattern (`@dataclass(frozen=True)`) means new fields are ignored by existing code. No
migration or backfill of existing rows is required.

### No changes to existing services

`po_receiving.py` imports `inventory.adjust` via a local import inside a `try/except` guard (the
same lazy-import pattern used by `returns_rma.py:426`). This avoids circular import risk and ensures
`inventory.py` remains unchanged.

## 10. Open Questions / Assumptions

1. **`transition_po` import**: This spec assumes `transition_po(po_id, target_status, actor_sub)`
   is importable from `app.services.purchase_orders` (delivered by PUR-007). If PUR-007 places it in
   a separate `app/services/po_lifecycle.py`, the import path must be updated in `po_receiving.py`.

2. **Line numbering scheme**: This spec assumes PO lines are stored as `LINE#1`, `LINE#2` … (1-based
   integer strings with no zero-padding). PUR-006 uses this scheme. If PUR-006 uses zero-padded
   strings (`LINE#001`) the `f"LINE#{line_no}"` format string must match.

3. **`get_purchase_order` location**: The return value of `receive_po` includes the updated PO
   snapshot via a call to `get_purchase_order(po_id)`. This spec assumes that function is importable
   from `app.services.purchase_orders` (delivered by PUR-006). The spec will need adjusting if
   PUR-006 co-locates it elsewhere.

4. **Header status conditional update**: Step 12 uses an unconditional `update_item` for the header
   status. If PUR-007's `transition_po` already guards the `received → closed` transition with a
   conditional, there is a potential for a 409 from the unconditional header update if a concurrent
   full-receive call happens. This can be resolved by wrapping the `status=received` set in the same
   `ConditionExpression="#s IN (:approved, :ordered, :partially_received)"` guard. Decision deferred
   to implementation review.

5. **Location for stock increment**: `inventory.adjust` defaults to `location_id="warehouse"`. PUR-008
   uses this default for all po_receipt increments. If multi-location inventory is ever introduced,
   the PO line schema will need a `location_id` field and `receive_po` will need to pass it through.
   For now, single-location is the correct assumption (`app/services/inventory.py:43` declares
   `DEFAULT_LOCATION = "warehouse"`).  <!-- VERIFIED: inventory.py:43 -->
   NOTE: the inventory table sort key attribute is named `location_sk` (not `sk`); its value is
   `f"LOC#{location_id}"` (see `inventory.py:60`). Any test that constructs inventory `Key` dicts
   directly must use `{"sku": sku, "location_sk": "LOC#warehouse"}`.  <!-- VERIFIED: inventory.py:119 -->

6. **Partial-receive over multiple lines**: The spec processes lines sequentially (loop in step 9).
   If the server crashes between line 2 and line 3 of a 5-line receipt, the receipt row exists (step
   8 succeeded), lines 1–2 were updated, but lines 3–5 were not. On replay with the same
   `receipt_correlation_id`, step 3 detects the existing receipt and returns early — lines 3–5 are
   never updated. This is an assumption: an operator must cancel and re-submit a new receipt for the
   remaining lines. An alternative is to write line updates inside a DynamoDB TransactWrite (up to 25
   items per transaction). The spec assumes sequential updates for simplicity; the implementation
   team should evaluate TransactWrite for correctness if partial-crash recovery is a requirement.

7. **Receipt line list in `PoReceiveIn`**: The ticket does not specify whether lines received in the
   same receipt must be distinct (no duplicate `line_no` values). This spec assumes input validation
   (Pydantic) should reject duplicates to avoid ambiguous updates. Implementation may add a
   `validator` checking `len(lines) == len({ln.line_no for ln in lines})`.
