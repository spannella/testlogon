# MFG-005 — Work-center / routing service

**Type:** Feature | **Priority:** P1 | **Estimate:** 3 days
**Milestone:** 2 — BOM & Routing

---

## 1. Summary & Goal

Create `app/services/manufacturing_routing.py` implementing:

1. **Work-center CRUD** — create, read, update, disable work centers on `T.mfg_work_centers`. A work center is a named production station with an integer capacity (`capacity_per_hour`) and a labor-cost rate (`cost_per_hour_cents` in integer cents).
2. **Routing tasks** — an ordered sequence of operations attached to either a BOM ID or a work-order ID, where each task names a work center and declares `setup_minutes` + `run_minutes_per_unit`. Routing rows live in the `mfg_work_centers` table under the work center's partition (see §3) or, more precisely, in a dedicated routing partition keyed off the parent entity (BOM or work order).
3. **`estimate_routing_cost(tasks, build_qty)`** — a pure function that computes total labor minutes and labor cost in cents for a given list of routing tasks and a build quantity, consuming only the fields on those task dicts (no additional I/O). This function is the cost input for MFG-008's optional costed-production GL hook and for MFG-010's MRP lead-time estimate.

The service is flag-gated (`_require_enabled` raising HTTP 404 when `S.manufacturing_mrp_enabled` is off), audited via the same best-effort `_audit` wrapper pattern as `app/services/inventory.py:92–98`, and has no effect on existing shop/cart/orders/billing code paths.

## 3. Data Model

MFG-005 uses **two** DynamoDB entities, both stored in the **existing `mfg_work_centers` table** (single-table design):

### 3.1 Work center header (`SK=META`)

This row is defined by MFG-002 (spec §3.2). MFG-005 is the service that reads/writes it; the table schema is unchanged.

| Attribute | DDB Type | Notes |
|---|---|---|
| `work_center_id` (PK) | S | `WC#{uuid4().hex}` |
| `sk` (SK) | S | `"META"` |
| `name` | S | Human label, 1–256 chars |
| `capacity_per_hour` | N | Integer units/hour (≥ 1) |
| `cost_per_hour_cents` | N | Integer cents ≥ 0 (labor rate) |
| `status` | S | `"active"` or `"inactive"` |
| `created_at` | N | `now_ts()` at creation |
| `updated_at` | N | `now_ts()` on every mutation |

**GSI_STATUS**: PK=`status` (S), SK=`created_at` (N). Enables list-by-status admin queries. `attr_types={"created_at": "N"}` already declared in MFG-002 TableDef.

### 3.2 Routing task rows (`SK=ROUTE#{parent_id}#{seq:04d}`)

A new row type in the same `mfg_work_centers` partition. The PK is `work_center_id` — routing tasks live **under the work center they reference**, which makes the "is this work center referenced by any open routing?" query a simple partition scan.

| Attribute | DDB Type | Notes |
|---|---|---|
| `work_center_id` (PK) | S | Same as parent work center; `WC#…` |
| `sk` (SK) | S | `ROUTE#{parent_id}#{seq:04d}` |
| `parent_id` | S | BOM ID or work-order ID this routing belongs to |
| `parent_type` | S | `"bom"` or `"work_order"` |
| `seq` | N | Display/execution order (0-based, gaps allowed) |
| `operation_name` | S | Human label for this step |
| `setup_minutes` | N | Fixed setup time per run (not per unit) |
| `run_minutes_per_unit` | N | Variable time per finished-goods unit |
| `created_at` | N | `now_ts()` |
| `updated_at` | N | `now_ts()` |

**Why PK = work_center_id for routing rows:** Placing routing rows in the work center's partition enables the disable-guard to find all active routing rows for that work center in a single `query(KeyConditionExpression=Key("work_center_id").eq(wc_id) & Key("sk").begins_with("ROUTE#"))` without a GSI scan. The trade-off is that fetching all routing tasks for a given BOM requires a GSI.

**GSI_ROUTE_PARENT**: PK=`parent_id` (S), SK=`seq` (N). Resolves the ordered routing task list for a BOM or work order via `query(IndexName="GSI_ROUTE_PARENT", KeyConditionExpression=Key("parent_id").eq(bom_id))` sorted by `seq` ascending.

This GSI must be added to the `mfg_work_centers` TableDef in `scripts/local-ddb-init.py`. The current last `TableDef` entry closes at line 2492 (`returns` table), so MFG-002 appends after line 2492 and MFG-005 updates that entry (verified `scripts/local-ddb-init.py:2483–2492`). The updated TableDef (replacing the MFG-002 version):

```python
# mfg_work_centers: work center headers (SK=META) + routing task rows
# (SK=ROUTE#{parent_id}#{seq:04d}).
# GSI_STATUS: admin listing by status (active/inactive) sorted by created_at.
# GSI_ROUTE_PARENT: resolve ordered routing tasks for a given BOM/work-order parent.
# attr_types: created_at (N) for GSI_STATUS; seq (N) for GSI_ROUTE_PARENT.
TableDef(
    _resolve_table_name(S.mfg_work_centers_table_name, "mfg_work_centers"),
    "work_center_id",
    "sk",
    gsi=[
        {"index_name": "GSI_STATUS",
         "partition_key": "status", "sort_key": "created_at"},
        {"index_name": "GSI_ROUTE_PARENT",
         "partition_key": "parent_id", "sort_key": "seq"},
    ],
    attr_types={"created_at": "N", "seq": "N"},
),
```

**Note on `just restart`:** Adding a new GSI to an existing TableDef in `scripts/local-ddb-init.py` takes effect on the next `just restart` (which calls `local-ddb-init.py` after wiping DynamoDB Local data). No data migration is required in dev; in production a `UpdateTable` call with the new GSI and an async backfill must precede the code deployment (see §8).

    created_at: int = 0
    updated_at: int = 0


class RoutingCostOut(BaseModel):
    build_qty: int

`setup_minutes` and `run_minutes_per_unit` are `int` (whole minutes) — fractional-minute scheduling is deferred. The `ge=0` lower bound allows zero (meaning "no setup time" or "instantaneous operation"), while the `le=100_000` upper bound (~69 days) prevents data-entry errors.

#### Cost estimation

```python
def estimate_routing_cost(
    tasks: List[Dict[str, Any]],
    build_qty: int,
) -> Dict[str, Any]:
    """
    Pure function — no DynamoDB I/O.

    Each task dict must contain:
      - "work_center_id": str
      - "setup_minutes": int (or Decimal — coerced via _to_int)
      - "run_minutes_per_unit": int
      - "cost_per_hour_cents": int   ← must be pre-loaded by caller

    Formula per task:
      task_minutes = setup_minutes + run_minutes_per_unit * build_qty
      task_cost_cents = ceil(task_minutes / 60 * cost_per_hour_cents)

    Totals:
      total_setup_minutes    = sum(setup_minutes for each task)
      total_run_minutes      = sum(run_minutes_per_unit * build_qty for each task)
      total_labor_minutes    = total_setup_minutes + total_run_minutes
      total_labor_cost_cents = sum(task_cost_cents for each task)

    Returns a dict matching RoutingCostOut fields (caller passes tasks with
    cost_per_hour_cents pre-populated; this function does not look up work centers).
    Raises ValueError for build_qty <= 0.
    """
```

## 5. Detailed Behavior & Edge Cases

### 5.1 `estimate_routing_cost` formula (exact)

For `build_qty` units and a task list `T`:

```
total_setup_minutes    = Σ task.setup_minutes
total_run_minutes      = Σ (task.run_minutes_per_unit × build_qty)
total_labor_minutes    = total_setup_minutes + total_run_minutes
total_labor_cost_cents = Σ ceil(
                           (task.setup_minutes + task.run_minutes_per_unit × build_qty)
                           / 60
                           × task.cost_per_hour_cents
                         )
```

Using `math.ceil` (not banker's rounding). This ensures a 1-minute job at 60 ¢/hr costs exactly 1 ¢, never rounds down to 0. `build_qty <= 0` raises `ValueError("build_qty must be >= 1")` before any summation.

Determinism guarantee: given the same `tasks` list and `build_qty`, the function always returns the same result — no timestamps, UUIDs, or RNG. The pytest acceptance criterion "deterministic labor minutes + cents for a given build qty" is satisfied by this pure-function design.

### 5.2 Disable-guard for work centers

`disable_work_center(wc_id)` executes the following checks in order before writing `status=inactive`:

1. **Fetch the META row** — 404 if not found; no-op return if already `inactive`.
2. **Scan routing rows** — query `T.mfg_work_centers` with `KeyConditionExpression=Key("work_center_id").eq(wc_id) & Key("sk").begins_with("ROUTE#")`. Collect all matching rows.
3. **For each routing row:** extract `parent_id` and `parent_type`.
   - If `parent_type == "bom"`: call `T.mfg_boms.get_item(Key={"bom_id": parent_id, "sk": "META"})`. If the BOM exists with `status == "active"` → raise `HTTPException(409, "Work center is referenced by active BOM {parent_id}")`.
   - If `parent_type == "work_order"`: call `T.mfg_work_orders.get_item(Key={"work_order_id": parent_id, "sk": "META"})`. If the work order exists with `status in {"created", "released", "in_progress"}` → raise `HTTPException(409, "Work center is referenced by open work order {parent_id}")`.
4. **Write** `status=inactive` + `updated_at=now_ts()` if no blocking dependency found.
5. Emit `_audit("mfg.work_center.disabled", user_sub, work_center_id=wc_id)`.

**Lazy BOM table import:** `manufacturing_routing.py` must import `T.mfg_boms` and `T.mfg_work_orders` at the point of use (top-level import is fine since they are just table handles from `T`, not circular service imports). The tables are available as `from app.core.tables import T` — the same import used by every other service file.

### 5.3 Adding routing tasks to an inactive work center

`add_routing_task` raises `HTTPException(409, "Work center {wc_id} is inactive and cannot accept new routing tasks")` when the referenced work center's `status == "inactive"`. This prevents routing from being attached to a disabled station.

### 5.4 `seq` collision on `add_routing_task`

`add_routing_task` uses a conditional `put_item` with `ConditionExpression="attribute_not_exists(sk)"`. If a `ROUTE#{parent_id}#{seq:04d}` row already exists, DynamoDB raises `ConditionalCheckFailedException` → the service raises `HTTPException(409, "Routing task with seq={seq} already exists for parent {parent_id}")`.

### 5.5 `replace_routing_for_parent` atomicity

True DynamoDB atomicity across an arbitrary number of deletes + writes is not available without transactions. `replace_routing_for_parent` uses a **sequential two-phase approach**:

1. Fetch all existing `ROUTE#{parent_id}#*` rows via `GSI_ROUTE_PARENT`.
2. `batch_writer()` delete all existing rows.
3. Validate new tasks (work center exists + active for each).
4. `batch_writer()` write new rows.

If step 3 raises (a referenced work center is inactive), step 4 is skipped and the caller receives the 409. The old routing has already been deleted at that point — this is a known partial-failure window. The caller must retry with a valid task list. This matches the trade-off made by similar bulk-replace patterns elsewhere in the codebase (e.g., BOM component replace in MFG-004). Full transactional replace (using `transact_write_items`) is deferred to a follow-up if the consistency requirement is tightened.

### 5.6 Decimal coercion from DynamoDB

`T.mfg_work_centers` uses `_FloatSafeTable` (from `app/core/tables.py:29–63` — class spans lines 29–62, `_safe_table` factory at line 65; verified) which coerces Python `float` to `Decimal` on writes. On reads, boto3 returns numeric attributes as `decimal.Decimal`. `_to_int` (following `inventory.py:67–73` — verified) handles this:

```python
def _to_int(value: Any, default: int = 0) -> int:
    try:
        if value is None: return default
        return int(value)
    except (TypeError, ValueError):
        return default
```

All `setup_minutes`, `run_minutes_per_unit`, `capacity_per_hour`, `cost_per_hour_cents`, `seq`, `created_at`, `updated_at` values go through `_to_int` before being returned in the output dict.

### 5.7 `get_routing_for_parent` sort guarantee

`GSI_ROUTE_PARENT` is queried with `ScanIndexForward=True` (ascending `seq`). The result is already in `seq` order — no client-side re-sort is needed. However, because `seq` values are caller-controlled integers (not necessarily contiguous), the service returns them in the DDB-sorted order and does not renumber gaps.

### 5.8 Empty routing list

`get_routing_for_parent` returns an empty list when no routing tasks exist for the given `parent_id`. `estimate_routing_cost_for_parent` with an empty task list returns `total_labor_minutes=0`, `total_labor_cost_cents=0` — no error. MFG-008's GL hook must treat a zero labor cost as a valid (no-labor) result.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

No `dev_mode` branch anywhere in `manufacturing_routing.py`. The service uses `T.mfg_work_centers` (DynamoDB Local in dev, real DynamoDB in prod) through the same `_safe_table` handle. The `_audit` wrapper calls `alerts.audit_event` which writes to `T.alerts` — the same path in both environments. No mock S3, no Cognito, no external services are touched.

### Idempotency

- **`create_work_center`**: Uses `put_item` without a condition; calling twice with the same name creates two separate work centers (different `work_center_id` UUIDs). Work center creation is not keyed off a caller-supplied correlation ID. This is intentional: work centers are admin-configured entities, not transactional records. Duplicate-name protection is a UI concern.
- **`add_routing_task`**: Idempotent on `seq` collision via `attribute_not_exists(sk)` conditional → 409 on duplicate, not silent overwrite.
- **`disable_work_center`**: Idempotent — calling on an already-inactive work center is a no-op (status is already `"inactive"`, returned without writing or auditing).
- **`replace_routing_for_parent`**: Not idempotent in the general case (two concurrent calls with different task lists will race). The caller (admin UI, MFG-006) is expected to perform this as a single synchronous write.

### Security

All write endpoints use `require_admin_or_root_csrf` (defined at `app/auth/policy.py:100`, imported by `app/routers/inventory.py:18` — both verified). Manufacturing work centers are internal production data — no customer-facing read path is exposed for routing or cost data. The `user_sub` for audit events always comes from the authenticated session dependency (never from the request body). `work_center_id` in URL path parameters is validated by the service's `get_work_center` → 404 before any mutation proceeds.

## 10. Open Questions / Assumptions

1. **Routing stored under work center PK vs. a separate routing table:** This spec stores `ROUTE#` rows in `mfg_work_centers` under the work center's partition. An alternative is a dedicated `mfg_routing_tasks` table keyed on `(parent_id, seq)`. The single-table approach was chosen to enable the disable-guard query with no GSI; the trade-off is that "list all routing for a BOM" requires the `GSI_ROUTE_PARENT` added here. If the platform decides routing tasks should be queryable without knowing `work_center_id` up front (e.g., bulk admin reads), a separate table may be cleaner.

2. **`setup_minutes` and `run_minutes_per_unit` as `int` vs `float`:** This spec uses `int` (whole minutes) consistent with the inventory integer-quantities convention. Sub-minute precision (e.g., 30-second setup) would require `float`. If precision requirements change, the model fields and `_to_int` helper would need to become `_to_float`.

3. **`replace_routing_for_parent` partial-failure window:** The sequential delete-then-write approach leaves a window where old routing is deleted but new routing is not yet written (e.g., if the process crashes between phases). If this is unacceptable, MFG-005 should use DynamoDB `transact_write_items` (max 100 items per transaction). For Phase 1, the sequential approach is assumed acceptable — routing tasks are admin configuration, not transactional records.

4. **Routing on work orders vs. BOMs:** This spec supports `parent_type = "work_order"` routing rows. However, MFG-007 (work-order lifecycle) may not need separate routing tasks — it may simply inherit the routing from the BOM. If work-order-specific routing is never needed, `parent_type` can be restricted to `"bom"` only and the `parent_type` field removed.

5. **`cost_per_hour_cents` on routing tasks vs. work centers:** The spec stores the cost rate on the work center (META row), not on the routing task row. `estimate_routing_cost` therefore requires the caller to pre-load `cost_per_hour_cents` per task. An alternative is to denormalize `cost_per_hour_cents` onto each routing task row at write time. Denormalization would make `estimate_routing_cost` a true pure function from stored data alone but would require backfilling task rows when a work center's cost rate changes.

6. **Disable vs. delete:** This spec implements `disable_work_center` (sets `status=inactive`) but not hard delete. A soft-disable is assumed safer because historical routing tasks referencing the work center remain queryable for audit. If hard delete is needed, it requires deleting all `ROUTE#` rows under the partition and blocking if any referencing parent is active.

7. **`list_work_centers` pagination:** Uses the `GSI_STATUS` index sorted by `created_at`. The cursor token encoding follows `app/core/cursor.py:encode_cursor`/`decode_cursor` (used by `app/routers/profile.py:19,554,620` and `app/routers/moderation_video_queue.py:19,134,140` — verified). Note: `inventory.py:list_low_stock` and `returns_rma.py:list_returns_by_status` use an internal `while True` exhaust-all-pages pattern (no caller-visible cursor); `list_work_centers` is designed to be paginated since work-center lists can grow large.
