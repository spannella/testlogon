# OFB-005 — Low-stock & reorder-point alerts

**Type:** Feature | **Priority:** P1 | **Estimate:** 2 days
**Depends on:** OFB-003 (inventory service), OFB-004 (reservation lifecycle)
**Downstream:** OFB-006 (inventory admin UI), OFB-007 (E2E tests)

---

## 1. Summary & Goal

OFB-005 wires **low-stock and reorder-point alerts** into the inventory service introduced by OFB-003. Whenever `available` drops to or below `reorder_point` (the per-SKU threshold) after any mutation — `reserve`, `commit_reservation`, `adjust`, or `set_on_hand` — a single alert is emitted to the catalog item's owner via the existing `app/services/alerts.write_alert` plumbing (the same path used by `catalog.low_stock` alerts since GAP-0347/SHOP-001).

**De-duplication** is enforced: once an alert fires for a (sku, location_id) pair the alert is suppressed until that pair recovers above the threshold and crosses back down again. This prevents a SKU hovering at the boundary from generating O(n) alerts. The sentinel mechanism mirrors the per-item TTL-less sentinel used in the catalog router for SHOP-001 (GAP-0347) but adapted to use **explicit recovery deletion** rather than TTL expiry, because inventory `available` can bounce up and down on the same row within minutes (reservations are released, TTL-expired, etc.).

The feature is gated by the existing `INVENTORY_RESERVATIONS_ENABLED` master switch (`app/core/settings.py:839`): with it off the inventory service is dormant and no alert logic runs. A **separate, finer-grained sub-flag** (`INVENTORY_LOW_STOCK_ALERTS_ENABLED`, default `true`) allows the alert behavior to be disabled without disabling reservations.

## 3. Data Model

### 3.1 Sentinel rows in the `inventory` table (single-table)

To track "has an alert already been fired for this (sku, location_id) since the last recovery", a sparse **sentinel row** is stored in the same `inventory` table. This reuses the conditional-put test-and-set pattern from SHOP-001 without adding a new table.

```
PK  = sku                         (e.g. "SKU-A")
SK  = SENTINEL#LOWSTOCK            (constant; does NOT collide with LOC# prefix)
entity         = "lowstock_alert_sentinel"
sku            = sku
location_id    = location_id
fired_at       = <Unix timestamp int>
```

Sentinel rows **never** carry `status` or `available`; they have no `GSI_AVAILABLE` projection attributes, so the existing `list_low_stock` query (which queries `GSI_AVAILABLE` by `status`) never returns them.

**Why not TTL-based (like catalog)?**
The catalog alert is for admin-driven stock adjustments where the crossing can only go down. The inventory service has `release_reservation` and `expire_due_reservations` paths that routinely push `available` *above* the threshold again within the same hour. A 1-hour TTL would either over-suppress (during an active reservation-release wave) or fail to re-alert after a genuine restock+redecrement within the window. Explicit deletion on recovery is cleaner.

### 3.2 No new DynamoDB tables required

The sentinel row reuses `T.inventory` (the existing `inventory` table). No schema change to `scripts/local-ddb-init.py` is required because:

- The sentinel SK `SENTINEL#LOWSTOCK` is a string; no new attribute type declarations are needed.
- The sentinel is not projected into `GSI_AVAILABLE` (it does not set `status` or `available`), so it never pollutes low-stock queries.

### 3.3 Alert event in `T.alerts`

`write_alert` writes to the existing `T.alerts` table (PK=`user_sub`, SK=`alert_id`) using the standard schema. No new table or GSI is required.

## 4. API / Service Design

### 4.1 New internal helpers in `app/services/inventory.py`

All functions below are **internal to the inventory service** (no new HTTP endpoints in OFB-005).

```python
_SENTINEL_SK = "SENTINEL#LOWSTOCK"
_LOWSTOCK_EVENT = "inventory.low_stock"


def _sentinel_key(sku: str, location_id: str) -> dict:
    """Primary key for the dedup sentinel row."""
    return {"sku": sku, "location_sk": _SENTINEL_SK}


def _maybe_emit_low_stock_alert(
    sku: str,
    location_id: str,
    available: int,
    reorder_point: int,
    user_sub: str,
    sku_label: Optional[str] = None,
) -> None:
    """Fire a single low-stock alert when available crosses reorder_point downward.

    Idempotent: a conditional put on the sentinel row ensures exactly one alert
    fires per downward crossing.  The sentinel is deleted by
    _maybe_clear_low_stock_sentinel when available recovers above reorder_point.
    Best-effort: any DDB or alerts error is swallowed to never break the caller.
    """
    ...


def _maybe_clear_low_stock_sentinel(
    sku: str,
    location_id: str,
    available: int,
    reorder_point: int,
) -> None:
    """Delete the sentinel row when available rises above reorder_point.

    Called after release_reservation, expire_due_reservations (indirect), and
    any upward adjust / set_on_hand that moves available back above threshold.
    Best-effort: errors are swallowed.
    """
    ...
```

**`_maybe_emit_low_stock_alert` logic:**

1. Guard: if `S.inventory_low_stock_alerts_enabled` is `False`, return.
2. Guard: if `available > reorder_point`, return (above threshold — no action).
3. Try `T.inventory.put_item(Item={...sentinel...}, ConditionExpression="attribute_not_exists(sku) AND attribute_not_exists(location_sk)")`.
   <!-- PK/SK attribute names confirmed: inventory table uses "sku" (PK) and "location_sk" (SK) per local-ddb-init.py:2458-2459 -->
   - Success → sentinel written, proceed to emit alert.
   - `ConditionalCheckFailedException` → sentinel already present (alert already fired for this crossing) → return (suppress).
   - Any other exception → return (best-effort).
4. On success: `write_alert(owner_sub, event="inventory.low_stock", outcome="warning", title=f"Low stock: {sku_label or sku} ({available} available)", details={...})` in a `try/except`. <!-- write_alert signature verified: alerts.py:356-366 -->

**`_maybe_clear_low_stock_sentinel` logic:**

1. If `available <= reorder_point`, return (still below threshold).
2. Try `T.inventory.delete_item(Key=_sentinel_key(sku, location_id))`. Errors are swallowed (idempotent).

**Resolving `owner_sub`:** The alert is sent to the user who owns the catalog item for this SKU. Because the inventory service does not store `owner_sub` on the inventory row (OFB-003 design: inventory rows store `sku`, `location_id`, quantities only), `_maybe_emit_low_stock_alert` resolves the owner by querying `T.catalog` via the `ByItemId` GSI using `sku` as the `item_id`. If no catalog item is found, the alert is skipped (best-effort). The `creator_id` field on the catalog item row is the `owner_sub`.

> **Open assumption (§10 Q1):** This resolution works only if `sku` on the inventory row equals `item_id` on the catalog item. The `ByItemId` GSI is declared at `scripts/local-ddb-init.py:123` with `partition_key="item_id"` on the `shopping_catalog` table. The lookup pattern (`IndexName="ByItemId"`, `FilterExpression="entity = :ent"`) is identical to `_find_item_by_id()` at `app/routers/catalog.py:702–718`. <!-- VERIFIED: local-ddb-init.py:123, catalog.py:702-718 -->

## 5. Detailed Behavior & Edge Cases

### 5.1 Downward crossing — normal path

1. Alice's catalog item `sku="WIDGET-A"`, `reorder_point=5`, `available=10`.
2. `reserve("WIDGET-A", 6)` → `available` drops to 4 (`4 <= 5` → crossing).
3. `_maybe_emit_low_stock_alert("WIDGET-A", "warehouse", available=4, reorder_point=5, ...)` is called.
4. Conditional `put_item` on sentinel succeeds → one `inventory.low_stock` alert written to Alice's alert stream.
5. Second call to `reserve("WIDGET-A", 1)` → `available` = 3 (`3 <= 5`).
6. `_maybe_emit_low_stock_alert` again → sentinel exists → `ConditionalCheckFailed` → **suppressed**. No duplicate.

### 5.2 Recovery and re-crossing

1. Continuing from above: `available=3`, sentinel row exists.
2. `release_reservation(rid)` → `available` restored to 9 (`9 > 5`).
3. `_maybe_clear_low_stock_sentinel` deletes sentinel row.
4. Next `reserve("WIDGET-A", 6)` → `available=3` again → sentinel write succeeds → **new alert fires**.

### 5.3 Threshold at zero (`reorder_point=0`)

`_status_for(available=0, reorder_point=0)` → `"out_of_stock"` (available ≤ 0 branch fires before the ≤ rp branch, `app/services/inventory.py:85`). `_maybe_emit_low_stock_alert` only fires for `0 < available <= reorder_point`. With `reorder_point=0` the condition is never true (available would need to be negative, which is prevented). Alert fires at out-of-stock level only if `reorder_point >= 1`.

**Design assumption:** Alert at `available=0` (out-of-stock) is a degenerate case of low-stock and should fire if `reorder_point >= 1`. This is handled naturally by `available <= reorder_point` (e.g., `0 <= 1`).

### 5.4 `commit_reservation` — available unchanged

When `reserve` fires, `available` is already decremented and the sentinel is written (if crossing). `commit_reservation` decrements `on_hand` and `reserved` equally, so `available = on_hand - reserved` is unchanged. The helper `_maybe_emit_low_stock_alert` is still called defensively in case the `reorder_point` was raised between reserve and commit, but the sentinel already exists from the reserve call and suppresses a duplicate.

### 5.5 Adjust upward crosses back over threshold

`adjust("WIDGET-A", +10, "restock")` → `available` goes from 3 to 13 (`13 > 5`). `_maybe_clear_low_stock_sentinel` deletes the sentinel. Subsequent downward adjust → alert fires fresh.

### 5.6 SKU with no catalog item

If `T.catalog.query(IndexName="ByItemId", ...)` returns no match for `sku` (catalog item deleted, or inventory row pre-created), `_maybe_emit_low_stock_alert` cannot resolve an `owner_sub`. The sentinel write still proceeds (dedup is preserved), but `write_alert` is skipped. No error is raised to the caller.

### 5.7 `available < 0` (impossible by invariant, defensive guard)

The inventory service enforces `available >= 0` via the `adjust` guard (`app/services/inventory.py:256–260`) and the `reserve` conditional (`available >= :q`). `_maybe_emit_low_stock_alert` is called with `available >= 0` only. The guard `if available > reorder_point: return` plus `if available <= 0 and reorder_point <= 0: return` covers the `reorder_point=0` degenerate case described in §5.3.

### 5.8 Concurrent reservation race at threshold boundary

Two goroutines both reserve the last unit at the threshold. The single-writer conditional update in `reserve` ensures exactly one succeeds (the other gets 409). The successful reservation decrements `available` and calls `_maybe_emit_low_stock_alert`. If both goroutines happen to pass the `available > reorder_point` guard simultaneously before the inventory write, both will attempt the sentinel conditional put; exactly one succeeds and fires the alert, the other gets `ConditionalCheckFailed` and suppresses — the same atomic test-and-set used for the catalog sentinel.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

All DynamoDB calls in `_maybe_emit_low_stock_alert` and `_maybe_clear_low_stock_sentinel` go through `T.inventory` (bound to DynamoDB Local in dev, real DynamoDB in prod). There is no `S.dev_mode` branch in the alert logic. `write_alert` itself branches on `S.dev_mode` for email delivery (writes to `.logs/dev-emails.log` in dev), but that is entirely within the existing alerts service and is unrelated to this ticket.

### 7.2 Idempotency

The sentinel conditional put (`attribute_not_exists`) is the sole dedup gate. It is idempotent: replaying `_maybe_emit_low_stock_alert` at the same `available` value after the sentinel was already written is a no-op. Replaying `_maybe_clear_low_stock_sentinel` is also a no-op (`delete_item` on a missing key is a no-op in DynamoDB).

### 7.3 Best-effort

Both helpers are wrapped in `try/except Exception: pass` at the call site in each mutation function. An alert failure **never** raises an exception that would roll back a reservation or inventory adjustment.

### 7.4 Security

- Alert recipient is `creator_id` from the catalog item — the item owner. No cross-user alert is possible.
- Sentinel rows carry no PII: only `sku`, `location_id`, and `fired_at`. They are not returned by any API endpoint.
- The `ByItemId` GSI query to resolve `owner_sub` uses an eventual-consistent read; a slight staleness is acceptable for alert delivery.

## 8. Backward Compatibility & Migration

### 8.1 Flag default OFF (master switch)

With `INVENTORY_RESERVATIONS_ENABLED=false` (the current default, `app/core/settings.py:839`) none of the inventory mutation functions are callable (they 404 at the router layer) and OFB-005 code is never reached. Existing behavior of all shop/cart/billing paths is unchanged byte-for-byte.

### 8.2 Sentinel rows are sparse

Sentinel rows use `SK="SENTINEL#LOWSTOCK"` which is not in the `LOC#*` namespace. `get_inventory(sku)` (`inventory.py:150`) issues `get_item(Key={"sku": sku, "location_sk": "LOC#warehouse"})` via `_location_sk()` (`inventory.py:59`) — it cannot accidentally return a sentinel row. `list_low_stock` (`inventory.py:319`) queries `GSI_AVAILABLE` keyed on `status` — sentinel rows omit `status` and `available` so they are never projected into that index. <!-- VERIFIED: inventory.py:59, 150, 319 -->

### 8.3 No DDB schema migration

The sentinel row pattern requires no new GSI, no `attr_types` change, and no table schema update. The `inventory` table already exists from OFB-002 scaffolding.

### 8.4 `alert_priority.py` and `alerts.py` additions are additive

Adding `"inventory.low_stock"` to `_PRIORITY_MAP` and `ALERT_CATEGORIES["commerce"]` does not change the behavior of any existing alert type; it only affects the new event type.

## 10. Open Questions / Assumptions

1. **Owner resolution via `ByItemId` GSI** — assumed `sku` on the inventory row equals `item_id` on the catalog item row. If a catalog item's SKU does not match its `item_id` (they could differ if SKU is a separate vendor ID), the GSI query returns nothing and the alert is silently skipped. The resolution should be verified against the catalog item create path (`app/routers/catalog.py:370–390`) to confirm `item_id` is the same value used as `sku` when provisioning inventory.

2. **`commit_reservation` available value** — `commit_reservation` (`app/services/inventory.py:456–489`) decrements `on_hand` and `reserved` by the same qty, leaving `available` unchanged from the post-reserve state. Calling `_maybe_emit_low_stock_alert` there is defensive (handles the case where `reorder_point` was raised since reserve). If the team prefers to skip the commit call for performance, that is acceptable given the sentinel already exists from the reserve call.

3. **Multi-location support** — OFB-003 stores `location_id` per-inventory row; the sentinel key includes `location_id` in the PK (`SENTINEL#LOWSTOCK` is the SK; if multi-location is added later, the SK should become `SENTINEL#LOWSTOCK#{location_id}`). For the current single-warehouse phase, `location_id="warehouse"` is the only value so this is not a concern — but the implementation should use the actual `location_id` from the row in the sentinel key, not hardcode `"warehouse"`, to be forward-compatible.

4. **Alert recipient when inventory is system-managed** — `reserve` / `commit_reservation` / `expire_due_reservations` pass `user_sub="system"` in some paths. The alert recipient is the catalog item `creator_id`, not the `user_sub` caller. This is intentional: the shop owner, not the customer, should receive low-stock alerts.

5. **`available == reorder_point` boundary** — `_status_for(available, rp)` returns `"low_stock"` for `available <= reorder_point` (not strictly below). Alert should fire at `available == reorder_point` as well. This is consistent with the catalog `_check_low_stock_alert` which fires for `new_stock <= threshold`.

6. **`out_of_stock` vs `low_stock` alert** — when `available=0` (and `reorder_point >= 1`), the status is `"out_of_stock"` but `available <= reorder_point` is still true. The same `inventory.low_stock` event type is used — the title will read "Low stock: SKU-A (0 available)". A separate `inventory.out_of_stock` event type is out of scope for OFB-005; the alert detail carries the `available` count so the admin can distinguish. This assumption should be confirmed with product.
