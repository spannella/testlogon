# HRM-007 — Payroll run service (draft / compute / approve)

**Type:** Feature | **Priority:** P1 | **Estimate:** 3 days
**Milestone:** 3 — Payroll & GL Hook

---

## 1. Summary & Goal

HRM-007 adds the payroll run lifecycle to `app/services/hr_payroll.py` (a new file, separate from `app/services/hr.py` to keep the position/employment service small). The deliverable is two service functions:

- `create_payroll_run(period_start, period_end, *, actor_sub, correlation_id=None)` — enumerates all `ACTIVE` employments from the `hr` table, computes each line's `gross_cents` via pay-period proration, and persists a `DRAFT` payroll run with one `LINE#` item per employment.
- `approve_payroll_run(payroll_run_id, *, actor_sub)` — validates the `DRAFT → APPROVED` transition and writes the status change. No money moves here; disbursement is HRM-008.

A `DRAFT` run enumerates exactly the `ACTIVE` employments at the moment the run is created and never retroactively changes as employments change. Idempotency is provided by `correlation_id`: re-creating a run for the same period with the same `correlation_id` returns the existing run rather than creating a duplicate.

The existing billing, cart, orders, and messaging surfaces are byte-for-byte unchanged when `S.hr_payroll_enabled` is `False` (the default).

## 3. Data Model

HRM-007 introduces no new DynamoDB tables. All items are stored in `T.hr` (the single `hr` table defined by HRM-002) using new `PK` prefixes `PAYROLL#` and `LINE#`.

### 3.1 Payroll Run META item

Stored at `PK=PAYROLL#{payroll_run_id}` / `SK=META`.

| Attribute | DDB type | Value |
|---|---|---|
| `PK` | S | `"PAYROLL#{payroll_run_id}"` |
| `SK` | S | `"META"` |
| `payroll_run_id` | S | `"PR_{sha256_hex_32}"` (deterministic) or `"PR_{uuid4_hex}"` (random) |
| `period_start` | N | Unix epoch seconds (caller-supplied, validated `period_start < period_end`) |
| `period_end` | N | Unix epoch seconds |
| `status` | S | `"DRAFT"` \| `"APPROVED"` \| `"POSTED"` |
| `currency` | S | Inherited from the first active employment; defaults to `"usd"` if no employments found |
| `line_count` | N | Number of `LINE#` items written (may be 0 for a run with no active employees) |
| `total_gross_cents` | N | Sum of all `LINE#` `gross_cents` values |
| `created_at` | N | `now_ts()` at creation time |
| `updated_at` | N | `now_ts()` at last status change |
| `actor_sub` | S | Admin `user_sub` who created the run |
| `approved_by` | S (optional) | Admin `user_sub` who approved; absent until `APPROVED` |
| `approved_at` | N (optional) | Unix epoch seconds of approval; absent until `APPROVED` |
| `correlation_id` | S (optional) | Stored for auditability; absent when none supplied |
| `GSI1PK` | S | `"PAYROLL#{status}"` — e.g. `"PAYROLL#DRAFT"` |
| `GSI1SK` | S | `"PAYROLL#{payroll_run_id}"` — string, consistent with HRM-002 §3.1/§3.3 and §5.5 |
| `entity_type` | S | `"PAYROLL_RUN"` — GSI_CREATED partition key for newest-first listing |

**GSI1SK is a string.** HRM-002 §3.1 declares `GSI1SK` as type `S` for all hr-table items (§5.5: "`GSI1SK` and `GSI2SK` hold string values … No numeric override is needed"). HRM-002 §3.3 reference table shows `Payroll Run META GSI1SK = PAYROLL_RUN#{id}`. DynamoDB does not allow mixed `S`/`N` for the same attribute name within one table's `AttributeDefinitions`, so using a numeric `GSI1SK` here would break position and employment queries that rely on string `GSI1SK`. The string `"PAYROLL#{payroll_run_id}"` enables keyset pagination on `GSI1`. **Newest-first time-ordered listing uses `GSI_CREATED`** (partition key `entity_type="PAYROLL_RUN"`, sort key `created_at` N), not `GSI1`. See §4.6.

**`GSI1PK` must be updated atomically with `status`** in `approve_payroll_run`, just as HRM-005's `update_position_status` will do for positions (`UpdateExpression="SET #status = :status, ..., GSI1PK = :gsi1pk"`). Note: `app/services/hr.py` does not yet exist (VERIFIED) — this is a forward reference to the HRM-005 pattern spec.

### 3.2 Payroll Line item

Stored at `PK=PAYROLL#{payroll_run_id}` / `SK=LINE#{employment_id}`.

| Attribute | DDB type | Value |
|---|---|---|
| `PK` | S | `"PAYROLL#{payroll_run_id}"` (same partition as META) |
| `SK` | S | `"LINE#{employment_id}"` |
| `payroll_run_id` | S | Redundant copy for easy projection |
| `employment_id` | S | FK to `EMPLOYMENT#{employment_id}` in the same `hr` table |
| `party_id` | S | Denormalized from the employment item for display |
| `pay_rate_cents` | N | Snapshot of the employment's `pay_rate_cents` at run creation time |
| `pay_period` | S | Snapshot of `pay_period` at run creation time |
| `gross_cents` | N | Computed proration amount (§5.1) |
| `currency` | S | Snapshot of `currency` from the employment |
| `status` | S | Always `"DRAFT"` when created; transitions with the run (HRM-008 sets to `"POSTED"`) |
| `created_at` | N | `now_ts()` |

**Co-location rationale:** Both META and LINE items share `PK=PAYROLL#{payroll_run_id}`, enabling a single `query(KeyConditionExpression=Key("PK").eq(f"PAYROLL#{payroll_run_id}"))` to retrieve the run and all its lines in one round-trip.

### 3.3 GSI layout — no change to HRM-002's `hr` table `attr_types`

HRM-002 (the authoritative foundation ticket for the `hr` table) defines `attr_types={"created_at": "N"}` only — `GSI1SK` is `S` for all entity types. **HRM-007 does NOT add `"GSI1SK": "N"` to `attr_types`.** The payroll run META item writes a string value for `GSI1SK` (e.g. `"PAYROLL#PR_abc123"`), consistent with position and employment items that use `"POSITION#{id}"` and `"EMPLOYMENT#{id}"` respectively. The HRM-002 `TableDef` is reproduced here for reference (no change needed):

```python
TableDef(
    _resolve_table_name(S.hr_table_name, "hr"),
    "PK", "SK",
    gsi=[
        {"index_name": "GSI1",       "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "GSI2",       "partition_key": "GSI2PK", "sort_key": "GSI2SK"},
        {"index_name": "GSI_CREATED","partition_key": "entity_type", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
    # GSI1SK is S (string) — no "N" override needed or permitted.
    # GSI2SK is S (string) — no "N" override needed.
    # GSI_CREATED sort key created_at is N — declared above.
)
```

`just restart` recreates the table with these settings. No `attr_types` change is required for HRM-007; the existing HRM-002 definition is correct and complete.

### 3.4 Idempotency guard item (optional — see §5.3)

No separate idempotency guard row is needed: the `PK=PAYROLL#{payroll_run_id}` / `SK=META` item itself serves as the idempotency guard via `attribute_not_exists(PK)` on `put_item`. Consuming the guard on first write and fetching on `ConditionalCheckFailedException` mirrors the pattern in `app/services/cart_reminders.py:201-211` (VERIFIED — `_mark_token_consumed` at line 198 uses `ConditionExpression="attribute_not_exists(pk)"` with `try/except` returning `False` on failure; note that `cart_reminders.py` uses lowercase `pk` while the `hr` table will use uppercase `PK` per the HRM-002 spec).

### 4.2 `create_payroll_run`

```python
def create_payroll_run(
    period_start: int,
    period_end: int,
    *,
    actor_sub: str,
    currency: str = "usd",
    correlation_id: Optional[str] = None,
) -> Dict[str, Any]:
    """
    Create a DRAFT payroll run for the given period.

    Enumerates all ACTIVE employments and computes gross_cents per line.
    Re-creating with the same correlation_id returns the existing run (idempotent).

    Args:
        period_start: Unix epoch seconds for the start of the pay period (inclusive).
        period_end:   Unix epoch seconds for the end of the pay period (inclusive).
        actor_sub:    user_sub of the admin initiating the run (written to audit log).
        currency:     Currency code; defaults to "usd". All line items inherit this.
        correlation_id: Optional caller-supplied idempotency key.

    Returns:
        Dict with the payroll run META item shape (§3.1).

    Raises:
        ValueError: if period_start >= period_end.
    """
```

**Behaviour:**

1. Validate `period_start < period_end`. Raise `ValueError("period_start must be before period_end")` otherwise.
2. Derive `payroll_run_id`:
   - If `correlation_id` supplied: `payroll_run_id = "PR_" + hashlib.sha256(correlation_id.encode("utf-8")).hexdigest()[:32]`.
   - Otherwise: `payroll_run_id = "PR_" + uuid.uuid4().hex`.
3. `ts = now_ts()`.
4. Build the META item (§3.1) with `status="DRAFT"`, `line_count=0`, `total_gross_cents=0` as placeholders.
5. Call `T.hr.put_item(Item=meta_item, ConditionExpression="attribute_not_exists(PK)")`.
   - On `ClientError` with `"ConditionalCheckFailedException"`: fetch and return the existing run via `get_payroll_run(payroll_run_id)` (idempotent replay — same `correlation_id`, no duplicate).
6. Enumerate active employments by paginating `list_employments(status="ACTIVE")` (from `app.services.hr`) until `next_cursor` is exhausted. Collect all active employment dicts.
7. For each employment, compute `gross_cents = _compute_gross(employment, period_start, period_end)` (§5.1).
8. Build and write each `LINE#` item: `T.hr.put_item(Item=line_item)`. No condition expression needed on line items — the `payroll_run_id` is unique, and line `SK=LINE#{employment_id}` is unique within the run.
9. Update the META item: `T.hr.update_item(...)` to set `line_count=len(lines)` and `total_gross_cents=sum(l["gross_cents"] for l in lines)`.
10. Call `audit_event("payroll_run.created", actor_sub, payroll_run_id=payroll_run_id, line_count=len(lines), period_start=period_start, period_end=period_end)` best-effort.
11. Return the updated META item dict.

### 4.3 `approve_payroll_run`

```python
def approve_payroll_run(
    payroll_run_id: str,
    *,
    actor_sub: str,
) -> Dict[str, Any]:
    """
    Transition a payroll run from DRAFT to APPROVED.

    Re-approving an already-APPROVED run is a no-op (returns current item).
    Approving a non-DRAFT, non-APPROVED run raises PayrollRunInvalidTransitionError.

    Args:
        payroll_run_id: The run to approve.
        actor_sub:      user_sub of the approving admin.

    Returns:
        Updated run META item with status="APPROVED".

    Raises:
        LookupError: if the run does not exist.
        PayrollRunInvalidTransitionError: if status is not DRAFT or APPROVED.
    """
```

**Behaviour:**

1. Fetch existing run via `get_payroll_run(payroll_run_id)`. If `None`, raise `LookupError("payroll_run_not_found")`.
2. `current_status = run["status"]`.
3. If `current_status == "APPROVED"`: return the existing item unchanged (re-approve is a no-op).
4. If `current_status != "DRAFT"`: raise `PayrollRunInvalidTransitionError(f"{current_status}→APPROVED")`.
5. `ts = now_ts()`.
6. `T.hr.update_item(Key={"PK": f"PAYROLL#{payroll_run_id}", "SK": "META"}, UpdateExpression="SET #status = :status, GSI1PK = :gsi1pk, approved_by = :approver, approved_at = :ts, updated_at = :ts", ExpressionAttributeNames={"#status": "status"}, ExpressionAttributeValues={":status": "APPROVED", ":gsi1pk": "PAYROLL#APPROVED", ":approver": actor_sub, ":ts": ts})`.
7. Call `audit_event("payroll_run.approved", actor_sub, payroll_run_id=payroll_run_id)` best-effort.
8. Fetch and return the updated item via `get_payroll_run(payroll_run_id)`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Pay-period proration table

`period_duration_seconds = period_end - period_start`

| `pay_period` | Formula for `gross_cents` |
|---|---|
| `MONTHLY` | `pay_rate_cents` (rate is already a monthly figure; no proration; the run period is expected to be one calendar month — see §10.4) |
| `BIWEEKLY` | `int(pay_rate_cents * period_duration_seconds / (14 * 86400))` |
| `WEEKLY` | `int(pay_rate_cents * period_duration_seconds / (7 * 86400))` |
| `HOURLY` | `int(pay_rate_cents * period_duration_seconds / 3600)` (rate is per hour; period in seconds / 3600 = hours in period) |

All intermediate values use Python integer multiplication and floor division (`int(...)` on a float result). Overflow is not a concern in Python but callers must validate `pay_rate_cents >= 0` (enforced by `CreateEmploymentIn` in HRM-003) and `period_duration_seconds > 0` (enforced by `CreatePayrollRunIn`).

**Example (biweekly):** A 14-day period (`period_duration_seconds = 14 * 86400 = 1_209_600`), `pay_rate_cents = 300000` (USD 3,000.00):
```
gross_cents = int(300000 * 1_209_600 / (14 * 86400)) = int(300000 * 1.0) = 300000
```

**Example (hourly, 40-hour week × 2 = 80 hours):** `period_duration_seconds = 80 * 3600 = 288_000`, `pay_rate_cents = 2500`:
```
gross_cents = int(2500 * 288000 / 3600) = int(200000) = 200000
```

### 5.2 `DRAFT → APPROVED` transition only

The allowed transitions for a payroll run are:

```python
_PAYROLL_RUN_ALLOWED_TRANSITIONS: Dict[str, Set[str]] = {
    "DRAFT":    {"APPROVED"},
    "APPROVED": {"POSTED"},    # POSTED transition happens in HRM-008, not here
    "POSTED":   set(),         # terminal
}
```

HRM-007 only implements `DRAFT → APPROVED`. The `APPROVED → POSTED` transition is HRM-008's scope and is included in the table here so the design is consistent. Callers cannot approve a `POSTED` run.

### 5.3 Idempotent run creation

Two callers simultaneously calling `create_payroll_run` with the same `correlation_id` compete on the `put_item` conditional. Exactly one wins and writes the META item. The other receives `ConditionalCheckFailedException` and returns the winner's item. Both callers see identical responses. Line items are never double-written because they are written only after the META `put_item` succeeds.

If the process crashes after the META `put_item` but before all `LINE#` items are written (partial failure), the run exists in DDB with `line_count=0` and incomplete lines. The retry (same `correlation_id`) will hit `ConditionalCheckFailedException` and return the partial run without re-enumerating employments. This partial-run case is handled by making the `update_item` for `line_count` / `total_gross_cents` idempotent: it uses `SET` (not `ADD`), so replaying a complete re-run (via a different `correlation_id`) after deleting the partial run is the operator's remediation. See §10.3 for the design trade-off.

### 5.4 Run with zero active employments

If there are no `ACTIVE` employments at the time `create_payroll_run` is called, the run is created with `line_count=0` and `total_gross_cents=0` in `DRAFT` status. This is valid: an admin may choose to approve a zero-line run (a no-op disbursement). HRM-008 must handle zero-line runs gracefully (transition to `POSTED` immediately with no ledger writes).

### 5.5 Re-approve is a no-op

`approve_payroll_run` called on an already-`APPROVED` run returns the existing item unchanged and emits no audit event for the second call (the re-approve check short-circuits before the audit call). This prevents audit log spam from retry-happy clients.

### 5.6 Concurrent approve

Two admins simultaneously calling `approve_payroll_run` on the same `DRAFT` run both call `update_item`. DynamoDB's `update_item` is atomic at the item level, so both writes succeed (both set `status=APPROVED`, `approved_by=<respective_admin>`, `approved_at=<respective_ts>`). The last writer wins for `approved_by` and `approved_at`. If exact "who approved first" semantics matter, a `ConditionExpression="attribute_not_exists(approved_by)"` can be added to `update_item` — the second write would then fail. This is an open question (§10.5).

### 5.7 Employment snapshots are immutable in the run

Once lines are written, subsequent changes to the employment (e.g., a pay rate increase) do NOT affect existing lines. The `pay_rate_cents` and `pay_period` on each `LINE#` item are point-in-time snapshots captured at run creation. This is the intended accounting behavior: a payroll run is a historical record of what was owed in that period.

### 5.8 Multi-currency runs

`create_payroll_run` accepts a `currency` parameter and passes it through to all lines. If an organization uses a single currency, all employment records carry the same `currency`. Multi-currency scenarios (e.g., USD and EUR employees in the same run) are deferred: HRM-007 produces a single `currency` for the run header and does not validate that all employment `currency` values match. HRM-008 (disbursement) must validate per-line currency consistency before posting. See §10.6.

### 5.9 DDB FilterExpression page-size gotcha

`list_employments(status="ACTIVE")` in `app/services/hr.py` queries `GSI1` with `KeyConditionExpression=Key("GSI1PK").eq("EMPLOYMENT#ACTIVE")` — this is a key condition, not a filter. Each DDB page returns honest `limit` items; the loop collects all pages via `next_cursor`. Per CLAUDE.md: "DDB FilterExpression doesn't reduce page size" — the `GSI1` key-condition path avoids this trap entirely.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007: no dev/prod code branches

`app/services/hr_payroll.py` contains no `if S.dev_mode:` branches. DynamoDB reads and writes are identical in dev (DynamoDB Local on port 8001, `DDB_ENDPOINT_URL=http://localhost:8001`) and production (real DynamoDB, IAM credentials). The only infrastructure difference is the endpoint URL, which is transparent to the service layer.

### 7.2 Idempotency

- **Run creation**: `attribute_not_exists(PK)` conditional `put_item` + `ConditionalCheckFailedException` → fetch-and-return. The same `correlation_id` from any caller (including post-timeout retries) produces the same `payroll_run_id` and the same response.
- **Line writes**: Lines are written only after the META `put_item` succeeds. A retry after a partial failure returns the existing run (see §5.3). Line writes themselves are `put_item` without a condition, so a retry that reaches line-writing would overwrite existing lines with identical data — safe because lines are deterministic snapshots.
- **Approve**: Re-approve is an explicit no-op (§5.5). No idempotency key is needed on the `update_item` call because the `status=DRAFT` pre-check prevents double-approval.

### 7.3 Security

- All endpoints are `require_admin_or_root_csrf` — regular users cannot create or approve payroll runs. Non-admin callers receive HTTP 403 before any service code runs.
- `payroll_run_id` is derived from `sha256(correlation_id)` or `uuid4()`, never from caller-supplied input directly. Callers cannot inject a `payroll_run_id` that collides with a `POSITION#` or `EMPLOYMENT#` item because the `PAYROLL#` namespace prefix is applied by the service.
- The `pay_rate_cents` and `gross_cents` values written to `LINE#` items are integers. No floating-point is persisted; proration uses integer arithmetic with floor semantics (§5.1).
- Audit events (`payroll_run.created`, `payroll_run.approved`) are written to `T.alerts` via `audit_event` for each run lifecycle event. These are best-effort (wrapped in `try/except`) — an audit failure never blocks the primary write.
- Employment data accessed during run creation is read-only. The service writes only to `T.hr` (the payroll-specific items); it never modifies employment or position records.

### 7.4 Money isolation

HRM-007 writes **zero ledger entries**. The `billing_shared.new_ledger_entry` function is referenced in this spec only as documentation of the contract HRM-008 must use. Any accidental call to `new_ledger_entry` from `hr_payroll.py` during HRM-007 is a bug; the test plan (§9) verifies this explicitly.

## 10. Open Questions / Assumptions

> **Verification status**: All existing-codebase claims in §2 and §4.9 have been verified against the live repo. No current-state claims were found to be incorrect. Three minor imprecisions were corrected: §2.9 (`license_agreements.py:265-298` → `:268-298`), §2.8 (explicit note that `audit_export_schedule.py:103-111` has a conditional FilterExpression), and §2.7 (clarified that messaging uses table-specific key names rather than the literal string `"pk"`).

1. **Assumption: `list_employments(status="ACTIVE")` from HRM-006 is the sole source of payroll-eligible employees.** The function queries `GSI1` with `Key("GSI1PK").eq("EMPLOYMENT#ACTIVE")` and paginates. If HRM-006 uses a different signature or return shape, `hr_payroll.py` must adapt. Verify against the HRM-006 implementation before writing `create_payroll_run`.

2. **Assumption: `MONTHLY` `gross_cents` equals `pay_rate_cents` with no proration.** This holds when the period is exactly one calendar month. If the caller passes a non-monthly period duration for a monthly-paid employee (e.g., a partial month), the current formula over- or under-pays. The ticket does not specify partial-month handling for monthly employees; an explicit validation (reject a run whose duration ≠ ~30 days if any monthly employees exist) is a possible follow-on. Recorded here as an assumption.

3. **Assumption: `T.hr` uses uppercase `PK`/`SK` as hash/range keys.** HRM-002 and HRM-005 both use `{"PK": ..., "SK": ...}` with uppercase key names. All service code must match. If HRM-002 instead uses lowercase `pk`/`sk`, this spec needs a one-character change throughout — verify at implementation time.

4. **Assumption: `period_start` and `period_end` are Unix epoch seconds (integers).** The `CreatePayrollRunIn` model enforces this. Callers passing millisecond timestamps would compute incorrectly large proration durations; the router should document the expected unit.

5. **Assumption: concurrent approve does not require "exactly one approver" semantics.** Last-writer-wins is acceptable for the initial implementation. If an approval audit trail requires a single canonical approver, add `ConditionExpression="attribute_not_exists(approved_by)"` to `approve_payroll_run`'s `update_item` — the losing concurrent approver gets a `ConditionalCheckFailedException` and should re-fetch to see the winning approver. Deferred pending product decision.

6. **Assumption: partial-run recovery (crash between META write and LINE writes) requires operator intervention.** A partial run can be detected by comparing `line_count` on the META item against the actual count from `get_payroll_run_lines`. A cleanup endpoint (or a `repair_payroll_run` service function) is out of scope for HRM-007 but may be needed for production robustness. The ticket does not specify recovery semantics; this assumption is explicit.

7. **Assumption: all active employments in a single run share the same currency.** HRM-007 uses the `currency` parameter passed to `create_payroll_run` (default `"usd"`) for the run header, and passes the employment's own `currency` through to each line. Multi-currency reconciliation (summing `total_gross_cents` across mixed-currency lines) is deferred to HRM-008 or a follow-on.

8. **RESOLVED: `GSI1SK` for payroll run META items is a string `"PAYROLL#{payroll_run_id}"`.** (Escalation ESCALATIONS.md plan-gap #15, resolved in §14.) HRM-002 §5.5 commits `GSI1SK` to type `S` across all hr-table items; payroll runs use the same string pattern as positions and employments. Newest-first time-ordered listing uses `GSI_CREATED` (numeric `created_at`), not `GSI1`. The earlier draft of this assumption proposing a numeric `GSI1SK` was incorrect and has been corrected throughout this spec.

9. **Open question: should `line_count` and `total_gross_cents` be updated transactionally with the LINE writes?** The current design uses a separate `update_item` call after all `put_item` calls. A DynamoDB `TransactWriteItems` could atomically write all lines and update the META in one call (up to 100 items per transaction). For large payrolls (>99 employees), `TransactWriteItems` would not be applicable without batching. The non-transactional approach is simpler and sufficient for the initial implementation; this is flagged as a follow-on optimization.

10. **Assumption: `now_ts()` at `app/core/time.py:2` is the correct timestamp source.** All other time-stamped HR items use `now_ts()`. Tests that verify `approved_at > 0` use `unittest.mock.patch("app.core.time.now_ts", return_value=12345)` to control the timestamp.
