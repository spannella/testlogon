# FXA-007 — Asset register router

## 1. Summary & Goal

FXA-007 creates `app/routers/fixed_assets.py` — the HTTP layer that exposes the fixed-asset register and its depreciation schedule to callers. The router mounts under the prefix `/ui/fixed-assets` and connects to the service functions established by FXA-005 (`create_asset`, `get_asset`, `list_assets`, `update_asset`, `dispose_asset`) and FXA-006 (`generate_schedule`) in `app/services/fixed_assets.py`.

Every handler is gated by `S.fixed_assets_enabled`; with the flag off all endpoints respond immediately with HTTP 503 and the message `"Fixed assets module is not enabled"`. When the flag is on, all asset-mutating operations are restricted to users with at least `ADMIN` or `ROOT` role via `require_admin_or_root_csrf` (which also enforces CSRF for cookie-authenticated requests); the schedule read endpoint is accessible to any authenticated session via `require_ui_session` (read-only, no money movement, no state mutation). Non-admin → 403. Unauthenticated → 401.

After this ticket:
- `POST /ui/fixed-assets` creates and returns a registered asset.
- `GET /ui/fixed-assets` lists assets for a given owner or status, paginated.
- `GET /ui/fixed-assets/{asset_id}` retrieves a single asset with computed `net_book_value_cents`.
- `PATCH /ui/fixed-assets/{asset_id}` applies a partial update (mutable fields only).
- `POST /ui/fixed-assets/{asset_id}/dispose` marks an asset disposed.
- `GET /ui/fixed-assets/{asset_id}/schedule` returns the generated depreciation schedule.

Existing shop, cart, orders, billing, and inventory paths are byte-for-byte unchanged when `FIXED_ASSETS_ENABLED` is false (the default).

### 2.5 Route-ordering constraint (CLAUDE.md gotcha)

CLAUDE.md documents that FastAPI matches routes in declaration order, citing the `/schedules`-before-`/{id}` gotcha (see KYC audit schedule routes). Any future literal sub-path (e.g. `/fixed-assets/classes` for FXA-016 if asset-class management is ever added) must be declared before `/{asset_id}`. The `{asset_id}/schedule` and `{asset_id}/dispose` sub-routes do not conflict because `schedule` and `dispose` are anchored under a path param, not a sibling of it. However, any literal collection-level path (e.g., a hypothetical `/fixed-assets/export`) must be placed before the `/{asset_id}` patterns in the router file.

## 3. Data Model

FXA-007 introduces no new DynamoDB tables or GSIs. It reads and writes through the tables established by FXA-003:

### 3.1 `fixed_assets` table (PK / SK)

| Key | Value |
|---|---|
| `pk` (S) | `"ASSET#{asset_id}"` |
| `sk` (S) | `"META"` |

GSIs used by the list endpoint:

| GSI name | PK | SK | `attr_types` |
|---|---|---|---|
| `GSI_OWNER` | `owner_sub` (S) | `acquired_at` (N) | `{"acquired_at": "N"}` |
| `GSI_STATUS` | `status` (S) | `acquired_at` (N) | (same key, shared) |

### 3.2 `fixed_asset_schedule` table

| Key | Value |
|---|---|
| `pk` (S) | `"ASSET#{asset_id}"` |
| `sk` (S) | `"PERIOD#{period:07d}"` — one row per depreciation period |

GSI used by `GET /{asset_id}/schedule`:

| GSI name | PK | SK | `attr_types` |
|---|---|---|---|
| `GSI_DUE` | `schedule_status` (S) | `period_end_ts` (N) | `{"period_end_ts": "N"}` |

The `GET /{asset_id}/schedule` handler does NOT query `GSI_DUE` — it reads by PK `"ASSET#{asset_id}"` over the base table to retrieve all periods for a single asset, sorted by SK (`PERIOD#0000001`, `PERIOD#0000002`, …). `GSI_DUE` is used only by the background depreciation poster (FXA-009) to find due-but-unposted periods across all assets.

## 4. API / Service Design

### 4.1 Router declaration

```python
# app/routers/fixed_assets.py
from __future__ import annotations

from fastapi import APIRouter, Depends, HTTPException, Query
from app.auth.deps import AuthenticatedUser
from app.auth.policy import require_admin_or_root_csrf
from app.models import (
    DepreciationScheduleOut,
    FixedAssetDisposeIn,
    FixedAssetIn,
    FixedAssetListOut,
    FixedAssetOut,
    FixedAssetPatchIn,
)
from app.services import fixed_assets as fxa
from app.services.sessions import require_ui_session

fixed_assets_router = APIRouter(prefix="/ui/fixed-assets", tags=["fixed-assets"])
```

### 4.2 Endpoint table

| Method | Path | Auth dep | Service call | Notes |
|---|---|---|---|---|
| `POST` | `/ui/fixed-assets` | `require_admin_or_root_csrf` | `fxa.create_asset(user.sub, body)` | 201 on create, 200 on idempotent replay |
| `GET` | `/ui/fixed-assets` | `require_admin_or_root_csrf` | `fxa.list_assets(owner_sub, status, limit, cursor)` | 200; `owner_sub` and `status` are optional query params |
| `GET` | `/ui/fixed-assets/{asset_id}` | `require_ui_session` | `fxa.get_asset(session["user_sub"], asset_id)` | 200 or 404 |
| `PATCH` | `/ui/fixed-assets/{asset_id}` | `require_admin_or_root_csrf` | `fxa.update_asset(user.sub, asset_id, body)` | 200 or 404 |
| `POST` | `/ui/fixed-assets/{asset_id}/dispose` | `require_admin_or_root_csrf` | `fxa.dispose_asset(user.sub, asset_id, body)` | 200 or 404 |
| `GET` | `/ui/fixed-assets/{asset_id}/schedule` | `require_ui_session` | `fxa.generate_schedule(asset_id)` | 200 or 404 |

All handlers call `fxa._require_enabled()` as their first statement, before any other logic, returning 503 when the flag is off.

### 4.3 Handler function signatures

```python
@fixed_assets_router.post("", response_model=FixedAssetOut, status_code=201)
async def create_asset(
    body: FixedAssetIn,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> FixedAssetOut:
    fxa._require_enabled()
    return fxa.create_asset(owner_sub=user.sub, req=body)


@fixed_assets_router.get("", response_model=FixedAssetListOut)
async def list_assets(
    owner_sub: str | None = Query(default=None, description="Filter by owner sub"),
    status: str | None = Query(default=None, description="Filter by status: active|fully_depreciated|disposed"),
    limit: int = Query(default=25, ge=1, le=100),
    cursor: str | None = Query(default=None),
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> FixedAssetListOut:
    fxa._require_enabled()
    result = fxa.list_assets(owner_sub=owner_sub, status=status, limit=limit, cursor=cursor)
    return FixedAssetListOut(**result)


@fixed_assets_router.get("/{asset_id}", response_model=FixedAssetOut)
async def get_asset(
    asset_id: str,
    session=Depends(require_ui_session),
) -> FixedAssetOut:
    fxa._require_enabled()
    asset = fxa.get_asset(owner_sub=session["user_sub"], asset_id=asset_id)
    if asset is None:
        raise HTTPException(status_code=404, detail="Asset not found")
    return asset


@fixed_assets_router.patch("/{asset_id}", response_model=FixedAssetOut)
async def update_asset(
    asset_id: str,
    body: FixedAssetPatchIn,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> FixedAssetOut:
    fxa._require_enabled()
    updated = fxa.update_asset(owner_sub=user.sub, asset_id=asset_id, patch=body)
    return updated


@fixed_assets_router.post("/{asset_id}/dispose", response_model=FixedAssetOut)
async def dispose_asset(
    asset_id: str,
    body: FixedAssetDisposeIn,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> FixedAssetOut:
    fxa._require_enabled()
    result = fxa.dispose_asset(owner_sub=user.sub, asset_id=asset_id, req=body)
    return result


@fixed_assets_router.get("/{asset_id}/schedule", response_model=DepreciationScheduleOut)
async def get_schedule(
    asset_id: str,
    session=Depends(require_ui_session),
) -> DepreciationScheduleOut:
    fxa._require_enabled()
    schedule = fxa.generate_schedule(asset_id=asset_id)
    return schedule
```

### 4.4 Route ordering

The handler declarations in `fixed_assets.py` are ordered as follows to satisfy the CLAUDE.md declaration-order constraint:

1. `POST ""` — collection create
2. `GET ""` — collection list
3. `GET "/{asset_id}/schedule"` — sub-resource GET (literal segment `schedule` under param)
4. `POST "/{asset_id}/dispose"` — sub-resource action (literal segment `dispose` under param)
5. `GET "/{asset_id}"` — single-item GET
6. `PATCH "/{asset_id}"` — single-item PATCH

`/{asset_id}/schedule` and `/{asset_id}/dispose` are placed before the bare `/{asset_id}` handlers because FastAPI's path matching is positional: if `/{asset_id}` were declared first, a request to `/{some_id}/schedule` would match the bare-param handler with `asset_id = "some_id/schedule"` (if the path param were greedy) or fail in unexpected ways. Since both sub-paths are two segments deep, they are structurally distinct from the single-segment `/{asset_id}` and FastAPI will differentiate them correctly regardless of order, but explicit ordering is still best practice per CLAUDE.md.

### 4.5 `main.py` registration

```python
# Immediately after: app.include_router(returns_rma_router)  [app/main.py:878]
from app.routers.fixed_assets import fixed_assets_router
app.include_router(fixed_assets_router)
```

The import and `include_router` call are a single inline block, not a conditional (`if S.fixed_assets_enabled:` style). This matches the `inventory_router` and `returns_rma_router` pattern: the router is always registered; handlers self-gate via `_require_enabled()` at request time. This avoids startup-time flag evaluation issues and keeps the router always reachable for health checks or feature-flag reads.

## 5. Detailed Behavior & Edge Cases

### 5.1 `POST /ui/fixed-assets` — create

1. `fxa._require_enabled()` → 503 if flag off.
2. `require_admin_or_root_csrf` → 403 if not admin/root; CSRF enforced for cookie sessions.
3. FastAPI validates the `FixedAssetIn` body: negative cost → 422; `salvage >= cost` → 422; non-`straight_line` method → 422.
4. Service `create_asset` computes `asset_id = sha256(correlation_id)[:32]`. If `correlation_id` is `None`, a random UUID is used so each call is unique.
5. `put_item` with `attribute_not_exists(pk)` guard. On `ConditionalCheckFailedException`, the service returns the existing item (idempotent replay returns 201 with the same body — this is intentional; the HTTP spec allows 201 on idempotent creates).
6. Audit event `"fixed_asset.created"` emitted (best-effort via `_audit`).
7. Response: `FixedAssetOut` with `net_book_value_cents = acquisition_cost_cents` (since `accumulated_depreciation_cents = 0` on creation).

### 5.2 `GET /ui/fixed-assets` — list

- No `owner_sub` or `status` filter → service queries `GSI_OWNER` for `owner_sub = user.sub` (admin sees only their own unless a target `owner_sub` is supplied). Admin can supply an arbitrary `owner_sub` to list another user's assets.
- `status` filter → service queries `GSI_STATUS` partitioned by `status` value.
- Both filters → service queries `GSI_OWNER` first, then filters by status in Python (a DynamoDB `FilterExpression` on the GSI) rather than a separate `GSI_STATUS` query; this avoids a cross-partition merge and keeps pagination coherent.
- Pagination: `cursor` decoded via `app/core/cursor.decode_cursor`; `LastEvaluatedKey` from DynamoDB encoded via `app/core/cursor.encode_cursor` into `next_cursor` on the response.
- Valid `status` values: `active`, `fully_depreciated`, `disposed`. An unrecognized value → 422 (service raises `HTTPException(422, "invalid status filter")`).
- Response: `FixedAssetListOut(items=[...], count=N, cursor=str|None)`.

### 5.3 `GET /ui/fixed-assets/{asset_id}` — get single

- `require_ui_session` → 401 if unauthenticated. Any authenticated user (role USER, ADMIN, ROOT) may call this endpoint; the service enforces ownership (non-admin users only see assets where `owner_sub == session["user_sub"]`). Admin or root sees the asset regardless of `owner_sub` — the service detects role via the `session["role"]` field and skips the ownership check for admins.
- 404 if asset does not exist or ownership check fails (same error code to avoid leaking existence to unauthorized callers).
- Response includes derived `net_book_value_cents = max(salvage_value_cents, acquisition_cost_cents - accumulated_depreciation_cents)` computed by the `FixedAssetOut` model validator.

### 5.4 `PATCH /ui/fixed-assets/{asset_id}` — partial update

- Only fields present on `FixedAssetPatchIn` are updated: `name`, `asset_class`, `gl_asset_account_id`, `gl_accum_depr_account_id`, `gl_depr_expense_account_id`, `gl_gain_loss_account_id`.
- Cost, salvage value, useful life, `acquired_at`, and `depreciation_method` are immutable after creation and absent from `FixedAssetPatchIn` — any attempt to pass them in the request body is silently ignored (Pydantic's default `extra="ignore"` behavior) rather than rejected, for forward-compatibility.
- 404 if asset not found.
- 409 if asset `status == "disposed"` — disposed assets are immutable.
- Audit event `"fixed_asset.updated"` emitted with before/after snapshots.

### 5.5 `POST /ui/fixed-assets/{asset_id}/dispose` — dispose

- 404 if asset not found.
- 409 if already `status == "disposed"` (idempotency guard: re-disposing is an error, not a no-op, since disposal may trigger payment flows via FXA-011).
- `proceeds_payment_intent_id` and `proceeds_amount_cents` must co-occur (validated in `FixedAssetDisposeIn.proceeds_fields_consistent` model validator → 422 if mismatched).
- When `proceeds_payment_intent_id` is supplied, the service calls into the existing `new_ledger_entry` / `apply_balance_delta` / `settle_or_reverse_ledger` path from `app/services/billing_shared.py` (functions at lines 224, 83, 262 respectively); it does NOT mint a new payment mechanism. `refund_payment` is a router-level helper in `app/routers/billing.py:1287` — it must **not** be called from the service layer. This constraint is enforced at the service layer (FXA-005) not the router.
- Sets `status = "disposed"`, `disposed_at = now_ts()`.
- Audit event `"fixed_asset.disposed"`.

### 5.6 `GET /ui/fixed-assets/{asset_id}/schedule` — get depreciation schedule

- `require_ui_session` — read-only, same ownership semantics as `GET /{asset_id}`.
- If no schedule rows exist (asset was never scheduled via FXA-006's `generate_schedule`), the service attempts to generate one on first call. If the asset itself does not exist → 404.
- Returns `DepreciationScheduleOut(asset_id, periods=[...], total_periods, posted_periods, remaining_periods)`.
- `periods` are ordered ascending by `period` (period 1 → period N), i.e., oldest-first. This matches the natural DDB sort order of `PERIOD#0000001` < `PERIOD#0000002` with `ScanIndexForward=True`. The ticket spec says "newest-or-oldest-first per spec" — this router defaults to oldest-first (ascending); a `?order=desc` query param may be added in a follow-up without a breaking change.
- Posted periods carry `journal_entry_id` and `posted_at`; scheduled periods carry `None` for both.

### 5.7 503 gate behavior

When `S.fixed_assets_enabled` is `False`:

```python
fxa._require_enabled()
# raises HTTPException(503, "Fixed assets module is not enabled")
```

FastAPI serializes this as:
```json
{"detail": "Fixed assets module is not enabled"}
```
with HTTP 503. No database I/O, no import side-effects. The router is registered unconditionally in `main.py` so the 503 is returned (not a connection error or 404), allowing clients to distinguish "disabled feature" from "wrong path".

### 5.8 CSRF behavior

`require_admin_or_root_csrf` calls `enforce_cookie_csrf(request)` (from `app/auth/policy.py:71–97`). For cookie-authenticated requests (browser SPA), non-GET methods require the `x-csrf-token` header to match the `ui_csrf` cookie. Bearer-token / API-key clients bypass CSRF (no session cookie present). This is identical to the behavior of the returns and inventory admin endpoints.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

The router contains zero `if S.dev_mode:` branches. All DynamoDB I/O is delegated to the service (`app/services/fixed_assets.py`) which itself has no dev/prod branches. Local development uses DynamoDB Local at port 8001 (via `DDB_ENDPOINT_URL=http://localhost:8001`); production uses real AWS DynamoDB — same table names, same code path.

### 7.2 Idempotency

- **Create**: deterministic `asset_id = sha256(correlation_id)[:32]`. Re-POSTing with the same `correlation_id` returns the existing asset unchanged (conditional put with `attribute_not_exists(pk)`). No duplicate rows are written.
- **Dispose**: re-disposing an already-`disposed` asset returns 409 (not idempotent by design — disposal triggers financial flows that must not be double-executed). The caller is expected to check the current status with `GET /{asset_id}` before re-attempting.
- **Update**: `PATCH` is idempotent by nature (updating to the same value produces the same result).
- **Schedule**: `GET /{asset_id}/schedule` triggers `generate_schedule` on first call; subsequent calls regenerate only `scheduled` (un-posted) periods — already-`posted` rows are never touched (FXA-006 contract). This makes the GET endpoint effectively idempotent.

### 7.3 Auth and ownership

- Only `ADMIN` or `ROOT` may create, list, update, or dispose assets. Users with role `USER` cannot perform any mutation and receive 403.
- `GET` endpoints (`/{asset_id}` and `/{asset_id}/schedule`) are accessible to any authenticated session. The service enforces ownership for non-admin callers: a `USER` role session can only retrieve assets where `owner_sub == session["user_sub"]`. Admin/root see any asset.
- All ownership checks are in the service layer (FXA-005), not the router. The router passes `session["user_sub"]` to the service for ownership resolution; it does not inspect `session["role"]` directly.
- Asset IDs are not guessable (sha256-derived hex strings), but security by obscurity is not relied upon — ownership enforcement is strict at the service layer.

### 7.4 CSRF

Non-GET mutations on cookie-authenticated sessions require `x-csrf-token` header. Bearer-auth API clients are exempt. This is enforced by `require_admin_or_root_csrf` (not by the router code itself), consistent with `app/routers/inventory.py:48` and `app/routers/returns_rma.py:62`.

### 7.5 Audit trail

Every mutation is wrapped in a best-effort `_audit` call (lazy-import `app.services.alerts.audit_event`, swallows exceptions). An audit failure never aborts the mutation. Events written:

| Handler | Audit event |
|---|---|
| `create_asset` | `"fixed_asset.created"` |
| `update_asset` | `"fixed_asset.updated"` (before/after snapshot) |
| `dispose_asset` | `"fixed_asset.disposed"` |

`generate_schedule` (called by `GET /{asset_id}/schedule`) emits `"fixed_asset.schedule_generated"` or `"fixed_asset.schedule_regenerated"` depending on whether pre-existing scheduled rows were overwritten (FXA-006 contract).

## 8. Backward Compatibility & Migration

### 8.1 Zero impact when flag is off

`FIXED_ASSETS_ENABLED` defaults to `false` in `.env.local.example` (established by FXA-002). With it off, no DynamoDB reads or writes ever reach the `fixed_assets` or `fixed_asset_schedule` tables from this code path. The existing catalog/cart/orders/billing/inventory/returns paths are entirely unaffected — they never import from `app/routers/fixed_assets` or `app/services/fixed_assets`.

### 8.2 No schema migration required

The three DynamoDB tables (`fixed_assets`, `fixed_asset_schedule`, `maintenance_orders`) are created by `scripts/local-ddb-init.py` (FXA-003) on every `just restart`. In production they must be created via an `aws dynamodb create-table` call (or Terraform/CDK) before the flag is enabled. No existing table is altered.

### 8.3 Forward compatibility with FXA-008 through FXA-013

- FXA-008 will add `gl_asset_account_id`, `gl_accum_depr_account_id`, `gl_depr_expense_account_id` default values to `create_asset`. The router's `POST /ui/fixed-assets` already accepts these fields in `FixedAssetIn` as optional (FXA-004) — when FXA-008 lands, the router does not change; the service back-fills defaults automatically.
- FXA-009 will add `post_depreciation_period(asset_id, period)` to the service. No new router endpoint is needed for the background poster; it is invoked by a startup loop.

## 10. Open Questions / Assumptions

1. **Assumption: `_require_enabled` raises 503, not 404.** The inventory service raises 404 at `app/services/inventory.py:54–56`; the ticket acceptance criteria say "All endpoints return 503 when `FIXED_ASSETS_ENABLED=false`". This spec uses 503. If the codebase convention is uniformly 404 for disabled features, the service-layer guard should be changed before FXA-007 lands.

2. **Assumption: Admin GET list returns all owners by default.** When no `owner_sub` query param is supplied to `GET /ui/fixed-assets`, the router passes `owner_sub=None` to the service. The service queries `GSI_STATUS` (or scans, depending on FXA-005 implementation) to return assets across all owners. Non-admin users are rejected by `require_admin_or_root_csrf` before reaching the service, so this does not expose cross-user data. FXA-005 must document whether it supports `owner_sub=None` for admin queries.

3. **Assumption: `GET /{asset_id}` uses `require_ui_session` (not `require_admin_or_root_csrf`).** The ticket description says the router uses `require_admin_session`-gated CRUD but the `GET /{asset_id}/schedule` read-only endpoint seems more naturally accessible to any authenticated user. The spec above uses `require_ui_session` for both GET endpoints; if only admins should be able to read asset details, change these to `require_admin_or_root_csrf`.

4. **Assumption: `generate_schedule` is called on every `GET /{asset_id}/schedule` request.** If `generate_schedule` is expensive (many DDB writes for a long-lived asset), the route could check whether rows already exist and only generate if the table is empty for that asset. FXA-006 makes re-generation idempotent (re-computes scheduled rows, never touches posted rows), so calling it repeatedly is safe but potentially redundant. A caching optimization is deferred.

5. **Assumption: Disposal of active assets with un-posted schedule periods does not block.** The spec allows disposal regardless of schedule state. FXA-011 (disposal GL journal) will add the proper double-entry for the gain/loss. Until then, `dispose_asset` marks the asset disposed without any GL posting. If the business rule is "asset must be fully depreciated before disposal", the service should enforce this; the router would then surface a 409 from the service. This question is left for FXA-011's review.

6. **Assumption: The `order` query param on `GET /{asset_id}/schedule` is not required for acceptance criteria.** The ticket says "returns the generated periods newest-or-oldest-first per spec" — this spec defaults to oldest-first (ascending by `period`). A `?order=desc` query param can be added without breaking existing callers. If the acceptance test explicitly requires descending, add `order: str = Query(default="asc", pattern="^(asc|desc)$")` and sort `periods` accordingly before returning.

7. **Open: Create endpoint — 201 or 200 on idempotent replay?** The spec returns 201 for both new create and idempotent replay. Returning 200 on replay is equally valid and more semantically precise. The decision should be consistent with `app/services/commerce_order_service.py` — check whether that service distinguishes between new and replay in its HTTP status.
