# SHP-010 — Shipment lifecycle state machine

## 1. Summary & Goal

SHP-010 adds the lifecycle state machine to `app/services/shipments.py` (created by SHP-008,
extended by SHP-009). The machine governs the canonical transition sequence:

```
pending_fulfillment → packed → label_created → shipped → in_transit → out_for_delivery → delivered
```

with two reachable side-states that model failures or reversals:

- **`exception`** — reachable from `shipped`, `in_transit`, or `out_for_delivery`; from
  `exception` the shipment may recover to `in_transit` or be closed to `returned`.
- **`returned`** — terminal; reachable from `exception`.
- **`cancelled`** — terminal; reachable from `pending_fulfillment`, `packed`, or `label_created`
  (not from `shipped` or later — the carrier already has the package).

All illegal transitions (any source→target pair not in the allowed map) return **HTTP 409** and
leave the DynamoDB row and version field unchanged. Concurrent calls for the same shipment are
serialized by a version-guarded conditional update that mirrors the pattern at
`app/services/purchase_history.py:420–430`.

On the **`→ shipped`** transition the caller must supply a tracking number. If only the
tracking number is given without an explicit carrier, the carrier is auto-detected via
`app/services/carrier_tracking.detect_carrier` (`:46`). The tracking URL is computed on the
fly using `build_tracking_url` (`:33`) and returned in the response but **never stored** —
same approach as `purchase_history.get_transaction_info` at `:389–394`.

No new DynamoDB tables, settings keys, or table handles are introduced. Every pre-existing
shop/cart/orders/billing code path is byte-for-byte unchanged when `SHIPPING_ENABLED=false`.

## 2. Context & Current State

### 2.1 `app/services/shipments.py` (SHP-008 + SHP-009 baseline)

SHP-008 creates `app/services/shipments.py` with four functions:

- `create_shipment(order_id, ship_group_seq, carrier_code, method_code, ship_to_address, items, *, correlation_id)` — writes a `shipments` row with initial `status="pending_fulfillment"` and `version=1`, plus `shipment_items` rows and a default `"00001"` package. (`docs/ofbiz/specs/SHP-008.md:189`, `docs/ofbiz/specs/SHP-008.md:169`.)
- `get_shipment(shipment_id)` — `T.shipments.get_item`; 404 if absent.
- `list_shipments_for_order(order_id)` — queries `GSI_ORDER` on `T.shipments`.
- `list_shipments_by_status(status)` — queries `GSI_STATUS` on `T.shipments`.

SHP-009 appends three more functions (`add_package`, `assign_item_to_package`,
`get_packing_status`) and a private `_require_enabled()` guard.

SHP-010 appends the transition functions to the same file — it does not fork it.

### 2.2 Version-guarded conditional update (existing pattern)

`app/services/purchase_history.py:444–464` (`mark_completed`) shows the canonical form that
combines a version guard with `ExpressionAttributeNames={"#st": "status"}` (reserved-word
alias — `app/services/purchase_history.py:451`):

```python
T.purchase_transactions.update_item(
    Key={"user_sub": item["user_sub"], "sk": item["sk"]},
    UpdateExpression="SET #st = :st, updated_at = :u, version = version + :one",
    ConditionExpression="version = :v",
    ExpressionAttributeNames={"#st": "status"},
    ExpressionAttributeValues={":st": target, ":u": updated_at, ":one": 1, ":v": int(item.get("version", 0))},
)
```

Note: `app/services/purchase_history.py:420–430` (`update_shipping`) also uses the version
guard and `ConditionalCheckFailedException` handler (`purchase_history.py:428–429`) but does
**not** include `ExpressionAttributeNames` (it does not update `status`). The `#st` alias
pattern is from `mark_completed:444–464` / `purchase_history.py:451`.

If two callers concurrently fetch the same version and both try to transition, only the first
DynamoDB write succeeds; the second receives `ConditionalCheckFailedException` and is turned
into HTTP 409 (`purchase_history.py:428–429` / `:462–463`: `raise HTTPException(409, "Conflict: transaction was updated by someone else")`).

SHP-008 writes `version=1` on every new `shipments` row (`docs/ofbiz/specs/SHP-008.md:203`),
so the guard is ready from creation time.

### 2.9 Status naming reconciliation (`pending_fulfillment` vs `created`)

The SHP-010 ticket description labels the initial state `"created"` while SHP-008's spec and

written by `create_shipment`. SHP-009 (`docs/ofbiz/specs/SHP-009.md:194`) already treats both
`{"created", "pending_fulfillment"}` as packable states. SHP-010 treats `"pending_fulfillment"`
as the canonical initial-status label (matching what SHP-008 writes), and uses `"packed"`,
`"label_created"`, `"shipped"`, `"in_transit"`, `"out_for_delivery"`, `"delivered"`,
`"exception"`, `"returned"`, and `"cancelled"` for the remainder. (See also Open Question OQ-1.)

## 3. Data Model

### 3.1 No new DynamoDB tables

SHP-010 writes only to `T.shipments` (the `shipments` table defined by SHP-002). No new
`TableDef` entries are added to `scripts/local-ddb-init.py`, no new settings keys to
`app/core/settings.py`, and no new table handles to `app/core/tables.py`.

### 3.2 `shipments` row — fields written or updated by SHP-010

SHP-010 extends the row schema established by SHP-008 (`docs/ofbiz/specs/SHP-008.md:182–210`)
with the following attributes modified on transition:

| Attribute | Type | When written | Notes |
|---|---|---|---|
| `status` (existing) | String | Every transition | Target state (see §3.3) |
| `version` (existing) | Number | Every transition | Incremented atomically: `version = version + 1` |
| `updated_at` (existing) | Number | Every transition | `now_ts()` |
| `tracking_number` | String | `→ shipped` | Required; stored for carrier polling (SHP-012) |
| `carrier` | String | `→ shipped` | Auto-detected or caller-supplied lowercase code |
| `shipped_at` | Number | `→ shipped` | `now_ts()` |
| `delivered_at` | Number | `→ delivered` | `now_ts()` |
| `exception_reason` | String | `→ exception` | Optional caller-supplied free-text |
| `cancelled_at` | Number | `→ cancelled` | `now_ts()` |
| `cancel_reason` | String | `→ cancelled` | Optional caller-supplied free-text |
| `returned_at` | Number | `→ returned` | `now_ts()` |

`tracking_number` is also stored at the top level (not inside a `shipping` sub-map) so that
SHP-012's `find_shipment_by_tracking` GSI lookup can target a scalar attribute — consistent
with how `purchase_history.py:416–418` promotes `tracking_number` to the top level for its
`TrackingIndex` GSI.

### 3.3 Legal transition table

```
LEGAL_TRANSITIONS = {
    "pending_fulfillment": {"packed", "cancelled"},
    "packed":              {"label_created", "cancelled"},
    "label_created":       {"shipped", "cancelled"},
    "shipped":             {"in_transit", "exception"},
    "in_transit":          {"out_for_delivery", "exception"},
    "out_for_delivery":    {"delivered", "exception"},
    "exception":           {"in_transit", "returned"},
    # Terminal states — no outgoing transitions
    "delivered": set(),
    "returned":  set(),
    "cancelled": set(),
}
```

Any `(current_status, requested_target)` pair not in `LEGAL_TRANSITIONS[current_status]`
raises `HTTPException(409, {"code": "illegal_transition", "from": current, "to": target})`.

### 3.4 New Pydantic model: `ShipmentTransitionIn`

Added to `app/models.py` in this ticket, placed in the `# ── Shipping / Logistics` block
after `ShipmentTrackingUpdateIn` (SHP-003 model):

```python
class ShipmentTransitionIn(BaseModel):
    """Generic input for status transitions that need no additional payload

```

All four models are pure additions to `app/models.py` — no existing model is modified.

## 4. API / Service Design

### 4.1 Primary entry point: `transition_shipment`

```python
def transition_shipment(
    shipment_id: str,
    target_status: str,
    *,
    tracking_number: Optional[str] = None,
    carrier: Optional[str] = None,
    exception_reason: Optional[str] = None,
    cancel_reason: Optional[str] = None,
    note: Optional[str] = None,
    actor_user_id: str,
) -> Dict[str, Any]:
```

This is the single write entry point for all status advances. The router (SHP-011) calls this
function with the appropriate keyword arguments extracted from the request body. Having a single
function is preferred over per-state helpers because it concentrates the optimistic-concurrency
logic and ensures the version guard is never accidentally bypassed by a helper that forgets it.

**Steps:**

1. Call `_require_enabled()`.
2. Fetch the current shipment row via `get_shipment(shipment_id)` — 404 if absent.
3. Read `current_status = item["status"]` and `current_version = int(item.get("version", 1))`.
4. Validate the transition: if `target_status not in LEGAL_TRANSITIONS.get(current_status, set())`,
   raise `HTTPException(409, {"code": "illegal_transition", "from": current_status, "to": target_status})`.
5. **`→ packed` gate**: call `get_packing_status(shipment_id)` and check `pack_complete`.
   If `pack_complete is False`, raise
   `HTTPException(409, {"code": "pack_incomplete", "message": "All items must be fully packed"})`.
   (Only checked when `target_status == "packed"`.)
6. **`→ shipped` gate**: `tracking_number` must be non-empty. If absent, raise
   `HTTPException(422, {"code": "tracking_required", "message": "tracking_number is required for shipped transition"})`.
   If `carrier` is `None` or empty, call `detect_carrier(tracking_number)` — if the return is
   also `None`, raise
   `HTTPException(422, {"code": "carrier_required", "message": "carrier could not be auto-detected; supply carrier explicitly"})`.
   (Only checked when `target_status == "shipped"`.)
7. Build `UpdateExpression` and `ExpressionAttributeValues` for the target state (see §4.2).
8. Execute `T.shipments.update_item(Key={"shipment_id": shipment_id}, ConditionExpression="version = :v", ...)`.
9. On `ConditionalCheckFailedException`, raise `HTTPException(409, {"code": "version_conflict", "message": "Concurrent update: retry"})`.
10. Emit `audit_event("shipment." + target_status, actor_user_id, None, shipment_id=shipment_id, from_status=current_status, **extra_audit_fields)`.
11. Return `get_shipment(shipment_id)` — the freshly fetched row with `tracking_url` injected (see §4.3).

### 4.2 `UpdateExpression` per target

The base expression is the same for all transitions:

```python
"SET #st = :st, updated_at = :u, version = version + :one"
```

with `ExpressionAttributeNames={"#st": "status"}` (reserved word guard, mirroring
`purchase_history.py:452`) and base values `":st": target_status, ":u": now_ts(), ":one": 1,
":v": current_version`.

Per-target additions:

| Target | Additional SET clauses | Additional values |
|---|---|---|
| `shipped` | `tracking_number = :tn, carrier = :c, shipped_at = :sa` | `":tn"`, `":c"`, `":sa": now_ts()` |
| `delivered` | `delivered_at = :da` | `":da": now_ts()` |
| `exception` | `exception_reason = :er` | `":er": exception_reason or ""` |
| `cancelled` | `cancelled_at = :ca, cancel_reason = :cr` | `":ca": now_ts()`, `":cr": cancel_reason or ""` |
| `returned` | `returned_at = :ra` | `":ra": now_ts()` |
| All others | *(none)* | |

### 4.3 `get_shipment` tracking URL projection

`get_shipment(shipment_id)` already exists in `shipments.py` (SHP-008). SHP-010 modifies
its return projection to inject `tracking_url` when both `carrier` and `tracking_number`
are present on the stored row — mirroring `purchase_history.get_transaction_info:389–394`:

```python
def _shipment_out(item: Dict[str, Any]) -> Dict[str, Any]:
    out = dict(item)
    carrier = out.get("carrier")
    tracking_number = out.get("tracking_number")
    if carrier and tracking_number:
        out["tracking_url"] = build_tracking_url(carrier, tracking_number)
    else:
        out["tracking_url"] = None
    return out
```

`tracking_url` is **not** persisted — it is computed on every read. The DynamoDB row never
stores it.

The router (SHP-011) can call `transition_shipment` directly. Thin wrappers are optional but
clarify intent:

```python
    return transition_shipment(shipment_id, "in_transit", actor_user_id=actor_user_id)

    return transition_shipment(shipment_id, "delivered", actor_user_id=actor_user_id)

def mark_exception(shipment_id: str, *, exception_reason: Optional[str] = None,
                   actor_user_id: str) -> Dict[str, Any]:
    return transition_shipment(shipment_id, "exception", exception_reason=exception_reason,
                               actor_user_id=actor_user_id)

def cancel_shipment(shipment_id: str, *, cancel_reason: Optional[str] = None,
                    actor_user_id: str) -> Dict[str, Any]:
    return transition_shipment(shipment_id, "cancelled", cancel_reason=cancel_reason,
                               actor_user_id=actor_user_id)
```

These are declared **after** `transition_shipment` in `shipments.py` and each is a single
`return` call — no additional DynamoDB logic.

## 5. Detailed Behavior & Edge Cases

### 5.1 Illegal transition: 409 with unchanged row

When the requested `(current_status, target_status)` is not in `LEGAL_TRANSITIONS`, the
function raises HTTP 409 **before** any DynamoDB call. The row is never touched, the
version is not incremented, and the shipment remains in its current state. The response body
is `{"code": "illegal_transition", "from": "<current>", "to": "<target>"}`.

Example: `delivered → cancelled` is illegal. A second `cancel` call after a carrier delivers
the package is rejected without side effects.

### 5.2 Concurrent transitions — version race

Two admin processes (e.g. a webhook delivery and a manual admin action) may fetch the
same shipment row (version=3) and both try to advance it to `in_transit`. The DynamoDB
conditional update `ConditionExpression="version = :v"` serializes them: the first
write succeeds (row → version=4); the second receives `ConditionalCheckFailedException`
which is caught and turned into HTTP 409
`{"code": "version_conflict", "message": "Concurrent update: retry"}`.
The caller should re-fetch and retry if the transition is still legal (this is the same
advice as `purchase_history.py:429`).

### 5.3 `→ packed` pack-complete gate

`get_packing_status(shipment_id)` (SHP-009) is called synchronously inside
`transition_shipment` before the DDB write. If `pack_complete is False`, the 409 is raised
before touching the version field. The gate is enforced even if the caller bypasses the
router (direct service-layer call). The gate is **skipped** for any other target state.

### 5.4 `→ shipped`: tracking_number required, carrier auto-detect

Three sub-cases:

1. **Both `tracking_number` and `carrier` supplied**: stored as-is (carrier is not re-validated
   against `CARRIER_TRACKING_URLS` — operators may use `"manual"` for carriers without online
   tracking, consistent with SHP-004's `manual` carrier).
2. **`tracking_number` supplied, `carrier` absent or empty**: `detect_carrier(tracking_number)`
   is called. If the return is a recognized code (`"ups"`, `"fedex"`, `"usps"`, `"dhl"`), it is
   used. If the return is `None` (unrecognized format), HTTP 422 is raised with
   `{"code": "carrier_required"}`.
3. **`tracking_number` absent**: HTTP 422 immediately; `detect_carrier` is not called.

The `carrier` value stored on the row is the auto-detected or caller-supplied value. Because
`build_tracking_url` silently returns `None` for unknown carriers (`:38–43`), a `"manual"`
carrier yields `tracking_url=None` in the response — this is correct and expected.

### 5.5 `→ shipped` when re-applied with a corrected tracking number

Because the version guard serializes writes, calling `→ shipped` on a shipment that is
already `"shipped"` is an **illegal transition** (`"shipped" → "shipped"` is not in
`LEGAL_TRANSITIONS`), so it returns 409. There is no "update tracking number in place"
path in SHP-010. If a tracking number is entered incorrectly, the admin must use the
`update_tracking` helper introduced in SHP-012 (separate ticket), which patches the
tracking-related fields without advancing state.

### 5.6 Terminal states

`"delivered"`, `"returned"`, and `"cancelled"` have empty outgoing transition sets.
Any attempt to transition away from them returns 409 `"illegal_transition"`. This is
enforced by `LEGAL_TRANSITIONS[current]["delivered"] == set()` etc.

### 5.7 `→ exception` recovery paths

From `exception`, two transitions are legal:
- `exception → in_transit` — carrier has resumed normal movement.
- `exception → returned` — carrier cannot deliver; package is returning.

Both go through the standard `transition_shipment` path. The `exception_reason` field is
not cleared when recovering to `in_transit` — it is retained as a historical record of
what went wrong. If a shipment has multiple exceptions (e.g. `in_transit → exception → in_transit
→ exception`), the `exception_reason` is overwritten with the latest value. If the audit trail
of all exceptions is needed, it is available via SHP-011's timeline endpoint (out of scope for
SHP-010).

### 5.8 `→ cancelled` restrictions

Cancellation is blocked from `"shipped"` and later because the carrier already has possession.
An operator who needs to recall a shipment after handover must go through the returns path
(SHP-009 note: returns are `exception → returned`, not `cancelled`). The `"cancelled"` state
is for pre-carrier-handover administrative cancellations only.

### 5.9 `get_shipment` output shape after SHP-010

The `_shipment_out(item)` projection is applied by `get_shipment` and by
`transition_shipment`'s final re-fetch. Fields added by SHP-010 that may be present on the
returned dict:

```
tracking_number, carrier, tracking_url (computed),
shipped_at, delivered_at, exception_reason,
cancelled_at, cancel_reason, returned_at
```

All are `Optional` — absent (key missing from DDB item) until the corresponding transition runs.
`tracking_url` is always present in the output but may be `None`.

### 5.10 DynamoDB reserved word: `status`

`status` is a DynamoDB reserved word. All `UpdateExpression` clauses for `status` use
`ExpressionAttributeNames={"#st": "status"}` and reference `#st` in the expression — same
as `purchase_history.py:451–452`. Forgetting this causes `ValidationException` at runtime.

### 5.11 Float→Decimal coercion

The `T.shipments` table handle is a `_FloatSafeTable` proxy (like all handles in
`app/core/tables.py`) that coerces Python `float` to `Decimal` before writing. Timestamps
written by SHP-010 are `int` (from `now_ts()`) — no coercion needed. The version increment
expression `version = version + :one` with `":one": 1` is DynamoDB server-side arithmetic
(no Python float).

## 6. Feature Flag & Config

### 6.1 Flag table

| Setting key | Env var | Default | Effect when off |
|---|---|---|---|
| `S.shipping_enabled` | `SHIPPING_ENABLED` | `false` | All `transition_shipment` calls raise 503 `{"code": "feature_disabled"}` |

SHP-010 introduces **no new settings keys**. The master `S.shipping_enabled` flag is
sufficient — the state machine is inseparable from the shipment lifecycle; there is no
meaningful sub-feature that should be independently flaggable.

### 6.2 No sub-flags

All transition helpers delegate to `transition_shipment`, which calls `_require_enabled()`
as its first line. A `False` flag makes every transition inert without touching the DDB row.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No `dev_mode` branches

`transition_shipment` and its helpers contain zero `if S.dev_mode` conditionals. The version
guard conditional DDB update is identical in dev (DynamoDB Local, port 8001) and prod (real
DynamoDB). `detect_carrier` and `build_tracking_url` are pure functions with no network calls
— same behaviour everywhere.

### 7.2 Idempotency

Transitions are **not** idempotent by design — advancing `packed → label_created` twice would
be rejected on the second call with HTTP 409 `"illegal_transition"` (because the current state
is already `"label_created"`, and `"label_created" → "label_created"` is not in the transition
map). There is no semantic idempotency key for transitions; the version guard plus the
LEGAL_TRANSITIONS check provide exactly-once semantics.

The exception: the caller may encounter a version conflict (concurrent write) and retry. If the
retry re-fetches the row and finds the state already advanced to the desired target (because the
concurrent write succeeded), the retry raises 409 `"illegal_transition"` — the caller should
treat this as a success indicator and not an error.

### 7.3 Billing ledger

No calls to `billing_shared.new_ledger_entry`. Shipment transitions do not move money. Shipping
cost reconciliation (billed weight vs estimated) and cancellation refunds are handled by the
existing `app/services/returns_rma.py` and `app/routers/billing.refund_payment` path — SHP-010
does not touch billing.

### 7.4 Security: admin-only transitions

Shipment status transitions require `require_admin_or_root` (`app/auth/policy.py:67`), enforced
in the SHP-011 router. There is no `require_admin_session` function in this codebase — the
correct import is `from app.auth.policy import require_admin_or_root`. The service layer
(`transition_shipment`) receives `actor_user_id` from the router and includes it in the audit
event but does not re-check the caller's role. This is the standard pattern (see
`app/services/tickets.py` etc.) — the service trusts the router's auth gate.

### 7.5 No PII in audit events or DynamoDB attributes written by SHP-010

The attributes written by SHP-010 (`tracking_number`, `carrier`, `exception_reason`,
`cancel_reason`) do not contain PII. `ship_to_address` is stored on the `shipments` row by
SHP-008 but is not written or emitted by SHP-010.

### 7.6 Tracking number as sensitive data

A tracking number is not PII but may be commercially sensitive (it reveals shipment timing
and destination to the carrier). It is stored in DynamoDB at rest (encrypted at rest via
AWS-managed DynamoDB encryption in prod). It is logged in the audit event only at the `INFO`
level. It is never emitted in HTTP response bodies to unauthenticated callers (all read
endpoints in SHP-011 require `require_ui_session`).

## 10. Open Questions / Assumptions

**OQ-1 (Initial status: `"pending_fulfillment"` vs `"created"`)**: The SHP-010 ticket
description names the start of the chain as `"created"`, but SHP-008's spec
(`docs/ofbiz/specs/SHP-008.md:189`) and its test plan (`:885`) use
`"pending_fulfillment"` as the value written by `create_shipment`. SHP-009 already accepts
both `{"created", "pending_fulfillment"}` as packable states (`docs/ofbiz/specs/SHP-009.md:194`).
**Assumption**: SHP-010 treats `"pending_fulfillment"` as canonical and lists it in
`LEGAL_TRANSITIONS` as the initial state. If `create_shipment` is later changed to write
`"created"`, only SHP-008 needs updating — SHP-010's `LEGAL_TRANSITIONS` dict would be
updated to replace the key accordingly. **Verify with SHP-008 implementor before merging.**

**OQ-2 (Pack gate behaviour for zero-item shipments)**: If a shipment has no `shipment_items`
rows (empty shipment), `get_packing_status` returns `pack_complete=True` (vacuously: all
0 items have remaining=0). **Assumption**: A zero-item shipment is allowed to advance to
`packed`. If zero-item shipments should be blocked, an additional `items` length check
(`len(items) > 0`) should be added to the `→ packed` gate. Confirm with product.

**OQ-3 (`"shipped"` in `ACTIVE_TRACKING_STATUSES`)**: `carrier_tracking.py:129–135` defines
`ACTIVE_TRACKING_STATUSES = {"shipped", "label_created", "picked_up", "in_transit", "out_for_delivery"}`.
SHP-012 will use this set to filter shipments worth polling. SHP-010 stores `status="shipped"`
on the `shipments` row, not `"label_created"`. The `ACTIVE_TRACKING_STATUSES` set includes
both, so a shipment in state `"shipped"` in the state machine will be picked up by the poller.
**No conflict**, but confirm SHP-012 reads `status` from `T.shipments` (not a separate
`tracking_status` field) so the two layers share a single source of truth.

**OQ-4 (Return path through `returns_rma`)**: `"returned"` is a terminal state reached from
`"exception"`. A returned shipment may trigger a refund via `returns_rma.py`. The linkage
(emitting a webhook, creating a return-RMA row) is **out of scope for SHP-010** — SHP-010
only updates the `shipments` row. If refund automation is required on `→ returned`, a future
ticket should hook into the `"shipment.returned"` audit event emitted here.

**OQ-5 (Tracking URL in `ShipmentOut` Pydantic model)**: SHP-003 defines `ShipmentOut`
with a `tracking_url: Optional[str]` field (`docs/ofbiz/specs/SHP-003.md`). This spec
assumes that field already exists. If it was omitted by SHP-003, it must be added there
(additive, backward-compatible). **Confirm with SHP-003 implementor.**

**OQ-6 (DynamoDB reserved word `status` in `GSI_STATUS`)**: The `GSI_STATUS` index uses
`status` as its partition key. DynamoDB partition key comparisons in `KeyConditionExpression`
do not require `ExpressionAttributeNames` — only projection/update expressions need it.
`KeyConditionExpression="status = :s"` raises `ValidationException` because `status` is
reserved. The query must use `ExpressionAttributeNames={"#st": "status"}` and
`KeyConditionExpression="#st = :s"`. SHP-008's `list_shipments_by_status` must use this
form. **Confirm SHP-008's implementation avoids the runtime error** (SHP-010 itself does not
call `list_shipments_by_status` but the `GSI_STATUS` definition is shared).
