# OFB-003 — Inventory item & stock-level model

**Type:** Feature | **Priority:** P0 | **Estimate:** 4 days
**Depends on:** OFB-002 (scaffolding already landed)
**Downstream:** OFB-004 (soft reservations), OFB-005 (low-stock alerts)

---

## 1. Summary & Goal

OFB-003 introduces a **first-class inventory record** that supersedes the ad-hoc `stock_count` scalar on catalog items. The inventory record is a DynamoDB row keyed `(sku, LOC#{location_id})` that tracks `on_hand`, `reserved`, `available = on_hand − reserved`, and `reorder_point`.

Three service-level entry points are provided:

- `get_inventory(sku)` — read the current record (or a zeroed virtual record if absent)
- `set_on_hand(sku, qty, reason)` — absolute set (admin stock receipt / cycle-count)
- `adjust(sku, delta, reason)` — atomic signed delta (positive = restock, negative = shrinkage/correction)

Every mutation emits an `alerts.audit_event` with before/after quantities. The catalog item's `stock_count` scalar remains as a **denormalized mirror** so the existing storefront UI (`_catalog_item_out`, `_compute_stock_status`) keeps working without change.

The entire feature is dormant until `INVENTORY_RESERVATIONS_ENABLED=true`. With the flag off, the `inventory` DynamoDB table may exist (it is created by OFB-002 scaffolding) but no catalog write path touches it, and all `/ui/inventory/*` endpoints return 404.

## 2. Context & Current State

### 2.1 The existing stock_count scalar

The only stock concept today is a nullable integer `stock_count` stored inline on each catalog item in the `shopping_catalog` table. It is written during item create (`app/routers/catalog.py:377–379`) and update (`app/routers/catalog.py:556–562`), and decremented at purchase time in `shoppingcart.purchase_cart` (`app/services/shoppingcart.py:517`).

The derived display label is computed by `_compute_stock_status` (`app/routers/catalog.py:94–104`): `None` → `"unlimited"`, `<=0` → `"out_of_stock"`, `<= low_stock_threshold` → `"low_stock"`, else `"in_stock"`. The threshold defaults to `S.catalog_default_low_stock_threshold` (`app/core/settings.py:833`, default `5`).

`CatalogItemOut` (`app/models.py:672`) exposes `stock_count: Optional[int]`, `stock_status: str`, `low_stock_threshold: int`, and `stock_updated_at: Optional[str]`. `CatalogItemCreateIn` (`app/models.py:538`) and `CatalogItemPatchIn` (`app/models.py:550`) accept `stock_count: Optional[int]` with `ge=0, le=10_000_000`.

There is **no `reserved` quantity**, no `available = on_hand − reserved` formula, no location dimension, and no audit trail for stock changes.

### 2.2 Cart purchase — decrement-at-purchase

`purchase_cart` (`app/services/shoppingcart.py:474`, stock-decrement block `498–538`) performs a decrement-at-purchase strategy: for each cart line item it issues a conditional `update_item` with `ConditionExpression "stock_count >= :qty"` and rolls back previously decremented lines on a `ConditionalCheckFailedException`. There are no soft reservations — stock is consumed at the exact moment `purchase_cart` executes. OFB-004 will replace this path; OFB-003 does not touch shoppingcart.py.

### 2.3 OFB-002 scaffolding already present

OFB-002 has already landed all prerequisites:

- `inventory` table defined in `scripts/local-ddb-init.py:2456–2464`, with `attr_types={"available": "N"}` for the `GSI_AVAILABLE` numeric sort key.
- `reservations` table defined in `scripts/local-ddb-init.py:2469–2478`, with `attr_types={"created_at": "N", "expires_at": "N"}`.
- `T.inventory` and `T.reservations` handles in `app/core/tables.py:317–318`, wired via `_safe_table(S.inventory_table_name)` and `_safe_table(S.reservations_table_name)` at lines 569–570.
- Feature flag `S.inventory_reservations_enabled` (`app/core/settings.py:839`, default `false`).
- Table name settings `S.inventory_table_name` and `S.reservations_table_name` (`app/core/settings.py:841–842`).

### 2.4 Inventory service and router already authored

Both `app/services/inventory.py` and `app/routers/inventory.py` exist and contain the full OFB-003 (and OFB-004) implementation. The router is already registered at `app/main.py:877`. This spec documents what was built so that reviewers, OFB-004, and OFB-005 authors have a single canonical reference; the implementation notes below describe the code as it stands.

### 2.5 The missing link: catalog → inventory provisioning

What does NOT yet exist (and is the primary deliverable of OFB-003 beyond the service itself) is the **bridge from catalog create/update to the inventory service**. When a catalog item is created or updated with a `stock_count` value, the inventory record for `sku = item_id` at `location_id = "warehouse"` must be upserted to match. This hook is absent from `app/routers/catalog.py` and must be added there, gated by `_flag_on()`.

### 2.6 Audit event pattern

`alerts.audit_event(event, user_sub, request=None, **fields)` (`app/services/alerts.py:644`) writes to `T.alerts`. `commerce_order_service` uses this directly (`app/services/commerce_order_service.py:106–117`). The inventory service wraps it in a fire-and-forget `_audit(event, user_sub, **fields)` helper (`app/services/inventory.py:92–98`) using a local import inside a `try/except`, so an alert table misconfiguration cannot break a stock mutation.

`shopping_catalog` (PK `PK` S, SK `SK` S) carries `stock_count`, `stock_updated_at`, and `low_stock_threshold` inline on item rows (`PK = CAT#{category_id}`, `SK = ITEM#{item_id}`). ### 4.4 Missing piece: catalog → inventory provisioning hook

**This is the primary code gap that OFB-003 must close.** When the flag is on and a catalog item create or update includes a `stock_count` value, the catalog router must call `inventory.set_on_hand(sku=item_id, qty=stock_count, ...)` so the inventory table stays in sync.

Add a helper to `app/services/inventory.py`:

```python
def provision_from_catalog(
    item_id: str,
    stock_count: int,
    *,
    low_stock_threshold: Optional[int] = None,
    user_sub: str = "system",
) -> None:
    """Upsert the inventory record for a catalog item from a stock_count write.

    Called by the catalog router after a successful put_item/update_item when
    INVENTORY_RESERVATIONS_ENABLED is on. Best-effort: any exception is
    swallowed so the catalog write is never rolled back on inventory failure.

    Sets on_hand=stock_count (preserving any existing reserved count);
    updates reorder_point to low_stock_threshold when provided.
    """
    if not _flag_on():
        return
    try:
        set_on_hand(
            item_id,
            stock_count,
            reason="catalog_provision",
            location_id=DEFAULT_LOCATION,
            reorder_point=low_stock_threshold,
            user_sub=user_sub,
        )
    except Exception:
        pass
```

Add calls in `app/routers/catalog.py`:

1. In `create_item`, after the successful `T.catalog.put_item` call and only when `body.stock_count is not None`:
   ```python
   from app.services import inventory as _inv_svc
   _inv_svc.provision_from_catalog(
       item_id, body.stock_count,
       low_stock_threshold=body.low_stock_threshold,
       user_sub=ctx["user_sub"],
   )
   ```

2. In `update_item` (`PATCH /categories/{category_id}/items/{item_id}`), after the successful `T.catalog.update_item` call and only when `body.stock_count is not None`:
   ```python
   _inv_svc.provision_from_catalog(
       item_id, body.stock_count,
       low_stock_threshold=body.low_stock_threshold,
       user_sub=ctx["user_sub"],
   )
   ```

The import is inside the function body (local import) to prevent a circular import at module load time, matching the pattern already used in `inventory._audit` (`app/services/inventory.py:94`).

The catalog `stock_count` scalar must continue to be written on the catalog row (no change to existing lines 377–379 or 556–562 in catalog.py). `provision_from_catalog` runs *in addition*, never *instead of*, the catalog write.

### 4.5 Return value from _catalog_item_out with flag on

When `INVENTORY_RESERVATIONS_ENABLED=true`, the storefront may want to surface `available` (the reservation-adjusted count) rather than the raw `stock_count`. The ticket AC says "available reflects on-hand minus reservations" but does NOT require changing the `CatalogItemOut` shape (which is consumed by the existing shop UI).

Two options:

A. Keep `CatalogItemOut.stock_count` pointing at the raw catalog scalar (backward compat); add a parallel `GET /ui/inventory/items/{sku}` call in the frontend when the flag is on.
B. In `_catalog_item_out`, when the flag is on, substitute `stock_count` with `inv.get_inventory(item_id)["available"]` if the record exists.

**Chosen: Option A.** The storefront continues to use the catalog `stock_count` as a fast denormalized read (no extra DDB hop on every listing call). The `GET /ui/inventory/items/{sku}` endpoint is available for admin dashboards and the checkout flow (OFB-004) to get the authoritative `available` count.

## 5. Detailed Behavior & Edge Cases

### 5.1 available invariant

`available` is always `on_hand − reserved`, recomputed and persisted on every mutation (`app/services/inventory.py:131`). The `GSI_AVAILABLE` index key `available` is always current. This means:

- `available` can never be negative as long as reservations are enforced with `ConditionExpression "available >= :q"` (OFB-004 `reserve` path).
- A `set_on_hand(qty)` where `qty < existing.reserved` would produce `available < 0`. The service **does not reject this** — it is valid for a physical inventory count to reveal that stock has gone below reserved (shrinkage, damage, theft). The resulting `available = negative` puts the record in `status = "out_of_stock"` and prevents further reservations. Administrators must reconcile.

### 5.2 adjust: create-on-positive, block-on-negative-nonexistent

`adjust` (`app/services/inventory.py:225–250`) handles two cases:

- Record absent + delta > 0: issues a conditional `put_item` with `attribute_not_exists(sku)`. On a lost race (another writer created the record concurrently), it retries recursively (single retry, then falls through to the increment path).
- Record absent + delta < 0: raises HTTP 409 "Cannot decrement nonexistent inventory". No side effects.

### 5.3 adjust: guard against dropping on_hand below reserved

Before issuing the `update_item`, `adjust` computes `new_available = (before + delta) - reserved`. If `new_available < 0` it raises HTTP 409 "Adjustment would drop on-hand below reserved quantity". This prevents stock from going below committed reservations due to manual corrections.

### 5.4 adjust: optimistic concurrency retry

The conditional `update_item` pins `on_hand = :exp_oh AND reserved = :exp_res`. A concurrent mutation (another process adjusting the same SKU) causes a `ConditionalCheckFailedException`. The service retries once with fresh values from a re-read. Two concurrent retries will not livelock because the second attempt reads the post-first-attempt state; the retry depth is bounded at one recursion level.

### 5.5 set_on_hand: preserves reservations

`set_on_hand` reads the current `reserved` count from the existing row (defaulting to 0 if the row is absent) and calls `_persist` with `on_hand=qty, reserved=existing_reserved`. The `reserved` field is **not reset** by an absolute set. This is intentional: a cycle-count that sets `on_hand=5` while 3 units are reserved results in `available=2`, which correctly reflects the actual available capacity.

### 5.6 status derivation

`_status_for(available, reorder_point)` (`app/services/inventory.py:84–89`):

- `available <= 0` → `"out_of_stock"`
- `0 < available <= reorder_point` → `"low_stock"`
- `available > reorder_point` → `"in_stock"`

The `reorder_point=0` edge case: `available=0` → `"out_of_stock"` (correct); `available=1, reorder_point=0` → `"in_stock"` (correct — threshold of 0 means no low-stock warning).

### 5.7 catalog mirror: stock_count lag

When an order is committed (OFB-004 `commit_reservation`), `on_hand` decrements in the inventory table but the catalog item's `stock_count` is NOT automatically decremented. This is by design for OFB-003 scope: the catalog `stock_count` remains the pre-reservation snapshot. OFB-004 or a follow-up must add a write-through on `commit_reservation` to update `T.catalog` (same pattern as the existing `shoppingcart` decrement). Until that hook exists, the catalog scalar may overstate actual available stock.

### 5.8 provision_from_catalog: best-effort, never blocks catalog write

`provision_from_catalog` swallows all exceptions. If the inventory table is missing (flag just enabled but `just restart` not yet run), the catalog write still succeeds. This prevents a misconfigured inventory backend from taking down the store.

### 5.9 location_id: single "warehouse" now

The schema is forward-compatible (location is a dimension on the key), but no multi-location routing is implemented. All catalog-provisioned records land in `location_id = "warehouse"`. Multi-location is deferred per OFB-001 scope decision.

### 5.10 SKU as item_id

The inventory service is generic: `sku` is an opaque string. When provisioned from catalog, `sku = item_id` (the catalog item's `item_id` field, e.g. a ULID). This means the inventory record for a catalog item can also be queried directly via `GET /ui/inventory/items/{item_id}`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

`app/services/inventory.py` contains no `if S.dev_mode` branch in business logic. All DDB calls use `T.inventory` / `T.reservations`, which resolve to moto (local dev) or real DynamoDB (prod) based on the endpoint configuration in `T`'s initialization (`app/core/tables.py:569–570`). The distinction is entirely at the boto3 endpoint level, invisible to the service code.

### 7.2 Idempotency

- **set_on_hand**: uses `_persist` which issues a full `put_item` (replace). Repeating the call with the same `qty` produces the same row. Idempotent.
- **adjust**: conditional `update_item` with optimistic lock. Not trivially idempotent (applying the same delta twice would double-apply). Callers (OFB-004 `commit_reservation`) must hold their own idempotency key before calling `adjust` directly. The `provision_from_catalog` hook calls `set_on_hand` (not `adjust`), so repeated catalog updates with the same `stock_count` are idempotent.
- **reserve / commit / release**: the reservation row's terminal status is guarded by `ConditionExpression "#status = :active"` in `_close_reservation` (`inventory.py:434–453`). A second `commit_reservation` or `release_reservation` call on an already-terminal reservation returns the existing record without modifying the inventory counters — idempotent under replay.

### 7.3 Security

- Admin mutations (`set_on_hand`, `adjust`, `list_low_stock`) require `require_admin_or_root_csrf`, which enforces both RBAC (role >= ADMIN) and CSRF token validation for cookie-auth requests (`app/auth/policy.py:100–106`). Bearer-auth requests from server-to-server paths skip CSRF per `enforce_cookie_csrf` implementation.
- Customer reads (`GET /items/{sku}`) and reservation operations require `require_ui_session` only. Reservation ownership is enforced at the application layer: `get_reservation` and `release_reservation` check that `res["user_sub"] == session["user_sub"]` (`app/routers/inventory.py:112–113`, `122–124`). A user cannot release another user's reservation.
- The `sku` value in `InventorySetOnHandIn` / `InventoryAdjustIn` is constrained to `min_length=1, max_length=256` (`app/models.py:596, 604`). The `location_id` is constrained to `max_length=128`. No injection risk from these fields reaching DDB (they become the partition/sort key value, not a query expression).
- `provision_from_catalog` runs with `user_sub` from `ctx["user_sub"]` (the authenticated catalog editor) so the audit trail correctly attributes the stock change to the human actor, not `"system"`.

## 8. Backward Compatibility & Migration

### 8.1 No breaking changes with flag off

With `INVENTORY_RESERVATIONS_ENABLED=false` (the default):

- `app/services/shoppingcart.py` is unchanged — it continues the decrement-at-purchase path against `T.catalog`.
- `app/routers/catalog.py` is unchanged except for a guarded call to `provision_from_catalog` that is a no-op when the flag is off (`provision_from_catalog` returns immediately on line 1 if `not _flag_on()`).
- `CatalogItemOut` is unchanged.
- The `inventory` and `reservations` tables exist but are not read or written by any live request.

### 8.2 Enabling the flag on an existing deployment

When `INVENTORY_RESERVATIONS_ENABLED` is flipped to `true` on a live deployment that has existing catalog items:

1. **Inventory table is empty**: `get_inventory(sku)` returns `None`; `get_or_zero` returns a zeroed virtual record. No error occurs.
2. **Catalog writes populate inventory going forward**: Only new `create_item` or `update_item` calls with a `stock_count` will upsert inventory records. Existing items do not get records automatically.
3. **Backfill**: A one-time admin job is needed to populate the inventory table from existing `T.catalog` scan data. This job can call `provision_from_catalog` for each item with a `stock_count` value. **This job is out of scope for OFB-003** — it is a follow-on operational task or can be done via the `PUT /ui/inventory/items` admin endpoint.
4. **OFB-004 reservation gate**: If OFB-004 is also enabled, items without an inventory record will fail reservations with 409 "No inventory for SKU". This is the correct behavior — the store should not allow checkout for items that have not been inventory-provisioned.

### 8.3 stock_count mirror drift

After OFB-003 is enabled, the catalog `stock_count` mirrors `on_hand` at the time of the last catalog write. If `commit_reservation` (OFB-004) decrements `on_hand` in inventory without updating the catalog scalar, the storefront will show a stale `stock_count`. The OFB-004 spec must address the write-through on commit to keep the mirror in sync, or the storefront must be updated to read from the inventory endpoint when the flag is on.

## 10. Open Questions / Assumptions

1. **SKU = item_id assumption**: It is assumed that the inventory `sku` for a catalog item is the catalog `item_id`. The ticket says "SKU → on-hand qty" but the catalog model has `item_id`, not a separate SKU attribute. If catalog items ever need a separate SKU string (e.g., variant SKUs within one `item_id`), the `provision_from_catalog` hook must be updated to derive the correct `sku` value. For OFB-003 scope, `sku = item_id`.

2. **Catalog stock_count mirror on commit**: When OFB-004 `commit_reservation` decrements `on_hand`, it does NOT update the catalog `stock_count` scalar. Assumption: OFB-004 will own this write-through (see section 8.3). If the storefront must always see reservation-accurate stock, OFB-004 is a blocking dependency for accurate catalog display.

3. **Negative available permitted**: The spec allows `on_hand < reserved` (shrinkage scenario). This is a conscious choice but could produce confusing UX (storefront shows negative available). An alternative is to cap `available` at 0 in the `InventoryRecordOut` projection. Current implementation does NOT cap — it exposes the real negative. Reviewers should confirm this is acceptable.

4. **Single-location only**: The `location_id = "warehouse"` default is the only location. Multi-location routing is deferred per OFB-001. The `location_id` dimension in all API inputs is validated but ignored for routing — all catalog items go to `"warehouse"`. If multi-location is needed before OFB-003 is stable, a routing strategy must be defined.

5. **Backfill scope**: No automatic backfill of existing catalog items into the inventory table on flag enablement. This is assumed to be an acceptable gap for the initial rollout (items only get inventory records after their next catalog write). If the business requires all existing items to have inventory records immediately, a migration script must be written.

6. **list_low_stock pagination**: `list_low_stock` loops all pages from `GSI_AVAILABLE` (`app/services/inventory.py:319–333`). On a large catalog this could return thousands of records. A cursor-paginated version may be needed for the admin UI. Current implementation is unbounded.

7. **audit_event in T.alerts**: `provision_from_catalog` calls `set_on_hand` which calls `_audit`. This writes to `T.alerts`. On high-volume catalog import jobs, this generates a high rate of audit rows. A batch import path (bypassing audit per-item) may be needed later.
