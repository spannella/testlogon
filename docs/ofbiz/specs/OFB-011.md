# OFB-011 — Returns/RMA admin + customer UI

## 1. Summary & Goal

OFB-011 is the **UI layer** for the Returns/RMA lifecycle introduced in OFBiz Milestone 3. The backend service (`app/services/returns_rma.py`) and all seven API endpoints (`app/routers/returns_rma.py`) were delivered in OFB-008, OFB-009, and OFB-010. This ticket adds the React/TypeScript frontend that makes those endpoints reachable from a browser:

1. **Customer "My Returns" page** — `frontend/src/pages/shop/MyReturnsPage.tsx` — lets a logged-in user list their open and historical returns, file a new return against a purchased order, and track status through the full lifecycle.
2. **Admin RMA queue page** — `frontend/src/pages/shop/admin/RmaAdminPage.tsx` — gives an `ADMIN`/`ROOT` user a filterable queue view with in-line action buttons (approve, reject, receive, refund, close).
3. **TypeScript types** — additive declarations in `frontend/src/api/types.ts` mirroring `ReturnOut` / `ReturnLineOut` / `ReturnRequestIn` / `ReturnDecisionIn` from `app/models.py`.
4. **Endpoint wrappers** — `frontend/src/api/endpoints/returnsRma.ts` following the same `api.get / api.post` pattern used by all other endpoint files.
5. **App.tsx routes and Sidebar nav entries** — both flag-gated behind `isReturnsRmaEnabled()` (customer) and the same flag combined with `canAccessGeneralAdminControls()` (admin).

**Non-goals:** no backend schema change; no new DynamoDB tables; no billing logic; no E2E spec (OFB-012 owns that).

### Gap in the backend for "My Returns" list

There is **no** `list_returns_by_user` function in `app/services/returns_rma.py` and **no** `GSI_USER` on the `returns` table. The existing `GET /ui/returns/{return_id}` endpoint only fetches a single return, and `list_returns_for_order` queries the `GSI_ORDER` index but requires the caller to know the `order_id` upfront. The customer "My Returns" page needs to list all returns for the logged-in user without enumerating orders.

This spec adds a `list_returns_by_user` service function and a new `GET /ui/returns` endpoint backed by a `GSI_USER` index on the `returns` table.

## 3. Data Model

### Existing `returns` table (no schema change for already-built columns)

```
PK  return_id  (S)      — uuid4().hex
SK  sk         (S)      — "META" (header) | "ITEM#{n}" (line n=1,2,…)
```

Header (`sk="META"`) attributes already written by OFB-008: `order_id`, `user_sub`, `status`, `reason`, `currency`, `refund_amount_cents`, `refund_ledger_sk`, `provider`, `decided_by`, `decision_note`, `created_at` (N), `updated_at` (N).

Line (`sk="ITEM#{n}"`) attributes: `line_no` (N), `item_id`, `sku`, `quantity` (N), `amount_cents` (N), `created_at` (N).

### New GSI: `GSI_USER`

To support `GET /ui/returns` (list the calling user's returns), a new GSI is needed on the header rows:

| Index name | Partition key | Sort key    | Projects  |
|------------|--------------|-------------|-----------|
| `GSI_USER` | `user_sub` (S) | `created_at` (N) | ALL |

Only header rows carry `user_sub`; line rows do not. The query filters `sk = "META"` client-side after retrieval (same pattern used for `GSI_ORDER` in `list_returns_for_order` at `app/services/returns_rma.py:295`).

### `scripts/local-ddb-init.py` change

The existing `TableDef` for `returns` (`scripts/local-ddb-init.py:2483–2492`, verified) must gain a third GSI entry:

```python
TableDef(
    _resolve_table_name(S.returns_table_name, "returns"),
    "return_id",
    "sk",
    gsi=[
        {"index_name": "GSI_ORDER",  "partition_key": "order_id",  "sort_key": "created_at"},
        {"index_name": "GSI_STATUS", "partition_key": "status",    "sort_key": "created_at"},
        {"index_name": "GSI_USER",   "partition_key": "user_sub",  "sort_key": "created_at"},  # NEW
    ],
    attr_types={"created_at": "N"},   # N already declared; covers all three GSI sort keys
)
```

`created_at` is already declared `"N"` in `attr_types`, so no additional `attr_types` entry is needed. Running `just restart` (which calls `scripts/local-ddb-init.py`) recreates the table with the new GSI. In production this requires an `UpdateTable` + async backfill before deploying.

## 4. API / Service Design

### 4a. New backend additions (service + router)

#### `app/services/returns_rma.py` — new function

```python
def list_returns_by_user(user_sub: str) -> List[Dict[str, Any]]:
    """List all return headers for a user via GSI_USER (newest-first)."""
    out: List[Dict[str, Any]] = []
    kwargs: Dict[str, Any] = {
        "IndexName": "GSI_USER",
        "KeyConditionExpression": Key("user_sub").eq(user_sub),
        "ScanIndexForward": False,
    }
    while True:
        r = T.returns.query(**kwargs)
        for it in r.get("Items", []):
            if it.get("sk") == "META":
                out.append(_return_header_out(it, []))   # lines omitted for list efficiency
        lek = r.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
    return out
```

Note: lines are omitted from the list view (no `_load_return` call per item). The detail endpoint `GET /ui/returns/{return_id}` already loads lines for full detail.

#### `app/routers/returns_rma.py` — new endpoint

```python
@returns_rma_router.get("", response_model=List[ReturnOut])
async def list_my_returns(session=Depends(require_ui_session)):
    rma._require_enabled()
    items = rma.list_returns_by_user(session["user_sub"])
    return [ReturnOut(**r) for r in items]
```

This is placed **before** the existing `GET /{return_id}` handler (FastAPI matches in declaration order — a literal `""` path does not conflict with `/{return_id}`, but insertion order is the safe convention used throughout this codebase).

## 5. Detailed Behavior & Edge Cases

### Customer "My Returns" page (`MyReturnsPage.tsx`)

**List view:**
- `useQuery(["returns", "mine"], listMyReturns)` — fetches all the user's returns (newest-first, server-side via `GSI_USER`).
- Status filter tabs: `all | requested | approved | rejected | received | refunded | closed` — client-side filter on the cached list (no separate query per status; the list is expected to be small, <100 entries per user).
- Each row shows: return ID (short: last 8 chars), order ID (linked to `/purchases/{orderId}` if that page exists, otherwise plain text), status badge, total refund amount, created date. Clicking a row expands or navigates to a detail view showing the full `ReturnOut` including per-line breakdown.
- `EmptyState` component when no returns exist.

**New return dialog (trigger: "Request a Return" button):**
- Multi-step: (1) enter `order_id`, (2) select which lines + quantities, (3) enter reason text, (4) confirm.
- The dialog does **not** fetch the order's line items from the backend (the backend validates ownership and qty; client builds the `lines` array from user input). An alternative simpler UX is a plain form with `order_id`, `reason`, and a dynamic list of `{ item_id, quantity }` rows — this avoids a cross-origin `GET /ui/purchases` dependency.
- On success: `queryClient.invalidateQueries(["returns", "mine"])` + `toast.success("Return request submitted")`.
- Errors: 404 → "Order not found or does not belong to your account"; 409 → "An open return already exists for this order"; 422 field errors shown inline.

**Status badge colors** (consistent with `StatusBadge` in `components/shared/StatusBadge.tsx`):

| Status     | Variant    |
|------------|------------|
| requested  | warning    |
| approved   | info       |
| received   | info       |
| refunded   | success    |
| closed     | neutral    |
| rejected   | danger     |

### Admin RMA queue page (`RmaAdminPage.tsx`)

**Queue view:**
- Status filter tabs (default: `requested`): `requested | approved | received | refunded | rejected | closed`.
- `useQuery(["returns", "admin", status], () => adminGetRmaQueue(status))` — re-queries on tab change.
- Table columns: `return_id`, `order_id`, `user_sub` (truncated), `reason` (truncated to 60 chars), `refund_amount_cents` (formatted), `created_at` (formatted date), `status` badge, action buttons.
- Action buttons per status (only the legal next transitions are shown):
  - `requested` → "Approve" + "Reject" buttons, each opening a `note` input dialog.
  - `approved`  → "Receive" button (no note required) + "Reject" button with note.
  - `received`  → "Refund" button (no user input; provider defaults to `"stripe"` server-side).
  - `refunded`  → "Close" button.
  - `rejected` / `closed` → no action buttons (terminal states).
- Each action mutation calls the corresponding `adminApproveReturn` etc. wrapper and on success calls `queryClient.invalidateQueries(["returns", "admin"])` + `toast.success`.

**Decision note dialog:**
- `Dialog` (shadcn/ui) with a `Textarea` for the optional note.
- Shared by approve and reject actions; title/CTA label changes based on which action triggered it.

**Refund action confirmation:**
- `ConfirmDialog` (existing shared component, `components/shared/ConfirmDialog.tsx`) with text "Issue refund of {amount} {CURRENCY}? This cannot be undone." — prevents accidental clicks.

**Row-level loading state:**
- While a mutation is pending for row `return_id`, that row's action buttons are disabled and show `Loader2` spinner. Use `useMutation`'s `isPending` flag combined with a local `pendingId` state.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity:** No `dev_mode` branch anywhere in this ticket. The frontend reads the same `VITE_RETURNS_RMA_ENABLED` regardless of environment. The backend `_require_enabled()` guard is environment-agnostic. The new `list_returns_by_user` function queries DynamoDB (moto in dev, real DDB in prod) through the same `T.returns` handle — no mock/real fork.

**Idempotency:** The mutation endpoints (approve, reject, receive, refund, close) are already idempotent at the service layer via the conditional `update_item` `_transition` pattern (`returns_rma.py:319–354`). The frontend guards against accidental double-submission with `isPending` button disabling and, for refund, a `ConfirmDialog`. React Query's `useMutation` does not retry on 4xx, so a replayed 409 (already in target state) is surfaced as a toast error without a second server round-trip.

**Ownership enforcement:** `GET /ui/returns/{return_id}` already checks `rec["user_sub"] != session["user_sub"]` and returns 404 (`app/routers/returns_rma.py:49–51`). The new `GET /ui/returns` uses `GSI_USER` keyed on `session["user_sub"]`, so users never see each other's returns. Admin endpoints are behind `require_admin_or_root_csrf` (`app/auth/policy.py:100`) which enforces both role (`ADMIN` or `ROOT`) and CSRF — the frontend `api.post` calls go through `frontend/src/api/client.ts` which attaches the `x-csrf-token` header from the `ui_csrf` cookie automatically.

**Role-gating:** `RmaAdminPage` performs a client-side role check (`canAccessGeneralAdminControls(accessToken)`) identical to the `InventoryAdmin` guard (`Sidebar.tsx:262–263`). `InventoryAdmin.tsx:91` does the same check inside the component; for `RmaAdminPage` the route itself is conditionally registered (same as `showBroadcastNavigation` routes at `App.tsx:396–398`). Even without this guard the backend rejects non-admin requests with 403, but the client-side check prevents the route from being registered and prevents the nav entry from appearing.

**No money-out logic in UI:** The "Refund" button calls `adminRefundReturn(returnId)` which maps to `POST /ui/returns/admin/{id}/refund`. All refund math, ledger writing (`new_ledger_entry` / `apply_balance_delta` / `settle_or_reverse_ledger`), and provider attribution live entirely in `returns_rma.refund_return` (`app/services/returns_rma.py:444–542`, provider param defaults to `"stripe"` at `:448`), which was designed and tested in OFB-010. The UI does not touch billing or ledger state directly.

## 8. Backward Compatibility & Migration

**Existing shop/cart/catalog/orders/billing code: zero changes.** The only backend changes in this ticket are:
1. A new service function `list_returns_by_user` added to `app/services/returns_rma.py`.
2. A new router handler `GET /ui/returns` added before the existing `GET /ui/returns/{return_id}` in `app/routers/returns_rma.py`.
3. An extra GSI (`GSI_USER`) in the `returns` TableDef in `scripts/local-ddb-init.py`.

Items 1 and 2 only execute when `RETURNS_RMA_ENABLED=true`; with the flag off they are dead code. Item 3 is additive — `just restart` recreates tables from scratch in dev (no migration needed). In production the GSI addition requires an `UpdateTable` call before deploying the new service code, because `list_returns_by_user` queries the index immediately on first call; the backfill is fast (returns table is empty or small at the time OFB-011 ships, since the customer UI to create returns does not yet exist in production).

**Frontend: zero changes to existing components.** All new files are net-new. The `api/types.ts` additions are purely additive. The `featureFlags.ts` addition is additive. The `App.tsx` and `Sidebar.tsx` changes insert conditional entries that are invisible when the flag is off.

## 10. Open Questions / Assumptions

1. **"My Returns" list — include lines in list response?** This spec assumes lines are omitted from the list view for efficiency (no `_load_return` call per item), so the list shows totals only. The detail view (`GET /ui/returns/{return_id}`) provides full line breakdown. _If the product decision is that the list should show per-line detail, the `list_returns_by_user` function needs to call `_load_return` per item (N+1 DDB calls) or batch-load lines in a second pass._

2. **"Request a Return" form — does the customer know their `item_id`?** The spec assumes the form takes free-form `item_id` text inputs because there is no existing `GET /ui/orders/{order_id}/items` endpoint that the frontend could use to present a picker. _Assumption: a future ticket adds an orders API for the frontend; for now, the customer enters the item_id manually (acceptable for a v1 admin-assisted flow)._

3. **Provider selection on refund** — `refund_return` in `returns_rma.py:449` accepts a `provider` parameter that defaults to `"stripe"`. The admin UI sends no provider body; the backend uses `"stripe"` by default. _Assumption: this is correct for v1. A follow-up ticket (post-OFB-012) can add a provider selector if PayPal/CCBill refunds are needed._

4. **GSI_USER — hot partition risk for high-volume users?** A user who places thousands of orders could accumulate hundreds of returns. The list call is paginated (while loop) but an unbounded query. _Assumption: returns volume per user is low enough (typically <20 lifetime) that no pagination cap is needed. Add a `Limit=200` safety cap to the query if the platform sees high-volume sellers._

5. **`RotateCcw` and `PackageX` Lucide icons** — assumed available in `lucide-react` (the icon set already used throughout the frontend). _If either is absent in the installed version, substitute `RefreshCw` / `Package` respectively._

6. **`/purchases/{orderId}` deep-link from "My Returns"** — the spec links the order ID in the customer list to `/purchases/{orderId}`. The `PurchasesPage` component (`frontend/src/pages/purchases/PurchasesPage.tsx:6`) reads `txnId` from params but uses it to show a `TransactionDetail` view, not an order detail view. _Assumption: until a proper order-detail route exists, the order_id is shown as plain text or linked to `/purchases` (list view) rather than `/purchases/{orderId}`._

7. **Admin "note" field on approve/reject** — the router accepts `ReturnDecisionIn | None` (`app/routers/returns_rma.py:72–73`). The UI shows a `Textarea` for the note but does not require it. _Assumption: note is optional; empty string is acceptable; the backend writes `decision_note = note or ""` (`app/services/returns_rma.py:380,400`)._
