# FAC-005 — Facility router (registered in main.py)

## 1. Summary & Goal

FAC-005 creates `app/routers/facilities.py` — the FastAPI router that exposes the facility and location CRUD surface to the outside world — and wires it into `app/main.py` alongside the existing OFBiz routers. This is the first ticket in the Milestone 2 stack that is user-visible: with FAC-005 merged and `FACILITY_FULFILLMENT_ENABLED=true`, `GET /openapi.json` will list the facility endpoints and they will be driveable from the browser or Playwright.

The router has four responsibilities:

1. **Flag gate** — every handler calls `_require_enabled()` as its first line so that mounting the router with the flag off is a no-op returning 404, exactly as `app/routers/inventory.py:32` does for `INVENTORY_RESERVATIONS_ENABLED`.
2. **Role split** — read endpoints use `require_ui_session` (storefront / admin can both read); mutating endpoints (create, update, archive facility; create, update, archive location) use `require_admin_or_root_csrf`, mirroring `app/routers/inventory.py:9–11`.
3. **Thin delegation** — each handler validates the request via the FAC-003 Pydantic model, calls the FAC-004 service function, maps the returned dict to the appropriate `Out` model, and returns it. No business logic lives in the router.
4. **`main.py` registration** — `facilities_router` is imported at `app/main.py:311`-style and included in the `create_app` body immediately after `inventory_router` and `returns_rma_router` (lines 877–878).

No DynamoDB tables, settings keys, or Pydantic models are added by this ticket (those are FAC-002, FAC-002, and FAC-003 respectively). No frontend changes ship with FAC-005; that is deferred to FAC-015.

## 3. Data Model

FAC-005 introduces no new DynamoDB tables, settings keys, or `T.*` handles. All DDB access happens through the FAC-004 service layer which reads/writes `T.facilities` (PK=`facility_id`, SK=`META` | `LOC#{location_id}`). The router is agnostic to the underlying storage shape.

For reference, the `facilities` table schema (defined in FAC-002) is:

| Key | Value | Notes |
|---|---|---|
| PK | `facility_id` | `sha256(owner_sub + "\|" + name)[:32]` — deterministic |
| SK | `META` | Facility header row |
| SK | `LOC#{location_id}` | Per-location sub-row |
| GSI_OWNER | PK=`owner_sub`, SK=`created_at` (N) | List facilities by owner |
| GSI_STATUS | PK=`status`, SK=`created_at` (N) | Admin queue by active/archived |

`attr_types={"created_at": "N"}` is declared in `scripts/local-ddb-init.py` (FAC-002 deliverable). The router never queries DynamoDB directly and carries no `attr_types` responsibility.

## 4. API / Service Design

### 4.1 Router declaration

```python
# app/routers/facilities.py
facilities_router = APIRouter(prefix="/ui/facilities", tags=["facilities"])
```

The prefix `/ui/facilities` is consistent with the OFBiz router family:
- `inventory_router` → `/ui/inventory`
- `returns_rma_router` → `/ui/returns`
- `facilities_router` → `/ui/facilities`

### 4.2 Flag-gate shim

```python
def _require_enabled() -> None:
    fac._require_enabled()
```

Called as the first statement of every handler. The service's `_require_enabled()` raises `HTTPException(status_code=404, detail="Facility fulfillment is not enabled")` when `S.facility_fulfillment_enabled` is `False`.

### 4.3 Imports

```python
from __future__ import annotations

from typing import Optional

from fastapi import APIRouter, Depends, HTTPException, Query

from app.auth.deps import AuthenticatedUser
from app.auth.policy import require_admin_or_root_csrf
from app.models import (
    FacilityIn,
    FacilityLocationIn,
    FacilityListOut,
    FacilityLocationListOut,
    FacilityLocationOut,
    FacilityOut,
)
from app.services import facilities as fac
from app.services.sessions import require_ui_session
```

### 4.4 Facility endpoints

#### `GET /ui/facilities` — list facilities

```python
@facilities_router.get("", response_model=FacilityListOut)
async def list_facilities(
    status: str = Query(default="active", pattern="^(active|archived|all)$"),
    limit: int = Query(default=50, ge=1, le=200),
    cursor: Optional[str] = Query(default=None),
    session=Depends(require_ui_session),
) -> FacilityListOut:
    _require_enabled()
    result = fac.list_facilities(
        owner_sub=session["user_sub"],
        status=status,
        limit=limit,
        cursor=cursor,
    )
    return FacilityListOut(**result)
```

**Auth**: `require_ui_session` — any authenticated user sees their own facilities. Admin/Root users who need to see all facilities across tenants use the admin queue endpoint (section 4.7).

**Behavior**: returns facilities owned by the session user, filtered by `status`. The `FacilityListOut` shape (FAC-003) includes a `next_cursor: Optional[str]` for pagination.

#### `POST /ui/facilities` — create facility

```python
@facilities_router.post("", response_model=FacilityOut, status_code=201)
async def create_facility(
    body: FacilityIn,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> FacilityOut:
    _require_enabled()
    rec = fac.create_facility(
        name=body.name,
        facility_type=body.facility_type,
        description=body.description,
        address=body.address,
        owner_sub=body.owner_sub or user.sub,
        idempotency_key=body.idempotency_key,
    )
    return FacilityOut(**rec)
```

**Auth**: `require_admin_or_root_csrf` — only admins/root can create facilities. The `owner_sub` in the body overrides the session user only when explicitly supplied (allows an admin to create a facility on behalf of another user). When absent, `owner_sub` defaults to `user.sub`.

**Idempotency**: the service computes `facility_id = sha256(owner_sub + "|" + name)[:32]` when `idempotency_key` is absent, or `sha256(idempotency_key)[:32]` when present. A `PUT` into an existing facility by the same key returns the existing record (HTTP 200 from the service; the router returns it with status 201 only on the initial call — or the router can always return 200 and let the service distinguish via `attribute_not_exists`; see Section 10.1).

#### `GET /ui/facilities/{facility_id}` — get facility

```python
@facilities_router.get("/{facility_id}", response_model=FacilityOut)
async def get_facility(
    facility_id: str,
    session=Depends(require_ui_session),
) -> FacilityOut:
    _require_enabled()
    rec = fac.get_facility(facility_id)
    if rec is None:
        raise HTTPException(status_code=404, detail="Facility not found")
    return FacilityOut(**rec)
```

**Auth**: `require_ui_session` — any authenticated user can read a facility record. FAC-004 service does not enforce ownership on reads (a facility ID is not secret; admins need cross-owner read access). If per-owner read isolation is required, that enforcement belongs in the service layer, not the router.

#### `PUT /ui/facilities/{facility_id}` — update facility

```python
@facilities_router.put("/{facility_id}", response_model=FacilityOut)
async def update_facility(
    facility_id: str,
    body: FacilityIn,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> FacilityOut:
    _require_enabled()
    rec = fac.update_facility(
        facility_id,
        actor_sub=user.sub,
        name=body.name,
        facility_type=body.facility_type,
        description=body.description,
        address=body.address,
    )
    return FacilityOut(**rec)
```

**Auth**: `require_admin_or_root_csrf`. **404 propagation**: if the service returns `None` (facility does not exist), the router raises `HTTPException(404, "Facility not found")`.

#### `DELETE /ui/facilities/{facility_id}` — archive facility

```python
@facilities_router.delete("/{facility_id}", response_model=FacilityOut)
async def archive_facility(
    facility_id: str,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> FacilityOut:
    _require_enabled()
    rec = fac.archive_facility(facility_id, actor_sub=user.sub)
    return FacilityOut(**rec)
```

**Soft-delete**: `DELETE` archives rather than hard-deletes, following the pattern of `archive_facility` in the FAC-004 service. The returned `FacilityOut.status` will be `"archived"`. Hard-deletes are not exposed.

### 4.5 Location endpoints

All location endpoints are nested under `/{facility_id}/locations`.

#### `GET /ui/facilities/{facility_id}/locations` — list locations

```python
@facilities_router.get("/{facility_id}/locations", response_model=FacilityLocationListOut)
```

**Auth**: `require_ui_session`. No pagination cursor for locations — a facility is expected to have O(100s) of locations, not millions. If a facility does not exist, the service returns an empty list (not 404); the router returns `{"locations": []}`.

### 4.6 Admin queue endpoints

Admin/Root users need to list facilities across all owners (e.g., to audit warehouse capacity). These live at `/ui/facilities/admin/...` and use `require_admin_or_root_csrf`.

**IMPORTANT**: The `/admin/queue` route MUST be declared BEFORE `/{facility_id}` in the router. FastAPI matches routes in declaration order. If `/{facility_id}` is declared first, `GET /ui/facilities/admin/queue` will be captured by the `/{facility_id}` handler with `facility_id="admin"` rather than routing to the admin handler. The same ordering constraint applies in `app/routers/kyc_cases.py` (CLAUDE.md: "the `/schedules` routes are declared BEFORE `/{export_id}`").

```python
@facilities_router.get("/admin/queue", response_model=FacilityListOut)
async def admin_list_facilities(
    status: str = Query(default="active", pattern="^(active|archived|all)$"),
    limit: int = Query(default=50, ge=1, le=200),
    cursor: Optional[str] = Query(default=None),
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> FacilityListOut:
    _require_enabled()
    result = fac.list_facilities(
        owner_sub=None,   # None = all owners (admin view)
        status=status,
        limit=limit,
        cursor=cursor,
    )
    return FacilityListOut(**result)
```

Passing `owner_sub=None` signals to the FAC-004 service that a cross-owner scan is requested (uses `GSI_STATUS` rather than `GSI_OWNER`).

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off 404 contract

With `FACILITY_FULFILLMENT_ENABLED=false` (the default), every request to any `/ui/facilities` endpoint returns:

```json
{"detail": "Facility fulfillment is not enabled"}
```

with HTTP 404. This is the standard OFBiz 404-gate contract, identical to `app/routers/inventory.py:32` and `app/services/returns_rma.py:71`. The `_require_enabled()` shim in the router delegates to `fac._require_enabled()` which raises `HTTPException(status_code=404, ...)`. No other response shape is possible.

Even with the router mounted (which it always is after FAC-005 merges), no facility data is accessible with the flag off. An operator flips `FACILITY_FULFILLMENT_ENABLED=true` in `.env.local` (or the prod environment) to activate the endpoints.

### 5.2 Route-ordering: `/admin/queue` before `/{facility_id}`

FastAPI resolves routes in declaration order within a router. The `GET /admin/queue` route must appear **before** `GET /{facility_id}` in `app/routers/facilities.py`, or the literal string `"admin"` will be captured as a `facility_id` path parameter and the handler will call `fac.get_facility("admin")`, returning 404 with the misleading message "Facility not found". The same pattern applies to all `/admin/...` sub-paths under `/{facility_id}`.

The complete intended declaration order in `app/routers/facilities.py`:

1. `GET /admin/queue` (admin list, cross-owner)
2. `GET ""` (user list, scoped to session user)
3. `POST ""` (create facility)
4. `GET /{facility_id}` (get facility)
5. `PUT /{facility_id}` (update facility)
6. `DELETE /{facility_id}` (archive facility)
7. `GET /{facility_id}/locations` (list locations)
8. `POST /{facility_id}/locations` (create location)
9. `GET /{facility_id}/locations/{location_id}` (get location)
10. `PUT /{facility_id}/locations/{location_id}` (update location)
11. `DELETE /{facility_id}/locations/{location_id}` (archive location)

### 5.3 Non-admin mutation → 403

A request by a `USER`-role session to `POST /ui/facilities` (or any other mutating endpoint) fails at the `require_admin_or_root_csrf` dependency with HTTP 403:

```json
{"detail": {"code": "role_required", "required_roles": ["admin", "root"], "actual_role": "user"}}
```

This is the standard FastAPI dependency rejection from `app/auth/policy.py:13–21`, unchanged.

### 5.4 CSRF enforcement on mutations

`require_admin_or_root_csrf` (at `app/auth/policy.py:100–106`) calls `enforce_cookie_csrf(request)` before checking the role. Cookie-authenticated admin requests that omit the `x-csrf-token` header, or whose `x-csrf-token` does not match the `ui_csrf` cookie value, receive HTTP 403 "Missing CSRF token" or "CSRF validation failed". Bearer-token-authenticated requests (e.g., from API key holders or programmatic clients) skip the CSRF check as per the `get_authenticated_user` logic in `app/auth/deps.py`.

### 5.5 404 propagation from service layer

The service functions `get_facility`, `update_facility`, `archive_facility`, `get_location`, `update_location`, and `archive_location` return `None` when the target record does not exist (they do not raise). The router checks for `None` and raises `HTTPException(404, ...)`. This keeps the service layer agnostic to HTTP and matches the pattern at `app/routers/inventory.py:40–42`.

### 5.6 `owner_sub` override on create

`POST /ui/facilities` accepts `body.owner_sub` (optional). If supplied by an admin, the created facility's `owner_sub` is the provided value, not `user.sub`. If absent, the facility is owned by the calling admin. This allows admins to provision facilities on behalf of users (e.g., onboarding a new warehouse operator). The value is passed verbatim to the service; the service does not validate that `body.owner_sub` corresponds to a real user (the users table is not consulted).

### 5.7 Empty location list for non-existent facility

`GET /ui/facilities/{facility_id}/locations` returns `{"locations": []}` (HTTP 200) when the facility does not exist. The service performs a `query(Key={"facility_id": fid}, FilterExpression=Attr("sk").begins_with("LOC#"))` which returns zero items for an unknown `fid`. The router does not verify the facility exists before listing its locations — a separate `GET /ui/facilities/{facility_id}` would return 404 for a non-existent facility. This "silent empty list" behaviour is acceptable for the locations endpoint because it avoids an extra DDB read per list call; Playwright E2E tests should create the facility first.

### 5.8 Inventory location dimension linkage

A `FacilityLocationOut.location_id` (e.g., `"bin-a1"`) can be passed directly as `location_id` to any `inventory.*` call. The inventory service's `_location_sk("bin-a1")` at `app/services/inventory.py:59` produces `LOC#bin-a1`, the DDB sort key for that stock record. FAC-005 does not call `inventory.*` directly; that linkage is exercised in FAC-006 (transfers) and FAC-007 (receiving). The router merely surfaces the `location_id` string in the `FacilityLocationOut` response.

### 5.9 `GET /openapi.json` schema generation

All FAC-003 models (`FacilityIn`, `FacilityOut`, etc.) must be importable with no errors at FastAPI startup. When `FACILITY_FULFILLMENT_ENABLED` is off (the default), schema generation still succeeds because the models are pure Pydantic with no DDB calls. The flag gate is a runtime per-request check, not an import-time guard. Therefore `GET /openapi.json` will list the `/ui/facilities` endpoints regardless of whether the flag is on or off; the 404 is returned at request time.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

The router itself contains no `if S.dev_mode` branches. The flag gate `_require_enabled()` is a boolean check on `S.facility_fulfillment_enabled` that behaves identically in dev (DynamoDB Local), test (moto), and prod (real DynamoDB). The `require_admin_or_root_csrf` dependency enforces CSRF in all environments (dev mode does not weaken it — the mock-KMS path used for session signing is transparent to the CSRF check).

### Role gate parity

`require_admin_or_root_csrf` from `app/auth/policy.py:100–106` is used unchanged. There is no relaxed-auth path for dev mode. This is consistent with `app/routers/inventory.py` and `app/routers/returns_rma.py`.

### Idempotency

The router itself is stateless and idempotent by construction: re-sending the same request produces the same observable outcome because idempotency is enforced in the service layer (FAC-004) via conditional DDB puts. The router does not retry; it simply delegates.

### Security — no over-fetching on `list_facilities`

`GET /ui/facilities` passes `owner_sub=session["user_sub"]` to the service, scoping the GSI query to only the caller's facilities. The `GET /admin/queue` endpoint passes `owner_sub=None` but requires `require_admin_or_root_csrf`, so unprivileged users cannot trigger a cross-owner scan.

### Security — path parameter validation

`facility_id` and `location_id` are raw strings from the URL path. They are passed directly to the service layer, which uses them as DDB key values. DynamoDB key values are strings with no injection surface (unlike SQL). No additional sanitisation is required, but `Field(min_length=1, max_length=128)` constraints on the input models prevent empty-string keys.

## 10. Open Questions / Assumptions

1. **HTTP 201 vs 200 on idempotent create.** `POST /ui/facilities` returns `status_code=201` on the first call. If the same idempotency key is replayed, the service returns the existing record (no error). The router cannot distinguish "created now" from "already existed" without an additional return value from the service (e.g., a `created: bool` flag). Two options: (a) always return 200 (simpler, matches most clients that ignore status codes); (b) have the service return `(dict, was_created: bool)` and let the router choose 200 or 201. **Assumption**: option (a) is used — the endpoint always returns 200. The `status_code=201` annotation in Section 4.4 is a placeholder; the actual implementation returns 200 for idempotent replays. Reviewers should confirm this is acceptable before implementation.

2. **`GET /ui/facilities` scoping: owner vs all.** The current design returns only the session user's own facilities. If the platform has a global facility registry (all users share a set of warehouses), the `owner_sub` filter should be removed and all active facilities returned to any authenticated user. **Assumption**: facilities are per-owner (each tenant/user has their own warehouses). If reviewers confirm a global registry model, `GET /ui/facilities` should omit the `owner_sub=session["user_sub"]` filter and replace it with a global `GSI_STATUS` query.

3. **`PUT /ui/facilities/{facility_id}` vs `PATCH`.** The ticket description says "create/update/archive facility". Using `PUT` requires the client to send all `FacilityIn` fields (full replacement). Using `PATCH` would allow partial updates. **Assumption**: `PUT` is used (full replacement), following `app/routers/inventory.py:45` which uses `PUT /ui/inventory/items`. A `PATCH` endpoint can be added later without breaking the `PUT`.

4. **Location `location_id` assignment strategy.** The FAC-004 service may derive `location_id` deterministically (e.g., `sha256(facility_id + "|" + name)[:32]`) or randomly (UUID). The router is agnostic to this. If the service uses a deterministic ID, `POST /ui/facilities/{facility_id}/locations` is idempotent for the same facility + name combination. **Assumption**: FAC-004 uses deterministic IDs (matching the facility create pattern) so that `create_location` is replay-safe.

5. **`list_locations` for non-existent facility returns 200 empty vs 404.** Section 5.7 specifies returning 200 with an empty list. If reviewers prefer 404 when the facility doesn't exist, the handler must call `fac.get_facility(facility_id)` first and raise 404 if absent. **Assumption**: 200 empty list is acceptable to avoid the extra DDB read.

6. **Admin queue cursor format.** `GET /ui/facilities/admin/queue` and `GET /ui/facilities` both accept a `cursor` query parameter. The cursor encoding/decoding is owned by `app/core/cursor.py`. The router passes the raw cursor string to the service; the service passes it to `cursor.decode(cursor)` before the DDB query. The router never inspects the cursor value.

7. **Whether `FacilityLocationListOut` needs a `next_cursor`.** Per FAC-003 spec (Section 10.3), `FacilityLocationListOut` is defined without a cursor field on the assumption that a facility has O(100) locations. If FAC-004 returns a cursor for large facilities, `FacilityLocationListOut` will need to be updated. This is a FAC-003 decision; FAC-005 accepts the shape as defined.
