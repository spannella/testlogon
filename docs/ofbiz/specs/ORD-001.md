# ORD-001 — Order-lifecycle scoping & state-machine design

## 1. Summary & Goal

ORD-001 is the foundational spike for the OFBiz Order Manager work stream. Its goal is to produce a precise, code-grounded design for how the platform's existing flat order record (`status="pending_payment"`, written by `app/services/commerce_order_service.py`) evolves into a full OFBiz-style sales-order state machine — covering seven primary statuses, four side states, an append-only audit trail, ship groups, and order adjustments — while remaining byte-for-byte additive: every code path is unchanged when `ORDER_LIFECYCLE_ENABLED` is off.

This document is the authoritative design reference for the downstream implementation tickets (ORD-002 through ORD-010) and supersedes any informal notes. No code is shipped with this ticket; the deliverable is this specification and a sign-off that no money path is forked.

## 3. Data Model

### 3.1 Critical constraint: `orders` table has no sort key today

The existing `orders` table was defined as PK-only (`order_id`, no SK) at `scripts/local-ddb-init.py:288`. Adding new SK-partitioned rows (HIST, SHIPGRP, ADJ) requires adding a sort key `sk` to the base table. This is a **schema migration**: the existing `orders` rows (which have no `sk` attribute) must be backward-compatible.

**Resolution**: Introduce `sk` as a sort key to the `orders` table. All existing rows continue to work because DynamoDB allows items without the sort key value stored — they are simply unreachable by SK-aware `get_item` calls. Existing `get_item(Key={"order_id": order_id})` calls (e.g. `returns_rma.py:107`) are broken by this change and must be updated to `get_item(Key={"order_id": order_id, "sk": "ORDER"})` in ORD-003.

The order header SK is `"ORDER"` (fixed literal). All new sub-item types use different SK prefixes under the same `order_id`.

### 3.2 Orders table — extended single-table layout

**Table**: `orders` (env `ORDERS_TABLE_NAME`, default `"orders"`)
**PK**: `order_id` (S) — unchanged
**SK**: `sk` (S) — **new**, added via ORD-003

| Row type | SK value | Description |
|---|---|---|
| Order header | `ORDER` | One per order; the record today is the header |
| Status history | `HIST#{ts:020d}#{event_id}` | One per transition; `ts` is `now_ts()` (int); `event_id` is `sha256(order_id|from|to|idempotency_key)[:16]` |
| Ship group | `SHIPGRP#{ship_group_id}` | One per logical shipment; `ship_group_id` is `uuid4().hex` |
| Order adjustment | `ADJ#{adjustment_id}` | One per discount/surcharge/tax/shipping line; `adjustment_id` is `uuid4().hex` |

### 3.3 GSIs on `orders`

Three GSIs total on the `orders` table after ORD-003. The two existing GSIs (`GSI_USER`, `GSI_STATUS`) are **unchanged**; two new GSIs are added:

**Existing GSIs (unchanged):**

| Index | PK | SK | Notes |
|---|---|---|---|
| `GSI_USER` | `user_id` (S) | `created_at` (S, ISO string) | Lists orders by user |
| `GSI_STATUS` | `status` (S) | `created_at` (S, ISO string) | Legacy status fan-out; still written as `status="pending_payment"` when flag is off |

**New GSIs (added in ORD-003):**

| Index | PK | SK | attr_types |
|---|---|---|---|
| `GSI_LIFECYCLE_STATUS` | `lifecycle_status` (S) | `updated_ts` (N, integer Unix seconds) | `{"updated_ts": "N"}` |
| `GSI_SHIP_DATE` | `ship_date_bucket` (S, `YYYY-MM-DD` of expected ship date) | `ship_ts` (N, integer Unix seconds of expected ship timestamp) | `{"ship_ts": "N"}` |

`GSI_LIFECYCLE_STATUS` is populated only on order header rows (SK=`ORDER`) that carry `lifecycle_status`. `ship_date_bucket` / `ship_ts` are populated only on SHIPGRP rows; the header itself does not carry them.

### 3.4 Numeric sort key requirement

Per CLAUDE.md, the DDB `attr_types` must declare `"N"` for numeric GSI sort keys. The ORD-003 `TableDef` must include:

```python
TableDef(
    _resolve_table_name(S.orders_table_name, "orders"),
    "order_id",
    "sk",
    gsi=[
        {"index_name": "GSI_USER", "partition_key": "user_id", "sort_key": "created_at"},
        {"index_name": "GSI_STATUS", "partition_key": "status", "sort_key": "created_at"},
        {"index_name": "GSI_LIFECYCLE_STATUS", "partition_key": "lifecycle_status", "sort_key": "updated_ts"},
        {"index_name": "GSI_SHIP_DATE", "partition_key": "ship_date_bucket", "sort_key": "ship_ts"},
    ],
    attr_types={"updated_ts": "N", "ship_ts": "N"},
)
```

### 3.5 `order_items` table — unchanged

The `order_items` table (`scripts/local-ddb-init.py:295`) is not modified. Ship groups reference item IDs by value, not as FK rows in this table.

### 3.6 Additive coexistence: `lifecycle_status` vs `status`

The `status` field on the order header is the **legacy field**. It remains `"pending_payment"` for all orders when `ORDER_LIFECYCLE_ENABLED` is off, and is never removed. When the flag is on, `lifecycle_status` is the canonical state-machine field. To keep legacy consumers (e.g. `GSI_STATUS` fans, `file_bundle_checkout.py:98`) intact, every lifecycle transition that succeeds also writes `status = _legacy_mirror(lifecycle_status)` on the header. The mirror mapping is:

| `lifecycle_status` | legacy `status` mirror |
|---|---|
| `created` | `pending_payment` |
| `approved` | `approved` |
| `allocated` | `processing` |
| `picking` | `processing` |
| `packed` | `processing` |
| `shipped` | `shipped` |
| `completed` | `completed` |
| `held` | `on_hold` |
| `backorder` | `backordered` |
| `cancelled` | `cancelled` |
| `returned` | `returned` |

## 4. API / Service Design

### 4.1 New service: `app/services/order_lifecycle.py`

The entire state-machine logic lives here. It is a pure additive layer — it reads and writes `T.orders` for header and HIST rows, but never touches `T.order_items`.

```python
# Status enum (str, Enum following mass_message_campaign_contract.py pattern)
class OrderLifecycleStatus(str, Enum):
    CREATED    = "created"
    APPROVED   = "approved"
    ALLOCATED  = "allocated"
    PICKING    = "picking"
    PACKED     = "packed"
    SHIPPED    = "shipped"
    COMPLETED  = "completed"
    HELD       = "held"
    BACKORDER  = "backorder"
    CANCELLED  = "cancelled"
    RETURNED   = "returned"

# Transition graph (data, not logic — mirrors video_state_machine.py pattern)
TRANSITIONS: Final[Mapping[OrderLifecycleStatus, FrozenSet[OrderLifecycleStatus]]] = {
    CREATED:   frozenset({APPROVED, HELD, CANCELLED}),
    APPROVED:  frozenset({ALLOCATED, HELD, CANCELLED, BACKORDER}),
    ALLOCATED: frozenset({PICKING, HELD, CANCELLED, BACKORDER}),
    PICKING:   frozenset({PACKED, HELD, CANCELLED, BACKORDER}),
    PACKED:    frozenset({SHIPPED, HELD, CANCELLED}),
    SHIPPED:   frozenset({COMPLETED, RETURNED}),
    COMPLETED: frozenset({RETURNED}),
    HELD:      frozenset({APPROVED, ALLOCATED, PICKING, PACKED, CANCELLED}),
    BACKORDER: frozenset({ALLOCATED, CANCELLED}),
    CANCELLED: frozenset(),
    RETURNED:  frozenset(),
}

# Typed error classes
class OrderNotFoundError(ValueError): ...
class OrderInvalidTransitionError(ValueError):
    def __init__(self, from_status: str, to_status: str): ...
class OrderConflictError(RuntimeError): ...  # optimistic concurrency race

# Primary entry point
def transition_order(
    order_id: str,
    target_status: OrderLifecycleStatus,
    *,
    actor: str,
    reason: str = "",
    idempotency_key: str | None = None,
) -> dict[str, Any]:
    ...

# Read helpers
def get_order_header(order_id: str) -> dict[str, Any] | None: ...
def list_status_history(order_id: str) -> list[dict[str, Any]]: ...
```

`transition_order` flow:
1. `get_item(Key={"order_id": order_id, "sk": "ORDER"})` → 404 if missing.
2. Read `current = item["lifecycle_status"]`.
3. Validate `target in TRANSITIONS[current]` → raise `OrderInvalidTransitionError` if not.
4. Derive `event_id = hashlib.sha256(f"{order_id}|{current}|{target}|{idempotency_key or ''}".encode()).hexdigest()[:16]`.
5. Conditional `update_item` on header: `ConditionExpression="lifecycle_status = :current_status"`, sets `lifecycle_status`, `status` (mirror), `updated_ts`, `updated_at`. Catches `ConditionalCheckFailedException` → raise `OrderConflictError`.
6. Append HIST row `SK=HIST#{ts:020d}#{event_id}` — best-effort (failure is logged, not raised).
7. Emit `audit_event("order_status_changed", actor, ...)`.
8. Return updated header dict.

Idempotency: a replay with the same `idempotency_key` from the same source/target will fail the conditional update (order is now already in `target_status`). The caller catches `OrderConflictError` and re-reads the current header; if it is already in `target_status`, the operation is considered a no-op success.

## 5. Detailed Behavior & Edge Cases

### 5.1 Full transition matrix

The table below is the canonical legal/illegal reference. ✓ = legal, — = illegal.

| From \ To | created | approved | allocated | picking | packed | shipped | completed | held | backorder | cancelled | returned |
|---|---|---|---|---|---|---|---|---|---|---|---|
| created | — | ✓ | — | — | — | — | — | ✓ | — | ✓ | — |
| approved | — | — | ✓ | — | — | — | — | ✓ | ✓ | ✓ | — |
| allocated | — | — | — | ✓ | — | — | — | ✓ | ✓ | ✓ | — |
| picking | — | — | — | — | ✓ | — | — | ✓ | ✓ | ✓ | — |
| packed | — | — | — | — | — | ✓ | — | ✓ | — | ✓ | — |
| shipped | — | — | — | — | — | — | ✓ | — | — | — | ✓ |
| completed | — | — | — | — | — | — | — | — | — | — | ✓ |
| held | — | ✓ | ✓ | ✓ | ✓ | — | — | — | — | ✓ | — |
| backorder | — | — | ✓ | — | — | — | — | — | — | ✓ | — |
| cancelled | — | — | — | — | — | — | — | — | — | — | — |
| returned | — | — | — | — | — | — | — | — | — | — | — |

Design rationale:
- `held` is reachable from any pre-`shipped` state (warehouse holds, payment disputes, compliance flag). It is resumable back to the prior fulfillment step or any earlier fulfillment step in `{approved, allocated, picking, packed}` — the warehouse decides the recovery point.
- `backorder` is reachable from `approved` or `allocated` (stock not available at time of allocation). It can only resume to `allocated` (re-attempt allocation when stock arrives) or cancel.
- `shipped → cancelled` is illegal; once physical goods are in transit the only recourse is `returned`.
- `returned` is only reachable from `shipped` or `completed`; it is a terminal state (the RMA system drives further steps).
- `cancelled` and `returned` are terminal states with empty target sets.

### 5.2 Legacy `status` and `GSI_STATUS` compatibility

The existing `GSI_STATUS` index on the `orders` table (`scripts/local-ddb-init.py:292`) is keyed on the `status` field. All lifecycle transitions mirror to the legacy `status` field (see Section 3.6). Existing consumers querying `GSI_STATUS` for `status="pending_payment"` will continue to see orders in `created` lifecycle state. The `file_bundle_checkout.py:98` write does not use the lifecycle module at all and continues to write `status="pending_payment"` with no `lifecycle_status` field — its rows are invisible to `GSI_LIFECYCLE_STATUS`.

### 5.3 `orders` table SK migration

Today `get_item(Key={"order_id": order_id})` fetches the header. After adding `sk` as a table sort key, these calls silently return nothing (DynamoDB requires the full primary key for `get_item` when a sort key exists). **All callers of `T.orders.get_item` / `self.orders_table.get_item` must be updated in ORD-003** to use `Key={"order_id": order_id, "sk": "ORDER"}`. Known callers:
- `returns_rma.py:107` — `T.orders.get_item(Key={"order_id": order_id})`
- `subscription_cycle_orders.py:39` — `self.orders_table.get_item(Key={"order_id": order_id})`

Existing items written without `sk` become unreachable unless a migration backfills `sk="ORDER"`. The migration strategy is:

1. In dev: `just restart` recreates tables from scratch; no migration needed.
2. In prod: a one-time migration script iterates existing `orders` rows (base-table scan), writes back `sk="ORDER"` using a conditional put (condition: `attribute_not_exists(sk)`) — idempotent, safe to re-run.

### 5.4 Concurrency and idempotency

The conditional `update_item` on the header uses `ConditionExpression="lifecycle_status = :current"`. Two concurrent callers driving the same transition:
- First caller wins the conditional update, writes HIST row, returns success.
- Second caller catches `ConditionalCheckFailedException`, raises `OrderConflictError`.
- The router returns HTTP 409 with `code="order_lifecycle_conflict"`.

Replay safety: the caller may include an `idempotency_key`. The `event_id` is derived from `sha256(order_id|from|to|idempotency_key)[:16]`. The HIST row PK is `(order_id, HIST#{ts}#{event_id})`; a replay produces the same `event_id` with a different `ts`, so it writes a second HIST row in the extremely unlikely case of a successful-but-connection-lost first attempt. This is acceptable (best-effort audit, not transactional) and matches the platform's existing audit convention.

### 5.5 `held` as a reversible pause

`held` is special: it stores the `pre_hold_status` on the header at the time of the hold transition so the system (or warehouse UI) can suggest the correct resume target. The `pre_hold_status` field is set on the header during the `→ held` transition and cleared on the `held → *` transition. This is a convenience field, not enforced by the state machine (the operator picks the resume target).

### 5.6 Cancel/return and money-out

Orders in `cancelled` or `returned` that require a refund use the existing `refund_payment` function at `app/routers/billing.py:1287`. The `order_lifecycle` service does not issue refunds directly; instead it records the transition and emits a `order_cancelled` / `order_returned` audit event. The cancel/return router endpoint (ORD-010) accepts an optional `issue_refund: bool` and if true delegates to `refund_payment`, passing `extra={"provider": original_provider, "order_id": order_id}` for FIN-013 provider attribution. The GL entry is a `new_ledger_entry` with `entry_type="adjustment"`, `reason="refund"`, and the provider — never a separate mechanism. `settle_or_reverse_ledger` at `billing_shared.py:262` is called to reverse any pending ledger entry from the original charge.

### 5.7 `created_at` ISO string vs. `updated_ts` integer

The existing `GSI_USER` and `GSI_STATUS` sort keys use ISO string `created_at`. New GSIs (`GSI_LIFECYCLE_STATUS`, `GSI_SHIP_DATE`) use integer `updated_ts` / `ship_ts` to enable range queries with numeric comparisons (`updated_ts > :since`). The header retains `created_at` (ISO string) for backward compatibility with the existing GSIs, and adds `updated_ts` (int) for the new lifecycle GSI. `now_ts()` from `app/core/time.py:2` is used for all integer timestamps.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity**: The lifecycle service and all DDB writes are identical in dev and prod. There is no `dev_mode` branch inside `order_lifecycle.py`. The only dev-specific behaviour is that `just restart` recreates the `orders` table from the updated `TableDef`; prod requires a migration for the new SK and new GSIs (see Section 5.3).

**Idempotency**: `commerce_order_service.create_order` already derives `order_id = sha256(correlation_id)[:32]` (line 67). Calling it twice with the same `correlation_id` produces the same `order_id` and the second `put_item` overwrites the first (DynamoDB put is idempotent for the same PK). Lifecycle transitions add a `ConditionExpression` guard that makes them exactly-once within a given source state. HIST rows are best-effort; duplicate HIST rows under different `ts` values are acceptable (they are advisory audit data).

**Ownership enforcement**: The `GET /orders/{order_id}` endpoint checks that `order["user_id"] == ctx["user_sub"]` unless the caller has `role >= ADMIN`. A non-admin user cannot read or transition another user's order. This is enforced at the router layer, mirroring the KYC cases ownership pattern.

**Input validation**: `transition_order` rejects transitions to `cancelled` / `returned` from post-`shipped` / post-`completed` states respectively. Any attempt to write a `lifecycle_status` value outside the `OrderLifecycleStatus` enum raises `ValueError` before touching DynamoDB.

**No money fork**: The lifecycle service contains zero Stripe/PayPal/CCBill calls. All money-out paths (ORD-010) call `refund_payment` at `app/routers/billing.py:1287`, which writes to `T.billing` via `new_ledger_entry` with full FIN-013 provider attribution. The GL continues to derive from the single-entry ledger; no parallel accounting mechanism is introduced.

### With flag off (zero change guarantee)

When `ORDER_LIFECYCLE_ENABLED=false` (default):
- `commerce_order_service.create_order` (line 39) writes exactly the same record it does today: `status="pending_payment"`, no `lifecycle_status`, no `updated_ts`, no HIST rows. Verified by a golden-record pytest in ORD-007.
- `T.orders.get_item` callers (e.g. `returns_rma.py:107`) continue to work because the header SK is `"ORDER"` only after ORD-003 adds the sort key; with the flag off, `create_order` still writes `sk="ORDER"` on all new rows (ORD-003 adds this field unconditionally as it is a table-level constraint).
- The `GSI_STATUS` and `GSI_USER` indexes are unchanged in schema and continue to receive their writes.
- The new `GSI_LIFECYCLE_STATUS` and `GSI_SHIP_DATE` indexes exist on the table but receive no writes with the flag off (no `lifecycle_status` field on new rows).
- All existing `orders_router` (none exists yet) / shop / cart / subscription cycle endpoints are byte-for-byte unchanged.

### SK migration (existing rows)

After ORD-003 adds `sk` as the `orders` table sort key, existing rows written without `sk` are unreachable via `get_item(Key={order_id, sk=ORDER})`. A migration is required:

**Dev**: handled automatically by `just restart` (drops and recreates tables).

**Prod**:
1. Deploy ORD-003 (new `TableDef` with `sk`, new GSIs) — `UpdateTable` adds GSIs; no data change.
2. Run a one-time migration script: scan `orders`, for each item without `sk`, write back with `sk="ORDER"` using `update_item` with `ConditionExpression="attribute_not_exists(sk)"` (idempotent). Cap at 1 MB DDB scan page size; run with exponential backoff.
3. Update all `get_item(Key={"order_id": ...})` callers to `Key={"order_id": ..., "sk": "ORDER"}` — this is part of ORD-003. Known callers: `returns_rma.py:107`, `subscription_cycle_orders.py:39`.

### `file_bundle_checkout.py` compatibility

`app/services/file_bundle_checkout.py:98` writes directly to `T.orders` without `sk`. After ORD-003 adds the sort key, this write must be updated to include `"sk": "ORDER"` to be retrievable. This is not a lifecycle feature — it is a migration fix in ORD-003.

## 9. Test Plan

### 9.1 Unit tests: `tests/test_ord_001_state_machine.py`

All tests are hermetic and offline. Pattern: `mock_aws()` context, moto in-memory DynamoDB for the `orders` table bound to `T.orders` via `object.__setattr__(T, "orders", moto_table)`. The `Settings` singleton `S` is frozen; flags are toggled via `object.__setattr__(S, "order_lifecycle_enabled", True)`. Route handler coroutines are called directly (not via `TestClient`).

**Test groups:**

1. **Transition graph completeness** — assert that every edge in the `TRANSITIONS` dict maps to a non-empty frozenset for non-terminal states, and terminal states (`cancelled`, `returned`) have empty sets.

2. **Legal transitions** — for a representative subset of the transition matrix, write a header row in source state, call `transition_order`, assert `lifecycle_status` on the returned dict equals the target, assert the legacy `status` mirror is correct, assert a HIST row exists.

3. **Illegal transitions** — attempt a transition not in `TRANSITIONS` (e.g. `created → shipped`), assert `OrderInvalidTransitionError` is raised, assert DDB was not written.

4. **Optimistic concurrency** — simulate a race by patching `T.orders.update_item` to raise `ClientError({"Error": {"Code": "ConditionalCheckFailedException"}})` on the first call; assert `OrderConflictError` is raised.

5. **Idempotency / replay** — call `transition_order` twice with the same `idempotency_key` and same target; the second call raises `OrderConflictError` (order is already in target state). The caller reads the current state and it matches the target → treats as no-op success.

6. **`backorder` sub-flag** — with `S.order_backorder_enabled=False`, attempt `approved → backorder`; assert `OrderInvalidTransitionError`. With flag `True`, same transition succeeds.

7. **Flag-off golden record** — call `commerce_order_service.create_order` with `S.order_lifecycle_enabled=False`; assert the written DDB item is byte-for-byte equal to today's schema (no `lifecycle_status`, no `updated_ts`, `status="pending_payment"`).

8. **Flag-on initial write** — call `create_order` with flag on; assert `lifecycle_status="created"`, `status="pending_payment"` (mirror), HIST row written with `from_status=None`, `to_status="created"`.

9. **`list_status_history`** — write three HIST rows with ascending `ts` values; assert returned list is newest-first by `ts`.

10. **`pre_hold_status` round-trip** — transition `approved → held`, assert `pre_hold_status="approved"` on header; transition `held → allocated`, assert `pre_hold_status` is cleared.

Gated: all tests use `beforeAll` that sets `ORDER_LIFECYCLE_ENABLED=1` via the dev-tools internal API (or skips if unavailable in CI). Covers:
- Alice creates a cart purchase (section 1) and the resulting order appears at `GET /ui/orders/{id}` with `lifecycle_status="created"`.
- Admin (charlie_admin) drives a `created → approved → allocated` transition sequence (section 2); each transition returns the updated status and a history entry.
- Attempting an illegal transition (`created → shipped`) returns HTTP 409 (section 3).
- OrdersPage UI (section 4) shows the order lifecycle badge.

## 10. Open Questions / Assumptions

1. **Assumption**: the `orders` table migration (adding `sk`) is acceptable as a breaking DDB schema change in dev (table drop/recreate). In prod, a migration script is required before ORD-003 is deployed. This must be confirmed by the ops team.

2. **Assumption (partially verified)**: `file_bundle_checkout.py:98` writes directly to `T.orders` and bypasses `commerce_order_service`. It will need `"sk": "ORDER"` added in ORD-003. A repo grep at spec-time found the following direct `T.orders` / `self.orders_table` callers beyond `commerce_order_service`: `file_bundle_checkout.py:98` (put_item), `returns_rma.py:107` (get_item), `subscription_cycle_orders.py:39` (get_item). All three require ORD-003 updates. Re-verify at implementation time for any new callers added in the interim.

3. **Open question**: Should `held` resume only to the `pre_hold_status` value (enforced) or to any valid target (operator choice)? This spec proposes operator choice with `pre_hold_status` as a hint. If enforcement is desired, `TRANSITIONS[HELD]` must be dynamically narrowed per-order, which complicates the static `TRANSITIONS` dict.

4. **Assumption**: `returned` is a terminal state managed entirely by the RMA module (ORD-010 / OFB-010). The lifecycle service only drives the `shipped/completed → returned` transition; all subsequent return-processing steps belong to `returns_rma.py`.

5. **Open question**: Should `GSI_STATUS` be updated to key on `lifecycle_status` instead of the legacy `status` field in a future cleanup ticket? This spec keeps them separate to avoid breaking existing GSI consumers. A cleanup ticket should be tracked post-launch.

6. **Assumption**: The ship-group fulfillment sub-statuses (`allocated → picking → packed → shipped` per ship group) and their roll-up to the order header are part of ORD-009, not this spec. This spec only defines the order-level state machine.

7. **Assumption**: `ORDER_LIFECYCLE_AUTO_APPROVE` triggers `created → approved` on payment confirmation, not at order creation time. The hook point is `shoppingcart.py:581` (after `create_order_from_line_items` returns and payment is confirmed). This avoids auto-approving orders that were created but not yet paid.

8. **Open question**: Integer vs. ISO `created_at` for `GSI_USER` and `GSI_STATUS`. The existing GSIs use ISO strings. Adding a parallel integer `created_ts` field and migrating the GSIs would improve range-query ergonomics but is out of scope for this milestone. Tracked as a future improvement.
