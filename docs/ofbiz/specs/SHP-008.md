# SHP-008 — Shipment & ship-group service

## 1. Summary & Goal

SHP-008 creates `app/services/shipments.py` — the first-class Shipment entity for the
OFBiz Shipping/Logistics module. The deliverables are:

1. **`create_shipment`**: Create a `shipments` row + linked `shipment_items` rows + a
   default single `shipment_packages` row from an order, with deterministic
   `shipment_id` for idempotent replay.
2. **Ship-group support**: Multiple shipments per order, each with its own `ship_to_address`
   and `carrier_code`/`method_code` (mirroring OFBiz `OrderItemShipGroup`). The
   per-group `ship_group_seq` is caller-supplied (1-based integer), and the
   `shipment_id` is derived from it deterministically so that two calls with the same
   `(order_id, ship_group_seq)` converge on the same row.
3. **Quantity guard**: The summed `quantity` across all shipments for a given order line
   must never exceed the ordered `quantity` on `T.order_items`. Over-ship is rejected
   with HTTP 422 before any write occurs.
4. **Read surface**: `get_shipment`, `list_shipments_for_order` (uses `GSI_ORDER` on
   `T.shipments`), and `list_shipments_by_status` (uses `GSI_STATUS` on `T.shipments`).
5. **Audit trail**: Every creation is emitted via `app/services/alerts.audit_event` with
   outcome, `order_id`, `shipment_id`, and `ship_group_seq`.

With `SHIPPING_ENABLED=false` (the default) every function in this service is unreachable
through any router path; the flag gate is enforced by the router (SHP-005 pattern) not by
the service layer itself, keeping the service pure business logic.

## 2. Context & Current State

### 2.1 Order and line-item source tables (reused, not extended)

`app/services/commerce_order_service.py:39` defines `create_order`, which writes a
`shipments`-linked order row to `T.orders` (PK `order_id`, no SK;
`scripts/local-ddb-init.py:287–294`) and one row per line item to `T.order_items`
(PK `order_id` / SK `item_id`; `local-ddb-init.py:295`), where `item_id` is the
1-based integer string from `commerce_order_service.py:88,91` (e.g. `"1"`, `"2"`, ...).

Each `T.order_items` row (`commerce_order_service.py:88–104`) carries:

| Field | Type | Notes |
|-------|------|-------|
| `order_id` | str | FK to `orders.order_id` |
| `item_id` | str | 1-based integer string (e.g. `"1"`) |
| `sku` | str | Product SKU |
| `quantity` | int | Ordered quantity |
| `amount_cents` | int | Line total in cents |

SHP-008 reads `T.order_items` to validate ordered quantities and denormalise `sku` onto

byte-for-byte unchanged.

### 2.2 Deterministic shipment_id derivation (mirrors commerce_order_service)

`app/services/commerce_order_service.py:67` computes:

```python
order_id = hashlib.sha256(corr.encode("utf-8")).hexdigest()[:32]
```

where `corr = f"{source_system}:{generated_order_id}"`. SHP-008 follows the same
pattern:

```python
correlation_id = f"shipment:{order_id}:{ship_group_seq}"
shipment_id = hashlib.sha256(correlation_id.encode("utf-8")).hexdigest()[:32]
```

The ticket spec explicitly cites this form: `sha256("shipment:{order_id}:{ship_group_seq}")[:32]`. This means calling `create_shipment` twice with the same `(order_id, ship_group_seq)` produces the same `shipment_id`, and the second `put_item` is idempotent (DynamoDB `put_item` with no condition expression overwrites an identical item with identical content; the caller receives the same `ShipmentOut`).

### 4.2 `_derive_shipment_id(order_id: str, ship_group_seq: int) -> str`

```python
def _derive_shipment_id(order_id: str, ship_group_seq: int) -> Tuple[str, str]:
    correlation_id = f"shipment:{order_id}:{ship_group_seq}"
    return hashlib.sha256(correlation_id.encode("utf-8")).hexdigest()[:32], correlation_id
```

Returns `(shipment_id, correlation_id)`. The `shipment_id` is a 32-hex-character
deterministic ID identical to the order-id derivation at
`commerce_order_service.py:67`.

### 4.3 `_get_order_items(order_id: str) -> Dict[str, Dict[str, Any]]`

Returns a dict keyed by `item_id` (string). Uses pagination (`LastEvaluatedKey` loop)
mirroring `returns_rma.py:111–123`:

```python
def _get_order_items(order_id: str) -> Dict[str, Dict[str, Any]]:
    out: Dict[str, Dict[str, Any]] = {}
    kwargs: Dict[str, Any] = {
        "KeyConditionExpression": Key("order_id").eq(order_id),
    }
    while True:
        r = T.order_items.query(**kwargs)
        for it in r.get("Items", []):
            out[str(it.get("item_id"))] = it
        lek = r.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
    return out
```

### 4.4 `_get_existing_shipped_qty(order_id: str) -> Dict[str, int]`

Aggregates already-shipped quantity per `item_id` across all existing shipments for this
order. Uses `GSI_ORDER` on `T.shipments` to find `shipment_id`s, then queries
`T.shipment_items` for each. Returns a dict mapping `item_id` → total already-shipped
quantity.

This is the function that enforces the over-ship guard: before writing, `create_shipment`
calls `_get_existing_shipped_qty(order_id)` and verifies that
`already_shipped[item_id] + new_qty ≤ ordered_qty[item_id]` for every line in the
incoming request.

```python
def _get_existing_shipped_qty(order_id: str) -> Dict[str, int]:
    # 1. List all shipment_ids for this order via GSI_ORDER
    shipment_ids: List[str] = []
    kwargs: Dict[str, Any] = {
        "IndexName": "GSI_ORDER",
        "KeyConditionExpression": Key("order_id").eq(order_id),
        "ProjectionExpression": "shipment_id",
    }
    while True:
        r = T.shipments.query(**kwargs)
        for it in r.get("Items", []):
            sid = it.get("shipment_id")
            if sid:
                shipment_ids.append(sid)
        lek = r.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek

    # 2. For each shipment, accumulate item quantities
    totals: Dict[str, int] = {}
    for sid in shipment_ids:
        items = _load_shipment_items(sid)
        for it in items:
            iid = str(it.get("item_id"))
            totals[iid] = totals.get(iid, 0) + int(it.get("quantity", 0))
    return totals
```

### 4.5 `_shipment_out(header: Dict, items: List, packages: List) -> Dict`

Projects raw DDB rows into the `ShipmentOut` shape. Computes `tracking_url` via
`build_tracking_url` (`app/services/carrier_tracking.py:33`) imported lazily to avoid
circular imports — same lazy-import pattern used in `carrier_tracking.py:153–156`
(`apply_tracking_result` imports `purchase_history` lazily to avoid the circular dep
since `purchase_history.py:14` already imports from `carrier_tracking`):

```python
def _shipment_out(
    header: Dict[str, Any],
    items: List[Dict[str, Any]],
    packages: List[Dict[str, Any]],
) -> Dict[str, Any]:
    from app.services.carrier_tracking import build_tracking_url  # lazy import

    tracking_number = header.get("tracking_number")
    carrier_code = header.get("carrier_code")
    tracking_url = (
        build_tracking_url(carrier_code, tracking_number)
        if (carrier_code and tracking_number)
        else None
    )
    return {
        "shipment_id": header.get("shipment_id"),
        "order_id": header.get("order_id"),
        "user_id": header.get("user_id"),
        "status": header.get("status"),
        "carrier_code": carrier_code,
        "method_code": header.get("method_code"),
        "ship_method_id": header.get("ship_method_id"),
        "tracking_number": tracking_number,
        "tracking_url": tracking_url,        # computed, never stored
        "ship_to_address": header.get("ship_to_address", {}),
        "ship_group_seq": int(header.get("ship_group_seq", 1)),
        "estimated_delivery": header.get("estimated_delivery"),
        "shipped_at": header.get("shipped_at"),
        "delivered_at": header.get("delivered_at"),
        "created_at": int(header.get("created_at", 0)),
        "updated_at": int(header.get("updated_at", 0)),
        "version": int(header.get("version", 1)),
        "purchase_txn_id": header.get("purchase_txn_id"),
        "items": [
            {
                "item_id": it.get("item_id"),
                "sku": it.get("sku"),
                "quantity": int(it.get("quantity", 0)),
            }
            for it in items
        ],
        "packages": [
            {
                "package_seq": pkg.get("package_seq"),
                "weight_oz": int(pkg.get("weight_oz", 0)),
                "length_in": pkg.get("length_in"),
                "width_in": pkg.get("width_in"),
                "height_in": pkg.get("height_in"),
                "contents": list(pkg.get("contents") or []),
                "billed_weight_oz": pkg.get("billed_weight_oz"),
                "created_at": int(pkg.get("created_at", 0)),
            }
            for pkg in sorted(packages, key=lambda p: str(p.get("package_seq", "")))
        ],
    }
```

### 4.6 `create_shipment(...)` — primary entry point

```python
def create_shipment(
    *,
    user_id: str,
    order_id: str,
    ship_group_seq: int,          # 1-based; caller-assigned (e.g. 1 for first group)
    carrier_code: str,
    method_code: str,
    ship_to_address: Dict[str, Any],
    line_items: List[Dict[str, Any]],   # each must have item_id, quantity; sku optional
    ship_method_id: Optional[str] = None,
    purchase_txn_id: Optional[str] = None,
    packages: Optional[List[Dict[str, Any]]] = None,  # SHP-009 extension point
) -> Dict[str, Any]:
```

**Steps:**

1. `_require_enabled()`
2. Validate `ship_group_seq >= 1`.
3. Validate `ship_to_address` has `line1` and `country` keys (per SHP-003 §5.5).
4. Validate `line_items` is non-empty and each element has `item_id` and `quantity >= 1`.
5. Fetch `order = T.orders.get_item(Key={"order_id": order_id}).get("Item")`. If absent → 422 `"Order not found"`.
6. Verify `order.get("user_id") == user_id` (ownership); mismatch → 404 (same 404-not-403 security pattern as `returns_rma.py:188–189`).
7. Fetch `order_items = _get_order_items(order_id)`. If empty → 422 `"Order has no line items"`.
8. Validate each `line_items` entry:
   - `item_id` must exist in `order_items` → 422 `"Item {item_id} not on order"`.
   - `quantity` must be `>= 1`.
9. Fetch `already_shipped = _get_existing_shipped_qty(order_id)`.
10. **Over-ship guard**: for each incoming `(item_id, qty)`, check
    `already_shipped.get(item_id, 0) + qty <= int(order_items[item_id]["quantity"])`.
    Violation → 422 `"Over-ship: item {item_id} would exceed ordered quantity {ordered}"`.
11. Compute `(shipment_id, correlation_id) = _derive_shipment_id(order_id, ship_group_seq)`.
12. `now = now_ts()`.
13. Build and `put_item` on `T.shipments` (idempotent — no condition expression; second
    write with identical content is a no-op in DynamoDB terms).
14. For each `line_item`, build and `put_item` on `T.shipment_items` (idempotent same way).
15. Write one default package row (`package_seq="00001"`) to `T.shipment_packages`.
16. Call `audit_event("shipment.created", user_id, None, outcome="success", shipment_id=..., order_id=..., ship_group_seq=..., carrier_code=..., method_code=..., item_count=len(line_items))`.
17. Return `_shipment_out(header, item_rows, [default_package])`.

### 4.7 `get_shipment(shipment_id: str) -> Optional[Dict[str, Any]]`

```python
def get_shipment(shipment_id: str) -> Optional[Dict[str, Any]]:
    _require_enabled()
    header = T.shipments.get_item(Key={"shipment_id": shipment_id}).get("Item")
    if header is None:
        return None
    items = _load_shipment_items(shipment_id)
    packages = _load_shipment_packages(shipment_id)
    return _shipment_out(header, items, packages)
```

`_load_shipment_items(shipment_id)` and `_load_shipment_packages(shipment_id)` are
private helpers that query `T.shipment_items` and `T.shipment_packages` by PK with
`LastEvaluatedKey` pagination (same pattern as `_get_order_items`).

### 4.8 `list_shipments_for_order(order_id: str) -> List[Dict[str, Any]]`

Uses `GSI_ORDER` (`order_id` / `created_at`):

```python
def list_shipments_for_order(order_id: str) -> List[Dict[str, Any]]:
    _require_enabled()
    out = []
    kwargs: Dict[str, Any] = {
        "IndexName": "GSI_ORDER",
        "KeyConditionExpression": Key("order_id").eq(order_id),
    }
    while True:
        r = T.shipments.query(**kwargs)
        for header in r.get("Items", []):
            sid = header.get("shipment_id")
            items = _load_shipment_items(sid)
            packages = _load_shipment_packages(sid)
            out.append(_shipment_out(header, items, packages))
        lek = r.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
    return out
```

Returns all ship groups for the order; the caller can group by `ship_group_seq` if needed.

### 4.9 `list_shipments_by_status(status: str, limit: int = 100) -> List[Dict[str, Any]]`

Uses `GSI_STATUS` (`status` / `created_at`). Returns headers only (no items/packages) for
the admin queue view — loading children for every row in a status sweep would be
expensive. The admin queue router (future SHP-010+) can call `get_shipment` for the full
record on demand.

```python
def list_shipments_by_status(status: str, limit: int = 100) -> List[Dict[str, Any]]:
    _require_enabled()
    out = []
    kwargs: Dict[str, Any] = {
        "IndexName": "GSI_STATUS",
        "KeyConditionExpression": Key("status").eq(status),
        "Limit": min(limit, 200),
        "ScanIndexForward": False,   # newest-first
    }
    r = T.shipments.query(**kwargs)
    for header in r.get("Items", []):
        out.append(_shipment_out(header, [], []))
    return out
```

Items and packages lists are empty in the abbreviated header-only form; the caller
is expected to call `get_shipment` if full detail is needed.

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent replay: same (order_id, ship_group_seq)

Because `shipment_id = sha256(f"shipment:{order_id}:{ship_group_seq}")[:32]`, two calls
with the same parameters produce the same `shipment_id`. The `T.shipments.put_item`
(no condition expression) will overwrite the row with identical content. Similarly,
`T.shipment_items.put_item` per `item_id` is idempotent. The default package
`put_item(package_seq="00001")` is also idempotent.

**Critical caveat**: if the caller replays with *different* line items or quantities for
the same `(order_id, ship_group_seq)`, the service overwrites the shipment with the new
payload. This is intentional (last-write-wins for idempotent creation, not for
state transitions). Protecting against accidental overwrites of an in-progress shipment
is SHP-010's responsibility (version guard on state transitions).

### 5.2 Over-ship guard ordering

Step 9–10 of `create_shipment` fetches existing shipped quantities *before* any write.
This is not transactional — a concurrent `create_shipment` call for a different
`ship_group_seq` on the same order can race past the guard. This race is acceptable in
practice: over-ship by a race is unlikely (ship groups are typically created serially),
and the hard limit is enforced downstream by inventory (SHP-009 / OFBiz INFRA). If
strict transactional safety is required in the future, a DDB transaction (`transact_write`)
covering the `shipments` + `shipment_items` writes with a conditional can be added
without changing the service interface.

### 5.3 Empty `line_items` in the request

`ShipmentIn.line_items` is declared `Field(min_length=1)` in SHP-003
(`models.py` — `ShipmentIn`), so Pydantic rejects empty lists at the router layer
before the service is called. The service layer adds a redundant check at step 4 as a
defence-in-depth guard for callers that bypass the router (e.g. direct unit tests).

### 5.4 Partial-shipment support (quantity < ordered)

The over-ship guard enforces `already_shipped + new_qty ≤ ordered_qty`. It does **not**
enforce `already_shipped + new_qty == ordered_qty`. This intentionally allows partial
fulfilment: ship group 1 might ship items 1–3, ship group 2 ships item 4 later. The
"fulfilment complete" state (all ordered lines shipped) is tracked separately by a
status update (SHP-010) that computes `sum(shipped_qty) == sum(ordered_qty)` for the
order.

### 5.5 Ship-to-address validation

`create_shipment` validates that `ship_to_address` contains non-empty `line1` and
`country` keys. Missing keys → 422. This follows the minimum-viable address validation
described in SHP-003 §5.5. Full postal-code / region validation is deferred.

### 5.6 Tracking URL: computed, never stored

`_shipment_out` calls `build_tracking_url(carrier_code, tracking_number)` at read time.
The result is **not** persisted to `T.shipments`. This follows the identical approach in
`purchase_history.py:389–394`:

```python
# Enrich shipping with tracking URL (computed, not stored)
if info.get("shipping"):
    carrier = info["shipping"].get("carrier")
    tracking_number = info["shipping"].get("tracking_number")
    if carrier and tracking_number:
        info["shipping"]["tracking_url"] = build_tracking_url(carrier, tracking_number)
```

This means tracking URLs automatically update if `CARRIER_TRACKING_URLS` changes
without a data migration.

### 5.7 Default package at creation

SHP-008 writes exactly one `shipment_packages` row at creation (`package_seq="00001"`,
`weight_oz=0`, `contents=[]`). SHP-009 will populate dimensions and weight, and may
add additional package rows. SHP-008 must NOT pre-populate `contents` from `shipment_items`
because SHP-009 owns that assignment (packed items are a separate operation from "what's
in this shipment").

### 5.8 version field and SHP-010 compatibility

Every `shipments` row is written with `version=1`. SHP-010 will use:

```python
T.shipments.update_item(
    Key={"shipment_id": shipment_id},
    UpdateExpression="SET #s = :s, updated_at = :u, version = version + :one",
    ConditionExpression="version = :v",
    ExpressionAttributeValues={":v": current_version, ":one": 1, ...},
)
```

This is the exact pattern from `purchase_history.py:414–430` (update_shipping version guard — VERIFIED).
SHP-008 establishes the initial `version=1` at creation so SHP-010 can safely use
`":v": 1` on the first transition.

### 5.9 Ownership enforcement vs. 404 vs. 403

If `order.get("user_id") != user_id`, the service returns 404 ("Order not found") rather
than 403 ("Forbidden"). This is the security-through-obscurity pattern used in
`returns_rma.py:188–190`: leaking that an order exists for another user is a privacy
violation; returning 404 prevents enumeration. Admin/root callers that need to create
shipments for any order bypass this check via a separate admin-scoped service function
(not in SHP-008 scope, but the gate is in the router via `require_admin_session`).

### 5.10 `ship_group_seq` assignment

`ship_group_seq` is caller-supplied (1-based integer). The typical caller (a checkout
router or admin tool) assigns seq=1 for the first and only group, seq=2 for a split
shipment, etc. The service does NOT auto-assign `seq`; requiring the caller to supply it
keeps `create_shipment` idempotent for any seq. The caller can enumerate
`list_shipments_for_order` to determine the next available seq before calling
`create_shipment` for a new group.

### 5.11 `ship_method_id` FK

`ship_method_id` is an optional opaque FK string of the form `{carrier_id}#METHOD#{method_code}`
(defined in SHP-004). SHP-008 stores it as-is without validation against
`T.shipping_carriers`. The FK is advisory (for display and future rate-reconciliation);
no referential integrity is enforced at the DDB level.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Zero `dev_mode` branches

`app/services/shipments.py` contains no `if S.dev_mode` conditionals. All DDB calls
use `T.shipments`, `T.order_items`, etc. — the same handles in dev (moto-backed
DDB Local) and prod (real DynamoDB). The moto test environment exercises the exact same
code path as production (SECOPS-007 parity).

### 7.2 Idempotency design

- **`create_shipment` for same `(order_id, ship_group_seq)`**: deterministic
  `shipment_id` + unconditional `put_item` → idempotent. Second call with same
  payload produces the same row. Second call with different payload overwrites the row
  (intentional: creation-time idempotency, not mutation protection — that is SHP-010's
  version guard).
- **`shipment_items` writes**: keyed by `(shipment_id, item_id)` — idempotent per item.
- **Default package write**: keyed by `(shipment_id, "00001")` — idempotent.
- **Audit event**: `audit_event` is fire-and-forget. A replay will emit a second audit
  event — this is acceptable and consistent with the pattern in
  `commerce_order_service.py:106`.

### 7.3 No billing ledger entries

`create_shipment` makes no calls to `billing_shared.new_ledger_entry`. No money moves
at shipment creation time. Shipping cost collection (if any) is a future SHP-013+
concern and must reuse `new_ledger_entry` + provider attribution when implemented.

### 7.4 Security

- **Ownership check** (step 6): `order.get("user_id") == user_id` → 404 on mismatch,
  preventing cross-user shipment creation and order enumeration.
- **Ship-to-address PII**: `ship_to_address` is stored as a DDB map and included in
  `ShipmentOut`. It must NOT be logged at INFO/DEBUG level. The `audit_event` call
  (step 16) must not include `ship_to_address` in `**fields`; only structural fields
  (`order_id`, `shipment_id`, `ship_group_seq`, `item_count`) are audited.
- **CSRF**: enforced by the router (SHP-010 will add `POST /ui/shop/shipments`) via
  `require_ui_session` — the session dep enforces CSRF on cookie non-GET requests
  (CLAUDE.md §Auth). The service itself is CSRF-agnostic.
- **Role gate**: admin-only shipment creation (e.g. warehouse admin creating a shipment
  on behalf of a buyer) is enforced by the router via `require_admin_session`; the
  service accepts `user_id` as a parameter and applies only ownership-level checks.

## 10. Open Questions / Assumptions

**OQ-1 (`ship_group_seq` numbering)**: The spec assumes `ship_group_seq` is a
caller-supplied 1-based integer (not auto-assigned by the service). This preserves
idempotency but requires the calling router to determine the next available seq (e.g.
`len(list_shipments_for_order(order_id)) + 1` or just `1` for a single-group order).
Verify that this is the intended UX — if the storefront uses SHP-008 directly from a
checkout flow, it may be simpler to auto-assign and use a UUID-based `shipment_id`
instead of the deterministic sha256 approach.

**OQ-2 (Over-ship race condition)**: The over-ship guard (step 9–10) is not
transactional. Two concurrent calls with `ship_group_seq=2` and `ship_group_seq=3`
on the same order could both pass the guard and both write, each shipping the full
quantity. If the order volume warrants it, a DynamoDB transaction
(`transact_write` with a `ConditionCheck` on the order) can be added without changing
the function signature. Assume acceptable for the current scope.

**OQ-3 (`version` initial value)**: The spec assumes `version=1` at creation. If SHP-010
uses `ConditionExpression="attribute_not_exists(version) OR version = :v"` to handle
old rows (pre-SHP-008) that might not have a `version` attribute, the initial value
of `1` vs `0` needs to be consistent. Clarify with SHP-010 implementer.

**OQ-4 (`ship_to_address` minimum validation)**: The spec validates only `line1` and
`country` presence. If address normalisation (e.g. `app/core/normalize.py`) applies to
shipping addresses, add a call to the normaliser for `postal_code` consistency.
Currently assumed not needed at creation time.

**OQ-5 (`purchase_txn_id` linkage)**: `purchase_txn_id` is optional at creation time.
The linkage to `purchase_transactions` (the legacy flat-sub-record model in
`purchase_history.py`) is advisory. The exact moment this FK gets populated (at
checkout? at shipping confirmation?) is not defined in SHP-008's scope. Assume callers
populate it when known, else leave `None`.

**OQ-6 (`list_shipments_by_status` pagination)**: The current design returns at most
`min(limit, 200)` results with no cursor. If the admin queue grows beyond 200 entries
in a given status, a pagination cursor (`LastEvaluatedKey` encoded via
`app/core/cursor.py`) will be needed. Deferred to SHP-010/011 when the admin queue
router is built.

**OQ-7 (Cancelled shipments and over-ship accounting)**: If a shipment is later
cancelled (SHP-010 transition to `cancelled`), its shipped quantities should be
subtracted from `_get_existing_shipped_qty` to allow re-shipping those items. The
current `_get_existing_shipped_qty` sums ALL existing shipments including cancelled
ones. This must be clarified: should cancelled shipments be excluded from the
over-ship check? Assumed YES — add a `FilterExpression="NOT #s = :cancelled"` to
the GSI_ORDER query for `shipment_ids` collection.
