# OFB-019 — Pricing/promotions rules engine

## 1. Summary & Goal

OFB-019 introduces a first-class **pricing rules engine** (`app/services/pricing_rules.py`) that extends the existing flat promo-code model with three new discount computation strategies: **tiered** (quantity-breakpoint unit-price tables), **bulk** (per-unit discount above a quantity threshold), and **conditional** (cart-total threshold, category/SKU scope, customer subscription-tier guard). It defines rule precedence and stacking semantics (best-deal-wins vs. stackable), and integrates those semantics into the existing `validate_promo_code` path so that a promo code can carry a rule reference. All existing percentage / fixed_amount / free_trial codes remain byte-for-byte unchanged when the flag is off.

**Scope of this ticket:** the rule-engine service and admin CRUD API only. Hooking the engine into `purchase_cart` and the cart-total endpoint is OFB-020. The admin UI is OFB-021.

### 3.2 Rule config payloads (`rule_config` map)

**Tiered** (`rule_type = "tiered"`):
```json
{
  "tiers": [
    {"min_qty": 1,  "max_qty": 4,  "unit_price_cents": 1000},
    {"min_qty": 5,  "max_qty": 9,  "unit_price_cents": 850},
    {"min_qty": 10, "max_qty": null, "unit_price_cents": 700}
  ]
}
```
Tiers must be non-overlapping, cover `min_qty >= 1`, sorted ascending. The last tier must have `max_qty = null` (unbounded). Applied per individual line item using its `quantity`; the total discount is `sum((original_unit_price - tier_unit_price) * qty)` across all in-scope items.

**Bulk** (`rule_type = "bulk"`):
```json
{
  "threshold_qty": 5,
  "discount_type": "percentage" | "fixed_per_unit",
  "discount_value": 15
}
```
Applies only to line items whose `quantity >= threshold_qty`. Discount is `discount_value%` of `unit_price_cents * qty` (percentage) or `discount_value cents * qty` (fixed_per_unit).

**Conditional** (`rule_type = "conditional"`):
```json
{
  "min_cart_total_cents": 5000,
  "discount_type": "percentage" | "fixed_amount",
  "discount_value": 10
}
```
Fires when the pre-discount cart total (sum of in-scope items) meets `min_cart_total_cents`. Discount applied to the entire in-scope subtotal.

### 3.3 Promo code linkage

An existing `PromoCodes` META record (`T.promo_codes`, `pk=PROMO#{code_id}`, `sk=META`) gains two optional new attributes:
- `pricing_rule_id` (S) — reference to the `PricingRules` record.
- `pricing_rule_stacking_mode` (S) — echo of the rule's `stacking_mode` for fast read without a second DDB lookup.

These are **additive** attributes; codes without them behave identically to today.

## 5. Detailed Behavior & Edge Cases

### 5.1 Tiered discount computation

For each in-scope cart item, look up the applicable tier by `item.quantity`:
- Find the unique tier where `tier.min_qty <= quantity` and (`tier.max_qty is null` or `quantity <= tier.max_qty`).
- If no tier covers the quantity (gap in config), treat as no discount for that item (never error at eval time).
- `item_discount = (original_unit_price - tier.unit_price_cents) * quantity`.
- Negative item discounts (tier price > original) are floored to 0.

### 5.2 Bulk discount computation

For each in-scope cart item where `quantity >= threshold_qty`:
- `percentage`: `discount = floor(unit_price_cents * quantity * discount_value / 100)`.
- `fixed_per_unit`: `discount = min(discount_value * quantity, unit_price_cents * quantity)`.
Items with `quantity < threshold_qty` are excluded; the rule reports `applied=False` for those items specifically.

If **no** in-scope items meet the threshold, the entire rule result is `applied=False, reason_skipped="quantity_below_threshold"`.

### 5.3 Conditional discount computation

1. Sum `line_total_cents` of all in-scope items → `scope_subtotal`.
2. If `scope_subtotal < min_cart_total_cents`: `applied=False, reason_skipped="cart_total_below_threshold"`.
3. Otherwise apply `discount_type` to `scope_subtotal` (same arithmetic as `_calculate_discount`).

### 5.4 Stacking and precedence

Rules are evaluated in priority order (ascending integer). The `apply_stacking` function:
1. Groups results by `stacking_mode`.
2. From `best_deal_wins` group: selects the result with the highest `discount_cents`; ties broken by lowest `priority` integer (the rule declared higher priority wins the tiebreak).
3. All `stackable` results are summed.
4. Combined discount = winner_discount + sum_of_stackable_discounts.
5. `final_cart_cents = max(0, cart_total_cents - combined_discount)`.

A rule with `applied=False` contributes 0 to all pools. It is still included in `per_rule_breakdown` for observability.

### 5.5 Integration into validate_promo_code

`validate_promo_code` (`app/services/promo_codes.py:239`) currently accepts `item_price_cents` but not `cart_items`. The integration shim is applied via a **new overloaded helper** that wraps the existing function rather than modifying it:

This calls the unmodified `promo_codes.validate_promo_code` first. If that returns `valid=True` and `promo["pricing_rule_id"]` is non-empty and `S.pricing_rules_enabled`, it calls `enrich_validate_result_with_rule` to replace the discount fields. ### 5.6 Scope filtering

- `scope_category_ids`: a non-empty set means "only apply to items whose `category_id` is in this set". An empty set means "all items".
- `scope_skus`: same semantics on `sku`.
- When both are non-empty, items matching **either** condition are in scope (union, not intersection) — consistent with OFBiz ProductPromo scope semantics.
- `scope_creator_user_id`: when set, the rule only activates for carts where `_resolve_cart_creator(items)` returns this value.

### 5.7 Subscription tier gate

If `required_subscription_plan_ids` is non-empty:
1. Query `T.subscriptions` for `SUBSCRIBER#{user_sub}` items with `sk` beginning `SUB#` (same pattern as `subscription_access.has_active_subscription`, `app/services/subscription_access.py:57–59`).
2. Check whether any active/trialing/past_due subscription row has `plan_id` in `required_subscription_plan_ids`.
3. If no matching active subscription: `applied=False, reason_skipped="subscription_tier_not_met"`.

### 5.8 Expiry and use-limit guards

These mirror `validate_promo_code`:
- If `expires_at > 0` and `expires_at < now_ts()`: rule is treated as inactive (excluded by `resolve_applicable_rules` before computation).
- `max_uses > 0` and `current_uses >= max_uses`: excluded.
- Per-user: if `max_uses_per_user > 0`, count `AUDIT#` rows for this user against this rule in `T.pricing_rules`. Uses are atomically incremented by OFB-020's `record_rule_redemption`.

### 5.9 Owner guard on mutations

`update_rule` and `deactivate_rule` fetch the META item and verify `item["created_by"] == creator_id` before writing. Admin/root may bypass this check (checked via the admin endpoint which uses `require_admin_or_root`).

### 5.10 Config validation at creation time

`create_rule` calls the appropriate `_validate_*_config` helper before writing to DDB. Validation failures return `(None, error_message)` without writing anything. The router converts this to HTTP 422.

### 5.11 Promo code linkage guard

If `linked_promo_code_id` is supplied:
- Fetch the promo record; verify `item["creator_user_id"] == creator_id`.
- Verify the promo record does not already have a `pricing_rule_id` (one-to-one linkage).
- Back-patch `T.promo_codes` item with `pricing_rule_id = rule_id` and `pricing_rule_stacking_mode = stacking_mode` inside the same logical transaction (two separate `update_item` calls — no DDB transactions required since rule creation is not idempotent-sensitive at the promo level; if the rule write succeeds but the promo back-patch fails, the rule will exist but not be reachable via code validation, leaving it orphaned; this is acceptable at P0 MVP and noted in Open Questions).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

All DDB reads/writes (`T.pricing_rules`, `T.promo_codes`) use the same boto3 call path in dev (moto-backed DDB Local, port 8001) and prod (real DynamoDB). There is no `if S.dev_mode` branch in the service layer. The subscription-tier gate calls `T.subscriptions` identically in both environments.

### 7.2 Idempotency of rule creation

Rule creation is intentionally non-idempotent (each call mints a new `rule_id`). Admin-level dedup is enforced by name uniqueness **per creator** via a pre-write GSI scan (ByCreatorCreatedAt filtered on name) — enforced as a soft warning, not a hard 409, because two rules may legitimately share a name for A/B testing.

### 7.3 Atomic redemption counting

`redeem_rule(rule_id, user_sub, original_price_cents, final_price_cents, cart_id)`
(called by OFB-020 at purchase time, not by OFB-019) uses a conditional `update_item`
identical to `redeem_promo_code`:
```python
ConditionExpression=Attr("current_uses").lt(max_uses)  # when max_uses > 0
```
This is the standard atomic-increment pattern (`app/services/promo_codes.py:416–433`,
`ConditionExpression=Attr("current_uses").lt(max_uses)` at line 421).

NOTE: the canonical export name is `redeem_rule` (per DECISIONS D2 / ESCALATIONS §A
row 25). The previous name `record_rule_redemption` used in early drafts is replaced
throughout. OFB-019 exports `redeem_rule`; OFB-020 imports and calls `redeem_rule`.

### 7.4 Discount cap / negative-total guard

`apply_stacking` always caps `total_discount_cents <= cart_total_cents`. A cart can be discounted to 0 but never below.

### 7.5 Input sanitization

- `name`, `description` are stripped of leading/trailing whitespace.
- `scope_category_ids` / `scope_skus` / `required_subscription_plan_ids` are deduplicated before storage.
- `rule_config` is validated by the type-specific validator before storage; unrecognized extra keys are dropped (do not silently persist).
- Priority clamped to [1, 1000]; priority 0 is not allowed (would overflow integer sort in certain comparisons).

### 7.6 Auth

- Create/update/delete: `require_ui_session`; ownership enforced by `created_by == ctx["user_sub"]`.
- Admin list: `require_admin_or_root` (`app/auth/policy.py:67`).
- Preview endpoint: `require_ui_session`; no cart-ownership check is needed (preview is read-only and uses caller-supplied sample data).

## 10. Open Questions / Assumptions

1. **Assumption: OFB-002 ships first or in the same PR.** If OFB-002 has not added `PRICING_RULES_ENABLED` to settings, OFB-019 adds it. If both tickets add it simultaneously, the second merge wins (idempotent). This needs coordination.

2. **Assumption: Promo code linkage is one-to-one (one rule per code, one code per rule).** The spec enforces this with a pre-write guard. If a creator legitimately needs to link the same rule to multiple codes (e.g., influencer-specific codes that all compute the same tiered discount), this constraint must be relaxed to one-to-many (rule→codes). Leaving as one-to-one for MVP.

3. **Open question: Should `scope_creator_user_id` be redundant with the promo code's own `creator_user_id` check?** Currently, creator-scoped rules and creator-scoped promo codes both filter on `creator_user_id`. If a platform-wide rule (no `scope_creator_user_id`) is attached to a creator's promo code, the creator check still applies via the promo validation path. Confirm whether platform-admin rules (no creator scope) should be attachable to any promo code or require `scope_creator_user_id = ""` as "platform admin only".

4. **Open question: Atomicity of rule-creation + promo-code back-patch.** As noted in §5.11, if the DDB `update_item` on the PromoCodes item fails after the rule META item is already written, the rule is orphaned (exists in PricingRules but not reachable via promo validation). For MVP this is acceptable. Production hardening should use a DDB TransactWriteItems (2-item transaction: PricingRules put + PromoCodes update).

5. **Assumption: `stacking_mode` is a per-rule attribute, not a global platform setting.** This means a creator can mix stackable and best-deal-wins rules in the same cart evaluation. The `apply_stacking` function handles this correctly, but it creates a UX complexity where customers cannot easily predict the applied discount. OFB-021 (admin UI) should display a clear preview.

6. **Assumption: `record_rule_redemption` (atomic use-counter increment) lives in OFB-020, not OFB-019.** OFB-019 defines the data model and computation engine only; redemption accounting at purchase time is OFB-020's responsibility. Tests in OFB-019 verify the guards (`max_uses` exclusion) but do not increment counters.

7. **Open question: Should `resolve_applicable_rules` scan all active rules or only explicit IDs?** For the promo-code-linked path, only the single linked rule ID is evaluated. For a future "auto-apply rules" path (not yet a ticket), the GSI scan would be needed. OFB-019 implements both paths but the auto-apply path is not wired at cart evaluation until a follow-up ticket explicitly requests it.

8. **Assumption: `required_subscription_plan_ids` uses `plan_id` from subscription rows, not `tier_id` from `admin_subscription_tiers`.** The `plan_id` field on `SUB#` records in `T.subscriptions` is used (per `app/services/admin_subscription_tiers.py:75`). If the platform uses a different subscription-tier identifier for gating, this assumption must be revised before OFB-019 ships.
