# PUR-004 — Supplier-product pricing (supplier↔SKU price / lead-time / MOQ)

**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days  
**Milestone:** 2 — Supplier & Supplier-Product Model  
**Depends on:** PUR-003

---

## 1. Summary & Goal

PUR-004 introduces `app/services/supplier_products.py`, which manages the many-to-many relationship between suppliers and catalog/inventory SKUs. Each record captures a supplier's quoted `unit_cost_cents`, `currency`, `lead_time_days`, `min_order_qty` (MOQ), the vendor's own part number (`supplier_sku`), and a `preferred` flag that marks the operator's primary source for a given SKU.

Four service functions are required:

- `upsert_supplier_product(supplier_id, sku, ...)` — idempotent create-or-replace, keyed on the (`supplier_id`, `sku`) pair.
- `get_supplier_product(supplier_id, sku)` — point read.
- `list_products_for_supplier(supplier_id)` — all SKUs sourced from one supplier.
- `list_suppliers_for_sku(sku)` — all suppliers offering a given SKU, ordered cheapest-first via `GSI_SKU` (ascending `unit_cost_cents`). This is the primary input to the PUR-011 reorder-suggestion engine.

SKU validation is enforced at upsert time: the provided string must either resolve as an inventory record (`inventory.get_inventory(sku)` returning non-None) or as a catalog item (`catalog:{item_id}` form where `item_id` exists in `T.catalog`). An unknown SKU raises `HTTPException(422)`.

This ticket ships no router (that is PUR-005) and no Pydantic models (also PUR-005). It is a pure service-layer module that PUR-005 imports and wraps.

## 2. Context & Current State

### 2.1 Existing OFBiz service pattern

`app/services/inventory.py` is the direct structural template:

- **Flag guard** at `inventory.py:50–56` — `_flag_on()` reads `getattr(S, "inventory_reservations_enabled", False)` and `_require_enabled()` raises `HTTPException(404)` when false. PUR-004 copies this verbatim, checking `S.purchasing_scm_enabled` instead.
- **`_audit` helper** at `inventory.py:92–98` — best-effort fire-and-forget wrapper around `alerts.audit_event`; swallows all exceptions. PUR-004 copies this pattern for `supplier_product.upsert` and `supplier_product.delete` events.
- **`_to_int` coercion** at `inventory.py:67–73` — coerces `Decimal` (DynamoDB numeric type) to `int`. PUR-004 uses the same pattern for `unit_cost_cents`, `lead_time_days`, `min_order_qty`, `created_at`, `updated_at`.
- **GSI-paginate loop** at `inventory.py:318–333` — `list_low_stock` loops with `ExclusiveStartKey` until `LastEvaluatedKey` is absent. `list_suppliers_for_sku` and `list_products_for_supplier` use the same loop.

### 2.2 Table established by PUR-002

`supplier_products` table (established in PUR-002, `scripts/local-ddb-init.py` after the `returns` block at `:2492`):

- **PK:** `supplier_id` (S), **SK:** `sk` = `SKU#{sku}` (S)
- **GSI_SKU:** partition `sku` (S), sort `unit_cost_cents` (N), `attr_types={"unit_cost_cents": "N"}`
- Handle: `T.supplier_products` (appended to `app/core/tables.py` after `returns: Any` at `:319`).

PUR-003 establishes `T.suppliers` and the supplier existence guarantee. PUR-004 does **not** re-validate supplier existence at upsert time (the supplier must be active, but validating that would introduce a read on the hot path; this is an assumption documented in section 10).

### 2.3 SKU validation sources

The ticket specifies validation against two sources:

1. **Inventory table** — `inventory.get_inventory(sku)` at `app/services/inventory.py:150–155`. Returns `None` when no inventory record exists for the string. The inventory table has a composite key: PK=`sku` (S) and SK=`location_sk` = `LOC#{location_id}` (`inventory.py:119`, `_get_raw`). `get_inventory` defaults `location_id` to `DEFAULT_LOCATION="warehouse"` (`inventory.py:43`, `:150`). A SKU is considered valid if it has a record at the warehouse location — SKUs that exist only at non-default locations will not be found by this check and will be treated as unknown. Any SKU where `set_on_hand` has been called (at the default warehouse location) is a valid SKU.

2. **Catalog table** — The catalog in `app/core/tables.py:351` (`T.catalog`) is the `shopping_catalog` DynamoDB table. Catalog items carry an `item_id` attribute. The shopping-cart convention (`app/services/shoppingcart.py:391`) forms catalog SKUs as `f"catalog:{item_id}"`. When the incoming `sku` starts with `"catalog:"`, PUR-004 splits off the `item_id` suffix and queries `T.catalog` via the `ByItemId` GSI using the same pattern as `catalog._find_item_by_id` at `app/routers/catalog.py:702–718`. A match (with `entity="item"` filter) confirms the SKU is valid.

Both lookups are needed because a supplier may be linked to a raw inventory SKU (e.g., `"WIDGET-A"`) or to a catalog item (`"catalog:01HXYZ..."`). Any other string that matches neither → `HTTPException(422, "Unknown SKU")`.

### 2.4 Deterministic-id pattern not applicable here

Unlike `supplier_id` (PUR-003) or `po_id` (PUR-006), a supplier-product row has no separate surrogate ID — its identity is the (`supplier_id`, `sku`) composite key expressed as `PK=supplier_id, SK=SKU#{sku}`. `put_item` without a condition expression is an upsert by definition (overwrites existing item at same key), which is both idempotent and the desired semantics: re-upserting with updated pricing replaces the previous pricing atomically.

### 2.5 Settings and flag

`S.purchasing_scm_enabled` is added by PUR-002 at `app/core/settings.py` (after line `:847`). PUR-004 reads it via `_flag_on()` / `_require_enabled()`, raising 404 when false, exactly as `inventory.py:54–56`.

## 3. Data Model

The `supplier_products` table is established by PUR-002. PUR-004 only defines the read/write pattern against it. No new tables are introduced by this ticket.

### 3.1 `supplier_products` table (recap for implementors)

| Attribute | Key role | DDB type | Description |
|---|---|---|---|
| `supplier_id` | PK (hash) | S | Foreign key into `T.suppliers` |
| `sk` | Sort key | S | `SKU#{sku}` |
| `sku` | GSI_SKU partition | S | The SKU string (raw inventory SKU or `catalog:{item_id}`) |
| `unit_cost_cents` | GSI_SKU sort key | **N** | Supplier's quoted unit price in cents |
| `currency` | attribute | S | ISO-4217 currency code, e.g. `"USD"` |
| `lead_time_days` | attribute | **N** (stored as int) | Typical supplier lead time in days |
| `min_order_qty` | attribute | **N** (stored as int) | Minimum order quantity (MOQ) |
| `supplier_sku` | attribute | S | Vendor's own part number (may differ from our SKU) |
| `preferred` | attribute | BOOL | True = this supplier is the preferred source for this SKU |
| `created_at` | attribute | **N** | Unix timestamp of first upsert (`now_ts()`) |
| `updated_at` | attribute | **N** | Unix timestamp of most recent upsert (`now_ts()`) |

**Note on `created_at` preservation:** `upsert_supplier_product` uses unconditional `put_item`. The caller must pass the original `created_at` when updating, or the service must read before write to preserve it. Section 5.3 below specifies the read-before-write strategy.

**GSI projection:** `GSI_SKU` projects ALL. `list_suppliers_for_sku` needs `supplier_id`, `unit_cost_cents`, `lead_time_days`, `min_order_qty`, `preferred`, and `currency` — all present in the GSI projection.

### 3.2 `attr_types` requirement

`GSI_SKU` sorts on `unit_cost_cents`, a numeric integer. The `TableDef` in `scripts/local-ddb-init.py` (PUR-002) must declare `attr_types={"unit_cost_cents": "N"}`. If omitted, DynamoDB stores `unit_cost_cents` as a String and ascending cost ordering breaks silently at query time. This is already specified in PUR-002's `TableDef` excerpt; it is restated here as a cross-check for the implementor.

#### SKU validation helper

```python
def _validate_sku_exists(sku: str) -> None:
    """Raise HTTPException(422) if sku is not known in inventory or catalog.

    Two lookup paths:
    1. Raw inventory SKU  — inventory.get_inventory(sku) returns non-None.
    2. Catalog SKU        — sku starts with "catalog:" and the item_id suffix
                            resolves in T.catalog via the ByItemId GSI
                            (same query as catalog._find_item_by_id at
                            app/routers/catalog.py:702–718).
    """
    from app.services import inventory as inv
    from boto3.dynamodb.conditions import Key

    # Path 1: inventory record exists
    if inv.get_inventory(sku) is not None:
        return

    # Path 2: catalog:{item_id} form
    if sku.startswith("catalog:"):
        item_id = sku[len("catalog:"):]
        if item_id:
            resp = T.catalog.query(
                IndexName="ByItemId",
                KeyConditionExpression=Key("item_id").eq(item_id),
                FilterExpression="entity = :ent",
                ExpressionAttributeValues={":ent": "item"},
                Limit=1,
            )
            if resp.get("Items"):
                return

    raise HTTPException(status_code=422, detail=f"Unknown SKU: '{sku}'")
```

Note: `T.catalog` is always available via `app/core/tables.py:351` regardless of the `purchasing_scm_enabled` flag. The SKU validation uses `T.catalog` (the `shopping_catalog` table) for the catalog path and the `inventory` service (which reads `T.inventory`) for the inventory path. If `S.inventory_reservations_enabled` is false, `inventory.get_inventory` returns `None` for all SKUs (the inventory table is empty), so only the catalog path will match for catalog-prefixed SKUs.

## 5. Detailed Behavior & Edge Cases

### 5.1 `upsert_supplier_product` — validation order

1. `_require_enabled()` — raise 404 if flag off.
2. Validate `unit_cost_cents >= 0` — raise 422 if negative.
3. Validate `min_order_qty >= 1` — raise 422 if less than 1.
4. `_validate_sku_exists(sku)` — raise 422 if unknown SKU.
5. Read existing item (read-before-write for `created_at` preservation).
6. Write `put_item` with merged `created_at` (see section 5.3).
7. `_audit("supplier_product.upsert", actor, ...)`.

### 5.2 `list_suppliers_for_sku` — cheapest-first ordering

`GSI_SKU` has partition key `sku` and sort key `unit_cost_cents` (N). Querying with `ScanIndexForward=True` returns rows in ascending `unit_cost_cents` order, exposing the cheapest supplier first. This is the guaranteed ordering for the PUR-011 reorder suggestion engine:

```python
resp = T.supplier_products.query(
    IndexName="GSI_SKU",
    KeyConditionExpression=Key("sku").eq(sku),
    ScanIndexForward=True,   # ascending unit_cost_cents
    Limit=limit,
    **({} if start_key is None else {"ExclusiveStartKey": start_key}),
)
items = [_record_out(it) for it in resp.get("Items", [])]
lek = resp.get("LastEvaluatedKey")
return items, lek
```

If two suppliers have identical `unit_cost_cents`, DynamoDB breaks the tie by `supplier_id` (GSI secondary sort is undefined; tie-breaking within a cost tier is not guaranteed). PUR-011 should apply a secondary sort by `lead_time_days` in application code after fetching the GSI results.

### 5.3 Read-before-write for `created_at` preservation

`put_item` in DynamoDB replaces the entire item — it does not merge. To preserve `created_at` on re-upsert, the service reads the existing item before writing:

```python
existing = T.supplier_products.get_item(
    Key={"supplier_id": supplier_id, "sk": _sk(sku)}
).get("Item")
created_at = _to_int(existing.get("created_at")) if existing else now_ts()
```

The full item is then written with the original `created_at` and a fresh `updated_at = now_ts()`. This is a two-round-trip upsert, not atomic. This is acceptable because:
- Two concurrent upserts for the same `(supplier_id, sku)` key are idempotent by key — the last writer wins on the DDB item.
- The only hazard is a tiny window where two concurrent upserts both read `existing=None` and both set `created_at = now_ts()`. Both will write slightly different timestamps, but both timestamps are "now", making the difference negligible for a creation timestamp. A conditional expression (`attribute_not_exists(supplier_id) OR ...`) would be more complex and buys little here.

### 5.4 `preferred` flag semantics

`preferred=True` marks one supplier as the operator-preferred source for a SKU. The service does not enforce uniqueness of `preferred=True` across suppliers for a given SKU — multiple suppliers may have `preferred=True` simultaneously. PUR-011's reorder suggestion engine should filter for `preferred=True` as a tie-breaker after cost and lead-time sorting.

Clearing the preferred flag on one supplier when setting it on another is a caller responsibility (the PUR-005 router endpoint may implement this convenience, but the service layer does not).

### 5.5 SKU validation: `catalog:` prefix normalization

The `catalog:` prefix is case-sensitive. Callers should not uppercase the prefix. The `item_id` portion must match exactly as stored in `T.catalog` (the `item_id` attribute is a `ulid_like()` string from `app/routers/catalog.py:52`, which is timestamp + lowercase hex UUID). The `ByItemId` GSI query is an equality match on the exact string.

### 5.6 SKU validation with `inventory_reservations_enabled=False`

When `S.inventory_reservations_enabled` is False, `T.inventory` exists (it is always wired) but is empty — no `set_on_hand` calls have been made and the table has no rows. `inventory.get_inventory(sku)` always returns `None` in this state. Therefore:

- Raw inventory SKUs (non-`catalog:` prefixed) will **always** fail validation when the inventory flag is off, even if the operator intends to use them.
- `catalog:` prefixed SKUs will still validate correctly via the catalog path.

This is intentional: if inventory reservations are not enabled, there are no tracked inventory SKUs to link. Operators who want to link suppliers to non-catalog SKUs must first enable inventory and call `set_on_hand`. This is documented in the Open Questions section.

### 5.7 `delete_supplier_product` behavior

`delete_item` in DynamoDB succeeds silently whether or not the item exists. To provide a useful `False` return value for "not found", the service does a `get_item` before deleting:

```python
existing = get_supplier_product(supplier_id, sku)
if existing is None:
    return False
T.supplier_products.delete_item(Key={"supplier_id": supplier_id, "sk": _sk(sku)})
_audit("supplier_product.delete", actor, supplier_id=supplier_id, sku=sku)
return True
```

### 5.8 Pagination cursor encoding

`list_products_for_supplier` and `list_suppliers_for_sku` return raw `LastEvaluatedKey` dicts, not the encoded cursor from `app/core/cursor.py`. The PUR-005 router wraps these in the standard cursor encoding using `encode_cursor` / `decode_cursor` from `app/core/cursor.py` (the pattern used in e.g. `app/routers/profile.py:554,620`) when exposing them over HTTP. Note: `app/routers/inventory.py` does not use cursor encoding (its `list_low_stock` endpoint fetches all items internally and returns them without pagination). The service layer returns the raw dict for simplicity and testability.

### 5.9 No billing interaction

PUR-004 is a pure pricing catalogue — it stores what a supplier charges but does not initiate any payment. Money-out (AP payment on receipt) is handled by PUR-012 which calls `billing_shared.new_ledger_entry`. PUR-004 does not touch the `billing` table.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

`T.supplier_products` wraps `ddb.Table("supplier_products")` via `_safe_table`. In dev, `ddb` points to DynamoDB Local (port 8001, intercepted by moto in tests). In prod, `ddb` is the real boto3 DynamoDB resource. No `dev_mode` branch exists in `supplier_products.py` — identical code both environments.

`_validate_sku_exists` queries `T.catalog` (the `shopping_catalog` DynamoDB table) and calls `inventory.get_inventory`. Both of these operations use the same DDB endpoint abstraction. No mock-specific logic is needed.

### Idempotency

`upsert_supplier_product` is idempotent on (`supplier_id`, `sku`): calling it N times with the same arguments produces exactly one item in DynamoDB (unconditional `put_item` at a fixed key). Each call updates `updated_at` but leaves the logical content unchanged if arguments are identical. This satisfies the acceptance criterion "Upsert is idempotent on (supplier_id, sku); re-upsert updates price/lead-time in place."

`delete_supplier_product` is idempotent: calling it on an already-deleted record returns `False` without error.

### Security

- No HTTP endpoints are introduced by this ticket. Authentication and authorization are the responsibility of PUR-005.
- `unit_cost_cents` is stored as an integer in cents; no float arithmetic is performed, eliminating precision errors.
- `currency` is stored as-is (no normalization). PUR-005 should validate it is a 3-letter ISO-4217 code in the Pydantic model.
- The `preferred` flag is a boolean attribute; no privilege escalation risk.
- Audit events are best-effort (exceptions swallowed); they must not be relied upon for security-critical audit trails. The security audit trail for high-risk AP operations belongs to PUR-012.

## 10. Open Questions / Assumptions

1. **Assumption: supplier existence is not re-validated at upsert time.** PUR-003 establishes `T.suppliers`. PUR-004 does NOT call `get_supplier` before writing a supplier-product row. Rationale: a read on the hot upsert path doubles round trips; the foreign-key constraint is a logical convention, not a DynamoDB-enforced constraint. An operator who deletes a supplier without first deleting its products will have orphaned rows. PUR-005's router should document this and the admin UI should cascade-delete. This is marked for verification in PUR-005.

2. **Assumption: `inventory_reservations_enabled=False` means no raw-string SKUs can be linked.** When the inventory flag is off, `inventory.get_inventory` always returns `None` because the inventory table is empty. Only `catalog:` prefixed SKUs will pass validation. If operators want to link suppliers to raw SKUs without enabling inventory, an alternative validation path would be needed (e.g., accept any non-empty string and skip validation). This spec follows the ticket text verbatim ("validate the SKU exists in the catalog or inventory"). Verify with product owner whether raw-string SKUs should be accepted when inventory is disabled.

3. **Assumption: `preferred` flag is not enforced unique per SKU at the service layer.** Multiple suppliers may be `preferred=True` for the same SKU simultaneously. This simplifies the upsert (no conditional clear-all-others) and avoids a GSI scan. The router or application logic can enforce uniqueness if desired. Verify with product owner.

4. **Assumption: `supplier_sku` (vendor's part number) is a free-form string, no uniqueness constraint.** Two different suppliers may use the same `supplier_sku` string for different products. No index on `supplier_sku` is needed at this stage. PUR-011 reorder suggestions use `sku` (our internal identifier) not `supplier_sku`. If cross-supplier deduplication by vendor part number is needed in the future, a `GSI_SUPPLIER_SKU` would be required.

5. **Assumption: currency is stored but not validated against a controlled list.** The service stores whatever string is passed. Validation against ISO-4217 belongs in the Pydantic model (PUR-005). Both dev and prod use the same DDB storage, so any invalid currency written in dev will also be writable in prod if the router validation is bypassed.

6. **Assumption: `lead_time_days=0` is a valid sentinel for "lead time not specified."** Some suppliers may not provide a lead time; callers should pass `0` or omit the field. PUR-011 should treat `0` as "unknown lead time" and rank it lower than any positive value.

7. **Assumption: SKU string length limits.** The ticket does not specify a max length. The inventory service models use `max_length=256` (`app/models.py:596`). PUR-004's service layer does not validate length; the Pydantic model in PUR-005 should cap `sku` at `max_length=256` for consistency.

8. **Question: should `list_suppliers_for_sku` filter to only active suppliers?** A supplier set to `status="inactive"` (PUR-003) would still appear in `list_suppliers_for_sku` because the GSI query is on `sku` and does not include a `status` filter. Applying a `FilterExpression` for `supplier_status = active` would require storing `supplier_status` redundantly on each `supplier_products` row. Alternatively, PUR-011 filters inactive suppliers post-fetch via a batch `get_supplier` call. Verify with product owner.

## 11. Dependencies

### Direct prerequisite
- **PUR-003** (Supplier CRUD service) — establishes the `suppliers` table and the `supplier_id` namespace. PUR-004 stores `supplier_id` as a foreign key and assumes the supplier record exists (assumption 1 above).
- **PUR-002** (Scaffolding) — establishes `T.supplier_products`, `T.suppliers`, `S.purchasing_scm_enabled`, and the `GSI_SKU` with correct `attr_types={"unit_cost_cents": "N"}`.

### Cross-module
- **OFBiz inventory** (`app/services/inventory.py`) — called by `_validate_sku_exists` at the inventory path. No data dependency; only a read-path call to `get_inventory`.
- **Catalog** (`app/core/tables.py:351`, `T.catalog`) — queried by `_validate_sku_exists` at the catalog path via `ByItemId` GSI. No data is written to the catalog table.
