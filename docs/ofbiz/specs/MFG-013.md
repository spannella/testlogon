# MFG-013 — Finished-goods ↔ catalog stock integration

## 1. Summary & Goal

MFG-013 wires the final link between the manufacturing work-order lifecycle (MFG-007)
and the storefront: when a completed work order produces finished goods via
`inventory.adjust(product_sku, +produced_qty, reason="mfg_produce")`, the legacy
catalog `stock_count` field on the matching catalog item row in `T.catalog` must be
updated to reflect the new available quantity so that the existing shop/cart/cart-badge
UI sees the produced stock immediately — without a separate write, page reload, or new
inventory path.

The ticket is deliberately narrow: **no new tables, no new write path into catalog stock,
no new billing touch**. It adds:

1. A new optional field pair `catalog_category_id` / `catalog_item_id` on the
   `mfg_work_orders` META row (and on `WorkOrderCreateIn`) to record which catalog
   item a finished-goods SKU corresponds to.
2. A new `_mirror_catalog_stock_count` helper in `app/services/manufacturing_work_orders.py`
   that is called best-effort inside `complete_work_order`, after the
   `inventory.adjust` succeed, mirroring `inventory.available` → `catalog.stock_count`.
3. A new optional `GET /ui/manufacturing/work-orders/{id}/catalog-stock` diagnostic
   endpoint that returns the current inventory and catalog `stock_count` side-by-side
   for a finished-goods SKU.
4. Regression assertions that after `complete_work_order`, both `inventory.get_inventory(sku).available`
   and the catalog item's `stock_count` agree.

The feature is gated behind the master `manufacturing_mrp_enabled` flag (default OFF).
With the flag off, the catalog `stock_count` path, cart `purchase_cart`, and all billing
code are byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 Inventory `adjust` — the single stock mutation

`app/services/inventory.py:209` defines `adjust(sku, delta, reason, *, location_id, user_sub)`.
It performs an optimistic conditional `update_item` on `T.inventory` (PK `sku`, SK attr
`location_sk` = `LOC#{location_id}` — `inventory.py:59–60`) and recomputes
`new_available = new_on_hand - reserved` on every mutation (`inventory.py:255`).
`_record_out` at `inventory.py:101` derives the computed view:

```python
available = on_hand - reserved
status = _status_for(available, reorder_point)   # "in_stock"|"low_stock"|"out_of_stock"
```

The Returns/RMA service (`app/services/returns_rma.py:432`) calls
`inv.adjust(sku, qty, reason="rma_restock")` using this exact same primitive after a
return is received. MFG-007's `complete_work_order` follows the same pattern with
`reason="mfg_produce"` (`docs/ofbiz/specs/MFG-007.md:§4.1`).

### 2.2 Catalog `stock_count` — the legacy mirror field

The catalog item row in `T.catalog` table name `shopping_catalog`
(`scripts/local-ddb-init.py:117–125`), PK `CAT#{category_id}` (`catalog.py:55–56`),
SK `ITEM#{item_id}` (`catalog.py:63–64`) carries a `stock_count` integer field.
`_compute_stock_status` at `app/routers/catalog.py:94` reads this field to compute the
stock badge:

```python
def _compute_stock_status(item: dict) -> str:
    sc = item.get("stock_count")
    if sc is None:
        return "unlimited"
    ...
```

`CatalogItemOut` at `app/models.py:672` surfaces `stock_count` / `stock_status` to
frontend consumers. The storefront badge, cart validation, and `purchase_cart`'s
stock-decrement guard (`app/services/shoppingcart.py:515–519`) all read `stock_count`
directly from the catalog row — NOT from the `inventory` table.

The existing `adjust_stock` endpoint at `app/routers/catalog.py:722` (auth:
`require_ui_session` at `:725`) is the only current code path that writes `stock_count`
on a catalog item outside of initial creation.

### 2.3 The gap: `inventory.adjust` does not touch `catalog.stock_count`

`inventory.adjust` updates `T.inventory` only. The catalog's `stock_count` is a
separate DynamoDB attribute on a different table/key. There is no post-adjust hook or
callback registered anywhere in `app/services/inventory.py`. This was explicitly deferred
in the OFB-003 design note (`OFBIZ_COMMERCE_TICKETS.md:56`): "Keep catalog `stock_count`
as a denormalized read-through mirror so the existing storefront UI keeps working."

ECM-010 (`docs/ofbiz/specs/ECM-010.md:268` — `### 4.4 New helper: _mirror_stock_count`)
specifies a `_mirror_stock_count` helper for the reservation-commit path. That helper calls `inventory.get_inventory(inventory_sku)`
and writes the result back to `catalog.stock_count`. MFG-013 reuses the same design
pattern from the production-complete path.

### 2.4 SKU → catalog item lookup gap

The `inventory` table uses `PK=sku` (a free-form string such as `"WIDGET-RED-M"`).
The `catalog` table uses `PK=CAT#{category_id}`, `SK=ITEM#{item_id}`. There is no GSI
or index in the catalog table that maps an inventory SKU to a catalog `(category_id,
item_id)` pair.

The existing `_find_item_by_id` helper in `app/routers/catalog.py:702` resolves by
`item_id` via the `ByItemId` GSI (`scripts/local-ddb-init.py:123`), but that requires
knowing the `item_id` already. The catalog item rows do not carry a `sku` field today
(`CatalogItemCreateIn` at `app/models.py:538` — verified, no `sku` field at lines
538–548; `_catalog_item_out` at `app/routers/catalog.py:107` — verified, no `sku`
projection at lines 107–127).

**MFG-013 design decision**: store `catalog_category_id` / `catalog_item_id` on the
`mfg_work_orders` META row at work-order creation time, supplied by the caller
(optional). This gives the completion path a direct catalog key without any GSI scan.
If the fields are absent (work order not linked to a catalog item), the mirror step is
skipped silently.

### 2.5 The `produce_guard` idempotency flag (MFG-007)

`complete_work_order` in `manufacturing_work_orders.py` uses a `produce_guard` flag on
the META row (`docs/ofbiz/specs/MFG-007.md:§3.2`). The guard is flipped atomically via
`ConditionExpression="produce_guard = :empty"` (MFG-007 spec §5.4 step 5; `:empty = ""`)
after calling `inventory.adjust`. This means the mirror write must happen inside the same
logical block — after the guard flip succeeds — to ensure it runs exactly once per
completion (if the guard already flipped, the second call to `complete_work_order` returns
early before reaching the mirror call).

### 2.6 Feature flag

`S.manufacturing_mrp_enabled` (env `MANUFACTURING_MRP_ENABLED`, default `false`) is
added to `app/core/settings.py` by MFG-002 (specified in `docs/ofbiz/specs/MFG-002.md:321–323`;
**not yet present** in the live `app/core/settings.py`). With this flag off,
`manufacturing_work_orders._require_enabled()` raises `HTTPException(404)` before any
code in the module executes, leaving all catalog/cart/billing code unchanged.
The `_require_enabled` / `_flag_on` pattern is modelled on `app/services/inventory.py:50–56`.

## 3. Data Model

No new DynamoDB tables are needed for MFG-013.

### 3.1 Schema additions to `mfg_work_orders` META row

Two optional string attributes are added to the existing META row structure defined in
`docs/ofbiz/specs/MFG-007.md:§3.2`. They are written at creation time and never updated:

| Attribute | DDB Type | Notes |
|---|---|---|
| `catalog_category_id` | S | `category_id` portion of the catalog item PK; empty string `""` when not linked |
| `catalog_item_id` | S | `item_id` portion of the catalog item PK; empty string `""` when not linked |

Both attributes are optional and stored as empty strings (not NULL/absent) to avoid
DynamoDB conditional-expression surprises with `attribute_not_exists`. Neither attribute
is projected onto any GSI. The full updated header row is:

```
PK  = work_order_id        (sha256(correlation_id)[:32])
SK  = "META"
--- existing MFG-007 fields ---
product_sku                (S)   finished-goods SKU for inventory
bom_id                     (S)   resolved BOM at creation
work_center_id             (S)   optional, "" if absent
quantity                   (N)
produced_qty               (N)
status                     (S)
correlation_id             (S)
issues_guard               (S)
produce_guard              (S)
location_id                (S)
user_sub                   (S)
created_at                 (N)   numeric — GSI sort key
updated_at                 (N)
--- new MFG-013 additions ---
catalog_category_id        (S)   "" when not catalog-linked
catalog_item_id            (S)   "" when not catalog-linked
```

No `attr_types` changes needed — both new fields are string type (S) and are not used
as GSI sort keys.

### 3.2 Catalog item row (no schema change)

`T.catalog` (table name `shopping_catalog`, `scripts/local-ddb-init.py:117–125`) item row is already:

```
PK  = CAT#{category_id}    (cat_pk helper: catalog.py:55–56)
SK  = ITEM#{item_id}       (item_sk helper: catalog.py:63–64)
stock_count         (N)   nullable integer; absent = unlimited   (models.py:684, CatalogItemOut)
stock_updated_at    (S)   ISO timestamp of last update           (models.py:687)
```

`_compute_stock_status` at `catalog.py:94` reads `stock_count` from this row. The
mirror write from MFG-013 targets the same `stock_count` / `stock_updated_at` fields
that `adjust_stock` already writes at `catalog.py:740–743`.

### 3.3 Inventory row (no schema change)

`T.inventory` (table name `inventory`, `scripts/local-ddb-init.py:2456–2464`) PK `sku`,
SK attr `location_sk` = `LOC#{location_id}` (`inventory.py:59–60`). After
`inventory.adjust(sku, +qty, ...)`, the row carries the fresh `on_hand`, `reserved`,
and `available` values that must be
mirrored to `catalog.stock_count`.

#### 4.2.2 `_mirror_catalog_stock_count` — new helper

```python
def _mirror_catalog_stock_count(
    product_sku: str,
    catalog_category_id: str,
    catalog_item_id: str,
    location_id: str = DEFAULT_LOCATION,
) -> None:
    """Write inventory.available → catalog.stock_count for a finished-goods SKU.

    Called best-effort after produce_guard flip in complete_work_order.
    Any error is silently swallowed — a mirror failure NEVER blocks completion
    or surfaces a 5xx to the caller (mirrors ECM-010._mirror_stock_count design).

    Skipped silently when catalog_category_id or catalog_item_id is empty.
    """
    if not catalog_category_id or not catalog_item_id:
        return
    try:
        from app.services import inventory as inv
        rec = inv.get_inventory(product_sku, location_id)
        if rec is None:
            return
        new_sc = max(0, rec["available"])
        from app.core.tables import T
        from app.routers.catalog import cat_pk, item_sk
        T.catalog.update_item(
            Key={"PK": cat_pk(catalog_category_id), "SK": item_sk(catalog_item_id)},
            UpdateExpression="SET stock_count = :sc, stock_updated_at = :now",
            ExpressionAttributeValues={
                ":sc": new_sc,
                ":now": _now_iso(),    # ISO timestamp, matching existing catalog pattern
            },
            ConditionExpression="attribute_exists(PK)",
        )
    except Exception:
        pass
```

`cat_pk` and `item_sk` are helper functions defined in `app/routers/catalog.py`. Because
`manufacturing_work_orders.py` is a service (not a router), the local import of
`cat_pk`/`item_sk` must be done inside the function body to avoid a circular import
(routers import services; services must not import routers at module level). The
`ConditionExpression="attribute_exists(PK)"` guard ensures the write is a no-op if the
catalog item was deleted, preventing silent item creation.

`_now_iso()` is a module-level helper that returns `datetime.now(timezone.utc).isoformat()`,
matching the identical pattern used by `now_iso()` in `app/routers/catalog.py:47`
(`datetime.now(timezone.utc).isoformat()`) for `stock_updated_at`. Do **not** use the
deprecated `datetime.utcnow()` — the rest of the codebase consistently uses the
timezone-aware form (`app/services/shoppingcart.py:26–27` is another example).

#### 4.2.3 `complete_work_order` — add mirror call after produce step

Inside `complete_work_order`, immediately after the `inventory.adjust` call succeeds
and the `produce_guard` is flipped to `"done"`, add the mirror call:

```python
# ... existing produce_guard flip CAS ...
if guard_flipped:
    inv.adjust(
        header["product_sku"],
        produced_qty,
        reason="mfg_produce",
        location_id=header.get("location_id", DEFAULT_LOCATION),
        user_sub=actor_sub,
    )
    # MFG-013: mirror the new inventory.available to catalog.stock_count
    _mirror_catalog_stock_count(
        product_sku=header["product_sku"],
        catalog_category_id=header.get("catalog_category_id", ""),
        catalog_item_id=header.get("catalog_item_id", ""),
        location_id=header.get("location_id", DEFAULT_LOCATION),
    )
    _write_event(work_order_id, current_status, "completed", actor_sub)
    ...
```

The mirror call is placed **after** the `inventory.adjust` so the catalog reflects the
post-produce available quantity. Any exception from `_mirror_catalog_stock_count` is
fully swallowed by that function, so it never interrupts the completion flow.

### 4.3 New diagnostic endpoint: `GET /ui/manufacturing/work-orders/{id}/catalog-stock`

Added to `app/routers/manufacturing_work_orders.py` (or the consolidated
`app/routers/manufacturing.py` per MFG-011):

```python
@work_orders_router.get(
    "/{work_order_id}/catalog-stock",
    response_model=WorkOrderCatalogStockOut,
)
async def get_work_order_catalog_stock(
    work_order_id: str,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
):
    _require_enabled()
    header = _get_header(work_order_id)
    if header is None:
        raise HTTPException(status_code=404, detail="Work order not found")
    product_sku = header.get("product_sku", "")
    location_id = header.get("location_id", DEFAULT_LOCATION)
    inv_rec = inv.get_inventory(product_sku, location_id)
    catalog_sc = None
    cat_id = header.get("catalog_category_id", "")
    item_id = header.get("catalog_item_id", "")
    if cat_id and item_id:
        catalog_item = T.catalog.get_item(
            Key={"PK": cat_pk(cat_id), "SK": item_sk(item_id)}
        ).get("Item")
        if catalog_item:
            sc = catalog_item.get("stock_count")
            catalog_sc = int(sc) if sc is not None else None
    return WorkOrderCatalogStockOut(
        work_order_id=work_order_id,
        product_sku=product_sku,
        inventory_available=inv_rec["available"] if inv_rec else None,
        inventory_on_hand=inv_rec["on_hand"] if inv_rec else None,
        catalog_stock_count=catalog_sc,
        in_sync=(
            inv_rec["available"] == catalog_sc
            if inv_rec and catalog_sc is not None
            else None
        ),
    )
```

Response model:

```python
class WorkOrderCatalogStockOut(BaseModel):
    work_order_id: str
    product_sku: str
    inventory_available: Optional[int] = None   # None if no inventory record
    inventory_on_hand: Optional[int] = None
    catalog_stock_count: Optional[int] = None   # None if not catalog-linked or catalog item not found
    in_sync: Optional[bool] = None              # None if either is None (unlimited/unlinked)
```

Auth: `require_admin_or_root_csrf` (admin read-only diagnostic; same auth gate as all
other manufacturing endpoints per MFG-011).

## 5. Detailed Behavior & Edge Cases

### 5.1 Normal path

1. Admin creates a work order with `catalog_category_id="cat-abc"` and
   `catalog_item_id="sku-xyz"`.
2. Work order is released and completed via MFG-007 mechanics.
3. `complete_work_order` calls `inventory.adjust("WIDGET-A", +50, reason="mfg_produce")`.
   Post-adjust, `inventory.get_inventory("WIDGET-A").available = 50`.
4. `_mirror_catalog_stock_count` is called; `T.catalog.update_item(...)` sets
   `stock_count = 50` on the catalog item row.
5. `GET /ui/catalog/categories/cat-abc/items` response includes `stock_count: 50,
   stock_status: "in_stock"` for the item.
6. `purchase_cart` (SHOP-001 path) can now decrement `stock_count` from 50.

### 5.2 Work order not catalog-linked

`catalog_category_id` or `catalog_item_id` is `""` or `None`. `_mirror_catalog_stock_count`
returns immediately on the first guard. The catalog item is untouched. No error.

### 5.3 Catalog item deleted between creation and completion

`T.catalog.update_item` with `ConditionExpression="attribute_exists(PK)"` raises
`ConditionalCheckFailedException`. The `except Exception: pass` in
`_mirror_catalog_stock_count` swallows it. The work order completes successfully; the
deleted catalog item remains absent. No data created or double-written.

### 5.4 Inventory record absent at mirror time

`inv.get_inventory(product_sku)` returns `None` (no inventory record for the SKU —
possible if `inventory_reservations_enabled` is off or no record was seeded). The
helper returns without writing. The catalog `stock_count` is unchanged. This is safe:
if there is no inventory record, the inventory module is dormant and `stock_count` is
still managed by the existing `adjust_stock` endpoint.

### 5.5 Replayed `complete_work_order` (idempotency)

On a replayed call, `_flip_guard` for `produce_guard` returns `False`
(`ConditionalCheckFailedException`) — the guard is already `"done"`. The function returns
the current header before reaching the `inventory.adjust` call. `_mirror_catalog_stock_count`
is NOT called on replay. The catalog `stock_count` retains whatever was written on the
first completion. This is correct: replaying a completion should never double-produce
or double-mirror.

### 5.6 `inventory.adjust` succeeds but mirror fails

`_mirror_catalog_stock_count` swallows all exceptions. The inventory `available` count
is authoritative. The catalog `stock_count` may be stale until the next manual
`PATCH /catalog/items/{id}/stock` call or a follow-up work order. The diagnostic
endpoint `GET .../catalog-stock` will show `in_sync: false` in this case. In practice,
`T.catalog.update_item` with moto/local DDB is extremely reliable; a silent failure
would require a DDB outage.

### 5.7 Cancel work order after partial production

`cancel_work_order` never calls `inventory.adjust(+qty)` for finished goods (the
`produce_guard` was never flipped). No catalog mirror write happens on cancel. If the
work order was somehow partially completed (which is not possible in Phase-1 with the
guard), the catalog `stock_count` would also not be mirrored.

### 5.8 Flag off with existing catalog items

When `manufacturing_mrp_enabled = false`, all manufacturing endpoints return 404 and no
manufacturing service code runs. The `shoppingcart.purchase_cart` path, the catalog
`adjust_stock` endpoint, and all billing paths are byte-for-byte unchanged. The new
`catalog_category_id` / `catalog_item_id` fields on the META row are never written when
the flag is off.

### 5.9 `stock_count` goes negative (oversell safety)

`_mirror_catalog_stock_count` writes `max(0, rec["available"])` — it never sets
`stock_count` to a negative value even if somehow `inventory.available` were negative
(which inventory.adjust prevents via the 409 guard at `inventory.py:256`).

### 5.10 Low-stock alert interaction

`_mirror_catalog_stock_count` does NOT call `_check_low_stock_alert`. The existing
`adjust_stock` endpoint at `app/routers/catalog.py:643–699` calls `_check_low_stock_alert`
after every stock mutation. The mirror write bypasses it to keep the helper side-effect-
free. A follow-up can call `_check_low_stock_alert` inline after the `T.catalog.update_item`
if that alert integration is required for manufacturing completions (out of scope for
MFG-013).

## 6. Feature Flag & Config

### 6.1 Master flag (from MFG-002)

| Key | Env var | Default | Notes |
|---|---|---|---|
| `S.manufacturing_mrp_enabled` | `MANUFACTURING_MRP_ENABLED` | `false` | All MFG module behavior gated here |

With the flag off: `_require_enabled()` in `manufacturing_work_orders.py` raises
`HTTPException(404)`. No catalog mirror is ever called.

### 6.2 No new flags for MFG-013

MFG-013 introduces no sub-flag of its own. The mirror call is always active when the
master flag is on, because a non-linked work order skips it gracefully. The diagnostic
endpoint follows the same gate.

### 6.3 Related flags that must be ON for the full path to work

| Flag | Env var | Default | Effect |
|---|---|---|---|
| `S.inventory_reservations_enabled` | `INVENTORY_RESERVATIONS_ENABLED` | `false` | Enables the `inventory` table and `adjust`; the mirror write reads from this table |
| `S.manufacturing_mrp_enabled` | `MANUFACTURING_MRP_ENABLED` | `false` | Required for any work order to be created or completed |

If `inventory_reservations_enabled = false`, `_mirror_catalog_stock_count` will find
`inventory.get_inventory(sku) = None` (no records exist) and skip silently. The work
order still completes; only the mirror is a no-op. This is the expected behavior for a
manufacturing-only deployment that has not enabled OFBiz inventory.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007

`_mirror_catalog_stock_count` calls `T.catalog.update_item`. `T.catalog` resolves to
`moto` in-process DynamoDB in dev (`scripts/run_local_mock_backend.sh`) and to real
DynamoDB in prod. No `dev_mode` branch exists. The helper is fully symmetric across
environments.

`inv.get_inventory` calls `T.inventory.get_item` — also symmetric.

### 7.2 Idempotency

`complete_work_order` is already idempotent via the `produce_guard` CAS. Because the
mirror call is placed inside the `if guard_flipped:` block, it runs exactly once. A
replayed completion call finds `produce_guard = "done"`, returns early, and never
reaches the mirror helper.

The `T.catalog.update_item` call itself is idempotent: writing the same `stock_count`
value twice has no visible side effect (the value is overwritten to the same integer).

### 7.3 Auth

The new `catalog_category_id` / `catalog_item_id` fields are accepted on `WorkOrderCreateIn`
via the `POST /ui/manufacturing/work-orders` endpoint, which is gated by
`require_admin_or_root_csrf` (defined at `app/auth/policy.py:100–106`). Only admin or
root users can link a work order to a catalog item. The mirror write is a server-side
internal operation — no user-facing path can force a catalog `stock_count` write without
admin privileges.

The diagnostic `GET .../catalog-stock` endpoint is also gated by
`require_admin_or_root_csrf`. No customer-facing endpoint exposes the raw
`inventory_available` / `in_sync` fields.

### 7.4 No billing touch

`_mirror_catalog_stock_count` writes only to `T.catalog.stock_count`. It touches no
billing table, no ledger entry, no wallet balance. The billing system is unchanged.

### 7.5 Circular-import safety

`manufacturing_work_orders.py` is a service module. The local import of
`cat_pk` / `item_sk` from `app/routers/catalog` is placed inside the function body of
`_mirror_catalog_stock_count`. This mirrors the lazy-import pattern used by
`returns_rma.py:425–427` (`from app.services import inventory as inv` inside the
`if inv_flag:` block) and by `browser_ssh_terminal.py`'s `_record_timeline` helper.
It avoids a module-level router→service circular import.

## 8. Backward Compatibility & Migration

### 8.1 Existing work orders (MFG-007, pre-MFG-013)

Work orders created before the MFG-013 schema change do not carry
`catalog_category_id` / `catalog_item_id`. `header.get("catalog_category_id", "")` will
return `""`, and `_mirror_catalog_stock_count` will skip the mirror silently. No
migration is needed and no existing work order is affected.

### 8.2 Catalog items with no associated inventory record

With `inventory_reservations_enabled = false` (or before any inventory record is
seeded), `inventory.get_inventory(sku)` returns `None`. The mirror is skipped. The
catalog `stock_count` remains as-is. This is backward-compatible — the catalog was
managing `stock_count` independently before and continues to do so.

### 8.3 `WorkOrderCreateIn` field additions

`catalog_category_id` and `catalog_item_id` are `Optional[str]` with `default=None` in
the Pydantic model and stored as `""` in DynamoDB when absent. All existing callers
of `WorkOrderCreateIn` and `create_work_order` that do not pass these fields continue
to work without change. The `WorkOrderOut` response model gains two nullable fields;
existing API consumers that do not read them are unaffected.

### 8.4 No DDB table migration

No new tables. No GSI additions to existing tables. No `attr_types` changes. `just restart`
after this ticket requires no schema change beyond what MFG-002 already added.

## 10. Open Questions / Assumptions

**OQ-1 (catalog `sku` field)**: The current catalog item row does not carry a `sku`
attribute matching the inventory `T.inventory` PK — confirmed by reading
`app/models.py:538–548` and `app/routers/catalog.py:107–127`. This spec introduces
`catalog_category_id` / `catalog_item_id` on the work order row instead of adding a
`sku` reverse-lookup GSI to `T.catalog`. Assumption: this is acceptable for Phase 1
because manufacturing work orders are admin-created and the admin knows the catalog
mapping. If the automatic SKU→catalog lookup is needed, a `ByInventorySku` GSI on
`T.catalog` would require adding a `sku` attribute to `CatalogItemCreateIn` and
populating it for all existing items (schema migration).

**OQ-2 (inventory flag independence)**: This spec assumes `_mirror_catalog_stock_count`
skips silently when `inventory_reservations_enabled = false`. Consequence: completing a
work order in a deployment where manufacturing is on but inventory is off does not update
the catalog. If that is unacceptable, an alternative is to call `inventory.adjust`
unconditionally regardless of the inventory flag (creating an inventory row if absent).
This would require modifying `inventory.adjust` to skip the `_require_enabled()` guard
when called from manufacturing — a cross-module coupling to avoid.

**OQ-3 (stock_count mirror vs. available)**: The mirror writes `max(0, rec["available"])`
(on_hand − reserved). The existing `purchase_cart` SHOP-001 path (`shoppingcart.py:515`)
reads and decrements `stock_count` directly, not via inventory. After a purchase, the
`stock_count` drops but `inventory.on_hand` does not (until ECM-010/OFB-004 is enabled).
So `in_sync: false` is the expected state after a customer purchase. This is documented
as a known limitation of operating both `stock_count` and inventory in parallel; ECM-010
is the remediation.

**OQ-4 (catalog key helper import)**: `cat_pk` and `item_sk` are module-level functions
in `app/routers/catalog.py`. If these helpers are refactored into a shared `app/core/catalog_keys.py`
module, the local import in `_mirror_catalog_stock_count` would need updating. Assumption:
they stay in `catalog.py` for now.

**OQ-5 (low-stock alert on production)**: MFG-013 does not trigger `_check_low_stock_alert`
when the mirror write crosses the low-stock threshold. If a production run of 3 units
lands a 5-unit-threshold item at `stock_count=3`, no alert fires. This is out of scope
for MFG-013 and should be tracked as a follow-up.

**OQ-6 (catalog item concurrent modification)**: If an admin edits `stock_count` on the
catalog item concurrently with a work order completion, the last writer wins (no version
CAS on the catalog row). The `T.catalog.update_item` in `_mirror_catalog_stock_count`
has no conditional guard beyond `attribute_exists(PK)`. This is the same risk accepted
by the existing `adjust_stock` endpoint and is acceptable for Phase 1.
