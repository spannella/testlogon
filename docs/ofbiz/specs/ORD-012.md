# ORD-012 — Status & ship-date list/query endpoints

**Type:** Feature | **Priority:** P1 | **Estimate:** 2 days
**Milestone:** 4 — Router & API

---

## 1. Summary & Goal

ORD-012 adds two admin-only list endpoints to the `app/routers/order_lifecycle.py` router introduced by ORD-011. Both endpoints expose paginated, GSI-backed queries over the `orders` table and are strictly additive over every prior ORD ticket:

1. `GET /ui/orders/lifecycle/by-status?status=picking` — queries `GSI_ORDER_STATUS` (PK `lifecycle_status`, SK numeric `updated_ts`) and returns order headers in the requested lifecycle state, newest-first by `updated_ts`.
2. `GET /ui/orders/lifecycle/by-ship-date?date=YYYY-MM-DD` — queries `GSI_ORDER_SHIPDATE` (PK `ship_date_bucket`, SK numeric `ship_ts`) and returns ship-group rows that have a planned ship date falling on the requested calendar day, newest-first by `ship_ts`.

Both endpoints use signed cursors from `app/core/cursor.py` (`encode_cursor` / `decode_cursor`) and loop on `LastEvaluatedKey` to guard against the CLAUDE.md FilterExpression page-size gotcha (DynamoDB applies FilterExpression only after reading up to 1 MB per page, so a single query call can silently miss items).

With `S.order_lifecycle_enabled = False` (default), every ORD-012 handler returns `503 Service Unavailable` and neither GSI receives any writes — existing shop/cart/orders/billing flows are byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 Orders table and existing GSIs

`scripts/local-ddb-init.py:287–294` defines the `orders` table today as a PK-only flat table (no sort key) with two string-sorted GSIs (`GSI_USER`, `GSI_STATUS`). After ORD-003 the table gains a base sort key `sk` (S), two lifecycle GSIs with numeric sort keys, and the single-table SK namespace (`ORDER`, `HIST#`, `SHIPGRP#`, `ADJ#`):

```python
TableDef(
    _resolve_table_name(S.orders_table_name, "orders"),
    "order_id",
    "sk",
    gsi=[
        {"index_name": "GSI_USER",            "partition_key": "user_id",         "sort_key": "created_at"},
        {"index_name": "GSI_STATUS",           "partition_key": "status",          "sort_key": "created_at"},
        {"index_name": "GSI_ORDER_STATUS",     "partition_key": "lifecycle_status","sort_key": "updated_ts"},
        {"index_name": "GSI_ORDER_SHIPDATE",   "partition_key": "ship_date_bucket","sort_key": "ship_ts"},
    ],
    attr_types={"updated_ts": "N", "ship_ts": "N"},
)
```

`docs/ofbiz/specs/ORD-003.md:103–142` is the authoritative schema reference for both new GSIs. `GSI_ORDER_STATUS` is populated by ORD-005 (`app/services/order_lifecycle.py`) on every successful `transition_order` call, which writes `lifecycle_status` (S) and `updated_ts` (N) to the `ORDER`-SK header row. `GSI_ORDER_SHIPDATE` is populated by ORD-009 (`app/services/ship_groups.py`) when a ship group is created or updated with a known `ship_ts`; it indexes `SHIPGRP#`-SK rows only (`docs/ofbiz/specs/ORD-009.md:116–130`).

### 2.2 `T.orders` handle

`app/core/tables.py:381` wires `T.orders = _safe_table(S.orders_table_name)`. All ORD-012 queries use this single handle — no new table alias is needed (`docs/ofbiz/specs/ORD-003.md:64–70`).

### 2.3 Cursor utilities

`app/core/cursor.py` provides:
- `encode_cursor(last_evaluated_key: Optional[Dict]) -> Optional[str]` — wraps the LEK in a versioned, HMAC-signed URL-safe base64 token (line 94). The `_json_default` helper at line 12 converts DynamoDB `Decimal` (from numeric GSI keys) to `int`/`float` so the cursor encodes cleanly.
- `decode_cursor(cursor: Optional[str]) -> Optional[Dict]` — verifies the HMAC signature and returns the raw `ExclusiveStartKey` dict (line 103). Returns `None` on a bad/tampered cursor.

Active usage precedent for the same pattern: `app/services/fraud_detection.py:356–378` (single-page GSI query + encode/decode; `list_review_queue` starts at line 356), `app/services/license_agreements.py:260–299` (multi-page filtered query with looping LEK and encode/decode at lines 268 and 298).

### 2.4 FilterExpression / LastEvaluatedKey gotcha

CLAUDE.md warns: "DynamoDB fetches up to 1MB *before* applying `FilterExpression`. Any query that filters a sparse attribute must loop via `LastEvaluatedKey` — a single `query()` call silently misses items beyond the first page on a busy table."

`GSI_ORDER_STATUS` queries are straightforward `KeyConditionExpression` queries with no FilterExpression; the GSI PK is already the exact `lifecycle_status` value, so DynamoDB returns only matching items. A single-page query is sufficient for a bounded `Limit`, but exposing `ExclusiveStartKey`-based pagination is still required so callers can page through large result sets. No looping beyond the requested page is needed for this GSI.

`GSI_ORDER_SHIPDATE` also uses a KeyConditionExpression on the exact `ship_date_bucket` day string. Like the status GSI, no FilterExpression is required for the base query. A `ship_ts BETWEEN` range condition (optional) is also a KeyConditionExpression, not a FilterExpression — so the 1MB page-before-filter concern applies only if an additional `FilterExpression` predicate is added to either query (e.g. filtering by `user_id` for a per-user sub-list). The ORD-012 endpoints do not add such a filter in the initial cut, but the loop guard is included defensively for correctness under future extension.

## 3. Data Model

### 3.1 No new tables or GSIs

ORD-012 introduces no DynamoDB table changes. Both queries target GSIs already declared by ORD-003 in `scripts/local-ddb-init.py`. The `attr_types={"updated_ts": "N", "ship_ts": "N"}` declarations ensure both numeric GSI sort keys are stored as `N` and queryable with integer range conditions — a prerequisite for correctness (`docs/ofbiz/specs/ORD-003.md:138`).

### 3.2 GSI_ORDER_STATUS — query semantics

| Attribute | DDB type | Role | Written by |
|---|---|---|---|
| `lifecycle_status` | S | GSI PK | ORD-005 `transition_order` on every `ORDER`-SK header |
| `updated_ts` | N | GSI SK | ORD-005 `transition_order`; `now_ts()` integer Unix seconds |
| `order_id` | S | projected | Identifies the order |
| `user_id` | S | projected | Owner (for ownership enforcement) |
| `status` | S | projected | Legacy mirror field |
| `amount_cents` | N | projected | For display |
| `currency` | S | projected | For display |

Projection type: `ALL` (set by ORD-003 — all attributes are available without a base-table fetch).

Query access pattern for ORD-012:
```
KeyConditionExpression: lifecycle_status = :status_val
ScanIndexForward: False   # newest updated_ts first
Limit: <page_size>
ExclusiveStartKey: <decoded cursor>  # when cursor present
```

Sparse population: `GSI_ORDER_STATUS` is populated only for orders written after ORD-007 initialises `lifecycle_status="created"` on newly created orders. Pre-ORD-007 orders have no `lifecycle_status` attribute and are absent from this GSI — this is correct and expected (ORD-005 spec: `docs/ofbiz/specs/ORD-005.md:587`).

### 3.3 GSI_ORDER_SHIPDATE — query semantics

| Attribute | DDB type | Role | Written by |
|---|---|---|---|
| `ship_date_bucket` | S | GSI PK | ORD-009 `create_ship_group` when `ship_ts` is provided |
| `ship_ts` | N | GSI SK | ORD-009 integer Unix seconds |
| `order_id` | S | projected | Parent order |
| `sk` | S | projected | `SHIPGRP#{ship_group_id}` — allows ship_group_id extraction |
| `ship_group_id` | S | projected | Logical shipment ID |
| `ship_method` | S | projected | Carrier/service code |
| `ship_status` | S | projected | Ship-group fulfillment status |
| `item_ids` | L | projected | Line-item references |

Projection type: `ALL`.

The `ship_date_bucket` string is derived from `ship_ts` by ORD-009 as:
```python
datetime.fromtimestamp(ship_ts, tz=timezone.utc).strftime("%Y-%m-%d")
```

Query access pattern for ORD-012:
```
KeyConditionExpression: ship_date_bucket = :date_val
ScanIndexForward: False   # newest ship_ts first within day
Limit: <page_size>
ExclusiveStartKey: <decoded cursor>  # when cursor present
```

### 4.1 New service functions in `app/services/order_lifecycle.py`

**Function 1: list orders by lifecycle status**

```python
def list_orders_by_status(
    *,
    status: str,
    limit: int = 50,
    cursor: Optional[str] = None,
) -> Dict[str, Any]:
    """Query GSI_ORDER_STATUS for orders in the given lifecycle state.

    Returns newest-first by updated_ts. Paginates via encode_cursor /
    decode_cursor (app/core/cursor.py). Does NOT loop on LastEvaluatedKey
    beyond the requested page — the cursor exposes the continuation point
    to the caller for explicit pagination.

    Returns:
        {
            "orders": [<OrderLifecycleOut-serialisable dict>, ...],
            "count": int,
            "cursor": Optional[str],   # None when no further pages
        }
    """
```

Raises `ValueError` if `status` is not a valid `OrderLifecycleStatus` value (validated before the DDB call — 400 at the router layer).

**Function 2: list ship groups by ship date**

```python
def list_ship_groups_by_date(
```

### 4.2 Internal implementation notes

**`list_orders_by_status` internals:**

```python
from boto3.dynamodb.conditions import Key
from app.core.cursor import encode_cursor, decode_cursor
from app.core.tables import T

kwargs: Dict[str, Any] = {
    "IndexName": "GSI_ORDER_STATUS",
    "KeyConditionExpression": Key("lifecycle_status").eq(status),
    "ScanIndexForward": False,
    "Limit": max(1, min(limit, 200)),   # cap at 200
}
lek = decode_cursor(cursor)
if lek:
    kwargs["ExclusiveStartKey"] = lek
resp = T.orders.query(**kwargs)
items = resp.get("Items", [])
return {
    "orders": [_header_item_to_dict(it) for it in items],
    "count": len(items),
    "cursor": encode_cursor(resp.get("LastEvaluatedKey")),
}
```

`_header_item_to_dict` is an internal helper (also used by ORD-011's `GET /ui/orders/{order_id}/lifecycle`) that serialises a raw DDB `ORDER`-SK item into an `OrderLifecycleOut`-compatible dict. It coerces DynamoDB `Decimal` values to `int` for numeric fields (`amount_cents`, `updated_ts`, `line_item_count`) consistent with the `_to_decimal` helper at `app/core/tables.py:11–26` and the `_FloatSafeTable` proxy at `app/core/tables.py:29`.

**`list_ship_groups_by_date` internals:**

```python
kwargs: Dict[str, Any] = {
    "IndexName": "GSI_ORDER_SHIPDATE",
    "KeyConditionExpression": Key("ship_date_bucket").eq(date),
    "ScanIndexForward": False,
    "Limit": max(1, min(limit, 200)),
}
lek = decode_cursor(cursor)
if lek:
    kwargs["ExclusiveStartKey"] = lek
resp = T.orders.query(**kwargs)

return {
    "ship_groups": [_shipgrp_item_to_dict(it) for it in items],
```

`_shipgrp_item_to_dict` serialises a `SHIPGRP#`-SK row into a `ShipGroup`-compatible dict, extracting `ship_group_id` from the `sk` field (`sk.split("#", 1)[1]`), coercing `ship_ts` and `created_at`/`updated_at` from `Decimal` to `int`.

### 4.3 Router endpoints in `app/routers/order_lifecycle.py`

Both endpoints are appended to the existing ORD-011 router **before** any `/{order_id}` path segment to avoid FastAPI capturing the literal string as a dynamic path parameter (CLAUDE.md gotcha, same as ORD-011 `/schedules`-before-`/{export_id}` pattern).

**Endpoint 1: by-status**

```python
@router.get("/ui/orders/lifecycle/by-status")
async def list_orders_by_lifecycle_status(
    status: str = Query(..., description="lifecycle_status value"),
    limit: int = Query(default=50, ge=1, le=200),
    cursor: Optional[str] = Query(default=None),
    actor: AuthenticatedUser = Depends(require_admin_or_root),
) -> Dict[str, Any]:
    if not S.order_lifecycle_enabled:
        raise HTTPException(503, "Order lifecycle feature is not enabled")
    try:
        OrderLifecycleStatus(status)
    except ValueError:
        raise HTTPException(400, f"Invalid lifecycle status: {status!r}")
    return list_orders_by_status(status=status, limit=limit, cursor=cursor)
```

- Auth: `require_admin_or_root` (from `app/auth/policy`, line 67) — admin or root role required.
- No CSRF parameter required: GET requests are exempt from CSRF per CLAUDE.md ("Cookie-auth non-GET requests require `x-csrf-token`").
- No ownership filter: the admin list returns all orders in that state system-wide.

**Endpoint 2: by-ship-date**

## 5. Detailed Behavior & Edge Cases

### 5.1 Status validation — 400 on unknown value

The `status` query parameter is validated against `OrderLifecycleStatus(status)` before any DDB call. Unknown values (e.g. `status=pending_payment`) return `400 Bad Request` with detail `"Invalid lifecycle status: 'pending_payment'"`. This prevents a DDB query on a PK value that can never have results and gives a clear error to API callers. The eleven valid values are defined in `app/models.py` (ORD-004).

### 5.2 Date validation — 400 on malformed date

The `date` parameter must match `^\d{4}-\d{2}-\d{2}$`. Malformed dates (e.g. `2024-1-5`, `today`) return `400 Bad Request`. Calendar validity (e.g. `2024-02-31`) is not enforced at the router — DynamoDB will simply return an empty result set because no `ship_date_bucket="2024-02-31"` items ever exist.

### 5.3 Cursor tamper resistance

`decode_cursor` verifies the HMAC signature before accepting a cursor. A tampered or expired cursor returns `None`, causing the query to start from the beginning (page 1) rather than raising an error. This matches the behaviour in `app/services/fraud_detection.py:368–370`. The service layer therefore treats a `None` decode as "no cursor" — callers that send a garbage cursor get the first page back, not a 400. This is the established platform convention.

### 5.4 Empty result set

Both endpoints return an empty list and `"cursor": null` when no items match (e.g. no orders in `holding` status, or no ship groups scheduled for a future date). `count: 0` is explicit so the caller can distinguish "no results" from "error".

### 5.5 Flag-off: 503 on every call

When `S.order_lifecycle_enabled = False`, both endpoints return `503 Service Unavailable` before any DDB interaction. This mirrors the ORD-011 pattern and ensures zero DDB reads when the feature is off.

### 5.6 Limit clamping

`limit` is a query parameter constrained `ge=1, le=200` at the Pydantic/FastAPI layer. The service layer additionally clamps with `max(1, min(limit, 200))` as a defense-in-depth measure. The cap at 200 matches the `scan_abandoned_carts` pattern in `app/services/shoppingcart.py:767` and prevents unbounded DDB reads in a single call.

### 5.7 Newest-first ordering via `ScanIndexForward=False`

`ScanIndexForward=False` returns items in descending sort-key order: newest `updated_ts` first for `by-status`, newest `ship_ts` first for `by-ship-date`. This matches the admin queue convention for all other list endpoints (e.g. `app/services/fraud_detection.py:364`, `app/services/license_agreements.py:265`).

### 5.8 Pre-ORD-007 orders absent from GSI_ORDER_STATUS

Orders created before ORD-007 initialises `lifecycle_status` on newly created orders have no `lifecycle_status` attribute and are therefore absent from `GSI_ORDER_STATUS`. The `by-status` endpoint silently omits them. This is correct — those orders are not part of the lifecycle state machine. The `by-ship-date` endpoint is unaffected since `SHIPGRP#` rows are only written by ORD-009 (which is itself gated on `ORDER_LIFECYCLE_ENABLED`).

### 5.9 GSI_ORDER_STATUS returns ORDER-SK rows only; GSI_ORDER_SHIPDATE returns SHIPGRP#-SK rows only

`lifecycle_status` and `updated_ts` are written only to `ORDER`-SK header rows by ORD-005. `HIST#`, `SHIPGRP#`, and `ADJ#` rows do not carry these attributes and are absent from the GSI. Conversely, `ship_date_bucket` and `ship_ts` are written only to `SHIPGRP#` rows by ORD-009 — ORDER headers and history rows never appear in `GSI_ORDER_SHIPDATE`. The serialisation helpers `_header_item_to_dict` and `_shipgrp_item_to_dict` will silently skip unexpected row types if the GSI projection ever returns a cross-type row (defensive guard: check `sk == "ORDER"` and `sk.startswith("SHIPGRP#")` respectively, return `None`, filter in the service before building the response list).

### 5.10 Concurrent writes during pagination

DynamoDB does not offer snapshot-consistent pagination. A page-2 cursor may return an order that has since been transitioned out of the queried status (its `lifecycle_status` changed between page 1 and page 2). This is acceptable for an admin list view — eventual consistency is the platform norm. Callers should not use these endpoints for business-critical consistency decisions; `GET /ui/orders/{order_id}/lifecycle` (ORD-011) provides the authoritative single-order read.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

Both endpoints perform identical DDB queries in dev (DynamoDB Local on port 8001) and prod (real DynamoDB). There is no `S.dev_mode` branch in ORD-012. The `GSI_ORDER_STATUS` and `GSI_ORDER_SHIPDATE` GSIs are declared with `attr_types={"updated_ts": "N", "ship_ts": "N"}` in `scripts/local-ddb-init.py` (ORD-003), ensuring numeric sort key behaviour is identical in both environments. No AWS-specific code path divergence is introduced.

### 7.2 Idempotency

Both endpoints are `GET` — pure read operations with no side effects, no state mutations, no audit events. They are trivially idempotent; repeated calls with the same parameters return the same data (modulo concurrent writes, per Section 5.10).

### 7.3 Authentication and authorisation

Both endpoints are gated on `require_admin_or_root` (`app/auth/policy.py:67`). A non-admin caller receives `403 Forbidden`. There is no per-order ownership check — admin list endpoints are system-wide views by design. Standard CSRF exemption applies to GET requests.

The `require_admin_or_root` dependency resolves via `get_authenticated_user` which supports both cookie-auth (HS256 JWT in `ui_access_token` cookie, role injected at `app/auth/deps.py`) and Bearer-token auth (Cognito JWT JWKS verification). Both auth modes are supported without code changes.

### 7.4 Information leakage scope

The by-status endpoint returns all orders in a given lifecycle state system-wide (all users). This is intentionally a privileged admin view. No `user_id` scoping is applied. If a future ticket needs per-user filtered listing, it would query `GSI_USER` with a `status` FilterExpression (invoking the FilterExpression loop guard) rather than adding a FilterExpression to the ORD-012 endpoint.

### 7.5 Cursor signing

Pagination cursors from ORD-012 are signed with the `CURSOR_SIGNING_SECRET` HMAC (defaulting to `"dev-cursor-secret"` in dev, a real secret in prod). A tampered cursor is silently rejected and treated as no cursor (page 1), preventing an adversary from injecting an arbitrary `ExclusiveStartKey` into a DynamoDB query. This is the same signing/rejection behaviour as all other cursor-using services in the codebase.

In dev, `just restart` recreates the table (already required since ORD-003 adds the base `sk` sort key). In prod, ORD-003 provides the `UpdateTable`-based incremental GSI addition path (`docs/ofbiz/specs/ORD-003.md:60`).

### 8.4 No existing caller breakage

`T.orders` is the only handle used. No existing service that reads from `T.orders` is changed. The new query functions `list_orders_by_status` and `list_ship_groups_by_date` are new exports in `app/services/order_lifecycle.py` — no existing import of that module is affected.

## 10. Open Questions / Assumptions

1. **ORD-011 file exists before ORD-012 lands.** This spec assumes `app/routers/order_lifecycle.py` was created by ORD-011. If ORD-011 is not yet merged, ORD-012 must either create the file or be blocked on ORD-011. (Assumption: ORD-011 is a declared dependency and will be merged first.)

2. **`order_store.py` exists with `query_order_rows`.** ORD-003 and ORD-005 reference `app/services/order_store.py` exposing `get_order_header`, `query_order_rows`. ORD-012's service functions do not use these helpers (they query a GSI directly, not the base table by PK), but the serialisation helper `_header_item_to_dict` may be shared with ORD-011's implementation. If `order_store.py` does not exist yet, `_header_item_to_dict` can be inlined in `order_lifecycle.py`.

3. **`GSI_ORDER_STATUS` contains `ALL` projected attributes.** This spec assumes the ORD-003 GSI definition uses `ProjectionType: ALL`. If only key + specific attributes are projected, the `_header_item_to_dict` helper must either project a minimal set or fetch the base-table item for any missing fields. Assumption: `ALL` projection is used (the ORD-003 spec does not specify otherwise and `ALL` is the simpler choice for an admin view).

4. **Limit cap at 200.** The spec sets a hard cap at 200 items per page, consistent with `scan_abandoned_carts` (`app/services/shoppingcart.py:767`). If a different limit cap is established by ORD-011, ORD-012 should match it.

5. **Date validation is format-only, not calendar-validity.** ORD-012 validates `YYYY-MM-DD` format but does not check whether the date exists on the calendar. A query for `2024-02-31` returns an empty result set rather than a 400. If calendar validation is required, add a `datetime.strptime(date, "%Y-%m-%d")` call in the router and catch `ValueError`.

6. **`ship_date_bucket` uses UTC, not the request's local timezone.** ORD-009 derives `ship_date_bucket` from `ship_ts` in UTC (`datetime.fromtimestamp(ship_ts, tz=timezone.utc)`). The `by-ship-date` endpoint therefore queries by UTC calendar day. The API documentation must make this explicit; callers in non-UTC timezones may need to pass the previous or next UTC day. Assumption: UTC is the correct and consistent choice for this platform.

7. **No `user_id` scoping on admin list endpoints.** This spec treats both endpoints as system-wide admin views with no per-user filtering. If a future requirement for scoped admin views (e.g. "all picking orders for a specific merchant") emerges, it would be added as a separate optional `user_id` query parameter backed by a `FilterExpression` on the GSI result (requiring the `LastEvaluatedKey` loop guard). This is explicitly deferred to a follow-up ticket.

8. **ORD-011 router path prefix.** This spec assumes the router uses paths `/ui/orders/lifecycle/by-status` and `/ui/orders/lifecycle/by-ship-date`. If ORD-011 uses a different prefix (e.g. `/ui/orders/` without `/lifecycle/`), the paths must be adjusted. The ticket text (`ORDER_LIFECYCLE_TICKETS.md:248`) specifies `GET /ui/orders/lifecycle/by-status` explicitly.
