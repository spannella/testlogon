**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days
**Milestone:** 4 — HTTP API Layer
**Depends on:** PTY-004, PTY-005, PTY-006, PTY-007
**Downstream:** PTY-012 (org/admin endpoints), PTY-013 (frontend wrappers), PTY-015 (full test suite)

## 1. Summary & Goal

PTY-011 creates `app/routers/party.py` — the HTTP boundary for the entire OFBiz-style Party/CRM
graph assembled by PTY-004 through PTY-007. The router exposes six route groups under the URL
prefix `/ui/party`, all protected by the existing `require_ui_session` session-cookie dependency
(`app/routers/contacts.py:12`). Every handler is gated by `S.party_crm_enabled`; with the flag
off (the default), every request returns `HTTP 503 {"detail": "party_crm_disabled"}` before any
service code runs.

The router is registered in `app/main.py` immediately after `contacts_router`
(`app/main.py:683`) using the same import pattern. It introduces no new DynamoDB tables, no new
Pydantic models (all of those come from PTY-003), and no changes to the service functions
(PTY-004 through PTY-007). The one design constraint to get right is declaration order: static
path segments (`/parties/lookup`) must appear before dynamic segments (`/parties/{party_id}`)
to prevent FastAPI's declaration-order matching from capturing the literal string
(see CLAUDE.md "schedules before /{export_id}" gotcha).

## 3. Data Model

PTY-011 introduces **no new DynamoDB tables or GSIs**. It is a pure routing layer that delegates
all persistence to the `app/services/party.py` service functions defined by PTY-004 through
PTY-007. The full single-table layout established by PTY-002 is:

| Row type | PK | SK | GSI projections |
|---|---|---|---|
| Party meta | `PARTY#{party_id}` | `META` | `GSI3PK=OWNER#{user_sub}` (if linked), `type=TYPE#{party_type}`, `created_at` (N) → `GSI_CREATED` |
| Party role | `PARTY#{party_id}` | `ROLE#{role_type}` | `GSI1PK=ROLE#{role_type}`, `GSI1SK=PARTY#{party_id}` |
| Party relationship | `PARTY#{party_id}` | `REL#{rel_type}#{to_party_id}` | mirror row `GSI3PK=REL_TO#{to_party_id}`, `GSI3SK=REL#{rel_type}#{from_party_id}` |
| Contact mechanism | `PARTY#{party_id}` | `MECH#{mech_type}#{mech_id}` | `GSI2PK=EMAIL#{norm}` / `PHONE#{e164}` / `POSTAL#{hash16}`, `GSI2SK=PARTY#{party_id}` |

`attr_types={"created_at": "N"}` declared in `scripts/local-ddb-init.py` by PTY-002
(`docs/ofbiz/specs/PTY-002.md:110`). All GSI sort keys (`GSI1SK`, `GSI2SK`, `GSI3SK`) are
String — no override needed.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off response

Every handler checks `_guard()` first. With `S.party_crm_enabled = False`:

```
HTTP 503 {"detail": "party_crm_disabled"}
```

No service function is called, no DynamoDB access occurs, and the contacts surface is entirely
unaffected.

### 5.2 Foreign-party access control

A caller may only read or mutate a party they have a legitimate relationship to. The authorization
model follows a two-tier approach:

**Tier 1 — implicit ownership (PERSON party linked to the calling user_sub):**
After `get_party(party_id)` succeeds, the handler checks whether the party item's `user_sub`
field matches `ctx["user_sub"]`. If so, the caller owns the party directly.

**Tier 2 — relationship-based access (org members, contact graph):**
If the party is not directly owned by the caller, the handler calls
`party_svc.list_relationships(caller_party_id, direction="to")` and verifies at least one
inbound relationship exists whose `from_party_id` equals a party owned by the caller.

If neither tier passes: `HTTP 403 {"detail": "party_access_denied"}`.

The `_assert_party_access(party_id, user_sub)` private helper encapsulates this logic so it can
be called consistently from every route that takes a `{party_id}` path parameter (the same
`_assert_org_admin` pattern established in PTY-008 — `docs/ofbiz/specs/PTY-008.md:338`).

**GET-only relaxation:** `GET /parties/{party_id}` returns 404 (not 403) for unknown party IDs
to avoid leaking party existence to unauthorized callers. `PATCH /parties/{party_id}` and all
sub-collection mutating endpoints return 403 for parties that exist but the caller cannot access.

### 5.3 `POST /parties` — caller's own PERSON party

When `body.party_type == "PERSON"` and `body.user_sub` is unset, the handler auto-sets
`user_sub = ctx["user_sub"]` so the created PERSON is immediately linked to the session.
`create_party` is idempotent via `correlation_id`; the handler forwards `body.correlation_id`
if present.

### 5.4 `GET /parties/lookup` — must be first among `/parties/*` routes

`/parties/lookup` is declared before `GET /parties/{party_id}` in the router file. FastAPI
matches routes in declaration order (`docs/ofbiz/specs/PTY-011.md §1` and CLAUDE.md §"Router
conventions"). If the order were reversed, a request to `/parties/lookup` would be captured by
the dynamic route and `get_party("lookup")` would return 404 rather than executing the lookup.

The lookup handler calls `party_svc.find_party_by_contact(mech_type, value)` (PTY-007).
404 is returned when no party matches; 503 is returned if `S.party_crm_enabled` is off
(same `_guard()` call). The `value` parameter is passed raw — normalization happens inside
`find_party_by_contact` (which calls `normalize_email` / `normalize_phone` /
`normalize_address_payload` from `app/core/normalize.py:60,66` and
`app/services/addresses.py:39` as documented in `docs/ofbiz/specs/PTY-007.md:15-17`).

### 5.5 `PATCH /parties/{party_id}` — status-only update

The only mutable field on a party at the router layer is `status`. Any attempt to change
`party_type` or `user_sub` through the router is rejected with 400. The `CrmPartyStatusIn`
model contains only a `status: CrmPartyStatus` field. The service's `update_party_status`
(PTY-004) validates allowed transitions (not `MERGED` via the API — that is reserved for
a future dedup operation).

### 5.6 Relationship `direction` parameter

`GET /parties/{party_id}/relationships` accepts `direction` in `{"from", "to", "both"}`.
Unknown values return 400 before calling the service. This avoids passing an invalid string into
`list_relationships`, which raises `ValueError` internally.

### 5.7 Idempotent role add

`POST /parties/{party_id}/roles` returns 200 (not 201) if the role already exists, consistent
with the PTY-005 idempotency guarantee (`docs/ofbiz/specs/PTY-005.md:102-107`). The response
body is the existing `CrmPartyRoleOut`. 201 is used only on actual creation.

Implementation: call `add_role(party_id, role_type)` — it returns the existing row on a
conditional `ConditionalCheckFailedException`. Use the returned dict's `_created` flag (or
compare `created_at` to `now_ts()` within a short window) to set the status code. Alternatively,
inspect the `T.party.get_item` response before writing; however, the recommended path is to
rely on the service's `ConditionalCheckFailedException` path per PTY-005 spec
(`docs/ofbiz/specs/PTY-005.md:216-222`) and return 200 on replay.

### 5.8 Relationship deletion via query parameters

`DELETE /parties/{party_id}/relationships` uses query parameters (`to_party_id`,
`relationship_type`) rather than a nested path segment. This avoids encoding
`REL#{rel_type}#{to_party_id}` into the URL and simplifies client construction. A DELETE with
body is valid per HTTP but avoided here for consistency with the contacts router's
`DELETE /contacts/{contact_id}` pattern (`app/routers/contacts.py:114`).

### 5.9 404 vs 403 ordering

For all `{party_id}` routes:
1. Call `get_party(party_id)`. If `None` → 404 `"party_not_found"`.
2. Call `_assert_party_access(party)`. If fails → 403 `"party_access_denied"`.

This order prevents the 403 from leaking party existence to callers who do not have access.

### 5.10 Empty `list_parties` response

`GET /parties` with no matching rows returns `{"parties": [], "cursor": null}`, not 404.
This matches the convention used by `list_contacts` (`app/routers/contacts.py:81`) which
returns `{"contacts": contacts}` (an empty list when there are no rows) on an empty result
(verified — the return is at line 81, `return {"contacts": contacts}`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

All handlers delegate to `app/services/party.py` which writes to `T.party` — the same
DynamoDB table in both environments. No `if S.dev_mode:` branch exists in the router or
service. The table is backed by DynamoDB Local in dev (port 8001) and real DynamoDB in prod;
from the router's perspective, the call signature is identical (`docs/ofbiz/specs/PTY-002.md:45`).

### 7.2 Idempotency

Party creation and relationship creation use deterministic-ID idempotency:

- `POST /parties` with the same `correlation_id` in the body → the service derives
  `party_id = sha256(correlation_id)[:32]` (sha256-derivation pattern verified at
  `app/services/commerce_order_service.py:67`) and issues a conditional put
  (`ConditionExpression="attribute_not_exists(PK)"`). On replay, the existing item is returned
  with `HTTP 201` (the router always returns 201; the service absorbs the duplicate silently).
  Note: `commerce_order_service.py` uses the same sha256-derivation idiom but does **not** use
  a conditional put itself — the `attribute_not_exists` guard is specified by PTY-004 for the
  party service. See `docs/ofbiz/specs/PTY-004.md:80` for details.

- `POST /parties/{id}/roles` with a duplicate role → `add_role` is idempotent; the router
  returns `HTTP 200` on replay (see §5.7).

- `POST /parties/{id}/relationships` with the same structural triple → `create_relationship`'s
  conditional put on `PK=PARTY#{from}`, `SK=REL#{type}#{to}` absorbs the duplicate; the router
  returns `HTTP 201` on both first write and replay (the service returns the existing item either
  way, per `docs/ofbiz/specs/PTY-006.md:96-100`).

### 7.3 CSRF

All non-GET routes require the `x-csrf-token` header matching the session's stored `csrf_token`
and the `ui_csrf` cookie. This validation is enforced entirely inside `require_ui_session`
(`app/services/sessions.py:429-436`) before the ctx dict is returned — `csrf_token` is NOT a
key in the returned ctx dict (verified: `app/services/sessions.py:454-462`).
No additional CSRF logic is needed in the router.

### 7.4 Input validation

- `party_type` in `POST /parties` is validated by `CrmPartyType` enum (Pydantic raises
  `422 Unprocessable Entity` on unknown value).
- `role_type` in `POST /parties/{id}/roles` is validated by `CrmPartyRoleType` enum.
- `relationship_type` in `POST /parties/{id}/relationships` is validated by
  `CrmRelationshipType` enum.
- `direction` in `GET /parties/{id}/relationships` is validated inline:
  `if direction not in {"from", "to", "both"}: raise HTTPException(400, ...)`.
- `mech_type` in query params is validated against `CrmContactMechType` before calling service.
- `value` normalization (email/phone/postal) occurs inside the service layer; any validation
  failure raises `HTTPException(400, ...)` which propagates to the caller.

### 7.5 No new secrets or encryption

The router handles no sensitive credentials, tokens, or KMS calls. Contact mechanism values
(email, phone, postal) are stored in DynamoDB in normalized plaintext — they are business
identifiers, not secrets.

## 10. Open Questions / Assumptions

1. **`_assert_party_access` granularity**: The spec assumes a two-tier check (direct `user_sub`
   ownership → relationship graph). An alternative is allowing any authenticated user to read any
   party (public-read semantics), restricting 403 only on mutations. The current design is
   conservative (403 on unauthorized reads too). **Assumption:** privacy-first — 403/404 on
   reads as well, pending product decision.

2. **`list_parties` scope**: Does `GET /parties` list only parties the caller owns/can access, or
   all parties in the system (admin-style global list)? **Assumption:** scoped to parties where
   `GSI3PK=OWNER#{user_sub}` (i.e. the caller's own party graph). A global admin listing is
   deferred to PTY-012.

3. **`POST /parties` — auto-create caller's PERSON party**: If the caller has no PERSON party
   yet and creates one with `party_type=PERSON`, the `user_sub` is auto-set. Should a second
   `POST /parties` with `party_type=PERSON` (no `correlation_id`) silently create a second,
   distinct PERSON? **Assumption:** yes — idempotency is opt-in via `correlation_id`.
   `ensure_person_party` (PTY-010) provides the "get or create" semantic separately.

4. **`PATCH /parties/{party_id}` — allowed transitions**: The spec defers transition validation to
   the service layer (`update_party_status` in PTY-004). It is assumed the service rejects any
   attempted transition to `MERGED` via the API (reserved for PTY future dedup flow).

5. **Relationship DELETE method**: Using `DELETE` with query parameters (not a request body) is
   unusual. An alternative is `DELETE /parties/{id}/relationships/{rel_type}/{to_party_id}`.
   **Assumption:** query-param DELETE is simpler for the frontend (avoids encoding slashes in
   `{rel_type}#{to_party_id}`); the convention matches the `remove_contact_mech` delete which
   uses path params only.

6. **Rate limiting**: No per-endpoint rate limiting is specified. **Assumption:** existing global
   session-based rate limiting (if any) is sufficient for Phase 1; per-endpoint caps deferred.

7. **`PTY-003` name conflict verification**: It is assumed `CrmPartyIn`, `CrmPartyOut`, etc. do
   not collide with any models added since the PTY-003 spec was written. The `Crm` prefix is
   specifically chosen to avoid the Watch Party `CreatePartyIn`/`PartyOut` names at
   `app/models.py:4085,4109`. This should be verified against the current `app/models.py` before
   implementation.

8. **`mech_type` validation on query params**: `GET /parties/{id}/mechs?mech_type=...` passes the
   value as a plain string query parameter (FastAPI cannot auto-validate an enum from a Query
   unless the type annotation is the enum type). **Assumption:** the handler validates the string
   inline: `if mech_type and mech_type not in CrmContactMechType._value2member_map_: raise
   HTTPException(400, ...)`.
