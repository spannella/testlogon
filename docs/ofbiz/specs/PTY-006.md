# PTY-006 — Party relationship service

**Type:** Feature | **Priority:** P1 | **Estimate:** 2 days  
**Milestone:** 2 — Party Service Core  
**Depends on:** PTY-004 (`app/services/party.py` + `T.party` handle), PTY-005 (role service; shares same module)

---

## 1. Summary & Goal

PTY-006 extends `app/services/party.py` — created by PTY-004 and extended by PTY-005 — with three
relationship-management functions:

| Function | Purpose |
|---|---|
| `create_relationship(from_party_id, to_party_id, relationship_type, *, correlation_id=None) -> dict` | Idempotent write of a primary edge row plus a mirror row on `GSI3` so inbound queries are O(1) |
| `list_relationships(party_id, *, direction="from"\|"to"\|"both", cursor=None, limit=50) -> dict` | Paginated retrieval of outbound, inbound, or all edges involving a party |
| `delete_relationship(from_party_id, to_party_id, relationship_type) -> None` | Removes both the primary and mirror rows atomically |

Three new router endpoints are added to `app/routers/party.py` under the existing `/ui/party` prefix.

The service stores edges as DynamoDB items on the existing `party` single-table (PTY-002), using the
already-provisioned `GSI3` index for inbound (to-side) queries. No new tables or GSIs are
introduced. The feature is entirely additive: with `S.party_crm_enabled` off (the default) all
three endpoints return HTTP 503 and the service functions are never invoked through the normal
request path.

### 2.4 Deterministic-ID idempotency pattern

`app/services/commerce_order_service.py:67` establishes the canonical hash derivation:

```python
order_id = hashlib.sha256(corr.encode("utf-8")).hexdigest()[:32]
```

Note: `commerce_order_service` uses an **unconditional** `put_item` (line 85) — it does not use
`ConditionExpression`. The conditional-put idempotency pattern with `attribute_not_exists` is
demonstrated instead by `app/services/sftp_mounts.py:193`,
`app/services/projects_store.py:110`, and `app/services/file_mounts.py:159`. On
`ConditionalCheckFailedException` the existing record is returned and no audit event is emitted.
PTY-006 uses the same pattern: when `correlation_id` is supplied, the `rel_id` (a non-key
attribute that ties primary and mirror rows) is derived as
`hashlib.sha256(correlation_id.encode()).hexdigest()[:32]`; when absent, `uuid4().hex` is used.
The relationship's identity is structural — its DynamoDB primary key
`PK=PARTY#{from}`, `SK=REL#{rel_type}#{to}` is deterministic purely from the three identifying
fields, so no separate `correlation_id` hash is needed for the PK itself. The `correlation_id`
is stored as a plain attribute for audit; the conditional put on the structural PK/SK already
provides natural idempotency.

## 3. Data Model

### 3.1 Primary relationship row

```
PK  = "PARTY#{from_party_id}"
SK  = "REL#{relationship_type}#{to_party_id}"
```

Full item:

```json
{
  "PK":               "PARTY#{from_party_id}",
  "SK":               "REL#{relationship_type}#{to_party_id}",
  "from_party_id":    "<hex32>",
  "to_party_id":      "<hex32>",
  "relationship_type":"EMPLOYMENT",
  "rel_id":           "<uuid4().hex or sha256(correlation_id)[:32]>",
  "created_at":       1749200000,
  "correlation_id":   "<value> | null"
}
```

**Notes:**

- `rel_id` is a bookkeeping attribute tying primary + mirror rows — useful for audit and for
  future cross-table references. It is NOT the DynamoDB key.
- `created_at` is an integer Unix seconds from `now_ts()`. It is NOT projected onto `GSI3`
  (no numeric sort needed there); `GSI3SK` is a plain String.
- No `GSI_CREATED` keys are written on relationship rows — the listing index is per-party (via
  the base table's `PK` + `SK begins_with "REL#"` query), not cross-party.

### 3.2 Mirror row (inbound / to-side)

```
PK  = "PARTY#{to_party_id}"
SK  = "MIRROR#{relationship_type}#{from_party_id}"
```

Full item:

```json
{
  "PK":               "PARTY#{to_party_id}",
  "SK":               "MIRROR#{relationship_type}#{from_party_id}",
  "from_party_id":    "<hex32>",
  "to_party_id":      "<hex32>",
  "relationship_type":"EMPLOYMENT",
  "rel_id":           "<same rel_id as primary row>",
  "created_at":       1749200000,
  "GSI3PK":           "REL_TO#{to_party_id}",
  "GSI3SK":           "REL#{relationship_type}#{from_party_id}"
}
```

**Notes:**

- The mirror row lives under the *to-party*'s partition (`PK=PARTY#{to_party_id}`) with a
  `MIRROR#` SK prefix, so `list_relationships(party_id, direction="to")` can query the base
  table with `PK=PARTY#{party_id}` + `SK begins_with "MIRROR#"` — no GSI needed for the
  to-side when querying per-party. The `GSI3PK/GSI3SK` fields additionally enable the
  inbound-only reverse lookup `REL_TO#{to_party_id}` across all parties, which is used by
  PTY-008 (`list_members` via `GROUP_MEMBER` relationships) and PTY-009 (contacts migration).
- `GSI3SK = "REL#{relationship_type}#{from_party_id}"` (String, no `attr_types` override
  needed — already String by default).

### 3.3 No `scripts/local-ddb-init.py` changes

PTY-006 writes no new tables. `GSI3` already exists on the `party` table from PTY-002
(`docs/ofbiz/specs/PTY-002.md:94-115`). The `GSI3PK` / `GSI3SK` attribute names are already
declared in `attr_types` (String). No schema change is required.

### 3.4 SK namespace summary for `party` table

After PTY-004, PTY-005, and PTY-006 the SK space within a single `PK=PARTY#{id}` partition is:

| SK prefix | Row type | Managed by |
|---|---|---|
| `META` | Party meta | PTY-004 |
| `ROLE#{role_type}` | Party role | PTY-005 |
| `REL#{rel_type}#{to_id}` | Outbound relationship (primary) | PTY-006 |
| `MIRROR#{rel_type}#{from_id}` | Inbound relationship (mirror) | PTY-006 |
| `MECH#{mech_id}` | Contact mechanism | PTY-007 |

## 4. API / Service Design

### 4.1 Service functions in `app/services/party.py`

Three new functions appended to the existing module:

```python
def create_relationship(
    from_party_id: str,
    to_party_id: str,
    relationship_type: str,
    *,
    correlation_id: Optional[str] = None,
) -> Dict[str, Any]:
    ...

def list_relationships(
    party_id: str,
    *,
    direction: str = "both",
    cursor: Optional[str] = None,
    limit: int = 50,
) -> Dict[str, Any]:
    ...

def delete_relationship(
    from_party_id: str,
    to_party_id: str,
    relationship_type: str,
) -> None:
    ...
```

#### `create_relationship` — detailed contract

1. **Validate inputs:**
   - `from_party_id != to_party_id`; raise `ValueError("self_relationship_not_allowed")` otherwise.
   - `relationship_type` in `{r.value for r in CrmRelationshipType}`; raise `ValueError("invalid_relationship_type")` otherwise.
   - `len(from_party_id) <= 64` and `len(to_party_id) <= 64`; raise `ValueError("party_id_too_long")` otherwise (guards against unbounded SK construction).

2. **Derive `rel_id`:**
   - If `correlation_id`: `rel_id = hashlib.sha256(correlation_id.encode()).hexdigest()[:32]`
   - Else: `rel_id = uuid.uuid4().hex`

3. **Build primary item** (`PK=PARTY#{from_party_id}`, `SK=REL#{relationship_type}#{to_party_id}`):
   ```python
   primary = {
       "PK": f"PARTY#{from_party_id}",
       "SK": f"REL#{relationship_type}#{to_party_id}",
       "from_party_id": from_party_id,
       "to_party_id":   to_party_id,
       "relationship_type": relationship_type,
       "rel_id":        rel_id,
       "created_at":    now_ts(),
       "correlation_id": correlation_id,
   }
   ```

4. **Build mirror item** (`PK=PARTY#{to_party_id}`, `SK=MIRROR#{relationship_type}#{from_party_id}`):
   ```python
   mirror = {
       "PK":    f"PARTY#{to_party_id}",
       "SK":    f"MIRROR#{relationship_type}#{from_party_id}",
       "from_party_id": from_party_id,
       "to_party_id":   to_party_id,
       "relationship_type": relationship_type,
       "rel_id":        rel_id,
       "created_at":    primary["created_at"],
       "GSI3PK":        f"REL_TO#{to_party_id}",
       "GSI3SK":        f"REL#{relationship_type}#{from_party_id}",
   }
   ```

5. **Write atomically** via `transact_write_items` with
   `ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)"` on the
   primary item only (the mirror's condition is not independently guarded — the primary
   condition is sufficient because the two rows share the same uniqueness invariant; the
   mirror SK is derived deterministically from the same three fields). On
   `ConditionalCheckFailedException` (DynamoDB code `"TransactionCanceledException"` with
   cancellation reason `ConditionalCheckFailed`): fetch and return the existing primary row
   without emitting an audit event (idempotent replay).

6. **Emit audit event** on success:
   ```python
   audit_event(
       "party_relationship_created",
       from_party_id,
       None,
       from_party_id=from_party_id,
       to_party_id=to_party_id,
       relationship_type=relationship_type,
       rel_id=rel_id,
   )
   ```

7. **Return** the primary item dict (caller strips `PK`/`SK` before returning to the API).

#### `list_relationships` — detailed contract

Returns `{"relationships": [...], "next_cursor": str | None, "count": int}`.

`direction` parameter handling:

| `direction` | Query strategy | Notes |
|---|---|---|
| `"from"` | Base-table query: `PK=PARTY#{party_id}` + `SK begins_with "REL#"` | Outbound edges only |
| `"to"` | Base-table query: `PK=PARTY#{party_id}` + `SK begins_with "MIRROR#"` | Inbound edges (mirror rows) |
| `"both"` | Two sequential queries — `"from"` then `"to"` — each with `limit // 2` (ceiling); merge + re-sort by `created_at` descending | No `next_cursor` when `direction="both"` |

For `"from"` and `"to"`:
- `ScanIndexForward=False` (newest-first by SK order within the PK partition — SK is string, so `REL#EMPLOYMENT#abc` < `REL#GROUP_MEMBER#xyz` lexicographically; ordering is consistent per-call but not strictly time-ordered when `relationship_type` varies; if strict time order is required, add `created_at` as a GSI sort — deferred).
- `Limit = min(limit, 100)`
- `ExclusiveStartKey = decode_cursor(cursor)` when cursor is not `None`
- `next_cursor = encode_cursor(resp.get("LastEvaluatedKey"))`

For `"both"`:
- `next_cursor` is always `None` (two-query merge invalidates DynamoDB's continuation key — same
  rationale as PTY-004's `list_parties(party_type=None)` from `docs/ofbiz/specs/PTY-004.md:277-280`).
- Each query capped to `ceil(limit / 2)` items.
- Result list deduplication: there should be no overlap between `REL#` and `MIRROR#` SK rows for
  the same party.

The response `relationships` list is a list of `CrmRelationshipOut`-compatible dicts (caller is
responsible for coercing `created_at` from Decimal to int via `int(item["created_at"])`).

#### `delete_relationship` — detailed contract

1. **Validate inputs:** same guards as `create_relationship` (type check, self-check, length
   check). Raise `ValueError` with the same codes.

2. **Build the two keys:**
   ```python
   primary_key = {"PK": f"PARTY#{from_party_id}", "SK": f"REL#{relationship_type}#{to_party_id}"}
   mirror_key  = {"PK": f"PARTY#{to_party_id}", "SK": f"MIRROR#{relationship_type}#{from_party_id}"}
   ```

3. **Delete atomically** via `transact_write_items` with two `Delete` operations (no
   `ConditionExpression` — deleting a non-existent key is silently ignored by DynamoDB).

4. **No error on missing relationship** — a delete of a non-existent edge is a no-op (no
   `ConditionalCheckFailed`, no exception). This matches the PTY-005 `remove_role` semantics
   (`docs/ofbiz/specs/PTY-005.md:548-552`: "removing a non-existent role does not error").

5. **Emit audit event** unconditionally (even if rows were absent — the operation is valid):
   ```python
   audit_event(
       "party_relationship_deleted",
       from_party_id,
       None,
       from_party_id=from_party_id,
       to_party_id=to_party_id,
       relationship_type=relationship_type,
   )
   ```

### 4.2 `_ddb_client()` helper

A module-level private helper for the low-level client needed by `transact_write_items`:

```python
def _ddb_client() -> Any:
    """Low-level DynamoDB client for transact_write_items.

    The resource-attached client mangles typed items in transact_write_items
    (observed against both moto and DynamoDB Local). A fresh low-level client
    built from the shared ddb resource's endpoint/region/credentials inherits
    the correct dev/prod endpoint. See agent_orchestrator._ddb_lowlevel_client
    for the same pattern (app/services/agent_orchestrator.py:25-51).
    """
    from app.core.aws import ddb  # local import: honours monkeypatched resource
    meta = ddb.meta.client.meta
    creds = getattr(ddb.meta.client._request_signer, "_credentials", None)
    kwargs: Dict[str, Any] = {
        "region_name": meta.region_name,
        "endpoint_url": meta.endpoint_url,
    }
    if creds is not None:
        kwargs["aws_access_key_id"] = creds.access_key
        kwargs["aws_secret_access_key"] = creds.secret_key
        if creds.token:
            kwargs["aws_session_token"] = creds.token
    return boto3.client("dynamodb", **kwargs)
```

Import `boto3` at the top of `app/services/party.py` (it is not currently needed for the first
four functions — PTY-004's DDB access goes through `T.party` which is a `_FloatSafeTable` resource
wrapper. The `import boto3` line must be added when PTY-006 is merged).

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent create replay

When the same `(from_party_id, to_party_id, relationship_type)` triple is written twice:

1. **First call:** `transact_write_items` succeeds → both rows written → audit event emitted →
   primary item dict returned.
2. **Second call:** `transact_write_items` raises `TransactionCanceledException` with
   `CancellationReasons[0].Code == "ConditionalCheckFailed"` → service fetches the existing
   primary row via `T.party.get_item(Key={"PK": ..., "SK": ...})` and returns it, no audit event.

The caller receives the same `CrmRelationshipOut` shape in both cases. HTTP status is `201` for
both (the endpoint cannot distinguish first-write from replay at the service layer without
inspecting the exception, which is intentionally not exposed at the HTTP boundary).

Note: if `correlation_id` is supplied it affects only `rel_id` derivation, not the PK/SK (which
are already deterministic). The conditional put is on the PK/SK; `correlation_id` collisions are
therefore not a concern for the relationship's structural identity.

### 5.2 Self-relationship rejection

`from_party_id == to_party_id` is rejected at two layers:
1. Pydantic `CrmRelationshipIn._parties_differ` validator raises `ValueError("from_party_id and to_party_id must differ")`, propagated by FastAPI as HTTP 422 before the service is reached.
2. Service-layer guard raises `ValueError("self_relationship_not_allowed")` for direct callers.

The two error messages differ intentionally (Pydantic message is end-user-facing; service message is for programmatic callers). The HTTP response is 422 in both cases.

### 5.3 Mirror row consistency

Primary and mirror rows are always written or deleted together via `transact_write_items` (atomic
DynamoDB transaction). This means:

- Partial writes are impossible: either both rows exist or neither does.
- `list_relationships(party_id, direction="from")` and `list_relationships(party_id, direction="to")`
  will always agree: every primary row has a corresponding mirror, and vice versa.
- `direction="both"` merges results from both base-table queries — there is no overlap because
  `REL#` rows appear only under the from-party's partition and `MIRROR#` rows only under the
  to-party's partition.

### 5.4 Delete of non-existent relationship

`delete_relationship` issues a `transact_write_items` with two `Delete` actions and no
`ConditionExpression`. DynamoDB silently ignores a `Delete` for a non-existent key. The function
always emits an audit event (for operational visibility) and returns without error. This matches
the PTY-005 `remove_role` contract (`docs/ofbiz/specs/PTY-005.md:548-552`: "removing a non-existent
role does not error").

### 5.5 `relationship_type` validation

The service validates `relationship_type` against the live enum values:
```python
_VALID_REL_TYPES = {r.value for r in CrmRelationshipType}
```

where `CrmRelationshipType` is imported from `app.models` at the top of the module
(`from app.models import CrmRelationshipType`). This import is added by PTY-006; prior PTY
tickets did not require model imports in the service layer. Alternatively, the service can define
its own `_VALID_REL_TYPES = {"EMPLOYMENT", "GROUP_MEMBER", "CONTACT_REL", "OWNER"}` as a plain
set (no import dependency) — which is the preferred approach to avoid circular imports between
`app/services/party.py` and `app/models.py`. **Assumed approach:** inline set constant
(see §10 — Open Questions #3).

### 5.6 `TransactionCanceledException` detection

`transact_write_items` raises `ClientError` with `response["Error"]["Code"] == "TransactionCanceledException"`. The cancellation reasons are in
`response["Error"]["Message"]` or `response["CancellationReasons"]`. The service catches:

```python
except ClientError as exc:
    code = exc.response.get("Error", {}).get("Code", "")
    if code == "TransactionCanceledException":
        # Idempotent replay — fetch and return existing primary row
        existing = T.party.get_item(
            Key={"PK": f"PARTY#{from_party_id}", "SK": f"REL#{relationship_type}#{to_party_id}"}
        ).get("Item")
        if existing:
            return existing
        raise  # If row genuinely absent, re-raise (unexpected state)
    raise
```

### 5.7 `list_relationships` ordering

Base-table queries on `PK=PARTY#{id}` with `SK begins_with "REL#"` return rows in SK
lexicographic order (`ScanIndexForward=False` reverses to descending). Within a single
`relationship_type`, ordering is by `to_party_id` descending (a random hex32, effectively
random). Strict `created_at`-based ordering within a party's relationships would require a
separate `created_at`-sorted GSI or a local sort in Python after fetching all items. For Phase 1
this is not required; the listing is "most recently added" in a loose sense only when there is a
single `relationship_type`. This limitation is documented in §10 — Open Questions #4.

### 5.8 `direction="both"` and no cursor

When `direction="both"`, the function issues two queries and merges the results. Because each query
has its own independent `LastEvaluatedKey`, no single cursor can represent "resume both queries at
position X". The function therefore returns `next_cursor=None` always for `direction="both"`.
Callers who need deep pagination must use `direction="from"` or `direction="to"` explicitly.
This is documented in the endpoint response and matches the PTY-004 `list_parties(party_type=None)`
precedent (`docs/ofbiz/specs/PTY-004.md:449`).

### 5.9 Decimal coercion from DynamoDB

`created_at` is stored as `N` on the primary row but is NOT part of any GSI on relationship rows.
When DynamoDB returns the item via `get_item` or `query`, the resource layer returns it as
`Decimal`. The `_item_to_rel_out` helper coerces to `int` — same pattern as PTY-004's
`_item_to_party_out` (`docs/ofbiz/specs/PTY-004.md:404-413`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

There is no `S.dev_mode` branch in `app/services/party.py`. The `transact_write_items` call works
identically in dev (DynamoDB Local at `http://localhost:8001`, configured via `.env.local`) and
in prod (real DynamoDB). DynamoDB Local has supported transactions since version 1.15 (2019).
The `_ddb_client()` helper inherits the endpoint from the shared `ddb` resource, so no
environment-specific URL is hardcoded. This matches the `agent_orchestrator._ddb_lowlevel_client`
approach (`app/services/agent_orchestrator.py:25-51`).

### Idempotency

Write idempotency is enforced at the DynamoDB layer via `attribute_not_exists(PK) AND attribute_not_exists(SK)` in the `transact_write_items` condition on the primary item. This is an atomic check-and-set; there is no TOCTOU race window. Idempotency for delete is provided by DynamoDB's silent-ignore behaviour on non-existent keys. No application-level pre-check is used.

### Security

- **No PII in keys:** All PK/SK values contain only `party_id` (32-char hex), `relationship_type` (uppercase ASCII enum), and the static prefixes `PARTY#`, `REL#`, `MIRROR#`, `REL_TO#`. No email, name, or other PII appears in any key.
- **No money-out path:** Party relationships carry no billing data. The billing/GL ledger constraint in the cross-cutting requirements does not apply here.
- **Input length guards:** `from_party_id` and `to_party_id` are capped at 64 chars before SK construction to prevent unbounded key lengths. All generated IDs are 32-char hex (well within this limit).
- **No ownership enforcement at this layer:** The router accepts any authenticated session and does not scope relationship reads or writes to the authenticated user's own parties. Ownership enforcement is deferred to a later milestone (same decision as PTY-004 §7). Direct callers can read relationships between any two parties.
- **`relationship_type` is validated before use in SK:** Prevents SK injection via specially crafted type strings (e.g. strings containing `#` separators). The enum constant set `_VALID_REL_TYPES` rejects any value not in the known set.
- **Audit trail:** Every successful create and delete emits an `audit_event` to `T.alerts` via the existing `app/services/alerts.py:644` mechanism.

### `app/routers/party.py` route ordering

The new routes are appended after the existing PTY-004 and PTY-005 routes. Route declaration order
matters in FastAPI (first match wins). The new paths are:
- `POST /ui/party/relationships` — static path segment `relationships`, declared before
  `GET /ui/party/{party_id}/relationships`. FastAPI evaluates `POST` and `GET` separately so
  there is no ambiguity here.
- `GET /ui/party/{party_id}/relationships` — path parameter `party_id` cannot accidentally
  match `relationships` because both are GET routes and FastAPI matches the most specific
  (static) first. **Caution:** if `GET /ui/party/{party_id}` (the per-party fetch from PTY-004)
  is declared before `GET /ui/party/{party_id}/relationships`, they do not conflict (FastAPI
  considers path segment count). However, `GET /ui/party/{party_id}/roles` (PTY-005) uses the
  same two-segment pattern — declaration order between `/roles` and `/relationships` does not
  matter since they use different terminal segments.
- `DELETE /ui/party/relationships/{from_party_id}/{relationship_type}/{to_party_id}` — four
  static+dynamic segments, no conflict with any existing route.

### `app/main.py`

No new `include_router` call is needed — `app/routers/party.py` was registered by PTY-004. PTY-006
only appends functions/endpoints inside files that are already registered.

### Database migration

No new DynamoDB tables. In dev environments, `just restart` wipes and recreates all tables;
no migration is needed. In production, `REL#` and `MIRROR#` SK rows are simply absent before
PTY-006 ships — no backfill required because the relationship graph starts empty.

## 10. Open Questions / Assumptions

1. **PTY-005 already merged.** This spec assumes `app/services/party.py` already contains the
   PTY-005 role functions (`add_role`, `remove_role`, `list_roles`, `parties_with_role`) when
   PTY-006 is implemented. If PTY-005 is delayed, PTY-006 can be implemented independently since
   it extends the same file with non-overlapping SK prefixes — the two deliverables do not share
   any code path.

2. **`CrmRelationshipIn` and `CrmRelationshipOut` available from PTY-003.** The router imports
   these models. If PTY-003 is delayed, the router can declare minimal inline Pydantic models
   to unblock PTY-006, with the inline models replaced by the PTY-003 imports once that ticket
   merges.

3. **Inline `_VALID_REL_TYPES` set rather than importing `CrmRelationshipType`.** Importing
   `CrmRelationshipType` from `app.models` in `app/services/party.py` risks a circular import
   because `app/models.py` imports from `app/core/normalize.py`, and `app/core/normalize.py`
   does not import from any service. The import chain is safe in one direction (`models → normalize`)
   but fragile if `party.py` later imports something that imports `models`. The safer approach is
   to define `_VALID_REL_TYPES = frozenset({"EMPLOYMENT", "GROUP_MEMBER", "CONTACT_REL", "OWNER"})`
   as an inline constant and keep `app/services/party.py` model-import-free (matching the
   PTY-004 pattern where the service works with plain dicts).

4. **Strict `created_at`-ordered listing deferred.** `list_relationships` returns items in SK
   lexicographic order, not strict chronological order. If callers require strict creation-time
   ordering (e.g. "show newest relationship first"), a `created_at`-sorted GSI or client-side
   sort would be needed. Neither is in scope for Phase 1. This is acceptable given the expected
   small cardinality (dozens of relationships per party in the B2B use case).

5. **`require_ui_session` import path.** PTY-004's spec (`docs/ofbiz/specs/PTY-004.md:310`) uses
   `from app.services.sessions import require_ui_session`, matching `app/routers/contacts.py:12`.
   PTY-006 follows the same import.

6. **`CrmRelationshipListOut` added to `app/models.py`.** PTY-003 does not define a list-response
   wrapper for relationships. PTY-006 adds `CrmRelationshipListOut` to `app/models.py`. The
   implementer must confirm PTY-003 has not already added this model before inserting it.

7. **Atomic delete semantics under partial failure.** If the `transact_write_items` delete call
   fails mid-flight (e.g. network timeout after primary is deleted but before mirror is deleted),
   the table would be in an inconsistent state. DynamoDB transactions are all-or-nothing at the
   DynamoDB level — a `TransactionCanceledException` means neither write succeeded. A timeout
   after the request leaves the client but before the response arrives may leave the transaction
   indeterminate. In this edge case a retry of `delete_relationship` is safe (DynamoDB silently
   ignores deletes of non-existent keys), so the application is eventually consistent.

8. **`boto3` import addition.** PTY-004's `app/services/party.py` uses only `T.party` (a resource
   wrapper) and has no direct `import boto3`. PTY-006's `_ddb_client()` needs `boto3.client(...)`.
   The implementer must add `import boto3` to the top-level imports of `app/services/party.py`.
