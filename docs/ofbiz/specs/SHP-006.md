# SHP-006 — Shipping-rate estimation engine

## 1. Summary & Goal

SHP-006 delivers `app/services/shipping_rates.py` — a pure-computation service that takes a destination ZIP code plus a list of line items (each carrying a quantity and an optional per-SKU shipping weight) and returns a `ShippingRateQuote` containing one `ShippingRateOption` per enabled carrier/method pair.

The engine is built around two interchangeable backends:

1. **Built-in deterministic estimator** (always available, no external calls): computes a rate from the method's `base_rate_cents`, a weight-based breakpoint ladder, and a flat zone modifier keyed on destination region. All decisions are pure functions of the input — given the same inputs the output is bit-for-bit identical.
2. **UPS Rating API seam** (live, gated by config): activated only when `S.ups_base_url` and `S.ups_client_id` are non-empty AND `S.shipping_rate_estimation_enabled` is `True`. The seam delegates to the existing `app/services/ups.ups_access_token()` / `_ups_post()` helpers (`app/services/ups.py:30`, `:53`). The response shape from the seam is coerced into identical `ShippingRateOption` objects — **no `dev_mode` branch in the result shape** (SECOPS-007 parity).

Total billable weight for a cart/order is derived by summing `quantity × per-SKU weight_oz` across all line items, falling back to a configurable default weight per unit when the catalog item has no `shipping_weight_oz` in its `attributes` map.

This ticket is purely a service layer — no router, no Pydantic model definitions, no `app/main.py` changes. Those belong to SHP-007.

## 3. Data Model

SHP-006 is a **stateless computation service** — it reads from `T.shipping_carriers` and `T.catalog` but writes nothing. No new DynamoDB tables. No new GSIs. `ShippingRateQuote` / `ShippingRateOption` are ephemeral response objects, not persisted rows.

The two table handles the service reads from:

| Handle | Table | Access pattern |
|---|---|---|
| `T.shipping_carriers` | `shipping_carriers` | Read all enabled methods via `list_enabled_methods_all_carriers()` (SHP-004 service call, not direct table access) |
| `T.catalog` | catalog | `get_item(Key=_catalog_item_key(category_id, item_id))` → `{"PK": f"CAT#{category_id}", "SK": f"ITEM#{item_id}"}` for per-SKU weight lookup (same helper as `app/services/shoppingcart.py:42–43`) |

Neither table is mutated by this service. The service owns no DynamoDB rows.

### 3.1 Weight-breakpoint ladder (in-memory constants)

The built-in estimator uses an in-memory breakpoint ladder per method code. Each breakpoint maps a minimum weight (oz) to an incremental rate in cents. The ladder is evaluated as: find the highest breakpoint whose `min_oz` ≤ `total_billed_weight_oz`, add `ladder_entry.increment_cents × ceil(total_billed_weight_oz / 16)` to `base_rate_cents`. This is evaluated per method row.

Default ladder (module-level constant `_WEIGHT_LADDER`, overridable via settings in a future ticket):

| method_code | min_oz | increment_cents_per_lb |
|---|---|---|
| `ground` | 0 | 15 |
| `ground` | 160 | 25 (>10 lbs) |
| `express` | 0 | 45 |
| `express` | 160 | 65 |
| `overnight` | 0 | 80 |
| `overnight` | 160 | 120 |
| `economy` | 0 | 10 |
| `economy` | 160 | 18 |
| `flat_rate` | 0 | 0 (flat rate — no weight increment) |

These are intentionally conservative defaults. Operators can override `base_rate_cents` and transition-day bands via the admin method CRUD (SHP-005), or replace the entire estimator with the live UPS seam.

### 3.2 Zone modifier table (in-memory constants)

Destination ZIP prefix → zone modifier integer (0–9, where 0 = origin zone, higher = farther). The modifier adds `zone × method_zone_rate_cents` to the computed weight rate.

Default per-method zone rate cents (module-level constant `_ZONE_RATE`):

| method_code | zone_rate_cents_per_zone |
|---|---|
| `ground` | 50 |
| `express` | 80 |
| `overnight` | 100 |
| `economy` | 30 |
| `flat_rate` | 0 |

Zone is determined by the first digit of `destination_zip` (US ZIP: digit 0 = zone 1 → East Coast, digit 9 = zone 8 → West Coast). If `origin_zip` is provided, the zone is `abs(int(destination_zip[0]) - int(origin_zip[0]))` (0–9), capped at 9. Without `origin_zip`, zone = `int(destination_zip[0])`.

This is a deliberate simplification. The live UPS seam replaces the zone table entirely when configured; the zone table is used only by the built-in estimator.

### 3.3 Dimensional weight computation

For each line item, dimensional weight is computed only when `length_in`, `width_in`, and `height_in` are all provided (passed in the `LineItemWeightInput` helper struct). Formula:

```
dim_weight_oz = ceil((length_in * width_in * height_in) / S.shipping_dim_divisor) * 16
actual_weight_oz = per_sku_weight_oz * quantity
billed_weight_oz_per_item = max(actual_weight_oz, dim_weight_oz)
```

When dimensions are absent, `billed_weight_oz_per_item = actual_weight_oz`. Total `total_billed_weight_oz = sum(billed_weight_oz_per_item for all items)`.

### 4.2 Weight aggregation helper

```python
class LineItemWeightInput:
    """Caller-constructed input describing one cart/order line item's weight contribution."""
    sku: str
    quantity: int                        # ge=1
    weight_oz: Optional[int]             # None → engine resolves from catalog
    length_in: Optional[float]           # for dimensional weight; None → skip dim calc
    width_in: Optional[float]
    height_in: Optional[float]
    category_id: Optional[str]           # needed for catalog lookup; None → use weight_oz or default
    item_id: Optional[str]               # needed for catalog lookup
```

```python
def resolve_item_weight_oz(item: LineItemWeightInput) -> int:
    """Resolve per-unit actual weight for a line item.

    Resolution order:
    1. item.weight_oz if explicitly provided (caller overrides catalog).
    2. catalog item's attributes["shipping_weight_oz"] when category_id + item_id are set
       and the row exists in T.catalog.
    3. _default_weight_oz() fallback.

    Returns the per-UNIT weight in oz (always >= 1).
    """
```

- Uses `T.catalog.get_item(Key=_catalog_item_key(item.category_id, item.item_id))` which produces `{"PK": f"CAT#{item.category_id}", "SK": f"ITEM#{item.item_id}"}` (same helper as `app/services/shoppingcart.py:42–43`; plain `category_id`/`item_id` without the `CAT#`/`ITEM#` prefixes will NOT match any row).
- `attributes.get("shipping_weight_oz")` on the catalog row is coerced to `int`. If absent or non-numeric, falls back to `_default_weight_oz()`.
- Returns `max(1, resolved_weight_oz)`.

```python
def compute_total_billed_weight_oz(items: List[LineItemWeightInput]) -> int:
    """Sum billed weight across all line items, applying dimensional weight where available.

    Returns total_billed_weight_oz >= 0 (0 for empty item list; minimum 1 oz when any items present).
    """
```

- For each item:
  - Calls `resolve_item_weight_oz(item)` → `per_unit_oz`.
  - `actual_oz = per_unit_oz * item.quantity`.
  - If all three dimension fields are non-None: `dim_oz = math.ceil((item.length_in * item.width_in * item.height_in) / _dim_divisor()) * 16`.
  - `billed_oz = max(actual_oz, dim_oz)` when dimensions available, else `actual_oz`.
- `total = sum(billed_oz for all items)`.
- Returns `max(total, 1) if items else 0`.

### 4.3 Built-in rate estimator

```python
def _builtin_estimate_cents(
    method: Dict[str, Any],
    total_billed_weight_oz: int,
    zone: int,
) -> int:
    """Compute a rate in cents for a single method row using the in-memory ladder + zone table.

    Args:
        method: A method dict as returned by list_enabled_methods_all_carriers().
        total_billed_weight_oz: Aggregated billed weight in oz.
        zone: Integer 0-9 derived from destination/origin ZIP.
    Returns:
        rate_cents >= 0. base_rate_cents + weight_increment + zone_increment.
    """
```

- Reads `method["base_rate_cents"]` as the floor.
- Applies the `_WEIGHT_LADDER[method_code]` breakpoint: finds the highest breakpoint whose `min_oz <= total_billed_weight_oz`; adds `increment_cents_per_lb × ceil(total_billed_weight_oz / 16)`.
- Adds `_ZONE_RATE.get(method_code, 0) × zone`.
- Returns `max(0, result)`.

```python
def _compute_zone(destination_zip: str, origin_zip: Optional[str]) -> int:
    """Derive a 0-9 zone integer from ZIP prefixes."""
```

- If either ZIP is empty or non-numeric first character, returns zone `4` (middle of US, conservative fallback).
- With `origin_zip`: `zone = min(9, abs(int(destination_zip[0]) - int(origin_zip[0])))`.
- Without `origin_zip`: `zone = int(destination_zip[0])`.

```python
def _estimated_delivery_date(transit_days_max: Optional[int]) -> Optional[str]:
    """Return ISO date string for estimated delivery, or None if transit_days_max is None."""
```

- `(date.today() + timedelta(days=transit_days_max)).isoformat()` when `transit_days_max` is not None.

### 4.4 Live UPS seam

```python
def _ups_available() -> bool:
    """True iff UPS base URL and client ID are both configured."""
    return bool(getattr(S, "ups_base_url", "")) and bool(getattr(S, "ups_client_id", ""))


def _ups_estimate(
    carrier_code: str,
    method_code: str,
    total_billed_weight_oz: int,
    destination_zip: str,
    origin_zip: Optional[str],
    currency: str,
) -> Optional[ShippingRateOption]:
    """Call UPS Rating API and coerce result into a ShippingRateOption.

    Returns None on any UPS error (caller falls back to built-in estimator).
    Does NOT raise — errors are absorbed silently (best-effort live rate).
    """
```

- Only called for `carrier_code == "ups"`.
- Builds UPS Rating API request payload (RateRequest/Shipment/Package shape).
- Calls `from app.services.ups import quote; result = quote(ups_payload)`.
- Parses `result["RateResponse"]["RatedShipment"][0]["TotalCharges"]["MonetaryValue"]` → `rate_cents`.
- Returns a `ShippingRateOption` with the parsed `rate_cents`, preserving `transit_days_min` / `transit_days_max` from the method row (UPS response may return `BillingWeight` but not transit days for simple rating).
- On any exception (`HTTPException`, `KeyError`, `IndexError`, network error): logs a warning and returns `None` — the caller falls back to the built-in estimator for that method.

**No `dev_mode` branch here**: when `_ups_available()` is False (dev environment with empty `UPS_BASE_URL`), the live seam is never entered. When `_ups_available()` is True in dev (e.g. local `UPS_BASE_URL=http://localhost:...` test endpoint), the same code path runs as in prod. The shape of the returned `ShippingRateOption` is identical in both environments.

### 4.5 Primary public function: `estimate_rates`

```python
def estimate_rates(
    *,
    destination_zip: str,
    origin_zip: Optional[str] = None,
    items: List[LineItemWeightInput],
    carrier_code_filter: Optional[str] = None,
    method_code_filter: Optional[str] = None,
    user_sub: str,
) -> ShippingRateQuote:
    """Compute shipping-rate options for the given destination and cart/order line items.

    Args:
        destination_zip: Destination ZIP (or postal code) string.
        origin_zip: Optional origin ZIP for more accurate zone calculation.
        items: Line items contributing to total billed weight.
        carrier_code_filter: When set, only include methods for this carrier.
        method_code_filter: When set, only include methods with this code.
        user_sub: Authenticated user sub for audit event.

    Returns:
        ShippingRateQuote with one ShippingRateOption per enabled method that
        passes the filter. Options are ordered: by carrier_code ascending, then
        rate_cents ascending within each carrier. An empty options list is valid
        and not an error.

    Raises:
        HTTPException(404) if shipping_enabled=False or shipping_rate_estimation_enabled=False.
    """
```

Algorithm:

1. `_require_enabled()`.
2. Validate `carrier_code_filter` against `SUPPORTED_CARRIER_CODES` if provided (`HTTPException(422, ...)`).
3. Validate `method_code_filter` against `SUPPORTED_METHOD_CODES` if provided.
4. Fetch `all_methods = list_enabled_methods_all_carriers()` (from SHP-004 service).
5. Apply filters: keep only rows where `(carrier_code_filter is None or row["carrier_code"] == carrier_code_filter)` and `(method_code_filter is None or row["method_code"] == method_code_filter)`.
6. `total_billed_weight_oz = compute_total_billed_weight_oz(items)`.
7. `zone = _compute_zone(destination_zip, origin_zip)`.
8. For each filtered method row, compute `ShippingRateOption`:
   - If `_ups_available()` and `row["carrier_code"] == "ups"`:
     - Try `opt = _ups_estimate(...)`. If opt is not None, use it.
     - If `_ups_estimate` returns None, fall back to `_builtin_estimate_cents(row, ...)`.
   - All other carriers always use `_builtin_estimate_cents`.
   - Build `ShippingRateOption(carrier_code=..., method_code=..., rate_cents=..., currency=row["currency"], transit_days_min=..., transit_days_max=..., estimated_delivery=_estimated_delivery_date(row["transit_days_max"]))`.
9. Sort options: `carrier_code` ascending (alphabetical), then `rate_cents` ascending.
10. Derive `request_id`:
    - If `items` is empty: `sha256(f"empty:{destination_zip}".encode())[:16]`.
    - Else: `sha256(f"cart:{total_billed_weight_oz}:{destination_zip}".encode())[:16]`.
11. Build and return `ShippingRateQuote(request_id=..., options=options, currency=getattr(S, "shipping_default_currency", "usd"), generated_at=now_ts())`.
12. Emit `audit_event("shipping_rate.estimated", user_sub, None, destination_zip=destination_zip, total_weight_oz=total_billed_weight_oz, option_count=len(options), outcome="success")`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Empty enabled-method set

When `list_enabled_methods_all_carriers()` returns an empty list (e.g. all carriers disabled, or flag just turned on before seeding), `estimate_rates` returns a `ShippingRateQuote` with `options=[]`. This is a valid, non-error response per the acceptance criteria. The caller (SHP-007 router) surfaces this directly to the client as an empty array — no 4xx raised.

### 5.2 Empty item list

`compute_total_billed_weight_oz([])` returns `0`. `estimate_rates` with an empty item list proceeds normally: all methods are included (no filter by weight), each option is priced at `base_rate_cents + 0 (weight) + zone_increment` — i.e. the minimum delivery cost for the zone. This is useful for a storefront pre-checkout preview that shows "starting from" rates.

### 5.3 Dimensional vs actual weight — per-item resolution

Dimensional weight is computed per line item independently, not on the total package. This means a cart with 2 items — a heavy flat box and a light but bulky item — each contributes its own `max(actual, dim)` independently. Total billed weight is the sum of per-item billed weights. This is the correct OFBiz model and avoids under-billing large-volume mixed carts.

For the `flat_rate` method code, `_builtin_estimate_cents` always returns `base_rate_cents` regardless of weight (the `_WEIGHT_LADDER["flat_rate"]` ladder has zero increment), so the `manual` carrier's flat-rate method is weight-invariant.

### 5.4 Unknown or absent catalog item

When `resolve_item_weight_oz` is called with a `category_id` + `item_id` that does not exist in `T.catalog` (e.g. the item was deleted after the cart was built), the function falls back silently to `_default_weight_oz()`. This matches the "never block estimation" principle: a missing catalog item should degrade gracefully to a conservative default weight rather than aborting the quote.

### 5.5 UPS seam fallback on error

`_ups_estimate` catches all exceptions and returns `None`. If UPS returns an unexpected payload shape (`KeyError` on `RatedShipment`), a non-200 response (`HTTPException(502)` from `_ups_post`), or a network timeout, the method falls back to the built-in estimator for that carrier/method combination. This means UPS carrier methods always appear in the result even when the live API is down, at the cost of potentially inaccurate rates.

The fallback is intentional and documented: operators who require exact live rates should implement proper circuit-breaker logic in a follow-up ticket. For MVP, conservative over-estimation is preferable to missing shipping options.

### 5.6 Deterministic ordering

Options in `ShippingRateQuote.options` are sorted by `(carrier_code, rate_cents)`. This ordering is stable across invocations with the same inputs regardless of the order `list_enabled_methods_all_carriers()` returns rows (which can vary by DDB scan ordering). A client should not rely on order, but determinism aids testing.

### 5.7 Currency normalisation

All `ShippingRateOption.currency` values come directly from the method row's `currency` attribute (seeded as `"usd"` by SHP-004's defaults). The `ShippingRateQuote.currency` top-level field is set to `S.shipping_default_currency` (default `"usd"`). Multi-currency support (mixed-currency options in a single quote) is out of scope — a future ticket can add currency normalisation if needed.

### 5.8 Filter validation timing

`carrier_code_filter` and `method_code_filter` are validated before calling `list_enabled_methods_all_carriers()` — this ensures the 422 is returned cheaply without a DDB round-trip. An unknown filter value does not degrade silently; it is an explicit error.

### 5.9 Zone computation for non-US ZIPs

The zone table uses the first digit of the destination ZIP as a US ZIP-based approximation. Non-US postal codes (e.g. `"SW1A 1AA"`) will have a non-numeric first character and fall back to `zone = 4`. This is acceptable for MVP scope (US-only shipping). International rates must go through the live UPS seam when implemented.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No `dev_mode` branch in result shape

`app/services/shipping_rates.py` contains zero `if S.dev_mode` conditionals. The built-in estimator runs in both dev and prod. The UPS seam runs when `ups_base_url` and `ups_client_id` are non-empty — in dev these are empty by default, so the seam is never entered unless explicitly configured. The `ShippingRateOption` shape returned is identical whether the built-in estimator or the UPS seam produced it.

This is the exact parity guarantee required by SECOPS-007: "same code path/shape both ways."

### 7.2 Idempotency

`estimate_rates` is fully idempotent — it performs no writes. Given the same `(destination_zip, items, carrier/method filters)` the response is bit-for-bit identical (deterministic `request_id`, deterministic ordering, deterministic built-in estimator). The `generated_at` field is the only timestamp and varies between calls; clients that need caching can key on `request_id`.

The `estimate_rates_for_cart` variant reads from `T.shopping_cart` (read-only) and `T.catalog` (read-only). Cart state mutations by concurrent calls do not affect a mid-flight estimate invocation; the next call will reflect the updated cart.

### 7.3 No money-out paths

SHP-006 is read-only computation. No calls to `new_ledger_entry` (`app/services/billing_shared.py:224` ✓), `refund_payment`, or any billing/wallet mutation. No new ledger entries are introduced.

### 7.4 Destination ZIP handling

`destination_zip` is a string accepted up to 20 characters (per `ShippingRateRequest.destination_zip` in SHP-003). The service does not validate ZIP format (5-digit, ZIP+4, Canadian, etc.) — the zone computation degrades gracefully to zone `4` for non-US formats (§5.9). Format validation is at the router/Pydantic layer (SHP-007).

### 7.5 Catalog read isolation

`resolve_item_weight_oz` reads `T.catalog` using `_catalog_item_key(category_id, item_id)` from `app/services/shoppingcart.py:42–43`, which produces `{"PK": f"CAT#{category_id}", "SK": f"ITEM#{item_id}"}`. Callers must pass the raw `category_id`/`item_id` values (without prefixes); the helper adds the prefixes. It never writes to the catalog table. A missing or malformed catalog row is handled silently (fallback weight). This prevents a corrupted catalog entry from blocking checkout estimation.

### 7.6 Audit events

`audit_event("shipping_rate.estimated", ...)` is emitted after every successful `estimate_rates` call (non-error path). It carries `destination_zip`, `total_weight_oz`, and `option_count`. No PII beyond `user_sub` (which is standard across all audit events). ZIP codes are considered location data — the audit event is consistent with the existing pattern on `purchase_history` and `commerce_order_service`.

## 10. Open Questions / Assumptions

1. **Assumption**: SHP-002, SHP-003, and SHP-004 are all merged before SHP-006 begins. Specifically: `T.shipping_carriers` handle exists, `ShippingRateQuote` / `ShippingRateOption` are importable from `app.models`, and `list_enabled_methods_all_carriers()` is importable from `app.services.shipping_carriers`.

2. **Assumption**: The `attributes["shipping_weight_oz"]` key is the agreed per-SKU weight field name in the catalog. This is not currently defined by any existing model or convention — this ticket introduces it as a forward-compatible addition to the catch-all `attributes` dict. If a future catalog schema migration adds a top-level `shipping_weight_oz` field to `CatalogItemCreateIn`, `resolve_item_weight_oz` should be updated to read it directly.

3. **Assumption**: The built-in weight ladder and zone rate constants in `_WEIGHT_LADDER` and `_ZONE_RATE` are acceptable placeholder defaults. Operators can tune rates via admin method CRUD (SHP-005 `update_method` on `base_rate_cents` and `transit_days_*`). Configuring weight-ladder and zone-rate overrides via env or DDB is out of SHP-006 scope.

4. **Assumption**: The UPS Rating API path to call is `"quote"` (i.e. `_ups_post("quote", payload)` → `ups.py:66` `quote(shipment)`). The `app/services/ups.py:66` `quote` function is already present and is the correct entry point for a rating request. The payload shape for UPS Rating API v2 (`RateRequest.Shipment.Package.PackageWeight.Weight`) is the caller's responsibility to construct correctly in `_ups_estimate`.

5. **Assumption**: Zone computation on the first digit of the destination ZIP (US-centric) is sufficient for the initial MVP scope. International shipping rates should use the live UPS seam (when configured) rather than the zone table.

6. **Open question**: Should `estimate_rates_for_cart` enforce that the cart belongs to `user_sub`? `app/services/shoppingcart.py:237` `get_cart(user_sub, cart_id)` already enforces ownership via the PK `USER#{user_sub}`. Passing a `cart_id` from another user will return `404` from `get_cart` naturally. No additional ownership check is needed.

7. **Open question**: Should `estimate_rates_for_cart` fail fast (raise 404) if the cart is in `PURCHASED` status, or return a valid quote? The current design returns a valid quote — the cart items still exist and the estimate is semantically valid for a post-purchase display. SHP-007 can choose to add a guard based on product decision.

8. **Assumption**: The `manual/flat_rate` method should always appear in `estimate_rates` results (at `base_rate_cents`, unaffected by weight). This is the expected behavior for "pick-up in store" or "manual fulfillment" scenarios and requires no special casing beyond the `_WEIGHT_LADDER["flat_rate"]` returning zero increment.

9. **Open question**: Should the `request_id` derivation include filter parameters (`carrier_code_filter`, `method_code_filter`)? Current design excludes them, so two calls with different filters on the same cart/weight/ZIP return different `options` lists but the same `request_id`. This could confuse a caching layer. A safer design includes filters in the hash: `sha256(f"cart:{total_weight_oz}:{destination_zip}:{carrier_code_filter or ''}:{method_code_filter or ''}".encode())[:16]`. This will be decided in SHP-007 implementation.
