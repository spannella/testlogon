# OFB-013 — Chart of accounts & GL account model

## 1. Summary & Goal

OFB-013 establishes the foundational **chart of accounts** (CoA) for the platform's general ledger. It delivers a seedable, CRUD-managed set of GL account definitions (account code, name, class, normal-balance side), stored in a new DynamoDB table (`gl_accounts`), and exposed through a ROOT-only management API. The chart seeds idempotently at startup with the seven accounts that directly map to existing money flows in the billing ledger. Account disabling is blocked when any journal entries reference the account (the OFB-014 enforcement hook). No billing behavior changes. Nothing activates unless the `GL_DOUBLE_ENTRY_ENABLED` flag, added by OFB-002, is `true`.

**Downstream dependency**: OFB-014 (GL posting service) reads this chart to map each billing ledger row to a debit/credit pair. Seeding the correct default accounts here is a pre-condition for that mapping logic.

## 3. Data Model

### New table: `gl_accounts`

Single-table design. One item per GL account.

**Primary key**

| Attribute      | Type | Value                                 |
|----------------|------|---------------------------------------|
| `account_code` | S    | Short mnemonic, e.g. `"1000"`, `"4000"` |
| `sk`           | S    | Always `"META"` (sole row per account) |

Using `account_code` as the partition key makes point reads by code O(1) without a GSI. The `sk="META"` convention (used across every other single-table entity: `app/services/returns_rma.py:236` ✓, `app/services/kyc_cases.py:139` ✓) leaves room for future sub-rows (audit history) without schema change.

**Item attributes**

| Attribute       | Type | Required | Notes                                                   |
|-----------------|------|----------|---------------------------------------------------------|
| `account_code`  | S    | Y        | PK; immutable after creation; 1–16 chars                |
| `sk`            | S    | Y        | Always `"META"`                                         |
| `name`          | S    | Y        | Human label, e.g. `"Cash / Bank"`                       |
| `account_class` | S    | Y        | `asset`, `liability`, `equity`, `revenue`, `expense`    |
| `normal_balance`| S    | Y        | `debit` or `credit`; derived from class by convention   |
| `description`   | S    | N        | Optional longer description; max 500 chars              |
| `is_active`     | BOOL | Y        | `true` = postable; `false` = disabled (soft delete)     |
| `is_system`     | BOOL | Y        | `true` = seeded default; ROOT cannot delete system accts|
| `created_at`    | N    | Y        | Unix timestamp integer (`now_ts()`)                     |
| `updated_at`    | N    | Y        | Unix timestamp integer (`now_ts()`)                     |
| `created_by`    | S    | Y        | `"system"` for seeded rows; ROOT `user_sub` for manual  |

**GSI: `GSI_CLASS`**

Enables listing all accounts of a given class (e.g. all `revenue` accounts for the OFB-014 mapping table).

| Index name  | Partition key    | Sort key         | Projects |
|-------------|-----------------|------------------|----------|
| `GSI_CLASS` | `account_class` (S) | `account_code` (S) | ALL    |

`account_code` as GSI sort key gives stable alphabetical ordering within a class. No `attr_types` override needed (both are String).

**GSI: `GSI_ACTIVE`** *(dropped — use scan + FilterExpression)*

The CoA is bounded (~100 accounts). `list_accounts(active_only=True)` uses a full table scan with `FilterExpression=Attr("gsi_active").eq("true")` rather than a GSI. This is simpler and correct for bounded sets (per ESCALATIONS.md §B OFB-013 open decision resolution). The `GSI_ACTIVE` index and its `gsi_active` denorm column are **removed from the design**.

`gsi_active` attribute is retained on items (written as `"true"`/`"false"` mirror of `is_active`) to keep FilterExpression queries correct, but no GSI is declared for it.

    "expense":      "debit",

    "equity":       "credit",

def seed_chart_of_accounts() -> None:
    """Idempotently write default accounts.

    Uses conditional put (attribute_not_exists(account_code)) so re-running
    after a restart never overwrites operator-modified names/descriptions.
    Called from the FastAPI startup hook when GL_DOUBLE_ENTRY_ENABLED=true.
    """

def get_account(account_code: str) -> Optional[Dict[str, Any]]:
    """Fetch a single account by code. Returns None if not found."""

def list_accounts(
    account_class: Optional[str] = None,
    active_only: bool = True,

    """List accounts, optionally filtered by class and/or active status.

    Uses GSI_CLASS when account_class is provided (key query).
    When active_only=True with no class filter, performs a full scan with
    FilterExpression=Attr("gsi_active").eq("true") — acceptable for bounded
    CoA size (~100 accounts; no GSI_ACTIVE index per reconciliation decision).
    """

def create_account(
    account_code: str,
    name: str,
    account_class: str,
    description: Optional[str],
    actor_sub: str,

    """Create a new GL account. Raises 409 if account_code exists.

    normal_balance is derived from account_class via NORMAL_BALANCE_FOR_CLASS.
    Raises 400 if account_class is not in ACCOUNT_CLASSES.

def update_account(
    account_code: str,
    name: Optional[str],
    description: Optional[str],
    actor_sub: str,
) -> Dict[str, Any]:
    """Update mutable fields (name, description) on an existing account.

    account_class and normal_balance are immutable after creation.
    Raises 404 if not found; 403 if is_system=True and caller tries
    to modify account_class (immutability guard).

def disable_account(account_code: str, actor_sub: str) -> Dict[str, Any]:
    """Soft-disable a GL account (set is_active=False, gsi_active="false").

    Raises 404 if not found.
    Raises 409 if the account has posted journal entries (deferred to

    returns False until T.gl_journal exists and is populated).
    System accounts (is_system=True) cannot be disabled; raises 403.

def enable_account(account_code: str, actor_sub: str) -> Dict[str, Any]:
    """Re-enable a previously disabled account."""

## 5. Detailed Behavior & Edge Cases

### Seed idempotency

`seed_chart_of_accounts` writes each `DEFAULT_ACCOUNTS` entry via a conditional `put_item` with `ConditionExpression="attribute_not_exists(account_code)"`. A `ConditionalCheckFailedException` means the row already exists and is silently swallowed. This guarantees re-running after every `just restart` is safe. Seeded accounts have `is_system=True`, `created_by="system"`.

### `normal_balance` derivation

The accounting identity — assets and expenses have debit normal balances; liabilities, equity, and revenue have credit normal balances — is encoded in `NORMAL_BALANCE_FOR_CLASS`. The service derives it from `account_class` at write time and stores it on the item. It is never accepted from the caller (not in `GlAccountIn`). This prevents inconsistent data: a `revenue` account can never be accidentally marked debit-normal.

### Disabling an account with posted entries

`disable_account` calls `_has_posted_entries(account_code: str) -> bool`. In OFB-013, this function reads from `T.gl_journal` (which will be introduced by OFB-014). Until OFB-014 ships, `T.gl_journal` is an empty table and the function always returns `False`, so disabling succeeds. Once OFB-014 posts journal entries, the check becomes active: any account with a matching `debit_account_code` or `credit_account_code` in `gl_journal` returns `True` and disable raises `HTTPException(409, "Cannot disable account with posted entries")`.

### System account protection

System accounts (`is_system=True`) represent the seven default accounts that OFB-014 mapping logic depends on. `disable_account` raises `HTTPException(403, "Cannot disable a system account")` for these. `update_account` allows name/description changes on system accounts (useful for localization) but blocks any structural changes.

### `account_code` immutability

`account_code` is the PK. Changing it requires creating a new account and disabling the old one — there is no rename endpoint. The `update_account` function only accepts `name` and `description`; attempting to change `account_code` or `account_class` via `PATCH` simply has no effect (those fields are absent from `GlAccountUpdateIn`).

### `account_code` format validation

The Pydantic model enforces `pattern=r"^[A-Za-z0-9_-]+$"`, max 16 chars. The service further validates that the provided `account_class` is in `ACCOUNT_CLASSES`; an invalid class returns `HTTPException(400, "Invalid account_class")`.

### Duplicate account creation

`create_account` writes with `ConditionExpression="attribute_not_exists(account_code)"`. A `ConditionalCheckFailedException` bubbles up as `HTTPException(409, "Account code already exists")`.

### Pagination

`list_accounts` with `active_only=True` and no class filter queries `GSI_ACTIVE` with `gsi_active="true"`. For large charts (>100 accounts), the function loops on `LastEvaluatedKey` (per CLAUDE.md DDB FilterExpression gotcha — though this is a key condition, not a filter, it is still good practice). Returns all results in memory; the CoA is bounded (O(100) accounts in practice).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

All DynamoDB reads and writes use the same `T.gl_accounts` handle regardless of `S.dev_mode`. There are no `if S.dev_mode` branches in `gl_accounts.py`. The seed runs identically against DynamoDB Local (dev) and real DynamoDB (prod). This follows the established pattern in `inventory.py` (`app/services/inventory.py:27–29` — "SECOPS-007 parity: identical code in dev … and prod") ✓.

### Idempotency

- **Seed**: conditional put on `attribute_not_exists(account_code)` — fully idempotent across restarts.
- **Create**: conditional put raises 409 on duplicate; callers can safely retry after a 409 with a different code.
- **Update**: `update_item` with `SET` expressions is idempotent given the same payload.
- **Disable/Enable**: uses a conditional `update_item` with `ConditionExpression="attribute_exists(account_code)"` to avoid creating rows; repeated calls on an already-disabled account are no-ops (idempotent at the state level; the timestamp updates, which is acceptable).

### Security

- All write endpoints use `require_root_session` — only ROOT users can mutate the CoA.
- `GET` list and detail also use `require_root_session`; the CoA is internal accounting data not exposed to regular users.
- `account_code` pattern validation prevents injection via PK.
- `is_system` is never accepted from the API caller; it is set by the seeder only.
- Audit events are emitted for every create/update/disable/enable with `actor_sub=user.sub`, providing a full mutation history in the alerts table.
- No PII is stored in the CoA; it contains only accounting classification data.

## 8. Backward Compatibility & Migration

### Zero-impact with flag off

With `GL_DOUBLE_ENTRY_ENABLED=false` (the prod default on initial rollout), this ticket is fully additive:

- New DynamoDB table `gl_accounts` is created empty at `just restart` but never queried.
- New settings keys default to their off/empty values.
- No existing router, service, or model is modified.
- The `T` object gains one new attribute (`gl_accounts`) but none of the 570 existing attributes are changed.

### Migration for prod enablement

When enabling `GL_DOUBLE_ENTRY_ENABLED=true` in production for the first time:

1. Deploy the code (new table already exists from OFB-002 scaffold or from this ticket's init script addition).
2. Set `GL_DOUBLE_ENTRY_ENABLED=true` in the environment and restart the backend.
3. The startup seed hook runs and conditionally writes the seven default accounts. If the table already has rows from a prior attempt, the conditional puts are silent no-ops.
4. No data migration needed for the billing ledger — existing `LEDGER#` rows are untouched; OFB-014 will backfill journal entries separately when its own flag is enabled.

### No DDB `UpdateTable` required

The `gl_accounts` table is **new** — it does not exist before this ticket. The `local-ddb-init.py` `TableDef` creates it from scratch including its GSIs. In production, the table must be created via an `UpdateTable` / `CreateTable` call before the code is deployed. The table creation is a one-time operation with no backfill dependency.

## 10. Open Questions / Assumptions

1. **Assumption**: OFB-002 was scoped to land table/settings/handles for `gl_accounts` and `gl_journal`, but as of the current codebase these are absent. OFB-013 absorbs the scaffolding responsibility for `gl_accounts` (but not `gl_journal` — that belongs to OFB-014). Verify with the OFB-002 owner whether `gl_journal` scaffolding was merged under a different commit.

2. **Assumption**: `GL_DOUBLE_ENTRY_ENABLED` is a single master switch covering both OFB-013 (CoA) and OFB-014 (posting). A separate `GL_COA_ENABLED` flag could allow the CoA to be seeded and managed before the posting engine is turned on, but this adds complexity. The spec uses the single flag per the OFB-002 design intent. Validate with engineering.

3. **Assumption**: Account codes are free-form strings (e.g. `"1000"`, `"4000"`, `"SALES_REV"`), not strictly numeric 4-digit codes. The constraint `pattern=r"^[A-Za-z0-9_-]+$"` is intentionally permissive to allow future multi-segment codes (e.g. `"4000-US"`). Confirm with accounting stakeholders.

4. **Open question**: Should `list_accounts` be accessible to `ADMIN` role (read-only, for financial reporting in OFB-016) or remain ROOT-only? This spec defaults to ROOT-only because the CoA is currently only useful to the GL posting service and platform finance tooling. If OFB-016 financial statements need ADMIN visibility, the `GET` endpoints should use `require_admin_session` instead.

5. **Open question**: The `gsi_active` string-mirror of `is_active` is a workaround for DynamoDB's inability to index Boolean attributes. An alternative is a scan with `FilterExpression` (acceptable for a bounded CoA of ~100 accounts). If the boolean-mirror approach feels hacky, replace `GSI_ACTIVE` with a simple scan in `list_accounts` and remove the GSI. The bounded size makes either approach O(1) in practice.

6. **Assumption**: `_has_posted_entries` is a service-internal function (not exported). It is a stub returning `False` in OFB-013 and will be filled in by OFB-014 when `T.gl_journal` has data. This forward-coupling is explicit; document it in a `# TODO: OFB-014` comment in the service.

7. **Assumption**: No frontend UI is needed for chart-of-accounts management in this ticket. The account codes are purely internal ERP metadata consumed by OFB-014's mapping layer. If a management UI is needed later, it belongs to a separate OFB-013-UI ticket.
