# MKT-004 — Marketing campaign service (CRUD + deterministic ids)

## 1. Summary & Goal

MKT-004 creates `app/services/marketing_campaigns.py` — the core service module for the marketing-campaigns subsystem. It delivers:

- **CRUD operations**: `create_campaign`, `get_campaign`, `list_campaigns`, `update_campaign` against the `MarketingCampaigns` DynamoDB table wired by MKT-002.
- **Deterministic ids**: `campaign_id = sha256(owner_id + "|" + name + "|" + created_bucket)[:24]`, where `created_bucket = now_ts() // 3600 * 3600` (hourly bucket). A retried create with the same owner, name, and timestamp bucket returns the existing item without writing a duplicate row.
- **Linked-entity validation**: at create/update time, an optional `ad_campaign_id` is validated against `ad_campaigns.get_campaign`, and each `promo_code_ids` entry is validated against `promo_codes.get_promo_code`. These are read-only checks; the marketing campaign references but never owns the linked entities.
- **Feature-flag gate**: every mutating entry point raises HTTP 403 when `S.marketing_campaigns_enabled` is `False`. Read paths (`get_campaign`, `list_campaigns`) work regardless of flag state.

This ticket does not implement the full status state machine (MKT-006), link attach/detach operations (MKT-005), or any HTTP router (MKT-011). It establishes the stable service API that all downstream tickets import.

## 2. Context & Current State

### Existing parallel: `app/services/ad_campaigns.py`

The ads campaign service at `app/services/ad_campaigns.py:35–63` is the direct structural model. Key differences:

- **ID scheme**: ads campaigns use `uuid4().hex[:12]` prefixed as `f"camp_{...}"` (`app/services/ad_campaigns.py:37`). Marketing campaigns replace this with a deterministic `sha256(...)[:24]` (no prefix) so duplicate creates are idempotent rather than producing a new row.
- **PK/SK namespace**: ads campaigns use `ACCT#{account_id}` / `CAMPAIGN#{campaign_id}` (`app/services/ad_campaigns.py:41–42`). Marketing campaigns use `OWNER#{owner_id}` / `MKTCAMP#{campaign_id}` per MKT-001/MKT-002.
- **Table handle**: ads campaigns write to `T.ad_campaigns` (`app/services/ad_campaigns.py:62`). Marketing campaigns write to `T.marketing_campaigns` (added by MKT-002).
- **Status**: ads campaigns start at `"draft"` and route through `pending_review` → `active` → ... (`app/services/ad_campaigns.py:52`, state machine at `:16–24`). Marketing campaigns also start at `"draft"` but follow a different SM (`draft → scheduled → active → paused → completed → archived`) defined in MKT-006; MKT-004 does not enforce transitions, only sets initial status.
- **Linked entities**: ads campaigns have no cross-service references. Marketing campaigns optionally reference an ads `campaign_id` (via `T.ad_campaigns`) and one or more promo code ids (via `T.promo_codes`).

## 3. Data Model

### Table: `MarketingCampaigns`

Created by MKT-002 in `scripts/local-ddb-init.py`. Reproduced here for completeness.

| Key | Type | Value pattern |
|-----|------|---------------|
| `pk` | S (HASH) | `OWNER#{owner_id}` |
| `sk` | S (RANGE) | `MKTCAMP#{campaign_id}` |

GSIs (per MKT-002 spec `docs/ofbiz/specs/MKT-002.md:121–123`):

| Index name | Partition key (S) | Sort key | Notes |
|------------|-------------------|----------|-------|
| `ByOwnerCreatedAt` | `owner_id` (S) | `created_at` (N) | Owner campaign listing, most-recent first |
| `ByStatusCreatedAt` | `status` (S) | `created_at` (N) | Admin queue / status filter |

`attr_types={"created_at": "N"}` — required so DynamoDB stores `created_at` as a Number, enabling integer range queries on the GSI sort key. Omitting this causes `ValidationException` at query time (CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha).

### Campaign item shape

A fully-populated item written by `create_campaign`:

```
pk                : "OWNER#{owner_id}"
sk                : "MKTCAMP#{campaign_id}"
campaign_id       : str  — sha256(owner_id|name|created_bucket)[:24]
owner_id          : str  — the user_sub of the creator
name              : str
objective         : str  — "awareness"|"traffic"|"conversions"|"retention"
status            : str  — always "draft" at creation
budget_cents      : int  ≥ 0
ad_campaign_id    : str | absent   — validated reference to T.ad_campaigns
promo_code_ids    : list[str]       — validated references to T.promo_codes
contact_list_ids  : list[str]       — not validated at create (MKT-007 owns validation)
segment_ids       : list[str]       — not validated at create (MKT-008 owns validation)
tracking_code     : str | absent    — free-form slug reference (MKT-010 owns validation)
start_date        : int | absent    — Unix timestamp
end_date          : int | absent    — Unix timestamp
created_at        : int             — now_ts() at creation; projected onto GSI sort keys
updated_at        : int             — now_ts(); updated on every write
```

`contact_list_ids`, `segment_ids`, and `tracking_code` are stored without cross-service validation in MKT-004. Their referential integrity is enforced by MKT-007/MKT-008/MKT-010 respectively, following the same "reference owns, linked entity is unaware" principle described in the ticket description.

### Deterministic ID calculation

```python
import hashlib
from app.core.time import now_ts

def _make_campaign_id(owner_id: str, name: str, ts: int) -> str:
    created_bucket = (ts // 3600) * 3600          # round down to hour boundary
    raw = f"{owner_id}\x00{name}\x00{created_bucket}".encode("utf-8")
    return hashlib.sha256(raw).hexdigest()[:24]
```

The `\x00` null-byte separator (as in `app/services/kyc_partner_api.py:121`) prevents prefix collisions where `owner="ab"` + `name="c"` would hash identically to `owner="a"` + `name="bc"` if concatenated directly. The hourly bucket means a genuine retry within the same clock-hour produces the same id; a create attempt in the next hour gets a different id (produces a new campaign), which is the correct semantics — retries within a reasonable window are idempotent, but re-creating the same-named campaign hours later is a new campaign.

```python
def _validate_ad_campaign_ref(ad_campaign_id: str) -> None:
    """Validate that the referenced ads campaign exists (by campaign_id GSI)."""
    from boto3.dynamodb.conditions import Key as _Key
    resp = T.ad_campaigns.query(
        IndexName="ByCampaignId",
        KeyConditionExpression=_Key("campaign_id").eq(ad_campaign_id),
        Limit=1,
```

Uses `IndexName="ByCampaignId"` — the same GSI already queried by `app/routers/ads.py:72–78` for ownership checks. Limit=1 makes the query efficient.

```python
def _validate_promo_code_refs(promo_code_ids: list[str]) -> None:

    from app.services.promo_codes import get_promo_code
```

#### Primary function: `create_campaign`

```python
def create_campaign(owner_id: str, data: MarketingCampaignCreateIn) -> dict:
    """
    Create a marketing campaign. Idempotent: a duplicate call with the same
    owner_id, name, and timestamp bucket (hourly) returns the existing item.

    Raises:
        HTTPException(403)  — module flag off
        HTTPException(422)  — invalid ad_campaign_id or promo_code_ids
    """
    _require_flag_enabled()

    if data.ad_campaign_id:
        _validate_ad_campaign_ref(data.ad_campaign_id)
    if data.promo_code_ids:
        _validate_promo_code_refs(data.promo_code_ids)

    ts = now_ts()
    campaign_id = _make_campaign_id(owner_id, data.name, ts)
    created_bucket = (ts // 3600) * 3600

    item: dict = {
        "pk": f"OWNER#{owner_id}",
        "sk": f"MKTCAMP#{campaign_id}",
        "campaign_id": campaign_id,
        "owner_id": owner_id,
        "name": data.name,
        "objective": data.objective,
        "status": "draft",
        "budget_cents": data.budget_cents,
        "promo_code_ids": list(data.promo_code_ids),
        "contact_list_ids": list(data.contact_list_ids),
        "segment_ids": list(data.segment_ids),
        "created_at": ts,
        "updated_at": ts,
    }
    if data.ad_campaign_id is not None:
        item["ad_campaign_id"] = data.ad_campaign_id
    if data.tracking_code is not None:
        item["tracking_code"] = data.tracking_code
    if data.start_date is not None:
        item["start_date"] = data.start_date
    if data.end_date is not None:
        item["end_date"] = data.end_date

    try:
        T.marketing_campaigns.put_item(
            Item=item,
            ConditionExpression="attribute_not_exists(pk) AND attribute_not_exists(sk)",
        )
    except ClientError as exc:
        if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
            # Idempotent re-create: return the existing row unchanged
            existing = get_campaign(owner_id, campaign_id)
            return existing if existing is not None else item
        raise

    try:
        from app.services.alerts import audit_event
        audit_event(
            "marketing.campaign.created",
            owner_id,
            campaign_id=campaign_id,
            name=data.name,
            objective=data.objective,
        )
    except Exception:
        pass

    return item
```

Key design decisions:
- `ConditionExpression="attribute_not_exists(pk) AND attribute_not_exists(sk)"` — the condition on both keys is used consistently with `app/services/provider_oauth.py:143` and `app/services/file_mounts.py:159`. Using both attributes avoids a corner case where `pk` exists but `sk` differs.
- On `ConditionalCheckFailedException` the existing item is read back and returned directly. This ensures the caller receives a complete, accurate item (including any fields written by the original create) rather than the locally-constructed `item` dict.
- `audit_event` is imported locally and wrapped in `try/except` (best-effort, mirrors the pattern in `app/services/ad_campaigns.py:154–172`).

```python
def list_campaigns(
    owner_id: str,
    limit: int = 100,
    cursor: Optional[str] = None,
) -> dict:
    """
    List marketing campaigns for an owner, newest first, paginated.

    Returns {"items": [...], "cursor": str|None}.
    """
    kwargs: dict = {
        "IndexName": "ByOwnerCreatedAt",
        "KeyConditionExpression": Key("owner_id").eq(owner_id),
        "ScanIndexForward": False,
        "Limit": min(limit, 200),
    }
    if cursor:
        from app.core.cursor import decode_cursor
        kwargs["ExclusiveStartKey"] = decode_cursor(cursor)

    resp = T.marketing_campaigns.query(**kwargs)
    items = resp.get("Items", [])
    last_key = resp.get("LastEvaluatedKey")

    next_cursor = None
    if last_key:
        from app.core.cursor import encode_cursor
        next_cursor = encode_cursor(last_key)

    return {"items": items, "cursor": next_cursor}
```

Uses the `ByOwnerCreatedAt` GSI with `ScanIndexForward=False` (newest first). Pagination follows `app/core/cursor.py` encode/decode helpers, consistent with how other list endpoints in the project paginate (e.g., `app/services/purchase_history.py`). No flag check.

#### Primary function: `update_campaign`

```python
def update_campaign(
    owner_id: str,
    campaign_id: str,
    data: MarketingCampaignUpdateIn,
) -> dict:
    """
    Update mutable campaign fields.

    Does NOT validate status transitions — that is MKT-006's responsibility.
    Validates ad_campaign_id and promo_code_ids references if supplied.

    Raises:
        HTTPException(403)  — module flag off
        HTTPException(404)  — campaign not found
        HTTPException(422)  — invalid ad_campaign_id or promo_code_ids
    """
    _require_flag_enabled()

    existing = get_campaign(owner_id, campaign_id)
    if existing is None:
        from fastapi import HTTPException
        raise HTTPException(status_code=404, detail="Campaign not found")

    updates = {k: v for k, v in data.model_dump(exclude_none=True).items()}
    if not updates:
        return existing  # nothing to do, return current state

    if "ad_campaign_id" in updates and updates["ad_campaign_id"] is not None:
        _validate_ad_campaign_ref(updates["ad_campaign_id"])
    if "promo_code_ids" in updates:
        _validate_promo_code_refs(updates["promo_code_ids"])

    updates["updated_at"] = now_ts()

    expr_parts: list[str] = []
    attr_values: dict = {}
    attr_names: dict = {}
    for i, (k, v) in enumerate(updates.items()):
        alias = f"#f{i}"
        val_alias = f":v{i}"
        attr_names[alias] = k
        attr_values[val_alias] = v
        expr_parts.append(f"{alias} = {val_alias}")

    T.marketing_campaigns.update_item(
        Key={"pk": f"OWNER#{owner_id}", "sk": f"MKTCAMP#{campaign_id}"},
        UpdateExpression="SET " + ", ".join(expr_parts),
        ExpressionAttributeNames=attr_names,
        ExpressionAttributeValues=attr_values,
    )

    try:
        from app.services.alerts import audit_event
        audit_event(
            "marketing.campaign.updated",
            owner_id,
            campaign_id=campaign_id,
            updated_fields=list(updates.keys()),
        )
    except Exception:
        pass

    return get_campaign(owner_id, campaign_id) or existing
```

The `update_item` expression builder mirrors `app/services/ad_campaigns.py:120–135` exactly. `updated_at` is always added to the updates dict so the item's modification timestamp is maintained. The status field is accepted in the update payload; the transition is not validated here — that is MKT-006's responsibility (mirrors `CampaignUpdateIn`'s behavior in `app/services/ad_campaigns.py:114–118`, which validates ad-campaign transitions).

## 5. Detailed Behavior & Edge Cases

### Idempotent re-create (the core guarantee)

A caller creates a campaign with `name="Summer 2026"`, `owner_id="u_alice"` at `ts=1750000000`. The hourly bucket is `1750000000 // 3600 * 3600 = 1749998000`. `campaign_id = sha256("u_alice\x00Summer 2026\x001749998000")[:24]`. If the create request is retried within the same hour (e.g., due to a network timeout), the same `campaign_id` is computed, the conditional put fails with `ConditionalCheckFailedException`, and the existing item is read back and returned. The caller observes a `200 OK` with the original creation data — indistinguishable from a first-time create.

If the same create is attempted in the next hour (`ts=1750003600`, bucket=`1750002000`), a different `campaign_id` is generated and a new row is written. This is correct: the hour boundary is the idempotency window.

### Validating the ads campaign reference

`_validate_ad_campaign_ref` queries `T.ad_campaigns` via `IndexName="ByCampaignId"` with `Limit=1`. This GSI is used by `app/routers/ads.py:72` for ownership checks, so it is expected to be populated for all active ads campaigns. If the GSI query returns no items, HTTP 422 is raised with `code="invalid_ad_campaign_id"`. The validation does not check ownership: a marketing campaign can reference an ads campaign owned by a different account (e.g., a shared brand campaign). Ownership semantics for this cross-owner scenario are a MKT-005/MKT-011 follow-up.

### Validating promo code references

`_validate_promo_code_refs` iterates `promo_code_ids` sequentially and calls `get_promo_code(code_id)` for each. The first missing id raises HTTP 422 with `code="invalid_promo_code_id"`. This is O(n) DDB reads where n = len(promo_code_ids). For MVP the list is assumed to be small (≤ 10); a batch-read optimization is a future follow-up.

Validation does not check whether the promo code is active (`item["active"]`). An inactive code may be referenced (for attribution tracking of a code that has since been deactivated). Active-state validation at campaign activation time is MKT-006's responsibility.

### `update_campaign` with an empty payload

If `MarketingCampaignUpdateIn` is submitted with all fields `None` (an empty update), `data.model_dump(exclude_none=True)` returns `{}`, the function skips the DDB `update_item` call, and returns the existing item unchanged. No `updated_at` bump occurs. This avoids unnecessary writes and eliminates spurious audit events.

### `update_campaign` with `promo_code_ids=[]`

An explicit `promo_code_ids=[]` (empty list, not `None`) is included in the updates payload by `exclude_none=True` because it is not `None`. The empty list is written to DDB, replacing any existing list. This is the correct way to detach all promo codes in a single update (MKT-005 will add finer-grained attach/detach; this is the bulk-replace path).

### `ad_campaign_id` set to `None` on update

`MarketingCampaignUpdateIn.ad_campaign_id: Optional[str] = None`. If the caller sends `{"ad_campaign_id": null}`, `exclude_none=True` omits it from the update dict — there is no way to un-set an `ad_campaign_id` via `update_campaign`. Detaching the ads campaign link is MKT-005's `detach_ad_campaign` operation. This is intentional: `update_campaign` is the "bulk field update" path; MKT-005 provides atomic link operations.

### Large `promo_code_ids` list on update

If a caller passes a large list (e.g., 50 promo codes), all 50 are validated sequentially before the DDB write. On the first missing code, HTTP 422 is raised and no writes occur (the validation is all-or-nothing before the mutation). The total DDB read cost is O(n) `get_item` calls at ~1ms each — acceptable for MVP.

### Concurrent creates with the same inputs

Two concurrent creates with identical `(owner_id, name, timestamp_in_same_hour)` compute the same `campaign_id` and both attempt a conditional put. One succeeds; the other gets `ConditionalCheckFailedException`. Both callers receive the same item (the winner's `created_at` is returned to both). This is the correct idempotency behavior.

### Reads when flag is off

`get_campaign` and `list_campaigns` do not call `_require_flag_enabled`. This is per the ticket spec: "reads of pre-existing data are unaffected." A campaign created before the flag was turned off remains readable. This mirrors how `promo_codes.get_promo_code` reads regardless of `S.promo_codes_enabled`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

There is no `if S.dev_mode:` branch in `marketing_campaigns.py`. All code paths (DDB reads/writes, sha256 computation, flag checks, audit events) execute identically in dev (DynamoDB Local at port 8001, moto-backed promo codes and ad campaigns) and in prod (real DynamoDB, real promo-codes table). This is full SECOPS-007 compliance — the same code path, same conditions, same table handles in both environments.

The only environmental difference is the DDB endpoint URL (`DDB_ENDPOINT_URL=http://localhost:8001` in dev), which is transparent to the service layer.

### Idempotency

`create_campaign` is idempotent within a one-hour window for the same `(owner_id, name)` input. The guarantee is:
1. Compute the same `campaign_id` for the same inputs.
2. Attempt a conditional `put_item`.
3. On conflict, read back and return the existing item.

The idempotency window is one hour (the `created_bucket` granularity). This is documented behavior — callers that need cross-hour idempotency must store the returned `campaign_id` and use `get_campaign` for subsequent reads.

`update_campaign` is not idempotent in the general case: two identical PATCH requests both update `updated_at`. The endpoint is safe to retry (writes the same values), but the `updated_at` timestamp will differ between the first and second call.

### Security

- **Owner scoping**: all DDB operations use `PK = OWNER#{owner_id}` where `owner_id` is the authenticated `user_sub`. There is no way to read or write another user's campaigns via these functions.
- **Linked-entity validation does not expose other users' data**: `_validate_ad_campaign_ref` confirms existence only (returns HTTP 422 if not found); it does not return the ads campaign item to the caller.
- **`_require_flag_enabled` raises before any DDB access**: if the flag is off, no read of `T.marketing_campaigns` or linked tables occurs in mutating paths.
- **Audit events**: `marketing.campaign.created` and `marketing.campaign.updated` are written best-effort to `T.alerts` via `alerts.audit_event`. They carry `campaign_id`, `owner_id`, and field names (not values) to avoid logging PII in the audit trail.
- **No billing writes**: this service is read-only with respect to `T.billing`, `T.promo_codes`, and `T.ad_campaigns`. No ledger entries, no promo redemptions, no ad spend adjustments occur here.

## 10. Open Questions / Assumptions

1. **Assumption: `ByCampaignId` GSI on `T.ad_campaigns`**. The validation helper `_validate_ad_campaign_ref` queries `T.ad_campaigns` via `IndexName="ByCampaignId"`. This GSI is used in `app/routers/ads.py:72` and is expected to exist. Verify it is declared in `scripts/local-ddb-init.py` under the `AdCampaigns` table definition. If it is missing, `_validate_ad_campaign_ref` must fall back to a table scan (unacceptable) or the validation approach must change.

2. **Assumption: cross-owner ad-campaign references are allowed**. A marketing campaign created by `owner_id="u_alice"` can reference an ads campaign owned by a different account. The ticket says campaigns "may reference an ads campaign_id (validated against `ad_campaigns.get_campaign`)". The validation checks existence only, not ownership. If this is incorrect and owners should only link their own ads campaigns, `_validate_ad_campaign_ref` needs to also verify `account.owner_sub == owner_id`.

3. **Assumption: one-hour idempotency window is sufficient**. The `created_bucket = (ts // 3600) * 3600` gives a 3600-second window. If network timeouts in production typically resolve within seconds, this is more than sufficient. If the platform needs longer windows (e.g., for async create-on-queue patterns), the bucket could be extended to one day (`// 86400 * 86400`). Confirm with the product team.

4. **Assumption: `contact_list_ids` and `segment_ids` are stored without validation**. MKT-004 does not validate these lists against `T.contact_lists` or `T.party_segments` because those services are MKT-007/MKT-008 and may not exist at the time MKT-004 lands. This means a campaign can be created referencing a non-existent contact list. MKT-007/MKT-008 should add validation at send-resolution time, not at campaign-create time.

5. **Assumption: `update_campaign` does not allow clearing `ad_campaign_id`**. Passing `{"ad_campaign_id": null}` in the PATCH body results in `exclude_none=True` omitting the field from updates. To detach an ads campaign link, callers must use MKT-005's `detach_ad_campaign`. If this behavior is unintuitive and the team prefers null to mean "clear this field", `exclude_none=True` must be changed to `exclude_unset=True` combined with a custom `None → DELETE_ATTRIBUTE` transform — a significant change to the update expression builder.

6. **Open question: pagination cursor format**. `list_campaigns` uses `app.core.cursor.encode_cursor` / `decode_cursor`. Verify these helpers exist and accept a DynamoDB `LastEvaluatedKey` dict. If the cursor module uses a different convention, adjust accordingly. The cursor is opaque to callers (a base64-encoded JSON blob).

7. **Assumption: `list_campaigns` returns all campaigns regardless of status**. There is no status filter on `list_campaigns`. Admin queries by status use the `ByStatusCreatedAt` GSI; a `list_campaigns_by_status(status)` function will be added by MKT-006 when the status machine is implemented, mirroring `app/services/ad_campaigns.py:82–106`.

8. **Assumption: `audit_event` import is safe from `marketing_campaigns.py`**. The lazy import `from app.services.alerts import audit_event` inside a `try/except` mirrors the pattern in `app/services/ad_campaigns.py:155`. This avoids circular imports since `alerts.py` imports from `app.core.tables` but not from `marketing_campaigns.py`.
