# SHP-001 — Shipping module scoping & data-model delta

## 1. Summary & Goal

SHP-001 is the foundational spike for the OFBiz Shipping/Logistics work stream (Phase 8, module H). Its deliverable is this design document — not code. The goal is to:

1. Map every OFBiz Shipping/Logistics entity (carrier party-role, ShipmentMethodType, CarrierShipmentMethod, Shipment, ShipmentItem, ShipmentPackage, ShipmentPackageContent, ShipmentRouteSegment, ShipGroup on OrderHeader) to the current codebase, explicitly calling out what exists, what is absent, and what is explicitly deferred.
2. Lock the new DynamoDB tables, GSIs, `attr_types`, settings keys, and `SHIPPING_ENABLED` flag group so SHP-002 through SHP-015 can implement without re-litigating data-model decisions.
3. Confirm that the existing `carrier_tracking.py` helpers and the transaction shipping sub-record (`purchase_transactions.shipping`) are reused — not replaced — and that all existing shop/cart/orders/billing behavior is byte-for-byte unchanged when every `SHIPPING_*` flag is off.

This document is the authoritative design reference for SHP-002 through SHP-015 and supersedes any informal notes. No production code is shipped with this ticket.

## 2. Context & Current State

### 2.1 Existing carrier primitives

`app/services/carrier_tracking.py` provides all carrier URL and status logic:

- **`CARRIER_TRACKING_URLS`** (`carrier_tracking.py:10`): dict mapping four carrier codes (`ups`, `fedex`, `usps`, `dhl`) to tracking URL templates.
- **`build_tracking_url(carrier, tracking_number)`** (`carrier_tracking.py:33`): formats a tracking URL from the template; returns `None` for unknown carriers.
- **`detect_carrier(tracking_number)`** (`carrier_tracking.py:46`): auto-detects carrier from tracking-number format (UPS `1Z` prefix, DHL JD/JJD prefix, FedEx/USPS digit-length disambiguation).
- **`map_carrier_status(carrier, raw_status)`** (`carrier_tracking.py:84`): normalises carrier-specific strings to the internal seven-value status enum: `label_created`, `picked_up`, `in_transit`, `out_for_delivery`, `delivered`, `exception`, `returned`.
- **`ACTIVE_TRACKING_STATUSES`** (`carrier_tracking.py:129`): set of statuses worth polling (`shipped`, `label_created`, `picked_up`, `in_transit`, `out_for_delivery`).
- **`apply_tracking_result(order, result)`** (`carrier_tracking.py:138`): applies a normalised carrier response to a transaction's shipping sub-record via `update_shipping`; fires `send_delivery_alert` on `delivered` transitions.

These helpers are stable and must not be forked. The shipping module will add a fifth carrier code (`manual`) alongside the existing four; `build_tracking_url` returns `None` for `manual`, which is the correct behavior.

### 2.2 Transaction shipping sub-record

`app/services/purchase_history.py` owns the flat shipping map on `purchase_transactions`:

- **`update_shipping(user_sub, txn_id, shipping)`** (`purchase_history.py:398`): optimistic-lock `update_item` on the transaction; stores the whole `shipping` dict as a nested map attribute and surfaces `tracking_number` at the top level for a (future) GSI.
- **`find_transaction_by_tracking(tracking_number)`** (`purchase_history.py:595`): full-table scan with `FilterExpression` — functional but slow at scale; the code comment acknowledges a TrackingIndex GSI would help.
- **`PurchaseShippingIn`** (`app/models.py:438`): the existing Pydantic shape for the shipping map: `carrier`, `tracking_number`, `tracking_url`, `status`, `shipped_at`, `delivered_at`, `estimated_delivery`, `carrier_events`, `last_carrier_check`, `address`.

The transaction shipping sub-record represents shipping for the whole transaction (one ship-to address, one tracking number). This is appropriate for the common case and remains the primary tracking surface for legacy transactions. The new Shipment entity adds structure on top of it without replacing it.

### 2.3 Tracking endpoint

`app/routers/purchase_history.py:118` exposes `GET /ui/shop/transactions/{txn_id}/tracking` — reads the shipping sub-record and builds a tracking URL via `build_tracking_url`. This endpoint is unchanged.

`app/routers/carrier_tracking_poller.py` exposes `POST /ui/shop/tracking/transactions/{txn_id}/poll` (buyer/seller) and `POST /ui/shop/tracking/poll-now` (admin) at the `carrier_tracking_poller_router`. These are unchanged.

`app/routers/carrier_tracking_mock.py` provides mock seed/lookup endpoints at `/mock/carrier-tracking/*`, gated by `S.dev_mode`. These are unchanged.

### 2.4 Order model

`app/services/commerce_order_service.py:39` (`create_order`) writes a single `T.orders` item with `status="pending_payment"` (line 75) and per-line `T.order_items` rows (lines 88–103). The `orders` table (`scripts/local-ddb-init.py:287`) has GSIs `GSI_USER` and `GSI_STATUS` with `created_at` stored as an ISO string (not numeric). There is no ship-group or ship-to-address field on the order record today.

### 2.5 Existing flag pattern (template for SHIPPING_ENABLED)

`app/core/settings.py:839` (`inventory_reservations_enabled`, env `INVENTORY_RESERVATIONS_ENABLED`, default `false`) and `app/core/settings.py:846` (`returns_rma_enabled`, env `RETURNS_RMA_ENABLED`, default `false`) establish the OFBiz flag convention: a single boolean on `S`, checked by a `_require_enabled()` / `_flag_on()` guard in the service that raises HTTP 404 when off (`app/services/returns_rma.py:67–73`). The shipping module follows exactly this pattern.

## 3. Data Model

### 3.1 Existing tables extended (additive, no schema change)

**`orders`** — gains two optional attributes written only when `SHIPPING_ENABLED` is on:
- `ship_group` (map): `{ ship_to_address: {...}, ship_method_id: str, carrier_code: str, method_code: str }`. Written by the new `shipping_service.attach_ship_group` call after order creation. Absent on legacy orders; readers must tolerate its absence.

**`purchase_transactions`** — unchanged. The `shipping` sub-map continues to be the source of truth for tracking URL/status for legacy and simple flows. When `SHIPPING_ENABLED` is on, `apply_tracking_result` also updates the linked Shipment's status via a best-effort call (never blocks the existing path).

### 3.2 New tables

All four tables follow the `TableDef(_resolve_table_name(S.<name>, "<default>"), pk, sk, gsi=[...], attr_types={...})` pattern used for `orders` at `scripts/local-ddb-init.py:287` and `reservations` at `scripts/local-ddb-init.py:2469`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Shipment status machine

Valid statuses and transitions (mirrors internal statuses from `carrier_tracking.py:84`):

```
draft → pending_fulfillment → label_created → picked_up → in_transit
                                                         → out_for_delivery → delivered
                                                         → exception
                                                         → returned
draft → cancelled
pending_fulfillment → cancelled
label_created → cancelled  (only if tracking not yet picked_up by carrier)
```

`advance_shipment_status` enforces valid transitions; invalid transitions return HTTP 409.

### 5.2 Tracking-number registration

When `update_shipment_tracking` is called:
1. `detect_carrier(tracking_number)` is called if `carrier_code` is not supplied, reusing `carrier_tracking.py:46`.
2. `build_tracking_url(carrier_code, tracking_number)` is called and stored on the Shipment, reusing `carrier_tracking.py:33`.
3. Status advances to `label_created` if currently `pending_fulfillment`.
4. If the Shipment has a `purchase_txn_id`, `update_shipping` (`purchase_history.py:398`) is called to keep the legacy shipping sub-record in sync. This is best-effort (`try/except`); it must never block shipment creation.

### 5.3 Tracking-poll integration

The carrier tracking poller (`app/routers/carrier_tracking_poller.py`) currently updates the transaction's shipping sub-record via `apply_tracking_result` (`carrier_tracking.py:138`), which calls `update_shipping`. When `SHIPPING_ENABLED` is on, `apply_tracking_result` will additionally find and update the linked Shipment row using `purchase_txn_id` as a back-link. This is additive: the existing `update_shipping` call is not removed.

### 5.4 Ship group on order

`attach_ship_group(order_id, ship_group_data)` writes the `ship_group` map attribute to `T.orders` via `update_item`. It is called once after `create_order`. If the flag is off, this call is never made; the `orders` item has no `ship_group` attribute (tolerated by readers). Existing code that reads `T.orders` must not break when `ship_group` is present — callers should use `.get("ship_group")`.

### 5.5 Idempotency

`create_shipment` derives its `shipment_id` from `sha256(correlation_id)[:24]` where `correlation_id = "SHIP#{order_id}#{seq}"` (seq is the 1-based shipment sequence for the order). A `put_item` with `ConditionExpression="attribute_not_exists(shipment_id)"` enforces single-write idempotency; a second call with the same `correlation_id` raises HTTP 409 "Shipment already exists".

`seed_default_carriers()` uses `carrier_id = sha256(carrier_code)[:16]`; each `put_item` uses `ConditionExpression="attribute_not_exists(carrier_id)"` — second seed is a no-op.

### 5.6 Money-out: shipping-cost refunds

There is no new billing path. If a shipping fee was charged via the existing cart/billing flow, refunding it uses the existing `refund_payment` endpoint in `app/routers/billing.py:1287`. The shipping module does not fork or duplicate billing logic. The GL (`billing_shared.new_ledger_entry`, `billing_shared.py:224`) is the single source of truth; shipping never writes ledger entries directly.

### 5.7 Partial shipments

A single order may have multiple Shipment rows (e.g. items split across two fulfillment batches). `list_shipments_for_order` returns all of them via `GSI_ORDER`. The `ShipmentItem` rows track which order lines are in which Shipment. Quantities in `ShipmentItem` may be less than the original order line quantity for partial fulfillments — but the sum across all Shipments for a line should not exceed the ordered quantity. Over-shipment validation is best-effort (warn, not block) in initial scope.

### 5.8 `manual` carrier

The `manual` carrier code is valid for `CarrierIn` and `ShipmentIn`. `build_tracking_url("manual", tn)` returns `None` (no template in `CARRIER_TRACKING_URLS`), so `tracking_url` on the Shipment will be `null`. `online_tracking=False` is set on the catalog row. The carrier tracking poller skips Shipments with `carrier_code="manual"`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007**: All four new DynamoDB tables exist in both dev (DynamoDB Local) and prod (real DynamoDB) with identical schemas. No `if S.dev_mode` branches in the service logic. The carrier seed (`seed_default_carriers`) runs in both environments. No mock-only code paths exist in production-running modules.

**Idempotency**: Every write uses deterministic IDs (`sha256(correlation_id)[:N]`) and conditional `put_item` with `attribute_not_exists(pk)`. Retried requests receive HTTP 409 with a stable error body, so callers can detect idempotent replays.

**Ownership enforcement**: `get_shipment` checks `shipment.user_id == session["user_sub"]`; foreign shipments return 404 (not 403) to avoid leaking existence. Admin/root bypasses this check.

**Audit trail**: Every mutation (create/advance/cancel/tracking-update) emits `audit_event(...)` via `app/services/alerts.audit_event` (same pattern as `commerce_order_service.py:106`).

**No PII in `shipment_id`**: The deterministic ID is a truncated SHA-256 of an opaque correlation string; no user-sub or address data is embedded.

**`_require_enabled()` is the sole gate**: All router handlers call `_require_enabled()` as their first statement. When `S.shipping_enabled` is `False`, the response is HTTP 404 — indistinguishable from a non-existent endpoint, preventing enumeration of the module by unauthorized callers.

## 8. Backward Compatibility & Migration

**No breaking changes to existing tables**: The `orders` table gains an optional `ship_group` attribute written only when the flag is on and a shipment is created. All existing readers of `T.orders` use dict `.get(...)` and tolerate absent attributes.

**No migration required for existing transactions**: The `purchase_transactions.shipping` sub-record remains the primary tracking surface for all transactions created before `SHIPPING_ENABLED` is turned on. `find_transaction_by_tracking` (`purchase_history.py:595`) continues to work; it scans on `tracking_number` at the top level. The existing scan-based implementation is adequate for initial scope; a `TrackingIndex` GSI is a deferred improvement noted in the code comment at line 599.

**`GSI_STATUS` on `orders` uses ISO string `created_at`**: The existing `orders` GSIs store `created_at` as an ISO string, not a Unix integer (`local-ddb-init.py:288–293`). New `shipments.GSI_STATUS` and `shipments.GSI_ORDER` use numeric `created_at` (Unix seconds, via `now_ts()`). These are different tables; there is no conflict.

**Router registration**: The new `shipping_router` is appended to `app/main.py`'s router list. No existing router prefix is reused. The shipping flag guard ensures the router is a no-op when disabled.

## 10. Open Questions / Assumptions

1. **`created_at` type on `orders` GSIs**: The existing `orders` table stores `created_at` as an ISO string (`local-ddb-init.py:291`). This spec assumes new shipment tables use numeric Unix seconds (`now_ts()`) for consistency with newer tables (e.g. `reservations` at `local-ddb-init.py:2477`). Verify with SHP-002 implementer that this divergence is intentional and that no cross-table join on `created_at` is ever attempted.

2. **Ship group on `order_items`**: This spec adds `ship_group` only to the `orders` header (single group per order). If multi-group (different items shipped to different addresses) is needed before the deferred milestone, an `order_items.ship_group_seq` integer attribute would be required. Assumed deferred.

3. **Shipping-fee billing**: Cart-level shipping cost is outside SHP scope. The assumption is that shipping fees are bundled into the cart total and already billed via the existing cart-checkout/billing path, so the Shipment entity is a fulfillment record only — not a billing record. If shipping fees need to be billed separately, a separate ticket is required before SHP is considered complete.

4. **`purchase_txn_id` back-link strategy**: This spec proposes storing `purchase_txn_id` on the Shipment so `apply_tracking_result` can find and sync the Shipment when a poll fires. The alternative — querying `GSI_ORDER` by `order_id` — requires the transaction to carry `order_id`, which not all legacy transactions do. Confirm that the link is always available at Shipment creation time.

5. **`orders` table no sort key**: `orders` has no sort key (`local-ddb-init.py:287–294`); `get_item(Key={"order_id": order_id})` is the primary access pattern. `attach_ship_group` uses `update_item(Key={"order_id": order_id}, ...)`. This is correct; assumed stable.

6. **`tracking_number` top-level attribute on `purchase_transactions`**: `update_shipping` at `purchase_history.py:416–418` also writes `tracking_number` at the top level of the transaction item (for a future GSI). The shipping module's best-effort sync call will trigger this side-effect on each tracking update. This is intentional and desirable.

7. **Carrier API live integration timeline**: `shipping_carrier_api_enabled` is a separate sub-flag (default `false`). This spec defers live UPS/FedEx/USPS/DHL rate-API calls to SHP-007+. The rate estimation endpoint returns catalog `base_rate_cents` until that flag is enabled.

## 14. Reconciliation Applied

- **Plan-gap row 44 (ESCALATIONS §A)** — `returned` carrier status ownership:
  **Resolution (authoritative)**: SHP-012 owns adding the carrier-raw → `returned` mapping inside `apply_tracking_result_to_shipment`. Specifically, SHP-012's `apply_tracking_result_to_shipment` must inspect the raw carrier event string **before** calling `map_carrier_status`; when the raw string contains "returned to sender" (or equivalent per-carrier variants such as UPS "RETURNED TO SENDER", FedEx "Return to Shipper"), it must map directly to `new_status = "returned"` without going through `map_carrier_status`. The claim in SHP-012's dependency table (§11) that `carrier_tracking.py` functions are "reused without modification" remains accurate — `map_carrier_status` itself is unchanged; the returned-to-sender mapping is applied as a pre-check in `apply_tracking_result_to_shipment` before delegating the rest of normalisation to `map_carrier_status`. SHP-001 does not claim `carrier_tracking.py` is unmodified; §11 no longer implies SHP-012 is blocked by this gap. Authoritative spec: SHP-012.

- **Open decision §10 Q4** — `purchase_txn_id` back-link population strategy:
  **Resolution (default applied)**: The `external_ref` fallback scan (SHP-014 §5.6, using `external_ref = order_id` written by `record_cart_purchase` at `purchase_history.py:270`) is the MVP resolution. `purchase_txn_id` on the Shipment row remains optional at creation time. SHP-008 callers are not required to supply it. SHP-014's `_link_txn_shipping` resolves the transaction via the `external_ref` scan when `purchase_txn_id` is absent. No new GSI on `purchase_transactions` is required for Phase 1. Authoritative spec: SHP-014 §5.6.
