# MKT-008 — Party segments (rule-based dynamic membership)

## 1. Summary & Goal

MKT-008 adds the dynamic-segment counterpart to MKT-007's static contact lists. A **party segment** is a stored predicate set — one or more rules of the form `(attribute, operator, value)` — that is evaluated over live party data to produce a membership set. Two execution modes are provided:

- **`evaluate_segment(segment_id, owner_id)`** — live evaluation, returns matching `party_id` values immediately. Used for preview and count estimation.
- **`snapshot_segment(segment_id, owner_id)`** — materializes a point-in-time membership snapshot as immutable DDB rows, indexed by snapshot timestamp. Used by MKT-009 for deterministic campaign sends.

Party attributes available for predicate matching today:

| Source | Attributes |
|--------|-----------|
| Profile (`app/services/profile.get_profile`) | `display_name`, `first_name`, `last_name`, `gender`, `location`, `locale`, `birthday` |
| Subscription (`app/services/subscription_access.has_active_subscription`) | `has_active_subscription` (bool), `subscription_status` (active/past_due/trialing) |
| Orders (`T.orders` via `GSI_USER` index) | `order_count` (N), `total_spend_cents` (N), `last_order_at` (S, ISO-8601 string) |
| Billing ledger (`T.billing` via `ddb_query_pk`) | `total_paid_cents` (N, sum of LEDGER# settled debits) |

Evaluation is **read-only over existing tables**. No row in `T.profile`, `T.subscriptions`, `T.orders`, or `T.billing` is modified by this service. The shared opt-out signal (`cart_reminders.is_user_opted_out`) is honored at send-resolution time by MKT-009; raw `evaluate_segment` returns all matching parties including opted-out ones (flagged in the result), while snapshot rows carry an `opted_out` bool so MKT-009 can suppress them without re-querying.

Everything is gated on `S.marketing_campaigns_enabled` (default off). With the flag off, all mutating paths in this service raise 403 and no new rows are written.

### Opt-out signal

`app/services/cart_reminders.py:95-107` — `is_user_opted_out(user_sub)` reads `T.cart_reminder_config` under `OPTOUT#USER#{sub}` / `META`. Opt-out state is a shared "do-not-contact" signal reused across cart reminders (same function used by MKT-007 `list_members_for_send`). MKT-008 calls it during `snapshot_segment` to record the `opted_out` flag on each snapshot member row.

### Deterministic segment_id (MKT-004 pattern)

MKT-004 established `sha256(owner_id + "\x00" + name + "\x00" + created_bucket)[:24]` for marketing object ids. MKT-008 applies the same scheme to `segment_id`. Snapshot ids use `sha256(segment_id + "\x00" + str(snap_ts))[:24]` to remain deterministic and idempotent across retry.

### Audit events

`app/services/alerts.py:644` — `audit_event(event, user_sub, request=None, **fields)`. MKT-008 calls it (fire-and-forget inside `try/except`) on segment creation, update, deletion, evaluation, and snapshotting. The same pattern appears at `app/services/commerce_order_service.py:106-117`.

### Existing party candidate enumeration challenge

There is no system-wide "users" scan index optimized for arbitrary attribute queries. The party candidate source for evaluation depends on predicate type:

- **Subscription predicates**: `T.subscriptions.query(pk=CREATOR#{creator_id})` returns all subscribers to a given creator. This is the only subscription-predicated segment type that is efficient without a full scan.
- **Profile and order/spend predicates**: candidate set is built from a configurable `candidate_source` on the segment: either a linked `contact_list_id` (evaluated against `T.contact_lists`) or a `segment_scope` of `"subscribers_of:{creator_id}"`. Free-form scans of `T.profile` or `T.orders` without a scoped input are explicitly rejected at validation time to prevent accidental full-table scans.

This constraint is noted in Section 10 (Open Questions).

MKT-008 uses the `PartySegments` DDB table (single-table, two row types) added by MKT-002. No new DDB tables are introduced beyond what MKT-002 defines.

### Table: PartySegments

Default name: `PartySegments` (env `DDB_PARTY_SEGMENTS`). Handle: `T.party_segments`.

#### Row types

| Row type | PK | SK | Key scalar attributes |
|----------|----|----|----------------------|
| Segment META | `OWNER#{owner_id}` | `SEGMENT#{segment_id}` | `owner_id` (S), `segment_id` (S), `name` (S), `description` (S), `rules` (List), `candidate_source` (S), `created_at` (N), `updated_at` (N) |

#### GSIs (to be added by MKT-002 or self-contained in MKT-008 if not yet declared)

| Index name | Partition key | Sort key | Type | Used by |
|------------|---------------|----------|------|---------|
| `ByOwnerCreatedAt` | `owner_id` (S) | `created_at` (N) | GLOBAL | `list_segments` — all segments for an owner, newest first |

```python

    "pk",
    "sk",
    gsi=[
        {"index_name": "ByOwnerCreatedAt",  "partition_key": "owner_id",   "sort_key": "created_at"},
        {"index_name": "BySegmentSnapTs",     "partition_key": "segment_id", "sort_key": "snap_ts"},
    ],
    attr_types={"created_at": "N", "snap_ts": "N"},
),
```

#### `rules` attribute schema

Each element of the `rules` list is stored as a DynamoDB Map:

```
{
  "attribute": "total_spend_cents",   # str, validated against VALID_ATTRIBUTES
  "operator":  "gte",                 # str, validated against VALID_OPERATORS
  "value":     5000                   # any JSON-compatible scalar; DDB stores as N/S/BOOL
}
```

#### `candidate_source` attribute schema

A string using one of two patterns:

- `"list:{list_id}"` — candidate party_ids drawn from a MKT-007 contact list (iterates `T.contact_lists` member rows under `LIST#{list_id}#PARTY#*`)
- `"subscribers_of:{creator_id}"` — candidate party_ids drawn from active/past_due/trialing subscribers of a creator (queries `T.subscriptions` with `pk=CREATOR#{creator_id}`)

Any other value is rejected with 422 at segment creation time.

#### Predicate validation constants

```python
# Validated at segment creation and update; unknown value → 422.
# NOTE: profile field is "location" (free-text), not "country" — mirrors
# PROFILE_FIELDS at app/services/profile.py:16-33.
VALID_ATTRIBUTES: frozenset[str] = frozenset({
    # Profile
    "display_name", "first_name", "last_name", "gender", "location", "locale",
    # Subscription
    "has_active_subscription", "subscription_status",
    # Order history
    "order_count", "total_spend_cents", "last_order_at",
    # Billing ledger
    "total_paid_cents",
})

VALID_OPERATORS: frozenset[str] = frozenset({
    "eq", "ne", "lt", "lte", "gt", "gte",
    "contains", "not_contains",  # string substring match only
    "exists", "not_exists",       # attribute presence check (value ignored)
})

# Operators restricted to numeric attributes
_NUMERIC_ONLY_OPERATORS: frozenset[str] = frozenset({"lt", "lte", "gt", "gte"})

_NUMERIC_ATTRIBUTES: frozenset[str] = frozenset({
    "order_count", "total_spend_cents", "last_order_at", "total_paid_cents",
})
```

#### Helper: `_require_flag()`

```python
def _require_flag() -> None:
    if not S.marketing_campaigns_enabled:
        raise HTTPException(403, "Marketing campaigns module is disabled")
```

Called at the top of all mutating functions (create, update, delete, snapshot). `evaluate_segment` is read-only and does not require the flag — it can be called to preview pre-existing segments when the flag is temporarily off.

#### Helper: `_segment_id(owner_id, name, ts)`

```python
def _segment_id(owner_id: str, name: str, ts: int) -> str:
    bucket = (ts // 3600) * 3600
    raw = f"{owner_id}\x00{name}\x00{bucket}".encode("utf-8")
    return hashlib.sha256(raw).hexdigest()[:24]
```

Deterministic within a one-hour window — a retried create with identical `(owner_id, name)` within the same hour returns the same id and the conditional put fails gracefully.

#### Helper: `_snap_id(segment_id, snap_ts)`

```python
def _snap_id(segment_id: str, snap_ts: int) -> str:
    raw = f"{segment_id}\x00{snap_ts}".encode("utf-8")
    return hashlib.sha256(raw).hexdigest()[:24]
```

Deterministic per `(segment_id, snap_ts)` — a re-run of `snapshot_segment` at the same second produces the same `snap_id` and the member writes are upserts, making the snapshot idempotent at second-level granularity.

#### Helper: `_validate_rules(rules)`

Validates each rule dict:
1. `attribute` must be in `VALID_ATTRIBUTES` — else `ValueError("Unknown attribute: {attr}")`.
2. `operator` must be in `VALID_OPERATORS` — else `ValueError("Unknown operator: {op}")`.
3. If `operator` is in `_NUMERIC_ONLY_OPERATORS` and `attribute` not in `_NUMERIC_ATTRIBUTES` → `ValueError("Operator {op} requires a numeric attribute")`.
4. `"contains"` / `"not_contains"` is only valid for string attributes (everything not in `_NUMERIC_ATTRIBUTES`) — else `ValueError`.
5. `value` must be present for all operators except `exists` / `not_exists`.

Called in `create_segment` and `update_segment`. Raises `HTTPException(422, detail=str(e))` wrapping any `ValueError`.

#### Helper: `_validate_candidate_source(candidate_source)`

Validates the format of the `candidate_source` string. Must match `^(list|subscribers_of):.+$`. Raises `HTTPException(422, ...)` on mismatch.

def evaluate_segment(
    segment_id: str,
    owner_id: str,

    """
    Reads the segment META, resolves candidates from candidate_source,
    then applies each rule predicate to the candidate's resolved attributes.
    Returns:
      {
        "segment_id": str,
        "evaluated_at": int,          # Unix timestamp
        "matching_count": int,
        "total_candidates": int,
        "opted_out_count": int,        # informational; not excluded from result
        "members": [

          ...

    Does NOT require the flag (preview always available).
    Raises 404 if segment not found.
    Emits best-effort audit_event("party_segment.evaluated", owner_id, segment_id=...).

def snapshot_segment(
    segment_id: str,
    owner_id: str,
) -> dict[str, Any]:
    """
    1. Calls evaluate_segment internally to resolve current membership.
    2. Writes a SNAP META row: pk=SEGMENT#{segment_id}, sk=SNAP#{snap_ts},
       snap_id=_snap_id(segment_id, snap_ts), party_count, opted_out_count.
    3. For each matching party, writes a member row:
         pk=SEGMENT#{segment_id}#SNAP#{snap_id}, sk=PARTY#{party_id},
         opted_out=is_user_opted_out(party_id), snapped_at=snap_ts.
       Member writes use put_item (upsert — idempotent for same snap_id).
    4. Snap META write uses a conditional put (attribute_not_exists(pk) AND
       attribute_not_exists(sk)) to prevent overwriting an existing snapshot.
       On ConditionalCheckFailedException at the META level (same-second replay),
       skips member writes and returns the existing snapshot metadata.
    5. Returns the SNAP META dict.
    Calls _require_flag().
    Emits audit_event("party_segment.snapshotted", owner_id, segment_id=...,
                       snap_id=..., party_count=...).
    """

#### Predicate evaluation helper (private)

```python
def _apply_rule(attributes: dict, rule: dict) -> bool:
    """
    Evaluates a single rule against a resolved attribute dict.
    Returns True if the party matches the rule, False otherwise.
    Operator semantics:
      eq / ne  — Python == / !=
      lt/lte/gt/gte — numeric comparison (coerce both sides to float)
      contains / not_contains — Python 'in' on str(attribute)
      exists — attribute key present and value is not None
      not_exists — attribute key absent or value is None
    Type coercion: if attribute value is Decimal (from DDB), convert to int.
    A rule where attribute is not in the resolved dict is treated as not_exists.
    """
```

## 5. Detailed Behavior & Edge Cases

### Predicate evaluation semantics

- **Multi-rule segments**: all rules are ANDed. A party matches only if every rule in the `rules` list evaluates to True.
- **Empty rules list**: validation rejects it (minimum 1 rule required, enforced in `_validate_rules`).
- **Decimal coercion**: DynamoDB returns `Decimal` for numeric attributes. `_apply_rule` converts both sides to `int` (or `float` for `last_order_at`) before numeric comparison, consistent with the `MessageEncryptionEnvelope` Decimal coercion pattern in `app/models.py`.
- **Missing attribute**: treated as `not_exists`. A rule `(order_count, gte, 1)` evaluates to False for a party with no orders, even though `order_count` would be 0. The caller should use `(exists, order_count)` AND `(order_count, gte, 1)` if they want to handle the zero-orders case.
- **`subscription_status` predicate**: `_resolve_attributes` queries `T.subscriptions` for the party's SUB# rows and returns the status of the most recent row sorted by `created_at` desc. If no subscription exists, the attribute is absent (evaluates as `not_exists`).
- **`has_active_subscription` predicate**: bool True iff any subscription row has `status in {"active","past_due","trialing"}`. No `creator_id` scoping — it checks across all creators. This differs from `has_active_subscription(subscriber_id, creator_id)` which is creator-scoped. For creator-scoped subscription checks, the caller should use `candidate_source="subscribers_of:{creator_id}"` which already scopes the candidate set.

### Candidate source constraints

- `"list:{list_id}"`: the list must exist in `T.contact_lists` and be owned by the same `owner_id`. If the list_id belongs to a different owner, validation returns 403 (not 404) to prevent information leakage.
- `"subscribers_of:{creator_id}"`: no ownership check on `creator_id` — any creator's subscriber list is a valid candidate source. The `creator_id` in the source does not need to match the segment `owner_id`.
- Free-form scan candidate sources (no scoping prefix) are deliberately not supported to prevent DynamoDB full-table scans.

### Snapshot immutability

- Once written, a snapshot's META row (`pk=SEGMENT#{segment_id}`, `sk=SNAP#{snap_ts}`) and its member rows are never mutated or deleted by this service.
- Re-calling `snapshot_segment` at a later time produces a new snapshot at the new `snap_ts`. The two snapshots coexist under separate `SNAP#` sort keys.
- Re-calling `snapshot_segment` at the exact same second produces the same `snap_ts` → same `snap_id` → member `put_item` calls are upserts (idempotent). The SNAP META conditional put fails on replay, and the service returns the existing metadata. This is the idempotency guarantee.

### Opt-out handling

- `evaluate_segment` includes opted-out parties in `members` but sets `opted_out=True` on their entries. The `opted_out_count` field lets the caller see the raw vs. send-eligible counts.
- `snapshot_segment` records `opted_out` on each member row by calling `is_user_opted_out(party_id)` at snapshot time. MKT-009 queries `list_snapshot_members(include_opted_out=False)` to get the send-eligible set. This means opt-out state at snapshot time is honored; a party who opts out after the snapshot was taken is still excluded only if MKT-009 re-evaluates opt-out at send time (MKT-009 spec concern, not MKT-008's).
- The `cart_reminder_config` table and its schema are untouched.

### Orders `created_at` as string

The `orders` table stores `created_at` as an ISO string (e.g. `"2026-05-15T12:00:00"`) per `app/services/commerce_order_service.py:65` (`self._now_iso()`). The `last_order_at` segment attribute stores this string. Segment rules using `last_order_at` with `lt`/`lte`/`gt`/`gte` operators compare the ISO string lexicographically, which is correct for UTC-normalized ISO-8601. The attribute is labelled `(N)` in the table description above as a conceptual numeric/temporal value, but the runtime type is string; predicates using `contains`/`not_contains` are also valid (e.g., matching on a specific date prefix).

### Large candidate sets

`_resolve_candidates` paginates through `T.contact_lists` or `T.subscriptions` via `LastEvaluatedKey` until exhausted, collecting all matching ids. For very large candidate sets (>10,000 parties), `evaluate_segment` and `snapshot_segment` may be slow. This is a known limitation (see Section 10). A `max_candidates` guard (default 5,000, env `SEGMENT_EVAL_MAX_CANDIDATES`) aborts evaluation with HTTP 400 `"candidate_set_too_large"` to prevent runaway scans.

### `FilterExpression` and pagination

`list_snapshot_members` with `include_opted_out=False` applies a DDB `FilterExpression`. Per CLAUDE.md: "DynamoDB fetches up to 1MB before applying FilterExpression." The function paginates with `LastEvaluatedKey` automatically until `limit` items are returned or the table is exhausted, exactly as the CLAUDE.md gotcha requires.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

All DDB operations use `T.party_segments` (handled by `_safe_table`), `T.contact_lists`, `T.subscriptions`, `T.orders`, `T.billing`, and `T.cart_reminder_config` — all of which are wired to `DDB_ENDPOINT_URL=http://localhost:8001` in dev and to real DynamoDB in prod via the same `boto3.resource` path. No `dev_mode` branch exists in this service. `is_user_opted_out` reads the same `T.cart_reminder_config` table in both envs.

### Idempotency

| Operation | Idempotency mechanism |
|---|---|
| `create_segment` | `ConditionExpression="attribute_not_exists(pk)"` on OWNER#{owner_id}/SEGMENT#{segment_id}; retry returns existing item |
| `snapshot_segment` (SNAP META) | `ConditionExpression="attribute_not_exists(pk) AND attribute_not_exists(sk)"` on SEGMENT#{segment_id}/SNAP#{snap_ts} |
| `snapshot_segment` (member rows) | `put_item` unconditionally — upsert; same `party_id` under same `snap_id` is idempotent |
| `update_segment` | Conditional on segment existence (404 guard); attribute-level `UpdateExpression` is idempotent |

### Security

- **Owner isolation**: every operation verifies `owner_id` from the authenticated session (`ctx["user_sub"]`). The segment META key includes `OWNER#{owner_id}` in the PK, so a cross-owner read would produce no result (DDB key miss → 404). There is no admin-impersonation path in this service for MKT-008 scope.
- **Candidate source ownership** (`"list:{list_id}"`) is validated against the requesting owner before evaluation begins. If the list's `owner_id` field on the META row does not match the requesting `owner_id`, the service returns 403.
- **No PII leakage via evaluation errors**: `_resolve_attributes` swallows all exceptions from profile/subscription/order/billing queries. A party with a restricted or deleted profile simply yields empty attributes and is unlikely to match any predicate. This prevents timing-based inference about whether a party exists.
- **Candidate size cap** (`segment_eval_max_candidates`) limits DDB read amplification. Operators exceeding the cap receive a structured 400 error rather than a silent timeout.
- **Audit events** on all mutating operations (including evaluate, which is read-only but potentially sensitive as it reveals who matches a segment) ensure operator visibility in the audit log.

### No existing table mutations

The `party_segments` table is new; no existing DDB rows are modified.

### `just restart` compatibility

Adding the `PartySegments` table definition to `scripts/local-ddb-init.py` follows the same pattern as all other tables. `just restart` recreates all tables; the new table is created alongside existing ones. No data migration is required.

### MKT-009 contract

`snapshot_segment` is specifically designed to produce rows queryable by `BySegmentSnapTs` GSI (`segment_id` pk, `snap_ts` sort key). MKT-009 will query this index to find the latest snapshot for a given segment and then call `list_snapshot_members` with `include_opted_out=False` to retrieve the send-eligible set. This interface is frozen and must not change after MKT-009 ships.

## 10. Open Questions / Assumptions

1. **Assumption: `T.contact_lists` uses `pk=LIST#{list_id}` / `sk=PARTY#{party_id}` for member rows** — inferred from MKT-007 spec Section 3. If the actual implementation differs, `_resolve_candidates` must be updated accordingly.

2. **Assumption: `orders.created_at` is an ISO string** — CONFIRMED. `app/services/commerce_order_service.py:19-20` defines `_now_iso()` as `datetime.now(timezone.utc).isoformat()`. The orders table `TableDef` at `scripts/local-ddb-init.py:287-294` has **no** `attr_types` declaration, so DDB stores `created_at` as String (S). The `last_order_at` predicate comparisons are therefore lexicographic on ISO strings, not numeric epoch. A note in the operator documentation should make this explicit. An alternative is to convert to epoch in `_resolve_attributes` for consistency; that's a MKT-001 data-model decision to revisit.

3. **Assumption: `orders.GSI_USER` has `user_id` (string) as its HASH key** — CONFIRMED at `scripts/local-ddb-init.py:291`. The query uses `Key("user_id").eq(party_id)`. Note that `user_id` in the orders table and `user_sub` in profiles/subscriptions are the same identifier; this should be verified end-to-end.

4. **Open question: billing ledger `total_paid_cents` derivation** — summing all `LEDGER#*` rows with `state="settled"` and `amount_cents > 0` (debits) from `T.billing` for `pk=USER#{party_id}` is a full-partition scan for every candidate. For large segments this is O(candidates × ledger_depth). A denormalized `total_paid_cents` balance field on the `BALANCE` row would be more efficient. Deferring to MKT-001 to decide whether to add that field or accept the scan cost (guarded by `segment_eval_max_candidates`).

5. **Open question: profile table scan for arbitrary owner populations** — There is currently no efficient way to enumerate "all users with `location` containing a specific string" without a full scan of `T.profile`. This spec constrains candidate sources to `list:` and `subscribers_of:` to avoid that. If cross-population segments are needed in the future, a GSI on profile attributes or a separate search index (e.g., the existing `app/services/discovery.py` index) would be required.

6. **Assumption: `T.subscriptions` stores subscriber-scoped rows at `pk=SUBSCRIBER#{subscriber_id}` / `sk=SUB#...`** with a `creator_id` field — CONFIRMED at `app/services/subscription_access.py:57-64`. The `"subscribers_of:{creator_id}"` resolution queries `pk=CREATOR#{creator_id}` with `sk begins_with "SUB#"` (the creator-scoped partition). CONFIRMED: `app/routers/subscription_server.py:543` shows `save_subscription` writes a `creator_index` item at `pk=CREATOR#{creator_id}` / `sk=SUB#{subscription_id}` with the full subscription dict (including `subscriber_id`). `app/services/account_deletion.py:532-535` documents this three-partition fan-out layout explicitly. The assumption is safe.

7. **Open question: maximum snapshot size** — The spec does not impose a hard cap on snapshot member count (distinct from the `max_candidates` evaluation cap). A large creator with 100,000 subscribers could produce a snapshot with 100,000 member rows. DDB `put_item` costs are linear. A `max_snapshot_members` env guard (e.g. 50,000) may be prudent; left to MKT-001 to decide.

8. **CORRECTED (pass 3): MKT-003 defines `PartySegmentCreateIn` with `predicates: List[SegmentPredicate]` (not `rules: list[SegmentRuleIn]`) and NO `candidate_source` field.** `SegmentRuleIn` does not exist in MKT-003. MKT-008's service uses `data.predicates` internally and renames the concept to "rules" only in its private helper `_validate_rules`. `candidate_source` validation must be added to `PartySegmentCreateIn` (via MKT-003 owner) or enforced purely at the service layer in MKT-008. See §13 for resolution detail.
