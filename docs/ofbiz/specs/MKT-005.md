# MKT-005 — Campaign ↔ ads / promo linkage & spend rollup

## 1. Summary & Goal

MKT-005 adds three capabilities to `app/services/marketing_campaigns.py` (introduced by MKT-004):

1. **Ad-campaign linkage** — `attach_ad_campaign(owner_id, campaign_id, ad_campaign_id)` and `detach_ad_campaign(owner_id, campaign_id)` write only to the `MarketingCampaigns` DDB row; the linked `AdCampaigns` row is read-only from this module's perspective.
2. **Promo-code linkage** — `attach_promo_code(owner_id, campaign_id, code_id)` and `detach_promo_code(owner_id, campaign_id, code_id)` maintain a `promo_code_ids` list on the campaign META row; the linked `PromoCodes` rows are untouched.
3. **Attribution rollup** — `compute_attribution(owner_id, campaign_id)` reads `lifetime_spent_cents` and `spent_today_cents` from the linked ads campaign, calls `promo_codes.get_promo_stats` for each linked promo code, and (once MKT-010 lands) reads denormalized counters from the linked tracking code — assembling a `CampaignAttributionOut` without ever writing to any external table.

The entire feature is gated on `S.marketing_campaigns_enabled`. The billing ledger, promo redemption counters, and ad billing records are strictly read-only; this ticket never forks billing or calls `new_ledger_entry`.

## 3. Data Model

MKT-005 introduces no new DDB tables. All writes go to the existing `MarketingCampaigns` table (from MKT-002) at the campaign META row only.

### Campaign META row — relevant fields

| Attribute | Type | Written by |
|-----------|------|-----------|
| `pk` | S | `OWNER#{owner_id}` (MKT-004) |
| `sk` | S | `MKTCAMP#{campaign_id}` (MKT-004) |
| `ad_campaign_id` | S or absent | MKT-004 (initial), MKT-005 (update) |
| `ad_account_id` | S or absent | MKT-005 (resolved at attach time; needed for spend lookup) |
| `promo_code_ids` | L (list of S) | MKT-004 (initial list), MKT-005 (append / filter) |
| `updated_at` | N | MKT-004 on create/update, MKT-005 on each attach/detach |

The `ad_account_id` attribute is new in MKT-005. It must be stored alongside `ad_campaign_id` because `get_campaign(account_id, campaign_id)` in `app/services/ad_campaigns.py:66` requires both. At attach time the service resolves the account via the `ByCampaignId` GSI on `AdCampaigns`; the resolved `account_id` is persisted so `compute_attribution` can do a direct point-get without an additional GSI query at read time.

### No new tables, no schema migration

The `MarketingCampaigns` table already exists (MKT-002). The `ad_account_id` and `promo_code_ids` attributes are additive sparse attributes — pre-existing rows without them default to `None` / `[]` in the service layer. No `scripts/local-ddb-init.py` changes are needed.

## 4. API / Service Design

All functions live in `app/services/marketing_campaigns.py` (MKT-004's file). The router endpoint wiring is deferred to MKT-011.

### 4.1 Flag guard helper

```python
# Already defined by MKT-004 in marketing_campaigns.py — reproduced here for clarity.
# CORRECTED: raises 403, not 404 (MKT-004 spec:194 uses status_code=403).
def _require_enabled() -> None:
    if not S.marketing_campaigns_enabled:
        raise HTTPException(status_code=403,          # 403 per MKT-004 spec:194
                            detail={"code": "marketing_campaigns_disabled",
                                    "message": "Marketing campaigns are not enabled"})
```

Called at the top of every mutating function. Reads (non-mutating) functions do not guard — pre-existing rows remain accessible when the flag is later toggled off.

### 4.2 `attach_ad_campaign`

```python
def attach_ad_campaign(
    owner_id: str,
    campaign_id: str,
    ad_campaign_id: str,
) -> dict:
    """Link an ads campaign to a marketing campaign.

    Validates the ads campaign exists and is owned by an ad account
    accessible to owner_id (resolved via ByCampaignId GSI).
    Writes ad_campaign_id + ad_account_id onto the marketing campaign row.
    Returns the updated MarketingCampaignOut dict.
    Raises HTTPException 404 if the marketing campaign or ads campaign does not exist.
    Raises HTTPException 403 if the marketing campaign belongs to a different owner.
    """
```

**Steps:**

1. `_require_enabled()`
2. Fetch the marketing campaign: `T.marketing_campaigns.get_item(Key={"pk": f"OWNER#{owner_id}", "sk": f"MKTCAMP#{campaign_id}"})`. If missing → 404. If `item["owner_id"] != owner_id` → 403 (defensive; the PK already encodes owner, but explicit check guards against any future SK-only queries).
3. Resolve the ads campaign via `ByCampaignId` GSI on `T.ad_campaigns`:
   ```python
   resp = T.ad_campaigns.query(
       IndexName="ByCampaignId",
       KeyConditionExpression=Key("campaign_id").eq(ad_campaign_id),
       Limit=1,
   )
   items = resp.get("Items", [])
   ```
   If `items` is empty → 404 (`"Ads campaign not found"`).
4. Extract `account_id = items[0]["account_id"]` from the resolved row.
5. Write `ad_campaign_id` and `ad_account_id` onto the marketing campaign row:
   ```python
   T.marketing_campaigns.update_item(
       Key={"pk": f"OWNER#{owner_id}", "sk": f"MKTCAMP#{campaign_id}"},
       UpdateExpression="SET ad_campaign_id = :ac, ad_account_id = :aa, updated_at = :ts",
       ExpressionAttributeValues={
           ":ac": ad_campaign_id,
           ":aa": account_id,
           ":ts": now_ts(),
       },
   )
   ```
6. Return the refreshed campaign item (re-fetch via `get_campaign(owner_id, campaign_id)`).

### 4.3 `detach_ad_campaign`

```python
def detach_ad_campaign(
    owner_id: str,
    campaign_id: str,
) -> dict:
    """Remove the linked ads campaign from a marketing campaign.

    Idempotent: if no ad_campaign_id is currently linked, returns the
    unchanged campaign without error.
    Returns the updated MarketingCampaignOut dict.
    """
```

**Steps:**

1. `_require_enabled()`
2. Fetch and ownership-check the marketing campaign (same as step 2 above).
3. Remove both attributes unconditionally (DDB REMOVE does not error on absent attributes):
   ```python
   T.marketing_campaigns.update_item(
       Key={"pk": f"OWNER#{owner_id}", "sk": f"MKTCAMP#{campaign_id}"},
       UpdateExpression="REMOVE ad_campaign_id, ad_account_id SET updated_at = :ts",
       ExpressionAttributeValues={":ts": now_ts()},
   )
   ```
4. Return refreshed campaign.

### 4.4 `attach_promo_code`

```python
def attach_promo_code(
    owner_id: str,
    campaign_id: str,
    code_id: str,
) -> dict:
    """Append a promo code to the campaign's promo_code_ids list.

    Validates the promo code exists.
    Idempotent: if code_id is already in the list, returns the campaign unchanged.
    Returns the updated MarketingCampaignOut dict.
    Raises HTTPException 404 if campaign or promo code does not exist.
    """
```

**Steps:**

1. `_require_enabled()`
2. Fetch and ownership-check the marketing campaign.
3. Validate the promo code: `from app.services.promo_codes import get_promo_code; code = get_promo_code(code_id)`. If `None` → 404 (`"Promo code not found"`).
4. Read current `promo_code_ids = item.get("promo_code_ids") or []`. If `code_id` already in the list → return current item (idempotent, no write).
5. Append via `list_append`:
   ```python
   T.marketing_campaigns.update_item(
       Key={"pk": f"OWNER#{owner_id}", "sk": f"MKTCAMP#{campaign_id}"},
       UpdateExpression=(
           "SET promo_code_ids = list_append("
           "if_not_exists(promo_code_ids, :empty), :new_code), "
           "updated_at = :ts"
       ),
       ExpressionAttributeValues={
           ":empty": [],
           ":new_code": [code_id],
           ":ts": now_ts(),
       },
   )
   ```
6. Return refreshed campaign.

### 4.5 `detach_promo_code`

```python
def detach_promo_code(
    owner_id: str,
    campaign_id: str,
    code_id: str,
) -> dict:
    """Remove a promo code from the campaign's promo_code_ids list.

    Idempotent: if code_id is not in the list, returns the campaign unchanged.
    Never modifies the PromoCodes table.
    Returns the updated MarketingCampaignOut dict.
    """
```

**Steps:**

1. `_require_enabled()`
2. Fetch and ownership-check the marketing campaign.
3. Read `promo_code_ids = item.get("promo_code_ids") or []`. If `code_id` not in list → return current item.
4. Build filtered list: `new_ids = [x for x in promo_code_ids if x != code_id]`.
5. Write the filtered list back:
   ```python
   T.marketing_campaigns.update_item(
       Key={"pk": f"OWNER#{owner_id}", "sk": f"MKTCAMP#{campaign_id}"},
       UpdateExpression="SET promo_code_ids = :ids, updated_at = :ts",
       ExpressionAttributeValues={":ids": new_ids, ":ts": now_ts()},
   )
   ```
6. Return refreshed campaign.

**Why read-modify-write instead of DDB native list index removal:** DDB's `REMOVE promo_code_ids[N]` requires knowing the numeric index, which can shift if concurrent updates happen. For list lengths expected to be small (campaign promo codes are typically single-digit), read-modify-write under the existing item version is correct and simpler. A `ConditionExpression` on `updated_at = :prev_ts` can be added for optimistic locking if contention becomes a concern (recorded as open question in Section 10).

### 4.6 `compute_attribution`

```python
def compute_attribution(
    owner_id: str,
    campaign_id: str,
) -> dict:
    """Compute a spend/redemption rollup for a marketing campaign.

    Read-only: never writes to MarketingCampaigns, AdCampaigns, PromoCodes,
    TrackingCodes, or the billing ledger.
    Returns a dict matching CampaignAttributionOut.
    Raises HTTPException 404 if the campaign does not exist.
    """
```

No `_require_enabled()` call — attribution is a read operation and remains accessible even if the flag is toggled off (consistent with MKT-004's `get_campaign`).

**Steps:**

1. Fetch the marketing campaign. If missing → 404.
2. **Ad spend:** If `item.get("ad_campaign_id")` and `item.get("ad_account_id")` are both set:
   ```python
   from app.services.ad_campaigns import get_campaign as get_ad_campaign
   ad_row = get_ad_campaign(item["ad_account_id"], item["ad_campaign_id"])
   ad_spend_cents = int(ad_row.get("lifetime_spent_cents") or 0) if ad_row else 0
   ```
   If `ad_row` is `None` (the linked campaign was deleted externally), `ad_spend_cents = 0` and the absence is not an error — the link is stale.
3. **Promo redemptions:** Iterate `promo_code_ids = item.get("promo_code_ids") or []`. For each `code_id`:
   ```python
   from app.services.promo_codes import get_promo_stats
   stats = get_promo_stats(code_id)
   promo_discount_cents += stats["total_discount_cents"]
   promo_redemptions += stats["total_redemptions"]
   ```
   Best-effort: wrap each call in `try/except Exception` and skip if the promo code row has been deleted. Log a warning.
4. **Tracking counts:** If `item.get("tracking_code")` is set and `T.tracking_codes` is available (MKT-010):
   ```python
   from app.services import tracking_codes as tc_svc
   tc_row = tc_svc.get_tracking_code(item["tracking_code"])
   tracking_visits = int(tc_row.get("visit_count") or 0) if tc_row else 0
   tracking_orders = int(tc_row.get("order_count") or 0) if tc_row else 0
   ```
   If `tracking_codes` module does not exist yet (MKT-010 not landed), catch `ImportError` and zero-fill. This allows MKT-005 to land independently of MKT-010.
5. Assemble and return:
   ```python
   return {
       "campaign_id": campaign_id,
       "ad_spend_cents": ad_spend_cents,
       "promo_discount_cents": promo_discount_cents,
       "promo_redemptions": promo_redemptions,
       "tracking_visits": tracking_visits,
       "tracking_orders": tracking_orders,
       "as_of": now_ts(),
   }
   ```

## 5. Detailed Behavior & Edge Cases

### Linking a non-existent ads campaign

`attach_ad_campaign` queries `AdCampaigns.ByCampaignId` GSI and returns 404 if the GSI returns zero items. The GSI is defined in `scripts/local-ddb-init.py:1121` on the `AdCampaigns` table and is always present after `just restart`.

### Linking an ads campaign from a different owner's ad account

The `ByCampaignId` GSI lookup returns the `AdCampaigns` row regardless of `account_id` ownership. The check "does this ad account belong to `owner_id`?" is intentionally skipped in MKT-005: the marketing module treats ad campaigns as external references — an owner may legitimately attach a campaign from any ad account they control, and validating ad-account ownership here would require importing `app/services/ad_accounts.py:get_ad_account` and crossing module boundaries. This is recorded as an open question in Section 10. For now, any valid ads campaign by `campaign_id` can be attached.

### Double-attach (idempotent ad-campaign link)

Calling `attach_ad_campaign` twice with the same `ad_campaign_id` overwrites the field with the same value. The `updated_at` is refreshed on each call. This is safe — `SET ad_campaign_id = :same_value` is idempotent in DDB.

### Re-attaching a different ads campaign

`attach_ad_campaign` overwrites `ad_campaign_id` unconditionally. The previous link is lost. Callers who need to keep a history should detach first — this module does not maintain an audit trail of linked campaign changes (deferred to MKT-006's audit event on lifecycle transitions).

### `detach_ad_campaign` when no link exists

The `REMOVE ad_campaign_id, ad_account_id` expression is a no-op if those attributes are absent. DDB does not error on REMOVE for absent attributes. The `updated_at` is still refreshed.

### `attach_promo_code` — duplicate prevention

Step 4 checks the in-memory list before writing. This is a read-before-write, not an atomic conditional. A race condition where two concurrent `attach_promo_code` calls for the same `code_id` could both pass the duplicate check and append twice is theoretically possible. Because list_append on DDB Lists is last-writer-wins on the attribute, both could complete and produce duplicates. Mitigation: `compute_attribution` and `detach_promo_code` both deduplicate before acting — `compute_attribution` sums stats once per distinct `code_id`, and `detach_promo_code` filters all occurrences. This means duplicates are harmless for correctness but waste a promo-stats query. The attack surface is low (only the campaign owner can call attach).

### `get_promo_stats` 200-row cap

`app/services/promo_codes.py:466` passes `Limit=200` to the REDEEM# query. High-volume codes will under-report. `compute_attribution` does not paginate through all redemption rows — it calls `get_promo_stats` as-is and trusts its contract. The `as_of` timestamp in `CampaignAttributionOut` communicates the snapshot nature of the result. See Section 10 for the open question on whether MKT-005 should own a paginated alternative.

### Stale linked ads campaign

If the linked ads campaign is deleted externally (e.g., by an ad platform admin), `get_ad_campaign(account_id, campaign_id)` returns `None`. `compute_attribution` returns `ad_spend_cents=0` rather than 404 — the marketing campaign record remains valid even if its linked ads campaign disappears. A stale-link warning field (`ad_campaign_stale: bool`) could be added to `CampaignAttributionOut` in a follow-up.

### Tracking code stub (MKT-010 not landed)

`compute_attribution` wraps the tracking-code import in `try/except ImportError`. When MKT-010 lands, the import resolves normally and tracking counts are included. Before MKT-010, `tracking_visits=0` and `tracking_orders=0`. This fallback is safe because `CampaignAttributionOut.tracking_visits` defaults to `0`.

### Flag off — reads still work

`compute_attribution` does not call `_require_enabled()`. An attribution read on a pre-existing campaign when the flag is off returns the rollup from whatever data is already in place. This matches MKT-004's `get_campaign` pattern (reads never gated).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

The attach/detach and attribution functions touch only DDB tables (`T.marketing_campaigns`, `T.ad_campaigns`, `T.promo_codes`). These handles use the `_safe_table` abstraction from `app/core/tables.py:65` (VERIFIED), which points at DynamoDB Local in dev and real DynamoDB in prod. There is no `S.dev_mode` branch and no mock path — the code is identical in both environments (SECOPS-007 parity). This mirrors how `app/services/ad_campaigns.py` and `app/services/promo_codes.py` are written.

**Note:** `T.tracking_codes` does **not** exist in the current codebase (`app/core/tables.py` and `app/core/settings.py` have no `tracking_codes` handle — MKT-002 is not yet implemented, UNCONFIRMED). `compute_attribution` accesses tracking-code data only via a lazy import of `app/services/tracking_codes` (MKT-010 stub), not via `T.tracking_codes` directly, so this is not a blocking issue. `T.ad_campaigns` (VERIFIED: `app/core/tables.py:174,426`) and `T.promo_codes` (VERIFIED: `app/core/tables.py:196,448`) exist today.

### Idempotency

- `attach_ad_campaign`: idempotent — overwriting the same `ad_campaign_id` produces the same state.
- `detach_ad_campaign`: idempotent — REMOVE on an absent attribute is a no-op.
- `attach_promo_code`: idempotent for the same `code_id` (duplicate check in step 4). Concurrent duplicates may append twice but `compute_attribution` deduplicates.
- `detach_promo_code`: idempotent — filtering a non-present `code_id` from the list is a no-op.
- `compute_attribution`: pure read, no writes, always idempotent.

None of these functions accept an external idempotency key — the operations are inherently idempotent by design (set-membership semantics). No `sha256(correlation_id)` deterministic-id scheme is needed here because there is no new row creation (all writes are `update_item` on the existing campaign META row).

### Security

- **Ownership enforcement:** Every mutating function fetches the campaign row by `PK=OWNER#{owner_id}` before writing. A caller cannot modify another owner's campaign because the PK embeds the `owner_id`.
- **No write to external tables:** `attach_promo_code` only validates that the promo code exists (`get_promo_code` is a read). The `PromoCodes` row's `current_uses`, `active` flag, and other fields are untouched.
- **No billing writes:** `compute_attribution` is strictly read-only. It never calls `new_ledger_entry`, `settle_or_reverse_ledger`, or `refund_payment`.
- **CSRF:** All attach/detach endpoints are non-GET cookie-auth routes and are subject to the standard `x-csrf-token` header enforcement in `app/auth/deps.py:require_ui_session`. No special CSRF handling needed.
- **Attribution endpoint is GET (no CSRF needed):** `GET /campaigns/{campaign_id}/attribution` uses `Depends(require_ui_session)` but, being a GET, does not require the CSRF header per the CLAUDE.md auth spec.

## 8. Backward Compatibility & Migration

### No schema migration required

The `MarketingCampaigns` table is brand-new (MKT-002). All rows are written by MKT-004 and later. There are no existing rows with stale shapes to migrate.

### MKT-004 compatibility

MKT-004's `create_campaign` already stores `ad_campaign_id` and `promo_code_ids` if provided in `MarketingCampaignCreateIn`. MKT-005 adds separate attach/detach operations as a complement, not a replacement. Callers may still supply these fields at create time (MKT-004 path) or manage them post-creation via MKT-005's endpoints — both work.

The new `ad_account_id` attribute is only written by MKT-005's `attach_ad_campaign`. Campaigns created by MKT-004 that include `ad_campaign_id` directly (without going through `attach_ad_campaign`) will lack `ad_account_id`, making `compute_attribution`'s ad-spend lookup fall back to zero. This is acceptable for campaigns created before MKT-005 lands; a one-time backfill can be run post-deploy to resolve `ad_account_id` for those rows. This is recorded in Section 10.

### Existing ads / promo / billing code untouched

With `MARKETING_CAMPAIGNS_ENABLED=0` (the default), every mutating entry point in `marketing_campaigns.py` raises HTTP **403** before touching any table. The `AdCampaigns`, `PromoCodes`, and all billing tables are byte-for-byte unchanged — there are no new write paths into them from this module.

### Hermetic offline pytest (`tests/test_mkt_005_linkage_attribution.py`)

**Test cases:**

1. **Attach valid ads campaign**
   - Seed: create a marketing campaign row via direct `put_item`; create an ad-campaigns row with a known `campaign_id` and `account_id`.
   - Call `attach_ad_campaign(owner, mkt_camp_id, ad_camp_id)`.

   - Call `attach_ad_campaign(owner, mkt_camp_id, "nonexistent")`.

   - Seed: marketing campaign with `ad_campaign_id` set.
   - Call `detach_ad_campaign(owner, mkt_camp_id)`.
   - Assert: `ad_campaign_id` and `ad_account_id` absent from row; `updated_at` refreshed.

4. **Detach ads campaign — no link (idempotent)**
   - Seed: marketing campaign with no `ad_campaign_id`.
   - Call `detach_ad_campaign(owner, mkt_camp_id)` — must not raise.
   - Assert: row unchanged except `updated_at`.

5. **Attach promo code — first attach**
   - Seed: promo code row in `PromoCodes` (`pk=PROMO#pc_xxx`, `sk=META`).
   - Call `attach_promo_code(owner, mkt_camp_id, "pc_xxx")`.
   - Assert: `promo_code_ids = ["pc_xxx"]`; promo META row `current_uses` unchanged.

6. **Attach promo code — idempotent (already in list)**
   - Seed: campaign with `promo_code_ids=["pc_xxx"]`.
   - Call `attach_promo_code(owner, mkt_camp_id, "pc_xxx")`.
   - Assert: `promo_code_ids = ["pc_xxx"]` (no duplicate).

7. **Attach promo code — non-existent code → 404**
   - Call `attach_promo_code(owner, mkt_camp_id, "pc_gone")`.
   - Assert: raises `HTTPException(status_code=404)`.

8. **Detach promo code — present**
   - Seed: `promo_code_ids=["pc_aaa", "pc_bbb"]`.
   - Call `detach_promo_code(owner, mkt_camp_id, "pc_aaa")`.
   - Assert: `promo_code_ids = ["pc_bbb"]`; PromoCodes untouched.

9. **Detach promo code — not in list (idempotent)**
   - Seed: `promo_code_ids=["pc_bbb"]`.
   - Call `detach_promo_code(owner, mkt_camp_id, "pc_other")` — must not raise.
   - Assert: `promo_code_ids = ["pc_bbb"]` unchanged.

10. **`compute_attribution` — full rollup**
    - Seed: marketing campaign with `ad_campaign_id=X`, `ad_account_id=A`, `promo_code_ids=["pc_1","pc_2"]`.
    - Seed `AdCampaigns` row: `lifetime_spent_cents=50000`.
    - Seed `PromoCodes` META rows + REDEEM# rows:
      - `pc_1`: 3 redeems, `discount_applied_cents` summing to 900.
      - `pc_2`: 1 redeem, `discount_applied_cents` = 500.
    - Call `compute_attribution(owner, mkt_camp_id)`.
    - Assert: `ad_spend_cents=50000`, `promo_discount_cents=1400`, `promo_redemptions=4`, `tracking_visits=0`, `tracking_orders=0` (MKT-010 not present), `as_of > 0`.
    - Assert: no write occurred to `AdCampaigns` or `PromoCodes` (verify row `lifetime_spent_cents` and `current_uses` unchanged).

11. **`compute_attribution` — stale ads campaign link**
    - Seed: marketing campaign with `ad_campaign_id=Y`, `ad_account_id=A` but NO `AdCampaigns` row for `(A, Y)`.
    - Assert: returns `ad_spend_cents=0` without raising.

12. **Flag off — mutating calls rejected**
    - `object.__setattr__(S, "marketing_campaigns_enabled", False)`.
    - Assert all five mutating functions raise `HTTPException(status_code=403)` (MKT-004 spec:194).
    - Assert `compute_attribution` returns normally (reads unaffected).

13. **Cross-owner access rejected**
    - Seed campaign owned by `owner_a`.
    - Call `attach_ad_campaign("owner_b", mkt_camp_id, ...)`.
    - Assert raises `HTTPException(status_code=404)` (PK lookup returns nothing for `OWNER#owner_b`).

## 10. Open Questions / Assumptions

1. **Ad-account ownership validation (assumed skipped for MKT-005):** The current design allows attaching any valid ads campaign by `campaign_id` without checking that the ad account belongs to `owner_id`. If cross-account attachment should be blocked, `attach_ad_campaign` must also call `ad_accounts.get_ad_account(account_id)` and compare `acct["owner_sub"]` with `owner_id`. Decision deferred; implementing this would require importing `app/services/ad_accounts.py` and adds one extra DDB read per attach call.

2. **`get_promo_stats` 200-row cap:** Attribution for campaigns with > 200 promo redemptions will under-report. Options: (a) MKT-005 implements a paginated replacement in `promo_codes.py` (additive, no change to existing `get_promo_stats` signature); (b) accept the cap as a known limitation with a `partial: bool` field on `CampaignAttributionOut`. Assumed: accept the cap for MKT-005, surface as a follow-up.

3. **`ad_account_id` backfill for MKT-004 rows:** Marketing campaigns created by MKT-004 that included `ad_campaign_id` directly will not have `ad_account_id`, so `compute_attribution` returns `ad_spend_cents=0` for them. A one-time backfill script resolving `ad_account_id` from the `ByCampaignId` GSI can be run post-deploy. Assumed: no automated migration in this ticket; backfill is manual and optional.

4. **Concurrent `attach_promo_code` race:** As described in Section 5, two concurrent attaches of the same `code_id` could produce a duplicate in the list. Assumed: harmless for correctness given `compute_attribution` deduplicates, and the campaign owner is the only caller. If stricter guarantees are required, a `ConditionExpression` checking `not contains(promo_code_ids, :code_id)` can be added, but DDB's `contains` function on list types is not supported in `ConditionExpression` as of this writing — an atomic check would require a DDB transaction. Deferred.

5. **`compute_attribution` caching:** For campaigns with many promo codes, the rollup may be slow (N sequential DDB queries). Assumed: caching deferred to a follow-up (e.g., write the rollup to a `ATTR#{campaign_id}` row with a TTL).

6. **MKT-010 tracking-code import guard:** `compute_attribution` catches `ImportError` to handle the case where `tracking_codes.py` does not yet exist. This is a temporary coupling smell. Once MKT-010 lands the `try/except ImportError` block should be removed and replaced with a direct import.

7. **`spent_today_cents` in attribution:** The ticket description references `spent_today_cents` alongside `lifetime_spent_cents` in the rollup. The spec includes only `lifetime_spent_cents` as the primary spend figure (it is the accumulating total). Whether `spent_today_cents` should be exposed as a separate `ad_spend_today_cents` field on `CampaignAttributionOut` is deferred to feedback on MKT-003's model definition.
