# POS-006 — Cash tender, change calc & cash ledger entry

## 1. Summary & Goal

POS-006 completes the cash-payment leg of an in-person sale. A cashier presents a
running cart (built by POS-005 via `shoppingcart.add_item`) to a customer, collects
banknotes, and presses "Tender Cash". This ticket delivers:

1. `app/services/pos_tender.py` — the `tender_cash(session_id, txn_id, amount_tendered_cents, *, idempotency_key)` function that validates the tendered amount, records an immutable `TENDER#...` row in the `pos` table, calls `purchase_cart` to settle the bound cart (creating one order and decrementing stock exactly once via the existing SHOP-001 path), and writes one `pos_cash_sale` ledger entry to `T.billing` via `billing_shared.new_ledger_entry`.
2. `app/routers/pos_tender.py` — a single `POST /ui/pos/sessions/{session_id}/transactions/{txn_id}/tender-cash` endpoint, flag-gated under `S.pos_enabled`.
3. The running cash-float counters on the `SESSION#{session_id}/META` row are updated (`cash_in_cents`, `change_out_cents`) so that POS-004's `close_session` can compute `expected_cash_cents` correctly.

POS is a sales *channel*, not a new commerce engine. This ticket writes zero new
cart/order/inventory/billing math. Every existing byte in those stacks is unchanged
when `POS_ENABLED=false`.

### 2.5 Tender row idempotency

The tender row at `SESSION#{session_id}/TENDER#{txn_id}` is written with
`ConditionExpression="attribute_not_exists(pos_pk)"` — a pattern established by
`app/services/inventory.py:242–245` and `app/services/refund_requests.py:160–162`.  <!-- verified: inventory.py:242, refund_requests.py:160–162 -->
A replayed call that hits the `ConditionalCheckFailedException` reads back the
existing tender row and returns idempotently (same `order_id`, same
`change_due_cents`), rather than raising an error.

The `txn_id` uniquely identifies the tender attempt within a session. The caller
(POS-005 cart-binding service) owns `txn_id` generation; this ticket treats it as
opaque and uses it as the row discriminator.

### 2.6 Session float counters

`close_session` in `app/services/pos_register.py` (POS-004) computes:

```
expected_cash_cents = opening_float_cents + cash_in_cents − change_out_cents
```

where `cash_in_cents` and `change_out_cents` are accumulated on the session row.
POS-006 must atomically increment both counters after a successful cash tender using
`update_item` with `ADD` (atomic increment), not a read-then-write.

## 3. Data Model

POS-006 reads the pre-existing `pos` table (owned by POS-003) and the `billing`
table (`T.billing`, PK `pk`, SK `sk` — `scripts/local-ddb-init.py:67–77`). No new
tables are introduced.

### 3.1 Tender row (new, written by POS-006)

```
pos_pk = "SESSION#{session_id}"
pos_sk = "TENDER#{txn_id}"
```

| Attribute | DDB type | Description |
|---|---|---|
| `pos_pk` | S | `"SESSION#{session_id}"` |
| `pos_sk` | S | `"TENDER#{txn_id}"` |
| `txn_id` | S | POS transaction identifier (from POS-005 TXN row) |
| `session_id` | S | Parent register session |
| `cashier_sub` | S | `user_sub` from the authenticated session |
| `kind` | S | `"cash"` (this ticket; `"card"` / `"wallet"` added in POS-007) |
| `amount_tendered_cents` | N | Banknotes the customer handed over |
| `total_cents` | N | Transaction total at time of tender (snapshot) |
| `change_due_cents` | N | `amount_tendered_cents − total_cents` (≥ 0) |
| `order_id` | S | Order id returned by `purchase_cart` |
| `ledger_sk` | S | SK of the billing ledger entry (for cross-reference / void in POS-008) |
| `idempotency_key` | S | Caller-supplied; sha256 is used as deterministic tender row discriminator |
| `status` | S | `"settled"` |
| `created_at` | N | `now_ts()` — **sort key for `GSI_SESSION_TXN`** |

`GSI_SESSION_TXN` (`partition_key=session_id`, `sort_key=created_at`) was declared
in POS-003's `TableDef` with `attr_types={"created_at": "N"}`. Tender rows
automatically appear in this GSI because they carry `session_id` and `created_at`
as top-level attributes.

### 3.2 Transaction row update (POS-005 row, mutated by POS-006)

```
pos_pk = "TXN#{txn_id}"
pos_sk = "META"
```

After `purchase_cart` succeeds, POS-006 updates the transaction row:

```
SET #status = :status, order_id = :order_id, settled_at = :now,
    ledger_sk = :ledger_sk, subtotal_cents = :subtotal_cents,
    tax_cents = :tax_cents, discount_cents = :discount_cents,
    total_cents = :total_cents
```

with `ConditionExpression="#status = :draft"` to guard against double-settlement.
`ConditionalCheckFailedException` → read back and return idempotently (same as the
cart's own replay path).

Fields written:

| Attribute | Value |
|---|---|
| `status` | `"settled"` |
| `order_id` | Order id from `purchase_cart` result |
| `settled_at` | `now_ts()` |
| `ledger_sk` | SK of the billing ledger entry |
| `subtotal_cents` | `cart_total_cents(cashier_sub, cart_id)` — canonical sum of line totals |
| `tax_cents` | `int(subtotal_cents * S.pos_default_tax_rate_bps / 10000)` — 0 when flag is 0 |
| `discount_cents` | `0` (POS-006 scope; coupon/promo discounts are a follow-up) |
| `total_cents` | `subtotal_cents + tax_cents − discount_cents` |

`tax_cents` and `discount_cents` are written here so that POS-009 (receipt generation)
can render the tax and discount lines from the TXN row without recomputing them.
`S.pos_default_tax_rate_bps` is defined by POS-003 §6.1 (default `0`, i.e., no tax
until the operator sets `POS_DEFAULT_TAX_RATE_BPS`).

### 3.3 Session row update (accumulate float counters)

```
pos_pk = "SESSION#{session_id}"
pos_sk = "META"
```

Atomic update after tender row is written:

```
ADD cash_in_cents :amount_tendered, change_out_cents :change_due
```

`ADD` is DynamoDB's atomic increment; no read-then-write is needed.

### 3.4 Billing ledger entry (written to `T.billing`)

Reuses the existing `billing` table (PK `pk`, SK `sk`).  <!-- verified: local-ddb-init.py:67–77 -->
Key attributes:

| Attribute | Value |
|---|---|
| `pk` | `user_pk(cashier_sub)` = `"USER#{cashier_sub}"` |
| `sk` | `ledger_sk(ts, entry_id)` = `"LEDGER#{ts}#{entry_id}"` |
| `entry_id` | `ulidish()` from `billing_shared.py:216` |
| `type` | `"credit"` |
| `amount_cents` | `total_cents` (the transaction total, not the tendered amount) |
| `state` | `"settled"` |
| `reason` | `"pos_cash_sale"` |
| `provider` | `"pos_cash"` (FIN-013 / GAP-0203 attribution) |
| `ledger_date` | UTC date string, derived automatically |
| `meta` | `{"session_id": ..., "txn_id": ..., "order_id": ..., "idempotency_key": ...}` |

No new GSIs needed — the existing `GSI_LEDGER_DATE` on `T.billing` (`scripts/
local-ddb-init.py:71–75`) indexes by `ledger_date` (PK `ledger_date` S, SK `sk`);
`reason="pos_cash_sale"` lets the platform financial dashboard filter POS cash entries
out of the provider breakdown.  <!-- verified: local-ddb-init.py:72–74 -->

## 4. API / Service Design

### 4.1 Service layer — `app/services/pos_tender.py`

```python
from __future__ import annotations

import hashlib
from typing import Any, Dict

from botocore.exceptions import ClientError
from fastapi import HTTPException

from app.core.settings import S
from app.core.tables import T
from app.core.time import now_ts
from app.services import billing_shared
from app.services import shoppingcart


def _flag_on() -> bool:
    return bool(getattr(S, "pos_enabled", False))


def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="POS is not enabled")


def _audit(event: str, user_sub: str, **fields: Any) -> None:
    """Fire-and-forget audit event; mirrors pos_register._audit."""
    try:
        from app.services.alerts import audit_event
        audit_event(event, user_sub, None, **fields)
    except Exception:
        pass


def tender_cash(
    session_id: str,
    txn_id: str,
    cashier_sub: str,
    amount_tendered_cents: int,
    *,
    idempotency_key: str,
) -> Dict[str, Any]:
    """Record a cash tender, purchase the bound cart, and write the ledger entry.

    Returns:
        {
            "txn_id": str,
            "session_id": str,
            "order_id": str,
            "total_cents": int,
            "amount_tendered_cents": int,
            "change_due_cents": int,
            "ledger_sk": str,
            "status": "settled",
        }

    Raises:
        HTTPException(404)  if POS_ENABLED is off
        HTTPException(422)  if amount_tendered_cents < total_cents
        HTTPException(404)  if session or transaction row not found
        HTTPException(409)  if transaction already settled (non-replay)
    """
    _require_enabled()
    ...
```

**Key invariants in `tender_cash`**:

1. **Load and validate the transaction draft**: Read `TXN#{txn_id}/META` from
   `T.pos`. If not found → 404. If `status != "draft"` and `status == "settled"`,
   check for idempotent replay (same `idempotency_key` on the row) → return
   existing result. If `status == "settled"` with a *different* idempotency key →
   409 ("Transaction already settled"). Statuses `"voided"` or `"refunded"` (POS-008)
   → 409 ("Transaction is voided/refunded").

2. **Validate tender amount**: `if amount_tendered_cents < total_cents: raise HTTPException(422, "Amount tendered is less than total")`. No order, no ledger, no stock decrement is written.

3. **Compute change**: `change_due_cents = amount_tendered_cents - total_cents`.

4. **Write tender row with idempotency guard**:
   ```python
   tender_row = {
       "pos_pk": f"SESSION#{session_id}",
       "pos_sk": f"TENDER#{txn_id}",
       ...
       "idempotency_key": idempotency_key,
   }
   try:
       T.pos.put_item(
           Item=tender_row,
           ConditionExpression="attribute_not_exists(pos_pk)",
       )
   except ClientError as exc:
       if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
           # Replay: read back existing row and return idempotently
           existing = T.pos.get_item(
               Key={"pos_pk": f"SESSION#{session_id}", "pos_sk": f"TENDER#{txn_id}"}
           ).get("Item")
           if existing:
               return _tender_out(existing)
           raise HTTPException(409, "Tender row collision")
       raise
   ```

5. **Call `purchase_cart`**: `shoppingcart.purchase_cart(cashier_sub, cart_id, idempotency_key=idempotency_key)`. This call handles its own idempotent replay (returns the same `order_id` on a re-run against an already-purchased cart). `cart_id` is read from the `TXN#{txn_id}/META` row. **`purchase_cart` has no `metadata` parameter** (`shoppingcart.py:474–481`); POS traceability fields (`pos_session_id`, `pos_txn_id`) are stored on the POS tender/transaction rows, not injected into the order metadata.

6. **Write billing ledger entry**:
   ```python
   led_sk, led_item = billing_shared.new_ledger_entry(
       key_name="pk",
       key_value=billing_shared.user_pk(cashier_sub),
       entry_type="credit",
       amount_cents=total_cents,
       state="settled",
       reason="pos_cash_sale",
       meta={"session_id": session_id, "txn_id": txn_id,
             "order_id": order_id, "idempotency_key": idempotency_key},
       extra={"provider": "pos_cash"},
   )
   T.billing.put_item(Item=led_item)
   ```

7. **Compute settlement totals** and **update transaction row** (mark settled):
   ```python
   subtotal = shoppingcart.cart_total_cents(cashier_sub, cart_id)
   tax      = int(subtotal * getattr(S, "pos_default_tax_rate_bps", 0) / 10000)
   discount = 0  # coupon/promo discounts are a follow-up
   total    = subtotal + tax - discount

   T.pos.update_item(
       Key={"pos_pk": f"TXN#{txn_id}", "pos_sk": "META"},
       UpdateExpression=(
           "SET #status = :s, order_id = :oid, settled_at = :t, ledger_sk = :lsk, "
           "subtotal_cents = :sub, tax_cents = :tax, discount_cents = :disc, total_cents = :tot"
       ),
       ExpressionAttributeNames={"#status": "status"},
       ExpressionAttributeValues={
           ":s": "settled", ":oid": order_id,
           ":t": now_ts(), ":lsk": led_sk,
           ":sub": subtotal, ":tax": tax, ":disc": discount, ":tot": total,
           ":draft": "draft",
       },
       ConditionExpression="#status = :draft",
   )
   ```
   `ConditionalCheckFailedException` here means a concurrent tender already
   settled the transaction (concurrent race between two terminals). Read back and
   return idempotently if the settled `idempotency_key` matches; otherwise 409.

8. **Atomically accumulate session float counters**:
   ```python
   T.pos.update_item(
       Key={"pos_pk": f"SESSION#{session_id}", "pos_sk": "META"},
       UpdateExpression="ADD cash_in_cents :amount, change_out_cents :change",
       ExpressionAttributeValues={":amount": amount_tendered_cents, ":change": change_due_cents},
   )
   ```
   No condition needed — `ADD` initialises from zero if the attribute is absent.

9. **Audit event** (fire-and-forget):
   ```python
   _audit("pos_cash_tender", cashier_sub,
          session_id=session_id, txn_id=txn_id, order_id=order_id,
          total_cents=total_cents, change_due_cents=change_due_cents)
   ```

**Order of writes** (resilience reasoning):

- Tender row written first (idempotency guard). If the process dies after this
  point, the caller can replay to resume.
- `purchase_cart` second — its own conditional update on the cart is the stock/order
  idempotency barrier. If it raises, the tender row is orphaned but harmless (no
  ledger, no order); a void call in POS-008 will clean it up.
- Ledger entry third — if this fails, the order exists but no ledger row exists. A
  compensating background reconciler (out of scope for POS-006) can detect this
  gap via the POS transaction row's `ledger_sk = None` sentinel.
- TXN status update fourth — if this fails, the transaction row stays `"draft"` but
  the `purchase_cart` early-return path means a replay will recover the same
  `order_id` and re-attempt the ledger write (idempotent because `new_ledger_entry`
  generates a fresh `ulidish` — see Section 5.3 for idempotency discussion).
- Session float counters last — they are non-critical for the tender itself and only
  matter for `close_session` cash reconciliation.

## 5. Detailed Behavior & Edge Cases

### 5.1 Under-tender: amount_tendered_cents < total_cents

Validation occurs in `tender_cash` before any DDB write:

```python
if amount_tendered_cents < txn["total_cents"]:
    raise HTTPException(
        status_code=422,
        detail=f"Amount tendered ({amount_tendered_cents}¢) is less than total ({txn['total_cents']}¢)"
    )
```

No tender row, no order, no ledger entry is written. This is a clean, zero-side-
effect rejection. The cart remains `OPEN`, the transaction remains `"draft"`, and
the cashier can attempt a new tender with a corrected amount.

### 5.2 Exact-cash tender (change_due_cents = 0)

`change_due_cents = amount_tendered_cents - total_cents = 0`. This is valid. The
tender row is written with `change_due_cents=0`. The session `change_out_cents`
counter is incremented by 0 (a no-op for DynamoDB ADD but correct).

### 5.3 Idempotent replay (same idempotency_key, same txn_id)

The `conditional_put` on the tender row will raise
`ConditionalCheckFailedException`. The handler reads back the existing tender row,
derives the same `_tender_out` dict, and returns HTTP 200 with the same payload.
No second `purchase_cart` call, no second ledger entry.

This replay path is safe because:
- The cart is already `PURCHASED` → `purchase_cart` would early-return the same
  `order_id` anyway (`shoppingcart.py:483–492`).
- The ledger entry `led_sk` is stored on the tender row and returned to the caller,
  enabling the client to correlate without a second write.

### 5.4 Session not found or session already closed

`tender_cash` reads the session row (`SESSION#{session_id}/META`) and validates:
- Row missing → `HTTPException(404, "Session not found")`.
- `status == "closed"` → `HTTPException(409, "Session is already closed")`.
- `status == "open"` and `register_id` mismatch is not enforced here (session is looked
  up by `session_id` alone; the cashier ownership check below is sufficient).

### 5.5 Cashier ownership check

After loading the transaction row, `tender_cash` asserts
`txn["cashier_sub"] == cashier_sub`. A mismatch → `HTTPException(403, "Not your
transaction")`. This prevents one cashier from settling another cashier's draft.

### 5.6 Stock out during purchase_cart

If `purchase_cart` raises `HTTPException(409, "Item '...' is out of stock")`, the
tender row has already been written. The tender row's `status` field is not yet
`"settled"` (the TXN row update happens *after* `purchase_cart` succeeds). The
`409` propagates to the caller. The cashier removes the out-of-stock item from the
cart (POS-005 remove-item endpoint) and re-tenders. On re-tender with the *same*
idempotency key, the `conditional_put` on the tender row will hit the
`ConditionalCheckFailedException` path — but since the tender row has no `order_id`
yet, the handler must distinguish this "stranded tender" case:

- Read back the existing tender row.
- If `order_id` is absent (empty string or key missing), delete the stranded tender
  row and allow the new tender to proceed (write a fresh tender row).
- If `order_id` is present, return idempotently.

This recovery behaviour is handled in the `ConditionalCheckFailedException` branch
by checking `existing.get("order_id")`.

### 5.7 Concurrent double-tender (race)

Two terminals tender the same `txn_id` concurrently. The first one writes the
tender row (wins the conditional put). The second one loses the `conditional_put`
and enters the replay path. If the first terminal's `purchase_cart` has not yet
updated the cart, the second terminal's `purchase_cart` call will block on the
cart's own conditional update — and one of them will get the early-return path.
The net result is exactly one order and one ledger entry regardless of the race.

### 5.8 currency

All amounts are integer cents. The currency is inherited from the session's register
configuration (`default_currency`, stored on `REGISTER#{register_id}/META`). For
POS-006, the ledger entry uses the same currency as the cart. The billing table ledger
entry does not carry a separate `currency` column — it is carried in the cart's own
`currency` field and denormalized into the `meta` map if needed.

### 5.9 Zero-total transaction

A transaction with `total_cents = 0` (all items comped or promo-discounted to zero)
is valid. Any `amount_tendered_cents >= 0` passes validation. Change is
`amount_tendered_cents`. The ledger entry is written with `amount_cents=0` — this is
valid per `new_ledger_entry` (no floor check at `billing_shared.py:224`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

`pos_tender.py` contains no `if S.dev_mode` branch. The same code path runs in both
environments. The DynamoDB calls go to DynamoDB Local in dev and real AWS DynamoDB
in prod — both speak the same API. The billing ledger entry uses `T.billing` (always
`_FloatSafeTable`-wrapped, `app/core/tables.py:65`). No mock/real fork is introduced
(SECOPS-007 parity).

### 7.2 Deterministic idempotency

The caller supplies an `idempotency_key` (required, min 8 chars). The tender row's
conditional put gates on `attribute_not_exists(pos_pk)` — a single atomic write, no
read-then-write race. The `purchase_cart` call uses its own internal idempotency
guard (cart status conditional update). The billing ledger entry is not itself
idempotent (each call to `new_ledger_entry` generates a fresh `ulidish()`), but the
tender row's `ledger_sk` field stores the winning entry's SK — a second `tender_cash`
call with the same idempotency key will hit the conditional-put replay path and
return the stored `ledger_sk`, never writing a second ledger entry.

### 7.3 CSRF

The endpoint uses `require_ui_session` (`app/services/sessions.py`). POST requests
from the browser carry the `x-csrf-token` header (set by `api/client.ts`). Bearer-
auth requests (API clients / E2E tests) bypass CSRF — same as all other `require_ui_session` endpoints.

### 7.4 Cashier ownership enforcement

`tender_cash` checks `txn["cashier_sub"] == cashier_sub` — a direct DDB row
ownership check — before writing anything. This prevents cross-cashier settlement.
Session ownership (`session["cashier_sub"] == cashier_sub`) is enforced by POS-004's
`get_open_session` check that is called by the router before dispatching to
`tender_cash`.

### 7.5 Sensitive data

No PAN, card number, or payment credential is handled in this ticket. `"pos_cash"`
is the only provider value written to the ledger. The `idempotency_key` is a caller-
generated opaque string (e.g., UUID); it is stored in the tender row and the ledger
`meta` but is not a secret.

## 8. Backward Compatibility & Migration

### 8.1 Existing tables: zero changes

No column, GSI, or access pattern is added to `shopping_cart`, `billing`, `orders`,
`catalog`, or any other existing table. The `billing` table receives new ledger rows
with `reason="pos_cash_sale"` and `provider="pos_cash"` — these are entirely additive
to the existing row set and are invisible to all existing billing queries (which
filter by `pk = USER#{user_sub}` and do not exclude by `reason`).

The `_provider_for` helper in `app/services/platform_financial_dashboard.py` already
handles unknown `provider` values by bucketing them as `"unknown"` (CLAUDE.md billing
gotcha, FIN-013). With `provider="pos_cash"`, these entries will appear in a new
`"pos_cash"` bucket in the provider breakdown. No existing provider bucket is
affected.

If the platform financial dashboard is to aggregate POS cash sales in a dedicated
UI, a display-name mapping for `"pos_cash"` should be added in a follow-up to that
service — but this is not a correctness concern for POS-006.

### 8.3 DynamoDB table recreation

The `pos` table was created by POS-003. No new GSIs or attribute definitions are
added by POS-006. A `just restart` cycle is not required after deploying POS-006
unless the `pos` table does not yet exist (i.e., POS-003 has not been run).

### 8.4 `source_system` restriction

`commerce_order_service.create_order` rejects `source_system` values outside
`{"shopping_cart", "commercial_direct", "subscription_cycle"}` (`:58`). POS calls
`purchase_cart`, which internally uses `source_system="shopping_cart"` (`:583`).
No change to this validation — POS-006 does not require a new `"pos"` channel value.

## 10. Open Questions / Assumptions

1. **`source_system` in orders**: POS-006 uses `source_system="shopping_cart"` to
   avoid breaking the allowlist in `commerce_order_service.py:58`. This means POS
   orders are indistinguishable from regular web-cart orders in the orders table
   unless the caller inspects `metadata.pos_txn_id`. **Assumption**: this is
   acceptable for POS-006; a dedicated `"pos"` channel value (requiring a one-line
   change to the allowlist) is a POS-009 follow-up if reporting requires it.

2. **Balance delta on cashier billing account**: The spec writes a `credit` ledger
   entry attributed to `cashier_sub` and calls `apply_balance_delta` (`billing_shared.py:83`)
   to increment `owed_settled_cents`. **Assumption**: the till's Z-report will reconcile
   this balance. If the cashier is not a billing user (no `BILLING` row),
   `apply_balance_delta` will create it via `ensure_balance_row` (`billing_shared.py:69`)
   automatically (it is called first inside `apply_balance_delta`).
   This must be called explicitly in `tender_cash` after the ledger `put_item`.
   <!-- CORRECTED: spec previously said "ensure_balance_row at billing.py:786" —
        ensure_balance_row is at billing_shared.py:69, not billing.py:786;
        billing.py:786 is inside set_default_pm() -->

3. **`purchase_cart` `user_sub`**: POS-006 passes `cashier_sub` as `user_sub` to
   `purchase_cart`, meaning the cart is owned by the cashier. **Assumption**: POS-005
   already creates the cart under `cashier_sub`. If the cart is owned by a different
   subject (e.g., a customer-facing kiosk sub), `purchase_cart` will 404. This needs
   to be confirmed against POS-005's cart-binding model.

4. **Currency**: The ledger entry uses the cart's currency. **Assumption**: POS
   only handles single-currency transactions per session. Multi-currency tendering is
   out of scope.

5. **Ledger entry duplicate on process crash**: If the process dies after
   `T.billing.put_item(Item=led_item)` but before the TXN row `update_item`, a
   replay will write a second ledger entry (different `ulidish`). **Assumption**: the
   stranded first entry is treated as a reconciliation concern and is addressed in
   POS-010 or a future X/Z report. Preventing it would require a distributed
   transaction, which is out of scope.

6. **`amount_tendered_cents` minimum**: The validator uses `ge=1`. A tender of 0¢
   is rejected by the Pydantic model. But if `total_cents=0`, the minimum valid
   tender is 0¢. **Assumption**: update the validator to `ge=0` to handle zero-total
   transactions (Section 5.9). The 422 guard `amount_tendered_cents < total_cents`
   still rejects any negative tender.

7. **POS router registration**: The spec proposes always-include with
   `_require_enabled()` guards, matching `returns_rma_router`. An alternative is
   `if S.pos_enabled: app.include_router(...)`. **Assumption**: the always-include
   pattern is preferred (consistent with returns and inventory).
