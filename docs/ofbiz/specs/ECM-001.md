# ECM-001 — Store-integration scoping spike & integration-surface map

**Type:** Spike | **Priority:** P0 | **Estimate:** 3 days

---

## 1. Summary & Goal

ECM-001 is a pure design artifact: it produces no new runtime code, no new tables, and no flag changes. Its output is this document plus a dependency matrix that every later ECM ticket refers back to. The goal is to enumerate every storefront touchpoint that must evolve to surface the ERP depth planned in the upstream milestones (variants, live inventory, pricing rules, order lifecycle, shipping), specify exactly how each touchpoint consumes an upstream module read-only, and confirm the off-flag fallback contract that guarantees zero regressions when all five integration flags are off.

The deliverable answers three questions for each integration point:

1. What does the current storefront code do today (line reference)?
2. Which upstream ticket/service replaces or enriches that behavior when its flag is on?
3. What is the exact byte-for-byte fallback when the flag is off?

## 2. Context & Current State

The storefront is implemented across four layers. Every claim here is verified against the codebase.

### 2.1 Catalog browse — scalar stock badges

`app/routers/catalog.py:94–127` defines `_compute_stock_status(item)` and `_catalog_item_out(item)`. Both functions read `item["stock_count"]` (a scalar integer stored directly on the catalog item in `T.catalog`, keyed `CAT#{category_id}` / `ITEM#{item_id}`). The three states emitted are `unlimited`, `in_stock`, `low_stock`, and `out_of_stock`. `CatalogItemOut` (`app/models.py:672–688`) carries `stock_count: Optional[int]`, `stock_status: str`, and `low_stock_threshold: int` as flat scalars — no variant dimension, no per-location breakdown.

`frontend/src/pages/shop/Catalog.tsx:180–193` renders exactly these two badges against `item.stock_status`. No variant selector, no real-time availability call.

### 2.2 Product detail — scalar add-to-cart

`frontend/src/pages/shop/ProductDetail.tsx:83–108` (`addToCartMutation`) sends `{ sku: item.item_id, name, quantity, unit_price_cents: item.price_cents, image_url, category_id, item_id }` — a scalar SKU equal to the catalog `item_id`. There is no concept of a variant SKU, option selection, or per-variant price delta at this layer today.

### 2.3 Cart item add — scalar stock decrement at purchase

`app/services/shoppingcart.py:311–367` (`add_item`) accepts `sku`, `unit_price_cents`, `quantity` as scalars. No reservation is created at add-time; stock is only checked at purchase.

`app/services/shoppingcart.py:498–538` (`purchase_cart`, stock block) performs a conditional `update_item` with `ConditionExpression="stock_count >= :qty"` directly against `T.catalog` at purchase time. A failed condition triggers manual rollback of all prior decrements in the same `purchase_cart` call (`shoppingcart.py:524–532`). This is the current oversell guard — it has no reservation TTL, no per-location awareness, and no integration with the first-class inventory table `T.inventory` that OFB-003 introduces.

### 2.4 Cart total — flat sum with optional promo

`app/routers/shoppingcart.py:169–172` (`ui_cart_total`) returns `cart_total_cents(user_sub, cart_id)` from `app/services/shoppingcart.py:301–303`, which sums `line_total_cents` across all cart items. No pricing-rule engine is consulted; the only discount path is `promo_codes.validate_promo_code` called later inside `purchase_cart` (`shoppingcart.py:545–576`, SHOP-002 block). The promo model supports `percentage`, `fixed_amount`, and `free_trial` discount types (`app/services/promo_codes.py:26`, `_calculate_discount` at `:376`) but has no concept of tiered/bulk/conditional rules.

`ShoppingCartTotalOut` (`app/models.py:982–985`) carries only `cart_id`, `total_cents`, `currency` — no breakdown of applied rules.

### 2.5 Checkout — purchase and order creation

`frontend/src/pages/shop/Checkout.tsx:133–138` calls `purchaseCart(cartId, ...)` which hits `POST /ui/shoppingcart/carts/{cart_id}/purchase`. The router (`shoppingcart.py:175–186`) requires an `X-Idempotency-Key` header. `purchase_cart` uses `_cart_purchase_idempotency_key(user_sub, cart_id)` (`shoppingcart.py:194–195`) as the canonical key for the order `correlation_id` passed to `commerce_order_service.create_order_from_line_items` (`shoppingcart.py:581–594`). The order header is written to `T.orders` with `status="pending_payment"` and no `lifecycle_status` field (`commerce_order_service.py:72–84`).

### 2.6 Existing flag infrastructure

`app/core/settings.py:839–847` already defines `inventory_reservations_enabled` (default `false`), `inventory_table_name`, `reservations_table_name`, and `returns_rma_enabled`. The pattern for a new flag is: a `bool` field on the frozen `Settings` dataclass reading from an env var with a `false`/`"0"` default. `app/services/inventory.py:50–56` shows the canonical gate helper — `_flag_on()` reads `S.inventory_reservations_enabled`; `_require_enabled()` raises HTTP 404 when off.

None of the five integration flags named in the ticket (`STORE_INTEGRATION_ENABLED`, `PRODUCT_DEPTH_ENABLED`, `INVENTORY_RESERVATIONS_ENABLED` — already exists, `PRICING_RULES_ENABLED`, `ORDER_LIFECYCLE_ENABLED`, `SHIPPING_ENABLED`) currently gating storefront behavior. `INVENTORY_RESERVATIONS_ENABLED` is the only one present.

### 2.7 Upstream modules already wired

`app/services/inventory.py` exists and implements `get_inventory`, `set_on_hand`, `adjust`, `reserve`, `commit_reservation`, `release_reservation`. It is gated by `_flag_on()` (`inventory.py:50–51`) → `S.inventory_reservations_enabled`. `T.inventory` and `T.reservations` are declared in the `Tables` dataclass at `app/core/tables.py:317–318` and instantiated at `app/core/tables.py:569–570` (via `S.inventory_table_name` / `S.reservations_table_name`). The `shoppingcart.py` purchase path does not yet call any of these functions — OFB-004 is the ticket that wires the reservation lifecycle.

`app/services/commerce_order_service.py:67` derives `order_id = sha256(correlation_id)[:32]` — the deterministic-id pattern this spec mandates for all integration idempotency keys.

## 3. Data Model

ECM-001 introduces **no new DynamoDB tables and no new rows**. It is a design artifact. This section documents the tables that later ECM tickets will read (as read-only consumers) and the tables where additive fields will be written.

### 3.1 Tables consumed read-only by ECM integration layer

| Table handle | DDB table name (default) | Owner ticket | What ECM reads |
|---|---|---|---|
| `T.catalog` | `shopping_catalog` | existing | `stock_count`, `price_cents`, `category_id`, `item_id` |
| `T.catalog_products` | `catalog_products` | PRD-001 | `product_type`, `parent_id` for variant topology |
| `T.catalog_product_versions` | `catalog_product_versions` | PRD-003 | variant feature selections |
| `T.inventory` | `inventory` | OFB-003 | `on_hand`, `reserved`, `available` per SKU+location |
| `T.reservations` | `reservations` | OFB-004 | active reservation TTL and qty |
| `T.orders` | `orders` | existing / ORD-003 | `lifecycle_status`, `fulfillment_status` |

All of the above handles (`T.catalog` at `tables.py:351`, `T.catalog_products` at `tables.py:379`, `T.catalog_product_versions` at `tables.py:380`, `T.orders` at `tables.py:381`, `T.inventory` at `tables.py:569`, `T.reservations` at `tables.py:570`) are already registered in `app/core/tables.py`. `T.shipments` (needed by ECM-007/section 5.5) does NOT yet exist — it is a forward reference that SHP-010 creates. ECM integration reads them through service-layer functions — never issuing DDB calls directly from `app/services/store_integration.py`.

### 3.2 Additive fields written to existing tables (flag-gated)

These fields are written by upstream tickets but are the read-seams for the ECM integration layer:

**`T.catalog` item rows** — upstream PRD-003 adds `product_type: "virtual" | "variant" | "flat"`, `variant_count: int`. ECM reads these to decide whether to call the variant enrichment path.

**`T.orders` header rows** — upstream ORD-007 adds `lifecycle_status` additively (with `ORDER_LIFECYCLE_ENABLED` on). ECM integration in the cart-to-order path passes through this field unchanged; the integration layer never writes it.

**No new GSIs are introduced by ECM-001.** GSIs for variant resolution (PRD-002), inventory SKU (OFB-003), and order status/shipdate (ORD-003) are defined by their respective owner tickets. ECM reads through them via service functions.

### 3.3 No ECM-owned DDB table

ECM-002 introduces `app/services/store_integration.py` as a thin gate/wrapper module. It holds no persistent state of its own — it is purely a read-merge layer over the upstream service functions. All persistence belongs to the upstream modules.

## 4. API / Service Design

ECM-001 defines the **integration surface contract** that ECM-002 through ECM-013 implement. No endpoints or service functions are created by this ticket. This section is a forward declaration of the call signatures and endpoint modifications that later tickets must fulfill.

### 4.1 New module: `app/services/store_integration.py` (ECM-002)

```python
def _integration_enabled(sub_flag: str | None = None) -> bool:
    """Return True iff STORE_INTEGRATION_ENABLED is on AND (sub_flag is None
    or the named sub-flag is also on). Reads through S singleton."""

def _safe_upstream(call: Callable[[], T], default: T) -> T:
    """Invoke call(); on any exception log at WARNING and return default.
    Guarantees upstream failures never propagate into browse/cart/checkout."""

async def enrich_catalog_item(
    item: dict,
    *,
    viewer: str,
    request: Request | None = None,
) -> CatalogItemOut:
    """(ECM-004) Return enriched CatalogItemOut. When STORE_VARIANT_SELECTION_ENABLED
    off or product has no variants, returns _catalog_item_out(item) unchanged."""

async def get_live_availability(
    sku: str,
    quantity: int = 1,
) -> StorefrontAvailabilityOut:
    """(ECM-005) Return availability from T.inventory. When
    STORE_SHOW_LIVE_AVAILABILITY off, returns legacy stock_count-based result."""

async def get_cart_pricing_breakdown(
    user_sub: str,
    cart_id: str,
) -> CartPricingBreakdownOut:
    """(ECM-006) Apply pricing rules. When STORE_APPLY_PRICING_RULES off,
    returns plain sum of line_total_cents with no rule lines."""

async def get_order_fulfillment_status(
    order_id: str,
    user_sub: str,
) -> OrderFulfillmentStatusOut:
    """(ECM-007) Return lifecycle + ship-group status. When
    STORE_SHOW_FULFILLMENT_STATUS off, returns legacy status field."""
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Read-merge sequence for a single product

The integration layer builds enriched output from a strict read-merge pipeline. Each step is wrapped in `_safe_upstream` so an upstream failure falls back to the previous layer's result:

```
1. catalog._catalog_item_out(item)          → base CatalogItemOut (current behavior)
2. product_variants.list_variants(item_id)  → StorefrontVariantOut[] (PRD-007)
   fallback: variants = None
3. For each variant: inventory.get_inventory(sku) → StorefrontAvailabilityOut
   fallback: availability derived from item.stock_count (legacy)
4. pricing_rules.compute_item_price(item_id, viewer) → effective price_cents
   fallback: item.price_cents unchanged
```

Step 2 is only executed when `STORE_VARIANT_SELECTION_ENABLED` is on. Step 3 is only executed when `STORE_SHOW_LIVE_AVAILABILITY` is on. Step 4 is only executed when `STORE_APPLY_PRICING_RULES` is on. All three off → output is byte-for-byte the existing `CatalogItemOut`.

### 5.2 Cart add-item with variant resolution

When `STORE_VARIANT_SELECTION_ENABLED` is on and the frontend sends `variant_id` in the add-to-cart body, `add_item` (`shoppingcart.py:311`) must:

1. Resolve `sku` from the variant record (PRD-007 provides `product_variants.get_variant_sku(variant_id)`).
2. Use the variant's effective `price_cents` (parent + Σ delta) as `unit_price_cents`.
3. Store `variant_id` on the cart item row so order line items carry it.

When the flag is off or `variant_id` is absent: identical to today — `sku = item_id`, `unit_price_cents` from request body.

### 5.3 Stock gate at purchase — reservation path vs. scalar path

**Flag off (`INVENTORY_RESERVATIONS_ENABLED = false`):** `purchase_cart` executes the existing conditional `update_item` directly against `T.catalog.stock_count` (`shoppingcart.py:514–538`). No change.

**Flag on:** `purchase_cart` calls `inventory.commit_reservation(reservation_id)` (OFB-004) instead of the scalar decrement. The reservation was created by `inventory.reserve(sku, qty)` at add-to-cart time (also OFB-004). If no reservation exists (cart was added before the flag was turned on), fall back to the scalar decrement path as a one-time bridge; log a warning. This bridge is implemented in ECM-008, not here.

### 5.4 Cart total with pricing rules

**Flag off (`STORE_APPLY_PRICING_RULES = false`):** `cart_total_cents` returns `Σ line_total_cents` unchanged. `ui_cart_total` returns `ShoppingCartTotalOut` with no `pricing_breakdown`. Existing `Checkout.tsx:133` `purchaseCart` call is unaffected.

**Flag on:** `store_integration.get_cart_pricing_breakdown(user_sub, cart_id)` calls `pricing_rules.apply_rules(items, viewer)` (OFB-020). The returned `CartPricingBreakdownOut.final_total_cents` is authoritative at purchase; `purchase_cart` uses it instead of the raw sum. The applied rule lines are persisted in the `metadata` dict of the order record (no new column; mirrors how promo discount is stored today at `shoppingcart.py:590`).

### 5.5 Order fulfillment surface

**Flag off (`STORE_SHOW_FULFILLMENT_STATUS = false`):** `ShoppingCartPurchaseOut` (`app/models.py:993`) is returned unchanged — `order_id`, `purchased_at`, `purchased_total_cents`, no lifecycle/ship fields. Buyer has no visibility into order progression beyond "order placed."

**Flag on:** The new buyer-facing `GET /ui/shoppingcart/orders/{order_id}` endpoint calls `store_integration.get_order_fulfillment_status(order_id, user_sub)` which reads `T.orders` for `lifecycle_status` (ORD-005) and `fulfillment_status` (SHP-014), and `T.shipments` for `ship_groups`/`tracking_numbers` (SHP-010). **Note:** `T.shipments` does not yet exist in `app/core/tables.py` — it is a forward reference that SHP-010 creates; ECM-007 must add it to `Tables` and `T` at that point. All reads are wrapped in `_safe_upstream`; if ORD or SHP tables do not yet exist, returns `OrderFulfillmentStatusOut` with all optional fields as `None`.

### 5.6 Out-of-stock handling at add-to-cart vs. purchase

Today stock is only checked at purchase (hard gate). The integration layer introduces a soft check at add-to-cart when `STORE_SHOW_LIVE_AVAILABILITY` is on: `availability.available < requested_qty` returns a 409 with `detail.code = "out_of_stock"`, matching the existing purchase-time error shape (`shoppingcart.py:534`). This is advisory — a concurrent purchase between the add check and the commit can still succeed or fail at the reservation layer.

### 5.7 Geo-blocking interaction

`app/routers/catalog.py:130–146` (`_item_geo_blocked`) already gates catalog item visibility. The integration layer inherits this: an item that is geo-blocked is excluded from browse results before enrichment runs. No change needed here.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

All integration enrichment calls the same upstream service functions in dev and prod. No `if S.dev_mode` branch exists in the integration layer. Dev uses moto/DDB-local for all tables; prod uses real DynamoDB. The `_safe_upstream` wrapper is identical in both environments — it never diverges by environment. This mirrors the approach used in `app/services/instance_monitoring.py` and `app/services/audit_export_pipeline.py`.

### 7.2 Idempotency

The cart purchase idempotency key `cart_purchase:{user_sub}:{cart_id}` (`shoppingcart.py:194–195`) is unchanged. The integration layer does not introduce new idempotency keys for read-merge operations. For the reservation commit path (ECM-008), the `reservation_id` is derived deterministically from `sha256(cart_id|sku|user_sub)`, mirroring `commerce_order_service.py:67`.

For the pricing-rules application, the `applied_rules` list is stored on the order `metadata` dict — no separate row, no new key. Re-purchasing an already-PURCHASED cart returns the cached result (`shoppingcart.py:483–492`) before any integration code runs.

### 7.3 Read-only contract

The integration layer is strictly read-only against all upstream services. It calls:
- `product_variants.list_variants(item_id)` — read
- `inventory.get_inventory(sku)` / `inventory.get_or_zero(sku)` — read
- `pricing_rules.apply_rules(items, viewer)` — pure computation, no write
- `order_lifecycle.get_order(order_id)` — read
- `shipments.list_ship_groups(order_id)` — read

No forked pricing logic, no forked inventory logic, no forked order logic. All writes remain owned by the upstream service that owns the table.

### 7.4 Security

The integration layer inherits the caller's `user_sub` and passes it to every upstream read call so per-user access isolation is enforced by the upstream service's PK pattern. No cross-user reads. No admin data surfaces to the buyer-facing integration endpoints — `get_order_fulfillment_status` is gated on `user_sub == order["user_id"]` before returning.

## 8. Backward Compatibility & Migration

### 8.1 Zero-regression guarantee

With all five flags off, every storefront code path is byte-for-byte unchanged:

| Touchpoint | Current behavior preserved? | Verification |
|---|---|---|
| `_catalog_item_out` return shape | Yes — no new fields when flags off | `CatalogItemOut` serializes identically |
| `cart_total_cents` return value | Yes — plain sum, no rule lines | `ShoppingCartTotalOut.total_cents` unchanged |
| `purchase_cart` stock decrement | Yes — scalar `T.catalog.update_item` | `shoppingcart.py:514–538` path untouched |
| `create_order_from_line_items` | Yes — `lifecycle_status` absent | `commerce_order_service.py:72–84` unchanged |
| Frontend `Checkout.tsx` | Yes — `purchaseCart` response shape unchanged | `ShoppingCartPurchaseOut` unchanged |

### 8.2 Additive model fields

All new Pydantic fields on `CatalogItemOut`, `ShoppingCartTotalOut`, and `ShoppingCartPurchaseOut` are `Optional` with `None` defaults. Existing serialized payloads are valid input for the updated models. No field renaming, no type narrowing, no required field additions.

### 8.3 No table migrations required

ECM-001 introduces no schema changes. Upstream tickets (OFB-003, PRD-001, ORD-003) own their table creation and add their fields additively to existing tables. The ECM integration layer reads new fields only when they are present (`item.get("lifecycle_status")` style, with `None` fallback).

### 8.4 Rollout ordering

The master flag `STORE_INTEGRATION_ENABLED` must not be turned on before the upstream flags it depends on are deployed and their tables are provisioned. The recommended rollout order is:

1. OFB-003/004 (`INVENTORY_RESERVATIONS_ENABLED`) — already partially shipped
2. PRD-001/007 (`PRODUCT_DEPTH_ENABLED`)
3. OFB-019/020 (`PRICING_RULES_ENABLED`)
4. ORD-005/007 (`ORDER_LIFECYCLE_ENABLED`)
5. SHP-010/012/014 (`SHIPPING_ENABLED`)
6. ECM-002 through ECM-013 (`STORE_INTEGRATION_ENABLED` + sub-flags)

Turning on an ECM sub-flag before its upstream flag is on is safe — `_safe_upstream` catches the 404 from `_require_enabled()` and returns the legacy default.

## 9. Test Plan

ECM-001 produces no runtime code, so the test artifacts it mandates are templates for later tickets.

### 9.1 Hermetic offline pytest pattern

All ECM tests follow the isolation pattern used throughout this codebase: moto-backed DynamoDB tables bound to frozen `T` handles via `object.__setattr__`, no TestClient, route handlers called directly as coroutines.

```python
import boto3, moto, types, asyncio, pytest
from app.core.tables import T
from app.core.settings import S

@pytest.fixture
def ddb_tables():
    with moto.mock_dynamodb():
        ddb = boto3.resource("dynamodb", region_name="us-east-1")
        catalog_table = ddb.create_table(
            TableName="shopping_catalog",
            KeySchema=[{"AttributeName": "PK", "KeyType": "HASH"},
                       {"AttributeName": "SK", "KeyType": "RANGE"}],
            AttributeDefinitions=[{"AttributeName": "PK", "AttributeType": "S"},
                                  {"AttributeName": "SK", "AttributeType": "S"}],
            BillingMode="PAY_PER_REQUEST",
        )
        object.__setattr__(T, "catalog", catalog_table)
        yield catalog_table
```

## 10. Open Questions / Assumptions

1. **Assumption**: `T.catalog` items will gain `product_type` from PRD-003 before ECM-004 is deployed. The enrichment step checks `item.get("product_type") == "virtual"` to decide whether to query variants. If PRD-003 is not yet deployed, all items are treated as flat (correct fallback).

2. **Assumption**: The pricing-rules engine (OFB-019) exposes a pure function `apply_rules(items: List[dict], viewer_sub: str) -> RuleApplicationResult` that is safe to call from an async context and makes no DDB writes. If OFB-019 has side effects (e.g. tracking rule impressions), `_safe_upstream` must NOT silently swallow a write failure — ECM-008 must verify this contract with the OFB-019 implementer.

3. **Open question**: Should `GET /ui/catalog/categories/{cat_id}/items` (list) perform per-item inventory reads, or only provide availability in the single-item detail endpoint? Per-item reads on a page of 50 products would be 50 serial DDB reads or one batch-get. Decision deferred to ECM-005; the spike assumes availability enrichment is opt-in at the list level via a `?include_availability=1` query param.

4. **Open question**: When both `STORE_APPLY_PRICING_RULES` and a promo code are present on the same cart, what is the stacking behavior? OFB-020 owns this, but ECM-006 must thread the promo code through to the pricing engine. Assumption for now: pricing rules run first; the promo `_calculate_discount` (`promo_codes.py:376`) runs after on the rule-reduced subtotal.

5. **Assumption**: `StorefrontAvailabilityOut.available` is always `max(0, on_hand - reserved)` — never negative. The inventory service's `get_or_zero` (`inventory.py:158`) already enforces this.

6. **Open question**: Does the frontend `Catalog.tsx` need a new API contract for variant selection, or will the existing `addToCartMutation` be extended with a `variant_id` field? Frontend ECM work (ECM-009/010) should resolve this; the spike assumes the existing `addCartItem` call in `ProductDetail.tsx:91` gains an optional `variant_id` field.

7. **Assumption**: The order fulfillment endpoint (`GET /ui/shoppingcart/orders/{order_id}`) is buyer-scoped: it filters by `order["user_id"] == ctx["user_sub"]`. Admin order views are owned by ORD-014 and share no code with the buyer view.

8. **Assumption**: All upstream services are called synchronously within async handlers using `asyncio.to_thread` for any blocking DDB I/O, following the existing pattern in `app/routers/google_drive_integration.py`.
