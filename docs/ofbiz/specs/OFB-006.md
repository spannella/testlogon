# OFB-006 — Inventory admin UI

**Type:** Feature | **Priority:** P1 | **Estimate:** 3 days
**Depends on:** OFB-003 (inventory service), OFB-004 (reservation lifecycle), OFB-005 (low-stock alerts)
**Downstream:** OFB-007 (E2E tests)

---

## 1. Summary & Goal

OFB-006 delivers the **admin-facing inventory management page** that lets admins and root users view, filter, and adjust stock levels without leaving the platform UI. The feature exposes per-SKU on-hand / reserved / available / reorder-point figures, highlights low-stock and out-of-stock SKUs with visual badges, supports a filterable low-stock view, and provides inline adjustment and set-on-hand actions with optimistic UI updates.

The implementation is split across three layers:

1. **Backend** — two additive service functions (`list_all_inventory`, `set_reorder_point_http`) and two new HTTP endpoints (`GET /ui/inventory/items` for paginated listing, `PATCH /ui/inventory/items/{sku}/reorder-point` for reorder-point mutation) added to the existing `app/routers/inventory.py`. Both are `require_admin_or_root_csrf`-gated.
2. **Frontend types + API wrappers** — four new/updated entries in `frontend/src/api/types.ts` and `frontend/src/api/endpoints/inventory.ts`.
3. **React page** — `frontend/src/pages/shop/admin/InventoryAdmin.tsx` is extended (the file already exists as a skeleton) to add the full-table listing with low-stock filter toggle and inline per-row adjust/reorder-point editing.

All changes are **additive and flag-gated** behind the existing `INVENTORY_RESERVATIONS_ENABLED` master switch (`app/core/settings.py:839`). With the flag off the new endpoints return 404 and the page renders the existing "Inventory management is not enabled" `EmptyState`. The catalog/cart/billing decrement-at-purchase path is byte-for-byte unchanged.

## 3. Data Model

No new DynamoDB tables or GSIs are required. OFB-006 reads from the existing `inventory` table.

### 3.1 Existing `inventory` table schema

```
Table:  inventory  (scripts/local-ddb-init.py:2456)
PK:     sku         (String)
SK:     location_sk (String)   — LOC#{location_id}  (e.g. "LOC#warehouse")

Attrs:  on_hand (N), reserved (N), available (N), reorder_point (N),
        status (S: in_stock | low_stock | out_of_stock),

        Projection: ALL
```

All rows in `T.inventory` use `location_sk = LOC#{location_id}` (enforced by `_location_sk()` at `app/services/inventory.py:59`). **CORRECTED:** OFB-005 low-stock alert sentinel rows are NOT stored in `T.inventory`. They are stored in `T.catalog` with PK=`LOWSTOCK_ALERT_SENTINEL#{creator_id}`, SK=`LOWSTOCK#{item_id}` (`app/routers/catalog.py:660–671`). The `inventory` table contains only real stock rows, so the `begins_with("LOC#")` filter in the scan path of `list_all_inventory` is a safety guard but there are no foreign sentinel rows to exclude in practice.

## 4. API / Service Design

### 4.1 New service functions in `app/services/inventory.py`

#### `list_all_inventory`

```python
def list_all_inventory(
    *,
    status_filter: Optional[str] = None,   # None = all; "low_stock" | "out_of_stock" | "in_stock"
    limit: int = 100,
    cursor: Optional[Dict[str, Any]] = None,
) -> Dict[str, Any]:
    """
    Return a page of inventory records, optionally filtered by status.

    Strategy:
    - status_filter provided → query GSI_AVAILABLE (efficient; status is the PK).
    - status_filter is None  → scan the inventory table with a FilterExpression
      that restricts location_sk to the "LOC#" prefix so sentinel rows are excluded.

    Both paths loop over LastEvaluatedKey internally (up to `limit` items) and
    return an opaque cursor for the next page.

    Returns: {"items": [_record_out(...)], "next_cursor": Optional[str], "total_returned": int}
    """
```

Implementation notes:

- **GSI path** (status_filter set): `T.inventory.query(IndexName="GSI_AVAILABLE", KeyConditionExpression=Key("status").eq(status_filter), Limit=limit, ExclusiveStartKey=cursor)`. All rows in `GSI_AVAILABLE` are real stock rows since every `_persist` call (at `app/services/inventory.py:123`) writes a `status` attribute.
- **Scan path** (status_filter=None): `T.inventory.scan(FilterExpression=Attr("location_sk").begins_with("LOC#"), Limit=limit, ExclusiveStartKey=cursor)`. Using `Attr("location_sk").begins_with("LOC#")` is a defensive guard; all real inventory rows use `location_sk = "LOC#" + location_id` (enforced by `_location_sk()` at `app/services/inventory.py:59`). OFB-005 sentinel rows are in `T.catalog`, not `T.inventory`, so the filter has no sentinel rows to exclude — it is still good defensive practice in case of future data model additions.
- Cursor encoding: use `app.core.cursor.encode_cursor` / `decode_cursor` (`app/core/cursor.py:94,103`) — same pattern as `app/routers/profile.py:554,620`. ✓
- The function calls `_require_enabled()` (`app/services/inventory.py:54`) and raises HTTPException 404 if the flag is off.

#### `set_reorder_point_http` (thin wrapper for router use)

The existing `set_reorder_point(sku, reorder_point, ...)` function at `app/services/inventory.py:303` already does everything needed. OFB-006 does not add a new service function for this operation — the router will call `inv.set_reorder_point` directly, as the other admin endpoints call `inv.set_on_hand` and `inv.adjust`.

### 4.2 New HTTP endpoints in `app/routers/inventory.py`

#### `GET /ui/inventory/items` — paginated all-inventory listing

```python
@inventory_router.get("/items", response_model=InventoryListOut)
async def list_inventory_items(
    status: Optional[str] = Query(default=None),          # None | "low_stock" | "out_of_stock" | "in_stock"
    limit: int = Query(default=50, ge=1, le=500),
    cursor: Optional[str] = Query(default=None),
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> InventoryListOut:
    ...
```

Behavior:
1. Calls `_require_enabled()`.
2. Validates `status` is None or one of the three allowed values; returns 422 otherwise.
3. Decodes `cursor` via `decode_cursor(cursor)` (returns None for missing/invalid).
4. Calls `inv.list_all_inventory(status_filter=status, limit=limit, cursor=decoded_cursor)`.
5. Returns `InventoryListOut(items=[InventoryRecordOut(**r) for r in result["items"]], next_cursor=result["next_cursor"], total_returned=result["total_returned"])`.

**Route ordering note**: `GET /items` must be declared **before** `GET /items/{sku}` in the router file (`app/routers/inventory.py:36`). FastAPI matches routes in declaration order; the literal path `/items` would otherwise be captured as `sku="items"` by the dynamic route. The existing file currently has `GET /items/{sku}` at line 36; the new `GET /items` is inserted before it.

#### `PATCH /ui/inventory/items/{sku}/reorder-point` — update reorder point

```python
@inventory_router.patch("/items/{sku}/reorder-point", response_model=InventoryRecordOut)
async def update_reorder_point(
    sku: str,
    body: InventorySetReorderPointIn,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> InventoryRecordOut:
    ...
```

Behavior:
1. Calls `_require_enabled()`.
2. Calls `inv.set_reorder_point(sku, body.reorder_point, location_id=body.location_id, user_sub=user.sub)`.
3. Returns `InventoryRecordOut(**rec)`.
4. 404 if no inventory record exists for `(sku, location_id)` — propagated from `set_reorder_point` which calls `_get_raw` first: if the row does not exist an HTTPException 404 should be raised. The existing `set_reorder_point` function (`app/services/inventory.py:303`) uses `_persist` which always `put_item` (creates if absent). For this endpoint the desired behavior is: if no inventory record exists, create one with `on_hand=0, reserved=0, reorder_point=body.reorder_point`. This matches the existing `set_reorder_point` service function semantics (it calls `_persist` which is an upsert).

## 5. Detailed Behavior & Edge Cases

### 5.1 Full-inventory table view

The main table lists all inventory rows returned by `GET /ui/inventory/items` (no `status` filter). Columns: SKU, On hand, Reserved, Available, Reorder point, Status badge, Adjust (inline ±qty input), Reorder point (inline edit).

Each row shows the status badge from `statusBadge(rec.status)` (already defined in `InventoryAdmin.tsx:30–44`). Rows with `status="low_stock"` display the amber outline badge; `status="out_of_stock"` displays the destructive red badge.

### 5.2 Status filter toggle

A filter control (three buttons or a `<Select>`) with options All / Low stock / Out of stock. Selecting a non-"All" option re-fetches with the corresponding `status` query parameter (leveraging `GSI_AVAILABLE` on the backend for efficiency). This replaces the existing "Low-stock items" card which reads from the separate `GET /ui/inventory/low-stock` endpoint — the new `GET /ui/inventory/items?status=low_stock` endpoint subsumes it and the old `listLowStock` call inside `InventoryAdmin.tsx` can be replaced.

React Query key: `["inventory", "items", { status, cursor }]` — changing the filter triggers a fresh query.

### 5.3 Inline adjust

Each row has a numeric `±qty` input and an "Apply" button (already implemented per-row in `InventoryRow` component in `InventoryAdmin.tsx:46–86`). The `onAdjust` callback calls `adjustInventory({ sku, delta, reason: "manual_adjust" })`. On success, `qc.invalidateQueries({ queryKey: ["inventory", "items"] })` refreshes the table.

The reason field for inline adjust is hardcoded to `"manual_adjust"`. Admins who need to supply a custom reason can use the existing SKU lookup form.

### 5.4 Inline reorder-point edit

Each row gains an editable reorder-point cell. The cell renders as plain text by default; clicking it reveals an `<Input type="number" min={0} />` with a checkmark button. Clicking checkmark calls `setInventoryReorderPoint(rec.sku, { reorder_point: newValue })`. On success, invalidate `["inventory", "items"]`. On cancel (Escape or blur with no change) revert to read-only.

This is a common "editable cell" pattern (no new shared component needed; a local `EditableCell` sub-component within the page file is sufficient).

### 5.5 Optimistic update requirement (acceptance criterion)

The ticket requires "recalculated available without reload." React Query's `onSuccess` callback invalidates the query key, triggering a background refetch. The stale table row is replaced with fresh data from the re-fetch. This satisfies the criterion without a manual optimistic write since the operation is admin-only (low concurrency) and the re-fetch is fast against DDB Local.

Alternative (full optimistic): `onMutate` can update the query cache by patching the specific row's `available` and `on_hand` values before the server round-trip. However, given that `adjust` has a conditional update path that may retry internally (OFB-003: `app/services/inventory.py:282–286`), the server-returned value is authoritative. A plain invalidation is sufficient.

### 5.6 Pagination

The `GET /ui/inventory/items` endpoint returns up to 500 rows per page (default 50). For inventories with more rows, the frontend renders a "Load more" button that appends the next page using `useInfiniteQuery` from React Query (same pattern as `ConversationView` message loading):

```typescript
useInfiniteQuery({
  queryKey: ["inventory", "items", status],
  queryFn: ({ pageParam }) =>
    listInventoryItems({ status, limit: 50, cursor: pageParam ?? undefined }),
  getNextPageParam: (lastPage) => lastPage.next_cursor ?? undefined,
});
```

All pages are flattened into a single table via `data.pages.flatMap(p => p.items)`. The "Load more" button is hidden when `!hasNextPage`.

### 5.7 Access-denied path

`InventoryAdmin.tsx:158–168` already renders `<EmptyState>` for `!allowed`. ✓ The `allowed` guard uses `canAccessGeneralAdminControls(accessToken)` (`frontend/src/lib/adminCapabilities.ts:47`) ✓, which returns `true` only for `role=root` or `role=admin` with profile type `general`. Scoped admins (e.g., `charlie_scoped`) are rejected.

### 5.8 Flag-off path

`InventoryAdmin.tsx:146–156` already renders "Inventory management is not enabled" when `!isInventoryReservationsEnabled()`. ✓ The frontend feature flag mirrors `INVENTORY_RESERVATIONS_ENABLED` via `VITE_INVENTORY_RESERVATIONS_ENABLED` (`frontend/src/lib/featureFlags.ts:161–162`). ✓

### 5.9 SKU lookup form (retained)

The existing "Manage SKU" card (single-SKU lookup + set-on-hand form) is retained as a secondary workflow for precise per-SKU management. The new all-SKU table is the primary view.

### 5.10 No DDB FilterExpression page-size trap

As noted in CLAUDE.md, `FilterExpression` does not reduce the page size DynamoDB returns before filtering. The scan path (`status_filter=None`) uses `begins_with("LOC#")` on `location_sk`. Since all rows in `T.inventory` are real stock rows with `LOC#` prefixed keys (OFB-005 sentinel rows are in `T.catalog`, not `T.inventory`), the filter matches virtually all rows. No silent data loss occurs at typical page sizes. If future data additions introduce non-`LOC#` rows, the filter provides protection; `next_cursor` will be non-null and the client iterates correctly.

### 5.11 `list_low_stock` vs `list_all_inventory`

The existing `GET /ui/inventory/low-stock` endpoint (`app/routers/inventory.py:78`) and `list_low_stock` service function (`app/services/inventory.py:318`) remain in place (they are used by the current `InventoryAdmin` skeleton and tested in `tests/test_ofb_inventory.py`). `GET /ui/inventory/items?status=low_stock` is functionally equivalent but also returns pagination cursors. The frontend `InventoryAdmin` migrates its low-stock card to use the new endpoint; the old endpoint is preserved for backward compatibility (OFB-007 E2E tests may reference it).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

All DynamoDB calls in `list_all_inventory` go through `T.inventory` (`app/core/tables.py:317,569`) — the same frozen handle used by all other inventory service functions. In dev, `T.inventory` is bound to DynamoDB Local (port 8001); in prod, to real DynamoDB. There is no `S.dev_mode` branch in the service logic. `encode_cursor` / `decode_cursor` (`app/core/cursor.py:94,103`) ✓ use HMAC-signed cursors that are identical in both environments.

### 7.2 Idempotency

- `list_all_inventory` is a read — always idempotent.
- `set_reorder_point` (via `PATCH /ui/inventory/items/{sku}/reorder-point`) calls `_persist` which is a `put_item` (upsert). Replaying the same PATCH twice with the same value produces the same result. The `updated_at` timestamp advances on each call, which is acceptable.

### 7.3 Security

- Both new endpoints (`GET /ui/inventory/items`, `PATCH .../reorder-point`) require `require_admin_or_root_csrf`, enforcing role ∈ {ADMIN, ROOT} **and** CSRF validation for cookie-authenticated requests (`app/auth/policy.py:100–106`). ✓ Bearer-token callers skip CSRF but must still pass role validation.
- `list_all_inventory` returns inventory data for **all SKUs system-wide**, not scoped to a specific `creator_id`. This is intentional for the admin view. Non-admin users cannot call this endpoint (403/404).
- The cursor is HMAC-signed (`app/core/cursor.py`) so clients cannot forge pagination positions.
- The `sku` path parameter in `PATCH /items/{sku}/reorder-point` is passed directly to `inv.set_reorder_point`. The service validates `reorder_point >= 0` via Pydantic (`InventorySetReorderPointIn.reorder_point: int = Field(ge=0)`). No SQL injection or DDB injection risk — DDB SDK uses parameterized expressions.

### 7.4 Scoped admin access

`require_admin_or_root_csrf` at `app/auth/policy.py:100` does not check `admin_profile.type`. A scoped admin passes the role check. For inventory management, this is intentional — the ticket specifies "admin/root-gated" without further scoping. If future policy requires restricting to `general` admins only, the dependency should be changed to `require_general_admin_or_root` (defined at `app/auth/policy.py:109`). ✓

## 10. Open Questions / Assumptions

1. **Scan vs. GSI for all-inventory list** — The `status_filter=None` path uses a table scan with `begins_with("LOC#")`. For catalogs with thousands of SKUs this is a full scan, which is O(items) reads and may be slow. An alternative is to add a new GSI with a constant partition key (e.g., `entity_type="inventory_record"`) allowing efficient query. This is deferred: the current single-warehouse phase likely has hundreds of SKUs, not millions. If performance is a concern in prod, the GSI can be added in a follow-up without breaking any API contracts (the cursor-based pagination already handles chunked loading).

2. **`list_all_inventory` vs. refactoring `list_low_stock`** — The spec introduces a new `list_all_inventory` function rather than generalizing `list_low_stock` (which always queries `GSI_AVAILABLE` and cannot return all statuses). Assumption: the two functions coexist; `list_low_stock` is not deprecated by OFB-006 since it is tested in `test_ofb_inventory.py` and may be used by the OFB-005 alert surfacing path.

3. **`require_admin_or_root_csrf` vs. `require_general_admin_or_root`** — The ticket says "admin/root-gated" with no further qualification. This spec uses `require_admin_or_root_csrf` (which accepts both general and scoped admins) to match the existing inventory admin endpoints (`app/routers/inventory.py:48,65`). If the product decision is that only general admins should manage inventory, the dependency should be `require_general_admin_or_root`. This assumption should be confirmed before implementation.

4. **Pagination UX: Load-more vs. pages** — The spec proposes `useInfiniteQuery` with a "Load more" button. An alternative is a server-side paginated table with numbered pages. The "Load more" pattern is simpler (no page-number state) and matches the existing `useInfiniteQuery` patterns in this codebase (e.g., message loading in `ConversationView`). If the catalog can have >500 SKUs, a page-number UI may be preferable. This is an assumption to confirm with the product owner.

5. **Reorder-point edit: upsert semantics** — `PATCH /ui/inventory/items/{sku}/reorder-point` uses `set_reorder_point` which calls `_persist` (upsert). If the SKU has no inventory row, a zeroed row is created. This may be unexpected (admin sets a reorder point for a SKU that has no stock). The alternative is to 404 when no inventory row exists. The upsert behavior is simpler and allows pre-configuring reorder points before stock arrives; this spec assumes upsert is correct.

6. **Inline adjust reason** — Inline adjust in the table row hardcodes `reason="manual_adjust"`. The existing SKU lookup form also uses `"manual_adjust"`. If audit logs need finer granularity (e.g., distinguish "admin table adjust" from "SKU lookup adjust"), a reason field could be added to the `InventoryAdjustIn` model. This is out of scope for OFB-006.

7. **Relationship between catalog `stock_count` and inventory `on_hand`** — OFB-003 describes `stock_count` as a "denormalized read-through mirror". This spec assumes the OFB-003 hook that keeps them in sync is already implemented. If it is not (i.e., the catalog `stock_count` is still the authoritative source), the admin UI will show inventory records that diverge from what the storefront displays. This dependency on OFB-003 must be verified before shipping OFB-006.
