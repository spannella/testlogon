# HRM-010 — Payroll-expense GL journal hook (derives from the ledger)

**Type:** Feature | **Priority:** P1 | **Estimate:** 2 days
**Milestone:** 3 — Payroll & GL Hook

---

## 1. Summary & Goal

HRM-010 extends `app/services/gl_posting.py` (the double-entry mapper introduced by OFB-013/OFB-014) so that a billing ledger row carrying `reason="payroll"` is mapped to a balanced double-entry journal entry:

- **Debit**: Salaries & Wages Expense — account code `S.hr_payroll_expense_account_code` (default `"6000"`, an OFBiz-conventional expense code)
- **Credit**: Cash/Bank — the same Cash account that all other money-out entries credit (account code resolved from the OFB-013 seeded chart)

HR does **not** post journals itself. HRM-008 writes the single-entry ledger row (via `billing_shared.new_ledger_entry`) with `reason="payroll"` into `T.billing`. The GL poster (OFB-014) already scans `GSI_LEDGER_DATE` day buckets; HRM-010 adds the `reason="payroll"` → `(Dr Salaries & Wages Expense / Cr Cash)` mapping entry to that mapper's dispatch table, and adds the Salaries & Wages Expense account to OFB-013's seeded chart so the trial balance still closes.

The entire change is additive. With `S.hr_payroll_gl_posting_enabled` off (or `S.gl_double_entry_enabled` off), payroll ledger rows flow through the existing GL poster as an unmapped/skipped entry — no journal is written and the ledger itself is untouched.

## 2. Context & Current State

### 2.1 `billing_shared.new_ledger_entry` — the upstream source

`app/services/billing_shared.py:224` defines `new_ledger_entry(*, key_name, key_value, entry_type, amount_cents, state, reason, meta=None, extra=None) -> Tuple[str, Dict[str, Any]]`. It stamps `ledger_date` (via `ledger_date_for_ts(ts)` at `billing_shared.py:253`) onto every item, which populates the `GSI_LEDGER_DATE` index used by `platform_financial_dashboard.py:148` to bucket entries by day. (`ledger_date_for_ts` is defined at `billing_shared.py:10`; `new_ledger_entry` body at `:224–259`; `entry_id` uses `ulidish()` at `:240`, not sha256 — sha256 is only used by HRM-008's caller-side SK override.)

HRM-008 calls this function per payroll line with:
```

entry_type="debit", state="settled", reason="payroll"
extra={"employment_id": ..., "party_id": ..., "payroll_run_id": ...}
```

(per `docs/ofbiz/specs/HRM-008.md` §3.1). The resulting item is written to `T.billing` — the same table as all Stripe/PayPal/CCBill charges — so the `GSI_LEDGER_DATE` index picks it up automatically at no extra cost.

## 3. Data Model

HRM-010 introduces no new DynamoDB tables and no changes to existing table schemas. It writes one new row type to `T.gl_journal` and one row to `T.gl_accounts`.

### 3.1 Journal entry item in `T.gl_journal`

One journal entry is written per payroll ledger row. The `T.gl_journal` schema is defined by OFB-014; the payroll entry uses the same shape:

| Attribute | DDB Type | Value |
|---|---|---|
| `journal_id` | S | `f"je_{sha256_str('payroll_journal:{entry_id}')[:24]}"` — deterministic from source `entry_id` |
| `sk` | S | `"JOURNAL#META"` (or the OFB-014 chosen sort key) |
| `source_entry_id` | S | The `entry_id` of the payroll billing row — the idempotency key |
| `source_ledger_date` | S | `ledger_date` from the billing item (YYYY-MM-DD) |
| `source_pk` | S | `f"PAYROLL#{payroll_run_id}"` — the billing table partition of the source row |
| `debit_account_code` | S | `S.hr_payroll_expense_account_code` (default `"6000"`) |
| `credit_account_code` | S | Cash/Bank account code resolved from `T.gl_accounts` (OFB-013 seed) |
| `amount_cents` | N | `line["gross_cents"]` — equal on both sides (balanced entry) |
| `description` | S | `f"Payroll disbursement — run {payroll_run_id}, employee {party_id}"` |
| `posted_at` | N | `now_ts()` at journal-write time |
| `state` | S | `"posted"` |
| `employment_id` | S | Denormalized from the billing item's `employment_id` field |
| `payroll_run_id` | S | Denormalized from the billing item's `payroll_run_id` field |

The idempotency guard is `ConditionExpression="attribute_not_exists(source_entry_id)"` on the `put_item` call; a `ConditionalCheckFailedException` means the entry was already posted and is silently skipped.

### 3.2 Chart-of-accounts addition in `T.gl_accounts`

The `seed_default_chart()` function in `app/services/gl_accounts.py` (OFB-013) gains one more default account. The item written uses the same shape as all other seeded accounts:

| Attribute | Value |
|---|---|
| `account_code` | `"6000"` (PK / hash key on `T.gl_accounts`) |
| `name` | `"Salaries & Wages Expense"` |
| `account_class` | `"expense"` |
| `normal_balance` | `"debit"` |
| `is_active` | `True` |
| `seeded` | `True` |
| `description` | `"Gross payroll expense for all disbursed payroll runs"` |

The seed uses `ConditionExpression="attribute_not_exists(account_code)"` so re-seeding on `just restart` is a no-op.

### 3.3 No schema changes to existing tables

`T.billing`, `T.hr`, `T.gl_journal`, and `T.gl_accounts` schemas are unchanged. No new GSIs, no new `attr_types` entries, no `local-ddb-init.py` changes are needed for HRM-010 — the `GSI_LEDGER_DATE` index on `billing` already indexes all `ledger_date`-bearing rows including `PAYROLL#*` partitions.

## 4. API / Service Design

HRM-010 has no HTTP endpoints of its own. Its deliverable is a pure service-layer extension: one mapping entry added to `gl_posting.py` and one account added to `gl_accounts.py`'s seed list.

### 4.1 Modified file: `app/services/gl_accounts.py` (OFB-013 file)

Add the Salaries & Wages Expense account to the `_DEFAULT_ACCOUNTS` list consumed by `seed_default_chart()`:

```python
# HRM-010: Salaries & Wages Expense for payroll GL hook
{
    "account_code": S.hr_payroll_expense_account_code,  # default "6000"
    "name": "Salaries & Wages Expense",
    "account_class": "expense",
    "normal_balance": "debit",
    "is_active": True,
    "seeded": True,
    "description": "Gross payroll expense for all disbursed payroll runs",
},
```

`seed_default_chart()` already iterates `_DEFAULT_ACCOUNTS` and calls `put_item` with `ConditionExpression="attribute_not_exists(account_code)"` for each entry. No other change is needed in `gl_accounts.py`.

### 4.2 Modified file: `app/services/gl_posting.py` (OFB-014 file)

#### 4.2.1 Mapping dispatch entry

The OFB-014 mapper uses a dispatch table keyed on `(entry_type, reason)` (or `reason` alone for well-known reasons). HRM-010 adds:

```python
# HRM-010: payroll disbursement → Dr Salaries & Wages Expense / Cr Cash
("debit", "payroll"): _payroll_journal_lines,
```

where `_payroll_journal_lines` is:

```python
def _payroll_journal_lines(
    item: Dict[str, Any],
    *,
    cash_account_code: str,
) -> List[Dict[str, Any]]:
    """Return the two-line journal for a payroll ledger row.

    Always balanced: debit amount == credit amount == item["amount_cents"].
    Raises ValueError if hr_payroll_gl_posting_enabled is False (caller
    should not have dispatched to this function in that case).
    """
    if not S.hr_payroll_gl_posting_enabled:
        raise ValueError("hr_payroll_gl_posting_enabled is False; mapping should not be invoked")
    amount = int(item["amount_cents"])
    return [
        {"account_code": S.hr_payroll_expense_account_code, "side": "debit",  "amount_cents": amount},
        {"account_code": cash_account_code,                  "side": "credit", "amount_cents": amount},
    ]
```

The `cash_account_code` is resolved once at startup (or at the first posting call) by `_resolve_cash_account()`, which queries `T.gl_accounts` for the single active account with `account_class="asset"` and `name` matching the conventional Cash/Bank account (OFB-013 seeds it as account code `"1000"` by convention). HRM-010 passes it as a module-level cached value so the lookup is not repeated per-entry.

#### 4.2.2 Gate check in the main dispatch loop

The outer dispatch loop in `gl_posting.py` (OFB-014) already checks `S.gl_double_entry_enabled`. HRM-010 adds a second early-exit to the payroll branch:

```python
if item.get("reason") == "payroll" and not S.hr_payroll_gl_posting_enabled:
    # payroll entries are skipped when the HR GL sub-flag is off,
    # even if gl_double_entry_enabled is on.
    _metrics_skipped.increment("reason=payroll,gate=hr_payroll_gl_posting_disabled")
    continue
```

This ensures that enabling the main GL flag (`GL_DOUBLE_ENTRY_ENABLED=1`) while leaving `HR_PAYROLL_GL_POSTING_ENABLED=0` does not post payroll journals.

#### 4.2.3 Balance invariant enforcement

The OFB-014 mapper already verifies `sum(d["amount_cents"] for d in lines if d["side"]=="debit") == sum(d["amount_cents"] for d in lines if d["side"]=="credit")` before persisting. An unbalanced result raises `GLImbalanceError` (or equivalent), which is logged and the entry is skipped (not persisted). For the payroll mapping the two amounts are always equal (both are `item["amount_cents"]`), so this check always passes — but the invariant check still runs.

#### 4.2.4 Idempotency guard

The OFB-014 idempotency mechanism — one journal per source `entry_id` — applies automatically to payroll entries because `entry_id` is deterministic (HRM-008 §4.2): `f"payroll_{sha256_str('payroll:{payroll_run_id}:{employment_id}')[:32]}"`. The `ConditionExpression="attribute_not_exists(source_entry_id)"` guard on `T.gl_journal` prevents duplicate journal entries on replay.

### 4.3 No new router, no new HTTP endpoint

HRM-010 does not expose any new API surface. The GL poster runs in the background (started by OFB-014's `start_gl_poster_task` startup hook, gated on `S.gl_double_entry_enabled`), and consuming `reason="payroll"` entries is entirely internal.

## 5. Detailed Behavior & Edge Cases

### 5.1 Both flags required for any journal to be written

A payroll ledger row receives a journal entry only when **both** of the following are `True`:
- `S.gl_double_entry_enabled` (OFB-014 master GL switch)
- `S.hr_payroll_gl_posting_enabled` (HRM-001 HR sub-gate)

When either is `False`, the payroll ledger row passes through the GL poster loop and is counted in the "skipped" metrics bucket. The billing table and the `T.hr` table are entirely unaffected.

### 5.2 Idempotent replay — one journal per source `entry_id`

The `entry_id` on every payroll billing row is deterministic from `(payroll_run_id, employment_id)` (HRM-008 §4.2). The GL poster can replay the same date bucket multiple times without producing duplicate journal entries because the `ConditionalCheckFailedException` path on `T.gl_journal` is treated as "already done". This mirrors the pattern used by `app/services/cart_reminders.py` (`_RECOVERY_CONSUMED_PK_PREFIX` at `cart_reminders.py:41`) for one-time-use recovery tokens.

### 5.3 Unresolvable Cash account code

If `T.gl_accounts` does not contain an active Cash/Bank account (e.g., the chart was not seeded, or the account was disabled), `_resolve_cash_account()` returns `None`. In that case the GL poster logs a warning and skips the entry — it does not crash the poster loop. The entry remains in the ledger and will be re-processed on the next poster run once the account is available (idempotency guarantee). This "fail-open for the poster, skip the entry" approach matches the OFB-014 design for unknown mapping types.

### 5.4 Unresolvable expense account code

If `S.hr_payroll_expense_account_code` (default `"6000"`) does not match any active account in `T.gl_accounts`, the same skip-with-warning behavior applies. The most common cause is deploying HRM-010 before OFB-013 (or before the chart is seeded). The fix is to run `seed_default_chart()` (which is idempotent) and let the poster retry.

### 5.5 Zero-amount payroll lines

HRM-008 allows zero-`gross_cents` lines (valid for unpaid leave). A zero-amount journal entry (`debit 0 / credit 0`) passes the balance invariant but is meaningless in the GL. The mapper should gate on `item["amount_cents"] > 0` and skip zero-amount entries with a debug log rather than writing a zero-value journal row.

### 5.6 `reason="payroll"` entries on non-`PAYROLL#` PK partitions

The GL poster does not restrict itself to `PAYROLL#` PK partitions — it queries by `ledger_date`. A hypothetical future use of `reason="payroll"` on a user partition would also map to the same journal template. This is unlikely (only `post_payroll_run` in `hr_payroll.py` ever sets `reason="payroll"`), but the mapping is key-name-agnostic and correct regardless of partition.

### 5.7 Flag changed mid-run

If `hr_payroll_gl_posting_enabled` is toggled from `False` to `True` after payroll runs have already been posted (their ledger entries exist but no journal entries were written), the next GL poster cycle will process those entries from the date-range backfill path (OFB-014 provides a `post_date_range(start, end)` backfill function). No special HRM-010 migration is needed; idempotency ensures no duplicates when the backfill runs over previously-skipped entries.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 — same code path both environments

The GL posting service uses `T.gl_journal` and `T.gl_accounts`, which are backed by DynamoDB Local in dev and real DynamoDB in prod. The `_safe_table` pattern in `app/core/tables.py` handles the endpoint URL difference transparently. There is no `dev_mode` conditional branch in the payroll journal mapping — the mapping function executes identically in both environments.

### 7.2 Idempotency

Three layers of idempotency protect against duplicate journal entries:

1. **Source `entry_id` determinism (HRM-008)**: The billing `entry_id` is `f"payroll_{sha256_str('payroll:{run_id}:{emp_id}')[:32]}"` — fixed for a given `(run, employment)` pair regardless of retry timing.
2. **GL poster's `attribute_not_exists(source_entry_id)` guard (OFB-014)**: The conditional `put_item` on `T.gl_journal` fails silently on replay.
3. **HR payroll's run-level status gate (HRM-008)**: `post_payroll_run` only posts `APPROVED` runs; re-posting a `POSTED` run is a no-op at the HR layer before the billing layer is ever reached.

### 7.3 Audit trail

The payroll ledger row written by HRM-008 already carries `employment_id`, `party_id`, and `payroll_run_id` in the DynamoDB item (via the `extra` dict). The journal entry written by HRM-010 denormalizes the same fields, so an auditor can cross-reference `T.gl_journal` → `T.billing` → `T.hr` without a scan.

### 7.4 No user-facing data exposure

The GL poster runs as a background worker process. It does not expose any HTTP endpoints. No user-controlled input can influence the journal mapping: `reason="payroll"` is set only by `post_payroll_run` in `hr_payroll.py`, which is an admin-only operation gated by `require_admin_or_root_csrf` from `app/auth/policy.py:100` (HRM-009; pattern verified in `app/routers/admin_notifications.py:13`).

### 7.5 Account code injection

`S.hr_payroll_expense_account_code` is an operator-supplied string loaded from the environment at process start. The GL poster uses it as a DynamoDB partition key lookup (`T.gl_accounts.get_item(Key={"account_code": code})`). DynamoDB key lookups are not SQL-injectable; the value is passed as a typed string attribute. No sanitization beyond type-checking is required.

## 8. Backward Compatibility & Migration

### 8.1 Existing billing rows are unaffected

`T.billing` is not modified. The `PAYROLL#*` partitions written by HRM-008 are new; existing `USER#*`, `PLATFORM#ESCROW`, and `PLATFORM#revenue` partitions are unchanged. With `gl_double_entry_enabled=False` (the default), the GL poster never runs and never reads any billing rows.

### 8.2 `T.gl_journal` is a new table (OFB-002)

`T.gl_journal` does not exist today. OFB-002 creates it. HRM-010 only writes to it; it never reads from `T.billing` in a way that could interfere with existing aggregations.

### 8.3 Chart of accounts is additive

HRM-010 adds one account (`"6000"` Salaries & Wages Expense) to `seed_default_chart()`. This is an append — no existing account is modified or removed. The `ConditionExpression="attribute_not_exists(account_code)"` guard on the seed makes the addition a no-op on re-seed if the account already exists.

### 8.4 No `just restart` action beyond normal table recreation

`scripts/local-ddb-init.py` is not changed by HRM-010 (the `T.gl_journal` and `T.gl_accounts` table definitions are added by OFB-002). Running `just restart` after HRM-010 merges will recreate all tables (including GL ones, if OFB-002 has also merged) and re-seed the chart via startup hook — this is the expected behaviour.

### 8.5 Production deployment order

To deploy HRM-010 safely in production:
1. Ensure OFB-002, OFB-013 (chart seed), and OFB-014 (GL poster) have shipped.
2. Ensure HRM-001 through HRM-009 have shipped.
3. Deploy HRM-010 (adds payroll mapping entry + chart account).
4. Set `HR_PAYROLL_GL_POSTING_ENABLED=1` only after confirming that `GL_DOUBLE_ENTRY_ENABLED=1` and the chart is seeded.
5. Historical payroll ledger rows can be backfilled via OFB-014's `post_date_range(start, end)` command without duplication.

## 10. Open Questions / Assumptions

1. **Assumption: `gl_posting.py` dispatch table is keyed on `(entry_type, reason)`.** The OFB-014 spec describes a mapping but does not prescribe the exact dict structure. If OFB-014 uses a different dispatch mechanism (e.g., a `reason`-only key, or a plugin registry), the `("debit", "payroll")` entry above must be adapted. The balance invariant and idempotency mechanism are unaffected.

2. **Assumption: `T.gl_journal` PK is `journal_id` with `source_entry_id` as an indexed attribute for the idempotency `attribute_not_exists` check.** OFB-014 defines the `gl_journal` table schema. If the idempotency key is structured differently (e.g., `source_entry_id` is the PK itself), the `_payroll_journal_lines` function above may need adjustment. The critical invariant is that one journal entry is written per source `entry_id`.

3. **Assumption: Cash/Bank account code is resolvable from `T.gl_accounts` by `account_class="asset"` and a conventional `name` prefix.** OFB-013 seeds the Cash/Bank account but does not specify whether its code is `"1000"`, `"1010"`, or another value. HRM-010 resolves it at runtime from the chart rather than hard-coding it — this is correct regardless of the exact code OFB-013 chooses.

4. **Assumption: The GL poster runs as a background task (`start_gl_poster_task`), not inline during payroll posting.** If OFB-014 wires the poster inline (e.g., as a post-write hook called synchronously inside `post_payroll_run`), HRM-010 would need to adapt. The offline test approach (patching `_post_one_entry`) remains valid either way.

5. **Assumption: `T.gl_accounts` uses `account_code` as the DynamoDB hash key.** This is the natural choice for a chart-of-accounts table and is consistent with OFB-013's description of CRUD keyed on account code. If OFB-013 uses a different key structure, the `seed_default_chart` append above must be adjusted.

6. **Assumption: `S.gl_double_entry_enabled` is the correct attribute name on the `S` singleton.** OFB-002 adds this setting using `GL_DOUBLE_ENTRY_ENABLED` as the env var (per `OFBIZ_COMMERCE_TICKETS.md:35`). The attribute naming convention in `app/core/settings.py` maps env vars to lowercase underscore names, making `s.gl_double_entry_enabled` the expected attribute. If OFB-002 uses a different attribute name, update the gate check in §4.2.2.

7. **Open: Should a failed journal write (e.g., `T.gl_journal` table does not exist) leave the payroll run in `POSTED` state?** HRM-008 transitions the run to `POSTED` before HRM-010's GL hook runs (the GL poster processes entries asynchronously from the `GSI_LEDGER_DATE` backlog). So yes — a GL failure after a successful payroll post should not roll back the payroll status. The GL poster retries on the next cycle. This is consistent with the `best-effort` GL design in OFB-014.
