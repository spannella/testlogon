# ECM-010 — Convert reservations → committed inventory on purchase

## 1. Summary & Goal

When `STORE_INTEGRATION_ENABLED` and `INVENTORY_RESERVATIONS_ENABLED` are both on,
`purchase_cart` must convert each cart line's active soft-reservation into a
committed on-hand decrement via `inventory.commit_reservation` (OFB-004) instead of
the current direct `stock_count` decrement against the catalog table. The catalog
`stock_count` column is preserved as a denormalized mirror so the existing Catalog UI
badge (`frontend/src/pages/shop/Catalog.tsx`) keeps working without change. With either
flag off the existing stock-decrement path runs byte-for-byte unchanged.

A pre-commit failure (order creation failure before the cart CAS commit) releases each
reservation that was committed in that run, restoring available stock. The cart CAS
already guarantees exactly-once execution; reservation commits reuse the same idempotent
guard in `_close_reservation` (`app/services/inventory.py:434`).

---

## 2. Context & Current State

### 2.1 Current purchase flow

`purchase_cart` (`app/services/shoppingcart.py:474`) runs the following sequence for
every cart item that has a `stock_count`:

1. **Stock gate** (`:498-538`): reads the catalog item, then does an atomic
   `UPDATE … SET stock_count = stock_count - :qty … ConditionExpression stock_count >= :qty`
   (the actual `T.catalog.update_item` call is at `:515`).
   On failure (`ConditionalCheckFailedException`) it rolls back previously decremented
   items and raises 409.
2. **Order creation** (`:581-594`): calls
   `commerce_order_service.create_order_from_line_items`.
3. **Cart CAS commit** (`:621-641`): sets `status = PURCHASED` with
   `ConditionExpression #status = :open`. Replay on `ConditionalCheckFailedException`
   returns the prior result at `:631`.
4. **Post-commit** (`:644-734`): entitlements, promo redemption, ledger, invoice, TTL
   removal — all best-effort.

The stock decrement at `:515` (`SET stock_count = stock_count - :qty`) is the only
point touching inventory. There is no OFBiz reservation call in this path today.

### 2.2 Soft-reservation service (ECM-008 / OFB-004)

`app/services/inventory.py` implements the full reservation lifecycle:

- `reserve(sku, quantity, *, cart_id, …)` (`:339`): decrements `available`, increments
  `reserved`, writes a `reservations` row with `status=active`.
- `commit_reservation(reservation_id, …)` (`:456`): calls `_close_reservation` with
  `terminal_status="committed"` — a `status = active` conditional update (idempotent
  under replay). On the first successful close it decrements `on_hand` and `reserved`
  by the reserved `quantity`; `available` is unchanged (already deducted at reserve
  time). Returns the reservation record on idempotent replays.
- `release_reservation(reservation_id, …)` (`:492`): `_close_reservation("released")`;
  restores `available += qty`, decrements `reserved`.
- Both commit and release are idempotent: `_close_reservation` returns `None` if the
  reservation is already terminal (`:450-452`).

ECM-008 (dependency) stores the `reservation_id` on each cart item row in
`T.shopping_cart` under the `reservation_id` attribute, keyed per-SKU with a
deterministic composite `{cart_id}#{sku}` dedup.

### 2.3 Catalog stock_count mirror

`_compute_stock_status` at `app/routers/catalog.py:94` reads `item.get("stock_count")`
directly from the catalog DynamoDB row. `CatalogItemOut` at `:122` surfaces it as
`stock_count`/`stock_status`. The Catalog badge (`frontend/src/pages/shop/Catalog.tsx`)
relies on this. This field must remain consistent with the OFBiz `on_hand` value or the
badge will mislead buyers.

### 2.4 Flags

- `S.inventory_reservations_enabled` (`app/core/settings.py:839`) — master switch for
  the OFBiz inventory module, default `false`.
- `STORE_INTEGRATION_ENABLED` — planned master-integration switch (ECM-002, not yet
  in `settings.py`; ECM-002 adds `S.store_integration_enabled`, default `false`).

### 2.5 Tables in scope

- `T.shopping_cart` — PK `USER#{sub}`, SK `CART#{id}` / `CART#{id}#ITEM#{sku}`.
  Cart items carry `reservation_id` (added by ECM-008).
- `T.inventory` — PK `sku`, SK `LOC#{location_id}`. Holds `on_hand`, `reserved`,
  `available`.
- `T.reservations` — PK `RES#{reservation_id}`, SK `META`. Holds `status`,
  `quantity`, `sku`, `cart_id`.
- `T.catalog` — PK `CAT#{category_id}`, SK `ITEM#{item_id}`. Holds `stock_count`.

|---|---|---|---|
| `GSI_CART` | `cart_id` (S) | `created_at` (N) | sparse; active reservations only (set on reserve, not cleared on commit/release — filter `status=active`) |

## 4. API / Service Design

All new logic lives in `app/services/shoppingcart.py`. No new endpoints or response
models are introduced by this ticket — the `purchase_cart` return dict is unchanged.

### 4.1 New helper: `_get_active_reservations_for_cart`

```python
def _get_active_reservations_for_cart(cart_id: str) -> List[Dict[str, Any]]:
    """Query GSI_CART for all active reservations belonging to cart_id.

    Returns raw DDB items (reservation_pk, sk, reservation_id, sku, quantity, …).
    Returns [] when the GSI has no results or the query fails (never raises).
    """
    try:
        resp = T.reservations.query(
            IndexName="GSI_CART",
            KeyConditionExpression=Key("cart_id").eq(cart_id),
            FilterExpression=Attr("status").eq("active"),
        )
        return resp.get("Items", [])
    except Exception:
        return []
```

Note: `FilterExpression` is applied client-side after the GSI page fetch; the GSI will
include committed/released rows once the cart advances. The filter is a safety net, not
a correctness mechanism — once committed, `_close_reservation` is a no-op on re-entry.

### 4.2 New helper: `_commit_cart_reservations`

```python
def _commit_cart_reservations(
    items: List[Dict[str, Any]],
    *,
    user_sub: str,
) -> List[str]:
    """Commit every reservation_id found on the provided cart item dicts.

    Returns the list of reservation_ids that were successfully committed.
    Raises nothing; individual failures are logged but do not abort the loop.
    Idempotent: inventory.commit_reservation is a no-op if already committed.
    """
    committed: List[str] = []
    for cart_item in items:
        rid = cart_item.get("reservation_id")
        if not rid:
            continue
        try:
            inventory.commit_reservation(rid, user_sub=user_sub)
            committed.append(rid)
        except HTTPException as exc:
            if exc.status_code == 404:
                continue  # reservation missing — treat as already committed
            _log_reservation_error("commit", rid, exc)
        except Exception as exc:
            _log_reservation_error("commit", rid, exc)
    return committed
```

### 4.3 New helper: `_release_cart_reservations`

```python
def _release_cart_reservations(
    items: List[Dict[str, Any]],
    *,
    user_sub: str,
    reason: str = "purchase_failed",
) -> None:
    """Release active reservations for all cart items (pre-commit failure path).

    Uses the reservation_id stored on each cart item dict. Falls back to a
    GSI_CART scan for any items missing reservation_id (e.g. added before ECM-008).
    Best-effort: individual failures are silently swallowed.
    """
    seen: set[str] = set()
    for cart_item in items:
        rid = cart_item.get("reservation_id")
        if rid:
            seen.add(rid)
            try:
                inventory.release_reservation(rid, reason=reason, user_sub=user_sub)
            except Exception:
                pass
    # Fallback: catch any reservations not stored on the item row.
    cart_id = (items[0].get("cart_id") if items else None)
    if cart_id:
        for raw in _get_active_reservations_for_cart(cart_id):
            rid = raw.get("reservation_id")
            if rid and rid not in seen:
                try:
                    inventory.release_reservation(rid, reason=reason, user_sub=user_sub)
                except Exception:
                    pass
```

### 4.4 New helper: `_mirror_stock_count`

```python
def _mirror_stock_count(
    cat_id: str,
    item_id: str,
    inventory_sku: str,
    location_id: str = inventory.DEFAULT_LOCATION,
) -> None:
    """Write the OFBiz on_hand - reserved value back to catalog.stock_count.

    This keeps the legacy CatalogItemOut badge accurate. Best-effort: any error
    is silently swallowed so it never blocks purchase completion.
    """
    try:
        rec = inventory.get_inventory(inventory_sku, location_id)
        if rec is None:
            return
        new_sc = max(0, rec["on_hand"] - rec["reserved"])
        T.catalog.update_item(
            Key=_catalog_item_key(cat_id, item_id),
            UpdateExpression="SET stock_count = :sc, stock_updated_at = :now",
            ExpressionAttributeValues={":sc": new_sc, ":now": _now_iso()},
        )
    except Exception:
        pass
```

`inventory_sku` is the SKU as stored in the OFBiz inventory table — for catalog items
this is `item.get("sku")` from the cart item row (same SKU used by ECM-008 to place the
reservation).

### 4.5 Modified function: `purchase_cart`

The change is additive and flag-gated. The existing direct catalog `stock_count`
decrement block (`:498-538`) is wrapped with a flag check:

```python
# ── ECM-010: Reservation-aware stock commit ──
_reservations_path = (
    _integration_enabled("inventory_reservations")  # S.store_integration_enabled
    and _flag_on()                                  # S.inventory_reservations_enabled
)

if _reservations_path:
    # All items that carry a reservation_id will be committed via OFBiz.
    # Items without reservation_id (legacy/unlimited stock) fall through
    # to the existing direct-decrement below only if stock_count is set.
    pass  # reservations committed after order creation (see post-CAS block)
else:
    # EXISTING path — unchanged
    for cart_item in items:
        ...  # lines :500-538 verbatim
```

The actual `_commit_cart_reservations` call is placed **after** order creation and
**before** the cart CAS commit so that a reservation release is possible if order
creation raises (pre-commit release window). The sequence becomes:

```
1. [flag OFF]  stock_count decrement block  (unchanged)
2. promo code validation
3. final_total calculation
4. commerce_order_service.create_order_from_line_items   # raises on failure
5. [flag ON]   _commit_cart_reservations(items, user_sub=user_sub)
               _mirror_stock_count(…) for each item with reservation_id
6. Cart CAS (ConditionExpression #status = :open)
   ConditionalCheckFailedException → idempotent return (existing :629-641)
7. post-commit: entitlements, promo, ledger, invoice, TTL removal
```

If step 4 raises before the commit, the `except` block in the new code calls
`_release_cart_reservations(items, user_sub=user_sub, reason="order_creation_failed")`.

Full modified signature (unchanged externally):

```python
def purchase_cart(
    user_sub: str,
    cart_id: str,
    *,
    idempotency_key: str | None = None,
    promo_code: str | None = None,
    promo_code_id: str | None = None,
) -> Dict[str, Any]:
```

Return dict is byte-for-byte unchanged — ECM-010 adds no new keys.

## 5. Detailed Behavior & Edge Cases

### 5.1 Happy path (flags ON, reservations present)

1. All cart items have `reservation_id` set by ECM-008.
2. `purchase_cart` skips the direct `stock_count` decrement block.
3. `commerce_order_service.create_order_from_line_items` succeeds; `order_id` obtained.
4. For each cart item: `inventory.commit_reservation(reservation_id)` is called.
   - `_close_reservation("committed")` transitions the row atomically (`:441`).
   - `on_hand -= qty`, `reserved -= qty` on the inventory row (`:474-479`).
   - `available` is unchanged (already deducted at reserve time).
5. `_mirror_stock_count` writes the new `on_hand - reserved` value back to
   `catalog.stock_count`.
6. Cart CAS commits status to PURCHASED.

### 5.2 Idempotent replay (cart already PURCHASED)

The existing early-return at `shoppingcart.py:483-492` returns the stored result before
any stock operations are reached. No double-commit occurs.

### 5.3 Concurrent second call (races the CAS)

The cart CAS at `:621` (`ConditionExpression #status = :open`) ensures exactly one call
succeeds. The loser hits `ConditionalCheckFailedException`; the existing handler at
`:629-641` reads the cart, sees status `PURCHASED`, and returns the prior result.
Reservation commits by the losing call are idempotent no-ops (already terminal).

### 5.4 Pre-commit failure (order creation raises)

`commerce_order_service.create_order_from_line_items` (`:581`) raises before the CAS
commit. The new `except` block calls `_release_cart_reservations`. This restores
`available += qty`, `reserved -= qty` on each inventory row so the items can be
purchased again.

The cart status remains `OPEN`; the buyer can retry.

### 5.5 Cart item missing `reservation_id` (legacy item / ECM-008 off)

If `reservation_id` is absent on a cart item (added before ECM-008 was deployed, or
ECM-008 degrade path ran), ECM-010's commit loop skips it silently. To avoid a stuck
cart, the mirror-write loop also skips that item. The direct `stock_count` decrement
block is NOT run when the flag is on — so a cart item with no `reservation_id` and a
finite `stock_count` would bypass all stock control. This is acceptable only during a
transition window; the deployment order (ECM-008 must precede ECM-010 in production)
eliminates the race. See Section 8 for the migration note.

### 5.6 Partial commit failure (commit succeeds for 3 of 4 items, fails for 1)

`_commit_cart_reservations` continues on individual failures (non-404 exceptions are
logged). The cart CAS proceeds; the order is created. The uncommitted reservation will
be expired by the TTL loop (`expire_due_reservations`, `inventory.py:538`), which calls
`release_reservation`, restoring available. The catalog `stock_count` for that SKU will
drift until the TTL loop runs. This is an acceptable short-window inconsistency; the
SKU's inventory row remains accurate.

### 5.7 Mirror-write failure

`_mirror_stock_count` is best-effort (wrapped in `try/except`). A failure does not block
purchase. The catalog badge may briefly show a stale count; the next buy or admin stock
update will re-sync.

### 5.8 Items with `stock_count = None` (unlimited stock)

The existing guard at `shoppingcart.py:511` (`if sc is None: continue`) is preserved in
the legacy path. In the reservation path, unlimited-stock items have no reservation (ECM-
008 only reserves when `stock_count` is not None) so `reservation_id` is absent → the
loop skips them naturally.

### 5.9 `reserve` quantity vs. `stock_count` decrement quantity mismatch

ECM-008 reserves `cart_item.quantity` units. `commit_reservation` uses the `quantity`
stored on the reservation row (`:471`), not the cart item's current quantity. A quantity
change between add-to-cart and checkout (via `set_item_quantity`) must be handled by
ECM-008's adjust-reservation path (out of scope here). ECM-010 trusts the reservation's
quantity is current.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007

All DynamoDB reads and writes go through `T.inventory`, `T.reservations`, and `T.catalog`
— the same table handles in both dev (DynamoDB Local via moto) and prod (real DynamoDB).
There is no `dev_mode` branch in any of the new helpers. Mirror-write failures are silent
in both environments identically.

### Idempotency

- **Cart CAS** (`ConditionExpression #status = :open`, `shoppingcart.py:626`): guarantees
  at-most-once purchase per cart. Existing early-return at `:483` handles already-
  PURCHASED carts.
- **`commit_reservation`**: `_close_reservation` uses `ConditionExpression #status = :active`
  (`inventory.py:444`); a second call returns `None` (already terminal) and the function
  returns the existing record — no double decrement.
- **`release_reservation`**: same idempotent guard via `_close_reservation`.
- **Deterministic dedup**: ECM-008 uses `{cart_id}#{sku}` as the dedup key when creating
  reservations; ECM-010 reads whatever `reservation_id` is stored — no additional dedup
  needed here.

### Security

- No money movement occurs in ECM-010; billing ledger is untouched (the existing
  `record_cart_purchase` / `new_ledger_entry` call at `:668` is unchanged).
- `commit_reservation` requires `user_sub`; the value passed is the authenticated buyer's
  `user_sub` from the session dependency, same as today.
- No new endpoints are added; the existing `POST /ui/shoppingcart/carts/{cart_id}/purchase` endpoint
  (`app/routers/shoppingcart.py:175`; router prefix `/ui/shoppingcart` at `:50`) is unchanged.
- The `GSI_CART` index is internal; no new API surface exposes it.
- Reservation rows do not contain PII beyond `user_sub`; audit events emitted by
  `inventory.commit_reservation` (`:488`) follow the existing `alerts.audit_event` path.

## 8. Backward Compatibility & Migration

### Flag-off parity

With `STORE_INTEGRATION_ENABLED=false` OR `INVENTORY_RESERVATIONS_ENABLED=false`:

- `purchase_cart` executes the existing stock-decrement loop at `shoppingcart.py:498-538`
  verbatim — zero regressions.
- No calls to `inventory.*` are made.
- `T.reservations` is not read.
- `_mirror_stock_count` is not called.

### Deployment order (must be respected)

1. Deploy ECM-008 (reserve on add-to-cart) with `INVENTORY_RESERVATIONS_ENABLED=false`.
2. Enable `INVENTORY_RESERVATIONS_ENABLED=true` — new add-to-cart calls begin placing
   reservations; existing carts are unaffected (no `reservation_id` on their items).
3. Deploy ECM-010 code with both flags still off.
4. Enable `STORE_INTEGRATION_ENABLED=true` — purchase path switches to reservation commit.
5. Any open cart that was created before step 2 (no `reservation_id`) will skip the
   commit loop and fall through to legacy `stock_count` decrement for those items
   (because the flag check guard must be: "flag on AND cart_item.reservation_id is set;
   otherwise legacy"). Adjust the flag logic to per-item granularity (see Section 10.1).

### GSI_CART backfill

`GSI_CART` is a new GSI on the reservations table. In DynamoDB Local (dev), `just restart`
recreates the table. In production, `UpdateTable` adds the GSI asynchronously; queries
against it before backfill completes may miss rows. ECM-010's pre-commit release falls
back to per-item `reservation_id` from the cart item (the primary release path), so a
partial GSI backfill window is safe — the fallback loop in `_release_cart_reservations`
is a secondary safety net, not the primary mechanism.

## 10. Open Questions / Assumptions

**10.1 Per-item fallback for mixed carts (assumption)**

The spec assumes that for a cart item lacking `reservation_id` (e.g., created before
ECM-008 deployed), the flag-on path simply skips it in the commit loop and also skips
the legacy `stock_count` decrement. This means a mixed cart (some items with reservation,
some without) could bypass stock control for the legacy items during the transition
window. Assumption: the deployment window is short enough and carts are short-lived
enough that this is acceptable. If not, a per-item fallback is needed: if flag on but
`reservation_id` absent and `stock_count` is finite, fall back to direct decrement for
that item only.

**10.2 `inventory_sku` mapping from cart item to OFBiz SKU (assumption)**

ECM-010 assumes `cart_item["sku"]` is the same SKU key used when creating the
reservation in ECM-008 and stored in the inventory row (`T.inventory`). If PRD
variants (ECM-004/ECM-007) introduce a separate OFBiz SKU namespace, the mapping must
go through the variant→SKU resolver. This ticket assumes 1:1 SKU identity.

**10.3 `_mirror_stock_count` SKU→catalog-item mapping (RISK — assumption incorrect)**

`_mirror_stock_count` receives `cat_id` and `item_id` from the cart item's
`category_id`/`item_id` fields. **Verified: `add_catalog_item` at `shoppingcart.py:370`
does NOT currently pass `category_id` or `item_id` to `add_item` (`shoppingcart.py:390-397`),
so cart items created via `add_catalog_item` today do NOT carry these fields.** ECM-008
must explicitly persist `category_id` and `item_id` onto the cart item row when placing
a reservation for a catalog item. ECM-010's `_mirror_stock_count` must skip silently if
either field is absent (the loop skips items without `reservation_id` anyway, but this
is a separate gap). Pure-commercial line items similarly lack these fields.

**10.4 Location ID for inventory commits (assumption)**

`inventory.commit_reservation` reads `location_id` from the reservation row itself
(`:470`), not from the cart item. Assumption: ECM-008 passes `location_id=DEFAULT_LOCATION`
("warehouse") when reserving catalog items, consistent with the single-location Phase-1
scope.

**10.5 Release path for the cart-CAS loser (assumption)**

If the cart CAS fails (concurrent second purchaser) after reservations were committed
by the loser, those reservations are already `committed` — irreversible. The assumption
is that this cannot happen because the cart CAS is the single-winner gate and only one
caller reaches the commit block. In a multi-process deployment the CAS still serializes
correctly; no additional guard is needed.

**10.6 `GSI_CART` production backfill window (assumption)**

Adding a new GSI to the `reservations` table in production requires an `UpdateTable`
call that triggers an async backfill. The assumption is that the time between enabling
the GSI and enabling `STORE_INTEGRATION_ENABLED=true` is long enough for backfill to
complete, or that the primary per-item release path (using `reservation_id` from the
cart item row) makes the GSI fallback non-critical during backfill.
