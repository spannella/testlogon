# PRD-010 — Product associations service

**Type:** Feature | **Priority:** P1 | **Estimate:** 3 days
**Milestone:** 4 — Bundles / Kits & Associations

---

## 1. Summary & Goal

PRD-010 creates `app/services/product_associations.py`, the pure service layer implementing non-variant, non-bundle product associations (OFBiz `ProductAssoc` types: SUBSTITUTE, COMPLEMENT, UPGRADE, MANUF). These associations power "related items", "customers also bought", "substitute products", and "frequently paired with" surfaces on the storefront and are consumed by the ECM eCommerce-integration module in a later milestone.

Key responsibilities:

1. **Add an association** between a source item and a target item of a specific type, using a deterministic id (`sha256(from_item_id + assoc_type + to_item_id)`) for idempotent upsert.
2. **Remove an association** by `assoc_id`.
3. **List associations** originating from a source item, with optional type filtering, returning hydrated target-item summaries resolved via `_find_item_by_id`.
4. **Flag gate** — all public functions are gated behind `S.product_depth_enabled` and `S.product_depth_assocs_enabled`; with both flags off the module is dormant.

No router endpoints ship in this ticket — those are PRD-011.

## 2. Context & Current State

### 2.1 Scalar catalog item and `_find_item_by_id`

The live catalog item lives on `T.catalog` (`app/core/tables.py:99`, table name from `S.catalog_table_name` at `app/core/settings.py:832`). Items are keyed `PK=CAT#{category_id}`, `SK=ITEM#{item_id}`, `entity="item"`. The `_catalog_item_out` projection at `app/routers/catalog.py:107` returns a `CatalogItemOut` (`app/models.py:672`) with fields `category_id` (:673), `item_id` (:674), `name` (:675), `description` (:676, Optional), `price_cents` (:677), `currency` (:678), and `image_urls` (:679). No association fields exist on `CatalogItemOut` today; PRD-003 §3.9 extends it additively with `product_type`, `variant_count`, `has_features`, and `bundle_component_count` optional fields — there is **no** `has_associations` field in PRD-003. PRD-010 does not require a new sentinel on `CatalogItemOut`; the `target_item` field in `ProductAssocOut` carries the hydrated summary directly.

`_find_item_by_id` at `app/routers/catalog.py:702` resolves a bare `item_id` to its DDB row via the `ByItemId` GSI on `T.catalog` (added in GAP-0348/SHOP-001, declared in `scripts/local-ddb-init.py:121-124`). It returns `None` when no `entity="item"` row matches. PRD-010 calls this helper to validate that both source and target items exist before writing an association row, and again during `list_associations` to hydrate target summaries.

Per the pattern established in PRD-009 §2.8, PRD-010 avoids importing from `app/routers/catalog.py` at module level by using a lazy local import (the same `_record_timeline` / lazy-import idiom used in `app/services/ec2_launcher.py:24-42` and `app/services/k8s_launcher.py:37`) or awaiting the `catalog_helpers.py` extraction that PRD-007 may establish. Note: `_record_timeline` lives in `ec2_launcher.py` / `k8s_launcher.py`, not in `instance_monitoring.py` — the lazy import flows in the opposite direction (launchers import from `instance_monitoring`).

### 2.2 `T.product_depth` and the feature flag

PRD-002 installs:

- `T.product_depth` — `app/core/tables.py` field `product_depth`, table name from `S.product_depth_table_name` (default `"product_depth"`, env `PRODUCT_DEPTH_TABLE_NAME`). This table does **not** yet exist in `app/core/tables.py` or `scripts/local-ddb-init.py` — PRD-002 adds it. PRD-010 depends on PRD-002 shipping first.
- `S.product_depth_enabled` (env `PRODUCT_DEPTH_ENABLED`, default `False`) — the master switch (`app/core/settings.py` near `:832`). Not yet present in the codebase; added by PRD-002.
- `S.product_depth_assocs_enabled` (env `PRODUCT_DEPTH_ASSOCS_ENABLED`, default `True` when master is on) — the associations sub-flag. **RISK: PRD-002 §4.1 defines sub-flags only for `variants`, `bundles`, `features`, and `price_components`; there is no `product_depth_assocs_enabled` in PRD-002's settings block.** PRD-010 must either (a) add this sub-flag itself in `app/core/settings.py` alongside the PRD-002 block, or (b) treat the master flag `product_depth_enabled` as sufficient gating without a separate assocs sub-flag. The flag is absent from the codebase today regardless.

The `product_depth` table schema (established by PRD-002, documented in `docs/ofbiz/specs/PRD-002.md:117-166`) has `PK` (String) / `SK` (String) and five GSIs. The one relevant to associations is `ByAssocSource`:

| GSI | Hash key | Sort key | Numeric? |
|---|---|---|---|
| `ByAssocSource` | `GSI_ASSOC_PK` (S) | `GSI_ASSOC_SK` (S) | No — String type, no `attr_types` entry needed |

`GSI_ASSOC_PK` value: `"ASSOC_SRC#{from_item_id}"`. `GSI_ASSOC_SK` value: `"{assoc_type}#{assoc_id}"`. This String sort key enables type-filtered queries via `begins_with("substitute#")` or `begins_with("complement#")` (lowercase enum values per PRD-003 §3.7) without a FilterExpression, and a full listing via `begins_with("")` (no prefix restriction). The other four GSIs (`ByVirtualParent`, `ByParent`, `ByFeatureCategory`, `ByItemPrice`) are used by other PRD services and are not touched by PRD-010.

### 2.3 Association types (OFBiz mapping)

The four supported types map directly from OFBiz `ProductAssoc.assocTypeId`:

| PRD-010 `assoc_type` (DDB value, per PRD-003 §3.7) | OFBiz type | Storefront meaning |
|---|---|---|
| `substitute` | `PRODUCT_SUBSTITUTE` | "Similar product, could replace this one" |
| `complement` | `PRODUCT_COMPLEMENT` | "Frequently bought together / cross-sell" |
| `upgrade` | `PRODUCT_UPGRADE` | "Premium version of this product / upsell" |
| `manuf` | `MANUF_COMPONENT` | "Used in manufacturing / bill of materials" |

Values are **lowercase** strings as prescribed by PRD-003 §3.2 (`docs/ofbiz/specs/PRD-003.md:83-90`). These are intentionally distinct from `PRODUCT_COMPONENT` (bundle/kit, handled by PRD-009 via `COMP#` rows) and `PRODUCT_VARIANT` (virtual↔variant, handled by PRD-007 via `VAR#` rows). PRD-010's associations only span these four types.

### 2.4 Deterministic-id idempotency pattern

`sha256` hex deterministic ids are established in `app/services/kyc_partner_api.py:120-126` (full digest) and used by PRD-007 for variant ids and by PRD-009 for component ids. PRD-003 §3.7 (`docs/ofbiz/specs/PRD-003.md:172`) specifies `assoc_id` as a **16-character** hex prefix. PRD-010 must use `:16` to match the model contract:

```python
assoc_id = hashlib.sha256(
    f"{from_item_id}\x00{assoc_type}\x00{to_item_id}".encode("utf-8")
).hexdigest()[:16]
```

The 16-character hex prefix is consistent with PRD-003 §5.6 (`docs/ofbiz/specs/PRD-003.md:296`) which explicitly states `sha256(from_item_id + assoc_type + to_item_id)[:16]`. **CORRECTED from `:32` — PRD-003 is the authoritative model spec.**

### 2.5 No billing or cart integration

PRD-010 is a pure metadata service. It does not write to `T.billing`, does not call `new_ledger_entry` (`app/services/billing_shared.py:224`), and does not call `refund_payment`. Associations are informational — they influence storefront display (related-product widgets) and potentially recommendation systems, but they do not affect cart pricing, inventory reservation, or payment flows. This constraint is additive and permanent.

### 2.6 Existing `now_ts()` and integer timestamps

All new DDB rows use integer Unix-second timestamps from `now_ts()` (defined in `app/core/time.py:2`, import: `from app.core.time import now_ts`; consistent with the rest of the platform as documented in `CLAUDE.md`). The `created_at` and `updated_at` attributes on association rows are integers, not ISO strings — unlike the existing catalog item rows which use `now_iso()` at `app/routers/catalog.py:47`. This is intentional: the `product_depth` table is a new service whose convention follows `now_ts()` throughout, consistent with PRD-007, PRD-008, and PRD-009.

### 2.7 `_require_category_owner` pattern

Ownership enforcement for mutation endpoints (add/remove) follows the pattern at `app/routers/catalog.py:247`: `_require_category_owner(category_id, user_sub)` resolves the category's `creator_id` and raises HTTP 403 if the caller is not the owner. Since associations are owned by the source item's creator, the association service accepts `user_sub` and stores it as `creator_id`; the router (PRD-011) is responsible for calling `_require_category_owner` before invoking the service functions.

## 3. Data Model

PRD-010 exclusively uses `T.product_depth`. No modifications to `T.catalog`, `T.billing`, `T.shopping_cart`, `T.orders`, or any other existing table.

### 3.1 Association row

Maps to OFBiz `ProductAssoc` with `assocTypeId` in {SUBSTITUTE, COMPLEMENT, UPGRADE, MANUF_COMPONENT} (`docs/ofbiz/specs/PRD-002.md:194`).

Written by `add_association`. Hard-deleted by `remove_association`.

| Attribute | Value | Notes |
|---|---|---|
| `PK` | `ITEM#{from_item_id}` | Source item partition |
| `SK` | `ASSOC#{assoc_type}#{assoc_id}` | Type-prefixed for begins_with filtering |
| `entity` | `"product_assoc"` | Discriminator |
| `assoc_id` | `sha256(from\x00type\x00to)[:16]` | Deterministic 16-char hex; idempotency key (PRD-003 §3.7) |
| `from_item_id` | `{from_item_id}` | Denormalized for projection |
| `to_item_id` | `{to_item_id}` | Denormalized for projection |
| `assoc_type` | `"substitute"` / `"complement"` / `"upgrade"` / `"manuf"` | Lowercase enum value (PRD-003 §3.7) |
| `sequence_num` | Integer ≥ 0 | Display sort order (caller-supplied, default 0) |
| `note` | Optional[str] | Free-text annotation (nullable) |
| `creator_id` | `{user_sub}` | Owning user |
| `created_at` | `now_ts()` — integer Unix seconds | Set on first write only |
| `updated_at` | `now_ts()` — integer Unix seconds | Updated on every upsert |
| `GSI_ASSOC_PK` | `"ASSOC_SRC#{from_item_id}"` | ByAssocSource partition key |
| `GSI_ASSOC_SK` | `"{assoc_type}#{assoc_id}"` | ByAssocSource sort key |

**SK prefix** `ASSOC#{assoc_type}#{assoc_id}` means (with lowercase enum values):
- `begins_with("ASSOC#substitute#")` returns only substitute rows.
- `begins_with("ASSOC#")` returns all association rows for a given source item (no type filter).

**No new GSI is required.** The `ByAssocSource` GSI was declared by PRD-002 (`docs/ofbiz/specs/PRD-002.md:149-152`). `list_associations` queries it by `GSI_ASSOC_PK="ASSOC_SRC#{from_item_id}"` with an optional `begins_with` on `GSI_ASSOC_SK`.

### 3.2 `scripts/local-ddb-init.py` change

No new table or GSI is needed. The `product_depth` table and `ByAssocSource` GSI were created by PRD-002. The `GSI_ASSOC_SK` attribute is a String — it does not appear in `attr_types` (confirmed in `docs/ofbiz/specs/PRD-002.md:163`). PRD-010 does not modify `scripts/local-ddb-init.py`.

### 3.3 DynamoDB access patterns

| Operation | DDB call | Key expression |
|---|---|---|
| `add_association` | `put_item` (unconditional upsert) | `PK=ITEM#{from}`, `SK=ASSOC#{type}#{id}` |
| `remove_association` | `delete_item` | Same PK/SK; raises 404 if item absent |
| `list_associations(item_id)` | `ByAssocSource` query | `GSI_ASSOC_PK="ASSOC_SRC#{item_id}"` |
| `list_associations(item_id, type="substitute")` | `ByAssocSource` query + begins_with | `GSI_ASSOC_SK` begins_with `"substitute#"` (lowercase) |
| `get_association(assoc_id)` (internal) | Direct PK+SK `get_item` | Requires `from_item_id` to reconstruct PK |

## 4. API / Service Design

The service module is `app/services/product_associations.py`. It is a pure Python module with no `APIRouter`; router endpoints are in PRD-011. All public functions raise `fastapi.HTTPException` on validation or storage errors.

### 4.1 Module-level flag helpers

```python
from app.core.settings import S
from app.core.tables import T

def _flag_on() -> bool:
    return (
        bool(getattr(S, "product_depth_enabled", False))
        and bool(getattr(S, "product_depth_assocs_enabled", True))
    )

def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="Product associations are not enabled")
```

Pattern follows `app/services/inventory.py:50-56` exactly (consistent with PRD-009 §4.1).

### 4.2 Enum and id helper

```python
from enum import Enum

# Internal alias; matches ProductAssocTypeEnum in app/models.py (PRD-003 §3.7,
# docs/ofbiz/specs/PRD-003.md:83-90). Values are lowercase per PRD-003.
class AssocType(str, Enum):
    SUBSTITUTE = "substitute"
    COMPLEMENT = "complement"
    UPGRADE    = "upgrade"
    MANUF      = "manuf"

def _assoc_id(from_item_id: str, assoc_type: str, to_item_id: str) -> str:
    """Deterministic 16-char hex id. sha256(from\x00type\x00to)[:16].
    Length matches PRD-003 §3.7 (docs/ofbiz/specs/PRD-003.md:172, :296).
    """
    import hashlib
    raw = f"{from_item_id}\x00{assoc_type}\x00{to_item_id}".encode("utf-8")
    return hashlib.sha256(raw).hexdigest()[:16]
```

### 4.3 `add_association`

```python
def add_association(
    from_item_id: str,
    assoc_type: AssocType,
    to_item_id: str,
    user_sub: str,
    sequence_num: int = 0,
    note: Optional[str] = None,
) -> Dict[str, Any]:
    """Add (or update) an association from source to target of the given type.

    1. _require_enabled()
    2. Validate assoc_type is a valid AssocType member; 422 otherwise.
    3. Assert from_item_id != to_item_id; 422 if equal ("Self-referential association").
    4. Assert source item exists on T.catalog via _find_item_by_id; 404 if absent.
    5. Assert target item exists on T.catalog via _find_item_by_id; 404 if absent.
    6. Compute assoc_id = _assoc_id(from_item_id, assoc_type, to_item_id).
    7. Build item dict with PK/SK, GSI keys, all attributes, now_ts() timestamps.
       If row already exists (checked via get_item before put), preserve created_at;
       update updated_at. For a pure upsert, use a conditional UpdateExpression for
       created_at preservation (SET updated_at=:now, ... IF attribute_exists → else
       put_item). In practice: attempt put_item with a ConditionExpression
       "attribute_not_exists(PK)" to detect first-create; on
       ConditionalCheckFailedException fall back to an update_item that sets
       updated_at, sequence_num, note but leaves created_at unchanged.
    8. Return the row as a dict.

    Idempotency: calling add_association with the same (from, type, to) triple is
    a no-op if sequence_num and note are unchanged; otherwise it updates those
    mutable fields (last-write-wins). The assoc_id is stable across calls.
    """
```

### 4.4 `remove_association`

```python
def remove_association(
    from_item_id: str,
    assoc_id: str,
    user_sub: str,
) -> None:
    """Remove an association by assoc_id from the given source item.

    1. _require_enabled()
    2. Reconstruct SK = "ASSOC#<type>#<assoc_id>" by querying the primary table
       for PK=ITEM#{from_item_id} with SK begins_with("ASSOC#") and filtering for
       the matching assoc_id attribute. This avoids storing the type in the URL
       while still enabling a direct delete_item call.
       Alternative (preferred for simplicity): the router passes the full
       assoc_type so the SK can be directly constructed without a pre-query.
       See §10 assumption A3.
    3. Call T.product_depth.delete_item(Key={"PK": pk, "SK": sk}) with
       ConditionExpression="attribute_exists(PK)"; on
       ConditionalCheckFailedException raise HTTP 404 ("Association not found").
    """
```

### 4.5 `list_associations`

```python
def list_associations(
    item_id: str,
    assoc_type: Optional[AssocType] = None,
    *,
    hydrate: bool = True,
    limit: int = 100,
    next_token: Optional[str] = None,
) -> Dict[str, Any]:
    """List outbound associations from item_id, optionally filtered by type.

    Returns:
    {
        "associations": [ProductAssocOut, ...],
        "next_token": Optional[str],
    }

    Access pattern:
    - Query ByAssocSource GSI: KeyConditionExpression=
        Key("GSI_ASSOC_PK").eq(f"ASSOC_SRC#{item_id}")
        [AND Key("GSI_ASSOC_SK").begins_with(f"{assoc_type.value}#") if type given]
        # assoc_type.value is lowercase, e.g. "substitute#", consistent with SK format
    - Pagination via ExclusiveStartKey decoded from next_token.

    Hydration (hydrate=True):
    - For each association row, call _find_item_by_id(to_item_id) to fetch the
      target item summary. Items no longer in the catalog (deleted) are omitted
      from the returned list (safe degradation — stale assoc rows are not an error).

    Safe to call on any item_id — returns empty list for items with no associations.
    With hydrate=False (internal use / bulk callers) returns raw assoc rows without
    target item resolution.
    """
```

### 4.6 `get_association` (internal helper)

```python
def _get_association_row(
    from_item_id: str,
    assoc_type: AssocType,
    to_item_id: str,
) -> Optional[Dict[str, Any]]:
    """Look up a single association row by its deterministic PK+SK. Returns None if absent."""
    assoc_id = _assoc_id(from_item_id, assoc_type.value, to_item_id)
    sk = f"ASSOC#{assoc_type.value}#{assoc_id}"
    resp = T.product_depth.get_item(
        Key={"PK": f"ITEM#{from_item_id}", "SK": sk}
    )
    return resp.get("Item")
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotency on `add_association`

The deterministic `assoc_id = sha256(from\x00type\x00to)[:16]` means the PK/SK composite `ITEM#{from}` / `ASSOC#{type}#{assoc_id}` is fully determined by the tuple. Calling `add_association` twice with the same (from, type, to) is an upsert:

- If `sequence_num` and `note` match the stored values: functionally a no-op (the row is re-written with an updated `updated_at`).
- If they differ: last-write-wins update of mutable fields; `assoc_id` and `created_at` are preserved.

This means duplicate calls from the frontend (e.g., double-click on "Add Related Product") are safe.

### 5.2 Self-referential association

`add_association` validates `from_item_id != to_item_id` before computing the id. A self-referential association (`from == to`) is semantically meaningless for all four types and raises HTTP 422 ("Cannot associate an item with itself").

### 5.3 Symmetric vs. directed associations

Associations are **directed**: `add_association(A, "complement", B)` does not automatically create `add_association(B, "complement", A)`. The storefront UI (ECM module, future milestone) is responsible for fetching associations in both directions if symmetric display is desired. This is a deliberate choice to avoid write amplification and to allow asymmetric relationships (e.g., A upgrades to B but not vice versa).

### 5.4 Stale target reference on `list_associations`

If a target item (`to_item_id`) is deleted from `T.catalog` after an association is created, `_find_item_by_id(to_item_id)` returns `None`. In this case, `list_associations` with `hydrate=True` **omits** that association from the returned list (safe degradation). The raw association row remains in `T.product_depth` and is not cleaned up automatically. A future garbage-collection pass or catalog-item delete hook could clean these up, but PRD-010 does not implement that.

With `hydrate=False`, stale rows are returned as-is (with `target_item=None`), giving the caller visibility into all raw association rows regardless of target existence.

### 5.5 Deletion of source item

If the source item is deleted from `T.catalog`, its association rows on `T.product_depth` are **not** automatically deleted. `list_associations` will still query and return (or omit on hydration failure) these rows. A catalog-item delete hook (if added) should call `remove_association` for each row, but this is out of scope for PRD-010.

### 5.6 Type filtering and GSI query

When `assoc_type` is provided to `list_associations`, the query uses:
```python
Key("GSI_ASSOC_PK").eq(f"ASSOC_SRC#{item_id}")
& Key("GSI_ASSOC_SK").begins_with(f"{assoc_type.value}#")
# assoc_type.value is lowercase, e.g. "substitute#" or "complement#"
```
This is an O(k) query where k = associations of that type, with no FilterExpression. The `ByAssocSource` GSI carries all projected attributes so no additional `get_item` calls are needed for the raw row data (only for hydrating the target item summary).

When no `assoc_type` is provided, the SK condition is omitted and all association rows for the source item are returned.

### 5.7 Max associations per source item per type

A cap of `S.product_depth_max_assocs_per_type` (env `PRODUCT_DEPTH_MAX_ASSOCS_PER_TYPE`, default `50`) is enforced in `add_association`:

```python
current_count = _count_associations(from_item_id, assoc_type)
if current_count >= S.product_depth_max_assocs_per_type:
    raise HTTPException(status_code=422, detail="Association limit reached for this type")
```

`_count_associations` is a count-only query against `ByAssocSource` using `Select="COUNT"`. This prevents unbounded growth in any one type bucket. The check is a best-effort guard (it does not use a DDB transaction), so a tiny race window exists if two concurrent requests both pass the check; the resulting over-count would be at most +1 per race and is tolerable.

### 5.8 `assoc_type` in `remove_association`

The SK `ASSOC#{type}#{assoc_id}` requires knowing the type to construct a direct `delete_item` call. The router (PRD-011) surfaces `DELETE /items/{id}/associations/{assoc_id}` without requiring the type in the URL. Two approaches:

1. **Preferred (simple)**: The router endpoint accepts `assoc_type` as a query parameter. This allows a direct SK construction.
2. **Alternative**: Perform a pre-query with `begins_with("ASSOC#")` filtered on the `assoc_id` attribute to find the row, then delete it by the discovered SK.

See §10 assumption A3 for the resolution.

### 5.9 Duplicate-type safety

Because `assoc_id` is derived from `(from, type, to)`, two calls to `add_association(A, "substitute", B)` and `add_association(A, "complement", B)` produce **different** `assoc_id` values and thus different SK rows — they co-exist. A source item can have the same target in multiple association types simultaneously (e.g., B is both a `substitute` and a `complement` for A). This is valid OFBiz semantics.

### 5.10 `sequence_num` sort

`list_associations` returns rows in the order returned by the `ByAssocSource` GSI query (sorted by `GSI_ASSOC_SK` = `"{type}#{assoc_id}"` lexicographically within a type). For display ordering, the caller can sort in Python by `sequence_num` after fetch. No secondary GSI for `sequence_num` ordering is required since the list is bounded (max 50 per type × 4 types = 200 rows at most for one source item).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

All DDB operations in `product_associations.py` use `T.product_depth` and `T.catalog` (via the lazy-imported `_find_item_by_id`). Both table handles resolve to DynamoDB Local (`DDB_ENDPOINT_URL=http://localhost:8001`) in dev and real DynamoDB in prod. There is no `S.dev_mode` branch anywhere in this service. Behavior is identical in both environments — same GSI query, same conditional write, same upsert logic. This follows the SECOPS-007 principle as documented in CLAUDE.md.

### Idempotency

- `add_association`: PK/SK is deterministic. An unconditional write (with `created_at` preservation on upsert) is used. Re-submitting the same (from, type, to) triple is safe and updates only `updated_at` and mutable fields.
- `remove_association`: calling on an already-removed association raises HTTP 404. The router (PRD-011) maps this to a user-visible "Association not found" message.
- `list_associations`: read-only; always idempotent.

### Access control

Every public write function (`add_association`, `remove_association`) accepts `user_sub` and stores it as `creator_id`. The service layer trusts that the caller (router, PRD-011) has already enforced ownership via `_require_category_owner(category_id, user_sub)` at `app/routers/catalog.py:247`. Ownership of an association is inherited from the source item's category ownership.

Read-only functions (`list_associations`, internal `_get_association_row`) perform no ownership checks, consistent with the existing read-only catalog endpoints (`list_items` at `app/routers/catalog.py:394`).

### Input validation

`assoc_type` is validated as an `AssocType` enum member before any DDB call. Invalid type strings are rejected with HTTP 422 before any write. `sequence_num` is bounded 0–10,000 (Pydantic `ge=0, le=10_000`). `note` is capped at 500 characters.

### Association flood protection

`add_association` checks the per-type association count before writing (§5.7). The check uses `Select="COUNT"` on the GSI — no row reads — and adds negligible latency.

## 8. Backward Compatibility & Migration

### With `PRODUCT_DEPTH_ENABLED=false` (default)

- `product_associations.py` public functions always raise HTTP 404 via `_require_enabled()`.
- Zero reads or writes to `T.product_depth`.
- `T.catalog` is untouched — no new reads or writes from this module.
- `_catalog_item_out` at `app/routers/catalog.py:107` continues to return `CatalogItemOut` with unchanged serialization — no association-related fields are added to `CatalogItemOut` by this ticket.
- `app/services/shoppingcart.py`, `app/services/billing_shared.py`, `app/routers/billing.py`, `app/services/inventory.py` are not modified.

### Existing scalar catalog items

Items with no `ASSOC#` rows on `T.product_depth` have zero outbound associations. `list_associations` returns `{"associations": [], "next_token": null}` for all such items. No migration or backfill of existing catalog data is required.

### Enabling the flag on a live system

`product_depth` is a new table created by PRD-002 with no existing data. Enabling `PRODUCT_DEPTH_ENABLED=true` on a live system with existing catalog items is safe: no `ASSOC#` rows exist yet, all association reads return empty, all write operations succeed normally. No migration is required.

### Removing an association type

The four types (`substitute`, `complement`, `upgrade`, `manuf`) are an additive enum. Adding new types in a future ticket requires only: (a) extending the `ProductAssocTypeEnum` / `AssocType` enum, (b) no schema change to `T.product_depth`. Removing a type is a breaking change (existing rows with that type become orphaned). Removal is out of scope.

## 10. Open Questions / Assumptions

**A1. `_find_item_by_id` import strategy.** This spec assumes PRD-007 establishes either a `catalog_helpers.py` extraction or a documented lazy-import pattern for service files that need `_find_item_by_id`. If neither is in place, PRD-010 uses a lazy local import inside each function that needs it, following the `_record_timeline` pattern in `app/services/ec2_launcher.py:24-42` (the local function body does `from app.services.instance_monitoring import record_timeline_event` to avoid a circular import). This avoids a circular import (service importing from a router). Assumption: the lazy-import approach is sufficient until a dedicated `app/services/catalog_helpers.py` is extracted.

**A2. `assoc_type` sub-flag granularity.** The spec assumes a single `product_depth_assocs_enabled` sub-flag gates all four association types. If independent flags per type (e.g., `product_depth_substitute_enabled`) are desired, they can be added later as additive settings without breaking any existing behavior. Current assumption: one sub-flag for all types is sufficient for MVP.

**A3. `remove_association` signature — type in URL or query param.** The spec describes two options for reconstructing the SK in `remove_association`. The **preferred approach** is to require `assoc_type` as a query parameter on `DELETE /items/{id}/associations/{assoc_id}` in the PRD-011 router, enabling a direct SK construction without a pre-query. This trades a slightly more verbose URL for elimination of a round-trip read. Assumption: PRD-011 will implement this convention; PRD-010's `remove_association` will accept `assoc_type: AssocType` as a required parameter.

**A4. Reverse-direction listing.** `list_associations(item_id)` lists only *outbound* associations (A is source). If "what items point TO me as a SUBSTITUTE?" is a required query, a `ByAssocTarget` GSI would be needed on `to_item_id`. Current assumption: inbound association listing is not required for the ECM integration milestone; it can be added by a future ticket with a new GSI on `T.product_depth` (no schema-breaking change, DynamoDB `UpdateTable` in prod).

**A5. Hydration N+1 performance.** `list_associations` with `hydrate=True` issues one `_find_item_by_id` GSI query per association row. For a list of 50 associations, this is 50 serial DDB reads. Future optimization: batch via `BatchGetItem` on `T.catalog` (using the known PK/SK of each target item). Current assumption: 50 reads at ~1ms each is acceptable for the initial implementation.

**A6. `sequence_num` as sort key.** The `ByAssocSource` GSI sorts by `GSI_ASSOC_SK = "{type}#{assoc_id}"` — this is lexicographic by type then by the sha256-derived id, not by `sequence_num`. Callers that want display-order sorting must sort in Python after fetch. Assumption: in-Python sort over a bounded list (max 200 rows) is sufficient; no secondary GSI on `sequence_num` is needed.

**A7. Bi-directional association enforcement.** Complement associations are typically symmetric in OFBiz (if A complements B, B complements A). PRD-010 does not auto-create the reverse direction. Assumption: the storefront or ECM module handles bi-directional display by calling `list_associations` in both directions; the service layer is not responsible for enforcing symmetry.
