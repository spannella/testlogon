# PRD-008 — Variant & feature router endpoints

**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days
**Milestone:** 3 — Variants & Features/Options

---

## 1. Summary & Goal

PRD-008 exposes the service functions from PRD-006 (`app/services/product_features.py`) and PRD-007 (`app/services/product_variants.py`) as HTTP endpoints registered in `app/routers/catalog.py`. All endpoints are gated behind `S.product_depth_enabled` and return `HTTP 501` ("Product depth is not enabled") when the flag is off. The existing catalog, cart, orders, and billing paths are byte-for-byte unchanged.

The eight endpoints added are:

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/ui/catalog/feature-categories` | Create a feature category (owner) |
| `POST` | `/ui/catalog/feature-categories/{fc_id}/values` | Add a feature value to a category (owner) |
| `POST` | `/ui/catalog/items/{item_id}/feature-categories` | Attach a feature category to an item (owner) |
| `GET` | `/ui/catalog/items/{item_id}/features` | List all attached feature categories + values |
| `POST` | `/ui/catalog/items/{item_id}/variants` | Create a variant from a feature-value selection |
| `GET` | `/ui/catalog/items/{item_id}/variants` | List variants with SKU, selected features, effective price |
| `DELETE` | `/ui/catalog/items/{item_id}/variants/{variant_id}` | Delete a variant |
| `PATCH` | `/ui/catalog/items/{item_id}/product-type` | Set/promote product type to virtual (or other) |

The `_catalog_item_out` helper at `app/routers/catalog.py:107` will be extended to populate the additive `product_type` and `variant_count` fields on `CatalogItemOut` (defined by PRD-003) by reading the `ITEM#{id}/TYPE` row and doing a count query on `ByVirtualParent` — only when `S.product_depth_enabled` is `True`.

## 2. Context & Current State

### 2.1 Existing catalog router

`app/routers/catalog.py` is a 1000-line module registered in `app/main.py:671` as `catalog_router` with prefix `/ui/catalog`. It is already fully populated with flat-item CRUD. The router has no concept of product types, variants, or feature categories today.

Key helpers in the existing router that PRD-008 reuses:

- `_find_item_by_id(item_id)` at `app/routers/catalog.py:702` — O(1) `ByItemId` GSI lookup; returns the full DDB row or `None`. This is the canonical way to resolve a bare `item_id` without knowing its `category_id`.
- `_require_category_owner(category_id, user_id)` at `app/routers/catalog.py:247` — reads `T.catalog.get_item(Key={...})` for the category META row and raises `HTTP 403` when `creator_id != user_id`. PRD-008 owns a parallel helper `_require_item_owner(item_id, user_sub)` that calls `_find_item_by_id` then extracts `creator_id` — same ownership semantics, different lookup path (item row rather than category META).
- `_catalog_item_out(item)` at `app/routers/catalog.py:107` — currently constructs `CatalogItemOut` with no `product_type`/`variant_count` fields. PRD-003 added those as optional fields defaulting to `None`/`None` on `CatalogItemOut` (`app/models.py:672`). PRD-008 extends `_catalog_item_out` to populate them when the flag is on.
- `encode_next_token` / `decode_next_token` at `app/routers/catalog.py:158,165` — base64-encoded JSON cursor, reused for variant/feature pagination.
- `now_iso()` at `app/routers/catalog.py:47` — ISO timestamp; service layer uses `now_ts()` (int Unix seconds) from `app/core/time.py:2`. Router endpoints call `now_iso()`; services use `now_ts()`. PRD-008 follows this existing split.

### 2.2 Auth dependency pattern

All existing catalog endpoints use `Depends(require_ui_session)` from `app/services/sessions.py:330` (imported at `app/routers/catalog.py:39`). This is a cookie+JWT session dependency returning `{"user_sub": str, "role": Role, ...}`. There is no admin-only endpoint in the catalog router today; the feature-category create/attach and variant create/delete operations are owner-gated by business logic, not by role. PRD-008 follows the same pattern: `Depends(require_ui_session)` on every endpoint, with ownership enforced in helper functions.

### 2.3 Flag gating convention

The canonical pattern for feature-flag gating in router endpoints is from `app/routers/catalog.py:591–636` (multipart conditional registration). For PRD-008, a simpler guard is used inside each handler, matching the inventory/returns pattern:

```python
# At the top of each PRD-008 endpoint handler:
if not getattr(S, "product_depth_enabled", False):
    raise HTTPException(status_code=501, detail="Product depth is not enabled")
```

Note: the inventory service's `_require_enabled()` at `app/services/inventory.py:54-56` raises `HTTP 404`, not `501`. PRD-008 uses `501` ("Not Implemented") to match the catalog router's own convention for unavailable features (`app/routers/catalog.py:592,605`). The `getattr(S, ..., False)` fallback idiom is the shared pattern.

## 3. Data Model

PRD-008 introduces no new DDB rows beyond those defined by PRD-006 and PRD-007. It does not modify `T.catalog`, `scripts/local-ddb-init.py`, `app/core/settings.py`, or `app/core/tables.py` — those changes are owned by PRD-002.

The one additive DDB write PRD-008 owns: none. All writes are delegated to the service functions.

The one additive DDB read PRD-008 introduces in `_catalog_item_out`: when `S.product_depth_enabled` is `True`, a `get_item(Key={"PK": f"ITEM#{item_id}", "SK": "TYPE"})` call on `T.product_depth` to populate `product_type`, and a `query(IndexName="ByVirtualParent", ...)` count to populate `variant_count`. These two extra reads are skipped when the flag is off — `product_type` remains `None`, `variant_count` remains `None`, and `has_features` remains `False`, giving byte-for-byte identical responses to today.

## 4. API / Service Design

### 4.1 New helper: `_require_item_owner`

Added to `app/routers/catalog.py` alongside `_require_category_owner` at `:247`:

```python
def _require_item_owner(item_id: str, user_sub: str) -> Dict[str, Any]:
    """Return the item row or raise 403/404.

    Calls _find_item_by_id (catalog.py:702) then checks creator_id.
    Raises 404 if item does not exist.
    Raises 403 if creator_id is set and does not match user_sub.
    """
    item = _find_item_by_id(item_id)
    if not item:
        raise HTTPException(status_code=404, detail="Item not found.")
    creator_id = item.get("creator_id")
    if creator_id and creator_id != user_sub:
        raise HTTPException(status_code=403, detail="Not authorized to manage this item.")
    return item
```

### 4.2 Extended `_catalog_item_out`

```python
def _catalog_item_out(item: dict) -> CatalogItemOut:
    # ... existing fields unchanged ...
    product_type = None
    variant_count = None
    has_features = False
    if getattr(S, "product_depth_enabled", False):
        try:
            from app.services import product_variants, product_features
            product_type = product_variants.get_product_type(item["item_id"])
            if product_type == "virtual":
                variants, _ = product_variants.list_variants(item["item_id"], limit=1000)
                variant_count = len(variants)
            feat_rows = product_features.list_product_features(item["item_id"])
            has_features = len(feat_rows) > 0
        except Exception:
            pass  # best-effort — never break existing item serialization
    return CatalogItemOut(
        # ... existing fields ...
        product_type=product_type,
        variant_count=variant_count,
        has_features=has_features,
    )
```

The `try/except` guard ensures that a misconfigured `T.product_depth` or a service error never corrupts the response for existing consumers. The lazy local import avoids circular imports (same pattern as `_record_timeline` in `app/services/ec2_launcher.py:24`, which uses a local import of `record_timeline_event` from `app/services/instance_monitoring` to break a circular dependency).

### 4.7 Route declaration order

The new routes must be declared **before** any existing wildcard routes that could shadow them. In particular:

- `/feature-categories` and `/feature-categories/{fc_id}/values` — these are entirely new path prefixes, no conflict.
- `/items/{item_id}/feature-categories`, `/items/{item_id}/features`, `/items/{item_id}/variants`, `/items/{item_id}/variants/{variant_id}`, `/items/{item_id}/product-type` — all added after the existing `/items/{item_id}/stock` and `/items/{item_id}/reviews` routes, using the same sub-path convention. FastAPI matches in declaration order; because these paths have distinct final segments (`feature-categories`, `features`, `variants`, `product-type`) there is no shadowing conflict with existing routes.

Note: `/items/search` at `app/routers/catalog.py:465` already uses the `search` literal before `{item_id}`, demonstrating the existing care taken for literal-vs-wildcard ordering. The same care applies here — all new literal sub-paths are safe.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off behavior

With `S.product_depth_enabled = False` (the default), every PRD-008 handler raises `HTTP 501 Not Implemented` with `detail="Product depth is not enabled"`. No DDB calls are made. The response body for all existing `/ui/catalog/*` endpoints is identical to today: `CatalogItemOut.product_type` is `None`, `variant_count` is `None`, `has_features` is `False`. These are additive optional fields that existing consumers (frontend, E2E tests, API clients) will silently ignore as per the PRD-003 contract.

### 5.2 Ownership chain for feature operations

Creating a feature value (`POST /feature-categories/{fc_id}/values`) requires that `ctx["user_sub"]` is the owner of the feature category (`FTCAT#{fc_id}/META.creator_id`). This is enforced inside `product_features.add_feature_value` via `_require_feature_category_owner`. The router does not re-check; it trusts the service layer to raise `HTTP 403`.

Attaching a feature category to an item (`POST /items/{item_id}/feature-categories`) requires:
1. Caller owns the item (checked in the router via `_require_item_owner`).
2. The feature category exists (checked in the service via `get_item`).
3. The feature category is NOT already attached (idempotent: if the `ITEM#{id}/FTAPPL#{fc_id}` row already exists, the conditional put raises `409`; the service catches it and re-returns the existing row — silent idempotency, not an error).

### 5.3 Variant creation pre-conditions

`POST /items/{item_id}/variants` delegates to `product_variants.create_variant` which enforces all pre-conditions (documented in `docs/ofbiz/specs/PRD-007.md §5`):
1. Item must exist.
2. Item must have `product_type = "virtual"` (TYPE row present with that value) — 422 if not.
3. `feature_values` must cover exactly all attached feature axes — 422 if any axis is missing or extra.
4. Each `feature_value_id` must exist in its `feature_category` — 422 if any value is unknown.
5. Deterministic `variant_id` — duplicate combination → 409.

The router handler re-surfaces the service's `HTTPException` unchanged. It does not catch and re-wrap them.

### 5.4 Listing variants on a non-virtual item

`GET /items/{item_id}/variants` calls `product_variants.list_variants(item_id, ...)`. A non-virtual item (no `VAR#` rows) returns `{"items": [], "next_token": null}` with `HTTP 200`. This is correct — the caller discovers the item has no variants rather than getting a 404.

### 5.5 Subscription access on read endpoints

Both `GET /items/{item_id}/features` and `GET /items/{item_id}/variants` check `can_access_creator(ctx["user_sub"], item.creator_id)` from `app/services/subscription_access.py` before returning data — consistent with `list_reviews` at `app/routers/catalog.py:839`. If the subscription check fails, `HTTP 403 "Subscription required"` is returned.

### 5.6 `variant_count` in `_catalog_item_out`

When `S.product_depth_enabled` is `True` and the item has `product_type = "virtual"`, `_catalog_item_out` performs a `list_variants(item_id, limit=1000)` call and takes `len(result)`. This is a single GSI query (O(1) in DDB terms), but it does add latency to all item-detail responses for virtual products. Since `list_variants` uses the `ByVirtualParent` GSI with `limit=1000` and most products have far fewer variants, this is acceptable. If the count exceeds 1000, it is reported as 1000+ (the service layer does not support COUNT queries on GSIs in moto, so an exact count requires fetching rows). This is flagged as a known trade-off in section 10.

### 5.7 Deleting a feature category that has attached products

`product_features.delete_feature_category` raises `HTTP 409 "Feature category is in use"` when any `FTAPPL#` row references it. This is enforced in the service layer; the router surfaces the error unchanged. The endpoint `DELETE /feature-categories/{fc_id}` is not in the PRD-008 surface (it is a future endpoint), but the service-layer guard is already available.

### 5.8 `sku_override` uniqueness

If `VariantCreateIn.sku_override` is provided, `product_variants.create_variant` validates that no existing variant for this parent has the same SKU (by scanning `VAR#` rows on the `T.product_depth` base table for the parent PK). This is a low-cardinality scan (bounded by the number of variants, typically < 100). If uniqueness fails, 409 is raised. The router does not add additional validation.

### 5.9 `has_features` field accuracy

`has_features` is populated by calling `product_features.list_product_features(item_id)` and checking `len > 0`. This is a `query` on `T.product_depth` with `PK=ITEM#{item_id}, SK begins_with "FTAPPL#"`. It is correct for all cases including the standalone-item path (returns `False`). It is wrapped in the `try/except` guard in `_catalog_item_out` so a DDB error never breaks existing serialization.

## 6. Feature Flag & Config

All settings keys are defined by PRD-002 in `app/core/settings.py` adjacent to the catalog block (`:832`). PRD-008 reads but does not define them.

| Setting | Env var | Default | Description |
|---|---|---|---|
| `S.product_depth_enabled` | `PRODUCT_DEPTH_ENABLED` | `False` | Master switch. All PRD-008 endpoints return `501` when off. `_catalog_item_out` skips depth reads when off. |
| `S.product_depth_variants_enabled` | `PRODUCT_DEPTH_VARIANTS_ENABLED` | `True` (when master on) | Sub-flag. Guards variant creation/listing/deletion inside the service layer. With this off and master on, feature endpoints still work but variant endpoints return `501`. |
| `S.product_depth_features_enabled` | `PRODUCT_DEPTH_FEATURES_ENABLED` | `True` (when master on) | Sub-flag. Guards feature-category/value endpoints. |

The master `product_depth_enabled` flag check is placed at the top of each handler body:

```python
if not getattr(S, "product_depth_enabled", False):
    raise HTTPException(status_code=501, detail="Product depth is not enabled")
```

This is distinct from the service-layer `_require_enabled()` guard. Both checks must pass for any operation to succeed. The double-check is intentional: the router guard gives a clean `501` to HTTP consumers before any service import occurs; the service guard is the safety net when the service is called outside the router (e.g., from tests or internal workers).

In `.env.local.example`, add:

```
PRODUCT_DEPTH_ENABLED=0
PRODUCT_DEPTH_VARIANTS_ENABLED=1
PRODUCT_DEPTH_FEATURES_ENABLED=1
```

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

All endpoint handlers call the service layer (`product_features.*`, `product_variants.*`) without any `S.dev_mode` branch. The service layer itself delegates all persistence to `T.product_depth` (DynamoDB), which is moto-backed in dev and real DynamoDB in prod. There is no separate mock path or in-memory fallback — the same code runs in both environments.

The `_catalog_item_out` best-effort `try/except` for depth reads is not a dev/prod divergence; it is a resilience guard that applies equally in both environments.

### 7.2 Idempotency

- **Feature category creation**: `product_features.create_feature_category` uses `attribute_not_exists(PK) AND attribute_not_exists(SK)` conditional put. A second call with the same `fc_id` gets `HTTP 409`. Callers wanting idempotency must supply a deterministic `fc_id` in `ProductFeatureCategoryCreateIn.fc_id`.
- **Feature value creation**: `feature_value_id = sha256_str(f"{fc_id}:{name_lower}")[:16]` (defined in PRD-006 `§2.5`). Two `add_feature_value` calls with the same `(fc_id, name)` produce the same `feature_value_id` and the second conditional put is caught and returns the existing row (silent idempotency).
- **Feature attachment**: `ITEM#{item_id}/FTAPPL#{fc_id}` — second attach of the same `(item_id, fc_id)` pair is caught by the conditional put and the service returns the existing row silently.
- **Variant creation**: `variant_id = sha256(parent_id + sorted_fv_tuple)[:16]` (PRD-007 `§5.1`). Second create of the same feature combination returns `HTTP 409` (not silent — duplicate combination is an explicit rejection, not an idempotent re-accept).

### 7.3 CSRF

All `POST`, `PATCH`, `DELETE` endpoints require the `x-csrf-token` header matching the session's stored `csrf_token` (enforced by `require_ui_session` / the CSRF middleware, same as all other non-GET catalog endpoints). `GET` endpoints skip CSRF.

### 7.4 Ownership enforcement

Every mutating endpoint (create, attach, delete) verifies `creator_id == ctx["user_sub"]` either in the router helper `_require_item_owner` (for item-scoped operations) or inside the service layer (for feature-category-scoped operations). A user who does not own an item or feature category receives `HTTP 403`. Non-owners can still call `GET` endpoints (subject to subscription gating).

### 7.5 Input validation

- `price_delta_cents` on `ProductFeatureValueCreateIn` — validated as signed int `ge=-10_000_000 le=10_000_000` per PRD-003 constraint.
- `position` — `ge=0, le=9999` per PRD-006.
- `feature_values` dict on `VariantCreateIn` — key count enforced `min_length=1, max_length=50` (max 50 feature axes per product).
- `sku_override` — max 256 chars; must not start with `"variant:"`.

## 8. Backward Compatibility & Migration

### 8.1 Existing endpoint responses

`CatalogItemOut` gains three new optional fields (`product_type`, `variant_count`, `has_features`) defined by PRD-003. These default to `None`, `None`, `False` when `S.product_depth_enabled = False`. The existing E2E tests (`frontend/e2e/catalog-subscriptions.spec.ts`) do not check for the absence of these fields, so no test changes are needed for the flag-off case.

### 8.2 No DDB schema changes

PRD-008 writes no new rows to `T.catalog` and makes no changes to `T.product_depth`'s schema — those are owned by PRD-002. No migration is needed when deploying PRD-008.

### 8.3 Router registration

The new endpoints are added to the existing `router` object in `app/routers/catalog.py`. No change to `app/main.py:671` is required — the router is already registered.

### 8.4 Models additive extension

`CatalogItemOut` at `app/models.py:672` gains optional fields per PRD-003. Any existing serialized response that omits the new fields will still deserialize correctly on the receiving end (pydantic defaults kick in). The existing `tests/test_catalog_inventory.py:65` suite passes unchanged because `_catalog_item_out` returns the same values for the pre-existing fields.

## 10. Open Questions / Assumptions

1. **Assumption**: PRD-002, PRD-003, PRD-006, and PRD-007 have all shipped before PRD-008 is started. `T.product_depth`, `S.product_depth_enabled`, all Pydantic models, and all service functions are available. PRD-008 will not compile if these prereqs are missing.

2. **Assumption**: The `product_depth_features_enabled` and `product_depth_variants_enabled` sub-flags have their Python defaults wired in settings.py by PRD-002 as `True` when master is on. If PRD-002 only ships the master flag, the sub-flag guards in service functions will use `getattr(S, "product_depth_features_enabled", True)` fallback — this is acceptable.

3. **Open question**: Should `GET /items/{item_id}/variants` be public (no auth) for storefront use? Currently spec'd with `require_ui_session`, which requires a logged-in user. If the storefront displays variants to anonymous visitors this needs to be relaxed. Recommend: for now, require session; a future ticket adds public variant listing.

4. **Open question**: `variant_count` in `_catalog_item_out` fetches up to 1000 variant rows to get a count. If a product has more than 1000 variants, the count is capped at 1000 (and the response says `1000`, not the true count). Alternative: add a separate `COUNT#` row on `T.product_depth` that is incremented on each variant create/delete. Recommend the separate `COUNT#` row approach for PRD-009 scale if needed; for PRD-008 the 1000-cap is acceptable.

5. **Assumption**: `has_features` is populated by querying `T.product_depth` with `SK begins_with "FTAPPL#"`. This requires the calling user to have access to `T.product_depth`. If `T.product_depth` does not exist (flag-off in a fresh environment), the `try/except` guard in `_catalog_item_out` swallows the `NoSuchTableError` and returns `has_features=False`. Verified by test `TestCatalogItemOutDepthFields::test_service_error_does_not_break_serialization`.

6. **Assumption**: `DELETE /items/{item_id}/variants/{variant_id}` is a hard delete (no soft-delete, no audit trail). If an audit trail is required, the caller should emit an audit event via `app.services.alerts.audit_event` before the delete — not implemented in PRD-008 but easy to add. PRD-008 does not call `audit_event` on variant deletes; the service layer does (per PRD-007).

7. **Open question**: When a variant is deleted, should the corresponding inventory SKU in `T.inventory` be cleaned up? PRD-008 does not do this; `T.inventory` is owned by OFB-003. The variant SKU (`"variant:{parent_id}:{variant_id}"`) will become an orphan in the inventory table. This is consistent with the OFBiz pattern where product deletion does not cascade to inventory — inventory cleanup is a separate administrative action.

8. **Assumption**: Route `/items/{item_id}/feature-categories` does not conflict with the existing `/categories/{category_id}/items` route — these are at different path positions in the URL structure (`/items/` prefix vs `/categories/` prefix) and FastAPI routes them correctly by prefix matching.
