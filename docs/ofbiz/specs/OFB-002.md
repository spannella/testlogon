## 1. Summary & Goal

OFB-002 is the pure-infrastructure complement to the OFB-001 spike. It lands the DynamoDB table definitions, `app/core/settings.py` keys, and `app/core/tables.py` handles required by every downstream OFB milestone, **with none of those milestones' runtime code**. When OFB-002 ships:

- `just restart` recreates all six new tables locally with no `ValidationException`.
- The `T` singleton exposes `T.inventory`, `T.reservations`, `T.returns`, `T.gl_accounts`, `T.gl_journal`, and `T.pricing_rules` as `_FloatSafeTable` handles.
- The `S` singleton exposes seven new boolean flags (all `False` by default) plus table-name overrides, so no new behavior activates until a downstream milestone turns on its own flag.
- A smoke pytest imports the handles and asserts flags/defaults without touching real AWS.

**Scope boundary:** OFB-002 is configuration scaffolding only. It introduces zero service logic, zero router code, zero Pydantic models, and zero frontend changes. All business behavior is deferred to the milestone that owns each flag.

### 3.1 `gl_accounts` — chart of accounts

| Attribute | Type | Notes |
|---|---|---|
| `account_id` | S (PK) | Short mnemonic: `CASH`, `AR`, `AP`, `SALES_REV`, `REFUNDS_CONTRA`, `TAX_PAYABLE`, `PROCESSOR_FEES` |
| `sk` | S (SK) | Always `META` for the single account record |
| `account_name` | S | Human label, e.g. "Accounts Receivable" |
| `account_class` | S | `asset` / `liability` / `equity` / `revenue` / `expense` |
| `normal_balance` | S | `debit` / `credit` (accounting convention) |
| `is_control_account` | BOOL | True for AR/AP; these reconcile to `BAL_FIELDS` in the billing table |
| `created_by` | S | ROOT `user_sub` who seeded or created the account |
| `created_at` | N | Unix timestamp via `now_ts()` |

GSI: **`GSI_CLASS`** — partition key `account_class` (S), sort key `account_id` (S). Enables the trial-balance grouped listing (all asset accounts, all liability accounts, etc.) without a scan. No numeric sort key: `account_id` is a string mnemonic, so no `attr_types` override needed.

**`TableDef` for `scripts/local-ddb-init.py`:**
```python
TableDef(
    _resolve_table_name(S.gl_accounts_table_name, "gl_accounts"),
    "account_id",
    "sk",
    gsi=[
        {"index_name": "GSI_CLASS", "partition_key": "account_class", "sort_key": "account_id"},
    ],
),
```

### 3.2 `gl_journal` — double-entry journal entries

| Attribute | Type | Notes |
|---|---|---|
| `journal_pk` | S (PK) | `JE#{journal_id}` where `journal_id = sha256(source_entry_id)[:32]` — deterministic from source |
| `sk` | S (SK) | `META` for header row; `LINE#{n}` for each debit/credit line (0-indexed) |
| `source_entry_id` | S | Billing ledger `entry_id`; idempotency anchor |
| `gl_date` | S | UTC date string `YYYY-MM-DD`, matches source `ledger_date` |
| `posted_at` | N | Unix timestamp of GL posting via `now_ts()` |
| `entry_type` | S | Source ledger `type` (e.g. `tip_debit`, `subscription_charge`, `adjustment`) |
| `total_debit_cents` | N | Sum of debit line amounts; must equal `total_credit_cents` |
| `total_credit_cents` | N | Sum of credit line amounts; must equal `total_debit_cents` |
| `posted_by` | S | `system_gl_poster` for background; ROOT `user_sub` for manual backfill |

Line rows (`sk = LINE#{n}`): `account_id`, `side` (`debit`/`credit`), `amount_cents`, `memo`.

GSIs:
- **`GSI_SOURCE`** — partition `source_entry_id` (S), sort `posted_at` (N). Used by `post_ledger_entry` to detect duplicate posts before writing. `attr_types={"posted_at": "N"}`.
- **`GSI_DATE`** — partition `gl_date` (S), sort `posted_at` (N). Used by `post_date_range` (backfill) and by the trial-balance endpoint to enumerate JEs within a date range. Same `attr_types`.

Note: both GSIs share the same numeric attribute `posted_at`, so `attr_types` need only declare it once.

**`TableDef` for `scripts/local-ddb-init.py`:**
```python
TableDef(
    _resolve_table_name(S.gl_journal_table_name, "gl_journal"),
    "journal_pk",
    "sk",
    gsi=[
        {"index_name": "GSI_SOURCE", "partition_key": "source_entry_id", "sort_key": "posted_at"},
        {"index_name": "GSI_DATE", "partition_key": "gl_date", "sort_key": "posted_at"},
    ],
    attr_types={"posted_at": "N"},
),
```

### 3.3 `pricing_rules` — tiered/bulk/conditional pricing engine

| Attribute | Type | Notes |
|---|---|---|
| `rule_pk` | S (PK) | `RULE#{rule_id}` where `rule_id = uuid4().hex` |
| `sk` | S (SK) | Always `META` |
| `rule_type` | S | `tiered` / `bulk` / `conditional` |
| `scope_key` | S | `ALL` / `SKU#{sku}` / `CAT#{category_id}` / `CREATOR#{creator_id}` |
| `priority` | N | Evaluation order; lower = higher priority; stacking controlled by `allow_stack` |
| `discount_type` | S | `percentage` / `fixed_amount` |
| `discount_value` | N | Percentage (1–100) or fixed cents |
| `conditions` | S | JSON-serialized condition set: `min_qty`, `min_cart_cents`, `valid_from`, `valid_until` |
| `creator_id` | S | ROOT `user_sub` for platform rules; creator `user_sub` for creator-scoped rules |
| `allow_stack` | BOOL | If `true`, lower-priority rules also apply after this one matches |
| `promo_code_id` | S | Optional bind to an existing promo code for joint redemption tracking |

Both numeric sort keys must appear in `attr_types`:

## 5. Detailed Behavior & Edge Cases

### 5.1 Table creation idempotency

`_ensure_table` in `scripts/local-ddb-init.py:2534` [VERIFIED] already handles the "table already exists" case: it reads `list_tables`, skips creation if the name is already present, but verifies and updates GSIs if the existing table differs from the `TableDef`. This means running `just restart` on an environment that already has the tables is safe — the GSI definitions will be verified but no data is lost.

### 5.2 `attr_types` completeness for `gl_journal`

`gl_journal` has two GSIs that both sort on `posted_at`. Since `_attribute_definitions` (`local-ddb-init.py:2496`) [VERIFIED] deduplicates attributes by name before building the `AttributeDefinitions` list, declaring `attr_types={"posted_at": "N"}` once covers both GSIs. However the code path in `_attribute_definitions` first sets the type to `"S"` (from the GSI loop) and then overwrites it with `attr_types` (line 2505) [VERIFIED: `attrs.update(table.attr_types)`], so the final type is always `"N"` as intended. No additional work is needed.

### 5.3 `pricing_rules` dual numeric keys

`pricing_rules` has two distinct numeric sort keys: `priority` (on `GSI_SCOPE`) and `created_at` (on `GSI_CREATOR`). Both must appear in `attr_types={"priority": "N", "created_at": "N"}`. If only one is declared, the other will be stored as String by DynamoDB Local and raise `ValidationException` when queried with an integer comparator. This is the same class of bug documented in CLAUDE.md.

### 5.4 Default table names must match `_resolve_table_name` fallbacks

`_resolve_table_name(S.gl_accounts_table_name, "gl_accounts")` returns `S.gl_accounts_table_name` if non-empty, else `"gl_accounts"`. Since `S.gl_accounts_table_name` defaults to `os.environ.get("GL_ACCOUNTS_TABLE_NAME", "gl_accounts")`, an unset `GL_ACCOUNTS_TABLE_NAME` env var yields `"gl_accounts"` from both paths — they stay in sync. The same logic holds for `gl_journal` and `pricing_rules`. This invariant must be verified: the default value in `settings.py` must equal the fallback string in `_resolve_table_name`.

### 5.5 Settings singleton import order

`app/core/settings.py` instantiates `S = Settings()` at module load time. `app/core/tables.py` imports `S` and calls `_safe_table(S.<table_name>)` at module load time. As long as the `Settings` dataclass definition and instantiation precede `Tables` usage in the import chain (which they do — `tables.py` imports `from .settings import S`), no circular-import issue exists. The three new settings attributes are pure `os.environ.get(...)` lookups with no side effects.

### 5.6 Flags are dormant — no code paths diverge

With all seven new flags at their default `False`, no existing code path changes at all. The flags are not read by any existing service. They only become meaningful when a downstream OFB ticket adds a `if not S.<flag>: raise HTTPException(404)` guard. Until then, `S.gl_double_entry_enabled` etc. exist purely as importable attributes.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**No `dev_mode` branches in any OFB-002 deliverable.** Table definitions, settings keys, and table handles are identical in dev (DynamoDB Local on port 8001, started by `scripts/local-stack-up.sh`) and prod (real DynamoDB). The `_ensure_table` path in `local-ddb-init.py:2534` runs only at startup; it is not invoked by request handlers at all.

**Idempotency:** `_ensure_table` is idempotent — re-running it on an existing table skips `create_table` and only verifies GSIs. Running `just restart` (which wipes and re-creates the local DDB data directory) is the destructive path, but that is intentional dev behavior. In prod, `scripts/local-ddb-init.py` is not run against real DynamoDB; table creation is a one-time infrastructure operation (CloudFormation/Terraform) outside this codebase.

**Security:** OFB-002 introduces no endpoints, no auth dependencies, and no data-access code. There is no security surface to harden. The downstream milestones that use these tables are responsible for applying `require_admin_or_root` (`app/auth/policy.py:67`) for admin-level paths (inventory ops, RMA queue) and `require_root_session` (`app/auth/deps.py:308`) for root-only paths (chart of accounts, journal browser, trial balance, pricing rule admin), plus CSRF headers on all non-GET requests — as specified in OFB-001, section 7. Note: `require_admin_session` does **not** exist in this codebase; the correct dependency is `require_admin_or_root` or `require_admin_or_root_csrf` (`app/auth/policy.py:100`) for combined role + CSRF enforcement.

**No money paths are opened.** The `gl_journal` table will eventually store derived accounting entries, but the only code that writes to it will be in OFB-013. At OFB-002 time the table is empty and unreferenced.

## 10. Open Questions / Assumptions

1. **Assumption:** The OFB-001 spike already merged `inventory`, `reservations`, `returns` tables and their settings/handle entries. This spec treats those as done and confirmed by reading `scripts/local-ddb-init.py:2452–2492`, `app/core/settings.py:839–847`, and `app/core/tables.py:317–319/569–571`. If any of those are missing, OFB-002 must also land those entries.

2. **Assumption:** `gl_accounts` uses `account_id` + `sk = "META"` as the key shape (PK + SK) rather than PK-only, to keep the table forward-compatible for future sub-rows (e.g., per-period balance snapshots keyed `SNAPSHOT#{date}`). If the finance stakeholder decides a simpler PK-only schema suffices, the `TableDef` drops the `"sk"` argument and the downstream `gl_accounts.py` service adjusts its get/put patterns.

3. **Open question:** Should `gl_journal` line items be stored as sub-rows (SK = `LINE#{n}`) or as a DynamoDB `List` attribute on the header row? The spec chooses sub-rows (consistent with how `order_items`, `signature_packet_fields`, and `returns` lines work in this codebase). However, a `List` attribute simplifies atomic writes for small JEs (2–4 lines). Decision should be confirmed before OFB-013 begins.

4. **Assumption:** `pricing_rules` stores `conditions` as a JSON-serialized string (S) rather than a DynamoDB `Map` (M), so the schema does not lock condition field names into `AttributeDefinitions`. If the implementer of OFB-019 prefers a `Map`, no `TableDef` change is needed — the attribute type only matters for index keys.

5. **Open question:** Should `pricing_rules` have a `GSI_STATUS` (partition `enabled` / `disabled`) to support an "active rules" query without filtering? Current design uses `GSI_SCOPE` and relies on a client-side `FilterExpression` for `enabled=true`. For a table expected to hold fewer than a few hundred rules, this is fine; at scale a GSI_STATUS may be warranted.

6. **Assumption:** The `inventory_low_stock_alerts_enabled` flag belongs in OFB-002 (added alongside the other Phase-1 flags) rather than waiting for OFB-005. This is consistent with the OFB-001 spec's flag table (`docs/ofbiz/specs/OFB-001.md:429`) and avoids a settings.py edit in OFB-005. If the team prefers minimum changes per ticket, the flag can be deferred to OFB-005 at the cost of a one-line settings.py edit in that ticket.

7. **Assumption:** The `gl_ar_ap_enabled` flag is included here (in the same settings block) for symmetry with the OFB-001 design even though OFB-015 is the milestone that uses it. Same rationale as `inventory_low_stock_alerts_enabled` above.
