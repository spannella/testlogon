# FAC-014 — Lot / serial tracking (optional)

## 1. Summary & Goal

FAC-014 threads optional lot and per-unit serial traceability through the three warehouse-side lifecycle services introduced by earlier FAC tickets: receiving (FAC-007 `app/services/receiving.py`), picking (FAC-008 `app/services/picking.py`), and shipping (FAC-010 `app/services/shipping_fulfillment.py`). When the sub-flag `FACILITY_LOT_SERIAL_ENABLED` is off (the default), all three services behave byte-for-byte identically to their current implementations. When on, a received lot and its per-unit serial numbers are recorded on inbound receipt lines, carried through picklist line confirmation, and stamped on the outbound shipment — making every shipped unit traceable back to its inbound receipt document and purchase order.

Concretely FAC-014 ships:

1. **`app/services/lot_serial.py`** — a dedicated service that owns all reads and writes to `T.lot_serial`, encapsulating lot registration, serial allocation, pick assignment, and the receipt→shipment traceability query.
2. **Thin hooks into FAC-007, FAC-008, and FAC-010** — each existing service gains a best-effort call-out to `lot_serial.*` when `S.facility_lot_serial_enabled` is `True`. The call-out is always wrapped in a `try/except` so a lot/serial failure never aborts the underlying warehouse operation.
3. **Two new Pydantic model extensions** in `app/models.py` — additive `lot_id` / `serials` fields on the existing `ReceiveLineIn`, `ReceiptLineOut`, `PickLineOut`, and `ShipmentOut` models, all optional (default `None`) to preserve backward compatibility.
4. **Two new read endpoints** in `app/routers/fulfillment.py` — `GET /ui/fulfillment/lots/{sku}/{lot_id}` and `GET /ui/fulfillment/lots/{sku}/{lot_id}/trace` — for lot detail and full receipt→shipment traceability, both gated by `require_admin_or_root_csrf`.

No existing table schemas are altered. No billing paths are touched. The existing inventory, shop, cart, orders, and billing flows are entirely unaffected regardless of flag state.

## 3. Data Model

FAC-014 writes to `T.lot_serial` (already created by FAC-002) and extends rows in `T.receipts`, `T.picklists`, and `T.shipments` with optional columns. It adds **one new GSI** to `T.lot_serial` beyond what FAC-002 defined, which requires the `lot_serial` `TableDef` in `scripts/local-ddb-init.py` to be updated.

### 3.1 Table: `lot_serial` — extended schema

**Primary key**: `sku` (S, hash) / `sk` (S, range)

The `sk` value uses two prefixes:

| `sk` prefix | Row type |
|---|---|
| `LOT#{lot_id}` | Lot header row — one per received lot at a given SKU |
| `SERIAL#{serial}` | Per-unit serial number row — one per physical unit |

**GSIs (updated by FAC-014)**:

| Index | Hash key | Range key | `attr_types` note |
|---|---|---|---|
| `GSI_LOT_STATUS` | `lot_status` (S) | `created_at` (N) | Already declared by FAC-002 (`attr_types={"created_at": "N"}`) |
| `GSI_RECEIPT` | `receipt_id` (S) | `created_at` (N) | **New in FAC-014** — needed for the traceability query: given a receipt, enumerate all lots received against it. `created_at` is numeric → must be in `attr_types`. |
| `GSI_SHIPMENT` | `shipment_id` (S) | `created_at` (N) | **New in FAC-014** — needed for the inverse traceability query: given a shipment, which lots were included? Numeric `created_at` → `attr_types`. |

The updated `TableDef` in `scripts/local-ddb-init.py` (replacing the FAC-002 definition):

```python
TableDef(
    _resolve_table_name(S.lot_serial_table_name, "lot_serial"),
    "sku",
    "sk",
    gsi=[
        {"index_name": "GSI_LOT_STATUS", "partition_key": "lot_status",  "sort_key": "created_at"},
        {"index_name": "GSI_RECEIPT",    "partition_key": "receipt_id",   "sort_key": "created_at"},
        {"index_name": "GSI_SHIPMENT",   "partition_key": "shipment_id",  "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
),
```

`receipt_id` and `shipment_id` are both string attributes (no numeric override needed) but are sparse — only lot header rows carry them (serial rows do not carry `shipment_id` directly; shipment association is derived through the lot).

### 3.2 Lot header row (`sk = "LOT#{lot_id}"`)

| Attribute | DDB type | Notes |
|---|---|---|
| `sku` | S | PK — the stock-keeping unit this lot belongs to |
| `sk` | S | `LOT#{lot_id}` where `lot_id = sha256(f"{receipt_id}:{sku}:{lot_label}")[:24]` |
| `lot_id` | S | Denormalised for projections |
| `lot_label` | S | Caller-supplied human label (e.g. `"2025-BATCH-001"`); may be empty string |
| `lot_status` | S | `"received"` / `"in_pick"` / `"shipped"` / `"quarantine"`. GSI_LOT_STATUS hash key. |
| `receipt_id` | S | The `T.receipts` receipt that created this lot. GSI_RECEIPT hash key. |
| `receipt_line_no` | N | 1-based line index on the receipt; links back to `T.receipts` `LINE#{n}` |
| `facility_id` | S | Facility where the lot was received |
| `location_id` | S | Bin where the lot was stocked |
| `quantity_received` | N | Total units in this lot |
| `quantity_available` | N | Units not yet assigned to a picklist line; decremented on pick assignment |
| `shipment_id` | S | Set when lot is shipped (GSI_SHIPMENT hash key). Absent (attribute not written) until shipped. |
| `picklist_id` | S | Set when lot is assigned to a pick line. Absent until picking. |
| `expiry_date` | S | Optional ISO-8601 date string (e.g. `"2026-12-31"`); absent when not applicable |
| `created_at` | N | Integer Unix timestamp (`now_ts()`). GSI sort key for all three GSIs. |
| `updated_at` | N | Updated on every state change |

### 3.3 Serial number row (`sk = "SERIAL#{serial}"`)

A serial row exists for every distinct physical unit within a lot. Serial numbers are supplied by the warehouse operator at receiving time.

| Attribute | DDB type | Notes |
|---|---|---|
| `sku` | S | PK |
| `sk` | S | `SERIAL#{serial}` where `serial` is the operator-supplied string (barcode, GTIN, etc.) |
| `serial` | S | Denormalised |
| `lot_id` | S | Parent lot — enables JOIN-like look-up from serial to lot |
| `status` | S | `"in_stock"` / `"picked"` / `"shipped"` / `"returned"` |
| `receipt_id` | S | Traceability anchor — which receipt introduced this unit |
| `picklist_id` | S | Set when serial is confirmed as picked. Absent until then. |
| `shipment_id` | S | Set when the shipment is finalised. Absent until then. |
| `created_at` | N | Integer Unix timestamp |
| `updated_at` | N | Updated on status transitions |

**Uniqueness constraint**: serial numbers are globally unique per SKU. `put_item` uses `ConditionExpression="attribute_not_exists(sk)"` to reject duplicate serial ingestion with a `ConditionalCheckFailedException`, surfaced as HTTP 409 to the caller.

### 3.4 `T.receipts` LINE row — additive columns (FAC-014)

FAC-007 already reserves `lot_id: S` on the LINE row (`docs/ofbiz/specs/FAC-007.md:157`). FAC-014 writes it and adds `serials: L` (a DynamoDB StringSet / List of serial strings). No schema migration is needed for existing rows — attributes are simply absent on pre-FAC-014 rows.

### 3.5 `T.picklists` LINE row — additive columns (FAC-014)

FAC-008 `LINE#{n}` rows gain two optional columns:

| Attribute | DDB type | Notes |
|---|---|---|
| `lot_id` | S | The lot from which this line was picked. Absent when sub-flag is off. |
| `serials` | L | List of serial number strings consumed from this lot for this pick. Absent when sub-flag is off. |

### 3.6 `T.shipments` META row — additive column (FAC-014)

| Attribute | DDB type | Notes |
|---|---|---|
| `lot_summary` | L | List of maps `{sku, lot_id, lot_label, serials: [...]}`. Aggregated from all picklist LINE rows at ship time. Absent when sub-flag is off or no lot tracking was performed. |

## 4. API / Service Design

### 4.1 New module: `app/services/lot_serial.py`

```python
"""OFBiz Lot/serial tracking service (ADR-001, FAC-014).

Additive + flag-gated (FACILITY_LOT_SERIAL_ENABLED, default OFF).
Every public function short-circuits to a no-op (or None) when the flag is off.
Never raises for missing data — callers (receive/pick/ship) call these as
best-effort hooks.

Public surface:
  register_lot(receipt_id, receipt_line_no, sku, lot_label, facility_id,
               location_id, quantity, serials, *, user_sub) -> dict | None
  assign_lot_to_pick(picklist_id, line_no, sku, lot_id, serials, *, user_sub)
                    -> None
  finalize_lot_shipment(shipment_id, picklist_id, *, user_sub) -> list[dict]
  get_lot(sku, lot_id) -> dict | None
  trace_lot(sku, lot_id) -> dict
  list_lots_for_receipt(receipt_id) -> list[dict]
"""
```

#### `register_lot` — called from `receive_shipment` in FAC-007

```python
def register_lot(
    receipt_id: str,
    receipt_line_no: int,
    sku: str,
    lot_label: str,
    facility_id: str,
    location_id: str,
    quantity: int,
    serials: list[str],  # may be empty
    *,
    user_sub: str = "system",
) -> dict | None:
```

Derives `lot_id = hashlib.sha256(f"{receipt_id}:{sku}:{lot_label}".encode()).hexdigest()[:24]`.

Writes the lot header row via `T.lot_serial.put_item` with `ConditionExpression="attribute_not_exists(sk)"`. A `ConditionalCheckFailedException` means the receipt is being replayed — returns the existing lot row without duplicating serial rows (idempotent).

For each serial in `serials`, writes a serial row via `T.lot_serial.put_item` with `ConditionExpression="attribute_not_exists(sk)"`. A duplicate serial raises HTTP 409 (`Serial number already registered for SKU`).

Returns the lot header dict. Returns `None` (silently) when `S.facility_lot_serial_enabled` is `False`.

#### `assign_lot_to_pick` — called from `confirm_pick` in FAC-008

```python
def assign_lot_to_pick(
    picklist_id: str,
    line_no: int,
    sku: str,
    lot_id: str,
    serials: list[str],  # subset of serials on the lot
    *,
    user_sub: str = "system",
) -> None:
```

Updates the lot header: decrements `quantity_available` by `len(serials) or picked_qty`; sets `lot_status = "in_pick"` and `picklist_id`. Uses a conditional update `ConditionExpression="quantity_available >= :req"` to prevent over-allocation (raises HTTP 409 on failure).

Updates each serial row: sets `status = "picked"` and `picklist_id` via a conditional update `ConditionExpression="#status = :in_stock"`.

No-op (silently) when `S.facility_lot_serial_enabled` is `False`.

#### `finalize_lot_shipment` — called from `ship_shipment` in FAC-010

```python
def finalize_lot_shipment(
    shipment_id: str,
    picklist_id: str,
    *,
    user_sub: str = "system",
) -> list[dict]:
```

Reads all picklist `LINE#{n}` rows from `T.picklists` that have a non-empty `lot_id`. For each unique `(sku, lot_id)` pair:
- Updates the lot header: sets `lot_status = "shipped"` and `shipment_id`.
- Updates each serial in the lot's `serials` list: sets `status = "shipped"` and `shipment_id`.

Returns a list of `{sku, lot_id, lot_label, serials: [...]}` maps (the `lot_summary` written to the shipment META by `ship_shipment`).

No-op (returns `[]`) when `S.facility_lot_serial_enabled` is `False`.

#### `get_lot` — direct read

```python
def get_lot(sku: str, lot_id: str) -> dict | None:
```

`T.lot_serial.get_item(Key={"sku": sku, "sk": f"LOT#{lot_id}"})`. Returns the item dict or `None`.

#### `trace_lot` — receipt→shipment traceability

```python
def trace_lot(sku: str, lot_id: str) -> dict:
```

Returns a fully hydrated trace document:

```json
{
  "lot": { ...lot header... },
  "receipt": { "receipt_id": "...", "facility_id": "...", "po_id": "..." },
  "serials": [ { "serial": "...", "status": "shipped", ... } ],
  "shipment": { "shipment_id": "...", "carrier": "...", "tracking_number": "..." }
}
```

The receipt portion is fetched from `T.receipts.get_item(Key={"receipt_id": lot["receipt_id"], "sk": "META"})`. The shipment portion is fetched from `T.shipments.get_item(Key={"shipment_id": lot.get("shipment_id"), "sk": "META"})` if `shipment_id` is set. Serial rows are fetched by querying `T.lot_serial` `begins_with("SERIAL#")` filtered to `lot_id = lot_id`.

Raises HTTP 404 if the lot does not exist.

#### `list_lots_for_receipt` — GSI_RECEIPT query

```python
def list_lots_for_receipt(receipt_id: str) -> list[dict]:
```

Queries `T.lot_serial` via `GSI_RECEIPT`: `KeyConditionExpression=Key("receipt_id").eq(receipt_id)`, `ScanIndexForward=False`. Returns only lot header rows (SK prefix `LOT#`).

#### FAC-007 `receive_shipment` hook (in `app/services/receiving.py`)

After writing each `LINE#{n}` row and (optionally) calling `inventory.adjust`, add:

```python

    try:

        lot = ls.register_lot(
            receipt_id=receipt_id,

            T.receipts.update_item(

        pass  # lot/serial failure must not roll back the receipt
```

The `line.get("lot_label")` guard means: if the caller does not supply `lot_label`, no lot row is created and the LINE row is left without `lot_id` — backward-compatible with the FAC-007 path that never sends lot data.

## 5. Detailed Behavior & Edge Cases

### Flag-off parity (the primary guarantee)

When `S.facility_lot_serial_enabled is False`:
- `receive_shipment` skips the `register_lot` block entirely — no read or write to `T.lot_serial`. The receipt LINE row is written without `lot_id` exactly as it was before this ticket.
- `confirm_pick` skips the `assign_lot_to_pick` block entirely — the picklist LINE row has no `lot_id` or `serials` column, identical to the pre-FAC-014 shape.
- `ship_shipment` calls `finalize_lot_shipment`, which immediately returns `[]` and takes no DDB action. The `if lot_summary:` guard prevents the `update_item` write.
- No endpoint in `fulfillment_router` that calls `_require_lot_serial_enabled()` is reachable — they 404 before touching any service.
- `T.lot_serial` exists as an empty DDB table but nothing reads or writes it.

### Receiving a lot without serials

`serials` is an empty list. `register_lot` writes the lot header row and skips the serial-row loop. The lot tracks only lot-level quantity (`quantity_received`, `quantity_available`) without individual unit provenance. This is a valid use case for bulk commodities.

### Receiving the same lot twice (idempotency)

`receive_shipment` is already idempotent via `sha256(correlation_id)` (`docs/ofbiz/specs/FAC-007.md:40`). When the same `correlation_id` is replayed, `receive_shipment` detects the existing receipt (via the `attribute_not_exists(receipt_id)` conditional) and returns the existing receipt without touching inventory or calling `register_lot`. The `try/except` block in the hook means even if `register_lot` is called on a replay, the `ConditionalCheckFailedException` on the lot header put_item is silently caught.

### Receiving a duplicate serial number

`register_lot` calls `T.lot_serial.put_item(..., ConditionExpression="attribute_not_exists(sk)")` for each serial. A `ConditionalCheckFailedException` means the serial was already registered (by a prior receipt). This is a **hard 409 error** surfaced to the caller — not silently swallowed — because it indicates a real data integrity problem (the same physical unit appearing on two different receipts is an error, not a race condition). The `try/except` wrapper in `receive_shipment` then catches this HTTP 409 and allows the receipt to complete, but the `lot_id` is NOT back-written to the LINE row, and the audit event records the partial failure.

### Picking more serials than available on the lot

`assign_lot_to_pick` guards with `ConditionExpression="quantity_available >= :req"`. A `ConditionalCheckFailedException` raises HTTP 409 (`Lot {lot_id} has insufficient available quantity`). The `try/except` in `confirm_pick` catches this and proceeds, but the picklist LINE row is NOT annotated with `lot_id`/`serials`. The warehouse operator must resolve the discrepancy manually or re-confirm with a valid lot assignment.

### Shipping without lot tracking

When a shipment's picklist LINE rows have no `lot_id` column (either because the sub-flag was off at pick time, or because the picker did not supply a `lot_id`), `finalize_lot_shipment` reads the LINE rows, finds no `lot_id` fields, returns `[]`, and the shipment META row receives no `lot_summary`. This is fully supported — lot tracking is optional at the line level even when the flag is on.

### Lot status transitions

```
received → in_pick → shipped
         ↘ quarantine (manual admin action only; no automated transition)
```

A lot can move from `received` directly to `quarantine` (admin action via a future PATCH endpoint, not part of FAC-014's scope). Quarantined lots cannot be assigned to a pick (`assign_lot_to_pick` checks `lot_status not in ("quarantine",)`). The `shipped` state is terminal; a shipped lot cannot be reassigned. Return/RMA handling is out of scope for FAC-014 (deferred to a future RMA-lot integration ticket).

### Serial status transitions

```
in_stock → picked → shipped
        ↘ (future: returned)
```

### Traceability query performance

`trace_lot` performs three DDB reads:
1. `get_item` on `T.lot_serial` for the lot header (PK lookup — O(1)).
2. `get_item` on `T.receipts` for the receipt header (PK lookup — O(1)).
3. `query` on `T.lot_serial` with `begins_with("SERIAL#")` filter on `lot_id` (base-table query on PK partition — O(serials per SKU); may need a FilterExpression on `lot_id` since all serials for a SKU share the same PK partition).
4. `get_item` on `T.shipments` for the shipment header (PK lookup — O(1), only if shipped).

For SKUs with large numbers of serials (> 1 MB per partition page), the serial query must paginate via `LastEvaluatedKey`. The implementation loops until no `LastEvaluatedKey` is present, per the CLAUDE.md pattern.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

All DDB writes use `T.lot_serial`, which resolves to either moto local DDB (dev) or real DynamoDB (prod) depending on the boto3 endpoint configured in `.env.local` / production environment. There is no `S.dev_mode` branch in `lot_serial.py`. Both envs receive identical code paths — the `_FloatSafeTable` class (`app/core/tables.py:29–62`) wraps every table handle returned by `_safe_table` (`app/core/tables.py:65–66`), providing float-to-Decimal coercion on `put_item`/`update_item`/`batch_writer` calls on both.

### Idempotency

- **Receipt replay**: `register_lot` uses `ConditionExpression="attribute_not_exists(sk)"` on the lot header put. A replay returns the existing row without creating duplicate serial rows.
- **Pick assignment**: `assign_lot_to_pick` uses a conditional quantity check. If the lot is already `in_pick` with the same `picklist_id`, the quantity guard still applies — a replay that sends the same serials twice will fail the `status = "in_stock"` serial-row guard (the serial is already `"picked"`) and raise HTTP 409, which `confirm_pick`'s `try/except` swallows.
- **Ship finalization**: `finalize_lot_shipment` updates lots with `ConditionExpression="#lot_status IN (:in_pick)"` so a second `ship_shipment` call (already idempotent at the shipment level via the `status = "draft"` guard in FAC-010) will find lots already in `"shipped"` state — the conditional fails, and the lots are not double-updated.

### Security

- Lot and serial data are internal warehouse records. All read/write endpoints are gated by `require_admin_or_root_csrf` (defined at `app/auth/policy.py:100–106` — VERIFIED) — the same guard used by `inventory.py`'s mutation endpoints (`app/routers/inventory.py:18,48,65,81` — VERIFIED). Customers cannot read lot or serial information.
- Serial numbers must not be logged at DEBUG level as they may encode sensitive pharmaceutical or regulated-item data. The `_audit` wrapper emits `lot_id` and a serial count but not individual serial strings.
- `lot_label` is free-text supplied by the operator and must be length-bounded to `max_length=200` in the Pydantic `ReceiveLineIn` model to prevent large-string DDB write amplification.

## 8. Backward Compatibility & Migration

### No existing data is altered

FAC-014 adds new attributes to rows that already exist in `T.receipts` and `T.picklists`. DynamoDB's schema-free model means pre-existing rows without `lot_id` / `serials` columns continue to work: all projections use `.get("lot_id")` / `.get("serials", [])` with a safe default.

### `T.lot_serial` — updated TableDef with two new GSIs

FAC-002 defined the `lot_serial` table with one GSI (`GSI_LOT_STATUS`). FAC-014 adds two more (`GSI_RECEIPT`, `GSI_SHIPMENT`). In the **development environment**, `just restart` drops and recreates all tables, so the updated `TableDef` takes effect automatically.

In **production**, adding GSIs to an existing DynamoDB table requires an `UpdateTable` API call and waits for `ACTIVE` status on each new index before the application can query them. The deployment sequence is:

1. Deploy the updated `scripts/local-ddb-init.py` (new `TableDef` only — no code changes yet).
2. Run `UpdateTable` on the `lot_serial` table to add `GSI_RECEIPT` and `GSI_SHIPMENT` and wait for both indexes to reach `ACTIVE`.
3. Deploy the FAC-014 application code (services + router endpoints + model extensions).
4. Set `FACILITY_LOT_SERIAL_ENABLED=true` only after both GSIs are confirmed `ACTIVE`.

Until step 4, the sub-flag is `false` and no code path queries the new GSIs.

### Pydantic model additions are non-breaking

All new fields on existing models are `Optional[...] = None`. Existing API consumers that do not send `lot_label` or `serials` in their request bodies see no change in behavior. Existing response consumers that do not read `lot_id` / `lot_summary` are unaffected by the new fields in responses.

## 10. Open Questions / Assumptions

1. **Assumption**: `T.lot_serial` is already wired in `app/core/tables.py` as `T.lot_serial = _safe_table(S.lot_serial_table_name)` by FAC-002. The spec relies on this. If FAC-002 ships without wiring `T.lot_serial` in the `T` singleton, FAC-014 must add that line before anything else.

2. **Assumption**: The picklist `LINE#{n}` rows written by FAC-008 `confirm_pick` use `update_item` (not `put_item`), so adding `lot_id` / `serials` via a second `update_item` after the pick confirmation is safe and will not overwrite other fields. If FAC-008 uses `put_item` (re-writes the whole row), the lot annotation must be merged into the same `update_item` call to avoid a lost-update race.

3. **Open question**: Should lot assignment be mandatory when `FACILITY_LOT_SERIAL_ENABLED=true`? The spec treats it as optional (the picker can confirm a line without supplying `lot_id`). An alternative is to enforce lot assignment when the flag is on and the receipt LINE has a `lot_id`. Recommendation: keep it optional for now (best-effort); a future stricter enforcement can be added as a validation rule.

4. **Assumption**: Serial numbers are unique per SKU (not globally unique across all SKUs). Two different SKUs can have the same serial string without conflict. The `T.lot_serial` PK is `sku` + `sk = "SERIAL#{serial}"`, which enforces this scoping naturally.

5. **Open question**: The `expiry_date` field on lot headers is stored as an ISO-8601 string. Should the system enforce receiving quarantine when a lot's `expiry_date` is in the past? FAC-014 stores the field but adds no enforcement. A future FIFO/FEFO (first-in-first-out / first-expired-first-out) picking strategy ticket can consume this field.

6. **Assumption**: `finalize_lot_shipment` reads the picklist from `T.picklists` using the `picklist_id` stored on the shipment META row. This requires that `T.shipments` META has a `picklist_id` attribute — which is confirmed by the FAC-002 spec (`docs/ofbiz/specs/FAC-002.md:305`: `"picklist_id: S, Source picklist"` — VERIFIED).

7. **Open question**: Can a single lot span multiple receipts? The current design keys `lot_id = sha256(receipt_id + sku + lot_label)`, making lots receipt-scoped. A real OFBiz lot is more broadly scoped (manufacturer lot). The spec takes the simpler receipt-scoped approach and defers multi-receipt lot merging to a future enhancement.
