# ORD-014 — Order-lifecycle admin page, customer view, route & nav

**Type:** Feature | **Priority:** P1 | **Estimate:** 4 days
**Milestone:** 5 — Frontend

---

## 1. Summary & Goal

ORD-014 delivers the complete frontend surface for the order-lifecycle state machine introduced by ORD-001 through ORD-013:

1. **Admin fulfillment board** (`frontend/src/pages/shop/admin/OrderFulfillmentBoard.tsx`) — a status-board / order detail with transition controls (only legal next states enabled), a status-history timeline, adjustments editor, and ship-group management; reads the two list endpoints from ORD-012 and all detail endpoints from ORD-011.
2. **Customer order timeline** (`frontend/src/pages/shop/OrderLifecyclePage.tsx`) — a read-only lifecycle timeline extending the existing `PurchasesPage` area, with a single self-cancel action gated on `lifecycle_status === "created"`.
3. **Routes in `frontend/src/App.tsx`** and **nav entries in `frontend/src/components/layout/Sidebar.tsx`** for both pages, all gated on `VITE_ORDER_LIFECYCLE_ENABLED` (default `false`) with the admin board additionally gated on `canAccessGeneralAdminControls`.

When the flag is off, neither route is reachable (the lazy import is never mounted) and the nav entries are absent. No existing route, component, or API call is altered.

## 3. Data Model

ORD-014 is entirely a frontend ticket. It reads from the backend DynamoDB data model established by ORD-003 (no new tables, GSIs, or DDB attributes added here).

**IMPORTANT — current vs. ORD-003 state**: The existing `orders` table (`scripts/local-ddb-init.py:287–294`) has PK=`order_id` with **no sort key** and GSIs `GSI_USER` (PK `user_id`, SK `created_at`) and `GSI_STATUS` (PK `status`, SK `created_at`). It uses a **separate** `order_items` table (PK `order_id`, SK `item_id`) — not a single-table SK-prefix pattern. ORD-003 must migrate this to the single-table layout described below; these rows do not exist yet. ORD-014 depends on ORD-003 completing that migration.

For reference, the single-table `orders` table **as extended by ORD-003** carries:

| SK Prefix | Row type |
|-----------|----------|
| `ORDER` | Header: `lifecycle_status`, `status` (legacy mirror), `amount_cents`, `adjusted_amount_cents`, `currency`, `user_id`, `created_at`, `updated_at`, `updated_ts` (numeric) |
| `HIST#{ts:020d}#{event_id}` | Status-history row: `from_status`, `to_status`, `actor`, `reason`, `ts` |
| `ADJ#{adjustment_id}` | Adjustment row: `type`, `label`, `amount_cents`, `currency`, `taxable`, `source_rule_ref` |
| `SHIPGRP#{ship_group_id}` | Ship-group row: `ship_method`, `address_ref`, `item_refs[]`, `ship_group_status`, `ship_ts` |

GSIs added by ORD-003 and used by ORD-012 list endpoints (not present yet in `scripts/local-ddb-init.py`):
- `GSI_ORDER_STATUS` (PK `lifecycle_status` S, SK `updated_ts` N) — must be declared with `attr_types={"updated_ts":"N"}` per the CLAUDE.md numeric-GSI gotcha
- `GSI_ORDER_SHIPDATE` (PK `ship_date_bucket` S, SK `ship_ts` N) — must be declared with `attr_types={"ship_ts":"N"}`

Frontend state is managed entirely through React Query — no Zustand store additions are needed.

## 5. Detailed Behavior & Edge Cases

### 5.1 Transition controls (admin board)

The `TRANSITIONS` dict from `app/services/order_lifecycle.py` (ORD-005) defines the legal graph. The frontend derives available next states from the `lifecycle_status` on the `OrderLifecycleOut` response — it does **not** hardcode the graph client-side to avoid drift. Instead:
- The lifecycle fetch returns `allowed_transitions: string[]` (a field ORD-011 must include in `OrderLifecycleOut`).
- `TransitionControls` renders one button per entry in `allowed_transitions`. Buttons outside that list are either absent or rendered disabled with a tooltip ("Not a legal transition from this state").
- On click, the component calls `transitionOrder(orderId, { target_status, reason })` via `useMutation`. On success it invalidates `["orders", orderId, "lifecycle"]` and `["orders", orderId, "history"]`. On 409 (conflict — concurrent write) it shows a toast: "Another agent just updated this order — refreshing." and refetches.

**Assumption A1**: ORD-011 includes `allowed_transitions: string[]` in the `OrderLifecycleOut` response. If it does not, the board must hardcode the graph as a `const TRANSITIONS: Record<string, string[]>` in a local util; this is noted as an open question in Section 10.

### 5.2 Adjustments editor

- Only visible (non-greyed) when `lifecycle_status` is one of `created | approved | allocated | picking | packed | held | backorder`.
- Add-form fields: `type` (select: discount / surcharge / tax / shipping / promotion), `label` (text), `amount_cents` (number; negative values used for discounts — the UI shows signed input with a "+"/"-" prefix toggle to make intent unambiguous), `currency` (read from order header; display only).
- On submission, calls `addAdjustment(orderId, body)`. On 409 (e.g. shipped state), shows toast "Adjustments are locked for shipped orders".
- Remove button calls `removeAdjustment(orderId, adjustmentId)` → confirm dialog → `api.del`.
- `adjusted_amount_cents` returned by the lifecycle fetch is rendered as "Adjusted Total" beside the base `amount_cents`.

### 5.3 Ship groups panel

- Default state: if `ship_groups` array is empty in the `OrderLifecycleOut`, the panel shows "Default single-group fulfillment (all items)" with a button "Split into ship groups".
- Split: shows a line-item list (from `order_items` embedded in the lifecycle response or from the original `CartItem` data); each item is assigned to a group via a select. On save, calls `createShipGroup` then `assignItemsToShipGroup`.
- Per-ship-group status pill shows the group's `ship_group_status`. Advancing a group (sub-status transition) is in scope only if ORD-011 exposes it; otherwise the panel shows the status as read-only and relies on the order-level transition.

**Assumption A2**: `OrderLifecycleOut` embeds `order_items` as `line_items: OrderLineItemOut[]`. Note that the current `commerce_order_service.create_order` (`app/services/commerce_order_service.py:87–104`) writes items to a **separate** `order_items` table (PK `order_id`, SK `item_id`) — they are not embedded in the order record itself. ORD-011 must join them when building `OrderLifecycleOut`. If the lifecycle endpoint returns only `item_ids`, a separate `GET /ui/orders/{order_id}/items` call is needed; this is an open question.

### 5.4 Customer self-cancel

- `SelfCancelCard` is rendered only when `lifecycle_status === "created"`.
- "Cancel Order" button opens `ConfirmDialog` ("This order will be cancelled and a full refund issued if payment was taken.").
- On confirm, calls `cancelOrder(orderId, { reason, refund: true })` from `orderLifecycle.ts`.
- On 409 ("Order cannot be cancelled in current state"), shows toast "Order has already advanced past the cancellable stage."
- On success, invalidates the lifecycle query → status badge updates to "cancelled".

### 5.5 History timeline rendering

`OrderStatusHistoryEntry` fields: `from_status`, `to_status`, `actor`, `reason`, `ts` (Unix seconds int). The component renders a vertical stepper (reusing the lucide icons from `ShippingTimeline`): each row shows `to_status` as the primary label, `from_status → to_status` in muted text, actor (truncated), ISO-formatted `ts`, and `reason` as a collapsible note. Newest-first order (backend returns newest-first per ORD-006).

### 5.6 Flag-off guard

Both pages import `isOrderLifecycleEnabled` from `featureFlags.ts` and return `null` (render nothing) if the flag is false. This is a belt-and-suspenders guard: since the routes are never registered when the flag is off (the lazy import lines in App.tsx are conditional), the guard is only reached in unusual environments where the JS bundle was cached with the flag-on build.

### 5.7 Loading and error states

- Each `useQuery` call shows a `Skeleton` card during `isLoading`.
- On error, shows an `Alert` with the error message. For 503 specifically: "Order lifecycle is not enabled on this server."
- Mutations show a `Loader2` spinner on the triggering button during `isPending`.

### 5.8 Pagination on the board list

The board list panel uses `useInfiniteQuery` against `getOrdersByStatus` (ORD-012 cursor-paginated). A "Load more" button at the bottom of `OrderListPanel` appends the next page. The `by-ship-date` tab fetches a single page (ship-date queries are already date-scoped and typically short).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No dev/prod divergence in the UI

The frontend contains no dev-mode branches. Both pages make the same API calls in dev and prod. The dev-mode behavior (mocked DDB, no real Stripe, mock KMS) is entirely backend-transparent to the React components.

### 7.2 Role enforcement is server-side only

The admin board nav entry and route guard (`canAccessGeneralAdminControls`) are a UX convenience; they do **not** constitute a security boundary. Every mutation endpoint in ORD-011 enforces `require_admin_or_root_csrf` server-side (`app/auth/policy.py:100–104`), which validates the role from the `ui_access_token` JWT cookie and checks the CSRF token. A customer who manually navigates to `/admin/orders` gets a 403 on every mutation — the UI will show the error but the data is never mutated.

### 7.3 Ownership enforcement

`GET /ui/orders/{order_id}/lifecycle` and `/history` (owner reads) enforce that the session's `user_sub` matches `order.user_id` at the backend (ORD-011). The customer page passes the `order_id` from the URL param; if the user navigates to another user's order ID they receive a 403/404 which the page renders as an error card.

### 7.4 CSRF

All mutations use `api.post` / `api.del` from `frontend/src/api/client.ts`, which auto-attaches the `X-CSRF-Token` header (client.ts:179–181). No additional CSRF handling is needed in ORD-014.

### 7.5 Idempotency for cancel

The customer self-cancel mutation calls `cancelOrder` which POSTs to `POST /ui/orders/{order_id}/cancel`. The backend (ORD-010) is idempotent: a second cancel of an already-cancelled order returns 409 which the UI displays as a toast, not a crash. The UI disables the cancel button after a successful mutation (by checking `lifecycle_status !== "created"` from the re-fetched query).

## 10. Open Questions / Assumptions

**A1 (RESOLVED)**: `OrderLifecycleOut` now includes `allowed_transitions: Optional[List[str]]` (added to ORD-004 §4.8 per ESCALATIONS §A row 28, reconciliation pass 2026-06-10). `TransitionControls` derives available buttons from `allowed_transitions` — no client-side hardcoding of the TRANSITIONS graph. ORD-011's `get_order_lifecycle` populates this field by computing `list(TRANSITIONS.get(current_status, set()))`.

**A2 (RESOLVED)**: `OrderLifecycleOut` now includes `line_items: Optional[List[OrderLineItemOut]]` (added to ORD-004 §4.8–4.9 per ESCALATIONS §A row 29, reconciliation pass 2026-06-10). ORD-011's `get_order_lifecycle` joins `T.order_items` rows when `lifecycle_status` is set. `ShipGroupsPanel` uses `line_items` to label items by name/SKU. `OrderLineItemOut` model is defined in ORD-004 §4.9.

**A3 (minor)**: What nav entry pointing to the customer timeline is most useful? The timeline requires a specific `order_id` URL parameter, so a generic `/orders` nav entry is of limited value. Options: (a) link from the existing `PurchasesPage` "View Lifecycle" button per order row (preferred, keeps nav clean); (b) a sidebar link to `/orders` with a search box. The spec assumes option (a): no new Commerce nav entry for the customer timeline; instead a "View Lifecycle" button is added to each row in `PurchaseHistory.tsx`. This modifies `PurchaseHistory.tsx` which was stated as not-modified above — flag this as a scope clarification.

**A4 (minor)**: Ship-group sub-status transitions (e.g., advancing a single ship group from `allocated → picking`) — does ORD-011 expose a per-ship-group transition endpoint? If not, the `ShipGroupsPanel` is purely informational and the ship group status is only advanced by the order-level transition. The spec treats per-ship-group transitions as out-of-scope for MVP.

**A5**: The `by-ship-date` query uses a `ship_date_bucket` field on ship-group rows (from ORD-003/ORD-009). The frontend needs to produce a `YYYY-MM-DD` date string for the query param. The date picker in the board's ship-date tab uses an HTML `<input type="date">` and passes the value verbatim to `getOrdersByShipDate({ date })`.
