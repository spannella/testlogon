# FXA-003 — DynamoDB tables (assets, depreciation schedule, work orders)

## 1. Summary & Goal

FXA-003 is the DynamoDB schema ticket for the Fixed Assets module. It adds exactly three `TableDef` entries to `scripts/local-ddb-init.py` so that `just restart` (which calls `scripts/local-ddb-init.py`) provisions the three new tables with their GSIs and correct `attr_types`. No service logic, no router, no Pydantic models — those belong to FXA-004 through FXA-007.

The three tables are:

- **`fixed_assets`** — the asset register: one row per fixed asset, keyed by `ASSET#{asset_id}`.
- **`fixed_asset_schedule`** — the straight-line depreciation schedule: one row per depreciation period per asset, keyed by `ASSET#{asset_id}` / `PERIOD#{period:07d}`.
- **`maintenance_orders`** — work orders against assets: one row per work order, keyed by `ASSET#{asset_id}` / `WO#{work_order_id}`.

With `FIXED_ASSETS_ENABLED=false` (the default), these tables exist in DynamoDB but are never accessed — the existing shop, cart, orders, billing, GL, and inventory paths are byte-for-byte unchanged.

## 2. Context & Current State

**`TableDef` / `_resolve_table_name` convention.** `scripts/local-ddb-init.py` defines a frozen `TableDef` dataclass at line 29 with fields `name`, `partition_key`, `sort_key`, `gsi`, and `attr_types`. The `_resolve_table_name(name, fallback)` helper at line 38 returns the setting value when non-empty, otherwise the hardcoded fallback — every table in the file uses this pattern. All three new tables must use it with the table-name settings introduced by FXA-002 (`S.fixed_assets_table_name`, `S.fixed_asset_schedule_table_name`, `S.maintenance_orders_table_name`).

**`attr_types` requirement for numeric GSI sort keys.** `_attribute_definitions` at line 2496 builds the `AttributeDefinitions` list from the partition/sort keys plus GSI keys, all defaulting to type `"S"`, then applies `attr_types` overrides (line 2505: `attrs.update(table.attr_types)`). If a GSI sort key contains integers but is not declared `"N"` in `attr_types`, DynamoDB stores the value as a String; querying with an integer `KeyConditionExpression` then raises `ValidationException` at runtime. Every numeric GSI sort key in this ticket must appear in `attr_types`. This is the numeric-GSI gotcha documented in `CLAUDE.md` and exhibited throughout the file — for example `created_at: "N"` on `sticker_collections` (line 84), `period_end_ts` and `acquired_at` must get the same treatment.

**Existing OFBiz table placement.** The last three `TableDef` entries in `_table_defs()` (lines 2479–2492) are the `returns` table, closing the OFBiz commerce block. The three new FXA tables should be appended immediately after line 2492 (before the list's closing `]` on line 2493), inside a clearly labelled OFBiz Fixed Assets comment block.

**`_ensure_table` idempotency.** `_ensure_table` at line 2534 checks `if table.name in existing` and adds only missing GSIs — re-running `just restart` against an already-provisioned stack will never fail or corrupt existing data. New tables are created with `BillingMode: PAY_PER_REQUEST` (line 2582); DynamoDB Local accepts the same argument.

**Settings dependencies (FXA-002).** FXA-003 reads `S.fixed_assets_table_name` (default `"fixed_assets"`), `S.fixed_asset_schedule_table_name` (default `"fixed_asset_schedule"`), and `S.maintenance_orders_table_name` (default `"maintenance_orders"`). These settings are introduced by FXA-002 in `app/core/settings.py`. FXA-003 must not be merged before FXA-002 is merged; if the FXA-002 settings are not present, `S.<name>` will raise `AttributeError` at init time.

**Tables handles (FXA-002).** `app/core/tables.py` exposes `T.fixed_assets`, `T.fixed_asset_schedule`, and `T.maintenance_orders` (added by FXA-002). FXA-003 creates the physical tables that those handles point to.

**`_wait_for_tables` and GSI readiness.** `main()` at line 2664 calls `_wait_for_tables(ddb, created)` which polls each table's `GlobalSecondaryIndexes.IndexStatus` until all reach `ACTIVE`. This is required for DynamoDB Local (line 2613–2624). FXA-003 tables with GSIs will correctly flow through this wait.

## 3. Data Model

### 3.1 `fixed_assets` table

Holds one item per fixed asset. The single-item-per-asset design (no fan-out sub-items) avoids transaction complexity for CRUD; the asset's accumulated depreciation and net book value are denormalized fields updated by the depreciation poster (FXA-007).

| Attribute | Type | Notes |
|---|---|---|
| `pk` | S | `"ASSET#{asset_id}"` — primary partition key |
| `sk` | S | `"META"` — literal string; only one row per asset |
| `owner_sub` | S | Cognito user_sub of the asset owner; GSI_OWNER partition key |
| `acquired_at` | N | Unix timestamp (int, `now_ts()`); GSI_OWNER and GSI_STATUS sort key |
| `status` | S | `"active"` / `"fully_depreciated"` / `"disposed"`; GSI_STATUS partition key |
| `asset_id` | S | UUID; also embedded in `pk` for O(1) lookup |
| *(all other asset fields)* | — | Non-key attributes; no special DDB type constraint |

**GSIs:**

| Index name | Partition key | Sort key | Sort key type | Purpose |
|---|---|---|---|---|
| `GSI_OWNER` | `owner_sub` (S) | `acquired_at` (N) | N | List all assets for a user, sorted by acquisition date |
| `GSI_STATUS` | `status` (S) | `acquired_at` (N) | N | Filter assets by status (e.g. all active, all disposed) |

**`attr_types`:** `{"acquired_at": "N"}` — both GSIs share the same numeric sort key; declaring it once suffices because `_attribute_definitions` deduplicates by attribute name (it builds a dict then converts to list).

**`TableDef` entry:**

```python
# Fixed Assets module (FXA-003) — asset register
TableDef(
    _resolve_table_name(S.fixed_assets_table_name, "fixed_assets"),
    "pk",
    "sk",
    gsi=[
        {"index_name": "GSI_OWNER",  "partition_key": "owner_sub", "sort_key": "acquired_at"},
        {"index_name": "GSI_STATUS", "partition_key": "status",    "sort_key": "acquired_at"},
    ],
    attr_types={"acquired_at": "N"},
),
```

### 3.2 `fixed_asset_schedule` table

Holds one row per depreciation period per asset. The sort key `PERIOD#{period:07d}` (period is a 1-based integer month count, zero-padded to 7 digits) gives natural chronological ordering via lexicographic DynamoDB sort within a single asset partition. The maximum 7-digit zero-pad supports up to 9,999,999 periods — far beyond any realistic useful life.

| Attribute | Type | Notes |
|---|---|---|
| `pk` | S | `"ASSET#{asset_id}"` — same as in `fixed_assets` for easy join by caller |
| `sk` | S | `"PERIOD#{period:07d}"` — e.g. `"PERIOD#0000001"` for month 1 |
| `schedule_status` | S | `"scheduled"` / `"posted"`; GSI_DUE partition key |
| `period_end_ts` | N | Unix timestamp of the end of this depreciation period; GSI_DUE sort key |
| `period` | N | 1-based integer month index |
| `period_start_ts` | N | Unix timestamp of the start of this period |
| `amount_cents` | N | Depreciation amount for this period in integer cents |
| `journal_entry_id` | S | Nullable; set when `schedule_status="posted"` |
| `posted_at` | N | Unix timestamp when this period was posted; null until posting |

**GSIs:**

| Index name | Partition key | Sort key | Sort key type | Purpose |
|---|---|---|---|---|
| `GSI_DUE` | `schedule_status` (S) | `period_end_ts` (N) | N | Depreciation poster queries `schedule_status="scheduled"` with `period_end_ts <= now_ts()` to find all due-but-unposted periods across all assets |

**`attr_types`:** `{"period_end_ts": "N"}`.

**`TableDef` entry:**

```python
# Fixed Assets module (FXA-003) — depreciation schedule (one row per period per asset)
TableDef(
    _resolve_table_name(S.fixed_asset_schedule_table_name, "fixed_asset_schedule"),
    "pk",
    "sk",
    gsi=[
        {"index_name": "GSI_DUE", "partition_key": "schedule_status", "sort_key": "period_end_ts"},
    ],
    attr_types={"period_end_ts": "N"},
),
```

### 3.3 `maintenance_orders` table

Holds work orders against an asset. Multiple work orders per asset are supported via the `WO#{work_order_id}` sort key. The asset-centric partition key (`ASSET#{asset_id}`) allows efficient fetch of all work orders for a given asset using a base-table Query (no GSI needed for that access pattern).

| Attribute | Type | Notes |
|---|---|---|
| `pk` | S | `"ASSET#{asset_id}"` |
| `sk` | S | `"WO#{work_order_id}"` |
| `wo_status` | S | `"open"` / `"in_progress"` / `"completed"` / `"cancelled"`; GSI_WO_STATUS partition key |
| `created_at` | N | Unix timestamp (`now_ts()`); GSI_WO_STATUS and GSI_WO_ASSIGNEE sort key |
| `assignee_sub` | S | Cognito user_sub of the assignee; GSI_WO_ASSIGNEE partition key |
| `work_order_id` | S | UUID; also embedded in `sk` |
| `asset_id` | S | Denormalized for cross-table access |
| *(other work-order fields)* | — | Non-key attributes |

**GSIs:**

| Index name | Partition key | Sort key | Sort key type | Purpose |
|---|---|---|---|---|
| `GSI_WO_STATUS` | `wo_status` (S) | `created_at` (N) | N | Open work-order queue: filter by `wo_status="open"`, sorted oldest-first |
| `GSI_WO_ASSIGNEE` | `assignee_sub` (S) | `created_at` (N) | N | List all work orders for a given assignee, newest-first or oldest-first |

**`attr_types`:** `{"created_at": "N"}` — both GSIs share `created_at`; one entry covers both.

**`TableDef` entry:**

```python
# Fixed Assets module (FXA-003) — maintenance work orders
TableDef(
    _resolve_table_name(S.maintenance_orders_table_name, "maintenance_orders"),
    "pk",
    "sk",
    gsi=[
        {"index_name": "GSI_WO_STATUS",   "partition_key": "wo_status",    "sort_key": "created_at"},
        {"index_name": "GSI_WO_ASSIGNEE", "partition_key": "assignee_sub", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
),
```

### 3.4 Cross-table key relationships

All three tables share the `ASSET#{asset_id}` prefix as their partition key. A caller building a full asset view:

1. `T.fixed_assets.get_item(Key={"pk": "ASSET#X", "sk": "META"})` — single asset record.
2. `T.fixed_asset_schedule.query(KeyConditionExpression=Key("pk").eq("ASSET#X"))` — all periods for that asset, naturally ordered `PERIOD#0000001` … `PERIOD#9999999`.
3. `T.maintenance_orders.query(KeyConditionExpression=Key("pk").eq("ASSET#X"))` — all WOs for that asset.

No DynamoDB transactions are needed for CRUD of individual items; the asset-register service (FXA-005) will use conditional puts for idempotent creation and standard `update_item` for mutations.

## 5. Detailed Behavior & Edge Cases

**Idempotent provisioning.** `_ensure_table` (line 2534) checks `if table.name in existing:` at line 2537. When the table already exists it reconciles missing GSIs (lines 2538–2576) and then `return`s at line 2577 — it never attempts a re-create. Running `just restart` multiple times is safe. The GSI reconciliation block (lines 2538–2576) also adds any missing GSIs to an existing table — this matters if FXA-003 is merged while a partially-provisioned stack exists (e.g. the table was created manually without all GSIs). The `_wait_for_tables` loop at line 2613 will block until all new GSIs reach `ACTIVE` status.

**`attr_types` deduplication.** `_attribute_definitions` builds a dict of attribute names to types (line 2497), meaning if the same attribute name appears as both the base-table sort key and a GSI sort key, the `attr_types` override applies to all references. For `fixed_assets`, `acquired_at` appears as both GSI_OWNER and GSI_STATUS sort key — the single `{"acquired_at": "N"}` entry correctly overrides the default `"S"` for both uses. Similarly for `created_at` in `maintenance_orders`.

**`PERIOD#{period:07d}` lexicographic sort.** DynamoDB sort keys are compared lexicographically for String types. `"PERIOD#0000001"` < `"PERIOD#0000012"` < `"PERIOD#9999999"` holds as long as the zero-padding width (7 digits) is constant. Using `period:07d` in the writer ensures this invariant — failing to zero-pad would break sort order (e.g. `"PERIOD#1"` > `"PERIOD#10"` lexicographically). The `fixed_asset_schedule` service (FXA-007) must always write `sk = f"PERIOD#{period:07d}"` and never a raw integer.

**`GSI_DUE` access pattern details.** The depreciation poster (FXA-007) will query:

```python
T.fixed_asset_schedule.query(
    IndexName="GSI_DUE",
    KeyConditionExpression=Key("schedule_status").eq("scheduled") & Key("period_end_ts").lte(now_ts()),
)
```

This is a range query on a numeric sort key — exactly the use case `attr_types={"period_end_ts": "N"}` supports. Without the `"N"` declaration DynamoDB would store `period_end_ts` as a String and the `lte(now_ts())` comparison would fail with `ValidationException: Condition parameter type does not match schema type`.

**`GSI_WO_STATUS` for open-queue listing.** The admin work-order queue will query `wo_status="open"` sorted by `created_at` ascending (oldest-first). DDB `ScanIndexForward=True` on `GSI_WO_STATUS` gives oldest-first within the `"open"` partition. In-progress orders (`wo_status="in_progress"`) appear in a separate GSI partition and do not pollute the open queue.

**`FilterExpression` pagination pitfall.** If the platform accumulates many `"posted"` schedule rows alongside `"scheduled"` rows in the `fixed_asset_schedule` table, a `GSI_DUE` query scoped to `schedule_status="scheduled"` will return only unposted rows without a `FilterExpression` (the partition key is the filter). However, if the poster additionally filters by `asset_class` or other non-key fields, DynamoDB applies `FilterExpression` after paging — callers must loop `LastEvaluatedKey` to avoid silently dropping items beyond the first 1 MB page. The FXA-007 poster must implement a pagination loop.

**Flag-off behavior.** With `FIXED_ASSETS_ENABLED=false` (default), no service code calls `T.fixed_assets`, `T.fixed_asset_schedule`, or `T.maintenance_orders`. The tables exist in DynamoDB but are empty and incur no read/write cost. The flag affects service and router behavior only, not table existence.

**DynamoDB Local numeric type handling.** DynamoDB Local (port 8001, Java process) honors `AttributeType: "N"` for `attr_types`-declared fields. The existing test suite has validated this for many numeric sort keys (e.g. `created_at: "N"` on `sticker_collections`, line 84; `period_end_ts` and `acquired_at` follow the same well-tested path). No special local-vs-prod divergence exists for type declarations.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity.** `scripts/local-ddb-init.py` runs only during local dev-stack startup (`just restart` / `just up`). In production, the equivalent tables are created via an `aws dynamodb create-table` CLI call or Terraform/CDK prior to deployment. The `TableDef` entries serve as the authoritative schema specification for both paths — no divergence. `BillingMode: PAY_PER_REQUEST` is used in both environments; no capacity planning is needed at table creation.

**Idempotency.** `_ensure_table` is idempotent by design (`scripts/local-ddb-init.py:2534`): when the table already exists (line 2537) it reconciles any missing GSIs (lines 2538–2576) and returns at line 2577 without attempting re-creation. Re-running `local-ddb-init.py` after a partial failure is safe and will converge to the desired schema without data loss.

**No data migration required.** These are new tables with no pre-existing rows. Migration is trivially the creation of the tables themselves.

**Security.** DynamoDB table names resolve from env vars. No secrets or credentials are introduced. Access to the tables in prod is gated by IAM policy (the same policy that grants access to other DDB tables) — FXA-003 requires no new IAM changes beyond extending the existing policy to cover the three new table names.

## 8. Backward Compatibility & Migration

**Zero impact on existing tables.** Adding entries to the `_table_defs()` list in `scripts/local-ddb-init.py` is purely additive: `_ensure_table` is called for each entry but only creates or updates tables named in that entry. No existing table is modified.

**FXA-002 prerequisite.** FXA-003 references `S.fixed_assets_table_name`, `S.fixed_asset_schedule_table_name`, and `S.maintenance_orders_table_name`. If FXA-002 has not been merged, `S.<attr>` raises `AttributeError` at `_table_defs()` call time. FXA-003 must be delivered and merged after FXA-002.

**Dev-stack restart required.** Developers running an existing local stack will need to run `just restart` after merging FXA-003 to create the three new tables. `just up` also calls `local-ddb-init.py` and will create them on a fresh stack. No manual `aws dynamodb create-table` call is needed in the local environment.

**Rolling deployment.** In production, the tables should be created before the FXA-002/003 code reaches any environment. Creating empty tables early is always safe — the service and router are both flag-gated so no DDB writes occur until `FIXED_ASSETS_ENABLED=true` is set.

**Test cases:**

1. **`test_gsi_owner_query_with_integer_sort_key`** — puts two items with distinct `owner_sub` and integer `acquired_at` values, queries `GSI_OWNER` with a `begins_with(pk, "ASSET#")` or range condition, asserts both items are returned in ascending `acquired_at` order. 2. **`test_gsi_status_query_filters_by_status`** — puts items with `status="active"` and `status="disposed"`, queries `GSI_STATUS` partition `"active"`, asserts only the active items are returned.

6. **`test_gsi_wo_assignee_query`** — puts work orders with distinct `assignee_sub` values, queries `GSI_WO_ASSIGNEE` for a specific assignee, asserts the correct subset is returned.

1. **Assumption: FXA-002 merged first.** The spec assumes `S.fixed_assets_table_name`, `S.fixed_asset_schedule_table_name`, and `S.maintenance_orders_table_name` are present in `app/core/settings.py` and that `T.fixed_assets`, `T.fixed_asset_schedule`, and `T.maintenance_orders` are declared in `app/core/tables.py`. If FXA-002 is not yet merged, the `_table_defs()` function will raise `AttributeError` when evaluating `S.fixed_assets_table_name`. Both tickets should be merged in FXA-002 → FXA-003 order.

2. **Assumption: `period:07d` zero-padding is sufficient.** 7-digit zero-padding allows 9,999,999 periods (over 833,000 years of monthly depreciation). This is not a real constraint; the assumption is just that the service layer (FXA-007) will always use `f"PERIOD#{period:07d}"` and never a shorter format string. If a future ticket changes the format, all existing rows with the old format become unsortable relative to new rows. The zero-padding format must be treated as a contract.

3. **Assumption: single `acquired_at` attribute serves both `GSI_OWNER` and `GSI_STATUS`.** The FXA-002 spec (section 3) specifies `GSI_OWNER (owner_sub / acquired_at numeric)` and `GSI_STATUS (status / acquired_at numeric)`. Both use the same `acquired_at` sort key. The `attr_types={"acquired_at": "N"}` declaration covers both. If a future ticket wants a different sort key on one of these GSIs (e.g. `last_updated_at` on `GSI_STATUS`), the `TableDef` and `attr_types` must be updated and the local stack must be restarted to apply the change.

4. **Open question: should `fixed_asset_schedule` also have a base-table GSI for listing all unposted periods for a single asset?** The `GSI_DUE` cross-asset index finds all due periods globally. A per-asset listing of schedule rows uses the base-table partition key `ASSET#{asset_id}` directly (no GSI needed). However, filtering per-asset rows by `schedule_status` within a base-table Query requires a `FilterExpression`, which DynamoDB applies after paging. If an asset has many `posted` periods, a base-table query for `scheduled` periods for that asset may require multiple pages. For a typical useful life of 3–7 years (36–84 periods), one DDB page (1 MB) comfortably holds all rows; no additional GSI is needed. **Assumption:** useful life does not exceed ~500 periods; a per-asset schedule is always fetchable in a single Query page.

5. **Open question: should `maintenance_orders` support querying open work orders for a specific asset?** The base-table partition key `ASSET#{asset_id}` covers "all WOs for asset X", and adding a `FilterExpression` for `wo_status="open"` is sufficient for the expected per-asset WO count (tens, not thousands). The `GSI_WO_STATUS` covers the global open-queue scenario. No additional compound GSI is assumed necessary.

6. **Assumption: `wo_status` values are a closed enum.** `GSI_WO_STATUS` is partitioned on the string value `"open"` / `"in_progress"` / `"completed"` / `"cancelled"`. If a new status value is introduced later (e.g. `"on_hold"`), existing `GSI_WO_STATUS` queries for `"open"` are unaffected; the new status creates a new partition in the index automatically. No schema migration is needed for new enum values.
