# FXA-001 — Fixed-assets scoping spike & GL-touchpoint delta

## 1. Summary & Goal

FXA-001 is the P0 foundational spike for the Fixed Assets work stream. Its deliverable is this design document: a precise, code-grounded scope declaration for the OFBiz FixedAsset application, a mapping of all accounting touchpoints, the complete DynamoDB data-model delta (three new tables with all PK/SK/GSIs and `attr_types`), every new Pydantic model shape, all new `Settings` keys and flags, and a documented decision log that downstream FXA-002 through FXA-017 tickets reference.

No implementation code ships with this ticket. The deliverable is this spec and reviewer sign-off that:

- The module is entirely additive. With `FIXED_ASSETS_ENABLED` off, every existing code path (shop, cart, orders, billing, inventory, GL) is byte-for-byte unchanged.
- Depreciation posts a balanced non-cash journal (Dr Depreciation Expense / Cr Accumulated Depreciation) directly to the double-entry GL journal (`app/services/gl_posting.py`, built by OFB-014). It does NOT call `billing_shared.new_ledger_entry` — no money moves.
- Disposal-with-proceeds routes money-out through the existing `refund_payment` / `settle_or_reverse_ledger` path (`app/routers/billing.py:1287`) — no parallel billing mechanism is introduced.
- All three deferred scopes (declining-balance/units-of-production depreciation, asset revaluation, lease accounting, multi-currency) are explicitly OUT of scope for this work stream.

## 2. Context & Current State

### 2.1 The fixed-assets scope decision

`docs/ofbiz-full-buildout-plan.md:50` initially classified Asset Maintenance / FixedAsset as "OUT (recommend)" in the Phase N row. The decision to reverse this — building fixed assets as an additive, flag-gated module — is recorded here. Scope IN:

- Fixed-asset register (CRUD, status lifecycle: active / fully_depreciated / disposed).
- Straight-line depreciation schedule generation and automated GL posting.
- Basic maintenance work orders (open → in_progress → completed / cancelled) per asset.

Scope explicitly OUT for this work stream (deferred, no code):

- Declining-balance or units-of-production depreciation.
- Asset revaluation / impairment.
- Lease accounting (IFRS 16 / ASC 842 right-of-use assets).
- Multi-currency asset records.
- Maintenance expense capitalization to asset cost.

### 2.2 Existing single-entry ledger

`app/services/billing_shared.py:224` defines `new_ledger_entry(*, key_name, key_value, entry_type, amount_cents, state, reason, meta=None, extra=None)` — the canonical write path for any money movement. It generates a ULID-ish `entry_id` via `ulidish()` (`billing_shared.py:216`) and a `LEDGER#{ts}#{entry_id}` sort key via `ledger_sk()` (`billing_shared.py:220–221`), denormalizes `ledger_date = ledger_date_for_ts(ts)` (`billing_shared.py:253`, helper at `billing_shared.py:10`) for the `GSI_LEDGER_DATE` per-day bucketing used by the platform financial dashboard (FIN-013), and returns `(sk, item)`. The `billing` table's `GSI_LEDGER_DATE` is declared in `scripts/local-ddb-init.py:64–77`.

Depreciation is a non-cash GL entry; it does NOT call `new_ledger_entry`. No money changes hands, so no ledger row, no `ledger_date` denorm, and no effect on balance or provider attribution.

### 2.3 Existing double-entry GL (OFB-013 / OFB-014)

`app/services/gl_accounts.py` (built by OFB-013, not yet merged as of this spike) will provide:

- A seedable chart of accounts with class (`asset`, `liability`, `equity`, `revenue`, `expense`) and normal-balance side (`debit` / `credit`).
- A `seed_default_accounts()` idempotent function that creates standard accounts for existing money flows.

`app/services/gl_posting.py` (OFB-014) will provide:

- A journal store keyed on `T.gl_journal` (DDB table).
- A `post_journal_entry(lines: list[JournalLine]) -> str` function that validates Σdr == Σcr and writes the entry with a deterministic or ULID-ish `journal_id`, returning that id.
- A `get_journal_entry(journal_id)` read path.

Both files are referenced here as the authority; they do not yet exist in the repository at the time of this spike. FXA-008 and FXA-009 both declare `OFB-013` / `OFB-014` as hard dependencies.

The depreciation journal will call `post_journal_entry` directly, bypassing `new_ledger_entry`. The journal entry must balance: Σ(debit lines) == Σ(credit lines). Trial balance (OFB-016) reads from `T.gl_journal` and must remain balanced after each depreciation post.

### 2.4 Disposal money-out path

`app/routers/billing.py:1287` defines `refund_payment(body: StripeRefundReq, ...)` (decorated `@dual_route("POST", "/billing/refund")`). When a fixed asset is sold / disposed with proceeds, the money-out flows through this path: the caller supplies a `payment_intent_id` referencing an existing payment record in `T.billing`, and `refund_payment` issues the Stripe refund, writes a ledger entry via `new_ledger_entry` (`billing.py:1306–1316`), adjusts the balance, reverses the original ledger row via `settle_or_reverse_ledger` (`billing.py:1323–1324`), and emits an `audit_event` (`billing.py:1332`).

The fixed-assets `dispose_asset` service function (FXA-005/FXA-011) accepts an optional `payment_intent_id` and delegates to `refund_payment` for any cash proceeds. No parallel billing mechanism is created. `docs/ofbiz-full-buildout-plan.md:107–108` states this constraint explicitly.

### 2.5 Existing additive / flag-gated pattern

`app/core/settings.py:836–847` holds the inventory + returns flags group immediately preceding the file-manager block (`settings.py:849`):

## 3. Data Model

### 3.1 Three new DynamoDB tables

All three tables are created at stack init time by `scripts/local-ddb-init.py` regardless of the flag state (consistent with the existing additive convention: tables exist; the service layer refuses to serve requests when the flag is off). Table names resolve through `S` settings with string fallbacks via `_resolve_table_name` (`scripts/local-ddb-init.py:38`, returns `name or fallback`).

#### Table: `fixed_assets`

Holds one row per registered asset.

| Attribute | Type | Description |
|-----------|------|-------------|
| `pk` | S | `ASSET#{asset_id}` — partition key |
| `sk` | S | `META` — sort key (only one row per asset for now) |
| `owner_sub` | S | GSI_OWNER partition key: the user/org who owns the asset |
| `acquired_at` | N | GSI_OWNER sort key; GSI_STATUS sort key (Unix timestamp int) |
| `status` | S | GSI_STATUS partition key: `active` / `fully_depreciated` / `disposed` |
| `asset_id` | S | Stable id, derived from sha256(correlation_id)[:32] |
| `name` | S | Human-readable name |
| `asset_class` | S | e.g. `equipment`, `furniture`, `software` |
| `acquisition_cost_cents` | N | Total cost at acquisition |
| `salvage_value_cents` | N | Expected residual value at end of useful life |
| `useful_life_months` | N | Schedule length |
| `depreciation_method` | S | `straight_line` (only value accepted) |
| `accumulated_depreciation_cents` | N | Running total, updated per period post |
| `gl_asset_account_id` | S | OFB-013 GL account for Fixed Assets |
| `gl_accum_depr_account_id` | S | OFB-013 GL account for Accumulated Depreciation |

**GSIs:**

### 4.4 New `app/routers/fixed_assets.py` — endpoints

Router: `fixed_assets_router = APIRouter(prefix="/ui/fixed-assets", tags=["fixed-assets"])`.

All handlers call `_require_enabled()` as the first line. All use `Depends(require_admin_or_root_csrf)` (`app/auth/policy.py:100–106`) for mutating methods (`POST`, `PATCH`) and `Depends(require_admin_or_root)` (`app/auth/policy.py:67–68`) for read endpoints. This is intentionally more restrictive than the inventory router (where reads use `require_ui_session` — `app/routers/inventory.py:10`); fixed-asset records are finance-sensitive and should not be visible to unauthenticated or non-admin sessions.

**Route declaration order** — literal sub-paths must appear before dynamic `/{asset_id}` captures (CLAUDE.md gotcha):

```
POST   /ui/fixed-assets                          # create_asset_endpoint
GET    /ui/fixed-assets                          # list_assets_endpoint
GET    /ui/fixed-assets/work-orders              # list_work_orders_queue (declared FIRST)
GET    /ui/fixed-assets/{asset_id}               # get_asset_endpoint
PATCH  /ui/fixed-assets/{asset_id}               # update_asset_endpoint
POST   /ui/fixed-assets/{asset_id}/dispose       # dispose_asset_endpoint
GET    /ui/fixed-assets/{asset_id}/schedule      # get_schedule_endpoint
POST   /ui/fixed-assets/{asset_id}/work-orders   # create_work_order_endpoint
GET    /ui/fixed-assets/{asset_id}/work-orders   # list_work_orders_for_asset
PATCH  /ui/fixed-assets/work-orders/{work_order_id}  # transition_work_order_endpoint
```

`PATCH /ui/fixed-assets/work-orders/{work_order_id}` is a top-level (non-nested) route so it must also precede `/{asset_id}`. In practice, FastAPI matches on the full path, so `work-orders/{work_order_id}` vs `{asset_id}` is unambiguous as long as the `GET /ui/fixed-assets/work-orders` (no trailing segment) is declared before `/{asset_id}`.

**Response models:** each endpoint declares `response_model=FixedAssetOut`, `DepreciationScheduleOut`, or `MaintenanceOrderOut` as appropriate. List endpoints return a `{"items": [...], "count": N, "cursor": str|null}` shape following the inventory / host-inventory convention.

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent asset creation

`asset_id = hashlib.sha256((correlation_id or f"asset:{uuid4().hex}").encode()).hexdigest()[:32]`, following `app/services/commerce_order_service.py:67`. A `put_item` with `ConditionExpression="attribute_not_exists(pk)"` is attempted. On `ConditionalCheckFailedException`, the service reads and returns the existing record — same conditional-put / read-on-collision approach used in `_mark_token_consumed` (`app/services/cart_reminders.py:207`, `ConditionExpression="attribute_not_exists(pk)"`).

### 5.2 Straight-line schedule math

`depreciable_base = acquisition_cost_cents - salvage_value_cents`. Period amount = `depreciable_base // useful_life_months`. The final period absorbs the rounding remainder: `final_amount = depreciable_base - (period_amount * (useful_life_months - 1))`. This guarantees `sum(amounts) == depreciable_base` with no fractional-cent drift.

`period_start_ts` for period N = `acquired_at + (N-1) * 30 * 86400` (approximate calendar month as 30 days — a simplification that avoids calendar-month arithmetic; exact calendar months are deferred). `period_end_ts = period_start_ts + 30 * 86400 - 1`.

### 5.3 Depreciation journal posting (non-cash, balanced, idempotent)

`journal_id = hashlib.sha256(f"{asset_id}:period:{period}".encode()).hexdigest()[:32]` — deterministic per `(asset_id, period)`.

Journal lines:
- Debit `gl_depr_expense_account_id` for `amount_cents`.
- Credit `gl_accum_depr_account_id` for `amount_cents`.

`post_journal_entry([debit_line, credit_line])` in `app/services/gl_posting.py` validates Σdr == Σcr before writing. If the period row already shows `schedule_status="posted"`, `post_depreciation_period` returns immediately (no second GL write). The `journal_id` uniqueness is enforced by the `attribute_not_exists(journal_id)` conditional on the GL journal table (OFB-014's responsibility).

After a successful post:
- `fixed_asset_schedule` row flipped: `schedule_status="posted"`, `journal_entry_id=journal_id`, `posted_at=now_ts()`.
- `fixed_assets` row: `accumulated_depreciation_cents` incremented via `update_item` with `ADD`.
- If `accumulated_depreciation_cents >= depreciable_base`: `status="fully_depreciated"`.

### 5.4 Disposal journal (balanced, idempotent, FXA-011)

On disposal, the service posts a closing journal with four lines (all via `post_journal_entry`):

1. Debit `gl_accum_depr_account_id` for `accumulated_depreciation_cents` (removing the contra-asset).
2. Credit `gl_asset_account_id` for `acquisition_cost_cents` (removing the asset).
3. Debit or Credit `gl_gain_loss_account_id` for the plug — gain if `proceeds > net_book_value_cents`, loss otherwise.
4. If proceeds > 0: Debit `Cash / Accounts Receivable` for `proceeds_amount_cents`.

A disposal with cash proceeds additionally calls `refund_payment(StripeRefundReq(payment_intent_id=..., amount_cents=...))` via the existing router function. The disposal journal `journal_id = hashlib.sha256(f"{asset_id}:disposal:{correlation_id}".encode()).hexdigest()[:32]`.

Remaining `scheduled` periods are updated to `schedule_status="cancelled"` in batch (query `GSI_DUE` for this asset's scheduled periods and write `cancelled`). A `disposed` asset rejects further `post_depreciation_period` calls (service guard).

### 5.5 Work-order lifecycle

Legal transitions: `open → in_progress`, `open → cancelled`, `in_progress → completed`, `in_progress → cancelled`. All other transitions (e.g. `completed → open`) raise HTTP 409 with `detail="illegal_transition"`. The transition validator uses a `VALID_TRANSITIONS: dict[str, set[str]]` constant in the service, not a state-machine class.

Creating a work order against a `disposed` asset raises HTTP 400 (`detail="asset_disposed"`).

### 5.6 `GSI_DUE` poster pagination

The background poster MUST paginate via `LastEvaluatedKey` because DynamoDB applies `FilterExpression` after the 1 MB page fetch — a single `query` call on a busy index can silently miss due items (CLAUDE.md "DDB FilterExpression doesn't reduce page size" gotcha). The poster loop:

```python
exclusive_start = None
while True:
    kwargs = {
        "IndexName": "GSI_DUE",
        "KeyConditionExpression": Key("schedule_status").eq("scheduled") & Key("period_end_ts").lte(now_ts()),
        "Limit": 100,
    }
    if exclusive_start:
        kwargs["ExclusiveStartKey"] = exclusive_start
    resp = T.fixed_asset_schedule.query(**kwargs)
    for row in resp.get("Items", []):
        post_depreciation_period(asset_id_from(row), period_from(row))
    exclusive_start = resp.get("LastEvaluatedKey")
    if not exclusive_start:
        break
```

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity:** The service code has zero `if S.dev_mode` branches. The three DDB tables exist in both environments (created by `scripts/local-ddb-init.py` in dev; by CDK/Terraform in prod). The GL journal calls (`post_journal_entry`) go through `T.gl_journal` — moto-backed in dev, real DDB in prod. No mock-only branch for any fixed-asset write.

**Idempotency contract:**

- Asset create: deterministic `asset_id = sha256(correlation_id)[:32]`; conditional put; read-and-return on collision.
- Depreciation post: deterministic `journal_id = sha256(f"{asset_id}:period:{period}")[:32]`; conditional put on GL journal; `schedule_status="posted"` guard in schedule row prevents double-increment.
- Disposal journal: deterministic `journal_id = sha256(f"{asset_id}:disposal:{correlation_id}")[:32]`; conditional put.
- Work-order create: deterministic `work_order_id = sha256(correlation_id)[:32]`; conditional put.

**Security:**

- All mutating endpoints (`POST`, `PATCH`) use `require_admin_or_root_csrf` (`app/auth/policy.py:100–106`) — enforcing both role and CSRF token for cookie-auth clients (mutation pattern mirrors `app/routers/inventory.py:48,65,81`). Bearer-token callers skip CSRF per the existing `enforce_cookie_csrf` logic (`app/auth/policy.py:71–97`).
- Read endpoints use `require_admin_or_root` (no CSRF needed for GET).
- No PII is stored on asset records beyond `owner_sub` (a Cognito sub, not an email address).
- Disposal money-out through `refund_payment` inherits all existing Stripe fraud-gate and provider-toggle guards (`app/services/payment_provider_health.py:440` `is_provider_enabled`; `app/services/fraud_detection.py:262` `evaluate_transaction`, `fraud_detection.py:428` `is_frozen`; GAP-0206/0207).

## 8. Backward Compatibility & Migration

**No schema migrations required** for existing tables. The three new tables are created fresh; no columns are added to `billing`, `catalog`, `inventory`, `reservations`, or `returns`.

**`just restart` behavior:** `scripts/local-ddb-init.py` runs `_table_defs()` on every restart and issues `create_table` (idempotent via `ResourceInUseException` suppression). The three new `TableDef` entries are appended; existing tables are untouched.

**Prod rollout:** The `FIXED_ASSETS_ENABLED` flag defaults to `false`, so the feature can be deployed to prod before it is enabled. DDB table creation (`CreateTable`) in prod must precede deploying the code that references the handles — standard pre-deploy migration.

**GL account seed (FXA-008):** The four new GL accounts (`Fixed Assets`, `Accumulated Depreciation`, `Depreciation Expense`, `Gain/Loss on Disposal`) are seeded idempotently by `gl_accounts.seed_default_accounts()` (OFB-013). If OFB-013 has not yet been deployed to prod, FXA-008 is blocked (declared dependency). No GL account ids are hard-coded in the fixed-assets service; they are resolved at asset-registration time from the seeded chart.

## 10. Open Questions / Assumptions

1. **Calendar-month vs. 30-day periods:** This spec uses 30-day periods for simplicity. The assumption is that 30-day periods are acceptable for a first implementation; exact calendar months (28/29/30/31 days) are deferred. This must be confirmed with the finance reviewer at sign-off.

2. **GL account IDs at asset registration:** This spec assumes the four seeded GL account IDs (from FXA-008 / OFB-013) are looked up by account `code` or `name` at asset-registration time and stored on the asset row. If `app/services/gl_accounts.py` uses a different lookup key (e.g. a numeric code vs. a slug string), FXA-008 must document the exact resolver signature before FXA-005 is implemented.

3. **`post_journal_entry` signature:** The exact function signature of `post_journal_entry` in `app/services/gl_posting.py` (OFB-014) is assumed to be `post_journal_entry(lines: list[JournalLine], *, journal_id: str | None = None) -> str`. If OFB-014 uses a different shape, FXA-009 must adapt. This is a hard dependency.

4. **`refund_payment` as an HTTP handler vs. a service function:** `app/routers/billing.py:1287` defines `refund_payment` as a FastAPI route handler with `Depends(require_ui_session)`. For disposal, the fixed-assets service calls the underlying billing logic, not the router handler directly. The assumption is that the billing write path will be extracted into a service function (or that the service calls `stripe.Refund.create` + `new_ledger_entry` inline, mirroring the existing pattern). This must be resolved at FXA-011 time.

5. **503 vs. 404 for disabled flag:** Inventory uses HTTP 404 (`app/services/inventory.py:56`). The ticket states 503. This spec uses 503 to match the ticket; the discrepancy with the inventory precedent should be confirmed with the team. Either is acceptable; consistency across the new fixed-assets service matters more than matching inventory.

6. **`owner_sub` scope:** This spec treats `owner_sub` as the registering admin's `user_sub`. An organization-level asset (shared across users) may require a different ownership model. The assumption is single-user ownership for now; org-level is deferred.

7. **Multi-currency deferred:** All `amount_cents` fields are implicitly USD. Adding a `currency` field later is additive but would require a new GSI or index for cross-currency reporting. Confirmed OUT of scope per ticket.
