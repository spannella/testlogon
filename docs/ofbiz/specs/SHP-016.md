# SHP-016 — Shipping TypeScript types & API endpoints

## 1. Summary & Goal

SHP-016 is a pure frontend ticket. It has two deliverables:

1. **TypeScript interfaces** appended to `frontend/src/api/types.ts` that mirror, 1-to-1, the Pydantic response shapes defined by SHP-003 in `app/models.py` and used by the SHP-005 (carrier admin), SHP-007 (rate estimation), SHP-011 (shipments lifecycle + buyer read), and SHP-013 (per-shipment poll) routers.
2. **Endpoint wrappers** in a new file `frontend/src/api/endpoints/shipping.ts`, following the pattern established by `frontend/src/api/endpoints/carrierTracking.ts` (30 lines) and `frontend/src/api/endpoints/cart.ts`, using the shared `api` axios wrapper from `frontend/src/api/client.ts`.

No runtime behaviour changes occur with `SHIPPING_ENABLED=false`: the backend returns HTTP 503 for every shipping endpoint (`_ensure_enabled()` pattern — `docs/ofbiz/specs/SHP-005.md:57–64`), and the frontend wrappers are simply never called.

No new pages, routes, or React Query hooks are introduced here; those are SHP-017 (admin UI) and SHP-018 (buyer UI). SHP-016 is the typed foundation both downstream tickets import from.

**Key design decisions for the TypeScript types:**

- **`status: string` not `Literal`**: mirrors the Python `ShipmentOut.status: str` (not `Literal`) decision in `docs/ofbiz/specs/SHP-003.md:250`. Using a TS union would require updating the types file if the state machine gains a new value (e.g. `pending_fulfillment`). `string` is safe here and consistent with `PurchaseTransactionSummary.status: string` at `types.ts:2721`.
- **Carrier code as union type**: `"ups" | "fedex" | "usps" | "dhl" | "manual"` provides compile-time exhaustiveness checking for input models (`CarrierIn`, `ShipmentIn`, `ShipmentStatusTransitionIn`) without sacrificing flexibility for response models where the value is read from the server.
- **`Record<string, unknown>` for address**: mirrors the Python `Dict[str, Any]` on `ShipGroupIn.ship_to_address` and `ShipmentIn.ship_to_address` (`docs/ofbiz/specs/SHP-003.md:192–199`). A typed `AddressIn` sub-interface would couple the types to the address schema, adding an unwanted dependency.
- **`tracking_url?: string | null`**: computed at read time by the backend via `build_tracking_url(carrier, tracking_number)` from `app/services/carrier_tracking.py:33` [VERIFIED: `app/services/carrier_tracking.py:33`]; never stored in DDB. Mirrors `CarrierTrackingView.tracking_url?: string | null` at `types.ts:2753` [VERIFIED: `frontend/src/api/types.ts:2753`].

## 5. Detailed Behavior & Edge Cases

### 5.1 `status` field: string not literal union

`ShipmentOut.status` is typed as `string` because `app/models.py`'s `ShipmentOut.status` is `str` (not `Literal[...]`) — the spec rationale is at `docs/ofbiz/specs/SHP-003.md:250`. Adding a TypeScript union `"draft" | "pending_fulfillment" | "label_created" | ...` would need updating every time the state machine adds an edge. The current set is:

| Status string | Phase |
|---|---|
| `draft` | Pre-submission |
| `pending_fulfillment` | Awaiting warehouse pick |
| `label_created` | Label printed |
| `picked_up` | Carrier has package |
| `in_transit` | Moving through carrier network |
| `out_for_delivery` | On delivery vehicle |
| `delivered` | Delivered |
| `exception` | Carrier exception |
| `returned` | Returned to sender |
| `cancelled` | Voided |

Of the seven tracking-phase statuses listed above, six (`label_created`, `picked_up`, `in_transit`, `out_for_delivery`, `delivered`, `exception`) are the actual return values of `map_carrier_status` at `app/services/carrier_tracking.py:84`. **`returned` is NOT produced by `map_carrier_status`** — "returned to sender" maps to `"exception"` at `carrier_tracking.py:104`. `returned` is a shipping-module addition (alongside `draft` and `cancelled`) that the service layer may set via state-machine transitions, but never via the carrier-normalization path (verified: `carrier_tracking.py:84–117`). Consumer code using `===` comparisons will receive type narrowing naturally in TypeScript even against a plain `string` field.

### 5.2 `estimateShippingRateForCart` body shape

`POST /ui/shop/shipping/estimate/cart/{cart_id}` resolves the line items from the caller's active cart server-side (via `list_items(user_sub, cart_id)` reused from `app/services/shoppingcart.py:277`, as described in `docs/ofbiz/specs/SHP-007.md:32–44`). The caller must still supply `destination_zip` and optionally `carrier_code`/`method_code` to filter results. The `Omit<ShippingRateRequest, "line_items">` type reflects this: `line_items` is ignored if supplied because the backend resolves them from DDB rather than accepting them from the request body. Making this explicit at the TS level avoids misleading callers about what the endpoint reads.

### 5.3 `disableCarrier` uses `api.del`

`DELETE /ui/shipping/carriers/{carrier_id}/disable` — the `disable` suffix is a named action following the OFBiz pattern for soft-deletes. Unlike a true DELETE that removes the row, this sets `enabled=false` and leaves all historical shipments intact. The TS wrapper uses `api.del` (consistent with `removeCartItem` in `cart.ts:38` [VERIFIED: `frontend/src/api/endpoints/cart.ts:37–38`]) which maps to `method: "DELETE"` in `client.ts:312` [VERIFIED: `frontend/src/api/client.ts:312`].

### 5.4 CSRF enforcement

All `api.post`, `api.patch`, `api.put`, and `api.del` calls in the shipping wrappers automatically attach the `X-CSRF-Token` header from the `ui_csrf` cookie, because `client.ts:179–182` attaches it unconditionally on every non-GET request [VERIFIED: `frontend/src/api/client.ts:179–182`]. Bearer-token callers (E2E `request` fixture, programmatic API clients) skip the CSRF enforcement on the backend per the `require_ui_session` (`app/services/sessions.py:330` [VERIFIED]) and `require_admin_or_root_csrf` (`app/auth/policy.py:100` [VERIFIED]) dep behaviour documented in `CLAUDE.md §CSRF`.

### 5.5 `listShipmentsByStatus` query parameter

`GET /ui/shop/shipments` requires `status` as a mandatory query parameter (the backend raises HTTP 422 if absent — `Query(...)` with no default in `docs/ofbiz/specs/SHP-011.md:232`). The TypeScript wrapper enforces this via `status: string` as a required positional argument with no default; callers cannot omit it.

### 5.6 `tracking_url` is computed, never stored

`ShipmentOut.tracking_url` is populated by the backend at serialization time via `build_tracking_url(carrier, tracking_number)` from `app/services/carrier_tracking.py:33` [VERIFIED]. It is `null` when no tracking number is set or when the carrier is `manual`. ### 5.7 `CarrierPollShipmentOut` vs `CarrierPollTransactionOut`

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity**: SHP-016 is a pure TypeScript types + endpoint-wrapper ticket. No backend logic is introduced here; all SECOPS-007 concerns (same code path dev and prod, no `dev_mode` bypass, no mock-only branches) belong to SHP-003 through SHP-013. The frontend wrappers call the same URL paths in both environments; the Vite proxy at `frontend/vite.config.ts` transparently routes `/ui` → `http://localhost:8000` in dev [VERIFIED: `frontend/vite.config.ts:67`] and the same paths are served by the FastAPI app in production.

**Idempotency**: the wrappers are pass-through HTTP clients; idempotency of the underlying operations is enforced by the service layer:
- Carrier create: deterministic `carrier_id = sha256(carrier_code)[:16]` (SHP-004).
- Shipment create: deterministic `shipment_id = sha256("shipment:{order_id}:{ship_group_seq}")[:32]` at `docs/ofbiz/specs/SHP-008.md:63–67`.
- Rate quote: `request_id = sha256(inputs)[:16]`; same inputs → same `request_id` and identical options list (SHP-006/SHP-007).

**Security**: no credentials, tokens, or secrets are constructed client-side by the shipping wrappers. The `api()` function in `client.ts` attaches the `Authorization: Bearer <accessToken>` header from `useAuthStore` and the `X-CSRF-Token` from the `ui_csrf` cookie; shipping wrappers rely on this transparently.

**Authorization**: the backend enforces `require_admin_or_root` (`app/auth/policy.py:67` [VERIFIED]) / `require_admin_or_root_csrf` (`app/auth/policy.py:100` [VERIFIED]) on admin mutating endpoints and `require_ui_session` (`app/services/sessions.py:330` [VERIFIED]) on buyer and estimation endpoints. The TypeScript layer has no mirrored role checks; admin-gated wrappers will receive HTTP 403 if called by a non-admin session, and the `ApiError` is surfaced to the caller as usual per `client.ts:250–266` [VERIFIED: `frontend/src/api/client.ts:250–266`].

## 10. Open Questions / Assumptions

1. **`CarrierListOut` shape**: assumed `{ carriers: CarrierOut[], cursor?: string | null }` consistent with paginated DDB patterns elsewhere (e.g. `PaginatedList<T>` at `types.ts:2209`). If SHP-005 returns a plain array instead, `CarrierListOut` should be replaced with `CarrierOut[]`. **Action**: verify against `app/routers/shipping_carriers.py:list_carriers` response model when SHP-005 is implemented.

2. **`disableCarrier` HTTP method**: assumed `DELETE /ui/shipping/carriers/{carrier_id}/disable` based on the SHP-005 ticket description ("disable" as a named sub-resource action). If SHP-005 uses `PATCH /ui/shipping/carriers/{carrier_id}` with `{ enabled: false }` instead, `disableCarrier` should be replaced with a call to `updateCarrier(carrierId, { enabled: false })`. **Action**: confirm against the SHP-005 implementation.

3. **`estimateShippingRateForCart` body**: assumed that when calling with a cart ID the backend accepts the same `ShippingRateRequest` body minus `line_items` (which it resolves from DDB). If the cart-estimate endpoint uses a different, narrower request model (e.g. only `destination_zip`), the TS input type should be tightened accordingly. **Action**: confirm against `app/routers/shipping_rates.py` request model when SHP-007 is implemented.

4. **`assignItemToPackage` response shape**: assumed the endpoint returns `ShipmentPackageOut` (the updated package) consistent with `docs/ofbiz/specs/SHP-011.md:283–288`. If it returns a different shape (e.g. `ShipmentOut` with full packages), the wrapper's return type must be updated.

5. **`PackingStatusOut.items` array shape**: the spec at `docs/ofbiz/specs/SHP-011.md:300–302` states the response carries a `pack_complete` flag and is "useful for warehouse UX" but does not detail the full items breakdown. The assumed shape `{ item_id, ordered_qty, packed_qty, remaining_qty }[]` is a reasonable inference from the packing semantics (SHP-009). **Action**: confirm the exact response model from `app/services/shipments.get_packing_status` when SHP-009 is implemented.

6. **Carrier method union types**: `method_code` is typed as `"ground" | "express" | "overnight" | "economy" | "flat_rate"` on `ShipmentMethodIn` mirroring the Pydantic pattern constraint at `docs/ofbiz/specs/SHP-003.md:131`. `ShipmentMethodOut.method_code` is typed as plain `string` (not union) because server responses are not validated client-side and new method codes may be added. This asymmetry is intentional and consistent with the `carrier_code` treatment on `CarrierOut`.

7. **`adminListShipmentsForOrder` path**: The full path `/ui/shop/shipments/orders/{order_id}/shipments` is derived from the router declaration in `docs/ofbiz/specs/SHP-011.md:334–338` where the `orders` segment is a literal prefix to avoid `/{shipment_id}` capturing it. This must be confirmed against the final `app/routers/shipments.py` registration.

8. **SHP-016 scope relative to SHP-013**: SHP-013 adds `POST /ui/shop/tracking/shipments/{shipment_id}/poll` to the existing `carrier_tracking_poller_router` (prefix `/ui/shop/tracking`). The `pollShipmentTracking` wrapper in `shipping.ts` calls this endpoint. It is plausible that this wrapper belongs in `carrierTracking.ts` for locality; placing it in `shipping.ts` is preferred because it returns `ShipmentOut` (a shipping type), not `CarrierTrackingView`. If the team prefers co-location with the existing carrier poll wrappers, the wrapper should be moved to `carrierTracking.ts` and `CarrierPollShipmentOut` exported from `types.ts` either way.
