# ECM-009 — Apply pricing rules at cart total & checkout

## 1. Summary & Goal

ECM-009 replaces the naive per-line summation in `cart_total_cents` with a
pricing-rule-aware computation: when `STORE_APPLY_PRICING_RULES` is on, cart line
items are run through the OFBiz pricing-rules engine (delivered by OFB-019 in
`app/services/pricing_rules.py`) to produce a structured `CartPricingBreakdownOut`
(subtotal, applied rule lines, rule discount, optional promo-code discount, and
final total). The same breakdown is computed inside `purchase_cart` so the preview
total and the committed charge are always derived from the same function call (no
client/server drift). Applied rule references are persisted onto the order record
and each order line item's `pricing_ref` for auditing and downstream reporting.

With `STORE_APPLY_PRICING_RULES` off, every code path executes byte-for-byte
identically to the pre-ECM-009 state: `cart_total_cents` returns a plain integer,
`purchase_cart` computes `total_cents` by summing `line_total_cents`, and
`ShoppingCartTotalOut` carries only `cart_id`, `total_cents`, and `currency`.

## 2. Context & Current State

### 2.1 Cart total today

`app/services/shoppingcart.py:301–303` defines `cart_total_cents`:

```python
def cart_total_cents(user_sub: str, cart_id: str) -> int:
    items = list_items(user_sub, cart_id)
    return sum(item.get("line_total_cents", 0) for item in items)
```

This plain integer is returned by `GET /ui/shoppingcart/carts/{cart_id}/total`
(`app/routers/shoppingcart.py:169–172`) and serialized as `ShoppingCartTotalOut`
(`app/models.py:982–985`), which currently has three fields: `cart_id`, `total_cents`,
`currency`.

### 2.2 Purchase path today

`purchase_cart` (`app/services/shoppingcart.py:474–734`) recomputes the total
independently at line 496 by summing `line_total_cents` from `list_items`. It then
applies a flat promo-code discount via a lazy import of `validate_promo_code`
(`app/services/promo_codes.py:239`) at lines 551–576, reduces `total_cents` to
`final_total = max(0, total_cents - discount_cents)` at line 578, and commits the
order with `commerce_order_service.create_order_from_line_items`
(`app/services/commerce_order_service.py:132`) at line 581. The `metadata` dict
passed to `create_order_from_line_items` (lines 586–593) stores `cart_id`,
idempotency keys, `promo_code_id`, `discount_cents`, and `original_total_cents`.
Order line items are written to `T.order_items` with a `pricing_ref` dict
(`commerce_order_service.py:98`), but that dict currently carries only the
original catalog pricing fields — no applied-rule references.

### 2.3 Promo code path today

`validate_promo_code` (`app/services/promo_codes.py:239`) validates a code string
and returns a dict with `discount_cents`, `code_id`, `discount_type` and other
fields. `redeem_promo_code` (`app/services/promo_codes.py:398`) performs an atomic
`current_uses` increment with a conditional check against `max_uses` and writes a
redemption row. Both functions survive unchanged: this ticket only extends the
calling site in `purchase_cart` to layer rule discounts before the promo-code
discount rather than replacing the promo path.

### 2.4 Pricing-rules engine (OFB-019 dependency)

`app/services/pricing_rules.py` (delivered by OFB-019) does not yet exist in the
codebase. ECM-009 depends on it being present and exposing a function with the
following contract (defined in OFB-019's spec):

```python
def apply_pricing_rules(
    user_sub: str,
    items: list[dict],           # each item: sku, quantity, unit_price_cents, line_total_cents
    *,
    checkout_type: str = "shop",
) -> PricingBreakdownResult:
    ...
```

where `PricingBreakdownResult` is a dataclass/named-tuple with fields
`subtotal_cents`, `rule_discount_cents`, `applied_rules` (list of rule-line dicts),
and `final_cents_before_promo`. ECM-009 must wrap this call in a `try/except` so a
missing or erroring engine degrades to the legacy summation (consistent with the
`_safe_upstream` contract introduced by ECM-002).

### 2.5 Store-integration module (ECM-002 dependency)

`app/services/store_integration.py` (delivered by ECM-002) does not yet exist. It
will expose `_integration_enabled(sub_flag: str) -> bool` which reads

`_integration_enabled("store_apply_pricing_rules")` to gate the new path.

## 3. Data Model

### 3.1 No new DynamoDB tables

ECM-009 does not introduce any new DynamoDB tables. All writes go to existing
tables already created by earlier scripts.

### 3.2 Additive attributes on existing items

**`shopping_cart` cart record** — the following fields are written alongside the
existing set at purchase-commit time (inside the `UpdateExpression` that sets
`#status = PURCHASED` at `shoppingcart.py:600–626`):

| New attribute | Type | Description |
|---|---|---|
| `rule_discount_cents` | N | Sum of rule discounts applied (0 when rules off or no rules matched) |
| `applied_rule_ids` | SS (string set) | Rule IDs from `PricingBreakdownResult.applied_rules` (omitted if empty) |
| `pricing_breakdown_version` | S | Version tag from the rules engine (e.g. `"1"`) for forward compatibility |

These are appended to the `update_expr` / `expr_values` block conditionally (only
when `rule_discount_cents > 0` or `applied_rule_ids` is non-empty), mirroring how
`promo_code_id` and `discount_cents` are conditionally appended at lines 617–620.

**`orders` metadata** — `commerce_order_service.create_order_from_line_items` accepts
an arbitrary `metadata` dict (`commerce_order_service.py:83`). ECM-009 extends the
dict passed at `shoppingcart.py:586–593` with two additive keys:

| Key | Value |
|---|---|
| `rule_discount_cents` | int — total rule discount (0 when off) |
| `applied_rules` | list[dict] — each `{rule_id, rule_name, discount_cents}` (empty list when off) |

**`order_items` pricing_ref** — each serialized order line item already carries a
`pricing_ref` dict (`commerce_order_service.py:98`). The dict is populated by
`from_shopping_cart_item` (`app/services/commercial_line_items.py:39`) which is
called inside `_commercial_line_items_from_cart_items` (`shoppingcart.py:198`).
ECM-009 extends the upstream `CommercialLineItem.pricing_ref` dict with two
optional additive keys:

| Key | Value |
|---|---|
| `applied_rule_id` | str — the rule whose discount was allocated to this line (empty string when none) |
| `line_rule_discount_cents` | int — per-line portion of the rule discount (0 when none) |

These are additive: existing readers of `pricing_ref` see the same fields they
always did; the new keys are present only when rules are on and a rule matched.

### 3.3 No `attr_types` additions required

All new attributes written to `shopping_cart` and `orders` are not GSI sort keys,
so no `attr_types` additions are needed in `scripts/local-ddb-init.py`.

## 4. API / Service Design

### 4.1 New function: `cart_pricing_breakdown`

**File**: `app/services/shoppingcart.py`

```python
def cart_pricing_breakdown(
    user_sub: str,
    cart_id: str,
) -> "CartPricingBreakdownOut":
    """
    Return the pricing breakdown for an open cart.
    When STORE_APPLY_PRICING_RULES is off, returns a trivial breakdown
    (subtotal == final_total, no rule lines) with zero discount — byte-for-byte
    equivalent to the old cart_total_cents() result.
    """
```

Internal logic:

1. Call `list_items(user_sub, cart_id)` to get line items.
2. Compute `subtotal_cents = sum(item["line_total_cents"] for item in items)`.
3. If `_integration_enabled("store_apply_pricing_rules")`:
   a. Call `_safe_upstream(lambda: apply_pricing_rules(user_sub, items, checkout_type="shop"), default=None)`.
   b. If result is not None, extract `rule_discount_cents` and `applied_rules`; else fall back to zero.
4. Compute `final_total_cents = max(0, subtotal_cents - rule_discount_cents)`.
5. Build and return `CartPricingBreakdownOut`.

The existing `cart_total_cents` function at line 301 **is kept unchanged** as a
thin compatibility shim: `return cart_pricing_breakdown(user_sub, cart_id).final_total_cents`.
This ensures all existing callers (including external code that might import
`cart_total_cents` directly) continue to work.

### 4.2 Updated `purchase_cart`

**File**: `app/services/shoppingcart.py` — `purchase_cart` function starting at line 474.

The existing summation at line 496:
```python
total_cents = sum(item.get("line_total_cents", 0) for item in items)
```
is replaced with a call to the shared breakdown function:
```python
breakdown = cart_pricing_breakdown(user_sub, cart_id)
total_cents = breakdown.subtotal_cents
rule_discount_cents = breakdown.rule_discount_cents
applied_rules = breakdown.applied_rules
```

The existing promo-code block (lines 550–576) runs unchanged against `total_cents`
(the subtotal before rule discounts). The stacking semantics are:

```
final_total = max(0, subtotal_cents - rule_discount_cents - promo_discount_cents)
```

i.e. rule discount is applied first (reducing the base), then the promo discount.
This matches the OFB-020 spec's "rule + code interaction" requirement. The existing
`original_total_cents = total_cents` assignment (line 548) is preserved; its
semantics become "subtotal before any discount" rather than "before promo only".

### 4.3 New response model: `CartPricingBreakdownOut`

**File**: `app/models.py` (added by ECM-003; described here for completeness)

```python
class AppliedRuleLineOut(BaseModel):
    rule_id: str
    rule_name: str
    discount_cents: int

class CartPricingBreakdownOut(BaseModel):
    cart_id: str
    subtotal_cents: int
    rule_discount_cents: int = 0
    applied_rules: list[AppliedRuleLineOut] = []
    promo_discount_cents: int = 0          # populated only when promo is validated
    promo_code_id: Optional[str] = None
    final_total_cents: int
    currency: str = "USD"
```

`CartPricingBreakdownOut` is a superset of `ShoppingCartTotalOut`. The existing
`ShoppingCartTotalOut` is kept intact at `app/models.py:982`; the total endpoint's
`response_model` is widened (see §4.4).

### 4.4 Updated endpoint: `GET /ui/shoppingcart/carts/{cart_id}/total`

**File**: `app/routers/shoppingcart.py:169`

```python
@router.get(
    "/carts/{cart_id}/total",
    response_model=CartPricingBreakdownOut,   # widened from ShoppingCartTotalOut
)
async def ui_cart_total(cart_id: str, ctx=Depends(require_ui_session)):
    breakdown = cart_pricing_breakdown(ctx["user_sub"], cart_id)
    return breakdown
```

`CartPricingBreakdownOut` is a strict superset of `ShoppingCartTotalOut`: it carries
`total_cents` as an alias for `final_total_cents` (via a `@property` or a
`model_validator`) so existing frontend reads of `response.total_cents` keep working
without a breaking schema change. With rules off, `applied_rules` is `[]`,
`rule_discount_cents` is `0`, and `final_total_cents == subtotal_cents` — identical
to the old response.

### 4.5 Updated endpoint: `POST /ui/shoppingcart/carts/{cart_id}/purchase`

**File**: `app/routers/shoppingcart.py:175`

The router call-site is unchanged. `purchase_cart` returns a dict that already feeds
`ShoppingCartPurchaseOut`. ECM-009 extends the returned dict with two additive
optional keys (`rule_discount_cents`, `applied_rules`). `ShoppingCartPurchaseOut`
(`app/models.py:993`) has **no** `model_config` today — FastAPI's `response_model`
serialization silently drops unknown keys without it. To surface these fields to the
browser, `ShoppingCartPurchaseOut` must gain the two optional nullable fields shown
below **and** add `model_config = ConfigDict(extra="ignore")` so existing dict keys
not in the model are dropped cleanly:

```python
class ShoppingCartPurchaseOut(BaseModel):
    # existing fields unchanged ...
    rule_discount_cents: Optional[int] = None
    applied_rules: Optional[list[AppliedRuleLineOut]] = None
```

Auth: `require_ui_session` (cookie + CSRF), unchanged.

### 4.6 Import structure

`app/services/shoppingcart.py` gains a lazy import guard for both new dependencies:

```python
# at the call site inside cart_pricing_breakdown():
try:
    from app.services.store_integration import _integration_enabled, _safe_upstream
    from app.services.pricing_rules import apply_pricing_rules
except ImportError:
    _integration_enabled = lambda _: False
    _safe_upstream = lambda fn, default: default
    apply_pricing_rules = None
```

This ensures the module remains importable during the period between ECM-009 landing
and OFB-019/ECM-002 landing (or if they are deployed in a different order).

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off path (STORE_APPLY_PRICING_RULES = false)

- `cart_pricing_breakdown` short-circuits after step 2 and returns
  `CartPricingBreakdownOut(cart_id=cart_id, subtotal_cents=s, rule_discount_cents=0,
  applied_rules=[], final_total_cents=s, currency="USD")`.
- `purchase_cart` sets `rule_discount_cents = 0`, `applied_rules = []`, and the
  stacking formula degenerates to `final_total = max(0, total_cents - promo_discount_cents)`,
  which is the current behavior at line 578.
- No new attributes are written to `shopping_cart`, `orders`, or `order_items` (the
  conditional-append logic for `applied_rule_ids` and `rule_discount_cents` only fires
  when those values are non-zero).

### 5.2 Rules engine error / unavailable

`_safe_upstream(lambda: apply_pricing_rules(...), default=None)` swallows any exception
and returns `None`. ECM-009 treats a `None` result as zero rule discount — identical
to flag-off. The purchase still completes; the rule engine being down only means the
customer does not receive the discount for this transaction. An `ERROR` level log line
is emitted with the exception, including `cart_id` and `user_sub`, so ops can detect
degraded mode.

### 5.3 Promo + rule stacking

Stacking order: rule discount reduces the subtotal first; the promo code's
`item_price_cents` argument receives `subtotal_cents - rule_discount_cents`. This
means a `percentage` promo code applies to the already-discounted price, which is the
"rule wins, then promo on remainder" behavior from OFB-020. The `original_total_cents`
field in the purchase response and the `PromoCodes` redemption record (via
`redeem_promo_code` at `promo_codes.py:398`) always reflects `subtotal_cents` (before
all discounts) so the redemption accounting remains consistent.

### 5.4 Zero-total cart

`max(0, subtotal_cents - rule_discount_cents - promo_discount_cents)` clamps to zero.
A zero-total purchase is already handled (the billing ledger write in
`purchase_history.py` records `amount_cents=0`) and must remain legal (e.g., fully
sponsored carts).

### 5.5 Empty cart

If `list_items` returns an empty list, `subtotal_cents = 0`, and
`apply_pricing_rules` is never called. The total endpoint returns
`final_total_cents=0`; `purchase_cart` raises `HTTPException(422)` via the existing
check that rejects empty-cart purchases (the `line_items` list being empty triggers a
`ValueError` inside `create_order_from_line_items` at `commerce_order_service.py:55`).

### 5.6 Idempotent replay of purchase_cart

The existing CAS at `shoppingcart.py:621–626` (`ConditionExpression="#status = :open"`)
guarantees single commit. On a replay where `cart.status == "PURCHASED"`, the function
returns the stored result at line 483–492 without recomputing any discounts.
`cart_pricing_breakdown` is never called on the replay path; no double-rule-application
risk.

### 5.7 Per-rule per-user redemption caps

Rule redemption caps (daily/total per user) are enforced inside `apply_pricing_rules`
(OFB-019's responsibility). ECM-009 only surfaces the result. The existing
`redeem_promo_code` path for code-bound rules runs unchanged after `purchase_cart`
commits, at lines 654–666.

### 5.8 Backward compatibility of cart_total_cents callers

`cart_total_cents` is imported by the router at `app/routers/shoppingcart.py:32`
and called at exactly **one** call-site in `app/` (`shoppingcart.py router:171`).
There are no other in-app callers (verified by grep). After ECM-009,
`cart_total_cents` becomes a one-liner that calls
`cart_pricing_breakdown(...).final_total_cents`, returning exactly the same integer
type as before.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity**: `app/services/pricing_rules.py` (from OFB-019) is expected to
be pure DynamoDB — no mock branch, no `S.dev_mode` fork. ECM-009 inherits this:
`cart_pricing_breakdown` calls `apply_pricing_rules` identically in dev and prod.
Dev only differs in that the DDB endpoint is `http://localhost:8001` (via
`S.ddb_endpoint_url`), which moto replicates.

**Idempotency**: `purchase_cart` is already idempotent via the `sha256(correlation_id)`
order ID derivation (`commerce_order_service.py:67`) and the CAS cart-status guard.
ECM-009 does not introduce any new write that could fire twice: `cart_pricing_breakdown`
is a pure read (no DDB writes); the additive attributes on the cart record are written
inside the existing `UpdateExpression` that is already guarded by the `#status = :open`
condition.

**Security**: `cart_pricing_breakdown` is called with `user_sub` from the session
cookie (`ctx["user_sub"]`), so rule evaluation is always scoped to the authenticated
buyer. Rule definitions (created by admin) are read-only within this call; ECM-009
does not expose any admin write surface. The `GET /total` endpoint is already
cookie-auth gated via `require_ui_session`.

**No billing fork**: ECM-009 does not call `new_ledger_entry` or touch the billing
table. The single ledger entry written for a cart purchase continues to be generated
by `record_cart_purchase` in `app/services/purchase_history.py:244` with `amount_cents
= final_total` (the rule-discounted value). The GL thus correctly reflects the amount
the customer actually paid.

## 8. Backward Compatibility & Migration

**Zero migration required**. All changes are additive:

- `ShoppingCartTotalOut` is replaced as the `response_model` by `CartPricingBreakdownOut`,
  which is a strict superset. Clients that only read `total_cents` see the same field
  (aliased from `final_total_cents`).
- `ShoppingCartPurchaseOut` gains two nullable optional fields. Existing clients
  ignore unknown fields via Pydantic's `extra="ignore"`.
- Existing cart records in DynamoDB carry no `rule_discount_cents` attribute; reads
  via `_cart_from_item` default to the current behavior.
- No table alterations. No backfill.
- Running `just restart` picks up the new settings defaults (both `false`) with no
  behavioral change.

If the ops team wants to enable pricing rules on an existing cart mid-session, the
next `GET /total` call reflects the new discount. The `purchase_cart` recomputes from
scratch (reads live items and calls `apply_pricing_rules` fresh), so there is no
stale-snapshot risk from a previous `GET /total` call.

## 9. Test Plan

### 9.1 Hermetic offline pytest (`tests/test_ecm_009_pricing_rules.py`)

Test isolation approach (consistent with CLAUDE.md pattern): use moto
`@mock_aws` to back `T.shopping_cart`, `T.orders`, and `T.order_items`; patch
the frozen singletons via `object.__setattr__(T, "shopping_cart", moto_table)`.
Call service functions directly (no `TestClient` — TestClient is unreliable in this
env). Stub `app.services.pricing_rules.apply_pricing_rules` and
`app.services.store_integration._integration_enabled` via `unittest.mock.patch`.
Toggle `S.store_apply_pricing_rules` and `S.store_integration_enabled` via
`object.__setattr__(S, "store_apply_pricing_rules", True)`.

**Test cases**:

1. **Flag-off parity** — With `S.store_apply_pricing_rules = False`, call
   `cart_pricing_breakdown`. Assert `rule_discount_cents == 0`, `applied_rules == []`,
   `final_total_cents == sum(line_total_cents)`. Assert `apply_pricing_rules` is never
   called. Assert `cart_total_cents` returns same integer as the old formula.

2. **Tiered rule applied at total** — Seed a cart with 3 items (quantities 1, 2, 5).
   Stub `apply_pricing_rules` to return `PricingBreakdownResult(subtotal_cents=1000,
   rule_discount_cents=100, applied_rules=[{rule_id: "r1", rule_name: "Qty5", discount_cents: 100}],
   final_cents_before_promo=900)`. Assert `CartPricingBreakdownOut.rule_discount_cents == 100`,
   `final_total_cents == 900`.

3. **Rule + promo stacking** — Same cart; also pass `promo_code="SAVE10"` that returns
   `discount_cents=50` for `item_price_cents=900`. Assert `final_total = 850`.
   Assert order `metadata["rule_discount_cents"] == 100` and
   `metadata["applied_rules"] == [{...}]`. Assert `original_total_cents == 1000`.

4. **Rules engine error → degrade** — Stub `apply_pricing_rules` to raise
   `RuntimeError("engine down")`. Assert `cart_pricing_breakdown` returns
   `rule_discount_cents == 0` and `final_total_cents == subtotal_cents`. Assert
   no exception propagates.

5. **Purchase idempotency replay** — Seed a PURCHASED cart. Call `purchase_cart`.
   Assert it returns the stored result without calling `apply_pricing_rules` or
   `cart_pricing_breakdown` again.

6. **Order metadata persistence** — Seed a cart, enable rules, call `purchase_cart`,
   query `T.orders` via moto. Assert the `metadata` dict on the stored order record
   contains `rule_discount_cents` and `applied_rules`.

7. **Order line item pricing_ref enrichment** — After purchase, query `T.order_items`.
   Assert each row's `pricing_ref` carries `applied_rule_id` and
   `line_rule_discount_cents` when a rule matched, or empty/zero when no rule matched.

8. **Zero-total (fully discounted) cart** — Stub rules returning `rule_discount_cents
   == subtotal_cents`. Assert `final_total == 0`. Assert purchase completes normally.

9. **Flag-off: purchase byte-for-byte parity** — Disable rules. Assert the cart update
   expression written to DDB does NOT contain `rule_discount_cents` or
   `applied_rule_ids`. Assert the purchase return dict has no `rule_discount_cents`
   key or it is `None`.

### 9.2 E2E Playwright spec (`frontend/e2e/pricing-rules.spec.ts`, owned by OFB-022)

Per OFB-022's acceptance criteria, this ECM-009 spec does not own the E2E test file
but must be compatible with it. The test sequence is:

1. Admin creates a tiered pricing rule (>= 3 units → 10% off) via the OFB-021 admin
   UI.
2. Alice adds 4 units of a catalog item to her cart.
3. `GET /ui/shoppingcart/carts/{id}/total` — assert `rule_discount_cents > 0`,

   `rule_discount_cents == 0` and `final_total_cents == subtotal_cents`.

## 10. Open Questions / Assumptions

1. **Assumption**: OFB-019 delivers `apply_pricing_rules(user_sub, items, *, checkout_type)
   -> PricingBreakdownResult` with the exact field names `subtotal_cents`,
   `rule_discount_cents`, `applied_rules`, `final_cents_before_promo`. If OFB-019
   uses different names, the adapter in `cart_pricing_breakdown` must be updated.

2. **Assumption**: ECM-002 delivers `_integration_enabled(sub_flag: str) -> bool` in
   `app/services/store_integration.py`. If that function is not present at the time
   ECM-009 lands, the lazy `ImportError` guard in §4.6 ensures the flag defaults to
   `False` safely.

3. **Open question**: Should rule discounts be visible in the `ShoppingCartPurchaseOut`
   response to the browser, or only stored on the order for ops/audit? The spec assumes
   the browser-facing purchase response includes `rule_discount_cents` as an optional
   nullable. If the product team decides to hide this from the browser, the field can
   be omitted from `ShoppingCartPurchaseOut` without changing any storage logic.

4. **Assumption**: Promo-code stacking order is "rule first, promo on remainder" (per
   OFB-020). If OFB-020 specifies "promo first, rule on remainder" or "best of" the
   calling order in `purchase_cart` must be swapped.

5. **Open question**: Should `cart_pricing_breakdown` cache its result to avoid a
   double `list_items` call (once for the preview, once inside `purchase_cart`)? Both
   calls happen in separate HTTP requests, so a per-request in-memory cache is
   sufficient. The current design does not add a cache; if profiling shows this is a
   hot path, a `functools.lru_cache` keyed on `(user_sub, cart_id)` with a short TTL
   can be added without API changes.

6. **Assumption**: `orders` table `created_at` GSI sort key is currently stored as a
   string ISO timestamp (confirmed by `commerce_order_service.py:20` `_now_iso()` →
   `datetime.now(timezone.utc).isoformat()`). This means the `GSI_USER` and
   `GSI_STATUS` indices at `scripts/local-ddb-init.py:291–292` are missing
   `attr_types={"created_at": "N"}` — but because they are string-typed, not numeric,
   this is not a bug. ECM-009 does not query by `created_at` on these indices and does
   not need to fix this pre-existing condition.

7. **Open question**: When `applied_rule_ids` is an empty set, DynamoDB rejects a
   write containing an empty `SS` (string set) attribute. The implementation must
   omit the `applied_rule_ids` field from the `UpdateExpression` entirely when
   `applied_rules` is empty, mirroring how `promo_code_id` is conditionally appended
   at `shoppingcart.py:617`.
