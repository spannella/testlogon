# MFG-008 — Optional costed-production GL hook

**Type:** Feature | **Priority:** P2 | **Estimate:** 2 days
**Milestone:** 3 — Work Orders / Production Runs

---

## 1. Summary & Goal

When a work order reaches `completed` status, optionally post a single ledger
entry that captures the total production cost (component material cost +
routing labor cost) into the **existing** billing ledger via
`billing_shared.new_ledger_entry` (`app/services/billing_shared.py:224–259`).

The entry carries `ledger_date` so it is visible to the `GSI_LEDGER_DATE`
day-bucket queries used by the platform financial dashboard
(`app/services/platform_financial_dashboard.py:147`) and, once OFB-013/014 is
built, can be automatically promoted to a double-entry journal entry
(WIP debit / Inventory — Finished Goods credit) by the GL posting service.

This is an **additive, sub-flag-gated hook inside MFG-007's completion
function** — it never touches a new table, never forks billing, and produces no
observable change when its sub-flag is off. The inventory-only path established
by MFG-007 (`inventory.adjust` issue/produce) is byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 Single-entry ledger (`billing_shared.new_ledger_entry`)

`app/services/billing_shared.py:224–259` defines `new_ledger_entry(*, key_name,
key_value, entry_type, amount_cents, state, reason, meta=None, extra=None)`.
It generates a time-stamped sort key (`LEDGER#{ts}#{entry_id}`), writes
`ledger_date` (YYYY-MM-DD derived from `now_ts()`) for day-bucket indexing, and
returns `(sk, item)` — the caller puts the item into the billing table.

All existing callers follow the same three-line pattern
(`app/routers/billing.py:1234–1244` `reason="charge_once"`,
`:1306–1316` `reason="refund"`, `:2418–2426`, etc.):

```python
led_sk, led_item = new_ledger_entry(
    key_name="pk",
    key_value=pk,
    entry_type="credit",
    amount_cents=amount,
    state="settled",
    reason="charge_once",
    extra={"provider": "stripe"},
)
ddb_put(T.billing, led_item)
```

The `billing` table schema in `scripts/local-ddb-init.py:67–77` declares
`GSI_LEDGER_DATE` with PK=`ledger_date` (S) and SK=`sk` (S). Only rows whose
`sk` begins with `LEDGER#` are intended to appear in this index; non-ledger rows
(payment methods, balance rows) never carry `ledger_date` and are naturally
excluded from the index.

### 2.2 GSI_LEDGER_DATE consumption

`app/services/platform_financial_dashboard.py:136–158` queries
`GSI_LEDGER_DATE` with `Key("ledger_date").eq(date_str) & Key("sk").begins_with("LEDGER#")`
(`platform_financial_dashboard.py:147–149`).
Any row written via `new_ledger_entry` automatically lands in this day-bucket
and is visible to the dashboard aggregation loop without schema changes.

OFB-014 (`OFBIZ_COMMERCE_TICKETS.md:262–280`) will drive double-entry GL
posting from the same `GSI_LEDGER_DATE` buckets, mapping each ledger row's
`type`/`reason` to chart-of-accounts debits/credits. A manufacturing row with
`reason="mfg_produce"` and `entry_type="internal_transfer"` must map cleanly
to a WIP→Finished-Goods account pair in OFB-013's chart. The `reason` and
`entry_type` values chosen here are the contract that OFB-014 will consume.

### 2.3 Work-order completion in MFG-007

MFG-007 creates `app/services/manufacturing_work_orders.py` with a
`complete_work_order(work_order_id, user_sub)` function that:

1. Loads the work-order header (`SK=META`) and validates `status == "in_progress"`.
2. Calls `inventory.adjust(product_sku, +produced_qty, reason="mfg_produce", user_sub=user_sub)`.
3. Flips `status = "completed"` and sets `completed_at = now_ts()` on the header.
4. Emits `alerts.audit_event("work_order.completed", ...)`.

MFG-008 inserts a fifth step — the GL hook — between steps 3 and 4, gated by
`S.manufacturing_cost_posting_enabled`. The hook is implemented **inside the
same `complete_work_order` function** in `manufacturing_work_orders.py`; there
is no separate module.

### 2.4 Component cost sourcing

The `mfg_boms` table (MFG-002) stores BOM header and component rows. Component
rows (`SK=COMP#{seq}`) carry `component_sku` and `quantity_per`. The issued
quantities for the work order are recorded as `ISSUE#{n}` rows in the
`mfg_work_orders` table, each carrying `component_sku` and `issued_qty`.

The catalog table (`app/routers/catalog.py:107–115`) stores `price_cents` per item.
A component's **standard cost** for the GL hook is its catalog `price_cents`
(read-through to the catalog table via the same per-SKU `T.catalog.get_item` pattern
used by `app/services/shoppingcart.py:381`; key shape:
`{"PK": f"CAT#{category_id}", "SK": f"ITEM#{item_id}"}` —
`shoppingcart.py:42–43`). If no catalog row exists for a component SKU,
`unit_cost_cents` defaults to 0 (the hook is best-effort; missing catalog cost
data must not block completion).

### 2.5 Routing labor cost sourcing

`app/services/manufacturing_routing.py` (MFG-005) exposes:

```python
def estimate_routing_cost(tasks: list[dict], build_qty: int) -> dict:
    # Pure function — no DynamoDB I/O (MFG-005.md:313–340).
    # Returns {"total_labor_minutes": int, "total_labor_cost_cents": int, ...}
    # Each task dict MUST carry "cost_per_hour_cents" pre-loaded by the caller.
```

`tasks` is the ordered list of routing-task dicts for the BOM (fetched via
`GSI_ROUTE_PARENT` on `T.mfg_work_centers`). The work order's `bom_id` and
`quantity` (= `produced_qty`) are stored on the header row (`SK=META`).
MFG-008 calls `estimate_routing_cost(routing_tasks, produced_qty)` to get
`labor_cost_cents` from the key `"total_labor_cost_cents"` in the returned
dict. **Critical**: `estimate_routing_cost` is a pure function; the caller
must pre-load each task dict's `cost_per_hour_cents` from the work-center
record (e.g., via the convenience wrapper `estimate_routing_cost_for_parent`
defined in MFG-005.md:344–355) before calling the pure function directly, or
simply call `estimate_routing_cost_for_parent(bom_id, produced_qty)` instead.

### 2.6 Idempotency via conditional put

MFG-007 already derives a deterministic `work_order_id =
hashlib.sha256(correlation_id.encode()).hexdigest()[:32]`
(`app/services/commerce_order_service.py:67` pattern). The GL hook must be
**exactly-once**: a replayed `complete_work_order` must not write a second
ledger entry. The mechanism is a DynamoDB conditional `put_item` with
`ConditionExpression="attribute_not_exists(sk)"` on the exact ledger SK
constructed from a deterministic `entry_id = hashlib.sha256(f"mfg:{work_order_id}".encode()).hexdigest()[:16]`.
`ConditionalCheckFailedException` is swallowed silently (idempotent replay;
not an error).

The `entry_id` is 16 hex chars — distinct enough to avoid collision in the
ULID-based entry namespace while remaining compact.

### 2.7 No money-out path

Production is an **internal value transfer** (materials + labor absorbed into
finished goods). There is no payment intent, no external provider, no wallet
debit, no refund needed. The ledger entry uses `entry_type="internal_transfer"`
and `state="settled"` immediately. No `provider` extra field is set (the
platform financial dashboard provider-breakdown in
`app/services/platform_financial_dashboard.py:110–114` (`_provider_for`)
buckets unknown/absent provider as `"unknown"`, which is correct for internal
manufacturing transactions — they should not appear in Stripe/PayPal/CCBill breakdowns).

## 3. Data Model

MFG-008 writes **exclusively to the existing `billing` table** via
`new_ledger_entry`. No new tables are created.

### 3.1 Ledger entry row (written to `T.billing`)

| Attribute | DDB Type | Value |
|---|---|---|
| `pk` (PK) | S | `"MFG#{work_order_id}"` |
| `sk` (SK) | S | `LEDGER#{ts}#{entry_id}` (from `new_ledger_entry`) |
| `entry_id` | S | `sha256(f"mfg:{work_order_id}")[:16]` |
| `ts` | N | Unix timestamp (`now_ts()`) |
| `type` | S | `"internal_transfer"` |
| `amount_cents` | N | `material_cost_cents + labor_cost_cents` |
| `state` | S | `"settled"` |
| `reason` | S | `"mfg_produce"` |
| `ledger_date` | S | YYYY-MM-DD from `ledger_date_for_ts(ts)` |
| `meta.work_order_id` | S | `work_order_id` |
| `meta.product_sku` | S | finished-goods SKU |
| `meta.produced_qty` | N | quantity produced |
| `meta.material_cost_cents` | N | sum of component costs |
| `meta.labor_cost_cents` | N | `estimate_routing_cost` result |
| `meta.bom_id` | S | BOM used for this production run |

**Key design choices:**

- `pk = "MFG#{work_order_id}"` places the row in a dedicated partition that does
  not collide with any existing `USER#{sub}` billing partition. This is safe
  because `new_ledger_entry` is generic (`key_name`/`key_value` parameters —
  `billing_shared.py:226–227`) and the billing table supports heterogeneous
  partitions (other non-user callers such as `ad_billing.py` and
  `sponsorship_deals.py` also write to `T.billing` with custom PK values).
  The `GSI_LEDGER_DATE` GSI projects `ledger_date` and `sk` universally, so the
  manufacturing entry appears in the day-bucket index regardless of PK prefix.
- The conditional put uses the **exact `sk`** returned by `new_ledger_entry`,
  which encodes `ts + entry_id`. Since `entry_id` is deterministic from
  `work_order_id`, the same work order will always produce the same SK and the
  conditional `attribute_not_exists(sk)` correctly prevents double-writes.
- No `apply_balance_delta` call and no `ensure_balance_row` call are needed —
  internal transfers do not affect any user's spendable wallet balance.

### 3.2 Existing `mfg_work_orders` header row (no schema change)

MFG-007 owns the `mfg_work_orders` table. MFG-008 reads but does not mutate the
header row. The `gl_posting_sk` field (the ledger SK written) is stored back onto
the work-order header as a convenience for audit lookup:

```
UpdateExpression="SET gl_posting_sk = :sk, gl_posted_at = :t"
```

This is a best-effort write (`try/except Exception: pass`) after the billing
table conditional put succeeds; it is not relied upon for idempotency.

## 4. API / Service Design

MFG-008 adds **no new endpoints**. All logic lives in
`app/services/manufacturing_work_orders.py` (MFG-007's module) as a private
helper called from `complete_work_order`.

### 4.1 Private helper: `_post_production_gl_entry`

```python
def _post_production_gl_entry(
    work_order_id: str,
    product_sku: str,
    produced_qty: int,
    bom_id: str | None,
    user_sub: str,
) -> str | None:
    """
    Write exactly one ledger entry for the completed work order.

    Returns the ledger SK on success, None if the entry already exists
    (idempotent replay) or if cost posting is disabled.

    Raises nothing — all exceptions are caught and logged; a cost-posting
    failure must NEVER prevent work-order completion.
    """
```

**Algorithm:**

1. Check `S.manufacturing_cost_posting_enabled`; return `None` if off.
2. Compute `material_cost_cents`:
   - Load `ISSUE#` rows for the work order from `T.mfg_work_orders`
     (`query(Key("work_order_id").eq(wo_id) & Key("sk").begins_with("ISSUE#"))`).
   - For each issued component, look up `price_cents` from the catalog table
     (`T.catalog` — key shape `{"PK": f"CAT#{category_id}", "SK": f"ITEM#{item_id}"}`,
     same pattern as `shoppingcart.py:381` / `shoppingcart.py:42–43`;
     fall back to 0 if not found or if BOM component row lacks `category_id`).
   - `material_cost_cents = sum(item["issued_qty"] * unit_cost for item in issues)`.
3. Compute `labor_cost_cents`:
   - If `bom_id` is set, call `estimate_routing_cost_for_parent(bom_id, produced_qty)`
     (MFG-005 convenience wrapper at `manufacturing_routing.py` — fetches tasks via
     `GSI_ROUTE_PARENT`, pre-loads `cost_per_hour_cents` per task, then calls
     `estimate_routing_cost`); extract `["total_labor_cost_cents"]`.
   - If `bom_id` is `None` or routing lookup fails, `labor_cost_cents = 0`.
4. `total_cost_cents = material_cost_cents + labor_cost_cents`.
5. Derive deterministic `entry_id = hashlib.sha256(f"mfg:{work_order_id}".encode()).hexdigest()[:16]`.
6. Call `new_ledger_entry(key_name="pk", key_value=f"MFG#{work_order_id}", entry_type="internal_transfer", amount_cents=total_cost_cents, state="settled", reason="mfg_produce", meta={...})` (`billing_shared.py:224–259`).
   **Override** the random `entry_id` that `new_ledger_entry` generates internally
   (`billing_shared.py:240` — `entry_id = ulidish()` is random): after the call,
   set `led_item["entry_id"] = entry_id` (the deterministic value from step 5)
   before the `put_item`. Without this override the conditional check in step 7
   cannot reliably detect a replay.
7. Attempt `T.billing.put_item(Item=led_item, ConditionExpression="attribute_not_exists(entry_id)")`.
   - `ConditionalCheckFailedException` → return `None` (already posted).
   - Any other exception → log + return `None` (never propagate).
8. Best-effort: update `gl_posting_sk` and `gl_posted_at` on the work-order header.
9. Emit `_audit("work_order.gl_posted", user_sub, work_order_id=work_order_id, amount_cents=total_cost_cents)`.
10. Return `led_sk`.

### 4.2 Integration point in `complete_work_order`

```python
async def complete_work_order(
    work_order_id: str,
    user_sub: str,
    produced_qty: int | None = None,
) -> dict:
    # ... MFG-007 steps 1–3: validate, inventory.adjust, flip status ...

    # MFG-008 GL hook (best-effort, never raises)
    _post_production_gl_entry(
        work_order_id=work_order_id,
        product_sku=header["product_sku"],
        produced_qty=int(header["quantity"]),
        bom_id=header.get("bom_id"),
        user_sub=user_sub,
    )

    # MFG-007 step 4: audit
    _audit("work_order.completed", user_sub, work_order_id=work_order_id)
    return _work_order_out(header)
```

The GL hook call is after the inventory mutation and status flip, inside the
same function, with no `await` (the helper is synchronous). This ensures the
inventory books are updated before the GL record is created.

## 5. Detailed Behavior & Edge Cases

### 5.1 Zero-cost production

If both `material_cost_cents` and `labor_cost_cents` are 0 (e.g., all component
catalog rows missing, no routing defined), the hook still writes a
`amount_cents=0` ledger entry when `manufacturing_cost_posting_enabled` is on.
A zero-amount entry is valid in the ledger (it has a ledger_date and type and
will be picked up by OFB-014), and omitting it would break idempotency detection
for future replays. The GL posting service (OFB-014) can choose to skip
zero-amount entries.

### 5.2 Catalog lookup failure

`T.catalog` (`app/core/tables.py:351`) is the same catalog table (`shopping_catalog`
by default) used by the shop. The catalog table uses `PK`/`SK` (uppercase) as
DynamoDB key attribute names (`scripts/local-ddb-init.py:119–120`). An item row's
DDB key is `PK="CAT#{category_id}"`, `SK="ITEM#{item_id}"`
(`app/routers/catalog.py:55–64`; `app/services/shoppingcart.py:42–43`).
Component SKUs for manufactured products may not be in the catalog (e.g., raw
materials entered only in inventory). The per-SKU lookup uses `get_item` with a
try/except; a missing item → `unit_cost_cents = 0` for that component. The hook
proceeds with partial cost data. This is logged at DEBUG level, not raised.

**Confirmed**: component `unit_cost` comes from `T.catalog`'s `price_cents` field
(`app/routers/catalog.py:115`). This requires that the BOM component row carries
both `category_id` and `item_id` for the `PK`/`SK` lookup to work; if absent,
the component's cost defaults to 0. See §10 for the open question on catalog key
resolution from component rows.

### 5.3 Routing not defined

If the work order has no `bom_id` (ad-hoc production without a BOM), or the BOM
has no routing tasks (no `ROUTE#` rows under any work center for that BOM), the
routing cost is 0. The hook does not raise; it posts with `labor_cost_cents=0`.

### 5.4 Flag disabled mid-flight

If `manufacturing_cost_posting_enabled` is toggled off after a work order is
started but before it is completed, the hook silently skips and the work order
completes without a ledger entry. This is consistent with other flag-gated paths
(the inventory reservations flag, for example, can be toggled without corrupting
in-flight reservations).

### 5.5 Billing table write failure

Any `ClientError` from `T.billing.put_item` (other than
`ConditionalCheckFailedException`) is caught inside `_post_production_gl_entry`
and logged. The work-order completion succeeds regardless. The calling function
`complete_work_order` has no `try/except` around the hook call; instead, the
hook itself is wholly defensive. This mirrors the pattern used by
`app/routers/newsfeed.py` engagement hooks (`_recsys_engage`, fire-and-forget,
best-effort — `newsfeed.py:5686`, called from like/reaction/comment/tip/unlock handlers).

### 5.6 Concurrent completion replay

Two concurrent calls to `complete_work_order` for the same `work_order_id`
(e.g., an admin double-submit): MFG-007's step-guard on the work-order header
(`ConditionExpression="status = :in_progress"`) ensures only one caller can flip
status to `completed`. However, if the guard check and the status flip are not
atomic (race window), both callers could reach the GL hook. The `attribute_not_exists(sk)`
conditional on the billing table ensures only the first write succeeds; the
second is silently swallowed.

### 5.7 `entry_id` collision

`sha256(f"mfg:{work_order_id}")[:16]` produces a fixed 16-char hex string per
work order. Since `work_order_id` itself is `sha256(correlation_id)[:32]`
(MFG-007), the composition is collision-resistant for all practical purposes.
The SK `LEDGER#{ts}#{entry_id}` encodes both the timestamp and the deterministic
entry_id; for idempotency the conditional put targets the exact `sk` returned by
`new_ledger_entry` on replay, which will always be the same `LEDGER#{same_ts}#{entry_id}`
only if `ts` is also deterministic. Since `ts = now_ts()` varies, the SK changes
across replay calls.

**Correction to §4.1 step 7**: the conditional must target `entry_id`, not `sk`,
because `sk` changes on each call. Use:

```python
T.billing.put_item(
    Item=led_item,
    ConditionExpression="attribute_not_exists(entry_id)",
)
```

`entry_id` is stored as a top-level attribute on the item
(`app/services/billing_shared.py:245`), so the condition `attribute_not_exists(entry_id)`
on a `put_item` across all items with the same PK correctly rejects a second
write with the same `entry_id`. Note that `new_ledger_entry` generates a
random `entry_id` via `ulidish()` (`billing_shared.py:240`); the caller
must override `led_item["entry_id"]` with the deterministic value before
calling `put_item` (see §4.1 step 6). This requires PK-scoped uniqueness: two different
work orders have different PKs (`MFG#{woid1}` vs `MFG#{woid2}`), so their
`entry_id`s are in different partitions and do not conflict. The same work order
always produces the same PK + same `entry_id` → the condition fires on replay.

### 5.8 OFB-014 compatibility

The `reason="mfg_produce"` and `entry_type="internal_transfer"` values must be
registered in OFB-013's chart-of-accounts mapping before OFB-014 can post the
double-entry. The ledger row's `meta.bom_id` and `meta.product_sku` are available
for the GL posting rule to use as account discriminators (e.g., map to a specific
WIP sub-account per product class). The key point is that the row is already in
`GSI_LEDGER_DATE` with a valid `ledger_date`, so OFB-014's day-bucket scan will
encounter it on the day of completion without any schema changes.

## 6. Feature Flag & Config

### 6.1 Sub-flag

| Setting | Env var | Default | Notes |
|---|---|---|---|
| `S.manufacturing_cost_posting_enabled` | `MANUFACTURING_COST_POSTING_ENABLED` | `false` | Sub-flag for GL hook only |

The sub-flag is independent of the master `S.manufacturing_mrp_enabled` flag
(`MANUFACTURING_MRP_ENABLED`). Both must be `true` for GL posting to occur:

```python
def _flag_on() -> bool:
    return (
        bool(getattr(S, "manufacturing_mrp_enabled", False))
        and bool(getattr(S, "manufacturing_cost_posting_enabled", False))
    )
```

This ensures that enabling cost posting without also enabling manufacturing is a
no-op (the `complete_work_order` function itself is gated on `manufacturing_mrp_enabled`
by `_require_enabled()` in MFG-007 — so the GL hook can never be reached if the
master flag is off).

In practice, having a separate sub-flag check inside `_post_production_gl_entry`
(checking only `manufacturing_cost_posting_enabled`) is also correct and simpler
to test, because the function can only be called from `complete_work_order` which
is already behind the master flag gate.

### 6.2 No new DynamoDB settings

The hook writes to `T.billing` (already wired at `app/core/tables.py:333` as
`billing=_safe_table(S.billing_table_name)`) and reads from `T.mfg_work_orders`,
`T.mfg_work_centers` (both MFG-002), and `T.catalog` (`tables.py:351` —
`catalog=_safe_table(S.catalog_table_name)`) — all existing handles. No new
`*_table_name` settings are needed.

Add to `.env.local.example`:

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

`new_ledger_entry` writes to DynamoDB Local in dev and to real DynamoDB in prod
via the same `T.billing` handle and the same `billing_table_name` setting. There
is no `dev_mode` branch in the billing-table write. MFG-008 inherits this parity
automatically — the same code runs in both environments. No mock path is added.

### 7.2 Idempotency

The `attribute_not_exists(entry_id)` conditional put (§5.7) guarantees at-most-once
ledger entry per work order. Combined with MFG-007's step-guard (at-most-once
`completed` transition), the overall invariant is: for any `work_order_id`,
at most one row with `pk="MFG#{work_order_id}"` and `entry_id=sha256(...)[:16]`
exists in `T.billing`.

### 7.3 Security

- The GL hook runs in the same server-side execution context as `complete_work_order`;
  no new authentication or authorization surface is exposed.
- The `pk = "MFG#{work_order_id}"` billing partition is never visible to end-user
  billing API endpoints (all user-facing billing queries use `pk = "USER#{sub}"`
  partitions). The manufacturing ledger rows are invisible to `GET /billing/history`.
- The `meta` dict serialized into DynamoDB contains only server-generated values
  (`work_order_id`, `product_sku`, `produced_qty`, `bom_id`, cost integers) — no
  user-supplied free-text is stored in ledger rows.
- Component catalog price lookups (`T.catalog.get_item`) are read-only and do
  not affect the catalog record.

## 8. Backward Compatibility & Migration

### 8.1 Existing billing table

The `billing` table already exists with the `GSI_LEDGER_DATE` index
(`scripts/local-ddb-init.py:67–77`). MFG-008 adds new rows under new
`MFG#…` partition keys — no existing row is mutated or deleted. The index
definition is unchanged. No `UpdateTable` or backfill is required.

### 8.2 Existing shop/cart/orders/billing paths

With `MANUFACTURING_COST_POSTING_ENABLED=false` (default), the hook is a single
branch check (`if not S.manufacturing_cost_posting_enabled: return None`) that
short-circuits immediately. The call to `_post_production_gl_entry` is itself
inside `complete_work_order`, which is only reachable when
`manufacturing_mrp_enabled=true` (MFG-007's `_require_enabled()` gate). This
means:

- All existing catalog, cart, order, and billing code paths are byte-for-byte
  unchanged regardless of the sub-flag value.
- Enabling `MANUFACTURING_COST_POSTING_ENABLED=true` without
  `MANUFACTURING_MRP_ENABLED=true` is a no-op because `complete_work_order` is
  itself unreachable.

### 8.3 Work-order header migration

The `gl_posting_sk` and `gl_posted_at` fields added to the header row are
optional (`SET` expression on existing rows, ignored if absent). Pre-existing
completed work orders have no `gl_posting_sk` field; any query on the header row
simply returns `None` for these fields. No migration script is needed.

### 8.4 OFB-013 prerequisite

The `reason="mfg_produce"` / `entry_type="internal_transfer"` values will appear
in `GSI_LEDGER_DATE` from day one but will not be posted to the GL until OFB-014
is built and OFB-013 maps these codes to accounts. This is by design — the rows
accumulate in the ledger and OFB-014 can backfill them for historical dates via
its backfill command (OFB-014 AC: "A backfill command can post historical ledger
rows for a date range without duplication").

## 10. Open Questions / Assumptions

1. **Component catalog key structure**: The BOM component row (`SK=COMP#{seq}`)
   stores `component_sku` but the catalog table uses a compound key
   `PK="CAT#{category_id}"` / `SK="ITEM#{item_id}"` (`catalog.py:55–64`,
   `shoppingcart.py:42–43`). **Verified**: the catalog table does have a `ByItemId`
   GSI on `item_id` (`local-ddb-init.py:123`, `catalog.py:703–718`) that allows
   an O(1) lookup by bare `item_id` without `category_id`. If BOM component rows
   carry `item_id` (not just a composite `{category_id}:{item_id}` SKU), this GSI
   can serve as a fallback. If the BOM component row carries only `component_sku`
   (which may not map to a catalog `item_id`), cost defaults to 0. MFG-004 must
   define whether `category_id` / `item_id` are stored on BOM component rows.

2. **Routing task ownership model**: MFG-005 spec (§3.2 of `MFG-005.md`) places
   routing tasks under the work center partition (PK=`work_center_id`,
   SK=`ROUTE#{parent_id}#{seq}`), resolved via `GSI_ROUTE_PARENT`. This spec
   assumes this design is final. If MFG-005 is revised to a different storage
   model, the routing lookup in §4.1 step 3 must be updated.

3. **`T.catalog` handle name**: **Verified** — `app/core/tables.py:351` exposes
   `T.catalog = _safe_table(S.catalog_table_name)`. The catalog table's DDB key
   attributes are `PK` and `SK` (uppercase, `local-ddb-init.py:119–120`). Item
   lookup uses `Key={"PK": f"CAT#{category_id}", "SK": f"ITEM#{item_id}"}` —
   identical to the pattern in `app/services/shoppingcart.py:42–43`. The
   `ByItemId` GSI on `item_id` (`catalog.py:703–718`) allows lookup by bare
   `item_id` if `category_id` is unavailable; the hook may use it as fallback.

4. **Synchronous vs. async**: `complete_work_order` is defined as `async` in
   MFG-007 (the router calls it with `await`). `_post_production_gl_entry` is
   synchronous (DynamoDB boto3 calls are synchronous). The spec calls the helper
   directly from `complete_work_order` without `await` or `asyncio.to_thread`.
   **Confirmed**: boto3 synchronous I/O inside an async FastAPI handler is
   acceptable — `app/services/inventory.py:209` (`adjust`) and all of
   `app/services/billing_shared.py` are synchronous and called directly from
   async routers throughout the app without `asyncio.to_thread`.

5. **`entry_id` uniqueness scope**: `attribute_not_exists(entry_id)` as the
   conditional on `put_item` is scoped to the partition `MFG#{work_order_id}`.
   Since `entry_id` is a top-level item attribute, the condition fires if **any**
   item in the partition carries that `entry_id`. For a manufacturing work order
   there is exactly one ledger entry per work order (one partition, one item),
   so this works correctly. **Assumption**: no other code path writes to the
   `MFG#{work_order_id}` partition, so the attribute uniqueness check is not
   polluted by other rows.

6. **`produced_qty` source**: The spec uses `header["quantity"]` as `produced_qty`.
   If MFG-007 allows a partial-completion produced quantity different from the
   original order quantity, the hook should use the actual `produced_qty` field
   set by the completion step, not the original `quantity`. **Assumption**: MFG-007
   stores `produced_qty` on the header after completion; the hook reads that field,
   falling back to `quantity` if absent.
