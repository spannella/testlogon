# MFG-004 — BOM service (CRUD + explosion)

## 1. Summary & Goal

MFG-004 creates `app/services/manufacturing_bom.py`, the authoritative service
layer for Bill of Materials data. It delivers:

1. **CRUD** for BOM headers and their ordered component lines, stored in
   `T.mfg_boms` using the single-table pattern already specified by MFG-002
   (`SK=META` header, `SK=COMP#{seq:04d}` component rows).
2. **Active-BOM resolution** via `get_active_bom(product_sku)`, which queries
   the `GSI_PRODUCT` index and returns the most-recently-created active BOM for
   a finished-goods SKU — the entry point used by work orders (MFG-007) and MRP
   (MFG-010).
3. **Multi-level BOM explosion** via `explode_bom(bom_id, build_qty)`, which
   recursively flattens a BOM into leaf-component requirements (accounting for
   scrap), detects cycles, and enforces a configurable depth cap.
4. **SKU validation** on creation: every `product_sku` and `component_sku` is
   confirmed against `inventory.get_or_zero` so stale/phantom SKUs are rejected
   at write time rather than silently polluting explosion results.
5. **Audit trail**: every mutation emits a best-effort `alerts.audit_event` via
   the same `_audit` wrapper pattern used by `inventory.py`.

The service is additive and flag-gated (`manufacturing_mrp_enabled`, default
`false`). With the flag off, no table is accessed and all existing
shop/cart/orders/billing paths are byte-for-byte unchanged.

### 2.6 Open-work-order guard

The acceptance criterion states that deleting/deactivating a BOM referenced
by an open work order raises a 409. "Open" means `status IN
{"created", "released", "in_progress"}`. The check queries `T.mfg_work_orders`
via `GSI_PRODUCT` (specified by MFG-002: `partition_key="product_sku"`,
`sort_key="created_at"`), filtering for the matching `bom_id` and an open
status. Because GSI_PRODUCT is keyed on `product_sku` (not `bom_id`), the
query fetches work orders for the BOM's `product_sku` and then filters in
Python for `item["bom_id"] == bom_id`. This is safe because a single
finished-goods SKU typically has O(1) concurrent work orders.

### 2.7 `mfg_boms` table shape (from MFG-002 spec)

Header row (`sk=META`): `bom_id`, `product_sku`, `name`, `output_quantity` (N),
`status` (`draft`/`active`/`inactive`), `created_at` (N), `updated_at` (N),
`created_by` (S).


| Attribute | DDB type | Notes |
|---|---|---|
| `bom_id` | S | partition key |
| `sk` | S | `"META"` |

| `output_quantity` | N | integer ≥ 1; units produced per build run |
| `status` | S | `draft` / `active` / `inactive` |

| Attribute | DDB type | Notes |
|---|---|---|

| `scrap_pct` | N | Decimal 0.0–1.0; default 0; stored via `_FloatSafeTable` |

| `unit_of_measure` | S | optional, default `"each"` |

**GSI:**

```
GSI_PRODUCT
  partition_key = "product_sku"  (S)
  sort_key      = "created_at"   (N)

```

## 5. Detailed Behavior & Edge Cases

### 5.1 `create_bom`

1. Call `_require_enabled()`.
2. Validate `output_quantity >= 1` (Pydantic enforces this; service re-checks
   and raises 422 if bypassed).
3. Validate `len(components) >= 0` (empty BOM is allowed for a placeholder
   `draft`).
4. For each component, read `inventory.get_or_zero(component_sku)`. If the
   returned record has `on_hand == 0 and reserved == 0 and updated_at == 0`
   (i.e. the virtual zero record, meaning the SKU was never registered), log a
   warning but **do not block creation** — the SKU may be registered later. This
   matches the ticket's wording "reference real catalog/inventory SKUs" as a
   best-effort read-through rather than a hard reject (hard rejection would
   prevent bootstrapping new SKUs).

   > **Assumption A1**: "validate" means a warning/log, not a 422 reject, for
   > unknown component SKUs. If the intent is hard rejection, add a 422 guard
   > here and update the test that verifies unknown SKU behavior. See Open
   > Questions.

5. Derive `bom_id = _bom_id_from_correlation(correlation_id)`.
6. Compute `now = now_ts()`.
7. Write header row via `T.mfg_boms.put_item(Item=header, ConditionExpression="attribute_not_exists(bom_id)")`.
   On `ConditionalCheckFailedException`, raise `HTTPException(409, "BOM already exists for this correlation_id")`.
8. Write each component row via `T.mfg_boms.put_item(Item=comp)`. Component
   rows are not conditional — in a retry scenario they are idempotent overwrites
   because the `bom_id + sk` key is deterministic from the header write.
9. Emit `_audit("bom.create", user_sub, bom_id=bom_id, product_sku=product_sku)`.
10. Return the full BOM dict (header + components projected via `_header_out` /
    `_component_out`).

### 5.2 `get_bom`

1. Call `_require_enabled()`.
2. Fetch all items for the partition via `T.mfg_boms.query(KeyConditionExpression=Key("bom_id").eq(bom_id))`.
3. Separate `sk == "META"` item from `sk.startswith("COMP#")` items.
4. If no `META` item found, return `None`.
5. Sort component items by `sk` (lexicographic, which equals numeric sort due to
   zero-padding) and project.
6. Return merged dict with `components` list.

### 5.3 `get_active_bom`

1. Call `_require_enabled()`.
2. Query `GSI_PRODUCT`:
   ```python
   T.mfg_boms.query(
       IndexName="GSI_PRODUCT",
       KeyConditionExpression=Key("product_sku").eq(product_sku),
       FilterExpression=Attr("status").eq("active"),
       ScanIndexForward=False,
       Limit=1,
   )
   ```
   `ScanIndexForward=False` with numeric `created_at` sort returns the
   most-recently-created active BOM first.
3. If no item returned, return `None`.
4. Call `get_bom(item["bom_id"])` to hydrate components.

**Note on FilterExpression + DDB page size**: A `FilterExpression` on `status`
does not reduce the fetched page — DDB applies it after reading up to `Limit`
items. With `Limit=1`, if the newest BOM is inactive, no active BOM is returned
even if older ones exist. This is intentional: `Limit=1` limits the *scanned*
rows to 1. For the multi-version use case, `Limit` should be omitted and the
first `status="active"` item in the result set is returned. Set `Limit=10` to
balance freshness with throughput.

> **Assumption A2**: `get_active_bom` uses `Limit=10` (not `Limit=1`) with
> `ScanIndexForward=False`, returning the first item whose `status == "active"`.
> This handles the case where the most recent BOM is inactive (superseded).

### 5.4 `update_bom`

1. Call `_require_enabled()`.
2. Load the existing header via `get_bom(bom_id)`; raise 404 if not found.
3. If `status` is being changed to `"inactive"` or the BOM is being deleted,
   call the open-work-order guard (Section 5.6).
4. Build a `UpdateExpression` for only the changed fields + `updated_at`.
5. Emit `_audit("bom.update", user_sub, bom_id=bom_id, changes={...})`.
6. Return updated BOM.

### 5.5 `delete_bom`

1. Call `_require_enabled()`.
2. Load the existing header; raise 404 if not found.
3. Run the open-work-order guard (Section 5.6).
4. Fetch all component rows for the partition.
5. Delete all rows (header + components) via `batch_writer` or serial
   `delete_item` calls.
6. Emit `_audit("bom.delete", user_sub, bom_id=bom_id, product_sku=...)`.

### 5.6 Open-work-order guard

```python
def _guard_no_open_work_orders(bom_id: str, product_sku: str) -> None:
    """Raises 409 if an open work order references this BOM."""
    resp = T.mfg_work_orders.query(
        IndexName="GSI_PRODUCT",
        KeyConditionExpression=Key("product_sku").eq(product_sku),
        FilterExpression=Attr("sk").eq("META") & Attr("bom_id").eq(bom_id)
            & Attr("status").is_in(["created", "released", "in_progress"]),
    )
    if resp.get("Items"):
        raise HTTPException(
            status_code=409,
            detail="BOM is referenced by an open work order",
        )
```

This is called from both `update_bom` (when changing status away from `active`)
and `delete_bom`. It reads `T.mfg_work_orders` which is provisioned by MFG-002.
If `T.mfg_work_orders` is not yet populated (MFG-007 not yet implemented), the
query returns an empty result set and the guard passes — allowing BOM CRUD to
work independently.

### 5.7 `explode_bom`

Full recursive algorithm (from MFG-001 spec, Section 5.1):

```
explode_bom(bom_id, build_qty, *, _depth=0, _seen=None):
  1. _require_enabled()
  2. If _depth > S.mfg_bom_max_explosion_depth → HTTPException(409, "BOM explosion depth exceeded")
  3. If _seen is None → _seen = set()
  4. If bom_id in _seen → HTTPException(409, "Cyclic BOM detected: {bom_id}")
  5. _seen.add(bom_id)
  6. Load header via get_bom(bom_id). If None → HTTPException(404, "BOM not found")
  7. output_quantity = header["output_quantity"]  (≥ 1)
  8. For each component in header["components"] (sorted by seq):
       qty_per = Decimal(component["quantity_per"])
       scrap   = Decimal(component["scrap_pct"])
       raw_req = qty_per / output_quantity * build_qty * (1 + scrap)
       req_qty = math.ceil(float(raw_req))
       sub_bom = get_active_bom(component["component_sku"])
       if sub_bom is not None:
           sub_results = explode_bom(sub_bom["bom_id"], req_qty,
                                     _depth=_depth+1, _seen=_seen)
           result.extend(sub_results)
       else:
           result.append({
               "component_sku": component["component_sku"],
               "required_qty":  req_qty,
               "depth":         _depth + 1,
           })
  9. Return result
```

**Key formula**: `required_qty = ceil(qty_per / output_quantity × build_qty × (1 + scrap_pct))`

The division by `output_quantity` normalizes per-output-unit quantities to the
actual build quantity. For example, a BOM with `output_quantity=10` and a
component with `quantity_per=3` means 0.3 units per output unit; a `build_qty`
of 50 requires `ceil(3/10 × 50 × 1.0) = ceil(15) = 15` units.

**Depth semantics**: `_depth=0` at the top-level call; a direct component of
the top BOM is at `depth=1` in the output; a sub-component's component is at
`depth=2`, etc. The depth cap comparison is `_depth > max_depth` (strictly
greater than), so `max_depth=5` allows 5 recursive levels (depths 1–5).

**`_seen` is passed by reference across recursive calls**, enabling cross-branch
cycle detection. A component appearing in multiple branches is not a cycle and
produces additive entries in the output (merging by SKU is the caller's
responsibility, e.g. `run_mrp`).

**Result merging by caller**: `explode_bom` returns a flat list where the same
`component_sku` may appear multiple times (once per path). MRP (MFG-010) sums
`required_qty` by SKU. Work orders (MFG-007) receive the pre-merged list from
a helper (see Section 5.8).

### 5.8 `get_exploded_requirements` — merged helper for work orders

```python
def get_exploded_requirements(
    bom_id: str,
    build_qty: int,
) -> Dict[str, Dict[str, Any]]:
    """Return {component_sku: {required_qty, depth}} merged across all paths."""
    raw = explode_bom(bom_id, build_qty)
    merged: Dict[str, Dict[str, Any]] = {}
    for entry in raw:
        sku = entry["component_sku"]
        if sku in merged:
            merged[sku]["required_qty"] += entry["required_qty"]
        else:
            merged[sku] = {"required_qty": entry["required_qty"], "depth": entry["depth"]}
    return merged
```

This helper is called by `manufacturing_work_orders.release_work_order` (MFG-007)
to obtain a flat, deduplicated component list before issuing inventory adjustments.
`explode_bom` itself returns the raw (potentially duplicated) list for MRP use.

### 5.9 Status transitions

Valid BOM status transitions enforced by `update_bom`:

| From → To | Allowed? | Guard |
|---|---|---|
| `draft` → `active` | Yes | None |
| `draft` → `inactive` | Yes | None |
| `active` → `inactive` | Yes | Open-WO guard |
| `inactive` → `active` | Yes | None |
| `active` → `draft` | No | 409 — cannot revert published BOM |
| `inactive` → `draft` | No | 409 |
| Any → delete | Yes (hard delete) | Open-WO guard |

Only one BOM per `product_sku` should be `active` at a time; this is a
convention enforced by the UI (MFG-006) but not a hard database constraint —
`get_active_bom` resolves the newest active BOM if multiple exist.

### 5.10 Edge cases and invariants

- **Empty BOM (`components=[]`)**: Allowed for `draft` status. Exploding an
  empty BOM returns an empty list. A work order against an empty BOM issues no
  components and produces finished goods directly.
- **`output_quantity > 1`**: Supported. `required_qty` formula divides by
  `output_quantity` to normalize per-unit consumption. `build_qty=1` on a BOM
  with `output_quantity=100` results in fractional raw requirements rounded up.
- **`scrap_pct=0` (default)**: The `(1 + 0.0)` factor is a no-op. `scrap_pct`
  must be stored in DynamoDB as a `Decimal` via `_FloatSafeTable`.
- **Component with `quantity_per < output_quantity`**: Valid — produces a
  fractional per-unit rate. `math.ceil` ensures at least 1 unit is required for
  any nonzero quantity_per.
- **DynamoDB `FilterExpression` does not reduce scanned pages** (CLAUDE.md):
  `_guard_no_open_work_orders` does not set a `Limit` on the `GSI_PRODUCT`
  query, so it fetches all work orders for the `product_sku` before filtering.
  If a product has O(1000s) work orders, this may be slow; for the MVP this is
  acceptable. A follow-up can add a per-status GSI or a sparse `open_bom_id`
  attribute.
- **Concurrent BOM activation**: If two admins activate different BOMs for the
  same `product_sku` concurrently, both are `active`; `get_active_bom` returns
  the newest. This is a last-write-wins soft constraint, not a hard uniqueness
  enforcement.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

No `dev_mode` branch exists in `manufacturing_bom.py`. All code paths execute
identically against DynamoDB Local (port 8001 in dev, moto in tests) and real
DynamoDB in production. The `_FloatSafeTable` proxy (`app/core/tables.py:29–62`) <!-- VERIFIED: class at :29, __getattr__ delegate at :61–62 -->
handles `Decimal` coercion for `quantity_per` and `scrap_pct` in all
environments.

`inventory.get_or_zero` (called for SKU validation) is itself SECOPS-007 clean —
it reads from `T.inventory` which is the same table handle in dev and prod.

### Idempotency

- **BOM creation**: `bom_id = sha256(correlation_id)[:32]` + conditional
  `put_item(ConditionExpression="attribute_not_exists(bom_id)")`. A replay with
  the same `correlation_id` returns 409 rather than overwriting. Callers
  that want update semantics should use `update_bom`.
- **Component writes**: Not conditional — idempotent overwrites on replay because
  `bom_id + sk` is deterministic.
- **`update_bom`**: Not idempotency-sensitive; a conditional update guard is
  not required (last-write-wins for header patches is acceptable).
- **`delete_bom`**: Idempotent — deleting a nonexistent row via `delete_item`
  succeeds silently in DynamoDB.

### Security

- All write endpoints use `require_admin_or_root_csrf` (mirroring <!-- VERIFIED: inventory.py:48 uses Depends(require_admin_or_root_csrf); policy.py:100–106 is the function definition -->
  `app/routers/inventory.py:48`, `app/auth/policy.py:100–106`).
- All read endpoints also use `require_admin_or_root_csrf` — BOM data is
  admin-internal; there are no storefront-facing BOM endpoints.
- `explode_bom`'s depth cap (`S.mfg_bom_max_explosion_depth=5`) prevents a
  crafted deeply-nested or cyclic BOM from exhausting the call stack or DynamoDB
  quota via recursive reads.
- Component SKU validation reads through `inventory.get_or_zero` (not a
  direct `get_item` on the catalog) so the BOM service never directly accesses
  the catalog or orders tables — cross-module coupling is limited to the
  inventory service boundary.

### `_FloatSafeTable` and Decimal

`quantity_per` and `scrap_pct` are stored as DynamoDB Number (`N`) attributes.
Python `float` values are rejected by boto3. The `_FloatSafeTable` proxy
(`tables.py:41–49`) coerces all floats to `Decimal` via `_to_decimal()` on <!-- VERIFIED: put_item at :41–44, update_item at :46–49; both call _to_decimal -->
`put_item` and `update_item`. Service code should convert input `float`/`Decimal`
to `Decimal(str(...))` before passing to DDB calls to avoid precision surprises.

## 10. Open Questions / Assumptions

**A1 — SKU validation strictness**: The ticket says "validate that `product_sku`
and every `component_sku` reference real catalog/inventory SKUs (read-through to
`inventory.get_or_zero`)." The spec interprets `get_or_zero`'s zero return as
a warning, not a hard 422 block, because `get_or_zero` returns a zeroed record
for unregistered SKUs (it never returns `None`). If the intent is a hard reject
for SKUs with no inventory record, the guard must check
`inventory.get_inventory(sku)` (which returns `None` for unknown SKUs) instead
and raise 422. Decision needed from the MFG-001 spike owner.

**A2 — `get_active_bom` scan behavior**: Using `Limit=1` on a `GSI_PRODUCT`
query with `ScanIndexForward=False` returns only the newest DDB item, which may
not be `active` (e.g. it was deactivated). The spec uses `Limit=10` and picks
the first `active` from the result set. If the product has many BOMs and
`Limit=10` is insufficient, the caller will miss the latest active one. A
follow-up can increase the limit or add a sparse `active_bom_id` pointer on a
product record.

**A3 — Multi-component duplicate SKU merging in `explode_bom`**: The current
design returns a flat list with potential duplicates (same `component_sku`
appears via multiple paths). `get_exploded_requirements` merges them. Work
orders (MFG-007) will use the merged helper. MRP (MFG-010) will sum across all
entries. Confirm this split is acceptable — alternatively, `explode_bom` could
merge internally, but this loses path-depth information.

**A4 — `output_quantity` normalization in explosion formula**: The formula uses
`qty_per / output_quantity * build_qty`. MFG-001 Section 5.1 states
`ceil(quantity_per * build_qty * (1 + scrap_pct))` without the division. The
division is needed when `quantity_per` is expressed as "units per BOM run"
rather than "units per output unit." The spec adopts the normalized form. If
`quantity_per` is defined as "units per output unit" in MFG-003's model, the
division must be removed. Confirm with MFG-003 model definition.

**A5 — Status revert from `active` to `draft`**: The spec blocks this
transition (409) to prevent reverting a published BOM. If draft editing of an
active BOM is required, the correct workflow is to create a new draft BOM and
deactivate the old one. Confirm this is the intended UX.

**A6 — Hard delete vs. soft delete**: The spec implements hard delete (removes
all DDB rows). An alternative is soft delete: set `status="archived"` without
removing rows, preserving the BOM for historical audit purposes (e.g., a
completed work order's component list was derived from this BOM). Confirm
whether audit completeness requires soft delete.
