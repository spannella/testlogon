# PRD-011 — Bundle & association router endpoints

**Type:** Feature | **Priority:** P1 | **Estimate:** 2 days
**Milestone:** 4 — Bundles / Kits & Associations

---

## 1. Summary & Goal

PRD-011 exposes the pure-service logic from PRD-009 (`app/services/product_bundles.py`) and PRD-010 (`app/services/product_associations.py`) as HTTP endpoints registered in `app/routers/catalog.py`. Six endpoints are added in total:

| Method | Path | Purpose |
|---|---|---|
| `PUT` | `/ui/catalog/items/{item_id}/bundle-components` | Full-replace component list (owner) |
| `GET` | `/ui/catalog/items/{item_id}/bundle` | Return bundle type + component list + computed price |
| `GET` | `/ui/catalog/items/{item_id}/expand` | Return flat component expansion lines + total price |
| `POST` | `/ui/catalog/items/{item_id}/associations` | Add one association (owner) |
| `GET` | `/ui/catalog/items/{item_id}/associations` | List associations with optional type filter |
| `DELETE` | `/ui/catalog/items/{item_id}/associations/{assoc_id}` | Remove one association (owner) |

All six endpoints are gated by `S.product_depth_enabled` and return `HTTP 501` ("Product depth is not enabled") when the flag is off. No modification to any existing route, model, service, or table is required: all endpoints are **appended** to the existing `app/routers/catalog.py` (currently 1000 lines; new endpoints follow the bulk-operations block at `:914`). The existing shop/cart/orders/billing paths are byte-for-byte unchanged with the flag off.

No new router registration in `app/main.py` is required — `catalog_router` is already registered at `app/main.py:671`.

## 4. API / Service Design

### 4.1 `_require_item_owner` helper

PRD-008 introduces this helper at `app/routers/catalog.py` (after `:247`). PRD-011 reuses it without modification:

```python
def _require_item_owner(item_id: str, user_sub: str) -> Dict[str, Any]:
    """Return the item row or raise 403/404.

    Calls _find_item_by_id (catalog.py:702) then checks creator_id.
    Raises 404 if item does not exist.
    Raises 403 if creator_id is set and does not match user_sub.
    """
    item = _find_item_by_id(item_id)
    if not item:
        raise HTTPException(status_code=404, detail="Item not found.")
    creator_id = item.get("creator_id")
    if creator_id and creator_id != user_sub:
        raise HTTPException(status_code=403, detail="Not authorized to manage this item.")
    return item
```

If PRD-008 is not yet merged, PRD-011 inlines this helper and removes the duplicate after PRD-008 merges.

### 4.2 Bundle component endpoints

#### `PUT /ui/catalog/items/{item_id}/bundle-components`

Full idempotent replace of all component rows. Maps to `product_bundles.set_components`.

```python
@router.put(
    "/items/{item_id}/bundle-components",
    response_model=BundleOut,
    status_code=200,
)
async def set_bundle_components(
    item_id: str,
    body: BundleSetIn,
    ctx=Depends(require_ui_session),
):
    """Replace all bundle/kit components. Owner-only.

    1. product_depth_enabled guard (501 if off).
    2. _require_item_owner — raises 404/403.
    3. Verify item product_type in ("bundle", "kit") — raises 422 if not set.
    4. Delegate to product_bundles.set_components(item_id, body.components, user_sub).
    5. Return BundleOut(bundle_item_id=item_id, product_type=...,
                        components=[...], computed_price_cents=..., currency=...).
    """
```

**Request body** (`BundleSetIn`):
```json
{
  "components": [
    {"component_item_id": "abc123", "quantity": 2, "sequence_num": 0},
    {"component_item_id": "def456", "quantity": 1, "sequence_num": 1}
  ]
}
```

**Response** (`BundleOut`):
```json
{
  "bundle_item_id": "item_xyz",
  "product_type": "kit",
  "components": [
    {
      "bundle_item_id": "item_xyz",
      "component_item_id": "abc123",
      "component_name": "Widget A",
      "quantity": 2,
      "sequence_num": 0,
      "unit_price_cents": 500,
      "currency": "USD",
      "created_at": 1720000000,
      "updated_at": 1720000000
    }
  ],
  "computed_price_cents": 1300,
  "currency": "USD"
}
```

`computed_price_cents` is always populated from `compute_bundle_price(item_id)`. For a kit it is the dynamic component sum; for a bundle it is the scalar `price_cents` from `T.catalog`.

The handler calls `compute_bundle_price` after `set_components` completes. If `set_components` raises (partial failure), the 5xx propagates and the caller retries the full PUT.

Returns the bundle/kit details and component list. Read-only.

@router.get(

    5. list_components(item_id) — hydrated via _find_item_by_id for name/price.

Non-owners may call this endpoint (read-only). The subscription gate mirrors `list_reviews` at `app/routers/catalog.py:830`.

#### `GET /ui/catalog/items/{item_id}/expand`

Returns the flat expansion — the integration seam for cart/checkout to get reservation lines.

```python
@router.get(
    "/items/{item_id}/expand",
    response_model=BundleExpandOut,
)
async def expand_bundle_endpoint(
    item_id: str,
    qty: int = Query(default=1, ge=1, le=1000),
    ctx=Depends(require_ui_session),
):
    """Return flat component lines for this bundle/kit at qty units.

    1. product_depth_enabled guard (501 if off).
    2. _find_item_by_id — raises 404 if absent.
    3. can_access_creator subscription gate.
    4. get_product_type — raises 422 if not bundle/kit.
    5. expand_bundle(item_id, qty) — recursive; raises 422 on cycle/depth exceeded.
    6. total_price_cents = sum(line.unit_price_cents * line.quantity for line in lines)
       (for kits) or scalar item price_cents * qty (for bundles).
    7. Return BundleExpandOut.
    """
```

**Response** (`BundleExpandOut`):
```json
{
  "bundle_item_id": "item_xyz",
  "product_type": "kit",
  "lines": [
    {"component_item_id": "abc123", "component_name": "Widget A",
     "sku": "catalog:abc123", "quantity": 4, "unit_price_cents": 500, "currency": "USD"},
    {"component_item_id": "def456", "component_name": "Widget B",
     "sku": "catalog:def456", "quantity": 2, "unit_price_cents": 300, "currency": "USD"}
  ],
  "total_price_cents": 2600,
  "currency": "USD"
}
```

`qty` is a query parameter defaulting to 1. Caller passes the cart quantity; `expand_bundle` multiplies each component quantity by `qty` recursively. Maximum `qty=1000` prevents trivially large responses.

### 4.3 Association endpoints

#### `POST /ui/catalog/items/{item_id}/associations`

Add one association from this item to another item.

```python
@router.post(
    "/items/{item_id}/associations",
    response_model=AssocOut,
    status_code=201,
)
async def create_association(
    item_id: str,
    body: AssocCreateIn,
    ctx=Depends(require_ui_session),

    1. product_depth_enabled guard (501 if off).
    2. _require_item_owner(item_id, user_sub) — raises 404/403.
    3. Validate body.to_item_id exists in T.catalog via _find_item_by_id — raises 404.
    4. Validate body.assoc_type in AssocType values — Pydantic handles this.
    5. product_associations.add_association(user_sub, item_id, body.to_item_id, body.assoc_type).
    6. Return AssocOut (hydrated with target item name/price/currency).
    """
```

**Request body** (`AssocCreateIn`):
```json
{"to_item_id": "target_item_id", "assoc_type": "complement"}
```

**Response** (`AssocOut`):
```json
{
  "assoc_id": "a1b2c3d4e5f6a7b8",
  "from_item_id": "item_xyz",
  "to_item_id": "target_item_id",
  "assoc_type": "complement",
  "target_name": "Related Widget",
  "target_price_cents": 999,
  "target_currency": "USD",
  "creator_id": "user_sub_abc",
  "created_at": 1720000000
}
```

`assoc_id` is the deterministic `sha256(from_item_id + assoc_type + to_item_id)[:16]`. If the same association already exists, `add_association` is a no-op (idempotent upsert); the handler returns `HTTP 201` on first create. On duplicate call the service returns the existing row and the handler returns `HTTP 200` — see §5.2.

#### `GET /ui/catalog/items/{item_id}/associations`

List all associations from this item, optionally filtered by type.

```python
@router.get(
    "/items/{item_id}/associations",
    response_model=AssocListOut,

async def list_item_associations(
    item_id: str,
    assoc_type: Optional[str] = Query(default=None),
    ctx=Depends(require_ui_session),

    1. product_depth_enabled guard (501 if off).
    2. _find_item_by_id — raises 404 if item absent.
    3. can_access_creator subscription gate.
    4. product_associations.list_associations(item_id, assoc_type).
    5. Return AssocListOut(items=[...], count=len(items)).

```

`assoc_type` is an optional query parameter. When supplied, the GSI query uses `begins_with("ASSOC#{assoc_type}")` on `GSI_ASSOC_SK`. When absent, all associations for the item are returned (no SK filter, just `GSI_ASSOC_PK = ASSOC_SRC#{item_id}`).

Invalid `assoc_type` values (not in `{"substitute","complement","upgrade","manuf"}`) return an empty list rather than a 400 — the GSI query simply finds no rows. The router validates the type via an explicit check before calling the service if strict validation is desired (see §5.4).

Read-only; no ownership check required.

## 5. Detailed Behavior & Edge Cases

### 5.1 Item not a bundle/kit on `PUT /bundle-components`

If the item exists but has no `ITEM#{id}/TYPE` row (standalone item) or `product_type` is not `"bundle"` or `"kit"`, the handler raises `HTTP 422` with detail `"Item is not a bundle or kit. Set product type first via PATCH /items/{id}/product-type."`. This message guides the caller to use the PRD-008 product-type endpoint before setting components.

### 5.2 Duplicate association idempotency

`add_association` uses a deterministic `assoc_id = sha256(from_item_id + assoc_type + to_item_id)[:16]`. The DDB write is an unconditional `put_item` (last-write-wins upsert). When called twice with the same `(from_item_id, assoc_type, to_item_id)` triplet, the second call writes the same row with an updated `updated_at` but no new row is created. The handler returns `HTTP 200` (not `201`) on subsequent calls by checking whether the creation timestamp equals `updated_at` or by an explicit DDB conditional; the simpler approach is to always return `HTTP 201` from the endpoint and document it as idempotent (callers must tolerate 201 on re-submission).

**Recommended approach**: return `HTTP 201` unconditionally. The deterministic ID guarantees idempotency at the storage layer regardless of the HTTP status code.

### 5.3 `GET /expand` for a non-bundle item

If the caller requests `GET /items/{id}/expand` on a standalone or virtual item, the handler raises `HTTP 422` ("Item is not a bundle or kit") after reading the TYPE row. This avoids confusing callers who may not know the item's product type in advance.

### 5.4 Unknown `assoc_type` query parameter

When `assoc_type` is supplied but is not a valid value (`"substitute" | "complement" | "upgrade" | "manuf"`), the handler raises `HTTP 400` ("Invalid assoc_type. Valid values: substitute, complement, upgrade, manuf") before calling the service. This is strictly better than silently returning an empty list, which can mask caller typos.

### 5.5 Self-association

Adding an association where `to_item_id == from_item_id` (item associated with itself) is rejected with `HTTP 422` ("An item cannot be associated with itself"). This check is performed in the router handler before calling `add_association`.

### 5.6 `GET /bundle` with zero components

A bundle or kit with no components is valid (owner still building it). `compute_bundle_price` for a kit with zero components returns `0`. The response is `{"bundle_item_id": "...", "product_type": "kit", "components": [], "computed_price_cents": 0, "currency": "USD"}`. No error is raised.

### 5.7 `GET /expand` with nested bundles exceeding depth

If a bundle's component graph exceeds `S.product_depth_max_bundle_depth` (default 3), `expand_bundle` raises `HTTP 422` ("Bundle nesting depth exceeds maximum (3)"). The router propagates this 422 to the caller unchanged.

### 5.8 Component item deleted after being added to a bundle

If a component item was added to a bundle and later deleted from `T.catalog`, `expand_bundle` calls `_find_item_by_id(component_item_id)` and raises `HTTP 404` ("Component item not found: {component_item_id}"). The `GET /expand` endpoint propagates this 404. The `GET /bundle` endpoint's `list_components` call succeeds (it only reads `T.product_depth`), but the `unit_price_cents` hydration step will fail to resolve the deleted component. The handler wraps the hydration in a `try/except` and emits `unit_price_cents=0, component_name="[deleted]"` for missing components rather than returning a 500 — this allows owners to still inspect and clean up their component list.

### 5.9 Association to non-existent target item

`POST /associations` validates `body.to_item_id` exists via `_find_item_by_id` before calling `add_association`. If the target does not exist, the handler raises `HTTP 404` ("Target item not found: {to_item_id}"). This prevents phantom association references in the storefront.

### 5.10 `PUT /bundle-components` with circular components

The component graph cycle check is performed inside `product_bundles.set_components` (via the per-component DFS in `cycle_check`) before any DDB writes. If a cycle is detected, the service raises `HTTP 422` ("Circular bundle reference detected"). `set_components` fails atomically — no partial writes. The handler propagates this 422.

### 5.11 Subscription gate behavior

For the three read-only endpoints (`GET /bundle`, `GET /expand`, `GET /associations`), the subscription gate runs as follows (consistent with `list_items` at `app/routers/catalog.py:402–405`):

```python
item = _find_item_by_id(item_id)
creator_id = item.get("creator_id")
if creator_id and not can_access_creator(ctx["user_sub"], creator_id):
    raise HTTPException(status_code=403, detail="Subscription required.")
```

The gate only fires when `creator_id` is set on the item and the caller is not the creator and does not have an active subscription. Items without a `creator_id` are accessible to all authenticated users.

### 5.12 Flag-off behavior

With `S.product_depth_enabled = False` (the default), every endpoint handler raises `HTTP 501`. No reads or writes to `T.product_depth` occur. The existing catalog endpoints remain at `HTTP 200`. This is verified by the test case `test_flag_off_returns_501` (§9.1).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/Prod parity

All six endpoints delegate to `product_bundles` and `product_associations` services, which exclusively use `T.product_depth` and `T.catalog`. Both tables resolve to DynamoDB Local on dev (`DDB_ENDPOINT_URL=http://localhost:8001`) and real DynamoDB in prod. There is no `S.dev_mode` branch in any of the involved code paths. Behavior is identical in both environments — same table handles, same GSI queries, same conditional writes. This satisfies SECOPS-007.

### Idempotency

- `PUT /bundle-components` — full idempotent replace. Submitting the same component list twice produces the same state. No DDB transaction; partial failure requires a full retry.
- `POST /associations` — deterministic `assoc_id = sha256(from_item_id + assoc_type + to_item_id)[:16]`. Submitting the same association twice is an upsert (last-write-wins on `updated_at`). The endpoint always returns 201, and clients must be tolerant of duplicate 201 responses.
- `DELETE /associations/{assoc_id}` — calling twice returns 404 on the second call. Callers should treat 404 on DELETE as success (resource already absent).

### Security

**Ownership enforcement**: Write endpoints (`PUT /bundle-components`, `POST /associations`, `DELETE /associations/{assoc_id}`) call `_require_item_owner(item_id, user_sub)` before any service call. The `_require_item_owner` helper at `app/routers/catalog.py` (introduced by PRD-008) reads the item from `T.catalog` via the `ByItemId` GSI (`scripts/local-ddb-init.py:123`) and checks `creator_id == user_sub`. A missing `creator_id` (legacy/seeded items) treats the item as ownerless and allows any authenticated user — consistent with the existing `_require_category_owner` at `app/routers/catalog.py:247–252`.

**Read-only access**: `GET /bundle`, `GET /expand`, `GET /associations` have no ownership check, only the `can_access_creator` subscription gate. Any authenticated user who has subscription access to the creator's catalog can read bundle details. This is consistent with how existing `GET /items/{id}/variants` and `GET /items/{id}/features` work in PRD-008.

**Input validation**: `assoc_type` is validated against the `AssocType` literal enum by Pydantic on `POST /associations`. Self-association (`from == to`) is rejected with 422. Max `qty=1000` on `GET /expand` prevents trivially large responses.

**No money paths**: PRD-011 introduces no charge, refund, or ledger operations. The `computed_price_cents` and `total_price_cents` fields are read-only price computations — they do not trigger any billing ledger entry. All monetary flows remain exclusively through `new_ledger_entry` at `app/services/billing_shared.py:224` (verified) and `refund_payment` at `app/routers/billing.py:1287` (verified).

## 8. Backward Compatibility & Migration

### With `PRODUCT_DEPTH_ENABLED=false` (the default)

The six new endpoints return `HTTP 501`. No existing endpoints are modified. `T.catalog`, `T.shopping_cart`, `T.billing`, and all existing services are untouched.

### With flag on but no TYPE row set

Calling `GET /items/{id}/bundle` or `GET /items/{id}/expand` on a standalone item returns `HTTP 422` ("Item is not a bundle or kit"). Calling `PUT /items/{id}/bundle-components` on a standalone item returns `HTTP 422`. No data corruption occurs. The item remains fully functional as a standalone catalog item.

### Enabling the flag on a live system

`T.product_depth` was created empty by PRD-002. Enabling `PRODUCT_DEPTH_ENABLED=true` on a live system with existing catalog items is safe. No existing item has a TYPE row or COMP# or ASSOC# rows. All new endpoints return valid empty results or 422 for non-bundle/non-kit items. No backfill or migration is required.

### Adding routes to a 1000-line router

PRD-011 appends six handlers after the bulk-operations block at `app/routers/catalog.py:914`. No existing handler is moved or modified. FastAPI route matching is declaration-order — there is no ambiguity risk with these new routes because all use `/items/{item_id}/bundle-components`, `/items/{item_id}/bundle`, `/items/{item_id}/expand`, `/items/{item_id}/associations`, and `/items/{item_id}/associations/{assoc_id}`, none of which conflict with existing routes. The existing `/items/{item_id}/reviews` and `/items/{item_id}/reviews/{review_id}` patterns confirm this path prefix is already in use without conflict.

### 9.2 E2E spec (`frontend/e2e/product-bundles.spec.ts`)

Covers the full HTTP surface via authenticated browser requests. Requires `PRODUCT_DEPTH_ENABLED=true` in the dev stack.

**Sections:**

**Section 1 — Bundle component CRUD (API)**
1. Create two scalar items A and B.
2. Promote item A to `"kit"` via `PATCH /items/{A}/product-type` (PRD-008 endpoint).
3. `PUT /items/{A}/bundle-components` with `[{component_item_id: B, quantity: 2}]` → `200`, `components.length == 1`.
4. `GET /items/{A}/bundle` → `computed_price_cents == 2 * B.price_cents`.
5. `GET /items/{A}/expand?qty=3` → `lines[0].quantity == 6`.
6. `PUT /items/{A}/bundle-components` with `[]` (clear) → `200`, `components == []`.

**Section 2 — Bundle ownership (API)**
1. Non-owner `PUT /items/{A}/bundle-components` → `403`.
2. Non-owner `DELETE /items/{A}/associations/{id}` → `403`.

**Section 3 — Associations CRUD (API)**
1. Create item X. `POST /items/{X}/associations` with `{to_item_id: B, assoc_type: "complement"}` → `201`, `assoc_id` is 16-char hex.
2. `GET /items/{X}/associations` → list contains the created association with `target_name`.
3. `GET /items/{X}/associations?assoc_type=complement` → filtered list.
4. `GET /items/{X}/associations?assoc_type=substitute` → empty list.
5. `DELETE /items/{X}/associations/{assoc_id}` → `200`, `{"ok": true}`.
6. `GET /items/{X}/associations` → empty list.

**Section 4 — Flag-off (API)**
1. With `PRODUCT_DEPTH_ENABLED` unset, `GET /items/{A}/bundle` → `501`.

**Section 5 — Edge cases (API)**
1. `POST /items/{X}/associations` with `to_item_id == X` → `422`.
2. `PUT /items/{B}/bundle-components` with `B` as component of `B` → `422` (self-cycle).
3. `GET /items/{B}/expand` on a standalone item → `422`.

## 10. Open Questions / Assumptions

**A1. PRD-008's `_require_item_owner` presence.** This spec assumes PRD-008 has already introduced `_require_item_owner` at `app/routers/catalog.py`. If PRD-011 ships before PRD-008, the helper is inlined and de-duplicated post-merge. Assumption: PRD-008 is a declared transitive dependency (PRD-011 → PRD-009 → PRD-007; PRD-011 → PRD-010 → PRD-007; PRD-008 also depends on PRD-007) and should ship first.

**A2. `product_bundles.get_product_type` vs. shared helper.** The spec assumes that `get_product_type(item_id)` resolves via a shared helper (either from `product_variants` or an extracted `catalog_helpers.py`). If PRD-007 is not yet merged, the TYPE row read is inlined in the PRD-011 handler and de-duplicated after PRD-007 merges. Assumption: PRD-007 ships before PRD-011.

**A3. HTTP 201 vs 200 on duplicate `POST /associations`.** This spec recommends always returning 201 for simplicity (deterministic ID guarantees storage idempotency). If strict REST semantics (200 on update, 201 on create) are required, the handler must distinguish first-write from upsert via DDB conditional + response shape. Assumption: 201 always is acceptable; document in API changelog.

**A4. `GET /bundle` hydration of deleted components.** This spec recommends emitting `unit_price_cents=0, component_name="[deleted]"` for components whose catalog item no longer exists, rather than raising 500 or skipping the component silently. Assumption: informative degraded output is preferable for management UIs where owners need to identify and remove stale components.

**A5. `AssocOut` target fields hydrated inline.** `list_associations` in PRD-010 calls `_find_item_by_id` per association to hydrate `target_name`, `target_price_cents`, `target_currency`. This means `N` associations = `N` catalog lookups (via `ByItemId` GSI). For typical product pages with 5–20 associations this is acceptable. If `list_associations` returns hydrated items, the router passes them through directly; if not, the router hydrates them. Assumption: PRD-010's `list_associations` returns pre-hydrated target summaries (as stated in PRD-010's acceptance criteria); the router does not re-hydrate.

**A6. `qty` cap on `GET /expand`.** Max `qty=1000` is proposed. If the frontend needs higher quantities (bulk orders, wholesale), this can be raised or made configurable via `S.product_depth_expand_max_qty`. Assumption: 1000 is sufficient for the storefront use case.

**A7. Bundle `currency` field.** `BundleOut.currency` is taken from the scalar bundle item's `currency` field on `T.catalog`. If components are in different currencies, `compute_bundle_price` raises 422 (currency mismatch, enforced by PRD-009). The router propagates this 422. Assumption: all components must be in the same currency as the bundle item (enforced by PRD-009 `add_component`).
