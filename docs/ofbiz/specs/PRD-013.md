## 1. Summary & Goal

PRD-013 exposes the service logic from PRD-012 (`app/services/product_price_components.py`) as three HTTP endpoints appended to the existing `app/routers/catalog.py`. The endpoints are:

| Method | Path | Purpose |
|---|---|---|
| `PUT` | `/ui/catalog/items/{item_id}/price-components` | Full-replace all price-component rows for one `price_type` (owner only) |
| `GET` | `/ui/catalog/items/{item_id}/price-components` | List all price-component rows for an item |
| `GET` | `/ui/catalog/items/{item_id}/effective-price` | Return the resolved active price for a given type and point in time |

All three endpoints are gated by `S.product_depth_enabled` and `S.product_depth_price_components_enabled`. With either flag off, every handler returns `HTTP 501`. No modification to any existing route, model, service, or table is required. The existing `price_cents` scalar on `CatalogItemOut` (set at `app/routers/catalog.py:115`) remains the authoritative DEFAULT_PRICE fallback when no components exist, so cart/checkout is byte-for-byte unchanged.

No new router registration in `app/main.py` is required — `catalog_router` is already registered at `app/main.py:671` with prefix `/ui/catalog`.

## 3. Data Model

PRD-013 introduces no new DynamoDB tables, GSIs, or `attr_types` entries. All rows are written by the PRD-012 service and stored in `T.product_depth` (introduced by PRD-002).

### 3.1 Price-component rows (written by PRD-012)

| Attribute | Value |
|---|---|
| `PK` | `ITEM#{item_id}` |
| `SK` | `PRICE#{price_type}#{effective_at:010d}` — zero-padded 10-digit decimal for lexicographic ordering |
| `entity` | `"price_component"` |
| `price_component_id` | `sha256(item_id + price_type + str(effective_at))[:16]` — deterministic 16-char hex |
| `item_id` | string |
| `price_type` | `PriceTypeEnum` value — `"LIST"`, `"DEFAULT"`, etc. |
| `amount_cents` | integer ≥ 0 |
| `currency` | ISO-4217 string (e.g. `"USD"`) |
| `effective_at` | integer Unix seconds — when this price becomes active |
| `expires_at` | integer Unix seconds or absent — when this price stops being active |
| `creator_id` | `{user_sub}` — the item owner |
| `created_at` | integer Unix seconds |
| `updated_at` | integer Unix seconds |
| `GSI_PRICE_PK` | `PRICE#{item_id}#{price_type}` — partition key for `ByItemPrice` GSI |
| `GSI_PRICE_SK` | `effective_at` (integer) — sort key for `ByItemPrice` GSI |

The SK zero-padding (`{effective_at:010d}`) ensures lexicographic scan order on the table primary key matches numeric order, allowing both `begins_with("PRICE#")` prefix scans and range queries within a single price type.

### 3.2 `resolve_effective_price` query pattern

```
ByItemPrice GSI query:
  KeyConditionExpression:
    GSI_PRICE_PK = "PRICE#{item_id}#{price_type}"
    AND GSI_PRICE_SK <= as_of
  ScanIndexForward: False    (newest-first → first result is the active component)
  Limit: 1
```

This query is evaluated inside `product_price_components.resolve_effective_price`. If the result set is empty (no component effective on or before `as_of`), the service returns the scalar `price_cents` from the item's `T.catalog` row. The endpoint calls `_find_item_by_id(item_id)` to obtain the fallback scalar before calling the service, so the fallback value is always available.

### 3.3 `list_price_components` query pattern

```
T.product_depth primary-key prefix query:
  PK = "ITEM#{item_id}"
  SK begins_with "PRICE#"
```

No GSI required. Returns all rows across all price types for the item. The endpoint applies a `price_type` filter as a Python-side predicate when the caller supplies the `?price_type=` query parameter (the GSI is used only by `resolve_effective_price`).

### 3.4 `set_price_components` write pattern (PRD-012)

Full idempotent replace for a single `(item_id, price_type)` pair:

1. Delete all existing `PRICE#{price_type}#*` rows for the item (SK-prefix scan + batch delete).
2. Write new rows for each element of the input list.

The `price_component_id` is deterministic: `sha256(item_id + price_type + str(effective_at))[:16]`. Submitting the same `(item_id, price_type, effective_at, amount_cents)` tuple twice produces the same `price_component_id` and the same stored row.

### 3.5 `scripts/local-ddb-init.py` — no change

The `product_depth` `TableDef` with `ByItemPrice` GSI and `attr_types={"GSI_PRICE_SK": "N"}` is fully established by PRD-002. PRD-013 makes no modifications to the init script.

```python
class PriceComponentSetIn(BaseModel):
    """Request body for PUT /items/{item_id}/price-components."""
    price_type: PriceTypeEnum
    components: List[ProductPriceComponentIn] = Field(default_factory=list)

class PriceComponentListOut(BaseModel):
    """Response body for GET /items/{item_id}/price-components."""
    item_id: str
    components: List[ProductPriceComponentOut]
    count: int

class EffectivePriceOut(BaseModel):
    """Response body for GET /items/{item_id}/effective-price."""
    item_id: str
    price_type: PriceTypeEnum
    as_of: int                              # Unix timestamp used for resolution
    amount_cents: int
    currency: str
    source: str                             # "price_component" | "scalar_fallback"
    price_component_id: Optional[str] = None  # None when source is "scalar_fallback"
```

`PriceComponentSetIn.components` may be an empty list — this is the idempotent "clear all components for this price type" operation. `EffectivePriceOut.source` tells the caller whether the returned price comes from a dated component row or from the scalar `price_cents` fallback, so downstream systems (cart, display) can react accordingly.

### 4.3 Endpoint signatures

All three endpoints are appended after the bulk-operations block at `app/routers/catalog.py:1000`.

#### `PUT /ui/catalog/items/{item_id}/price-components`

```python
@router.put(
    "/items/{item_id}/price-components",
    response_model=PriceComponentListOut,
    status_code=200,
)
async def set_price_components(
    item_id: str,
    body: PriceComponentSetIn,
    ctx=Depends(require_ui_session),
) -> PriceComponentListOut:
    """Full idempotent replace of all price-component rows for one price_type.

    1. product_depth_enabled guard (HTTP 501 if off).
    2. product_depth_price_components_enabled guard (HTTP 501 if off).
    3. _require_item_owner(item_id, ctx["user_sub"]) → HTTP 404/403.
    4. Validate component date windows (see §5.3).
    5. product_price_components.set_price_components(
           item_id, body.price_type, body.components, user_sub).
    6. Return PriceComponentListOut with all components for this price_type.
    """
```

**Request body** (`PriceComponentSetIn`):
```json
{
  "price_type": "DEFAULT",
  "components": [
    {"price_type": "DEFAULT", "amount_cents": 1999, "currency": "USD",
     "effective_at": 1720000000, "expires_at": 1751535999},
    {"price_type": "DEFAULT", "amount_cents": 2499, "currency": "USD",
     "effective_at": 1751536000}
  ]
}
```

**Response** (`PriceComponentListOut`): the list of all component rows now active for this item + price_type, ordered by `effective_at` ascending.

#### `GET /ui/catalog/items/{item_id}/price-components`

```python
@router.get(
    "/items/{item_id}/price-components",
    response_model=PriceComponentListOut,
)
async def list_price_components(
    item_id: str,
    price_type: Optional[PriceTypeEnum] = Query(default=None),
    ctx=Depends(require_ui_session),
) -> PriceComponentListOut:
    """List all price-component rows for this item.

    1. product_depth_enabled guard (HTTP 501 if off).
    2. product_depth_price_components_enabled guard (HTTP 501 if off).
    3. _find_item_by_id(item_id) → HTTP 404 if absent.
    4. can_access_creator subscription gate.
    5. product_price_components.list_price_components(item_id).
    6. If price_type query param supplied, filter results to that type.
    7. Return PriceComponentListOut.
    """
```

`price_type` is an optional `PriceTypeEnum` query parameter. When present, only components of that type are returned; when absent, all types are returned. Pydantic enum coercion at the query-param level ensures invalid strings raise HTTP 422 before the handler is entered.

Read-only endpoint; no ownership check — only the subscription gate.

#### `GET /ui/catalog/items/{item_id}/effective-price`

```python
@router.get(
    "/items/{item_id}/effective-price",
    response_model=EffectivePriceOut,
)
async def get_effective_price(
    item_id: str,
    price_type: PriceTypeEnum = Query(default=PriceTypeEnum.DEFAULT),
    as_of: Optional[int] = Query(default=None, ge=0),
    ctx=Depends(require_ui_session),
) -> EffectivePriceOut:
    """Return the resolved active price for this item at a given point in time.

    1. product_depth_enabled guard (HTTP 501 if off).
    2. product_depth_price_components_enabled guard (HTTP 501 if off).
    3. _find_item_by_id(item_id) → HTTP 404 if absent.
    4. can_access_creator subscription gate.
    5. resolved_as_of = as_of if as_of is not None else now_ts().
    6. product_price_components.resolve_effective_price(
           item_id, resolved_as_of, price_type).
       Returns (amount_cents, currency, price_component_id|None).
       price_component_id is None when the scalar fallback is used.
    7. source = "price_component" if price_component_id else "scalar_fallback".
    8. Return EffectivePriceOut.
    """
```

`price_type` defaults to `PriceTypeEnum.DEFAULT` — the most common caller need. `as_of` defaults to `now_ts()` (current time) when not supplied, enabling "what is the price right now" queries. Supplying `as_of` in the past or future enables historical or scheduled-price lookups (useful for the variant matrix in PRD-015).

The `as_of=0` edge case (explicit zero) is permitted by `ge=0` — it means "earliest possible time" and will always trigger the scalar fallback unless a component with `effective_at=0` exists.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off behavior

With `S.product_depth_enabled = False` (the default) or `S.product_depth_price_components_enabled = False`, all three handlers raise `HTTP 501 Not Implemented` ("Product depth is not enabled" / "Price components are not enabled"). No reads or writes to `T.product_depth` occur. Existing catalog endpoints continue returning `HTTP 200` unchanged.

### 5.2 Non-owner access to write endpoint

`PUT /items/{item_id}/price-components` calls `_require_item_owner(item_id, user_sub)` before any service invocation. If the item does not exist, `HTTP 404` is raised. If the item exists but `creator_id != user_sub`, `HTTP 403` is raised. Items with no `creator_id` (legacy/seeded items) treat any authenticated user as owner, consistent with `_require_category_owner` at `app/routers/catalog.py:247–252`.

### 5.3 Component date-window validation

Before calling `set_price_components`, the handler validates that within the submitted `components` list:

- No two components of the same `price_type` have overlapping `[effective_at, expires_at)` windows. If `component.expires_at` is absent, the window is treated as open-ended.
- No component has `expires_at <= effective_at` (zero-length window). Return `HTTP 422` ("expires_at must be greater than effective_at").
- No component's `price_type` differs from `body.price_type` (belt-and-suspenders: Pydantic already coerces, but the service may reassign). Return `HTTP 422` if any component's `price_type` value does not match `body.price_type`.

The handler performs this validation in a Python loop before calling the service, so the service can assume valid windows. Overlap detection: sort by `effective_at`, then check consecutive pairs.

### 5.4 Empty component list (clear operation)

`PUT /items/{item_id}/price-components` with `{"price_type": "DEFAULT", "components": []}` is the idempotent "clear all DEFAULT components" operation. The service deletes all existing `PRICE#DEFAULT#*` rows and writes none. The response returns `PriceComponentListOut(item_id=..., components=[], count=0)`. This is a valid, intentional use case — an operator rolling back to scalar pricing.

### 5.5 Scalar fallback in `GET /effective-price`

When `resolve_effective_price` finds no component row with `effective_at <= as_of` for the requested `price_type`, it falls back to the item's scalar `price_cents` from `T.catalog`. The handler sources this fallback value from the `item` dict already fetched in step 3 (`_find_item_by_id`), then calls the service with that value as the `scalar_fallback`:

```python
item = _find_item_by_id(item_id)  # already fetched
scalar_price = ddb_to_int(item.get("price_cents", 0))
amount_cents, currency, pc_id = product_price_components.resolve_effective_price(
    item_id, resolved_as_of, price_type, scalar_fallback=scalar_price
)
```

The service returns `(scalar_price, item.get("currency", "USD"), None)` in the fallback path; `pc_id` is `None`. The response sets `source="scalar_fallback"` and `price_component_id=None`.

For the `DEFAULT` price type, the scalar `price_cents` is always available. For non-DEFAULT types (e.g. `LIST`, `PROMO`), a fallback to scalar `price_cents` may not be semantically correct — the caller receives `source="scalar_fallback"` and should interpret this as "no PROMO price configured; use the DEFAULT price instead."

### 5.6 `as_of` parameter — historical queries

Supplying `as_of` in the past returns the price that was active at that historical moment. Supplying `as_of` in the future returns the price that will be active at that future moment (scheduled price). Both are legitimate queries. There is no validation that `as_of` must be in the past or present.

### 5.7 `GET /price-components` on item with no depth rows

`list_price_components` delegates to a SK-prefix query on `T.product_depth` with `PK=ITEM#{item_id}` and `SK begins_with "PRICE#"`. If the item exists in `T.catalog` but has no `PRICE#` rows in `T.product_depth`, the query returns an empty list. The response is `PriceComponentListOut(item_id=..., components=[], count=0)` — not a 404. This is correct: the item exists, it simply has no price components configured.

### 5.8 Currency mismatch across components

All components in a single `PUT` call are required to use the same `currency` value. If any component uses a different currency than the first, the handler raises `HTTP 422` ("All components must use the same currency"). The PRD-012 service enforces this at write time, but the router checks it eagerly so the error is surfaced before any DDB writes occur.

### 5.9 `price_type` in component vs. body.price_type

`ProductPriceComponentIn` carries `price_type` as a field to support future batch-upsert patterns. In the `PUT /price-components` endpoint, each component's `price_type` must equal `body.price_type`. The handler raises `HTTP 422` if any component's `price_type` differs.

### 5.10 Deterministic `price_component_id`

`price_component_id = sha256(f"{item_id}\x00{price_type}\x00{effective_at}".encode())[:16]`. This is the same component produced regardless of the number of times `set_price_components` is called with the same input. The PRD-012 service computes this; the router surfaces it in `ProductPriceComponentOut`.

### 5.11 Route declaration order — no conflict with existing routes

The three new routes use the path prefix `/items/{item_id}/price-components` and `/items/{item_id}/effective-price`. FastAPI matches routes in declaration order. The existing `/items/{item_id}/stock` (`:721`), `/items/{item_id}/reviews` (`:830` GET, `:861` POST, `:904` DELETE), `/items/reorder` (`:421`), `/items/search` (`:465`), and `/items/bulk-delete` / `/items/bulk-update` (`:926`, `:954`) have distinct path segments. There is no ambiguity. The literal segments `price-components` and `effective-price` are unambiguous against all existing `{item_id}` sub-paths.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

All three endpoints delegate to `product_price_components.set_price_components`, `list_price_components`, and `resolve_effective_price` (PRD-012). These functions use only `T.product_depth` and `T.catalog` — both of which resolve to DynamoDB Local at `http://localhost:8001` in dev and real AWS DynamoDB in prod. There is no `S.dev_mode` branch anywhere in this ticket. Behavior is identical in both environments. This satisfies SECOPS-007.

### 7.2 Idempotency

- `PUT /price-components` is a full idempotent replace scoped to `(item_id, price_type)`. Submitting the same component list twice produces the same stored state. The `price_component_id = sha256(item_id + price_type + str(effective_at))[:16]` is a stable correlation key for the same logical component, enabling callers to detect no-op re-submissions.

- `GET /price-components` and `GET /effective-price` are pure reads; they are trivially idempotent.

### 7.3 Security

**Ownership**: `PUT /price-components` calls `_require_item_owner` before any service call. Non-owners receive `HTTP 403`. `_require_item_owner` reads `T.catalog` via `ByItemId` GSI and checks `creator_id == user_sub`.

**Subscription gate**: `GET /price-components` and `GET /effective-price` apply `can_access_creator(ctx["user_sub"], creator_id)` after `_find_item_by_id`. Unauthenticated callers cannot reach these endpoints because `require_ui_session` rejects them before the handler body runs.

**No money movement**: These three endpoints are read-only enrichment for the price display layer. None call `new_ledger_entry` (`app/services/billing_shared.py:224`) <!-- VERIFIED: app/services/billing_shared.py:224 --> or `refund_payment` (`app/routers/billing.py:1287`). <!-- VERIFIED: app/routers/billing.py:1287 --> Cart and checkout paths continue to use the scalar `price_cents` from `T.catalog` exclusively. The price-component layer resolves informational prices for display, not authorization of charges.

**Input validation**: `price_type` is a `PriceTypeEnum` — Pydantic raises `HTTP 422` on unknown values before the handler body executes. `amount_cents` is bounded `ge=0, le=10_000_000_00`. `effective_at` and `expires_at` are bounded `ge=0`. The router additionally validates date-window non-overlap (§5.3) and currency consistency (§5.8) before calling the service.

## 8. Backward Compatibility & Migration

### 8.1 With `PRODUCT_DEPTH_ENABLED=false` (the default)

All three new endpoints return `HTTP 501`. No existing endpoints are modified. `T.catalog`, `T.shopping_cart`, `T.billing`, and all existing services are untouched. The scalar `price_cents` on `CatalogItemOut` is unchanged.

### 8.2 With flag on but no price-component rows

`GET /price-components` returns `{"item_id": "...", "components": [], "count": 0}` — not a 404. `GET /effective-price` returns `{"source": "scalar_fallback", "amount_cents": <item.price_cents>, ...}`. Both are valid "no depth data configured" responses.

### 8.3 Enabling on a live system

`T.product_depth` was created empty by PRD-002. Enabling `PRODUCT_DEPTH_ENABLED=true` on a live system with existing catalog items is safe. All existing items have no `PRICE#` rows; all three endpoints return empty / fallback results. No backfill or migration is required.

### 8.4 Route declaration order

PRD-013 appends three handlers after line 1000 of `app/routers/catalog.py`. No existing handler is moved or modified. The path segments `/price-components` and `/effective-price` are new and do not shadow any existing route.

### 8.5 `CatalogItemOut` unchanged

The three new endpoints do not modify `CatalogItemOut`. The `product_type`, `variant_count`, `has_features`, and `bundle_component_count` fields introduced by PRD-003 are not relevant to the price-component endpoints. Future PRD-015 UI work may choose to include `effective_price_cents` in `CatalogItemOut`, but that is outside PRD-013's scope.

## 10. Open Questions / Assumptions

1. **Assumption**: The PRD-012 service (`app/services/product_price_components.py`) provides `set_price_components`, `list_price_components`, and `resolve_effective_price` as specified. If the service interface differs (e.g. `resolve_effective_price` does not accept a `scalar_fallback` argument), the router falls back to calling `_find_item_by_id` to obtain `price_cents` and passes it explicitly. This spec assumes the service signature includes a `scalar_fallback` parameter.

2. **Assumption**: `_require_item_owner` is introduced by PRD-008 and is present on the branch when PRD-013 is implemented. If PRD-008 is not yet merged, PRD-013 inlines the identical 8-line helper and deduplicates after merge.

3. **Assumption**: `PriceTypeEnum` in `app/models.py` uses uppercase string values (`"LIST"`, `"DEFAULT"`, etc.) as established by PRD-003 §3.3. The query parameter validator on `GET /effective-price` accepts the enum values case-sensitively. Callers must pass `?price_type=DEFAULT`, not `?price_type=default`.

4. **Assumption**: Date-window overlap validation (§5.3) is a router-level check, not delegated to the PRD-012 service. If PRD-012 already enforces this in the service and raises `HTTP 422`, the router's pre-check is redundant but harmless (it will fire first, before the service is called).

5. **Open question**: Should `GET /effective-price` require item ownership, or should it be read-only (subscription-gated only)? This spec treats it as read-only with the subscription gate, consistent with how `GET /items/{id}/bundle` behaves in PRD-011 (§4.2). If product pricing is considered confidential and only the owner should see it, the handler should call `_require_item_owner` instead.

6. **Open question**: `GET /price-components` returns components across all price types when no `price_type` filter is supplied. If items with many price types and many dated rows produce large lists, a pagination mechanism may be needed. For now the design assumes bounded row counts (a given item is unlikely to have more than a few dozen dated rows), consistent with how `list_associations` works in PRD-011 without pagination.

7. **Assumption**: `as_of=0` on `GET /effective-price` is valid (means "from Unix epoch"). This is an unusual but not invalid query. The service correctly returns the scalar fallback unless a component with `effective_at=0` was explicitly set.

8. **Assumption**: The `currency` field on `EffectivePriceOut` is taken from the winning component row when `source="price_component"`, and from `item.get("currency", "USD")` when `source="scalar_fallback"`. The router extracts this from the `(amount_cents, currency, price_component_id)` tuple returned by the service.

9. **Open question**: Should the `PUT /price-components` endpoint accept components for multiple price types in a single call (e.g. set DEFAULT and PROMO simultaneously)? This spec follows the PRD-012 interface which scopes each `set_price_components` call to a single `price_type`. If multi-type batch updates are needed, that is a scope extension beyond PRD-013.
