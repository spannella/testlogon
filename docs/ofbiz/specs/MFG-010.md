# MFG-010 — Lite MRP engine (requirements explosion → suggestions)

**Type:** Feature | **Priority:** P1 | **Estimate:** 5 days
**Milestone:** 4 — Lite MRP

---

## 1. Summary & Goal

MFG-010 implements `app/services/manufacturing_mrp.py`, the lite Material
Requirements Planning (MRP) engine. A single MRP "run" produces a deterministic,
read-only snapshot of net requirements for every demand-bearing SKU within a
configurable planning horizon, then emits per-SKU action suggestions (`produce` /
`purchase` / `none`) that feed the MFG-012 admin UI and any downstream automation.

The engine does **not** mutate inventory, orders, or billing. It reads from
`T.orders`, `T.order_items`, `T.mfg_work_orders`, `T.mfg_mrp`, and
`inventory.get_or_zero`, writes only to `T.mfg_mrp`, and is entirely
flag-gated (`manufacturing_mrp_enabled`, default OFF).

The two public service functions are:

- `run_mrp(horizon_days, location_id, *, user_sub, correlation_id) → MrpRunOut`
- `get_mrp_run(run_id) → MrpRunOut`

The algorithm is:

```
net_requirement = gross_demand − on_hand_available − scheduled_receipts
suggested_quantity = max(0, net_requirement)
suggested_action  = "none" if suggested_quantity == 0 else
                    "produce" if active_bom_exists else "purchase"
```

### 2.3 Demand source — orders / order_items tables

`app/services/commerce_order_service.py:15–16` sets:

```python
self.orders = T.orders
self.order_items = T.order_items
```

Orders are stored in `T.orders` (PK=`order_id`; `scripts/local-ddb-init.py:287–294`)
with a `GSI_STATUS` index (`partition_key="status"`, `sort_key="created_at"`;
`local-ddb-init.py:292`). Each order item row sits in `T.order_items`
(PK=`order_id`, SK=`item_id`; `local-ddb-init.py:295`) with a `sku` attribute
and an integer `quantity` field written at `commerce_order_service.py:96`.

**IMPORTANT — `created_at` is an ISO 8601 string, not a Unix integer.**
`commerce_order_service._now_iso()` (`commerce_order_service.py:19–20`) returns
`datetime.now(timezone.utc).isoformat()`, so every order row's `created_at` is
a string like `"2024-01-15T12:00:00+00:00"`. The horizon filter in
`_collect_gross_demand` must therefore use `datetime.fromisoformat()` comparison,
NOT `int(item["created_at"])`. Example:

```python
from datetime import datetime, timezone, timedelta
cutoff_dt = datetime.now(timezone.utc) - timedelta(days=horizon_days)
# keep item only if datetime.fromisoformat(item["created_at"]) >= cutoff_dt
```

"Open" sales orders contributing gross demand are those with `status IN
{"pending_payment"}` — the only status written by `commerce_order_service`
(`commerce_order_service.py:75`). Statuses like `"paid"` or `"confirmed"` are
not set by `CommerceOrderService`; see open question §10.2 for discussion.

Note: `GSI_STATUS` at `local-ddb-init.py:292` does **not** declare
`attr_types={"created_at": "N"}`, consistent with `created_at` being stored as
a String in DDB. The horizon comparison must be done **in Python after query**,
not as a DDB `FilterExpression` numeric comparison. The service scans each
open-demand status partition and filters `created_at` in Python via
`datetime.fromisoformat()` + horizon delta.

### 2.4 BOM explosion — manufacturing_bom.explode_bom

`docs/ofbiz/specs/MFG-004.md` specifies `explode_bom(bom_id, build_qty)`,
which returns:


### 2.5 Scheduled receipts — open work orders

`docs/ofbiz/specs/MFG-002.md:225–226` shows `mfg_work_orders` has two GSIs:
`GSI_STATUS` (PK=`status`, SK=`created_at`) and `GSI_PRODUCT`
(PK=`product_sku`, SK=`created_at`). Open work orders in statuses
`{"created", "released", "in_progress"}` represent in-flight production.
Their `quantity` attribute on the META row is the scheduled receipt for the
`product_sku`.

Purchase-order scheduled receipts are deferred: the PUR (Purchasing) module
does not yet exist — no `purchasing_scm_enabled` flag, no `T.purchase_orders`
handle, no purchasing service file. The MRP engine accepts an optional
`scheduled_receipts_override: Dict[str, int]` parameter for callers that can
supply purchase-order quantities; otherwise it queries only open work orders.

## 3. Data Model

MFG-010 writes exclusively to `T.mfg_mrp`, which is provisioned by MFG-002
(`docs/ofbiz/specs/MFG-002.md:233–288`). No new tables are introduced.

### 3.1 `mfg_mrp` — single-table layout (MFG-002 spec)

```
PK: mrp_run_id  (S)  sha256(correlation_id)[:32] or uuid4().hex
SK: sk           (S)  "META" | "REQ#{sku}#{seq:06d}"
```

**Header row** (`sk = "META"`):

| Attribute | DDB Type | Notes |
|---|---|---|
| `mrp_run_id` | S | PK; deterministic or random |
| `sk` | S | `"META"` |
| `status` | S | `pending` / `running` / `completed` / `failed` |
| `horizon_days` | N | Planning horizon used (integer) |
| `location_id` | S | Inventory location scoped (default `"warehouse"`) |
| `correlation_id` | S | Caller-supplied idempotency key |
| `created_at` | N | Unix seconds (integer) |
| `completed_at` | N | Unix seconds; 0 until complete |
| `requirement_count` | N | Total `REQ#` rows written |
| `user_sub` | S | Requestor |

**Requirement row** (`sk = "REQ#{sku}#{seq:06d}"`):

The `sku` embedded in the SK allows per-SKU `get_item` lookups; `seq` (zero-padded
6-digit integer) disambiguates multiple rows per SKU if the explosion produces
the same component through different BOM paths at different depths (uncommon,
but structurally possible with multi-level BOMs).

| Attribute | DDB Type | Notes |
|---|---|---|
| `mrp_run_id` | S | PK; FK to header |
| `sk` | S | `"REQ#{sku}#{seq:06d}"` |
| `sku` | S | Component or finished-goods SKU |
| `gross_requirement` | N | Total demand (integer) |
| `on_hand_available` | N | `inventory.get_or_zero(sku).available` |
| `scheduled_receipts` | N | From open work orders (+ future PO receipts) |
| `net_requirement` | N | gross − available − scheduled_receipts (may be negative) |
| `suggested_action` | S | `"produce"` / `"purchase"` / `"none"` |
| `suggested_quantity` | N | `max(0, net_requirement)` |
| `bom_id` | S | BOM used for produce suggestions; empty for purchase/none |

**GSI (from MFG-002 spec, `scripts/local-ddb-init.py:279–288`):**

```
GSI_RUN_STATUS  PK: status (S)  SK: created_at (N)
```

Purpose: list pending/running/completed MRP runs for the admin queue.

`attr_types`: `{"created_at": "N"}` — mandatory per CLAUDE.md numeric-GSI gotcha.

**TableDef** (already specified in MFG-002):

```python

    "sk",

        {"index_name": "GSI_RUN_STATUS", "partition_key": "status", "sort_key": "created_at"},
```

This `TableDef` is appended at `scripts/local-ddb-init.py` after the

### 4.2 `run_mrp` algorithm (step-by-step)

1. **Resolve parameters.** `horizon_days` defaults to
   `S.mfg_mrp_default_horizon_days` (30). `location_id` defaults to
   `"warehouse"` (matching `inventory.DEFAULT_LOCATION`).

2. **Derive run ID.** `corr = correlation_id or f"mrp_run:{uuid4().hex}"`;
   `mrp_run_id = hashlib.sha256(corr.encode()).hexdigest()[:32]`.

3. **Idempotency check.** Attempt
   `T.mfg_mrp.put_item(Item={...header, status="running"}, ConditionExpression="attribute_not_exists(mrp_run_id)")`.
   On `ConditionalCheckFailedException`, fetch and return the existing run via
   `get_mrp_run(mrp_run_id)` — this covers both re-runs and concurrent
   duplicate requests.

4. **Collect gross demand.** Call `_collect_gross_demand(horizon_days, location_id)`.
   Open demand statuses: `{"pending_payment"}` (the only status written by
   `CommerceOrderService`; extend if additional statuses are confirmed — see §10.2).
   Cutoff: `datetime.now(timezone.utc) - timedelta(days=horizon_days)`. Compare
   against `created_at` as an ISO 8601 string via `datetime.fromisoformat()` —
   orders do NOT store an integer Unix timestamp (see §2.3). Result: `{sku: qty}`
   dict of finished-goods gross demand.

5. **For each demanded finished-goods SKU:**
   a. Read `inventory.get_or_zero(sku, location_id)` to get `on_hand_available`.
   b. Read open work-order scheduled receipts for `sku` via `_collect_scheduled_receipts({sku}, location_id)`.
   c. `net_req = gross_qty - on_hand_available - scheduled_receipts`.
   d. If `net_req <= 0`: write `REQ#` row with `suggested_action="none"`,
      `suggested_quantity=0`. **Do not explode into components** — no shortage.
   e. If `net_req > 0` and an active BOM exists (`get_active_bom(sku)` is not None):
      - Emit a `produce` suggestion row for the finished good.
      - Call `manufacturing_bom.explode_bom(bom_id, net_req)` to get
        the flattened component list.
      - For each component in the explosion result, recursively compute
        supply vs. demand (the component may itself have a BOM — the BOM
        service handles recursive explosion; the MRP engine simply calls
        `explode_bom` which returns the fully-flattened leaf list).
      - For each leaf component SKU, read its `inventory.get_or_zero` and
        open work-order receipts, compute `net_requirement`, and write a
        `REQ#` row with `suggested_action="purchase"` if no active BOM
        exists, or `"produce"` if it does.
   f. If `net_req > 0` and no active BOM exists: write `REQ#` row with
      `suggested_action="purchase"`, `suggested_quantity=net_req`.

6. **Aggregate duplicate component SKUs.** Multiple finished-goods SKUs may share
   a common component. The engine maintains an in-memory `{sku: agg}` dict and
   accumulates `gross_requirement` across all exploded demand paths before writing
   `REQ#` rows, so each component SKU appears at most once in the output.

7. **Finalize.** Update the META row: `status="completed"`,
   `completed_at=now_ts()`, `requirement_count=len(req_rows)`.

8. **Audit.** Call `_audit("mrp.run_completed", user_sub, run_id=mrp_run_id,
   requirement_count=...)`. Best-effort.

9. **Return.** Call `get_mrp_run(mrp_run_id)` and return the result.

### 4.3 `get_mrp_run` algorithm

1. `T.mfg_mrp.get_item(Key={"mrp_run_id": run_id, "sk": "META"})` — raise
   `HTTP 404` if not found.
2. Paginated `query(KeyConditionExpression=Key("mrp_run_id").eq(run_id) & Key("sk").begins_with("REQ#"))`.
   Collect all REQ rows (must loop via `LastEvaluatedKey` — per CLAUDE.md "DDB
   FilterExpression doesn't reduce page size" gotcha; a busy table may require
   multiple query pages).
3. Return a dict combining header fields + `requirements` list. Each REQ row
   maps directly to an `MrpRequirementOut` dict.

## 5. Detailed Behavior & Edge Cases

### 5.1 Surplus SKU (negative net requirement)

When `on_hand_available + scheduled_receipts >= gross_requirement`, the net
requirement is ≤ 0. The engine writes a `REQ#` row with
`suggested_action="none"` and `suggested_quantity=0`. The `net_requirement`
field preserves the actual (negative) value so operators can see the magnitude
of the surplus. BOM explosion is **not** triggered for surplus finished goods —
there is no unfulfilled demand to push through the component tree.

### 5.2 Component aggregation across multiple finished-goods SKUs

If `SKU_A` demands 10 units of `COMP_X` and `SKU_B` also demands 5 units of
`COMP_X`, the single `REQ#COMP_X#000000` row records
`gross_requirement=15`, then subtracts shared supply once. This prevents
double-counting on-hand against both demand streams. The aggregation
dict must be built before any REQ rows are written.

### 5.3 Multi-level BOMs and depth limit

`manufacturing_bom.explode_bom` (MFG-004) handles multi-level explosion
recursively up to the configured depth cap (decided in MFG-001; default 5).
From the MRP engine's perspective, `explode_bom` returns the flat leaf list —
MFG-010 does not re-implement explosion logic. If a component has its own
active BOM, `explode_bom` recurses into it and returns only true leaf
components. The MRP engine therefore always receives leaf-level `required_qty`
values; it applies the net-requirement formula once per leaf.

### 5.4 BOM cycle detection

Cycle detection is `explode_bom`'s responsibility (MFG-004). If the BOM
service raises `HTTP 409` (cycle detected), the MRP run catches it, marks the
run header `status="failed"`, writes an error message to the header
`error_detail` attribute, and re-raises a `HTTP 500` to the caller explaining
which BOM triggered the cycle.

### 5.5 Concurrent re-run with same correlation_id

Two concurrent `run_mrp` calls with the same `correlation_id` race on the
`put_item` with `attribute_not_exists`. Exactly one wins; the other
catches `ConditionalCheckFailedException` and immediately calls
`get_mrp_run(mrp_run_id)` to return the in-progress or completed run. No
double REQ rows are written because only the winning writer ever emits them.

### 5.6 GSI_STATUS query — horizon filter in Python

The `orders` table's `GSI_STATUS` has `created_at` as a String-type sort key
(`scripts/local-ddb-init.py:292` does not declare `attr_types`). This is
consistent with `created_at` being an ISO 8601 string
(`commerce_order_service._now_iso()` at `commerce_order_service.py:19–20`).
The MRP engine cannot use a DDB `KeyConditionExpression` range comparison on a
String sort key to filter by cutoff timestamp. Instead:

1. Query `GSI_STATUS` for each open demand status partition. Today only one
   query is needed: `status="pending_payment"`. If additional statuses are
   confirmed (see §10.2), add them here.
2. Fetch all items (paginate via `LastEvaluatedKey`).
3. Filter in Python: keep only items where
   `datetime.fromisoformat(item["created_at"]) >= cutoff_dt`
   where `cutoff_dt = datetime.now(timezone.utc) - timedelta(days=horizon_days)`.
   **Do NOT use `int(item["created_at"])` — orders store an ISO string, not a
   Unix integer (`commerce_order_service.py:19–20`, `commerce_order_service.py:76`).**

This is safe for typical order volumes. If the `orders` table grows very large,
a future migration can store `created_at` as a numeric Unix timestamp with
`attr_types={"created_at": "N"}` on the GSI and use server-side filtering;
that change is out of scope for MFG-010.

### 5.7 Work-order scheduled receipts query

`T.mfg_work_orders` `GSI_STATUS` has `attr_types={"created_at": "N"}` (from
MFG-002 spec). For each open-work-order status (`"created"`, `"released"`,
`"in_progress"`), query `GSI_STATUS` and accumulate `quantity` keyed by
`product_sku`. This is three DDB queries at run time. The result is merged
into the per-SKU `scheduled_receipts` map before net-requirement computation.

### 5.8 Future Purchasing module (PUR) integration hook

`_collect_scheduled_receipts` accepts an optional
`po_receipts: Optional[Dict[str, int]] = None` parameter. When the PUR module
is implemented (it does not exist today — no `purchasing_scm_enabled` flag,
no `T.purchase_orders`), the MRP run caller or the router can inject open
purchase-order quantities here. Until then, the parameter defaults to `None`
and is silently ignored; `scheduled_receipts` is populated from work orders
only.

### 5.9 Inventory read — no location-based multi-warehouse support

`inventory.DEFAULT_LOCATION = "warehouse"` (`inventory.py:43`). The
`location_id` parameter threads through `get_or_zero` calls so MRP is
location-scoped; however, multi-warehouse support is deferred (per MFG-001
scope decision). In Phase 1 only `"warehouse"` is meaningful.

### 5.10 Empty demand — no gross demand in horizon

If no open orders exist within the horizon, `_collect_gross_demand` returns
an empty dict. `run_mrp` writes only the META header row
(`requirement_count=0`, `status="completed"`). `get_mrp_run` returns an empty
`requirements` list. This is a valid completed run, not an error.

### 5.11 Atomicity caveat

DynamoDB provides no cross-partition transactions for writing multiple REQ rows
plus updating the META header. The engine writes REQ rows first (any write
failure leaves the run in `status="running"`), then updates the header to
`status="completed"`. On retry with the same `correlation_id`, the
`ConditionalCheckFailedException` detects the existing `"running"` or
`"completed"` run and returns it. If a run is found in `"running"` status when
fetched via `get_mrp_run`, callers should treat it as in-progress. A separate
administrative `PATCH /ui/manufacturing/mrp/runs/{id}` endpoint (MFG-011) can
mark a stale `"running"` run as `"failed"` if needed.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

No `S.dev_mode` branch exists in `manufacturing_mrp.py`. The identical code
path runs against moto DDB (local) and real DDB (prod). The read-only nature of
the MRP engine (it never calls `inventory.adjust` or any billing function) means
there is no risk of dev-mode mock data leaking into prod behavior.

### 7.2 Idempotency

- **Run-level:** `correlation_id` → deterministic `mrp_run_id` via
  `sha256(...)[:32]`, protected by `attribute_not_exists` conditional put.
  Any retry with the same `correlation_id` returns the same run without writing
  new REQ rows.
- **REQ row writes:** because the run always starts from `status="running"` (set
  atomically on the META row) and the idempotency check fires before any REQ
  rows are written, a partially-written run from a crashed worker simply stays
  in `status="running"` and is not retried without an explicit new
  `correlation_id` or a manual reset.
- **MRP runs are read-only against all other tables.** They do not issue
  reservations, do not decrement inventory, do not write ledger entries.

### 7.3 Auth and access control

All MRP endpoints (implemented by MFG-011) use
`require_admin_or_root_csrf` (`app/auth/policy.py:100`). No non-admin user
can trigger an MRP run or read its output. Sessions use cookie-based auth with
CSRF validation; Bearer-auth skips CSRF per the CLAUDE.md auth contract.

### 7.4 Sensitive data

MRP run outputs contain SKU-level demand and inventory data. They are stored
in `T.mfg_mrp` (not encrypted at rest beyond the baseline DDB encryption).
`mrp_run_id` is deterministic and must not be guessable from public inputs;
the `sha256(correlation_id)` derivation is safe because `correlation_id` is
admin-supplied and non-public.

## 8. Backward Compatibility & Migration

### 8.1 No migration required

MFG-010 adds one new service file and writes exclusively to `T.mfg_mrp`.
With `MANUFACTURING_MRP_ENABLED=false` (default), no existing code path
changes, no table is mutated, and the four manufacturing tables remain dormant.

### 8.2 Enabling the flag in production

The recommended procedure:

1. Deploy the code with `MANUFACTURING_MRP_ENABLED=false` (default).
2. Confirm `mfg_mrp` table exists in prod DDB (created by MFG-002 deployment).
3. Flip `MANUFACTURING_MRP_ENABLED=true` in the environment.
4. Trigger a test MRP run via the admin UI (MFG-012) or direct API call.

No data backfill is required — MRP runs are ephemeral snapshots computed on
demand from existing `orders`, `order_items`, and `mfg_work_orders` data.

### 8.3 `orders` GSI_STATUS sort-key type caveat

The `orders` table's `GSI_STATUS` has `created_at` as a String sort key today
(`scripts/local-ddb-init.py:292`). This is consistent with the ISO 8601 string
format written by `commerce_order_service._now_iso()` (`commerce_order_service.py:19–20`).
MFG-010 works around this by filtering in Python with `datetime.fromisoformat()`.
If in a future release the table is migrated to a numeric `created_at` sort key
(requiring `UpdateTable` + backfill in prod), the `_collect_gross_demand` function
can add a server-side range filter — the public API and DDB table schema used by
`T.mfg_mrp` are unaffected.

## 10. Open Questions / Assumptions

1. **VERIFIED:** The `orders` table's `GSI_STATUS.created_at` is a String
   type (no `attr_types={"created_at": "N"}` at `scripts/local-ddb-init.py:287–294`).
   Moreover, `created_at` is an ISO 8601 string (`commerce_order_service.py:19–20`),
   not a Unix integer, so the horizon filter MUST use `datetime.fromisoformat()` in
   Python — confirmed and corrected throughout this spec.

2. **CORRECTED:** `CommerceOrderService.create_order` writes only
   `status="pending_payment"` (`commerce_order_service.py:75`). No other status is
   written by the orders service. The statuses `"paid"` and `"confirmed"` are NOT
   present in the orders table today. The MRP engine should query only
   `status="pending_payment"` unless a product decision explicitly adds other
   statuses (which would require adding a status-transition function to
   `commerce_order_service.py`). The earlier claim of three statuses was wrong.

3. **Assumption:** MFG-004's `explode_bom(bom_id, build_qty)` returns a flat
   leaf list (all multi-level recursion handled inside the BOM service). If
   MFG-004 returns only one level (direct components), MFG-010 must implement
   its own recursive loop calling `get_active_bom` + `explode_bom` per
   intermediate component. Spec assumes flat output per MFG-007's precedent
   (`docs/ofbiz/specs/MFG-007.md:105`).

4. **Question:** What happens if `explode_bom` raises `HTTP 409` (cycle
   detected) mid-run? Spec proposes: mark run `status="failed"`, surface error
   to caller. Confirm with team whether the run should still persist partial
   results.

5. **Assumption:** There is no Purchasing module yet — `T.purchase_orders` and
   `S.purchasing_scm_enabled` do not exist (confirmed by grep). The
   `po_receipts` parameter on `_collect_scheduled_receipts` is a forward-
   compatibility hook but is unused in this ticket's scope.

6. **Question:** Should the MRP engine handle `forecast` rows (demand not
   backed by a real order)? The ticket mentions "any explicit forecast rows"
   but no `mrp_forecast` table or model is specified anywhere in the
   manufacturing backlog. This spec defers forecast rows to a future ticket
   and implements demand from orders only.

7. **Assumption:** `mfg_work_orders.quantity` (the build quantity, N type)
   represents the full planned scheduled receipt for MRP purposes, even if the
   work order is only partially issued. The engine uses `quantity` as written
   on the META row; `produced_qty` is 0 until completion, so completed work
   orders (which already produced finished goods and incremented `inventory`)
   do not contribute a second time as scheduled receipts.

8. **Assumption:** Component SKUs are resolved via `manufacturing_bom.explode_bom`
   which returns `required_qty` as integers (using `math.ceil`). MFG-010 stores
   these as integers in `T.mfg_mrp` — no floating-point quantities in REQ rows.
