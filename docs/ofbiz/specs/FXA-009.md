# FXA-009 — Depreciation journal posting (non-cash, balanced, idempotent)

## 1. Summary & Goal

FXA-009 adds `post_depreciation_period(asset_id: str, period: int) -> DepreciationPeriodOut` to `app/services/fixed_assets.py`. For a given `(asset_id, period)` pair, the function:

1. Resolves the schedule row from `T.fixed_asset_schedule` and the asset row from `T.fixed_assets`.
2. Derives a deterministic `journal_id = sha256(f"{asset_id}:period:{period}")[:32]`.
3. Calls `gl_posting.post_journal_entry(journal_id, lines)` — a two-line balanced non-cash entry: **Debit Depreciation Expense / Credit Accumulated Depreciation** for the period's `amount_cents`. The call validates Σdebits == Σcredits before writing; an unbalanced entry raises and nothing is persisted.
4. Flips the schedule row to `schedule_status="posted"` and back-writes `journal_entry_id` / `posted_at` via a conditional `update_item`.
5. Increments `accumulated_depreciation_cents` on the asset row via an atomic `ADD` and, when the running total reaches the depreciable base (`acquisition_cost_cents - salvage_value_cents`), transitions `status` to `"fully_depreciated"`.

Every step is idempotent: if the schedule row already shows `schedule_status="posted"`, the function returns immediately without re-posting. The `post_journal_entry` call itself guards against double-writes via `attribute_not_exists` on the journal table. A re-call therefore produces no duplicate GL entry and no second increment of `accumulated_depreciation_cents`.

This ticket does **not** introduce the background poster loop (that belongs to FXA-010). It is a pure service-layer function that can be called by the FXA-007 admin endpoint, by the FXA-010 poster, or by a test fixture.

## 3. Data Model

FXA-009 writes to two pre-existing tables (`T.fixed_asset_schedule`, `T.fixed_assets`) and reads from a third (`T.gl_journal` via the `gl_posting.post_journal_entry` abstraction). It introduces no new tables or GSIs.

### 3.1 `fixed_asset_schedule` — fields updated by FXA-009

The following attributes are written **only** by `post_depreciation_period` (not `generate_schedule`):

| Attribute | DDB type | Written by FXA-009 | Notes |
|---|---|---|---|
| `schedule_status` | S | `"posted"` | Overwritten from `"scheduled"` |
| `journal_entry_id` | S | deterministic `sha256(...)[:32]` | Added for the first time |
| `posted_at` | N | `now_ts()` | Added for the first time; must be numeric for any future GSI |

The `update_item` targeting `pk="ASSET#{asset_id}"`, `sk="PERIOD#{period:07d}"` uses a `ConditionExpression="schedule_status = :scheduled"` to guard against a concurrent double-post. If the condition fails (status is already `"posted"`), the function treats it as an idempotent replay and reads + returns the existing row. No attribute in the other columns (`period`, `period_start_ts`, `period_end_ts`, `amount_cents`, `asset_id`) is modified.

### 3.2 `fixed_assets` — fields updated by FXA-009

| Attribute | DDB type | Update expression | Notes |
|---|---|---|---|
| `accumulated_depreciation_cents` | N | `ADD accumulated_depreciation_cents :delta` | Atomic increment by `amount_cents` |
| `status` | S | `SET #s = :fully_depreciated` | Only applied when accumulated >= depreciable base |
| `updated_at` | N | `SET updated_at = :ts` | Always updated on a successful post |

Both writes are done in a single `update_item` call with `ReturnValues="ALL_NEW"` so the post-update balance is available for the `fully_depreciated` check in one round trip.

**Why atomic ADD?** A read-modify-write pattern would introduce a race condition if two periods for the same asset are posted concurrently (e.g. two poster instances on different workers). Using DynamoDB's `ADD` operation makes the increment atomic per DDB item-level guarantees.

**`fully_depreciated` flip:** After the `ADD`, the returned `accumulated_depreciation_cents` is compared against `acquisition_cost_cents - salvage_value_cents` (both read from the asset row at the start). If `accumulated >= depreciable_base`, a second conditional `update_item` flips `status = "fully_depreciated"` with `ConditionExpression="status = :active"` to prevent double-flip racing.

### 3.3 `gl_journal` — rows written by `gl_posting.post_journal_entry`

FXA-009 does not write to `T.gl_journal` directly; it delegates to `gl_posting.post_journal_entry`. The OFB-014 implementation is responsible for writing journal rows. For completeness, the expected schema per `docs/adr/ADR-001-ofbiz-commerce-erp.md:296`:

| PK | SK | Key attributes |
|---|---|---|
| `JE#{journal_id}` | `META` | `journal_id`, `gl_date` (YYYY-MM-DD), `posted_at` (N), `source_type` (`"depreciation"`), `source_entity_id` (`asset_id`), `memo` |
| `JE#{journal_id}` | `LINE#1` | `line_no` (1), `account_id`, `debit_cents` (N, > 0), `credit_cents` (N, 0) |
| `JE#{journal_id}` | `LINE#2` | `line_no` (2), `account_id`, `debit_cents` (N, 0), `credit_cents` (N, > 0) |

The depreciation entry always has exactly two lines. `GSI_SOURCE.source_entry_id` is set to `"depr:{asset_id}:{period}"` on the META row so OFB-014's idempotency check can locate existing entries by source. `GSI_DATE.gl_date` is `ledger_date_for_ts(period_end_ts)` — reusing the same YYYY-MM-DD bucketing function used by `billing_shared.ledger_date_for_ts` (`app/services/billing_shared.py:10–13`) so trial-balance day queries stay consistent.

## 4. API / Service Design

### 4.1 `post_depreciation_period` — core service function

**Location:** `app/services/fixed_assets.py` (extends the file created by FXA-005/FXA-006)

```python
def post_depreciation_period(
    asset_id: str,
    period: int,
    *,
    actor_sub: str = "system",
) -> DepreciationPeriodOut:
    """Post a balanced non-cash journal entry for one depreciation period.

    Idempotent: if the period row already shows schedule_status="posted",
    returns the existing row without re-posting.  If the GL journal entry
    already exists (ConditionalCheckFailedException from gl_posting), the
    function catches the conflict, reads the existing row, and returns it.

    Raises:
        HTTPException(503): FIXED_ASSETS_ENABLED is false.
        HTTPException(404): asset_id or period not found.
        HTTPException(409): asset is disposed or period is cancelled.
        HTTPException(422): GL account IDs are not resolved on the asset.
        ValueError: journal lines do not balance (raised inside gl_posting).
    """
    ...
```

**Pseudocode (detailed in section 5):**

1. `_require_enabled()` — raises 503 if `S.fixed_assets_enabled` is false.
2. `asset = _get_asset_item(asset_id)` — raises 404 if not found; raises 409 if `status == "disposed"`.
3. `_validate_gl_ids(asset)` — raises 422 if `gl_depr_expense_account_id` or `gl_accum_depr_account_id` is None or empty.
4. `schedule_row = _get_schedule_row(asset_id, period)` — raises 404 if not found; returns early (idempotent) if `schedule_status == "posted"`; raises 409 if `schedule_status == "cancelled"`.
5. `amount_cents = int(schedule_row["amount_cents"])`.
6. `journal_id = hashlib.sha256(f"{asset_id}:period:{period}".encode()).hexdigest()[:32]` (from `docs/ofbiz/specs/FXA-001.md:513`).
7. Build two `JournalLine` objects:
   - Line 1: `account_id=asset["gl_depr_expense_account_id"]`, `debit_cents=amount_cents`, `credit_cents=0`
   - Line 2: `account_id=asset["gl_accum_depr_account_id"]`, `debit_cents=0`, `credit_cents=amount_cents`
8. `gl_posting.post_journal_entry(lines, journal_id=journal_id, source_type="depreciation", source_entity_id=asset_id, memo=f"Depreciation period {period} for asset {asset_id}", gl_date=ledger_date_for_ts(int(schedule_row["period_end_ts"])))` — raises `ValueError` on imbalance; catches `ConditionalCheckFailedException` as idempotent replay.
9. Flip schedule row to `posted` (conditional update — section 5.2).
10. Increment `accumulated_depreciation_cents` on asset row (section 5.3).
11. If fully depreciated, flip asset status (section 5.4).
12. Emit `audit_event("fixed_asset.depreciation_posted", actor_sub, asset_id=asset_id, period=period, journal_entry_id=journal_id, amount_cents=amount_cents)`.
13. Return `DepreciationPeriodOut` built from the updated schedule row.

### 4.2 HTTP endpoint — `POST /ui/fixed-assets/{asset_id}/depreciation-periods/{period}/post`

**Location:** `app/routers/fixed_assets.py` (extends the file from FXA-007)

This endpoint was previewed in `FIXED_ASSETS_TICKETS.md:140` under FXA-007's router. It exposes `post_depreciation_period` to admin users and is the hook the FXA-010 background poster calls via direct service invocation (not HTTP).

```
POST /ui/fixed-assets/{asset_id}/depreciation-periods/{period}/post
Auth: Depends(require_admin_or_root_csrf)   # app/auth/policy.py:100
Request body: none (all parameters come from path)
```

**Declaration order:** The literal path `/depreciation-periods/{period}/post` is unique enough that it does not collide with other sub-paths. However, per the CLAUDE.md `/schedules`-before-`/{id}` pattern, any static sub-paths (e.g. a future `/depreciation-periods/summary`) must be declared **before** `/{period}` in the router. The `/post` suffix is a verb, not a sub-resource; it prevents ambiguity with a future `GET /depreciation-periods/{period}`.

**503 guard:** The handler checks `S.fixed_assets_enabled` and raises HTTP 503 before delegating to the service, consistent with the `_require_enabled()` guard pattern established in FXA-007 (`docs/ofbiz/specs/FXA-001.md:75`).

**Auth:** `require_admin_or_root_csrf` (not `require_ui_session`) because depreciation posting is an administrative accounting operation. `require_admin_or_root_csrf` is defined at `app/auth/policy.py:100–106`; it enforces `role >= ADMIN` and additionally enforces CSRF for cookie-authenticated requests. `require_admin_session` does **not exist** in this codebase — `app/auth/deps.py:308` defines only `require_root_session`; the admin-level dependency is `require_admin_or_root_csrf` from `app/auth/policy.py`. FXA-007's specification confirms this: all state-mutating FXA endpoints use `Depends(require_admin_or_root_csrf)` (`docs/ofbiz/specs/FXA-007.md:134,168`).

## 5. Detailed Behavior & Edge Cases

### 5.1 Early return — already posted period (idempotent)

If the schedule row already has `schedule_status="posted"` when `post_depreciation_period` is called:

1. The function reads `journal_entry_id` and `posted_at` from the existing row.
2. Returns a `DepreciationPeriodOut` populated from the existing row.
3. Does **not** call `gl_posting.post_journal_entry`.
4. Does **not** modify `accumulated_depreciation_cents` again.
5. Does **not** emit any audit event (the event was already emitted on the original post).

This is the primary idempotency gate and handles all re-runs by the FXA-010 background poster.

### 5.2 Schedule row conditional update

After a successful `post_journal_entry`, the schedule row is updated:

```python
T.fixed_asset_schedule.update_item(
    Key={"pk": f"ASSET#{asset_id}", "sk": f"PERIOD#{period:07d}"},
    UpdateExpression="SET schedule_status = :posted, journal_entry_id = :jid, posted_at = :ts",
    ConditionExpression="schedule_status = :scheduled",
    ExpressionAttributeValues={
        ":posted": "posted",
        ":scheduled": "scheduled",
        ":jid": journal_id,
        ":ts": now_ts(),
    },
)
```

If this conditional update fails with `ConditionalCheckFailedException` (meaning another worker posted the same period concurrently between the early-return check and this update), the function catches the exception and reads the current row to return its state — correct final state is guaranteed because both writers applied the same journal entry via the OFB-014 `attribute_not_exists` guard. No `accumulated_depreciation_cents` increment is attempted in this case (the first writer already incremented it).

### 5.3 `accumulated_depreciation_cents` atomic increment

```python
result = T.fixed_assets.update_item(
    Key={"pk": f"ASSET#{asset_id}", "sk": "META"},
    UpdateExpression="ADD accumulated_depreciation_cents :delta SET updated_at = :ts",
    ExpressionAttributeValues={":delta": amount_cents, ":ts": now_ts()},
    ReturnValues="ALL_NEW",
)
new_accumulated = int(result["Attributes"]["accumulated_depreciation_cents"])
```

`ADD` is atomic at the DynamoDB item level. Two concurrent posts of the same period would both reach this point only if both cleared the `post_journal_entry` `attribute_not_exists` guard — impossible if OFB-014 correctly enforces it. Defense in depth: even if both increments executed, the `accumulated_depreciation_cents` would be over-incremented; the `fully_depreciated` status transition (below) uses a separate conditional that reads the post-increment value, so it would fire on the second write too. The net over-count would be caught by the `> depreciable_base` check (section 5.5).

### 5.4 `fully_depreciated` status transition

After the `ADD`, inspect the returned `new_accumulated`:

```python
depreciable_base = (
    int(asset["acquisition_cost_cents"]) - int(asset["salvage_value_cents"])
)
if new_accumulated >= depreciable_base:
    try:
        T.fixed_assets.update_item(
            Key={"pk": f"ASSET#{asset_id}", "sk": "META"},
            UpdateExpression="SET #s = :fd",
            ConditionExpression="#s = :active",
            ExpressionAttributeNames={"#s": "status"},
            ExpressionAttributeValues={":fd": "fully_depreciated", ":active": "active"},
        )
        audit_event("fixed_asset.fully_depreciated", actor_sub,
                    asset_id=asset_id, accumulated=new_accumulated)
    except ClientError as exc:
        if not _is_conditional_conflict(exc):
            raise
        # Already fully_depreciated or disposed — no action needed
```

The `ConditionExpression="#s = :active"` guards against double-flip: if the asset was already transitioned by a concurrent post or was disposed (FXA-011), the conditional silently fails. `_is_conditional_conflict` is imported from `app/services/kyc_cases.py` or reimplemented locally — the same check is used across the codebase (`app/services/kyc_cases.py:112–113`).

### 5.5 Over-accumulation guard (salvage floor)

After the final period posts, `net_book_value_cents = acquisition_cost_cents - accumulated_depreciation_cents` must equal `salvage_value_cents`. The schedule generation (FXA-006) guarantees `sum(period.amount_cents) == depreciable_base` exactly (last-period rounding from `docs/ofbiz/specs/FXA-001.md:505–509`). Therefore accumulation never exceeds the depreciable base when all periods post. FXA-009 does not need a separate cap — but if `accumulated_depreciation_cents` somehow exceeded the depreciable base (e.g. a manual DDB edit or a future test), `fully_depreciated` would be triggered on the first such post, and subsequent posts would fail the `"disposed"` or `"fully_depreciated"` asset guard at step 2 (the asset status check).

### 5.6 GL account ID validation

If either `gl_depr_expense_account_id` or `gl_accum_depr_account_id` on the asset row is `None` or an empty string, `post_depreciation_period` raises `HTTPException(422, detail="gl_account_ids_not_resolved")`. This guards against posting to an unlinked account, which would create orphaned GL lines that break trial balance. The condition arises only if FXA-008's seed has not run, which should not happen in normal operation (`FIXED_ASSETS_ENABLED` gates both the seed and the router).

### 5.7 Disposed asset guard

`T.fixed_assets` returns `status="disposed"` for a disposed asset. FXA-009 raises `HTTPException(409, detail="asset_disposed")` at step 2. FXA-011's `dispose_asset` cancels remaining schedule rows (`schedule_status="cancelled"`); even without the asset-level guard, a cancelled period would be caught at step 4's `schedule_status == "cancelled"` check (`HTTPException(409, detail="period_cancelled")`).

### 5.8 Unbalanced journal lines (programming error guard)

`gl_posting.post_journal_entry` validates Σdebits == Σcredits internally and raises `ValueError("unbalanced journal entry")` if lines do not balance. For the depreciation two-line entry, both lines always carry `amount_cents`, so they are always balanced by construction. This guard is meaningful for future callers that might pass custom lines. FXA-009 lets the `ValueError` propagate — it becomes an HTTP 500 at the router boundary, which is appropriate since an unbalanced entry indicates a programming error, not a user input error.

### 5.9 `gl_posting.post_journal_entry` not yet merged

Until OFB-014 is deployed, FXA-009 cannot be fully wired. The service function is written with the lazy import (`from app.services import gl_posting`) so the file is import-safe even when `gl_posting.py` does not exist — it only fails at call time. Tests mock `gl_posting` at the module level (see section 9).

### 5.10 `period_end_ts` → `gl_date` mapping

The OFB-016 trial-balance day-bucket queries against `GSI_DATE` will pick up this entry on the correct date.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Zero `dev_mode` branches

`post_depreciation_period` contains no `if S.dev_mode` conditional. The same code path runs in dev (DynamoDB Local at port 8001, moto-backed `T.gl_journal` in tests) and prod (real DynamoDB). The `gl_posting.post_journal_entry` abstraction owns any dev/prod divergence for the journal write; FXA-009 delegates to it without branching.

`billing_shared.ledger_date_for_ts` (`app/services/billing_shared.py:10–13`) is already prod-identical; no mock variant is needed.

### 7.2 Idempotency layers

FXA-009 has three independent idempotency guards, from outermost to innermost:

1. **Schedule row status check** (service-layer pre-flight): if `schedule_status == "posted"`, return early without any DDB write.
2. **GL journal conditional-put** (OFB-014 responsibility): `attribute_not_exists(pk)` on `T.gl_journal` PK `JE#{journal_id}` prevents a duplicate journal entry at the DDB level. The `journal_id` is deterministic per `(asset_id, period)` so two concurrent calls derive the same ID and at most one write succeeds.
3. **Schedule row conditional update** (`ConditionExpression="schedule_status = :scheduled"`): prevents updating an already-posted row's `journal_entry_id` / `posted_at` fields even if the GL write succeeded and the process crashed before the status flip.

The combination makes the function safe under concurrent invocation, network retries, and process restarts. A failed run that partially completed leaves the system in a consistent state: either the journal is written and the schedule row is `posted` (consistent), or neither write committed (retry will succeed), or the journal is written but the schedule row is not yet `posted` (the next call detects `schedule_status == "scheduled"`, posts the journal again — OFB-014's `attribute_not_exists` returns a `ConditionalCheckFailedException`, the caller catches it and proceeds to flip the schedule row — consistent).

### 7.3 `accumulated_depreciation_cents` double-increment prevention

The `ADD` operation is isolated per `(asset_id, period)` in that a given period can only post one `amount_cents` to the asset's accumulator because:
- Layer 1: the schedule row status check prevents a second call from reaching the `ADD`.
- Layer 2: if two concurrent calls pass layer 1 simultaneously, OFB-014's `attribute_not_exists` ensures only one GL write succeeds. The loser catches `ConditionalCheckFailedException` before reaching the `ADD` step.

### 7.4 Security

- `post_depreciation_period` is gated by `require_admin_or_root_csrf` (`app/auth/policy.py:100`) at the HTTP boundary. Direct service calls (from FXA-010 background loop) run with `actor_sub="system"` and are not exposed to external callers.
- `journal_id = sha256(...)[:32]` is non-guessable but not secret — it is an internal DDB key recorded on the schedule row for auditability. No credentials or PII are stored.
- GL account IDs are read from the asset row, which is written by an admin at registration time. A malicious admin could set a wrong `gl_depr_expense_account_id`, but this is an authorization concern (admin trust boundary), not a FXA-009 concern.
- Audit events are written to `T.alerts` via `app/services/alerts.audit_event` (`:644`) on every successful post and on the `fully_depreciated` transition. These events are immutable append-only records in the existing audit trail.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact with `FIXED_ASSETS_ENABLED=false`

With the master flag off, `post_depreciation_period` raises HTTP 503 immediately. The function is never called from any path that was active before this ticket. No imports are added at module level in files that existing active paths rely on (the lazy `from app.services import gl_posting` is inside the function body).

`app/main.py` gains one new `include_router` line for the FXA-007 router (FXA-007's ticket) and potentially one new `add_event_handler` line for FXA-010. FXA-009 itself adds no `main.py` changes.

### 8.2 No schema migrations

FXA-009 writes `journal_entry_id` and `posted_at` as new attributes on existing schedule rows. DynamoDB's schema-free design means adding attributes to an item is always backward-compatible — existing items without these attributes are unaffected, and existing queries that do not project them continue to work.

### 8.3 Prod rollout order

1. OFB-002 and OFB-013/OFB-014 must be merged and deployed first (GL tables and `gl_posting.py` must exist).
2. FXA-002 through FXA-008 must be deployed (settings, tables, models, service, router, GL account seed).
3. FXA-009 can be deployed with `FIXED_ASSETS_ENABLED=false`; no runtime behavior changes.
4. Enable `FIXED_ASSETS_ENABLED=true` and `FIXED_ASSETS_DEPRECIATION_POSTING_ENABLED=true` (separate env var flip after FXA-010 is deployed).

### 8.4 Existing assets created before FXA-008 (null GL IDs)

If assets were created while FXA-008's seed had not yet run (null `gl_*_account_id` fields), `post_depreciation_period` raises 422. The fix is to re-patch the asset via `PATCH /ui/fixed-assets/{asset_id}` with the correct GL account IDs, which is an admin action. No automated migration is needed for FXA-009 since the production environment will have `FIXED_ASSETS_ENABLED=false` until the full stack is deployed.

## 10. Open Questions / Assumptions

1. **`post_journal_entry` exact signature.** This spec assumes `post_journal_entry(lines: list[JournalLine], *, journal_id: str | None = None, source_type: str, source_entity_id: str, memo: str, gl_date: str) -> str`. If OFB-014 uses a different parameter shape (e.g. a `JournalHeader` wrapper object), FXA-009 must adapt the call site. This is the single most critical external assumption (`docs/ofbiz/specs/FXA-001.md:689`).

2. **`attribute_not_exists` on which field.** This spec assumes OFB-014 enforces `attribute_not_exists(pk)` on the `JE#{journal_id}` partition key of `T.gl_journal`. If OFB-014 uses a different uniqueness key (e.g. `source_entry_id`), the idempotency layer 2 guarantee may differ. The FXA-009 side is deterministic (`journal_id = sha256(...)[:32]`), so layer 1 (schedule status check) is the primary guard regardless.

3. **`gl_date` type: string or numeric.** The ADR (`docs/adr/ADR-001-ofbiz-commerce-erp.md:296`) notes `GSI_DATE (gl_date / posted_at N)` with a comment "if numeric". This spec uses `gl_date` as a YYYY-MM-DD string (consistent with `ledger_date_for_ts`), which matches the `GSI_LEDGER_DATE` convention on the billing table. If OFB-014 uses a numeric `gl_date` (Unix timestamp), `attr_types` and the query format differ. Confirmation from OFB-014 maintainer required.

4. **`_is_conditional_conflict` helper location.** This spec assumes a shared helper (identical to `app/services/kyc_cases.py:112–113`) is available. If it is not extracted to a shared module (e.g. `app/core/ddb_helpers.py`), FXA-009 reimplements it locally — two lines, no coordination needed.

5. **`actor_sub` on direct calls.** When the background poster (FXA-010) calls `post_depreciation_period`, it passes `actor_sub="system"`. The audit event records `"system"` as the actor. This is the same pattern used by `app/services/compute_billing.py` (no explicit `actor_sub`, loop runs headlessly). If audit requirements demand a real user sub, the poster must be updated.

6. **`net_book_value_cents` computation.** `DepreciationPeriodOut` does not include `net_book_value_cents` — that lives on `FixedAssetOut`. FXA-009 does not need to return the asset's NBV; callers that need it issue a separate `GET /ui/fixed-assets/{asset_id}`.

7. **Concurrent poster instances.** With `--workers 1` (CLAUDE.md dev constraint), no concurrency issue exists in dev. In prod, if two uvicorn workers run the FXA-010 poster loop concurrently, the three-layer idempotency in section 7.2 prevents double-posting. This spec assumes single-worker dev, multi-worker prod is safe due to DDB atomicity.

8. **`ledger_date_for_ts` import.** `billing_shared.ledger_date_for_ts` is a module-level function in `app/services/billing_shared.py:10–13`. FXA-009 imports it directly: `from app.services.billing_shared import ledger_date_for_ts`. This import is safe (no circular dep; `billing_shared` does not import `fixed_assets`).
