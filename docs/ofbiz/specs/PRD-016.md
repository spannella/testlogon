## 1. Summary & Goal

PRD-016 is the validation gate for the entire product-depth milestone. It produces two
testing artifacts:

1. **Five hermetic offline pytest suites** (`tests/test_prd_product_depth_*.py`) that
   exercise every service introduced in PRD-004 through PRD-013 — category-tree
   move/cycle/ancestry, feature attach/ordering, variant dedupe-idempotency and price
   computation, bundle/kit expansion and cycle rejection, association dedupe, and
   price-component date-window resolution — plus one flag-off regression assertion that
   confirms the existing `CatalogItemOut` serialization and catalog endpoints are
   byte-for-byte unchanged when `PRODUCT_DEPTH_ENABLED` is unset.

2. **One Playwright E2E spec** (`frontend/e2e/catalog-depth.spec.ts`) that exercises
   the admin UI flows added in PRD-015 (create virtual product, attach features, generate
   variants, compose a bundle, build a category tree) under the seeded-session and CSRF
   patterns standard in this repo.

No new production code is written in this ticket. Every test must pass against the code
delivered by PRD-004 through PRD-015. The suites are the acceptance-gate proof that
every PRD-004–015 acceptance criterion is met.

## 2. Context & Current State

### 2.1 Existing test infrastructure

The repo runs pytest via `.venv/bin/pytest` (invoked as `just test`; no `pytest.ini`,
`setup.cfg`, or `pyproject.toml` exists — pytest uses its defaults). Tests do
not rely on the running dev stack; they patch DynamoDB via moto or Mock objects. The
canonical hermetic pattern used across the codebase is:

- Import the module under test after entering a `mock_aws()` context.
- Create real in-memory DynamoDB tables (not mocks) using `boto3.resource(...).create_table(...)`.
- Replace the frozen `T` handle(s) the module reads with `patch.object(module, "T", fake_T)`,
  where `fake_T` is a `types.SimpleNamespace` carrying only the handles the test needs
  (`tests/test_gap_0223_0224_ec2_host_inventory.py:94–98`).
- Mutate the frozen `Settings` singleton via `object.__setattr__(S, "field", value)` and
  restore on teardown (`tests/test_gap_0223_0224_ec2_host_inventory.py:104–118`).
- Call service functions or route-handler coroutines directly via `asyncio.run(...)`
  (`tests/test_catalog_inventory.py:97`, `tests/test_gap_0220_0221_ssh_stored_key.py:316`
  uses `asyncio.new_event_loop()`). The FastAPI `TestClient` is not used in this codebase.
- Cleanup uses `unittest.TestCase.addCleanup` + `contextlib.ExitStack` for deterministic
  ordering.

The `tests/conftest.py` stubs out `prometheus_client` and `multipart` at import time so
none of the service imports fail offline.

`http://localhost:8000` via `page.request`, not the browser. The flag for depth features

skips gracefully if it is false.

### 2.7 The product_depth DynamoDB table (from PRD-002)

The `product_depth` table is **to be declared by PRD-002** in `scripts/local-ddb-init.py`
adjacent to the `shopping_catalog` definition (currently at `:117–125`; PRD-002 will
insert the new `TableDef` immediately after it). It has five GSIs:

- `ByParent` — `GSI_PARENT_PK` (S) / `GSI_PARENT_SK` (N, = `position`), `attr_types={"GSI_PARENT_SK": "N"}`
- `ByVirtualParent` — `GSI_VIRT_PK` (S, = `"VIRTUAL#{parent_item_id}"`) / `GSI_VIRT_SK` (N, = `created_at`)
- `ByFeatureCategory` — `GSI_FTCAT_PK` (S, = `"FTCAT#{feature_category_id}"`) / `GSI_FTCAT_SK` (N, = `position`)
- `ByAssocSource` — `GSI_ASSOC_PK` (S, = `"ASSOC_SRC#{from_item_id}"`) / `GSI_ASSOC_SK` (S, = `"{assoc_type}#{assoc_id}"`)
- `ByItemPrice` — `GSI_PRICE_PK` (S, = `"PRICE#{item_id}#{price_type}"`) / `GSI_PRICE_SK` (N, = `effective_at`)

Numeric GSI sort keys (`GSI_PARENT_SK`, `GSI_VIRT_SK`, `GSI_FTCAT_SK`,
`GSI_PRICE_SK`) are declared with `attr_types` per the CLAUDE.md gotcha. `GSI_ASSOC_SK`
is a String sort key and requires no `attr_types` entry.

### 5.2 Category-tree cases (test_prd_product_depth_categories.py)

**TestCategoryTree (flag on):**
- `test_add_child_creates_tree_row` — call `add_child(None, "cat1", "alice")` then
  query `T.product_depth` for `PK=CAT#cat1, SK=TREE`; assert `depth=1`,
  `GSI_PARENT_PK="PARENT#root"`, `path="root/cat1"`.
- `test_add_grandchild_increments_depth` — chain two `add_child` calls; assert
  grandchild has `depth=2`, `path="root/cat1/cat2"`.
- `test_list_children_via_gsi` — insert three children with distinct positions; assert
  `list_children("cat_parent")` returns them ordered by position ascending.
- `test_get_ancestry_root_child` — single-hop tree; assert `get_ancestry("cat_child")`
  returns the parent row.
- `test_get_breadcrumb_three_levels` — three levels; assert
  `get_breadcrumb("grandchild")` returns `["root_name", "child_name", "grandchild_name"]`.
- `test_list_descendants_bfs` — tree with 3 children and 2 grandchildren; assert
  `list_descendants("root_cat")` returns all 5 descendants.
- `test_move_category_updates_path` — move `cat_b` from parent `root_a` to parent
  `root_c`; assert the `TREE` row for `cat_b` has an updated `path` and `GSI_PARENT_PK`
  pointing at `root_c`.
- `test_move_category_rejects_cycle` — attempt to move `root_a` under `child_of_a`
  (which is already a descendant); assert `HTTPException(400, ...)` is raised.
- `test_max_depth_enforced` — build a chain up to `PRODUCT_DEPTH_MAX_CATEGORY_DEPTH`
  levels deep; assert that adding one more level raises `HTTPException(400, ...)`.
- `test_position_ordering_among_siblings` — insert three children with positions 2, 0,
  1; assert `list_children` returns them in order 0, 1, 2.

**TestFlagOffRegression:**
- `test_flag_off_no_T_product_depth_reads` — with `S.product_depth_enabled=False`, call
  `_catalog_item_out(LEGACY_ITEM_DICT)` (from `app/routers/catalog.py:107`) and assert
  that the returned `CatalogItemOut` has exactly the same field values as a pre-PRD-003
  `CatalogItemOut` constructed directly. Assert `product_type` is absent or `None`,
  `variant_count` is absent or 0, etc.
- `test_flag_off_tree_endpoints_return_501` — call the tree router handler coroutines
  directly (e.g. `list_category_tree`) with `S.product_depth_enabled=False` and assert
  they raise `HTTPException(status_code=404)` or 501 (per the endpoint contract).
- `test_legacy_catalog_item_dict_roundtrip` — construct the exact field set that
  `app/routers/catalog.py:360–390` writes to DynamoDB (no depth fields present); pass
  it through `_catalog_item_out`; assert the result equals a `CatalogItemOut` built with
  the same fields and default values. This guards against PRD-003 inadvertently changing
  default values or making formerly-optional fields required.

- `test_feature_value_price_delta_signed` — add a value with `price_delta_cents=-200`;

### 5.4 Variant cases (test_prd_product_depth_variants.py)

- `test_variant_id_deterministic` — call `_variant_id("parent1", ["fv_red", "fv_xl"])`

- `test_variant_id_ignores_order` — call with `["fv_xl", "fv_red"]` and

- `test_create_variant_duplicate_rejected` — create the same variant twice; assert the

- `test_compute_variant_price_pure` — parent `price_cents=1000`,

### 5.5 Bundle cases (test_prd_product_depth_bundles.py)

- `test_set_components_writes_rows` — call `set_components("bundle1",
  [{"item_id":"c1","quantity":2}, {"item_id":"c2","quantity":1}], "alice")`; assert two
  `BUNDLE#{bundle1}#{c1}` and `BUNDLE#{bundle1}#{c2}` rows on `T.product_depth`.
- `test_kit_price_is_sum_of_components` — seed a KIT product with two components (prices

- `test_bundle_price_uses_override` — BUNDLE product with `price_cents=999` override;

- `test_expand_bundle_flattens_lines` — call `expand_bundle("kit1", qty=3)`; assert the

  outer qty (e.g., component with qty=2 becomes qty=6 for an outer qty=3).
- `test_expand_bundle_cycle_rejected` — add `bundle1` as a component of itself; assert

- `test_expand_bundle_nested_depth_bounded` — create a chain A → B → C → D of depth 4
  (A contains B, B contains C, etc.); set `PRODUCT_DEPTH_MAX_BUNDLE_DEPTH=3`; assert

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity in tests

Both pytest suites and the E2E spec exercise the same code path regardless of environment.
There is no `dev_mode` branch in any depth service; all depth services write only to
`T.product_depth` (DynamoDB), which is backed by DynamoDB Local in dev and DynamoDB in
prod. The tests exercise prod code with moto in-memory tables — no mock-only branches
are introduced.

### 7.2 Deterministic-id idempotency (tested)

PRD-016 explicitly tests idempotency at three points:

1. **Variant id** (`test_variant_id_deterministic`, `test_variant_id_ignores_order`) —
   `sha256(parent_item_id + sorted(feature_value_ids))` must be stable across calls and
   order-invariant.
2. **Association id** (`test_add_association_deterministic_id`) —
   `sha256(from_item_id + assoc_type + to_item_id)` must prevent duplicate rows.
3. **`set_components` idempotency** — calling `set_components` twice with the same
   component list must leave the table in the same state (upsert semantics, no duplicate
   rows).

### 7.3 Flag-off immutability (tested)

`TestFlagOffRegression.test_legacy_catalog_item_dict_roundtrip` asserts that a legacy
catalog item dict (no `product_type`, no `variant_count`, no `has_features`) passes
through `_catalog_item_out` (from `app/routers/catalog.py:107`) and produces a
`CatalogItemOut` with identical serialized output to the pre-PRD-003 baseline. This
guards against silent field-default drift in the Pydantic model.

### 7.4 Ownership assertions (not forked)

The depth services delegate ownership checks to the existing `_require_category_owner`
helper (`app/routers/catalog.py:247`) and `_find_item_by_id` (`app/routers/catalog.py:702`).
Tests that verify 403 for non-owners call the router handler coroutines directly with a
`ctx={"user_sub": "non_owner", "role": "USER", ...}` dict, not via HTTP. This is the
same pattern used throughout the repo: `tests/test_catalog_inventory.py:97`
(`asyncio.run(catalog.adjust_stock("i1", body, ctx=ctx))` with
`patch.object(catalog, "T", Mock(catalog=table))`).

`require_ui_session` is in `app/services/sessions:330`, not `app/auth/deps`; the
catalog router imports it from `app.services.sessions` (`app/routers/catalog.py:39`).

### 7.5 No new money paths

Price components are read-only enrichment (`resolve_effective_price` is queried at
display time). The cart's `price_cents` comes from the scalar catalog item field written
at item creation (`app/routers/catalog.py:370`, `"price_cents": int(body.price_cents)`);
price components never mutate that field and never generate ledger entries. The tests do
not interact with `app/services/billing_shared.py` or `T.billing`.

## 8. Backward Compatibility & Migration

### 8.1 Zero-touch migration

The test for backward compatibility (`TestFlagOffRegression`) verifies that no
migration is required for existing data. With `PRODUCT_DEPTH_ENABLED=false` (the
default), no code path reads `T.product_depth` and the `CatalogItemOut` serialization
is unchanged.

### 8.2 Test data isolation

Each pytest test class operates in an isolated moto context via `ExitStack` +
`mock_aws()`. Tables are named with a `_test` suffix to avoid any accidental overlap
with other test classes that might share module-level moto state (though moto in-process
isolation should be sufficient, the explicit suffix removes any ambiguity). The E2E spec
uses timestamp-suffixed names (`${TS}`) for all created objects to avoid conflicts across
runs without a `just restart`.

### 8.3 No schema migration for production

`product_depth` is a new table created by `just restart` / `scripts/local-ddb-init.py`.
In production an `UpdateTable` + index backfill is required only when migrating from a
pre-PRD-002 deployment. The tests do not address production migration; they create the
table schema fresh in every `setUp`.
