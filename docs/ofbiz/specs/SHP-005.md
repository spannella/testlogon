# SHP-005 — Carrier/ship-method admin router

## 1. Summary & Goal

SHP-005 creates `app/routers/shipping_carriers.py` — the HTTP interface over the
carrier/ship-method catalog service introduced by SHP-004. It exposes:

- **Admin CRUD** (create/list/get/update/disable carriers and their methods) gated
  behind `require_admin_or_root` from `app/auth/policy.py:67` ✓.
- **Storefront list** of enabled ship methods, consumable by the checkout flow,
  gated behind `require_ui_session` from `app/services/sessions.py:330` ✓.

Every handler raises HTTP 503 when `S.shipping_enabled` is `False` (the master
flag introduced by SHP-002, defaulting to `False`). This is the same `_ensure_enabled`
sentinel pattern used in `app/routers/consumer_tax_documents.py:35–37` ✓. The router is
registered in `app/main.py` adjacent to the existing carrier routers at lines 79–80
(`carrier_tracking_mock_router` at line 79, `carrier_tracking_poller_router` at line 80) ✓. No existing route,
service, billing path, or DDB table is modified; with the flag off the new file is
effectively dead code.

## 3. Data Model

SHP-005 is a pure router ticket — it reads and writes via the SHP-004 service, which
owns all DDB access. The single table this ticket touches indirectly is
`T.shipping_carriers` (defined by SHP-002).

### 3.1 `shipping_carriers` table — row shapes consumed by this router

(Full table spec is in `docs/ofbiz/specs/SHP-002.md §3.1`.)

```
PK:  carrier_id (String) — sha256(carrier_code)[:16]
SK:  "CARRIER#"          — carrier header row
     "METHOD#{code}"     — ship method row
GSI: GSI_CODE (carrier_code / sk)
```

**Carrier header row** (SK = `CARRIER#`):
`carrier_id`, `carrier_code`, `display_name`, `online_tracking`, `enabled`,
`created_at` (Number), `updated_at` (Number).

**Method row** (SK = `METHOD#{method_code}`):
`carrier_id`, `carrier_code`, `method_code`, `method_label`, `base_rate_cents`,
`currency`, `transit_days_min`, `transit_days_max`, `enabled`, `created_at`,
`updated_at`.

No `attr_types` override needed for this table — no numeric GSI sort key (the GSI sort
key is `sk`, a String). Numeric `created_at` / `updated_at` are item attributes, not
GSI sort keys. This matches the `SHP-002.md §3.1` TableDef with an empty `attr_types`.

### 3.2 No new tables or DDB definitions in SHP-005

All table definitions, settings keys, and table handle assignments are in SHP-002/SHP-004.
SHP-005 adds no entries to `scripts/local-ddb-init.py`, `app/core/settings.py`, or
`app/core/tables.py`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Create carrier (`POST /ui/shipping/admin/carriers`)

1. `_ensure_enabled()` — raises 503 if flag off.
2. Validate `CarrierIn` — Pydantic rejects unknown carrier codes with 422.
3. Delegate to `create_carrier(carrier_code, display_name)` (SHP-004 service).
4. The service derives `carrier_id = sha256(carrier_code.encode())[:16]` and writes the
   carrier header row with `sk=CARRIER#`. The `sha256`-based ID is deterministic, so
   calling `create_carrier` with the same `carrier_code` is idempotent (SHP-004 uses
   `ConditionExpression=Attr("carrier_id").not_exists()` to guard against duplicate
   writes; if the row already exists the service returns the existing item — no error).
5. `online_tracking` is derived from `carrier_code in CARRIER_TRACKING_URLS`
   (`app/services/carrier_tracking.py:10` ✓).
6. An audit event is emitted by the SHP-004 service via `app/services/alerts.audit_event`
   (the router does NOT emit its own audit; the service owns the audit per the
   `app/services/commerce_order_service.py:106` pattern ✓).
7. Return `CarrierOut` with HTTP 201.

### 5.2 Update carrier (`PATCH /ui/shipping/admin/carriers/{carrier_id}`)

1. `_ensure_enabled()`.
2. `get_carrier(carrier_id)` — if not found, re-raise as HTTP 404
   `{"code": "carrier_not_found"}`.
3. Accepted patch fields: `display_name`. Callers cannot change `carrier_code`
   (it is the identity of the carrier; changing it would break historical shipments that
   reference it). The router validates that no unknown fields are in the request body
   and returns 422 for unrecognised keys.
4. Return updated `CarrierOut`.

### 5.3 Disable carrier (`DELETE /ui/shipping/admin/carriers/{carrier_id}`)

Semantically a soft-disable: sets `enabled=False` on the carrier header row. It does
NOT delete any DDB item. Historical shipments already linked to this carrier are
unaffected — they retain their `carrier_code` and tracking data. The service function
`disable_carrier` sets `enabled=False` and updates `updated_at`. Returns HTTP 200
`{"ok": True, "carrier_id": ...}`. Re-disabling an already-disabled carrier is a
no-op (idempotent).

### 5.4 Add ship method (`POST /ui/shipping/admin/carriers/{carrier_id}/methods`)

1. `_ensure_enabled()`.
2. Validate `ShipmentMethodIn` (Pydantic + `transit_days_min <= transit_days_max`).
3. Look up the carrier; 404 if not found.
4. Service `add_method` writes `sk=METHOD#{method_code}` with
   `ConditionExpression=Attr("carrier_id").not_exists()`. If the row already exists
   the service raises `MethodAlreadyExists`; the router translates this to HTTP 409
   `{"code": "method_already_exists"}`. This allows safe re-posting on network retry
   only when the method does NOT already exist.
5. Return `ShipmentMethodOut` with HTTP 201.

### 5.5 Storefront list (`GET /ui/shipping/methods`)

Returns a flat list of all enabled methods across all enabled carriers, ordered by
carrier code then method code. The SHP-004 service uses `GSI_CODE` to scan enabled
carriers and then queries their method rows in a single pass. No pagination — the
complete method catalog is typically fewer than 25 rows and fits in a single response.
Non-admin users see only this endpoint; the `/admin/*` hierarchy is 403 for them.

### 5.6 PATCH body validation

The `PATCH` endpoints accept a `dict` body (not a typed Pydantic model). This allows
partial updates without requiring all fields. The router filters the incoming dict to
only the accepted patchable fields before delegating to the service:

- Carrier patch: `{"display_name": str}`.
- Method patch: `{"method_label": str, "base_rate_cents": int, "currency": str,
  "transit_days_min": Optional[int], "transit_days_max": Optional[int]}`.

Any key outside this allowlist causes a 422 response before the service is called.

### 5.7 Exception mapping

| Service exception | HTTP response |
|---|---|
| `CarrierNotFound` | 404 `{"code": "carrier_not_found", "carrier_id": ...}` |
| `MethodNotFound` | 404 `{"code": "method_not_found", "carrier_id": ..., "method_code": ...}` |
| `MethodAlreadyExists` | 409 `{"code": "method_already_exists"}` |
| Pydantic `ValidationError` (body) | 422 (FastAPI default) |

Unexpected DDB errors (`ClientError`) are not caught here — they propagate to the
global FastAPI exception handler (`app/main.py`) and return HTTP 500.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

There is no `dev_mode` branch in this router. All 11 endpoints follow the same code
path in dev (DynamoDB Local on port 8001, moto S3) and in prod (real DynamoDB). The
`_ensure_enabled()` check is identical in both environments — setting `SHIPPING_ENABLED=true`
in `.env.local` enables the feature locally with the exact same logic path as prod.

No in-memory fallback, no `if S.dev_mode:` branch, no mock substitution in this file.
The only environment-specific behaviour is in `carrier_tracking.py` (unchanged) and the
underlying moto mock (irrelevant to this router).

### 7.2 Idempotency

- `POST /ui/shipping/admin/carriers` — idempotent for the same `carrier_code`: the
  SHP-004 service uses a conditional put; duplicate creation returns the existing row,
  not an error. This satisfies the SHP-001 seed-idempotency requirement (the seeder
  calls `create_carrier` for UPS/FedEx/USPS/DHL/manual on startup without checking
  whether they already exist).
- `DELETE` (disable) — idempotent: disabling an already-disabled carrier or method is
  a no-op returning the same 200 body.
- `POST /methods` — **not** fully idempotent on replay: re-posting an existing method
  returns 409 (design intent — use PATCH to update an existing method, not re-POST).

### 7.3 CSRF

Mutation endpoints use `require_admin_or_root_csrf` (`app/auth/policy.py:100`), which
calls `enforce_cookie_csrf` (`policy.py:71`). This enforces the `x-csrf-token` header
on cookie-authenticated requests and is a no-op for Bearer-token clients (API keys,
E2E `request` fixture). The read endpoints (`GET`) use `require_admin_or_root` without
CSRF; safe methods do not mutate state so no CSRF protection is needed.

### 7.4 Role enforcement

The admin CRUD paths raise HTTP 403 for a `Role.USER` caller via `require_roles` in
`app/auth/policy.py:49`. The error body is structured:
`{"code": "role_required", "required_roles": ["admin", "root"], "actual_role": "user"}`
(role values are lowercase strings — `Role.ADMIN.value == "admin"`, etc., per `app/auth/roles.py:9-11`).
The storefront list endpoint (`GET /ui/shipping/methods`) accepts any authenticated
session (`Role.USER` included).

### 7.5 No money movement

SHP-005 manages the carrier/method **catalog** only. No billing ledger entries, no
`refund_payment` calls, no Stripe/PayPal/CCBill integration. Money movement (refund of
shipping charges) belongs to SHP-011/RMA, which must reuse `refund_payment` per the
cross-cutting constraint; SHP-005 does not touch it.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact with flag off

With `SHIPPING_ENABLED=false` (the default):
- All 11 new endpoints return 503.
- `app/services/carrier_tracking.py`, `carrier_tracking_poller`, `carrier_tracking_mock`
  are byte-for-byte unchanged.
- `app/routers/shoppingcart.py`, `app/services/shoppingcart.py`,
  `app/services/commerce_order_service.py`, and all billing paths are byte-for-byte
  unchanged.
- `app/core/tables.py` gains four new `_FloatSafeTable` handles (`shipping_carriers`,
  `shipments`, `shipment_items`, `shipment_packages`) per SHP-002 (these do not yet exist —
  `app/core/tables.py` has no `shipping*` entries today, confirmed) ✓; these are
  always-initialised from settings-supplied table names and fail lazily only
  when the endpoints are actually invoked.

### 8.2 `GET /openapi.json` change

The 11 new paths appear in the OpenAPI schema regardless of the flag value (unconditional
`include_router`). This is consistent with how all other routers are registered (e.g.
`carrier_tracking_poller_router` at `main.py:681`). The `tags=["shipping-carriers"]`
label keeps the new group visually distinct from the existing carrier-tracking group
in Swagger UI.

### 8.3 No DDB migration

`shipping_carriers` is a new table. Existing DDB tables (`orders`, `purchase_transactions`,
`billing`, etc.) are not modified. Existing rows are not touched.

### 8.4 Enabling in production

1. Deploy the code with `SHIPPING_ENABLED=false` (default). Verify OpenAPI shows the
   new paths; hitting them returns 503.
2. Run `scripts/local-ddb-init.py` equivalent in prod to create the `shipping_carriers`
   table (plus `shipments`, `shipment_items`, `shipment_packages` from SHP-002).
3. Set `SHIPPING_ENABLED=true`. Verify `GET /ui/shipping/methods` returns `{"methods":[]}`.
4. Call the seeder (`seed_default_carriers()` from SHP-004) to populate UPS/FedEx/USPS/DHL/manual.
5. Verify admin CRUD works end-to-end.

## 10. Open Questions / Assumptions

**OQ-1 (SHP-004 service interface)**: This spec assumes the SHP-004 service exposes
exactly the function names listed in §2.4 and §4.1. If SHP-004 uses a class-based
service (e.g. `ShippingCarrierService`) rather than module-level functions, the router
will need a thin adapter. Verify against the SHP-004 spec before implementation.

**OQ-2 (CarrierIn uniqueness constraint)**: The spec assumes `create_carrier` is
idempotent (same carrier code → return existing row). If SHP-004 raises a
`CarrierAlreadyExists` exception instead, the router must catch it and return 200
(or 201) with the existing `CarrierOut`. Clarify intended behaviour with SHP-004 owner.

**OQ-3 (Storefront authentication)**: The storefront endpoint (`GET /ui/shipping/methods`)
uses `require_ui_session`. If unauthenticated pre-checkout browsing needs shipping costs,
a future ticket (SHP-007 or later) will need to add a public variant. SHP-005 is
session-gated for now.

**OQ-4 (PATCH body model)**: The spec uses an untyped `dict` for PATCH bodies filtered
by an allowlist. An alternative is a dedicated `CarrierPatchIn` / `ShipmentMethodPatchIn`
Pydantic model with all fields `Optional`. The typed approach gives better OpenAPI
documentation. Either approach is valid; preference is the typed model for cleaner
OpenAPI output — but that requires adding two more model classes to `app/models.py`
as part of this ticket rather than deferring to SHP-003/future cleanup.

**OQ-5 (Re-enabling a disabled carrier/method)**: The spec assumes `update_carrier`
can set `enabled=True` on a previously disabled carrier (via the PATCH endpoint). The
DELETE endpoint only sets `enabled=False`; there is no separate "re-enable" endpoint.
A PATCH with `{"enabled": true}` would re-enable a carrier. This should be in the
accepted-fields allowlist for the carrier patch endpoint. If re-enabling is not desired
(admin must delete and re-create), remove `enabled` from the patchable fields.

**OQ-6 (Pagination for `list_methods`)**: The spec returns all methods for a carrier in
a single response (no pagination). This is safe because the maximum method count per
carrier is bounded by the `method_code` enum (5 values). If the enum is extended later,
cursor pagination may be needed.
