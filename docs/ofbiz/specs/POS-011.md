# POS-011 — POS router (registered in app/main.py)

**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days
**Dependencies:** POS-004, POS-005, POS-006, POS-007, POS-008, POS-009, POS-010

---

## 1. Summary & Goal

POS-011 is the thin HTTP layer that surfaces the entire POS service stack
(POS-004 through POS-010) via a FastAPI router. It creates
`app/routers/pos.py`, registers it in `app/main.py`, and exposes 14 endpoints
under the `/ui/pos/` prefix, all gated on `S.pos_enabled`.

The router's contract is:

- **Additive and flag-gated.** Every handler immediately raises `HTTPException(404)`
  when `S.pos_enabled` is `False`. With the flag off, no existing
  shop/cart/orders/billing/inventory byte is modified and no new behaviour is
  observable.
- **No logic duplication.** The router contains only HTTP adaptation (request
  parsing, response serialisation, auth wiring, flag guard). All business logic
  remains in the service modules delivered by POS-004 through POS-010.
- **Standard auth model.** Register config endpoints require
  `require_admin_or_root_csrf` (mirroring `app/routers/returns_rma.py:61`).
  Cashier-action endpoints require `require_ui_session` plus an ownership check
  (cashier `user_sub` must match session's `cashier_sub`). CSRF applies to all
  non-GET cookie-auth requests (standard — enforced by `require_ui_session` and
  `require_admin_or_root_csrf`).
- **Deterministic idempotency forwarded.** `TenderRequestIn.idempotency_key` is
  passed through to the service layer unchanged; the router does not generate or
  re-derive it.

## 2. Context & Current State

### 2.1 Existing router registration pattern (`app/main.py`)

Routers are registered in `app/main.py` via lazy imports inside `create_app()`.
The `returns_rma_router` follows the exact pattern this ticket copies
(`app/main.py:312` top-level import, `app/main.py:878` `app.include_router`). POS follows
the same structure.

### 2.2 Flag-gate idiom

`app/services/returns_rma.py:67–73` (cited in POS-004 spec §2.2) establishes:

```python
def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="Returns/RMA is not enabled")
```

The POS router calls `pos_register._require_enabled()` (defined in POS-004) at
the top of every handler. This is identical to how `app/routers/returns_rma.py:33`
calls `rma._require_enabled()` (service: `app/services/returns_rma.py:71`).

### 2.3 Auth dependencies in use

| Dependency | File:line | Used for |
|---|---|---|
| `require_ui_session` | `app/services/sessions.py:330` | Cashier-action handlers; returns `{"user_sub", "session_id", "role", "ip", "tenant_id"}` dict |
| `require_admin_or_root_csrf` | `app/auth/policy.py:100` | Admin register-config handlers; calls `enforce_cookie_csrf` (`app/auth/policy.py:71`) then role check |
| `get_authenticated_user` | `app/auth/deps.py:199` | Paired with `require_ui_session` where both the session dict and typed `AuthenticatedUser` are needed |

The `role` value is `session["role"]` (a string matching `Role` enum values) or
`user.role` from `AuthenticatedUser`. For the cashier gate, `session["user_sub"]`

## 3. Data Model

POS-011 introduces no new DynamoDB rows. It reads and writes the `pos`
single-table (defined by POS-003) via `T.pos`. All rows and GSIs are owned by
POS-003 through POS-010 and are reproduced here for cross-reference.

### 3.1 Rows in `T.pos`

| Row kind | pos_pk | pos_sk | Owner ticket |
|---|---|---|---|
| Register config | `REGISTER#{register_id}` | `META` | POS-004 |
| Open-session sentinel | `OPEN_SENTINEL#REGISTER#{register_id}` | `OPEN` | POS-004 |
| Session / till | `SESSION#{session_id}` | `META` | POS-004 |
| Transaction draft | `TXN#{txn_id}` | `META` | POS-005/006 |
| Tender record | `SESSION#{session_id}` | `TENDER#{txn_id}#{tender_seq}` | POS-006/007 |

### 3.2 GSIs on the `pos` table

| GSI name | Partition key | Sort key | attr_type | Used by |
|---|---|---|---|---|
| `GSI_REGISTER_OPEN` | `register_id` | `opened_at` | N | POS-004 |
| `GSI_CASHIER` | `cashier_sub` | `opened_at` | N | POS-004/011 |
| `GSI_SESSION_TXN` | `session_id` | `created_at` | N | POS-005/010 |

Both `opened_at` and `created_at` must appear in
`attr_types={"opened_at": "N", "created_at": "N"}` in `scripts/local-ddb-init.py`
(CLAUDE.md DynamoDB gotcha for numeric GSI sort keys). This is already specified
in POS-003 and POS-004 spec §3.4.

### 3.3 Other tables touched (via delegated services, not directly by this router)

| Table | Handle | Purpose | Service called |
|---|---|---|---|
| `shopping_cart` | `T.shopping_cart` | Cart binding + settlement | POS-005, POS-006 via `purchase_cart` |
| `shopping_catalog` | `T.catalog` | SKU/barcode resolution | POS-005, SKU lookup in router |
| `billing` | `T.billing` | Ledger entries, wallet delta | POS-006/007 via `new_ledger_entry`/`apply_wallet_delta` |

### 4.5 Ownership helper

A shared internal helper `_require_cashier_owns_session(cashier_sub, session_id)` is
called from every handler that takes a `session_id` path parameter:

```python
def _require_cashier_owns_session(cashier_sub: str, session_id: str) -> Dict[str, Any]:
    """Resolve session and assert caller is its cashier. Returns session dict."""
    rec = pos_register.get_session(session_id)
    if rec is None:
        raise HTTPException(404, "Session not found")
    if rec["cashier_sub"] != cashier_sub:
        raise HTTPException(403, "Not your session")
    return rec
```

For `txn`-scoped endpoints (`/txns/{txn_id}/*`) a companion helper
`_require_cashier_owns_txn(cashier_sub, txn_id)` resolves the txn record, reads
its `session_id`, and delegates to `_require_cashier_owns_session`.

Admins (`role in {ADMIN, ROOT}`) bypass the ownership check and may operate on
any session (useful for forced-close / audit).

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off short-circuit

Every handler's first statement:

```python
pos_register._require_enabled()   # raises HTTPException(404) if S.pos_enabled is False
```

This is identical to `rma._require_enabled()` in `app/routers/returns_rma.py:33`
(service impl at `app/services/returns_rma.py:71`).
No other POS code path is reached when the flag is off.

### 5.2 POST /ui/pos/registers (create register)

- Requires `role in {ADMIN, ROOT}`. CSRF enforced by `require_admin_or_root_csrf`.
- Delegates to `pos_register.create_register(body.label, body.location_id, body.default_currency, creator_sub=user.sub)`.
- Returns 201 `RegisterConfig`. Duplicate `label+location_id` returns 409 (from
  the service-layer conditional put).

### 5.3 GET /ui/pos/registers

- Requires `role in {ADMIN, ROOT}`.
- Delegates to `pos_register.list_registers()`.
- Returns `List[RegisterConfig]`. Paginator is not required for MVP (register
  count is bounded by store count).

### 5.4 POST /ui/pos/sessions/open

- Any authenticated user can open a session (the register config determines which
  physical terminals exist; the cashier sub is taken from `session["user_sub"]`).
- Delegates to `pos_register.open_session(cashier_sub, body.register_id, body.opening_float_cents, idempotency_key=body.idempotency_key)`.
- 409 if a session is already open for that register (sentinel conditional-put
  failure, from POS-004).
- Returns `RegisterSessionOut`.

### 5.5 POST /ui/pos/sessions/{session_id}/close

- Ownership: `cashier_sub == session["user_sub"]` (or admin bypass).
- Delegates to `pos_register.close_session(session_id, body.counted_cash_cents)`.
- 409 if already closed (from POS-004).
- Returns updated `RegisterSessionOut` with `over_short_cents` populated.

### 5.6 GET /ui/pos/sessions/{session_id}/report

- Ownership enforced.
- Query param `kind` defaults to `"x"`. Only `"x"` is valid for an `open`
  session; `"z"` requires status `"closed"` (service raises 409 otherwise, from
  POS-010).
- Returns `SessionReportOut` with by-tender totals, refunds, voids, and
  over/short fields.

### 5.7 POST /ui/pos/sessions/{session_id}/lines (add/scan)

- Ownership enforced. Session must be `"open"` (service raises 409 otherwise).
- If `body.sku` is supplied, the router resolves the catalog item via the
  `ByItemId` GSI on `T.catalog` (per POS-005 §2.2) before calling the service.
  If the SKU does not match any catalog item → `HTTPException(404, "Unknown SKU")`.
- If `category_id + item_id` are supplied, they are forwarded directly.
- Delegates to `pos_cart.add_line_item(session_id, sku_or_ids, body.quantity)`.
- Returns `PosTransactionOut` with updated `subtotal_cents`.

### 5.8 DELETE /ui/pos/sessions/{session_id}/lines/{sku}

- Ownership enforced.
- Delegates to `pos_cart.remove_line_item(session_id, sku)`.
- Returns updated `PosTransactionOut`.

### 5.9 POST /ui/pos/sessions/{session_id}/tender

- Ownership enforced. Session must be `"open"`.
- Body `TenderRequestIn.idempotency_key` forwarded unchanged.
- Delegates to `pos_tender.tender(session_id, tenders=[t.model_dump() for t in body.tenders], idempotency_key=body.idempotency_key)`.
- Under-sum tender (tenders total < txn total) → the service returns the txn
  still in `open_draft` status; the router returns 200 with the draft so the
  cashier can add the remaining split.
- Full settlement → service calls `purchase_cart`, creates the order, writes
  ledger entries, updates session float counters; router returns 200
  `PosTransactionOut` with `status="tendered"` and `order_id` populated.
- Replay of a completed idempotency_key → service returns the original
  `PosTransactionOut` unchanged; router returns 200 (idempotent).

### 5.10 POST /ui/pos/txns/{txn_id}/void

- Ownership enforced via `_require_cashier_owns_txn`.
- Pre-settlement only; settled txn → 409 "Must refund a settled transaction".
- Delegates to `pos_tender.void_transaction(txn_id)`.
- Returns `PosTransactionOut` with `status="voided"`.

### 5.11 POST /ui/pos/txns/{txn_id}/refund

- Ownership enforced via `_require_cashier_owns_txn`.
- Must be settled (`status="tendered"`); pre-settlement → 409.
- Delegates to `pos_tender.refund_transaction(txn_id, body.line_refs, body.reason)`.
- Returns `PosTransactionOut` with `status="refunded"` and updated tenders list
  (negative refund tender row appended).

### 5.12 GET /ui/pos/txns/{txn_id}/receipt

- Ownership enforced via `_require_cashier_owns_txn`.
- Delegates to `pos_receipt.get_or_create_receipt(txn_id)` (POS-009).
- Returns `Response(content=pdf_bytes, media_type="application/pdf")` — not
  `PlainTextResponse` (CLAUDE.md GAP-0209 binary-safety requirement, also cited
  in POS-009 spec §1).
- Adds `Content-Disposition: attachment; filename="receipt_{txn_id}.pdf"` header.
- Pre-settlement txn (no `order_id`) → 409 "Transaction not yet settled".

### 5.13 404 vs 403 for foreign sessions/txns

The ownership helper returns 404 (not 403) when the session_id itself is not
found, and 403 only when the session exists but is owned by a different cashier.
This prevents enumeration of valid session IDs by non-owning users while still
giving the cashier a usable error on a genuine ownership conflict.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

The router contains no `if S.dev_mode:` branch. All service calls go through the
same code path in dev and prod. The `T.pos` DDB handle is resolved at module load
via `_safe_table(S.pos_table_name)` regardless of environment. Moto intercepts the
boto3 calls in dev; real DynamoDB responds in prod. No divergence.

### 7.2 Idempotency

`TenderRequestIn.idempotency_key` (optional str) is forwarded to
`pos_tender.tender(...)`. The service derives a deterministic `txn_id` from it via
`hashlib.sha256(idempotency_key.encode()).hexdigest()[:32]` (same scheme as
`commerce_order_service.py:67`). A replay with the same key hits the existing
`TXN#` row (via DynamoDB conditional-put on `attribute_not_exists(pos_pk)`) and
returns the previously recorded `PosTransactionOut` without repeating the
`purchase_cart` or ledger write.

For `open_session`, the same mechanism is used on `OpenSessionIn.idempotency_key`
(POS-004 spec §2.4).

### 7.3 CSRF

All non-GET cookie-auth requests are CSRF-validated:

- Admin endpoints via `require_admin_or_root_csrf` which calls `enforce_cookie_csrf`
  (`app/auth/policy.py:71`) before the role check.
- Cashier endpoints via `require_ui_session` (`app/services/sessions.py:330`),
  which enforces the `x-csrf-token` header for non-GET methods when the
  `ui_session` cookie is present.
- Bearer-token callers (API-key or programmatic) are exempt (no session cookie).

### 7.4 Ownership enforcement and privilege escalation

The `_require_cashier_owns_session` helper compares `session["user_sub"]` against
the session row's `cashier_sub`. Admin/root callers bypass this check (they can
inspect or close any session). A cashier cannot escalate to a different cashier's
session.

### 7.5 Money-out via existing paths only

The router never writes to `T.billing` directly. All refund money-out goes through
`pos_tender.refund_transaction` → `billing.refund_payment`
(`app/routers/billing.py:1287`) or `billing_shared.settle_or_reverse_ledger`
(`app/services/billing_shared.py:262`). No new refund mechanism is introduced
(POS-008 constraint, also the NON-NEGOTIABLE constraint stated in the master
ticket file).

## 8. Backward Compatibility & Migration

### 8.1 Zero impact when flag is off

With `POS_ENABLED` absent or `false`:

- `app/main.py` still imports and registers `pos_router` at startup; registering
  an APIRouter with no reachable handlers is harmless.
- Every `/ui/pos/*` request receives `{"detail": "POS is not enabled"}` with
  status 404.
- No existing `/ui/catalog`, `/ui/shoppingcart`, `/ui/billing`, or `/ui/orders`
  route changes.

### 8.2 Enabling in a running system

Setting `POS_ENABLED=true` requires:

1. `just restart` (or equivalent) so `scripts/local-ddb-init.py` creates the
   `pos` table with its three GSIs and `attr_types`.
2. At least one `POST /ui/pos/registers` call to seed a register config.
3. No data migration of existing tables is required.

In production the `pos` table can be pre-created via `UpdateTable` without
touching any existing table; the router flag can then be flipped independently.

### 8.3 POS-012+ (frontend) dependency

POS-011 does not depend on any frontend ticket. POS-012 (TypeScript types +
endpoint wrappers) depends on POS-011's endpoint shapes being stable. The
response models are defined in `app/models.py` by POS-002 and do not change
shape in this ticket.

## 10. Open Questions / Assumptions

1. **Assumption: `pos_register._require_enabled()` is the shared flag guard.**
   All upstream specs (POS-004 through POS-010) place `_require_enabled()` in
   `app/services/pos_register.py`. This router imports and calls it. If a later
   implementation moves it to a separate `pos_common.py`, the import changes but
   the call-site pattern is unchanged.

2. **Assumption: POS cashier == any `require_ui_session` user + ownership.**
   The ticket states "cashier session subject for tendering". There is no
   dedicated cashier `Role` value in `app/auth/roles.py:8` (only `ROOT`, `ADMIN`,
   `USER`). Cashier authority is therefore modelled as: any authenticated user who
   owns the session (i.e. `session["user_sub"] == session_row["cashier_sub"]`).
   If a dedicated cashier role or admin scope is required, the spec should be
   revisited before implementation.

3. **Assumption: `pos_tender.tender(...)` is the unified entry point.**
   POS-006 and POS-007 specs describe `tender_cash` and `tender_card`/`tender_wallet`
   separately. POS-011 assumes a single consolidated `tender(...)` function in
   `pos_tender.py` that dispatches by `kind` internally. If POS-006/007
   implementations keep separate entry points, each handler in the router calls
   the appropriate one with a short dispatch block.

4. **Assumption: SKU barcode lookup via ByItemId GSI on `T.catalog`.**
   POS-005 spec §2.2 cites `app/routers/catalog.py:702` `_find_item_by_id`. This
   spec assumes the router imports that helper or replicates the GSI query inline
   to resolve bare SKUs. If the catalog service exports `find_item_by_sku(sku)`,
   that is preferred.

5. **Assumption: `pos_receipt.get_or_create_receipt(txn_id)` returns `bytes`.**
   POS-009 spec §1 states the receipt PDF is stored via `upload_billing_receipt`
   and a re-print retrieves the stored bytes. The receipt endpoint here calls
   `get_or_create_receipt` and expects a dict `{"pdf_bytes": bytes, ...}` (or
   similar). If the POS-009 implementation returns a URL rather than raw bytes,
   the receipt handler must issue a secondary fetch.

6. **Open: admin bypass scope.** Should admin access to foreign sessions be
   logged as an audit event? CLAUDE.md POS-004 spec §2.3 establishes the
   `_audit` pattern. Recommend: yes, emit `pos_admin_session_access` via `_audit`
   whenever an ADMIN/ROOT bypasses the cashier ownership check.

7. **Open: `pos_router` placement in `app/main.py`.** The spec places the
   registration adjacent to `returns_rma_router` at line `:878`. If other POS
   routers (e.g. a separate `pos_tender_router` from POS-006 if that spec ships
   its own router) are already registered, they should be consolidated into the
   single `pos_router` in POS-011 to avoid prefix conflicts.
