**Type:** Feature | **Priority:** P1 | **Estimate:** 3 days

**Depends on:** PUR-006 (PO entity & creation), PUR-007 (approval state machine), PUR-008 (receiving → inventory)

## 1. Summary & Goal

PUR-010 is the HTTP presentation layer for the purchase-order lifecycle.  It wires three existing service modules — `purchase_orders.py` (PUR-006), and the transition/receiving functions from PUR-007/PUR-008 — to a set of admin-gated REST endpoints appended to `app/routers/purchasing.py` (which already holds the supplier/supplier-product endpoints from PUR-005). It also adds the eight Pydantic models that serialize PO data across the wire.

The deliverables are:

1. **Eight Pydantic models** appended to `app/models.py` immediately after the supplier models from PUR-005, in the OFBiz ERP block: `PurchaseOrderLineIn`, `PurchaseOrderLineOut`, `PurchaseOrderCreateIn`, `PurchaseOrderOut`, `PurchaseOrderListOut`, `PoTransitionIn`, `PoReceiveLineIn`, `PoReceiveIn`, and `PoReceiptOut`.
2. **Eight router endpoints** on `app/routers/purchasing.py` covering the full PO lifecycle: create, get, list, submit, approve, reject, cancel, and receive.
3. With `purchasing_scm_enabled=false` (the master switch default) every endpoint returns 404 with no side effects; the flag's off state is enforced by delegating to the service layer's `_require_enabled()`, exactly as the supplier endpoints do.

No new DynamoDB tables, settings keys, or table handles are added; all infrastructure is supplied by PUR-002 (tables/settings/handles), PUR-006 (service functions), PUR-007 (transition functions), and PUR-008 (receiving function).

### 2.4 Declaration-order FastAPI constraint

## 3. Data Model

PUR-010 introduces **no new DynamoDB tables or settings keys**. All table definitions and handles are established by PUR-002. This section documents the wire shapes only.

### 3.1 `purchase_orders` table (read by this ticket, written by PUR-006/007/008)

**PK** = `po_id` (S), **SK** = `sk` (S)

| SK value | Row type | Key attrs consumed |
|---|---|---|
| `"META"` | Header | `status`, `supplier_id`, `created_at` (GSI sort key) |
| `"LINE#{n}"` (1-based) | Line | `sku`, `quantity_ordered`, `quantity_received`, `unit_cost_cents`, `line_total_cents` |

| GSI | Partition key | Sort key | `attr_types` |
|---|---|---|---|
| `GSI_SUPPLIER` | `supplier_id` (S) | `created_at` (N) | `{"created_at": "N"}` |
| `GSI_STATUS` | `status` (S) | `created_at` (N) | `{"created_at": "N"}` |

Header fields surfaced to the API: `po_id`, `supplier_id`, `status`, `currency`, `subtotal_cents`, `expected_delivery_date`, `created_by`, `approved_by`, `approved_at`, `rejected_by`, `rejected_reason`, `cancelled_by`, `cancelled_at`, `created_at`, `updated_at`, `correlation_id`, `line_count`.

Line fields surfaced: `line_no`, `sku`, `quantity_ordered`, `quantity_received`, `unit_cost_cents`, `line_total_cents`, `currency`, `supplier_sku`.

### 3.2 `po_receipts` table (read by this ticket, written by PUR-008)


## 5. Detailed Behavior & Edge Cases

### 5.1 PO lifecycle legal transitions (PUR-007 enforcement)

The state machine is defined in `PURCHASING_SCM_TICKETS.md:15` and documented in `docs/ofbiz/specs/PUR-007.md:34–44`:

```
draft       → submitted   (submit, session auth, creator only)
submitted   → approved    (approve, admin only)
submitted   → rejected    (reject, admin only)
submitted   → cancelled   (cancel, admin only)
approved    → ordered     (future; not exposed in PUR-010)
approved    → rejected    (reject, admin only)
approved    → cancelled   (cancel, admin only)
approved / ordered / partially_received → partially_received / received (via receive)
received    → closed      (auto, triggered by receive_po when fully received)
```

`transition_po` returns a 409 on any unlisted transition. Replaying the same transition (e.g. approving an already-approved PO) is a no-op returning the current state (idempotent, not a 409 storm) — per `docs/ofbiz/specs/PUR-007.md:66`.

### 5.2 Decimal coercion for DynamoDB attributes

DynamoDB returns numeric fields as Python `Decimal` via boto3. The `_po_out` helper must coerce all numeric fields (`subtotal_cents`, `created_at`, `updated_at`, `approved_at`, `cancelled_at`, and all line numeric fields) to `int` before constructing the Pydantic model, or Pydantic will surface a validation error. The pattern is `int(item.get("subtotal_cents") or 0)`, mirroring `_to_int` in `app/services/returns_rma.py:76–82`.

### 5.3 `_po_out` helper

A module-level helper in the router converts the service dict to the response model:

```python
def _to_int(v: Any, default: int = 0) -> int:
    try:
        return default if v is None else int(v)
    except (TypeError, ValueError):
        return default

def _line_out(ln: Dict[str, Any]) -> PurchaseOrderLineOut:
    return PurchaseOrderLineOut(
        line_no=_to_int(ln.get("line_no")),
        sku=ln.get("sku", ""),
        quantity_ordered=_to_int(ln.get("quantity_ordered")),
        quantity_received=_to_int(ln.get("quantity_received")),
        unit_cost_cents=_to_int(ln.get("unit_cost_cents")),
        line_total_cents=_to_int(ln.get("line_total_cents")),
        currency=ln.get("currency", "USD"),
        supplier_sku=ln.get("supplier_sku", ""),
    )

def _po_out(rec: Dict[str, Any]) -> PurchaseOrderOut:
    header = rec.get("header", rec)
    lines = [_line_out(ln) for ln in rec.get("lines", [])]
    return PurchaseOrderOut(
        po_id=header.get("po_id", ""),
        supplier_id=header.get("supplier_id", ""),
        status=header.get("status", "draft"),
        currency=header.get("currency", "USD"),
        subtotal_cents=_to_int(header.get("subtotal_cents")),
        expected_delivery_date=header.get("expected_delivery_date"),
        created_by=header.get("created_by", ""),
        approved_by=header.get("approved_by"),
        approved_at=_to_int(header.get("approved_at")) or None,
        rejected_by=header.get("rejected_by"),
        rejected_reason=header.get("rejected_reason"),
        cancelled_by=header.get("cancelled_by"),
        cancelled_at=_to_int(header.get("cancelled_at")) or None,
        created_at=_to_int(header.get("created_at")),
        updated_at=_to_int(header.get("updated_at")),
        correlation_id=header.get("correlation_id"),
        line_count=_to_int(header.get("line_count")),
        lines=lines,
    )
```

Both `get_purchase_order` and `transition_po` return the same `{"header": {...}, "lines": [...]}` shape: `transition_po` calls `get_purchase_order(po_id)` internally as its final step (`docs/ofbiz/specs/PUR-007.md:291`). `_po_out` reads the `"header"` sub-key in all cases; the `rec.get("header", rec)` fallback in the helper handles the edge case gracefully but in practice the dict always has a `"header"` key.

~~**Assumption A1**~~ — **RESOLVED**: `transition_po` returns the full `{"header", "lines"}` dict (confirmed by PUR-007 step 13). The `approve`, `reject`, `cancel`, and `submit` endpoints do **not** need a second `get_purchase_order` call — `_po_out(rec)` on the return value of `transition_po` is sufficient and correct.

### 5.4 `404` vs `409` for missing PO on transition

If the caller supplies an unknown `po_id`, `transition_po` will fail to fetch the header and the service raises `HTTPException(404)`. The router does not need to replicate a 404 check — the service is the authority.

### 5.5 Flag-off behavior

Every endpoint calls into a service function whose first statement is `_require_enabled()`. With `PURCHASING_SCM_ENABLED=false`, `_require_enabled()` raises `HTTPException(404, "Purchasing/SCM is not enabled")`. No DynamoDB access occurs. The response body is `{"detail": "Purchasing/SCM is not enabled"}`. Existing shop/cart/orders/billing code is byte-for-byte unchanged.

### 5.6 Empty `POST /submit` body

`submit`, `approve`, `cancel`, and `reject` endpoints accept no request body (or an optional `PoTransitionIn` for cancel/reject). FastAPI handles an absent body correctly when the parameter is typed `Optional[PoTransitionIn] = None`. The `submit` endpoint takes no body at all.

### 5.7 Concurrent approve race

Two admins approving the same `submitted` PO concurrently: the first wins the conditional `update_item`; the second's `ConditionalCheckFailedException` is caught by `transition_po` (`docs/ofbiz/specs/PUR-007.md:287–289`), which re-fetches the header, finds it already `approved`, and since `approved == approved` (same target) the replay guard at step 4 returns the current full record. The caller receives a 200 with the already-approved PO — not a 409. This matches the idempotency behavior documented in `docs/ofbiz/specs/PUR-007.md:257–258`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

The router delegates entirely to service functions (`po_svc.*`, `receiving_svc.*`) that contain no `if S.dev_mode` branches — all DDB access goes through `T.purchase_orders` / `T.po_receipts` whether backed by DynamoDB Local (dev) or real DynamoDB (prod). The only environment difference is which DynamoDB endpoint boto3 targets, controlled by `DDB_ENDPOINT_URL` in `.env.local`.

### 7.2 Idempotency

- **Create**: deterministic `po_id = sha256(correlation_id)[:32]` (PUR-006). A duplicate `POST /purchase-orders` with the same `correlation_id` returns the existing PO rather than creating a second one.
- **Transitions**: `transition_po`'s conditional `update_item` is idempotent under replay — re-applying the same transition returns the current state without a 409.
- **Receive**: `receipt_id = sha256(receipt_correlation_id)[:32]` (PUR-008). Replaying `POST /{po_id}/receive` with the same `receipt_correlation_id` finds the existing receipt row (via `GSI_RECEIPT` or the conditional `put_item`) and does not double-increment inventory.

### 7.3 Security

- **CSRF**: All non-GET endpoints use `require_admin_or_root_csrf` which calls `enforce_cookie_csrf` (defined at `app/auth/policy.py:71–97`) before the role check. Bearer-authenticated API callers skip CSRF (no session cookie present).
- **Ownership on submit**: `POST /{po_id}/submit` checks `header["created_by"] == session["user_sub"]`; mismatched → 403. This prevents an authenticated non-admin from submitting another user's draft.
- **Role isolation**: approve and reject are strictly `ADMIN | ROOT`. A USER-role session correctly receives 403 even if it somehow has the PO `po_id`.
- **Input limits**: `lines` is capped at 500 entries (`max_length=500`) and `unit_cost_cents` is capped at `1_000_000_000` (£10M/unit, prevents int overflow in subtotal).
- **No customer-visible purchasing data**: There are no user-facing (non-admin) list or get endpoints for POs. Purchasing data is staff-only.

## 10. Open Questions / Assumptions

**A1** — ~~OPEN~~ **RESOLVED**: `transition_po` returns the full `{"header": {...}, "lines": [...]}` dict — confirmed by PUR-007 step 13 (`docs/ofbiz/specs/PUR-007.md:291`). Router handlers call `_po_out(rec)` directly on the `transition_po` return; no second `get_purchase_order` fetch is needed.

**A2** — `submit` ownership granularity: The spec requires only the PO's creator (`created_by`) to submit. An alternative is to allow any admin to submit any PO. The ticket says submit is not admin-gated (`require_ui_session`), implying creator-only. **Confirm the business rule with the product owner.**

**A3** — `ordered` status reachability: The state machine includes `approved → ordered` (e.g. when a physical PO document is sent to the supplier), but PUR-010 does not expose a `/mark-ordered` endpoint. The `ordered` status can be set via a future ticket (or included now as `POST /{po_id}/mark-ordered` with `require_admin_or_root_csrf`). The current design leaves `ordered` reachable only internally (or via PUR-011 reorder-suggestion auto-PO). **Confirm whether a `/mark-ordered` endpoint is in scope for PUR-010 or deferred.**

**A4** — `PoReceiptOut.lines` shape: The spec uses `List[Dict[str, Any]]` for `PoReceiptOut.lines` to avoid a deep nesting problem (the receipt line shape mirrors `PoReceiveLineIn` but adds a `sku` field from the PO line). A dedicated `PoReceiptLineOut` model could replace this. **Decide if a named model is needed or if `Dict` is acceptable for receipts.**

**A5** — List POs without filter: The spec gates `list_purchase_orders` to require at least one of `supplier_id` or `status`. This matches the scan-prevention principle for GSI queries. However, a root/admin "show all recent POs" view would need a different query pattern (e.g., a `GSI_CREATED_AT` GSI not in scope for PUR-002). **Confirm the unbounded-list constraint with product.**

**A6** — `currency` validation: `PurchaseOrderCreateIn.currency` accepts any 3–10-char string. The service does not currently validate against a currency allowlist. If invalid currencies are a concern, add an `@field_validator` checking against a known set (or delegate to the supplier-product currency field). **Confirm if hard validation is needed.**
