# ECM-004 — Variant-aware catalog read service

**Type:** Feature | **Priority:** P0 | **Estimate:** 4 days
**Dependencies:** ECM-003 (Pydantic models), PRD-007 (virtual↔variant service)

---

## 1. Summary & Goal

ECM-004 adds `enrich_catalog_item(item, *, viewer)` to `app/services/store_integration.py` (the module scaffolded by ECM-002). When `STORE_VARIANT_SELECTION_ENABLED` is on, the function queries the PRD-007 virtual↔variant service (`app/services/product_variants.py`) to attach a `variants: List[StorefrontVariantOut]` list and associated option-selection metadata to a catalog item DynamoDB dict, then returns a fully-populated `CatalogItemOut`.

When the flag is off, the item is a virtual product with no variants stored, or the upstream PRD-007 call fails, the function returns the legacy `CatalogItemOut` unchanged — the exact same object that `_catalog_item_out(item)` (`app/routers/catalog.py:107`) currently produces today.

Crucially, ECM-004 is a **pure read-topology service function**. It resolves each variant's inventory SKU mapping (PRD-001 variant→SKU) but does **not** query live stock counts — that is ECM-005's responsibility. The `availability` field on each `StorefrontVariantOut` is always `None` from this function; ECM-005 populates it in a subsequent pass.

## 2. Context & Current State

### 2.1 The existing catalog read path

`app/routers/catalog.py:107–127` defines `_catalog_item_out(item: dict) -> CatalogItemOut`. It reads a single raw DynamoDB dict from `T.catalog` and constructs the scalar `CatalogItemOut` shape (`app/models.py:672–688`). The `list_items` endpoint at `catalog.py:394–418` calls it for every item in a category page. The `search_items` endpoint at `catalog.py:465–498` calls it for every scan match. No variant dimension exists anywhere in this path today.

`CatalogItemOut` (`app/models.py:672–688`) is a **16-field** scalar model: `category_id`, `item_id`, `name`, `description`, `price_cents`, `currency`, `image_urls`, `attributes`, `creator_id`, `created_at`, `updated_at`, `stock_count`, `stock_status`, `low_stock_threshold`, `stock_updated_at`, `position`. The ECM-003 spec adds two optional fields at the end of this class: `variants: Optional[List[StorefrontVariantOut]] = None` and `availability: Optional[StorefrontAvailabilityOut] = None`.

### 2.2 The store_integration.py scaffold (ECM-002)

ECM-002 introduces `app/services/store_integration.py` (does not yet exist — confirmed by `ls app/services/` finding no such file). It provides:

- `_integration_enabled(sub_flag)` — AND-combines `S.store_integration_enabled` with the named per-surface sub-flag; uses `getattr(S, attr, False)` for forward-compatibility (`docs/ofbiz/specs/ECM-002.md:154`).
- `_safe_upstream(call, default)` — swallows all exceptions from `call()`, logs at WARNING with `exc_info=True`, and returns `default` (`docs/ofbiz/specs/ECM-002.md:165`).

ECM-004 extends this module with `enrich_catalog_item` and the async variant `_safe_upstream_async`.

### 2.3 The flags that guard this ticket

`S.store_integration_enabled` + `S.store_variant_selection_enabled` together gate `enrich_catalog_item`. Both default `false` and are inserted into `app/core/settings.py` after `returns_table_name` (`settings.py:847`) by ECM-002. The ECM-002 spec confirms neither flag exists in the codebase today (`docs/ofbiz/specs/ECM-002.md:73` — "store_integration.py does not exist").

### 2.4 The PRD-007 upstream: product_variants.py

PRD-007 (`CATALOG_DEPTH_TICKETS.md:130–148`) will introduce `app/services/product_variants.py` with the following semantics:

- A **virtual product** (parent) has rows on `T.product_depth` keyed `PK=ITEM#{parent_item_id}` / `SK=VAR#{variant_id}` (`docs/ofbiz/specs/PRD-007.md:103–104`). Listing those children is a single GSI query on the `ByVirtualParent` GSI (`PRD-007.md:123–132`, `GSI_VIRT_PK=VIRTUAL#{parent_item_id}`). — **CORRECTED** from `VARIANT#{parent_id}#{variant_id}` and `GSI_VARIANT_PARENT`.
- A **standalone/non-virtual product** has zero such rows. Querying it returns an empty list immediately.
- Each variant row carries: `variant_id` (deterministic `sha256(parent_item_id + canonical_fv_tuple)[:16]`), `sku` (inventory key), `feature_values` (Dict[str, str] feature-category-id → feature-value-id; `PRD-007.md:109`), `price_delta_cents` (signed integer), and `created_at` (integer Unix seconds, used as the numeric `GSI_VIRT_SK` sort key; `PRD-007.md:113,115`). — **CORRECTED**: field is `feature_values` not `option_selections`; GSI sort key is `created_at` not `sequence_num`.
- Effective price for a variant = `parent.price_cents + variant.price_delta_cents`.
- The public function ECM-004 calls is `list_variants(parent_item_id: str, limit: int = 100, start_key: Optional[Dict] = None) -> Tuple[List[Dict[str, Any]], Optional[Dict[str, Any]]]` (`docs/ofbiz/specs/PRD-007.md:255–266`). — **CORRECTED**: returns a pagination `Tuple`, not a plain `List`. ECM-004's `_fetch_variants` must unpack the first element of the tuple.

**The `T.product_depth` table** (`scripts/local-ddb-init.py:278–285`) exists today as `catalog_products` with a single GSI `GSI_PRODUCT_TYPE` (partition key `GSI_PRODUCT_TYPE_PK`, sort key `GSI_PRODUCT_TYPE_SK`). PRD-002 adds additional GSIs to this table — or adds a dedicated `product_depth` table. ECM-004 treats the upstream GSI as an opaque detail owned by PRD-007 and calls only `list_variants`; it does not access `T.product_depth` directly.

### 2.5 The CatalogItemOut.product_type field (PRD-003)

PRD-003 (`CATALOG_DEPTH_TICKETS.md:48–64`) extends `CatalogItemOut` with an optional `product_type` field (values: `"virtual"`, `"variant"`, `"standalone"`, `"bundle"`, `"kit"`, `"digital"`), default `None`. ECM-004 uses `item.get("product_type")` from the raw DynamoDB dict to decide whether to call `list_variants` at all: only items with `product_type == "virtual"` can have variants. Items without a `product_type` field (all pre-depth legacy items) behave as standalone and return unchanged.

### 2.6 The existing catalog item DynamoDB row layout

DynamoDB rows in `T.catalog` for **catalog items** use `PK = CAT#{category_id}` and `SK = ITEM#{item_id}` — verified at `app/routers/catalog.py:362–363` (`create_item` puts with `cat_pk(category_id)` / `item_sk(item_id)`) and confirmed by `_query_page(pk=cat_pk(category_id), sk_begins="ITEM#", ...)` at `catalog.py:407`. The helper functions are `cat_pk` at `catalog.py:55–56` (returns `CAT#{category_id}`) and `item_sk` at `catalog.py:63–64` (returns `ITEM#{item_id}`). — **CORRECTED**: the original claim that both PK and SK equal `ITEM#{item_id}` was wrong. The `entity` discriminator field equals `"item"` for items vs `"category"` for categories. The `item_id` field is stored as a top-level attribute (used by the `ByItemId` GSI at `scripts/local-ddb-init.py:123`). The PRD-003 change adds `product_type` as a top-level attribute on these rows; ECM-004 reads it from the raw dict that was already fetched by `list_items` or `search_items`.

### 2.7 No DynamoDB writes in this ticket

ECM-004 is a pure read service. It reads from `T.product_depth` (via `product_variants.list_variants`) and from the raw catalog item dict already fetched upstream. It writes nothing to DynamoDB, issues no ledger entries, and does not touch billing.

## 3. Data Model

ECM-004 introduces **no new DynamoDB tables and no schema changes**. The data it reads comes from two existing/planned sources:

### 3.1 Source 1 — T.catalog (existing)

The raw catalog item dict fetched by `_query_page` (`catalog.py:182–196`) contains all scalar fields needed to build the base `CatalogItemOut`. ECM-004 passes this same dict through unchanged when the variant path is not taken.

Key fields read by ECM-004:

| Field | Source | Purpose |
|---|---|---|
| `product_type` | PRD-003 addition to `T.catalog` rows | Gate: only `"virtual"` triggers variant lookup |
| `price_cents` | existing | Base price used to compute effective variant prices |
| `item_id` | existing | Key passed to `list_variants(parent_item_id)` |

### 3.2 Source 2 — T.product_depth (PRD-002, read-only)

ECM-004 reads variant rows through `product_variants.list_variants(parent_item_id)`. `list_variants` returns a pagination tuple `(rows, last_evaluated_key)` (`docs/ofbiz/specs/PRD-007.md:255–266`); `_fetch_variants` unpacks `rows[0]` (the list). For ECM-004's variant enrichment all variants are fetched in a single call (the default `limit=100` is sufficient for typical product variant counts); pagination cursor handling beyond 100 variants is deferred to a follow-up. Each variant dict in the returned list contains:

| Field | DynamoDB attr | Notes |
|---|---|---|
| `variant_id` | `variant_id` | Opaque id = `sha256(parent_item_id + canonical_fv_tuple)[:16]` (`PRD-007.md:106`) |
| `sku` | `sku` | Inventory key; the SKU ECM-005 will query for live stock |
| `feature_values` | `feature_values` | Dict[str, str] — feature-category-id → feature-value-id (`PRD-007.md:109`) |
| `price_delta_cents` | `price_delta_cents` | Signed int; may be negative (sale option) |
| `created_at` | `created_at` | Integer Unix seconds; doubles as `GSI_VIRT_SK` numeric sort key (`PRD-007.md:113,115`) |

— **CORRECTED**: `option_selections` does not exist on PRD-007 variant rows; the field is `feature_values`. `sequence_num` does not exist; the GSI sort key is `created_at`. Per the CLAUDE.md gotcha, PRD-002 must declare `GSI_VIRT_SK` with `attr_types={"GSI_VIRT_SK": "N"}` in `scripts/local-ddb-init.py`. ECM-004 trusts the list returned by `list_variants` to already be ordered by `created_at` ascending (the GSI query uses `ScanIndexForward=True`, `PRD-007.md:130`).

### 3.3 Output shape (from ECM-003)

`StorefrontVariantOut` (defined in ECM-003 / `app/models.py`):

```
variant_id:         str
sku:                str
option_selections:  Dict[str, str]
price_cents:        int        — parent.price_cents + variant.price_delta_cents; ge=0
availability:       Optional[StorefrontAvailabilityOut] = None   — always None from ECM-004
```

The `availability` field is explicitly `None` from this function. ECM-005 (`availability_for_skus`) populates it in a second pass inside ECM-006 when `STORE_SHOW_LIVE_AVAILABILITY` is also on.

## 4. API / Service Design

### 4.1 Function signature

ECM-004 adds one public function to `app/services/store_integration.py`:

```python
def enrich_catalog_item(
    item: dict,
    *,
    viewer: dict,
) -> CatalogItemOut:
    """Return a CatalogItemOut enriched with variant topology when STORE_VARIANT_SELECTION_ENABLED is on.

    - item:   raw DynamoDB dict already fetched from T.catalog (same dict _catalog_item_out receives).
    - viewer: the session dict from require_ui_session (carries user_sub, role).

    When the flag is off OR the item is not virtual OR the upstream call fails,
    returns the same scalar CatalogItemOut that _catalog_item_out(item) would produce.
    Guaranteed to never raise: all upstream errors degrade to the legacy scalar path.
    """
```

The function is **synchronous** because `list_variants` (PRD-007) is a synchronous DynamoDB call. If PRD-007 evolves to an async call, the async variant `enrich_catalog_item_async` is added at that point (ECM-006 decides which form to call from the router).

### 4.2 Internal helper: `_build_storefront_variant`

A module-private helper constructs a single `StorefrontVariantOut` from a PRD-007 variant dict and the parent's base price:

```python
def _build_storefront_variant(
    variant_dict: dict,
    parent_price_cents: int,
) -> StorefrontVariantOut:
    effective_price = max(0, parent_price_cents + int(variant_dict.get("price_delta_cents", 0)))
    return StorefrontVariantOut(
        variant_id=variant_dict["variant_id"],
        sku=variant_dict["sku"],
        option_selections=dict(variant_dict.get("feature_values") or {}),  # PRD-007 field is feature_values
        price_cents=effective_price,
        availability=None,   # populated by ECM-005, not here
    )
```

Note: PRD-007 stores the option mapping as `feature_values` (Dict[feature_category_id → feature_value_id]; `PRD-007.md:109`). `StorefrontVariantOut.option_selections` (the ECM-003 wire shape) is populated from this field. `max(0, ...)` clamps effective price to zero — a variant with a large negative delta cannot produce a negative price (edge case: a promotional feature value whose delta exceeds the parent price).

### 4.3 Full implementation outline

```python
from __future__ import annotations

import logging
from typing import Callable, List, Optional, TypeVar

from app.core.settings import S
from app.models import CatalogItemOut, StorefrontVariantOut

logger = logging.getLogger(__name__)
_T = TypeVar("_T")

# ... ECM-002 helpers (_integration_enabled, _safe_upstream) already in this file ...


def enrich_catalog_item(item: dict, *, viewer: dict) -> CatalogItemOut:
    # Fast path: flag off or item is not a virtual product
    if not _integration_enabled("variant_selection"):
        return _catalog_item_out_local(item)

    product_type = item.get("product_type")
    if product_type != "virtual":
        return _catalog_item_out_local(item)

    parent_item_id = item.get("item_id", "")
    variants: List[StorefrontVariantOut] = _safe_upstream(
        lambda: _fetch_variants(parent_item_id, item.get("price_cents", 0)),
        default=[],
    )

    base = _catalog_item_out_local(item)
    return base.model_copy(update={"variants": variants or None})


def _catalog_item_out_local(item: dict) -> CatalogItemOut:
    """Thin re-implementation of catalog.py:_catalog_item_out to avoid a
    circular import (catalog.py imports store_integration.py in ECM-006)."""
    from app.routers.catalog import _catalog_item_out  # lazy import, avoids circular
    return _catalog_item_out(item)


def _fetch_variants(
    parent_item_id: str,
    parent_price_cents: Any,
) -> List[StorefrontVariantOut]:
    from app.services import product_variants  # lazy import: PRD-007 may not exist yet
    # list_variants returns (rows, last_evaluated_key) — unpack first element
    raw_variants, _lek = product_variants.list_variants(parent_item_id)
    base_price = int(parent_price_cents or 0)
    return [_build_storefront_variant(v, base_price) for v in raw_variants]
```

**Lazy imports are essential** here. `app/routers/catalog.py` will import `store_integration.enrich_catalog_item` (in ECM-006). If `store_integration.py` imported `catalog.py` at module level, a circular import results. The lazy import inside `_catalog_item_out_local` breaks the cycle. Similarly, `product_variants` (PRD-007) is imported lazily so that the entire ECM layer remains importable even before PRD-007 is merged — `_safe_upstream` catches the `ModuleNotFoundError` and degrades to `default=[]`.

### 4.4 No new HTTP endpoints

ECM-004 adds a service function only. The catalog endpoints (`list_items` at `catalog.py:394`, `search_items` at `catalog.py:465`, and the per-item detail endpoint) are wired to call `enrich_catalog_item` in ECM-006, not here. This strict separation means ECM-004 can be merged, tested, and flag-validated before ECM-006 touches the router.

### 4.5 Auth

`enrich_catalog_item` receives the `viewer` session dict from the caller (the router's `require_ui_session` context). It passes `viewer` through to `_fetch_variants` for potential future ownership checks but does not enforce any auth itself. `list_variants` (PRD-007) is expected to be a pure data function (no auth; ownership of the parent item was already verified by the router before calling `enrich_catalog_item`).

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag off — byte-for-byte legacy path

When `_integration_enabled("variant_selection")` returns `False` (either because `store_integration_enabled` is off, or because `store_variant_selection_enabled` is off while the master is on), `enrich_catalog_item` returns `_catalog_item_out_local(item)` — the exact same object that the existing router currently produces. The `variants` and `availability` fields (added by ECM-003) remain `None`, which serialises to `"variants": null` in the JSON response unless the router sets `response_model_exclude_none=True`.

**No existing tests break**: `_catalog_item_out` is called by both flags-off paths; the returned object is structurally identical to what all existing tests assert.

### 5.2 Virtual product with variants — happy path

1. `item.get("product_type") == "virtual"`.
2. `_fetch_variants(parent_item_id, base_price)` calls `product_variants.list_variants(parent_item_id)`.
3. `list_variants` returns `([{"variant_id": "abc", "sku": "RED-M", "feature_values": {"fc_color": "fv_red", "fc_size": "fv_m"}, "price_delta_cents": 500, "created_at": 1700000000}, ...], last_ek)`. `_fetch_variants` unpacks the tuple.
4. Each is mapped through `_build_storefront_variant`: effective price = `base_price + 500`, clamped to ≥ 0, `availability=None`.
5. The base `CatalogItemOut` is copied with `variants=[...]`. The `stock_status` on the parent item itself is set to `"unlimited"` when `stock_count is None` (existing `_compute_stock_status` logic at `catalog.py:94`); this is correct because virtual parents hold no stock — stock lives on the variant SKUs in the inventory service.

### 5.3 Non-virtual (standalone) product — no-op

`item.get("product_type")` is `None` (legacy item), `"standalone"`, `"digital"`, or any non-`"virtual"` string → `enrich_catalog_item` returns `_catalog_item_out_local(item)` immediately without querying `T.product_depth`. This is the hot path for all currently-existing catalog items.

### 5.4 Virtual product with zero variants

`product_variants.list_variants(parent_item_id)` returns `([], None)`. `_fetch_variants` unpacks the tuple to `raw_variants = []`. `_safe_upstream` returns `[]` (the lambda succeeds, just empty). `base.model_copy(update={"variants": [] or None})` evaluates to `{"variants": None}` because `[] or None` is `None`. The parent item is returned with `variants=None` — indistinguishable from a standalone item on the wire. This is intentional: a virtual product with no variants configured yet should not confuse the frontend into rendering an empty picker.

The implementation must use `variants or None` (not `variants if variants else None`) to collapse an empty list to `None`.

### 5.5 Upstream failure — degrade to legacy

If `product_variants.list_variants` raises any exception (module not yet merged, DynamoDB error, timeout), `_safe_upstream` catches it, logs at WARNING with traceback, and returns `default=[]`. The outer `[] or None` collapses this to `None`. The response is the same as the flag-off path — no 500, no partial data.

If `product_variants` itself does not yet exist (pre-PRD-007 import), the `ModuleNotFoundError` from the lazy import inside `_fetch_variants` is also caught by `_safe_upstream`. This means ECM-004 can be merged before PRD-007 without breaking the application.

### 5.6 Negative price_delta_cents

A feature value with a large negative delta (e.g. a clearance variant) could produce `parent_price_cents + price_delta_cents < 0`. `max(0, ...)` in `_build_storefront_variant` clamps the effective price to zero. The spec does not validate that the resulting zero-price is commercially sensible — that is a PRD-007 data-entry concern. ECM-004 simply enforces the model-level constraint (`StorefrontVariantOut.price_cents: int` with `ge=0` from ECM-003).

### 5.7 Variant list ordering

The list returned by `list_variants` is ordered by `created_at` ascending (integer Unix seconds; the `GSI_VIRT_SK` numeric sort key on the `ByVirtualParent` GSI — `PRD-007.md:37,115`; GSI uses `ScanIndexForward=True`, `PRD-007.md:130`). — **CORRECTED**: the sort key is `created_at` / `GSI_VIRT_SK`, not `sequence_num`. ECM-004 preserves list order and does not re-sort. PRD-007 owns the ordering contract.

### 5.8 feature_values with None value

If `variant_dict.get("feature_values")` is `None` (defensive case — should not happen in well-formed PRD-007 data), `dict(None or {})` evaluates to `dict({})` = `{}`. The variant is returned with an empty `option_selections` on the wire shape rather than crashing. This matches Pydantic's `Dict[str, str]` field which accepts an empty dict. — **CORRECTED**: the defensive guard reads `feature_values`, not `option_selections`.

### 5.9 Thread safety

`enrich_catalog_item` is a pure function with no module-level mutable state. The lazy imports (`from app.services import product_variants`) are safe under Python's import lock for concurrent first-import scenarios. Subsequent calls do not re-import. No locks needed.

### 5.10 viewer parameter

The `viewer` dict (session context from `require_ui_session`) is accepted but currently unused inside `enrich_catalog_item`. It is included in the signature to match the ECM-003 forward declaration (`docs/ofbiz/specs/ECM-003.md:207`) and to allow future per-viewer variant personalisation (e.g. subscription-tier-gated variants) without a signature change.

Default: `false`. When `false`, `enrich_catalog_item` short-circuits on line 1 and the entire variant path is dormant.

### 6.2 Variant-selection sub-flag (from ECM-002)

### 6.4 No new env vars

ECM-004 introduces no additional env vars beyond those already specified by ECM-002. All flag reading goes through `S` singleton via `_integration_enabled`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 dev/prod parity

`enrich_catalog_item` has no `if S.dev_mode` branch. The function calls `product_variants.list_variants` in both dev (moto-backed `T.product_depth`) and prod (real DynamoDB) identically. PRD-007 is responsible for its own dev/prod parity; ECM-004 simply delegates to it.

The `_safe_upstream` wrapper ensures that if the upstream is a mock in dev that behaves differently than prod, any deviation results in a degraded (not broken) response.

### 7.2 Idempotency

`enrich_catalog_item` is a pure read function. It produces no writes and has no idempotency concern of its own. The deterministic variant id from PRD-007 (`sha256(parent_id + sorted_feature_tuple)` per `CATALOG_DEPTH_TICKETS.md:138`) ensures that repeated reads of the same variant return the same `variant_id` and `sku`, making the function referentially stable.

### 7.3 Security: no data leakage across viewers

The `viewer` parameter allows ECM-004 to enforce per-viewer variant visibility in the future (e.g. a variant that is only visible to subscribers of a certain tier). Currently, all variants from `list_variants` are returned to all authenticated viewers. The authentication boundary is enforced by the router's `Depends(require_ui_session)` before `enrich_catalog_item` is called; ECM-004 does not bypass it.

Subscription access to the parent category is already enforced by `can_access_creator` at `catalog.py:403–405` (before the item list loop). ECM-004 inherits this gate without duplicating it.

### 7.4 No money path

ECM-004 reads topology only. It touches neither billing ledger entries nor inventory reservation counts. Cart purchase (`purchase_cart` at `shoppingcart.py:474`) is not called and the billing path is entirely separate.

## 8. Backward Compatibility & Migration

### 8.1 Zero migration required

All existing `T.catalog` rows lack a `product_type` field. `item.get("product_type")` returns `None`, which is not `"virtual"`, so every existing item takes the standalone no-op path. No backfill of existing rows is needed.

### 8.2 Additive-only model changes

`CatalogItemOut.variants` and `CatalogItemOut.availability` (added by ECM-003) default to `None`. Any existing code that constructs `CatalogItemOut` by keyword — `_catalog_item_out` at `catalog.py:110` — continues to work without modification because the new fields are keyword-only optional parameters with defaults.

Any existing test that asserts the shape of a `CatalogItemOut` response must not assert the *absence* of `variants`/`availability` — it must allow `None` values in those positions. In practice, all existing catalog tests (`tests/test_catalog_inventory.py`, etc.) use `response.json()` dict assertions and check only the fields they care about; extra `None` keys do not break those assertions.

### 8.3 Existing endpoints unchanged until ECM-006

ECM-004 adds a service function. The router endpoints are not modified in this ticket. `list_items` and `search_items` still call `_catalog_item_out(item)` directly until ECM-006 swaps those call sites to `enrich_catalog_item`. This means ECM-004 can be merged, code-reviewed, and tested independently before ECM-006 touches the live endpoints.

### 8.4 Rolling deployment

`STORE_VARIANT_SELECTION_ENABLED` defaults `false`, so a deployment of ECM-004 behind the flag is entirely safe. Enabling the flag on a running system requires:
1. PRD-002 tables deployed (no new tables from ECM-004 itself).
2. PRD-007 merged and `PRODUCT_DEPTH_ENABLED=true`.
3. Virtual products created with variant rows.
4. `STORE_INTEGRATION_ENABLED=true` + `STORE_VARIANT_SELECTION_ENABLED=true`.

Steps 1–4 can be performed incrementally; ECM-004 degrades gracefully at each intermediate state.

    sys.modules["app.services.product_variants"] = mock_pv

    from app.services.store_integration import enrich_catalog_item

test.describe("ECM-004: variant-enriched catalog read", () => {
    test.skip(!process.env.STORE_VARIANT_SELECTION_ENABLED, "flag off");

## 10. Open Questions / Assumptions

1. **Assumption: `product_variants.list_variants` is synchronous.** If PRD-007 implements it as `async def`, ECM-004 must use `await` and provide an `async def enrich_catalog_item_async` variant. ECM-006 then must `await` it inside the async route handler. This spec assumes sync; if wrong, the change is localised to the `_fetch_variants` call site.

2. **Assumption: `T.product_depth` is the table `catalog_products` (currently named so in `scripts/local-ddb-init.py:279`).** PRD-002 may rename it or add a separate `product_depth` table. ECM-004 does not access the table directly, so this is transparent.

3. **Verified: `list_variants` orders rows by `created_at` ascending** (integer Unix seconds, the `GSI_VIRT_SK` numeric sort key on `ByVirtualParent` with `ScanIndexForward=True` — `PRD-007.md:37,115,130`). ECM-004 preserves list order and does not re-sort. If PRD-007 returns them unordered (e.g. before GSI is in place), the UI picker (ECM-007) can sort client-side. — **CORRECTED** from original assumption that sort key was `sequence_num`.

4. **Assumption: `product_type` field is stored on the `T.catalog` item row itself (not derived from `T.product_depth`).** PRD-003 adds `product_type` as a top-level attribute on `T.catalog` rows, per `CATALOG_DEPTH_TICKETS.md:55`. If instead it's derived by querying `T.product_depth`, ECM-004 needs an additional lookup before the `product_type == "virtual"` check.

5. **Open question: Does `enrich_catalog_item` need to set `product_type` on the returned `CatalogItemOut`?** PRD-003 adds `product_type` as an optional field on `CatalogItemOut`. If `_catalog_item_out_local` reads it from the raw dict, it is already present. ECM-004 currently delegates entirely to `_catalog_item_out_local` for the base object and does not explicitly set `product_type`. This is correct only if `_catalog_item_out_local` forwards `product_type` from the raw dict to `CatalogItemOut`.

6. **Assumption: `StorefrontVariantOut` is imported from `app.models` after ECM-003 is merged.** If ECM-003 is not yet merged when ECM-004 is tested, the import fails. The CI pipeline must enforce ECM-003 → ECM-004 dependency ordering.

7. **Assumption: viewer-specific variant visibility is not required in this ticket.** All authenticated viewers who can access the parent category see all variants. If subscription-tier-gated variants are a future requirement, the `viewer` parameter already exists in the signature to accommodate it.
