## 1. Summary & Goal

ORD-015 delivers the full test suite for the order-lifecycle work stream (ORD-001 through ORD-014). It produces three hermetic offline pytest suites and one Playwright E2E spec, proving that all service logic is correct in isolation (no network, no real AWS), that the feature flag strictly preserves the pre-existing order record byte-for-byte, and that the full user-facing and admin-facing flows work end-to-end in the running dev stack.

The test suites are:

| File | Focus |
|------|-------|
| `tests/test_ord_lifecycle.py` | Transition matrix (legal/illegal), single-writer race condition, replay idempotency, status-history append, `get_order_lifecycle` read helper, flag-off golden record |
| `tests/test_ord_adjustments_shipgroups.py` | Adjustment math + state gating, ship-group creation/assignment, per-group fulfillment roll-up to header |
| `tests/test_ord_cancel_refund.py` | Cancel (pre-shipped states), return (shipped/completed), refund billing path, double-cancel/double-refund idempotency |
| `frontend/e2e/order-lifecycle.spec.ts` | Admin transition board, customer timeline, adjustment CRUD, self-cancel |

Non-goals: ORD-015 does not implement any service or router code — it only adds tests for the code already specified in ORD-005 through ORD-014. It does not change `app/services/commerce_order_service.py`, any billing file, or any existing E2E spec.

## 5. Detailed Behavior & Edge Cases

### 5.1 `tests/test_ord_lifecycle.py`

**5.1.1 Full transition matrix coverage**

The test iterates over every `(from_status, target_status)` pair that appears as a key in `TRANSITIONS` and asserts each is accepted. It then iterates over illegal pairs (edges not in the TRANSITIONS dict) and asserts `OrderTransitionError` is raised. Every legal edge in the ORD-005 graph must have a corresponding test row:

- Forward happy path: `created→approved`, `approved→allocated`, `allocated→picking`, `picking→packed`, `packed→shipped`, `shipped→completed`
- Side transitions: `created→held`, `approved→held`, `allocated→backorder`, `picking→backorder`, `held→approved`, `held→allocated`, `held→picking`, `held→packed`
- Cancel from pre-shipped: `created→cancelled`, `approved→cancelled`, `allocated→cancelled`, `picking→cancelled`, `packed→cancelled`, `held→cancelled`, `backorder→cancelled`
- Return from post-shipped: `shipped→returned`, `completed→returned`
- Illegal examples: `completed→approved`, `shipped→created`, `cancelled→approved`, `returned→shipped`

**5.1.2 Single-writer race condition**

Two concurrent `transition_order` calls from `created → approved` on the same `order_id` are simulated by: (1) calling `transition_order` once to succeed, then (2) manually patching the header back to `lifecycle_status="created"` in DDB and observing that the second call — which uses the stale original `from_status` in its CAS guard — raises `OrderConflictError`. This verifies the conditional `update_item` guard works.

Alternatively: patch `T.orders.update_item` to raise a `ClientError` with code `ConditionalCheckFailedException` on the second call and assert `OrderConflictError` is raised.

**5.1.3 Replay idempotency**

Call `transition_order` with `idempotency_key="key1"` for `created → approved`. Call it again with the same `idempotency_key`. Assert: exactly one HIST row exists for the transition (the second call is a no-op), both calls return the same `event_id`, and the header `lifecycle_status` remains `approved`.

Implementation: `_derive_event_id` from ORD-005 produces the same SHA-256 hex for the same inputs (`docs/ofbiz/specs/ORD-005.md:38–41`). The history append checks for an existing HIST row keyed by `event_id` before writing (ORD-006).

**5.1.4 Status-history append on every transition**

Seed an order at `created`. Drive through `created→approved→allocated→picking`. After each transition, call `list_status_history(order_id)` and assert: the count of HIST rows equals the number of transitions driven so far; the most recent entry has the correct `from_status`, `to_status`, `actor`, `reason`, and a non-zero `ts`; entries are returned newest-first.

**5.1.5 Golden-record flag-off test**

With `S.order_lifecycle_enabled = False`:
1. Capture the DDB item written by `CommerceOrderService.create_order` (scan the in-memory orders table).
2. Assert the item contains exactly the keys present in `app/services/commerce_order_service.py:72–84`: `order_id`, `user_id`, `status` (value `"pending_payment"`), `created_at`, `updated_at`, `source_system`, `correlation_id`, `currency`, `amount_cents`, `line_item_count`, `metadata`. And `sk = "ORDER"` (added by ORD-003 unconditionally).
3. Assert the item does NOT contain `lifecycle_status`, `adjusted_amount_cents`, or any HIST/ADJ/SHIPGRP rows.
4. Assert the `order_items` table rows are unchanged.

With `S.order_lifecycle_enabled = True`:
5. Capture the same DDB item for a newly created order.
6. Assert it contains all of the above keys PLUS `lifecycle_status="created"`.
7. Query for HIST rows and assert exactly one `created` history entry exists.

### 5.2 `tests/test_ord_adjustments_shipgroups.py`

**5.2.1 Adjustment math**

Seed an order at `approved` (pre-shipped) with `amount_cents = 10000`. Apply adjustments:
- Discount: `type="discount"`, `amount_cents=-1500` (negative)
- Tax: `type="tax"`, `amount_cents=800` (positive)
- Shipping: `type="shipping"`, `amount_cents=500` (positive)

Assert `compute_adjusted_amount(order_id)` = `10000 + (-1500) + 800 + 500 = 9800`. Assert `adjusted_amount_cents` on the ORDER-SK header = 9800. Assert the base `amount_cents` on the header is still 10000 (never mutated).

**5.2.2 State gating for adjustments**

Assert `add_adjustment` raises `ValueError` (or `OrderTransitionError`) when the order is at `shipped`, `completed`, `cancelled`, or `returned`. Assert it succeeds for all pre-`shipped` states: `created`, `approved`, `allocated`, `picking`, `packed`, `held`, `backorder`.

**5.2.3 Currency mismatch**

Create an order with `currency="USD"`. Attempt to add an adjustment with `currency="EUR"`. Assert a `ValueError` with a currency-mismatch message is raised and no ADJ row is written.

**5.2.4 Remove adjustment + re-computation**

Add two adjustments, then remove one. Assert `compute_adjusted_amount` reflects only the remaining adjustment and the ORDER header `adjusted_amount_cents` is updated accordingly.

**5.2.5 Ship-group creation and item exclusivity**

Create an order with 3 line items (`item_id = "1"`, `"2"`, `"3"`). Create ship group A with items `["1","2"]` and ship group B with item `["3"]`. Assert both SHIPGRP rows exist. Attempt to add item `"1"` to ship group B and assert a double-assignment error is raised. Attempt to reference a non-existent `item_id="99"` and assert an unknown-item error is raised.

**5.2.6 Per-ship-group fulfillment roll-up**

Create two ship groups (A: items `["1"]`, B: items `["2","3"]`) on an order at `allocated`. Advance ship group A to `shipped`. Assert the ORDER header `lifecycle_status` remains `allocated` (not yet all groups shipped). Advance ship group B to `shipped`. Assert `transition_order` was called (or the header updated) to advance the ORDER to `shipped`. Assert `list_ship_groups` returns both groups with `ship_status="shipped"`.

### 5.3 `tests/test_ord_cancel_refund.py`

**5.3.1 Cancel with refund (pre-shipped)**

Patch `new_ledger_entry`, `apply_balance_delta`, and `settle_or_reverse_ledger` as `MagicMock`. Seed an order at `approved` with `amount_cents=5000` and `payment_intent_id="pi_test"` stored in the header. Call `cancel_order(order_id, reason="customer_request", actor="alice", refund=True)`.

Assert:
- ORDER header `lifecycle_status="cancelled"`.
- One HIST row appended with `to_status="cancelled"`.
- `new_ledger_entry` called exactly once with `reason="refund"`, `amount_cents=5000`, `entry_type="adjustment"`.
- `apply_balance_delta` called exactly once.
- Audit event `"order_cancelled"` emitted once.

**5.3.2 Cancel without refund**

Call `cancel_order(order_id, reason="duplicate", actor="alice", refund=False)`. Assert: ORDER header transitions to `cancelled`. `new_ledger_entry` NOT called. `apply_balance_delta` NOT called. Audit event `"order_cancelled"` emitted once.

**5.3.3 Illegal cancel (shipped → cancelled)**

Seed order at `shipped`. Call `cancel_order`. Assert `OrderTransitionError` raised and header `lifecycle_status` remains `shipped`.

**5.3.4 Cancel with adjustments (adjusted refund amount)**

Patch `compute_adjusted_amount` to return `4200` (discount applied to base `5000`). Call `cancel_order(..., refund=True)`. Assert `new_ledger_entry` called with `amount_cents=4200`, not `5000`.

**5.3.5 Return with refund (completed → returned)**

Seed order at `completed`. Call `return_order(order_id, reason="damaged", actor="admin", refund=True)`. Assert ORDER `lifecycle_status="returned"`, `new_ledger_entry` called once with `reason="refund"`, audit event `"order_returned"` emitted.

**5.3.6 Double-cancel idempotency**

Call `cancel_order` once on an order at `created`. Then call it again. Assert the second call raises `OrderTransitionError` (state machine CAS rejects transition from `cancelled → cancelled`), no duplicate HIST rows written, `new_ledger_entry` called only once total.

**5.3.7 Double-refund prevention**

Seed an order with a `refund_ledger_sk` field already set on the header (simulating a prior refund already written). Assert `cancel_order(..., refund=True)` does NOT call `new_ledger_entry` again. (Implementation: `cancel_order` checks `header.get("refund_ledger_sk")` before issuing the refund.)

## 6. Feature Flag & Config

The entire order-lifecycle work stream is gated behind one flag, established by ORD-002. **These settings do not yet exist in `app/core/settings.py`** [verified: `grep order_lifecycle_enabled app/core/settings.py` returns nothing] — ORD-002 adds them. ORD-015 tests use `object.__setattr__(S, ...)` to set them, which works whether the attribute is newly added or pre-existing:

| Setting attribute | Env variable | Type | Default |
|---|---|---|---|
| `S.order_lifecycle_enabled` | `ORDER_LIFECYCLE_ENABLED` | `bool` | `false` |
| `S.order_lifecycle_auto_approve` | `ORDER_LIFECYCLE_AUTO_APPROVE` | `bool` | `false` |
| `S.order_backorder_enabled` | `ORDER_BACKORDER_ENABLED` | `bool` | `false` |

ORD-015 tests must:

1. **Explicitly enable the flag** before testing lifecycle behavior: `object.__setattr__(S, "order_lifecycle_enabled", True)` with cleanup.
2. **Test the flag-off path** in the golden-record test: `object.__setattr__(S, "order_lifecycle_enabled", False)` and assert the pre-lifecycle record shape.
3. **Test flag-off 503** in the E2E spec: with the feature flag off (controlled via the running dev stack's `.env.local`), every lifecycle endpoint returns 503 with `{"code": "feature_disabled"}`. The E2E test skips this assertion if the flag cannot be toggled at test runtime — instead, it documents it as a manual verification step.

The `order_backorder_enabled` sub-flag gates the `→ BACKORDER` transition edges at runtime. Tests that exercise `backorder` transitions must set `object.__setattr__(S, "order_backorder_enabled", True)`. Tests exercising the default path leave it `False` and assert that `allocated→backorder` raises `OrderTransitionError` (the backorder edge is in TRANSITIONS but gated by a runtime flag check inside `transition_order`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

The service layer writes only to DynamoDB (`T.orders` [verified: `app/core/tables.py:381`], `T.order_items` [verified: `app/core/tables.py:382`], `T.billing` via imported billing primitives) and to the `alerts` table via `audit_event` [verified: `app/services/alerts.py:644`]. None of these paths branch on `S.dev_mode`. The `orders` table is DynamoDB local in dev and real DynamoDB in prod — the same code path both ways. No `if S.dev_mode` branch is introduced by ORD-015.

The billing refund path called from `cancel_order` / `return_order` calls `new_ledger_entry` + `apply_balance_delta` + `settle_or_reverse_ledger` from `app/services/billing_shared.py` [verified: `billing_shared.py:224,83,262`] — the same primitives used by `billing.refund_payment` (`app/routers/billing.py:1287`, with billing primitives call site at `:1306–1324`). No Stripe mock call is made from the service layer; the Stripe refund API call lives in the billing router (not in the order service), so the service-layer tests can patch the billing primitives without encountering Stripe.

### 7.2 Idempotency

Transition idempotency is enforced by SHA-256 `event_id` derivation (`docs/ofbiz/specs/ORD-005.md:38`):

```python
event_id = hashlib.sha256(
    f"{order_id}|{from_status or ''}|{to_status}|{idempotency_key or ''}".encode()
).hexdigest()[:16]
```

A replay with the same `idempotency_key` produces the same `event_id`. Before writing the HIST row, `transition_order` checks whether `HIST#{ts}#{event_id}` already exists and returns the cached result if so.

Refund idempotency is enforced by the `refund_ledger_sk` guard on the ORDER header: once a refund ledger entry is written, its `sk` is stored on the header, and any subsequent `cancel_order(..., refund=True)` call is a no-op on the billing side.

Adjustment idempotency: `add_adjustment` derives `adjustment_id = hashlib.sha256(f"{order_id}|{adj_in.type}|{adj_in.amount_cents}|{adj_in.label}".encode()).hexdigest()[:16]`, so re-submitting the same adjustment is a no-op (the ADJ row already exists under that key).

### 7.3 Security

- **Ownership enforcement**: `cancel_order` called from the owner endpoint (customer self-cancel) enforces that `caller_sub == order["user_id"]` before proceeding. Admin callers bypass this check. Tests in `test_ord_cancel_refund.py` include an ownership-failure case (wrong user_sub → `OrderNotFoundError` to avoid leaking existence).
- **No PII in HIST rows**: HIST rows store only status strings, actor IDs, reason strings, and timestamps — no billing card numbers, addresses, or order item details.

## 8. Backward Compatibility & Migration

ORD-015 is test-only and makes no schema, service, or router changes. The only file it creates are test files and the E2E spec. It has no migration requirements.
