# FAC-013 — Warehouse / fulfillment admin page + route + nav

## 1. Summary & Goal

FAC-013 is the frontend milestone of the facility/fulfillment stack. It delivers a
single admin page — `frontend/src/pages/shop/admin/WarehouseFulfillmentAdmin.tsx` —
that consolidates all warehouse operator workflows into four tabbed panels:
**Facilities & Locations**, **Stock Transfers**, **Receiving**, and **Pick / Pack /
Ship** (fulfillment queue). It also wires the page into the application router
(`frontend/src/App.tsx`) and the sidebar navigation
(`frontend/src/components/layout/Sidebar.tsx`), both of which are gated on the
`FACILITY_FULFILLMENT_ENABLED` flag and admin/root role.

The goal is to let a warehouse administrator:

1. Create facilities and location bins without a page reload.
2. Initiate, advance, and complete stock transfers.
3. Post an inbound receiving line (receive goods into a location).
4. Drive an order through the pick → pack → ship lifecycle, entering a carrier
   tracking number at ship time.

All mutations use React Query `useMutation` + query-key invalidation so the view
refreshes automatically. No new DynamoDB tables, backend services, or API endpoints
are introduced by this ticket — it is a pure frontend change that calls the HTTP
surfaces shipped by FAC-005 (`/ui/facilities`) and FAC-011 (`/ui/fulfillment`).

### 4.5 `WarehouseFulfillmentAdmin.tsx` component structure

The page component is the primary deliverable. It is structured as four
`TabsContent` panels inside a single `Tabs` root, where the default active tab is
`"facilities"`.

#### Top-level component

```tsx
export default function WarehouseFulfillmentAdmin() {
  const qc = useQueryClient();
  const accessToken = useAuthStore((s) => s.accessToken);
  const allowed = canAccessGeneralAdminControls(accessToken);

  if (!isFacilityFulfillmentEnabled()) {
    return <EmptyState icon={<Warehouse />}
      title="Warehouse management is not enabled"
      description="Enable FACILITY_FULFILLMENT_ENABLED to manage facilities and fulfillment." />;
  }
  if (!allowed) {
    return <EmptyState icon={<AlertTriangle />}
      title="Access denied"
      description="Warehouse management requires admin or root access." />;
  }

  return (
    <div className="space-y-6 p-6">
      <div className="flex items-center gap-2">
        <Warehouse className="h-6 w-6" />
        <h1 className="text-2xl font-semibold tracking-tight">
          Warehouse & Fulfillment
        </h1>
      </div>
      <Tabs defaultValue="facilities">
        <TabsList>
          <TabsTrigger value="facilities">Facilities & Locations</TabsTrigger>
          <TabsTrigger value="transfers">Transfers</TabsTrigger>
          <TabsTrigger value="receiving">Receiving</TabsTrigger>
          <TabsTrigger value="fulfillment">Fulfillment Queue</TabsTrigger>
        </TabsList>
        <TabsContent value="facilities"><FacilitiesPanel qc={qc} /></TabsContent>
        <TabsContent value="transfers"><TransfersPanel qc={qc} /></TabsContent>
        <TabsContent value="receiving"><ReceivingPanel qc={qc} /></TabsContent>
        <TabsContent value="fulfillment"><FulfillmentPanel qc={qc} /></TabsContent>
      </Tabs>
    </div>
  );
}
```

Each panel is a local function component defined in the same file, receiving `qc:
QueryClient` as a prop (avoids `useQueryClient()` call in every sub-component and
simplifies unit testing).

#### Panel: `FacilitiesPanel`

- **Query key**: `["facilities"]`.
- **Reads**: `GET /ui/facilities` → `listFacilities()`. Response shape:
  `{ facilities: Facility[], count: number }`.
- **Renders**: a `Card` with a `Table` listing facility name, type, status.
  "Locations" link per row expands (via local React state `expandedFacilityId`)
  to a sub-table loaded by `GET /ui/facilities/{id}/locations`.
- **Mutations**:
  - "Create Facility" — opens a `Dialog` (controlled via `showCreateFacility:
    boolean` state) containing a mini-form (name, facility_type select, optional
    address). On submit: `POST /ui/facilities` via `createFacility(body)`. On
    success: `qc.invalidateQueries({ queryKey: ["facilities"] })` + close dialog +
    `toast.success("Facility created")`.
  - "Create Location" (per facility row) — opens a second `Dialog`
    (`showCreateLocation` + `targetFacilityId` state). Fields: `location_id`
    (string, admin-defined bin label), `location_type` (select: aisle / bay / bin
    / default), optional `description`. On submit: `POST /ui/facilities/{id}/locations`
    via `createLocation(facilityId, body)`. On success: `qc.invalidateQueries({
    queryKey: ["facilities", facilityId, "locations"] })` + `toast.success`.
  - "Archive Facility" — `PATCH /ui/facilities/{id}` with `{ status: "archived" }`.
    Shows a confirmation `AlertDialog` before executing. On success: invalidates
    `["facilities"]`.

#### Panel: `TransfersPanel`

- **Query key**: `["fulfillment", "transfers"]`.
- **Reads**: `GET /ui/fulfillment/transfers?status=requested&limit=50` (default
  filter: active transfers). Filter dropdown (controlled state `statusFilter:
  string`) switches the query parameter. Uses `useQuery` with a dynamic key:
  `["fulfillment", "transfers", statusFilter]`.
- **Renders**: `Table` of transfers with columns: Transfer ID (truncated), From →
  To (location labels), Status badge, Created date. Each row has action buttons
  rendered based on current status:
  - `requested` → "Advance to In-Transit" (calls `POST
    /ui/fulfillment/transfers/{id}/advance`).
  - `in_transit` → "Complete" (calls `POST
    /ui/fulfillment/transfers/{id}/complete`) and "Cancel".
  - `completed` / `cancelled` — no action buttons (terminal states).
- **"Initiate Transfer" button** opens a `Dialog` with a form: from_facility_id
  (select), from_location_id (select, dependent on from_facility_id), to_facility_id
  (select), to_location_id (select), SKU + quantity lines (dynamic list, min 1).
  On submit: `POST /ui/fulfillment/transfers` via `createTransfer(body)`. On
  success: `qc.invalidateQueries({ queryKey: ["fulfillment", "transfers"] })`.
- **Mutation error handling**: a 409 (overdraw rejected by the backend) surfaces as
  `toast.error("Insufficient stock at source location")`.

#### Panel: `ReceivingPanel`

- **Query key**: `["fulfillment", "receipts"]`.
- **Reads**: `GET /ui/fulfillment/receipts?facility_id=...&limit=50` (paginated by
  facility). Facility selector controls the query parameter.
- **"Post Receipt" form** — always visible at the top of the panel (no dialog, since
  receiving is the primary action here). Fields: facility_id (select, required),
  location_id (select, dependent on facility), optional PO reference
  (`po_id: string`), correlation_id (auto-generated client-side as
  `crypto.randomUUID()` but displayed + editable for manual idempotency control),
  and a repeating lines section (SKU, ordered_qty, received_qty). On submit:
  `POST /ui/fulfillment/receipts` via `receiveShipment(body)`. On success:
  `qc.invalidateQueries({ queryKey: ["fulfillment", "receipts"] })` +
  `toast.success("Receipt posted")`.
- **Idempotency note**: the correlation_id field is prepopulated with
  `crypto.randomUUID()` on form mount but editable, so an operator can re-submit
  the same receipt after a network failure without double-counting on-hand.
- **Table**: lists recent receipts with columns: Receipt ID (truncated), Facility,
  Location, PO ID (or "—"), Status badge, Created date.

#### Panel: `FulfillmentPanel`

This is the pick/pack/ship queue — the most complex panel.

- **Query key**: `["fulfillment", "picklists"]`.
- **Reads**: `GET /ui/fulfillment/picklists?status=open&limit=50`. Filter tabs at
  the top of the panel switch between `open`, `in_pick`, `picked`, `packed`
  statuses (using a second tier of local tab state inside the panel, not the outer
  `Tabs` component — this avoids URL coupling and keeps navigation simple).
- **Picklist table columns**: Picklist ID (truncated), Order ID, Facility, Status
  badge, Created date. Each row expands (accordion via controlled `expandedPicklist`
  state) to show pick lines (SKU, location, qty, picked_qty, line_status).
- **Actions per status**:
  - `open` → No separate "Start Picking" button. The `open → in_pick` header
    transition is driven implicitly by the **first** "Confirm Pick" action on any
    line (FAC-008 §3.2 + FAC-011 §4.5; confirmed in pass 3 — see §10 item 2).
    The panel should show per-line "Confirm Pick" buttons for `open` picklists
    directly.
    <!-- CORRECTED pass 3: no explicit picklist advance endpoint; removed "Start Picking" button -->
  - `in_pick` → per-line "Confirm Pick" button that opens a small inline form for
    `picked_qty` input; on submit calls `POST
    /ui/fulfillment/picklists/{id}/lines/{n}/confirm` via `confirmPick(picklistId,
    lineIndex, pickedQty)`. When all lines are `picked`, the picklist flips to
    `picked` automatically (backend-driven).
  - `picked` → "Pack" button opens a `Dialog` (`PackDialog`) for entering package
    details (weight_g, dimensions_cm: {l, w, h}, and contents — pre-populated from
    the picked lines). Submits `POST /ui/fulfillment/picklists/{id}/pack` via
    `packPicklist(picklistId, packages)`. On success: invalidates
    `["fulfillment", "picklists"]` and `["fulfillment", "shipments"]`.
  - `packed` → "Ship" button opens a `ShipDialog` with required fields: `carrier`
    (select: ups / fedex / usps / dhl / other) and `tracking_number` (string input,
    required, at least 5 chars). Submits `POST
    /ui/fulfillment/shipments/{shipment_id}/ship` via `shipShipment(shipmentId,
    carrier, trackingNumber)`. On success: tracking number is immediately visible in
    the shipment detail; invalidates `["fulfillment", "picklists"]` and
    `["fulfillment", "shipments"]`.
- **"Generate Picklist" button** — at the top of the panel, opens a `Dialog` with a
  single `order_id` text field and a `facility_id` select. Calls `POST
  /ui/fulfillment/picklists` via `generatePicklist(orderId, facilityId)`. On
  success: `qc.invalidateQueries({ queryKey: ["fulfillment", "picklists"] })` +
  `toast.success("Picklist generated for order ${orderId}")`.

### 4.6 Query key hierarchy

The full set:

| Data | Query key |

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag off

When `VITE_FACILITY_FULFILLMENT_ENABLED` is absent or `false` (the default),
`isFacilityFulfillmentEnabled()` returns `false`. The page component renders the
"not enabled" `EmptyState` immediately without firing any API calls (all `useQuery`
calls must be guarded with `enabled: isFacilityFulfillmentEnabled() && allowed`).
The sidebar nav entry is hidden entirely. Navigating directly to `/admin/warehouse`
still renders the page component, which shows the empty state — it does not 404
(the 404 comes from the backend if any API call is attempted with the backend flag
also off). This matches the behavior of `InventoryAdmin.tsx:146–156`.

### 5.2 Role guard

`canAccessGeneralAdminControls(accessToken)` (from
`frontend/src/lib/adminCapabilities.ts:47`) returns `true` for `role === "root"`
unconditionally, and for `role === "admin"` only when the admin profile type is
`"general"` (not `"scoped"`). Scoped admins cannot access this page. This mirrors
the inventory admin check at `InventoryAdmin.tsx:91`.
<!-- VERIFIED: adminCapabilities.ts:47–51; InventoryAdmin.tsx:91 `const allowed = canAccessGeneralAdminControls(accessToken)` -->

### 5.3 Tracking number visibility

After a successful `shipShipment(...)` call, the shipment row in the `packed` tab
will disappear (status flips to `shipped`). The tracking number must remain
accessible: either the Fulfillment panel includes a "Shipped" status filter tab
showing completed shipments (each row expands to show carrier + tracking), or a
separate `ShipmentsPanel` section exists within the Fulfillment tab. The recommended
approach is to include a `shipped` filter tab in the `FulfillmentPanel` so the
acceptance criterion ("tracking number entered at ship is visible on the shipment
view") is met without additional navigation.

### 5.4 Dependent selects (facility → location)

When building the "Create Location", "Initiate Transfer", and "Post Receipt" forms,
the location select is populated from `GET /ui/facilities/{id}/locations`. The query
must use `enabled: !!selectedFacilityId` to avoid a request with an empty string
path param. When the user changes the facility select, the location select resets to
`""` (uncontrolled React state reset pattern).

### 5.5 Optimistic updates

No optimistic updates are used. Every mutation waits for the server response before
invalidating queries. This avoids stale reservation/stock state and is consistent
with the inventory admin pattern (`InventoryAdmin.tsx:126–131`).
<!-- VERIFIED: InventoryAdmin.tsx:126–131 onSuccess block; no onMutate/optimistic update present -->

### 5.6 Pack dialog contents pre-population

The `PackDialog` reads the picklist's confirmed pick lines (available in the
expanded picklist detail already loaded) and pre-populates one package's `contents`
field with those lines. The operator may add more packages (multi-package shipment)
or adjust weights/dimensions. Validation: contents total qty for each SKU must not
exceed picked_qty (enforced client-side before submit; the backend also enforces
this and returns 409 on violation with `toast.error("Pack qty exceeds picked qty")`).

### 5.7 Concurrent state transitions

If two admin users view the same picklist simultaneously and one completes a pick
action, the other's "Confirm Pick" submission will receive a 409 from the backend
(conditional guard on the DDB item status). The error is surfaced as `toast.error(
"Action failed — the picklist state may have changed. Refreshing.")` followed by
`qc.invalidateQueries({ queryKey: ["fulfillment", "picklists"] })` to force a
refetch of current state.

### 5.8 Empty states

Each panel renders an `<EmptyState>` component when its query returns an empty list:
- Facilities panel: "No facilities yet. Create your first facility."
- Transfers panel: "No transfers found for the selected status."
- Receiving panel: "No receipts found for this facility."
- Fulfillment panel: "No picklists in this status. Generate a picklist for an order."

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

The frontend page calls the same HTTP endpoints in dev and prod — there are no
`dev_mode` branches in React components. The Vite proxy (`vite.config.ts`) forwards
`/ui/facilities` and `/ui/fulfillment` to the backend in dev; in prod these resolve
directly to the backend service. No mock or stub paths exist in the frontend code.

### 7.2 CSRF

All non-GET API calls go through the shared `api/client.ts` Axios instance, which
attaches the `x-csrf-token` header from the `ui_csrf` cookie on every request
(established pattern — see `frontend/src/api/client.ts`). The FAC-013 page does
not bypass or supplement this mechanism.

### 7.3 Idempotency surface

The receiving form's `correlation_id` field (Section 4.5, `ReceivingPanel`) is the
user-visible idempotency key. It is pre-populated with `crypto.randomUUID()` on form
mount so normal usage is idempotent-by-default. Re-submitting with the same
`correlation_id` is a no-op at the backend (FAC-007 deterministic receipt ID via
`sha256(correlation_id)[:32]`), which means a network retry after a timeout will
not double-post the receipt.

### 7.4 Role enforcement

Role enforcement is duplicated: the frontend hides the nav entry and guards the
page component (defense-in-depth UX), but the real enforcement is in the backend's
`require_admin_or_root_csrf` dependency. A non-admin user who navigates directly to
`/admin/warehouse` sees the `<EmptyState>` "Access denied" screen with no API calls
fired.

### 7.5 Sensitive data

Tracking numbers (carrier, `tracking_number` string) are low-sensitivity metadata.
Facility addresses are stored server-side and returned in API responses — they are
not cached in localStorage or any persistent client store; React Query's in-memory
cache is cleared on tab close.
