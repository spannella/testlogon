# MFG-006 — BOM & routing admin UI

## 1. Summary & Goal

MFG-006 delivers the manufacturing admin UI: a React page under
`frontend/src/pages/shop/admin/ManufacturingAdmin.tsx` (alongside the inventory
admin at `frontend/src/pages/shop/admin/InventoryAdmin.tsx`) that exposes BOM
CRUD, component editing, work-center management, routing-task editing, and a
live BOM-explosion preview for a configurable build quantity. The page is
tab-structured (three tabs: **BOMs**, **Work Centers**, **Routing Tasks**),
admin/root-gated client-side and server-side, and completely hidden or 404 when
`MANUFACTURING_MRP_ENABLED=false` / `VITE_MANUFACTURING_MRP_ENABLED=false`.

The page consumes the backend endpoints from MFG-011 (`app/routers/manufacturing.py`)
which delegates to services MFG-004 (`manufacturing_bom.py`) and MFG-005
(`manufacturing_routing.py`). MFG-006 ships no backend logic of its own; it is
purely a frontend + thin TypeScript types/endpoint-wrapper ticket.

## 4. API / Service Design

### 4.1 Frontend endpoint wrappers — `frontend/src/api/endpoints/manufacturing.ts`

New file; no existing `manufacturing.ts` in `frontend/src/api/endpoints/`
(confirmed by `ls frontend/src/api/endpoints/` returning only `hostInventory.ts`
and `inventory.ts` for the OFBiz modules).

```ts
import { api } from "@/api/client";
import type {
  BomOut, BomHeaderIn, BomUpdateIn, ExplodedComponentOut,
  WorkCenterOut, WorkCenterIn,
  RoutingTaskOut, RoutingTaskIn,
} from "@/api/types";

const BASE = "/ui/manufacturing";

// ── BOMs ───────────────────────────────────────────────────────────────────

export const createBom = (body: BomHeaderIn) =>
  api.post<BomOut>(`${BASE}/boms`, body);

export const listBoms = (params?: { product_sku?: string; status?: string; limit?: string }) =>
  api.get<BomOut[]>(`${BASE}/boms`, params as Record<string, string>);

export const getBom = (bomId: string) =>
  api.get<BomOut>(`${BASE}/boms/${encodeURIComponent(bomId)}`);

export const updateBom = (bomId: string, body: BomUpdateIn) =>
  api.patch<BomOut>(`${BASE}/boms/${encodeURIComponent(bomId)}`, body);

export const deleteBom = (bomId: string) =>
  api.del<void>(`${BASE}/boms/${encodeURIComponent(bomId)}`);

export const explodeBom = (bomId: string, buildQty: number) =>
  api.get<ExplodedComponentOut[]>(
    `${BASE}/boms/${encodeURIComponent(bomId)}/explode`,
    { build_qty: String(buildQty) },
  );

// ── Work Centers ───────────────────────────────────────────────────────────

export const createWorkCenter = (body: WorkCenterIn) =>
  api.post<WorkCenterOut>(`${BASE}/work-centers`, body);

export const listWorkCenters = (status?: "active" | "inactive") =>
  api.get<WorkCenterOut[]>(`${BASE}/work-centers`, status ? { status } : undefined);

export const updateWorkCenter = (wcId: string, body: Partial<WorkCenterIn>) =>
  api.patch<WorkCenterOut>(`${BASE}/work-centers/${encodeURIComponent(wcId)}`, body);

// ── Routing Tasks ──────────────────────────────────────────────────────────

export const listRoutingTasks = (bomId: string) =>
  api.get<RoutingTaskOut[]>(`${BASE}/boms/${encodeURIComponent(bomId)}/routing-tasks`);

export const createRoutingTask = (bomId: string, body: RoutingTaskIn) =>
  api.post<RoutingTaskOut>(
    `${BASE}/boms/${encodeURIComponent(bomId)}/routing-tasks`,
    body,
  );

export const updateRoutingTask = (bomId: string, taskId: string, body: Partial<RoutingTaskIn>) =>
  api.patch<RoutingTaskOut>(
    `${BASE}/boms/${encodeURIComponent(bomId)}/routing-tasks/${encodeURIComponent(taskId)}`,
    body,
  );

export const deleteRoutingTask = (bomId: string, taskId: string) =>
  api.del<void>(
    `${BASE}/boms/${encodeURIComponent(bomId)}/routing-tasks/${encodeURIComponent(taskId)}`,
  );
```

### 4.2 Backend routing tasks endpoints (required from MFG-011)

Routing task endpoints are not explicitly listed in the MFG-011 ticket text but
are implied by MFG-005's acceptance criterion ("routing tasks are returned in
declared order; work centers CRUD"). MFG-011 must declare them in
`app/routers/manufacturing.py` as:

```python
@manufacturing_router.post("/boms/{bom_id}/routing-tasks", status_code=201)
async def create_routing_task(
    bom_id: str,
    body: RoutingTaskIn,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
):
    _require_enabled()
    return routing_svc.create_routing_task(bom_id, body.dict(), user_sub=user.sub)

@manufacturing_router.get("/boms/{bom_id}/routing-tasks")
async def list_routing_tasks(
    bom_id: str,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
):
    _require_enabled()
    return routing_svc.list_routing_tasks(bom_id)

@manufacturing_router.patch("/boms/{bom_id}/routing-tasks/{task_id}")
async def update_routing_task(
    bom_id: str,
    task_id: str,
    body: RoutingTaskUpdateIn,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
):
    _require_enabled()
    return routing_svc.update_routing_task(bom_id, task_id, body.dict(exclude_none=True), user_sub=user.sub)

@manufacturing_router.delete("/boms/{bom_id}/routing-tasks/{task_id}", status_code=204)
async def delete_routing_task(
    bom_id: str,
    task_id: str,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
):
    _require_enabled()
    routing_svc.delete_routing_task(bom_id, task_id, user_sub=user.sub)
```

Route ordering: the literal `/boms/{bom_id}/routing-tasks` sub-path must be
declared before any bare `/{bom_id}` catch-all routes in the same
`APIRouter` (same as the CLAUDE.md `/schedules`-before-`/{export_id}` rule).

All endpoints enforce `require_admin_or_root_csrf` — the same dependency used
in `app/routers/inventory.py:48`. The `_require_enabled()` gate at the top of
each handler ensures 404 when the master flag is off.

## 5. Detailed Behavior & Edge Cases

### 5.1 Page structure — `ManufacturingAdmin.tsx`

```
ManufacturingAdmin
├── Feature-flag guard (EmptyState if isManufacturingMrpEnabled() is false)
├── Role guard (EmptyState if !canAccessGeneralAdminControls(accessToken))
└── <Tabs defaultValue="boms">
    ├── <TabsList>
    │   ├── <TabsTrigger value="boms">   BOMs
    │   ├── <TabsTrigger value="work-centers">  Work Centers
    │   └── <TabsTrigger value="routing">  Routing
    ├── <TabsContent value="boms">    → <BomTab />
    ├── <TabsContent value="work-centers"> → <WorkCenterTab />
    └── <TabsContent value="routing"> → <RoutingTab />
```

Each tab is a separate inner component (not a separate file), co-located in
`ManufacturingAdmin.tsx` to avoid prop-drilling the shared `queryClient`.

### 5.2 BOM Tab — `<BomTab />`

**List panel** (left or top):

- `useQuery(["mfg", "boms"], () => listBoms({ limit: "200" }))` populates a
  `<Table>` with columns: `product_sku`, `name`, `output_quantity`, `status`
  (badge: draft=outline, active=green, inactive=gray), `created_at` (formatted
  relative timestamp).
- Row click selects the BOM and populates the detail/edit panel.
- "New BOM" button opens the create dialog.

**Create dialog** (`<BomCreateDialog />`):

- Fields: `product_sku` (text), `name` (text), `output_quantity` (number, min
  1), `status` (select: draft/active/inactive, defaults to draft).
- "Add Component" row inside the dialog: `component_sku`, `quantity_per`
  (float), `scrap_pct` (float 0–0.99), `seq` (int). Multiple rows allowed.
- Submit calls `createBom(body)`. On success: toast "BOM created", invalidate
  `["mfg", "boms"]`, close dialog.
- Validation: `product_sku` required; `output_quantity` must be ≥ 1;
  `quantity_per` must be > 0; `scrap_pct` in `[0, 1)`.

**Detail/edit panel** (shown when a BOM is selected):

- Displays BOM header fields; `name` and `status` are editable inline.
  - Name: `<Input>` with an "Update" button → `updateBom(bomId, { name })`.
  - Status: `<Select>` → `updateBom(bomId, { status })`. Transitions `active →
    inactive` may return 409 (open work order); display the error message from
    the response body.
- **Components grid**: editable table of `BomComponentOut` rows. Each row
  allows editing `quantity_per` and `scrap_pct` inline (blur-to-save via
  `PATCH /boms/{id}` with the updated component list — the backend PATCH merges
  the component array). "Delete" button per row (sets `quantity_per=0` on the
  component row, which the service interprets as removal — or calls a dedicated
  component-delete endpoint if MFG-011 exposes one; see A3).
- "Add Component" button appends a blank row; saving triggers `PATCH /boms/{id}`
  with the full updated components list.
- "Delete BOM" button (danger): confirmation dialog → `deleteBom(bomId)`. 409
  response ("referenced by open work order") shown as an inline error, not a
  toast, so the admin can read it without it auto-dismissing.

**Explosion preview panel** (below components grid, always visible when a BOM
is selected):

```
Build qty: [  10  ]  [Explode]
─────────────────────────────────────────────
Component SKU    Required Qty    Depth
──────────────── ─────────────── ─────
SKU-A            20              1
SKU-C            60              2
```

- `buildQty` state (default: 1); user changes value in an `<Input type="number">`.
- On "Explode" click (or on change if the query is instant enough): calls
  `explodeBom(bomId, buildQty)` — implemented as a `useQuery` with
  `{ queryKey: ["mfg", "boms", bomId, "explode", buildQty], queryFn: () => explodeBom(bomId, buildQty), enabled: !!selectedBomId }`.
- The query refetches whenever `buildQty` changes (React Query deduplicates by
  key). No button is strictly needed — auto-fetch on `buildQty` change is
  preferred UX ("live explode" stated in ticket).
- Results are rendered in a compact `<Table>` with color-coding by depth
  (depth 1 = normal weight, depth 2+ = muted text, indented by depth × 0.5rem).
- Empty result (BOM with no components) shows a muted "No components" message.
- 409 from explosion (cycle detected or depth exceeded) shows an inline error
  badge rather than a toast.

### 5.3 Work Center Tab — `<WorkCenterTab />`

- `useQuery(["mfg", "work-centers"], () => listWorkCenters())` populates a
  `<Table>` with columns: `name`, `capacity_per_hour`, `cost_per_hour_cents`
  (formatted as currency: `$X.XX / hr`), `status` (badge).
- "New Work Center" button → create dialog with fields: `name`, `capacity_per_hour`
  (int ≥ 1), `cost_per_hour_cents` (int ≥ 0, displayed as a dollars-and-cents
  `<Input type="number" step="0.01">`; multiply by 100 before sending), `status`.
- Inline editing on row: click a row to expand an edit form with the same fields.
  Save calls `updateWorkCenter(wcId, body)`. Deactivating a work center
  referenced by an open routing task returns 409; surface as inline error.
- No delete endpoint is exposed for work centers (they may be referenced
  historically); status `"inactive"` is the retirement mechanism.

### 5.4 Routing Tasks Tab — `<RoutingTab />`

- BOM selector: a `<Select>` listing all BOMs (re-uses the `["mfg", "boms"]`
  query; shows `{name} ({product_sku})`). Selecting a BOM loads its routing
  tasks via `useQuery(["mfg", "routing-tasks", selectedBomId], () => listRoutingTasks(selectedBomId), { enabled: !!selectedBomId })`.
- Task list: `<Table>` with columns: `seq`, `name`, `work_center_name` (from
  `WorkCenterOut` resolved by `work_center_id`), `setup_minutes`,
  `run_minutes_per_unit`, actions (Edit / Delete).
- "Add Task" button → dialog with fields: `work_center_id` (select from active
  work centers), `name`, `setup_minutes`, `run_minutes_per_unit`, `seq`.
  Submit calls `createRoutingTask(bomId, body)`.
- Edit: populates a dialog pre-filled from the existing task; save calls
  `updateRoutingTask(bomId, taskId, body)`.
- Delete: confirmation → `deleteRoutingTask(bomId, taskId)`.
- **Routing cost estimate** (read-only display below the task list):
  derived client-side as `sum(setup_minutes) + sum(run_minutes_per_unit * buildQty)` total
  minutes, converted to cost using `sum(run_minutes_per_unit / 60 * cost_per_hour_cents +
  setup_minutes / 60 * cost_per_hour_cents)`. The client-side estimate is
  approximate; the authoritative value comes from `estimate_routing_cost` on the
  backend (MFG-005), but a dedicated UI endpoint for this is not in scope for
  MFG-006. The display updates reactively as task or build-qty changes.

### 5.5 BOM status transitions and error surface

`active → inactive` is blocked when an open work order exists (409 from the
backend, detail: `"BOM is referenced by an open work order"` per MFG-004
Section 5.6). The UI must surface this as an inline callout
(`<Alert variant="destructive">`) rather than a dismissible toast, because the
admin must understand the blocker before they can act.

`draft → active` activates the BOM and makes it eligible for work orders and
MRP; no guard fires. The UI shows a confirmation dialog for this transition
("Activating this BOM will make it available to work orders. Continue?") to
prevent accidental activation.

### 5.6 `product_sku` resolution for display

The BOM list shows `product_sku` as a raw SKU string. If the catalog integration
(MFG-013) is eventually available, the UI could resolve a display name. For
MFG-006 scope, the raw SKU is displayed. A tooltip can show the SKU in full when
truncated.

### 5.7 Empty states

- No BOMs exist: `<EmptyState icon=<Factory> title="No BOMs defined" description="Create a BOM to track component requirements for finished goods." />`.
- No work centers: `<EmptyState icon=<Wrench> title="No work centers" />`.
- No routing tasks for selected BOM: inline muted text "No routing tasks for
  this BOM yet."
- `EmptyState` is imported from `@/components/shared/EmptyState` (same as
  `InventoryAdmin.tsx:18`).

### 5.8 Loading and error states

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

This ticket is a pure frontend ticket. There is no backend business logic in
MFG-006 itself. All data mutations flow through MFG-011 router → MFG-004/MFG-005
service layer, which are already SECOPS-007 clean (no `dev_mode` branches in
service code per MFG-004 Section 7). The UI page code runs identically in dev
(DDB local, port 8001) and production.

### Idempotency

Idempotency for BOM creation (deterministic `bom_id = sha256(correlation_id)`)
is a service-layer concern (MFG-004 Section 7). The UI does not supply a
`correlation_id` on create — it submits the form once and handles 409 responses
as duplicate-creation errors ("A BOM with this identity already exists"). For
manual admin interaction this is sufficient; automated clients can supply
`correlation_id` via the API directly.

### Security

**CSRF**: All POST/PATCH/DELETE calls from `frontend/src/api/client.ts` include
the `x-csrf-token` header (read from the `ui_csrf` cookie, attached at
`frontend/src/api/client.ts:179`). For manufacturing endpoints the backend
enforces CSRF via `enforce_cookie_csrf` (`app/auth/policy.py:72–96`), which is
called from `require_admin_or_root_csrf` (`app/auth/policy.py:100–106`). CSRF is
NOT enforced in `app/auth/deps.py` — that file only contains session
extraction/validation logic. No additional frontend CSRF handling is required.

**Auth**: The page hard-gates on `canAccessGeneralAdminControls(accessToken)`
(client-side) and every backend endpoint gates on `require_admin_or_root_csrf`
(server-side). A non-admin user who navigates directly to `/admin/manufacturing`
sees the access-denied `<EmptyState>` without any data being fetched.

**Input sanitization**: All SKU and name inputs are plain strings passed
directly to the backend Pydantic models. `BomHeaderIn.product_sku` has
`max_length=256` and `min_length=1` (MFG-003), rejecting empty or overlong
strings with a 422. The UI `<Input>` elements have no special sanitization —
the backend is the authoritative validator.

**Explosion depth**: The `explode_bom` endpoint returns 409 when a cycle or
depth limit is hit (MFG-004 Section 5.7). The UI surfaces this as an inline
error and does not retry automatically.

## 10. Open Questions / Assumptions

**A1 — Routing task storage location**: MFG-001 open question 7 assumes
routing tasks live on `T.mfg_boms` as `SK=TASK#{seq:04d}` rows. If MFG-005
resolves this differently (e.g., tasks on `T.mfg_work_centers`), the routing
endpoint URLs in Section 4 must change accordingly, and the `<RoutingTab>`
BOM-selector UX changes to a work-center-selector UX. This spec proceeds with
the per-BOM assumption (the OFBiz WorkEffortGoodStandard model).

**A2 — `RoutingTaskIn` / `RoutingTaskOut` models**: Not yet confirmed in the
MFG-003 spec text. The shapes in Section 4.3 are inferred from MFG-005's
description. Implementation must verify these models against whatever MFG-003
actually defines and update TypeScript types accordingly.

**A3 — Component update mechanism**: The spec assumes BOM component rows are
updated by PATCHing the BOM header with a full replacement `components` array.
If MFG-011 exposes individual component PATCH/DELETE endpoints (e.g.,
`PATCH /boms/{id}/components/{seq}`), the UI can call those instead. This is
preferred for atomicity. Assumption: the MFG-011 spec for BOM update handles
only `name` and `status` (per MFG-004 Section 4.1 `update_bom` signature) and
component editing requires a separate endpoint not yet specified. For MFG-006
MVP, the "edit components" UI can use `DELETE + POST` (delete old BOM,
re-create with updated components) or be limited to adding new components only.
The safest MVP approach: provide "add component" (POST new BOM with updated
component list) and disable inline component editing until a dedicated endpoint
is available.

**A4 — `work_center_name` in `RoutingTaskOut`**: To avoid a per-task N+1 fetch
for work-center names, the spec assumes `RoutingTaskOut` carries a
`work_center_name` denormalized string. If the backend omits this, the frontend
resolves names from the pre-fetched `WorkCenterOut` list by `work_center_id`.
The TypeScript type marks it `optional` to handle both cases.

**A5 — BOM list response shape**: The spec assumes `GET /ui/manufacturing/boms`
returns a plain `BomOut[]` array (mirroring `GET /ui/inventory/low-stock`'s
`{ items: [] }` wrapper vs. the array pattern). The MFG-011 spec says "list
BOMs" but does not specify the exact wrapper. If the backend wraps the array in
`{ boms: [] }`, the `listBoms` endpoint wrapper and the TypeScript type need the
`BomListResp` wrapper type. Both shapes are defined in Section 3.1; the
implementation picks the correct one once MFG-011 is confirmed.

**A6 — Routing cost estimate in the UI**: Section 5.4 specifies a client-side
approximate routing cost estimate. The authoritative estimate lives in
`manufacturing_routing.estimate_routing_cost` (MFG-005). If MFG-011 exposes a
dedicated `GET /ui/manufacturing/boms/{id}/routing-cost?build_qty=N` endpoint,
the UI should prefer that over the client-side approximation. Decision deferred
to MFG-011 implementation.
