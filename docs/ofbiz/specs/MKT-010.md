# MKT-010 — Tracking codes (visit + order + redemption attribution)

## 1. Summary & Goal

MKT-010 creates `app/services/tracking_codes.py` — the OFBiz `TrackingCode` /
`TrackingCodeVisit` / `TrackingCodeOrder` analog for the testlogon marketing
module. It delivers:

- **`create_tracking_code(owner_id, data)`** — creates a code META row keyed on a
  globally-unique slug (`TRACK#{code_slug}` / `META`). Duplicate slugs are
  rejected with HTTP 409; identical retries (same slug + same campaign_id) are
  idempotent via `attribute_not_exists(pk)` conditional put.
- **`record_visit(code_slug, party_id?, referrer?)`** — appends a VISIT child row
  (`TRACK#{code_slug}` / `VISIT#{ts:010d}#{nonce}`) and atomically increments
  `visit_count` on the META row. Visits are always appended (never deduplicated)
  so time-series analytics are accurate. Anonymous visits use `party_id="anon"`.
- **`record_order(code_slug, order_id, campaign_id)`** — appends an ORDER child row
  (`TRACK#{code_slug}` / `ORDER#{order_id}`) idempotently. A second call with the
  same `order_id` is silently ignored (no double-count on webhook replay).
- **`get_tracking_code(code_slug)`** — point lookup on the META row; returns `None`
  for unknown slugs.
- **`list_tracking_codes_for_campaign(campaign_id)`** — queries the
  `ByCampaignCreatedAt` GSI to enumerate all codes for a campaign.
- **`link_promo_redemption(code_slug, promo_code_id, user_id)`** — records the
  linkage between a promo redemption and a tracking code on the tracking-codes
  side only. The promo code's `current_uses` counter and `REDEEM#` rows in
  `T.promo_codes` remain the authoritative source of truth; this function writes
  nothing to `T.promo_codes`.

The module is gated on `S.marketing_campaigns_enabled`. With the flag off, all
mutating calls raise HTTP 403 immediately. Read operations (`get_tracking_code`,
`list_tracking_codes_for_campaign`) are unaffected by the flag.

The module produces no new billing writes and never calls
`billing_shared.new_ledger_entry`. Attribution figures are read-only over
existing rows.

## 2. Context & Current State

### Existing analogues and patterns cited

**Slug uniqueness — `app/services/promo_codes.py:85`**
`create_promo_code` (verified: `promo_codes.py:85`) enforces global code
uniqueness via a `ByCodeString` GSI lookup before inserting (verified:
`promo_codes.py:141–147`). Tracking codes use a simpler path:
the PK itself (`TRACK#{code_slug}`) is globally scoped (no owner prefix in the
PK), so a `ConditionExpression="attribute_not_exists(pk)"` conditional put on
`(PK=TRACK#{code_slug}, SK=META)` is sufficient. A
`ConditionalCheckFailedException` means the slug is taken.

**Conditional put idempotency — `app/services/cart_reminders.py:198–211`**
`_mark_token_consumed` (verified: `cart_reminders.py:198`) uses the canonical pattern:
```python
T.cart_reminder_config.put_item(
    Item={...},
    ConditionExpression="attribute_not_exists(pk)",
)
```
On collision `ClientError` is raised with code `"ConditionalCheckFailedException"`.
MKT-010 reuses this pattern for both slug-uniqueness enforcement (create) and
order-idempotency (record_order keyed on `ORDER#{order_id}`).

**Visit/click row append — `app/services/affiliate_links.py:190–235`**
`record_click` (line 190) appends an immutable child row (PK=`link_id`,
SK=`click_id` — a random `clk_<uuid12>` string, **not** a timestamp-based key)
then calls `_increment_link_clicks` (line 258) via an atomic
`update_item(..., UpdateExpression="SET click_count = if_not_exists(click_count, :zero) + :one")`
(verified: `affiliate_links.py:260`). The `AffiliateClicks` table therefore uses
a UUID sort key. MKT-010 diverges here: VISIT rows use
`SK=VISIT#{ts:010d}#{nonce}` (ten-digit zero-padded ts + 8-hex nonce from
`secrets.token_hex(4)`) so visits are naturally time-ordered in the table's
`ByCodeTs` GSI; the atomic counter increment reuses the `if_not_exists` idiom
from `_increment_link_clicks`.

**Atomic counter increment — `app/services/promo_codes.py:418–429`**
`redeem_promo_code` increments `current_uses` atomically (verified:
`promo_codes.py:418–429`). The function has two branches: when `max_uses > 0`
it adds a `ConditionExpression=Attr("current_uses").lt(max_uses)`; the
unconditional branch (lines 425–429) is the closer analogue:
```python
_tbl().update_item(
    Key={"pk": _promo_pk(code_id), "sk": "META"},
    UpdateExpression="SET current_uses = current_uses + :one, updated_at = :ts",
    ExpressionAttributeValues={":one": 1, ":ts": now_ts()},
)
```
Note that `promo_codes.py` does not use `if_not_exists` because the `META` row
is always written with `current_uses=0` at create time. MKT-010's visit/order
counters add `if_not_exists(visit_count, :zero) + :one` because a cold META row
written in the same transaction may not yet have the counter attribute present
(defensive guard consistent with `affiliate_links.py:260`).

**Cart-recovery redirect — `app/routers/shoppingcart.py:268–282`**
The public no-auth `GET /recover/{token}` endpoint (verified: `shoppingcart.py:268`)
calls a service function and returns `RedirectResponse(url=..., status_code=302)`.
The public tracking visit endpoint `GET /ui/marketing/t/{code_slug}` (MKT-011)
follows exactly this shape: call `record_visit`, then 302-redirect to
`S.public_base_url` (verified: `settings.py:349`) plus the campaign's
`destination_url` stored on the META row.

**Promo redemption stats — `app/services/promo_codes.py:462–482`**
`get_promo_stats(code_id)` (verified: `promo_codes.py:462`) queries `T.promo_codes`
SK-prefix `REDEEM#` and aggregates `total_redemptions` and `total_discount_cents`. The
`link_promo_redemption` function in MKT-010 appends a `PROMO#{promo_code_id}`
row to the tracking code's partition so attribution reads can find the linkage
without touching `T.promo_codes` at all.

**Deterministic id scheme — `app/services/marketing_campaigns.py` (MKT-004 spec)**
MKT-004 uses `sha256(owner_id + "\x00" + name + "\x00" + created_bucket)[:24]`
for campaign ids (null-byte separator, per `docs/ofbiz/specs/MKT-004.md:158`).
Tracking codes do not use a deterministic hash for the META row because the
caller-supplied `code_slug` is itself the primary key (globally unique by
construction). The `nonce` in VISIT sort keys uses `secrets.token_hex(4)`
(8 hex chars) to guarantee uniqueness even when two visits arrive in the same
second.

**Promo code internals are untouched**
`redeem_promo_code` (verified: `promo_codes.py:398`) atomically increments
`current_uses` and writes a `REDEEM#` row in `T.promo_codes`. MKT-010 never
calls `redeem_promo_code`. The promo side of the attribution flow is:
1. The caller (checkout handler) calls `redeem_promo_code` as before — unchanged.
2. After successful redemption, the caller optionally calls
   `tracking_codes.link_promo_redemption(code_slug, promo_code_id, user_id)`
   which writes a lightweight cross-reference row **only** in `T.tracking_codes`.
3. `compute_attribution` (MKT-005) reconciles promo totals by calling
   `promo_codes.get_promo_stats(promo_code_id)` — still the authoritative source.

**Feature flag guard pattern — `app/services/marketing_campaigns.py` (MKT-004)**
Per the MKT-004 spec (see `docs/ofbiz/specs/MKT-004.md:74–82`), every mutating service
function begins:
```python
if not S.marketing_campaigns_enabled:
    raise HTTPException(status_code=403, detail="marketing_campaigns disabled")
```
MKT-010 follows the same pattern.

**`audit_event` pattern — `app/services/alerts.py:644`**
Signature (verified: `alerts.py:644`): `audit_event(event: str, user_sub: str, request=None, **fields)`.
MKT-010 emits one audit event on `create_tracking_code` (event
`"tracking_code.created"`) and one on `record_order` (event
`"tracking_code.order_attributed"`), both best-effort (try/except around the
call so attribution never blocks on an audit failure).

## 3. Data Model

MKT-010 writes exclusively to `T.tracking_codes` — the `TrackingCodes` DynamoDB
table defined in MKT-002 and its `scripts/local-ddb-init.py` `TableDef`.

### `TrackingCodes` table (defined by MKT-002)

Default name: `TrackingCodes` (env `DDB_TRACKING_CODES`).
Table handle: `T.tracking_codes` (wired by MKT-002 in `app/core/tables.py`).
`scripts/local-ddb-init.py` `TableDef`:

```python
TableDef(
    _resolve_table_name(S.tracking_codes_table_name, "TrackingCodes"),
    "pk",
    "sk",
    gsi=[
        {"index_name": "ByCampaignCreatedAt",
         "partition_key": "campaign_id", "sort_key": "created_at"},
        {"index_name": "ByCodeTs",
         "partition_key": "code_slug", "sort_key": "ts"},
    ],
    attr_types={"created_at": "N", "ts": "N"},
),
```

Both GSI sort keys are numeric (`"N"`) — omitting `attr_types` causes
`ValidationException` on integer-value GSI queries (CLAUDE.md DynamoDB gotcha).

### Row shapes

#### Code META row

| Field | Type | Value |
|-------|------|-------|
| `pk` | S | `TRACK#{code_slug}` |
| `sk` | S | `META` |
| `code_slug` | S | the slug (3–50 chars, `[A-Za-z0-9_-]`) |
| `campaign_id` | S | owning campaign id |
| `owner_id` | S | `user_sub` of the creator |
| `destination_url` | S | redirect target for `GET /t/{code_slug}` |
| `created_at` | N | Unix timestamp (appears in `ByCampaignCreatedAt` GSI) |
| `visit_count` | N | denormalized counter, incremented atomically |
| `order_count` | N | denormalized counter, incremented atomically |

`campaign_id` is the `ByCampaignCreatedAt` GSI partition key. Every META row
must write this attribute for the GSI to index it.

#### Visit row

| Field | Type | Value |
|-------|------|-------|
| `pk` | S | `TRACK#{code_slug}` |
| `sk` | S | `VISIT#{ts:010d}#{nonce}` |
| `code_slug` | S | (denormalized for `ByCodeTs` GSI) |
| `ts` | N | Unix timestamp — GSI sort key in `ByCodeTs` |
| `party_id` | S | user sub or `"anon"` for anonymous visits |
| `referrer` | S | optional, truncated to 500 chars |

`ts` is the `ByCodeTs` GSI sort key; it must be declared `"N"` in `attr_types`.

#### Order row

| Field | Type | Value |
|-------|------|-------|
| `pk` | S | `TRACK#{code_slug}` |
| `sk` | S | `ORDER#{order_id}` |
| `order_id` | S | from the commerce order service |
| `attributed_at` | N | Unix timestamp |
| `campaign_id` | S | denormalized from META for query convenience |

The ORDER SK `ORDER#{order_id}` makes `record_order` idempotent: a second
conditional put on the same SK raises `ConditionalCheckFailedException` which is
caught and silently ignored.

#### Promo-linkage row

| Field | Type | Value |
|-------|------|-------|
| `pk` | S | `TRACK#{code_slug}` |
| `sk` | S | `PROMO#{promo_code_id}#{user_id}` |
| `promo_code_id` | S | the linked promo code |
| `user_id` | S | the redeeming user |
| `linked_at` | N | Unix timestamp |

This row records the fact that a promo redemption was attributed to this tracking
code. `compute_attribution` (MKT-005) may query these rows by SK-prefix
`PROMO#` to count redemptions attributed via this code. The authoritative
discount figures still come from `promo_codes.get_promo_stats`.

## 4. API / Service Design

### 4.1 Service module: `app/services/tracking_codes.py`

All functions live in this new file. They import `T` from `app.core.tables` and
`S` from `app.core.settings`. No circular imports: this module imports from
`app.services.promo_codes` (read-only validation) and `app.services.alerts`
(audit, best-effort).

#### Key helpers

```python
import hashlib, secrets
from boto3.dynamodb.conditions import Key
from botocore.exceptions import ClientError
from app.core.tables import T
from app.core.settings import S
from app.core.time import now_ts
from fastapi import HTTPException

def _pk(code_slug: str) -> str:
    return f"TRACK#{code_slug}"

def _require_flag() -> None:
    if not S.marketing_campaigns_enabled:
        raise HTTPException(status_code=403, detail="marketing_campaigns disabled")

def _tbl():
    return T.tracking_codes
```

#### `create_tracking_code`

```python
def create_tracking_code(
    owner_id: str,
    data: TrackingCodeCreateIn,       # from app.models
    destination_url: str = "",
) -> dict:
```

Behavior:
1. `_require_flag()`
2. Validate that `data.campaign_id` references a known marketing campaign via
   `marketing_campaigns.get_campaign(owner_id, data.campaign_id)` — returns 404
   if not found.
3. Build the META item with `pk=_pk(data.code_slug)`, `sk="META"`,
   `campaign_id=data.campaign_id`, `owner_id=owner_id`,
   `created_at=now_ts()`, `visit_count=0`, `order_count=0`,
   `destination_url=destination_url`.
4. `T.tracking_codes.put_item(Item=item, ConditionExpression="attribute_not_exists(pk)")`
5. On `ConditionalCheckFailedException`: raise `HTTPException(409, "Tracking code slug already exists")`.
6. Emit `audit_event("tracking_code.created", owner_id, code_slug=data.code_slug, campaign_id=data.campaign_id)` (best-effort try/except).
7. Return the item dict.

**Idempotency note**: unlike MKT-004 campaigns, tracking code slugs have no
hourly-bucket dedup window. The caller supplies the slug and owns collision
handling. A 409 means "choose a different slug".

#### `get_tracking_code`

```python
def get_tracking_code(code_slug: str) -> Optional[dict]:
```

Single `get_item(Key={"pk": _pk(code_slug), "sk": "META"})`. Returns `None` for
unknown slugs. No flag guard (reads always work).

#### `list_tracking_codes_for_campaign`

```python
def list_tracking_codes_for_campaign(
    campaign_id: str,
    limit: int = 50,
) -> list[dict]:
```

Queries `ByCampaignCreatedAt` GSI:
```python
T.tracking_codes.query(
    IndexName="ByCampaignCreatedAt",
    KeyConditionExpression=Key("campaign_id").eq(campaign_id),
    ScanIndexForward=False,  # newest first
    Limit=limit,
)
```
Returns `Items` (META rows only; VISIT/ORDER rows do not write `campaign_id` on
the GSI partition key, so they do not appear here).

#### `record_visit`

```python
def record_visit(
    code_slug: str,
    party_id: Optional[str] = None,
    referrer: Optional[str] = None,
) -> None:
```

Behavior:
1. No flag guard — visits must be recordable even if the flag is toggled off
   after a campaign is launched (in-flight links must not silently fail).
   Specifically, the public `GET /t/{code_slug}` endpoint in MKT-011 must record
   the visit regardless of flag state (visit recording is read-only for the user).
2. Verify the META row exists via `get_tracking_code(code_slug)`. If `None`,
   silently return (unknown slug — do not leak existence via error).
3. Build the VISIT item:
   - `ts = now_ts()`
   - `nonce = secrets.token_hex(4)` (8 hex chars)
   - `sk = f"VISIT#{ts:010d}#{nonce}"`
   - `party_id = party_id or "anon"`
   - `referrer = (referrer or "")[:500]` or omitted if empty
4. `T.tracking_codes.put_item(Item=visit_item)` (no condition needed — the
   nonce guarantees uniqueness).
5. Atomically increment `visit_count` on META:
   ```python
   T.tracking_codes.update_item(
       Key={"pk": _pk(code_slug), "sk": "META"},
       UpdateExpression="SET visit_count = if_not_exists(visit_count, :z) + :one",
       ExpressionAttributeValues={":one": 1, ":z": 0},
   )
   ```
   Wrapped in `try/except` — a counter failure must not prevent the redirect.

#### `record_order`

```python
def record_order(
    code_slug: str,
    order_id: str,
    campaign_id: str = "",
) -> bool:
    """Returns True on first attribution, False on replay (already attributed)."""
```

Behavior:
1. No flag guard (see rationale for `record_visit`).
2. Build the ORDER item with `pk=_pk(code_slug)`, `sk=f"ORDER#{order_id}"`,
   `attributed_at=now_ts()`, `campaign_id=campaign_id`.
3. Conditional put with `ConditionExpression="attribute_not_exists(sk)"`.
4. On `ConditionalCheckFailedException`: return `False` (already attributed).
5. On success: increment `order_count` on META (same `update_item` + try/except
   pattern as `record_visit`).
6. Emit `audit_event("tracking_code.order_attributed", ...)` best-effort.
7. Return `True`.

**Why `attribute_not_exists(sk)` not `attribute_not_exists(pk)`**: both the META
row and the ORDER row share the same `pk = TRACK#{code_slug}`. The uniqueness
condition must target the sort key to distinguish them.

#### `link_promo_redemption`

```python
def link_promo_redemption(
    code_slug: str,
    promo_code_id: str,
    user_id: str,
) -> None:
```

Behavior:
1. `_require_flag()`
2. `T.tracking_codes.put_item(Item={pk, sk=f"PROMO#{promo_code_id}#{user_id}", ...})`
   with no condition (multiple redemptions by different users are allowed; a
   user re-redeeming the same promo through the same code is a no-op since the
   SK is deterministic).

## 5. Detailed Behavior & Edge Cases

### Slug collision vs. duplicate create

Two distinct cases exist:
- **Different owners, same slug**: always a 409 — slugs are globally unique
  (PK has no owner namespace). The owner must choose a different slug.
- **Same owner, same slug, same campaign_id (retry)**: the conditional put raises
  `ConditionalCheckFailedException`. The service fetches the existing META row
  and returns it (idempotent retry). This only applies if the caller catches the
  409 from the HTTP layer and retries — at the service level, the existing item
  is returned directly.

The slug is case-sensitive. `SUMMER2024` and `summer2024` are distinct slugs.

### Visit count accuracy under concurrent requests

`record_visit` uses `if_not_exists(visit_count, :z) + :one` which is atomic at
the DynamoDB item level. Under high concurrent load the visit counter is
eventually consistent (DynamoDB applies each conditional update atomically) but
there is no hot-key concern unless a single slug receives thousands of
requests per second — acceptable for the MVP.

The VISIT child row put (no condition) is idempotent in the sense that each
invocation of `record_visit` generates a fresh nonce, so two concurrent calls
each write their own distinct row. There is no "exactly once" semantic for
visits — that would require client-side dedup.

### Order idempotency on webhook replay

Commerce order webhooks (or retry loops) may call `record_order` multiple times
for the same `order_id`. The `attribute_not_exists(sk)` condition on
`ORDER#{order_id}` prevents double-counting. The `order_count` counter is only
incremented on the first successful attribution (the `try/except` on the counter
increment is inside the success branch after the conditional put succeeds).

### Promo reconciliation guarantee

`link_promo_redemption` does NOT increment `order_count` or any counter — it is
purely a cross-reference row. The promo redemption count visible to the
attribution rollup (MKT-005) comes from `promo_codes.get_promo_stats(code_id)`
which queries `REDEEM#` rows in `T.promo_codes`. The acceptance criterion states
"promo redemption counts attributed to a campaign reconcile to
`promo_codes.get_promo_stats`" — this is satisfied because MKT-005's
`compute_attribution` calls `get_promo_stats` directly; the PROMO linkage rows
in `T.tracking_codes` are supplementary metadata, not a counter.

### `destination_url` validation

The `destination_url` field is stored as-is; the router should validate it is
either empty or starts with `https?://` or `/` (relative path). A blank
`destination_url` causes the public endpoint to redirect to `/` (storefront
root), which is a safe fallback. Full URL validation is deferred to MKT-011.

### Cart reminder integration

`app/services/cart_reminders.py:214` (`generate_recovery_link`) creates a
recovery URL that can optionally embed a `utm_code` query parameter carrying a
tracking code slug. MKT-010 itself does not modify `cart_reminders.py`. The
integration is:
- The MKT-009 `send_campaign` function (MKT-009 spec `docs/ofbiz/specs/MKT-009.md`)
  embeds the campaign's tracking-code-tagged link in message bodies.
- If a campaign is linked to cart reminders (future work), the recovery link
  would carry `?tc={code_slug}`, and the recovery handler would call
  `record_visit` after redirect.
- This path is additive and does not require changes to `cart_reminders.py` for
  the MKT-010 MVP.

### No destination_url on anonymous bot traffic

`record_visit` is called before the redirect; if it throws (e.g., the table is
not yet initialized), the router must still attempt the redirect. The router
wraps `record_visit` in a try/except so a recording failure is logged but never
surfaces as a 500 to the browser.

| `record_order` | proceeds (no flag guard — see §5) |
| `get_tracking_code` | proceeds |
| `list_tracking_codes_for_campaign` | proceeds |

The rationale for no flag guard on `record_visit`/`record_order`: once a
campaign with a tracking code is live and links have been emailed to users, the
flag may be toggled for maintenance without wanting to lose attribution data
for in-flight clicks. Reads and attribution appends are always safe.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

MKT-010 uses only DynamoDB (via `T.tracking_codes`) and the existing
`audit_event` function. Both are DDB-backed in dev (moto in-process) and prod
(real DynamoDB) without any `if S.dev_mode:` branch. The
`app/services/alerts.audit_event` function at `app/services/alerts.py:644` is
itself already dev/prod-aware; MKT-010 does not need to branch on `dev_mode`.

There is no S3, SES, KMS, or any other AWS service touched. SECOPS-007 parity is
trivially satisfied.

### Idempotency summary

| Operation | Idempotency mechanism |
|-----------|----------------------|
| `create_tracking_code` | `attribute_not_exists(pk)` on `META` row; collision → 409 or return-existing on retry |
| `record_visit` | No dedup — each call appends a new row with a unique nonce |
| `record_order` | `attribute_not_exists(sk)` on `ORDER#{order_id}` |
| `link_promo_redemption` | Deterministic SK `PROMO#{promo_code_id}#{user_id}`; second put is a silent overwrite (same data) |

### Security

- **Slug enumeration**: `get_tracking_code` returns `None` for unknown slugs;
  the public endpoint silently redirects to `/` rather than returning a 404 that
  would confirm slug non-existence. This matches the affiliate link pattern in
  `app/services/affiliate_links.py`.
- **Referrer truncation**: stored at max 500 chars to prevent oversized DDB items
  (DDB item limit is 400KB; referrers are rarely > 500 chars).
- **party_id from auth context**: the public endpoint cannot verify party_id;
  it passes `party_id=None` (stored as `"anon"`). Authenticated endpoints that
  call `record_visit` directly (future dashboard testing) may pass the session
  user_sub.
- **No PII in sort keys**: VISIT sort keys contain only a timestamp and a random
  nonce. `party_id` is stored as a field, not in the key, so user subs do not
  appear in index scans by default.
- **Slug injection**: `TrackingCodeCreateIn.code_slug` regex
  `^[A-Za-z0-9_-]{3,50}$` (MKT-003 spec, `docs/ofbiz/specs/MKT-003.md:89`)
  blocks path separators, query characters, and whitespace. Safe to embed in
  `GET /t/{code_slug}` without URL-encoding.

## 10. Open Questions / Assumptions

1. **`destination_url` in `TrackingCodeCreateIn`**: The MKT-003 spec
   (`docs/ofbiz/specs/MKT-003.md:288–305`) does not include `destination_url`
   in `TrackingCodeCreateIn` or `TrackingCodeOut`. This spec adds it as an
   optional field because the public redirect endpoint needs a target URL. If
   MKT-011 prefers to derive the destination from the linked campaign's settings
   (e.g., `campaign.landing_page_url`), `destination_url` on the tracking code
   can be made optional with the campaign field as fallback. **Assumption**: it
   is more flexible to allow per-code destination override.

2. **`record_visit` flag guard**: The spec opts to skip the flag guard for visit
   recording so in-flight campaign links keep working after a flag toggle.
   **Assumption**: this is the correct UX. If strict flag enforcement is
   required (e.g., for compliance), `record_visit` would need the guard and the
   public endpoint would 404 on unknown/flag-off slugs.

3. **`record_order` callsite ownership**: The ticket states the order attribution
   hook is "non-invasive". **Assumption**: the callsite lives in
   `app/services/commerce_order_service.py` (or equivalent) as a best-effort
   call after the order is persisted, gated by `S.marketing_campaigns_enabled`.
   The tracking-code slug must be passed in the order creation request context
   (e.g., from a cookie or query parameter set when the user clicked a
   `GET /t/{code_slug}` link). The exact mechanism for passing the slug from
   the visit to the order is out of scope for MKT-010 and deferred to MKT-011.

4. **Promo reconciliation counting method**: `compute_attribution` (MKT-005)
   counts promo redemptions via `promo_codes.get_promo_stats`. The PROMO linkage
   rows in `T.tracking_codes` are supplementary. **Assumption**: there is no
   requirement to count "only the redemptions that came via this tracking code"
   vs. "all redemptions of the linked promo". If per-code promo attribution is
   needed, the linkage rows support it, but MKT-005 currently does not use them.

5. **Visit deduplication**: visits are always appended (no dedup). For fraud
   prevention or unique-visit metrics, a visitor hash (like
   `app/services/affiliate_links.py:205` which hashes `IP:UA`) could be added.
   **Assumption**: this is deferred; raw visit counts are sufficient for MVP.

6. **`list_tracking_codes_for_campaign` ownership check**: the function queries
   by `campaign_id` without verifying the caller owns the campaign.
   **Assumption**: the router (MKT-011) enforces ownership before calling this
   function, matching the pattern in `app/routers/ads.py:60–65`
   (`_require_account_owner`).

7. **`link_promo_redemption` callsite**: the ticket states the hook is
   "non-invasive" via the **existing** `promo_codes.redeem_promo_code`.
   **Assumption**: after `redeem_promo_code` returns successfully, the caller
   retrieves the tracking code slug from the request context (session cookie or
   query parameter) and calls `tracking_codes.link_promo_redemption` best-effort.
   MKT-010 does not modify `promo_codes.redeem_promo_code`.
