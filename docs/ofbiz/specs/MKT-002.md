# MKT-002 — Marketing settings, feature flag & table handles

## 1. Summary & Goal

MKT-002 is a pure-scaffolding chore ticket. It lands the infrastructure that every subsequent MKT ticket depends on before any service logic is written:

1. **Feature flag** — `S.marketing_campaigns_enabled` (env `MARKETING_CAMPAIGNS_ENABLED`, default **off**) added to `app/core/settings.py`, following the exact boolean pattern at line 821 (`cart_reminders_enabled`). With the flag off the ads platform, promo codes, and cart reminders are byte-for-byte unchanged.
2. **Table-name settings** — four new string settings mirroring `promo_codes_table_name` at `app/core/settings.py:1995`: `marketing_campaigns_table_name`, `contact_lists_table_name`, `party_segments_table_name`, `tracking_codes_table_name`.
3. **DynamoDB table definitions** — four `TableDef` entries appended to `scripts/local-ddb-init.py:_table_defs()`, following the `_resolve_table_name(S.<key>, "<default>")` pattern and declaring every numeric GSI sort key with `attr_types={"<key>": "N"}` (the CLAUDE.md gotcha).
4. **Table handles** — four `_safe_table(...)` entries added to the `Tables` dataclass and the `T = Tables(...)` singleton in `app/core/tables.py`, mirroring `T.promo_codes` at line 448.
5. **Smoke test** — a hermetic offline pytest that imports `T` and `S` and asserts all four handles are non-None and the flag defaults to `False`.

No service logic, router, or Pydantic model changes are made in this ticket. Every implementation decision about table schemas, GSIs, and naming is already recorded in MKT-001 (`docs/ofbiz/specs/MKT-001.md`, Section 3 and Section 6); this spec translates those decisions into exact file changes.

## 3. Data Model

The four table schemas are taken verbatim from MKT-001 Section 3 (`docs/ofbiz/specs/MKT-001.md`). This section re-states them in the exact form needed for `scripts/local-ddb-init.py` `TableDef` entries.

### Table: MarketingCampaigns

Default name: `MarketingCampaigns` (env `DDB_MARKETING_CAMPAIGNS`).

| Key | Type | Role |
|-----|------|------|
| `pk` | S (HASH) | `OWNER#{owner_id}` |
| `sk` | S (RANGE) | `MKTCAMP#{campaign_id}` |

GSIs:

| Index name | PK (S) | SK | Notes |
|------------|--------|----|-------|
| `ByOwnerCreatedAt` | `owner_id` | `created_at` (N) | Owner campaign listing |
| `ByStatusCreatedAt` | `status` | `created_at` (N) | Admin campaign queue |
| `ByCampaignId` | `campaign_id` | — (no sort key) | Point-lookup by `campaign_id` alone; used by the MKT-011 ownership helper `_require_campaign_owner` (needs to resolve a campaign without knowing `owner_id`) and by `get_campaign_by_id` in MKT-004 |

`attr_types={"created_at": "N"}` — without this declaration `_attribute_definitions` would default `created_at` to type `"S"`, which causes a `ValidationException` when the service queries the GSI with an integer value. The `ByCampaignId` GSI has no sort key and uses only a string PK, so no additional `attr_types` entry is needed for it.

### Table: ContactLists

Default name: `ContactLists` (env `DDB_CONTACT_LISTS`).

Single-table pattern: list META rows and per-member rows coexist using distinct PK/SK namespaces.

| Row type | PK | SK |
|----------|----|----|
| List META | `OWNER#{owner_id}` | `LIST#{list_id}` |
| Member | `LIST#{list_id}` | `PARTY#{party_id}` |

GSIs:

| Index name | PK (S) | SK | Notes |
|------------|--------|----|-------|
| `ByOwnerCreatedAt` | `owner_id` | `created_at` (N) | META rows, owner listing |
| `ByListJoinedAt` | `list_id` | `joined_at` (N) | Member rows, pagination for send resolution |

`attr_types={"created_at": "N", "joined_at": "N"}` — both GSI sort keys are numeric.

### Table: PartySegments

Default name: `PartySegments` (env `DDB_PARTY_SEGMENTS`).

| Row type | PK | SK |
|----------|----|----|
| Segment META | `OWNER#{owner_id}` | `SEGMENT#{segment_id}` |
| Snapshot member | `SEGMENT#{segment_id}` | `SNAP#{snap_ts:010d}#{party_id}` |

GSIs:

| Index name | PK (S) | SK | Notes |
|------------|--------|----|-------|
| `ByOwnerCreatedAt` | `owner_id` | `created_at` (N) | Segment listing |
| `BySegmentSnapTs` | `segment_id` | `snap_ts` (N) | Latest snapshot resolution |

`attr_types={"created_at": "N", "snap_ts": "N"}`.

Note: `snap_ts` appears only on snapshot-member rows; META rows do not write this attribute. DynamoDB sparse GSIs handle this correctly — META rows simply do not appear in the `BySegmentSnapTs` index.

### Table: TrackingCodes

Default name: `TrackingCodes` (env `DDB_TRACKING_CODES`).

Single-table pattern: META, VISIT, and ORDER rows share the same table.

| Row type | PK | SK |
|----------|----|----|
| Code META | `TRACK#{code_slug}` | `META` |
| Visit | `TRACK#{code_slug}` | `VISIT#{ts:010d}#{nonce}` |
| Order | `TRACK#{code_slug}` | `ORDER#{order_id}` |

GSIs:

| Index name | PK (S) | SK | Notes |
|------------|--------|----|-------|
| `ByCampaignCreatedAt` | `campaign_id` | `created_at` (N) | All codes for a campaign |
| `ByCodeTs` | `code_slug` | `ts` (N) | Time-ordered visit/order scan |

`attr_types={"created_at": "N", "ts": "N"}`.

Note: VISIT rows write `ts` (numeric Unix seconds) and appear in `ByCodeTs`. ORDER rows also write `ts` (as `attributed_at`). META rows write `created_at` but not `ts`, so they appear in `ByCampaignCreatedAt` only.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag semantics

`S.marketing_campaigns_enabled` is read through the `Settings` singleton `S` at `app/core/settings.py` line 2772. The singleton is instantiated once at module import, so the flag value is fixed for the lifetime of the process. Changing the env var after startup has no effect without a restart — consistent with all other feature flags in the codebase.

When `False` (the default):

- No existing table (`AdCampaigns`, `PromoCodes`, `Contacts`, `billing`, `cart_reminder_config`, etc.) is touched.
- The four new tables are still created by `scripts/local-ddb-init.py` at `just restart` time, so a flag-toggle at runtime never requires a schema migration.
- `T.marketing_campaigns`, `T.contact_lists`, `T.party_segments`, and `T.tracking_codes` are live handles pointing at real DDB tables (they resolve immediately at module import like every other handle). Downstream tickets (MKT-004 through MKT-011) will check `S.marketing_campaigns_enabled` themselves before performing writes; the handles being available does not bypass that check.

### 5.2 `attr_types` omission is a silent failure

DynamoDB Local does not reject a table creation call that lists a GSI sort key with type `"S"` when the service later queries it with an integer. The error surfaces at runtime as a `ValidationException: "Value provided in ExpressionAttributeValues unused in expressions"` or a type mismatch error on the GSI key. This is the CLAUDE.md gotcha reproduced in the `PromoCodes` table (`attr_types={"created_at": "N"}` at `scripts/local-ddb-init.py:1316` ← VERIFIED), the `BroadcastSessions` table (`attr_types={"scheduled_at": "N"}` at `scripts/local-ddb-init.py:729` ← VERIFIED), and dozens of others. All four new tables have at least one numeric GSI sort key; every one must be declared in `attr_types`.

Affected keys per table:

| Table | Numeric GSI sort keys |
|-------|-----------------------|
| MarketingCampaigns | `created_at` |
| ContactLists | `created_at`, `joined_at` |
| PartySegments | `created_at`, `snap_ts` |
| TrackingCodes | `created_at`, `ts` |

### 5.3 `_FloatSafeTable` proxy and import-time handle creation

`_safe_table(name)` calls `ddb.Table(name)` where `ddb` is the boto3 DynamoDB resource from `app/core/aws.py:6` ← VERIFIED (imported in `app/core/tables.py:7`). In dev, this resource is pointed at `http://localhost:8001`; in prod it uses the real AWS endpoint. The `ddb.Table(name)` call does **not** validate that the table exists — it creates a lazy resource object. Existence is only checked on first actual DDB call (e.g., `get_item`). Therefore, adding handles for tables that do not yet exist (before `just restart` has run) does not cause an import error.

### 5.4 `Tables` dataclass is frozen

`Tables` is declared `@dataclass(frozen=True)`. Field additions must be paired with instantiation additions or Python raises `TypeError: __init__() got an unexpected keyword argument` at the `T = Tables(...)` call. The smoke test (Section 9) verifies both by importing `T` directly.

### 5.5 Conflicts with existing `marketing_content` / `marketing_engagement`

`T.marketing_content` and `T.marketing_engagement` are already wired (`app/core/tables.py:287-288` ← VERIFIED for dataclass fields; `app/core/tables.py:538-539` ← VERIFIED for instantiation), backed by settings at `app/core/settings.py:2516-2517` ← VERIFIED. These belong to AGENT-017 (Marketing AI Agent). The new names `marketing_campaigns`, `contact_lists`, `party_segments`, `tracking_codes` are distinct; no rename or alias is needed.

### 5.6 GSI index naming collision risk

GSI names are scoped per table (not global). Using `ByOwnerCreatedAt` as a GSI name on both `MarketingCampaigns`, `ContactLists`, and `PartySegments` is safe — each table creates its own independent index under that name. Downstream code that queries a GSI by `IndexName="ByOwnerCreatedAt"` must specify the correct `T.<table>` handle to avoid querying the wrong table.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity**: `_safe_table(S.marketing_campaigns_table_name)` calls `ddb.Table(name)` where `ddb` is the same boto3 resource used by every other handle. In dev it resolves to DynamoDB Local at `http://localhost:8001` (sourced from `DDB_ENDPOINT_URL` in `.env.local`); in prod it resolves to real DynamoDB. No `if S.dev_mode` branching is introduced. No mock or stub paths are created. The table handles behave identically in both environments — SECOPS-007 parity is automatic.

**`scripts/local-ddb-init.py` idempotency**: `_ensure_table` at `scripts/local-ddb-init.py:2534` ← VERIFIED calls `client.list_tables` first (`scripts/local-ddb-init.py:2536`); if the table already exists, it optionally backfills missing GSIs via `client.describe_table` (`scripts/local-ddb-init.py:2539`). Running `main()` multiple times (e.g., `just restart` after a code change) is safe — existing tables and their data are not dropped. This is the correct behavior for the four new tables.

**Security considerations for MKT-002 specifically**: This ticket introduces no endpoints, no auth dependencies, and no data access paths. The only security-relevant property is that `S.marketing_campaigns_enabled` defaults to `False`, ensuring the module surface is invisible until explicitly enabled. The handles being imported at module load time do not expose any data — they are lazy boto3 resource objects.

**No sensitive data in settings**: the five new settings keys are table names and a boolean. They do not contain secrets, keys, or credentials.

## 8. Backward Compatibility & Migration

**Zero impact on existing code**. All changes are purely additive:

- `app/core/settings.py`: new fields appended. No existing field is renamed or removed. Any code that reads `S.promo_codes_table_name`, `S.cart_reminders_enabled`, etc., is unaffected.
- `app/core/tables.py`: the `Tables` dataclass gains four new fields; existing fields at lines 70–319 are untouched. `T.promo_codes`, `T.contacts`, `T.billing`, etc., resolve identically. Code that accesses `T` by attribute (all existing code) is unaffected.
- `scripts/local-ddb-init.py`: four `TableDef` entries are appended to the list. The `main()` function iterates the list and calls `_ensure_table` for each entry. Existing tables are not recreated; `_ensure_table` skips already-existing tables. The four new tables are created fresh on the next `just restart`.

**Production deployment order**: in production, the four new DDB tables must be created (`aws dynamodb create-table`) before deploying the code that introduces the new handle imports. If the code is deployed before the tables exist, the import succeeds (handles are lazy), but the first DDB call against a missing table raises `ResourceNotFoundException`. Because `S.marketing_campaigns_enabled` defaults to `False`, no caller in MKT-002 itself makes any DDB calls — the risk is zero for this ticket. Downstream tickets (MKT-004 through MKT-011) gate DDB writes on the flag, so the same applies there.

**No data migration required**. No existing rows are modified. No existing GSIs are updated.

## 10. Open Questions / Assumptions

1. **Assumption**: the flag bool pattern `os.environ.get("...", "0") not in ("0", "false", "False")` is chosen over the `.lower() in ("1", "true", "yes", "on")` form because it is consistent with the nearest adjacent flags in the file (`promo_codes_enabled` at line 1996, `refund_requests_enabled` at line 2032). Either form is equivalent; this assumption should be confirmed with the team before the PR is merged.

2. **Assumption**: the `Tables` frozen dataclass declaration order (fields then instantiation) must be in sync. The implementation must add fields in exactly the order: `marketing_campaigns`, `contact_lists`, `party_segments`, `tracking_codes` — both in the `class Tables:` body and in the `T = Tables(...)` call. Python frozen dataclasses require positional consistency for future `replace()` calls; attribute access by name is unaffected by order.

3. **Open question**: should `.env.local.example` receive a `# MARKETING_CAMPAIGNS_ENABLED=0` entry? This is a convention question (some flags are commented-out in `.env.local.example`, some are not). The recommendation is yes — add a commented-out entry so the flag is discoverable. This is a 1-line change outside the scope of the three primary file changes but should be confirmed.

4. **Assumption**: the `TrackingCodes` table uses `pk=TRACK#{code_slug}` with a string slug as part of the PK. DynamoDB does not enforce slug uniqueness across the `pk` namespace by itself (two rows with the same `pk` but different `sk` values are distinct items). Slug uniqueness for the META row is enforced in the service layer (MKT-010) via `ConditionExpression="attribute_not_exists(pk)"` on the `TRACK#{slug}#META` write — not by the table schema. This is the standard single-table pattern; no UNIQUE constraint mechanism is needed here.

5. **Assumption**: the `ByOwnerCreatedAt` GSI name is reused across all three tables that need an owner-paginated listing (MarketingCampaigns, ContactLists, PartySegments). DynamoDB GSI names are scoped per table, so this is safe. Downstream code must always pair the `IndexName` with the correct `T.<handle>` to avoid ambiguity.

6. **Assumption**: the `ContactLists` table's `ByOwnerCreatedAt` GSI applies only to META rows (which carry an `owner_id` attribute). Member rows (`LIST#{list_id}` / `PARTY#{party_id}`) do not write `owner_id`, so they will not appear in this GSI. This is correct behavior. Implementers of MKT-007 must not accidentally write `owner_id` onto member rows.

7. **Open question**: should the table default names use PascalCase (`MarketingCampaigns`) or snake_case (`marketing_campaigns`)? The codebase is mixed: `PromoCodes` uses PascalCase, while `inventory`, `returns`, `reservations` use snake_case. This spec follows the PascalCase convention used by the adjacent promo-codes table. Confirm with the team before the PR if snake_case is preferred.
