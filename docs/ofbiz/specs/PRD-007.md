# PRD-007 — Virtual↔variant product service

**Type:** Feature | **Priority:** P0 | **Estimate:** 5 days
**Milestone:** 3 — Variants & Features/Options

---

## 1. Summary & Goal

PRD-007 creates `app/services/product_variants.py`, the pure service layer that implements the VIRTUAL↔VARIANT product relationship. Its responsibilities are:

1. **Promote** a scalar catalog item to the `"virtual"` product type by writing a `TYPE` marker row on `T.product_depth`.
2. **Create variants** under a virtual parent: validate each `feature_category_id → feature_value_id` mapping against the attached feature axes (PRD-006), compute a deterministic `variant_id = sha256(parent_id + sorted_feature_value_tuple)[:16]`, and write a `VAR#` row on `T.product_depth` with the effective price and inventory SKU.
3. **Reject duplicate combinations** idempotently — a conditional put that raises 409 when the same `variant_id` already exists.
4. **List variants** of a virtual parent via the `ByVirtualParent` GSI in a single query (O(1), no scan).
5. **Compute effective price** as a pure, side-effect-free function: `parent_price_cents + Σ(feature_value.price_delta_cents for each selected value)`.
6. **Protect the standalone path**: a non-virtual item has zero variant rows; all existing catalog endpoints, cart, and billing paths are byte-for-byte unchanged when `PRODUCT_DEPTH_ENABLED` is off.

No router endpoints ship in this ticket — those are PRD-008. No frontend changes are needed at this stage.

## 3. Data Model

PRD-007 exclusively uses the `product_depth` table established by PRD-002. No modifications to `T.catalog` or any other table.

### 3.1 TYPE marker row (parent product promotion)

Written by `set_product_type(item_id, product_type, user_sub)`:

| Attribute | Value |
|---|---|
| `PK` | `ITEM#{item_id}` |
| `SK` | `TYPE` |
| `entity` | `"product_type"` |
| `product_type` | `"virtual"` (or any `ProductTypeEnum` value) |
| `creator_id` | `{user_sub}` |
| `created_at` | `now_ts()` — integer Unix seconds |
| `updated_at` | `now_ts()` — updated on every `set_product_type` call |

A `put_item` with no condition is used (last-write-wins is correct — you can re-promote a standalone item to virtual or back). There is no version column here because the TYPE row carries no state machine beyond the enum value.

### 3.2 Variant row

Written by `create_variant(parent_item_id, feature_values, user_sub, sku_override=None)`:

| Attribute | Value |
|---|---|
| `PK` | `ITEM#{parent_item_id}` |
| `SK` | `VAR#{variant_id}` |
| `entity` | `"variant"` |
| `variant_id` | `sha256(parent_item_id + canonical_fv_tuple)[:16]` — see §5.1 |
| `parent_item_id` | `{parent_item_id}` |
| `sku` | `"variant:{parent_item_id}:{variant_id}"` or `sku_override` when provided |
| `feature_values` | `{"fc_id_1": "fv_id_1", ...}` — the validated, canonical mapping |
| `price_delta_cents` | `compute_price_delta(feature_values)` — signed int |
| `effective_price_cents` | `parent_price_cents + price_delta_cents` |
| `creator_id` | `{user_sub}` |
| `created_at` | `now_ts()` — integer Unix seconds |
| `GSI_VIRT_PK` | `VIRTUAL#{parent_item_id}` |
| `GSI_VIRT_SK` | `{created_at}` — integer (numeric sort, declared in `attr_types`) |

The variant row is written with a conditional put:
```
ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)"
```
`ConditionalCheckFailedException` maps to HTTP 409 ("Variant already exists for this feature combination").

### 3.3 `ByVirtualParent` GSI query for listing

`list_variants(parent_item_id)` executes:
```python
T.product_depth.query(
    IndexName="ByVirtualParent",
    KeyConditionExpression=Key("GSI_VIRT_PK").eq(f"VIRTUAL#{parent_item_id}"),
    ScanIndexForward=True,   # chronological
)
```

A non-virtual item returns zero rows from this query — indistinguishable from a virtual item with no variants yet created.

### 4.3 `derive_variant_id`

```python
def derive_variant_id(
    parent_item_id: str,
    feature_values: Dict[str, str],   # {feature_category_id: feature_value_id}
) -> str:
    """Deterministic 16-char hex id.

    canonical_tuple = sorted(feature_values.items())   # sort by fc_id
    raw = f"{parent_item_id}|" + "|".join(f"{fc}:{fv}" for fc, fv in canonical_tuple)
    return hashlib.sha256(raw.encode("utf-8")).hexdigest()[:16]
    """
```

Sorting `feature_values.items()` by key (feature_category_id) ensures that `{"color": "red", "size": "L"}` and `{"size": "L", "color": "red"}` produce the same id. The `|` delimiter prevents collisions across different numbers of features.

### 4.6 `create_variant`

```python
def create_variant(
    parent_item_id: str,
    feature_values: Dict[str, str],   # {feature_category_id: feature_value_id}
    user_sub: str,
    sku_override: Optional[str] = None,
) -> Dict[str, Any]:
    """Create a variant child under a virtual parent.

    Steps (all or nothing from the caller's view — no transactions needed
    because the conditional put is the only write):
    1. _require_enabled()
    2. Read parent item from T.catalog via _find_item_by_id; 404 if absent.
    3. Read parent TYPE row; assert product_type == "virtual" (403 if not virtual).
    4. Validate every feature_category_id in feature_values is attached to the parent
       via product_features.list_product_features(parent_item_id) — 422 if any axis
       is not attached.
    5. For each feature_category_id, call product_features.get_feature_value to assert
       the value exists within that category — 422 if any value is unknown.
    6. variant_id = derive_variant_id(parent_item_id, feature_values)
    7. price_delta = compute_price_delta(feature_values)
    8. effective_price = parent["price_cents"] + price_delta
    9. sku = sku_override or f"variant:{parent_item_id}:{variant_id}"
   10. T.product_depth.put_item(variant_row,
           ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)")
       → ConditionalCheckFailedException → HTTP 409
   11. Return the written variant row dict.
    """
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Deterministic variant id

```
canonical_tuple = tuple(sorted(feature_values.items()))  # sort by fc_id ascending
raw = parent_item_id + "|" + "|".join(f"{fc}:{fv}" for fc, fv in canonical_tuple)
variant_id = hashlib.sha256(raw.encode("utf-8")).hexdigest()[:16]
```

Taking the first 16 hex characters (64-bit collision space) is sufficient for the bounded set of feature combinations on any single product. If two different products have the same feature-value tuple, they still produce different variant ids because `parent_item_id` is included in the hash input.

### 5.2 Duplicate combination rejection

The conditional put with `attribute_not_exists(PK) AND attribute_not_exists(SK)` is evaluated server-side by DynamoDB. A race between two concurrent `create_variant` calls for the same `(parent_item_id, feature_values)` will resolve to exactly one winner (201) and one loser (409). This is the same single-writer oversell-prevention model used in `app/services/inventory.py` (the `available >= :qty` conditional in `reserve`).

### 5.3 Price computation correctness

`compute_price_delta` fetches each feature value's `price_delta_cents` from `T.product_depth` (via the `FTCAT#{fc_id} / FTVAL#{fv_id}` row written by PRD-006). If a feature value has been deleted between variant creation and the call, the function raises 404. Callers that need a "best-effort" price should catch this and fall back to `effective_price_cents` stored on the variant row (denormalized at creation time). The stored `effective_price_cents` is never retroactively updated when feature prices change — it is a snapshot at creation. This is the OFBiz convention for ProductAssoc price deltas.

### 5.4 Parent must be virtual before variants can be added

Step 3 of `create_variant` reads the TYPE row. If the parent has no TYPE row (standalone by default), the call is rejected with 422 and the message "Parent item must be of type 'virtual' before variants can be added." Callers must invoke `set_product_type(item_id, "virtual", user_sub)` first.

### 5.5 Feature-category validation sequence

Step 4 builds the set of attached feature-category ids from `list_product_features(parent_item_id)`. If `feature_values` contains a key not in this set, it is rejected with 422. If `feature_values` is missing a key that is attached to the parent, it is also rejected — every attached feature axis must be resolved in a single variant selection (partial selections are not allowed). This mirrors OFBiz's ProductConfigConstraint pattern.

### 5.6 Stock for variants lives in T.inventory, not stock_count

The scalar `stock_count` field on the parent catalog item row (`T.catalog`) is semantically invalidated once the item becomes virtual — a virtual product has no stock of its own; stock lives per-variant-SKU in `T.inventory`. When `list_variants` is called, the service may optionally join inventory data by calling `inventory.get_or_zero(sku)` for each variant to populate `stock_status`. This join is skipped when `S.inventory_reservations_enabled` is `False` (the default — verified: `app/core/settings.py:839`), and `stock_status="unlimited"` is returned instead — consistent with `_compute_stock_status` at `app/routers/catalog.py:94` (verified).

### 5.7 `sku_override` validation

If `sku_override` is provided it must not start with `"variant:"` (to avoid confusion with the auto-derived format) and must be unique across the parent's variants (validated by checking for any existing variant row with the same SKU via a base-table query before the conditional put). If uniqueness fails, raise 409.

### 5.8 Existing items with no TYPE row

`get_product_type` returns `None` for any item that has no `ITEM#{id}/TYPE` row. Services that consume this should treat `None` as `"standalone"`. `list_variants` returns `([], None)` for such items, and the router (PRD-008) must not 404 — listing variants on a non-virtual item is a valid no-op.

### 5.9 Circular reference not applicable to variants

Unlike bundles (PRD-009), variants cannot form cycles — a variant's `parent_item_id` is a scalar string referencing the virtual parent, not a recursive composition. No cycle detection is needed in this ticket.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

All DynamoDB operations in `product_variants.py` use `T.product_depth`, which resolves to either the local DynamoDB (dev, via `DDB_ENDPOINT_URL=http://localhost:8001`) or real DynamoDB (prod) with no code branching. There is no `S.dev_mode` check anywhere in the service. The behavior is identical in both environments — same table, same GSI, same conditional-put guard. This follows the SECOPS-007 principle.

### Idempotency

`derive_variant_id` is a pure function of `(parent_item_id, feature_values)`. Re-submitting the same combination produces the same `variant_id` and the same `PK/SK`. The conditional put (`attribute_not_exists`) then short-circuits with a 409 rather than creating a duplicate. The caller (PRD-008 router) maps 409 to a user-visible message like "This variant combination already exists", not a server error.

`set_product_type` uses a last-write-wins unconditional `put_item` — calling it twice with the same type is a no-op in effect (the row is overwritten with the same value and an updated `updated_at`).

### Access control

Every public write function (`set_product_type`, `create_variant`, `delete_variant`) accepts `user_sub` and must be called from an endpoint that first runs `_require_category_owner(category_id, user_sub)` (`app/routers/catalog.py:247` — verified). Catalog router endpoints use `require_ui_session` from `app/services/sessions.py:330` (verified — NOT from `app/auth/deps.py`). The service layer trusts the passed `user_sub` and stores it as `creator_id` on each row. The router (PRD-008) is responsible for enforcing ownership before calling into the service.

Ownership of a variant is inherited from the parent item's category ownership. Querying a variant (read-only) does not require ownership — `list_variants` and `get_product_type` perform no ownership checks, consistent with the existing read-only catalog endpoints.

### Variant SKU privacy

The `sku` field is an internal inventory key and should not be exposed to non-owner users in the storefront-facing response (PRD-008 should strip or suppress it from public-facing endpoints). Within this service layer, `sku` is always persisted.

## 8. Backward Compatibility & Migration

### With `PRODUCT_DEPTH_ENABLED=false` (default)

- `product_variants.py` functions always raise HTTP 404 via `_require_enabled()`.
- No reads or writes to `T.product_depth` occur from variant paths.
- `T.catalog` is untouched — zero new reads or writes.
- `_catalog_item_out` (`app/routers/catalog.py:107` — verified) continues to return a `CatalogItemOut` with the fields it currently carries (`app/models.py:672-688` — verified); the `product_type` and `variant_count` fields are added by PRD-003 (unimplemented). Once PRD-003 ships, they default to `None` / `0` when depth rows are absent — identical to pre-depth behavior.
- `app/services/shoppingcart.py` is not modified.

### Existing scalar items

Scalar items (no `ITEM#{id}/TYPE` row on `T.product_depth`) are treated as `standalone`. `list_variants` returns an empty list. The router (PRD-008) can call both on any item without branching.

### Enabling the flag on a live system

`product_depth` is a new table — no existing data exists on it. Enabling `PRODUCT_DEPTH_ENABLED=true` on a live system with existing catalog items is safe: none of those items have a TYPE row, so they remain `standalone` and all depth-aware queries return empty/default results. No backfill or migration is required.

### `effective_price_cents` staleness

`effective_price_cents` is a denormalized snapshot stored on each variant row at creation time. It is not retroactively updated when the parent's `price_cents` or a feature value's `price_delta_cents` changes. This is by design (OFBiz ProductAssoc convention) and is documented in the `VariantOut` model. The cart/checkout path in PRD-008 should re-compute `parent_price_cents + Σ(deltas)` at add-to-cart time rather than trusting the stored snapshot, but this does not affect the service behavior defined here.

## 10. Open Questions / Assumptions

**A1. Feature-value ownership scoping.** This spec assumes that any feature category in the system can be attached to any item (owner creates both). If per-owner isolation of feature categories is required (creator A's "Color" axis is invisible to creator B), PRD-006 must add a `creator_id` filter to `list_product_features` and this service must enforce it. Current assumption: feature categories are creator-scoped by `creator_id` on the row, and the existing `_require_category_owner` guard in the router prevents cross-owner attachment.

**A2. Partial feature-value selection.** This spec requires all attached feature axes to be selected in one variant creation call. If the product owner wants optional axes (not all combinations must be materialized), PRD-006 must add an `optional: bool` flag to the `FTAPPL#` row. Current assumption: all attached axes are required.

**A3. `effective_price_cents` staleness strategy.** Spec documents that stored `effective_price_cents` is a snapshot and does not auto-update. If the team wants live price resolution, a follow-up ticket should remove the denormalized field and compute it at read time. Current assumption: snapshot is acceptable.

**A4. Variant deletion semantics.** `delete_variant` is a hard delete. If a variant has active cart lines or inventory reservations, deleting it will leave dangling SKU references. This spec does not address the cleanup. Assumption: callers are responsible for ensuring no active cart/reservation before deleting; the service performs no referential-integrity check.

**A5. Maximum variant count per parent.** No cap is currently enforced. If a parent has 10 feature axes each with 10 values, a pathological caller could create 10^10 combinations. Assumption: a practical limit (e.g., 1000 variants per parent) should be enforced via a `Limit` check before each `create_variant` call; this can be a configurable `S.product_depth_max_variants_per_item` setting defaulting to `1000`.

**A6. `_find_item_by_id` circular import.** The service calls `_find_item_by_id` from `app/routers/catalog.py`. This import pattern (service importing from router) is unusual in this codebase. Assumption: the call should either be made a lazy local import (as in `app/services/instance_monitoring.py`) or `_find_item_by_id` should be extracted to a shared helper in `app/services/catalog_helpers.py` to avoid the circular dependency. The latter is preferred.

**A7. Inventory join in `list_variants`.** Spec states the join is optional and skipped when `inventory_reservations_enabled` is off. Assumption: the join is implemented in the service (not the router) and returns `stock_status="unlimited"` when not joined, consistent with `_compute_stock_status` at `app/routers/catalog.py:94`.
