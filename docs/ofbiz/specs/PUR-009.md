# PUR-009 — PO → AP payable / supplier payment via existing ledger

**Type:** Feature | **Priority:** P1 | **Estimate:** 4 days  
**Milestone:** 3 — Purchase Orders & Approval  
**Depends on:** PUR-008 (receiving), OFB-015 (AP subledger)

---

## 1. Summary & Goal

PUR-009 closes the financial loop on the buy-side: once a PO reaches `received` status (via PUR-008),
the platform owes money to the supplier. This ticket delivers:

1. **`record_ap_payable(po_id)`** — posts a single `purchase_payable` ledger entry on the
   `purchase_orders` table (keyed by `po_id`) via `billing_shared.new_ledger_entry`. Idempotent:
   re-calling with the same `po_id` is a no-op due to a DynamoDB conditional put guard keyed on a
   deterministic entry-id derived from `sha256(f"payable:{po_id}")[:32]`.
2. **`settle_supplier_payment(po_id, payment_ref, provider)`** — marks the payable as `settled` via
   `billing_shared.settle_or_reverse_ledger` and back-writes `ledger_entry_id`, `paid_at`, and
   `amount_cents` onto the PO header row.
3. **`get_ap_payable(po_id)`** — retrieves the current payable ledger row for a PO.

The billing table (`T.billing`) is *not* touched. All ledger rows live in `T.purchase_orders` —
the `new_ledger_entry` / `settle_or_reverse_ledger` primitives are generic (`key_name`/`key_value`
arguments) and accept any DynamoDB table. This keeps AP payables in the purchasing table where they
belong, and the `GSI_LEDGER_DATE` index on `T.billing` (described in `CLAUDE.md` FIN-013) is
replicated on `T.purchase_orders` so the OFB-015 AP subledger aging query can bucket payables by day
without scanning the buyer-facing billing table.

With `PURCHASING_SCM_ENABLED=false` every function raises `HTTPException(404)` and all existing
shop/cart/orders/billing behavior is byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 `billing_shared.new_ledger_entry` — the single money-write primitive

`app/services/billing_shared.py:224–259` defines `new_ledger_entry(*, key_name, key_value,
entry_type, amount_cents, state, reason, meta=None, extra=None)`. The function:

- Stamps `ts = now_ts()`, generates a `ulidish()` entry_id (`billing_shared.py:240`, call site),
  builds SK via `ledger_sk(ts, entry_id)` = `"LEDGER#{ts}#{entry_id}"` (`billing_shared.py:220–221`).
- Persists `ledger_date = ledger_date_for_ts(ts)` (a `YYYY-MM-DD` string, `billing_shared.py:253`)
  for the FIN-013 `GSI_LEDGER_DATE` day-bucket query used by the platform financial dashboard.
- Returns `(sk, item)` — the caller is responsible for `table.put_item(Item=item)`.
- Accepts `extra={"provider": "..."}` as a pass-through dict (`billing_shared.py:255–256`); FIN-013 /
  GAP-0203 requires provider attribution on all money-out entries so the platform financial dashboard
  provider-breakdown works correctly.

`app/services/billing_shared.py:262–274` defines `settle_or_reverse_ledger(table, key_name,
key_value, ledger_sk_value, new_state)` — a simple `update_item` on `#s = :s` that flips the
`state` field.

### 2.2 How callers use `new_ledger_entry` today

All existing callers write to `T.billing` with `key_name="pk"` / `key_value=user_pk(user_id)`
(`billing_shared.py:23` defines `user_pk`; e.g. `app/routers/billing.py:1126–1136`, `1306–1316`).
The function signature is fully generic — it
accepts any table and any key name/value pair. PUR-009 passes `key_name="po_id"`, `key_value=po_id`,
and writes to `T.purchase_orders`. This is the first non-`T.billing` caller, but no changes to
`billing_shared.py` are required.

### 2.3 Existing `entry_type` vocabulary

Current `entry_type` values in use (confirmed by reading source):
`"credit"` (`app/routers/billing.py:1129`), `"debit"` (`billing.py:2421`),
`"adjustment"` (`billing.py:1309`),
`"proration_charge"` / `"proration_credit"` (`app/routers/subscription_server.py:1671` — note:
this is a **router** file, not a service),
`"refund_credit"` / `"refund_debit"` (`app/services/refund_requests.py:258`).

PUR-009 introduces two new entry types: `"purchase_payable"` (a liability recognised on receipt)
and `"purchase_payment"` (the cash-out event when the supplier is paid). These map onto the
OFB-014 GL posting mapper (Accounts Payable liability account, and Cash/Bank asset account,
respectively) without requiring any change to `billing_shared.py`.

### 2.4 Provider attribution (FIN-013 / GAP-0203)

`CLAUDE.md` under "Ledger provider attribution": "Provider-originated ledger entries must persist a
`provider` field ... or the dashboard provider breakdown buckets them as `unknown`." Supplier
payments are initiated manually (admin-triggered, not via Stripe/PayPal/CCBill), so PUR-009
uses `provider="manual"` to signal deliberate omission of a third-party processor, rather than
leaving the field absent. This surfaces correctly in the OFB-015 AP aging view.

### 2.5 PO header data established by PUR-006 / PUR-007 / PUR-008

`docs/ofbiz/specs/PUR-006.md:74–110` documents the `purchase_orders` table schema. The header row
(`SK="META"`) carries:
- `po_id` (PK), `supplier_id`, `status`, `currency`, `subtotal_cents`, `created_by`, `created_at` (N),
  `updated_at` (N), `correlation_id`, `line_count`.

PUR-008 advances `status` to `received` (and then `closed` via `transition_po`) after all lines are
received. PUR-009 triggers on the `received` transition: `record_ap_payable` should be called by
the PUR-008 receiving service as a best-effort post-receive hook (or by the PUR-010 router after
`receive_po` returns successfully).

### 2.6 `purchase_orders` table GSI gap — `GSI_LEDGER_DATE` not yet present

PUR-002 (`docs/ofbiz/specs/PUR-002.md`) establishes the `purchase_orders` table with `GSI_SUPPLIER`
and `GSI_STATUS`. It does **not** add `GSI_LEDGER_DATE`. PUR-009 must add this GSI to
`scripts/local-ddb-init.py` so that:
- The OFB-015 AP subledger can query payable entries by calendar day (same day-bucket pattern used
  on `T.billing` by `app/services/platform_financial_dashboard.py:137–152`).
- The OFB-014 GL posting mapper can locate unpublished payable entries efficiently.

`ledger_date` is a string (`YYYY-MM-DD`) so no `attr_types` entry is needed for it — the sort key
in the existing `billing` table definition at `scripts/local-ddb-init.py:71–76` confirms
`attr_types={"ledger_date": "S"}` (which is the default and can be omitted, but should be explicit
for clarity). The `billing` GSI uses `sort_key: "sk"` (`local-ddb-init.py:74`); PUR-009's
`GSI_LEDGER_DATE` on `purchase_orders` mirrors this exactly.

**Note:** `S.purchasing_scm_enabled`, `S.purchase_orders_table_name`, `T.purchase_orders`, and the
`purchase_orders` `TableDef` in `scripts/local-ddb-init.py` do **not exist** in the current
codebase — all are created by PUR-002 (confirmed: `grep purchasing_scm app/core/settings.py`
returns no results). PUR-009 is not implementable until PUR-002 lands.

### 2.7 Idempotency anchor: deterministic `entry_id`

`billing_shared.new_ledger_entry` always generates a fresh `ulidish()` entry_id (line 240), making
it non-idempotent by default. PUR-009 achieves idempotency by:
1. Deriving a fixed entry_id: `payable_entry_id = hashlib.sha256(f"payable:{po_id}".encode()).hexdigest()[:32]`.
2. Computing the SK: `payable_sk = ledger_sk(ts_placeholder, payable_entry_id)` — but `ts` must
   also be stable. Strategy: the first call stores `ts` + `sk` onto the PO header (`payable_ts`,
   `payable_ledger_sk`); re-calls detect the stored SK and return early.
3. DynamoDB conditional put: `ConditionExpression="attribute_not_exists(po_id) OR attribute_not_exists(payable_ledger_sk)"` on the header read-before-write (see section 5).

This is the same `attribute_not_exists`-gated conditional pattern used in
`app/services/inventory.py:242–247` to prevent a race on first-time SKU record creation within
`adjust()` (not `set_on_hand()` — the guard is in the create-on-first-adjust path).

## 3. Data Model

PUR-009 does not introduce new DynamoDB tables. It adds rows to the existing `purchase_orders` table
(established by PUR-002) and one new GSI to that table.

### 3.1 New row type in `purchase_orders`: `PAYABLE` ledger row

Ledger rows written via `new_ledger_entry` use SK = `LEDGER#{ts}#{entry_id}`.

| Attribute | Type | Description |
|---|---|---|
| `po_id` | S | Hash key (= `key_value` in `new_ledger_entry` call) |
| `sk` | S | `LEDGER#{ts}#{entry_id}` — value of `payable_sk` |
| `entry_id` | S | `sha256("payable:{po_id}")[:32]` — deterministic |
| `ts` | N | Unix timestamp at first-write (stored on header for replay) |
| `type` | S | `"purchase_payable"` |
| `amount_cents` | N | `header.subtotal_cents` |
| `state` | S | `"pending"` → `"settled"` (or `"reversed"` on cancel) |
| `reason` | S | `"supplier_payment"` (per ticket description) |
| `ledger_date` | S | `YYYY-MM-DD` UTC date (FIN-013 / GSI_LEDGER_DATE partition key) |
| `meta` | M | `{"po_id": po_id, "supplier_id": ..., "correlation_id": ...}` |
| `provider` | S | `"manual"` (FIN-013 attribution pass-through in `extra`) |
| `currency` | S | ISO-4217 code from PO header |

### 3.2 PO header fields added by PUR-009

The `META` row gains three new write-once fields set by `record_ap_payable`:

| Attribute | Type | Description |
|---|---|---|
| `payable_ledger_sk` | S | SK of the payable ledger row; presence = payable has been posted |
| `payable_ts` | N | `ts` used when building the ledger SK; needed for replay |
| `payable_entry_id` | S | The deterministic entry_id; redundant but useful for debugging |

And three more set by `settle_supplier_payment`:

| Attribute | Type | Description |
|---|---|---|
| `ledger_entry_id` | S | The `entry_id` of the settled payment ledger row |
| `paid_at` | N | Unix timestamp of settlement |
| `paid_amount_cents` | N | Amount cents actually settled (must equal `subtotal_cents`) |

### 3.3 New GSI on `purchase_orders`: `GSI_LEDGER_DATE`

Mirrors the existing `GSI_LEDGER_DATE` on `T.billing` (`scripts/local-ddb-init.py:71–76`).

```python
TableDef(
    _resolve_table_name(S.purchase_orders_table_name, "purchase_orders"),
    "po_id",
    "sk",
    gsi=[
        {"index_name": "GSI_SUPPLIER",     "partition_key": "supplier_id", "sort_key": "created_at"},
        {"index_name": "GSI_STATUS",       "partition_key": "status",      "sort_key": "created_at"},
        {"index_name": "GSI_LEDGER_DATE",  "partition_key": "ledger_date", "sort_key": "sk"},
    ],
    attr_types={"created_at": "N"},
)
```

`ledger_date` is type `S` (default); `sk` is type `S` (default). No additional `attr_types` entry
required. Header rows and line rows carry no `ledger_date`, so they are never projected into
`GSI_LEDGER_DATE` — only the `LEDGER#…` rows appear in that index, exactly mirroring the
`T.billing` table design.

## 5. Detailed Behavior & Edge Cases

### 5.1 `record_ap_payable` step-by-step

1. `_require_enabled()` — 404 if `PURCHASING_SCM_ENABLED=false`.
2. `header = T.purchase_orders.get_item(Key={"po_id": po_id, "sk": "META"}).get("Item")` — 404 if absent.
3. Guard: `header["status"]` must be `"received"` or `"closed"` — 409 otherwise. AP payables are only
   valid after goods have been physically received (PUR-008 transitions the PO to `received`; PUR-007
   then auto-closes it; both states are valid here to accommodate the ordering race between PUR-008
   `receive_po` completing and PUR-009 being called).
4. **Idempotency check**: if `header.get("payable_ledger_sk")` is non-empty, fetch the existing
   ledger row and return it immediately — no write. This is the primary idempotency gate.
5. Guard: `int(header.get("subtotal_cents", 0)) > 0` — 422 if zero (PO has no cost).
6. Compute deterministic entry_id: `entry_id = _payable_entry_id(po_id)`.
7. Stamp `ts = now_ts()`. Build `sk = ledger_sk(ts, entry_id)`.
8. Call `new_ledger_entry(key_name="po_id", key_value=po_id, entry_type="purchase_payable",
   amount_cents=int(header["subtotal_cents"]), state="pending", reason="supplier_payment",
   meta={"po_id": po_id, "supplier_id": header["supplier_id"],
         "correlation_id": header.get("correlation_id", "")},
   extra={"provider": "manual", "currency": header.get("currency", "usd"),
          "payment_ref": ""})`.
   This call only *builds* the item; it does not write. Override `entry_id` in the returned item
   with the deterministic value before writing.
9. `T.purchase_orders.put_item(Item=led_item)` — write the ledger row.
10. Back-write onto the header via `update_item`:
    ```
    SET payable_ledger_sk = :sk,
        payable_ts        = :ts,
        payable_entry_id  = :eid,
        updated_at        = :now
    ConditionExpression: attribute_not_exists(payable_ledger_sk)
    ```
    If `ConditionalCheckFailedException` is raised, another concurrent caller posted the payable
    first — fetch and return the stored row (idempotent no-op, not an error).
11. Emit `audit_event("purchase_order_ap_payable_posted", actor_sub, None, po_id=po_id,
    amount_cents=..., ledger_sk=sk)` best-effort.
12. Return the ledger row dict.

### 5.2 `settle_supplier_payment` step-by-step

1. `_require_enabled()`.
2. Load header — 404 if absent.
3. `payable_sk = header.get("payable_ledger_sk")` — 409 `"payable not posted"` if absent.
4. Load existing payable row from `T.purchase_orders.get_item(Key={"po_id": po_id, "sk": payable_sk})`.
5. Guard: `payable["state"] == "settled"` → 409 `"already settled"` to prevent double-pay.
   (Legitimate idempotency: caller can detect 409 and skip, or check `get_ap_payable` first.)
6. `settle_or_reverse_ledger(T.purchase_orders, "po_id", po_id, payable_sk, "settled")`.
7. Back-write payment linkage on the header:
   ```
   SET ledger_entry_id  = :eid,
       paid_at          = :now,
       paid_amount_cents = :cents,
       updated_at       = :now
   ```
8. Emit `audit_event("purchase_order_ap_settled", actor_sub, None, po_id=po_id,
   payment_ref=payment_ref, provider=provider, amount_cents=...)` best-effort.
9. Return the updated header dict (via `get_purchase_order(po_id)`).

### 5.3 Cancelling or reversing an AP payable

If a received PO is subsequently cancelled (unusual but possible if goods are returned in full
before the ledger is settled), the caller should call `settle_or_reverse_ledger(..., "reversed")`
directly on the payable row. PUR-009 does not expose a dedicated cancel-payable endpoint; that path
is handled by PUR-007's `transition_po` cancel hook, which should call
`po_ap_ledger.reverse_ap_payable(po_id, actor_sub)` — a thin wrapper around `settle_or_reverse_ledger`.
Spec for `reverse_ap_payable` deferred to PUR-007 addendum / PUR-010 cancel endpoint.

### 5.4 Currency mismatch guard

`header["currency"]` is stored on creation (PUR-006). `record_ap_payable` reads this value and
asserts it equals the expected denomination. If the currency field is missing from a legacy PO row,
default to `"usd"` (same fallback used in `billing.py:1131`). No currency conversion is performed:
multi-currency AP reconciliation is deferred to OFB-015 scope.

### 5.5 Zero-subtotal PO

A PO with `subtotal_cents=0` (e.g. a sample/free goods PO) skips AP posting — `record_ap_payable`
returns `None` with no write. The PO header gets no `payable_ledger_sk`. This is not an error; OFB-015
should treat a missing `payable_ledger_sk` as `amount=0`.

### 5.6 Double-call race (concurrent `record_ap_payable` for the same PO)

Step 10's `ConditionExpression="attribute_not_exists(payable_ledger_sk)"` ensures that only one
concurrent caller succeeds in setting the header. The second caller catches
`ConditionalCheckFailedException`, fetches the already-stored row, and returns it. The ledger row
itself was already written in step 9 before the conditional update; a failure in step 10 leaves an
orphaned ledger row (with no header back-pointer). This orphan is harmless for the financial
calculation (it has no `payable_ledger_sk` reference on the header and won't appear in AP aging
queries that start from the header), and will be cleaned up by a future reconciliation sweep. The
simpler alternative — writing header first, ledger second — risks leaving a header with a broken
`payable_ledger_sk` pointing to a not-yet-written row. The current ordering is safer: the ledger
row is always durable before the header pointer is set.

### 5.7 OFB-015 AP aging integration

OFB-015 queries `GSI_LEDGER_DATE` on `T.purchase_orders` for entries where
`ledger_date BETWEEN cutoff AND today` and `type = "purchase_payable"` and `state = "pending"`.
Each row's `meta.supplier_id` is the open-item party for aging (current / 30 / 60 / 90+). This is
structurally identical to how AR aging queries `GSI_LEDGER_DATE` on `T.billing` for
`type="credit", state="pending"` per-user. The `supplier_id` field on the payable row (via `meta`)
drives the per-supplier aging bucket.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

No `dev_mode` branch anywhere in `po_ap_ledger.py`. DynamoDB local (moto in tests; DDB Local on
port 8001 in dev) is the same code path as real DynamoDB. There is no mock ledger, no skip-posting
flag. The only dev-vs-prod difference is the DDB endpoint URL, resolved by `app/core/aws.py`.

### 7.2 Idempotency guarantees

| Operation | Idempotency mechanism |
|---|---|
| `record_ap_payable` (first call) | Deterministic `entry_id = sha256("payable:{po_id}")[:32]`; conditional put on header with `attribute_not_exists(payable_ledger_sk)` |
| `record_ap_payable` (replay) | Header `payable_ledger_sk` presence check → early return of existing row |
| `settle_supplier_payment` (first call) | Atomic `state` flip via `settle_or_reverse_ledger` |
| `settle_supplier_payment` (replay) | 409 on `state == "settled"` guard; caller can treat 409 as idempotent if `payment_ref` matches |

Re-calling `record_ap_payable` for the same `po_id` never produces a second `LEDGER#` row — the
deterministic entry_id would collide and be silently overwritten if the conditional put succeeded, but
the header check prevents any second write attempt from reaching the DDB layer.

### 7.3 Security considerations

- `record_ap_payable` is called internally (from PUR-008 `receive_po` or the PUR-010 router) — it
  is never an unauthenticated path. The PUR-010 endpoint that calls it uses
  `Depends(require_admin_or_root_csrf)`.
- `settle_supplier_payment` is exclusively admin-gated (`require_admin_or_root_csrf`) — releasing
  money to a supplier requires at minimum ADMIN role.
- The `payment_ref` field is stored verbatim in the audit log and the ledger row `meta`. No
  injection concern: it is never interpolated into DynamoDB expressions; it is stored as a plain
  string value.
- `amount_cents` for the payable is always derived from `header.subtotal_cents` — never from caller
  input. A caller cannot inflate the payable by passing a larger amount.

### 7.4 Audit trail

Every mutation emits an `audit_event` (from `app.services.alerts.audit_event`, per the pattern in
`app/services/commerce_order_service.py:9` and `app/routers/billing.py:49` — both confirmed as the
import line for `audit_event`). Events:
- `"purchase_order_ap_payable_posted"` — on first successful `record_ap_payable`.
- `"purchase_order_ap_settled"` — on successful `settle_supplier_payment`.
- `"purchase_order_ap_reversed"` — on `reverse_ap_payable` (PUR-007/010 addendum).

All emit best-effort (wrapped in `try/except`), so a non-critical audit failure never blocks the
financial transaction.

## 8. Backward Compatibility & Migration

### 8.1 Additive only

`T.billing`, `app/routers/billing.py`, `app/services/billing_shared.py`, and every existing
shop/cart/orders path are untouched. The new `po_ap_ledger.py` service imports from `billing_shared`
but adds no calls from the billing router into purchasing.

### 8.2 No data migration required on first deploy

The `purchase_orders` table is newly created by PUR-002 (no existing rows in production before the
feature flag is enabled). On `PURCHASING_SCM_ENABLED=true` first deploy, no backfill is needed.

### 8.3 Adding `GSI_LEDGER_DATE` to `purchase_orders`

The `purchase_orders` table is defined in `scripts/local-ddb-init.py` by PUR-002. PUR-009 modifies
that `TableDef` to add the `GSI_LEDGER_DATE` GSI. In dev: `just restart` recreates the table with
the new GSI. In prod: if the table was already created (e.g. feature was enabled in staging), a
`UpdateTable` API call is required to add the GSI before deploying PUR-009 code. Because the feature
flag defaults to `false` and no production environment is expected to have the table yet at the time
of this spec, the migration is effectively a no-op. The `scripts/local-ddb-init.py` change is the
canonical source of truth.

### 8.4 `purchase_orders` table `TableDef` change

PUR-002 spec defines the `purchase_orders` TableDef with two GSIs. PUR-009 extends it to three.
This is a backward-compatible change: `CreateTable` is idempotent (DDB Local returns
`ResourceInUseException` on duplicate — handled by the existing `try/except` in
`scripts/local-ddb-init.py`). The PUR-009 implementor must coordinate with PUR-002/PUR-010 to
ensure the final `TableDef` at merge time includes all three GSIs in a single call.

## 10. Open Questions / Assumptions

1. **Assumption**: `record_ap_payable` is called from the PUR-008 `receive_po` service as a
   best-effort post-receive hook (not from the PUR-010 HTTP layer). If preferred by the team, it
   can instead be called from `POST /{po_id}/receive` in the router. Either way the idempotency
   guarantee holds. **Verify with PUR-008 implementor.**

2. **Assumption**: `provider="manual"` is the correct attribution string for internal AP ledger
   entries. The FIN-013 / GAP-0203 requirement (`CLAUDE.md`) specifies `provider` must be non-absent.
   The OFB-015 dashboard should recognise `"manual"` as a non-processor origin. **Confirm with
   finance team which string the OFB-015 AP aging view filters on.**

3. **Open**: Should the AP payable track `tax_cents` separately (for VAT/GST on supplier invoices),
   or is `subtotal_cents` the total-including-tax amount? The current PO data model (PUR-006)
   does not have a tax field. **Tax breakdown deferred — raise in OFB-015 scope if needed.**

4. **Assumption**: The `GSI_LEDGER_DATE` sort key is `sk` (same as the billing table at
   `scripts/local-ddb-init.py:72`). An alternative would be `ts` (numeric), which would allow
   range queries within a day. `sk` is chosen for consistency with the existing design. If OFB-015
   requires intra-day time ordering, change to `ts` with `attr_types={"ts": "N"}`. **Confirm with
   OFB-015 implementor.**

5. **Open**: Is a `reverse_ap_payable` function (for PO cancellation after receipt) in scope for
   PUR-009 or deferred to PUR-007's cancel-after-receipt addendum? The ticket text does not mention
   cancellation of received POs. Assumed deferred.

6. **Assumption**: The `purchase_orders` table key attributes are `po_id` (PK) and `sk` (SK), per
   `docs/ofbiz/specs/PUR-006.md:72–73`. PUR-009 writes with `key_name="po_id"` throughout.

7. **Assumption**: The billing table (`T.billing`) is NOT used at all by PUR-009. Supplier
   payables are a firm liability of the organisation (not a user receivable/payable), so they
   do not belong in the user-keyed billing table. **Confirm this separation is acceptable for
   OFB-014 GL mapping** — the GL poster will need to query `T.purchase_orders` `GSI_LEDGER_DATE`
   for `purchase_payable` entries in addition to `T.billing`.
