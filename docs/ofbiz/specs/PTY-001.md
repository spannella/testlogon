# PTY-001 — Party/CRM feature flag & settings keys

**Type:** Chore | **Priority:** P0 | **Estimate:** 1 day  
**Milestone:** 1 — Scaffolding & Data Model

---

## 1. Summary & Goal

PTY-001 is the foundation ticket for the entire OFBiz Party/CRM buildout. It introduces three new boolean feature flags and one table-name key into `app/core/settings.py`, wires the `party` table handle into `app/core/tables.py`, and documents both additions in `.env.local.example` and `CLAUDE.md`. No business logic, no new DynamoDB table definition (that is PTY-002), and no router/service files are modified — the sole deliverable is the flag scaffold that every downstream ticket will gate behind.

The goal is to ensure:
- All three flags default to `False` (off) with no environment variable set, so the production binary can ship the new code before the feature is exposed to users.
- No existing settings key, table name, or runtime behavior changes — the diff is purely additive.
- A minimal pytest asserts all three flags default off, following the established pattern for offline settings tests in this repo.

## 2. Context & Current State

### Existing feature-flag patterns

Boolean feature flags in this codebase follow one of two idioms, both defined as fields on the frozen `Settings` dataclass (`app/core/settings.py:6`):

**Idiom A — default OFF (the pattern PTY-001 must follow):**
```python
browser_ssh_terminal_enabled: bool = os.environ.get("BROWSER_SSH_TERMINAL_ENABLED", "0") not in ("0", "false", "False")
```
(`app/core/settings.py:124`) — the default string is `"0"`, which is in the reject-set, so `not in` evaluates to `False`. This is the canonical default-off pattern.

A second default-off variant appears for the newsfeed recsys:
```python
newsfeed_recsys_enabled: bool = os.environ.get("NEWSFEED_RECSYS_ENABLED", "false").lower() in ("1", "true", "yes", "on")
```
(`app/core/settings.py:2014`) — the allow-set idiom. Either variant produces the same `False` default; Idiom A is more common (used by `browser_ssh_terminal_enabled`, `messaging_transcription_enabled`, `messaging_tts_enabled`).

**Related sub-flag cluster example** (`app/core/settings.py:1875–1877`):
```python
messaging_translation_enabled: bool = os.environ.get("MESSAGING_TRANSLATION_ENABLED", "1") not in ("0", "false", "False")
messaging_transcription_enabled: bool = os.environ.get("MESSAGING_TRANSCRIPTION_ENABLED", "0") not in ("0", "false", "False")
messaging_tts_enabled: bool = os.environ.get("MESSAGING_TTS_ENABLED", "0") not in ("0", "false", "False")
```
PTY-001's three flags follow this cluster pattern.

## 3. Data Model

PTY-001 itself introduces no DynamoDB table or schema — it only names the table that PTY-002 will create. The sole data-model artifact is the settings key:

| Setting field | Env var | Default | Type | Purpose |
|---|---|---|---|---|
| `party_crm_enabled` | `PARTY_CRM_ENABLED` | `False` | `bool` | Master gate for the entire Party/CRM feature surface |
| `party_crm_contacts_migration_enabled` | `PARTY_CRM_CONTACTS_MIGRATION_ENABLED` | `False` | `bool` | Sub-flag: allow migration of legacy contacts into party records |
| `party_crm_org_accounts_enabled` | `PARTY_CRM_ORG_ACCOUNTS_ENABLED` | `False` | `bool` | Sub-flag: enable B2B organisation account APIs (PTY-008+) |
| `party_table_name` | `DDB_PARTY_TABLE` | `"party"` | `str` | DynamoDB table name for the `party` single-table store |

**Sub-flag semantics:**
- `party_crm_contacts_migration_enabled` is only meaningful when `party_crm_enabled` is also `True`. The migration service (PTY-006) must check both.
- `party_crm_org_accounts_enabled` is only meaningful when `party_crm_enabled` is `True`. The org-accounts router (PTY-008) must check both. Neither sub-flag is checked by PTY-001 itself.
- With all three flags at their defaults (`False`), every later PTY router that uses `_require_party_crm_enabled()` (defined in a later ticket) will return `503 {"detail": "Party/CRM feature is disabled"}` before touching DynamoDB.

## 5. Detailed Behavior & Edge Cases

### Flag off (default): complete no-op

With `PARTY_CRM_ENABLED` unset or `"0"`:
- `S.party_crm_enabled` is `False`.
- `T.party` resolves to a handle that will raise `ResourceNotFoundException` on any DynamoDB call, but no code calls it because every downstream router/service will guard on `party_crm_enabled`.
- Existing `contacts` (`app/routers/contacts.py`), `addresses` (`app/services/addresses.py`), `profile`, and `users` subsystems are byte-for-byte unchanged.
- The `GET /ui/config` endpoint (which serialises select settings for the frontend) does not expose `party_crm_enabled` until a later ticket adds it explicitly — no frontend change in PTY-001.

### Flag `True` with no table yet (pre-PTY-002 state)

If a developer sets `PARTY_CRM_ENABLED=1` before running PTY-002's DDB init, `T.party` is a valid handle but any call to it returns `ResourceNotFoundException`. This is expected and acceptable during development; PTY-002 creates the table.

### Sub-flag independence

`party_crm_contacts_migration_enabled=True` with `party_crm_enabled=False` must be treated as fully off by migration code. The migration service (PTY-006) must check:
```python
if not S.party_crm_enabled or not S.party_crm_contacts_migration_enabled:
    raise HTTPException(503, "Party/CRM migration is disabled")
```
PTY-001 does not enforce this; it only defines the flags. The enforcement spec belongs to PTY-006.

### Env-var naming convention

The `DDB_` prefix is used for some table names (`DDB_CONTACTS_TABLE`, `DDB_PARTY_TABLE`) and not others (`ADDRESSES_TABLE_NAME`, `PROFILE_TABLE_NAME`). The ticket explicitly specifies `DDB_PARTY_TABLE` (following `DDB_CONTACTS_TABLE`), so this must not be changed to `PARTY_TABLE_NAME` for consistency — the spec matches the ticket's exact env-var names.

### Settings dataclass is frozen

`Settings` is `@dataclass(frozen=True)` (`app/core/settings.py:6`). Tests that need to flip a flag must use `object.__setattr__(S, "party_crm_enabled", True)` — the same pattern used in `tests/test_gap_0151_fan_club_feature_flag.py:26`.

## 6. Feature Flag & Config

| Key | Env var | Default | Notes |
|---|---|---|---|
| `S.party_crm_enabled` | `PARTY_CRM_ENABLED` | `False` | Master gate; checked by every PTY router |
| `S.party_crm_contacts_migration_enabled` | `PARTY_CRM_CONTACTS_MIGRATION_ENABLED` | `False` | Sub-gate for PTY-006 migration paths |
| `S.party_crm_org_accounts_enabled` | `PARTY_CRM_ORG_ACCOUNTS_ENABLED` | `False` | Sub-gate for PTY-008+ org endpoints |
| `S.party_table_name` | `DDB_PARTY_TABLE` | `"party"` | DynamoDB table name consumed by PTY-002+ |

**Flag semantics:**

- All flags are evaluated at import time (the `Settings` dataclass is instantiated once as `S = Settings()` at `app/core/settings.py:2772`). Changing the env var at runtime after process start has no effect.
- In the local dev stack the flags remain `0` (off) by default, so existing E2E suites run against a codebase with PTY-001 landed without any new table or endpoint being active.
- Turning on `PARTY_CRM_ENABLED=1` in `.env.local` without re-running `scripts/local-ddb-init.py` (PTY-002's work) will leave `T.party` pointing at a non-existent table — acceptable as a dev-time guard.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity:** The flag is a single boolean field on the shared `Settings` dataclass; there is no `dev_mode` branch, mock path, or separate prod code. The same code evaluates `PARTY_CRM_ENABLED` in both environments. This satisfies SECOPS-007.

**Idempotency:** Settings are read-only (frozen dataclass). Re-running `scripts/local-ddb-init.py` after PTY-001 is merged has no effect from PTY-001's perspective (no new `TableDef` is added in this ticket).

**Security:** Adding a new `str` setting `party_table_name` with a safe default (`"party"`) poses no security risk. The flag fields are `bool`; there is no code path that reads them at this ticket's scope. No new secret or credential is introduced.

**Tables dataclass is frozen:** `T = Tables(...)` is also a `@dataclass(frozen=True)`. Mutating `T.party` for tests requires `object.__setattr__(T, "party", mock_table)` — same pattern as existing hermetic tests (e.g. `tests/test_gap_0220_0221_ssh_stored_key.py`).

## 8. Backward Compatibility & Migration

**No migration required.** This ticket is purely additive:

- Existing settings fields are unchanged. The `Settings` dataclass gains four new fields with defaults; old deployments that don't set the env vars see identical behaviour.
- `app/core/tables.py` gains two lines (one field, one handle assignment). The `Tables` dataclass is frozen but adding a field is backward-compatible for constructors that use keyword arguments — and the single `T = Tables(...)` call at the bottom of `tables.py` is the only constructor site, so the new kwarg is added there simultaneously.
- No DynamoDB table is created in this ticket; `T.party` simply resolves to a handle for a table that does not yet exist locally. This is safe: existing startup probes do not iterate `T` fields, so there is no health-check that would fail on a missing table.
- The `.env.local.example` addition is documentation-only; existing `.env.local` files (gitignored) are unaffected.
- `CLAUDE.md` update is documentation-only.

**Rollback:** Remove the four fields from `Settings`, the one field and one constructor kwarg from `Tables`, the appended stanza in `.env.local.example`, and the two CLAUDE.md rows. No DynamoDB resources exist to clean up.

## 10. Open Questions / Assumptions

1. **Assumption:** The ticket specifies `DDB_PARTY_TABLE` (matching `DDB_CONTACTS_TABLE` prefix convention) rather than `PARTY_TABLE_NAME` (matching `ADDRESSES_TABLE_NAME` / `PROFILE_TABLE_NAME` convention). 3. **Assumption:** `party_crm_enabled` is checked by a `_require_party_crm_enabled()` guard function defined in a later ticket (PTY-004 or PTY-005), not in PTY-001 itself. PTY-001 does not add any guard function or router dependency.

4. **Assumption:** The `T.party` handle is added in PTY-001 (alongside the settings key) rather than waiting for PTY-002 (the table definition ticket). This is consistent with how other tables are wired: the handle exists from day 1 and raises `ResourceNotFoundException` at call time if the table is absent — it never prevents import. PTY-002 will create the actual DynamoDB table.

5. **Open question:** Should PTY-001 also add a `party` field to the `GET /ui/config` frontend config endpoint (so the React app can read `party_crm_enabled`)? The ticket does not mention this, and no other purely scaffolding ticket touches the config endpoint. This is deferred to the first PTY ticket that adds a frontend page.

6. **Open question:** Is there a need for a `party_crm_admin_enabled` sub-flag for admin-only Party endpoints, separate from `party_crm_enabled`? The current ticket lists only three flags. Deferred to PTY-004/PTY-005 design.

7. **Assumption:** `CLAUDE.md` and `.env.local.example` updates are within PTY-001's scope even though they are documentation files. The ticket acceptance criteria explicitly lists them.
