# ECM-014 — Order fulfillment endpoint + order detail/tracking page

## 1. Summary & Goal

ECM-014 has two deliverables that together close the post-purchase loop for the store integration:

1. **Backend HTTP endpoint** `GET /ui/shoppingcart/orders/{order_id}/fulfillment` — a thin router handler in `app/routers/shoppingcart.py` that enforces `require_ui_session`, calls `order_fulfillment_status(order_id, user_sub=ctx["user_sub"])` from ECM-012 (`app/services/store_integration.py`), and returns `OrderFulfillmentStatusOut`.

2. **Frontend order detail/tracking page** — a new React page `frontend/src/pages/shop/OrderDetail.tsx` that renders the lifecycle timeline and per-ship-group tracking links for a given `order_id`, reachable at the route `/orders/:orderId`. The checkout success screen (`frontend/src/pages/shop/Checkout.tsx:184`) is updated to show a "View Order" link to this page when the integration is on. The route and a nav entry in the Commerce sidebar group are both flag-gated so with `STORE_SHOW_FULFILLMENT_STATUS` off there is zero new surface area.

The result is: buyer completes checkout → success screen links to `/orders/{order_id}` → page calls `GET /ui/shoppingcart/orders/{order_id}/fulfillment` → page renders timeline + tracking links. All of this is additive and default-off; the existing cart/checkout/billing paths are byte-for-byte unchanged with the flag off.

## 4. API / Service Design

### 4.1 Backend endpoint

**File:** `app/routers/shoppingcart.py` (appended after line 173, after the existing `/carts/{cart_id}/total` handler)

**Declaration order:** the new path `/orders/{order_id}/fulfillment` contains no static segment that conflicts with existing paths under `/ui/shoppingcart/`. All existing paths start with `/carts/`; the new path starts with `/orders/`. No FastAPI route-ordering concern arises (unlike the `schedules`-before-`/{export_id}` case in `app/routers/audit_export.py`).

```python
from app.models import OrderFulfillmentStatusOut

@router.get("/orders/{order_id}/fulfillment", response_model=OrderFulfillmentStatusOut)
async def ui_get_order_fulfillment(
    order_id: str,
    ctx=Depends(require_ui_session),
) -> OrderFulfillmentStatusOut:
    if not S.store_integration_enabled or not S.store_show_fulfillment_status:
        raise HTTPException(503, "Order fulfillment tracking is not enabled")
    from app.services.store_integration import order_fulfillment_status
    return order_fulfillment_status(order_id, user_sub=ctx["user_sub"])
```

**Auth dependency:** `require_ui_session` from `app/services/sessions.py` (imported at `shoppingcart.py:28`; used at `shoppingcart.py:54`). Returns `ctx` dict containing `ctx["user_sub"]`.

**Ownership enforcement:** delegated entirely to `order_fulfillment_status` in the service layer. The service raises `HTTPException(403)` when `item["user_id"] != user_sub` and `HTTPException(404)` when the order does not exist.

**503 guard:** The router performs a two-flag check (`store_integration_enabled AND store_show_fulfillment_status`) before calling the service. This is a defense-in-depth gate — the service's `_integration_enabled()` also gates — but explicit checks in the router make the behavior observable at the HTTP layer without needing to import the service.

**Late import of `store_integration`:** The `from app.services.store_integration import order_fulfillment_status` is a local import inside the handler. This avoids a circular-import risk (the shoppingcart router already imports from `app.services.shoppingcart` which imports from many shared modules) and follows the pattern used for `from app.services.invoices import create_invoice_safe` at `shoppingcart.py:698`.

**HTTP semantics:**

| Status | Condition |
|---|---|
| 200 | Owner calls with valid `order_id`; returns `OrderFulfillmentStatusOut` |
| 403 | `order["user_id"] != ctx["user_sub"]` |
| 404 | No item in `T.orders` for this `order_id` |
| 503 | Either integration flag off |

**`main.py` changes:** None. The `shoppingcart_router` is already registered at `app/main.py:670` (`from app.routers.shoppingcart import router as shoppingcart_router` at `main.py:71`). The new handler is appended to the same `router` object in `shoppingcart.py`.

### 4.3 `OrderDetail` page component

**File:** `frontend/src/pages/shop/OrderDetail.tsx` (new file)

**Route parameter:** `orderId` via `useParams()` from `react-router-dom`.

**React Query fetch:**

```ts
const fulfillmentQuery = useQuery({
  queryKey: ["order-fulfillment", orderId],
  queryFn: () => getOrderFulfillmentStatus(orderId!),
  enabled: !!orderId,
  retry: 1,
  staleTime: 30_000,
});
```

Cache key `["order-fulfillment", orderId]` matches the convention documented in ECM-013 §4.2 so invalidations from other surfaces hit the same cache entry.

**Loading state:** `Skeleton` components (from `@/components/ui/skeleton`, same as `Checkout.tsx:18`) for the header card and timeline while `fulfillmentQuery.isLoading`.

**Error state:** If the query returns a 403 (non-owner) or 404, `ApiError` is caught and an appropriate message is rendered without a full-page crash. The `api.get` wrapper in `api/client.ts` throws `ApiError`; React Query surfaces this as `fulfillmentQuery.error`.

**Page sections (top to bottom):**

1. **Breadcrumb / back link** — `<Button variant="ghost" onClick={() => navigate(-1)}>` with `ArrowLeft` icon.
2. **Order summary card** — `order_id` (truncated to 12 hex chars, matching `Checkout.tsx:192`'s `orderId.slice(0, 12)`), `created_at`, `amount_cents` formatted via `Intl.NumberFormat`, `currency`. Shows `legacy_status` badge when `flag_active === false`.
3. **Lifecycle timeline** — rendered only when `fulfillment.lifecycle_status` or `fulfillment.fulfillment_status` is present. Reuses `ShippingTimeline` from `frontend/src/pages/purchases/ShippingTimeline.tsx` when the lifecycle steps map cleanly, or renders a thin `OrderLifecycleTimeline` inline component for ORD-specific step labels (`created → approved → picking → packed → shipped → delivered`). Step dates come from `ship_groups[0].shipped_at` for the "Shipped" step.
4. **Ship group cards** — one `Card` per `ship_group` in `fulfillment.ship_groups`. Each card shows: ship-group ID, `fulfillment_sub_status` badge, and — when `tracking_number` is present — a tracking link rendered as `<a href={tracking_url} target="_blank" rel="noopener noreferrer">`. The `tracking_url` comes directly from the API response (computed server-side by `build_tracking_url`; never constructed in the frontend).
5. **Status history accordion** — collapsed by default using `shadcn/ui` `Collapsible` or a plain `<details>` element. Lists `status_history` rows (newest-first from the service) showing `from_status → to_status`, `actor`, `reason`, and `ts`. Shown only when `status_history.length > 0`.

**Flag-off rendering:** When `fulfillment.flag_active === false` (all flags off), the page renders only the order summary card with the `legacy_status` badge. The timeline and ship-group sections are hidden. A note `"Detailed tracking is not available for this order"` is shown in their place.

**Imports:** `useParams`, `useNavigate` from `react-router-dom`; `useQuery` from `@tanstack/react-query`; `getOrderFulfillmentStatus` from `@/api/endpoints/orders`; `OrderFulfillmentStatus`, `ShipGroup` from `@/api/types`; `ShippingTimeline` from `../purchases/ShippingTimeline`; shadcn/ui primitives `Card`, `CardContent`, `CardHeader`, `CardTitle`, `Badge`, `Button`, `Skeleton`; `ArrowLeft`, `Package`, `Truck`, `ExternalLink` from `lucide-react`.

## 5. Detailed Behavior & Edge Cases

**Ownership on endpoint.** The service (ECM-012) raises `HTTPException(403)` before any enrichment when `item["user_id"] != user_sub`. The router handler propagates this directly; FastAPI serializes it as `{"detail": "Forbidden"}` with status 403.

**Order not found.** `T.orders.get_item(Key={"order_id": order_id})` returns `{}` (DynamoDB never raises on a miss per CLAUDE.md). The service raises `HTTPException(404, "Order not found")`. Frontend `OrderDetail` handles `fulfillmentQuery.error` and renders a "Order not found" message with a back-navigation button.

**Flag-off 503 on the endpoint.** The router handler returns 503 before calling the service. The frontend `OrderDetail` catches `ApiError` with `status === 503` and renders a "Order tracking is not available" message rather than an error crash.

**`orderId` undefined in `OrderDetail`.** `useParams()` can return `undefined` for unmatched routes. The `enabled: !!orderId` guard on the query prevents a fetch with an empty string. The page renders a "No order specified" message when `!orderId`.

**Navigation from Checkout.** The "Track Order" button navigates to `/orders/${orderId}`. Because `OrderDetail` is lazy-loaded, React Suspense needs a fallback. `App.tsx` already wraps `Suspense` around the lazy route tree; no new `Suspense` boundary is needed.

**Stale data on tracking page.** Shipment status can advance while the buyer is viewing the page. The `staleTime: 30_000` setting means the query refetches after 30 seconds when the tab re-focuses. The user can also trigger a manual refetch by clicking a "Refresh" button (optional, low-priority polish). No polling is implemented in the frontend (the carrier-tracking poller runs server-side via `carrier_tracking_poller.py`).

**Carrier tracking URL construction.** `tracking_url` is returned by the backend from `build_tracking_url(carrier, tracking_number)` (`app/services/carrier_tracking.py:33`). It is `null` for unknown carriers (returned as `None` in Python → `null` in JSON). The frontend renders a link only when `tracking_url` is truthy; otherwise shows the `tracking_number` as plain text.

**Multiple ship groups.** When `ship_groups.length > 1`, each group renders in a separate `Card` with its own status badge and tracking section. Groups with `fulfillment_sub_status === "picking"` and no `tracking_number` render as "In preparation" with no tracking link.

**Decimal coercion on `amount_cents`.** DynamoDB returns numeric attributes as Python `Decimal`. `OrderFulfillmentStatusOut.amount_cents` must be declared as `Optional[int]` and the service must coerce `int(item.get("amount_cents", 0))` before constructing the Pydantic model. This matches the existing `shoppingcart._ddb_int` pattern (`app/services/shoppingcart.py:46`).

**`created_at` ISO string.** The `orders` table stores `created_at` as an ISO string (set by `_now_iso()` at `commerce_order_service.py:65`). The frontend formats it using `new Date(createdAt).toLocaleDateString(...)` (no epoch conversion needed, unlike Unix timestamps).

**CSRF.** This is a `GET` endpoint; CSRF is not required. The `require_ui_session` dependency still validates the session cookie. Bearer-auth requests also work (they bypass CSRF per CLAUDE.md).

**No write path; no billing touch.** This ticket is pure read on the backend. No ledger entry, no payment method access, no `refund_payment` call.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**No dev/prod code fork in the endpoint.** The `ui_get_order_fulfillment` handler calls `order_fulfillment_status` without any `S.dev_mode` branch. In dev, `T.orders` and `T.shipments` are DynamoDB Local handles (`scripts/local-ddb-init.py:288`); in prod they are real DynamoDB handles. The `_safe_upstream` wrapper in ECM-012 handles both — a missing table in dev degrades to the legacy response the same way it would in prod.

**Idempotency.** The endpoint is a pure read (GET). No writes occur; idempotency is trivially satisfied.

**Ownership before enrichment.** The 403 check in the service (`item["user_id"] != user_sub`) runs unconditionally on the first DDB read, before any enrichment queries. No partial data is returned to a non-owner — the exception is raised before `_fetch_lifecycle_rows` or `_fetch_shipments` is called. This prevents an information-disclosure window where an attacker could infer lifecycle state from a timing side-channel.

**No PII in ship group.** `ShipGroupFulfillmentOut.tracking_url` is a public carrier URL (no secret material). `address_ref` is an opaque identifier, not a formatted address. The buyer's delivery address is not projected into the endpoint response.

**`encodeURIComponent` on `orderId` in frontend.** The TS wrapper (`getOrderFulfillmentStatus`) applies `encodeURIComponent(orderId)` to prevent injection via a crafted `order_id` string. The `order_id` is a deterministic 32-hex-char SHA-256 prefix (`commerce_order_service.py:67`) so in practice it is safe, but the encoding is applied defensively.

**503 rather than 404 for disabled feature.** Returning 503 (not 404) for a disabled feature flag is the project convention used across multiple feature-gated routers (e.g. `app/routers/call_recording.py:41`, `app/routers/chat_bot.py:83`). Note: `app/routers/inventory.py` uses 404 for its `_require_enabled()` gate — that is not the model to follow here. 503 distinguishes "feature not enabled" from "resource does not exist" (404) for clients and monitoring dashboards.

**Audit event.** The endpoint does not write an audit event because it is a read. The underlying `order_fulfillment_status` service does not write one either (ECM-012 §7). If audit logging for order reads is needed, it should be added to ECM-012's service layer (outside ECM-014 scope).

## 8. Backward Compatibility & Migration

**Existing routes unchanged.** The new path `/ui/shoppingcart/orders/{order_id}/fulfillment` starts with `/orders/` which does not conflict with any existing path under the `/ui/shoppingcart/` prefix (all current paths use `/carts/`).

**Existing `ShoppingCartPurchaseOut` unchanged.** The `CartPurchase` TS interface at `types.ts:2094` does not gain new fields from ECM-014. The Checkout component's mutation handler at `Checkout.tsx:136–143` is unchanged; the only addition is the conditional "Track Order" button that reads `data.order_id` (already in state) without modifying `data`.

**Existing purchase-history tracking surface unchanged.** `GET /ui/purchases/transactions/{txn_id}/tracking` (`app/routers/purchase_history.py:118`) continues operating independently. The new `/orders/{order_id}/fulfillment` endpoint reads from the same underlying `orders` and `shipments` tables but does not modify `purchase_transactions` rows. Buyers who use the existing `/purchases` page continue to see the same transaction tracking view.

**No DDB migration.** All new tables (`shipments`) and new fields (`lifecycle_status`, `fulfillment_status`, `SHIPGRP#` rows) are additive and owned by upstream tickets. Orders created before ORD-007 was deployed simply return `lifecycle_status: null` and `ship_groups: []` from ECM-012, which is valid per the Pydantic model. `OrderDetail.tsx` renders gracefully for these older orders (shows only the order summary card).

**Frontend routes are opt-in.** The `/orders/:orderId` route is conditionally registered only when `storeConfig.store_show_fulfillment_status` is true. Users who bookmark the URL while the flag is off see a "route not matched" error or are redirected to `/shop`. A simple fallback in `OrderDetail` (`if (!storeConfig) return <Navigate to="/purchases" />`) ensures graceful degradation.

**Sidebar nav is additive.** The new "Order Tracking" entry is appended to the Commerce section array; existing entries are not reordered. Because the array is constructed with a spread operator for the conditional entry, the items above it are byte-for-byte unchanged.

**Pattern:** mirrors `tests/test_gap_0223_0224_ec2_host_inventory.py` — moto in-memory DDB tables bound to the frozen `T` handles via `object.__setattr__`, frozen `S` flags flipped the same way, route handlers called directly as coroutines on a fresh `asyncio.new_event_loop()`.

No `TestClient` is used (broken in this env per CLAUDE.md). The handler is called as a coroutine directly:

```python
import asyncio
from unittest.mock import MagicMock, patch
import moto, boto3, pytest
from app.routers.shoppingcart import ui_get_order_fulfillment
from app.core.settings import S
from app.core import tables as T_mod

@pytest.fixture(autouse=True)
def _tables(monkeypatch):
    with moto.mock_aws():
        ddb = boto3.resource("dynamodb", region_name="us-east-1")
        orders_tbl = ddb.create_table(
            TableName="orders",
            KeySchema=[{"AttributeName": "order_id", "KeyType": "HASH"}],
            AttributeDefinitions=[{"AttributeName": "order_id", "AttributeType": "S"}],
            BillingMode="PAY_PER_REQUEST",
        )
        object.__setattr__(T_mod.T, "orders", orders_tbl)
        # also patch T.shipments to a minimal in-memory table or MagicMock
        object.__setattr__(S, "store_integration_enabled", True)
        object.__setattr__(S, "store_show_fulfillment_status", True)
        object.__setattr__(S, "order_lifecycle_enabled", False)
        object.__setattr__(S, "shipping_enabled", False)
        yield orders_tbl

def _fake_ctx(user_sub: str) -> dict:
    return {"user_sub": user_sub}

def run(coro):
    return asyncio.new_event_loop().run_until_complete(coro)
```

**Test cases:**

1. **Happy path — owner, flag on.** Seed `orders_tbl` with `order_id="abc123"`, `user_id="alice"`, `status="pending_payment"`, `amount_cents=4999`, `currency="USD"`. Call `run(ui_get_order_fulfillment("abc123", ctx=_fake_ctx("alice")))`. Assert: response has `order_id="abc123"`, `legacy_status="pending_payment"`.

2. **Ownership enforcement — foreign caller.** Same seed. Call with `ctx=_fake_ctx("bob")`. Assert `HTTPException` with `status_code=403`.

3. **Order not found.** Call with `order_id="nonexistent"`. Assert `HTTPException` with `status_code=404`.

4. **Flag off — master flag.** `object.__setattr__(S, "store_integration_enabled", False)`. Call with valid owner. Assert `HTTPException` with `status_code=503`.

5. **Flag off — sub-flag.** `store_integration_enabled=True`, `store_show_fulfillment_status=False`. Call. Assert 503.

6. **Degrade gracefully — `order_fulfillment_status` raises.** Patch `app.routers.shoppingcart.order_fulfillment_status` to raise `RuntimeError("upstream failure")`. Assert `RuntimeError` propagates (ECM-012's `_safe_upstream` wrapper covers upstream DDB errors; a total service failure surfaces as 500, which is acceptable — the test confirms the handler does not silently swallow it).

7. **`amount_cents` Decimal coercion.** Seed `amount_cents` as `Decimal("2500")`. Assert response `amount_cents == 2500` (int).

8. **Response model validates.** Assert `isinstance(result, OrderFulfillmentStatusOut)` and `result.flag_active == True` when enrichment succeeds, `False` when flags off.

The above tests isolate the **router layer**. ECM-012's service tests (in `tests/test_ecm_012_fulfillment_status.py`) cover the full service behavior including ship-group merging, degrade paths, and multi-group scenarios.

## 10. Open Questions / Assumptions

1. **Assumption: `StoreConfig` and `useStoreConfig` (ECM-013) are available at the `App.tsx` top level.** If the `useStoreConfig` hook is not hoisted into `App.tsx` (e.g. if it is only used inside shop pages), the conditional route registration needs an alternative approach — e.g. a `<StoreIntegrationGuard>` wrapper component that fetches the config and conditionally renders its children. ECM-014 assumes the simpler hook-at-App approach; the implementor should confirm with ECM-013.

2. **Assumption: `/orders/:orderId` is the correct route path.** The ticket spec says "alongside `cart/checkout` at `App.tsx:363`". An `orders` root-level path is proposed. If `orders` conflicts with an existing route (no conflict found in the current `App.tsx:355–379`), an alternative such as `order-detail/:orderId` can be used.

3. **Open: should `OrderDetail` be accessible from the existing `/purchases` page?** The `/purchases` page shows `purchase_transactions` records with `external_ref=order_id`. A "View Fulfillment" link from `TransactionDetail.tsx` to `/orders/{external_ref}` would close the UX loop without requiring a separate nav entry. This is a UX enhancement outside ECM-014's scope but should be tracked as a follow-up.

4. **Open: `ShippingTimeline` reuse vs. new `OrderLifecycleTimeline`.** The existing `ShippingTimeline` uses `txnStatus` (COMPLETED/CANCELLED/etc.) — the purchase-transaction status vocabulary — not the ORD lifecycle vocabulary (`created/approved/picking/packed/shipped/delivered`). If the step labels and colour semantics differ, a thin `OrderLifecycleTimeline` inline component is preferred over bending `ShippingTimeline`'s prop interface. This should be confirmed with the designer before implementation.

5. **Assumption: `flag_active` field on `OrderFulfillmentStatusOut` is available.** Confirmed by pass 3: ECM-012 spec §4.2 explicitly includes `flag_active: bool = False` on `OrderFulfillmentStatusOut`. ECM-003's simpler definition does not list it, but ECM-012 is the authoritative spec for the full model shape (ECM-003 defines a base shape; ECM-012 extends it with operational fields). The field is confirmed present; no fallback to inferring from `lifecycle_status` is needed.

6. **Open: does the nav entry point to `/orders` (a list) or `/purchases`?** ECM-014 proposes pointing the "Order Tracking" sidebar entry to `/purchases` (the existing purchase history page) in the absence of a dedicated order-list page. A dedicated `/orders` list page (showing only ERP orders) is out of scope for ECM-014; if needed it becomes ECM-016.

7. **Assumption: `useStoreConfig` fetches `GET /ui/store/config` (ECM-013) and returns `DEFAULT_STORE_CONFIG` (all false) while loading.** ECM-013 spec §4.4 confirms the hook signature is `useStoreConfig(): StoreConfig` (never returns `null`) and returns `data ?? DEFAULT_STORE_CONFIG`. ~~Returns `null` while loading~~ — this was incorrect. The Checkout and Sidebar components may use the non-null-safe form `storeConfig.store_show_fulfillment_status` safely (it is always a `StoreConfig`), though the nullish-safe `storeConfig?.store_show_fulfillment_status` also works. Note: `GET /ui/store/config` backend endpoint is owned by ECM-013 (not ECM-002, per ECM-002 spec §4.3 which adds no router).
