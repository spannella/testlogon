# OFB-009 — RMA approve/reject + receive → restock

## 1. Summary & Goal

OFB-009 is the admin-decision slice of the Returns/RMA lifecycle introduced in OFBiz Milestone 3. Its scope is:

1. Admin endpoints (`ADMIN` or `ROOT` role, CSRF-enforced) to **approve** or **reject** a customer return request, and to **mark it received**.
2. On the `received` transition, **restock** the returned quantity back into the inventory system via `inventory.adjust(sku, +qty, reason="rma_restock")` (OFB-003), incrementing on-hand exactly once.
3. Guard the restock side-effect behind the inventory feature flag (`INVENTORY_RESERVATIONS_ENABLED`) so RMA approve/reject/receive still works correctly when inventory is disabled — the only missing effect is the on-hand increment.
4. Notify the requesting customer (via the existing alert plumbing) after each state change.
5. All transitions are idempotent under replay using a single-writer conditional `status` guard in DynamoDB.

This ticket does not own the refund step (OFB-010) or any frontend (OFB-011), but all four admin actions (approve, reject, receive, and the OFB-010 refund) share the same `returns_rma_router` registered in `app/main.py:878`.

OFB-009 introduces no new tables. All data lives in the existing `returns` table (OFB-008).

### `returns` table — single-table layout

| PK (`return_id`) | SK (`sk`) | Purpose |
|---|---|---|
| `{uuid32}` | `META` | Return header — carries status, decision fields, actor, timestamps |
| `{uuid32}` | `ITEM#{n}` (n = 1, 2, …) | Per-line row — sku, quantity, amount_cents |

**Header row attributes relevant to OFB-009**

| Attribute | Type | Written by |
|---|---|---|
| `status` | S | `_transition` — conditional flip |
| `decided_by` | S | `approve_return`, `reject_return` — admin `user_sub` |
| `decision_note` | S | `approve_return`, `reject_return` — optional free text |
| `updated_at` | N | `_transition` — `now_ts()` on every flip |

**OFB-010 fields** (written by `refund_return`, not in scope for OFB-009 but present on the same META row):

| Attribute | Type |
|---|---|
| `refund_amount_cents` | N |
| `refund_ledger_sk` | S |
| `provider` | S |

### Valid status machine

```
requested → approved  → received → refunded → closed
         ↘ rejected
          (approved can also be rejected)
```

`_VALID_TRANSITIONS` (`returns_rma.py:53`):

```python
{
    "requested": {"approved", "rejected"},
    "approved":  {"received", "rejected"},
    "received":  {"refunded"},
    "refunded":  {"closed"},
    "rejected":  set(),
    "closed":    set(),
}
```

`approved` can be rejected (e.g., admin cancels after approving before goods arrive). Terminal states `rejected` and `closed` have no exits.

### GSI layout

Both GSIs carry only `META` rows (line rows do not carry `order_id` or a `status` attribute — `list_returns_by_status` filters for `sk == "META"` post-query at `returns_rma.py:306`).

```
GSI_STATUS  PK=status (S)   SK=created_at (N)
GSI_ORDER   PK=order_id (S) SK=created_at (N)
```

`attr_types={"created_at": "N"}` in `scripts/local-ddb-init.py:2491` is mandatory — omitting it causes DynamoDB to store the numeric timestamp as String, breaking integer range queries.

## 4. API / Service Design

### Service layer (`app/services/returns_rma.py`)

#### `approve_return`

```python
def approve_return(
    return_id: str,
    *,
    actor_sub: str,
    note: Optional[str] = None,
) -> Dict[str, Any]:
```

1. `_require_enabled()` — 404 when `RETURNS_RMA_ENABLED=false`
2. `_load_return(return_id)` — query all rows; 404 if header missing
3. `_require_transition(current_status, "approved")` — 409 for illegal transitions; no-op if already `approved`
4. `_transition(return_id, "requested", "approved", extra_set={"decided_by": actor_sub, "decision_note": note})` — single-writer conditional `update_item` with `ConditionExpression="#s = :from"`. Returns `ALL_OLD` on success, `None` if the condition failed (concurrent / replay)
5. On `None` → return current state (idempotent)
6. `_audit("rma.approved", ...)` + `_notify(requester_sub, "Return approved", ...)`
7. Return `_return_header_out(...)` via `get_return(return_id)`

#### `reject_return`

```python
def reject_return(
    return_id: str,
    *,
    actor_sub: str,
    note: Optional[str] = None,
) -> Dict[str, Any]:
```

Identical structure to `approve_return` with two differences:
- `_require_transition(current_status, "rejected")` accepts both `requested` and `approved` as source (per `_VALID_TRANSITIONS`)
- `_transition(return_id, current_status, "rejected", ...)` passes `current_status` (not the literal `"requested"`) as `from_status` so both `requested → rejected` and `approved → rejected` go through the same code path

#### `receive_return`

```python
def receive_return(
    return_id: str,
    *,
    actor_sub: str,
) -> Dict[str, Any]:
```

1. `_require_enabled()` — 404 when flag off
2. `_load_return(return_id)` — load header + all line rows (lines needed for restock)
3. `_require_transition(current_status, "received")` — only `approved → received` is valid
4. `_transition(return_id, "approved", "received", actor_sub=actor_sub)` — single-writer guard
5. On `None` → return current state (idempotent replay; restock already ran on the first transition)
6. **Restock** (only on first successful transition):
   ```python
   if bool(getattr(S, "inventory_reservations_enabled", False)):
       for ln in lines:
           if ln["sku"] and ln["quantity"] > 0:
               inv.adjust(sku, qty, reason="rma_restock", user_sub="system")
   ```
   - Wrapped in `try/except` — restock failure must not roll back the `received` status
   - `reason="rma_restock"` identifies the adjustment in the `inventory.adjust` audit trail
7. `_audit("rma.received", ...)` + `_notify(requester_sub, "Return received", ...)`

#### `_transition` (core primitive)

```python
def _transition(
    return_id: str,
    from_status: str,
    to_status: str,
    *,
    actor_sub: str,
    extra_set: Optional[Dict[str, Any]] = None,
) -> Optional[Dict[str, Any]]:
```

Issues a DynamoDB `update_item` with:
- `UpdateExpression`: `SET #s = :to, updated_at = :now [, <extra_set attrs>]`
- `ConditionExpression`: `#s = :from`
- `ReturnValues`: `ALL_OLD`

Returns the prior header on success. Returns `None` on `ConditionalCheckFailedException` (idempotent replay / concurrent loser). Re-raises all other `ClientError`s.

## 5. Detailed Behavior & Edge Cases

### Approve

- **Happy path**: `requested → approved`. Sets `decided_by`, `decision_note`, `updated_at`. Notifies requester.
- **Replay** (already `approved`): `_require_transition` is a no-op for `current == target`; `_transition` returns `None` because `ConditionExpression` fails; returns current state without re-notifying.
- **Concurrent race**: Two admin processes call approve simultaneously. One wins the conditional write; the other gets `ConditionalCheckFailedException`, returns `None`, and returns the current (already approved) state — same external outcome, no double-notification.
- **Non-existent return**: 404 from `_load_return`.
- **Wrong status** (e.g., already rejected or received): `_require_transition` raises 409 `"Illegal return transition rejected -> approved"`.

### Reject

- **From `requested`**: `requested → rejected`. Common path when admin declines the request immediately.
- **From `approved`**: `approved → rejected`. Admin reverses a previous approval before goods arrive. `_transition` uses the live `current_status` (not the literal `"requested"`) to handle both source states identically.
- **Terminal replay** (already `rejected`): 409 from `_require_transition` because `"rejected"` maps to an empty transition set — this is correct; a rejected return cannot be un-rejected via this endpoint.
- **`note` field**: persisted as `decision_note`; max 500 characters enforced by `ReturnDecisionIn`; empty string stored when omitted.

### Receive

- **Pre-condition**: return must be `approved`. Any other status → 409.
- **Restock gating**: the `inventory_reservations_enabled` flag is read at call time via `getattr(S, "inventory_reservations_enabled", False)` — no module-level caching, so an operator can enable/disable the flag at runtime and the next receive call will reflect the current value.
- **Missing SKU on a line**: if `sku` is `None` or falsy (e.g., catalog item that had no SKU), the loop skips that line. This is intentional — the return is still marked received; only stockable lines are restocked.
- **Zero-quantity line**: `qty > 0` guard prevents a zero-delta `adjust` call.
- **Inventory row does not exist** (SKU never had an inventory record): `inventory.adjust` with a positive delta creates the row on first call (`put_item` with `ConditionExpression="attribute_not_exists(sku)"` at `inventory.py:242`).
- **Restock failure** (e.g., DynamoDB error, network blip): wrapped in `try/except Exception`. The `received` status transition is already committed; the failed restock is swallowed. The operator must manually correct inventory if this occurs. The audit trail from `inventory.adjust` will show the failed attempt.
- **Replay after first receive**: `_transition` returns `None` because the row is already `received` (condition fails). The restock block is never reached — no double-increment.

### Admin queue

- The `GSI_STATUS` query returns only `META` rows (line rows carry no `status` attribute, so they never appear in the index result set). The `list_returns_by_status` function also filters for `sk == "META"` as a belt-and-suspenders guard.
- Lines are not eagerly loaded in the queue listing (only the header). The client fetches a full return with `GET /ui/returns/{return_id}` for line detail.
- `LastEvaluatedKey` pagination is handled by the service loop (`returns_rma.py:299-312`).

### Notification contract

`_notify` (`returns_rma.py:94`) is best-effort: any exception is silently swallowed. The notification is sent to `header["user_sub"]` (the original requester), not to `actor_sub` (the admin who made the decision). The category is `"returns"` for all events.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

There is no `dev_mode` branch anywhere in `returns_rma.py` or `inventory.py`. The same DynamoDB conditional-write code runs in:
- **Dev**: moto in-process mock via `T.returns` / `T.inventory` (`app/core/tables.py:569,571`)
- **Prod**: real DynamoDB tables

`_audit` and `_notify` are best-effort thin wrappers that delegate to the same `alerts.audit_event` / `alerts.write_alert` functions used by all other platform services.

### Idempotency

`receive_return` idempotency has two interlocking layers:

1. **`_transition` conditional guard** (`returns_rma.py:341-354`): the `update_item` carries `ConditionExpression="#s = :from"` with `from_status="approved"`. If the row is already `received` (or any other status), the condition fails and `_transition` returns `None`.
2. **Restock only on first transition** (`returns_rma.py:424-435`): the restock loop runs only when `old is not None`, i.e., only on the first successful `approved → received` flip. A replay that gets `None` back returns current state without re-entering the inventory adjust path. This guarantees the on-hand increment happens exactly once per return.

`approve_return` and `reject_return` are idempotent by the same `_transition` pattern.

### Ownership / authorization

- Only `ADMIN` or `ROOT` role users can call the admin endpoints. `require_admin_or_root_csrf` (`app/auth/policy.py:100`) enforces both role and CSRF.
- A customer who attempts a direct `POST /ui/returns/admin/{id}/approve` gets 403 from the role check.
- The admin queue (`GET /ui/returns/admin/queue`) is also role-gated — a customer cannot enumerate all returns.
- Customer read (`GET /ui/returns/{return_id}`) enforces ownership: `rec["user_sub"] != session["user_sub"]` → 404 (not 403, to avoid leaking the existence of foreign returns).

### Audit trail

Every successful state transition emits a `audit_event` to `T.alerts` with the event name `rma.approved`, `rma.rejected`, or `rma.received`, including `return_id`, `order_id`, and `actor_sub`. The inventory adjustment emits a separate `inventory.adjust` audit event with `reason="rma_restock"`, `before`, and `after` on-hand counts.

## 8. Backward Compatibility & Migration

### Additive-only

- No existing table schema is modified. `T.orders`, `T.order_items`, `T.billing`, `T.catalog`, `T.cart` are read-only for OFB-009.
- The `returns` table is a new table. With `RETURNS_RMA_ENABLED=false` (the default) it is never accessed.
- The `inventory` table is a new table (OFB-003). With `INVENTORY_RESERVATIONS_ENABLED=false` the restock path is dead code.

### Dev environment migration

`just restart` recreates all DynamoDB tables via `scripts/local-ddb-init.py`. The `returns`, `inventory`, and `reservations` table definitions are already present at `local-ddb-init.py:2479-2492`. No manual migration step is needed for the dev stack.

### Production migration

1. Deploy code with both flags off (no-op).
2. Run `UpdateTable` to create the `returns` table (and `inventory` / `reservations` if not yet created by OFB-003/004).
3. Enable `RETURNS_RMA_ENABLED=true` to activate the feature.
4. Enable `INVENTORY_RESERVATIONS_ENABLED=true` independently when the inventory system is ready.

There is no data migration — the `returns` table is empty at launch and receives new rows only after the flag is on.

## 10. Open Questions / Assumptions

1. **`_notify` alert category**: `returns_rma.py:101` passes `category="returns"`. This assumes `alerts.write_alert` / `create_alert` accepts a `category` kwarg. If the kwargs signature does not support it, the call will silently drop it (best-effort wrapper). Verified acceptable.

2. **Partial restock with multi-location inventory**: `inventory.adjust` defaults to `location_id="warehouse"` (the single default location). Multi-location is deferred per OFB-001. If a future OFB adds multi-location, `receive_return` will need to carry the target `location_id` per line.

3. **Restock for non-inventory-tracked items**: If a returned SKU has no inventory record and `delta > 0`, `inventory.adjust` creates the record at `on_hand=delta` (OFB-003 behavior at `inventory.py:242`). This is assumed correct — a restock implicitly bootstraps inventory tracking for the SKU.

4. **Reject after receive**: The state machine (`_VALID_TRANSITIONS`) does not allow `received → rejected`. This is intentional — goods have already been physically received. A "undo receive" path is not in scope.

5. **`decided_by` on receive**: `receive_return` does not persist `decided_by` on the row (it is already set by `approve_return`). The actor who performed the physical receipt is tracked only in the audit event (`rma.received`), not in the DynamoDB header. This is assumed acceptable for the current milestone.

6. **`line_rows` not re-loaded after transition**: `receive_return` loads lines before calling `_transition`. If a concurrent process modifies line rows between load and transition (not possible with current write paths, but theoretically possible), the restock would use stale line data. Assumed safe given line rows are immutable after creation.

7. **Notification function resolution**: `_notify` discovers the notification function via `getattr(alerts, "create_alert", None) or getattr(alerts, "send_alert", None)` at call time. This is resilient to refactoring but means a missing function is silently a no-op. Assumed acceptable as notifications are not transactional.
