# OFB-010 — RMA refund via existing billing

## 1. Summary & Goal

OFB-010 is the refund-issuance slice of the Returns/RMA lifecycle (OFBiz Milestone 3). Its scope is:

1. When an admin marks a return as refunded (`POST /ui/returns/admin/{return_id}/refund`), issue the credit through the **existing billing-ledger primitives** — `new_ledger_entry` + `apply_balance_delta` + `settle_or_reverse_ledger` from `app/services/billing_shared.py` — writing exactly one `type="adjustment", reason="refund"` ledger entry with a `provider` field for FIN-013 attribution. No parallel refund mechanism is minted.
2. Persist a `refund_ledger_sk` back-reference on the return header (for auditability and idempotency guards) and a `provider` stamp for the platform financial dashboard's provider breakdown.
3. Where an originating `ledger_sk` is available on the order record, reverse that row to `state="reversed"` (mirroring `billing.refund_payment` at `app/routers/billing.py:1324`).
4. Where an originating `payment_intent_id` is available on the order record, call `mark_invoice_refunded` on the linked invoice (best-effort).
5. All of the above is **idempotent**: the single-writer `received → refunded` conditional transition ensures the refund posts exactly once.

This ticket does **not** own: the customer request flow (OFB-008), admin approve/reject/receive (OFB-009), any frontend UI (OFB-011), or E2E test spec (OFB-012).

## 3. Data Model

### No new DynamoDB tables

OFB-010 is purely additive to existing tables. No schema changes are needed.

### `returns` table — header row (SK="META") — field additions from OFB-010

The following fields are written during `refund_return` on a successful `received → refunded` transition (via `_transition`'s `extra_set` and a subsequent best-effort `update_item`):

| Field | Type | Set by | Purpose |
|---|---|---|---|
| `refund_amount_cents` | Number | `_transition extra_set` | Total amount credited (sum of all return-line `amount_cents`) |
| `provider` | String | `_transition extra_set` | Payment provider attribution (`"stripe"` / `"paypal"` / `"ccbill"`) for FIN-013 |
| `refund_ledger_sk` | String | post-transition `update_item` | SK of the new billing ledger entry — enables O(1) lookup and prevents double-write on replay |

No `attr_types` change needed: `refund_amount_cents` is stored as a DynamoDB Number natively; `provider` and `refund_ledger_sk` are Strings. Neither is a GSI key.

### `billing` table — refund ledger entry

Written by `new_ledger_entry` in `billing_shared.py:224`:

| Field | Value |
|---|---|
| `pk` | `USER#{user_sub}` |
| `sk` | `LEDGER#{ts}#{entry_id}` (e.g. `LEDGER#1748000000#1748000000000_abc12345678901234`) |
| `entry_id` | `ulidish()` — `{ts_ms}_{random_hex16}` |
| `ts` | Unix timestamp integer |
| `type` | `"adjustment"` |
| `amount_cents` | Sum of returned-line amounts (integer) |
| `state` | `"settled"` |
| `reason` | `"refund"` |
| `ledger_date` | `"YYYY-MM-DD"` UTC (FIN-013 GSI key) |
| `provider` | `"stripe"` (or caller-supplied) |
| `return_id` | Return identifier |
| `order_id` | Originating order identifier |
| `meta` | `{"reason": "rma_refund", "return_id": ..., "order_id": ...}` |

The `ledger_date` field is computed automatically by `ledger_date_for_ts` and ensures the entry is immediately visible in the `GSI_LEDGER_DATE` daily aggregation used by the platform financial dashboard.

### `billing` table — BALANCE row update

`apply_balance_delta` decrements `payments_settled_cents` by `amount_cents` on the `USER#{user_sub}` / `BALANCE` row. The delta is `{"payments_settled_cents": -amount}`. If the BALANCE row does not yet exist for the user, `ensure_balance_row` creates it (`billing_shared.py:69`).

### `billing` table — original charge row reversal (best-effort)

If `order.ledger_sk` is non-empty, `settle_or_reverse_ledger` sets `state = "reversed"` on the original charge ledger row at that SK. This is a best-effort `update_item` that can be retried without harm (it is idempotent). If `ledger_sk` is absent (order was never paid through the standard billing path), this step is skipped silently.

## 4. API / Service Design

### Service function

```python
# app/services/returns_rma.py

def refund_return(
    return_id: str,
    *,
    actor_sub: str,
    provider: str = "stripe",
) -> Dict[str, Any]:
    """Refund a received return through the existing billing ledger path.

    Posts exactly one type="adjustment", reason="refund" ledger entry attributed
    to `provider` (FIN-013). Idempotent: the refund only posts on the first
    received -> refunded transition.

    Returns the updated ReturnOut-shaped dict.
    Raises HTTPException(404) if return not found.
    Raises HTTPException(409) if current status is not "received" (and not
      already "refunded" — idempotent replay returns current state silently).
    Raises HTTPException(422) if the computed refund amount is <= 0.
    """
```

### Updated router handler

```python
@returns_rma_router.post("/admin/{return_id}/refund", response_model=ReturnOut)
async def admin_refund(
    return_id: str,
    body: RmaRefundIn | None = None,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
):
    rma._require_enabled()
    provider = (body.provider if body and body.provider else None) or "stripe"
    rec = rma.refund_return(return_id, actor_sub=user.sub, provider=provider)
    return ReturnOut(**rec)
```

### Ordering of operations in `refund_return`

1. `_require_enabled()` — short-circuit 404 when flag off.
2. `_load_return(return_id)` — load header + lines; 404 if not found.
3. `_require_transition(header.status, "refunded")` — 409 for illegal transitions; no-op if already `"refunded"`.
4. Compute `amount = sum(line.amount_cents)`. 422 if `amount <= 0`.
5. `_transition(return_id, "received", "refunded", actor_sub, extra_set={"refund_amount_cents": amount, "provider": provider})` — single-writer guard. If returns `None` (already transitioned), skip ledger write and return current state.
6. Look up `order.ledger_sk` and `order.payment_intent_id` from `T.orders` (best-effort `_get_order`).
7. `new_ledger_entry(...)` → `(led_sk_value, led_item)`.
8. `ddb_put(T.billing, led_item)` — write ledger row.
9. `apply_balance_delta(T.billing, pk, {"payments_settled_cents": -amount}, currency=currency)`.
10. If `original_ledger_sk` is present: `settle_or_reverse_ledger(T.billing, "pk", pk, original_ledger_sk, "reversed")`.
11. Best-effort `T.returns.update_item` to write `refund_ledger_sk` back to the header (outside the conditional transition to avoid complicating the atomic guard).
12. Best-effort `invoices.mark_invoice_refunded(user_sub, payment_intent_id)` if `payment_intent_id` is known.
13. `_audit("rma.refunded", actor_sub, ...)` — fire-and-forget.
14. `_notify(user_sub, "Return refunded", ...)` — fire-and-forget.
15. Return `get_return(return_id)`.

## 5. Detailed Behavior & Edge Cases

### Partial-quantity refunds

Return lines store `amount_cents = unit_price * returned_qty` (computed in `request_return` at `returns_rma.py:221`). The refund amount is the sum across all lines. For a 4-unit order at 250 cents/unit where the customer returns 1 unit, `amount_cents = 250`. The math is unit-tested in `tests/test_ofb_returns_rma.py:316-326` (`test_partial_quantity_prorate`).

### Idempotency — the double-write guard

The `_transition` call at step 5 uses `ConditionExpression="#s = :from"` where `:from = "received"`. DynamoDB's conditional write guarantees exactly-once semantics:

- **First call**: condition succeeds, returns `ALL_OLD` (the pre-transition header). Ledger write proceeds.
- **Replay / concurrent second call**: `ConditionalCheckFailedException` → `_transition` returns `None`. `refund_return` detects `old is None`, skips the billing write entirely, and returns the current state. No second `LEDGER#` row is written.

A `CONSUMED#` idempotency row (as used by cart-recovery links) is not needed here because the DynamoDB status field itself serves as the single-use token.

### Zero-amount guard

If all return lines have `amount_cents = 0` (e.g., a return of a zero-price promotional item), the refund raises `HTTPException(422)` before touching the billing table. This prevents a zero-credit ledger row from polluting the financial dashboard.

### Missing order linkage

`order.ledger_sk` may be absent if the order was created through a path that does not write this field (e.g., legacy data or `CommerceOrderService.create_order` which does not persist `ledger_sk` — see `commerce_order_service.py:72-84`). The reversal step is silently skipped: `if original_ledger_sk: settle_or_reverse_ledger(...)`. This is the same defensive pattern used by `billing.refund_payment` at `app/routers/billing.py:1323-1324`.

### Invoice marking

`invoices.mark_invoice_refunded` is looked up via `getattr(inv_svc, "mark_invoice_refunded", None)` (`returns_rma.py:526`) because the symbol does not exist on the `invoices` module — it currently lives only on `subscription_server.py:266` for the subscription-billing context. Two outcomes:

- **If `mark_invoice_refunded` is added to `app/services/invoices.py`**: the `getattr` pattern will find it automatically with no RMA code change.
- **If it is not present**: the `getattr` returns `None`, the `if marker is not None` guard skips the call, and the return proceeds. No error.

### Provider attribution

The `provider` field is written to both the return header (via `_transition extra_set`) and the billing ledger entry (via `new_ledger_entry extra={"provider": provider}`). The latter is required by FIN-013 / GAP-0203 so the platform financial dashboard can bucket the entry under the correct provider column. Default is `"stripe"`. The router accepts an optional `RmaRefundIn.provider` override to support PayPal and CCBill orders.

### Order-currency propagation

The `currency` used in `apply_balance_delta` comes from `header.get("currency", "usd")` on the return header. The return's `currency` is set in `request_return` from `order.get("currency", "usd")` at `returns_rma.py:233`. This ensures the BALANCE row currency matches the order denomination.

### Admin impersonation

`actor_sub` is the admin's subject, written to `decided_by` (via `_transition extra_set` in `approve_return` / `reject_return`) and embedded in the audit event. For the refund specifically, `actor_sub` appears in the `rma.refunded` audit event but is **not** written to `refund_amount_cents` or the ledger entry — the ledger is user-attributed (the customer who placed the order).

### Concurrent admin calls

Two concurrent admin calls to refund the same return will race on `_transition`. One will win the conditional write and proceed to post the ledger entry; the other will receive `None` from `_transition` and return the current state without a second write. This is the same optimistic concurrency pattern used throughout the platform.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

`refund_return` contains no `dev_mode` branch. The billing primitives (`new_ledger_entry`, `apply_balance_delta`, `settle_or_reverse_ledger`) operate identically against DynamoDB Local (dev) and real DynamoDB (prod). The `invoices.mark_invoice_refunded` call (best-effort) goes through the same `T.invoices` handle in both environments.

There is no Stripe API call in `refund_return`. Unlike `billing.refund_payment` (which calls `stripe.Refund.create` at `billing.py:1300`), RMA refunds post only to the internal billing ledger. If an actual Stripe refund is required in prod (to reverse the charge at the payment processor), that is a separate concern outside this ticket's scope (see Open Questions, item 1).

### Idempotency

- Status transition: single-writer DynamoDB conditional write (Section 5).
- Ledger write: protected by the transition guard — the `ddb_put(T.billing, led_item)` at step 8 only runs on the first successful transition. No idempotency key is needed on the ledger row itself because the upstream guard prevents a second call from reaching it.
- `refund_ledger_sk` back-write: unconditional best-effort `update_item` after the transition. Safe to replay (same value written repeatedly is harmless).

### Security

- **Ownership**: `refund_return` does not re-check that `actor_sub` owns the return. Ownership is enforced by `require_admin_or_root_csrf` at the router layer — only ADMIN/ROOT can call the endpoint. Customer-facing read endpoints enforce `rec["user_sub"] == session["user_sub"]` at `returns_rma.py:49`.
- **CSRF**: all admin mutation endpoints require `x-csrf-token` header matching `ui_csrf` cookie (enforced by `enforce_cookie_csrf` in `require_admin_or_root_csrf`). Bearer-auth callers (e.g., integration tests) skip CSRF per the standard platform convention.
- **Amount clamping**: `amount` is the server-side sum of line amounts stored at request time. The admin cannot supply an amount — there is no client-controlled amount parameter, eliminating the risk of over-refunding.
- **Double-refund**: prevented by DynamoDB conditional transition (see Section 5).

## 8. Backward Compatibility & Migration

### Additive

With `RETURNS_RMA_ENABLED=false` (the default), the `returns_rma_router` is registered but all endpoints return 404. The `billing`, `orders`, and `order_items` tables are untouched. No migration is needed for existing data.

### When enabling the flag in an existing environment

The `returns` table must exist before `RETURNS_RMA_ENABLED=true` is set. In dev, `just restart` recreates all tables via `scripts/local-ddb-init.py`. In prod, run `local-ddb-init.py` (or its prod equivalent) before deploying the flag change.

### Schema stability

`ReturnOut` already includes all OFB-010 fields (`refund_amount_cents`, `refund_ledger_sk`, `provider`). These were zero-valued / null before a refund — existing clients reading in-progress returns will continue to see `refund_amount_cents: 0` and `provider: null` until the return transitions to `refunded`. This is backward-compatible.

### `mark_invoice_refunded` on the invoices module

OFB-010 uses a defensive `getattr` pattern (Section 5) so the feature works regardless of whether `invoices.mark_invoice_refunded` is added. If a future ticket adds the function to `app/services/invoices.py`, the RMA service will call it automatically with no change required here.

### E2E spec — `frontend/e2e/returns-rma.spec.ts` (OFB-012)

The refund endpoint is one node in the full lifecycle:

```
POST /ui/returns (alice)  →  POST /admin/{id}/approve  →  POST /admin/{id}/receive  →  POST /admin/{id}/refund
```

OFB-010 acceptance checks in the E2E spec:

1. After `POST /admin/{id}/refund` returns 200, `GET /ui/returns/{id}` returns `status="refunded"` and `refund_amount_cents > 0`.
2. A second `POST /admin/{id}/refund` call returns 200 (idempotent replay) with the same `refund_ledger_sk` and still-single billing entry (verifiable via the billing history API).
3. `POST /admin/{id}/refund` on a `"requested"` return returns 409.

## 10. Open Questions / Assumptions

1. **No Stripe `Refund.create` call is made**: The RMA refund posts only to the internal ledger. The assumption is that internal credit (wallet/balance adjustment) is sufficient for the MVP, and a real payment-processor reversal is out of scope for OFB-010. If Stripe refund is required, it must be added before prod enablement — the clean extension point is between steps 6 and 7 in the ordering (Section 4), guarded by a separate `S.rma_provider_refund_enabled` flag.

2. **`provider` defaults to `"stripe"`**: The assumption is that most orders in the early rollout are Stripe-settled. For multi-provider support, the order record should carry a `provider` field (set at checkout time in the billing router). OFB-010 could read `order.get("provider", "stripe")` as the default instead of hard-coding, reducing the need for the admin to specify it manually.

3. **`mark_invoice_refunded` attribution**: The invoice service (`app/services/invoices.py`) does not currently expose `mark_invoice_refunded`. The `getattr` guard in `returns_rma.py:526` prevents a crash. The assumption is that a future ticket will add this function to the invoices module; no OFB-010 code change will be needed when that happens.

4. **`payments_settled_cents` vs `payments_pending_cents`**: `refund_return` always decrements `payments_settled_cents`. `billing.refund_payment` at `billing.py:1318-1321` branches on the payment's current status to choose between the two. For RMA refunds, the order payment is assumed to be settled (it must be `paid` for a return to be approved). If a return is somehow issued on a pending payment, the balance row will show an inconsistency. This should be documented as a known limitation.

5. **Multi-line, multi-sku returns with mixed providers**: The current design uses a single `provider` field for the entire return. If future orders support split-tender payment (partial Stripe + partial wallet), the per-line provider granularity is lost. This is out of scope for OFB-010.

6. **BALANCE row creation race**: `apply_balance_delta` calls `ensure_balance_row` which does a `get_item` + conditional `put_item`. Under high concurrency two concurrent refunds for the same user could both attempt to create the BALANCE row; the second `put_item` would fail silently (no `ConditionExpression` on `ensure_balance_row`). This is an existing platform limitation, not introduced by OFB-010.
