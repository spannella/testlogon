# PRD-004 — Category-tree service (parent/child rollup)

**Type:** Feature | **Priority:** P0 | **Estimate:** 4 days
**Milestone:** 2 — Category Trees

---

## 1. Summary & Goal

PRD-004 creates `app/services/product_categories.py` — the pure-Python service layer that extends the flat `CAT#{id}/META` category model (currently in `app/routers/catalog.py`) into a multi-level tree. It does not add router endpoints (those are PRD-005); it provides the callable functions that the router will delegate to.

The six headline capabilities this service delivers:

1. **`add_child`** — attach an existing category as a child of a parent, writing the `TREE` row on `T.product_depth` that carries the `ByParent` GSI keys and materialized `path`.
2. **`move_category`** — re-parent a category to a new parent, with cycle detection and a bulk path-rewrite of all affected descendants.
3. **`list_children`** — return the immediate children of a category ordered by `position`, resolved via a single `ByParent` GSI query (no scan).
4. **`get_ancestry`** — return the full ordered ancestor list from the root down to (but not including) the category itself.
5. **`get_breadcrumb`** — human-readable name list for display: `["Electronics", "Phones", "Android"]`.
6. **`list_descendants`** — return all nodes in a subtree (BFS using repeated `list_children` queries).

The design constraint is strict: with `PRODUCT_DEPTH_ENABLED` off, `list_categories` (`app/routers/catalog.py:294`) returns the identical flat list as today — no `T.product_depth` reads are ever issued. The service is entirely dormant when the flag is off.

## 2. Context & Current State

### 2.1 The flat category model (T.catalog)

The existing category entity lives on `T.catalog` (`app/core/tables.py:99` type annotation; `app/core/tables.py:351` instantiation; table `shopping_catalog`). Each category is a single DynamoDB row with `PK=CAT#{category_id}`, `SK=META`, `entity="category"` (`app/routers/catalog.py:261–274`). The row carries:

- `category_id`, `name`, `description`, `creator_id`, `created_at` (ISO-8601 string via `now_iso()`)
- `GSI1PK="CATS"`, `GSI1SK=f"{name.lower()}#{category_id}"` — the flat listing index

There is no `parent_category_id`, no `path`, and no `position` on this row. The flat `GSI1` query at `app/routers/catalog.py:199–208` (`_gsi_categories_page`) is the only listing path. There is also a scan fallback at `app/routers/catalog.py:211–217` (`_scan_categories`) used when `GSI1` is not yet provisioned.

The `_require_category_owner` helper at `app/routers/catalog.py:247–252` fetches the `META` row and enforces ownership only when `creator_id` is non-None (`if creator_id and creator_id != user_id`). This helper is reused by the tree service for ownership checks.

The table schema (`scripts/local-ddb-init.py:117–125`) has no `attr_types` argument — `GSI1SK` is a string. This remains unchanged.

### 2.2 The product_depth table (T.product_depth, from PRD-002)

**PRD-002 is a prerequisite and has not yet been implemented.** Neither `T.product_depth`, `S.product_depth_enabled`, nor `S.product_depth_table_name` exist in the current codebase (`app/core/tables.py`, `app/core/settings.py` confirmed). PRD-004 cannot be compiled until PRD-002 ships.

PRD-002 adds `T.product_depth` (table `product_depth`) with five GSIs. The one PRD-004 uses is `ByParent`:

```
IndexName: "ByParent"
Partition key: GSI_PARENT_PK  (String) = "PARENT#{parent_category_id}" or "PARENT#root"
Sort key:      GSI_PARENT_SK  (Number) = position (integer)
attr_types:    {"GSI_PARENT_SK": "N"}
```

PRD-002 also defines the primary-key pattern for the `category_tree` entity row:
`PK=CAT#{category_id}`, `SK=TREE`, `entity="category_tree"`.

This row is the tree-metadata overlay. The `META` row on `T.catalog` continues to hold the human-readable fields (`name`, `description`, `creator_id`). The `TREE` row on `T.product_depth` holds only tree-structural fields (`parent_category_id`, `path`, `position`, `depth`).

### 2.3 The _scan_categories fallback (the scan PRD-004 must not break)

`app/routers/catalog.py:211–217` catches any `ValidationException` from `_gsi_categories_page` and falls through to a full-table scan filtered on `entity == "category"`. This fallback reads only from `T.catalog`; it never touches `T.product_depth`. PRD-004 must not add `entity="category_tree"` rows to `T.catalog` (they go only to `T.product_depth`), so the fallback's filter remains correct.

### 2.4 Pattern for default-off services

The canonical model is `app/services/inventory.py:50–57` (`app/services/returns_rma.py:68–73` also follows the same pattern):

```python
def _flag_on() -> bool:
    return bool(getattr(S, "inventory_reservations_enabled", False))

def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="Inventory reservations are not enabled")
```

Every public function in `product_categories.py` that touches `T.product_depth` calls `_require_enabled()` first. Read-only helpers used by the router for the flag-off path (e.g. enriching the flat list with position data) are never called when the flag is off.

### 2.5 Max-depth configuration (new setting)

PRD-002 (`app/core/settings.py`) adds `product_depth_enabled` adjacent to the catalog block at line 832 (`catalog_table_name`) and the inventory/returns block at lines 836–847 (`inventory_reservations_enabled`, `returns_rma_enabled`). PRD-004 adds one more setting adjacent to it: `product_depth_max_category_depth` (`PRODUCT_DEPTH_MAX_CATEGORY_DEPTH`, default `10`). This is the exclusive upper bound on `depth` (root = depth 0; max = 9 with default of 10). The setting is consulted only when `product_depth_enabled` is true.

### 2.6 The audit plumbing

The canonical audit pattern is the fire-and-forget `_audit` wrapper in `app/services/inventory.py:92–98` (same pattern at `app/services/returns_rma.py:85–90`):


## 3. Data Model

### 3.1 The TREE row on T.product_depth

One row per category that has been placed in the tree. Root-level categories (no parent) also get a `TREE` row, with `parent_category_id=None` and `GSI_PARENT_PK="PARENT#root"`.

| Attribute | Type | Description |
|---|---|---|
| `PK` | S | `CAT#{category_id}` |
| `SK` | S | `TREE` |
| `entity` | S | `"category_tree"` |
| `category_id` | S | Matches `PK` suffix |
| `parent_category_id` | S\|None | `None` for root-level |
| `path` | S | Slash-delimited ancestor id chain: `"root/abc/def/ghi"`. Root-level = `"root/{category_id}"`. Used for prefix queries during subtree operations and for breadcrumb resolution. |
| `depth` | N | Integer depth (root-level children = 1; root itself is not stored) |
| `position` | N | Integer position among siblings (0-based, caller-supplied, default 0) |
| `creator_id` | S | Owning `user_sub` (copied from `META` row at write time) |
| `created_at` | N | Unix int timestamp (via `now_ts()` — note: the sibling `META` row on `T.catalog` uses ISO string via `now_iso()`; the TREE row uses integer for numeric GSI compatibility) |
| `updated_at` | N | Unix int timestamp (via `now_ts()`) |
| `GSI_PARENT_PK` | S | `"PARENT#{parent_category_id}"` or `"PARENT#root"` |
| `GSI_PARENT_SK` | N | = `position` |

**GSI projection:** ALL (the service reads the full row from the GSI result).

### 3.2 No changes to T.catalog rows

The `META` row on `T.catalog` (`PK=CAT#{id}`, `SK=META`) is not modified. `GSI1PK`/`GSI1SK` are written exactly as before (`create_category` at `app/routers/catalog.py:260–274`). The `TREE` row on `T.product_depth` is an additive overlay that the tree service reads/writes independently.

### 3.3 Path invariant

The `path` attribute is a materialized materialized string: each segment is a category_id, joined with `/`, starting from `"root"`. Examples:

- A root-level category `abc` has `path="root/abc"`.
- Its child `def` has `path="root/abc/def"`.
- A grandchild `ghi` has `path="root/abc/def/ghi"`.

This allows `list_descendants` to perform a DynamoDB `begins_with` query on `path` (via a GSI not used in PRD-004 directly — descendants are found by BFS on `ByParent`, not by a path index scan). However, `move_category` uses `path` to detect cycles: if `proposed_new_parent.path` starts with `category.path`, the re-parent would create a cycle.

### 3.4 position uniqueness

Sibling `position` values are not enforced to be unique at the database level. The service provides a `_next_position` helper that queries the `ByParent` GSI (sorted numerically descending by `GSI_PARENT_SK`) and returns `max_position + 1`. Callers may supply an explicit `position`; collisions are allowed (DynamoDB GSI sort keys need not be unique). The sort order for listing is stable by `position` ascending, then `category_id` for ties.

## 4. API / Service Design

### 4.1 Module: `app/services/product_categories.py`

All public functions are synchronous (DynamoDB calls via boto3 Resource API, consistent with `app/services/inventory.py` and `app/services/returns_rma.py`). The router (PRD-005) calls them from async endpoints via `await asyncio.to_thread(...)` or directly (boto3 Table calls release the GIL but are not coroutines — the existing `app/routers/catalog.py` calls them synchronously from async endpoints with no `to_thread` wrapper; PRD-004 follows the same convention).

#### 4.1.1 Internal helpers

```python
def _flag_on() -> bool:
    return bool(getattr(S, "product_depth_enabled", False))

def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="Product depth is not enabled")

def _max_depth() -> int:
    return int(getattr(S, "product_depth_max_category_depth", 10))

def _tree_pk(category_id: str) -> str:
    return f"CAT#{category_id}"

def _get_tree_row(category_id: str) -> Optional[Dict[str, Any]]:
    """Fetch the TREE row for a category; returns None if not yet in the tree."""
    resp = T.product_depth.get_item(Key={"PK": _tree_pk(category_id), "SK": "TREE"})
    return resp.get("Item")

def _require_tree_row(category_id: str) -> Dict[str, Any]:
    item = _get_tree_row(category_id)
    if not item:
        raise HTTPException(status_code=404, detail=f"Category {category_id!r} is not in the tree")
    return item

def _require_catalog_meta(category_id: str) -> Dict[str, Any]:
    """Fetch the META row from T.catalog; 404 if absent."""
    item = T.catalog.get_item(Key={"PK": f"CAT#{category_id}", "SK": "META"}).get("Item")
    if not item:
        raise HTTPException(status_code=404, detail=f"Category {category_id!r} not found")
    return item

def _next_position(parent_category_id: Optional[str]) -> int:
    """Return max(sibling positions) + 1, or 0 if no siblings exist."""
    gsi_pk = f"PARENT#{parent_category_id}" if parent_category_id else "PARENT#root"
    resp = T.product_depth.query(
        IndexName="ByParent",
        KeyConditionExpression=Key("GSI_PARENT_PK").eq(gsi_pk),
        ScanIndexForward=False,
        Limit=1,
    )
    items = resp.get("Items", [])
    if not items:
        return 0
    return int(items[0].get("GSI_PARENT_SK", 0)) + 1

def _audit(event: str, user_sub: str, **fields: Any) -> None:
    try:
        from app.services.alerts import audit_event
        audit_event(event, user_sub or "system", None, **fields)
    except Exception:
        pass
```

#### 4.1.2 `add_child`

```python
def add_child(
    *,
    parent_category_id: Optional[str],   # None = attach at root level
    child_category_id: str,
    user_sub: str,
    position: Optional[int] = None,
) -> Dict[str, Any]:
    """
    Attach child_category_id as a child of parent_category_id in the tree.

    Preconditions:
    - product_depth_enabled must be True.
    - child_category_id must exist on T.catalog (META row).
    - parent_category_id (if not None) must already have a TREE row.
    - child_category_id must NOT already have a TREE row (409 if it does).
    - The resulting depth (parent.depth + 1) must be < _max_depth() (422 if not).
    - user_sub must own child_category_id (403 via _require_catalog_meta + creator_id check).

    Returns the newly written TREE row as a dict.
    """
```

Behavior:

1. `_require_enabled()`
2. Fetch `child_meta = _require_catalog_meta(child_category_id)`
3. Check `child_meta["creator_id"] == user_sub`; if not, raise 403.
4. If `_get_tree_row(child_category_id)` is not None, raise 409 `"Category is already in the tree"`.
5. If `parent_category_id` is not None, `parent_row = _require_tree_row(parent_category_id)`. Otherwise `parent_row = None`.
6. Compute `new_depth = (int(parent_row["depth"]) + 1) if parent_row else 1`. If `new_depth >= _max_depth()`, raise 422 `"Maximum category depth exceeded"`.
7. Compute `new_path`: if root-level: `f"root/{child_category_id}"`; else `f"{parent_row['path']}/{child_category_id}"`.
8. `pos = position if position is not None else _next_position(parent_category_id)`.
9. `gsi_pk = f"PARENT#{parent_category_id}" if parent_category_id else "PARENT#root"`.
10. Write the `TREE` row to `T.product_depth` with `ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)"`. Catch `ConditionalCheckFailedException` → 409 `"Category is already in the tree"`.
11. `_audit("category_tree.add_child", user_sub, child_category_id=child_category_id, parent_category_id=parent_category_id)`.
12. Return the written row as a dict.

#### 4.1.3 `move_category`

```python
def move_category(
    *,
    category_id: str,
    new_parent_category_id: Optional[str],   # None = move to root
    user_sub: str,
    position: Optional[int] = None,
) -> Dict[str, Any]:
    """
    Re-parent category_id under new_parent_category_id.

    Cycle detection: rejected if new_parent_category_id is a descendant of
    category_id (i.e. new_parent.path starts with category.path).
    Max-depth: rejected if any descendant would exceed _max_depth() after move.
    Own-or-admin: user_sub must own category_id.
    """
```

Behavior:

1. `_require_enabled()`
2. `child_meta = _require_catalog_meta(category_id)`.
3. Check `child_meta["creator_id"] == user_sub`; 403 if not.
4. `category_row = _require_tree_row(category_id)`.
5. If `new_parent_category_id` is not None:
   a. `new_parent_row = _require_tree_row(new_parent_category_id)`.
   b. **Cycle check**: if `new_parent_row["path"]` starts with `category_row["path"] + "/"` OR equals `category_row["path"]`, raise 422 `"Re-parenting would create a cycle"`.
   c. `new_depth = int(new_parent_row["depth"]) + 1`.
   d. Compute `path_prefix_old = category_row["path"]`. The depth delta `delta = new_depth - int(category_row["depth"])`. Verify `new_depth + delta < _max_depth()` (conservative check — if any descendant would exceed; the exact check iterates `list_descendants` once).
6. Compute new `new_path` and `new_depth` for `category_id` itself.
7. Call `_bulk_update_paths(category_id, old_path=category_row["path"], new_path=new_path, depth_delta=new_depth - int(category_row["depth"]))` to patch all descendants.
8. Write the updated `TREE` row for `category_id` (overwrite with `put_item`).
9. `_audit("category_tree.move", user_sub, ...)`.
10. Return the updated row.

`_bulk_update_paths(category_id, old_path, new_path, depth_delta)` BFS-traverses the subtree via repeated `list_children` calls and updates each descendant's `TREE` row in-place (individual `update_item` calls — no batch transaction required for MVP). This is O(N) where N is the subtree size.

#### 4.1.4 `list_children`

```python
def list_children(
    parent_category_id: Optional[str],
    *,
    limit: int = 50,
    start_key: Optional[Dict[str, Any]] = None,
) -> Tuple[List[Dict[str, Any]], Optional[Dict[str, Any]]]:
    """
    Return (items, last_evaluated_key) for immediate children of parent_category_id,
    sorted by position ascending. Uses the ByParent GSI — single query, no scan.
    items: list of TREE row dicts.
    """
```

Behavior:

1. `_require_enabled()`
2. `gsi_pk = f"PARENT#{parent_category_id}" if parent_category_id else "PARENT#root"`.
3. Query `T.product_depth` with `IndexName="ByParent"`, `KeyConditionExpression=Key("GSI_PARENT_PK").eq(gsi_pk)`, `ScanIndexForward=True` (ascending position), `Limit=limit`, `ExclusiveStartKey=start_key` if provided.
4. Return `(items, resp.get("LastEvaluatedKey"))`.

#### 4.1.5 `get_ancestry`

```python
def get_ancestry(category_id: str) -> List[Dict[str, Any]]:
    """
    Return ordered list of TREE rows from the root ancestor down to (but not
    including) category_id. Returns [] for root-level categories.
    Uses the materialized path — O(depth) get_item calls.
    """
```

Behavior:

1. `_require_enabled()`
2. `row = _require_tree_row(category_id)`.
3. Parse `path = row["path"]`. The path is `"root/{c1}/{c2}/.../category_id"`. Ancestor IDs are the segments between `"root"` and the final segment.
4. For each ancestor ID (in order root→leaf), call `_get_tree_row(ancestor_id)` and append to the result list. Skip any `None` returns (defensive: the path and tree rows should be consistent; log a warning but continue).
5. Return the list. Never raises if the category is at root level — returns `[]`.

#### 4.1.6 `get_breadcrumb`

```python
def get_breadcrumb(category_id: str) -> List[Dict[str, str]]:
    """
    Return [{"category_id": ..., "name": ...}, ...] from root ancestor to
    category_id (inclusive). Each entry fetches the META row from T.catalog
    for the name. O(depth) get_item calls on T.catalog.
    """
```

Behavior:

1. `ancestry = get_ancestry(category_id)` — list of ancestor TREE rows.
2. Append `_require_tree_row(category_id)` to the list (so category itself is included).
3. For each entry in the combined list, call `T.catalog.get_item(Key={"PK": f"CAT#{tree_row['category_id']}", "SK": "META"})` to fetch the display name.
4. Return `[{"category_id": id, "name": name}, ...]` in root-to-leaf order.

#### 4.1.7 `list_descendants`

```python
def list_descendants(
    category_id: str,
    *,
    max_results: int = 500,
) -> List[Dict[str, Any]]:
    """
    Return all descendant TREE rows (BFS, not including category_id itself).
    Bounded by max_results to prevent runaway on deep/wide trees.
    Uses repeated list_children calls — no scan.
    """
```

Behavior:

1. `_require_enabled()`
2. BFS queue starts with `[category_id]`. Result list starts empty.
3. While queue is non-empty and `len(results) < max_results`:
   a. Pop a category from the queue.
   b. Call `list_children(parent_category_id=cat_id, limit=200)` — no pagination loop for BFS MVP (PRD-005 can add deeper pagination later).
   c. Append each child TREE row to `results`. Append each child's `category_id` to the queue.
4. Return `results`.

#### 4.1.8 `remove_from_tree`

```python
def remove_from_tree(
    category_id: str,
    *,
    user_sub: str,
    cascade: bool = False,
) -> None:
    """
    Remove the TREE row for category_id.
    With cascade=False: raises 409 if the category has children in the tree.
    With cascade=True: recursively removes all descendant TREE rows first.
    Does NOT delete the META row from T.catalog (that is delete_category's job).

```

This function is called by the PRD-005 router's `DELETE /categories/{id}` extension and by the existing `delete_category` endpoint when `product_depth_enabled` is True (guarded so it is a no-op when the flag is off).

## 5. Detailed Behavior & Edge Cases

### 5.1 add_child idempotency

`add_child` uses a `ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)"` conditional put, which is DynamoDB's standard idempotency gate. A second call with the same `child_category_id` always returns 409. To support caller-side retry of transient network failures, the caller should check whether the category is already in the tree (via `_get_tree_row`) before retrying — the service does not silently absorb duplicates.

### 5.2 Cycle detection detail

The path-prefix check in `move_category` is the canonical OFBiz `ProductCategoryRollup` cycle guard. The check is:

```
cycle if new_parent_row["path"].startswith(category_row["path"] + "/")
        or new_parent_row["path"] == category_row["path"]
```

The second condition catches moving a category under itself (identity re-parent). Moving to the current parent (no-op move) is allowed — the path/position/depth stay the same; the service writes the TREE row and returns normally.

### 5.3 max_depth enforcement

`add_child` enforces the limit at write time: `new_depth >= _max_depth()` → 422. `move_category` must check the entire subtree: it calls `list_descendants(category_id)` first, computes `max_descendant_depth = max(int(d["depth"]) for d in descendants, default=int(row["depth"]))`, then verifies `max_descendant_depth + depth_delta < _max_depth()`. If this would exceed the limit, raise 422 `"Move would exceed maximum category depth"` before modifying any rows.

### 5.4 position ties

When two siblings share the same `position` value, `list_children` returns them in an unspecified order relative to each other (DynamoDB GSI sort order is total but ties between items at the same sort-key value are not defined). The caller (PRD-005 router) will sort ties by `category_id` ascending for a deterministic UI display. This is an acceptable MVP tradeoff; a `PATCH /categories/{id}/position` reorder endpoint can enforce strict uniqueness later.

### 5.5 Orphaned TREE rows

If a `META` row is deleted from `T.catalog` without calling `remove_from_tree`, the TREE row on `T.product_depth` becomes an orphan. `get_breadcrumb` and `get_ancestry` handle this defensively: a missing `META` row for an ancestor is logged as a warning and the entry is skipped in the breadcrumb output. `list_children` returns orphaned TREE rows as-is (they carry `category_id` and `name` is not on the TREE row — the router must enrich them). PRD-005 will enrich each `list_children` result with the `META` name.

### 5.6 Delete behavior

`delete_category` in `app/routers/catalog.py:325` deletes the `META` row. When `product_depth_enabled` is True, the router (PRD-005) will call `remove_from_tree(category_id, cascade=False)` first. With `cascade=False`, if the category has tree children the delete is rejected with 409, consistent with the existing `"Category has items. Use cascade=true to delete."` pattern at `app/routers/catalog.py:347`.

### 5.7 Race conditions in _bulk_update_paths

`move_category` is not atomic across descendant path updates. A concurrent `list_children` call during the update may see a partially updated subtree (some descendants with the new path, some with the old). This is an accepted MVP tradeoff for a non-transactional DynamoDB pattern. The `updated_at` timestamp on each TREE row provides a simple consistency signal. A future migration to DynamoDB TransactWriteItems (capped at 100 items) could make shallow subtrees atomic.

### 5.8 Root categories without a TREE row

A category created via `POST /ui/catalog/categories` (`app/routers/catalog.py:260`) never gets a `TREE` row until `add_child` (or a root-attachment call from PRD-005) explicitly places it in the tree. `_get_tree_row` returns `None` for such categories; the flat `list_categories` endpoint continues to return them without any tree metadata. This is the correct behavior: the tree is an opt-in overlay.

## 6. Feature Flag & Config

### 6.1 Master flag

The master flag is `product_depth_enabled` (`S.product_depth_enabled`), introduced in PRD-002 at `app/core/settings.py`. It does not yet exist in the codebase; PRD-002 will add it adjacent to the catalog block (`catalog_table_name` at `:832`) and the inventory/returns flags (`inventory_reservations_enabled` at `:839`, `returns_rma_enabled` at `:846`):

```python
product_depth_enabled: bool = os.environ.get("PRODUCT_DEPTH_ENABLED", "false").lower() == "true"
```

Default is `False`. With flag off:
- `product_categories.py` all public functions raise 404 immediately.
- `T.product_depth` table exists (PRD-002 creates it at startup) but is never queried.
- `list_categories` (`app/routers/catalog.py:293`) is byte-for-byte unchanged.

### 6.2 Max-depth setting

New setting to be added in `app/core/settings.py` adjacent to `product_depth_enabled`:

```python
product_depth_max_category_depth: int = int(
    os.environ.get("PRODUCT_DEPTH_MAX_CATEGORY_DEPTH", "10")
)
```

Env var: `PRODUCT_DEPTH_MAX_CATEGORY_DEPTH`, default `10`. Allows operators to reduce the tree height (e.g. set to `4` for a shallow category taxonomy) without a code change.

### 6.3 Flag gating in product_categories.py

Every public function calls `_require_enabled()` as its first statement. The `_flag_on` helper uses `getattr(S, "product_depth_enabled", False)` so it is safe to call even before PRD-002's settings keys exist on `S` (e.g., in tests that do not patch the settings object).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

`product_categories.py` contains zero `S.dev_mode` branches. All DynamoDB calls use `T.product_depth` and `T.catalog` — in dev this resolves to DynamoDB Local; in prod to the real AWS DynamoDB endpoint. The table handle is wired by PRD-002 via `_safe_table(S.product_depth_table_name)` (`app/core/tables.py:65–66`), which wraps the boto3 Table in `_FloatSafeTable` (`app/core/tables.py:29`) for float-to-Decimal coercion uniformly.

### 7.2 Idempotency

`add_child` is idempotent under replay only in the "already-written" sense: a second call returns 409 rather than silently succeeding. True idempotent replay (same result for same inputs, no error) is not needed here because `add_child` is not a billing or ledger operation. The 409 on replay is the correct semantics — callers can check `GET /categories/{id}/tree` (PRD-005) to confirm placement before retrying.

`move_category` and `remove_from_tree` are last-writer-wins on the TREE row. A client that retries a `move` after a timeout will re-apply the same re-parent; since the path/depth are recomputed from the new parent's current state, re-applying is safe.

### 7.3 Ownership enforcement

Every mutating function (`add_child`, `move_category`, `remove_from_tree`) fetches the `META` row from `T.catalog` and asserts `creator_id == user_sub`. The PRD-005 router may additionally call `_get_category_meta` (`app/routers/catalog.py:240`) or the local `_require_category_owner` (`app/routers/catalog.py:247`) before delegating to the service. Note: `_require_category_owner` only raises 403 when `creator_id` is non-None and mismatched; the service's own check must be stricter. The double-check (router + service) is intentional: the service is self-contained and callable from non-HTTP contexts (e.g., admin scripts) without relying on the router's guard.

### 7.4 Path injection

`category_id` values in the `path` string are stored as-is. Since `category_id` values are generated by `uuid.uuid4().hex` (see `app/routers/catalog.py:262`) or supplied by the caller but validated to be non-empty strings, they cannot contain `/` by construction (UUIDs are hex-only). A defensive `if "/" in category_id: raise ValueError` guard is added in `_tree_pk` to prevent path-separator injection if the creation point ever changes.

### 7.5 No money paths

PRD-004 introduces no billing, ledger, or payment operations. It does not call `new_ledger_entry` or `refund_payment`. There is nothing to fork.

## 8. Backward Compatibility & Migration

### 8.1 Flag-off invariant

With `PRODUCT_DEPTH_ENABLED=false` (the default):

- `GET /ui/catalog/categories` returns the same response as before PRD-004 ships — `CatalogCategoryListOut` items built from `T.catalog` GSI1 query only.
- No `TREE` rows are written to `T.product_depth`.
- `T.product_depth` is empty (or may contain rows from tests) but is never queried.

### 8.2 Existing categories are not retroactively tree-placed

Enabling `PRODUCT_DEPTH_ENABLED=true` on an existing deployment does **not** automatically place all categories in the tree. Operators must call `POST /ui/catalog/categories/{id}/children` (PRD-005) explicitly for each category they wish to place. Categories not in the tree continue to appear in the flat `list_categories` listing and are valid targets for item creation; they simply have no breadcrumb or tree positioning.

A bulk backfill script (out of scope for PRD-004) could iterate `list_categories` and call `add_child` for each category to produce a flat one-level tree. This is deferred to an ops runbook.

### 8.3 Schema migration risk

The `TREE` row's primary key (`CAT#{id}` / `TREE`) lives on `T.product_depth`, not `T.catalog`. No existing row on `T.catalog` shares the SK `"TREE"` — the existing catalog rows use `SK="META"` (categories) and `SK=ITEM#{id}` (items). There is no risk of collision.

### 8.4 GSI1 flat listing unaffected

The `GSI1` on `T.catalog` is keyed on `GSI1PK="CATS"` / `GSI1SK=f"{name.lower()}#{id}"`. PRD-004 never writes to `T.catalog`. The `GSI1` listing path is untouched.

## 10. Open Questions / Assumptions

**OQ-1** (Assumption: path separator is `/`): Category IDs generated by `uuid.uuid4().hex` are hex-only and cannot contain `/`. If the caller-supplied `category_id` field (`CatalogCategoryCreateIn.category_id` at `app/models.py:521` — `Optional[str] = None`) is used, the assignment at `app/routers/catalog.py:262` does not currently restrict special characters. **Assumption**: PRD-005 will add a validation that rejects `category_id` values containing `/` or `#`. The service adds a defensive guard.

**OQ-2** (Assumption: owner of child must own the parent too for `add_child`): The current implementation only checks that `user_sub` owns the child category. Should cross-user parent-child relationships be allowed (e.g., Alice adds her category as a child of Bob's category)? **Assumption: no** — both parent and child must share the same `creator_id`. The service will add a check that `parent_meta["creator_id"] == user_sub` when `parent_category_id` is not None.

**OQ-3** (Assumption: `position` is caller-supplied or auto-incremented): The auto-increment approach (`_next_position` returns max + 1) produces gaps when categories are deleted. A gap-free sequence would require a read-modify-write on the sibling list, which introduces concurrency risk. **Assumption**: gaps in positions are acceptable for MVP; the UI can always call the reorder endpoint (PRD-005) to compact positions.

**OQ-4** (Assumption: `move_category` path rewrite is non-atomic): `_bulk_update_paths` makes N individual `update_item` calls with no DynamoDB transaction. For large subtrees this can interleave with concurrent reads. **Assumption**: for MVP, eventual consistency is acceptable; a follow-up ticket will wrap moves into DynamoDB TransactWriteItems for subtrees <= 25 nodes.

**OQ-5** (Assumption: flat `list_categories` is not enriched with tree data): With the flag on, `GET /ui/catalog/categories` (`app/routers/catalog.py:294`) still returns a flat `CatalogCategoryListOut` with no `parent_category_id` or `position` fields. **Assumption**: tree enrichment of the flat list is a PRD-005 concern (the router can optionally join TREE rows). PRD-004 only provides the service functions; it does not modify `list_categories`.

**OQ-6** (Assumption: PRD-003 models for tree outputs): PRD-004 requires `CategoryTreeOut` and `BreadcrumbItemOut` Pydantic models. The ticket assigns model definition to PRD-003, but PRD-003 does not explicitly enumerate these shapes. **Assumption**: PRD-004 defines them locally in `app/services/product_categories.py` as plain TypedDicts (no Pydantic) and the router (PRD-005) wraps them in proper Pydantic response models. Alternatively, PRD-003 can be extended; flag for PRD-003 reviewer.
