# ECM-008 — Reserve stock on add-to-cart / checkout-begin

**Type:** Feature | **Priority:** P0 | **Estimate:** 4 days
**Dependencies:** ECM-005 (live availability projection), OFB-004 (soft reservation service — already implemented in `app/services/inventory.py`)

---

## 1. Summary & Goal

ECM-008 hooks the shopping-cart mutation functions (`add_item`, `add_catalog_item`, `set_item_quantity`, `decrement_item`, `delete_cart`) into the existing soft-reservation lifecycle (`app/services/inventory.py`) so that:

1. **Adding an item to a cart places a soft reservation** — available stock decreases immediately, preventing oversell by other concurrent shoppers.
2. **Adjusting quantity adjusts the reservation delta** — the inventory `reserved` counter stays in sync with the cart quantity.
3. **Deleting a cart or removing all items releases all its reservations** — stock is freed immediately rather than waiting for the TTL loop.
4. **Re-adding the same SKU is idempotent** — a deterministic reservation-ID (`sha256("{cart_id}#{sku}")[:16]`) is used as an upsert key so multiple `add_item` calls for the same `{cart_id, sku}` never create duplicate reservations.
5. **Reservation failure never blocks the cart add** — if the inventory service errors (SKU not registered, over-capacity, or DDB unavailable), the function degrades gracefully to the current behavior and the item is added without a reservation.
6. **With the flag off, zero behavior changes** — every call-site guard is `if _reservations_enabled_for_sku(sku):` and the `app/services/inventory.py` module remains entirely dormant.

The existing reservation expiry loop (`expire_due_reservations` in `inventory.py`) and the cart abandonment loop (`expire_abandoned_carts` in `shoppingcart.py`) handle stranded reservations; ECM-008 does not add a new background task.

## 2. Context & Current State

### 2.1 Cart item mutation functions

The five functions that ECM-008 touches all live in `app/services/shoppingcart.py`:

| Function | Line | What it does today |
|---|---|---|
| `add_item` | `:311` | Upserts a `CART#{cart_id}#ITEM#{sku}` row; increments qty if already present (early return at `:337` for existing item; new-item return at `:367`) |
| `add_catalog_item` | `:370` | Resolves the catalog row (`sku = f"catalog:{item_id}"` at `:391`), then delegates to `add_item` |
| `set_item_quantity` | `:400` | Overwrites qty via unconditional `put_item` at `:419`; deletes row if qty ≤ 0 (`:410`) |
| `decrement_item` | `:424` | Decrements qty; early `return` at `:437` if result ≤ 0 (item deleted) |
| `delete_cart` | `:448` | Batch-deletes all `CART#{cart_id}#ITEM#*` rows and the cart row itself via `batch_writer` |

None of these functions currently call the inventory service. The only inventory touch today is at purchase time in `purchase_cart` (`shoppingcart.py:474`), where `stock_count` is decremented on the `T.catalog` table via a conditional `stock_count >= :qty` expression (`shoppingcart.py:518`).

### 2.2 Existing soft-reservation service (OFB-004)

`app/services/inventory.py` already provides the full reservation lifecycle, implemented and tested (see `tests/test_ofb_inventory.py`):

- `reserve(sku, quantity, *, location_id, cart_id, user_sub, ttl_seconds)` — `inventory.py:339` — atomically decrements `available` via `ConditionExpression="available >= :q"` on `T.inventory` and writes a `RES#{uuid}` row to `T.reservations`. Raises `HTTPException(409)` on out-of-stock (`inventory.py:371`).
- `release_reservation(reservation_id, *, reason, user_sub, terminal_status)` — `inventory.py:492` — flips the reservation to `released`, restores `available` on `T.inventory`. Idempotent under replay.
- `commit_reservation(reservation_id)` — `inventory.py:456` — flips to `committed`, decrements `on_hand`. Called at purchase time (ECM-010).
- `expire_due_reservations(*, now, limit)` — `inventory.py:538` — queries `GSI_EXPIRY` (partition key `gsi_expiry_pk = "SCHED#ACTIVE"`, `inventory.py:44`) for overdue active reservations and calls `release_reservation` on each. Not yet wired to a background task.

The `reserve` function uses a randomly generated `uuid4().hex` as the `reservation_id` (`inventory.py:383`). ECM-008 must add a `reservation_id: Optional[str] = None` parameter (the spec's earlier use of the name `correlation_id` was informal; the parameter name is `reservation_id`) so the cart layer can pass a deterministic ID derived from `{cart_id}#{sku}`, enabling idempotent upsert.

### 2.3 Reservation table schema

`T.reservations` (`scripts/local-ddb-init.py:2469`; handle: `app/core/tables.py:318`) stores reservation rows as:

```
PK  = reservation_pk  ("RES#{reservation_id}")
SK  = sk              ("META")
GSI_SKU   : sku (HASH) / created_at (N, RANGE)
GSI_EXPIRY: gsi_expiry_pk (HASH) / expires_at (N, RANGE)
```

There is no GSI keyed on `cart_id` today. ECM-008 adds `GSI_CART` (partition key `cart_id`, sort key `created_at`) to support `list_active_reservations_for_cart(cart_id)` — needed by `delete_cart` and the adjustment path.

### 2.4 Feature flag — today

`S.inventory_reservations_enabled` (`app/core/settings.py:839`, env `INVENTORY_RESERVATIONS_ENABLED`, default `false`) is the existing master switch for `T.inventory` / `T.reservations`. With it off the inventory service is dormant and the `_require_enabled()` guard raises 404 (`inventory.py:54–56`). The internal `_flag_on()` helper is at `inventory.py:50`.

ECM-008 introduces a second, narrower flag `S.store_cart_reservations_enabled` (env `STORE_CART_RESERVATIONS_ENABLED`, default `false`) that gates specifically the cart-reservation hooks. Both flags must be true for ECM-008 behavior to activate. The two-flag design means operators can have `INVENTORY_RESERVATIONS_ENABLED=true` (for manual admin stock adjustments via ECM-006 UI) without enabling automatic cart-hooks, allowing a phased rollout.

## 3. Data Model

### 3.1 No new DynamoDB tables

ECM-008 reuses `T.inventory` and `T.reservations` exactly as defined by OFB-003/004. No new tables are needed.

### 3.2 New GSI on `reservations` table — `GSI_CART`

The `delete_cart` and quantity-adjustment paths need to enumerate all active reservations for a given `cart_id` without a full-table scan. A new GSI is added:

```
GSI_CART: partition_key = cart_id (S), sort_key = created_at (N)
```

This is a sparse GSI: rows without a `cart_id` attribute (manually created admin reservations) are not projected into it, which is correct.

The `scripts/local-ddb-init.py` `TableDef` for `reservations` (currently at line `2469`) becomes:

```python
TableDef(
    _resolve_table_name(S.reservations_table_name, "reservations"),
    "reservation_pk",
    "sk",
    gsi=[
        {"index_name": "GSI_SKU",    "partition_key": "sku",           "sort_key": "created_at"},
        {"index_name": "GSI_EXPIRY", "partition_key": "gsi_expiry_pk", "sort_key": "expires_at"},
        {"index_name": "GSI_CART",   "partition_key": "cart_id",       "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N", "expires_at": "N"},
)
```

`cart_id` is already `str` (S) so no new `attr_types` entry is needed for it. `created_at` is already declared `N` and covers the `GSI_CART` sort key as well. This is a pure additive change; existing `GSI_SKU` and `GSI_EXPIRY` queries are unaffected.

### 3.3 `reservation_id` derivation — deterministic key

ECM-008 computes a stable reservation ID for each `{cart_id, sku}` pair:

```python
# In app/services/shoppingcart.py (new helper)
def _cart_sku_reservation_id(cart_id: str, sku: str) -> str:
    """Deterministic 32-hex-char reservation ID for a cart+sku pair.
    Stable across retries; ensures re-adding the same SKU is idempotent.
    """
    from app.core.crypto import sha256_str
    return sha256_str(f"{cart_id}#{sku}")[:32]
```

`sha256_str` is already defined in `app/core/crypto.py:13–14` as `hashlib.sha256(s.encode("utf-8")).hexdigest()`.

The reservation row PK becomes `RES#{sha256(cart_id#sku)[:32]}`. Because the hash is deterministic, a second call to `add_item` for the same `{cart_id, sku}` derives the same `reservation_id` and the `_upsert_cart_reservation` helper (§4.2) can read the existing row before deciding whether to create a new one or adjust the quantity delta.

### 3.4 `correlation_id` field on `inventory.reserve`

The existing `reserve` function (`inventory.py:339`) uses `uuid4().hex` as the `reservation_id`. ECM-008 adds an optional `reservation_id: Optional[str] = None` parameter:

```python
def reserve(
    sku: str,
    quantity: int,
    *,
    location_id: str = DEFAULT_LOCATION,
    user_sub: str = "system",
    cart_id: Optional[str] = None,
    ttl_seconds: Optional[int] = None,
    reservation_id: Optional[str] = None,   # NEW — deterministic caller-supplied ID
) -> Dict[str, Any]:
```

When `reservation_id` is supplied the function uses it instead of `uuid4().hex` at line `383`. This is additive: all existing callers that omit `reservation_id` continue to receive random IDs.

The reservation row must also carry a `cart_reservation_correlation_id` attribute (the same value as `reservation_id`) so the upsert helper can distinguish a "same-cart re-add" (adjust delta) from a "different cart for the same SKU" (separate reservation). In practice, because the PK itself encodes the `{cart_id, sku}` hash, the lookup `get_item(Key={"reservation_pk": "RES#{id}", "sk": "META"})` is sufficient.

### 3.5 Additive fields on `ShoppingCartItemOut` (optional)

`ShoppingCartItemOut` (`app/models.py:956–971`) gains one optional additive field:

## 4. API / Service Design

### 4.1 No new public endpoints

ECM-008 is entirely a service-layer wiring ticket. All cart endpoints (`POST /ui/shoppingcart/carts/{cart_id}/items`, `PATCH /…/items/{sku}`, `DELETE /…/items/{sku}`, `DELETE /…/carts/{cart_id}`) remain registered in `app/main.py` without change. Auth dependencies (`Depends(require_ui_session)`) are unchanged.

### 4.2 New helpers in `app/services/shoppingcart.py`

**`_cart_sku_reservation_id(cart_id, sku) -> str`** (§3.3)

**`_reservations_flag() -> bool`**

```python
def _reservations_flag() -> bool:
    """True iff both the inventory master switch and the cart-reservation hook are on."""
    return (
        bool(getattr(S, "inventory_reservations_enabled", False))
        and bool(getattr(S, "store_cart_reservations_enabled", False))
    )
```

**`_upsert_cart_reservation(user_sub, cart_id, sku, new_qty) -> Optional[str]`**

This is the core idempotency helper. It:

1. Derives `res_id = _cart_sku_reservation_id(cart_id, sku)`.
2. Attempts `T.reservations.get_item(Key={"reservation_pk": f"RES#{res_id}", "sk": "META"})` to check for an existing active reservation.
3. **No existing active reservation** → calls `inventory.reserve(sku, new_qty, cart_id=cart_id, user_sub=user_sub, reservation_id=res_id)`. Returns `res_id` on success.
4. **Existing active reservation with different `quantity`** → computes `delta = new_qty - existing["quantity"]`. If `delta > 0`, calls `inventory.reserve` for `delta` units with a different `reservation_id` (random). Then updates the canonical reservation row's `quantity` field via `update_item` to `new_qty`. This "delta-reserve" approach avoids releasing and re-creating — it only touches the incremental units. If `delta < 0` (quantity decrease), calls `_partial_release(res_id, abs(delta))` (§4.3). If `delta == 0` (same qty), no-op.
5. **Existing reservation in terminal status** (`committed`, `released`, `expired`) → treats as absent and creates a fresh one.
6. **Any exception** → logs at `WARNING` level and returns `None` (degrade gracefully — item is still added to cart without a reservation).

Returns the canonical `res_id` string if a reservation exists/was created; `None` on degrade.

**`_release_cart_sku_reservation(cart_id, sku, *, user_sub) -> None`** (best-effort)

Derives `res_id`, looks up the active reservation row, calls `inventory.release_reservation(res_id, reason="cart_item_removed", user_sub=user_sub)`. Swallows all exceptions (a failed release is not user-visible; the TTL loop handles stranded reservations).

**`_release_all_cart_reservations(cart_id, *, user_sub) -> int`** (best-effort, returns count released)

Queries `GSI_CART` for all `cart_id = cart_id` rows, then calls `release_reservation` on each active one. Used by `delete_cart`. Paginates via `LastEvaluatedKey` (DynamoDB FilterExpression gotcha per CLAUDE.md).

### 4.3 `_partial_release(res_id, delta_qty)` helper in `inventory.py`

When a quantity decrease is smaller than the full reservation (e.g., cart had 5 units, user sets to 3 — release 2), we need a partial release. Since `release_reservation` is all-or-nothing, ECM-008 adds:

```python
def partial_release(
    reservation_id: str,
    release_qty: int,
    *,
    user_sub: str = "system",
) -> Dict[str, Any]:
    """Reduce an active reservation by ``release_qty`` units without closing it.

    Updates both the reservation row quantity and the inventory available counter.
    Raises 422 if release_qty >= existing quantity (use release_reservation instead).
    Idempotent: if reservation is already terminal, returns current state.
    """
```

Implementation: reads the current reservation row; validates `release_qty < existing["quantity"]`; does an optimistic `update_item` on the reservation row decrementing `quantity` by `release_qty` under `ConditionExpression="#status = :active AND quantity >= :rq"`; then decrements `reserved` and increments `available` on `T.inventory` by `release_qty`.

This function is additive to `inventory.py` and does not affect any existing caller.

### 4.4 Wiring into cart mutation functions

All modifications are within `try/except Exception` blocks so reservation errors never propagate to the caller. The logic is guard-wrapped:

#### `add_item` (`shoppingcart.py:311`)

`add_item` has **two** return paths — both must be hooked:

- **Existing-item path** (line `337`, `return _item_from_item(updated)`): fires when the SKU is already in the cart; `new_qty` is computed at line `320`.
- **New-item path** (line `367`, `return _item_from_item(item)`): fires for a first-time add.

Both paths need the reservation hook applied before the `return` statement. The helper reads `item.get("quantity")` (or `updated.get("quantity")`) for the post-merge quantity. Example for the new-item path (identical structure for the existing-item path):

```python
# ECM-008: soft-reserve on add-to-cart (flag-gated, best-effort)
res_id: Optional[str] = None
if _reservations_flag():
    try:
        from app.services import inventory as _inv
        res_id = _upsert_cart_reservation(
            user_sub, cart_id, sku,
            int(item.get("quantity", 1)),
        )
    except Exception:
        pass  # degrade: item added without reservation
if res_id:
    item = {**item, "reservation_id": res_id}
return _item_from_item(item)
```

The `add_catalog_item` function at `:370` calls `add_item` and inherits the reservation automatically — no extra hook needed.

#### `set_item_quantity` (`shoppingcart.py:400`)

After the successful `put_item` at line `419` and before `return _item_from_item(updated)`:

```python
if _reservations_flag():
    try:
        from app.services import inventory as _inv
        if quantity <= 0:
            _release_cart_sku_reservation(user_sub, cart_id, sku)
        else:
            _upsert_cart_reservation(user_sub, cart_id, sku, quantity)
    except Exception:
        pass
```

When `quantity <= 0` the item row is already deleted above (`:410`), so the release is correct.

#### `decrement_item` (`shoppingcart.py:424`)

After the successful `put_item` or `delete_item` and before the final return:

```python
if _reservations_flag():
    try:
        from app.services import inventory as _inv
        if new_qty <= 0:
            _release_cart_sku_reservation(user_sub, cart_id, sku)
        else:
            _upsert_cart_reservation(user_sub, cart_id, sku, new_qty)
    except Exception:
        pass
```

#### `delete_cart` (`shoppingcart.py:448`)

After the `batch_writer` block that deletes all item rows and the cart row (`:455`):

```python
if _reservations_flag():
    try:
        _release_all_cart_reservations(cart_id, user_sub=user_sub)
    except Exception:
        pass
```

The `user_sub` is already available from the function signature.

### 4.5 Reservation expiry background task wiring

`expire_due_reservations` in `inventory.py` is already fully implemented (`:538`) but is not currently wired to any background loop. ECM-008 **does not add a new task** — instead, the existing `_cart_abandonment_loop` in `app/routers/shoppingcart.py` is extended to also call `expire_due_reservations()` on each tick when the flag is on:

```python
# Inside _cart_abandonment_loop, after expire_abandoned_carts():
if getattr(S, "inventory_reservations_enabled", False):
    try:
        from app.services.inventory import expire_due_reservations
        n = expire_due_reservations()
        if n:
            logger.info("reservation_expiry_tick", extra={"released": n})
    except Exception:
        logger.exception("Reservation expiry tick failed")
```

This is safe because `expire_due_reservations` is already idempotent (conditional update guard) and the cart-abandonment loop runs on a configurable interval (`S.cart_abandonment_scan_interval_sec` — `settings.py:815`, env `CART_ABANDONMENT_SCAN_INTERVAL_SEC`, default **300 s** / 5 minutes). The reservation TTL default is 1800 s (`INVENTORY_RESERVATION_TTL_SECONDS`), so expired reservations are cleaned up within six loop periods at most.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag off — exact current behavior

When `_reservations_flag()` returns `False` (either flag absent or false), every `try/except` block with the reservation call is never entered. `add_item`, `add_catalog_item`, `set_item_quantity`, `decrement_item`, and `delete_cart` behave byte-for-byte identically to today. No DDB calls to `T.inventory` or `T.reservations` are made.

### 5.2 Idempotent re-add (same SKU, same cart)

**Scenario**: user adds SKU "WIDGET-RED-M" once (quantity 2), then clicks "Add" again (quantity 1 more).

1. First `add_item` call: `new_qty = 2`. `_upsert_cart_reservation` finds no active reservation for the derived `res_id`. Creates reservation for quantity 2. Returns `res_id`.
2. `add_item` sets `item["quantity"] = 3` (incremented at `:320`).
3. Second `add_item` call: `new_qty = 3`. `_upsert_cart_reservation` finds active reservation for `res_id` with `existing["quantity"] == 2`. Computes `delta = 3 - 2 = 1`. Calls `inventory.reserve(sku, 1, ...)` with a fresh random `reservation_id` to atomically claim 1 more unit. Updates canonical reservation row quantity to 3.

At no point is the full 3-unit reservation double-counted: `T.inventory.reserved` increases by 2 on call 1 and by 1 on call 2 — total 3, matching `item["quantity"]`.

### 5.3 Oversell race — concurrent checkouts of the last unit

Two users, Alice and Bob, both click "Add to Cart" for the last unit of SKU "LAST-UNIT".

- Alice's `inventory.reserve("LAST-UNIT", 1, ...)` wins the `available >= 1` conditional update. `available` drops to 0.
- Bob's `inventory.reserve("LAST-UNIT", 1, ...)` fails the conditional check. `ClientError(ConditionalCheckFailedException)` is raised inside `inventory.reserve`, which re-raises as `HTTPException(409, "Item 'LAST-UNIT' is out of stock")`.
- ECM-008's `try/except Exception` in `add_item` catches this `HTTPException` and **suppresses it**, degrading to an item add without a reservation.

This is the correct degradation: the reservation is advisory. Purchase-time stock enforcement remains in `purchase_cart` (`:514`), so Bob's eventual checkout still receives the 409 out-of-stock error. The reservation simply gives Alice a stronger hold during her browsing session.

If operators want harder enforcement at add-time (reject the add when out of stock), that is a future flag (`STORE_RESERVATION_HARD_ENFORCE`, out of scope for ECM-008). For now, degrade-to-no-reservation is the specified behavior per the ticket acceptance criteria.

### 5.4 Inventory row absent for SKU

When `T.inventory` has no row for a given SKU (common for all pre-existing catalog items before ECM-003/006 creates inventory records), `inventory.reserve` raises `HTTPException(409, "No inventory for SKU '...'")`. ECM-008's `try/except` suppresses this and the cart add succeeds without a reservation. The `_reservations_flag()` guard ensures this path is never hit when the flag is off.

### 5.5 Cart expiry and stranded reservations

When `expire_abandoned_carts` (`shoppingcart.py:912`) transitions a cart to `status="EXPIRED"` (`shoppingcart.py:948`), it does not call `delete_cart` — it only updates the cart row's `status` field. This means item rows and reservations persist until the DDB TTL sweeps them. ECM-008 handles this in two complementary ways:

1. The `expire_due_reservations` call in the abandonment loop (§4.5) releases reservation rows whose `expires_at` is past, regardless of whether the cart was explicitly deleted.
2. The reservation TTL (`INVENTORY_RESERVATION_TTL_SECONDS`, default 1800 s) is shorter than the cart abandonment threshold (`CART_ABANDONMENT_EXPIRE_HOURS`, default 720 h = 2592000 s), so reservations naturally expire long before the cart TTL sweeps the item rows.

No additional coupling between cart expiry and reservation release is required.

### 5.6 `delete_cart` release ordering

`delete_cart` (`shoppingcart.py:448`) uses a DynamoDB `batch_writer` to delete item rows first, then the cart row (`batch.delete_item(Key=cart["PK"], cart["SK"])`). ECM-008's `_release_all_cart_reservations` call is placed **after** the batch writer context exits, so the DDB item rows are deleted before the release attempt. If the release call fails, the items are still gone — the TTL loop handles the stranded reservations.

### 5.7 `partial_release` — concurrent quantity decrements

If two browser tabs call `PATCH /items/{sku}` simultaneously (both reducing quantity), two concurrent `_upsert_cart_reservation` calls could both compute `delta < 0` from the same stale `existing["quantity"]`. The `partial_release` guard `ConditionExpression="#status = :active AND quantity >= :rq"` on the reservation row prevents double-release: the second concurrent call finds `quantity` already decremented and its conditional update fails; the function returns the current state without touching `T.inventory`. Note: `set_item_quantity` itself uses an unconditional `put_item` at line `419` (no CAS guard on the cart row); the reservation adjustment is best-effort after the cart put succeeds. The CAS guard `ConditionExpression="#status = :open"` at `shoppingcart.py:626` belongs to `purchase_cart`, not `set_item_quantity`.

### 5.8 `add_catalog_item` — SKU mapping

`add_catalog_item` constructs `sku = f"catalog:{item_id}"` (`shoppingcart.py:391`) and delegates to `add_item`. The reservation is placed against this compound SKU. The corresponding `T.inventory` row must have been seeded with `sku = "catalog:{item_id}"` for the reservation to succeed. With the reservation flag off this is irrelevant; with it on, ECM-006 (catalog enrichment) and ECM-005 (availability projection) are expected to ensure the inventory row exists for catalog items.

### 5.9 `ShoppingCartItemOut.reservation_id` presence

`_item_from_item` at `shoppingcart.py:79–104` builds the response dict from the DDB item. The `reservation_id` attribute is only set on the in-memory `item` dict after the reservation call — it is **not persisted** to DynamoDB (the cart item row does not store `reservation_id`). This is intentional: the `T.reservations` table is the authoritative source; caching `reservation_id` on the cart item row would create a stale-reference risk when the reservation expires. The `reservation_id` in the response is therefore only valid for the duration of the HTTP response and is used solely for the frontend "reserved" indicator (ECM-022).

### 6.4 Reservation TTL

`S.inventory_reservation_ttl_seconds` (env `INVENTORY_RESERVATION_TTL_SECONDS`, default `1800`, `settings.py:840`) controls how long a cart reservation holds stock before the expiry loop releases it. This value is passed as `ttl_seconds` to `inventory.reserve`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 — no dev/prod branching

ECM-008 introduces no `if S.dev_mode:` branches. All DDB operations go through the same `T.inventory` (`app/core/tables.py:317`) and `T.reservations` (`app/core/tables.py:318`) handles regardless of environment. In dev, these resolve to DynamoDB Local (`:8001`). The `_reservations_flag()` guard is a runtime settings check — identical behavior in dev and prod.

The `sha256_str` function used for deterministic `reservation_id` derivation (`app/core/crypto.py:13–14`) has no dev/prod branching.

### 7.2 Idempotency — reservation upsert

The deterministic `reservation_id = sha256("{cart_id}#{sku}")[:32]` ensures:
- Multiple `add_item` calls for the same `{cart_id, sku}` converge to a single active reservation row.
- Network retries that replay an `add_item` POST never double-reserve stock.
- `_upsert_cart_reservation` reads the existing row before acting, so the DDB write is conditional on `existing.quantity != new_qty`.

The `release_reservation` and `partial_release` functions already use `ConditionExpression="#status = :active"` guards so concurrent release replays are idempotent no-ops.

### 7.3 Security — reservation does not bypass price/billing

ECM-008 only writes to `T.reservations` and `T.inventory`. It does not touch `T.billing`, the ledger, or any promo-code table. The reservation is advisory stock-hold only; the authoritative money-out event remains `purchase_cart` → `billing_shared.new_ledger_entry`. No billing path diverges.

### 7.4 Security — reservation_id in response is non-secret

`reservation_id` in `ShoppingCartItemOut` is a deterministic hash of `{cart_id}#{sku}`. Since both `cart_id` and `sku` are already visible to the authenticated user, revealing their hash adds no information. The hash is used only as a DDB lookup key; it is not a capability token and carries no access rights.

### 7.5 Reservation TTL vs. cart abandonment expiry

`INVENTORY_RESERVATION_TTL_SECONDS` (default 1800 s = 30 min, `settings.py:840`) must always be less than `CART_ABANDONMENT_EXPIRE_HOURS` (default 720 h = 30 days, `settings.py:818`). If misconfigured (TTL > abandonment window), reservations could outlive the cart, holding stock after the cart is considered abandoned. Validation: `_reservations_flag()` could emit a startup warning if `S.inventory_reservation_ttl_seconds > S.cart_abandonment_expire_hours * 3600` — but this is advisory, not a runtime error.

## 8. Backward Compatibility & Migration

### 8.1 `T.reservations` GSI addition — zero downtime

Adding `GSI_CART` to the `reservations` table is additive. In dev, `just restart` recreates the table with the new GSI. In production, a `UpdateTable` call adds the GSI; DynamoDB backfills it asynchronously (existing rows acquire the GSI entry as they are scanned). During backfill, `_release_all_cart_reservations` may miss reservations whose `cart_id` entry is not yet in the GSI — the TTL loop handles these as a safety net. The cart-reservation hooks must not be turned on until the GSI backfill completes (operator runbook note: verify GSI status is `ACTIVE` before enabling `STORE_CART_RESERVATIONS_ENABLED=true`).

### 8.2 Existing `inventory.reserve` callers

The `reservation_id: Optional[str] = None` parameter is additive to the `reserve` function signature. All existing callers (`tests/test_ofb_inventory.py`, any admin endpoints from ECM-006) omit it and continue to receive random IDs. No behavioral change.

### 8.3 Existing cart item DDB rows

Pre-existing cart item DDB rows (`type=item`) do not have a `reservation_id` attribute. `_item_from_item` returns `None` for missing attributes, so `ShoppingCartItemOut.reservation_id` will be `None` for items added before ECM-008 was deployed. This is correct: those items have no reservation.

### 8.4 `ShoppingCartItemOut` additive field

Adding `reservation_id: Optional[str] = None` to `app/models.py:956` is backward-compatible. Existing E2E tests that assert `ShoppingCartItemOut` fields check for the presence of known fields; the new optional field is absent from existing responses and invisible to those assertions.

### 8.5 `partial_release` function — new addition to `inventory.py`

`partial_release` is a new export from `app/services/inventory.py`. It is additive; it does not modify any existing function. It is not exposed via any API endpoint — it is called only internally by `_upsert_cart_reservation` in `shoppingcart.py`.

## 10. Open Questions / Assumptions

1. **Assumption: `inventory.reserve` receives the caller-supplied `reservation_id` via the new parameter (§3.4).** If the OFB-004 implementation freezes the random-ID approach, `_upsert_cart_reservation` must instead query `GSI_SKU` filtered by `cart_id` to find the existing reservation. The `GSI_CART` approach (§3.2) is cleaner and avoids a read-before-write on every add; the spec assumes the `reservation_id` parameter is added.

2. **Assumption: `T.reservations.GSI_CART` backfill completes before `STORE_CART_RESERVATIONS_ENABLED=true` is set in production.** If operators enable the flag before backfill, `_release_all_cart_reservations` may miss older reservations (pre-backfill rows not yet in the GSI). The TTL loop provides the safety net but the gap may hold stock for up to `INVENTORY_RESERVATION_TTL_SECONDS`. Documented as an operator runbook step.

3. **Assumption: `add_catalog_item` constructs `sku = "catalog:{item_id}"` and the corresponding `T.inventory` row has been seeded with the same SKU string.** If ECM-005/006 uses a different SKU format for catalog items, the reservation call silently degrades (§5.4). This is acceptable — the cart add still succeeds.

4. **Assumption: the cart's `user_sub` is passed through to `inventory.reserve` as `user_sub` for audit logging.** The `add_item` function signature already receives `user_sub` as its first argument, so this is straightforward.

5. **Assumption: `partial_release` uses an optimistic conditional update (not a read-modify-write).** If moto's conditional `update_item` behavior for `quantity >= :rq` differs from real DynamoDB, tests may need to use `patch` to stub the DDB call directly. The `test_ofb_inventory.py` pattern (moto + frozen T) handles this.

6. **Open: should the `reservation_id` be stored on the cart item DDB row?** The current spec does NOT persist it (§5.9). If ECM-010 (commit-on-purchase) needs to look up the reservation by `{cart_id, sku}` at purchase time, it can rederive the same deterministic ID using `_cart_sku_reservation_id`. Storing it on the cart item row would be a convenience denormalization. This is deferred — ECM-010 can decide based on its own implementation needs.

7. **Open: should a `409 InsufficientStock` from `inventory.reserve` be surfaced to the user as a soft warning in the cart UI (e.g., "We couldn't reserve this item; stock may be limited") rather than silently degrading?** The acceptance criteria specify degrade-to-no-reservation, but UX-wise, a non-blocking toast could improve the experience. This is an ECM-022 (cart indicators) concern, not ECM-008.

8. **Assumption: the `expire_due_reservations` call in the abandonment loop (§4.5) is safe even when `store_cart_reservations_enabled=false` as long as `inventory_reservations_enabled=true`.** The loop guard checks only `inventory_reservations_enabled`, so manually-created admin reservations (from ECM-006 UI) are still expired by the loop regardless of the cart-hook flag.
