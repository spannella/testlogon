# POS-013 — Register terminal page + route + nav

**Type:** Feature | **Priority:** P1 | **Estimate:** 4 days
**Dependencies:** POS-012 (frontend types + endpoint wrappers)

---

## 1. Summary & Goal

POS-013 delivers the entire cashier-facing browser UI for the in-person point-of-sale
channel. It adds a `frontend/src/pages/pos/` directory containing the register
terminal page and its sub-components, wires a lazy-loaded React Router route into
`frontend/src/App.tsx`, adds a sidebar + mobile nav entry, and exports a
`isPosEnabled()` feature flag from `frontend/src/lib/featureFlags.ts`.

When `POS_ENABLED` is off (`VITE_POS_ENABLED=0` / absent): the nav entry is
invisible, the route is not rendered, and every existing shop/cart/orders/billing
component is byte-for-byte unchanged. When the flag is on and the user holds admin
or root role: the full open → scan → tender → receipt → close workflow is available
from a single page.

The page is purely a consumer of the POS-012 endpoint wrappers
(`frontend/src/api/endpoints/pos.ts`) — it never calls backend routes directly.

## 3. Data Model

POS-013 is a pure frontend ticket. It introduces no DynamoDB tables, no new
backend rows, and no new settings keys. All data it displays comes from the
`pos` single-table (PK `pos_pk` / SK `pos_sk`) defined by POS-003 and
surfaced by the POS-011 router via the POS-012 wrappers.

The relevant backend shapes (consumed read-only by the UI) are:

| Shape | Source | Key fields |
|---|---|---|
| `RegisterConfig` | POS-002/011 | `register_id`, `label`, `location_id`, `default_currency` |
| `RegisterSession` | POS-002/011 | `session_id`, `register_id`, `cashier_sub`, `status`, `opening_float_cents`, `closing_float_cents`, `expected_cash_cents`, `counted_cash_cents`, `over_short_cents`, `opened_at`, `closed_at` |
| `PosTransaction` | POS-002/011 | `txn_id`, `session_id`, `cart_id`, `order_id`, `status`, `subtotal_cents`, `discount_cents`, `tax_cents`, `total_cents`, `tenders`, `receipt_id` |
| `Tender` | POS-002/011 | `kind` (`cash`/`card`/`wallet`), `amount_cents`, `change_due_cents`, `payment_method_id` |
| `SessionReportOut` | POS-010/011 | `kind`, `gross_sales_cents`, `by_tender`, `refunds_cents`, `voids_cents`, `discount_cents`, `tax_cents`, `opening_float_cents`, `expected_cash_cents`, `counted_cash_cents`, `over_short_cents`, `generated_at` |

All monetary fields are integer cents; the UI divides by 100 for display.

## 4. API / Service Design

POS-013 consumes but does not define API endpoints. The complete backend surface
is specified in POS-011. This section documents the React Query call patterns and
component contract with the POS-012 wrappers.

### 4.1 Frontend API wrapper imports (from POS-012 `pos.ts`)

```ts
// All from frontend/src/api/endpoints/pos.ts (POS-012)
listRegisters()                                   // GET /ui/pos/registers
openSession(body: OpenSessionIn)                  // POST /ui/pos/sessions/open
closeSession(sessionId, body: CloseSessionIn)     // POST /ui/pos/sessions/{id}/close
getSession(sessionId)                             // GET  /ui/pos/sessions/{id}
getSessionReport(sessionId, kind: "x"|"z")        // GET  /ui/pos/sessions/{id}/report
addLine(sessionId, body: AddLineItemIn)           // POST /ui/pos/sessions/{id}/lines
removeLine(sessionId, sku)                        // DELETE /ui/pos/sessions/{id}/lines/{sku}
tender(sessionId, body: TenderRequestIn)          // POST /ui/pos/sessions/{id}/tender
voidTxn(txnId)                                    // POST /ui/pos/txns/{id}/void
refundTxn(txnId, body: RefundTxnIn)              // POST /ui/pos/txns/{id}/refund
getReceipt(txnId)                                 // GET  /ui/pos/txns/{id}/receipt
```

### 4.2 React Query keys

| Key | Shape | Stale time |
|---|---|---|
| `["pos", "registers"]` | `RegisterConfig[]` | 60 s |
| `["pos", "session", sessionId]` | `RegisterSession` | 5 s |
| `["pos", "session", sessionId, "report", kind]` | `SessionReportOut` | 0 (always refetch) |
| `["pos", "txn", txnId]` | `PosTransaction` | 5 s |
| `["billing", "payment-methods"]` | reuse existing | 30 s (existing) |

`queryClient.invalidateQueries(["pos", "session", sessionId])` is called after
every mutation that modifies session state (addLine, removeLine, tender, close).

### 4.3 Primary components

```
frontend/src/pages/pos/
├── PosTerminalPage.tsx     — top-level page; owns session state machine
├── SessionPanel.tsx        — open/close session form + over/short display
├── ScanLinePanel.tsx       — SKU/barcode input + product search + line list
├── CartSummary.tsx         — running total/tax/discount table
├── TenderModal.tsx         — Dialog: cash + change calc, card PM select, wallet, split
├── ReceiptPreview.tsx      — receipt HTML preview + print/reprint button
└── ReportView.tsx          — X / Z report display table
```

`PosTerminalPage.tsx` is the only component registered as a route; all others are
local sub-components imported by it.

### 4.4 Session state machine

The page models the cashier workflow as a local enum:

```ts
type PosUiState =
  | { kind: "no_session" }
  | { kind: "session_open"; session: RegisterSession; activeTxnId: string | null }
  | { kind: "tendering"; session: RegisterSession; txn: PosTransaction }
  | { kind: "receipt"; txn: PosTransaction }
  | { kind: "report"; session: RegisterSession; report: SessionReportOut };
```

State transitions:

```
no_session ──(open)──► session_open ──(scan/add)──► session_open (activeTxnId set)
session_open ──(tender)──► tendering ──(settle)──► receipt ──(close)──► no_session
session_open ──(view report x)──► report ──(back)──► session_open
receipt ──(void)──► session_open
receipt ──(refund)──► receipt (refunded txn)
receipt ──(reprint)──► receipt (same)
session_open ──(close session)──► report (Z report shown, status closed)
```

This local state is `React.useState` on `PosTerminalPage` — it is not put in a
global Zustand store. React Query holds server state; local state holds UI phase.

## 5. Detailed Behavior & Edge Cases

### 5.1 Open/close session panel (`SessionPanel.tsx`)

**Open form** (shown when `state.kind === "no_session"`):
- Fields: register selector (dropdown from `useQuery(["pos","registers"])`),
  opening float (currency input, integer cents internally).
- Validation: register required, opening float `>= 0` (Zod: `z.number().int().min(0)`).
- Submit calls `openSession` mutation; on success transitions to `session_open`.
- If backend returns 409 (already open): toast "Register already has an open session".

**Close form** (shown when `state.kind === "session_open"` and no active txn):
- Field: counted cash (currency input).
- Displays expected cash (from session data) and live over/short preview as the
  cashier types.
- Submit calls `closeSession`; on success fetches Z report and transitions to
  `state.kind === "report"` with the Z report data.
- 409 on double-close: toast "Session already closed".

### 5.2 Scan/add line panel (`ScanLinePanel.tsx`)

- Text input accepts SKU or barcode (submit on Enter or click Add).
- On submit: fires `addLine(sessionId, { sku: inputValue, quantity: 1 })` mutation.
  - 404 → toast "SKU not found".
  - Success → invalidates `["pos","session",sessionId]`; input cleared.
- Quantity spinners on each line item call `addLine` with updated qty (the backend
  service handles upsert-style qty edits per POS-005).
- Remove button calls `removeLine(sessionId, sku)`; optimistic removal with rollback
  on error (standard React Query optimistic update pattern).
- All mutations are disabled while a tender is in progress (`state.kind === "tendering"`).

### 5.3 Running cart summary (`CartSummary.tsx`)

- Derived from `session.active_txn` embedded in the `RegisterSession` response, or
  the separate `PosTransaction` if already created.
- Shows: line items table (name, qty, unit price, line total), subtotal, discount,
  tax (if applicable), **bold** total.
- "Tender" button becomes active only when at least one line item exists and total > 0.

### 5.4 Tender modal (`TenderModal.tsx`)

Rendered as a `<Dialog>` from shadcn/ui; opened by the "Tender" button.

**Cash tab:**
- Input: amount tendered (currency input, ge total).
- Live change due = `amountTendered - total` (computed in component, not sent to
  backend until submit).
- Validation: `z.number().int().min(transaction.total_cents, "Tender below total")`.

**Card tab:**
- Payment method selector: `useQuery(["billing","payment-methods"])` populates a
  `<Select>` of saved cards (reuses the existing query key established by
  `frontend/src/pages/billing/BillingPage.tsx`).
- Amount field (defaults to full remaining balance for split tender).

**Wallet tab:**
- Amount field (defaults to full remaining balance).

**Split tender:**
- "+ Add tender" button adds a row to a local `tenders: TenderIn[]` array.
- Running "paid so far" / "remaining" display.
- Submit is disabled until `sum(tenders.amount_cents) >= transaction.total_cents`.
- On submit: `tender(sessionId, { tenders, idempotency_key: crypto.randomUUID() })`.
  - 422 → toast "Tender amount below total".
  - 4xx from card/wallet provider → toast the backend `detail` message.
  - Success → close modal; transition to `state.kind === "receipt"`.

**Idempotency key:** generated with `crypto.randomUUID()` when the modal opens.
It is stored in component state so that clicking Submit twice (accidental double-tap)
sends the same key both times.

### 5.5 Receipt preview/print (`ReceiptPreview.tsx`)

- Fetches `getReceipt(txnId)` which returns HTML (or PDF per POS-009).
- HTML receipts: rendered inside an `<iframe srcDoc=…>` for print isolation.
- PDF receipts: served binary-safe by the backend as `application/pdf` (GAP-0209
  pattern); opens in a new tab via `window.open(url, "_blank")`.
- "Print" button calls `window.print()` (targets the iframe via `contentWindow.print()`).
- "New Sale" button transitions back to `session_open` with `activeTxnId: null`.
- "Void" button only shown when `txn.status === "tendered"` and session still open;
  calls `voidTxn(txnId)` — only allowed pre-settlement (backend enforces 409 if
  post-settlement).
- "Refund" button shown when `txn.status === "tendered"` (settled); opens a refund
  sub-form with line/qty selection and reason field; calls `refundTxn`.

### 5.6 X/Z report view (`ReportView.tsx`)

- Shown when `state.kind === "report"`.
- Two modes: X (midshift, fetch anytime) and Y (Z report, only after close).
- Displayed as a summary card:
  - Header: session ID, register label, cashier, opened/closed timestamps.
  - Gross sales, by-tender breakdown (cash/card/wallet), refunds, voids,
    discount, tax.
  - Cash float reconciliation: opening float, expected cash, counted cash,
    over/short (highlighted in amber if |over_short| > 0).
- "Print" button calls `window.print()` on the report section (uses
  `@media print` CSS to hide the rest of the shell).
- "Back" button returns to `session_open` (X report) or `no_session` (Z report,
  session closed).

### 5.7 Role gate in the page itself

`PosTerminalPage` reads `accessToken` from `useAuthStore` and calls
`canAccessGeneralAdminControls(accessToken)`. If false (regular USER role):

```tsx
return (
  <div className="p-8 text-center text-muted-foreground">
    Point of Sale is restricted to admin and cashier roles.
  </div>
);
```

This is a client-side guard for UX only; the backend enforces the role gate
authoritatively via the POS-011 auth dependencies.

### 5.8 Flag-off guard in the page itself

If `isPosEnabled()` returns false at render time (stale VITE bundle):

```tsx
return <Navigate to="/" replace />;
```

The route guard in `App.tsx` prevents navigation when the flag is off, but the
in-page guard defends against edge cases (e.g., a cached bundle with the flag on
served after server-side disablement).

### 5.9 Error states

- Network error on any mutation: `toast.error(err.response?.data?.detail ?? "Request failed")`.
- All mutations show a loading spinner on their submit button (standard shadcn/ui
  `<Button disabled={isPending}>`).
- If session load fails (e.g., session expired mid-shift): toast + transition to
  `no_session`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

The frontend contains zero `dev_mode` branches. All money paths (tender, refund,
void) call the same POS-012 wrappers regardless of environment. The backend POS
service layer (POS-006/007/008) handles dev/prod parity internally.

The receipt iframe renders the same HTML from the backend in both environments; the
PDF open-in-new-tab path works identically.

### 7.2 Idempotency

The `TenderModal` generates its idempotency key (`crypto.randomUUID()`) once when
the modal opens and stores it in `useState`. Clicking "Pay" twice in rapid
succession (or a network retry) sends the same `idempotency_key` to
`POST /ui/pos/sessions/{id}/tender`. The backend (POS-006) rejects the duplicate
via conditional write and returns the existing transaction, which the UI treats as
a success. The modal closes and the receipt is shown.

### 7.3 CSRF

All POST/DELETE mutations go through `frontend/src/api/client.ts:178-182` (verified)
which attaches the `X-CSRF-Token` header from the `ui_csrf` cookie automatically.
The backend reads this via `S.ui_csrf_header_name` = `"x-csrf-token"` (verified:
`app/core/settings.py:101`) and enforces it in `app/services/sessions.py:427-435`
(verified) for all non-GET `require_ui_session` cookie-auth requests.

### 7.4 Role security

The frontend role gate (`canAccessGeneralAdminControls`) is defence-in-depth only.
The authoritative gate is the backend:

- Register config endpoints: `require_admin_or_root_csrf` (POS-011 §4.2; verified:
  `require_admin_or_root_csrf` exists at `app/auth/policy.py:100-104`).
- Cashier endpoints: `require_ui_session` + `session["user_sub"] == session_row.cashier_sub`
  ownership check (POS-011 §4.2). A USER-role cashier with their own open session
  can tender; they cannot open a session without the register existing (admin creates
  registers), and cannot access another cashier's session.

### 7.5 Payment method exposure

Card payment methods listed in the Tender modal come from
`GET /ui/billing/payment-methods` — the same endpoint used by the existing
checkout flow. The response contains only the last-4 digits and brand; no full
card numbers are ever surfaced.

## 10. Open Questions / Assumptions

1. **Assumption: POS-012 TypeScript types follow exactly the Pydantic shapes in
   POS-002.** `RegisterSession.status` is assumed to be `"open" | "closed"` (not
   `"opening"` or other). If POS-012 changes field names (e.g., `session_status`
   instead of `status`), component destructuring must be updated.

2. **Assumption: `getReceipt(txnId)` returns an HTML string** (Content-Type
   `text/html`) in dev mode and a PDF binary in prod. `ReceiptPreview.tsx` must
   inspect the response Content-Type header to decide between iframe and new-tab
   rendering. If the backend always returns HTML (even in prod), the PDF branch
   is dead code that can be removed.

3. **Assumption: the `pos.ts` endpoint wrapper uses the same `api` axios instance
   as `cart.ts`** (`frontend/src/api/client.ts:1`) which attaches CSRF and handles
   401→logout. If POS-012 creates a separate axios instance, the CSRF header may
   not be sent automatically — this would be a POS-012 bug to fix before POS-013
   integration.

4. **Assumption: `canAccessGeneralAdminControls` is the correct role gate for
   cashiers.** The ticket describes "admin/cashier" role but the existing role enum
   only has `USER | ADMIN | ROOT` (confirmed in `app/auth/roles.py`). There is no
   dedicated CASHIER role. The assumption is that the platform operator grants ADMIN
   role to cashiers and uses the general-admin scope. If a future `CASHIER` role or
   a scoped admin `"pos_cashier"` scope is introduced, `adminCapabilities.ts` and
   the Sidebar filter must be updated.

5. **Assumption: `PosTransaction.tenders` is an array of `Tender` objects already
   embedded in the `PosTransactionOut` response** (not a separate endpoint call).
   If the backend returns tender details only from a separate
   `GET /ui/pos/txns/{id}/tenders` endpoint, the `ReceiptPreview` and `TenderModal`
   success handler must be updated to fetch that endpoint separately.

6. **Assumption: the receipt HTML returned by `getReceipt` is self-contained
   (inline CSS, no external fonts/images)** so it renders correctly inside
   `<iframe srcDoc>`. If the receipt HTML references relative paths, the iframe
   needs `src` with a blob URL instead of `srcDoc`.

7. **Open question: should the POS terminal route be `/pos` or `/pos/terminal`?**
   If multiple POS sub-pages are anticipated (e.g., a register config page at
   `/pos/registers`), the terminal page should be at `/pos/terminal` and a POS
   index page at `/pos`. This spec assumes a single route `/pos` for simplicity;
   if the register config UI is needed as a separate page it would be `/pos` (config)
   and `/pos/terminal` (cashier view). This decision should be confirmed before
   implementation.

8. **Open question: barcode scanner hardware integration.** The scan input accepts
   keyboard wedge barcode scanners (USB HID, presents as keyboard). If a dedicated
   Web Serial / Web HID API integration is required for non-wedge scanners, that is
   out of scope for POS-013 and would be a separate ticket.
