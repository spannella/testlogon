# PRD-009 — Bundle/kit composition service

**Type:** Feature | **Priority:** P0 | **Estimate:** 5 days
**Milestone:** 4 — Bundles / Kits & Associations

---

## 1. Summary & Goal

PRD-009 creates `app/services/product_bundles.py`, the pure service layer that implements bundle and kit product composition. The service distinguishes two subtypes:

- **Bundle**: a product with a fixed `price_cents` override. The bundle price is what the customer pays, regardless of the sum of component prices. Analogous to OFBiz ProductAssoc type=PRODUCT_COMPONENT with a fixed ProductPrice override.
- **Kit**: a product whose price equals the sum of its component prices each multiplied by the component quantity. No price override is stored — price is always computed at read-time.

Key responsibilities:

1. **Declare product type** as `"bundle"` or `"kit"` by writing a `TYPE` marker row on `T.product_depth` (same pattern as PRD-007's `set_product_type`).
2. **Manage components** via `set_components` (idempotent full-replace), `add_component`, and `remove_component`: each component row is a `COMP#{component_item_id}` SK on `PK=ITEM#{bundle_item_id}`, storing quantity and display sequence.
3. **List components** via `list_components(bundle_item_id)` — a single SK-prefix query, no scan.
4. **Expand a bundle** via `expand_bundle(bundle_item_id, qty)` — returns a flat list of `BundleComponentLine` dicts, each with a resolved `component_item_id`, `component_name`, `sku`, `quantity` (component qty × parent qty), and `unit_price_cents`. This is the cart integration seam.
5. **Compute bundle price** via `compute_bundle_price(bundle_item_id)` — for kits this is `Σ(component.price_cents × component.quantity)` over the expanded lines; for bundles it returns the stored `price_cents` override on the scalar item.
6. **Reject circular references** via DFS cycle detection before any component write.
7. **Protect the standalone path** — with `PRODUCT_DEPTH_ENABLED` off every existing shop/cart/billing path is byte-for-byte unchanged.

No router endpoints ship in this ticket — those are PRD-011.

```python
T.product_depth.query(
    KeyConditionExpression=Key("PK").eq(f"ITEM#{bundle_item_id}") &
                           Key("SK").begins_with("COMP#"),
    ScanIndexForward=True,     # ascending sequence_num if DDB sorts by SK
```

Because `sequence_num` is stored as a regular attribute (not the SK), results are sorted by `component_item_id` lexicographically (via the SK). The caller optionally sorts in Python by `sequence_num` after fetch — no `attr_types` issue arises because `sequence_num` is never a GSI key.

### 4.5 `set_components`

```python
def set_components(
    bundle_item_id: str,
    components: List[Dict[str, Any]],   # [{"component_item_id": str, "quantity": int, "sequence_num": int}, ...]
    user_sub: str,
) -> List[Dict[str, Any]]:
    """Idempotent full-replace of all components.

    1. _require_enabled()
    2. Assert bundle item exists and has product_type in ("bundle", "kit").
    3. For each incoming component: assert item exists, validate no cycle (full DFS
       over the incoming graph), validate depth.
    4. Fetch current component rows (list_components).
    5. Using a DynamoDB batch write:
       a. Delete rows for component_item_ids present in current but absent in new.
       b. Put rows for every component in new (upsert).
    6. Return the new component list as projected dicts.

    This operation is atomic at the application level but not a DDB transaction.
    Partial failure is possible — callers should treat a non-200 response as requiring
    a re-submit of the full list.
    """
```

The `_depth` parameter is internal (not exposed via the API). External callers always call with the default `_depth=0`.

### 4.8 `compute_bundle_price`

```python
def compute_bundle_price(
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Bundle vs. Kit distinction

**Bundle** (`product_type="bundle"`): The scalar item's `price_cents` on `T.catalog` is the authoritative price. The owner controls this via the standard `PATCH /ui/catalog/items/{id}` endpoint (already implemented). `compute_bundle_price` for a bundle simply returns `item["price_cents"]`. Components are still listed and expanded (for stock reservation), but their individual prices do not affect the bundle price.

**Kit** (`product_type="kit"`): The scalar item's `price_cents` is ignored at checkout. `compute_bundle_price` calls `expand_bundle(bundle_item_id, qty=1)` and sums `line.unit_price_cents * line.quantity` over all returned lines. The kit price is dynamic — if a component's catalog price changes, the kit price changes automatically on the next call. No denormalized kit price is stored.

### 5.2 Cycle detection

Before any component write, `cycle_check(bundle_item_id, candidate_component_item_id)` performs a DFS starting from `candidate_component_item_id`:

```
visited = set()
stack = [candidate_component_item_id]
while stack:
    node = stack.pop()
    if node == bundle_item_id:
        raise HTTPException(422, "Circular bundle reference detected")
    if node in visited:
        continue
    visited.add(node)
    for child in list_components(node):
        stack.append(child["component_item_id"])
```

The DFS is bounded by `S.product_depth_max_bundle_depth` — if the stack depth exceeds the limit, the check raises 422. This prevents a malicious caller from constructing a very deep graph to exhaust memory during expansion.

The check is called both in `add_component` and in `set_components` (per-component before any write).

### 5.3 Depth bounding

`expand_bundle` tracks recursion depth via the internal `_depth` counter:

```python
if _depth >= S.product_depth_max_bundle_depth:
    raise HTTPException(
        status_code=422,
        detail=f"Bundle nesting depth exceeds maximum ({S.product_depth_max_bundle_depth})"
    )
```

The default limit of 3 allows: bundle → sub-bundle → leaf item (two levels of nesting). Deeper graphs should be flattened by the owner.

### 5.4 Component SKU derivation

When a component is a scalar catalog item (no TYPE row, or TYPE row with `product_type="standalone"`), its SKU for inventory reservation is `f"catalog:{component_item_id}"` — the same format used by `add_catalog_item` at `app/services/shoppingcart.py:391` — VERIFIED.

When a component is itself a variant (TYPE row with `product_type="variant"`), the caller must have already resolved the specific variant SKU before calling `expand_bundle` — `expand_bundle` does not perform variant selection. In this case `expand_bundle` returns the component's catalog-sku and documents that the caller must substitute with the selected variant SKU before calling `reserve`.

When a component is another bundle/kit, `expand_bundle` recurses and returns the flat leaf lines (no bundle-of-bundle line is emitted).

### 5.5 Price for bundle expansion lines

`expand_bundle` calls `_find_item_by_id(component_item_id)` to read `price_cents` and `name` from `T.catalog`. If the component item no longer exists in the catalog, `expand_bundle` raises 404 ("Component item not found: {component_item_id}"). This prevents silently expanding a bundle with deleted components.

### 5.6 `set_components` atomicity

`set_components` performs a batch of DDB operations:
1. Fetch current components.
2. For items to delete: call `T.product_depth.delete_item` per row.
3. For items to upsert: call `T.product_depth.put_item` per row.

This is not a DDB transaction (no `transact_write`). In the event of a partial failure (e.g., crash mid-batch), the bundle is in an inconsistent state. The endpoint should be idempotent: a retry of the same `set_components` call produces the same final state. Callers should treat any non-200 response as requiring a full retry.

### 5.7 Bundle with zero components

A bundle or kit with zero components is valid (the owner may still be building it). `compute_bundle_price` for a kit with zero components returns 0. `expand_bundle` for an empty bundle/kit returns `[]`. Adding an empty bundle to a cart produces zero reservation calls. This is intentional — cart validation is the cart service's responsibility.

### 5.8 Component max count

A practical cap of `S.product_depth_max_bundle_components` (env `PRODUCT_DEPTH_MAX_BUNDLE_COMPONENTS`, default `50`) is enforced in `add_component` and `set_components`:

```python
current = list_components(bundle_item_id)
if len(current) >= S.product_depth_max_bundle_components:
    raise HTTPException(status_code=422, detail="Component limit reached")
```

This prevents a pathological bundle from generating a fan-out that exhausts the DDB read budget during expansion.

### 5.9 Self-referential component

A bundle with `bundle_item_id == component_item_id` is a degenerate cycle. The cycle check in §5.2 will catch this immediately (the starting node equals `bundle_item_id`), raising 422 before any write.

### 5.10 Component item must exist

`add_component` validates that the component item exists on `T.catalog` via `_find_item_by_id`. Items soft-deleted (if a soft-delete mechanism is ever added) or absent return 404. This prevents phantom component references.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

All DDB operations in `product_bundles.py` use `T.product_depth` and `T.catalog`, which resolve to local DynamoDB Local (`DDB_ENDPOINT_URL=http://localhost:8001`) or real DynamoDB in prod. There is no `S.dev_mode` branch anywhere in this service. Behavior is identical in both environments — same table, same SK-prefix query, same conditional writes. This follows the SECOPS-007 principle.

### Idempotency

- `add_component`: the component row key `PK=ITEM#{bundle_item_id}`, `SK=COMP#{component_item_id}` is deterministic. An unconditional `put_item` (upsert) is used — re-submitting the same component with different quantity is a last-write-wins update, not a duplicate. This is intentional: quantity updates should overwrite.
- `set_components`: the entire component set is replaced idempotently — submitting the same list twice produces the same state.
- `set_bundle_type`: last-write-wins `put_item` on the TYPE row (same as PRD-007 `set_product_type`). Re-calling with the same type updates only `updated_at`.
- `remove_component`: calling `remove_component` on an already-removed component returns 404. The router (PRD-011) should map this to a user-visible "Component not found" message, not a server error.

### Access control

Every public write function accepts `user_sub` and must be called from an endpoint that has already run `_require_category_owner(category_id, user_sub)` at `app/routers/catalog.py:247` — VERIFIED. The service layer trusts `user_sub` and stores it as `creator_id` on component rows. Ownership of a bundle is inherited from the bundle item's category ownership. Catalog router endpoints use `require_ui_session` from `app/services/sessions.py:330` — VERIFIED (not `app/auth/deps.py`).

Read-only functions (`list_components`, `expand_bundle`, `compute_bundle_price`) perform no ownership checks — consistent with the existing read-only catalog endpoints.

### Cycle-detection security

The cycle-check DFS traverses the existing component graph, which could be adversarially deep. The depth bound `S.product_depth_max_bundle_depth` limits the number of recursion steps in the DFS to `max_depth × max_components` nodes in the worst case. With defaults (depth=3, components=50), this is at most 150 DDB reads for a single cycle check — a bounded fan-out.

## 8. Backward Compatibility & Migration

### With `PRODUCT_DEPTH_ENABLED=false` (default)

- `product_bundles.py` functions always raise HTTP 404 via `_require_enabled()`.
- Zero reads or writes to `T.product_depth`.
- `T.catalog` is untouched — no new reads or writes.
- `_catalog_item_out` at `app/routers/catalog.py:107` continues to return `CatalogItemOut` with `product_type=None`, `bundle_component_count=None` — identical to today.
- `app/services/shoppingcart.py` is not modified.
- `app/services/inventory.py` is not modified.
- `app/services/billing_shared.py` is not modified.

### Existing scalar catalog items

Items with no TYPE row on `T.product_depth` are `standalone` by convention. `list_components` returns `[]`, `compute_bundle_price` raises 422 ("Item is not a bundle or kit"), and `expand_bundle` raises 422. The router (PRD-011) gates these endpoints behind a check for bundle/kit type.

### Enabling the flag on a live system

`product_depth` is a new table created by PRD-002 with no existing data. Enabling `PRODUCT_DEPTH_ENABLED=true` on a live system with existing catalog items is safe. No existing item has a TYPE row or COMP# rows, so all items remain `standalone` and all bundle endpoints return safe empty results or 422. No backfill or migration is required.

### Price staleness for kits

Kit prices are computed at call time from current catalog prices. There is no denormalized kit price on the DDB item. If a component's price changes, `compute_bundle_price` reflects the new price on the next call. This is intentional and differs from the variant `effective_price_cents` snapshot (PRD-007 §8). The cart-integration caller should call `compute_bundle_price` at add-to-cart time and pass the result into `add_item`.

## 10. Open Questions / Assumptions

**A1. `set_product_type` shared vs. duplicated.** This spec assumes PRD-007 ships first and provides `set_product_type` (or an extracted `catalog_helpers.set_product_type`). If PRD-009 ships before PRD-007, it inlines the TYPE write and later de-duplicates. Assumption: PRD-007 is a declared dependency and ships first.

**A2. Bundle price ownership.** For bundles (fixed-price override), the "correct" price is the scalar item's `price_cents` on `T.catalog`. This means the owner uses the standard `PATCH /ui/catalog/items/{id}` endpoint to set the bundle price — no new "set bundle price" endpoint is needed. This assumes the scalar item's price is always the authoritative bundle price. If an independent "bundle price override" field is desired (separate from the displayed catalog price), a `BUNDLE_PRICE#{bundle_item_id}` row would be needed; current assumption: scalar `price_cents` is the override.

**A3. Nested bundle expansion line shape.** When a component is itself a bundle/kit, `expand_bundle` recurses and returns flat leaf lines — no intermediate bundle-summary line. If the storefront needs to display sub-bundle grouping (e.g., "Sub-bundle X: [A, B, C]"), a tree-shaped response would be needed instead. Current assumption: flat expansion is sufficient for cart reservation (OFB-004 integration point).

**A4. Kit component price snapshot vs. live.** Kit prices are dynamic (re-computed from current catalog prices at call time). If a component price changes between the customer viewing a kit and adding it to cart, the price at add-to-cart time will differ from the displayed price. Assumption: this is acceptable (same as any catalog price change); no "price lock" mechanism is designed here.

**A5. Variant components in bundles.** If a bundle contains a virtual product (product_type="variant"), `expand_bundle` returns the virtual item's catalog SKU and price, not a specific variant. The caller (cart integration) must resolve variant selection before calling `reserve`. Assumption: PRD-009 does not handle variant selection during expansion — that is the responsibility of the cart or a future "configurable bundle" ticket.

**A6. Currency homogeneity.** If components are in different currencies, `compute_bundle_price` for a kit would produce a meaningless sum. Assumption: all components must share the bundle's currency; `add_component` validates that `component.currency == bundle.currency` (reading from `T.catalog`). If currencies differ, raise 422 ("Currency mismatch: component currency does not match bundle currency").

**A7. Soft-delete for components.** `remove_component` performs a hard delete. There is no soft-delete mechanism. If audit trails of removed components are needed, the caller should emit an audit event via `app/services/alerts.audit_event` before calling `remove_component`. Assumption: hard delete is acceptable; no audit trail is built into the service layer.

**A8. DynamoDB transaction for `set_components`.** The spec uses a non-transactional batch of puts/deletes. A `transact_write` could make this atomic at the DDB layer but has a 100-item limit and adds per-call latency. Assumption: non-transactional batch + idempotent retry is acceptable given the bounded component count (max 50).
