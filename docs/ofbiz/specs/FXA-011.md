# FXA-011 — Asset disposal with proceeds via existing refund path

## 1. Summary & Goal

FXA-011 extends `dispose_asset` (established by FXA-005, exposed by FXA-007) with two new responsibilities:

1. **Closing GL journal.** When an asset is disposed, post a balanced three-line (or two-line for zero-gain/loss) closing journal entry to `T.gl_journal` via `gl_posting.post_journal_entry` (OFB-014): Debit Accumulated Depreciation, Credit Fixed Asset Cost, and Credit/Debit Gain/Loss on Disposal for the plug amount. This entry removes the asset and its contra account from the balance sheet and books any gain or loss in the income statement.

2. **Cash-proceeds money-out via existing refund path.** When the disposal request includes a `proceeds_payment_intent_id`, the function routes the money-out through `refund_payment` (`app/routers/billing.py:1287`) — the same Stripe-refund path used everywhere else in the system. No new payment mechanism is introduced. The single-entry billing ledger and provider attribution (FIN-013) stay correct because the call goes through `new_ledger_entry` with `provider="stripe"` inside `refund_payment`.

Both behaviors are idempotent: a deterministic `disposal_journal_id = sha256(f"disposal:{asset_id}")[:32]` prevents double-posting the GL journal, and re-disposing an already-`disposed` asset returns 409 (not a silent no-op) because disposal triggers financial flows. Remaining scheduled depreciation periods are bulk-cancelled on disposal so the FXA-010 poster never picks them up again.

Everything is additive. With `FIXED_ASSETS_ENABLED=false` all code paths are unreachable and all existing shop / cart / orders / billing / inventory paths are byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 `dispose_asset` as established by FXA-005

`docs/ofbiz/specs/FXA-005.md:412–433` defines the current `dispose_asset` pseudocode. At the end of FXA-005/FXA-007, `dispose_asset`:

- Verifies the asset exists and belongs to the caller (`owner_sub` check).
- Guards against double-disposal with `ConditionExpression="#status <> :disposed_val"` on the `update_item` call.
- Sets `status="disposed"`, `disposed_at=now_ts()`, optionally `disposal_reason`.
- Emits `_audit("fixed_asset.disposed", ...)` (best-effort).
- Returns the updated `FixedAssetOut`.

Critically, FXA-005 section 5.6 (`docs/ofbiz/specs/FXA-005.md:436`) explicitly defers proceeds handling: *"Proceeds money-out is NOT handled by this service. If `req.proceeds_payment_intent_id` is set, the router (FXA-007) calls `refund_payment` / `settle_or_reverse_ledger` after `dispose_asset` returns successfully."* FXA-011 owns those deferred steps — both the proceeds routing and the closing GL journal — and places them **inside the service** (not the router) to keep the money/GL logic in one place, away from HTTP concerns.

### 2.5 Depreciation schedule cancellation requirement

`docs/ofbiz/specs/FXA-009.md:54` notes that `schedule_status` has three values: `"scheduled"`, `"posted"`, and `"cancelled"`. The FIXED_ASSETS_TICKETS.md acceptance criteria (`:228`) state: *"its remaining scheduled depreciation periods are marked cancelled and never post."* The FXA-010 poster (GSI_DUE query documented at `docs/ofbiz/specs/FXA-009.md:520–526`) queries `GSI_DUE` with `schedule_status="scheduled"` — rows marked `"cancelled"` are invisible to the poster and will never be processed.

### 2.6 GL closing journal math (accounting)

A straight-line asset disposal follows this three-way journal entry:

```
Dr Accumulated Depreciation  accumulated_depreciation_cents
Dr/Cr Gain/Loss on Disposal  |NBV - proceeds|  (plug amount; sign depends on gain vs. loss)
   Cr Fixed Asset Cost        acquisition_cost_cents
```

Where `NBV = acquisition_cost_cents - accumulated_depreciation_cents`. The plug:
- `proceeds_amount_cents > NBV` → **gain** → Credit Gain/Loss account
- `proceeds_amount_cents < NBV` → **loss** → Debit Gain/Loss account
- `proceeds_amount_cents == NBV` → no plug needed (two-line journal balances without it)
- No proceeds and `accumulated_depreciation_cents < acquisition_cost_cents` → **loss = NBV** → Debit Gain/Loss account

This entry always satisfies Σdebit == Σcredit (verified below in §5.1). The `gl_asset_account_id` (account `FA-ASSET`, seeded by FXA-008, `docs/ofbiz/specs/FXA-008.md:110`), `gl_accum_depr_account_id` (`FA-ACCUM-DEPR`, `docs/ofbiz/specs/FXA-008.md:111`), and `gl_gain_loss_account_id` (`FA-GAIN-LOSS`, `docs/ofbiz/specs/FXA-008.md:113`) are read from the asset row, stored there by `create_asset` (FXA-008 extension).

## 3. Data Model

FXA-011 introduces **no new DynamoDB tables or GSIs**. It writes to tables already created by FXA-003 and OFB-002.

### 3.1 `fixed_assets` table — new attributes written on disposal

FXA-011 extends the `dispose_asset` `update_item` call to write two new attributes:

| Attribute | DDB Type | Written by FXA-011 | Notes |
|---|---|---|---|
| `disposal_journal_id` | S | `sha256(corr)[:32]` | Idempotency key for the closing journal; stored for audit |
| `disposal_proceeds_cents` | N | `proceeds_amount_cents` or `0` | Denormalized proceeds for reporting; `0` when no payment intent |

These are additive attributes on the existing `ASSET#{asset_id} / META` row. No GSI or `attr_types` change is required. The attributes are absent on pre-FXA-011 rows and are surfaced as `Optional[int]` / `Optional[str]` on `FixedAssetOut` (see §4.3).

### 3.2 `fixed_asset_schedule` table — bulk cancellation of remaining periods

On disposal, FXA-011 bulk-cancels all `schedule_status="scheduled"` rows for the asset. This is a scan-and-update pattern:

```
T.fixed_asset_schedule.query(
    KeyConditionExpression=Key("pk").eq(_asset_pk(asset_id))
)
→ for each item where schedule_status == "scheduled":
    T.fixed_asset_schedule.update_item(
        Key={"pk": pk, "sk": item["sk"]},
        UpdateExpression="SET schedule_status = :c",
        ExpressionAttributeValues={":c": "cancelled"},
        ConditionExpression="schedule_status = :s",
        ExpressionAttributeValues includes {":s": "scheduled"},
    )
```

The condition guard (`schedule_status = :s`) ensures the update is a no-op if the period was posted concurrently. The full `query` iterates `LastEvaluatedKey` to handle assets with many periods (per the CLAUDE.md "FilterExpression doesn't reduce page size" gotcha — a `Query` without filter uses `Limit` and may not return all rows in one call).

### 3.3 `gl_journal` table — disposal closing journal rows

FXA-011 writes to `T.gl_journal` indirectly via `gl_posting.post_journal_entry`. The journal schema is as specified by OFB-014 (`docs/ofbiz/specs/FXA-009.md:156–165`):

| PK | SK | Key attributes |
|---|---|---|
| `JE#{disposal_journal_id}` | `META` | `journal_id`, `gl_date` (YYYY-MM-DD), `posted_at` (N), `source_type="disposal"`, `source_entity_id=asset_id`, `memo` |
| `JE#{disposal_journal_id}` | `LINE#1` | Dr Accumulated Depreciation: `debit_cents=accumulated_depreciation_cents`, `credit_cents=0` |
| `JE#{disposal_journal_id}` | `LINE#2` | Cr Fixed Asset Cost: `debit_cents=0`, `credit_cents=acquisition_cost_cents` |
| `JE#{disposal_journal_id}` | `LINE#3` | Gain/Loss plug (present only when `|proceeds - NBV| > 0`): see §5.1 |

The `gl_date` is `ledger_date_for_ts(disposed_at)` — reusing `app/services/billing_shared.py:10–13` so the disposal entry slots into the trial balance day bucket matching the disposal timestamp, consistent with FXA-009's use of the same helper.

### 3.4 `billing` table — refund ledger entry (via `refund_payment`)

When `proceeds_payment_intent_id` is supplied, `refund_payment` writes one new `LEDGER#ts#entry_id` row to `T.billing` (PK = `USER#{owner_sub}`) and reverses the original `LEDGER` row for the payment intent. These writes are entirely internal to `refund_payment`; FXA-011 does not write to `T.billing` directly.

### 3.5 `scripts/local-ddb-init.py` — no changes required

All tables (`fixed_assets`, `fixed_asset_schedule`, `gl_journal`, `billing`) already have their `TableDef` entries from earlier tickets (FXA-003, OFB-002). No new `attr_types` additions are needed by FXA-011.

## 4. API / Service Design

### 4.1 Extended `dispose_asset` function signature (unchanged from FXA-005)

```python
# app/services/fixed_assets.py
def dispose_asset(
    owner_sub: str,
    asset_id: str,
    req: FixedAssetDisposeIn,
) -> FixedAssetOut:
    """Dispose a fixed asset, post the closing GL journal, cancel remaining
    schedule periods, and optionally route cash proceeds through refund_payment.

    Idempotent at the status level: if the asset is already disposed, raises
    HTTPException(409, "already_disposed") — disposal triggers financial flows
    and must not be double-executed.

    Raises:
        HTTPException(503): FIXED_ASSETS_ENABLED is false.
        HTTPException(404): asset_id not found or wrong owner_sub.
        HTTPException(409): asset is already disposed.
        HTTPException(422): GL account IDs not resolved (gl_asset_account_id,
                            gl_accum_depr_account_id, or gl_gain_loss_account_id
                            is None/empty on the asset row).
        HTTPException(404): proceeds_payment_intent_id not found in T.billing
                            (raised inside refund_payment).
        ValueError: journal lines do not balance (raised inside gl_posting,
                    indicates a programming error — should never occur in prod).
    """
```

The signature is identical to the FXA-005 / FXA-007 contract; no caller change is needed.

### 4.2 New internal helper: `_post_disposal_journal`

```python
def _post_disposal_journal(
    asset: Dict[str, Any],
    proceeds_cents: int,
    disposed_at: int,
    disposal_journal_id: str,
) -> None:
    """Build and post the three-way disposal closing GL journal.

    Lines (always Σdr == Σcr):
      Dr Accumulated Depreciation  accumulated_depreciation_cents
      Dr/Cr Gain/Loss on Disposal  |proceeds - NBV|  (credit if gain; debit if loss)

Passing `ctx=None` raises `AttributeError` on `.get()`. The minimal dict `{"user_sub": owner_sub}` satisfies all accesses: `ctx.get("actor_sub")` returns `None` (no actor override), `ctx["user_sub"]` returns `owner_sub`, and since `target_user_sub` (the `user_sub=None` kwarg) is falsy the admin-impersonation branch is skipped — `effective_sub == owner_sub` and `admin_tags == {}`. This is consistent with the "no parallel billing mechanism" constraint (`docs/ofbiz/specs/FXA-001.md:11`).

## 5. Detailed Behavior & Edge Cases

### 5.1 Disposal journal balance proof

The GL disposal journal is **non-cash only** — consistent with FXA-009's depreciation design (`docs/ofbiz/specs/FXA-001.md:10`). Proceeds are handled entirely by `refund_payment` in the billing ledger; including them as a GL line would double-count against billing-ledger-derived trial balance entries. The journal de-recognizes the asset at cost and books NBV as gain/loss:

**Two-line balance (fully depreciated, NBV = 0):**

| Line | Account | Debit | Credit |
|---|---|---|---|
| 1 | Accumulated Depreciation | `C` | 0 |
| 2 | Fixed Asset Cost | 0 | `C` |

Σdr = `C`, Σcr = `C`. Balanced.

**Three-line with loss (partially depreciated, no proceeds):**

| Line | Account | Debit | Credit |
|---|---|---|---|
| 1 | Accumulated Depreciation | `D` | 0 |
| 2 | Gain/Loss on Disposal | `NBV` = `C - D` | 0 |
| 3 | Fixed Asset Cost | 0 | `C` |

Σdr = `D + (C - D)` = `C`, Σcr = `C`. Balanced.

**When proceeds exist**, the gain/loss computation uses `proceeds_amount_cents` vs NBV for the P&L recognition, but the proceeds cash does not appear as a GL line — that is handled by the billing ledger via `refund_payment`. The gain/loss line still uses `NBV - proceeds` (negative = gain, positive = loss):

| Scenario | Gain/Loss line |
|---|---|
| `P > NBV` (gain) | Cr Gain/Loss `P - NBV` |
| `P < NBV` (loss) | Dr Gain/Loss `NBV - P` |
| `P == NBV` (breakeven) | No line 3; two-line journal balances as Dr Accum-Depr / Cr Asset |
| `P == 0`, `D == C` (fully depr, written off) | No line 3; two-line journal |
| `P == 0`, `D < C` (early write-off) | Dr Gain/Loss `NBV` |

The GL journal function validates Σdr == Σcr before writing — any coding error here raises `ValueError` immediately and nothing is persisted.

### 5.2 Full `dispose_asset` pseudocode (FXA-011 extension)

```
1.  _require_enabled()                        # 503 if flag off
2.  item = T.fixed_assets.get_item(Key={"pk": _asset_pk(asset_id), "sk": "META"}).get("Item")
    if not item: raise HTTPException(404)
    if item["owner_sub"] != owner_sub: raise HTTPException(404)  # ownership oracle protection
3.  if item["status"] == "disposed": raise HTTPException(409, "already_disposed")
4.  Validate GL IDs exist:
    for field in ("gl_asset_account_id", "gl_accum_depr_account_id", "gl_gain_loss_account_id"):
        if not item.get(field): raise HTTPException(422, f"GL account not resolved: {field}")
5.  ts = now_ts()
6.  corr = req.correlation_id or f"disposal:{asset_id}"
    disposal_journal_id = hashlib.sha256(corr.encode()).hexdigest()[:32]
7.  proceeds = req.proceeds_amount_cents or 0
8.  # --- Post closing GL journal (idempotent) ---
    _post_disposal_journal(item, proceeds, ts, disposal_journal_id)
9.  # --- Bulk-cancel remaining schedule periods ---
    _cancel_remaining_periods(asset_id)
10. # --- Route cash proceeds through billing (only if payment intent supplied) ---
    if req.proceeds_payment_intent_id:
        _route_disposal_proceeds(
            owner_sub=owner_sub,
            payment_intent_id=req.proceeds_payment_intent_id,
            amount_cents=proceeds,
            asset_id=asset_id,
        )
11. # --- Flip asset status (conditional update = double-disposal guard) ---
    T.fixed_assets.update_item(
        Key={"pk": _asset_pk(asset_id), "sk": "META"},
        UpdateExpression=(
            "SET #status = :s, disposed_at = :ts, updated_at = :ts,"
            " disposal_journal_id = :jid, disposal_proceeds_cents = :p"
            + (", disposal_reason = :dr" if req.disposal_reason else "")
        ),
        ExpressionAttributeNames={"#status": "status"},
        ExpressionAttributeValues={
            ":s": "disposed", ":ts": ts, ":jid": disposal_journal_id,
            ":p": proceeds,
            **({":dr": req.disposal_reason} if req.disposal_reason else {}),
            ":not_disposed": "disposed",
        },
        ConditionExpression="#status <> :not_disposed",
    )
12. updated_item = T.fixed_assets.get_item(Key={"pk": _asset_pk(asset_id), "sk": "META"})["Item"]
13. _audit("fixed_asset.disposed", owner_sub,
           asset_id=asset_id, disposal_journal_id=disposal_journal_id,
           proceeds_amount_cents=proceeds,
           disposal_reason=req.disposal_reason, outcome="success")
14. return _item_to_out(updated_item)
```

**Ordering rationale:** Steps 8–10 run before step 11 (the status flip). This means:
- The GL journal and proceeds routing are attempted first.
- If `refund_payment` raises (e.g., payment intent not found → 404), the asset remains `active` and the caller can retry after fixing the payment intent reference.
- If the status flip (step 11) fails with `ConditionalCheckFailedException` (concurrent second request beat this one), the GL journal and proceeds route have already fired. This is safe because `_post_disposal_journal` is idempotent (deterministic `journal_id`, `attribute_not_exists` guard) and `refund_payment` operates on the Stripe payment intent (which can only be refunded once — Stripe enforces this). The final 409 to the losing concurrent request is correct behavior.

### 5.3 `_post_disposal_journal` pseudocode

```python
def _post_disposal_journal(
    asset: Dict[str, Any],
    proceeds_cents: int,
    disposed_at: int,
    disposal_journal_id: str,
) -> None:
    from app.services import gl_posting  # lazy import; patchable in tests

    C = int(asset["acquisition_cost_cents"])
    D = int(asset.get("accumulated_depreciation_cents", 0))
    NBV = C - D
    gain_loss = proceeds_cents - NBV  # positive = gain, negative = loss

    lines = [
        gl_posting.JournalLine(
            account_id=asset["gl_accum_depr_account_id"],
            debit_cents=D, credit_cents=0,
        ),
        gl_posting.JournalLine(
            account_id=asset["gl_asset_account_id"],
            debit_cents=0, credit_cents=C,
        ),
    ]
    if gain_loss > 0:  # gain: credit Gain/Loss
        lines.append(gl_posting.JournalLine(
            account_id=asset["gl_gain_loss_account_id"],
            debit_cents=0, credit_cents=gain_loss,
        ))
    elif gain_loss < 0:  # loss: debit Gain/Loss
        lines.append(gl_posting.JournalLine(
            account_id=asset["gl_gain_loss_account_id"],
            debit_cents=-gain_loss, credit_cents=0,
        ))
    # gain_loss == 0: two-line journal balances without a gain/loss entry

    from app.services.billing_shared import ledger_date_for_ts
    try:
        gl_posting.post_journal_entry(
            lines,
            journal_id=disposal_journal_id,
            source_type="disposal",
            source_entity_id=asset["asset_id"],
            memo=f"Asset disposal: {asset['name']} ({asset['asset_id']})",
            gl_date=ledger_date_for_ts(disposed_at),
        )
    except ClientError as exc:
        if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
            return  # already posted — idempotent replay
        raise
```

### 5.4 `_route_disposal_proceeds` pseudocode

```python
def _route_disposal_proceeds(
    owner_sub: str,
    payment_intent_id: str,
    amount_cents: int,
    asset_id: str,
) -> None:
    from app.routers.billing import refund_payment  # lazy import; avoids circular dep
    from app.models import StripeRefundReq

    refund_payment(
        body=StripeRefundReq(
            payment_intent_id=payment_intent_id,
            amount_cents=amount_cents,
            reason=f"Asset disposal proceeds: {asset_id}",
        ),
        req=None,
        ctx={"user_sub": owner_sub},   # required: _billing_write_user_context reads ctx["user_sub"]
        actor=None,
        user_sub=None,
    )
```

If `refund_payment` raises any exception (404 for missing payment intent, 400 for amount > original charge, Stripe SDK errors), it propagates directly from `dispose_asset` and the asset status is NOT flipped (step 11 has not run yet — see §5.2 ordering rationale). The caller receives the appropriate HTTP error and can fix the payment intent reference before retrying.

### 5.5 `_cancel_remaining_periods` pseudocode

```python
def _cancel_remaining_periods(asset_id: str) -> int:
    pk = _asset_pk(asset_id)
    cancelled = 0
    last_key = None
    while True:
        kwargs: Dict[str, Any] = {
            "KeyConditionExpression": Key("pk").eq(pk),
        }
        if last_key:
            kwargs["ExclusiveStartKey"] = last_key
        resp = T.fixed_asset_schedule.query(**kwargs)
        for row in resp.get("Items", []):
            if row.get("schedule_status") != "scheduled":
                continue
            try:
                T.fixed_asset_schedule.update_item(
                    Key={"pk": pk, "sk": row["sk"]},
                    UpdateExpression="SET schedule_status = :c",
                    ExpressionAttributeValues={":c": "cancelled", ":s": "scheduled"},
                    ConditionExpression="schedule_status = :s",
                )
                cancelled += 1
            except ClientError as exc:
                if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
                    pass  # posted concurrently — leave as posted
                else:
                    raise
        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break
    return cancelled
```

### 5.6 Edge cases

| Scenario | Behavior |
|---|---|
| Asset already `disposed` | Step 3 raises `HTTPException(409, "already_disposed")` before any GL/billing write |
| GL account IDs not resolved (FXA-008 not yet run) | Step 4 raises `HTTPException(422, "GL account not resolved: gl_asset_account_id")` — disposal blocked until seed runs |
| `proceeds_payment_intent_id` with no matching billing record | `refund_payment` raises `HTTPException(404, "Payment record not found")` at step 10; asset status NOT flipped |
| `proceeds_amount_cents > 0` without `proceeds_payment_intent_id` | `FixedAssetDisposeIn.proceeds_fields_consistent` validator raises 422 before service is called |
| Concurrent duplicate disposal requests | Whichever reaches step 11 first wins; the second gets `ConditionalCheckFailedException` → 409. The GL journal (step 8) is idempotent. The `refund_payment` call (step 10) may run twice on the same payment intent — Stripe rejects the second refund attempt; the exception propagates from the second request (which will also get 409 from step 11 anyway) |
| `accumulated_depreciation_cents == 0` (asset never depreciated) | Journal: Dr Accumulated Depr `0` not posted; Dr Gain/Loss `NBV`; Cr Fixed Asset `C`. The zero-debit line for Accumulated Depreciation is omitted from `lines` (only non-zero lines are added) |
| `accumulated_depreciation_cents == acquisition_cost_cents` (fully depreciated, NBV = 0, no proceeds) | Two-line journal: Dr Accumulated Depr `C`, Cr Fixed Asset `C`. No gain/loss line |
| `gl_gain_loss_account_id` is None but gain/loss is non-zero | Step 4 raises HTTPException(422) blocking disposal. If gain_loss == 0 this field is not used — but step 4 validates all three GL IDs unconditionally |
| Re-dispose after partial failure (GL posted, proceeds failed, status not flipped) | Retry is safe: GL journal is idempotent (catches `ConditionalCheckFailedException`), `refund_payment` will re-attempt (caller must fix PI reference if that was the error) |
| `useful_life_months` periods all already `posted` (fully depreciated asset) | `_cancel_remaining_periods` has no rows to cancel (query returns all `posted`). No-op, returns 0 |
| Asset with no schedule (generate_schedule never called) | `_cancel_remaining_periods` queries `T.fixed_asset_schedule` and gets zero rows. No-op. Disposal proceeds normally |

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

No `if S.dev_mode` branch anywhere in the extended `dispose_asset` or its helpers. Both environments:
- Use the same `T.fixed_assets` / `T.fixed_asset_schedule` DDB handles backed by DynamoDB Local in dev and real DynamoDB in prod.
- Call `gl_posting.post_journal_entry` (via lazy import) — that service's internal dev/prod handling is OFB-014's responsibility; this caller is indifferent.
- Call `refund_payment` — which already handles the Stripe mock (port 12111) in dev vs. real Stripe in prod via `app/core/settings.py` stripe config.

The `ledger_date_for_ts` function (`app/services/billing_shared.py:10–13`) is pure Python with no env-specific branches.

### 7.2 Idempotency contract

| Operation | Idempotency mechanism |
|---|---|
| GL disposal journal | Deterministic `disposal_journal_id = sha256(corr)[:32]`; OFB-014 `attribute_not_exists(pk)` guard catches `ConditionalCheckFailedException` as a silent no-op (§5.3) |
| Schedule cancellation | `ConditionExpression="schedule_status = :s"` on each row's update; concurrent post of the same period → leaves it `posted` |
| Asset status flip | `ConditionExpression="#status <> :not_disposed"` on the `update_item`; second request gets 409 |
| Proceeds routing | Not idempotent by design — `refund_payment` hits Stripe's API and Stripe enforces one-refund-per-intent. The 409 from the status flip prevents the second caller from reaching step 10 in the concurrent scenario |

**Re-dispose semantics:** Re-disposing an already-disposed asset is a 409, not a silent no-op. This is consistent with FXA-007's note (`docs/ofbiz/specs/FXA-007.md:359`): *"re-disposing an already-disposed asset returns 409 (not idempotent by design — disposal triggers financial flows that must not be double-executed)."*

### 7.3 Security

- **Ownership enforcement.** Step 2 checks `item["owner_sub"] == owner_sub` before any write. Mismatches return HTTP 404 (not 403) — same oracle-protection approach as `get_asset` (`docs/ofbiz/specs/FXA-005.md:499–501`).
- **Admin-only.** `require_admin_or_root_csrf` on the dispose endpoint (`app/auth/policy.py:100–106`) enforces ADMIN or ROOT role. Non-admin callers receive 403 before `dispose_asset` is reached.
- **CSRF protection.** Cookie-authenticated POST requests go through `enforce_cookie_csrf` inside `require_admin_or_root_csrf`. Bearer-token callers skip CSRF (consistent with the rest of the codebase per CLAUDE.md auth patterns).
- **No secrets in audit events.** The `disposal_journal_id` and `proceeds_amount_cents` emitted to `audit_event` are financial record metadata. The `payment_intent_id` is not emitted directly in the fixed-asset audit event (it is emitted inside `refund_payment`'s own audit call at `app/routers/billing.py:1332–1343`).
- **Stripe payment intent ownership.** `refund_payment` looks up the payment record in `T.billing` by `user_pk(user_id) / pay_sk(payment_intent_id)`. If the payment intent belongs to a different user, the lookup returns `None` → 404. This means an attacker supplying someone else's PI gets a 404, not a refund.

### 8.1 Additive only — no breaking changes

- `dispose_asset` signature is unchanged.
- `FixedAssetOut` gets two new optional fields (`disposal_journal_id`, `disposal_proceeds_cents`) that are absent on pre-FXA-011 rows and deserialize as `None` — no existing consumer breaks.

- No new routes, no new tables, no `scripts/local-ddb-init.py` changes.

### 8.2 Existing disposed assets

Assets disposed under FXA-005/FXA-007 (before FXA-011) lack `disposal_journal_id` and `disposal_proceeds_cents`. They remain `status="disposed"`. No GL closing journal was posted for them. This is acceptable — they are pre-feature records. If a retroactive closing journal is needed for pre-FXA-011 disposals, that is a separate one-off migration task outside this scope.

### 8.3 GL account dependency

If `FIXED_ASSETS_ENABLED=true` but FXA-008's `seed_gl_depreciation_accounts()` has not yet run, the asset's GL account ID fields will be `None`. Step 4 in `dispose_asset` catches this and raises HTTP 422. Disposal is blocked until the seed runs. This is a safe degradation — no partial write occurs.

## 10. Open Questions / Assumptions

1. **Assumption: GL journal does NOT include the cash proceeds leg.** The disposal closing journal is non-cash (same as the depreciation journal in FXA-009). The proceeds cash side is handled entirely by the billing ledger via `refund_payment`. This is consistent with the FXA-001 design note (`docs/ofbiz/specs/FXA-001.md:10`: "non-cash GL entry... does NOT call `new_ledger_entry` — no money moves"). The gain/loss recognized in the GL journal is the NBV write-off amount only; the actual proceeds versus NBV spread is visible by reconciling the GL journal against the billing ledger (OFB-016 scope). **Verify with finance reviewer before implementation.**

2. **Assumption: Single `FA-GAIN-LOSS` account for both gains and losses.** FXA-008 (`docs/ofbiz/specs/FXA-008.md:601`) notes the option of two separate accounts. This spec uses one bifurcated account. **Confirm with finance reviewer.**

3. ~~**Assumption: `refund_payment` can be called with `ctx=None, actor=None, user_sub=<str>`.**~~ **RESOLVED (verified):** `ctx=None` does NOT work — `_billing_write_user_context` (`app/routers/billing.py:594–595`) calls `ctx.get(...)` and `ctx["user_sub"]` unconditionally, raising `AttributeError`/`TypeError` on `None`. The correct call uses `ctx={"user_sub": owner_sub}` (pattern verified from `billing_dunning.py:192`). See §4.6 and §5.4 for the corrected pseudocode.

4. **Assumption: `accumulated_depreciation_cents = 0` on assets that were never depreciated.** The disposal journal omits the accumulated depreciation debit line when `D = 0` (or emits it with `debit_cents=0`). The `gl_posting.post_journal_entry` implementation must accept zero-amount lines, or the zero-debit line must be filtered out before calling it. This spec filters zero-amount lines from `lines` before passing to `post_journal_entry`.

5. **Assumption: `_cancel_remaining_periods` runs to completion before the asset status flip.** If the query/update loop for cancellations is slow (many periods), the asset may remain `active` longer than expected during disposal. This is acceptable — the status flip is the authoritative terminal gate, and the poster checks `schedule_status="scheduled"` before posting, so any period not yet cancelled will not post because the asset is `disposed` by the time step 11 completes.

6. **Assumption: `dispose_asset` for assets with no GL accounts (pre-FXA-008) raises 422.** The alternative is to post the journal without a gain/loss line (two-line only). This spec takes the stricter approach — require all four GL IDs. **Confirm with product: should disposal be allowed without the GL accounts?**

7. **Assumption: `disposal_journal_id` uses `req.correlation_id or f"disposal:{asset_id}"`.** If `req.correlation_id` is None on the first attempt and some other value on a retry, a different `disposal_journal_id` is generated, which would post a second journal entry. Callers should always pass the same `correlation_id` across retries. **This should be documented in the API reference for FXA-007.**
