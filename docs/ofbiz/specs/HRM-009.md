# HRM-009 — HR + payroll router (registered in app/main.py)

**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days
**Milestone:** 3 — Payroll & GL Hook (router layer)

## 1. Summary & Goal

HRM-009 creates `app/routers/hr.py`, the HTTP layer that stitches the HR service functions (HRM-004 through HRM-008) to the REST surface, and registers it in `app/main.py`. The router:

- Exposes position CRUD (`POST/GET /positions`, `GET /positions/{position_id}`, `PATCH /positions/{position_id}/status`) backed by `app.services.hr`.
- Exposes employment lifecycle (`POST/GET /employments`, `GET /employments/{employment_id}`, `POST /employments/{employment_id}/terminate`) backed by `app.services.hr`.
- Exposes payroll run lifecycle (`POST/GET /payroll`, `GET /payroll/{payroll_run_id}`, `GET /payroll/{payroll_run_id}/lines`, `POST /payroll/{payroll_run_id}/approve`, `POST /payroll/{payroll_run_id}/post`) backed by `app.services.hr_payroll`.
- Enforces admin/root-only access plus cookie-CSRF on every non-GET path.
- Returns HTTP 404 `{"code": "hr_disabled"}` for every `/ui/hr/*` route when `S.hr_enabled` is `False`; additionally returns 404 `{"code": "hr_payroll_disabled"}` for every `/ui/hr/payroll*` route when `S.hr_payroll_enabled` is `False`. No service code runs in either disabled path.
- Is registered in `app/main.py` immediately after the `contacts_router` include at `app/main.py:683`.

All existing billing, cart, orders, messaging, and subscription code is byte-for-byte unchanged when both flags are off (the default).

### 2.6 Route declaration order — static before dynamic

CLAUDE.md documents the "IMPORTANT: declare static segments before dynamic `/{...}` capture" gotcha. The `/schedules` routes in the audit exports router are declared before `/{export_id}` for the same reason (CLAUDE.md, "Scheduled audit export reports" section). HRM-009 applies this rule in two places:
- `/payroll` list/create must appear before `/payroll/{payroll_run_id}` get.
- `/payroll/{payroll_run_id}/lines`, `/payroll/{payroll_run_id}/approve`, `/payroll/{payroll_run_id}/post` all appear before any wildcard catch that might be added later.
- `/employments/{employment_id}/terminate` must be declared before any potential future route that would capture `/employments/{employment_id}/{sub}` generically — no conflict in the current design, but the ordering must be maintained.

### 2.7 CSRF enforcement

CLAUDE.md: "Cookie-auth non-GET requests require `x-csrf-token: <token>` header matching both the session's stored `csrf_token` and the `ui_csrf` cookie value. Bearer-auth requests skip CSRF." `enforce_cookie_csrf` at `app/auth/policy.py:71` handles this transparently — the router handler only needs `Depends(require_admin_or_root_csrf)` on non-GET endpoints.

### 2.8 Billing/ledger — no forking

HRM-009 exposes the `POST /payroll/{payroll_run_id}/post` endpoint which calls `hr_payroll.post_payroll_run`. ### 4.1 Router skeleton

```python

from app.auth.deps import AuthenticatedUser
from app.auth.policy import require_admin_or_root, require_admin_or_root_csrf
from app.core.settings import S
from app.models import (
    CreateEmploymentIn, CreatePayrollRunIn, CreatePositionIn,
    EmploymentOut, PayrollLineOut, PayrollRunOut, PositionOut,
    TerminateEmploymentIn, UpdatePositionStatusIn,
)
import app.services.hr as hr_svc
import app.services.hr_payroll as payroll_svc

router = APIRouter(prefix="/ui/hr", tags=["hr"])
```

The prefix `/ui/hr` places all endpoints under the standard `/ui/` namespace used by every other UI-session-gated feature. Tags `["hr"]` group the endpoints in Swagger UI.

### 4.2 Feature-flag guards

```python
def _require_hr() -> None:
    if not S.hr_enabled:
        raise HTTPException(status_code=404, detail={"code": "hr_disabled"})

def _require_payroll() -> None:
    _require_hr()
    if not S.hr_payroll_enabled:
        raise HTTPException(status_code=404, detail={"code": "hr_payroll_disabled"})
```

`_require_hr()` is called at the start of every position and employment endpoint handler. `_require_payroll()` is called at the start of every payroll endpoint handler (it calls `_require_hr()` first, providing the two-level gate). No service code runs after these guards raise.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off response contract

With `S.hr_enabled = False`:
- Every request to any `/ui/hr/*` path (positions, employments, payroll) receives HTTP 404 `{"detail": {"code": "hr_disabled"}}` before any service code is invoked.
- `T.hr` is never accessed; no DynamoDB reads or writes occur.

With `S.hr_enabled = True` and `S.hr_payroll_enabled = False`:
- Requests to `/ui/hr/positions*` and `/ui/hr/employments*` proceed normally.
- Requests to `/ui/hr/payroll*` receive HTTP 404 `{"detail": {"code": "hr_payroll_disabled"}}`.

### 5.2 Non-admin caller

A user with `role=USER` calling any HR endpoint (GET or POST) receives HTTP 403 `{"detail": {"code": "role_required", "required_roles": ["admin", "root"], "actual_role": "user"}}` from `require_admin_or_root` / `require_admin_or_root_csrf`. The flag check (`_require_hr()`) is placed after the auth dependency in FastAPI's dependency resolution order — that is, `Depends(require_admin_or_root_csrf)` resolves before the function body runs, so the 403 fires before the flag check. This is intentional: unauthorized callers should not learn whether the feature is enabled.

**Implementation note:** Because `_require_hr()` is called at the top of the handler body (not as a `Depends`), the auth dependency resolves first. If a future ticket requires flag-off to return 404 even before auth, `_require_hr()` can be promoted to a `Depends` that runs unconditionally — but the current spec matches the `admin_compute.py` pattern where `_check_enabled()` is called inside the handler.

### 5.3 Missing resource handling

GET endpoints that call `get_position` / `get_employment` / `get_payroll_run` receive `None` when the item does not exist. The router maps this to HTTP 404:
```python
item = hr_svc.get_position(position_id)
if item is None:
    raise HTTPException(status_code=404, detail={"code": "position_not_found"})
return PositionOut(**item)
```

### 5.4 `POST /payroll/{id}/post` — idempotency and partial failure

`post_payroll_run` (HRM-008) is idempotent per `(payroll_run_id, employment_id)` via deterministic ledger correlation ids (`sha256(f"payroll:{payroll_run_id}:{employment_id}")`) on each `new_ledger_entry` call. If a post partially fails (some lines post, then a network error), the run remains `APPROVED` (HRM-008 transitions to `POSTED` only after all lines succeed). Re-calling `POST /payroll/{id}/post` triggers a safe retry: the service re-iterates lines, the conditional `put_item` for each ledger entry on `attribute_not_exists(pk)` is a no-op for lines that already posted, and new lines are written. The router returns 200 with the updated run once the service confirms `status="POSTED"`.

### 5.5 List endpoint response shape

All list endpoints return a consistent envelope:
```json
{"items": [...], "next_cursor": null}
```
`next_cursor` is a signed cursor string (from `app/core/cursor.py:94 encode_cursor` **verified**) or `null` when there are no more pages. Clients supply `?cursor=<next_cursor>` to page forward.

### 5.6 `PATCH /positions/{id}/status` vs `PUT`

The spec uses `PATCH` (not `PUT`) because only the `status` field changes. `UpdatePositionStatusIn` carries a single `status: str` field. The router passes the caller's `user.sub` as `actor_sub` to `update_position_status` for audit logging.

### 5.7 `POST /employments/{id}/terminate` returns 409 if already terminated

`terminate_employment` raises `TerminateAlreadyTerminatedError` (defined in HRM-006) for an idempotent re-terminate. The router maps this to HTTP 409 rather than 200, because a retry after timeout should re-confirm success by checking `GET /employments/{id}` first. This is a deliberate non-idempotent design for the terminate endpoint: the operation is significant (end of employment), and a 409 prompts the caller to verify intent rather than silently proceeding.

### 5.8 `actor_sub` threading

The `user.sub` from the authenticated session is threaded through to every service call that accepts `actor_sub`. This ensures audit events carry the real admin's identity even when the platform has impersonation active (impersonation context is on `request.state`, resolved by `audit_event` itself at `app/services/alerts.py:656-665` if `request` is passed — the router passes `None` for `request`, so the basic `user_sub` audit form is used).

### 5.9 Response model coercion

The service layer returns plain `Dict[str, Any]` items from DynamoDB. The router constructs Pydantic response models using `PositionOut(**item)`, `EmploymentOut(**item)`, etc. DynamoDB stores integer attributes as `Decimal`; the Pydantic models must include `@model_validator(mode="before")` coercions for `int`-typed fields (e.g., `pay_rate_cents`, `gross_cents`, `created_at`, `period_start`, `period_end`), mirroring the `MessageEncryptionEnvelope` coercion at the MEMORY.md "Bug Fixes Applied" section. This is HRM-003's responsibility; HRM-009 relies on it being present.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007: no dev/prod branches

`app/routers/hr.py` contains no `if S.dev_mode:` branches. The route handlers delegate entirely to the service layer, which itself is dev/prod parity-clean per HRM-005 through HRM-008. DynamoDB reads and writes in dev (DynamoDB Local, `DDB_ENDPOINT_URL=http://localhost:8001`) and prod (real DynamoDB) are identical at the service layer.

### 7.2 Idempotency at the router layer

The router itself adds no idempotency logic — that lives entirely in the service layer. The only router-level idempotency concern is re-approval and re-post, which the service handles (re-approve is a no-op returning the existing `APPROVED` item; re-post is safe via deterministic ledger correlation ids per HRM-008). The router returns 200 (not 201) on `POST /payroll/{id}/approve` and `POST /payroll/{id}/post` to avoid any confusion about whether a new resource was created.

### 7.3 Authorization

- **Role enforcement**: `require_admin_or_root` / `require_admin_or_root_csrf` (from `app/auth/policy.py:67,100` **verified**) enforce `Role.ADMIN` or `Role.ROOT` via `role_allows_admin_features` at `app/auth/roles.py:60` (**verified**). Regular users (role `USER`) receive 403.
- **CSRF enforcement**: `require_admin_or_root_csrf` calls `enforce_cookie_csrf(request)` for cookie-authenticated non-GET requests. Bearer-token callers skip CSRF (no session cookie present). This matches the CLAUDE.md CSRF requirement.
- **Payroll access scope**: All payroll routes are admin/root only. There is no per-employment-record ownership check — HR is a platform-administrative function, not a per-user feature.

### 7.4 Audit trail

Each mutating endpoint passes `user.sub` as `actor_sub` to the service function, which emits audit events via `app/services/alerts.py:644 audit_event` (**verified**) best-effort. The router does not emit additional audit events. The audit trail for each operation is:
- Position create: `position.created`
- Position status update: `position.status_updated`
- Employment create: `employment.created`
- Employment terminate: `employment.terminated`
- Payroll run create: `payroll_run.created`
- Payroll run approve: `payroll_run.approved`
- Payroll run post: `payroll_run.posted`

### 7.5 No direct billing calls

The router calls `payroll_svc.post_payroll_run(...)` and never imports or calls `billing_shared.new_ledger_entry` directly (`app/services/billing_shared.py:224` **verified**). All ledger writes are encapsulated in `hr_payroll.py` (HRM-008). This architectural constraint is verified by the test plan's explicit assertion that `new_ledger_entry` is not imported in `app/routers/hr.py`.

## 10. Open Questions / Assumptions

1. **Assumption: `PositionNotFoundError`, `PositionInvalidTransitionError`, `TerminateAlreadyTerminatedError`, `EndDateBeforeStartDateError`, `PayrollRunInvalidTransitionError` are all defined in `app/services/hr.py` or `app/services/hr_payroll.py` as `ValueError` subclasses.** The router catches these by type in the handler body. If HRM-005/006 use generic `ValueError` with a string discriminator instead of subclasses, the router must use a string comparison (`except ValueError as e: if "already_terminated" in str(e): ...`) — less clean. Verify the exact exception types from HRM-005/006 implementations before writing the router.

2. **Assumption: `UpdatePositionStatusIn` is a Pydantic model added by HRM-003 with a single `status: str` field.** The ticket text mentions `PATCH /positions/{position_id}` (status only). If HRM-003 uses a different model name or includes additional fields, the router import must be updated.

3. **Assumption: all list service functions return `{"items": [...], "next_cursor": Optional[str]}`.** The router passes this dict directly as the response for list endpoints. If any service function returns a different envelope (e.g., `{"positions": [...], "cursor": ...}`), the router must remap before returning.

4. **Assumption: `require_admin_or_root_csrf` from `app/auth/policy.py:100` is the correct dependency for non-GET endpoints.** The ticket says "admin dep per the CLAUDE.md convention and `app/auth/roles.py:60 role_allows_admin_features`". `require_admin_or_root_csrf` at `app/auth/policy.py:100` matches this. If the project introduces a dedicated `require_hr_admin` scope (like `AdminScope.BILLING_SUPPORT` for billing), the router dep would change — no such scope is planned in the HR ticket backlog.

5. **Assumption: re-approve (`POST /payroll/{id}/approve` on an already-APPROVED run) returns HTTP 200 with the existing run, not 409 or 204.** This matches HRM-007 §5.5 ("re-approve is a no-op"). If the product team wants 409 on re-approve to signal "already done", the router must check the current status before calling `approve_payroll_run` and raise 409 itself (the service returns the existing item silently). Deferred pending product decision.

6. **Assumption: `POST /payroll/{id}/post` on an already-POSTED run returns HTTP 409**, not 200. HRM-008 defines `post_payroll_run` as idempotent at the ledger level but raises `PayrollRunInvalidTransitionError` when the run is already `POSTED` (terminal state, per the transition table in HRM-007 §5.2: `"POSTED": set()`). The router maps this to 409. If HRM-008 instead returns the existing item silently, the router maps to 200.

7. **Open question: should the router gate on `user.sub` being an actual party record?** The HR service functions accept any `actor_sub` for audit purposes, but they don't validate that the admin's `user_sub` has an employee record or any HR-specific party role. This is intentional — HR admin endpoints are platform-administrative, not employee-self-service. No change needed unless a future ticket adds per-HR-admin role scope.

8. **RISK — Assumption: the `party` table handle (`T.party`) and the `party` service functions exist from HRM-004's dependency on PTY-004/PTY-010.** `T.party` does NOT exist anywhere in the current codebase (`app/core/tables.py` has no `party` entry, and `grep -r "T\.party"` returns nothing — **verified**). The employment `create_employment` service call includes a `party.create_relationship(...)` call that writes to `T.party`. The router passes `party_id` from the request body — it does not create the party record itself. Ensure HRM-004 and PTY-004/PTY-010 are complete (and `T.party` is wired in `app/core/tables.py`) before HRM-009 is implemented. If those tickets are not done, the service import in `app/routers/hr.py` may compile but runtime calls to `hr_svc.create_employment` will fail at `T.party` access.

9. **Assumption: `actor_sub` is passed as `user.sub` from the authenticated session, not from the request body.** Admin actions are attributed to the authenticated admin, not to a caller-supplied identity. No `actor_sub` field appears in any request model.

10. **Assumption: the `/ui/hr` prefix does not collide with any existing router prefix.** Confirmed by grepping: `grep -r 'prefix="/ui/hr"' /home/ubuntu/testlogon/app/routers/` returns no results. The prefix is free.
