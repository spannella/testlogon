# MFG-012 — MRP Suggestions Admin UI

**Type:** Feature | **Priority:** P2 | **Estimate:** 3 days
**Milestone:** 4 — Lite MRP

---

## 1. Summary & Goal

MFG-012 delivers the MRP suggestions admin page: a React component at
`frontend/src/pages/shop/admin/MrpSuggestionsPage.tsx` that lets an admin or
root user trigger a new MRP run (with a horizon-days picker), inspect the
resulting requirement rows grouped by `produce` vs. `purchase` suggestion type,
and execute one-click hand-offs:

- A **`produce`** suggestion opens a pre-filled "New Work Order" dialog backed
  by the `createWorkOrder` endpoint (MFG-009 pattern), passing `product_sku` and
  `suggested_quantity` as defaults.
- A **`purchase`** suggestion deep-links to the Purchasing module's PO-create
  route if present (`/admin/purchasing/po/new?sku=...&qty=...`) or, when the
  Purchasing module does not yet exist (the current state — no `purchasing_scm_enabled`
  flag, no router), shows the suggested quantity and SKU in a read-only action
  panel with a "Copy details" affordance for manual purchasing action.

The page is additive: it consumes the backend endpoints from MFG-011
(`app/routers/manufacturing.py`) and the service from MFG-010
(`app/services/manufacturing_mrp.py`) via new TypeScript wrappers appended to
`frontend/src/api/endpoints/manufacturing.ts`. No backend service code is written
or modified by this ticket.

The entire feature is completely hidden — no route, no nav item, no API calls —
when `VITE_MANUFACTURING_MRP_ENABLED` is falsy (the default).

## 2. Context & Current State

### 2.1 Backend MRP endpoints (from MFG-010 + MFG-011)

Both endpoints live under `/ui/manufacturing/mrp` and require
`require_admin_or_root_csrf` (`app/auth/policy.py:100–106`). The full contract,
as specified in `docs/ofbiz/specs/MFG-010.md:§4.4`, is:

| Method | Path | Body | Returns |
|--------|------|------|---------|
| `POST` | `/ui/manufacturing/mrp/run` | `MrpRunIn` | `MrpRunOut` |
| `GET`  | `/ui/manufacturing/mrp/runs/{run_id}` | — | `MrpRunOut` |

`MrpRunIn` carries `horizon_days?: int`, `location_id?: str`,
`correlation_id?: str`. Both fields default server-side to `S.mfg_mrp_default_horizon_days`
(30 days) and `"warehouse"` respectively.

`MrpRunOut` includes a top-level `requirements: MrpRequirementOut[]` list. Each
`MrpRequirementOut` has the fields defined in `docs/ofbiz/specs/MFG-010.md:§4.5`:
`sku`, `gross_requirement`, `on_hand_available`, `scheduled_receipts`,
`net_requirement`, `suggested_action` (`"produce"` | `"purchase"` | `"none"`),
`suggested_quantity`, `bom_id`.

A POST to `/ui/manufacturing/mrp/run` is idempotent when the same
`correlation_id` is passed: it returns the existing run (per
`docs/ofbiz/specs/MFG-010.md:§5.5`). The run is synchronous for MVP — the
response carries `status="completed"` when the function returns (no async
polling needed unless the run horizon produces very large demand sets).

## 3. Data Model

MFG-012 introduces **no new DynamoDB tables**. All MRP data lives in the
`mfg_mrp` table provisioned by MFG-002 (specified in
`docs/ofbiz/specs/MFG-002.md`). Work orders created via the produce hand-off
live in `mfg_work_orders` (also MFG-002).

### 3.1 `mfg_mrp` — single-table layout (recap from MFG-010)

```
PK: mrp_run_id  (S)   sha256(correlation_id)[:32]
SK: sk           (S)   "META" | "REQ#{sku}#{seq:06d}"
```

The relevant fields for the UI:

**Header row** (`sk = "META"`):
- `mrp_run_id`, `status`, `horizon_days`, `location_id`, `created_at`, `completed_at`, `requirement_count`

**Requirement row** (`sk = "REQ#{sku}#{seq:06d}"`):
- `sku`, `gross_requirement`, `on_hand_available`, `scheduled_receipts`, `net_requirement`, `suggested_action`, `suggested_quantity`, `bom_id`

GSI: `GSI_RUN_STATUS` (PK=`status` S, SK=`created_at` N); `attr_types: {"created_at": "N"}`.
This GSI is used by the "Run History" panel to list past runs sorted by recency.

### 3.2 TypeScript types — additions to `frontend/src/api/types.ts`

These are appended after the `WorkOrderListResp` block that MFG-009 will add
(`docs/ofbiz/specs/MFG-009.md:§3.1`; currently neither `WorkOrderListResp` nor
any manufacturing types exist in `frontend/src/api/types.ts` — verified). If MFG-009
has not yet merged, these three interfaces are appended at the end of the file:

```ts
// ─── MRP Suggestions (MFG-012) ──────────────────────────────────────────────

export interface MrpRunIn {
  horizon_days?: number;
  location_id?: string;
  correlation_id?: string;
}

export interface MrpRequirementOut {
  sku: string;
  gross_requirement: number;
  on_hand_available: number;
  scheduled_receipts: number;
  net_requirement: number;          // may be negative (surplus)
  suggested_action: "produce" | "purchase" | "none";
  suggested_quantity: number;       // always >= 0
  bom_id: string;
}

export interface MrpRunOut {
  mrp_run_id: string;
  status: "pending" | "running" | "completed" | "failed";
  horizon_days: number;
  location_id: string;
  created_at: number;
  completed_at: number;
  requirement_count: number;
  user_sub: string;
  requirements: MrpRequirementOut[];
}
```

## 4. API / Service Design

### 4.1 Endpoint wrappers — `frontend/src/api/endpoints/manufacturing.ts`

MFG-006 creates this file (not yet present — verified absent from
`frontend/src/api/endpoints/`); MFG-009 appends work-order wrappers. MFG-012
appends MRP wrappers to the **same file**:

```ts
// ── MRP Suggestions (MFG-012) ────────────────────────────────────────────────

export const triggerMrpRun = (body: MrpRunIn) =>
  api.post<MrpRunOut>(`${BASE}/mrp/run`, body);

export const getMrpRun = (runId: string) =>
  api.get<MrpRunOut>(`${BASE}/mrp/runs/${encodeURIComponent(runId)}`);
```

`BASE` is the existing `"/ui/manufacturing"` constant declared by MFG-006.
No existing wrappers are modified.

### 4.2 Page component — `frontend/src/pages/shop/admin/MrpSuggestionsPage.tsx`

Top-level component structure:

```
MrpSuggestionsPage
├── Feature-flag guard: if (!isManufacturingMrpEnabled()) → <EmptyState>
├── Role guard: if (!canAccessGeneralAdminControls(accessToken)) → <EmptyState>
└── two-column layout (max-w-7xl)
    ├── Left column (w-1/3): <RunTriggerPanel />
    └── Right column (w-2/3): <SuggestionsPanel />
```

**Top-level state:**
- `currentRunId: string | null` — the run currently displayed on the right.
- `selectedReq: MrpRequirementOut | null` — the requirement row that has an
  open hand-off dialog.

### 4.3 `<RunTriggerPanel />`

A `<Card>` with:
- **Horizon picker**: a `<Select>` (or `<Input type="number" min=1 max=365>`)
  for `horizon_days`, defaulting to 30. Options: 7, 14, 30, 60, 90 days plus
  "Custom" which reveals a number input. The chosen value is local state
  `horizonDays`.
- **"Run MRP" button**: triggers `triggerMrpRun`:

```ts
const runMutation = useMutation({
  mutationFn: () =>
    triggerMrpRun({
      horizon_days: horizonDays,
      correlation_id: crypto.randomUUID(),   // fresh UUID → new run each click
    }),
  onSuccess: (run) => {
    toast.success(`MRP run completed — ${run.requirement_count} requirements`);
    setCurrentRunId(run.mrp_run_id);
    qc.invalidateQueries({ queryKey: ["mfg", "mrp", "runs"] });
  },
  onError: (err) => toast.error((err as any)?.message || "MRP run failed"),
});
```

The `correlation_id` is re-seeded with `crypto.randomUUID()` at call time (not
at panel-mount time) so each button click produces an independent run. The
button is disabled while `runMutation.isPending`.

- **Run history list**: a `useQuery` fetching recent completed runs to allow
  switching to a past run:

```ts
const historyQuery = useQuery({
  queryKey: ["mfg", "mrp", "runs"],
  queryFn: () => listMrpRuns({ limit: 20 }),
  enabled: allowed,
  staleTime: 60_000,
});
```

`listMrpRuns` is an additional endpoint wrapper (see Section 4.5) calling
`GET /ui/manufacturing/mrp/runs` (a list endpoint added by MFG-011).

Each history entry is a row showing `created_at` (relative), `horizon_days`,
`requirement_count`, and `status` badge. Clicking a row sets `currentRunId`.
The currently selected run gets a highlighted background.

If no run exists yet, the panel shows a muted "No runs yet — trigger your first
MRP run above."

### 4.4 `<SuggestionsPanel />`

Driven by `currentRunId`. When `currentRunId` is null, renders a placeholder
`<EmptyState icon={BarChart3}>` with the message "Run MRP to see suggestions."

When `currentRunId` is set:

```ts
const runQuery = useQuery({
  queryKey: ["mfg", "mrp", "run", currentRunId],
  queryFn: () => getMrpRun(currentRunId!),
  enabled: !!currentRunId && allowed,
  staleTime: 300_000,   // 5 min — MRP runs are immutable once completed
});
```

Renders a `<Tabs defaultValue="produce">`:

```
<TabsList>
  <TabsTrigger value="produce">  Produce  ({produceCount})
  <TabsTrigger value="purchase"> Purchase ({purchaseCount})
  <TabsTrigger value="none">     Surplus  ({noneCount})
</TabsList>
```

Each tab renders a `<Table>` of the filtered requirement rows.

**Produce tab columns:**
| Column | Source |
|--------|--------|
| SKU | `req.sku` |
| Gross Demand | `req.gross_requirement` |
| On-hand | `req.on_hand_available` |
| Scheduled | `req.scheduled_receipts` |
| Net Need | `req.net_requirement` (bold, colored amber if > 0) |
| Suggested Qty | `req.suggested_quantity` |
| Action | `<Button size="sm" onClick={() => openProduceDialog(req)}>Create Work Order</Button>` |

**Purchase tab columns:**
| Column | Source |
|--------|--------|
| SKU | `req.sku` |
| Gross Demand | `req.gross_requirement` |
| On-hand | `req.on_hand_available` |
| Scheduled | `req.scheduled_receipts` |
| Net Need | `req.net_requirement` |
| Suggested Qty | `req.suggested_quantity` |
| Action | `<Button size="sm" variant="outline" onClick={() => openPurchasePanel(req)}>Purchase Details</Button>` |

**Surplus tab columns** (same minus the Action column; read-only):
Shows rows with `suggested_action="none"`, conveying surplus. Each row has
`net_requirement` displayed in muted green to indicate supply exceeds demand.

### 4.5 Additional MRP list endpoint wrapper

The run-history panel needs a list of past runs. MFG-011 exposes
`GET /ui/manufacturing/mrp/runs` (list by GSI_RUN_STATUS). MFG-012 adds:

```ts
export const listMrpRuns = (params?: { status?: string; limit?: number }) =>
  api.get<MrpRunOut[]>(`${BASE}/mrp/runs`, params as Record<string, string>);
```

The backend list endpoint returns an array of run headers (without `requirements`
to keep response size small). Each header includes `mrp_run_id`, `status`,
`horizon_days`, `created_at`, `requirement_count`. The full `requirements` array
is only fetched via `getMrpRun(runId)` on demand.

This endpoint must be implemented in MFG-011. See Section 11 for the dependency
note. If MFG-011 does not yet expose a list endpoint, the history panel degrades
gracefully (shows only the most recently triggered run stored in component state,
which is still fully functional for the primary workflow).

## 5. Detailed Behavior & Edge Cases

### 5.1 Horizon picker defaults and validation

The `horizonDays` input is a controlled `<Input type="number">` with `min=1`
and `max=365`. Values outside this range are clamped before submission; the
server also enforces `ge=1, le=365` on `MrpRunIn.horizon_days`
(`docs/ofbiz/specs/MFG-010.md:§4.5`). A value of 0 or negative is rejected
client-side before the POST fires.

### 5.2 Run status display

The backend guarantees synchronous completion for MVP: `POST /ui/manufacturing/mrp/run`
returns `status="completed"` (or `"failed"`) before the HTTP response is sent
(`docs/ofbiz/specs/MFG-010.md:§4.2`, steps 7–9). The UI does not need a polling
loop. If the status comes back `"failed"` (BOM cycle detected mid-run), the panel
shows a red `<Alert>` with the `error_detail` field from the run header, and no
requirements are displayed.

### 5.3 `produce` suggestion with null `bom_id`

A `produce` suggestion should always carry a non-empty `bom_id` (set by the MRP
engine when it finds an active BOM). If `bom_id` is empty (edge case: BOM was
deactivated after the run completed), the create-work-order dialog still opens
but the `bom_id` field is blank. The admin may supply a BOM ID manually. The
backend will attempt to auto-resolve the active BOM if no `bom_id` is supplied
(MFG-007 contract).

### 5.4 Component aggregation display

The MRP engine aggregates requirements per SKU across all demand paths
(`docs/ofbiz/specs/MFG-010.md:§5.2`). The suggestions panel therefore shows at
most one row per SKU per run. The `gross_requirement` already reflects the sum
of all demand contributions. No client-side deduplication is needed.

### 5.5 Empty suggestions (no gross demand)

If the MRP run returns `requirement_count=0` (no open orders in the horizon),
the Produce and Purchase tabs each show a shadcn/ui `<EmptyState>` — "No
produce requirements in this planning horizon" / "No purchase requirements."
The Surplus tab is also empty. This is a valid completed run with no
actionable suggestions.

### 5.6 Requirement rows with `suggested_action="none"` (surplus)

Surplus rows are displayed in the Surplus tab as read-only reference data. No
action button is shown — a surplus means current supply exceeds demand and no
production or procurement is needed. The `net_requirement` value (which may be
negative) is shown in muted green to visually distinguish surplus from shortage.

### 5.7 Creating a work order from MRP: idempotency guard

The `<ProduceHandOffDialog />` seeds `correlation_id` with `crypto.randomUUID()`
at dialog-open time (not at button-click time), matching the pattern established
by MFG-009 (`docs/ofbiz/specs/MFG-009.md:§7`). Double-clicking Submit while the
mutation is in-flight is prevented by disabling the button during `isPending`.
Closing and re-opening the dialog generates a new UUID.

### 5.8 Concurrent run trigger

If an admin triggers two runs in quick succession (unlikely but possible), each
carries a fresh `crypto.randomUUID()` as `correlation_id`, so both produce
independent run IDs. The `historyQuery` is invalidated after each run, so the
run history panel refreshes and shows both.

### 5.9 Flag-off behavior

With `VITE_MANUFACTURING_MRP_ENABLED=false` (default):
- `MrpSuggestionsPage.tsx` renders an `<EmptyState>` immediately (no API calls).
- The `admin/mrp-suggestions` route exists in `App.tsx` but shows the empty state.
- The nav item `MRP Suggestions` is filtered from the sidebar by the
  `showMrpSuggestionsAdmin` predicate.

With the backend flag `MANUFACTURING_MRP_ENABLED=false`:
- Every endpoint called by the page returns 404 (`_require_enabled()` in the
  service, per `docs/ofbiz/specs/MFG-010.md:§6`).
- React Query surfaces error states; the page renders error cards without crashing.

### 5.10 Role-only access (scoped admin exclusion)

`canAccessGeneralAdminControls(accessToken)` from
`frontend/src/lib/adminCapabilities.ts:47–52` returns `true` only for ROOT or
ADMIN with `admin_profile.type === "general"`. Scoped admins (e.g.
`charlie_scoped` with only `content_moderation` scope) see an access-denied
`<EmptyState>`. This matches the policy for every other manufacturing admin page.

### 5.11 MRP run history panel — list endpoint not yet implemented

If MFG-011's list endpoint (`GET /ui/manufacturing/mrp/runs`) is not yet
deployed, `listMrpRuns` returns a 404. The `historyQuery` error state is handled
gracefully: the history panel renders a muted "Run history unavailable" note.
The trigger-and-view workflow (trigger a run → see its suggestions immediately)
is unaffected because `triggerMrpRun`'s `onSuccess` callback sets `currentRunId`
directly from the POST response.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

MFG-012 is a pure frontend page. It makes HTTP calls through the shared Axios
client (`frontend/src/api/client.ts`) which is dev/prod identical. The backend
endpoints it calls (`manufacturing_mrp.py`, `manufacturing_work_orders.py`) have
no `dev_mode` branches (confirmed by `docs/ofbiz/specs/MFG-010.md:§7.1`,
`docs/ofbiz/specs/MFG-007.md:§7`). No mock paths, no `S.dev_mode` conditionals.

### 7.2 Idempotency

- **MRP run trigger**: each "Run MRP" click seeds a fresh `crypto.randomUUID()`
  as `correlation_id`, producing an independent new run. The page never reuses
  the same `correlation_id` across button clicks (unlike the work-order create
  dialog, where the UUID is seeded at dialog-open to prevent double-submit).
  Rationale: an MRP run is an intentional query; re-running with the same
  horizon should show fresh demand data, not a cached run.
- **Work-order create from produce hand-off**: `correlation_id` is seeded at
  `<ProduceHandOffDialog>` open time, so double-clicking Submit is idempotent
  (backend returns the same work order on the second call via
  `sha256(correlation_id)` deterministic ID — `docs/ofbiz/specs/MFG-007.md:§7.1`).
- **MRP runs are immutable**: once `status="completed"`, no endpoint mutates
  the run. React Query's `staleTime: 300_000` on `getMrpRun` respects this.

### 7.3 Auth and CSRF

All POST calls carry `x-csrf-token` automatically via `frontend/src/api/client.ts`.
The `require_admin_or_root_csrf` backend dependency (`app/auth/policy.py:100–106`)
enforces both role ≥ ADMIN and CSRF on the MRP run endpoint and the work-order
create endpoint. GET calls are CSRF-exempt per the auth contract
(CLAUDE.md: "non-GET requests require `x-csrf-token`").

### 7.4 Sensitive data considerations

MRP run outputs contain SKU-level demand and inventory levels — commercially
sensitive information. The page is admin-gated both client-side (feature-flag +
role check) and server-side (`require_admin_or_root_csrf`). MRP run IDs exposed
in the URL or clipboard are opaque SHA-256 hashes; they do not reveal input data.
The `<PurchaseActionPanel>`'s "Copy details" button copies only SKU and quantity
strings — no internal IDs, session tokens, or user data.

### 7.5 No billing or inventory mutation

The MRP suggestions page triggers only a POST to `/ui/manufacturing/mrp/run`
(read-only against all tables except `T.mfg_mrp`) and optionally a POST to
`/ui/manufacturing/work-orders` (which writes only to `T.mfg_work_orders` via
MFG-007). No billing ledger entries, no inventory adjustments, no cart/order
mutations are made by MFG-012.

## 10. Open Questions / Assumptions

1. **Assumption: MFG-011 exposes `GET /ui/manufacturing/mrp/runs` as a list
   endpoint.** MFG-011's spec (`MANUFACTURING_MRP_TICKETS.md:222–242`) lists
   `POST /ui/manufacturing/mrp/run` and `GET /ui/manufacturing/mrp/runs/{id}` but
   does not explicitly enumerate a top-level `GET /ui/manufacturing/mrp/runs` list.
   This spec assumes MFG-011 adds that list endpoint (querying GSI_RUN_STATUS on
   `T.mfg_mrp`) as it is the natural companion to the single-run GET. If MFG-011
   does not include the list endpoint, the run-history panel degrades to showing
   only the most recently triggered run (stored in component state).

2. **Assumption: `POST /ui/manufacturing/mrp/run` returns synchronously.** The
   MFG-010 spec (`docs/ofbiz/specs/MFG-010.md:§4.2`) describes a synchronous
   algorithm that completes before returning. If the MRP engine is refactored to
   be async (e.g. for very large demand sets), the UI will need a polling loop
   checking `getMrpRun(runId)` until `status="completed"`. MFG-012 does not
   implement this polling — a follow-up ticket would be needed.

3. **Assumption: `MrpRunOut.requirements` is always populated in the POST
   response.** The spec (`docs/ofbiz/specs/MFG-010.md:§4.2` step 9) says
   `run_mrp` calls `get_mrp_run(mrp_run_id)` and returns the full result
   including `requirements`. If the list endpoint omits `requirements`, only
   `getMrpRun` (the detail call) is used for the suggestions panel.

4. **Assumption: the MFG-011 list endpoint (`GET /ui/manufacturing/mrp/runs`)
   returns run headers without the `requirements` array** (lightweight response
   for the history panel). This must be confirmed with the MFG-011 implementer.
   If the list endpoint returns full runs with embedded `requirements`, the
   history panel's stale-time and payload size may need adjustment.

5. **Assumption: `suggested_action="produce"` always corresponds to a known
   `bom_id`.** The MRP engine only assigns `"produce"` when `get_active_bom(sku)`
   is not None (`docs/ofbiz/specs/MFG-010.md:§4.2` step 5e). A `bom_id`-less
   `produce` row is a theoretical edge case (BOM deactivated between run and
   display). The UI handles it gracefully by showing a blank `bom_id` field in
   the create dialog.

6. **Question: should the Produce tab display a BOM explosion preview** (component
   quantities) inline, or only after clicking "Create Work Order"? The ticket
   description ("view requirement rows grouped by produce/purchase") implies a
   flat list view. A nested-expansion BOM preview is deferred to a follow-up
   for simplicity; the work-order create dialog in `ProductionQueue.tsx` already
   has this via `<ComponentAvailabilityPreview />`.

7. **Assumption: `net_requirement` in `MrpRequirementOut` may be negative (surplus
   rows).** This is explicit in `docs/ofbiz/specs/MFG-010.md:§4.5`. The Surplus
   tab must render the raw value (possibly negative) rather than `suggested_quantity`
   (always ≥ 0) to show the magnitude of surplus.

8. **Question: should triggering a new MRP run auto-clear the previous run from
   the suggestions panel?** This spec proposes: yes — `runMutation.onSuccess`
   sets `currentRunId` to the new run ID, which replaces the suggestions panel
   content. The old run remains accessible in the history list. Confirm with the
   product team whether "always show latest run" is the desired default.

9. **Assumption: `listMrpRuns` API returns runs in descending `created_at` order.**
   GSI_RUN_STATUS's sort key is numeric `created_at` (N type, per
   `docs/ofbiz/specs/MFG-002.md`). The backend query uses `ScanIndexForward=False`
   to return newest-first. The frontend history list renders in this order.

10. **Assumption: the `<PurchaseActionPanel>` "Copy details" uses the Clipboard
    API (`navigator.clipboard.writeText`).** This API requires HTTPS in production.
    In dev (localhost), the browser allows it. An `isSecureContext` guard should
    be added to show a fallback text selection if the Clipboard API is unavailable.
