# SHP-009 — Package contents & packing

## 1. Summary & Goal

SHP-009 extends `app/services/shipments.py` (created by SHP-008) with the full package-management layer for physical shipments: adding packages to a shipment, assigning order line-items to specific packages, and computing and persisting a billed package weight per package that can be reconciled against the SHP-006 rate estimate when the carrier charges at ship time.

Three service functions are added:

1. **`add_package(shipment_id, package_in) -> ShipmentPackageOut`** — appends a new `shipment_packages` row and returns the persisted package including its `package_seq` and initial `billed_weight_oz`.
2. **`assign_item_to_package(shipment_id, package_seq, content_in) -> ShipmentPackageOut`** — records a `ShipmentPackageContentIn` association (item + quantity) onto the package, validating that the cumulative packed quantity for the item across all packages never exceeds the `shipment_items` row's quantity.
3. **`get_packing_status(shipment_id) -> Dict[str, Any]`** — returns a per-item packed-vs-required comparison and a boolean `pack_complete` flag (all items fully packed) that the SHP-010 lifecycle state machine can check before permitting the `created → packed` transition.

Billed weight per package is computed by `_compute_billed_weight_oz(weight_oz, length_in, width_in, height_in)` using the same dimensional-weight formula introduced in SHP-006 (`actual_oz vs cubic_in / dim_divisor * 16`, taking the larger). The result is stored as `billed_weight_oz` on the `shipment_packages` row.

With `SHIPPING_ENABLED=false` (default), all code paths introduced here return 503 and every pre-existing shop/cart/orders/billing table is byte-for-byte unchanged.

### 2.5 Dimensional-weight formula (SHP-006 reference)

SHP-006 (`app/services/shipping_rates.py`, docs/ofbiz/specs/SHP-006.md:68–72) established the dimensional-weight divisor pattern. The formula is:

```
dim_weight_oz = math.ceil((length_in * width_in * height_in) / S.shipping_dim_divisor) * 16
billed_weight_oz = max(actual_weight_oz, dim_weight_oz)
```

`S.shipping_dim_divisor` (default `139`) is defined by SHP-006 in `app/core/settings.py` (`docs/ofbiz/specs/SHP-006.md:479`). SHP-009 calls the same pure function rather than duplicating the formula. SHP-006 uses `math.ceil` (see `docs/ofbiz/specs/SHP-006.md:144,241`) — SHP-009 must match this to avoid under-reporting dim weight.

### 2.7 Audit events (SHP-008 pattern)

SHP-008 calls `audit_event` (imported from `app/services/alerts`) for every creation/transition, mirroring `app/services/commerce_order_service.py:106-117`. SHP-009 emits two events: `shipment_package_added` and `shipment_package_contents_updated`.

### 2.8 Idempotency pattern (SHP-008 reference)

SHP-008 uses a deterministic `sha256(correlation_id)[:24]` for `shipment_id` so that `create_shipment` called twice for the same `(order_id, ship_group)` returns the same shipment without writing a duplicate row (conditional `put_item` with `attribute_not_exists(shipment_id)`).

SHP-009 does not require the same idempotency for `add_package` (packages are not keyed by a user-supplied correlation ID; they are additive and sequenced) but must be idempotent for `assign_item_to_package` when the same `(shipment_id, package_seq, item_id, quantity)` is submitted twice: if a content row already exists for `item_id` in that package with the same quantity, the call is a no-op.

## 3. Data Model

### 3.1 No new DynamoDB tables

SHP-009 uses only `T.shipments`, `T.shipment_items`, and `T.shipment_packages` — all scaffolded by SHP-002. No new `TableDef` entries are added to `scripts/local-ddb-init.py`, no new settings keys to `app/core/settings.py`, and no new table handles to `app/core/tables.py`.

### 3.2 `shipment_packages` row schema (extended)

The SHP-002 schema is extended with `billed_weight_oz` (written by SHP-009, not present in bare SHP-002 or SHP-008):

| Attribute | Type | Nullable | Notes |
|---|---|---|---|
| `shipment_id` (PK) | String | no | FK to `shipments` |
| `package_seq` (SK) | String | no | `"00001"`, `"00002"`, … |
| `weight_oz` | Number | no | Declared weight in ounces (`ge=0`); 0 allowed (empty box) |
| `length_in` | Number | yes | Box length in inches |
| `width_in` | Number | yes | Box width in inches |
| `height_in` | Number | yes | Box height in inches |
| `contents` | List | no | `[{item_id, sku, quantity}]`; empty list until `assign_item_to_package` is called |
| `billed_weight_oz` | Number | yes | `max(weight_oz, dim_weight_oz)`; absent if all dimensions missing |
| `created_at` | Number | no | Integer Unix seconds (`now_ts()`) |

`billed_weight_oz` is written on `add_package` (using the declared `weight_oz` as the initial actual weight, compared against the computed dim weight from the supplied dimensions if all three are present), and recomputed on every `assign_item_to_package` call in case the caller passes updated dimensions via the content assignment body (this is not required — see §5.4 for the dimension-update flow).

### 3.3 New Pydantic model: `AssignItemToPackageIn`

Added to `app/models.py` in this ticket. Placed in the `# ── Shipping / Logistics` section after `ShipmentPackageOut`:

class AssignItemToPackageIn(BaseModel):

The optional weight/dimension fields on `AssignItemToPackageIn` allow the warehouse operator to correct the package dimensions while assigning its final item, avoiding a separate `PATCH` round-trip for the common flow of "scan item into box, then weigh the sealed box." The SHP-011 router exposes this field set.

## 4. API / Service Design

### 4.1 Service function: `add_package`

```python
def add_package(
    shipment_id: str,
    package_in: ShipmentPackageIn,
) -> Dict[str, Any]:
```

**Steps:**

1. Call `_require_enabled()`.
2. Call `get_shipment(shipment_id)` — raises 404 if not found.
3. Verify `shipment["status"] in {"created", "pending_fulfillment"}` — raises `HTTPException(409, {"code": "shipment_not_packable", ...})` for any other status.
4. Compute the next `package_seq` by querying `T.shipment_packages` for all rows with `shipment_id` (via `KeyConditionExpression="shipment_id = :sid"`) and taking `len(existing) + 1`, zero-padded to 5 digits.
5. Compute `billed_weight_oz` via `_compute_billed_weight_oz(package_in.weight_oz, package_in.length_in, package_in.width_in, package_in.height_in)` (see §4.4).
6. Write the `shipment_packages` row via `T.shipment_packages.put_item`:
   ```python
   {
       "shipment_id": shipment_id,
       "package_seq": seq_str,
       "weight_oz": package_in.weight_oz,
       "length_in": package_in.length_in,
       "width_in": package_in.width_in,
       "height_in": package_in.height_in,
       "contents": [c.model_dump() for c in package_in.contents],
       "billed_weight_oz": billed_weight_oz,
       "created_at": now_ts(),
   }
   ```
7. If `package_in.contents` is non-empty, call `_validate_and_apply_contents(shipment_id, seq_str, package_in.contents)` (see §4.3) — this applies the same quantity-cap validation used by `assign_item_to_package`.
8. Emit `audit_event("shipment_package_added", actor_user_id="system", resource_id=shipment_id, package_seq=seq_str)`.
9. Return the persisted row as a `ShipmentPackageOut`-compatible dict.

**Idempotency:** `add_package` is **not** idempotent by design — each call creates a new package. The caller owns the decision of how many packages to add. Repeated calls simply append additional packages.

### 4.2 Service function: `assign_item_to_package`

```python
def assign_item_to_package(
    shipment_id: str,
    package_seq: str,
    content_in: AssignItemToPackageIn,
) -> Dict[str, Any]:
```

**Steps:**

1. Call `_require_enabled()`.
2. Fetch the shipment (404 if missing). Verify status in `{"created", "pending_fulfillment"}` — 409 otherwise.
3. Fetch the `shipment_items` row for `(shipment_id, content_in.item_id)` — raises `HTTPException(404, {"code": "shipment_item_not_found"})` if the `item_id` is not part of this shipment.
4. Fetch all packages for this shipment (`T.shipment_packages.query(KeyConditionExpression=Key("shipment_id").eq(shipment_id))`).
5. Compute `already_packed` = sum of `c["quantity"]` across every content entry in every package where `c["item_id"] == content_in.item_id`.
6. Check `already_packed + content_in.quantity <= shipment_item["quantity"]`; if not, raise `HTTPException(400, {"code": "over_pack", "message": f"Packing {content_in.quantity} units of item {content_in.item_id} would exceed the shipment quantity of {shipment_item['quantity']} (already packed: {already_packed})"})`.
7. Fetch the target package `T.shipment_packages.get_item(Key={"shipment_id": shipment_id, "package_seq": package_seq})` — raises 404 if the package does not exist.
8. **Idempotency check**: if the package's `contents` list already contains an entry with `item_id == content_in.item_id` and `quantity == content_in.quantity`, return the package unchanged (no double-write). If it contains an entry with the same `item_id` but different quantity, replace it (the operator is correcting the quantity; quantity cap is re-validated against the new total).
9. Update `contents` by appending or replacing the `{item_id, sku, quantity}` entry.
10. If `content_in.weight_oz` or any dimension field is non-None, apply those updates to the package's own `weight_oz`/`length_in`/`width_in`/`height_in`.
11. Recompute `billed_weight_oz = _compute_billed_weight_oz(new_weight_oz, new_length_in, new_width_in, new_height_in)`.
12. Write back via `T.shipment_packages.update_item`:
    ```python
    UpdateExpression="SET contents = :c, billed_weight_oz = :bw, updated_at = :u"
    ExpressionAttributeValues={
        ":c": updated_contents,
        ":bw": billed_weight_oz,
        ":u": now_ts(),
    }
    ```
    (Add `weight_oz = :w, length_in = :l, width_in = :wi, height_in = :h` to the expression only when the caller supplied new dimensions.)
13. Emit `audit_event("shipment_package_contents_updated", resource_id=shipment_id, package_seq=package_seq, item_id=content_in.item_id)`.
14. Return the updated package row as a dict.

### 4.3 Private helper: `_validate_and_apply_contents`

```python
def _validate_and_apply_contents(
    shipment_id: str,
    package_seq: str,
    contents: List[ShipmentPackageContentIn],
    *,
    existing_packages: Optional[List[Dict[str, Any]]] = None,
) -> None:
```

Used by `add_package` when `ShipmentPackageIn.contents` is non-empty at creation time. Fetches all current packages (or reuses `existing_packages` when pre-fetched by `assign_item_to_package`), then iterates `contents` and validates the quantity cap for each `item_id`. Raises `HTTPException(400, {"code": "over_pack", ...})` on the first violation. If all items pass, the `contents` list is already embedded in the row written by `add_package` (step 6), so this helper does no further writes — it is a pure validation pass. Callers that need per-item sequential cap validation (e.g. when contents contains duplicates for the same `item_id`) accumulate the running total as they iterate.

### 4.4 Private helper: `_compute_billed_weight_oz`

```python
def _compute_billed_weight_oz(
    weight_oz: int,
    length_in: Optional[float],
    width_in: Optional[float],
    height_in: Optional[float],
) -> int:
```

Reuses the formula from SHP-006:

```python
import math
from app.core.settings import S

def _compute_billed_weight_oz(weight_oz, length_in, width_in, height_in):
    if length_in and width_in and height_in:
        cubic = length_in * width_in * height_in
        dim_oz = math.ceil(cubic / S.shipping_dim_divisor) * 16
        return max(int(weight_oz), dim_oz)
    return int(weight_oz)
```

`math.ceil` (not `int`/truncation) matches SHP-006's formula (`docs/ofbiz/specs/SHP-006.md:144,241`); using `int()` would under-charge fractional cubic inches.

`S.shipping_dim_divisor` (default `139`) is added by SHP-006. This function is called from both `add_package` and `assign_item_to_package`. It is a pure function — no DDB access.

### 4.5 Service function: `get_packing_status`

```python
def get_packing_status(shipment_id: str) -> Dict[str, Any]:
```

**Steps:**

1. Call `_require_enabled()`.
2. Fetch all `shipment_items` rows (`T.shipment_items.query(KeyConditionExpression=Key("shipment_id").eq(shipment_id))`).
3. Fetch all `shipment_packages` rows (same pattern).
4. For each `shipment_item`, compute `packed_quantity` = sum of `content["quantity"]` across all packages where `content["item_id"] == item["item_id"]`.
5. Build `items: List[PackingItemStatus]` and compute `pack_complete = all(i["remaining"] == 0 for i in items)`.
6. Return a `PackingStatusOut`-compatible dict including `shipment_id`, `pack_complete`, `items`, and the full `packages` list as `ShipmentPackageOut`-compatible dicts.

`get_packing_status` is read-only — no writes, no audit event.

## 5. Detailed Behavior & Edge Cases

### 5.1 Over-pack guard

The primary invariant: `sum(packed quantity for item_id across all packages) <= shipment_item.quantity`. The check uses the **current** `shipment_items` row, not the original `order_items` row. This is correct because SHP-008's `create_shipment` already enforces that the shipment items' quantities do not exceed the ordered quantities (the over-ship guard).

The over-pack check is performed **before** any write. If it fails, nothing is written and the 400 response is returned. The check is not a DynamoDB conditional expression — it is computed client-side by fetching and summing the `contents` lists. This avoids a complex multi-item atomic conditional in DynamoDB while remaining correct because package management is an admin-only operation (no concurrent consumer-side writes to `shipment_packages`).

### 5.2 Default package created by SHP-008

`create_shipment` (SHP-008) always writes a single package row at `package_seq="00001"` with empty `contents` and `weight_oz=0`. This provides a sensible default for single-box shipments: the operator can call `assign_item_to_package` directly without first calling `add_package`. If the shipment requires multiple boxes, the operator calls `add_package` to create additional packages, then assigns items. The initial default package row is never deleted by SHP-009 (deletion is out-of-scope).

### 5.3 Multi-package split

An order line of quantity 10 can be split across two packages: 6 units in package `"00001"` and 4 in `"00002"`. The operator makes two `assign_item_to_package` calls, each with its `package_seq`. The quantity cap is enforced cumulatively: the first call is checked against 0 already packed, the second against 6 already packed. Both calls succeed if the total ≤ 10.

### 5.4 Dimension update on `assign_item_to_package`

When the operator seals a box and measures it, they may pass new `weight_oz`/`length_in`/`width_in`/`height_in` values on the `AssignItemToPackageIn` body. This triggers a `billed_weight_oz` recomputation. If only some dimensions are supplied (e.g. `weight_oz` is updated but no new dimensions), the `_compute_billed_weight_oz` helper uses the package's **existing** `length_in`/`width_in`/`height_in` fetched in step 7 (merged with the caller-supplied values). This prevents losing a previously set dimension by supplying a partial update.

### 5.5 `pack_complete` invariant and transition gate

`get_packing_status` returns `pack_complete=True` only when every `shipment_item` has `remaining == 0`. The SHP-010 state machine's `created → packed` transition calls `get_packing_status` and raises `HTTPException(409, {"code": "pack_incomplete", "message": "All shipment items must be fully packed before advancing to packed status"})` if `pack_complete` is `False`. This gate ensures no shipment can be marked `packed` while items remain unpacked.

### 5.6 Shipments in non-packable statuses

`add_package` and `assign_item_to_package` both reject shipments with status outside `{"created", "pending_fulfillment"}` (409). This prevents modifying packages on a shipment that has already been handed to the carrier (`label_created` or later). If re-packing is needed (e.g. due to a carrier error before handover), the operator must revert the shipment status — that is SHP-010 scope.

### 5.7 Empty `contents` on `add_package`

A package may be created with `contents=[]`. This is valid (a reserve package for partial packing). `billed_weight_oz` is still computed from `weight_oz` and dimensions. The package will appear in `get_packing_status` but contribute 0 packed quantity for all items.

### 5.8 `sku` field on content entries

`sku` is optional on `ShipmentPackageContentIn` and `AssignItemToPackageIn`. If omitted, the service looks it up from the `shipment_items` row and fills it in before persisting. This ensures `contents` always carries `sku` for packing-slip generation without requiring the caller to supply it.

### 5.9 Concurrent `assign_item_to_package` calls

Because the over-pack validation is client-side (not a DynamoDB conditional), two concurrent calls assigning the last unit of the same `item_id` to different packages could both pass the check (both read 0 packed, both compute 1 <= required_quantity). The result is an over-packed state. This is acceptable for a warehouse management workflow where the `shipment_packages` table is written by a single warehouse operator at a time. A future hardening ticket could add a per-shipment lock row. An audit event is emitted on every write; detecting over-pack post-hoc is possible via the audit trail.

### 5.10 Billed weight reconciliation

`billed_weight_oz` on each package is the per-package billable weight. The total shipment billed weight = `sum(p.billed_weight_oz for p in packages)`. This total is what the carrier will charge at ship time. The SHP-006 estimate used at checkout was derived from the cart's line-item weights. If the two diverge (e.g. the actual box is heavier than the per-SKU default weight), the difference can be surfaced to the admin in SHP-011's shipment detail view. No billing ledger entry is created here — billing is settled via the existing `purchase_transactions` + `purchase_history.update_shipping` path.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No `dev_mode` branches

`app/services/shipments.py` contains zero `if S.dev_mode` conditionals. The `_compute_billed_weight_oz` helper is a pure arithmetic function — identical behaviour in dev and prod. DynamoDB access goes through `T.shipment_packages` and `T.shipment_items`, both `_FloatSafeTable` proxies that coerce floats to Decimal on write via `_to_decimal` (`app/core/tables.py:41-49`, covering both `put_item` and `update_item` paths). Dev uses DynamoDB Local (port 8001); prod uses real DynamoDB. Both paths are identical code.

### 7.2 Idempotency

- **`add_package`**: Not idempotent. Each call adds a distinct package row. The admin UI prevents accidental double-add by showing the current package count.
- **`assign_item_to_package`**: Idempotent for identical inputs (`item_id` + `quantity` already in the package's `contents` list → no-op, same response). Corrective re-assignment (same `item_id`, new `quantity`) replaces the entry; the quantity cap is re-validated.
- **`get_packing_status`**: Fully idempotent — pure read.

### 7.3 No billing ledger entries

No calls to `billing_shared.new_ledger_entry`. Package management does not move money. Shipping cost reconciliation (billed weight vs estimated) is handled at shipment creation/transition time in SHP-010/SHP-011 scope.

### 7.4 No `refund_payment` calls

Over-pack validation rejections are pre-flight checks; no charge has occurred at this stage. Returns/refunds of shipping costs go through the existing `app/services/returns_rma.py` and `app/routers/billing.py:refund_payment` path (as noted in the global constraints) — SHP-009 does not touch this.

### 7.5 Auth and authorization

`add_package` and `assign_item_to_package` are admin-only operations (called from `require_admin_or_root_csrf` endpoints in SHP-011; `app/auth/policy.py:100`). The function `require_admin_session` does not exist in the codebase — the correct dependency is `require_admin_or_root_csrf`. The service layer receives the `shipment_id` from the router; the router enforces that the caller is an admin and that the shipment belongs to an order they are authorized to manage (SHP-011's ownership validation). SHP-009 itself does not re-verify admin role — it trusts the router's auth gate (standard pattern, e.g. `app/services/tickets.py` service functions assume the router has enforced session).

`get_packing_status` is readable by the buyer (their own shipments) and by admins. SHP-011's router enforces the ownership check (`shipment.user_id == ctx["user_sub"]` for non-admin callers).

### 7.6 No PII in audit events

`audit_event` params include `shipment_id`, `package_seq`, and `item_id`. None of these carry PII. `ship_to_address` is stored on the `shipments` row but is not emitted in audit events by SHP-009.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact with flag off

With `SHIPPING_ENABLED=false` (the default introduced by SHP-002):

- `app/services/shoppingcart.py` — byte-for-byte unchanged.
- `app/services/commerce_order_service.py` — byte-for-byte unchanged.
- `app/services/billing_shared.py` — byte-for-byte unchanged.
- `app/routers/billing.py`, `app/routers/paypal.py`, `app/services/billing_ccbill.py` — byte-for-byte unchanged.
- `app/services/purchase_history.py` — byte-for-byte unchanged.
- `app/services/carrier_tracking.py` — byte-for-byte unchanged.

The `_require_enabled()` guard fires at the top of each service function so no new DynamoDB calls are made when the flag is off.

### 8.2 New models are additive

`AssignItemToPackageIn` and `PackingStatusOut` / `PackingItemStatus` are pure additions to `app/models.py`. No existing model is modified or renamed. They are appended in the `# ── Shipping / Logistics` block after `ShipmentPackageOut` (docs/ofbiz/specs/SHP-003.md §4.6).

### 8.3 `ShipmentPackageOut.billed_weight_oz` is already `Optional`

SHP-003 already declared `billed_weight_oz: Optional[int] = None` on `ShipmentPackageOut` (docs/ofbiz/specs/SHP-003.md:272) in anticipation of SHP-009 writing it. SHP-008's default package row (`weight_oz=0`, no dimensions, empty `contents`) will have `billed_weight_oz=0` after SHP-009 runs `_compute_billed_weight_oz(0, None, None, None) = 0`. Callers that handled `billed_weight_oz=None` (from before SHP-009) must now expect `0` — a safe additive change since `0` is falsy in the same way.

### 8.4 Enabling in production

1. Ensure SHP-002, SHP-003, SHP-004, SHP-006, SHP-008 are deployed. The `shipment_packages` table already exists.
2. Deploy SHP-009 with `SHIPPING_ENABLED=false`. No behaviour change.
3. Set `SHIPPING_ENABLED=true`. The three service functions become live.
4. Verify via `POST /ui/shipping/shipments/{id}/packages` (SHP-011 router) that a package can be added and `billed_weight_oz` is correctly computed.
5. Verify the over-pack guard: attempt to assign more units than the `shipment_item.quantity`; confirm 400 `"over_pack"` response.
6. Verify `GET /ui/shipping/shipments/{id}/packing-status` returns `pack_complete=false` before all items are assigned and `pack_complete=true` after.

## 10. Open Questions / Assumptions

**OQ-1 (SHP-008 default package `billed_weight_oz`)**: This spec assumes SHP-008 writes `billed_weight_oz=0` on the default package row (computed from `weight_oz=0, no dims`). If SHP-008 omits `billed_weight_oz` entirely, `ShipmentPackageOut.billed_weight_oz` will be `None` until SHP-009 touches the row. Both `0` and `None` are handled by the `Optional[int]` field in `ShipmentPackageOut`. Confirm with SHP-008 implementor.

**OQ-2 (Concurrent packing race)**: The over-pack check is client-side (read-then-check-then-write). Two warehouse operators concurrently assigning the last unit to different packages will both pass the check. The spec documents this as acceptable (single-operator workflow). If multi-operator packing is required, a per-shipment version field with conditional update (mirroring `purchase_history.py:420`) should be added. Confirm with product.

**OQ-3 (Package deletion)**: The spec explicitly excludes package deletion (no `delete_package` function). If deletion is required (e.g. operator added too many packages), it is a future ticket. Confirm scope with SHP-011 author.

**OQ-4 (Sku auto-fill)**: The spec assumes that when `sku` is absent from `AssignItemToPackageIn`, the service fills it from `shipment_items`. If `shipment_items` rows can themselves have a null `sku` (allowed by the schema), the `sku` on the content entry will also be null. This is acceptable for packing — `sku` is denormalised and advisory.

**OQ-5 (Partial `pack_complete` with ship-group subsets)**: SHP-008 supports multi-group shipments per order. `get_packing_status` is scoped to a single `shipment_id`. If an order has two shipments (two ship groups), each has its own `pack_complete` flag. The `created → packed` gate in SHP-010 is per-shipment, not per-order. Confirm with SHP-010 author.

**OQ-6 (`shipping_dim_divisor` from SHP-006)**: This spec assumes `S.shipping_dim_divisor` is added by SHP-006. If SHP-006 is not yet merged when SHP-009 is implemented, the helper should use `getattr(S, "shipping_dim_divisor", 139)` as a fallback default to avoid an `AttributeError`.

**OQ-7 (`AssignItemToPackageIn` placement in `app/models.py`)**: This spec adds `AssignItemToPackageIn` and `PackingStatusOut`/`PackingItemStatus` to `app/models.py` as part of SHP-009. They could alternatively live in `app/routers/shipments.py` (SHP-011) if the team prefers to keep `app/models.py` for SHP-003-defined shapes only. `app/models.py` is preferred for OpenAPI documentation consistency.
