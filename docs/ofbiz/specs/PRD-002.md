## 1. Summary & Goal

PRD-002 is the infrastructure prerequisite for every downstream product-depth ticket (PRD-003 through PRD-016). It produces exactly three artifacts:

1. **A new DynamoDB table definition** — `product_depth` — added to `scripts/local-ddb-init.py` with the five GSIs designed in PRD-001, numeric sort keys declared with `attr_types`, and no modification to the existing `shopping_catalog` table definition.
2. **Settings keys** in `app/core/settings.py` — the master switch `product_depth_enabled` (default `False`) plus one table-name key and four sub-feature flags (variants, bundles, features, price-components), all adjacent to the existing catalog block at `:832`.
3. **A table handle** `T.product_depth` wired in `app/core/tables.py` via `_safe_table(S.product_depth_table_name)`, adjacent to `T.catalog` at `:351`.

No service logic, no router endpoints, and no model changes ship in this ticket. The sole behavioral guarantee is: with `PRODUCT_DEPTH_ENABLED` unset (the default), `just restart` creates the new table but nothing in the existing shop/cart/orders/billing paths references it, so existing behavior is byte-for-byte unchanged.

## 3. Data Model

PRD-002 creates exactly one new DynamoDB table: `product_depth`. The table design is prescribed by PRD-001 §3.2–§3.3 (already reviewed and signed off). This section reproduces the definitive `TableDef` and describes what each GSI is for; it does not repeat the full entity-attribute tables (those are in PRD-001 §3.2 and will be used by PRD-003 through PRD-013).

### 3.1 `product_depth` TableDef

```python
# To be inserted in scripts/local-ddb-init.py, immediately after the
# shopping_catalog TableDef at :117–125.
#
# OFBiz Catalog/Product Depth — PRD-002.
# Dedicated table for all product-depth entities (PRD-001 decision: dedicated
# table keeps T.catalog's ByItemId GSI and entity-filter scan clean).
# Five GSIs; four carry numeric sort keys declared in attr_types.
TableDef(
    _resolve_table_name(S.product_depth_table_name, "product_depth"),
    "PK",
    "SK",
    gsi=[
        # ByParent: category-tree parent → ordered children.
        # Partition: GSI_PARENT_PK = "PARENT#{parent_category_id}" (or "PARENT#root")
        # Sort:      GSI_PARENT_SK = position (int) — ordered sibling listing.
        {"index_name": "ByParent",          "partition_key": "GSI_PARENT_PK",  "sort_key": "GSI_PARENT_SK"},
        # ByFeatureCategory: feature-category → ordered feature values.
        # Partition: GSI_FTCAT_PK = "FTCAT#{feature_category_id}"
        # Sort:      GSI_FTCAT_SK = position (int) — display order.
        {"index_name": "ByFeatureCategory", "partition_key": "GSI_FTCAT_PK",   "sort_key": "GSI_FTCAT_SK"},
        # ByVirtualParent: virtual product → variant children (chronological).
        # Partition: GSI_VIRT_PK = "VIRTUAL#{parent_item_id}"
        # Sort:      GSI_VIRT_SK = created_at (int Unix timestamp).
        {"index_name": "ByVirtualParent",   "partition_key": "GSI_VIRT_PK",    "sort_key": "GSI_VIRT_SK"},
        # ByAssocSource: product → outbound associations (substitute/complement/upgrade/manuf).
        # Partition: GSI_ASSOC_PK = "ASSOC_SRC#{from_item_id}"
        # Sort:      GSI_ASSOC_SK = "{assoc_type}#{assoc_id}" (String — no attr_types needed).
        {"index_name": "ByAssocSource",     "partition_key": "GSI_ASSOC_PK",   "sort_key": "GSI_ASSOC_SK"},
        # ByItemPrice: item+price-type → price components (newest-first range query).
        # Partition: GSI_PRICE_PK = "PRICE#{item_id}#{price_type}"
        # Sort:      GSI_PRICE_SK = effective_at (int Unix timestamp).
        {"index_name": "ByItemPrice",       "partition_key": "GSI_PRICE_PK",   "sort_key": "GSI_PRICE_SK"},
    ],
    attr_types={
        "GSI_PARENT_SK": "N",   # category position
        "GSI_FTCAT_SK":  "N",   # feature-value position
        "GSI_VIRT_SK":   "N",   # variant created_at
        "GSI_PRICE_SK":  "N",   # price effective_at
        # Note: GSI_ASSOC_SK is a String (assoc_type#assoc_id) — omitted intentionally.
        # Note: "effective_at" (item attribute) is also N but not a GSI key itself.
    },
)
```

### 3.2 Rationale for five GSIs

| GSI | Access pattern it enables | Entity type |
|---|---|---|
| `ByParent` | `list_children(parent_category_id)` — single GSI query, no scan | `category_tree` |
| `ByFeatureCategory` | `list_feature_values(fc_id)` ordered by `position` | `feature_value` |
| `ByVirtualParent` | `list_variants(parent_item_id)` chronological | `variant` |
| `ByAssocSource` | `list_associations(item_id[, type])` with SK prefix | `product_assoc` |
| `ByItemPrice` | `resolve_effective_price(item_id, type, as_of)` range scan | `price_component` |

Without these GSIs, every listing operation would require a full-table scan. The `ByParent` GSI replaces the category fallback scan at `app/routers/catalog.py:211` (`_scan_categories`) for tree-aware listing. The entity-type filter scan used in catalog search sits at `app/routers/catalog.py:485` (`item.get("entity") != "item"`).

### 3.3 Primary-key patterns (entity rows, summary)

These are the PK/SK prefixes that service modules will write. They are prescribed by PRD-001 §3.2 and reproduced here for completeness. PRD-002 itself does not write any rows.

| Entity | PK | SK | GSI attributes |
|---|---|---|---|
| `product_type` marker | `ITEM#{item_id}` | `TYPE` | — |
| `category_tree` | `CAT#{category_id}` | `TREE` | `GSI_PARENT_PK`, `GSI_PARENT_SK` |
| `feature_category` | `FTCAT#{fc_id}` | `META` | — |
| `feature_value` | `FTCAT#{fc_id}` | `FTVAL#{fv_id}` | `GSI_FTCAT_PK`, `GSI_FTCAT_SK` |
| `feature_appl` | `ITEM#{item_id}` | `FTAPPL#{fc_id}` | — |
| `variant` | `ITEM#{parent_id}` | `VAR#{variant_id}` | `GSI_VIRT_PK`, `GSI_VIRT_SK` |
| `bundle_component` | `ITEM#{bundle_id}` | `COMP#{component_id}` | — |
| `product_assoc` | `ITEM#{from_id}` | `ASSOC#{type}#{assoc_id}` | `GSI_ASSOC_PK`, `GSI_ASSOC_SK` |
| `price_component` | `ITEM#{item_id}` | `PRICE#{type}#{effective_at:010d}` | `GSI_PRICE_PK`, `GSI_PRICE_SK` |

All rows carry `entity` (discriminator string), `creator_id` (owning `user_sub`), `created_at` (Unix int), and `updated_at` (Unix int).

## 5. Detailed Behavior & Edge Cases

### 5.1 Table-creation behavior on `just restart`

`just restart` invokes `scripts/local-ddb-init.py` which calls `_table_defs()` and creates all listed tables. The new `TableDef` will cause DynamoDB Local to create a `product_depth` table with `PK`/`SK` (both String) as the primary key, plus five GSIs. The four numeric sort keys must appear in `AttributeDefinitions` with `AttributeType: "N"` — the `_attribute_definitions` helper at `scripts/local-ddb-init.py:2496–2506` handles this via the `attr_types` dict overlay. If any numeric key is accidentally omitted from `attr_types`, the first write of a row with an integer value for that key will silently store it as `"S"`, and the first GSI range query using that key as a number will raise `ValidationException: Type mismatch for Index Key`. This is the core CLAUDE.md gotcha that this ticket explicitly guards against.

### 5.2 `_attribute_definitions` processes `attr_types` correctly

The helper at `scripts/local-ddb-init.py:2496–2506` (verified):

```python
def _attribute_definitions(table: TableDef) -> List[Dict[str, str]]:
    attrs = {table.partition_key: "S"}
    if table.sort_key:
        attrs[table.sort_key] = "S"
    for gsi in table.gsi:
        attrs[gsi["partition_key"]] = "S"
        if gsi.get("sort_key"):
            attrs[gsi["sort_key"]] = "S"
    attrs.update(table.attr_types)   # ← overrides: N wins  (scripts/local-ddb-init.py:2505)
    return [{"AttributeName": k, "AttributeType": v} for k, v in attrs.items()]
```

For `product_depth`: `attrs` after the loop will contain `GSI_PARENT_SK: "S"`, `GSI_FTCAT_SK: "S"`, `GSI_VIRT_SK: "S"`, `GSI_PRICE_SK: "S"`, and `GSI_ASSOC_SK: "S"`. The `attrs.update(...)` then overrides the four numeric ones to `"N"`. `GSI_ASSOC_SK` stays `"S"`. This is correct.

### 5.3 Existing `shopping_catalog` table is unchanged

No `attr_types`, no new GSI, no rename. Existing data and indexes are untouched. Smoke test: `T.catalog.table_name` still resolves to `shopping_catalog` after this change.

### 5.4 `T.product_depth` at startup with flag off

Even when `PRODUCT_DEPTH_ENABLED=false`, the `product_depth` table is created (by `_table_defs`) and `T.product_depth` resolves to a valid `_FloatSafeTable`. This is consistent with the inventory and returns tables, which are always created but whose service modules check the flag before doing anything. Having the table present with the flag off incurs no cost and simplifies testing (tests can mutate the table without needing the flag on).

### 5.5 Sub-flag independence

A service module implementing variants (PRD-007) will check:

```python
def _require_variants_enabled() -> None:
    if not S.product_depth_enabled or not S.product_depth_variants_enabled:
        raise HTTPException(status_code=404, detail="Product variants are not enabled")
```

With `PRODUCT_DEPTH_ENABLED=true` and `PRODUCT_DEPTH_VARIANTS_ENABLED=false`, variant endpoints return 404 while category-tree and feature endpoints (if their sub-flags are on) continue to work. PRD-002 does not implement these guards — it only installs the settings keys they will read.

### 5.6 DDB Local table-already-exists handling

`scripts/local-ddb-init.py` wraps each `create_table` call in a `try/except ClientError` that ignores `ResourceInUseException` (the "table already exists" error) at `scripts/local-ddb-init.py:2589–2591`. This means re-running the init script (e.g. after a partial failure) is safe. The `product_depth` table follows the same pattern.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

All three artifacts (table definition, settings keys, table handle) behave identically in dev (DynamoDB Local at `http://localhost:8001`) and production (AWS DynamoDB). There is no `if S.dev_mode` branch introduced in this ticket. The `_safe_table` wrapper is already environment-agnostic — it proxies to whatever boto3 endpoint `ddb` (from `app/core/aws.py`) is configured to use.

The `product_depth` table is created by `scripts/local-ddb-init.py` in dev and by an `UpdateTable`/`CreateTable` migration in production. No code path in this ticket diverges between the two environments.

### 7.2 Idempotency

PRD-002 itself has no write path. The `_table_defs()` function is idempotent (create-or-ignore). Downstream tickets will implement deterministic entity IDs (e.g. `sha256(parent_item_id + sorted_feature_tuple)[:16]` for variants) as prescribed by PRD-001 §3 and enforced by the `condition_expression=Attr("SK").not_exists()` or unconditional put pattern that each service chooses.

### 7.3 Security

- `T.product_depth` is a table handle only. Access control is enforced by service modules checking `creator_id == user_sub` before writes and by router auth deps (`require_ui_session` (`app/services/sessions.py:330`), `require_admin_or_root` / `require_admin_or_root_csrf` (`app/auth/policy.py:67,100`)). Note: `require_admin_session` does not exist in this codebase — downstream tickets must use `require_admin_or_root` or `require_admin_or_root_csrf`.
- The table name is not user-visible; it is configured server-side only.
- No IAM, KMS, or Cognito changes are needed in this ticket.
- No PII is stored in the `product_depth` table. `creator_id` is a `user_sub` — the same type stored in every other table.

PRD-002 adds `attr_types` only to the new `product_depth` `TableDef`. The existing `shopping_catalog` `TableDef` does not gain `attr_types` — it does not need them (its GSI sort keys are already Strings, and `GSI1SK` is a string `"{name.lower()}#{category_id}"`). No existing table is modified.
