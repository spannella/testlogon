# POS-009 — Receipt generation reusing the receipts pipeline

**Type:** Feature | **Priority:** P1 | **Estimate:** 3 days
**Dependencies:** POS-007 (card/wallet tender, split tender, full settlement flow)

---

## 1. Summary & Goal

POS-009 generates a printable receipt for every settled POS transaction and
exposes a reprint endpoint that returns the same receipt deterministically on
repeat calls. The receipt covers: store/register/cashier/session header, line
items with quantities and per-item prices, subtotal/discount/tax/total footer,
and a tender breakdown (cash tendered + change due, card kind + last-4 digits,
wallet amount).

The implementation is entirely additive:

- A new `app/services/pos_receipt.py` module that calls the **existing** pure-Python
  PDF writer (`app/services/receipts.py:_render_pdf` / `_pdf_escape`) and stores
  the output via the **existing** S3/file-manager upload path
  (`app/services/filemanager.upload_billing_receipt`). No new PDF library, no
  new binary dependency, no fork of `receipts.py`.
- A `receipt_id` field appended to the `PosTransactionOut` model
  (`app/models.py`) via the `TXN#` row in `T.pos`.
- A `GET /ui/pos/txns/{txn_id}/receipt` endpoint (wired in POS-011) that serves
  the PDF binary-safe, following the exact `Response(media_type="application/pdf")`
  pattern already used in `app/routers/audit_export.py:303` and
  `app/routers/questionnaires.py:895` to avoid UTF-8 re-encoding corruption.

With `S.pos_enabled = False` (the default), none of this code is reachable
through the router surface. All existing shop/cart/orders/billing/receipts paths
are byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 Existing receipt pipeline (`app/services/receipts.py`)

`app/services/receipts.py` is a dependency-free, pure-Python receipt writer.
Key public surface:

- `_render_pdf(lines: List[str]) -> bytes` (`:53`) — builds a conforming PDF-1.4
  byte stream using manually assembled PDF objects. No `reportlab`, no system
  dependency. The same pattern is cited in `CLAUDE.md` for `_render_audit_pdf`
  in `app/services/audit_export_pipeline.py`.
- `_pdf_escape(text: str) -> str` (`:35`) — escapes `\`, `(`, `)` for PDF string
  literals. Must be applied to every text token before embedding.
- `_render_receipt_lines(payload: ReceiptPayload) -> List[str]` (`:138`) —
  builds the human-readable line list from a `ReceiptPayload` dataclass.
- `get_or_create_receipt(user_sub: str, txn_id: str) -> Dict[str, Any]` (`:199`)
  — top-level function used by `app/routers/purchase_history.py:157` and
  `app/services/consumer_tax_documents.py:666`. Calls
  `_build_receipt_payload` → `_render_pdf` → `upload_billing_receipt` →
  `set_receipt_info`. Always regenerates (no short-circuit cache today;
  note: calling it twice for the same txn hits `require_not_exists` at
  `filemanager.py:2442` with a 409 on the second upload).

POS-009 does **not** call `get_or_create_receipt`. That function is coupled to
`get_transaction_item` (which reads from `T.purchase_transactions`, the billing
table) and to a `ReceiptPayload` that expects a Stripe/PayPal payment record.
POS receipts carry different data (register, session, cashier, tender breakdown
with cash change). POS-009 builds its own parallel payload dataclass and line
renderer in `pos_receipt.py`, but reuses `_render_pdf` from `receipts.py`
directly to avoid duplicating the PDF byte-stream builder. (`_pdf_escape` is
already applied inside `_render_pdf` at `receipts.py:56`; callers need not
apply it separately.)

### 2.2 Upload and storage path (`app/services/filemanager.py`)

`upload_billing_receipt(user, *, txn_id, content)` at `filemanager.py:2431`:

- Puts the PDF bytes to S3 at `{user}/objects/{uuid}` with
  `ContentType="application/pdf"` (`:2444`).
- Writes a file-manager node record in `T.files` so the receipt appears in the
  user's file manager under `/billing/receipts/{txn_id}.pdf` (`:2441`).
- Returns `{"path": path, "size": size}` — no URL field (contrast with
  `upload_profile_photo` at `:2427` which appends a dev mock URL).

`build_download_url(path: str)` at `filemanager.py:2374` builds the download URL:
`"{S.public_base_url}/v1/fs/download?path={quote(path)}"`.

For POS receipts the `user` argument is the **cashier's** `user_sub` (the session
owner), and `txn_id` is the POS transaction id (e.g. `pos_txn_<ulid>`).

There is a `require_not_exists` guard at `:2442` that raises 409 if the file
node already exists. The idempotency strategy (Section 5.4) must route around
this on reprints.

### 2.3 POS data model established by POS-003/004/006/007

From the prior specs and `POS_TICKETS.md:53`:

- `T.pos` — single-table DynamoDB store. PK `pos_pk`, SK `pos_sk`.
- TXN row: `pos_pk = TXN#{txn_id}`, `pos_sk = META`. Carries `status` (`tendered`
  after full settlement), `session_id`, `cart_id`, `order_id`, `cashier_sub`,
  `subtotal_cents`, `discount_cents`, `tax_cents`, `total_cents`, `ledger_sk`
  (back-ref to billing ledger), and will gain `receipt_id` / `receipt_path` /
  `receipt_generated_at` via POS-009.
- Tender rows: `pos_pk = SESSION#{session_id}`, `pos_sk = TENDER#{txn_id}#{seq:04d}`.
  Carry `kind` (`cash|card|wallet`), `amount_cents`, `change_due_cents`
  (cash only), `pi_id` (card only), `ledger_sk`.
- Session row: `pos_pk = SESSION#{session_id}`, `pos_sk = META`. Carries
  `register_id`, `cashier_sub`, `status`, `opening_float_cents`.
- Register row: `pos_pk = REGISTER#{register_id}`, `pos_sk = META`. Carries
  `label`, `location_id`, `default_currency`.

The `PosTransactionOut` model (`app/models.py`) defined by POS-002 already
includes a `receipt_id: Optional[str]` field (from `POS_TICKETS.md:33`). This
field is `None` before settlement; POS-009 populates it with the `receipt_id`
once the receipt is written.

### 2.4 Binary-safe PDF response pattern

`app/routers/audit_export.py:303` and `app/routers/questionnaires.py:895`
already use the correct pattern:

```python
return Response(
    content=pdf_bytes,
    media_type="application/pdf",
    headers={"Content-Disposition": 'attachment; filename="receipt-{txn_id}.pdf"'},
)
```

`CLAUDE.md` (GAP-0209 section) documents why `PlainTextResponse` must not be
used for PDF: it UTF-8 re-encodes the bytes and corrupts the binary stream.

## 3. Data Model

POS-009 adds two attributes to the existing `TXN#{txn_id} / META` row in `T.pos`:

| Attribute | Type | Notes |
|---|---|---|
| `receipt_id` | String | Deterministic: `sha256("pos_receipt:" + txn_id)[:16]`. Written once; subsequent reprints skip the write. |
| `receipt_path` | String | File-manager path: `/billing/receipts/{txn_id}.pdf`. Stored for direct S3 resolution on reprint. |
| `receipt_generated_at` | Number (int) | Unix timestamp of first generation. |

No new DynamoDB table, no new GSI, no `attr_types` change. The `pos` table
(established by POS-003) already has PK `pos_pk` / SK `pos_sk`; these new
attributes are sparse attributes on the existing TXN row.

The update is a conditional `update_item` guarded by
`attribute_not_exists(receipt_id)` so that a concurrent second call cannot
overwrite a receipt already written (first-writer wins; see Section 5.4).

**No change to `scripts/local-ddb-init.py`** — all required tables and GSIs were
declared by POS-003.

### 4.2 Integration hook in `pos_tender.py` (POS-007 file)

After the final `purchase_cart` call and TXN-status update in `pos_tender.py`

from app.services.pos_receipt import generate_pos_receipt  # local import

### 4.3 Endpoint (wired by POS-011)

Two sub-endpoints live under `GET /ui/pos/txns/{txn_id}/receipt` in
`app/routers/pos.py`:

**GET /ui/pos/txns/{txn_id}/receipt** (accept: `application/json`)

```python
@router.get("/txns/{txn_id}/receipt", response_model=ReceiptLinkOut)
async def pos_get_receipt_meta(
    txn_id: str,
    ctx=Depends(require_ui_session),
) -> ReceiptLinkOut:
    _require_pos_enabled()
    txn = _get_pos_txn_or_404(txn_id)
    _require_txn_owner_or_admin(txn, ctx)
    result = generate_pos_receipt(txn_id, cashier_sub=txn["cashier_sub"])
    return ReceiptLinkOut(**result)
```

**GET /ui/pos/txns/{txn_id}/receipt/pdf** (accept: `application/pdf`)

```python
@router.get("/txns/{txn_id}/receipt/pdf")
async def pos_get_receipt_pdf(
    txn_id: str,
    ctx=Depends(require_ui_session),
) -> Response:
    _require_pos_enabled()
    txn = _get_pos_txn_or_404(txn_id)
    _require_txn_owner_or_admin(txn, ctx)
    pdf_bytes = get_receipt_bytes(txn_id, cashier_sub=txn["cashier_sub"])
    return Response(
        content=pdf_bytes,
        media_type="application/pdf",
        headers={
            "Content-Disposition": f'attachment; filename="pos-receipt-{txn_id}.pdf"'
        },
    )
```

**Auth**: `require_ui_session` (from `app/services/sessions.py:330`). The
`_require_txn_owner_or_admin` helper checks that `ctx["user_sub"]` equals
`txn["cashier_sub"]` OR `ctx["role"]` is ADMIN/ROOT. Foreign cashiers get 403.

**CSRF**: cookie-auth non-GET requests require `x-csrf-token` header. Both
endpoints are GET — no CSRF token required.

**Flag gate**: `_require_pos_enabled()` raises `HTTPException(404, "POS disabled")`
when `S.pos_enabled` is `False`, keeping the surface absent with the flag off.

### 4.4 Pydantic models (`app/models.py`)

No new model is required. `ReceiptLinkOut` (`app/models.py:509`) is reused for
the JSON response. It has four fields: `txn_id`, `receipt_path`, `receipt_url`,
`generated_at`. The `receipt_id` key that `generate_pos_receipt` includes in its

`PosTransactionOut` (defined by POS-002) already carries
`receipt_id: Optional[str]` — POS-009 writes that field to the TXN row so the
serializer can populate it.

## 5. Detailed Behavior & Edge Cases

### 5.1 Receipt content specification

`_render_pos_receipt_lines(p: PosReceiptPayload) -> List[str]` produces lines in
this order (all amounts in dollars with two decimal places, e.g. `"$12.50"`):

```
IN-PERSON SALE RECEIPT
----------------------------------------
Register  : {register_label}
Session   : {session_id[:8]}...
Cashier   : {cashier_name}
Date      : {fmt_ts(settled_at)}   # UTC, "May 31, 2026 14:22:01 UTC"

ITEMS
----------------------------------------
  {item_name}
    Qty: {qty}  x ${unit_price}  =  ${line_total}
  ...  (one block per line item; single-qty items omit the qty breakdown)
----------------------------------------
Subtotal  :              ${subtotal_cents/100:.2f}
Discount  :             -${discount_cents/100:.2f}   # omitted if 0
Tax       :              ${tax_cents/100:.2f}         # omitted if 0
----------------------------------------
TOTAL     :              ${total_cents/100:.2f}

TENDER
----------------------------------------
  Cash      :  ${cash_tendered/100:.2f}
  Change    : -${change_due/100:.2f}     # per cash tender; omitted if 0
  Card ({kind} ...{last4}) : ${card_amount/100:.2f}  # per card tender
  Wallet    :  ${wallet_amount/100:.2f}  # per wallet tender
----------------------------------------
```

`_fmt_ts` is the same helper defined at `receipts.py:31`:
`datetime.fromtimestamp(ts, tz=timezone.utc).strftime("%B %d, %Y %H:%M:%S UTC")`.
Copy into `pos_receipt.py` (do not import the private symbol across modules).

Card `last4` is read from the tender row's `card_ref` field (format `"visa_4242"`,
split on `_` → kind=`"visa"`, last4=`"4242"`). If `card_ref` is absent, render
as `"Card (...????)  $X.XX"`.

`_render_pdf` already calls `_pdf_escape` on every line internally
(`receipts.py:56`); `_render_pos_receipt_lines` passes plain strings and does
NOT call `_pdf_escape` itself — that would double-escape backslashes and
parentheses.

### 5.2 Data resolution at receipt generation time

`generate_pos_receipt` performs the following reads from `T.pos` before calling
`_render_pos_receipt_lines`:

1. **TXN row** (`TXN#{txn_id} / META`) — confirms `status == "tendered"` (raises
   `HTTPException(409, "receipt only available for settled transactions")` if not).
   Reads `session_id`, `cart_id`, `cashier_sub`, `subtotal_cents`,
   `discount_cents`, `tax_cents`, `total_cents`, `settled_at`.

2. **Session row** (`SESSION#{session_id} / META`) — reads `register_id`,
   `cashier_sub` (cross-check), `opened_at`.

3. **Register row** (`REGISTER#{register_id} / META`) — reads `label`, `currency`.

4. **Tender rows** (`SESSION#{session_id} / TENDER#{txn_id}*`) — queried via
   `T.pos.query(KeyConditionExpression=...)` with `begins_with(pos_sk, f"TENDER#{txn_id}#")`.
   Returns all tender legs for this txn ordered by sk (sequence order).

5. **Line items** — fetched from the existing cart via a local import:
   ```python
   from app.services.shoppingcart import list_items as list_cart_items
   line_items = list_cart_items(cashier_sub, cart_id)
   ```
   Mirrors the pattern in `receipts.py:117`.

6. **Cashier display name** — fetched via `app/services/profile.get_profile(cashier_sub)`,
   same as `receipts.py:108`.

All fetches except the TXN row are best-effort; a fetch failure should degrade
gracefully (empty list / "Unknown" label) rather than fail the receipt entirely.

### 5.3 Settlement status guard

`generate_pos_receipt` MUST check `txn["status"] == "tendered"` before generating.
- `status == "voided"` → `HTTPException(409, "voided transactions have no receipt")`.
- `status == "refunded"` → receipt is still available (the original sale receipt
  is valid; a separate refund notice is outside POS-009 scope).
- `status == "open"` → `HTTPException(409, "transaction not yet settled")`.

### 5.4 Idempotency / reprint strategy

Receipt generation must be idempotent: calling `generate_pos_receipt` twice for
the same `txn_id` must return the same receipt without re-rendering or attempting
a duplicate S3 write (which would hit `require_not_exists` at `filemanager.py:2442`
and raise 409).

Strategy:

1. At the start of `generate_pos_receipt`, read the TXN row and check for
   `receipt_path` attribute.
2. If `receipt_path` is set, skip rendering; build and return the metadata dict
   from the stored `receipt_path`, `receipt_id`, and `receipt_generated_at`.
3. If `receipt_path` is absent, render the PDF, upload via
   `upload_billing_receipt`, then write `receipt_id`, `receipt_path`, and
   `receipt_generated_at` back to the TXN row via a conditional `update_item`:

   ```python
   T.pos.update_item(
       Key={"pos_pk": f"TXN#{txn_id}", "pos_sk": "META"},
       UpdateExpression=(
           "SET receipt_id = :rid, receipt_path = :rp, "
           "receipt_generated_at = :rg"
       ),
       ConditionExpression="attribute_not_exists(receipt_id)",
       ExpressionAttributeValues={
           ":rid": receipt_id,
           ":rp": upload["path"],
           ":rg": generated_at,
       },
   )
   ```

4. If the `ConditionExpression` fails (`ConditionalCheckFailedException`), a
   concurrent caller already wrote the receipt. Re-read the TXN row and return
   the values written by the winner. This is the standard "first-writer wins"
   idempotency pattern.

The deterministic `receipt_id = sha256("pos_receipt:" + txn_id)[:16]` means the
id does not require storage for computation — it can always be recomputed from
`txn_id` alone.

### 5.5 `get_receipt_bytes` — on-demand re-render fallback

For the PDF endpoint, `get_receipt_bytes` must handle the case where the S3
object has been wiped (e.g. after `just restart`):

1. Fetch the TXN row; if `receipt_path` is set, attempt to retrieve the bytes
   from S3 via the file-manager download path.
2. If the S3 get fails (key not found), fall back to re-rendering the PDF from
   live DDB data, re-uploading, and updating the TXN row (replace `receipt_path`
   unconditionally this time).
3. If TXN row has no `receipt_path` yet (settlement completed but receipt hook
   has not run), call `generate_pos_receipt` first.

In dev, the moto in-process S3 mock is wiped on each `just restart`, making
this fallback path exercised routinely.

### 5.6 Receipt available in `PosTransactionOut`

The `receipt_id` field on `PosTransactionOut` should be populated by the
service layer whenever the TXN row is read via `_txn_row_to_out(item)`. The
serializer reads `item.get("receipt_id")` directly from the DDB item. No
separate endpoint fetch is needed.

### 5.7 Voided transactions

A voided transaction (POS-008 `void_transaction`) never reaches `status = "tendered"`.
The receipt generation hook in `pos_tender.py` runs only after full settlement.
`generate_pos_receipt` rejects void status with 409 (Section 5.3).

### 5.8 Partial refund after settlement

A refunded transaction retains `status = "tendered"` (POS-008 sets a separate
`refund_id` attribute). The original sale receipt remains valid and retrievable.
POS-009 does not generate a separate refund receipt; that is outside scope.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

No dev/prod divergence is introduced:

- PDF rendering (`_render_pdf`) is pure Python with no external dependency —
  the same function runs in dev and prod.
- S3 storage uses `upload_billing_receipt` from `filemanager.py:2431`, which
  calls `boto3` / moto transparently. In dev, moto intercepts at the botocore
  layer (per `CLAUDE.md`); in prod, the real S3 bucket is used. Same code path
  both ways.
- The receipt generation hook in `pos_tender.py` runs in both modes. No
  `if S.dev_mode:` branch is added.
- `build_download_url` (`filemanager.py:2374`) builds the download URL from
  `S.public_base_url`; dev and prod differ only in the value of that setting.

### 7.2 Idempotency

- `receipt_id` is deterministic: `sha256("pos_receipt:" + txn_id)[:16]`. It can
  be recomputed at any time without reading DDB.
- A conditional put (`attribute_not_exists(receipt_id)`) ensures the DDB write
  is idempotent under concurrent calls (first-writer wins pattern).
- `upload_billing_receipt` uses a fresh `uuid4()` for the S3 key on each call,
  but the file-manager path uses the deterministic `{txn_id}.pdf` filename. The
  `require_not_exists` guard on the path means re-upload is only attempted when
  the DDB path attribute is absent (the idempotency check in step 1 prevents
  reaching the upload if `receipt_path` is already stored).

### 7.3 Security

- The receipt endpoint enforces `_require_txn_owner_or_admin`: a cashier can
  only fetch receipts for their own transactions; admin/root users can fetch any.
  This prevents cross-cashier receipt enumeration.
- `txn_id` values from the URL are validated by the `_get_pos_txn_or_404` lookup
  before use — no format injection risk.
- The `Content-Disposition: attachment` header prevents the browser from
  rendering the PDF inline in potentially unsafe contexts.
- PDF content is built from DDB-stored data, not from arbitrary user input.
  `_pdf_escape` applied to all text values prevents PDF string injection.

until POS goes to prod.

### 8.3 Migration (prod)

When POS is eventually promoted to prod, pre-existing settled transactions without
receipts will yield `receipt_id = None` in `PosTransactionOut` and a 404/regenerate
response on `GET /receipt`. The on-demand regeneration path in `get_receipt_bytes`
(Section 5.5) handles this gracefully — the first reprint request for an old
transaction will render and store the receipt.

## 10. Open Questions / Assumptions

**OQ-1 — S3 bucket for POS receipts**: `upload_billing_receipt` stores files in
`/billing/receipts/{txn_id}.pdf` under the cashier's user-scoped S3 prefix
(`{cashier_sub}/objects/{uuid}`). This places POS receipts alongside billing
receipts from Stripe/PayPal purchases in the cashier's file manager. Assumption:
this is acceptable; the file manager path is namespaced by user, so cross-cashier
visibility does not occur. If POS receipts should live in a separate prefix (e.g.
`/pos/receipts/`), `upload_billing_receipt` would need a new overloaded variant
or a `folder` parameter — raise before implementation.

**OQ-2 — Cart availability after settlement** *(VERIFIED — pass 3)*: `list_items`
(`app/services/shoppingcart.py:277-285`) queries by PK+SK prefix only — it has no
cart-status check and never calls `_require_open_cart`. It returns items from a
PURCHASED cart without error. No fallback to TXN-row line-item snapshot is needed.

**OQ-3 — Tax is stored on TXN row, not computed**: POS-009 assumes
`tax_cents` is a pre-computed value already stored on the TXN row by POS-006/007.
If tax computation is deferred to receipt time (e.g. using `S.pos_default_tax_rate_bps`),
the receipt service would need to compute `tax_cents = int(subtotal_cents * S.pos_default_tax_rate_bps / 10000)`.
The design above stores and reads `tax_cents` from the TXN row; verify this
matches the POS-006 implementation.

**OQ-4 — Cashier display name** *(VERIFIED — pass 3)*: `get_profile` at
`app/services/profile.py:262-265` returns `empty_profile()` (a dict with
`display_name: None`) when the profile row is missing — it never raises. The
receipt renderer MUST handle `display_name=None` by falling back to
`cashier_sub[:8]`; this is an implementation requirement for
`_render_pos_receipt_lines`, not a risk to the overall design.

**OQ-5 — Reprint authorization model**: The spec gates reprint on cashier OR
admin. An alternative is to make receipts available to the customer (buyer), not
the cashier, since the customer is the one who needs the receipt. However, in a
POS context the "customer" may not have a platform account. Assumption: for v1,
the cashier and admin/root can access receipts; customer-facing receipt delivery
(e.g. email) is outside POS-009 scope.

**OQ-6 — `upload_billing_receipt` path collision**: `require_not_exists` at
`filemanager.py:2442` raises 409 if `/billing/receipts/{txn_id}.pdf` already
exists in the file-manager node table. The idempotency check (Section 5.4) reads
`receipt_path` from the TXN row before calling `upload_billing_receipt`. In the
rare case where the TXN row write succeeded but the file-manager node was already
written by a previous partially-failed call, the re-entry would hit this 409. The
`get_receipt_bytes` fallback path must catch this 409 and proceed to the S3 read
path. Alternatively, `upload_billing_receipt` could be extended with an
`overwrite=True` flag — raise this as a decision before implementation.
