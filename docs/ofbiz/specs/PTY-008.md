# PTY-008 — B2B organization account service

**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days  
**Milestone:** 3 — B2B Organizations & Legacy Migration  
**Depends on:** PTY-005 (role service), PTY-006 (relationship service)  
**Downstream:** PTY-012 (B2B org-account router), PTY-015 (test suite)

---

## 1. Summary & Goal

PTY-008 adds a B2B org-account helper layer to `app/services/party.py`, gated by
`S.party_crm_org_accounts_enabled`. It introduces four service-level functions:

| Function | Purpose |
|---|---|
| `create_org_account(name, *, owner_user_sub, correlation_id=None) -> dict` | Atomic single-call provisioning of a PARTY_GROUP party + CUSTOMER + BILL_TO roles + EMPLOYMENT/OWNER relationship to the owner's PERSON party, with the ORG_ADMIN role on that relationship's from-party |
| `add_member(org_party_id, actor_party_id, member_party_id, role_type) -> dict` | Add a PERSON party as a GROUP_MEMBER of the org; actor must hold ORG_ADMIN on the org |
| `remove_member(org_party_id, actor_party_id, member_party_id) -> None` | Remove a GROUP_MEMBER relationship; actor must hold ORG_ADMIN on the org |
| `list_members(org_party_id) -> list[dict]` | Return all GROUP_MEMBER relationships with each member's org-scoped role |

Together they implement the OFBiz Party Manager B2B org concept on the existing `party`
single-table, reusing only the PTY-005 role functions and PTY-006 relationship functions already
on that table. No new DynamoDB tables or GSIs are introduced. With the sub-flag off
(`S.party_crm_org_accounts_enabled=False`) all four service functions are never called through
the normal request path and the party table is untouched by org operations.

### 2.5 Deterministic-id idempotency pattern

`app/services/commerce_order_service.py:67` establishes the deterministic-ID derivation
pattern (hash-only; no conditional write):

```python
order_id = hashlib.sha256(corr.encode("utf-8")).hexdigest()[:32]
```

PTY-004 extends this with a `put_item` using `ConditionExpression="attribute_not_exists(PK)"`.
On `ConditionalCheckFailedException` the existing row is returned and no audit event is
emitted (`docs/ofbiz/specs/PTY-004.md:422-428`). Note: `commerce_order_service.py` itself does
**not** use `attribute_not_exists` — the full idempotent pattern is introduced by PTY-004.

`create_org_account` accepts an optional `correlation_id`. When supplied, the PARTY_GROUP's
`party_id` is derived as `hashlib.sha256(correlation_id.encode()).hexdigest()[:32]`, and the
entire provisioning sequence is re-entrant: if the PARTY_GROUP row already exists the function
fetches and returns it without re-running role or relationship writes.

## 3. Data Model

PTY-008 introduces **no new DynamoDB tables, no new GSIs, and no schema changes**. It writes
only rows already covered by the `party` table's existing SK namespace (established by
PTY-004 through PTY-007). All new rows use the key schema defined in PTY-002:

```
PK  STRING hash key
SK  STRING range key
```

With four GSIs: `GSI1` (role lookup), `GSI2` (contact-mech reverse lookup), `GSI3` (inbound
relationship mirror / owner lookup), `GSI_CREATED` (type / created_at numeric sort key).

### 3.1 Rows written by `create_org_account`

A single call to `create_org_account("Acme Corp", owner_user_sub="usr_abc")` that creates a
new org produces the following rows on `T.party`:

#### (a) PARTY_GROUP META row

```
PK  = "PARTY#{org_party_id}"
SK  = "META"
```

Full item:

```json
{
  "PK":           "PARTY#{org_party_id}",
  "SK":           "META",
  "party_id":     "{org_party_id}",
  "party_type":   "PARTY_GROUP",
  "status":       "active",
  "name":         "Acme Corp",
  "created_at":   1749200000,
  "updated_at":   1749200000,
  "type":         "TYPE#PARTY_GROUP",
  "GSI_CREATED":  "TYPE#PARTY_GROUP"
}
```

Notes:
- `name` is a plain string attribute — the only addition PTY-008 makes to the base
  `create_party` shape. The PTY-004 `create_party` function does not accept a `name`
  argument; PTY-008 passes it by calling `T.party.update_item` after `create_party`
  (or by inlining the name in its own `put_item` — see §4.1).
- `type = "TYPE#PARTY_GROUP"` and the numeric `created_at` on `GSI_CREATED` follow the
  PTY-004 conventions for `list_parties(party_type="PARTY_GROUP")` to work.

#### (b) CUSTOMER role row

```
PK  = "PARTY#{org_party_id}"
SK  = "ROLE#CUSTOMER"
```

Written by `add_role(org_party_id, "CUSTOMER")` per PTY-005 conventions.

#### (c) BILL_TO role row

```
PK  = "PARTY#{org_party_id}"
SK  = "ROLE#BILL_TO"
```

Written by `add_role(org_party_id, "BILL_TO")`.

#### (d) EMPLOYMENT/OWNER relationship (primary row, under owner's partition)

```
PK  = "PARTY#{owner_person_party_id}"
SK  = "REL#OWNER#{org_party_id}"
```

Written by `create_relationship(owner_person_party_id, org_party_id, "OWNER")`.  
Full item shape follows `docs/ofbiz/specs/PTY-006.md:3.1`.

#### (e) EMPLOYMENT/OWNER mirror row (under org's partition)

```
PK  = "PARTY#{org_party_id}"
SK  = "MIRROR#OWNER#{owner_person_party_id}"
```

Written atomically with (d) by `create_relationship` via `transact_write_items`.

#### (f) ORG_ADMIN role row on owner

```
PK  = "PARTY#{owner_person_party_id}"
SK  = "ROLE#ORG_ADMIN"
```

Wait — the ticket says the owner is linked "with the `ORG_ADMIN` role". Per the OFBiz model,
`ORG_ADMIN` is a role on the PERSON party in the context of the org, not a global role on
the party. Since the `party` table's role rows (`PK=PARTY#{id}`, `SK=ROLE#{type}`) are
global to the party (PTY-005's design), a global `ORG_ADMIN` role on the owner's PERSON
would grant them ORG_ADMIN on *all* orgs they belong to. To support per-org ORG_ADMIN,
the role is stored on the `GROUP_MEMBER` relationship row's `role_type` attribute rather than
as a standalone `ROLE#` row. See §4.1 for the resolution.

## 4. API / Service Design

### 4.1 Service functions in `app/services/party.py`

Four new public functions and one private helper are appended after the PTY-007 contact-mech
functions.

#### `_assert_org_admin` — private guard

```python
def _assert_org_admin(org_party_id: str, actor_party_id: str) -> None:
    """Raise HTTPException(403) if actor_party_id does not hold ORG_ADMIN on org_party_id.

    ORG_ADMIN is stored as org_role="org_admin" on the GROUP_MEMBER relationship row
    (or on the OWNER relationship row for the org creator). This function checks the
    actor's membership relationship for the org_role attribute.
    """
    resp = T.party.get_item(
        Key={
            "PK": f"PARTY#{actor_party_id}",
            "SK": f"REL#GROUP_MEMBER#{org_party_id}",
        }
    )
    item = resp.get("Item")
    if not item:
        # Also check OWNER relationship (the org creator)
        resp2 = T.party.get_item(
            Key={
                "PK": f"PARTY#{actor_party_id}",
                "SK": f"REL#OWNER#{org_party_id}",
            }
        )
        item = resp2.get("Item")
    if not item or item.get("org_role") not in ("org_admin", "owner"):
        raise HTTPException(403, "org_admin role required")
```

#### `create_org_account`

Full signature:

```python
def create_org_account(
    name: str,
    *,
    owner_user_sub: str,
    correlation_id: Optional[str] = None,
) -> Dict[str, Any]:
```

Step-by-step contract:

1. **Validate `name`:** strip whitespace; reject empty string or length > 256 with
   `HTTPException(422, "name_required")` / `HTTPException(422, "name_too_long")`.

2. **Derive `org_party_id`:**
   - If `correlation_id`: `org_party_id = hashlib.sha256(correlation_id.encode()).hexdigest()[:32]`
   - Else: `org_party_id = uuid.uuid4().hex`

3. **Idempotency check:** attempt `T.party.put_item` with the PARTY_GROUP META item and
   `ConditionExpression="attribute_not_exists(PK)"`. On `ConditionalCheckFailedException`
   fetch the existing META row via `get_party(org_party_id)` and return it (no further writes,
   no audit event).

4. **Write PARTY_GROUP META row** with `name` stored directly as `item["name"]`. The
   `create_party(party_type="PARTY_GROUP", ...)` PTY-004 call does not accept `name`, so
   PTY-008 either (a) calls `create_party` then `update_item` to add `name`, or (b) inlines
   its own `put_item` that mirrors the PTY-004 schema and adds `name`. **Chosen approach (b):**
   inline `put_item` — avoids a second round-trip and keeps the idempotency condition atomic
   with the full item shape. The inlined schema must exactly match the PTY-004 conventions
   (`type`, `GSI_CREATED` keys, numeric `created_at`).

5. **Ensure PERSON party for owner:** call `get_party` to resolve the owner's PERSON
   `party_id`. This function does not call `ensure_person_party` (PTY-010) directly to avoid
   a hard dependency — instead it accepts `owner_user_sub` and resolves the party via
   `GSI3` (`GSI3PK=OWNER#{owner_user_sub}`). If no PERSON party is found, raise
   `HTTPException(404, "owner_person_party_not_found")` — the caller must create a PERSON
   party first (via `create_party(party_type="PERSON", user_sub=owner_user_sub)` or
   `ensure_person_party` from PTY-010 when available). See §10 — Open Question #1.

6. **Assign CUSTOMER role** on the org: `add_role(org_party_id, "CUSTOMER")` (idempotent).

7. **Assign BILL_TO role** on the org: `add_role(org_party_id, "BILL_TO")` (idempotent).

8. **Create OWNER relationship** from owner PERSON → org PARTY_GROUP:
   `create_relationship(owner_person_party_id, org_party_id, "OWNER", correlation_id=f"{org_party_id}:owner")`.
   The `correlation_id` suffix makes this relationship idempotent across retries.

9. **Write ORG_ADMIN org_role onto the OWNER relationship row:** after `create_relationship`
   returns, call `T.party.update_item` to set `org_role = "owner"` on the primary relationship
   row `PK=PARTY#{owner_person_party_id}`, `SK=REL#OWNER#{org_party_id}`.

10. **Emit audit event:**
    ```python
    audit_event(
        "party_org_account_created",
        owner_user_sub,
        None,
        org_party_id=org_party_id,
        name=name,
        owner_person_party_id=owner_person_party_id,
    )
    ```

11. **Return** the PARTY_GROUP META dict (caller populates `CrmOrgAccountOut` from it).

#### `add_member`

Full signature:

```python
def add_member(
    org_party_id: str,
    actor_party_id: str,
    member_party_id: str,
    role_type: str = "member",
) -> Dict[str, Any]:
```

Step-by-step contract:

1. **Validate `role_type`:** must be one of `{"member", "admin", "org_admin"}`.
   Raise `HTTPException(422, "invalid_org_role")` otherwise.

2. **Assert actor is ORG_ADMIN:** call `_assert_org_admin(org_party_id, actor_party_id)`.
   Raises `HTTPException(403)` if not.

3. **Verify org PARTY_GROUP exists:** `get_party(org_party_id)` — raise
   `HTTPException(404, "org_not_found")` if absent or if `party_type != "PARTY_GROUP"`.

4. **Reject self-membership:** `member_party_id != org_party_id` (a PARTY_GROUP cannot be
   a member of itself). Raise `HTTPException(422, "self_membership_not_allowed")`.

5. **Idempotency — existing membership check:** call `T.party.get_item(Key={"PK":
   f"PARTY#{member_party_id}", "SK": f"REL#GROUP_MEMBER#{org_party_id}"})`. If the row
   exists, return it unchanged (no duplicate audit event).

6. **Create GROUP_MEMBER relationship:**
   `rel = create_relationship(member_party_id, org_party_id, "GROUP_MEMBER")`.

7. **Write `org_role` onto the primary relationship row:** `T.party.update_item(Key={"PK":
   f"PARTY#{member_party_id}", "SK": f"REL#GROUP_MEMBER#{org_party_id}"},
   UpdateExpression="SET org_role = :r", ExpressionAttributeValues={":r": role_type})`.

8. **Emit audit event:**
   ```python
   audit_event(
       "party_org_member_added",
       actor_party_id,
       None,
       org_party_id=org_party_id,
       member_party_id=member_party_id,
       role_type=role_type,
   )
   ```

9. **Return** the updated relationship dict (with `org_role` set).

#### `remove_member`

Full signature:

```python
def remove_member(
    org_party_id: str,
    actor_party_id: str,
    member_party_id: str,
) -> None:
```

Step-by-step contract:

1. **Assert actor is ORG_ADMIN:** `_assert_org_admin(org_party_id, actor_party_id)`.

2. **Reject self-remove of the org's sole owner:** check whether `member_party_id` holds
   an `OWNER` relationship to the org (`T.party.get_item(Key={"PK":
   f"PARTY#{member_party_id}", "SK": f"REL#OWNER#{org_party_id}"})`). If so, raise
   `HTTPException(409, "cannot_remove_org_owner")` — same semantics as
   `app/services/org_service.py:359-361`.

3. **Delete GROUP_MEMBER relationship:** `delete_relationship(member_party_id, org_party_id,
   "GROUP_MEMBER")` (no-op if the relationship does not exist — PTY-006 semantics).

4. **Emit audit event:**
   ```python
   audit_event(
       "party_org_member_removed",
       actor_party_id,
       None,
       org_party_id=org_party_id,
       member_party_id=member_party_id,
   )
   ```

#### `list_members`

Full signature:

```python
def list_members(
    org_party_id: str,
    *,
    cursor: Optional[str] = None,
    limit: int = 50,
) -> Dict[str, Any]:
```

Implementation strategy:

- Query `GSI3` with `GSI3PK = "REL_TO#{org_party_id}"` and
  `GSI3SK begins_with "REL#GROUP_MEMBER#"`. This returns all mirror rows for
  GROUP_MEMBER relationships pointing *to* the org, giving the inbound membership view.
  The `from_party_id` attribute on each mirror row is the member's PERSON party_id.
- Apply pagination using `encode_cursor` / `decode_cursor` from `app/core/cursor.py`
  (same pattern as `app/services/license_agreements.py:20,268,298`).
- Each mirror row already carries `from_party_id`, `to_party_id`, `relationship_type`,
  `rel_id`, `created_at`. The `org_role` attribute is on the **primary** row
  (`PK=PARTY#{member}`, `SK=REL#GROUP_MEMBER#{org}`), not the mirror. After fetching the
  mirror list, fetch `org_role` for each member via `BatchGetItem` on the primary keys.
- Return `{"members": [...], "next_cursor": str | None, "count": int}`.

The `BatchGetItem` step adds one extra DDB call per page of results. For Phase 1 this is
acceptable given typical org sizes (< 100 members). A future optimisation could denormalise
`org_role` onto the mirror row at write time — deferred (see §10 — Open Question #2).

## 5. Detailed Behavior & Edge Cases

### 5.1 `create_org_account` replay safety

Each step in the provisioning sequence is idempotent:

1. `put_item` with `attribute_not_exists(PK)` → no-op on second call.
2. `add_role(org_party_id, "CUSTOMER")` → PTY-005 `add_role` uses `put_item` idempotency.
3. `add_role(org_party_id, "BILL_TO")` → same.
4. `create_relationship(owner_person_party_id, org_party_id, "OWNER", correlation_id=...)` →
   PTY-006 uses `transact_write_items` with `attribute_not_exists` condition → idempotent.
5. `update_item` for `org_role="owner"` on the OWNER relationship row → sets the same value;
   idempotent at the attribute level.

If the process crashes between steps (e.g. after the PARTY_GROUP write but before the CUSTOMER
role write), the next call detects the existing PARTY_GROUP via the `ConditionalCheckFailedException`
path and returns the existing row. The CUSTOMER and BILL_TO role writes are therefore not re-applied
on replay. This means a partial crash between steps 4 and 7 leaves the org without roles.

**Resolution:** For Phase 1, the idempotency guard (step 3) is placed at step 1 (PARTY_GROUP write).
A full replay (where `correlation_id` is the same) therefore re-runs steps 5-9 if the PARTY_GROUP
already existed, ensuring roles and relationships are re-applied to convergence. The service
does **not** early-return on the idempotency check; instead it fetches the existing PARTY_GROUP
and continues with steps 5 onward. Only duplicate role/relationship writes are skipped (by the
underlying PTY-005/PTY-006 idempotency). This is the correct convergent-write pattern.

Specifically: the `ConditionalCheckFailedException` handler fetches the existing row and then
**continues execution** through steps 5-9 (not returning early). An early return would leave
the org in an incompletely-provisioned state if the crash occurred after the PARTY_GROUP write
but before the roles/relationships were written.

### 5.2 ORG_ADMIN authorization check design

The `ORG_ADMIN` check is scoped per-org, not global. It is implemented by inspecting the
`org_role` attribute on the actor's GROUP_MEMBER or OWNER relationship row to the specific org:

- Actor is org creator → `PK=PARTY#{actor}`, `SK=REL#OWNER#{org}`, `org_role="owner"` → allowed.
- Actor is an added member with `role_type="org_admin"` → `PK=PARTY#{actor}`,
  `SK=REL#GROUP_MEMBER#{org}`, `org_role="org_admin"` → allowed.
- Actor has `role_type="member"` or `role_type="admin"` → `org_role` is `"member"` or
  `"admin"` → denied with 403.
- Actor has no relationship to the org → `get_item` returns no `Item` → denied with 403.

This mirrors the `assert_org_membership` pattern in `app/services/org_service.py:165-171`.

### 5.3 Non-ORG_ADMIN member cannot mutate

`add_member` and `remove_member` call `_assert_org_admin` before performing any write.
The `list_members` function does not require ORG_ADMIN (read-only, equivalent to
`list_members` in `app/services/org_service.py:221-226` which requires only `min_role="viewer"`).

### 5.4 Cannot remove org owner

Removing the org owner (the PERSON party holding an `OWNER` relationship to the org) is
rejected with `HTTPException(409, "cannot_remove_org_owner")`. This matches
`app/services/org_service.py:359-361` ("Cannot remove the org owner. Transfer ownership first.").
PTY-008 does not implement ownership transfer; that is a future milestone.

### 5.5 `_resolve_person_party` router helper

The router must translate `ctx["user_sub"]` (the authenticated user's `user_sub` string) into
a PERSON `party_id` for the `actor_party_id` argument to service functions. This lookup queries
`GSI3` with `GSI3PK = "OWNER#{user_sub}"` and returns the first matching party_id. If no
PERSON party exists, the router raises `HTTPException(404, "person_party_not_found_for_user")`.
This helper is a private function in `app/routers/party.py` (not in the service layer, since it
involves HTTP-layer concerns).

### 5.6 `list_members` ordering

`GSI3` rows are ordered by `GSI3SK` string (lexicographic) within a `GSI3PK` partition.
`GSI3SK = "REL#GROUP_MEMBER#{member_party_id}"` — ordering is by member `party_id` (hex32),
which is effectively random. Strict `created_at`-ordered member listing would require a
`created_at`-sorted GSI — deferred (see §10 — Open Question #2).

### 5.7 `member_count` in `CrmOrgAccountOut`

`CrmOrgAccountOut.member_count` is derived at query time by calling `list_members` and
counting the results. For `GET /ui/party/orgs/{org_party_id}`, the router calls `list_members`
with `limit=1000` (practical cap for Phase 1). An alternative is to maintain a denormalised
counter on the PARTY_GROUP META row (updated by `add_member` / `remove_member` via atomic
`update_item` increment/decrement) — deferred as a performance optimisation (§10 — Open
Question #3).

### 5.8 `add_member` for existing member

If `member_party_id` already has a `GROUP_MEMBER` relationship to `org_party_id`, `add_member`
detects the existing row in step 5 and returns it unchanged (no duplicate write, no audit event).
The `org_role` is NOT updated if the member already exists — callers must use a separate
`update_member_role` function (not in PTY-008 scope) to change an existing member's role.

### 5.9 Flag-off behaviour

With `S.party_crm_org_accounts_enabled=False` (the default):
- All five PTY-012 router endpoints return HTTP 503.
- `T.party` is never written by org-account code.
- `app/services/org_service.py`, `T.organizations`, `T.billing`, `T.shopping_cart`, and all
  other existing subsystems are byte-for-byte unchanged.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

There is no `S.dev_mode` branch in `app/services/party.py`. All DynamoDB operations
(`put_item`, `update_item`, `get_item`, `query`) work identically in dev (DynamoDB Local at
`http://localhost:8001`) and in prod (real DynamoDB). The `T.party` handle inherits the correct
endpoint from `app/core/tables.py` via `_safe_table(S.party_table_name)`. The `transact_write_items`
calls made by `create_relationship` / `delete_relationship` (PTY-006) use `_ddb_client()` which
derives the endpoint from the shared `ddb` resource (`app/services/party.py:_ddb_client()`).
No mock branch or `if S.dev_mode` path is needed.

### Idempotency

`create_org_account` with the same `correlation_id` converges to the same final state on
repeated calls. The idempotency guard is at step 3 (PARTY_GROUP `put_item`) — see §5.1 for
the convergent-write strategy. `add_member` is idempotent at the membership level (existing
membership check in step 5). `remove_member` is idempotent by PTY-006 `delete_relationship`
semantics (no-op on non-existent rows).

No application-level TOCTOU window exists for `create_org_account` because the PARTY_GROUP
write uses a conditional `attribute_not_exists(PK)` at the DynamoDB layer. Concurrent calls
with the same `correlation_id` will see exactly one succeed and the rest return the existing
row.

### Security

- **No PII in DynamoDB keys.** All PK/SK values contain only `party_id` (32-char hex),
  `relationship_type` (uppercase ASCII enum), and static prefixes. `name` is stored as a
  plain attribute on the META row, not in any key or GSI value.
- **ORG_ADMIN is per-org, not global.** The `org_role` attribute on the relationship row
  scopes the ORG_ADMIN privilege to a specific org. A user cannot gain ORG_ADMIN on one org
  by being ORG_ADMIN on another.
- **No money-out path.** PTY-008 assigns billing roles (`BILL_TO`) to the org party for
  downstream use by the order/billing subsystems, but it does not initiate any payment
  or ledger entry. The billing ledger (`app/services/billing_shared.py:224` —
  `new_ledger_entry`) is untouched by PTY-008.
- **Input validation.** `name` is length-validated (max 256). `org_party_id`, `actor_party_id`,
  `member_party_id` are capped at 64 chars (inherited from PTY-006's SK-injection guard) before
  use in DynamoDB keys. `role_type` is validated against a static allowlist.
- **Audit trail.** Every successful `create_org_account`, `add_member`, and `remove_member`
  emits an `audit_event` to `T.alerts` via `app/services/alerts.py:644`.

## 10. Open Questions / Assumptions

1. **Owner's PERSON party must pre-exist.** The spec assumes the caller creates or resolves a
   PERSON party for `owner_user_sub` before calling `create_org_account`. PTY-010
   (`ensure_person_party`) provides the idempotent creation path, but PTY-008 is in Milestone 3
   and PTY-010 is in Milestone 4. For Phase 1, `create_org_account` raises 404 if no PERSON
   party is found for the owner. The PTY-012 router will call PTY-010's `ensure_person_party`
   first when PTY-010 is available, or require the caller to pre-create the PERSON party.

2. **`org_role` denormalisation onto mirror row.** Currently `list_members` requires a
   `BatchGetItem` to fetch `org_role` from each member's primary relationship row after
   querying the GSI3 mirror rows. A simpler approach would denormalise `org_role` onto the
   mirror row at write time (`add_member` calls `update_item` on both the primary and mirror
   rows). Deferred: for Phase 1, the `BatchGetItem` approach is correct and performs acceptably
   for expected org sizes (< 100 members).

3. **`member_count` maintenance.** `CrmOrgAccountOut.member_count` is computed at query time
   by counting `list_members` results rather than maintaining a counter on the META row. This
   is correct but costs one extra DDB query per `GET /ui/party/orgs/{id}`. A denormalised
   `member_count` counter (updated by atomic `update_item` on `add_member` / `remove_member`)
   would be more efficient. Deferred for Phase 1.

4. **Multiple orgs per PERSON party.** A single PERSON party can be ORG_ADMIN on multiple
   orgs (multiple `REL#OWNER#` or `REL#GROUP_MEMBER#` rows with `org_role="org_admin"` across
   different org_party_ids). The `_assert_org_admin` check is correctly scoped per-org by
   fetching the specific `SK=REL#GROUP_MEMBER#{org_party_id}` or `SK=REL#OWNER#{org_party_id}`
   row — no risk of cross-org privilege escalation.

5. **`GET /ui/party/orgs` scope.** The list endpoint returns orgs where the authenticated user
   is a member (either as owner or GROUP_MEMBER). This requires querying GSI3 with
   `GSI3PK="REL_TO#{actor_person_party_id}"` and `GSI3SK begins_with "REL#OWNER#"` or
   `"REL#GROUP_MEMBER#"`, then resolving the PARTY_GROUP META for each. Alternatively, the
   router queries `GSI_CREATED` with `type="TYPE#PARTY_GROUP"` and filters in Python — but
   this scales poorly. The GSI3-based approach is correct but requires knowing `actor_person_party_id`
   (resolved via `_resolve_person_party`). This resolution is assumed to work; the edge case
   where `_resolve_person_party` returns no match will 404 (user has no PERSON party).

6. **Ownership transfer deferred.** PTY-008 does not implement transferring org ownership from
   one PERSON party to another. The only guard for this scenario is `remove_member` rejecting
   removal of the org owner. A `transfer_ownership` function (updating `org_role` on the old
   OWNER relationship row to `"member"` and creating a new OWNER relationship for the new
   owner) is out of scope for Phase 1.

7. **`CrmOrgAccountOut.roles` population.** The `roles` field lists the org's party roles
   (CUSTOMER, BILL_TO). The router populates this by calling `list_roles(org_party_id)` and
   coercing to `CrmPartyRoleOut`. This is an extra DDB query per `GET /ui/party/orgs/{id}`
   but is bounded (orgs have at most a few roles in Phase 1).

8. **`create_org_account` writes `name` on the PARTY_GROUP META row.** PTY-004's `create_party`
   does not accept a `name` argument. PTY-008 either (a) calls `create_party` then
   `update_item`, or (b) inlines its own `put_item`. The spec recommends (b) to make the
   idempotency condition atomic with the full item. The implementer must ensure the inlined
   item schema exactly matches PTY-004's META row shape (including `type`, `GSI_CREATED`
   keys, numeric `created_at`) so that `list_parties(party_type="PARTY_GROUP")` continues
   to work via the `GSI_CREATED` index.
