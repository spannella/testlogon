# FXA-014 — Frontend types & endpoint wrappers

## 1. Summary & Goal

FXA-014 is the sole frontend deliverable before the admin UI page (FXA-015). It has two outputs:

1. **TypeScript interface declarations** added to `frontend/src/api/types.ts` that exactly mirror the backend Pydantic models introduced by FXA-004 (`FixedAssetIn`, `FixedAssetPatchIn`, `FixedAssetOut`, `FixedAssetListOut`, `FixedAssetDisposeIn`, `DepreciationPeriodOut`, `DepreciationScheduleOut`, `MaintenanceOrderIn`, `MaintenanceOrderTransitionIn`, `MaintenanceOrderOut`, `MaintenanceOrderListOut`).
2. **Endpoint wrapper functions** in a new file `frontend/src/api/endpoints/fixedAssets.ts` that call every HTTP endpoint exposed by FXA-007 (`/ui/fixed-assets`) and FXA-013 (`/ui/fixed-assets/{id}/work-orders`, `/ui/fixed-assets/work-orders`), using the shared `api` client from `frontend/src/api/client.ts`.

The deliverable is strictly additive. No existing source file is modified beyond appending new `export interface` blocks to `frontend/src/api/types.ts`. With `VITE_FIXED_ASSETS_ENABLED=false` (the default) the new file is never imported by any active UI path, so existing shop/cart/orders/billing behavior is unchanged. A TypeScript build (`tsc --noEmit`) must pass with the new types in place.

### 2.2 Existing `OkResp` and `PaginatedList<T>` shared types

`OkResp` at `frontend/src/api/types.ts:2941` is `{ ok: boolean }`. `PaginatedList<T>` at `frontend/src/api/types.ts:2209` is `{ items: T[]; next_token?: string }`. Purpose-built list interfaces (`FixedAssetListOut`, `MaintenanceOrderListOut`) are declared locally in the section, following the same pattern used by `InventoryLowStockResp` at `frontend/src/api/types.ts:2174` (which also declares its own list shape rather than reusing a generic).

### 2.3 Shared `api` client

`frontend/src/api/client.ts` exports a typed `api` function with convenience shorthands:
- `api.get<T>(path, params?)` — GET, query params as `Record<string, string>`.
- `api.post<T>(path, body?, params?)` — POST, body JSON-serialized.
- `api.patch<T>(path, body?)` — PATCH.
- `api.del<T>(path, params?)` — DELETE.

The client automatically reads the `ui_csrf` cookie and attaches it as `X-CSRF-Token` on every request (`frontend/src/api/client.ts:179–181`). Callers never need to set the CSRF header manually. Non-GET mutations (POST, PATCH, DELETE) therefore satisfy the CSRF requirement from FXA-014's acceptance criteria without any special handling in the endpoint wrapper file.

### 2.4 Pattern for endpoint wrapper files

`frontend/src/api/endpoints/inventory.ts` is the canonical reference:
- Single import: `import { api } from "@/api/client"`.
- Named type imports: `import type { InventoryRecord, ... } from "@/api/types"`.
- One `export const` arrow function per endpoint.
- Optional query params accumulated into a `Record<string, string>` local variable before being passed to `api.get`.
- File is flag-gated in comments only; the server-side 503/404 handles runtime gating.

`frontend/src/api/endpoints/tickets.ts` demonstrates the pattern for endpoints with optional multi-param filtering (e.g. `listTickets` at `frontend/src/api/endpoints/tickets.ts:93–107`) and the POST transition pattern (e.g. `setTicketStatus` at `frontend/src/api/endpoints/tickets.ts:117–118` — uses `api.post`, not `api.patch`).

## 3. Data Model

FXA-014 introduces no DynamoDB tables and no new backend objects. All persistent state is owned by FXA-003/FXA-005/FXA-012. This section documents only the TypeScript-side shape of the data and how it maps to the backend DynamoDB attributes through the JSON API layer.

### 3.1 Numeric fields

All money fields (`acquisition_cost_cents`, `salvage_value_cents`, `accumulated_depreciation_cents`, `net_book_value_cents`, `cost_cents`, `proceeds_amount_cents`, `amount_cents`) are declared as TypeScript `number`. The backend stores them as DynamoDB `N` type, the service coerces them to Python `int`, and FastAPI serializes them as JSON numbers — no `string`-encoded cents on this API. This differs from Stripe amounts which some other endpoints handle as strings; Fixed Assets uses plain `number` throughout.

All timestamp fields (`acquired_at`, `created_at`, `updated_at`, `period_start_ts`, `period_end_ts`, `posted_at`, `scheduled_for`, `completed_at`) are Unix epoch integers declared as `number` in TypeScript, consistent with `InventoryRecord.updated_at: number` at `frontend/src/api/types.ts:2171` and `MaintenanceOrderOut.created_at: int` in `docs/ofbiz/specs/FXA-004.md:357`.

### 3.2 Status literal unions

Rather than plain `string` (which risks silent typos in UI code), the `Out` interface uses TypeScript union literals for status fields:

- `FixedAsset.status`: `"active" | "fully_depreciated" | "disposed"`
- `DepreciationPeriod.schedule_status`: `"scheduled" | "posted" | "cancelled"`
- `MaintenanceOrder.wo_status`: `"open" | "in_progress" | "completed" | "cancelled"`

The backend `Out` models declare these as plain `str` (no Pydantic `Literal`) since they are output-only fields; the frontend tightening to a union literal is safe and benefits type-checking without being a breaking change.

### 3.3 `net_book_value_cents` — derived field

`FixedAssetOut.net_book_value_cents` is computed server-side by the `model_validator(mode="after")` on `FixedAssetOut` (`docs/ofbiz/specs/FXA-004.md:223–227`). It is always present in the JSON response. The TypeScript interface declares it as a non-optional `number`.

### 3.4 GL account ID fields

Four optional GL account ID strings on `FixedAssetOut` (`gl_asset_account_id`, `gl_accum_depr_account_id`, `gl_depr_expense_account_id`, `gl_gain_loss_account_id`) are declared as `string | null` — they are `null` until FXA-008 seeds the accounts and the asset is registered with defaults. Existing assets created before FXA-008 runs will have `null` values in these fields.

## 5. Detailed Behavior & Edge Cases

### 5.1 CSRF handling

The `api` client reads `document.cookie` for the `ui_csrf` cookie on every call and sets `X-CSRF-Token` automatically (`frontend/src/api/client.ts:179–181`). All POST and PATCH wrappers in `fixedAssets.ts` go through `api.post` and `api.patch`, so they unconditionally attach the CSRF header. No extra header wiring is needed in the endpoint wrapper file. The acceptance criterion "endpoint wrappers send the CSRF header on non-GET calls" is satisfied by this shared mechanism.

### 5.2 `encodeURIComponent` on path parameters

`assetId` values are SHA-256 hex strings (32 lowercase hex characters) — they contain only `[0-9a-f]` and never require percent-encoding. `workOrderId` follows the same pattern. Nevertheless, `encodeURIComponent` is applied to both for defense-in-depth, matching the pattern in `removeTicketSpaceMember` at `frontend/src/api/endpoints/tickets.ts:142`. This prevents breakage if the ID generation scheme ever changes.

### 5.3 `listAssets` — optional parameters

All four query params (`owner_sub`, `status`, `limit`, `cursor`) are optional. The backend applies no filter when a param is absent (`owner_sub=null` → all assets visible to the caller's admin session; `status=null` → all statuses). Passing `undefined` for an optional string produces no entry in the `params` object, so the backend receives no query string entry for that param. This is consistent with `listTickets` at `frontend/src/api/endpoints/tickets.ts:93–107`.

### 5.4 `listWorkOrders` vs `listWorkOrderQueue`

Two distinct wrappers list work orders:
- `listWorkOrders(assetId, opts?)` — scoped to a single asset, paginated. Calls `GET /ui/fixed-assets/{assetId}/work-orders`. Used by the per-asset drawer (FXA-015).
- `listWorkOrderQueue(opts?)` — cross-asset queue, filterable by status. Calls `GET /ui/fixed-assets/work-orders`. Used by the open-WO queue tab (FXA-015). The `status` param accepts `"open" | "in_progress"` only (the queue is for actionable orders; `completed`/`cancelled` are retrievable from the per-asset list).

The naming disambiguation prevents FXA-015 from accidentally calling the wrong endpoint when rendering the queue tab vs. the per-asset drawer.

### 5.5 `disposeAsset` — conditional proceeds fields

The `FixedAssetDisposeIn` interface declares `proceeds_payment_intent_id` as `string | null` (a Stripe PaymentIntent id) and `proceeds_amount_cents` as `number | null`. The backend model validator requires they co-occur (`docs/ofbiz/specs/FXA-004.md:257–270`). The TypeScript interface does not encode this co-occurrence constraint (TypeScript has no built-in XOR-optional type that is ergonomic). The FXA-015 form component must validate this pair before calling `disposeAsset`, or rely on the 422 from the server. Both are acceptable; documenting the dependency here so FXA-015 can add a form-level error.

### 5.6 503 on flag-off

When `FIXED_ASSETS_ENABLED=false`, all endpoints return HTTP 503 with `detail="Fixed assets module is not enabled"`. The `api` client's error handler (`frontend/src/api/client.ts:269–276` — the `!res.ok` branch) throws an `ApiError` with `status=503` and `detail` from the response body. React Query's `useQuery`/`useMutation` will surface this as a query error. The FXA-015 page should catch this and show an appropriate disabled state, but that is outside the scope of FXA-014. The wrappers themselves pass through the error unchanged.

### 5.7 TypeScript build validity

After FXA-014 is merged, `tsc --noEmit` (or `vite build`) must pass with zero new type errors. The acceptance criterion "types compile and match the backend response shapes" is verified by:

1. Running `cd frontend && npx tsc --noEmit` — no new errors.
2. Importing from `fixedAssets.ts` in a test file that calls every wrapper with correctly-typed arguments — no implicit `any` values.

The file uses only `string`, `number`, `boolean`, and union literals — no `any`, no type assertions, no `as unknown as`. The `opts?` parameter objects use optional property syntax so callers can pass no arguments without type errors.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

FXA-014 introduces no backend code and no DynamoDB I/O. There is therefore no dev/prod code-path divergence introduced by this ticket. The backend endpoints being wrapped already satisfy SECOPS-007 parity per their own specs (FXA-007, FXA-013).

### 7.2 CSRF

Covered in §5.1. The shared `api/client.ts` mechanism is the single enforcement point — no wrapper-level duplication.

### 7.3 No client-side secrets

`fixedAssets.ts` contains no API keys, no credentials, and no secrets. All auth flows through the existing cookie/Bearer machinery in `api/client.ts`.

### 7.4 Input exposure

`FixedAssetIn` and `MaintenanceOrderIn` accept only the fields the backend model accepts. TypeScript's structural typing means callers cannot accidentally send extra fields that would be ignored or cause issues server-side — only the declared fields appear in the serialized JSON body.

### 7.5 Money field representation

All money fields are plain integers (cents). There is no float arithmetic in the wrapper layer. Callers must supply integer values; the TypeScript type is `number` (not `integer`, which TypeScript does not have), so the enforcement is by convention and documentation rather than type system. A future lint rule (`no-restricted-syntax` on non-integer literals for `*_cents` params) is outside the scope of FXA-014 but is a sensible follow-up.

## 10. Open Questions / Assumptions

1. **`FixedAssetOut` `updated_at` field**: The FXA-004 spec lists `updated_at: int = 0` on `FixedAssetOut` (`docs/ofbiz/specs/FXA-004.md:203`). `MaintenanceOrderOut` gains `updated_at: int` via the FXA-012 data-model spec (`docs/ofbiz/specs/FXA-012.md:182` — section 3, not section 4.1). Both interfaces in FXA-014 include `updated_at: number`. Note that `MaintenanceOrderOut` as defined in FXA-004 (`docs/ofbiz/specs/FXA-004.md:349–374`) does NOT include `updated_at`; the field is added by FXA-012 (`docs/ofbiz/specs/FXA-012.md:182`). If FXA-012 is not yet merged when FXA-014 is implemented, the `MaintenanceOrder` TS interface must still include `updated_at: number` in anticipation of FXA-012.

2. **`DepreciationScheduleOut` ordering**: FXA-007 acceptance criterion says "newest-or-oldest-first per spec" but does not canonicalize order (`docs/ofbiz/specs/FXA-007.md:147`). The TypeScript `DepreciationPeriod[]` array accepts either order. The UI (FXA-015) should sort by `period` ascending before rendering; this is a display concern, not a type concern.

3. **`listWorkOrderQueue` status param scope**: The FXA-013 acceptance criterion says "returns only open/in-progress orders" (`FIXED_ASSETS_TICKETS.md:269`). The spec assumes the queue endpoint accepts a `status` query param to allow the UI to filter between `open` and `in_progress`. If the backend implementation hard-codes the filter to `open|in_progress` with no param, the `opts?.status` param in `listWorkOrderQueue` is harmlessly ignored by the server and causes no error.

4. **`FixedAssetIn.depreciation_method` optional vs. required**: The backend `FixedAssetIn` has `depreciation_method: Literal["straight_line"] = "straight_line"` with a default, so the field is optional. The TypeScript `FixedAssetIn` marks it `depreciation_method?: DepreciationMethod`. If a future ticket adds `"declining_balance"` as a second literal, both the TypeScript type alias and the interface field need updating.

5. **Response envelope vs. flat object**: All endpoints in FXA-007 and FXA-013 return the model directly (not wrapped in `{ asset: FixedAssetOut }` or `{ order: MaintenanceOrderOut }` envelopes), consistent with the FXA-007 spec endpoint table (`docs/ofbiz/specs/FXA-007.md:149–158`). This assumption must be verified against the actual FXA-007 implementation before FXA-015 uses the wrappers.

6. **`MaintenanceOrderListOut.count` field**: FXA-004 specifies `count: int` on `MaintenanceOrderListOut` (`docs/ofbiz/specs/FXA-004.md:379–383`). If the FXA-013 router omits `count` from the response (returning only `items` and `cursor`), the TypeScript interface should make `count` optional (`count?: number`).
