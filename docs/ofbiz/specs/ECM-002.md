# ECM-002 — Feature flag, settings & graceful-degrade helper

**Type:** Chore | **Priority:** P0 | **Estimate:** 1 day

---

## 1. Summary & Goal

ECM-002 creates the settings foundation and the single shared helper module that every later ECM ticket will import. The deliverables are:

1. Five new `bool` fields on `Settings` (`app/core/settings.py`): one master switch (`store_integration_enabled`) and four per-surface sub-flags (`store_show_live_availability`, `store_apply_pricing_rules`, `store_show_fulfillment_status`, `store_variant_selection_enabled`). All default `false`.

2. A new service module `app/services/store_integration.py` with exactly two public helper functions:
   - `_integration_enabled(sub_flag=None)` — gate check that AND-combines the master switch with an optional named sub-flag.
   - `_safe_upstream(call, default)` — error-swallowing wrapper that catches any exception from an upstream call, logs a WARNING, and returns the supplied default.

No endpoint logic is added. No DynamoDB tables are introduced. Existing shop/cart/orders/billing behavior is byte-for-byte unchanged with all flags off (the new module is never called by any existing code path in this ticket).

### 4.2 New module `app/services/store_integration.py`

The module exposes exactly two public helpers. No imports from `app.core.tables` (no DDB), no imports from `app.routers.*`, no FastAPI `HTTPException`.

**Full function signatures:**

```python
from __future__ import annotations

import logging
from typing import Callable, TypeVar

from app.core.settings import S

logger = logging.getLogger(__name__)

_T = TypeVar("_T")

# Sub-flag name → Settings attribute name mapping.
_SUB_FLAG_ATTRS: dict[str, str] = {
    "live_availability": "store_show_live_availability",
    "pricing_rules": "store_apply_pricing_rules",
    "fulfillment_status": "store_show_fulfillment_status",
    "variant_selection": "store_variant_selection_enabled",
}


def _integration_enabled(sub_flag: str | None = None) -> bool:
    """Return True iff STORE_INTEGRATION_ENABLED is on AND, when sub_flag is
    provided, the named per-surface sub-flag is also on.

    sub_flag must be one of: "live_availability", "pricing_rules",
    "fulfillment_status", "variant_selection", or None (master-only check).

    Uses getattr with a False default so callers written before the settings
    fields existed still degrade gracefully.
    """
    if not getattr(S, "store_integration_enabled", False):
        return False
    if sub_flag is None:
        return True
    attr = _SUB_FLAG_ATTRS.get(sub_flag)
    if attr is None:
        logger.warning("_integration_enabled: unknown sub_flag %r", sub_flag)
        return False
    return bool(getattr(S, attr, False))


def _safe_upstream(call: Callable[[], _T], default: _T) -> _T:
    """Invoke call(); on any exception log at WARNING and return default.

    Guarantees that an upstream module being unavailable, raising an
    unexpected exception, or returning an invalid shape never breaks
    browse/cart/checkout. The upstream call is synchronous; async callers
    must await before passing the coroutine result in, or use
    asyncio.run/_safe_upstream_async (defined in ECM-004+).
    """
    try:
        return call()
    except Exception:
        logger.warning(
            "_safe_upstream: upstream call failed, returning default",
            exc_info=True,
        )
        return default
```

**Design choices explained:**

- `_SUB_FLAG_ATTRS` is a module-level dict rather than a series of `if/elif` chains. This makes the valid set of sub-flag names explicit and discoverable, and makes the unknown-name branch testable without patching.
- The `_T = TypeVar("_T")` typing preserves the return type of `_safe_upstream` without requiring `Any`, allowing callers to be type-checked.
- `logger.warning(..., exc_info=True)` emits the full traceback at WARNING level (not DEBUG), matching the project's convention for operational-significance log messages (see `app/services/account_deletion.py:280` — VERIFIED, `app/services/achievement_progress.py:304` — VERIFIED).
- No `asyncio` in this module — ECM-002 is pure sync scaffolding. Async variants (`_safe_upstream_async`) will be introduced in ECM-004 when the first `await`-able upstream call appears.

## 5. Detailed Behavior & Edge Cases

### 5.1 `_integration_enabled` call matrix

| Master flag | sub_flag arg | Sub-flag value | Return |
|---|---|---|---|
| `false` | any | any | `False` |
| `true` | `None` | — | `True` |
| `true` | `"variant_selection"` | `false` | `False` |
| `true` | `"variant_selection"` | `true` | `True` |
| `true` | `"unknown_key"` | — | `False` (logs WARNING) |
| `true` | `None` | — | `True` (sub-flags irrelevant) |

### 5.2 `_safe_upstream` exception handling

- Catches the base `Exception` class, not only `HTTPException` or `ClientError`. This is intentional: upstream modules may raise `ValueError` (schema mismatch), `KeyError` (missing field), `botocore.exceptions.ClientError` (DDB unavailable), `HTTPException` (service logic), or arbitrary unexpected errors. All must be swallowed equally.
- `exc_info=True` on the logger call means the full traceback appears in the log stream — essential for debugging upstream failures in production without them surfacing to the user.
- The `default` value is returned as-is. The caller is responsible for providing a type-correct default (e.g., the legacy `_catalog_item_out(item)` result for ECM-004).
- `_safe_upstream` is **not** a decorator. It is a call-site wrapper used as `result = _safe_upstream(lambda: upstream_fn(args), default_value)`. Keeping it non-decorator avoids import-time side effects and makes the default explicit at the call site.

### 5.3 Unknown sub_flag name

If a caller passes a sub_flag name that is not in `_SUB_FLAG_ATTRS` (e.g., a typo in a future ticket), `_integration_enabled` logs a WARNING and returns `False`. This is the safe direction: an unknown flag name causes the feature to stay off, not accidentally on.

### 5.4 Getattr defensive read

Both helpers use `getattr(S, attr, False)` rather than `S.attr`. Because `S` is a frozen dataclass instance (not a dict), attribute access on a missing field raises `AttributeError`. The `getattr` default prevents this in any environment where the settings file hasn't been deployed yet (e.g., a canary instance running old code against a new env var set). This mirrors `app/services/inventory.py:51`: `getattr(S, "inventory_reservations_enabled", False)` (VERIFIED).

### 5.5 Thread safety

`S` is a module-level singleton created at import time. Its fields are immutable (frozen dataclass). Both `_integration_enabled` and `_safe_upstream` are stateless functions — no locks or shared mutable state.

### 5.6 Sync-only in ECM-002

Later tickets (ECM-004 onward) introduce `async` upstream calls. `_safe_upstream` as defined here only supports synchronous callables. The ECM-004 spec will introduce `_safe_upstream_async(coro, default)` that `await`s the coroutine inside a `try/except`. Both helpers will live in `store_integration.py` to keep all integration scaffolding co-located.

## 6. Feature Flag & Config

### 6.1 Master flag

| Property | Value |
|---|---|
| Settings field | `store_integration_enabled: bool` |
| Env var | `STORE_INTEGRATION_ENABLED` |
| Default | `false` (`.lower() == "true"` idiom) |
| Behaviour when `false` | `_integration_enabled()` always returns `False`; all four sub-flags are irrelevant; `store_integration.py` is dormant |

### 6.2 Per-surface sub-flags

| Settings field | Env var | Consumed by |
|---|---|---|
| `store_show_live_availability` | `STORE_SHOW_LIVE_AVAILABILITY` | ECM-005: live availability enrichment on catalog items |
| `store_apply_pricing_rules` | `STORE_APPLY_PRICING_RULES` | ECM-006: pricing-rule engine on cart total |
| `store_show_fulfillment_status` | `STORE_SHOW_FULFILLMENT_STATUS` | ECM-007: fulfillment status on order view |
| `store_variant_selection_enabled` | `STORE_VARIANT_SELECTION_ENABLED` | ECM-004: variant topology enrichment on catalog items |

All four default `false`. A sub-flag being `true` while the master is `false` has no effect — `_integration_enabled(sub_flag)` short-circuits on the master.

### 6.3 Activation sequence for production rollout

The intended rollout order (from ECM-001 dependency matrix) is:

1. Deploy ECM-002 code with all flags `false` — no behavior change at all.
2. Enable `STORE_INTEGRATION_ENABLED=true` + `STORE_VARIANT_SELECTION_ENABLED=true` after ECM-003/ECM-004 land.
3. Enable `STORE_SHOW_LIVE_AVAILABILITY=true` after ECM-005 + OFB-003 land.
4. Enable `STORE_APPLY_PRICING_RULES=true` after ECM-006 + OFB-019 land.
5. Enable `STORE_SHOW_FULFILLMENT_STATUS=true` after ECM-007 + ORD-007 land.

Kill switch: setting `STORE_INTEGRATION_ENABLED=false` at runtime (requires app restart; Settings is read at import) disables all surfaces simultaneously.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

There is no mock/real branch in `store_integration.py`. The module reads only `S.*` settings flags and invokes caller-supplied callables — it has no direct AWS or network dependency. The downstream upstream calls (inventory, pricing rules, etc.) carry their own dev/prod parity; `_safe_upstream` is transparent to them.

In dev mode (`S.dev_mode = True`), the master flag still defaults `false`, so no behavior change in dev either unless the operator explicitly sets `STORE_INTEGRATION_ENABLED=true` in `.env.local`. This is intentional: dev environments should be able to test the integration path with the flags on.

### 7.2 Idempotency

`_integration_enabled` and `_safe_upstream` are pure functions with no side effects and no state. They are trivially idempotent.

### 7.3 Security

- `_safe_upstream` swallows exceptions but never suppresses security-critical checks. It is only called in enrichment paths (add variants, add availability, add pricing breakdown) — paths that return additional data on top of an already-authenticated, already-authorized base response. A failure in an enrichment call degrades to the base response; it cannot bypass auth or widen access.
- The module introduces no new API surface, no new tokens, no new secrets.
- Log lines use `%`-style formatting (not f-strings) to avoid accidental sensitive-data leakage via `str()` coercion of complex objects in the `exc_info` call. The structured `exc_info=True` ensures the traceback is captured rather than user-supplied values.

## 10. Open Questions / Assumptions

1. **Assumption:** The five ECM flags are placed immediately after `returns_table_name` (`settings.py:847`) and before the `# File manager` block at `settings.py:849`. If another ticket inserts settings in that range before ECM-002 lands, the placement may shift — the ordering within the file does not affect behavior, only readability.

2. **Assumption:** `_safe_upstream` is synchronous only in ECM-002. ECM-004 will need an async variant (`_safe_upstream_async`). This should be noted in ECM-004's spec; the implementation here does not need to anticipate it.

3. **Question:** Should `_integration_enabled` raise `RuntimeError` (not return `False`) when called with an unknown sub_flag string? The current spec returns `False` with a WARNING because the safe direction for an unknown flag is "off". If the team prefers strict fail-fast behavior in development, an `AssertionError` could be raised when `S.dev_mode` is `True`. This spec assumes "fail safe" is correct; the reviewer should confirm.

4. **Assumption:** The upstream-module flags (`PRODUCT_DEPTH_ENABLED`, `PRICING_RULES_ENABLED`, `ORDER_LIFECYCLE_ENABLED`, `SHIPPING_ENABLED`) are NOT added by ECM-002. They are added by their owning tickets (PRD-series, OFB-series, ORD-series, SHP-series). `_integration_enabled` gates only on ECM-owned flags. This means a caller in ECM-005 that also needs `INVENTORY_RESERVATIONS_ENABLED` must check both: `_integration_enabled("live_availability") and inventory._flag_on()`. This separation of concerns is intentional — ECM does not own the upstream flags.

5. **Assumption:** `_SUB_FLAG_ATTRS` is a module-level constant rather than computed from `S.__dataclass_fields__` to avoid coupling to the internal dataclass structure and to make the valid sub-flag vocabulary explicit at the code level.

6. **Question:** Should `_safe_upstream` accept an optional `label: str` argument to improve log readability (e.g., `"variant_enrichment"`)? The current spec omits it to keep the API minimal; callers can add the label themselves in the `except` block if needed. Confirm with the team before ECM-004 lands.
