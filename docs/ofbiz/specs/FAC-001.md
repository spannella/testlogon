# FAC-001 — Facility/fulfillment scoping spike & data-model delta

## 1. Summary & Goal

FAC-001 is the P0 foundational spike for the OFBiz Facility/Fulfillment work stream. Its deliverable is this design document: a precise, code-grounded mapping of the OFBiz Facility application onto the existing inventory foundation, a gap analysis documenting what does and does not exist, the complete DynamoDB data-model delta (five new tables with all PK/SK/GSIs and `attr_types`), every new Pydantic model shape, all new `Settings` keys, the `FACILITY_FULFILLMENT_ENABLED` flag contract, and the cross-module dependency contracts that downstream FAC-002 through FAC-010 tickets reference.

No implementation code ships with this ticket. The deliverable is this spec and reviewer sign-off that:
- The multi-location model is additive to existing `DEFAULT_LOCATION = "warehouse"` inventory rows.
- No money path is forked; write-offs and refunds continue through `billing_shared.new_ledger_entry` and `refund_payment`.
- With `FACILITY_FULFILLMENT_ENABLED` off, every existing code path (shop, cart, orders, billing) is byte-for-byte unchanged.

## 2. Context & Current State

### Existing inventory foundation

`app/services/inventory.py` implements a flag-gated (`INVENTORY_RESERVATIONS_ENABLED`) first-class SKU stock record with a reservation lifecycle. Key facts drawn directly from the source:

- `DEFAULT_LOCATION = "warehouse"` at `app/services/inventory.py:43` — all existing stock rows use this implicit single location. The `_location_sk(location_id)` helper at `:59` produces `LOC#{location_id}` as the DynamoDB sort key, meaning location is already a dimension of the primary key; only one value (`warehouse`) is used today.
- `get_inventory(sku, location_id)` at `:150` reads `T.inventory` keyed `(sku, LOC#{location_id})`. Multi-location queries against new facility location IDs use this same call without any code change.
- `adjust(sku, delta, reason, *, location_id, user_sub)` at `:209` performs an optimistic single-writer conditional increment/decrement with create-on-adjust for positive deltas (`:225–251`). This is the canonical write path receiving/transfers will call.
- `reserve(sku, quantity, *, location_id, ...)` at `:339` performs a `available >= qty` conditional update (DDB `ConditionExpression="available >= :q"` at `:365`) and writes a new reservation row; it is NOT idempotent (each call creates a new reservation). `commit_reservation` at `:456` decrements `on_hand + reserved` and is idempotent via `_close_reservation` at `:434–453`; `release_reservation` at `:492` returns quantity to available and is likewise idempotent via `_close_reservation`.
- `set_on_hand(...)` at `:176` sets absolute quantity and is the initial seeding path.
- Audit events are emitted via the `_audit()` wrapper at `:92–98` which lazy-imports `app.services.alerts.audit_event` and swallows exceptions.

### Auth dependencies

`app/routers/inventory.py:9–11` establishes the role model: admin mutations use `require_admin_or_root_csrf` (imported from `app/auth/policy`); reads use `require_ui_session` (from `app/services/sessions`). The facilities router follows the identical split.

### What the current foundation does NOT cover (gap analysis)

1. **No facility/warehouse entity** — `location_id` is a bare, unvalidated string. There is no record asserting that `"warehouse"` is a real, ownable facility with an address or type.
2. **No location/bin hierarchy** — a single string `"warehouse"` covers all physical bins. OFBiz models `Facility` → `FacilityLocation` (aisle/bay/level). There is no bin-level granularity.
3. **No inter-location transfers** — moving stock from one location to another requires two raw `adjust` calls with no coordinating transfer lifecycle record, no in-transit state, and no idempotency guard.
4. **No receiving (inbound goods)** — there is no receipt document linking an inbound delivery to a purchase order. The Purchasing module (`PUR`) owns POs; receiving must consume that contract without duplicating it.
5. **No pick/pack/ship** — orders have no fulfillment lifecycle. There is no picklist, no pick confirmation, no packing step, and no shipment record linking carrier/tracking to an order.
6. **No lot/serial tracking** — `inventory.py` tracks only on_hand/reserved per SKU+location, not individual lots or serial numbers. This is an optional stretch goal.

## 3. Data Model

All five new tables follow the project's single-table pattern. Keys are strings (`S`) unless overridden in `attr_types`. Numeric GSI sort keys **must** be listed in `attr_types` per the DynamoDB GSI numeric-sort-key gotcha documented in CLAUDE.md.

## 5. Detailed Behavior & Edge Cases

### Multi-location additive compatibility

Existing inventory rows were written with `location_sk = "LOC#warehouse"` (from `_location_sk(DEFAULT_LOCATION)` at `app/services/inventory.py:59`). The facilities layer treats `"warehouse"` as a valid `location_id` that maps directly to those existing rows. An auto-seeded default facility named `"Default Warehouse"` with `facility_id = sha256("system|Default Warehouse")[:32]` and a single location with `location_id = "warehouse"` is created on first use (via `create_facility` idempotent put) so pre-existing inventory rows are attributable. No migration of existing DDB items is required.

### Transfer idempotency and stock integrity

`complete_transfer` reads the transfer META row, pins `status = "in_transit"` in a conditional update, then executes the dual `inventory.adjust` pair. If the conditional update succeeds, the adjustments run exactly once. If the process crashes between the two adjusts (partial execution), the second adjust is safe to replay because the conditional has already flipped to `"completed"` — a replayed call reads `status != in_transit` and returns the cached result without re-adjusting. The source-side adjust uses the existing `available >= qty` guard in `inventory.adjust` via the `new_available < 0` check at `app/services/inventory.py:256` — a transfer cannot move more than available stock.

### Receiving idempotency

`receipt_id = sha256(correlation_id)[:32]` is derived before the first DDB write. The write uses `ConditionExpression="attribute_not_exists(receipt_id)"`. A second call with the same `correlation_id` will hit a `ConditionalCheckFailedException`, which the service catches and converts to a 200 with the existing receipt. The per-line `inventory.adjust(+qty)` calls only run on the first write, so on-hand is incremented exactly once.

### Picklist short-pick handling

If picked_qty < quantity for a line after all other lines are confirmed, the picklist transitions to `status = "picked"` but with the LINE row carrying `line_status = "short"`. The `commit_picklist` helper calls `commit_reservation` for the actual picked_qty (not the reserved qty), and calls `release_reservation` for the remainder. If inventory reservations are disabled, `inventory.adjust(sku, -picked_qty, "pick")` is called instead and the short remainder is left as-is (the caller is responsible for backorder handling — the ORD module handles that contract).

### Lot/serial tracking (stretch)

The `lot_serial` table, if enabled, would be written by the receiving and shipping paths. A lot `lot_id = sha256(supplier_lot_number)[:16]` scoped per SKU. Serial numbers are unique per-unit strings. This is explicitly out of scope for FAC-001 through FAC-010 and deferred to FAC-011+. The `FACILITY_LOT_SERIAL_ENABLED` flag (default false) will gate this sub-feature.

### PUR module contract

The Purchasing module owns PO records. The receiving service (`receiving.py`) consumes POs by:
1. Accepting an optional `po_id` on receipt creation.
2. Writing `ordered_qty` (looked up from the PO line — the PUR module must expose `get_po_line(po_id, sku) -> {ordered_qty}`) and `received_qty` per line.
3. Exposing `list_receipts_for_po(po_id)` so the PUR module can query received quantities without owning the receipt table.

The PUR module never writes to `T.receipts`; it only reads via `list_receipts_for_po`. This one-way contract avoids circular dependencies.

### ORD module fulfillment event contract

When `ship_shipment` finalises a shipment, it emits an `audit_event("fulfillment.shipped", ...)` with `order_id`, `shipment_id`, `carrier`, `tracking_number`, and `shipped_at`. The ORD module (when `ORDER_LIFECYCLE_ENABLED`) subscribes to this event to advance the order status to `shipped`. The shipping service does not write to `T.orders` directly — that remains the ORD module's responsibility.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity**: All five service files contain zero `if S.dev_mode` branches in business logic. DynamoDB table access uses the same `T.*` handles in both environments. moto intercepts boto3 in dev; real DynamoDB is used in prod. The `_audit()` wrapper's lazy import of `app.services.alerts.audit_event` works identically in both.

**Idempotency strategy**:
- `create_facility`: `sha256(owner_sub|name)[:32]` deterministic ID + `attribute_not_exists(facility_id)` conditional put. Replay returns the existing record.
- `receive_shipment`: `sha256(correlation_id)[:32]` deterministic receipt ID + `attribute_not_exists(receipt_id)` conditional put. Replay returns existing receipt without re-adjusting inventory.
- `complete_transfer`: `status = "in_transit"` conditional flip — exactly one winner, dual adjust runs once.
- `commit_picklist` / `ship_shipment` / `cancel_shipment`: `status = <expected>` conditional flip (mirrors `_close_reservation` at `app/services/inventory.py:434–453`). Idempotent replays return the current record without side effects.

**Billing / money-out parity**: Write-offs for damaged goods received are recorded via `billing_shared.new_ledger_entry` (`app/services/billing_shared.py:224`) with `entry_type="inventory_writeoff"`, `extra={"facility_id": ..., "location_id": ...}`. Refunds triggered by order cancellation after pack still flow through the existing `refund_payment` path in `app/routers/billing.py:1287`. No new billing code path is introduced.

**Auth**: All mutation endpoints require `require_admin_or_root_csrf` (CSRF-validated, admin or root role). Read endpoints require `require_ui_session`. No endpoint is public (unauthenticated). Transfer completion and receipt posting are admin operations because they mutate on-hand stock — the same gating as `inventory_router` PUT/POST endpoints at `app/routers/inventory.py:48,65,81`.

## 10. Open Questions / Assumptions

1. **Assumption**: The Purchasing module (`PUR`) will expose a `get_po_line(po_id: str, sku: str) -> dict` callable that `receiving.py` can import. If PUR is not yet built, the receiving service accepts `ordered_qty` directly from the caller instead of looking it up.

2. **Assumption**: `facility_id` deterministic derivation uses `sha256(owner_sub + "|" + name)[:32]` matching the `commerce_order_service.py:67` pattern. This means two users cannot create a facility with the same name under the same sub — which is the correct uniqueness constraint. Cross-user name collisions are impossible because `owner_sub` is in the hash input.

3. **Open question**: Should `create_location` IDs be deterministic (e.g., `sha256(facility_id + "|" + description)[:16]`)? A deterministic ID would make location creation idempotent but would prevent two locations with the same label. The current design uses `uuid4().hex` for location IDs (non-deterministic, supports multiple bins with the same description). Reviewers should confirm.

4. **Assumption**: The `lot_serial` table is defined in `local-ddb-init.py` in FAC-002 for forward compatibility but not wired in `T` until FAC-011+ explicitly enables it. The `FACILITY_LOT_SERIAL_ENABLED` flag governs it separately.

5. **Open question**: Should `archive_facility` block if there is open stock at that facility (available > 0 across any location)? The current design assumes it should — returning 409 — to prevent orphaned inventory. This needs reviewer confirmation.

6. **Assumption**: Write-off events for damaged stock use `billing_shared.new_ledger_entry` with zero `amount_cents` (stock quantity loss is not a financial debit by itself; it triggers a separate accounting entry by the finance team). If write-offs should carry a cost value, the `ReceiveIn` model will need a `unit_cost_cents` field that becomes the ledger amount.

7. **Assumption**: The `shipments.shipped_at` column is `N` (numeric Unix timestamp, 0 until shipped) and therefore must appear in `attr_types={"...", "shipped_at": "N"}`. Reviewers should confirm whether a secondary sort on `shipped_at` is required or whether `created_at` suffices for all shipment query patterns.
