# ORD-011 — Order-lifecycle router (transitions, history, adjustments, ship groups)

**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days
**Milestone:** 4 — Router & API

## 1. Summary & Goal

ORD-011 wires the service layer built in ORD-005 through ORD-010 into an HTTP API surface.  It delivers one new file — `app/routers/order_lifecycle.py` — and one registration line in `app/main.py`.

The router exposes:

| Method | Path | Auth | Service function |
|--------|------|------|-----------------|
| `POST` | `/ui/orders/{order_id}/transition` | admin/root + CSRF | `order_lifecycle.transition_order` |
| `GET`  | `/ui/orders/{order_id}/lifecycle`   | owner or admin/root | `order_lifecycle.get_order_lifecycle` |
| `GET`  | `/ui/orders/{order_id}/history`     | owner or admin/root | `order_lifecycle.list_status_history` |
| `POST` | `/ui/orders/{order_id}/adjustments` | admin/root + CSRF | `order_adjustments.add_adjustment` |
| `DELETE` | `/ui/orders/{order_id}/adjustments/{adjustment_id}` | admin/root + CSRF | `order_adjustments.remove_adjustment` |
| `POST` | `/ui/orders/{order_id}/ship-groups` | admin/root + CSRF | `order_ship_groups.create_ship_group` |
| `POST` | `/ui/orders/{order_id}/ship-groups/{ship_group_id}/assign` | admin/root + CSRF | `order_ship_groups.assign_items_to_ship_group` |
| `POST` | `/ui/orders/{order_id}/cancel`      | owner (pre-approval) or admin/root + CSRF | `order_lifecycle.cancel_order` |

All endpoints return HTTP 503 with `{"code": "feature_disabled"}` when `S.order_lifecycle_enabled` is `False` (default). No existing route in `shoppingcart`, `catalog`, or `billing` is modified.

## 2. Context & Current State

### 2.1 Existing orders table — flat structure

`scripts/local-ddb-init.py:287–294` defines the `orders` table today with PK `order_id` and **no sort key**, plus two GSIs (`GSI_USER`, `GSI_STATUS`). `CommerceOrderService.create_order` at `app/services/commerce_order_service.py:39` writes a single item per order keyed on `order_id` alone (`:85`), with hard-coded `"status": "pending_payment"` at line 75.

After ORD-003 adds a sort key `sk`, the ORDER-SK header row is keyed `{"order_id": order_id, "sk": "ORDER"}`. Additional SK partitions `HIST#`, `SHIPGRP#`, `ADJ#` are written under the same PK. The `order_items` table at `scripts/local-ddb-init.py:295` (PK `order_id`, SK `item_id`) is unchanged.

### 2.2 No existing lifecycle router

`ls /home/ubuntu/testlogon/app/routers/` shows no `order_lifecycle.py`. The `shoppingcart.py` router at `app/routers/shoppingcart.py:50` handles cart/purchase only; it calls `commerce_order_service.create_order_from_line_items` indirectly through `purchase_cart` at `app/services/shoppingcart.py:581`. There is no transition, history, adjustment, or ship-group surface anywhere.

### 2.3 Auth pattern: `require_ui_session` + `require_admin_or_root_csrf`

The project uses two complementary auth dependencies:

- `require_ui_session` from `app/services/sessions.py:330` — validates the `ui_access_token` cookie (HS256 JWT) **or** Bearer token, then looks up the live session row; returns `{"user_sub": str, "session_id": str, "role": str, "ip": str, "tenant_id": str, ...}` (role is the enum's `.value` string, not the enum). CSRF is enforced automatically on non-GET cookie-auth requests inside this dependency.
- `require_admin_or_root_csrf` from `app/auth/policy.py:100` — combines `get_authenticated_user` (role check: ADMIN or ROOT) with an explicit `enforce_cookie_csrf(request)` call for cookie-auth non-GET requests.

The `returns_rma_router` at `app/routers/returns_rma.py` is the closest precedent: customer reads use `require_ui_session`; admin writes use `require_admin_or_root_csrf` (`app/routers/returns_rma.py:61, 73`).

### 2.4 Route ordering: static segments before dynamic path params

CLAUDE.md documents the FastAPI declaration-order gotcha: the static segment `/schedules` must be declared before the dynamic `/{export_id}` catch-all. The same rule applies here. The path `POST /ui/orders/{order_id}/ship-groups/{ship_group_id}/assign` is unambiguous, but any future static paths under `/ui/orders/` (e.g. the ORD-012 `/ui/orders/lifecycle/by-status`) must be declared before `/{order_id}` endpoints. Within ORD-011, there are no same-level static/dynamic conflicts, but the router file must be structured with static sub-paths (e.g. admin routes if any) before parametric ones.

### 2.5 Feature-flag 503 pattern

`app/routers/call_recording.py:39–41` shows the canonical pattern used across the project:

```python
def _require_lifecycle_enabled():
    if not S.order_lifecycle_enabled:
        raise HTTPException(
            status_code=503,
            detail={"code": "feature_disabled", "message": "Order lifecycle is disabled"},

```

This guard is called at the top of every handler. Mounting the router unconditionally in `app/main.py` (always attached, conditionally active) matches the unconditional mounting of `returns_rma_router` at `app/main.py:878`. Note: `returns_rma`'s own `_require_enabled()` guard (`app/services/returns_rma.py:71`) raises **404** with a plain-string detail — a different pattern. ORD-011 uses the 503+dict pattern from `call_recording.py`.

### 4.3 Ownership guard

```python
def _require_order_owner_or_admin(order_header: dict, ctx: dict) -> None:
    """Raise 403/404 if requester does not own the order and is not admin/root."""
    from app.auth.roles import Role, normalize_role
    role = normalize_role(ctx.get("role"))
    if role in (Role.ADMIN, Role.ROOT):
        return  # admin bypasses ownership check
    if order_header.get("user_id") != ctx["user_sub"]:
        raise HTTPException(status_code=404, detail={"code": "order_not_found"})
```

Returning 404 (not 403) for foreign-order access by a non-admin matches the `returns_rma` pattern (`app/routers/returns_rma.py:51`) — 403 would reveal that the order exists.

### 4.4 Endpoint signatures

#### `POST /ui/orders/{order_id}/transition` (admin/root)

```python
@router.post("/{order_id}/transition", response_model=OrderTransitionResult)
async def transition_order_endpoint(
    order_id: str,
    body: OrderTransitionRequest,
    request: Request,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> OrderTransitionResult:
    _require_enabled()
    from app.services import order_lifecycle
    try:
        result = order_lifecycle.transition_order(
            order_id,
            body.target_status.value,
            actor=user.sub,
            reason=body.reason,
            idempotency_key=body.idempotency_key,
        )
    except order_lifecycle.OrderNotFoundError:
        raise HTTPException(404, {"code": "order_not_found"})
    except order_lifecycle.OrderTransitionError as exc:
        raise HTTPException(409, {"code": "illegal_transition", "detail": str(exc)})
    except order_lifecycle.OrderConflictError as exc:
        raise HTTPException(409, {"code": "conflict", "detail": str(exc)})
    return result
```

- Only `require_admin_or_root_csrf` — owners cannot self-transition (except via the dedicated `/cancel` endpoint).
- Maps `OrderTransitionError` and `OrderConflictError` to 409.
- The `Request` parameter is accepted by `require_admin_or_root_csrf` (which calls `enforce_cookie_csrf(request)` internally via its dependency chain in `app/auth/policy.py:100`).

```python
@router.post("/{order_id}/cancel", response_model=OrderLifecycleOut)
async def cancel_order_endpoint(
    order_id: str,
    body: OrderCancelIn,
    request: Request,
    ctx = Depends(require_ui_session),
) -> OrderLifecycleOut:
    _require_enabled()
    from app.services import order_lifecycle
    from app.auth.roles import Role, normalize_role
    header = order_lifecycle.get_order_header(order_id)
    if header is None:
        raise HTTPException(404, {"code": "order_not_found"})

    role = normalize_role(ctx.get("role"))
    is_admin = role in (Role.ADMIN, Role.ROOT)

    # Ownership gate (non-admin path)
    if not is_admin and header.get("user_id") != ctx["user_sub"]:
        raise HTTPException(404, {"code": "order_not_found"})

    # Owners can only self-cancel pre-approval orders; admins can cancel any pre-shipped state
    current_status = header.get("lifecycle_status", "")
    OWNER_CANCELLABLE = {"created", "approved"}
    PRE_SHIPPED = {"created", "approved", "allocated", "picking", "packed", "held", "backorder"}
    if not is_admin and current_status not in OWNER_CANCELLABLE:
        raise HTTPException(
            409,
            {"code": "cancel_not_allowed", "detail": f"Owners can only cancel orders in status {OWNER_CANCELLABLE}"},
        )

    try:
        result = order_lifecycle.cancel_order(
            order_id,
            reason=body.reason,
            refund=body.refund,
            actor=ctx["user_sub"],
        )
    except order_lifecycle.OrderTransitionError as exc:
        raise HTTPException(409, {"code": "illegal_transition", "detail": str(exc)})
    except order_lifecycle.OrderConflictError as exc:
        raise HTTPException(409, {"code": "conflict", "detail": str(exc)})
    return result
```

- Uses `require_ui_session` (not `require_admin_or_root_csrf`) so both owners and admins can reach the endpoint.
- CSRF is automatically enforced for cookie-auth POST requests inside `require_ui_session`.
- The owner-cancellable status set `{"created", "approved"}` is the pre-payment/pre-allocation window. Admins extend this to any pre-`shipped` state (per ORD-001's cancellation scope).

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag off → unconditional 503

When `S.order_lifecycle_enabled = False`, every handler's first statement raises HTTP 503. The router is still mounted (registration in `app/main.py` is unconditional), but every request immediately returns:

```json
{"detail": {"code": "feature_disabled", "message": "Order lifecycle is disabled"}}
```

No service module is imported, no DynamoDB table is read, and no existing route is affected. This is the same pattern as `call_recording.py:39–41`. (Contrast: `app/services/returns_rma.py:71` raises 404 with a plain-string detail — a different guard style.)

### 5.2 Foreign-order access returns 404, not 403

A non-admin user requesting lifecycle data for an order they do not own receives `404 order_not_found`, not `403 Forbidden`. This prevents information disclosure (the 404 gives no hint that the order exists). Admin/root users always receive the real order or a genuine 404. This follows `app/routers/returns_rma.py:49–51`.

### 5.3 Illegal transitions → 409

The service layer (ORD-005) raises `OrderTransitionError` for illegal state graph edges (e.g. `packed → created`) and `OrderConflictError` for concurrent CAS conflicts (another request advanced the state before this one). Both map to HTTP 409. The router never swallows these — it maps them verbatim so clients can distinguish "bad request" (400/422) from "state conflict" (409).

### 5.4 Adjustment on a post-ship order → 409

`order_adjustments.add_adjustment` and `remove_adjustment` call `_require_pre_ship_state` which raises `AdjustmentStateError` when `lifecycle_status` is in `{shipped, completed, cancelled, returned}`. The router maps this to 409. The error message includes the current status so the client knows why.

### 5.5 Cancel with `refund=true` on an order with no payment_intent_id

`order_lifecycle.cancel_order` (ORD-010) uses a best-effort payment lookup: it reads `ledger_sk` and `payment_intent_id` from the order header and metadata, following the pattern in `app/services/returns_rma.py:492–494`. If neither is present, the function still transitions the order to `cancelled` and writes the HIST row but issues no refund — it does not return an error. The ORD-011 cancel endpoint propagates this behavior: the caller receives `{"lifecycle_status": "cancelled", ...}` with no error. Clients that need to confirm a refund was issued should inspect the response order's `metadata.refund_ledger_sk`.

### 5.6 Double-cancel is a no-op

`cancel_order` checks the current `lifecycle_status`. If the order is already `cancelled`, the ORD-005 state machine raises `OrderConflictError` (the CAS guard fails because the current status is not a cancellable source state). The router maps this to 409 with `code=conflict`. The client should treat 409 as "nothing to do".

### 5.7 Owner-cancel CSRF

The `/cancel` endpoint uses `require_ui_session`. Per CLAUDE.md auth conventions, `require_ui_session` enforces CSRF for non-GET cookie-auth requests. No separate `enforce_cookie_csrf` call is needed in the handler. Bearer-auth clients (e.g. the `commercial_checkout` router or batch job scripts) bypass CSRF automatically.

### 5.8 `?include=` parameter on `/lifecycle`

The `GET /{order_id}/lifecycle` endpoint accepts a comma-separated `include` query parameter. Valid tokens are `history`, `adjustments`, `ship_groups`. Unknown tokens are silently ignored (the service returns `None` for uncollected fields). This is more ergonomic than multiple endpoints and avoids N+1 round trips on the common "show order detail" screen.

Example: `GET /ui/orders/abc123/lifecycle?include=history,adjustments` returns `OrderLifecycleOut` with `status_history=[...]`, `adjustments=[...]`, and `ship_groups=None`.

### 5.9 Concurrent transition race

If two admin requests both try to advance the same order from `approved → allocated` simultaneously:

1. Request A wins the DynamoDB conditional `update_item` (CAS on `lifecycle_status = "approved"`).
2. Request B's conditional update fails with `ConditionalCheckFailedException`.
3. The service layer catches the DDB error and raises `OrderConflictError`.
4. The router returns 409 `{"code": "conflict"}` to request B.

The client should re-fetch the order and decide whether to retry.

### 5.10 `subscription_cycle_orders.py` and `returns_rma.py` access patterns unchanged

`app/services/subscription_cycle_orders.py:39` reads orders with `self.orders_table.get_item(Key={"order_id": order_id})`. After ORD-003 adds `sk`, this call will fail because the table now has a sort key and DynamoDB requires both PK and SK for `get_item`. ORD-003 must define a `get_order_header` function in `app/services/order_store.py` that reads `Key={"order_id": order_id, "sk": "ORDER"}`, and the callers in `subscription_cycle_orders.py` and `returns_rma.py` must be updated to use `get_order_header`. This is a migration concern for ORD-003 (it is already called out in `docs/ofbiz/specs/ORD-003.md`). ORD-011 does not touch these callers; it only imports the new service functions.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

All reads and writes go through `T.orders` (DynamoDB Local in dev, real DynamoDB in prod). There is no `S.dev_mode` branch in the router or service layer. The refund path (via `cancel_order` → `order_lifecycle.cancel_order`) delegates to `new_ledger_entry` / `apply_balance_delta` / `settle_or_reverse_ledger` from `app/services/billing_shared.py:224`, which themselves have no mock branch. The Stripe mock at port 12111 handles Stripe API calls transparently in dev. This is full SECOPS-007 parity.

### 7.2 Idempotency

**Transition idempotency**: the `idempotency_key` field on `OrderTransitionRequest` drives deterministic `event_id = sha256(order_id|from|to|idempotency_key)[:16]` (ORD-005). A replayed transition with the same `idempotency_key` returns the existing `OrderTransitionResult` without a second DDB write (the HIST row already exists; the header CAS check short-circuits on `ConditionalCheckFailedException` → `OrderConflictError` which the router returns as 409; the client checks whether `event_id` is already known).

**Adjustment idempotency**: `add_adjustment` uses `adjustment_id = sha256(order_id|actor|adj_type|amount_cents|label)[:16]` (ORD-008). A duplicate call returns the existing row.

**Cancel idempotency**: a second `POST .../cancel` on an already-`cancelled` order returns 409 `conflict`. The client should tolerate this as "already done".

### 7.3 Security

**CSRF**: All non-GET cookie-auth requests require a valid `x-csrf-token` header matching the `ui_csrf` cookie. Admin endpoints use `require_admin_or_root_csrf` which explicitly calls `enforce_cookie_csrf(request)` (`app/auth/policy.py:100–106`). The `/cancel` endpoint uses `require_ui_session`, which enforces CSRF for cookie-auth POST requests automatically.

**Ownership enforcement**: the `_require_order_owner_or_admin` helper is called on every owner-readable endpoint before any DDB read beyond the header. A missing or foreign `user_id` is never surfaced.

**No money forking**: the `refund=true` path in `cancel_order` exclusively calls `new_ledger_entry` (`app/services/billing_shared.py:224`), `apply_balance_delta` (`app/services/billing_shared.py:83`), and `settle_or_reverse_ledger` (`app/services/billing_shared.py:262`) from `app/services/billing_shared.py`. These are the same primitives used by `billing.refund_payment` (declared `app/routers/billing.py:1287`; primitives called at lines 1306–1324) and `returns_rma.refund_return` (`app/services/returns_rma.py:444–542`). No Stripe/PayPal/CCBill SDK call is made directly from ORD-011.

**Role escalation**: the `/transition`, `/adjustments`, `/ship-groups` endpoints require ADMIN or ROOT role. An authenticated USER calling these endpoints receives 403 (from `require_admin_or_root_csrf` before the handler body even runs).

## 8. Backward Compatibility & Migration

### 8.1 Existing shop/cart/billing paths unchanged

With `ORDER_LIFECYCLE_ENABLED=false`:
- `shoppingcart.py:purchase_cart` at line 581 calls `create_order_from_line_items` as before.
- `commerce_order_service.create_order` writes `{"order_id": ..., "status": "pending_payment", ...}` as before — no `lifecycle_status`, no `sk` sort key, no HIST row.
- `returns_rma.py` and `subscription_cycle_orders.py` read from `T.orders` as before.
- No existing route is modified by ORD-011.

### 8.2 Orders table PK-only → PK+SK schema migration (ORD-003 concern)

After ORD-003 adds `sk` as a sort key to the `orders` table, the pre-existing callers `returns_rma.py:107` (`T.orders.get_item(Key={"order_id": order_id})`) and `subscription_cycle_orders.py:39` (`self.orders_table.get_item(Key={"order_id": order_id})`) and `file_bundle_checkout.py:98` (`T.orders.put_item(Item={...})` without `sk`) will break at runtime. ORD-003 is responsible for migrating these callers to use `app/services/order_store.get_order_header(order_id)` (which reads `Key={"order_id": order_id, "sk": "ORDER"}`) and for ensuring `put_item` calls include `"sk": "ORDER"`. ORD-011 assumes ORD-003's migration is complete before ORD-011 merges.

### 8.3 Existing `orders` table DDB data

Orders created before ORD-007 enables the flag have no `sk` attribute, no `lifecycle_status`, and no HIST rows. If an operator enables `ORDER_LIFECYCLE_ENABLED` on a stack with pre-existing orders, `get_order_header` will not find those orders under `sk="ORDER"` and will return `None`, causing 404 on lifecycle endpoints. A data backfill script (outside ORD-011 scope) is required to write `sk="ORDER"` onto existing header rows. This is an explicit open question (Section 10.3).

### 8.4 `file_bundle_checkout.py` direct `T.orders.put_item` call

`app/services/file_bundle_checkout.py:98` writes directly to `T.orders` without using `create_order` or `order_store`. After ORD-003's schema change, this write must include `"sk": "ORDER"`. ORD-003 owns this fix. ORD-011 is not affected at the router level, but the migration note is recorded here so reviewers can verify ORD-003 covers this caller.

## 10. Open Questions / Assumptions

1. **Assumption**: ORD-003's `orders` table migration (adding `sk` sort key) runs before ORD-011 code is deployed. All legacy callers (`subscription_cycle_orders.py`, `returns_rma.py`, `file_bundle_checkout.py`) have been updated by ORD-003 to use `order_store.get_order_header` before this router is active.

2. **Assumption**: The `order_lifecycle.py` service exports `OrderNotFoundError`, `OrderTransitionError`, and `OrderConflictError` as named exception classes. The `order_adjustments.py` service exports `OrderNotFoundError`, `AdjustmentStateError`, `AdjustmentNotFoundError`, `CurrencyMismatchError`. The `order_ship_groups.py` service exports `OrderNotFoundError`, `ShipGroupNotFoundError`, `ItemAssignmentError`. If these names differ in the ORD-005/ORD-008/ORD-009 implementations, the router's `except` clauses must be updated.

3. **Open**: Pre-existing DynamoDB orders (written before ORD-007 enables `ORDER_LIFECYCLE_ENABLED`) have no `sk` attribute and will return 404 from all lifecycle endpoints. A backfill strategy is needed before enabling the flag on a production stack with existing order data. Suggested approach: a one-time migration script that scans `T.orders` for items without `sk`, writes `{"order_id": ..., "sk": "ORDER"}` via `put_item` with the existing attributes unchanged. This migration script is out of scope for ORD-011.

4. **Assumption**: `require_admin_or_root_csrf` does not require a `ctx = Depends(require_ui_session)` alongside it. Looking at `app/routers/returns_rma.py`, `user: AuthenticatedUser = Depends(require_admin_or_root_csrf)` is sufficient for the admin endpoints, and the `user.sub` attribute carries the actor's user_sub.

5. **Open**: The cancel endpoint's `refund=true` path calls `cancel_order` which internally calls billing primitives. In the dev environment, the Stripe mock at port 12111 handles any Stripe API calls, but the mock always returns `requires_payment_method` for off-session PaymentIntents (per CLAUDE.md). E2E cancel-with-refund tests should seed wallet balance directly into DynamoDB or use a `refund=false` scenario to avoid Stripe mock limitations.

6. **Assumption**: `OrderAdjustmentIn`, `ShipGroupCreateIn`, `ShipGroupAssignIn`, and `OrderCancelIn` are appended to `app/models.py` by ORD-011. They are not part of ORD-004's scope (ORD-004 only defines response/service shapes). If the reviewer prefers to move these into ORD-004 for consistency, the diff is trivial.

7. **Open**: The `subscription_cycle_orders.CanonicalOrderEntitlementsRepository.get_order` method at `app/services/subscription_cycle_orders.py:34–45` reads the order header directly with `get_item(Key={"order_id": order_id})`. After ORD-003 adds `sk`, this returns no item (DDB requires both PK and SK). ORD-003 must explicitly list this caller in its migration plan.
