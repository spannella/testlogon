# FAC-015 — Hermetic pytest + E2E test suite

## 1. Summary & Goal

FAC-015 closes the final milestone of the facility/fulfillment stack by delivering
a complete, always-green automated test layer:

- **Four hermetic offline pytest suites** — one per logical subdomain — that run
  under the standard `just test` runner with no live AWS, no running backend, and no
  network. Each suite binds moto in-memory DynamoDB to the exact frozen `T` handles
  via `object.__setattr__` and flips frozen `S` flag fields the same way, following
  the established pattern from `tests/test_ofb_inventory.py` and
  `tests/test_ofb_returns_rma.py`.

- **One Playwright E2E spec** (`frontend/e2e/facility-fulfillment.spec.ts`) that
  drives a live stack through the four main user journeys: create facility/location,
  stock transfer, receiving, and a full pick → pack → ship order cycle with carrier
  tracking. It uses the seeded-session + CSRF + admin-identity pattern from
  `e2e_admin_session_setup.py`.

- **Flag-off parity assertions** in both layers confirming that with
  `FACILITY_FULFILLMENT_ENABLED=false` all FAC endpoints return 404 and the
  existing shop / cart / order / billing paths are byte-for-byte unchanged.

No new DynamoDB tables, settings keys, Pydantic models, service functions, or
frontend components are introduced by this ticket. It exercises code delivered by
FAC-002 through FAC-014 exclusively.

## 3. Data Model

FAC-015 adds no new DynamoDB tables. The tests consume the tables defined by
FAC-002. Each pytest suite creates its own isolated in-process moto tables in
`setUp`, so there is no shared state between test classes or test runs.

### Helper table-factory pattern (used in all four suites)

```python
def _t(ddb, name, pk, sk=None, gsi=None, attr_types=None):
    """Thin helper mirroring tests/test_ofb_returns_rma.py:37–61."""
    attrs = {pk: "S"}
    schema = [{"AttributeName": pk, "KeyType": "HASH"}]
    if sk:
        attrs[sk] = "S"
        schema.append({"AttributeName": sk, "KeyType": "RANGE"})
    gsis_spec = []
    for g in gsi or []:
        attrs[g["pk"]] = "S"
        ks = [{"AttributeName": g["pk"], "KeyType": "HASH"}]
        if g.get("sk"):
            attrs[g["sk"]] = "S"
            ks.append({"AttributeName": g["sk"], "KeyType": "RANGE"})
        gsis_spec.append({"IndexName": g["name"], "KeySchema": ks,
                          "Projection": {"ProjectionType": "ALL"}})
    for k, v in (attr_types or {}).items():
        attrs[k] = v
    kw = dict(
        TableName=name,
        KeySchema=schema,
        AttributeDefinitions=[{"AttributeName": k, "AttributeType": v}
                               for k, v in attrs.items()],
        BillingMode="PAY_PER_REQUEST",
    )
    if gsis_spec:
        kw["GlobalSecondaryIndexes"] = gsis_spec
    return ddb.create_table(**kw)
```

## 5. Detailed Behavior & Edge Cases

### 5.1 `tests/test_fac_facilities.py`

**setUp** binds: `T.facilities`, `T.inventory`, `T.reservations`.
**Flags enabled**: `S.facility_fulfillment_enabled = True`,
`S.inventory_reservations_enabled = True`.

**Test cases**:

1. `test_create_facility_returns_id` — `facilities.create_facility(owner_sub, name, ...)` returns a dict with non-empty `facility_id`; a `get_item` on the table confirms the META row exists.

2. `test_create_facility_idempotent` — calling `create_facility` twice with the same `owner_sub` + `name` (and therefore the same deterministic `sha256(owner_sub|name)[:32]` id) does not raise; both calls return the same `facility_id` and the table still holds exactly one META row for that id.

3. `test_create_location_and_list` — `create_location(facility_id, label, ...)` adds a `LOC#{location_id}` SK row; `list_locations(facility_id)` returns it.

4. `test_archive_facility` — `archive_facility(facility_id, actor_sub)` flips `status=archived`; a subsequent `get_facility` reflects the change.

5. `test_default_facility_back_compat` — the auto-seeded default `warehouse` facility (keyed on `DEFAULT_LOCATION = "warehouse"` from `app/services/inventory.py:43`) is accessible via `get_facility("warehouse")` after module import, confirming that pre-existing inventory rows at `location_id="warehouse"` remain attributable to the default facility.

6. `test_flag_off_create_facility_404` — with `S.facility_fulfillment_enabled = False`, `create_facility(...)` raises `HTTPException(status_code=404)` — exercising `_require_enabled()` from FAC-004.

### 5.2 `tests/test_fac_transfers.py`

**setUp** binds: `T.facilities`, `T.transfers`, `T.inventory`, `T.reservations`.
**Flags enabled**: both `facility_fulfillment_enabled` and `inventory_reservations_enabled`.

**Fixtures**: `_seed_inventory(sku, on_hand, location_id)` calls
`inventory.set_on_hand(sku, on_hand, location_id=location_id)` directly on the
moto table.

**Test cases**:

1. `test_create_transfer_requested` — `transfers.create_transfer(from_loc, to_loc, lines, actor_sub)` writes a META row with `status="requested"` and one `ITEM#0` row; the returned dict carries both.

2. `test_advance_to_in_transit` — `transfers.advance_transfer(transfer_id, actor_sub)` flips status to `"in_transit"`; on-hand at neither location changes yet.

3. `test_complete_transfer_dual_adjust` — completing an in-transit transfer calls `inventory.adjust(sku, -qty, ...)` at `from_loc` and `inventory.adjust(sku, +qty, ...)` at `to_loc`; net on-hand across both locations is unchanged (verified via `inventory.get_inventory`).

4. `test_complete_transfer_idempotent` — calling `complete_transfer` on an already-completed transfer is a no-op (status guard on `"in_transit"` condition returns `None`); `inventory.adjust` is called exactly once total (verified by seeding a counter via a `unittest.mock.patch` on `inventory.adjust` rather than counting DDB writes — or alternatively by asserting on-hand values are as expected after two complete calls).

5. `test_complete_transfer_overdraw_409` — seeding `from_loc` with `on_hand=2`, `reserved=2` (`available=0`) and attempting a transfer of qty=1 raises `HTTPException(status_code=409)` (from `inventory.adjust` via `app/services/inventory.py:256–259`); the source on-hand is unchanged.

6. `test_cancel_in_transit_no_stock_moved` — `transfers.cancel_transfer(transfer_id, actor_sub)` sets status to `"cancelled"`; neither location's on-hand changes (transfer was in-transit, stock never moved).

7. `test_cancel_completed_raises` — attempting to cancel an already-completed transfer raises `HTTPException(status_code=409)` (terminal-status guard).

8. `test_flag_off_create_transfer_404` — with flag off, `create_transfer` raises 404.

### 5.3 `tests/test_fac_receiving.py`

**setUp** binds: `T.facilities`, `T.transfers`, `T.inventory`, `T.reservations`.
**Flags enabled**: both.

**Fixtures**: `_seed_inventory` as above; `_correlation_id()` returns a unique
`uuid4().hex` per call.

**Test cases**:

1. `test_receive_increments_on_hand` — `receiving.receive_shipment(facility_id, location_id, lines=[{sku, qty}], correlation_id=cid)` returns a receipt dict with a `receipt_id`; `inventory.get_inventory(sku, location_id)["on_hand"]` equals the seeded value plus `qty`.

2. `test_receive_creates_location_stock_on_first_receive` — receiving into a location with no prior inventory row creates the row (via the `inventory.adjust` create-on-adjust branch at `app/services/inventory.py:225–248`); `get_inventory` returns a record rather than `None`.

3. `test_receive_replay_idempotent` — submitting the same `correlation_id` twice; the second call is a no-op: `receipt_id = sha256(correlation_id)[:32]` collides (conditional `put_item` with `attribute_not_exists(receipt_id)` guard); on-hand is unchanged after the second call. Assert `get_inventory(sku)["on_hand"]` equals the initial seed plus `qty` (not plus `2*qty`).

4. `test_receive_partial_po` — a receipt with `po_id` set for 3 of an ordered 5 units records `received_qty=3`; a second receipt of 2 more units advances `received_qty=5` and `status="complete"`; both still idempotent under replay.

5. `test_receive_inventory_disabled_skip` — with `S.inventory_reservations_enabled = False`, `receive_shipment` still writes the receipt header row but skips the `inventory.adjust` call; on-hand at the location is zero (no row was created). This mirrors the RMA restock guard at `app/services/returns_rma.py:424`.

6. `test_flag_off_receive_404` — with `S.facility_fulfillment_enabled = False`, `receive_shipment` raises 404.

### 5.4 `tests/test_fac_pick_pack_ship.py`

**setUp** binds: `T.facilities`, `T.transfers`, `T.picklists`, `T.shipments`,
`T.inventory`, `T.reservations`.
**Flags enabled**: both.

**Fixtures**:
- `_seed_inventory(sku, on_hand, location_id)` via `inventory.set_on_hand`.
- `_seed_order(order_id, lines)` writes synthetic rows directly into the test's
  in-memory order store. Because the FAC picking service imports
  `commerce_order_service` to read order lines, this fixture must either (a) patch
  `picking.commerce_order_service.get_order_lines` as a `MagicMock` returning a
  known list, or (b) bind `T.orders` / `T.order_items` and write rows directly.
  Option (b) is preferred for integration fidelity: bind the `orders` and
  `order_items` handles alongside the FAC handles.

**Test cases**:

1. `test_generate_picklist` — `picking.generate_picklist(order_id, facility_id, actor_sub)` creates a META row with `status="open"` and one `LINE#0` row per order line carrying `sku`, `qty`, `from_location_id`, `status="pending"`.

2. `test_confirm_pick_all_lines_commits_reservation` — after seeding a reservation (via `inventory.reserve`), calling `picking.confirm_pick(picklist_id, line_index=0, picked_qty=qty, actor_sub)` marks the line `picked` and, when all lines are picked, calls `inventory.commit_reservation(reservation_id)`; on-hand decrements by `qty` and `reserved` returns to 0.

3. `test_confirm_pick_idempotent` — confirming the same line twice (same line index, same qty) is a no-op on the second call (status guard on `"pending"` → `"picked"` transition); `commit_reservation` is called exactly once.

4. `test_confirm_pick_no_reservation_adjust_fallback` — when no reservation exists for the line (e.g., inventory flag was off at order time), `confirm_pick` calls `inventory.adjust(sku, -qty, reason="pick", ...)` directly instead; on-hand decrements without a reservation row.

5. `test_partial_pick_backorder_state` — confirming one of two lines leaves the picklist in `"open"` state (not `"picked"`), and the unconfirmed line remains `"pending"`.

6. `test_pack_creates_shipment` — `picking.pack_picklist(picklist_id, packages=[{contents, weight}], actor_sub)` flips picklist to `"packed"`, creates a shipment META row with `status="draft"`, and writes `PKG#0` row(s); packed quantities reconcile to picked quantities.

7. `test_pack_idempotent` — packing an already-packed picklist is a no-op (conditional guard on `status="picked"`); the shipment is not duplicated.

8. `test_pack_over_qty_409` — attempting to pack more units than were picked raises `HTTPException(status_code=409)`.

9. `test_ship_stamps_carrier_and_tracking` — `shipping_fulfillment.ship_shipment(shipment_id, carrier="UPS", tracking_number="1Z999AA10123456784", actor_sub)` flips shipment to `"shipped"`, persists `carrier` and `tracking_number` on the META row; a `get_shipment` read-back confirms the values.

10. `test_ship_idempotent` — calling `ship_shipment` on an already-shipped shipment is a no-op (conditional guard on `status="packed"`); no second audit event is emitted.

11. `test_cancel_packed_releases_reservation` — cancelling a `"packed"` (but not yet `"shipped"`) shipment calls `inventory.release_reservation` for each active reservation associated with the picklist lines; on-hand is restored and `reserved` returns to 0.

12. `test_flag_off_generate_picklist_404` — with `S.facility_fulfillment_enabled = False`, `generate_picklist` raises 404.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007**: The services under test use no `dev_mode` branch in business logic
(all FAC services follow the `app/services/inventory.py` convention). The moto
tables used in tests are structurally identical to the real DynamoDB tables defined
in `scripts/local-ddb-init.py`; any schema divergence (e.g., a missing `attr_types`
declaration) will surface as a `ValidationException` in the test, acting as a
schema-parity canary.

**Idempotency assertions**: The test suite explicitly verifies every idempotency
guarantee defined in FAC-006 through FAC-010:

- Transfer completion: the `status = in_transit` conditional guard means a second
  `complete_transfer` call leaves on-hand unchanged.
- Receipt replay: `receipt_id = sha256(correlation_id)[:32]` collides; the
  conditional `put_item` (same pattern as `commerce_order_service.py:67`) rejects
  the duplicate; on-hand is not double-incremented.
- Pick confirm: the `status = pending` → `picked` conditional guard; `commit_reservation`
  idempotency is already tested in `tests/test_ofb_inventory.py`; FAC-015 only
  asserts the upstream call is made exactly once.
- Pack: the `status = picked` conditional guard on picklist.
- Ship: the `status = packed` conditional guard on shipment.

**Security**: The E2E spec asserts that a USER-role session (Alice) receives 403
when attempting a warehouse mutation. This validates the `require_admin_or_root_csrf`
gate introduced by FAC-005 and FAC-011. The pytest suites do not test auth (that is
handled by `app/auth/` unit tests); they call service functions directly.

**Audit events**: The suites do not assert on audit-event content (audit is
best-effort fire-and-forget; the `_audit()` helper swallows all exceptions). They
confirm that audit failures do not propagate to callers — i.e., patching
`app.services.alerts.audit_event` to raise does not cause any service function to
raise.

## 8. Backward Compatibility & Migration

FAC-015 is test-only. It adds no new code paths, database rows, or API surfaces. The
only risk is that a poorly written test could inadvertently mutate a live table
handle via a leaked `object.__setattr__` call; the `addCleanup` / `ExitStack`
pattern (identical to `tests/test_ofb_returns_rma.py:117–126`) prevents this.

The existing `tests/test_ofb_inventory.py` and `tests/test_ofb_returns_rma.py` suites
are not modified by this ticket. The new FAC suites import `app.services.inventory`
alongside the FAC services; since they bind `T.inventory` in the same `setUp`, there
is no cross-test pollution.

The Playwright config at `frontend/playwright.config.ts` (1 worker, 1 retry,
Chromium only) requires that the new `facility-fulfillment.spec.ts` creates no
shared module-level state that persists across retried tests. All describe-block
variables (`facilityId`, `locationId`, `transferId`, `receiptId`, `picklistId`,
`shipmentId`) are declared `let` at describe scope and assigned in `beforeAll`; they
are effectively reset on a Playwright worker restart (retry) because the module
re-initializes from the `beforeAll`.

        self.stack.enter_context(mock_aws())
        ddb = boto3.resource("dynamodb", region_name="us-east-1")

        self.fac_table = _t(ddb, "facilities", "facility_id", "sk", ...)
        self.xfr_table = _t(ddb, "transfers", "transfer_id", "sk", ...)
        ...

        from app.core import tables as T_mod

        from app.services import facilities, transfers, receiving, picking, shipping_fulfillment

        # bind handles + restore on cleanup
        for attr, tbl in [("facilities", self.fac_table), ...]:
            orig = getattr(T_mod.T, attr)
            object.__setattr__(T_mod.T, attr, tbl)

        self.fac = facilities
        self.xfr = transfers
        ...
