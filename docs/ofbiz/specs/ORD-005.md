# ORD-005 — Order state-machine service

**Type:** Feature | **Priority:** P0 | **Estimate:** 4 days
**Milestone:** 2 — State machine & status history

---

## 1. Summary & Goal

ORD-005 creates `app/services/order_lifecycle.py` — the pure business-logic layer that owns the order state machine. It introduces:

1. `TRANSITIONS: dict[str, set[str]]` — the legal transition graph as data, derived from the ORD-001 design.
2. `transition_order(order_id, target_status, *, actor, reason, idempotency_key=None)` — the single public entry point that validates an edge, performs a conditional `update_item` on the ORDER-SK header (optimistic concurrency on the current `lifecycle_status`), mirrors the legacy `status` field, and returns an `OrderTransitionResult`.
3. `get_order_lifecycle(order_id)` — a thin read helper that fetches the ORDER-SK header and returns an `OrderLifecycleOut`, used by ORD-011 router endpoints.
4. Typed exception classes (`OrderTransitionError`, `OrderNotFoundError`, `OrderConflictError`) that the ORD-011 router maps to HTTP 409/404/409.

The service is a pure additive layer over the header written by `commerce_order_service.create_order` (`app/services/commerce_order_service.py:72`) and never touches `order_items` rows. When `S.order_lifecycle_enabled` is `False` (default), no code path imports or calls this service.

### 2.2 Deterministic `order_id` derivation

`app/services/commerce_order_service.py:67` computes:
```python
order_id = hashlib.sha256(corr.encode("utf-8")).hexdigest()[:32]
```
ORD-005 mirrors this pattern for the transition `event_id`:
```python
event_id = hashlib.sha256(
    f"{order_id}|{from_status}|{to_status}|{idempotency_key or ''}".encode()
).hexdigest()[:16]
```
Both use SHA-256 → hex prefix; the idempotency semantics are identical — the same inputs always produce the same ID, so a replayed transition with the same `idempotency_key` can be detected by checking whether the HIST row already exists (ORD-006) before writing.

The KYC service's `update_item` pattern (`app/services/kyc_cases.py:210-228`) uses a `version` counter as the CAS predicate (`ConditionExpression="version = :expected_version"`); ORD-005 instead guards on `lifecycle_status = :current_status`, which is semantically equivalent (the current value must match for the write to proceed) but does not require a separate counter field.

## 3. Data Model

ORD-005 reads and writes the `orders` table exclusively through the ORDER-SK header row. It does not create new DynamoDB items (HIST rows are written by ORD-006, which ORD-005 calls as a hook).

### 3.1 Orders table — header row (ORDER-SK), additive fields

**Table**: `orders` (env `ORDERS_TABLE_NAME`, default `"orders"`)
**Key**: `order_id` (S, PK) + `sk="ORDER"` (S, range key added by ORD-003)

Fields written or updated by `transition_order`:

| Attribute | Type | Written by | Notes |
|---|---|---|---|
| `lifecycle_status` | S | ORD-005 first write via ORD-007; updated on each transition | GSI_ORDER_STATUS PK — set to `target_status.value` |
| `updated_ts` | N | ORD-005 on each transition | `now_ts()`; GSI_ORDER_STATUS SK |
| `status` | S | ORD-005 mirrors `lifecycle_status` | legacy field; keeps existing `GSI_STATUS` populated |
| `updated_at` | S | ORD-005 | ISO-8601 string (`_now_iso()`) |
| `pre_hold_status` | S | ORD-005 entering/exiting `held` | Saved when entering `held`; cleared when resuming |

All other fields (`order_id`, `user_id`, `source_system`, `correlation_id`, `currency`, `amount_cents`, `line_item_count`, `metadata`, `created_at`) are written only at creation by `commerce_order_service.create_order` and never touched by ORD-005.

### 3.2 DynamoDB GSI_ORDER_STATUS (from ORD-003)

After a transition, `lifecycle_status` (S) and `updated_ts` (N) are written to the ORDER header. DynamoDB automatically projects these into `GSI_ORDER_STATUS`:
- PK: `lifecycle_status` (S)
- SK: `updated_ts` (N) — `attr_types={"updated_ts": "N"}` declared in `scripts/local-ddb-init.py` by ORD-003

This enables admin list queries by status (ORD-011/ORD-012).

### 3.3 HIST rows (written by ORD-006 hook)

ORD-005 calls `_append_history_row(order_id, from_status=..., to_status=..., actor=..., reason=..., event_id=..., ts=...)` after a successful `update_item`. This function lives in ORD-006 (`order_lifecycle.py`'s internal helper) and appends:

```
SK = HIST#{ts:020d}#{event_id}
```

The HIST row is written after the CAS-protected header update. If the HIST write fails, the state change is not rolled back (best-effort ordering; matches the platform's audit convention — see CLAUDE.md).

#### 4.1.1 Typed exceptions

```python
class OrderNotFoundError(Exception):
    """The order_id does not correspond to an existing ORDER-SK row."""
    def __init__(self, order_id: str) -> None:
        super().__init__(f"Order not found: {order_id}")
        self.order_id = order_id


class OrderTransitionError(Exception):
    """The requested transition is not a legal edge in TRANSITIONS."""
    def __init__(self, from_status: str, to_status: str) -> None:
        super().__init__(
            f"Illegal transition: {from_status!r} → {to_status!r}"
        )
        self.from_status = from_status
        self.to_status = to_status


class OrderConflictError(Exception):
    """A concurrent writer changed lifecycle_status before this write landed."""
    def __init__(self, order_id: str) -> None:
        super().__init__(f"Concurrent lifecycle update conflict on order {order_id}")
        self.order_id = order_id
```

These three exceptions map cleanly to HTTP responses in the ORD-011 router:
- `OrderNotFoundError` → 404
- `OrderTransitionError` → 409 (with `code="illegal_transition"`)
- `OrderConflictError` → 409 (with `code="lifecycle_conflict"`)

#### 4.1.2 Transition graph `TRANSITIONS`

```python
_S = OrderLifecycleStatus   # local alias for brevity

TRANSITIONS: dict[str, set[str]] = {
    # Forward arc (happy path)
    _S.CREATED.value:   {_S.APPROVED.value, _S.HELD.value, _S.CANCELLED.value},
    _S.APPROVED.value:  {_S.ALLOCATED.value, _S.HELD.value, _S.CANCELLED.value},
    _S.ALLOCATED.value: {_S.PICKING.value, _S.HELD.value, _S.BACKORDER.value, _S.CANCELLED.value},
    _S.PICKING.value:   {_S.PACKED.value, _S.HELD.value, _S.BACKORDER.value, _S.CANCELLED.value},
    _S.PACKED.value:    {_S.SHIPPED.value, _S.HELD.value, _S.CANCELLED.value},
    _S.SHIPPED.value:   {_S.COMPLETED.value, _S.RETURNED.value},
    _S.COMPLETED.value: {_S.RETURNED.value},
    # Side states
    _S.HELD.value:      {_S.APPROVED.value, _S.ALLOCATED.value, _S.PICKING.value,
                         _S.PACKED.value, _S.CANCELLED.value},
    _S.BACKORDER.value: {_S.ALLOCATED.value, _S.PICKING.value, _S.CANCELLED.value},
    # Terminal states — empty sets
    _S.CANCELLED.value: set(),
    _S.RETURNED.value:  set(),
}
```

Design notes:
- `HELD` is reachable from any pre-`shipped` state except `CREATED` (which goes directly to `APPROVED` or `CANCELLED`). Resuming from `HELD` requires knowing the prior state — the service uses `pre_hold_status` saved on the header.
- `BACKORDER` is only reachable from `ALLOCATED` and `PICKING` (warehouse-level states). The `S.order_backorder_enabled` sub-flag (ORD-002) gates whether the service permits `→ BACKORDER` transitions at runtime.
- `CANCELLED` and `RETURNED` are terminal; their sets are empty. Any attempt to transition away from a terminal state raises `OrderTransitionError` immediately (empty set lookup).
- `TRANSITIONS` is module-level data — plain Python dict, no class required. Tests can inspect it directly without instantiating a service object.
- The graph is deliberately encoded as `str → set[str]` (using `.value`) rather than `OrderLifecycleStatus → set[OrderLifecycleStatus]` so that DynamoDB-read strings can be looked up without an enum coercion step that might fail on stale values.

#### 4.1.3 `_derive_event_id`

```python
def _derive_event_id(
    order_id: str,
    from_status: Optional[str],
    to_status: str,
    idempotency_key: Optional[str],
) -> str:
    raw = f"{order_id}|{from_status or ''}|{to_status}|{idempotency_key or ''}"
    return hashlib.sha256(raw.encode("utf-8")).hexdigest()[:16]
```

This mirrors the `order_id = sha256(correlation_id)[:32]` pattern at `commerce_order_service.py:67`. The 16-character hex prefix provides 64 bits of collision resistance, adequate for transition events within a single order.

#### 4.1.6 `transition_order` — primary public function

```python
def transition_order(
    order_id: str,
    target_status: str | OrderLifecycleStatus,
    *,
    actor: str,
    reason: str = "",
    idempotency_key: Optional[str] = None,
) -> OrderTransitionResult:
    """
    Validate and execute one state-machine transition on the order header.

    Parameters
    ----------
    order_id : str
        The SHA-256-derived order ID (32 hex chars).
    target_status : str | OrderLifecycleStatus
        The desired new lifecycle_status.
    actor : str
        The user_sub or "system" driving the transition; written to the HIST row.
    reason : str
        Human-readable reason; written to the HIST row.
    idempotency_key : Optional[str]
        Caller-supplied key for exactly-once semantics; see §5.3.

    Returns
    -------
    OrderTransitionResult
        Contains the updated OrderLifecycleOut, event_id, from_status, to_status.

    Raises
    ------
    OrderNotFoundError  — order_id not found in DynamoDB (or no lifecycle_status).
    OrderTransitionError — current → target is not a legal TRANSITIONS edge.
    OrderConflictError  — ConditionalCheckFailedException (concurrent writer won).
    """
    target = target_status.value if isinstance(target_status, OrderLifecycleStatus) else str(target_status)

    # 1. Read current state
    header = get_order_header(order_id)
    if not header:
        raise OrderNotFoundError(order_id)

    current = str(header.get("lifecycle_status") or "")
    if not current:
        raise OrderNotFoundError(order_id)   # order exists but lifecycle not yet initialised

    # 2. Validate edge
    legal_targets = TRANSITIONS.get(current, set())
    if target not in legal_targets:
        raise OrderTransitionError(current, target)

    # 3. Backorder sub-flag guard
    if target == _S.BACKORDER.value and not S.order_backorder_enabled:
        raise OrderTransitionError(current, target)

    # 4. Derive idempotency ID
    event_id = _derive_event_id(order_id, current, target, idempotency_key)

    # 5. Conditional update_item (optimistic concurrency)
    ts = now_ts()
    now_str = _now_iso()

    update_expr_parts = [
        "lifecycle_status = :new_status",
        "#status = :new_status",       # mirror legacy status
        "updated_ts = :updated_ts",
        "updated_at = :updated_at",
    ]
    expr_values: Dict[str, Any] = {
        ":new_status": target,
        ":updated_ts": ts,
        ":updated_at": now_str,
        ":current_status": current,
    }
    expr_names: Dict[str, str] = {"#status": "status"}

    # HELD bookkeeping: save pre-hold status when entering HELD; clear when leaving
    if target == _S.HELD.value:
        update_expr_parts.append("pre_hold_status = :pre_hold")
        expr_values[":pre_hold"] = current
    elif current == _S.HELD.value:
        update_expr_parts.append("REMOVE pre_hold_status")

    update_expr = "SET " + ", ".join(
        p for p in update_expr_parts if not p.startswith("REMOVE")
    )
    remove_parts = [p[len("REMOVE "):] for p in update_expr_parts if p.startswith("REMOVE")]
    if remove_parts:
        update_expr += " REMOVE " + ", ".join(remove_parts)

    try:
        T.orders.update_item(
            Key={"order_id": order_id, "sk": "ORDER"},
            UpdateExpression=update_expr,
            ExpressionAttributeNames=expr_names,
            ExpressionAttributeValues=expr_values,
            ConditionExpression="lifecycle_status = :current_status",
            ReturnValues="ALL_NEW",
        )
    except ClientError as exc:
        if _is_conditional_conflict(exc):
            raise OrderConflictError(order_id) from exc
        raise

    # 6. Append history row (ORD-006 hook) — best-effort
    try:
        _append_history_row(
            order_id=order_id,
            from_status=current,
            to_status=target,
            actor=actor,
            reason=reason,
            event_id=event_id,
            ts=ts,
        )
    except Exception:
        pass   # history failure does not roll back the transition

    # 7. Audit event — best-effort
    try:
        audit_event(
            "order_status_changed",
            actor,
            None,
            outcome="success",
            order_id=order_id,
            from_status=current,
            to_status=target,
            event_id=event_id,
        )
    except Exception:
        pass

    # 8. Return result
    updated_header = get_order_header(order_id)
    return OrderTransitionResult(
        order=_header_to_lifecycle_out(updated_header),
        event_id=event_id,
        from_status=current,
        to_status=target,
    )
```

The `_append_history_row` function and its HIST row schema are specified in ORD-006. ORD-005 calls it via a plain function call (`from app.services.order_lifecycle import _append_history_row` is not needed — both live in the same file). ORD-006 adds `_append_history_row` as a function defined in the same `order_lifecycle.py` module.

#### 4.1.8 `_header_to_lifecycle_out`

```python
def _header_to_lifecycle_out(header: Dict[str, Any]) -> OrderLifecycleOut:
    """Convert a raw DynamoDB ORDER-SK dict to OrderLifecycleOut."""
    ls_raw = header.get("lifecycle_status")
    ls: Optional[OrderLifecycleStatus] = None
    if ls_raw:
        try:
            ls = OrderLifecycleStatus(ls_raw)
        except ValueError:
            ls = None  # stale/unknown value; degrade gracefully

    return OrderLifecycleOut(
        order_id=header["order_id"],
        status=str(header.get("status") or "pending_payment"),
        created_at=str(header.get("created_at") or ""),
        updated_at=str(header.get("updated_at") or ""),
        source_system=str(header.get("source_system") or ""),
        correlation_id=str(header.get("correlation_id") or ""),
        amount_cents=int(header.get("amount_cents") or 0),
        currency=str(header.get("currency") or "USD"),
        line_item_count=int(header.get("line_item_count") or 0),
        metadata=dict(header.get("metadata") or {}),
        lifecycle_status=ls,
        updated_ts=int(header["updated_ts"]) if header.get("updated_ts") is not None else None,
        pre_hold_status=header.get("pre_hold_status"),
        adjustments=None,   # not fetched here; ORD-011 enriches when requested
        ship_groups=None,   # same
    )
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag guard at the call site

`transition_order` is only reachable when `S.order_lifecycle_enabled` is `True`. The ORD-011 router enforces this:
```python
if not S.order_lifecycle_enabled:
    raise HTTPException(503, detail={"code": "order_lifecycle_disabled"})
```
The service itself does **not** re-check the flag — single-responsibility: the router gates access; the service trusts its caller. This is consistent with `app/services/kyc_cases.py` where `KycCaseStore` methods do not check `S.kyc_*` flags (those checks live in the router).

### 5.2 Legal-edge validation before the DDB round-trip

The transition graph check (step 2) happens entirely in Python before any DDB call. An illegal-edge rejection never touches the database. This means:
- 409 "illegal_transition" responses have zero DDB cost.
- The graph is a pure dict; `TRANSITIONS.get(current, set())` returns an empty set for unknown statuses (e.g. a stale string value not in the enum), producing a clean `OrderTransitionError` rather than a `KeyError`.

### 5.3 Idempotency semantics

If a caller supplies an `idempotency_key`, `_derive_event_id` produces a deterministic `event_id = sha256(order_id|from|to|idempotency_key)[:16]`. On a replay (same inputs, same key):
- The HIST row with that `event_id` already exists (written by ORD-006 on the first attempt).
- The order header's `lifecycle_status` is already `target` (the first attempt succeeded).
- The conditional `update_item` would still fire (`ConditionExpression="lifecycle_status = :current_status"` with `:current_status = target`) — and succeed if `lifecycle_status == target`, or fail with `ConditionalCheckFailedException` if yet another concurrent writer moved it further.

To detect a replay cleanly before issuing the DDB call, `transition_order` should first check: if `current == target` (the header already shows the target state) AND `idempotency_key` is set AND the HIST row for `event_id` exists (ORD-006 §4.1.3 provides `history_row_exists(order_id, event_id) -> bool` — **this function is now owned and defined in ORD-006**), return an `OrderTransitionResult` immediately as a no-op. This avoids the spurious `update_item` on replay.

If ORD-006 has not yet merged, the simpler fallback: if `current == target`, return the current `OrderLifecycleOut` with the pre-computed `event_id` and `from_status=target` (both equal). The caller cannot distinguish a replay from a no-op.

### 5.4 `HELD` bookkeeping

Entering `HELD` from any pre-shipped state is allowed. The service writes `pre_hold_status = current` on the header to record which state the order was in before the hold. Resuming from `HELD`:
- `TRANSITIONS["held"]` returns `{"approved", "allocated", "picking", "packed", "cancelled"}`.
- The caller must explicitly pass the desired resume state as `target_status`; the service does not auto-resume to `pre_hold_status`. This gives the admin control over which state to resume to (e.g., resume to `approved` after resolving a payment hold rather than resuming to `picking`).
- When the transition leaves `HELD`, `REMOVE pre_hold_status` is added to the `UpdateExpression`.

### 5.5 `BACKORDER` sub-flag

`TRANSITIONS["allocated"]` and `TRANSITIONS["picking"]` both include `"backorder"`. However, the service checks `S.order_backorder_enabled` and raises `OrderTransitionError` if the flag is off. This means the graph data is permissive (backorder is a legal edge) but the runtime enforces the flag. Tests must toggle `S.order_backorder_enabled = True` via `object.__setattr__` to exercise the backorder path.

### 5.6 Concurrent update (race condition)

Two concurrent `transition_order` calls for the same `order_id`, both starting from the same `lifecycle_status = "approved"`, both targeting `"allocated"`:
1. Both read `current = "approved"`.
2. Both attempt `update_item` with `ConditionExpression="lifecycle_status = :current_status"` (`:current_status = "approved"`).
3. DynamoDB guarantees serial write order. The first writer succeeds; the header is now `"allocated"`.
4. The second writer's condition fails → `ConditionalCheckFailedException` → `OrderConflictError`.
5. The second caller receives a 409 `code="lifecycle_conflict"` and can retry after re-reading the current state.

This is the "single winner" acceptance criterion from the ticket. Exactly one HIST row is written. No duplicate history.

### 5.7 `lifecycle_status` absent on header (order predates lifecycle)

If the header exists but has no `lifecycle_status` attribute (an order created before ORD-007 stamps the initial `"created"` status), `transition_order` raises `OrderNotFoundError`. This is intentional: the lifecycle service cannot be invoked on an order that has not been initialised into the state machine. ORD-007 provides the backfill path for legacy orders when the flag is enabled.

### 5.8 Terminal state protection

`TRANSITIONS["cancelled"]` and `TRANSITIONS["returned"]` are both empty sets. The transition validation `target not in TRANSITIONS.get(current, set())` evaluates `target not in set()` which is always `True`. This means any attempt to transition out of a terminal state raises `OrderTransitionError` without a separate terminal-check branch. The behaviour is correct-by-construction.

### 5.9 `legacy status` mirror

Every successful transition also writes `"#status": ":new_status"` to keep the `status` field (and `GSI_STATUS`) in sync with `lifecycle_status`. This is the additive coexistence design from ORD-001 Section 3.6. The legacy `status` field was previously only ever `"pending_payment"`; after ORD-005, it mirrors the lifecycle status string. Existing callers that read `order["status"]` will see the lifecycle status value (e.g. `"shipped"`) rather than the perpetual `"pending_payment"`. This is a deliberate, documented behaviour change on flag-on orders.

### 5.10 `UpdateExpression` construction for SET + REMOVE

DynamoDB does not allow `SET` and `REMOVE` in the same clause keyword, but does allow them as separate clauses in one `UpdateExpression` string: `"SET a=:a, b=:b REMOVE c"`. The service constructs the expression by collecting `SET` parts and `REMOVE` parts separately, then concatenating. This avoids injecting `REMOVE` into the `SET` parts list.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

`order_lifecycle.py` contains no `if S.dev_mode` branch. The transition logic, conditional DDB update, idempotency derivation, and audit event emission are identical in dev (DynamoDB Local, port 8001) and prod (real DynamoDB). The `T.orders` handle (`app/core/tables.py:381`) is wired from `S.orders_table_name` (`app/core/settings.py:1124`, env `ORDERS_TABLE_NAME`, default `"orders"`) in all environments.

The `audit_event` call resolves to `app/services/alerts.py:644` in both envs; in dev it writes to DynamoDB Local; in prod to real DynamoDB. No mock branch.

### 7.2 Idempotency

**Transition idempotency**: `_derive_event_id` produces a stable ID from `order_id|from|to|idempotency_key`. A replayed call with the same key returns the same `event_id` and the same logical outcome (see §5.3).

**Conditional update idempotency**: if the header already shows `lifecycle_status == target` (e.g. first call succeeded but the response was lost), the conditional `update_item` fires with `ConditionExpression="lifecycle_status = :current_status"` where `:current_status` is the value read in step 1. If step 1 reads the already-transitioned `target`, the condition becomes `target == target` — the write succeeds but is a no-op (DynamoDB sets the same values). Only if a concurrent writer moved it to a third state does the condition fail.

**HIST row idempotency**: ORD-006's `_append_history_row` uses `ConditionExpression="attribute_not_exists(sk)"` on the HIST row. A replayed write with the same `event_id` (same `HIST#{ts:020d}#{event_id}` SK) fails silently — no duplicate history.

### 7.3 Security

**Ownership enforcement**: `transition_order` accepts an `order_id` and `actor`; it does not verify that `actor` owns the order. Ownership and role checks are the responsibility of the ORD-011 router before calling the service. This is consistent with `KycCaseStore.apply_admin_decision` which also does not re-check `admin_sub` ownership — the router enforces it.

**`actor` sanitisation**: `actor` is written to the HIST row (ORD-006) and to the `audit_event` kwargs. It must be a non-empty string. The ORD-011 router derives `actor` from the authenticated session (`ctx["user_sub"]`) so it is always a valid Cognito sub. If called programmatically (e.g. from ORD-007's auto-approve hook), `actor` is the string `"system"`.

**No money-path fork**: `transition_order` does not touch the billing ledger. Money-out transitions (`→ CANCELLED`, `→ RETURNED`) are handled in ORD-010, which calls `refund_payment` (`app/routers/billing.py:1287`) and `settle_or_reverse_ledger` (`app/services/billing_shared.py:262`); `new_ledger_entry` is at `app/services/billing_shared.py:224`. None of these are called by ORD-005.

**DynamoDB injection**: `UpdateExpression`, `ExpressionAttributeNames`, and `ExpressionAttributeValues` are used for all attribute references; no string interpolation of user-supplied values into the expression string. This follows the established pattern in `app/services/kyc_cases.py:210-228` (the `update_item` call block, with `ExpressionAttributeNames` at line 217).

## 8. Backward Compatibility & Migration

### 8.1 Flag-off orders (existing behavior)

Orders created with `ORDER_LIFECYCLE_ENABLED=false` have no `lifecycle_status` attribute on their header row. These orders are invisible to `transition_order` (step 1 raises `OrderNotFoundError` for `lifecycle_status` absence). Admin endpoints in ORD-011 that list by lifecycle status will simply not include these orders (GSI_ORDER_STATUS is sparsely populated).

### 8.2 Enabling the flag on a live system

When `ORDER_LIFECYCLE_ENABLED` is flipped to `true`:
1. **New orders** receive `lifecycle_status="created"` (ORD-007).
2. **Existing orders** (created before the flag flip) have no `lifecycle_status` and cannot be transitioned until they are backfilled. ORD-007 optionally provides an admin-triggered backfill endpoint (`POST /ui/orders/lifecycle/backfill`) that stamps `lifecycle_status="created"` on all flag-less ORDER headers.

### 8.3 No changes to existing code paths

`commerce_order_service.py`, `shoppingcart.py:581`, `file_bundle_checkout.py`, and `returns_rma.py` are all modified by ORD-003 (adding `sk="ORDER"` and `get_item` key fix) and ORD-007 (optionally stamping `lifecycle_status` at creation). ORD-005 itself makes no changes to any of these files.

### 8.4 Rollback

If `ORDER_LIFECYCLE_ENABLED` is reset to `false` after being on:
- New orders revert to the old shape (no `lifecycle_status`).
- Orders already transitioned retain their `lifecycle_status` attribute but the lifecycle service is no longer called.
- Existing `GSI_ORDER_STATUS` entries remain populated but receive no new writes.
- No data loss; no DynamoDB schema change is required to roll back.
