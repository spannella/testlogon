# ECM-012 — Order fulfillment-status read service

## 1. Summary & Goal

ECM-012 adds `order_fulfillment_status(order_id, *, user_sub)` to `app/services/store_integration.py` — a read-only aggregation function that projects three upstream data planes (ORD lifecycle state, FAC ship-group pick/pack/ship state, SHP tracking numbers) into a single `OrderFulfillmentStatusOut` response, ownership-checked against the requesting `user_sub`.

The goal is to give a buyer a single, coherent view of their order's progress from "placed" through "delivered" without forking any write path. When `STORE_SHOW_FULFILLMENT_STATUS` is off (or when the upstream ORD/SHP flags are off), the function returns only the legacy scalar order summary that already exists on the `orders` table today. Any upstream lookup that fails or returns nothing degrades gracefully — the call never returns 500 due to a missing shipment or lifecycle row.

This ticket is a **pure read service**. No billing paths are touched, no order state is advanced, and no new DynamoDB write paths are introduced. The underlying tables written by ORD-005/ORD-012 and SHP-012/SHP-014 are queried; `store_integration.py` is not their owner.

## 3. Data Model

ECM-012 is a read-only service. It introduces **no new DynamoDB tables and no new write paths**. All tables queried are created by upstream tickets. The sections below describe the expected schema those tables will carry when ECM-012 reads them, based on the upstream ticket specifications.

### 3.1 `orders` table (existing, extended by ORD-003)

PK: `order_id` (S). No sort key on the header row. The upstream ORD-003 adds single-table rows under additional sort-key partitions:

| Row type | SK prefix | Key additive fields |
|---|---|---|
| Header | *(none — PK-only)* | `user_id`, `status`, `lifecycle_status` (ORD), `fulfillment_status` (SHP-014), `created_at` |
| Status history | `HIST#{ts:020d}#{event_id}` | `from_status`, `to_status`, `actor`, `reason`, `ts` |
| Ship group | `SHIPGRP#{ship_group_id}` | `ship_method`, `address_ref`, `item_refs[]`, `fulfillment_sub_status` |
| Adjustment | `ADJ#{adjustment_id}` | `adj_type`, `amount_cents`, `label` |

`lifecycle_status` is added additively by ORD-007 when `ORDER_LIFECYCLE_ENABLED` is on; with the flag off the field is absent and ECM-012 must handle that gracefully. `fulfillment_status` is added additively by SHP-014 when `SHIPPING_ENABLED` is on.

Existing GSIs remain unchanged: `GSI_USER` (`user_id`/`created_at`) and `GSI_STATUS` (`status`/`created_at`) at `scripts/local-ddb-init.py:291`. ORD-003 adds `GSI_ORDER_STATUS` (`lifecycle_status`/`updated_ts`, numeric `updated_ts`) and `GSI_ORDER_SHIPDATE` (`ship_day_bucket`/`ship_ts`, numeric `ship_ts`) — ECM-012 does not query those GSIs (it fetches by `order_id` directly).

Because ECM-012 queries `T.orders` by the known `order_id` (a direct `get_item` or a `query` when also fetching child rows), there is no GSI lookup here. The `orders` table already has `attr_types` for numeric GSI sort keys from ORD-003 — no change needed in `scripts/local-ddb-init.py` for this ticket.

### 3.2 `shipments` table (new, created by SHP-010)

PK: `shipment_id` (S), SK: `sk` (S). SHP-010 creates this table with rows:

| Row type | SK | Key fields |
|---|---|---|
| Shipment header | `META` | `order_id`, `ship_group_seq`, `carrier`, `tracking_number`, `status`, `method`, `shipped_at` |
| Shipment item | `ITEM#{item_id}` | `order_item_id`, `quantity`, `sku` |
| Package | `PKG#{n}` | `weight_oz`, `dims`, `contents[]` |

GSI on `shipments`: `GSI_ORDER` (`order_id`/`created_at`, numeric `created_at`) is needed so ECM-012 can find all shipments for an `order_id` without scanning. SHP-010 specifies this GSI; the `attr_types={"created_at":"N"}` entry must appear in `scripts/local-ddb-init.py` when that ticket adds the table.

ECM-012 queries `T.shipments` via `GSI_ORDER` keyed on `order_id` to enumerate all ship groups + tracking numbers.

### 3.3 No new tables in `scripts/local-ddb-init.py` for ECM-012

ECM-012 reads from `T.orders` (existing) and `T.shipments` (new in SHP-010). Neither table definition changes as a result of this ticket. The `Tables` dataclass (`app/core/tables.py`) must gain `shipments: Any` (added by SHP-010); ECM-012 simply references `T.shipments`.

## 4. API / Service Design

### 4.1 Service function in `app/services/store_integration.py`

```python
def order_fulfillment_status(
    order_id: str,
    *,
    user_sub: str,
) -> "OrderFulfillmentStatusOut":
```

**Algorithm:**

1. Fetch the order header: `T.orders.get_item(Key={"order_id": order_id})`. If absent, raise `HTTPException(404, "Order not found")`.
2. Ownership check: if `item["user_id"] != user_sub`, raise `HTTPException(403, "Forbidden")`.
3. Build the **legacy base** from the header unconditionally (status, order_id, created_at, amount_cents, currency). This is returned even with all flags off.
4. If `_integration_enabled("store_show_fulfillment_status")` is False OR `ORDER_LIFECYCLE_ENABLED` is False: return the base with only `legacy_status` populated and all enriched fields `None`.
5. Attempt `_safe_upstream(lambda: _fetch_lifecycle_rows(order_id), default=[])` to get history + ship-group rows (SK prefix `HIST#` and `SHIPGRP#`). Degradation: if this raises or returns empty, `lifecycle_status` falls back to `item.get("lifecycle_status")` already on the header.
6. If `SHIPPING_ENABLED` is False: skip shipment lookup; `ship_groups` carry only the ORD-level `fulfillment_sub_status`, no tracking.
7. Attempt `_safe_upstream(lambda: _fetch_shipments(order_id), default=[])` to query `T.shipments` via `GSI_ORDER`. For each shipment, compute `tracking_url = build_tracking_url(shipment["carrier"], shipment["tracking_number"])` (reusing `app/services/carrier_tracking.build_tracking_url:33`).
8. Merge ship-group sub-statuses from ORD rows and SHP shipments into `ShipGroupFulfillmentOut` items.
9. Derive top-level `fulfillment_status` from `item.get("fulfillment_status")` (written by SHP-014); if absent, compute from the ship groups: all delivered → `delivered`; any shipped → `partially_shipped` or `shipped`; else `unfulfilled`.
10. Return `OrderFulfillmentStatusOut`.

## 5. Detailed Behavior & Edge Cases

**Ownership enforcement.** The `orders` table carries `user_id` (set by `CommerceOrderService.create_order` at `commerce_order_service.py:74`). The service compares `item["user_id"] != user_sub` and raises 403 before any enrichment. An admin caller (ECM-014's admin path, if any) should call the service with `user_sub=None` and a separate ownership bypass parameter — but that is ECM-014's concern, not ECM-012's.

**Foreign or nonexistent order_id.** `T.orders.get_item` returns `{}` when the item does not exist (DynamoDB never raises on a miss). The service raises `HTTPException(404)` when `resp.get("Item")` is falsy.

**Flag off — legacy fallback.** When `_integration_enabled("store_show_fulfillment_status")` returns False, the function returns immediately after building the base dict: `order_id`, `legacy_status=item["status"]`, all optional fields absent/None, `flag_active=False`. No upstream tables are queried. This is byte-for-byte safe because `item["status"]` is always present on every order row (set to `"pending_payment"` unconditionally at `commerce_order_service.py:75`).

**ORD flag on but no lifecycle rows yet.** If `ORDER_LIFECYCLE_ENABLED` is on but the order was created before ORD-007 was deployed (no `lifecycle_status` on the header, no HIST rows), the service returns `lifecycle_status=None`, `status_history=[]`. No error.

**SHP flag on but no shipments.** `_fetch_shipments` returns `[]` (GSI query with zero results). `fulfillment_status` falls back to `item.get("fulfillment_status", "unfulfilled")`. `ship_groups` is empty. No error.

**Upstream query timeout / DDB error.** Both `_fetch_lifecycle_rows` and `_fetch_shipments` are wrapped in `_safe_upstream(call, default)` (from ECM-002). Any exception — `ClientError`, timeout, unexpected shape — returns the `default` (`[]`), and the function continues with partial data. The caller receives a degraded but valid response, not a 500.

**Tracking URL computation.** `build_tracking_url(carrier, tracking_number)` at `carrier_tracking.py:33` returns `None` for unknown carriers. The `tracking_url` field on `ShipGroupFulfillmentOut` is `Optional[str]`; a `None` URL is valid. The URL is computed in the service layer and never stored, matching the existing convention in `purchase_history.get_transaction_info` (`:389`).

**Multi-package shipments / multiple ship groups.** A single order may have N ship-group rows (ORD `SHIPGRP#` items) and M shipment records (SHP). The merge logic joins on `ship_group_seq`: each ORD ship-group row carries a `ship_group_seq` int that matches the `ship_group_seq` on the SHP shipment header (set by SHP-010). If no shipment exists for a group (not yet shipped), the `ShipGroupFulfillmentOut` carries ORD sub-status only, with `shipment_id=None`.

**Pagination on order child rows.** The `orders` table query for child rows (HIST/SHIPGRP/ADJ) must loop `LastEvaluatedKey` per the CLAUDE.md DDB note ("DDB FilterExpression doesn't reduce page size"). `_fetch_lifecycle_rows` must implement this loop; the volume of rows per order is small in practice (one header + O(10) history entries) but the loop is required for correctness.

**`created_at` field type.** The existing `orders` table stores `created_at` as an ISO string (computed by `_now_iso()` at `commerce_order_service.py:65`, written into the record at `:76`). `amount_cents` is stored as an `int` (`:81`). The service must coerce `Decimal` to `int` for `amount_cents` (DynamoDB returns numeric attributes as `Decimal`), matching the pattern in `shoppingcart._ddb_int` (`shoppingcart.py:46`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**No dev/prod code fork.** `order_fulfillment_status` reads from DynamoDB Local in dev (via the existing `T` handle setup in `app/core/tables.py`) and from real DynamoDB in prod. No `S.dev_mode` branch exists in this function. The `_safe_upstream` wrapper handles both environments identically: if the tables don't exist (e.g. ORD/SHP not yet deployed) the upstream call raises and the wrapper returns the default. This matches the SECOPS-007 parity requirement.

**Idempotency.** This is a pure read function; idempotency is trivially satisfied — repeated calls with the same `(order_id, user_sub)` return the same response (or a more-progressed one if state advanced in the meantime). No writes occur.

**Ownership security.** The 403 check on `item["user_id"] != user_sub` runs unconditionally before any enrichment. A timing attack that fetches partial data before the check is not possible because the header is fetched first and the check is synchronous.

**No PII leakage.** `ShipGroupFulfillmentOut` does not include delivery address detail (only `address_ref`, an opaque reference string from the ship-group row). The full address lives in ORD ship-group rows and is not projected into ECM-012's response unless explicitly added (which this spec does not do).

**Tracking URL generation.** Tracking URLs are computed server-side via `build_tracking_url` (already public information) and never stored, matching the convention in `purchase_history.get_transaction_info` (`purchase_history.py:389–394`). No new secret material is generated or exposed.

**`_safe_upstream` and exception suppression.** The wrapper swallows all exceptions from upstream reads. This is intentional: a non-responsive ORD/SHP table must not cause a 500 on the cart/checkout/post-order flow. The degraded response always includes `legacy_status` so the buyer still has useful information.

## 8. Backward Compatibility & Migration

**Existing order records are byte-for-byte unchanged.** The `orders` table rows written today by `CommerceOrderService.create_order` (`commerce_order_service.py:72–85`, dict construction + `put_item`) are not modified. ECM-012 adds no write path.

**Existing `ShoppingCartPurchaseOut` is unchanged.** The model at `app/models.py:993` does not gain new fields from ECM-012 (enrichment fields are on `OrderFulfillmentStatusOut`, a separate response).

**Existing purchase-history tracking endpoint is unchanged.** `GET /ui/purchases/transactions/{txn_id}/tracking` (`purchase_history.py:118`) continues to serve the `purchase_transactions` shipping sub-record without modification. ECM-012 reads both the order table (for lifecycle) and the shipments table (for ship groups); it does not replace the transaction tracking endpoint.

**Zero-data-migration path.** All ORD/SHP data is additive (new SK rows under existing PKs, new tables). An order created before ORD-005 was deployed simply has no `lifecycle_status` on the header; ECM-012 returns `lifecycle_status=None` for it, which is valid per the Pydantic model's `Optional[str] = None` default.

**No DDB schema changes in this ticket.** `scripts/local-ddb-init.py` is not modified by ECM-012. The `orders` GSI additions are ORD-003's responsibility; the `shipments` table creation is SHP-010's responsibility.

**Flag rollout.** All four flags default to `false`. In production, the intended rollout order is: deploy ORD/SHP tables + services first, validate data is populating, then flip `STORE_SHOW_FULFILLMENT_STATUS=true`. With any flag off, the existing behavior is preserved exactly.

## 10. Open Questions / Assumptions

1. **Assumption: `T.shipments` is added to the `Tables` dataclass and `T` singleton by SHP-010**, not by ECM-012. If SHP-010 is not deployed when ECM-012 is deployed, `T.shipments` will not exist and `_fetch_shipments` must handle `AttributeError` (the `_safe_upstream` wrapper covers this).

2. **Assumption: `ShipGroupFulfillmentOut` and `OrderFulfillmentStatusOut` are added to `app/models.py` by ECM-003**, not by ECM-012. ECM-012 imports them with a `TYPE_CHECKING` guard or a direct import once ECM-003 is merged.

3. **Assumption: the `ship_group_seq` int on the ORD `SHIPGRP#` row is the join key** to the `ship_group_seq` field on the SHP shipment header. This join contract should be confirmed with ORD-009 and SHP-010 implementors before coding the merge logic.

4. **Open: does `_integration_enabled("store_show_fulfillment_status")` return False when only `STORE_INTEGRATION_ENABLED` is off, or also when the sub-flag is off?** The ECM-002 spec says `_integration_enabled(sub_flag)` gates on BOTH the master flag AND the sub-flag. ECM-012 assumes this two-level AND semantics. If the semantics change in ECM-002, the gate call may need adjustment.

5. **Open: is `lifecycle_status` stored on the order header row (by ORD-007) or only in HIST rows?** The ORD-007 spec says it stamps `lifecycle_status` on the header at `:72` of `commerce_order_service.py`. ECM-012 reads it from the header first (`item.get("lifecycle_status")`), falling back to the most recent HIST row if absent. If ORD-007 changes this decision, the fallback logic needs updating.

6. **Open: address ref format.** The ship-group row carries `address_ref` (an opaque string, presumably a user address ID from `T.addresses`). ECM-012 does not resolve this to a full address. If the frontend needs a formatted address in the fulfillment status view, a separate address lookup will be required (out of scope for ECM-012, potentially ECM-014's concern).

7. **Assumption: `STORE_SHOW_FULFILLMENT_STATUS` returns 503 (not 404) when off**, consistent with the ECM-002 convention of returning 503 for disabled integration features (the 503 pattern appears in `app/routers/call_recording.py:41` and `app/routers/chat_bot.py:83`; note that `app/routers/inventory.py` uses 404 for its flag-disabled gate, not 503). If ECM-002 adopts 404 instead, the HTTP endpoint in ECM-014 should be adjusted accordingly.
