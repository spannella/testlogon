# MFG-011 — Manufacturing router (BOM / routing / work orders / MRP)

**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days
**Milestone:** 4 — Router / HTTP surface

---

## 1. Summary & Goal

MFG-011 creates `app/routers/manufacturing.py`, the single HTTP surface that
exposes all four manufacturing service modules under the `/ui/manufacturing/*`
prefix. It is a thin adapter layer — no business logic lives here; every
handler delegates immediately to the service functions implemented by MFG-004,
MFG-005, MFG-007, and MFG-010. The router is registered in `app/main.py`
immediately after `returns_rma_router` (currently wired at `app/main.py:878` — verified).

The router delivers:

1. **BOM endpoints** — CRUD for BOM headers and components, and the
   multi-level BOM explosion preview.
2. **Work-center / routing endpoints** — CRUD for work centers and their
   ordered routing tasks, plus the routing cost estimate.
3. **Work-order lifecycle endpoints** — create, list, get, and all five
   lifecycle transitions (release, start, complete, cancel, and a standalone
   GET for the issued-components list).
4. **MRP endpoints** — trigger a lite-MRP run, get a run by ID.

**All write endpoints require** `require_admin_or_root_csrf`
(`app/auth/policy.py:100` — verified). GET endpoints use the same dependency so that
manufacturing data is not publicly readable.

Every endpoint calls the service's `_require_enabled()` guard as its first
statement; when `S.manufacturing_mrp_enabled` is `False` the entire router
is a no-op that returns HTTP 404 for every path.

**Additive constraint**: with the feature flag off, every existing route in
the application — shop, cart, orders, billing, inventory, returns — is
byte-for-byte unchanged. Mounting the router itself is safe at all times.

### 2.4 Literal-before-dynamic route ordering (FastAPI gotcha)

`CLAUDE.md` and `app/routers/audit_export.py:137–139` (verified) document that FastAPI
matches routes in declaration order. The literal segments `mrp/runs`,
`mrp/run` (POST), and `work-orders/{id}/release|start|complete|cancel` must be
declared before any dynamic `{id}` catch-all for the same prefix. The exact
ordering problem arose in the audit-export router where `/schedules` had to
precede `/{export_id}` — an identical risk exists here for:

- `/ui/manufacturing/work-orders/{id}/release` — the action literal must
  appear before `GET /ui/manufacturing/work-orders/{id}` (or conversely, since
  `POST /{id}/release` is distinguishable from `GET /{id}` by method, the risk
  is only real when two routes share the same method _and_ prefix).
- `/ui/manufacturing/mrp/run` (POST) and `/ui/manufacturing/mrp/runs/{id}`
  (GET) — the prefix `mrp/run` vs `mrp/runs/{id}` are distinct string prefixes
  so there is no ambiguity; however both must precede any hypothetical future
  `mrp/{id}` catch-all.
- `/ui/manufacturing/boms/{id}/explode` — literal path suffix `explode` must
  be declared before any route that would match `{something}` at that position.

## 4. API / Service Design

### 4.1 Router module: `app/routers/manufacturing.py`

```python
"""Manufacturing router — BOM / routing / work orders / MRP (MFG-011).

Additive + flag-gated (MANUFACTURING_MRP_ENABLED, default OFF). Every handler
calls _require_enabled() first; with the flag off all paths return 404 and the
existing shop/cart/orders/billing paths are byte-for-byte unchanged.

Role: ALL endpoints require require_admin_or_root_csrf.
SECOPS-007: identical behaviour dev (moto/local DDB) and prod (real DDB); no
dev_mode branch in the business logic.

Route-ordering note: literal sub-paths (e.g. /boms/{id}/explode,
/work-orders/{id}/release) are declared BEFORE any catch-all /{id} GET routes
for the same prefix to prevent FastAPI from matching the literal as a path param.
"""
from __future__ import annotations

from fastapi import APIRouter, Depends, HTTPException, Query
from typing import Any, Dict, List, Optional

from app.auth.deps import AuthenticatedUser
from app.auth.policy import require_admin_or_root_csrf
from app.models import (
    BomHeaderIn, BomOut, BomComponentIn,
    WorkCenterIn, WorkCenterOut,
    RoutingTaskIn, RoutingTaskOut, RoutingCostOut,
    WorkOrderCreateIn, WorkOrderOut,
    MrpRunIn, MrpRunOut, MrpRequirementOut,
)
from app.services import manufacturing_bom as bom
from app.services import manufacturing_routing as routing
from app.services import manufacturing_work_orders as wo
from app.services import manufacturing_mrp as mrp

manufacturing_router = APIRouter(
    prefix="/ui/manufacturing",
    tags=["manufacturing"],
)


def _require_enabled() -> None:
    bom._require_enabled()  # all four services share the same flag
```

### 4.2 BOM endpoints

Route ordering: `/boms/active` (if added in future), then `/boms/{id}/explode`,
then `/boms/{id}`, then `/boms`.

```python
@manufacturing_router.post("/boms", response_model=BomOut, status_code=201)
async def create_bom(
    body: BomHeaderIn,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> BomOut:
    _require_enabled()
    rec = bom.create_bom(
        product_sku=body.product_sku,
        name=body.name,
        output_quantity=body.output_quantity,
        components=[c.model_dump() for c in body.components],
        status=body.status,
        correlation_id=body.correlation_id,
        user_sub=user.sub,
    )
    return BomOut(**rec)


@manufacturing_router.get("/boms", response_model=List[BomOut])
async def list_boms(
    product_sku: Optional[str] = Query(default=None, max_length=256),
    status: Optional[str] = Query(default=None),
    limit: int = Query(default=100, ge=1, le=500),
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> List[BomOut]:
    _require_enabled()
    items = bom.list_boms(product_sku=product_sku, status=status, limit=limit)
    return [BomOut(**i) for i in items]


# IMPORTANT: /boms/{id}/explode declared BEFORE /boms/{id} so "explode" is
# never captured as an id path param.
@manufacturing_router.get("/boms/{bom_id}/explode")
async def explode_bom(
    bom_id: str,
    build_qty: int = Query(ge=1, le=10_000_000),
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> Dict[str, Any]:
    _require_enabled()
    components = bom.explode_bom(bom_id, build_qty)
    return {"bom_id": bom_id, "build_qty": build_qty, "components": components}


@manufacturing_router.get("/boms/{bom_id}", response_model=BomOut)
async def get_bom(
    bom_id: str,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> BomOut:
    _require_enabled()
    rec = bom.get_bom(bom_id)
    if rec is None:
        raise HTTPException(status_code=404, detail="BOM not found")
    return BomOut(**rec)


@manufacturing_router.patch("/boms/{bom_id}", response_model=BomOut)
async def update_bom(
    bom_id: str,
    body: dict,          # sparse patch: name?, status?
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> BomOut:
    _require_enabled()
    rec = bom.update_bom(
        bom_id,
        name=body.get("name"),
        status=body.get("status"),
        user_sub=user.sub,
    )
    return BomOut(**rec)


@manufacturing_router.delete("/boms/{bom_id}", status_code=204)
async def delete_bom(
    bom_id: str,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> None:
    _require_enabled()
    bom.delete_bom(bom_id, user_sub=user.sub)
```

**`body: dict` for PATCH** mirrors the sparse-patch style used by other
platform routers (e.g. `app/routers/profile.py`). Only `name` and `status` are
read; unknown keys are silently ignored. A future ticket may introduce a
dedicated `BomPatchIn` Pydantic model if validation tightens.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off behaviour

When `S.manufacturing_mrp_enabled` is `False`:

- Every handler calls `_require_enabled()` → `bom._require_enabled()` →
  raises `HTTPException(status_code=404, ...)`.
- `GET /openapi.json` still lists all paths (FastAPI registers routes at import
  time regardless of flag), but all return 404 at runtime. This is the same
  behaviour as `app/routers/inventory.py` — the OpenAPI schema always reflects
  the full surface; the flag controls runtime availability.
- No imports of any `T.mfg_*` handle occur in the router itself; handles are
  only accessed inside the service layer, which is never called when the flag
  is off.

### 5.2 Literal action sub-paths vs dynamic `{id}` catch-all

FastAPI routes match in declaration order. The risks are:

| Risk scenario | Mitigation |
|---------------|------------|
| `GET /boms/explode` captured as `get_bom(bom_id="explode")` | Declare `GET /boms/{id}/explode` before `GET /boms/{id}` — FastAPI will match the more specific three-segment path first |
| `POST /work-orders/abc/release` captured by `GET /work-orders/{id}` | Different HTTP methods; no ambiguity. But keep action POST routes declared before the GET for clarity and future-proofing |
| `POST /mrp/run` captured by a hypothetical `GET /mrp/{id}` | Declare `/mrp/run` and `/mrp/runs/{id}` before any `/mrp/{id}` if one is added |

The `CLAUDE.md` audit-export schedules note (`app/routers/audit_export.py:137` — verified)
is the canonical reference for this ordering discipline.

### 5.3 PATCH body validation

BOM and work-center PATCH handlers accept a raw `dict` body rather than a
strict Pydantic model for now. Unknown keys are silently ignored. The service
layer applies field-level validation (name max length, status enum bounds).
If an empty dict is received, the service is called with all `None` kwargs and
returns the unchanged record (no-op update). A `400` is NOT raised for an empty
patch — this allows idempotent PATCH calls.

A dedicated `BomPatchIn` / `WorkCenterPatchIn` model with `Optional` fields is
the recommended follow-up; deferring it avoids models.py churn before the
service layer is stable.

### 5.4 Work-order lifecycle 409 messages

When `release_work_order` raises 409 due to insufficient component stock
(re-raised from `manufacturing_work_orders._issue_components` per MFG-007 §5.2),
the handler propagates the HTTPException unchanged. The `detail` string already
identifies the blocking component SKU and shortage quantity. Clients should
surface this to the admin verbatim.

Illegal-transition 409s (e.g. trying to release an already-released work order)
also propagate unchanged from `wo.release_work_order` →
`wo._require_transition` → HTTPException(409).

### 5.5 MRP run idempotency

`mrp.run_mrp` derives `mrp_run_id = sha256(correlation_id)[:32]` (same pattern
as `app/services/commerce_order_service.py:67` — verified). If a caller submits the same `correlation_id`
twice, the second call either finds the existing run (overwrite path defined by
MFG-010 spec §5.3) or returns the cached run. Either way, `POST /mrp/run`
returns HTTP 201. Clients that need to distinguish new-vs-cached runs should
compare the returned `created_at` vs `updated_at` fields.

### 5.6 `completed`/`cancelled` work orders are immutable

After a work order reaches `completed` or `cancelled`, all four action
sub-paths return 409 ("Illegal transition: ..."). The GET endpoint always
succeeds.

### 5.7 Explode endpoint with unknown `bom_id`

If `bom_id` does not exist, `bom.explode_bom` raises HTTPException(404). The
handler propagates it. The `build_qty` query parameter must satisfy `ge=1` —
FastAPI's built-in validation returns 422 before the handler is invoked.

### 5.8 Routing cost estimate when no routing exists

If `routing.estimate_routing_cost_for_parent(parent_id, build_qty)` is called
for a `parent_id` that has no routing tasks, the function returns a zero-cost
`RoutingCostOut` (all fields 0, `tasks=[]`). This is not a 404; the absence of
routing tasks is a valid configuration (some products have no labor routing).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

The router contains no `dev_mode` branches. Service functions (`manufacturing_bom`,
`manufacturing_routing`, `manufacturing_work_orders`, `manufacturing_mrp`) operate
identically against moto-backed local DynamoDB (port 8001, `DDB_ENDPOINT_URL`)
and production DynamoDB. The `_FloatSafeTable` proxy (`app/core/tables.py:29–62` — verified)
handles float→Decimal coercion on both paths transparently. No mock API keys,
no S3 writes, no KMS calls exist in the manufacturing stack — parity is trivially
maintained.

### 7.2 Idempotency

| Operation | Idempotency guarantee |
|-----------|-----------------------|
| `POST /boms` (with `correlation_id`) | `bom_id = sha256(correlation_id)[:32]`; repeated call with same `correlation_id` is a no-op conditional put (returns existing record) |
| `POST /work-orders` (with `correlation_id`) | Same sha256 scheme; `wo.create_work_order` uses conditional `attribute_not_exists(work_order_id)` put |
| `POST /work-orders/{id}/release` | `issues_guard="done"` flag; replayed call is a no-op (returns current header) |
| `POST /work-orders/{id}/complete` | `produce_guard="done"` flag; replayed call is a no-op |
| `POST /mrp/run` (with `correlation_id`) | `mrp_run_id = sha256(correlation_id)[:32]`; re-run overwrites requirement rows in place |

### 7.3 Security

- **CSRF**: `require_admin_or_root_csrf` delegates to `enforce_cookie_csrf`
  (`app/auth/policy.py:71–97`) which validates the `x-csrf-token` header
  against the `ui_csrf` cookie for cookie-auth requests.
  Bearer-auth callers (API key / test clients) bypass CSRF.
- **Ownership**: manufacturing data is scoped to the platform (not per-user);
  admin scope guards are sufficient. Work orders record `created_by` (user_sub)
  for audit purposes but there is no per-user ownership filter.
- **Input bounds**: all numeric fields use Pydantic `ge`/`le` constraints
  defined in MFG-003 models. The router adds `Query(ge=1, le=10_000_000)` on
  `build_qty` and `limit` parameters.
- **Audit trail**: every write operation in the service layer emits a
  best-effort `alerts.audit_event`. The router adds no additional audit calls —
  service-layer audit is the single source of truth.

## 8. Backward Compatibility & Migration

### 8.1 Additive — no existing routes changed

The `manufacturing_router` prefix `/ui/manufacturing` is entirely new. No
existing endpoint paths are touched. No existing DynamoDB tables are written.
With `MANUFACTURING_MRP_ENABLED=false` (the default), all existing routes
continue to function exactly as before.

### 8.2 `app/main.py` import addition

The new import (`from app.routers.manufacturing import manufacturing_router`)
and `include_router` call are the only changes to `app/main.py`. They are
additive — Python imports are idempotent and `include_router` adds routes
without modifying existing ones.

### 8.3 `GET /openapi.json` expansion

The OpenAPI schema gains ~20 new paths once the router is mounted. This is
visible in Swagger UI (`/docs`) but does not break any existing client. The
acceptance criterion explicitly states `GET /openapi.json` must list the new
paths.

### 8.4 No DynamoDB schema migration

The four manufacturing tables are brand-new and do not share partitions with
any existing tables. No `UpdateTable` or backfill is required. In production,
the tables must be created (via a migration script or `scripts/local-ddb-init.py`
equivalent) before the flag is turned on. In dev, `just restart` recreates them.

## 10. Open Questions / Assumptions

1. **MFG-003 models must pre-exist**: This spec assumes `BomHeaderIn`, `BomOut`,
   `WorkCenterIn`, `WorkCenterOut`, `RoutingTaskIn`, `RoutingTaskOut`,
   `RoutingCostOut`, `WorkOrderCreateIn`, `WorkOrderOut`, `MrpRunIn`, `MrpRunOut`,
   and `MrpRequirementOut` are all defined in `app/models.py` by MFG-003. If
   any shape differs from `docs/ofbiz/specs/MFG-003.md`, the import list and
   handler `response_model` declarations must be updated.

2. **`MrpRunOut` shape**: MFG-010 owns the `MrpRunOut` model. This spec assumes
   it exposes at minimum `mrp_run_id`, `status`, `created_at`, `horizon_days`,
   `location_id`, and `requirements: List[MrpRequirementOut]`. If the shape
   embeds requirements as a nested list vs a separate endpoint, the
   `get_mrp_run` handler may need a dedicated response model.

3. **PATCH body typing**: Using raw `dict` for PATCH body means FastAPI cannot
   auto-generate a request schema in OpenAPI. A dedicated `BomPatchIn` model is
   recommended before stabilisation but deferred here to avoid blocking on
   MFG-003 scope changes.

4. **Routing task delete endpoint**: The spec for MFG-005 defines
   `remove_routing_task(work_center_id, parent_id, seq)` but this router does
   not expose a `DELETE /work-centers/{work_center_id}/routing/{parent_id}/{seq}`
   endpoint. Adding it is a one-line handler; it is deferred to avoid scope
   creep. Confirmed assumption: the `replace_routing_for_parent` (PUT full
   replace) is sufficient for MVP.

5. **`estimate_routing_cost_for_parent` availability**: This spec uses
   `routing.estimate_routing_cost_for_parent(parent_id, build_qty)` as the
   convenience wrapper (defined in `docs/ofbiz/specs/MFG-005.md:346`). If
   MFG-005 only implements the pure `estimate_routing_cost(tasks, build_qty)`
   function and not the parent-ID wrapper, the router handler must first call
   `routing.get_routing_for_parent(parent_id)`, enrich tasks with work-center
   `cost_per_hour_cents`, and then call the pure function.

6. **Work-order `produced_qty` on complete**: `body` for `POST .../complete` is
   optional (`dict | None`). If absent, the service defaults `produced_qty` to
   the work order's `quantity` field. This is consistent with MFG-007 §4.1.

7. **`require_admin_or_root_csrf` vs role-scoped admin**: All manufacturing
   endpoints use `require_admin_or_root_csrf` (ADMIN or ROOT). Scoped admin
   profiles (e.g. `AdminProfileType.GENERAL`) are not checked in Phase 1; any
   admin can manage manufacturing. A narrower `require_admin_scope("manufacturing")`
   can be added in a follow-up without changing the router's external contract.

8. **MRP `correlation_id` in `MrpRunIn`**: The MFG-010 ticket says
   `mrp_run_id = sha256(correlation_id)`. This spec assumes `MrpRunIn` includes
   a `correlation_id: Optional[str]` field. If the model omits it, the service
   auto-generates a UUID-based correlation ID and the run is not idempotent from
   the caller's perspective.
