# OFB-022 — Pricing/promotions tests

## 1. Summary & Goal

OFB-022 delivers the **test layer** for the pricing-rules engine added by OFB-019 and wired into the cart by OFB-020. It produces two artefacts:

1. `tests/test_ofb_pricing_rules.py` — a hermetic offline pytest suite that exercises every rule type, stacking variant, redemption-cap scenario, and flag-off guard entirely within moto-backed in-memory DynamoDB, calling service functions directly (no `TestClient`, no network).
2. `frontend/e2e/pricing-rules.spec.ts` — a Playwright E2E spec that exercises the full happy-path flow: an admin creates a tiered rule, a buyer adds items, the cart-total endpoint returns the rule-discounted amount, and the purchase endpoint charges the discounted total and stores `applied_rule_ids` on the order.

These tests lock in the contracts defined by OFB-019 and OFB-020 so that future refactors cannot silently regress discount math, stacking precedence, or the end-to-end checkout discount.

## 5. Detailed Behavior & Edge Cases

### 5.1 Tiered discount math test cases

A tiered rule with:
```json
{"tiers": [
  {"min_qty": 1, "max_qty": 4,    "unit_price_cents": 1000},
  {"min_qty": 5, "max_qty": 9,    "unit_price_cents": 850},
  {"min_qty": 10, "max_qty": null, "unit_price_cents": 700}
]}
```
applied to a cart item with `unit_price_cents=1200, quantity=7` must compute:
- Applicable tier: 5–9 → `unit_price_cents=850`
- `item_discount = (1200 - 850) * 7 = 2450`
- `RuleDiscountResult.discount_cents == 2450, applied == True`

Edge cases the test suite must cover:
- **Boundary exactly at tier boundary**: `quantity=5` hits tier 5–9 (not 1–4).
- **Quantity 1**: hits first tier.
- **Quantity=10**: hits the unbounded last tier.
- **Tier price > original unit price**: discount for that item floored to 0 (never negative).
- **Gap in tiers (config validation)**: `create_rule` with non-contiguous tiers returns `(None, error_message)` before writing to DDB.
- **Overlapping tiers (config validation)**: same.
- **Last tier has `max_qty` set (config validation)**: `(None, error_message)`.

### 5.2 Bulk discount math test cases

A bulk rule with `threshold_qty=5, discount_type="percentage", discount_value=15` on a cart item with `quantity=6, unit_price_cents=1000`:
- `discount = floor(1000 * 6 * 15 / 100) = 900`
- `applied=True`

When `quantity=4` (below threshold): `applied=False, reason_skipped="quantity_below_threshold"`.

When ALL in-scope items are below threshold: `RuleDiscountResult.discount_cents=0, applied=False`.

`fixed_per_unit` variant: `threshold_qty=3, discount_value=50` on `quantity=4, unit_price_cents=200`:
- `discount = min(50 * 4, 200 * 4) = 200` (50 cents × 4 items)

### 5.3 Conditional discount math test cases

A conditional rule with `min_cart_total_cents=5000, discount_type="percentage", discount_value=10`:
- Cart total = 6000 → `discount = floor(6000 * 10/100) = 600`, `applied=True`.
- Cart total = 4999 → `applied=False, reason_skipped="cart_total_below_threshold"`.
- Cart total = 5000 (exactly at boundary) → `applied=True` (meets, not exceeds).

Scope filtering: when `scope_category_ids=["cat_A"]` and the cart has one item from `cat_A` and one from `cat_B`, only the `cat_A` item's `line_total_cents` counts toward the threshold and receives the discount.

### 5.4 Stacking precedence test cases

**Case 1 — Two best-deal-wins rules, different discounts:**
- Rule X: `stacking_mode=best_deal_wins, priority=1, discount_cents=500`
- Rule Y: `stacking_mode=best_deal_wins, priority=2, discount_cents=300`
- `apply_stacking([X_result, Y_result]).total_discount_cents == 500` (X wins)
- `applied_rule_ids == [X.rule_id]`

**Case 2 — Tiebreak by priority:**
- Rule A: `stacking_mode=best_deal_wins, priority=3, discount_cents=500`
- Rule B: `stacking_mode=best_deal_wins, priority=1, discount_cents=500`
- Winner is B (lower priority integer = higher declared priority).

**Case 3 — Two stackable rules:**
- Rule P: `stacking_mode=stackable, discount_cents=400`
- Rule Q: `stacking_mode=stackable, discount_cents=300`
- `total_discount_cents == 700`

**Case 4 — Mixed modes:**
- Rule S: `stacking_mode=stackable, discount_cents=200`
- Rule T: `stacking_mode=best_deal_wins, discount_cents=600`
- Rule U: `stacking_mode=best_deal_wins, discount_cents=400`
- T wins the best-deal-wins group (600 > 400). Combined = 200 + 600 = 800.

**Case 5 — Cap at cart total:**
- Cart total = 1000, combined discount from stacking = 1500.
- `final_cart_cents = 0`, `total_discount_cents = 1000` (capped).

**Case 6 — Applied=False rules contribute 0:**
- Rule with `applied=False` (threshold not met): contributes 0 to all pools; still appears in `per_rule_breakdown` with `discount_cents=0`.

### 5.5 Redemption cap test cases

**Global cap (`max_uses`):**
1. Create rule with `max_uses=2`.
2. First two purchases: `redeem_rule` succeeds; `current_uses` reaches 2.
3. Third call to `resolve_applicable_rules` excludes the rule (`current_uses >= max_uses`). Purchase proceeds with `rules_discount_cents=0`.

**Per-user cap (`max_uses_per_user=1`):**
1. User A purchases once; `REDEEM#{user_a}#{ts}` row written.
2. Second purchase by user A: `_check_uses` finds the existing row; `resolve_applicable_rules` excludes the rule for user A.
3. User B's first purchase: rule still applies (per-user cap per user).

**Atomic increment race (concurrent `redeem_rule` calls):**
The conditional `update_item` with `Attr("current_uses").lt(max_uses)` (identical to `app/services/promo_codes.py:416–433` — `try:` at 416, `ConditionExpression=Attr("current_uses").lt(max_uses)` at 421, `return None, "This code has been fully redeemed"` at 432, bare `raise` at 433) is the enforcement mechanism. The test verifies that the `ClientError("ConditionalCheckFailedException")` path in `redeem_rule` returns `(None, "This rule has been fully redeemed")` without raising.

### 5.6 Scope filtering edge cases

- `scope_category_ids=[]` and `scope_skus=[]`: all items are in scope.
- `scope_category_ids=["cat_X"]` and `scope_skus=["sku_Y"]`: items from `cat_X` OR with sku `sku_Y` are in scope (union, per OFB-019 §5.6).
- Cart item with `category_id=None`: does not match any `scope_category_ids` unless the set is empty.

### 5.7 Subscription tier gate edge cases

- `required_subscription_plan_ids=[]`: gate passes for all users.
- User has active sub with `plan_id="gold"` and rule requires `plan_id in ["gold"]`: `applied=True`.
- User has trialing/past_due sub: same active-status query as `subscription_access.has_active_subscription` at `app/services/subscription_access.py:55–68` (status in `{"active","past_due","trialing"}`).
- User has cancelled/expired sub: `applied=False, reason_skipped="subscription_tier_not_met"`.
- `T.subscriptions` not seeded for user (no rows): `applied=False`.

### 5.8 Flag-off guard

When `S.pricing_rules_enabled=False`:
- Direct call to `compute_discount` or `apply_stacking`: still executes (these are pure math functions, not gated). The flag gates the **entry points** only.
- `cart_total_with_rules`: falls through to `cart_total_cents` (returns `rules_discount_cents=0`).
- `_apply_pricing_rules`: returns zero-discount result immediately.
- Router handler `ui_create_rule`: raises `HTTPException(404)` via `_require_enabled()`.
- `validate_promo_code_with_rules` with a promo that has `pricing_rule_id` set: flag off → calls `validate_promo_code` directly, returns the flat discount, ignores the rule reference.

### 5.9 Promo code with linked rule — no double-count

When `promo_code` carries `pricing_rule_id`, `validate_promo_code_with_rules` computes the discount via the engine. `_apply_pricing_rules` in `purchase_cart` receives `exclude_rule_ids={pricing_rule_id}` to prevent the same rule from being counted twice. The test must verify:
- `total_discount_cents` = rule_discount (applied once via promo path)
- `rules_discount_cents` from `_apply_pricing_rules` = 0 (rule excluded from auto-discovery)

### 5.10 Idempotency of purchase

`purchase_cart` has an early-return guard at `app/services/shoppingcart.py:483–492`: if `cart.status == "PURCHASED"`, it returns the cached result. The cached result after OFB-020 includes `applied_rule_ids`. A second call with the same idempotency key must return the same `purchased_total_cents` and `applied_rule_ids`. The test seeds an already-PURCHASED cart record with `applied_rule_ids` and verifies the early-return path surfaces them.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Test isolation (SECOPS-007 parity in tests)

All pytest tests use moto in-memory DynamoDB. The exact frozen `T.pricing_rules`, `T.promo_codes`, `T.shopping_cart`, `T.orders`, `T.order_items`, and `T.subscriptions` handles are replaced via `object.__setattr__(T, "<attr>", moto_table)` and restored in tearDown. This pattern is required because `T` is a frozen dataclass; it mirrors `tests/test_ofb_inventory.py:121–127` (T patching via `object.__setattr__`) and `tests/test_gap_0265_0266_kyc_risk_scoring.py:105–117` (same idiom for multiple tables).

No test contacts real DynamoDB, real Stripe, real AWS, or any network endpoint.

### 7.2 Commerce side-effect stubs

`commerce_order_service.create_order_from_line_items`, `commerce_entitlement_orchestrator.process_order_entitlements`, `record_cart_purchase`, `get_profile`, and `_commercial_line_items_from_cart_items` are stubbed via `patch.object` (same pattern as `tests/test_gap_0343_shop_promo_checkout.py:131–159`). These stubs prevent real billing/entitlement side-effects while allowing the rule-engine and redemption-accounting logic to run against moto tables.

### 7.3 Idempotency assertions

- `redeem_rule` is called twice for the same `(rule_id, user_sub)` when `max_uses_per_user=1` after the first redemption; the second invocation must return `(None, error)` without corrupting `current_uses`.
- `purchase_cart` with `cart.status == "PURCHASED"` must return the same `purchased_total_cents` and `applied_rule_ids` as the first call.
- `create_rule` is intentionally non-idempotent (each call mints a new `rule_id`); a test asserting that two calls with identical params produce two distinct `rule_id` values confirms this.

### 7.4 Discount cap / negative-total

Every test that verifies `final_cart_cents` must assert `final_cart_cents >= 0`. The cap-at-zero test (`total_discount_cents > cart_total_cents` scenario) specifically asserts `final_cart_cents == 0, total_discount_cents == cart_total_cents` (capped, not the raw combined).

### 7.5 No auth bypass in E2E

All E2E API calls use real cookie-session auth from `e2e_session_setup.py` / `e2e_admin_session_setup.py`. The `x-csrf-token` header is sent on every non-GET request (required by `require_ui_session` for cookie-auth paths). The admin endpoint `GET /ui/admin/pricing-rules` must use `charlie_admin` — a `role=admin, admin_profile.type=general` identity.

## 10. Open Questions / Assumptions

1. **Assumption: OFB-019 ships `redeem_rule` as a top-level export.** The OFB-020 spec (`docs/ofbiz/specs/OFB-020.md` §2.4) calls it `redeem_rule`. OFB-019's spec (§7.3) calls it `record_rule_redemption`. The name used in OFB-022 tests must match whichever name OFB-019 actually exports. If OFB-019 uses `record_rule_redemption`, OFB-022 imports that name instead. Verify at merge time.

2. **Assumption: `resolve_applicable_rules` accepts `exclude_rule_ids`.** OFB-020 §10 notes this as an assumption. If OFB-019 does not add `exclude_rule_ids`, the no-double-count test (I-03 in the pytest suite, C.4 in the E2E spec) must be adjusted to verify the manual subtraction path instead.

3. **Assumption: The E2E stack runs with `PRICING_RULES_ENABLED=true` for sections A–C.** If the default stack does not enable the flag, the E2E spec must dynamically skip or be run with a specific flag-enabling setup script. A `beforeAll` guard that calls `GET /ui/pricing-rules` and skips on 404 is the recommended approach.

4. **Assumption: charlie_admin session has `admin_profile.type="general"`.** The `GET /ui/admin/pricing-rules` endpoint uses `require_admin_or_root` from `app/auth/policy.py:67`. `e2e_admin_session_setup.py` creates a `charlie_admin` identity with `type=general` — this is the correct identity. If `require_admin_or_root` is from `app/auth/deps.py` rather than `policy.py`, verify the import path in OFB-019's router before writing the E2E helpers.

5. **Assumption: `cart_total_with_rules` is the endpoint handler return value, not `cart_total_cents`.** OFB-020 §4.3 specifies that the `GET /ui/shoppingcart/carts/{id}/total` handler calls `cart_total_with_rules` when `pricing_rules_enabled`. The E2E test C.1 asserts `raw_total_cents` and `rules_discount_cents` in the response. If OFB-020 does not rename `total_cents` to `raw_total_cents` in the response (it may keep `total_cents` as the discounted value and add `raw_total_cents`), the E2E assertion field names must match whatever OFB-020 actually ships.

6. **Assumption: `applied_rule_ids` is always a list (not a DynamoDB StringSet).** `ShoppingCartPurchaseOut.applied_rule_ids` in the Pydantic model is `Optional[List[str]]`. In DynamoDB the cart record stores it as SS (StringSet), but the service layer converts it to a Python `list` before returning. The E2E assertion `expect(body.applied_rule_ids).toHaveLength(1)` relies on this conversion. If OFB-020 returns a raw SS, the E2E assertion must use `expect(Array.from(body.applied_rule_ids)).toHaveLength(1)`.

7. **Open question: Should OFB-022 test `validate_promo_code_with_rules` with `cart_items=None` (single-item promo validation)?** The function must not crash when `cart_items` is omitted (for backwards-compatible callers). Test I-02 covers this implicitly (promo without linked rule), but an explicit `cart_items=None` call through the promo-with-rule path should be added.

8. **Assumption: Test P-03 (combined promo + rule) must handle the creator resolution correctly.** `purchase_cart`'s `_resolve_cart_creator` returns `None` for items without `creator_user_id` and falls back to `user_sub` (`app/services/shoppingcart.py:553–558`). The test must seed cart items with `creator_user_id` matching the promo code's `creator_user_id` to pass the promo creator-scope check, or seed the items without `creator_user_id` so the fallback `user_sub` matches (as done in `tests/test_gap_0343_shop_promo_checkout.py:191–207`).
