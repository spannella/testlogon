# POS-010 — X/Z session reports (till summary)

**Type:** Feature | **Priority:** P1 | **Estimate:** 2 days
**Dependencies:** POS-006, POS-007, POS-008

---

## 1. Summary & Goal

POS-010 adds `session_report(session_id, kind)` to `app/services/pos_register.py`
and exposes it as `GET /ui/pos/sessions/{session_id}/report?kind=x|z` (wired in
POS-011). It produces two complementary till-summary reports:

- **X report** (mid-shift, non-resetting): callable on an **open** session at any
  time; returns a snapshot of current-shift totals without modifying any state.
- **Z report** (end-of-shift): callable only on a **closed** session (POS-004
  `close_session` must have run first); returns the final, authoritative till
  summary and sets `z_report_printed_at` on the session row so it can only be
  printed once (subsequent calls replay the same data idempotently).

Both report kinds aggregate directly from the rows already written to the `pos`
single-table by POS-006/007/008 — they never scan; they always query
`GSI_SESSION_TXN` for that session. The report reconciles the by-tender totals
(cash/card/wallet) against the ledger entries written in POS-006/007/008. No new
billing paths, no new money movement, no new tables.

The entire feature is gated by the existing default-off `S.pos_enabled` flag
(env `POS_ENABLED`). With the flag off the route returns 404 and zero bytes of
the existing shop/cart/orders/billing stack are affected.

## 2. Context & Current State

### 2.1 Existing `pos` single-table and its GSIs

POS-003 (`scripts/local-ddb-init.py`, appended after `returns` at `:2483`
— `returns` TableDef confirmed at `scripts/local-ddb-init.py:2483`, closing `]` at `:2493`) defines
the `pos` table with PK `pos_pk` / SK `pos_sk` and three GSIs:

| GSI | Partition key | Sort key | `attr_types` |
|---|---|---|---|
| `GSI_REGISTER_OPEN` | `register_id` | `opened_at` (N) | `{"opened_at":"N"}` |
| `GSI_CASHIER` | `cashier_sub` | `opened_at` (N) | same row |
| `GSI_SESSION_TXN` | `session_id` | `created_at` (N) | `{"created_at":"N"}` |

Both numeric sort keys are declared in `attr_types` to avoid the
`ValidationException` described in the CLAUDE.md "DynamoDB numeric GSI sort keys"
gotcha. The same `attr_types={"opened_at": "N", "created_at": "N"}` declaration
covers all three GSIs (POS-004 spec §3.4, reproduced in
`docs/ofbiz/specs/POS-004.md:200–218`). <!-- UNCONFIRMED: pos table not yet in local-ddb-init.py; POS-003 not implemented -->

### 2.2 Row types written to `GSI_SESSION_TXN`

The following row kinds all carry top-level `session_id` + numeric `created_at`
and therefore appear in `GSI_SESSION_TXN` automatically:

| PK pattern | SK pattern | Kind attribute | Written by |
|---|---|---|---|
| `SESSION#{session_id}` | `TENDER#{txn_id}#{seq:04d}` | `cash` / `card` / `wallet` | POS-006/007 |
| `SESSION#{session_id}` | `REFUND#{txn_id}#{seq:04d}` | `cash_refund` / `card_refund` / `wallet_refund` | POS-008 |

Cash tender rows (POS-006) carry `amount_tendered_cents` (banknotes given by customer),
`change_due_cents` (change returned), `total_cents`, `ledger_sk`, and `kind="cash"`.
Card/wallet tender rows (POS-007) carry `amount_cents` (the leg amount), `total_cents`,
`ledger_sk`, and `kind="card"` / `kind="wallet"`.
(`app/services/pos_tender.py`; POS-006 spec §3.1, POS-007 spec §3.2, POS-008 spec §3.4.)

Transaction rows (`TXN#{txn_id}/META`) carry `status`, `subtotal_cents`,
`discount_cents`, `tax_cents`, `total_cents`, and `voided_at` (POS-008 spec §3.2,
§3.3). They also appear in `GSI_SESSION_TXN` via their `session_id` + `created_at`
attributes.

### 2.3 Session row (`SESSION#{session_id}/META`)

Written and closed by POS-004 (`app/services/pos_register.py`, per
`docs/ofbiz/specs/POS-004.md:135–157`; UNCONFIRMED — POS-004 not yet implemented).
Key fields for POS-010:

| Attribute | Role in report |
|---|---|
| `status` | Guard: X requires `"open"`, Z requires `"closed"` |
| `opening_float_cents` | Opening cash drawer balance |
| `cash_in_cents` | Running sum of cash amounts received (per POS-006 §3.3) |
| `change_out_cents` | Running sum of change disbursed (per POS-006 §3.3) |
| `expected_cash_cents` | Computed at close: `opening_float + cash_in − change_out` |
| `counted_cash_cents` | Physically counted at close (provided in `CloseSessionIn`) |
| `over_short_cents` | `counted − expected` (signed) |
| `opened_at`, `closed_at` | Report timestamps |
| `cashier_sub`, `register_id` | Report header |

The session row is the **primary source of truth** for the cash float math;
POS-010 reads it directly rather than recomputing from individual tenders (which
would diverge if any float update was missed). The per-tender query via
`GSI_SESSION_TXN` is used only to build the by-tender breakdown and the
gross/refund/void subtotals.

### 2.4 Platform financial dashboard — query discipline

`app/services/platform_financial_dashboard.py` demonstrates the correct
aggregation discipline for the POS report: it always queries `GSI_LEDGER_DATE`
per-day (`app/services/platform_financial_dashboard.py:136–158` — VERIFIED) instead of scanning the full billing table. POS-010 follows
the same discipline — it always queries `GSI_SESSION_TXN` (partition
`session_id`) instead of scanning the full `pos` table. A session with thousands
of transactions (e.g. a busy retail terminal) must not degrade to a full-table
scan. The GSI query loops via `LastEvaluatedKey` until exhausted (per CLAUDE.md
"DDB FilterExpression doesn't reduce page size" gotcha — a session spread across
multiple DynamoDB pages must be fully fetched before aggregating).

## 3. Data Model

POS-010 introduces **no new tables** and **no new GSIs**. It reads `T.pos`
(session row + `GSI_SESSION_TXN` items) and writes a single new attribute on the
session row for Z-report tracking.

### 3.1 New attribute on `SESSION#{session_id}/META`

| Attribute | DDB type | Written by | Description |
|---|---|---|---|
| `z_report_printed_at` | N | `session_report(kind="z")` | `now_ts()` on first Z print; absent = not yet printed |

Written with `ConditionExpression="attribute_not_exists(z_report_printed_at)"`
so that a replay of the Z-report call after a crash-and-retry reads back the
existing timestamp rather than re-firing the `pos_z_report_printed` audit event.
The `ConditionalCheckFailedException` is caught and treated as a successful
idempotent replay (same as the tender-row pattern in POS-006 §2.5,
`docs/ofbiz/specs/POS-006.md:89–95`).

### 3.2 Report summary output (in-memory only — not persisted)

The report is computed on-demand each time it is requested (X report) or on
first Z-report invocation. **No separate `REPORT#` row is stored** in DDB.
The report dict is returned directly in the HTTP response. This is consistent
with `platform_financial_dashboard.py`'s approach of computing aggregates in
Python after querying the ledger rather than materialising a separate row.

If the caller needs a durable report artifact (e.g. for printing), the POS-011
router layer should serialize and return it — the service layer returns the dict.

## 4. API / Service Design

### 4.1 Service function — `app/services/pos_register.py`

```python
def session_report(
    session_id: str,
    kind: str,                # "x" or "z"
    *,
    cashier_sub: str,         # authenticated caller; enforces ownership
) -> Dict[str, Any]:
    """
    Produce an X or Z till summary for ``session_id``.

    X-report: non-resetting mid-shift snapshot; session must be ``"open"``.
    Z-report: end-of-shift; session must be ``"closed"``; sets
              ``z_report_printed_at`` on the session row (idempotent).

    Returns the report dict suitable for direct JSON serialisation.
    Raises HTTPException(404) when flag off.
    Raises HTTPException(400) with ``code="invalid_report_kind"`` for unknown kind.
    Raises HTTPException(403) when ``cashier_sub`` does not own the session.
    Raises HTTPException(409) when session status does not match report kind.
    """
```

Internal helper decomposition:

```python
def _query_session_txn_rows(session_id: str) -> List[Dict[str, Any]]:
    """
    Query all rows from GSI_SESSION_TXN (partition_key=session_id, sort=created_at
    ascending). Loops via LastEvaluatedKey until exhausted.
    Returns TENDER#, REFUND#, and TXN# rows for this session.
    """

def _aggregate_rows(
    rows: List[Dict[str, Any]],
    session: Dict[str, Any],
) -> Dict[str, Any]:
    """
    Pure function (no DDB calls): accepts the raw row list and session item,
    returns the aggregated report dict. This is the unit-testable core.

    Aggregates:
      - gross_sales_cents           = Σ total_cents for settled TXN rows
      - discount_cents              = Σ discount_cents for settled TXN rows
      - tax_cents                   = Σ tax_cents for settled TXN rows
      - refund_total_cents          = Σ amount_cents for REFUND# rows
      - void_count                  = count of TXN rows with status "voided"
      - tender_breakdown: dict keyed by kind ("cash"/"card"/"wallet") →
          { gross_cents, refund_cents, net_cents, transaction_count }
      - cash section specifically:
          opening_float_cents       = from session row
          cash_in_cents             = from session row (or Σ cash tenders)
          change_out_cents          = from session row (or Σ change_due)
          expected_cash_cents       = session row or computed: float + in − change
          counted_cash_cents        = session row (null for X reports)
          over_short_cents          = session row (null for X reports)
    """
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Row classification

`_aggregate_rows` classifies each row by a combination of `pos_pk` and `pos_sk`.

**Key schema** (from POS-005/006/007/008 specs):
- TENDER rows: `pos_pk = "SESSION#{session_id}"`, `pos_sk = "TENDER#{txn_id}#{seq:04d}"`
- REFUND rows: `pos_pk = "SESSION#{session_id}"`, `pos_sk = "REFUND#{txn_id}#{seq:04d}"`
- TXN rows: `pos_pk = "TXN#{txn_id}"`, `pos_sk = "META"` — discriminate by **pk prefix**, not sk

| Condition | Classification | Action |
|---|---|---|
| `pos_sk.startswith("TENDER#")` | Sale tender leg | accumulate by `kind` into `tender_breakdown` |
| `pos_sk.startswith("REFUND#")` | Refund tender leg | accumulate by `kind` into refund bucket |
| `pos_pk.startswith("TXN#") and pos_sk == "META"` | Transaction | count settled vs voided; accumulate `subtotal_cents`, `discount_cents`, `tax_cents` |
| All other rows | Ignored | skipped silently |

The function discriminates as follows:

```python
sk = row.get("pos_sk", "")
pk = row.get("pos_pk", "")
if sk.startswith("TENDER#"):   ...
elif sk.startswith("REFUND#"): ...
elif pk.startswith("TXN#") and sk == "META":    ...
```

> **CORRECTED**: The original draft used `sk.startswith("TXN#")`, which would never match
> because TXN rows have `pos_sk = "META"` (not `"TXN#..."`). The correct discriminator
> checks `pos_pk` for the `"TXN#"` prefix (POS-005 spec §2.3, POS-006 spec §3.2).

### 5.2 Tender `amount_cents` vs `total_cents`

For split-tender transactions (POS-007), multiple `TENDER#` rows exist for the
same `txn_id`. The gross sales total is derived from TXN rows (`pos_pk = "TXN#{txn_id}"`,
`pos_sk = "META"`, field `total_cents`) — NOT summed from `TENDER#` per-leg amounts.
This avoids double-counting in split-tender scenarios.

The tender breakdown per `kind` uses the leg amount field, which differs by tender type:
- Cash tenders (POS-006): `amount_tendered_cents` (banknotes received) minus `change_due_cents` = net cash received. Use `total_cents` from the TXN row as the gross cash sale amount, or equivalently `amount_tendered_cents - change_due_cents`.
- Card/wallet tenders (POS-007): `amount_cents` (the leg amount charged).

`_aggregate_rows` must read both field names: `_to_int(row.get("amount_cents") or row.get("amount_tendered_cents"))`
for the generic leg-amount path, then apply the cash-specific change deduction separately.

> **CORRECTED**: Original draft stated "Each row carries `amount_cents`" — cash TENDER rows
> (POS-006) use `amount_tendered_cents`, not `amount_cents` (POS-006 spec §3.1). Card/wallet
> rows (POS-007) use `amount_cents` (POS-007 spec §3.2).

### 5.3 Cash section sourcing

For a **closed** session (Z report): `expected_cash_cents`, `counted_cash_cents`,
`over_short_cents`, `cash_in_cents`, and `change_out_cents` are read directly from
the session row (written atomically by POS-004 `close_session`). This is the
authoritative figure and must not be recomputed from tender rows.

For an **open** session (X report): `counted_cash_cents` and `over_short_cents`
are `None`. `expected_cash_cents` is recomputed inline:
```
expected = opening_float_cents + cash_in_cents − change_out_cents
```
using the session row's running counters (maintained atomically by POS-006).

### 5.4 Z-report status guard and idempotency

Before writing `z_report_printed_at`:

1. Read the session row.
2. If `status != "closed"` → raise `HTTPException(409, "Session must be closed for a Z report")`.
3. Attempt `update_item` with `ConditionExpression="attribute_not_exists(z_report_printed_at)"`.
4. On success: emit `_audit("pos_z_report_printed", ...)`.
5. On `ConditionalCheckFailedException`: re-read `z_report_printed_at` from the
   item (it was already set). Return the same report data as if the write had just
   succeeded — no audit event re-emitted (idempotent).

### 5.5 X-report status guard

If `status == "closed"` and `kind == "x"` → raise `HTTPException(409, "Session is closed; use kind=z for the final report")`. This prevents cashiers from mistaking a stale X snapshot for the authoritative Z.

### 5.6 Empty session

A session with no completed transactions (all voided, or no transactions at all)
returns a valid report with all totals zero and `void_count` reflecting the
voided transactions. This must not error.

### 5.7 Decimal coercion from DynamoDB

All numeric fields retrieved from DynamoDB may be `Decimal` (boto3 default).
Use a `_to_int` helper (identical in pattern to
`app/services/platform_financial_dashboard.py:71–79` — VERIFIED) throughout `_aggregate_rows`
to coerce every numeric attribute before arithmetic:

```python
def _to_int(v: Any) -> int:
    from decimal import Decimal
    if v is None: return 0
    if isinstance(v, Decimal): return int(v)
    try: return int(v)
    except (TypeError, ValueError): return 0
```

### 5.8 ADMIN/ROOT bypass for ownership check

If `ctx["role"]` is `"admin"` or `"root"` (the `require_ui_session` dependency
at `app/services/sessions.py:454` returns `{"role": role.value, ...}` where `role`
is a `Role` enum; `Role.ADMIN.value="admin"`, `Role.ROOT.value="root"` — VERIFIED at
`app/auth/roles.py:8–11`; `normalize_role` at `app/auth/roles.py:48–57` — VERIFIED),
the ownership check
(`cashier_sub == session["cashier_sub"]`) is skipped. This allows store managers
to pull any register's report. The service function accepts a `role` argument or
the router passes `ctx["role"]` through and the service checks it.

### 5.9 `LastEvaluatedKey` exhaustion

`_query_session_txn_rows` must loop until no `LastEvaluatedKey` is returned. A
single `query()` call is not sufficient (per CLAUDE.md "DDB FilterExpression
doesn't reduce page size" gotcha). Because no `FilterExpression` is applied —
all rows for the `session_id` partition are wanted — the only truncation risk is
DynamoDB's 1MB page limit for busy sessions.

```python
def _query_session_txn_rows(session_id: str) -> List[Dict[str, Any]]:
    from boto3.dynamodb.conditions import Key
    out: List[Dict[str, Any]] = []
    kwargs: Dict[str, Any] = {
        "IndexName": "GSI_SESSION_TXN",
        "KeyConditionExpression": Key("session_id").eq(session_id),
        "ScanIndexForward": True,   # oldest first (created_at ascending)
    }
    while True:
        resp = T.pos.query(**kwargs)
        out.extend(resp.get("Items", []))
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
    return out
```

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

`session_report` is a **read-mostly** function. The only write is the idempotent
`z_report_printed_at` conditional `update_item`. Both dev (DynamoDB Local at
port 8001) and prod (real DynamoDB) execute the same code path — there is no
`if S.dev_mode` branch. The `T.pos` handle resolves to a `_FloatSafeTable`
wrapping the real or local table depending on `DDB_ENDPOINT_URL`.

### 7.2 Idempotency

- **Z-report**: The `z_report_printed_at` conditional write (§5.4) ensures that
  a crash-and-retry returns the same `z_report_printed_at` timestamp and the same
  aggregate data. The aggregate is recomputed from DDB rows on every call (not
  stored), so the report content is always current with respect to any in-flight
  refunds that landed after the first Z print attempt. This is intentional: the
  Z-report is the final summary of a closed session; the GSI data is immutable
  once the session is closed.
- **X-report**: Pure read — fully idempotent by definition.

### 7.3 Security

- **Ownership enforcement**: Cashiers may only report on their own sessions.
  ADMIN and ROOT roles bypass this check (§5.8).
- **Flag gating**: With `POS_ENABLED=false`, the service raises 404. The router
  (POS-011) adds a second guard via `_require_enabled()` so double defence is in
  place even if the service is called directly in tests.
- **No sensitive data leakage**: The report does not expose raw billing ledger
  entries, card numbers, or payment-method tokens. Card tender rows carry only
  the last-4-digit hint (if set on the tender row by POS-007); that is surfaced
  in the tender breakdown under `card_hint`.
- **CSRF**: `GET` requests carry no CSRF requirement under the existing
  `require_ui_session` middleware (CLAUDE.md §Auth dependency).

## 10. Open Questions / Assumptions

1. **Assumption**: POS-006 spec §3.3 states that `cash_in_cents` and
   `change_out_cents` are maintained atomically on the session row via `ADD`. The
   Z-report reads them from the session row directly rather than recomputing from
   individual `TENDER#` rows. If the POS-006 implementation drifts from this
   spec, there could be a discrepancy. **Resolution**: The implementation of
   POS-010 must assert the session-row counters are the authoritative source; if
   POS-006 was not implemented as specified, POS-010 should compute from tender
   rows as a fallback (with a warning log).

2. **Assumption**: The `pos_sk` of transaction rows always starts with `TXN#`
   as established by POS-005. REFUND rows start with `REFUND#`. If POS-008
   used a different SK prefix in its actual implementation, `_aggregate_rows`
   must be updated accordingly.

3. **Assumption**: `GSI_SESSION_TXN` projects `ALL` attributes (as declared in
   the POS-003 `TableDef`). This means `TENDER#` rows are fully readable from
   the GSI without a second `get_item` round-trip. If the actual GSI uses
   `KEYS_ONLY` projection, POS-010 would need to fall back to individual
   `get_item` calls per row.

4. **Open question**: Should a Z report be callable more than once for
   re-printing? The current spec marks `z_report_printed_at` on first call and
   treats replays as idempotent (same data returned). If the business requirement
   is that the Z report must be "printed exactly once, forever blocked after",
   the service should raise 409 on the second call. The ticket text says
   "end-of-shift, produced at close" which implies a single authoritative event,
   but does not explicitly prohibit reprints. **Default implementation**: allow
   re-reads (idempotent, same timestamp returned); promote to a constraint only
   if POS-011 or a future ticket specifies it.

5. **Assumption**: Discount amounts on transactions (`discount_cents` on the
   `TXN#META` row) are populated by POS-005's cart-binding path from the bound
   cart's promo code logic. If `discount_cents` is absent on some rows
   (pre-POS-010 rows written before the field existed), `_to_int(None)` returns
   0 — the `_to_int` helper handles this gracefully.

6. **Assumption**: Tax totals (`tax_cents`) are computed per-transaction by the
   cart/order service and recorded on the TXN row by POS-005/006. If tax is not
   tracked at the TXN row level (e.g. only stored on the order), POS-010 will
   report `tax_cents=0` for those transactions. A follow-up ticket would be
   needed to back-fill or compute tax from the order.
