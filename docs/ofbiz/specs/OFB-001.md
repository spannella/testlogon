# OFB-001 — OFBiz module mapping spike & data-model delta

**Type:** Spike | **Priority:** P0 | **Estimate:** 4 days  
**Status:** Superseded by `docs/adr/ADR-001-ofbiz-commerce-erp.md` (Proposed, 2026-06-09)

The free-form design doc deliverable (`docs/ofbiz-commerce-plan.md`) called for in the original ticket acceptance criteria has been consolidated into ADR-001. This spec records the full engineering rationale, data-model delta, and downstream mapping so that every OFB ticket from OFB-002 onward has a single authoritative reference.

---

## 1. Summary & Goal

OFB-001 is the scoping spike that answers one question: **which OFBiz commerce/ERP capabilities are worth building natively on top of testlogon's existing cart/order/ledger stack, and what new tables and settings are needed to host them?**

The deliverable is not code — it is a decision (captured in ADR-001) that:

1. Maps every OFBiz domain (orders, inventory/warehouse, AR/AP/GL, MRP, pricing/promotions, returns) against the current data model, identifying what exists, what is missing, and what the gap is.
2. Selects a cherry-pick approach: four domains in, rest deferred or rejected.
3. Defines the DynamoDB tables, GSIs, settings keys, and feature flags that subsequent milestones will build against.
4. Produces a dependency graph and milestone sequencing so every downstream OFB ticket can reference a specific section here.
5. Obtains reviewer sign-off (engineering + finance) that the GL design correctly derives debits/credits from the existing ledger rather than creating a parallel money mechanism.

## 2. Context & Current State

### 2.1 Orders

`CommerceOrderService.create_order` (`app/services/commerce_order_service.py:39`) writes one row to `orders` (PK `order_id`, no sort key) plus N rows to `order_items` (PK `order_id`, SK `item_id`). The `orders` table has two GSIs: `GSI_USER` (partition `user_id`, sort `created_at`) and `GSI_STATUS` (partition `status`, sort `created_at`) — `scripts/local-ddb-init.py:288–294`. The order `status` is hard-coded to `"pending_payment"` at creation time (`commerce_order_service.py:75`). There is no fulfillment state machine, no `shipped` or `returned` status, and no order-line update path once an order is written.

The `order_id` is a deterministic SHA-256 of the `correlation_id` (`commerce_order_service.py:67`), giving free idempotency: submitting the same `correlation_id` twice produces the same `order_id` and a DynamoDB `put_item` replaces the row idempotently.

`create_order_from_line_items` (`commerce_order_service.py:132`) is the thin forwarding wrapper used by `purchase_cart` (`shoppingcart.py:581–584`).

### 2.2 Catalog stock

Stock is a scalar `stock_count` attribute on the catalog item (integer or None). The derived label is computed by `_compute_stock_status` (`app/routers/catalog.py:94–104`): `None` → `"unlimited"`, `≤0` → `"out_of_stock"`, `≤ low_stock_threshold` → `"low_stock"`, else `"in_stock"`. `low_stock_threshold` defaults to `S.catalog_default_low_stock_threshold` (`app/core/settings.py:833`, env `CATALOG_LOW_STOCK_THRESHOLD`, default `5`).

The Pydantic models that carry `stock_count` are `CatalogItemCreateIn` (`app/models.py:538`), `CatalogItemPatchIn` (`app/models.py:550`), `CatalogStockOut` (`app/models.py:573`), and `CatalogItemOut` (`app/models.py:672`). There is no `reserved` quantity, no `available = on_hand - reserved` computation, no first-class `reorder_point` field, and no warehouse/location dimension.

### 2.3 Cart purchase and stock decrement

`purchase_cart` (`app/services/shoppingcart.py:474`) performs a **decrement-at-purchase** strategy. For each line item it issues a conditional DynamoDB `update_item` with `UpdateExpression "SET stock_count = stock_count - :qty"` and `ConditionExpression "stock_count >= :qty"` (`shoppingcart.py:517–519`). On a `ConditionalCheckFailedException` it manually rolls back all previously decremented lines in a best-effort loop (`shoppingcart.py:522–537`) and raises a 409 "out of stock". There are no soft reservations — stock is only consumed at the exact moment `purchase_cart` executes. Idempotency relies on `_cart_purchase_idempotency_key` (`shoppingcart.py:194`) and the `cart_purchase:{user}:{cart}:{order}` trigger event (`shoppingcart.py:597`).

### 2.4 Billing ledger (single-entry)

`new_ledger_entry` (`app/services/billing_shared.py:224`) writes one DynamoDB row per money event. The item carries `{type, amount_cents, state ∈ {pending, settled, reversed}, reason, provider, ledger_date}`. Account balances live in four running counters in `BAL_FIELDS` (`billing_shared.py:15`): `owed_pending_cents`, `owed_settled_cents`, `payments_pending_cents`, `payments_settled_cents`. `apply_balance_delta` (`billing_shared.py:83`) does atomic `ADD` updates on these counters. `compute_due` (`billing_shared.py:158`) derives amounts owed from the counters.

`ledger_date` is a denormalized UTC date string (`YYYY-MM-DD`) added by FIN-013/GAP-0202 (`billing_shared.py:253`, `ledger_date_for_ts` helper at `:10`). The billing table has a `GSI_LEDGER_DATE` index on `(ledger_date, sk)` used by `platform_financial_dashboard._query_ledger_by_date` (`app/services/platform_financial_dashboard.py:136–147`) to bucket entries by day for KPI aggregation. **This index is the derivation source for the double-entry GL — the GL posting loop reads it, never the single-entry ledger directly.**

This is strictly single-entry: there is no contra-account, no debit/credit pair, no chart of accounts, no trial balance. The existing accounting CSV mapper (`app/services/audit_export_accounting.py`) exports ledger rows to QuickBooks/Xero column shapes but does not produce a balanced ledger.

### 2.5 Refunds

`refund_payment` (`app/routers/billing.py:1287`) is the only refund mechanism. It calls the provider (Stripe), writes a `type="adjustment", reason="refund", state="settled"` ledger entry with `provider` attribution (FIN-013/GAP-0203) (`billing.py:1306–1316`), reverses the balance counters (`billing.py:1318–1321`), and marks the original ledger row as `reversed` via `settle_or_reverse_ledger` (`billing.py:1323–1324`). Any RMA refund **must reuse this path** — no parallel refund mechanism is acceptable.

### 2.6 Promotions (flat)

`VALID_DISCOUNT_TYPES = {"percentage", "fixed_amount", "free_trial"}` (`app/services/promo_codes.py:26`). `_calculate_discount` (`promo_codes.py:376`) applies flat per-code math. `validate_promo_code` (`promo_codes.py`) is called from `purchase_cart` (`shoppingcart.py:551–574`). There is no tiered pricing (e.g., 5+ units → 10% off), no bulk discount, no conditional rule (minimum cart value, specific category), no scope dimension (SKU/category/creator), and no rule-stacking or precedence.

### 2.7 Existing accounting CSV mapper

`app/services/audit_export_accounting.py` maps `UnifiedAuditEvent` (a billing ledger row via `BillingLedgerAdapter`) to QuickBooks (`billing_event_to_quickbooks_row`, `:105`) and Xero (`billing_event_to_xero_row`, `:124`) column formats. The `_qb_transaction_type` helper already maps ledger entry types to QB transaction types (`audit_export_accounting.py:38–65`; mapping dict at `:47–57`). **The GL design must remain compatible with this mapper** — it is a downstream consumer that must keep working unchanged.

### 2.8 Invoices

`app/services/invoices.py:272` manages `create_invoice` (`:272`), monotonic invoice numbering (`_next_invoice_number` at `:82`), and PDF rendering (`_render_invoice_pdf` area). `list_invoices` (`:395`) / `admin_list_invoices` (`:492`) use the `invoices` table. The AR derivation in Milestone 4 reconciles to `invoices.py` — it does not replace it.

### 2.9 Gap summary

| OFBiz capability | testlogon today | Gap |
|---|---|---|
| Warehouse / location model | None | No `location_id` dimension on stock |
| Soft reservations | None (decrement-at-purchase only) | No reserve→commit→release lifecycle |
| Returns / RMA entity | None | No `returns` table, no state machine |
| Double-entry GL | Single-entry ledger | No chart of accounts, journal entries, trial balance |
| AR / AP subledgers + aging | `BAL_FIELDS` + `invoices.py` (partial) | No aged receivables/payables view |
| Rules-based pricing | Flat promo codes only | No tiered/bulk/conditional/scoped rules |
| MRP / manufacturing | None | Explicitly deferred |
| Multi-warehouse transfer orders | None | Explicitly deferred |

## 3. Data Model

All new tables follow `_resolve_table_name(S.<name>, "<default>")`, use `_FloatSafeTable` via `_safe_table(...)` in `app/core/tables.py`, and are appended to the `_ofbiz_tables()` block in `scripts/local-ddb-init.py` (currently at line 2452). Numeric GSI sort keys **must** be declared in `attr_types` per the CLAUDE.md gotcha; failing to do so causes `ValidationException` at query time.

### 3.1 `inventory` — first-class SKU stock record

| Attribute | Type | Notes |
|---|---|---|
| `sku` | S (PK) | Matches catalog item `item_id` (logical SKU) |
| `location_sk` | S (SK) | Value `LOC#{location_id}`, default `LOC#warehouse` |
| `location_id` | S | Denorm for queries; default `warehouse` |
| `on_hand` | N | Physical units in stock |
| `reserved` | N | Units soft-reserved, not yet committed |
| `available` | N | `on_hand - reserved`; written on every update |
| `reorder_point` | N | Alert threshold; mirrors catalog `low_stock_threshold` if not set |
| `status` | S | `in_stock` / `low_stock` / `out_of_stock`; derived, stored for GSI |
| `updated_at` | N | Unix timestamp (`now_ts()`) |
| `catalog_item_key` | S | `{category_id}#{item_id}` for denorm sync back to `T.catalog` |

GSI: **`GSI_AVAILABLE`** — partition `status` (S), sort `available` (N). Enables low-stock filter queries without a scan. `attr_types={"available": "N"}`.

Already defined at `scripts/local-ddb-init.py:2456–2464`.

### 3.5 `gl_journal` — double-entry journal entries

| Attribute | Type | Notes |
|---|---|---|
| `journal_pk` | S (PK) | `JE#{journal_id}` where `journal_id = sha256(source_entry_id)[:32]` |
| `sk` | S (SK) | `META` for header; `LINE#{n}` for each debit/credit line |
| `source_entry_id` | S | Source billing ledger `entry_id`; idempotency key |
| `gl_date` | S | UTC date string `YYYY-MM-DD` (matches source `ledger_date`) |
| `posted_at` | N | Unix timestamp of GL posting |
| `entry_type` | S | Source ledger `type` (e.g. `tip_debit`, `subscription_charge`, `adjustment`) |
| `total_debit_cents` | N | Sum of debit lines; must equal `total_credit_cents` |
| `total_credit_cents` | N | Sum of credit lines; must equal `total_debit_cents` |
| `posted_by` | S | `system_gl_poster` for background posts; ROOT sub for manual |

Line rows (`sk = LINE#{n}`): `account_id`, `side` (`debit`/`credit`), `amount_cents`, `memo`.

GSIs:
- **`GSI_SOURCE`** — partition `source_entry_id` (S), sort `posted_at` (N). Idempotency check: `source_entry_id` already has a JE → skip. `attr_types={"posted_at": "N"}`.
- **`GSI_DATE`** — partition `gl_date` (S), sort `posted_at` (N). Trial-balance date range queries. Same `attr_types`.

**Not yet in `scripts/local-ddb-init.py` or `app/core/tables.py`** — deliverable of OFB-002.

### 3.6 `pricing_rules` — tiered/bulk/conditional pricing engine

| Attribute | Type | Notes |
|---|---|---|
| `rule_pk` | S (PK) | `RULE#{rule_id}` where `rule_id = uuid4().hex` |
| `sk` | S (SK) | `META` |

- **`GSI_CREATOR`** — partition `creator_id` (S), sort `created_at` (N). Admin rule listing. `attr_types={"created_at": "N"}`.

**Not yet in `scripts/local-ddb-init.py` or `app/core/tables.py`** — deliverable of OFB-002.

```python
    # returns {applied_rules: [...], discount_cents: int, final_price_cents: int}
```

Integration point: `purchase_cart` calls `evaluate_rules` for each line when `S.pricing_rules_enabled` is on, before the `validate_promo_code` call. Flat promo codes remain unchanged.

## 5. Detailed Behavior & Edge Cases

### 5.1 Inventory — available-qty atomicity

`available` must be kept consistent with `on_hand - reserved`. The strategy is to **always compute and write `available` as a derived attribute on every `update_item`** using a single DynamoDB `update_item` expression (e.g., `SET on_hand = :h, available = :h - reserved`). This is safe because `on_hand` and `reserved` are numeric; the expression evaluates server-side. A conditional expression (`available >= :qty`) on the `reserve` path enforces the oversell guard — the same pattern as `shoppingcart.py:518`.

### 5.2 Reservation TTL-release loop

Pattern reused from `start_cart_abandonment_task` (`app/routers/shoppingcart.py:358`, registered in `app/main.py:985`). The loop queries `GSI_EXPIRY` with `gsi_expiry_pk = "SCHED#ACTIVE"` and `expires_at < now()`, releases each reservation (add quantity back to `available`, update status to `expired`, flip `gsi_expiry_pk` to `SCHED#DONE`), and emits an audit event. A conditional `status = active` guard on the release prevents double-release. Loop interval = `S.inventory_reservation_ttl_seconds / 4` (check four times per TTL window).

### 5.3 Returns — quantity validation

`request_return` must validate that `sum(line.quantity)` for each `item_id` does not exceed the original `order_items` quantity. It fetches the `order_items` row (PK `order_id`, SK `item_id`) and checks. An additional check gates on order status: only orders in `paid` / `fulfilled` status (once the order state machine is expanded) are returnable; `pending_payment` orders are not.

### 5.4 Returns — ownership enforcement

`request_return` and `get_return` (customer path) verify `order.user_id == user_sub`. A mismatch returns 403. Admin paths bypass this check but require `require_admin_session`.

### 5.5 GL posting — balanced entries and the type→account map

Every call to `post_ledger_entry` must produce a balanced JE (Σdebits == Σcredits) or raise `ValueError` and not persist. The type→account mapping is a Python dict in `gl_posting.py` (no DB lookup at post time):

| Entry type | Debit account | Credit account |
|---|---|---|
| `tip_debit`, `unlock_debit`, `subscription_charge` | `CASH` | `SALES_REV` |
| `tip_credit`, `unlock_credit`, `deposit` | `SALES_REV` | `CASH` |
| `refund` / `adjustment` (negative) | `REFUNDS_CONTRA` | `CASH` |
| `payout` | `AP` | `CASH` |
| `chargeback` | `AR` | `CASH` |
| Tax-carrying entries | `CASH` debit split: `SALES_REV` + `TAX_PAYABLE` credit |

This mapping is **a deliverable of OFB-013**, not OFB-001; the table above is normative guidance for the implementer.

### 5.6 GL idempotency

`post_ledger_entry` computes `journal_id = sha256(source_entry_id)[:32]` (same `hashlib.sha256(...).hexdigest()[:32]` pattern as `commerce_order_service.py:67`). Before writing, it queries `GSI_SOURCE` by `source_entry_id`. If a row exists, it returns the existing JE without writing. The conditional `attribute_not_exists(journal_pk)` on `put_item` provides a race-safe belt-and-suspenders guard.

### 5.7 Catalog stock_count mirror

When `INVENTORY_RESERVATIONS_ENABLED` is on, the catalog `stock_count` field becomes a read-through mirror: `inventory.set_on_hand` and `inventory.adjust` write back to `T.catalog` (the `catalog_item_key` attribute on the inventory record identifies which item to update) via `update_item`. The catalog item's `stock_count` always equals the inventory record's `on_hand`. `_compute_stock_status` (`catalog.py:94`) continues to use `stock_count` — no change needed in the catalog router.

### 5.8 Pricing rules — stacking and precedence

Rules are evaluated in `priority` order (ascending). The first matching, non-stackable rule short-circuits further evaluation. Stackable rules (`allow_stack=True`) accumulate their discounts additively. The total `discount_cents` is capped at `unit_price_cents * quantity` (no negative prices). When both a pricing rule and a promo code apply, the promo code discount is applied **after** the pricing rules (the existing `validate_promo_code` path is unchanged; pricing rules reduce the `total_cents` that `validate_promo_code` receives).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**No `dev_mode` branches.** All inventory, reservation, RMA, GL posting, and pricing rule services run identical Python/DynamoDB code in dev (in-process moto via `app/core/dev_s3.py` pattern, local DDB on port 8001) and prod (real DynamoDB). There are no `if S.dev_mode` forks in business logic — same pattern as the audit-export and KYC-partner-API services cited in CLAUDE.md.

**Idempotency strategy:**
- Order creation: deterministic `sha256(correlation_id)` already in `commerce_order_service.py:67`.
- GL journal entries: `sha256(source_entry_id)` + conditional `attribute_not_exists` guard — one JE per source `entry_id`, forever.
- Reservation release: conditional `status = "active"` guard on every release path (TTL-loop, cart-abandon, manual).
- RMA refund: `refund_ledger_sk` stored on the `returns` row; a second call checks for an existing non-empty value and returns the existing outcome without a second provider call.

**Role gating:**
- Customer-facing (cart, return request, "My Returns"): `Depends(require_ui_session)` (`app/auth/deps.py`) + CSRF on non-GET.
- Admin (inventory ops, RMA queue, approve/reject/receive): `Depends(require_admin_or_root)` (`app/auth/policy.py:67`) + CSRF. Note: `require_admin_session` does not exist; use `require_admin_or_root` or `require_admin_or_root_csrf` (`:100`) for combined role+CSRF check.
- ROOT-only (chart of accounts, journal browser, trial balance, financial statements, pricing rule admin): `Depends(require_root_session)` (`app/auth/deps.py:308`).

**Money security:** RMA refunds call `refund_payment` (`billing.py:1287`) directly. Note: `refund_payment` itself does **not** call `_require_provider_enabled` (GAP-0206) or `_fraud_gate` (GAP-0207) — those guards exist on charge paths (`pay_balance`, `charge_once`, `wallet_deposit`), not on the refund path. OFB-010 should add an explicit provider-enabled check before calling `refund_payment` to prevent issuing refunds via a disabled provider. No separate refund path is created.

**Audit events:** Every inventory adjustment, reservation state change, RMA transition, GL post, and pricing rule change emits `app/services/alerts.audit_event(...)` (same pattern as `commerce_order_service.py:106`). Event names: `inventory_adjusted`, `inventory_reserved`, `reservation_committed`, `reservation_released`, `rma_requested`, `rma_approved`, `rma_rejected`, `rma_received`, `rma_refunded`, `gl_entry_posted`, `pricing_rule_created`, `pricing_rule_updated`, `pricing_rule_deleted`.

## 8. Backward Compatibility & Migration

**Zero behavior change with flags off.** The existing `purchase_cart`, `_compute_stock_status`, `new_ledger_entry`, `refund_payment`, and `validate_promo_code` paths are not touched when all OFBiz flags are off. The new tables (`inventory`, `reservations`, `returns`, `gl_accounts`, `gl_journal`, `pricing_rules`) are created by `scripts/local-ddb-init.py` on `just restart` regardless of flags — empty tables cause no harm.

**Catalog `stock_count` migration (OFB-003).** When `INVENTORY_RESERVATIONS_ENABLED` is first turned on in an environment, existing catalog items have `stock_count` but no inventory records. OFB-003 includes a one-shot migration script (`scripts/ofbiz-inventory-seed.py`) that reads all catalog items with `stock_count is not None` and creates corresponding inventory records. The migration is idempotent (uses a conditional `attribute_not_exists(sku)` put).

**GL backfill (OFB-014).** Historical billing ledger rows predate the GL. The `post_date_range(start, end)` function (Milestone 4) provides the backfill path, querying `GSI_LEDGER_DATE` day by day and calling `post_ledger_entry` for each row. Because GL posting is idempotent per `entry_id`, the backfill can be re-run safely. The backfill must be run **before** turning on `GL_DOUBLE_ENTRY_ENABLED` in prod to ensure the books are complete from day one.

**`audit_export_accounting.py` compatibility.** The QB/Xero CSV mapper reads from `UnifiedAuditEvent` (a billing ledger row projection). The GL work does not change the billing table schema — it adds rows to `gl_journal`. The CSV mapper is unaffected.

## 10. Open Questions / Assumptions

1. **Assumption:** `order.user_id` is the same as the session `user_sub` — verified from `commerce_order_service.py:74` (order record sets `"user_id": user_id`; `purchase_cart` at `shoppingcart.py:582` passes `user_id=user_sub`). Ownership checks in returns are safe.

2. **Assumption:** `location_id` dimension is forward-compatible but only `"warehouse"` is used. Multi-location is deferred. If a future ticket needs multi-location, the `LOC#{location_id}` SK design accommodates it without a schema migration.

3. **Open question:** What is the correct order status when an order is eligible for return? Currently `commerce_order_service.py:75` hard-codes `status = "pending_payment"` — there is no `"paid"` or `"fulfilled"` status today. OFB-008 may need to either (a) extend the order state machine or (b) validate against the billing ledger (look for a settled ledger entry for the cart that produced the order) rather than the order status field. This needs eng + product sign-off before OFB-008 ships.

4. **Open question:** Should the GL posting loop run as a startup task (like `start_audit_export_worker_task`) or on a cron (`POST /internal/gl/post-date` triggered externally)? Recommendation: startup task with a configurable polling interval (`GL_POSTING_POLL_INTERVAL_SECONDS`, default `3600`). Final decision deferred to OFB-014.

5. **Assumption:** The type→account mapping (section 5.5) covers all `entry_type` values currently in production. The canonical list is derived from `audit_export_accounting.py:47–57` and the `VALID_DISCOUNT_TYPES` set. An "unknown" entry type must raise loudly rather than post silently to a catch-all account.

6. **Open question:** Finance stakeholder sign-off on the debit/credit mapping (section 5.5) is required before OFB-013 ships. Until then, the GL tables exist but `GL_DOUBLE_ENTRY_ENABLED` remains `false`.

7. **Assumption:** Pricing rule discounts are applied per-SKU (the `evaluate_rules` call is per line item in `purchase_cart`). Cart-level conditional rules (e.g., minimum total) receive the current `total_cents` before per-line discounts. The exact evaluation order (per-line rules first, then cart-level rules) must be confirmed with product before OFB-019.

8. **Assumption:** `pricing_rules` and the existing `promo_codes` service are separate; a `PricingRule` may optionally carry a `promo_code_id` to enforce the promo code's `max_uses` cap, but the flat promo code path is otherwise unchanged. This needs confirmation that there is no double-redemption risk.
