# ORD-004 — Pydantic models for lifecycle, history, ship groups, adjustments

**Type:** Feature | **Priority:** P0 | **Estimate:** 2 days
**Milestone:** 1 — Foundation (flag, data model, tables)

---

## 1. Summary & Goal

ORD-004 adds the Pydantic request/response vocabulary that every downstream order-lifecycle ticket (ORD-005 through ORD-010) will import. The deliverable is a set of new model classes appended to `app/models.py` — nothing more:

- `OrderLifecycleStatus` — the canonical status enum (str, Enum)
- `OrderStatusHistoryEntry` — a single audit-trail row shape
- `ShipGroup` — a logical shipment within an order (address ref + line refs + status)
- `OrderAdjustment` — a money line applied to an order (discount / surcharge / tax / shipping / promotion)
- `OrderTransitionRequest` — request body for `POST .../transition`
- `OrderTransitionResult` — response from a successful transition
- `OrderLifecycleOut` — the enriched order response, additive over the existing flat shape

No service, router, DynamoDB table, settings, or frontend file is changed. All new classes are appended at the end of `app/models.py` under a comment banner `# ── Order Lifecycle (ORD-004) ──`. With `ORDER_LIFECYCLE_ENABLED=false` (default), none of these models are referenced by any active code path and existing serialisation is byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 Where orders are written today

`commerce_order_service.CommerceOrderService.create_order` (`app/services/commerce_order_service.py:39`) is the single order-creation entry point. It:

- Derives a deterministic `order_id = sha256(corr)[:32]` where `corr = correlation_id or f"{source_system}:{uuid4().hex}"` (`app/services/commerce_order_service.py:66–67`).
- Writes a single DynamoDB item to `T.orders` (`app/services/commerce_order_service.py:85`) with fields: `order_id`, `user_id`, `status="pending_payment"` (`:75`), `created_at` (ISO string), `updated_at`, `source_system`, `correlation_id`, `currency`, `amount_cents`, `line_item_count`, `metadata`.
- Writes one `T.order_items` row per line item (`:88–104`).

The `_line_amount_cents` helper at `app/services/commerce_order_service.py:27` establishes the money convention: `amount_cents` is a non-negative `int` derived from `pricing_ref.unit_price_cents`, `pricing_ref.amount_cents`, or `pricing_ref.price_cents` — always an integer, never a float, never a string.

### 2.2 Current order status field

`status="pending_payment"` is the only value ever written today (`app/services/commerce_order_service.py:75`). The `UnifiedCheckoutSessionOut` response model at `app/models.py:905` carries `status: str = "pending_payment"`. There is no `lifecycle_status` field anywhere in the current schema.

### 2.3 Existing models.py conventions

`app/models.py` is the monolithic models file (14 633 lines at time of writing). The file:

- Imports `from enum import Enum` (`app/models.py:7`) and `from pydantic import BaseModel, Field, conint, field_validator, model_validator` (`app/models.py:11–18`).
- Uses `class SomeStatus(str, Enum)` for string enums, e.g. `PmIdeaStatus` (`app/models.py:7828`), `PmIdeaCategory` (`app/models.py:7812`), `PmIdeaPriority` (`app/models.py:7821`).
- Expresses money as `amount_cents: int = Field(..., ge=0)` or `conint(ge=0)`, e.g. `app/models.py:823` (`conint(ge=0, le=100000000)`) and `app/models.py:13165` (`int = Field(..., ge=0)`). Negative amounts are never used for credit values; surcharges/discounts store absolute magnitude and a `type` field carries sign semantics.
- Uses `Optional[str] = None` for optional string fields throughout.
- Uses `Optional[List[...]]` with `= None` default for additive collections that may not be populated (e.g. `app/models.py:446` — `carrier_events: Optional[List[Dict[str, Any]]] = None`).
- Appends new model groups under section comment banners (`# ── Ad Performance Optimization (ADS-017) ──` at line 12385, etc.).

### 2.4 Existing address model

`AddressBase` / `AddressOut` at `app/models.py:1411–1431` define the address shape used across the platform. `AddressOut` has `address_id: str` and the full line1/city/state/postal_code/country fields. `ShipGroup` references a shipping address by `address_id` rather than embedding the full address inline — consistent with how the platform references user addresses by ID elsewhere (e.g. `app/models.py:1443`).

### 2.5 Existing return/order output patterns

`ReturnOut` at `app/models.py:655` shows how an order-linked model carries `order_id: str`, `status: str`, `currency: str = "usd"`, and `refund_amount_cents: int = 0`. `ReturnRequestIn` at `app/models.py:638` uses `order_id: str = Field(min_length=1, max_length=128)` as the canonical order ID field shape.

### 2.6 ORD-001 design decisions adopted here

ORD-001 (`docs/ofbiz/specs/ORD-001.md`) established:

- The additive `lifecycle_status` + legacy `status` coexistence decision (Section 3.6).
- The eleven-member status set: `created`, `approved`, `allocated`, `picking`, `packed`, `shipped`, `completed`, `held`, `backorder`, `cancelled`, `returned`.
- The SK partition design for history (`HIST#`), ship groups (`SHIPGRP#`), and adjustments (`ADJ#`) under the `orders` table.
- The `OrderLifecycleOut` field list (Section 4.2, ORD-001).

ORD-004 materialises those decisions as concrete Pydantic classes. Where ORD-001 showed a sketch, this spec is the authoritative definition that downstream tickets import.

## 3. Data Model

ORD-004 introduces no DynamoDB changes. It is a pure `app/models.py` addition. The DDB single-table layout for the `orders` table (PK `order_id`, SK `sk`, new GSIs `GSI_LIFECYCLE_STATUS` and `GSI_SHIP_DATE`) is specified in ORD-003.

### 3.1 Summary of DDB row shapes (informational — implemented in ORD-003)

| Row type | SK pattern | Carries |
|---|---|---|
| Order header | `ORDER` | `lifecycle_status`, `status` (mirror), `updated_ts`, all existing fields |
| Status history | `HIST#{ts:020d}#{event_id}` | `from_status`, `to_status`, `actor`, `reason`, `ts`, `event_id` |
| Ship group | `SHIPGRP#{ship_group_id}` | `ship_group_id`, `ship_method`, `address_id`, `item_ids[]`, `ship_status`, `ship_date_bucket`, `ship_ts` |
| Order adjustment | `ADJ#{adjustment_id}` | `adjustment_id`, `adj_type`, `amount_cents`, `currency`, `label`, `taxable`, `source_rule_ref` |

The Pydantic models in Section 4 map onto these DDB row shapes for serialisation and API response construction. The model fields align with the DDB attributes to make `**item` construction straightforward in ORD-005+.

### 4.1 Insertion point in `app/models.py`

All new classes are appended at the end of `app/models.py` (after the last existing `model_rebuild()` call at line 12891 and the `AffiliateTopProductsOut` class at line 14632), under the banner:

```python

```

No existing class is modified. No `model_rebuild()` is needed for these models (they contain no forward references that aren't already resolved by the time they are defined at file end).

### 4.2 `OrderLifecycleStatus` enum

```python
class OrderLifecycleStatus(str, Enum):
    CREATED   = "created"
    APPROVED  = "approved"
    ALLOCATED = "allocated"
    PICKING   = "picking"
    PACKED    = "packed"
    SHIPPED   = "shipped"
    COMPLETED = "completed"
    HELD      = "held"
    BACKORDER = "backorder"
    CANCELLED = "cancelled"
    RETURNED  = "returned"
```

Design notes:
- `str, Enum` follows the identical pattern used for `PmIdeaStatus` (`app/models.py:7828`) and `PmIdeaCategory` (`app/models.py:7812`). Pydantic serialises `str` enums as their `.value` string, not as `"OrderLifecycleStatus.created"`.
- All eleven members match ORD-001 Section 3.1 exactly. No aliases or synonyms.
- Terminal states (`CANCELLED`, `RETURNED`) have empty transition sets in ORD-005's `TRANSITIONS` dict; the enum itself does not encode terminality.
- This enum is used as the type for `lifecycle_status` fields in `OrderLifecycleOut`, `OrderStatusHistoryEntry`, `OrderTransitionRequest`, and `ShipGroup`.

### 4.3 `OrderStatusHistoryEntry`

```python
class OrderStatusHistoryEntry(BaseModel):
    event_id: str = Field(min_length=1, max_length=32)
    from_status: Optional[str] = None        # None for the initial "created" event
    to_status: str                           # always populated
    actor: str = Field(min_length=1, max_length=255)
    reason: str = Field(default="", max_length=500)
    ts: int = Field(ge=0)                    # Unix seconds (now_ts())
```

Design notes:
- `from_status` is `Optional[str]` (not `Optional[OrderLifecycleStatus]`) because history rows written by ORD-006 are read back from DynamoDB as raw strings; coercing to enum on read may fail if the DDB item predates the enum definition. Using `str` is the defensive choice, consistent with `ReturnOut.status: str` (`app/models.py:659`).
- `to_status` is `str` for the same reason.
- `ts` is a non-negative integer (Unix seconds from `now_ts()`), consistent with all numeric timestamps in the codebase (e.g. `created_at: int = 0` in `ReservationOut` at `app/models.py:626`).
- `event_id` is the 16-char hex prefix of `sha256(order_id|from|to|idempotency_key)` defined in ORD-005. Max length 32 gives room for future expansion.
- `reason` defaults to `""` so that system-generated events (e.g. auto-approve) do not need an explicit reason.
- The DDB SK is `HIST#{ts:020d}#{event_id}`; this model does NOT carry `sk` — the SK is a DDB internal field, not exposed in the API response.

### 4.4 `ShipGroup`

```python
class ShipGroup(BaseModel):
    ship_group_id: str = Field(min_length=1, max_length=64)
    ship_method: str = Field(default="", max_length=128)   # e.g. "GROUND", "EXPRESS_2D"
    address_id: Optional[str] = Field(default=None, max_length=128)
    item_ids: List[str] = Field(default_factory=list)      # item_id values from order_items
    ship_status: OrderLifecycleStatus = OrderLifecycleStatus.CREATED
    ship_date_bucket: Optional[str] = Field(default=None, max_length=10)  # YYYY-MM-DD
    ship_ts: Optional[int] = Field(default=None, ge=0)    # Unix seconds
    tracking_number: Optional[str] = Field(default=None, max_length=256)
    tracking_url: Optional[str] = Field(default=None, max_length=2048)
    created_at: int = Field(default=0, ge=0)
    updated_at: int = Field(default=0, ge=0)
```

Design notes:
- `address_id` is an opaque reference to a `AddressOut.address_id` (`app/models.py:1428`). The address is not embedded inline; the caller resolves it separately. This keeps the `ShipGroup` row compact and avoids denormalization drift.
- `item_ids` is a `List[str]` of `item_id` values from the `T.order_items` table (where `item_id` is the 1-based integer string, e.g. `"1"`, `"2"`). The list is stored as a DynamoDB `SS` (String Set) attribute on the SHIPGRP row. An empty list means the ship group covers all order items (i.e. not yet explicitly partitioned).
- `ship_status` is typed as `OrderLifecycleStatus` because ship-group status mirrors the order-level status values for the fulfillment arc: `allocated → picking → packed → shipped`. However the default is `CREATED` to represent "not yet allocated to a ship group". This reuse of the same enum avoids a separate `ShipGroupStatus` enum and aligns with OFBiz's single-status-domain approach.
- `ship_date_bucket` is `YYYY-MM-DD` string used as the GSI_SHIP_DATE partition key; `ship_ts` is the integer Unix timestamp for range queries. Both are `Optional` because they are only populated when a ship date is known.
- `tracking_number` / `tracking_url` mirror `PurchaseShippingIn` at `app/models.py:440–441`.
- `created_at` / `updated_at` are integer Unix seconds, consistent with `now_ts()` usage.

**Validation constraint**: `ship_status` must be one of `{CREATED, ALLOCATED, PICKING, PACKED, SHIPPED}` for an active ship group; `CANCELLED` is also valid. A `model_validator` enforcing this is deferred to ORD-009 (ship group service) since at the model layer the constraint is informational, not safety-critical.

### 4.5 `OrderAdjustment`

```python
class OrderAdjustmentType(str, Enum):
    DISCOUNT  = "discount"
    SURCHARGE = "surcharge"
    TAX       = "tax"
    SHIPPING  = "shipping"
    PROMOTION = "promotion"


class OrderAdjustment(BaseModel):
    adjustment_id: str = Field(min_length=1, max_length=64)
    adj_type: OrderAdjustmentType
    amount_cents: int = Field(..., ge=0)     # always non-negative; sign conveyed by adj_type
    currency: str = Field(default="USD", min_length=3, max_length=8)
    label: str = Field(default="", max_length=255)    # human-readable description
    taxable: bool = False                             # whether this line itself is taxable
    source_rule_ref: Optional[str] = Field(default=None, max_length=128)
    created_at: int = Field(default=0, ge=0)
```

Design notes:
- `adj_type` uses a new `OrderAdjustmentType(str, Enum)` rather than a `Literal[...]` because the type also appears as a DDB-stored string and must be roundtrippable through serialisation without loss; an enum is safer than a `Literal` when a new type is added later.
- `amount_cents: int = Field(..., ge=0)` — always non-negative, consistent with the `_line_amount_cents` convention at `app/services/commerce_order_service.py:27`. The `adj_type` carries the sign semantics: `discount` and `promotion` reduce the total; `surcharge`, `tax`, `shipping` increase it. This matches how billing ledger entries work (`new_ledger_entry` at `app/services/billing_shared.py:224` uses a single positive `amount_cents` with a separate `entry_type`/`reason` for direction).
- `currency` defaults to `"USD"` per the platform convention (`app/models.py:824`).
- `label` is a human-readable string for display (e.g. `"10% Early Bird Discount"`, `"CA Sales Tax 8.5%"`).
- `taxable` indicates whether this adjustment line itself is subject to tax calculation — relevant for tax-inclusive shipping lines.
- `source_rule_ref` is an opaque reference to the pricing rule, promotion code, or tax rule that generated this adjustment (e.g. a `PromoCodeOut.code_id` from `app/models.py:3485`). Stored as-is for audit/GL attribution; not validated by the model.
- The DDB SK is `ADJ#{adjustment_id}`; `adjustment_id` is `uuid4().hex` generated in ORD-008.

### 4.6 `OrderTransitionRequest`

```python
class OrderTransitionRequest(BaseModel):
    target_status: OrderLifecycleStatus
    reason: str = Field(default="", max_length=500)
    idempotency_key: Optional[str] = Field(default=None, max_length=128)
```

Design notes:
- This is the request body for `POST /ui/orders/{order_id}/transition` (ORD-005).
- `target_status` is the only required field; `reason` and `idempotency_key` are optional.
- `idempotency_key` enables exactly-once semantics for retried requests (derived in ORD-005 as `sha256(order_id|from|to|idempotency_key)[:16]`).
- Max lengths are defensive; no semantic validation is done at model level (transition legality is enforced by the service in ORD-005).

### 4.7 `OrderTransitionResult`

```python
class OrderTransitionResult(BaseModel):
    order: "OrderLifecycleOut"
    event_id: str
    from_status: Optional[str] = None
    to_status: str
```

Design notes:
- `order` is a forward reference to `OrderLifecycleOut` (Section 4.8). Since both classes are defined in the same block at end-of-file, there is no circular dependency; Python resolves the string annotation at class-creation time. If any forward-reference issue arises, a `OrderTransitionResult.model_rebuild()` call at file end resolves it (following the `SignatureTemplateMigrationCheckIn.model_rebuild()` pattern at `app/models.py:12382`).
- `from_status` is `Optional[str]` — `None` for the initial `created` event.
- `to_status` is `str` for consistency with `OrderStatusHistoryEntry.to_status`.
- `event_id` is the 16-char hex transition ID written to the HIST row; the caller uses it for idempotency replay detection.

### 4.8 `OrderLifecycleOut`

This is the enriched order response model. It is additive over the existing flat shape. The core fields mirror the DynamoDB `order_record` written by `create_order` (`app/services/commerce_order_service.py:72–84`), **not** the slimmer return dict (`:119–130`, which lacks `updated_at`, `line_item_count`, and `metadata`). The ORD-005 router reads the DDB record directly to populate this model.

```python
class OrderLifecycleOut(BaseModel):
    # ── Core fields (mirror of DDB order_record written by create_order :72–84) ──
    order_id: str
    status: str                              # legacy mirror (always "pending_payment" or a mirror value)
    created_at: str                          # ISO string (existing convention)
    updated_at: str                          # ISO string
    source_system: str
    correlation_id: str
    amount_cents: int = Field(ge=0)
    currency: str = Field(default="USD", min_length=3, max_length=8)
    line_item_count: int = Field(default=0, ge=0)
    metadata: Dict[str, Any] = Field(default_factory=dict)

    # ── Lifecycle fields (populated only when ORDER_LIFECYCLE_ENABLED is on) ──
    lifecycle_status: Optional[OrderLifecycleStatus] = None
    updated_ts: Optional[int] = Field(default=None, ge=0)   # Unix seconds
    pre_hold_status: Optional[str] = None                   # set when status is HELD

    # ── Enriched collections (None = not fetched; [] = fetched but empty) ──
    adjustments: Optional[List[OrderAdjustment]] = None
    ship_groups: Optional[List[ShipGroup]] = None
    status_history: Optional[List[OrderStatusHistoryEntry]] = None
```

Design notes:
- The first block (`order_id` through `metadata`) mirrors the DDB `order_record` keys written by `commerce_order_service.create_order` at `app/services/commerce_order_service.py:72–84`. The slimmer return dict (`:119–130`) omits `updated_at`, `line_item_count`, and `metadata`; the ORD-005 orders router must read the DDB item directly to populate those fields.
- `lifecycle_status: Optional[OrderLifecycleStatus] = None` is the key additive field. It is `None` on all orders written before ORD-007 (which backfills `lifecycle_status="created"` for flag-on orders). Existing consumers that only read `status` never see this field.
- `updated_ts: Optional[int]` is the integer Unix timestamp needed by `GSI_LIFECYCLE_STATUS` (numeric sort key declared in ORD-003 with `attr_types={"updated_ts": "N"}`). The existing `updated_at` ISO string is retained for backward compat.
- `pre_hold_status: Optional[str]` is a convenience hint set by ORD-005 during `→ HELD` transitions (Section 5.5 of ORD-001).
- `adjustments`, `ship_groups`, `status_history` use `Optional[List[...]] = None` to distinguish "not requested" (None) from "requested and empty" ([]). The `GET /orders/{order_id}` router in ORD-005 will optionally populate these based on `?include=history,adjustments,ship_groups` query parameters.
- `checkout_session_id` from the existing `create_order` return dict (`:129`) is intentionally omitted from `OrderLifecycleOut`. Note that `checkout_session_id` is only in the return dict as a top-level convenience key, not in the DDB record. The canonical location is `metadata["checkout_session_id"]` (set by `unified_checkout.py:113`). Existing consumers read `result["checkout_session_id"]` from the raw dict; `OrderLifecycleOut` is the **API response** model, not the internal service return type.

## 5. Detailed Behavior & Edge Cases

### 5.1 Validation: `amount_cents` must be non-negative

`OrderAdjustment.amount_cents: int = Field(..., ge=0)` rejects negative values at parse time. If a caller attempts to encode a discount as a negative amount, Pydantic raises a `ValidationError` with `"value should be greater than or equal to 0"`. The correct representation is `adj_type=DISCOUNT, amount_cents=500` (meaning: apply a $5.00 discount).

### 5.2 Validation: `OrderLifecycleStatus` rejects unknown strings

Because `OrderLifecycleStatus` is a `str, Enum`, Pydantic V2 will raise a `ValidationError` when deserialising an unknown value (e.g. `"pending_payment"` — which is the legacy `status` value, not a lifecycle status). This is intentional: the `status` field (legacy) and `lifecycle_status` field (enum-typed) must never be confused. Any code that reads a DDB item and populates `lifecycle_status` must guard against items that predate ORD-007 (where `lifecycle_status` may be absent or `None`).

### 5.3 Forward reference in `OrderTransitionResult`

`order: "OrderLifecycleOut"` is a string annotation. Because all six models are appended in a single contiguous block at end-of-file, Python resolves the annotation correctly when `OrderTransitionResult` is instantiated. If a future refactor moves `OrderLifecycleOut` to a different file, a `from __future__ import annotations` import at the top of that file and a `model_rebuild()` call suffice.

### 5.4 `ShipGroup.item_ids` DynamoDB representation

DynamoDB `SS` (String Set) attributes cannot be empty; an empty `List[str]` at the model level must be stored as an absent attribute (or a `List` type) in DynamoDB, not an empty `SS`. The ORD-009 service layer handles this translation: when `item_ids == []`, it stores the attribute as a DynamoDB `L` (List) type or omits it. The model layer is neutral — `List[str]` serialises/deserialises correctly with either DDB representation.

### 5.5 `OrderAdjustment.taxable` semantics

`taxable: bool = False` is a flag on the adjustment line itself, not on the underlying order item. Its purpose is to enable future tax calculation services to know whether a shipping adjustment or surcharge should itself be included in the tax base. It carries no enforcement logic in ORD-004. The default `False` is conservative.

### 5.6 `OrderLifecycleOut.metadata` field

`metadata: Dict[str, Any]` is a passthrough of the `metadata` dict written by `create_order` (`app/services/commerce_order_service.py:83`). It may contain `cart_id`, `checkout_session_id`, `idempotency_key`, `promo_code_id`, `discount_cents`, `original_total_cents` (from `shoppingcart.py:581–593`). These sub-fields are intentionally untyped at the model layer; structured access is the responsibility of the service that wrote them.

### 5.7 `OrderStatusHistoryEntry.from_status` as None for creation event

When ORD-007 writes the initial `HIST#` row for a newly-created order, `from_status` is `None` (no prior state). The model accepts this because `from_status: Optional[str] = None`. Consumers that display history should render `None` as `"—"` or `"(initial)"`.

### 5.8 `currency` field casing

The existing `commerce_order_service.py` writes `currency` from `self._currency(item)` which returns `.upper()` (`app/services/commerce_order_service.py:24`). `OrderAdjustment.currency` defaults to `"USD"` (uppercase). `OrderLifecycleOut.currency` defaults to `"USD"`. The platform has mixed casing historically (`currency: str = "usd"` in `ReturnOut` at `app/models.py:661`); for the lifecycle models, uppercase is used throughout to match the order service convention.

## 6. Feature Flag & Config

ORD-004 adds only Pydantic models. These classes exist unconditionally in the codebase after this PR — they are Python class definitions, not runtime behavior. There is no flag that hides a class definition.

The flag-gating is at the **usage site**: ORD-005 (service), ORD-007 (order creation hook), and ORD-008+ (adjustments/ship groups) all check `S.order_lifecycle_enabled` before exercising these models. With the flag off, no handler ever instantiates these models and no API response ever includes their fields.

| Flag (from ORD-002) | Env var | Default | Relevance to ORD-004 |
|---|---|---|---|
| `S.order_lifecycle_enabled` | `ORDER_LIFECYCLE_ENABLED` | `false` | Master gate; no model is serialised into a response until this is `true` |
| `S.order_lifecycle_auto_approve` | `ORDER_LIFECYCLE_AUTO_APPROVE` | `false` | Affects initial `lifecycle_status` written by ORD-007; not relevant to model shapes |
| `S.order_backorder_enabled` | `ORDER_BACKORDER_ENABLED` | `false` | Gates whether `BACKORDER` is a legal `target_status` in `OrderTransitionRequest`; the enum member exists regardless |

**No new settings are introduced by ORD-004.** The three flags are defined in ORD-002 (`app/core/settings.py:1131–1143` per ORD-002 spec).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity**: Pydantic model classes are pure Python with no dev/prod branching. The same class definition runs in both environments. There is no `if S.dev_mode` within any new model. Full parity by construction.

**Idempotency**: Models are stateless value objects. Instantiating `OrderTransitionRequest` twice with the same payload produces two equal objects; no side effects occur. Idempotency for the mutation path is in ORD-005 (`sha256(order_id|from|to|idempotency_key)[:16]` event_id derivation).

**Input validation**:
- `amount_cents: int = Field(..., ge=0)` — rejects negative values.
- `adj_type: OrderAdjustmentType` — rejects strings outside the enum.
- `lifecycle_status: Optional[OrderLifecycleStatus]` — rejects unknown status strings when present.
- `reason: str = Field(default="", max_length=500)` — rejects excessively long reason strings (DoS mitigation).
- `idempotency_key: Optional[str] = Field(default=None, max_length=128)` — length-bounded.

**No secrets or PII**: None of the new models carry authentication tokens, passwords, PII, or payment credentials. They are purely structural/financial data.

**Ownership enforcement**: Not applicable to model definitions. Enforcement is in the ORD-005 router layer: `GET /orders/{order_id}` checks `order["user_id"] == ctx["user_sub"]` unless `role >= ADMIN`.

## 8. Backward Compatibility & Migration

### 8.1 Zero change to existing serialisation

No existing model class is modified. All new classes are appended. The `app/models.py` import surface (`from app.models import ...`) is unchanged for existing importers; they import what they need and new symbols are invisible until explicitly imported.

### 8.2 `OrderLifecycleOut` does not break `create_order` callers

The existing `create_order` return value is a plain `dict` (`app/services/commerce_order_service.py:119`). Callers such as `shoppingcart.py:595` (`order_id = str(order.get("order_id") or "")`) read directly from the dict. `OrderLifecycleOut` is a **new** response model used only by the ORD-005 orders router, which re-reads the DDB record to populate the full field set — it does not replace the internal return dict. Existing callers are unaffected.

### 8.3 `status` field retention

`OrderLifecycleOut.status: str` keeps the legacy field. Any consumer expecting `response["status"] == "pending_payment"` will continue to receive it. The new `lifecycle_status` is additive alongside it, never replacing it.

### 8.4 `Optional` defaults for enriched collections

`adjustments`, `ship_groups`, `status_history` all default to `None`. A response serialised when the flag is off (or before ORD-007/ORD-008/ORD-009 are deployed) will carry `"adjustments": null, "ship_groups": null, "status_history": null` — or these fields are excluded if the router uses `response_model_exclude_none=True`. Either way, existing consumers that do not know about these fields ignore them.

### 8.5 No DynamoDB migration

ORD-004 adds no DDB tables or GSIs. The DDB migration (adding `sk` sort key, new GSIs) is ORD-003's responsibility.

## 10. Open Questions / Assumptions

1. **Assumption**: `checkout_session_id` is excluded from `OrderLifecycleOut` (it lives in `metadata`). If any storefront consumer constructs an `OrderLifecycleOut` from a `create_order` return dict and expects `checkout_session_id` as a top-level field, this PR breaks it. A grep of all `checkout_session_id` usages at time of ORD-004 implementation should confirm it is only read from the raw dict (`order.get("checkout_session_id")`), never from a typed model.

2. **Assumption**: `ShipGroup.ship_status` reuses `OrderLifecycleStatus` (the order-level enum) rather than defining a separate `ShipGroupStatus` enum. This covers the fulfillment arc (`ALLOCATED → PICKING → PACKED → SHIPPED`) and `CANCELLED`. If ORD-009 needs a richer set of per-ship-group sub-statuses (e.g. `LABEL_PRINTED`, `OUT_FOR_DELIVERY`), a separate enum should be introduced at that point. This assumption must be confirmed with ORD-009.

3. **Assumption**: `OrderAdjustment.amount_cents` is always non-negative. If the billing team requires signed amounts for credit memos or partial reversals, the constraint `ge=0` must be relaxed (or a separate `CreditMemo` model added). Confirm with ORD-008 (adjustments service).

4. **Open question**: Should `OrderLifecycleOut` extend `UnifiedCheckoutSessionOut` (`app/models.py:900`) by inheritance, or remain a standalone model? Inheritance would couple the lifecycle response to the checkout session response; standalone is safer. This spec chooses standalone.

5. **Assumption**: `OrderAdjustmentType` is a separate `str, Enum` class (not a nested enum inside `OrderAdjustment`). This is consistent with `PmIdeaStatus` / `PmIdeaPriority` / `PmIdeaCategory` being top-level classes. Some IDEs and OpenAPI generators handle nested enums poorly.

6. **Assumption**: The `source_rule_ref` field in `OrderAdjustment` is an opaque string, not a typed FK to a specific model. If ORD-008 adds structured rule references (e.g. a `PromoRule` model), `source_rule_ref` can be augmented to carry the rule type alongside the ID. For now, the string is sufficient for audit purposes.

7. **Open question**: `OrderLifecycleOut.metadata` is `Dict[str, Any]`. Should it be `Optional[Dict[str, Any]] = None` to match the existing `app/models.py:456` convention, or `Dict[str, Any] = Field(default_factory=dict)` (non-nullable)? This spec uses `default_factory=dict` to ensure a dict is always serialised (never `null`), consistent with `commerce_order_service.py:83` which always writes `metadata=dict(...)`.

8. **Assumption**: All timestamps in new models are `int` (Unix seconds from `now_ts()`), not ISO strings. `OrderLifecycleOut` retains the legacy ISO-string `created_at`/`updated_at` for backward compat, but all new timestamp fields (`updated_ts`, `ship_ts`, `ts` in history entries) are integers.
