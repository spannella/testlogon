# PRD-012 — Product-level price components

**Type:** Feature | **Priority:** P1 | **Estimate:** 4 days
**Milestone:** 5 — Price Components

---

## 1. Summary & Goal

PRD-012 implements the service layer for OFBiz-style `ProductPrice` rows: per-product, per-type, date-windowed price components stored on `T.product_depth` and queried via the `ByItemPrice` GSI. The three public functions — `set_price_component`, `list_price_components`, and `resolve_effective_price` — enrich the existing scalar `price_cents` field without touching the charge path at all. Cart, checkout, and the billing ledger are byte-for-byte unchanged whether the flag is on or off; `resolve_effective_price` is a pure read that returns the scalar fallback when no component rows exist.

The service is the read/write core; HTTP endpoints live in the follow-on ticket PRD-013. This ticket ships `app/services/product_price_components.py` only.

## 3. Data Model

All price-component rows live on `T.product_depth`. No change to `T.catalog`, `T.shopping_cart`, `T.billing`, or any other existing table.

### 3.1 Price-component row schema

| Attribute | Type | Value / Notes |
|---|---|---|
| `PK` | S | `ITEM#{item_id}` |
| `SK` | S | `PRICE#{price_type}#{effective_at:010d}` — zero-padded for lexicographic order |
| `entity` | S | `"price_component"` — discriminator |
| `price_component_id` | S | `sha256(item_id|price_type|effective_at)[:16]` |
| `item_id` | S | denormalized for projections |
| `price_type` | S | one of `LIST`, `DEFAULT`, `PROMO`, `COMPETITIVE`, `MINIMUM`, `AVERAGE_COST` |
| `amount_cents` | N | `ge=0, le=10_000_000_00` |
| `currency` | S | ISO 4217, e.g. `"USD"` |
| `effective_at` | N | Unix timestamp integer (`ge=0`); the open-left edge of the window |
| `expires_at` | N | Unix timestamp integer (`ge=0`) or absent — `None` = open-ended |
| `creator_id` | S | `user_sub` of the owner at write time |
| `created_at` | N | Unix int (`now_ts()`) at first write |
| `updated_at` | N | Unix int (`now_ts()`) at every write |
| `GSI_PRICE_PK` | S | `"PRICE#{item_id}#{price_type}"` — GSI partition |
| `GSI_PRICE_SK` | N | same integer as `effective_at` — GSI sort key |

**Why the SK embeds a zero-padded `effective_at`**: A SK-prefix query on the main table (`SK begins_with "PRICE#{type}#"`) returns rows in lexicographic order. Zero-padding to 10 digits (`{effective_at:010d}`) keeps the numeric ordering consistent with lexicographic ordering up to Unix timestamp `9999999999` (year 2286). The GSI uses the raw integer for range queries.

### 3.2 GSI access pattern (`ByItemPrice`)

Declared in `scripts/local-ddb-init.py` by PRD-002 (no change needed here):

```python
{"index_name": "ByItemPrice", "partition_key": "GSI_PRICE_PK", "sort_key": "GSI_PRICE_SK"},
```

with `attr_types={"GSI_PRICE_SK": "N"}` in the same `TableDef`.

**`resolve_effective_price` query**: Scan `GSI_PRICE_PK = "PRICE#{item_id}#{price_type}"` with `GSI_PRICE_SK <= as_of`, `ScanIndexForward=False`, `Limit=1`. This retrieves the most-recently-effective component for `(item_id, price_type)` as of `as_of`. A second condition — `expires_at IS NULL OR expires_at >= as_of` — is applied as a `FilterExpression`. Because DynamoDB applies filters after fetching the page, this fetch uses `Limit=20` (not 1) to allow filter discards; the first non-expired row wins.

**`list_price_components` query**: Scan `GSI_PRICE_PK = "PRICE#{item_id}#{price_type}"`, `ScanIndexForward=False` (newest first), no limit by default (all components for that type). When `price_type=None`, the service issues one query per defined type. The `is_active` field is computed in Python after the fetch.

### 3.3 No new `scripts/local-ddb-init.py` changes

The `ByItemPrice` GSI and `"GSI_PRICE_SK": "N"` in `attr_types` are fully established by PRD-002. PRD-012 introduces no new table definitions or GSIs.

## 4. API / Service Design

### 4.1 Module: `app/services/product_price_components.py`

```python
"""
OFBiz-style product price components (PRD-012).

Stores per-product, per-type, date-windowed price rows on T.product_depth using
the ByItemPrice GSI.  This is a READ-ONLY ENRICHMENT layer: it never calls
new_ledger_entry, refund_payment, or any payment SDK.  Cart/checkout pricing
continues to use the scalar price_cents from T.catalog unchanged.

Public surface:
  set_price_component(item_id, creator_id, body) -> ProductPriceComponentOut
  list_price_components(item_id, price_type=None) -> List[ProductPriceComponentOut]
  resolve_effective_price(item_id, as_of, price_type="DEFAULT") -> int
"""

import hashlib
from typing import List, Optional

from boto3.dynamodb.conditions import Key
from fastapi import HTTPException

from app.core.settings import S
from app.core.tables import T
from app.core.time import now_ts
from app.models import PriceTypeEnum, ProductPriceComponentIn, ProductPriceComponentOut

_ALL_PRICE_TYPES = [e.value for e in PriceTypeEnum]
_FETCH_WINDOW = 20  # rows fetched per GSI page for resolve (filter may discard some)
```

#### 4.1.1 Flag guard

```python
def _require_enabled() -> None:
    if not getattr(S, "product_depth_enabled", False):
        raise HTTPException(status_code=404, detail="Product depth is not enabled.")
    if not getattr(S, "product_depth_price_components_enabled", True):
        raise HTTPException(status_code=404, detail="Price components are not enabled.")
```

Called by `set_price_component` and `list_price_components` (write/read). NOT called by `resolve_effective_price` — that function is a pure fallback helper safe to call unconditionally.

#### 4.1.2 `_make_component_id`

```python
def _make_component_id(item_id: str, price_type: str, effective_at: int) -> str:
    key = f"{item_id}|{price_type}|{effective_at}".encode()
    return hashlib.sha256(key).hexdigest()[:16]
```

Deterministic: same inputs always yield the same 16-char hex id. Idempotent upserts on `set_price_component` produce the same `price_component_id`.

#### 4.1.3 `_row_to_out`

```python
def _row_to_out(row: dict, as_of: Optional[int] = None) -> ProductPriceComponentOut:
    now = as_of if as_of is not None else now_ts()
    eff = int(row["effective_at"])
    exp = int(row["expires_at"]) if row.get("expires_at") is not None else None
    active = eff <= now and (exp is None or now <= exp)
    return ProductPriceComponentOut(
        price_component_id=row["price_component_id"],
        item_id=row["item_id"],
        price_type=row["price_type"],
        amount_cents=int(row["amount_cents"]),
        currency=row.get("currency", "USD"),
        effective_at=eff,
        expires_at=exp,
        is_active=active,
    )
```

#### 4.1.4 `set_price_component`

```python
def set_price_component(
    item_id: str,
    creator_id: str,
    body: ProductPriceComponentIn,
) -> ProductPriceComponentOut:
    """
    Upsert a single price component row.

    Idempotent: (item_id, price_type, effective_at) uniquely identifies the row.
    Calling twice with the same triple updates amount_cents / expires_at /
    updated_at but never creates a second row (same price_component_id, same PK/SK).

    Does NOT modify T.catalog.  Does NOT write a ledger entry.
    """
    _require_enabled()

    eff = int(body.effective_at)
    pt = body.price_type.value if hasattr(body.price_type, "value") else str(body.price_type)

    if body.expires_at is not None and body.expires_at < eff:
        raise HTTPException(
            status_code=422,
            detail="expires_at must be >= effective_at.",
        )

    pc_id = _make_component_id(item_id, pt, eff)
    now = now_ts()
    row = {
        "PK": f"ITEM#{item_id}",
        "SK": f"PRICE#{pt}#{eff:010d}",
        "entity": "price_component",
        "price_component_id": pc_id,
        "item_id": item_id,
        "price_type": pt,
        "amount_cents": int(body.amount_cents),
        "currency": body.currency,
        "effective_at": eff,
        "expires_at": body.expires_at,          # stored as int or omitted (None → not written)
        "creator_id": creator_id,
        "created_at": now,
        "updated_at": now,
        "GSI_PRICE_PK": f"PRICE#{item_id}#{pt}",
        "GSI_PRICE_SK": eff,                    # numeric for ByItemPrice GSI
    }
    # Remove None values so DynamoDB doesn't store NULL attributes for GSI keys
    row = {k: v for k, v in row.items() if v is not None}

    T.product_depth.put_item(Item=row)
    return _row_to_out(row)
```

**Idempotency**: `put_item` without a condition expression is an unconditional upsert (last-write-wins). Same `(item_id, price_type, effective_at)` → same `PK/SK` → overwrites the previous row. `created_at` is technically overwritten on re-upsert; if first-write semantics are needed for `created_at`, a conditional `attribute_not_exists(PK) AND attribute_not_exists(SK)` can be added with a separate `update_item` fallback. Assumption A1 (see §10) keeps the simpler unconditional upsert.

#### 4.1.5 `list_price_components`

```python
def list_price_components(
    item_id: str,
    price_type: Optional[str] = None,
) -> List[ProductPriceComponentOut]:
    """
    Return all price components for an item, optionally filtered by price_type.

    When price_type is None, queries each type in _ALL_PRICE_TYPES and merges
    results.  Rows are returned newest-effective-at first within each type.

    Respects _require_enabled().  Returns [] when both flag and components absent.
    """
    _require_enabled()

    types_to_query = [price_type] if price_type else _ALL_PRICE_TYPES
    now = now_ts()
    results: List[ProductPriceComponentOut] = []

    for pt in types_to_query:
        resp = T.product_depth.query(
            IndexName="ByItemPrice",
            KeyConditionExpression=Key("GSI_PRICE_PK").eq(f"PRICE#{item_id}#{pt}"),
            ScanIndexForward=False,
        )
        for row in resp.get("Items", []):
            results.append(_row_to_out(row, as_of=now))

    return results
```

**Why loop per type rather than a single query**: The `ByItemPrice` GSI partition key embeds `price_type` (`PRICE#{item_id}#{pt}`). Fetching all types for an item requires either a scan (expensive) or one GSI query per type (at most 6 queries for 6 types). For the typical use case (1–3 price components per item) this is preferable to a scan.

**Pagination**: A single `query` call fetches up to 1 MB. For typical price-component volumes (tens of rows per type) this is sufficient without pagination. If `LastEvaluatedKey` is present (very large historical price log), the function paginates transparently by looping via `LastEvaluatedKey` until exhausted (caller receives all rows). The loop is added inside the per-type block.

#### 4.1.6 `resolve_effective_price`

```python
def resolve_effective_price(
    item_id: str,
    as_of: int,
    price_type: str = "DEFAULT",
) -> int:
    """
    Return the active price in cents for (item_id, price_type) as of as_of.

    Algorithm:
      1. Query ByItemPrice GSI: GSI_PRICE_PK = "PRICE#{item_id}#{price_type}",
         GSI_PRICE_SK <= as_of, ScanIndexForward=False, Limit=_FETCH_WINDOW.
      2. For each row (newest-effective first), check expires_at:
         accept the first row where expires_at IS NULL OR expires_at >= as_of.
      3. If no active component found AND price_type == "DEFAULT":
         fall back to T.catalog scalar price_cents (via ByItemId GSI on T.catalog).
      4. If no active component and price_type != "DEFAULT": return 0 (no floor/promo active).

    This function DOES NOT call _require_enabled(): it is safe to call from
    cart/checkout regardless of the product_depth flag state.  When flags are
    off and no rows exist, step 3/4 always applies.

    Never raises.  Returns 0 as a last resort.
    """
    # Step 1: GSI range query
    resp = T.product_depth.query(
        IndexName="ByItemPrice",
        KeyConditionExpression=(
            Key("GSI_PRICE_PK").eq(f"PRICE#{item_id}#{price_type}")
            & Key("GSI_PRICE_SK").lte(as_of)
        ),
        ScanIndexForward=False,
        Limit=_FETCH_WINDOW,
    )
    # Step 2: find first non-expired row
    for row in resp.get("Items", []):
        exp = row.get("expires_at")
        if exp is None or int(exp) >= as_of:
            return int(row["amount_cents"])

    # Step 3: scalar fallback for DEFAULT
    if price_type == "DEFAULT":
        return _scalar_price_fallback(item_id)

    return 0


def _scalar_price_fallback(item_id: str) -> int:
    """
    Read the scalar price_cents from T.catalog via the ByItemId GSI.
    Returns 0 if the item does not exist or price_cents is absent.
    """
    try:
        resp = T.catalog.query(
            IndexName="ByItemId",
            KeyConditionExpression=Key("item_id").eq(item_id),
            FilterExpression="entity = :ent",
            ExpressionAttributeValues={":ent": "item"},
            Limit=1,
        )
        items = resp.get("Items", [])
        if items:
            return int(items[0].get("price_cents", 0))
    except Exception:
        pass
    return 0
```

**Why `resolve_effective_price` skips the flag guard**: Cart/checkout code may call this in future as a non-breaking enrichment. Requiring the flag would mean the cart 404s when the feature is disabled. The function returns the scalar fallback when no rows exist — which is always the case when the flag is off — so it is silently a no-op when depth is disabled.

**`_FETCH_WINDOW = 20`**: DynamoDB fetches 20 rows before applying `FilterExpression` for the `expires_at` check. In practice price histories rarely exceed 5–10 rows per type; 20 covers edge cases without excessive over-fetch.

## 5. Detailed Behavior & Edge Cases

### 5.1 Date window resolution

A product has two DEFAULT price components:
- `effective_at=1_000_000, expires_at=1_100_000, amount_cents=999`
- `effective_at=1_200_000, expires_at=None (open-ended), amount_cents=1299`

`resolve_effective_price(item_id, as_of=1_050_000, "DEFAULT")` → 999 (first component active).
`resolve_effective_price(item_id, as_of=1_150_000, "DEFAULT")` → 0 (gap period) → falls back to scalar `price_cents` since `price_type == "DEFAULT"`.
`resolve_effective_price(item_id, as_of=1_300_000, "DEFAULT")` → 1299 (second component active).

The GSI query `GSI_PRICE_SK <= as_of` returns rows with `effective_at <= as_of` only (no future-dated rows). The `expires_at` filter is applied in Python after the fetch.

### 5.2 Multiple rows same effective_at, same type

Since the SK is `PRICE#{type}#{effective_at:010d}`, two `set_price_component` calls with the same `(item_id, price_type, effective_at)` produce the same SK → the second write is an unconditional upsert that silently replaces the first. No duplicate rows are created. Callers who need to maintain a history must use different `effective_at` values.

### 5.3 `expires_at` before `effective_at`

Rejected at service entry with `HTTP 422 "expires_at must be >= effective_at."`. This prevents logically impossible windows (a price that expires before it takes effect).

### 5.4 No price components exist (`resolve_effective_price` fallback)

`resolve_effective_price("item_xyz", as_of=now_ts(), "DEFAULT")` queries the GSI and gets 0 rows. Falls back to `_scalar_price_fallback("item_xyz")`, which queries the `ByItemId` GSI on `T.catalog`. If the item exists, returns its `price_cents`. If the item does not exist (stale reference), returns `0`. Never raises.

This is the critical back-compat guarantee stated in the acceptance criteria: with no depth rows, the cart's existing `int(item.get("price_cents", 0))` path (`app/services/shoppingcart.py:394`) and `resolve_effective_price` both return the same value.

### 5.5 `price_type` not in enum

`set_price_component` accepts `price_type` via `ProductPriceComponentIn.price_type: PriceTypeEnum` — Pydantic rejects any value outside the enum with a 422. `list_price_components` accepts `price_type: Optional[str]`; an unknown string produces a GSI query that returns 0 rows (no error). `resolve_effective_price` accepts `price_type: str`; an unknown string produces 0 rows → returns `0` (non-DEFAULT types have no scalar fallback).

### 5.6 Currency mismatch

`set_price_component` stores the `currency` specified in `body.currency`. No validation is performed against the item's scalar `currency` field on `T.catalog`. It is the caller's responsibility to provide a consistent currency. The `list_price_components` response surfaces mixed currencies in the list so the API consumer can detect mismatches. A future version may add a validation step; for now, omitting it keeps the service simpler and avoids a catalog read on every write.

### 5.7 `list_price_components` across all types — query cost

Querying all 6 types issues at most 6 GSI queries. Each query on `T.product_depth` reads `GSI_PRICE_PK = "PRICE#{item_id}#{pt}"`. For the typical case of a new product with no history rows this costs 6 × (1 empty query). For a heavily-priced product with 50 rows per type, 6 × 50 = 300 rows; all returned in memory. If future performance profiling shows this is a bottleneck, a secondary GSI on `ITEM#{item_id}` partitioned over all `PRICE#*` rows can be added without a breaking change.

### 5.8 AVERAGE_COST — not surfaced to storefront

`AVERAGE_COST` is a COGS reference for internal cost accounting. It is stored the same way as other types. The PRD-013 `GET /items/{id}/effective-price?price_type=AVERAGE_COST` endpoint is owner-only and not included in any public catalog response. Cart/checkout never call `resolve_effective_price(price_type="AVERAGE_COST")`.

### 5.9 `set_price_component` with `effective_at = 0` (epoch)

Valid. `ge=0` allows `effective_at=0` (Unix epoch). This models a price that has been effective since the beginning of time — useful for seeding historical data. No special treatment.

### 5.10 Concurrent writes to the same (item_id, price_type, effective_at)

Two concurrent `set_price_component` calls with identical inputs race on `put_item`. Both succeed; the last writer wins on `amount_cents` / `expires_at` / `updated_at`. The `price_component_id` is deterministic so it is the same regardless of which write lands last. No DDB transaction or conditional expression is needed — idempotency at the ID level is sufficient.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

All reads and writes go through `T.product_depth` (moto-backed DynamoDB Local in dev, real DynamoDB in prod) and `T.catalog` (same). There is no `S.dev_mode` branch in `app/services/product_price_components.py`. The `ByItemPrice` GSI and `ByItemId` GSI queries are identical SQL-free DDB queries in both environments. This satisfies SECOPS-007.

`_scalar_price_fallback` uses `T.catalog.query(IndexName="ByItemId", ...)`, the same query already implemented by `app/routers/catalog.py:709–714` (`_find_item_by_id`).  <!-- VERIFIED: _find_item_by_id at :702, query at :709-714, IndexName="ByItemId", FilterExpression="entity = :ent" --> No new AWS service or mock path is introduced.

### Idempotency

`set_price_component` is an unconditional `put_item` upsert. The `price_component_id` is deterministic from `sha256(item_id|price_type|effective_at)[:16]`. Submitting the same body twice:
- writes the same `PK/SK` row
- returns the same `price_component_id`
- `created_at` is overwritten to the second call's timestamp (see assumption A1)

`list_price_components` and `resolve_effective_price` are pure reads with no side effects.

### Security

**No ownership enforcement in the service layer**: `set_price_component` accepts a `creator_id` parameter but does not validate it against the item's `creator_id` in `T.catalog`. Ownership enforcement is the router's responsibility (PRD-013 will use `_require_item_owner` from `app/routers/catalog.py`, introduced by PRD-008 — `_require_item_owner` does NOT currently exist in the live codebase; consistent with `_require_category_owner` at `app/routers/catalog.py:247`).  <!-- VERIFIED: _require_category_owner at :247 exists; _require_item_owner is PRD-008 planned, not yet present --> The service is a dumb write layer.

**No money paths**: `set_price_component` writes only to `T.product_depth`. It never calls `new_ledger_entry` (`app/services/billing_shared.py:224`), `refund_payment` (`app/routers/billing.py:1287`), or any payment-provider SDK. `resolve_effective_price` returns an `int` — it is the caller's responsibility to pass this value into the charge path (via cart → `add_catalog_item` at `app/services/shoppingcart.py:370`, which reads `price_cents` at `:394`), which PRD-013 or a future caller may do.  <!-- CORRECTED: function is named `add_catalog_item` (not `add_catalog_item_to_cart`), defined at :370 not :390; the price_cents read is at :394 -->

**`AVERAGE_COST` visibility**: The service stores and returns it on `list_price_components`. The PRD-013 router gates this type on owner-only access. The service does not enforce visibility itself.

**Input bounds**: `amount_cents ge=0, le=10_000_000_00` matches the existing `CatalogItemCreateIn.price_cents` bound at `app/models.py:542`.  <!-- VERIFIED: Field(ge=0, le=10_000_000_00) at models.py:542 --> `effective_at ge=0, expires_at ge=0` prevent negative timestamps. All enforced by Pydantic before the service sees the values.

## 10. Open Questions / Assumptions

**A1. `created_at` on upsert.** The spec uses an unconditional `put_item`. This means `created_at` is overwritten on every upsert. If immutable `created_at` (first-write-wins) is needed, use a conditional `put_item(ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)")` with a fallback `update_item` to update only mutable fields. This spec assumes last-write-wins is acceptable; the simpler path is preferred unless auditors require an immutable creation timestamp.

**A2. Currency validation against scalar item currency.** The spec does not validate `body.currency` against `T.catalog` item currency on write. This trades a catalog round-trip for simplicity. If currency consistency is a hard requirement (e.g. for multi-currency storefronts), add `_scalar_price_fallback`-style catalog read in `set_price_component` and reject mismatches with `HTTP 422`.

**A3. `list_price_components` pagination for large histories.** The spec notes that `LastEvaluatedKey` pagination should be added for large histories. For the current use case (< 100 rows per item per type) a single unbounded query is safe. If price-component history log use cases emerge (e.g. storing a year of daily promotional prices = 365 rows), add `Limit` + `next_token` cursor to `list_price_components`. Assumption: single-page response is sufficient at launch.

**A4. `resolve_effective_price` called from cart.** The spec explicitly keeps `resolve_effective_price` flag-independent so it can be called from `app/services/shoppingcart.py` in a future ticket (e.g. "use component price if available, fall back to scalar"). That wiring is NOT in PRD-012 or PRD-013 — the cart continues to use `item.get("price_cents")` exclusively. Assumption: the cart integration is a follow-on ticket (not in scope for this milestone).

**A5. Thread safety of `_scalar_price_fallback`.** The function is a pure read with no shared mutable state. Concurrent calls are safe. The `try/except` around the DDB query ensures any transient DDB error returns `0` rather than propagating, consistent with the "never raises" contract.

**A6. GSI `_FETCH_WINDOW=20` for `resolve_effective_price`.** The 20-row window assumes at most 19 expired rows precede the active row for a given `(item_id, price_type)` at any `as_of`. If price histories grow longer, increase this constant. A follow-up can page through the GSI if the first page yields no active component.
