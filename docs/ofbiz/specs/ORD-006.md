# ORD-006 — Order status-history (append-only audit trail)

**Type:** Feature | **Priority:** P0 | **Estimate:** 2 days
**Milestone:** 2 — State machine & audit trail

---

## 1. Summary & Goal

ORD-006 adds the append-only HIST row writes and corresponding `list_status_history` read helper that the ORD-005 state-machine service calls after every successful lifecycle transition. It also wires the `audit_event("order_status_changed", ...)` call that the ORD-001 design requires (`docs/ofbiz/specs/ORD-001.md:216`).

The deliverables are two additions to `app/services/order_lifecycle.py` (the service created by ORD-005):

1. **`_append_history_row`** — internal helper that writes one `HIST#{ts:020d}#{event_id}` item to `T.orders` after a confirmed header CAS update. Write is best-effort: failure is logged and never rolls back the preceding state change.
2. **`list_status_history`** — public read function that queries all `HIST#` rows under an `order_id`, sorts newest-first (DDB native lexicographic order on the SK), and deserialises them into `OrderStatusHistoryEntry` dicts.

In addition, the initial `created` HIST row (ORD-007 concern) must be seeded by the same `_append_history_row` helper when `create_order` stamps `lifecycle_status="created"` with the flag on. ORD-006 provides the helper; ORD-007 calls it.

All behaviour is gated behind `S.order_lifecycle_enabled`. With the flag off the helpers exist in the module but are never called; `T.orders` receives zero new writes.

## 3. Data Model

ORD-006 introduces **no new DynamoDB tables or GSIs**. All writes go into the existing `T.orders` table under the `HIST#` SK prefix established by ORD-003.

### 3.1 HIST row shape

Each history row lives in the same DynamoDB table as the order header (`T.orders`, PK `order_id`). It uses the SK prefix `HIST#` to partition it from header rows (`ORDER`) and future ship-group (`SHIPGRP#`) and adjustment (`ADJ#`) rows.

| Attribute | Type | Value / Notes |
|-----------|------|---------------|
| `order_id` | S | Partition key — same `order_id` as the header |
| `sk` | S | `HIST#{ts:020d}#{event_id}` — sort key; zero-padded ts gives lexicographic chronological ordering |
| `event_id` | S | 16-char hex prefix of `sha256(order_id\|from_status\|to_status\|idempotency_key_or_empty)` |
| `from_status` | S | Previous `lifecycle_status` value; absent (or `None`) for the initial `created` event |
| `to_status` | S | New `lifecycle_status` value |
| `actor` | S | `user_sub` of the caller (user or admin) |
| `reason` | S | Free-text reason from `OrderTransitionRequest.reason`; empty string when not provided |
| `ts` | N | `now_ts()` at the time of the successful header update (integer Unix seconds) |

The SK template `HIST#{ts:020d}#{event_id}` uses 20 decimal digits for the timestamp (sufficient until year 33658), matching the SK width discipline from `instance_monitoring.py:442` (`{ts:010d}` there; order history uses a wider field because order history may outlive compute instances). The `event_id` suffix disambiguates the (astronomically unlikely) case where two transitions complete within the same second for the same order.

### 3.2 Numeric attribute: `ts`

`ts` is stored as DynamoDB type `N` (integer). It is NOT a GSI sort key on the `orders` table — the HIST rows are queried by prefix scan on the base table SK (`begins_with("HIST#")`) and returned in native DDB order (ascending by SK string). Since the 20-digit zero-padded decimal timestamp is lexicographically ordered, `ScanIndexForward=False` on the base table delivers newest-first results without a separate GSI.

No `attr_types` declaration is needed for `ts` in `scripts/local-ddb-init.py` because `ts` is not a primary key or GSI key — it is a plain attribute on the item. The ORD-003 `TableDef` declaration already handles the two numeric GSI keys (`updated_ts` and `ship_ts`) that do require `attr_types`.

### 3.3 HIST row vs ORDER header — no conflict

DynamoDB single-table design with a composite PK allows multiple row types to share the same partition key. The header is always `sk="ORDER"` (a literal that cannot match `begins_with("HIST#")`), so header and history rows coexist without collision.

#### 4.1.3 `history_row_exists` — idempotency probe (owns this function per ESCALATIONS row 27)

```python
def history_row_exists(order_id: str, event_id: str) -> bool:
    """Return True if a HIST row with the given event_id already exists for order_id.

    Used by transition_order (ORD-005 §5.3) to detect a replay before issuing
    the conditional update_item, enabling a clean idempotency fast-path.
    Queries the base table by SK prefix and scans for a matching event_id suffix.

            KeyConditionExpression=Key("order_id").eq(order_id)
            & Key("sk").begins_with(f"HIST#"),
            FilterExpression="event_id = :eid",

            Limit=1,
```

#### 4.1.4 `_append_history_row` — best-effort HIST put_item

```python
def _append_history_row(
    order_id: str,
    *,
    from_status: Optional[str],
    to_status: str,
    actor: str,
    reason: str,
    event_id: str,
    ts: int,
) -> None:
    """Write one HIST#{ts:020d}#{event_id} item to T.orders.

    This is a best-effort write. A failure here must NEVER roll back the
    preceding header CAS update that already committed the state change.
    Failure is logged at WARNING level and swallowed.

    The caller (transition_order) always provides the ts and event_id that
    were used for the CAS update, ensuring the HIST row is consistent with
    what the header reflects.
    """
    item: Dict[str, Any] = {
        "order_id": order_id,
        "sk": f"HIST#{ts:020d}#{event_id}",
        "event_id": event_id,
        "to_status": to_status,
        "actor": actor,
        "reason": reason,
        "ts": ts,
    }
    if from_status is not None:
        item["from_status"] = from_status
    # from_status is absent (not stored as None) for the initial "created" event.
    # DynamoDB cannot store None; omitting the attribute is the correct representation.
    try:
        T.orders.put_item(Item=item)
    except Exception:
        logger.warning(
            "order_hist_write_failed order_id=%s event_id=%s from=%s to=%s",
            order_id, event_id, from_status, to_status,
            exc_info=True,
        )
```

**Why `from_status` is omitted rather than stored as `None`**: DynamoDB rejects `None` attribute values. Storing an absent attribute is the correct approach; `list_status_history` reads it back with `.get("from_status")` which returns `None` for missing keys.

**Why `ts` is passed in by the caller**: The caller (`transition_order`) already called `now_ts()` to stamp `updated_ts` on the header. Reusing the same `ts` keeps the header's `updated_ts` and the HIST row's `ts` in sync. A second `now_ts()` call inside `_append_history_row` could produce a slightly later timestamp and create a confusing mismatch.

#### 4.1.6 `list_status_history` — public read helper

```python
def list_status_history(
    order_id: str,
    *,
    limit: int = 100,
) -> List[Dict[str, Any]]:
    """Return status-history entries for an order, newest-first.

    Queries the HIST# SK prefix on T.orders with ScanIndexForward=False
    so DynamoDB returns items in descending SK (= descending ts) order.
    Each item is mapped to an OrderStatusHistoryEntry-compatible dict.

    The caller must verify order ownership before calling this function.
    """
    from app.models import OrderStatusHistoryEntry

    eff_limit = max(1, min(int(limit), 500))
    resp = T.orders.query(
        KeyConditionExpression=Key("order_id").eq(order_id)
        & Key("sk").begins_with("HIST#"),
        ScanIndexForward=False,
        Limit=eff_limit,
    )
    entries = []
    for raw in resp.get("Items", []):
        entry = OrderStatusHistoryEntry(
            event_id=raw.get("event_id", ""),
            from_status=raw.get("from_status"),        # None if absent
            to_status=raw.get("to_status", ""),
            actor=raw.get("actor", ""),
            reason=raw.get("reason", ""),
            ts=int(raw.get("ts", 0)),
        )
        entries.append(entry.model_dump())
    return entries
```

**Pagination note**: A `Limit=eff_limit` cap (max 500) is imposed. Orders rarely exceed a handful of transitions; the 500-item cap protects against any pathological accumulation. For the current ticket, single-page response is sufficient. If pagination is needed later, `LastEvaluatedKey` can be wired into a cursor via `app/core/cursor.py`.

### 4.2 Router endpoint `GET /ui/orders/{order_id}/history`

This endpoint is defined in the ORD-005 router (`app/routers/orders.py`) which mounts at `/ui/orders`. ORD-006 implements the service function that powers it.

```python
@router.get("/orders/{order_id}/history")
async def get_order_history(
    order_id: str,
    ctx: dict = Depends(require_ui_session),
) -> dict:
    if not S.order_lifecycle_enabled:
        raise HTTPException(status_code=404, detail="Order lifecycle not enabled")
    header = get_order_header(order_id)
    if header is None:
        raise HTTPException(status_code=404, detail="Order not found")
    if header.get("user_id") != ctx["user_sub"] and ctx.get("role") not in (Role.ADMIN, Role.ROOT):
        raise HTTPException(status_code=403, detail="Forbidden")
    entries = list_status_history(order_id)
    return {"order_id": order_id, "history": entries, "count": len(entries)}
```

Auth: `require_ui_session` (`app/auth/deps.py`). Ownership: `header["user_id"] == ctx["user_sub"]` unless ADMIN/ROOT. No CSRF check needed for GET.

## 5. Detailed Behavior & Edge Cases

### 5.1 Ordering guarantee: header CAS first, HIST second

The ORD-001 spec (`docs/ofbiz/specs/ORD-001.md:215`) states: "Append HIST row — best-effort (failure is logged, not raised)." This means:

- If the header CAS succeeds but `_append_history_row` fails (e.g. transient DDB throttle), the order is in the new state but has no HIST row for that transition. This is acceptable: the status change is durable; the history row is an audit convenience.
- If the header CAS fails (concurrent transition), `_append_history_row` is never called. No spurious HIST row is written.
- There is no DynamoDB transaction wrapping both writes, consistent with the platform's best-effort audit convention (see `ssh_key_manager.py:29–42`, `instance_monitoring.py:450–460`).

### 5.2 `from_status` on the initial `created` event

When ORD-007 calls `_append_history_row` for the initial event at order creation, it passes `from_status=None`. The helper omits the `from_status` attribute from the DDB item entirely. `list_status_history` deserialises it as `None` via `.get("from_status")`. The `OrderStatusHistoryEntry` model accepts `Optional[str] = None` for this field (ORD-004, Section 4.3). API consumers should render `None` as `"—"` or `"(initial)"`.

### 5.3 Idempotency via deterministic `event_id`

The `event_id = sha256(order_id|from|to|idempotency_key_or_empty)[:16]` derivation (ORD-005 step 4) means that a retried call with the same `idempotency_key` produces the same `event_id`. The SK `HIST#{ts:020d}#{event_id}` includes the `event_id`, so if the `put_item` were retried it would write to the same SK — a no-op overwrite of the identical item. However, in practice the conditional header update fails on replay (the order is already in `target_status`), so `_append_history_row` is never called on a true replay. This is belt-and-suspenders protection.

### 5.4 Actor value for system-generated transitions

When `transition_order` is called by an automated path (e.g. auto-approve on payment confirmation in ORD-007), the `actor` argument is the user's `user_sub` (for a user-initiated payment) or a literal like `"system_auto_approve"` (for a purely automated trigger). The HIST row records whatever `actor` string is passed. There is no enum constraint on `actor`; it is an opaque string.

### 5.5 `ts` field and DynamoDB Decimal

`now_ts()` returns a Python `int` (`app/core/time.py:2`). DynamoDB boto3 stores integers as `Decimal` on read-back. `list_status_history` explicitly casts `int(raw.get("ts", 0))` to handle both `int` and `Decimal` values, consistent with the `@model_validator(mode="before")` Decimal coercion in `MessageEncryptionEnvelope` (referenced in project memory).

### 5.6 `list_status_history` does not verify order ownership

`list_status_history` is a pure DDB read function. Ownership enforcement is the router's responsibility (as it is throughout the platform — services do not enforce auth, routers do). Callers that invoke `list_status_history` directly in tests do not need to set up auth context.

### 5.7 `ScanIndexForward=False` with `begins_with` works correctly in moto

moto's DynamoDB implementation correctly handles `begins_with` key conditions combined with `ScanIndexForward=False`. The SK prefix `HIST#` collates lexicographically below all numeric chars, so all HIST rows for an order sort before `ORDER` in ascending order and after in descending order — the `begins_with("HIST#")` condition isolates them regardless of `ScanIndexForward`.

### 5.8 Empty history for orders created before flag was on

Orders created when `ORDER_LIFECYCLE_ENABLED` was off have no `lifecycle_status` field and no `HIST#` rows. `list_status_history` returns an empty list. The router returns `{"history": [], "count": 0}`. The `get_order_header` call that precedes the history query will find the header at `sk="ORDER"` (written with `sk="ORDER"` by ORD-003-updated `commerce_order_service`), so a 404 is not returned for legacy orders — they just have no history.

### 5.9 `reason` field — empty string vs absent

The `reason` attribute is always written to the DDB item (even when empty string), unlike `from_status` which is omitted when None. This is because `reason` has a known default value (`""`) while `from_status` represents a semantically absent prior state. An empty `reason` in DDB is a valid, searchable string attribute; a missing `from_status` is a meaningful absence.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity**: `_append_history_row` and `list_status_history` call `T.orders.put_item` and `T.orders.query` respectively — DynamoDB boto3 calls that are identical in dev (DynamoDB Local on port 8001, sourced from `.env.local` via `scripts/run_local_mock_backend.sh`) and prod (real DynamoDB). There is no `if S.dev_mode` branch in either function. Full parity by construction.

**Idempotency**: The deterministic `event_id = sha256(...)[:16]` ensures that a put_item retry writes the same item to the same SK, making the write effectively idempotent. The SK uniqueness constraint (`order_id + HIST#ts#event_id`) is enforced by the deterministic construction. Two different transitions for the same order produce different `event_id` values (different `from_status` / `to_status` inputs), so they produce different SKs.

**Security**:
- No PII beyond `actor` (which is a `user_sub`, already stored in every `T.orders` header row) is written to HIST rows.
- The `actor` field is taken directly from the authenticated session's `ctx["user_sub"]` at the router layer; it cannot be spoofed by a request body.
- `list_status_history` enforces ownership at the router layer before the DDB query. The raw DDB response is never returned — it is deserialised through `OrderStatusHistoryEntry`, which strips any unexpected DDB attributes.
- No payment credentials, tokens, or secrets are stored in HIST rows.

**No forked billing path**: ORD-006 writes only to `T.orders`. It never touches `T.billing`, `billing_shared.new_ledger_entry`, or any payment path. History rows are purely informational / audit records.

## 8. Backward Compatibility & Migration

### 8.1 Zero change to existing order write path

`commerce_order_service.create_order` (`app/services/commerce_order_service.py:39`) is not modified by ORD-006. Its call to `self.orders.put_item(Item=order_record)` at line 85 is unchanged. ORD-007 will add the `_append_history_row` call to `create_order` when the flag is on; ORD-006 only provides the helper function.

### 8.2 Existing orders have no HIST rows — graceful

`list_status_history` returns an empty list for any `order_id` with no `HIST#` rows. The API response `{"history": [], "count": 0}` is valid. Clients that expect the history array to be non-empty for lifecycle-enabled orders should only call this endpoint after ORD-007 has been deployed (which seeds the initial `created` event).

### 8.3 `sk="ORDER"` header prerequisite (ORD-003)

`list_status_history` queries by `KeyConditionExpression=Key("order_id").eq(order_id) & Key("sk").begins_with("HIST#")`. This requires the `orders` table to have `sk` as a sort key (added by ORD-003). If ORD-003 has not been deployed, the query will raise a DynamoDB `ValidationException` ("Query key condition not supported"). ORD-006 must not be deployed without ORD-003.

### 8.4 Dev environment: `just restart`

Adding the sort key to `orders` via ORD-003 requires `just restart` in dev (table drop + recreate). Once ORD-003 is deployed and `just restart` has been run, ORD-006 history writes work immediately with no further migration.

### 8.5 Production: no backfill required

Existing orders written before `ORDER_LIFECYCLE_ENABLED` is turned on have no `lifecycle_status` field. Turning on the flag makes `list_status_history` return empty lists for these orders — which is correct; they have no lifecycle history. No backfill is required. If a future requirement demands synthetic history for pre-flag orders, a one-time migration script can call `_append_history_row` with `from_status=None, to_status="pending_payment", actor="migration_script"`.

## 10. Open Questions / Assumptions

1. **Assumption**: ORD-005 (`transition_order`) already derives `event_id` from `sha256(order_id|from|to|idempotency_key_or_empty)[:16]` and calls `now_ts()` once to stamp `updated_ts`. ORD-006's `_append_history_row` accepts `event_id` and `ts` as parameters rather than recomputing them, ensuring the HIST row is consistent with the header. If ORD-005 does not pre-compute and pass these values, `_append_history_row` must call `now_ts()` and `hashlib.sha256(...)` itself.

2. **Assumption**: `transition_order` in ORD-005 raises `OrderConflictError` on CAS failure and `OrderInvalidTransitionError` on an illegal transition edge — neither of which reaches step 6 (HIST write). If an exception escapes `transition_order` for any other reason before the CAS, `_append_history_row` is not called. This is the correct behaviour.

3. **Assumption**: `list_status_history` is a synchronous function (not `async def`). The platform's service layer is synchronous; async/await is used only at the FastAPI router layer. This is confirmed by `commerce_order_service.py:39` and `ssh_key_manager.py:29`.

4. **Assumption**: A `Limit=500` cap on `list_status_history` is sufficient. Most orders have fewer than 10 transitions. If an order somehow accumulates hundreds of transitions (e.g. repeated HELD/released cycles in automated testing), the cap may silently truncate. A `cursor` pagination parameter can be added later via `app/core/cursor.py` if needed.

5. **DECIDED (ESCALATIONS §B ORD-006)**: `GET /ui/orders/{order_id}/history` is accessible to both the order owner and ADMIN/ROOT users. The router checks `order["user_id"] == ctx["user_sub"]` unless `role >= ADMIN`. This is already reflected in the §4.2 router handler which uses `_require_order_owner_or_admin`. No spec change required; decision is confirmed.

6. **Assumption**: The `_audit_safe` wrapper uses a local import of `app.services.alerts` (rather than a module-level import) to avoid circular imports. `app/services/alerts.py` is a heavy module with many dependencies; a local import at the call site is the established pattern (confirmed by `ssh_key_manager.py:38`).

7. **DECIDED (ESCALATIONS §B ORD-006)**: The raw `idempotency_key` is NOT persisted as a separate DDB attribute on the HIST row. The hashed `event_id` is sufficient for support-tooling queries (the event is uniquely identifiable by `event_id`). If raw-key lookup is needed in the future, it can be added additively. No schema change required.

8. **Assumption**: The `reason` field is stored as a plain `str` attribute even when it is `""` (empty string). DynamoDB cannot store empty strings in all configurations, but boto3 with `BillingMode=PAY_PER_REQUEST` and the SDK's `boto3.dynamodb.types.TypeSerializer` handles empty strings correctly in recent SDK versions (boto3 ≥ 1.28). If this is a concern, `reason` can be omitted when empty (like `from_status`) and `list_status_history` uses `.get("reason", "")`.
