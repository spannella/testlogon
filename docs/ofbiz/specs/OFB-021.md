# OFB-021 — Pricing/promotions admin UI

## 1. Summary & Goal

OFB-021 adds a flag-gated **admin rule builder** for the pricing-rules engine introduced by OFB-019/020. Administrators (role `ADMIN` or `ROOT`) can create, inspect, edit, and deactivate each rule type (tiered, bulk, conditional) through a dedicated React page at `frontend/src/pages/shop/admin/PricingRulesAdmin.tsx`. The page lives alongside the existing per-creator promo-code management at `/promo` and the inventory admin at `admin/inventory`, reachable via the route `admin/pricing-rules`. A live preview panel calls the engine's `/ui/pricing-rules/{rule_id}/preview` endpoint (from OFB-019) with a configurable sample cart, so admins can verify discount math before activating a rule.

All existing shop, cart, orders, and billing code is byte-for-byte unchanged when the feature flag `PRICING_RULES_ADMIN_UI_ENABLED` is off.

## 2. Context & Current State

## 3. Data Model

OFB-021 introduces **no new DynamoDB tables or attributes**. It is a pure UI + admin-endpoint layer that reads/writes through the `PricingRules` table already specified in OFB-019.

The admin endpoint `GET /ui/admin/pricing-rules` (added by OFB-019) queries the `ByActive` GSI on `T.pricing_rules` with `active_pk="ACTIVE"`. The spec in OFB-019 declares the GSI, the `attr_types={"GSI1SK": "N", "created_at": "N"}` entry in `scripts/local-ddb-init.py`, and the `T.pricing_rules` handle wired at `app/core/tables.py`. OFB-021 has no further schema changes.

The preview payload passed to `POST /ui/pricing-rules/{rule_id}/preview` is an in-memory structure; it is never persisted.

## 4. API / Service Design

### 4.1 New admin-scoped endpoint: list rules platform-wide

This endpoint is specified in OFB-019 but is documented here for completeness since OFB-021 owns its frontend consumer.

```
GET /ui/admin/pricing-rules
Auth: require_admin_or_root (app/auth/policy.py:67)
Query params:
  active: Optional[bool] = None   — filter by active flag; omit for all
  cursor: Optional[str] = None    — opaque pagination cursor
  limit: int = 50                 — max items per page, capped at 200
Response: PricingRulesAdminListOut
```

`PricingRulesAdminListOut` (new model in `app/models.py`):
```python
class PricingRulesAdminListOut(BaseModel):
    rules: List[PricingRuleOut] = []
    total_count: int = 0
    cursor: Optional[str] = None
```

### 4.2 New admin-scoped preview endpoint

The creator-level `POST /ui/pricing-rules/{rule_id}/preview` (OFB-019) checks that the caller owns the rule. Admins need to preview rules they did not create. OFB-021 adds a parallel admin endpoint that skips the ownership check:

```
POST /ui/admin/pricing-rules/{rule_id}/preview
Auth: require_admin_or_root
```

Request body reuses `PricingRulePreviewIn` from OFB-019:
```python
class PricingRulePreviewIn(BaseModel):
    # Sample cart items for discount simulation
    cart_items: List[PricingRulePreviewItem]
    cart_total_cents: int   # pre-computed or derived by caller
    user_sub: str = ""      # optional: used for subscription-gate checks

class PricingRulePreviewItem(BaseModel):
    sku: str
    quantity: int = 1
    unit_price_cents: int
    category_id: str = ""
    line_total_cents: int   # must equal quantity * unit_price_cents; validated server-side
```

Response reuses `PricingRulePreviewOut` from OFB-019:
```python
class PricingRulePreviewOut(BaseModel):
    rule_id: str
    applied: bool
    discount_cents: int
    final_cart_cents: int
    reason_skipped: Optional[str] = None
    per_item_discounts: List[PerItemDiscountOut] = []

class PerItemDiscountOut(BaseModel):
    sku: str
    quantity: int
    original_cents: int
    discounted_cents: int
    discount_cents: int
```

The handler delegates directly to `pricing_rules.compute_discount(rule, cart_items, cart_total_cents, user_sub)` without calling `resolve_applicable_rules` (the admin is previewing a specific rule in isolation).

### 4.3 Admin PATCH (update any rule, not just own)

Admins need to toggle `active`, adjust `priority`, or set `expires_at` on rules they did not create. OFB-021 adds:

```
PATCH /ui/admin/pricing-rules/{rule_id}
Auth: require_admin_or_root_csrf (app/auth/policy.py:100)
Body: PricingRuleAdminUpdateIn
Response: PricingRuleOut
```

```python
class PricingRuleAdminUpdateIn(BaseModel):
    active: Optional[bool] = None
    priority: Optional[int] = Field(default=None, ge=1, le=1000)
    expires_at: Optional[int] = None   # 0 = clear expiry; positive = future ts
    max_uses: Optional[int] = Field(default=None, ge=0)
    name: Optional[str] = Field(default=None, max_length=200)
    description: Optional[str] = None
```

The handler calls `pricing_rules.update_rule(rule_id, actor_sub, **updates)` using the admin's `user_sub` as `creator_id`; the service must be updated to skip the ownership check when `bypass_ownership=True` is passed. Alternatively (simpler, lower-risk), the service exports a new `admin_update_rule(rule_id, actor_sub, **updates)` function that skips the `if item["created_by"] != creator_id` guard present in the user-facing `update_rule`.

### 4.4 Router registration

`app/routers/pricing_rules.py` (OFB-019) gains three new handler functions for the three admin endpoints. They are declared **before** any `/{rule_id}` dynamic routes to avoid FastAPI capturing the literal `admin` as a `rule_id` path parameter — the same ordering requirement noted for KYC templates in CLAUDE.md.

The router is registered in `app/main.py` under the existing `pricing_rules_router` import (added by OFB-019). No new router file.

## 5. Detailed Behavior & Edge Cases

### 5.1 Rule builder form — type selection

The admin page presents a three-tab or radio-group type selector: **Tiered**, **Bulk**, **Conditional**. Selecting a type replaces the `rule_config` section with the appropriate field set:

- **Tiered**: a repeating "Add tier" row with `min_qty` (read-only for all rows after the first; auto-set to previous row's `max_qty + 1`), `max_qty` (empty = unbounded, only valid for the last row), and `unit_price_cents` (cents). The UI enforces: at least one tier, no gap or overlap between rows, last row has empty `max_qty`. Client-side validation mirrors `_validate_tiered_config` in the service.

- **Bulk**: single form with `threshold_qty` (integer ≥ 2), `discount_type` (select: `percentage` | `fixed_per_unit`), and `discount_value`. Client shows a helper: "e.g. 15 = 15% off per unit above threshold".

- **Conditional**: `min_cart_total_cents` rendered as a dollar-formatted input, `discount_type` (select: `percentage` | `fixed_amount`), `discount_value`.

### 5.2 Scope and stacking controls

All rule types share a collapsible **Scope & Stacking** section:
- `scope_category_ids` — multi-value text input (comma-separated or tag input); empty = all categories
- `scope_skus` — multi-value text input; empty = all SKUs
- `scope_creator_user_id` — single text input; empty = platform-wide
- `required_subscription_plan_ids` — multi-value; empty = no subscription gate
- `stacking_mode` — select: `best_deal_wins` | `stackable`
- `priority` — numeric input 1–1000; default 500
- `applies_to_checkout_types` — multi-select from `{subscription, vod, shop, tip, unlock}` (mirrors `VALID_CHECKOUT_TYPES` at `app/services/promo_codes.py:25`; verified identical set)

### 5.3 Live preview panel

The preview panel on the right side of the page (or in a drawer on mobile) has:
- A sample-cart editor: add/remove rows with `sku`, `quantity`, `unit_price_cents`.
- A `cart_total_cents` field auto-computed from rows but manually overrideable (for testing threshold conditions without adding items).
- An optional `user_sub` field (used to test subscription-gate behavior).
- A **Run Preview** button that fires `POST /ui/admin/pricing-rules/{rule_id}/preview`.

The preview response renders:
- `applied: true/false` with a green/amber badge.
- `reason_skipped` if not applied.
- `discount_cents` formatted as `$X.XX`.
- Per-item breakdown table: sku / qty / original / discounted / saved.
- Final cart total.

The preview is purely informational — it does not write to DDB or affect `current_uses`. Errors from the API surface as inline error text beneath the button, not a toast, to preserve the panel state.

### 5.4 Rule list view

The admin list (`GET /ui/admin/pricing-rules`) renders a sortable table:
- Columns: Name, Type badge (`tiered`/`bulk`/`conditional`), Stacking mode, Priority, Active toggle, Uses (`current_uses / max_uses` or `∞`), Expires, Created by, Actions.
- Active toggle issues `PATCH /ui/admin/pricing-rules/{rule_id}` with `{active: <toggled>}` immediately on change (optimistic update in React Query).
- Actions column: Edit (opens the rule builder pre-populated), Preview (opens the preview panel), Deactivate (confirmation dialog → `DELETE /ui/pricing-rules/{rule_id}`, reusing the creator endpoint which is idempotent).

Since the admin endpoint returns all active rules (flag-filtered), the UI also offers an **"Show inactive"** toggle that appends `?active=false` (or omits the `active` query param to fetch all).

### 5.5 Edit pre-population

When "Edit" is clicked, the rule builder form is opened as a dialog (shadcn/ui `Dialog`) pre-populated from the `PricingRuleOut` row. The form issues `PATCH /ui/admin/pricing-rules/{rule_id}` on submit. The `rule_config` object is parsed back into the appropriate field set based on `rule_type` — `rule_type` itself is immutable after creation (changing type would require a new rule; the server returns 400 on `rule_type` in a PATCH body).

### 5.6 Promo code linkage display

When a `PricingRuleOut` has `linked_promo_code_id` set, the rule list row shows a chip "Linked code: `{code}`" that navigates to `/promo` (the existing `PromoCodesPage`) with a `?highlight={code_id}` query param. The `PromoCodesPage` does not currently consume this param; the chip is informational only in OFB-021 scope — the deep-link behavior is a follow-up.

### 5.7 Empty and loading states

- Initial load with no rules: empty state with a "Create your first pricing rule" call-to-action.
- `isLoading`: conditional render guarded by `isLoading` (same pattern as `InventoryAdmin.tsx:334`; note that `InventoryAdmin.tsx` does not use `<Skeleton>` components — use a spinner or a guarded `null` render).
- Network error: toast via `sonner` (same pattern as `PromoCodesPage.tsx:4,224`).

### 5.8 Stale data after create/update

React Query key for the admin list: `["pricing-rules", "admin", "list"]`. After any mutation (create, update, deactivate), `queryClient.invalidateQueries({ queryKey: ["pricing-rules", "admin", "list"] })` is called in `onSuccess`. The preview endpoint is not cached (no `useQuery`; fires on button click via `useMutation`).

### 5.9 Flag-off behavior

When `PRICING_RULES_ADMIN_UI_ENABLED=0` (or `VITE_PRICING_RULES_ADMIN_UI_ENABLED=0`):
- The lazy-loaded route component is never imported.
- The route `admin/pricing-rules` is not registered in `App.tsx` (conditional rendering).
- The nav item is hidden (conditional render in the sidebar).
- Backend: the three admin endpoints introduced in §4 still exist in the router, but `_require_admin_ui_enabled()` (a helper mirroring the pattern in `app/routers/promo_codes.py:40–43`) returns HTTP 404. The creator-facing `GET/POST /ui/pricing-rules` endpoints from OFB-019 are governed by their own `pricing_rules_enabled` flag and are not affected by this ticket's UI flag.

### 5.10 Pagination of admin list

The admin list uses `useInfiniteQuery` with `cursor`-based pagination matching the OFB-019 service's cursor encoding (from `app/core/cursor.py`). A "Load more" button appends the next page. The default page size is 50 rules.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/Prod Parity

The three admin endpoints call the same `pricing_rules.py` service functions in both dev and production. There is no `dev_mode` branch in the admin handlers. The preview endpoint calls `compute_discount` in-memory with zero DDB writes — identical in both environments.

### Idempotency

Rule creation uses the `sha256(correlation_id)` pattern from `commerce_order_service.py:67`: `rule_id = "pr_" + uuid4().hex[:12]` (the full hex is effectively random and collision-resistant, not correlation-ID-derived). Rule creation is therefore not idempotent on retries — the caller should check for a 409 (duplicate name within a creator's scope) before retrying. The admin `PATCH` is fully idempotent: sending the same payload twice produces the same DDB state.

### Role enforcement

Admin endpoints use `Depends(require_admin_or_root)` or `Depends(require_admin_or_root_csrf)` (for state-mutating PATCH). Scoped admins (e.g., `content_moderation`) do not satisfy `Role.ADMIN | Role.ROOT` via `require_roles` (`app/auth/policy.py:49–54`) and receive HTTP 403. The frontend `canAccessGeneralAdminControls` gate prevents the UI from even attempting the call, but the server is authoritative.

### CSRF

The admin PATCH uses `require_admin_or_root_csrf` (defined at `app/auth/policy.py:100–106`). Cookie-authenticated requests that lack a valid `x-csrf-token` header matching `ui_csrf` cookie receive HTTP 403. Bearer-auth API clients skip CSRF. The frontend `api/client.ts` (`api/client.ts:179–181`) attaches the CSRF header from the `ui_csrf` cookie on every request (including GETs; the server ignores it on safe methods).

### Input validation

- `rule_config` is validated by the service (`_validate_tiered_config`, `_validate_bulk_config`, `_validate_conditional_config`) before any DDB write. Malformed configs return 400.
- `priority` is clamped to `ge=1, le=1000` via Pydantic `Field` — no DDB write on out-of-range values.
- `expires_at=0` is explicitly handled as "clear expiry" — not treated as epoch zero.
- `scope_creator_user_id` is not validated against DDB (the user may not exist yet or may be a future creator); this is by design — the rule is a filter, not a relationship.

### Audit trail

Every PATCH issued through the admin endpoint passes the admin's `user_sub` as `actor_sub` to the `AUDIT#` row written by `update_rule`. This ensures the audit trail in the `PricingRules` table distinguishes creator edits from admin overrides.

## 8. Backward Compatibility & Migration

### Existing promo codes

`app/services/promo_codes.py` is untouched by OFB-021. The `PromoCodesPage.tsx` at `/promo` is untouched. No DDB records are mutated. Existing `percentage | fixed_amount | free_trial` codes continue to function regardless of all pricing-rules flags.

### Shopping cart and checkout

`app/services/shoppingcart.py` and `app/routers/shoppingcart.py` are untouched by OFB-021. Hooking the engine into the cart is OFB-020's scope. OFB-021 only provides the management UI.

### DynamoDB tables

No `UpdateTable` operation is needed for OFB-021. The `PricingRules` table is created fresh by OFB-019 (`scripts/local-ddb-init.py` addition). In an environment where OFB-019 has not yet been deployed, the admin endpoints return 404 (the `_require_pricing_rules_enabled()` guard fires). No migration script is needed.

### Route collision

The new route `admin/pricing-rules` is a static path that does not collide with any existing route in `frontend/src/App.tsx`. The backend admin endpoints are added after the existing `GET /ui/pricing-rules` and `GET /ui/pricing-rules/{rule_id}` routes — the literal `admin` prefix on `/ui/admin/pricing-rules` paths avoids any dynamic-segment capture by `{rule_id}`.

- Deactivate via creator `DELETE` endpoint; `?active=false` query returns deactivated rule.

**Section 2 — Admin preview API (6 tests)**
- `POST /ui/admin/pricing-rules/{rule_id}/preview` with valid cart → `applied=true`, `discount_cents > 0`.
- Preview with condition not met (cart below threshold) → `applied=false`.
- Preview as alice → 403.
- Preview with flag off (skip if env does not allow runtime flag toggle; assert 404 on a separately created flag-off endpoint — see open question §10.2).

**Section 3 — Admin PATCH API (5 tests)**
- PATCH `{active: false}` → rule deactivated; re-fetch confirms.
- PATCH `{priority: 1}` → priority stored.
- PATCH without CSRF → 403.
- PATCH as alice → 403.
- PATCH `expires_at=0` clears expiry.

**Section 4 — Pricing Rules Admin UI page (15 tests)**
- Navigate to `/admin/pricing-rules`; page visible for charlie_admin.
- Navigate as alice → redirected or 403-blocked (depending on ProtectedRoute implementation).
- "Create Rule" button opens dialog; type selector shows Tiered / Bulk / Conditional.

- Active toggle in table → optimistic update + PATCH fired.
- "Edit" opens pre-populated dialog; change name → saved.
- "Preview" opens preview panel; add 2 cart rows; click "Run Preview" → result rendered.
- Preview with insufficient cart total → "Not applied" badge shown.
- Deactivate confirmation dialog → row disappears from active list; reappears with "Show inactive" toggle.
- Empty state visible when no rules.

## 10. Open Questions / Assumptions

1. **Assumption: OFB-019 is fully shipped before OFB-021 is deployed.** The admin UI depends on `app/services/pricing_rules.py`, `T.pricing_rules`, `S.pricing_rules_enabled`, the `PricingRules` DDB table, and the `PricingRuleOut` model being present. If OFB-019 is in flight simultaneously, the `_require_pricing_rules_enabled()` guard in the admin endpoints (which checks `S.pricing_rules_enabled`) will return 404 in environments where OFB-019 has not been enabled, making the admin UI silently empty rather than broken.

2. **Assumption: the preview endpoint from OFB-019 does not increment `current_uses`.** The spec states it is informational only. This must be verified against the OFB-019 implementation; if preview calls the full `compute_discount` path which has side effects, a `dry_run=True` parameter must be threaded through.

3. **Open: should `PATCH /ui/admin/pricing-rules/{rule_id}` allow editing `rule_config`?** The spec above allows it. If editing the config of a rule mid-flight (with active carts) could produce inconsistent discounts, it should be restricted to inactive rules only. Decision deferred to OFB-022 test results.

4. **Assumption: scoped admins (e.g., `billing_support`) are excluded from pricing rule management.** `require_admin_or_root` already enforces `Role.ADMIN | Role.ROOT`. The `canAccessGeneralAdminControls` frontend check further restricts to `admin_profile.type === "general"`. If a scoped-admin use-case arises later, it requires a new `AdminScope` value.

5. **Open: pagination UX for the admin list.** This spec uses "Load more" (infinite scroll). If the typical rule count is low (<50), a simple non-paginated list with a client-side filter would be simpler. The cursor-based approach is spec'd to remain consistent with the underlying service API.

6. **Assumption: `PricingRulePreviewIn`, `PricingRulePreviewOut`, and `PerItemDiscountOut` Pydantic models are defined in OFB-019.** If OFB-019 does not define them, OFB-021 must add them to `app/models.py` before the admin preview endpoint can use them.

7. **Open: sidebar nav placement.** The new "Pricing Rules" nav item should appear in the admin section of the sidebar. The exact location (before or after "Inventory") depends on current sidebar ordering, which is not audited in this spec. The implementer should place it adjacently to `admin/inventory`.
