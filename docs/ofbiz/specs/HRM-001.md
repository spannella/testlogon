# HRM-001 — HR feature flag & settings keys

## 1. Summary & Goal

HRM-001 is the P0 scaffolding ticket for Phase M — Human Resources of the OFBiz ERP buildout. Its sole deliverable is the addition of three boolean feature flags and two string settings keys to `app/core/settings.py`, the singleton `S`, and the companion documentation files (`.env.local.example`, `CLAUDE.md`). No router, service, DynamoDB table, or Pydantic model is created here; those belong to HRM-002 through HRM-010.

The flags establish the flag-hierarchy contract that every downstream HRM ticket must honour:

- `hr_enabled` — master gate. When `False`, the HR module does not exist from the perspective of any other subsystem. All downstream services guard their public entry points with a `_require_enabled()` helper that raises `HTTPException(status_code=404, ...)` (following the `returns_rma` precedent: `app/services/returns_rma.py:71–73`, called from each handler in `app/routers/returns_rma.py`; settings key at `app/core/settings.py:846`).
- `hr_payroll_enabled` — sub-gate for payroll run CRUD. Ignored (and irrelevant) when `hr_enabled` is `False`.
- `hr_payroll_gl_posting_enabled` — sub-gate for the double-entry GL journal-entry write triggered after a payroll run is `APPROVED`. Ignored when `hr_payroll_enabled` or `hr_enabled` is `False`.

The string keys supply the DynamoDB table name and the GL expense-account code default needed by HRM-002 and HRM-010 respectively, both of which reference them before any HR business logic is written.

## 3. Data Model

HRM-001 introduces **no DynamoDB tables**. The `hr` table is defined in HRM-002. This section documents only the settings-level data contract that constrains HRM-002's table definition.

### Settings-derived DynamoDB contract

| Setting key | Env var | Default | Used by |
|---|---|---|---|
| `hr_table_name` | `DDB_HR_TABLE` | `"hr"` | HRM-002: `TableDef(_resolve_table_name(S.hr_table_name, "hr"), "pk", "sk", ...)` and `app/core/tables.py`: `hr=_safe_table(S.hr_table_name)` |

The table name default `"hr"` is lowercase per the inventory/returns precedent. Operators may override via `DDB_HR_TABLE=hr_staging` in `.env.local` without touching code.

### GL expense account

| Setting key | Env var | Default | Used by |
|---|---|---|---|
| `hr_payroll_expense_account_code` | `HR_PAYROLL_EXPENSE_ACCOUNT_CODE` | `"6000"` | HRM-010: resolves the debit GL account code for payroll journal entries without hard-coding |

`"6000"` is the conventional OFBiz Salaries & Wages Expense ledger code. The type is `str` (not `int`) because GL account codes are identifiers, not arithmetic values, and may carry leading zeros in some chart-of-accounts schemes.

## 4. API / Service Design

HRM-001 ships **no endpoints and no service functions**. The deliverable is purely settings scaffolding. The section below documents the _interface contract_ that downstream tickets will rely on.

### Flag-gating contract (not implemented here, but specified here)

Every future HRM router must guard its handler at the earliest possible point:

```python
# app/routers/hr.py (HRM-005+)
from app.core.settings import S
from fastapi import HTTPException

def _require_hr() -> None:
    if not S.hr_enabled:
        raise HTTPException(status_code=404, detail="hr_disabled")

def _require_payroll() -> None:
    _require_hr()
    if not S.hr_payroll_enabled:
        raise HTTPException(status_code=404, detail="hr_payroll_disabled")

def _require_payroll_gl() -> None:
    _require_payroll()
    if not S.hr_payroll_gl_posting_enabled:
        raise HTTPException(status_code=404, detail="hr_payroll_gl_disabled")
```

This pattern mirrors the `_require_enabled()` helper in `app/services/returns_rma.py:71–73` (which calls `_flag_on()` at `:67–68` and raises `HTTPException(status_code=404, detail="Returns/RMA is not enabled")`). Note: `browser_ssh_terminal.py` uses a different approach (a local `browser_ssh_terminal_enabled()` helper function that returns a `bool` from the env directly, without raising) and `_mock_enabled()` in `app/routers/ups.py:22–23` checks `S.dev_mode`, not a feature flag — neither is the right model for HRM feature-flag guarding.

### Settings accessor surface

After HRM-001 merges, the following attributes are available on the `S` singleton with no import changes required by callers (since `S` is a module-level singleton):

```python
S.hr_enabled                      # bool, default False
S.hr_payroll_enabled               # bool, default False
S.hr_payroll_gl_posting_enabled    # bool, default False
S.hr_table_name                    # str, default "hr"
S.hr_payroll_expense_account_code  # str, default "6000"
```

## 5. Detailed Behavior & Edge Cases

### Flag independence

The three boolean flags are logically nested (`hr_payroll_gl_posting_enabled` only makes sense when `hr_payroll_enabled` is on, which only makes sense when `hr_enabled` is on), but at the settings layer each is fully independent. A misconfigured deployment that sets `hr_payroll_gl_posting_enabled=1` without `hr_enabled=1` will not crash — the outer guard in downstream routers will 404 before the inner flag is ever checked.

### No coupling to existing flags

`hr_enabled` does not interact with any existing flag. Setting it to `True` (or `False`) does not change the behavior of `returns_rma_enabled`, `newsfeed_recsys_enabled`, `browser_ssh_terminal_enabled`, or any other flag. With `hr_enabled=False` (the default), the DynamoDB table `hr` need not even exist; any call to `T.hr` from service code (HRM-002+) will only happen after the flag is checked.

### Table name collision avoidance

The default `"hr"` is not used by any existing table in `scripts/local-ddb-init.py` (verified: the string `"hr"` does not appear as a table name default in the current file). Operators using non-default table names (e.g., for blue/green deployments) set `DDB_HR_TABLE=hr_blue`.

### GL account code validation

`hr_payroll_expense_account_code` is a raw string and is not validated at settings load time. HRM-010 must validate that the code resolves to a real account in the chart-of-accounts before posting. An empty string or unrecognised code at posting time should raise a descriptive error in HRM-010, not here.

### `Settings` is `frozen=True`

`app/core/settings.py:6`. The `Settings` dataclass is frozen; the `S` singleton cannot be mutated at runtime by service code. Tests that need to verify flag-off behavior use `object.__setattr__(S, "hr_enabled", False)` and restore with a `try/finally` block (following the `test_newsfeed_recsys.py:74–87` pattern).

## 8. Backward Compatibility & Migration

### Zero-change guarantee

With all three flags at their defaults (`False`), this ticket is byte-for-byte additive:

- The `Settings` dataclass gains five new fields with default values. No existing field changes its default or type.
- No existing table name is modified.
- `S = Settings()` at `app/core/settings.py:2772` continues to work without any env-var change.
- No router, service, or test file outside `tests/test_hrm_001_flags.py` is modified.

### Migration

There is no DynamoDB migration in this ticket. The `hr` table does not exist until HRM-002 runs `scripts/local-ddb-init.py`. Any deployment that sets `HR_ENABLED=1` without running `just restart` (which recreates all tables via `scripts/local-ddb-init.py`) will encounter DynamoDB `ResourceNotFoundException` on first use of `T.hr` — this is expected and intentional: HRM-002 must be deployed before the flag is turned on in any environment.

### `.env.local` impact

Existing `.env.local` files on developer machines do not set `HR_ENABLED`, `HR_PAYROLL_ENABLED`, `HR_PAYROLL_GL_POSTING_ENABLED`, `DDB_HR_TABLE`, or `HR_PAYROLL_EXPENSE_ACCOUNT_CODE`. Absence of these variables results in the defaults (`False`/`False`/`False`/`"hr"`/`"6000"`). No developer needs to update their `.env.local` unless they are actively working on HR functionality.

## 10. Open Questions / Assumptions

1. **Assumption: flag naming prefix `hr_` is final.** The ticket descriptor uses `hr_` throughout. If a future renaming to `hrm_` is desired, it should be decided before HRM-001 merges — all downstream HRM-002 through HRM-010 tickets reference `S.hr_enabled` and the env vars.

2. **Assumption: three boolean flags is the correct granularity.** The ticket specifies exactly `hr_enabled`, `hr_payroll_enabled`, and `hr_payroll_gl_posting_enabled`. There is no separate `hr_positions_enabled` or `hr_employments_enabled` sub-gate. If finer-grained rollout is needed, that is out of scope for HRM-001.

3. **Assumption: `"6000"` is a valid code in the seeded chart of accounts.** HRM-001 picks the conventional OFBiz Salaries & Wages Expense code. OFB-013's own `DEFAULT_ACCOUNTS` list contains only 7 accounts (`1000`, `1200`, `2000`, `2100`, `4000`, `4900`, `5100`) — account `"6000"` is **not** in OFB-013's default chart. However, HRM-010 (§2.4) explicitly seeds account `"6000"` (Salaries & Wages Expense, expense class, debit normal balance) as an additive append to `seed_default_chart()`. `hr_payroll_expense_account_code` therefore resolves correctly once HRM-010 is deployed. This is a forward dependency on HRM-010, not a plan gap. (Resolved pass 3 — FORWARD_DEP on HRM-010 `docs/ofbiz/specs/HRM-010.md §2.4`.)

4. **Assumption: the `hr` table name does not collide with any existing DynamoDB table.** Verified by `grep`-searching `scripts/local-ddb-init.py` — no current `TableDef` uses `"hr"` as its name. However, if a staging environment already has a DynamoDB table named `hr` for an unrelated purpose, operators must set `DDB_HR_TABLE` to avoid a collision.

5. **Assumption: `frozen=True` + `object.__setattr__` is the accepted test-isolation pattern.** This is confirmed by `tests/test_newsfeed_recsys.py:73–87` (save orig at `:73`, setattr at `:74`, restore in `tearDown` at `:86`) and `tests/test_compute_billing_timer_gap0228.py:117–123`. No alternative (e.g., dependency injection of `Settings`) is in use.

6. **Assumption: `.env.local.example` additions do not need a `just restart` guard.** Because the new env vars default to `"0"`, a developer who does not explicitly set them gets the default-off behavior with no action required. The `just restart` guidance in HRM-002 (table creation) is sufficient.

7. **Open question: should `hr_payroll_expense_account_code` be a settings key at all, or a seeded DynamoDB configuration row?** The ticket explicitly specifies a settings key. However, a multi-tenant deployment might want per-tenant expense accounts. This is deferred — the settings key approach is correct for the single-tenant/platform-operator model that the rest of the OFBiz buildout assumes.
