# MFG-009 — Work-order admin UI (production queue)

## 1. Summary & Goal

MFG-009 delivers the production-queue admin page: a React component at
`frontend/src/pages/shop/admin/ProductionQueue.tsx` that lets an admin or root
user create work orders, inspect the exploded component availability before
releasing them, drive all lifecycle transitions (release / start / complete /
cancel), and see the resulting finished-goods inventory change — all without a
full page reload.

The page is additive: it consumes the backend endpoints provided by MFG-007
(`app/services/manufacturing_work_orders.py`) and MFG-011
(`app/routers/manufacturing.py`) via TypeScript wrappers added to the shared
`frontend/src/api/endpoints/manufacturing.ts` file that MFG-006 created. No
backend service code is written by this ticket; the only backend coupling is the
existing endpoint contract from MFG-007/MFG-011.

The feature is completely hidden — no route, no nav item, no API calls — when
`VITE_MANUFACTURING_MRP_ENABLED` is falsy (the default).

## 3. Data Model

MFG-009 introduces **no new DynamoDB tables**. All production-queue data lives
in the `mfg_work_orders` table provisioned by MFG-002.
The `mfg_work_orders` table is **not yet present** in `scripts/local-ddb-init.py`
(current file is 2710 lines; last TableDef closes at line 2492; `_table_defs()`
closing `]` is at line 2493). MFG-002 inserts the `TableDef` at line 2492+.
Per `docs/ofbiz/specs/MFG-001.md:§3.3`:

```
PK: work_order_id   (sha256(correlation_id)[:32])
SK: "META"               — header row
    "ISSUE#{n:04d}"      — one row per issued component (written at release)
    "EVENT#{ts:010d}"    — state-transition log
```

The two GSIs used by the list endpoint:

```
GSI_STATUS:  PK=status (S),       SK=created_at (N)
GSI_PRODUCT: PK=product_sku (S),  SK=created_at (N)
attr_types: {"created_at": "N"}
```

`GSI_STATUS` is the primary index for the production queue: the page queries
`status IN ("created", "released", "in_progress")` to show active orders and
`status = "completed"` / `status = "cancelled"` for the history tab.

### 4.3 `<ActiveQueueTab />`

Renders work orders in `created | released | in_progress` statuses.

**Data**: three parallel `useQuery` calls (or one call with a custom status list
— see Section 5.2 for the status list discussion):

```ts
const activeQuery = useQuery({
  queryKey: ["mfg", "work-orders", "active"],
  queryFn: () => listWorkOrders({ limit: "200" }),
  enabled: allowed,
  select: (rows) => rows.filter(
    (wo) => ["created", "released", "in_progress"].includes(wo.status)
  ),
});
```

Because the backend `listWorkOrders` with no `status` filter returns all orders,
client-side filter is required for the active view. Alternatively, the backend
`list_work_orders` function accepts a `status` query param and queries
`GSI_STATUS` directly; three separate calls (one per active status) are also
valid. The simpler one-call approach is preferred for MVP.

**List layout**: a `<Table>` with columns:
- `Status` badge (created=outline, released=blue, in_progress=orange)
- `Product SKU`
- `Quantity` (planned)
- `Work Center` (resolved from `work_center_id` or "—")
- `Created` (relative timestamp)
- `Actions` (context-specific action buttons — see Section 5.3)

Row click opens the `<WorkOrderDetailSheet />`.

**"New Work Order" button**: opens `<WorkOrderCreateDialog />`.

### 4.4 `<HistoryTab />`

Renders work orders with `completed | cancelled` statuses, using the same list
endpoint with a `status` filter. Columns add `Produced Qty` and a `Completed

on `WorkOrderOut`; use `updated_at` as a proxy — see Section 10.2).

History tab is read-only (no action buttons).

### 4.5 `<WorkOrderCreateDialog />`

Fields:
- `product_sku` (text, required)
- `quantity` (number input, min 1)
- `bom_id` (optional — text field with placeholder "Leave blank to auto-resolve

On submit: `createWorkOrder(body)`. On 422: surface Pydantic error messages

### 4.6 `<WorkOrderDetailSheet />`

A right-aligned `<Sheet>` (or `<Dialog>`) opened when a row is selected. Calls
`getWorkOrder(wo.work_order_id)` to get the full record with `issues[]`.

Sections:
1. **Header summary** — `work_order_id` (truncated), `product_sku`, `quantity`,
   `status` badge, `created_at`.
2. **Component Availability Preview** — shown for all non-completed, non-cancelled
   orders; see Section 4.7.
3. **Action Bar** — status-conditional buttons; see Section 5.3.
4. **Issued Components** (shown once status ≥ `released`) — a table of
   `WorkOrderIssueOut` rows from the detail response.
5. **Event Log** (future; deferred — see Section 10.3).

### 4.7 `<ComponentAvailabilityPreview />`

Given a work order with a `bom_id`, this sub-component:

1. Calls `explodeBom(bom_id, quantity)` via:
   ```ts
   const explodeQuery = useQuery({
     queryKey: ["mfg", "boms", bom_id, "explode", quantity],
     queryFn: () => explodeBom(bom_id, quantity),
     enabled: !!bom_id && status !== "completed" && status !== "cancelled",
   });
   ```
2. For each `ExplodedComponentOut`, calls `getInventoryItem(component_sku)`:
   ```ts
   const inventoryQueries = useQueries({
     queries: (explodeQuery.data ?? []).map((comp) => ({
       queryKey: ["inventory", "item", comp.component_sku],
       queryFn: () => getInventoryItem(comp.component_sku),
       retry: false,
       // 404 = SKU not in inventory (treat as available=0)
     })),
   });
   ```
3. Merges the two datasets into `ComponentAvailability[]`.
4. Renders a compact table:

```
Component SKU   Required   Available   On-Hand   Status
─────────────── ────────── ─────────── ───────── ──────
SKU-PANEL-A     10         12          12        ✓ OK
SKU-BOLT-M5     40         35          35        ⚠ Short 5
SKU-WASHER      120        0           0         ✗ None
```

Color coding: `available >= required` → green tick; `0 < available < required` →
amber warning badge showing shortfall; `available = 0` → red badge.

The preview is shown before release (when `status = "created"`) and after release
(when `status = "released"`, showing actual issued quantities from `issues[]`
instead of the explosion preview).

When `bom_id` is null (work order created with explicit `bom_id` not yet set),
the preview shows a muted "BOM not yet resolved" message.

## 5. Detailed Behavior & Edge Cases

### 5.1 Status-badge color mapping

| Status | Badge variant | Color |
|--------|--------------|-------|
| `created` | outline | default/muted |
| `released` | solid | blue |
| `in_progress` | solid | orange/amber |
| `completed` | solid | green |
| `cancelled` | outline | gray/muted |

Consistent with MFG-006's `ManufacturingAdmin.tsx` BOM status badges.

### 5.2 Action buttons per status (Section 4.3 / 4.6)

| Status | Buttons shown |
|--------|--------------|
| `created` | **Release** (primary), **Cancel** (destructive outline) |
| `released` | **Start** (primary), **Complete** (secondary), **Cancel** (destructive outline) |
| `in_progress` | **Complete** (primary), **Cancel** (destructive outline) |
| `completed` | _(none)_ |
| `cancelled` | _(none)_ |

- **Release** fires `releaseWorkOrder(wo.work_order_id)`.
- **Start** fires `startWorkOrder(wo.work_order_id)`.
- **Complete** opens a small inline form asking for `produced_qty` (pre-filled
  with `wo.quantity`), then fires `completeWorkOrder(wo.work_order_id, { produced_qty })`.
- **Cancel** opens a confirmation `<AlertDialog>` asking for an optional note,
  then fires `cancelWorkOrder(wo.work_order_id, { note })`.

All actions use `useMutation`:
```ts
onSuccess: (updated) => {
  toast.success(`Work order ${updated.status}`);
  qc.invalidateQueries({ queryKey: ["mfg", "work-orders"] });
  qc.invalidateQueries({ queryKey: ["inventory"] });  // finished-goods update
  setSelectedWo(updated);  // refresh detail panel in place
},
onError: (err) => {
  // Surface 409 detail inline in the sheet, not just a toast
  setActionError(extractDetail(err));
},
```

`qc.invalidateQueries(["inventory"])` ensures the inventory page reflects the
new on-hand count without requiring a manual reload, satisfying the acceptance
criterion "finished-goods on-hand increases in the inventory page without
reload".

### 5.3 409 inline error surface for failed release

When `releaseWorkOrder` returns a 409, the `onError` handler extracts the
`detail` string from the Axios error response body (using a helper
`extractDetail(err): string`). This message is displayed inside the detail
sheet, directly below the action buttons, in an amber/red inline `<Alert>` —
not as a `toast` so the admin can read the full component name without
auto-dismiss. The alert is cleared when the user navigates away or retries.

Example 409 message surfaced inline:
> "Insufficient stock for component 'SKU-BOLT-M5': Adjustment would drop on-hand
> below reserved quantity"

The component availability preview will simultaneously highlight `SKU-BOLT-M5`
in red, giving the admin the visual and textual signal at the same time.

### 5.4 Work-center name resolution

`WorkOrderOut.work_center_id` is an opaque string. The page resolves names by
maintaining a `useQuery(["mfg", "work-centers"], () => listWorkCenters())`
cache (the same query in `ManufacturingAdmin.tsx`). Name lookup:
`workCenters?.find((wc) => wc.work_center_id === wo.work_center_id)?.name ?? "—"`.
No extra network call; this query is already cached from the `ManufacturingAdmin`
page visit.

### 5.5 Inventory query for unknown SKU (404 handling)

`getInventoryItem` returns a 404 when the SKU has no inventory record. The
`useQueries` call sets `retry: false`; an error result for a component maps to
`available = 0` and `on_hand = 0` in the `ComponentAvailability` merge. The
status column shows "⚠ No record" in muted text (distinct from "✗ None" which
means the record exists but has zero available).

### 5.6 List performance and pagination

`listWorkOrders({ limit: "200" })` fetches up to 200 headers in one call. For
an MVP shop this is sufficient. The backend's `GSI_STATUS` loop with
`LastEvaluatedKey` (per `docs/ofbiz/specs/MFG-007.md:§5.8`) returns at most 200
items matching the given status before returning. If the production queue grows
beyond 200 active orders, an infinite-scroll or "load more" pattern is required
— deferred to a follow-up ticket (see Section 10.5).

### 5.7 `produced_qty` pre-fill in Complete dialog

The complete form pre-fills `produced_qty` with `wo.quantity`. The field is an
`<Input type="number">` with `min=1`. If the admin leaves it at the default,
the service uses it as-is (`WorkOrderCompleteIn.produced_qty` sent to backend);
if the admin clears it (sends `null`), the backend defaults to `wo.quantity`
anyway per `docs/ofbiz/specs/MFG-007.md:§5.4` step 3. In the frontend, send
the numeric value explicitly rather than an empty/null to avoid confusion.

### 5.8 Flag-off behavior

With `VITE_MANUFACTURING_MRP_ENABLED=false` (default):
- `ProductionQueue.tsx` renders an `<EmptyState>` immediately (no API calls).
- The `admin/production-queue` route exists in `App.tsx` but the page shows the
  empty state.
- The nav item `Production Queue` is filtered out by the
  `showProductionQueueAdmin` predicate in `Sidebar.tsx`.

With the backend flag `MANUFACTURING_MRP_ENABLED=false`:
- Every endpoint called by the page returns 404 (`_require_enabled()` in the
  router, per `docs/ofbiz/specs/MFG-007.md:§6`).
- The client-side queries return errors; React Query shows loading/error states.
- This state is not expected in a consistent deployment (both flags should match),
  but the page degrades gracefully without crashing.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity**: The page makes only standard `api.get` / `api.post` calls
through the shared Axios client (`frontend/src/api/client.ts`). No dev-mode
mock branch exists in the frontend. The backend endpoints the page calls are
themselves SECOPS-007 clean (no `dev_mode` branches in
`manufacturing_work_orders.py` or the router) — confirmed by
`docs/ofbiz/specs/MFG-007.md:§7`.

**Idempotency from the UI perspective**:
- The "New Work Order" form includes a hidden `correlation_id` field seeded with
  a `crypto.randomUUID()` at dialog-open time. If the admin double-clicks Submit,
  the second network call carries the same `correlation_id` → backend returns the
  already-created work order (deterministic-id idempotency per MFG-007:§7).
- Action buttons are disabled while the corresponding mutation is in-flight
  (`useMutation.isPending`) to prevent double-submission.

**Security**:
- All POST calls carry `x-csrf-token` automatically via

## 10. Open Questions / Assumptions

1. **Assumption: MFG-006 has shipped before MFG-009.** `ProductionQueue.tsx`
   extends `frontend/src/api/endpoints/manufacturing.ts` (created by MFG-006)
   and reads `isManufacturingMrpEnabled()` (defined by MFG-006 in
   `featureFlags.ts`). If MFG-009 ships first, it must create both the file and
   the flag constant, then MFG-006 should not duplicate them.

2. **Assumption: `WorkOrderOut.updated_at` is used as a proxy for `completed_at`
   on the history tab.** The `mfg_work_orders` header row does not expose a
   dedicated `completed_at` field in `WorkOrderOut` per `docs/ofbiz/specs/MFG-003.md:259–274`.
   The `EVENT#{ts}` rows carry per-transition timestamps, but they are not
   projected into `WorkOrderOut`. `updated_at` reflects the last mutation and
   serves adequately for the history sort. If a dedicated `completed_at` field is
   added to `WorkOrderOut` (trivial service change), the history tab should prefer
   it.

3. **Assumption: `listWorkOrders` with no status filter returns all statuses.**
   The ticket spec (`MFG-007:§4.1`) shows `status: Optional[str]` on
   `list_work_orders`. If no `status` is passed the backend returns all work
   orders (up to `limit`). The frontend applies a client-side `.filter()` to
   separate active from history. If the backend only accepts single-status
   queries on `GSI_STATUS`, the frontend must make separate calls per status;
   this is an implementation detail of MFG-011's router.

4. **Assumption: `useQueries` from React Query handles parallel inventory lookups.**
   `useQueries` is available in `@tanstack/react-query` v5 (version
   `^5.62.0` per `frontend/package.json`) and is the correct hook for a
   dynamic number of parallel queries driven by a list. **CORRECTION: the
   original claim that `useQueries` is "already used in this project, e.g.
   `frontend/src/pages/feed/FeedPage.tsx`" is wrong** — `FeedPage.tsx` uses
   only `useQuery`, and no file in `frontend/src/` currently imports
   `useQueries`. The hook is available from the installed package but is a
   new usage in this codebase. Import it as:
   `import { useQueries } from "@tanstack/react-query";`

5. **Assumption: page limit of 200 work orders is sufficient for MVP.** If the
   production queue exceeds 200 active orders, the page will silently miss older
   entries. A follow-up should add cursor-based pagination or an infinite-scroll.
   The backend loop in `list_work_orders` already handles `LastEvaluatedKey`
   (MFG-007:§5.8), so the pagination contract is available.

6. **Assumption: the `<ComponentAvailabilityPreview />` is shown only when
   `bom_id` is set on the work order.** If a work order was created with an
   explicit `bom_id` but the BOM was subsequently deactivated, `explodeBom` may
   return a 404 or 409. The component handles these errors gracefully: a query
   error state renders a muted "Could not load BOM explosion" message.

7. **Question: should the work-center select in the create dialog make a backend
   call?** The create dialog needs a list of active work centers to populate the
   optional select. `listWorkCenters()` is already called by `ManufacturingAdmin.tsx`.
   Since both pages may be open in the same session, the React Query cache will
   likely have the data already. No extra network call on first open if the admin
   visited `ManufacturingAdmin` recently; otherwise one call on dialog open.

8. **Assumption: `correlation_id` in the create form is seeded client-side with
   `crypto.randomUUID()` at dialog-open time.** This is the frontend-idempotency
   contract: repeated Submit clicks without closing the dialog reuse the same
   `correlation_id` → no duplicate work order. Closing and reopening the dialog
   generates a fresh UUID.

9. **Assumption: the `cancel` confirmation dialog exposes a note field, matching
   `WorkOrderCancelIn.note`.** Sending an empty note is also valid (the backend
   accepts `null`). If the admin leaves the note blank, the frontend sends
   `{}` (empty body) rather than `{ note: "" }`.

10. **Assumption: action buttons in the detail sheet are inside a `<form>` or use
    explicit `type="button"` to prevent accidental submit on Enter.** Using
    shadcn/ui `<Button>` with `type="button"` or `type="submit"` should be
    consistent with existing patterns in `InventoryAdmin.tsx`.
