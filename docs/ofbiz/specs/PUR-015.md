# PUR-015 — Purchase-orders admin page (create / approve / receive)

**Type:** Feature | **Priority:** P1 | **Estimate:** 4 days
**Milestone:** 5 — Frontend
**Depends on:** PUR-013 (Frontend types + endpoint wrappers), PUR-014 (Suppliers admin page)

## 1. Summary & Goal

PUR-015 builds the purchase-orders admin page at
`frontend/src/pages/shop/admin/PurchaseOrdersAdmin.tsx`. It is the primary UI for the
buying workflow established by PUR-006 through PUR-012: an admin or root user can
create a draft PO against any active supplier, move it through the approval lifecycle
(submit → approve / reject), enter received quantities against an approved PO, and
convert low-stock reorder suggestions into draft POs — all without a page reload.

The page lives alongside the existing `InventoryAdmin.tsx` and the PUR-014
`SuppliersAdmin.tsx` under `frontend/src/pages/shop/admin/`. It is accessible at
the route `admin/purchase-orders` (registered by PUR-016). It is flag-gated on the
client side via a new `isPurchasingScmEnabled()` helper in
`frontend/src/lib/featureFlags.ts` (mirroring `isInventoryReservationsEnabled()` at
`featureFlags.ts:161`) and role-gated via
`canAccessGeneralAdminControls(accessToken)` from `frontend/src/lib/adminCapabilities.ts`.

With `PURCHASING_SCM_ENABLED=false` on the backend every purchasing endpoint returns
404. The page itself is never rendered for non-admin sessions. Existing shop, cart,
orders, and billing code is byte-for-byte unchanged.

## 3. Data Model

PUR-015 introduces no new DynamoDB tables. All tables are established by PUR-002.
This section documents the relevant table shapes for the receiving panel's idempotency
key design and for understanding the query parameters on list calls.

### 3.1 `purchase_orders` table (PUR-002)

```
PK  = po_id          (string, sha256 hex [:32])
SK  = "META"         (header row)
     "LINE#{n}"      (line rows, n = 1-based integer)

GSI_SUPPLIER  :  partition_key = supplier_id
                 sort_key      = created_at  (N — numeric)
GSI_STATUS    :  partition_key = status
                 sort_key      = created_at  (N — numeric)
```

`attr_types = {"created_at": "N"}` (per CLAUDE.md DDB-numeric-GSI gotcha and the
pattern at `scripts/local-ddb-init.py:2491` — that line is `attr_types={"created_at": "N"}`
on the `returns` table, the nearest existing analogue).

Status values: `draft | submitted | approved | ordered | partially_received | received | closed | rejected | cancelled`.

### 3.2 `po_receipts` table (PUR-002)

```
PK  = po_id
SK  = "RECEIPT#{receipt_id}"   (receipt_id = sha256(receipt_correlation_id)[:32])
GSI_RECEIPT :  partition_key = receipt_id
```

The frontend's receiving panel must supply a `receipt_correlation_id` (a UUID generated
client-side and held in React state). The backend derives `receipt_id =
sha256(receipt_correlation_id)[:32]`. Replaying the same correlation ID is a no-op:
the backend performs a `ConditionExpression="attribute_not_exists(po_id)"` put and
returns the existing receipt on conflict (PUR-008 idempotency contract).

### 3.3 `suppliers` table (PUR-002)

Read-only from this page (supplier picker uses `GET /suppliers`):

```
PK  = supplier_id
SK  = "META"
GSI_STATUS :  partition_key = status
              sort_key      = created_at  (N)
```

### 3.4 No new tables

PUR-015 is a pure frontend ticket. No `scripts/local-ddb-init.py` changes, no
`app/core/settings.py` changes, no `app/core/tables.py` changes. All purchasing
table definitions, settings keys (`purchasing_scm_enabled`, `purchase_orders_table_name`,
`po_receipts_table_name`, `suppliers_table_name`, `supplier_products_table_name`,
`purchase_order_reorder_suggestions_enabled`), and `T.*` handles are established by
PUR-002 (none yet present in `app/core/settings.py` or `app/core/tables.py`).

## 4. API / Service Design

PUR-015 is a frontend-only ticket. There is no new backend service or router code;
this section describes the **frontend component API** (React component interfaces,
React Query key conventions, and mutation signatures).

### 4.1 React Query key conventions

| Key | Shape | Description |
|-----|-------|-------------|
| `["purchasing", "orders"]` | base | invalidated after any PO mutation |
| `["purchasing", "orders", {status, supplier_id}]` | list | scoped query for the list panel |
| `["purchasing", "order", po_id]` | detail | single PO + lines |
| `["purchasing", "suppliers"]` | list | supplier picker options |
| `["purchasing", "suggestions"]` | list | reorder suggestions |

Calls to `queryClient.invalidateQueries({ queryKey: ["purchasing", "orders"] })`
after any mutation (approve/reject/cancel/receive) will invalidate both the list and
any cached detail entries (React Query's prefix-matching).

### 4.2 Component structure

```
PurchaseOrdersAdmin.tsx
  ├── <PoListPanel>        — filter by status/supplier; renders rows with status badges
  ├── <PoDetailDrawer>     — Sheet slide-over showing PO header + line table
  │     └── <ReceivingPanel>  — enter quantities per line; calls receive mutation
  ├── <CreatePoDialog>     — Dialog to build a new PO (pick supplier, add lines)
  └── <ReorderSuggestionsPanel>  — shows suggestions; "Create draft PO" per suggestion
```

All are defined in a single file `PurchaseOrdersAdmin.tsx` (not split into
sub-files) following the `InventoryAdmin.tsx` single-file pattern.

### 4.3 Key function signatures (TypeScript)

```ts
// ── list query ──
const ordersQuery = useQuery({
  queryKey: ["purchasing", "orders", { status: statusFilter, supplier_id: supplierFilter }],
  queryFn: () => listPurchaseOrders({ status: statusFilter, supplier_id: supplierFilter }),
  enabled: allowed && isPurchasingScmEnabled() && (!!statusFilter || !!supplierFilter),
});

// ── supplier picker (for CreatePoDialog) ──
const suppliersQuery = useQuery({
  queryKey: ["purchasing", "suppliers"],
  queryFn: () => listSuppliers({ status: "active" }),
  enabled: allowed && isPurchasingScmEnabled(),
});

// ── detail query ──
const detailQuery = useQuery({
  queryKey: ["purchasing", "order", selectedPoId],
  queryFn: () => getPurchaseOrder(selectedPoId!),
  enabled: !!selectedPoId && allowed,
});

// ── reorder suggestions ──
const suggestionsQuery = useQuery({
  queryKey: ["purchasing", "suggestions"],
  queryFn: getReorderSuggestions,
  enabled: allowed && isPurchasingScmEnabled(),
});

// ── create PO ──
const createMut = useMutation({
  mutationFn: (body: PurchaseOrderIn) => createPurchaseOrder(body),
  onSuccess: () => {
    toast.success("Draft PO created");
    qc.invalidateQueries({ queryKey: ["purchasing", "orders"] });
    setCreateOpen(false);
  },
  onError: () => toast.error("Failed to create PO"),
});

// ── lifecycle transitions ──
type TransitionAction = "submit" | "approve" | "reject" | "cancel";
const transitionMut = useMutation({
  mutationFn: ({ po_id, action, reason }: { po_id: string; action: TransitionAction; reason?: string }) => {
    const fns = {
      submit: () => submitPurchaseOrder(po_id),
      approve: () => approvePurchaseOrder(po_id),
      reject: () => rejectPurchaseOrder(po_id, reason ? { reason } : undefined),
      cancel: () => cancelPurchaseOrder(po_id, reason ? { reason } : undefined),
    };
    return fns[action]();
  },
  onSuccess: (updated) => {
    toast.success(`PO ${updated.status}`);
    qc.invalidateQueries({ queryKey: ["purchasing", "orders"] });
    qc.setQueryData(["purchasing", "order", updated.po_id], updated);
  },
  onError: (err: unknown) => {
    const msg = (err as { response?: { data?: { detail?: string } } })
      ?.response?.data?.detail ?? "Transition failed";
    toast.error(msg);   // surfaces "Illegal transition" 409 text to admin
  },
});

// ── receive ──
const receiveMut = useMutation({
  mutationFn: ({
    po_id,
    lines,
    receipt_correlation_id,
  }: {
    po_id: string;
    lines: PoReceiveLineIn[];
    receipt_correlation_id: string;
  }) => receivePurchaseOrder(po_id, { lines, receipt_correlation_id }),
  onSuccess: (receipt) => {
    toast.success("Received — inventory updated");
    qc.invalidateQueries({ queryKey: ["purchasing", "orders"] });
    qc.setQueryData(["purchasing", "order", receipt.po.po_id], receipt.po);
    setReceiptCorrelationId(crypto.randomUUID());  // rotate for next receive
  },
  onError: (err: unknown) => {
    const detail = (err as { response?: { data?: { detail?: string } } })
      ?.response?.data?.detail;
    if (detail?.includes("over-receive")) {
      toast.error("Cannot receive more than ordered quantity");
    } else if (detail?.includes("409")) {
      toast.error("PO must be in approved/ordered/partially_received status");
    } else {
      toast.error("Receiving failed");
    }
  },
});

// ── create PO from suggestion ──
const createFromSuggestionMut = useMutation({
  mutationFn: (supplier_id: string) => createPoFromSuggestion(supplier_id),
  onSuccess: (po) => {
    toast.success(`Draft PO ${po.po_id.slice(0, 8)}… created`);
    qc.invalidateQueries({ queryKey: ["purchasing", "orders"] });
    qc.invalidateQueries({ queryKey: ["purchasing", "suggestions"] });
  },
  onError: () => toast.error("Failed to create PO from suggestion"),
});
```

### 4.4 `receipt_correlation_id` lifecycle

`receipt_correlation_id` is a stable UUID generated with `crypto.randomUUID()` and
stored in component state (`useState<string>(() => crypto.randomUUID())`). It is
passed as-is to `receivePurchaseOrder`. On a successful receipt, the component rotates
to a new UUID (`setReceiptCorrelationId(crypto.randomUUID())`) so the next receive
action gets a fresh idempotency key. On error the existing ID is retained — the user
may retry and the backend's idempotency guard prevents double-posting.

## 5. Detailed Behavior & Edge Cases

### 5.1 List panel — filters and pagination

The list panel renders a `<Table>` of PO rows. Two filter controls sit above it:

- **Status selector** (`<Select>`) with options: All, draft, submitted, approved,
  ordered, partially\_received, received, closed, rejected, cancelled.
- **Supplier selector** (`<Select>`) populated by `suppliersQuery.data.items` (active
  suppliers only). Shows supplier name + `supplier_id[:8]` suffix.

Both filters default to empty strings (no filter). Because the backend returns 422 if
both are absent, the `enabled` condition on `ordersQuery` requires at least one
filter to be set (`!!statusFilter || !!supplierFilter`). Before either filter is
chosen, the panel renders an `<EmptyState>` prompt: "Select a status or supplier to
browse purchase orders."

Pagination: the backend returns `next_token` in `PurchaseOrderListResp`. The list panel
uses `useState<string | undefined>()` for cursor and renders a "Load more" button when
`next_token` is present.

### 5.2 PO row — status badges

```ts
function statusBadge(status: PoStatus): JSX.Element {
  const map: Record<PoStatus, { label: string; variant: "default" | "outline" | "destructive" | "secondary" }> = {
    draft:              { label: "Draft",              variant: "secondary" },
    submitted:          { label: "Pending approval",   variant: "outline" },
    approved:           { label: "Approved",           variant: "default" },
    ordered:            { label: "Ordered",            variant: "default" },
    partially_received: { label: "Partial receipt",    variant: "outline" },
    received:           { label: "Received",           variant: "default" },
    closed:             { label: "Closed",             variant: "secondary" },
    rejected:           { label: "Rejected",           variant: "destructive" },
    cancelled:          { label: "Cancelled",          variant: "destructive" },
  };
  const { label, variant } = map[status] ?? { label: status, variant: "outline" };
  return <Badge variant={variant}>{label}</Badge>;
}
```

Badges update immediately after a transition via `qc.setQueryData` in `onSuccess`
(optimistic local update) without waiting for a list refetch.

### 5.3 PO detail drawer (`<Sheet>`)

Clicking any row in the list panel opens a `<Sheet>` (shadcn `sheet.tsx`) with the
full PO detail loaded via `detailQuery`. The sheet contains:

- Header section: supplier name (resolved from `suppliersQuery` by `supplier_id`),
  status badge, `po_id` (monospace, copyable), created date, subtotal.
- Lines table: columns — Line, SKU, Ordered qty, Received qty, Unit cost, Line total.
  Each row shows `quantity_received` vs `quantity_ordered` with a progress indicator.
- Action bar: buttons visible based on current status:
  - `draft` → "Submit for approval" button (`submit` transition, any session).
  - `submitted` → "Approve" + "Reject" buttons (admin only — hidden if not admin).
  - `approved` / `ordered` / `partially_received` → "Receive" button (opens
    `<ReceivingPanel>`).
  - Any non-terminal status → "Cancel" button (admin only).
  - Terminal (`received`, `closed`, `rejected`, `cancelled`) → no action buttons.

### 5.4 Receiving panel (`<ReceivingPanel>`)

The receiving panel is a `<div>` that replaces the action bar when the user clicks
"Receive". It renders one numeric `<Input>` per PO line, labelled with the SKU and
showing remaining quantity (`quantity_ordered - quantity_received`) as placeholder:

```
Line 1  SKU: WIDGET-A   Ordered: 100   Already received: 40   [  ] qty to receive
Line 2  SKU: GADGET-B   Ordered:  20   Already received:  0   [  ] qty to receive
```

Validation (client-side, before submission):
- Each entered value must be a positive integer.
- `entered + quantity_received <= quantity_ordered` — over-receive is blocked before
  the API call with an inline field error.
- At least one line must have a non-zero quantity.

On submit, `receiveMut.mutate({ po_id, lines: [{line_no, quantity}, ...], receipt_correlation_id })`.
Only lines with non-zero entered values are included in the `lines` array.

When `receiveMut.isPending`, the Submit button is replaced by a `<Loader2>` spinner.

After success, the panel collapses and the sheet re-renders the updated PO (lines
now show new `quantity_received` values; status badge may have changed to
`partially_received` or `received`).

### 5.5 Create PO dialog

The "New PO" button opens a `<Dialog>` with a multi-step form built with
React Hook Form + Zod:

**Step 1 — Select supplier**: A `<Select>` populated by `suppliersQuery`. Disabled
if no active suppliers exist (shows "No active suppliers — create one first" message
with link to the PUR-014 suppliers page).

**Step 2 — Add lines**: A dynamic field array (React Hook Form `useFieldArray`) where
each row has:
- `sku` (`<Input>`) — free text; validates non-empty, max 256 chars.
- `quantity_ordered` (`<Input type="number">`) — integer ≥ 1.
- `unit_cost_cents` (`<Input type="number">`) — optional; placeholder "Auto (from
  supplier pricing)"; if left blank the backend defaults from the supplier-product
  record (PUR-006 service).

Minimum one line required (`minLength: 1` in Zod). "Add line" button appends a row;
trash icon removes.

**Optional fields** (collapsible `<details>` section):
- `expected_delivery_date` (`<Input type="date">`).
- `correlation_id` (`<Input>`) — defaults to a UUID generated client-side; shown as
  a read-only field with a "Regenerate" button to let the user force a new ID if they
  want to re-submit with new data.

On submit, `createMut.mutate(body)`. The dialog closes and the newly created draft PO
appears at the top of the list (after query invalidation).

### 5.6 Reorder suggestions panel

A collapsible `<Card>` labeled "Reorder suggestions" at the bottom of the page.
Hidden when `PURCHASE_ORDER_REORDER_SUGGESTIONS_ENABLED` is false on the backend
(the endpoint 404s; `suggestionsQuery.error` is detected and the panel renders
a "Not enabled" notice instead of an error toast).

When data is available, renders:
- A table of suggestions grouped visually by supplier (sorted by `supplier_id`).
- Columns: SKU, Available, Reorder point, Suggested qty, Unit cost, Est. cost.
- Per-supplier "Create draft PO" button that calls `createFromSuggestionMut.mutate(supplier_id)`.

Warnings (SKUs with no supplier mapping) are rendered as a yellow `<Alert>` listing
the SKU strings.

### 5.7 Error and loading states

- `ordersQuery.isLoading` → `<Skeleton>` rows (3) in the table body.
- `ordersQuery.isError` → inline `<Alert variant="destructive">` with the error
  message; a "Retry" button calls `ordersQuery.refetch()`.
- `detailQuery.isLoading` → `<Skeleton>` within the open `<Sheet>`.
- 409 transition errors surface the backend `detail` string in `toast.error` (e.g.
  "Illegal transition from draft to received" gives the admin actionable feedback).
- 422 over-receive errors surface as a field-level validation message in the
  receiving panel (caught in `onError` by checking for `"over-receive"` in the detail
  string).

### 5.8 Approve/reject/cancel confirmations

Approve, reject, and cancel are destructive or irreversible actions. Each shows an
`<AlertDialog>` confirmation step:
- "Approve" → "Confirm approval — this PO will be sent to the supplier."
- "Reject" → includes a `<Textarea>` for rejection reason (forwarded as `reason` in
  `PoTransitionIn`); required field.
- "Cancel" → "Cancel this PO? Received quantities cannot be cancelled." The backend
  also enforces this (409 if any quantity received).

### 5.9 Flag-off behavior

If `isPurchasingScmEnabled()` returns false (env `VITE_PURCHASING_SCM_ENABLED` not
set or `false`), the component renders:

```tsx
return (
  <div className="p-6">
    <EmptyState
      icon={<ShoppingCart className="h-10 w-10" />}
      title="Purchase orders are not enabled"
      description="Enable the purchasing & SCM feature flag to manage purchase orders."
    />
  </div>
);
```

This guard runs before any React Query hook invocations are evaluated (all queries
have `enabled: allowed && isPurchasingScmEnabled()`), so no 404 network calls are
made when the flag is off.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007

PUR-015 contains no environment-branching logic. The component calls the same API
paths in dev (Vite proxy → `localhost:8000`) and prod (same frontend bundle, different
upstream). No `if (isDev)` branches.

### 7.2 Idempotency

Two idempotency keys flow through PUR-015:

**PO creation**: The `<CreatePoDialog>` generates a `correlation_id` UUID on mount
(`useState(() => crypto.randomUUID())`). It is shown to the user as a read-only
field. If the user submits the form, closes the dialog, and reopens it, the same UUID
is reused — the backend's `sha256(correlation_id)[:32]` idempotency guarantee (PUR-006
service, mirroring `app/services/commerce_order_service.py:67`,
`order_id = hashlib.sha256(corr.encode("utf-8")).hexdigest()[:32]`) means the
duplicate request returns the same PO. The "Regenerate" button mints a new UUID only
when the user explicitly wants a fresh PO.

**Receiving**: `receipt_correlation_id` is generated once per `<ReceivingPanel>`
mount and rotated on successful receipt (§4.4). This ensures that a double-click
on the submit button or a retry after a network timeout does not double-increment
inventory. The backend guard is `ConditionExpression="attribute_not_exists(po_id)"`
on the `po_receipts` row (PUR-008).

### 7.3 Security

**Role gating**: The page renders an `<EmptyState>` if
`canAccessGeneralAdminControls(accessToken)` returns false, before any queries run.
The backend independently enforces `require_admin_or_root_csrf` on all PO mutation
endpoints — the client-side guard is defense-in-depth only.

**CSRF**: The `api` client at `client.ts:178–182` attaches `X-CSRF-Token` from the
`ui_csrf` cookie on every request (no method guard in client code; backend enforces
CSRF only on non-GET mutations). No additional CSRF handling is needed in
PUR-015 components.

**Supplier data**: `unit_cost_cents`, supplier contact details, and PO subtotals are
staff-only. The component is not rendered for regular users; the route (PUR-016) is
not linked in any non-admin nav.

**Reject reason**: The rejection reason textarea is sent as `PoTransitionIn.reason`
(max 500 chars on the backend Pydantic model). The `<Textarea>` enforces `maxLength={500}`.

## 10. Open Questions / Assumptions

**A1 — `listPurchaseOrders` requires at least one filter**: The component is designed
to require at least one filter before firing the list query (`enabled: !!statusFilter
|| !!supplierFilter`). This is based on PUR-010's spec that the backend returns 422 on
an unfiltered list. If the backend is changed to allow unfiltered lists (e.g. bounded
by a default `limit`), the guard can be relaxed and a default "All recent POs" view
becomes possible. Confirm with PUR-010 implementer.

**A2 — `submit` auth level**: The backend `POST /{po_id}/submit` uses
`require_ui_session` (not admin-only) per PUR-010 spec §2. This means any
authenticated user who knows the `po_id` can submit it. The frontend gate
(`canAccessGeneralAdminControls`) hides the "Submit" button from non-admins in the
UI, but this is defense-in-depth only. If the business rule should be "only the
creating admin can submit", the backend route needs `require_admin_or_root_csrf`.
Assumption: admin-only UI gate is sufficient; verify with PUR-007/010 implementer.

**A3 — `unit_cost_cents` display**: The component shows `unit_cost_cents` as cents.
For display (`"$1.23"`) the component uses `(value / 100).toFixed(2)` inline in JSX.
This is consistent with the existing `CatalogPage` price display pattern. No shared
currency formatter exists in `frontend/src/lib/` as of reading; a local helper
`centsToDollars(cents: number): string` can be defined at the top of the file.

**A4 — Partial-receive re-entry**: After a partial receipt the user may want to
receive the remainder. The `<ReceivingPanel>` pre-populates the "qty to receive"
input placeholder with `quantity_ordered - quantity_received` (the remaining
balance). The user types the actual quantity. This is an assumption; an alternative
UX would be to pre-fill the input with the remaining balance. The pre-fill approach
risks accidental full receipt on a second partial — the placeholder approach is safer.

**A5 — `createPoFromSuggestion` body params**: PUR-012 spec §4.2 open question A6
notes the endpoint may accept an optional body with `currency` and
`expected_delivery_date`. The current design passes no body. If PUR-012 adds these as
body fields in the final implementation, the `<ReorderSuggestionsPanel>` will need a
per-suggestion form to collect them. Confirm with PUR-012 implementer before coding.

**A6 — Supplier name resolution in PO list**: The `PurchaseOrder` shape returns
`supplier_id` (not `supplier_name`). The list panel resolves names by looking up the
`suppliersQuery.data.items` array. This works when the number of distinct suppliers is
small (< 100, which is the default `listSuppliers` page size). For a large supplier
base, the lookup will miss suppliers on page 2+. Assumption: admin deployments will
have < 100 active suppliers at any one time; a more robust approach (e.g. denormalise
`supplier_name` onto the PO header in PUR-006) is a follow-up.

**A7 — Reject/cancel confirmation UX**: The `<AlertDialog>` confirmation is proposed
for approve, reject, and cancel. The "reject" flow includes a reason `<Textarea>`.
This could alternatively be a `<Dialog>` (more space). Either is acceptable; the
spec uses `<AlertDialog>` because it is already in the shadcn bundle
(`alert-dialog.tsx`) and its constrained width is fine for a short reason text.

**A8 — `isPurchasingReorderSuggestionsEnabled` frontend flag**: The reorder suggestions
panel is hidden based on the sub-flag. In practice, the panel will call
`getReorderSuggestions()` regardless of the client-side flag (the flag only controls
whether the panel renders). If the backend returns 404 (sub-flag off), the query
enters an error state and the panel shows a "Not enabled" notice. The client-side
flag is therefore only a render optimization; the backend is the authoritative gate.
