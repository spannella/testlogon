# MKT-003 — Marketing Pydantic models

## 1. Summary & Goal

MKT-003 adds all Pydantic request/response models for the marketing-campaigns module to `app/models.py`. These models are the shared vocabulary that every downstream MKT ticket (MKT-004 through MKT-011) consumes: campaign CRUD, contact-list management, party-segment rule evaluation, tracking-code management, and attribution rollup.

No DDB tables, no service logic, no router endpoints are introduced here — those are MKT-002 (settings/tables), MKT-004 (service CRUD), and MKT-011 (router registration). This ticket only produces importable, round-trippable Pydantic classes that other tickets can import from `app.models` without any circular dependency.

The acceptance bar is narrow and testable offline: every new model must pass `.model_validate({...}).model_dump()` round-trips, money fields must reject negatives, segment predicates must reject unknown attributes/operators, and the existing `CampaignCreateIn` (line 4565) and `CampaignUpdateIn` (line 4912) are untouched.

## 3. Data Model

MKT-003 is a pure-Python model ticket; it has no DDB schema changes. The DynamoDB table definitions are owned by MKT-002. This section documents only the field-level conventions that models enforce.

### Money fields

All money fields use `int` (cents). `budget_cents` is `ge=0` (zero is valid for awareness campaigns with no spend cap, unlike ads which require `ge=100`). No `Decimal` types are used; Pydantic coerces `float` to `int` via `ge=0` validation at model construction time.

### Timestamp fields

Input timestamps (`start_date`, `end_date`) are `Optional[int]` (Unix seconds). Output timestamps (`created_at`, `updated_at`) are `int` with `= 0` default to allow safe deserialization of legacy DDB items that predate a field.

### Status literals

Campaign status values come from the MKT-006 state machine:

```
"draft" | "scheduled" | "active" | "paused" | "completed" | "archived"
```

On `MarketingCampaignCreateIn`, `status` is not present — campaigns always start as `"draft"`. On `MarketingCampaignUpdateIn`, `status: Optional[str] = None` is accepted (no regex) because the service-level state machine in MKT-006 validates transitions; model-level rejection would duplicate that logic.

### Segment predicate validation

`VALID_SEGMENT_ATTRIBUTES` and `VALID_OPERATORS` are module-level sets defined in `app/models.py` near the `SegmentPredicate` class. A `@field_validator` on `SegmentPredicate.attribute` and `SegmentPredicate.operator` raises `ValueError` for unknown values, surfacing as HTTP 422 at the endpoint layer. This is the same pattern used for `CampaignCreateIn._validate_category` at `app/models.py:4585–4591` (✓).

### Tracking code slug

`TrackingCodeCreateIn.code_slug` is constrained to URL-safe characters: `Field(..., pattern=r"^[A-Za-z0-9_-]{3,50}$")`. This makes the slug safe for embedding in `GET /ui/marketing/t/{code_slug}` without URL-encoding.

#### `SegmentPredicate`

```python
VALID_SEGMENT_ATTRIBUTES: frozenset[str] = frozenset({
    "subscription_tier",
    "total_spend_cents",
    "profile_country",
    "profile_city",
})

VALID_SEGMENT_OPERATORS: frozenset[str] = frozenset({
    "eq", "neq", "gt", "gte", "lt", "lte", "in", "not_in",
})

class SegmentPredicate(BaseModel):
    attribute: str
    operator: str
    value: Any

    @field_validator("attribute")
    @classmethod
    def _validate_attribute(cls, v: str) -> str:
        if v not in VALID_SEGMENT_ATTRIBUTES:
            raise ValueError(
                f"Unknown segment attribute '{v}'. "
                f"Valid: {sorted(VALID_SEGMENT_ATTRIBUTES)}"
            )
        return v

    @field_validator("operator")
    @classmethod
    def _validate_operator(cls, v: str) -> str:
        if v not in VALID_SEGMENT_OPERATORS:
            raise ValueError(
                f"Unknown segment operator '{v}'. "
                f"Valid: {sorted(VALID_SEGMENT_OPERATORS)}"
            )
        return v
```

`VALID_SEGMENT_ATTRIBUTES` and `VALID_SEGMENT_OPERATORS` are module-level `frozenset` constants — not inline in the validator — so MKT-008's service can import and use them for evaluation logic without re-defining the allowlist. `value: Any` is intentional; the operator semantics determine the expected type (string for `eq`/`neq`, int for comparisons, list for `in`/`not_in`), and strict typing is deferred to the service's evaluator.

## 5. Detailed Behavior & Edge Cases

### `budget_cents` vs ads' minimum

`CampaignCreateIn` at `app/models.py:4568` enforces `ge=100` (minimum $1). `MarketingCampaignCreateIn` uses `ge=0` because marketing campaigns may be organic (contact-list blasts with no ad spend). A validator cross-checking "if budget_cents == 0 then ad_campaign_id must be None" is tempting but deferred to the service layer (MKT-004) — a model-level cross-field constraint would make `MarketingCampaignUpdateIn` awkward (you may update budget without touching `ad_campaign_id`).

### `promo_code_ids`, `contact_list_ids`, `segment_ids` as lists vs sets

These are `List[str]` not `Set[str]` to preserve insertion order in the DDB item (DDB stores them as DynamoDB Lists, which are ordered). Deduplication is enforced by the service (MKT-004/MKT-005) using a conditional put on each attach operation.

### `SegmentPredicate.value: Any`

The `Any` type is intentional and mirrors the `challenge_context: Dict[str, Any]` pattern at `app/models.py:28` (✓: `challenge_context: Dict[str, Any] = Field(default_factory=dict)`). Pydantic does not coerce `Any` — the value is stored as-is. For `"in"` and `"not_in"` operators the evaluator (MKT-008) expects a list; for `"gt"/"gte"/"lt"/"lte"` it expects an int. This is validated at evaluate-time, not at model-construction time, consistent with how the rest of the codebase handles flexible rule payloads.

### `TrackingCodeCreateIn.campaign_id` must reference an existing campaign

This constraint is enforced by the service (MKT-010's `create_tracking_code`) via a `get_campaign` call, not by the model. The model only checks `min_length=1`. An invalid `campaign_id` surfaces as HTTP 404/422 at the service layer.

### `ContactListMemberIn.party_id` ownership semantics

A list owner can add any `party_id` to their list regardless of whether that user is their contact. The `T.contacts` check (used by `seed_from_contacts` in MKT-007) is an optional convenience, not a requirement for `add_member`. The model does not enforce a contact-book relationship.

### Round-trip safety for DDB-originated data

DDB stores numbers as `Decimal`. All `int` fields on `*Out` models must be safe against `Decimal` input. The existing pattern at `app/models.py:4600–4608` uses plain `int` fields without explicit coercion — Pydantic v2 automatically coerces `Decimal` to `int` for `int`-typed fields in `model_validate` mode. No `@model_validator` Decimal coercion is needed here (the `MessageEncryptionEnvelope` pattern noted in CLAUDE.md is specific to nested structs, not top-level numeric fields).

### `CampaignAttributionOut.as_of` semantics

`as_of` is `now_ts()` at the moment `compute_attribution` is called (MKT-005). It is not cached or stored in DDB — each call to `GET /ui/marketing/campaigns/{id}/attribution` triggers a fresh read. The model exposes `as_of` so the frontend can show "as of N minutes ago" without computing the delta itself.

### Objective extension from ads module

`CampaignCreateIn.objective` accepts `awareness|traffic|conversions` (`app/models.py:4567`). `MarketingCampaignCreateIn` extends the set with `"retention"`. The two models are independent classes with independent validators; no shared base class is used (adding a base class would risk accidentally breaking `CampaignCreateIn` validation if the base changes — additive-only constraint).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity**: Pydantic models are pure Python with no AWS calls, no `if S.dev_mode` branching, no mock paths. They behave identically in dev and prod. No SECOPS-007 action is required for this ticket.

**Idempotency**: Model construction is inherently idempotent — calling `MarketingCampaignCreateIn.model_validate(data)` twice with the same input produces an equal result. The deterministic-id scheme (sha256 of `owner_id|name|created_bucket`) lives in the service layer (MKT-004), not the model.

**Security considerations for models**:

- `SegmentPredicate.attribute` and `.operator` are validated against explicit allowlists (`VALID_SEGMENT_ATTRIBUTES`, `VALID_SEGMENT_OPERATORS`) at model-construction time. An unknown attribute or operator raises `ValidationError` which FastAPI converts to HTTP 422 before any service code runs. This prevents injection of arbitrary DDB attribute names into the segment evaluator (MKT-008).
- `TrackingCodeCreateIn.code_slug` regex `^[A-Za-z0-9_-]{3,50}$` blocks slugs containing path separators (`/`), query separators (`?`), fragment markers (`#`), and whitespace, preventing URL-injection in the public visit redirect endpoint.
- `budget_cents: int = Field(..., ge=0)` and all other money fields use `ge=0`, so negative amounts are rejected at the model layer before reaching the service — no negative-balance exploit path is possible through the marketing module.
- `ContactListMemberIn.party_id: str = Field(..., min_length=1)` rejects empty strings that could be stored as `PARTY#` with no suffix in DDB.

## 10. Open Questions / Assumptions

1. **Assumption**: `objective` extends the ads module's set `(awareness|traffic|conversions)` with `"retention"`. If future campaigns require more objectives (e.g., `"lead_generation"`, `"brand_safety"`), the regex on both `MarketingCampaignCreateIn` and `MarketingCampaignUpdateIn` must be updated in tandem. A `Literal[...]` type would make the set more discoverable in IDEs but `str` + pattern is the established convention in this codebase (`app/models.py:4567`). Confirm objective set is final before MKT-011 ships.

2. **Assumption**: `VALID_SEGMENT_ATTRIBUTES` is the authoritative allowlist for predicate evaluation (MKT-008 imports this frozenset). The initial set `{"subscription_tier", "total_spend_cents", "profile_country", "profile_city"}` is minimal MVP. New attributes should be added to this frozenset (and the evaluator's dispatch table in MKT-008) in a single coordinated PR to avoid a validator accepting an attribute the evaluator cannot handle.

3. **Open question**: Should `SegmentPredicate.value` have a union type (`str | int | List[str | int]`) instead of `Any`? This would give better IDE and schema documentation. Drawback: Pydantic v2 union validation for `List[...]` requires careful discriminator config to avoid over-coercion. Current recommendation: keep `Any`, add a `@model_validator(mode="after")` in MKT-008's service if type-safety is needed at evaluation time.

4. **Assumption**: `ContactListOut.member_count` is a denormalized counter on the META row, maintained by `add_member`/`remove_member` in MKT-007 via DDB `ADD` expression. This avoids a `COUNT` query on each list read. The counter may drift if `remove_member` fails mid-operation; a reconciliation scan is a known follow-up.

5. **Assumption**: `CampaignAttributionOut` is always computed on-demand (MKT-005) and never cached in DDB. For campaigns with many promo codes (e.g., 100+), `get_promo_stats` is called per code — up to 100 sequential DDB queries. This is acceptable for MVP. A cached summary row (SK `ATTRIBUTION#latest`) is a performance follow-up once usage patterns are clear.

6. **Open question**: The `ContactListMemberOut.suppressed` field exposes the opt-out status of other users to the list owner. Confirm this is acceptable from a privacy standpoint (the list owner learns that a specific `party_id` has opted out). Alternative: filter suppressed members from `*Out` responses and return only `suppressed: false` members to callers, surfacing the count delta implicitly. Needs PM/legal sign-off before MKT-007 ships.

7. **Assumption**: `TrackingCodeOut` exposes `owner_id` in the response. This means the `GET /ui/marketing/tracking-codes/{slug}` endpoint (MKT-011) reveals the owner of a code. For public codes (e.g., embedded in external landing pages), this leaks the owner's `user_sub`. If that is a concern, `owner_id` should be omitted from `TrackingCodeOut` and only included in an internal/admin variant. Flagged for MKT-011 to decide.
