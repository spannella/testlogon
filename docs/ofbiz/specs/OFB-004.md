# OFB-004 — Soft reservations on add-to-cart / checkout

**Type:** Feature | **Priority:** P0 | **Estimate:** 5 days
**Depends on:** OFB-003 (inventory item & stock-level model — already landed)
**Downstream:** OFB-005 (low-stock alerts), OFB-006 (inventory admin UI), OFB-007 (E2E tests)

---

## 1. Summary & Goal

OFB-004 wires the reservation lifecycle already implemented in `app/services/inventory.py` into the shopping cart's add-to-cart and checkout paths, and starts the background expiry loop that reclaims stranded reservations.

The goal is to replace the purchase-time stock decrement (a `stock_count >= :qty` conditional update at `app/services/shoppingcart.py:515–537` with manual rollback at line 524) with a three-phase lifecycle:

1. **Reserve** — at `add_catalog_item` time, call `inventory.reserve(sku, qty, cart_id=...)`. `available` drops; `on_hand` is unchanged. The reservation row tracks the expiry TTL.
2. **Commit** — inside `purchase_cart`, after the cart status is flipped to `PURCHASED`, call `inventory.commit_reservation(reservation_id)`. `on_hand` and `reserved` both drop by the reserved quantity; `available` is already correct.
3. **Release** — when a cart is deleted or expires without purchase, call `inventory.release_reservation(reservation_id)`. `reserved` drops; `available` is restored.

Additionally, a TTL-release background loop (`start_reservation_expiry_task`) calls `inventory.expire_due_reservations()` on a configurable interval, reclaiming any reservations whose `expires_at` has passed without a commit or explicit release.

All changes are **additive and flag-gated** behind `S.inventory_reservations_enabled` (`INVENTORY_RESERVATIONS_ENABLED`, default `false`). With the flag off, every code path in `shoppingcart.py` is byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 The reservation service is complete but unwired

`app/services/inventory.py` already contains the full OFB-004 service layer:

- `reserve(sku, qty, *, location_id, user_sub, cart_id, ttl_seconds)` — single-writer conditional `available >= :q` update, writes a reservation row (`T.reservations`) (`inventory.py:339–411`).
- `commit_reservation(reservation_id)` — flips reservation to `committed`, decrements `on_hand` and `reserved` (`inventory.py:456–489`).
- `release_reservation(reservation_id, *, reason, terminal_status)` — flips to `released` or `expired`, restores `available` (`inventory.py:492–535`).
- `expire_due_reservations(*, now, limit)` — queries `GSI_EXPIRY` (partition `SCHED#ACTIVE`, numeric sort key `expires_at`) and calls `release_reservation(..., terminal_status="expired")` for each overdue row (`inventory.py:538–562`).
- `_close_reservation` — shared conditional update that flips `status = active → terminal`, guarded by `ConditionExpression="#status = :active"` so concurrent commit/release/expire calls are idempotent (`inventory.py:434–453`).

None of these functions are called from `app/services/shoppingcart.py` today. A search for `reserve`, `commit_reservation`, and `release_reservation` in `shoppingcart.py` returns zero hits.

### 2.2 The existing decrement-at-purchase path

`purchase_cart` (`app/services/shoppingcart.py:474–734`) currently loops over cart line items and for each item that has a `category_id` and `item_id`, it performs:

```python
T.catalog.update_item(
    Key=catalog_key,
    UpdateExpression="SET stock_count = stock_count - :qty, stock_updated_at = :now",
    ConditionExpression="stock_count >= :qty",
    ExpressionAttributeValues={":qty": qty, ":now": _now_iso()},
)
```
(`app/services/shoppingcart.py:515–519`)

On `ConditionalCheckFailedException`, it loops back and manually restores all previously decremented rows (`app/services/shoppingcart.py:523–532`). This is a read-modify-write spread across multiple DynamoDB operations with no atomicity across the loop — a race window exists between lines 524 and 532.

### 2.3 add_catalog_item does not touch stock

`add_catalog_item` (`app/services/shoppingcart.py:370–397`) reads the catalog item to build a cart payload but does not decrement or reserve stock. It sets `sku = f"catalog:{item_id}"` on the cart item record (`line 391`). This is the canonical SKU format that the reservation service should use as its `sku` key for catalog items.

### 2.4 Cart item records carry no reservation_id field today

`_item_from_item` (`app/services/shoppingcart.py:79–104`) does not emit a `reservation_id` field. `ShoppingCartItemOut` (`app/models.py:956–970`) has no `reservation_id`. The cart item DDB row has no `reservation_id` column today. This field must be added additively.

### 2.5 delete_cart does not release reservations

`delete_cart` (`app/services/shoppingcart.py:448–458`) deletes the cart row and its item rows in a batch write. It does not look for or release any reservations. With OFB-004 active, deleting a cart must iterate item rows and call `release_reservation` for each item that carries a `reservation_id`.

### 2.6 Background expiry loop exists for cart abandonment, not for reservations

`_cart_abandonment_loop` in `app/routers/shoppingcart.py:323` and `start_cart_abandonment_task` at line 358 demonstrate the pattern: a plain `asyncio.create_task` wrapping an `async while True: ... await asyncio.sleep(interval)` loop, registered via `app.add_event_handler("startup", ...)` in `app/main.py:985`. The reservation expiry loop must follow the same pattern.

### 2.7 Tables, settings, and handles already exist

- `T.inventory` at `app/core/tables.py:317`, wired at line `569`.
- `T.reservations` at `app/core/tables.py:318`, wired at line `570`.
- `S.inventory_reservations_enabled` at `app/core/settings.py:839`, default `false`.
- `S.inventory_reservation_ttl_seconds` at `app/core/settings.py:840`, default `1800` (30 min).
- `GSI_EXPIRY` on `T.reservations` with partition `gsi_expiry_pk` (S) and sort `expires_at` (N, `attr_types={"expires_at": "N"}` at `scripts/local-ddb-init.py:2477`).

No new DynamoDB tables or settings infrastructure is needed; only a new `INVENTORY_RESERVATION_SCAN_INTERVAL_SEC` setting (details in Section 6) and the `reservation_id` attribute on cart item rows (backward-compatible: absent on legacy rows).

## 4. API / Service Design

### 4.1 Modified service functions in `app/services/shoppingcart.py`

All modifications are gated by `_inv_enabled()` (a thin `bool(getattr(S, "inventory_reservations_enabled", False))` check, mirroring `inventory._flag_on()`). With `_inv_enabled()` returning `False`, every new code path is skipped and the function behaves exactly as before.

#### 4.1.1 `add_catalog_item` — reserve on add

```python
def add_catalog_item(
    user_sub: str,
    cart_id: str,
    *,
    category_id: str,
    item_id: str,
    quantity: int = 1,
    location_id: str = "warehouse",  # matches inventory.DEFAULT_LOCATION (inventory.py:43)
) -> Dict[str, Any]:
```

> **Note:** The constant `DEFAULT_INVENTORY_LOCATION` does not exist in `shoppingcart.py`. Either define `DEFAULT_INVENTORY_LOCATION = "warehouse"` at the top of `shoppingcart.py`, or import `DEFAULT_LOCATION` from `app.services.inventory`. The string `"warehouse"` is the canonical default (`inventory.py:43`).

**New behavior (flag on):**

After the existing catalog lookup and currency check, before calling `add_item`, attempt `inventory.reserve(sku, quantity, user_sub=user_sub, cart_id=cart_id)`. The `sku` is `f"catalog:{item_id}"` (same format already used by `add_item` at `shoppingcart.py:391`).

If `inventory.get_inventory(sku)` returns `None` (no inventory record for this SKU), the item is treated as **unlimited stock** and the reservation path is skipped (matching the existing `if sc is None: continue` guard at `shoppingcart.py:511–512`). Note: `reserve()` itself raises 409 on a missing inventory record (`inventory.py:358–359`), so the caller must gate on `get_inventory` returning `None` before calling `reserve`.

On a successful reserve, write `reservation_id` from the returned `ReservationOut` onto the cart item payload before passing it to `add_item`. The payload dict gains `"reservation_id": res["reservation_id"]`.

On 409 from `reserve` (out-of-stock), re-raise as-is — the existing "Item is out of stock" 409 response path is preserved.

**If the item already exists in the cart** (quantity increment case): the existing `add_item` code path sums quantities. With OFB-004, the existing reservation is released first (`inventory.release_reservation(existing_reservation_id)` if `existing.get("reservation_id")`), then a fresh reservation for the new total quantity is created. This avoids quantity drift between the reservation and the cart row.

#### 4.1.2 `purchase_cart` — commit on success, skip legacy decrement

```python
def purchase_cart(
    user_sub: str,
    cart_id: str,
    *,
    idempotency_key: str | None = None,
    promo_code: str | None = None,
    promo_code_id: str | None = None,
) -> Dict[str, Any]:
```

**New behavior (flag on):**

The current `# ── SHOP-001: Stock validation + atomic decrement ──` block at `shoppingcart.py:498–538` is **skipped entirely** when `_inv_enabled()` is `True`. Instead:

1. Before transitioning the cart to `PURCHASED`, call `_verify_reservations(user_sub, cart_id, items)` (new private helper, see 4.1.4). This validates that every item with a `reservation_id` has an `active` reservation and that the reserved quantity matches the cart quantity. Any mismatch (expired, quantity changed, missing) raises 409 with `code="reservation_expired"` and the cart remains `OPEN` so the customer can re-add items.

2. After the cart status update succeeds (after `T.shopping_cart.update_item` at `shoppingcart.py:621–627`), commit all reservations: iterate items, call `inventory.commit_reservation(item["reservation_id"])` for each item that carries one. Commit calls are best-effort (`try/except`): a commit failure does NOT roll back the cart purchase (the order has been created). A failed commit is logged and surfaces as an audit event `inventory.commit_failed`.

The existing post-purchase flow (entitlement orchestration, promo redemption, `record_cart_purchase`, invoice creation) is unchanged.

#### 4.1.3 `delete_cart` — release on delete

```python
def delete_cart(user_sub: str, cart_id: str) -> None:
```

**New behavior (flag on):**

Before issuing the batch delete, iterate item rows and for each item that carries a `reservation_id`, call `inventory.release_reservation(reservation_id, reason="cart_deleted", user_sub=user_sub)` (best-effort, swallows exceptions). Releases happen before the batch delete so that if the process crashes between release and delete, the reservation is already gone and the expiry loop will not double-count it.

`expire_abandoned_carts` in `shoppingcart.py:912` transitions carts to `EXPIRED` status but does not delete items. The reservation expiry background loop handles those via TTL; no change needed here.

#### 4.1.4 `_verify_reservations` — pre-purchase validation helper (new)

```python
def _verify_reservations(
    user_sub: str,
    cart_id: str,
    items: List[Dict[str, Any]],
) -> None:
    """Raise 409 if any active reservation is expired or quantity-mismatched.
    No-op if _inv_enabled() is False."""
```

For each item in `items` that has a `reservation_id`:

1. Call `inventory.get_reservation(reservation_id)`.
2. If `None` or `status != "active"`, raise `HTTPException(409, detail={"code": "reservation_expired", "message": "One or more items are no longer reserved. Please refresh your cart."})`.
3. If `res["quantity"] != item["quantity"]`, raise 409 with `code="reservation_quantity_mismatch"`.

Items without a `reservation_id` (legacy rows or unlimited-stock items) pass through unchecked.

`_item_from_item` (`shoppingcart.py:77–104`) gains one line:

This is unconditional (not flag-gated): existing rows without the field return nothing, new rows with the field return it. `ShoppingCartItemOut` gains `reservation_id: Optional[str] = None`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Reserve on add — SKU derivation

`add_catalog_item` sets `sku = f"catalog:{item_id}"` before calling `inventory.reserve`. This matches the SKU used by `add_item` and stored on cart item rows (`shoppingcart.py:391`). The inventory record for a catalog item is expected to be keyed on this same `sku` value. OFB-003's catalog-to-inventory bridge (the hook in `app/routers/catalog.py`) must use the same `f"catalog:{item_id}"` SKU format when provisioning the inventory record.

### 5.2 Concurrent oversell race

Two concurrent checkouts of the last unit both call `reserve("catalog:X", 1, ...)`. Both read the inventory row atomically. The first call's `update_item` with `ConditionExpression="available >= :q"` succeeds and sets `available = 0`. The second call arrives at the same condition with the stale `available = 1` but DynamoDB returns `ConditionalCheckFailedException` because the row has since changed; `inventory.reserve` re-reads... no, it does not retry — it raises `HTTPException(409)` immediately (`app/services/inventory.py:371`). The caller's 409 bubbles up from `add_catalog_item` as "Item is out of stock", which is the existing behavior for the decrement path at `shoppingcart.py:534`.

### 5.3 Quantity update to an existing cart item

`add_item` (`shoppingcart.py:311`) is also called when the same SKU already exists in the cart (it increments quantity). `add_catalog_item` calls `add_item` internally. OFB-004 must detect the existing item before calling `add_item`:

1. Read `T.shopping_cart.get_item(Key=item_key)` to check for an existing reservation.
2. If `existing["reservation_id"]` is present: release old reservation (quantity = `existing["quantity"]`), then reserve the new total quantity (`existing["quantity"] + payload["quantity"]`).
3. If the new reserve fails (no stock for the delta), re-reserve the original quantity as a recovery step (best-effort). If re-reserve also fails (e.g., the original units were just claimed), return 409.

### 5.4 Item removal from cart (`set_item_quantity` to 0, `decrement_item`)

`set_item_quantity(user_sub, cart_id, sku, 0)` calls `T.shopping_cart.delete_item(Key=key)` (`shoppingcart.py:410`). OFB-004 must: if flag on and item has `reservation_id`, call `release_reservation` before deleting.

`decrement_item` similarly deletes the row when `new_qty <= 0` (`shoppingcart.py:435`). When `new_qty > 0`, a quantity decrease must: release old reservation, re-reserve at the new quantity. A re-reserve failure at this point is handled by returning 409 and leaving the quantity unchanged.

### 5.5 purchase_cart idempotency (replay)

The existing idempotency pattern (`shoppingcart.py:483–492`, `629–640`) returns the stored purchase result if `status == "PURCHASED"`. With OFB-004, commits are already done in the first pass; a replay returns early before the commit loop is reached. The `_close_reservation` guard (`status = active` condition) ensures that if the cart status was set to PURCHASED but the process crashed before commits completed, a replay of `purchase_cart` must attempt the commits again. But `_close_reservation` returns `None` on replay (already committed), and `commit_reservation` returns the existing record — no double-decrement.

### 5.6 Reservation TTL vs. cart TTL

Reservation TTL (`S.inventory_reservation_ttl_seconds`, default 1800 s = 30 min) is shorter than cart TTL (`S.cart_ttl_days * 86400`, default 30 days). After a reservation expires, the cart item row still exists but its `reservation_id` no longer points to an `active` reservation. `_verify_reservations` catches this at checkout time and returns 409, prompting the buyer to re-add the item. The buyer experience: re-adding the item triggers a fresh `reserve` call; if stock is still available, a new reservation is created and `reservation_id` on the cart item is updated. If no stock, 409 is returned.

### 5.7 Non-catalog items (direct `add_item` SKUs, digital goods)

Items added via `POST /ui/shoppingcart/carts/{cart_id}/items` (`ShoppingCartItemIn`, not `CatalogCartItemIn`) do not go through `add_catalog_item` and do not have a `category_id`/`item_id`. These items have no inventory record (they are typically digital or bespoke) and the reservation path is not invoked. Their `reservation_id` field remains absent.

### 5.8 `expire_abandoned_carts` and reservation cleanup

`expire_abandoned_carts` (`shoppingcart.py:912`) transitions OPEN carts older than `expire_hours` to status `EXPIRED`. It does NOT delete item rows. Reservations on expired carts are cleaned up by `expire_due_reservations` when their `expires_at` passes (within the TTL window). There is no immediate release on cart expiry — the TTL loop is the backstop. If the operator sets `inventory_reservation_ttl_seconds` shorter than the cart expiry window, reservations will self-heal before the cart is processed.

### 5.9 `add_catalog_item` for zero-stock catalog items (unlimited)

If `inventory.get_inventory(sku)` returns `None`, the item is treated as unlimited and no reservation is attempted. The existing cart item write proceeds without a `reservation_id`. This maintains backward compatibility for catalog items that existed before OFB-003 provisioned inventory records for them.

### 5.10 Audit trail

Every reserve, commit, release, and expire call emits an `audit_event` via `inventory._audit` (`inventory.py:92–98`). The event names are `inventory.reserve`, `inventory.commit_reservation`, `inventory.release_reservation`, and `inventory.release_reservation` (with `reason="ttl_expired"` and `terminal_status="expired"`). A commit failure in the post-purchase path emits an additional `inventory.commit_failed` event written directly from `purchase_cart`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

The reservation service (`app/services/inventory.py`) already documents its SECOPS-007 compliance: "identical code in dev (moto / local DDB) and prod (real DDB); no `dev_mode` branch in the business logic" (`inventory.py:27–29`). All new code in `shoppingcart.py` follows the same rule: no `if S.dev_mode` branches in the reservation integration path.

The `expire_due_reservations` function and `_close_reservation` are DDB-only. No S3, Cognito, or external HTTP calls are made.

### 7.2 Idempotency

- **`reserve`**: Not inherently idempotent (each call creates a new reservation row). The caller (`add_catalog_item`) must check for an existing `reservation_id` before calling reserve to avoid double-reservations.
- **`commit_reservation`**: Idempotent via `_close_reservation`'s `status = active` guard. Replay returns the existing committed record without touching inventory.
- **`release_reservation`**: Idempotent via the same guard. Double-release is a no-op.
- **`expire_due_reservations`**: Safe under concurrent runs — each reservation's `_close_reservation` CAS ensures exactly one winner.
- **`_verify_reservations`**: Read-only; idempotent by definition.

### 7.3 Security

- Reservation ownership is enforced: `GET /ui/inventory/reservations/{id}` and `POST .../release` both check `res["user_sub"] not in (session["user_sub"], "system")` and raise 404 on mismatch (`app/routers/inventory.py:112–113`, `123–124`). A user cannot release another user's reservation via the API. (Note: the check allows `"system"` as a special-case service-internal owner, enabling the expiry loop's `user_sub="system"` to call `release_reservation` without ownership conflicts.)
- The internal service calls inside `purchase_cart` and `delete_cart` do not re-check ownership because `user_sub` is already validated at the cart level (both functions start with `get_cart(user_sub, cart_id)` which returns 404 for non-owned carts).
- `reservation_id` values are random UUID hex (128 bits of entropy), not guessable.
- The `gsi_expiry_pk` attribute is removed from the DDB row on terminal transition (`REMOVE gsi_expiry_pk` in `_close_reservation` at `inventory.py:443`), so the expiry GSI never accumulates terminal rows.

## 8. Backward Compatibility & Migration

### 8.1 Flag-off behavior unchanged

All changes to `shoppingcart.py` are conditional on `_inv_enabled()`. With the flag off:

- `add_catalog_item`: no `reserve` call, no `reservation_id` on cart items — identical to today.
- `purchase_cart`: the `SHOP-001` decrement block runs as today.
- `delete_cart`: no release calls.
- The expiry loop function is never registered as a startup task.

### 8.2 Existing cart items with no reservation_id

After the flag is enabled, legacy cart items that were added before OFB-004 have no `reservation_id`. `_verify_reservations` skips items without `reservation_id` (the check is gated on `item.get("reservation_id")`). `purchase_cart` for a mixed cart (some items with reservations, some without) still falls back to the legacy `SHOP-001` decrement for legacy items and commits reservations for new items. This is handled by: when flag is on, the `SHOP-001` loop runs only for items that have NO `reservation_id`, and `_commit_reservations` runs for items that DO.

### 8.3 No DynamoDB schema migration required

The `reservation_id` attribute is written at `put_item` time; no schema change or `UpdateTable` is needed. DDB's schemaless nature handles sparse attributes. The `inventory` and `reservations` tables already exist from OFB-002/003.

### 8.4 Enabling the flag in production

The recommended order:

1. Deploy the code with flag off (zero behavior change).
2. Run OFB-003's catalog-to-inventory sync to populate inventory records for existing catalog items with `stock_count > 0`.
3. Enable `INVENTORY_RESERVATIONS_ENABLED=true`.
4. New add-to-cart operations now reserve; existing legacy cart sessions without `reservation_id` fall back gracefully.

## 10. Open Questions / Assumptions

1. **Assumption: catalog SKU format.** The spec assumes the inventory record for a catalog item is keyed on `sku = f"catalog:{item_id}"`. This must match how OFB-003's catalog-to-inventory bridge provisions inventory records in `app/routers/catalog.py`. If the bridge uses a different SKU format, the `reserve` call in `add_catalog_item` will always find no inventory record (unlimited path). **Verify against the OFB-003 implementation before finalizing.**

2. **Assumption: mixed cart handling.** The spec proposes running the legacy `SHOP-001` decrement loop for items without a `reservation_id` alongside the new commit path for items with one. This dual-path logic must be tested carefully to avoid double-counting. An alternative is to block purchase of carts containing a mix of reservation-backed and non-reservation-backed catalog items (return 409 "Cart contains stale items, please re-add"). The simpler dual-path approach is assumed here.

3. **Open: quantity decrease re-reserve failure recovery.** If `set_item_quantity` decreases quantity and the re-reserve at the lower quantity fails (e.g., another user claimed units in the window between release and re-reserve), what is the UX? Current proposal: return 409, leave the item quantity unchanged. The old reservation is already released, so available is temporarily higher than it should be. An alternative is to hold the reservation before releasing. Clarification needed.

4. **Open: `add_item` direct path.** Direct `add_item` calls (not via `add_catalog_item`) bypass the reservation path entirely because they have no `category_id`/`item_id`. This is correct for digital/bespoke items. If physical items are ever added via the direct `add_item` path with a valid inventory SKU, they will not be reserved. Documenting this as a known limitation for this milestone.

5. **Assumption: no new HTTP endpoints.** The spec adds no new endpoints. The internal reservation manipulation (reserve, commit, release) happens entirely in service-layer calls from within `shoppingcart.py`. If a customer-facing "view my reservation" UI is needed, it can be served by the existing `GET /ui/inventory/reservations/{id}` endpoint — the `reservation_id` is now surfaced on `ShoppingCartItemOut`.

6. **Open: reservation expiry loop startup behavior.** The loop currently checks `_inv_enabled()` at registration time (via `start_reservation_expiry_task`). If the flag is toggled at runtime (env var reload), the loop does not start retroactively. This matches the behavior of all other startup task patterns in the codebase (e.g., `start_cart_abandonment_task`). Acceptable for this milestone.

7. **Assumption: `GSI_CART` on reservations table is not needed.** Looking up all active reservations for a given `cart_id` would require a new GSI. The current spec does not add this because: (a) `delete_cart` already reads all item rows for the cart via `SK.begins_with(f"CART#{cart_id}#ITEM#")`, and each item row carries the `reservation_id`; (b) `_verify_reservations` also reads from the item rows. No GSI for `cart_id` on the reservations table is needed.
