# FXA-013 — Maintenance work-order router

## 1. Summary & Goal

FXA-013 extends `app/routers/fixed_assets.py` (created by FXA-007) with four HTTP endpoints that expose the maintenance work-order service layer (`app/services/asset_maintenance.py`, created by FXA-012) to admin callers. The router already exists; this ticket appends the work-order handlers to it.

After this ticket:

- `POST /ui/fixed-assets/{asset_id}/work-orders` — create a work order against an active asset.
- `GET /ui/fixed-assets/{asset_id}/work-orders` — list work orders for a specific asset, paginated.
- `GET /ui/fixed-assets/work-orders` — cross-asset open/in-progress queue, filterable by status, paginated.
- `PATCH /ui/fixed-assets/work-orders/{work_order_id}` — transition a work order's lifecycle state and/or reassign.

All four endpoints return 503 when `FIXED_ASSETS_ENABLED` is off; when on, all require at least `ADMIN` or `ROOT` role (`require_admin_or_root_csrf` for mutating calls, `require_admin_or_root` for reads). Non-admin callers receive 403. Unauthenticated callers receive 401.

The route-ordering constraint from CLAUDE.md (literal paths before dynamic captures) is critical here: the literal `/work-orders` queue path and the `/work-orders/{work_order_id}` path must both be declared **before** the `/{asset_id}/...` patterns to prevent FastAPI from swallowing the literal `"work-orders"` segment as an `asset_id` path parameter.

Existing shop, cart, orders, billing, inventory, and all other paths are byte-for-byte unchanged when `FIXED_ASSETS_ENABLED` is false (the default).

### 2.7 `PATCH /work-orders/{work_order_id}` and the `asset_id` resolution problem

The `maintenance_orders` DynamoDB table (per `docs/ofbiz/specs/FXA-012.md:3.1`) uses `pk = "ASSET#{asset_id}"` as its hash key and `sk = "WO#{work_order_id}"` as its range key. A `PATCH` by `work_order_id` alone cannot construct the DDB primary key without `asset_id`. The FXA-012 spec raises this explicitly as Open Question 5 (§10) and assumes option (a): `asset_id` is carried in the request body as a field of `MaintenanceOrderTransitionIn`. FXA-013 implements this assumption.

## 5. Detailed Behavior & Edge Cases

### 5.1 `GET /ui/fixed-assets/work-orders` — cross-asset queue

The queue endpoint is the primary tool for an admin reviewing all outstanding maintenance work. Default behavior (no query params) returns the 50 most recently created `"open"` work orders across all assets.

1. `maint._require_enabled()` — 503 if flag off.
2. `require_admin_or_root` — 403 if not admin/root.
3. `status` defaults to `"open"` but callers can pass `status=in_progress` for work in progress, or `status=completed` / `status=cancelled` to audit closed orders.
4. `list_work_orders(wo_status=status, ...)` queries `GSI_WO_STATUS` via the service (Mode B in FXA-012 §5.3). `ScanIndexForward=False` returns most-recently-created orders first.
5. If `assignee_sub` is also supplied, the service applies it as a `FilterExpression` over the `GSI_WO_STATUS` results. Per CLAUDE.md "DDB FilterExpression doesn't reduce page size" gotcha: the service fetches up to `limit` items from DDB's pre-filter page and then applies the in-memory filter — the caller may receive fewer than `limit` items even when more matching items exist beyond the `cursor`. The caller must follow `cursor` to paginate completely.
6. Response: `MaintenanceOrderListOut(items=[...], count=N, cursor=str|None)`.
7. When `status` is an unrecognized value (e.g. `"broken"`), the service queries `GSI_WO_STATUS` with that value as the partition key. No matching rows exist, so the result is an empty list — not an error. The router does NOT validate the status string against a whitelist; unrecognized statuses return `items=[], count=0, cursor=null`.

### 5.2 `PATCH /ui/fixed-assets/work-orders/{work_order_id}` — transition / reassign

The `PATCH` endpoint is the single mutating work-order operation: it transitions lifecycle state and optionally reassigns the work order.

1. `maint._require_enabled()` — 503 if flag off.
2. `require_admin_or_root_csrf` — 403 if not admin/root; CSRF enforced for cookie sessions (`app/auth/policy.py:100–106`).
3. FastAPI validates `MaintenanceOrderTransitionIn`: `asset_id` must be non-empty; `target_status` must be one of `"in_progress"`, `"completed"`, `"cancelled"` (Pydantic `Literal` field); `cost_cents` must be `>= 0` when present.
4. Router validates: if `cost_cents` is present in the body and `body.target_status != "completed"`, return `HTTPException(422, "cost_cents is only valid when target_status is completed")`. This addresses FXA-012 Open Question 2 — the service stores `cost_cents` unconditionally, but the router rejects the combination early. The check is:
   ```python
   if body.cost_cents is not None and body.target_status != "completed":
       raise HTTPException(status_code=422, detail="cost_cents only valid on completed transition")
   ```
5. `maint.transition_work_order(body.asset_id, work_order_id, body, user.sub)`:
   - 404 if work order not found.
   - 409 `"illegal_transition"` if the state machine forbids the requested transition.
   - 409 `"concurrent_transition"` if a concurrent writer won the optimistic lock (per `docs/ofbiz/specs/FXA-012.md:5.4`).
6. Response: `MaintenanceOrderOut` reflecting the post-transition state.

**Idempotency replay**: If the client retries a `PATCH` after receiving a 409 `"concurrent_transition"`, it should re-`GET` the current state before retrying. The endpoint does not guarantee idempotency on the `PATCH` path — transitions are point-in-time state changes, not idempotent writes.

### 5.3 `POST /ui/fixed-assets/{asset_id}/work-orders` — create

1. `maint._require_enabled()` — 503 if flag off.
2. `require_admin_or_root_csrf` — 403 if not admin/root; CSRF enforced.
3. FastAPI validates `MaintenanceOrderIn`: `title` 1–200 chars; `description` max 2000; `scheduled_for` is a Unix timestamp (not validated by Pydantic beyond being an `int`; negative values are accepted at the model layer — the service does not reject them).
4. `maint.create_work_order(asset_id, body, user.sub)`:
   - 404 if asset does not exist (service calls `get_asset` from `app/services/fixed_assets.py`).
   - 400 `"asset_disposed"` if the asset has `status == "disposed"`.
   - On `ConditionalCheckFailedException` (duplicate `correlation_id`), returns the existing work order with HTTP 201 (idempotent replay — same body, same status code, per the FXA-007 create-asset precedent at `docs/ofbiz/specs/FXA-007.md:264`).
5. Response: `MaintenanceOrderOut` with `wo_status="open"`, `cost_cents=None`, `completed_at=None`. HTTP 201.

### 5.4 `GET /ui/fixed-assets/{asset_id}/work-orders` — per-asset list

1. `maint._require_enabled()` — 503 if flag off.
2. `require_admin_or_root` — 403 if not admin/root.
3. `maint.list_work_orders(asset_id=asset_id, wo_status=status, ...)` queries the base table partition `pk = "ASSET#{asset_id}"` (Mode A in `docs/ofbiz/specs/FXA-012.md:5.3`). This is a bounded-partition query with `ScanIndexForward=False` (newest first).
4. If `asset_id` does not exist or has no work orders, the service returns `items=[], count=0, cursor=null` — the router does not verify that the asset exists before calling the service. This means an invalid `asset_id` silently returns an empty list rather than a 404. This is acceptable: the admin is already authenticated; the empty list is unambiguous.
5. Response: `MaintenanceOrderListOut(items=[...], count=N, cursor=str|None)`.
6. Optional `status` query parameter (`?status=open`) is applied as a `FilterExpression` over the partition scan. Per the CLAUDE.md DDB FilterExpression gotcha, a sparse `status` filter can return fewer than `limit` items from a single DDB page — the caller must follow `cursor` for a complete list.

### 5.5 Route-ordering conflict avoidance

A concrete illustration of why the ordering matters: with the prefix `/ui/fixed-assets`, a request to `GET /ui/fixed-assets/work-orders?status=open` has the path segment `work-orders` immediately after the prefix. If `GET "/{asset_id}/work-orders"` were registered before `GET "/work-orders"`, FastAPI would resolve `asset_id = "work-orders"` and route to the per-asset list handler rather than the cross-asset queue — returning an empty list for a non-existent asset `"work-orders"` instead of the intended queue.

The correct declaration order within `fixed_assets_router` (all four FXA-013 handlers must precede all `/{asset_id}` FXA-007 handlers):

```
1. GET  /work-orders                        ← FXA-013, literal
2. PATCH /work-orders/{work_order_id}       ← FXA-013, literal prefix
3. POST ""                                  ← FXA-007
4. GET  ""                                  ← FXA-007
5. POST /{asset_id}/work-orders             ← FXA-013, dynamic
6. GET  /{asset_id}/work-orders             ← FXA-013, dynamic
7. GET  /{asset_id}/schedule                ← FXA-007
8. POST /{asset_id}/dispose                 ← FXA-007
9. GET  /{asset_id}                         ← FXA-007
10. PATCH /{asset_id}                       ← FXA-007
```

Steps 5–6 (the per-asset work-order routes) must also come before steps 7–10 because both `/{asset_id}/work-orders` and `/{asset_id}/schedule` are two-segment paths under `/{asset_id}`. FastAPI differentiates them by the second segment (`work-orders` vs `schedule`), so their relative order among themselves is irrelevant for correctness — but placing them above the bare `/{asset_id}` single-segment routes is required.

### 5.6 `status` query param name collision

Both `list_work_orders_queue` (`GET /work-orders`) and `list_work_orders_for_asset` (`GET /{asset_id}/work-orders`) use the query parameter name `status` (not `wo_status`) for caller ergonomics. Internally, the service function parameter is `wo_status`. The router maps `status → wo_status` at the call site. This keeps the HTTP API consistent with REST conventions while keeping the service parameter name aligned with the DDB attribute name.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

The router contains no `if S.dev_mode` branches. All handlers call through `app/services/asset_maintenance.py` which itself contains no `dev_mode` branches (per `docs/ofbiz/specs/FXA-012.md:7.1`). All DDB I/O uses DynamoDB Local in dev (port 8001), moto in tests, and real DynamoDB in prod — the same code path in all environments (SECOPS-007). The `encode_cursor` / `decode_cursor` functions in `app/core/cursor.py:94–103` already handle `Decimal` from the boto3 resource API in all environments.

### 7.2 Idempotency

| Endpoint | Mechanism |
|---|---|
| `POST /{asset_id}/work-orders` | Delegated to `create_work_order`: deterministic `work_order_id = sha256(corr)[:32]`; `attribute_not_exists(sk)` conditional put; replay returns existing row with HTTP 201 |
| `PATCH /work-orders/{work_order_id}` | **Not idempotent at the HTTP layer.** The service uses `ConditionExpression="wo_status = :current"` to prevent double-apply; a retry after a successful transition will receive `ConditionalCheckFailedException` → HTTP 409 `"concurrent_transition"`. | `GET /work-orders` | Read-only; inherently idempotent. |
| `GET /{asset_id}/work-orders` | Read-only; inherently idempotent. |

### 7.3 Security

**Role enforcement.** Every handler requires `ADMIN` or `ROOT` role. `require_admin_or_root_csrf` (`app/auth/policy.py:100–106`) is used for `POST` and `PATCH`; `require_admin_or_root` (`app/auth/policy.py:67–68`) is used for `GET`. Non-admin users receive 403 before any service function executes.

**CSRF.** `require_admin_or_root_csrf` calls `enforce_cookie_csrf` (`app/auth/policy.py:71–97`): cookie-auth non-GET requests must carry `x-csrf-token` matching `ui_csrf`. Bearer-auth requests bypass CSRF per `enforce_cookie_csrf`'s no-session-cookie early return at `app/auth/policy.py:87–89`.

**Ownership scope.** The `create_work_order` handler passes `user.sub` as `actor_sub` to the service. The service calls `get_asset(actor_sub, asset_id)` to confirm the asset exists and belongs to that admin. If the asset belongs to a different `owner_sub`, the service raises HTTP 404 (`"asset_not_found"`). This prevents an admin from creating work orders against another admin's assets.

**`PATCH` `asset_id` in body.** The body field `asset_id` (needed to construct the DDB primary key, per §2.7) is validated by Pydantic (`min_length=1, max_length=64`). There is no authorization check that `body.asset_id` matches the asset the calling admin owns — the service will raise 404 if the asset does not exist or does not belong to the actor. This is the same ownership boundary as the `GET /{asset_id}` handler.

**No money movement.** `cost_cents` is stored as metadata only. No calls to `app/services/billing_shared.new_ledger_entry`, `app/routers/billing.refund_payment`, or any GL function are made. The audit events written by the service (`alerts.audit_event`, `app/services/alerts.py:644`) are the only write side-effect beyond the `maintenance_orders` table.

**Input size bounds.** `title` max 200 chars, `description` max 2000 chars (enforced by Pydantic `Field(max_length=...)` on `MaintenanceOrderIn`). `limit` is capped at 200 (`Query(ge=1, le=200)`). These bounds prevent oversized payloads from reaching DDB.

## 10. Open Questions / Assumptions

1. **`MaintenanceOrderTransitionIn.asset_id` field presence.** The spec assumes `asset_id` is added to `MaintenanceOrderTransitionIn` by FXA-004 (or, if FXA-004 did not include it, by FXA-013 itself). If `asset_id` is absent from the model, the `PATCH /work-orders/{work_order_id}` endpoint cannot resolve the DDB primary key. This is the most critical assumption in the spec and must be verified before implementation begins.

2. **Route-ordering in the existing `fixed_assets.py`.** This spec assumes FXA-007 was implemented strictly following `docs/ofbiz/specs/FXA-007.md:233–242`. If the existing handler order differs, the insertion point for FXA-013 handlers must be adjusted — the invariant is that `/work-orders` literal handlers appear before any `/{asset_id}` dynamic handlers, regardless of the FXA-007 handler order among themselves.

3. **`list_work_orders` with no filter raises 400.** The queue endpoint defaults `status="open"` so in practice it always supplies a `wo_status` filter. The `GET /{asset_id}/work-orders` endpoint always supplies `asset_id`. There is no code path through the router that results in all three of `asset_id`, `wo_status`, and `assignee_sub` being `None` — the service's 400 guard (FXA-012 §5.3) is therefore unreachable from the FXA-013 router. This is by design; the guard exists as a service-level safety net for future direct callers.

4. **`GET /{asset_id}/work-orders` does not 404 on unknown asset.** If the caller supplies an `asset_id` that does not exist, the service returns an empty list rather than 404. This is a deliberate tradeoff: verifying the asset exists requires an additional DDB `get_item` call on `T.fixed_assets` before the work-order query, which adds latency for the common path (valid asset, some work orders). A 404 for an unknown asset would be marginally more RESTful but is not worth the cost. Assumption: the admin UI calling this endpoint always constructs the URL from a known asset record.

5. **Admin cross-asset queue pagination with sparse `FilterExpression`.** When `assignee_sub` is combined with `wo_status` on the queue endpoint, the DDB `FilterExpression` does not reduce the page size (CLAUDE.md gotcha). On a table with many open orders and few assigned to a specific person, a caller may receive `items=[]` with a non-null `cursor` — the cursor points to the next DDB page, which may contain matching items. The spec accepts this behavior (it matches the behavior of every other sparse-filter endpoint in the codebase). The assumption is that the admin frontend follows cursors until `cursor=null`.

6. **`status` query param defaulting to `"open"` on the queue endpoint.** The default `status="open"` means `GET /ui/fixed-assets/work-orders` without any query params returns only open orders. This is the highest-value default for the "work order backlog" use case. If an admin wants all statuses, they must call the endpoint multiple times or the frontend must make parallel requests. No `status=all` wildcard is provided by the service. Assumption: the frontend handles multi-status display via parallel or sequential calls.

7. **`MaintenanceOrderListOut` in `app/models.py`.** If FXA-004 did not define this wrapper model, FXA-013 must add it. The fields are `items: List[MaintenanceOrderOut]`, `count: int`, `cursor: Optional[str]`. It is a simple envelope with no validation beyond type checking.
