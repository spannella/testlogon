# FAC-011 — Fulfillment router (registered in main.py)

## 1. Summary & Goal

FAC-011 creates `app/routers/fulfillment.py` — the single FastAPI router that
exposes the entire warehouse-fulfillment HTTP surface to the outside world —
and wires it into `app/main.py` alongside the existing OFBiz family. This
ticket is the first time the Milestone 3 and 4 services (transfers, receiving,
picking, packing, shipping) become reachable over the network.

The router has five responsibilities:

1. **Flag gate** — every handler calls a module-level `_require_enabled()`
   shim that delegates to `fac._require_enabled()` (same one-liner pattern as
   `app/routers/inventory.py:32–33`) so mounting the router with
   `FACILITY_FULFILLMENT_ENABLED=false` is a no-op: every path returns 404.

2. **Role split** — warehouse-operator mutations (create transfer, advance,
   complete, cancel transfer; receive shipment; generate picklist; confirm pick;
   pack; ship) use `require_admin_or_root_csrf` (`app/auth/policy.py:100–106`);
   all read endpoints use `require_ui_session`
   (`app/services/sessions.py:require_ui_session`). This mirrors the auth import
   pattern in `app/routers/inventory.py:17–18,27`.

3. **Thin delegation** — each handler validates the request via the FAC-003
   Pydantic model, calls the appropriate service function from FAC-006, FAC-007,
   FAC-008, FAC-009, or FAC-010, maps the returned dict to the `Out` model, and
   returns it. Zero business logic lives in the router.

4. **No prefix ambiguity** — transfer endpoints live under
   `/ui/fulfillment/transfers`; receiving under `/ui/fulfillment/receipts`;
   picklist under `/ui/fulfillment/picklists`; shipment under
   `/ui/fulfillment/shipments`. The FAC-005 `facilities_router` retains its own
   `/ui/facilities` prefix; only the `/ui/facilities/transfers` alternative
   noted in the ticket description is **not used** (consolidating everything
   under `/ui/fulfillment` keeps the auth boundary in one router file).

5. **`main.py` registration** — `fulfillment_router` is imported and included
   immediately after the `facilities_router` line, keeping the OFBiz router
   block contiguous at `app/main.py:314` / `app/main.py:880`.

No DynamoDB tables, settings keys, or Pydantic models are added by this ticket
(those are FAC-002 and FAC-003 respectively). No frontend changes ship with
FAC-011; that is deferred to FAC-012/FAC-013.

## 3. Data Model

FAC-011 introduces no new DynamoDB tables, GSIs, `attr_types` overrides,
settings keys, or `T.*` handles. All DynamoDB access is delegated entirely to
the service layer. The relevant table schemas (all created by FAC-002) are
summarised below for reference when writing tests.

**`transfers`** (`T.transfers`): PK=`transfer_id` (S), SK=`sk` (S).

`sk="META"` header; `sk="LINE#{n}"` lines.

`attr_types={"created_at": "N", "shipped_at": "N"}`. (FAC-009 / `docs/ofbiz/specs/FAC-009.md:200–212`)

`scripts/local-ddb-init.py` is **untouched** by FAC-011.

## 4. API / Service Design

### 4.1 Router declaration

```python
# app/routers/fulfillment.py
fulfillment_router = APIRouter(prefix="/ui/fulfillment", tags=["fulfillment"])
```

The prefix `/ui/fulfillment` is consistent with the OFBiz family and matches
the FAC-006 spec's router placement (`docs/ofbiz/specs/FAC-006.md:271`).

### 4.2 Module boilerplate

```python
"""Fulfillment router — transfers, receiving, picklist, pack, ship
(ADR-001, FAC-006..FAC-010, Milestone 3/4).

Additive + flag-gated (FACILITY_FULFILLMENT_ENABLED, default OFF). Every
handler short-circuits to 404 when the flag is off. Zero business logic
lives here — all logic is delegated to the service layer.

Role model (SECOPS-007 / ADR §Security):
  * Warehouse-operator mutations → require_admin_or_root_csrf.
  * Read endpoints → require_ui_session.
"""
from __future__ import annotations

from typing import Optional

from fastapi import APIRouter, Depends, HTTPException, Query

from app.auth.deps import AuthenticatedUser
from app.auth.policy import require_admin_or_root_csrf
from app.models import (
    # Transfer
    TransferIn, TransferOut,
    # Receiving
    ReceiveIn, ReceiptOut,
    # Picklist
    PicklistOut, ConfirmPickIn,
    # Packing
    PackPacklistIn, ShipmentOut,
    # Shipping
    ShipIn,
)
from app.services import facilities as fac
from app.services import transfers as xfr
from app.services import receiving as rcv
from app.services import picking as pck
from app.services import packing as pak
from app.services import shipping_fulfillment as shp
from app.services.sessions import require_ui_session

fulfillment_router = APIRouter(prefix="/ui/fulfillment", tags=["fulfillment"])


def _require_enabled() -> None:
    fac._require_enabled()
```

### 4.3 Transfer endpoints

All transfer mutations delegate to `app/services/transfers.py` (FAC-006).
The full service API surface is documented in `docs/ofbiz/specs/FAC-006.md:157–291`.

#### `POST /ui/fulfillment/transfers` — create transfer

```python
@fulfillment_router.post("/transfers", response_model=TransferOut, status_code=201)
async def create_transfer_endpoint(
    body: TransferIn,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> TransferOut:
    _require_enabled()
    rec = xfr.create_transfer(
        from_facility_id=body.from_facility_id,
        from_location_id=body.from_location_id,
        to_facility_id=body.to_facility_id,
        to_location_id=body.to_location_id,
        lines=[ln.model_dump() for ln in body.lines],
        notes=body.notes,
        idempotency_key=body.idempotency_key,
        owner_sub=user.sub,
    )
    return TransferOut(**rec)
```

**Auth**: `require_admin_or_root_csrf` — only warehouse admins/root may
initiate transfers. `owner_sub` is always the authenticated session user.

#### `GET /ui/fulfillment/transfers/{transfer_id}` — fetch transfer

```python
@fulfillment_router.get("/transfers/{transfer_id}", response_model=TransferOut)
async def get_transfer_endpoint(
    transfer_id: str,
    session=Depends(require_ui_session),
) -> TransferOut:
    _require_enabled()
    rec = xfr.get_transfer(transfer_id)
    if rec is None:
        raise HTTPException(status_code=404, detail="Transfer not found")
    return TransferOut(**rec)
```

**Auth**: `require_ui_session` — any authenticated user may read a transfer.
Ownership restriction (e.g. only the owning admin sees it) is deferred;
the read is currently unscoped so any session-authenticated user can fetch
by ID. Admin-only scoping can be added in a subsequent ticket.

#### `GET /ui/fulfillment/transfers` — list transfers

```python
@fulfillment_router.get("/transfers")
async def list_transfers_endpoint(
    status: Optional[str] = Query(default=None,
        pattern="^(requested|in_transit|completed|cancelled)$"),
    limit: int = Query(default=50, ge=1, le=200),
    cursor: Optional[str] = Query(default=None),
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
):
    _require_enabled()
    return xfr.list_transfers(
        status_filter=status, limit=limit, cursor=cursor
    )
```

**Auth**: `require_admin_or_root_csrf` — bulk transfer listing is admin-only.

#### `POST /ui/fulfillment/transfers/{transfer_id}/advance` — requested → in_transit

```python
@fulfillment_router.post("/transfers/{transfer_id}/advance", response_model=TransferOut)
async def advance_transfer_endpoint(
    transfer_id: str,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> TransferOut:
    _require_enabled()
    rec = xfr.advance_to_in_transit(transfer_id, actor_sub=user.sub)
    return TransferOut(**rec)
```

#### `POST /ui/fulfillment/transfers/{transfer_id}/complete` — in_transit → completed

```python
@fulfillment_router.post("/transfers/{transfer_id}/complete", response_model=TransferOut)
async def complete_transfer_endpoint(
    transfer_id: str,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> TransferOut:
    _require_enabled()
    rec = xfr.complete_transfer(transfer_id, actor_sub=user.sub)
    return TransferOut(**rec)
```

**Note**: `complete_transfer` atomically decrements the source location and
increments the destination via `inventory.adjust` pairs (FAC-006 §5); this is
the step that actually moves stock. The router carries no knowledge of this —
it delegates entirely.

#### `POST /ui/fulfillment/transfers/{transfer_id}/cancel`

```python
@fulfillment_router.post("/transfers/{transfer_id}/cancel", response_model=TransferOut)
async def cancel_transfer_endpoint(
    transfer_id: str,
    body: TransferCancelIn | None = None,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> TransferOut:
    _require_enabled()
    rec = xfr.cancel_transfer(
        transfer_id,
        actor_sub=user.sub,
        reason=body.reason if body else None,
    )
    return TransferOut(**rec)
```

`TransferCancelIn` is a minimal model: `class TransferCancelIn(BaseModel): reason: Optional[str] = None`. Because it exists only as a convenience wrapper it can live directly in `fulfillment.py` or in `app/models.py` — either is acceptable; placing it in `app/models.py` keeps all models colocated.

### 4.4 Receiving endpoints

All receiving delegates to `app/services/receiving.py` (FAC-007).

#### `POST /ui/fulfillment/receipts` — receive inbound goods

```python
@fulfillment_router.post("/receipts", response_model=ReceiptOut, status_code=201)
async def receive_shipment_endpoint(
    body: ReceiveIn,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> ReceiptOut:
    _require_enabled()
    rec = rcv.receive_shipment(
        facility_id=body.facility_id,
        location_id=body.location_id,
        lines=[ln.model_dump() for ln in body.lines],
        po_id=body.po_id,
        correlation_id=body.correlation_id,
        actor_sub=user.sub,
    )
    return ReceiptOut(**rec)
```

**Idempotency**: `correlation_id` is caller-supplied; the service derives
`receipt_id = sha256(correlation_id)[:32]` and uses
`ConditionExpression="attribute_not_exists(receipt_id)"` so re-submits are
no-ops (FAC-007 §4.2 deterministic-id pattern). The router passes
`correlation_id` through transparently.

### 4.9 `require_admin_or_root_csrf` — how it works

Defined at `app/auth/policy.py:100–106`:

```python
async def require_admin_or_root_csrf(
    request: Request,
    user: AuthenticatedUser = Depends(get_authenticated_user),
) -> AuthenticatedUser:
    enforce_cookie_csrf(request)
    return require_roles(user, {Role.ADMIN, Role.ROOT})
```

Cookie-auth non-GET requests must carry `x-csrf-token: <token>` matching the
`ui_csrf` cookie value. The CSRF validation logic lives at
`app/auth/policy.py:94–97` (within `enforce_cookie_csrf` which starts at line 71).
Bearer-auth requests skip CSRF (`app/auth/policy.py:87–89`).
A `role < ADMIN` user gets `HTTPException(403)` via `require_roles`
(`app/auth/policy.py:49–53`).

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off guarantees

With `FACILITY_FULFILLMENT_ENABLED=false` (the default):

- The router is mounted via `app.include_router(fulfillment_router)` unconditionally
  (same as `inventory_router`), so it appears in `GET /openapi.json` with its
  full schema. This is intentional: tooling that inspects the schema before
  enabling the flag will see the surface.
- Every handler's first statement is `_require_enabled()`, which calls
  `fac._require_enabled()`, which raises `HTTPException(status_code=404,
  detail="Facility fulfillment is not enabled")`. No service is ever called,
  no DynamoDB table is touched, and no side effects occur.
- The existing shop, cart, orders, billing, inventory, reservations, returns,
  and facilities paths are byte-for-byte unchanged.

### 5.2 Path collision — orders/{order_id}/picklists vs orders/{order_id}/shipments

Both paths share the `/orders/{order_id}` prefix. FastAPI's route-declaration
order determines priority. Since the two paths differ at the third segment
(`/picklists` vs `/shipments`) there is no collision — FastAPI resolves both
correctly regardless of declaration order.

The `/facilities/{facility_id}/receipts` path similarly does not collide with
`/facilities/{facility_id}` (which is on the separate `facilities_router`
under `/ui/facilities`), because these are entirely separate router prefixes
(`/ui/fulfillment` vs `/ui/facilities`).

### 5.3 Transfer `complete` — the stock-movement step

`POST /ui/fulfillment/transfers/{transfer_id}/complete` is the only endpoint
in this router that triggers a pair of `inventory.adjust` calls (via
`xfr.complete_transfer`). The 409 that propagates when the source location
would overdraw (`available < qty`) comes from `app/services/inventory.py:256–260`
and surfaces directly to the HTTP client with no wrapping in the router. The
router does not catch or suppress this.

Idempotency: `xfr.complete_transfer` guards the `in_transit → completed`
transition with a `ConditionExpression="#status = :in_transit"` conditional
update (FAC-006 spec §4.1). A replay after completion returns the existing
record without re-running the inventory adjusts. The router is agnostic to
this; it always calls `complete_transfer` and returns whatever the service
returns.

### 5.4 Receiving — `correlation_id` pass-through

`POST /ui/fulfillment/receipts` requires a caller-supplied `correlation_id`
in `ReceiveIn`. The router does not generate, validate, or inspect this
value beyond basic Pydantic field validation (non-empty string, max 256 chars).
Idempotency is entirely the service's responsibility:
`receipt_id = sha256(correlation_id)[:32]` and
`ConditionExpression="attribute_not_exists(receipt_id)"` (FAC-007 §4.2).

If the `correlation_id` field is absent from `ReceiveIn` (optional by
FAC-003 design), the service must generate a random one — this is the service's
contract, not the router's. The router passes `body.correlation_id` through
and accepts `None`.

### 5.5 Pick confirmation — line_no path parameter

`line_no` is a path parameter of type `int`. FastAPI validates it as a
non-negative integer. The service (`pck.confirm_pick`) raises
`HTTPException(404)` if the `LINE#{line_no}` row does not exist. The router
propagates this unchanged.

`picked_qty` in `ConfirmPickIn` is validated `ge=0` (FAC-003 spec): a zero
value represents a fully short-picked line.

### 5.6 Packing — overlapping shipment/orders paths

The `/orders/{order_id}/shipments` and `/orders/{order_id}/picklists` GET
endpoints share the `/orders/{order_id}` prefix stub. FastAPI resolution is
correct because the third path segment disambiguates. However, both handlers
must be declared before any static path under `/orders/` would shadow a dynamic
one. The recommended declaration order:

```
/orders/{order_id}/picklists   # declared first
/orders/{order_id}/shipments   # declared second
```

No static `/orders/` prefixes exist in the router, so no shadowing concern
applies.

### 5.7 Ship — fulfillment event emission

`shp.ship_shipment` (FAC-010) is responsible for emitting the fulfillment
event that the Order-lifecycle module (`ORD`) consumes to advance the order
to `shipped`. The router does not know about or interact with the event
system — it calls `shp.ship_shipment(...)` and returns the result. If the
event emission fails (best-effort in the service), the router still returns
200 to the client with the updated `ShipmentOut`.

### 5.8 404 vs 403 disambiguation

- **Flag off** → 404 `"Facility fulfillment is not enabled"` (from `_require_enabled`).
- **Not found** → 404 `"<Resource> not found"` (explicit `raise HTTPException(404, ...)` in the handler after checking the service returned `None`).
- **Insufficient role** → 403 from `require_admin_or_root_csrf` (via `require_roles`, `app/auth/policy.py:49–53`).
- **CSRF failure** → 403 `"Missing CSRF token"` / `"CSRF validation failed"` (from `enforce_cookie_csrf`, `app/auth/policy.py:94–97`).
- **Business invariant violated** (overdraw, illegal transition, over-pack) → 409 propagated from the service.

### 5.9 No `status_code=204` on cancel/complete

All action endpoints return the updated resource (200 by default) rather than
`204 No Content`. This allows the caller to immediately read the new state
without a separate GET and mirrors the pattern in `app/routers/returns_rma.py`
where every admin action (approve, reject, receive, refund, close) returns
a `ReturnOut` (`app/routers/returns_rma.py:69–118`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

`fulfillment.py` contains **no** `dev_mode` or `S.dev_mode` branch. Auth
enforcement (`require_admin_or_root_csrf`, `require_ui_session`) runs
identically in dev (DynamoDB Local port 8001, moto S3/Cognito) and prod (real
DynamoDB, real Cognito). The `_require_enabled()` shim uses `getattr(S, ...)`,
which works with both the real singleton and the moto-backed test singleton
mutated via `object.__setattr__`. No test-only path exists in router code.

### Idempotency

The router itself is stateless and carries no idempotency logic. Each
service function owns its own idempotency:

- **Transfers** — `create_transfer` uses `sha256(idempotency_key)[:32]` or
  `uuid4().hex`; `complete_transfer` guards on `status = in_transit`.
- **Receiving** — `receive_shipment` guards with
  `ConditionExpression="attribute_not_exists(receipt_id)"` on
  `sha256(correlation_id)`.
- **Picklist confirm** — `_confirm_line` conditions on `line_status = :open`.
- **Pack** — `pack_picklist` conditions on `status = :picked`.
- **Ship** — `ship_shipment` conditions on `status = :packed` (or `draft`,
  per FAC-010).

The router passes all caller-supplied idempotency keys (`correlation_id`,
`idempotency_key`) through to the service unchanged and without generating
alternatives.

### Security

- **Auth boundaries are router-layer only.** Service functions accept plain
  `actor_sub: str` parameters and do not enforce role checks. This is
  consistent with every other OFBiz service function (e.g.
  `app/services/inventory.py:209` — `def adjust(sku, delta, reason, *, location_id, user_sub)`
  accepts `user_sub` as a plain string). The router is the sole auth gate.

- **CSRF** — `require_admin_or_root_csrf` calls `enforce_cookie_csrf(request)`
  before the role check (`app/auth/policy.py:100–106`). Cookie-auth mutation
  requests that omit the `x-csrf-token` header get 403 immediately.
  Bearer-auth API clients (no `ui_session` cookie) skip CSRF
  (`app/auth/policy.py:87–89` — early return when session cookie absent).

- **Non-admin read** — transfer/picklist/shipment GET endpoints use
  `require_ui_session` (any authenticated user). This is appropriate for
  read-only access; if row-level access control is needed (e.g. a customer
  should only see their own order's shipments) it must be added to the
  relevant `list_*` service functions as a `user_sub` filter, not in the
  router.

- **No customer PII** in transfers, receipts, picklists, or shipments. The
  only user-identity field stored is `owner_sub` / `actor_sub` (an opaque
  UUID sub) on the header rows. No name, email, or address fields flow
  through this router.

## 10. Open Questions / Assumptions

1. **`TransferCancelIn` placement**: The spec places this lightweight model
   (`reason: Optional[str]`) in `app/models.py` alongside the other FAC-003
   models. An alternative is to define it inline in `fulfillment.py`. The
   `app/models.py` placement is preferred for consistency (all request/response
   models are in one file per project convention).

2. **Read-endpoint ownership scope**: `GET /ui/fulfillment/transfers/{id}` uses
   `require_ui_session`, meaning any authenticated user can fetch any transfer by
   ID. This matches how `GET /ui/inventory/items/{sku}` and
   `GET /ui/returns/{return_id}` work. If row-level isolation is needed
   (warehouse operator A should not see operator B's transfers), the service's
   `get_transfer` must add an ownership check. This is deferred.

3. **`/ui/facilities/transfers` vs `/ui/fulfillment/transfers`**: The ticket
   description lists both as possibilities. This spec uses
   `/ui/fulfillment/transfers` exclusively — one router, one prefix, one import.
   If the frontend team needs `/ui/facilities/transfers` for URL aesthetics,
   the facilities_router can be extended in a follow-up without modifying
   fulfillment.py.

4. **`list_transfers` auth**: The spec requires `require_admin_or_root_csrf`
   for `GET /ui/fulfillment/transfers` (bulk list). This is conservative and
   matches the `GET /ui/inventory/low-stock` admin-only pattern at
   `app/routers/inventory.py:79–86`. If a non-admin should be able to list their
   own transfers (filtered by `owner_sub`), a `require_ui_session` variant
   with a service-side `owner_sub=session["user_sub"]` filter is the correct
   approach.

5. **`ShipIn` model** — FAC-003 must define `ShipIn` with at least
   `carrier: str` and `tracking_number: str`. This spec assumes FAC-003 has done
   so. If `ShipIn` is missing from FAC-003 it must be added before FAC-011 lands
   (or defined inline in `fulfillment.py` as a one-off).

6. **`ConfirmPickIn` model** — FAC-003 must define `ConfirmPickIn` with
   `picked_qty: int = Field(ge=0)`. Same note as above.

7. **`GeneratePicklistIn` model** — FAC-003 must define `GeneratePicklistIn`
   with at minimum `order_id: str`, `facility_id: str`, and
   `location_id: Optional[str]`.

8. **`status_code=201` on receiving** — `POST /ui/fulfillment/receipts`
   returns 201 Created even on an idempotent replay (the service returns the
   existing receipt). This is consistent with how
   `app/services/commerce_order_service.py` handles idempotent order creation
   (returns the existing record without raising). If the caller needs to
   distinguish first-write from replay, a response header (e.g.
   `X-Idempotent-Replay: true`) can be added in a follow-up.

9. **`list_receipts_for_facility` auth** — requires `require_admin_or_root_csrf`
   (admin-only) on the assumption that receipt lists are operational data, not
   customer-facing. If a facility operator (non-admin role) needs to list
   receipts, a dedicated `require_warehouse_operator` scope (via
   `require_admin_scope`) should be defined in FAC-002.

10. **`cancel_shipment` — reservation release propagation**: `shp.cancel_shipment`
    (FAC-010) is responsible for calling `inventory.release_reservation` for any
    active reservations on the cancelled shipment's picklist. The router passes
    through any 409 from the service if a release fails. This is acceptable: the
    HTTP client gets a clear error rather than silent data inconsistency.
