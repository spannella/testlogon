# SHP-012 — Tracking-number/status on shipments (reuse carrier_tracking)

## 1. Summary & Goal

SHP-012 bridges the first-class `shipments` table (created by SHP-008, governed by the state
machine in SHP-010) into the existing carrier-tracking infrastructure so that incoming carrier
status updates advance a shipment's status rather than only updating the flat
`purchase_transactions.shipping` sub-map.

The three concrete deliverables are:

1. **Refactor `apply_tracking_result`** in `app/services/carrier_tracking.py` so it can target
   either a `purchase_transactions` row (unchanged legacy path) **or** a `shipments` row
   (new path). Both paths share `map_carrier_status` (`:84`), the idempotent old==new
   short-circuit (`:163–168`), and the `send_delivery_alert` call on first-delivery (`:192–194`).
   Zero change to the existing transaction path.

2. **Add `find_shipment_by_tracking(tracking_number)`** to `app/services/shipments.py` — a
   GSI-backed O(1) lookup that replaces the scan-loop fallback currently used by
   `purchase_history.find_transaction_by_tracking` (`:595–620`). This lets the webhook receiver
   and the polling layer resolve a shipment without a full-table scan.

3. **Add `apply_tracking_result_to_shipment(shipment, result)`** — the shipment-flavored
   counterpart of `apply_tracking_result`. It calls `transition_shipment` (SHP-010) rather than
   `update_shipping` so the version guard, legal-transition enforcement, and audit events all
   apply through the same single write path.

With `SHIPPING_ENABLED=false`, every new code path is unreachable and all pre-existing
shop/cart/orders/billing/tracking behaviour is byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 The existing `apply_tracking_result` (carrier_tracking.py:138–195)

`app/services/carrier_tracking.py:138` defines:

```python
def apply_tracking_result(
    order: Dict[str, Any],
    result: Dict[str, Any],
) -> Optional[Dict[str, Any]]:
```

It is tightly coupled to the `purchase_transactions` shape: it reads `order["user_sub"]` /
`order["txn_id"]` (`:183–185`) and calls `update_shipping(str(buyer_sub), str(txn_id), shipping)`
(`:188`) from `app/services/purchase_history`. The docstring explicitly names "purchase-transaction
DynamoDB item" as the expected input. No shipment-aware path exists.

The idempotent short-circuit at `:163–168` — if `new_status == old_status`, return `None` — is the
key reusable invariant. This ticket preserves it for both targets.

`send_delivery_alert` at `:198` fires alerts using `order.get("seller_sub")`, `order.get("seller_id")`,
`order.get("metadata", {}).get("seller_sub")` and `order.get("user_sub")` / `order.get("buyer_id")`.
The shipment row (SHP-008) carries `user_id` as the buyer identifier; the seller is on the linked
order row. SHP-012 passes the required keys into the delivery alert so it fires correctly from
either target.

### 2.2 `map_carrier_status` and `ACTIVE_TRACKING_STATUSES` (carrier_tracking.py:84, :129)

`map_carrier_status(carrier, raw_status) -> str` at `:84` is a pure, carrier-agnostic function
that normalises carrier-specific status strings to our internal enum
(`label_created`, `picked_up`, `in_transit`, `out_for_delivery`, `delivered`, `exception`,
`returned`). It is already used by the poller (`carrier_tracking_poller.py:27–30`).

`ACTIVE_TRACKING_STATUSES` at `:129–135` is a Python set:

```python
ACTIVE_TRACKING_STATUSES = {
```

SHP-013 (the next ticket) uses this set to filter shipments worth polling. SHP-012 makes

### 2.3 Existing scan fallback: `find_transaction_by_tracking` (purchase_history.py:595)

`app/services/purchase_history.py:595–620` implements `find_transaction_by_tracking` as a
`T.purchase_transactions.scan` with `FilterExpression="tracking_number = :tn"` and a
`LastEvaluatedKey` loop. The comment at `:598–600` acknowledges this is a full-table scan and
that a GSI (TrackingIndex) would be more efficient. That comment predates the shipping tickets
and refers to the `purchase_transactions` table — it is not the scan SHP-012 addresses (that
table already promotes `tracking_number` at the top level for its own future GSI use, per
`purchase_history.py:416–418`).

SHP-012 introduces a new GSI (`TrackingNumberIndex`) on `T.shipments` so that shipments can be
resolved by tracking number with a single `query` — avoiding a scan of the potentially large
shipments table.

### 2.4 `transition_shipment` (SHP-010)

SHP-010 introduces `transition_shipment(shipment_id, target_status, *, ...)` in
`app/services/shipments.py`. This function enforces `LEGAL_TRANSITIONS`, the version guard, and
the `→ shipped` tracking requirement. SHP-012's `apply_tracking_result_to_shipment` calls
`transition_shipment` to advance the status — it does **not** write directly to `T.shipments`.
This ensures the version guard and legal-transition enforcement are never bypassed by carrier
status updates.

Key constraint from SHP-010: `transition_shipment` raises `HTTPException(409, code="illegal_transition")`
for out-of-order transitions. A shipment already in `"delivered"` will therefore reject a second
`"delivered"` update — providing the idempotent re-apply invariant without additional code.

### 2.5 `carrier_tracking_poller.py` — existing `poll_order` architecture

`app/services/carrier_tracking_poller.py:48` defines `poll_order(order: Dict)` which:
1. Reads `shipping.carrier` and `shipping.tracking_number` from the order item.
2. Calls `_lookup_carrier_state(carrier, tracking_number)` to fetch the mock carrier state.
3. Calls `map_carrier_status(carrier, raw_status)` to normalise.
4. Calls `apply_tracking_result(order, result)`.

SHP-013 (not this ticket) will extend `poll_order` to also cover shipments. SHP-012's job is to
make step 4 work for shipments by providing `apply_tracking_result_to_shipment`. The existing
`poll_order` function and its callers (`poll_one`, `poll_all`, `get_pollable_orders`) are not
changed by SHP-012.

## 3. Data Model

### 3.1 New GSI: `TrackingNumberIndex` on `shipments`

SHP-012 adds a GSI to the `shipments` table so that `find_shipment_by_tracking` can resolve a
shipment in O(1) without scanning.

**Schema delta to `scripts/local-ddb-init.py`:**

The `TableDef` for `shipments` (added by SHP-002 following the pattern at `scripts/local-ddb-init.py:2483–2492`
for the `returns` table — which uses the same `GSI_ORDER` + `GSI_STATUS` + `attr_types={"created_at":"N"}` shape; confirmed in SHP-002 verification log §12 entry 8) is amended to include a third GSI entry:

```python
TableDef(
    _resolve_table_name(S.shipments_table_name, "shipments"),
    "shipment_id",                      # PK (hash-only, no sort key)
    gsi=[
        {"index_name": "GSI_ORDER",
         "partition_key": "order_id", "sort_key": "created_at"},
        {"index_name": "GSI_STATUS",
         "partition_key": "status",   "sort_key": "created_at"},
        {"index_name": "TrackingNumberIndex",
         "partition_key": "tracking_number"},   # ← new, hash-only
    ],
    attr_types={"created_at": "N"},     # numeric sort key on GSI_ORDER + GSI_STATUS
)
```

`tracking_number` is a String type (no `attr_types` entry needed — `attr_types` is only
required for Number keys per the CLAUDE.md DynamoDB gotcha). The GSI is sparse: only shipment
rows that have had a tracking number assigned (i.e. that have advanced to `"shipped"` via
SHP-010's `transition_shipment`) will appear in the index. Rows in earlier states
(`pending_fulfillment`, `packed`, `label_created`) carry no `tracking_number` attribute and
are simply absent from the index — exactly the desired behaviour.

**Top-level `tracking_number` attribute:** SHP-010's `transition_shipment` already writes
`tracking_number` at the top level of the `shipments` row (`:3.2` of SHP-010 spec; consistent
with `purchase_history.py:416–418` for `purchase_transactions`). No additional write is
required by SHP-012 for the GSI to see the attribute.

### 3.2 No new tables, settings keys, or table handles

SHP-012 is additive-only to the `shipments` table's GSI list. No new `TableDef`, no new
`S.*` setting, and no new `T.*` handle are introduced. All new Python symbols are added to
existing files (`app/services/carrier_tracking.py` and `app/services/shipments.py`).

### 3.3 `shipments` row — no new persisted attributes

`apply_tracking_result_to_shipment` drives the DynamoDB write through `transition_shipment`
(SHP-010), which already writes `status`, `version`, `updated_at`, `shipped_at`,
`delivered_at`, `exception_reason`, `returned_at`, etc. (SHP-010 spec §3.2). SHP-012 adds
two optional carrier-event attributes to the shipment row (written directly by
`_update_shipment_carrier_metadata`):

| Attribute | Type | When written | Notes |
|---|---|---|---|
| `carrier_events` | List | On any status update that includes events | Capped at 20 entries; mirrors the cap in `apply_tracking_result` (`:175–178`) |
| `last_carrier_check` | Number (Unix ts) | Every time carrier metadata is refreshed | `now_ts()`; allows the poller to skip recently-checked shipments |
| `status_description` | String | When carrier provides a human-readable description | Optional; overwritten on each refresh |
| `estimated_delivery` | String | When carrier provides an ETA | Optional; overwritten on each refresh |

These four attributes are written via a separate `update_item` call **after** `transition_shipment`
returns successfully. They are supplementary metadata — their absence does not affect correctness.
If the `update_item` for metadata fails, the exception is swallowed (best-effort, matching the
`send_delivery_alert` pattern at `carrier_tracking.py:198–239`).

## 4. API / Service Design

### 4.1 New function: `find_shipment_by_tracking`

Added to `app/services/shipments.py` (the file extended by SHP-008 through SHP-010):

```python
def find_shipment_by_tracking(tracking_number: str) -> Optional[Dict[str, Any]]:
    """Resolve a shipment by tracking number using the TrackingNumberIndex GSI.

    Returns the first matching shipment item or None.
    Unlike purchase_history.find_transaction_by_tracking, this is a GSI query
    (O(1)) not a full-table scan.
    """
    if not tracking_number or tracking_number == "unknown":
        return None
    resp = T.shipments.query(
        IndexName="TrackingNumberIndex",
        KeyConditionExpression="tracking_number = :tn",
        ExpressionAttributeValues={":tn": tracking_number},
        Limit=1,
    )
    items = resp.get("Items", [])
    if not items:
        return None
    return _shipment_out(items[0])   # inject tracking_url (SHP-010 helper)
```

`_require_enabled()` is **not** called here — `find_shipment_by_tracking` is also invoked by
the poller (SHP-013) which runs regardless of the shipping flag in its transaction path. The
function silently returns `None` when the index is empty (no rows have been shipped yet).

### 4.2 New function: `apply_tracking_result_to_shipment`

Added to `app/services/carrier_tracking.py` (the refactored path, co-located with the existing
`apply_tracking_result`). To avoid a circular import (`shipments.py` imports
`carrier_tracking.py` helpers; `carrier_tracking.py` would now import `shipments.py`), the import
of `transition_shipment` is done lazily inside the function body — the same pattern used by the
existing `apply_tracking_result` for its `update_shipping` import at `:156`.

```python
def apply_tracking_result_to_shipment(
    shipment: Dict[str, Any],
    result: Dict[str, Any],
) -> Optional[Dict[str, Any]]:
    """Apply a normalized carrier tracking result to a shipments row.

    ``shipment`` is a full shipments DynamoDB item (must include ``shipment_id``,
    ``status``, ``user_id``, and optionally ``order_id``/``seller_sub``).
    ``result`` is a normalized tracking response with at least a ``status`` field.

    Returns the updated shipment dict if the shipment was changed (via
    transition_shipment), or None if nothing changed (idempotent: status
    unchanged or transition illegal).

    The delivery alert fires exactly once on the first transition to "delivered",
    mirroring apply_tracking_result's behaviour.
    """
    from app.core.time import now_ts
    from app.services.shipments import transition_shipment

    new_status = (result.get("status") or "").strip()
    if not new_status:
        return None

    old_status = (shipment.get("status") or "").strip()
    delivered_already = old_status == "delivered"

    # Idempotent: same status → no-op (mirrors apply_tracking_result:163–168)
    if new_status == old_status:
        return None

    # Attempt the transition through the state machine.
    # transition_shipment raises HTTPException(409) for illegal transitions.
    # We treat illegal transitions as a no-op (carrier sent a status we can't
    # honour from the current state — e.g. "delivered" on a cancelled shipment).
    shipment_id = str(shipment.get("shipment_id") or "")
    if not shipment_id:
        return None

    try:
        updated = transition_shipment(
            shipment_id,
            new_status,
            actor_user_id="carrier_tracking_webhook",
        )
    except Exception:
        # Illegal transition, version conflict, or flag-off — treat as no-op.
        return None

    # Write supplementary metadata (carrier_events, last_carrier_check, etc.)
    # best-effort — failure never blocks the caller.
    try:
        _update_shipment_carrier_metadata(shipment_id, result)
    except Exception:
        pass

    # Fire the delivery alert exactly once.
    if new_status == "delivered" and not delivered_already:
        _send_shipment_delivery_alert(shipment, shipment.get("tracking_number"))

    return updated


def _update_shipment_carrier_metadata(
    shipment_id: str,
    result: Dict[str, Any],
) -> None:
    """Persist supplementary carrier metadata on the shipment row.

    Does NOT advance status or version — uses an unconditional update_item
    (no ConditionExpression) to merge the metadata fields. Best-effort only.
    """
    from app.core.time import now_ts
    from app.core.tables import T

    set_exprs = ["last_carrier_check = :lcc"]
    vals: Dict[str, Any] = {":lcc": now_ts()}

    if result.get("status_description"):
        set_exprs.append("status_description = :sd")
        vals[":sd"] = result["status_description"]
    if result.get("estimated_delivery"):
        set_exprs.append("estimated_delivery = :ed")
        vals[":ed"] = result["estimated_delivery"]
    events = result.get("events")
    if events:
        set_exprs.append("carrier_events = :ce")
        vals[":ce"] = list(events)[:20]

    T.shipments.update_item(
        Key={"shipment_id": shipment_id},
        UpdateExpression="SET " + ", ".join(set_exprs),
        ExpressionAttributeValues=vals,
    )


def _send_shipment_delivery_alert(
    shipment: Dict[str, Any],
    tracking_number: Optional[str],
) -> None:
    """Alert the buyer (and seller, if resolved) that a shipment was delivered.

    Reuses send_delivery_alert's write_alert path but adapted for the shipment
    shape. Best-effort — never raises.
    """
    from app.services.alerts import write_alert

    shipment_id = str(shipment.get("shipment_id") or "")
    buyer_sub = str(shipment.get("user_id") or shipment.get("buyer_id") or "")
    seller_sub = str(
        shipment.get("seller_sub")
        or (shipment.get("metadata") or {}).get("seller_sub")
        or ""
    )
    tn = str(tracking_number or "")

    details = {
        "alert_type": "delivery_confirmed",
        "shipment_id": shipment_id,
        "tracking_number": tn,
    }

    targets = [s for s in (seller_sub, buyer_sub) if s]
    seen: set = set()
    for sub in targets:
        if sub in seen:
            continue
        seen.add(sub)
        try:
            write_alert(
                sub,
                event="delivery_confirmed",
                outcome="success",
                title="Package delivered",
                details=details,
            )
        except Exception:
            pass
```

### 4.3 Refactoring `apply_tracking_result` — parameterised target

Rather than duplicating the idempotent old==new check and delivery-alert logic, the existing
`apply_tracking_result` is kept **byte-for-byte unchanged** for the `purchase_transactions`
path. `apply_tracking_result_to_shipment` is a **separate** function — parallel, not derived.
This minimises diff and regression risk on the transaction path.

The SHP-012 ticket description says "refactored/parameterized so it can target a shipment record,
not only a `purchase_transactions` item". Concretely this means:

- The common logic (idempotent check, metadata capping, delivery alert) is extracted into private
  helpers `_update_shipment_carrier_metadata` and `_send_shipment_delivery_alert` that are
  co-located in `carrier_tracking.py` alongside the existing `send_delivery_alert`.
- The two public entry points — `apply_tracking_result` (for transactions) and
  `apply_tracking_result_to_shipment` (for shipments) — remain distinct functions with distinct
  signatures to avoid a mixed-target callable that requires an `isinstance` branch.
- The existing `apply_tracking_result` at `:138` is **not modified**. Any reference to it in
  `carrier_tracking_poller.py:102`, `carrier_tracking_poller.py:27–30`, and tests continues to
  work without change.

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent re-apply: status unchanged → no-op

`apply_tracking_result_to_shipment` checks `new_status == old_status` before calling
`transition_shipment`. If the carrier sends the same status twice (e.g., two `"in_transit"`
webhooks), the function returns `None` without touching DynamoDB. This mirrors the existing
behaviour at `carrier_tracking.py:163–168`.

Additionally, even if the old==new guard were removed, `transition_shipment` would reject the
transition with HTTP 409 `"illegal_transition"` (because `in_transit → in_transit` is not in
`LEGAL_TRANSITIONS`). The old==new check is therefore an **optimisation** (avoids a DDB fetch
inside `transition_shipment`) rather than the sole guard.

### 5.2 Carrier sends status that skips a state

The carrier may jump directly from `"picked_up"` to `"delivered"` without reporting
`"in_transit"` or `"out_for_delivery"`. In `LEGAL_TRANSITIONS` (SHP-010), `"picked_up"` is not
a defined state — the shipment's canonical statuses are those in `LEGAL_TRANSITIONS`; after
`shipped`, the next legal states are `in_transit` and `exception`. The `map_carrier_status`
normalisation maps raw carrier statuses to internal statuses that may or may not match the
current shipment state.

**Handling:** `transition_shipment` will raise HTTP 409 `"illegal_transition"` for a
carrier-imposed skip (e.g., `shipped → delivered` is not legal — the path is `shipped →
in_transit → out_for_delivery → delivered`). The `except Exception` block in
`apply_tracking_result_to_shipment` swallows this 409 and returns `None`. The shipment stays
in its current state. The supplementary metadata (`last_carrier_check`, `status_description`,
carrier events) is still written via `_update_shipment_carrier_metadata`. This is the correct
behaviour: we record that we saw the carrier event, but we do not violate the legal-transition
invariant.

An alternative (relaxing certain transitions for carrier-initiated updates) is deferred. If
the product team decides that carrier webhooks may legitimately skip intermediary states, the
`LEGAL_TRANSITIONS` map in SHP-010 can be updated to add more edges — SHP-012's code does not
change.

### 5.3 Delivery alert fires exactly once

`delivered_already = old_status == "delivered"` is captured **before** calling
`transition_shipment`. If the shipment was already `"delivered"` before this invocation,
`new_status == old_status` fires the early return and the alert is never reached. If the
shipment was in any other state and `new_status == "delivered"`, the alert fires after
`transition_shipment` succeeds. If `transition_shipment` raises (e.g. version conflict),
the alert is never fired — it fires only on confirmed success.

### 5.4 Seller sub resolution for the delivery alert

The `shipments` row (SHP-008) carries `user_id` for the buyer. The seller is not always
present on the shipment row; it may be on the linked order (`orders` table,
`commerce_order_service.py:72`). SHP-012 makes a best-effort attempt to find a seller: it
reads `shipment.get("seller_sub")` and `shipment.get("metadata", {}).get("seller_sub")`.
If neither is present, only the buyer alert is sent. A future ticket (SHP-014 or beyond)
can enrich the shipment row with `seller_sub` at creation time; until then the alert is
buyer-only in most cases.

### 5.5 Version conflict during carrier update

If two concurrent carrier webhooks fire for the same shipment (e.g., `in_transit` and
`out_for_delivery` arrive nearly simultaneously), one will succeed and one will receive a
version conflict (HTTP 409 `code="version_conflict"` from `transition_shipment`). The
`except Exception` in `apply_tracking_result_to_shipment` swallows this. The losing update
is effectively discarded. This is acceptable: the status that wins is the most recent DDB
write, and the carrier will re-deliver the event (or the next poll cycle will pick up the
final state).

### 5.6 `find_shipment_by_tracking` — multiple shipments with the same tracking number

A tracking number should uniquely identify a single shipment route segment. In edge cases
(e.g., a re-used test tracking number or a data bug), the GSI may return multiple rows.
`find_shipment_by_tracking` uses `Limit=1` and returns the first result. No ordering is
guaranteed by a hash-only GSI — callers should not assume the "correct" shipment is returned
when duplicates exist. Deduplication is an operator responsibility (data quality).

### 5.7 Shipment in terminal state — status update silently ignored

A carrier may send a `"delivered"` event for a shipment that has already been `"cancelled"`
(e.g., the package was held, admin cancelled the shipment in the system, then the carrier
delivered it anyway). `apply_tracking_result_to_shipment` will attempt `cancelled → delivered`,
which is not in `LEGAL_TRANSITIONS`. The `except Exception` absorbs the 409. The supplementary
metadata (`last_carrier_check`, etc.) **is still written** by `_update_shipment_carrier_metadata`
— the carrier event is recorded even though the status cannot advance. This preserves the
audit trail.

### 5.8 `ACTIVE_TRACKING_STATUSES` compatibility

`ACTIVE_TRACKING_STATUSES` contains `{"shipped", "label_created", "picked_up", "in_transit",
"out_for_delivery"}`. The shipment state machine (SHP-010) uses `status` values that are a
superset: `pending_fulfillment`, `packed`, `label_created`, `shipped`, `in_transit`,
`out_for_delivery`, `delivered`, `exception`, `returned`, `cancelled`. The intersection:
`label_created`, `shipped`, `in_transit`, `out_for_delivery` — are the states a shipment can
be in that are also in `ACTIVE_TRACKING_STATUSES`. `"packed"` and `"pending_fulfillment"` are
pre-carrier states and should not be polled (no tracking number yet). `"exception"` is
intentionally absent from `ACTIVE_TRACKING_STATUSES` (polling stops on exception; the admin
must resolve manually). SHP-013 will use `ACTIVE_TRACKING_STATUSES` filtered against
`T.shipments` by `status` (via `GSI_STATUS`); this set intersection produces exactly the right
set of shipments to poll.

### 5.9 `tracking_url` is never stored

`find_shipment_by_tracking` returns the result of `_shipment_out(item)` (SHP-010's projection
helper), which injects `tracking_url` at read time via `build_tracking_url`. This attribute is
never written to DynamoDB — consistent with `purchase_history.get_transaction_info:389–394`.

### 5.10 Flag interaction: `shipping_enabled=False`

`find_shipment_by_tracking` does **not** call `_require_enabled()` (§4.1 rationale: the
function is also a lookup helper for the legacy transaction path's routing).
`apply_tracking_result_to_shipment` calls `transition_shipment` lazily inside a `try/except`.
If `shipping_enabled=False`, `transition_shipment` raises HTTP 503 `feature_disabled`, which
is caught and swallowed. The function returns `None`. The supplementary metadata write is also
skipped (the `try` block around `_update_shipment_carrier_metadata` swallows any error). Net
result: with the flag off, carrier tracking results are silently no-ops for shipments — the
legacy `apply_tracking_result` (transaction path) is entirely unchanged.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No `dev_mode` branches

`find_shipment_by_tracking`, `apply_tracking_result_to_shipment`, `_update_shipment_carrier_metadata`,
and `_send_shipment_delivery_alert` contain zero `if S.dev_mode` conditionals. The DynamoDB
GSI query in `find_shipment_by_tracking` works identically against DynamoDB Local (port 8001,
dev) and real DynamoDB (prod). The `_lookup_carrier_state` mock used by the poller is in
`carrier_tracking_mock.py` (the mock router); it is not referenced in SHP-012's new functions.

### 7.2 Idempotency guarantees

**Delivery alert:** fires at most once per shipment per delivery (guarded by `delivered_already`
capture before `transition_shipment`).

**Metadata write:** `_update_shipment_carrier_metadata` is unconditional (`update_item` with no
`ConditionExpression`). It is idempotent in the DynamoDB sense — a repeated write for the same
values is a no-op in terms of business logic, since the fields are overwritten to the same
values. Concurrent metadata writes may interleave harmlessly; they do not affect `version` or
`status`.

**Status transition:** guaranteed exactly-once via `transition_shipment`'s version guard. Two
concurrent `apply_tracking_result_to_shipment` calls for the same shipment produce: one
successful transition + one swallowed 409. The metadata write may race; at worst the
`last_carrier_check` timestamp is slightly stale — no correctness issue.

### 7.3 Billing ledger

No calls to `billing_shared.new_ledger_entry`. Carrier status updates do not move money.
Shipping refunds are handled by `returns_rma.py` and `billing.refund_payment` — SHP-012 does
not touch billing.

### 7.4 Deterministic idempotency keys

`find_shipment_by_tracking` resolves by `tracking_number`, which is deterministic (same number
→ same shipment). No SHA-256 idempotency key is required here because the GSI PK is the
natural idempotency key.

### 7.5 Security: no new auth surface

SHP-012 adds no router endpoints, so there are no new auth decisions in this ticket. The
functions are called by the polling layer (SHP-013, admin-gated endpoint) and the webhook
receiver. Callers are responsible for their own authentication; the service functions do not
re-check identity.

### 7.6 Tracking number sensitivity

As noted in SHP-010 §7.6, a tracking number is not PII but is commercially sensitive. It is
stored at rest (DynamoDB encryption in prod). The `TrackingNumberIndex` GSI makes it queryable
by value — access is gated by the IAM role that has table/index access (no broader exposure than
the base table). In dev, DynamoDB Local (port 8001) has no IAM enforcement; access is limited
to the local network.

### 7.7 `purchase_transactions` path unchanged

A regression assertion (§9.1 test `test_transaction_path_unchanged`) confirms that
`apply_tracking_result(order, result)` still calls `update_shipping` (not `transition_shipment`)
and that `find_transaction_by_tracking` still uses the scan-loop. Neither function is modified
by SHP-012.

## 8. Backward Compatibility & Migration

### 8.1 `apply_tracking_result` — no change

The existing function at `carrier_tracking.py:138` is not modified. Its signature, logic, lazy
imports, idempotent check, and delivery alert path are byte-for-byte unchanged. Tests that
already cover it (`tests/test_carrier_tracking.py` or equivalent) continue to pass.

### 8.2 GSI addition to `shipments` table

In development, `just restart` recreates the table with the new GSI (the init script drops and
recreates all tables). No migration needed locally.

In production, adding a GSI to an existing DynamoDB table is an online operation (AWS applies
it asynchronously; the table remains available). The backfill is automatic: DynamoDB projects
existing rows that carry the `tracking_number` attribute into the new GSI. The service code
that calls `T.shipments.query(IndexName="TrackingNumberIndex", ...)` may be deployed before the
GSI backfill completes — during the window the query returns fewer results than expected, but
this is safe (a missed lookup just means the carrier update is applied via the next poll cycle).
Deployment order: add the `TableDef` GSI entry and apply with `UpdateTable` before deploying
SHP-012's Python code.

### 8.3 Additive-only changes

All new Python symbols (`find_shipment_by_tracking`, `apply_tracking_result_to_shipment`,
`_update_shipment_carrier_metadata`, `_send_shipment_delivery_alert`, `get_shipment_tracking_view`)
are pure additions. No existing function bodies, signatures, or module-level names in
`carrier_tracking.py`, `carrier_tracking_poller.py`, `purchase_history.py`, or `shipments.py`
are modified (except `find_shipment_by_tracking` appended to `shipments.py`).

### 8.4 Legacy scan preserved

`find_transaction_by_tracking` in `purchase_history.py:595` is **not deleted or changed**.
The ticket says to add a GSI-backed lookup for shipments; it does not say to fix the
transaction-side scan. If the transaction scan becomes a performance concern, a
`TrackingNumberIndex` on `purchase_transactions` is a separate (post-SHP-012) task.

## 10. Open Questions / Assumptions

**OQ-1 (Circular import: `carrier_tracking` ↔ `shipments`)**: `shipments.py` imports from
`carrier_tracking.py` (for `detect_carrier`, `build_tracking_url`). Adding
`apply_tracking_result_to_shipment` to `carrier_tracking.py` creates a reverse dependency
(`carrier_tracking.py` → `shipments.py`). The design resolves this with a lazy import
(`from app.services.shipments import transition_shipment` inside the function body), matching
the pattern already used in the existing `apply_tracking_result` at `:156` for `update_shipping`.
**Assumption**: The lazy-import pattern is sufficient. If the import graph is restructured in
a future ticket, these helpers may need to move to a dedicated `app/services/shipment_tracking.py`
module. Verify the lazy import does not produce import-cycle errors in the test environment.

**OQ-2 (Seller sub on the shipment row)**: SHP-008's `create_shipment` does not appear to store
`seller_sub` on the shipment row (the spec references `user_id` as the buyer; seller is on the
order). `_send_shipment_delivery_alert` makes a best-effort attempt to find a seller but falls
back to buyer-only if absent. **Assumption**: Buyer-only alerts are acceptable at this stage.
If seller alerting is required, SHP-008 should be amended to write `seller_sub` (derived from
the linked order) onto the shipment row at creation time.

**OQ-3 (`_shipment_out` accessibility)**: SHP-010 adds `_shipment_out` as a module-private helper
in `shipments.py`. `find_shipment_by_tracking` (also in `shipments.py`) calls it directly.
`get_shipment_tracking_view` (in `carrier_tracking_poller.py`) calls `get_shipment` (which
already applies `_shipment_out` internally per SHP-010 §4.3). **No cross-module access of
private helpers is needed.** Confirm `get_shipment` applies `_shipment_out` before returning
(SHP-010 OQ-5 open question on `tracking_url` in `ShipmentOut`).

**OQ-4 (`TrackingNumberIndex` GSI on `purchase_transactions`)**: The ticket description says
"add a `find_shipment_by_tracking(tracking_number)` lookup (GSI-backed; avoid the scan-loop
fallback used at `app/services/purchase_history.py:595` by indexing `tracking_number`)."
**Assumption**: The GSI is on the `shipments` table (new), not on `purchase_transactions`
(pre-existing). The scan-loop in `purchase_history.py:595` is acknowledged technical debt that
is **not** fixed by SHP-012. The ticket's description is ambiguous; this spec assumes the new
GSI targets `T.shipments`. If the intent was to also add a GSI to `T.purchase_transactions`,
that is a separate change to SHP-002/SHP-012 scope.

**OQ-5 (Carrier-skipped-state transitions — relaxed edges)**: The current `LEGAL_TRANSITIONS`
map (SHP-010) does not allow `shipped → delivered` directly. Real carriers sometimes skip
intermediate statuses. **Assumption**: The SHP-010 state machine is strict and SHP-012 silently
drops any carrier update that violates it (the metadata is still written). If the product
team decides that carrier-initiated skips should be allowed, the fix is in SHP-010
(`LEGAL_TRANSITIONS`), not in SHP-012.

**OQ-6 (Metadata write — version bump)**: `_update_shipment_carrier_metadata` writes
`last_carrier_check`, `carrier_events`, `status_description`, `estimated_delivery` without
a `ConditionExpression`. This means two concurrent poller calls may interleave metadata writes.
The design accepts this because these fields are informational (display-only) and their
last-write-wins semantics are acceptable. If strict metadata consistency is required, a version
guard should be added — but that would require reading the current row first, adding latency and
complexity. **Assumption**: Unconditional metadata update is sufficient.
