# ECM-005 — Live availability projection from inventory/reservations

**Type:** Feature | **Priority:** P0 | **Estimate:** 4 days
**Dependencies:** ECM-003 (Pydantic models), ECM-002 (flag scaffold), FAC-004 (FACILITY), OFB-003/OFB-004 (OFBIZ_COMMERCE)

---

## 1. Summary & Goal

ECM-005 wires the existing OFBiz Phase-1 inventory & soft-reservation service (`app/services/inventory.py`) into the storefront catalog read path so that `stock_status` and `stock_count` on browse grids and product-detail pages reflect **reservation-adjusted availability** (`available = on_hand − reserved`) instead of the static scalar `stock_count` that is decremented only at purchase time.

The feature is additive and gated behind the `STORE_SHOW_LIVE_AVAILABILITY` sub-flag (default OFF, within the ECM-002 master switch `STORE_INTEGRATION_ENABLED`). With both flags off, the catalog router continues to call the existing `_compute_stock_status` (`app/routers/catalog.py:94`) on the raw `stock_count` scalar, and the response is byte-for-byte unchanged. When the flags are on, the router enriches each `CatalogItemOut` with a populated `StorefrontAvailabilityOut` (from ECM-003) derived from live inventory records.

Three concrete deliverables:

1. **`availability_for_skus(skus, location_id)`** — a new batch-read function in `app/services/store_integration.py` that issues at most one `BatchGetItem` round-trip for up to 100 SKUs and returns a `Dict[str, StorefrontAvailabilityOut]`.
2. **`_apply_live_availability(item_out, avail_map)`** — a pure helper that rebinds `stock_status`, `stock_count`, and `availability` on a `CatalogItemOut` instance from the availability map, falling through to the existing scalar when the SKU is absent from the map (degrade path).
3. **`_catalog_item_out` enrichment** — the catalog router's `list_items` (`catalog.py:394`), `search_items` (`catalog.py:465`), and single-item reads call `availability_for_skus` when the flag is on, then call `_apply_live_availability` per item.

No new DynamoDB tables are required. No existing DynamoDB rows are altered. No billing path is touched.

def _compute_stock_status(item: dict) -> str:
    sc = item.get("stock_count")
    if sc is None:

    sc = int(sc)
    if sc <= 0:

### 2.5 SKU-to-inventory mapping convention

**CORRECTED:** In the current catalog system, `shoppingcart.py:391` (VERIFIED) shows that `add_catalog_item` constructs cart SKUs as `f"catalog:{item_id}"` — a prefixed string, not the raw `item_id`. The `payload["sku"]` at lines 315/342 is the caller-provided SKU; it is only set to `f"catalog:{item_id}"` when going through the `add_catalog_item` convenience path. The inventory service (`T.inventory`) keys on whatever string the merchant uses as `sku` when calling `PUT /ui/inventory/items`. There is no enforced convention that maps catalog `item_id` to the inventory `sku` namespace today.

**Design decision for ECM-005:** The implementation must document the SKU namespace expected in `T.inventory` for catalog items. The simplest convention (and the one assumed by this spec) is that merchants register inventory rows with `sku = item_id` (the bare item ID, not prefixed). If the deployment uses a different namespace, the `availability_for_skus` lookup will return empty maps and degrade path A applies. Confirm this convention with the merchant onboarding team before shipping. When ECM-004's variant layer is active, each variant's explicit `sku` field is used instead; that wiring is ECM-006's responsibility.

### 2.6 Reorder-point / low-stock threshold alignment

## 3. Data Model

ECM-005 introduces **no new DynamoDB tables** and no schema changes. It adds a single-pass `BatchGetItem` call pattern against the existing `T.inventory` table.

### 3.1 BatchGetItem key structure

The existing `T.inventory` table PK is `sku` (String), SK is `location_sk` (String, always `"LOC#{location_id}"`) — both VERIFIED at `scripts/local-ddb-init.py:2456–2459` and `inventory.py:119`. A batch read for SKUs `["sku-A", "sku-B"]` at `location_id="warehouse"` maps to:

```python
keys = [
    {"sku": s, "location_sk": f"LOC#{location_id}"}
    for s in skus
]
```

DynamoDB `BatchGetItem` supports up to 100 keys per call and returns items in arbitrary order; the function builds the response dict keyed on `sku` after the call returns.

### 3.2 No new GSIs, no attr_types changes

All existing GSIs and `attr_types` declarations in `scripts/local-ddb-init.py:2452–2492` (VERIFIED: inventory at 2456–2464, reservations at 2469–2478) remain unchanged. `BatchGetItem` uses the table's primary key and requires no index.

### 3.3 Reservation total is already denormalised

The `reserved` field on each inventory row (`T.inventory`) is maintained as a denormalised counter by `reserve()` (defined at `inventory.py:339`; the `update_item` that increments `reserved` is at `inventory.py:362–381` — VERIFIED) and restored by `release_reservation()` (defined at `inventory.py:492`; the `update_item` that decrements `reserved` is at `inventory.py:511–513` — VERIFIED) and `expire_due_reservations()` (delegates to `release_reservation`, `inventory.py:538`). ECM-005 reads this denormalised field directly — it does not sum reservation rows from `T.reservations`. This keeps the batch-read path to a single table and one round-trip, and is consistent with `_record_out` at `inventory.py:101–115` (VERIFIED) which performs the same read.

## 4. API / Service Design

### 4.1 `availability_for_skus` in `app/services/store_integration.py`

```python
from typing import Dict, List, Optional
import boto3
from app.core.tables import T
from app.core.settings import S
from app.models import StorefrontAvailabilityOut
from app.services.inventory import _to_int, _status_for, _default_reorder_point, DEFAULT_LOCATION  # inventory.py:67,84,76,43 — all VERIFIED

def availability_for_skus(
    skus: List[str],
    location_id: str = DEFAULT_LOCATION,
) -> Dict[str, StorefrontAvailabilityOut]:
    """Batch-read live availability for a list of SKUs from T.inventory.

    Returns a dict keyed by SKU. SKUs with no inventory row are absent from
    the dict (the caller falls through to the legacy stock_count scalar).

    Chunked at 100 keys per BatchGetItem call (DynamoDB hard limit).
    Raises no exceptions — any boto3 error propagates to _safe_upstream.
    """
```

**Algorithm:**

1. Deduplicate `skus` and filter empty strings.
2. Chunk into groups of up to 100.
3. For each chunk, call `T.inventory.meta.client.batch_get_item` with `RequestItems = { T.inventory.name: { "Keys": [...] } }`.
4. Collect all returned items from `Responses`. Handle `UnprocessedKeys` by looping (standard DynamoDB unprocessed-keys retry pattern).
5. For each returned item, build a `StorefrontAvailabilityOut`:
   - `on_hand = _to_int(item["on_hand"])`
   - `reserved = _to_int(item["reserved"])`
   - `available = on_hand - reserved`
   - `reorder_point = _to_int(item.get("reorder_point"), _default_reorder_point())`
   - `stock_status = _status_for(available, reorder_point)`
   - `low_stock = (available > 0 and available <= reorder_point)`
6. Return the populated dict.

**Callers should always wrap in `_safe_upstream`** so any boto3 exception (e.g. `ResourceNotFoundException` when inventory table is absent, `ProvisionedThroughputExceededException` in prod) degrades gracefully to the static `stock_count` scalar.

### 4.2 `_apply_live_availability` helper in `app/services/store_integration.py`

```python
def _apply_live_availability(
    item_out: CatalogItemOut,
    avail_map: Dict[str, StorefrontAvailabilityOut],
) -> CatalogItemOut:
    """Rebind stock_status, stock_count, and availability on item_out from avail_map.

    If the SKU is absent from avail_map (inventory service returned nothing for it),
    returns item_out unchanged (flag-off / degrade path parity).
    """
```

**Algorithm:**

1. `avail = avail_map.get(item_out.item_id)` — use `item_id` as the SKU for flat items.
2. If `avail is None`: return `item_out` unchanged.
3. Mutate a copy (or update fields in-place using `model_copy(update={...})` for Pydantic v2):
   - `stock_status = avail.stock_status`
   - `stock_count = avail.available`  (overwrite the static scalar with live available count)
   - `availability = avail`
4. Return the updated instance.

The `stock_count` override uses `avail.available` (not `on_hand`) so the badge label "Only N left" in `Catalog.tsx:182` shows the reservation-adjusted count, not gross stock.

## 5. Detailed Behavior & Edge Cases

### 5.1 Normal path (flag on, inventory row exists)

Given `on_hand=10, reserved=3, reorder_point=5`:
- `available = 7`
- `stock_status = "in_stock"` (7 > 5)
- `low_stock = False`
- `CatalogItemOut.stock_count = 7`, `stock_status = "in_stock"`, `availability.available = 7`

Given `on_hand=4, reserved=2, reorder_point=5`:
- `available = 2`
- `stock_status = "low_stock"` (0 < 2 <= 5)
- `low_stock = True`
- Badge in `Catalog.tsx:180` shows "Only 2 left" (reads `item.stock_count = 2`)

Given `on_hand=2, reserved=2, reorder_point=5`:
- `available = 0`
- `stock_status = "out_of_stock"`
- `CatalogItemOut.stock_count = 0`, Add-to-Cart button in `ProductDetail.tsx:267` disabled

### 5.2 Item with no inventory row (degrade path A)

The SKU is absent from `T.inventory` (e.g., the merchant has not initialised inventory for that item). `availability_for_skus` returns a dict that does not contain the SKU. `_apply_live_availability` returns `item_out` unchanged. The response carries the static `stock_count` scalar from the catalog DDB item and the legacy `_compute_stock_status` result — same as flag-off behaviour.

### 5.3 Inventory service unavailable (degrade path B)

boto3 raises any exception from `BatchGetItem` (network error, DDB unavailable, unrecognised table, capacity exceeded). `_safe_upstream` catches it, logs a WARNING, and returns `default={}`. Every `_apply_live_availability` call gets an empty map and returns the item unchanged. The browse/detail page renders with the static `stock_count` scalar. No 500 is raised.

### 5.4 Flag off (exact legacy behaviour)

`_integration_enabled("live_availability")` returns `False` if either `S.store_integration_enabled` or `S.store_show_live_availability` is falsy. The enrichment block is skipped entirely. `T.inventory` is never queried. The response for `list_items` / `search_items` is byte-for-byte identical to pre-ECM-005 behaviour — same `stock_count` scalar, same `_compute_stock_status` result, `availability = None`.

### 5.5 `stock_count = None` (unlimited items)

When the catalog DDB item has no `stock_count` attribute (creator has not set a stock limit), `_compute_stock_status` returns `"unlimited"`. If the same item also has no inventory row, degrade path A applies and `"unlimited"` is preserved. If an inventory row exists, the live availability supersedes: `available = on_hand - reserved` and the status is one of `in_stock / low_stock / out_of_stock`. This is correct — a merchant who opts into inventory management for a previously unlimited item expects the live count to take over.

### 5.6 Oversold / negative available

If through a race or admin correction `on_hand < reserved`, `available` may be negative. `_status_for(available, reorder_point)` with `available <= 0` returns `"out_of_stock"`, which is the correct storefront signal. `low_stock = False` in this case (available is not > 0). `stock_count` is set to the negative integer, but the frontend's Add-to-Cart disable check (`item.stock_status === "out_of_stock"`) triggers before the count is displayed, so the negative value is never rendered.

### 5.7 BatchGetItem chunking

`availability_for_skus` chunks at 100 keys. A category page with more than 100 items (unlikely today, but possible with `page_size: int = Query(default=50, ge=1, le=200)` at `catalog.py:399` — VERIFIED) issues multiple round-trips. Unprocessed keys from a batch response are retried in the same call via a while loop on `UnprocessedKeys`. Max retries: 3 (configurable via setting `store_live_avail_batch_max_retries`; after which remaining SKUs are treated as absent).

### 5.8 Location dimension

ECM-005 reads from the default location `"warehouse"` only (matching `DEFAULT_LOCATION = "warehouse"` in `inventory.py:43`). Multi-location availability (FAC-004 and beyond) is a follow-up. The `location_id` parameter on `availability_for_skus` exists for forward-compatibility but always defaults to `DEFAULT_LOCATION` in the catalog enrichment path.

### 5.9 Geo-blocked items

`_item_geo_blocked` filtering happens before the enrichment block in `list_items` (`catalog.py:413` — VERIFIED: geo-check is in the item-append loop before `out` is built); geo-blocked items are never passed to `availability_for_skus`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

`availability_for_skus` calls `T.inventory` via boto3 `BatchGetItem`. In dev, `T.inventory` is backed by DynamoDB Local (port 8001), which supports `BatchGetItem` identically to real DynamoDB. In prod, it is backed by real DynamoDB. There is **no `dev_mode` branch** in the enrichment logic. This satisfies SECOPS-007.

The `_safe_upstream` wrapper ensures that any infrastructure discrepancy (e.g., DynamoDB Local not running during a unit test) degrades to the static scalar rather than raising a 500, which also applies in prod.

### 7.2 Idempotency

`availability_for_skus` is a pure read with no side effects. It can be called any number of times with the same inputs and produces the same result (modulo concurrent inventory mutations, which is the desired behaviour). No write path is introduced.

### 7.3 Read-after-reserve consistency

Between a customer reserving an item (via `reserve()`, `inventory.py:339`) and the next page-load of the catalog, the `reserved` counter on the inventory row is updated atomically by `inventory.reserve()`. Because ECM-005 reads the denormalised `reserved` counter from the inventory row (not by summing live reservation records), the read is a single `BatchGetItem` with no risk of stale aggregation.

### 7.4 Security

No new privilege escalation. The enrichment runs in the same auth context as the existing `list_items` / `search_items` request (a `require_ui_session`-authenticated user). The availability data (on_hand, reserved counts) is a storefront-visible business metric, not a secret. Displaying it to any authenticated user is consistent with how `stock_count` is already exposed today.

The `availability_for_skus` function does not accept user-controlled input for the `location_id` parameter when called from the catalog router — it uses `S.store_live_avail_location_id` which is set by a server-side env var.

### 7.5 No billing entanglement

`availability_for_skus` reads `T.inventory` only. It does not read or write `T.billing`, `T.reservations`, or `T.carts`. The GL derived from `app/services/billing_shared.new_ledger_entry` is not touched. No money flows.

## 8. Backward Compatibility & Migration

### 8.1 Zero-downtime rollout

Because both flags default to `false`, deploying the code change has zero observable effect on any existing request. The flags can be enabled independently per environment by setting the env vars on the running process.

### 8.2 Existing `CatalogItemOut` consumers

Clients that parse `CatalogItemOut` JSON today see: `stock_count: int | null`, `stock_status: str`. After ECM-005 (flag off): unchanged. After ECM-005 (flag on): `stock_count` may differ from the stored scalar (it reflects `available` now) and a new key `availability` appears in the JSON object. Clients that ignore unknown keys are unaffected; strongly-typed clients that reject unknown keys should apply ECM-013's type-update ticket first (or tolerate extra keys via `additionalProperties: true` in their schema).

### 8.3 Existing E2E tests

All existing Playwright E2E tests run with `STORE_INTEGRATION_ENABLED=false` (default). They are byte-for-byte unaffected. New E2E tests for ECM-005 are additive under a feature flag conditional.

### 8.4 No DynamoDB migration

No new tables, no new GSIs, no attribute back-fills. Items in `T.inventory` that were written before ECM-005 are read exactly as written. The only prerequisite for live availability to appear is that the merchant has initialised inventory rows for their SKUs via the existing `PUT /ui/inventory/items` admin endpoint.

## 10. Open Questions / Assumptions

1. **Assumption: `item_id` equals `sku` for flat (non-variant) catalog items.** This is consistent with `shoppingcart.py:315` where the cart item's `sku` field is set from the passed payload which `ProductDetail.tsx:91` populates with `item.item_id`. ECM-004's variant layer (PRD-007) introduces proper SKUs per variant; until ECM-004 is wired, `item_id` is the only available key. The next spec pass should confirm no scenario exists where `item_id != sku` for non-variant items today.

2. **Assumption: `availability_for_skus` uses `S.store_live_avail_location_id` (default `"warehouse"`) for all catalog lookups.** This is correct for a single-warehouse deployment. Multi-warehouse (FAC-004) is deferred. If a catalog item spans multiple warehouses, aggregate availability (sum across locations) is not computed by this ticket — it reads one location only.

3. **Open question: should `availability` be included in the response when the inventory row exists but `INVENTORY_RESERVATIONS_ENABLED` is false?** Currently `inventory._flag_on()` gates all mutations but not reads. `get_inventory` does not call `_require_enabled()`. ECM-005 will read `T.inventory` regardless of `inventory_reservations_enabled` as long as `store_show_live_availability` is on. This is deliberate — the admin may have seeded inventory rows and enabled the storefront flag without the reservation lifecycle flag. Confirm this is acceptable or add a guard.

4. **Resolved: `_apply_live_availability` must use `model_copy(update={...})`** (Pydantic v2 immutable pattern). The project is on Pydantic v2 (`pydantic==2.6.4` — VERIFIED in `requirements.txt`) and `model_copy` is already in use (e.g. `app/routers/vod.py:320`). Use `item_out.model_copy(update={"stock_count": avail.available, "stock_status": avail.stock_status, "availability": avail})`.

5. **Assumption: `BatchGetItem` is the correct read pattern rather than parallel `GetItem` calls.** `BatchGetItem` reduces round-trips from N to ceil(N/100) but results in a table-wide read unit cost proportional to N. For browse grids of 50 items this is negligible. For search results scanning up to 200 items (catalog `search_items` `Limit=200` inner scan), two `BatchGetItem` calls are issued. Confirm DynamoDB billing model is acceptable for prod traffic volume.

6. **Assumption: ECM-003's `StorefrontAvailabilityOut` will be merged to `main` before ECM-005 is implemented.** If ECM-003 is not yet merged, ECM-005 must carry a forward declaration of `StorefrontAvailabilityOut` or be blocked.

7. **Open question: should `availability` serialise as `null` or be omitted from the JSON when the flag is off?** Current `CatalogItemOut` with `availability: Optional[StorefrontAvailabilityOut] = None` serialises as `"availability": null` in FastAPI's default JSON mode. To omit the key, the router would need `response_model_exclude_none=True` or the model would use `model_config = ConfigDict(exclude_none=True)`. Confirm desired wire shape with frontend; omitting the key is cleaner for clients doing key-presence checks.
