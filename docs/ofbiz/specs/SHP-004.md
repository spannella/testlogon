# SHP-004 — Carrier & ship-method service

## 1. Summary & Goal

SHP-004 delivers `app/services/shipping_carriers.py` — the service layer that owns the carrier/ship-method catalog introduced by SHP-002's `shipping_carriers` table. The deliverables are:

1. **Carrier CRUD**: `create_carrier`, `get_carrier`, `list_carriers`, `update_carrier`, `disable_carrier`.
2. **Per-carrier method CRUD**: `add_method`, `get_method`, `list_methods`, `update_method`, `disable_method`.
3. **Idempotent default seed**: `seed_default_carriers()` that writes UPS, FedEx, USPS, DHL, and a `manual` carrier — each with a canonical set of ship methods — using `attribute_not_exists(carrier_id)` conditional puts so repeated calls produce no duplicates and no data loss.
4. **Audit events** on every mutating call via `app/services/alerts.audit_event` (mirroring the pattern used at `app/services/commerce_order_service.py:106`).
5. **Online-tracking flag derivation**: each carrier row carries `online_tracking: bool` derived from whether its `carrier_code` appears in `CARRIER_TRACKING_URLS` from `app/services/carrier_tracking.py:10`; the `manual` carrier always has `online_tracking=False`.

No router code, no Pydantic model definitions, no DynamoDB table definitions, and no changes to `app/main.py` are part of this ticket — those belong to SHP-002 (table/settings/handles), SHP-003 (models), and SHP-005 (router).

## 2. Context & Current State

### 2.1 Carrier tracking primitives (reused, not replaced)

`app/services/carrier_tracking.py:10` defines `CARRIER_TRACKING_URLS`, a plain dict with exactly four keys: `"ups"`, `"fedex"`, `"usps"`, `"dhl"` (verified). This is the canonical source of truth for which carrier codes support online tracking. `build_tracking_url(carrier, tracking_number)` (`carrier_tracking.py:33`) returns `None` for any code not in that dict, including `"manual"`.

`carrier_tracking.py:84` (`map_carrier_status`) normalises raw carrier status strings. Its docstring lists seven values: `label_created`, `picked_up`, `in_transit`, `out_for_delivery`, `delivered`, `exception`, `returned` — but **the function body never actually returns `"returned"`**: line 104 maps `"returned to sender"` to `"exception"`. The `returned` status exists as a valid business value that service code can write directly; it is not produced by `map_carrier_status`. This enum is also used as the valid shipment status set (SHP-003's `ShipmentStatusEnum`).

SHP-004 adds no code to `carrier_tracking.py`. The module is imported read-only for the `CARRIER_TRACKING_URLS` dict.

### 2.2 shipping_carriers table (from SHP-002)

The `shipping_carriers` table lands in `scripts/local-ddb-init.py` as part of SHP-002. Its schema (documented in SHP-002.md §3.1):

- **PK** `carrier_id` (String) — deterministic `sha256(carrier_code.encode("utf-8"))[:16]`.
- **SK** `sk` (String) — `"CARRIER#"` for carrier header rows; `"METHOD#{method_code}"` for method rows.
- **GSI_CODE**: partition key `carrier_code`, sort key `sk` — allows lookup of a carrier header (plus all its methods) by code without knowing `carrier_id`.

No `attr_types` override needed: both GSI keys are String. The corresponding handle is `T.shipping_carriers` (added by SHP-002 to `app/core/tables.py`).

### 2.3 Flag guard pattern (from SHP-002 / existing services)

The master flag `S.shipping_enabled` (env `SHIPPING_ENABLED`, default `False`) is introduced by SHP-002. The guard pattern for OFBiz services is established by `app/services/inventory.py:50–56` (`_flag_on()` / `_require_enabled()`, verified) and `app/services/returns_rma.py:67–73` (verified). Both raise `HTTPException(404, ...)` when off. SHP-004 follows this identical pattern.

### 2.4 Audit event pattern (from commerce_order_service)

`app/services/commerce_order_service.py:106–117` calls `audit_event("commerce_order_created", user_id, None, outcome="success", ...)` after a successful `put_item` (verified: `audit_event` call at `commerce_order_service.py:106`). The function signature is `alerts.audit_event(event: str, user_sub: str, request=None, **fields)` (`app/services/alerts.py:644`, verified). SHP-004 adopts this verbatim: every mutating service function calls `audit_event(...)` as a best-effort last step (not inside a try/except that would silently swallow the primary error).

### 2.5 Idempotent seed pattern (from notification_templates)

`app/services/notification_templates.py:102` (`seed_default_templates`, verified) illustrates the idempotent seed pattern: loop over a static list, do a `get_item` probe first, skip if the row already exists, write if absent. SHP-004 uses the DynamoDB `attribute_not_exists(carrier_id)` conditional put instead of a probe-then-write, because the `put_item` conditional is atomic and eliminates the probe/write race.

### 2.6 Deterministic carrier_id derivation (from commerce_order_service)

`app/services/commerce_order_service.py:67` derives a deterministic `order_id` via `hashlib.sha256(corr.encode("utf-8")).hexdigest()[:32]` (verified). SHP-004 uses the same `hashlib.sha256` approach: `carrier_id = hashlib.sha256(carrier_code.encode("utf-8")).hexdigest()[:16]`. This guarantees that seeding UPS always produces the same `carrier_id`, making the seed idempotent and allowing downstream services (SHP-006 rate engine, SHP-008 shipment creation) to hard-reference carrier ids.

### 2.7 Existing ShipmentMethod / CarrierOut models (from SHP-003)

SHP-003 adds the following shapes to `app/models.py` (exact fields are SHP-003's deliverable, not re-defined here):

- `CarrierIn`, `CarrierOut` — carrier header create/response.
- `ShipmentMethodIn`, `ShipmentMethodOut` — method create/update/response.

SHP-004 imports these from `app/models` and returns them from service functions so the router layer in SHP-005 can call `CarrierOut(**carrier_record)` directly.

## 3. Data Model

The `shipping_carriers` table is single-table with two row types. This section specifies the exact attribute shapes the service writes and reads; the `TableDef` is SHP-002's deliverable and is not repeated here.

### 3.1 Carrier header row (SK = `"CARRIER#"`)

Written by `create_carrier` and `seed_default_carriers`. Read by `get_carrier`, `list_carriers`.

| Attribute | DDB Type | Notes |
|---|---|---|
| `carrier_id` | S (PK) | `sha256(carrier_code)[:16]` — deterministic |
| `sk` | S (SK) | Literal `"CARRIER#"` |
| `carrier_code` | S | `ups` / `fedex` / `usps` / `dhl` / `manual` |
| `display_name` | S | Human-readable, e.g. `"UPS"` |
| `online_tracking` | BOOL | `carrier_code in CARRIER_TRACKING_URLS` |
| `enabled` | BOOL | Soft-disable; defaults `True` on create |
| `created_at` | N | `now_ts()` — integer Unix seconds |
| `updated_at` | N | `now_ts()` — updated on every mutation |

`carrier_code` also appears on this row to support the `GSI_CODE` query that retrieves the header by code.

### 3.2 Method row (SK = `"METHOD#{method_code}"`)

Written by `add_method` / `seed_default_carriers`. Read by `list_methods`, `get_method`.

| Attribute | DDB Type | Notes |
|---|---|---|
| `carrier_id` | S (PK) | Same as parent carrier header row |
| `sk` | S (SK) | `METHOD#{method_code}` |
| `carrier_code` | S | Denormalised for GSI_CODE queries |
| `method_code` | S | `ground` / `express` / `overnight` / `economy` / `flat_rate` |
| `method_label` | S | Display label, e.g. `"UPS Ground"` |
| `base_rate_cents` | N | Default flat rate in cents (≥ 0) |
| `currency` | S | ISO 4217 code, e.g. `"usd"`; defaults to `S.shipping_default_currency` |
| `transit_days_min` | N | Optional lower bound on transit days |
| `transit_days_max` | N | Optional upper bound on transit days |
| `online_tracking` | BOOL | Inherited from parent carrier; stored for denormalised reads |
| `enabled` | BOOL | Soft-disable; defaults `True` on add |
| `created_at` | N | `now_ts()` |
| `updated_at` | N | `now_ts()` |

`base_rate_cents` is the default rate input used by SHP-006's built-in estimator when no weight-based breakpoint overrides apply.

Five carrier headers with their methods. Each `carrier_id` is deterministic from `carrier_code`.

## 4. API / Service Design

All public functions live in `app/services/shipping_carriers.py`. There are no endpoints in this ticket — those are SHP-005. Functions are synchronous (no `async`), following the inventory and returns_rma service pattern.

### 4.1 Module-level helpers

```python
import hashlib
from typing import Any, Dict, List, Optional

from app.core.settings import S
from app.core.tables import T
from app.core.time import now_ts
from app.services.alerts import audit_event
from app.services.carrier_tracking import CARRIER_TRACKING_URLS


SUPPORTED_CARRIER_CODES = {"ups", "fedex", "usps", "dhl", "manual"}

SUPPORTED_METHOD_CODES = {"ground", "express", "overnight", "economy", "flat_rate"}


def _flag_on() -> bool:
    return bool(getattr(S, "shipping_enabled", False))


def _require_enabled() -> None:
    if not _flag_on():
        from fastapi import HTTPException
        raise HTTPException(status_code=404, detail="Shipping is not enabled")


def _carrier_id(carrier_code: str) -> str:
    """Deterministic carrier_id: sha256(carrier_code)[:16]."""
    return hashlib.sha256(carrier_code.encode("utf-8")).hexdigest()[:16]


def _method_sk(method_code: str) -> str:
    return f"METHOD#{method_code}"


def _online_tracking(carrier_code: str) -> bool:
    return carrier_code in CARRIER_TRACKING_URLS
```

### 4.2 Carrier CRUD functions

```python
def create_carrier(
    *,
    carrier_code: str,
    display_name: str,
    user_sub: str,
) -> Dict[str, Any]:
    """Create a carrier header row. Raises 409 if carrier_code already exists."""
```

- Validates `carrier_code` against `SUPPORTED_CARRIER_CODES`; raises `HTTPException(422, ...)` on unknown code.
- Derives `carrier_id = _carrier_id(carrier_code)`.
- Sets `online_tracking = _online_tracking(carrier_code)`, `enabled = True`.
- Uses `put_item` with `ConditionExpression="attribute_not_exists(carrier_id)"` to prevent overwriting an existing carrier header. Catches `ConditionalCheckFailedException` → raises `HTTPException(409, "Carrier already exists")`.
- Emits `audit_event("shipping_carrier.created", user_sub, None, carrier_id=..., carrier_code=..., outcome="success")`.
- Returns the written dict.

```python
def get_carrier(carrier_id: str) -> Optional[Dict[str, Any]]:
    """Fetch carrier header by carrier_id. Returns None if not found."""
```

- Calls `T.shipping_carriers.get_item(Key={"carrier_id": carrier_id, "sk": "CARRIER#"})`.
- Returns `resp.get("Item")` (may be `None`).

```python
def get_carrier_by_code(carrier_code: str) -> Optional[Dict[str, Any]]:
    """Fetch carrier header by carrier_code via GSI_CODE. Returns None if not found."""
```

- Queries `GSI_CODE` with `carrier_code = :code AND sk = :header_sk` where `:header_sk = "CARRIER#"`.
- Returns the single item or `None`.

```python
def list_carriers(
    *,
    include_disabled: bool = False,
) -> List[Dict[str, Any]]:
    """Return all carrier header rows, optionally including disabled ones."""
```

- Scans `T.shipping_carriers` with `FilterExpression="sk = :header AND attribute_exists(carrier_id)"` where `:header = "CARRIER#"`.
- When `include_disabled=False`, adds `AND enabled = :true` to the filter.
- Returns sorted by `carrier_code` for deterministic output.
- **Note**: The table is small (≤ 20 rows at any realistic scale), so a full-table scan is acceptable. There is no pagination cursor needed.

```python
def update_carrier(
    carrier_id: str,
    *,
    display_name: Optional[str] = None,
    user_sub: str,
) -> Dict[str, Any]:
    """Update carrier header fields. Returns updated item. Raises 404 if not found."""
```

- Fetches the existing row; 404 if absent.
- Builds a `SET` expression for any non-None arguments plus `updated_at = :ts`.
- Uses `update_item` with `ConditionExpression="attribute_exists(carrier_id)"`.
- Emits `audit_event("shipping_carrier.updated", user_sub, None, carrier_id=..., fields_updated=[...], outcome="success")`.
- Returns the post-update item via `get_carrier`.

```python
def disable_carrier(carrier_id: str, *, user_sub: str) -> Dict[str, Any]:
    """Soft-disable a carrier. Disabled carriers are hidden from rate estimation."""
```

- Calls `update_item` setting `enabled = :false, updated_at = :ts` with `ConditionExpression="attribute_exists(carrier_id)"`.
- Does **not** touch method rows (method rows retain their `enabled` flag independently; the carrier-level disable is an override that the rate engine checks at the carrier level before examining method rows).
- Emits `audit_event("shipping_carrier.disabled", user_sub, None, carrier_id=..., outcome="success")`.
- Returns updated carrier header.

### 4.4 Idempotent seed function

```python
def seed_default_carriers() -> int:
    """Seed the default carrier + method set idempotently.

    Returns the number of carrier header rows created (0 = already seeded).
    Individual method rows that already exist are also skipped without error.
    """
```

- Iterates over `_DEFAULT_CARRIERS` (module-level constant list, defined in §3.3 above).
- For each entry in `_DEFAULT_CARRIERS`:
  1. Attempts `put_item` on the carrier header row with `ConditionExpression="attribute_not_exists(carrier_id)"`. Catches `ConditionalCheckFailedException` and continues (already exists is a success for idempotency).
  2. For each method in the carrier's default method list, attempts `put_item` on the method row with the same conditional. Catches `ConditionalCheckFailedException` and continues.
- Does **not** call `_require_enabled()` — seeding should work even before the flag is on (so a migration script can seed the table as part of deployment before the flag is flipped).
- Emits a single `audit_event("shipping_carriers.seeded", "system", None, created=N)` at the end.
- Returns count of carrier header rows written (not total rows — methods are not counted separately).

## 5. Detailed Behavior & Edge Cases

### 5.1 Disable carrier — effect on rate estimation

`disable_carrier` sets `enabled=False` on the carrier header row only. It does not cascade to method rows. The rate engine (SHP-006) must check the carrier-level `enabled` flag before iterating methods. A disabled carrier's methods will never appear in a rate quote, even if the method row itself has `enabled=True`. This means re-enabling a carrier (`update_carrier` setting `enabled=True`) immediately exposes all its methods without a separate method re-enable step.

Historical shipments referencing a disabled carrier are not touched — `shipments` rows retain their `carrier_code`/`method_code` and remain queryable. The disable only prevents new rate quotes and shipment creation from selecting that carrier.

### 5.2 disable_method — effect on estimation

A disabled method row is excluded from `list_methods(include_disabled=False)` and from `list_enabled_methods_all_carriers()`. A method can be disabled even if its parent carrier is enabled. Historical shipments referencing the method are unaffected.

### 5.3 Duplicate carrier_code — conditional put semantics

`create_carrier` uses `attribute_not_exists(carrier_id)` on the PK, not on `carrier_code`. Because `carrier_id` is deterministic from `carrier_code`, two concurrent `create_carrier("ups")` calls will attempt to write the same PK. Exactly one will succeed; the other sees `ConditionalCheckFailedException` → 409. This is the correct behavior: no duplicates, no silent data loss.

### 5.4 add_method — carrier must exist and be non-disabled

`add_method` fetches the carrier header first. If the carrier does not exist, it returns 404. If the carrier is disabled, `add_method` also returns 404 (to prevent phantom methods on an inactive carrier). An admin who wants to add a method to a disabled carrier must re-enable it first.

### 5.5 Seed default — re-entrant safety

`seed_default_carriers` can be called at every app startup or by a migration script without any lock. Each `put_item` is conditional; concurrent calls on a fresh table race to create each row — all rows eventually exist, no duplicates are created. On a fully-seeded table, all conditional puts fail silently (caught `ConditionalCheckFailedException`) and the function returns 0.

### 5.6 Unknown carrier_code in create_carrier

Only codes in `SUPPORTED_CARRIER_CODES = {"ups", "fedex", "usps", "dhl", "manual"}` are accepted. A caller submitting `"royalmail"` gets `HTTPException(422, "Unknown carrier code: royalmail. Supported: ups, fedex, usps, dhl, manual")`. This validation is at the service layer, not only at the router/Pydantic layer, so unit tests can exercise it directly without going through FastAPI.

### 5.7 online_tracking flag derivation

`_online_tracking(carrier_code)` returns `carrier_code in CARRIER_TRACKING_URLS`. For the four known carriers (`ups`, `fedex`, `usps`, `dhl`) this is `True`. For `manual`, `CARRIER_TRACKING_URLS` does not contain `"manual"` (`carrier_tracking.py:10`), so this returns `False`. For any future custom carrier added via `create_carrier` with a code not in `CARRIER_TRACKING_URLS`, the flag is also `False`.

The `online_tracking` value is written once at creation time and is also denormalised onto method rows. If a future ticket adds a new carrier to `CARRIER_TRACKING_URLS`, existing carrier rows would need an explicit `update_carrier` call to reflect the change — this is intentional (no silent flag drift).

### 5.8 currency default

`add_method` defaults `currency` to `getattr(S, "shipping_default_currency", "usd")`. `S.shipping_default_currency` is introduced by SHP-002 (env `SHIPPING_DEFAULT_CURRENCY`, default `"usd"`). The `getattr` with a fallback means the service degrades gracefully if SHP-002 is not yet merged — tests that freeze `S` without the new field still work.

### 5.9 transit_days ordering validation

`update_method` and `add_method` validate that when both `transit_days_min` and `transit_days_max` are provided, `transit_days_min <= transit_days_max`. Violation raises `HTTPException(422, "transit_days_min must be <= transit_days_max")`. Either field can be provided alone (the other remains `None`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No dev_mode branch

`app/services/shipping_carriers.py` contains zero `if S.dev_mode` conditionals. All code paths — seed, CRUD, conditional puts — run identically against moto in dev and real DynamoDB in prod. This matches the invariant established by `app/services/inventory.py` and `app/services/returns_rma.py`.

### 7.2 Idempotency guarantees

- **seed_default_carriers**: fully idempotent via `attribute_not_exists(carrier_id)` conditional puts. Re-seeding on a populated table is a no-op.
- **create_carrier**: idempotent under retry for the same `carrier_code` — the second call gets 409, not a silent overwrite.
- **update_carrier / update_method**: last-writer-wins semantics (no optimistic-lock version check needed for catalog data; concurrent admin edits are rare and the last write wins gracefully). `updated_at` is always written.
- **disable_carrier / disable_method**: idempotent — disabling an already-disabled carrier/method is a no-op update.

### 7.3 No money-out paths

SHP-004 manages catalog data only. There are no billing, ledger, or refund operations in this service. No calls to `new_ledger_entry` or `refund_payment`.

### 7.4 Audit trail

Every mutating function emits `audit_event(...)` to `T.alerts` as a best-effort fire-and-forget call (no try/except wrapper around it at the call site — if audit fails, it propagates and the caller surfaces a 500, which is the safer posture for catalog mutations that affect rate estimation downstream). The `user_sub` parameter is the authenticated admin's `sub` from the session (`require_admin_or_root_csrf` from `app/auth/policy.py:100` in SHP-005 — **not** `require_admin_session`, which does not exist in this codebase; the analogous OFBiz routers `inventory.py` and `returns_rma.py` both use `require_admin_or_root_csrf`); for the seed function it is the string literal `"system"`.

### 7.5 Carrier code as public surface

`carrier_code` values (`ups`, `fedex`, `usps`, `dhl`, `manual`) are stable identifiers used in `CARRIER_TRACKING_URLS`, `detect_carrier`, and will be used in shipment rows. They must never be renamed silently — `update_carrier` intentionally does not expose `carrier_code` as an updatable field. Only `display_name` and `enabled` are mutable on the carrier header.

### 8.2 Adding shipping_carriers table handle to Tables

### 8.3 Seed on fresh vs. existing deployments

In dev, `seed_default_carriers()` should be called from a startup hook or from a one-time script. The spec proposes that SHP-005's router registration also hooks `seed_default_carriers()` into the `on_startup` lifecycle when `S.shipping_enabled` is True — but that is SHP-005's implementation detail. For this ticket, `seed_default_carriers` is a standalone callable that can be invoked from `scripts/local-ddb-seed.py` or a migration script.

In production, the `shipping_carriers` table is empty on first deployment. Enabling `SHIPPING_ENABLED=true` without seeding first means the rate engine (SHP-006) sees zero carriers and returns an empty-but-valid quote (per SHP-006's acceptance criteria). An explicit seed step is required before the shipping flag is flipped on in production.

## 10. Open Questions / Assumptions

1. **Assumption**: SHP-002 and SHP-003 are merged before SHP-004 implementation begins — `T.shipping_carriers` handle exists and `CarrierOut` / `ShipmentMethodOut` are importable from `app/models`.

2. **Assumption**: `S.shipping_default_currency` is added by SHP-002 (env `SHIPPING_DEFAULT_CURRENCY`, default `"usd"`). SHP-004 references it with a `getattr(S, "shipping_default_currency", "usd")` fallback.

3. **Assumption**: The seed `base_rate_cents` values in §3.3 are reasonable default placeholders. They are easily overridable by an admin via `update_method`. A future ticket could expose a seed-overrides config mechanism; for now the values are hardcoded in the service module.

4. **Open question**: Should `disable_carrier` also cascade to disable all method rows? The current design says no (carrier-level disabled is a runtime gate; method rows are not touched). This simplifies re-enabling: flipping the carrier back on exposes all pre-existing methods. If a product requirement emerges that methods must be independently archived on carrier disable, this is a backward-compatible add.

5. **Open question**: Does `update_method` need to support changing `method_code`? The current design says no — `method_code` is part of the SK (`METHOD#{method_code}`) and cannot be changed in place. Renaming would require delete + re-add, which would break any historical `ShipmentOut` rows referencing the old code. This is the safer default.

6. **Assumption**: `SUPPORTED_METHOD_CODES` is intentionally closed at `{"ground", "express", "overnight", "economy", "flat_rate"}` for now. A later ticket could make it extensible (e.g., allow arbitrary strings), but closed validation simplifies the SHP-006 rate engine which maps method codes to transit-day estimates.

7. **Assumption**: The `manual` carrier's `flat_rate` method with `base_rate_cents=0` is the correct default. Real manual shipments would have the admin update the method's rate or the order-level shipping cost added separately. This is a known limitation of the current scope.

8. **Open question**: Should `seed_default_carriers()` be called from a startup hook (registered in `main.py`) or from `scripts/local-ddb-seed.py`? The `notification_templates` precedent (`app/services/notification_templates.py:102`) seeds on startup behind a flag. SHP-005 may register the startup hook; for SHP-004 we leave the call site undefined and only implement the function.
