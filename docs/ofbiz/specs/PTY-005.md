**Ticket type:** Feature | **Priority:** P0 | **Estimate:** 2 days  
**Milestone:** 2 — Party Service Core  
**Depends on:** PTY-004 (`app/services/party.py` with `T.party` + `get_party`), PTY-003 (`CrmPartyRoleType`, `CrmAddRoleIn`, `CrmPartyRoleOut` models), PTY-002 (`T.party` handle + `GSI1` definition), PTY-001 (`S.party_crm_enabled` flag)

## 1. Summary & Goal

PTY-005 extends `app/services/party.py` (created by PTY-004) with four functions that manage the
many-to-many mapping between parties and their roles:

| Function | Purpose |
|---|---|
| `add_role(party_id, role_type) -> dict` | Idempotent write of a `ROLE#…` child row; no-op if already present |
| `remove_role(party_id, role_type) -> None` | Delete the `ROLE#…` row; no-op if absent |
| `list_roles(party_id) -> list[dict]` | Return all roles held by a single party |
| `parties_with_role(role_type) -> list[dict]` | Return all parties holding a given role via `GSI1` (O(1) index query, not a scan) |

Together they implement the OFBiz `PartyRole` entity pattern using DynamoDB's single-table design:
each role is a child row stored under the same partition key as the party's `META` row (`PK =
PARTY#{party_id}`), and a `GSI1` projection makes the reverse lookup cheap. The feature is
entirely additive: with `S.party_crm_enabled` off the new endpoints return HTTP 503 and the four
service functions are never invoked through the normal request path.

### 2.3 Idempotent conditional-put pattern

`app/services/provider_oauth.py:143` and `app/services/file_mounts.py:159` use
`ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)"` for idempotent
puts. PTY-005 follows the same pattern on the `ROLE#` row: if the role row already exists,
`ConditionalCheckFailedException` is caught and the existing row is returned without error. This
mirrors the idempotent create in PTY-004 (`ConditionExpression="attribute_not_exists(PK)"`),
extended here to check both key components because the `party` table is a single-table design
where `PK` is shared by multiple row types.

The relevant error-code detection helper is already established by `app/services/kyc_cases.py:112`
[VERIFIED]:

```python
def _is_conditional_conflict(exc: ClientError) -> bool:
    return str(exc.response.get("Error", {}).get("Code", "")) == "ConditionalCheckFailedException"
```

PTY-005 adds the same private helper to `app/services/party.py` (it may already be present if
PTY-004 uses it for `update_party_status`; if so, PTY-005 reuses it without duplicating).

### 2.4 `delete_item` for non-existing rows

DynamoDB's `delete_item` is a no-op when the key does not exist — it returns `{}` rather than
raising an error. This means `remove_role` requires no existence check: simply call
`T.party.delete_item(Key={"PK": f"PARTY#{party_id}", "SK": f"ROLE#{role_type}"})`. This matches
the pattern used by `app/services/addresses.py:108` [VERIFIED]
(`T.addresses.delete_item(Key={"user_sub": ..., "address_id": ...})`).

## 3. Data Model

### 3.1 Role child row

Each role assignment is a single DynamoDB item:

```json
{
  "PK":        "PARTY#<party_id>",
  "SK":        "ROLE#<role_type>",
  "party_id":  "<party_id>",
  "role_type": "<role_type>",
  "created_at": 1749200000,
  "GSI1PK":   "ROLE#<role_type>",
  "GSI1SK":   "PARTY#<party_id>"
}
```

**Field notes:**

- `PK` and `SK` are the primary key. `PK = PARTY#{party_id}` places the role row in the same
  partition as the `META` row — enabling a single `query(PK=PARTY#{party_id})` to return both
  the party's metadata and all its roles in one round-trip (as used by `list_roles`).
- `SK = ROLE#{role_type}` distinguishes role rows from the `META` row and from future row types
  (`REL#…` for relationships, `MECH#…` for contact mechs). The `ROLE#` prefix makes `list_roles`
  filterable with a `begins_with` condition rather than a post-filter scan.
- `GSI1PK = ROLE#{role_type}` enables `parties_with_role(role_type)` to query all parties holding
  a given role with one GSI query.
- `GSI1SK = PARTY#{party_id}` is the sort key on `GSI1`. It is a String (confirmed in
  `docs/ofbiz/specs/PTY-002.md:418`) and makes results alphabetically ordered by `party_id`.
- `created_at` is an integer Unix timestamp from `app/core/time.now_ts()` (used for audit only;
  not a GSI sort key on `GSI1`, so no `attr_types` override is needed for this field beyond what
  PTY-002 already declared for `GSI_CREATED`).

### 3.2 No schema changes required

The `party` table definition in `scripts/local-ddb-init.py` (added by PTY-002) already includes
`GSI1` with `GSI1PK` / `GSI1SK`. PTY-005 writes no new tables, adds no new GSIs, and makes no
changes to `scripts/local-ddb-init.py` or `app/core/tables.py`.

### 3.3 Role row co-residency with `META` row

`T.party.query(KeyConditionExpression=Key("PK").eq(f"PARTY#{party_id}") & Key("SK").begins_with("ROLE#"))`
returns only role rows within a party's partition. This is the `list_roles` implementation.
Using `begins_with("ROLE#")` is intentional: it ensures that a future `begins_with("REL#")` or
`begins_with("MECH#")` query on the same partition does not interfere.

#### `add_role` — detailed contract

```python
def add_role(party_id: str, role_type: str) -> Dict[str, Any]:
```

1. Validate `role_type in _VALID_ROLE_TYPES`; raise `ValueError(f"invalid_role_type: {role_type}")`.
2. Verify the party exists: `existing_party = get_party(party_id)`. If `None`, raise `KeyError(party_id)`.
3. Build the role item:
   ```python
   item = {
       "PK": f"PARTY#{party_id}",
       "SK": f"ROLE#{role_type}",
       "party_id": party_id,
       "role_type": role_type,
       "created_at": now_ts(),
       "GSI1PK": f"ROLE#{role_type}",
       "GSI1SK": f"PARTY#{party_id}",
   }
   ```
4. Call `T.party.put_item(Item=item, ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)")`.
5. On `ClientError` with `ConditionalCheckFailedException`: the role already exists. Fetch and
   return the existing row:
   ```python
   resp = T.party.get_item(Key={"PK": f"PARTY#{party_id}", "SK": f"ROLE#{role_type}"})
   return resp["Item"]
   ```
   No audit event is emitted on idempotent replay.
6. On success, call:
   ```python
   audit_event(
       "party_role_added",
       existing_party.get("user_sub") or "system",
       None,
       party_id=party_id,
       role_type=role_type,
   )
   ```
7. Return the `item` dict.

#### `remove_role` — detailed contract

```python
def remove_role(party_id: str, role_type: str) -> None:
```

1. Validate `role_type in _VALID_ROLE_TYPES`; raise `ValueError`.
2. Check if the role currently exists — fetch it to determine whether to emit an audit event:
   ```python
   resp = T.party.get_item(Key={"PK": f"PARTY#{party_id}", "SK": f"ROLE#{role_type}"})
   existing_role = resp.get("Item")
   ```
3. Call `T.party.delete_item(Key={"PK": f"PARTY#{party_id}", "SK": f"ROLE#{role_type}"})`.
   (No-op if the item is absent — DynamoDB semantics guarantee this.)
4. If `existing_role` was found (step 2), emit:
   ```python
   audit_event(
       "party_role_removed",
       "system",      # no party user_sub lookup here to keep remove_role lightweight
       None,
       party_id=party_id,
       role_type=role_type,
   )
   ```
   If `existing_role` was `None`, return silently — no audit event, no error.

**Design note on the pre-fetch in `remove_role`:** The audit event is only meaningful when a role
is actually present. A fire-and-forget `delete_item` without a pre-check would generate spurious
`party_role_removed` audit events on calls that remove nonexistent roles. The two-step
(get → delete) pattern has a small TOCTOU window but is acceptable here because role deletion is
not a critical financial operation. Callers who need a stronger atomicity guarantee should use a
`ConditionExpression="attribute_exists(PK)"` on the `delete_item` call and catch
`ConditionalCheckFailedException`.

#### `list_roles` — detailed contract

```python
def list_roles(party_id: str) -> List[Dict[str, Any]]:
```

Query the primary key range within the party's partition:

```python
resp = T.party.query(
    KeyConditionExpression=Key("PK").eq(f"PARTY#{party_id}") & Key("SK").begins_with("ROLE#"),
)
return resp.get("Items", [])
```

No pagination loop is needed for Phase 1: a single party is expected to hold at most ~20 roles,
which is far below DynamoDB's 1 MB page limit. If a future requirement mandates > 100 roles per
party, a pagination loop must be added.

**No existence check on `list_roles`:** This is intentional. The function returns an empty list for
a party that has no roles, regardless of whether the party record itself exists. Callers who need a
404 for unknown parties must call `get_party(party_id)` first (the router does this).

#### `parties_with_role` — detailed contract

```python
def parties_with_role(role_type: str) -> List[Dict[str, Any]]:
```

1. Validate `role_type in _VALID_ROLE_TYPES`; raise `ValueError`.
2. Query `GSI1` with a pagination loop (DynamoDB may paginate large role membership lists):
   ```python
   items = []
   last_key = None
   while True:
       kwargs: Dict[str, Any] = {
           "IndexName": "GSI1",
           "KeyConditionExpression": Key("GSI1PK").eq(f"ROLE#{role_type}"),
       }
       if last_key:
           kwargs["ExclusiveStartKey"] = last_key
       resp = T.party.query(**kwargs)
       items.extend(resp.get("Items", []))
       last_key = resp.get("LastEvaluatedKey")
       if not last_key:
           break
   return items
   ```
3. Returns a list of role-row dicts (each carrying `party_id`, `role_type`, `created_at`, `GSI1PK`,
   `GSI1SK`). Callers who need full party META records must follow up with `get_party(row["party_id"])`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent `add_role`

Two calls with the same `(party_id, role_type)` pair must both succeed. The conditional put
(`attribute_not_exists(PK) AND attribute_not_exists(SK)`) enforces this atomically at the database
layer.

- **First call:** `put_item` succeeds; row written; audit event emitted. Returns new item.
- **Second call:** `put_item` raises `ConditionalCheckFailedException`; service reads the existing
  row via `get_item` and returns it. No audit event emitted (the role was not newly added).
- **Caller behavior:** both calls receive HTTP 201. The `created_at` field in the response will be
  identical for both calls (the value from the first write), allowing callers to detect replays if
  needed.

### 5.2 Removing a non-existent role

`remove_role(party_id, "SUPPLIER")` when the party holds no `SUPPLIER` role is explicitly a no-op:

- `get_item` for the role row returns `{}` (no `"Item"` key).
- `delete_item` is called (no-op in DynamoDB).
- No audit event emitted.
- No exception raised.
- Router returns HTTP 204.

This matches the ticket's acceptance criterion: "removing a non-existent role does not error".

### 5.3 `remove_role` on a non-existent party

`remove_role` does not call `get_party`. If the `party_id` does not exist as a `META` row, the
`delete_item` call is still a no-op (there is no role row to delete). The function returns silently.
Callers who need a 404 on an unknown party should call `get_party` explicitly before `remove_role`.
The router does not perform this check for the DELETE endpoint — the intent is idempotent cleanup,
not strict existence enforcement. This is documented as a deliberate API design choice (Section 10).

### 5.4 `list_roles` for a party with no roles

Returns an empty list `[]`. The `query` call with `begins_with("ROLE#")` returns zero items rather
than raising an error. The router wraps this in `{"roles": [], "count": 0}`.

### 5.5 `parties_with_role` pagination

The GSI1 query uses a `while True` loop with `LastEvaluatedKey` to handle arbitrarily many parties
sharing the same role. DynamoDB's 1 MB page limit is hit when approximately 5000–10000 role rows
share the same `GSI1PK` value. For Phase 1 party counts this is not a concern, but the loop is
correct by construction. The function returns the full list in memory rather than streaming — for
very large datasets a cursor-based endpoint should be added.

### 5.6 `parties_with_role` returns role rows, not party META rows

The GSI1 projection includes all attributes of the role row (`party_id`, `role_type`, `created_at`,
`GSI1PK`, `GSI1SK`). It does not include party META attributes (`party_type`, `status`, etc.).
Callers who need full party details must follow up with `get_party(row["party_id"])` for each
result. The endpoint `/ui/party/by-role/{role_type}` intentionally returns the lightweight role
projection to avoid N+1 DynamoDB calls at the API boundary.

### 5.7 `role_type` case sensitivity

`CrmPartyRoleType` values are uppercase (e.g. `"CUSTOMER"`). The service validates against the
frozen set of uppercase strings. A caller sending `"customer"` (lowercase) receives HTTP 422. No
case-normalization is applied — this is consistent with how other enum-validated fields work in
the codebase (e.g., `party_type` validation in `create_party`).

### 5.8 Concurrent `add_role` from two processes

Two concurrent `add_role(party_id, "SUPPLIER")` calls will race on the conditional put. Exactly one
will win; the other will catch `ConditionalCheckFailedException` and read the existing row. Both
return the same role item. No duplicate rows are created. This is the same atomicity guarantee as
PTY-004's idempotent `create_party`.

### 5.9 `list_roles` co-residency with future row types

When PTY-006 (relationships) and PTY-007 (contact mechs) add rows with `SK = REL#…` and
`SK = MECH#…` to the same partition, the `begins_with("ROLE#")` key condition expression on
`list_roles` ensures those future rows are never accidentally included in the roles list. This is
the key benefit of the prefixed SK design.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

`app/services/party.py` contains no `S.dev_mode` branch. All four new service functions operate
identically in dev (moto-backed DynamoDB Local at `http://localhost:8001`, credentials from
`.env.local`) and prod (real DynamoDB). The only environment-specific behaviour is the DynamoDB
endpoint URL, which is transparent to the service code.

### Idempotency

`add_role` uses a conditional put (`attribute_not_exists(PK) AND attribute_not_exists(SK)`) for
atomic idempotency — no pre-check race window. `remove_role` uses DynamoDB's native no-op semantics
for absent keys. Both patterns are already established in the codebase
(`app/services/provider_oauth.py:143` [VERIFIED], `app/services/addresses.py:108` [VERIFIED]).

### Security

- **No PII in role row keys.** `PK = PARTY#<party_id>` and `SK = ROLE#<role_type>` carry only
  opaque identifiers. `party_id` is either a truncated SHA-256 or a `uuid4().hex` (no user email,
  name, or phone).
- **No money-out path.** PTY-005 has no billing, ledger, or payment integration. The GL/refund
  constraints in the cross-cutting requirements do not apply.
- **`require_ui_session` scoping.** Any authenticated user can add or remove roles on any party by
  `party_id`. There is no per-user ownership enforcement at this stage — the same gap acknowledged
  in PTY-004 (Section 7). Scoped access control is deferred to a later milestone.
- **`role_type` is not a free-form string.** Validation against `_VALID_ROLE_TYPES` prevents
  injection of arbitrary strings into GSI partition keys (which are stored as `ROLE#{role_type}`).
  An invalid role type is rejected with HTTP 422 before any DynamoDB write.
- **Audit trail.** Every first-time `add_role` and every effective `remove_role` emits an
  `audit_event` to `T.alerts`, following the same pattern as all other service-layer mutations
  in the codebase. Idempotent replays do not generate duplicate audit events.

## 10. Open Questions / Assumptions

1. **PTY-004 is assumed to be merged before PTY-005 is implemented.** If PTY-004 is delayed,
   PTY-005 cannot proceed because it extends `app/services/party.py` and calls `get_party`.

2. **PTY-003 models are assumed present.** `CrmPartyRoleType`, `CrmAddRoleIn`, and `CrmPartyRoleOut`
   are assumed to be in `app/models.py` when PTY-005 ships. If PTY-003 is delayed, the service
   can use a hardcoded `frozenset` of valid role type strings and the router can inline minimal
   Pydantic models. The PTY-004 spec (`docs/ofbiz/specs/PTY-004.md:671-673`) acknowledges the
   same fallback.

3. **`remove_role` does NOT verify party existence.** The design choice (Section 5.3) is that
   `remove_role` is a no-op for both nonexistent roles and nonexistent parties. An alternative
   design would call `get_party(party_id)` and raise `KeyError` for unknown parties. The current
   choice is deliberate: the DELETE endpoint semantics are "ensure this role is absent" rather
   than "assert the party exists and then remove the role". If the codebase convention shifts to
   require party validation on all writes, this should be revisited.

4. **`parties_with_role` returns all parties globally, not scoped to the requesting user.** This
   is the same gap as PTY-004's list endpoints (Section 7 of the PTY-004 spec). A future ticket
   should add per-organisation scoping when multi-tenant isolation is required.

5. **`parties_with_role` returns role rows, not full party objects.** Callers need a separate
   `get_party` call per row to get full party details. If the typical use case is always "parties
   with role + their names/type", a composite query (batch-get after the GSI query) should be
   considered in a follow-up ticket.

6. **`list_roles` does not paginate.** If a party could hold more than ~5000 roles, the single
   `query` call could silently truncate results. For Phase 1 (small enum of 7 role types) this is
   not possible — a party can hold at most 7 distinct roles. This assumption must be revisited if
   `CrmPartyRoleType` is extended to dozens of values and a party can hold many of them.

7. **`CrmPartyRoleOut` as a list-element vs a dedicated detail type.** The spec uses
   `CrmPartyRoleOut` as both the single-role response (from `POST …/roles`) and as list elements
   (from `GET …/roles` and `GET /by-role/…`). If a future ticket needs to embed full party
   metadata inline the list response, a distinct `CrmRoleWithPartyOut` model would be needed.

8. **Route ordering in `app/routers/party.py`.** The `GET /ui/party/by-role/{role_type}` endpoint
   must be declared before `GET /ui/party/{party_id}`. The implementer must audit the route
   declaration order in the file as it exists after PTY-004 is merged, not as described in the
   PTY-004 spec, since other tickets may have been merged in between.

9. **Audit `user_sub` in `remove_role`.** The current design passes `"system"` as `user_sub` to
   `audit_event` in `remove_role` because the service function does not receive the requesting
   user's sub (it is not a parameter). An alternative is to add an optional `actor_sub` parameter
   to `remove_role` and thread the `ctx["user_sub"]` down from the router. This is a low-priority
   improvement; the current approach matches how `create_party` handles the `user_sub or "system"`
   fallback.
