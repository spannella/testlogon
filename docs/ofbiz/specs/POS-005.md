# POS-005 — POS cart binding — scan/add line items reusing shoppingcart

**Type:** Feature | **Priority:** P0 | **Estimate:** 4 days

---

## 1. Summary & Goal

POS-005 adds `bind_txn_draft`, `add_line_item`, `set_line_item_qty`, and `remove_line_item` to `app/services/pos_register.py` (or a co-located `app/services/pos_cart.py`). A POS transaction draft acquires exactly one standard shopping cart owned by the cashier's `user_sub`; all item math then flows through the existing `app/services/shoppingcart.py` primitives (`add_item`, `list_items`, `set_item_quantity`, `decrement_item`, `_item_from_item`, `cart_total_cents`). POS introduces no parallel pricing, no duplicate inventory reservation, and no duplicated total calculation — it is a thin wrapper that translates a "scan" into an `add_item` call and surfaces the same running total that `purchase_cart` will later consume.

The ticket is scoped to the cart-binding and line-item mutation layer only. Settlement (POS-006/007), void/refund (POS-008), receipt (POS-009), and the HTTP router (POS-011) are downstream dependencies.

## 2. Context & Current State

### 2.1 Shopping cart primitives

`app/services/shoppingcart.py` provides all cart operations required:

- `_item_sk(cart_id, sku)` at `:38` — DynamoDB SK key helper for line items.
- `_catalog_item_key(category_id, item_id)` at `:42` — DDB key for catalog lookup, used by `add_catalog_item`.
- `_item_from_item(item)` at `:79` — projects a DDB item into `{sku, name, quantity, unit_price_cents, line_total_cents, ...}`. `line_total_cents = quantity * unit_price_cents` is computed here; all POS totals must be derived from this function, never inline arithmetic.
- `add_item(user_sub, cart_id, payload)` at `:311` — upserts a line item, accumulates quantity on re-add of the same SKU, calls `_touch_cart_activity`, returns `_item_from_item(...)`.
- `add_catalog_item(user_sub, cart_id, *, category_id, item_id, quantity)` at `:370` — resolves the catalog item via `_catalog_item_key`, builds the payload (sku=`catalog:{item_id}`, name, price_cents, creator_user_id) and delegates to `add_item`.
- `set_item_quantity(user_sub, cart_id, sku, quantity)` at `:400` — sets exact qty; qty ≤ 0 removes the row.
- `decrement_item(user_sub, cart_id, sku, amount)` at `:424` — removes `amount` units; removes row when qty reaches 0.
- `list_items(user_sub, cart_id)` at `:277` — queries `CART#{cart_id}#ITEM#` prefix, sorts by SKU, returns projected items.
- `cart_total_cents(user_sub, cart_id)` at `:301` — `sum(item["line_total_cents"] for item in list_items(...))`.
- `start_cart(user_sub)` at `:256` — creates an OPEN cart with a UUID cart_id, sets TTL from `S.cart_ttl_days` (`:819`).
- `_require_open_cart(cart)` at `:306` — raises 409 if cart status is not `OPEN`.

### 2.2 Catalog lookup

`app/routers/catalog.py:702` defines `_find_item_by_id(item_id)`, which queries `T.catalog` via the `ByItemId` GSI (declared in `scripts/local-ddb-init.py:123`). This allows O(1) resolution of a bare `item_id` without knowing `category_id`. Catalog items carry `PK=CAT#{category_id}`, `SK=ITEM#{item_id}`, `entity="item"`, `name`, `price_cents`, `currency`, `category_id`, `item_id`, and `stock_count` (optional). The serializer `_catalog_item_out()` at `catalog.py:107` documents the full field set. The `_catalog_item_key` helper in shoppingcart at `:42` constructs `{"PK": f"CAT#{category_id}", "SK": f"ITEM#{item_id}"}`.

### 2.3 POS `pos` table and T.pos (established by POS-003)

Per POS-003 the single-table `pos` store has:
- PK `pos_pk` / SK `pos_sk`.
- Row `REGISTER#{register_id}` / `META` — register config.
- Row `SESSION#{session_id}` / `META` — session state (status `open|closed`, `cashier_sub`, `opening_float_cents`, `opened_at`).
- Row `TXN#{txn_id}` / `META` — transaction draft (status `open|tendered|voided|refunded`, `session_id`, `bound_cart_id`, `created_at`).
- GSI `GSI_REGISTER_OPEN` (pk=`register_id`, sk=`opened_at` numeric).
- GSI `GSI_SESSION_TXN` (pk=`session_id`, sk=`created_at` numeric).
- GSI `GSI_CASHIER` (pk=`cashier_sub`, sk=`opened_at` numeric).
- All numeric GSI sort keys declared with `attr_types={"opened_at":"N","created_at":"N"}`.

`T.pos` is wired in `app/core/tables.py` via `_safe_table(S.pos_table_name)`.

### 2.4 pos_register.py (established by POS-004)

POS-004 delivers `create_register`, `open_session`, `get_open_session`, and `close_session` in `app/services/pos_register.py`. The session row carries `cashier_sub` and `status="open"`. POS-005 extends this file (or adds a thin `pos_cart.py` imported by it).

### 2.5 Feature flag

Per POS-003, `S.pos_enabled` is `os.environ.get("POS_ENABLED","0") not in ("0","false","False")` — default `False`. All POS code paths must short-circuit with `HTTPException(status_code=404, detail="POS not enabled")` when this is `False`.

### 2.6 No existing barcode field on catalog items

The catalog item schema (fields visible in `_catalog_item_out()` at `catalog.py:107`) carries `item_id`, `name`, `price_cents`, `attributes` (arbitrary dict), but no dedicated `barcode` top-level attribute. A "scan by barcode" in POS-005 is therefore resolved by treating the scanned value as either an `item_id` (lookup via `ByItemId` GSI) or a free-form `sku` (treated as a raw SKU payload). The `attributes` dict may hold a `barcode` key, but that requires a full-scan; POS-005 avoids that by requiring callers to pass `item_id` for catalog items and raw `sku` for non-catalog quick-add items.

### 2.7 Idempotency convention

`commerce_order_service.py:67` derives `order_id = sha256(correlation_id)[:32]`. POS-005 uses the same pattern: the `txn_id` for a new draft is derived as `sha256(f"pos_txn:{session_id}:{correlation_id}")[:32]` so replaying a `bind_txn_draft` call with the same `correlation_id` returns the same `txn_id` and the same already-bound cart.

## 3. Data Model

POS-005 introduces one new row type and modifies an existing one, all in the single `pos` table already defined by POS-003. No new tables are required.

### 3.1 TXN draft row (new in POS-005)

```
PK  = TXN#{txn_id}          (pos_pk)
SK  = META                   (pos_sk)

Attributes:
  txn_id          str    — sha256(f"pos_txn:{session_id}:{correlation_id}")[:32]
  session_id      str    — FK to SESSION#{session_id}/META
  cashier_sub     str    — denormalized from session for ownership checks
  status          str    — "open" | "tendered" | "voided" | "refunded"
  bound_cart_id   str    — cart_id of the bound cart in T.shopping_cart
  subtotal_cents  int    — snapshot written at bind time, updated after every line mutation
  created_at      int    — now_ts()
  updated_at      int    — now_ts()
  correlation_id  str    — caller-supplied opaque string for idempotent re-bind
```

GSI `GSI_SESSION_TXN` requires denormalized `session_id` (pk) and `created_at` (sk, numeric) on this row so downstream reports (POS-010) can query a session's transactions without scanning.

The `subtotal_cents` value on the TXN row is a **denormalized snapshot** written after every cart mutation; it must always equal `cart_total_cents(cashier_sub, bound_cart_id)`. The canonical source of truth for the total is always `cart_total_cents` — the snapshot is for read convenience and must be refreshed atomically (read-compute-write within the same mutation call).

### 3.2 Session row modification

The existing `SESSION#{session_id}/META` row (from POS-004) is not structurally changed. POS-005 adds no new attributes to it.

### 3.3 Shopping cart row (existing, in T.shopping_cart)

A standard cart row `PK=USER#{cashier_sub}`, `SK=CART#{cart_id}`, `type="cart"`, `status="OPEN"` (created via `start_cart`). Line items are standard `CART#{cart_id}#ITEM#{sku}` rows. No new fields; no schema change. The existing TTL mechanism (`S.cart_ttl_days`) from `:819` applies unchanged.

### 3.4 DynamoDB scripts/local-ddb-init.py changes

The `pos` `TableDef` was established by POS-003 with:

## 4. API / Service Design

### 4.1 New functions in `app/services/pos_register.py`

#### `bind_txn_draft`

```python
def bind_txn_draft(
    cashier_sub: str,
    session_id: str,
    correlation_id: str,
) -> Dict[str, Any]:
```

**Purpose:** Idempotently create or return an open POS transaction draft for the given session, binding it to a freshly-started shopping cart.

**Steps:**
1. Verify `S.pos_enabled`; raise `HTTPException(404)` if not.
2. Load session row `T.pos.get_item(Key={"pos_pk": f"SESSION#{session_id}", "pos_sk": "META"})`. Raise 404 if absent; raise 409 if `status != "open"`.
3. Verify `item["cashier_sub"] == cashier_sub`; raise 403 if mismatch (foreign cashier).
4. Compute `txn_id = hashlib.sha256(f"pos_txn:{session_id}:{correlation_id}".encode()).hexdigest()[:32]`.
5. Attempt `T.pos.put_item` with `ConditionExpression="attribute_not_exists(pos_pk)"` for the new TXN row (status=`"open"`, `bound_cart_id` from a fresh `start_cart(cashier_sub)` call, `created_at=now_ts()`).
6. On `ConditionalCheckFailedException` (row already exists): load and return the existing row — the cart was already bound.
7. Return the TXN row dict.

**Idempotency guarantee:** Two calls with the same `(session_id, correlation_id)` yield the same `txn_id` and the same already-bound cart. The conditional put is the atomicity gate.

#### `add_line_item`

```python
def add_line_item(
    cashier_sub: str,
    txn_id: str,
    *,
    # exactly one of the two scan modes
    sku: str | None = None,               # raw SKU / quick-add
    name: str | None = None,              # required when sku is given
    unit_price_cents: int | None = None,  # required when sku is given
    item_id: str | None = None,           # catalog lookup by item_id
    category_id: str | None = None,       # optional hint; avoids GSI if both given
    quantity: int = 1,
) -> Dict[str, Any]:
```

**Purpose:** Resolve the item (catalog or raw SKU), add it to the bound cart, refresh the TXN's denormalized `subtotal_cents`, and return the updated running total.

**Resolution logic:**
- If `item_id` is provided:
  - If `category_id` is also provided: use `_catalog_item_key(category_id, item_id)` directly (O(1) `get_item` on `T.catalog`).
  - If `category_id` is absent: resolve via `ByItemId` GSI (same as `_find_item_by_id` in `app/routers/catalog.py:702`), filtering `entity="item"`.
  - On 404 (item absent or `entity != "item"`): raise `HTTPException(404, "Catalog item not found")` — cart is never mutated.
  - Build payload for `add_item`: `sku=f"catalog:{item_id}"`, name, `unit_price_cents=int(item["price_cents"])`, `category_id`, `item_id`, `creator_user_id=item.get("creator_id")`.
  - Delegate to `shoppingcart.add_item(cashier_sub, txn["bound_cart_id"], payload)`.
- If `sku` is provided (quick-add path): validate `name` and `unit_price_cents` are present; call `shoppingcart.add_item(cashier_sub, txn["bound_cart_id"], {"sku": sku, "name": name, "quantity": quantity, "unit_price_cents": unit_price_cents})`.

**After add_item:** Call `_refresh_txn_subtotal(cashier_sub, txn_id, bound_cart_id)` (see below).

**Returns:** `{"txn_id": txn_id, "total_cents": <refreshed total>, "item": <ShoppingCartItemOut dict>}`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Unknown SKU / barcode — cart never partially mutated

If `item_id` is provided but the catalog lookup fails (missing row, `entity != "item"`, or out-of-stock check at catalog layer), `add_line_item` raises `HTTPException(404)` before calling `add_item`. Because `add_item` is never invoked, the cart is never touched. The TXN row's `subtotal_cents` is not updated, and `_refresh_txn_subtotal` is not called.

This satisfies the acceptance criterion: "Unknown SKU/barcode → 404; the cart is never left partially mutated."

### 5.2 Re-binding idempotency

`bind_txn_draft` derives `txn_id` deterministically from `sha256(f"pos_txn:{session_id}:{correlation_id}")[:32]`. The DDB conditional put `attribute_not_exists(pos_pk)` is the atomicity gate:
- First call: put succeeds, a new cart is started.
- Subsequent calls with identical `(session_id, correlation_id)`: conditional put raises `ConditionalCheckFailedException`; the handler loads the existing row and returns it with its existing `bound_cart_id`.

The bound cart retains all previously added items across re-bind calls.

### 5.3 Stale `subtotal_cents` on concurrent mutation

`_refresh_txn_subtotal` is a best-effort read-then-write (not a DDB atomic counter). The canonical total is always `cart_total_cents(cashier_sub, bound_cart_id)`. The TXN row snapshot exists for fast reading only. If two clients race on the same TXN (unsupported in normal POS operation — one cashier per session), the snapshot may transiently lag. At tender time (POS-006), `purchase_cart` recomputes `sum(line_total_cents)` at `:496`, so any snapshot discrepancy never affects the settled amount.

### 5.4 Cart status guard

`shoppingcart.add_item` calls `_require_open_cart(cart)` at `:313`, which raises 409 if `status != "OPEN"`. This guard also protects against adding items to a cart that was accidentally purchased or deleted outside POS context.

### 5.5 TXN status guard

`_load_open_txn` raises 409 if `status != "open"`. A tendered, voided, or refunded TXN cannot be re-mutated.

### 5.6 Quantity set to 0 = remove

`set_line_item_qty` with `quantity=0` calls `shoppingcart.set_item_quantity(..., 0)`, which deletes the row at `:409–411`. The refreshed total reflects the removed item. This matches the existing cart behavior.

### 5.7 Catalog currency mismatch

`add_catalog_item` in `shoppingcart.py:387–388` raises 409 if the catalog item's currency differs from the cart's currency. **POS-005 does NOT inherit this guard automatically**: `add_line_item` calls `shoppingcart.add_item` directly (not `add_catalog_item`), which has no currency check. The implementation must explicitly replicate the guard — fetch `cart.get("currency")` from `get_cart(cashier_sub, bound_cart_id)` and compare against `item.get("currency", "USD")` before calling `add_item`, raising 409 on mismatch.

### 5.8 Session closed while cart is mid-transaction

If the session is `closed` (by a concurrent `close_session` call from POS-004), `_load_open_txn` raises 409 (the TXN row reflects the session state indirectly via its own `status`). However, if the TXN was still `"open"` at the time the session was closed, the guard in `_load_open_txn` is at the TXN level; the session check in `bind_txn_draft` (step 2) happens only at bind time. For subsequent mutations, `_load_open_txn` checks TXN status, not session status. POS-008 (void) handles orphaned open TXNs at session-close time.

### 5.9 Catalog item vs raw-SKU total parity

`add_catalog_item` at `:370` sets `unit_price_cents = int(item.get("price_cents", 0))` from the live catalog row. The raw-SKU path passes `unit_price_cents` directly from the caller's payload. In both cases `_item_from_item` at `:79` computes `line_total_cents = qty * unit_price_cents`. `cart_total_cents` at `:301` sums all `line_total_cents`. POS adds no discount or tax at this layer — those are applied at tender/settlement time.

### 5.10 Flag-off behavior

When `S.pos_enabled` is `False`:
- `bind_txn_draft`, `add_line_item`, `set_line_item_qty`, `remove_line_item`, and `list_txn_items` all raise `HTTPException(404, "POS not enabled")` before touching any table.
- No cart is started, no `T.pos` row is written, and the existing `T.shopping_cart` and `T.catalog` tables are byte-for-byte unaffected.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/Prod parity

All DDB writes use the same code path whether `S.dev_mode` is on or off. There is no `if dev_mode` branch. `T.pos` resolves to DynamoDB Local in dev and real DynamoDB in prod — the service code is identical. The catalog lookup (`T.catalog`) and cart mutations (`T.shopping_cart`) use the same frozen handles. No mock paths are introduced in POS-005.

### 7.2 Idempotency

`bind_txn_draft` is idempotent: the `txn_id` is a deterministic hash of `(session_id, correlation_id)`, and the conditional DDB put ensures at-most-one cart is created per unique `(session_id, correlation_id)`. Replaying with identical inputs returns the existing draft.

`add_line_item` is **not** idempotent for the same SKU: a second call accumulates quantity (matching `shoppingcart.add_item:320`, which increments). Callers that need exact-quantity semantics must use `set_line_item_qty`.

### 7.3 Ownership and authorization

- `bind_txn_draft` checks `session["cashier_sub"] == cashier_sub` (403 on mismatch).
- `_load_open_txn` checks `txn["cashier_sub"] == cashier_sub` (403 on mismatch).
- The `cashier_sub` is always taken from `ctx["user_sub"]` in the HTTP handler (from the authenticated session cookie), never from the request body.
- The bound cart is owned by `cashier_sub` (`PK=USER#{cashier_sub}`). A foreign user cannot query or mutate it because `add_item` / `list_items` / `set_item_quantity` in `shoppingcart.py` use `_user_pk(user_sub)` as the DDB PK — ownership is enforced by the access pattern, not a separate check.

### 7.4 CSRF

Non-GET HTTP handlers use `require_ui_session` from `app/services/sessions.py` (`sessions.py:330`), which enforces CSRF for cookie-based requests (matching the pattern used in `app/routers/shoppingcart.py:28`).

### 7.5 No money movement

POS-005 only mutates `T.pos` (TXN draft) and `T.shopping_cart` (cart + items). It writes nothing to `T.billing` and calls no billing service. All money movement is deferred to POS-006 (cash tender via `new_ledger_entry`) and POS-007 (card/wallet tender).

## 8. Backward Compatibility & Migration

### 8.1 Existing routes unchanged

The `app/routers/shoppingcart.py` router (registered at `app/main.py:670`) is not modified. All existing `/ui/shoppingcart/*` endpoints continue to function identically.

### 8.2 No schema migration required

The `pos` table is new (POS-003). The `shopping_cart` table gains no new attributes. The `catalog` table is read-only from POS-005's perspective.

### 8.3 Additive-only with flag off

`S.pos_enabled = False` (the default) means the service functions short-circuit before touching any table. No routing changes are required at `app/main.py` until POS-011 registers the router. The service functions are importable but effectively inert when the flag is off.

### 8.4 Cart TTL

Carts created by `bind_txn_draft` via `start_cart` inherit the standard TTL (`S.cart_ttl_days` at `settings.py:819`). If a POS transaction draft is abandoned (no tender), the cart expires naturally and the TXN row is left in `status="open"`. POS-008 (void) or POS-010 (session close) should explicitly void orphaned open TXNs to avoid confusion, but this is not a correctness issue for POS-005.

## 10. Open Questions / Assumptions

1. **Assumption: `pos_register.py` is the home file.** The ticket says "In `app/services/pos_register.py` (or a thin `pos_cart.py`)". This spec assumes co-location in `pos_register.py` for simplicity. If a separate `pos_cart.py` is preferred, the function signatures are identical and `pos_register.py` re-exports them.

2. **Assumption: no barcode field on catalog items.** The catalog item schema has no `barcode` column in `app/routers/catalog.py:107–127`. Scan-by-barcode is therefore resolved as either `item_id` lookup (catalog path) or raw `sku` (quick-add). If a future `barcode` field is added to catalog items, a `ByBarcode` GSI would be needed. This is deferred.

3. **Assumption: cashier owns the bound cart.** The bound cart's `PK = USER#{cashier_sub}`. If multi-cashier environments require a shared cart (e.g., a cart owned by the register, not the cashier), the `user_sub` passed to `start_cart` and all shoppingcart calls would need to be the register's service identity. This spec assumes single-cashier-per-session ownership (matching POS-004's `cashier_sub` model).

4. **Assumption: `start_cart` is called at bind time.** The cart is created eagerly when `bind_txn_draft` is first called. A lazy approach (create cart on first `add_line_item`) would require a two-phase bind, complicating idempotency. Eager bind is simpler.

5. **Question: stock reservation at add-item time?** `shoppingcart.add_item` does NOT decrement stock at add time — stock is decremented atomically at `purchase_cart` (`:498–538`). POS-005 inherits this behavior. If real-time stock reservation per scan is required (to prevent concurrent oversell on multi-terminal setups), that is a SHOP-001 extension and is out of scope here.

6. **Assumption: `S.cart_ttl_days` applies to POS carts.** No POS-specific cart TTL is introduced. The standard TTL applies. If POS carts should expire faster, a `S.pos_cart_ttl_hours` setting could override, but this is not in scope for POS-005.

7. **Assumption: no tax at this layer.** `subtotal_cents` in the TXN draft is the pre-tax, pre-discount total. Tax computation is a POS-006/007 concern at settlement time. `total_cents` on `PosTransactionOut` (POS-002) is the post-tax, post-discount final amount.
