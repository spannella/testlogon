# ORD-013 — Frontend types & endpoint wrappers

**Type:** Feature | **Priority:** P1 | **Estimate:** 2 days
**Milestone:** 5 — Frontend

---

## 1. Summary & Goal

ORD-013 provides the TypeScript contract layer that bridges the backend API surface delivered by ORD-011/ORD-012 and the React admin/customer UI delivered by ORD-014.

The deliverable is two files:

1. **Type additions to `frontend/src/api/types.ts`** — TypeScript interfaces and a string-literal union type mirroring the ORD-004 Pydantic models (`OrderLifecycleStatus`, `OrderStatusHistoryEntry`, `ShipGroup`, `OrderAdjustment`, `OrderAdjustmentType`, `OrderTransitionRequest`, `OrderTransitionResult`, `OrderLifecycleOut`) plus five request-body/response types introduced by ORD-011 (`OrderAdjustmentIn`, `OrderAdjustmentDeleteResp`, `ShipGroupCreateIn`, `ShipGroupAssignIn`, `OrderCancelIn`) and two paginated list response shapes from ORD-012 (`OrdersByStatusResp`, `ShipGroupsByDateResp`). **Note**: ORD-012's by-ship-date endpoint returns ship groups, not order headers; the TypeScript name is `ShipGroupsByDateResp` (mirrors Pydantic `ShipGroupsByDateOut`).

2. **New `frontend/src/api/endpoints/orderLifecycle.ts`** — Typed endpoint wrappers for every route in the ORD-011 router plus the two ORD-012 list endpoints, using the `api` client from `frontend/src/api/client.ts` (which auto-attaches the CSRF token from the `ui_csrf` cookie on every non-GET call).

The entire set is hidden from the UI when `VITE_ORDER_LIFECYCLE_ENABLED` is `false` (default). With the flag off, the wrapper module still compiles and exports — they simply are not called, because the ORD-014 page and nav entry are not mounted.

## 3. Data Model

ORD-013 introduces no DynamoDB tables, GSIs, or server-side schema. It is a pure TypeScript addition. The DDB schema is owned by ORD-003; the Pydantic models are owned by ORD-004.

For reference, the DDB row shapes that the TypeScript types mirror (for reviewers cross-checking field names):

| Row type | SK pattern | Key attributes carried in the TS type |
|---|---|---|
| Order header | `ORDER` | `order_id`, `status`, `lifecycle_status`, `amount_cents`, `currency`, `updated_ts`, `adjustments?`, `ship_groups?`, `status_history?` |
| Status history | `HIST#{ts:020d}#{event_id}` | `event_id`, `from_status?`, `to_status`, `actor`, `reason`, `ts` |
| Ship group | `SHIPGRP#{ship_group_id}` | `ship_group_id`, `ship_method`, `address_id?`, `item_ids`, `ship_status`, `ship_date_bucket?`, `ship_ts?`, `tracking_number?`, `tracking_url?`, `created_at`, `updated_at` |
| Order adjustment | `ADJ#{adjustment_id}` | `adjustment_id`, `adj_type`, `amount_cents`, `currency`, `label`, `taxable`, `source_rule_ref?`, `created_at` |

The `sk` attribute is a DDB-internal field and is **not** included in any TypeScript interface (it never appears in API responses).

#### 4.1.1 `OrderLifecycleStatus`

```typescript
export type OrderLifecycleStatus =
```

A string-literal union type rather than a `const enum` or `enum`. Rationale: the `api` client deserialises JSON directly to `string`; a string-literal union provides exhaustiveness checking in `switch` statements while being assignment-compatible with `string` values from the API response. This matches the project convention for status fields (e.g. `status: "low_stock" | "out_of_stock" | "in_stock"` implicit in `InventoryRecord`) rather than using TypeScript enums (which have awkward serialisation behavior).

#### 4.1.6 `OrderLifecycleOut`

```typescript
export interface OrderLifecycleOut {
  // Core fields — always present (mirror of commerce_order_service return dict)
  order_id: string;
  status: string;               // legacy "pending_payment" or lifecycle mirror
  created_at: string;           // ISO string (existing convention)
  updated_at: string;           // ISO string
  source_system: string;
  correlation_id: string;
  amount_cents: number;
  currency: string;
  line_item_count: number;
  metadata: Record<string, unknown>;

  // Lifecycle fields — present only when ORDER_LIFECYCLE_ENABLED is on
  lifecycle_status?: OrderLifecycleStatus | null;
  updated_ts?: number | null;    // Unix seconds; GSI_LIFECYCLE_STATUS sort key
  pre_hold_status?: string | null;

  // Enriched collections — null = not fetched; [] = fetched and empty
  adjustments?: OrderAdjustment[] | null;
  ship_groups?: ShipGroup[] | null;
  status_history?: OrderStatusHistoryEntry[] | null;
}
```

`lifecycle_status` and the enriched collections use `| null` (not `| undefined`) because Pydantic serialises `Optional` fields with `None` values as JSON `null` when `response_model_exclude_none` is not set on the endpoint — and ORD-011 does not set that flag. ORD-014 code should treat both `null` and `undefined` as "not present" using optional chaining (`order.adjustments?.length ?? 0`).

**Note on `adjusted_amount_cents`**: ORD-008 writes this value to the DDB `ORDER`-SK header row, but `OrderLifecycleOut` in ORD-004 does NOT include it as a Pydantic field (verified: `docs/ofbiz/specs/ORD-004.md` Section 4.8 shows no `adjusted_amount_cents` in the model; `_header_to_lifecycle_out` in ORD-005 does not map it). It is therefore absent from this TypeScript interface. If a future spec adds it to `OrderLifecycleOut`, add `adjusted_amount_cents?: number | null` here.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag off: wrappers still compile and export; backend returns 503

When `ORDER_LIFECYCLE_ENABLED=false` on the backend, every call to any wrapper will receive `ApiError(503, "Order lifecycle is disabled")`. The `api` client throws this as an `ApiError` (from `client.ts:269–276`). React Query surfaces it as a query/mutation error. ORD-014's page renders a "Feature not available" message. The wrappers themselves do not need to inspect the flag — the flag is enforced exclusively by the backend router guard and reflected to the frontend via the thrown `ApiError`.

On the frontend, `VITE_ORDER_LIFECYCLE_ENABLED=false` prevents the page and nav entry from mounting (via ORD-014 flag gate), so end users never encounter the 503 in normal operation. Developers testing with the flag off can still call the wrappers directly in the browser console and will see the 503 error surfaced by React Query dev tools.

### 5.2 `getOrderLifecycle` with no `include` — null collections

When called as `getOrderLifecycle(orderId)` with no `include` argument, the backend returns `OrderLifecycleOut` with `adjustments: null`, `ship_groups: null`, `status_history: null`. ORD-014 components must guard against this with `order.adjustments ?? []`. The wrapper's return type makes this explicit: `adjustments?: OrderAdjustment[] | null`.

### 5.3 `removeOrderAdjustment` uses `api.del` (not `api.post`)

`api.del` in `client.ts:312` issues `DELETE`. There is no request body for the delete call — the `adjustment_id` is in the URL path only. The backend at `DELETE /ui/orders/{order_id}/adjustments/{adjustment_id}` returns `{"deleted": true}` (verified: ORD-011 Section 4.4 `return {"deleted": True}`). **CORRECTED**: the wrapper uses `OrderAdjustmentDeleteResp` (not `OkResp`) because the shapes differ (`{deleted: boolean}` vs `{ok: boolean}`). Compare with `deleteCart(cartId)` in `cart.ts:52` which uses `api.del<OkResp>` — that endpoint's backend returns `{ok: true}`. *(Verified: `OkResp` at `types.ts:2941` is `{ok: boolean}`; `deleteCart` at `cart.ts:52`.)*

### 5.4 Idempotency key for `transitionOrder`

The `OrderTransitionRequest.idempotency_key` field is optional. ORD-014 components that drive transitions should generate a stable key for each user-initiated transition attempt (e.g. `crypto.randomUUID()` generated once on button click, retained in component state through retries). On a successful 200, the `OrderTransitionResult.event_id` is available for logging/display. On a 409 `conflict`, the consumer treats the order as already in the target state and should re-fetch the lifecycle to show the current state.

### 5.5 CSRF on mutations

`api.post`, `api.patch`, and `api.del` all go through the central `api<T>` function in `client.ts:151`, which always reads `getCookie("ui_csrf")` and sets `X-CSRF-Token` (lines 179–181). No per-wrapper CSRF setup is needed. This is consistent with all other mutation wrappers in the project.

### 5.6 `listOrdersByStatus` — static path before dynamic `/{order_id}`

The `/ui/orders/lifecycle/by-status` and `/ui/orders/lifecycle/by-ship-date` paths contain the literal segment `lifecycle` which appears **before** the dynamic `/{order_id}` segment in the backend router declaration (per ORD-012 and the CLAUDE.md FastAPI path ordering gotcha). This matters only to the backend; on the frontend the wrapper calls the correct full path directly and there is no routing ambiguity in the TypeScript layer.

**Note**: the response `cursor` field (from ORD-012) is used for pagination continuation — not `next_cursor`. ORD-014 components should read `resp.cursor` to determine whether a next page exists.

### 5.7 `OrderLifecycleOut.status` vs. `lifecycle_status` coexistence

`status: string` is the legacy field always present. `lifecycle_status?: OrderLifecycleStatus | null` is the additive field set only when the flag is on and the order was created after ORD-007 activated. ORD-014 should display `lifecycle_status` when non-null, falling back to `status` for older orders. The wrapper returns both fields without transformation — the presentation logic belongs in ORD-014.

### 5.8 `cancelOrder` — re-fetch after success

A successful `cancelOrder` call returns the updated `OrderLifecycleOut` with `lifecycle_status: "cancelled"`. ORD-014 should use this as the optimistic response to the React Query cache (`useMutation.onSuccess` → `queryClient.setQueryData(["order-lifecycle", orderId], result.data)`), rather than relying on a separate re-fetch. This avoids a visible flash while the GET query re-validates.

### 5.9 `ShipGroupAssignIn.item_ids` must be non-empty

The backend model has `min_length=1` on `item_ids`. Sending an empty array returns 422. ORD-014's "Assign items" form must disable the submit button when no items are selected. The TypeScript type does not encode the minimum-length constraint (`string[]` rather than `[string, ...string[]]` which would be overly restrictive for form state), so the UI layer must enforce it.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

TypeScript types and endpoint wrappers are pure compile-time + fetch code with no environment branches. The `api` client in `client.ts` calls the Vite proxy (port 3000 → backend port 8000) in dev and the real origin in prod. No `import.meta.env.MODE` or `process.env.NODE_ENV` branches exist in the wrappers. Full parity by construction.

### 7.2 Idempotency at the frontend layer

`transitionOrder` callers should generate a per-attempt `idempotency_key` (e.g. `crypto.randomUUID()`) and retain it across retries of the same intended transition. This prevents a network retry from producing a second history entry. The wrapper does not auto-generate the key — that decision belongs to the calling component (ORD-014), since the component knows whether a given call is a retry.

For `addOrderAdjustment`, the backend derives `adjustment_id = sha256(order_id|actor|adj_type|amount_cents|label)[:16]` (ORD-008). Submitting the same adjustment body twice from the UI returns the existing row. The wrapper does not need to deduplicate — the backend is idempotent.

### 7.3 Security

**No secrets in wrappers**: all functions receive `orderId` and body parameters. No API keys, tokens, or PII are embedded. The `api` client reads `accessToken` from `useAuthStore` and the CSRF cookie from `document.cookie`; both are managed by the auth layer, not by individual wrappers.

**XSS via `metadata` display**: `OrderLifecycleOut.metadata` is `Record<string, unknown>` and may carry arbitrary string values. ORD-014 must render these through React's standard JSX text nodes (never via `dangerouslySetInnerHTML`) to prevent XSS. This is a ORD-014 concern, not ORD-013, but the type definition makes the opaque nature of `metadata` explicit.

**No `any` types**: all wrapper return types are fully typed (`Promise<OrderTransitionResult>`, `Promise<ShipGroup>`, etc.). TypeScript's `strict` mode (if configured in `tsconfig.json`) will flag any `any` leak. The dedicated `OrderAdjustmentDeleteResp` interface is used for `removeOrderAdjustment` (rather than `OkResp` or `any`) — casting to `any` is prohibited.

## 10. Open Questions / Assumptions

1. ~~**Assumption: backend `removeOrderAdjustment` returns `{"deleted": true}` not `{"ok": true}`**~~ **RESOLVED**: Verified against ORD-011 Section 4.4 (`return {"deleted": True}`). The wrapper uses `OrderAdjustmentDeleteResp { deleted: boolean }`, not `OkResp`. No further action.

2. ~~**Assumption: `OrdersByStatusResp` and `OrdersByShipDateResp` field names match this spec**. ORD-012 does not yet have a spec file~~ **RESOLVED + CORRECTED**: `docs/ofbiz/specs/ORD-012.md` exists and defines `OrdersByStatusOut` (`orders`, `count`, `cursor`) and `ShipGroupsByDateOut` (`ship_groups`, `count`, `cursor`). All three TypeScript types, wrappers, and imports in this spec have been corrected accordingly. `total_scanned` does not exist in ORD-012; `items` does not exist; `next_cursor` does not exist — `cursor` is used.

3. ~~**Assumption: `adjusted_amount_cents` is present in `OrderLifecycleOut` when adjustments exist**~~ **RESOLVED + CORRECTED**: Verified against `docs/ofbiz/specs/ORD-004.md` Section 4.8 and ORD-005 `_header_to_lifecycle_out`: `adjusted_amount_cents` is NOT a field of `OrderLifecycleOut`. It is a DDB attribute written by ORD-008 but not projected into the Pydantic model. Removed from the TypeScript `OrderLifecycleOut` interface.

4. **Assumption: `OrderLifecycleStatus | string` on `from_status`/`to_status` is the correct union**. ORD-004 Section 4.3 notes that `from_status` and `to_status` are `str` (not `Optional[OrderLifecycleStatus]`) in the Pydantic model as a defensive choice for pre-flag orders. This means the JSON may carry e.g. `"to_status": "pending_payment"` for legacy history rows. The TypeScript union `OrderLifecycleStatus | string` collapses to `string` in TypeScript (since `OrderLifecycleStatus` is already a subtype of `string`), making the type less precise. If the backend guarantees only enum values in history rows, `to_status: OrderLifecycleStatus` is sufficient; if legacy strings are possible, `string` is the correct type and the union is redundant. The spec uses `OrderLifecycleStatus | string` as a documentation signal that both forms may appear, not for type narrowing.

5. **Assumption: `OrderCancelIn.refund` defaults `false` on the backend**. ORD-011 shows `class OrderCancelIn(BaseModel): refund: bool = False`. The TypeScript type marks `refund?: boolean` (optional) to match — callers that omit it get the backend default. If ORD-014 always sends `refund` explicitly, the `?` is cosmetic.

6. **Assumption: `getOrderLifecycle` with no `include` parameter sends no `include` query param** (not `?include=`). The backend's `include: str = Query(default="")` treats an absent param the same as `include=""` (empty string → empty set). The wrapper should omit the `params.include` key entirely when the array is empty/absent, not send `include=""`. The current implementation omits the key when `include` is undefined or `[]`.

7. **Open: should `listOrdersByStatus` and `listOrdersByShipDate` use `useInfiniteQuery` in ORD-014?** The wrappers as written return a single page. If ORD-014 implements infinite scroll, it would call these wrappers with a `cursor` from the response `cursor` field (ORD-012 uses `cursor` not `next_cursor`). The wrapper signature already accepts `cursor` as an optional parameter; no change is needed. This is a ORD-014 design decision.

8. **Assumption: `frontend/src/lib/featureFlags.ts` does not import from `orderLifecycle.ts`** (no circular dependency). `featureFlags.ts` reads only `import.meta.env` values; it does not import from `api/`. The `isOrderLifecycleEnabled` export is safe.
