# OFB-014 — Double-entry journal entries derived from the ledger

## 1. Summary & Goal

Implement `app/services/gl_posting.py`: a GL posting engine that reads every row
from the existing single-entry billing ledger (`billing` DynamoDB table, SK prefix
`LEDGER#`) and emits a balanced double-entry journal entry per row into a new
`gl_journal` DynamoDB table.  Each posted entry carries at least two lines
(debit + credit) that sum to zero.  The engine:

- is gated behind the `GL_DOUBLE_ENTRY_ENABLED` flag (default **off**);
- is **idempotent** — re-posting the same source `entry_id` is a guaranteed no-op;
- is **read-only with respect to the billing table** — it never writes to `billing`
  or changes any existing ledger row;
- derives account codes from the OFB-013 chart (`T.gl_accounts`), mapping ledger
  `type` / `reason` / `state` / `provider` to the correct debit and credit sides;
- runs as a background async loop (`run_gl_posting_loop`) that polls new ledger
  rows via `GSI_LEDGER_DATE` day-buckets, plus exposes a `POST /ui/admin/gl/backfill`
  REST endpoint (ROOT only) for historical date-range backfills.

## 3. Data Model

### 3.1 New table: `gl_journal`

Single-table design.  Lives in DynamoDB, sized similarly to the billing table.
OFB-002 adds the `TableDef` to `scripts/local-ddb-init.py`; OFB-014 consumes it.

#### Item shapes

**Journal entry header** (`SK = JE#{journal_entry_id}`):

```
PK            = "JE#GLOBAL"                           (constant — enables ENTRIES_BY_DATE GSI scan)
SK            = "JE#{journal_entry_id}"               (journal_entry_id = sha256(source_entry_id)[:24])
journal_entry_id  string
source_entry_id   string   (billing ledger entry_id — idempotency key)
source_sk         string   (full LEDGER#ts#entry_id SK for traceability)
source_pk         string   (USER#sub of the originating ledger row)
ledger_date       string   (YYYY-MM-DD, copied from source row — GSI partition key)
posted_at         int      (Unix ts)
state             string   ("posted")
entry_type        string   (ledger row type, e.g. "tip_debit")
entry_reason      string   (ledger row reason)
entry_state       string   (ledger row state at post time)
provider          string   (stripe|paypal|ccbill|unknown)
total_amount_cents int     (absolute value of the ledger row amount)
```

**Journal entry line** (`SK = JL#{journal_entry_id}#{seq:04d}`):

```
PK            = "JE#GLOBAL"
SK            = "JL#{journal_entry_id}#{seq:04d}"     (seq = 0001, 0002, …)
journal_entry_id  string
seq               int
account_code      string   (e.g. "1000")
account_name      string   (denorm for readability)
side              string   ("debit" | "credit")
amount_cents      int      (always positive; sign is encoded in side)
```

#### GSIs

**`ENTRIES_BY_DATE`** — enables per-day range queries for the OFB-015/OFB-016
statement generators without scanning the full table:

```
PK  = ledger_date   (S)
SK  = posted_at     (N)
```

**`SOURCE_ENTRY_IDX`** — one-item lookup from source `entry_id` to confirm
whether a row has already been posted (supports idempotency guard):

```
PK  = source_entry_id   (S)
SK  = posted_at         (N)
```

## 4. API / Service Design

### 4.1 Service: `app/services/gl_posting.py`

```python
# Module-level mapping: ledger entry type/reason → (debit_account, credit_account)
# Each value is a tuple[account_code, account_code].  Tax and fee splits are
# handled via _split_lines().  Unrecognised types fall through to _DEFAULT_MAPPING.
ACCOUNT_MAPPING: dict[str, tuple[str, str]] = {
    # Money-in (settled charges) — Cash debited, Sales Revenue credited
    # Account codes match OFB-013 DEFAULT_ACCOUNTS (OFB-013.md:195-210):
    #   1000=Cash/Bank, 4000=Sales Revenue, 1200=AR, 2100=Sales Tax Payable,
    #   4900=Refunds/Returns (contra-revenue), 5100=Processor Fees.
    "tip_debit":          ("1000", "4000"),
    "unlock_debit":       ("1000", "4000"),
    "catalog_purchase":   ("1000", "4000"),
    "deposit":            ("1000", "4000"),
    "subscription_charge": ("1000", "4000"),
    "credit":             ("1000", "4000"),
    # Platform earned revenue — no separate commission account in OFB-013 seed;
    # map to 4000 (Sales Revenue) until OFB-013 is extended.
    "platform_commission":     ("1000", "4000"),
    "platform_ad_commission":  ("1000", "4000"),
    "ad_revenue_credit":       ("1000", "4000"),
    # Refunds — Refunds/Returns contra (4900) debited, Cash (1000) credited
    "refund":         ("4900", "1000"),
    "tip_refund":     ("4900", "1000"),
    "unlock_refund":  ("4900", "1000"),
    "chargeback":     ("4900", "1000"),
    "adjustment":     ("4900", "1000"),   # reversed payment adjustments
    # Generic debit (owed) — AR (1200) debit / Revenue (4000) credit
    "debit":          ("1200", "4000"),   # AR debit / Revenue credit
}
_DEFAULT_MAPPING = ("1000", "4000")


def _journal_entry_id(source_entry_id: str) -> str:
    """Deterministic, collision-resistant ID derived from the source entry."""
    return hashlib.sha256(source_entry_id.encode()).hexdigest()[:24]


def _is_already_posted(source_entry_id: str) -> bool:
    """Check SOURCE_ENTRY_IDX for an existing journal entry.

    Returns True if at least one item exists for this source_entry_id,
    meaning the ledger row has already been posted.
    """
    resp = T.gl_journal.query(
        IndexName="SOURCE_ENTRY_IDX",
        KeyConditionExpression=Key("source_entry_id").eq(source_entry_id),
        Limit=1,
    )
    return bool(resp.get("Items"))


def _build_lines(
    journal_entry_id: str,
    entry_type: str,
    amount_cents: int,
    tax_cents: int = 0,
    fee_cents: int = 0,
) -> list[dict]:
    """Produce the journal line items for a single ledger row.

    Basic case (no tax/fee split):
      line 1: debit  account=debit_account  amount=amount_cents
      line 2: credit account=credit_account amount=amount_cents

    With tax_cents > 0 (on settled charges):
      line 1: debit  Cash          amount=amount_cents
      line 2: credit SalesRevenue  amount=(amount_cents - tax_cents)
      line 3: credit TaxPayable    amount=tax_cents

    With fee_cents > 0 (processor fee embedded in amount):
      line 2a: credit SalesRevenue  amount=(amount_cents - fee_cents)
      line 2b: debit  ProcessorFees amount=fee_cents   [net = same debit]
    Invariant: sum(debit amounts) == sum(credit amounts) always.
    """


def _split_lines(
    journal_entry_id: str,
    entry_type: str,
    amount_cents: int,
    ledger_item: dict,
) -> list[dict]:
    """High-level line builder that reads optional tax_cents / fee_cents from
    the ledger item's ``meta`` dict (e.g. ``meta.tax_cents``, ``meta.fee_cents``)
    and delegates to ``_build_lines``.  For the current ledger schema those
    fields are not yet present, so this defaults to the no-split path."""


def post_ledger_entry(ledger_item: dict) -> str | None:
    """Map one billing ledger row to a balanced journal entry.

    Returns the ``journal_entry_id`` of the newly created entry, or ``None``
    if the entry was skipped (already posted, state not postable, amount zero).

    Raises ``GLUnbalancedEntryError`` if the generated lines do not balance —
    this MUST propagate (never silently swallowed) so callers surface the bug.

    Idempotency: guarded by ``_is_already_posted(source_entry_id)``.  If True,
    returns ``None`` without touching the table.  On True→write race (two workers
    posting the same entry simultaneously), the ``put_item`` conditional
    ``attribute_not_exists(PK)`` on the header item guarantees exactly-once
    semantics; the loser receives ``ConditionalCheckFailedException`` and returns
    None gracefully.
    """


def post_date(date_str: str) -> dict[str, int]:
    """Post all unposted ledger entries for a single YYYY-MM-DD date.

    Queries ``GSI_LEDGER_DATE`` (same pattern as
    ``platform_financial_dashboard._query_ledger_by_date``), filters to
    state in (``settled``, ``pending``) and skips ``reversed`` / ``failed`` /
    ``voided`` rows (reversals are themselves separate ledger rows of type
    ``refund`` / ``adjustment``).

    Returns ``{"posted": int, "skipped": int, "errors": int}``.
    """


def post_date_range(start_date: str, end_date: str) -> dict[str, int]:
    """Backfill: post all unposted ledger entries across an inclusive date range.

    Caps at ``S.gl_backfill_max_days`` days to guard against runaway scans.
    Accumulates per-date ``post_date`` results.
    """


async def run_gl_posting_loop(*, poll_interval: int | None = None) -> None:
    """Background async loop: post yesterday's and today's ledger rows every
    ``poll_interval`` seconds (default ``S.gl_posting_poll_interval_seconds``).

    Posts yesterday first (safe: all ledger rows for the day are written),
    then today (idempotent re-runs are cheap because already-posted entries
    short-circuit immediately).
    """
    interval = poll_interval or S.gl_posting_poll_interval_seconds
    while True:
        try:
            today = ledger_date_for_ts(now_ts())
            yesterday = _prev_date(today)
            post_date(yesterday)
            post_date(today)
        except Exception:
            logger.exception("gl_posting_loop_error")
        await asyncio.sleep(interval)


def start_gl_posting_task() -> None:
    """Register the GL posting background loop at app startup (gated on flag)."""
    if S.gl_double_entry_enabled:
        asyncio.ensure_future(run_gl_posting_loop())
        logger.info("GL double-entry posting loop started")
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Posting state filtering

Rows are posted when `state in ("settled", "pending")`.
`"reversed"` / `"failed"` / `"voided"` rows are **skipped** (counted in
`skipped`).  Reversal events are their own ledger rows of type `"refund"` or
`"adjustment"` with `state="settled"` and will be posted separately, producing
the correct Dr Refunds/Cr Cash journal entry.

### 5.2 Balance invariant enforcement

`_build_lines` validates `sum(line.amount_cents for line in lines if line.side == "debit") == sum(line.amount_cents for line in lines if line.side == "credit")`.
If violated (bug in mapping table), `GLUnbalancedEntryError` is raised **before
any DynamoDB write**.  The entry is counted in `errors` in `post_date`; the
loop logs and continues (never halts the poster for one bad row).

### 5.3 Idempotency guarantee

Two-layer:

1. **Pre-check**: `_is_already_posted(source_entry_id)` queries `SOURCE_ENTRY_IDX`.
   Returns None if any hit found.
2. **Conditional put** on the header item:
   `ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)"`.
   If a concurrent worker races past the pre-check and writes first, the loser
   catches `ConditionalCheckFailedException` and returns None (not an error).

The `journal_entry_id` is `sha256(source_entry_id)[:24]` (pure function), so
both workers would attempt to write the same PK/SK — the conditional is the
correct tie-breaker.

### 5.4 Tax split (future-proofing)

Current ledger rows do not embed `tax_cents` or `fee_cents` in their `meta`.
`_split_lines` reads `ledger_item.get("meta", {}).get("tax_cents", 0)` and
`ledger_item.get("meta", {}).get("fee_cents", 0)`.  For today's ledger rows
these are zero → two-line entries only.  When tax tracking is added (future
ticket), existing call sites pass `extra={"meta": {"tax_cents": N}}` and
OFB-014 picks them up automatically without schema changes.

### 5.5 Unknown entry types

If `entry_type` is absent from `ACCOUNT_MAPPING`, the poster falls back to
`_DEFAULT_MAPPING = ("1000", "4000")` (Cash / Sales Revenue) and logs a
`WARNING: unknown_entry_type type=<x> falling_back_to_default`.  The entry is
still posted; finance team can reclassify via a manual journal entry in a
future accounting admin UI (OFB-017).

### 5.6 Zero-amount rows

Rows with `amount_cents == 0` are skipped (counted in `skipped`).  Zero-amount
ledger rows are structurally valid but generate trivially-balanced zero-value
journal entries that add noise; skipping them is safe.

### 5.7 Pending rows re-processing

A row posted while `state="pending"` will still be in `SOURCE_ENTRY_IDX` if
it later transitions to `"settled"` or `"reversed"`.  The engine **does not
re-post** settled confirmations of already-posted pending rows.  This is
acceptable in Phase 1; a future pass-2 settlement-posting step (e.g.
`post_settled_entry(original_entry_id)`) can mark pending entries as
`state="needs_settlement_posting"` and emit an additional adjustment line.
This is noted as an open question (Section 10).

### 5.8 Backfill cap

`post_date_range` computes `days = (end - start).days + 1`.  If `days >
S.gl_backfill_max_days`, raises `HTTPException(422, "date range exceeds max")`.
This prevents accidentally scanning years of ledger data in a single request.

### 5.9 Multi-line entry write atomicity

The header and all line items are written using `batch_writer` in a single
`BatchWriteItem` call (up to 25 items per batch; typical entries have 2–3
lines so they fit in one batch).  The conditional is only on the header item.
If the batch write fails partway through (extremely unlikely with moto/DDB),
the header may be missing while lines are present, or vice versa.  On the next
run, the pre-check will not find a header in `SOURCE_ENTRY_IDX` (lines don't
carry `source_entry_id` as the GSI key), so the entry will be re-posted and
the orphan lines will be overwritten.  This is acceptable — the worst case is
one duplicate set of lines with the same SK, which the last writer wins.

no CPU is consumed and no DDB calls are made.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**No dev/prod branching** in `gl_posting.py`.  The module reads from `T.billing`
(moto DDB in dev, real DDB in prod) and writes to `T.gl_journal` via the same
`_FloatSafeTable` proxy used throughout the codebase.  The posting logic —
account mapping, balance check, conditional put — runs identically in both
environments.

**Billing table is read-only** from gl_posting.py's perspective.  It calls only
`T.billing.query(IndexName="GSI_LEDGER_DATE", ...)`.  It never calls `put_item`,
`update_item`, or `delete_item` on `T.billing`.  This is a hard constraint: the
existing ledger byte-stream is inviolable.

**Auth**: The `POST /ui/admin/gl/backfill` endpoint requires `require_root`
(ROOT role), consistent with the `POST /ui/admin/financial-dashboard/rollup`
pattern (`app/routers/platform_financial_dashboard.py:167`).  Read endpoints
require `require_admin_or_root`, consistent with the dashboard GET endpoints
(line 68).

**CSRF**: All non-GET requests under `/ui/` enforce CSRF via the standard
cookie-auth path (`app/auth/deps.get_authenticated_user` / the `x-csrf-token`
header pattern).  Bearer-token clients skip CSRF as documented in CLAUDE.md.

**No PII exposure**: Journal entry lines contain `account_code`, `amount_cents`,
and `side` only.  The `source_pk` field (e.g. `USER#alice`) is stored on the
header item and is accessible only to ADMIN/ROOT.  The listing endpoint never
surfaces `source_pk` in the response model (`GlEntryOut` omits it intentionally).

**Audit**: `post_date` emits `audit_event("gl_posting_completed", "system_gl_poster", None, date=date_str, posted=N, errors=N)` via `app.services.alerts.audit_event`.  Backfill invocations emit `audit_event("gl_backfill_triggered", user.sub, request, ...)`.

## 8. Backward Compatibility & Migration

**Zero impact when flag is off** (default).  No existing billing, cart, order,
or subscription code is touched.  `T.billing`, `T.billing_config`,
`platform_financial_dashboard.py`, and all billing routers are read-only from
OFB-014's perspective.

**Table creation** is handled by OFB-002 (`scripts/local-ddb-init.py`).
`just restart` recreates `gl_journal` from scratch in local dev.  In production,
`gl_journal` is provisioned before the flag is turned on; there is no data
migration (the table starts empty and is populated forward).

**Historical backfill** is explicit: ROOT must call `POST /ui/admin/gl/backfill`
with the desired date range.  The background loop only posts present and past-day
entries on an ongoing basis; it does not automatically crawl the full historical
ledger at startup.

**OFB-013 accounts must be seeded** before OFB-014's flag is enabled.  If
`T.gl_accounts` is empty or an account code referenced by `ACCOUNT_MAPPING` is
missing, `post_ledger_entry` falls back to the default mapping (Cash / Sales
Revenue) and logs a warning rather than failing hard.  A future health-check
endpoint (OFB-017) can alert when unmapped types exceed a threshold.

**No `app/models.py` changes** are strictly required for the background posting
path.  The two new Pydantic models (`GlBackfillIn`, `GlBackfillOut`,
`GlEntryOut`, `GlLineOut`) can live in `app/models.py` alongside the existing
`PlatformFinancial*` models, or locally in the router file.  Preference:
add them to `app/models.py` for consistency.

## 10. Open Questions / Assumptions

1. **Assumption**: OFB-013's `gl_accounts` table is seeded with the account
   codes listed in Section 2.4 before OFB-014's flag is enabled.  If not
   seeded, the fallback mapping still produces balanced entries; finance
   reclassification is deferred to OFB-017.

2. **Assumption**: `ACCOUNT_MAPPING` in `gl_posting.py` uses hardcoded
   account codes (`"1000"`, `"4000"`, etc.) matching OFB-013's seed data.
   If OFB-013 uses different codes, the mapping must be updated before the
   flag is turned on.  A health-check or seed-verification test in OFB-013
   should assert the exact codes used here.

3. **Open question**: Should `state="pending"` rows be posted at all, or only
   `state="settled"`?  The ticket says "idempotent per source `entry_id`";
   it does not restrict to settled rows.  This spec posts both pending and
   settled but does not re-post a pending row when it later transitions to
   settled.  **Verify with finance stakeholder** whether a settlement-posting
   step (updating the existing journal entry or emitting a new one) is needed
   for Phase 1.

4. **CORRECTED (pass 3)**: The invariant "reversals always produce their own
   `refund`/`adjustment` row" does **NOT** hold for all provider paths.
   Code-verified: CCBill failure paths (`billing_ccbill.py:583,670`) and Stripe
   webhook payment-failure paths (`billing.py:1551,1586`) call
   `settle_or_reverse_ledger(..., "reversed")` without creating any new ledger
   row.  PayPal capture failures behave the same (`paypal.py:1065`).  Only
   explicit operator-triggered refunds (`billing.py:1306-1316`) and PayPal
   refund webhooks (`paypal.py:1369-1399`) create a separate `adjustment` row.
   **Consequence**: posting `state="pending"` rows risks orphaned journal entries
   with no offsetting reversal for ~all provider failure paths.  The safe Phase 1
   approach is to post only `state="settled"` rows (see open question §10.3).

5. **Assumption**: The `gl_journal` table uses `PK="JE#GLOBAL"` as a single
   global partition for all journal entries, allowing the `ENTRIES_BY_DATE` GSI
   to be queried without a per-user partition.  For extremely high-volume
   deployments this may become a hot partition.  A future sharding strategy
   (e.g. `PK="JE#SHARD#{ledger_date[-2:]}"`) can be adopted without breaking
   the `SOURCE_ENTRY_IDX` idempotency guard (that GSI uses `source_entry_id`
   as PK, independent of the main-table PK).

6. **Assumption**: The `journal_entry_id` is `sha256(source_entry_id)[:24]`
   (first 24 hex chars = 96-bit prefix).  Collision probability across ~10^9
   entries is ~10^{-20} — effectively zero.  If a stricter uniqueness guarantee
   is required, use the full 64-char hex.

7. **Open question**: Should `T.gl_journal` writes use `batch_writer` (up to
   25 items per `BatchWriteItem` call) or individual `put_item` calls?  The
   batch writer is more efficient but loses per-item error granularity.  Given
   typical 2–3 line entries, a single batch call per journal entry is
   recommended.  Confirm with the team.

8. **Assumption**: The background posting loop posts `yesterday` and `today`
   on every poll.  This means a row written late in the day will be posted
   within one `gl_posting_poll_interval_seconds` of its `ledger_date`.  Rows
   from days further in the past require an explicit backfill call.
