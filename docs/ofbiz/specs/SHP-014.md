# SHP-014 — Link shipments to order fulfillment + purchase-history tracking

## 1. Summary & Goal

SHP-014 closes the loop between the warehouse-facing shipment domain (the first-class
`shipments` table created by SHP-008, governed by the SHP-010 state machine and exposed by
the SHP-011 router) and the **buyer-facing** order/transaction surface that already exists in
`app/services/purchase_history.py` and `app/services/commerce_order_service.py`.

Two distinct denormalizations are introduced, both gated behind a single default-OFF flag:

1. **Transaction-side tracking bridge.** When a shipment is shipped (or its tracking status
   advances), a compact shipment summary — `carrier`, `method`, `tracking_number`, `status`,
   and the computed `tracking_url` — is written onto the matching `purchase_transactions`
   record through the **existing** `purchase_history.update_shipping` function
   (`app/services/purchase_history.py:398`). Because the buyer's existing tracking endpoint
   `GET /ui/purchase-history/transactions/{txn_id}/tracking`
   (`app/routers/purchase_history.py:118`) reads straight off the transaction's `shipping`
   sub-map, the shipment surfaces in the buyer's order view **with zero frontend change**.

2. **Order-side fulfillment status.** An order-level `fulfillment_status` field
   (`unfulfilled → partially_shipped → shipped → delivered`) is derived from the order's ship
   groups and written **additively** onto the `orders` row, **without ever mutating the
   existing `status` field** (which still carries `pending_payment`/payment-lifecycle
   semantics — `app/services/commerce_order_service.py:75`).

The link is **idempotent**: re-shipping or re-linking the same shipment compares the
denormalized status before writing (the exact pattern used by `apply_tracking_result`,
`app/services/carrier_tracking.py:163–168`), so there is no double-write, no duplicate alert,
and no version churn on the transaction record.

## 3. Data Model

SHP-014 introduces **no new DynamoDB table** and no new table handle. All changes are
additive attributes on two existing rows.

### 3.1 Additive `fulfillment_status` on `orders`

| Attribute | Type | Allowed values | When written |
|---|---|---|---|
| `fulfillment_status` | String | `unfulfilled`, `partially_shipped`, `shipped`, `delivered` | On every link/relink; derived from ship groups |
| `fulfillment_updated_at` | String (ISO) | — | Same `_now_iso()` clock the order uses (`commerce_order_service.py:19`) |

The existing `status` field (`pending_payment`, …) is **never read or written** by this
path. `fulfillment_status` is absent on legacy rows and on any order whose shipments have not
yet been linked; readers treat absence as `unfulfilled`.

### 3.2 Denormalized shipment summary on `purchase_transactions.shipping`

SHP-014 writes a compact summary into the transaction's existing `shipping` sub-map via
`update_shipping` (no schema change — `shipping` is already a free-form map):

| Key | Source on shipment row | Notes |
|---|---|---|
| `carrier` | `shipment.carrier` (or `carrier_code`) | `update_shipping` auto-detects from tracking number if absent (`purchase_history.py:408–411`) |
| `method` | `shipment.method_code` | Display only |
| `tracking_number` | `shipment.tracking_number` | Promoted to txn top-level by `update_shipping` (`:416–418`) |
| `status` | `shipment.status` | The shipment's canonical state-machine status |
| `shipment_id` | `shipment.shipment_id` | Back-reference for idempotency comparison |

`tracking_url` is **not** stored — `get_transaction_info` computes it at read time
(`purchase_history.py:389–394`), and the tracking endpoint recomputes it (`router :133`).

### 3.3 No new table justification

A separate `order_fulfillment` table was considered and rejected: fulfillment status is a
single derived scalar per order and a single summary per transaction, both of which fit
naturally on rows that are already fetched on the read path. A new table would add a join
with no query-pattern benefit.

## 4. API / Service Design

All new logic lives in a new module `app/services/shipment_order_link.py` plus one additive
method on `CommerceOrderService`. No new router is added (the buyer tracking surface already
exists). An optional admin endpoint is described in §4.5.

### 4.1 The link hook — `link_shipment_to_order_fulfillment`

```python
# app/services/shipment_order_link.py
def link_shipment_to_order_fulfillment(shipment: dict) -> dict:
    """Denormalize a shipment onto its order + purchase transaction.

    Called after a shipment is created/shipped or its tracking status advances.
    Best-effort and idempotent: no-ops when the flag is off, when nothing
    changed, or when the linkage cannot be resolved.

    Returns {"order_linked": bool, "txn_linked": bool, "fulfillment_status": str | None}.
    """
```

Behavior:

1. `if not S.shipping_order_link_enabled: return {"order_linked": False, "txn_linked": False, "fulfillment_status": None}`.
2. Resolve `order_id = shipment.get("order_id")`; if absent → return no-op.
3. **Order side**: call `_recompute_order_fulfillment(order_id)` (§4.2).
4. **Transaction side**: resolve the txn via `user_sub = shipment.get("user_id")` and
   `txn_id = shipment.get("purchase_txn_id")`; if both present, call
   `_link_txn_shipping(user_sub, txn_id, shipment)` (§4.3). If `purchase_txn_id` is absent,
   fall back to resolving the txn by `external_ref == order_id` (§5.6).
5. Wrap each side in its own `try/except` so a transaction-side failure never blocks the
   order-side write (and vice-versa) — mirrors the best-effort posture of
   `apply_tracking_result`'s alert path (`carrier_tracking.py:192–193`).

### 4.2 Fulfillment derivation from ship groups

```python
def _recompute_order_fulfillment(order_id: str) -> str | None:
    shipments = shipments_svc.list_shipments_for_order(order_id)   # SHP-011, GSI_ORDER
    new_status = derive_fulfillment_status(shipments)
    commerce_order_service.set_fulfillment_status(order_id, new_status)  # idempotent
    return new_status


def derive_fulfillment_status(shipments: list[dict]) -> str:
    if not shipments:
        return "unfulfilled"
    statuses = [s.get("status") for s in shipments]
    delivered = {"delivered"}
    shipped_or_beyond = {"shipped", "in_transit", "out_for_delivery", "delivered"}
    if all(s in delivered for s in statuses):
        return "delivered"
    if all(s in shipped_or_beyond for s in statuses):
        return "shipped"
    if any(s in shipped_or_beyond for s in statuses):
        return "partially_shipped"
    return "unfulfilled"
```

`derive_fulfillment_status` is **pure** (no I/O), so it is unit-testable in isolation. The
canonical shipment status vocabulary is SHP-010's `LEGAL_TRANSITIONS`
(`pending_fulfillment`, `packed`, `label_created`, `shipped`, `in_transit`,
`out_for_delivery`, `delivered`, `exception`, `returned`, `cancelled`).

**`cancelled` / `exception` handling**: a `cancelled` ship group is excluded from the "all"
quantifiers (treated as not-counting), so an order with one delivered group and one cancelled
group derives `delivered`. `exception` counts as "not yet shipped-or-beyond" for the
all-shipped test but does **not** by itself force `partially_shipped` unless another group has
actually shipped. (See §5.4 for the precise truth table.)

### 4.3 Transaction-side denormalization (idempotent)

```python
def _link_txn_shipping(user_sub: str, txn_id: str, shipment: dict) -> bool:
    from app.services.purchase_history import get_transaction_info, update_shipping
    info = get_transaction_info(user_sub, txn_id)          # 404 if missing → caught by caller
    current = info.get("shipping") or {}
    summary = {
        "carrier": shipment.get("carrier") or shipment.get("carrier_code"),
        "method": shipment.get("method_code"),
        "tracking_number": shipment.get("tracking_number"),
        "status": shipment.get("status"),
        "shipment_id": shipment.get("shipment_id"),
    }
    # IDEMPOTENCY: compare before write (mirrors carrier_tracking.py:163-168)
    if _summary_equal(current, summary):
        return False
    merged = {**current, **{k: v for k, v in summary.items() if v is not None}}
    update_shipping(user_sub, txn_id, merged)              # version-guarded write
    return True
```

`_summary_equal` compares only the keys SHP-014 owns (`shipment_id`, `status`,
`tracking_number`, `carrier`, `method`) so unrelated `shipping` keys written by the carrier
poller (`carrier_events`, `delivered_at`) are left intact and do not trigger a re-write.

### 4.4 Additive order writer — `set_fulfillment_status`

```python
# new method on CommerceOrderService (app/services/commerce_order_service.py)
def set_fulfillment_status(self, order_id: str, fulfillment_status: str) -> bool:
    """Additively write fulfillment_status; NEVER touches `status`. Idempotent."""
    existing = self.orders.get_item(Key={"order_id": order_id}).get("Item")
    if not existing:
        return False
    if existing.get("fulfillment_status") == fulfillment_status:
        return False                                       # idempotent no-op
    self.orders.update_item(
        Key={"order_id": order_id},
        UpdateExpression="SET fulfillment_status = :fs, fulfillment_updated_at = :u",
        ExpressionAttributeValues={":fs": fulfillment_status, ":u": self._now_iso()},
    )
    return True
```

The `UpdateExpression` lists **only** `fulfillment_status` and `fulfillment_updated_at`; the
`status` attribute is not in the expression and is therefore physically untouched.

### 4.5 Wiring point + optional admin endpoint

The hook is invoked **after** a shipment write succeeds, at the SHP-011 admin endpoints that
create or advance a shipment (`POST /ui/shop/shipments`, `POST .../{id}/advance`) and from
SHP-013's poller integration when a carrier event advances a shipment. The call is appended
after the existing service call returns, wrapped in `try/except` so a link failure never
fails the shipment operation.

An optional admin convenience endpoint
`POST /ui/shop/shipments/{shipment_id}/relink` (`require_admin_or_root_csrf`) re-runs the hook
for one shipment — useful for backfilling legacy shipments after the flag is turned on. It
returns the `link_shipment_to_order_fulfillment` result dict.

## 5. Detailed Behavior & Edge Cases

### 5.1 Single ship group, full lifecycle

Order with one ship group: `unfulfilled` (no shipment) → admin creates shipment (still
`unfulfilled`/`pending_fulfillment`) → `shipped` (tracking assigned) → order
`fulfillment_status = "shipped"`; transaction `shipping.status = "shipped"` with carrier +
tracking. Poller advances shipment to `delivered` → order `fulfillment_status = "delivered"`;
transaction `shipping.status = "delivered"`. The buyer's existing tracking endpoint reflects
each step with no FE change.

### 5.2 Multiple ship groups — partial vs full

Order with two ship groups A and B:

| A status | B status | Derived `fulfillment_status` |
|---|---|---|
| `pending_fulfillment` | `pending_fulfillment` | `unfulfilled` |
| `shipped` | `pending_fulfillment` | `partially_shipped` |
| `shipped` | `packed` | `partially_shipped` |
| `shipped` | `shipped` | `shipped` |
| `delivered` | `shipped` | `shipped` |
| `delivered` | `delivered` | `delivered` |

This is the core acceptance criterion: an order is `partially_shipped` when *some* (not all)
groups have reached `shipped`-or-beyond.

### 5.3 Re-link idempotency

Re-running the hook for an unchanged shipment: `set_fulfillment_status` sees an equal
`fulfillment_status` and no-ops (§4.4); `_link_txn_shipping` sees an equal summary and returns
`False` without calling `update_shipping` (§4.3). No version churn on the transaction, no
duplicate audit/alert. This is the `apply_tracking_result` "compare before write" invariant
(`carrier_tracking.py:163–168`) applied to two targets.

### 5.4 `cancelled` and `exception` ship groups

`cancelled` groups are filtered out of the quantifier checks: an order whose only non-cancelled
group is `delivered` derives `delivered`; an order with **all** groups cancelled derives
`unfulfilled` (nothing was fulfilled). `exception` is treated as "not shipped-or-beyond": it
can yield `partially_shipped` only if a *sibling* group has genuinely shipped; an order with a
single `exception` group stays `unfulfilled`. These rules live entirely in the pure
`derive_fulfillment_status` function and are exhaustively unit-tested.

### 5.5 Transaction not yet present / not COMPLETED

If `get_transaction_info` raises 404 (no matching transaction — e.g., a
`commercial_direct` order with no `purchase_transactions` row), `_link_txn_shipping`'s caller
swallows the error and proceeds with the order-side write only. If the transaction is
`CANCELLED`, `update_shipping` itself raises 409 (`purchase_history.py:402–403`); the caller
swallows it (you cannot attach shipping to a cancelled purchase — correct behavior).

### 5.6 `purchase_txn_id` absent on the shipment row

`purchase_txn_id` is optional on the shipment row (SHP-008). When absent, SHP-014 resolves the
transaction by scanning the buyer's transactions for `external_ref == order_id` (the linkage at
`purchase_history.py:270`). To avoid a cross-partition scan, the lookup is keyed by the
shipment's `user_id` (the buyer partition) and filtered on `external_ref`. If still
unresolved, the transaction side is skipped (order side still updates).

### 5.7 Version conflict on the transaction write

`update_shipping` is version-guarded and raises 409 on a concurrent write
(`purchase_history.py:428–429`). The link hook treats this as a transient no-op: the next
hook invocation (next shipment advance, or the admin `relink`) re-reads the current version
and retries. SHP-014 does not implement an internal retry loop — last-write-wins via the next
event is acceptable for a denormalized display field.

### 5.8 Flag-off is a hard no-op

With `S.shipping_order_link_enabled = False`, `link_shipment_to_order_fulfillment` returns its
no-op dict on line 1, before any table access. No `fulfillment_status` is ever written, no
transaction is touched, and the legacy `status` field is byte-for-byte unchanged.

### 5.9 Order-side write but no shipments found

If `list_shipments_for_order` returns an empty list (e.g., the only shipment was cancelled and
purged), `derive_fulfillment_status` returns `unfulfilled` and `set_fulfillment_status` writes
it (or no-ops if already `unfulfilled`). The function never raises on an empty group set.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Zero `dev_mode` branches

`shipment_order_link.py` and `set_fulfillment_status` contain no `if S.dev_mode:` branch. All
DynamoDB access (`list_shipments_for_order`, `get_item`/`update_item` on `orders`,
`update_shipping` on `purchase_transactions`) executes identically against DynamoDB Local
(dev, port 8001) and real DynamoDB (prod). The only environment difference is the endpoint URL.

### 7.2 Idempotency — compare-before-update on both targets

Both writes follow the `apply_tracking_result` discipline (`carrier_tracking.py:163–168`):

- **Order side**: `set_fulfillment_status` reads the current `fulfillment_status` and returns
  early when it equals the derived value — no `update_item`, no churn.
- **Transaction side**: `_link_txn_shipping` builds the summary and returns `False` when it
  equals the keys already on `shipping` — `update_shipping` (and its `version` increment) is
  never called. Because `update_shipping` is itself version-guarded
  (`purchase_history.py:424`), even a genuine concurrent write is serialized, not corrupted.

Re-linking therefore produces **no duplicate alert and no version inflation**, satisfying the
acceptance criterion.

### 7.3 Security

The hook is server-internal and is invoked from already-authorized admin endpoints
(`require_admin_or_root_csrf`, SHP-011) and the trusted poller. It performs no auth decisions
of its own. The transaction lookup is keyed by the **buyer's** `user_sub` taken from the
shipment row's `user_id` (denormalized from `T.orders` at shipment-creation time, SHP-008), so
the denormalization can never write a shipment summary onto a different user's transaction.
The optional `relink` endpoint reuses SHP-011's admin/CSRF guard; a USER-role caller receives
403 before the hook runs.

### 7.4 No money movement

SHP-014 writes only display/status fields. No call to `billing_shared.new_ledger_entry`,
no `update_shipping`-adjacent monetary mutation. Fulfillment status is informational.

## 8. Backward Compatibility & Migration

- **Legacy `status` untouched.** `set_fulfillment_status` lists only `fulfillment_status` and
  `fulfillment_updated_at` in its `UpdateExpression`; the payment-lifecycle `status`
  (`commerce_order_service.py:75`) is never read or written by SHP-014. With the flag off,
  the entire path is dead code.
- **No frontend change for the tracking surface.** The buyer reads shipment tracking through
  the **unchanged** `GET .../transactions/{txn_id}/tracking` endpoint
  (`app/routers/purchase_history.py:118`); the denormalized summary lands in the existing
  `shipping` sub-map. No new buyer route, no React change.
- **`fulfillment_status` is additive and sparse.** Legacy orders lack the attribute; any
  reader that wants it treats absence as `unfulfilled`. No DynamoDB migration or backfill is
  required to deploy.
- **Backfill is optional and idempotent.** After enabling the flag, an operator may run the
  `relink` endpoint per shipment (or a one-off script over `GSI_STATUS`) to populate
  `fulfillment_status` on in-flight orders. Because both writes are compare-before-update,
  a backfill that overlaps with live traffic is safe.
- **No new table** → no `scripts/local-ddb-init.py` `TableDef` change. The `orders` and
  `purchase_transactions` tables are reused as-is.

## 10. Open Questions / Assumptions

- **OQ-1 (`purchase_txn_id` population).** This spec assumes SHP-008's `create_shipment`
  stores `purchase_txn_id` when the order originated from a cart purchase. SHP-008 lists it as
  **optional** (`SHP-008.md:207`); when absent, §5.6's `external_ref` fallback covers it. If
  product wants guaranteed linkage, SHP-008 should set `purchase_txn_id` at shipment creation.
- **OQ-2 (shipment status field name).** SHP-008 names the carrier field `carrier_code` on
  input but the persisted row may carry `carrier`; SHP-010's `transition_shipment` writes
  `carrier` (free-form). `_link_txn_shipping` reads `carrier` then `carrier_code` to be safe.
  Confirm the actual persisted attribute name when SHP-008 lands.
- **OQ-3 (cancelled/exception derivation).** The §5.4 truth table is a product decision
  encoded in `derive_fulfillment_status`. If the business wants `exception` to force
  `partially_shipped` on its own, only the pure function changes.
- **OQ-4 (relink endpoint necessity).** The admin `relink` endpoint (§4.5) is a convenience
  for backfill; it can be dropped if backfill is done by a one-off script instead.
- **OQ-5 (where to wire the hook).** This spec wires it into SHP-011's create/advance handlers
  and SHP-013's poller. The exact call sites depend on SHP-011/SHP-013 final shape; the hook
  itself is decoupled and can be called from any post-write point.

## 14. Reconciliation Applied

- **Open decision §12 row 20 / §13 row 20** — `purchase_txn_id` population strategy:
  **Resolution (default applied)**: The `external_ref` fallback (§5.6, using `external_ref = order_id` written by `record_cart_purchase` at `purchase_history.py:270`) is the MVP resolution. `purchase_txn_id` remains optional on the Shipment row. SHP-008's `create_shipment` is not required to receive `purchase_txn_id` from the checkout caller for Phase 1. `_link_txn_shipping` resolves the transaction via the `external_ref` scan when `purchase_txn_id` is absent; this covers all cart-originated orders. If guaranteed zero-miss linkage is needed in a future phase, path (a) from SHP-001 §14 applies: checkout returns both `order_id` and `txn_id` and the caller passes `purchase_txn_id` explicitly. No spec change to SHP-008 is required. Authoritative default: ESCALATIONS §B SHP-014 row.
