## 1. Summary & Goal

MFG-014 closes the test gap across the entire manufacturing/MRP subsystem (MFG-001
through MFG-013) by delivering:

1. **Four hermetic offline pytest suites** — `tests/test_mfg_bom.py`,
   `tests/test_mfg_work_orders.py`, `tests/test_mfg_mrp.py`, and
   `tests/test_mfg_cost_posting.py` — that bind moto in-memory DynamoDB tables to
   the exact frozen `T.*` handles via `object.__setattr__`, flip the
   `S.manufacturing_mrp_enabled` flag the same way, and call service functions
   directly. No real AWS, no network, no `TestClient` (broken in this environment —
   see §9).

2. **One Playwright E2E spec** — `frontend/e2e/manufacturing.spec.ts` — that walks
   the full BOM → work-order → production → MRP path against the live dev stack
   using seeded admin sessions (Charlie/root via `e2e_admin_session_setup.py`) and
   CSRF headers, asserting real inventory deltas at each step.

3. **A flag-off regression block** in each pytest suite that asserts every service
   function raises `HTTPException(404)` (and that the test-facing router returns 404
   for every path) when `manufacturing_mrp_enabled` is `False`.

The test files produce zero side effects with the flag off; they do not touch the
existing `inventory`, `billing`, `orders`, `catalog`, or `cart` tables beyond what
the services themselves already do.

## 5. Detailed Behavior & Edge Cases

### 5.1 BOM explosion tests (`tests/test_mfg_bom.py`)

**Single-level explosion with scrap.**
Fixture: BOM for `FG-001` with `output_quantity=10`, one component `RAW-A`
with `quantity_per=2`, `scrap_pct=0.10` (10% scrap).
For `build_qty=5`:
```
required_qty = ceil(2 / 10 * 5 * (1 + 0.10)) = ceil(1.1) = 2
```
Assert `explode_bom` returns `[{"component_sku": "RAW-A", "required_qty": 2, "depth": 0}]`.

**Nested explosion with scrap (two levels).**
Fixture: BOM `B1` for `FG-001` (output=1) has component `SUB-001` (qty_per=3).
BOM `B2` for `SUB-001` (output=1) has component `RAW-B` (qty_per=2, scrap=0.05).
For `build_qty=2`:
- `SUB-001` required = `ceil(3/1 * 2 * 1.0)` = 6 (no scrap at level 0).
- `RAW-B` required = `ceil(2/1 * 6 * 1.05)` = `ceil(12.6)` = 13.
Assert `explode_bom` flattens to `[{"component_sku": "RAW-B", "required_qty": 13, "depth": 1}]`
(intermediate `SUB-001` consumed by explosion, not returned as a leaf).

**Cycle detection.**
Fixture: BOM `C1` for `FG-X` has component `FG-X` (same SKU, creating a self-loop).
Assert `explode_bom` raises `HTTPException(409)` with a message referencing the
cycle rather than recursing until stack overflow.

**Deactivating a BOM with an open work order blocked (409).**
Create BOM → create work order referencing it → attempt `delete_bom` → assert 409.
After cancelling the work order → `delete_bom` succeeds.

**Flag-off assertion.**
With `S.manufacturing_mrp_enabled = False`, any call to `create_bom` raises
`HTTPException(404)`.

### 5.2 Work-order lifecycle tests (`tests/test_mfg_work_orders.py`)

**Release → issue (component decrement).**
Seed inventory: `RAW-A` on_hand=20, `RAW-B` on_hand=10. BOM for `FG-001` requires
`RAW-A` qty 5 and `RAW-B` qty 3 per build unit, build_qty=2.
After `release_work_order`:
- `inventory.get_or_zero("RAW-A").on_hand == 10` (was 20, issued 10)
- `inventory.get_or_zero("RAW-B").on_hand == 4` (was 10, issued 6)
- Two `ISSUE#` rows written to `mfg_work_orders` table.
- Work-order `status == "released"`.

**Complete → produce (finished-goods increment).**
Continue from the released order above, advance to `in_progress` then `complete_work_order`.
Assert:
- `inventory.get_or_zero("FG-001").on_hand == 2` (was 0, produced 2).
- Work-order `status == "completed"`.
- `produce_guard == "done"` on the META row.

**Replay idempotency.**
Call `complete_work_order` a second time on the already-completed work order.
Assert:
- Returns the same header dict (no error).
- `inventory.get_or_zero("FG-001").on_hand` is still 2 (not 4).
- No second `ISSUE#` row was written.

**Insufficient-stock block (409).**
Seed `RAW-A` on_hand=3 (below the 10 needed). Call `release_work_order`.
Assert raises `HTTPException(409)`. Assert `RAW-A` on_hand is still 3 (rollback).
Assert work-order `status` is still `"created"` (no partial state written).

**Illegal transition (409).**
Attempt `complete_work_order` on a work order in `created` status (skipping
release). Assert raises `HTTPException(409)`.

**Cancel un-issue.**
Seed `RAW-A` on_hand=20. Release a work order (issues 10 units). Cancel the
released order. With `S.mfg_cancel_unissue_enabled = True`, assert
`RAW-A` on_hand is restored to 20.

**Flag-off assertion.**
With `S.manufacturing_mrp_enabled = False`, `create_work_order` raises `HTTPException(404)`.

### 5.3 MRP math tests (`tests/test_mfg_mrp.py`)

**Basic net-requirement math.**
Fixture:
- Open sales orders for `FG-001`: total quantity 50 within horizon.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity**: all four service modules use moto-backed local DDB in dev
and real DDB in prod through the same `T.*` handle — no `dev_mode` branch anywhere
in manufacturing business logic. The tests exercise the real service code on
moto-bound handles; the same code runs unmodified in prod.

**Idempotency surface**:
- `create_work_order`: deterministic `sha256(correlation_id)[:32]` id; duplicate
  call with same `correlation_id` returns 409 (not a silent overwrite).
- `release_work_order`: `issues_guard` CAS (`issues_guard <> :done`) prevents
  double-issue under replay. Tests verify this by calling `release_work_order`
  twice and asserting component inventory is decremented only once.
- `complete_work_order`: `produce_guard` CAS prevents double-produce. Tests verify
  finished-goods `on_hand` is incremented only once.
- `run_mrp`: `attribute_not_exists(mrp_run_id)` conditional put on META row; second
  call with same `correlation_id` returns the existing run.
- GL hook: deterministic `entry_id = sha256("mfg:{work_order_id}")[:16]`;
  `attribute_not_exists(sk)` conditional put to `T.billing`.

**Security**: all manufacturing write endpoints require `require_admin_or_root_csrf`
(`app/auth/policy.py:100`). The E2E spec asserts that Bob (a USER role) receives
403 on any write endpoint. The hermetic tests do not exercise the HTTP auth layer
(they call service functions directly); auth enforcement is validated in the E2E
spec.

**No money-out path**: production is an internal value transfer. The GL hook uses
`entry_type="internal_transfer"`, `state="settled"`, no `provider` field. No
payment intent, no wallet debit, no refund path is triggered.

**Audit trail**: every service transition emits `alerts.audit_event` via the
`_audit` best-effort wrapper (lazy import, swallows exceptions). Tests do not assert
audit output (fire-and-forget), consistent with the inventory and returns test
suites.

## 8. Backward Compatibility & Migration

**Flag-off guarantee**: with `MANUFACTURING_MRP_ENABLED=false` (the default), the
four manufacturing tables are provisioned but never accessed. The test suites
include at least one `test_flag_off_returns_404` case per service module (see §9.4).
The existing `inventory`, `billing`, `orders`, `catalog`, and `cart` tables and
their behavior are byte-for-byte unchanged when the flag is off — verified by the
flag-off regression block.

**No schema migrations**: the four manufacturing tables are new, so there are no
existing rows to migrate. The `scripts/local-ddb-init.py` table definitions are
additive: they appear after the `returns` `TableDef` at line 2492 and are created

## 10. Open Questions / Assumptions

1. **`T.orders` / `T.order_items` in hermetic tests**: `test_mfg_mrp.py` must bind
   these tables from `app/core/tables.py`. The test creates minimal order rows
   directly (skipping `commerce_order_service`) to avoid pulling in that service's
   full dependency tree. Assumption: `T.orders` PK=`order_id` (S), `T.order_items`
   PK=`order_id` (S) SK=`item_id` (S) — as confirmed by `scripts/local-ddb-init.py:287–295`
   (`orders` TableDef at line 287; `order_items` at line 295;
   referenced in `docs/ofbiz/specs/MFG-010.md:87`).

2. **`orders` GSI_STATUS sort key is String, not Number**: per `docs/ofbiz/specs/MFG-010.md:99–104`,
   `GSI_STATUS` on `T.orders` does not declare `attr_types={"created_at": "N"}`,
   so `created_at` is stored as String. The `run_mrp` implementation filters
   horizon in Python rather than using a DDB `FilterExpression` numeric range.
   The hermetic test seeds `created_at` as an integer on order rows and does not
   assert the GSI filter — it asserts only the final `gross_requirement` value.
   Assumption: this is correct and the MFG-010 implementation handles the String
   created_at on the orders GSI.

3. **E2E inventory seed endpoint**: the E2E spec (Section 2) needs to set on_hand
   for component SKUs. Assumption: `PATCH /ui/inventory/{sku}` (from MFG-011 /
   the inventory router at `app/routers/inventory.py`) accepts admin credentials
   and a `on_hand` body field. If no such endpoint exists, the test must seed
   inventory directly via DDB (Python script in `beforeAll`, similar to how
   `e2e_session_setup.py` seeds sessions).

4. **`mfg_cancel_unissue_enabled` default**: the MFG-007 spec states the default
   is `true`. The test `test_cancel_no_unissue_when_flag_off` must explicitly set
   `S.mfg_cancel_unissue_enabled = False`. Assumption: this setting is added to
   `app/core/settings.py` by MFG-002 alongside the master flag.

5. **BOM explosion formula for nested levels**: the MFG-004 spec (`docs/ofbiz/specs/MFG-004.md:343`)
   states `required_qty = ceil(quantity_per / output_quantity * build_qty * (1 + scrap_pct))`.
   For the nested-explosion test, each level applies its own `(1 + scrap_pct)` factor
   independently. Assumption: the explosion multiplies level quantities sequentially
   (depth-first), not additively.

6. **MRP `run_mrp` behavior when the BOM table has no record for a demand SKU**: if
   a finished-goods SKU has a sales order but no active BOM, MRP should emit a
   `suggested_action="purchase"` suggestion for the finished good itself (it is
   treated as a raw buy-to-stock item). Assumption: this is the correct fallback
   as implied by MFG-010 spec but not tested by MFG-014 explicitly.

7. **E2E flag sentinel**: the manufacturing E2E spec requires
   `MANUFACTURING_MRP_ENABLED=true` in the dev stack `.env.local`. Assumption:
   the CI/dev environment sets this flag when running the manufacturing E2E suite.
   If not, Section 4 of the spec must be annotated `test.skip` or the runner must
   set `process.env.MANUFACTURING_MRP_ENABLED`.
