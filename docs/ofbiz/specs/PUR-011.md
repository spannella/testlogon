# PUR-011 — Reorder-driven PO suggestions from low-stock signals

**Type:** Feature | **Priority:** P1 | **Estimate:** 4 days  
**Milestone:** 4 — Reorder-Driven Suggestions  
**Depends on:** PUR-006 (PO entity & creation service), PUR-004 (supplier-product pricing), OFB-005 (low-stock signals via `app/services/inventory.py`)

---

## 1. Summary & Goal

PUR-011 adds `app/services/reorder_suggestions.py`, a pure service module that:

1. Reads the live low-stock and out-of-stock inventory signals from the existing `inventory.list_low_stock` query (OFB-005, `app/services/inventory.py:318`).
2. For each low SKU, selects the best (preferred or cheapest) supplier via `supplier_products.list_suppliers_for_sku(sku)` (PUR-004, `GSI_SKU` ordered by `unit_cost_cents`).
3. Computes a suggested reorder quantity: `max(reorder_point - available, MOQ)`, rounded up to the nearest MOQ multiple.
4. Groups suggestions by supplier, ready for the HTTP layer (PUR-012) to present as an admin-facing list.
5. Materializes a suggestion into a `draft` Purchase Order via `purchase_orders.create_purchase_order` (PUR-006) using a deterministic correlation ID keyed on the suggestion, so repeated calls are idempotent.
6. Surfaces SKUs that have no supplier-product mapping as structured `"no_supplier"` warnings rather than silently discarding them.

The module is entirely service-layer (no router, no new tables, no direct DynamoDB writes of its own). It is gated behind the sub-flag `purchase_order_reorder_suggestions_enabled` (PUR-002), which defaults to `false`. With either `purchasing_scm_enabled` or `purchase_order_reorder_suggestions_enabled` off, every function raises `HTTPException(404)` and no DynamoDB access occurs. All existing shop/cart/orders/billing/inventory behavior is byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 Low-stock signal source (OFB-005)

`inventory.list_low_stock(location_status: str = "low_stock")` at `app/services/inventory.py:318–333` queries `T.inventory` via `GSI_AVAILABLE` (partition key `status`, sort key `available` numeric) and pages through all matching records:

```python
def list_low_stock(location_status: str = "low_stock") -> List[Dict[str, Any]]:
    out: List[Dict[str, Any]] = []
    kwargs: Dict[str, Any] = {
        "IndexName": "GSI_AVAILABLE",
        "KeyConditionExpression": Key("status").eq(location_status),
    }
    while True:
        resp = T.inventory.query(**kwargs)
        for it in resp.get("Items", []):
            out.append(_record_out(it))
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
    return out
```

The `_record_out` helper at `app/services/inventory.py:101–115` returns a dict with `sku`, `location_id`, `on_hand`, `reserved`, `available`, `reorder_point`, `status`, and `updated_at`. The `reorder_point` is read from the DDB item and falls back to `_default_reorder_point()` at `app/services/inventory.py:76–77` (`S.catalog_default_low_stock_threshold`, defaulting to `5`). The `status` field is one of `"in_stock"`, `"low_stock"`, or `"out_of_stock"` computed by `_status_for` at `app/services/inventory.py:84–89`.

PUR-011 calls this function with both `"low_stock"` and `"out_of_stock"` statuses to capture the full set of SKUs needing replenishment.

### 2.2 Supplier-product source (PUR-004)

`supplier_products.list_suppliers_for_sku(sku)` queries the `supplier_products` table via `GSI_SKU` (partition key `sku`, sort key `unit_cost_cents` N), returning all supplier-product records for a given SKU in ascending `unit_cost_cents` order — cheapest supplier first. Each record carries `supplier_id`, `unit_cost_cents`, `currency`, `lead_time_days`, `min_order_qty` (MOQ), `supplier_sku`, and `preferred` (bool).

The `GSI_SKU` is defined in `scripts/local-ddb-init.py` with `attr_types={"unit_cost_cents": "N"}` per PUR-002 scaffolding:

```
supplier_products — PK=supplier_id, SK=SKU#{sku}
GSI_SKU: partition=sku, sort=unit_cost_cents (N)
```

When the `preferred` flag is set on any record, the selection algorithm picks that record first regardless of cost rank. If no record carries `preferred=true`, the cheapest-by-`unit_cost_cents` record wins (the head of the GSI result).

### 2.3 Purchase-order creation (PUR-006)

`purchase_orders.create_purchase_order(...)` at `app/services/purchase_orders.py` (added by PUR-006, not yet in codebase) models its sha256-based deterministic ID on the existing `commerce_order_service.create_order` at `app/services/commerce_order_service.py:39–130`:

- Deterministic `po_id = hashlib.sha256(correlation_id.encode()).hexdigest()[:32]` (same pattern as `commerce_order_service.py:67`).
- Header `put_item` + per-line `put_item` loop.
- **NOTE**: `commerce_order_service.create_order` does NOT itself use `attribute_not_exists` — it issues an unconditional `put_item`. The idempotency guard (`ConditionExpression="attribute_not_exists(po_id)"`) is a PUR-006 design requirement, not a reuse of existing code. A duplicate call with the same `correlation_id` hits the same `po_id` key; the conditional `put_item` returns `ConditionalCheckFailedException` and the service returns the existing PO — idempotent.
- Returns `{"header": {...}, "lines": [...]}`.

PUR-011 builds the correlation ID as `sha256(f"reorder:{supplier_id}:{sorted_sku_list}")[:32]` (see Section 5.1 for the exact formula) so the same set of SKUs for the same supplier always produces the same `po_id`.

## 3. Data Model

PUR-011 introduces **no new DynamoDB tables**. All tables it reads are established by PUR-002 and written by OFB-005 (inventory) or PUR-004 (supplier_products). This section documents the read shapes PUR-011 depends on.

### 3.1 `inventory` table (read-only)

**PK** = `sku` (S), **SK** = `location_sk` (S, value `LOC#{location_id}`)

| GSI | Partition key | Sort key | `attr_types` |
|---|---|---|---|
| `GSI_AVAILABLE` | `status` (S) | `available` (N) | `{"available": "N"}` |

Fields consumed: `sku`, `available` (int), `reorder_point` (int), `status` (str), `location_id` (str).

PUR-011 calls `list_low_stock("low_stock")` and `list_low_stock("out_of_stock")` — two GSI queries over the same index with different partition key values. The combined result is de-duplicated by `sku` (taking the record with the lowest `available`; in a single-location deployment there are no duplicates).

### 3.2 `supplier_products` table (read-only)

**PK** = `supplier_id` (S), **SK** = `SKU#{sku}` (S)

| GSI | Partition key | Sort key | `attr_types` |
|---|---|---|---|
| `GSI_SKU` | `sku` (S) | `unit_cost_cents` (N) | `{"unit_cost_cents": "N"}` |

Fields consumed per record: `supplier_id`, `sku`, `unit_cost_cents` (int), `min_order_qty` (int), `preferred` (bool), `lead_time_days` (int), `supplier_sku` (str), `currency` (str).

### 3.3 `purchase_orders` table (read+write via PUR-006)

Documented in `docs/ofbiz/specs/PUR-006.md`. PUR-011 calls `purchase_orders.create_purchase_order(...)` which writes `META` + `LINE#{n}` rows — PUR-011 never writes directly to this table.

### 3.4 In-memory `ReorderSuggestion` shape

The service returns a list of these dicts — no DDB storage. The HTTP layer (PUR-012) serializes them to `ReorderSuggestionOut`:

```python
{
    "supplier_id": str,
    "supplier_name": str,   # from get_supplier() call; empty-string if unavailable
    "lines": [
        {
            "sku": str,
            "available": int,
            "reorder_point": int,
            "suggested_qty": int,
            "unit_cost_cents": int,
            "currency": str,
            "lead_time_days": int,
            "supplier_sku": str,
            "status": str,  # "low_stock" | "out_of_stock"
        },
        ...

    "total_cost_cents": int,   # Σ(suggested_qty * unit_cost_cents) across all lines
    "suggestion_correlation_id": str,  # deterministic, see §5.1
```

```python
{
    "sku": str,
```

#### 4.1.1 Flag helpers

```python
def _master_on() -> bool:
    return bool(getattr(S, "purchasing_scm_enabled", False))

def _suggestions_on() -> bool:
    return _master_on() and bool(getattr(S, "purchase_order_reorder_suggestions_enabled", False))

def _require_enabled() -> None:
    if not _suggestions_on():
        raise HTTPException(status_code=404, detail="Reorder suggestions are not enabled")
```

Both flags must be `true`; `_require_enabled()` is the first statement in every public function.

#### 4.1.2 Quantity math helper

```python
def _suggested_qty(available: int, reorder_point: int, moq: int) -> int:
    """Compute suggested order quantity.

    Formula: max(reorder_point - available, moq), rounded UP to nearest moq multiple.
    ``available`` may be negative (fully out-of-stock).  moq must be >= 1.
    """
    moq = max(int(moq), 1)
    gap = max(int(reorder_point) - int(available), moq)
    # Round up to nearest MOQ multiple
    remainder = gap % moq
    return gap if remainder == 0 else gap + (moq - remainder)
```

This is a pure function with no I/O — easy to unit-test in isolation.

#### 4.1.3 Supplier selection helper

```python
def _pick_supplier(
    candidates: List[Dict[str, Any]]
) -> Optional[Dict[str, Any]]:
    """Return the preferred supplier record, or cheapest if none preferred."""
    if not candidates:
        return None
    preferred = [c for c in candidates if c.get("preferred")]
    return preferred[0] if preferred else candidates[0]
```

`candidates` is the result of `list_suppliers_for_sku(sku)`, already sorted by ascending `unit_cost_cents` from `GSI_SKU`. If multiple records carry `preferred=true`, the first one (lowest cost among preferred) is returned.

#### 4.1.4 Main entry point: `compute_suggestions`

```python
def compute_suggestions(
    location_id: str = "warehouse",
) -> Dict[str, Any]:
    """Scan low-stock inventory and return suggestions grouped by supplier.

    Returns:
        {
          "suggestions": [ReorderSuggestion, ...],   # grouped by supplier_id
          "warnings":    [{"sku": ..., "available": ..., "reorder_point": ..., "status": ...}, ...],
          "scanned_at":  int,   # now_ts()
        }

    Raises HTTPException(404) when either flag is off.
    """
    _require_enabled()
    ...
```

Implementation steps:

1. **Collect low SKUs**: call `inventory.list_low_stock("low_stock")` and `inventory.list_low_stock("out_of_stock")`. Merge the two lists, de-duplicate by `sku` (take the entry with the lower `available`; ties broken by `out_of_stock` taking priority). SKUs present in both lists keep the `out_of_stock` record.

2. **Per-SKU supplier lookup**: for each unique `sku`, call `supplier_products.list_suppliers_for_sku(sku)`. This is a GSI query — one DDB round trip per SKU. If the result is empty, append to `warnings` and continue.

3. **Pick supplier and compute quantity**: call `_pick_supplier(candidates)` and `_suggested_qty(available, reorder_point, moq)`.

4. **Group by supplier**: accumulate `{supplier_id: [line, ...]}`. One suggestion per supplier.

5. **Enrich with supplier name** (best-effort): call `suppliers.get_supplier(supplier_id)` for each unique `supplier_id`. If the call fails or returns `None` (supplier deleted), use `supplier_name=""`.

6. **Build correlation IDs**: for each suggestion group, compute `suggestion_correlation_id` (see §5.1).

7. Return `{"suggestions": [...], "warnings": [...], "scanned_at": now_ts()}`.

#### 4.1.5 Convert suggestion to PO: `create_purchase_order_from_suggestion`

```python
def create_purchase_order_from_suggestion(
    suggestion: Dict[str, Any],
    *,
    actor_sub: str,
    currency: str = "USD",
    expected_delivery_date: Optional[str] = None,
) -> Dict[str, Any]:
    """Materialize a reorder suggestion into a draft PO (idempotent).

    Uses ``suggestion["suggestion_correlation_id"]`` as the PO correlation ID,
    so repeated calls with the same suggestion return the same ``po_id`` without
    creating a duplicate.

    Returns the ``{"header": {...}, "lines": [...]}`` dict from
    ``purchase_orders.create_purchase_order``.
    Raises HTTPException(404) when either flag is off.
    """
    _require_enabled()
    corr = suggestion["suggestion_correlation_id"]
    lines = [
        {
            "sku": ln["sku"],
            "quantity_ordered": ln["suggested_qty"],
            "unit_cost_cents": ln["unit_cost_cents"],
        }
        for ln in suggestion["lines"]
    ]
    po = purchase_orders.create_purchase_order(
        created_by=actor_sub,
        supplier_id=suggestion["supplier_id"],
        lines=lines,
        currency=currency,
        expected_delivery_date=expected_delivery_date,
        correlation_id=corr,
    )
    _audit(
        "reorder_suggestion.po_created",
        actor_sub,
        supplier_id=suggestion["supplier_id"],
        po_id=po["header"]["po_id"],
        line_count=len(lines),
        correlation_id=corr,
    )
    return po
```

The `purchase_orders.create_purchase_order` function uses `sha256(corr)[:32]` as the `po_id` and protects the header write with `attribute_not_exists(po_id)`. A second call with the same `corr` will encounter a `ConditionalCheckFailedException` and return the existing PO — exact idempotency guarantee.

## 5. Detailed Behavior & Edge Cases

### 5.1 Deterministic `suggestion_correlation_id`

The correlation ID must be stable across re-runs of `compute_suggestions` so that `create_purchase_order_from_suggestion` is idempotent. Construction:

```python
import hashlib, json

def _suggestion_correlation_id(supplier_id: str, skus: List[str]) -> str:
    # Sort SKUs so the ID is independent of iteration order
    key = json.dumps({"supplier_id": supplier_id, "skus": sorted(skus)}, sort_keys=True)
    return "reorder:" + hashlib.sha256(key.encode()).hexdigest()[:32]
```

This means: if the same supplier covers the same set of low SKUs on two consecutive calls, `create_purchase_order_from_suggestion` on either result returns the same `po_id`. If the low-SKU set changes between runs (a new SKU drops below its reorder point, or a previous one is replenished), the correlation ID changes and a new PO is created.

**Important caveat**: a new PO is only created if the SKU set is different. If SKU A was restocked after the first suggestion PO was created and then goes low again, the new suggestion for supplier X without SKU A will produce a new `po_id` (different SKU set → different hash). This is correct: the old PO covered a different demand signal.

### 5.2 MOQ rounding examples

| `available` | `reorder_point` | `moq` | `gap = max(rp-avail, moq)` | after rounding | result |
|---|---|---|---|---|---|
| 3 | 10 | 5 | max(7, 5) = 7 | ceil(7/5)*5 = 10 | 10 |
| 0 | 10 | 3 | max(10, 3) = 10 | ceil(10/3)*3 = 12 | 12 |
| -5 | 10 | 5 | max(15, 5) = 15 | already multiple | 15 |
| 10 | 10 | 1 | max(0, 1) = 1 | already multiple | 1 |
| 8 | 10 | 10 | max(2, 10) = 10 | already multiple | 10 |

The `available` value may be zero or negative when a SKU is `out_of_stock` (on_hand = 0, reserved = 0) or in a transient state where reserved exceeds on_hand. The formula handles both cases correctly since `available` enters the `max()` call directly.

### 5.3 No-supplier warning shape

When `list_suppliers_for_sku(sku)` returns an empty list, the SKU is appended to `warnings` as:

```python
{
    "sku": sku,
    "available": record["available"],
    "reorder_point": record["reorder_point"],
    "status": record["status"],  # "low_stock" | "out_of_stock"
}
```

The warning is **never silently dropped**. The caller (PUR-012 endpoint) must surface it in the response so admins know which SKUs need a supplier assignment before reordering can be automated. There is no 404 or 422 for a no-supplier SKU; warnings are a normal part of the response shape.

### 5.4 Multi-location considerations

`inventory.list_low_stock` returns one record per `(sku, location_sk)` pair. In the current single-location deployment (`DEFAULT_LOCATION = "warehouse"`) there is at most one record per SKU. When multi-location support is added (future), multiple records for the same SKU may appear. PUR-011 de-duplicates by `sku`, summing `available` across locations or taking the minimum — **Assumption A1** (see Section 10). For now, the de-dup takes the record with the lower `available` to produce a conservative suggestion.

### 5.5 Flag-off behavior

With either flag off, every public function in `reorder_suggestions.py` raises `HTTPException(404, "Reorder suggestions are not enabled")`. No DDB queries are issued. `T.inventory`, `T.supplier_products`, `T.purchase_orders` are not accessed. Existing shop/cart/billing behavior is unchanged.

### 5.6 Empty low-stock result

If `list_low_stock` returns an empty list (no SKU is currently low), `compute_suggestions` returns `{"suggestions": [], "warnings": [], "scanned_at": <ts>}`. This is not an error. The PUR-012 endpoint maps this to an HTTP 200 with an empty list.

### 5.7 Supplier-product GSI pagination

`list_suppliers_for_sku` must paginate via `LastEvaluatedKey` using the same loop pattern as `inventory.list_low_stock:321–333`. A SKU with many suppliers (unlikely but possible for a commodity item) must not truncate results, because the cheapest supplier might be on page 2. The GSI query uses `ScanIndexForward=True` (ascending `unit_cost_cents`), so the first item on page 1 is cheapest — pagination is only needed for the `preferred` flag scan, which requires seeing all records. In practice, most SKUs have 1–5 suppliers; the loop exits after one page.

### 5.8 `create_purchase_order` called with supplier from a different partition

`create_purchase_order` calls `get_supplier(supplier_id)` internally to validate the supplier exists (PUR-006 behavior). If the supplier was deleted between `compute_suggestions` and `create_purchase_order_from_suggestion`, the PO creation raises `HTTPException(404, "Supplier not found")`. The caller (PUR-012 router) should propagate this 404. This is not a data-consistency issue — it is a TOCTOU gap that will be encountered rarely.

### 5.9 `total_cost_cents` overflow guard

`total_cost_cents = sum(ln["suggested_qty"] * ln["unit_cost_cents"] for ln in lines)`. Python ints are unbounded; no overflow risk. However, the PUR-010 `unit_cost_cents` cap of `1_000_000_000` per unit and the `quantity_ordered` cap of `10_000_000` means the theoretical max per-line total is `10^15` cents — never stored in DDB by PUR-011 (it is in-memory only). The persisted `line_total_cents` on the PO row is subject to PUR-006's own validation.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

`reorder_suggestions.py` contains no `if S.dev_mode` branches. Every DDB access goes through `T.inventory`, `T.supplier_products`, and `T.purchase_orders` regardless of environment. In dev, these handles point at DynamoDB Local (port 8001). In prod, they point at real DynamoDB. The only environmental difference is `DDB_ENDPOINT_URL` in `.env.local`. This mirrors `app/services/inventory.py:1–29` which documents identical SECOPS-007 parity.

The `_audit` helper uses a lazy local import of `app.services.alerts.audit_event` in a `try/except` block, so an audit failure never aborts the main operation — same as `inventory._audit:92–98`.

### 7.2 Idempotency

**`compute_suggestions`** is a read-only scan; it is inherently idempotent (no writes). Calling it concurrently or repeatedly is safe.

**`create_purchase_order_from_suggestion`** is idempotent by construction:

- The `suggestion_correlation_id` is deterministic (same input → same hash).
- `purchase_orders.create_purchase_order` uses `sha256(corr)[:32]` as `po_id` and guards the header write with `attribute_not_exists(po_id)`.
- A second call with the same suggestion returns the existing PO rather than creating a duplicate (PUR-006 idempotency contract).
- The audit event fires on the first call only (the second call short-circuits at the `put_item` condition before reaching the `_audit` call in PUR-006). PUR-011's own `_audit("reorder_suggestion.po_created", ...)` is called after `create_purchase_order` returns — if `create_purchase_order` returns the existing PO (no-op path), the audit is still emitted. This is acceptable (audit shows intent, not just effect).

### 7.3 Security

**No customer-facing exposure**: `reorder_suggestions.py` exports no HTTP endpoints. All surfaces are mediated by PUR-012's admin-gated router (`require_admin_or_root_csrf` at `app/auth/policy.py:100–106`). A USER-role session cannot reach any suggestion function.

**No money movement**: `compute_suggestions` is read-only. `create_purchase_order_from_suggestion` creates a `draft` PO only — no payment, no inventory decrement, no ledger entry. The PO must proceed through the full approval lifecycle (PUR-007) and receiving (PUR-008) before any financial or stock side-effect occurs.

**Suggestion data never leaves the service layer**: the in-memory `ReorderSuggestion` dict holds no secrets. `unit_cost_cents` is supplier pricing data; it is only returned to admin/root role callers via PUR-012.

**Input validation**: `_suggested_qty` is called with `available` and `reorder_point` drawn from DDB records written by the inventory service — both are integers via `_to_int`. `moq` comes from `supplier_products` — also an integer. The function guards `moq = max(int(moq), 1)` to prevent division-by-zero.

## 10. Open Questions / Assumptions

**A1 — Multi-location de-duplication**: The spec assumes a single-location deployment (`DEFAULT_LOCATION = "warehouse"`). When multi-location is introduced, `list_low_stock` may return multiple records per SKU. The current de-dup (take the record with the lower `available`) may not be the correct business rule — an operator might want a location-specific suggestion rather than a global one. This should be revisited when multi-location support is added. For now, single-location is the safe assumption.

**A2 — `get_supplier` availability**: `compute_suggestions` calls `suppliers.get_supplier(supplier_id)` to enrich the suggestion with a `supplier_name`. If the `suppliers` service function is not yet available (PUR-003 unmerged), the enrichment can be skipped (`supplier_name=""`). The spec treats `get_supplier` as best-effort. Verify PUR-003 is merged before PUR-011 to get full enrichment.

**A3 — `purchase_orders.create_purchase_order` return shape on idempotent replay**: The PUR-006 spec describes the idempotent path as "returns the existing PO rather than creating a second one." This assumes the service re-fetches and returns `{"header": {...}, "lines": [...]}` even on the no-op path. If the implementation returns `None` on replay (some conditional-put patterns do this), `create_purchase_order_from_suggestion` must handle `None` and call `get_purchase_order(po_id)` explicitly. Confirm with PUR-006 implementer.

**A4 — `preferred` tie-breaking**: If two supplier-product records for the same SKU both carry `preferred=true`, the spec selects `candidates[0]` (the first in ascending `unit_cost_cents` order from `GSI_SKU`). This means "cheapest among preferred" wins. Confirm this is the intended business rule.

**A5 — Suggestion scope**: The spec scans all SKUs across all users' inventory records in a single-tenant deployment. In a multi-tenant deployment (where `T.inventory` is shared and rows belong to different tenants), the scan would surface suggestions across tenants. PUR-011 assumes single-tenant for now. The `location_id` parameter could be extended to a `tenant_id` filter in future without breaking the current call site.

**A6 — `audit_event` on idempotent replay**: The spec emits `"reorder_suggestion.po_created"` from PUR-011's wrapper even on the idempotent path (where the PO already exists). An alternative is to check whether the PO was newly created (e.g., by comparing the `created_at` timestamp to now) and only audit on first creation. This adds complexity without clear benefit — the audit record shows admin intent. Leaving as-is unless audit volume becomes a concern.

**A7 — SKUs below reorder point but not `low_stock`**: `_status_for(available, reorder_point)` (`app/services/inventory.py:84–89`) evaluates three cases in order: (1) `available <= 0` → `"out_of_stock"`, (2) `available <= reorder_point` → `"low_stock"`, (3) else `"in_stock"`. Therefore `available == reorder_point` is `"low_stock"` only when `available > 0`; if `available == reorder_point == 0` the result is `"out_of_stock"`. `list_low_stock("low_stock")` will return the `available == reorder_point > 0` SKU. The suggested quantity for this case is `max(0, moq) = moq` (gap = 0, max(0, moq) = moq). This is intentional — once at the reorder point, an order of at least MOQ is suggested.
