# SHP-002 — Shipping tables, settings & feature flags scaffolding

## 1. Summary & Goal

SHP-002 is the first code-shipping ticket in the OFBiz Shipping/Logistics work stream. Its deliverable is the pure infrastructure layer that every downstream SHP ticket depends on: four new DynamoDB tables in `scripts/local-ddb-init.py`, five new settings keys plus the master `SHIPPING_ENABLED` flag in `app/core/settings.py`, and four new table handles wired into `app/core/tables.py`.

No business logic, no Pydantic models, no routers, no service functions. The goal is that after this ticket merges, `just restart` recreates all four tables locally with no `ValidationException`, `T.shipping_carriers` / `T.shipments` / `T.shipment_items` / `T.shipment_packages` all resolve to live `_FloatSafeTable` proxies, and `S.shipping_enabled` defaults to `False` so the entire shipping surface is dormant.

## 2. Context & Current State

### 2.1 TableDef infrastructure

`scripts/local-ddb-init.py:28` defines the `TableDef` frozen dataclass (`@dataclass(frozen=True)`) with fields `name`, `partition_key`, `sort_key` (optional), `gsi` (list, default `[]`), and `attr_types` (a `Dict[str, str]` defaulting to `{}`). `_resolve_table_name` (`local-ddb-init.py:38`) returns `name or fallback` — the first argument when non-empty, falling back to a string literal; this is the canonical pattern for making table names settable via env var. The `_attribute_definitions` helper (`local-ddb-init.py:2496`) merges `attr_types` overrides *after* inferring `"S"` for all key attributes — so specifying `{"created_at": "N"}` in `attr_types` is the required mechanism to declare a numeric GSI sort key. Omitting it causes DynamoDB to default to String, which produces `ValidationException` when queried with integer values (CLAUDE.md gotcha).

## 3. Data Model

All four tables follow the single-table DynamoDB single-owner principle from `local-ddb-init.py`. Each `TableDef` is appended to the list returned by `_table_defs()` after the `returns` entry at line 2492.

### 3.1 Table: `shipping_carriers`

Carrier/ship-method catalog. Two row types share the same table: carrier header rows (SK = `CARRIER#`) and method rows (SK = `METHOD#{method_code}`).

| Attribute | Type | Notes |
|-----------|------|-------|
| `carrier_id` (PK) | String | Deterministic: `sha256(carrier_code.encode())[:16]` |
| `sk` (SK) | String | `CARRIER#` for header; `METHOD#{method_code}` for method rows |
| `carrier_code` | String | `ups` / `fedex` / `usps` / `dhl` / `manual` |
| `display_name` | String | e.g. "UPS Ground" |
| `online_tracking` | Boolean | True iff `carrier_code` is in `CARRIER_TRACKING_URLS` |
| `enabled` | Boolean | Soft-disable; disabled carriers hidden from rate estimation |
| `created_at` | Number | Unix epoch integer (`now_ts()`) — header row only |
| `updated_at` | Number | Unix epoch integer — header row only |
| `method_code` | String | `ground` / `express` / `overnight` / `economy` / `flat_rate` — method rows only |
| `method_label` | String | Display label — method rows only |
| `base_rate_cents` | Number | Default flat rate cents (≥ 0) — method rows only |
| `currency` | String | ISO 4217, e.g. `usd` — method rows only |
| `transit_days_min` | Number | Optional — method rows only |
| `transit_days_max` | Number | Optional — method rows only |

**GSIs:**
- `GSI_CODE` (`carrier_code` / `sk`) — query all methods for a carrier code; also find the carrier header row by code.

**`attr_types`:** none required — both GSI keys are String type (`carrier_code` and `sk`).

**TableDef:**
```python
TableDef(
    _resolve_table_name(S.shipping_carriers_table_name, "shipping_carriers"),
    "carrier_id",
    "sk",
    gsi=[
        {"index_name": "GSI_CODE", "partition_key": "carrier_code", "sort_key": "sk"},
    ],
)
```

### 3.2 Table: `shipments`

First-class Shipment entity — one per fulfillment batch, linked to one `orders` record. No sort key: `shipment_id` alone is the primary key so `get_item` is a direct hash lookup.

| Attribute | Type | Notes |
|-----------|------|-------|
| `shipment_id` (PK) | String | `sha256(correlation_id.encode())[:24]`; `correlation_id = "SHIP#{order_id}#{seq}"` |
| `order_id` | String | FK to `orders.order_id` |
| `user_id` | String | Buyer `user_sub` |
| `status` | String | Status enum: `pending` / `label_created` / `picked_up` / `in_transit` / `out_for_delivery` / `delivered` / `exception` / `returned` / `cancelled` |
| `carrier_code` | String | `ups` / `fedex` / `usps` / `dhl` / `manual` |
| `method_code` | String | e.g. `ground` |
| `ship_method_id` | String | Opaque FK: `{carrier_id}#METHOD#{method_code}` |
| `tracking_number` | String | Optional; set when label created |
| `tracking_url` | String | Built via `build_tracking_url`; set with tracking_number |
| `ship_to_address` | Map | Snapshot of address at ship time |
| `estimated_delivery` | String | ISO date string (optional) |
| `shipped_at` | Number | Unix epoch integer (optional) |
| `delivered_at` | Number | Unix epoch integer (optional) |
| `created_at` | Number | Unix epoch integer |
| `updated_at` | Number | Unix epoch integer |
| `weight_oz` | Number | Optional total weight |
| `purchase_txn_id` | String | Optional FK to `purchase_transactions.sk` |
| `correlation_id` | String | Stored for idempotency audits |

**GSIs:**
- `GSI_ORDER` (`order_id` / `created_at`) — list all shipments for an order, sorted by creation time.
- `GSI_STATUS` (`status` / `created_at`) — admin queue of shipments in a given status, sorted by creation time.

**`attr_types`:** `{"created_at": "N"}` — required because `created_at` is a numeric Unix timestamp used as the GSI sort key in both `GSI_ORDER` and `GSI_STATUS`. Without this declaration DynamoDB stores it as String, and integer-value range queries on the GSI raise `ValidationException`.

**TableDef:**
```python
TableDef(
    _resolve_table_name(S.shipments_table_name, "shipments"),
    "shipment_id",
    gsi=[
        {"index_name": "GSI_ORDER", "partition_key": "order_id", "sort_key": "created_at"},
        {"index_name": "GSI_STATUS", "partition_key": "status", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
)
```

## 5. Detailed Behavior & Edge Cases

### 5.1 `just restart` idempotency

`_ensure_table` (`local-ddb-init.py:2534`) checks whether the table name already exists in `client.list_tables()` (`local-ddb-init.py:2536`). If it does, it inspects `describe_table` and attempts to add any missing GSIs via `update_table`. Because no GSI on any shipping table is being added after-the-fact (all GSIs are declared from day one), the existing-table branch will be a no-op for all four shipping tables on every restart after the first.

### 5.2 `attr_types` validation chain

When `_attribute_definitions` is called for the `shipments` table:
1. Default dict starts with `{"shipment_id": "S"}` (hash key, string).
2. GSI partition key `order_id` → `"S"`.
3. GSI sort key `created_at` → `"S"` (initial default).
4. GSI partition key `status` → `"S"`.
5. `attrs.update({"created_at": "N"})` overrides the sort key to numeric.

Result: `created_at` is declared as `AttributeType: N` in both the `AttributeDefinitions` sent to DynamoDB and all GSI key schemas that reference it. This is required for integer range queries on both `GSI_ORDER` and `GSI_STATUS`.

For `shipping_carriers`, `shipment_items`, and `shipment_packages`, no numeric GSI sort keys exist, so `attr_types={}` (the default) is correct.

### 5.3 Flag is read, not enforced, in this ticket

SHP-002 does not introduce any guard code. The `shipping_enabled` flag is read by the `S` singleton immediately after `settings.py` is imported (at app startup). It defaults to `false`. Downstream service files (SHP-004, SHP-006, SHP-008) will add `_require_enabled()` guards — a pattern established by `app/services/returns_rma.py:67`–`:73` (verified):

```python
def _flag_on() -> bool:
    return bool(getattr(S, "returns_rma_enabled", False))

def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="Returns/RMA is not enabled")
```

The shipping equivalent will use `S.shipping_enabled` and raise `HTTPException(404, "Shipping is not enabled")`.

### 5.4 `_FloatSafeTable` proxy

All four handles are wrapped in `_FloatSafeTable` via `_safe_table` (`tables.py:65`). `_FloatSafeTable` (`tables.py:29`) intercepts `put_item` and `update_item` to coerce floats to `Decimal` via `_to_decimal`; all other attribute access falls through via `__getattr__` to the underlying boto3 `Table`. This means any `put_item` or `update_item` call that passes float values (e.g. `weight_oz = 16.5`) will have them coerced to `Decimal` automatically, avoiding the boto3 float-rejection error without each call site needing to know. `.name` is accessible on handles via `__getattr__` delegation to the boto3 Table.

### 5.5 Table name collisions

The default names `shipments` is a short, generic word. On a shared DynamoDB Local instance, no existing table uses this name (verified: `grep -n '"shipments"\|"shipment_items"\|"shipment_packages"\|"shipping_carriers"' scripts/local-ddb-init.py` returns no results at the time of writing). If a deployment uses a table-name prefix via env var, all four table names are fully configurable.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No dev/prod divergence in this ticket

SHP-002 is pure infrastructure with zero business logic. The `_ensure_table` function (`local-ddb-init.py:2534`) runs identically against DynamoDB Local (port 8001) and real DynamoDB — there is no `dev_mode` branch. Table creation is a one-time idempotent operation (re-running returns immediately when the table already exists). No mock path, no real path — just DynamoDB create-if-absent.

### 7.2 Settings singleton is process-global and immutable at runtime

`S` is a `@dataclass(frozen=True)` `Settings` instance (`app/core/settings.py:6`), with fields set at import time from `os.environ`. Test code mutates settings via `object.__setattr__(S, field, value)` as established in `tests/test_gap_0223_0224_ec2_host_inventory.py:110`. This is the only safe mutation path; no test helper should call `os.environ` mutation after import.

### 7.3 Table handles are unconditionally wired

Every table in `app/core/tables.py` is wired unconditionally (see the `T = Tables(...)` block at `tables.py:321`–`572`). The shipping handles follow the same pattern — they do not check `S.shipping_enabled` at wiring time. `_safe_table(name)` (`tables.py:65`) only calls `ddb.Table(name)` (a local boto3 resource reference), which makes no network call; actual DynamoDB traffic only occurs when a service calls `put_item` / `query` / etc. The feature flag gates business logic, not table handle creation.

### 7.4 No PII in new tables at this stage

SHP-002 creates empty tables; no data is written. When SHP-008 writes `ship_to_address` maps to `shipments`, those maps will contain street addresses (PII). That concern is for SHP-008 to document; this ticket introduces no PII.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact on existing tables

No existing `TableDef` is modified. No existing settings key is changed. No existing `Tables` field is renamed or removed. Existing code that imports `T.orders`, `T.order_items`, `T.purchase_transactions`, etc., is completely unaffected.

### 8.2 Additive-only changes

- `scripts/local-ddb-init.py`: four new entries appended to the returned list. `_table_defs()` is called exactly once at startup; adding entries to the list is safe.
- `app/core/settings.py`: seven new fields appended after `:847`. The `Settings` dataclass is frozen; appending fields does not affect existing field access.
- `app/core/tables.py`: four new fields appended to the `Tables` dataclass after `returns`. The `Tables` dataclass is also frozen (`@dataclass(frozen=True)` at `tables.py:68`). Because Python dataclasses must list all fields in the constructor, and `T` is constructed with explicit keyword arguments in `tables.py:321`, adding new keyword arguments at the end does not break existing code.

### 8.3 DynamoDB Local migration

`just restart` runs `scripts/local-ddb-init.py` from scratch (wipe + recreate). The four new tables appear automatically on the next `just restart`. No manual `aws dynamodb create-table` invocation is needed.

On a production DynamoDB environment where the tables do not yet exist, deploying the updated `local-ddb-init.py`-equivalent provisioning script creates them. Because `_ensure_table` uses `create_table` with a `TableAlreadyExistsException` guard (implicit in the `if table.name in existing` check), re-running the provisioning script is safe.

## 10. Open Questions / Assumptions

1. **Placement in `settings.py`**: Assumed that the new block is appended after the `returns_rma` block at `settings.py:847` (in the OFBiz section). An alternative is to place it adjacent to the carrier tracking block at `settings.py:343`–`:346`. The two locations are logically equivalent; the assumption here is that keeping all OFBiz flags grouped together (inventory → returns → shipping) is more readable.

2. **`SHIPMENTS_TABLE_NAME` vs `SHIPMENT_TABLE_NAME`**: The ticket ticket specifies `shipments_table_name` (plural), matching the table's default name `"shipments"`. This is consistent with `orders_table_name` / `"orders"` and `reservations_table_name` / `"reservations"`. Assumed correct.

3. **`shipments` table has no sort key**: The `orders` table (`local-ddb-init.py:287`) also has no sort key (`order_id` alone is the primary key). The assumption is that `shipment_id` is globally unique (derived from `sha256(correlation_id)[:24]`) and no composite primary key is needed. If an administrative pattern requires listing all shipments for a user without going through `order_id`, a `GSI_USER` on `user_id` / `created_at` could be added here or in a follow-up ticket. Not assumed necessary for SHP-002.

4. **No `shipments` → `purchase_transactions` back-link at table creation time**: The `purchase_txn_id` attribute described in Section 3.2 is stored when SHP-008 links a shipment to a transaction. The attribute is not declared in the `TableDef` because it is not a key attribute — it is a regular map attribute written by service code.

5. **`shipping_default_currency` vs `stripe_default_currency`**: Both exist independently. Shipping rate quotes use `shipping_default_currency`; payment settlement continues to use `stripe_default_currency`. They happen to default to the same value (`"usd"`).

6. **`shipment_packages.package_seq` as string**: Zero-padded `"00001"` chosen over an integer to avoid the `attr_types={"package_seq": "N"}` requirement and to allow lexicographic sort in any range scan. Since packages are only ever queried by exact `shipment_id` + `package_seq` or by prefix query, the numeric vs string distinction has no functional impact.

7. **No `_ensure_table` GSI-add logic for shipping tables**: The `_ensure_table` hot-path that adds missing GSIs (via `update_table`) is used when a GSI is added to an existing table in a subsequent PR. Because all GSIs for all four shipping tables are declared from the start, the hot-path will never trigger for these tables in normal operation. If a GSI is added in a future SHP ticket, no special migration code is needed — `_ensure_table` handles it automatically.
