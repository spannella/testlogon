# PTY-007 — Unified contact-mechanism service (email / phone / postal)

## 1. Summary & Goal

PTY-007 adds the `contact_mech` layer to the OFBiz-style party graph being built in `app/services/party.py`. It enables a party (PERSON or PARTY_GROUP, created by PTY-004) to carry multiple contact mechanisms — email addresses, phone numbers, and postal/mailing addresses — each tagged with one or more typed purposes (e.g., `PRIMARY_EMAIL`, `BILLING`, `SHIPPING`). A reverse-lookup index lets callers resolve a party from a known contact value without scanning.

This ticket is additive and flag-gated. With `S.party_crm_enabled = False` (the default), no existing surface — `app/routers/contacts.py`, `app/services/addresses.py`, `app/services/profile.py` — is altered in any way.

## 2. Context & Current State

### What already exists

**Legacy contacts table** (`scripts/local-ddb-init.py:691`): bare two-column table `TableDef("Contacts", "owner_id", "contact_id")` — no GSIs. Used by `app/routers/contacts.py`; unchanged by this ticket.

## 3. Data Model

### Single table: `party` (owned by PTY-002)

All contact-mech rows share the `party` table (PK = `PK`, SK = `SK`).

#### Primary row — mech item

| Attribute | Type | Value |
|-----------|------|-------|
| `PK` | S | `PARTY#{party_id}` |
| `SK` | S | `MECH#{mech_type}#{mech_id}` |
| `mech_id` | S | `uuid4().hex` (or `sha256(correlation_id)[:32]` if supplied) |
| `party_id` | S | foreign key to `PARTY#{party_id} / META` |
| `mech_type` | S | `EMAIL` \| `PHONE` \| `POSTAL` |
| `value` | S or M | normalized scalar for EMAIL/PHONE; full address dict for POSTAL |
| `purposes` | SS | set of purpose strings (validated against allowlist) |
| `verified` | BOOL | default `False`; set to `True` only by a server-side verification flow (future) |
| `created_at` | N | `now_ts()` — integer Unix seconds |
| `updated_at` | N | `now_ts()` |
| `correlation_id` | S | the caller-supplied `correlation_id` string, persisted as-is (omitted when `None`); enables PTY-010 `_resync_postal_mech` to identify PTY-010-seeded mechs via a `starts_with("MECH:POSTAL:{user_sub}:")` filter on `list_contact_mechs` results |
| `GSI2PK` | S | `EMAIL#{normalized}` / `PHONE#{e164}` / `POSTAL#{sha256_hex[:16]}` |
| `GSI2SK` | S | `PARTY#{party_id}` |

The `GSI2PK` for POSTAL is the first 16 hex chars of `sha256(json.dumps(normalized_addr, sort_keys=True).encode()).hexdigest()`. This allows `find_party_by_contact("POSTAL", addr_dict)` to normalize-then-hash and query `GSI2`.

#### Reverse-lookup GSI (already declared by PTY-002, but explicitly confirmed here)

`GSI2` (`GSI2PK` partition / `GSI2SK` sort) must be declared in `scripts/local-ddb-init.py` inside the `party` `TableDef` alongside the existing GSIs. This GSI allows O(1) lookup of all parties for a given contact value.

#### `attr_types` required

The `party` table `TableDef` (added by PTY-002) must declare:

```python
attr_types={"created_at": "N", "GSI1SK": "S", "GSI3SK": "S"}
```

The mech `created_at` / `updated_at` fields are not GSI sort keys (they are item attributes), so they do not need `attr_types` entries. However `GSI_CREATED` (used by PTY-004's `list_parties`) must carry `attr_types={"created_at": "N"}` — ensure the `party` table `TableDef` includes that as PTY-002 specifies.

## 4. API / Service Design

### 4.1 Service functions — `app/services/party.py` additions

```python
# Purpose allowlist (module-level constant)
CONTACT_MECH_PURPOSES = frozenset({
    "PRIMARY_EMAIL",
    "BILLING",
    "SHIPPING",
    "PRIMARY_PHONE",
    "FAX",
    "WORK_EMAIL",
    "WORK_PHONE",
    "HOME_PHONE",
    "MOBILE_PHONE",
    "GENERAL_CORRESPONDENCE",
    "SALES_CORRESPONDENCE",
    "BILLING_CORRESPONDENCE",
})

def add_contact_mech(
    party_id: str,
    mech_type: str,
    value: Any,        # str for EMAIL/PHONE, dict for POSTAL
    purposes: List[str],
    *,
    correlation_id: Optional[str] = None,
    verified: bool = False,
) -> Dict[str, Any]:
    ...

def list_contact_mechs(
    party_id: str,
    mech_type: Optional[str] = None,  # None → all types
) -> List[Dict[str, Any]]:
    ...

def update_contact_mech(
    party_id: str,
    mech_id: str,
    *,
    purposes: Optional[List[str]] = None,
    verified: Optional[bool] = None,
) -> Dict[str, Any]:
    ...

def remove_contact_mech(
    party_id: str,
    mech_id: str,
) -> None:
    ...

def find_party_by_contact(
    mech_type: str,
    value: Any,        # str for EMAIL/PHONE, dict for POSTAL
) -> List[Dict[str, Any]]:   # list of party dicts (via get_party)
    ...
```

All functions raise `HTTPException(400, ...)` for invalid `mech_type` or unknown purposes, `HTTPException(404, "party not found")` when `get_party(party_id)` returns nothing, and `HTTPException(404, "mech not found")` in `update_contact_mech` / `remove_contact_mech`.

**`add_contact_mech` internals:**
1. Call `get_party(party_id)` — raises 404 if absent.
2. Validate `mech_type in {"EMAIL", "PHONE", "POSTAL"}` — 400 otherwise.
3. Normalize value: `normalize_email(value)` for EMAIL; `normalize_phone(value)` for PHONE; `normalize_address_payload(value, require_all=True)` for POSTAL (line1 required).
4. Validate each element of `purposes` against `CONTACT_MECH_PURPOSES` — 400 on unknown purpose.
5. Derive `mech_id = hashlib.sha256(correlation_id.encode()).hexdigest()[:32]` if `correlation_id` is supplied, else `uuid.uuid4().hex`.
6. Build `gsi2_pk` from the normalized value: `f"EMAIL#{norm}"`, `f"PHONE#{e164}"`, or `f"POSTAL#{hash16}"`.
7. Write the item with `ConditionExpression="attribute_not_exists(#pk)"` (using `ExpressionAttributeNames={"#pk": "PK"}`). Include `correlation_id` as a plain string attribute on the item when it is not `None` (see §3 data-model table). On `ConditionalCheckFailedException`, if `correlation_id` was supplied, read and return the existing item (idempotent replay); otherwise propagate as 409.
8. Emit `audit_event("party.contact_mech.add", party_id, mech_type=mech_type, mech_id=mech_id)`.
9. Return the written item.

**`remove_contact_mech` internals:**

The public signature `remove_contact_mech(party_id: str, mech_id: str) -> None` does NOT include `mech_type`. Because the DynamoDB SK is `MECH#{mech_type}#{mech_id}`, the function must resolve `mech_type` internally before it can build the full SK. The resolution strategy is:

1. Call `list_contact_mechs(party_id, mech_type=None)` to retrieve all mech items for the party.
2. Find the item whose `mech_id` attribute equals the supplied `mech_id`. Raise `HTTPException(404, "mech not found")` if no item matches.
3. Read `mech_type` from the matched item to reconstruct `SK = f"MECH#{mech_type}#{mech_id}"`.
4. Delete the primary row using that full SK.
5. Emit `audit_event("party.contact_mech.remove", party_id, mech_id=mech_id)`.

**`find_party_by_contact` internals:**
1. Normalize `value` using the same path as `add_contact_mech` (EMAIL/PHONE → scalar norm; POSTAL → hash16 of canonical JSON).
2. Query `GSI2` using `KeyConditionExpression=Key("GSI2PK").eq(gsi2_pk)`.
3. For each returned item, call `get_party(item["party_id"])` and collect non-None results.
4. Return the list of party dicts.

## 5. Detailed Behavior & Edge Cases

### 5.1 Normalization rules

- **EMAIL**: `normalize_email(value)` (`app/core/normalize.py:60`) — strips whitespace, lowercases, rejects if no `@` or length > 254. `find_party_by_contact("EMAIL", "Alice@X.com ")` produces `GSI2PK = "EMAIL#alice@x.com"` matching the stored normalized value.
- **PHONE**: `normalize_phone(value)` (`app/core/normalize.py:66`) — strips formatting, returns `+{digits}`. 10-digit → `+1{digits}`. Returns 400 on unrecognized format.
- **POSTAL**: `normalize_address_payload(value, require_all=True)` (`app/services/addresses.py:39`) — `line1` is mandatory; `country` defaults to `"US"`; all fields are stripped/truncated. The `GSI2PK` hash is `sha256(json.dumps(normalized, sort_keys=True))[:16]` computed over the dict returned by `normalize_address_payload`. POSTAL `value` stored on the item is the full normalized dict (stored as a DynamoDB `M` attribute), not a scalar.

### 5.2 Purpose validation

Unknown purposes raise `HTTPException(400, f"Unknown purpose(s): {unknown}")`. The purpose list is stored as a DynamoDB `SS` (string set). An empty `purposes` list is valid (a mech with no tagged purpose is permitted). Duplicate purposes in the input list are silently de-duplicated before storage.

### 5.3 Idempotency

When `correlation_id` is supplied, `mech_id = sha256(correlation_id)[:32]` and the `put_item` uses `ConditionExpression="attribute_not_exists(#pk)"`. On `ConditionalCheckFailedException` the existing item is returned unchanged — no error is raised. This matches the pattern in `app/services/commerce_order_service.py:67`.

When `correlation_id` is not supplied, a fresh `uuid4().hex` is used and every call creates a new mech regardless of duplicated values. Callers that want idempotency must supply a `correlation_id`.

### 5.4 Multiple mechs of the same type

A party can have multiple EMAIL, PHONE, or POSTAL mechs. `list_contact_mechs(party_id, mech_type="EMAIL")` filters by a DynamoDB `begins_with` on the SK: `SK begins_with "MECH#EMAIL#"`. A `mech_type=None` call queries all `SK begins_with "MECH#"`.

### 5.5 Reverse-lookup collisions

`GSI2` returns all items with the same `GSI2PK`. For EMAIL/PHONE, collisions are expected when the same address appears across multiple parties (e.g., a shared billing email). `find_party_by_contact` returns all matching parties — the caller decides which to use. For POSTAL, hash collisions are astronomically rare but not impossible; in that case the caller receives multiple results and must disambiguate on the full address value.

### 5.6 Party existence check

`add_contact_mech`, `list_contact_mechs`, `update_contact_mech`, `remove_contact_mech` all call `get_party(party_id)` first (raises `HTTPException(404, "party not found")`). This prevents orphaned mech rows from accumulating against deleted parties.

### 5.7 update_contact_mech scope

`update_contact_mech` only allows changing `purposes` and `verified`. The `mech_type` and `value` are immutable after creation (to preserve the `GSI2PK` index). To change a contact value, callers must `remove_contact_mech` + `add_contact_mech`. This prevents stale `GSI2PK` values.

### 5.8 Flag guard

Every service function begins with:
```python
if not S.party_crm_enabled:
    raise HTTPException(404, "Party CRM is not enabled")
```
The router (PTY-011) adds a second guard at the handler level. The double guard ensures neither direct service calls nor HTTP calls bypass the flag.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Single code path**: All DynamoDB writes go to `T.party` regardless of environment. There is no `dev_mode` branch — moto intercepts botocore calls in dev, real DynamoDB is used in prod; the application code is identical (SECOPS-007).

**Idempotency**: `sha256(correlation_id)[:32]` for `mech_id` + `ConditionExpression="attribute_not_exists(#pk)"` ensures a repeated call with the same `correlation_id` is a no-op that returns the original item. The `add_contact_mech` catch block reads back and returns the existing row on `ConditionalCheckFailedException`.

**Value sensitivity**: POSTAL addresses are full personal-address data. The `value` field is stored in DynamoDB and never hashed for the primary item (only hashed for the `GSI2PK` reverse-lookup key). Access to mech rows is gated on `require_ui_session`; the router (PTY-011) additionally enforces that the requesting user is the party owner or holds admin-level session (`require_admin_session` for foreign-party reads) — that authorization logic belongs to PTY-011.

**Phone normalization and E.164**: `normalize_phone` (`app/core/normalize.py:66`) is already used by `app/services/profile.py:9` (`from app.core.normalize import normalize_email, normalize_phone`) for the `displayed_telephone_number` profile field (`profile.py:215-216`). Reusing it ensures the same E.164 form is stored in both the profile and the party mech, enabling future cross-system deduplication.

**No secrets stored**: `verified` is a plain boolean. The verification token/OTP flow (if built in a future ticket) would be a separate temporary token stored elsewhere, never in the mech row.

**Audit trail**: Every `add_contact_mech` / `remove_contact_mech` call emits an `audit_event` to `T.alerts` via `app.services.alerts.audit_event`. `update_contact_mech` emits `"party.contact_mech.update"`. The audit payload includes `party_id`, `mech_type`, `mech_id`, and (for add) the normalized value, so compliance tooling can reconstruct the history.

## 10. Open Questions / Assumptions

1. **POSTAL GSI2PK hash stability**: This spec assumes the canonical JSON for POSTAL hashing is `json.dumps(normalized_dict, sort_keys=True)`. If the set of keys returned by `normalize_address_payload` changes (e.g., a new optional field is added), existing `GSI2PK` hashes will not match. The assumption is that the normalized dict shape is stable for a given address; adding fields would require re-indexing all POSTAL mechs.

2. **`value` storage for POSTAL as DynamoDB `M`**: DynamoDB `put_item` auto-maps a Python `dict` to a Map attribute. Queries returning `value` will get back a Python `dict`. This is assumed correct and matching `ContactMechOut.value: Any`.

3. **E164 normalization for international numbers**: `normalize_phone` (`app/core/normalize.py:66`) only handles US 10-digit and `+{digits}` formats. Numbers in formats like `+44 7911 123456` (with spaces) are handled by the `re.sub(r"[\s\-\(\)\.]", "", s)` strip, but `s2.startswith("+")` logic only strips non-digit characters after `+`. This spec assumes that behavior is correct; non-US numbers in `+44...` form work; ambiguous 7-8 digit numbers without a country prefix will get 400.

4. **No `value` mutation in `update_contact_mech`**: Assumed immutable to preserve `GSI2PK` consistency. If business needs require updating a value in place, a separate migration pattern (remove + add) must be documented.

5. **`verified` flag semantics**: Currently a plain stored boolean with no server-side enforcement. The assumption is that future verification flows will set it via a separate endpoint (not in scope here). 6. **Duplicate values across mechs on the same party**: No uniqueness constraint prevents a party from having two EMAIL mechs with the same address. The assumption is this is acceptable (OFBiz allows it), and the `correlation_id` idempotency guard handles the "add once" use case.

A direct module-level `from app.services.alerts import audit_event` would also work (no circular import risk since `alerts.py` does not import `party.py`), but the codebase convention in `ssh_key_manager.py` and `host_inventory.py` is to use the lazy local-import wrapper so that an alerts failure can never break the caller. CORRECTED: the spec previously claimed a module-level import was consistent with `ssh_key_manager.py`; that service actually uses a local import.
