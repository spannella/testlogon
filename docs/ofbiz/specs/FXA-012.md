# FXA-012 — Maintenance work-order service & lifecycle

## 1. Summary & Goal

FXA-012 adds the maintenance work-order service layer to `app/services/asset_maintenance.py` (a sibling module to the asset register service in `app/services/fixed_assets.py`). It implements four public functions — `create_work_order`, `get_work_order`, `list_work_orders`, and `transition_work_order` — that own all DynamoDB I/O against `T.maintenance_orders`.

The core delivery:

- **Work-order CRUD**: create a work order against any non-disposed asset; retrieve or list by asset, status, or assignee; record an optional `cost_cents` on completion.
- **Lifecycle enforcement**: the state machine `open → in_progress → completed` (and `→ cancelled` from `open` or `in_progress`) is enforced in the service layer by a `VALID_TRANSITIONS` constant dict, mirroring the pattern at `app/services/tickets.py:30–40` (`_STATUS_TRANSITIONS: dict[str, tuple[str, ...]]`). <!-- VERIFIED: tickets.py:30 --> Illegal transitions raise HTTP 409 with `detail="illegal_transition"`.
- **Asset guard**: creating a work order against a `disposed` asset raises HTTP 400 with `detail="asset_disposed"`. Validation uses `get_asset` from `app/services/fixed_assets.py` (FXA-005).
- **Audit trail**: every create and every transition emits a best-effort `audit_event` call, using the `_audit` wrapper established by `app/services/inventory.py:92–98`. <!-- VERIFIED: inventory.py:92–98 -->
- **Deterministic-id idempotency**: `work_order_id = sha256(corr)[:32]` where `corr = correlation_id or f"wo:{actor_sub}:{uuid4().hex}"`, identical to the pattern at `app/services/commerce_order_service.py:64–67`. <!-- VERIFIED: commerce_order_service.py:64,66,67 -->
- **Cost recording only**: `cost_cents` is stored on the work-order row for reporting at completion time. No GL posting, no billing ledger write. Maintenance expense capitalization is explicitly out of scope per `docs/ofbiz/specs/FXA-001.md:32` (out-of-scope list item: "Maintenance expense capitalization to asset cost").

All code is additive and flag-gated on `S.fixed_assets_enabled`. Existing shop, cart, orders, billing, and inventory paths are byte-for-byte unchanged with the flag off.

## 5. Detailed Behavior & Edge Cases

### 5.1 `create_work_order` — idempotent creation with asset guard

```
1. _require_enabled()
2. Validate asset is not disposed:
       from app.services.fixed_assets import get_asset
       asset = get_asset(actor_sub, asset_id)
       if asset is None:
           raise HTTPException(404, "asset_not_found")
       if asset.status == "disposed":
           raise HTTPException(400, "asset_disposed")
3. Derive correlation key:
       corr = body.correlation_id or f"wo:{actor_sub}:{uuid4().hex}"
       work_order_id = sha256(corr.encode()).hexdigest()[:32]
4. Build the DDB item:
       ts = now_ts()
       pk = _wo_pk(asset_id)
       sk = _wo_sk(work_order_id)
       item = {
           "pk": pk, "sk": sk,
           "work_order_id": work_order_id,
           "asset_id": asset_id,
           "title": body.title,
           "description": body.description,
           "wo_status": "open",
           "assignee_sub": body.assignee_sub,    # may be None
           "scheduled_for": body.scheduled_for,  # may be None
           "correlation_id": corr,
           "created_at": ts,
           "updated_at": ts,
       }
       # cost_cents and completed_at are absent on create
5. Conditional put:
       try:
           ddb_put(T.maintenance_orders, item,
                   condition_expression="attribute_not_exists(pk) AND attribute_not_exists(sk)")
       except ClientError as exc:
           if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
               existing = T.maintenance_orders.get_item(
                   Key={"pk": pk, "sk": sk}
               ).get("Item") or {}
               _audit("maintenance_order.create.idempotent", actor_sub,
                      work_order_id=work_order_id, asset_id=asset_id)
               return _item_to_out(existing)
           raise
6. _audit("maintenance_order.created", actor_sub,
           work_order_id=work_order_id, asset_id=asset_id,
           title=body.title, assignee_sub=body.assignee_sub,
           correlation_id=corr, outcome="success")
7. return _item_to_out(item)
```

**Why `attribute_not_exists(pk) AND attribute_not_exists(sk)` (not just `pk`):** The `maintenance_orders` table has multiple rows per partition key (one `WO#` row per work order within an asset's partition). The uniqueness constraint is on the composite `(pk, sk)` pair — `attribute_not_exists(pk)` alone would fail on the second work order created for the same asset. The condition must target `sk` or use `attribute_not_exists(sk)`.

**Asset guard timing:** The `get_asset` call at step 2 is a best-effort guard — it is not wrapped in a DDB transaction with the conditional put. A concurrent disposal between step 2 and step 5 can slip through. This is acceptable: a work order created nanoseconds before an asset is disposed is a legitimate race; the admin can cancel it immediately. A transactional guard would require `TransactWriteItems` across two tables, adding complexity out of proportion to the risk.

### 5.3 `list_work_orders` — three query modes

The function selects the DDB query path based on which filter arguments are non-None. Priority: `asset_id` > `wo_status` > `assignee_sub`. Exactly one index is queried per call; combining filters uses `FilterExpression` post-query.

**Mode A — by asset (base table):** When `asset_id` is supplied, query the base table on `pk = "ASSET#{asset_id}"` with `ScanIndexForward=False` (most recently created first). Optional `wo_status` becomes a `FilterExpression`. This is the tightest query (bounded partition) and is the common case for the asset-detail view.

**Mode B — by status (GSI_WO_STATUS):** When `wo_status` is supplied and `asset_id` is None, query `GSI_WO_STATUS` with `wo_status` as partition key, `ScanIndexForward=False`. This drives the open work-order queue. Because `FilterExpression` on `GSI_WO_STATUS` does not reduce the DDB page size (CLAUDE.md "DDB FilterExpression" gotcha), a status-only query returns up to `limit` items from the index page, honouring the `cursor`. An optional `assignee_sub` filter here becomes a `FilterExpression` that may yield fewer than `limit` items from a single page — callers must follow the `cursor` to get a complete list.

**Mode C — by assignee (GSI_WO_ASSIGNEE):** When `assignee_sub` is supplied and both `asset_id` and `wo_status` are None, query `GSI_WO_ASSIGNEE`. An optional `wo_status` becomes a `FilterExpression`.

```python
def list_work_orders(asset_id=None, wo_status=None, assignee_sub=None, cursor=None, limit=50):
    _require_enabled()
    kwargs = {"ScanIndexForward": False, "Limit": limit}
    if cursor:
        kwargs["ExclusiveStartKey"] = decode_cursor(cursor)

    if asset_id:
        # Mode A — base table, bounded partition
        kwargs["KeyConditionExpression"] = Key("pk").eq(_wo_pk(asset_id))
        if wo_status:
            kwargs["FilterExpression"] = "wo_status = :s"
            kwargs["ExpressionAttributeValues"] = {":s": wo_status}
        resp = T.maintenance_orders.query(**kwargs)
    elif wo_status:
        # Mode B — open/in-progress queue
        kwargs["IndexName"] = "GSI_WO_STATUS"
        kwargs["KeyConditionExpression"] = Key("wo_status").eq(wo_status)
        if assignee_sub:
            kwargs["FilterExpression"] = "assignee_sub = :a"
            kwargs["ExpressionAttributeValues"] = {":a": assignee_sub}
        resp = T.maintenance_orders.query(**kwargs)
    elif assignee_sub:
        # Mode C — assignee queue
        kwargs["IndexName"] = "GSI_WO_ASSIGNEE"
        kwargs["KeyConditionExpression"] = Key("assignee_sub").eq(assignee_sub)
        if wo_status:
            kwargs["FilterExpression"] = "wo_status = :s"
            kwargs["ExpressionAttributeValues"] = {":s": wo_status}
        resp = T.maintenance_orders.query(**kwargs)
    else:
        raise HTTPException(400, "supply asset_id, wo_status, or assignee_sub")

    items = [_item_to_out(i) for i in resp.get("Items", [])]
    result: Dict[str, Any] = {"items": items, "count": len(items)}
    if resp.get("LastEvaluatedKey"):
        result["cursor"] = encode_cursor(resp["LastEvaluatedKey"])
    return result
```

### 5.4 `transition_work_order` — lifecycle enforcement

```
1. _require_enabled()
2. resp = T.maintenance_orders.get_item(Key={"pk": _wo_pk(asset_id), "sk": _wo_sk(work_order_id)})
   item = resp.get("Item")
   if not item: raise HTTPException(404, "work_order_not_found")
3. current = item["wo_status"]
   target = body.target_status
   if target not in VALID_TRANSITIONS.get(current, set()):
       raise HTTPException(409, "illegal_transition",
                           headers={"X-Current-Status": current,
                                    "X-Target-Status": target})
4. ts = now_ts()
   update_expr_parts = ["wo_status = :s", "updated_at = :ts"]
   expr_vals = {":s": target, ":ts": ts, ":current": current}
   # Set completed_at on completion:
   if target == "completed":
       update_expr_parts.append("completed_at = :ts")
   # Record cost_cents if provided (only meaningful on completed, but stored regardless):
   if body.cost_cents is not None:
       update_expr_parts.append("cost_cents = :cc")
       expr_vals[":cc"] = body.cost_cents
   # Optional reassignment:
   if body.assignee_sub is not None:
       update_expr_parts.append("assignee_sub = :as")
       expr_vals[":as"] = body.assignee_sub
   T.maintenance_orders.update_item(
       Key={"pk": _wo_pk(asset_id), "sk": _wo_sk(work_order_id)},
       UpdateExpression="SET " + ", ".join(update_expr_parts),
       ExpressionAttributeValues=expr_vals,
       ConditionExpression="wo_status = :current",
   )
5. updated = T.maintenance_orders.get_item(Key={"pk": _wo_pk(asset_id), "sk": _wo_sk(work_order_id)})["Item"]
6. _audit(f"maintenance_order.{target}", actor_sub,
           work_order_id=work_order_id, asset_id=asset_id,
           previous_status=current, new_status=target,
           cost_cents=body.cost_cents, outcome="success")
7. return _item_to_out(updated)
```

**`ConditionExpression="wo_status = :current"`** on the update prevents two concurrent transition calls from double-applying. If a second concurrent call wins the optimistic lock, the first caller's `update_item` raises `ConditionalCheckFailedException`. The service maps this to HTTP 409 `"concurrent_transition"` — distinct from `"illegal_transition"` so the caller can disambiguate.

**`cost_cents` policy:** The `MaintenanceOrderTransitionIn` model accepts `cost_cents` on any transition, but business logic stores it unconditionally. Passing `cost_cents` on a transition to `cancelled` is allowed at the service layer — the router (FXA-013) may add a validation that `cost_cents` is only accepted alongside `target_status="completed"`, but the service itself does not reject it to keep the layer boundary clean.

### 5.5 State machine definition

```
VALID_TRANSITIONS = {
    "open":        {"in_progress", "cancelled"},
    "in_progress": {"completed", "cancelled"},
    "completed":   set(),   # terminal
    "cancelled":   set(),   # terminal
}
```

Illegal transitions and their HTTP responses:

| `current` | `target` | HTTP |
|---|---|---|
| `completed` | `open` | 409 `illegal_transition` |
| `completed` | `in_progress` | 409 `illegal_transition` |
| `cancelled` | any | 409 `illegal_transition` |
| `open` | `completed` | 409 `illegal_transition` (must go through `in_progress`) |

### 5.6 `_item_to_out` Decimal coercion

DynamoDB returns numeric attributes as `Decimal` instances from the boto3 resource API. `_item_to_out` coerces `created_at` and `updated_at` via `int(item["created_at"])`. Other optional numeric fields (`cost_cents`, `scheduled_for`, `completed_at`) use `int(v) if v is not None else None`. This avoids `ValidationError` from Pydantic when it receives `Decimal` for an `int` field (the same issue addressed for `MessageEncryptionEnvelope` in the codebase, as noted in MEMORY.md).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

`app/services/asset_maintenance.py` contains zero `if S.dev_mode` branches. All DDB I/O uses the same code path against DynamoDB Local (port 8001 in dev, moto in tests) and real DynamoDB (prod). The `encode_cursor` / `decode_cursor` functions in `app/core/cursor.py` handle `Decimal` from both environments via `_json_default` at `app/core/cursor.py:17–18`. <!-- VERIFIED: cursor.py:17–18 -->

### 7.2 Idempotency contract

| Operation | Idempotency mechanism |
|---|---|
| `create_work_order` | Deterministic `work_order_id = sha256(corr)[:32]`; `attribute_not_exists(sk)` conditional put; on `ConditionalCheckFailedException` fetch-and-return existing row |
| `transition_work_order` | `ConditionExpression="wo_status = :current"` on `update_item`; re-calling with the same `target_status` from the same `current` is idempotent at the data level (the transition is a no-op if already applied) but raises `ConditionalCheckFailedException` if the status has already moved — the caller must re-fetch to get the current row |

There is no idempotency key for transitions: transitions are point-in-time state changes, and replaying a transition (e.g. `open → in_progress`) after it has already been applied is logically a `completed → in_progress` attempt (or similar), which is correctly rejected by the state machine. If callers need transition idempotency, they should check the current `wo_status` before calling.

### 7.3 Security

- **Admin-only.** All endpoints in FXA-013 use `require_admin_or_root_csrf` (mutating) or `require_admin_or_root` (reads). Non-admin users receive 403 before any service function is reached. The `asset_maintenance` service itself does not enforce roles — the router layer owns that boundary.
- **CSRF.** Cookie-auth `POST`/`PATCH` requests require `x-csrf-token` matching the session's `csrf_token`. Enforced by `require_admin_or_root_csrf` at `app/auth/policy.py:100–106`. <!-- VERIFIED: policy.py:100–106 --> Bearer-auth requests skip CSRF per the existing `enforce_cookie_csrf` logic at `app/auth/policy.py:71–97`. <!-- VERIFIED: policy.py:71 (enforce_cookie_csrf definition) -->
- **Ownership via asset guard.** `create_work_order` calls `get_asset(actor_sub, asset_id)` which raises 404 if the asset belongs to a different `owner_sub`. This prevents admins from creating work orders against another admin's assets.
- **No PII stored.** Work-order rows contain `assignee_sub` (an opaque Cognito sub, not an email address), `title`, `description` (arbitrary text — callers should avoid embedding PII), and cost/timestamp fields.
- **No money movement.** `cost_cents` is stored as metadata only. No billing path is invoked.
- **Audit trail.** Create and every transition emit a best-effort `audit_event` to `T.alerts`. These events are queryable by admins via the existing audit log infrastructure.

## 10. Open Questions / Assumptions

1. **`create_work_order` asset-ownership scope.** The spec assumes `actor_sub` is used as `owner_sub` when calling `get_asset(actor_sub, asset_id)`. If the asset register is org-scoped (a deferred capability per `docs/ofbiz/specs/FXA-001.md:10.6`), this check would fail for admins who are not the asset owner. The assumption is single-user ownership matching FXA-005 — confirmed acceptable until org-scope is addressed.

2. **`cost_cents` validation on non-completed transitions.** The spec stores `cost_cents` unconditionally when present in `MaintenanceOrderTransitionIn`, even if `target_status` is `"cancelled"`. The assumption is that the router (FXA-013) adds a 422 validation if `cost_cents` is supplied alongside `target_status != "completed"`. If no such router validation is added, `cost_cents` on a cancellation is silently stored — harmless but potentially confusing in reporting.

3. **`assignee_sub` GSI index sparsity.** `GSI_WO_ASSIGNEE` is sparse: rows without `assignee_sub` are not indexed. DynamoDB does not index items where the attribute is absent. Unassigned work orders will not appear in `list_work_orders(assignee_sub=...)` queries, which is the intended behavior. This must be confirmed: if a null `assignee_sub` should appear in an "unassigned queue", the design would require a sentinel value (e.g. `"UNASSIGNED"`) and a separate query mode.

4. **`list_work_orders` with no filter raises 400.** The spec raises HTTP 400 if all three filters (`asset_id`, `wo_status`, `assignee_sub`) are None, rather than performing a full table scan. A full scan is O(N) on the table size and is not provided. This assumption should be confirmed with the team — if a "list all work orders" scan is required, it needs a separate admin-only scan endpoint.

5. **`transition_work_order` `asset_id` source.** The `PATCH /ui/fixed-assets/work-orders/{work_order_id}` route (FXA-013) has `work_order_id` in the path but not `asset_id`. The service function requires `asset_id` to construct the DDB primary key. Two options: (a) embed `asset_id` in the request body of `MaintenanceOrderTransitionIn`, or (b) add a GSI that allows lookup by `work_order_id` alone (currently not present). **RESOLVED (pass 3 / FORWARD_DEP):** `docs/ofbiz/specs/FXA-013.md:§2.7` and `§3.2` confirm option (a): `MaintenanceOrderTransitionIn` carries `asset_id: str = Field(min_length=1, max_length=64)` as a required field, and the PATCH handler passes `body.asset_id` to the service as the `asset_id` argument. Resolves when FXA-004 / FXA-013 build.

6. **`completed_at` set on every completion transition.** If a work order is somehow transitioned to `"completed"` twice (which the conditional put prevents, but which can happen if the conditional fails silently), `completed_at` would be overwritten with a later timestamp. The assumption is that the `ConditionExpression="wo_status = :current"` guard prevents a second `completed` write once the status is already `"completed"` (since `VALID_TRANSITIONS["completed"]` is empty, any re-transition raises 409 before `update_item` is called).

7. **Decimal coercion for `GSI_WO_STATUS` / `GSI_WO_ASSIGNEE` sort key.** DynamoDB Local and moto return `created_at` as `Decimal`. `_item_to_out` converts via `int(item["created_at"])`. This is consistent with the Decimal-handling pattern throughout the billing and messaging service code. Confirmed correct.
