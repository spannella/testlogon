# PUR-003 — Supplier (vendor party) model & CRUD service

## 1. Summary & Goal

PUR-003 delivers `app/services/suppliers.py`: the foundational supplier party record that underpins every downstream purchasing ticket (PUR-004 supplier-product pricing, PUR-006 purchase-order creation, PUR-011 reorder suggestions). The service owns one DynamoDB table (`suppliers`, declared and scaffolded in PUR-002), exposes five mutating functions (`create_supplier`, `update_supplier`, `set_supplier_status`) and two read functions (`get_supplier`, `list_suppliers`), and guards all paths behind the `purchasing_scm_enabled` master flag.

Idempotency is the primary invariant: `create_supplier(user_sub, name)` is a pure function of its arguments — re-calling with the same `(user_sub, name)` pair yields the same `supplier_id` and does not create a duplicate row. Status deactivation is soft: `set_supplier_status("inactive")` excludes the supplier from active list queries but the row persists in full for history. Every mutation emits an audit event via a best-effort `_audit` helper. No new billing mechanism is introduced here; this ticket is purely a party-record service.

## 3. Data Model

The `suppliers` table is a single-table design with one row per supplier (PK=`supplier_id`, SK=`"META"`). There are no sub-rows; all supplier data fits in the one header record. The `GSI_STATUS` index is the only secondary index and drives `list_suppliers`.

### 3.1 `suppliers` DynamoDB table

| Attribute | DDB Type | Notes |
|---|---|---|
| `supplier_id` (PK) | S | `sha256(f"supplier:{user_sub}:{name}")[:32]` |
| `sk` (SK) | S | Always `"META"` |
| `name` | S | Canonical display name; used in the hash for idempotency |
| `status` | S | `"active"` or `"inactive"` |
| `email` | S | Optional; stored as-is (no normalization) |
| `phone` | S | Optional; stored in E.164 format after `normalize_phone()` |
| `address` | M | Optional nested map: `{line1, line2, city, state, postal_code, country}` |
| `default_currency` | S | ISO 4217 string, e.g. `"USD"` |
| `payment_terms_days` | N | Net-days integer (e.g. 30) |
| `created_by` | S | `user_sub` of the admin who called `create_supplier` |
| `created_at` | N | `now_ts()` integer (Unix seconds) |
| `updated_at` | N | `now_ts()` integer; set on every write |

**GSI: `GSI_STATUS`**

| Attribute | Type | Role |
|---|---|---|
| `status` (PK) | S | Partition: `"active"` or `"inactive"` |
| `created_at` (SK) | N | Sort: oldest-first within a status partition |

`attr_types={"created_at": "N"}` is required in `scripts/local-ddb-init.py` (per CLAUDE.md DDB-numeric-GSI gotcha); this is provided by PUR-002's `TableDef` entry. Without it, DynamoDB stores `created_at` as String and `KeyConditionExpression` integer comparisons raise `ValidationException`.

**Key access patterns:**

| Operation | Access pattern |
|---|---|
| `get_supplier(supplier_id)` | `get_item(Key={"supplier_id": sid, "sk": "META"})` |
| `create_supplier` / `update_supplier` / `set_supplier_status` | `put_item` on the primary key |
| `list_suppliers(status=, cursor=, limit=)` | Query `GSI_STATUS`, PK=`status`, paginated with `Limit` + `ExclusiveStartKey` |

## 5. Detailed Behavior & Edge Cases

### 5.1 `create_supplier` — idempotency and `created_at` preservation

The deterministic id `supplier_id = hashlib.sha256(f"supplier:{user_sub}:{name}".encode()).hexdigest()[:32]` means two calls with the same `(user_sub, name)` target the exact same DynamoDB primary key. A plain `put_item` would reset `created_at` on the second call, losing the original creation timestamp.

The correct pattern is a **read-then-conditional-write**:

1. `get_item(Key={"supplier_id": sid, "sk": "META"})` to check if the row already exists.
2. If it does not exist: `put_item` with `created_at = now_ts()` and `status = "active"`.
3. If it already exists: return `_supplier_out(existing_item)` without writing — the supplier's data was already set at creation time, and `create_supplier` is not intended as an update path. (Callers who want to mutate fields use `update_supplier`.)

This approach avoids the race condition introduced by a `ConditionExpression="attribute_not_exists(supplier_id)"` conditional write failing under concurrent creation (which would require the caller to re-read on `ConditionalCheckFailedException`). Because supplier creation is an infrequent admin operation, the extra read is acceptable and simplifies the implementation.

Audit: emit `"supplier.created"` only on the first-write path, not on the idempotent-replay path.

### 5.2 `update_supplier` — field-level partial update

`update_supplier` loads the existing item with `get_item`. If the item does not exist, it raises `HTTPException(404)`. Otherwise it merges only the provided (non-None) fields onto the existing item dict, stamps `updated_at = now_ts()`, and calls `put_item` with the merged item. This is a full-item overwrite (not a DynamoDB `update_item` expression), which is simpler and sufficient because the row fits in a single item. The overwrite is safe because the row's `created_at` and `created_by` are preserved from the loaded item.

Phone normalization: if `phone` is provided and non-empty, call `normalize_phone(phone)` from `app.core.normalize` before storing. If `normalize_phone` raises `ValueError`, surface it as `HTTPException(422, detail="Invalid phone number")`.

### 5.3 `set_supplier_status` — soft deactivation

Valid status values: `"active"` and `"inactive"`. Any other value raises `HTTPException(422, detail="status must be 'active' or 'inactive'")`. The implementation loads the existing item, asserts it exists (else 404), and uses a DynamoDB `update_item` with:

```python
T.suppliers.update_item(
    Key={"supplier_id": supplier_id, "sk": "META"},
    UpdateExpression="SET #status = :s, updated_at = :now",
    ExpressionAttributeNames={"#status": "status"},
    ExpressionAttributeValues={":s": status, ":now": now_ts()},
    ReturnValues="ALL_NEW",
)
```

Using `update_item` (not `put_item`) preserves all other fields atomically and returns the updated item in one round-trip. `ReturnValues="ALL_NEW"` avoids a second `get_item` call.

When `status = "inactive"`: the row's `status` attribute changes to `"inactive"`. Subsequent `list_suppliers(status="active")` queries on `GSI_STATUS` will not return this supplier because the GSI partition key has changed. The row is fully preserved and retrievable via `get_supplier(supplier_id)` (which uses a direct `get_item`, not the GSI).

### 5.4 `list_suppliers` — GSI pagination

The function queries `GSI_STATUS` with `KeyConditionExpression=Key("status").eq(status)`, `ScanIndexForward=True` (ascending `created_at`), and `Limit=limit`. The `cursor` parameter is decoded via `app.core.cursor.decode_cursor(cursor)` to an `ExclusiveStartKey` (or `None` for the first page). The response's `LastEvaluatedKey` is encoded via `app.core.cursor.encode_cursor(lek)` and returned as the next page's `cursor`.

```python
from boto3.dynamodb.conditions import Key
from app.core.cursor import decode_cursor, encode_cursor

def list_suppliers(status: str = "active", *, cursor: Optional[str] = None, limit: int = 50):
    _require_enabled()
    kwargs: Dict[str, Any] = {
        "IndexName": "GSI_STATUS",
        "KeyConditionExpression": Key("status").eq(status),
        "ScanIndexForward": True,
        "Limit": limit,
    }
    lek = decode_cursor(cursor)
    if lek:
        kwargs["ExclusiveStartKey"] = lek
    resp = T.suppliers.query(**kwargs)
    items = [_supplier_out(it) for it in resp.get("Items", [])]
    next_cursor = encode_cursor(resp.get("LastEvaluatedKey"))
    return {"suppliers": items, "cursor": next_cursor}
```

Unlike `inventory.list_low_stock` (which exhausts all pages in a single call), `list_suppliers` returns one page per call to support the paginated admin UI. The `limit` is capped at 200 to prevent runaway reads; values above 200 are silently clamped.

### 5.5 `status` validation gate

The only valid status transitions for `set_supplier_status` are:
- `active → inactive`
- `inactive → active`
- `active → active` (no-op, idempotent)
- `inactive → inactive` (no-op, idempotent)

There is no lifecycle state machine here; both transitions are always legal (no rejection of "already inactive" input). This differs from the PO lifecycle (PUR-006 + PUR-007) which has strict `_VALID_TRANSITIONS`.

### 5.6 Interaction with downstream tickets

- **PUR-004** (`supplier_products.py`): `upsert_supplier_product` calls `get_supplier(supplier_id)` to validate the supplier exists. An `inactive` supplier is still a valid FK target — the inactive status does not block product associations. (Active-supplier enforcement on PO creation is a PUR-006 concern.)
- **PUR-006** (`purchase_orders.py`): `create_purchase_order` calls `get_supplier(supplier_id)` and raises `HTTPException(422)` if the supplier is `inactive`. This check is in PUR-006, not here.
- **PUR-005** (router): Pydantic validation happens in the router layer. The service receives already-validated Python types; it does not validate `email` format or `default_currency` enum (Pydantic handles that).

### 5.7 `name` uniqueness is per-`user_sub`, not global

The hash `sha256(f"supplier:{user_sub}:{name}")` means two different admin users can create a supplier with the same name and they will receive different `supplier_id`s. If global uniqueness of supplier names is desired, that is a PUR-013 UI-layer concern (duplicate-name warning), not a hard DynamoDB constraint. The acceptance criterion only requires idempotency for the same caller, which this design satisfies.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity**: `app/services/suppliers.py` contains zero `dev_mode` branches. The DynamoDB code path is identical in dev (moto-backed local DDB at port 8001, `T.suppliers` bound by PUR-002 via `_safe_table(S.suppliers_table_name)`) and prod (real DynamoDB). There are no mock supplier endpoints; the real service runs in both environments.

**Idempotency**: `create_supplier(user_sub, name)` is deterministically idempotent via sha256. `update_supplier` and `set_supplier_status` are naturally idempotent: re-calling with the same arguments produces the same DDB state. `list_suppliers` is a pure read and inherently idempotent.

**Security — all endpoints are staff-only**: The router (PUR-005) gates all supplier endpoints behind `require_admin_or_root_csrf` from `app/auth/policy.py:100`. This enforces both ADMIN/ROOT role (`:106`) and CSRF for cookie-auth sessions (`:105`). No supplier endpoint is customer-facing. No supplier endpoint is added to `API_KEY_ROUTE_EXEMPTIONS`.

**Input validation**: `name` is validated for length (1–200 chars) by the `SupplierCreateIn` Pydantic model in PUR-005. `payment_terms_days` is validated `ge=0, le=365`. Phone is normalized to E.164 or rejected with 422. `email` is stored as-is (no backend regex validation beyond Pydantic's `Optional[str]`; if strict email validation is needed it can be added via a field validator in the model, which is a PUR-005 concern).

**Supplier id is not secret**: `supplier_id` is a truncated sha256 derived from public inputs. It must not be treated as a capability token. Access control is at the endpoint auth layer, not by obscuring the id.

## 8. Backward Compatibility & Migration

PUR-003 is purely additive. It introduces one new file (`app/services/suppliers.py`) and, via PUR-002, one new DynamoDB table (`suppliers`). No existing file is modified.

**Migration**: The `suppliers` table is created by `scripts/local-ddb-init.py` (added by PUR-002). Running `just restart` recreates the table from scratch in the dev environment. In production, the `suppliers` table is created as an empty new table via an `UpdateTable`-equivalent (new table creation) before enabling `PURCHASING_SCM_ENABLED`. Because the table is new with no existing data, there is no backfill or migration required.

**`GSI_STATUS` with numeric `created_at`**: The `attr_types={"created_at": "N"}` declaration in PUR-002's `TableDef` ensures DynamoDB Local accepts integer `created_at` values as the numeric GSI sort key. All `put_item` calls in PUR-003 write `created_at` as an integer (`now_ts()` returns `int`). No string-vs-number coercion issue arises.

**Forward compatibility with PTY Party Manager**: The `supplier_id` is a stable sha256-derived string. Future PTY tickets can reference `supplier_id` in a `party_roles` table without modifying the `suppliers` table. The `created_by` field stores the admin `user_sub` who created the record, which PTY can later use to associate the supplier party record with the platform user party record.

## 10. Open Questions / Assumptions

1. **Assumption**: PUR-002 is merged and green before PUR-003 starts. `T.suppliers`, `S.purchasing_scm_enabled`, and `S.suppliers_table_name` are all present in the codebase. PUR-003 does not modify `scripts/local-ddb-init.py`, `app/core/tables.py`, or `app/core/settings.py`.

2. **Assumption**: The `suppliers` table PK is `supplier_id` (S) and SK is `sk` (always `"META"` for this ticket). There are no sub-rows in the suppliers table (unlike `purchase_orders` which has `LINE#{n}` rows). This is consistent with the PUR-001 design spec at `docs/ofbiz/specs/PUR-001.md:66–88`.

3. **Assumption**: Idempotency is scoped to `(user_sub, name)`. If two different admin users (e.g. charlie_admin and root) both create `name="Acme"`, they produce different `supplier_id`s. If global uniqueness is required (same name from any user produces the same id), the hash must change to `sha256(f"supplier:global:{name}")`. This decision should be confirmed before PUR-005 ships — the acceptance criteria say "same name twice is idempotent" without specifying the user scope.

4. **Assumption**: `email` is stored as-is. The Pydantic model in PUR-005 may add `EmailStr` validation if desired, but the service layer does not re-validate. The test plan above does not assert email format rejection.

5. **Open question**: Should `update_supplier` be allowed to change `name`? If `name` changes, the hash `sha256(f"supplier:{user_sub}:{name}")` would generate a different `supplier_id` for future creates, but the existing row keeps its old `supplier_id`. This is acceptable (the row itself is not re-keyed), but it means the idempotency guarantee only applies to the `name` value at creation time. Confirmed assumption: `name` is updatable; the hash is used only at creation.

6. **Open question**: What is the behavior when `set_supplier_status("inactive")` is called on a supplier that has open purchase orders in `draft` or `submitted` status (PUR-006)? The current design allows deactivation regardless; PUR-006's `create_purchase_order` will enforce the active-status check at PO creation time. PUR-007's `transition_po` may additionally check supplier status at approval time. This cross-ticket validation policy should be confirmed during PUR-006 design.

7. **Assumption**: The `address` field is an unvalidated `Dict[str, Any]`. A structured `SupplierAddress` Pydantic model (e.g. `{line1, city, state, postal_code, country}`) could be added in PUR-005's models.py additions for stronger typing. The service layer stores and returns whatever dict is provided.

8. **Assumption**: `list_suppliers(status="all")` is not a valid call. The `status` parameter must be `"active"` or `"inactive"`. Listing all suppliers regardless of status requires two calls or a DynamoDB scan, which is not exposed via this API surface. If an admin "all suppliers" view is needed, it is a PUR-005/PUR-013 UI design concern.

9. **Assumption**: `T.suppliers` will exist as a handle in `app/core/tables.py` after PUR-002 is merged. If PUR-003 is developed in a worktree before PUR-002 is merged, a `Tables` dataclass field for `suppliers: Any` must be temporarily present. The worktree setup should depend on the PUR-002 branch.

## 11. Dependencies

- **PUR-001** (`docs/ofbiz/specs/PUR-001.md`) — design spike that established the data model, function signatures, and `supplier_id` hash formula used in this spec. All design decisions in this ticket are grounded in PUR-001.

- **PUR-002** (tables, settings, flag, handles) — **hard blocker**. PUR-003 requires `T.suppliers`, `S.purchasing_scm_enabled`, and `S.suppliers_table_name` to exist in `app/core/tables.py` and `app/core/settings.py` before `app/services/suppliers.py` can import them. The `scripts/local-ddb-init.py` `TableDef` entry for `suppliers` (with `attr_types={"created_at": "N"}`) must be present before `just restart` can create the table.

- **PUR-004** (supplier-product pricing service) — blocked on PUR-003. `upsert_supplier_product` in PUR-004 calls `get_supplier(supplier_id)` to validate the FK. PUR-004 cannot be tested end-to-end until PUR-003 is merged.

- **PUR-005** (Pydantic models + purchasing router) — blocked on PUR-003 and PUR-004. The `POST /ui/purchasing/suppliers` endpoint in PUR-005 calls `suppliers.create_supplier(...)`. The `SupplierOut`, `SupplierCreateIn`, `SupplierPatchIn`, `SupplierListOut`, and `SupplierStatusIn` Pydantic models specified in Section 4.2 of this ticket are physically added to `app/models.py` by PUR-005, not PUR-003 (the service returns raw dicts; the router wraps them).

- **`app/services/alerts.audit_event`** — runtime dependency of `_audit`. The function is available unconditionally; the lazy import pattern (matching `inventory.py:92`) prevents circular-import issues and ensures the service can be imported in test contexts where the alerts module may not be fully initialized.

- No dependency on billing (`billing_shared.py`), inventory (`inventory.py`), or orders. PUR-003 is a pure party-record service with no money movement.
