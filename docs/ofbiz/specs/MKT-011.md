# MKT-011 — Marketing campaign router (registered in main.py)

## 1. Summary & Goal

MKT-011 creates `app/routers/marketing_campaigns.py` — the HTTP surface that exposes every service function built by MKT-004 through MKT-010 as FastAPI endpoints. It registers two routers in `app/main.py`: a user-facing `router` (prefix `/ui/marketing`, tags `["marketing"]`) and an admin-only `admin_router` (prefix `/ui/admin/marketing`, tags `["marketing-admin"]`). It also registers a third, prefix-free public router exposing one no-auth redirect endpoint.

The file's sole job is routing: it validates ownership, translates service exceptions into HTTP status codes, and enforces the `S.marketing_campaigns_enabled` feature flag as a 404/403 guard on every mutating endpoint. No business logic is duplicated here — all logic lives in the service modules assembled by earlier MKT tickets.

After this ticket, `GET /openapi.json` lists all marketing campaign endpoints, and the MKT-012 frontend wrappers and MKT-013 UI page can be built against a stable HTTP contract.

### 4.2 Flag gate helper

```python
def _require_enabled() -> None:
    """Raise 404 when the marketing campaigns module is disabled.
    Called on every mutating endpoint. GET endpoints skip this check."""
    if not S.marketing_campaigns_enabled:
        raise HTTPException(status_code=404, detail="Marketing campaigns are not enabled")
```

Pattern matches `app/routers/promo_codes.py:40–43`.

### 4.3 Ownership helper

```python
def _require_campaign_owner(campaign_id: str, user_sub: str) -> dict:
    """Return the campaign item or raise 404 (never 403, to prevent enumeration)."""
    from app.services.marketing_campaigns import get_campaign_by_id
    item = get_campaign_by_id(campaign_id)           # GSI lookup by campaign_id alone
    if not item or item.get("owner_id") != user_sub:
        raise HTTPException(status_code=404, detail="Campaign not found")
    return item
```

`get_campaign_by_id(campaign_id)` performs a GSI query on `ByOwnerCreatedAt` or, if not provided, a `scan`-free lookup via a secondary index — the exact implementation is specified in MKT-004/MKT-011 coordination. The router never accesses `T.marketing_campaigns` directly.

### 4.8 Public visit endpoint (`public_router`, no prefix)

```python
@public_router.get("/ui/marketing/t/{code}")
async def tracking_visit_redirect(code: str, request: Request):
    """
    Public endpoint: record a tracking-code visit and redirect to storefront.
    No auth required — the tracking code slug is the only credential.
    Pattern: app/routers/shoppingcart.py:268–282 (cart recover redirect, decorator at line 268).
    """
```

**Behavior:**
1. Look up tracking code via `get_tracking_code(code)`.
2. If code not found or `status != "active"`: redirect to `/` (302) without recording.
3. Extract `ip_address = request.client.host if request.client else "0.0.0.0"` and `user_agent = request.headers.get("user-agent", "")` (pattern from `app/routers/affiliate_links.py:244–245`).
4. Call `record_visit(code, ip_address=ip_address, user_agent=user_agent, party_id=None)` — fire-and-forget; exceptions are swallowed to never break the redirect.
5. Return `RedirectResponse(url=redirect_url, status_code=302)` where `redirect_url = tracking_item.get("redirect_url") or "/"`.

The flag gate does NOT apply here — even with the module off, a pre-existing tracking link embedded in an email should still redirect cleanly. The `record_visit` call is skipped when the module flag is off to avoid phantom data.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off behavior per method type

| Operation type | Flag off behavior |
|---|---|
| `POST /campaigns` (create) | `_require_enabled()` → 404 |
| `GET /campaigns` (list) | Returns empty list or existing data — no gate |
| `GET /campaigns/{id}` (read) | Returns existing data — no gate |
| `PATCH /campaigns/{id}` (update) | `_require_enabled()` → 404 |
| `POST /campaigns/{id}/transition` | `_require_enabled()` → 404 |
| `POST /campaigns/{id}/send` | `_require_enabled()` → 404 |
| `GET /campaigns/{id}/attribution` | Returns existing data — no gate |
| All list/segment/tracking create/mutate | `_require_enabled()` → 404 |
| All list/segment/tracking GET | No gate |
| `GET /ui/marketing/t/{code}` | Redirect proceeds; `record_visit` skipped |
| Admin `GET /campaigns/pending` | Returns existing data; admin route has no flag gate |
| Admin `POST /campaigns/{id}/review` | No flag gate — admin can approve/reject existing pending campaigns even if module is off (avoids stuck queue) |

### 5.2 `POST /campaigns` idempotency

`create_campaign` in the service layer (MKT-004) uses a deterministic id: `campaign_id = sha256(owner_id + "|" + name + "|" + created_bucket)[:24]`. The DDB write uses `ConditionExpression="attribute_not_exists(pk)"`. On conflict (duplicate within the same hour bucket), the service returns the existing item. The router returns **200** (not 201) when the returned item was pre-existing — the service communicates this via a `"created": bool` field on the return dict. If `result["created"] is True` → `status_code=201`; else `200`.

### 5.3 Ownership enforcement on contact lists and segments

The router calls service functions passing `owner_id = ctx["user_sub"]`. The service layer enforces `PK=OWNER#{owner_id}` key access, so a mismatched `owner_id` returns `None` from a `get_item` → service raises `HTTPException(404)`. The router does not add a second ownership layer; it relies entirely on the service's DDB access pattern.

### 5.4 `POST /campaigns/{id}/send` → 202

`send_campaign` (MKT-009) may process O(thousands) of recipients. The endpoint returns `202 Accepted` immediately with `{"ok": true, "campaign_id": ..., "queued": true}`. The actual send is synchronous in the current implementation (no background task queue): `send_campaign` is called directly in the handler and may take several seconds for large lists. This is acceptable for MVP and matches the existing `audit_export_worker` pattern of synchronous processing in dev. A future async background task can be added without changing the HTTP contract (202 is already the right code).

### 5.5 `POST /segments/{id}/evaluate` → live count

`evaluate_segment` returns a `{"count": int, "sample": list[str]}` (first 20 matching `party_id` values for UI preview). The router passes through the service result verbatim. No auth scope beyond ownership is required — the segment evaluator reads profile/subscription/order tables but returns only counts and anonymized ids.

### 5.6 `POST /campaigns/{id}/transition` error mapping

```
CampaignTransitionError  → HTTP 409 Conflict
CampaignActivationError  → HTTP 422 Unprocessable Entity
                           body: {"detail": {"code": exc.code, "message": str(exc)}}
HTTPException(404)       → pass through (campaign not found)
HTTPException(403)       → pass through (flag disabled, reached only if _require_enabled bypassed)
```

Pattern from `docs/ofbiz/specs/MKT-006.md:437–451`.

### 5.7 Admin review creates an audit trail

`review_campaign_endpoint` sets `actor_sub = user.sub` (the admin's sub). The `transition_campaign` service call emits `audit_event("marketing_campaign.reviewed", actor_sub, ...)` via `app.services.alerts.audit_event` (best-effort; `audit_event` is defined at `app/services/alerts.py:644`). Note: `app/services/ad_campaigns.py` does not use `audit_event` — the earlier citation was incorrect.

### 5.8 Public visit endpoint — no DDB write on unknown code

If `get_tracking_code(code)` returns `None`, the handler redirects to `/` without any DDB write. This prevents an unauthenticated caller from creating phantom rows by hitting `/ui/marketing/t/<random>`.

### 5.9 `GET /lists/{list_id}/members` pagination

Returns `{"members": [...], "cursor": str | null, "count": int}`. The router accepts an optional `?cursor=` query param and `?limit=` (default 50, max 200), forwarding to `list_members(list_id, owner_id, cursor, limit)`. Cursor encoding follows `app/core/cursor.py` — base64 of the DynamoDB `LastEvaluatedKey`.

### 5.10 `DELETE /lists/{list_id}/members/{party_id}` idempotency

Deleting a non-existent member is a no-op (not 404). The service performs a conditional delete that silently succeeds if the item is already absent. The router returns `{"ok": true}` in either case.

## 6. Feature Flag & Config

The feature flag and all table-name settings are added by MKT-002 (`docs/ofbiz/specs/MKT-002.md`). No new settings are introduced by MKT-011 itself.

### Flag

```python
# app/core/settings.py (added by MKT-002)
marketing_campaigns_enabled: bool = os.environ.get(
    "MARKETING_CAMPAIGNS_ENABLED", "0"
) not in ("0", "false", "False")
```

Environment variable: `MARKETING_CAMPAIGNS_ENABLED`. Default: **off** (`"0"`). Pattern from `app/core/settings.py:821` (`cart_reminders_enabled`), but with `"0"` default instead of `"1"`.

### Impact of flag = False

- All `_require_enabled()` calls return 404. The endpoints exist in the OpenAPI schema (they are registered unconditionally) but every mutating call is silently refused.
- `GET` endpoints return whatever data was written before the flag was turned off. This is intentional: an admin can read existing campaign data even while the module is disabled.
- The public redirect `GET /ui/marketing/t/{code}` still redirects but skips `record_visit`. Pre-existing tracking links in emails remain functional redirects.
- Existing `app/routers/ads.py`, `app/routers/promo_codes.py`, `app/services/cart_reminders.py`, and all billing routes are unaffected. The flag is read only in `marketing_campaigns.py` (router) and the service functions in `app/services/marketing_campaigns.py`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

The router contains no `if S.dev_mode` branches. All DDB reads/writes go through `T.*` table handles which resolve against DynamoDB Local (`DDB_ENDPOINT_URL=http://localhost:8001`) in dev and real DynamoDB in prod — identical code path, different endpoint. The tracking-code redirect and the alert/email sends in `send_campaign` are already SECOPS-007 compliant in their respective service modules (MKT-009 uses `send_alert_email` which branches on `S.dev_mode` internally; the router is unaware of this).

### Idempotency

- **Campaign create**: deterministic id + `ConditionExpression="attribute_not_exists(pk)"` at the service layer (MKT-004). Router returns 200 vs 201 based on `result["created"]`.
- **Campaign send**: `send_id = sha256(campaign_id + "\x00" + str(snapshot_ts) + "\x00" + party_id)[:24]` dedup write on `T.marketing_send_log` (MKT-009). Replay of the same snapshot delivers nothing new.
- **Tracking-code order attribution**: `record_order(code, order_id)` uses `ConditionExpression="attribute_not_exists(pk)"` keyed on `ORDER#{order_id}` (MKT-010). Idempotent per `order_id`.
- **Member add**: `add_member(list_id, party_id)` is a no-op on duplicate insert (MKT-007).

### Security

- **Foreign-owner access**: all read/mutate endpoints that take a resource id enforce ownership by passing `owner_id = ctx["user_sub"]` to the service. The service's DDB key access pattern (`PK=OWNER#{owner_id}`) physically prevents cross-owner reads. The router returns 404 (not 403) on ownership failure to prevent enumeration — this matches the account-level helper `_require_account_owner` at `app/routers/ads.py:60–64`, which raises 404 on ownership mismatch. Note: the campaign-level helper `_require_campaign_owner` in ads.py raises 403 for foreign-owner (`app/routers/ads.py:83`) — MKT-011 deliberately uses the stricter 404-only posture.
- **Admin review bypass**: admin endpoints use `require_admin_or_root` (not `require_ui_session`), so `user.sub` is the admin's own sub. The `transition_campaign` service call on behalf of an admin supplies the *campaign owner's* sub (from the existing item) as `owner_id`, not the admin's sub — preventing a privilege escalation where an admin accidentally writes under their own namespace.
- **CSRF**: all non-GET endpoints using cookie auth require the `x-csrf-token` header enforced by `require_ui_session` (CLAUDE.md auth dependency section). The public visit endpoint has no session, so CSRF is not applicable.
- **Public visit endpoint**: the only unauthenticated write surface is `record_visit`, which appends a VISIT row. This row carries no PII beyond the IP/UA already logged by standard request middleware. Rate limiting is acceptable as a future hardening step; it is not required for MVP.
- **No money writes**: the router never calls `app.services.billing_shared.new_ledger_entry` or any payment API. Attribution is read-only. Campaign-linked promo redemptions still flow through `promo_codes.redeem_promo_code` — unchanged.

## 8. Backward Compatibility & Migration

### No breaking changes

All changes are additive:
- New router file `app/routers/marketing_campaigns.py` — new file, no existing files modified.
- Three `include_router` calls added to `app/main.py` — existing routes are unaffected.
- With `MARKETING_CAMPAIGNS_ENABLED=0` (the default), the new endpoints return 404/403 on mutation; existing ads, promo, cart-reminders, and billing code paths are byte-for-byte unchanged.
- `GET /openapi.json` gains new paths but no existing paths are altered.

### DynamoDB

No schema changes to existing tables. The four new tables (`MarketingCampaigns`, `ContactLists`, `PartySegments`, `TrackingCodes`) and the send-log table (`MarketingCampaignSendLog`) are created by MKT-002/MKT-009 via `just restart`. Existing DynamoDB Local data is unaffected.

### Migration checklist (prod deploy)

1. Run `scripts/local-ddb-init.py` additions (MKT-002) to create the five new tables in prod DynamoDB before deploying backend code. Tables with no rows are safe to create at any time.
2. Deploy backend with `MARKETING_CAMPAIGNS_ENABLED=0` (default). All new endpoints exist in the schema but return 404 on mutation.
3. Enable the flag via `MARKETING_CAMPAIGNS_ENABLED=1` once the frontend (MKT-013) is deployed.

## 10. Open Questions / Assumptions

1. **`get_campaign_by_id` signature**: This spec assumes MKT-004/011 coordination produces a service function that resolves a campaign by `campaign_id` alone (without `owner_id`), using the `ByOwnerCreatedAt` GSI or a dedicated `ByCampaignId` GSI. If MKT-004 only provides `get_campaign(owner_id, campaign_id)`, the router's `_require_campaign_owner` must perform a GSI scan by `campaign_id`. The ads router resolves this at `app/routers/ads.py:67–84` via `T.ad_campaigns.query(IndexName="ByCampaignId", ...)` — the same approach is applicable here. The preferred resolution is to add a `ByCampaignId` GSI to `MarketingCampaigns` (analogous to `AdCampaigns`), but this requires a MKT-002 amendment. Assumption: MKT-002 already includes this GSI (based on MKT-001's note about mirroring the ads model).

2. **`POST /campaigns/{id}/send` — synchronous or async**: This spec recommends 202 Accepted with synchronous execution (MVP). If send latency becomes a problem for large lists, a background asyncio task (mirroring `start_audit_export_worker_task`) can be added. This is recorded as a future improvement.

3. **`CampaignReviewIn` model ownership**: The spec assumes `CampaignReviewIn` is defined in `app/models.py` by MKT-003. If MKT-003 does not include it, MKT-011 defines it inline: `class CampaignReviewIn(BaseModel): decision: str; notes: str = ""`.

4. **`ad_account_id` in marketing campaign item**: `compute_attribution` in MKT-005 requires both `ad_account_id` and `ad_campaign_id` to call `get_campaign(account_id, campaign_id)` (the ads service API requires both). This spec assumes MKT-004/005 store `ad_account_id` on the marketing campaign row when `attach_ad_campaign` is called. If not, attribution will always show `ad_spend_cents=0` for linked ads campaigns.

5. **Admin review — flag gate**: This spec makes admin review endpoints NOT gated on the feature flag, so admins can process existing pending campaigns even if the module is disabled. This is a deliberate policy choice, not an oversight.

6. **`status_code` on idempotent create (200 vs 201)**: FastAPI requires declaring `status_code` at the decorator level. For the idempotent-create case (existing item returned), returning 200 from a `@router.post(..., status_code=201)` endpoint requires returning a `Response` with explicit `status_code`. The implementation uses `JSONResponse(content=result, status_code=200 if not result["created"] else 201)`. This is acceptable but slightly non-standard; an alternative is to always return 201 (RFC 7231 permits 201 for idempotent creates that return the existing resource).

7. **Rate limiting on `GET /ui/marketing/t/{code}`**: The public visit endpoint is unauthenticated. For MVP no rate limit is applied. A future ticket should add per-IP rate limiting (using the existing DDB-backed `_bucket_limit` in `app/services/rate_limit.py`).
