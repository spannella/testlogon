# HRM-006 — Employment-period service (hire / terminate / list)

**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days
**Milestone:** 2 — Employee & Position Service Core

---

## 1. Summary & Goal

HRM-006 delivers the **employment lifecycle service layer** in `app/services/hr.py`: the ability to hire a party into a position (`create_employment`), terminate that employment (`terminate_employment`), retrieve a single record (`get_employment`), and list records by either employee or status (`list_employments`), plus a utility setter (`set_employment_status`).

The ticket has three explicit side-effects that must be atomic in intent but tolerant in failure:

1. **Party-graph mirror** — on create, a `PartyRelationship` of type `EMPLOYMENT` is written to `T.party` via `party.create_relationship(...)` (PTY-006) so the employment is discoverable from both the HR single-table and the party graph without duplicating identity data.
2. **Position status update** — on hire, the referenced position is transitioned to `FILLED` via `update_position_status` (HRM-005); on terminate, it is transitioned back to `OPEN` (configurable). Both are best-effort: a failure never blocks the employment write.
3. **Audit trail** — `audit_event` calls are emitted for `employment.created` and `employment.terminated` via `app.services.alerts.audit_event` (`app/services/alerts.py:644`).

Everything is additive and flag-gated: with `S.hr_enabled = False` (the default, set by HRM-001) every `/ui/hr/*` endpoint returns 404 and zero service code runs. Existing billing, cart, orders, shop, and party surfaces are byte-for-byte unchanged.

### 2.3 HR single-table GSI layout — HRM-002's deliverable

From `docs/ofbiz/specs/HRM-002.md §3.1` and `HR_TICKETS.md:35-38`:

- **GSI1** (`GSI1PK` S / `GSI1SK` S) — entity-type/status lookup. For employment rows: `GSI1PK = "EMPLOYMENT#{status}"`, `GSI1SK = "EMPLOYMENT#{employment_id}"`. Queries by exact employment status without a scan.
- **GSI2** (`GSI2PK` S / `GSI2SK` S) — party reverse-lookup. For employment rows: `GSI2PK = "PARTY#{party_id}"`, `GSI2SK = "EMPLOYMENT#{employment_id}"`. Resolves all of an employee's employment history.
- **GSI_CREATED** (`entity_type` S / `created_at` N) — newest-first listing across all statuses. The numeric `created_at` sort key requires `attr_types={"created_at": "N"}` in the `TableDef` to prevent `ValidationException` (CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha; confirmed pattern at `scripts/local-ddb-init.py:84`).

`start_date` and `end_date` are stored as numeric epoch seconds. They are **not** used as GSI sort keys in HRM-006 (only `created_at` and `GSI1SK`/`GSI2SK` are), so no additional `attr_types` entries are required beyond what HRM-002 already declares. They are stored as `N` attributes by virtue of being Python `int` values written by boto3.

## 3. Data Model

HRM-006 introduces no new DynamoDB tables or GSIs — all are defined in HRM-002. This section documents the exact item shapes written and read.

### 3.1 Employment META item

Stored at `PK=EMPLOYMENT#{employment_id}` / `SK=META`.

| Attribute | DynamoDB type | Value |
|---|---|---|
| `PK` | S | `"EMPLOYMENT#{employment_id}"` |
| `SK` | S | `"META"` |
| `employment_id` | S | `"EMP_{sha256_hex_32}"` (deterministic) or `"EMP_{uuid4_hex}"` (random) |
| `party_id` | S | Employee's PERSON party id (from PTY-004 / HRM-004) |
| `position_id` | S | Position id (from HRM-005) |
| `org_party_id` | S | Org's PARTY_GROUP party id |
| `status` | S | `"ACTIVE"`, `"TERMINATED"`, or `"ON_LEAVE"` |
| `start_date` | N | Epoch seconds (integer); provided by caller |
| `end_date` | N (optional) | Epoch seconds (integer); absent when status is `ACTIVE`/`ON_LEAVE` |
| `pay_rate_cents` | N | Positive integer; e.g. `500000` for $5,000/month |
| `pay_period` | S | `"MONTHLY"`, `"BIWEEKLY"`, `"WEEKLY"`, or `"HOURLY"` |
| `currency` | S | ISO 4217 lower-case; default `"usd"` |
| `created_at` | N | `now_ts()` at creation — GSI_CREATED sort key |
| `updated_at` | N | `now_ts()` at last mutation |
| `GSI1PK` | S | `"EMPLOYMENT#{status}"` — updated atomically on every status change |
| `GSI1SK` | S | `"EMPLOYMENT#{employment_id}"` — stable; enables cursor pagination on GSI1 |
| `GSI2PK` | S | `"PARTY#{party_id}"` — stable; employee reverse-lookup partition |
| `GSI2SK` | S | `"EMPLOYMENT#{employment_id}"` — stable; employee reverse-lookup sort key |
| `entity_type` | S | `"EMPLOYMENT"` — GSI_CREATED partition key |
| `correlation_id` | S (optional) | Stored for auditability; absent when no `correlation_id` was supplied |
| `termination_reason` | S (optional) | Free text; written only on `TERMINATED` transition |

**Why `GSI1SK = "EMPLOYMENT#{employment_id}"`:** The ticket specifies `GSI1PK=EMPLOYMENT#{status}` and the GSI design in HRM-002 states `GSI1SK` as the sort key for this index. Using the string-prefixed `employment_id` (stable, unique) enables cursor-safe pagination on the status index. The `GSI_CREATED` index (`entity_type` / `created_at`) serves newest-first listing separately.

**Why `start_date` and `end_date` are not used as GSI sort keys here:** These fields are stored as numbers but are not declared as GSI sort keys in the `hr` table definition (they are data attributes, not index keys). The `attr_types={"created_at": "N"}` declaration by HRM-002 handles the one numeric GSI sort key (`GSI_CREATED`). No additional `attr_types` entries are needed for HRM-006.

### 3.2 GSI access patterns

| Query | Index | KeyConditionExpression |
|---|---|---|
| All employments for a party | GSI2 | `GSI2PK = "PARTY#{party_id}"` |
| All active employments | GSI1 | `GSI1PK = "EMPLOYMENT#ACTIVE"` |
| All terminated employments | GSI1 | `GSI1PK = "EMPLOYMENT#TERMINATED"` |
| Newest-first (all statuses) | GSI_CREATED | `entity_type = "EMPLOYMENT"`, `ScanIndexForward=False` |
| Single record | primary | `PK = "EMPLOYMENT#{id}"`, `SK = "META"` |

### 3.3 Party-graph mirror item

Written to `T.party` by `party.create_relationship(...)` (PTY-006), NOT by HRM-006 directly:

- Primary: `PK=PARTY#{party_id}` / `SK=REL#EMPLOYMENT#{org_party_id}`
- Mirror GSI3: `GSI3PK=REL_TO#{org_party_id}` / `GSI3SK=REL#EMPLOYMENT#{party_id}`

HRM-006's responsibility is only to call `party.create_relationship(...)` — the item layout is owned by PTY-006.

#### `create_employment`

```python
def create_employment(
    party_id: str,
    position_id: str,
    org_party_id: str,
    pay_rate_cents: int,
    pay_period: str,
    start_date: int,
    *,
    currency: str = "usd",
    actor_sub: str,
    correlation_id: Optional[str] = None,
) -> Dict[str, Any]:
```

**Behaviour:**

1. Validate `pay_rate_cents > 0` and `pay_period in {"MONTHLY","BIWEEKLY","WEEKLY","HOURLY"}`; raise `ValueError` on failure (router maps to 422).
2. Derive `employment_id`:
   - If `correlation_id` is supplied: `employment_id = "EMP_" + hashlib.sha256(correlation_id.encode("utf-8")).hexdigest()[:32]`.
   - Otherwise: `employment_id = "EMP_" + uuid.uuid4().hex`.
3. `ts = now_ts()`.
4. Build full DDB item (all attributes from §3.1; `status="ACTIVE"`, `end_date` absent, `entity_type="EMPLOYMENT"`).
5. Write with idempotency guard:
   ```python
   try:
       T.hr.put_item(Item=item, ConditionExpression="attribute_not_exists(PK)")
   except ClientError as e:
       if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
           return get_employment(employment_id)  # idempotent replay
       raise
   ```
6. **Party-graph mirror** (best-effort):
   ```python
   try:
       from app.services import party as _p
       _p.create_relationship(
           from_party_id=party_id,
           to_party_id=org_party_id,
           relationship_type="EMPLOYMENT",
           correlation_id=employment_id,
       )
   except Exception:
       pass  # never blocks employment write
   ```
7. **Position flip to FILLED** (best-effort):
   ```python
   try:
       update_position_status(position_id, "FILLED", actor_sub=actor_sub)
   except Exception:
       pass  # never blocks employment write
   ```
8. Emit audit event:
   ```python
   try:
       audit_event("employment.created", actor_sub,
                   employment_id=employment_id, party_id=party_id,
                   position_id=position_id, org_party_id=org_party_id)
   except Exception:
       pass
   ```
9. Return the item dict.

**Returns:** `Dict[str, Any]` matching the `Employment` schema.

#### `terminate_employment`

```python
def terminate_employment(
    employment_id: str,
    end_date: int,
    *,
    actor_sub: str,
    reason: Optional[str] = None,
) -> Dict[str, Any]:
```

**Behaviour:**

1. Fetch item via `get_employment(employment_id)`. If `None`, raise `LookupError("employment_not_found")` (router maps to 404).
2. **Idempotency guard:** if `item["status"] == "TERMINATED"`, return item immediately (no-op replay — CLAUDE.md specifies "re-terminate is a no-op").
3. Validate `end_date >= item["start_date"]`; raise `ValueError("end_date_before_start_date")` if not (router maps to 422).
4. `ts = now_ts()`.
5. Write status update atomically:
   ```python
   update_expr = (
       "SET #status = :status, end_date = :end_date, "
       "updated_at = :ts, GSI1PK = :gsi1pk"
   )
   if reason:
       update_expr += ", termination_reason = :reason"
   T.hr.update_item(
       Key={"PK": f"EMPLOYMENT#{employment_id}", "SK": "META"},
       UpdateExpression=update_expr,
       ExpressionAttributeNames={"#status": "status"},
       ExpressionAttributeValues={
           ":status": "TERMINATED",
           ":end_date": end_date,
           ":ts": ts,
           ":gsi1pk": "EMPLOYMENT#TERMINATED",
           **({":reason": reason} if reason else {}),
       },
   )
   ```
   The `GSI1PK` must be updated in the same write to keep the status index consistent (no stale reads between two separate writes).
6. **Position revert** (best-effort, gated on `S.hr_position_revert_on_terminate`):
   ```python
   if S.hr_position_revert_on_terminate:
       try:
           revert_status = getattr(S, "hr_position_revert_status", "OPEN")
           update_position_status(item["position_id"], revert_status, actor_sub=actor_sub)
       except Exception:
           pass
   ```
7. Emit audit event best-effort: `audit_event("employment.terminated", actor_sub, employment_id=employment_id, end_date=end_date, reason=reason)`.
8. Return the updated item via `get_employment(employment_id)`.

**Returns:** Updated `Dict[str, Any]` matching the `Employment` schema.

#### `list_employments`

```python
def list_employments(
    *,
    party_id: Optional[str] = None,
    status: Optional[str] = None,
    cursor: Optional[str] = None,
    limit: int = 50,

```

**Contract:** exactly one of `party_id` or `status` should be provided by the caller. If both are `None`, the function falls back to the GSI_CREATED newest-first scan. If both are provided, `party_id` takes precedence (GSI2 result is then client-filtered; the router should reject this combination).

**Behaviour — `party_id` path (GSI2):**
```python
kwargs = {
    "IndexName": "GSI2",
    "KeyConditionExpression": Key("GSI2PK").eq(f"PARTY#{party_id}"),
    "Limit": limit,
}
if cursor:
    kwargs["ExclusiveStartKey"] = decode_cursor(cursor)
resp = T.hr.query(**kwargs)
```

**Behaviour — `status` path (GSI1):**
```python
kwargs = {
    "IndexName": "GSI1",
    "KeyConditionExpression": Key("GSI1PK").eq(f"EMPLOYMENT#{status}"),
    "Limit": limit,
}
if cursor:
    kwargs["ExclusiveStartKey"] = decode_cursor(cursor)
resp = T.hr.query(**kwargs)
```

**Behaviour — unfiltered path (GSI_CREATED):**
```python
kwargs = {
    "IndexName": "GSI_CREATED",
    "KeyConditionExpression": Key("entity_type").eq("EMPLOYMENT"),

    kwargs["ExclusiveStartKey"] = decode_cursor(cursor)
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Create — idempotent replay

When `correlation_id` is supplied and a `ConditionalCheckFailedException` is raised, `create_employment` fetches and returns the existing item. The returned item may have status `TERMINATED` if the employment was subsequently terminated — callers should not assume the replayed record is `ACTIVE`.

### 5.2 Terminate — already-terminated idempotency

If `item["status"] == "TERMINATED"`, `terminate_employment` returns immediately without re-running any side-effects (no redundant `update_position_status`, no duplicate audit event). This is the specified idempotent replay contract from `HR_TICKETS.md:126`.

### 5.3 Terminate — `end_date < start_date` rejection

`end_date >= start_date` is validated at both the Pydantic model layer (HRM-003) and inside `terminate_employment` (defence-in-depth). The service raises `ValueError("end_date_before_start_date")`; the router maps this to HTTP 422.

### 5.4 Position flip — best-effort only

Both the hire-side `FILLED` flip and the terminate-side revert are wrapped in `try/except Exception: pass`. A position that does not exist, is already `CLOSED`, or whose transition is invalid will silently fail without preventing the employment write. This matches the ticket spec: "best-effort, flag-gated; never blocks the employment write" (`HR_TICKETS.md:125`).

### 5.5 Party-graph mirror — best-effort only

`party.create_relationship(...)` failure is silently swallowed. The employment record in `T.hr` is the authoritative source of truth; the party graph mirror is a secondary index that may lag or be absent if PTY-006 is not yet deployed or fails. Callers of `list_relationships` on the party graph should not assume an employment relationship is always present.

### 5.6 `list_employments` with both `party_id` and `status`

If both `party_id` and `status` are supplied, the function uses the `party_id` GSI2 path and does **not** additionally filter by status. The router (HRM-009) should reject this with HTTP 400 (`"only one of party_id or status may be specified"`). The service itself does not enforce this to keep the service layer simple.

### 5.7 `list_employments` — DynamoDB FilterExpression gotcha

None of the three list paths use `FilterExpression` — all filtering is done via GSI key conditions. This avoids the CLAUDE.md "DDB FilterExpression doesn't reduce page size" gotcha where DynamoDB fetches up to 1 MB before applying the filter, silently returning fewer items than `Limit`.

### 5.8 `set_employment_status` — no transition validation

`set_employment_status` does not enforce allowed status transitions. It is an admin/root escape hatch for corrections and `ON_LEAVE` transitions. Transition validation (if required later) is a separate concern.

### 5.9 Concurrent create with same `correlation_id`

Two concurrent creates with identical `correlation_id` will race on `put_item`. One will succeed; the other will catch `ConditionalCheckFailedException` and return the winner's item. Both callers get back the same record.

### 5.10 `end_date` on create

`create_employment` does not accept an `end_date`. Employments are created in `ACTIVE` status with no end date. This aligns with the `CreateEmploymentIn` model (HRM-003) which does not include `end_date`.

Default `True` (enabled): when an employment is terminated, the linked position is reverted to `OPEN` so it can be re-filled. Operators may set `HR_POSITION_REVERT_ON_TERMINATE=0` to suppress this behaviour (e.g. when the position is being eliminated along with the termination).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 dev/prod parity

All DynamoDB reads and writes go through `T.hr` (HRM-002) and `T.party` (PTY-002). Both handles resolve to real DynamoDB Local in dev and real AWS DynamoDB in prod. There is no `S.dev_mode` branch in the service layer for employment operations — the same code path runs in both environments. This is the explicit requirement of SECOPS-007 as applied throughout the project (confirmed: every service referenced in CLAUDE.md "Common Gotchas" uses a single code path gated only by the feature flag, not `dev_mode`).

### 7.2 Deterministic-id idempotency

The `sha256(correlation_id)[:32]` employment id derivation mirrors `app/services/commerce_order_service.py:67`. A `put_item` with `ConditionExpression="attribute_not_exists(PK)"` enforces single-write semantics. Concurrent duplicate creates are safe (one wins, both callers get the same record).

### 7.3 Party-graph write ordering

The HR table write (step 5 in `create_employment`) is the primary authoritative write. The party-graph mirror (step 6) is best-effort and happens after. If the process crashes between steps 5 and 6, the HR record exists but the party graph mirror does not — a repair job can replay `create_relationship` using `employment_id` as `correlation_id` to deduplicate. This is acceptable given the party graph is a secondary index, not the system of record.

### 7.4 CSRF enforcement

All non-GET employment endpoints use `require_admin_or_root_csrf` (defined in `app/auth/policy.py:100`), which calls `enforce_cookie_csrf(request)` before the role check. Bearer-token clients (no session cookie) bypass CSRF per the existing project convention (CLAUDE.md "Bearer-auth requests bypass CSRF").

### 7.5 Role boundary

Employment data is admin/root-only. No `USER`-role endpoint exposes employment records. The `party_id` stored on an employment item is an opaque party identifier, not a `user_sub` — preventing direct user identity leakage.

### 7.6 Sensitive data

`pay_rate_cents` is stored in plaintext DynamoDB. This is consistent with how the project stores all financial data (see `billing_shared.py` ledger entries). If encryption at rest is required, it is a KMS-layer concern configured at the DynamoDB table level, not in the service code.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact when flag is off

With `S.hr_enabled = False` (the default), the router (HRM-009) returns 404 for every `/ui/hr/*` path before any service code runs. The `hr` table may not exist at all — `T.hr` is a lazy handle and only raises `ResourceNotFoundException` on actual DDB calls, which never happen when the flag is off. Existing billing, cart, orders, shop, contacts, and party surfaces are byte-for-byte unchanged.

### 8.2 `hr` table creation

The `hr` table is created by `scripts/local-ddb-init.py` (HRM-002). `just restart` recreates it. In production, the table must be created via `CreateTable` before `HR_ENABLED=1` is set. The safe deployment order is:

1. Deploy code with `HR_ENABLED=0` (default).
2. Run `CreateTable` for the `hr` table in the target region.
3. Wait for `ACTIVE` table status.
4. Set `HR_ENABLED=1` in environment.

### 8.3 No existing data migration

HRM-006 is a net-new feature. There are no existing employment records to migrate.

### 8.4 Party graph migration

If PTY-006 was deployed before HRM-006 and party-graph mirrors were written by another path, `create_relationship` with the same `(from_party_id, to_party_id, relationship_type)` key must be idempotent (PTY-006 spec: "Deterministic-id idempotency on the relationship key prevents duplicate edges", `PARTY_CRM_TICKETS.md:123`). HRM-006 passes `correlation_id=employment_id` to ensure deduplication.

## 10. Open Questions / Assumptions

1. **`app/services/party.py` exists when HRM-006 is implemented.** This spec assumes PTY-006 (party relationship service) has been implemented and `party.create_relationship(...)` is importable. If PTY-006 is deferred, the `create_relationship` call must be guarded by a flag check: `if S.party_crm_enabled: try: _p.create_relationship(...) except: pass`.

2. **`start_date` is caller-supplied as an integer epoch.** The spec assumes callers pass a Unix epoch integer (consistent with `now_ts()` returning `int`). If callers pass ISO 8601 strings, the service needs a coercion step; HRM-003's `Employment` model should validate this.

3. **Position reversion on terminate defaults to `OPEN`, not `CLOSED`.** The ticket says "back to `OPEN`/`CLOSED` policy on terminate" without specifying which. This spec defaults to `OPEN` so the position can be re-filled. If the business policy is to close positions on termination, `S.hr_position_revert_status` should be added as a settings key.

4. **`GSI1SK = "EMPLOYMENT#{employment_id}"` for employment items.** The HRM-002 ticket specifies `GSI1PK = "EMPLOYMENT#{status}"` but does not explicitly state `GSI1SK`. By analogy with positions (`GSI1SK = "POSITION#{position_id}"`, `HR_TICKETS.md:103`) and the GSI description ("entity-type/status lookup"), this spec uses `"EMPLOYMENT#{employment_id}"` as `GSI1SK` for consistency and cursor stability.

5. **`set_employment_status` has no transition validation.** This is intentional as a flexible admin escape hatch. If transition guards are required (e.g. cannot go from `TERMINATED` back to `ACTIVE`), they should be specified in a follow-up ticket.

6. **`pay_rate_cents` and `pay_period` are immutable after create.** The ticket does not specify an update path for compensation changes. This spec treats compensation as immutable on the employment record; compensation changes would be modelled as a terminate + re-hire or a separate amendment record (out of scope for HRM-006).

7. **`org_party_id` is not validated against `T.party`.** This spec does not verify that `org_party_id` corresponds to an existing `PARTY_GROUP` party. Adding this validation requires a `T.party.get_item` call and couples HRM-006 more tightly to PTY-004; it is assumed to be a precondition enforced by the UI/caller.
