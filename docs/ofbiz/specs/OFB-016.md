# OFB-016 — Financial statements (trial balance, P&L, balance sheet)

## 1. Summary & Goal

OFB-016 builds three accounting statement generators over the double-entry GL
populated by OFB-014:

- **Trial balance** — debits equal credits across all posted GL accounts for any
  date range. An out-of-balance result is surfaced as a hard error (never
  silently rendered).
- **Income statement (P&L)** — revenue minus expense for a configurable period,
  derived from OFB-013's revenue and expense account classes.
- **Balance sheet** — assets equal liabilities plus equity as-of any date,
  derived from OFB-013's asset, liability, and equity account classes. The
  balance-sheet equation must hold exactly; any imbalance is reported as an
  error, not suppressed.

In addition, the income-statement revenue figure is cross-checked against the
existing platform financial dashboard GMV/net-revenue numbers
(`app/services/platform_financial_dashboard.py`), and any variance beyond a
configurable tolerance is flagged in the response.

The feature is additive and gated behind `GL_STATEMENTS_ENABLED` (default
`false`). With the flag off, every existing billing, shop, cart, order, and
refund path is byte-for-byte unchanged. With the flag on, the statement
generators are pure read-only views over `T.gl_journal` and `T.gl_accounts` —
they never write to those tables or to `T.billing`.

## 2. Context & Current State

### 2.1 GL journal table (OFB-014)

`app/services/gl_posting.py` (OFB-014) writes two item shapes to `T.gl_journal`:

**Header** — `PK = "JE#GLOBAL"`, `SK = "JE#{journal_entry_id}"` — carries
`source_entry_id`, `ledger_date` (YYYY-MM-DD), `posted_at` (N), `entry_type`,
`total_amount_cents`, and `state = "posted"`. See
`docs/ofbiz/specs/OFB-014.md:112–130`.

**Line** — `PK = "JE#GLOBAL"`, `SK = "JL#{journal_entry_id}#{seq:04d}"` —
carries `account_code`, `account_name`, `side` (`"debit"` | `"credit"`), and
`amount_cents` (always positive; sign encoded in `side`). See
`docs/ofbiz/specs/OFB-014.md:131–142`.

Two GSIs on `T.gl_journal` (declared in `scripts/local-ddb-init.py` by
OFB-014):

| GSI name | PK | SK (type) | Purpose |
|---|---|---|---|
| `ENTRIES_BY_DATE` | `ledger_date` (S) | `posted_at` (N) | Per-day entry enumeration for statements |
| `SOURCE_ENTRY_IDX` | `source_entry_id` (S) | `posted_at` (N) | Idempotency guard in gl_posting.py |

The `attr_types={"posted_at": "N"}` declaration in `scripts/local-ddb-init.py`
is required to prevent `ValidationException` when querying numeric sort keys
(CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha).

### 2.2 Chart of accounts (OFB-013)

`app/services/gl_accounts.py` (OFB-013) maintains account records in
`T.gl_accounts` keyed by `account_code` / `sk = "META"`. Each account carries
`account_class` (`"asset"`, `"liability"`, `"equity"`, `"revenue"`,
`"expense"`), `normal_balance` (`"debit"` | `"credit"`), and `is_active`.

The default seeded accounts (`docs/ofbiz/specs/OFB-013.md:195–210`) are:

| Code | Name | Class | Normal balance |
|------|------|-------|----------------|
| `1000` | Cash / Bank | asset | debit |
| `1200` | Accounts Receivable | asset | debit |
| `2000` | Accounts Payable | liability | credit |
| `2100` | Sales Tax Payable | liability | credit |
| `4000` | Sales Revenue | revenue | credit |
| `4900` | Refunds / Returns | revenue (contra) | debit |
| `5100` | Processor Fees | expense | debit |

Note: OFB-013 (`docs/ofbiz/specs/OFB-013.md:195`) and OFB-014
(`docs/ofbiz/specs/OFB-014.md:67–79`) use the **same** codes: `1000`, `1200`,
`2000`, `2100`, `4000`, `4900`, `5100`. OFB-014's `ACCOUNT_MAPPING`
(`OFB-014.md:241–265`) maps all entry types to these codes (previously a
discrepancy existed in a draft of OFB-014 but was corrected there; both specs
now agree — see OFB-014 verification log items 26–30).

## 3. Data Model

### 3.1 No new DynamoDB tables

OFB-016 introduces **no new DynamoDB tables**. All statements are computed
on-demand by reading `T.gl_journal` (via `ENTRIES_BY_DATE` GSI) and
`T.gl_accounts` (via GSI_CLASS). Materialized statement snapshots are not stored
in this ticket; historical retrieval is deferred to OFB-017 or a future caching
layer.

Rationale: the `T.gl_journal` data volume at OFB-016 rollout will be modest
(backfill from existing ledger rows). In-memory aggregation over one day's
journal entries is O(100–10 000) items and sub-second. Caching can be added
later without schema changes once load patterns are understood.


### 3.3 `app/core/tables.py` additions

OFB-013 and OFB-014 add `T.gl_accounts` and `T.gl_journal`. OFB-016 reads both
handles. No new fields on `Tables` are needed for this ticket.

### 3.4 Logical data shapes (in-memory only)

The service builds these shapes in memory and returns them via Pydantic models:

**Account balance** (one per active account, aggregated from journal lines):

```
account_code  str
account_name  str
account_class str   # "asset" | "liability" | "equity" | "revenue" | "expense"
normal_balance str  # "debit" | "credit"
debit_cents   int   # sum of all debit lines for this account in the period
credit_cents  int   # sum of all credit lines for this account in the period
net_cents     int   # debit_cents - credit_cents (positive = net debit balance)
```

**Trial balance row** (account_code + net balance, signed for normal side):

```
account_code  str
account_name  str
account_class str
debit_cents   int   # shown in debit column when net_balance is debit-normal
credit_cents  int   # shown in credit column when net_balance is credit-normal
```

The trial balance totals its debit column and credit column; if they differ the
service raises `GLTrialBalanceError` (never returns a silently unbalanced result).

## 4. API / Service Design

### 4.1 Service: `app/services/gl_statements.py`

```python
"""GL financial statements service (OFB-016, Milestone 4).

Additive, flag-gated (GL_STATEMENTS_ENABLED, default OFF). All public
functions call _require_enabled() first. SECOPS-007: no dev_mode branches;
same DDB path in dev (moto) and prod. Read-only: never writes to T.gl_journal
or T.gl_accounts.

Dependencies:
  T.gl_journal  — OFB-014: journal entry headers + lines
  T.gl_accounts — OFB-013: chart of accounts (account class, normal balance)
"""

from __future__ import annotations

import hashlib
import logging
from datetime import datetime, timezone
from decimal import Decimal
from typing import Any, Dict, List, Optional

from boto3.dynamodb.conditions import Key

from app.core.settings import S
from app.core.tables import T
from app.core.time import now_ts

logger = logging.getLogger(__name__)


class GLTrialBalanceError(Exception):
    """Raised when Σ(debit totals) ≠ Σ(credit totals) across all accounts.

    Never caught within gl_statements.py — must propagate to callers so the
    imbalance is surfaced as an explicit error, not a silently wrong statement.
    """


class GLBalanceSheetError(Exception):
    """Raised when Assets ≠ Liabilities + Equity as-of the requested date.

    Same propagation rule as GLTrialBalanceError.
    """


def _require_enabled() -> None:
    """Raise HTTPException(404) when GL_STATEMENTS_ENABLED=false."""
    from fastapi import HTTPException
    if not S.gl_statements_enabled:
        raise HTTPException(
            status_code=404,
            detail={"code": "feature_disabled", "message": "GL statements are disabled"},
        )


def _to_int(v: Any) -> int:
    if v is None:
        return 0
    if isinstance(v, Decimal):
        return int(v)
    try:
        return int(v)
    except (TypeError, ValueError):
        return 0


# ---------------------------------------------------------------------------
# Journal line aggregation
# ---------------------------------------------------------------------------

def _query_journal_lines_for_date_range(
    start_date: str,
    end_date: str,
) -> List[Dict[str, Any]]:
    """Query T.gl_journal ENTRIES_BY_DATE GSI for all items in [start_date, end_date].

    Queries each day in the range independently (same per-day pagination
    pattern as platform_financial_dashboard._query_ledger_by_date at
    app/services/platform_financial_dashboard.py:136–158 ✓, adapted to query
    T.gl_journal ENTRIES_BY_DATE GSI instead of T.billing GSI_LEDGER_DATE).

    Returns the raw DDB items — both JE# headers and JL# lines. Callers
    filter by SK prefix.
    """
    from app.services.platform_financial_dashboard import _date_range
    dates = _date_range(start_date, end_date)
    out: List[Dict[str, Any]] = []
    for date_str in dates:
        kwargs: Dict[str, Any] = {
            "IndexName": "ENTRIES_BY_DATE",
            "KeyConditionExpression": Key("ledger_date").eq(date_str),
        }
        while True:
            resp = T.gl_journal.query(**kwargs)
            out.extend(resp.get("Items", []))
            lek = resp.get("LastEvaluatedKey")
            if not lek:
                break
            kwargs["ExclusiveStartKey"] = lek
    return out


def _aggregate_account_balances(
    items: List[Dict[str, Any]],
) -> Dict[str, Dict[str, Any]]:
    """Sum debit and credit amounts per account_code from JL# line items.

    Returns a dict keyed by account_code:
    {
        "account_code": str,
        "debit_cents": int,
        "credit_cents": int,
    }

    Items that are JE# headers (SK starts with "JE#") are skipped; only
    JL# line items (SK starts with "JL#") contribute.
    """
    balances: Dict[str, Dict[str, Any]] = {}
    for item in items:
        sk = str(item.get("SK") or item.get("sk") or "")
        if not sk.startswith("JL#"):
            continue
        code = str(item.get("account_code") or "")
        if not code:
            continue
        bucket = balances.setdefault(code, {
            "account_code": code,
            "account_name": str(item.get("account_name") or ""),
            "debit_cents": 0,
            "credit_cents": 0,
        })
        side = str(item.get("side") or "")
        amount = _to_int(item.get("amount_cents"))
        if side == "debit":
            bucket["debit_cents"] += amount
        elif side == "credit":
            bucket["credit_cents"] += amount
    return balances


def _fetch_account_metadata(
    account_codes: List[str],
) -> Dict[str, Dict[str, Any]]:
    """Batch-fetch account class and normal_balance from T.gl_accounts.

    Uses individual get_item calls (point reads, O(1) per account). The CoA
    is bounded to O(100) accounts so this is acceptable without batching.
    Returns a dict keyed by account_code.
    """
    meta: Dict[str, Dict[str, Any]] = {}
    for code in account_codes:
        resp = T.gl_accounts.get_item(Key={"account_code": code, "sk": "META"})
        item = resp.get("Item")
        if item:
            meta[code] = {
                "account_class": str(item.get("account_class") or "unknown"),
                "normal_balance": str(item.get("normal_balance") or "debit"),
                "account_name": str(item.get("name") or ""),
            }
    return meta

# Trial balance
# ---------------------------------------------------------------------------

def compute_trial_balance(
    start_date: str,
    end_date: str,
) -> Dict[str, Any]:
    """Compute trial balance for the period [start_date, end_date].

    Algorithm:
    1. Query T.gl_journal ENTRIES_BY_DATE GSI for all dates in range.
    2. Sum debit/credit per account_code from JL# line items.
    3. Fetch account metadata (class, normal_balance) from T.gl_accounts.
    4. For each account, determine the balance-column presentation:
       - Debit-normal account (asset, expense): net_debit = debit - credit;
         positive net goes in Debit column, negative (overcredited) in Credit.
       - Credit-normal account (liability, equity, revenue): net_credit =
         credit - debit; positive net in Credit, negative in Debit.
    5. Sum all Debit column entries and all Credit column entries.
    6. If total_debit_cents ≠ total_credit_cents, raise GLTrialBalanceError
       with the amounts. NEVER return a silently unbalanced trial balance.

    Returns:
    {
        "period": {"start_date": str, "end_date": str},
        "rows": [TrialBalanceRowOut],
        "total_debit_cents": int,
        "total_credit_cents": int,
        "balanced": True,   # always True (error raised if False)
        "computed_at": int,
    }
    """


def _tb_row(
    code: str,
    name: str,
    account_class: str,
    normal_balance: str,
    debit_cents: int,
    credit_cents: int,
) -> Dict[str, Any]:
    """Build a single trial-balance row with the correct debit/credit column
    presentation for the account's normal balance side.

    Debit-normal (asset, expense):
        net = debit_cents - credit_cents
        tb_debit  = max(net, 0)
        tb_credit = max(-net, 0)

    Credit-normal (liability, equity, revenue):
        net = credit_cents - debit_cents
        tb_debit  = max(-net, 0)
        tb_credit = max(net, 0)
    """


# ---------------------------------------------------------------------------
# Income statement (P&L)
# ---------------------------------------------------------------------------

def compute_income_statement(
    start_date: str,
    end_date: str,
) -> Dict[str, Any]:
    """Compute income statement for the period [start_date, end_date].

    Revenue accounts (account_class="revenue") contribute their net credit
    balance. Expense accounts (account_class="expense") contribute their net
    debit balance. Contra-revenue (e.g. Refunds/Returns, account 4900 which
    is technically class "revenue" with debit normal_balance) reduces the
    revenue total via its net debit balance.

    income = Σ(revenue_account net_credit) - Σ(expense_account net_debit)

    Dashboard reconciliation:
    - Calls platform_financial_dashboard.get_kpis(start_date, end_date).
    - Compares net_revenue_cents (dashboard) to gl_revenue_cents (GL-derived).
    - variance_cents = gl_revenue_cents - dashboard_net_revenue_cents
    - variance_bps = abs(variance_cents) / max(gl_revenue_cents, 1) * 10000
    - reconciled = variance_bps <= S.gl_statements_reconcile_tolerance_bps
    - If not reconciled, the response includes a non-null reconciliation_warning.

    Returns:
    {
        "period": {"start_date": str, "end_date": str},
        "revenue_rows": [IncomeStatementRowOut],   # revenue accounts
        "expense_rows": [IncomeStatementRowOut],   # expense accounts
        "total_revenue_cents": int,
        "total_expense_cents": int,
        "net_income_cents": int,       # revenue - expense
        "dashboard_net_revenue_cents": int,   # from get_kpis()
        "reconciliation_variance_cents": int,
        "reconciliation_variance_bps": int,
        "reconciled": bool,
        "reconciliation_warning": Optional[str],  # None when reconciled
        "computed_at": int,
    }
    """


def _classify_revenue_expense(
    account_balances: Dict[str, Dict[str, Any]],
    account_meta: Dict[str, Dict[str, Any]],
) -> tuple[List[Dict[str, Any]], List[Dict[str, Any]]]:
    """Split aggregated account balances into revenue rows and expense rows.

    Revenue: account_class == "revenue" — net contribution = credit_cents - debit_cents
    Expense: account_class == "expense" — net contribution = debit_cents - credit_cents
    Non-revenue/expense accounts (asset, liability, equity) are excluded.
    """


# ---------------------------------------------------------------------------
# Balance sheet
# ---------------------------------------------------------------------------

def compute_balance_sheet(as_of_date: str) -> Dict[str, Any]:
    """Compute balance sheet as-of the end of as_of_date.

    "As-of a date" means: query all journal entries from the earliest available
    ledger_date up to and including as_of_date. The earliest date is derived
    by querying T.gl_journal ENTRIES_BY_DATE for the minimum ledger_date present.
    If no entries exist yet, returns a zero balance sheet with balanced=True
    (zero assets = zero liabilities + zero equity).

    Equation: total_asset_cents == total_liability_cents + total_equity_cents
    If the equation does not hold, raise GLBalanceSheetError.

    Retained earnings: net_income accumulated from all posted revenue and expense
    entries up to as_of_date is included in equity as "Retained Earnings" (a
    synthetic account, not stored in T.gl_accounts — it is computed, not posted
    directly). This is the standard double-entry balance-sheet closure: the
    income-statement net income is the bridge between the P&L and the balance
    sheet's equity section.

    Returns:
    {
        "as_of_date": str,
        "asset_rows": [BalanceSheetRowOut],
        "liability_rows": [BalanceSheetRowOut],
        "equity_rows": [BalanceSheetRowOut],       # includes Retained Earnings
        "total_asset_cents": int,
        "total_liability_cents": int,
        "total_equity_cents": int,
        "retained_earnings_cents": int,            # net income component
        "balanced": True,    # always True (error raised if False)
        "computed_at": int,
    }
    """


def _earliest_posted_date() -> Optional[str]:
    """Scan T.gl_journal ENTRIES_BY_DATE for the lexicographically smallest
    ledger_date. Uses a single query per a known set of plausible start years,
    or a fallback scan with Limit=1 on the GSI ordered by ledger_date (S) /
    posted_at (N). Returns None when T.gl_journal is empty."""


# ---------------------------------------------------------------------------
# Public entry points
# ---------------------------------------------------------------------------

def get_trial_balance(start_date: str, end_date: str) -> Dict[str, Any]:
    _require_enabled()
    return compute_trial_balance(start_date, end_date)


def get_income_statement(start_date: str, end_date: str) -> Dict[str, Any]:
    _require_enabled()
    return compute_income_statement(start_date, end_date)


def get_balance_sheet(as_of_date: str) -> Dict[str, Any]:
    _require_enabled()
    return compute_balance_sheet(as_of_date)
```

### 4.3 Router: `app/routers/gl_statements.py`

Mounted at prefix `/ui/admin/gl/statements`, registered in `app/main.py`.
All endpoints call the service's `_require_enabled()` indirectly (the service
functions do it internally). Auth is `require_admin_or_root` for reads
(consistent with `/ui/admin/financial-dashboard/*` at
`app/routers/platform_financial_dashboard.py:68`).

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| `GET` | `/ui/admin/gl/statements/trial-balance` | `require_admin_or_root` | Trial balance for a period |
| `GET` | `/ui/admin/gl/statements/income-statement` | `require_admin_or_root` | P&L for a period |
| `GET` | `/ui/admin/gl/statements/balance-sheet` | `require_admin_or_root` | Balance sheet as-of a date |

Query parameters:
- Trial balance and income statement: `start_date: str` (YYYY-MM-DD),
  `end_date: str` (YYYY-MM-DD). Both required.
- Balance sheet: `as_of_date: str` (YYYY-MM-DD). Required.

Error responses:
- `404` when `GL_STATEMENTS_ENABLED=false` (feature disabled).
- `422` for invalid date format or `start_date > end_date`.
- `409 {"code": "trial_balance_unbalanced", ...}` when
  `GLTrialBalanceError` is raised. Includes `total_debit_cents` and
  `total_credit_cents` in the error body.
- `409 {"code": "balance_sheet_unbalanced", ...}` when
  `GLBalanceSheetError` is raised. Includes `total_asset_cents`,
  `total_liability_cents`, `total_equity_cents`.
- `503 {"code": "gl_not_ready"}` when `T.gl_journal` exists but has no
  entries for the requested period (empty table, OFB-014 not yet run).

## 5. Detailed Behavior & Edge Cases

### 5.1 Trial balance out-of-balance is a hard error

When `Σ(debit column) ≠ Σ(credit column)`, `compute_trial_balance` raises
`GLTrialBalanceError(f"unbalanced: debit={D}, credit={C}")` before returning
any result. The router catches this and returns HTTP 409:

```json
{
  "code": "trial_balance_unbalanced",
  "message": "Trial balance does not balance",
  "total_debit_cents": D,
  "total_credit_cents": C,
  "variance_cents": D - C
}
```

This invariant should be impossible if OFB-014's posting engine is correct
(it validates each journal entry before writing). An unbalanced trial balance
signals either a bug in OFB-014 or manual DynamoDB mutation; surfacing it as
an error enables immediate investigation.

### 5.2 Balance-sheet equation enforcement

`compute_balance_sheet` computes:
- `total_asset_cents` = sum of net debit balances across all asset accounts.
- `total_liability_cents` = sum of net credit balances across all liability accounts.
- `retained_earnings_cents` = `total_revenue_cents - total_expense_cents` (computed
  inline from revenue and expense accounts for the period from inception to
  `as_of_date`).
- `total_equity_cents` = sum of net credit balances across equity accounts +
  `retained_earnings_cents`.

If `total_asset_cents ≠ total_liability_cents + total_equity_cents`, raises
`GLBalanceSheetError`. This is a hard contract — the balance sheet is never
returned in an unbalanced state.

### 5.3 Contra-revenue (account 4900: Refunds / Returns)

Account `4900` is tagged with `account_class = "revenue"` in OFB-013 but its
`normal_balance = "debit"` (it is contra-revenue — a debit-normal revenue
account). The income statement handles this correctly:

- For any revenue account where `normal_balance = "debit"`: its contribution
  to total revenue is its net debit balance (positive debits _reduce_ revenue).
- `total_revenue_cents = Σ(credit-normal revenue net_credit) - Σ(debit-normal revenue net_debit)`

This ensures refunds and returns correctly reduce the income statement's revenue
line without requiring a separate treatment.

### 5.4 Dashboard revenue reconciliation

The income statement calls `platform_financial_dashboard.get_kpis(
start_date=start_date, end_date=end_date)` (keyword-only; `platform_financial_dashboard.py:367` ✓)
to obtain `dashboard_net_revenue_cents`. The reconciliation:

```
variance_cents = gl_revenue_cents - dashboard_net_revenue_cents
variance_bps = abs(variance_cents) * 10000 // max(gl_revenue_cents, 1)
reconciled = variance_bps <= S.gl_statements_reconcile_tolerance_bps  # default 50 bps
```

If `not reconciled`:
```
reconciliation_warning = (
    f"GL revenue ({gl_revenue_cents} cents) differs from platform dashboard "
    f"({dashboard_net_revenue_cents} cents) by {variance_cents} cents "
    f"({variance_bps} bps). This may indicate an incomplete OFB-014 backfill "
    f"or a mapping gap in gl_posting.ACCOUNT_MAPPING."
)
```

The warning is informational only — it does not block the endpoint or cause
a non-200 response. The response's `reconciled` field allows callers to
programmatically detect the discrepancy.

The dashboard query and the GL query cover the same `[start_date, end_date]`
window. They will inevitably disagree during an OFB-014 partial-backfill
window. Setting `GL_STATEMENTS_RECONCILE_TOLERANCE_BPS=10000` disables the
warning entirely.

Note: `get_kpis` has a keyword-only signature: `get_kpis(*, start_date, end_date)`
(`platform_financial_dashboard.py:367` ✓). Callers must use keyword arguments.

### 5.5 Empty GL journal (OFB-014 not yet run)

When `T.gl_journal` has no entries for the requested period, all account
balances are zero. The trial balance has `total_debit_cents = 0` and
`total_credit_cents = 0` — this is technically balanced (0 == 0) and is
returned with `balanced: true`. The income statement returns all zeros with
`reconciliation_warning` explaining the discrepancy with the dashboard. The
balance sheet returns all zeros and is balanced (0 == 0 + 0).

This ensures the service degrades gracefully before OFB-014 has run.

### 5.6 Earliest-date computation for balance sheet

The balance sheet needs all journal entries from the beginning of time through
`as_of_date`. Since `T.gl_journal`'s `ENTRIES_BY_DATE` GSI uses `ledger_date`
as the partition key, there is no efficient single query for "all entries before
date X". The approach is:

1. `_earliest_posted_date()` scans by querying each year-prefix (`"2024"`,
   `"2025"`, etc.) via `Key("ledger_date").begins_with(year)` in the GSI,
   sorted ascending on `posted_at`, with `Limit=1` to find the minimum date
   per year. The earliest non-None result is the inception date.
2. `compute_balance_sheet` then calls `_query_journal_lines_for_date_range(
   inception_date, as_of_date)` to accumulate all lines.

As an alternative: if `as_of_date` is today or in the future, using the
platform_financial_dashboard date range from the first-ever rollup date (stored
in `T.financial_rollups`) could seed the inception date without a journal scan.
This optimisation is flagged in Section 10.

### 5.7 Date validation

Both endpoints validate `start_date`/`end_date`/`as_of_date` are valid
YYYY-MM-DD strings and that `start_date <= end_date`. The validation uses
the same `_parse_date` helper from
`app/services/platform_financial_dashboard.py:86` ✓ rather than duplicating
it. An `as_of_date` in the future is accepted (returns a balance sheet with
whatever is posted up to the current day, since no future entries exist).

### 5.8 Account metadata fallback

If `T.gl_accounts.get_item` returns no item for an account code that appears in
the journal (e.g. OFB-013 was not fully seeded), the service falls back to:
- `account_class = "unknown"` — the account does not appear in any statement
  section but is listed as an "unclassified" row in the trial balance with its
  raw debit/credit totals.
- A `WARN: unclassified_account code=<x>` log entry.

This prevents a missing account from causing a `KeyError` or skipping amounts
silently.

### 5.9 Line-item ordering

- Trial balance rows: sorted by `account_code` alphabetically (numeric codes
  sort by string lexicography: "1000" < "1200" < ... < "5100").
- Income statement revenue rows: descending by `amount_cents` (largest revenue
  account first).
- Income statement expense rows: descending by `amount_cents`.
- Balance sheet sections: each sorted by `account_code`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

`gl_statements.py` contains no `if S.dev_mode` branches. All DDB reads go
through `T.gl_journal` and `T.gl_accounts` regardless of environment. The
moto-backed DDB in dev is populated with the same schema and GSIs as
production. Statements computed in dev against seeded test data will produce
identical output to prod for identical inputs. This follows the established
pattern in `inventory.py` and `gl_accounts.py` (OFB-013 spec).

### Idempotency

All three statement endpoints are pure read operations. They are fully
idempotent — repeated calls with the same parameters produce the same
result (deterministic aggregation over immutable posted journal entries).

### Security

- All statement endpoints require `require_admin_or_root` (ADMIN or ROOT).
  Financial statements are platform-internal aggregate data; end users never
  see them.
- The income-statement response includes
  `dashboard_net_revenue_cents` derived from
  `platform_financial_dashboard.get_kpis()`. That function (`platform_financial_dashboard.py:367`)
  queries the same billing ledger that the admin dashboard reads — no new
  data exposure.
- No PII is present in GL journal lines (`account_code`, `amount_cents`,
  `side` only). The `source_pk` field on the journal header (which
  contains `USER#{sub}`) is deliberately excluded from the statement output
  (Pydantic models omit it).
- `GLTrialBalanceError` and `GLBalanceSheetError` are raised before any
  response is written, so a caller never receives partial data alongside an
  error condition.
- Audit events are emitted for each statement computation via
  `_audit("gl_statement_computed", user.sub, statement_type=..., period=...)`.
  These are best-effort (wrapped in `try/except`, never block the response).

### Balance invariant contracts

The trial balance and balance sheet invariants are enforced in the service
layer, not the router. This means they apply whether the service is called
from the router, a background task, or a test. This separation ensures that
future callers (e.g. OFB-018 test suite) cannot accidentally bypass the
invariant check.

## 10. Open Questions / Assumptions

1. **~~Account code discrepancy between OFB-013 and OFB-014 specs~~ — RESOLVED**:
   Both OFB-013 (`OFB-013.md:195–210` ✓) and OFB-014 (`OFB-014.md:67–79` ✓)
   use the same account codes: `1000`, `1200`, `2000`, `2100`, `4000`, `4900`,
   `5100`. OFB-014's `ACCOUNT_MAPPING` (`OFB-014.md:241–265`) was corrected in a
   prior verification pass (items 26–30 in OFB-014's verification log) to use
   these codes exclusively. No discrepancy exists. Any future extension (e.g.
   adding a `4500` platform-commission account to OFB-013) would require
   updating `ACCOUNT_MAPPING` in OFB-014 to match.

2. **Assumption: No Equity posting accounts exist today**: The default chart
   (OFB-013) has no equity account. The balance sheet's equity section will
   consist entirely of `retained_earnings_cents` (synthetic, computed as revenue
   minus expense). If OFB-013 is extended to include an Owner's Equity or
   Capital account, the balance sheet logic must be updated to sum those
   accounts' credit balances into `total_equity_cents`. Validate with the
   OFB-013 owner.

3. **Assumption: `_earliest_posted_date()` year-prefix scan is sufficient**:
   Querying `ENTRIES_BY_DATE` with a year-prefix (`begins_with("2024")`) per year
   is workable for a platform that has been running since 2024. If journal entries
   exist from years earlier than 2024, the earliest-date scan will miss them. An
   alternative is to store the inception date in a metadata row in `T.gl_journal`
   (e.g. `PK="METADATA"`, `SK="INCEPTION_DATE"`) written by OFB-014's backfill
   command. This is cleaner and should be proposed to the OFB-014 implementer.

4. **Open question: Should the balance sheet cover all-time or a specified
   inception date?**: The spec computes the balance sheet from inception
   (earliest journal entry) to `as_of_date`. An alternative design is to accept
   `from_date` and `as_of_date` parameters (a "period balance sheet"), which is
   non-standard but useful for comparing balance sheets at two points in time.
   The standard accounting balance sheet is a cumulative all-time snapshot;
   this spec follows the standard.

5. **Assumption: `get_kpis` returns the right revenue figure for reconciliation**:
   `platform_financial_dashboard.get_kpis()` returns `net_revenue_cents` based on
   `REVENUE_ENTRY_TYPES = {"platform_commission", "platform_ad_commission",
   "ad_revenue_credit"}` (`platform_financial_dashboard.py:45–51`). The GL income
   statement derives revenue from all `account_class = "revenue"` accounts (codes
   `4000`, `4900` and any others). These two sets are not identical (the dashboard
   counts only commission/ad revenue; the GL counts all revenue entries). The
   reconciliation therefore compares semantically different quantities. The correct
   comparison is GL `total_revenue_cents` vs dashboard `gmv_cents - refunds_cents`
   (gross merchandise value net of refunds), not `net_revenue_cents`. This design
   question must be resolved before implementing the reconciliation logic.

6. **Assumption: `GL_STATEMENTS_ENABLED` is a separate flag from
   `GL_DOUBLE_ENTRY_ENABLED`**: This allows deploying the statement endpoints
   independently of the posting engine. The statements degrade gracefully when
   the journal is empty (returns all-zero, balanced). If a combined flag is
   preferred, the reconciliation tolerance setting becomes moot since the
   dashboard will always diverge from a zero GL.

7. **Assumption: Statement computation is not cached**: For the initial
   implementation, all three statements are computed on demand from raw journal
   entries. For large date ranges (e.g. a full-year P&L over hundreds of
   thousands of journal lines), this could be slow. OFB-017 (or a future
   performance ticket) can add a `gl_statement_cache` table. The service API
   is designed to make this addition transparent (the public functions in
   `gl_statements.py` are the sole entry points; caching can be layered inside
   them).

8. **Assumption: Multi-currency is out of scope**: All amounts are in cents of
   a single currency (USD). The `currency` field on `T.billing.BALANCE` rows
   defaults to `"usd"` (via `apply_balance_delta`/`apply_wallet_delta` at
   `billing_shared.py:83, 127, 185` ✓). If multi-currency support is
   needed, the GL statement service would need to group by currency before
   aggregating.
