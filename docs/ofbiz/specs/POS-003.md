# POS-003 — POS DynamoDB tables, settings & feature flag

## 1. Summary & Goal

POS-003 is the infrastructure scaffolding ticket for the Point-of-Sale module. It
delivers exactly three concrete changes:

1. A new `TableDef` entry in `scripts/local-ddb-init.py` that creates the `pos`
   single-table store with PK `pos_pk` / SK `pos_sk` and three GSIs (all with
   numeric sort keys declared in `attr_types`).
2. Three settings keys in `app/core/settings.py`: `pos_table_name` (table name),
   `pos_enabled` (master flag, default **off**), and `pos_cash_drawer_required`
   (drawer-present check, default **off**).
3. A `pos: Any` field on the `Tables` frozen dataclass in `app/core/tables.py`
   and the corresponding `_safe_table(S.pos_table_name)` initialiser in the
   singleton `T`.

No router, no service logic, and no Pydantic model changes land in this ticket —
those are POS-004/POS-005/POS-002 respectively. With `POS_ENABLED=false` (the
default), the entire POS surface remains unreachable and zero bytes of the
existing shop/cart/orders/billing stack are modified.

## 3. Data Model

### 3.1 Single-table design

The `pos` table uses a generic `pos_pk` / `pos_sk` primary key rather than
domain-specific names, following the single-table pattern used by `catalog`
(`PK`/`SK`) and `file_manager` (`PK`/`SK`). This lets all POS entity types coexist
in one table with row-type discrimination encoded in the key prefix.

**Table:** `pos` (default name; overridable via `POS_TABLE_NAME` env var)
**PK:** `pos_pk` (S)
**SK:** `pos_sk` (S)

### 3.2 Row types and key shapes

| Row type | `pos_pk` | `pos_sk` | Notes |
|---|---|---|---|
| Register config | `REGISTER#{register_id}` | `META` | One row per physical terminal |
| Session header | `SESSION#{session_id}` | `META` | Till open/close lifecycle |
| Tender sub-row | `SESSION#{session_id}` | `TENDER#{txn_id}` | Cash-float-accountable tender record |
| Transaction header | `TXN#{txn_id}` | `META` | Cart+order wrapper for one sale |

These shapes are specified in POS-002 (`docs/ofbiz/specs/POS-002.md`, sections
3.1–3.4) and are reproduced here for completeness. POS-003 does not write any of
these rows — it only provisions the table that will hold them.

### 3.3 GSI definitions

All three GSIs use `ProjectionType: ALL` (the framework default in
`_global_secondary_indexes()` at `scripts/local-ddb-init.py:2516`; the
`"ProjectionType": "ALL"` literal is at `:2528`).

#### GSI_REGISTER_OPEN

Answers: "Is there an open session for register `R`? Return the most recently
opened one."

| | Key |
|---|---|
| Partition key | `register_id` (S) — denormalised on `SESSION#` rows |
| Sort key | `opened_at` (N) — integer Unix seconds |

Query pattern: `KeyConditionExpression = "register_id = :r"`,
`FilterExpression = "status = :open"`, `ScanIndexForward = False`, `Limit = 1`.

This is the guard used by `open_session` (POS-004) to enforce "only one OPEN
session per register". The filter is applied after key lookup; because there is
at most one open session per register at any given time, DDB will return it in the
first page without a scan.

#### GSI_SESSION_TXN

Answers: "List all transactions for session `S` in chronological order."

| | Key |
|---|---|
| Partition key | `session_id` (S) — denormalised on `TXN#` rows |
| Sort key | `created_at` (N) — integer Unix seconds |

Query pattern: `KeyConditionExpression = "session_id = :s"`,
`ScanIndexForward = True`. Used by X-report and Z-report generation (POS-007/008).

#### GSI_CASHIER

Answers: "List all sessions opened by cashier `C`, newest first."

| | Key |
|---|---|
| Partition key | `cashier_sub` (S) — user sub, denormalised on `SESSION#` rows |
| Sort key | `opened_at` (N) — integer Unix seconds |

Query pattern: `KeyConditionExpression = "cashier_sub = :sub"`,
`ScanIndexForward = False`. Used for cashier history and audit endpoints.

### 3.4 attr_types declaration

All three numeric sort keys must appear in `attr_types` or DynamoDB stores them
as string and queries with integer values raise `ValidationException`:

```python
attr_types={"opened_at": "N", "created_at": "N"}
```

`opened_at` appears in both `GSI_REGISTER_OPEN` and `GSI_CASHIER`; `created_at`
appears in `GSI_SESSION_TXN`. A single `attr_types` dict covers both because
`_attribute_definitions()` deduplicates by attribute name.

### 3.5 Complete TableDef

```python
# POS-003 — Point of Sale single-table store.
# Register config, session headers, tender sub-rows, and transaction headers
# all live in one table keyed by pos_pk/pos_sk.
# GSI_REGISTER_OPEN: find the open session per register (register_id → opened_at N).
# GSI_SESSION_TXN:   list a session's transactions (session_id → created_at N).
# GSI_CASHIER:       list a cashier's sessions     (cashier_sub → opened_at N).
TableDef(
    _resolve_table_name(S.pos_table_name, "pos"),
    "pos_pk",
    "pos_sk",
    gsi=[
        {
            "index_name": "GSI_REGISTER_OPEN",
            "partition_key": "register_id",
            "sort_key": "opened_at",
        },
        {
            "index_name": "GSI_SESSION_TXN",
            "partition_key": "session_id",
            "sort_key": "created_at",
        },
        {
            "index_name": "GSI_CASHIER",
            "partition_key": "cashier_sub",
            "sort_key": "opened_at",
        },
    ],
    attr_types={"opened_at": "N", "created_at": "N"},
),
```

## 4. API / Service Design

POS-003 introduces no endpoints and no service functions. It is purely
infrastructure. This section documents the read/write interface that
**downstream tickets will depend on** so that POS-004 can be developed without
revisiting POS-003.

### 4.1 Table handle access

```python
from app.core.tables import T

# Write a register row
T.pos.put_item(Item={
    "pos_pk": f"REGISTER#{register_id}",
    "pos_sk": "META",
    "register_id": register_id,
    ...
})

# Query GSI_REGISTER_OPEN for a specific register's open session
resp = T.pos.query(
    IndexName="GSI_REGISTER_OPEN",
    KeyConditionExpression="register_id = :r",
    FilterExpression="#s = :open",
    ExpressionAttributeNames={"#s": "status"},
    ExpressionAttributeValues={":r": register_id, ":open": "open"},
    ScanIndexForward=False,
    Limit=1,
)
```

`T.pos` is a `_FloatSafeTable` proxy (same as every other `T.*`), so callers
never need to coerce floats manually.

### 4.2 Settings access

```python
from app.core.settings import S

# Feature flag guard (used in every POS handler)
if not S.pos_enabled:
    raise HTTPException(status_code=404, detail="POS is not enabled")

# Cash drawer requirement (used in open_session)
if S.pos_cash_drawer_required and not drawer_acknowledged:
    raise HTTPException(status_code=422, detail="Cash drawer acknowledgment required")
```

### 4.3 Flag guard helper (forward reference for POS-004)

Following the returns/RMA pattern (`app/services/returns_rma.py:67-73`), the POS
service will expose:

```python
def _flag_on() -> bool:
    return bool(getattr(S, "pos_enabled", False))

def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="POS is not enabled")
```

POS-003 does not implement these — it only ensures `S.pos_enabled` exists and
defaults to `False` so the `getattr` fallback in `_flag_on` is never needed.

## 5. Detailed Behavior & Edge Cases

### 5.1 Table provisioning idempotency

`_ensure_table()` (`scripts/local-ddb-init.py:2534`) is called once per
`TableDef` at stack startup. If the `pos` table already exists, the function
exits early at `:2537-2577` but still reconciles any missing GSIs. This means
`just restart` is safe to run multiple times — the table creation is idempotent
and the GSI additions are additive.

### 5.2 GSI attribute collision with other row types

`opened_at` and `created_at` are attribute names also used by other tables.
Within the `pos` table they appear only on `SESSION#` and `TXN#` rows
respectively; `REGISTER#` and `TENDER#` rows do not carry these attributes. DDB
sparse-index semantics mean rows without `opened_at`/`created_at` are simply not
projected into the respective GSI — no error, no pollution.

### 5.3 `attr_types` must cover both GSIs sharing `opened_at`

`GSI_REGISTER_OPEN` and `GSI_CASHIER` both use `opened_at` as their sort key.
`_attribute_definitions()` deduplicates attribute names (builds a dict, then
applies overrides). A single `"opened_at": "N"` entry in `attr_types` covers
both GSIs without duplication. If `opened_at` were not in `attr_types`, DDB would
default it to `"S"` and queries with `between` on integer timestamps would
silently return wrong results (lexicographic ordering) or raise
`ValidationException`.

### 5.4 Default table name

The default table name is `"pos"` — short, unique within the codebase, and
consistent with the pattern (e.g. `"returns"` for `returns_table_name`). The
env var `POS_TABLE_NAME` overrides it for multi-tenant or staging deployments.

### 5.5 Flag is a master switch, not a per-endpoint guard

`S.pos_enabled = False` means the entire POS surface returns 404 for every
request. It does not deactivate the table or prevent its creation — the table
exists regardless of the flag so that enabling POS mid-deployment does not
require a schema migration. Disabling the flag after data has been written to the
table is safe; the data persists and is accessible again when the flag is
re-enabled.

### 5.6 `pos_cash_drawer_required` is a UX safety flag, not a security gate

When `True`, `open_session` (POS-004) must receive an explicit
`drawer_acknowledged: bool = True` in `OpenSessionIn`. This prevents accidental
session opens on registers without a physical drawer. The flag defaults to
`False` to support receipt-only (no-cash) deployments.

## 6. Feature Flag & Config

### 6.1 Settings additions to `app/core/settings.py`

Insertion point: immediately after `returns_table_name` at line `:847`,
extending the OFBiz settings block.

```python
# OFBiz commerce/ERP — POS (Point of Sale) channel (POS-001..POS-NNN).
# Master switch defaults OFF. With pos_enabled=False every POS endpoint returns
# 404 and the module is dormant; existing shop/cart/orders/billing bytes are
# unchanged.
pos_enabled: bool = os.environ.get("POS_ENABLED", "false").lower() == "true"
pos_table_name: str = os.environ.get("POS_TABLE_NAME", "pos")
pos_cash_drawer_required: bool = (
    os.environ.get("POS_CASH_DRAWER_REQUIRED", "false").lower() == "true"
)
```

### 6.2 Environment variables

| Env var | Default | Purpose |
|---|---|---|
| `POS_ENABLED` | `"false"` | Master flag; `"true"` enables all POS endpoints |
| `POS_TABLE_NAME` | `"pos"` | DynamoDB table name override |
| `POS_CASH_DRAWER_REQUIRED` | `"false"` | Require cash-drawer ack on `open_session` |

### 6.3 `.env.local.example` addition

```
# Point of Sale (POS) — off by default
POS_ENABLED=false
# POS_TABLE_NAME=pos
# POS_CASH_DRAWER_REQUIRED=false
```

The commented-out lines match the existing convention for dev-only or opt-in feature
flags. Note: `INVENTORY_RESERVATIONS_ENABLED` and `RETURNS_RMA_ENABLED` are **not**
present in `.env.local.example` (confirmed by grep) — those settings ship with
their defaults and are enabled only by operator action. POS follows the same pattern.

### 6.4 Flag idiom rationale

The `os.environ.get(..., "false").lower() == "true"` idiom is used (not `not in
("0","false","False")`) because POS defaults **off**. The "not in" idiom is for
default-**on** flags. `inventory_reservations_enabled` (:839) and
`returns_rma_enabled` (:846) both use `.lower() == "true"` for the same reason.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

The `pos` table is a real DynamoDB table in both dev (DynamoDB Local, port 8001)
and prod (AWS DynamoDB). No `dev_mode` branch is introduced. `_ensure_table()`
at startup handles both environments identically — it calls `create_table` (or
`update_table` for new GSIs) regardless of environment.

### 7.2 Startup idempotency

`_ensure_table()` is re-entrant: if the `pos` table already exists (e.g., after
a hot restart without `just restart`), the function exits at `:2537` without
error. This means adding POS-003 to a live deployment that already had the
table provisioned (e.g., by a previous run) is safe.

### 7.3 Table handle is always initialised

`T.pos = _safe_table(S.pos_table_name)` is evaluated at module import time (when
`app/core/tables.py` is first loaded). It does not check `S.pos_enabled`. This
means:

- If `POS_ENABLED=false`, `T.pos` is a valid `_FloatSafeTable` pointing at a
  real DynamoDB table handle — no lazy initialisation is needed.
- POS service code can always import `T.pos` without a startup guard.
- There is no risk of `AttributeError` on `T.pos` in tests that set
  `pos_enabled=True` after module import.

### 7.4 Security: no POS data accessible with flag off

The flag guard `_require_enabled()` (to be implemented in POS-004) is the
authoritative access control at the handler layer. There is no POS router in
`app/main.py` at this stage — the router itself does not exist yet. When it is
added (POS-004), it will be conditionally registered or will short-circuit to 404
on every handler, exactly as `app/services/returns_rma.py` does.

## 8. Backward Compatibility & Migration

### 8.1 Zero impact on existing tables

POS-003 does not touch `shopping_cart`, `orders`, `billing`, `catalog`,
`inventory`, `reservations`, or `returns`. No existing `TableDef` is modified.
No `S` attribute is renamed. No `T.*` field is renamed.

### 8.2 New field on a frozen dataclass

`Tables` is a `frozen=True` dataclass. Adding a field (`pos: Any`) is backward-
compatible at the Python level: existing code that constructs `T` via the `T =
Tables(...)` singleton call simply gains one more named argument. No existing
caller constructs `Tables(...)` directly; all access is via the module-level `T`.

### 8.3 Dev restart required after deploy

After deploying POS-003, `just restart` (or `scripts/local-ddb-init.py`) must be
run once to create the `pos` table in DynamoDB Local. In production, the startup
hook in `scripts/local-ddb-init.py` runs on every deploy and is idempotent, so
no manual migration is needed.

### 8.4 Rollback

Disabling POS is `POS_ENABLED=false` (restart optional). The table is never
dropped by rollback — dropping it is a manual operator action if needed. This
matches the pattern for inventory and returns.

### 9.1 Smoke pytest (unit, offline)

**File:** `tests/test_pos_003_tables_settings.py`

The test is hermetic and offline: it uses moto to spin up an in-memory DynamoDB,
manually calls `_ensure_table()` with the POS `TableDef`, and then asserts
that:

1. The `pos` table was created with `pos_pk` / `pos_sk` as the primary key.
2. `GSI_REGISTER_OPEN` exists with `register_id` (HASH) and `opened_at` (RANGE).
3. `GSI_SESSION_TXN` exists with `session_id` (HASH) and `created_at` (RANGE).
4. `GSI_CASHIER` exists with `cashier_sub` (HASH) and `opened_at` (RANGE).
5. `opened_at` and `created_at` attribute definitions carry `AttributeType: N`.
6. A `put_item` with integer `opened_at` followed by a `query` on
   `GSI_REGISTER_OPEN` with a `between` condition returns the item (proves
   numeric sort key is active and not silently treated as string).
7. `S.pos_enabled` is `False` when `POS_ENABLED` is unset.
8. `S.pos_table_name` is `"pos"` when `POS_TABLE_NAME` is unset.
9. `S.pos_cash_drawer_required` is `False` when `POS_CASH_DRAWER_REQUIRED` is unset.

11. Setting `POS_ENABLED=true` in the environment (via `monkeypatch.setenv` or

Test isolation follows the repo pattern (see `tests/test_gap_0223_0224_ec2_host_inventory.py`):
moto `mock_aws()` context; `_ensure_table()` called manually on the test DDB

`TestClient` is not used — this ticket has no handlers.

```python
"""POS-003: smoke test — pos table, GSIs, attr_types, settings, T.pos handle.

Offline, hermetic.  Uses moto in-memory DynamoDB.

from __future__ import annotations

from contextlib import ExitStack
from decimal import Decimal

import boto3

try:
    from moto import mock_aws
except ImportError:
    mock_aws = None

    """Load scripts/local-ddb-init.py via importlib (hyphen in filename prevents

    tests/test_local_ddb_init_kyc_screening.py:19-26)."""

    import sys
    from pathlib import Path

    path = Path("scripts/local-ddb-init.py").resolve()

    assert spec and spec.loader
    mod = importlib.util.module_from_spec(spec)
    sys.modules[spec.name] = mod
    spec.loader.exec_module(mod)
    return mod


def _pos_table_def():

    from app.core.settings import S
    return mod.TableDef(
        mod._resolve_table_name(S.pos_table_name, "pos"),
        "pos_pk",
        "pos_sk",
        gsi=[
            {"index_name": "GSI_REGISTER_OPEN",
             "partition_key": "register_id", "sort_key": "opened_at"},
            {"index_name": "GSI_SESSION_TXN",
             "partition_key": "session_id", "sort_key": "created_at"},

        self.addCleanup(self.stack.close)
        self.stack.enter_context(mock_aws())
        self.ddb = boto3.resource("dynamodb", region_name="us-east-1")
        # load via importlib — hyphenated filename prevents normal import
        mod = _load_ddb_init_module()
        mod._ensure_table(self.ddb, _pos_table_def())
        self.table = self.ddb.Table("pos")

    # --- settings ---

    def test_pos_enabled_default_false(self):
        from app.core.settings import S
        self.assertFalse(S.pos_enabled)

    def test_pos_table_name_default(self):
        from app.core.settings import S
        self.assertEqual(S.pos_table_name, "pos")

    def test_pos_cash_drawer_required_default_false(self):
        from app.core.settings import S
        self.assertFalse(S.pos_cash_drawer_required)

    # --- table handle ---

    def test_T_pos_is_not_none(self):

        self.assertIsNotNone(T.pos)

    # --- table schema ---

    def test_primary_key_schema(self):
        desc = self.table.meta.client.describe_table(TableName="pos")["Table"]
        ks = {k["AttributeName"]: k["KeyType"] for k in desc["KeySchema"]}
        self.assertEqual(ks["pos_pk"], "HASH")
        self.assertEqual(ks["pos_sk"], "RANGE")

    def test_gsi_names_present(self):
        desc = self.table.meta.client.describe_table(TableName="pos")["Table"]
        gsi_names = {g["IndexName"] for g in desc.get("GlobalSecondaryIndexes", [])}
        self.assertIn("GSI_REGISTER_OPEN", gsi_names)
        self.assertIn("GSI_SESSION_TXN", gsi_names)
        self.assertIn("GSI_CASHIER", gsi_names)

    def test_numeric_attr_types(self):
        desc = self.table.meta.client.describe_table(TableName="pos")["Table"]
        attr_map = {a["AttributeName"]: a["AttributeType"]
                    for a in desc["AttributeDefinitions"]}
        self.assertEqual(attr_map["opened_at"], "N")
        self.assertEqual(attr_map["created_at"], "N")

    def test_numeric_gsi_query_roundtrip(self):
        """opened_at must be stored and queried as N, not as S."""
        self.table.put_item(Item={
            "pos_pk": "SESSION#sess_abc",
            "pos_sk": "META",
            "register_id": "reg_001",
            "session_id": "sess_abc",
            "cashier_sub": "user_x",
            "status": "open",
            "opened_at": Decimal("1700000000"),
        })
        resp = self.table.query(
            IndexName="GSI_REGISTER_OPEN",
            KeyConditionExpression=(
                "register_id = :r AND opened_at BETWEEN :lo AND :hi"
            ),
            ExpressionAttributeValues={
                ":r": "reg_001",
                ":lo": Decimal("1699999999"),
                ":hi": Decimal("1700000001"),
            },
        )
        self.assertEqual(len(resp["Items"]), 1)
        self.assertEqual(resp["Items"][0]["session_id"], "sess_abc")
```

## 10. Open Questions / Assumptions

1. **Assumption: `pos_pk`/`pos_sk` as generic key names** — The ticket specifies
   these exact attribute names. Using generic names (not `pk`/`sk` or
   `register_id`/`session_id`) avoids attribute-name collisions with row payloads
   that carry those same field names as data attributes. Verify that the POS-004
   service layer always writes `pos_pk`/`pos_sk` consistently and never
   accidentally maps `pk`/`sk` onto these rows.

2. **Assumption: `"pos"` as the default table name** — Short and distinctive.
   Confirm no collision with any existing DynamoDB table name in staging/prod
   environments before deploying. `_table_defs()` already owns all local names;
   a grep of `"pos"` in the existing `_table_defs()` list returns no match.

3. **Assumption: insertion point for settings** — The spec places the POS block
   after `returns_table_name` at `:847`. The ticket says "next to
   `shopping_cart_table_name` (:811) / `orders_table_name` (:1124)". Both anchor
   points are in the same section; `:847` (after returns) is the most cohesive.
   Confirm with the author that the Returns block is the intended insertion point,
   not immediately before `orders_table_name`.

4. **Assumption: `opened_at` is the right GSI sort key for `GSI_CASHIER`** — Using
   `opened_at` allows cashier sessions to be listed newest-first by open time,
   which is the natural display order. If the requirement changes to "sort by
   closed_at for Z-report purposes", `GSI_CASHIER` would need a separate sort key.
   This can be added as a new GSI in a later ticket without schema breakage.

5. **Assumption: `pos_cash_drawer_required` is a boolean flag on `S`** — The
   ticket lists this as a setting. If the requirement is per-register (not global),
   this flag will need to become a per-row attribute on the register config. For
   POS-003, the global flag is sufficient and can be replaced by per-register
   logic in POS-004 or POS-006 without schema changes.

6. **Assumption: `GSI_SESSION_TXN` uses `session_id` as partition key** —
   Consistent with the POS-002 spec (section 3.3) where `session_id` is
   denormalised onto `TXN#` rows. Confirm that POS-005 writes `session_id` on
   every transaction row.

7. **Assumption: `register_id` is denormalised onto `SESSION#` rows** — Required
   for `GSI_REGISTER_OPEN` to work. POS-004 must write `register_id` as a top-
   level attribute (not nested inside a map) on every `SESSION#/META` row.
