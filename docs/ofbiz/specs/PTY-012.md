# PTY-012 — B2B org-account router + migration admin endpoints

**Type:** Feature | **Priority:** P1 | **Estimate:** 2 days
**Milestone:** 4 — Router
**Depends on:** PTY-008 (org-account service), PTY-009 (contacts migration), PTY-010 (person party backfill), PTY-011 (party/CRM router)
**Downstream:** PTY-013 (frontend types + wrappers), PTY-014 (Party/CRM page), PTY-015 (test suite)

---

## 1. Summary & Goal

PTY-012 extends the `app/routers/party.py` file created by PTY-011 with two groups of new
HTTP endpoints:

1. **B2B org-account endpoints** — six HTTP routes under the `/ui/party` prefix that expose the
   `create_org_account`, `list_members`, `add_member`, and `remove_member` service functions
   (from PTY-008's `app/services/party.py`) to authenticated browser sessions. Mutating endpoints
   require the caller to hold `ORG_ADMIN` on the target org (verified by the router via the
   `_resolve_person_party` helper introduced in PTY-008's design).

2. **Admin migration endpoints** — two admin-only HTTP routes under `/ui/admin/party` that
   trigger the PTY-009 contacts backfill and the PTY-010 `ensure_person_party` backfill,
   respectively, and report how many records were processed.

All six org endpoints are doubly gated by `S.party_crm_enabled` and
`S.party_crm_org_accounts_enabled`; the two admin endpoints are gated by `S.party_crm_enabled`
and `S.party_crm_contacts_migration_enabled`. With the relevant flag(s) off every handler
returns HTTP 503 and no service code runs. The existing `app/routers/contacts.py` surface,
`T.contacts`, `T.billing`, and all other subsystems are byte-for-byte unchanged when the flags
are off.

## 3. Data Model

PTY-012 introduces **no new DynamoDB tables, no new GSIs, and no schema changes**. It is purely
a router layer over the `party` table (PTY-002) already defined by prior tickets.

For completeness, the relevant `party` single-table key shapes used by these endpoints:

| Row type | PK | SK | GSI |
|---|---|---|---|
| PARTY_GROUP META (org) | `PARTY#{org_party_id}` | `META` | `GSI_CREATED`: `TYPE#PARTY_GROUP` / `created_at (N)` |
| PERSON META (member) | `PARTY#{person_party_id}` | `META` | `GSI3`: `OWNER#{user_sub}` / `PARTY#{party_id}` |
| OWNER relationship | `PARTY#{person_party_id}` | `REL#OWNER#{org_party_id}` | `GSI3`: `REL_TO#{org_party_id}` / `REL#OWNER#{person_party_id}` |
| GROUP_MEMBER relationship | `PARTY#{person_party_id}` | `REL#GROUP_MEMBER#{org_party_id}` | `GSI3`: `REL_TO#{org_party_id}` / `REL#GROUP_MEMBER#{person_party_id}` |
| CUSTOMER role | `PARTY#{org_party_id}` | `ROLE#CUSTOMER` | `GSI1`: `ROLE#CUSTOMER` / `PARTY#{org_party_id}` |
| BILL_TO role | `PARTY#{org_party_id}` | `ROLE#BILL_TO` | `GSI1`: `ROLE#BILL_TO` / `PARTY#{org_party_id}` |

`created_at` is a numeric GSI sort key (`attr_types={"created_at": "N"}`) per PTY-002 — see
`scripts/local-ddb-init.py:84` for the established pattern (`attr_types={"created_at": "N"}`
is used there for the broadcast profiles table). No additions to `local-ddb-init.py`
are required by PTY-012.

The `party` table handle will be `T.party` wired in `app/core/tables.py` (PTY-002 adds it
adjacent to `T.contacts` at line 354 via `_safe_table(S.party_table_name)`; the handle does
not exist in the current codebase — it is added by PTY-002).

## 4. API / Service Design

### 4.1 Router file and prefix

File: `app/routers/party.py` (created by PTY-011; does not exist yet in current codebase)
Prefix for org endpoints: `/ui/party` (declared on the `APIRouter`)
Prefix for admin endpoints: `/ui/admin/party` (declared on a separate `APIRouter`)

PTY-012 appends two logical blocks to the party router file:

- **Block A** — Org-account endpoints, after the existing PTY-011 `/parties` block.
- **Block B** — Admin migration endpoints, using a second `APIRouter` with prefix
  `/ui/admin/party`, registered separately in `app/main.py`.

### 4.2 Org-account endpoints (Block A)

Ordering constraint: the `/orgs` static segment must appear **before** any `/parties/{party_id}`
dynamic segment in the declaration order (already satisfied if appended after PTY-011's
`/parties` block, since the FastAPI router resolves by declaration order).

All six endpoints check flags first:

```python
def _check_org_flag():
    if not S.party_crm_enabled or not S.party_crm_org_accounts_enabled:
        raise HTTPException(503, "party_crm_org_accounts feature not enabled")
```

#### `POST /ui/party/orgs` — create org account

```python
@router.post("/orgs", status_code=201)
async def create_org(
    body: CrmCreateOrgAccountIn,
    ctx: dict = Depends(require_ui_session),
) -> CrmOrgAccountOut:
```

Calls `party.create_org_account(body.name, owner_user_sub=ctx["user_sub"], correlation_id=body.correlation_id)`.
Returns the populated `CrmOrgAccountOut`. The `owner_user_sub` is always the authenticated
caller — clients cannot create orgs on behalf of other users. `body.owner_user_sub` is present
in the model (PTY-008) but the router ignores it and always uses `ctx["user_sub"]`, preventing
privilege escalation.

#### `GET /ui/party/orgs` — list orgs for caller

```python
@router.get("/orgs")
async def list_orgs(
    cursor: Optional[str] = None,
    ctx: dict = Depends(require_ui_session),
) -> dict:
```

Resolves the caller's PERSON party via `_resolve_person_party(ctx["user_sub"])`, then queries
`T.party` via `GSI3` (pattern `GSI3PK = "REL_TO#{person_party_id}"`, SK prefix `REL#OWNER#` or
`REL#GROUP_MEMBER#`) to enumerate all orgs the caller belongs to. For each relationship,
fetches the PARTY_GROUP META row and constructs `CrmOrgAccountOut`. Returns
`{"orgs": [...], "next_cursor": cursor_str | None}`. Pagination via `app/core/cursor.py`
`encode_cursor` (`:94`) / `decode_cursor` (`:103`) — same pattern as `list_parties`.

#### `GET /ui/party/orgs/{org_party_id}` — get single org

```python
@router.get("/orgs/{org_party_id}")
async def get_org(
    org_party_id: str,
    ctx: dict = Depends(require_ui_session),
) -> CrmOrgAccountOut:
```

Fetches `PK=PARTY#{org_party_id}`, `SK=META`. Verifies the caller has a relationship to the
org (OWNER or GROUP_MEMBER row) — a caller with no relationship receives 404 (not 403) to avoid
org enumeration. Returns `CrmOrgAccountOut` with `member_count` populated from `list_members`.

#### `POST /ui/party/orgs/{org_party_id}/members` — add member (ORG_ADMIN required)

```python
@router.post("/orgs/{org_party_id}/members", status_code=201)
async def add_org_member(
    org_party_id: str,
    body: CrmOrgMemberIn,
    ctx: dict = Depends(require_ui_session),
) -> CrmRelationshipOut:
```

Resolves `actor_party_id = _resolve_person_party(ctx["user_sub"])`. Calls
`party.add_member(org_party_id, actor_party_id=actor_party_id, member_party_id=body.member_party_id, role_type=body.role_type)`.
Service function raises `HTTPException(403)` if actor is not ORG_ADMIN. Returns
`CrmRelationshipOut` describing the new GROUP_MEMBER relationship.

#### `DELETE /ui/party/orgs/{org_party_id}/members/{member_party_id}` — remove member (ORG_ADMIN required)

```python
@router.delete("/orgs/{org_party_id}/members/{member_party_id}", status_code=204)
async def remove_org_member(
    org_party_id: str,
    member_party_id: str,
    ctx: dict = Depends(require_ui_session),
) -> Response:
```

Resolves `actor_party_id`. Calls `party.remove_member(org_party_id, actor_party_id, member_party_id)`.
Service raises `HTTPException(403)` for non-admin, `HTTPException(409, "cannot_remove_org_owner")`
for the org owner. Returns 204 on success.

#### `GET /ui/party/orgs/{org_party_id}/members` — list members

```python
@router.get("/orgs/{org_party_id}/members")
async def list_org_members(
    org_party_id: str,
    cursor: Optional[str] = None,
    ctx: dict = Depends(require_ui_session),
) -> dict:
```

No ORG_ADMIN required (read-only). Verifies the caller has any relationship to the org (same
visibility guard as `get_org`). Calls `party.list_members(org_party_id, cursor=cursor)`. Returns
`{"members": [...], "next_cursor": cursor_str | None}`.

### 4.3 Admin migration endpoints (Block B)

Separate `APIRouter(prefix="/ui/admin/party", tags=["admin-party-crm"])`. Auth:
`require_admin_or_root_csrf` from `app/auth/policy.py:100-106` (verified). Both endpoints
are gated:

```python
def _check_migration_flag():
    if not S.party_crm_enabled or not S.party_crm_contacts_migration_enabled:
        raise HTTPException(503, "party_crm_contacts_migration feature not enabled")
```

#### `POST /ui/admin/party/migrate-contacts` — trigger contacts backfill

```python
@admin_party_router.post("/migrate-contacts")
async def migrate_contacts(
    body: CrmMigrateContactsIn,
    actor: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> CrmMigrateContactsOut:
```

Where `CrmMigrateContactsIn` is:

```python
class CrmMigrateContactsIn(BaseModel):
    owner_id: Optional[str] = None   # None = all owners; set for targeted single-user backfill
```

Calls `party_contacts_migration.run_contacts_backfill(owner_id=body.owner_id)`. Maps the
returned dict (`scanned`, `projected`, `errors` keys from PTY-009) to `CrmMigrateContactsOut`. Emits an audit event
`audit_event("party_crm.migrate_contacts", actor.sub, owner_id=body.owner_id, ...)` after the
call. **This endpoint is synchronous** — the backfill runs inline in the request. For large
deployments, callers should scope to a single `owner_id`. A future async job variant is
deferred (§10 — Open Question #1).

#### `POST /ui/admin/party/ensure-person/{user_sub}` — ensure PERSON party for one user

```python
@admin_party_router.post("/ensure-person/{user_sub}")
async def ensure_person_party(
    user_sub: str,
    actor: AuthenticatedUser = Depends(require_admin_or_root_csrf),
) -> CrmEnsurePersonOut:
```

Calls `party.ensure_person_party(user_sub)`. Returns `CrmEnsurePersonOut` with `party_id`,
`created` flag, and `mechs_synced` count. Emits
`audit_event("party_crm.ensure_person", actor.sub, target_user_sub=user_sub, ...)`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off responses

With `S.party_crm_org_accounts_enabled=False` every org endpoint returns:
```json
{"detail": "party_crm_org_accounts feature not enabled"}
```
with status 503. With `S.party_crm_contacts_migration_enabled=False` every admin migration
endpoint returns 503. No service code runs. `T.party`, `T.contacts`, and all billing/shop
subsystems are byte-for-byte unchanged. Existing `/ui/party` (PTY-011) endpoints are unaffected
by the `party_crm_org_accounts_enabled` flag — they are gated only by `party_crm_enabled`.

### 5.2 ORG_ADMIN authorization flow

For `POST /orgs/{org_party_id}/members` and `DELETE /orgs/{org_party_id}/members/{member_id}`:

1. Router resolves `actor_party_id` via `_resolve_person_party(ctx["user_sub"])`.
2. Router passes `actor_party_id` to the service function.
3. Service function `_assert_org_admin(org_party_id, actor_party_id)` (PTY-008) reads
   the actor's relationship row to the org (`PK=PARTY#{actor}`, `SK=REL#OWNER#{org}` or
   `SK=REL#GROUP_MEMBER#{org}`). If `org_role` is `"owner"` or `"org_admin"`, the check passes.
   Any other value or a missing row raises `HTTPException(403, "org_admin_required")`.
4. Service proceeds with the write.

A user who has not yet been linked to a PERSON party (i.e., `_resolve_person_party` returns
nothing) receives `HTTPException(404, "person_party_not_found_for_user")`. Callers without a
PERSON party cannot create or manage orgs. The expected path to remedy this is for an admin to
call `POST /ui/admin/party/ensure-person/{user_sub}` first.

### 5.3 Caller visibility guard for `GET /orgs/{org_party_id}`

To prevent org enumeration, a caller with no OWNER or GROUP_MEMBER relationship to the org
receives 404, not 403. The check is:

```python
person_party_id = _resolve_person_party(ctx["user_sub"])
rel = T.party.get_item(
    Key={"PK": f"PARTY#{person_party_id}", "SK": f"REL#OWNER#{org_party_id}"}
).get("Item") or T.party.get_item(
    Key={"PK": f"PARTY#{person_party_id}", "SK": f"REL#GROUP_MEMBER#{org_party_id}"}
).get("Item")
if not rel:
    raise HTTPException(404, "org_not_found")
```

This guard also covers `list_org_members` via the same check before calling `list_members`.

### 5.4 `POST /ui/party/orgs` — owner_user_sub ignored

`CrmCreateOrgAccountIn.owner_user_sub` is defined in the Pydantic model (PTY-008 §4.2) but
the router always overrides it with `ctx["user_sub"]`. This prevents a caller from creating
an org owned by a different user. The service function `create_org_account` receives
`owner_user_sub=ctx["user_sub"]` unconditionally.

### 5.5 `migrate-contacts` with no `owner_id` — long-running request

When `owner_id=None`, `run_contacts_backfill` scans all rows in `T.contacts` and may run for
seconds on a populated database. The endpoint is synchronous (no background task). In dev,
the table is always small. In prod, callers should supply `owner_id` for incremental execution.
The response JSON is returned only after the full backfill completes. A 504 gateway timeout is
possible for very large contact sets — deferred async job variant noted in §10.

### 5.6 `migrate-contacts` idempotency

`run_contacts_backfill` (PTY-009) is replay-safe: for each `(owner_id, contact_id)` pair, if
the PERSON party and CONTACT_REL relationship already exist on `T.party`, the idempotent
`attribute_not_exists(PK)` puts are no-ops (counted under `projected`, not as errors). Re-calling
`migrate-contacts` for the same `owner_id` produces zero net writes and returns
`scanned == X, projected == X, errors == 0` (all rows examined and re-projected idempotently).

### 5.7 `ensure-person` idempotency

`ensure_person_party` (PTY-010) is idempotent: it uses a `GSI3` lookup
(`GSI3PK=OWNER#{user_sub}`) to check for an existing PERSON party before writing. If found,
`created=False` is returned and mech sync still runs (re-syncing any changed email/phone/postal
mechs). If not found, a new PERSON party is written, `created=True`, and mechs are back-filled.
Re-calling for the same `user_sub` is safe and costs one extra GSI read.

### 5.8 Admin migration and `require_admin_or_root_csrf`

`require_admin_or_root_csrf` (`app/auth/policy.py:100-106`) calls `enforce_cookie_csrf`
(`app/auth/policy.py:71-97`) before the role check. For cookie-auth POST requests this
requires an `x-csrf-token` header matching the `ui_csrf` cookie (per CLAUDE.md CSRF
section). Bearer-token admin callers (e.g. scripts) skip CSRF enforcement automatically
because `enforce_cookie_csrf` returns early (`app/auth/policy.py:87-89`) when no
`ui_session` cookie is present.

### 5.9 `POST /ui/party/orgs` — `correlation_id` scoping

`correlation_id` is optional. When omitted, `create_org_account` generates a fresh `uuid4()`,
making each call create a new org. When supplied, the org `party_id` is deterministic
(`sha256(correlation_id.encode()).hexdigest()[:32]`) and replays are no-ops. Clients should
supply `correlation_id` when implementing retry-safe creation (e.g. frontend form submission
with idempotency key). The correlation key namespace is global to the `party` table — clients
should use namespaced keys (e.g. `"org_create:{user_sub}:{timestamp}"`) to avoid accidental
cross-caller collisions.

### 5.10 DynamoDB FilterExpression and pagination in `list_orgs`

`list_orgs` queries `GSI3` with `GSI3PK = "REL_TO#{person_party_id}"` and filters on SK prefix
(`begins_with(SK, "REL#OWNER#")` OR `begins_with(SK, "REL#GROUP_MEMBER#")`). Per the CLAUDE.md
gotcha: "DDB FilterExpression doesn't reduce page size" — the query fetches up to 1MB before
applying the filter. PTY-012 must loop via `LastEvaluatedKey` until exhausted to avoid silently
missing relationships on a busy table. The `encode_cursor`/`decode_cursor` pattern from
`app/core/cursor.py` is used for client-facing pagination, but the inner DynamoDB loop must
always drain internally per page.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

PTY-012 is a pure router layer. All DynamoDB operations run against `T.party`, which inherits
its endpoint from `app/core/tables.py` via `_safe_table(S.party_table_name)`. In dev this
resolves to DynamoDB Local at `http://localhost:8001`; in prod, to real DynamoDB. There is no
`if S.dev_mode` branch in either the router or the service functions it calls. The
`run_contacts_backfill` function (PTY-009) reads `T.contacts` — also bound via `_safe_table`
with no mock/real split. Full parity guaranteed.

### Idempotency

- **`POST /ui/party/orgs`** with the same `correlation_id` returns the same org (deterministic
  `party_id`, no duplicate DDB row). Verified by the `attribute_not_exists(PK)` conditional
  at the DDB layer.
- **`POST /orgs/{id}/members`** for an already-existing member returns the existing row
  (PTY-008 §5.8 — no duplicate GROUP_MEMBER relationship).
- **`DELETE /orgs/{id}/members/{member_id}`** on a non-existent relationship is a no-op (PTY-006
  `delete_relationship` semantics).
- **`POST /migrate-contacts`** is fully idempotent (PTY-009 per §5.6 above).
- **`POST /ensure-person/{user_sub}`** is idempotent (PTY-010 per §5.7 above).

### Security

- **No cross-user org creation.** The router ignores `body.owner_user_sub` and always uses
  `ctx["user_sub"]`. A user cannot create an org on behalf of another user.
- **Org enumeration prevented.** `GET /orgs/{org_party_id}` and `GET /orgs/{org_party_id}/members`
  return 404 (not 403) for callers with no relationship to the org.
- **ORG_ADMIN is per-org.** An ORG_ADMIN on org A cannot manage members of org B. Enforced by
  `_assert_org_admin` checking the `org_role` attribute on the specific org's relationship row.
- **Admin migration requires ADMIN or ROOT + CSRF.** The `require_admin_or_root_csrf` dependency
  enforces both role and CSRF for cookie-auth callers.
- **Admin migration emits audit events.** Both `migrate-contacts` and `ensure-person` emit
  `audit_event(...)` (`app/services/alerts.py:644`) to `T.alerts` so all admin-triggered
  backfills are traceable in the audit log.
- **No PII in DynamoDB keys.** All PK/SK values are prefixed hex IDs or uppercase enum strings;
  `name` and `display_name` are stored as plain attributes only.
- **No money-out path.** Neither the org endpoints nor the migration endpoints initiate any
  payment, ledger write, or call to `billing_shared.new_ledger_entry`. The billing table is
  untouched.

## 8. Backward Compatibility & Migration

### Legacy contacts surface unchanged

With `PARTY_CRM_ENABLED=0` (the default), none of the new endpoints exist in the routing
table in any observable way. The existing `app/routers/contacts.py` surface
(`GET/POST/PATCH/DELETE /ui/contacts`) is byte-for-byte unchanged. `T.contacts`, `T.billing`,
`T.shopping_cart`, and all other tables are never written by party router code.

Even with `PARTY_CRM_CONTACTS_MIGRATION_ENABLED=1`, the migration is triggered only by an
explicit admin `POST /ui/admin/party/migrate-contacts` call — it never runs automatically on
startup or on any contact write path. The forward hook in `app/routers/contacts.py:add_contact`
(PTY-009) is the only automatic trigger; it is best-effort and wrapped in `try/except`, so a
migration failure never blocks the legacy write.

### Staged rollout

| Phase | Flags to enable | Result |
|---|---|---|
| Dark (default) | all off | No party endpoints reachable; all legacy surfaces unchanged |
| Base party | `PARTY_CRM_ENABLED=1` | PTY-011 `/ui/party/parties` endpoints live; no orgs |
| Orgs | `PARTY_CRM_ENABLED=1` + `PARTY_CRM_ORG_ACCOUNTS_ENABLED=1` | Full PTY-012 Block A org endpoints live |
| Migration | `PARTY_CRM_ENABLED=1` + `PARTY_CRM_CONTACTS_MIGRATION_ENABLED=1` | Admin migration endpoints live |

Each phase is reversible by toggling the relevant env var and restarting the backend.

### No DynamoDB table migrations required

PTY-012 writes only to `T.party`, which is created by PTY-002's `TableDef` in
`scripts/local-ddb-init.py`. In prod, the `party` table must be created before any flag is
enabled. No existing table schema is changed.

## 10. Open Questions / Assumptions

1. **CORRECTED (pass 3):** `run_contacts_backfill` (PTY-009) returns `{"scanned": int, "projected": int, "errors": int}` — verified against `docs/ofbiz/specs/PTY-009.md §4.1`. The originally assumed keys (`contacts_projected`, `parties_created`, `relationships_created`, `skipped_existing`) were wrong. `CrmMigrateContactsOut` and all references have been updated to use `scanned`/`projected`/`errors`.

2. **CORRECTED (pass 3):** `ensure_person_party` (PTY-010) returns a plain `str` (party_id) — verified against `docs/ofbiz/specs/PTY-010.md §4.1`. It does NOT return a dict with `created`/`mechs_synced`. The `CrmEnsurePersonOut` model still exposes `created` and `mechs_synced` for a useful API response, but the router must derive `created` by performing a GSI3 existence check before calling `ensure_person_party` (and set `mechs_synced=0` unless PTY-010 is later extended). The inline model definition in §2.6 now documents this derivation requirement.

3. **Open question:** The `migrate-contacts` endpoint is synchronous. For a platform with
   10,000+ contacts per user, a full `owner_id=None` backfill could time out. Should this
   be an async background task (returning a job ID like the audit export worker at
   `app/services/audit_export_worker.py`)? Phase 1 defers this; the endpoint documents
   the timeout risk and recommends supplying `owner_id`.

4. **FORWARD_DEP (pass 3):** The `_resolve_person_party(user_sub)` helper is a private function in `app/routers/party.py`. PTY-008 §5.5 describes it and places it in the router file. PTY-011 creates that file; if PTY-011 does not include the helper, PTY-012 must add it. Both specs confirm it lives in `app/routers/party.py` — this is a FORWARD_DEP resolved when PTY-011 or PTY-012 lands (whichever provides it first). No plan gap exists.

5. **VERIFIED (pass 3):** The GSI3 namespace is not polluted by contact-mech rows. PTY-007 mech items use `GSI2` (`GSI2PK`/`GSI2SK`) for reverse-lookup — they carry no `GSI3PK`/`GSI3SK` attributes. PTY-006 relationship mirror rows use `GSI3PK="REL_TO#{to_party_id}"`. A `list_orgs` query with `GSI3PK="REL_TO#{person_party_id}"` therefore returns only inbound relationship mirrors — no contact-mech rows can appear. The `begins_with(SK, "REL#OWNER#")` / `begins_with(SK, "REL#GROUP_MEMBER#")` filter in `list_orgs` is still needed to exclude CONTACT_REL and EMPLOYMENT mirrors, which also land under the same `GSI3PK` partition — this was already correctly specified. Verified via `docs/ofbiz/specs/PTY-007.md §3` (mech schema: no GSI3 fields) and `docs/ofbiz/specs/PTY-006.md §3` (mirror row schema).

6. **FORWARD_DEP (pass 3):** `CrmOrgMemberIn.role_type` values `"member"`, `"admin"`, `"org_admin"` map directly to the `org_role` attribute written on the GROUP_MEMBER relationship row. Confirmed by `docs/ofbiz/specs/PTY-008.md §4.1 add_member` step 7: `T.party.update_item(... UpdateExpression="SET org_role = :r", ExpressionAttributeValues={":r": role_type})`. The mapping is verbatim — no translation needed. Resolves when PTY-008 is built.
