# PRD-003 — Product-depth Pydantic models

**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days
**Milestone:** 1 — Scaffolding & Data Model

---

## 1. Summary & Goal

PRD-003 adds the Pydantic model layer that every downstream product-depth service and router ticket (PRD-004 through PRD-013) will use for request validation and response serialization. The ticket is purely additive to `app/models.py`: it introduces new enum and model classes and extends `CatalogItemOut` with optional sentinel fields, leaving every existing model and endpoint byte-for-byte unchanged.

The concrete deliverables are:

1. **`ProductTypeEnum`** — a `str, Enum` discriminator covering the six OFBiz product-type identifiers (`virtual`, `variant`, `standalone`, `bundle`, `kit`, `digital`).
2. **Variant models** — `VariantCreateIn` / `VariantOut`: create a feature-value combination under a virtual parent; output the effective price and inventory SKU.
3. **Feature models** — `ProductFeatureCreateIn` / `ProductFeatureOut` (a single value within a feature category) and `ProductFeatureCategoryOut` (the parent axis, e.g. "Color").
4. **Bundle models** — `BundleComponentIn` / `BundleOut`: declare component items with quantities; output the flattened expansion and computed price.
5. **Association models** — `ProductAssocIn` / `ProductAssocOut` with `ProductAssocTypeEnum`.
6. **Price-component models** — `ProductPriceComponentIn` / `ProductPriceComponentOut` with `PriceTypeEnum`.
7. **Additive extension of `CatalogItemOut`** — four new optional fields (`product_type`, `variant_count`, `has_features`, `bundle_component_count`) whose defaults preserve the existing serialization for items without depth rows.

Nothing in this ticket writes to DynamoDB. No new service or router is created. No existing model field is modified.

## 3. Data Model

PRD-003 is a models-only ticket. No new DynamoDB table or GSI is created here; that is PRD-002's responsibility. However, every input and output model must faithfully mirror the DynamoDB row layouts decided in PRD-001 (§3.2) because the downstream service tickets (PRD-004/006/007/009/010/012) will use these models as the validated input gate and the serialization contract.

### 3.1 ProductTypeEnum

```
Enum values   →  DynamoDB `product_type` attribute on the TYPE row (PK=ITEM#{id}, SK=TYPE)
"standalone"  →  OFBiz FINISHED_GOOD / DIGITAL_GOOD — default for pre-depth items
"virtual"     →  OFBiz PRODUCT_VIRTUAL — has VARIANT children, no direct stock
"variant"     →  OFBiz PRODUCT_VARIANT — child of a virtual parent, has its own SKU
"bundle"      →  OFBiz PRODUCT_BUNDLE — fixed-price multi-component; one DDB TYPE row
"kit"         →  OFBiz KIT — component-sum price; structurally identical to bundle in DDB
"digital"     →  OFBiz DIGITAL_GOOD — downloadable; no inventory reservation
```

### 3.2 ProductAssocTypeEnum

```
"substitute"  →  OFBiz ProductAssoc.assocTypeId PRODUCT_SUBSTITUTE
"complement"  →  cross-sell (PRODUCT_COMPLEMENT)
"upgrade"     →  upsell (PRODUCT_UPGRADE)
"manuf"       →  manufacturing association (MANUF_COMPONENT)
```

### 3.3 PriceTypeEnum

```
"LIST"          →  OFBiz ProductPrice.productPriceTypeId DEFAULT_PRICE list
"DEFAULT"       →  active sell price (fallback from scalar price_cents)
"PROMO"         →  promotional override
"COMPETITIVE"   →  competitive-set reference price
"MINIMUM"       →  floor price (never sell below)
"AVERAGE_COST"  →  COGS reference; not surfaced to storefront
```

### 3.4 Variant models

`VariantCreateIn` fields:
- `parent_item_id: str` — the virtual parent's item_id (validated non-empty, max 64).
- `feature_values: Dict[str, str]` — mapping of `feature_category_id → feature_value_id`. Min 1 entry; PRD-007 will validate that each value belongs to the named category and that the combination is unique.
- `sku_override: Optional[str] = None` — explicit SKU; if absent the service derives `variant:{parent_item_id}:{variant_id}`. Max 128.

`VariantOut` fields:
- `variant_id: str` — the deterministic 16-char hex id.
- `parent_item_id: str`.
- `sku: str` — the inventory-reservation key.
- `feature_values: Dict[str, str]` — the feature_category_id → feature_value_id map.
- `price_delta_cents: int` — signed aggregate delta from feature value deltas.
- `effective_price_cents: int` — parent `price_cents` + `price_delta_cents`.

- `created_at: int` — Unix timestamp integer.

`ProductFeatureOut`:
- `feature_value_id: str`.
- `feature_category_id: str`.
- `name: str`.
- `price_delta_cents: int`.
- `position: int`.

`ProductFeatureCategoryOut` (the parent axis, e.g. "Color"):

- `values: List[ProductFeatureOut] = Field(default_factory=list)` — populated by the service when `include_values=True`; empty list otherwise.

`ProductPriceComponentIn`:

- `expires_at: Optional[int] = Field(default=None, ge=0)`.

- `amount_cents: int`.
- `currency: str`.
- `effective_at: int`.

### 3.9 CatalogItemOut extension

Four new optional fields are appended to the existing `CatalogItemOut` definition at `app/models.py:672`. All default to back-compat values so no existing serialization changes:

```python
# Product-depth additive fields (PRD-003). All Optional / 0-default so pre-depth
# items round-trip unchanged; _catalog_item_out (catalog.py:110) does not pass these.
product_type: Optional[ProductTypeEnum] = None
# None means "no depth row" — consumers treat it as "standalone" per PRD-001 §3.2.1.
variant_count: int = 0
# 0 when no VAR#* rows exist or flag is off.
has_features: bool = False
# False when no FTAPPL#* rows exist or flag is off.
bundle_component_count: int = 0
# 0 when no COMP#* rows exist or flag is off.
```

The `product_type` field uses `Optional[ProductTypeEnum]` (not the plain string) so callers benefit from enum validation when the field is present. A `None` value is the back-compat sentinel meaning "pre-depth scalar item"; the service layer interprets `None` as `standalone` per PRD-001.

## 5. Detailed Behavior & Edge Cases

### 5.1 CatalogItemOut round-trip for pre-depth items

A scalar catalog item dict returned by `T.catalog.get_item` contains none of the four new depth fields. When `_catalog_item_out` constructs `CatalogItemOut`, the new fields (`product_type`, `variant_count`, `has_features`, `bundle_component_count`) are absent from the keyword arguments. Pydantic `BaseModel` sets each absent field to its declared default: `None`, `0`, `False`, `0`. The serialized JSON is identical to what was returned before PRD-003 was applied, because `product_type=None` is excluded from JSON output only if `model_config` uses `exclude_none=True`. The current `CatalogItemOut` carries no such config, so `product_type: null` will appear in JSON output. This is the correct behavior: API consumers that do not know the field will ignore it, and the value `null` is semantically equivalent to "standalone / pre-depth item."

If `null` in the response is undesirable for existing consumers, `CatalogItemOut` can be decorated with `model_config = ConfigDict(populate_by_name=True)` and the new fields can carry `exclude=True` at the field level — but this is **not** the recommended approach as it prevents the fields from ever being consumed by PRD-014 TypeScript mirrors. The accepted behavior is `null` for pre-depth items.

### 5.2 ProductTypeEnum validation in VariantCreateIn

`VariantCreateIn.feature_values` is a `Dict[str, str]` with minimum one entry. An empty dict passes the model validation but will be rejected at the service layer (PRD-007) with an HTTP 422. PRD-003 does not add a `model_validator` for this because the valid set of feature-category ids and feature-value ids is only knowable at DynamoDB query time, not statically.

### 5.3 price_delta_cents in ProductFeatureCreateIn

`price_delta_cents` is a signed integer (`ge=-10_000_000_00, le=10_000_000_00`). A value of `-999999999` is valid at model level (deep discount). The service layer (PRD-006) is responsible for asserting that `parent.price_cents + Σdeltas >= 0` before writing; this constraint is a business rule enforced in the write path, not the model.

### 5.4 BundleOut.computed_price_cents derivation

`computed_price_cents` is a read-only computed field. For `product_type="kit"` it equals `Σ(component.unit_price_cents × component.quantity)`. For `product_type="bundle"` it equals the bundle item's scalar `price_cents`. This distinction is computed by `expand_bundle` in PRD-009; `BundleOut` carries it as a plain `int` — not a `@computed_field` — so it round-trips through DynamoDB cache rows in future without re-running the formula.

### 5.5 ProductPriceComponentIn.effective_at not defaulting in the model

`effective_at` carries `ge=0` but no `default`. The field is required in `ProductPriceComponentIn`. The service layer (PRD-012) will substitute `now_ts()` when the caller omits `effective_at` — this is done at the endpoint level via a FastAPI `Body(...)` default, not in the Pydantic model. Keeping `effective_at` required in the model prevents silent "effective now" behavior from creeping into batch imports where the caller must be explicit.

### 5.6 ProductAssocOut.assoc_id determinism

`assoc_id = sha256(from_item_id + assoc_type + to_item_id)[:16]`. The same `(from, type, to)` triple always produces the same `assoc_id`, making duplicate creation idempotent (PRD-010 uses a conditional put on `SK=ASSOC#{assoc_type}#{assoc_id}`). The `assoc_id` field in `ProductAssocOut` is therefore stable and can be used as a stable external reference.

### 5.7 variant_id determinism in VariantOut

`variant_id = sha256(parent_item_id + sorted_feature_value_tuple)[:16]` (PRD-001 §3.2.5). The sorted tuple is `sorted(feature_values.items())` so `{"color": "red", "size": "xl"}` and `{"size": "xl", "color": "red"}` produce the same `variant_id`. `VariantOut.variant_id` carries this pre-computed value; the service layer (PRD-007) is responsible for computing and storing it.

### 5.8 BundleComponentOut is nested, not a top-level resource

`BundleComponentOut` is always returned inside `BundleOut.components`. It is never an API response root. This means PRD-011's `GET /items/{id}/bundle` and `GET /items/{id}/expand` return a `BundleOut` directly; they do not return a list of `BundleComponentOut` at the root level.

### 5.9 ProductFeatureCategoryOut.values default behavior

`values` defaults to an empty list. The PRD-006 service function `list_feature_categories` may or may not populate this list depending on the caller's `include_values` flag. The router endpoint (PRD-008) will offer `?include_values=true` as a query param. When `include_values=False` (the default for list endpoints), `values=[]` is serialized; no field is omitted.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No code path divergence

PRD-003 introduces zero runtime behavior. No `dev_mode` branch exists in Pydantic model definitions. All validation rules (`ge`/`le` bounds, enum membership, string min/max lengths) apply identically in dev and prod.

### 7.2 Idempotency via deterministic ids

Two of the new output models carry deterministic ids that PRD-007/010 will compute and store:

- `VariantOut.variant_id` — `sha256(parent_item_id + sorted(feature_values.items()))[:16]`. Re-creating the same feature combination produces the same `variant_id`, which the service writes with a conditional put to prevent duplicates.
- `ProductAssocOut.assoc_id` — `sha256(from_item_id + assoc_type + to_item_id)[:16]`. Same tuple always maps to the same id.

These invariants are documented in the model fields via `Field(description=...)` so OpenAPI consumers understand the stable-key contract.

### 7.3 Enum membership validation as input guard

`ProductTypeEnum`, `ProductAssocTypeEnum`, and `PriceTypeEnum` provide strict enum validation at the FastAPI request-parsing boundary. An unknown string (e.g. `"VIRTUAL"` in uppercase, or a typo like `"substutite"`) raises a 422 Unprocessable Entity before the handler body is entered. This prevents invalid discriminator values from ever reaching DynamoDB.

### 7.4 Price bounds

`ProductPriceComponentIn.amount_cents` is bounded `ge=0, le=10_000_000_00` (100 million dollars), matching the existing `CatalogItemCreateIn.price_cents` bound at `app/models.py:542`. `ProductFeatureCreateIn.price_delta_cents` allows negative values (deep discount), mirroring OFBiz's signed `ProductPrice.price` field.

### 7.5 Billing parity note

PRD-003 models carry no money-movement logic. The `ProductPriceComponentOut` model describes a price-enrichment layer that is **read-only** relative to billing: it never calls `new_ledger_entry` (at `app/services/billing_shared.py:224`) or `refund_payment` (at `app/routers/billing.py:1287`). Money only moves through the existing cart → checkout → ledger path, using the `price_cents` the price-component layer resolves before the cart line is written. This preserves the SECOPS-007 requirement that no new billing paths are introduced.

## 8. Backward Compatibility & Migration

### 8.1 Existing catalog endpoints unchanged

The existing endpoints that return `CatalogItemOut` (`POST /ui/catalog/categories/{category_id}/items` at `app/routers/catalog.py:352`, `GET /ui/catalog/categories/{category_id}/items`, `PATCH /ui/catalog/categories/{category_id}/items/{item_id}`, and the full-text-search endpoint at `:465`) all call `_catalog_item_out(item)` without change. Because the four new `CatalogItemOut` fields have safe defaults, the serialized output acquires four additional keys with `null`/`0`/`false` values. Consumers using strict JSON deserialization that error on unknown keys need to update their client; consumers using lenient parsing are unaffected.

**Breaking change risk**: Technically, adding fields to a JSON response is not a breaking change under REST semantics. However, the `null` value for `product_type` is a new key that was previously absent. If any downstream test asserts `"product_type" not in response` that test will break. PRD-003's test plan (§9) includes a regression assertion to document the exact new shape.

### 8.2 No DynamoDB schema migration

PRD-003 adds no DynamoDB tables or index changes. Those are deferred to PRD-002 (pending). There is therefore no table migration, no backfill, and no `just restart` step required for PRD-003 alone.

### 8.3 Models are additive to app/models.py

The new enums and model classes are appended after the existing `CatalogItemOut` block (`:672-692`) and before the `CatalogReorderReq` class at `:695`. The insertion point is immediately after the `CatalogItemListOut` class at `:691`. No existing line in `app/models.py` is modified except the `CatalogItemOut` class body itself (four new field lines appended).

## 10. Open Questions / Assumptions

1. **Assumption**: `product_type=None` in `CatalogItemOut` JSON output is acceptable to all existing API consumers, including the frontend `CatalogItem` TypeScript type (which will be extended in PRD-014). If any existing frontend consumer uses strict type guards that reject the `null` value on this field, PRD-014 must add `product_type?: ProductType | null` before PRD-003 ships.

2. **Assumption**: `BundleComponentOut.line_total_cents` is computed and set by the service (PRD-009), not in the Pydantic model. If PRD-009 decides to use a `@computed_field` instead, `BundleComponentOut` would need a `@property` decorated with `@computed_field`, but this requires `model_config = ConfigDict(arbitrary_types_allowed=True)` and complicates serialization. The current design keeps `line_total_cents` as a plain `int` set by the service.

3. **Open question**: Should `ProductFeatureCategoryOut.created_at` be an `int` (Unix timestamp, consistent with inventory/reservation models) or a `str` (ISO string, consistent with `CatalogCategoryOut.created_at` at `app/models.py:531`)? The PRD-001 data model uses Unix int for `created_at` on all depth rows. This spec follows that decision (int), meaning the feature-category out shape is inconsistent with the flat catalog category out shape. PRD-014 must align the TypeScript type accordingly.

4. **Assumption**: `VariantCreateIn.feature_values: Dict[str, str]` min-length constraint (`min_length=1`) is enforced via `Field(min_length=1)`. In Pydantic v2, `Field(min_length=1)` on a `Dict` field validates that the dict has at least one key. If this behavior differs in the installed Pydantic version, a `model_validator(mode="after")` should be added instead.

5. **Open question**: Should `ProductPriceComponentIn.effective_at` have a default of `0` (making it optional) or remain required? This spec keeps it required so callers are explicit. If the price-component router endpoint (PRD-013) needs to default to "now", it does so via `Body(default_factory=now_ts)` in the endpoint signature rather than in the model.

6. **Assumption**: The `PriceTypeEnum` values are uppercase strings (`"LIST"`, `"DEFAULT"`, etc.) matching OFBiz `productPriceTypeId` values. This is intentional to ease future OFBiz data migration. The frontend (PRD-014) will display them with proper casing via a label map.

7. **Assumption**: `BundleComponentOut` is defined before `BundleOut` in the file (forward-reference issue). In `app/models.py`, classes must be defined before they are used as type hints, or `from __future__ import annotations` at the top of the file (already present at `app/models.py:1`) defers evaluation, making declaration order irrelevant. Both `BundleComponentOut` and `BundleOut` can be declared in any order.
