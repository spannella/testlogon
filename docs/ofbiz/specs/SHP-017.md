# SHP-017 — Shipping admin UI (carriers, rates, shipments)

## 1. Summary & Goal

SHP-017 delivers the admin-facing React pages that let operators manage the entire shipping
module introduced by SHP-001 through SHP-016. There are three distinct views, all under
`frontend/src/pages/shop/admin/` and all behind the `VITE_SHIPPING_ENABLED` feature flag
plus a `canAccessGeneralAdminControls` role guard:

1. **CarrierAdmin** (`ShippingCarrierAdmin.tsx`) — list/create/update/disable carriers;
   expand each carrier to list/add/update/disable its ship methods.
2. **ShipmentQueue** (`ShippingShipmentQueue.tsx`) — live queue of shipments filtered by
   status; create a shipment from an order; drive the full lifecycle (pack → label →
   ship → deliver); assign items to packages; enter a tracking number and see the
   computed tracking URL.
3. **RateRuleEditor** (`ShippingRateRuleEditor.tsx`) — display the current rate estimation
   parameters per carrier/method (base rate, weight breakpoints) and let admins update them.

These pages call only the endpoint wrappers defined by SHP-016 in
`frontend/src/api/endpoints/shipping.ts` — no new HTTP calls are introduced. No existing
shop/cart/orders/billing component is modified. With `VITE_SHIPPING_ENABLED=false` (the
default), the lazy imports are never evaluated and the nav entries are hidden.

## 3. Data Model

SHP-017 is a pure frontend ticket. It introduces no new DynamoDB tables, settings keys,
or backend service changes. The full DDB schema for shipping was locked by SHP-001/SHP-002:

| DDB table | Handle | PK / SK | Relevant GSIs |
|---|---|---|---|
| `shipping_carriers` | `T.shipping_carriers` | `carrier_id` / `sk` (`CARRIER#` or `METHOD#{method_code}`) | — |
| `shipments` | `T.shipments` | `shipment_id` / (none, single-row per shipment) | `GSI_ORDER (order_id, created_at)`, `GSI_STATUS (status, created_at)` — both use numeric `created_at` per `attr_types={"created_at":"N"}` in `scripts/local-ddb-init.py` |
| `shipment_items` | `T.shipment_items` | `shipment_id` / `item_id` | — |
| `shipment_packages` | `T.shipment_packages` | `shipment_id` / `package_seq` | — |

The React pages read from and write to these tables only through the backend REST layer —
no direct DDB access from the frontend.

### 3.1 React Query key hierarchy

```
["shipping", "carriers"]                          — CarrierListOut
["shipping", "carriers", carrierId]               — CarrierOut (single)
["shipping", "carriers", carrierId, "methods"]    — ShipmentMethodOut[]
["shipping", "methods"]                           — enabled methods (storefront)
```

Mutations invalidate the minimal set of affected keys. For example, `advanceShipmentStatus`

to refresh both the detail pane and the status-filtered queue.

## 5. Detailed Behavior & Edge Cases

### 5.1 Lifecycle advance: legal transitions and UI state

The backend enforces the transition graph (SHP-010); the UI reflects only the legal
next states per the current shipment status to reduce operator error. Buttons are
`disabled` when a mutation is pending.

| Current status | Legal next statuses (advance button labels) |
|---|---|
| `created` | `packed` ("Mark as packed") |
| `packed` | `label_created` ("Create label") |
| `label_created` | `shipped` ("Mark as shipped" — opens TrackingDialog) |
| `shipped` | `in_transit` ("Mark in-transit"), `exception` ("Flag exception") |
| `in_transit` | `out_for_delivery` ("Out for delivery"), `exception` ("Flag exception") |
| `out_for_delivery` | `delivered` ("Mark delivered"), `exception` ("Flag exception") |
| `delivered` | — (terminal, no advance button) |
| `exception` | `in_transit` ("Resume transit"), `returned` ("Mark returned"), `cancelled` ("Cancel") |
| `returned` | — (terminal) |
| `cancelled` | — (terminal) |

The backend returns HTTP 409 for illegal transitions. The UI catches this via the
`onError` handler and shows `toast.error("Invalid status transition")`.

### 5.2 Tracking URL display

`ShipmentOut.tracking_url` is computed at read time by the backend (`build_tracking_url`
from `app/services/carrier_tracking.py:33`). When `tracking_url` is non-null, the detail
pane renders:
```tsx
<a href={shipment.tracking_url} target="_blank" rel="noopener noreferrer"
   className="text-blue-600 underline">
  {shipment.tracking_number} ({shipment.carrier_code.toUpperCase()})
</a>
```
When null (manual carrier or no tracking number yet), render the tracking number as plain
text or "No tracking number" muted text.

### 5.3 Packing completeness gate

When `packingQuery.data.pack_complete === false`, the "Advance to label_created" button is
`disabled` and shows a tooltip: "Pack all items before creating a label." The packing
status table highlights rows with `remaining_qty > 0` in amber.

### 5.4 Auto-detect carrier hint (client-side)

In `TrackingDialog`, below the `tracking_number` input, display a read-only hint:
```tsx
const detectedCarrier = detectCarrierClientSide(trackingNumber);
// shows: "Detected: UPS" or "Unknown carrier — select manually"
```
`detectCarrierClientSide` is a minimal JS translation of `app/services/carrier_tracking.py:46`
`detect_carrier` (detection rules applied in order, matching the backend's priority):

1. matches `^1Z[A-Z0-9]{16}$` (exactly 18 chars) → `"ups"`
   (`_UPS_PATTERN`, carrier_tracking.py:20)
2. matches `^(JJD?\d{18,20}|\d{10})$` — i.e. JD/JJD prefix **or** exactly 10 digits → `"dhl"`
   (`_DHL_PATTERN`, carrier_tracking.py:30)
3. all digits AND length in `{12, 15}` → `"fedex"` (lengths 12/15 only; 20/22 are claimed
   by USPS before FedEx in the backend logic — `_FEDEX_LENGTHS={12,15,20,22}` minus
   `_USPS_LENGTHS={20,22,30,34}` = `{12,15}` remaining for FedEx)
4. all digits AND (length in `{20,22,30,34}` OR starts with `94/92/93/70/23/13`) → `"usps"`
5. otherwise → `null`

This hint is display-only; the backend auto-detects authoritatively. The `carrier_code`
field in the form remains optional — if the operator supplies it, it overrides auto-detection
on the backend.

### 5.5 Create shipment pre-population

When the admin opens `CreateShipmentDialog` from the shipment queue, the `order_id` field
can be pre-populated if the queue was navigated to via a link from an order management page
(future: URL query param `?order_id=xxx`). For this ticket, the field is a free-text input.

### 5.6 Optimistic UI and stale data

Shipment status changes can also be driven by the backend poller (SHP-013) or tracking
webhook (SHP-012). The `queueQuery` uses `refetchInterval: 30_000` to refresh the status-filtered
queue every 30 seconds without a full page reload. The detail pane does not auto-refresh
(relies on `pollMut` or manual navigation). This matches the pattern in
`frontend/src/pages/shop/admin/InventoryAdmin.tsx` which does not auto-poll.

### 5.7 `base_rate_cents` display and edit

All money fields are stored as integer cents (`base_rate_cents: number` in
`ShipmentMethodOut`). The UI converts to a dollar string for display
(`(cents / 100).toFixed(2)`) and parses on save (`Math.round(parseFloat(dollarStr) * 100)`).
Fractional-cent values are rejected client-side with `toast.error("Invalid rate amount")`.

### 5.8 Empty queue state

When `queueQuery.data` is an empty array for the selected status filter, render
`<EmptyState icon={<Package />} title="No shipments" description="No shipments with
status '{statusFilter}'." />`.

### 5.9 403 / 503 handling

Any API call that returns HTTP 503 (flag off on backend) is caught by the global `client.ts`
error handler and typically propagates as an `AxiosError`. The `isShippingEnabled()` guard
(see §6) prevents the pages from rendering in the first place when the frontend flag is
also off. If there is a flag mismatch (frontend flag on, backend flag off), the mutation
`onError` handlers show `toast.error("Shipping is not enabled on the server")`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

The three admin pages call the same URLs in dev and prod. The Vite proxy transparently
routes `/ui/shipping/*` and `/ui/shop/shipments/*` to `http://localhost:8000` in dev;
no `dev_mode` branch exists in the frontend. Idempotency guarantees (`carrier_id`,
`shipment_id` deterministic by SHP-004/SHP-008) mean repeated form submissions do not
create duplicate records, which is important for dev workflows where forms may be
re-submitted.

### 7.2 Idempotency surface visible to admin

- **Create carrier**: `carrier_id = sha256(carrier_code)[:16]` (SHP-004). Clicking "Create"
  twice for the same `carrier_code` returns the existing record (200, not 409). The UI
  should treat a successful response identically in both cases.
- **Create shipment**: `shipment_id = sha256("shipment:{order_id}:{ship_group_seq}")[:32]`
  (SHP-008). Double-submit of `CreateShipmentDialog` returns the existing shipment. The
  `onSuccess` handler should always navigate to the shipment detail regardless.
- **Shipping refund on cancel**: handled server-side by SHP-015 using
  `sha256("shipping_refund:{shipment_id}")[:32]` as the idempotency key. The UI shows
  "Cancel" once (terminal after advance to `cancelled`); no double-cancel risk from the UI.

### 7.3 Security

- **CSRF**: all `api.post`, `api.patch`, `api.del` calls in `shipping.ts` automatically
  attach `X-CSRF-Token` from the `ui_csrf` cookie via `client.ts:178–182` (comment at 178,
  `getCookie("ui_csrf")` at 179, `headers.set("X-CSRF-Token", csrf)` at 181). No additional
  CSRF handling is needed in the component layer.
- **Role gate**: `canAccessGeneralAdminControls(accessToken)` from
  `frontend/src/lib/adminCapabilities.ts:47` returns `true` only for `role=root` or
  `role=admin` with `profile.type==="general"`. Scoped admins (`auth_support`,
  `billing_support`, `content_moderation`) — tracked in `adminCapabilities.ts:37` — are
  excluded. The backend enforces the same check via `require_admin_or_root` (line 67) /
  `require_admin_or_root_csrf` (line 100) from `app/auth/policy.py`.
- **Buyer isolation**: the buyer-facing endpoints (`/ui/shop/my/orders/...`) are not called
  from these admin pages. Admin pages call `/ui/shop/shipments/...` (admin prefix).
  The ownership check on buyer endpoints is a backend concern (SHP-011).
- **Tracking URL is computed server-side**: the frontend renders `tracking_url` as an
  anchor tag but never constructs it; `build_tracking_url` from
  `app/services/carrier_tracking.py:33` is the authoritative source. The value is always
  sourced from the `ShipmentOut` response, never synthesized client-side.
- **No secrets in the frontend**: rate estimation may use UPS rating API in prod (SHP-006).
  The API credentials (`S.ups_client_id`, `S.ups_client_secret`) are backend-only env vars
  never exposed to the client.

## 10. Open Questions / Assumptions

1. **Route path for admin shipping pages**: assumed `/admin/shipping/carriers`,
   `/admin/shipping/shipments`, `/admin/shipping/rates` (nested under `admin/shipping/`
   to avoid collision with buyer-facing `/shop` paths). If the team prefers
   `/admin/shipping-carriers` (flat), update `App.tsx` routes and Sidebar entries
   accordingly.

2. **Rate breakpoint editing**: the ticket description says "rate-rule editor". SHP-006
   defines the estimation engine with per-method weight breakpoints and zone modifiers, but
   SHP-007 does not expose a CRUD API for those breakpoints — only the estimation call. This
   spec scopes the "rate-rule editor" to editing `base_rate_cents` and transit days on
   existing methods (which SHP-005's `PATCH /ui/shipping/carriers/{id}/methods/{code}`
   supports) plus a rate preview. Full breakpoint/zone rule CRUD is deferred to a follow-up
   ticket. **Assumption**: SHP-017 AC ("rate-rule editor") is satisfied by the base-rate +
   transit-day edit + preview combination. Confirm with product.

3. **Create shipment address input**: `ShipmentIn.ship_to_address` is `Dict[str, Any]` on
   the backend. This spec proposes a JSON textarea for the MVP to avoid coupling to an
   address schema not yet formalized by SHP-001. A structured address form (name, street,
   city, state, ZIP, country) is a clean-up follow-up. **Assumption**: JSON textarea is
   acceptable for the admin-only create dialog.

4. **Order lookup for create shipment**: `CreateShipmentDialog` requires an `order_id` but
   there is no `/ui/shop/orders` list endpoint for admins in the current codebase (orders
   are created by the commerce service and queried by user ID via the buyer path). The admin
   will need to know or copy the `order_id`. A lookup widget is deferred to SHP-018 /
   follow-up. **Assumption**: free-text `order_id` input is acceptable for MVP admin workflow.

5. **`disableCarrier` HTTP verb**: SHP-016 spec (§5.3) notes the assumed path
   `DELETE /ui/shipping/carriers/{carrier_id}/disable`. If SHP-005 used
   `PATCH /carriers/{id}` with `{ enabled: false }` instead, `disableCarrier` wrapper in
   `shipping.ts` must be corrected and the UI call updated. **Assumption**: follows the
   `api.del(`.../disable`)` wrapper as specified in SHP-016.

6. **Sidebar grouping**: the three shipping entries are assumed to appear in the same
   "Admin" nav group as "Inventory" (`Sidebar.tsx:237`). If shipping warrants its own
   "Shipping" sub-group, the `NAV_ITEMS` array in `Sidebar.tsx` needs a new group object.
   **Assumption**: entries added to the existing admin group to match InventoryAdmin.

7. **`CarrierListOut` vs `CarrierOut[]`**: SHP-016 §10 open question 1 notes uncertainty
   about whether `listCarriers` returns `{ carriers: CarrierOut[], cursor?: string }` or a
   plain array. This spec assumes `CarrierListOut` shape (paginated). If SHP-005 returns a
   plain array, the query function and the React component's `.data.carriers` access must
   be updated to `.data` directly.

8. **Seeded default carriers**: SHP-004 seeds `ups/fedex/usps/dhl/manual` idempotently.
   Section A3 of the E2E test assumes this seed has run (via `just up` or `just restart`).
   If the seed is not run before the E2E, the carrier table will be empty and A3 will need
   to create carriers first.
