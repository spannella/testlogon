# PUR-001 — Purchasing/SCM data-model & sequencing spike

## 1. Summary & Goal

PUR-001 is the foundational design spike for the OFBiz Purchasing/SCM work stream. Its goal is to produce a precise, code-grounded design for the buy-side counterpart of the existing sales-order stack: a self-contained **Supplier** party record, **SupplierProduct** pricing (supplier↔SKU), a **PurchaseOrder** entity with a guarded approval lifecycle, a **Receipt** that increments inventory through the existing `inventory.adjust` primitive, and a **reorder-suggestion** engine wired to the OFB-005 low-stock signals. The design is entirely additive: with `PURCHASING_SCM_ENABLED=false` (the default) every existing byte — catalog, cart, orders, billing, inventory — is unchanged and the new tables are dormant.

This document is the authoritative reference for PUR-002 through PUR-012 and supersedes any informal notes. No code is shipped here; the deliverable is this specification and confirmation that no money path is forked.

## 2. Context & Current State

### 2.1 Existing flag-gated OFBiz modules

Two precedent modules already follow the additive/flag-gated pattern this work stream must mirror:

- **Inventory & reservations** (`app/services/inventory.py`) — gated by `S.inventory_reservations_enabled` (`app/core/settings.py:839`). Master gate `_require_enabled()` at `inventory.py:54` raises `HTTPException(404)` when off. Tables `inventory` and `reservations` are declared at `scripts/local-ddb-init.py:2456` and `2469`. Handles wired in `app/core/tables.py:569–571` as `T.inventory`, `T.reservations`.

- **Returns / RMA** (`app/services/returns_rma.py`) — gated by `S.returns_rma_enabled` (`app/core/settings.py:846`). Same `_require_enabled` pattern at `returns_rma.py:71`. Table `returns` declared at `scripts/local-ddb-init.py:2483`. Handle wired at `app/core/tables.py:319` as `T.returns`.

Both follow the pattern in `app/core/tables.py`: the `Tables` dataclass field is declared at the bottom of the class (`:310–319`), and the `T` singleton at line `:321` binds each handle via `_safe_table(S.<name>)` (lines `:569–571`).

### 2.2 Deterministic-id idempotency pattern

`commerce_order_service.CommerceOrderService.create_order` at `app/services/commerce_order_service.py:39` derives `order_id = hashlib.sha256(corr.encode("utf-8")).hexdigest()[:32]` at line `:67`. The same pattern must be applied to all new entity ids (`supplier_id`, `po_id`, `receipt_id`) so that callers who retry with the same correlation string do not create duplicate records.

### 2.3 Order-header + per-line single-table pattern

`create_order` at `commerce_order_service.py:85` writes a header row with `put_item`, then loops over line items at line `:88–103` writing one item row per line into `T.order_items`. The PurchaseOrder model mirrors this: one header row (`SK=META`) plus N line rows (`SK=LINE#{n}`) in the same `purchase_orders` table, following single-table DynamoDB design.

### 2.4 Inventory adjust primitive

`inventory.adjust(sku, delta, reason, *, location_id, user_sub)` at `app/services/inventory.py:209` is the only sanctioned write path for on-hand changes. It handles create-on-adjust for positive deltas (`:230`), guards against negative-available with a conditional update (`:256`), and calls `_audit` (`:250`). The receiving path must call this function, never issue a parallel `put_item` on the inventory table.

The `list_low_stock(location_status)` function at `app/services/inventory.py:318` queries the `GSI_AVAILABLE` index in a paginated loop and is the OFB-005 signal source for reorder suggestions. `reorder_point` is stored on the inventory record and exposed via `_record_out` at line `:104`.

### 2.5 Billing ledger — single-entry principle

`billing_shared.new_ledger_entry` at `app/services/billing_shared.py:224` is the one and only write path for all money movements. It writes to `T.billing` (PK=`pk`, SK=`LEDGER#{ts}#{entry_id}`) and stamps `ledger_date` (YYYY-MM-DD UTC string) on every entry for the `GSI_LEDGER_DATE` index (`scripts/local-ddb-init.py:72`). FIN-013 / CLAUDE.md requires every provider-originated entry to carry `extra={"provider": "..."}` for dashboard attribution. `settle_or_reverse_ledger` at `billing_shared.py:262` updates the `state` field on an existing entry. AP payables for supplier payments must flow entirely through this mechanism — no new payment/refund mechanism.

### 2.6 State-machine precedents

Three existing conditional-update state machines provide implementation patterns:

- `app/services/inventory.py:434` (`_close_reservation`) — `ConditionExpression="#status = :active"` guard on a `update_item`; `ConditionalCheckFailedException` → idempotent no-op.
- `app/services/kyc_cases.py:228` — `ConditionExpression="version = :expected_version"` with a `_is_conditional_conflict` helper at line `:112`.
- `app/services/video_state_machine.py` — `_ALLOWED_TRANSITIONS` dict pattern.

### 2.7 Audit event pattern

`inventory._audit` at `app/services/inventory.py:92` is a best-effort wrapper around `alerts.audit_event` that swallows all exceptions. All new service mutations must use the same pattern.

### 2.8 Router registration precedent

`app/main.py:311` imports `inventory_router`; line `:877` calls `app.include_router(inventory_router)`. The new `purchasing_router` must follow the same import+register pattern, placed immediately after the `returns_rma_router` registration at line `:878`.

## 3. Data Model

### 3.1 Overview

Four new DynamoDB tables, all declared immediately after the `returns` block at `scripts/local-ddb-init.py:2492`. Each uses `_resolve_table_name(S.<name>, "<default>")`. With `PURCHASING_SCM_ENABLED=false` all tables exist but receive zero writes and their handles are simply idle.

### 3.2 `suppliers` table

Stores vendor party records. Self-contained within this module; forward-compatible with the Party Manager (`PARTY_CRM_TICKETS.md`/PTY) by using a stable `supplier_id` that PTY can reference.

| Attribute | Type | Notes |
|---|---|---|
| `supplier_id` (PK) | S | `sha256(f"supplier:{user_sub}:{name}")[:32]` — deterministic idempotency |
| `sk` (SK) | S | Always `"META"` |
| `name` | S | Canonical display name |
| `status` | S | `active` \| `inactive` |
| `email` | S | (optional) primary contact email |
| `phone` | S | (optional) E.164 phone |
| `address` | M | Nested map: `{line1, city, state, postal_code, country}` |
| `default_currency` | S | ISO 4217 (e.g. `"USD"`) |
| `payment_terms_days` | N | Net-days (e.g. 30) |
| `created_by` | S | `user_sub` of creator |
| `created_at` | N | `now_ts()` integer |
| `updated_at` | N | `now_ts()` integer |

**GSIs:**

| Index | PK | SK | attr_types |
|---|---|---|---|
| `GSI_STATUS` | `status` (S) | `created_at` (N) | `{"created_at": "N"}` |

`GSI_STATUS` enables `list_suppliers(status="active")` via a paginated query loop (mirroring `inventory.list_low_stock` at `inventory.py:318`).

### 3.4 `purchase_orders` table

Single-table layout: one header row (`SK=META`) plus N line rows (`SK=LINE#{n}`) per PO. Mirrors `commerce_order_service` header+items pattern (`commerce_order_service.py:85–103`).

**Header row (`SK=META`):**

| Attribute | Type | Notes |
|---|---|---|
| `po_id` (PK) | S | `sha256(correlation_id)[:32]` |
| `sk` (SK) | S | `"META"` |
| `supplier_id` | S | FK to `suppliers` |
| `status` | S | PO lifecycle state (see Section 5.1) |
| `currency` | S | ISO 4217 |
| `subtotal_cents` | N | Sum of all `line_total_cents` |
| `expected_delivery_date` | S | ISO date string (optional) |
| `created_by` | S | `user_sub` |
| `approved_by` | S | `user_sub` (set on approval) |
| `approved_at` | N | `now_ts()` integer |
| `rejected_by` | S | `user_sub` (set on rejection) |
| `rejected_reason` | S | Free-text |
| `correlation_id` | S | Caller-supplied idempotency key |
| `ledger_entry_sk` | S | Billing ledger SK (set by PUR-009 on payment) |
| `paid_at` | N | `now_ts()` integer |
| `created_at` | N | `now_ts()` integer |
| `updated_at` | N | `now_ts()` integer |

**Line row (`SK=LINE#{n}`, 1-based):**

| Attribute | Type | Notes |
|---|---|---|
| `po_id` (PK) | S | Same as header |
| `sk` (SK) | S | `LINE#{n}` (n zero-padded to 6 digits for lexicographic sort: `LINE#000001`) |
| `line_no` | N | 1-based integer |
| `sku` | S | |
| `quantity_ordered` | N | |
| `quantity_received` | N | Starts 0; incremented by receipts (PUR-008) |
| `unit_cost_cents` | N | Defaulted from `supplier_products` if omitted at creation |
| `line_total_cents` | N | `quantity_ordered * unit_cost_cents` |

**GSIs on `purchase_orders`:**

| Index | PK | SK | attr_types |
|---|---|---|---|
| `GSI_SUPPLIER` | `supplier_id` (S) | `created_at` (N) | `{"created_at": "N"}` |
| `GSI_STATUS` | `status` (S) | `created_at` (N) | `{"created_at": "N"}` |

Both GSIs are populated only on header rows (`SK=META`); line rows carry no GSI attributes. `GSI_SUPPLIER` drives `list_purchase_orders(supplier_id=...)` and `GSI_STATUS` drives the approval/receiving queues (`list_purchase_orders(status="submitted")`).

**`TableDef` snippet:**
```python

    "sk",

    ],
    attr_types={"created_at": "N"},
),
```

### 3.5 `po_receipts` table

Each receiving event is a separate row keyed by `po_id` (partition) and `RECEIPT#{receipt_id}` (sort). This allows multiple partial receipts against the same PO while supporting idempotent lookup by `receipt_id`.

| Attribute | Type | Notes |
|---|---|---|
| `po_id` (PK) | S | FK to `purchase_orders` header |
| `sk` (SK) | S | `RECEIPT#{receipt_id}` |
| `receipt_id` | S | `sha256(receipt_correlation_id)[:32]` |
| `received_by` | S | `user_sub` |
| `lines` | L | List of `{line_no, quantity_received}` maps |
| `created_at` | N | `now_ts()` integer |

**GSIs:**

| Index | PK | SK | attr_types |
|---|---|---|---|
| `GSI_RECEIPT` | `receipt_id` (S) | — | none |

`GSI_RECEIPT` enables `get_receipt_by_id(receipt_id)` for idempotent replay detection (check whether a receipt already exists before processing).

**`TableDef` snippet:**
```python
TableDef(
    _resolve_table_name(S.po_receipts_table_name, "po_receipts"),
    "po_id",
    "sk",
    gsi=[
        {"index_name": "GSI_RECEIPT", "partition_key": "receipt_id"},
    ],
),
```

## 5. Detailed Behavior & Edge Cases

### 5.1 PO lifecycle state machine

The seven primary statuses plus two side-exits form the following directed graph. The guard function `transition_po` enforces this via `ConditionExpression="#status = :expected"` (mirroring `inventory._close_reservation` at `inventory.py:434`).

```
draft ──► submitted ──► approved ──► ordered ──► partially_received ──► received ──► closed
           │              │              │              │
           └──► rejected  └──► rejected  └──► cancelled └──► cancelled
 draft ──────────────────────────────────────────────────────────────────► cancelled
 submitted ──────────────────────────────────────────────────────────────► cancelled
 approved  ──────────────────────────────────────────────────────────────► cancelled
```

**Legal transitions table:**

| From | To | Actor constraint |
|---|---|---|
| `draft` | `submitted` | any purchasing staff |
| `draft` | `cancelled` | any purchasing staff |
| `submitted` | `approved` | admin/root only |
| `submitted` | `rejected` | admin/root only |
| `submitted` | `cancelled` | any purchasing staff |
| `approved` | `ordered` | any purchasing staff (after sending order to supplier) |
| `approved` | `rejected` | admin/root only |
| `approved` | `cancelled` | any purchasing staff |
| `ordered` | `partially_received` | system (auto, first partial receipt) |
| `ordered` | `received` | system (auto, full receipt) |
| `ordered` | `cancelled` | admin/root only — no quantity received yet |
| `partially_received` | `received` | system (auto, final receipt completes all lines) |
| `received` | `closed` | system (auto, after AP payable posted) |

**Illegal/blocked:**
- `ordered → cancelled` when any line has `quantity_received > 0` → HTTP 422 (not 409; it is a validation failure, not a concurrency conflict).
- Any transition not in the table above → HTTP 409 with `code="po_invalid_transition"`.
- Replaying an already-applied transition: `ConditionalCheckFailedException` → read current status; if already equal to `target_status`, treat as no-op success (HTTP 200). If not equal, the race was lost — return HTTP 409.

**`ordered` status**: explicit acknowledgment that the purchase order has been issued to the supplier. This is a manual step by purchasing staff between `approved` and receiving. The `ordered` → `partially_received` / `received` transitions are triggered automatically by the receiving service (PUR-008), not manually.

### 5.2 Receiving → inventory increment

`receive_po` in `app/services/po_receiving.py` executes the following sequence for each call:

1. Look up the receipt by `receipt_id` via `GSI_RECEIPT` — if found, return existing receipt (idempotent no-op).
2. Validate PO is in `approved`, `ordered`, or `partially_received` — else HTTP 409.
3. For each line in the receipt payload:
   - Read the PO line row (`SK=LINE#{n}`).
   - Compute new `quantity_received = existing + quantity`. If this would exceed `quantity_ordered` → HTTP 422 `"over_receive"`.
   - If `S.inventory_reservations_enabled` is `True`: call `inventory.adjust(sku, +quantity, reason="po_receipt", user_sub=actor_sub)`. If `inventory_reservations_enabled` is `False`: skip the inventory call (still record the receipt and advance `quantity_received`).
   - Update line row `quantity_received` via `update_item` with `ADD quantity_received :qty`.
4. Write the `po_receipts` row (`SK=RECEIPT#{receipt_id}`).
5. Recompute PO header status:
   - All lines: `quantity_received >= quantity_ordered` → `received`.
   - Some but not all → `partially_received`.
   - None changed (no-op replay) → leave `ordered`.
6. Update PO header `status` and `updated_at` via conditional `update_item`.
7. Emit `audit_event("po_received", actor_sub, po_id=..., receipt_id=...)`.

### 5.3 AP payable linkage (PUR-009 pre-design)

On a PO reaching `received` status, PUR-009 creates a supplier payable using `billing_shared.new_ledger_entry` at `app/services/billing_shared.py:224`:

```python
sk, item = new_ledger_entry(
    key_name="pk",
    key_value=f"SUPPLIER#{supplier_id}",   # supplier's billing partition
    entry_type="ap_payable",
    amount_cents=po["subtotal_cents"],
    state="pending",
    reason="supplier_payment",
    extra={
        "provider": "internal",            # FIN-013 attribution (no payment network)
        "po_id": po_id,
        "supplier_id": supplier_id,
    },
)
T.billing.put_item(Item=item)
```

The correlation guarantee: the `po_id` is stored in `extra` so the AP subledger (OFB-015) can join payables back to POs. Re-posting uses a `attribute_not_exists(pk)` conditional (or a deterministic `entry_id` derived from `sha256(po_id)[:16]`) so exactly one payable per PO is written. `settle_or_reverse_ledger` at `billing_shared.py:262` transitions the payable from `pending` to `settled` when the supplier is actually paid. The `ledger_entry_sk` is written back onto the PO header so `GET /purchase-orders/{po_id}` can return it.

### 5.4 Reorder suggestion algorithm

`generate_reorder_suggestions()` in `app/services/reorder_suggestions.py`:

1. Call `inventory.list_low_stock("low_stock")` and `inventory.list_low_stock("out_of_stock")` — both paginated loops against `GSI_AVAILABLE` (per `inventory.py:318`).
2. For each low/OOS SKU:
   - Call `supplier_products.list_suppliers_for_sku(sku)` (cheapest first via `GSI_SKU`).
   - If no results: append to `no_supplier_skus` list (surfaces as a warning, not an error).
   - Else: pick the first (cheapest/preferred) supplier.
   - Compute `gap = max(reorder_point - available, 0)`.
   - `suggested_qty = max(gap, MOQ)` rounded up to the nearest MOQ multiple: `math.ceil(gap / MOQ) * MOQ` if `gap > 0` else `MOQ`.
3. Group results by supplier.
4. Return `ReorderSuggestionListOut`.

`create_purchase_order_from_suggestion(supplier_id, skus, user_sub)` materializes a `draft` PO via `create_purchase_order` with `correlation_id = sha256(f"reorder:{supplier_id}:{sorted_skus_str}")[:32]` so repeated calls for the same set of SKUs from the same supplier are idempotent.

### 5.5 Supplier deactivation

`set_supplier_status(supplier_id, "inactive")` updates `status` and `updated_at` on the supplier header. It does NOT cascade to `supplier_products` rows (those remain; they become inaccessible from the active supplier list but can still be retrieved directly). Open POs against an inactive supplier are not automatically cancelled — purchasing staff must manually cancel or complete them. This matches the "preserve history" requirement.

### 5.6 SKU validation in supplier-product upsert

`upsert_supplier_product` must validate the SKU before writing. It calls `inventory.get_inventory(sku)` (returns `None` if absent) first; if `None` it falls back to a catalog lookup against `T.catalog` (handle at `app/core/tables.py:99`; table name configured via `S.catalog_table_name`, default `"shopping_catalog"`, `app/core/settings.py:832`). Note that catalog items use `item_id` as their primary key, not `sku`; the fallback scan must match on the `item_id` field or be omitted in favour of a registry-only approach. If neither finds the SKU → HTTP 422 `"sku_not_found"`. This validation is skipped when `purchasing_scm_enabled=False` (the function raises 404 before reaching it).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity**: No `dev_mode` branch in any purchasing service function. The DynamoDB code path is identical in dev (moto/local DDB) and prod (real DDB). The `inventory.adjust` call in `receive_po` goes through the existing `T.inventory` handle, which is moto-backed in dev without any branching.

**Idempotency guarantees by entity:**
- `create_supplier`: same `(user_sub, name)` → same `supplier_id` via `sha256`. Second `put_item` overwrites silently (DynamoDB put is idempotent for the same PK+SK).
- `create_purchase_order`: same `correlation_id` → same `po_id`. Second write overwrites the header (idempotent). Line rows are keyed by `(po_id, LINE#{n})`; the same loop produces the same SK values. Idempotent under retry.
- `receive_po`: `receipt_id = sha256(receipt_correlation_id)[:32]`. First thing in the function: query `GSI_RECEIPT` for `receipt_id`; if found, return existing receipt without touching inventory or PO lines.
- `transition_po`: `ConditionExpression="#status = :expected"`. If the PO is already in `target_status` (replay after connection-lost success), the conditional fails, the function reads the current header, finds it already at `target_status`, and returns 200.
- AP payable (PUR-009): deterministic `entry_id = sha256(po_id)[:16]` embedded in the SK. Conditional `attribute_not_exists(sk)` prevents double-posting.

**Security / access control:**
- All purchasing endpoints require `require_admin_or_root_csrf`, enforcing both the role check and CSRF for cookie-auth sessions. There are no customer-facing purchasing endpoints.
- Supplier records do not contain secrets; no KMS encryption needed.
- `rejected_reason` and `decision_note` fields are free-text and sanitized by Pydantic `max_length` constraints.
- No purchasing endpoint is added to `API_KEY_ROUTE_EXEMPTIONS`; purchasing is not part of the partner API surface.

**No money fork**: `po_receiving.py` calls `inventory.adjust` for stock changes and never writes to `T.billing`. `billing_shared.new_ledger_entry` is the only write path for AP payables (PUR-009). `settle_or_reverse_ledger` is the only path for marking payables settled. Zero new Stripe/PayPal/CCBill calls.

## 10. Open Questions / Assumptions

1. **Assumption**: The `purchase_orders` table uses a single-table layout with `SK=META` for headers and `SK=LINE#{n}` for lines. This means `get_item(Key={"po_id": po_id, "sk": "META"})` is the canonical header fetch. All callers must include the SK; a bare `get_item(Key={"po_id": po_id})` will silently return nothing once the table has a sort key.

2. **Assumption**: AP payables are written to the existing `billing` table under a `SUPPLIER#{supplier_id}` partition key. This co-locates supplier payables with customer billing entries in one table. If the AP subledger (OFB-015) requires a dedicated `accounts_payable` table for isolation (e.g. for access-control reasons), this decision must be revisited in PUR-009.

3. **Open question**: Should the `ordered` status be required, or should `approved` transition directly to `partially_received` / `received` when a receipt arrives? The current design includes `ordered` as a distinct staff-driven step (issuing the PO to the supplier). If the workflow is automated (EDI, API order placement), `ordered` may be skipped. Confirm with the finance/ops team before PUR-007 implementation.

4. **Assumption**: `receipt_correlation_id` is caller-supplied for idempotency. If the caller does not supply one, a fresh UUID is generated and the receipt is not replay-safe. The API will document this; callers should always supply a stable `receipt_correlation_id` when retry is possible.

5. **Assumption**: The reorder suggestion quantity formula is `max(ceil((reorder_point - available) / MOQ) * MOQ, MOQ)`. Edge cases: `available == reorder_point` → `gap = 0` → `suggested_qty = MOQ` (one MOQ of stock). `available > reorder_point` → a SKU at `low_stock` status by the inventory `_status_for` function (which checks `available <= reorder_point`, per `inventory.py:87`) cannot have `available > reorder_point`. Confirm the formula with operations before PUR-011.

6. **Open question**: Should `partially_received` be a separate GSI partition key value in `GSI_STATUS`, or should the receiving queue query for both `ordered` and `partially_received`? The current design uses a single `GSI_STATUS` index keyed on `status`, so the receiving queue must issue two separate queries (one per status) or use a scan with filter expression. A dedicated GSI partition `RECEIVING` (covering both) would simplify the query but adds complexity. Defer decision to PUR-010.

7. **Assumption**: Supplier records in this module are forward-compatible with the Party Manager (`PARTY_CRM_TICKETS.md`/PTY). The `supplier_id` is a stable sha256-derived identifier. PTY may later reference this `supplier_id` in a `party_roles` table without modifying the `suppliers` table itself.

8. **Assumption**: The `ordered` → `cancelled` transition is blocked once any quantity has been received (HTTP 422). The `partially_received` → `cancelled` path is simply not in the legal transitions table. If a business need arises to cancel a partially-received PO, a dedicated `cancel_with_restock` operation (which reverses the inventory adjustments) would be required — that is out of scope for this milestone.

9. **Open question**: Should supplier payment (PUR-009) write the ledger entry to `T.billing` under `pk = SUPPLIER#{supplier_id}` (as proposed in Section 5.3) or under the purchasing staff member's `pk = USER#{user_sub}`? Confirm the AP subledger ownership model with the finance team before PUR-009 implementation.
