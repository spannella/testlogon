# ORD-008 — Order adjustments (discount/surcharge/tax/shipping lines)

**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days
**Milestone:** 3 — Adjustments & ship groups

---

## 1. Summary & Goal

ORD-008 implements adjustment management on the order record: the ability to
attach one or more signed money lines (discounts, surcharges, tax, shipping,
promotions) to an order and have those lines roll up into a single
`adjusted_amount_cents` attribute on the ORDER-SK header. The base line total
(`amount_cents`, computed at `app/services/commerce_order_service.py:69`) is
never mutated; adjustments are stored as separate `ADJ#` SK rows in the single
`orders` table (schema established by ORD-003) and their net effect is derived
on every read/write.

The deliverable is a new module `app/services/order_adjustments.py` exporting
three public functions:

- `add_adjustment(order_id, adj_in, *, actor)` — validates state gate and
  currency, writes one `ADJ#{adjustment_id}` row, recomputes and updates
  `adjusted_amount_cents` on the header, emits an audit event.
- `remove_adjustment(order_id, adjustment_id, *, actor)` — validates state
  gate, deletes the `ADJ#` row, recomputes and updates `adjusted_amount_cents`.
- `list_adjustments(order_id)` — queries all `ADJ#` rows under the order and
  returns them as `OrderAdjustment` instances.

A fourth helper `compute_adjusted_amount(order_id)` calculates the net total
from the current header `amount_cents` plus the signed contribution of every
`ADJ#` row; this helper is consumed internally and exported for ORD-010 (which
needs the adjusted total when computing refund amounts on cancel/return).

All behaviour is gated behind `S.order_lifecycle_enabled` (default `false`).
With the flag off, no call site imports or invokes this service, and the
`orders` table receives zero new writes.

## 2. Context & Current State

### 2.1 Base `amount_cents` established at order creation

`CommerceOrderService.create_order` at `app/services/commerce_order_service.py:39`
computes:

```python
amount_cents = sum(self._line_amount_cents(it) for it in parsed)   # :69
```

and writes it to the ORDER header (`app/services/commerce_order_service.py:81`):

```python
"amount_cents": int(amount_cents),
```

This value represents the raw sum of all line-item prices (quantity × unit
price) and is never modified after creation. ORD-008 does not touch this field
or any `order_items` rows.

### 2.2 `_line_amount_cents` money convention

`app/services/commerce_order_service.py:27` returns a non-negative `int`
derived from `pricing_ref.unit_price_cents`, `pricing_ref.amount_cents`, or
`pricing_ref.price_cents`, guarded by `max(0, ...)`. The money convention for
the platform is: `amount_cents` is always a non-negative integer; sign
semantics are carried by a separate `type`/`reason` field, not by negative
values. ORD-008 follows this convention for `OrderAdjustment.amount_cents`
(always `>= 0`, per ORD-004); the adjustment type (`discount`, `promotion`) is
what signals subtraction.

### 2.5 `lifecycle_status` pre-shipped gate

ORD-005 establishes the `TRANSITIONS` graph in `app/services/order_lifecycle.py`.
The pre-shipped states (those where adjustments are allowed) are:
`created`, `approved`, `allocated`, `picking`, `packed`, `held`, `backorder`.
The post-shipped or terminal states where adjustments are **rejected** are:
`shipped`, `completed`, `cancelled`, `returned`.

in `order_adjustments.py` (a frozenset), not by calling `transition_order`.
This keeps the adjustment service independent of the state-machine service and
avoids circular imports.

## 3. Data Model

ORD-008 introduces no new DynamoDB tables or GSIs — those are all established
by ORD-003. It only writes `ADJ#`-SK rows and updates the `adjusted_amount_cents`
attribute on the ORDER-SK header within the existing `orders` table.

### 3.1 ADJ row DynamoDB item shape

```
Table: orders   (env ORDERS_TABLE_NAME, default "orders")
PK:    order_id (S)
SK:    "ADJ#{adjustment_id}"   (adjustment_id = uuid4().hex, 32 hex chars)
```

Attributes written by `add_adjustment`:

| Attribute | DDB type | Value |
|---|---|---|
| `order_id` | S | The order's 32-hex order_id |
| `sk` | S | `ADJ#{adjustment_id}` |
| `adjustment_id` | S | Same as embedded in sk |
| `type` | S | `adj_in.adj_type.value` |
| `amount_cents` | N | `adj_in.amount_cents` (non-negative int) |
| `currency` | S | `adj_in.currency.upper()` |
| `label` | S | `adj_in.label` (max 255 chars) |
| `taxable` | BOOL | `adj_in.taxable` |
| `source_rule_ref` | S | `adj_in.source_rule_ref` (omitted if `None`) |
| `created_at` | S | `_now_iso()` |
| `created_by` | S | `actor` |

No new DDB table, no new GSI, no new `attr_types` declaration in
`scripts/local-ddb-init.py`. The `orders` table already carries the `ADJ#`
SK partition after ORD-003.

### 3.2 ORDER-SK header update — `adjusted_amount_cents`

After every `add_adjustment` or `remove_adjustment` call, the ORDER-SK header
row is updated via:

```python
T.orders.update_item(
    Key={"order_id": order_id, "sk": "ORDER"},
    UpdateExpression="SET adjusted_amount_cents = :v, updated_at = :ts",
    ExpressionAttributeValues={
        ":v": recomputed_total,
        ":ts": _now_iso(),
    },
)
```

`adjusted_amount_cents` is a standalone attribute (`N`) on the ORDER-SK row,
parallel to `amount_cents`. The base `amount_cents` is never modified.
`adjusted_amount_cents` defaults to `amount_cents` when no adjustments exist
(the first successful `add_adjustment` writes the initial value). On
`remove_adjustment` of the last adjustment, `adjusted_amount_cents` is set
back to the base `amount_cents`.

### 3.3 Sign convention in `_compute_net_total`

```python
_NEGATIVE_TYPES = frozenset({"discount", "promotion"})

def _compute_net_total(base_amount_cents: int, adj_rows: List[Dict]) -> int:
    total = base_amount_cents
    for row in adj_rows:
        amount = int(row.get("amount_cents") or 0)
        if row.get("type") in _NEGATIVE_TYPES:
            total -= amount
        else:
            total += amount
    return max(0, total)   # floor at 0; no negative totals
```

The floor `max(0, ...)` prevents `adjusted_amount_cents` going negative (e.g.
a discount larger than the base total). This matches the `max(0, ...)` guard
in `app/services/commerce_order_service.py:31`.

#### 4.1.1 Exception classes

> **CORRECTION**: ORD-011 (`docs/ofbiz/specs/ORD-011.md:297,299`) catches
> `AdjustmentStateError` and `CurrencyMismatchError` from this module — not
> `AdjustmentNotAllowedError`/`AdjustmentCurrencyError`. The implementation
> **must** use the names below so the ORD-011 router's `except` clauses match.

```python
class AdjustmentStateError(Exception):
    """Order is in a post-shipped or terminal state; adjustments are rejected."""
    def __init__(self, order_id: str, lifecycle_status: str) -> None:
        super().__init__(
            f"Adjustments not allowed on order {order_id} "
            f"in status {lifecycle_status!r}"
        )
        self.order_id = order_id
        self.lifecycle_status = lifecycle_status


class CurrencyMismatchError(Exception):
    """Adjustment currency does not match the order currency."""
    def __init__(self, order_currency: str, adj_currency: str) -> None:
        super().__init__(
            f"Adjustment currency {adj_currency!r} does not match "
            f"order currency {order_currency!r}"
        )


class AdjustmentNotFoundError(Exception):
    """The adjustment_id does not exist under this order."""
    def __init__(self, order_id: str, adjustment_id: str) -> None:
        super().__init__(
            f"Adjustment {adjustment_id!r} not found on order {order_id!r}"
        )
```

The ORD-011 router maps these to
(`docs/ofbiz/specs/ORD-011.md:297–300,322`):
- `AdjustmentStateError` → HTTP 409 (`code="adjustment_state_error"`)
- `CurrencyMismatchError` → HTTP 422 (`code="currency_mismatch"`)
- `AdjustmentNotFoundError` → HTTP 404 (`code="adjustment_not_found"`)

Any `OrderNotFoundError` from `order_store.get_order_header` propagates as-is
and the router maps it to HTTP 404.

#### 4.1.9 Public function: `add_adjustment`

> **CORRECTION**: ORD-011 calls `add_adjustment(order_id, body, actor=user.sub)`
> where `body` is `OrderAdjustmentIn` (defined by ORD-011, not `OrderAdjustment`).
> The parameter type is `OrderAdjustmentIn` — it has the same fields as
> `OrderAdjustment` except it lacks `adjustment_id` and `created_at`.
> `adjustment_id` is always generated inside the service.

```python
def add_adjustment(
    order_id: str,
    adj_in: "OrderAdjustmentIn",   # app.models.OrderAdjustmentIn (ORD-011)
    *,
    actor: str,
) -> OrderAdjustment:
    """
    Add one adjustment line to a pre-shipped order.

    Parameters
    ----------
    order_id : str
        The SHA-256-derived order ID (32 hex chars).
    adj_in : OrderAdjustmentIn
        The adjustment to apply (router request body). ``amount_cents``
        must be >= 0. ``currency`` must match the order currency.
        ``adjustment_id`` is always auto-generated (``uuid4().hex``).
    actor : str
        The user_sub or ``"system"`` applying the adjustment; written to
        the ADJ row as ``created_by``.

    Returns
    -------
    OrderAdjustment
        The persisted adjustment with ``adjustment_id`` and ``created_at``
        populated.

    Raises
    ------
    OrderNotFoundError      — order_id not found.
    AdjustmentStateError    — order is shipped/completed/cancelled/returned.
    CurrencyMismatchError   — adj_in.currency != order.currency.
    """
    header = _get_order_or_raise(order_id)
    _assert_adjustment_allowed(header)
    _assert_currency_match(header, adj_in.currency)

    adj_id = uuid.uuid4().hex
    sk_val = f"ADJ#{adj_id}"
    now_str = _now_iso()
    now_int = now_ts()

    item: Dict[str, Any] = {
        "order_id": order_id,
        "sk": sk_val,
        "adjustment_id": adj_id,
        "type": adj_in.adj_type.value,
        "amount_cents": adj_in.amount_cents,
        "currency": adj_in.currency.upper(),
        "label": adj_in.label or "",
        "taxable": adj_in.taxable,
        "created_at": now_str,
        "created_by": actor,
    }
    if adj_in.source_rule_ref:
        item["source_rule_ref"] = adj_in.source_rule_ref

    T.orders.put_item(Item=item)

    # Recompute adjusted total from all ADJ rows (including the new one).
    all_adjs = query_order_rows(order_id, sk_prefix="ADJ#")
    base = int(header.get("amount_cents") or 0)
    new_total = _compute_net_total(base, all_adjs)
    _update_header_total(order_id, new_total)

    try:
        audit_event(
            "order_adjustment_added",
            actor,
            None,
            outcome="success",
            order_id=order_id,
            adjustment_id=adj_id,
            adj_type=adj_in.adj_type.value,
            amount_cents=adj_in.amount_cents,
            currency=adj_in.currency.upper(),
            adjusted_amount_cents=new_total,
        )
    except Exception:
        pass

    return OrderAdjustment(
        adjustment_id=adj_id,
        adj_type=adj_in.adj_type,
        amount_cents=adj_in.amount_cents,
        currency=adj_in.currency.upper(),
        label=adj_in.label or "",
        taxable=adj_in.taxable,
        source_rule_ref=adj_in.source_rule_ref,
        created_at=now_int,
    )
```

#### 4.1.10 Public function: `remove_adjustment`

```python
def remove_adjustment(
    order_id: str,
    adjustment_id: str,
    *,
    actor: str,
) -> None:
    """
    Remove one adjustment line from a pre-shipped order and recompute total.

    Raises
    ------
    OrderNotFoundError      — order_id not found.
    AdjustmentStateError    — order is shipped/completed/cancelled/returned.
    AdjustmentNotFoundError — adjustment_id not found under this order.
    """
    header = _get_order_or_raise(order_id)
    _assert_adjustment_allowed(header)

    sk_val = f"ADJ#{adjustment_id}"
    existing = T.orders.get_item(
        Key={"order_id": order_id, "sk": sk_val}
    ).get("Item")
    if not existing:
        raise AdjustmentNotFoundError(order_id, adjustment_id)

    T.orders.delete_item(Key={"order_id": order_id, "sk": sk_val})

    # Recompute from remaining ADJ rows.
    remaining = query_order_rows(order_id, sk_prefix="ADJ#")
    base = int(header.get("amount_cents") or 0)
    new_total = _compute_net_total(base, remaining)
    _update_header_total(order_id, new_total)

    try:
        audit_event(
            "order_adjustment_removed",
            actor,
            None,
            outcome="success",
            order_id=order_id,
            adjustment_id=adjustment_id,
            adjusted_amount_cents=new_total,
        )
    except Exception:
        pass
```

#### 4.1.11 Public function: `list_adjustments`

```python
def list_adjustments(order_id: str) -> List[OrderAdjustment]:
    """
    Return all adjustment rows for an order, sorted by creation time ascending.

    Raises
    ------
    OrderNotFoundError — order_id not found.
    """
    _get_order_or_raise(order_id)   # validates existence
    rows = query_order_rows(order_id, sk_prefix="ADJ#")
    rows.sort(key=lambda r: str(r.get("created_at") or ""))
    result = []
    for row in rows:
        try:
            result.append(OrderAdjustment(
                adjustment_id=str(row.get("adjustment_id") or ""),
                adj_type=OrderAdjustmentType(str(row.get("type") or "")),
                amount_cents=int(row.get("amount_cents") or 0),
                currency=str(row.get("currency") or "USD"),
                label=str(row.get("label") or ""),
                taxable=bool(row.get("taxable", False)),
                source_rule_ref=row.get("source_rule_ref"),
                created_at=0,
            ))
        except (ValueError, TypeError):
            continue   # skip rows with stale/unknown type values
    return result
```

#### 4.1.12 Public function: `compute_adjusted_amount`

```python
def compute_adjusted_amount(order_id: str) -> int:
    """
    Return the current adjusted total without making any writes.
    Returns the base ``amount_cents`` when no ADJ rows exist.

    Used by ORD-010 to compute the refund amount on cancel/return.
    """
    header = _get_order_or_raise(order_id)
    base = int(header.get("amount_cents") or 0)
    # Prefer the pre-computed attribute if present and consistent.
    if header.get("adjusted_amount_cents") is not None:
        return int(header["adjusted_amount_cents"])
    # Fallback: recompute from ADJ rows (first call before any adjustment).
    adj_rows = query_order_rows(order_id, sk_prefix="ADJ#")
    return _compute_net_total(base, adj_rows)
```

### 4.2 Router wiring (in ORD-011 router)

ORD-008 is a service-only ticket. The HTTP endpoints are owned by the ORD-011

```python

# Input model: OrderAdjustmentIn from app/models.py (defined by ORD-011:123)

    add_adjustment, remove_adjustment, list_adjustments,
    AdjustmentStateError, CurrencyMismatchError, AdjustmentNotFoundError,

@router.post("/{order_id}/adjustments", response_model=OrderAdjustment)

    body: OrderAdjustmentIn,
    request: Request,
```

## 5. Detailed Behavior & Edge Cases

### 5.1 State-gate: `lifecycle_status` absent

If an order has no `lifecycle_status` attribute (written before ORD-007 ran
the initialisation hook), `_assert_adjustment_allowed` receives `ls = ""`.
The empty string is not in `_ADJUSTMENT_ALLOWED_STATUSES`, so
`AdjustmentStateError` is raised with message `"(uninitialized)"`. This
prevents applying adjustments to orders that have not been enrolled in the
lifecycle state machine.

### 5.2 Currency comparison is case-insensitive and normalised to uppercase

`_assert_currency_match` normalises both `order.currency` and `adj.currency`
to `.upper()` before comparing. The order header always stores currency
in uppercase (per `commerce_order_service.py:24`, which calls `.upper()`).
An adjustment submitted with `currency="usd"` will pass the check against an
order with `currency="USD"`.

### 5.3 Zero-amount adjustments are accepted

`amount_cents=0` is valid (`ge=0` in `OrderAdjustment`). A zero-amount
adjustment might represent a free shipping override, a placeholder for a
pending tax calculation, or a system marker. The net total is unchanged.
No special handling is needed.

### 5.4 Discount larger than base total

`_compute_net_total` applies `max(0, total)`. If the sum of all discounts and
promotions exceeds `amount_cents`, `adjusted_amount_cents` is set to `0` (not
negative). The ORD-011 router should surface a warning in this case if the
caller is a human operator, but the service does not reject the write — the
business may legitimately grant a 100% discount.

### 5.5 Race condition on simultaneous `add_adjustment` calls

`add_adjustment` does a read (`query_order_rows`) then a write
(`_update_header_total`) without a conditional expression on `adjusted_amount_cents`.
Two concurrent `add_adjustment` calls on the same order can produce a last-write-wins
race on `adjusted_amount_cents` (one thread's recomputed total overwrites the
other's). Given that adjustments are admin-driven operations (ORD-011 admin
auth), concurrent calls to the same order are unlikely in practice. If
stronger consistency is needed, a future pass can add a conditional expression
on the UPDATE using an `adjustment_count` counter or an `updated_ts` guard.

### 5.6 `query_order_rows` pagination

`query_order_rows` from ORD-003 (`app/services/order_store.py`) uses
`KeyConditionExpression = "order_id = :pk AND begins_with(sk, :pfx)"`.
DynamoDB returns up to 1 MB of results per page; with up to ~100 adjustment
rows expected per order, a single page suffices in all practical cases. If
ORD-009's ship-group data is co-located in the same PK partition and creates
many rows, the `sk_prefix="ADJ#"` filter at the query level (not at the
FilterExpression level) ensures only ADJ rows are returned and counted.
If ORD-008 encounters more than ~3000 ADJ rows in the future, loop-until-
`LastEvaluatedKey` must be added.

### 5.7 Idempotency via `adjustment_id`

`add_adjustment` accepts an optional `adjustment_id` in `adj_in`. If the
caller supplies one (e.g. a deterministic ID derived from a pricing-rule
trigger), a DDB `put_item` with a duplicate `adjustment_id` will silently
overwrite the existing ADJ row. For true create-only idempotency, the caller
must use a `ConditionExpression="attribute_not_exists(sk)"`. The ORD-011 router
always passes `OrderAdjustmentIn` (no `adjustment_id` field), so `add_adjustment`
always generates a fresh `uuid4().hex` — API-driven adjustments never accidentally
collide.

### 5.8 Interaction with ORD-010 cancel/return refunds

ORD-010 (`cancel_order`, `return_order`) calls `compute_adjusted_amount(order_id)`
to determine the effective refund amount. If the order has an
`adjusted_amount_cents` attribute on its header, that value is used directly.
If not (no adjustments were ever applied), the base `amount_cents` is used.
This means the refund always reflects the most recently computed adjusted
total, accounting for any discounts or surcharges in force at the time of
cancel/return.

### 5.9 `list_adjustments` skips rows with stale adj_type values

If a future schema evolution deprecates an `adj_type` string value, the
`OrderAdjustmentType(str(...))` coercion in `list_adjustments` will raise
`ValueError` for that row. The `try/except (ValueError, TypeError): continue`
guard ensures backward-compatible reads — stale rows are silently omitted
from the list rather than raising 500. A monitoring alert (out of scope for
this ticket) should fire if `continue` is hit in prod.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

`order_adjustments.py` contains no `if S.dev_mode` branch. The DDB writes,
state-gate check, currency validation, audit event, and total recomputation
are identical in dev (DynamoDB Local, port 8001, `T.orders` wired from
`S.orders_table_name` at `app/core/tables.py:381` [VERIFIED]) and prod (real DynamoDB).
The `audit_event` call resolves to `app/services/alerts.py:644` [VERIFIED] in
both envs; in dev it writes to DynamoDB Local, in prod to real DynamoDB. No mock branch.

### 7.2 Idempotency

**`remove_adjustment`**: The delete is idempotent if the caller retries after
a network timeout. If the `ADJ#` row is already absent (the first attempt
succeeded but the response was lost), the `get_item` check in `remove_adjustment`
raises `AdjustmentNotFoundError` — and the router returns 404. Callers should
treat 404 on a retry as a successful removal (the goal state was reached).

**`add_adjustment`**: Not idempotent — each call generates a fresh `uuid4().hex`
and writes a new row. Callers that need exactly-once semantics can extend
`OrderAdjustmentIn` with an optional `idempotency_key` field in a follow-up,
and add a `ConditionExpression="attribute_not_exists(sk)"` guard in
`add_adjustment`. The ORD-011 router does not expose such a key today.

### 7.3 Security

**Ownership / admin enforcement**: `order_adjustments.py` accepts an `actor`
parameter and does not verify that `actor` is an admin. Ownership and role
checks are the responsibility of the ORD-011 router (requiring `Role.ADMIN`
or `Role.ROOT` for POST/DELETE). This is consistent with how
`transition_order` in `order_lifecycle.py` defers ownership checks to the
router (per ORD-005 Section 7.3).

**No money-path fork**: The adjustment service only writes metadata rows and
updates a derived counter attribute. No billing ledger entry is written here.
`adjusted_amount_cents` is an informational field used to compute refund
amounts in ORD-010; the actual billing debit is written by ORD-010 via the
existing `new_ledger_entry` path (`app/services/billing_shared.py:224`)
[VERIFIED] and `refund_payment` (`app/routers/billing.py:1287`) [VERIFIED —
`refund_payment` is a router-layer function in `billing.py`, not in
`billing_shared.py`].

**DynamoDB injection**: All attribute values are passed via
`ExpressionAttributeValues`; no user-supplied string is interpolated into
`UpdateExpression` or `KeyConditionExpression` strings.

**`label` and `source_rule_ref` sanitisation**: Both are bounded by Pydantic
`Field(max_length=...)` at parse time. Downstream display in the admin UI
should HTML-escape `label` (React auto-escapes by default).

## 8. Backward Compatibility & Migration

### 8.1 Zero impact on existing order records

Existing orders (created before `ORDER_LIFECYCLE_ENABLED=true`) have no
`adjusted_amount_cents` attribute on their header. `compute_adjusted_amount`
falls back to `amount_cents` when the attribute is absent (Section 4.1.12).
Any code that reads `order["amount_cents"]` is unchanged. Any code that reads
`order.get("adjusted_amount_cents")` gets `None` for old orders and an integer
for orders with adjustments.

### 8.2 `OrderLifecycleOut.adjustments` remains `None` by default

`OrderLifecycleOut.adjustments: Optional[List[OrderAdjustment]] = None` is
populated only when the ORD-011 router explicitly calls `list_adjustments`
(triggered by `?include=adjustments` query param). Consumers that read the
lifecycle output without the include param never see the `adjustments` field
populated; the response is backward-compatible.

### 8.3 No new DynamoDB tables or GSIs

ORD-008 writes only to the `orders` table (already extended by ORD-003).
`just restart` in dev recreates the table with the schema from ORD-003; no
additional `local-ddb-init.py` change is needed for ORD-008.

### 8.4 Rollback

If `ORDER_LIFECYCLE_ENABLED` is reset to `false` after ORD-008 adjustments
have been applied to orders:
- Existing `ADJ#` rows remain in DynamoDB but are never queried.
- `adjusted_amount_cents` attributes remain on order headers but are never
  surfaced in responses (the lifecycle router returns 503 when off).
- No data loss; no rollback script is required.

## 10. Open Questions / Assumptions

1. **Assumption: `amount_cents` in `OrderAdjustment` is always non-negative
   (`ge=0`), with `adj_type` carrying sign semantics.** The ORD-003 schema note
   (`docs/ofbiz/specs/ORD-003.md:204`) says `"Integer; negative for discounts"`.
   The ORD-004 Pydantic model spec (`docs/ofbiz/specs/ORD-004.md:185`) says
   `Field(..., ge=0)`. The ticket description at
   `ORDER_LIFECYCLE_TICKETS.md:159` says `"Discounts are negative, surcharges
   positive"`. This spec follows ORD-004 (non-negative, type-based sign). If
   the billing team confirms signed amounts are required (e.g. for credit
   memos), remove the `ge=0` constraint and update `_compute_net_total` to use
   the raw signed value directly. **Needs confirmation before implementation.**

2. **Assumption: `query_order_rows(order_id, sk_prefix="ADJ#")` loops until
   `LastEvaluatedKey` is exhausted.** If `order_store.query_order_rows` only
   returns the first DynamoDB page (max 1 MB), adjustments beyond the first
   page would be silently missed. The implementation must ensure
   `query_order_rows` is fully paginating. This must be verified when ORD-003
   delivers `order_store.py`.

3. **Assumption: `_update_header_total` does not use a conditional expression.**
   For the current single-admin workflow, last-write-wins is acceptable.
   If concurrent adjustment writers become common (automated pricing engines),
   add a conditional expression guarding on an `adjustment_version` counter.

4. **Open question: should `adjusted_amount_cents` be initialised to
   `amount_cents` at order creation (ORD-007)?** If yes, every ORDER header
   always has `adjusted_amount_cents` from creation onwards and `compute_adjusted_amount`
   can skip the DDB fallback. If no (the current design), orders without
   adjustments lack the attribute and `compute_adjusted_amount` falls back.
   Initialising at creation would simplify ORD-010's refund logic.

5. **Assumption: `created_by` stores the raw `actor` string (user_sub or
   `"system"`).** There is no validation that `actor` is a valid user sub.
   The ORD-011 router always passes `ctx["user_sub"]`, which is a Cognito sub.

6. **Open question: should `list_adjustments` return a paginated response
   (with cursor) or a flat list?** For typical orders with fewer than 20
   adjustments, a flat list is appropriate. If catalog-pricing automation
   generates hundreds of adjustment lines per order, pagination will be needed.
   For ORD-008, a flat list with a hard cap of 500 rows (matching the
   `Limit=500` cap in `app/routers/messaging.py:list_conversations`) is sufficient.

7. **Assumption: `OrderAdjustmentIn` (ORD-011) is the only input model for
   adjustment creation.** The `adjustment_id` field is intentionally excluded
   from the create request to prevent callers from supplying colliding IDs.
   If the pricing engine requires deterministic IDs, a separate
   `source_rule_ref`-based idempotency mechanism (e.g. a `ConditionExpression`
   on `put_item`) should be added in a follow-up.

8. **Assumption: the `orders` table has been extended with `sk` as the sort key
   by ORD-003 before this ticket is implemented.** If ORD-003 has not merged,
   all `get_item` and `put_item` calls in this spec will fail with
   `ValidationException` (missing sort key).
