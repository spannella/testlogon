# SHP-018 — Buyer shipping/tracking UI integration

## 1. Summary & Goal

SHP-018 surfaces the shipping module to buyers in two places:

1. **Checkout** (`frontend/src/pages/shop/Checkout.tsx`): when `S.shipping_enabled` and `S.shipping_rate_estimation_enabled` are both on, inject a **Shipping Options** block between the Order Summary card and the Payment Method card, letting the buyer pick a rated ship method before placing the order. The chosen method's `amount_cents` is added to the displayed total. With either flag off the block is entirely absent — the `Checkout.tsx` file is byte-for-byte unchanged at runtime.

2. **Transaction detail** (`frontend/src/pages/purchases/TransactionDetail.tsx`): when the flag is on (and a linked shipment exists from SHP-014), extend the existing "Shipping" sub-section in the Order Details card to show the new `fulfillment_status`, the first shipment's `carrier`, `method_label`, and `tracking_url`. Because SHP-014 already denormalises carrier/tracking/status onto the `purchase_transactions` row via the existing `update_shipping()` path, this is almost entirely a read-only display change. With the flag off or with no shipment, the panel behaves exactly as today.

This ticket is deliberately **read-only on the buyer side**. It introduces no new write paths that mutate the cart, order, shipment, or billing data. The one additive write is that `purchaseCart` passes an optional `ship_method_id` to the existing checkout endpoint (added by SHP-007/SHP-008 upstreams), which is simply `undefined` when the flag is off.

## 3. Data Model

SHP-018 introduces **no new DynamoDB tables or GSIs**. All reads go to tables provisioned by upstream tickets.

### Read paths used

**Rate estimate** (checkout, flag-gated):

- Calls `POST /ui/shop/shipping/estimate` (from SHP-007) which reads `T.shipping_carriers` and catalog item weights. No new reads in SHP-018 itself.

**Fulfillment status on transaction detail** (flag-gated):

- `GET /ui/purchase-history/transactions/{txn_id}` (existing `purchase_transactions` table, PK `user_sub` / SK `TXN#{created_at}#{txn_id}`). The `shipping` sub-map already stores carrier/tracking/status written by SHP-014.
- SHP-014 additively writes `fulfillment_status` directly onto the `shipping` sub-map of the transaction row. SHP-018 reads it from `txn.shipping.fulfillment_status` in the TypeScript `PurchaseShipping` type.
- SHP-014 also writes `fulfillment_status` onto the `orders` table row (PK `order_id`). SHP-018 does not read the `orders` table directly; it reads the denormalised value on the transaction.

### Additive field on `PurchaseShipping` (TypeScript)

The existing `PurchaseShipping` interface (`frontend/src/api/types.ts:2735`) is extended **additively** by SHP-016 with two new optional fields:

```ts
fulfillment_status?: string;   // "unfulfilled"|"partially_shipped"|"shipped"|"delivered"
method_label?: string;         // human display label from the carrier ship method
```

**CORRECTION — backend model change IS required (SHP-016 scope):** `PurchaseShippingIn` (`app/models.py:438`) uses `Optional[...]` for every existing field, but Pydantic v2 drops unrecognised keys when the endpoint serializes the response via `response_model=PurchaseTransactionInfo` (`app/routers/purchase_history.py:66`). If `fulfillment_status` and `method_label` are not declared as `Optional[str] = None` fields on `PurchaseShippingIn`, FastAPI will silently omit them from `GET /ui/purchase-history/transactions/{txn_id}`, and the buyer UI will never see them. SHP-016 (or SHP-014) must extend `PurchaseShippingIn` with these two fields alongside the TypeScript type changes:

```python
# app/models.py — PurchaseShippingIn, add after existing fields
fulfillment_status: Optional[str] = None   # written by SHP-014
method_label: Optional[str] = None        # written by SHP-014
```

### `purchaseCart` optional ship_method_id

The `purchase_cart` function signature gains an optional `ship_method_id: str | None = None` parameter (added by SHP-007/SHP-008). SHP-018's checkout block passes the buyer's selection through. When the flag is off or no selection is made the parameter remains `None` and the existing checkout path is completely unchanged.

## 5. Detailed Behavior & Edge Cases

### 5.1 Checkout — `ShippingOptionsBlock`

**Render condition** (inside `Checkout.tsx`):

```tsx
{isShippingEnabled() && <ShippingOptionsBlock
  cartId={cartId}
  onSelect={(optionId, priceCents) => {
    setSelectedShipMethodId(optionId);
    setShippingCents(priceCents);
  }}
/>}
```

**`ShippingOptionsBlock` component** (new file `frontend/src/pages/shop/ShippingOptionsBlock.tsx`):

- Renders a "Shipping" card with a destination address form (name, address1, city, state/province, postal_code, country). The form is minimal — only postal_code and country are required for estimation.
- On blur/change of any destination field, if postal_code and country are both filled, fires `useQuery` with key `["shipping-estimate", cartId, destination]` calling `estimateShipping(cartId, destination)`.
- Renders a radio-button list of `ShippingRateOption` items: carrier label, method label, transit days, and formatted `amount_cents`. Defaults to the first (cheapest) option.
- `staleTime: 300_000` (5 min) — estimate is stable for a session unless destination changes.
- If the query returns empty options or errors, shows "Shipping not available for this address" and sets `selectedShipMethodId` to `null`. The "Place Order" button is not blocked by a missing shipping selection — shipping is optional at the UI level (an order without a ship method proceeds as before; the seller assigns the shipment later).
- The component is entirely absent (not rendered, not imported, no network call) when `isShippingEnabled()` returns `false`.

**Total display**: When a shipping option is selected, `shippingCents` is added to `effectiveTotal` in the parent and shown as a separate "Shipping" line in the Order Summary card, above the existing Total row. This is display-only; the actual shipping charge is captured by the order service (SHP-008) when the cart purchase is committed with `ship_method_id`.

**Edge cases**:

- Flag off → `ShippingOptionsBlock` is never imported (lazy-safe) and `selectedShipMethodId` / `shippingCents` state is never initialised; `purchaseCart` call omits `ship_method_id`.
- Cart has only digital items with no weight → estimator returns empty options; block shows "Standard shipping not applicable" and does not block checkout.
- Destination country not supported → estimator returns 0 options; same "not available" state.
- Estimate fetch fails (network/503) → React Query error state; block shows a soft "Could not load shipping options" message; checkout is still usable.
- User changes destination after selecting an option → query key changes, prior selection is cleared (`setSelectedShipMethodId(null)`), new estimate fires.

### 5.2 Transaction detail — fulfillment status and shipment details

**Render condition** in `TransactionDetail.tsx`:

The existing `{txn.shipping && ...}` block (line 447) is extended. No wrapper flag check is needed in the render path because: (a) if the flag was off when the order was placed no `fulfillment_status` or `method_label` field will be present on the `shipping` sub-map, and (b) if the flag is turned off after the fact the fields are simply absent/`undefined` and the existing optional-chaining renders gracefully.

However, to avoid showing a misleadingly empty "Fulfillment" row, the new fields are rendered with a `?.` guard:

```tsx
{txn.shipping?.fulfillment_status && (
  <div>
    <dt className="text-muted-foreground">Fulfillment</dt>
    <dd className="capitalize">
      {txn.shipping.fulfillment_status.replace(/_/g, " ")}
    </dd>
  </div>
)}
{txn.shipping?.method_label && (
  <div>
    <dt className="text-muted-foreground">Ship Method</dt>
    <dd>{txn.shipping.method_label}</dd>
  </div>
)}
```

These two `<div>` blocks are inserted into the existing `<dl>` grid at lines 450–497 of `TransactionDetail.tsx`, after `carrier` and before `shipped_at`.

**`ShippingTimeline` extension** (optional, flag-off safe):

`ShippingTimeline.tsx` currently derives `shippedAt` from `txn.shipping?.shipped_at`. SHP-014 writes `shipped_at` onto the shipping sub-map when the shipment transitions to `shipped`. No prop change is needed — the existing `shippedAt` prop path already handles this.

If `fulfillment_status === "partially_shipped"` a distinct visual cue is desirable but deferred to SHP-017 (admin UI). For now the timeline shows "Shipped" as complete only when `shippedAt` is non-null (i.e. all groups shipped and `fulfillment_status === "shipped"`). Partially-shipped shows the step as "upcoming" (same as today when no `shipped_at` exists).

**Edge cases**:

- Transaction has no linked shipment (order placed with flag off, or digital-only order) → `txn.shipping` is `null` or has no `fulfillment_status` → existing block shows nothing, unchanged.
- Multiple ship groups → SHP-014 denormalises the "first shipped" group's carrier/tracking onto the transaction. The buyer sees one tracking entry, which is intentional for the MVP. Multi-group display is a follow-up in SHP-017.
- `tracking_url` is `null` (manual carrier with no online-tracking) → tracking number shown as plain text, no hyperlink (existing code path at `TransactionDetail.tsx:474`).
- `fulfillment_status` transitions (`unfulfilled → partially_shipped → shipped → delivered`) are written by SHP-014 idempotently and flow to the buyer view through the existing `getTransaction` query (staleTime 0; no caching beyond React Query's default).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007

- The `ShippingOptionsBlock` calls `POST /ui/shop/shipping/estimate` via the shared `api` axios instance (cookie + CSRF header attached by `client.ts`). The backend endpoint uses `require_ui_session`; CSRF is enforced on every non-GET. Same code path dev and prod — no `dev_mode` branch in the estimate response shape.
- The `purchaseCart` mutation uses the existing `POST /ui/shop/cart/{cart_id}/purchase` endpoint which already enforces `require_ui_session`. Adding `ship_method_id` to the body does not change auth requirements.
- Shipping rate options are derived server-side from the `shipping_carriers` table; the frontend displays what the server returns — buyers cannot inject custom `amount_cents`.

### Ownership / IDOR

- `GET /ui/purchase-history/transactions/{txn_id}` uses `require_ui_session` (`app/services/sessions.py:330`) and fetches by `(user_sub, sk)` pattern — buyers can only read their own transactions (enforced in `_fetch_txn` at `app/services/purchase_history.py:131`).
- `POST /ui/shop/shipping/estimate` resolves the cart by `(user_sub, cart_id)` — buyers can only estimate for their own cart (SHP-007 design).

### Idempotency

SHP-018 introduces no new write paths of its own. The `ship_method_id` passed at checkout feeds into SHP-008's idempotent shipment-creation path (deterministic `shipment_id = sha256("shipment:{order_id}:{ship_group_seq}")[:32]`). Replaying the same cart purchase returns the already-purchased result from `purchase_cart`'s idempotency guard (`app/services/shoppingcart.py:483` — guard on `cart.get("status") == "PURCHASED"`).

### CSRF

The `estimateShipping` call uses `api.post(...)` — the shared axios instance (`frontend/src/api/client.ts`) automatically attaches `x-csrf-token` from the `ui_csrf` cookie. Backend enforces this for all non-GET cookie-auth requests.

## 8. Backward Compatibility & Migration

### Zero-migration path

All changes are additive:

- `PurchaseShipping` TypeScript type gains two new `optional` fields; existing code that destructures only `carrier`/`tracking_number` is unaffected.
- `PurchaseTransactionInfo.shipping` (already `Optional[PurchaseShippingIn]`) is unchanged; `PurchaseShippingIn` gains no new required fields in SHP-018.
- `Checkout.tsx` gains a conditional block with `isShippingEnabled()` guarding it; the `false` branch renders nothing. The `purchaseMutation` function is unchanged when `selectedShipMethodId` is `null`.
- `TransactionDetail.tsx` gains two conditional `<div>` blocks with `?.` guards; existing orders with no `fulfillment_status` on their `shipping` map render identically.
- No DDB schema change, no new tables, no `TableDef` additions.

### Flag-off parity assertion (SHP-019 regression test)

SHP-019 (shipping test suite) includes a test that with `SHIPPING_ENABLED=false` / `VITE_SHIPPING_ENABLED=false`:

1. The checkout page response body contains no `data-testid="shipping-options"` element.
2. `POST /ui/shop/shipping/estimate` returns 503 (`shipping_not_enabled`).
3. `GET /ui/purchase-history/transactions/{txn_id}` returns the same body as today (no new keys visible at the HTTP level).

### In-flight orders during flag rollout

If the flag is toggled on while existing orders are in flight, those orders have no `fulfillment_status` or `method_label` on their `shipping` map. The UI renders them identically to today (optional fields absent → conditional blocks hidden). No backfill is required.

## 10. Open Questions / Assumptions

1. **Assumption**: SHP-014 writes `fulfillment_status` and `method_label` into the existing `shipping` sub-map of the `purchase_transactions` row (not as separate top-level attributes). This spec reads them from `txn.shipping.fulfillment_status` and `txn.shipping.method_label`. If SHP-014 stores them at top level the TypeScript type and template accessor paths must be adjusted.

2. **CORRECTED (no longer an assumption)**: `PurchaseShippingIn` (`app/models.py:438`) **must** be extended with `fulfillment_status: Optional[str] = None` and `method_label: Optional[str] = None`. Pydantic v2 silently drops unrecognised keys during `response_model` serialization at `GET /ui/purchase-history/transactions/{txn_id}` (`app/routers/purchase_history.py:66`). Without these fields on the model, the buyer UI receives `undefined` for both properties even if SHP-014 wrote them into DDB. This backend model change belongs to SHP-016 (or SHP-014) and is a **hard prerequisite** for the TransactionDetail display in SHP-018.

3. **Assumption**: `ShippingRateOption` provided by SHP-016 has at minimum `{ method_id: string; carrier: string; method_label: string; amount_cents: number; currency: string; estimated_transit_days?: number }`. If the shape differs, `ShippingOptionsBlock` radio rendering must adapt.

4. **Open question**: Should the checkout shipping estimate require a full postal address, or only postal_code + country? A minimal 2-field form reduces friction; a full address form matches what is needed for the eventual SHP-008 shipment `ship_to`. This spec assumes postal_code + country are the minimum required fields for estimation; the full address form is collected but additional fields are optional.

5. **Open question**: When `ship_method_id` is passed to `purchaseCart` and the rate has changed since the estimate (stale quote), should the backend recompute and store the current rate, or trust the stored method's current rate? This is an SHP-008 concern; SHP-018 does not need to resolve it but should document that the buyer sees an estimate that may differ from the final billed amount.

6. **Assumption**: Partially-shipped orders (some ship groups shipped, others not) show `fulfillment_status = "partially_shipped"`. The `ShippingTimeline` shows the "Shipped" step as "current" (in-progress) rather than "complete" in this case. The spec defers this visual distinction to SHP-017 since SHP-018 does not touch `ShippingTimeline` logic.

7. **Assumption**: The `estimateShipping` API wrapper is provided by SHP-016 in `frontend/src/api/endpoints/shipping.ts`. SHP-018 imports it from there. If SHP-016 is not yet merged when SHP-018 is implemented, a local stub wrapper suffices as a bridging measure.
