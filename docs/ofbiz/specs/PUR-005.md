### 4.3 Supplier endpoints

Declaration order: literal sub-paths (`/suppliers`) before dynamic (`/suppliers/{supplier_id}`); within supplier-product sub-paths the listing routes before the single-item route.

#### `POST /ui/purchasing/suppliers`
```python
@purchasing_router.post("/suppliers", response_model=SupplierOut, status_code=201)
async def create_supplier(
    body: SupplierCreateIn,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
):
```
- Calls `sup_svc.create_supplier(user.sub, body.name, email=..., phone=..., address=body.address.model_dump() if body.address else None, default_currency=body.default_currency, payment_terms_days=body.payment_terms_days)`.
- Returns `SupplierOut(**rec)`. HTTP 201.
- Service raises 404 when flag off (propagated by FastAPI).

#### `GET /ui/purchasing/suppliers`
```python
@purchasing_router.get("/suppliers", response_model=SupplierListOut)
async def list_suppliers(
    status: str = Query(default="active", pattern=r"^(active|inactive)$"),
    limit: int = Query(default=50, ge=1, le=200),
    next_token: Optional[str] = Query(default=None),
    user: AuthenticatedUser = Depends(require_admin_or_root),
):
```
- Decodes `next_token` via `decode_cursor(next_token)` → raw `ExclusiveStartKey`.
- Calls `sup_svc.list_suppliers(status=status, cursor=start_key, limit=limit)` → `{"suppliers": [...], "cursor": Optional[str]}`.  ← returns a Dict per PUR-003 spec, not a Tuple
- The returned `cursor` is already an encoded string from `encode_cursor`; pass it through directly as `next_token`.
- Returns `SupplierListOut(items=[SupplierOut(**s) for s in result["suppliers"]], next_token=result["cursor"])`.

#### `GET /ui/purchasing/suppliers/{supplier_id}`
```python
@purchasing_router.get("/suppliers/{supplier_id}", response_model=SupplierOut)
async def get_supplier(
    supplier_id: str,
    user: AuthenticatedUser = Depends(require_admin_or_root),
):
```
- Calls `sup_svc.get_supplier(supplier_id)`. None → 404.
- Returns `SupplierOut(**rec)`.

#### `PATCH /ui/purchasing/suppliers/{supplier_id}`
```python
@purchasing_router.patch("/suppliers/{supplier_id}", response_model=SupplierOut)
async def patch_supplier(
    supplier_id: str,
    body: SupplierPatchIn,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
):
```
- If `body.status` is set, calls `sup_svc.set_supplier_status(supplier_id, body.status, user.sub)`.  ← `user_sub` is positional per PUR-003 spec
- Builds `patch_fields` from the non-None, non-status fields in `body.model_dump(exclude_none=True, exclude={"status"})`.
- If `patch_fields` is non-empty, calls `sup_svc.update_supplier(supplier_id, user.sub, **patch_fields)`.  ← `user_sub` is positional per PUR-003 spec
- Re-fetches via `get_supplier(supplier_id)` and returns `SupplierOut`.
- Empty body (all None) → 422 with message "At least one field must be provided".

#### `DELETE /ui/purchasing/suppliers/{supplier_id}`

Not required by the acceptance criteria of this ticket. Soft deactivation via PATCH `status="inactive"` is the supported lifecycle path. A hard-delete endpoint can be added in a future ticket (see section 10, assumption 6).

### 4.4 Supplier-product endpoints

The prefix structure under `/ui/purchasing` is:
- `/suppliers/{supplier_id}/products` — list products for a supplier
- `/suppliers/{supplier_id}/products/{sku}` — get/upsert/delete a specific supplier↔SKU record
- `/skus/{sku}/suppliers` — list suppliers for a SKU (cheapest-first)

This ordering ensures no literal/dynamic conflicts: `/suppliers` (literal) before `/{supplier_id}` would conflict if misplaced. Within the supplier-product sub-path, the list `/products` is declared before the single-item `/products/{sku}`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off 404

With `S.purchasing_scm_enabled=False` (the default), every endpoint returns HTTP 404 with detail `"Purchasing/SCM is not enabled"`. This 404 comes from the service layer (`_require_enabled()` in both `suppliers.py` and `supplier_products.py`). FastAPI propagates `HTTPException` from synchronous service calls correctly even inside `async def` handlers.

### 5.2 PATCH semantics: status + field update in one call

`SupplierPatchIn` allows `status` and mutable fields to be patched in a single request. The handler applies them sequentially: `set_supplier_status` first (if present), then `update_supplier` (if any non-status field is set). The intermediate state after `set_supplier_status` is never exposed to the caller. If both operations succeed, the handler re-fetches and returns the final state. If `update_supplier` fails after `set_supplier_status` succeeds, the status change persists (not rolled back). This is acceptable because the two operations are logically independent, and a partial success is less harmful than a rollback attempt.

### 5.3 Supplier existence check on PUT product

`GET /ui/purchasing/suppliers/{supplier_id}/products/{sku}` (PUT upsert) explicitly validates the supplier exists before delegating to the service. This prevents orphaned `supplier_products` rows for non-existent suppliers (PUR-004 spec, section 10, assumption 1). The check is a `get_item` call on `T.suppliers` via `sup_svc.get_supplier(supplier_id)` — one extra round trip on the write path. Inactive suppliers (`status="inactive"`) are still allowed to receive product upserts, so the check is existence-only, not status-filtered.

### 5.4 Empty PATCH body

If a client sends `PATCH /ui/purchasing/suppliers/{id}` with `{}` (all fields None), the handler returns HTTP 422 with `{"detail": "At least one field must be provided"}`. This is a router-level guard, not a Pydantic model validator, because the model must accept all-None (it is a partial update model by design).

### 5.5 `GET /suppliers` status filter

The `status` query parameter defaults to `"active"`. The Pydantic `Query` annotation enforces the pattern `r"^(active|inactive)$"`. An invalid value (e.g., `status=pending`) triggers FastAPI's automatic 422 validation error without reaching the handler.

### 5.6 `GET /suppliers` pagination

`list_suppliers` returns at most `limit` items plus a `next_token`. The token is an HMAC-signed cursor produced by `encode_cursor(lek)` where `lek` is the raw DynamoDB `LastEvaluatedKey`. The cursor includes the `status` partition key and the `created_at` sort key. Since both `supplier_id` (string) and `created_at` (numeric N) appear in the `LastEvaluatedKey`, and `app/core/cursor.py:12–19` serializes `Decimal` to `int` via `_json_default`, the cursor round-trips cleanly across the N-typed `created_at`. NOTE: `list_suppliers` returns its own cursor string (already encoded via `encode_cursor`); the router passes it through to `SupplierListOut.next_token` directly.

### 5.7 `GET /suppliers/{supplier_id}/products` for unknown supplier

No supplier existence pre-check is performed. An unknown `supplier_id` produces an empty list (the DynamoDB `query` on a non-existent PK returns zero items). This is consistent with how `list_products_for_supplier` works at the service layer (PUR-004 spec, section 4.2). The caller should use `GET /suppliers/{id}` to confirm existence before enumerating products.

### 5.8 SKU path parameter with `catalog:` prefix

A supplier-product `sku` of the form `catalog:{item_id}` becomes a path parameter segment, e.g. `PUT /ui/purchasing/suppliers/abc123/products/catalog:01HXZ9ABC`. The colon character is valid in a URL path segment (RFC 3986 §3.3) and FastAPI/Starlette will route it correctly. The `item_id` portion (a ULID-like lowercase hex string) contains no `/` characters, so the path parameter captures the full `catalog:` prefixed string intact.

### 5.9 `DELETE /suppliers/{id}/products/{sku}` idempotency

The service's `delete_supplier_product` returns `False` for a non-existent record (after a read-before-delete). The router returns 404. A second DELETE on the same record returns 404. This is not idempotent in the HTTP sense (idempotent would mean a second DELETE returns 204). The 404 on re-delete is the safer behavior: it signals "already gone" clearly to the caller rather than silently succeeding. HTTP DELETE idempotency is a SHOULD not a MUST (RFC 9110 §9.3.5).

### 5.10 Non-admin access → 403

`require_admin_or_root` and `require_admin_or_root_csrf` both call `require_roles(user, {Role.ADMIN, Role.ROOT})` which raises `HTTPException(403, {"code": "role_required", ...})` per `app/auth/policy.py:13–22`. A `USER`-role session trying any purchasing endpoint receives HTTP 403 with the standard error shape.

### 5.11 `preferred` flag: no uniqueness enforcement at the router layer

The router does not clear `preferred=True` on other supplier-products when setting `preferred=True` on one. Multiple suppliers may hold `preferred=True` simultaneously for the same SKU. This is noted in PUR-004 spec, section 5.4, and is intentional for simplicity. The admin UI may implement a "set preferred" button that first clears the flag on all others then upserts the new one; that is a multi-call sequence in the client.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

`purchasing_router` calls service functions that access `T.suppliers` and `T.supplier_products` via `_safe_table(...)`. In dev, `ddb` points to DynamoDB Local (port 8001, moto in tests). In prod, `ddb` is the real boto3 DynamoDB resource. No `dev_mode` branch exists in the router or service layers. The auth dependencies (`require_admin_or_root_csrf`, `require_admin_or_root`) apply identically in both environments because they depend on `get_authenticated_user`, which inspects the request's JWT cookies or Bearer token regardless of environment.

### Idempotency

- `POST /suppliers` is idempotent by name+user_sub via the sha256-based `supplier_id` derivation in `create_supplier` (PUR-003 spec, section 3.1). A duplicate POST with the same `name` returns the existing `supplier_id` without error.
- `PUT /suppliers/{id}/products/{sku}` is idempotent on the `(supplier_id, sku)` pair: repeated calls overwrite the same DDB key.
- `DELETE /suppliers/{id}/products/{sku}` on an already-deleted record returns 404 (not idempotent; see section 5.9).

### Security

- All endpoints require `ADMIN` or `ROOT` role. A `USER`-role session receives 403 without reaching any service logic.
- CSRF is enforced on all mutating endpoints (`POST`, `PATCH`, `PUT`, `DELETE`) via `require_admin_or_root_csrf`. Bearer-token clients skip CSRF per the `enforce_cookie_csrf` logic at `app/auth/policy.py:71–97`.
- `supplier_id` is derived from `sha256(f"supplier:{user_sub}:{name}")`. The `user_sub` scopes the hash so two admins with the same company name cannot accidentally share a `supplier_id`.
- Supplier contact information (email, phone, address) is stored as-is in DynamoDB. No PII encryption is applied at this tier; existing platform PII handling (if any) is not disrupted. This is noted as an open question.
- `unit_cost_cents` is a non-negative integer; negative values are rejected by the Pydantic `ge=0` constraint before reaching the service. No float arithmetic is performed.

## 10. Open Questions / Assumptions

1. **Assumption: `create_supplier` scopes `supplier_id` to `user_sub`.** The hash is `sha256(f"supplier:{user_sub}:{name}")[:32]`. This means two admins creating a supplier with the same name get different `supplier_id` values. If the system should have globally unique suppliers by name (independent of who creates them), the hash should omit `user_sub`. Verify with product owner: is per-creator scoping intended, or should supplier identity be name-global?

2. **Assumption: inactive suppliers can still receive product upserts.** The PUT product endpoint checks supplier existence but not status. This allows maintaining a price catalog for a temporarily inactive supplier. Verify whether inactive suppliers should be blocked from new product associations.

3. **Assumption: no hard delete endpoint for suppliers.** Soft deactivation via `PATCH status=inactive` is the only supported deactivation path. A hard delete would require cascading deletion of all `supplier_products` rows (a scan on `PK=supplier_id` + batch delete). This is deferred. If a hard delete is needed before PUR-005 ships, add it explicitly.

4. **Assumption: `catalog:` prefixed SKUs in URL path parameters are safe.** The colon character is valid in URL paths (RFC 3986 §3.3). If the `item_id` portion of a `catalog:{item_id}` SKU ever contained a forward slash, path routing would break. ULID-like item IDs (timestamp + lowercase hex) do not contain slashes, so this is safe for the current ID format. If item IDs are changed to include slashes, path parameters must be replaced with query parameters.

5. **CORRECTED: `EmailStr` is NOT imported in `app/models.py`.** The pydantic import block at `app/models.py:11–19` contains only `AliasChoices, BaseModel, ConfigDict, Field, conint, field_validator, model_validator`. Neither `EmailStr` nor `AnyHttpUrl` are present. `RegisterStartReq` at `app/models.py:119` uses `email: str` (plain `str`), not `EmailStr`. The `SupplierCreateIn.email` and `SupplierPatchIn.email` fields in this spec use `Optional[str]` (consistent with PUR-003's own model definitions), NOT `Optional[EmailStr]`. No new pydantic import is needed.

6. **Assumption: PII classification of supplier contact fields.** `email`, `phone`, and `address` are stored in plaintext in DynamoDB. These are business contact fields (vendor accounts), not end-user PII. The platform's existing user-PII handling does not apply here. If supplier contact data is subject to the same data-retention or encryption requirements as user PII, this must be resolved before GA.

7. **Assumption: `SupplierAddressIn.country` is ISO 3166-1 alpha-2.** The spec constrains to `max_length=2`. Full ISO validation (against a known list) is not enforced in this ticket. An invalid two-letter string will be stored as-is. Add a validator in a follow-up if needed.

8. **Question: should `GET /purchasing/suppliers` be paginated server-side or client-side?** The spec implements server-side pagination via `GSI_STATUS` + `Limit` + `ExclusiveStartKey`. For a typical operator with dozens of suppliers this is unnecessary. For large deployments with thousands of suppliers it is essential. The implementation uses server-side pagination consistently with the rest of the platform (e.g., `list_low_stock` at `app/services/inventory.py:318–333`).

9. **Question: should `list_products_for_supplier` filter by status?** Currently it returns all SKU records including those from inactive suppliers (if called via the supplier-id path directly). The caller must check `GET /suppliers/{id}` separately to know if the supplier is active. A `FilterExpression` for `preferred=true` or status filtering can be added as a query parameter in a future ticket.

10. **Question: cursor encoding for `GSI_SKU` LastEvaluatedKey.** The `GSI_SKU` sort key is `unit_cost_cents` (numeric N). The `app/core/cursor.py:12–19` `_json_default` serializer handles `Decimal → int`, so the numeric sort key round-trips correctly through the cursor. This assumption should be validated with an integration test that pages through `list_suppliers_for_sku` with numeric sort keys.
