# PUR-013 — Frontend types + endpoint wrappers

**Type:** Feature | **Priority:** P1 | **Estimate:** 2 days
**Milestone:** 5 — Frontend
**Depends on:** PUR-005 (Supplier & supplier-product models + router), PUR-010 (Purchase-order models + router endpoints), PUR-012 (Reorder-suggestion endpoints + optional background scan)

---

## 1. Summary & Goal

PUR-013 adds the TypeScript presentation layer that mirrors every new Pydantic shape
introduced by PUR-005, PUR-010, and PUR-012 into `frontend/src/api/types.ts`, and
supplies a single typed endpoint-wrapper module at
`frontend/src/api/endpoints/purchasing.ts` covering all routes on
`app/routers/purchasing.py`.

The deliverables are:

1. **TypeScript interfaces** appended to `frontend/src/api/types.ts` in a dedicated
   `// ─── Purchasing/SCM ─────────────────────────────────────────────────────`
   section, mirroring the backend Pydantic shapes for suppliers, supplier-products,
   purchase orders, receipts, and reorder suggestions.

2. **Endpoint wrappers** in a new file `frontend/src/api/endpoints/purchasing.ts`
   consuming the shared axios-like `api` object from `frontend/src/api/client.ts` and
   typed against the interfaces above; one export per backend route.

With `PURCHASING_SCM_ENABLED=false` on the backend every endpoint returns 404. This
ticket makes no assertion about that; the wrappers call the backend and let the caller
(React Query hooks in PUR-014 / PUR-015) handle the 404 as a disabled-feature signal.
No existing shop, cart, orders, or billing code is touched.

## 3. Data Model

PUR-013 introduces no DynamoDB tables. This section describes the wire shapes that the
TypeScript interfaces mirror. All shapes derive from the Pydantic models specified in
the three upstream tickets.

### 3.1 Supplier shapes (mirrors PUR-005 `app/models.py` block)

Backend Pydantic sources: `SupplierAddressIn`, `SupplierCreateIn`, `SupplierPatchIn`,
`SupplierAddressOut`, `SupplierOut`, `SupplierListOut`, `SupplierProductUpsertIn`,
`SupplierProductOut`, `SupplierProductListOut`.

Key field types:
- `supplier_id`: deterministic sha256 hex string (32 chars)
- `status`: `"active" | "inactive"` — the only two values the backend accepts
- `created_at`, `updated_at`: Unix integer timestamps (the backend stores these as
  DDB type N; `InventoryRecord.updated_at` in `types.ts:2171` is already typed
  `number` for the same reason)
- `payment_terms_days`: integer (net-days)
- `unit_cost_cents`, `min_order_qty`, `lead_time_days`: integers
- `preferred`: boolean

### 3.2 Purchase-order shapes (mirrors PUR-010 `app/models.py` block)

Backend Pydantic sources: `PurchaseOrderLineIn`, `PurchaseOrderLineOut`,
`PurchaseOrderCreateIn`, `PurchaseOrderOut`, `PurchaseOrderListOut`,
`PoTransitionIn`, `PoReceiveLineIn`, `PoReceiveIn`, `PoReceiptOut`.

Key field types:
- `po_id`: deterministic sha256 hex string (32 chars)
- `status`: `"draft" | "submitted" | "approved" | "ordered" | "partially_received" | "received" | "closed" | "rejected" | "cancelled"`
- `created_at`, `updated_at`, `approved_at`, `cancelled_at`: Unix integers
- `subtotal_cents`, `unit_cost_cents`, `line_total_cents`: integers
- `lines`: embedded `PurchaseOrderLineOut[]` on the full `PurchaseOrderOut`; empty
  array on list responses where the backend returns headers only
- `receipt_correlation_id`: caller-supplied idempotency key (opaque string)

### 3.3 Reorder-suggestion shapes (mirrors PUR-012 `app/models.py` block)

Backend Pydantic sources: `ReorderSuggestionOut`, `ReorderSuggestionListOut`.

Key field types:
- `suggestions`: flat list sorted by `supplier_id` then `sku`
- `warnings`: list of bare SKU strings (backend returns `List[str]` from PUR-011)
- `generated_at`: Unix integer timestamp
- `estimated_cost_cents`: `suggested_qty * unit_cost_cents` (pre-computed by service)

  reason?: string;
}

  line_no: number;

}

  lines: PoReceiveLineIn[];

export interface PoReceiptLine {
  line_no: number;

  quantity_received: number;
}

export interface PoReceipt {
  receipt_id: string;
  po_id: string;

  received_at: number;

`PoReceiptLine` is a client-side convenience type; the backend's `PoReceiptOut.lines`

always carry `line_no`, `sku`, and `quantity_received` per the PUR-008 service
contract. If the backend later adds more fields, the extra keys are simply ignored by
TypeScript's structural typing.

## 5. Detailed Behavior & Edge Cases

### 5.1 `encodeURIComponent` on all path parameters

`supplier_id` is a 32-character hex string from `sha256(...)[:32]`, which is URL-safe.
`po_id` is likewise hex-safe. However, `sku` may contain arbitrary characters including
slashes, colons, and spaces (e.g. `catalog:abc123` or `SKU-001/A`). All three path
parameters must be wrapped in `encodeURIComponent(...)` to prevent router mis-routing
on the backend. The `getInventoryItem` wrapper in `inventory.ts:14` already uses this
pattern for `sku`.

### 5.2 `listPurchaseOrders` requires at least one filter

The backend raises HTTP 422 if neither `supplier_id` nor `status` is provided (to
prevent unbounded scans — PUR-010 spec §5 / open question A5). The TypeScript function
signature accepts an object with both fields optional. Calling `listPurchaseOrders({})`
will succeed at compile time but produce a 422 at runtime. PUR-014/015 pages must
always pass at least one filter. A defensive approach in the wrapper itself would be
to type-narrow with an overloaded signature or a union constraint, but the simpler
approach — acceptable for an internal admin-only surface — is a comment warning:

```ts
/**
 * At least one of `supplier_id` or `status` must be provided;
 * the backend returns 422 if both are absent.
 */
export const listPurchaseOrders = ...
```

### 5.3 `submitPurchaseOrder` uses session auth, not admin auth

The backend `POST /purchase-orders/{po_id}/submit` uses `require_ui_session` (not
admin-only). From the frontend's perspective, the call is identical to any other
mutation — the `api` client always attaches the `ui_csrf` cookie header. No special
handling is needed in the wrapper.

### 5.4 `rejectPurchaseOrder` and `cancelPurchaseOrder` with no body

The backend `PoTransitionIn` body is `Optional` (body is allowed to be absent). In
the TypeScript wrappers, `body?: PoTransitionIn` maps to `api.post(path, body)` where
`body` may be `undefined`. The `api.post` implementation at `client.ts:293–298` handles
`body != null ? JSON.stringify(body) : undefined` — an `undefined` body sends no
`Content-Type` and no body, which FastAPI accepts for `Optional[PoTransitionIn] = None`
parameters.

### 5.5 `PoReceipt.lines` typed as `PoReceiptLine[]`

The backend Pydantic model `PoReceiptOut.lines` is `List[Dict[str, Any]]` (PUR-010 spec
§4.1, open question A4 — a concrete `PoReceiptLineOut` was deferred). The TypeScript
interface uses a concrete `PoReceiptLine` with the three known fields (`line_no`, `sku`,
`quantity_received`). This is safe via TypeScript's structural typing: additional backend
keys are silently ignored. If the backend later narrows `PoReceiptOut.lines` to a typed
model, the TypeScript interface will already be compatible.

### 5.6 `PurchaseOrder.lines` on list vs. get responses

`GET /purchase-orders` (list) returns `PurchaseOrderListOut` where each element is the
header only (no lines array in the service's list function — the backend does not
hydrate lines during a list scan to avoid N+1 DDB queries). `GET /purchase-orders/{po_id}`
(get single) returns the full `PurchaseOrder` with `lines` populated. The TypeScript
interface `PurchaseOrder.lines` is typed `PurchaseOrderLine[]` (always present, defaults
to empty array). Pages must call `getPurchaseOrder(po_id)` to get the lines; the list
response's `lines` will be `[]` and `line_count` gives the correct count.

### 5.7 `PoStatus` as a branded string union

Using `type PoStatus = "draft" | ...` rather than an `enum` or plain `string` enables
TypeScript exhaustive-switch checking in PUR-014/015 UI badge components and avoids
runtime overhead. The `PurchaseOrder.status` field is typed `PoStatus`, so any new
backend status that is not in the union will produce a compile error when a page does a
`switch(po.status)` with a `default: assertNever(po.status)` pattern.

### 5.8 `generated_at` and other integer Unix timestamps

All timestamp fields on backend purchasing models are Unix integer seconds (type N in
DynamoDB). They are represented as `number` in TypeScript (not `string`). This is
consistent with `InventoryRecord.updated_at: number` at `types.ts:2171` and
`CartItem` timestamps. Pages should use `new Date(generated_at * 1000)` to display
human-readable dates.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007

PUR-013 contains no environment-branching logic. The wrappers call the same API paths
in dev (Vite proxy → `localhost:8000`) and prod (same proxy, different upstream). The
Vite configuration in `frontend/vite.config.ts` already proxies `/ui/**` to
`http://localhost:8000` (per CLAUDE.md "Vite proxies all `/api`, `/ui`, ... paths to
`http://localhost:8000`"). No new proxy rules are required.

### 7.2 Idempotency

`createPurchaseOrder` accepts a `correlation_id` field. Callers in PUR-014/015 pages
should pass a deterministic correlation ID (e.g. a form-submission UUID held in React
state) when creating POs from a form, so that duplicate form submissions do not create
duplicate POs. The backend's `sha256(correlation_id)[:32]` idempotency guarantee
(PUR-006) means repeated calls are safe. `receivePurchaseOrder` requires
`receipt_correlation_id` (required field, no default) — PUR-015 pages must generate a
stable UUID per receiving action and store it in React state before the first call.

### 7.3 Security

- **No secrets in the frontend**: supplier `unit_cost_cents` and PO `subtotal_cents`
  are staff-only data. The pages in PUR-014/015 are role-gated (admin/root only) and
  are not accessible to regular users. PUR-013 types are in `types.ts` which is a
  build artifact; no data is exposed by merely defining types.
- **CSRF**: the `api` client at `client.ts:178–182` attaches `x-csrf-token` from the
  `ui_csrf` cookie on every non-GET request. PUR-013 wrappers call `api.post`,
  `api.put`, `api.patch`, `api.del` which all go through this path. No additional CSRF
  handling is needed.
- **Path encoding**: `encodeURIComponent` on `supplier_id`, `po_id`, and `sku`
  prevents path injection (e.g., a `sku` of `"../../admin/..."` would otherwise escape
  the intended sub-path).

## 10. Open Questions / Assumptions

**A1 — `PoReceiptOut.lines` backend shape**: PUR-010 spec §4.1 open question A4 notes
that `PoReceiptOut.lines` is `List[Dict[str, Any]]` and a dedicated `PoReceiptLineOut`
model may be added later. The TypeScript `PoReceiptLine` interface assumes three fields
(`line_no`, `sku`, `quantity_received`) based on PUR-008 service semantics. If the
backend adds more fields to the receipt line dict, `PoReceiptLine` must be updated
before those fields can be consumed by UI code.

**A2 — `PurchaseOrder.lines` on list responses**: The spec assumes `GET /purchase-orders`
(list) returns POs with `lines: []` (empty array). This is based on the service-layer
description in PUR-006/010 which does not explicitly state whether lines are hydrated
on list queries. If the backend does hydrate lines on list responses, the `lines`
interface is already compatible (it accepts the full array). Verify with PUR-010
implementer.

**A3 — Flat vs. grouped `ReorderSuggestionListOut.suggestions`**: PUR-012 spec §3.3
open question A3 notes the response may change from a flat list to a grouped dict by
`supplier_id`. The current TypeScript interface assumes a flat list
(`suggestions: ReorderSuggestion[]`). If the backend changes to a grouped structure,
both `ReorderSuggestionListResp` and the `getReorderSuggestions` wrapper must be
updated, and PUR-015 UI grouping logic will need to be revised.

**A4 — `SupplierListResp` vs. `PaginatedList<Supplier>`**: The backend `SupplierListOut`
inherits from `CatalogPageOut` (which has `next_token?: string`) and adds `items`.
The TypeScript `SupplierListResp` interface is defined explicitly rather than using
`PaginatedList<Supplier>`. Decide whether to use the existing generic to reduce type
proliferation; functionally equivalent.

**A5 — `listPurchaseOrders` without filter**: The current wrapper allows calling with
`{}` (no filter), which the backend rejects with 422. A stricter TypeScript overload
could be defined:
```ts
export function listPurchaseOrders(params: { supplier_id: string; status?: string; ... }): ...
export function listPurchaseOrders(params: { status: string; supplier_id?: string; ... }): ...
```
This adds type-safety at the cost of wrapper complexity. Leaving as-is with a JSDoc
warning is simpler and acceptable for an admin-only internal API.

**A6 — `createPoFromSuggestion` body**: PUR-012 spec §4.2 notes the
`POST /reorder-suggestions/{supplier_id}/create-po` endpoint receives an optional body
with `currency` and `expected_delivery_date`. The current wrapper passes no body. If
PUR-012 implementation adds these as required body fields, the wrapper must be updated.
Verify the final PUR-012 router signature before PUR-013 implementation.

**A7 — Re-export vs. direct import**: The `export type { ... }` re-export block in
`purchasing.ts` is a convenience. If `noUnusedLocals` in a future `eslint` config flags
unused re-exports, they can be removed and downstream pages can import from
`@/api/types` directly. This has no functional impact.
