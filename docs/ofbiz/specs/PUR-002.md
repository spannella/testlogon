## 3. Data Model

All four tables use DynamoDB single-table design (a shared physical table per logical entity) consistent with the returns/inventory precedent. PK and SK are always `"S"` (string). Numeric GSI sort keys must appear in `attr_types` with value `"N"` or DynamoDB stores them as strings and queries with numeric comparators fail at runtime.

### 3.1 `suppliers`

Stores vendor party records created/managed by PUR-003.

| Field | Key role | Type | Notes |
|---|---|---|---|
| `supplier_id` | PK (hash) | S | `sha256(f"supplier:{user_sub}:{name}")[:32]` — deterministic, idempotent |
| `sk` | Sort key | S | Always `"META"` (one row per supplier) |
| `status` | GSI_STATUS PK | S | `"active"` \| `"inactive"` |
| `created_at` | GSI_STATUS SK | **N** | Unix timestamp integer |

**GSI:** `GSI_STATUS` — partition `status` / sort `created_at` (N). Enables the admin list endpoint to page through active suppliers ordered by recency without a table scan.

**`attr_types`:** `{"created_at": "N"}`

**TableDef location:** `scripts/local-ddb-init.py`, inserted after the `returns` block (currently ending at `:2492`).

```python
TableDef(
    _resolve_table_name(S.suppliers_table_name, "suppliers"),
    "supplier_id",
    "sk",
    gsi=[
        {"index_name": "GSI_STATUS", "partition_key": "status", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
),
```

### 3.2 `supplier_products`

Stores the supplier ↔ SKU pricing relationship created/managed by PUR-004.

| Field | Key role | Type | Notes |
|---|---|---|---|
| `supplier_id` | PK (hash) | S | Foreign key into `suppliers` |
| `sk` | Sort key | S | `SKU#{sku}` — allows `Query(PK=supplier_id)` to list all SKUs for a supplier |
| `sku` | GSI_SKU PK | S | Enables reverse lookup: all suppliers offering a given SKU |
| `unit_cost_cents` | GSI_SKU SK | **N** | Ascending sort exposes cheapest supplier first (PUR-011 reorder suggestions) |

**GSI:** `GSI_SKU` — partition `sku` / sort `unit_cost_cents` (N). The cheapest-supplier query (`ScanIndexForward=True`) used by PUR-004 `list_suppliers_for_sku` and PUR-011 reorder suggestion engine.

**`attr_types`:** `{"unit_cost_cents": "N"}`

```python
TableDef(
    _resolve_table_name(S.supplier_products_table_name, "supplier_products"),
    "supplier_id",
    "sk",
    gsi=[
        {"index_name": "GSI_SKU", "partition_key": "sku", "sort_key": "unit_cost_cents"},
    ],
    attr_types={"unit_cost_cents": "N"},
),
```

### 3.3 `purchase_orders`

Stores PO headers (`SK=META`) and line items (`SK=LINE#{n}`) created/managed by PUR-006 through PUR-009.

| Field | Key role | Type | Notes |
|---|---|---|---|
| `po_id` | PK (hash) | S | `sha256(correlation_id)[:32]` — deterministic |
| `sk` | Sort key | S | `"META"` for header; `"LINE#{n}"` for line items (1-based) |
| `supplier_id` | GSI_SUPPLIER PK | S | Per-supplier PO history for PUR-006 list endpoint |
| `created_at` | GSI_SUPPLIER SK / GSI_STATUS SK | **N** | Unix timestamp on header row only |
| `status` | GSI_STATUS PK | S | `draft`\|`submitted`\|`approved`\|`ordered`\|`partially_received`\|`received`\|`closed`\|`rejected`\|`cancelled` |

**GSIs:**
- `GSI_SUPPLIER` — partition `supplier_id` / sort `created_at` (N). Retrieves all POs for a supplier, newest-first or oldest-first.
- `GSI_STATUS` — partition `status` / sort `created_at` (N). Drives the approval queue (filter on `submitted`) and the receiving queue (filter on `approved`/`ordered`).

Both GSI sort keys are the same `created_at` attribute. DynamoDB requires declaring it once in `attr_types` — the single `{"created_at": "N"}` entry covers both GSIs because `_attribute_definitions` iterates all GSIs and then applies the override map (see `scripts/local-ddb-init.py:2496–2506`).

**`attr_types`:** `{"created_at": "N"}`

```python
TableDef(
    _resolve_table_name(S.purchase_orders_table_name, "purchase_orders"),
    "po_id",
    "sk",
    gsi=[
        {"index_name": "GSI_SUPPLIER", "partition_key": "supplier_id", "sort_key": "created_at"},
        {"index_name": "GSI_STATUS",   "partition_key": "status",      "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
),
```

**Note on line rows:** Line rows (`SK=LINE#{n}`) do NOT carry `supplier_id` or `status`, so they are never projected into either GSI. The header row (SK=META) carries those attributes. GSI queries return only header items; callers then `Query(PK=po_id, SK begins_with "LINE#")` for lines.

### 3.4 `po_receipts`

Stores receiving events against PO lines, created/managed by PUR-009.

| Field | Key role | Type | Notes |
|---|---|---|---|
| `po_id` | PK (hash) | S | Foreign key to the PO being received against |
| `sk` | Sort key | S | `RECEIPT#{receipt_id}` — lists all receipts for a PO |
| `receipt_id` | GSI_RECEIPT PK | S | Idempotent lookup: find a receipt by its own ID without knowing the PO |

**GSI:** `GSI_RECEIPT` — partition `receipt_id`, no sort key. Used for idempotency checking before writing a new receipt (prevents double-receive on retried requests). Projections: ALL.

**`attr_types`:** `{}` (no numeric sort key needed — `receipt_id` is a string and `GSI_RECEIPT` has no sort key).

```python
TableDef(
    _resolve_table_name(S.po_receipts_table_name, "po_receipts"),
    "po_id",
    "sk",
    gsi=[
        {"index_name": "GSI_RECEIPT", "partition_key": "receipt_id"},
    ],
),
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Table creation ordering

The four new `TableDef` entries must be appended as a contiguous block after the `returns` `TableDef` at `scripts/local-ddb-init.py:2483–2492`. Order within the block does not matter for correctness (DDB creates tables in parallel), but the block must stay contiguous for readability.

### 5.2 `attr_types` gotcha for shared sort key names

`purchase_orders` uses `created_at` as the sort key in both `GSI_SUPPLIER` and `GSI_STATUS`. `_attribute_definitions` (`:2496–2506`) collects attribute names from all GSI definitions and then calls `attrs.update(table.attr_types)`. Since both GSIs reference the same attribute name `created_at`, a single `attr_types={"created_at": "N"}` entry is sufficient and correct — declaring it twice would be a no-op but is misleading.

### 5.3 `GSI_RECEIPT` has no sort key

`po_receipts.GSI_RECEIPT` uses only a partition key (`receipt_id`). The `TableDef` for `po_receipts` must therefore omit `"sort_key"` from the GSI definition dict; the `_global_secondary_indexes` helper at `scripts/local-ddb-init.py:2516–2531` checks `gsi.get("sort_key")` before appending a RANGE key (the no-sort-key path is safe). The `_key_schema` helper at `scripts/local-ddb-init.py:2509–2513` handles the table's own sort key separately. Matches the pattern at lines `:56–60` where `api_keys`' single GSI has no sort key (`{"index_name": ..., "partition_key": "user_sub"}` with no `"sort_key"` entry).

### 5.4 `_safe_table` wraps `ddb.Table(name)` eagerly at import time

`_safe_table` calls `ddb.Table(name)` during module import of `app.core.tables`. In production this is fine because the table exists in DDB before the app starts. In tests, `ddb.Table(name)` constructs a lightweight boto3 resource object without hitting the network; the actual table must exist in the moto mock before any `put_item`/`query` call is made. The smoke test (section 9.1) only asserts the handle is non-`None` — it does not call any DDB method, so no moto setup is required for the smoke test itself.

### 5.5 `purchase_order_reorder_suggestions_enabled` is independent

The secondary flag allows operators to enable the master purchasing module (PUR-003 through PUR-010) in production before turning on the background reorder-suggestion engine (PUR-011), which emits inventory signals and may produce noise if not yet tuned. The secondary flag is read directly by `app/services/purchasing_reorder.py` (PUR-011) and not by any other purchasing service.

### 5.6 Default table names do not collide with existing tables

Running `grep -r '"suppliers"\|"supplier_products"\|"purchase_orders"\|"po_receipts"'` against `scripts/local-ddb-init.py` returns no existing `TableDef` entries. The default names are safe.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

`_safe_table(S.<name>)` wraps `ddb.Table(name)` which calls the real DynamoDB endpoint in production and the moto-intercepted endpoint in dev. No `dev_mode` branch, no conditional import — identical code path both environments. This pattern is used by all 100+ existing table handles in `app/core/tables.py`.

`scripts/local-ddb-init.py` runs against DynamoDB Local (port 8001) in dev and against the real DynamoDB endpoint in prod (via `AWS_ENDPOINT_URL` or absence thereof). The same `TableDef` list drives both — SECOPS-007 schema parity is automatic.

### Idempotency of table creation

`scripts/local-ddb-init.py` wraps each `create_table` call in a `try/except ClientError` that ignores `ResourceInUseException` (table already exists). Running `just restart` is therefore safe to call multiple times — idempotent table creation is already the convention for all 100+ existing tables.

### Security: no credential surface in this ticket

PUR-002 only adds settings keys, `TableDef` entries, and `_safe_table` wires. No HTTP endpoints are exposed, no IAM policies change, and no data is written. The four new DynamoDB tables will be empty until downstream PUR tickets start writing records.

## 10. Open Questions / Assumptions

1. **Assumption: `purchase_orders` GSI sort key sharing is intentional.** Both `GSI_SUPPLIER` and `GSI_STATUS` sort on `created_at`. This is correct and consistent (same as `returns` at `scripts/local-ddb-init.py:2487–2490`). If PUR-001 decided that an `updated_at`-based sort for `GSI_STATUS` would better reflect queue ordering, `attr_types` would need a second numeric key entry; this spec follows the ticket text verbatim.

2. **Assumption: `po_receipts.GSI_RECEIPT` has no sort key.** The ticket spec says `GSI_RECEIPT (partition receipt_id)` with no sort key mentioned. This means the GSI supports only `get_item`-style lookups (point reads by `receipt_id`). If PUR-009 needs to list receipts by `received_at` across all POs (admin receiving dashboard), a sort key would be needed. This is flagged as an assumption to verify in PUR-009 design.

3. **Assumption: `purchase_order_reorder_suggestions_enabled` is sufficient granularity.** The ticket lists this as a distinct settings key. If PUR-011 is broken into smaller sub-features (e.g., signal emission vs. PO auto-creation), additional flags may be needed. This spec implements exactly what the ticket text states.

4. **Assumption: No TTL is needed on any of the four tables at this milestone.** `suppliers`, `supplier_products`, and `purchase_orders` are permanent business records. `po_receipts` are permanent audit records. TTL would only be appropriate for a soft-delete/archival pattern added in a future milestone. The `_enable_ttl_if_needed` calls at `scripts/local-ddb-init.py:2672–2696` are not required here.

5. **Assumption: Default table names do not collide with existing DynamoDB tables.** Verified by grep above. However, in a shared AWS account with other services, the operator should set explicit values via env var (e.g., `SUPPLIERS_TABLE_NAME=purchasing_suppliers`) to avoid potential collisions.

6. **Assumption: `Tables` dataclass field order does not matter for Python.** The `Tables` dataclass is `frozen=True` and constructed with keyword arguments in `T = Tables(...)`. Appending new fields at the end does not change the positional layout of existing fields and will not break any `T.existing_field` access.
