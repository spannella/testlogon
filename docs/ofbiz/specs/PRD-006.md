# PRD-006 — Product feature & feature-category model

**Type:** Feature | **Priority:** P0 | **Estimate:** 4 days
**Milestone:** 3 — Variants & Features/Options

---

## 1. Summary & Goal

PRD-006 introduces the OFBiz `ProductFeature` / `ProductFeatureCategory` / `ProductFeatureAppl` triad as a pure-service layer, with no router endpoints (those arrive in PRD-008). It creates `app/services/product_features.py` providing five functions:

1. `create_feature_category` — create a named axis (e.g. "Color", "Size") owned by a user.
2. `add_feature_value` — add a single selectable value (e.g. "Red", "XL") to an axis, with an optional signed `price_delta_cents` and `position`.
3. `list_feature_categories` — paginate all categories owned by a user, optionally hydrating their values.
4. `attach_feature_category_to_product` — write a `ProductFeatureAppl`-style link (`FTAPPL#{fc_id}`) onto an item row in `T.product_depth`, recording which feature axis applies to a product.
5. `list_product_features` — resolve all attached feature categories for an item, with their values ordered by `position` ascending.

Guard every public function with `_require_enabled()` that checks `S.product_depth_features_enabled` (sub-flag) AND `S.product_depth_enabled` (master). With either flag off the functions raise `HTTP 404`; the catalog/cart/orders/billing paths remain byte-for-byte unchanged.

Deletion of an in-use feature category is blocked: `delete_feature_category` refuses to proceed if any `FTAPPL#` row references the category.

### 2.5 Idempotency / deterministic ID pattern

`app/core/crypto.py:13` ✓ provides `sha256_str(s: str) -> str` (hexdigest). The returns/RMA service uses deterministic IDs for idempotent replay. PRD-006 follows the same convention: `feature_category_id` is caller-supplied or `uuid4().hex`; `feature_value_id` is `sha256_str(f"{fc_id}:{name.strip().lower()}")[:16]` — giving the same ID for the same (category, name) pair, so duplicate `add_feature_value` calls with identical inputs are idempotent (conditional `put_item` on `attribute_not_exists(PK) AND attribute_not_exists(SK)` will silently accept a re-put of the same row or raise `ConditionalCheckFailedException` which the service catches and returns the existing row).

## 3. Data Model

All rows land on `T.product_depth`. No rows land on `T.catalog`. The table is declared by PRD-002 (`scripts/local-ddb-init.py`; no changes needed here).

### 3.1 Feature-category row

```
PK   = "FTCAT#{feature_category_id}"
SK   = "META"
entity       = "feature_category"
feature_category_id  (str)
name         (str)   — display label, e.g. "Color"
description  (str | absent)
creator_id   (str)   — user_sub of the owner
created_at   (int)   — Unix timestamp; now_ts()
updated_at   (int)   — Unix timestamp; now_ts()
```

No GSI attributes needed on this row (looked up by PK+SK only). Inserted via `put_item` with `attribute_not_exists(PK) AND attribute_not_exists(SK)` condition.

### 3.2 Feature-value row

```
PK   = "FTCAT#{feature_category_id}"
SK   = "FTVAL#{feature_value_id}"
entity              = "feature_value"
feature_value_id    (str)   — sha256_str(f"{fc_id}:{name_lower}")[:16]
feature_category_id (str)
name                (str)   — display label, e.g. "Red"
price_delta_cents   (int)   — signed; may be negative (0 default)
position            (int)   — display order within the category, 0-based; ge=0 le=9999
creator_id          (str)
created_at          (int)
updated_at          (int)
GSI_FTCAT_PK  = "FTCAT#{feature_category_id}"
GSI_FTCAT_SK  = position   (int, numeric — MUST be N in attr_types per CLAUDE.md gotcha)
```

The `ByFeatureCategory` GSI (partition `GSI_FTCAT_PK`, sort `GSI_FTCAT_SK`) enables a single O(1) query returning all values for a feature category, ordered by `position`.

### 3.3 Feature-application row (ProductFeatureAppl)

```
PK   = "ITEM#{item_id}"
SK   = "FTAPPL#{feature_category_id}"
entity              = "feature_appl"
item_id             (str)
feature_category_id (str)
creator_id          (str)   — user_sub who created the attach link
created_at          (int)
```

No GSI needed: to list all attached categories for an item, the service issues `query(PK="ITEM#{item_id}", SK begins_with "FTAPPL#")`. To list all items using a feature category, callers iterate via a filter (PRD-006 does not need a reverse index; that is a future optimization if needed).

### 3.4 Attribute-type declaration (PRD-002 responsibility, confirmed here)

`GSI_FTCAT_SK` must be declared `"N"` in `attr_types`. This is already in the PRD-002 `TableDef` (`docs/ofbiz/specs/PRD-002.md:§3.1`). PRD-006 does not modify `scripts/local-ddb-init.py`; it relies on the PRD-002 table definition. If PRD-002 has not shipped, the `ByFeatureCategory` GSI queries will fail with `ValidationException` at runtime.

## 4. API / Service Design

### 4.1 Module: `app/services/product_features.py`

All functions are synchronous (the catalog router is async but calls synchronous service helpers via direct call, not `asyncio.to_thread` — same pattern as `app/services/inventory.py` called from `app/routers/catalog.py`).

#### Internal helpers

```python
def _flag_on() -> bool:
    return (
        bool(getattr(S, "product_depth_enabled", False))
        and bool(getattr(S, "product_depth_features_enabled", True))
    )

def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="Product features are not enabled")

def _fc_pk(fc_id: str) -> str:
    return f"FTCAT#{fc_id}"

def _fv_sk(fv_id: str) -> str:
    return f"FTVAL#{fv_id}"

def _appl_sk(fc_id: str) -> str:
    return f"FTAPPL#{fc_id}"

def _item_pk(item_id: str) -> str:
    return f"ITEM#{item_id}"

def _fv_id(fc_id: str, name: str) -> str:
    """Deterministic feature-value id: sha256(fc_id + ":" + name_lower)[:16]."""
    from app.core.crypto import sha256_str
    return sha256_str(f"{fc_id}:{name.strip().lower()}")[:16]

def _audit(event: str, user_sub: str, **fields: Any) -> None:
    try:
        from app.services.alerts import audit_event
        audit_event(event, user_sub or "system", None, **fields)
    except Exception:
        pass
```

#### `create_feature_category`

```python
def create_feature_category(
    name: str,
    user_sub: str,
    *,
    feature_category_id: Optional[str] = None,
    description: Optional[str] = None,
) -> Dict[str, Any]:
```

- Calls `_require_enabled()`.
- `fc_id = feature_category_id or uuid.uuid4().hex`.
- Builds item with `PK=_fc_pk(fc_id)`, `SK="META"`, and all required attrs.
- `T.product_depth.put_item(Item=..., ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)")`.
- On `ConditionalCheckFailedException` → raises `HTTP 409 "Feature category already exists"`.
- Emits `_audit("product_feature_category.created", user_sub, fc_id=fc_id)`.
- Returns the raw DDB item dict (router/test projects into `ProductFeatureCategoryOut`).

#### `get_feature_category`

```python
def get_feature_category(fc_id: str) -> Optional[Dict[str, Any]]:
```

- `T.product_depth.get_item(Key={"PK": _fc_pk(fc_id), "SK": "META"}).get("Item")`.
- Returns `None` if absent (caller raises 404).

#### `list_feature_categories`

```python
def list_feature_categories(
    user_sub: str,
    *,
    include_values: bool = False,
    limit: int = 50,
    exclusive_start_key: Optional[Dict[str, Any]] = None,
) -> Tuple[List[Dict[str, Any]], Optional[Dict[str, Any]]]:
```

- Calls `_require_enabled()`.
- Performs a `scan` on `T.product_depth` with `FilterExpression="entity = :e AND creator_id = :u"` (small owner-scoped data set; full-table scan acceptable given the product_depth table is sparse in early usage; a future GSI for `creator_id` is an open question).
- If `include_values=True`, for each category, calls `_list_values_for_category(fc_id)` to hydrate `values`.
- Returns `(items, last_evaluated_key)`.

#### `add_feature_value`

```python
def add_feature_value(
    fc_id: str,
    name: str,
    user_sub: str,
    *,
    price_delta_cents: int = 0,
    position: int = 0,
) -> Dict[str, Any]:
```

- Calls `_require_enabled()`.
- Validates: `abs(price_delta_cents) <= 10_000_000_00` (same bound as `price_cents` in `CatalogItemCreateIn`, `app/models.py:542` ✓); `0 <= position <= 9999`.
- Verifies the feature category exists via `get_feature_category(fc_id)`: missing → `HTTP 404 "Feature category not found"`.
- Verifies `creator_id == user_sub` (ownership check): mismatch → `HTTP 403 "Not authorized"`.
- `fv_id = _fv_id(fc_id, name)`.
- Builds item with `PK=_fc_pk(fc_id)`, `SK=_fv_sk(fv_id)`, and GSI attrs `GSI_FTCAT_PK`, `GSI_FTCAT_SK=position`.
- `T.product_depth.put_item(Item=..., ConditionExpression="attribute_not_exists(PK) AND attribute_not_exists(SK)")`.
- On `ConditionalCheckFailedException` → reads the existing row and returns it unchanged (idempotent: same `(fc_id, name)` → same `fv_id` → same SK → same conditional fails → same row returned).
- Emits `_audit("product_feature_value.added", user_sub, fc_id=fc_id, fv_id=fv_id, name=name)`.
- Returns item dict.

#### `get_feature_value`

```python
def get_feature_value(fc_id: str, fv_id: str) -> Optional[Dict[str, Any]]:
```

- `T.product_depth.get_item(Key={"PK": _fc_pk(fc_id), "SK": _fv_sk(fv_id)}).get("Item")`.

#### `_list_values_for_category`

```python
def _list_values_for_category(
    fc_id: str,
    *,
    limit: int = 500,
) -> List[Dict[str, Any]]:
```

- Queries `T.product_depth` via the `ByFeatureCategory` GSI:
  ```python
  T.product_depth.query(
      IndexName="ByFeatureCategory",
      KeyConditionExpression=Key("GSI_FTCAT_PK").eq(f"FTCAT#{fc_id}"),
      ScanIndexForward=True,   # ascending position
      Limit=limit,
  )
  ```
- Returns `resp["Items"]` sorted by `position` ascending (GSI sort handles it; explicit Python sort by `position` as secondary insurance).

#### `attach_feature_category_to_product`

```python
def attach_feature_category_to_product(
    item_id: str,
    fc_id: str,
    user_sub: str,
) -> Dict[str, Any]:
```

- Calls `_require_enabled()`.
- Verifies the feature category exists via `get_feature_category(fc_id)`: missing → `HTTP 404 "Feature category not found"`.
- Verifies feature-category `creator_id == user_sub`: mismatch → `HTTP 403`.
- Writes `FTAPPL#{fc_id}` row onto `T.product_depth` at `PK=_item_pk(item_id)`, `SK=_appl_sk(fc_id)`.
- Uses `put_item` without `attribute_not_exists` condition (attach is idempotent; re-attaching the same category is a no-op at the data level).
- Emits `_audit("product_feature_appl.created", user_sub, item_id=item_id, fc_id=fc_id)`.
- Returns the written item dict.

#### `list_product_features`

```python
def list_product_features(
    item_id: str,
) -> List[Dict[str, Any]]:
```

- Calls `_require_enabled()`.
- Queries `T.product_depth` for all `FTAPPL#` rows on the item:
  ```python
  T.product_depth.query(
      KeyConditionExpression=Key("PK").eq(_item_pk(item_id)) & Key("SK").begins_with("FTAPPL#"),
  )
  ```
- For each `FTAPPL` row, resolves the feature category META row (via `get_feature_category`) and its values (via `_list_values_for_category`).
- Returns a list of dicts shaped like `ProductFeatureCategoryOut`, with `values` populated and ordered by `position`.
- If the item has no FTAPPL rows, returns `[]` (non-virtual/non-variant items have zero features; the function is a pure no-op for them, preserving existing standalone behavior unchanged).

#### `delete_feature_value`

```python
def delete_feature_value(fc_id: str, fv_id: str, user_sub: str) -> None:
```

- Calls `_require_enabled()`.
- Verifies ownership via `get_feature_category(fc_id)`.
- Deletes `T.product_depth` item `(FTCAT#{fc_id}, FTVAL#{fv_id})`.
- Emits `_audit("product_feature_value.deleted", user_sub, fc_id=fc_id, fv_id=fv_id)`.

#### `delete_feature_category`

```python
def delete_feature_category(fc_id: str, user_sub: str) -> None:
```

- Calls `_require_enabled()`.
- Verifies ownership.
- **In-use guard**: queries T.product_depth for any `FTAPPL#{fc_id}` row across all items using a GSI scan OR a table scan with filter `SK = "FTAPPL#{fc_id}"`. Implementation detail: a `scan` with `FilterExpression=Attr("SK").eq(_appl_sk(fc_id))` finds all items using this category. If any rows exist → `HTTP 409 "Feature category is in use by one or more products. Detach it first."`.
- If unused: batch-deletes all feature-value rows for the category via `_list_values_for_category(fc_id)` + `batch_writer().delete_item`.
- Deletes the META row.
- Emits `_audit("product_feature_category.deleted", user_sub, fc_id=fc_id)`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Duplicate feature-value name within a category

Two calls `add_feature_value(fc_id, "Red", user_sub)` produce the same `fv_id = _fv_id(fc_id, "red")` (normalized to lowercase before hashing). The second call hits `ConditionalCheckFailedException`, fetches the existing row, and returns it unchanged. This is the correct idempotency contract: the caller receives the same logical value regardless of how many times it issues the request.

### 5.2 Case-sensitivity in feature-value naming

`_fv_id` normalizes `name.strip().lower()` before hashing, so "Red" and "red" map to the same `fv_id`. The stored `name` attribute reflects the first write's original casing. A subsequent call with a different casing (e.g. "RED") is idempotent (returns existing row) rather than creating a duplicate.

### 5.3 `price_delta_cents` sign validation

`price_delta_cents` is a signed int: positive means the variant costs more (e.g. "+500" for "XL"), negative means it costs less. The bound is `ge=-10_000_000_00, le=10_000_000_00` (same magnitude as `CatalogItemCreateIn.price_cents`, `app/models.py:542` ✓). Validation is in `add_feature_value` (service layer), not only in the Pydantic model, so direct service calls also enforce it.

### 5.4 Position ordering

The `ByFeatureCategory` GSI sorts by `GSI_FTCAT_SK` (= `position`, numeric). Multiple feature values may share the same `position` integer — DynamoDB GSI order within the same partition/sort value is stable within a batch but unspecified across writes. The service sorts the Python result by `(position, name)` as a secondary tie-breaker to produce a deterministic order.

### 5.5 Attaching a category to a non-existent item

`attach_feature_category_to_product` does NOT verify that `item_id` references a valid catalog item. The FTAPPL row's `PK = "ITEM#{item_id}"` is a logical reference — the catalog item lives on `T.catalog`, and cross-table foreign-key enforcement is not available in DynamoDB. PRD-008 (router layer) MUST call `_find_item_by_id(item_id)` (`app/routers/catalog.py:702` ✓) before calling `attach_feature_category_to_product`. The service itself only verifies the feature-category half of the link.

### 5.6 Re-attaching a category (idempotency of attach)

`attach_feature_category_to_product` is unconditional (`put_item` without `attribute_not_exists`). Re-attaching the same `(item_id, fc_id)` pair is a no-op: it overwrites the existing row with identical data (same `created_at` and `creator_id` are preserved since they are always written from the same source). This is intentionally lenient: attach-twice is not an error.

### 5.7 Deleting a feature category while values exist

`delete_feature_category` deletes all child `FTVAL#` rows before deleting the META row (via batch writer). This runs without a transaction — if the batch fails mid-way, orphaned FTVAL rows remain. The re-run of `delete_feature_category` will attempt the same cleanup again (idempotent due to DynamoDB `delete_item` being a no-op for missing keys). A compensating transaction is out of scope for this ticket.

### 5.8 `list_feature_categories` scan behavior

The scan uses `FilterExpression` with `creator_id`. Per the CLAUDE.md gotcha: "DDB FilterExpression doesn't reduce page size" — the scan fetches up to 1MB before filtering. For large deployments this degrades, but the `product_depth` table is expected to be sparse. A `creator_id` GSI is listed as an open question (§10).

### 5.9 Feature values belonging to multiple categories

A feature value is uniquely scoped to one feature category (its `PK = FTCAT#{fc_id}`). There is no cross-category sharing of values in this design (unlike OFBiz's ProductFeature table which allows reuse). Each category independently owns its value rows.

### 5.10 Blocking deletion of in-use feature values (individual values)

`delete_feature_value` does NOT check whether the value is referenced in a variant selection row (`VAR#` row on `T.product_depth`). That check is PRD-007's responsibility — variant creation references `feature_value_id` values, and PRD-007 must handle the case where a referenced value is deleted. PRD-006 only enforces that the category-level deletion is blocked when categories are attached to products.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

All DynamoDB operations in `app/services/product_features.py` use `T.product_depth` — the same table handle in dev (moto-backed local DDB) and prod (real DynamoDB). No `S.dev_mode` branches. No mock paths. The only environment difference is the DDB endpoint URL injected via `AWS_ENDPOINT_URL`, which is handled transparently by `T.product_depth` (via `_safe_table` at `app/core/tables.py:65` ✓).

### 7.2 Idempotency

| Operation | Idempotency mechanism |
|---|---|
| `create_feature_category` | Conditional `attribute_not_exists` → 409 on duplicate `fc_id`; caller-supplied `fc_id` allows deterministic replay. |
| `add_feature_value` | `fv_id = sha256(fc_id:name_lower)[:16]` → same `(fc_id, name)` always yields same `fv_id`; conditional put + catch returns existing row on replay. |
| `attach_feature_category_to_product` | Unconditional `put_item` — idempotent overwrite. |
| `delete_feature_value` / `delete_feature_category` | `delete_item` is a no-op for missing keys — replay safe. |

### 7.3 Ownership enforcement

- Only the `creator_id` owner of a feature category may add values to it, attach it to a product, or delete it.
- `creator_id` is set at `create_feature_category` time from the authenticated `user_sub` and never updated.
- The ownership check (`creator_id == user_sub`) is in every mutating service function. The router layer (PRD-008) adds an additional check via `_require_category_owner` on the catalog side, but the service must not rely on the router performing this check.
- ROOT/ADMIN users are not given special bypass in the service layer. If an admin needs to modify a feature category owned by another user, a separate admin-override path (out of scope) would be required.

### 7.4 Input sanitization

- `name.strip()` is applied before storing to avoid leading/trailing whitespace inconsistencies.
- `name` max length is 128 (enforced by the PRD-003 `ProductFeatureCreateIn` Pydantic model; service re-checks with `len(name) > 128 → HTTP 400`).
- `feature_category_id` and any user-supplied IDs are validated as non-empty strings (max 64 chars).

## 8. Backward Compatibility & Migration

### 8.1 Existing catalog endpoints unchanged

With `PRODUCT_DEPTH_ENABLED=false` (the default), no code path in the existing catalog, cart, or billing flow touches `product_features.py`. The `T.product_depth` table handle is wired by PRD-002 but is never queried by pre-depth code. Zero migration is required.

### 8.2 `CatalogItemOut` extension

PRD-003 extends `CatalogItemOut` with `has_features: bool = False`. The existing `_catalog_item_out` at `app/routers/catalog.py:107` ✓ never passes `has_features=`, so it defaults to `False` in every existing serialization. When PRD-008 wires the router to call `list_product_features`, it will inject `has_features=True` when the returned list is non-empty. This is additive and does not change existing client contracts.

> **NOTE (verification):** `CatalogItemOut` at `app/models.py:672` does not yet carry `has_features` — PRD-003 has not shipped. The existing 10-field shape is preserved; the `has_features` addition is a PRD-003 deliverable.

### 8.3 `product_depth` table on first `just restart`

The `product_depth` table is created by `scripts/local-ddb-init.py` on every `just restart` (added by PRD-002). It starts empty. No backfill or migration is needed for existing `shopping_catalog` data — feature categories are net-new entities with no relation to existing `ITEM#` or `CAT#` rows until explicitly created and attached.

### 8.4 Production deployment order

1. Deploy PRD-002 (table + settings + flag; flag defaults OFF).
2. Deploy PRD-003 (models only; no runtime behavior change).
3. Deploy PRD-006 (service module; still dormant behind flag).
4. Enable flag `PRODUCT_DEPTH_ENABLED=true` + `PRODUCT_DEPTH_FEATURES_ENABLED=true` after smoke tests pass.

No `UpdateTable` backfill is required because the `product_depth` table is new and starts empty.

### 9.2 E2E spec — `frontend/e2e/product-features.spec.ts`

This spec exercises the PRD-008 HTTP endpoints that are gated on PRD-006. It lives in the same spec suite as `catalog-subscriptions.spec.ts` but in a separate file (to avoid contaminating the pre-depth catalog tests).

Sections:

- **Section A — Feature-category CRUD API**: `POST /feature-categories` (create); `GET /feature-categories` (list); `DELETE /feature-categories/{id}` (blocked if in use, succeeds if unused).
- **Section B — Feature-value API**: `POST /feature-categories/{id}/values` (add value, idempotent second call); ordering by position; reject out-of-bound `price_delta_cents`.
- **Section C — Attach and list**: `POST /items/{id}/feature-categories` (attach); `GET /items/{id}/features` returns values ordered by position.

Auth: all endpoints use `require_ui_session` (cookie auth via `injectAuth(page, "alice")`); non-owner operations use `injectAuth(page, "bob")` and expect 403.

## 10. Open Questions / Assumptions

1. **Assumption: PRD-002 ships before PRD-006.** `T.product_depth`, `S.product_depth_enabled`, and `S.product_depth_features_enabled` are consumed but not defined in this ticket. If PRD-002 is not deployed, the service module will fail to import (`AttributeError: 'Tables' object has no attribute 'product_depth'`). The `getattr(S, "product_depth_enabled", False)` guard in `_flag_on()` uses `getattr` with a default to survive a settings object that lacks the key; the `T.product_depth` reference does not have the same protection. Mitigation: the module's module-level code must not reference `T.product_depth` at import time — only inside function bodies, so the import succeeds even without PRD-002.

2. **Assumption: PRD-003 models are importable.** `ProductFeatureCreateIn`, `ProductFeatureOut`, `ProductFeatureCategoryOut` are expected in `app/models.py`. If PRD-003 has not shipped, the service module's callers will fail at model construction. PRD-006 service functions return raw dicts and do not directly import these models; the router (PRD-008) does the import. This decoupling means PRD-006 can be developed and unit-tested without PRD-003, as long as PRD-003 ships before PRD-008.

3. **Open question: `list_feature_categories` scan vs. creator-id GSI.** The current design uses a full-table scan with `FilterExpression="entity = :e AND creator_id = :u"`. For very large deployments this degrades. Adding a `ByCreator` GSI (`partition = creator_id`, sort = `created_at`) to `T.product_depth` would fix this. The PRD-002 spec did not include this GSI. Options: (a) accept scan for now, add GSI in a follow-up; (b) amend PRD-002 to add the GSI before shipping. **Recommendation**: accept scan for now; add GSI in a follow-up once usage patterns are understood.

4. **Open question: global feature-category visibility.** The current design scopes feature categories to their `creator_id` (catalog owner). A marketplace model where multiple sellers share a "Color" axis is not addressed. Assumption: each seller owns their own categories; a shared-category model is a future milestone.

5. **Assumption: `delete_feature_value` does not block on variant references.** PRD-007 creates variant rows referencing `feature_value_id`. Deleting a value that is referenced by a live variant is currently not blocked at the service level. PRD-007 MUST either (a) add a guard in `delete_feature_value` by querying variant rows, or (b) tolerate stale value references gracefully. This is PRD-007's responsibility, noted here for the handoff.

6. **Assumption: `position` uniqueness is not enforced.** Two feature values may share the same `position` integer. Tie-breaking is done by `(position, name)` alphabetically in the Python layer. Enforcing uniqueness would require a transaction or a conditional write that is not implemented here.

7. **Open question: feature-category attach — item ownership verification.** The service `attach_feature_category_to_product` verifies that the caller owns the feature category but does NOT verify that the caller owns the catalog item. The PRD-008 router must call `_find_item_by_id` and `_require_category_owner` before calling `attach_feature_category_to_product`. If PRD-008 forgets this check, any user can attach their own feature category to someone else's product item (silently writing an FTAPPL row). This is an ownership gap that must be explicitly documented in PRD-008.
