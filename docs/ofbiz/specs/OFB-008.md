# OFB-008 — Return/RMA entity & request flow

**Type:** Feature | **Priority:** P0 | **Estimate:** 4 days
**Milestone:** 3 — Returns / RMA
**Depends on:** OFB-002 (scaffolding: tables, settings, flags)
**Downstream:** OFB-009 (approve/reject/receive + restock), OFB-010 (refund via billing), OFB-011 (UI), OFB-012 (E2E)

---

## 1. Summary & Goal

OFB-008 delivers the **return/RMA entity model and the customer request flow**. It is the foundation that OFB-009, OFB-010, OFB-011, and OFB-012 build on.

Specifically, this ticket:

1. Creates `app/services/returns_rma.py` — the service layer for the returns entity, including the `request_return` function that opens a return against a purchased order, all validation logic (ownership, per-line quantity bounds, duplicate-open guard), the `get_return` / `list_returns_for_order` helpers, and the complete status-transition machinery (`_transition`, `_require_transition`, `_VALID_TRANSITIONS`) that the admin-decision tickets (OFB-009/010) will drive.
2. Creates `app/routers/returns_rma.py` — the FastAPI router with customer-facing endpoints registered under `require_ui_session`, and the admin endpoint stubs (registered under `require_admin_or_root_csrf`) that are fully exercised by OFB-009/010.
3. Registers the router in `app/main.py` under the existing `include_router` pattern.
4. The entire feature is guarded by `S.returns_rma_enabled` (default `False`); every handler raises HTTP 404 when the flag is off.

The goal is a **complete returns entity** — header + per-line items stored in DynamoDB single-table, keyed off existing `orders` / `order_items` records — and a **correct customer request flow** that the admin and refund tiers plug into without touching.

## 3. Data Model

### 3.1 `returns` table (single-table design)

Table name: `S.returns_table_name` (default `"returns"`). Already in `scripts/local-ddb-init.py:2483`.

| Attribute | Type | Notes |
|-----------|------|-------|
| `return_id` | S (PK) | `uuid.uuid4().hex` — 32-char hex, globally unique. Not deterministic-id (there is no natural correlation_id at request time; idempotency is enforced via the one-open-return-per-order 409 guard). |
| `sk` | S (SK) | `"META"` for the header row; `"ITEM#{idx}"` (1-indexed, zero-padded not required) for each return line. |
| `order_id` | S | On header (META) only. Projected onto `GSI_ORDER`. Line rows do NOT store `order_id` so they are invisible to the GSI query. |
| `user_sub` | S | On header only. Ownership check: foreign-owner return → 404. |
| `status` | S | Header only. Values: `requested`, `approved`, `rejected`, `received`, `refunded`, `closed`. Projected onto `GSI_STATUS`. |
| `reason` | S | Header only. Customer-supplied return reason, max 500 chars. |
| `currency` | S | Header only. Inherited from the originating order record. Lowercase (e.g. `"usd"`). |
| `refund_amount_cents` | N | Header only. Initialised `0`; written by OFB-010 refund transition. |
| `refund_ledger_sk` | S | Header only. Written post-refund as a linkage back to the billing ledger row. |
| `provider` | S | Header only. Written by OFB-010; mirrors `extra={"provider": ...}` (FIN-013). |
| `decided_by` | S | Header only. Admin sub set on approve/reject. |
| `decision_note` | S | Header only. Optional free-text note from admin. |
| `created_at` | N | Header and line rows. Integer Unix timestamp from `now_ts()`. GSI sort key — **must** be `"N"` in `attr_types`. |
| `updated_at` | N | Header only. Integer Unix timestamp, updated on every transition. |
| `line_no` | N | Line rows only. 1-based integer; used for deterministic ordering in `_return_header_out`. |
| `item_id` | S | Line rows only. Matches `order_items.item_id` on the parent order. |
| `sku` | S | Line rows only. Denormalized from `order_items.sku` at request time. |
| `quantity` | N | Line rows only. Requested return quantity (1..purchased). |
| `amount_cents` | N | Line rows only. Prorated: `unit_price_cents × quantity`. |

### 3.2 GSIs

Both GSIs are already declared in `scripts/local-ddb-init.py:2488–2491` with `attr_types={"created_at": "N"}`:

| GSI name | PK | SK | Purpose |
|----------|----|----|---------|
| `GSI_ORDER` | `order_id` (S) | `created_at` (N) | List all returns for an order (duplicate-open guard; OFB-011 order detail view). Line rows carry no `order_id` attribute, so only META rows appear. |
| `GSI_STATUS` | `status` (S) | `created_at` (N) | Admin RMA queue by status (OFB-009 `GET /ui/returns/admin/queue`). Only META rows projected. |

### 3.3 No GSI_USER

The `returns` table has no `GSI_USER` (keyed on `user_sub`). This is intentional for Milestone 3: a customer's returns are reachable by first fetching their orders via `T.orders`'s existing `GSI_USER` and then querying `GSI_ORDER` per-order. A direct `GSI_USER` can be added in a later milestone if the "My Returns" list becomes a high-read path. See Section 10.

### 3.4 Reused tables (read-only for OFB-008)

- `T.orders` (PK=`order_id`): ownership check; currency; `ledger_sk` and `payment_intent_id` read by OFB-010.
- `T.order_items` (PK=`order_id`, SK=`item_id`): purchased quantity and unit price for validation and proration.

No schema changes are made to either table.

## 5. Detailed Behavior & Edge Cases

### 5.1 `request_return` validation flow

Executed in this order:

1. **Flag check** — `_require_enabled()` → HTTP 404 if `S.returns_rma_enabled` is off.
2. **Order ownership** — `T.orders.get_item(Key={"order_id": order_id})`. Not found or `order["user_id"] != user_sub` → HTTP 404 ("Order not found"). Returns 404 rather than 403 to avoid leaking existence of foreign orders.
3. **Order line items** — query `T.order_items` by PK=`order_id` with full pagination. Empty result → HTTP 404 ("Order has no line items").
4. **Duplicate-open guard** — query `GSI_ORDER` via `list_returns_for_order(order_id)`. If any returned META row has `status in _OPEN_STATUSES` → HTTP 409 ("An open return already exists for this order"). One open return per order at a time.
5. **Non-empty lines** — `len(lines) == 0` → HTTP 422.
6. **Per-line validation** (iterate each line):
   - Duplicate `item_id` within the request → HTTP 422.
   - `item_id` not found in `order_items` dict → HTTP 422 (`f"Item {item_id} is not on order {order_id}"`).
   - `quantity < 1 or quantity > purchased_qty` → HTTP 422 (`f"quantity for item {item_id} must be 1..{purchased}"`).
7. **Amount proration** — `unit_price_cents = order_item["amount_cents"] // max(1, purchased_qty)`. Line `amount_cents = unit_price_cents * requested_qty`.
8. **Write** — `T.returns.put_item(Item=header)` then one `put_item` per line row (not transactional; partial write is benign since the header drives all state transitions).
9. **Audit** — `rma.requested` event with `return_id`, `order_id`, `line_count`, `reason`.

### 5.2 Status transition graph

```
requested ──────────────── approved ──── received ──── refunded ──── closed
     \                         \
      └── rejected               └── rejected
```

Terminals: `rejected`, `closed` (no further transitions).

`_require_transition(current, target)`:
- `current == target` → no-op (idempotent replay; the DDB conditional will return `None` and the caller re-reads and returns current state).
- `target not in _VALID_TRANSITIONS[current]` → HTTP 409 (`f"Illegal return transition {current} -> {target}"`).

### 5.3 Concurrency / idempotency

The `_transition` function uses a **single-writer conditional update**:
```python
T.returns.update_item(
    Key={"return_id": return_id, "sk": "META"},
    UpdateExpression="SET #s = :to, updated_at = :now [, extra fields]",
    ConditionExpression="#s = :from",
    ReturnValues="ALL_OLD",
)
```
On `ConditionalCheckFailedException`, it returns `None`. The caller re-reads and returns current state. This makes every admin action safe to replay and race-condition-resistant.

### 5.4 Quantity over-return prevention

The current design blocks **one open return per order** rather than tracking per-item returnable quantity. If Alice returns 2 of 4 units and the return is closed (`closed` is terminal), she can open a second return for the remaining 2. If she tries to open a second return while the first is still open → 409.

This is intentional: tracking partial returns per item would require summing `ITEM#` rows across all historical returns per order, which adds complexity beyond the OFB-008 scope. Quantity granularity within a single return is fully validated (1..purchased).

### 5.5 Currency normalisation

The return inherits its `currency` from the originating order record: `str(order.get("currency", "usd")).lower()`. This is passed through to the refund path (OFB-010) to drive the billing `apply_balance_delta` `currency` argument.

### 5.6 Missing `list_my_returns` endpoint

The current router only exposes `GET /ui/returns/{return_id}` for customers — there is no "list all my returns" endpoint. A customer who knows the `return_id` can read it; a customer who wants to browse their history must go via the order detail page (OFB-011). If a direct `GET /ui/returns` endpoint is needed for OFB-011, it would require either: (a) a `GSI_USER` on the `returns` table, or (b) scanning orders via `GSI_USER` + querying `GSI_ORDER` per-order. See Section 10.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

There is no `if S.dev_mode` branch in the service layer. All DynamoDB operations run against the same code path in dev (DynamoDB Local via moto in tests, or DynamoDB Local on port 8001 in the running stack) and prod (real DynamoDB). The `_audit` and `_notify` helpers use best-effort lazy imports and swallow exceptions so they never fail the main flow, but they run the same code both envs.

### Idempotency

- **`request_return`**: not idempotent by design. A second request for the same order while one is open returns 409. After the first return closes, a new one can be opened.
- **`_transition`**: idempotent via the conditional update. Replaying the same transition with the same `from_status` when the record is already in `to_status` returns `None` (the condition `#s = :from` fails) and the caller returns the current state — no double write.
- **`refund_return`** (OFB-010): idempotent via the same single-writer guard. The billing ledger entry is only written on the first successful `received → refunded` transition.

### Security

- **Ownership enforcement**: `order["user_id"] != user_sub` → HTTP 404. The router's `get_return` also returns 404 for foreign return IDs, not 403, so existence is never leaked.
- **Admin gate**: all `/admin/*` endpoints use `require_admin_or_root_csrf`, which enforces both role (`ADMIN` or `ROOT`) and CSRF for cookie-authenticated requests (`app/auth/policy.py:100–106`).
- **Input bounds**: `ReturnLineIn.quantity` has `ge=1, le=10_000_000` (Pydantic). `ReturnRequestIn.reason` has `max_length=500`. `order_id` has `max_length=128`.
- **No PII in audit fields**: `audit_event` receives `return_id`, `order_id`, `line_count`, `reason` — no payment card data, no PII beyond the user sub (which is always the audit subject).

## 8. Backward Compatibility & Migration

### No schema changes to existing tables

`orders` and `order_items` are read-only for OFB-008. No GSI is added to them. No attribute is added to their rows.

### DynamoDB table creation

The `returns` table is created by `scripts/local-ddb-init.py` when `just restart` (or `just up`) runs. Because `local-ddb-init.py` uses `create_table` (not `update_table`), `just restart` will recreate the table from scratch in dev. In a production environment, this table must be provisioned ahead of deployment (standard pre-deploy migration: run `local-ddb-init.py` or equivalent CloudFormation/Terraform with `RETURNS_TABLE_NAME` matching the env var).

### Flag-off safety

Before the flag is flipped on in any environment, no returns data exists and no returns code path runs. **CORRECTED**: `_safe_table` (`app/core/tables.py:65`) always returns a `_FloatSafeTable` object wrapping `ddb.Table(name)` — it never returns `None`. The table object is created eagerly at module import time regardless of whether the physical DynamoDB table exists; errors only surface on the first actual DDB call. However, `_require_enabled()` will have already raised HTTP 404 before any `T.returns` call is reached when the flag is off, so a missing table in that case never causes a runtime error.

### Order `created_at` type inconsistency

The `orders` table's `GSI_USER` and `GSI_STATUS` declare `created_at` as a sort key but the `orders` `TableDef` in `scripts/local-ddb-init.py:287–294` has no `attr_types` override — meaning `orders.created_at` is an ISO string, not an integer. OFB-008 does not change this. The `returns` table correctly uses integer `created_at` (with `attr_types={"created_at": "N"}`).

## 10. Open Questions / Assumptions

1. **Assumption**: `orders.user_id` is the correct ownership field (not `user_sub`). `CommerceOrderService.create_order` stores `user_id` as the caller's `user_sub` (`app/services/commerce_order_service.py:42` — `user_id: str` parameter; stored at line `74` as `"user_id": user_id`). Verified: the ownership check in `request_return` (`app/services/returns_rma.py:189`) uses `order.get("user_id") != user_sub`. This is correct as long as orders are always created with the user's sub as the `user_id` argument.

2. **Assumption**: The one-open-return-per-order rule applies globally across all item lines. An alternative design would allow concurrent per-item returns (one per SKU). The current design is simpler and aligns with the ticket's "duplicate-open-return" language.

3. **Open question**: Should `POST /ui/returns` return HTTP 201 (resource created) or 200? The ticket does not specify. Standard REST convention for a creation endpoint is 201; the spec mandates 201.

4. **Open question**: Is there a customer `GET /ui/returns` (list all my returns) endpoint needed for OFB-011's "My Returns" view? The current router only exposes `GET /ui/returns/{return_id}`. Options:
   - Add `GSI_USER` (PK=`user_sub`, SK=`created_at`) to the `returns` table — requires a `scripts/local-ddb-init.py` update and a prod `UpdateTable`. This is the cleanest approach.
   - Fetch returns per-order from `GSI_ORDER` and aggregate client-side — N queries, not scalable.
   - The OFB-011 spec should resolve this. For now, `GSI_USER` is the recommended approach and should be added as an additive change (existing data is unaffected; new writes will populate it).

5. **Assumption**: `provider` defaults to `"stripe"` in `refund_return`. This is appropriate because the existing billing layer in this project is primarily Stripe-first. However, if an order was paid via PayPal or CCBill, the refund provider should match the original payment. OFB-010 should look up the originating payment record to determine the provider rather than defaulting to `"stripe"`.

6. **Open question**: Should a closed return be reopenable (e.g., if a dispute arises)? The current `_VALID_TRANSITIONS` makes `closed` terminal. The ticket does not address re-opening.

7. **Assumption**: The `returns` table uses DynamoDB `put_item` for both header and line rows (not a TransactWriteItems call). Partial writes (header written, lines partially written) are benign because: (a) all quantity validation runs before any write; (b) a header in `status="requested"` with no lines is caught at read time by the service functions; and (c) the test suite does not exercise partial-write failure. A future hardening pass could wrap the header + lines in a `TransactWriteItems` call (max 25 items per transaction, sufficient for typical order sizes).
