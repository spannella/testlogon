# PTY-010 — Link PERSON parties to users/profiles/addresses

**Type:** Feature | **Priority:** P1 | **Estimate:** 2 days
**Milestone:** 3 — B2B Organizations & Legacy Migration
**Depends on:** PTY-007 (contact-mech service), PTY-009 (contacts migration)
**Downstream:** PTY-011 (party router), PTY-012 (admin migration endpoints), PTY-015 (test suite)

---

## 1. Summary & Goal

PTY-010 bridges the OFBiz-style party graph to the platform's existing `profiles` and `addresses`
subsystems. It adds one primary public function — `ensure_person_party(user_sub) -> str` — to
`app/services/party.py`. This function idempotently creates (or retrieves) the PERSON party that
represents the platform user identified by `user_sub`, then back-fills that party's contact
mechanisms (PTY-007) by reading from the profile and addresses stores: a `PRIMARY_EMAIL` mech from
`displayed_email`, a `PRIMARY_PHONE` mech from `displayed_telephone_number`, and one `POSTAL` mech
per address flagged `is_primary_mailing = True` (with `SHIPPING` and `BILLING` purposes).

The party and `profiles`/`addresses` stores are kept strictly segregated: the party layer only
**reads** from profiles and addresses tables; it never writes back to them. Forward-sync hooks are
wired into `app/services/profile.py:apply_profile_update` and
`app/services/addresses.py:set_primary_address` as best-effort, flag-gated callbacks that re-sync
only the changed party mech (email, phone, or postal) when those fields change. With the flag off
(`S.party_crm_enabled = False`, the default), every new hook is a no-op and the legacy surfaces
are byte-for-byte unchanged.

The canonical pattern established by `app/services/commerce_order_service.py:67`:

## 3. Data Model

### 3.1 No new tables or GSIs

PTY-010 writes exclusively to the existing `party` single-table established by PTY-002. No new
DynamoDB tables, GSIs, or `attr_types` entries are needed. The `scripts/local-ddb-init.py`
`TableDef` for the `party` table is unchanged by this ticket.

### 3.2 Party-meta row written by `ensure_person_party`

`ensure_person_party` calls `create_party("PERSON", user_sub=user_sub, correlation_id=f"PERSON:USER:{user_sub}")`.
The resulting META row (written by PTY-004) is:

```json
{
  "PK":           "PARTY#<party_id>",
  "SK":           "META",
  "party_id":     "<sha256('PERSON:USER:<user_sub>')[:32]>",
  "party_type":   "PERSON",
  "status":       "ACTIVE",
  "user_sub":     "<user_sub>",
  "type":         "TYPE#PERSON",
  "created_at":   1749200000,
  "updated_at":   1749200000,
  "correlation_id": "PERSON:USER:<user_sub>",
  "GSI3PK":       "OWNER#<user_sub>",
  "GSI3SK":       "PARTY#<party_id>"
}
```

On a second call the `ConditionExpression="attribute_not_exists(PK)"` in `create_party` raises
`ConditionalCheckFailedException`, which PTY-004 catches and converts to a read-and-return of the
existing item — `ensure_person_party` does not need to handle this itself.

### 3.3 Contact-mech rows written by the back-fill

Each contact mech written for the PERSON party follows the schema from PTY-007 (Section 3). The
deterministic `correlation_id` values that drive mech idempotency are:

| Source field | `mech_type` | `purposes` | `correlation_id` |
|---|---|---|---|
| `profile.displayed_email` | `EMAIL` | `["PRIMARY_EMAIL"]` | `"MECH:EMAIL:{user_sub}"` |
| `profile.displayed_telephone_number` | `PHONE` | `["PRIMARY_PHONE"]` | `"MECH:PHONE:{user_sub}"` |
| primary address (`is_primary_mailing=True`) | `POSTAL` | `["SHIPPING", "BILLING"]` | `"MECH:POSTAL:{user_sub}:{address_id}"` |

Using these deterministic correlation IDs guarantees that repeated calls to `ensure_person_party`
for the same user do not accumulate duplicate mech rows (PTY-007's
`ConditionExpression="attribute_not_exists(#pk)"` absorbs replays).

### 3.4 Mech replacement on re-sync

The forward-sync hooks (`_resync_email_mech`, `_resync_phone_mech`, `_resync_postal_mech`) do not
use `update_contact_mech` (which is scope-limited to `purposes` and `verified`). Instead, they
remove the old mech (using the deterministic `mech_id = sha256(correlation_id)[:32]`) and
add the new one with the same `correlation_id`. Because PTY-007's add uses
`ConditionExpression="attribute_not_exists(#pk)"`, the remove must happen before the re-add. If
the remove fails because the old mech does not exist (first run or already removed), this is
silently ignored. If the add fails because the mech already exists with the same value, the
`ConditionalCheckFailedException` is caught and the existing item is returned unchanged.

## 4. API / Service Design

### 4.1 New function: `ensure_person_party`

```python
# app/services/party.py (additions)

def ensure_person_party(user_sub: str) -> str:
    """
    Idempotently create (or retrieve) the PERSON party for a platform user.
    Back-fills EMAIL / PHONE / POSTAL contact mechs from profile + addresses.
    Returns the party_id string.

    Raises HTTPException(404, "Party CRM is not enabled") when
    S.party_crm_enabled is False.
    """
    ...
```

**Execution steps:**

1. Guard: `if not S.party_crm_enabled: raise HTTPException(404, "Party CRM is not enabled")`.
2. Call `create_party("PERSON", user_sub=user_sub, correlation_id=f"PERSON:USER:{user_sub}")` —
   returns existing dict on replay (idempotent via PTY-004).
3. Extract `party_id = result["party_id"]`.
4. Call `_backfill_mechs(party_id, user_sub)`.
5. Return `party_id`.

### 4.2 Internal function: `_backfill_mechs`

```python
def _backfill_mechs(party_id: str, user_sub: str) -> None:
    """
    Read profile identity + primary address and upsert contact mechs on the
    party. Each add call uses a deterministic correlation_id so repeated calls
    are no-ops. Never raises — all errors are logged and suppressed.
    """
    ...
```

**Execution steps (each sub-step is wrapped in its own `try/except Exception`; failures are
logged but never re-raised so a single bad mech never blocks the others or the caller):**

1. **Email mech:** call `get_profile_identity(user_sub)` (lazy import from
   `app.services.profile`). If `result["email"]` is not None, call:
   ```python
   add_contact_mech(
       party_id, "EMAIL", result["email"],
       purposes=["PRIMARY_EMAIL"],
       correlation_id=f"MECH:EMAIL:{user_sub}",
   )
   ```
2. **Phone mech:** same call with `result["phone"]`, `"PHONE"`, `["PRIMARY_PHONE"]`,
   `f"MECH:PHONE:{user_sub}"`.
3. **Postal mech:** call `list_addresses(user_sub)` (lazy import from `app.services.addresses`).
   For each address where `address.get("is_primary_mailing")` is truthy, call:
   ```python
   add_contact_mech(
       party_id, "POSTAL", address,
       purposes=["SHIPPING", "BILLING"],
       correlation_id=f"MECH:POSTAL:{user_sub}:{address['address_id']}",
   )
   ```
   Only `is_primary_mailing=True` addresses are projected. A user with no primary address
   produces no POSTAL mech (valid state).

For `_resync_email_mech(user_sub, new_email)`:
1. `party_id = _find_person_party_id(user_sub)` — return silently if `None`.
2. `mech_id = hashlib.sha256(f"MECH:EMAIL:{user_sub}".encode()).hexdigest()[:32]`
3. Attempt `remove_contact_mech(party_id, mech_id)` — silently ignore 404.
4. If `new_email` is not None: call `add_contact_mech(party_id, "EMAIL", new_email, ["PRIMARY_EMAIL"], correlation_id=f"MECH:EMAIL:{user_sub}")`.

`_resync_phone_mech` follows the identical pattern with `"MECH:PHONE:{user_sub}"`.

`_resync_postal_mech(user_sub, address)`:
1. `party_id = _find_person_party_id(user_sub)` — return silently if `None`.
2. Find all existing POSTAL mechs via `list_contact_mechs(party_id, mech_type="POSTAL")`.
   Remove any whose `correlation_id` starts with `f"MECH:POSTAL:{user_sub}:"`.
3. Call `add_contact_mech(party_id, "POSTAL", address, ["SHIPPING", "BILLING"], correlation_id=f"MECH:POSTAL:{user_sub}:{address['address_id']}")`.

```python
def _sync_party_mechs_after_profile_update(
    user_sub: str,
    old: Dict[str, Any],
    new: Dict[str, Any],
) -> None:
    """
    Best-effort party mech re-sync after a profile update.
    Called only when S.party_crm_enabled and S.party_crm_profile_sync_enabled are both True.
    Never raises — failures are logged and suppressed so the profile write is never
    rolled back.
    """
    import logging
    _log = logging.getLogger(__name__)
    try:
        from app.core.settings import S as _S
        if not (_S.party_crm_enabled and _S.party_crm_profile_sync_enabled):
            return
        from app.services.party import _resync_email_mech, _resync_phone_mech
        email_changed = old.get("displayed_email") != new.get("displayed_email")
        phone_changed = old.get("displayed_telephone_number") != new.get("displayed_telephone_number")
        if email_changed:
            _resync_email_mech(user_sub, new.get("displayed_email"))
        if phone_changed:
            _resync_phone_mech(user_sub, new.get("displayed_telephone_number"))
    except Exception:
        _log.exception("party.sync_mechs_after_profile_update_error user_sub=%s", user_sub)
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotency guarantee

`ensure_person_party(user_sub)` called N times for the same `user_sub` must produce the same
`party_id` and must not accumulate duplicate contact mechs. This is guaranteed by two layers:

- `create_party` uses a `ConditionExpression="attribute_not_exists(PK)"` put (PTY-004); on
  replay it reads and returns the existing row.
- Each `add_contact_mech` call uses a deterministic `correlation_id` (Section 4.2 table). On
  replay, PTY-007's `ConditionalCheckFailedException` handler returns the existing mech
  unchanged.

### 5.2 User with no profile email or phone

`get_profile_identity(user_sub)` returns `email: None` / `phone: None` when the user has not set
those fields. `_backfill_mechs` skips the `add_contact_mech` call for any field that is `None`.
The PERSON party is still created; it simply has no EMAIL or PHONE mech until the user fills in
the profile fields and the sync hook fires.

### 5.3 User with multiple addresses, only one primary

`list_addresses(user_sub)` may return many addresses. `_backfill_mechs` projects only those where
`is_primary_mailing=True`. In normal operation at most one address carries this flag; in edge
cases where data inconsistency produces multiple primaries (e.g. from a crashed `set_primary_address`
run), all of them are projected as separate POSTAL mechs. This is safe because each has a unique
`address_id` and thus a unique `correlation_id`.

### 5.4 Email cleared (set to None) on re-sync

When `apply_profile_update` clears `displayed_email` (new value = `None`), `_resync_email_mech`
is called with `new_email=None`. The function removes the old mech (step 3) and skips the
`add_contact_mech` call (step 4 is guarded by `if new_email is not None`). The party retains
no EMAIL mech afterward — this correctly reflects the profile state.

### 5.5 Party does not exist yet when sync hook fires

The sync hooks in `profile.py` and `addresses.py` call `_find_person_party_id(user_sub)` first.
If the user's PERSON party has not been provisioned yet (because `ensure_person_party` has never
been called), `_find_person_party_id` returns `None` and the hook returns immediately without
error. The sync is effectively a no-op until the party is provisioned. This is the correct
behavior: the sync hooks are forward-only and only relevant once the party exists.

### 5.6 `T.party` unavailable (flag off)

When `S.party_crm_enabled` is `False`, `T.party` is wired to `_safe_table(S.party_table_name)`
which resolves to a handle for a table that may or may not exist locally. All sync hooks check
the flag before touching `T.party` (via the lazy import path). `ensure_person_party` guards
itself with an explicit flag check at step 1 (Section 4.1). No DynamoDB call is made with the
flag off.

### 5.7 Circular import prevention

`app/services/party.py` must never be imported at module load time by `app/services/profile.py`
or `app/services/addresses.py`. All references to `app.services.party` inside those two files
use lazy imports (inside `try/except` blocks), following the pattern already established for
`app.services.discovery` at `app/services/profile.py:396` and `app.services.kyc_cases` at
`app/services/profile.py:422`.

### 5.8 `_resync_postal_mech` old-mech removal

Old POSTAL mechs are identified by querying `list_contact_mechs(party_id, mech_type="POSTAL")`
and filtering for items whose stored `correlation_id` starts with `f"MECH:POSTAL:{user_sub}:"`.
This is a soft match: only mechs seeded by PTY-010 are removed. Manually added POSTAL mechs
(via the PTY-011 router with user-supplied correlation IDs) are not touched.

### 5.9 Back-fill atomicity

`_backfill_mechs` is not transactional. If it is interrupted mid-way (e.g. process kill), it
leaves a partial mech set. The next call to `ensure_person_party` will complete the back-fill
idempotently because each `add_contact_mech` with the same `correlation_id` returns the existing
mech if it already exists. There is no DynamoDB transaction wrapping the whole back-fill; this
matches the non-transactional patterns used throughout the codebase.

### 5.10 Audit events

`ensure_person_party` emits one audit event after the party is created or confirmed:
```python
audit_event("party.ensure_person_party", user_sub, party_id=party_id)
```
This mirrors the pattern in PTY-004 and PTY-007. Audit events are fire-and-forget writes to
`T.alerts` via `app/services/alerts.py:644`. No audit event is emitted when the back-fill
skips a mech due to a missing value (None email/phone).

| `S.party_crm_profile_sync_enabled` | `PARTY_CRM_PROFILE_SYNC_ENABLED` | `False` | bool (new) |

```python
party_crm_profile_sync_enabled: bool = os.environ.get(
    "PARTY_CRM_PROFILE_SYNC_ENABLED", "0"
) not in ("0", "false", "False")
```

**Flag semantics:**

- `party_crm_enabled=False` (default): all of PTY-010's code paths are entirely inert.
  `ensure_person_party` raises 404, sync hooks are no-ops, `profiles` and `addresses` write
  surfaces are byte-for-byte unchanged.
- `party_crm_enabled=True`, `party_crm_profile_sync_enabled=False`: `ensure_person_party`
  works and backfills mechs, but the forward-sync hooks in `profile.py` and `addresses.py`
  are disabled. Operators can provision parties and run backfills without automatic propagation.
- Both `True`: full live sync — every profile email/phone/primary-address change is propagated
  to the linked party's mechs best-effort.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity:** `ensure_person_party` and the re-sync helpers write exclusively to the
`party` DynamoDB table via `T.party`. In dev, `T.party` is backed by DynamoDB Local on port 8001.
In prod, it is backed by AWS DynamoDB. There is no `dev_mode` branch; the code path is identical
in both environments. The `get_profile_identity` and `list_addresses` calls read from `T.profile`
and `T.addresses` respectively — also identical in dev/prod.

**Idempotency:** The deterministic `correlation_id` scheme (`f"PERSON:USER:{user_sub}"` for the
party, `f"MECH:{TYPE}:{user_sub}"` / `f"MECH:POSTAL:{user_sub}:{address_id}"` for mechs) ensures
any number of `ensure_person_party` calls produce exactly one party and at most one mech per
unique source field per user. Re-running a bulk back-fill (PTY-012 admin endpoint) is safe.

**Security — no cross-user data exposure:** `ensure_person_party` takes `user_sub` as a plain
string argument. The caller (PTY-012 admin endpoint or PTY-009 migration) is responsible for
ensuring it only passes authorized `user_sub` values. The function itself issues no
caller-identity check — it is a server-side utility, not a user-facing endpoint. The forward-sync
hooks are wired to the `user_sub` already extracted from the authenticated session by
`require_ui_session`, so there is no user-controlled `user_sub` input in the sync path.

**Read-only against profiles/addresses:** The party layer issues only `get_item` and `query`
calls against `T.profile` and `T.addresses`. It never calls `put_item`, `update_item`, or
`delete_item` on those tables. This is enforced by code convention and verified by the test suite
(mock tables assert no writes).

**Lazy imports prevent startup coupling:** The `from app.services.party import ...` imports in
`profile.py` and `addresses.py` are inside `try/except` blocks executed at call time, not at
module load. This prevents `app.services.party` from being pulled into the import graph during
`app/main.py` startup, which would fail if `T.party` is not yet initialized (e.g. during tests
that mock only a subset of tables).

## 8. Backward Compatibility & Migration

**Additive only:** No existing DynamoDB rows, table schemas, or API response shapes are changed.
The `profiles` and `addresses` tables gain no new attributes. The `T.profile` and `T.addresses`
table handles are read-only from the party layer's perspective.

**Hook location is non-breaking:** The new `_sync_party_mechs_after_profile_update` call is
appended after the existing discovery re-index hook at `app/services/profile.py:375-376`. The
hook is a no-op with the flag off, so all existing callers of `apply_profile_update` —
`app/services/addresses.py:110,136` and `app/routers/profile.py:283,293,397`
(note: `app/routers/settings.py` does not exist; `app/routers/kyc_cases.py` does not call
`apply_profile_update` — verified) — continue to behave identically. The same applies to
`_sync_party_postal_mech` appended to `set_primary_address`.

**Migration path:** The PTY-012 admin endpoint `POST /ui/admin/party/ensure-person/{user_sub}`
drives on-demand back-fill for individual users. A full bulk back-fill over all platform users is
out of scope for PTY-010; it is expected to be implemented as a background admin sweep in PTY-012
or a follow-up operations script.

**Rollback:** Disabling `PARTY_CRM_ENABLED=0` after enabling it leaves orphaned rows in the
`party` table but leaves `profiles`/`addresses` completely intact. The next `just restart` in dev
wipes DynamoDB Local and the party table is re-created empty. In prod, orphaned party rows are
harmless — they are not read by any legacy code path and can be cleaned up offline.

## 10. Open Questions / Assumptions

1. **Assumption: PTY-007 `add_contact_mech` stores `correlation_id` on the item.** The PTY-007
   spec (section 4) does not explicitly list `correlation_id` as a persisted attribute. PTY-010's
   `_resync_postal_mech` queries `list_contact_mechs` and filters by stored `correlation_id` to
   find old mechs to remove. If PTY-007 does not persist `correlation_id`, `_resync_postal_mech`
   must use a different identification strategy (e.g., store a tag `party_sync_source: "PTY-010"`
   on the mech item). **Verify with PTY-007 implementer.**

2. **Assumption: `remove_contact_mech` accepts a `mech_id` derived as `sha256(correlation_id)[:32]`
   and does not require a `mech_type` prefix.** The PTY-007 service stores `SK = MECH#{mech_type}#{mech_id}`;
   `remove_contact_mech(party_id, mech_id)` must internally reconstruct the SK. If the API
   requires `mech_type` to be passed as well, the re-sync helpers must be updated to pass it.
   **Verify function signature from PTY-007 spec section 4.**

3. **Assumption: `_find_person_party_id` GSI3 query is sufficient.** A user could theoretically
   have multiple PERSON parties linked to the same `user_sub` (if `create_party` is called more
   than once without a `correlation_id`). `ensure_person_party` always uses the deterministic
   `correlation_id = "PERSON:USER:{user_sub}"`, so in practice only one party can be created this
   way. However, if parties are created via other paths (PTY-009 migration, manual admin create),
   `GSI3` may return multiple results. The implementation takes the first META row returned.
   **Document this in code comments and decide whether to enforce uniqueness via a GSI3 count
   check.**

4. **Open: bulk back-fill for all users.** This ticket covers per-user ensure + admin single-user
   endpoint (PTY-012). A "run for all users" sweep is not specified here. If PTY-012 needs it, a
   scan-based loop over all Cognito users (or over `T.profile`) calling `ensure_person_party` per
   `user_sub` is the expected implementation. This is flagged as a PTY-012 concern.

5. **Open: mech `verified` flag.** The back-filled mechs from profile/addresses carry
   `verified=False` (the default). There is no verification flow defined in Phase 1. A future
   ticket (Phase 2) should define the verification path and back-fill `verified=True` for users
   whose email/phone is already confirmed via Cognito MFA.

6. **Assumption: `normalize_email` / `normalize_phone` do not raise for already-normalized
   values.** Profile stored values go through `normalize_email` / `normalize_phone` at
   `app/services/profile.py:212-216` before storage, so back-filling them into `add_contact_mech`
   (which normalizes again) should be idempotent. **VERIFIED** (`app/core/normalize.py:60-81`):
   `normalize_email` is `strip().lower()` + length/`@` check — a no-op on an already-normalized
   value. `normalize_phone` re-strips formatting and re-applies E.164 rules — a no-op on a value
   already in `+1NNNNNNNNNN` form. Double-normalization is safe.
