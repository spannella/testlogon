PTY-002 creates the physical DynamoDB table definition for the Party/CRM single-table design and wires the resulting table handle (`T.party`) into `app/core/tables.py`. ## 2. Context & Current State

### 2.1 How other tables are registered

`scripts/local-ddb-init.py` declares every DynamoDB table as a frozen `TableDef` dataclass (lines 28–35) inside the `_table_defs()` function (line 42). `TableDef` accepts:

- `name: str` — resolved via `_resolve_table_name(setting_value, fallback)` (line 38)
- `partition_key: str` — always `"S"` unless overridden by `attr_types`
- `sort_key: Optional[str]`
- `gsi: List[Dict]` — each dict has `index_name`, `partition_key`, `sort_key`
- `attr_types: Dict[str, str]` — overrides attribute type for numeric sort keys (critical: without this, DynamoDB stores numeric values as strings and raises `ValidationException` at query time)

The `_attribute_definitions()` function at line 2496 merges base key, GSI key, and `attr_types` overrides. All projection types default to `ALL` (line 2528).

Nearest neighbours in the file are:
- `addresses` table at line 98 — `TableDef(_resolve_table_name(S.addresses_table_name, "addresses"), "user_sub", "address_id")` — simple, no GSIs
- `Contacts` table at line 691 — `TableDef(os.getenv("DDB_CONTACTS_TABLE", "Contacts"), "owner_id", "contact_id")` — uses raw `os.getenv` instead of `_resolve_table_name`; the new `party` table should use `_resolve_table_name(S.party_table_name, "party")` for consistency with post-2023 additions

PTY-001 (not yet merged) will add `S.party_table_name: str = os.environ.get("DDB_PARTY_TABLE", "party")` to `app/core/settings.py` alongside `contacts_table_name` at line 498. PTY-002 depends on that setting being present.

### 2.2 How table handles are wired

`app/core/tables.py` defines the `Tables` frozen dataclass (line 68) and its singleton `T` (line 321). Each field is typed `Any` (set to a `_FloatSafeTable` proxy around a `boto3.dynamodb.Table`). `_safe_table(name)` at line 65 constructs the proxy. The pattern used by the nearest neighbor is:

```
# in dataclass body
contacts: Any      # line 102

# in T = Tables(...) instantiation
contacts=_safe_table(S.contacts_table_name),    # line 354
```

`T` is a `frozen=True` dataclass; test fixtures mutate individual fields via `object.__setattr__(T, "party", moto_table)` — the same pattern used by `tests/test_gap_0197_affiliate_analytics.py` lines 121–122 and `tests/test_ad_placement_fraud_gate.py` lines 74–81.

### 2.3 Access pattern requirements

The Party CRM single table will store four logical entity types in one DynamoDB table (PK/SK design):

| Row type | PK | SK |
|---|---|---|
| Party meta | `PARTY#{party_id}` | `META` |
| Party role | `PARTY#{party_id}` | `ROLE#{role_type}` |
| Party relationship | `PARTY#{party_id}` | `REL#{rel_type}#{to_party_id}` |
| Contact mechanism | `PARTY#{party_id}` | `MECH#{mech_id}` |

Four access patterns drive the GSI requirements:
1. **Role/type lookup** — "find all parties with role `ORG_ADMIN`" or "list all `PARTY_GROUP` parties" → needs a GSI keyed on a role/type marker with `created_at` sort for newest-first pagination
2. **Contact-mech reverse lookup** — "which party owns `alice@example.com`?" → needs a sparse GSI keyed on the normalized contact-mech value (e.g. `EMAIL#alice@example.com`)
3. **Owner/user_sub lookup** — "which party records are linked to Cognito user `sub_abc123`?" → needs a GSI keyed on `OWNER#{user_sub}`
4. **Newest-first listing by type** — "list all PERSON parties ordered by `created_at` descending" → needs a GSI with `type` as partition key and numeric `created_at` as sort key; `ScanIndexForward=False` gives newest-first

## 3. Data Model

### 3.1 DynamoDB Table: `party`

**Table name:** resolved via `_resolve_table_name(S.party_table_name, "party")`  
**Partition key:** `PK` (String)  
**Sort key:** `SK` (String)

#### GSI definitions

| Index name | Partition key | Sort key | Purpose |
|---|---|---|---|
| `GSI1` | `GSI1PK` (S) | `GSI1SK` (S) | Role/type lookup — PK = `ROLE#{role_type}` or `TYPE#{party_type}`, SK = arbitrary discriminator (e.g. `PARTY#{party_id}`) |
| `GSI2` | `GSI2PK` (S) | `GSI2SK` (S) | Contact-mech reverse — PK = `EMAIL#{value}` / `PHONE#{value}` / `POSTAL#{value}`, SK = `PARTY#{party_id}` |
| `GSI3` | `GSI3PK` (S) | `GSI3SK` (S) | Owner/user_sub — PK = `OWNER#{user_sub}`, SK = `PARTY#{party_id}` |
| `GSI_CREATED` | `type` (S) | `created_at` (N) | Newest-first listing by party_type — PK = e.g. `TYPE#PERSON`, numeric `created_at` sort |

All indexes use `ProjectionType: ALL` (the default in `_global_secondary_indexes()` at line 2528).

#### `attr_types` declaration

```python
attr_types={"created_at": "N", "GSI1SK": "S", "GSI2SK": "S", "GSI3SK": "S"}
```

`created_at` must be declared `"N"` — this is the key constraint from the CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha. Without it, moto and real DynamoDB both store `created_at` as String and raise `ValidationException` when a query supplies an integer value via `KeyConditionExpression`. `GSI1SK`, `GSI2SK`, and `GSI3SK` are String and need no override but should be listed explicitly so `_attribute_definitions()` includes them (they are generated as `"S"` by default from the GSI loop at lines 2500–2503, so explicit listing is optional — but not harmful for clarity).

#### `TableDef` entry (to be inserted after the `returns` table, line 2492, before the closing `]`)

```python
# Party/CRM single table (PTY-002). Stores Party meta, role, relationship,
# and contact-mech rows in one table. GSI_CREATED uses a numeric created_at
# sort key for newest-first pagination; GSI1/2/3 are all-string.
TableDef(
    _resolve_table_name(S.party_table_name, "party"),
    "PK",
    "SK",
    gsi=[
        {"index_name": "GSI1", "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        {"index_name": "GSI2", "partition_key": "GSI2PK", "sort_key": "GSI2SK"},
        {"index_name": "GSI3", "partition_key": "GSI3PK", "sort_key": "GSI3SK"},
        {"index_name": "GSI_CREATED", "partition_key": "type", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
),
```

Note: `GSI1SK`, `GSI2SK`, `GSI3SK` are String so no override is needed for them. Only `created_at` (the numeric sort key on `GSI_CREATED`) requires the override.

## 5. Detailed Behavior & Edge Cases

### 5.1 `just restart` idempotency

`_ensure_table()` at line 2534 checks `if table.name in existing` before calling `create_table`. On a fresh restart it creates the table; on a running stack it is a no-op. The missing-GSI back-fill path at lines 2542–2574 will add any GSI that was declared after the table was first created — this handles partial re-deployments without a full wipe.

### 5.2 Numeric sort key on `GSI_CREATED`

The `_attribute_definitions()` function at line 2496 first populates all keys as `"S"`, then applies `attr_types` overrides (line 2505). The `created_at` override `"N"` must be present in `attr_types` on the `TableDef`; omitting it means `created_at` is declared as `AttributeType: "S"` in `CreateTable`, which silently accepts string storage but raises `ValidationException: "Type mismatch for key created_at expected: N actual: S"` the first time a service calls `.query(KeyConditionExpression=Key("type").eq("TYPE#PERSON") & Key("created_at").between(start, end))`.

### 5.3 GSI_CREATED partition key is `type`, not `GSI4PK`

Unlike `GSI1`/`GSI2`/`GSI3` which use the generic `GSIxPK`/`GSIxSK` attribute names, `GSI_CREATED` uses `type` (String) as its partition key. This mirrors the `billing` table's `ledger_date`-partitioned index (line 76 of ddb-init). Using a semantic attribute name means the attribute is also directly queryable without the GSI, and downstream service code is more readable (`item["type"] = "TYPE#PERSON"` instead of `item["GSI4PK"] = "TYPE#PERSON"`).

### 5.4 `_FloatSafeTable` proxy

`T.party` is a `_FloatSafeTable` instance. Services that write `created_at` as an integer (from `now_ts()`) will not hit the float-coercion path. The proxy is transparent for all other operations: `T.party.query(...)`, `T.party.get_item(...)`, `T.party.delete_item(...)`, `T.party.scan(...)` all delegate to the underlying boto3 Table unchanged via `__getattr__` at line 61.

### 5.5 Flag-off behavior

With `S.party_crm_enabled = False` (the default), `T.party` is still initialized at module import time — `ddb.Table("party")` only records the table name; it does not make a network call. No code outside the Party/CRM feature domain references `T.party`, so the table handle is inert. The DynamoDB Local table still gets created by `just restart` regardless of the flag (table creation in `local-ddb-init.py` is unconditional — no flag check).

### 5.6 Table name collision risk

The default name `"party"` is all-lowercase and not prefixed. A search of `scripts/local-ddb-init.py` confirms no existing table uses `"party"` as a name (the `watch_party_participants` table at line 1599 uses `"watch_party_participants"`, not `"party"`). In multi-tenant or staging environments, operators set `DDB_PARTY_TABLE` to a namespaced value (e.g. `"staging_party"`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

The `TableDef` approach in `local-ddb-init.py` is the local-dev equivalent of a CloudFormation/Terraform `AWS::DynamoDB::Table` resource. The attribute definitions, GSI key schemas, and projection types are identical in both environments. There is no `dev_mode` branch in the table definition or handle. SECOPS-007 is satisfied by construction: the same `T.party` handle is used regardless of environment.

### 7.2 Idempotency

`_ensure_table()` is idempotent: it skips `create_table` if the table already exists and back-fills missing GSIs. Running `just restart` twice (or deploying the same code revision twice) is safe.

### 7.3 Security

The `party` table will store PII (email addresses, phone numbers, postal addresses) in contact-mech rows. At this scaffolding stage, no data is stored. When PTY-006 writes contact-mech rows:
- Email and phone values in `GSI2PK` will be normalized (lowercased, stripped) before write — raw values are never stored denormalized
- Postal values in `GSI2PK` will be hashed or truncated to a prefix to avoid storing full addresses as a GSI key (design decision deferred to PTY-006)
- DynamoDB encryption at rest uses the account-default AWS-managed key (same as all other tables)

No IAM or resource-based policy changes are required by PTY-002 alone.

## 10. Open Questions / Assumptions

1. **Assumption: PTY-001 is merged before PTY-002 ships.** The `TableDef` uses `S.party_table_name`; if PTY-001's settings are absent, the import will raise `AttributeError`. Mitigation: PTY-002 can include an inline fallback `getattr(S, "party_table_name", "party")` if PTY-001 is delayed, but the cleaner approach is strict ordering.

2. **Assumption: `type` is not already a reserved DynamoDB keyword in the context of GSI keys.** `type` is not in the DynamoDB reserved words list for key attribute names (it is reserved for expressions but not for schema definitions). Confirmed by the existing `billing` table which uses `ledger_date` as a GSI PK (line 76 of ddb-init) without issues. If `type` causes a problem in practice, the fallback is to rename to `party_type_gsi_pk` and update the relevant service writes.

3. **Assumption: `GSI_CREATED` partition key value format is `TYPE#PERSON` / `TYPE#PARTY_GROUP`.** This namespaced format avoids collisions if other item types are ever projected onto this GSI. The alternative (`PERSON` / `PARTY_GROUP` raw values) is simpler but risks collision with future item types. Namespaced format assumed.

4. **Question: Should GSI1SK be numeric for time-ordered role lookups?** The ticket says GSI1SK carries `PARTY#{party_id}` (a string). If a future requirement is "show me the newest 10 parties with role ORG_ADMIN", GSI1SK would need to be `created_at` (numeric). The current design uses a string SK for GSI1; a future migration can add a `GSI1_CREATED` index if needed. Confirmed string for now per ticket spec.

5. **Assumption: Projection type `ALL` on all GSIs.** This simplifies downstream reads (no need to fetch the base record for GSI results) at the cost of higher storage. Given typical party record sizes (< 1 KB per row), this is acceptable. If the table grows extremely large, the team can move to `INCLUDE` projections.

6. **Question: Should the table be flag-gated in `_table_defs()`?** Other tables in the file are unconditionally created regardless of feature flags (e.g. `recommendations` table is always created even when `NEWSFEED_RECSYS_ENABLED=0`). Consistent with that pattern, the `party` table will always be created by `local-ddb-init.py`. No flag check in `_table_defs()`.

7. **Assumption: `GSI3PK`/`GSI3SK` on the META row for owner lookup.** Sparse indexing (only rows carrying both `GSI3PK` and `GSI3SK` appear in GSI3). PARTY_GROUP parties and PERSON parties without a linked `user_sub` never write these attributes, so they are invisible to GSI3 queries. This is the same pattern used by `kyc_cases` with `assigned_admin_sub` at line 156 of ddb-init.
