# ORD-002 — Feature flag & settings

**Type:** Chore | **Priority:** P0 | **Estimate:** 1 day
**Milestone:** 1 — Foundation (flag, data model, tables)

---

## 1. Summary & Goal

ORD-002 wires the three order-lifecycle feature flags into `app/core/settings.py` so that all downstream tickets (ORD-003 through ORD-NNN) have a single, stable place to guard new behavior. The flags are strictly additive: every code path activated by a later ticket reads `S.order_lifecycle_enabled` (and optionally `S.order_lifecycle_auto_approve` or `S.order_backorder_enabled`) at runtime, so with all three flags off the platform behaves byte-for-byte identically to its pre-ORD state.

No service, router, or DynamoDB schema change is introduced by this ticket. The entire deliverable is:

1. Three new fields on the `Settings` dataclass (`app/core/settings.py`), defaulting to `False`.
2. A one-paragraph entry in `docs/ofbiz/specs/ORD-001.md` (the ORD-001 design spike document — no separate `docs/order-lifecycle-plan.md` is produced) that names the flags and their env vars.
3. A hermetic pytest (`tests/test_ord_002_feature_flags.py`) that asserts the defaults and confirms each flag responds to its env var.

## 2. Context & Current State

### 2.1 The Settings dataclass and S singleton

All runtime configuration in the platform flows through a single frozen `@dataclass(frozen=True)` named `Settings` in `app/core/settings.py:6–7` (decorator at line 6, class keyword at line 7). Every field is a class attribute with an `os.environ.get(...)` default. The module-level singleton `S = Settings()` is evaluated once at import time (`app/core/settings.py:2772`). Because the dataclass is frozen, tests that need to toggle a flag do so via `object.__setattr__(module.S, "flag", value)` and restore the original in a `finally` block — this is the established pattern throughout the test suite (e.g. `tests/test_compute_billing_timer_gap0228.py:117`).

### 2.2 Existing order-related settings

The two table-name settings for the current order model already live at `app/core/settings.py:1124–1125`:

```python
orders_table_name: str = os.environ.get("ORDERS_TABLE_NAME", "orders")
order_items_table_name: str = os.environ.get("ORDER_ITEMS_TABLE_NAME", "order_items")
```

These are part of a group that also covers `payments_table_name`, `entitlements_table_name`, and entitlement thresholds (`app/core/settings.py:1126–1130`). The new lifecycle flag group belongs immediately after line 1130, before the blank line that separates this commerce block from the newsfeed block at line 1133.

### 2.3 Current order behavior (no lifecycle logic yet)

`app/services/commerce_order_service.py:39` defines `create_order`. It writes a single `status="pending_payment"` field (`app/services/commerce_order_service.py:75`) to the `orders` table and returns without any lifecycle logic. The `orders` DynamoDB table is a simple single-hash-key table (no sort key) with two GSIs: `GSI_USER` (PK=`user_id`, SK=`created_at`) and `GSI_STATUS` (PK=`status`, SK=`created_at`) — defined at `scripts/local-ddb-init.py:287–294`. Neither GSI has a numeric `attr_types` declaration, which is appropriate since `created_at` is stored as an ISO-8601 string in the current code (`app/services/commerce_order_service.py:20`).

The only call site that produces order records today is `app/services/shoppingcart.py:581`, which delegates to `commerce_order_service.create_order_from_line_items`. With all new flags off, this call site and the order record it produces must remain entirely unchanged.

### 2.4 Established pattern for default-off feature flags

The codebase uses two idiomatic spellings for "default false" booleans; the canonical pattern for non-security feature flags is:

```python
some_feature_enabled: bool = os.environ.get("SOME_FEATURE_ENABLED", "false").lower() in ("1", "true", "yes", "on")
```

Examples using the set pattern: `signature_pdf_enabled` (`app/core/settings.py:913`), `newsfeed_recsys_enabled` (`app/core/settings.py:2014`). Note: `ticket_boards_enabled` (`app/core/settings.py:432`) uses the older spelling `.lower() == "true"` rather than `.lower() in ("1", "true", "yes", "on")` — it is **not** a conforming example of this pattern. ORD-002 follows the broader set-of-affirmative-strings convention used by `signature_pdf_enabled` and `newsfeed_recsys_enabled`.

## 4. API / Service Design

ORD-002 ships no endpoints and no service functions. The deliverable is three new dataclass fields.

### 4.1 New fields in `Settings` (insertion point: after `app/core/settings.py:1130`)

```python
# Order lifecycle feature flags (ORD-002)
# Master gate: when false, all order-lifecycle code paths are unreachable.
order_lifecycle_enabled: bool = os.environ.get(
    "ORDER_LIFECYCLE_ENABLED", "false"
).lower() in ("1", "true", "yes", "on")

# When true, a paid order auto-advances created → approved immediately after
# payment confirmation.  Ignored when order_lifecycle_enabled is false.
order_lifecycle_auto_approve: bool = os.environ.get(
    "ORDER_LIFECYCLE_AUTO_APPROVE", "false"
).lower() in ("1", "true", "yes", "on")

# When true, the state machine allows the backorder side-state.
# Ignored when order_lifecycle_enabled is false.
order_backorder_enabled: bool = os.environ.get(
    "ORDER_BACKORDER_ENABLED", "false"
).lower() in ("1", "true", "yes", "on")
```

These fields are grouped under a comment banner `# Order lifecycle feature flags (ORD-002)` for discoverability and are inserted between the existing entitlement threshold settings (line 1130) and the blank line before the newsfeed section (line 1132). No existing field is modified.

### 4.2 Access pattern in downstream tickets

All downstream service/router code that reads these flags must import from the singleton:

```python
from app.core.settings import S

def transition_order(order_id: str, ...) -> ...:
    if not S.order_lifecycle_enabled:
        raise HTTPException(status_code=404, detail="Order lifecycle not enabled")
    ...
```

The flags are never passed as arguments — callers always read `S.<flag>` directly, consistent with how `S.signature_pdf_enabled`, `S.browser_ssh_terminal_enabled`, and similar flags are used throughout the codebase.

### 4.3 No router registration required

Unlike `browser_ssh_terminal_enabled` (which conditionally registers a router in `app/main.py`) or `compute_billing_enabled` (which gates a startup task), the order lifecycle flag gates service-layer behavior, not router mounting. No change to `app/main.py` is needed in ORD-002. ORD-005 (state machine) will add the conditional behavior at the service layer.

## 5. Detailed Behavior & Edge Cases

### 5.1 All flags default off — zero behavior change

With `ORDER_LIFECYCLE_ENABLED` absent from the environment (or set to `"false"`, `"0"`, `"no"`, `"off"`), `S.order_lifecycle_enabled` is `False`. The same holds for `order_lifecycle_auto_approve` and `order_backorder_enabled`. No downstream ticket activates any code path until it explicitly checks `S.order_lifecycle_enabled`. This is enforced at review time for each ORD-NNN PR.

### 5.2 Sub-flag dependency

`order_lifecycle_auto_approve` and `order_backorder_enabled` are only meaningful when `order_lifecycle_enabled` is `True`. Downstream code must always check the master gate first:

```python
if not S.order_lifecycle_enabled:
    return  # or raise 404
if S.order_lifecycle_auto_approve:
    ...
```

There is no platform-level enforcement of this dependency in ORD-002 itself. Convention is documented here and in the order-lifecycle plan.

### 5.3 Boolean parsing robustness

The `".lower() in ("1", "true", "yes", "on")` pattern accepts case-insensitive values from deployment pipelines (e.g., Terraform `"True"`, Kubernetes config maps `"yes"`, legacy `.env` files `"1"`). The explicit `"false"` default ensures a missing env var always yields `False` rather than relying on the absence of a truthful string — this prevents accidental activation if the env var is set to an empty string.

### 5.4 Reload behavior

Because `S` is a module-level singleton evaluated at import time, the flags cannot be toggled at runtime without restarting the process (or using `object.__setattr__` in tests). This matches all other feature flags in the platform and is by design.

### 5.5 Flag interaction with existing `status` field

The legacy `status="pending_payment"` field written by `commerce_order_service.create_order` (`app/services/commerce_order_service.py:75`) is unchanged. When `order_lifecycle_enabled` is `True`, ORD-005 will additionally write `lifecycle_status="created"` and mirror `status` — but that is outside this ticket's scope.

## 6. Feature Flag & Config

| Flag name (Python) | Env var | Default | Purpose |
|--------------------|---------|---------|---------|
| `S.order_lifecycle_enabled` | `ORDER_LIFECYCLE_ENABLED` | `false` | Master gate for all order-lifecycle code paths |
| `S.order_lifecycle_auto_approve` | `ORDER_LIFECYCLE_AUTO_APPROVE` | `false` | Auto-advance `created → approved` on payment confirmation |
| `S.order_backorder_enabled` | `ORDER_BACKORDER_ENABLED` | `false` | Allow `backorder` side-state in the state machine |

**`.env.local.example` entry** (to be added by this ticket):

```bash
# Order lifecycle state machine (ORD-002+). Default off.
# ORDER_LIFECYCLE_ENABLED=true
# ORDER_LIFECYCLE_AUTO_APPROVE=false
# ORDER_BACKORDER_ENABLED=false
```

All three lines are commented out so that a fresh `setup_ubuntu.sh` run leaves the flags off. An operator who wants to enable the lifecycle in dev uncomments `ORDER_LIFECYCLE_ENABLED=true`.

**No `frontend/.env.local.example` entry is needed**: the flags are server-side only. The frontend has no equivalent config to toggle; lifecycle state will be surfaced through the order API response shape (added in ORD-004), not through a frontend feature flag.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity**: The three flags resolve identically in dev and prod — same `os.environ.get` call, same default, same boolean parse. There is no `S.dev_mode` branch or mock path. A dev environment with `ORDER_LIFECYCLE_ENABLED=true` runs the same code path as production.

**Idempotency**: Settings are stateless and idempotent by definition. The `S` singleton is read-only after import; re-reading `S.order_lifecycle_enabled` in any number of request handlers returns the same value.

**Security**: These flags control feature enablement, not authentication or authorization. They carry no secret material. No HMAC, encryption, or signing is involved. Downstream tickets that implement actual state transitions will use the existing `require_ui_session` (`app/services/sessions.py:330`) / `require_admin_or_root` (`app/auth/policy.py:67`) auth dependencies and the conditional-write concurrency pattern (`ConditionExpression` on `update_item`) — but those are out of scope for ORD-002. (Note: there is no `require_admin_session` function in the codebase; the correct admin dependency is `require_admin_or_root`.)

**No audit event required**: Adding a setting field to a frozen dataclass is not an auditable runtime event. The `audit_event` helper (`app/services/alerts.audit_event`) is not called in this ticket; it will be called by ORD-006 (status history) on each state transition.

---

## 8. Backward Compatibility & Migration

**Zero migration required.** The new fields have default values derived from the environment. On a fresh process start with no new env vars set, `S.order_lifecycle_enabled` is `False` and no downstream behavior changes. Existing DynamoDB tables, API endpoints, and frontend pages are untouched.

**Rolling restart safety**: Because the flags default off, a rolling restart of the backend during a deployment that includes this PR is safe. Old processes have no knowledge of the fields; new processes start with the flags off. There is no intermediate state where half the fleet has the flag on.

**No DynamoDB schema migration**: ORD-003 will add GSIs to the `orders` table. `just restart` recreates the table from `scripts/local-ddb-init.py`. In production, `UpdateTable` is required for a live table. But that is ORD-003's responsibility; ORD-002 touches no DynamoDB schema.

**No `order_items` table changes**: The `order_items` table (`scripts/local-ddb-init.py:295`, `T.order_items`, `app/core/tables.py:382`) is not modified by this ticket or referenced by its flags.

## 9. Test Plan

### 9.1 Hermetic unit test: `tests/test_ord_002_feature_flags.py`

The test file is self-contained, offline, and requires no moto, no live DynamoDB, and no running backend. It imports `app.core.settings` and probes `S` directly. Because `S` is frozen, flag mutations use `object.__setattr__` with cleanup in `finally`.

```python
"""ORD-002: smoke tests for ORDER_LIFECYCLE_* feature flags.

Offline, hermetic — no AWS, no DynamoDB, no network.
Mutations to the frozen S singleton use object.__setattr__ and are
always restored in a finally block.
"""
from __future__ import annotations
import os
import importlib


def test_defaults_are_all_false():
    """All three lifecycle flags default to False with no env vars set."""
    import app.core.settings as m
    assert m.S.order_lifecycle_enabled is False
    assert m.S.order_lifecycle_auto_approve is False
    assert m.S.order_backorder_enabled is False


def test_order_lifecycle_enabled_toggles_via_env(monkeypatch):
    """ORDER_LIFECYCLE_ENABLED=true flips the flag on."""
    monkeypatch.setenv("ORDER_LIFECYCLE_ENABLED", "true")
    # Re-instantiate Settings with the patched environment.
    import app.core.settings as m
    fresh = m.Settings()
    assert fresh.order_lifecycle_enabled is True


def test_order_lifecycle_enabled_false_for_zero(monkeypatch):
    """ORDER_LIFECYCLE_ENABLED=0 stays False."""
    monkeypatch.setenv("ORDER_LIFECYCLE_ENABLED", "0")
    import app.core.settings as m
    assert m.Settings().order_lifecycle_enabled is False


def test_order_lifecycle_auto_approve_toggles(monkeypatch):
    """ORDER_LIFECYCLE_AUTO_APPROVE=true flips the sub-flag on."""
    monkeypatch.setenv("ORDER_LIFECYCLE_AUTO_APPROVE", "true")
    import app.core.settings as m
    assert m.Settings().order_lifecycle_auto_approve is True


def test_order_backorder_enabled_toggles(monkeypatch):
    """ORDER_BACKORDER_ENABLED=yes flips the sub-flag on."""
    monkeypatch.setenv("ORDER_BACKORDER_ENABLED", "yes")
    import app.core.settings as m
    assert m.Settings().order_backorder_enabled is True


def test_object_setattr_pattern_for_downstream_tests():
    """Demonstrates object.__setattr__ mutation used by downstream service tests."""
    import app.core.settings as m
    orig = m.S.order_lifecycle_enabled
    try:
        object.__setattr__(m.S, "order_lifecycle_enabled", True)
        assert m.S.order_lifecycle_enabled is True
    finally:
        object.__setattr__(m.S, "order_lifecycle_enabled", orig)
    assert m.S.order_lifecycle_enabled is False
```

**Test strategy notes:**

- `monkeypatch.setenv` patches `os.environ` for the duration of the test; `m.Settings()` instantiates a fresh dataclass that reads the patched env. The module-level `S` singleton is NOT re-evaluated (it was already imported), so the tests instantiate a new `Settings()` object rather than inspecting `S` for the env-var toggle tests.
- The `test_object_setattr_pattern_for_downstream_tests` test validates that the frozen-dataclass mutation idiom works on `S`, documenting the pattern for ORD-003+ test authors.
- No `TestClient`, no FastAPI app, no async context needed.

### 9.2 Regression: existing order tests must remain green

Running `pytest tests/test_commerce_order_service.py` must produce the same result before and after this PR. The `_service` monkeypatch in that file patches `T` on the module, not `S`, so no interaction is expected. Verify explicitly in CI.

### 9.3 No E2E spec required

ORD-002 introduces no user-visible behavior. The flags are off by default and no new endpoint or UI exists. The E2E spec for the order lifecycle will be introduced in the milestone that ships the first visible feature (likely ORD-005 or ORD-008).

## 10. Open Questions / Assumptions

1. **Assumption**: The insertion point for the three new fields is immediately after `app/core/settings.py:1130` (after `api_entitlement_near_cap_thresholds`, before the blank line preceding the newsfeed block). This keeps order-related settings co-located. If the reviewer prefers a dedicated section further down the file (e.g., after line 2770, just before `S = Settings()`), the fields can be moved without functional impact.

2. **Assumption**: The flag naming convention `ORDER_LIFECYCLE_ENABLED` (underscore-separated uppercase) is consistent with the existing commerce flags (`ORDERS_TABLE_NAME`, `ORDER_ITEMS_TABLE_NAME`). No abbreviation is used. If a shorter name is preferred (e.g., `ORD_LIFECYCLE_ENABLED`), this spec assumes the longer form is chosen for clarity.

3. **Assumption**: `order_lifecycle_auto_approve` sub-flag semantics (auto-advance `created → approved` on payment confirmation) are confirmed by ORD-001 design note. If ORD-001 revises the transition graph so that `approved` is not a distinct state, this sub-flag may need to be renamed or dropped.

4. **Assumption**: `order_backorder_enabled` is a sub-flag of `order_lifecycle_enabled` in terms of runtime behavior, but is a separate env var (not a comma-list under the master flag). This matches how `messaging_transcription_enabled` and `messaging_tts_enabled` are each separate booleans rather than a combined comma-list.

5. **Open question**: Should there be a fourth flag `ORDER_LIFECYCLE_SHIP_GROUP_ENABLED` to independently gate ship-group functionality (ORD-009), separate from the state-machine (ORD-005)? This spec defers the question to ORD-009's design phase. If ship groups are always bundled with the master flag, no additional flag is needed.

6. **Open question**: The `.env.local.example` update adds commented-out lines. If the CI pipeline runs integration tests with `ORDER_LIFECYCLE_ENABLED=true` to validate downstream tickets, who owns updating `.env.local.example` from commented to uncommented? This spec assumes ORD-003 or the first milestone 2 ticket makes that change when the first testable behavior exists.
