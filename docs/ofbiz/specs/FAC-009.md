# FAC-009 — Pack into packages

## 1. Summary & Goal

FAC-009 delivers `pack_picklist(picklist_id, packages, *, packed_by)` in
`app/services/packing.py` (a new sibling of the FAC-008 `picking.py` module).
Its responsibility is exactly one lifecycle step: **consume the output of a
completed pick, group the picked lines into one or more physical packages, and
create a draft shipment record** so FAC-010 (`ship_shipment`) has a concrete
`T.shipments` row to finalize.

Concretely this ticket ships:

1. **`pack_picklist(...)`** — validates that each package's contents sum to the
   picked quantities (no over-pack, no under-pack unless a partial-pack mode is
   explicitly enabled), writes a `T.shipments` draft header + `PKG#{n}` rows,
   writes `shipment_id` back onto the picklist `META` row, and flips the
   picklist status from `picked` to `packed` via a single-writer conditional
   update.
2. **`get_shipment(shipment_id)`** and **`list_shipments_for_order(order_id)`**
   — read helpers consumed by the FAC-011 router.
3. **Idempotency** — the picklist status guard (`#status = :picked`) is the
   single-writer fence: a replay that arrives while the first call is still
   in-flight races to the same conditional, and only one winner proceeds. A
   second call after the picklist is already `packed` immediately returns the
   existing shipment (no double-write, no error).
4. **Audit** — `alerts.audit_event("packing.packed", ...)` emitted best-effort
   after the write.

Everything is **additive and flag-gated** behind `S.facility_fulfillment_enabled`
(default `False`). With the flag off the entire module is dormant: the
`_require_enabled()` guard raises HTTP 404, and all existing shop/cart/orders/
billing code is byte-for-byte unchanged.

## 5. Detailed Behavior & Edge Cases

### 5.1 `pack_picklist` — step-by-step

1. **Flag gate**: `_require_enabled()`. Raises 404 when `S.facility_fulfillment_enabled` is `False`.

2. **Input validation**:
   - `packages` must be non-empty.
   - Each package must have at least one `contents` line.
   - Each contents line: `sku` non-empty, `quantity >= 1`.
   - Duplicate `(order_line_id, sku)` pairs across packages are allowed (split
     shipment scenario); duplicate within a single package are rejected (409
     "Duplicate SKU in package contents").

3. **Load picklist**: `T.picklists.get_item(Key={"picklist_id": pid, "sk": "META"})`.
   Raises 404 if absent.

4. **Status pre-check** (pre-flight, not the authoritative guard):
   - If `meta["status"] == "packed"`: the picklist was already packed. Look up
     and return the existing shipment via `get_shipment(meta["shipment_id"])`.
     This is the fast idempotent-replay path — avoids a no-op conditional write.
   - If `meta["status"] != "picked"`: raise 409
     `f"Picklist is in status '{meta['status']}'; expected 'picked'"`.

5. **Load pick lines**: `T.picklists.query(KeyConditionExpression=Key("picklist_id").eq(pid) & Key("sk").begins_with("LINE#"))`.
   Filter to rows whose `sk` begins with `"LINE#"`. Build a dict
   `picked_by_sku: Dict[str, int]` mapping each SKU to its cumulative
   `picked_qty` across all lines. Also build `order_line_id_for_sku` for
   contents cross-referencing.

6. **Quantity reconciliation**:
   - Build `packed_by_sku: Dict[str, int]` by summing `quantity` across all
     packages' `contents` for each SKU.
   - For each SKU in `packed_by_sku`:
     - If `sku` not in `picked_by_sku`: raise 409
       `f"SKU '{sku}' in packages was not in the picklist"`.
     - If `packed_by_sku[sku] > picked_by_sku[sku]`: raise 409
       `f"Over-pack: SKU '{sku}' packed {n} but only {m} was picked"`.
   - The inverse (picked more than packed) is **allowed by default** — partial
     packing scenarios are valid (e.g., a large pallet is partially boxed; the
     remainder ships in a second wave). Over-pack is the hard error because it
     implies inventory that does not exist.

7. **Generate `shipment_id`**: `shipment_id = uuid4().hex`.

8. **Write `PKG#{n}` rows** (one `put_item` per package, 1-based index).
   No conditional expression on package rows — they are children of the
   shipment header and the shipment header does not yet exist. If the process
   crashes after writing some packages but before the header, the orphaned rows
   carry the `shipment_id` that was never written to the picklist; they become
   invisible to queries (no META row, no GSI entry). The idempotency fence at
   step 9 ensures step 7 only runs once per picklist.

9. **Write shipment `META` row** via unconditional `put_item` (the authoritative
   guard is on the picklist, not the shipment):
   ```
   T.shipments.put_item(Item={
       "shipment_id": shipment_id,
       "sk": "META",
       "order_id": meta["order_id"],
       "picklist_id": picklist_id,
       "status": "draft",
       "carrier": "",
       "tracking_number": "",
       "package_count": len(packages),
       "created_by": packed_by,
       "created_at": now_ts(),
       "shipped_at": 0,
       "updated_at": now_ts(),
   })
   ```

10. **Flip picklist to `packed`** via `_transition_picklist(picklist_id, "picked", "packed", extra_set={"shipment_id": shipment_id, "updated_at": now_ts()})`:
    - On success (`old` is not `None`): proceed to step 11.
    - On `None` return (concurrent write or already-packed replay): the shipment
      rows written in steps 8–9 are orphaned. Load the picklist `META` again,
      read `meta["shipment_id"]`, and return `get_shipment(meta["shipment_id"])`.
      The orphaned rows are unreachable and will not interfere. This is
      acceptable under the low-frequency replay assumption; a cleanup task is
      outside scope.

11. **Emit audit event**:
    ```python
    _audit("packing.packed", packed_by,
           picklist_id=picklist_id,
           shipment_id=shipment_id,
           order_id=meta.get("order_id"),
           package_count=len(packages))
    ```

12. **Return** `_shipment_out(header, pkg_rows)`.

### 5.2 Over-pack vs under-pack

- **Over-pack** (packed quantity > picked quantity for any SKU): **hard 409 error**.
  Packing more units than were picked implies physical impossibility — the
  picker never collected those units.
- **Under-pack** (packed quantity < picked quantity for any SKU): **allowed**.
  The remaining picked-but-not-packed units are not tracked by FAC-009; the
  assumption is the caller packs all remaining units in subsequent calls (which
  is also allowed since the picklist remains in `picked` status until a
  successful pack). If the business rule later requires full-pack enforcement
  (all picked units must be in some package), this can be toggled via a new
  `S.packing_require_full_coverage` flag (default `False`) without changing the
  existing call sites.

### 5.3 Idempotency invariants

- **Same picklist, first call succeeds**: writes shipment, flips picklist to
  `packed`. Subsequent calls reach the fast-path at step 4 and return the
  existing shipment.
- **Same picklist, concurrent second call** (first call in-flight at step 9,
  second call also passes the pre-flight check at step 4 because the status is
  still `picked`): both calls write separate shipment rows (different
  `shipment_id` values). The conditional at step 10 ensures only one caller
  wins the `picked → packed` fence. The losing caller's orphaned shipment rows
  are garbage-collected as described in step 10.
- **Already-cancelled picklist**: step 4 raises 409. No shipment is created.

### 5.4 No inventory side-effect

`pack_picklist` does **not** call `inventory.commit_reservation` or
`inventory.adjust`. Those calls are already made by FAC-008 `confirm_pick` at
the point each pick line is confirmed (reservation committed → on-hand
decremented). By the time `pack_picklist` is called the inventory is already
settled. This is the correct separation: pick = inventory gate; pack = shipment
creation.

### 5.5 Relationship to FAC-010 `ship_shipment`

`pack_picklist` creates a `draft` shipment. FAC-010 `ship_shipment` calls the
shipment-level guard (`ConditionExpression="#status = :draft"` or
`"#status = :packed"`) and stamps `carrier`, `tracking_number`, `shipped_at`,
and advances the status to `shipped`. FAC-009 is the only writer of the
`draft` status; FAC-010 is the only writer of `shipped`. Neither touches the
other's state machine entry.

### 5.6 `order_id` on the shipment

The shipment `META` row carries `order_id` copied from the picklist `META`.
This enables `GSI_ORDER` queries (`list_shipments_for_order`) without an
extra lookup. If the picklist `META` has no `order_id` (should never happen
after FAC-008 correctly writes it), the shipment is written with
`order_id = ""` and will not appear in order-scoped queries — a safe
degradation that does not raise an error.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

`packing.py` contains **no** `dev_mode` or `S.dev_mode` branch. DynamoDB
reads and writes go to `T.picklists` and `T.shipments` in both dev (DynamoDB
Local on port 8001, accessed via moto-backed `_safe_table`) and prod (real
DynamoDB). The `_safe_table` wrapper at `app/core/tables.py:65–66` <!-- VERIFIED: tables.py:65 def _safe_table(), :66 returns _FloatSafeTable(ddb.Table(name)) --> provides
float-to-Decimal coercion identically in both environments. This mirrors
every other OFBiz service: `app/services/inventory.py:1–29`,
`app/services/returns_rma.py:67–68` <!-- VERIFIED: returns_rma.py:67 def _flag_on() -->,
`app/services/receiving.py` (FAC-007, not yet implemented).

The `_audit` helper lazy-imports `app.services.alerts.audit_event`. In dev
that module logs to the console; in prod it writes to the `T.alerts` DynamoDB
table. No divergence in the calling code.

### Idempotency

The primary idempotency fence is the single-writer conditional update on the
picklist `META` row (`ConditionExpression="#status = :picked"`). At most one
concurrent caller can win this transition. The fast-path pre-check (step 4 of
§5.1) short-circuits the vast majority of replays without a write, matching
the pattern in `app/services/returns_rma.py:382–384` <!-- VERIFIED: returns_rma.py:382–384 if old is None: return get_return(return_id) -->.

The shipment row itself is not conditionally written; its idempotency is
derived from the picklist fence. This is equivalent to the pattern in
`app/services/receiving.py` where the receipt header is the idempotency gate
and line rows are written unconditionally after the header is secured.

### Security

- `pack_picklist` is a warehouse mutation; it MUST be called only from a
  handler protected by `require_admin_or_root_csrf` (FAC-011). The service
  function itself does not enforce this — it accepts any caller-supplied
  `packed_by` string. The auth boundary is the router layer, consistent with
  all other OFBiz service functions (e.g. `inventory.adjust` at
  `app/services/inventory.py:209` <!-- VERIFIED: inventory.py:209 def adjust() --> accepts `user_sub` as a plain parameter).
- `packed_by` is stamped on both the shipment `created_by` field and the audit
  event. It must be the authenticated user's `user_sub` (enforced by the router
  extracting it from `session.user_sub`).
- No customer-PII fields are stored in the shipment or package rows.

## 10. Open Questions / Assumptions

1. **`packing.py` vs extending `picking.py`**: The ticket text says "add
   `pack_picklist` to `app/services/picking.py` (or a sibling `packing.py`)".
   This spec assumes `packing.py` (one file per lifecycle step, matching the
   established pattern of separate `receiving.py`, `picking.py` files). If the
   implementor places it in `picking.py` the logic is identical; only the
   module boundary changes.

2. **Over-pack enforcement level**: The spec rejects over-pack (packed >
   picked) with a hard 409. Under-pack is allowed. This is the minimally safe
   default. If the product requires that all picked units ship in the same pack
   operation, add `S.packing_require_full_coverage` (default `False`) with a
   check: `if sum(packed) < sum(picked): raise 409 "Under-pack not allowed"`.

3. **Package `dimensions_cm` naming vs mm**: FAC-002
   (`docs/ofbiz/specs/FAC-002.md:315`) names the map `dimensions_cm` while
   `PackageIn` (`docs/ofbiz/specs/FAC-003.md:345–347`) uses `_mm` suffix
   fields. This spec stores the value under the DDB attribute name
   `dimensions_cm` (matching FAC-002) and maps `PackageIn.length_mm` →
   `dimensions_cm.l`. If FAC-003 is revised to align names before
   implementation this assumption is moot.

4. **Orphaned shipment rows on concurrent losing call**: The spec accepts
   orphaned PKG rows as an acceptable outcome of a rare concurrency scenario.
   A stricter approach (write shipment header first with a
   `attribute_not_exists(shipment_id)` conditional, then write PKG rows, then
   fence the picklist) would avoid orphans but would require a two-table
   conditional that DynamoDB does not support natively. A background sweep
   cleaning up `draft` shipments with no matching `packed` picklist can be
   added in a later cleanup ticket if orphaned rows accumulate.

5. **Partial-pack multi-wave flow**: The current spec only supports a single
   `pack_picklist` call per picklist (the picklist goes directly to `packed`).
   If the warehouse wants to pack in multiple waves (e.g. box SKU-A first, then
   SKU-B on a second call), a `packing_session` intermediate status would be
   needed. This is not in scope for FAC-009.

6. **`order_id` on picklist**: The spec reads `order_id` from the picklist
   `META` row (written by FAC-008). If FAC-008 does not write `order_id` onto
   the picklist header the shipment's `GSI_ORDER` entry will be missing. This
   dependency on FAC-008's output schema is assumed correct; the implementor
   must verify FAC-008's actual `META` write before shipping FAC-009.

7. **`picked_qty` vs `quantity` on LINE rows**: The spec reads `picked_qty`
   (the confirmed amount) not `quantity` (the originally requested amount) as
   the ceiling for over-pack checks. If a pick was short-picked (picked < ordered),
   `picked_qty` reflects reality; using `quantity` would block packing of a
   short-pick scenario. Assumption: `picked_qty` is the correct ceiling.
