# ORD-010 — Cancel & return transitions (refund via existing billing)

**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days
**Milestone:** 4 — Router & API (pre-req for ORD-011)

---

## 1. Summary & Goal

ORD-010 adds two service-layer functions — `cancel_order` and `return_order` — to `app/services/order_lifecycle.py` (created by ORD-005). These functions drive the lifecycle state machine into the terminal `cancelled` and `returned` states, and optionally issue a refund through the **existing** billing ledger primitives: `new_ledger_entry`, `apply_balance_delta`, and `settle_or_reverse_ledger` from `app/services/billing_shared.py`.

Key invariants:

1. **No parallel refund mechanism.** Every money-out path calls the same primitives that `billing.refund_payment` uses (`app/routers/billing.py:1306–1324`). The general ledger continues to derive from the single-entry ledger.
2. **Provider attribution preserved.** Refund ledger entries carry `extra={"provider": <provider>, "order_id": <order_id>}` per the FIN-013 / GAP-0203 requirement (`app/services/billing_shared.py:235`).
3. **Refund amount accounts for ORD-008 adjustments.** The amount refunded is `compute_adjusted_amount(order_id)` from `app/services/order_adjustments.py`, not the raw `amount_cents`. If no adjustments exist, `compute_adjusted_amount` falls back to the base `amount_cents` transparently.
4. **Idempotent.** A second cancel/return of the same order is a no-op (the state machine's CAS guard prevents a double-transition). A second refund of the same payment is prevented because the ledger entry is only written inside the single-writer CAS block.
5. **Additive, flag-gated.** With `S.order_lifecycle_enabled = False` (default), the existing shop/cart/orders/billing flows are byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 Current order record — no cancel/return logic

`CommerceOrderService.create_order` at `app/services/commerce_order_service.py:39` is the only order-creation path. It hard-codes `"status": "pending_payment"` at line 75 and persists the header at line 85. There is no `cancel_order`, no `return_order`, no `lifecycle_status`, and no refund hook anywhere in the order layer today. The `orders` table at `scripts/local-ddb-init.py:288` has PK `order_id` with no sort key in the base definition (ORD-003 adds `sk`).

### 2.2 Existing billing refund path (the one ORD-010 reuses)

`billing.refund_payment` at `app/routers/billing.py:1287–1344` is the authoritative refund handler. Its four-step write sequence is:

1. `new_ledger_entry(key_name="pk", key_value=pk, entry_type="adjustment", amount_cents=amount, state="settled", reason="refund", extra={"stripe_payment_intent_id": ..., "stripe_refund_id": ..., "provider": "stripe"})` — `app/routers/billing.py:1306–1315`.
2. `ddb_put(T.billing, led_item)` — `app/routers/billing.py:1316`.
3. `apply_balance_delta(T.billing, pk, ...)` — `app/routers/billing.py:1318–1321`. Note: this call is conditional on payment status — `payments_pending_cents` for `"processing"`/`"requires_action"` payments (line 1319); `payments_settled_cents` for all others (line 1321). ORD-010's `_refund_order_payment` always uses the `payments_settled_cents` branch (orders are presumed settled before cancellation).
4. `settle_or_reverse_ledger(T.billing, "pk", pk, pay["ledger_sk"], "reversed")` — `app/routers/billing.py:1323–1324` (conditional: only when `pay.get("ledger_sk")` is set).

ORD-010 replicates this exact sequence inside `cancel_order` / `return_order`, imported from `app.services.billing_shared` (which exports all four primitives — `new_ledger_entry` at `app/services/billing_shared.py:224`, `apply_balance_delta` at `:83`, `settle_or_reverse_ledger` at `:262`, `ddb_put` at `:32`, `user_pk` at `:23`). The `returns_rma.refund_return` function (`app/services/returns_rma.py:444–542`) is the precedent for doing this from outside the billing router — it already uses the same four primitives to issue a refund.

### 2.3 FIN-013 provider attribution requirement

`app/services/billing_shared.py:235` contains the authoritative comment:

> provider-originating transactions MUST pass `extra={"provider": "stripe"|"paypal"|"ccbill"}` so the platform financial dashboard provider breakdown can attribute the entry.

ORD-010 passes `extra={"provider": provider, "order_id": order_id}` where `provider` is read from the order record's `metadata` (best-effort), defaulting to `"stripe"` when absent. This matches the `returns_rma.refund_return` pattern at `app/services/returns_rma.py:503–504`.

### 2.4 Order payment linkage

Today `commerce_order_service.create_order` does not store `payment_intent_id` or `ledger_sk` on the order header. The `app/services/shoppingcart.py:581–594` call site passes `metadata={"cart_id": ..., "idempotency_key": ..., "request_idempotency_key": ..., "promo_code_id": ..., "discount_cents": ..., "original_total_cents": ...}` but no billing fields. The RMA service at `app/services/returns_rma.py:492–494` reads `order.get("ledger_sk")` and `order.get("payment_intent_id") or (order.get("metadata") or {}).get("payment_intent_id")` as best-effort lookups.

ORD-010 follows the same best-effort pattern: it reads `ledger_sk` and `payment_intent_id` from the order header (and its `metadata` map) when available, uses them to reverse the original charge and update the payment record, but proceeds with the balance-delta refund even when they are absent. This matches the RMA precedent and is appropriate because orders may have been paid through non-Stripe paths or via wallet balance.

### 2.5 Adjusted refund amount (ORD-008 dependency)

ORD-008 defines `compute_adjusted_amount(order_id)` in `app/services/order_adjustments.py`. Per `docs/ofbiz/specs/ORD-008.md:562`, this function reads `adjusted_amount_cents` from the ORDER-SK header and falls back to `amount_cents` when the attribute is absent. ORD-010 calls this function to determine the refund amount, so discounts/surcharges are automatically honoured. The function is a read-only helper — no DDB writes.

### 2.6 State machine — cancellable and returnable states

From the `TRANSITIONS` graph defined in ORD-005 (`docs/ofbiz/specs/ORD-005.md:190–206`):

- `CANCELLED` is reachable from: `created`, `approved`, `allocated`, `picking`, `packed`, `held`, `backorder` — all pre-`shipped` states.
- `RETURNED` is reachable from: `shipped`, `completed`.
- `CANCELLED` and `RETURNED` have empty outbound sets (terminal).

ORD-010 calls `transition_order` from ORD-005 to perform the state change (optimistic CAS), then conditionally issues the refund. The refund is issued *after* the successful CAS, not atomically with it — matching the pattern in `returns_rma.refund_return` (`app/services/returns_rma.py:482–509`).

### 2.7 Audit event convention

`app/services/commerce_order_service.py:106` calls `audit_event("commerce_order_created", user_id, None, ...)` [verified: `commerce_order_service.py:106`]. ORD-010 emits `audit_event("order_cancelled", ...)` and `audit_event("order_returned", ...)` via the same `app.services.alerts.audit_event` import convention shown at `app/services/commerce_order_service.py:9` [verified].

## 3. Data Model

ORD-010 introduces **no new DynamoDB tables, GSIs, or `attr_types` declarations**. It writes to the existing `orders` table (ORD-003 schema) and the existing `billing` table, both of which are already defined in `scripts/local-ddb-init.py`.

### 3.1 Orders table — ORDER-SK header, additive fields

**Table**: `orders` (env `ORDERS_TABLE_NAME` → `S.orders_table_name`, default `"orders"`) [verified: `app/core/settings.py:1124`, `scripts/local-ddb-init.py:288`]
**Key after ORD-003**: `order_id` (S, PK) + `sk = "ORDER"` (S, range key)

The current `orders` table (before ORD-003) has only `order_id` as PK with no sort key, plus `GSI_USER` (`user_id`, `created_at`) and `GSI_STATUS` (`status`, `created_at`) [verified: `scripts/local-ddb-init.py:288–294`]. ORD-003 adds `sk`, `GSI_ORDER_STATUS` (`lifecycle_status`, `updated_ts N`), and `GSI_ORDER_SHIPDATE`.

Fields written by `cancel_order` / `return_order` on the ORDER-SK header:

| Attribute | DDB type | Notes |
|---|---|---|
| `lifecycle_status` | S | Set to `"cancelled"` or `"returned"` by `transition_order` (ORD-005) |
| `status` | S | Legacy mirror, also set to `"cancelled"` / `"returned"` by `transition_order` |
| `updated_ts` | N | `now_ts()` — projected into `GSI_ORDER_STATUS` SK (added by ORD-003) |
| `updated_at` | S | ISO-8601 string |
| `cancellation_reason` | S | Reason string passed to `cancel_order`; written after CAS via `update_item` |
| `cancellation_ledger_sk` | S | `led_sk_value` returned by `new_ledger_entry`; written after refund for linkage/idempotency audit |
| `return_ledger_sk` | S | `led_sk_value` for returned orders |
| `refund_amount_cents` | N | Actual amount refunded (≥ 0); written after refund |

All other header fields (`order_id`, `user_id`, `source_system`, `correlation_id`, `currency`, `amount_cents`, `adjusted_amount_cents`, `line_item_count`, `metadata`, `created_at`) are untouched.

### 3.2 Billing table — new refund ledger entry

The refund ledger entry is written to the existing `billing` table under the user's billing partition key using the standard `new_ledger_entry` path:

| Attribute | Value |
|---|---|
| `pk` | `USER#{user_id}` (from `user_pk(user_id)`) |
| `sk` | `LEDGER#{ts}#{entry_id}` (from `ledger_sk(ts, entry_id)`) |
| `type` | `"adjustment"` |
| `reason` | `"refund"` |
| `state` | `"settled"` |
| `amount_cents` | `compute_adjusted_amount(order_id)` |
| `ledger_date` | UTC date string from `ledger_date_for_ts(ts)` — FIN-013 GSI attribution |
| `provider` | `order.get("provider") or (order.get("metadata") or {}).get("provider") or "stripe"` |
| `order_id` | the order's `order_id` (for cross-reference) |

The `ledger_date` field is written automatically by `new_ledger_entry` at `app/services/billing_shared.py:253` [verified: `billing_shared.py:251–253`, `"ledger_date": ledger_date_for_ts(ts)`]. No schema change is needed.

### 3.3 Idempotency key for refund ledger entry

The refund ledger `entry_id` is derived deterministically:

```python
import hashlib
refund_correlation = f"cancel_refund:{order_id}:{lifecycle_status_at_cancel}"
refund_entry_id = hashlib.sha256(refund_correlation.encode()).hexdigest()[:16]
```

This mirrors the `sha256(corr)[:32]` pattern from `commerce_order_service.py:67` [verified: `commerce_order_service.py:67`, `order_id = hashlib.sha256(corr.encode("utf-8")).hexdigest()[:32]`]. If `new_ledger_entry` is called a second time with the same deterministic `refund_entry_id` embedded in the SK, the `ddb_put` will silently overwrite an identical item (idempotent). In practice, the second call cannot happen because the CAS in `transition_order` (ORD-005) will return `None` (conflict) on the second call and the refund block is never reached.

#### 4.1.2 `_refund_order_payment` — internal helper

```python
def _refund_order_payment(
    *,
    user_id: str,
    order_id: str,
    amount_cents: int,
    currency: str,
    reason: str,           # "order_cancelled" | "order_returned"
    provider: str,         # e.g. "stripe"
    original_ledger_sk: Optional[str],
) -> str:
    """Issue a billing-ledger refund for an order.

    Reuses new_ledger_entry / apply_balance_delta / settle_or_reverse_ledger
    from app.services.billing_shared — identical sequence to
    billing.refund_payment (app/routers/billing.py:1306-1324) and
    returns_rma.refund_return (app/services/returns_rma.py:496-509).

    Returns the led_sk_value so the caller can store it on the order header.
    Never raises on refund errors: a failed ledger write is best-effort
    (logged), but the state transition is not rolled back.
    """
    from app.services.billing_shared import (
        apply_balance_delta,
        ddb_put,
        new_ledger_entry,
        settle_or_reverse_ledger,
        user_pk,
    )

    pk = user_pk(user_id)
    led_sk_value, led_item = new_ledger_entry(
        key_name="pk",
        key_value=pk,
        entry_type="adjustment",
        amount_cents=int(amount_cents),
        state="settled",
        reason="refund",
        meta={"reason": reason, "order_id": order_id},
        extra={"provider": provider, "order_id": order_id},
    )
    ddb_put(T.billing, led_item)
    apply_balance_delta(
        T.billing, pk,
        {"payments_settled_cents": -int(amount_cents)},
        currency=currency,
    )
    if original_ledger_sk:
        settle_or_reverse_ledger(
            T.billing, "pk", pk, original_ledger_sk, "reversed"
        )
    return led_sk_value
```

This helper is `_refund_order_payment` (internal, prefixed with `_`). It is called from both `cancel_order` and `return_order`. It is not exported.

#### 4.1.3 `cancel_order` — public function

```python
def cancel_order(
    order_id: str,
    *,
    actor: str,
    reason: str,
    refund: bool = False,
    idempotency_key: Optional[str] = None,
) -> Dict[str, Any]:
    """Transition a pre-shipped order to 'cancelled'.

    Validates that the current lifecycle_status is a pre-shipped state.
    Optionally issues a refund through the existing billing ledger path.

    Raises:
        OrderNotFoundError   — order does not exist
        OrderTransitionError — already shipped/completed/returned (409)
        OrderConflictError   — concurrent lifecycle update (409)
    """
```

**Pre-condition check**: Before calling `transition_order`, `cancel_order` reads the order header via `get_order_header(order_id)`. If the current `lifecycle_status` is `"shipped"`, `"completed"`, or `"returned"`, it raises `OrderTransitionError(current, "cancelled")` with a detail message indicating the caller must use `return_order` for post-shipment reversal. This guards the semantic "pre-shipped only" rule in addition to the `TRANSITIONS` graph check performed inside `transition_order`.

**Transition**: Calls `transition_order(order_id, "cancelled", actor=actor, reason=reason, idempotency_key=idempotency_key)`. If `transition_order` raises `OrderConflictError` (CAS failed — already in target state or concurrent writer won), and the current state is already `"cancelled"`, the function returns the current header as a no-op (idempotent replay). Any other `OrderConflictError` or `OrderTransitionError` is re-raised.

**Refund (conditional on `refund=True`)**:

1. Read `adjusted_amount_cents` via `compute_adjusted_amount(order_id)` from `app.services.order_adjustments`.
2. If amount is 0, skip the refund (nothing to refund).
3. Resolve `provider` from `order.get("provider") or (order.get("metadata") or {}).get("provider") or "stripe"`.
4. Call `_refund_order_payment(user_id=order["user_id"], order_id=order_id, amount_cents=amount, currency=order.get("currency", "usd"), reason="order_cancelled", provider=provider, original_ledger_sk=order.get("ledger_sk"))`.
5. Write `cancellation_ledger_sk` and `refund_amount_cents` back to the ORDER-SK header via `T.orders.update_item`. Failures are caught and logged — the state is already `"cancelled"` and cannot be rolled back.

**Audit**: `audit_event("order_cancelled", actor, None, order_id=order_id, reason=reason, refund=refund, refund_amount_cents=refund_amount)`.

**Return value**: The updated ORDER-SK header dict (same shape as `get_order_header` returns).

#### 4.1.4 `return_order` — public function

```python
def return_order(
    order_id: str,
    *,
    actor: str,
    reason: str,
    refund: bool = False,
    idempotency_key: Optional[str] = None,
) -> Dict[str, Any]:
    """Transition a shipped/completed order to 'returned'.

    Called by the Returns/RMA module (OFB-010 / returns_rma.py) as the
    bridge that drives the order lifecycle state alongside the RMA record.
    Can also be called directly by an admin.

    Raises:
        OrderNotFoundError   — order does not exist
        OrderTransitionError — not shipped/completed (409)
        OrderConflictError   — concurrent lifecycle update (409)
    """
```

**Pre-condition check**: Reads the header. If `lifecycle_status` is not in `{"shipped", "completed"}`, raises `OrderTransitionError(current, "returned")` — only shipped/completed orders go through `return_order`; pre-shipped reversal uses `cancel_order`.

**Transition**: Calls `transition_order(order_id, "returned", actor=actor, reason=reason, idempotency_key=idempotency_key)`. Idempotent replay (already `"returned"`) returns the current header without re-issuing the refund.

**Refund (conditional on `refund=True`)**: Identical sequence to `cancel_order` but with `reason="order_returned"` and writing `return_ledger_sk` / `refund_amount_cents` to the ORDER-SK header.

**Audit**: `audit_event("order_returned", actor, None, order_id=order_id, reason=reason, refund=refund, refund_amount_cents=refund_amount)`.

**Return value**: Updated ORDER-SK header dict.

## 5. Detailed Behavior & Edge Cases

### 5.1 Pre-shipped-only cancellation

States from which `cancelled` is reachable per the ORD-005 `TRANSITIONS` graph: `created`, `approved`, `allocated`, `picking`, `packed`, `held`, `backorder`. States `shipped` and `completed` are **not** in this set. `cancel_order` adds a semantic pre-check (separate from the CAS graph) to return a clear 409 message ("shipped/completed orders must use return_order") rather than a generic "Illegal transition" error. Both checks are present — belt and suspenders.

### 5.2 Idempotency — double-cancel

If `cancel_order` is called twice with the same `order_id` and `idempotency_key`:

1. First call: CAS succeeds → `lifecycle_status` → `"cancelled"`, refund ledger entry written (if `refund=True`), `cancellation_ledger_sk` written.
2. Second call: `get_order_header` returns `lifecycle_status = "cancelled"`. `transition_order` CAS fails (`ConditionalCheckFailedException`). `cancel_order` detects the already-`"cancelled"` state and returns the current header. The refund block is never reached on the second call.

### 5.3 Idempotency — double-refund prevention

The refund block inside `cancel_order` is executed only after a successful CAS (the order was not yet `"cancelled"`). Since the CAS is single-writer, there is exactly one caller that succeeds. On second call, the CAS fails and the refund block is skipped entirely. No additional `attribute_not_exists` guard on the ledger row is needed.

As a belt-and-suspenders measure, the `entry_id` embedded in the ledger SK is derived deterministically from `order_id` and the transition's from-status (see §3.3). A hypothetical second write would produce an identical SK and item, which `ddb_put` would overwrite idempotently.

### 5.4 Refund amount — zero adjustments

When no `ADJ#` rows exist (the common case), `compute_adjusted_amount` returns the base `amount_cents` from the ORDER-SK header. The refund amount is therefore the original order total. This is correct for a full-order cancel.

When adjustments exist (ORD-008 feature is on), `compute_adjusted_amount` returns `adjusted_amount_cents` from the header (written by ORD-008). A 10% discount means the refund is 90% of the line total — the customer is refunded exactly what they paid after adjustments.

### 5.5 Currency

`currency` is read from the ORDER-SK header (`order.get("currency", "usd")`). It is passed to `apply_balance_delta`'s `currency` parameter, which is used by `ensure_balance_row` to initialize the balance row's currency on first write. Since the order and the original payment share the same currency (both derived from the line items at `commerce_order_service.py:70`), this is consistent.

### 5.6 Original ledger SK absent

If `order.get("ledger_sk")` is `None` (e.g., the order was created before ORD-010 was deployed, or it was paid via wallet balance with no Stripe charge), `_refund_order_payment` simply skips the `settle_or_reverse_ledger` call. The balance delta (`{"payments_settled_cents": -amount}`) and the new refund ledger entry are still written. This matches `returns_rma.refund_return:508–509` which does the same conditional skip.

### 5.7 Refund failure after state change

The CAS transition to `cancelled`/`returned` and the billing refund write are **not atomic**. If the billing write fails after the CAS succeeds:

- The order header already shows `lifecycle_status = "cancelled"`.
- The billing balance delta and ledger entry were NOT written.
- `cancellation_ledger_sk` is absent from the header.

This is the same best-effort pattern used by `returns_rma.refund_return`. The retry path: a second call to `cancel_order` with `refund=True` will find the order already `"cancelled"` (idempotent replay) and return the header — it will NOT re-issue the refund. To handle the failure-after-CAS edge case, the ORD-011 router should expose a dedicated re-issue endpoint, or ops can manually write the ledger row via the existing `POST /billing/refund` endpoint with the `payment_intent_id` from the order's `metadata`.

This behavior is explicitly noted as a known limitation and listed in §10 Open Questions.

### 5.8 `held` → `cancelled`

`held` is a pre-shipped state and `cancelled` is in `TRANSITIONS["held"]`. `cancel_order` accepts an order in the `held` state and transitions it to `cancelled` normally. The `pre_hold_status` attribute is left on the header as a historical record (not cleaned up, since the order is now terminal).

### 5.9 `return_order` as an RMA bridge

The RMA module (`app/services/returns_rma.py:444`) already issues a refund via the billing primitives when `refunded` status is reached. When an ORD-011 admin also calls `return_order(order_id, refund=True)` on the same order, this results in two refund ledger entries: one from `returns_rma.refund_return` and one from `return_order`. This double-refund scenario is a cross-module coordination issue.

Design decision: `return_order` is the lifecycle-only bridge — it transitions the order header to `returned` and optionally issues a refund. It does **not** check whether an RMA refund was already issued. When the RMA module is in use, the typical call pattern is:

- RMA module calls `return_order(order_id, refund=False)` — transition only, no billing.
- RMA module then issues the refund via its own `refund_return` path.

The `refund=True` parameter on `return_order` is intended for admin direct-cancel-after-shipment scenarios where no RMA was opened. The ORD-011 router documentation must make this contract explicit.

### 5.10 `backorder` → `cancelled`

`backorder` is reachable only with `S.order_backorder_enabled = True` (ORD-002 sub-flag). If the sub-flag is off, the `backorder` state cannot be entered; however, `cancelled` is in `TRANSITIONS["backorder"]` and `cancel_order` handles it normally if the order somehow reaches `backorder`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

All DynamoDB writes go through `T.orders` (moto-backed in dev via `scripts/local-ddb-init.py:288`) and `T.billing` (moto-backed; `billing` table at `scripts/local-ddb-init.py:68` [verified: `billing` table defined at `:67–77` with `GSI_LEDGER_DATE`]). No `S.dev_mode` branch exists in the service functions. Billing primitives from `app/services/billing_shared.py` already work identically in both dev (moto) and prod (real DynamoDB). The pattern is established by `returns_rma.refund_return` which is tested against moto with no separate mock path.

### 7.2 Idempotency summary

| Operation | Idempotency mechanism |
|---|---|
| `transition_order("cancelled")` | CAS on `lifecycle_status`; `ConditionalCheckFailedException` → return current header |
| `transition_order("returned")` | Same CAS |
| Refund ledger write | Only inside the successful CAS block (single-writer); deterministic `entry_id` from `sha256(order_id|from_status)[:16]` |
| `cancellation_ledger_sk` write | `update_item` after refund; idempotent overwrite if repeated |

### 7.3 Security

- **Ownership**: `cancel_order` and `return_order` accept `actor` (user_sub) but do not re-verify ownership internally — this is the ORD-011 router's responsibility. The service layer trusts the router to have enforced ownership before calling.
- **Amount floor**: `max(0, compute_adjusted_amount(order_id))` before the refund call. Zero-amount orders are skipped (no ledger write, no balance delta).
- **No Stripe API call**: ORD-010 does NOT call `stripe.Refund.create`. It only writes to the internal billing ledger (`T.billing`). This is intentional — the billing ledger is the source of truth for the platform GL; actual payment-provider refund dispatch is a separate concern (the ORD-011 router or a follow-up ticket can wire the Stripe API call if needed, following the pattern in `billing.refund_payment:1300–1304` [verified: `app/routers/billing.py:1300–1304`, `refund = stripe.Refund.create(...)`]). The design avoids requiring Stripe mock configuration in tests.
- **CSRF**: Not applicable at the service layer; enforced by ORD-011 router via `require_admin_or_root_csrf`.

## 10. Open Questions / Assumptions

**A1** — `order_lifecycle.py` already exists (created by ORD-005). This spec assumes ORD-005 has merged before ORD-010 begins implementation. The `TRANSITIONS` dict, `transition_order`, `get_order_header`, and `OrderTransitionError`/`OrderNotFoundError`/`OrderConflictError` are all available.

**A2** — `compute_adjusted_amount(order_id)` is exported from `app/services/order_adjustments.py` (ORD-008). This spec assumes ORD-008 has merged, or that `cancel_order` falls back gracefully: if the import fails (ORD-008 not yet deployed), a local fallback reads `adjusted_amount_cents` from the header directly, defaulting to `amount_cents`. The fallback is a one-line guard and does not affect behavior when ORD-008 is present.

**A3** — The `orders` table has `sk` as a sort key (ORD-003). If ORD-003 has not merged, the ORDER-SK key pattern (`{"order_id": ..., "sk": "ORDER"}`) will fail. ORD-010 is blocked on ORD-003.

**A4** — No Stripe API call in `cancel_order`/`return_order`. This is a deliberate choice (see §7.3). If a future ticket requires actual provider-side refund dispatch, it should hook into the existing `billing.refund_payment` endpoint or a new service function that wraps `stripe.Refund.create`. ORD-010 intentionally avoids this complexity.

**A5** — Failure-after-CAS (state changed but billing write failed) is acknowledged as a known gap. The recommended recovery path is manual re-issue via the existing `POST /billing/refund` endpoint. A future ticket could add an `order_cancel_refund_retry` background job, but this is out of scope for ORD-010.

**A6** — `return_order(refund=False)` is the expected call signature from the RMA module (OFB-010). The RMA module issues its own refund via `returns_rma.refund_return`. The ORD-011 router documentation must make the `refund=False` contract explicit to prevent accidental double-refund.

**A7** — The `T.billing` handle is imported from `app.core.tables`. The billing table name is not explicitly set in the order-lifecycle service today. `T.billing` is confirmed available at `app/core/tables.py` (used by `returns_rma.py:506`).
