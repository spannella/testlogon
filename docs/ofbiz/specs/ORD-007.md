# ORD-007 — Lifecycle integration at order creation (flag-gated)

**Type:** Feature | **Priority:** P0 | **Estimate:** 2 days
**Milestone:** 2 — State machine & status history

---

## 1. Summary & Goal

ORD-007 is the integration glue that connects the order state machine (ORD-005/ORD-006) with the platform's existing order-creation paths. When `ORDER_LIFECYCLE_ENABLED` is on, `CommerceOrderService.create_order` stamps `lifecycle_status="created"` on the new order header and writes the initial `created` HIST row. A second sub-flag, `ORDER_LIFECYCLE_AUTO_APPROVE`, optionally fires `transition_order(order_id, "approved", actor="system", ...)` immediately after order creation to advance the order to `approved` once payment has been taken. When either flag is off, the persisted order record is byte-for-byte identical to its pre-ORD-007 form — the only code changes are additive branches guarded by `if S.order_lifecycle_enabled`.

Two independent call sites drive orders today:
1. `CommerceOrderService.create_order` at `app/services/commerce_order_service.py:39` — the canonical path used by shopping cart (`app/services/shoppingcart.py:581`) and subscription cycle orders. [verified: `commerce_order_service.py:39–130`; `shoppingcart.py:581–595`]
2. `app/services/file_bundle_checkout.py:98` — a direct `T.orders.put_item` that bypasses the service class entirely. [verified: `file_bundle_checkout.py:94–110`]

ORD-007 instruments **only** the first path (`create_order`). The `file_bundle_checkout` path is not part of this ticket's scope (it uses a non-`sha256`-derived `order_id` and does not go through `CommerceOrderService`; integration there is tracked as a follow-up).

- `_append_history_row(order_id, *, from_status, to_status, actor, reason, event_id, ts)` — internal helper that writes `HIST#{ts:020d}#{event_id}` to `T.orders`.

### 2.5 `now_ts()` and `_now_iso()`

`app/core/time.py:2` defines `now_ts() -> int` returning `int(time.time())`. [verified: `time.py:2`] `CommerceOrderService._now_iso()` at line 19 returns `datetime.now(timezone.utc).isoformat()`. [verified: `commerce_order_service.py:18–20`] ORD-007 uses both:
- `now_ts()` for the numeric `ts` written to the HIST row.
- `_now_iso()` (already available inside `CommerceOrderService`) for `updated_at` when stamping `lifecycle_status`.

### 2.6 Idempotency anchor

The initial `created` HIST row uses a deterministic `event_id` derived from:
```python
event_id = sha256(f"{order_id}|None|created|").hexdigest()[:16]
```
This mirrors the `_derive_event_id(order_id, None, "created", None)` convention from ORD-005/ORD-006. Because `create_order` is itself idempotent via the `correlation_id → order_id` SHA-256 derivation (line 67), a replay of `create_order` with the same `correlation_id` produces the same `order_id` and therefore the same `event_id`, ensuring no duplicate HIST rows (ORD-006's `_append_history_row` uses `attribute_not_exists(sk)` on write).

### 2.7 Auto-approve idempotency anchor

The auto-approve `transition_order` call supplies an `idempotency_key` derived from the `order_id`:
```python
idempotency_key = f"auto_approve:{order_id}"
```
This ensures that if `create_order` is replayed (same `correlation_id`) and the auto-approve branch runs again, `transition_order` detects the replay via the deterministic `event_id = sha256(order_id|created|approved|auto_approve:{order_id})[:16]` and returns without writing a duplicate HIST row.

### 2.8 `file_bundle_checkout.py` out of scope

`app/services/file_bundle_checkout.py:98` writes directly to `T.orders` with a non-SHA-256 `order_id = uuid.uuid4().hex` (line 94) and no `correlation_id`. It bypasses `CommerceOrderService` entirely. ORD-007 does not instrument this path; doing so would require rethinking its `order_id` derivation and is out of scope.

## 3. Data Model

ORD-007 writes no new DynamoDB tables and adds no new GSIs. It extends the shape of the existing `orders` table ORDER-SK header row additively.

### 3.1 `orders` table — ORDER-SK header row, additive fields

**Table**: `orders` (env `ORDERS_TABLE_NAME`, default `"orders"`) [verified: `settings.py:1124`; `local-ddb-init.py:288–294`]
**Key**: `order_id` (S, PK) + `sk="ORDER"` (S, SK — added by ORD-003)

New attributes written by ORD-007 **only when `S.order_lifecycle_enabled` is `True`**:

| Attribute | DDB Type | Written at | Value |
|---|---|---|---|
| `lifecycle_status` | S | `create_order` + `put_item` | `"created"` initially; `"approved"` if auto-approve runs |
| `updated_ts` | N | `create_order` + `put_item` | `now_ts()` at creation time (integer Unix seconds) |
| `updated_at` | S | `create_order` + `put_item` | ISO-8601 string via `_now_iso()`; overwrites the pre-existing `updated_at` value from line 77 with the same timestamp |

When `S.order_lifecycle_enabled` is `False`, the `order_record` dict is identical to the pre-ORD-007 shape: `status`, `created_at`, `updated_at`, `source_system`, `correlation_id`, `currency`, `amount_cents`, `line_item_count`, `metadata`, and (after ORD-003) `sk` — no `lifecycle_status`, no `updated_ts`.

### 3.2 HIST rows written by ORD-007

ORD-007 writes exactly one HIST row at order creation (the `created` event) plus optionally a second HIST row if auto-approve fires. Both follow the ORD-006 schema:

| Attribute | Type | Value for the `created` row |
|---|---|---|
| `order_id` | S | PK — same `order_id` as the header |
| `sk` | S | `HIST#{ts:020d}#{event_id}` |
| `event_id` | S | `sha256(f"{order_id}|None|created|")[:16]` |
| `from_status` | — | **ABSENT** — ORD-006 §4.1.3 omits this attribute entirely when `from_status=None` is passed (DynamoDB rejects `None`; absent attribute is read back as `None` via `.get("from_status")`). The `_append_history_row` call in Change 2 already passes `from_status=None` correctly; only this table entry was wrong. [corrected: see §13] |
| `to_status` | S | `"created"` |
| `actor` | S | `user_id` from `create_order`'s `user_id` argument |
| `reason` | S | `"order_created"` (fixed string) |
| `ts` | N | `now_ts()` at creation |

The auto-approve HIST row (if fired) is written by `transition_order` as part of its normal ORD-006 flow; ORD-007 does not write it directly.

### 3.3 No `attr_types` changes needed

`updated_ts` appears as a GSI sort key for `GSI_ORDER_STATUS` (ORD-003 schema), which already declares `attr_types={"updated_ts": "N"}` in `scripts/local-ddb-init.py`. [verified: current `local-ddb-init.py:288–294` does NOT yet have `GSI_ORDER_STATUS` — it only has `GSI_USER` and `GSI_STATUS`; the `GSI_ORDER_STATUS` definition and `attr_types={"updated_ts": "N"}` are added by ORD-003 as a prerequisite; see ORD-003 spec §3.3] ORD-007 writes `updated_ts` into the ORDER header row; DynamoDB automatically projects it into the GSI. No additional `attr_types` declaration is required by ORD-007.

## 4. API / Service Design

### 4.1 Changes to `app/services/commerce_order_service.py`

ORD-007 makes **three additive changes** to `CommerceOrderService.create_order`:

**Change 1 — Stamp `lifecycle_status` on `order_record`**

After the existing `order_record` dict is assembled at line 72–84 and before `self.orders.put_item(Item=order_record)` at line 85, insert:

```python
# ORD-007: stamp lifecycle_status when order lifecycle is enabled
if S.order_lifecycle_enabled:
    ts_now = now_ts()
    order_record["lifecycle_status"] = "created"
    order_record["updated_ts"] = ts_now
    # updated_at is already set above; overwrite to be consistent with ts_now
    order_record["updated_at"] = self._now_iso()
```

The `put_item` call at line 85 is unchanged. The flag check is the only guard; no other code is conditionally compiled.

**Change 2 — Write the initial HIST row**

After `self.orders.put_item(Item=order_record)` at line 85, insert (still within the `if S.order_lifecycle_enabled` block, best-effort):

```python
# ORD-007: append the initial 'created' HIST row
if S.order_lifecycle_enabled:
    try:
        from app.services.order_lifecycle import _append_history_row, _derive_event_id
        _append_history_row(
            order_id,
            from_status=None,
            to_status="created",
            actor=user_id,
            reason="order_created",
            event_id=_derive_event_id(order_id, None, "created", None),
            ts=ts_now,
        )
    except Exception:
        pass  # HIST write failure is non-fatal; matches platform audit convention
```

The local import (`from app.services.order_lifecycle import ...`) avoids a circular-import risk: `order_lifecycle.py` imports `order_store.py`, which does not import `commerce_order_service.py`, so the dependency graph is acyclic. The lazy import also means that with the flag off, `order_lifecycle.py` is never imported by `create_order`.

**Change 3 — Auto-approve on payment success**

After the HIST row write, and only when `S.order_lifecycle_auto_approve` is also `True`:

```python
# ORD-007: auto-advance created → approved when ORDER_LIFECYCLE_AUTO_APPROVE is on
if S.order_lifecycle_enabled and S.order_lifecycle_auto_approve:
    try:
        from app.services.order_lifecycle import transition_order
        transition_order(
            order_id,
            "approved",
            actor="system",
            reason="auto_approved_on_payment",
            idempotency_key=f"auto_approve:{order_id}",
        )
    except Exception:
        pass  # best-effort; failure does not prevent order creation from returning
```

This call fires from inside `create_order`, which is called from `shoppingcart.purchase_cart` at `app/services/shoppingcart.py:581` after payment has been taken (the cart is only purchased when the billing path succeeds). The `actor="system"` string is written to the HIST row.

### 4.2 Return contract unchanged

The `create_order` function's return dict at line 119–130 is not modified by ORD-007. The returned `status` key still reflects the legacy `status` field (`"pending_payment"`) when `lifecycle_status` has not been mirrored back yet. Callers that care about the lifecycle status (ORD-011 admin UI) read it separately.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off golden record

With `S.order_lifecycle_enabled = False` (the default), `order_record` must contain exactly the same keys and values as before ORD-007:

```python
{
    "order_id": ...,      # sha256(corr)[:32]
    "user_id": ...,
    "status": "pending_payment",
    "created_at": ...,    # ISO-8601 string
    "updated_at": ...,    # same value as created_at
    "source_system": ...,
    "correlation_id": ...,
    "currency": ...,
    "amount_cents": ...,
    "line_item_count": ...,
    "metadata": {...},
    "sk": "ORDER",        # added unconditionally by ORD-003
}
```

No `lifecycle_status`, no `updated_ts`, no additional keys. The acceptance criterion requires a golden-record pytest that asserts this shape exactly.

### 5.2 Flag-on, auto-approve off

`order_record` written to DynamoDB gains `lifecycle_status="created"` and `updated_ts=<int>`. The HIST row `HIST#{ts:020d}#{event_id}` is written. The returned dict from `create_order` is unchanged (no `lifecycle_status` key). The `orders` table after the `put_item` has:
- One ORDER-SK header with `lifecycle_status="created"`.
- One HIST row with `to_status="created"`, `from_status=""`, `actor=user_id`, `reason="order_created"`.

### 5.3 Flag-on, auto-approve on

After the above two writes, `transition_order(order_id, "approved", actor="system", ...)` fires. It:
1. Reads the ORDER header (now `lifecycle_status="created"`).
2. Validates `"created" → "approved"` as a legal edge in `TRANSITIONS`.
3. Performs a conditional `update_item` guarded on `lifecycle_status = "created"`.
4. Sets `lifecycle_status="approved"`, `status="approved"`, `updated_ts=<new_ts>`, `updated_at=<new_str>`.
5. Calls `_append_history_row(order_id, from_status="created", to_status="approved", actor="system", reason="auto_approved_on_payment", ...)`.

After these five steps the order has two HIST rows and `lifecycle_status="approved"` on the header. The `create_order` return dict still shows `"status": "pending_payment"` (the legacy field is mirrored in the header, but the return value was assembled before the transition fired).

### 5.4 HIST write failure is non-fatal

The HIST `put_item` is wrapped in `try/except Exception: pass`. If it fails (e.g. DynamoDB Local is unavailable), `create_order` continues normally and returns the order dict. The state of the order header in DynamoDB is correct (`lifecycle_status="created"`) even if the HIST row is missing. This matches the platform's established audit convention (CLAUDE.md "best-effort transactional ordering: header CAS first, then history append; history append failure is logged but does not roll back the state change").

### 5.5 Auto-approve failure is non-fatal

The `transition_order` call for auto-approve is wrapped in `try/except Exception: pass`. If it fails (e.g. `OrderConflictError` from a concurrent write, or a transient DDB error), `create_order` returns successfully with the order in `lifecycle_status="created"`. The auto-approve is not retried. A background admin can manually advance the order to `approved` via the ORD-011 transition endpoint.

This best-effort semantics is acceptable here because `transition_order` is called immediately after `put_item` within the same synchronous execution context, and there is no concurrent writer yet (the order was just created). In the rare case of a transient DDB error, the order will be stuck at `created` until manual intervention.

### 5.6 Idempotency of `create_order` replay

If `create_order` is called twice with the same `correlation_id` (i.e. the caller retries after a timeout), both calls derive the same `order_id = sha256(correlation_id)[:32]`. The second call's `put_item` at line 85 overwrites the first call's item (DynamoDB `put_item` without a `ConditionExpression` is unconditionally overwriting). The HIST `put_item` uses `_append_history_row`, which adds `ConditionExpression="attribute_not_exists(sk)"` per ORD-006 — the second write silently fails. The auto-approve `transition_order` call on the second replay:
- Reads the header, sees `lifecycle_status="created"` (first call wrote it, second `put_item` overwrote but also includes `lifecycle_status="created"`).
- Calls `transition_order` with `idempotency_key=f"auto_approve:{order_id}"`.
- `_derive_event_id` produces the same `event_id` as the first call.
- ORD-006's HIST idempotency check: the HIST row with that `event_id` already exists → the `attribute_not_exists(sk)` guard on the HIST write returns a `ConditionalCheckFailedException`, which `_append_history_row` catches and swallows silently.
- `transition_order` checks `current == target` (both `approved`) → detects replay → returns the existing state without writing.

The net result of a replay is that the order ends up in the same state as the original call, with no duplicate HIST rows.

### 5.7 Interaction with `shoppingcart.purchase_cart` idempotency

`shoppingcart.purchase_cart` at line 483 short-circuits on `cart.get("status") == "PURCHASED"` and returns the cached `last_order_id` without calling `create_order` again. This means ORD-007's flag-on path fires at most once per cart. The DynamoDB-level `ConditionExpression="#status = :open"` at line 626 is a separate idempotency guard on the cart record. Both guards are unaffected by ORD-007.

### 5.8 Subscription cycle order path

`create_order_from_line_items` is also called from subscription cycle processing (`source_system="subscription_cycle"`). The lifecycle integration applies there too: a subscription renewal order will receive `lifecycle_status="created"` and, if auto-approve is on, advance to `"approved"` immediately. This is intentional: subscription orders are typically pre-authorized and can be considered approved on creation.

### 5.9 `lifecycle_status` in the GSI before auto-approve

With auto-approve on, the ORDER header transitions through two states (`created` → `approved`) within a single synchronous call. The GSI `GSI_ORDER_STATUS` receives two writes: first `lifecycle_status="created"` (from the initial `put_item`), then `lifecycle_status="approved"` (from `transition_order`'s `update_item`). Any concurrent GSI query between these two writes may observe the order as `created`. This window is bounded by the duration of two sequential DynamoDB operations (~a few milliseconds) and is considered acceptable.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

ORD-007 adds no `if S.dev_mode` branch. The lifecycle stamping, HIST write, and auto-approve call are identical in dev (DynamoDB Local port 8001, moto in tests) and prod (real DynamoDB). The `T.orders` handle at `app/core/tables.py:381` is wired identically in both environments. [verified: `tables.py:381`] The `_append_history_row` helper (from ORD-006) uses `T.orders` directly, so it also uses the same handle. This matches the parity requirement stated throughout CLAUDE.md.

### 7.2 Idempotency

Three layers of idempotency protect against replays:

1. **`order_id` derivation** (`commerce_order_service.py:67`): same `correlation_id` always yields the same `order_id`. Unchanged by ORD-007.
2. **HIST row guard**: `_append_history_row` uses `ConditionExpression="attribute_not_exists(sk)"` (ORD-006). A replay with the same `event_id` produces the same `sk = HIST#{ts:020d}#{event_id}`. The second write is a silent no-op.
3. **Auto-approve idempotency**: `transition_order` with `idempotency_key=f"auto_approve:{order_id}"` produces a deterministic `event_id`; ORD-005's replay-detect path short-circuits when `lifecycle_status` is already `"approved"`.

### 7.3 Security

**No new attack surface**: ORD-007 adds no new API endpoints. The flag check happens inside the service layer, never at the HTTP layer. Malicious callers cannot selectively disable lifecycle stamping because the flag is a process-level setting, not a per-request parameter.

**`actor` for system-initiated transitions**: The auto-approve `transition_order` call uses `actor="system"`, a reserved string literal. This is written to the HIST row's `actor` field and to the `audit_event` kwargs. No user-supplied value is interpolated as `actor`. The pattern follows ORD-001's specification that `actor` for programmatic transitions is the string `"system"`.

**No money-path fork**: ORD-007 does not touch the billing ledger. The `new_ledger_entry` call at `purchase_history.py:294` is unchanged. [verified: `purchase_history.py:244,294` — `record_cart_purchase` defined at 244; `new_ledger_entry` called at 294] ORD-007 runs its lifecycle writes after the ledger entry (it runs inside `create_order`, which is called before `record_cart_purchase` at `shoppingcart.py:668`). [verified: `shoppingcart.py:581,668`] The ordering is: `create_order` (+ lifecycle stamps) → cart status update → entitlement processing → promo redemption → `record_cart_purchase` (billing ledger). ## 8. Backward Compatibility & Migration

### 8.1 Existing orders (pre-ORD-007)

Orders written before `ORDER_LIFECYCLE_ENABLED` is turned on have no `lifecycle_status` attribute. They are invisible to the GSI `GSI_ORDER_STATUS` (sparse index) and to `transition_order` (which raises `OrderNotFoundError` when `lifecycle_status` is absent). Existing shop/cart/billing flows that read `order["status"]` continue to see `"pending_payment"` unchanged.

### 8.2 Enabling the flag in production

The recommended deploy sequence:
1. Deploy ORD-003 (adds `sk="ORDER"` unconditionally; runs migration script to backfill `sk` on existing items).
2. Deploy ORD-005/ORD-006 (creates `order_lifecycle.py`; no writes to `T.orders` yet since flag is off).
3. Set `ORDER_LIFECYCLE_ENABLED=true` in `.env.local` (dev) or SSM/Secrets Manager (prod).
4. New orders from this point forward receive `lifecycle_status="created"`.

There is no required backfill of existing orders to enable the flag. Pre-flag orders remain accessible through the legacy `status` field and the existing `GSI_STATUS` index; they simply do not participate in the lifecycle state machine until an optional admin backfill (specified in ORD-005 §8.2).

### 8.3 Rollback

Setting `ORDER_LIFECYCLE_ENABLED=false` stops new orders from receiving `lifecycle_status`. Orders that already received it retain the attribute; the lifecycle service is no longer called for new orders, but the ORD-011 admin endpoints (which check `S.order_lifecycle_enabled`) will return 503 for any lifecycle-related calls. No data loss; no schema rollback required.

### 8.4 `file_bundle_checkout.py` not affected

`app/services/file_bundle_checkout.py:98` writes to `T.orders` directly. After ORD-003, it must include `"sk": "ORDER"`. ORD-007 does not add `lifecycle_status` to this path; orders created via `file_bundle_checkout` never enter the lifecycle state machine unless explicitly backfilled. This is documented as a known gap; the `file_bundle_checkout` integration is tracked separately.

## 10. Open Questions / Assumptions

1. **Assumption**: ORD-003 has merged and `order_record` already includes `"sk": "ORDER"` unconditionally before ORD-007 is implemented. If ORD-003 is not merged, ORD-007's `put_item` will write without `sk`, making the item unreachable by `get_item(Key={"order_id":..., "sk":"ORDER"})` (which `transition_order` uses). The ORD-007 spec assumes ORD-003 is a hard prerequisite.

2. **Assumption**: ORD-005 and ORD-006 have merged and `app/services/order_lifecycle.py` exports `_append_history_row`, `_derive_event_id`, and `transition_order` before ORD-007 is implemented. If ORD-007 must ship before ORD-006, the initial HIST write can be inlined directly in `create_order` without calling `_append_history_row`; the inline version is removed when ORD-006 merges.

3. **Assumption**: `S.order_lifecycle_enabled` and `S.order_lifecycle_auto_approve` are delivered by ORD-002. If ORD-002 has not merged, the `getattr(S, "order_lifecycle_enabled", False)` fallback pattern (used in `returns_rma.py:68`) can be used as a bridge: `bool(getattr(S, "order_lifecycle_enabled", False))`.

4. **Open question**: Should `create_order`'s return dict include `lifecycle_status` when the flag is on? The current spec deliberately excludes it (to preserve backward compatibility). If consumers need it, adding it is a non-breaking additive change — a new key in a dict does not break existing callers. Decision: do not add it in ORD-007; if downstream needs it, a follow-up ticket can add it.

5. **Open question**: The auto-approve transition fires synchronously inside `create_order`, extending its latency by one extra DDB round-trip (the `get_order_header` read inside `transition_order`) plus one `update_item`. Under high load this adds ~5–15ms. If this is unacceptable, the auto-approve could be deferred to a background task or a post-`create_order` hook in `shoppingcart.purchase_cart`. Deferred to performance review; the synchronous approach is simpler and consistent with the "best-effort fire-and-forget" exception handling already in place.

6. **Assumption**: `file_bundle_checkout.py` is explicitly out of scope for ORD-007. Its orders will not receive `lifecycle_status` and will not participate in the lifecycle state machine. This is acceptable because `file_bundle_checkout` is a legacy path that uses a non-standard `order_id` derivation.

7. **RESOLVED (CORRECTED)**: ~~The `from_status` field in the initial HIST row is an empty string `""` rather than `None`.~~ ORD-006 §4.1.3 explicitly omits `from_status` from the DDB item entirely when `None` is passed (conditional `if from_status is not None: item["from_status"] = from_status`). ORD-006 §5.2 confirms: "ORD-007 calls `_append_history_row`... passes `from_status=None`. The helper omits the `from_status` attribute from the DDB item entirely." The initial HIST row has no `from_status` attribute; `list_status_history` returns `None` for it via `.get("from_status")`. The ORD-007 Change 2 code already correctly passes `from_status=None`; only the §3.2 data-model table entry and §9.1 test assertions were wrong (corrected in §3.2 and §9.1 in pass 3). [corrected: see §13]

8. **Open question**: Should `create_order` emit a separate `audit_event("order_lifecycle_initialised", ...)` distinct from the existing `"commerce_order_created"` audit event already at line 106? The current spec says no — the existing audit event at line 106 is sufficient; the HIST row itself is the audit record for the `created` lifecycle event. A separate audit event would be redundant. However, if the audit export pipeline (ENTERPRISE-004) requires a distinct event type to filter lifecycle-initialised orders, an additive `audit_event` call inside the `if S.order_lifecycle_enabled:` block can be added without changing the flag-off behavior.
