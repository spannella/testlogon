# MFG-002 — Manufacturing tables, settings & feature flag

## 1. Summary & Goal

MFG-002 is a pure scaffolding ticket: it creates the four DynamoDB tables needed
by the manufacturing/MRP subsystem, exposes them via `app/core/tables.T` handle
fields, and adds a master feature flag plus supporting settings keys to
`app/core/settings.S`. No business logic is implemented; the deliverable is
infrastructure that downstream tickets (MFG-003 through MFG-010) can import
without circular dependencies or table-creation races.

The master flag `manufacturing_mrp_enabled` defaults OFF. With it off, the
existing inventory (`T.inventory`, `T.reservations`), cart, orders, and billing
code paths are byte-for-byte unchanged; the four new tables are provisioned but
never accessed.

## 3. Data Model

All four tables use DynamoDB single-table design with a sort key so that
header rows (`SK=META`) and child rows (`SK=COMP#…`, `SK=ISSUE#…`, etc.) live in
the same partition. Every GSI sort key that holds a Unix timestamp (integer) is
numeric and listed in `attr_types`.

### 3.1 `mfg_boms`

Stores BOM headers and component lines for finished-goods SKUs.

| Attribute | Type | Description |
|---|---|---|
| `bom_id` (PK) | S | UUID, generated at creation |
| `sk` (SK) | S | `META` (header row) or `COMP#{seq:04d}` (component row) |
| `product_sku` | S | Finished-goods SKU this BOM produces (header only) |
| `name` | S | Human-readable BOM name |
| `output_quantity` | N | Units of `product_sku` produced per build cycle |
| `status` | S | `active` \| `inactive` \| `archived` |
| `created_at` | N | Unix seconds |
| `updated_at` | N | Unix seconds |
| `component_sku` | S | (Component rows only) SKU of component |
| `quantity_per` | N | (Component rows only) Units needed per output unit |
| `scrap_pct` | N | (Component rows only) Decimal 0.0–1.0 waste factor |
| `seq` | N | (Component rows only) Sort order integer |

**GSIs:**

```
GSI_PRODUCT  PK: product_sku (S)  SK: created_at (N)
```

Purpose: resolve the active BOM(s) for a finished-goods SKU — called by
`manufacturing_bom.get_active_bom(product_sku)` (MFG-004).

`attr_types`: `{"created_at": "N"}`

**TableDef:**
```python

    "sk",
    gsi=[
        {"index_name": "GSI_PRODUCT", "partition_key": "product_sku", "sort_key": "created_at"},

```

## 5. Detailed Behavior & Edge Cases

### 5.1 Table-name collision avoidance

Each default table name (`mfg_boms`, `mfg_work_centers`, `mfg_work_orders`,
`mfg_mrp`) is distinct from every existing table in the codebase — confirmed
by `grep` over `app/core/settings.py`. The `_resolve_table_name(S.<field>,
"<default>")` pattern allows per-environment overrides via env vars while
defaulting safely.

### 5.2 `_FloatSafeTable` and `scrap_pct`

BOM component rows carry `scrap_pct` (a percentage like `0.05` for 5% waste).
DynamoDB's boto3 serializer rejects Python `float` values. `_safe_table` wraps
all `put_item` and `update_item` calls with `_to_decimal()` (`tables.py:11-26`),
so callers can pass a Python float for `scrap_pct` without explicit conversion.
This is consistent with how other services (e.g., `app/services/recommendations.py`
which stores `float` affinity scores via `_decay()` at line 71 and
`compute_affinity_scores()` at line 171) use `T.*` handles.

### 5.3 `just restart` idempotency

`scripts/local-ddb-init.py` calls `create_table` inside a `try/except
ClientError` guard that skips `ResourceInUseException` (table already exists).
The four new tables will be created fresh on a clean restart and skipped if
already present — no manual cleanup needed. Locally this means `just restart`
(which calls `local-stack-down.sh` + `local-stack-up.sh` + the init script)
cleanly provisions all four tables.

### 5.4 Cold-start import order

`app/core/tables.py` imports `app/core/settings.py` at module level (`from
.settings import S`). Adding new fields to `S` before wiring them into `T` is
the only safe order; the reverse would cause `AttributeError` at import time.
Settings must be merged first (Section 4.1), tables second (Section 4.2), then
`local-ddb-init.py` (Section 4.3) — all in a single commit so the unit-test
import smoke test passes.

### 5.5 No-op when flag is off

Downstream services (MFG-003+) will implement:

```python
def _flag_on() -> bool:
    return bool(getattr(S, "manufacturing_mrp_enabled", False))

def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="Manufacturing/MRP not enabled")
```

MFG-002 itself does not call `_require_enabled()` — it only provisions the
infrastructure. The flag only becomes behaviorally meaningful when a downstream
service calls `_require_enabled()` at the top of its public functions.

### 5.6 GSI_PRODUCT shared by two tables

Both `mfg_boms` and `mfg_work_orders` define a GSI named `GSI_PRODUCT` with
`product_sku` as the partition key. These are on separate DynamoDB tables, so
the same index name is fine. The consumer (MFG-004 BOM service and MFG-007 work
order service) queries the table-specific handle (`T.mfg_boms` vs
`T.mfg_work_orders`) so there is no ambiguity.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity (SECOPS-007):** There is no `dev_mode` branch in table
creation or settings parsing. The `_resolve_table_name` pattern and the
`os.environ.get(...)` defaults produce identical behavior in both environments.
In prod, operators set `MFG_BOMS_TABLE_NAME` etc. to the real DynamoDB table
names (which may include an environment prefix, e.g. `prod-mfg-boms`); in dev
the defaults are used. No code distinguishes environments.

**Idempotency:** Table creation is already idempotent in `local-ddb-init.py`
via `ResourceInUseException` catch. Settings parsing is stateless. Table handles
in `T` are initialized once at module import time and are immutable (`frozen=True`
dataclass).

**Security:** No new authentication surfaces are introduced. The four table
handles are only accessible to server-side Python code (behind
`require_ui_session` or `require_admin_or_root_csrf` in downstream routers).
Table names are server-side configuration only; they are never exposed in API
responses or client-visible error messages.

**`_FloatSafeTable` write safety:** All four new handles are wrapped in
`_FloatSafeTable` (via `_safe_table`), consistent with every other handle in
`tables.py`. This prevents `boto3` `ParamValidationError` from float-typed
`scrap_pct` or cost fields without any caller-side boilerplate.

## 8. Backward Compatibility & Migration

**Additive only:** No existing table, setting, router, or model is modified. The
four new settings fields and four new `T` fields are additions to frozen
dataclasses; because both `Settings` and `Tables` use `frozen=True` dataclasses
that are initialized once at module import, any field added to the class
definition and its corresponding `T = Tables(...)` initializer call is
immediately available throughout the process lifetime.

**No DynamoDB schema migration in prod:** Operators provision the four new tables
before deploying the code that uses them. Because the tables are only accessed
when `manufacturing_mrp_enabled=true` and downstream services call
`_require_enabled()`, the order of operations is: (1) deploy the code with the
flag off, (2) create the four tables in prod DDB, (3) enable the flag. Step 2
can be done with the same `local-ddb-init.py` script (adapted for prod
endpoints) or via Terraform/CDK.

**Existing test suite:** No existing pytest or Playwright test references the new
settings fields or table handles. Adding fields to a frozen dataclass does not
change the behavior of any existing field. The import-time initialization of `T`
will fail immediately (at server startup) if any new `_safe_table(S.<name>)`
call targets an invalid settings attribute — catching config mistakes at boot
rather than at first request.

## 10. Open Questions / Assumptions

1. **Assumption: settings insertion point.** The spec places the manufacturing
   block at `settings.py:847`, immediately after the `returns_table_name` field.
   If other OFBiz tickets (OFB-011 through OFB-015 from `OFBIZ_COMMERCE_TICKETS.md`)
   have already added settings between returns and the file manager block, the
   insertion point shifts down. The implementing engineer should re-check the line
   numbers at implementation time and insert after the last OFBiz-phase block.

2. **Assumption: `Tables` dataclass field order does not matter.** Python
   dataclass field order only affects `__init__` argument order, and `T` is
   always constructed with keyword arguments. Adding the four new fields anywhere
   in the `Tables` class body after `returns` is safe. The spec places them
   immediately after `returns` for spatial locality.

3. **Assumption: no dedicated `mfg_routing` table at this milestone.** The ticket
   description lists four tables. MFG-005 (work-center routing) will store routing
   tasks as rows within the `mfg_work_orders` or `mfg_boms` partitions (or a
   separate sub-table). If MFG-005 requires its own `mfg_routing` table this will
   need a follow-up MFG-002 addendum; deferred to MFG-005 design.

4. **Assumption: `mfg_mrp_default_horizon_days` is read at service call time, not
   at settings load time.** The value is a simple integer read from `S` each time
   the MRP service is called, consistent with how `S.inventory_reservation_ttl_seconds`
   is read in `inventory.py:81`. No caching or pre-computation.

5. **Assumption: GSI `GSI_PRODUCT` naming conflict is acceptable.** The same
   index name appears on `mfg_boms` and `mfg_work_orders`. DynamoDB allows
   duplicate index names across tables. Callers must use the right table handle;
   this is enforced naturally since each service file imports only `T.mfg_boms`
   or `T.mfg_work_orders`.

6. **Question: should `mfg_work_orders.sk` carry the `EVENT#{ts}#{id}` sub-rows
   or should events live in a separate `mfg_work_order_events` table?** The spec
   chooses co-location (single-table, following the `TIMELINE#` pattern in
   `instance_monitoring.py` and `EVENT#` pattern in audit exports). If write
   throughput on a single partition becomes a concern (unlikely at MVP scale),
   a separate events table can be split out without changing the header schema.

7. **Assumption: `mfg_mrp` REQ rows use `REQ#{sku}#{seq:06d}` as SK.** The `#`
   in a DynamoDB sort key is valid and is used throughout the codebase (e.g.,
   `billing_shared.ledger_sk` returns `LEDGER#{ts}#{entry_id}`). The `{seq:06d}`
   zero-padding ensures lexicographic order matches insertion order for a fixed-
   width integer sequence. Confirm the maximum number of SKUs in a single MRP run
   does not exceed 999,999 before finalizing the format.
