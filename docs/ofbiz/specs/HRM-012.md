# HRM-012 — HR admin page, route & nav entry

**Type:** Feature | **Priority:** P1 | **Estimate:** 3 days

---

## 1. Summary & Goal

HRM-012 delivers the browser-facing HR management surface: a single lazy-loaded React page at `/hr` containing three tabs — Positions, Employees/Employment, and Payroll — wired to the endpoint wrappers from HRM-011 and backed by the router from HRM-009. The nav entry in `Sidebar.tsx` and the route in `App.tsx` are both flag-gated so they are completely invisible when `hr_enabled` is off or the user lacks admin/root role. This ticket is purely frontend; it touches no backend service or DDB schema.

**Goal:** An admin or root user can, from a single `/hr` page, manage positions, hire and terminate employees, and create/approve/post payroll runs — all through the existing HRM-009 `/ui/hr/*` API, with React Query cache invalidation after every mutation.

## 3. Data Model

HRM-012 introduces no new DynamoDB tables or schema changes. It is entirely a frontend concern. All persistence is handled by the existing `hr` single-table defined in HRM-002 and the `billing` table (via payroll posting in HRM-008). The relevant existing DDB row shapes consumed read-only by this page are:

| Row | PK | SK | Key attributes |
|-----|----|----|----------------|
| Position | `POSITION#{position_id}` | `META` | `title`, `department`, `status` ∈ {`OPEN`,`FILLED`,`CLOSED`}, `created_at` (N) |
| Employment | `EMPLOYMENT#{employment_id}` | `META` | `party_id`, `position_id`, `status` ∈ {`ACTIVE`,`TERMINATED`,`ON_LEAVE`}, `pay_rate_cents`, `pay_period`, `start_date` (N), `end_date` (N, optional) |
| PayrollRun | `PAYROLL#{payroll_run_id}` | `META` | `period_start`, `period_end`, `status` ∈ {`DRAFT`,`APPROVED`,`POSTED`}, `created_at` (N) |
| PayrollLine | `PAYROLL#{payroll_run_id}` | `LINE#{employment_id}` | `gross_cents`, `currency`, `employment_id` |

These schemas are owned by HRM-002 / HRM-003 / HRM-007. HRM-012 never writes to DDB directly.

## 4. API / Service Design

HRM-012 consumes the existing HRM-009 router and HRM-011 endpoint wrappers. No new backend endpoints are introduced.

### 4.1 Endpoint wrappers (consumed, defined by HRM-011)

All live in `frontend/src/api/endpoints/hr.ts`. Relevant signatures for this ticket:

```typescript
// Positions
listPositions(params?: { status?: string; cursor?: string }): Promise<{ positions: PositionOut[]; next_cursor?: string }>
createPosition(req: CreatePositionIn): Promise<PositionOut>
updatePositionStatus(positionId: string, status: "OPEN" | "FILLED" | "CLOSED"): Promise<PositionOut>

// Employment
listEmployments(params?: { status?: string; party_id?: string; cursor?: string }): Promise<{ employments: EmploymentOut[]; next_cursor?: string }>
createEmployment(req: CreateEmploymentIn): Promise<EmploymentOut>
terminateEmployment(employmentId: string, req: TerminateEmploymentIn): Promise<EmploymentOut>

// Payroll
listPayrollRuns(params?: { status?: string; cursor?: string }): Promise<{ runs: PayrollRunOut[]; next_cursor?: string }>
createPayrollRun(req: CreatePayrollRunIn): Promise<PayrollRunOut>
getPayrollRun(payrollRunId: string): Promise<PayrollRunOut & { lines: PayrollLineOut[] }>
approvePayrollRun(payrollRunId: string): Promise<PayrollRunOut>
postPayrollRun(payrollRunId: string): Promise<PayrollRunOut>
```

All non-GET calls attach `x-csrf-token` automatically via the axios instance in `api/client.ts`.

### 4.2 React Query key convention

All queries under this page use a `["hr", ...]` namespace to isolate from other modules and simplify targeted invalidation:

| Query key | Fetcher |
|-----------|---------|
| `["hr", "positions"]` | `listPositions()` |
| `["hr", "employments"]` | `listEmployments()` |
| `["hr", "payroll-runs"]` | `listPayrollRuns()` |
| `["hr", "payroll-run", runId]` | `getPayrollRun(runId)` |

After any mutation, `queryClient.invalidateQueries({ queryKey: ["hr"] })` invalidates the full HR namespace, ensuring lists refresh.

### 4.3 No new API routes

HRM-012 adds zero backend routes. The backend surface is fully specified by HRM-009.

## 5. Detailed Behavior & Edge Cases

### 5.1 Page guard

On mount, `HrPage.tsx` calls `canAccessGeneralAdminControls(accessToken)` and `isHrEnabled()`. If either is false, the component renders a `<Navigate to="/" replace />` — the user is redirected silently rather than seeing an empty/broken page. This mirrors the pattern used for role-gated nav items: the route is registered but the page redirects rather than rendering content for unauthorized callers.

**Assumption A:** There is no server-side capability endpoint that pushes `hr_enabled` dynamically to the client. The flag is read from the `VITE_HR_ENABLED` build-time env, identical to `VITE_INVENTORY_RESERVATIONS_ENABLED` (see `featureFlags.ts:161`). Real-time dynamic capability surfacing (e.g. via a `/ui/settings/features` endpoint) is not in scope for this ticket; see Section 10.

### 5.2 Positions tab

- **List**: `useQuery(["hr", "positions"], () => listPositions())` renders a shadcn/ui `Table` with columns: Title, Department, Status badge, Created date, Actions.
- **Status badge colours**: `OPEN` → `bg-green-500`, `FILLED` → `bg-blue-500`, `CLOSED` → `bg-gray-500`.
- **Create position**: A `Dialog` with a `Form` (React Hook Form + Zod) for `title: string` (required, min 1 char) and `department: string` (required). On submit, `useMutation` calls `createPosition(req)`. On success: `toast.success("Position created")`, `queryClient.invalidateQueries(["hr"])`, dialog closes.
- **Update status**: A `Select` dropdown per row (or a dedicated action button) calls `updatePositionStatus(id, newStatus)` with the same invalidation / toast pattern. Illegal transitions (e.g. `FILLED → OPEN`) return 409 from the backend; the page surfaces this as `toast.error(err.detail ?? "Invalid status transition")`.
- **Cursor pagination**: `next_cursor` from the response enables a "Load more" button. The query is keyed `["hr", "positions", cursor]` so each page is cached independently.

### 5.3 Employees / Employment tab

- **List employments**: `useQuery(["hr", "employments"], () => listEmployments())` renders a Table with columns: Employment ID, Party ID (employee identifier), Position (resolved via a secondary lookup or denormalized in response), Status, Pay Rate, Pay Period, Start Date, End Date, Actions.
- **Hire**: Opens a Dialog with fields: `party_id` (required text field representing the employee PERSON party — obtained from the Party module, HRM-004), `position_id` (Select sourced from `listPositions({status: "OPEN"})`), `pay_rate_cents` (integer, validated ≥ 0 via Zod), `pay_period` (Select: MONTHLY / BIWEEKLY / WEEKLY / HOURLY), `start_date` (date picker → Unix epoch). On success: `toast.success("Employee hired")`, cache invalidated.
- **Terminate**: Per-row action button opens a confirmation Dialog with `end_date` (date picker) and optional `reason` text. Calls `terminateEmployment(id, req)`. Idempotent — if already terminated, the backend returns 409; the page shows `toast.warning("Employment already terminated")`.
- **Status filter**: A `Select` at the top of the tab allows filtering by `ACTIVE` / `TERMINATED` / `ON_LEAVE`; the query re-runs with the new param.

### 5.4 Payroll tab

The payroll tab has three sub-sections rendered as a nested state machine (not nested tabs — use a controlled `selectedRun` state to show the run detail panel alongside the list):

**Run list panel:**
- `useQuery(["hr", "payroll-runs"], () => listPayrollRuns())` renders runs with columns: Run ID, Period, Status badge, Created date, Actions.
- Status badge: `DRAFT` → `secondary`, `APPROVED` → outline, `POSTED` → default.
- "New Run" button opens a Dialog with `period_start` / `period_end` (date pickers) and optional `correlation_id` (hidden, auto-set to `sha256(period_start + period_end + timestamp)` client-side to support idempotent re-submit on network error). The `correlation_id` is NOT exposed in the UI — it is set programmatically.
- Clicking a run row sets `selectedRun` and opens the detail panel.

**Run detail panel** (shown when `selectedRun` is set):
- `useQuery(["hr", "payroll-run", selectedRun], () => getPayrollRun(selectedRun))` fetches lines.
- Displays run metadata + a Table of lines (Employment ID, Gross Cents formatted as currency, Status).
- "Approve" button (shown when status = `DRAFT`) calls `approvePayrollRun(runId)`. Disabled while mutation is pending.
- "Post" button (shown when status = `APPROVED`) calls `postPayrollRun(runId)`. Shows a confirmation Dialog before proceeding ("Post payroll? This writes ledger entries and cannot be undone."). The backend enforces idempotency via deterministic correlation IDs (HRM-008); re-posting is safe.
- "Back" link returns `selectedRun` to null.

**Edge cases:**
- Posting when `hr_payroll_enabled` is off: backend returns 404; page shows `toast.error("Payroll feature is not enabled")`.
- Approving a non-DRAFT run: backend returns 409; page shows `toast.error("Run is not in DRAFT status")`.
- Network error on post: the mutation error handler shows `toast.error("Payroll post failed — retry is safe due to idempotent IDs")`.

### 5.5 Loading and error states

Every `useQuery` call renders a `Loader2` spinner (from lucide-react) while loading and a `<Card>` with error text if `isError` is true (consistent with `JobDashboardPage.tsx`). Empty lists render a muted helper text ("No positions yet — create one to get started.").

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity:** The page calls exactly the same `/ui/hr/*` endpoints in both environments; there is no `dev_mode` branch in the frontend component. CSRF is handled uniformly by the axios instance in `client.ts` (reads the `ui_csrf` cookie and attaches `x-csrf-token`). The component is indifferent to whether the backend is running against DynamoDB Local or AWS DynamoDB.

**Role enforcement at two layers:**
1. *Frontend*: `canAccessGeneralAdminControls(accessToken)` decoded from the `ui_access_token` JWT cookie prevents non-admins from seeing the route and nav item. Per `adminCapabilities.ts:47–52`, this is `true` only for `role="root"` or `role="admin"` with `admin_profile.type="general"`.
2. *Backend*: `require_admin_or_root` (`app/auth/policy.py:67`) returns 403 for any non-admin/root caller regardless of frontend state, so bypassing the UI guard provides no escalation path.

**Idempotency on the frontend side:** The Create Position and Hire Employment dialogs disable their submit button after the first click (`mutation.isPending === true`) to prevent double-submit. The Create Payroll Run dialog generates a deterministic `correlation_id` from the period dates client-side so that a network-error retry re-submits the same ID and the backend returns the existing run (HRM-008 conditional-put semantics).

**Sensitive data:** Pay rate and gross cents are rendered in the UI only for authenticated admin/root sessions. No data is cached to `localStorage`. On logout, `useAuthStore.logout()` (`authStore.ts:43–63`) calls `clearAllCacheForUser(prevUserId)` from `frontend/src/lib/offlineCache.ts:197` (fire-and-forget, clears IndexedDB offline cache). React Query's in-memory cache is **not** cleared by a dedicated `queryClient.clear()` call; the in-memory cache expires naturally when the session guard redirects unauthenticated requests. <!-- CORRECTED: spec incorrectly claimed queryClient.clear() in client.ts 401 handler; actual is clearAllCacheForUser via offlineCache.ts per authStore.ts:54–61 -->

## 8. Backward Compatibility & Migration

HRM-012 is purely additive. With `VITE_HR_ENABLED=false` (default):

- No import of `HrPage` is executed (lazy import, not evaluated until the route is visited).
- The nav item filter at `Sidebar.tsx:307–329` returns `false` for the `/hr` path and the item is omitted from the rendered list. <!-- VERIFIED: Sidebar.tsx:307–329 -->
- The React Router `<Route path="hr">` is registered in the component tree but React Router only renders a route when its path matches — visiting `/hr` with the flag off hits the page guard that immediately redirects to `/`, so the route is effectively unreachable.
- `frontend/src/lib/featureFlags.ts`, `App.tsx`, and `Sidebar.tsx` are the only existing files modified; all three changes are additive (new constant + new Route + new predicate row), no existing lines are removed.
- All existing admin routes and nav items are unchanged.

**Migration:** No DynamoDB table migrations are needed. No backend code changes are needed (all backend work is in HRM-001 through HRM-010). The only deploy action is setting `VITE_HR_ENABLED=true` (frontend env rebuild) and `HR_ENABLED=1` (backend env restart) when the module is ready to activate.

## 10. Open Questions / Assumptions

**Assumption A (flag delivery):** The `isHrEnabled()` check reads from a build-time `VITE_HR_ENABLED` env variable, not from a server-side capabilities endpoint. This means the frontend flag and the backend flag (`HR_ENABLED`) must be toggled together. If the project later introduces a `/ui/settings/features` endpoint that returns `{"hr_enabled": true}`, HRM-012's approach will need to be revisited. For now, the VITE flag pattern is consistent with every other feature flag in `featureFlags.ts`.

**Assumption B (party_id UX):** The "Hire" dialog asks for `party_id` as a raw text field. In practice, this requires the admin to know the employee's PERSON party ID (from the Party module, HRM-004). A future ticket should add a party lookup/autocomplete. For now, the raw text field is acceptable for an admin-only surface.

**Assumption C (payroll period dates):** `period_start` and `period_end` are sent as ISO-8601 date strings; the backend HRM-007 converts them to epoch integers. If HRM-007 instead expects epoch integers directly, the `CreatePayrollRunIn` TS type from HRM-011 will specify `number`, and the date pickers must emit epoch values. This spec assumes the backend accepts ISO strings and HRM-011 types reflect this.

**Assumption D (payroll lines in GET response):** `getPayrollRun(runId)` returns both the run metadata and the `lines` array in a single response (i.e., `PayrollRunOut` includes a `lines: PayrollLineOut[]` field). If lines are returned via a separate `GET /payroll/{runId}/lines` endpoint, the detail panel needs a second `useQuery`. Clarify with HRM-009 implementer.

**Assumption E (correlation_id client-generation):** The client generates `correlation_id` for payroll run creation as a deterministic hash of period dates + a session timestamp. The backend only uses it for conditional-put idempotency. This is safe because the backend never surfaces `correlation_id` back to the client; it is only used as a conditional put key. If HRM-008 requires `correlation_id` to be a UUID (not a hash), the client should use `crypto.randomUUID()` and store it in `useRef` so a retry reuses the same value.

**Open Question 1:** Should the nav entry go in the existing "Account" group (where other admin links live, `Sidebar.tsx:190–248`) or in a new "HR" group? The Account group already holds 54 items (`Sidebar.tsx:192–247`), so a dedicated "HR" group improves scannability. This spec assumes a new group is added; if the team prefers consolidating into Account, the implementation is a single-line change. <!-- CORRECTED: count was ~30, actual is 54 per Sidebar.tsx:192–247 -->

**Open Question 2:** Should the `/hr` path be `admin/hr` (matching other admin routes like `admin/moderation`) or the bare `hr`? The ticket says "route it in `App.tsx` as `/hr`", so this spec uses `hr`. This is the authoritative guidance from the ticket; no change needed unless the team decides to namespace admin routes more consistently.
