# FXA-015 — Fixed-assets admin page (register + depreciation + work orders)

## 1. Summary & Goal

FXA-015 delivers the fixed-assets admin page at
`frontend/src/pages/shop/admin/FixedAssetsAdmin.tsx`. It is the primary UI surface for
the entire Fixed Assets module and composes three functional panels:

1. **Asset register table** — a paginated `<Table>` listing all fixed assets (name, class,
   cost, accumulated depreciation, net book value, status) with a create/edit `<Dialog>` and
   a dispose action.
2. **Depreciation schedule drawer** — a `<Sheet side="right">` that opens when an admin
   clicks a row; it calls `GET /{asset_id}/schedule` and renders the period timeline with
   `journal_entry_id` drill-through links for posted periods.
3. **Maintenance work-order tab** — a `<Tabs>` panel that splits the page into "Assets" and
   "Work Orders"; the Work Orders tab shows the open/in-progress queue plus a
   create/transition `<Dialog>`.

All actions are admin/root-gated: the page renders an `<EmptyState>` access-denied view for
non-admin callers, matching the identical guard in
`frontend/src/pages/shop/admin/InventoryAdmin.tsx:158–168`. The page is flag-gated on
`isFixedAssetsEnabled()` (introduced by FXA-014), rendering a "module not enabled" empty
state when the flag is off — matching the `isInventoryReservationsEnabled()` guard at
`InventoryAdmin.tsx:146–156`.

After this ticket, an admin can register a fixed asset, view its generated depreciation
schedule with per-period journal entry IDs, observe net book value update after a period
posts, and create/complete maintenance work orders — all without a page reload.

## 3. Data Model

FXA-015 introduces no new DynamoDB tables, GSIs, or settings. All persistent state is owned
by FXA-003's three tables (`fixed_assets`, `fixed_asset_schedule`, `maintenance_orders`).
This section documents the client-side data shape as rendered from the API responses.

### 3.1 Asset register display fields

| Display column | Source field | Formatting |
|---|---|---|
| Name | `FixedAsset.name` | Plain string |
| Class | `FixedAsset.asset_class` | Plain string |
| Cost | `FixedAsset.acquisition_cost_cents` | `formatCents(v)` → `$1,234.56` |
| Accum. Depr. | `FixedAsset.accumulated_depreciation_cents` | `formatCents(v)` |
| Net Book Value | `FixedAsset.net_book_value_cents` | `formatCents(v)` |
| Status | `FixedAsset.status` | `<Badge>` (see §4.2) |
| Actions | — | Schedule drawer trigger, Edit, Dispose |

`net_book_value_cents` is always present in the API response — computed server-side by the
`model_validator(mode="after")` on `FixedAssetOut` as
`max(salvage_value_cents, acquisition_cost_cents - accumulated_depreciation_cents)` (per
`docs/ofbiz/specs/FXA-004.md:81`). The UI never recomputes it.

### 3.2 Depreciation schedule display fields

| Amount | `DepreciationPeriod.amount_cents` | `formatCents(v)` |

### 3.3 Work-order display fields

### 4.4 Create/Edit asset dialog

Controlled by `createOpen` (new) or `editAsset !== null` (edit). Reuses the same `<Dialog>`.

Fields in the form (all `useState`, NOT react-hook-form — consistent with `AdminCatalog.tsx`
which uses local state for its create-category dialog at `AdminCatalog.tsx:56–60`):
- `name: string` — required, `maxLength=200`
- `asset_class: string` — required, `maxLength=50` <!-- CORRECTED: FXA-004.md:137 `Field(min_length=1, max_length=50)` -->
- `acquisition_cost_cents: string` — numeric input (dollar amount, converted to cents)
- `salvage_value_cents: string` — numeric input (dollar amount, converted to cents)
- `useful_life_months: string` — numeric input (months, 1–1200)
- `acquired_at: string` — `<Input type="date">`, converted to Unix timestamp
- `depreciation_method` — fixed to `"straight_line"` in this milestone (no select needed)
- Four optional GL account ID fields (`gl_asset_account_id`, `gl_accum_depr_account_id`,
  `gl_depr_expense_account_id`, `gl_gain_loss_account_id`) — text inputs, collapsible under
  an "Advanced GL mapping" disclosure section

Edit mode pre-fills from `editAsset` and calls `updateMut` (only mutable fields: `name`,
`asset_class`, four GL IDs). Cost/salvage/useful-life/acquired-at are read-only in edit mode
(greyed inputs) because changing them would invalidate the existing schedule.

Client-side validation before calling the mutation:
- `name` non-empty.
- `acquisition_cost_cents` > 0.
- `salvage_value_cents` < `acquisition_cost_cents` (matches `docs/ofbiz/specs/FXA-004.md:150–156`). <!-- CORRECTED: line 55 is about model_validator pattern generally; the actual salvage constraint is the @model_validator at lines 150–156 -->
- `useful_life_months` between 1 and 1200.
- `acquired_at` parseable as a valid date.

Error display: inline `<p className="text-sm text-destructive">` beneath each field (no
toast for validation errors).

### 4.5 Dispose asset confirm dialog

Uses `<ConfirmDialog>` for the confirmation step, then opens a secondary `<Dialog>` for
the disposal details (reason + optional proceeds). Splitting into two dialogs prevents
accidental trigger — the user must explicitly confirm "Yes, dispose" before seeing the
proceeds form.

Proceeds form fields (optional, co-occur per `docs/ofbiz/specs/FXA-004.md:257–270`):
- `disposal_reason: string` — text area.
- `proceeds_payment_intent_id: string` — text input (only when proceeds are being recorded).
- `proceeds_amount_cents: string` — dollar-amount input, converted to cents.
- Validation: if either proceeds field is non-empty, both must be filled.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off state

When `isFixedAssetsEnabled()` returns `false` (the default in dev):
```tsx
if (!isFixedAssetsEnabled()) {
  return (
    <div className="p-6">
      <EmptyState
        icon={<Building2 className="h-10 w-10" />}
        title="Fixed asset management is not enabled"
        description="Enable the VITE_FIXED_ASSETS_ENABLED feature flag to manage fixed assets."
      />
    </div>
  );
}
```
No API calls are made; no queries fire (`enabled: allowed` is irrelevant because the
component never reaches the hook declarations after the early return).

### 5.2 Access-denied state

Non-admin callers (`canAccessGeneralAdminControls(accessToken)` returns `false`) see an
`<AlertTriangle>` empty state and no data is fetched (`enabled: allowed` guards every
`useQuery`/`useMutation`).

### 5.3 Net book value live update

After the FXA-010 background poster ticks (or a manual post via future per-period post
endpoint), `accumulated_depreciation_cents` on the asset row increments. The
`["fixed-assets", "list"]` query has `staleTime: 30_000` — within 30 seconds of the
poster running, `refetchOnWindowFocus: true` (React Query default) triggers a fresh fetch
that propagates the new NBV. The depreciation schedule sheet query (`staleTime: 60_000`)
refreshes the `posted_at`/`journal_entry_id` fields within 60 seconds.

### 5.4 NBV floor at salvage value

The server-side `model_validator` enforces `net_book_value_cents >= salvage_value_cents` per
`docs/ofbiz/specs/FXA-004.md:81`. The UI never recomputes NBV; it always displays the value
returned in the API response. A `formatCents` helper (using `Intl.NumberFormat` as at
`AdminCatalog.tsx:44–49`) is used throughout.

### 5.5 Dispose button disabled guard

The "Dispose" action button is disabled (and the `<ConfirmDialog>` unreachable) when
`asset.status === "disposed"`. This prevents a second disposal which would return HTTP 409
from the server (`docs/ofbiz/specs/FXA-011.md:11` — re-disposing raises 409, not a no-op).
The button tooltip shows "Already disposed" when disabled.

### 5.6 Work order illegal-transition handling

If the admin submits a transition that the server rejects with HTTP 409
(`"illegal_transition"`), the `transitionMut.onError` handler shows a toast:
`"Transition not allowed (check lifecycle state)"`. The dialog stays open so the admin can
choose a different `target_status`. The mutation does not call `qc.invalidateQueries` on
error.

### 5.7 Disposed-asset work-order creation

If the admin selects a disposed asset and tries to create a work order, the server returns
HTTP 400 (`"asset_disposed"` per `docs/ofbiz/specs/FXA-012.md:10`). The `createWoMut.onError`
toast says `"Failed to create work order — is the asset active?"`. For better UX, the
asset selector should visually distinguish disposed assets (greyed or `(disposed)` suffix in
the option label) so admins avoid the error path.

### 5.8 Proceeds co-occurrence validation

In the dispose dialog, if one of `proceeds_payment_intent_id` / `proceeds_amount_cents` is
filled and the other is empty, the "Confirm Disposal" button is disabled and an inline error
reads: `"Both proceeds fields must be filled together."` This mirrors the server-side
`model_validator` at `docs/ofbiz/specs/FXA-004.md:257–270` and prevents a 422 from ever
reaching the user.

### 5.9 Journal entry drill-through (display-only)

`journal_entry_id` chips in the schedule drawer are display-only in this milestone. When a
caller sees a chip, they can copy the ID manually. A future FXA-018 (GL browser page) can
make these into links. No navigation-breaking dependency is introduced.

### 5.10 Pagination

`listAssets({ limit: 50 })` fetches the first page. If `assetsQuery.data?.cursor` is
non-null, a "Load more" button is rendered at the bottom of the table. Clicking it calls
`listAssets({ cursor: data.cursor, limit: 50 })` and merges results into local state. This
is simpler than `useInfiniteQuery` because the asset register is not expected to exceed a
few hundred rows in practice; full pagination via React Query infinite query is a follow-up.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

FXA-015 is a pure frontend component with no backend I/O. There is no dev/prod code-path
divergence in this ticket. Backend parity for the API layer is the responsibility of the
upstream tickets (FXA-007, FXA-009, FXA-011, FXA-012, FXA-013).

### 7.2 CSRF

The `api/client.ts` shared instance reads `document.cookie` for `ui_csrf` and attaches
`X-CSRF-Token` on every non-GET call. All mutations (`createMut`, `updateMut`, `disposeMut`,
`createWoMut`, `transitionMut`) call `api.post` or `api.patch` which are the CSRF-bearing
methods. No extra header handling is needed in the page component.

### 7.3 Admin gating

The page component itself enforces admin access via `canAccessGeneralAdminControls` (which
decodes the JWT's `role` and `admin_profile.type` claims at
`frontend/src/lib/adminCapabilities.ts:47–52`). <!-- VERIFIED: adminCapabilities.ts:47–52 --> This is a defence-in-depth guard — the
backend enforces its own auth via `require_admin_or_root_csrf` on every state-mutating
endpoint (`app/auth/policy.py:100–106`). <!-- VERIFIED: policy.py:100 --> A non-admin who bypasses the frontend guard will receive HTTP 403 from the
backend.

### 7.4 Money fields

All money inputs (`acquisition_cost_cents`, `salvage_value_cents`, `proceeds_amount_cents`,
`cost_cents`) are dollar-amount string inputs converted to integer cents via
`Math.round(parseFloat(v) * 100)` before being passed to the mutation. This avoids
floating-point rounding by converting once at the boundary, consistent with the pattern used
in `AdminCatalog.tsx:44–49` (`formatPrice` / `price_cents`). <!-- VERIFIED: AdminCatalog.tsx:44–49 defines formatPrice via Intl.NumberFormat; the FXA-015 helper will be named formatCents following the same Intl.NumberFormat pattern --> Negative or NaN values disable the submit
button (client-side guard matches `InventoryAdmin.tsx:283–288`). <!-- VERIFIED: InventoryAdmin.tsx:285–286 has Number.isNaN + < 0 check -->

### 7.5 No client-side secrets

The page component contains no API keys, credentials, or secrets. All authentication
flows through the existing cookie/Bearer machinery in `api/client.ts`.

## 10. Open Questions / Assumptions

1. **`asset_id` in `MaintenanceOrderTransitionIn`.** FXA-013 section 2.7 resolves Open
   Question 5 of FXA-012: the body includes `asset_id`. FXA-015 assumes this is the final
   contract. If the backend implementation provides a separate `GET /work-orders/{id}`
   endpoint that returns `asset_id`, the page could derive it from a lookup instead of
   requiring it in the transition body — but that is FXA-013's call.

2. **Per-period manual post endpoint.** FXA-009 describes `post_depreciation_period` as a
   service function callable by the FXA-007 admin endpoint; FXA-007's endpoint table does
   not list a `POST /{asset_id}/periods/{period}/post` endpoint. FXA-015 does not include a
   "Post period" button in the schedule drawer for this milestone. If FXA-007 or a follow-up
   ticket exposes such an endpoint, the schedule table can add a "Post" action for
   `"scheduled"` rows.

3. **`DepreciationScheduleOut` ordering.** FXA-014 open question 2 notes the API does not
   canonicalize sort order. FXA-015 sorts `periods` ascending by `period` before rendering
   (`[...scheduleData.periods].sort((a, b) => a.period - b.period)`). If the backend already
   returns ascending order this is a no-op; if it returns descending, the sort corrects it.

4. **Proceeds payment integration.** The dispose dialog accepts a `proceeds_payment_intent_id`
   string typed in by the admin. There is no `<Select>` of existing Stripe PaymentIntents.
   This is acceptable for an admin-only tool; a future improvement could integrate with
   the billing history endpoint to provide a picker.

5. **`useful_life_months` maximum.** The backend `FixedAssetIn` model field has
   `ge=1, le=1200` (`docs/ofbiz/specs/FXA-004.md:148`). FXA-015 applies the same bounds in
   the client-side guard. The `<Input>` has `min={1} max={1200}`.

6. **Pagination UX.** FXA-015 uses a simple "Load more" append pattern. If the expected
   asset count ever exceeds a few hundred, a `useInfiniteQuery` refactor (as used by
   `useInfiniteQuery` in ConversationView) would be appropriate — but is out of scope here.

7. **Disposed-asset selector filtering in work order creation.** The asset
   `<Select>` in the WO create dialog includes all assets from `assetsQuery.data.items`
   including `"disposed"` assets. A greyed option or exclusion is recommended for clarity
   but the server will return 400 if selected — so behavior is safe even without filtering.
   FXA-015 adds a `(disposed)` label suffix and `disabled` attribute on those options for
   defensive UX.

8. **`work_order_id` field on `MaintenanceOrder`.** FXA-013 spec section 2.7 adds `asset_id`
   to `MaintenanceOrderTransitionIn`. This requires that the `transitionWorkOrder` wrapper
   in `fixedAssets.ts` passes `{ ...body, asset_id: transitionTarget.asset_id }`. The
   FXA-014 spec's `transitionWorkOrder` signature takes `(workOrderId, body)` where `body`
   is `MaintenanceOrderTransitionIn`. FXA-015 must ensure `asset_id` is included in the
   body object. If `MaintenanceOrderTransitionIn` in `types.ts` does not include `asset_id`,
   an intersection type or a local override is needed — this should be resolved with
   FXA-013/FXA-014 before FXA-015 is implemented.
