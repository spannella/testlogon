# POS-007 — Card / wallet tender via existing billing

**Type:** Feature | **Priority:** P0 | **Estimate:** 4 days

---

## 1. Summary & Goal

POS-007 extends `app/services/pos_tender.py` (created by POS-006) with two new
functions — `tender_card(...)` and `tender_wallet(...)` — that route in-person
card and wallet payments through the **existing** billing infrastructure without
forking any billing logic.

- **Card tender** delegates to the same Stripe PaymentIntent path used by
  `charge_once` (`app/routers/billing.py:1179`), including the provider-toggle
  503 gate (`_require_provider_enabled`, `:100`) and the fraud gate
  (`_fraud_gate`, `:118`). The ledger entry is written via
  `billing_shared.new_ledger_entry` with `extra={"provider":"stripe"}` for
  financial-dashboard attribution.
- **Wallet tender** deducts from the cashier-user's in-platform wallet via
  `billing_shared.apply_wallet_delta` (`:185`), raising the existing
  `ConditionalCheckFailedException` → 400 path on insufficient balance.
- **Split tender** allows a single POS transaction to be paid across multiple
  tender legs (e.g., partial cash + partial card). The transaction stays in
  status `"open"` until the sum of all tender legs equals `total_cents`; only
  at that point is `purchase_cart` called (once) to produce a single order.

The entire module is behind the default-off `S.pos_enabled` flag established by
POS-003. Zero bytes of the existing shop/cart/orders/billing stack change when
the flag is off.

### 2.2 Existing `charge_once` path (`app/routers/billing.py:1179`)

`charge_once` at `:1179` is a router-level function decorated with
`@dual_route("POST", "/billing/charge-once")`. It:

1. Calls `ensure_stripe_configured()` (`:636`) — raises 501 if Stripe SDK is
   absent or unconfigured.
2. Calls `_require_provider_enabled("stripe")` (`:100`) — raises 503 if an
   admin has toggled Stripe off via `POST /ui/admin/payment-providers/stripe/toggle`
   (backed by `app/services/payment_provider_health.py:440`).
3. Calls `_fraud_gate(user_id, amount_cents, "credit", req=req)` (`:118`) —
   raises 403 on frozen account or blocked transaction.
4. Calls `stripe.PaymentIntent.create(...)` with `off_session=True, confirm=True`.
5. Calls `new_ledger_entry(...)` with `extra={"provider": "stripe"}`, writes it
   via `ddb_put(T.billing, led_item)`.
6. Calls `settle_or_reverse_ledger(T.billing, ...)` if `pi.status == "succeeded"`.
7. Calls `put_payment_record(user_id, pi, led_sk, payment_method_type, ...)` (`:693`).
8. Calls `record_billing_transaction(...)` (`:67`, from `purchase_history`).
9. Returns `{"status": pi["status"], "payment_intent_id": pi["id"]}`.

POS-007 does **not** call `charge_once` as an HTTP handler. It calls the same
underlying Stripe + ledger primitives directly in `pos_tender.py`, mirroring
the sequence at `:1180`–`:1283`. The pattern of calling the router function via
`from app.routers import billing as stripe_router` (as `billing_dunning.py:189`
does) is NOT used for POS, because `charge_once` hard-codes `ctx` and `actor`
kwargs that assume HTTP session context. Instead, POS-007 replicates the minimal
Stripe + ledger call sequence in service code, keeping the same guard ordering.

### 2.3 Existing `apply_wallet_delta` path (`app/services/billing_shared.py:185`)

`apply_wallet_delta(table, pk, delta_cents, *, currency)` at `:185` performs a

### 2.5 POS-006 tender-row schema and settlement flow

POS-006 establishes the tender row with SK `TENDER#{txn_id}` (a single cash
tender per transaction, no sequence suffix):

```
PK  pos_pk = SESSION#{session_id}
SK  pos_sk = TENDER#{txn_id}          ← POS-006 schema (no sequence suffix)
```

POS-007 **extends** this schema to support multiple tender legs per transaction
by introducing a sequence number in the SK:

```
PK  pos_pk = SESSION#{session_id}
SK  pos_sk = TENDER#{txn_id}#{tender_seq:04d}   ← POS-007 extended schema
```

This means POS-006 (`tender_cash`) must also be updated to write the new SK
format (`TENDER#{txn_id}#0000`) and increment `tender_count`, so that the split-
tender `begins_with("TENDER#{txn_id}#")` query works uniformly across all tender
kinds. See §7 assumption 7 and the POS-006 dependency note in §11.

Attributes added/used by POS-007: `tender_id`, `txn_id`, `kind`
(`cash|card|wallet`), `amount_cents`, `change_due_cents`, `payment_method_id`
(card/wallet only), `pi_id` (Stripe PaymentIntent id, card only), `ledger_sk`
(back-ref for void/reversal), `created_at`.

POS-006 also establishes the TXN update pattern: after a fully settled cash
tender the TXN row is updated with `status="settled"`, `order_id`, `ledger_sk`
(per `docs/ofbiz/specs/POS-006.md` §3.2). POS-007 changes the final settled
status to `"tendered"` (split-tender semantic: `"open"` → partial legs →
`"tendered"` at full settlement); POS-006 will need to align to this status value
or POS-007 must tolerate `"settled"` as an alias.

### 2.6 Split tender pattern — not yet implemented

POS-006 handles only single-tender (cash) settlement. POS-007 introduces the
concept of **accumulated tenders**: multiple `TENDER#` rows can exist under the
same `SESSION#{session_id}` for the same `txn_id` before `purchase_cart` is
called. The sum check `Σ tenders − Σ change = total_cents` is the settlement
gate.

## 3. Data Model

### 3.1 No new tables

POS-007 writes only to the existing `pos` table (`T.pos`) and `billing` table
(`T.billing`). No new `TableDef` entries are required in
`scripts/local-ddb-init.py`.

### 3.2 Tender row (extended from POS-006)

All tender rows (cash from POS-006, card/wallet from POS-007) share the schema:

```
PK  pos_pk = SESSION#{session_id}
SK  pos_sk = TENDER#{txn_id}#{tender_seq:04d}
```

Additional fields introduced by POS-007:

| Attribute | Type | Present when |
|---|---|---|
| `kind` | str | always: `"card"` or `"wallet"` |
| `payment_method_id` | str | card: stored-PM id; wallet: `"wallet"` sentinel |
| `pi_id` | str | card only: Stripe `PaymentIntent.id` |
| `ledger_sk` | str | always: billing table back-ref for POS-008 reversal |
| `ledger_pk` | str | always: billing table `pk` (`USER#{cashier_sub}`) |
| `provider` | str | always: `"stripe"` or `"wallet"` |
| `tender_seq` | int | monotonic counter per txn (0000, 0001, ...) |

`tender_seq` is stored as a zero-padded 4-digit string in the SK so that
`begins_with("TENDER#{txn_id}#")` queries return tenders in insertion order.

### 3.3 TXN row modifications (split tender state)

The TXN row (`TXN#{txn_id}` / `META`) from POS-005 gains two new attributes
written by `tender_card`/`tender_wallet` **before** full settlement:

| Attribute | Type | Description |
|---|---|---|
| `pending_tender_cents` | int | Sum of all tender legs recorded so far (excluding change) |
| `tender_count` | int | Number of tender legs recorded (used to derive `tender_seq`) |

These are incremented atomically via `update_item` with an `ADD` expression so
concurrent tender legs are safely serialized by DynamoDB. They are reset to 0
only if a partial tender is reversed (POS-008 scope).

After full settlement, POS-007 also writes `status="tendered"`, `order_id`,
and one `ledger_sk` per tender leg onto the TXN row (multi-valued; stored as
`ledger_sks: list[str]`). The `ledger_sks` list enables POS-008 to reverse
each per-tender ledger entry independently.

### 3.4 DynamoDB `attr_types` for numeric GSI sort keys

The `pos` `TableDef` in `scripts/local-ddb-init.py` was established by POS-003
with:

```python
attr_types={"opened_at": "N", "created_at": "N"}
```

POS-007 does not add new GSIs and does not modify `attr_types`. No schema
changes to `scripts/local-ddb-init.py` are required by this ticket.

## 4. API / Service Design

### 4.1 New functions in `app/services/pos_tender.py`

#### `tender_card`

```python
def tender_card(
    cashier_sub: str,
    session_id: str,
    txn_id: str,
    amount_cents: int,
    payment_method_id: str,
    *,
    idempotency_key: str,
    currency: str = "usd",
) -> Dict[str, Any]:
```

**Steps:**

1. Call `_require_pos_enabled()` — raises `HTTPException(404)` if `S.pos_enabled`
   is `False`.
2. Load the TXN draft: `_load_open_or_partially_tendered_txn(cashier_sub, txn_id)`.
   Raises 404 if absent, 403 if cashier mismatch, 409 if `status` is not
   `"open"` (the partially-tendered state retains `status="open"` until full
   settlement).
3. Validate `amount_cents >= 1`.
4. Compute the `tender_seq` for this leg atomically (see §3.3): derive from
   `txn["tender_count"]` before incrementing.
5. Derive a deterministic `tender_id = sha256(f"pos_tender_card:{txn_id}:{idempotency_key}")[:32]`.
6. **Idempotency gate**: attempt a conditional `put_item` on the
   `SESSION#{session_id}` / `TENDER#{txn_id}#{tender_seq:04d}` row with
   `ConditionExpression="attribute_not_exists(pos_pk)"`. On
   `ConditionalCheckFailedException`, load and return the existing tender row
   with its already-recorded `pi_id` and `ledger_sk`.
7. Call `_require_provider_enabled("stripe")` — raises 503 if Stripe is toggled
   off.
8. Call `_fraud_gate(cashier_sub, amount_cents, "credit")` — raises 403 on
   frozen account or blocked transaction.
9. Call `ensure_stripe_configured()`.
10. Call `get_or_create_customer(cashier_sub)` to retrieve/create the Stripe
    customer for the cashier's account.
11. Create the Stripe PaymentIntent:
    ```python
    pi = stripe.PaymentIntent.create(
        amount=int(amount_cents),
        currency=currency,
        customer=customer_id,
        payment_method=payment_method_id,
        off_session=True,
        confirm=True,
        description=f"POS card tender txn:{txn_id}",
        metadata={"app_user_id": cashier_sub, "purpose": "pos_card_tender",
                  "pos_txn_id": txn_id, "pos_session_id": session_id},
        idempotency_key=f"pos_card:{txn_id}:{idempotency_key}",
    )
    ```
12. Determine `state = "settled"` if `pi["status"] == "succeeded"`, else
    `"pending"`. On Stripe `CardError`: write an audit event and raise
    `HTTPException(402, str(exc))` — the tender row is NOT written, the TXN
    stays `"open"`.
13. Call `new_ledger_entry(key_name="pk", key_value=user_pk(cashier_sub), entry_type="credit", amount_cents=amount_cents, state=state, reason="pos_card_tender", meta={"pos_txn_id": txn_id, "pi_id": pi["id"]}, extra={"provider": "stripe"})`.
    Write the ledger item: `ddb_put(T.billing, led_item)`.
14. If `state == "settled"`: call `put_payment_record(cashier_sub, pi, led_sk, "card")`.
15. Write the tender row to `T.pos` (put_item, idempotency gate already passed).
16. Atomically increment `pending_tender_cents` and `tender_count` on the TXN
    row via `update_item` with `ADD pending_tender_cents :a, tender_count :one`.
17. Recompute `pending_tender_cents` from the updated TXN. If
    `pending_tender_cents == txn["subtotal_cents"]` (full settlement):
    a. Call `purchase_cart(cashier_sub, txn["bound_cart_id"], idempotency_key=f"pos:{txn_id}")`.
    b. Update TXN row: `status="tendered"`, `order_id`, `ledger_sks`, `settled_at`.
    c. Increment session `expected_cash_cents` by 0 (card does not affect till
       cash float).
18. Emit `audit_event("pos_card_tender", cashier_sub, None, ...)` (best-effort,
    wrapped in `try/except`).
19. Return `PosTenderOut` dict.

#### `tender_wallet`

```python
def tender_wallet(
    cashier_sub: str,
    session_id: str,
    txn_id: str,
    amount_cents: int,
    *,
    idempotency_key: str,
) -> Dict[str, Any]:
```

**Steps:**

1–6. Same as `tender_card` steps 1–6 (flag gate, load TXN, validate, idempotency).
   `tender_id = sha256(f"pos_tender_wallet:{txn_id}:{idempotency_key}")[:32]`.

7. Call `apply_wallet_delta(T.billing, user_pk(cashier_sub), -int(amount_cents))`.
   Catch `ClientError` (from `botocore.exceptions`) and check
   `exc.response["Error"]["Code"] == "ConditionalCheckFailedException"` —
   raise `HTTPException(400, "Insufficient wallet balance")` on match.
   The tender row is NOT written; the TXN stays `"open"`.

8. Call `new_ledger_entry(key_name="pk", key_value=user_pk(cashier_sub), entry_type="debit", amount_cents=amount_cents, state="settled", reason="pos_wallet_tender", meta={"pos_txn_id": txn_id}, extra={"provider": "wallet"})`.
   Write the ledger item: `ddb_put(T.billing, led_item)`.

9. Write the tender row to `T.pos`.

10. Atomically increment `pending_tender_cents` and `tender_count` on the TXN
    row. If `pending_tender_cents == txn["subtotal_cents"]` (full settlement):
    a. Call `purchase_cart(cashier_sub, txn["bound_cart_id"], idempotency_key=f"pos:{txn_id}")`.
    b. Update TXN row: `status="tendered"`, `order_id`, `ledger_sks`, `settled_at`.

11. Emit audit event (best-effort).

12. Return `PosTenderOut` dict.

## 5. Detailed Behavior & Edge Cases

### 5.1 Under-sum tender — transaction stays open

If the sum of all recorded tenders is less than `subtotal_cents`, the TXN row
remains `status="open"`. No order is created, `purchase_cart` is not called,
and no stock is decremented. The caller receives a `PosTenderOut` with
`settled=False`.

The cashier can add more tender legs (additional calls to POST /tender with
different `kind` values or larger amounts) until the full amount is covered.

### 5.2 Over-tender is an error

`tender_card` and `tender_wallet` reject `(pending_tender_cents + amount_cents) > subtotal_cents`
with `HTTPException(422, "Tender amount exceeds remaining balance")`. The TXN
remains open; no ledger entry is written and no Stripe charge is made. This
prevents accidental double-charging.

The remaining balance for a given TXN is:
`remaining_cents = subtotal_cents - pending_tender_cents`.

### 5.3 Stripe card decline — no side effects

If `stripe.PaymentIntent.create` raises `stripe.error.CardError`, the function:
1. Emits an audit event (`outcome="failure"`).
2. Raises `HTTPException(402, str(exc))`.
3. Does NOT write a tender row.
4. Does NOT write a ledger entry.
5. Does NOT increment `pending_tender_cents` on the TXN.

The TXN stays `"open"` and the cashier can retry with a different card or
switch to another tender kind.

### 5.4 Insufficient wallet balance — no side effects

`apply_wallet_delta(T.billing, pk, -amount_cents)` raises `ClientError` (from
`botocore.exceptions`) with
`exc.response["Error"]["Code"] == "ConditionalCheckFailedException"` when
`wallet_balance_cents < amount_cents`. `tender_wallet` catches `ClientError`,
checks the code, and raises `HTTPException(400, "Insufficient wallet balance")`.
No tender row and no ledger entry are written; `pending_tender_cents` is not
incremented. (This mirrors the pattern in `app/routers/billing.py:2585–2590`.)

### 5.5 Provider disabled (Stripe toggled off) — 503 before Stripe call

`_require_provider_enabled("stripe")` is called **before** any Stripe API call
and **before** the ledger write. In `charge_once` the actual call order is
`ensure_stripe_configured()` (`:1180`) → `_require_provider_enabled` (`:1181`)
→ `_fraud_gate` (`:1183`). POS-007's §4.1 step 7 mirrors this order. A 503 from
this gate writes no tender row, no ledger entry, and makes no outbound call.
(`app/routers/billing.py:1181`.)

### 5.6 Fraud gate blocks card tender — 403

`_fraud_gate(cashier_sub, amount_cents, "credit")` is called after the provider
check and before the Stripe call. On `403`, no Stripe call, no tender row, no
ledger entry are produced. This matches `app/routers/billing.py:1183`.

### 5.7 Idempotency on replay (card)

`tender_card` uses a two-level idempotency scheme:
1. **DynamoDB layer**: `ConditionExpression="attribute_not_exists(pos_pk)"` on
   the tender row `put_item`. A replayed call with the same
   `(txn_id, idempotency_key)` fails the conditional put and returns the
   existing tender row immediately — no second Stripe call is made.
2. **Stripe layer**: the Stripe `idempotency_key` kwarg (`f"pos_card:{txn_id}:{idempotency_key}"`)
   ensures that even if the DDB conditional put did somehow run twice, Stripe
   deduplicates the charge.

The DDB conditional put is the primary guard. The Stripe idempotency key is a
belt-and-suspenders safety net.

### 5.8 Split tender example: cash + card

1. `POST /tender` with `kind="cash"`, `amount_cents=500`, `change_due_cents=0`
   (POS-006). TXN `pending_tender_cents = 500`. Total is 1500. Not settled.
2. `POST /tender` with `kind="card"`, `amount_cents=1000`. Card charged via
   Stripe. Ledger entry written. `pending_tender_cents = 1500`. Now equals
   `subtotal_cents`. Settlement: `purchase_cart` called, order created, TXN
   `status="tendered"`.
3. Response contains `settled=True`, `order_id=...`.

Only one `purchase_cart` call occurs, producing exactly one order and one stock
decrement pass.

### 5.9 Mixed tender refund (POS-008 scope)

When POS-008 issues a refund for a split-tender transaction, it reverses
each ledger entry independently. The `ledger_sks` list on the TXN row
provides the back-refs. Cash refunds reverse the cash ledger entry and
adjust the session's `expected_cash_cents`. Card refunds go through
`refund_payment` / `settle_or_reverse_ledger`. Wallet refunds call
`apply_wallet_delta(T.billing, pk, +amount_cents)`. This detail is POS-008
scope; POS-007 only ensures `ledger_sks` is populated correctly.

### 5.10 `pending_tender_cents` atomic increment

The `ADD pending_tender_cents :a, tender_count :one` expression on the TXN row
is atomic (single DynamoDB write). The post-write value of `pending_tender_cents`
is read from the `ReturnValues="ALL_NEW"` response to decide whether settlement
is triggered. This eliminates the TOCTOU race of read-then-compare:

```python
resp = T.pos.update_item(
    Key={"pos_pk": f"TXN#{txn_id}", "pos_sk": "META"},
    UpdateExpression="ADD pending_tender_cents :a, tender_count :one",
    ExpressionAttributeValues={":a": amount_cents, ":one": 1},
    ReturnValues="ALL_NEW",
)
new_pending = int(resp["Attributes"]["pending_tender_cents"])
```

Only the thread/process that sees `new_pending == subtotal_cents` calls
`purchase_cart`.

### 5.11 `source_system` for the resulting order

`purchase_cart` at `app/services/shoppingcart.py:474` does not pass
`source_system` — it calls `CommerceOrderService.create_order_from_line_items`
with `source_system="shopping_cart"` (`:584`). This satisfies the existing
allowlist at `commerce_order_service.py:58`
(`{"shopping_cart","commercial_direct","subscription_cycle"}`). The POS context
is traceable via `metadata={"pos_txn_id": txn_id, "pos_session_id": session_id}`
passed into `purchase_cart`'s `idempotency_key` computation. No change to the
allowlist is required.

### 5.12 Currency matching

`tender_card` passes `currency` from `txn["currency"]` (stored on the TXN row
from the cart's default, which follows `S.default_currency` or
`S.stripe_default_currency` — `S.cart_default_currency` does not exist;
`app/core/settings.py:325` has `default_currency` and `:364` has
`stripe_default_currency`). The Stripe `PaymentIntent.create` call uses this
currency. Mismatches between the cashier's billing currency and the cart currency
are rejected by `purchase_cart`'s catalog currency check at
`shoppingcart.py:387–388`.

### 5.13 `tender_seq` derivation

`tender_count` is read from the TXN row before the `ADD` update so the tender
row SK can be constructed. The `tender_seq` equals the pre-update `tender_count`
value (0-indexed): first tender is `0000`, second is `0001`, etc. If the
idempotency gate fails (row already exists), the function returns the existing
row without incrementing `tender_count`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

All DDB writes (`T.pos`, `T.billing`) use the same code path in dev (DynamoDB
Local port 8001, moto in-process S3) and prod. There is no `if S.dev_mode`
branch in `pos_tender.py`. The Stripe mock (stripe-mock at port 12111) is used
in dev via `S.stripe_api_base`; the same `stripe.PaymentIntent.create` call runs
in both environments. `_require_provider_enabled("stripe")` reads from
`T.payment_provider_health` in both envs (SECOPS-007 parity).

### 7.2 Idempotency

`tender_card` and `tender_wallet` both use deterministic `tender_id` derivation:
`sha256(f"pos_tender_{kind}:{txn_id}:{idempotency_key}")[:32]`. The DynamoDB
conditional put on the tender row (`attribute_not_exists(pos_pk)`) is the
primary atomicity gate. Stripe's `idempotency_key` parameter provides a
secondary safeguard for the Stripe network call.

Replaying `purchase_cart` with `idempotency_key=f"pos:{txn_id}"` is safe: the
function at `shoppingcart.py:482–492` detects `status == "PURCHASED"` and
returns the existing `order_id` without re-running stock decrement or ledger
writes.

### 7.3 Security

- `cashier_sub` is always taken from the authenticated session (`ctx["user_sub"]`),
  never from the request body.
- Ownership check: `_load_open_or_partially_tendered_txn` verifies
  `txn["cashier_sub"] == cashier_sub`; raises 403 on mismatch.
- The bound cart is owned by `cashier_sub` via `PK=USER#{cashier_sub}`, so no
  foreign user can purchase it.
- CSRF is enforced on all non-GET POS endpoints by `require_ui_session` (cookie
  auth path), consistent with `app/routers/shoppingcart.py`.
- All financial figures are integer cents — no floating-point arithmetic in any
  tender path. `_FloatSafeTable` wrapping at `app/core/tables.py:29` coerces
  `float` to `Decimal` automatically.

### 7.4 Audit trail

Every card tender and wallet tender emits `audit_event(...)` via the
`app/services/alerts.py:644` helper, wrapped in a best-effort `try/except`
so audit failure never blocks the tender. Fields: `pos_txn_id`, `session_id`,
`kind`, `amount_cents`, `provider`, `pi_id` (card only), `outcome`.

### 8.1 Existing routes unchanged

`app/routers/billing.py` (`charge_once`, `wallet_withdraw`, `wallet_deposit`)
are not modified. All existing `/billing/*` endpoints are byte-for-byte

modified. The new `pending_tender_cents` and `tender_count` attributes on TXN
rows are added via `update_item ADD` and use DynamoDB's sparse attribute model —

POS-006 (cash tender) and POS-007 (card/wallet tender) are independent additions
to `pos_tender.py`. Deploying POS-006 without POS-007 is safe: `tender_cash` is
the only function available; `POST /ui/pos/txns/{txn_id}/tender` with `kind="card"`
or `kind="wallet"` returns 422 (Pydantic enum rejection) until POS-007 is deployed
and the router handler dispatches to the new functions.

## 10. Open Questions / Assumptions

1. **Assumption: `tender_card` calls billing primitives directly, not `charge_once` as HTTP.** `charge_once` at `app/routers/billing.py:1179` has `ctx=Depends(require_ui_session)` and `actor=Depends(get_authenticated_user)` kwargs that presuppose an HTTP request context. Calling it as a function (as `billing_dunning.py:192` does with `pay_balance`) requires passing a synthetic `ctx` dict; this works but requires carefully constructing `{"user_sub": cashier_sub}`. This spec instead calls the underlying Stripe + ledger primitives directly, which is cleaner and avoids tight coupling to the router layer. If the team prefers the `stripe_router.charge_once(body, req=None, ctx={"user_sub": cashier_sub})` pattern, the behavior is equivalent but the coupling increases.

2. **Assumption: partial tender uses `status="open"` not a new `"partial_tender"` status.** Introducing a new status value would require migrating all `_load_open_txn` guards in POS-005 and any POS-008 logic. Keeping `status="open"` and tracking progress via `pending_tender_cents` is simpler and avoids a schema change. An explicit `partial_tender` status could be added as a forward-compatible enhancement.

3. **Assumption: wallet tender deducts from the cashier's wallet, not a customer's wallet.** The POS model is cashier-centric: the `cashier_sub` owns the billing account for POS purposes. If a POS sale should deduct from a named customer's wallet, a `customer_sub` field would need to be added to the TXN row and all tender functions. This spec assumes cashier-only wallets.

4. **Assumption: no tax at the tender layer.** `pos_default_tax_rate_bps` from POS-003 settings applies at `purchase_cart` invocation (or in a pre-purchase `tax_cents` computation). POS-007 does not add tax logic; the `total_cents` in the TXN represents the cart total (pre-tax) and the tax is computed and appended before the cart is settled. The exact tax application is POS-006 scope; POS-007 inherits whatever `subtotal_cents` the TXN carries.

5. **Assumption: `put_payment_record` is called only for card (not wallet).** Stripe payment records (`PAY#{pi_id}` rows in `T.billing`) are only meaningful for Stripe-originated payments. Wallet tenders have no external payment reference. POS-008 (refund) will reverse wallet tenders via `apply_wallet_delta` directly, not via `refund_payment` (which requires a `payment_intent_id`).

6. **Question: should the fraud gate use the transaction amount or the cumulative split amount?** `_fraud_gate` at `:118` evaluates the individual `amount_cents` being tendered, not the total transaction amount. For a $1500 transaction split as $500 cash + $1000 card, the fraud gate sees $1000 for the card leg. If the intent is to gate on the full transaction amount, the call should pass `txn["subtotal_cents"]` instead. This spec uses the individual leg amount to match the `charge_once` behavior, which also evaluates the amount being charged in that call.

7. **Assumption: `tender_count` on TXN row starts at 0.** POS-006 (cash tender) also writes a tender row and must also increment `tender_count`. If POS-006 does not increment this counter, POS-007's `tender_seq` derivation must fall back to a DDB query to count existing `TENDER#{txn_id}#` rows. This spec assumes POS-006 is updated to also use the `ADD tender_count :one` pattern when it writes its tender row, so POS-007 gets a consistent sequence counter.
