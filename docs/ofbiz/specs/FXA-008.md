# FXA-008 — Depreciation GL accounts seed

## 1. Summary & Goal

FXA-008 has two tightly coupled deliverables:

1. **Extend `app/services/gl_accounts.py`** (the OFB-013 chart-of-accounts service) with four depreciation-specific accounts: **Fixed Assets** (asset class, debit-normal), **Accumulated Depreciation** (expense class; see §5.5 and Open Question 4 for the `contra_asset` class constraint), **Depreciation Expense** (expense class, debit-normal), and **Gain/Loss on Disposal** (revenue class; see Open Question 4 for the `income` class constraint). The seed extension hooks into the existing `seed_chart_of_accounts()` idempotent function (`docs/ofbiz/specs/OFB-013.md:214`) so no new startup lifecycle is needed. <!-- CORRECTED: OFB-013 names the function seed_chart_of_accounts(), not seed_default_accounts() -->

2. **Resolve and persist GL account codes onto each new asset** during `create_asset` in `app/services/fixed_assets.py` (FXA-005). The `gl_*_account_id` fields on `FixedAssetIn` / `FixedAssetOut` actually store the OFB-013 `account_code` string (e.g. `"FA-ASSET"`) — the PK of the `gl_accounts` table (`docs/ofbiz/specs/OFB-013.md:91`). When a caller omits one or more `gl_*_account_id` fields, `create_asset` fills in the seeded `account_code` defaults before writing the asset row. <!-- CORRECTED: OFB-013 PK is account_code, not account_id; these fields store the account_code value -->

After this ticket:
- `seed_gl_depreciation_accounts()` seeds exactly the four accounts, exactly once (idempotent), with correct class and normal-balance side.
- `create_asset` always stores non-null GL account codes on the asset row if the seed has run.
- FXA-009's `post_depreciation_period` can read `asset.gl_depr_expense_account_id` and `asset.gl_accum_depr_account_id` (which hold `account_code` values) directly from the asset row without a separate lookup.

Everything is additive. With `FIXED_ASSETS_ENABLED=false` the seed function is never called and no existing GL chart is modified.

2. For each item, calls `T.admin_messaging_templates.get_item(Key=..., ProjectionExpression="pk")`.
3. If `"Item"` is already in the response, `continue` (skip — already seeded, idempotent).

### 4.1 `seed_gl_depreciation_accounts()` — new function in `app/services/gl_accounts.py`

<!-- NOTE: account_class values "contra_asset" and "income" below are PENDING OFB-013 extension (see Open Question 4). Replace with valid classes once OFB-013 ACCOUNT_CLASSES is updated. The account_code IS the DDB PK in OFB-013 (docs/ofbiz/specs/OFB-013.md:91); no sha256 derivation is needed. -->

```python
_DEPRECIATION_ACCOUNTS = [
    {
        "account_code": "FA-ASSET",
        "name": "Fixed Assets",          # OFB-013 field is "name", not "account_name"
        "account_class": "asset",
        "description": "Fixed assets at acquisition cost",
    },
    {
        "account_code": "FA-ACCUM-DEPR",
        "name": "Accumulated Depreciation",
        "account_class": "contra_asset",  # REQUIRES OFB-013 ACCOUNT_CLASSES extension
        "description": "Contra-asset: accumulated depreciation to date",
    },
    {
        "account_code": "FA-DEPR-EXPENSE",
        "name": "Depreciation Expense",
        "account_class": "expense",
        "description": "Periodic depreciation charge to P&L",
    },
    {
        "account_code": "FA-GAIN-LOSS",
        "name": "Gain/Loss on Disposal",
        "account_class": "revenue",       # nearest valid OFB-013 class; "income" is not valid
        "description": "Net gain (credit) or loss (debit) on asset disposal",
    },
]


def seed_gl_depreciation_accounts() -> int:
    """Seed the four GL accounts required by the Fixed Assets depreciation module.

    Idempotent: each account is keyed by account_code (the DDB PK in OFB-013).
    Uses attribute_not_exists(account_code) conditional put — same pattern as
    seed_chart_of_accounts() (docs/ofbiz/specs/OFB-013.md:338). An existing
    account is never overwritten. Returns the number of accounts newly created.
    """
    created = 0
    ts = now_ts()
    for acct in _DEPRECIATION_ACCOUNTS:
        code = acct["account_code"]
        # OFB-013 derives normal_balance from account_class via NORMAL_BALANCE_FOR_CLASS
        # (docs/ofbiz/specs/OFB-013.md:185–191). For contra_asset / revenue overrides,
        # set normal_balance explicitly until NORMAL_BALANCE_FOR_CLASS is extended.
        normal_balance = NORMAL_BALANCE_FOR_CLASS.get(acct["account_class"], "debit")
        try:
            T.gl_accounts.put_item(
                Item={
                    "account_code": code,          # PK — docs/ofbiz/specs/OFB-013.md:91
                    "sk": "META",
                    "name": acct["name"],          # OFB-013 field name
                    "account_class": acct["account_class"],
                    "normal_balance": normal_balance,
                    "description": acct.get("description"),
                    "is_active": True,
                    "gsi_active": "true",          # required for GSI_ACTIVE
                    "is_system": True,
                    "created_at": ts,
                    "updated_at": ts,
                    "created_by": "system",        # required field — docs/ofbiz/specs/OFB-013.md:101
                },
                ConditionExpression="attribute_not_exists(account_code)",  # idempotent
            )
            created += 1
        except T.gl_accounts.meta.client.exceptions.ConditionalCheckFailedException:
            pass  # already exists — idempotent
        except Exception:
            logger.exception("Failed to seed GL account %s", code)
    if created:
        logger.info("Seeded %d GL depreciation accounts", created)
    return created
```

### 4.4 Modification to `create_asset` in `app/services/fixed_assets.py`

FXA-008 extends the `create_asset` function defined by FXA-005 to resolve default GL account codes when the caller omits them. The modification is a `_resolve_gl_defaults(req: FixedAssetIn) -> Dict[str, Optional[str]]` helper that runs after `_require_enabled()` and before the DDB write. Since `account_code` IS the OFB-013 PK (`docs/ofbiz/specs/OFB-013.md:91`), the lookup is a direct `get_item` via `get_account(code)` — no scan needed. <!-- CORRECTED: reuses get_account() from OFB-013, not a scan-based get_account_id_by_code -->

```python
_GL_CODE_MAP = {
    "gl_asset_account_id":        "FA-ASSET",
    "gl_accum_depr_account_id":   "FA-ACCUM-DEPR",
    "gl_depr_expense_account_id": "FA-DEPR-EXPENSE",
    "gl_gain_loss_account_id":    "FA-GAIN-LOSS",
}


def _resolve_gl_defaults(req: FixedAssetIn) -> Dict[str, Optional[str]]:
    """Return a dict of resolved GL account codes for the four depreciation accounts.

    For each field: use the caller-supplied value if present; otherwise look up
    the seeded default by account_code from T.gl_accounts using the OFB-013
    get_account() function (direct PK get_item — O(1)).
    Returns None for any account not found (seed has not run or OFB-013 not deployed).
    """
    from app.services.gl_accounts import get_account  # lazy import; avoids circular dep

    resolved: Dict[str, Optional[str]] = {}
    for field, code in _GL_CODE_MAP.items():
        caller_value = getattr(req, field)
        if caller_value is not None:
            resolved[field] = caller_value
        else:
            try:
                item = get_account(code)      # direct get_item by account_code (PK)
                resolved[field] = item["account_code"] if item else None
            except Exception:
                resolved[field] = None  # best-effort; asset can still be created
    return resolved
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Seed idempotency — second call

<!-- CORRECTED: mechanism is attribute_not_exists conditional put (OFB-013 pattern), not get-then-skip -->

On the second and subsequent calls to `seed_gl_depreciation_accounts()`:

1. Each `put_item` uses `ConditionExpression="attribute_not_exists(account_code)"` (same pattern as `seed_chart_of_accounts()` per `docs/ofbiz/specs/OFB-013.md:338`).
2. The second call receives `ConditionalCheckFailedException` for each account already present, which is silently swallowed.
3. `created` stays at 0; the log line "Seeded N GL depreciation accounts" is not emitted.

This is a conditional-put (`attribute_not_exists`) approach, matching `seed_chart_of_accounts()` exactly. The advantage over get-then-skip is atomic safety: no TOCTOU window. Both a simultaneous startup and a repeated restart are safe — `ConditionalCheckFailedException` is silently swallowed for pre-existing rows.

### 5.2 `GL_DOUBLE_ENTRY_ENABLED` flag interaction

The OFB-013 chart-of-accounts seed and GL posting are gated by `GL_DOUBLE_ENTRY_ENABLED` (ADR `:280`). The depreciation GL accounts must exist whether or not double-entry posting is active for existing money flows, because the depreciation journal (FXA-009) is a non-cash journal that does not derive from the billing ledger. Therefore `seed_gl_depreciation_accounts()` is gated by `FIXED_ASSETS_ENABLED` alone, not by `GL_DOUBLE_ENTRY_ENABLED`. The accounts will be present in the chart before FXA-009 begins posting to them.

### 5.3 GL account codes on `create_asset` when seed has not run

If `seed_gl_depreciation_accounts()` has not run (e.g. first deploy before startup, or OFB-013 table does not exist yet), `get_account("FA-ASSET")` will either raise a boto3 `ResourceNotFoundException` (table missing) or return `None` (account not seeded yet). The `try/except` in `_resolve_gl_defaults` catches this and returns `None` for the relevant fields. The asset row is written with `None` GL account codes. FXA-009 (`post_depreciation_period`) must handle a `None` GL account code gracefully — it should raise a 422 or skip the period with an error log rather than posting an unlinked journal entry. This guard belongs in FXA-009; FXA-008 only commits to best-effort resolution. <!-- CORRECTED: get_account() replaces get_account_id_by_code() -->

### 5.4 Caller-supplied GL account ID overrides

If `FixedAssetIn.gl_asset_account_id = "custom_account_123"` is supplied, `_resolve_gl_defaults` returns that value unchanged (the `if caller_value is not None` branch). No validation is performed that `"custom_account_123"` exists in `T.gl_accounts` — that check is deferred to FXA-009 (which will look up the account at posting time). Validating at create time would add a DDB read per account per asset creation; for now, a broken GL account ID is caught at posting time rather than registration time.

### 5.5 The `contra_asset` class and trial-balance sign convention

**RISK (Open Question 4):** The OFB-013 `ACCOUNT_CLASSES` frozenset is `{"asset", "liability", "equity", "revenue", "expense"}` (`docs/ofbiz/specs/OFB-013.md:184`). `"contra_asset"` is NOT a member of this set. `create_account()` raises `HTTPException(400, "Invalid account_class")` if `account_class not in ACCOUNT_CLASSES` (`docs/ofbiz/specs/OFB-013.md:245`). The `seed_gl_depreciation_accounts()` code uses `put_item` directly (bypassing that service-layer validation), so the write would succeed in DDB — but `NORMAL_BALANCE_FOR_CLASS.get("contra_asset", "debit")` would produce `"debit"` (the default), not `"credit"`. This is incorrect for accumulated depreciation.

**Required fix before implementation:** OFB-013 must extend `ACCOUNT_CLASSES` to include `"contra_asset"` and add `"contra_asset": "credit"` to `NORMAL_BALANCE_FOR_CLASS`. OFB-016 must also classify `contra_asset` correctly on the balance sheet. This must be coordinated before FXA-008 is merged. <!-- CORRECTED: contra_asset is not in OFB-013 ACCOUNT_CLASSES; specific risk and fix documented -->

Until that extension lands, the interim approach in §3.2 (using `account_class="expense"` as a placeholder) is incorrect for trial-balance purposes. The implementer must block on OFB-013 reviewer sign-off.

### 5.6 `is_system = True` prevents accidental deletion

All four seeded accounts carry `is_system: true`. The OFB-013 ROOT-gated `POST /ui/gl/accounts/{code}/disable` endpoint (per `docs/ofbiz/specs/OFB-013.md:261–268`) enforces `if item.get("is_system"): raise HTTPException(403, ...)`. <!-- CORRECTED: endpoint is POST /ui/gl/accounts/{code}/disable, not DELETE /ui/gl-accounts/{account_id}; OFB-013 uses code not account_id as path param --> FXA-008 does not implement that guard (it lives in OFB-013's router), but it must set `is_system: true` so OFB-013 can enforce it.

### 5.7 Asset PATCH after creation — overriding seeded defaults

An admin can override a seeded GL account ID post-registration via `PATCH /ui/fixed-assets/{asset_id}` with `FixedAssetPatchIn`. For example, a multi-entity org may want assets registered under one legal entity to use entity-specific GL accounts. The PATCH path is already implemented by FXA-007; FXA-008 has no action here beyond ensuring the fields are present and patchable.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity:** `seed_gl_depreciation_accounts()` has no `if S.dev_mode` branch. The same `get_item` / `put_item` calls run against DynamoDB Local (dev, port 8001) and real DynamoDB (prod). Both environments return `Decimal` for numeric fields; no numeric fields are written in the seed items (only strings and boolean), so no coercion is required here.

**Idempotency mechanism:** The seed is idempotent via `attribute_not_exists(account_code)` conditional put. Since `account_code` is the DDB PK (`docs/ofbiz/specs/OFB-013.md:91`), the same `account_code` on a second startup yields `ConditionalCheckFailedException`, which is silently swallowed. No TOCTOU window — both a simultaneous startup and a repeated restart are safe. <!-- CORRECTED: removed get-then-skip description; OFB-013 uses conditional put -->

**Multiple instances / rolling deploy:** If two uvicorn workers start simultaneously with `FIXED_ASSETS_ENABLED=true`, both may pass the `"Item" in existing` check before either writes. The second `put_item` is a no-op in terms of correctness (it writes the same values). DDB item sizes are tiny (< 200 bytes per account) and writes are idempotent. The `is_system: true` flag is set by both writers, so no corruption occurs.

**Security:**
- `seed_gl_depreciation_accounts()` is called only from a startup handler (or alongside `seed_chart_of_accounts()` from OFB-013, which itself is startup-only). It is never exposed via HTTP. <!-- CORRECTED: seed_chart_of_accounts(), not seed_default_accounts() -->
- The seeded accounts carry `is_system: true` to prevent ROOT-gated deletion (enforced in OFB-013's delete handler, not here).
- Account IDs derived from `sha256` are non-guessable but also non-secret — they are internal DDB keys. No credentials or PII are stored on account rows.
- The `get_account()` call reads the `gl_accounts` table without any auth check because it is an internal service-to-service call (invoked from `create_asset`, which already enforces `require_ui_session` + ADMIN/ROOT role check at the router layer per `docs/ofbiz/specs/FXA-005.md:268–274`). <!-- CORRECTED: require_admin_session does not exist in this codebase (app/auth/deps.py has no such function); correct pattern is require_ui_session + manual role check, as verified in app/auth/deps.py and confirmed by FXA-005 spec:274 -->

## 10. Open Questions / Assumptions

1. **`seed_chart_of_accounts()` extension vs. independent call (RESOLVED).** OFB-013's seed function is `seed_chart_of_accounts()` (`docs/ofbiz/specs/OFB-013.md:214`), not `seed_default_accounts()`. FXA-008 registers `seed_gl_depreciation_accounts()` as a separate startup handler in `app/main.py` guarded by `S.fixed_assets_enabled`. This is correct regardless of OFB-013 merge order. <!-- CORRECTED: question resolved by verification of OFB-013 spec -->

2. **`account_code` as the lookup key (RESOLVED — confirmed).** OFB-013 uses `account_code` as the DDB partition key (`docs/ofbiz/specs/OFB-013.md:91`). The `get_account(account_code)` function is already defined in OFB-013 (`docs/ofbiz/specs/OFB-013.md:222`). No scan and no extra lookup helper is needed. <!-- CORRECTED: resolved by OFB-013 spec verification -->

3. **Scan vs. GSI for account lookup (RESOLVED — no scan needed).** `account_code` IS the partition key, so lookup is a direct `get_item` call — O(1). The scan approach in the original spec was incorrect. <!-- CORRECTED: scan entirely replaced by direct get_item -->

4. **`contra_asset` and `income` as valid `account_class` values (OPEN — BLOCKING RISK).** OFB-013's `ACCOUNT_CLASSES = frozenset({"asset", "liability", "equity", "revenue", "expense"})` (`docs/ofbiz/specs/OFB-013.md:184`). Neither `"contra_asset"` nor `"income"` is in this set. OFB-013's `create_account()` raises 400 for invalid classes; `NORMAL_BALANCE_FOR_CLASS` has no entry for these classes. **FXA-008 is BLOCKED until OFB-013 is extended to include `contra_asset` (with `normal_balance="credit"`) and `income` (or use `revenue` instead) in both `ACCOUNT_CLASSES` and `NORMAL_BALANCE_FOR_CLASS`. OFB-016 must also be updated to classify `contra_asset` under the asset side of the balance sheet.** For the Gain/Loss account, using `"revenue"` as the class is the nearest valid option and may be acceptable to the finance reviewer.

5. **`get_account` lazy import in `create_asset` — circular import risk (LOW).** The lazy import `from app.services.gl_accounts import get_account` inside `_resolve_gl_defaults` avoids a circular import between `fixed_assets.py` and `gl_accounts.py`. The OFB-013 spec (`docs/ofbiz/specs/OFB-013.md:175–211`) shows `gl_accounts.py` imports only from `app.core.tables`, `app.core.time`, `app.core.settings`, and standard library — no import from `fixed_assets.py`. No circular dependency risk.

6. **Gain/Loss on Disposal — single account or two accounts.** Accounting practice sometimes uses two separate accounts: `"Gain on Disposal"` (credit-normal) and `"Loss on Disposal"` (debit-normal). This spec seeds a single `"Gain/Loss on Disposal"` account, letting the disposal journal (FXA-011) post either a net credit (gain) or a net debit (loss) to the same account. If the finance reviewer requires two separate accounts, FXA-011's spec (and this seed list) must be updated.

7. **`account_code` stability across environments.** The `FA-*` account codes appear in dev, staging, and prod identically (they are the DDB PK). Test fixtures may hard-code these code strings for assertions. Renaming a code requires a data migration. The assumption is that the four `FA-*` codes are stable. <!-- CORRECTED: removed the sha256-derived account_id stability claim; account_code is the PK and is stable by design -->
