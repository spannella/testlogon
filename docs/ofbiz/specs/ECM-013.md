# ECM-013 — Frontend types & endpoint wrappers

**Type:** Feature | **Priority:** P1 | **Estimate:** 2 days
**Dependencies:** ECM-003 (Pydantic models), ECM-012 (fulfillment-status service + endpoint)

---

## 1. Summary & Goal

ECM-013 is a pure frontend ticket that makes the TypeScript layer aware of every
new shape introduced by the ECM integration layer. It has two deliverables:

1. **TypeScript interfaces** in `frontend/src/api/types.ts` that mirror the four
   ECM-003 Pydantic models (`StorefrontVariant`, `StorefrontAvailability`,
   `CartPricingBreakdown`, `OrderFulfillmentStatus`), the ECM-008 line-availability
   shape, and the ECM-002 feature-flag config shape — plus additive optional
   fields on the existing `CatalogItem`, `CartTotal`, and `CartPurchase` interfaces.

2. **API endpoint wrappers** — two new functions in `frontend/src/api/endpoints/cart.ts`
   (`getCartLineAvailability`, `getStoreConfig`) and a new thin module
   `frontend/src/api/endpoints/orders.ts` exporting `getOrderFulfillmentStatus` —
   each typed to the new interfaces and following the `api.get<T>` pattern
   established at `cart.ts:40–41`.

With all store-integration flags off (the default), the new interfaces and
wrappers add zero behavioral change: no existing wrappers change signature, no
new network calls are made by existing pages, and `tsc --noEmit` passes without
errors. ECM-011 (Cart UI enrichment) and ECM-014 (order tracking page) are the
first consumers; they import directly from the files this ticket defines.

### 2.4 ECM-012 fulfillment-status endpoint

ECM-012 (`docs/ofbiz/specs/ECM-012.md`) adds `order_fulfillment_status(order_id,
user_sub)` to `app/services/store_integration.py` and exposes it (via ECM-014)
as `GET /ui/shoppingcart/orders/{order_id}/fulfillment`. The response is
`OrderFulfillmentStatusOut`. Ownership is enforced server-side (foreign order_id
→ 403/404). With `STORE_SHOW_FULFILLMENT_STATUS` off, the response carries only
`order_id` with all other fields `None` / `[]`.

The ECM-013 ticket exposes this as the `getOrderFulfillmentStatus(orderId)`
wrapper so ECM-014 and any other consumer can import from a typed endpoint file
without constructing the URL manually.

### 2.5 ECM-002 `GET /ui/store/config` endpoint

ECM-002 introduces a lightweight settings-read endpoint
`GET /ui/store/config` that returns the effective flag state for the requesting
session — pure settings read, no DDB I/O. The ECM-011 spec
(`docs/ofbiz/specs/ECM-011.md:139–146`) establishes the shape and notes that
ECM-013 is the ticket that delivers the `getStoreConfig` wrapper and the
`StoreConfig` TypeScript interface. ECM-011 (Cart UI) and ECM-014 (order page)
both consume them.

### 2.6 ECM-008 line-availability endpoint

ECM-008 introduces `GET /ui/shoppingcart/carts/{cart_id}/line-availability`
returning `{ cart_id, lines: LineAvailability[] }`. ECM-011
(`docs/ofbiz/specs/ECM-011.md:227–254`) documents the response shape.
ECM-013 provides the `getCartLineAvailability` wrapper and the
`CartLineAvailabilityResp` / `LineAvailability` interfaces.

### 2.7 TypeScript strict-mode constraints

`frontend/tsconfig.json` (confirmed by file read; there is no `tsconfig.app.json`)
enables `"strict": true`, `"noUnusedLocals": true`, `"noUnusedParameters": true`,
and `"noUncheckedIndexedAccess": true`. All new interfaces must satisfy strict-mode
type-checking. Optional fields use `?: T` (not `| undefined`) where the backend
Python model uses `Optional[T] = None`, ensuring `null` round-trips are
representable as `null | undefined` in TS.

## 3. Data Model

ECM-013 is a pure frontend ticket — no DynamoDB tables, no GSIs, and no
`scripts/local-ddb-init.py` changes. The "data model" section documents only
the TypeScript type graph.

### 3.1 New top-level interfaces in `frontend/src/api/types.ts`

All definitions are appended to the shopping-cart / catalog cluster, after the
existing `StockAdjustment` interface at `types.ts:2154` [verified: `types.ts:2154`].

#### 3.1.1 `StorefrontAvailability`

Mirrors `StorefrontAvailabilityOut` (`ECM-003/app/models.py`). No `location_id`,
`reorder_point`, or `updated_at` — those are internal fields omitted from the
storefront projection (present on `InventoryRecord` [`types.ts:2163–2172`]).

```ts
// ─── Store integration — ECM-003 / ECM-013 ───────────────────────────────────

export interface StorefrontAvailability {
  available: number;       // on_hand − reserved; may be 0 or negative
  on_hand: number;
  reserved: number;
  low_stock: boolean;      // available > 0 && available <= reorder_point
  stock_status: string;    // "in_stock" | "low_stock" | "out_of_stock"
}
```

#### 3.1.2 `StorefrontVariant`

Mirrors `StorefrontVariantOut`. `option_selections` is typed as
`Record<string, string>` (the TS equivalent of `Dict[str, str]`).

```ts
export interface StorefrontVariant {
  variant_id: string;
  sku: string;
  option_selections: Record<string, string>;
  price_cents: number;
  availability?: StorefrontAvailability | null;
}
```

#### 3.1.3 `AppliedPricingRuleLine`

Mirrors `AppliedPricingRuleLineOut`. `discount_type` is typed as `string` rather
than a union literal because the OFB-020 vocabulary is not yet finalised
(ECM-003 §10.2 open question).

```ts
export interface AppliedPricingRuleLine {
  rule_id: string;
  rule_name: string;
  discount_type: string;   // "percentage" | "fixed_amount" | "bulk" | "conditional"
  discount_cents: number;
  applies_to_skus: string[];
}
```

#### 3.1.4 `CartPricingBreakdown`

Mirrors `CartPricingBreakdownOut`. `total_cents` is included as a backward-compat
alias for `final_total_cents` — ECM-009 will keep `total_cents == final_total_cents`
on the wire so existing callers that only read `total_cents` continue to work
unchanged (ECM-003 §10.5 assumption).

```ts
export interface CartPricingBreakdown {
  cart_id: string;
  subtotal_cents: number;
  applied_rules: AppliedPricingRuleLine[];
  discount_cents: number;
  final_total_cents: number;
  total_cents: number;     // backward-compat alias: equals final_total_cents
  currency: string;
}
```

#### 3.1.5 `ShipGroup`

Mirrors `ShipGroupOut`. `shipped_at` is a Unix timestamp integer (not a string)
consistent with the project's convention for numeric timestamps (`InventoryRecord.updated_at`
at `types.ts:2171` [verified]).

```ts
export interface ShipGroup {
  ship_group_id: string;
  status: string;          // "pending" | "picked" | "packed" | "shipped" | "delivered"
  items: string[];         // SKUs in this ship group
  carrier?: string | null;
  tracking_number?: string | null;
  shipped_at?: number | null;         // Unix timestamp
  estimated_delivery?: string | null; // ISO date string
}
```

#### 3.1.6 `OrderFulfillmentStatus`

Mirrors `OrderFulfillmentStatusOut`. All fields except `order_id` are optional
with null-safe defaults to match the flag-off / partial-upstream state
(ECM-003 §5.5 and ECM-012 degrade behavior).

```ts
export interface OrderFulfillmentStatus {
  order_id: string;
  lifecycle_status?: string | null;
  fulfillment_status?: string | null;
  ship_groups: ShipGroup[];
  tracking_numbers: string[];
}
```

#### 3.1.7 `LineAvailability` and `CartLineAvailabilityResp`

Mirrors the ECM-008 `line-availability` endpoint response described in
ECM-011 (`docs/ofbiz/specs/ECM-011.md:227–254`).

```ts
export interface LineAvailability {
  sku: string;
  reservation_id?: string | null;
  reserved_qty: number;
  expires_at: number;      // Unix ts; 0 if no reservation
  available: number;
  on_hand: number;
  low_stock: boolean;
  status: string;          // "in_stock" | "low_stock" | "out_of_stock"
}

export interface CartLineAvailabilityResp {
  cart_id: string;
  lines: LineAvailability[];
}
```

#### 3.1.8 `StoreConfig`

The effective runtime flag state returned by `GET /ui/store/config`. All flags
default to `false` server-side. The frontend treats a fetch error as
all-`false` (degraded to today's behavior, ECM-011 §5.7).

```ts
export interface StoreConfig {
  store_integration_enabled: boolean;
  store_show_live_availability: boolean;
  store_apply_pricing_rules: boolean;
  store_show_fulfillment_status: boolean;
  store_variant_selection_enabled: boolean;
  store_cart_reservations_enabled: boolean;
}
```

The `store_cart_reservations_enabled` sub-flag is introduced by ECM-008 (env
`STORE_CART_RESERVATIONS_ENABLED`, default `false`). Including it here avoids a
later breaking change to the `StoreConfig` interface.

## 4. API / Service Design

### 4.1 New wrappers in `frontend/src/api/endpoints/cart.ts`

Two new wrappers are appended to the existing `cart.ts` file (139 lines
[verified: `frontend/src/api/endpoints/cart.ts`]). The file already imports
`CartTotal` and `CartPurchase` from `@/api/types` [verified: `cart.ts:7–8`];
the import block is extended to also import the new interfaces.

#### 4.1.1 `getStoreConfig`

Calls the ECM-002 settings endpoint. No parameters. Uses `api.get<StoreConfig>`.

```ts
// ─── Store integration config (ECM-002 / ECM-013) ─────────────────────────────

export const getStoreConfig = () =>
  api.get<StoreConfig>("/ui/store/config");
```

**Backend endpoint**: `GET /ui/store/config`
**Auth**: `Depends(require_ui_session)` (cookie + CSRF) — same dependency used
throughout `app/routers/shoppingcart.py` [verified: `shoppingcart.py:28,54`].
**Response**: `StoreConfig` (all booleans).
**Cache key** (React Query, used by ECM-011): `["store-config"]`,
`staleTime: 5 * 60 * 1000` (5 minutes — config changes are operator actions).

#### 4.1.2 `getCartLineAvailability`

Calls the ECM-008 line-availability endpoint for a given cart.

```ts
export const getCartLineAvailability = (cartId: string) =>
  api.get<CartLineAvailabilityResp>(
    `/ui/shoppingcart/carts/${cartId}/line-availability`,
  );
```

**Backend endpoint**: `GET /ui/shoppingcart/carts/{cart_id}/line-availability`
**Auth**: `Depends(require_ui_session)`.
**Response**: `CartLineAvailabilityResp` (`{ cart_id, lines: LineAvailability[] }`).
**Flag-off behavior**: backend returns `{ cart_id, lines: [] }` when
`STORE_SHOW_LIVE_AVAILABILITY` is off; no 404.
**Cache key** (React Query, used by ECM-011): `["cart-line-availability", cartId]`.

### 4.2 New file `frontend/src/api/endpoints/orders.ts`

A new file is created rather than appending to `purchases.ts` because the
fulfillment-status endpoint lives under the `shoppingcart` router URL space
(`/ui/shoppingcart/orders/…`), not under the purchase-history path
(`/ui/purchase-history/…`). Mixing them in `purchases.ts` would couple
unrelated domains.

```ts
import { api } from "@/api/client";
import type { OrderFulfillmentStatus } from "@/api/types";

// ─── Order fulfillment status (ECM-012 / ECM-013) ─────────────────────────────
// Endpoint gated by STORE_SHOW_FULFILLMENT_STATUS (default off).
// With flag off, backend returns { order_id, lifecycle_status: null,
// fulfillment_status: null, ship_groups: [], tracking_numbers: [] }.

export const getOrderFulfillmentStatus = (orderId: string) =>
  api.get<OrderFulfillmentStatus>(
    `/ui/shoppingcart/orders/${encodeURIComponent(orderId)}/fulfillment`,
  );
```

**Backend endpoint**: `GET /ui/shoppingcart/orders/{order_id}/fulfillment`
(introduced by ECM-014 in `app/routers/shoppingcart.py`, backed by
`order_fulfillment_status` from ECM-012 in `app/services/store_integration.py`
[neither file nor function exists yet — ECM-002/ECM-012 are pre-implementation specs]).
**Auth**: `Depends(require_ui_session)` [pattern: `shoppingcart.py:28`].
Ownership enforced server-side.
**Response**: `OrderFulfillmentStatus`.
**Cache key** (React Query, used by ECM-014): `["order-fulfillment", orderId]`.
**Error handling**: 403 → non-owner (ApiError propagates to the caller);
404 → order does not exist. Both are handled by `api.get` via `ApiError`.

**Import in existing files**: `cart.ts` already imports from `@/api/types`
and follows the `api.get<T>` pattern. `orders.ts` follows the same import
structure as `purchases.ts` (`frontend/src/api/endpoints/purchases.ts:1–6`)
— no new patterns introduced.

### 4.4 Shared hook `useStoreConfig` (optional, consumed by ECM-011/ECM-014)

ECM-011 §6.3 documents a `useStoreConfig` hook. ECM-013 creates it at
`frontend/src/hooks/useStoreConfig.ts` so ECM-011 and ECM-014 can import from
a single location. This hook is a thin React Query wrapper:

```ts
import { useQuery } from "@tanstack/react-query";
import { getStoreConfig } from "@/api/endpoints/cart";
import type { StoreConfig } from "@/api/types";

const DEFAULT_STORE_CONFIG: StoreConfig = {
  store_integration_enabled: false,
  store_show_live_availability: false,
  store_apply_pricing_rules: false,
  store_show_fulfillment_status: false,
  store_variant_selection_enabled: false,
  store_cart_reservations_enabled: false,
};

export function useStoreConfig(): StoreConfig {
  const { data } = useQuery({
    queryKey: ["store-config"],
    queryFn: getStoreConfig,
    staleTime: 5 * 60 * 1000,
    retry: false,
  });
  return data ?? DEFAULT_STORE_CONFIG;
}
```

The `retry: false` prevents noisy console errors when `GET /ui/store/config`
is not yet deployed (ECM-002 not merged). The `DEFAULT_STORE_CONFIG` fallback
keeps the app in the legacy code path transparently. `noUnusedLocals` is
satisfied because `DEFAULT_STORE_CONFIG` is returned in the fallback path.

**File location**: `frontend/src/hooks/useStoreConfig.ts` (new file; the
`frontend/src/hooks/` directory already exists with other hooks in the project
[verified: 26 hook files including `useMessagingStream.ts`, `useFeedTimelineQuery.ts`, etc.]).

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off path — zero behavioral change

With all store-integration flags off (the default), neither `getStoreConfig`
nor `getCartLineAvailability` nor `getOrderFulfillmentStatus` is called by
any existing page. The new interfaces compile into type-checking artifacts only;
they have no runtime footprint until ECM-011 or ECM-014 call the new wrappers.

The additive fields on `CatalogItem`, `CartTotal`, and `CartPurchase` are typed
`? T | null`. TypeScript strict mode requires callers to handle `undefined` and
`null`; existing callers that ignore these fields compile without modification
because the fields are optional.

### 5.2 `CartTotal` backward-compat alias `total_cents`

`CartPricingBreakdown.total_cents` duplicates `final_total_cents` as a
backward-compat alias (ECM-003 §10.5). The TypeScript interface includes both
fields. Consumers that currently read `total?.total_cents` (e.g., `Cart.tsx`
via `getCartTotal` returning `CartTotal`) continue to work unchanged because:

- `CartTotal.pricing_breakdown?.total_cents` equals `CartTotal.total_cents`
  (same numeric value, ECM-009's server-side guarantee).
- `CartTotal` itself keeps its three original fields; the `pricing_breakdown`
  sub-field is the opt-in enrichment path.

ECM-011 reads `pricing_breakdown.final_total_cents` for the "Total" row when
flags are on; it falls back to `CartTotal.total_cents` when `pricing_breakdown`
is absent.

### 5.3 `OrderFulfillmentStatus` degrade path

When `STORE_SHOW_FULFILLMENT_STATUS` is off the backend returns:

```json
{
  "order_id": "<id>",
  "lifecycle_status": null,
  "fulfillment_status": null,
  "ship_groups": [],
  "tracking_numbers": []
}
```

The `OrderFulfillmentStatus` TypeScript interface models this exactly —
`lifecycle_status` and `fulfillment_status` are `string | null | undefined`, and
`ship_groups` / `tracking_numbers` default to empty arrays on the wire. ECM-014
(the order tracking page) renders a "Status unavailable" placeholder whenever
`lifecycle_status` is null, without a secondary fetch or error state.

### 5.4 `StoreConfig` missing endpoint — graceful degrade

If `GET /ui/store/config` returns a non-200 response (ECM-002 not yet
deployed; backend restart; etc.), the `useQuery` in `useStoreConfig` sets
`data` to `undefined`. The `data ?? DEFAULT_STORE_CONFIG` expression returns
the all-false default. All flag-gated UI renders `null` (today's behavior).
No visible error is shown to the user.

### 5.5 `CartLineAvailabilityResp.lines` empty array vs. absent

The backend always returns a valid JSON object with `lines: []` when the flag
is off, not a 404 or a missing key. The TypeScript interface models `lines` as
`LineAvailability[]` (not optional) to match this guarantee. If somehow the
response arrives without `lines`, TypeScript's optional-chaining (`?.lines ?? []`)
in consumer code (ECM-011) prevents a runtime error.

### 5.6 `encodeURIComponent` on order IDs

`getOrderFulfillmentStatus` wraps the `orderId` parameter in
`encodeURIComponent`. Order IDs are 32-character lowercase hex strings generated by
`hashlib.sha256(...).hexdigest()[:32]` in `app/services/commerce_order_service.py:67`
and contain no URL-special characters, but `encodeURIComponent` is added
defensively, matching the pattern in `inventory.ts:14` (`getInventoryItem`).
Note: `getTransaction` in `purchases.ts:31–32` does NOT use `encodeURIComponent`
(transaction IDs are plain strings passed directly into the URL).

### 5.7 `ShipGroup.items` typing

`items: string[]` contains SKUs, not order line item IDs (ECM-003 §5.6). A
cart item with `quantity=3` contributes the same SKU once. Consumer code (ECM-014)
renders each item as a string badge; no numeric quantity is available from
this field. `noUncheckedIndexedAccess` is satisfied because ECM-014 will use
`items.map(sku => ...)`, which iterates safely.

### 5.8 `tsc` compilation gate

After ECM-013 merges, running `cd frontend && npx tsc --noEmit` must succeed
with zero errors. The acceptance criterion in the ticket description is
"tsc passes with no errors." The implementation must:

- Ensure `StoreConfig` is exported from `types.ts` (marked `export interface`).
- Ensure all types referenced by new interface bodies (`StorefrontAvailability`
  referenced by `StorefrontVariant`, `AppliedPricingRuleLine` referenced by
  `CartPricingBreakdown`, etc.) are declared before their first use in the
  file, or TypeScript forward-reference resolution handles it (interfaces are

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

ECM-013 is pure TypeScript. No `import.meta.env.DEV` or `process.env.NODE_ENV`
conditionals are introduced. The interface definitions and wrapper functions
are identical in both the dev Vite build and the production bundle.

The `useStoreConfig` hook uses the same `getStoreConfig` wrapper in both
environments. In dev, the backend returns the flag values from `.env.local`
(which can enable flags for E2E testing). In prod, the flags are read from the
actual environment. No frontend-specific mock path is added.

### 7.2 Idempotency

All new wrappers are read-only `GET` calls. React Query deduplicates concurrent
calls with the same key. Multiple calls to `getStoreConfig()` within the same
render cycle hit the React Query cache (after the first fetch) — one network
request per stale-time window. No write paths are introduced by this ticket.

### 7.3 Security

- **Ownership**: `getOrderFulfillmentStatus` does not include the `user_sub`
  in the URL (the backend reads it from the session cookie). A user cannot
  substitute another user's `order_id` — the backend's ownership check
  (`order.user_id == user_sub`) returns 403. The frontend makes no attempt to
  enforce ownership client-side (server is authoritative).
- **XSS**: `rule_name` from `AppliedPricingRuleLine`, `carrier`, and
  `tracking_number` from `ShipGroup` are rendered as React text content by
  ECM-011/ECM-014 consumers — not via `dangerouslySetInnerHTML`. React escapes
  these strings automatically.
- **No new auth paths**: All three new wrappers use `api.get<T>` from
  `client.ts`, which attaches the CSRF cookie header and the Bearer token from
  `useAuthStore`. No new auth mechanism is introduced.
- **`encodeURIComponent` on IDs**: Applied in `getOrderFulfillmentStatus` as
  a defense-in-depth measure. Cart IDs and order IDs are UUIDs (no special
  characters), but this prevents path-injection if the ID format ever relaxes.

## 8. Backward Compatibility & Migration

### 8.1 `types.ts` — additive only

All changes to `types.ts` are purely additive:

- New interfaces are appended after existing ones in the shopping-cart cluster.
- `CatalogItem`, `CartTotal`, and `CartPurchase` gain optional nullable fields.
  TypeScript optional fields (`?: T`) are backward-compatible: existing callers
  that do not reference the new fields compile without change.
- No existing interface, field name, or field type is removed or renamed.
- The file is not auto-generated; it is a hand-maintained file and will continue
  to accept additions without regeneration.

### 8.2 `cart.ts` — additive only

Two new exported functions are appended. The existing 140 lines of `cart.ts`
are untouched: no existing function signature changes, no import is removed.
The `CartTotal` return type on `getCartTotal` (line 41) is not changed — the
enrichment is accessible via `CartTotal.pricing_breakdown` which is `undefined`
when the flag is off. If a future ECM ticket needs to return `CartPricingBreakdown`
directly, it adds a `getCartPricingBreakdown` wrapper rather than changing the
existing `getCartTotal` signature.

### 8.3 `orders.ts` — new file, no migration

`orders.ts` is a new file with no prior version. No DDB migration, no backend
restart, and no data backfill is required. The file can be added to the codebase
while `GET /ui/shoppingcart/orders/{order_id}/fulfillment` is still undeployed
(ECM-014 not yet merged) — the wrapper exists but is not called by any page.

### 8.4 `useStoreConfig.ts` — new file, no migration

New hook file. No existing hook is replaced. ECM-011 and ECM-014 import from
this file; no other file is impacted before they land.

### 8.5 `just restart` safety

Restarting the dev stack with all flags at their defaults (`false`) produces
no behavioral change in any existing shop page. The new TypeScript types compile
successfully with flag-off. No DDB schema changes means `just restart` continues
to work without table recreation.

## 10. Open Questions / Assumptions

1. **Assumption: `GET /ui/store/config` is introduced by ECM-002's implementation.**
   The ECM-002 spec (`docs/ofbiz/specs/ECM-002.md`) describes only the `Settings`
   fields and the `store_integration.py` helpers — it does not explicitly add a
   router endpoint. ECM-011 §2.6 attributes the endpoint to "ECM-013 (or ECM-002)."
   This spec assigns the backend endpoint (`GET /ui/store/config`, a three-line
   FastAPI handler reading from `S`) to ECM-013's implementation work, to be
   registered in `app/routers/shoppingcart.py` alongside other cart endpoints.
   If the reviewer decides ECM-002 should own it, ECM-013 is only the frontend
   wrapper. The wrapper implementation (`getStoreConfig`) is identical either way.

2. **Assumption: `GET /ui/shoppingcart/orders/{order_id}/fulfillment` is the
   correct URL.** ECM-012 calls the service function `order_fulfillment_status`
   but does not specify a URL path (it is a service ticket). ECM-014 owns the
   router endpoint. This spec assumes the path prefix `/ui/shoppingcart/orders/`
   mirrors the existing cart namespace (`/ui/shoppingcart/carts/`). If ECM-014
   uses a different path (e.g., `/ui/orders/{order_id}/fulfillment`), only the
   `getOrderFulfillmentStatus` URL string in `orders.ts` needs updating —
   the TypeScript interface and React Query cache key are unaffected.

3. **Assumption: `CartPricingBreakdown.total_cents` is guaranteed equal to
   `final_total_cents` on the wire.** ECM-003 §10.5 raises this as an open
   question and assumes the service layer keeps them consistent. If ECM-009
   does NOT include `total_cents` (the backward-compat alias) on the wire, the
   `CartTotal.total_cents` field on the outer `ShoppingCartTotalOut` covers the
   existing `total_cents` read paths. The `CartPricingBreakdown` interface's
   `total_cents` field should be marked `total_cents?: number` (optional) in
   that scenario so it does not cause a type error when absent.

4. **Assumption: `StoreConfig` fields from the backend are camelCase-free.**
   The project uses `snake_case` keys for all API responses (FastAPI default).
   The TypeScript interfaces mirror `snake_case` (e.g., `store_integration_enabled`
   not `storeIntegrationEnabled`). Consumers access `config.store_integration_enabled`
   directly. No Axios response transformer is configured in `client.ts` to convert
   casing, so the interface field names must match the backend's JSON output exactly.

5. **Open question: Should `useStoreConfig` be in `frontend/src/hooks/` or
   `frontend/src/stores/`?** Other shared hooks (`useAuthStore`, `useImpersonationStore`,
   `useThemeStore`) are Zustand stores in `frontend/src/stores/`. `useStoreConfig`
   is a React Query hook, not a Zustand store — it is appropriate in `hooks/`.
   Confirm with the reviewer whether a `stores/storeConfigStore.ts` (Zustand atom
   pre-fetched at app startup) would be preferable for avoiding per-component
   refetches.

6. **Assumption: `orders.ts` file name does not conflict with any existing file.**
   Confirmed by `ls frontend/src/api/endpoints/` [verified: no `orders.ts` in the
   ~180 files in that directory]. The nearest related file is `purchases.ts`, which
   targets a different URL namespace and is not renamed or merged.

7. **Open question: Should `CartPurchase.fulfillment_status` be added now
   or deferred to ECM-014?** Adding it in ECM-013 creates the field in the type
   before any backend endpoint returns it, which is forward-safe (optional field).
   Deferring it to ECM-014 keeps ECM-013 minimal. This spec adds it now (additive,
   zero-cost in TS) so ECM-014 can reference it without a types.ts diff in its own
   PR.
