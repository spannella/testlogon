## 1. Summary & Goal

POS-014 delivers the complete automated test coverage for the POS module:

1. **Hermetic offline pytest** (`tests/test_pos_*.py`) — no real AWS, no network,
   no FastAPI `TestClient` (which is broken in this repo). Uses moto in-memory
   DynamoDB tables bound to the frozen `T` / `S` handles via `object.__setattr__`,
   billing/charge collaborators patched at the source module level, and route
   handler coroutines called directly. Covers POS-004 through POS-010 in six
   focused test modules.

2. **Playwright E2E spec** (`frontend/e2e/pos.spec.ts`) — exercises the full
   open→scan→tender→receipt→close workflow against the live dev stack (`just up`),
   using the seeded admin/cashier session pattern from `e2e_admin_session_setup.py`
   with CSRF headers. Covers a cash sale with change, split tender, refund, and
   the `POS_ENABLED=0` flag-off case.

**Success criteria (from the ticket):**

- Pytest suite passes offline with no real AWS/network.
- Asserts: single order + single ledger entry per sale, refund-once idempotency,
  over/short math, total parity with the shoppingcart subtotal.
- E2E covers open→sale→receipt→close, split tender, refund, and flag-off.
- With `POS_ENABLED=0`, regression confirms existing shop/cart/order/billing tests
  are unaffected.

## 2. Context & Current State

### 2.1 Hermetic test isolation pattern (repo standard)

`tests/test_gap_0223_0224_ec2_host_inventory.py:74–128` is the canonical example
of this repo's hermetic test pattern:

- `mock_aws()` context manager from `moto` creates in-process DynamoDB.
- Both modules under test share a `SimpleNamespace` as a fake `T` object:
  `patch.object(module_a, "T", fake_T)` and `patch.object(module_b, "T", fake_T)`.
- `Settings` (`S`) is a frozen dataclass; flags are toggled with
  `object.__setattr__(S, "pos_enabled", True)` and restored in `tearDown`.
- No `TestClient`, no live `uvicorn`, no boto3 calls to real AWS.

The `test_gap_0206_0207_billing_gates.py:19` docstring explicitly states: "the
FastAPI TestClient is unusable here" — route handlers are called directly with
`asyncio.run(handler(...))` or `loop.run_until_complete(handler(...))`.

### 2.2 Flag-off isolation pattern

`tests/test_gap_0151_fan_club_feature_flag.py:38–43` shows how to test a
`_require_enabled()` guard directly (the fan-club guard raises **503**; the
returns/RMA guard raises **404** — POS uses 404, mirroring returns/RMA):

```python
def test_check_enabled_blocks_when_flag_off():
    _set_flag(False)
    with pytest.raises(HTTPException) as exc:
        fan_club._check_enabled()
    assert exc.value.status_code == 503  # fan-club raises 503; pos_register raises 404
```

POS follows the same `_require_enabled()` pattern from `pos_register.py`
(POS-004 spec §2.2, mirroring `app/services/returns_rma.py:71–73`
[`_flag_on` is at `:67–68`; `_require_enabled` itself is `:71–73`]). The
flag-off test calls `pos_register._require_enabled()` directly with
`S.pos_enabled=False` and asserts `HTTPException(404)` (same 404 as returns/RMA).

### 2.4 DynamoDB tables and keys (from POS-003 and POS-011 spec §3.1)

The `pos` single-table (PK `pos_pk`, SK `pos_sk`) carries:

| pos_pk | pos_sk | Row kind |
|---|---|---|
| `REGISTER#{register_id}` | `META` | Register config |
| `OPEN_SENTINEL#REGISTER#{register_id}` | `OPEN` | One-open guard |
| `SESSION#{session_id}` | `META` | Session / till |
| `TXN#{txn_id}` | `META` | Transaction draft |
| `SESSION#{session_id}` | `TENDER#{txn_id}#{seq:04d}` | Tender record |
| `SESSION#{session_id}` | `REFUND#{txn_id}#{seq:04d}` | Refund record |

GSIs (POS-011 spec §3.2): `GSI_REGISTER_OPEN` (`register_id` → `opened_at` N),
`GSI_CASHIER` (`cashier_sub` → `opened_at` N), `GSI_SESSION_TXN` (`session_id`
→ `created_at` N). All numeric sort keys must be declared in `attr_types` per the
CLAUDE.md DynamoDB gotcha; `scripts/local-ddb-init.py` encodes this via
`attr_types={"opened_at": "N", "created_at": "N"}` (POS-003 spec §3.4).

### 4.2 Shared test fixture pattern

Each test class extends `unittest.TestCase` with `@unittest.skipIf(mock_aws is None, ...)`.
`setUp` builds the `ExitStack`, enters `mock_aws()`, creates the moto tables, wires
`fake_T = SimpleNamespace(pos=pos_table, shopping_cart=cart_table, ...)`, patches
both the service module and any shared imports, then toggles `S.pos_enabled = True`
via `object.__setattr__`. `addCleanup(self._restore_settings)` restores all
`object.__setattr__` changes.

```python
# Canonical setUp skeleton (same shape as test_gap_0223_0224_ec2_host_inventory.py:76–114)
class TestPosSession(unittest.TestCase):
    def setUp(self):
        self.stack = ExitStack()
        self.addCleanup(self.stack.close)
        self.stack.enter_context(mock_aws())
        ddb = boto3.resource("dynamodb", region_name="us-east-1")
        self.pos_table = _make_pos_table(ddb)
        import app.services.pos_register as pr
        self.pr = pr
        self.S = pr.S
        fake_T = SimpleNamespace(pos=self.pos_table)
        self.stack.enter_context(patch.object(pr, "T", fake_T))
        self._orig = {"pos_enabled": self.S.pos_enabled}
        object.__setattr__(self.S, "pos_enabled", True)
        self.addCleanup(self._restore_settings)

    def _restore_settings(self):
        for k, v in self._orig.items():
            object.__setattr__(self.S, k, v)
```

### 4.3 Async handler invocation pattern

For tests that call route handlers directly (e.g. the flag-off test calling
`pos_register._require_enabled()`, or tender handlers that are async):

```python
import asyncio
loop = asyncio.new_event_loop()
self.addCleanup(loop.close)
result = loop.run_until_complete(handler_coro(...))
```

This mirrors `test_gap_0220_0221_ssh_stored_key.py` which drives WS handlers on
a fresh event loop.

## 5. Detailed Behavior & Edge Cases

### 5.1 `test_pos_session.py` — POS-004 coverage

**test_open_close_happy_path**
Calls `open_session(cashier_sub="alice", register_id="reg_001",
opening_float_cents=5000)`. Asserts session row written (`pos_pk=SESSION#...`,
`status="open"`, `opening_float_cents=5000`, `opened_at` numeric). Then calls
`close_session(session_id, counted_cash_cents=5000)` with no cash tenders yet.
Asserts `expected_cash_cents = 5000` (no movement), `over_short_cents = 0`,
`status="closed"`.

**test_double_open_409**
Opens session on `reg_001`, then tries to open again on the same register.
Asserts `HTTPException(409)`. The sentinel row at `OPEN_SENTINEL#REGISTER#{id}`
/ `OPEN` must be present and the conditional put must raise
`ConditionalCheckFailedException` which the service converts to 409.

**test_close_already_closed_409**
Opens then closes a session, then tries to close again. Asserts 409.

**test_over_short_math**
Opens with float 10000, records two mock cash tender rows in the `pos` table
(total cash_in=15000, change_out=3000), then calls `close_session(counted=14000)`.
Expected = `opening_float + cash_in − change_out` = 10000 + 15000 − 3000 = 22000.
over_short = counted − expected = 14000 − 22000 = −8000. Asserts those exact
integer values on the returned session.

**test_audit_events_emitted**
Patches `pos_register._audit` (the fire-and-forget wrapper around
`alerts.audit_event`). Asserts it is called with `event="pos_session_opened"` on
open and `event="pos_session_closed"` on close.

**test_flag_off_raises_404**
`object.__setattr__(S, "pos_enabled", False)`. Calls
`pos_register._require_enabled()`. Asserts `HTTPException(404)`.

### 5.2 `test_pos_cart.py` — POS-005 coverage

**test_bind_returns_same_cart_on_replay**

**test_unknown_sku_404**

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/prod parity

The POS services (POS-004 through POS-010) are designed with zero `S.dev_mode`
branches in money paths — the same `billing_shared.new_ledger_entry`,
`purchase_cart`, and `refund_payment` paths run in both dev and prod (SECOPS-007
parity). The test suite validates this: no test checks that a code path diverges
based on `S.dev_mode`. Any test that would need to pass a `dev_mode` condition
to get a different result is a spec violation and must be raised as a bug.

POS-014 tests cover the prod-equivalent path. The dev moto in-process DynamoDB
is the same code path as real DynamoDB — no mock-vs-real forking in the services.

### 7.2 Idempotency

Three layers of idempotency are exercised:

1. **Cart purchase replay** — `purchase_cart` at `app/services/shoppingcart.py:474`
   (function definition); idempotency early-return at `:483–492` ✓ — returns the
   existing result on second call for an already-`PURCHASED` cart.
   `test_cash_idempotency` in `test_pos_cash_tender.py` verifies this by calling
   `tender_cash` twice with the same `idempotency_key` and asserting
   `purchase_cart` is called exactly once.

2. **Refund idempotency** — `refund_transaction` derives its refund row key from
   `sha256(f"pos_refund:{txn_id}:{reason}")` (deterministic ID, same pattern as
   `app/services/commerce_order_service.py:67` ✓ which uses `sha256(correlation_id)[:32]`).
   A `ConditionExpression=attribute_not_exists(pos_pk)` on the refund row write
   prevents double-refund. `test_refund_idempotency` verifies the second call
   returns the same result without a second ledger write.

3. **Session open idempotency** — `open_session` with the same `idempotency_key`
   returns the existing session (the `SESSION#.../META` row's PK is derived from
   the key). `test_bind_returns_same_cart_on_replay` in `test_pos_cart.py`
   covers the transaction-draft level.

### 7.3 Security

- All tests that call router handlers check that `pos_register._require_enabled()`
  raises 404 when `S.pos_enabled=False`.
- `test_pos_void_refund.py:test_void_settled_txn_409` verifies that post-settlement
  void is blocked (money has moved; must use refund path).
- Over/short math is integer arithmetic only (no float) — `test_over_short_math`
  asserts exact cent values, covering the integer contract.
- The E2E spec verifies the cashier ownership check: a request with `alice`'s
  session token against `charlie_admin`'s POS session returns 403.

## 10. Open Questions / Assumptions

1. **Assumption: `pos_tender.py` exports a single `tender(...)` dispatcher.**
   POS-011 spec §10.3 notes it may be a unified function or separate
   `tender_cash`/`tender_card`/`tender_wallet`. Tests use `patch.object` targeted
   at the actual function names; if the implementation ships separate functions,
   each test calls the appropriate one.

2. **Assumption: `void_transaction` uses a cart-cancel/cart-release helper from
   `shoppingcart.py`.** The exact function name (`cancel_cart`, `release_cart`,
   etc.) is not yet defined in this repo. Tests patch whichever release primitive
   the POS-008 implementation uses. If POS-008 uses `T.shopping_cart.update_item`
   directly, the test patches `pos_tender.T.shopping_cart.update_item` instead.

3. **Assumption: refund idempotency key is `sha256(f"pos_refund:{txn_id}:{reason}")`.**
   The POS-008 spec does not finalize the key derivation scheme. The test
   `test_refund_idempotency` will need to be updated if POS-008 uses a different
   correlation key. The key property being tested (second call returns same result
   with no second DB write) is stable regardless of the key scheme.

4. **Assumption: `S.inventory_reservations_enabled` controls restock on refund.**
   POS-008 spec §1 gates restock on `S.inventory_reservations_enabled`. If the
   implementation uses a dedicated `S.pos_restock_on_refund` flag instead, the
   tests toggle that flag name.

5. **Assumption: Z report closes the session implicitly or requires the session
   to already be closed by `close_session`.** POS-010 spec §1 states "callable
   only on a closed session". The test `test_z_report_requires_closed_session_409`
   verifies this precondition. If the implementation calls `close_session`
   internally as a side effect, the test is adjusted accordingly.

6. **Assumption: `session_report` queries `GSI_SESSION_TXN` (not scans).**
   POS-010 spec §1 mandates GSI-based aggregation ("don't scan; query the GSI").
   The hermetic test validates this indirectly: moto does not enforce index
   consistency the same way real DynamoDB does under concurrent writes, but the
   test seeds rows with the `session_id` + `created_at` attributes required by
   the GSI so the query returns them correctly. A direct assertion that
   `T.pos.scan` is never called (via spy) would be a stronger test if desired.

7. **Open: flag-off E2E requires a backend with `POS_ENABLED=0`.** Section 806
   cannot run against the default dev stack. It is marked with a
   `test.skip("requires POS_ENABLED=0 restart")` guard and run in a separate
   CI step. The ticket should confirm whether this is run automatically or
   manually.

8. **Open: catalog item seeding in E2E.** Section 802 seeds a catalog item via
   the catalog API. The catalog API requires admin/root role. The spec uses the
   `root` identity for seeding. If the test catalog item was created in a
   previous run, an idempotent upsert (PATCH or ignore 409) must be used.

**Decision D-1 (PLAN_GAP):** Which implementation ticket is responsible for adding `pos_default_tax_rate_bps: int` to `app/core/settings.py`? POS-003 spec §6.1 omits it; POS-001 is a design-only spike; no other spec currently owns it. Either POS-003 must be updated to include this fourth setting, or a dedicated ticket must be created. Until resolved, any POS service that reads `S.pos_default_tax_rate_bps` (POS-005 total parity, POS-007 tax at settlement, POS-009 receipt rendering) will fail with `AttributeError` at runtime.
