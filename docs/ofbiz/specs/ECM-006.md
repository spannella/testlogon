# ECM-006 — Catalog router — surface variants & availability (flag-gated)

**Type:** Feature | **Priority:** P0 | **Estimate:** 2 days
**Dependencies:** ECM-004 (variant-aware catalog read service), ECM-005 (live availability projection)

---

## 1. Summary & Goal

ECM-006 wires the two services introduced by ECM-004 and ECM-005 into the three active catalog read paths so that every browse, search, and per-item detail response carries `variants` and `availability` fields when `STORE_INTEGRATION_ENABLED` is on. It also adds the missing `GET /ui/catalog/categories/{category_id}/items/{item_id}` endpoint that `ProductDetail.tsx` needs to fetch a single item efficiently (the page currently resolves items client-side by fetching the whole category list).

With `STORE_INTEGRATION_ENABLED` off (or any upstream sub-flag off), every response is byte-for-byte identical to the current shape. No existing endpoints are renamed, removed, or re-parameterised. No new routers are created, and no DynamoDB writes occur in this ticket.

The concrete deliverables are:

1. **`list_items` enrichment** — after assembling `out: List[CatalogItemOut]`, call `enrich_catalog_item` (ECM-004) per item when `STORE_VARIANT_SELECTION_ENABLED` is on, then call `_apply_live_availability` (ECM-005) when `STORE_SHOW_LIVE_AVAILABILITY` is on, handling both flags independently so each can be enabled or disabled separately.
2. **`search_items` enrichment** — same enrichment block applied to `matches` at the end of the scan loop.
3. **New `GET /ui/catalog/categories/{category_id}/items/{item_id}`** — a dedicated single-item read, enriched identically to the list path, so `ProductDetail.tsx` can request a single item without fetching the full category page. This endpoint is the "per-item read used by ProductDetail" referred to in the ticket description and in `docs/ofbiz/specs/ECM-005.md:220`.
4. **Batch variant enrichment** — `list_items` and `search_items` collect variant SKUs from ECM-004's output and pass the full SKU set to `availability_for_skus` in a single `BatchGetItem` call rather than one call per item, keeping per-page latency bounded.

## 2. Context & Current State

### 2.1 The three catalog read paths today

`app/routers/catalog.py:394–418` defines `list_items` (`GET /ui/catalog/categories/{category_id}/items`). It calls `_query_page` to retrieve a DynamoDB page keyed `CAT#{category_id}` / `ITEM#*`, applies the geo-block filter at `catalog.py:413`, sorts by position at `catalog.py:417`, and returns `CatalogItemListOut`. Every item is converted via `_catalog_item_out(item)` at `catalog.py:415`. — VERIFIED `catalog.py:394–418`.

`app/routers/catalog.py:465–498` defines `search_items` (`GET /ui/catalog/items/search`). It scans `T.catalog` in pages of 200 items, applies the geo-block filter at `catalog.py:488`, calls `_catalog_matches` for text matching, and converts matches with `_catalog_item_out(item)` at `catalog.py:491`. — VERIFIED `catalog.py:465–498`.

There is no dedicated `GET /ui/catalog/categories/{category_id}/items/{item_id}` endpoint — VERIFIED: `@router.get` routes in `catalog.py` are `categories`, `items/search`, `images`, `items/{item_id}/reviews` only. The `ProductDetail.tsx` page at `frontend/src/pages/shop/ProductDetail.tsx:62–70` fetches the full category item list via `getCategoryItems(categoryId!)` (`frontend/src/api/endpoints/cart.ts:69`) and then finds the target item client-side at `ProductDetail.tsx:68–70`: `(itemsQuery.data?.items ?? []).find(i => i.item_id === itemId)`. This works today because categories are small, but it becomes expensive when ECM-004 variant enrichment adds per-item upstream calls — fetching 50 enriched items to display one is wasteful.

### 2.2 `_catalog_item_out` is the current conversion point

`app/routers/catalog.py:107–127` defines `_catalog_item_out(item: dict) -> CatalogItemOut`. It reads a raw DynamoDB dict and constructs the scalar `CatalogItemOut` (`app/models.py:672–688`). — VERIFIED: function at `catalog.py:107`, model at `models.py:672`. This function is also called from `update_item` (PATCH at `catalog.py:588`) and the image upload handler (`catalog.py:634`). — VERIFIED: `return _catalog_item_out(item)` at `catalog.py:588` and `catalog.py:634`. ECM-006 does not modify `_catalog_item_out` — enrichment is a post-construction layer applied at the read-endpoint call sites only, consistent with the ECM-005 spec decision at `docs/ofbiz/specs/ECM-005.md:190` ("The helper remains pure and reads only the raw DDB item dict").

### 2.3 ECM-004 enrichment contract

ECM-004 (`docs/ofbiz/specs/ECM-004.md:118–131, 174–190`) adds `enrich_catalog_item(item: dict, *, viewer: dict) -> CatalogItemOut` to `app/services/store_integration.py`. The first argument is the **raw DynamoDB dict** (same dict `_catalog_item_out` receives at `catalog.py:107`), **not** a `CatalogItemOut`. `viewer` is the **full session dict** from `require_ui_session` (carrying `user_sub`, `role`, etc.), **not** a bare string. When `STORE_VARIANT_SELECTION_ENABLED` is on and the item has `product_type == "virtual"`, it calls `product_variants.list_variants(parent_item_id)` (using `item.get("item_id")`) and returns a `CatalogItemOut` with `variants: List[StorefrontVariantOut]` populated via `model_copy`. When the flag is off, the product is not virtual, or the upstream call fails (via `_safe_upstream`), it returns the scalar `CatalogItemOut` that `_catalog_item_out_local(item)` produces (a lazy-import wrapper around `catalog.py:_catalog_item_out`). `StorefrontVariantOut.availability` is always `None` from ECM-004; ECM-005 / ECM-006 populate it in a subsequent pass.

### 2.4 ECM-005 enrichment contract

ECM-005 (`docs/ofbiz/specs/ECM-005.md:16–18`) adds `availability_for_skus(skus, location_id) -> Dict[str, StorefrontAvailabilityOut]` and `_apply_live_availability(item_out, avail_map) -> CatalogItemOut` to `app/services/store_integration.py`. `availability_for_skus` issues a single `BatchGetItem` against `T.inventory`, chunked at 100 SKUs. `_apply_live_availability` rebinds `stock_status`, `stock_count`, and `availability` on a `CatalogItemOut` from the availability map; if the SKU is absent from the map it returns the input unchanged. Both functions already handle the sub-flag gate internally via `_integration_enabled("store_show_live_availability")`.

### 2.5 SKU resolution for variants

When ECM-004's enrichment runs, `CatalogItemOut.variants` contains `StorefrontVariantOut` objects each carrying a `sku` field (the inventory key for that variant). For the availability batch call, ECM-006 must collect SKUs from variants rather than using `item_out.item_id`. For flat (non-virtual) items, `variants` is `None` or empty, and `item_out.item_id` is used as the SKU (per `docs/ofbiz/specs/ECM-005.md:80–82` design decision — **CORRECTED**: `shoppingcart.py:315` reads a caller-provided `sku`; the cart-add convenience path at `shoppingcart.py:391` constructs `sku = f"catalog:{item_id}"`, not bare `item_id`. ECM-005 explicitly notes at §2.5 that `item_id` as the inventory SKU namespace is a **design decision, not an existing enforced convention** — merchants register inventory rows with whatever `sku` they choose. `availability_for_skus` will return an empty map if inventory rows are keyed differently, falling through to the degrade path).

### 2.6 Existing models to be extended

`CatalogItemOut` (`app/models.py:672`) gains two additive optional fields from ECM-003: `variants: Optional[List[StorefrontVariantOut]] = None` and `availability: Optional[StorefrontAvailabilityOut] = None`. **Neither field exists in the current model** (`models.py:672–688` is a 16-field scalar — VERIFIED). `CatalogItemListOut` (`app/models.py:691`) inherits from `CatalogPageOut` (`models.py:516`) and contains `items: List[CatalogItemOut]` — VERIFIED `models.py:691–692`; it requires no change. ### 2.7 `_integration_enabled` gate

`app/services/store_integration.py` (created by ECM-002) provides `_integration_enabled(sub_flag=None)` which AND-combines `S.store_integration_enabled` with the named sub-flag. ECM-002 defines a `_SUB_FLAG_ATTRS` dict (`docs/ofbiz/specs/ECM-002.md:136–141`) that maps **short alias keys** to Settings attribute names: `"variant_selection"` → `store_variant_selection_enabled`, `"live_availability"` → `store_show_live_availability`. ECM-006 must call `_integration_enabled("variant_selection")` and `_integration_enabled("live_availability")` respectively.

### 4.2 Enrichment helper `_enrich_item_list`

To avoid repeating the identical four-line enrichment block in three places, introduce a module-level helper in `app/routers/catalog.py`:

```python
def _enrich_item_list(
    raw_items: List[dict],
    viewer_ctx: dict,
) -> List[CatalogItemOut]:
    """Apply ECM-004 variant + ECM-005 live-availability enrichment when flags are on.

    raw_items:   list of raw DynamoDB dicts (the same dicts _catalog_item_out receives).
    viewer_ctx:  the full session dict from require_ui_session (ctx), passed to
                 enrich_catalog_item as viewer=viewer_ctx per ECM-004's signature.

    Called from list_items, search_items, and get_item_detail (which wraps its single
    raw dict in a one-element list).
    When both flags are off, returns CatalogItemOut objects built by _catalog_item_out
    unchanged (zero enrichment overhead).
    """
    # ECM-004 variant enrichment (per-item, upstream PRD-007 service call).
    # NOTE: _integration_enabled uses short alias "variant_selection", NOT the full
    # settings attribute name (ECM-002 _SUB_FLAG_ATTRS maps "variant_selection" →
    # store_variant_selection_enabled; passing the full name returns False).
    if _si._integration_enabled("variant_selection"):
        items: List[CatalogItemOut] = [
            _si._safe_upstream(
                lambda raw=raw: _si.enrich_catalog_item(raw, viewer=viewer_ctx),
                _catalog_item_out(raw),
            )
            for raw in raw_items
        ]
    else:
        items = [_catalog_item_out(raw) for raw in raw_items]
    # ECM-005 live availability enrichment (batch BatchGetItem on T.inventory).
    # NOTE: short alias "live_availability" required (ECM-002 _SUB_FLAG_ATTRS).
    if _si._integration_enabled("live_availability"):
        # Collect SKUs: use each variant's sku when variants are populated,
        # else fall back to item_id (the flat-item convention).
        skus: List[str] = []
        for item in items:
            if item.variants:
                skus.extend(v.sku for v in item.variants)
            else:
                skus.append(item.item_id)
        avail_map = _si._safe_upstream(
            lambda: _si.availability_for_skus(skus),
            default={},
        )
        # For variant items, patch availability onto each StorefrontVariantOut;
        # for flat items, patch stock_status/stock_count/availability onto the item itself.
        enriched: List[CatalogItemOut] = []
        for item in items:
            if item.variants:
                new_variants = [
                    v.model_copy(update={"availability": avail_map.get(v.sku)})
                    for v in item.variants
                ]
                item = item.model_copy(update={"variants": new_variants})
            else:
                item = _si._apply_live_availability(item, avail_map)
            enriched.append(item)
        items = enriched
    return items
```

`lambda raw=raw: ...` (default-argument capture) is required inside the list comprehension to avoid the classic Python late-binding closure bug over `raw`.

### 4.5 New endpoint `GET /ui/catalog/categories/{category_id}/items/{item_id}`

```python
@router.get(
    "/categories/{category_id}/items/{item_id}",
    response_model=CatalogItemOut,
)
async def get_item_detail(
    category_id: str,
    item_id: str,
    request: Request,
    ctx=Depends(require_ui_session),
) -> CatalogItemOut:
    """Fetch a single catalog item by category + item_id.

    Added by ECM-006 to support ProductDetail.tsx's per-item read without
    fetching the entire category page. Auth: require_ui_session (same as
    list_items). Geo-block and subscription gate enforced as in list_items.
    Returns 404 if the item does not exist in this category.
    Enriches with variants + live availability when integration flags are on.
    """
    # Subscription gate: mirror list_items behavior
    category = _get_category_meta(category_id)
    creator_id = category.get("creator_id")
    if creator_id and not can_access_creator(ctx["user_sub"], creator_id):
        raise HTTPException(status_code=403, detail="Subscription required to view this catalog.")

    # Fetch the specific item using the existing PK/SK schema
    resp = T.catalog.get_item(Key={"PK": cat_pk(category_id), "SK": item_sk(item_id)})
    raw = resp.get("Item")
    if not raw or raw.get("entity") != "item":
        raise HTTPException(status_code=404, detail="Item not found.")

    # Geo-block check (GEO-001, mirrors list_items:413)
    if _item_geo_blocked(request, raw):
        raise HTTPException(status_code=403, detail="This item is not available in your region.")

    # Pass raw dict directly to _enrich_item_list (which calls enrich_catalog_item
    # with the raw dict and ctx as required by ECM-004's signature).
    [enriched] = _enrich_item_list([raw], ctx)
    return enriched
```

**Route ordering note**: This route must be declared AFTER `GET /categories/{category_id}/items` (the list route at `catalog.py:394`) and before `PATCH /categories/{category_id}/items/{item_id}` (the update route at `catalog.py:519`). FastAPI matches routes in declaration order; a GET with two path segments (`{category_id}/items/{item_id}`) would only clash with a hypothetical GET at the same pattern, which does not exist today.

**Auth**: `Depends(require_ui_session)` — the same dependency as `list_items`, `search_items`, and `update_item`. No new auth dependency.

**DDB read**: A single `get_item` using the table's primary key `PK=CAT#{category_id}`, `SK=ITEM#{item_id}`. This is O(1) and returns exactly one row. It does NOT use `_find_item_by_id` (which uses the `ByItemId` GSI) because we already have both `category_id` and `item_id`, making the base-table lookup cheaper.

**Response model**: `CatalogItemOut`, the same Pydantic model returned by `_catalog_item_out`. When enrichment flags are off, the output is identical to a single element from `list_items`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag combinations

| `STORE_INTEGRATION_ENABLED` | `STORE_VARIANT_SELECTION_ENABLED` | `STORE_SHOW_LIVE_AVAILABILITY` | Result |
|---|---|---|---|
| off | any | any | `_enrich_item_list` returns input unchanged; response is byte-for-byte current shape |
| on | off | off | No enrichment; same as flag-off |
| on | on | off | `variants` populated on virtual items; `availability` is `null` everywhere |
| on | off | on | `stock_status`/`stock_count`/`availability` overwritten from inventory; no `variants` |
| on | on | on | Variants populated; per-variant `availability` populated; flat-item `availability` populated |

`_integration_enabled` gates each block independently via `_SUB_FLAG_ATTRS` lookup + `getattr(S, attr, False)` (ECM-002 `docs/ofbiz/specs/ECM-002.md:136–162`), so each sub-flag can be toggled without affecting the other.

### 5.2 Flat (non-virtual) item with live availability

ECM-004 returns the item unchanged (`variants = None`). `_enrich_item_list` takes the `else` branch and calls `_apply_live_availability(item, avail_map)` using `item.item_id` as the SKU key. The response carries `availability: StorefrontAvailabilityOut` and overwritten `stock_status`/`stock_count`; `variants` remains `null`.

### 5.3 Virtual item with two variants, both in stock

ECM-004 attaches `variants = [v1, v2]` each with their own `sku`. `_enrich_item_list` collects `[v1.sku, v2.sku]` for the batch call. `avail_map` returns entries for both. Each `StorefrontVariantOut` is rebuilt with `.model_copy(update={"availability": avail_map[v.sku]})`. The parent `CatalogItemOut.availability` remains `null` (it is not meaningful for virtual items; ECM-007 will drive the Add-to-Cart state from the selected variant's availability). The parent `stock_status` remains the static value from `_compute_stock_status`; ECM-007 overrides this client-side based on the selected variant.

### 5.4 Virtual item with one variant out of stock

Only one variant's `availability.stock_status` is `"out_of_stock"`. The other variant may still be in stock. The parent item's `stock_status` remains unchanged (`"in_stock"` or `"unlimited"`). ECM-007 handles the Add-to-Cart disable logic per selected variant, not at browse-grid level.

### 5.5 Inventory service unavailable (degrade)

`_safe_upstream(lambda: _si.availability_for_skus(skus), default={})` catches any exception and returns `{}`. `_apply_live_availability(item, {})` finds no SKU in the map and returns `item_out` unchanged. The response carries the static `stock_count`/`stock_status` from the catalog DDB item — the same values as with the flag off. No 500 is propagated to the client.

### 5.6 PRD-007 variant service unavailable (degrade)

`_safe_upstream(lambda raw=raw: _si.enrich_catalog_item(raw, viewer=viewer_ctx), _catalog_item_out(raw))` catches any exception and returns the scalar `CatalogItemOut` (built from the raw dict). The response carries `variants = null`, indistinguishable from a flat item. The browse grid and ProductDetail render as today.

### 5.7 `get_item_detail` — item exists in a different category

The endpoint uses `PK = CAT#{category_id}` and `SK = ITEM#{item_id}`. If the item_id belongs to a different category, the `get_item` call returns no item and the handler raises 404. This is the correct behavior — the URL structure couples item reads to their owning category, consistent with how `list_items` works.

### 5.8 `get_item_detail` — geo-blocked item

When `_item_geo_blocked(request, raw)` returns `True`, the handler raises HTTP 403 (matching the geo-block semantics specified in `catalog.py:130–146`). Note that `list_items` silently drops geo-blocked items (`continue`) rather than 403-ing because it returns a list; `get_item_detail` returns a scalar so 403 is the appropriate signal.

### 5.9 Pagination unchanged

`list_items` and `search_items` pagination parameters (`page_size`, `next_token`, `encode_next_token`, `decode_next_token`) are not modified. Enrichment runs after the page is assembled and does not affect `LastEvaluatedKey` logic. The `next_token` in the response continues to represent the DynamoDB pagination cursor into `T.catalog`, not into `T.inventory`.

### 5.10 Position sort unchanged

`list_items` sorts `out` by `position` at `catalog.py:417` before the enrichment call. Enrichment does not reorder items; it only mutates individual `CatalogItemOut` objects in place via `model_copy`. The sort is preserved.

### 5.11 `_enrich_item_list` called with empty list

If a category has zero items (or all are geo-blocked), `items = []`. Both the ECM-004 list comprehension and the ECM-005 `BatchGetItem` call are skipped (`skus = []` → no `BatchGetItem` issued). Returns `[]` immediately.

### 5.12 SKU list deduplication for BatchGetItem

`T.inventory`'s `BatchGetItem` requires each key to appear at most once. If multiple variants share a SKU (not valid per PRD-007's deterministic-id design, but defensive), or if two catalog items happen to share an `item_id` (also invalid), the `availability_for_skus` function (owned by ECM-005) is responsible for deduplicating. ECM-006 passes SKUs as collected; ECM-005's spec states it deduplicates: "Deduplicate `skus` and filter empty strings" (`docs/ofbiz/specs/ECM-005.md:138`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity**: All paths in `_enrich_item_list` and `get_item_detail` are identical in dev (moto DDB, mock PRD service, `T.inventory` and `T.catalog` backed by DynamoDB Local at port 8001) and prod (real DDB). There is no `if S.dev_mode` branch. The `_safe_upstream` wrapper ensures upstream service unavailability degrades gracefully in both environments.

**Idempotency**: `GET` endpoints are inherently idempotent. ECM-006 introduces no writes.

**No new auth surface**: `get_item_detail` uses the same `require_ui_session` dependency as all other catalog read endpoints. The subscription gate (`can_access_creator`) and geo-block check are applied before any item data is returned — neither check is omitted for the single-item path. This mirrors `list_items`'s auth checks at `catalog.py:402–405` and `catalog.py:413`.

**Geo-block surfacing**: `get_item_detail` raises HTTP 403 for geo-blocked items rather than silently dropping them (as `list_items` does). This is the correct behavior for a scalar read and does not leak information beyond what a 404 would (the category lookup succeeds before the geo check, so a 404 here would require a separate endpoint call to verify category existence).

**No billing interaction**: ECM-006 is read-only. No ledger entries, no `new_ledger_entry` calls, no `refund_payment` calls. The GL is not touched.

**Upstream error containment**: `_safe_upstream` swallows all exceptions from ECM-004 and ECM-005 service calls with WARNING-level logging. A degraded response (no variants, static stock count) is returned rather than a 500. This aligns with the project's pattern for best-effort enrichment (see `app/services/ssh_key_manager.py:29–41` `_audit`, and `app/services/newsfeed_recsys.py:178–205`).

## 8. Backward Compatibility & Migration

### 8.1 Existing endpoint behavior

`GET /ui/catalog/categories/{category_id}/items` and `GET /ui/catalog/items/search` keep their exact request signatures (same query parameters, same auth). With `STORE_INTEGRATION_ENABLED=false` (the default), responses are byte-for-byte identical to pre-ECM-006 responses. The `variants` and `availability` fields added to `CatalogItemOut` by ECM-003 serialise as `null` (FastAPI includes `null` for `Optional` fields by default); they were already present in the schema but null-valued from ECM-003 onwards.

### 8.2 Frontend `CatalogItem` type

The two new optional fields (`variants?: StorefrontVariant[] | null`, `availability?: StorefrontAvailability | null`) are additive. Existing consumer code that reads `item.stock_status` or `item.stock_count` continues to work unchanged because those fields are still present on every response. The frontend does not need to be updated to handle the new fields until ECM-007 is implemented.

### 8.3 New `GET /ui/catalog/categories/{category_id}/items/{item_id}` endpoint

This is a net-new endpoint. No existing code calls it. It is registered after the existing category-items list route in `app/routers/catalog.py`, so FastAPI's route precedence is unambiguous. The `ProductDetail.tsx` page will not call it until ECM-007 migrates it from `getCategoryItems` to `getCatalogItem`; until then, the endpoint exists but is unused by the frontend.

### 8.4 No DynamoDB migration required

No table schema changes. No backfill. The `T.catalog` item rows may or may not carry `product_type`; those without it are treated as standalone (flat) items by ECM-004, which is already the pre-ECM-006 behavior.

## 10. Open Questions / Assumptions

1. **`get_item_detail` geo-block response code**: This spec raises HTTP 403 for geo-blocked items. The alternative is 404 (to avoid leaking item existence). The current `list_items` silently drops geo-blocked items (returning a shorter list without signaling the omission). For a scalar GET, 403 is more informative and is used by other geo-check endpoints in this codebase (`check_geo_access` raises 403 per `app/services/geo_check.py`). **Assumption**: 403 is correct; change to 404 if the security posture requires hiding item existence.

2. **Parent `CatalogItemOut.stock_status` for virtual items**: When a virtual item has variants, each variant carries its own `availability`. The parent's `stock_status` is left as the static `_compute_stock_status` result (from the catalog `stock_count` scalar). ECM-007 and the browse-grid badge will need to decide whether to show the parent's status or derive it from all-variants-out-of-stock. **Assumption**: ECM-006 makes no opinion; this is ECM-007's design concern.

3. **`enrich_catalog_item` is synchronous vs. async**: The ECM-004 spec shows a synchronous function signature. If PRD-007 calls are async (e.g., if `product_variants.list_variants` is `async`), the `lambda` in `_enrich_item_list` would need to be an `await`-able coroutine and `_enrich_item_list` itself would need to be `async`. **Assumption**: ECM-004 implements `enrich_catalog_item` as a synchronous function (matching `docs/ofbiz/specs/ECM-004.md`'s function signature), callable from within a sync list comprehension. If ECM-004 ships as `async`, ECM-006 must be updated to `await asyncio.gather(...)` across items. — **VERIFIED (pass 3)**: ECM-004.md:134 explicitly states "The function is **synchronous** because `list_variants` (PRD-007) is a synchronous DynamoDB call."

4. **Batch variant SKU collection order for `availability_for_skus`**: `_enrich_item_list` collects variant SKUs in item-iteration order. The `availability_for_skus` BatchGetItem response is unordered (DynamoDB does not guarantee order). **Assumption**: the `avail_map` keyed by SKU is order-independent, which is how ECM-005's function returns it. No ordering dependency exists. — **VERIFIED (pass 3)**: ECM-005.md:129–156 defines `availability_for_skus` as returning `Dict[str, StorefrontAvailabilityOut]` keyed by sku; consumers call `avail_map.get(v.sku)` (a dict lookup), which is inherently order-independent.

5. **`_enrich_item_list` as a module-level function vs. inline**: This spec introduces `_enrich_item_list` as a reusable helper to avoid three-way duplication. An alternative is to inline the block at each call site. **Assumption**: the helper is preferable for maintainability; its presence in `catalog.py` at module level (not inside a class) is consistent with `_catalog_item_out`, `_compute_stock_status`, and other helpers in the same file.

6. **`_safe_upstream` lambda default-argument capture**: The corrected spec uses `lambda raw=raw: _si.enrich_catalog_item(raw, viewer=viewer_ctx)` to capture `raw` correctly in the list comprehension. Python's closure semantics require this default-argument trick. **Assumption**: this pattern is correct per the existing `app/services/newsfeed_recsys.py` lambda usage; the reviewer should confirm. — **VERIFIED (pass 3)**: `app/routers/newsfeed.py:2481` uses the identical pattern `lambda r=receipt: sqs.delete_message(...)` inside a loop; the default-argument capture technique is already established in this codebase.

7. **No `exclude_none` on response model**: FastAPI serialises `None` optional fields as `null` in JSON. With integration off, `variants: null` and `availability: null` will appear in the response JSON. This is a minor wire-format change from pre-ECM-003 responses (which had no such keys). **Assumption**: this is acceptable; ECM-003 already introduced these fields to the schema and downstream consumers must tolerate `null` optional fields per standard JSON API conventions. — **VERIFIED (pass 3)**: ECM-003.md:76 explicitly states "they serialise as `null` unless the router sets `exclude_none=True`, which is fine for optional enrichment" — confirming the null-in-JSON behavior is by design.
