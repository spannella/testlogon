# MFG-001 — Manufacturing/MRP scoping spike & inventory-integration delta

## 1. Summary & Goal

MFG-001 is the foundational design spike for the OFBiz Manufacturing/MRP work stream. It produces a precise, code-grounded specification covering:

1. The mapping of OFBiz Manufacturing entities (BOM/ProductBom, RoutingTask/WorkEffort, MrpEvent/requirements) onto the existing inventory foundation.
2. A pinned integration contract: how production runs issue components and receive finished goods exclusively through the existing `inventory.adjust` primitive — introducing no new stock store.
3. The schema for four new DynamoDB tables (`mfg_boms`, `mfg_work_centers`, `mfg_work_orders`, `mfg_mrp`), the settings keys, the master feature flag, and the lite-MRP net-requirement formula.
4. Explicit deferral decisions: phantom sub-assemblies beyond depth 5, finite-capacity scheduling, backflush variance accounting beyond a single GL hook, and co-product/by-product yields.

This document is the authoritative reference for MFG-002 through MFG-014. No runnable code is shipped here; the deliverable is this specification and the confirmation that no billing/money path is forked.

### 2.1 Existing flag-gated OFBiz modules

The `reservations` table uses `PK=reservation_pk (RES#{reservation_id})`, `SK=META`, with `GSI_SKU` (partition `sku`, numeric sort `created_at`) and `GSI_EXPIRY` (partition `gsi_expiry_pk`, numeric sort `expires_at`), both declared with `attr_types={"created_at": "N", "expires_at": "N"}`.

**Returns / RMA** (`app/services/returns_rma.py`) is gated by `S.returns_rma_enabled` (`app/core/settings.py:846`). Same `_require_enabled` pattern at `returns_rma.py:71–73`. Table `returns` declared at `scripts/local-ddb-init.py:2483`. Handle wired at `app/core/tables.py:319` as `T.returns`.

The `Tables` frozen dataclass (`app/core/tables.py:68`) declares fields at lines `:317–319`; the singleton `T` at `:321` binds each handle via `_safe_table(S.<name>)` at `:569–571`. New fields must be added to the dataclass declaration AND the `T = Tables(...)` constructor call.

### 2.2 The inventory adjust primitive — the integration contract anchor

`inventory.adjust(sku, delta, reason, *, location_id, user_sub)` at `app/services/inventory.py:209` is the single authoritative mutation for on-hand stock changes. It uses an optimistic conditional update (`on_hand = :exp_oh AND reserved = :exp_res`) with a retry-on-conflict loop (`:282–285`), recomputes `available = on_hand - reserved`, and enforces that `available` cannot go negative (`available < 0` → 409 at `:256–260`). Every call emits an `_audit` event (`:289–298`).

The soft-reservation path (`reserve` at `:339`, `commit_reservation` at `:456`) is a higher-level lifecycle for customer checkout. For manufacturing, components should be issued via `adjust(component_sku, -qty, reason="mfg_issue")` directly — not reserve/commit — because a production order represents a concrete consumption commitment, not a tentative hold. The reserved quantity remains on `reserved` for customer-facing carts; manufacturing issues reduce `on_hand` directly once the work order is released.

The produce path is `adjust(fg_sku, +qty, reason="mfg_produce")` — the same primitive the Returns/RMA service uses for restock at `app/services/returns_rma.py` (which calls `adjust` after a return is accepted). Finished goods produced by a work order land in the existing `inventory` record, recompute `available`, and surface immediately in the `GSI_AVAILABLE` low-stock index and the catalog stock mirror. No new stock ledger or write path is introduced.

### 2.3 Deterministic-id idempotency pattern

`commerce_order_service.CommerceOrderService.create_order` derives `order_id = hashlib.sha256(corr.encode("utf-8")).hexdigest()[:32]` at `app/services/commerce_order_service.py:67`. All new manufacturing entity IDs (`bom_id`, `work_order_id`, `mrp_run_id`) must follow the same pattern: `sha256(correlation_id)[:32]`. This ensures that callers who retry with the same correlation string do not create duplicate records.

### 2.4 Single-table header+line pattern

`create_order` at `commerce_order_service.py:85` writes a header row with `put_item`, then loops over line items writing one row per line into `T.order_items` (`:88–103`). The BOM and work-order tables mirror this: one header row (`SK=META`) plus N component/event rows (`SK=COMP#{seq}` / `SK=ISSUE#{n}` / `SK=EVENT#{ts}`) within the same partition.

### 2.5 Billing ledger — the GL hook anchor

`billing_shared.new_ledger_entry` at `app/services/billing_shared.py:224` is the single authoritative ledger-entry factory. It writes a row with `key_name`/`key_value`, `entry_id`, `ts`, `type`, `amount_cents`, `state`, `reason`, and `ledger_date` (so rows appear in `GSI_LEDGER_DATE` for platform-financial-dashboard day buckets). The optional `extra` dict is a pass-through onto the persisted DynamoDB item (used to attach `provider` for payment-provider attribution, per FIN-013).

Any costed production posting from MFG-008 must call this function with `key_name="work_order_id"`, never mint a parallel ledger store, and never use a `dev_mode` branch. Money-out (refund/cancel/RMA) reuses `billing.py:refund_payment`; for manufacturing there is no money-out — production is an internal value transfer, so no refund path is invoked.

### 2.6 Open sales-order demand source

The `orders` table (`app/core/tables.py:129`) is keyed `PK=order_id` with `GSI_STATUS` on partition `status` / numeric sort `created_at` (note: `created_at` is stored as an ISO string in existing rows — `scripts/local-ddb-init.py:288–294` declares the GSI but with no `attr_types` override, so it is treated as a string sort). Open orders have `status` values including `"pending_payment"` and `"fulfilled"` (set by `commerce_order_service.py:75`). For MRP gross-demand collection, only orders in `pending_payment` or `"processing"` statuses represent unfulfilled demand.

The `order_items` table (`app/core/tables.py:130`) is keyed `PK=order_id`, `SK=item_id` and holds `sku`, `quantity` (`:96`), and `amount_cents` per line item — the demand signal for MRP.

## 5. Detailed Behavior & Edge Cases

### 5.1 BOM explosion algorithm

`explode_bom(bom_id, build_qty, *, _depth=0, _seen=None)`:

1. If `_depth > S.mfg_bom_max_explosion_depth` (default 5), raise `HTTPException(409, "BOM explosion depth exceeded")`.
2. If `_seen is None`, initialize `_seen = set()`.
3. If `bom_id` is in `_seen`, raise `HTTPException(409, "Cyclic BOM detected")`.
4. Add `bom_id` to `_seen`.
5. Load all `COMP#{seq}` rows for the BOM from `T.mfg_boms`.
6. For each component row:
   - `required_qty = ceil(quantity_per * build_qty / output_quantity * (1 + scrap_pct))`
   - If `get_active_bom(component_sku)` returns a BOM (sub-assembly), recurse: `explode_bom(sub_bom.bom_id, required_qty, _depth=_depth+1, _seen=_seen)` and collect leaf components.
   - If no active BOM for component, append `{component_sku, required_qty, depth: _depth+1}` to the result.
7. Return the flattened list. Note: if the same component_sku appears via multiple paths, the caller (`run_mrp`) merges by sku and sums `required_qty`.

**Deferred**: phantom sub-assemblies (components that exist only as planning aids and whose stock is never tracked). These would require a `phantom: bool` flag on the component row and pass-through explosion without issuing the phantom itself. Deferred to a follow-up ticket; depth-5 limit provides sufficient coverage for the MVP.

### 5.2 Work-order lifecycle state machine

```
created → released → in_progress → completed
         ↘                        ↗
           cancelled (from created/released/in_progress only)
```

**Release** (`released`): Calls `explode_bom(bom_id, quantity)`, then for each exploded component calls `inventory.adjust(component_sku, -required_qty, reason="mfg_issue", user_sub=user_sub)`. If any adjust raises a 409 (insufficient stock), the entire release aborts and already-issued adjustments are reversed (compensating adjust with `reason="mfg_issue_reversal"`). Writes one `ISSUE#{n}` row per component. Sets `components_issued=True`.

**Complete** (`completed`): Calls `inventory.adjust(product_sku, +produced_qty, reason="mfg_produce", user_sub=user_sub)`. Sets `finished_goods_produced=True`. If `S.manufacturing_cost_posting_enabled`, calls `billing_shared.new_ledger_entry(...)` (MFG-008).

**Idempotency guards**: `components_issued` and `finished_goods_produced` boolean flags on the header row prevent double-issue or double-produce on replay. Both guards are written via a conditional `update_item` with `attribute_not_exists(components_issued)` or `components_issued = :false`.

**Cancellation**: Only allowed when `status in ("created", "released", "in_progress")`. If `components_issued=True`, component quantities must be returned via `inventory.adjust(component_sku, +qty, reason="mfg_cancel_return")` for each ISSUE row before the status transitions.

### 5.3 Lite-MRP net-requirement formula

```
net_requirement(sku) = gross_demand(sku) - on_hand_available(sku) - scheduled_receipts(sku)
```

Where:
- **`gross_demand(sku)`** = sum of `quantity` from `order_items` rows whose `order_id` belongs to an `orders` row with `status IN ["pending_payment", "processing"]` and `created_at >= now - horizon_days*86400`.
- **`on_hand_available(sku)`** = `inventory.get_or_zero(sku, location_id).available` (`app/services/inventory.py:158–173`), which returns 0 for unknown SKUs.
- **`scheduled_receipts(sku)`** = sum of planned `quantity` from `mfg_work_orders` rows (GSI_PRODUCT, `status IN ["released", "in_progress"]`). If the Purchasing module (PUR-001+) is present and `purchasing_scm_enabled=True`, also add open purchase-order line quantities for the SKU.

**Suggestion logic**:
- If `net_requirement > 0` and `get_active_bom(sku)` is not None: `suggested_action="produce"`, `suggested_quantity=net_requirement`.
- If `net_requirement > 0` and no active BOM: `suggested_action="purchase"`, `suggested_quantity=net_requirement`.
- If `net_requirement <= 0`: `suggested_action="none"`, `suggested_quantity=0`.

**BOM explosion into component requirements**: After computing finished-goods net requirements, each SKU with `suggested_action="produce"` is exploded through its BOM. Each component net requirement is computed independently using the same formula (component `gross_demand` comes from production requirements, not sales orders; component `scheduled_receipts` from open work orders for that component). The run records both finished-goods and component requirements in `REQ#{sku}#{seq}` rows.

### 5.4 Edge cases

- **SKU with no inventory record**: `get_or_zero` returns a zeroed virtual record (`on_hand=0, available=0`) — MRP treats it as fully unsupplied.
- **Surplus (net_requirement < 0)**: `net_requirement` is stored as a signed integer; `suggested_quantity` is clamped to 0. This allows callers to distinguish surplus from exact-zero.
- **MRP re-run idempotency**: `mrp_run_id = sha256(correlation_id)[:32]`. A re-run with the same `correlation_id` overwrites the header row and replaces all `REQ#{sku}#{seq}` rows for that run. The run never mutates any `inventory` record.
- **BOM without matching inventory SKU**: `explode_bom` does not validate that component SKUs have inventory records. Validation is the responsibility of `create_bom` (which calls `inventory.get_or_zero` to confirm the SKU exists in the inventory table before writing the component row).
- **Work order for SKU with no active BOM**: Allowed at creation time only if `bom_id` is explicitly supplied. If `bom_id` is absent and no active BOM exists, creation raises 422.
- **Concurrent adjust race on component issue**: The `inventory.adjust` retry loop (`inventory.py:282–285`) handles concurrent mutations transparently. A release with insufficient stock for any component results in a 409 after retries; the partial-issue reversal path handles cleanup.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007**: All service-layer code executes identically against DynamoDB Local (moto in tests, port 8001 in dev) and real DynamoDB in production. No `dev_mode` branch in business logic. The `_FloatSafeTable` proxy in `app/core/tables.py:29–62` handles the Decimal coercion transparently in all environments.

**Inventory adjust calls**: `inventory.adjust` is already SECOPS-007 clean — the same conditional-update loop runs against moto and real DynamoDB. Manufacturing callers add no new env-specific logic.

**Ledger entries (MFG-008)**: `billing_shared.new_ledger_entry` writes to `T.billing` (the real billing table), so costed entries appear in `GSI_LEDGER_DATE` aggregations in all environments. No dev-mode mock path.

**Idempotency**:
- BOM creation: `bom_id = sha256(correlation_id)[:32]`; `put_item` with `ConditionExpression="attribute_not_exists(bom_id)"` raises 409 on duplicate; callers must supply `correlation_id` for idempotent re-sends.
- Work order creation: same sha256 derivation from `correlation_id`.
- Work order component issue: `components_issued` guard on the header row (conditional put on `attribute_not_exists(components_issued)`).
- Work order produce: `finished_goods_produced` guard (same pattern).
- MRP run: `mrp_run_id = sha256(correlation_id)[:32]`; overwrites previous run rows (last-write-wins idempotency for re-runs).

**Security**:
- All manufacturing endpoints require `require_admin_or_root_csrf` (mirroring the inventory admin mutation pattern at `app/routers/inventory.py:48`).
- No manufacturing data is visible to `require_ui_session` callers (no storefront-facing endpoints).
- Component SKU validation in `create_bom` reads through `inventory.get_or_zero` to confirm the SKU is tracked; unknown SKUs are rejected with a 422 so stale BOMs cannot silently reference phantom materials.
- `explode_bom` depth limit (`mfg_bom_max_explosion_depth`, default 5) prevents a crafted cyclic or extremely deep BOM from causing a stack overflow.

## 10. Open Questions / Assumptions

1. **Assumption**: Orders with `status="pending_payment"` represent unfulfilled demand for MRP purposes. Assumption is that orders with `status="fulfilled"` or `"cancelled"` are excluded. This needs confirmation that the full set of "open" order statuses in the existing `orders` table is `{"pending_payment", "processing"}` — no other intermediate states are used.

2. **Assumption**: The `created_at` field in the `orders` table (set as an ISO string at `commerce_order_service.py:65,76`) means that MRP cannot use a numeric range query on `GSI_STATUS` to filter by horizon. The MRP service must do a client-side filter after fetching all open orders. This is acceptable for an MVP (small table) but will become a scan bottleneck at scale. A follow-up to add a numeric `created_at_ts` shadow field is recommended.

3. **Assumption**: Sub-assembly depth of 5 is sufficient for the expected product catalog. This should be validated with stakeholders before MFG-004 ships.

4. **Assumption**: The `output_quantity` field on a BOM header (how many units the BOM produces per run) defaults to 1 for simple single-unit assemblies. The explosion formula `ceil(quantity_per * build_qty / output_quantity * (1 + scrap_pct))` must preserve integer semantics and always round up.

5. **Assumption**: Work-order cancellation after `components_issued=True` reverses component quantities. This requires iterating all `ISSUE#{n}` rows. A partial-issue reversal during a failed `release` uses the same loop. Both paths must handle the case where the compensating `adjust` itself fails (e.g., if inventory was deleted between issue and reversal) — swallowed exception with audit log is the correct behavior, mirroring the `_audit` wrapper pattern.

6. **Open question**: Should the `mfg_work_orders` `GSI_STATUS` include a `user_sub` partition to scope the production queue per user? Current design is global (all work orders visible to all admins). Confirm with product that this is intentional.

7. **Open question**: Routing tasks (work-center assignments with `setup_minutes` / `run_minutes_per_unit`) live in MFG-005. Should routing tasks be stored per-BOM (on `T.mfg_boms` as `SK=TASK#{seq}` rows) or per-work-center (on `T.mfg_work_centers`)? Current assumption is per-BOM, making a work-center a referenced entity rather than a scheduling owner. This is the OFBiz model (WorkEffortGoodStandard links routing tasks to the BOM).

8. **Assumption**: The Purchasing module (PUR-001+) does not exist yet. MRP's `_collect_scheduled_receipts` must compile cleanly and function correctly when `T.purchase_orders` does not exist (use `getattr(T, "purchase_orders", None)` guard).

9. **Assumption**: The costed GL hook (MFG-008) uses work order cost = `sum(component unit_cost * issued_qty) + routing labor cost`. Component `unit_cost` is not currently stored on inventory records — this must be added as an optional field in MFG-008's scope, or the GL entry uses `amount_cents=0` (a zero-value internal transfer) until cost data is available.
