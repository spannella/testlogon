# FAC-002 — Facility tables, settings & feature flag

## 1. Summary & Goal

FAC-002 is the P0 scaffolding chore that lands the DynamoDB table definitions designed in FAC-001 into the running codebase. It has three concrete, verifiable deliverables:

1. **Five new `TableDef` entries** in `scripts/local-ddb-init.py` (placed after the existing `returns` table block at line 2492), each using `_resolve_table_name(S.<key>, "<default>")` and with numeric GSI sort keys listed in `attr_types`.

3. **Five new `Tables` dataclass fields + five `_safe_table(...)` initialisations** in `app/core/tables.py` (appended after `T.returns` at lines 319 and 571 respectively).

No service logic, no routers, no Pydantic models, and no frontend changes ship with this ticket. The sole acceptance bar is that `just restart` recreates all new tables without a `ValidationException`, that `S.facility_fulfillment_enabled` defaults to `False`, and that a smoke test can import `app.core.tables.T` and dereference each new handle.

With the flag off (the default), every existing code path — shop, cart, orders, billing, inventory, returns — is byte-for-byte unchanged. This is enforced structurally: no existing service file is touched.

### `attr_types` correctness requirement

`scripts/local-ddb-init.py:34–35` and the CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha both state that any attribute used as a GSI sort key with integer values **must** appear in `attr_types` with value `"N"`. If omitted, DynamoDB stores the attribute as String and raises `ValidationException` when queried with integer values. The existing `attr_types={"available": "N"}` at line 2463 and `attr_types={"created_at": "N", "expires_at": "N"}` at line 2477 are the canonical examples. Every new table that uses `created_at` as a GSI sort key must repeat this declaration.

**CRITICAL CONSTRAINT**: `_attribute_definitions()` (`scripts/local-ddb-init.py:2496–2506`) collects key attributes from the table PK/SK and all GSI partition/sort keys, then calls `attrs.update(table.attr_types)`. Every entry in `attr_types` ends up in the `AttributeDefinitions` list passed to `create_table`. DynamoDB (and moto) raise `ValidationException` if `AttributeDefinitions` contains an attribute that is **not** a key in the base table or any GSI. Therefore `attr_types` must contain **only** attributes that serve as keys — never non-key numeric attributes, even for forward-compatibility purposes.

## 3. Data Model

All five tables follow the project's single-table keying pattern (header row + child rows on the same partition). The data model is specified in full in FAC-001. This section reproduces the exact `TableDef` shapes that FAC-002 must land.

### 3.1 `facilities` table

Stores facility headers (SK=`META`) and per-facility location rows (SK=`LOC#{location_id}`) on the same partition. Enables per-facility batch reads with a single `query(Key={"facility_id": fid})`.

**Access patterns requiring GSIs:**
- List all facilities for a user sorted newest-first → `GSI_OWNER` (PK=`owner_sub`, SK=`created_at`)
- Admin active/archived facility queue → `GSI_STATUS` (PK=`status`, SK=`created_at`)

Both GSIs sort on `created_at` which is a Unix integer timestamp — requires `attr_types={"created_at": "N"}`.

```python
TableDef(
    _resolve_table_name(S.facilities_table_name, "facilities"),
    "facility_id",
    "sk",
    gsi=[
        {"index_name": "GSI_OWNER",  "partition_key": "owner_sub", "sort_key": "created_at"},
        {"index_name": "GSI_STATUS", "partition_key": "status",    "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
),
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag default and activation path

`S.facility_fulfillment_enabled` defaults to `False` via `os.environ.get("FACILITY_FULFILLMENT_ENABLED", "false").lower() == "true"`. This evaluates at module import time. The value is accessed by the `_flag_on()` helper in FAC-004's `app/services/facilities.py`, which is never imported by any existing service or router — so the flag's presence in `Settings` has zero runtime effect before FAC-004 ships.

To activate: set `FACILITY_FULFILLMENT_ENABLED=true` in `.env.local`. This is explicitly not done in `.env.local.example` until the full milestone (FAC-004 + FAC-005) is ready for testing.

### 5.2 Table creation at `just restart`

`scripts/local-ddb-init.py` calls `_table_defs()` and iterates over the list, calling `ddb.create_table(...)` for each (with `BillingMode="PAY_PER_REQUEST"`). The `_attribute_definitions` helper at `scripts/local-ddb-init.py:2496–2506` reads `attr_types` and overrides the default `"S"` type for listed attributes. Because `created_at` is declared as `"N"` in every new table's `attr_types`, DynamoDB Local will correctly type the GSI sort keys as `Number`. A missing `attr_types` declaration would silently type `created_at` as `String` during table creation, causing `ValidationException` on any query that supplies an integer value — this is the exact gotcha documented in CLAUDE.md.

### 5.3 `shipped_at` is a non-key attribute — excluded from `attr_types`

**CORRECTED**: The `shipments` table uses `attr_types={"created_at": "N"}` only. `shipped_at` must **not** be listed in `attr_types`.

`_attribute_definitions()` at `scripts/local-ddb-init.py:2496–2506` builds the `AttributeDefinitions` list by collecting all PK/SK/GSI key attributes then calling `attrs.update(table.attr_types)`. The DynamoDB (and moto) `create_table` API enforces that every entry in `AttributeDefinitions` must match exactly one key in the `KeySchema` or a GSI `KeySchema`. Including `shipped_at` (which is not a GSI key) would cause `ValidationException: Number of attributes in KeySchema does not exactly match number of attributes defined in AttributeDefinitions`, breaking `just restart`.

If a future ticket adds a `GSI_SHIPPED` index keyed on `shipped_at`, that ticket must also add `"shipped_at": "N"` to `attr_types` at the same time — the `_ensure_table` path for existing tables (`scripts/local-ddb-init.py:2534`) already handles adding new GSIs + their attribute definitions via `UpdateTable`.

### 5.4 `po_id` sentinel value for `receipts`

DynamoDB GSIs only index a row when the partition key attribute is **present and non-null**. Standalone receipts (not tied to a PO) must still be indexable by status. The `GSI_PO` index has PK=`po_id`, so standalone receipts set `po_id = "NONE"` (a string sentinel). This avoids sparse-index gaps in the `GSI_STATUS` index (which has PK=`status` and is independent of `po_id`). The service layer (FAC-007) enforces this sentinel. The table definition itself has no constraint; this is a service-layer convention.

### 5.5 Frozen `Tables` dataclass — `object.__setattr__` in tests

`Tables` is `@dataclass(frozen=True)` (`app/core/tables.py:68`). <!-- VERIFIED: tables.py:68 --> Tests must use `object.__setattr__(tables_mod.T, "facilities", moto_table)` to bind moto tables — the same pattern used by every existing hermetic test in the codebase (e.g., `tests/test_ofb_inventory.py:121`). <!-- VERIFIED: test_ofb_inventory.py:121 --> Attempting `T.facilities = moto_table` raises `FrozenInstanceError`.

### 5.6 `_safe_table` wraps inert table handles at import

When `app.core.tables` is imported, `_safe_table(S.facilities_table_name)` calls `ddb.Table("facilities")`. This does **not** connect to DynamoDB or validate the table exists — it creates a lazy boto3 Table reference. The first actual DynamoDB call (e.g., `T.facilities.put_item(...)`) will fail if DynamoDB Local is not running. In tests, `object.__setattr__` replaces the handle before any call is made. In production the tables exist and the handle is valid.

### 5.7 No change to existing tables or services

`T.inventory`, `T.reservations`, `T.returns`, and the three corresponding `Settings` keys are untouched. The `inventory.py` service (`app/services/inventory.py`) imports only `T.inventory` and `T.reservations` — neither file is touched by this ticket. The `_table_defs()` list grows from 3 to 9 OFBiz entries; the existing 3 entries are unchanged.

## 10. Open Questions / Assumptions

1. **Assumption**: The `receipts` table uses `po_id = "NONE"` as a sentinel for standalone receipts (not tied to a PO). This keeps the `GSI_PO` index dense (no sparse-index silent-miss risk) at the cost of a naming convention. Alternative: omit `po_id` entirely for standalone receipts and accept that `GSI_PO` will not index those rows. Reviewers should confirm the sentinel approach is acceptable.

2. **Assumption**: `shipped_at` is included in `attr_types={"...", "shipped_at": "N"}` for the `shipments` table even though it is not a current GSI sort key. This is a forward-compatibility choice. If reviewers prefer to add `shipped_at` to `attr_types` only when a GSI actually uses it (to keep `attr_types` minimal), the `UpdateTable` path in prod must be planned at that future ticket.

3. **Assumption**: The `lot_serial` table is created by `just restart` (the `TableDef` entry lands in `_table_defs()`) but `T.lot_serial` is a wired handle in `app/core/tables.py`. If reviewers want the `lot_serial` table completely invisible until FAC-011+, it should be omitted from `_table_defs()` now and added by FAC-011+ (which would require a `just restart` then). The current design creates the table early to avoid a breaking restart.

4. **Assumption**: The `Tables` dataclass ordering convention is "append new fields at the end". If a specific ordering is required (e.g., alphabetical) the diff to `tables.py` must be adjusted — but since `Tables` is a positional-keyword-argument dataclass and `T = Tables(...)` uses keyword arguments, ordering of fields in the class body does not affect the constructor call.

5. **Open question**: Should `FACILITY_FULFILLMENT_ENABLED=true` be added to the **test** `.env.local` (used by `just e2e`) now, or only when FAC-005 ships with the first E2E test? Adding it early is a no-op (no router mounted yet); omitting it is also correct. The current recommendation is to wait for FAC-005 so the flag is only enabled when there is observable test coverage.

6. **Assumption**: The table name `"receipts"` does not collide with any existing table. Grep confirms no existing `receipts` table in `scripts/local-ddb-init.py`. The name `"transfers"` also does not collide. Both are safe.
