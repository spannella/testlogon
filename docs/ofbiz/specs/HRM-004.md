**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days
**Milestone:** 2 — Employee & Position Service Core

## 1. Summary & Goal

HRM-004 creates `app/services/hr.py` and places within it the single entry-point function that establishes an employee in the platform: `ensure_employee_party`. The design principle is **no forking of the party model**: an employee is not a new entity stored in the `hr` table. An employee is a PERSON party (owned by `app/services/party.py`, `T.party` table, PTY-004) that carries the `EMPLOYEE` role (stored as a `PARTY#{id} / ROLE#EMPLOYEE` row in `T.party`, PTY-005).

`ensure_employee_party` stitches together two already-specified party-layer calls:

1. `party.ensure_person_party(user_sub)` — idempotently creates or retrieves the PERSON party for a platform user (PTY-010), or `party.create_party("PERSON", ...)` for a non-platform person (PTY-004).
2. `party.add_role(party_id, "EMPLOYEE")` — idempotent; adding a duplicate role is a no-op (PTY-005).

The `hr` table (`T.hr`, HRM-002) is NOT written to by this ticket. Employee identity lives entirely in `T.party`. The `hr` table is reserved for HR-specific entities — Positions (HRM-005), Employments (HRM-006), and Payroll Runs (HRM-007, HRM-008) — which reference `party_id` as a foreign key but do not duplicate any identity data.

A deterministic-id idempotency scheme (SHA-256 of `correlation_id`, truncated to 32 hex chars, with a conditional `attribute_not_exists(PK)` put at the party layer) ensures that re-calling with the same `correlation_id` always returns the same `party_id` without creating duplicates. An audit event is emitted via `app.services.alerts.audit_event` (`app/services/alerts.py:644` — verified) on the first successful onboarding, not on idempotent replays.

#### Primary function

```python
def ensure_employee_party(
    user_sub: Optional[str] = None,
    *,
    person_fields: Optional[Dict[str, Any]] = None,
    correlation_id: Optional[str] = None,
) -> str:
    """
    Idempotently provision a PERSON party carrying the EMPLOYEE role.

    Returns the party_id. Re-calling with the same correlation_id or user_sub
    returns the same party_id with no duplicate items.

    Args:
        user_sub: Platform user's Cognito sub. If provided, delegates to
            party.ensure_person_party which back-fills contact mechs.
            Must be provided OR person_fields must be non-empty.
        person_fields: Optional dict of additional fields (e.g. display_name,
            email) to pass through to party.create_party when creating a
            non-platform person record. Ignored when user_sub is supplied.
        correlation_id: Opaque client-supplied string for deterministic-id
            idempotency. SHA-256(correlation_id)[:32] becomes the party_id
            when creating a new party from person_fields. Ignored (but
            accepted) when user_sub is supplied — ensure_person_party
            is already user_sub-keyed.

    Returns:
        str: the party_id of the PERSON party.

    Raises:
        ValueError: if neither user_sub nor person_fields is supplied.
        HTTPException(503): propagated from party layer if DynamoDB unavailable.
    """
    if not user_sub and not person_fields:
        raise ValueError("ensure_employee_party: user_sub or person_fields required")

    is_new_party = False

    if user_sub:
        # Delegates to PTY-010: idempotent, user_sub-keyed, back-fills mechs.
        party_id = party.ensure_person_party(user_sub)
        # Check whether this party already holds the EMPLOYEE role.
        # add_role is idempotent per PTY-005 — calling it on an existing role
        # is always a no-op (returns immediately without a DDB write).
        existing_roles = party.list_roles(party_id)
        is_new_party = "EMPLOYEE" not in {r["role_type"] for r in existing_roles}
    else:
        # Non-platform person: use create_party with deterministic id.
        fields = dict(person_fields or {})
        party_record = party.create_party(
            "PERSON",
            user_sub=None,
            correlation_id=correlation_id,
            **fields,
        )
        party_id = party_record["party_id"]
        existing_roles = party.list_roles(party_id)
        is_new_party = "EMPLOYEE" not in {r["role_type"] for r in existing_roles}

    # add_role is idempotent: duplicate EMPLOYEE role is a no-op per PTY-005.
    party.add_role(party_id, "EMPLOYEE")

    if is_new_party:
        audit_event(
            "employee_onboarded",
            user_sub or party_id,
            None,
            party_id=party_id,
            correlation_id=correlation_id or "",
            outcome="success",
        )

    return party_id
```

#### Design notes

- `list_roles(party_id)` from PTY-005 is called to determine `is_new_party` before calling `add_role`. This avoids a redundant audit event on repeated calls with the same `user_sub` or `correlation_id`. The extra read is acceptable — `list_roles` queries the base table by `PK=PARTY#{party_id}` with a `begins_with(SK, "ROLE#")` expression (O(roles) read, bounded).
- `add_role` is unconditionally called even when the role exists — the PTY-005 idempotency guarantee absorbs it cheaply (the conditional put catches the duplicate and returns without error).
- The audit event is only emitted when the EMPLOYEE role is genuinely new — not on idempotent replays. This prevents audit-log spam when the same worker is onboarded in bulk or a retry storm occurs.

## 5. Detailed Behavior & Edge Cases

### 5.1 `user_sub` path: `ensure_person_party` is user-keyed

`party.ensure_person_party(user_sub)` (PTY-010) is keyed on `user_sub`. If the platform user has already been onboarded (e.g., as a CUSTOMER for billing), their PERSON party already exists. `ensure_person_party` returns the existing `party_id`. `add_role` adds `EMPLOYEE` without disturbing the `CUSTOMER` role or any other existing role — the party model explicitly supports multiple roles per party (PTY-005).

### 5.2 `person_fields` + `correlation_id` path: non-platform employees

When `user_sub` is absent but `correlation_id` is supplied, `party_id = sha256(correlation_id.encode())[:32]`. The conditional `attribute_not_exists(PK)` put in `party.create_party` ensures that:
- First call: creates the party item and returns the new `party_id`.
- Subsequent calls with same `correlation_id`: DynamoDB raises `ConditionalCheckFailedException`; `party.create_party` catches this and re-fetches the existing item, returning the same `party_id`. No duplicate is created.

When `correlation_id` is absent and `user_sub` is absent, a fresh `uuid4().hex` is used as `party_id`. Callers who do not supply `correlation_id` accept that retries create new party records (but this is rare — most callers supply at least `user_sub`).

### 5.3 Role collision: `EMPLOYEE` already present

If the party already holds the EMPLOYEE role, `party.add_role` (PTY-005) performs a conditional put with `attribute_not_exists(SK)` on the `ROLE#EMPLOYEE` row, which fails gracefully. No error is raised, no DynamoDB throughput is wasted beyond the failed conditional check, and `ensure_employee_party` returns the `party_id` normally. `is_new_party` is `False` so no audit event fires.

### 5.4 Partial failure: party created but `add_role` fails

If `ensure_employee_party` successfully calls `party.create_party` (writing the PERSON party row) but then `party.add_role` raises (e.g., transient DynamoDB error), the party record exists without the EMPLOYEE role. This is a partial-failure window. The next call with the same `correlation_id` will:
1. `party.create_party` returns the existing record (conditional put catches the duplicate).
2. `party.add_role` is retried and succeeds.

The partial state (PERSON party without EMPLOYEE role) is benign — the party is not yet queryable via `parties_with_role("EMPLOYEE")` and no Employment record can be created against it until `add_role` succeeds. Callers should not catch and suppress the `add_role` exception; they should let it propagate so the higher layer (router or background job) retries.

### 5.5 `person_fields` is ignored when `user_sub` is supplied

When `user_sub` is given, `ensure_person_party(user_sub)` from PTY-010 controls all field population (it reads from `get_profile_identity` and `list_addresses`). Any `person_fields` dict passed alongside `user_sub` is silently ignored. This is intentional: the profile/address tables are the authoritative source for platform users; `person_fields` is for non-platform persons only.

### 5.6 Audit event `user_sub` field for non-platform persons

When `user_sub` is absent, the audit event's first positional argument (the `user_sub` parameter of `audit_event`) is set to `party_id`. `audit_event` calls `get_profile_identity(user_sub)` at `app/services/alerts.py:669` (verified) which will raise `Exception` for a non-platform id and be swallowed at `:670–671` (`except Exception: identity = {}` — verified). This is the established pattern — the audit event still writes to `T.alerts` with `party_id` in the `user_sub` column and the `party_id` field in `**fields`.

### 5.7 Flag gate placement

`ensure_employee_party` is a service function. It does **not** call `_require_hr()` internally. The canonical pattern in this codebase is to define the guard helper in the service module and call it from each handler — see `_require_enabled()` at `app/services/returns_rma.py:71–73` (verified), which raises `HTTPException(status_code=404, ...)` and is called from each handler in `app/routers/returns_rma.py`. HRM-004's `_require_hr()` follows the same placement (defined in `app/services/hr.py`, called by HRM-009 router handlers and HRM-006 service entry points). Service functions themselves remain testable with the flag off by bypassing the guard in unit tests. Callers (HRM-009 router, HRM-006 service) must invoke `_require_hr()` before calling `ensure_employee_party`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007

There are no `if S.dev_mode:` branches in `app/services/hr.py`. All DynamoDB writes go to `T.party` and `T.alerts` via the shared `_safe_table`/`_FloatSafeTable` proxy (`app/core/tables.py:29–66` — verified; handles `float`→`Decimal` coercion identically in both environments). `audit_event` at `app/services/alerts.py:644` (verified) is itself dev/prod parity-clean (no mock path). The moto in-process S3 mock is irrelevant to this ticket — no S3 calls are made.

### Idempotency

Two axes of idempotency:

1. **`user_sub`-keyed**: `ensure_person_party(user_sub)` is idempotent by design (PTY-010 uses a `user_sub` GSI lookup to find and return an existing party before attempting a create). Re-calling `ensure_employee_party(user_sub=X)` any number of times returns the same `party_id`.

2. **`correlation_id`-keyed**: `party.create_party(..., correlation_id=C)` computes `party_id = sha256(C)[:32]` and uses `attribute_not_exists(PK)` to prevent double-writes. Re-calling with the same `C` returns the existing record.

`add_role("EMPLOYEE")` is idempotent per PTY-005 (`attribute_not_exists(SK)` conditional put).

The audit event is guarded by `is_new_party` — fired at most once per `(party_id, EMPLOYEE role)` pair regardless of how many times `ensure_employee_party` is called.

### Security

- **No PII duplication**: employee identity (name, email, address) lives exclusively in `T.party` (and by extension `T.profile` / `T.addresses` which PTY-010 reads from). The `hr` table stores only HR-domain entities (`POSITION`, `EMPLOYMENT`, `PAYROLL_RUN`) that reference `party_id` as an opaque key. A data breach of `T.hr` exposes compensation data but not PII.
- **No unguarded write paths**: `ensure_employee_party` is a service function reachable only from router handlers that enforce `require_admin_or_root` (HRM-009) or flag-gated employment creation (HRM-006). No unauthenticated code path reaches it.
- **Audit trail**: every first-time EMPLOYEE role assignment emits an `employee_onboarded` audit event to `T.alerts`, providing a non-repudiable record of when each person was enrolled in the HR system.

## 10. Open Questions / Assumptions

1. **Assumption: `party.list_roles(party_id)` returns a list of dicts with key `role_type` (string).** This is inferred from PTY-005's description (`PARTY_CRM_TICKETS.md:94–111`). If the return shape is different (e.g., a list of `PartyRole` Pydantic objects), the `is_new_party` check in `ensure_employee_party` must be adjusted. The next spec-verify pass should confirm the exact return type of `party.list_roles`.

2. **Assumption: adding a duplicate EMPLOYEE role via `party.add_role` is truly a no-op (does not raise).** PTY-005 states "adding a duplicate role is idempotent" (`PARTY_CRM_TICKETS.md:102`). If the implementation raises a specific exception on duplicate (e.g., `DuplicateRoleError`) rather than silently returning, `ensure_employee_party` should add a `try/except DuplicateRoleError: pass` around the `add_role` call. The current design assumes silent no-op. Verify against the PTY-005 implementation before merging HRM-004.

3. **Assumption: `person_fields` is a flat dict of additional DynamoDB attributes to pass through to `create_party`.** PTY-004 does not specify additional keyword arguments beyond `party_type`, `user_sub`, and `correlation_id`. If `create_party` has a strict signature that rejects unknown kwargs, the `**fields` spread must be replaced with an explicit `extra_fields=fields` parameter. Verify `create_party` signature against PTY-004 implementation.

4. **Assumption: the EMPLOYEE role string is `"EMPLOYEE"` (uppercase).** `PARTY_CRM_TICKETS.md:57` (repo root — verified) lists `EMPLOYEE` in the `PartyRoleType` enum. PTY-003 has not been merged yet (confirmed: `PartyRoleType` not present in `app/models.py` — VERIFIED). If the enum value ends up lowercase or differently cased, the hard-coded `"EMPLOYEE"` string in `ensure_employee_party` must match. Add a test that imports `PartyRoleType.EMPLOYEE.value` (once available) and asserts it equals `"EMPLOYEE"`.

5. **Assumption: the `hr` module file is `app/services/hr.py` (not `app/services/hrm.py`).** The ticket descriptor and all HRM-002, HRM-003 specs consistently use `app/services/hr.py`. This is confirmed to be the correct path.

6. **Open question: should `ensure_employee_party` accept a `role_type` parameter to allow assigning roles other than `EMPLOYEE` (e.g., `CONTRACTOR`)?** The current spec hard-codes `"EMPLOYEE"`. If the HR module later needs to support multiple employment-type roles (e.g., `CONTRACTOR`, `INTERN`), the function signature would need to change. For now, hard-coding `"EMPLOYEE"` is the simplest correct implementation.

7. **Open question: should `person_fields` include `display_name`, `email`, etc. or is that handled entirely by the PTY-007 contact-mech layer?** For non-platform persons, `display_name` and `email` may be passed as `person_fields` kwargs, but PTY-004's `create_party` may not accept them directly (it might expect contact mechs to be added via `add_contact_mech` from PTY-007). The spec above passes `**fields` to `create_party` optimistically. If `create_party` rejects unknown fields, the caller must use `add_contact_mech` post-creation.

8. **Assumption: `audit_event` at `app/services/alerts.py:644` is safe to call with a `party_id` (not a real `user_sub`) as its second argument.** `audit_event` calls `get_profile_identity(user_sub)` and swallows any exception. A `party_id` string that does not match any real `user_sub` will cause `get_profile_identity` to raise or return `{}`, which is silently swallowed. The audit row is still written with `user_sub=party_id`. This is consistent with how other service code uses `audit_event` with non-user-sub identifiers (e.g., `app/services/commerce_order_service.py:106` uses `user_id` which is also a `user_sub` string — verified; no validation enforces this).
