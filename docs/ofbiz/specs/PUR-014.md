# PUR-014 — Suppliers admin page

**Type:** Feature | **Priority:** P1 | **Estimate:** 3 days
**Milestone:** 5 — Frontend Admin UI
**Depends on:** PUR-013 (frontend types + endpoint wrappers)

---

## 1. Summary & Goal

PUR-014 adds a **Suppliers admin page** at `frontend/src/pages/shop/admin/SuppliersAdmin.tsx`.
The page lives under the `admin/` directory alongside the existing
`InventoryAdmin.tsx` (`frontend/src/pages/shop/admin/InventoryAdmin.tsx`). It
gives admin/root users a single screen to:

1. **Browse and filter** the supplier list (active/inactive toggle).
2. **Create** a new supplier via an inline dialog (React Hook Form + Zod).
3. **Edit** an existing supplier's contact info, currency, and payment terms via
   a separate edit dialog (same form, pre-populated).
4. **Activate / deactivate** a supplier with a status toggle.
5. **Manage supplier-product pricing** inline per supplier: view the per-supplier
   product list, upsert a `(supplier_id, sku)` pricing row (`unit_cost_cents`,
   `lead_time_days`, MOQ), and delete a pricing row — all without a page reload.

The page is **flag-gated** (hidden and rendering a disabled-feature empty-state
when `VITE_PURCHASING_SCM_ENABLED=false`) and **role-gated** (renders a 403 empty
state for non-admin/root users). All data mutations are optimistic-free: the UI
disables the trigger button during the in-flight mutation and invalidates the
relevant React Query cache keys on success, so the table refreshes from the
server automatically.

## 4. API / Service Design

PUR-014 consumes existing API endpoints; it introduces no new backend code.

### 4.1 Backend endpoints consumed

All require admin or root role. CSRF is enforced for mutations.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/ui/purchasing/suppliers?status=active&limit=50&next_token=…` | Paginated list |
| `POST` | `/ui/purchasing/suppliers` | Create supplier (status 201) |
| `PATCH` | `/ui/purchasing/suppliers/{id}` | Edit fields or set status |
| `GET` | `/ui/purchasing/suppliers/{id}/products?limit=50&next_token=…` | List pricing rows |
| `PUT` | `/ui/purchasing/suppliers/{id}/products/{sku}` | Upsert pricing row |
| `DELETE` | `/ui/purchasing/suppliers/{id}/products/{sku}` | Remove pricing row (204) |

### 4.2 React Query keys

```ts
// Supplier list
["purchasing", "suppliers", status]           // status: "active" | "inactive"

// Single supplier (prefetched or fetched on edit open)
["purchasing", "suppliers", supplierId]

// Supplier-product list
["purchasing", "supplier-products", supplierId]
```

Mutation `onSuccess` handlers invalidate:
- Create: `["purchasing", "suppliers", "active"]` (new supplier defaults to active).
- Patch: `["purchasing", "suppliers", status]` and `["purchasing", "suppliers", supplierId]`.
- Status toggle (via PATCH): both status variants (`["purchasing", "suppliers", "active"]`
  and `["purchasing", "suppliers", "inactive"]`).
- Upsert product: `["purchasing", "supplier-products", supplierId]`.
- Delete product: `["purchasing", "supplier-products", supplierId]`.

```ts
// frontend/src/api/endpoints/purchasing.ts (added by PUR-013)
export const listSuppliers = (status = "active", limit = 50, next_token?: string) =>
  api.get<SupplierListOut>("/ui/purchasing/suppliers",
    { status, limit: String(limit), ...(next_token ? { next_token } : {}) });

export const createSupplier = (body: SupplierCreateIn) =>
  api.post<Supplier>("/ui/purchasing/suppliers", body);

export const patchSupplier = (id: string, body: SupplierPatchIn) =>
  api.patch<Supplier>(`/ui/purchasing/suppliers/${id}`, body);

export const listProductsForSupplier = (supplierId: string, limit = 50, next_token?: string) =>
  api.get<SupplierProductListOut>(`/ui/purchasing/suppliers/${supplierId}/products`,
    { limit: String(limit), ...(next_token ? { next_token } : {}) });

export const upsertSupplierProduct = (supplierId: string, sku: string, body: SupplierProductUpsertIn) =>
  api.put<SupplierProduct>(`/ui/purchasing/suppliers/${supplierId}/products/${encodeURIComponent(sku)}`, body);

export const deleteSupplierProduct = (supplierId: string, sku: string) =>
  api.del<void>(`/ui/purchasing/suppliers/${supplierId}/products/${encodeURIComponent(sku)}`);
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off empty state

When `isPurchasingScmEnabled()` returns `false` (i.e., `VITE_PURCHASING_SCM_ENABLED`
is unset or `"false"`), the component returns immediately with:

```tsx
<EmptyState
  icon={<Package className="h-10 w-10" />}
  title="Purchasing & SCM is not enabled"
  description="Enable the purchasing & SCM feature flag to manage suppliers."
/>
```

This mirrors `InventoryAdmin.tsx:146-156` exactly. The React Query queries are
**not** issued when the flag is off (`enabled: allowed && isPurchasingScmEnabled()`).

### 5.2 Role-denied empty state

Non-admin/root users (determined by `canAccessGeneralAdminControls(accessToken)`)
see:

```tsx
<EmptyState
  icon={<AlertTriangle className="h-10 w-10" />}
  title="Access denied"
  description="Supplier management requires admin or root access."
/>
```

Again matching `InventoryAdmin.tsx:158-168`.

### 5.3 Supplier list — status filter

The page maintains a `status: "active" | "inactive"` state variable (default
`"active"`). A segmented control (two `Button` variants — `"default"` when
active, `"outline"` when inactive) toggles between the two views. Switching
status triggers `qc.invalidateQueries` implicitly via the React Query key
change (`["purchasing", "suppliers", status]`).

### 5.4 Create supplier dialog

Clicking **+ Add Supplier** opens a `Dialog` (shadcn) containing a `useForm`
driven by `supplierSchema`. On submit:
- `createSupplier(formValues)` mutation fires.
- On success: `qc.invalidateQueries(["purchasing", "suppliers", "active"])`,
  `toast.success("Supplier created")`, dialog closes, form resets.
- On error (4xx): `toast.error("Failed to create supplier")`.
- The Submit button is `disabled` while `createMut.isPending`.
- The dialog does not attempt to pre-populate fields (create only).

Fields: `name` (required), `email`, `phone`, `default_currency` (default `"USD"`),
`payment_terms_days` (default `30`). Address fields are intentionally omitted
from the create dialog to reduce friction; an address can be added via the edit
dialog.

### 5.5 Edit supplier dialog

Each row in the supplier table has an **Edit** button (pencil icon). Clicking it
pre-populates the `useForm` with the row's current values and opens a second
dialog (same layout as create, but with `defaultValues` from the row). On
submit, `patchSupplier(supplierId, changedFields)` fires. The patch body only
includes fields that differ from the original values (compare form output to
`supplier` object before submitting); an all-same-fields submit is a no-op (the
button is disabled when `formState.isValid && !formState.isDirty`).

### 5.6 Status toggle

Each row has a `Switch` (shadcn) showing the current active/inactive status.
Toggling it calls `patchSupplier(supplierId, { status: newStatus })`. On success
the query for both `"active"` and `"inactive"` is invalidated so the row
disappears from the current view (the supplier has moved to the other list) and
the switch reflects the new state.

### 5.7 Inline supplier-product pricing section

Clicking a supplier row (or an **Expand** chevron button) expands an inline
accordion panel showing that supplier's product pricing table. This uses local
`expandedSupplierId: string | null` state — only one supplier is expanded at a
time to limit concurrent queries.

Within the expanded panel:
- `useQuery(["purchasing", "supplier-products", supplierId])` fetches
  `listProductsForSupplier(supplierId)`. Loading state shows a spinner.
- The products are displayed in a nested `Table` with columns: SKU, Cost (formatted
  as currency), Lead time (days), MOQ, Preferred, Actions.
- An **Add Pricing Row** button at the bottom of the panel opens the product
  form in a `Dialog`.
- Each existing row has an **Edit** pencil (pre-populates the form) and a
  **Delete** trash button.

### 5.8 Upsert product dialog

The product dialog reuses `productSchema`. On submit:
- `upsertSupplierProduct(supplierId, sku, formValues)` mutation fires.
- SKU is editable only in create mode; in edit mode the SKU field is `readOnly`
  (the SKU identifies the row — to reroute to a different SKU the user must
  delete the old row and create a new one).
- On success: `qc.invalidateQueries(["purchasing", "supplier-products", supplierId])`,
  `toast.success("Pricing saved")`, dialog closes.
- On error 422 (unknown SKU from the backend): `toast.error("SKU not found in
  catalog or inventory")`.

### 5.9 Delete product row

Clicking the trash icon shows a `ConfirmDialog` (from
`@/components/shared/ConfirmDialog`, already used by `AdminCatalog.tsx:28`).
On confirm: `deleteSupplierProduct(supplierId, sku)`. On success:
`qc.invalidateQueries(["purchasing", "supplier-products", supplierId])`,
`toast.success("Pricing row deleted")`.

### 5.10 Pagination

The `listSuppliers` and `listProductsForSupplier` APIs support cursor-based
pagination via `next_token`. The page loads the first page (limit=50) on mount.
A **Load more** button appears at the bottom of the table when `next_token` is
present in the response. Clicking it issues a second query with `next_token=...`
and appends the results to the displayed list. This is implemented with simple
`useState` accumulation (not `useInfiniteQuery`) to keep the component
straightforward; the total supplier count for most deployments fits within one
page.

### 5.11 Empty supplier list

When `items.length === 0` for the current status filter, show:
```tsx
<EmptyState
  icon={<Building2 className="h-10 w-10" />}
  title={status === "active" ? "No active suppliers" : "No inactive suppliers"}
  description={status === "active"
    ? "Add a supplier to get started."
    : "No suppliers have been deactivated yet."}
/>
```

### 5.12 Loading and error states

- Initial load: full-area `Loader2` spinner.
- Query error: `toast.error` via the query's `onError` option (or an inline
  error card if the initial load fails).

### 5.13 Currency display

`unit_cost_cents` is displayed using `Intl.NumberFormat` with `style: "currency"`,
matching the `formatPrice` helper in `AdminCatalog.tsx:44-50`:
```ts
function formatPrice(cents: number, currency = "USD"): string {
  return new Intl.NumberFormat("en-US", { style: "currency", currency })
    .format(cents / 100);
}
```

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No client-side behavior branching

The component does not contain any `if (dev_mode)` or environment-specific
branches. The flag (`VITE_PURCHASING_SCM_ENABLED`) is the only branch.

### 7.2 CSRF

All state-mutating API calls (`POST`, `PATCH`, `PUT`, `DELETE`) go through
`api.post`/`api.patch`/`api.put`/`api.del` which automatically attach
`X-CSRF-Token` from the `ui_csrf` cookie (`frontend/src/api/client.ts:179-181`).
No manual header injection is required.

### 7.3 Idempotency (user-visible)

- **Create supplier**: the service layer (PUR-003) derives `supplier_id =
  sha256(f"supplier:{actor_sub}:{name}")[:32]`, so creating the same supplier
  name twice is idempotent server-side. The UI does not need to handle this
  specially; it will receive the same 201 body both times.
- **Upsert product**: `PUT /ui/purchasing/suppliers/{id}/products/{sku}` is
  always a full replace of the pricing row; repeating the exact same request
  leaves the data unchanged.
- **Double-click guard**: all mutation trigger buttons are `disabled` while
  `mut.isPending` to prevent duplicate in-flight requests.

### 7.4 No money movement in this page

PUR-014 manages supplier and product-pricing master data only. No payments,
ledger entries, or billing mutations occur here. The billing path (PUR-009) is
triggered by PO receipt, not from this page.

### 7.5 Role enforcement is server-side

The frontend role check (`canAccessGeneralAdminControls`) is UX-only — it hides
the UI but the backend enforces 403 for every endpoint regardless. A user who
bypasses the frontend check will receive 403 from the API, which the client
renders as a `toast.error` via the `api` client's 403 handler
(`frontend/src/api/client.ts:251-265`).

## 10. Open Questions / Assumptions

1. **PUR-013 is fully implemented before this ticket starts.** The component
   imports `Supplier`, `SupplierProduct`, `listSuppliers`, `createSupplier`,
   etc. from files delivered by PUR-013. If PUR-013 is in progress, stub the
   types locally and import from the final location when PUR-013 lands.

2. **Supplier addresses are display-only in the create dialog.** The create
   dialog omits address fields to reduce form complexity. An address can be
   patched in via the edit dialog using the full `SupplierAddressIn` sub-form.
   If the PM wants address capture at creation time, this is a scope addition.

3. **Inline expansion shows only the first page of product pricing rows.**
   The product list query fetches `limit=50` per page. If a supplier has more
   than 50 product-pricing rows, the "Load more" control appears inside the
   expanded panel. Assumption: 50 rows per supplier is sufficient for the
   initial MVP.

4. **SKU encoding for URL path segments.** `encodeURIComponent(sku)` is used
   in `deleteSupplierProduct` and `upsertSupplierProduct` to handle SKUs
   containing `/`, `#`, or other URL-special characters. The backend must use
   FastAPI's default path-parameter decoding (which it does). SKUs containing
   literal `%` are a known edge case (double-encoding risk); flagged here but
   treated as out of scope until a real SKU format is finalized.

5. **No address edit sub-form in V1.** The `SupplierPatchIn.address` field
   accepts a full `SupplierAddressIn` map, but the edit dialog renders only
   the top-level scalar fields (`name`, `email`, `phone`, `default_currency`,
   `payment_terms_days`, `status`). Address editing is deferred to a follow-up.

6. **Preferred supplier flag display.** The product table renders a `Badge`
   (e.g., "Preferred") when `preferred === true`. The upsert form includes a
   `Checkbox` for the `preferred` field. There is no enforcement that only one
   supplier per SKU can be preferred — the backend stores it as a per-row
   boolean; the page does not enforce uniqueness.

7. **No bulk actions in V1.** There is no multi-select or bulk delete/activate
   for suppliers or pricing rows. This is a scope simplification for the 3-day
   estimate.

8. **`canAccessGeneralAdminControls` is used (not just `require_admin_or_root`
   backend role).** The frontend mirrors the general-admin profile check that
   `InventoryAdmin.tsx` uses. A scoped admin (e.g., `admin_profile.type ===
   "moderation"`) would see the access-denied empty state from the frontend even
   though the backend would also return 403. This is consistent with the
   inventory admin UI pattern.
