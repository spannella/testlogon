# PTY-009 — Additive contacts→party migration (back-compatible)

**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days
**Milestone:** 3 — Migration & Profile Linking
**Depends on:** PTY-004, PTY-006, PTY-007

---

## 1. Summary & Goal

PTY-009 introduces `app/services/party_contacts_migration.py` — a read-only projection layer that
maps every existing `Contacts` DynamoDB row (owned by `app/routers/contacts.py`) onto the OFBiz
party graph being built by PTY-004 through PTY-007.

For each `(owner_id, contact_id)` pair in the legacy contacts table, the migration ensures:

1. A `PERSON` party exists for the **owner** (keyed on `owner_id`).
2. A `PERSON` party exists for the **contact** (keyed on `contact_id`).
3. A `CONTACT_REL` relationship edge exists from the owner party to the contact party (PTY-006).
4. A `CONTACT` role is assigned to the contact party within the owner's scope (PTY-005).
5. The contact's `display_name`, `is_favorite`, `is_blocked`, and `profile_photo_url` are carried
   over onto the relationship item as extended attributes.

The contacts table is never written, mutated, or deleted by this ticket. With
`S.party_crm_contacts_migration_enabled` off (the default), the existing
`app/routers/contacts.py` surface (`list_contacts`, `add_contact`, `update_contact`,
`remove_contact`) is byte-for-byte identical to today's behavior.

## 3. Data Model

### 3.1 Source table: `Contacts` (read-only)

| Attribute | Type | Notes |
|-----------|------|-------|
| `owner_id` | S (PK) | User sub of the contact list owner |
| `contact_id` | S (SK) | User sub of the contact entry |
| `display_name` | S | Display name at time of add |
| `profile_photo_url` | S | Optional photo URL |
| `is_favorite` | BOOL | Favorite flag |
| `is_blocked` | BOOL | Blocked flag |
| `added_at` | S | ISO-8601 timestamp string |

**PTY-009 never writes this table.** It is queried with
`KeyConditionExpression=Key("owner_id").eq(owner_id)` via the same paging loop as
`list_contacts`.

### 3.2 Target table: `party` (all writes go here)

Defined by PTY-002. Single-table, `PK` (S) hash key, `SK` (S) range key.

#### 3.2.1 PERSON party rows (created by PTY-004 `create_party`)

| Attribute | Value |
|-----------|-------|
| `PK` | `PARTY#{party_id}` |
| `SK` | `META` |
| `party_id` | `sha256(f"contacts-person:{user_sub}")[:32]` |
| `party_type` | `PERSON` |
| `status` | `ACTIVE` |
| `user_sub` | the platform `user_sub` |
| `display_name` | from `get_profile_identity(user_sub)` |
| `profile_photo_url` | from `get_profile_identity(user_sub)` |
| `created_at` | `now_ts()` (N) |
| `updated_at` | `now_ts()` (N) |
| `type` | `TYPE#PERSON` (for `GSI_CREATED` query) |
| `GSI3PK` | `OWNER#{user_sub}` |
| `GSI3SK` | `PARTY#{party_id}` |

The `GSI3` index (`GSI3PK` = `OWNER#{user_sub}`) is used to look up whether a PERSON party
already exists for a given `user_sub` before creating one — enabling idempotent re-runs.

#### 3.2.2 CONTACT role rows (created by PTY-005 `add_role`)

| Attribute | Value |
|-----------|-------|
| `PK` | `PARTY#{contact_party_id}` |
| `SK` | `ROLE#CONTACT` |
| `party_id` | `contact_party_id` |
| `role_type` | `CONTACT` |
| `GSI1PK` | `ROLE#CONTACT` |
| `GSI1SK` | `PARTY#{contact_party_id}` |
| `created_at` | `now_ts()` (N) |

#### 3.2.3 CONTACT_REL relationship rows (created by PTY-006 `create_relationship`)

Two rows per relationship — primary and mirror — as specified by PTY-006:

**Primary row:**

| Attribute | Value |
|-----------|-------|
| `PK` | `PARTY#{owner_party_id}` |
| `SK` | `REL#CONTACT_REL#{contact_party_id}` |
| `from_party_id` | `owner_party_id` |
| `to_party_id` | `contact_party_id` |
| `relationship_type` | `CONTACT_REL` |
| `rel_id` | `sha256(f"contacts-rel:{owner_id}:{contact_id}")[:32]` |
| `created_at` | `now_ts()` (N) |
| **Extended attrs** | |
| `is_favorite` | BOOL — carried from legacy row |
| `is_blocked` | BOOL — carried from legacy row |
| `display_name` | S — display name at migration time |
| `profile_photo_url` | S — optional |
| `migrated_from` | `"contacts"` — provenance marker |

**Mirror row** (for inbound/to-side lookups):

| Attribute | Value |
|-----------|-------|
| `PK` | `PARTY#{contact_party_id}` |
| `SK` | `MIRROR#CONTACT_REL#{owner_party_id}` |
| `from_party_id` | `owner_party_id` |
| `to_party_id` | `contact_party_id` |
| `relationship_type` | `CONTACT_REL` |
| `GSI3PK` | `REL_TO#{contact_party_id}` |
| `GSI3SK` | `REL#CONTACT_REL#{owner_party_id}` |

Both rows written atomically via `T.party.transact_write_items` if the relationship does not
already exist. If only one of the pair exists (partial write from a previous crash), the migration
detects the state via `get_item` checks and repairs the missing row.

### 3.3 No new tables or GSIs

PTY-009 creates no new DynamoDB tables and adds no new GSIs. All writes target the existing
`party` table defined by PTY-002. The `Contacts` table schema is untouched.

## 4. API / Service Design

### 4.1 Module: `app/services/party_contacts_migration.py`

```python
from __future__ import annotations

import hashlib
import logging
from typing import Any, Dict, List, Optional

from boto3.dynamodb.conditions import Key

from app.core.tables import T
from app.core.settings import S
from app.core.time import now_ts
from app.services.party import (
    create_party,
    get_party,
    add_role,
    create_relationship,
)
from app.services.profile import get_profile_identity

logger = logging.getLogger(__name__)

# ── Deterministic-ID helpers ──────────────────────────────────────────────────

def _person_party_id(user_sub: str) -> str:
    """Stable party_id for a platform user. sha256 of scoped correlation key."""
    corr = f"contacts-person:{user_sub}"
    return hashlib.sha256(corr.encode("utf-8")).hexdigest()[:32]

def _rel_correlation_id(owner_id: str, contact_id: str) -> str:
    """Stable correlation_id for the (owner, contact) relationship edge."""
    return f"contacts-rel:{owner_id}:{contact_id}"

# ── Core projection ───────────────────────────────────────────────────────────

def _ensure_person_party(user_sub: str) -> str:
    """
    Idempotently ensure a PERSON party exists for user_sub.

    Uses _person_party_id() as the deterministic party_id and passes it as
    correlation_id to create_party so repeated calls are no-ops (conditional
    attribute_not_exists(PK) put).

    Returns party_id.
    """
    ...

def _project_contact_row(
    owner_id: str,
    contact_id: str,
    contact_item: Dict[str, Any],
) -> None:
    """
    Project one legacy contacts row into the party graph.

    Steps:
    1. _ensure_person_party(owner_id) → owner_party_id
    2. _ensure_person_party(contact_id) → contact_party_id
    3. add_role(contact_party_id, "CONTACT") — idempotent (no-op if exists)
    4. create_relationship(
           owner_party_id, contact_party_id, "CONTACT_REL",
           correlation_id=_rel_correlation_id(owner_id, contact_id),
           extra={
               "is_favorite": contact_item.get("is_favorite", False),
               "is_blocked": contact_item.get("is_blocked", False),
               "display_name": contact_item.get("display_name", ""),
               "profile_photo_url": contact_item.get("profile_photo_url"),
               "migrated_from": "contacts",
           },
       )  — idempotent via correlation_id
    """
    ...

# ── Backfill entrypoint ───────────────────────────────────────────────────────

def run_contacts_backfill(*, owner_id: Optional[str] = None) -> Dict[str, int]:
    """
    Project all legacy contacts rows (or rows for a single owner_id) onto the
    party graph.

    Arguments:
        owner_id: when supplied, process only this user's rows. When None,
                  scan all owners via DynamoDB Scan on T.contacts (admin path).

    Returns:
        {
            "scanned": int,      # total contact rows examined
            "projected": int,    # rows successfully projected (new or already existed)
            "errors": int,       # rows skipped due to exceptions
        }

    Raises nothing — errors per-row are caught, logged, and counted.
    Guard: raises RuntimeError("party_crm_contacts_migration_enabled is off")
           if S.party_crm_contacts_migration_enabled is False.
    """
    ...

# ── Forward hook (called by add_contact) ─────────────────────────────────────

def maybe_project_new_contact(
    owner_id: str,
    contact_id: str,
    contact_item: Dict[str, Any],
) -> None:
    """
    Best-effort forward hook. Called by app/routers/contacts.add_contact after
    the legacy put_item succeeds, when S.party_crm_contacts_migration_enabled.

    All exceptions are swallowed — a party-graph failure must never break the
    legacy add_contact response.
    """
    if not S.party_crm_contacts_migration_enabled:
        return
    try:
        _project_contact_row(owner_id, contact_id, contact_item)
    except Exception:
        logger.exception(
            "party_contacts_migration: forward hook failed for owner=%s contact=%s",
            owner_id,
            contact_id,
        )
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Backfill scan strategy

`run_contacts_backfill(owner_id=None)` uses `T.contacts.scan()` with a pagination loop
(checking `LastEvaluatedKey`). Because DynamoDB `FilterExpression` does not reduce page size,
the scan reads all items up to 1 MB at a time before applying any filter. With `owner_id`
supplied, a `KeyConditionExpression` query is used instead (same paging loop as `list_contacts`
at `app/routers/contacts.py:66-78` <!-- VERIFIED: app/routers/contacts.py:66-78 -->).

### 5.2 Idempotency — full replay safety

Each of the four operations in `_project_contact_row` is idempotent:

- `_ensure_person_party(user_sub)` → `create_party(..., correlation_id=f"contacts-person:{user_sub}")`:
  conditional `attribute_not_exists(PK)` put; on conflict, reads back and returns existing party.
- `add_role(contact_party_id, "CONTACT")` (PTY-005): uses `put_item` with
  `ConditionExpression="attribute_not_exists(PK)"` on the `ROLE#CONTACT` SK row; conflict is
  silently ignored.
- `create_relationship(..., correlation_id=_rel_correlation_id(...))`: `rel_id = sha256(corr)[:32]`
  used as SK component; conditional put on the primary row; conflict returns existing. If the
  primary row exists but the mirror is missing (partial write), the migration detects and repairs
  the mirror (see §5.3 below).

Re-running `run_contacts_backfill()` on a fully-migrated dataset produces zero new writes and
zero errors.

### 5.3 Partial-write recovery for relationship rows

After `_project_contact_row` writes the primary `REL#CONTACT_REL#{contact_party_id}` row, it
writes the mirror row `MIRROR#CONTACT_REL#{owner_party_id}` in a separate `put_item`. If the
process crashes between these two writes, the next backfill run encounters the existing primary
(conditional check fails → no-op) but the mirror is missing. The recovery path:

1. On `ConditionalCheckFailedException` for the primary row, read back the existing item.
2. Check whether the mirror row exists via `T.party.get_item(Key={"PK": ..., "SK": ...})`.
3. If mirror is absent, write it (unconditional `put_item` since the primary already exists).

This recovery is transparent — it runs within the normal `_project_contact_row` call, not as a
separate repair sweep.

### 5.4 Profile enrichment at backfill time

`_ensure_person_party` calls `get_profile_identity(user_sub)` to populate `display_name` and
`profile_photo_url` on the PERSON party's `META` row. If the profile does not exist
(e.g., the user was deleted), `get_profile_identity` may raise an exception. In this case,
`_ensure_person_party` falls back to `display_name=user_sub` and `profile_photo_url=None`, logs
a warning, and continues — the party is still created (matching the behavior of `add_contact` at
`app/routers/contacts.py:97-98` <!-- VERIFIED: app/routers/contacts.py:97-98 — `display_name=inp.user_id`, `profile_photo_url=None` fallback values -->).

### 5.5 Blocked contacts

`is_blocked=True` on a legacy row is carried into the `CONTACT_REL` primary item as
`is_blocked=True`. The party graph does not enforce any semantic restriction based on this flag —
it is stored as an informational attribute for higher-level consumers (PTY-011 router, future
block-list queries). The legacy `app/routers/contacts.py` block semantics are unchanged.

### 5.6 Favorite contacts

`is_favorite=True` is carried into the `CONTACT_REL` primary item as `is_favorite=True`. No
sorting or GSI behavior is added in this ticket for favorites — the attribute is available for
consumers to filter/sort on in application logic.

### 5.7 Contacts table pagination

The `Contacts` table has no GSIs and a numeric `Limit` cap. The backfill paging loop mirrors the
`list_contacts` implementation precisely (`app/routers/contacts.py:66-78` <!-- VERIFIED -->):

```python
last_key = None
while True:
    kwargs = {"KeyConditionExpression": Key("owner_id").eq(owner_id), "Limit": 500}
    if last_key:
        kwargs["ExclusiveStartKey"] = last_key
    resp = T.contacts.query(**kwargs)
    items.extend(resp.get("Items", []))
    last_key = resp.get("LastEvaluatedKey")
    if not last_key:
        break
```

For the all-owners scan path, `T.contacts.scan(Limit=500)` is used with the same `LastEvaluatedKey`
loop.

### 5.8 Large contact lists

An owner with 10,000 contacts will trigger 10,000 `_project_contact_row` calls. Each call makes
at most 6 DynamoDB operations on `T.party` (2× `get_item` checks, 2× `put_item` for parties,
1× `put_item` for role, 2× `put_item` for primary + mirror). On a fully-migrated dataset
re-run, every `create_party` conditional fails immediately (1 `get_item` each), so the overhead
is O(contacts) `get_item` calls — acceptable for a background job.

For very large deployments, `run_contacts_backfill` should be called with `owner_id` set to
process one user at a time, driven by the admin endpoint's pagination support (PTY-012 concern).

### 5.9 Flag-off guarantee

When `S.party_crm_contacts_migration_enabled` is `False`:

- `run_contacts_backfill` raises `RuntimeError` immediately — the admin endpoint (PTY-012) will
  catch this and return 503.
- `maybe_project_new_contact` returns immediately without doing anything.
- The lazy import inside `add_contact` is never reached.
- **No import of `party_contacts_migration` or `party` occurs in any request path.**
  The `from app.services.party_contacts_migration import maybe_project_new_contact` import is
  inside the `if S.party_crm_contacts_migration_enabled:` block, so it is only reached at
  runtime when the flag is on.

### 5.10 Owner equals contact (self-contact)

The `Contacts` table's `add_contact` handler at `app/routers/contacts.py:88-89` <!-- VERIFIED: app/routers/contacts.py:88-89 --> already rejects
`user_id == user_sub` with HTTP 400. Existing rows in the legacy table cannot have
`owner_id == contact_id`. The migration does not add a redundant check but logs a warning and
skips any such row defensively.

### 5.11 Deleted users

If a `contact_id` in the legacy table corresponds to a user who has since been deleted from
the `users` table, `get_profile_identity(contact_id)` may fail. The PERSON party for that
`contact_id` is still created (without enriched profile data) so the relationship graph is
structurally correct. A future cleanup sweep (out of scope here) could purge orphaned PERSON
parties.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Single code path**: All reads from `T.contacts` and writes to `T.party` use the same boto3
calls in both dev and prod. Moto intercepts at the botocore layer in dev; real DynamoDB is used
in prod. There are no `if S.dev_mode` branches in `party_contacts_migration.py`. This is
SECOPS-007 parity.

**Idempotency**: Every write path uses a deterministic `party_id` or `rel_id` derived via
`sha256(scoped_correlation_key)[:32]` plus `ConditionExpression="attribute_not_exists(PK)"`. A
backfill run that is interrupted and restarted from the beginning produces the same final state as
a single complete run. The count of **new** DynamoDB writes decreases toward zero on repeated
full runs (only partial-write repairs produce new writes after a complete migration).

**Read-only on `Contacts`**: PTY-009 calls only `T.contacts.query` and `T.contacts.scan` against
the legacy table — never `put_item`, `update_item`, or `delete_item`. This is enforced by code
review (no `T.contacts.put_item` may appear in `party_contacts_migration.py`).

**No new data exposure**: The migration copies `display_name`, `is_favorite`, `is_blocked`, and
`profile_photo_url` fields that already exist in the `Contacts` table and are already returned
by `list_contacts`. No new PII is introduced into the party graph beyond what was already
accessible via the contacts API.

**Audit trail**: Each successful `_project_contact_row` call emits an `audit_event` via
`app.services.alerts.audit_event` <!-- VERIFIED: app/services/alerts.py:644 -->:

```python
audit_event(
    "party.contacts_migration.projected",
    owner_id,
    contact_id=contact_id,
    owner_party_id=owner_party_id,
    contact_party_id=contact_party_id,
)
```

This is best-effort (inside a `try/except`) and fire-and-forget. The audit write goes to
`T.alerts` <!-- VERIFIED: app/core/tables.py:330 --> (same table used by all other audit events in
the system). Re-runs emit duplicate audit events for already-projected rows — the audit log is
append-only and this is acceptable.

**No secrets**: `profile_photo_url` is a URL, not a token or credential. `is_blocked` is a
user preference flag. Neither requires encryption at rest beyond what DynamoDB provides.

### 8.1 Legacy contacts surface is unchanged with flag off

Even with the flag on, a failure in `maybe_project_new_contact` does not affect the HTTP
response returned by `add_contact`. The legacy `ContactEntry` response is returned regardless of
whether the party graph projection succeeded. This means the party graph may temporarily be
behind the contacts table — the backfill entrypoint reconciles this.

### 8.3 No schema migration for `Contacts` table

The `Contacts` DynamoDB table schema (bare two-column, no GSIs) is unchanged. No
`UpdateTable` call or `just restart` is needed for this ticket alone.

This is the same operation as `_ensure_person_party` defined here. Once PTY-010 is
implemented, `party_contacts_migration._ensure_person_party` should be refactored to delegate

before PTY-010, the local `_ensure_person_party` function is the correct implementation — it
follows the same PTY-004 `create_party(correlation_id=...)` pattern and does not duplicate logic.

## 10. Open Questions / Assumptions

1. **PTY-006 `extra` parameter**: This spec assumes PTY-006's `create_relationship` will be
   extended to accept an `extra: Optional[Dict]` dict that is merged onto the primary row item.
   If PTY-006 is merged without this parameter, PTY-009 will write the primary relationship row
   directly (via `T.party.put_item`) using the same SK scheme as PTY-006, to avoid requiring a
   PTY-006 amendment. This assumption must be verified when PTY-006 is implemented.

2. **`_ensure_person_party` vs PTY-010's `ensure_person_party`**: This spec defines
   `_ensure_person_party` as a module-private function in `party_contacts_migration.py` rather
   than in `party.py`, because PTY-010 (which adds the public `ensure_person_party` to
   `party.py`) is a parallel ticket. The assumption is that once PTY-010 is done, PTY-009's
   local helper will be refactored to delegate to `party.ensure_person_party`. No circular
   dependency exists because `party_contacts_migration.py` imports from `party.py` (one
   direction only).

3. **All-owners scan performance**: The `T.contacts.scan()` path for `run_contacts_backfill(owner_id=None)`
   performs a full table scan. On a table with millions of rows this will be slow and expensive.
   The assumption is that for Phase 1 this is acceptable (run once, admin-only, not in the hot
   path). A GSI-based enumeration of distinct owners is deferred to a future optimization ticket.

4. **`added_at` field on legacy rows**: The `added_at` ISO-8601 string from legacy contact rows
   is NOT carried over to the party graph relationship row in this spec. It is available if
   needed (the `contact_item` dict is passed to `_project_contact_row`) but storing it would
   require an additional attribute on the relationship item. The assumption is that `created_at`
   (set to `now_ts()` at migration time) is sufficient for the party graph, and `added_at` from
   the legacy table remains the canonical source for the legacy surface.

5. **Concurrent forward hook + backfill**: If a forward hook fires for `add_contact` while
   a backfill is running, both may attempt to create the PERSON party and CONTACT_REL for the
   same `(owner_id, contact_id)` pair concurrently. The `attribute_not_exists(PK)` conditional
   put ensures only one write wins; the loser receives `ConditionalCheckFailedException` and
   reads back the existing item. This is safe — the outcome is correct regardless of which
   writer "wins". No additional locking is needed.

6. **`migrated_from` attribute on relationship rows**: The `migrated_from="contacts"` marker on
   primary rows is an informational provenance field. This spec assumes it is useful for future
   auditing and cleanup but does not add a GSI for it. If queries by provenance are needed
   later, a new GSI would be required.

7. **`profile_photo_url` staleness**: The photo URL captured at migration time may become stale
   if the user updates their profile photo later. PTY-009 does not add a mechanism to re-sync
   this field. The assumption is that the party graph's `display_name` and `profile_photo_url`
   on relationship rows are a snapshot at migration time, not live-synced. PTY-010's forward hook
   on profile updates will handle re-syncing the PERSON party's `META` row but not individual
   relationship extended attributes.
