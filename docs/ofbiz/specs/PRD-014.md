# PRD-014 — Frontend types & endpoint wrappers

## 1. Summary & Goal

PRD-014 delivers the TypeScript layer that connects the React frontend to the product-depth backend introduced in PRD-003 through PRD-013. The work is purely additive: new TypeScript interfaces are appended to `frontend/src/api/types.ts`, and a new file `frontend/src/api/endpoints/catalog-depth.ts` wraps every PRD-005/008/011/013 route in a typed, axiom-instance call. Existing `CatalogItem` consumers in `frontend/src/api/endpoints/cart.ts` and the shop pages are byte-for-byte unchanged; new fields on the extended `CatalogItem` type are all optional with safe defaults. The endpoint file is the foundation PRD-015 (admin UI) and PRD-016 (E2E tests) build on.

### Backend routes to wrap (PRD-005 / PRD-008 / PRD-011 / PRD-013)

All new routes live under `prefix="/ui/catalog"` on the existing `catalog.router` (`app/routers/catalog.py:42`). <!-- VERIFIED: catalog.py:42 — `router = APIRouter(prefix="/ui/catalog", ...)` --> They are gated by `S.product_depth_enabled` (a PRD-002 deliverable; not yet present in `app/core/settings.py` or `app/core/tables.py`). <!-- RISK: `S.product_depth_enabled` and `T.product_depth` do NOT yet exist — PRD-002 prereq unmerged --> They fall into four groups:

**Category-tree (PRD-005):**
- `POST /ui/catalog/categories/{id}/children` — add a child category
- `PATCH /ui/catalog/categories/{id}/move` — re-parent a category
- `GET /ui/catalog/categories/{id}/tree` — subtree rooted at `{id}`
- `GET /ui/catalog/categories/{id}/breadcrumb` — ancestry path to root

**Variants & features (PRD-008):**
- `POST /ui/catalog/feature-categories` — create a feature category
- `POST /ui/catalog/feature-categories/{id}/values` — add a feature value
- `POST /ui/catalog/items/{id}/feature-categories` — attach feature category to product
- `GET /ui/catalog/items/{id}/features` — list attached feature categories + values
- `POST /ui/catalog/items/{id}/variants` — create variant from feature selections
- `GET /ui/catalog/items/{id}/variants` — list variants with effective prices
- `DELETE /ui/catalog/items/{id}/variants/{variant_id}` — remove a variant

**Bundles & associations (PRD-011):**
- `PUT /ui/catalog/items/{id}/bundle-components` — set/replace component list
- `GET /ui/catalog/items/{id}/bundle` — bundle metadata + component list
- `GET /ui/catalog/items/{id}/expand` — flattened component lines + computed price
- `POST /ui/catalog/items/{id}/associations` — add an association
- `GET /ui/catalog/items/{id}/associations` — list associations (optional type filter)
- `DELETE /ui/catalog/items/{id}/associations/{assoc_id}` — remove an association

**Price components (PRD-013):**
- `PUT /ui/catalog/items/{id}/price-components` — upsert a price component row
- `GET /ui/catalog/items/{id}/price-components` — list all price component rows
- `GET /ui/catalog/items/{id}/effective-price` — resolve active price for a date/type

## 5. Detailed Behavior & Edge Cases

### Flag-off behavior

All product-depth routes return `404` (or `501`) when `S.product_depth_enabled` is `False`. The endpoint wrappers call those URLs regardless; the backend error propagates as an `ApiError` with `status 404`. Callers (PRD-015 UI components) must check the flag themselves before rendering depth-UI sections — PRD-015 fetches `GET /ui/catalog/config` (or `GET /ui/catalog/depth-enabled`) to learn the flag value client-side. With the flag off, `CatalogItem` objects returned from existing endpoints omit the four new fields entirely; TypeScript consumers see them as `undefined`, which is correct since they are typed `?`.

### `null` vs absent for `new_parent_category_id` in `MoveCategoryIn`

The `PATCH /categories/{id}/move` body carries `new_parent_category_id: string | null`. A `null` value signals promotion to the root (no parent). TypeScript callers must explicitly pass `null` (not omit the key) for promote-to-root to distinguish from "not provided". The backend validates this via Pydantic `Optional[str]` with explicit `None`.

<!-- NOTE: PRD-005 defines MoveCategoryIn field as "new_parent_category_id". Verify against PRD-005 router implementation when merged. -->

### `as_of` param for `getEffectivePrice`

When omitted, the backend resolves using `now_ts()` at request time. When provided, it must be a Unix integer (seconds). The wrapper converts it with `String(asOf)` for the query string; the backend converts back via `int()`.

### `feature_values` dict keys are `feature_category_id`, not names

The `VariantIn.feature_values` map is keyed by `feature_category_id` (not human-readable name) and valued by `feature_value_id`. <!-- CORRECTED: was "feature_selections" / "feature_id" — aligned with PRD-003 §3.4 / PRD-008 §4.3 --> This matches the backend `VariantCreateIn.feature_values` field from PRD-003. Callers must use IDs, not display strings.

### `setBundleComponents` is replace-all (PUT semantics)

`PUT /items/{id}/bundle-components` replaces the full component set. Callers must send the complete desired component list; partial updates are not supported. The wrapper name `setBundleComponents` signals idempotent replace semantics.

### `EffectivePriceOut.source` discriminates fallback

When no dated price component matches, `source` is `"scalar_fallback"` and `amount_cents` is the item's scalar `price_cents` from the `T.catalog` row (`app/routers/catalog.py:115`). <!-- CORRECTED: field is "amount_cents" not "price_cents" on EffectivePriceOut per PRD-013 §4.3 --> When a component matches, `source` is `"price_component"` and `price_component_id` is set.

### Duplicate association idempotency

`addAssociation` with an already-existing `(from, type, to)` triple returns the existing `ProductAssoc` row (PRD-003 §3.7 deterministic id = `sha256(from_item_id + assoc_type + to_item_id)[:16]`). The backend responds `200` with the existing row rather than `409` — callers may safely call this without a pre-existence check.

### Duplicate variant idempotency

Similarly, `createVariant` with an already-existing feature-selection tuple returns `200` with the existing `Variant` row (deterministic id = `sha256(parent_id + sorted feature-value tuple)`, PRD-007). No `409`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity**: all endpoint wrappers call the same `/ui/catalog/*` URL in both environments. There is no `dev_mode` branch in frontend code. CSRF token attachment is handled unconditionally by `api/client.ts` (`:179-182`) when the `ui_csrf` cookie is present.

**Idempotency**: The wrappers themselves are stateless HTTP calls. Idempotency is enforced by the backend (deterministic ids for variants and associations, conditional puts for feature categories). Frontend callers need not implement retry deduplication.

**Auth**: All depth routes use cookie-based `require_ui_session` on the backend (`app/services/sessions.py:330`). <!-- VERIFIED: catalog.py:39 imports from app.services.sessions (not app.auth.deps) --> The `api()` function attaches the `Authorization: Bearer` header from `useAuthStore` (`client.ts:168-170`) <!-- VERIFIED: client.ts:168-170 --> for every call. CSRF is automatically attached for non-GET calls (`client.ts:179-182`). <!-- VERIFIED: client.ts:179-182 --> No new auth plumbing is needed.

**Type safety**: All new types are exported from `frontend/src/api/types.ts` and imported by `catalog-depth.ts` using `import type` (tree-shakable, no runtime bundle impact). The new `ProductType`, `ProductAssocType`, and `PriceType` string unions are non-exhaustive (backend may add values) so callers should use them as type hints, not exhaustive switch guards.

**No money mutations**: None of the wrappers in this ticket initiate a charge, issue a refund, or touch the billing ledger. Price-component data is read-only enrichment from the frontend's perspective.

## 10. Open Questions / Assumptions

1. **`CatalogCategory` extension**: PRD-004 adds `parent_category_id`, `path`, and `position` to category rows. This ticket assumes those fields should also appear as optionals on the existing `CatalogCategory` interface in `types.ts`. If PRD-004/005 decide to return a distinct `DepthCatalogCategory` shape instead, the `addChildCategory` and `moveCategory` wrappers should use that shape, not the existing `CatalogCategory`.

2. **Flag endpoint**: PRD-014 assumes a lightweight `GET /ui/catalog/depth-enabled` (or `GET /ui/catalog/config`) endpoint exists or will exist (from PRD-002/003) so PRD-015 can read the flag. If no such endpoint is planned, PRD-015 will need to infer flag status from the 404 on a depth call. This assumption should be resolved before PRD-015 starts.

3. **`expandBundle` quantity param**: The wrapper passes `qty` as a query param. <!-- CORRECTED from "quantity" — PRD-011 §4.1 uses "qty" confirmed at PRD-011:301 --> Verify the final router implementation uses this name.

4. **`setBundleComponents` response shape**: `PUT /items/{id}/bundle-components` is assumed to return a `Bundle` object (full representation after replacement). <!-- NOTE: PRD-011 §4.3 returns BundleOut which maps to Bundle here --> If the backend returns `OkResp` instead, the wrapper return type should be `OkResp`.

5. **`addChildCategory` response shape**: Assumed to return `CatalogCategory` (possibly with the new `parent_category_id` / `path` fields from PRD-004). If it returns the tree node shape instead, the return type should be `CategoryTreeNode`.

6. **`ProductFeaturesOut` shape**: Assumed to be a grouped structure (feature categories with nested values). If the backend returns a flat array of `ProductFeature` objects keyed only by `feature_category_id`, the interface should be `ProductFeature[]` instead.

7. **`CatalogItem.product_type` vs `ProductTypeEnum` in backend**: The spec assumes `CatalogItemOut` will carry `product_type` as one of the six string literals defined in `ProductTypeEnum` (PRD-003). If the backend exposes a different set of values or uses a different field name, the `ProductType` union and the optional field on `CatalogItem` must be updated to match.

8. **Separate `catalog-depth.ts` vs extending `cart.ts`**: The spec calls for a new file to avoid coupling. The alternative is appending to `cart.ts`. The recommendation is a separate file for clarity; if the team prefers a single file, all exports should be added after the existing `reorderCatalogItems` export in `cart.ts` under a clear section comment.
