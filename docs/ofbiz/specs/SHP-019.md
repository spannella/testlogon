# SHP-019 — Shipping/logistics tests (hermetic pytest + e2e)

## 1. Summary & Goal

SHP-019 is the final milestone of the shipping/logistics work stream: it adds the full test harness that validates every behavior introduced by SHP-001 through SHP-018. The deliverable is two artifacts:

1. **Hermetic offline pytest suites** in `tests/test_shp_*.py` — seven focused files covering carrier/method CRUD and seed idempotency, rate estimation math and breakpoints, shipment create/idempotency/ship-group split/over-ship, package packing invariants, lifecycle transitions and version race, tracking application (reusing `carrier_tracking` helpers) with delivered-alert-once, order-fulfillment linkage and idempotency, and shipping-refund-via-billing idempotency. All tests run offline with moto-bound frozen `T` and no real AWS/network.

2. **A Playwright E2E spec** at `frontend/e2e/shipping.spec.ts` — covering the admin carrier/method management lifecycle, a rate estimate at checkout, the full admin create-pack-ship flow, tracking surface on the buyer transaction view, and flag-off invisibility.

A cross-cutting regression assertion confirms that with `shipping_enabled=False` the existing `carrier_tracking`, `purchase_history`, and checkout paths are byte-for-byte unchanged.

## 5. Detailed Behavior & Edge Cases

### Carrier CRUD + seed idempotency

The default seed (`seed_default_carriers()`) inserts five carriers: `ups`, `fedex`, `usps`, `dhl`, `manual`. Each carrier row uses the carrier code as `carrier_id`. The seed uses conditional `put_item(ConditionExpression="attribute_not_exists(carrier_id)")` or equivalent — a second call to `seed_default_carriers()` must produce no additional rows and must not overwrite customised rows. Tests verify: (a) row count is idempotent, (b) `online_tracking=True` for the four known carriers and `False` for `manual`, (c) disabling a carrier causes `list_carriers()` to omit it but `list_carriers(include_disabled=True)` to return it.

### Rate estimation breakpoints

`estimate_rates` aggregates line-item weights from `line_items[*].weight_grams * quantity`. It then resolves dimensional weight per method: `dim_weight = (length * width * height) / method.dim_divisor` (default divisor 5000 if not set on the method); billable weight = `max(actual_weight, dim_weight)`. Rate tiers use the method's `breakpoints` list (list of `{max_grams, rate_cents}` sorted ascending); if billable weight exceeds all breakpoints the last tier applies. An empty list of enabled methods returns `[]` without error (never raises). Tests cover: (a) single item weight × quantity, (b) dimensional vs actual winner selection, (c) breakpoint boundary (exactly at max_grams uses that tier), (d) empty-method case.

### Shipment create / idempotency / ship-group split / over-ship

`create_shipment` derives `shipment_id = hashlib.sha256(f"shipment:{order_id}:{ship_group_seq}".encode()).hexdigest()[:32]` (same pattern as `commerce_order_service.py:67`). A second call with the same `(order_id, ship_group_seq)` must return the existing row without creating a duplicate — verified by checking that `T.shipments.put_item` is guarded by `ConditionExpression="attribute_not_exists(shipment_id)"` and the idempotent path returns the existing item on `ConditionalCheckFailedException`. Ship-group split: an order with two groups (e.g. 3 qty of SKU-A → group 1 ships 2, group 2 ships 1) creates two shipment rows with distinct `ship_group_seq` and distinct `shipment_id`; `list_shipments_for_order` returns both. Over-ship: attempting to create a third group shipping 1 more unit when the full 3 are already assigned raises `ValueError` (or `HTTPException(400)`) before any DynamoDB write.

### Package packing invariants

After `add_package`, calls to `assign_item_to_package` accumulate packed quantities per `(shipment_id, item_id)`. The invariant is: `sum(packed_qty for item_id) <= shipment_item.quantity`. Over-packing a single item raises `ValueError`. Advancing the shipment to `packed` is rejected (409 / `ValueError`) if any shipment item's total packed quantity is less than its shipment quantity. Tests: (a) multi-package split with total equal to shipment-item qty succeeds, (b) over-pack raises before any write, (c) `advance_lifecycle(shipment_id, "packed")` with partially-packed item raises.

### Lifecycle state machine and version race

Legal transitions: `created → packed → label_created → shipped → in_transit → out_for_delivery → delivered`. Side states reachable from specific states: `exception` from `in_transit`/`out_for_delivery`, `returned` from `delivered`/`exception`, `cancelled` from `created`/`packed`/`label_created`. Illegal transitions return `409` and leave the item unchanged. Version guard: `advance_lifecycle` uses `ConditionExpression="version = :expected"` on `T.shipments.update_item`; a concurrent write wins; the loser receives `ConditionalCheckFailedException` which is surfaced as a typed `ShipmentConflictError` (409). Tests: (a) full happy path `created→shipped`, (b) illegal direct `created→delivered` raises, (c) two concurrent calls to `created→packed` with the same initial `version` — the second call fails with conflict.

The `shipped` transition specifically requires a non-empty `tracking_number`. When only a tracking number is given (no `carrier`), `detect_carrier(tracking_number)` (`carrier_tracking.py:46`) auto-fills the carrier. A tracking number that matches no known carrier and has `carrier=""` raises `ValueError("carrier required for manual tracking numbers")`. UPS number `1Z12345E0205271688` auto-detects as `ups`.

### Tracking apply — reuse carrier helpers, delivered-alert-once

SHP-012 refactors `apply_tracking_result` to accept either a `purchase_transactions` item (existing path, unchanged) or a `shipments` item. The parameterisation is via a `target_table` / callback argument — the tests confirm: (a) a status update on a shipment item calls `T.shipments.update_item` not `T.purchase_transactions.update_item`, (b) the delivered alert fires exactly once for `in_transit → delivered`, (c) a repeat apply of the same `delivered` status is a no-op (the old==new guard at `carrier_tracking.py:169` short-circuits). The existing transaction path is exercised in the same test class to prove both still work.

`find_shipment_by_tracking` uses `T.shipments.query` on `GSI_TRACKING` (a dedicated tracking-number GSI, not a scan like `purchase_history.py:595`) — a test seeds a shipment with a tracking number and asserts the GSI query returns it.

### Order-fulfillment linkage and idempotency

On `advance_lifecycle(shipment_id, "shipped")`, the service calls `purchase_history.update_shipping(buyer_sub, txn_id, {...})` to denormalise the carrier/tracking/status onto the matching `purchase_transactions` item (via `external_ref = order_id` linkage, `purchase_history.py:270`). It also writes `fulfillment_status` on the `orders` row additively — when all ship groups reach `shipped`, `fulfillment_status = "shipped"`; when some are `shipped` and some are still `created/packed`, `fulfillment_status = "partially_shipped"`. The existing `status` field on `orders` is never mutated (test: assert `status == "pending_payment"` throughout). Idempotency: shipping the same shipment a second time (re-advance) must not write a second `update_shipping` call if the tracking number/status/carrier are already identical — compare existing `shipping` sub-map before the update (mirrors the old==new guard in `apply_tracking_result`).

### Shipping refund via billing

SHP-015 introduces `cancel_shipment_with_refund(shipment_id, user_sub, reason)` which:
1. Reads the shipment to retrieve `shipping_amount_cents` (the rate charged at ship time) and `billing_idempotency_key = sha256(f"shipping_refund:{shipment_id}")[:32]`.
2. Checks whether a refund ledger entry with that idempotency key already exists on the `billing` table. **CORRECTION**: the `billing` table SK is `LEDGER#{ts}#{entry_id}` (from `billing_shared.py:220–221` `ledger_sk`), not `LEDGER#REFUND#{idempotency_key}`. A direct `get_item` cannot look up by idempotency key. Instead, the idempotency key must be stored in `meta={"idempotency_key": billing_idempotency_key}` (matching the pattern at `billing.py:1133,1241`) and the check must use a `query + FilterExpression` on the `billing` table PK `USER#{user_sub}`, or store a separate sentinel item with SK `SHIPPING_REFUND#{billing_idempotency_key}` using a `ConditionExpression="attribute_not_exists(pk)"` conditional put. The sentinel pattern is simpler and consistent with the one-time-use pattern in `cart_reminders.py`. If it exists, return without writing a second ledger row — idempotent.
3. Calls `new_ledger_entry(key_name="pk", key_value=f"USER#{user_sub}", entry_type="adjustment", amount_cents=-shipping_amount_cents, state="settled", reason="shipping_refund", extra={"provider": provider, "shipment_id": shipment_id, "idempotency_key": billing_idempotency_key})` from `app/services/billing_shared.py:224`.
4. The GL derives from this ledger entry — nothing is posted directly to any parallel GL table.
5. Advances shipment status to `cancelled`.

Tests: (a) single cancel with `shipping_amount_cents=500` writes one ledger entry and sets status to `cancelled`, (b) calling `cancel_shipment_with_refund` twice with same `shipment_id` returns the same ledger entry, writes exactly one DDB row, (c) `shipping_amount_cents=0` (no charge) writes no ledger entry and still cancels the shipment.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity**: All shipping service code runs the same DynamoDB paths in both dev (moto in-process) and prod (real DDB). There are no `if S.dev_mode:` branches in the shipping services or shipment lifecycle — the mock carrier surface (`carrier_tracking_mock.py`) is a standalone dev tool; the shipments service calls `apply_tracking_result` regardless of mode. The E2E spec seeds tracking state via `POST /mock/carrier-tracking/seed` (the existing mock endpoint at `carrier_tracking_mock.py:34`) and uses the same `POST /ui/shop/tracking/shipments/{shipment_id}/poll` admin endpoint to trigger a synchronous poll — no background timer dependence in tests.

**Idempotency keys**: Every mutable operation uses a deterministic key so replay is safe:
- Shipment creation: `sha256("shipment:{order_id}:{ship_group_seq}")[:32]` — same as the order-ID pattern at `commerce_order_service.py:67`.
- Shipping refund: `sha256("shipping_refund:{shipment_id}")[:32]` — checked against the billing table before writing.
- Order-fulfillment link: status compared before update (mirrors `apply_tracking_result`'s old==new guard at `carrier_tracking.py:167`).

**Security**:
- Buyer read (`GET /ui/shop/shipments/{shipment_id}`) resolves the order's `user_id` field and compares to `ctx["user_sub"]`; mismatched ownership → 404 (not 403, to avoid confirming existence).
- Admin write paths use `require_admin_or_root` from `app/auth/policy.py:67`, same as `carrier_tracking_poller_router` (`app/routers/carrier_tracking_poller.py:22,69`).
- Tracking number is stored at the shipment layer — not visible to buyers via the shipments read; buyers see only the denormalised view from `purchase_transactions.shipping` (which already has carrier/tracking_url from `update_shipping`).

**Billing/GL integrity**: Shipping refunds pass through `new_ledger_entry` from `billing_shared.py:224` with `extra={"provider": provider}` for FIN-013 attribution. No parallel write path. The GL derives from this entry exactly as the CLAUDE.md "Billing ledger queries" note requires.

## 8. Backward Compatibility & Migration

**Flag off = zero change**: With `S.shipping_enabled = False`, every shipping router returns a static 503/404 response before touching any DDB table. The four shipping tables need not exist for the flag-off case — the `T.shipping_carriers` / `T.shipments` / `T.shipment_items` / `T.shipment_packages` handles are created lazily via `_safe_table(name)` but never written.

**`orders` table**: The new `fulfillment_status` field is additive — written only when `shipping_enabled=True` and a shipment is advanced. Existing reads of `orders` rows that don't have this field are unaffected (`item.get("fulfillment_status")` returns `None`). The `status` field (`"pending_payment"`) is never modified by shipping code.

**`purchase_transactions` shipping sub-map**: SHP-014 denormalisation calls the existing `update_shipping` (`:398`) path, which already handles partial sub-map updates. Pre-shipping transactions (no `shipment_id` in metadata) look identical from the `GET .../tracking` endpoint.

## 10. Open Questions / Assumptions

1. **`apply_tracking_result` refactor interface**: The spec assumes SHP-012 parameterises `apply_tracking_result` to accept either a `purchase_transactions` or `shipments` item via a callback/target argument. If SHP-012 instead creates a separate `apply_tracking_result_to_shipment` function, `test_shp_005` must be adjusted to call the correct entry point.

2. **`shipment_packages` sort key type**: The spec treats `package_seq` as a String (`"PKG#001"`) to avoid mixed-type GSI sort-key issues. If SHP-009 uses a numeric `package_seq` (e.g. `1`, `2`), the `attr_types` declaration must include `{"package_seq":"N"}` in `scripts/local-ddb-init.py`.

3. **`find_shipment_by_tracking` GSI name**: **CORRECTED (pass 3)**: SHP-012 §3.1 explicitly defines the GSI as `TrackingNumberIndex` (hash-only on `tracking_number`) — not `GSI_TRACKING`. `test_shp_005_tracking.py` and any fixture setup must use `IndexName="TrackingNumberIndex"` when querying `T.shipments` by tracking number.

4. **`fulfillment_status` write target**: The spec assumes `fulfillment_status` is written to the `orders` table's existing row (no sort key, PK=`order_id`). If SHP-014 writes it to a separate GSI attribute or a sub-document, the test fixture must be updated.

5. **E2E flag-toggle mechanism**: **OPEN DECISION (pass 3)**: No `/internal/feature-flags` endpoint exists anywhere in the current codebase (confirmed by grep). `SHIPPING_ENABLED` (introduced by SHP-002) cannot be toggled at runtime from a Playwright test. Section 74 flag-off assertions must either be implemented as pytest-only (using `object.__setattr__(S, "shipping_enabled", False)`) or a new runtime-toggle endpoint must be created. The spec recommends pytest-only as the default path.

6. **Cart-reference in estimate endpoint**: SHP-007 allows a cart-bound variant of `POST /ui/shop/shipping/estimate` that reads from the caller's active cart. The E2E section 71 uses an inline `line_items` payload (not cart-bound) to avoid coupling to shopping cart state. If the estimate endpoint requires either cart_id or line_items (not both), this assumption holds.

7. **Carrier seed in dev stack**: The spec assumes `seed_default_carriers()` is wired into `startup` (alongside `local-ddb-seed.py`) so default carriers exist in the dev stack when E2E tests run. If it is not, section 70 must create all necessary carriers before the rate-estimate test in section 71.

8. **Admin UI routes**: The spec references `/shop/admin/shipments` as the shipment-queue admin page (from SHP-017). If the route is different (e.g. `/shop/admin/shipping`), update sections 72 and 74 accordingly.
