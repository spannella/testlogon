# MKT-013 — Marketing campaigns page, route & nav

## 1. Summary & Goal

MKT-013 delivers the complete frontend surface for the marketing campaigns module: a multi-panel page tree under `frontend/src/pages/marketing/`, a set of lazy-loaded routes in `frontend/src/App.tsx`, and sidebar/mobile-nav entries — all gated on a client-readable `VITE_MARKETING_CAMPAIGNS_ENABLED` feature flag so the entire section is invisible when the module is off.

The goal is to let a user complete the full marketing workflow from the browser: create a marketing campaign, link an ads campaign and promo codes to it, build a static contact list, define a rule-based segment and run a live count via the `evaluate` endpoint, mint a tracking code, trigger a send, and read the attribution roll-up panel. An admin can additionally visit the pending-review queue for campaigns requiring review. Every page consumes the MKT-012 API wrappers and backend routes from MKT-011; this ticket adds no new backend logic.

The ads page tree at `frontend/src/pages/ads/` (lazy imports at `frontend/src/App.tsx:179-229`) is the closest structural precedent:

- `CampaignList.tsx:27-185` is 185 lines: `useQuery` for list, `useMutation` for create/status-update, a `CampaignEditor` dialog component, status badge `Record<string, variant>`, and per-item action buttons.
- The `CampaignEditor.tsx` component (`CampaignEditor.tsx:31-38`) is a controlled `Dialog` with props `open`, `onOpenChange`, `onSubmit`, `isPending`, `defaultValues`, `title` — MKT-013 mirrors this pattern for `MarketingCampaignEditor`. Note: the existing `CampaignEditor` has no `mode` prop; it is stateless and caller-driven via `defaultValues`.

### 2.2 Feature-flag routing pattern

Three guard patterns already exist for feature-flagged routes:

1. **Broadcast** (App.tsx:280, 396-398): `const showBroadcastNavigation = isBroadcastNavigationEnabled()` in the `App` component body; route is rendered conditionally `{showBroadcastNavigation && <Route …/>}`.
2. **Agent SSH QA** (App.tsx:279, 518-520): same pattern with `isAgentSshQaEnabled()`. Note: `isBroadcastNavigationEnabled()` also uses a kill-switch (`broadcastNavigationEnabled && !broadcastNavigationKillSwitch`, `featureFlags.ts:164-167`); marketing MVP uses a simpler single-bool flag (no kill-switch), matching the inventory pattern.
3. **Inventory admin** (Sidebar.tsx:263): `showInventoryAdmin = isInventoryReservationsEnabled() && canAccessGeneralAdminControls(accessToken)` — combines flag with role check.

MKT-013 follows pattern 1: a single `const showMarketingCampaigns = isMarketingCampaignsEnabled()` boolean in the `App()` component body, then each marketing route is wrapped `{showMarketingCampaigns && <Route …/>}`.

### 2.3 Feature-flag definition pattern

`frontend/src/lib/featureFlags.ts` follows a consistent structure (186 lines total):


The inventory flag (`inventoryReservationsEnabled`, `featureFlags.ts:161`) defaults to `false` — the same default MKT-013 requires. A kill-switch variant is not needed at MVP.

## 3. Data Model

MKT-013 is a pure frontend ticket. It introduces no DynamoDB tables, no backend models, and no settings changes. All DDB/model work is owned by MKT-001 through MKT-011.

The frontend data model is the shape of the React Query cache keys and the TS interface set provided by MKT-012:

| Query key | Description |
|-----------|-------------|
| `["marketing-campaigns"]` | owner's campaign list |

| `["contact-lists"]` | owner's list list |
| `["contact-list", listId]` | single list meta |

No Zustand store is needed — all state is server-side via React Query. Local dialog state (create/edit open) is `useState`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Route structure

All routes are under `marketing/` (inside the `<AppShell>` protected block):

| Path | Component | Notes |
|------|-----------|-------|
| `marketing/campaigns` | `MarketingCampaignListPage` | Campaign list + create dialog |
| `marketing/campaigns/:campaignId` | `MarketingCampaignDetailPage` | Tabs: Overview, Links, Send, Attribution |
| `marketing/lists` | `ContactListManagerPage` | List CRUD + member management |
| `marketing/lists/:listId` | `ContactListDetailPage` | Members table + seed-from-contacts |
| `marketing/segments` | `SegmentBuilderPage` | Segment CRUD + live evaluate |
| `marketing/tracking-codes` | `TrackingCodeManagerPage` | Tracking code CRUD |
| `marketing/attribution` | `AttributionPanelPage` | Cross-campaign attribution summary |
| `marketing/admin` | `MarketingAdminReviewPage` | Admin/root only — pending review queue |

All routes are wrapped `{showMarketingCampaigns && <Route … />}` in App.tsx. The admin route additionally checks `canAccessGeneralAdminControls(accessToken)` at render time (renders nothing with a `null` return if not admin/root — no redirect, consistent with the existing pattern for `admin/` routes that don't actively redirect).

### 5.2 MarketingCampaignListPage

The campaign list page follows `CampaignList.tsx` structurally:

- `useQuery(["marketing-campaigns"], listMarketingCampaigns)` — staleTime 30 000 ms.
- Campaign rows display: name, objective, status badge, budget, linked ads campaign name, linked promo count, tracking code slug.
- Status badge variant map: `draft → "outline"`, `scheduled → "secondary"`, `active → "default"`, `paused → "secondary"`, `completed → "outline"`, `archived → "outline"`, `pending_review → "secondary"`.
- Lifecycle action buttons per status:
  - `draft`: **Submit for Review** (`transition → pending_review`), **Delete/Archive**
  - `pending_review`: no owner actions (awaiting admin)
  - `active`: **Pause**, **Archive**
  - `paused`: **Resume** (`transition → active`), **Archive**
  - `scheduled`: **Cancel** (`transition → draft`)
  - `completed` / `archived`: no actions
- A **New Campaign** button opens `MarketingCampaignEditor` dialog.
- Invalidates `["marketing-campaigns"]` on any mutation success.

### 5.3 MarketingCampaignEditor

A `Dialog` component, receivable as either `mode="create"` or `mode="edit"` with a `campaign` prop. Fields:

- `name` (required, string)
- `objective` (required, select: `"awareness" | "acquisition" | "retention" | "conversion"`)
- `budget_cents` (number input, displayed as dollars — convert ×100 on submit)
- `start_at` / `end_at` (optional date inputs, converted to Unix timestamps)
- `notes` (optional textarea)

On create, calls `createMarketingCampaign(body)`. On edit, calls `updateMarketingCampaign(campaignId, body)`. Uses React Hook Form + Zod for validation. Error from `useMutation` displayed via `toast.error(...)` from `sonner` (consistent with `PromoCodesPage.tsx` pattern).

### 5.4 MarketingCampaignDetailPage

Accessed at `marketing/campaigns/:campaignId`. Uses `useParams()` to extract `campaignId`.

Tab layout (shadcn/ui `Tabs`, mirroring `BillingPage.tsx` pattern):

1. **Overview** — campaign metadata display; edit button opens `MarketingCampaignEditor` in `mode="edit"`.
2. **Links** — two sub-sections: Ads Campaign picker + Promo Codes picker.
3. **Send** — audience summary (selected list + segment names), **Send Campaign** button (POST 202 returns immediately, toast "Send initiated").
4. **Attribution** — renders `AttributionPanel` component (see §5.8).

Navigation via `useSearchParams` to persist the active tab across navigation (pattern: `?tab=links`).

### 5.5 LinkPickerDialog (Ads Campaign)

A `Dialog` showing `listCampaigns(accountId)` results from the existing `ads.ts` wrapper. Requires the user to have an ad account: if `listMyAdAccounts()` returns an empty array, shows an informational message "No ad account found — create one in Ads Manager". On selection, calls `attachAdCampaign(campaignId, { ad_campaign_id })`. On deselect, calls `detachAdCampaign(campaignId)`. Invalidates `["marketing-campaign", campaignId]`.

The ad account ID must be resolved first via `listMyAdAccounts()` (from `ads.ts`); the account selector matches the existing `CampaignList.tsx:29` pattern (`useSearchParams` for `?account=`).

### 5.6 LinkPickerDialog (Promo Codes)

A `Dialog` showing `listPromoCodes()` results from `promoCodes.ts`. Supports multi-select (checkbox list). Calls `attachPromoCode(campaignId, codeId)` per selection and `detachPromoCode(campaignId, codeId)` per deselection. Only shows active, non-expired promo codes; expired codes are shown as disabled items. Invalidates `["marketing-campaign", campaignId]`.

### 5.7 ContactListManagerPage and ContactListDetailPage

`ContactListManagerPage`:
- Lists all contact lists via `useQuery(["contact-lists"], listContactLists)`.
- Create button opens a simple name/description dialog (`createContactList`).
- Each list row shows name, `member_count`, created_at.
- Click navigates to `marketing/lists/:listId`.

`ContactListDetailPage`:
- Header: list name + member count.
- Members table with columns: party display name (if resolvable), email, `opted_out` badge, `joined_at`.
- **Add Member** button — opens a dialog with a party-ID/email input field; calls `addMember(listId, { party_id })`.
- **Remove** per row calls `removeMember(listId, partyId)`.
- **Seed from Contacts** button calls `seedFromContacts(listId)` and invalidates `["contact-list-members", listId]`. Shows a toast with the count returned by the API.
- Opted-out members are shown with a `Badge variant="secondary"` "Suppressed" label — visible to the owner but excluded from sends (enforced server-side).

### 5.8 SegmentBuilderPage

- Lists segments via `useQuery(["party-segments"], listSegments)`.
- Create/edit uses a predicate builder UI: a list of predicate rows, each with three fields — **Attribute** (select from server-enumerated values), **Operator** (select: `eq | neq | gt | gte | lt | lte | in | not_in`), **Value** (text/number input).
- **Evaluate** button (per segment): calls `evaluateSegment(segmentId)` via `useMutation`, stores result in local state, displays "Matching: N parties" below the segment row. `staleTime` for this query is 0 — always refetch on button press (live count).
- **Snapshot** button: calls `snapshotSegment(segmentId)`; shows a toast "Snapshot created: <snapshot_id>".
- Opted-out parties are excluded from send resolution but the evaluate count is the raw count. A footnote: "Final send count may be lower due to opt-out suppression."
- Segment CREATE/UPDATE uses React Hook Form; unknown attribute or operator yields a 422 from the backend which is surfaced as a toast.

### 5.9 TrackingCodeManagerPage

- Lists tracking codes via `useQuery(["tracking-codes"], listTrackingCodes)`.
- Create dialog: `name` (required), `redirect_url` (required URL field), optional `campaign_id` picker.
- Each row shows: `slug` (monospace), campaign name link, visit/order counts from `TrackingCodeOut.visit_count`/`order_count`, copy-to-clipboard button for the full `GET /ui/marketing/t/{slug}` URL. The frontend computes the public URL as `window.location.origin + "/ui/marketing/t/" + slug`.
- Slug is read-only after creation. Duplicate slug → 409 → toast "Tracking code slug already in use".

### 5.10 AttributionPanelPage and AttributionPanel component

`AttributionPanel` is a pure presentational component accepting a `CampaignAttributionOut` prop:

```
┌─ Attribution ──────────────────────────────────────┐
│  Ad Spend        $<ad_spend_cents / 100>           │
│  Promo Discount  $<promo_discount_cents / 100>     │
│  Visits          <visit_count>                     │
│  Orders          <order_count>                     │
│  Redemptions     <redemption_count>                │
│  as of           <as_of formatted>                 │
└────────────────────────────────────────────────────┘
```

Used in two places:
1. The **Attribution** tab of `MarketingCampaignDetailPage` — single-campaign view.
2. `AttributionPanelPage` at `marketing/attribution` — shows all campaigns in a table with per-row attribution, sorted by visit_count descending.

Data for `AttributionPanelPage` is fetched via `useQuery(["marketing-campaigns"], listMarketingCampaigns)` + per-campaign `useQuery(["marketing-attribution", id], () => getAttribution(id))` in a loop. For MVP this is N+1; a dedicated batch endpoint is a follow-up.

### 5.11 MarketingAdminReviewPage

Gated to admin/root. Shows campaigns in `pending_review` status fetched from `GET /ui/admin/marketing/campaigns/pending`. Each row shows campaign owner, name, objective, budget. **Approve** and **Reject** buttons call `POST /ui/admin/marketing/campaigns/{id}/review` with `{ decision: "approve" | "reject", notes }`. Rejection opens a notes dialog. Invalidates on success.

### 5.12 Flag-off behavior

When `isMarketingCampaignsEnabled()` returns false:

- All `marketing/*` routes render nothing (conditional rendering in `App.tsx`).
- The sidebar Commerce section marketing items are filtered out by the path-based filter in the `NAV_GROUPS` filter closure.
- The mobile nav `MORE_LINKS` marketing entry is filtered.
- Navigating directly to `/marketing/campaigns` with flag off renders the `<AppShell>` outlet with no matching route — React Router falls through to `<Route path="*" element={<ErrorPage status={404} />} />` (the existing catch-all at `App.tsx:558`), rendering a 404 "Page Not Found" screen with a "Back to Dashboard" button.
- No API calls are made; no backend data is fetched.

### 5.13 Error states

- 403/404 from any mutation: `toast.error(err.response?.data?.detail ?? "Something went wrong")` — consistent with `PromoCodesPage.tsx`.
- Backend 404 on `getMarketingCampaign`: the detail page renders `<ErrorPage status={404} title="Campaign not found" />` using the existing `components/shared/ErrorPage` (`ErrorPage.tsx:5-8`; props are `status`, `title`, `description` — no `message` prop).
- Network error on evaluate: treat as 0 count, show "Could not fetch count" inline.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

MKT-013 is frontend-only. All API calls go through the Vite proxy (`/ui/*` → `http://localhost:8000`) in dev and the same nginx proxy path in production. No `import.meta.env.DEV` branches exist in the new components. CSRF header handling is inherited from `api/client.ts` which already attaches the `x-csrf-token` cookie header to all non-GET requests (consistent with the existing pattern).

### Idempotency

The UI does not need special idempotency handling beyond:
- **Create campaign**: if the user double-clicks, the `useMutation` `isPending` state disables the Submit button during the in-flight request. The backend deterministic-id scheme (MKT-004) ensures a retried POST returns the existing campaign with 200 rather than creating a duplicate — the frontend's `onSuccess` invalidation is safe to re-run.
- **Send campaign**: the Send button is disabled while `sendMut.isPending`. A 202 response always invalidates `["marketing-campaign", campaignId]` and shows a toast; a re-click re-sends (intentional — the user may want to send again with a fresh snapshot). The backend dedup (MKT-009 per `(campaign_id, snapshot_ts, party_id)`) prevents double delivery.

### Security

- No secrets are stored client-side. The tracking code slug is the only credential for the public visit redirect; it is not displayed in the browser history URL — the slug is in the redirect path only.
- `MarketingAdminReviewPage` checks `canAccessGeneralAdminControls(accessToken)` (from `adminCapabilities.ts`) in the component body and returns `null` before rendering, so the review UI never appears for non-admin users even if the flag is on.
- Attribution data is fetched under `require_ui_session` — the response is owner-scoped by MKT-011's `_require_campaign_owner` helper. The frontend does not add any additional access control beyond what the session cookie enforces.

## 10. Open Questions / Assumptions

1. **Assumption**: `VITE_MARKETING_CAMPAIGNS_ENABLED` is a build-time env var (identical to `VITE_INVENTORY_RESERVATIONS_ENABLED`), not a runtime server-fetched flag. If the requirement changes to runtime toggling (e.g., for A/B), a `/ui/config/features` endpoint and `useFeatureFlags` hook are a follow-up.

2. **Assumption**: The `marketing/campaigns` root path does not collide with the existing `agents/marketing` tree (App.tsx:538-541). Confirmed — one is `/marketing/*` the other is `/agents/marketing/*`. React Router evaluates children sequentially so these do not overlap.

3. **Assumption**: The `AttributionPanelPage` at `marketing/attribution` uses per-campaign `getAttribution` calls (N+1). For typical MVP usage (< 20 campaigns per user) this is acceptable. A batch attribution endpoint is a performance follow-up for MKT-015+.

4. **Assumption**: `MarketingAdminReviewPage` is accessible to both ADMIN and ROOT roles (using `canAccessGeneralAdminControls(accessToken)` from `adminCapabilities.ts`), consistent with other admin pages like `InventoryAdmin`. If marketing review requires a finer-grained scope (e.g., a `marketing_review` admin scope), that is a follow-up.

5. **Assumption**: MKT-012 delivers all TS types and API wrapper functions before MKT-013 starts. The MKT-013 component stubs will have import errors until MKT-012 is merged.

6. **Assumption**: The `evaluate_segment` endpoint (MKT-008) can be called on-demand from the UI without rate-limit concern for MVP (a single user evaluating their own segments). If abuse is a concern, the existing `_ai_rate_limit_or_429` pattern from `app/routers/messaging.py` can be applied server-side.

7. **Assumption**: The `LinkPickerDialog` for ads campaigns requires the user to already have an ad account (visible from `listMyAdAccounts()`). If the user has no ad account, the picker shows an empty state with a link to `/ads/dashboard`. This is an acceptable UX shortcut — the alternative is an inline ad-account create flow, which is out of scope.

8. **Assumption**: `ContactListMemberOut` includes a `opted_out: bool` field (per MKT-007 behavior) so the UI can render the "Suppressed" badge without a separate lookup.

9. **Open question**: Should the Segment builder support compound predicates (AND/OR logic) in the MVP UI, or only flat AND-only lists? The MKT-008 spec describes predicates as a flat list (implicitly AND). The UI should match: a flat list of predicate rows with no AND/OR toggle in MVP, deferring compound logic to a follow-up.

10. **Open question**: Should the tracking-code `redirect_url` be validated client-side as a full URL (using `new URL(...)`)? Recommendation: yes — a Zod `string().url()` schema in the create dialog prevents obviously malformed redirects being stored, consistent with the general Zod validation approach in existing forms.
