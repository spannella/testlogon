# MFG-007 — Work-order lifecycle service (issue → produce)

## 1. Summary & Goal

MFG-007 implements `app/services/manufacturing_work_orders.py`, the production-run
engine that bridges the BOM (MFG-004) and inventory (`app/services/inventory.py`)
subsystems. It delivers:

1. **Work-order creation** — deterministic `work_order_id = sha256(correlation_id)[:32]`
   (same scheme used by `commerce_order_service.py:67`), resolving the active BOM
   automatically when the caller omits `bom_id`.
2. **State machine** — `created → released → in_progress → completed` (plus
   `cancelled` from `released` or `in_progress`). Illegal transitions → 409.
3. **Component issue (release step)** — explodes the BOM for the build quantity
   (via `manufacturing_bom.explode_bom`) then calls
   `inventory.adjust(component_sku, -required_qty, reason="mfg_issue")` for each
   leaf component. Records one `ISSUE#{n:04d}` row per component for traceability.
   Insufficient component stock → 409, entire release rolled back (no partial issue
   in Phase 1). An `issues_guard = "done"` flag on the header prevents double-issue
   on replay.
4. **Finished-goods receipt (complete step)** — calls
   `inventory.adjust(product_sku, +produced_qty, reason="mfg_produce")` exactly
   once, gated by a `produce_guard = "done"` flag; replayed completion is a no-op.
5. **Cancel** — optionally un-issues all components (configurable flag
   `mfg_cancel_unissue_enabled`, default `true`) by calling
   `inventory.adjust(component_sku, +issued_qty, reason="mfg_unissue")` per issued
   component; never produces finished goods.
6. **Audit trail** — every transition emits `alerts.audit_event` best-effort.

The service is additive, flag-gated (`manufacturing_mrp_enabled`, default OFF).
With the flag off, the entire module is dormant: existing shop/cart/orders/billing
code is byte-for-byte unchanged.

### 2.1 Inventory adjust primitive

Negative `delta` is guarded at `inventory.py:256–260`:

instances, roll back any already-issued components, and re-raise a descriptive 409
to the caller.

### 2.3 Deterministic work-order ID

`app/services/commerce_order_service.py:66–67`:

```python

order_id = hashlib.sha256(corr.encode("utf-8")).hexdigest()[:32]
```

`create_work_order` follows the identical pattern:
`work_order_id = hashlib.sha256(corr.encode()).hexdigest()[:32]`, where `corr` is

### 2.4 Step-guard idempotency pattern

The ticket cites "per-step guard flag" for replay protection. The
`returns_rma.receive_return` function (`returns_rma.py:409–438`) uses a
`status = approved` conditional `update_item` guard (the `_transition` helper at
`returns_rma.py:420` writes `approved → received` and returns `None` on replay).
MFG-007 uses an `issues_guard`
/ `produce_guard` string attribute on the META row instead of status alone,
because status changes across multiple transitions and a replayed `POST .../complete`
on an already-`completed` order must also be blocked (not just the first call).

### 2.5 BOM explosion input

`manufacturing_bom.explode_bom(bom_id, build_qty)` (MFG-004) returns:
```
[{"component_sku": str, "required_qty": int, "depth": int}, ...]
```
Each `required_qty` is `ceil(quantity_per / output_quantity * build_qty * (1 + scrap_pct))`
per `docs/ofbiz/specs/MFG-004.md:343`. MFG-007 calls this function during release
and stores the results as `ISSUE#` rows before touching inventory.

### 2.6 State machine transitions

Valid transitions (mirrors `returns_rma.py:53–60` pattern):

```
created    → released | cancelled
released   → in_progress | cancelled
in_progress→ completed | cancelled
completed  → (terminal)
cancelled  → (terminal)
```

Issue step runs on `created → released` transition.
Produce step runs on `in_progress → completed` transition (or `released → completed`
as a shortcut — see Section 5.3).
Cancel un-issue runs on any `→ cancelled` transition only if `issues_guard == "done"`.

### 2.8 Audit wrapper precedent

`app/services/inventory.py:92–98` (local import of `alerts.audit_event`, swallows

## 3. Data Model

All rows for a single production run live in the `mfg_work_orders` table partition
`PK = work_order_id`, provisioned by MFG-002 (`scripts/local-ddb-init.py:2492+`).

### 3.1 Row types in a single partition

| SK | Purpose |
|----|---------|
| `META` | Work-order header |
| `ISSUE#{n:04d}` | One row per component issued (1-based, zero-padded to 4 digits) |
| `EVENT#{ts:010d}#{event_id}` | Append-only state-transition log |

### 3.2 Header row (`SK = "META"`)

| Attribute | DDB Type | Notes |
|-----------|----------|-------|
| `work_order_id` (PK) | S | `sha256(correlation_id)[:32]` |
| `sk` | S | `"META"` |
| `product_sku` | S | Finished-goods SKU |
| `quantity` | N | Ordered build quantity |
| `produced_qty` | N | Actual produced qty (0 until complete step) |
| `bom_id` | S | BOM used; resolved if not provided by caller |
| `work_center_id` | S | Optional; empty string `""` if not assigned |
| `status` | S | `created`, `released`, `in_progress`, `completed`, `cancelled` |
| `correlation_id` | S | Caller seed for deterministic id |
| `issues_guard` | S | `""` initially; `"done"` after issue step completes atomically |
| `produce_guard` | S | `""` initially; `"done"` after produce step completes atomically |
| `location_id` | S | Inventory location (default `"warehouse"`) |
| `user_sub` | S | Creator identity |
| `created_at` | N | Unix seconds (`now_ts()`) |
| `updated_at` | N | Unix seconds |

The `issues_guard` and `produce_guard` fields are written via conditional
`update_item` with `ConditionExpression="issues_guard <> :done"` (and analogously
for `produce_guard`) — DynamoDB's `<>` operator provides the single-writer
CAS required for idempotency. A `ConditionalCheckFailedException` means the step
already ran; the handler returns the current header without error.

### 3.3 Issue row (`SK = "ISSUE#{n:04d}"`)

| Attribute | DDB Type | Notes |
|-----------|----------|-------|
| `work_order_id` (PK) | S | Same as header |
| `sk` | S | `ISSUE#0001`, `ISSUE#0002`, … |
| `seq` | N | 1-based integer matching the SK suffix |
| `component_sku` | S | Exploded leaf component SKU |
| `required_qty` | N | From `explode_bom` result |
| `issued_qty` | N | Equals `required_qty` in Phase 1 (no partial issue) |
| `status` | S | `issued` (only written when actually issued) |
| `issued_at` | N | Unix seconds |
| `location_id` | S | Inventory location adjusted |

Issue rows are written in a batch immediately before the `issues_guard` flip. They
are never updated after writing.

### 3.4 Event row (`SK = "EVENT#{ts:010d}#{event_id}"`)

| Attribute | DDB Type | Notes |
|-----------|----------|-------|
| `work_order_id` (PK) | S | |
| `sk` | S | `EVENT#` prefixed, sortable ascending |
| `event_id` | S | `uuid4().hex` |
| `from_status` | S | Previous status |
| `to_status` | S | New status |
| `actor_sub` | S | User who triggered the transition |
| `ts` | N | Unix seconds |
| `note` | S | Optional human note (empty string if absent) |

### 3.5 GSIs (from MFG-002 `scripts/local-ddb-init.py:2492+`)

```
GSI_STATUS   PK: status (S)       SK: created_at (N)
GSI_PRODUCT  PK: product_sku (S)  SK: created_at (N)
```

## 4. API / Service Design

### 4.1 Service module: `app/services/manufacturing_work_orders.py`

```python
"""Work-order lifecycle service (MFG-007).

State machine: created → released → in_progress → completed (+ cancelled).
Issue: inventory.adjust(-qty) per component on release.
Produce: inventory.adjust(+qty) on completion.
Both steps are idempotent via header guard flags.
Flag-gated: manufacturing_mrp_enabled (default false).
SECOPS-007: identical code dev (moto/local DDB) and prod (real DDB); no dev_mode branch.
"""
import hashlib
import uuid
from math import ceil
from typing import Any, Dict, List, Optional

from boto3.dynamodb.conditions import Key
from botocore.exceptions import ClientError
from fastapi import HTTPException

from app.core.settings import S
from app.core.tables import T
from app.core.time import now_ts

DEFAULT_LOCATION = "warehouse"
_MFG_CANCEL_UNISSUE_DEFAULT = True

_VALID_TRANSITIONS: Dict[str, set] = {
    "created":     {"released", "cancelled"},
    "released":    {"in_progress", "completed", "cancelled"},
    "in_progress": {"completed", "cancelled"},
    "completed":   set(),
    "cancelled":   set(),
}
```

#### Public functions

```python
def create_work_order(
    product_sku: str,
    quantity: int,
    *,
    bom_id: Optional[str] = None,
    work_center_id: Optional[str] = None,
    correlation_id: Optional[str] = None,
    location_id: str = DEFAULT_LOCATION,
    user_sub: str = "system",
) -> Dict[str, Any]:
    """Create a work order in status=created. Returns the header dict."""

def get_work_order(work_order_id: str) -> Optional[Dict[str, Any]]:
    """Return header + issues list, or None if not found."""

def list_work_orders(
    status: Optional[str] = None,
    product_sku: Optional[str] = None,
    limit: int = 100,
) -> List[Dict[str, Any]]:
    """List work orders (headers only). Filters via GSI_STATUS or GSI_PRODUCT."""

def release_work_order(
    work_order_id: str,
    *,
    actor_sub: str,
) -> Dict[str, Any]:
    """Transition created → released. Explodes BOM and issues all components.
    Raises 409 if insufficient stock; rolls back any partial issues."""

def start_work_order(
    work_order_id: str,
    *,
    actor_sub: str,
) -> Dict[str, Any]:
    """Transition released → in_progress. No inventory side-effect."""

def complete_work_order(
    work_order_id: str,
    *,
    produced_qty: Optional[int] = None,
    actor_sub: str,
) -> Dict[str, Any]:
    """Transition in_progress (or released) → completed. Receives finished goods.
    produced_qty defaults to the work order's quantity if not supplied.
    Idempotent: replayed call returns the current header without double-producing."""

def cancel_work_order(
    work_order_id: str,
    *,
    actor_sub: str,
    note: Optional[str] = None,
) -> Dict[str, Any]:
    """Transition created|released|in_progress → cancelled.
    Un-issues components if issues_guard==done and mfg_cancel_unissue_enabled."""
```

#### Internal helpers

```python
def _get_header(work_order_id: str) -> Optional[Dict[str, Any]]:
    """GET META row only (no ISSUE rows). Returns None if absent."""

def _get_issue_rows(work_order_id: str) -> List[Dict[str, Any]]:
    """Query all ISSUE#{n} rows for the given work order."""

def _require_transition(current: str, target: str) -> None:
    """Raises HTTPException(409) if current→target is invalid."""

def _write_event(work_order_id: str, from_status: str, to_status: str,
                 actor_sub: str, note: str = "") -> None:
    """Put an EVENT row (append-only, best-effort — swallows ClientError)."""

def _issue_components(
    work_order_id: str,
    exploded: List[Dict[str, Any]],
    location_id: str,
    user_sub: str,
) -> List[Dict[str, Any]]:
    """Call inventory.adjust(-required_qty) per component.
    On any 409, reverse all already-issued adjustments and re-raise.
    Returns the list of ISSUE row dicts written to DDB."""

def _unissue_components(
    issue_rows: List[Dict[str, Any]],
    user_sub: str,
) -> None:
    """Reverse-adjust all issued components back into inventory (best-effort per row)."""

def _flip_guard(
    work_order_id: str,
    guard_attr: str,
    new_status: str,
    actor_sub: str,
) -> bool:
    """Atomically set guard_attr="done" + status=new_status on the META row
    using ConditionExpression="attribute_not_exists(guard_attr) OR guard_attr = :empty".
    Returns True if the flip succeeded; False if already done (ConditionalCheckFailed)."""
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Work-order creation

1. Compute `corr = correlation_id or f"mfg_work_order:{uuid4().hex}"`.
2. Compute `work_order_id = hashlib.sha256(corr.encode()).hexdigest()[:32]`.
3. Resolve BOM: if `bom_id` is provided, verify it exists via `T.mfg_boms.get_item`;
   if absent, call `manufacturing_bom.get_active_bom(product_sku)`. No active BOM
   → 422 (`"No active BOM found for SKU"`).
4. Write META row with `status="created"`, `issues_guard=""`, `produce_guard=""`.
   Use `ConditionExpression="attribute_not_exists(work_order_id)"` so a replayed
   POST with the same `correlation_id` hits `ConditionalCheckFailedException` →
   service reads and returns the existing record (idempotent create).

### 5.2 Release: component issue

The release handler is the most complex:

1. Load header; call `_require_transition("created", "released")`.
2. Check `issues_guard`: if already `"done"`, the issue step already completed on a
   previous (partial) call — skip straight to flipping `status="released"`.
3. Call `manufacturing_bom.explode_bom(header["bom_id"], header["quantity"])` to get
   the component list.
4. For each component in explosion order (index `n` starting at 1):
   a. Call `inventory.adjust(component_sku, -required_qty, reason="mfg_issue", location_id=..., user_sub=actor_sub)`.
   b. On success, append the component to `issued_so_far` list and write the
      `ISSUE#{n:04d}` row to `T.mfg_work_orders`.
   c. On `HTTPException(409)` from `inventory.adjust`:
      - Call `_unissue_components(issued_so_far)` to reverse all issued adjustments
        via `inventory.adjust(component_sku, +issued_qty, reason="mfg_unissue")`.
      - Raise `HTTPException(409, detail=f"Insufficient stock for component '{component_sku}': {original_detail}")`.
5. After all components issued successfully, call `_flip_guard(work_order_id, "issues_guard", "released", actor_sub)`.
   - If `ConditionalCheckFailedException` (replay): the ISSUE rows already exist but
     the status flip may not have happened yet — re-read the header and return it.
6. Write EVENT row (`created → released`).
7. Emit `_audit("work_order.released", actor_sub, work_order_id=..., bom_id=..., component_count=n)`.

**Rollback note**: since DynamoDB has no multi-item transactions for this pattern
(and transactions are not used in the existing inventory service), the rollback is
compensating — `_unissue_components` best-effort reverses each component. If a
reversal itself fails (e.g., inventory record was deleted between issue and rollback),
the failure is logged via `_audit("work_order.release_rollback_partial_failure", ...)`.
This is acceptable at Phase 1 scope, consistent with how `returns_rma.py` handles
its own multi-step operations without DDB transactions.

### 5.3 Start: no inventory side-effect

`released → in_progress` is a bookkeeping transition: status flip + EVENT row +
audit. No inventory calls. The `work_center_id` may be updated here if the caller
passes it. Useful for production-floor tracking (MFG-009 UI).

### 5.4 Complete: produce finished goods

1. Load header; call `_require_transition(header["status"], "completed")`.
   Valid source statuses are `released` and `in_progress`.
2. Check `produce_guard`: if already `"done"`, return the current header (idempotent).
3. Resolve `produced_qty = request.produced_qty or header["quantity"]`.
4. Call `inventory.adjust(header["product_sku"], +produced_qty, reason="mfg_produce", location_id=header["location_id"], user_sub=actor_sub)`.
   - `inventory.adjust` with a positive delta on a nonexistent SKU creates the record
     (per `inventory.py:229–248`). Finished goods therefore always land in the inventory
     table even if no prior stock existed.
5. Flip `produce_guard = "done"`, `status = "completed"`, `produced_qty = produced_qty`
   via conditional update:
   ```
   ConditionExpression="produce_guard = :empty"
   UpdateExpression="SET produce_guard=:done, #status=:completed, produced_qty=:pqty, updated_at=:now"
   ```
   On `ConditionalCheckFailedException`: a concurrent completion already ran;
   re-read and return.
6. Write EVENT row (`{from_status} → completed`).
7. Emit `_audit("work_order.completed", actor_sub, work_order_id=..., produced_qty=..., product_sku=...)`.

### 5.5 Cancel: optional un-issue

1. Load header; call `_require_transition(header["status"], "cancelled")`.
2. If `header["issues_guard"] == "done"` and `_cancel_unissue_enabled()`:
   a. Load all `ISSUE#` rows via `_get_issue_rows(work_order_id)`.
   b. Call `_unissue_components(issue_rows, actor_sub)` — best-effort per component.
3. Update header: `status = "cancelled"`, `updated_at = now_ts()`.
   No `produce_guard` flip needed (produce step is permanently skipped for cancelled orders).
4. Write EVENT row and audit event.

`_cancel_unissue_enabled()` reads `bool(getattr(S, "mfg_cancel_unissue_enabled", True))`.

### 5.6 Illegal transitions

Any attempted transition not in `_VALID_TRANSITIONS[current_status]` raises:
```python
HTTPException(409, detail=f"Cannot transition from '{current}' to '{target}'")
```
Follows the same 409 pattern as `returns_rma.py:357–365` (`_require_transition`),
but uses a different detail string (the returns service uses
`f"Illegal return transition {current} -> {target}"` at `returns_rma.py:364`).

### 5.7 Not-found handling

`get_work_order` returns `None` for a missing `work_order_id`. All mutation
handlers call `_get_header(work_order_id)`; if it returns `None` they raise:
```python
HTTPException(404, detail="Work order not found")
```

### 5.8 GSI list pagination

`list_work_orders` queries `GSI_STATUS` or `GSI_PRODUCT`. DynamoDB
`FilterExpression` does not reduce page size (CLAUDE.md gotcha). The implementation
loops via `LastEvaluatedKey` until the requested `limit` is satisfied or all items
are exhausted, consistent with `returns_rma.py`'s paging pattern.

### 5.9 `ISSUE#` zero-padding

`ISSUE#{n:04d}` pads to 4 digits. This supports up to 9,999 components per work
order without sort-key collisions. If a BOM explosion returns more than 9,999 leaf
components, the SK format needs extending — flagged as an edge case assumption in
Section 10.

### 5.10 `produced_qty` vs `quantity` divergence

`produced_qty` may be less than `quantity` (under-production) if the caller passes
a lower value to `complete_work_order`. The service accepts this in Phase 1 without
enforcing equality, so partial completions are allowed. Yield variance accounting is
deferred to MFG-008's costed GL hook.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity**: No `dev_mode` branch exists in the service. `inventory.adjust`
(called for both issue and produce) itself contains no `dev_mode` branch
(`inventory.py:209–300`). The same DDB table (`T.mfg_work_orders`) and the same
`T.inventory` handle are used in both environments. In dev, DynamoDB Local
(port 8001) serves both; in prod, the real DDB endpoint is used. The `moto`
test harness binds the same frozen `T` handles — no environment-specific paths.

**Idempotency**:
- _Create_: `attribute_not_exists(work_order_id)` condition on META `put_item`.
  Replayed create with the same `correlation_id` hits the same `work_order_id` key,
  gets `ConditionalCheckFailedException`, reads and returns the existing record.
- _Issue step_: `issues_guard` CAS: `ConditionExpression="issues_guard = :empty"`.
  Replayed release when `issues_guard == "done"` skips re-issuing components entirely.
- _Produce step_: `produce_guard` CAS analogously.
- _Cancel_: no guard needed; DDB status update on a terminal row is a no-op
  (transition guard already 409s on a second cancel attempt).

**Security**:
- All work-order endpoints require `require_admin_or_root_csrf`
  (`app/auth/policy.py:100–106`), preventing USER-role access.
- Work-order IDs are deterministic but not secret: a `work_order_id` derived from
  `sha256(correlation_id)[:32]` must not be assumed confidential — admin auth is
  the access gate, not ID obscurity.
- Component inventory is adjusted under the `actor_sub` identity, preserving the
  per-user audit trail in `inventory.py`.
- The `correlation_id` is stored on the META row but never surfaced in list
  responses (only detail reads). It should not contain PII; validated to `max_length=256`.
- `_audit` swallows exceptions so a broken `alerts` table can never block a
  production run from completing.

## 10. Open Questions / Assumptions

1. **Assumption: partial issue is not supported in Phase 1.** If component A issues
   successfully but component B has insufficient stock, the entire release is rolled
   back. MFG-009 UI can show the specific blocking component from the 409 detail.
   If partial issue (releasing what's available and back-ordering the rest) is needed,
   it requires a separate `ISSUE#` status=`"pending"` design and is deferred.

2. **Assumption: `released → completed` shortcut is valid.** The state machine allows
   `released → completed` (skipping `in_progress`) for small shops that do not track
   the in-progress phase. The produce step runs the same way regardless of
   whether the source status is `released` or `in_progress`. This is consistent with
   the ticket's stated machine (`created → released → in_progress → completed`) but
   adds the shortcut for practical workflow support.

3. **Assumption: `ISSUE#` zero-padding supports up to 9,999 components.** If a
   production team needs BOMs with more than 9,999 leaf components (after explosion),
   the SK format must be extended to `ISSUE#{n:06d}` before the first row is written.
   This is unlikely at MVP scale.

4. **Assumption: `_unissue_components` is best-effort (no rollback of the rollback).**
   If the compensating inventory reversal for a failed release itself fails (e.g.,
   the inventory row was externally deleted), the failure is audited but not retried.
   This matches the compensation pattern in `returns_rma.py`. A full 2PC or DDB
   transaction scheme would require a redesign; deferred.

5. **Assumption: `explode_bom` is called once per release, not cached.** If the BOM is
   modified between release attempts on the same work order, the second attempt uses
   the updated BOM. This is acceptable because the first attempt would have already
   failed (either stock issue or not committed), so no issued inventory is orphaned.

6. **Assumption: `T.mfg_boms` is readable from `manufacturing_work_orders.py`.**
   `create_work_order` must verify the `bom_id` when supplied. It does this via a
   `T.mfg_boms.get_item` call. This creates a cross-module table dependency: the work
   orders service reads the BOMs table directly. The alternative (delegating to
   `manufacturing_bom.get_bom`) is preferred to avoid coupling to table internals —
   listed as an open question for the implementing engineer to confirm.

7. **Question: should `produce_guard` flip and `inventory.adjust` for produce be wrapped
   in a DynamoDB TransactWrite?** The current design does `inventory.adjust` first,
   then `_flip_guard`. If the server crashes between the two, the inventory is adjusted
   but the `produce_guard` is not set, causing a double-produce on restart. The risk
   is low (inventory was already increased) but not zero. Using
   `T.mfg_work_orders.update_item` with `ConditionExpression` alone cannot atomically
   cover both tables. A `TransactWrite` across `T.inventory` and `T.mfg_work_orders`
   would solve it but is not consistent with how `inventory.adjust` is used elsewhere.
   Recommendation: flip the guard first (CAS), then call `inventory.adjust`. If the
   adjust fails after the guard flip, the work order is marked completed but inventory
   is not updated — less bad than a double-produce. This is an explicit trade-off to
   document in code.

8. **Assumption: `actor_sub` for admin-triggered lifecycle is the admin's `user_sub`
   from the session, not the work order's `user_sub`.** The inventory `adjust` call
   carries `user_sub=actor_sub` so audit events attribute the stock movement to the
   operator who triggered the transition, not the original creator.

9. **Assumption: the `location_id` from the work order header is used for all
   inventory adjustments.** Components and finished goods are assumed to reside in
   the same location. Multi-location cross-issue is deferred.
