# PUR-012 — Reorder-suggestion endpoints + optional background scan

**Type:** Feature | **Priority:** P2 | **Estimate:** 3 days
**Milestone:** 4 — Reorder Suggestions & Background Scan
**Depends on:** PUR-011 (reorder suggestions service), PUR-010 (PO router endpoints)

---

## 1. Summary & Goal

PUR-012 is the HTTP presentation layer and optional background-automation layer for the
reorder-suggestion engine built in PUR-011. It adds two admin-gated endpoints to
`app/routers/purchasing.py` and an optional periodic background task that watches for newly
low-stock SKUs and emits alerts:

1. **`GET /ui/purchasing/reorder-suggestions`** — computes and returns the current set of
   reorder suggestions on demand, grouped by supplier.

2. **`POST /ui/purchasing/reorder-suggestions/{supplier_id}/create-po`** — materializes the
   suggestions for one supplier into a single `draft` PurchaseOrder via the
   `create_purchase_order_from_suggestion` function from PUR-011.

3. **`start_reorder_suggestion_task`** (optional) — a FastAPI startup-registered async loop
   that runs a background reorder scan on a configurable interval, gated by
   `purchase_order_reorder_suggestions_enabled`. When a scan finds SKUs that were not
   low-stock at the previous scan, it emits one `write_alert` per affected admin via
   `app.services.alerts`. Best-effort, non-blocking, never raises out of the loop.

Both endpoints and the background task gate on **two flags**: the master switch
`purchasing_scm_enabled` (returning 404 when off) and the sub-flag
`purchase_order_reorder_suggestions_enabled` (returning 503 when the master is on but
suggestions are disabled). With both flags off, all existing shop/cart/orders/billing/inventory
behavior is byte-for-byte unchanged.

Two new Pydantic models are added to `app/models.py`: `ReorderSuggestionOut` and
`ReorderSuggestionListOut`.

## 3. Data Model

PUR-012 introduces **no new DynamoDB tables**. All tables are established by PUR-002. This
section documents the wire shapes only and describes the dedup-sentinel scheme for the
background scan.

### 3.1 Tables read by PUR-012 (all established by PUR-002)

| Table handle | PK | SK | Role |
|---|---|---|---|
| `T.inventory` | `sku` | `LOC#{location_id}` | Low-stock query via `GSI_AVAILABLE` |
| `T.supplier_products` | `supplier_id` | `SKU#{sku}` | Supplier/cost lookup via `GSI_SKU` |
| `T.purchase_orders` | `po_id` | `sk` | PO creation by suggestion endpoint |
| `T.suppliers` | `supplier_id` | `META` | Supplier name/status lookup |

### 3.2 Background-scan dedup sentinel

The background scan needs to track which (supplier, sku) pairs triggered an alert within
a configurable dedup window to avoid flooding admins on every poll. Sentinels are written as
sparse rows into `T.purchase_orders` with a purpose-specific SK pattern:

```
PK = REORDER_ALERT_SENTINEL#{supplier_id}
SK = SKU#{sku}
ttl_epoch = now + S.reorder_suggestion_alert_dedup_ttl_seconds
```

The conditional `put_item` with `attribute_not_exists(po_id) AND attribute_not_exists(sk)`
acts as an atomic test-and-set (same pattern as `catalog.py:670`). A
`ConditionalCheckFailedException` means the alert fired within the dedup window — suppress.
On success, fire `write_alert` and let DynamoDB TTL reclaim the sentinel row.

This approach reuses `T.purchase_orders` (which already exists and has no schema constraint
on PK format) without adding a new table. The sentinel rows are invisible to PO queries
because no query on `T.purchase_orders` scans for `PK` values starting with
`REORDER_ALERT_SENTINEL#`.

**attr_types note**: No numeric GSI sort key is needed for the sentinel scheme; the
sentinel rows carry only scalar string attributes and a numeric `ttl_epoch` (not a GSI sort
key). No changes to `scripts/local-ddb-init.py` are required for the sentinel beyond what
PUR-002 already provisions for `T.purchase_orders`.

#### 4.2.1 Compute reorder suggestions on demand

```
GET /ui/purchasing/reorder-suggestions
Auth:  require_admin_or_root
200:   ReorderSuggestionListOut
404:   purchasing_scm_enabled=false OR purchase_order_reorder_suggestions_enabled=false
       (both flags raise 404 per PUR-011 _require_enabled())
```

```python
@purchasing_router.get("/reorder-suggestions", response_model=ReorderSuggestionListOut)
async def get_reorder_suggestions(
    user: AuthenticatedUser = Depends(require_admin_or_root),
):
    result = await asyncio.to_thread(reorder_svc.compute_suggestions)
    flat_suggestions = [
        _suggestion_out(ln, s)
        for s in result["suggestions"]
        for ln in s.get("lines", [])
    ]
    warnings = [
        ReorderSuggestionWarningOut(**w) for w in result.get("warnings", [])
    ]
    return ReorderSuggestionListOut(
        suggestions=flat_suggestions,
        warnings=warnings,
        total_skus_low=len(flat_suggestions),
        scanned_at=result.get("scanned_at", 0),  # PUR-011 key is "scanned_at"
    )
```

`compute_suggestions()` from PUR-011 is synchronous (boto3 DynamoDB calls) and is therefore
wrapped in `asyncio.to_thread` to avoid blocking the event loop — the same technique used
in `app/routers/google_drive_integration.py` [VERIFIED: lines 160,240,340] per CLAUDE.md.
The function raises `HTTPException(404)` when either flag is off
(`docs/ofbiz/specs/PUR-011.md:222–224`); propagates naturally through FastAPI.

Note: PUR-011's `compute_suggestions()` returns supplier-grouped `ReorderSuggestion` dicts
(each containing `supplier_id`, `supplier_name`, a `lines` list, and
`suggestion_correlation_id`) — not a flat per-SKU list. The router flattens each
`suggestion["lines"]` into `ReorderSuggestionOut` entries tagged with their `supplier_id`.

`_suggestion_out(line: Dict, suggestion: Dict) -> ReorderSuggestionOut` is a module-level
helper (see Section 5.4) that maps a service line dict plus its parent suggestion dict to
the Pydantic model, handling `Decimal` coercion.

#### 4.2.2 Materialize suggestion into draft PO

```
POST /ui/purchasing/reorder-suggestions/{supplier_id}/create-po
Auth:  require_admin_or_root_csrf
Body:  (none required)
200:   PurchaseOrderOut  (the created/existing draft PO)
404:   purchasing_scm_enabled=false OR purchase_order_reorder_suggestions_enabled=false
       (both flags raise 404 per PUR-011 _require_enabled())
409:   no low-stock SKUs for this supplier (no suggestion to materialize)
```

```python
@purchasing_router.post(
    "/reorder-suggestions/{supplier_id}/create-po",
    response_model=PurchaseOrderOut,
)
async def create_po_from_suggestion(
    supplier_id: str,
    user: AuthenticatedUser = Depends(require_admin_or_root_csrf),
):
    # compute_suggestions() returns grouped suggestions; find the one for supplier_id
    suggestions_result = await asyncio.to_thread(reorder_svc.compute_suggestions)
    suggestion = next(
        (s for s in suggestions_result.get("suggestions", [])
         if s.get("supplier_id") == supplier_id),
        None,
    )
    if suggestion is None or not suggestion.get("lines"):
        raise HTTPException(409, f"No low-stock SKUs for supplier {supplier_id}")
    result = await asyncio.to_thread(
        reorder_svc.create_purchase_order_from_suggestion,
        suggestion,                  # positional: the suggestion dict
        actor_sub=user.sub,          # keyword-only
    )
    return _po_out(result)
```

`create_purchase_order_from_suggestion` (PUR-011) takes the **full suggestion dict** as its
first positional argument, reads `suggestion["suggestion_correlation_id"]` as the PO
correlation key (a sha256 of the supplier_id + sorted SKU set —
`docs/ofbiz/specs/PUR-011.md:362–364`), then calls `purchase_orders.create_purchase_order`
from PUR-006. The 409 guard for no suggestions is handled **in the router** before calling
the service. It raises `HTTPException(404)` if either flag is off. The returned PO is in
`draft` status. If a PO with the same `suggestion_correlation_id` already exists (same SKU
set), the service returns the existing PO unchanged (idempotent — conditional `put_item`
on `po_id`).

`_po_out` is the same helper already defined in the purchasing router by PUR-010 (Section
5.3 of the PUR-010 spec).

### 4.3 Background scan startup function (`app/services/reorder_suggestions.py`)

The background task lives in the service module, not the router, following the pattern of
`start_audit_export_worker_task` in `app/services/audit_export_worker.py:129`. This keeps
the business logic out of the router layer.

```python
# app/services/reorder_suggestions.py  (additions for PUR-012)

import asyncio
import logging

logger = logging.getLogger(__name__)

_REORDER_SCAN_INITIAL_DELAY_SECONDS = 30   # let startup tasks finish

async def _reorder_suggestion_loop() -> None:
    """Periodic background scan for new low-stock SKUs (PUR-012)."""
    await asyncio.sleep(_REORDER_SCAN_INITIAL_DELAY_SECONDS)
    _last_sku_set: set[str] = set()
    while True:
        if S.purchase_order_reorder_suggestions_enabled:
            try:
                result = compute_suggestions()
                current_skus = {s["sku"] for s in result["suggestions"]}
                new_skus = current_skus - _last_sku_set
                if new_skus:
                    _emit_reorder_alert(new_skus, result["suggestions"])
                _last_sku_set = current_skus
            except Exception:
                logger.exception("reorder_suggestion_scan_failed")
        await asyncio.sleep(S.reorder_suggestion_scan_interval_seconds)


async def start_reorder_suggestion_task() -> None:
    """FastAPI startup hook — register the background scan if enabled (PUR-012)."""
    if not S.purchase_order_reorder_suggestions_enabled:
        logger.info("Reorder suggestion background scan disabled")
        return
    asyncio.create_task(_reorder_suggestion_loop())
```

**Alert emission helper** (best-effort, never raises):

```python
def _emit_reorder_alert(new_skus: set[str], all_suggestions: list[dict]) -> None:
    """Emit a purchasing.reorder_suggestion_new_sku alert for newly low-stock SKUs."""
    try:
        from app.services.alerts import write_alert
        from app.core.time import now_ts
        sku_list = sorted(new_skus)
        for sku in sku_list:
            suggestion = next((s for s in all_suggestions if s["sku"] == sku), None)
            if suggestion is None:
                continue
            supplier_id = suggestion.get("supplier_id", "")
            # Dedup sentinel — conditional put on T.purchase_orders
            sentinel_pk = f"REORDER_ALERT_SENTINEL#{supplier_id}"
            sentinel_sk = f"SKU#{sku}"
            try:
                T.purchase_orders.put_item(
                    Item={
                        "po_id": sentinel_pk,
                        "sk": sentinel_sk,
                        "entity": "reorder_alert_sentinel",
                        "ttl_epoch": now_ts() + S.reorder_suggestion_alert_dedup_ttl_seconds,
                    },
                    ConditionExpression=(
                        "attribute_not_exists(po_id) AND attribute_not_exists(sk)"
                    ),
                )
            except ClientError as exc:
                if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
                    continue  # already alerted within dedup window
                continue       # unexpected DDB error — suppress
            # Sentinel placed successfully → fire alert
            write_alert(
                "system",
                event="purchasing.reorder_suggestion_new_sku",
                outcome="warning",
                title=f"Reorder needed: {sku} (supplier {supplier_id})",
                details={
                    "sku": sku,
                    "supplier_id": supplier_id,
                    "available": suggestion.get("available", 0),
                    "reorder_point": suggestion.get("reorder_point", 0),
                    "suggested_qty": suggestion.get("suggested_qty", 0),
                },
            )
    except Exception:
        logger.exception("reorder_alert_emit_failed")
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag hierarchy

Two flags gate the reorder-suggestion functionality:

1. **Master switch** `S.purchasing_scm_enabled`: when `False`, `_require_enabled()` in
   `app/services/purchase_orders.py` (and `app/services/suppliers.py`) raises
   `HTTPException(404)`. The `compute_suggestions()` function also calls this guard because
   it ultimately needs `T.inventory`, `T.supplier_products`, and `T.suppliers` which are
   dormant when the module is off.

2. **Sub-flag** `S.purchase_order_reorder_suggestions_enabled`: when `False` (or when the
   master switch is also `False`), `_require_enabled()` in `reorder_suggestions.py` raises
   `HTTPException(404, "Reorder suggestions are not enabled")`
   (per `docs/ofbiz/specs/PUR-011.md:222–224`; the 503 in the endpoint table above is a
   router-level guard for documentation clarity, but the actual service raises 404).

The background task checks `S.purchase_order_reorder_suggestions_enabled` at the top of
each loop iteration (not just at startup), so the feature can be toggled dynamically
without a restart — matching the cart abandonment loop at `app/routers/shoppingcart.py:327`.

### 5.2 `compute_suggestions()` is not cached

The GET endpoint recomputes suggestions on every call (no caching). Suggestions represent
current inventory state and must be fresh. The background scan maintains its own `_last_sku_set`
in memory to track changes between loops; this state is ephemeral and is re-bootstrapped on
restart (acceptable: the worst case is re-emitting an already-known alert on restart, which
is suppressed by the dedup sentinel in DynamoDB).

### 5.3 Suggestion quantity math (PUR-011 definition)

Per `docs/ofbiz/specs/PUR-011.md:232–242` (function `_suggested_qty`):

```python
moq = max(int(moq), 1)
gap = max(int(reorder_point) - int(available), moq)   # at least one MOQ
remainder = gap % moq
suggested_qty = gap if remainder == 0 else gap + (moq - remainder)  # round up to MOQ multiple
estimated_cost_cents = suggested_qty * unit_cost_cents
```

This math lives in `reorder_suggestions.py` (PUR-011). The router surfaces `suggested_qty`
and `estimated_cost_cents` directly from the service dict without recomputing.

### 5.4 `_suggestion_out` helper

PUR-011's `compute_suggestions()` returns **supplier-grouped** suggestion dicts; each
`suggestion` has `supplier_id`, `supplier_name`, `suggestion_correlation_id`, and a `lines`
list. The router flattens these into per-SKU `ReorderSuggestionOut` entries:

```python
def _suggestion_out(line: Dict[str, Any], suggestion: Dict[str, Any]) -> ReorderSuggestionOut:
    """Map one PUR-011 suggestion line + its parent supplier dict to ReorderSuggestionOut."""
    suggested_qty = _to_int(line.get("suggested_qty"))
    unit_cost_cents = _to_int(line.get("unit_cost_cents"))
    return ReorderSuggestionOut(
        sku=line.get("sku", ""),
        supplier_id=suggestion.get("supplier_id", ""),
        supplier_name=suggestion.get("supplier_name", ""),
        available=_to_int(line.get("available")),
        reorder_point=_to_int(line.get("reorder_point")),
        suggested_qty=suggested_qty,
        unit_cost_cents=unit_cost_cents,
        moq=_to_int(line.get("min_order_qty"), 1),  # field name in PUR-011 is min_order_qty
        lead_time_days=_to_int(line.get("lead_time_days")),
        supplier_sku=line.get("supplier_sku", ""),
        estimated_cost_cents=suggested_qty * unit_cost_cents,
    )
```

`_to_int` is the same helper already defined in the purchasing router (PUR-010 Section 5.3
[VERIFIED: `docs/ofbiz/specs/PUR-010.md:461–465`]).
DynamoDB returns numeric attributes as `Decimal`; the coercion is mandatory to avoid Pydantic
validation errors.

### 5.5 No suggestions for a supplier

When `POST .../reorder-suggestions/{supplier_id}/create-po` is called and the current
`compute_suggestions()` produces no rows for `supplier_id` (e.g. all of that supplier's
SKUs are in-stock), the service raises `HTTPException(409, "No low-stock SKUs for supplier
{supplier_id}")`. The caller receives a 409, not a 200 with an empty PO. This is consistent
with the principle that a PO must have at least one line.

### 5.6 `create-po` idempotency

`create_purchase_order_from_suggestion` uses the `suggestion_correlation_id` pre-computed
by `compute_suggestions()` (PUR-011 §5.1):

```python
# Inside PUR-011 compute_suggestions(), per docs/ofbiz/specs/PUR-011.md:361–364:
import hashlib, json
key = json.dumps({"supplier_id": supplier_id, "skus": sorted(skus)}, sort_keys=True)
suggestion_correlation_id = "reorder:" + hashlib.sha256(key.encode()).hexdigest()[:32]
```

The correlation ID is based on the **sorted set of low-stock SKUs for the supplier**, NOT
on a wall-clock timestamp. Two calls with the same supplier covering the same SKU set produce
the same `po_id`. When the low-stock SKU set changes (a new SKU drops below reorder point,
or a previous one is replenished), the correlation ID changes and a new PO is created.

The `create_purchase_order` service (PUR-006) detects the duplicate via a conditional
`put_item(ConditionExpression="attribute_not_exists(po_id)")` and returns the existing PO
without modification. Callers receive a 200 either way.

The `scanned_at` field from `compute_suggestions()` is informational only — it is NOT part
of the idempotency key.

### 5.7 Warnings (SKUs with no supplier)

`compute_suggestions()` surfaces SKUs in `low_stock` or `out_of_stock` status that have no
entry in `T.supplier_products` as a `"warnings"` list of **dicts** (per PUR-011 §5.3:
`docs/ofbiz/specs/PUR-011.md:384–395`):
```python
{"sku": str, "available": int, "reorder_point": int, "status": str}
```
`ReorderSuggestionListOut.warnings` is `List[ReorderSuggestionWarningOut]` (not `List[str]`).
The `create-po` endpoint only materializes SKUs that have a supplier; warning-only responses
(no `suggestions`, only `warnings`) return 409 rather than creating an empty PO.

### 5.8 Background scan `_last_sku_set` semantics

The background loop tracks the set of SKUs that were in a low/out-of-stock state at the
previous scan. On the first scan after startup, `_last_sku_set` is empty, so **all**
currently low SKUs are treated as "new" — this produces alerts for every low-stock SKU on
the first run. The dedup sentinel prevents duplicate notifications within the TTL window
(`S.reorder_suggestion_alert_dedup_ttl_seconds`, default 3600 s) even if the server
restarts frequently.

If the server restarts, `_last_sku_set` resets to empty and the first scan may re-emit
alerts that were suppressed before the restart — the sentinel in DynamoDB provides the
authoritative dedup across restarts.

### 5.9 Behavior with `inventory_reservations_enabled=false`

`compute_suggestions()` queries `T.inventory` via `inventory.list_low_stock`. That function
does NOT call `_require_enabled()` — it is a pure read and does not gate on the inventory
flag (the flag guards write paths: set_on_hand, adjust, reserve). Therefore
`compute_suggestions()` can return results even when `inventory_reservations_enabled=false`.
If no inventory records exist (e.g. inventory was never seeded), `list_low_stock` returns
an empty list and `compute_suggestions()` returns `suggestions=[]`, `warnings=[]`.

### 5.10 `asyncio.to_thread` requirement

`compute_suggestions()` and `create_purchase_order_from_suggestion()` are synchronous
functions that issue boto3 DynamoDB calls. To avoid stalling the uvicorn event loop, both
router handlers wrap them in `await asyncio.to_thread(...)`. The background loop runs in
a dedicated `asyncio.Task`; within that task the boto3 calls are still synchronous but
they run in an executor thread via the same `asyncio.to_thread` pattern, keeping the main
event loop unblocked.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

Both endpoints and the background scan delegate entirely to `reorder_suggestions.py` and
`purchase_orders.py` which contain no `if S.dev_mode` branches. All DynamoDB access goes
through `T.inventory`, `T.supplier_products`, `T.purchase_orders`, `T.suppliers` whether
backed by DynamoDB Local (dev, `DDB_ENDPOINT_URL=http://localhost:8001`) or real DynamoDB
(prod). No mock/real fork is introduced. Alert emission via `write_alert` writes to
`T.alerts` in both environments — in dev this records to DynamoDB Local; in prod it
additionally dispatches via SES/webhooks per the configured alert preferences. No
`if S.dev_mode` branch in the alert path.

### 7.2 Idempotency

- **GET `/reorder-suggestions`**: purely read-only; idempotent by definition.
- **POST `/{supplier_id}/create-po`**: deterministic `po_id = sha256(f"reorder:{supplier_id}:{snapshot_ts}")[:32]`. A duplicate call within the same wall-clock second produces the same `po_id` and returns the existing PO unchanged (PUR-006 conditional `put_item`). Calls separated by more than one second produce a new PO with a fresh snapshot timestamp.
- **Background scan alert**: dedup sentinel in `T.purchase_orders` with TTL provides cross-restart idempotency. Two scan iterations within the `reorder_suggestion_alert_dedup_ttl_seconds` window for the same (supplier, sku) emit only one alert.

### 7.3 Security

- **CSRF**: `POST .../create-po` uses `require_admin_or_root_csrf` [VERIFIED:
  `app/auth/policy.py:100–106`] which calls `enforce_cookie_csrf` at
  `app/auth/policy.py:71–97` [VERIFIED]. Bearer-token API clients skip CSRF.
- **Role isolation**: Both endpoints require `ADMIN` or `ROOT` role. A `USER`-role session
  receives 403 via `role_required_error` at `app/auth/policy.py:13–22`.
- **No money movement at this layer**: `create-po` only creates a `draft` PO. No ledger
  entry, no payment method charge. Money-out is initiated only later (PUR-009) when an
  admin explicitly pays the AP payable on a `received` PO.
- **Background task runs as "system"**: `_emit_reorder_alert` passes `user_sub="system"` to
  `write_alert`. No user's session or authorization is used inside the background loop.
- **Input caps**: `supplier_id` path parameter inherits FastAPI string defaults (max length
  enforced in the service layer via `get_supplier` validation from PUR-003).

With `PURCHASING_SCM_ENABLED=false` (the default), every new endpoint returns 404 at the
service layer. With `PURCHASE_ORDER_REORDER_SUGGESTIONS_ENABLED=false`, the

### 8.2 `app/models.py` additive change

Two new Pydantic model classes are appended to `app/models.py`. All models are loaded at
startup regardless of flag state. This has no runtime cost and means the new shapes appear
in `/openapi.json` even when the flags are off.

### 8.3 `app/main.py` additive change

One import and one `add_event_handler("startup", ...)` call are added. When
`purchase_order_reorder_suggestions_enabled=false`, `start_reorder_suggestion_task` logs and
returns immediately — no `asyncio.Task` is created and the startup time is unaffected.

### 8.4 DynamoDB sentinel rows in `T.purchase_orders`

The background alert dedup sentinel writes rows with non-standard `po_id` values
(`REORDER_ALERT_SENTINEL#...`). These rows are never returned by `list_purchase_orders`
because that function queries by `GSI_STATUS` or `GSI_SUPPLIER` — both partition keys must
match specific `status` or `supplier_id` values, neither of which the sentinel rows carry.
The sentinel rows are also DynamoDB-TTL reclaimed automatically. No migration or schema
change is required.

### 8.5 `scripts/local-ddb-init.py` — no change

No new table definitions are needed. The two new settings keys (`reorder_suggestion_scan_interval_seconds`, `reorder_suggestion_alert_dedup_ttl_seconds`) are simple integers on `S` and have no DynamoDB representation.

## 10. Open Questions / Assumptions

**A1 — `compute_suggestions()` return shape from PUR-011**: ~~RESOLVED~~ — verified against
`docs/ofbiz/specs/PUR-011.md`. The actual return shape is:
```python
{
    "suggestions": [<supplier-grouped dicts with "lines" sub-list>],
    "warnings":    [{"sku": str, "available": int, "reorder_point": int, "status": str}, ...],
    "scanned_at":  int,   # NOT "generated_at", NOT "total_skus_low"
}
```
The router flattens `suggestions[*].lines` into `ReorderSuggestionOut` items. Idempotency
uses `suggestion["suggestion_correlation_id"]` (SKU-set hash), not `scanned_at`.

**A2 — `create_purchase_order_from_suggestion` snapshot freshness**: ~~RESOLVED~~ — per
`docs/ofbiz/specs/PUR-011.md:302–345` the function signature is
`create_purchase_order_from_suggestion(suggestion: Dict, *, actor_sub, ...)`. The router
must call `compute_suggestions()` first, locate the target supplier's suggestion dict, then
pass the full dict to `create_purchase_order_from_suggestion`. This is a double-scan
(compute in both GET and POST) but avoids shared server-side state.

**A3 — Flat vs grouped suggestion response**: `ReorderSuggestionListOut.suggestions` is a
flat list sorted by `supplier_id`+`sku`. A grouped-by-supplier dict (`{supplier_id:
[suggestions]}`) would be more natural for the `create-po` workflow but breaks the standard
list response pattern used elsewhere. The frontend can group client-side. **Confirm with
product/frontend team whether a grouped shape is preferred for PUR-012 or deferred to
PUR-013 (TypeScript types).**

**A4 — Background scan alert recipient**: `write_alert("system", ...)` writes an alert
row in `T.alerts` with `user_sub="system"`. This is not surfaced to any admin's alert
feed unless `"system"` alerts are displayed in the admin alerts UI. An alternative is to
broadcast to all users with the `ADMIN` or `ROOT` role. The ticket says "emits an alert" —
the simplest interpretation is an audit record. **Confirm the intended delivery channel
(audit log only vs admin alert feed) with product.**

**A5 — Dedup sentinel placement**: This spec places dedup sentinels in `T.purchase_orders`
to avoid adding a new table. If this pollutes PO queries in unforeseen ways, a dedicated
`T.purchasing_alerts` table or a key in `T.alerts` would be cleaner. **Review with the
PUR-002 table-design owner before implementing.**

**A6 — `asyncio.to_thread` in the background loop**: The background loop itself runs as an
`asyncio.Task`. The spec wraps `compute_suggestions()` in `asyncio.to_thread` within the
loop. An alternative is to make `compute_suggestions()` natively async (wrapping the boto3
calls internally). The per-call overhead of `asyncio.to_thread` is minimal (microseconds)
and the approach keeps the service layer synchronous (consistent with `inventory.list_low_stock`
at `app/services/inventory.py:318`). **Confirm preferred async boundary style with
the team.**
