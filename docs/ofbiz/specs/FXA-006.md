# FXA-006 — Straight-line depreciation schedule generation

## 1. Summary & Goal

FXA-006 adds `generate_schedule(asset_id: str) -> DepreciationScheduleOut` to `app/services/fixed_assets.py`. The function computes a complete straight-line depreciation schedule for a registered asset, writes one `PERIOD#` row per month into `T.fixed_asset_schedule`, and returns the full schedule. Re-generating over an existing schedule is idempotent: rows whose `schedule_status` is already `"posted"` are never touched; rows still in `"scheduled"` state are recomputed in place (overwritten). The sum of all period `amount_cents` values equals the depreciable base (`acquisition_cost_cents - salvage_value_cents`) exactly — the last period absorbs any integer-cent rounding remainder.

No money moves during schedule generation. No ledger entry is written. No GL journal is posted. This function is a pure scheduling step; the depreciation poster (FXA-009) is the separate background task that will later query `GSI_DUE` and post each due period to the GL. FXA-006 produces the data that poster will consume.

The function is gated by `S.fixed_assets_enabled` and lives entirely within the already-established file boundary of `app/services/fixed_assets.py` (FXA-005's home). No router change is required here — the router endpoint `GET /ui/fixed-assets/{asset_id}/schedule` belongs to FXA-007. FXA-006 is the service layer only.

## 3. Data Model

FXA-006 writes exclusively to the `fixed_asset_schedule` table (established by FXA-003). No new table, GSI, or schema change is introduced.

### 3.1 `fixed_asset_schedule` row written by `generate_schedule`

| Attribute | DDB type | Value | Notes |
|---|---|---|---|
| `pk` | S | `"ASSET#{asset_id}"` | Partition key |
| `sk` | S | `"PERIOD#{period:07d}"` | Sort key; e.g. `"PERIOD#0000001"` for month 1 |
| `asset_id` | S | `asset_id` | Denormalized for cross-table access |
| `period` | N | 1-based integer | Period index |
| `period_start_ts` | N | Unix timestamp | Start of this calendar month |
| `period_end_ts` | N | Unix timestamp | End of this calendar month (exclusive start of next); GSI_DUE sort key |
| `amount_cents` | N | Integer cents | `base_amount` for periods 1..N-1; `base_amount + remainder` for period N |
| `schedule_status` | S | `"scheduled"` | Set on write; never overwritten if already `"posted"` |

`journal_entry_id` and `posted_at` are absent from rows written by `generate_schedule` — they are added only by the future FXA-009 poster.

### 3.2 Period timestamp computation

Period timestamps are computed from `acquired_at` using `calendar.monthrange` to get the exact number of days in each calendar month, advancing month by month. The computation must not use a fixed 30-day approximation (which would drift by days over a multi-year asset life and cause `period_end_ts` values to skew away from real accounting period end dates).

**Algorithm** (pseudo-code):

```python
import calendar
from datetime import datetime, timezone, timedelta

def _period_timestamps(acquired_at: int, useful_life_months: int) -> list[tuple[int, int]]:
    """Return list of (period_start_ts, period_end_ts) for each month."""
    result = []
    # Period 1 starts on the first day of the month in which acquired_at falls
    dt = datetime.fromtimestamp(acquired_at, tz=timezone.utc).replace(
        day=1, hour=0, minute=0, second=0, microsecond=0
    )
    for _ in range(useful_life_months):
        year, month = dt.year, dt.month
        days_in_month = calendar.monthrange(year, month)[1]
        period_start = int(dt.timestamp())
        dt_end = dt.replace(day=days_in_month, hour=23, minute=59, second=59)
        period_end = int(dt_end.timestamp())
        result.append((period_start, period_end))
        # Advance to first day of next month
        if month == 12:
            dt = dt.replace(year=year + 1, month=1, day=1)
        else:
            dt = dt.replace(month=month + 1, day=1)
    return result
```

This ensures `period_end_ts` for each row reflects the actual last second of the calendar month, which is what the GSI_DUE poster needs to evaluate `period_end_ts <= now_ts()` correctly.

### 3.3 GSI_DUE interaction (read-only in FXA-006)

FXA-006 does not query `GSI_DUE` — it only writes `schedule_status="scheduled"` rows that will later appear in that index. The poster (FXA-009) is the reader. FXA-006 must write `period_end_ts` as a DynamoDB Number (Python `int`), not a `Decimal` or `str`, to be compatible with the GSI sort key type declared as `attr_types={"period_end_ts": "N"}` in `scripts/local-ddb-init.py`.

### 4.1 Primary function: `generate_schedule`

```python
def generate_schedule(asset_id: str) -> "DepreciationScheduleOut":
    """Generate or regenerate the straight-line depreciation schedule for an asset.

    - Reads the asset record via get_asset(asset_id) (raises 404 if not found).
```

### 4.3 Internal helper: `_compute_schedule_amounts`

```python
def _compute_schedule_amounts(
    acquisition_cost_cents: int,
    salvage_value_cents: int,
    useful_life_months: int,
) -> list[int]:
    """Return a list of useful_life_months integer-cent amounts summing exactly to
    (acquisition_cost_cents - salvage_value_cents). The last element absorbs
    any remainder from integer division."""
    depreciable_base = acquisition_cost_cents - salvage_value_cents
    if depreciable_base <= 0:
        return [0] * useful_life_months
    base_amount, remainder = divmod(depreciable_base, useful_life_months)
    amounts = [base_amount] * useful_life_months
    amounts[-1] += remainder  # last period absorbs the remainder
    return amounts
```

This is a pure function with no DDB access, making it trivially unit-testable.

### 4.4 `generate_schedule` internal flow (step by step)

1. Call `_require_enabled()` — raises 503 if `S.fixed_assets_enabled` is `False`.
2. Call `get_asset(asset_id)` — raises 404 if the asset does not exist.
3. Guard disposed assets: if `asset["status"] == "disposed"`, raise 409.
4. Fetch all existing period rows via a base-table Query on `pk="ASSET#{asset_id}"` with `sk begins_with "PERIOD#"`. Build a dict `existing: dict[int, dict]` keyed by period number (int). Track which periods already have `schedule_status="posted"`.
5. Compute the full `amounts` list via `_compute_schedule_amounts(...)`.
6. Compute `timestamps` via `_period_timestamps(asset["acquired_at"], asset["useful_life_months"])`.
7. For each period index `i` in `range(useful_life_months)`:
   - `period = i + 1`
   - If `existing.get(period, {}).get("schedule_status") == "posted"`: skip — do not write.
   - Otherwise: write (put_item) the row unconditionally.
8. Re-fetch the complete schedule via `get_schedule(asset_id)` to return a consistent view.
9. Emit `audit_event("fixed_asset.schedule_generated", owner_sub, asset_id=asset_id, periods=useful_life_months)` (best-effort, in `try/except`).
10. Return the `DepreciationScheduleOut`.

### 4.5 DDB write per period row

```python
T.fixed_asset_schedule.put_item(Item={
    "pk": f"ASSET#{asset_id}",
    "sk": f"PERIOD#{period:07d}",
    "asset_id": asset_id,
    "period": period,               # int — DDB Number
    "period_start_ts": period_start_ts,  # int — DDB Number
    "period_end_ts": period_end_ts,      # int — DDB Number (GSI_DUE sort key)
    "amount_cents": amount_cents,        # int — DDB Number
    "schedule_status": "scheduled",      # str
})
```

All numeric attributes must be Python `int` (not `Decimal`, not `float`) to avoid DynamoDB storing them as strings. The `period_end_ts` int is the GSI_DUE sort key; a string value here would cause a `ValidationException` at query time from the poster (same gotcha documented in CLAUDE.md).

## 5. Detailed Behavior & Edge Cases

### 5.1 Rounding: sum invariant

For any asset, `sum(amounts) == acquisition_cost_cents - salvage_value_cents` exactly. The `divmod` approach guarantees this: `base_amount * (useful_life_months - 1) + (base_amount + remainder) = base_amount * useful_life_months + remainder = depreciable_base`. This holds for all valid inputs including:

- **Even division** (`depreciable_base % useful_life_months == 0`): remainder is 0, all periods equal.
- **Uneven division** (`depreciable_base % useful_life_months != 0`): periods 1..N-1 get `base_amount`; period N gets `base_amount + remainder`. The remainder is always in `[1, useful_life_months - 1]` cents.
- **Single period** (`useful_life_months == 1`): the single row gets the full `depreciable_base`.

### 5.2 Regeneration over partially-posted schedule

When `generate_schedule` is called on an asset that already has some posted periods:

- Period rows with `schedule_status="posted"` are **never touched**. Their `amount_cents`, `journal_entry_id`, `posted_at`, `period_start_ts`, and `period_end_ts` are unchanged.
- Period rows with `schedule_status="scheduled"` are **overwritten** with freshly computed values. This matters if an admin corrects `acquisition_cost_cents` or `salvage_value_cents` (requires an asset-update path outside this ticket scope) and then triggers regeneration.
- The rounding-remainder invariant applies only to the unposted portion: the total of all `amount_cents` across all periods (posted + scheduled) after regeneration continues to equal the original `depreciable_base`. Implementation note: since posted periods are never rewritten, the `_compute_schedule_amounts` function is still called for the full `useful_life_months` list; the skip logic in step 7 of section 4.4 simply discards the computed values for already-posted indices without writing them. The scheduler does not attempt to re-balance the remaining periods to account for any posted rounding discrepancy — the amounts are recomputed from scratch for the full life and skipped for posted rows, so a regeneration that hits posted rows will produce a consistent schedule if the underlying asset fields haven't changed, and may need a manual adjustment if they have.

### 5.3 Disposed asset guard

An asset with `status="disposed"` must never have new schedule rows generated — there is nothing to depreciate. The 409 is intentional (not 404) because the asset exists but the operation is not legal in its current state. This mirrors the `returns_rma.py` pattern of returning 409 for illegal lifecycle transitions (`app/services/returns_rma.py:357–364`, `_require_transition`).

### 5.4 `period_start_ts` for period 1 vs. `acquired_at`

The `_period_timestamps` helper anchors period 1 to the **first day of the calendar month** in which `acquired_at` falls, not to the exact `acquired_at` timestamp. This is the standard accounting convention: a piece of equipment acquired on the 15th of March is depreciated from 1 March in its first period. Callers who want asset-acquisition-date-exact period starts can pass `acquired_at` for the first day of a month — the result is identical. The FXA-007 `GET /schedule` endpoint will surface both `period_start_ts` and `period_end_ts` so the UI can display the calendar range.

### 5.5 Zero-depreciable-base edge case

If `acquisition_cost_cents == salvage_value_cents` (depreciable base = 0), `_compute_schedule_amounts` returns `[0] * useful_life_months`. All rows are written with `amount_cents=0`. The asset is technically fully depreciated on arrival; FXA-005 does not prevent registration of such assets (they may represent donated assets received at salvage value). The schedule is valid but meaningless for GL posting purposes.

### 5.6 Missing `acquired_at` field

`acquired_at` is a required field on `FixedAssetIn` (`docs/ofbiz/specs/FXA-004.md:142`). If a DDB item is somehow missing it (legacy data issue), `_period_timestamps` will receive `0` (via `_to_int` coercion), anchoring all periods to 1 January 1970. The schedule will write and be correct relative to that anchor but will be semantically wrong. Service code should log a warning in this case. The guard is defensive; FXA-005's `create_asset` enforces `acquired_at` at create time.

### 5.7 Large `useful_life_months`

`FixedAssetIn.useful_life_months` is bounded by `Field(ge=1, le=1200)` (FXA-004), so the maximum schedule has 1 200 rows (100 years). Each write is a separate `put_item` call. At 1 200 puts, with the local DDB latency of ~1 ms per write, generation completes in ~1.2 s. For production use the ceiling remains 1 200, which is still within acceptable synchronous request time for an admin-only action. No batch write is needed; `BatchWriteItem` would add complexity for marginal gain.

### 5.8 Idempotency: calling `generate_schedule` twice on an unposted asset

Two successive calls with no intervening posts produce identical schedules. The `put_item` in step 7 unconditionally overwrites existing `"scheduled"` rows; the resulting item values are deterministic (derived from the same immutable asset fields). No duplicate row can exist because the PK+SK combination is fixed per period.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007 parity**: `generate_schedule` contains no `if S.dev_mode` branch. It uses `T.fixed_asset_schedule` directly, which resolves to the local DDB-local instance in dev (via moto or DDB-local on port 8001, depending on test context) and to the real DynamoDB table in prod. The `put_item` calls are identical in both environments. No mock/dev shortcut is permitted.

**Idempotency**: A repeated call to `generate_schedule(asset_id)` with the same asset state produces the same schedule rows. The `put_item` calls for `"scheduled"` rows are unconditional overwrites — no conditional expression is needed because duplicate generation is not an error. The amounts and timestamps are deterministic functions of the immutable asset fields.

**No transactions**: Each period row is written with a separate `put_item`. There is no DynamoDB transaction wrapping the batch because: (a) a partial write is recoverable — the caller can simply retry `generate_schedule`, which will overwrite any partially-written rows; (b) DynamoDB transactions are limited to 100 items and would be inadequate for a 1 200-period asset anyway; (c) the idempotency of individual `put_item` makes retry safe.

**Authorization**: `generate_schedule` is called only from the FXA-007 router, which gates every handler on `require_admin_or_root_csrf` (`app/auth/policy.py:100` <!-- VERIFIED -->; also used in `app/routers/returns_rma.py:61` <!-- VERIFIED -->). Non-admin users cannot trigger schedule generation. The asset ownership check (does the caller own this asset?) is enforced at the router level by FXA-007, not in the service function — consistent with the pattern in `app/services/returns_rma.py` where ownership is checked in service code via `order["user_id"] != user_sub` (`app/services/returns_rma.py:189` <!-- VERIFIED -->).

**Audit trail**: Every successful generation emits `audit_event("fixed_asset.schedule_generated", ...)` to `T.alerts`. The audit write is best-effort (in `try/except`), matching the pattern in `app/services/inventory.py` and `app/services/returns_rma.py`. A failed audit write never blocks the schedule generation.

**No PII in schedule rows**: The `fixed_asset_schedule` table does not store user PII. The `owner_sub` lives only on the `fixed_assets` table. The schedule partition key `"ASSET#{asset_id}"` is an opaque UUID; it does not expose the owner.

2. **`test_uneven_remainder_on_last_period`** — Asset with `acquisition_cost_cents=10_000`, `salvage_value_cents=0`, `useful_life_months=3`. Depreciable base = 10 000. `divmod(10000, 3) = (3333, 1)`. Assert: periods 1 and 2 have `amount_cents=3333`; period 3 has `amount_cents=3334`; `sum == 10_000`.

3. **`test_sum_invariant_many_months`** — Asset with `acquisition_cost_cents=100_001`, `salvage_value_cents=1`, `useful_life_months=120`. Depreciable base = 100 000. Assert `sum(amounts) == 100_000` exactly.

4. **`test_salvage_floor_affects_base`** — Asset with `acquisition_cost_cents=50_000`, `salvage_value_cents=5_000`, `useful_life_months=10`. Depreciable base = 45 000; base_amount = 4 500; remainder = 0. Assert all 10 rows have `amount_cents=4_500`.

5. **`test_regenerate_leaves_posted_untouched`** — Seed one period row with `schedule_status="posted"` and `amount_cents=999` (arbitrary sentinel). Call `generate_schedule`. Assert: the posted row is unchanged (`amount_cents` still `999`, `schedule_status` still `"posted"`); all other rows have freshly computed `amount_cents` values.

6. **`test_regenerate_idempotent`** — Call `generate_schedule` twice on an unposted asset. Assert: second call returns identical schedule (same `amount_cents` list, same `period_end_ts` values).

7. **`test_period_timestamps_calendar_boundaries`** — Asset with `acquired_at` set to a mid-month Unix timestamp for January 2024. Assert: `period_start_ts` for period 1 equals the Unix timestamp of 2024-01-01 00:00:00 UTC; `period_end_ts` for period 1 equals the Unix timestamp of 2024-01-31 23:59:59 UTC; `period_start_ts` for period 2 equals 2024-02-01 00:00:00 UTC; `period_end_ts` for period 2 equals 2024-02-29 23:59:59 UTC (2024 is a leap year — 29 days in February).

8. **`test_flag_off_raises_503`** — Flip `S.fixed_assets_enabled = False`. Call `generate_schedule`. Assert `HTTPException` with `status_code=503`.

9. **`test_asset_not_found_raises_404`** — Call `generate_schedule("nonexistent")` with no matching row in `fixed_assets`. Assert `HTTPException` with `status_code=404`.

10. **`test_disposed_asset_raises_409`** — Seed an asset with `status="disposed"`. Call `generate_schedule`. Assert `HTTPException` with `status_code=409`.

11. **`test_zero_depreciable_base`** — Asset with `acquisition_cost_cents=5_000`, `salvage_value_cents=5_000`, `useful_life_months=5`. Assert: 5 rows written, all `amount_cents=0`.

12. **`test_period_end_ts_stored_as_int`** — After generation, read a raw DDB item from `schedule_tbl`. Assert that `item["period_end_ts"]` is a Python `int` (or `Decimal` — boto3 returns `Decimal`, but must not be `str`). This catches a regression where a `datetime` or `float` is accidentally written as a string.

### 9.2 Unit tests for pure helpers

Both `_compute_schedule_amounts` and `_period_timestamps` are pure functions with no DDB access. They can be tested without moto:

- `TestComputeScheduleAmounts` (plain `unittest.TestCase`) — covers even, uneven, single period, and zero-base cases.
- `TestPeriodTimestamps` — covers month-boundary advance, February leap-year (Feb 2024 = 29 days), February non-leap (Feb 2023 = 28 days), December-to-January year rollover.

### 9.3 E2E spec: `frontend/e2e/fixed-assets.spec.ts`

FXA-006 is a service-layer function; end-to-end coverage requires the FXA-007 router endpoint `POST /ui/fixed-assets/{asset_id}/schedule` (which calls `generate_schedule`) and `GET /ui/fixed-assets/{asset_id}/schedule` (which calls `get_schedule`). The E2E spec is authored as part of FXA-007 but covers FXA-006 behavior:

- Create an asset via `POST /ui/fixed-assets` (admin session).
- Call `POST /ui/fixed-assets/{id}/schedule` — assert HTTP 200 and `total_periods == useful_life_months`.
- Call `GET /ui/fixed-assets/{id}/schedule` — assert same number of periods; assert `sum(p.amount_cents for p in periods) == acquisition_cost_cents - salvage_value_cents`.
- Call `POST /ui/fixed-assets/{id}/schedule` again — assert idempotent (same amounts).
- Assert that calling either endpoint with `FIXED_ASSETS_ENABLED=false` returns 503.

## 10. Open Questions / Assumptions

1. **Assumption: FXA-005 is merged before FXA-006.** `generate_schedule` calls `get_asset(asset_id)` from the same file. If FXA-005 has not shipped, this call does not exist. This is listed as an explicit dependency (`FIXED_ASSETS_TICKETS.md:129`).

2. **Assumption: `acquired_at` is anchored to the first-of-month for period-1 start.** Standard accounting convention. If the business wants day-of-acquisition-exact period starts (periods end on the same date each month), the `_period_timestamps` helper must change. Decision needs finance sign-off before implementation.

3. **Assumption: `period_end_ts` is the last second of the calendar month (23:59:59 UTC).** The GSI_DUE poster will query `period_end_ts <= now_ts()` to find due periods. Using 23:59:59 of the month-end day means a period is eligible for posting starting at midnight UTC on the first day of the following month. If the team wants 00:00:00 of the first day of the following month as `period_end_ts` instead, both the helper and the poster need to be consistent. This spec uses 23:59:59 of the last calendar day.

4. **Assumption: No asset-field mutability after schedule generation.** `acquisition_cost_cents`, `salvage_value_cents`, and `useful_life_months` are treated as immutable after the first `create_asset`. If an admin must correct them, they must re-generate the schedule. `FixedAssetPatchIn` (FXA-004) deliberately omits these fields. If mutation is later required, a separate `PATCH /fixed-assets/{id}/amend` endpoint and schedule re-generation flow is needed.

5. **Assumption: `generate_schedule` is synchronous.** For 1 200 periods at ~1 ms per DDB write in production (latency to us-east-1), total write time is ~1.2 s. This is acceptable for an admin-only operation. If writes must be faster, a `BatchWriteItem` path (writing 25 items per request) reduces DDB round trips by 48×. This optimization is deferred.

6. **Assumption: No DynamoDB transaction around the full generation.** A partially written schedule can be repaired by calling `generate_schedule` again. The spec documents this in section 7. If atomicity is required (all periods written or none), a DynamoDB transaction is needed; but it is limited to 100 items, insufficient for assets with more than 100 months of life.

7. **Open question: should `generate_schedule` be exposed as `POST /schedule` (triggering a write) or only implicitly called on `create_asset`?** FXA-007's ticket description (`FIXED_ASSETS_TICKETS.md:140`) says `GET /{asset_id}/schedule` returns the schedule. It does not explicitly define a `POST /schedule` endpoint. The caller of `generate_schedule` is assumed to be either (a) the `create_asset` service function (auto-generating on registration) or (b) an explicit admin-only `POST /ui/fixed-assets/{id}/schedule` endpoint in FXA-007. This needs to be decided in FXA-007 before the router ships.

8. **Assumption: Audit events use `owner_sub` retrieved from the asset row.** The service function does not receive a `user_sub` caller argument — it reads `owner_sub` from the DDB asset item. If the audit trail needs to record the *admin* who triggered the generation (not the asset owner), the FXA-007 router must pass `session["user_sub"]` as an argument to `generate_schedule` and forward it to `audit_event`. This is left as a FXA-007 decision.
