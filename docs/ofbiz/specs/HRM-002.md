## 1. Summary & Goal

HRM-002 is the DynamoDB scaffolding ticket for the HR module. Its two deliverables are:

1. A `TableDef` entry in `scripts/local-ddb-init.py` that creates (or idempotently ensures) the `hr` single-table with its three GSIs (`GSI1`, `GSI2`, `GSI_CREATED`) and declares numeric sort keys so DynamoDB Local stores them as `N` rather than `S`.
2. The `hr: Any` field declaration in the `Tables` dataclass and the corresponding `hr=_safe_table(S.hr_table_name)` initialiser in the `T` singleton in `app/core/tables.py`.

HRM-002 introduces no service functions, no endpoints, and no Pydantic models — those belong to HRM-003 through HRM-010. It depends entirely on HRM-001 having added `S.hr_table_name` (default `"hr"`) and the three boolean flags to `app/core/settings.py`.

The goal is that after HRM-002 lands, `just restart` recreates the `hr` table cleanly, `T.hr` resolves to a live boto3 table handle at import time, and all existing tables are unchanged. No runtime code other than `app/core/tables.py` is modified.

### 2.2 `TableDef` and `_table_defs()` mechanics

`scripts/local-ddb-init.py:29–35` defines the `@dataclass(frozen=True) class TableDef` with fields:
- `name: str` — resolved DynamoDB table name
- `partition_key: str` — PK attribute name
- `sort_key: Optional[str]` — SK attribute name (omit for partition-only tables)
- `gsi: List[Dict[str, str]]` — GSI specs with `index_name`, `partition_key`, optional `sort_key`
- `attr_types: Dict[str, str]` — overrides the default `"S"` type for any attribute

`_attribute_definitions()` at `scripts/local-ddb-init.py:2496` builds the DynamoDB `AttributeDefinitions` list by defaulting every key (base + GSI) to `"S"`, then applying `attr_types` overrides (`attrs.update(table.attr_types)`, line 2505). This is the mechanism that prevents `ValidationException` for numeric GSI sort keys: without an `attr_types={"created_at": "N"}` override, DynamoDB Local stores `created_at` as `S`, and any query with an integer comparison raises `ValidationException`.

`_resolve_table_name(name, fallback)` at line 38 returns `name or fallback`. For the HR table this will evaluate to `S.hr_table_name or "hr"`, which is always `"hr"` (or whatever the operator has set `DDB_HR_TABLE` to).

The `_ensure_table()` function at line 2534 is idempotent: if the table already exists it skips `create_table` and, if `gsi` is non-empty, calls `update_table` only for GSIs that are genuinely missing.

## 3. Data Model

### 3.1 HR single-table design

The `hr` table uses a generic `PK` / `SK` single-table pattern (same as `projects` at line 270–276, `kyc_cases` at line 139–158, `shopping_catalog` at line 118–124). All HR entity types coexist in this one table, keyed by entity-type prefixes.

#### Base table keys

| Attribute | DynamoDB type | Role |
|---|---|---|
| `PK` | `S` (HASH) | Entity identifier e.g. `POSITION#{position_id}`, `EMPLOYMENT#{employment_id}`, `PAYROLL_RUN#{run_id}` |
| `SK` | `S` (RANGE) | Record discriminator e.g. `META`, `LINE#{line_id}` |

#### GSI1 — entity-type / status lookup

| Attribute | DynamoDB type | Role |
|---|---|---|
| `GSI1PK` | `S` (HASH) | Entity-type + status composite key e.g. `POSITION#OPEN`, `EMPLOYMENT#ACTIVE`, `PAYROLL_RUN#DRAFT` |
| `GSI1SK` | `S` (RANGE) | Entity id e.g. `POSITION#{position_id}` — used for keyset pagination |

Downstream services (HRM-005, HRM-006, HRM-008) will query `GSI1` with `KeyConditionExpression=Key("GSI1PK").eq("POSITION#OPEN")` to list all open positions without scanning the base table. The `GSI1SK` sort key allows cursor-based pagination via `encode_cursor` / `decode_cursor` from `app/core/cursor.py`.

`GSI1PK` and `GSI1SK` are both `S` — no `attr_types` override needed for these keys.

#### GSI2 — party reverse-lookup

| Attribute | DynamoDB type | Role |
|---|---|---|
| `GSI2PK` | `S` (HASH) | Party identifier e.g. `PARTY#{party_id}` |
| `GSI2SK` | `S` (RANGE) | Entity reference e.g. `EMPLOYMENT#{employment_id}` |

Downstream services (HRM-004, HRM-006) will query `GSI2` with `KeyConditionExpression=Key("GSI2PK").eq(f"PARTY#{party_id}")` to resolve all HR rows for an employee party. This is the standard single-table reverse-lookup pattern used by `projects` (`GSI2PK`/`GSI2SK` at line 275) and `shopping_catalog` (lines 121–123).

`GSI2PK` and `GSI2SK` are both `S` — no `attr_types` override needed.

#### GSI_CREATED — newest-first listing

| Attribute | DynamoDB type | Role |
|---|---|---|
| `entity_type` | `S` (HASH) | Coarse entity namespace e.g. `POSITION`, `EMPLOYMENT`, `PAYROLL_RUN` |
| `created_at` | `N` (RANGE) | Unix epoch seconds from `now_ts()` |

Downstream services list entities newest-first via `KeyConditionExpression=Key("entity_type").eq("POSITION")` with `ScanIndexForward=False`. The `entity_type` HASH key is `S`; the `created_at` RANGE key must be declared `N` — it is the only attribute requiring an `attr_types` override.

**Critical:** `attr_types={"created_at": "N"}` must appear in the `TableDef`. Omitting it causes `created_at` to be stored as `S`, breaking `GSI_CREATED` queries with integer values.

### 3.2 `TableDef` representation

```python
# scripts/local-ddb-init.py — insert after line 691 (Contacts def)
TableDef(
    _resolve_table_name(S.hr_table_name, "hr"),
    "PK",
    "SK",
    gsi=[
        # GSI1: entity-type/status lookup
        # e.g. GSI1PK="POSITION#OPEN" → list all open positions
        {"index_name": "GSI1", "partition_key": "GSI1PK", "sort_key": "GSI1SK"},
        # GSI2: party reverse-lookup
        # e.g. GSI2PK="PARTY#{party_id}" → list all HR rows for an employee
        {"index_name": "GSI2", "partition_key": "GSI2PK", "sort_key": "GSI2SK"},
        # GSI_CREATED: newest-first listing by entity type
        # e.g. entity_type="POSITION", ScanIndexForward=False → newest positions first
        {"index_name": "GSI_CREATED", "partition_key": "entity_type", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
),
```

### 3.3 Item shapes (reference for downstream tickets)

This table does not mandate item shapes — those are HRM-003's scope. The following shapes are documented here purely as context for understanding the key design choices above.

| Entity | PK | SK | GSI1PK | GSI1SK | GSI2PK | GSI2SK | entity_type | created_at |
|---|---|---|---|---|---|---|---|---|
| Position META | `POSITION#{id}` | `META` | `POSITION#{status}` | `POSITION#{id}` | _(absent)_ | _(absent)_ | `POSITION` | `int` |
| Employment META | `EMPLOYMENT#{id}` | `META` | `EMPLOYMENT#{status}` | `EMPLOYMENT#{id}` | `PARTY#{party_id}` | `EMPLOYMENT#{id}` | `EMPLOYMENT` | `int` |
| Payroll Run META | `PAYROLL_RUN#{id}` | `META` | `PAYROLL_RUN#{status}` | `PAYROLL_RUN#{id}` | _(absent)_ | _(absent)_ | `PAYROLL_RUN` | `int` |
| Payroll Line | `PAYROLL_RUN#{id}` | `LINE#{employment_id}` | _(absent)_ | _(absent)_ | _(absent)_ | _(absent)_ | _(absent)_ | _(absent)_ |

Payroll lines are nested under their run's PK and do not need GSI projection — they are always fetched via the base table `PK`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Table already exists (idempotent `just restart`)

`_ensure_table()` at `scripts/local-ddb-init.py:2534` checks `table.name in existing` before calling `create_table`. If the `hr` table already exists from a previous run and all three GSIs are present, the function returns immediately. If the table exists but a GSI is missing (e.g., from a partial previous run), `_ensure_table` calls `update_table` for the missing GSI.

**RISK — `attr_types` not consulted during GSI backfill.** The `update_table` path (lines 2543–2574) hardcodes `"AttributeType": "S"` for any new GSI attribute (`scripts/local-ddb-init.py:2546, 2548`). It does NOT call `_attribute_definitions` and therefore does NOT apply `table.attr_types` overrides. If the `hr` table was created before `GSI_CREATED` existed and `_ensure_table` tries to add it later, `created_at` would be registered as `"S"` in `AttributeDefinitions` — breaking integer comparisons. **Mitigation:** the `hr` table is brand-new (not an upgrade to an existing table), so `GSI_CREATED` is always created alongside it on the initial `create_table` call, where `_attribute_definitions` IS used. This risk only materialises if a developer manually creates the table without `GSI_CREATED` then re-runs the init script. In that case `just restart` (which wipes DynamoDB Local entirely) is the safe recovery path.

### 5.2 `T.hr` handle with no table present

If a developer sets `HR_ENABLED=1` before running `just restart` (and therefore before the `hr` table exists), `T.hr` still resolves to a valid `_FloatSafeTable` handle — the boto3 `Table` object is constructed without verifying the table's existence. Any actual DynamoDB call will raise `ResourceNotFoundException`. This is the identical behaviour of every other table handle in `T`, and is acceptable: HRM-001 documents this in its "Migration" section.

### 5.3 `HR_ENABLED=0` (default): no code path touches `T.hr`

With `S.hr_enabled = False` (the default), no downstream service or router will call `T.hr` because every HR endpoint guards with `if not S.hr_enabled: raise HTTPException(404)`. `T.hr` is initialised at import time unconditionally, but since it is a lazy boto3 handle it imposes no runtime cost or network call until a DynamoDB operation is performed.

### 5.4 `attr_types={"created_at": "N"}` — precision

`_attribute_definitions()` (line 2496–2506) first populates defaults from the partition and sort keys of the base table and all GSIs (all `"S"`), then calls `attrs.update(table.attr_types)`. The `GSI_CREATED` index's sort key `created_at` defaults to `"S"` in the first pass; the `attr_types` override corrects it to `"N"`. DynamoDB requires that the `AttributeDefinitions` list match the types actually stored in items; since `now_ts()` returns an `int`, using `N` is correct and mandatory.

### 5.5 `GSI1SK` and `GSI2SK` as string keys

`GSI1SK` and `GSI2SK` hold string values like `POSITION#{position_id}` and `EMPLOYMENT#{employment_id}`. No numeric override is needed. The `_attribute_definitions` function's default `"S"` for all unoverridden keys is correct for these attributes.

### 5.6 `entity_type` as GSI_CREATED partition key — sparse index

Items that do not carry `entity_type` (e.g., `PAYROLL_RUN` payroll lines stored under `SK=LINE#{id}`) are sparse with respect to `GSI_CREATED` — they will not be projected into the index. This is intentional: `GSI_CREATED` lists only the top-level META items for each entity type. The `Projection=ALL` setting (imposed by `_global_secondary_indexes()` at line 2524–2529) means all attributes of qualifying items are projected, allowing downstream code to construct full `PositionOut` objects from index results without falling back to base-table gets.

### 5.7 Downstream `start_date` / `end_date` epoch keys

The ticket description mentions "any numeric employment-period `start_date`/`end_date` epoch keys used as GSI sort keys". HRM-002's current `TableDef` does NOT include GSIs keyed on `start_date` or `end_date` — the ticket description is forward-looking, noting that if HRM-005/HRM-006 add such GSIs, their `attr_types` declarations must be included in the same `TableDef` update. HRM-002 itself declares only `{"created_at": "N"}` because `GSI_CREATED` is the only numeric sort key added here.

If a future HRM ticket adds a GSI with a numeric sort key (e.g., `{"index_name": "GSI_PERIOD", "sort_key": "start_date"}`), it must include `"start_date": "N"` in `attr_types`. The `_ensure_table` mechanism will add the GSI via `update_table` without recreating the table, but `AttributeDefinitions` must include the new numeric attribute.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007

There are no `dev_mode` branches in this ticket. The `TableDef` is evaluated identically in dev (DynamoDB Local at `http://localhost:8001`) and prod (real DynamoDB). The `_safe_table` factory calls `ddb.Table(name)` where `ddb` is the boto3 resource configured by `app/core/tables.py` (which reads the endpoint URL from `DDB_ENDPOINT_URL` in dev). No mock paths, no conditional imports, no `if S.dev_mode:` switches. This satisfies SECOPS-007.

### Idempotency

`_ensure_table()` is idempotent by design (see §5.1). Re-running `scripts/local-ddb-init.py` or `just restart` any number of times produces the same `hr` table state. The `PK`/`SK` choice and GSI schema never change once created — any schema change requires a new GSI (added via `update_table`, which `_ensure_table` handles) rather than table recreation.

`T.hr` itself is also idempotent: it is a module-level singleton constructed once at import time and shared by all importers.

### Security

HRM-002 introduces no secrets, tokens, or sensitive configuration. The `hr_table_name` setting controls a DynamoDB table name; an operator who can set env vars already has full infrastructure access. The `hr` table's access control is enforced at the boto3 / IAM layer in prod (the same IAM role that governs all other DynamoDB tables).

The `PK`/`SK` single-table design does not expose cross-tenant or cross-user data by itself — access control is enforced at the service layer in HRM-004+ (each service function constrains queries to `user_sub`-scoped keys or admin-gated endpoints).

## 8. Backward Compatibility & Migration

### Zero-change guarantee

With HRM-002 landed and `HR_ENABLED=0` (the default):
- `scripts/local-ddb-init.py` creates the `hr` table on the next `just restart`, but this has no effect on any existing table or any running service.
- `app/core/tables.py` gains two lines (`hr: Any` field and `hr=_safe_table(...)` initialiser) but no existing field changes.
- No router, service, model, or test file outside `tests/test_hrm_002_table_handle.py` is modified.
- `T` is `@dataclass(frozen=True)` — the new `hr` field is additive; Python dataclass inheritance guarantees existing positional usage (there is none — `Tables` is always constructed with keyword arguments in the `T = Tables(...)` call) is unaffected.

### Migration

There is no DynamoDB migration in this ticket. The `hr` table is newly created; no existing data is affected. In a prod deployment the sequence is:

1. Deploy the code containing HRM-001 + HRM-002 (settings keys + table definition + handle wiring).
2. Run `scripts/local-ddb-init.py` (or the equivalent prod table-initialisation step) to create the `hr` table.
3. Turn on `HR_ENABLED=1` (and restart the process) when the downstream service/router code (HRM-003+) is deployed.

Step 2 before step 3 ensures `T.hr` always finds the table ready when first called.

### `.env.local` impact on existing developers

Existing `.env.local` files do not set `DDB_HR_TABLE`. Absence results in the default `"hr"`. Developers do not need to update their `.env.local`; running `just restart` after HRM-002 lands creates the table automatically.

## 10. Open Questions / Assumptions

1. **Assumption: HRM-001 will add `S.hr_table_name` with default `"hr"` before HRM-002 is implemented.** Confirmed by the HRM-001 spec at `docs/ofbiz/specs/HRM-001.md:§6`. HRM-002 depends on HRM-001 and must not be merged first.

2. **Assumption: The `party` `TableDef` (PTY-002) is not yet present in `scripts/local-ddb-init.py`.** Verified by `grep` returning no match for `"party"` or `DDB_PARTY` as a table name default in the file. The ticket states "next to Contacts/party defs" meaning the neighbourhood around line 691 (Contacts), not that the party def already exists there.

3. **Assumption: `GSI1SK` and `GSI2SK` are always string values (entity-id prefixed strings).** If a downstream HRM ticket decides to use a numeric timestamp as `GSI1SK` or `GSI2SK` for date-range queries, `attr_types` must be updated. This is deferred to the ticket that introduces such a pattern.

4. **Assumption: `start_date` and `end_date` epoch values are NOT GSI sort keys in HRM-002's schema.** The ticket description says "any numeric employment-period start_date/end_date epoch keys used as GSI sort keys" should be declared `N`. HRM-002 does not add a date-period GSI; if HRM-006 (Employment service) adds one, it will update this `TableDef` to include the new GSI and its `attr_types` entry. The current `attr_types={"created_at": "N"}` is the only numeric key in HRM-002's scope.

5. **Assumption: `GSI_CREATED` `entity_type` partition key is a plain string (e.g. `"POSITION"`, `"EMPLOYMENT"`, `"PAYROLL_RUN"`).** Not a compound key like `"ENTITY_TYPE#{foo}"`. This matches the `kyc_cases` pattern where `entity_type` is used as a plain HASH key for the sparse entity-type GSI (`scripts/local-ddb-init.py:150`).

6. **Assumption: Downstream HRM services will use `GSI1` for status-filtered list queries and `GSI_CREATED` for newest-first unfiltered list queries, not a single combined index.** The two indexes serve different access patterns: `GSI1` for "list all OPEN positions" and `GSI_CREATED` for "list all positions by creation time". A single combined index is not possible in DynamoDB single-table design for both patterns simultaneously.

7. **Open question: Should `GSI1SK` encode the entity id as a plain id (`{position_id}`) or as a prefixed string (`POSITION#{position_id}`)?** The spec above uses the prefixed form (e.g. `POSITION#{position_id}`) to allow the same value to serve as both the `GSI1SK` for pagination and as the base-table `PK` without an extra mapping step. This is an implementation detail for HRM-005; HRM-002 only declares the index and does not mandate the value format.

8. **Open question: Should `GSI_CREATED`'s `entity_type` HASH key be overridable via an `attr_types` entry?** Currently it defaults to `"S"` (correct — entity types are strings). No override needed. This is documented explicitly to prevent a future maintainer from adding `"entity_type": "S"` as a redundant override.
