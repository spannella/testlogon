**Type:** Feature | **Priority:** P0 | **Estimate:** 5 days

## 1. Summary & Goal

PUR-006 creates `app/services/purchase_orders.py`, the buy-side mirror of `app/services/commerce_order_service.py`. A purchase order (PO) records an organisation's intent to buy specific quantities of SKUs from a named supplier at agreed pricing. The service exposes three public functions:

- `create_purchase_order(...)` — deterministic-id create with header + per-line rows; `draft` initial status.
- `get_purchase_order(po_id)` — returns header + all ordered lines.
- `list_purchase_orders(...)` — paginated lists by supplier (via `GSI_SUPPLIER`) or by status (via `GSI_STATUS`).

No router is delivered by this ticket. HTTP endpoints are added by the PO router ticket (PUR-010 per cross-ref in PUR-002 spec at `docs/ofbiz/specs/PUR-002.md:436`). No state transitions beyond initial `draft` creation are handled here — that belongs to PUR-007.

The ticket is **additive and flag-gated**: with `PURCHASING_SCM_ENABLED=false` (the default) every function raises `HTTPException(404)` and all existing shop/cart/orders/billing/inventory code is byte-for-byte unchanged.

## 3. Data Model

The `purchase_orders` table is established by PUR-002. PUR-006 writes to it but does not modify its schema.

### 3.1 `purchase_orders` table (from PUR-002 spec)

**Table key:** PK=`po_id` (S), SK=`sk` (S)

#### Header row (SK = `"META"`)

| Attribute | Type | Description |
|---|---|---|
| `po_id` | S | `sha256(correlation_id)[:32]` — deterministic |
| `sk` | S | `"META"` |
| `supplier_id` | S | GSI_SUPPLIER partition key |
| `status` | S | GSI_STATUS partition key; always `"draft"` on creation |
| `currency` | S | ISO-4217 code; defaults from supplier-product or caller |
| `subtotal_cents` | N | `Σ line_total_cents` across all lines |
| `expected_delivery_date` | S | ISO date string (`YYYY-MM-DD`), optional |
| `created_by` | S | `user_sub` of the user who submitted the request |
| `created_at` | N | Unix timestamp integer (`now_ts()`); GSI_SUPPLIER and GSI_STATUS sort key |
| `updated_at` | N | Unix timestamp integer; same value as `created_at` on initial write |
| `correlation_id` | S | The caller-provided or generated correlation string; stored for debugging |
| `line_count` | N | Number of line rows written |

#### Line row (SK = `"LINE#{n}"`, 1-based)

| Attribute | Type | Description |
|---|---|---|
| `po_id` | S | Same as header PK |
| `sk` | S | `LINE#{n}` (e.g. `LINE#1`, `LINE#2`) |
| `line_no` | N | Integer 1-based position; mirrors `item_id` in commerce order |
| `sku` | S | The SKU to purchase |
| `quantity_ordered` | N | Units to purchase; `>= 1` |
| `quantity_received` | N | Received so far; always `0` on creation (PUR-008 increments this) |
| `unit_cost_cents` | N | Per-unit cost in cents |
| `line_total_cents` | N | `quantity_ordered × unit_cost_cents` |
| `currency` | S | Denormalized from header |
| `supplier_sku` | S | Vendor's part number from supplier_products, if available; else `""` |

**Note on line rows and GSIs:** Line rows carry no `supplier_id` or `status` attribute, so they are never projected into `GSI_SUPPLIER` or `GSI_STATUS`. The two-pass fetch in `get_purchase_order` first queries by `PK=po_id` to retrieve all items, then splits them by `SK` prefix.

### 3.2 GSIs on `purchase_orders` (established by PUR-002)

| GSI name | Partition key | Sort key | Type | Use |
|---|---|---|---|---|
| `GSI_SUPPLIER` | `supplier_id` (S) | `created_at` (N) | All projection | `list_purchase_orders(supplier_id=...)` |
| `GSI_STATUS` | `status` (S) | `created_at` (N) | All projection | `list_purchase_orders(status=...)` |

Both GSIs share `created_at` as their sort key; `attr_types={"created_at": "N"}` (a single entry covers both, per `scripts/local-ddb-init.py:2496–2506` behavior documented in PUR-002 spec).

### 3.3 No new tables in this ticket

PUR-006 introduces no new DynamoDB tables, settings keys, or `T.*` handles. All infrastructure is established by PUR-002.

### 4.2 Module-level helpers

Exact mirrors of `inventory.py:50–98` and `returns_rma.py:76–92`:

```python
def _flag_on() -> bool:
    return bool(getattr(S, "purchasing_scm_enabled", False))

def _require_enabled() -> None:
    if not _flag_on():
        raise HTTPException(status_code=404, detail="Purchasing/SCM is not enabled")

def _to_int(value: Any, default: int = 0) -> int:
    try:
        return default if value is None else int(value)
    except (TypeError, ValueError):
        return default

def _audit(event: str, actor: str, **fields: Any) -> None:
    try:
        from app.services.alerts import audit_event
        audit_event(event, actor or "system", None, **fields)
    except Exception:
        pass

def _line_sk(n: int) -> str:
    return f"LINE#{n}"

def _get_all_po_items(po_id: str) -> Tuple[Optional[Dict], List[Dict]]:
    """Query all items for a PO and split header from lines."""
    kwargs: Dict[str, Any] = {
        "KeyConditionExpression": Key("po_id").eq(po_id),
    }
    header: Optional[Dict[str, Any]] = None
    lines: List[Dict[str, Any]] = []
    while True:
        resp = T.purchase_orders.query(**kwargs)
        for item in resp.get("Items", []):
            if item.get("sk") == "META":
                header = item
            elif str(item.get("sk", "")).startswith("LINE#"):
                lines.append(item)
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
    lines.sort(key=lambda ln: _to_int(ln.get("line_no")))
    return header, lines
```

### 4.3 Public service functions

#### `create_purchase_order`

```python
def create_purchase_order(
    *,
    created_by: str,
    supplier_id: str,
    lines: List[Dict[str, Any]],
    currency: str = "USD",
    correlation_id: Optional[str] = None,
    expected_delivery_date: Optional[str] = None,
) -> Dict[str, Any]:
    """Create a new purchase order in draft status.

    Args:
        created_by: user_sub of the requester.
        supplier_id: Must reference an existing supplier (PUR-003).
        lines: List of dicts with keys:
            - sku (str, required)
            - quantity_ordered (int, required, >= 1)
            - unit_cost_cents (int, optional — defaults from supplier_products)
            - currency (str, optional — defaults from supplier_products or header)
        currency: Header-level currency fallback (ISO-4217).
        correlation_id: Caller-supplied idempotency key; generated if absent.
        expected_delivery_date: Optional ISO date YYYY-MM-DD.

    Returns:
        Dict with keys: po_id, status, supplier_id, subtotal_cents, currency,
        created_at, updated_at, correlation_id, expected_delivery_date,
        line_count, lines (list of line dicts).

    Raises:
        HTTPException(404) — flag off.
        HTTPException(422) — lines empty, quantity < 1, or unit_cost_cents
                             cannot be resolved for a line.
        HTTPException(409) — a PO with the same correlation_id already exists
                             (idempotent replay returns the existing record).
    """
```

**Detailed write sequence** (mirrors `commerce_order_service.py:64–104`):

1. `_require_enabled()`.
2. Validate `lines` is non-empty; raise 422 if not.
3. Build `corr = correlation_id or f"po:{supplier_id}:{uuid4().hex}"`.
4. Compute `po_id = hashlib.sha256(corr.encode()).hexdigest()[:32]` (mirrors `commerce_order_service.py:67`).
5. **Idempotency check**: call `get_purchase_order(po_id)` — if a header already exists, return the existing record immediately (no duplicate writes).
6. `now = now_ts()`.
7. For each line, resolve `unit_cost_cents`:
   - If provided by caller and `>= 0`, use it.
   - Else call `supplier_products.get_supplier_product(supplier_id, sku)` (local import); if it returns a record use `record["unit_cost_cents"]`.
   - Else raise `HTTPException(422, f"unit_cost_cents required for SKU '{sku}': no supplier-product record found")`.
   - Validate `quantity_ordered >= 1`; raise 422 if not.
   - Compute `line_total_cents = quantity_ordered * unit_cost_cents`.
8. Compute `subtotal_cents = sum(line_total_cents for each line)`.
9. Write header row (`SK="META"`) with `put_item`.
10. Write each line row (`SK=LINE#{n}`) in a `for idx, line in enumerate(resolved_lines, start=1)` loop; each `put_item` includes `line_no=idx`, `quantity_received=0` (mirrors `commerce_order_service.py:88–104`).
11. Call `_audit("purchase_order_created", created_by, po_id=po_id, supplier_id=supplier_id, subtotal_cents=subtotal_cents, line_count=len(resolved_lines), correlation_id=corr)` (mirrors `commerce_order_service.py:106–117`).
12. Return assembled dict.

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotency on `correlation_id`

The idempotency check in step 5 of `create_purchase_order` uses `get_purchase_order(po_id)` — a `Query` by PK on `T.purchase_orders`. If a header row already exists, return immediately without writing any new rows. This means:

- Replay with the same `correlation_id` is a no-op: the caller receives the original PO unchanged.
- A replay that changes any field (e.g., different `quantity_ordered`) still returns the original — the `correlation_id` determines identity, not content. This matches the `commerce_order_service` convention.
- A partially-written PO (header written, crash before all lines) will be returned as-is on replay. Section 10 flags this as an assumption to verify.

### 5.2 `unit_cost_cents` defaulting

The lookup `supplier_products.get_supplier_product(supplier_id, sku)` is called with the same `supplier_id` as the PO header. If the supplier has never registered this SKU (no `supplier_products` row), the caller must provide `unit_cost_cents` explicitly. This design keeps the service lean: no implicit creation of supplier-product records.

If `unit_cost_cents = 0` is supplied explicitly by the caller, it is accepted (free goods or inter-company transfers). The validation is `unit_cost_cents >= 0`, not `> 0`.

### 5.3 `subtotal_cents` computation

`subtotal_cents = sum(qty * unit_cost for each resolved line)`. Integer arithmetic only — no floats involved. The `_FloatSafeTable` wrapper at `app/core/tables.py:29–59` (`put_item` override at `:41–44`, `update_item` at `:46–49`, `batch_writer` at `:51–59`) coerces any float to `Decimal` before DDB writes, providing a safety net, but PUR-006 produces only integers.

### 5.4 `currency` resolution

The header `currency` is the caller-provided value. Individual lines inherit the header currency by default unless the caller passes per-line `currency`. Currency normalization (uppercasing, ISO validation) is delegated to the Pydantic model in the router ticket (PUR-010) — the service layer stores whatever string is passed. Line rows carry a denormalized `currency` field to make the line self-describing for future AP reconciliation.

### 5.5 `list_purchase_orders` — mutual exclusivity

If both `supplier_id` and `status` are provided, raise `HTTPException(422, "Provide exactly one of supplier_id or status")`. If neither is provided, raise `HTTPException(422, "One of supplier_id or status is required")`. This mirrors the `CatalogStockAdjustIn` validation at `app/models.py:566–570`.

`list_purchase_orders` returns header-only dicts. Lines are not included in list responses (avoids reading all line rows for every PO in a paginated list). Callers who need lines call `get_purchase_order(po_id)`.

### 5.6 `ScanIndexForward=False` for newest-first ordering

Both GSI queries use `ScanIndexForward=False` to return most-recently-created POs first. The GSI sort key is `created_at` (Unix timestamp integer). For a newly created PO with `created_at = now_ts()`, this means it surfaces at the top of the list immediately.

### 5.7 `GSI_STATUS` partition values

Valid `status` values for the initial ticket: only `"draft"` is ever written by PUR-006. PUR-007 will write `"submitted"`, `"approved"`, `"rejected"`, `"cancelled"`, `"ordered"`, `"partially_received"`, `"received"`, `"closed"`. The service validates that status values passed to `list_purchase_orders(status=...)` are non-empty strings but does not restrict them to a known set — the GSI simply returns no results for an unknown status.

### 5.8 `expected_delivery_date` validation

The service accepts any non-empty string. Format enforcement (`YYYY-MM-DD`) is a Pydantic-layer responsibility in PUR-010. The service stores `None` (attribute absent) when not provided.

### 5.9 Line row `LINE#{n}` format and `get_purchase_order` ordering

Line rows use zero-padded `n` only if there are more than 9 lines and lexicographic ordering is required. This spec uses `f"LINE#{n}"` without zero-padding (following `ITEM#{idx}` in `returns_rma.py:252`). Because `_get_all_po_items` sorts by `line_no` (the stored integer) in Python after fetching, lexicographic SK ordering is irrelevant for correctness. Zero-padding is optional for aesthetics; the sort is on the integer attribute.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

`T.purchase_orders` is a `_FloatSafeTable` wrapping `ddb.Table("purchase_orders")`. In dev, `ddb` points to DynamoDB Local (port 8001) or moto in tests. In prod it is real DynamoDB. No `dev_mode` branch exists in `purchase_orders.py` — identical code paths both environments. This follows the pattern in `inventory.py`, `returns_rma.py`, and every other OFBiz service module.

The `_audit` helper uses a local import of `alerts.audit_event` (same pattern as `inventory.py:92–98` and `returns_rma.py:85–91`) so an import-time failure in the alerts module does not prevent the service from loading.

### Idempotency

`create_purchase_order` is fully idempotent on `correlation_id`:
- Same `correlation_id` → same `po_id` (deterministic SHA-256 hash).
- The read-before-write check in step 5 prevents duplicate `put_item` calls.
- If the header already exists, the function returns the existing record — no error, no mutation.

`get_purchase_order` is read-only and trivially idempotent.

`list_purchase_orders` is read-only and trivially idempotent.

### Security

- `purchase_orders.py` is a pure service module with no HTTP surface. Authentication and CSRF enforcement are the responsibility of PUR-010's router.
- `created_by` is the `user_sub` of the authenticated user as passed by the router; the service does not validate it independently.
- `subtotal_cents` is computed server-side from stored `unit_cost_cents` and `quantity_ordered`. No client-supplied total is trusted.
- Supplier-product pricing is fetched from `T.supplier_products` (server-side), not passed by the caller, when `unit_cost_cents` is omitted from the line. This prevents a caller from under-pricing a PO line.
- Audit events are best-effort (exceptions swallowed in `_audit`). They are informational only, not the primary security audit trail.

## 10. Open Questions / Assumptions

1. **Assumption: Partial write (header written, process crash before line rows) is treated as a complete PO by the idempotency check.** The idempotency check in step 5 looks for an existing header row (`SK="META"`). If a crash occurs after writing the header but before writing all lines, a replay with the same `correlation_id` returns the partial PO (missing lines). This is an inherent limitation of non-transactional multi-`put_item` sequences. DynamoDB Transactions could fix this (writing header + all lines atomically) at the cost of added complexity. Verify with the team whether transactional writes are warranted; this spec assumes they are not needed for the initial implementation.

2. **Assumption: `created_by` is a `user_sub` string (from the authenticated session) and is not validated against the `users` table.** The service stores whatever string is passed. The router (PUR-010) injects `user.sub` from `Depends(require_admin_or_root_csrf)` (`app/auth/policy.py:100`), so only authenticated admin/root users can create POs. Supplier-facing creation (e.g., a supplier portal) is not in scope for this milestone.

3. **Assumption: `supplier_id` is not validated against `T.suppliers` at create time.** PUR-003 establishes the `suppliers` table and the `supplier_id` namespace, but PUR-006 does not do a `get_item` check against it on the PO create hot path. A non-existent `supplier_id` will create a PO with an orphaned FK. The router (PUR-010) can enforce this at the HTTP boundary. Verify with the team whether service-layer FK validation is required.

4. **Assumption: `list_purchase_orders` returns header-only items (no lines).** This matches the `list_returns_by_status` pattern at `app/services/returns_rma.py:298–312` (filters to `sk == "META"` rows in the GSI result) which returns header-only dicts. Callers who need lines call `get_purchase_order`. If the PUR-010 router needs to display a line-count in the list view, the `line_count` attribute on the header provides this without an extra fetch.

5. **Assumption: `currency` on line rows is denormalized from the header, not independently validated.** All lines on a PO are assumed to be in the same currency as the header. Multi-currency POs are not supported in this milestone. If a caller supplies per-line `currency` that differs from the header, the service stores it but does not reconcile or error. PUR-012 (AP/ledger) should validate currency consistency when producing the payable.

6. **Assumption: `GSI_STATUS` and `GSI_SUPPLIER` both project ALL attributes.** This means line rows (which lack `supplier_id` and `status`) are never projected into either GSI (DynamoDB only indexes items that have the GSI's partition key attribute). Only header rows carry `supplier_id` and `status`, so GSI queries correctly return header-only results. This is confirmed by the PUR-002 spec note: "Line rows (SK=LINE#{n}) do NOT carry `supplier_id` or `status`, so they are never projected into either GSI."

7. **Assumption: `now_ts()` (integer Unix seconds from `app/core/time.py:2`) is the timestamp used for `created_at` and `updated_at`.** This is consistent with other OFBiz services that use numeric timestamps (`inventory.py:141`, `returns_rma.py:232–244`) and is required because `created_at` is the numeric GSI sort key (stored as DDB type N). Note: `commerce_order_service.py` uses ISO strings via `_now_iso()` — PUR-006 intentionally diverges here (see section 2.1).

8. **Question: Should `list_purchase_orders` accept a `ScanIndexForward` parameter to allow oldest-first ordering?** The receiving workflow (PUR-008) may want oldest-approved-POs-first for FIFO processing. The default `ScanIndexForward=False` (newest-first) is appropriate for the approval queue but not for FIFO receiving. This spec defaults to newest-first with no override parameter; verify whether a `sort_asc: bool = False` parameter should be added.
