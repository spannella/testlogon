## 1. Summary & Goal

PTY-013 adds the TypeScript layer that connects the React frontend to every HTTP endpoint
delivered by PTY-011 and PTY-012. Two files are created or extended:

1. **`frontend/src/api/types.ts`** — new `// ── Party/CRM (PTY-013) ──` section near the end of
   the file (after line 13160, the current last line), containing TypeScript interfaces that
   mirror the `Crm`-prefixed Pydantic models from PTY-003 (`app/models.py`).

2. **`frontend/src/api/endpoints/party.ts`** — new file using the shared `api` helper from
   `frontend/src/api/client.ts` to expose one typed async function per backend route, following
   the same shape as `frontend/src/api/endpoints/contacts.ts`.

3. **`frontend/src/api/endpoints/party.test.ts`** — new vitest unit test file asserting URL and
   payload construction for every wrapper, following the pattern established by
   `frontend/src/api/endpoints/devtools.test.ts` (spy on `api.get` / `api.post` / etc.).

No backend files are touched. No existing frontend files are modified except
`frontend/src/api/types.ts` (additive append only). The existing contacts surface
(`frontend/src/api/endpoints/contacts.ts`, `frontend/src/api/types.ts` ContactEntry block
at line 3143) is byte-for-byte unchanged.

## 3. Data Model

PTY-013 is a **purely frontend TypeScript ticket** — it introduces no new DynamoDB tables, no
new backend service functions, and no new Pydantic models. The complete single-table DDB
schema is established by PTY-002 and documented in `docs/ofbiz/specs/PTY-011.md §3`. The
TypeScript interfaces in this ticket are read-side projections of the JSON that the
PTY-011/PTY-012 endpoints return.

For completeness, the response shapes that the TypeScript interfaces must match:

| DDB row type | JSON field reflected in TypeScript |
|---|---|
| Party META `PARTY#{id}` / `META` | `CrmPartyOut`: `party_id`, `party_type`, `status`, `created_at`, `updated_at`, `user_sub?` |
| Role row `PARTY#{id}` / `ROLE#{type}` | `CrmPartyRoleOut`: `party_id`, `role_type`, `created_at` |
| Relationship `PARTY#{from}` / `REL#{type}#{to}` | `CrmRelationshipOut`: `from_party_id`, `to_party_id`, `relationship_type`, `created_at` |
| Contact mech `PARTY#{id}` / `MECH#{type}#{mech_id}` | `CrmContactMechOut`: `mech_id`, `party_id`, `mech_type`, `value`, `purposes`, `verified`, `created_at`, `updated_at` |
| Org party (PARTY_GROUP + roles + relationships) | `CrmOrgOut`: `org_party_id`, `name`, `owner_user_sub`, `status`, `created_at`, `updated_at`, `member_count`, `roles` |
| Org membership `GROUP_MEMBER` relationship | `CrmOrgMemberOut`: `member_party_id`, `role_type`, `joined_at`, `user_sub?` |

## 5. Detailed Behavior & Edge Cases

### 5.1 CSRF — automatically handled by `client.ts`

All non-GET calls (`api.post`, `api.patch`, `api.del`) go through `api` in `client.ts:151`.
The CSRF token is read from the `ui_csrf` cookie at `client.ts:179`
(`const csrf = getCookie("ui_csrf"); headers.set("X-CSRF-Token", csrf)`) and set on every
request. The endpoint wrappers do **not** add any CSRF header manually; doing so would be
redundant and would duplicate the logic. This is the same convention as `contacts.ts` and every
other endpoint file.

### 5.2 `lookupParty` — passes `mech_type` and `value` as raw strings

`lookupParty(mech_type, value)` passes the two required query params as a plain object literal.
Unlike `listParties` / `listRelationships` / `listContactMechs`, both params are required
(no `cleanParams` needed — an absent `mech_type` or `value` would be a programming error).
Passing `undefined` as either argument triggers a TypeScript compile-time error because the
function signature is `(mech_type: CrmContactMechType, value: string)`.

Normalization (lowercase email, E.164 phone) is performed server-side inside
`find_party_by_contact` (PTY-007 service). The client passes the raw user input; the backend
normalizes and matches.

### 5.3 `deleteRelationship` — query params on DELETE

`api.del<void>(path, params)` calls `api(path, { method: "DELETE", params })` at
`client.ts:312–313` (verified: `api.del = <T>(path, params?) => api<T>(path, { method: "DELETE", params })`).
The `params` object becomes a query string (`?to_party_id=...&relationship_type=...`).
This is consistent with how the backend declares the endpoint:
`DELETE /parties/{party_id}/relationships?to_party_id=...&relationship_type=...`
per `docs/ofbiz/specs/PTY-011.md §4.4`.

A DELETE with a body is avoided because it is non-standard and the `contacts.ts` delete at
`frontend/src/api/endpoints/contacts.ts:15` also uses path params, not a body.

### 5.4 `CrmContactMechOut.value` union type

Contact mechanisms of type `EMAIL` or `PHONE` return `value` as a `string`. `POSTAL` mechs
return `value` as a `CrmPostalAddress` object. The TypeScript union `string | CrmPostalAddress`
is the correct narrow type. Consumers (e.g. `PartyPage.tsx` in PTY-014) must narrow this with
`typeof value === "string"` before rendering. The backend serializes POSTAL mechs as a nested
JSON object (not a stringified JSON string), so no JSON.parse is needed client-side.

### 5.5 Pagination — `cursor` parameter

`listParties`, `listRelationships`, and `listOrgs` all accept an optional `cursor: string`
parameter that is passed verbatim to the backend as a query param. This is the opaque
base64-encoded cursor from `app/core/cursor.py` as used by other list endpoints (e.g.
the `messages` and `tickets` paginators). The response envelopes — `CrmPartyListOut`,
`CrmRelationshipListOut`, `CrmOrgListOut` — carry `cursor: string | null` where `null` means
no further pages.

### 5.6 `adminMigrateContacts` and `adminEnsurePerson` — require admin session

These two wrappers post to `/ui/admin/party/*` endpoints. The backend enforces
`require_admin_session` (at minimum ADMIN role). The frontend is responsible for only rendering
the UI controls that invoke these wrappers when the logged-in user holds the admin role
(determined via the auth store's `role` field). The endpoint file itself does not gate on
role — that is the caller's responsibility, consistent with every other admin wrapper
(e.g., `frontend/src/api/endpoints/adminRoles.ts`).

### 5.7 `cleanParams` — avoids passing empty string as a query parameter

If `listParties({ party_type: undefined })` is called, the `cleanParams` helper filters out
the `undefined` value so the resulting query string is `?` (empty), not `?party_type=undefined`.
Similarly, `limit: undefined` is filtered out and the backend applies its default of 50.
This mirrors the `devtools.ts:34` pattern exactly.

### 5.8 Enum literal types — must stay in sync with backend

The union literal types `CrmPartyRoleType`, `CrmRelationshipType`, `CrmContactMechType`, and
`CrmContactMechPurpose` are manually kept in sync with the corresponding Python Enum values
in PTY-003. If new values are added to the backend enums post-PTY-013, both the Python enum
and the TypeScript union literal must be updated together. The vitest test suite provides a
compile-time guard (TypeScript will error if an unknown literal is passed to a typed function).
A future improvement would be to auto-generate types from the OpenAPI spec, but that is out
of scope for Phase 1.

### 5.9 `createOrg` vs org-account PERSON party precondition

The backend's `POST /ui/party/orgs` endpoint (PTY-012) requires the caller to already have
a PERSON party (`ensure_person_party` must have been called). The `createOrg` wrapper does
not enforce this precondition — it is the caller's responsibility to handle the 422 or 404
that the backend returns if no PERSON party exists for the session's `user_sub`. PTY-014
(PartyPage) will call `ensure_person_party` lazily on page load.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No frontend mock/dev branch

`party.ts` contains no `if (DEV_MODE)` or `import.meta.env.DEV` branch. Every wrapper
calls the real backend URL via `api` from `client.ts`. The backend itself handles the
dev/prod distinction inside `app/services/party.py` (single DynamoDB path regardless of
`S.dev_mode`). SECOPS-007 parity is therefore satisfied by construction.

### 7.2 CSRF enforced unconditionally

`client.ts:179` reads `ui_csrf` and attaches `X-CSRF-Token` on every request. The wrappers
cannot accidentally bypass CSRF because they delegate to `api`, which always does the cookie
read. There is no Bearer-only bypass path at the frontend layer (the frontend always has both
cookies and Bearer; the `X-CSRF-Token` is attached regardless of which auth mode the backend
will use for the session).

### 7.3 Idempotency fields threaded through

`CrmPartyIn.correlation_id` and `CrmRelationshipIn.correlation_id` are optional fields in the
TypeScript request interfaces, matching the backend Pydantic models. PTY-014 (PartyPage) will
generate idempotency keys (e.g., `crypto.randomUUID()`) and pass them via `createParty` /
`createRelationship`. The wrappers are transparent pass-throughs: they serialize the body to
JSON and let the backend perform the `sha256(correlation_id)[:32]` derivation
(per `docs/ofbiz/specs/PTY-004.md:80`).

### 7.4 No PII in URLs

All PII values (email, phone, postal address) are in request bodies (`api.post` / `api.patch`)
or query params. The `lookupParty` call passes `value` (e.g. an email address) as a query
param — this ends up in server access logs. This is an inherent property of `GET` + query-param
lookups and is acceptable for the Phase 1 CRM use case (the endpoint is session-authenticated,
not public). A future improvement could use a `POST /parties/lookup` with a body, but that
would break REST conventions and is deferred.

## 10. Open Questions / Assumptions

1. **`CrmContactMechOut.value` union type vs two separate fields:** The spec assumes `POSTAL`
   mechs serialize `value` as a nested JSON object (`CrmPostalAddress`) and `EMAIL`/`PHONE`
   mechs serialize `value` as a plain string. If PTY-003 instead stores POSTAL as a
   stringified JSON string, the TypeScript type should be `string` (and PTY-014 would
   JSON.parse it). **Assumption:** object serialization (not stringified). Verify against
   the PTY-003 spec (`docs/ofbiz/specs/PTY-003.md`) and actual backend output before
   implementing PTY-014.

2. **`CrmOrgOut.roles` field:** The spec includes `roles: CrmPartyRoleType[]` on `CrmOrgOut`
   to show which roles the org party carries (`CUSTOMER`, `BILL_TO`, etc.). If the backend
   response for `GET /ui/party/orgs/{id}` does not embed the roles array (instead requiring
   a separate `GET /parties/{id}/roles` call), remove `roles` from `CrmOrgOut` and have
   PTY-014 fetch roles separately. **Assumption:** embedded for convenience — verify against
   the PTY-012 router response shape once that spec is written.

3. **`CrmOrgMemberOut.user_sub` optionality:** An org member may be a `PARTY_GROUP` (org-of-orgs
   scenario), in which case there is no `user_sub`. The interface marks it `user_sub?: string | null`.
   If the backend always guarantees a `user_sub` for members (only PERSON parties can be members),
   the `?` can be removed. **Assumption:** nullable for future-proofing.

4. **Admin migration wrapper prefix:** The admin migration endpoints (`/ui/admin/party/*`) use
   a different prefix from the party router (`/ui/party/*`). The `adminMigrateContacts` and
   `adminEnsurePerson` wrappers use hardcoded `/ui/admin/party/...` paths rather than the
   `BASE` constant. This matches how `frontend/src/api/endpoints/adminRoles.ts` uses a separate
   `/ui/admin/...` prefix. **Assumption:** correct and consistent with PTY-012 router design.

5. **`deleteRelationship` body vs query params:** The spec passes `to_party_id` and
   `relationship_type` as query params (via `api.del(path, params)`). The `api.del` shortcut
   in `client.ts:312` passes params as a query string. If the backend changes to a path-param
   design (e.g. `DELETE /parties/{id}/relationships/{rel_type}/{to_party_id}`), the wrapper
   signature would change. **Assumption:** query-param DELETE as per PTY-011 spec.

6. **`listOrgs` scope:** The `GET /ui/party/orgs` backend endpoint (PTY-012) may return only
   orgs where the caller is a member, or all orgs in the system (admin-style). The wrapper
   accepts a `cursor` for pagination in either case. The TypeScript interface does not need
   to know which scoping is applied — that is purely backend logic. **Assumption:** scoped
   to caller's memberships.

7. **`CrmPartyStatus` `"merged"` value:** The `merged` status is listed as a possible value per
   PTY-003. If the backend enum omits `merged` in Phase 1 (deferred per PTY-011 §5.5), the
   TypeScript union should also omit it to avoid a false sense of completeness. **Assumption:**
   include it in the union but document as reserved.
