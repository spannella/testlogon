# FAC-012 — Frontend types & endpoint wrappers

## 1. Summary & Goal

FAC-012 adds the TypeScript counterparts to all backend surfaces introduced by FAC-003 through FAC-011: a block of TypeScript interfaces in `frontend/src/api/types.ts` that mirror the FAC-003 Pydantic shapes, two new endpoint-wrapper files (`frontend/src/api/endpoints/facilities.ts` and `frontend/src/api/endpoints/fulfillment.ts`), a `VITE_FACILITY_FULFILLMENT_ENABLED` feature flag in `frontend/src/lib/featureFlags.ts`, and no changes to any existing type or wrapper.

The goal is to give the FAC-013 page component a typed, tested, zero-`any` API layer it can import directly — the same layer pattern that `InventoryAdmin.tsx` (`frontend/src/pages/shop/admin/InventoryAdmin.tsx:19–24`) uses against `frontend/src/api/endpoints/inventory.ts`. <!-- VERIFIED: InventoryAdmin.tsx:19–24 is the import block from inventory.ts; spec previously cited :21–24 (off-by-2) -->

Scope boundary: FAC-012 covers **only** types, wrappers, and the feature-flag export. Routes, pages, nav entries, and E2E specs are FAC-013 and FAC-015.

## 3. Data Model

FAC-012 is a frontend-only ticket. It introduces no DynamoDB tables, no settings keys, and no changes to `scripts/local-ddb-init.py`, `app/core/tables.py`, or `app/core/settings.py`.

The TypeScript types below mirror the Pydantic shapes defined in FAC-003 (`docs/ofbiz/specs/FAC-003.md`, Section 4). Field names and types are preserved exactly so that `JSON.parse(response)` on a backend `FacilityOut` / `TransferOut` / `ShipmentOut` payload satisfies the TypeScript interface without any runtime transformation.

All `int` Pydantic fields become `number` in TypeScript. All `Optional[X]` become `X | undefined` (using TypeScript's idiomatic `optional property` syntax `field?: X`). All `List[T]` become `T[]`. All `Optional[int]` timestamp fields (e.g. `completed_at`, `shipped_at`, `delivered_at`) become `number | undefined` rather than a default of `0`, mirroring the FAC-003 note that these fields are absent until the event occurs (`docs/ofbiz/specs/FAC-003.md`, Section 5.2).

## 5. Detailed Behavior & Edge Cases

### 5.1 `encodeURIComponent` on all path parameters

Every function that interpolates a dynamic value into a URL path calls `encodeURIComponent`. This matches the existing inventory wrapper at `frontend/src/api/endpoints/inventory.ts:14` (`encodeURIComponent(sku)`) <!-- VERIFIED: inventory.ts:14 --> and prevents path-injection if a `facility_id`, `location_id`, `sku`, or `transfer_id` contains a slash or other reserved character. The backend does not decode double-encoded values differently; a forward slash in an ID would break routing at the proxy layer regardless, so encoding is the correct defense.

### 5.2 Pagination `params` shape

The `api.get` convenience method at `client.ts:290–291` accepts `params?: Record<string, string>`. <!-- VERIFIED: client.ts:290 --> Pagination parameters (`limit`, `cursor`, `status`) are therefore typed as `string` in the wrapper function's `params` argument even though the backend interprets `limit` as an integer. The caller passes `String(50)` or `"50"` — the URL serialisation via `new URLSearchParams` at `client.ts:160` converts everything to strings anyway. <!-- CORRECTED from :161: URLSearchParams is at client.ts:160 -->

### 5.3 `correlation_id` is required on `ReceiveIn`

`ReceiveIn.correlation_id` is typed as `string` (not `string | undefined`) in the TypeScript interface, matching the FAC-003 Pydantic field which is required (not `Optional`). This is intentional: the TypeScript compiler will enforce that callers always supply an idempotency key before the backend rejects a missing value with a 422.

### 5.4 `PackPacklistIn` vs `ShipmentIn` naming

FAC-003 defines a `ShipmentIn` Pydantic model that includes `picklist_id`, `carrier`, `tracking_number`, and `packages`. However the FAC-011 `pack_picklist_endpoint` takes the picklist ID from the URL path (`/picklists/{picklist_id}/pack`) and accepts only the package list in the body — which FAC-003 calls `PackPacklistIn`. This spec uses `PackPacklistIn` for the body and keeps `ShipIn` for the ship endpoint body (carrier + tracking_number), matching the FAC-011 handler signatures exactly.

If FAC-011 was implemented with a single body model that includes all fields, the wrapper can be adjusted without changing any consumer — the type is only imported in the wrapper file and the page.

### 5.5 `cancelTransfer` with optional body

`cancelTransfer(transferId, body?)` passes `body ?? {}` to `api.post`. When `body` is `undefined` (no reason provided), the backend receives an empty JSON object `{}`, which Pydantic accepts because `TransferCancelIn.reason` is `Optional`. This avoids a 422 from a missing body on a `POST` with `Content-Type: application/json`.

The same pattern is used in `cart.ts:purchaseCart` (`body ?? {}`).

### 5.6 `advanceTransfer`, `completeTransfer`, `archiveFacility`, `archiveLocation`, `cancelShipment` — no request body

These action endpoints accept no body; the router handlers in FAC-005 and FAC-011 have no `body:` parameter. Calling `api.post<T>(url)` with no body argument matches `client.ts:297`: `body != null ? JSON.stringify(body) : undefined` resolves to `undefined`, so no `Content-Type` header is set and no body is sent. <!-- CORRECTED from :294: the `body != null` conditional is at client.ts:297; line 294 is `api<T>(path, {` --> This is the correct behaviour for bodyless POSTs.

### 5.7 `listFacilityReceipts` path collision with `getFacility`

`listFacilityReceipts` calls `GET /ui/fulfillment/facilities/{facilityId}/receipts`. This path is under the `/ui/fulfillment` prefix (the `fulfillment_router`) and does NOT collide with `GET /ui/facilities/{facilityId}` (the `facilities_router` under prefix `/ui/facilities`). The proxy in `vite.config.ts` routes both prefixes to the backend, and the backend discriminates by the full path. No proxy-rule conflict.

### 5.8 `isFacilityFulfillmentEnabled` usage in FAC-013

`isFacilityFulfillmentEnabled()` returns a **module-level computed boolean** (evaluated once at import time, not dynamically). This is the same approach used by `isInventoryReservationsEnabled()` at `featureFlags.ts:161`. The flag is safe to read in component render functions and React hooks without triggering re-renders. If runtime flag toggling is needed, the pattern would need to change to a React context or store — but that is outside FAC-012 scope and is not needed since the flag maps directly to the `VITE_*` env var baked into the bundle at build time.

### 5.9 `FacilityListOut.next_cursor` vs `FacilityLocationListOut` (no cursor)

`FacilityListOut` includes `next_cursor?: string` because the `list_facilities` service function paginates. `FacilityLocationListOut` does not include `next_cursor` because the spec (FAC-003 Section 4.2 note) expects a facility to have O(100) locations, making pagination unnecessary. If FAC-004 later adds pagination to `list_locations`, a `next_cursor?: string` field can be added to `FacilityLocationListOut` without a breaking change (additive field on an interface).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/Prod parity

`facilities.ts` and `fulfillment.ts` contain no `import.meta.env` reads and no `dev_mode` branches. The wrapper functions call the same endpoint paths (`/ui/facilities/*`, `/ui/fulfillment/*`) in dev and prod. The backend's dev/prod parity is guaranteed by the service layer (FAC-004 through FAC-010); the frontend wrappers are agnostic to environment.

### CSRF

`client.ts:179–182` reads the `ui_csrf` cookie and attaches it as `X-CSRF-Token` on every non-GET request automatically. <!-- VERIFIED: client.ts:179–182 matches (getCookie("ui_csrf") + headers.set("X-CSRF-Token", csrf)) --> The wrapper functions do not need to handle CSRF explicitly — mutations (`api.post`, `api.put`, `api.del`) pick up the token automatically. This is identical to how `inventory.ts:adjustInventory` <!-- VERIFIED: inventory.ts:20 --> and `cart.ts:purchaseCart` <!-- VERIFIED: cart.ts:43–50 --> work.

### No secrets or PII in types

The TypeScript interfaces carry only the fields the backend sends. `owner_sub`, `created_by`, `received_by`, `actor_sub` are opaque sub strings (not names, emails, or addresses). No new PII categories are introduced.

### Idempotency surface

`ReceiveIn.correlation_id` is typed non-optional. The TypeScript compiler will flag any caller that omits it, preventing the class of bug where a receiving form submits without a correlation key and double-increments on-hand on network retry. `TransferIn.idempotency_key` remains optional (the backend generates a UUID fallback when absent) — reflected by `idempotency_key?: string` in the interface.

### No `any` types

Every wrapper function is fully typed. The `api.get<T>` / `api.post<T>` generic parameter is always supplied. `Partial<FacilityIn>` on `updateFacility` is the idiomatic TypeScript way to accept patch bodies; it does not introduce `any`. The ticket's acceptance criterion ("no `any` for the new shapes") is met by the design.

## 10. Open Questions / Assumptions

1. **`FacilityListOut.next_cursor` field name.** This spec mirrors the `TransferListOut.next_cursor` naming convention from FAC-003. If the FAC-004 service uses `cursor` as the pagination continuation token key instead of `next_cursor`, the `FacilityListOut` interface must change. Verify against `list_facilities` return shape in `app/services/facilities.py` before merging.

2. **`PicklistListOut` wrapper shape.** FAC-011 `list_picklists_for_order` returns `{"picklists": [...]}` (a plain inline dict, not a `PicklistListOut` response model). The TypeScript interface `PicklistListOut` mirrors this. If the endpoint is changed to use a Pydantic response model in a later pass, the interface is already correct and no wrapper change is needed.

3. **`ShipmentListOut` vs inline return.** Similarly, `list_shipments_for_order` in FAC-011 delegates to `pak.list_shipments_for_order`. Whether that service returns `{"shipments": [...], "next_cursor": ...}` or a bare list depends on FAC-009's implementation. The spec assumes the former (with cursor) to be consistent with the other list endpoints.

4. **`updateFacility` HTTP verb.** This spec uses `api.put` (`PUT /ui/facilities/{id}`). If FAC-005 implements update as `PATCH` instead, the wrapper must change to `api.patch`. Verify the FAC-005 router handler declaration before merging.

5. **`updateLocation` HTTP verb.** Same question as item 4, for `PUT /ui/facilities/{fid}/locations/{lid}`.

6. **`archiveFacility` / `archiveLocation` response model.** The spec assumes these return `FacilityOut` / `FacilityLocationOut` with `status: "archived"`. If FAC-005 returns `204 No Content`, the wrapper return type should be `void` (or `undefined`). Verify against the FAC-005 spec.

7. **`VITE_FACILITY_FULFILLMENT_ENABLED` in `frontend/.env.local.example`.** This spec recommends adding the env var comment but does not require it as a blocking AC. The flag defaults to `false` without the env var, so the build succeeds without it.

8. **`PackPacklistIn` naming.** This spec names the pack-endpoint body type `PackPacklistIn` (matching FAC-003). If FAC-011 was implemented with a different body model name (e.g. `PackIn`), the TypeScript interface name should match the backend model for clarity, but the JSON field names are what matter at runtime.

9. **Lot/serial wrappers.** FAC-014 (lot/serial tracking) is a separate ticket and is P2/optional. The `LotOut` and `SerialOut` TypeScript interfaces are included in FAC-012 alongside the other types (the backend models exist in FAC-003) but no endpoint wrappers are created for the lot/serial endpoints — those ship with FAC-014.
