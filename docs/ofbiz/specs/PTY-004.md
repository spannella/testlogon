# PTY-004 — Party CRUD service (PERSON / PARTY_GROUP)

**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days  
**Milestone:** 2 — Party Service Core  
**Depends on:** PTY-002 (`T.party` handle), PTY-003 (Pydantic models)

## 1. Summary & Goal

PTY-004 creates `app/services/party.py`, the single-table access layer for the OFBiz Party/CRM
model. It exposes four public functions:

| Function | Purpose |
|---|---|
| `create_party(party_type, *, user_sub=None, correlation_id=None) -> dict` | Idempotent write of a `PARTY#…/META` row |
| `get_party(party_id) -> dict \| None` | Fetch a single party by ID |
| `list_parties(party_type=None, *, cursor=None, limit=50) -> dict` | Newest-first paginated listing via `GSI_CREATED` |
| `update_party_status(party_id, status) -> dict` | Validated status transition + audit event |

The service is entirely additive. With `S.party_crm_enabled` off (the default), no existing code
path touches `T.party`; every caller in downstream tickets is required to guard itself with the
same flag. With the flag on, the service provides the persistence layer for all future party-role,
relationship, contact-mechanism, and organisation-account tickets (PTY-005 through PTY-010).

## 3. Data Model

### 3.1 Party-meta row (`SK = META`)

```json
{
  "PK":         "PARTY#<party_id>",
  "SK":         "META",
  "party_id":   "<party_id>",
  "party_type": "PERSON | PARTY_GROUP",
  "status":     "ACTIVE",
  "user_sub":   "<cognito_sub> | null",
  "type":       "TYPE#PERSON | TYPE#PARTY_GROUP",
  "created_at": 1749200000,
  "updated_at": 1749200000,
  "correlation_id": "<value> | null",
  "GSI3PK":    "OWNER#<user_sub>",
  "GSI3SK":    "PARTY#<party_id>"
}
```

**Field notes:**

- `type` is the `GSI_CREATED` partition key value (e.g. `TYPE#PERSON`). It allows `list_parties`
  to issue a GSI query with `Key("type").eq(f"TYPE#{party_type}")` and get newest-first ordering
  via `ScanIndexForward=False`. When `party_type=None` the service must do separate queries per
  type or a filtered scan (see Section 5.3).
- `created_at` and `updated_at` are integer Unix seconds from `app/core/time.now_ts()`.
- `GSI3PK` / `GSI3SK` are only written when `user_sub` is not `None`. They enable the future
  `find_parties_by_user_sub(user_sub)` O(1) GSI query without scanning.
- `correlation_id` is stored as a plain attribute for audit purposes; it is not used for queries.

### 3.2 DynamoDB table summary (not new — established by PTY-002)

The `party` table is defined at `scripts/local-ddb-init.py` (added by PTY-002) with:

```python

```

## 4. API / Service Design

### 4.1 Service module: `app/services/party.py`

```python
from __future__ import annotations

import hashlib
import uuid
from typing import Any, Dict, List, Optional

from boto3.dynamodb.conditions import Key
from botocore.exceptions import ClientError

from app.core.cursor import decode_cursor, encode_cursor
from app.core.tables import T
from app.core.time import now_ts
from app.services.alerts import audit_event


_VALID_PARTY_TYPES = {"PERSON", "PARTY_GROUP"}

_PARTY_STATUS_TRANSITIONS: Dict[str, set] = {
    "ACTIVE":   {"ACTIVE", "INACTIVE", "MERGED"},
    "INACTIVE": {"INACTIVE", "ACTIVE"},
    "MERGED":   {"MERGED"},
}


def create_party(
    party_type: str,
    *,
    user_sub: Optional[str] = None,
    correlation_id: Optional[str] = None,
) -> Dict[str, Any]:
    ...

def get_party(party_id: str) -> Optional[Dict[str, Any]]:
    ...

def list_parties(
    party_type: Optional[str] = None,
    *,
    cursor: Optional[str] = None,
    limit: int = 50,
) -> Dict[str, Any]:
    ...

def update_party_status(party_id: str, status: str) -> Dict[str, Any]:
    ...
```

#### `create_party` — detailed contract

```python
def create_party(
    party_type: str,
    *,
    user_sub: Optional[str] = None,
    correlation_id: Optional[str] = None,
) -> Dict[str, Any]:
```

1. Validate `party_type in _VALID_PARTY_TYPES`; raise `ValueError` otherwise (caller converts to
   HTTP 422).
2. Derive `party_id`:
   - If `correlation_id` is supplied: `party_id = hashlib.sha256(correlation_id.encode()).hexdigest()[:32]`
   - Otherwise: `party_id = uuid.uuid4().hex`
3. Build the item dict with `PK`, `SK`, all scalar fields, integer `created_at = now_ts()`, and
   optionally `GSI3PK`/`GSI3SK` when `user_sub` is not `None`.
4. Call `T.party.put_item(Item=item, ConditionExpression="attribute_not_exists(PK)")`.
5. On `ClientError` with code `ConditionalCheckFailedException`, fetch the existing item via
   `get_party(party_id)` and return it (idempotent replay — no audit event emitted on replay).
6. On success, call `audit_event("party_created", user_sub or "system", None, party_id=party_id, party_type=party_type)`.
7. Return the item dict.

#### `get_party` — detailed contract

```python
def get_party(party_id: str) -> Optional[Dict[str, Any]]:
```

Single `T.party.get_item(Key={"PK": f"PARTY#{party_id}", "SK": "META"})`. Returns `None` if the
item is absent; returns the item dict otherwise. Strips internal GSI keys (`GSI3PK`, `GSI3SK`)
before returning to avoid leaking key structure to callers.

#### `list_parties` — detailed contract

```python
def list_parties(
    party_type: Optional[str] = None,
    *,
    cursor: Optional[str] = None,
    limit: int = 50,
) -> Dict[str, Any]:
```

Returns `{"parties": [...], "next_cursor": str | None, "count": int}`.

- When `party_type` is supplied, query `GSI_CREATED` with
  `Key("type").eq(f"TYPE#{party_type}")`, `ScanIndexForward=False` (newest-first),
  `Limit=limit`, `ExclusiveStartKey=decode_cursor(cursor)` (when cursor is not `None`).
- When `party_type` is `None`, issue two sequential queries — one for `TYPE#PERSON` and one for
  `TYPE#PARTY_GROUP` — both with `limit // 2` (rounded up), merge and re-sort by `created_at`
  descending in Python, then slice to `limit`. In this case no `next_cursor` is returned (callers
  wanting large all-type listings should filter by type). This approach avoids a full-table scan
  and is correct for the expected party counts in this application.
- Encode `resp.get("LastEvaluatedKey")` via `encode_cursor`; if absent, `next_cursor` is `None`.

**Page size cap:** `limit = min(limit, 100)` to prevent unbounded scans.

#### `update_party_status` — detailed contract

```python
def update_party_status(party_id: str, status: str) -> Dict[str, Any]:
```

1. `existing = get_party(party_id)` — raise `KeyError` if not found (caller converts to 404).
2. `current_status = existing["status"]`
3. Validate: `status in _PARTY_STATUS_TRANSITIONS[current_status]`; raise `ValueError` if not
   (caller converts to 422).
4. If `status == current_status`, return the existing item unchanged (no-op, no audit event).
5. Call `T.party.update_item(...)` with `UpdateExpression="SET #s = :s, updated_at = :u"` and
   `ConditionExpression="#s = :cur"` to guard against concurrent status changes.
6. Catch `ConditionalCheckFailedException` → raise `ValueError("concurrent_status_conflict")`.
7. Emit `audit_event("party_status_changed", existing.get("user_sub") or "system", None, party_id=party_id, from_status=current_status, to_status=status)`.
8. Return the updated item (re-fetch via `get_party` after the update).

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent create replay

When the caller supplies the same `correlation_id` twice:

1. First call: `put_item` succeeds → returns the newly-created item + emits audit event.
2. Second call: `put_item` raises `ConditionalCheckFailedException` → service calls
   `get_party(party_id)` and returns the existing item without emitting a second audit event.

The caller cannot distinguish a first create from a replay by the response shape — both return
a `201` with the same `PartyOut`. This is intentional: idempotency is a contract guarantee, not
a debug signal. If the caller needs to detect replays they should use the `created_at` field.

### 5.2 `correlation_id` collision under different `party_type`

Because `party_id = sha256(correlation_id)[:32]` is purely content-addressed, two calls with the
same `correlation_id` but different `party_type` values will hit the same `PK`. The second call
will return the first party's record unchanged (the `ConditionExpression` prevents overwrite).
Callers are responsible for namespacing their `correlation_id` values to avoid cross-type
collisions (e.g. prefix with the party type: `"PERSON:invoice-42"`).

### 5.3 `list_parties` with `party_type=None`

The `GSI_CREATED` index uses `type` as the partition key (`TYPE#PERSON` or `TYPE#PARTY_GROUP`).
DynamoDB GSI queries require an equality condition on the partition key, so a single query cannot
return rows from both types. When `party_type=None`:

- Two queries are issued (one per type), each limited to `ceil(limit / 2)` items.
- Results are merged and re-sorted by `created_at` descending in Python.
- The total result set is sliced to `limit`.
- No `next_cursor` is returned (because the two-query merge invalidates DynamoDB's internal
  continuation key). Callers who need deep pagination must pass an explicit `party_type`.

This design explicitly trades completeness for simplicity; the expected total party count per user
in Phase 1 is small (hundreds, not millions).

### 5.4 Concurrent status update race condition

Between `get_party` and `update_item`, another process could advance the status. The
`ConditionExpression="#s = :cur"` guard ensures that if the status has moved, DynamoDB raises
`ConditionalCheckFailedException`. The service converts this to `ValueError("concurrent_status_conflict")`, which the router maps to HTTP 409.

### 5.5 `MERGED` status is terminal

Once a party reaches `MERGED` status, no further transitions are allowed. The transition table
has `"MERGED": {"MERGED"}` (self-only). Any attempt to move out of `MERGED` raises a `ValueError`
with message `"invalid_status_transition"`, which the router converts to HTTP 422.

### 5.6 `user_sub` ownership

When `user_sub` is provided, `GSI3PK = "OWNER#{user_sub}"` and `GSI3SK = "PARTY#{party_id}"` are
written onto the META row. This allows future `find_parties_by_user_sub(user_sub)` to query
`GSI3` without scanning. No ownership enforcement is implemented in PTY-004 — any authenticated
user can create a party record linked to any `user_sub`. Access control scoping is deferred to a
later milestone.

### 5.7 Decimal coercion from DynamoDB

DynamoDB returns all numeric attributes as `Decimal`. Both `created_at` and `updated_at` must be
coerced to `int` in `_item_to_party_out` before constructing `PartyOut`. This matches the pattern
used throughout the codebase (e.g. `app/services/purchase_history.py` Decimal-to-int coercions).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

There is no `S.dev_mode` branch in `app/services/party.py`. All four service functions operate
identically in dev (moto-backed DynamoDB Local) and prod (real DynamoDB). The only
environment-specific behaviour is which DynamoDB endpoint is used — this is handled transparently
by the boto3 client configuration sourced from `.env.local` (`DDB_ENDPOINT_URL=http://localhost:8001`).

### Idempotency

Write idempotency is enforced at the database layer via `attribute_not_exists(PK)` on `put_item`,
not by pre-checking existence with a `get_item`. This is the correct approach because
pre-check → write has a TOCTOU race window. The conditional put is atomic.

`update_party_status` uses a version-guarded update (`ConditionExpression="#s = :cur"`) to prevent
lost updates under concurrent callers. This is a lightweight optimistic-lock that does not require
a separate version counter.

### Security considerations

- **No PII in `party_id`:** `party_id` is either a truncated SHA-256 of the caller-supplied
  `correlation_id` or a random `uuid4().hex`. Neither leaks user identity in URLs or logs.
- **`correlation_id` is not secret:** it is stored on the DDB item and returned in audit events.
  Callers should not use secrets as `correlation_id` values.
- **Owner isolation:** `GSI3` allows future per-user scoping but PTY-004 does not enforce it.
  The router uses `require_ui_session` which authenticates the caller but does not scope reads to
  `ctx["user_sub"]`. A future ticket should add ownership-based filtering when user-scoped list
  endpoints are needed.
- **Input validation:** `party_type` is validated against `_VALID_PARTY_TYPES` before any DynamoDB
  call. An invalid type raises `ValueError` at the service layer, converted to HTTP 422 by the
  router.
- **No money-out path:** this service has no billing or payment integration. The GL/ledger
  constraint in the cross-cutting requirements does not apply here.

### 9.2 E2E spec: `frontend/e2e/party-crm.spec.ts`

**Prerequisite:** `PARTY_CRM_ENABLED=1` set in the test environment (or via `.env.local`).

**Section 1 — Flag off returns 503:**
- `POST /ui/party` with flag off (default) → 503.
- `GET /ui/party/anything` with flag off → 503.

**Section 2 — CRUD via authenticated session (Alice):**
- Create PERSON party → 201, `party_id` present.
- Create PARTY_GROUP party → 201.

- `GET /ui/party?party_type=PERSON` → list contains the created party.

**Section 3 — Idempotency:**
- POST with same `correlation_id` twice → same `party_id` in both responses; `GET /ui/party?party_type=PERSON` count unchanged.

**Section 4 — Pagination:**
- Create 5 PERSON parties. `GET /ui/party?party_type=PERSON&limit=2` → 2 results + `next_cursor`. Follow cursor → next 2. Follow again → remaining 1, no cursor.

## 10. Open Questions / Assumptions

1. **PTY-003 models assumed present.** This spec assumes `CreatePartyIn`, `PartyOut`, and
   `UpdatePartyStatusIn` are added to `app/models.py` by PTY-003 before PTY-004 is implemented.
   If PTY-003 is delayed, the router can inline minimal Pydantic models locally to unblock
   PTY-004.

2. **`require_ui_session` returns a `dict` with key `"user_sub"`.** This is confirmed by
   `app/routers/contacts.py:63-64`. PTY-004 follows the same pattern.

3. **No per-user scoping on list/get.** The current design allows any authenticated user to fetch
   any party record by `party_id`. This may be revisited in a later milestone when B2B
   organisation account isolation is implemented (PTY-010).

4. **`correlation_id` uniqueness is the caller's responsibility.** The service does not validate
   uniqueness across `party_type` values. If two callers independently use the same opaque ID for
   different purposes, the second caller silently receives the first party record. Callers should
   use a namespace prefix (e.g. `f"PERSON:{their_id}"`).

5. **`list_parties(party_type=None)` returns no `next_cursor`.** This assumption is documented in
   Section 5.3. If future requirements demand deep pagination across both types, the data model
   will need a single shared partition key (e.g. `ALL_PARTIES`) on `GSI_CREATED`, which is a
   schema change requiring `UpdateTable` in prod.

6. **`now_ts()` is not mocked in the default test setup.** Timing-sensitive tests (e.g.
   pagination ordering) must either patch `app.services.party.now_ts` or create parties with
   explicit sleeps between creations. The recommended approach is patching — see
   `tests/test_newsfeed_recsys.py` for the `now_ts` patch pattern.

7. **`app/main.py` router registration placement.** The spec says "next to the contacts router"
   but does not prescribe a line number because `app/main.py` is modified by many tickets. The
   implementer should confirm the current line number of the contacts `include_router` call before
   inserting.

8. **CSRF enforcement.** `POST` and `PATCH` endpoints use `require_ui_session` (cookie auth) and
   therefore require the `x-csrf-token` header in E2E tests, following the same pattern as all
   other non-GET cookie-auth endpoints. Bearer-auth callers (e.g. API key integrations) bypass
   CSRF.
