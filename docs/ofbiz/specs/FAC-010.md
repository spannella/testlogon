# FAC-010 — Ship shipment (carrier, tracking, order linkage)

## 1. Summary & Goal

FAC-010 delivers `app/services/shipping_fulfillment.py`, the final warehouse-side lifecycle step in the OFBiz Facility application. Its single core responsibility is: **finalize a draft shipment by stamping carrier and tracking number, advancing the shipment status to `shipped`, and emitting the fulfillment event that the ORD Order-lifecycle module consumes to advance the order to `shipped`**.

Concretely this ticket ships:

1. **`ship_shipment(shipment_id, *, carrier, tracking_number, shipped_by, service_level=None, notes=None)`** — the primary entry point in `app/services/shipping_fulfillment.py`. It conditions on `status = "draft"` (the value set by FAC-009 `pack_picklist`), stamps `carrier`, `tracking_number`, `shipped_at`, and advances the shipment to `shipped` via a single-writer conditional update. On success it optionally links the tracking number into the purchase-transaction shipping record via `purchase_history.update_shipping` and emits the `order.fulfillment.shipped` event for the ORD module to consume.
2. **`cancel_shipment(shipment_id, *, cancelled_by, reason="")`** — cancels a draft-or-packed shipment that has not yet been shipped. Transitions `status = "draft"` (or `"packed"` if FAC-002/009 ever writes that as an intermediate) → `"cancelled"`, and calls `inventory.release_reservation` for each picklist LINE row that still carries an active `reservation_id`. This is the backorder/cancel path described in the ticket acceptance criteria.
3. **`get_shipment(shipment_id)` and `list_shipments_for_order(order_id, *, limit, cursor)`** — thin read helpers consumed by the FAC-011 router (the same helpers defined in FAC-009 `packing.py`; FAC-010 re-exports them rather than duplicating).
4. **Idempotency** — `ship_shipment` is idempotent on replay: the single-writer `ConditionExpression="#status = :draft"` ensures at most one caller stamps the shipment. A second call that finds `status = "shipped"` returns the existing record without re-emitting the event.
5. **Audit** — `alerts.audit_event("shipping.shipped", ...)` emitted best-effort after the write; `alerts.audit_event("shipping.cancelled", ...)` for cancel.

Everything is **additive and flag-gated** behind `S.facility_fulfillment_enabled` (default `False`). With the flag off the entire module is dormant, and all existing shop/cart/orders/billing code is byte-for-byte unchanged.

## 3. Data Model

FAC-010 reads from `T.picklists` (to retrieve LINE rows for reservation release) and reads/writes `T.shipments` (to stamp carrier/tracking and advance status). It does not add any new tables or GSIs.

### 3.1 `shipments` table — updated `META` row

Already defined by FAC-002 (`docs/ofbiz/specs/FAC-002.md:273–318`) and first written by FAC-009. FAC-010 updates the following fields on the existing `META` row:

| Attribute | Written by FAC-010 | Notes |
|---|---|---|
| `status` | `"shipped"` | Was `"draft"` from FAC-009; FAC-010 is the only writer of `"shipped"` |
| `carrier` | e.g. `"ups"`, `"fedex"` | Validated against `CARRIER_TRACKING_URLS` keyset; lowercased |
| `tracking_number` | caller-supplied string | Non-empty, `max_length=200` |
| `service_level` | e.g. `"ground"`, `"overnight"` | Optional; omitted if not supplied |
| `notes` | optional free-text string | Omitted if not supplied |
| `shipped_at` | `now_ts()` | Was `0` from FAC-009; GSI sort key in `attr_types` |
| `shipped_by` | `user_sub` of actor | Actor identity |
| `updated_at` | `now_ts()` | Refresh on every write |

The `PKG#{n}` rows created by FAC-009 are never modified by FAC-010 — packages are immutable once packed.

### 3.2 `picklists` table — read only for cancel path

FAC-010's `cancel_shipment` reads picklist `LINE#{n}` rows to enumerate `reservation_id` values for release. It also reads the picklist `META` to verify the association. It does NOT write to `T.picklists` — the picklist remains in `"packed"` status (its terminal warehouse status). The cancel path advances only the `T.shipments` status, not the picklist status. If the ORD module needs to know the order was cancelled, the ORD transition (`packed → cancelled`) is triggered separately.

### 3.3 `attr_types` — no changes needed

FAC-002 already declared `attr_types={"created_at": "N", "shipped_at": "N"}` on the `shipments` table definition (`docs/ofbiz/specs/FAC-002.md:292`). FAC-010 writes `shipped_at` as an integer, which is compatible with that declaration.

### 3.4 Access patterns

| Query | Mechanism |
|---|---|
| Fetch shipment META + package rows | `T.shipments.query(KeyConditionExpression=Key("shipment_id").eq(sid))` — returns all rows in one call |
| Update shipment META (ship) | `T.shipments.update_item(Key={"shipment_id": sid, "sk": "META"}, ..., ConditionExpression="#status = :draft")` |

## 5. Detailed Behavior & Edge Cases

### 5.1 `ship_shipment` — step-by-step

1. **Flag gate**: `_require_enabled()`. Raises HTTP 404 when `S.facility_fulfillment_enabled` is `False`.

2. **Input validation**:
   - `tracking_number` must be non-empty.
   - `carrier` may be omitted; if omitted `detect_carrier(tracking_number)` is called. If detection returns `None` **and** the caller also omitted `carrier`, raise HTTP 422 `"carrier required when tracking number format is unrecognized"`.
   - If `carrier` is supplied (or auto-detected), normalise to lowercase and verify it is a key in `CARRIER_TRACKING_URLS` (`carrier_tracking.py:10`). Unknown carrier → HTTP 422 `"unknown carrier '{carrier}'; known: ups, fedex, usps, dhl"`.

3. **Load shipment META**: `T.shipments.get_item(Key={"shipment_id": sid, "sk": "META"})`. Raises HTTP 404 if absent.

4. **Status pre-check** (pre-flight, not the authoritative guard):
   - If `meta["status"] == "shipped"`: the shipment was already shipped. Load and return the existing record — fast idempotent-replay path.
   - If `meta["status"] == "cancelled"`: raise HTTP 409 `"Shipment is cancelled; cannot ship a cancelled shipment"`.
   - If `meta["status"] != "draft"`: raise HTTP 409 `f"Shipment is in status '{meta['status']}'; expected 'draft'"`.

5. **Build `extra_set`** for the `update_item`:
   ```python
   extra_set = {
       "carrier": carrier,
       "tracking_number": tracking_number,
       "shipped_at": now_ts(),
       "shipped_by": shipped_by,
       "updated_at": now_ts(),
   }
   if service_level:
       extra_set["service_level"] = service_level
   if notes:
       extra_set["notes"] = notes
   ```

6. **Conditional update** via `_transition_shipment(shipment_id, "draft", "shipped", extra_set=extra_set)`:
   - On success (`old` is not `None`): proceed to step 7.
   - On `None` return (concurrent write): re-read the current META. If `status == "shipped"` — the concurrent caller won, return the current record (idempotent no-op). Otherwise raise HTTP 409 `"Concurrent modification; retry"`.

7. **Purchase-transaction tracking linkage** (best-effort; best-effort `try/except`):
   ```python
   if meta.get("order_id"):
       try:
           _link_tracking_to_order(
               order_id=meta["order_id"],
               carrier=carrier,
               tracking_number=tracking_number,
           )
       except Exception:
           pass
   ```
   `_link_tracking_to_order` resolves the buyer `user_sub` from `T.orders.get_item(Key={"order_id": order_id, "sk": "ORDER"})` and calls `purchase_history.update_shipping(user_sub, order_id, {"carrier": carrier, "tracking_number": tracking_number, "status": "shipped"})` (`purchase_history.py:398`). This call is guarded: if `T.orders` or the purchase-transaction lookup fails for any reason, the failure is swallowed — the shipment is already stamped and the primary DDB write succeeded.

8. **Order lifecycle hand-off** (best-effort, gated by `S.order_lifecycle_enabled`):
   ```python
   if bool(getattr(S, "order_lifecycle_enabled", False)) and meta.get("order_id"):
       try:
           from app.services.order_lifecycle import transition_order, OrderLifecycleStatus
           idempotency_key = f"ship:{shipment_id}"
           transition_order(
               meta["order_id"],
               OrderLifecycleStatus.SHIPPED,
               actor=shipped_by,
               reason=f"order.fulfillment.shipped shipment_id={shipment_id}",
               idempotency_key=idempotency_key,
           )
       except Exception:
           pass
   ```
   The `idempotency_key = f"ship:{shipment_id}"` is deterministic: replaying `ship_shipment` for the same shipment produces the same key. `transition_order` derives `event_id = sha256(order_id|packed|shipped|ship:{shipment_id})[:16]` (per `ORD-001.md:211`), so the HIST row is also idempotent on replay. The transition is best-effort — a `transition_order` failure (e.g., order already in `shipped` from a prior call) does not roll back the shipment stamp.

9. **Emit audit event** (best-effort):
   ```python
   _audit("shipping.shipped", shipped_by,
          shipment_id=shipment_id,
          order_id=meta.get("order_id"),
          picklist_id=meta.get("picklist_id"),
          carrier=carrier,
          tracking_number=tracking_number)
   ```

10. **Return** the updated shipment via `get_shipment(shipment_id)` with `tracking_url` injected by `_shipment_out`.

### 5.2 `cancel_shipment` — step-by-step

1. **Flag gate**: `_require_enabled()`.

2. **Load shipment META**: raises HTTP 404 if absent.

3. **Status pre-check**:
   - If `status == "cancelled"`: fast idempotent return of current record.
   - If `status == "shipped"`: raise HTTP 409 `"Cannot cancel a shipped shipment; use the returns flow"`.
   - If `status != "draft"`: raise HTTP 409 `f"Shipment is in status '{meta['status']}'; expected 'draft'"`.

4. **Conditional update** via `_transition_shipment(shipment_id, "draft", "cancelled", extra_set={"cancel_reason": reason or "", "cancelled_by": cancelled_by, "cancelled_at": now_ts(), "updated_at": now_ts()})`:
   - On `None` return: re-read and return current state as no-op.

5. **Release active reservations** (best-effort; gated by `S.inventory_reservations_enabled`):
   - Load picklist `META` from `T.picklists` via `meta["picklist_id"]`.
   - Query all `LINE#*` rows for that picklist.
   - For each line where `reservation_id` is non-empty and `line_status in {"open", "picked"}`:
     ```python
     try:
         inventory.release_reservation(
             reservation_id,
             reason="shipment_cancelled",
             user_sub=cancelled_by,
         )
     except Exception:
         pass
     ```
   The call mirrors the guarded best-effort pattern at `app/services/returns_rma.py:424–435` (an `inventory_reservations_enabled`-gated `try/except` loop; note that `returns_rma.py` calls `inv.adjust` for RMA restock, not `release_reservation` — the structural pattern is the same). A partial release (some reservations fail) is accepted — inventory is best-effort on cancel; any unreleased reservations will expire via the existing TTL poller (`app/services/inventory.py:538–562`, `expire_due_reservations`).

6. **Emit audit event**: `_audit("shipping.cancelled", cancelled_by, shipment_id=shipment_id, ...)`.

7. **Return** updated shipment.

### 5.3 Carrier validation and auto-detection

The `CARRIER_TRACKING_URLS` keyset at `app/services/carrier_tracking.py:10` is `{"ups", "fedex", "usps", "dhl"}`. FAC-010 validates the supplied or auto-detected `carrier` against this keyset. Future carriers are added by extending this dict — FAC-010 validation is forward-compatible because it reads the live keyset at runtime.

`detect_carrier` returns `None` for tracking numbers that match none of the four known patterns. When detection fails and the caller also omitted `carrier`, HTTP 422 is returned (not 404 — the input is invalid, not missing). When detection fails but the caller supplied an explicit `carrier` that passes keyset validation, the explicit carrier is used without auto-detection.

### 5.4 `_link_tracking_to_order` — purchase-transaction linkage

The FAC order model (`T.orders`, `commerce_order_service.py:85`) and the purchase-transaction model (`T.purchase_transactions`, `purchase_history.py`) are two separate DynamoDB tables. `T.orders.order_id` is the `sha256(correlation_id)[:32]` deterministic ID (`commerce_order_service.py:67`). The purchase-transaction `txn_id` may differ from `order_id` in legacy flows; however, for the OFBiz stack, the `order_id` on the picklist is the value that was written by `commerce_order_service.create_order`, so it matches the `orders` table PK. `_link_tracking_to_order` uses `T.orders.get_item(Key={"order_id": order_id, "sk": "ORDER"})` to fetch `user_id`/`user_sub`, then calls `purchase_history.update_shipping(user_sub, order_id, shipping_dict)`. If the ORD tables have not yet been migrated (pre-ORD-003, no `sk` sort key), this call silently returns `None`; the shipment row is already stamped and the best-effort fallthrough is acceptable.

### 5.5 Idempotency invariants

- **Same shipment, first `ship_shipment` call succeeds**: stamps carrier/tracking, transitions to `shipped`, triggers lifecycle event exactly once. Subsequent calls reach the fast-path at step 4 and return the existing record.
- **Same shipment, concurrent second `ship_shipment` call** (both pass the step 4 pre-flight): only one wins the conditional update. The losing call reads the current record at step 6 and returns it as a no-op.
- **`cancel_shipment` on already-cancelled**: fast return at step 3.
- **`ship_shipment` after cancel**: rejected at step 4 with HTTP 409.
- **`cancel_shipment` after ship**: rejected at step 3 with HTTP 409 — use the returns flow.

### 5.6 Relationship to FAC-009 and ORD

FAC-009 (`pack_picklist`) creates `status = "draft"`. FAC-010 (`ship_shipment`) advances to `"shipped"`. The ORD module (`transition_order`) advances the order header from `"packed"` to `"shipped"`. The three state machines (shipment, order lifecycle, purchase-transaction shipping) are driven independently by FAC-010's best-effort calls, ensuring that a partial failure in any downstream system does not roll back the physical shipment record.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

`shipping_fulfillment.py` contains **no** `dev_mode` or `S.dev_mode` branch. All DynamoDB writes go to `T.shipments` and reads go to `T.picklists` in both dev (DynamoDB Local on port 8001, via the `_FloatSafeTable` wrapper defined at `app/core/tables.py:29`; the `_safe_table` factory wrapping each handle is at `app/core/tables.py:65–66`) <!-- VERIFIED: tables.py:29 class _FloatSafeTable; tables.py:65-66 def _safe_table --> and prod (real DynamoDB). Calls to `purchase_history.update_shipping` and `order_lifecycle.transition_order` are also code-path-identical; no mock/real fork. This mirrors `app/services/receiving.py` (FAC-007) and `app/services/packing.py` (FAC-009).

The `_audit` helper lazy-imports `app.services.alerts.audit_event`: in dev this logs to the console and writes to `T.alerts` (DynamoDB Local); in prod it writes to real DynamoDB. No divergence in the calling code.

### Idempotency

The primary idempotency fence is the single-writer conditional update on the shipment `META` row (`ConditionExpression="#status = :draft"`). At most one concurrent caller wins this transition. The fast-path pre-check (step 4 of §5.1, §5.2) short-circuits the vast majority of replays without a write, matching the pattern in `app/services/returns_rma.py:382–384` <!-- VERIFIED: returns_rma.py:382 if old is None: return get_return(return_id) -->.

The downstream order lifecycle call is additionally idempotent: `idempotency_key = f"ship:{shipment_id}"` is deterministic, and `transition_order` derives a fixed `event_id` from this key (`ORD-001.md:211`). Even if the network drops between the shipment stamp and the lifecycle call, a replay of `ship_shipment` will re-enter the fast path (shipment already `shipped`) and not re-call `transition_order`.

### Security

- `ship_shipment` and `cancel_shipment` are warehouse mutations; they MUST be called only from handlers protected by `require_admin_or_root_csrf` (FAC-011). The service functions themselves accept any caller-supplied `shipped_by` / `cancelled_by` string; the auth boundary is the router layer, consistent with all other OFBiz service functions.
- `shipped_by` and `cancelled_by` are the authenticated user's `user_sub` (extracted from `session.user_sub` by the router); they are stamped on the DDB row and the audit event for accountability.
- `tracking_number` is stored in DDB; it is carrier-opaque text and carries no PII. `carrier` is validated against a closed keyset; no injection risk.
- Read endpoints (`GET /shipments/{id}`, `GET /orders/{oid}/shipments`) use `require_ui_session` — any authenticated user can read shipments. If per-user isolation is required (e.g., buyers should only see their own shipments), the router must add an ownership check against `order_id → user_id`. This is out of scope for FAC-010 but noted as a follow-up for FAC-011.

## 10. Open Questions / Assumptions

1. **`shipping_fulfillment.py` vs extending `packing.py`**: The ticket text says "create `app/services/shipping_fulfillment.py` (or extend `packing.py`)". This spec chooses a separate `shipping_fulfillment.py` (one file per lifecycle step, mirroring the separation of `receiving.py`, `picking.py`, `packing.py`). If the implementor places `ship_shipment` in `packing.py`, the logic is identical; only the module boundary changes.

2. **Shipment `status = "packed"` vs `"draft"`**: FAC-002 (`docs/ofbiz/specs/FAC-002.md:304`) lists the shipment lifecycle as `draft / packed / shipped / delivered / cancelled`. FAC-009 writes `status = "draft"` on creation. The distinction between `"draft"` and `"packed"` is not yet enforced — FAC-009 writes `"draft"` and the FAC-002 spec mentions `"packed"` as a second step before shipping. This spec **assumes FAC-009 writes `"draft"` and FAC-010 transitions from `"draft"` to `"shipped"`, skipping a `"packed"` intermediate**. If a `"packed"` intermediate is introduced (e.g., by a separate `confirm_pack` step), `_transition_shipment` in FAC-010 would guard on `"packed"` instead of `"draft"`. The implementor must verify the actual status written by FAC-009 before shipping FAC-010.

3. **`_link_tracking_to_order` and `T.orders` SK migration**: This spec calls `T.orders.get_item(Key={"order_id": order_id, "sk": "ORDER"})` (the ORD-003 schema where `sk` is a table sort key). If ORD-003 has not yet shipped when FAC-010 is deployed, this call returns nothing (the existing `orders` rows have no `sk`). The best-effort `try/except` around `_link_tracking_to_order` makes this safe — tracking linkage simply doesn't happen until ORD-003 migrates the orders table. This is an explicit assumption about the deployment ordering.

4. **Purchase-transaction vs order-ID mismatch**: `purchase_history.update_shipping(user_sub, txn_id, ...)` (`purchase_history.py:398`) expects a `txn_id` that matches the `sk` in `T.purchase_transactions`. The `order_id` from `T.orders` may differ from the `txn_id` in `T.purchase_transactions` for orders created via `file_bundle_checkout.py` or legacy paths. This spec assumes that for OFBiz-stack orders (created via `commerce_order_service.create_order`), `order_id == txn_id`. If this assumption is wrong, `_link_tracking_to_order` will silently fail (best-effort), but the shipment row is still stamped correctly.

5. **`cancel_shipment` and picklist status**: This spec does NOT advance the picklist from `"packed"` to `"cancelled"` when a shipment is cancelled. The picklist remains `"packed"`. If the business requires the picklist to also be cancelled (to allow re-picking for a replacement shipment), a call to a `cancel_picklist`-equivalent function (or a new `cancel_packed_picklist` that guards on `"packed"` status) would be needed. This is left as a follow-up.

6. **Multiple shipments per order**: An order may have multiple picklists (partial fulfilment), each producing a separate shipment. `cancel_shipment` only cancels the one shipment and releases the reservations for that shipment's picklist. It does not affect other open or draft shipments for the same order.

7. **`ShipShipmentIn` vs extending `ShipmentIn`**: FAC-003's `ShipmentIn` includes `packages` and `picklist_id` (for a combined pack+ship flow). This spec introduces a narrower `ShipShipmentIn` (carrier + tracking only) for the separate ship step. Both models should exist in `app/models.py`; the router chooses the appropriate one per endpoint.
