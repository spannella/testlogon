# FXA-002 — Settings, feature flags & table handles

## 1. Summary & Goal

FXA-002 is the pure scaffolding ticket for the Fixed Assets module. It wires three new feature flags and three new table-name settings into the `Settings` dataclass (`app/core/settings.py`) and exposes three corresponding `_FloatSafeTable` handles in the `Tables` singleton (`app/core/tables.py`). No service logic, no router, no DynamoDB schema change — those belong to FXA-003 and later tickets. The goal is that all downstream FXA tickets can import `from app.core.settings import S` and `from app.core.tables import T` and find `S.fixed_assets_enabled`, `S.fixed_assets_depreciation_posting_enabled`, `S.fixed_assets_depreciation_poll_interval`, and `T.fixed_assets`, `T.fixed_asset_schedule`, `T.maintenance_orders` already present, without any import-time error.

Every flag defaults to disabled (`False` / off). With all flags off the entire existing shop, cart, orders, billing, inventory, and GL paths remain byte-for-byte unchanged.

## 3. Data Model

FXA-002 itself introduces no DynamoDB tables. It only adds the *table-name settings* that FXA-003 will use to create the tables at stack-init time and that `T.<handle>` will resolve to at import time. The three table names are:

| Settings field | Env var | Default table name |
|---|---|---|
| `fixed_assets_table_name` | `FIXED_ASSETS_TABLE_NAME` | `fixed_assets` |
| `fixed_asset_schedule_table_name` | `FIXED_ASSET_SCHEDULE_TABLE_NAME` | `fixed_asset_schedule` |
| `maintenance_orders_table_name` | `MAINTENANCE_ORDERS_TABLE_NAME` | `maintenance_orders` |

All three defaults are snake-case matching the `T.<handle>` attribute name — the same convention used by `inventory`, `reservations`, and `returns`.

The physical table schemas (PK, SK, GSIs, `attr_types`) are specified in FXA-003 and are not reproduced here to avoid drift. The design notes from the FXA-001 spike are:

- `fixed_assets`: PK `pk=ASSET#{asset_id}`, SK `sk=META`; GSI_OWNER (`owner_sub` / `acquired_at` N); GSI_STATUS (`status` / `acquired_at` N).
- `fixed_asset_schedule`: PK `pk=ASSET#{asset_id}`, SK `sk=PERIOD#{period:07d}`; GSI_DUE (`schedule_status` / `period_end_ts` N).
- `maintenance_orders`: PK `pk=ASSET#{asset_id}`, SK `sk=WO#{work_order_id}`; GSI_WO_STATUS (`wo_status` / `created_at` N); GSI_WO_ASSIGNEE (`assignee_sub` / `created_at` N).

All numeric GSI sort keys will require `attr_types` entries in `scripts/local-ddb-init.py` (FXA-003) — this is the numeric-GSI gotcha documented in CLAUDE.md.

## 5. Detailed Behavior & Edge Cases

**Import-time resolution.** `T = Tables(...)` is evaluated at module import time. `_safe_table(S.fixed_assets_table_name)` calls `ddb.Table("fixed_assets")`, which constructs a lazy boto3 `Table` resource — it does NOT make any network call. The table does not need to exist in DynamoDB for the import to succeed. This means the handle is safe to import even before FXA-003 has created the table, as long as no DynamoDB operation (put_item, query, etc.) is actually invoked.

**Flag-off behavior.** When `FIXED_ASSETS_ENABLED` is not set or set to any value other than `"true"` (case-insensitive), `S.fixed_assets_enabled` is `False`. Downstream services check this flag before any DDB access; when the flag is off those code paths are never reached and `T.fixed_assets` is never called. The handle is wired (so `from app.core.tables import T; T.fixed_assets` succeeds) but never exercised.

**`FIXED_ASSETS_DEPRECIATION_POSTING_ENABLED` independence.** This flag being `True` has no effect unless `FIXED_ASSETS_ENABLED` is also `True`. The depreciation poster (FXA-007) will gate on `S.fixed_assets_enabled and S.fixed_assets_depreciation_posting_enabled`. Having the secondary flag off by default prevents accidental GL journal writes during initial rollout of the asset register.

**`FIXED_ASSETS_DEPRECIATION_POLL_INTERVAL` type.** The `int(os.environ.get(..., "86400"))` expression is evaluated once at settings construction. If `FIXED_ASSETS_DEPRECIATION_POLL_INTERVAL` is set to a non-integer string the `int()` call will raise `ValueError` at startup — this is intentional and matches the existing pattern (e.g. `compute_billing_poll_interval` at line 2386). Operations should validate their env before deploying.

**Frozen dataclass mutation in tests.** `Settings` is `@dataclass(frozen=True)` (`app/core/settings.py:6`). Tests must flip flags using `object.__setattr__(S, "fixed_assets_enabled", True)` and restore the original value in a `finally` block, following the pattern in `tests/test_compute_billing_timer_gap0228.py` lines 117–123 (`tests/test_compute_billing_timer_gap0228.py:117-123`). Never use `S.fixed_assets_enabled = True` (raises `FrozenInstanceError`).

**Tables frozen dataclass.** `Tables` is also `@dataclass(frozen=True)` (`app/core/tables.py:68`). Tests that need to inject a moto-backed table for `T.fixed_assets` must use `object.__setattr__(T, "fixed_assets", moto_table)` and restore in `finally`, as shown throughout the test suite (e.g. `tests/test_gap_0226_0227_k8s_host_inventory.py` line 110 — `tests/test_gap_0226_0227_k8s_host_inventory.py:110`).

**Env-var override.** All three table-name settings accept overrides through env vars, allowing staging/prod environments to use isolated table names (e.g. `FIXED_ASSETS_TABLE_NAME=prod_fixed_assets`) without code changes.

## 6. Feature Flag & Config

| Setting | Env var | Default | Purpose |
|---|---|---|---|
| `fixed_assets_enabled` | `FIXED_ASSETS_ENABLED` | `False` | Master gate; every FXA route and service checks this |
| `fixed_assets_depreciation_posting_enabled` | `FIXED_ASSETS_DEPRECIATION_POSTING_ENABLED` | `False` | Secondary gate for the background GL-posting loop |
| `fixed_assets_depreciation_poll_interval` | `FIXED_ASSETS_DEPRECIATION_POLL_INTERVAL` | `86400` (24 h) | Sleep interval in seconds between depreciation poster runs |
| `fixed_assets_table_name` | `FIXED_ASSETS_TABLE_NAME` | `"fixed_assets"` | DDB table for asset records |
| `fixed_asset_schedule_table_name` | `FIXED_ASSET_SCHEDULE_TABLE_NAME` | `"fixed_asset_schedule"` | DDB table for depreciation schedule rows |
| `maintenance_orders_table_name` | `MAINTENANCE_ORDERS_TABLE_NAME` | `"maintenance_orders"` | DDB table for work orders |

Both boolean flags use the `os.environ.get(..., "false").lower() == "true"` idiom (explicit allowlist, matching the `inventory_reservations_enabled` and `returns_rma_enabled` pattern at `app/core/settings.py:839` and `app/core/settings.py:846`) rather than the `not in ("0", "false", "False")` deny-based idiom used by some newer flags (e.g. `compute_billing_enabled` at `app/core/settings.py:2385`). This makes `"false"`, `"False"`, `"0"`, and absence all map to `False`, and only the string `"true"` (any capitalisation) maps to `True`.

The poll-interval default of 86400 seconds (24 hours) is appropriate for a batch depreciation posting job: depreciation periods are monthly, so a daily check provides a comfortable margin for any delayed GL posts without excessive DDB reads.

No changes to `.env.local.example` are required for dev operation since all flags default to off. Teams enabling the feature in dev will export `FIXED_ASSETS_ENABLED=true` in their local env.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/Prod parity.** The settings read from environment variables identically in dev and prod — no `S.dev_mode` branch. Table-name overrides (e.g. prefixing with an environment name) apply equally to both environments. The `_safe_table(name)` wrapper and the underlying `ddb.Table(name)` boto3 resource honour `DDB_ENDPOINT_URL` for local DynamoDB and the real AWS endpoint in prod — same code path (SECOPS-007 parity).

**Idempotency.** This ticket contains no writes. Re-importing `app.core.settings` or `app.core.tables` after an env-var change has no effect because the module is cached by Python's import machinery; a process restart is required to pick up new env-var values. This is identical to every other setting in the codebase.

**Security.** No secrets are introduced. Table names are not sensitive. Both feature flags default to off, which is the safer default: enabling them requires a deliberate operator action.

## 8. Backward Compatibility & Migration

**Zero breaking changes.** Adding fields to a `@dataclass(frozen=True)` with default values is fully backward-compatible: existing code that does not reference the new fields continues to work. The `Tables` dataclass addition is also backward-compatible for the same reason — existing attributes are unchanged.

**No DynamoDB changes.** FXA-002 does not create or alter any DynamoDB table. `T.fixed_assets`, `T.fixed_asset_schedule`, and `T.maintenance_orders` will resolve to lazy boto3 `Table` objects pointing at tables that do not yet exist. Any attempt to call DDB operations on them (before FXA-003 creates the tables) will raise `ResourceNotFoundException` from boto3 — but since the handles are never called while `S.fixed_assets_enabled` is False, this is not a runtime concern.

**No `just restart` required.** This ticket only changes Python source files. No new DynamoDB tables are added and no schema migration is needed. A plain backend restart picks up the changes. `just restart` is required only when FXA-003 lands (to recreate the DDB tables).

**Rollback.** Removing or reverting the six new Settings fields and the three Tables fields is safe at any time before FXA-003 lands. After FXA-003 the tables exist but are still not referenced by any active code path while the flag is off.

## 10. Open Questions / Assumptions

1. **Assumption: placement in `settings.py`.** The new block is placed immediately before `S = Settings()` (currently line 2772), after the Legal Exports section (lines 2765–2770). If another FXA-parallel ticket lands first and shifts the line numbers, the placement description still applies (after Legal Exports, before the singleton instantiation).

2. **Assumption: `"false".lower() == "true"` idiom.** The ticket description says "following the existing flag pattern (e.g. `inventory_reservations_enabled` at `app/core/settings.py:839`)". That line uses `.lower() == "true"`. Some newer flags (e.g. `compute_billing_enabled` at `app/core/settings.py:2385`) use `not in ("0", "false", "False")` — a deny-based idiom that makes `"1"` and `"yes"` truthy. The spec standardises on the explicit allow-list form from the cited reference (line 839) for consistency with the OFBiz module family. If the team prefers the deny-based form, the env-var parsing string changes but the field names and defaults do not.

3. **Assumption: `fixed_asset_schedule` (singular).** The ticket uses `fixed_asset_schedule_table_name` (singular "schedule"), which matches the table's role as a per-asset schedule container. "fixed_assets_schedule" would also be defensible. The singular form is used here to match the FXA-003 description.

4. **Assumption: `maintenance_orders` vs. `asset_work_orders`.** The ticket and FXA-003/FXA-008 all use `maintenance_orders`. The `T.maintenance_orders` handle name is fixed accordingly. Future tickets should not introduce a parallel `work_orders` handle for the same table.

5. **Assumption: no `.env.local.example` update.** The flags all default to off and the table-name defaults are sensible for dev. If the team decides to add `FIXED_ASSETS_ENABLED=false` as a commented-out entry in `.env.local.example` (for discoverability), that is a one-line additive change with no logic impact.

6. **Open question: should `fixed_assets_depreciation_posting_enabled` be a sub-field of the master gate or fully independent?** Currently the downstream poster (FXA-007) will check `S.fixed_assets_enabled and S.fixed_assets_depreciation_posting_enabled`. If the master gate is off, the secondary flag is irrelevant. An alternative is a single `fixed_assets_depreciation_posting_enabled` flag that implies the master is on. The spec keeps them separate (matching the `compute_billing_enabled` / `AUDIT_EXPORT_WORKER_ENABLED` pattern of compound gates) to allow the asset register to be turned on for testing without immediately activating the background GL writer.
