## 1. Summary & Goal

HRM-013 delivers the complete verification layer for the HR module introduced by HRM-001 through HRM-012. It does not add new runtime behavior — it exercises every service path introduced by the preceding HR tickets through two complementary test surfaces:

1. **`tests/test_hr.py`** — a hermetic, offline pytest suite that runs against in-memory moto DynamoDB tables. No AWS credentials, no dev stack, no running backend required. Covers employee-party provisioning, position CRUD and status transitions, employment lifecycle (hire/terminate), payroll compute/draft/approve, ledger-posting idempotency, GL journal derivation, and the flag-off regression proof.

2. **`frontend/e2e/hr.spec.ts`** — a Playwright E2E spec using the standard 1-worker Chromium config, seeded with admin/root sessions via `e2e_admin_session_setup.py`, covering the full happy-path HR workflow through the live stack plus the flag-off unreachable-route assertion.

The goal is to prove that: (a) all HR service paths work correctly in isolation; (b) the `/ui/hr/*` router is truly inert when the flags are off; and (c) the billing, ledger, and GL surfaces are byte-for-byte unchanged by HR activity when `S.hr_enabled` is `False`.

## 3. Data Model

The `hr` table is a single-table store (PK=`pk`, SK=`sk`). All three HR entity types live in it. The `party` table is owned by the Party/CRM module (PTY-002) and is only read/written by `app/services/party.py` — the HR test suite patches `T.party` when exercising `ensure_employee_party`.

### 3.1 HR table GSIs (from HRM-002)

| GSI name | Partition key | Sort key | Numeric attr_types |
|---|---|---|---|
| `GSI1` | `GSI1PK` (S) | `GSI1SK` (S) | none (string-typed status/entity keys) |
| `GSI2` | `GSI2PK` (S) | `GSI2SK` (S) | none |
| `GSI_CREATED` | `entity_type` (S) | `created_at` (N) | `{"created_at": "N"}` |

The `created_at` GSI sort key **must** be declared `"N"` in `attr_types` (the CLAUDE.md "DynamoDB numeric GSI sort keys" gotcha — omitting it stores integers as strings and causes `ValidationException` on `>` / `<` comparisons).

### 3.2 Key access patterns

| Entity | PK | SK | GSI1PK | GSI1SK | GSI2PK | GSI2SK |
|---|---|---|---|---|---|---|
| Position | `POSITION#{position_id}` | `META` | `POSITION#{status}` | `POSITION#{position_id}` | — | — |
| Employment | `EMPLOYMENT#{employment_id}` | `META` | `EMPLOYMENT#{status}` | `EMPLOYMENT#{employment_id}` | `PARTY#{party_id}` | `EMPLOYMENT#{employment_id}` |
| PayrollRun | `PAYROLL#{payroll_run_id}` | `META` | `PAYROLL#{status}` | `PAYROLL#{payroll_run_id}` | — | — |
| PayrollLine | `PAYROLL#{payroll_run_id}` | `LINE#{employment_id}` | — | — | — | — |

`entity_type` on each item is the string prefix (e.g. `"POSITION"`, `"EMPLOYMENT"`, `"PAYROLL"`) for `GSI_CREATED` newest-first listing.

### 3.3 Party table (read/written by hr.py, owned by PTY-002)

The `party` table (default name `"party"`) uses `PK`/`SK` with:
- `PARTY#{party_id}` / `META` — party record
- `PARTY#{party_id}` / `ROLE#{role_type}` — role rows
- `REL#{from_party_id}` / `REL#{to_party_id}#{rel_type}#{rel_id}` — relationship rows

The `hr` test suite only needs `T.party` to be backed by an in-memory moto table when testing `ensure_employee_party` — its schema is the simple `PK`/`SK` composite pattern.

## 5. Detailed Behavior & Edge Cases

### 5.1 Employee party (HRM-004 coverage)

- `ensure_employee_party(user_sub="alice")` must call `party.ensure_person_party("alice")` → obtain `party_id` → call `party.add_role(party_id, "EMPLOYEE")` → return `party_id`. The PERSON party record remains in `T.party`; no employee identity data is duplicated into `T.hr`.
- **Idempotency**: calling with the same `user_sub` twice must return the same `party_id` and write exactly one `EMPLOYEE` role row (second call is a no-op because `add_role` uses `attribute_not_exists(sk)` guard).
- **Correlation-id idempotency**: calling with the same `correlation_id` returns the existing `party_id` even across different `user_sub` values (the deterministic id is `sha256(correlation_id).hexdigest()[:32]`).
- Audit event `"hr.employee.onboarded"` must be emitted via `app.services.alerts.audit_event` at `app/services/alerts.py:644` (verified).

### 5.2 Position status transitions (HRM-005 coverage)

| From | To | Expected |
|---|---|---|
| `OPEN` | `FILLED` | success |
| `OPEN` | `CLOSED` | success |
| `FILLED` | `CLOSED` | success |
| `FILLED` | `OPEN` | `ValueError` / 409 |
| `CLOSED` | any | `ValueError` / 409 |

List by status uses `GSI1PK = "POSITION#{status}"` (no scan). Newest-first list uses `GSI_CREATED` with `entity_type = "POSITION"` and numeric `created_at` in descending sort.

### 5.3 Employment lifecycle (HRM-006 coverage)

- `create_employment(...)` writes the `EMPLOYMENT#{employment_id}` / `META` row, calls `party.create_relationship(from_party_id=party_id, to_party_id=org_party_id, relationship_type="EMPLOYMENT", ...)` (PTY-006), and calls `update_position_status(position_id, "FILLED")` (best-effort, never raises).
- `list_employments(party_id=...)` uses `GSI2PK = "PARTY#{party_id}"` — reverse-lookup, no scan.
- `list_employments(status="ACTIVE")` uses `GSI1PK = "EMPLOYMENT#ACTIVE"` — no scan.
- `terminate_employment(employment_id, end_date)` where `end_date < item["start_date"]` raises `ValueError("end_date must be >= start_date")`.
- Re-terminating an already-`TERMINATED` employment is a no-op (returns existing item unchanged).

### 5.4 Payroll compute math (HRM-007 coverage)

The proration test table (covered by dedicated unit tests in the pytest suite):

| `pay_period` | `pay_rate_cents` | period days | expected `gross_cents` |
|---|---|---|---|
| `MONTHLY` | 500_000 | any full month | 500_000 (rate as-is) |
| `BIWEEKLY` | 200_000 | 14 days | 200_000 (one biweek) |
| `BIWEEKLY` | 200_000 | 28 days | 400_000 (two biweeks) |
| `WEEKLY` | 100_000 | 7 days | 100_000 |
| `HOURLY` | 2_500 | 7 days (40h/week) | 100_000 (40 hours × 2500) |

The `approve_payroll_run` transition matrix:
- `DRAFT` → `APPROVED`: success.
- `APPROVED` → `APPROVED`: no-op (idempotent), returns current item.
- `POSTED` → `APPROVED`: `ValueError`.

### 5.5 Payroll posting idempotency (HRM-008 coverage)

- Per-line correlation id: `sha256(f"payroll:{payroll_run_id}:{employment_id}").hexdigest()[:32]`.
- Each `new_ledger_entry` call writes to `T.billing` (same table as Stripe/PayPal charges) with `pk = f"PAYROLL#{payroll_run_id}"`, `entry_type = "debit"`, `state = "settled"`, `reason = "payroll"`.
- Re-posting an already-`POSTED` run must write zero additional billing rows. Tests assert `new_ledger_entry` call count equals number of lines on first post, and zero on second post.
- Partial failure: if the billing write for line 2 raises `ClientError` after line 1 succeeds, the run stays `APPROVED`. On retry, only line 2 is re-attempted (line 1's `attribute_not_exists(sk)` guard prevents double-payment).

### 5.6 GL journal derivation (HRM-010 coverage)

- A `T.billing` item with `reason="payroll"` fed to `gl_posting.post_ledger_entry(item)` produces exactly one balanced journal entry: `Σdebits == Σcredits`, with one Dr line at account code `S.hr_payroll_expense_account_code` (default `"6000"`) and one Cr line at the Cash account.
- With `S.hr_payroll_gl_posting_enabled = False` (or `S.gl_double_entry_enabled = False`), the posting function returns without writing any journal row.
- Idempotent: posting the same ledger `entry_id` twice writes exactly one journal row (second call hits the `attribute_not_exists(source_entry_id)` guard on `T.gl_journal`).

### 5.7 Flag-off regression (cross-cutting)

With all three `S.hr_*` flags off:
- Every `GET`/`POST`/`PATCH` to `/ui/hr/*` returns HTTP 404.
- `T.hr` receives zero `put_item`/`update_item` calls (verified by mock assertion).
- `T.billing` receives zero `put_item` calls with `reason="payroll"` (verified by scanning the mock billing table after all service calls).
- `T.gl_journal` receives zero writes (verified by scanning the mock GL journal table).
- The existing billing router (`app/routers/billing.py`) and its ledger entries are untouched (no side effects from HR module import).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

All HR service code is DynamoDB-only with no `dev_mode` branch. `new_ledger_entry` (`app/services/billing_shared.py:224`) writes to the same `T.billing` table in both dev (DynamoDB Local) and prod (DynamoDB). The GL poster (`app/services/gl_posting.py`, OFB-014) uses the same `T.gl_journal` handle in both environments. No HR path introduces an `if S.dev_mode:` fork.

### 7.2 Deterministic-id idempotency

Every write path that accepts a `correlation_id` derives its primary id as:
```python
import hashlib, uuid
id_ = hashlib.sha256(correlation_id.encode()).hexdigest()[:32] if correlation_id else uuid.uuid4().hex
```
The first write uses `ConditionExpression="attribute_not_exists(pk)"` (or `attribute_not_exists(sk)` for SK-keyed rows). A second write with the same `correlation_id` hits the condition, raises `ConditionalCheckFailedException`, which the service swallows and converts to a get-and-return (the existing item is returned unchanged).

### 7.3 Payroll billing idempotency

Per-line correlation id for billing writes:
```python
corr = hashlib.sha256(f"payroll:{payroll_run_id}:{employment_id}".encode()).hexdigest()[:32]
sk, item = billing_shared.new_ledger_entry(
    key_name="pk", key_value=f"PAYROLL#{payroll_run_id}",
    entry_type="debit", amount_cents=line["gross_cents"],
    state="settled", reason="payroll",
    meta={"entry_id": corr},
    extra={"employment_id": employment_id, "party_id": party_id, "payroll_run_id": payroll_run_id},
)
# new_ledger_entry returns (sk, item) but does NOT write to DDB (verified: billing_shared.py:259)
T.billing.put_item(Item=item, ConditionExpression="attribute_not_exists(sk)")
```
The `ConditionExpression="attribute_not_exists(sk)"` guard on the caller's `put_item` (not inside `new_ledger_entry` itself) prevents any duplicate money-out entry. This satisfies the "never fork billing" constraint: payroll uses the same idempotency mechanism as Stripe charge replays.

### 7.4 Authorization

All HR endpoints require `ADMIN` or `ROOT` role (`require_admin_or_root_csrf` from `app/auth/policy.py:100`). A `USER`-role cookie receives HTTP 403. CSRF is enforced for all non-GET requests when the session cookie is present (matching the pattern in `app/auth/policy.py:71–97`).

### 7.5 No money-out without approval

`post_payroll_run` rejects runs that are not `APPROVED`. A `DRAFT` run returns HTTP 409. A `POSTED` run returns HTTP 409 (already posted — caller should not retry posting; idempotent re-post at the service layer is a no-op but the router surface is explicit).

## 8. Backward Compatibility & Migration

### 8.1 Zero impact on existing surfaces when flags are off

The `hr_router` is included unconditionally in `create_app()` (so route URLs are registered), but every handler checks `S.hr_enabled` at the top and returns 404 before touching any service code. With the flags off:

- `T.billing` is never written by HR code.
- `T.party` is never read by HR code.
- `T.hr` is never accessed at all (the table handle is created by `_safe_table`, which does nothing if the table does not exist — this is the existing pattern for all tables on a clean host before `just restart`).

### 8.2 No schema changes to existing tables

- `T.billing` receives new rows with `pk = "PAYROLL#{id}"` and `reason="payroll"`. Existing rows with `pk = "USER#{user_sub}"` are unaffected. The `GSI_LEDGER_DATE` index (`scripts/local-ddb-init.py:64-77` — verified, partition key `ledger_date` (S), sort key `sk`) picks up the new rows automatically because `new_ledger_entry` already stamps `ledger_date` (`billing_shared.py:253`).
- `T.party` gains `ROLE#EMPLOYEE` rows for employee parties. Existing party rows are unaffected.
- `T.gl_journal` gains rows with `reason="payroll"`. The existing `source_entry_id` idempotency index is shared — no schema change.

### 8.3 DynamoDB table creation

The `hr` table is created by `scripts/local-ddb-init.py` (HRM-002) with `attr_types={"created_at": "N"}` for `GSI_CREATED`. Running `just restart` recreates it. In production, an `UpdateTable` + backfill is not needed because the table is net-new (no migration from an existing `hr` table).

```python
            ("hr", self.hr_table),
            ("party", self.party_table),
            ("billing", self.billing_table),
            ("gl_journal", self.gl_journal_table),
        ):
            original = getattr(T, name)
            object.__setattr__(T, name, handle)
            self.addCleanup(object.__setattr__, T, name, original)

        from app.core.settings import S
        self.S = S
        for flag, default_val in (
            ("hr_enabled", False),
            ("hr_payroll_enabled", False),
            ("hr_payroll_gl_posting_enabled", False),
        ):
            object.__setattr__(S, flag, default_val)
            self.addCleanup(object.__setattr__, S, flag, default_val)
```

`_make_hr_table(ddb)` creates the table with:
- `KeySchema: [{HASH: "pk"}, {RANGE: "sk"}]`
- `GlobalSecondaryIndexes: [GSI1 (GSI1PK/GSI1SK), GSI2 (GSI2PK/GSI2SK), GSI_CREATED (entity_type/created_at)]`
- `AttributeDefinitions: pk(S), sk(S), GSI1PK(S), GSI1SK(S), GSI2PK(S), GSI2SK(S), entity_type(S), created_at(N)`

The `created_at` attribute type must be `"N"` — this is what the `attr_types={"created_at": "N"}` entry in `scripts/local-ddb-init.py` controls, and omitting it would cause `ValidationException` when querying `GSI_CREATED`.

#### 9.1.3 How to call route handlers directly (no TestClient)

Per CLAUDE.md ("the project's standard test-isolation pattern"), `TestClient` is broken in this environment. Route handler coroutines are called directly on a fresh event loop:

```python
import asyncio
from fastapi import HTTPException

async def _call(coro):
    return await coro

def _run(coro):
    return asyncio.new_event_loop().run_until_complete(coro)

# Example: test flag-off router guard
try:
    _run(hr_router_positions_handler(
        body=..., user=_fake_admin_user()
    ))
    self.fail("Expected HTTPException")
except HTTPException as exc:
    self.assertEqual(exc.status_code, 404)
```

The `_fake_admin_user()` helper returns a minimal `AuthenticatedUser` stub with `role=Role.ADMIN` — avoiding any real auth dependency.

## 10. Open Questions / Assumptions

1. **Flag-toggling in E2E**: Sections 78-81 require `HR_ENABLED=1` in the backend env. The spec assumes the E2E runner sets this via a `.env.local` override before starting the stack (`just restart HR_ENABLED=1 HR_PAYROLL_ENABLED=1`). If the backend supports a `POST /internal/set-flag` endpoint (as some other modules use for dev-mode toggling), that is the preferred mechanism. **Verify** whether a live-flag-toggle endpoint exists at `/internal/` before implementing.

2. **`T.gl_journal` handle**: The GL journal table handle (`T.gl_journal`) is added by OFB-002 and must exist in `app/core/tables.py` before HRM-013's tests can reference it. If OFB-002 is not merged, the GL journal tests must patch `gl_posting.T.gl_journal` directly rather than going through the shared `T`. The spec assumes OFB-002 is merged.

3. **`app/services/gl_posting.py` import path**: HRM-010 adds the payroll mapping entry to this file. If the import path in `hr_payroll.py` is `from app.services import gl_posting` (lazy, via `importlib`), the patch target changes. The spec assumes direct module-level import so `patch("app.services.gl_posting.post_ledger_entry")` is the correct patch target.

4. **`party.create_relationship` signature**: The spec assumes `create_relationship(from_party_id, to_party_id, relationship_type, *, correlation_id=None)` per PTY-006. If the signature differs (e.g. positional `org_party_id`), adjust `create_employment` call sites in the test.

5. **Payroll line count for 0-employment runs**: HRM-008 states zero-line runs transition to `POSTED` immediately. The spec covers this in `test_post_payroll_writes_ledger_entries_via_new_ledger_entry` with a guard for `line_count == 0`. **Confirm** that `create_payroll_run` with no `ACTIVE` employments produces a run with `line_count=0` (not an error).

6. **`billing` table PK/SK in tests**: The test `_make_billing_table(ddb)` must match the production schema (`pk`/`sk` with the `GSI_LEDGER_DATE` GSI). Mismatching the schema produces silent misses on GSI queries. The billing table definition in `scripts/local-ddb-init.py:64-77` is the reference.

7. **`just restart` precondition for E2E**: The CLAUDE.md "Test data accumulates" gotcha applies. E2E sections 78-81 seed positions, employments, and payroll runs that accumulate across runs. Consider adding `afterAll` cleanup blocks that delete the seeded HR DDB rows (similar to the `resetBobToUser()` DDB cleanup in `admin-roles.spec.ts:112`).

8. **HRM-012 frontend prerequisite**: Section 81 (HrPage UI) requires HRM-012 to be merged. If HRM-013 is merged before HRM-012, section 81 should be skipped (`test.skip`) and enabled in a follow-up PR.
