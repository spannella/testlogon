# MKT-012 — Frontend types & endpoint wrappers

## 1. Summary & Goal

MKT-012 adds the TypeScript layer that makes the marketing-campaigns API consumable by the React
frontend. It has two deliverables:

1. **TypeScript interfaces** in `frontend/src/api/types.ts` that mirror the MKT-003 Pydantic models
   (`MarketingCampaignOut`, `ContactListOut`, `ContactListMemberOut`, `PartySegmentOut`,
   `TrackingCodeOut`, `CampaignAttributionOut`, and the matching `*In`/request shapes).
2. **Endpoint wrapper module** at `frontend/src/api/endpoints/marketing.ts` that exposes typed
   `api.get`/`api.post`/`api.patch`/`api.del` calls covering every route defined by MKT-011.

When complete, `tsc --noEmit` (strict mode, `tsconfig.json:16`) passes clean, and the MKT-013 page
components can import from `marketing.ts` without any `any` casts.

This ticket is **purely additive**: no existing endpoint wrappers, types, or pages are modified.
With `MARKETING_CAMPAIGNS_ENABLED=0` (the default), the API calls will receive `404` from the
backend; the wrappers themselves are always importable and are just typed fetch helpers.

## 2. Context & Current State

### TypeScript type file

`frontend/src/api/types.ts` is 13,160 lines (`wc -l frontend/src/api/types.ts`). New marketing
interfaces will be appended as a new section at the end of the file, following the established
pattern of contiguous feature sections (e.g., `// ─── Promo Codes & Coupons (PROMO-001) ───` at line 4081, `// ─── Ad Accounts & Campaigns (ADS-001) ───` at line 5979). No existing interfaces are altered.

### Existing ads and promo types to mirror

The two closest precedents are:

- `Campaign` (`frontend/src/api/types.ts:5993–6006`) — the ads `CampaignOut` mirror. Uses plain
  `string` status (`status: string` at line 6003), `number` for all money/timestamp fields.
  Note: `Campaign` has no `start_date`/`end_date` fields; those are marketing-domain additions.
- `PromoCodeOut` (`frontend/src/api/types.ts:4083–4098`) — uses `number` for cents, booleans for
  flags, `string[]` for list fields. `PromoCodeStatsOut` (`4105–4116`) extends `PromoCodeOut` with
  an optional `stats` sub-object.

### Endpoint wrapper patterns

Two direct structural models:

- `frontend/src/api/endpoints/ads.ts` — imports `{ api }` from `"../client"`, imports types from
  `"../types"` using `import type { ... }`, groups endpoints by feature in sections with comments.
  Longer inline bodies (e.g., `URLSearchParams` construction) used for query-param endpoints.
- `frontend/src/api/endpoints/promoCodes.ts` — uses the `@/api/client` alias, imports named types
  via `import type { ... } from "@/api/types"`, one function per route, concise one-liner arrow
  functions for simple cases.

The marketing wrapper follows `promoCodes.ts` style: `@/api/client` alias, named `import type`
from `@/api/types`, and one function per MKT-011 route.

### Axios client (`frontend/src/api/client.ts`)

The `api` object (`client.ts:151`) is not an axios instance; it is a typed `fetch` wrapper that:

- Attaches `Authorization: Bearer <accessToken>` from `useAuthStore` (`client.ts:168–170`).
- Reads the `ui_csrf` cookie and injects `X-CSRF-Token` header on every request (`client.ts:179–181`),
  so **no caller needs to pass CSRF manually** — the client handles it globally.
- Exposes `api.get<T>(path, params?)`, `api.post<T>(path, body?)`, `api.patch<T>(path, body?)`,
  `api.put<T>(path, body?)`, `api.del<T>(path, params?)`, and `api.upload<T>(path, formData)`.
- Returns `Promise<T>` directly (not `AxiosResponse<T>`).

This means every wrapper in `marketing.ts` follows the same shape as `promoCodes.ts` lines 22–55:
`api.post<TypedResponse>("/ui/marketing/...", body)` — no extra headers, no manual CSRF.

### TypeScript strict mode

`frontend/tsconfig.json:16` sets `"strict": true`. Additionally `noUnusedLocals: true` and
`noUnusedParameters: true` are set (`tsconfig.json:17–18`). Every declared type must be used by at
least one exported function in `marketing.ts`, and every function parameter must be used in the
body. `tsc --noEmit` is the acceptance gate.

### No existing marketing types or wrappers

`grep -r "MarketingCampaign\|ContactList\|PartySegment\|TrackingCode\|CampaignAttribution"
frontend/src/api/` returns no output — confirmed the types and wrapper module do not exist yet.

## 3. Data Model

MKT-012 is a purely frontend ticket; it introduces no DynamoDB tables, no backend models, and no
settings changes. All DDB tables and backend models are owned by MKT-002 (tables/settings),
MKT-003 (Pydantic models), and MKT-011 (router).

The TypeScript interfaces in this section mirror the backend Pydantic `*Out` models defined in
`docs/ofbiz/specs/MKT-003.md:§4`. All money fields are `number` (cents, integer), all timestamps
are `number` (Unix seconds). The mapping follows the existing `Campaign` type at
`frontend/src/api/types.ts:5993–6006` (Python `int` → TypeScript `number`;
Python `Optional[str]` → TypeScript `string | null` or `string | undefined`).

The authoritative Pydantic shapes are in `docs/ofbiz/specs/MKT-003.md` (spec) and will live in
`app/models.py` once MKT-003 is implemented. This spec treats the MKT-003 spec as the source of
truth for field names and types.

**Design notes:**

- `status: string` (not a union literal) on `MarketingCampaignOut` follows the `Campaign` type at
  `frontend/src/api/types.ts:6003` — the server enforces the state machine; the frontend renders
  it without compile-time exhaustiveness.
- `SegmentAttribute` and `SegmentOperator` are TypeScript union string types (not `string`) because
  both sets are small, stable, and form the core of the segment-builder UI (MKT-013). Keeping them
  as union types lets the segment-builder form get exhaustiveness from the compiler.
- `SegmentPredicate.value` uses `string | number | string[] | number[]` rather than `unknown`/`any`
  to maintain strict-mode compatibility while accommodating both scalar and list operands for `in`/
  `not_in` operators.
- `MarketingCampaignListOut`, `ContactListListOut`, `PartySegmentListOut`, and `TrackingCodeListOut`
  wrap the `items` + `next_cursor` shape to match the server's paginated list responses (mirrors
  `PromoCodeListOut` at `frontend/src/api/types.ts:4100–4103`).
- `ContactListMembersOut` uses `members` + `cursor` + `count` to match the router spec in
  `docs/ofbiz/specs/MKT-011.md:§5.9`.

## 5. Detailed Behavior & Edge Cases

### 5.1 CSRF handling

No wrapper needs to set `x-csrf-token` manually. `client.ts:179–181` reads the `ui_csrf` cookie
and injects the header on every request, including `POST`/`PATCH`/`DELETE`. This is the same
pattern used by every other endpoint wrapper (`promoCodes.ts`, `ads.ts`, `billing.ts`, etc.).
Any E2E test calling the backend via `page.request` (which carries cookies) must still pass the
`x-csrf-token` header manually, as documented in `CLAUDE.md:§E2E tests`.

### 5.2 Idempotent campaign create (200 vs 201)

`createMarketingCampaign` always returns `Promise<MarketingCampaignOut>`. The router
(`docs/ofbiz/specs/MKT-011.md:§5.2`) returns HTTP 200 for a re-created (existing) campaign and
201 for a fresh create. The wrapper does not expose the HTTP status code to callers (the `api`
client resolves any `2xx` response to `T`). Callers detect idempotency via the returned
`campaign_id` matching a previously known id, not via status code. This is acceptable because
`createMarketingCampaign` in MKT-013 React Query mutation is `onSuccess: (data) => ...` — the
data shape is the same in both cases.

### 5.3 Flag-off behavior (404 from backend)

With `MARKETING_CAMPAIGNS_ENABLED=0`, all `POST`/`PATCH`/`DELETE` calls receive HTTP 404. The
`api` client in `client.ts:268–276` converts non-2xx responses to `ApiError`. React Query
mutations in MKT-013 handle this via `onError` and display a toast. No special handling is needed
in the wrappers themselves — the existing error path handles it uniformly.

GET endpoints (`listMarketingCampaigns`, `getMarketingCampaign`, etc.) have no flag gate — they
return existing data regardless of whether `MARKETING_CAMPAIGNS_ENABLED` is on or off, per
`docs/ofbiz/specs/MKT-011.md:§5.1` ("Read-only endpoints remain accessible regardless of flag state"). The
wrappers are unaware of flag state.

### 5.4 Pagination cursors

`listMarketingCampaigns`, `listContactLists`, `listContactListMembers`, `listPartySegments`, and
`listTrackingCodes` all accept an optional `cursor` query parameter. The cursor is an opaque
base64-encoded string produced by `app/core/cursor.py` on the backend. Callers pass it verbatim.
MKT-013 will use React Query's `useInfiniteQuery` with `getNextPageParam: (last) => last.next_cursor ?? undefined`.

### 5.5 `sendMarketingCampaign` returns 202

The backend returns HTTP 202 Accepted. The `api` client treats any `2xx` as success and resolves
to the JSON body. `CampaignSendOut` defines `queued: boolean` which will always be `true` in the
202 response. Callers in MKT-013 display "Campaign send queued" toast on success.

### 5.6 Public visit redirect (`/ui/marketing/t/{code}`)

This endpoint is not wrapped in `marketing.ts`. It is a browser-nav redirect, not a fetch call:
`window.location.href = "/ui/marketing/t/summer24"` or `<a href="/ui/marketing/t/summer24">`.
The Vite proxy forwards it to the backend which 302-redirects to the storefront. No TypeScript
wrapper is needed.

### 5.7 `SegmentPredicate.value` typing strictness

`value: string | number | string[] | number[]` is strictly typed. When MKT-013 builds the segment
predicate UI, it constructs predicates with values conforming to this union. For `in`/`not_in`
operators the builder always provides `string[]` or `number[]`. For comparison operators it
provides `number`. TypeScript union narrowing in the builder component handles the type correctly
without casts.

### 5.8 `noUnusedLocals` compliance

Every imported type must appear in at least one exported function signature. The import list in
`marketing.ts` is kept exactly as large as needed. If a type is declared in `types.ts` but not yet
used by any wrapper (e.g., `SegmentMemberOut` — used only by a future MKT-013 query), it is NOT
imported in `marketing.ts`; instead, MKT-013 imports it directly from `@/api/types`. The wrapper
module only imports types it actually consumes in function signatures.

**Types declared in `types.ts` but NOT imported in `marketing.ts` (only used by MKT-013 pages
directly):**

- `SegmentMemberOut` — returned by a pagination query in the MKT-013 snapshot-viewer component,
  not by any wrapper function.
- `MarketingCampaignUpdateIn` — MKT-013 forms `import type { MarketingCampaignUpdateIn }` directly
  when constructing the PATCH body; the wrapper accepts it as a parameter so it IS imported.

Wait — `MarketingCampaignUpdateIn` is a parameter of `updateMarketingCampaign`, so it is imported.
`SegmentMemberOut` is not a parameter or return type of any wrapper (no `/segments/{id}/members`
endpoint is listed in MKT-011); it belongs to a potential future endpoint. It is declared in
`types.ts` for completeness but is not imported in `marketing.ts`.

## 6. Feature Flag & Config

MKT-012 is a frontend-only ticket. The TypeScript interfaces and wrapper functions are always
available regardless of the `MARKETING_CAMPAIGNS_ENABLED` backend flag.

The frontend flag visibility (hiding the Marketing section from the sidebar) is implemented by
MKT-013, not MKT-012. MKT-013 reads a `marketing_campaigns_enabled` client-side flag (from the
`/ui/config` or equivalent feature-flag endpoint already used by other flagged features) and
conditionally renders the nav item and route.

MKT-012 itself has no flag-gated code paths. Importing from `marketing.ts` when the module is
disabled is harmless — the functions are never called because the MKT-013 page does not render.

**No new environment variables, settings keys, or feature-flag reads are introduced by this
ticket.**

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

TypeScript code and the `fetch`-based `api` client have no concept of dev vs prod at the module
level. The Vite proxy in `frontend/vite.config.ts` forwards all `/ui/*` and `/internal/*` paths to
`http://localhost:8000` in dev; in prod the same paths go to the real backend. The wrappers are
identical in both environments — no `import.meta.env.VITE_*` switches are used.

### Idempotency

The wrappers themselves are pure functions: calling `createMarketingCampaign(body)` twice with the
same body produces two identical `fetch` calls. The idempotency guarantee (returning the existing
campaign rather than an error on duplicate create) is entirely server-side (MKT-004 deterministic
id + `ConditionExpression="attribute_not_exists(pk)"`). The wrapper does not need to implement
dedup logic.

### Security

- **No secrets in wrappers**: the wrappers contain only path strings and type assertions. No
  tokens, API keys, or credentials appear in `marketing.ts`.
- **CSRF**: the `api` client attaches `X-CSRF-Token` from the `ui_csrf` cookie automatically
  (`client.ts:179–181`). Wrappers do not need to read cookies or set headers.
- **Path parameter injection**: all path parameters (`campaignId`, `listId`, `segmentId`,
  `codeSlug`, `partyId`, `codeId`) are TypeScript `string`. No URL-encoding is applied by the
  wrappers; callers are responsible for passing valid id strings (UUIDs or slug-constrained
  values). Since `TrackingCodeCreateIn.code_slug` is validated server-side with
  `^[A-Za-z0-9_-]{3,50}$` (`docs/ofbiz/specs/MKT-003.md:§4`), the slug is already URL-safe.
- **No `any` casts**: strict mode (`tsconfig.json:16`) combined with `noUnusedLocals` and
  `noUnusedParameters` prevents accidental `any` widening. All wrapper return types are
  explicitly parameterized (`api.post<MarketingCampaignOut>(...)`).

"""
Offline cross-check: TS interface field names in marketing.ts must match
Pydantic model field names from MKT-003 (app/models.py).

Strategy: parse frontend/src/api/types.ts to extract field names from the
MarketingCampaignOut, ContactListOut, PartySegmentOut, TrackingCodeOut, and

import re, pathlib, pytest

TS_TYPES_FILE = pathlib.Path("frontend/src/api/types.ts")

def _extract_interface_fields(interface_name: str) -> set[str]:
    """Return the set of field names declared in 'interface <name> { ... }'."""
    src = TS_TYPES_FILE.read_text()
    pattern = rf"interface {re.escape(interface_name)}\s*\{{([^}}]+)\}}"
    m = re.search(pattern, src, re.DOTALL)
    if not m:
        return set()
    block = m.group(1)
    # field lines look like: "  campaign_id: string;"
    return {
        line.split(":")[0].strip().rstrip("?")
        for line in block.splitlines()
        if ":" in line and "//" not in line.lstrip()
    }

## 10. Open Questions / Assumptions

1. **Assumption — `SegmentMemberOut` is not yet returned by any MKT-011 route**: The MKT-011
   router spec (`docs/ofbiz/specs/MKT-011.md:§4.6`) does not define a `GET /segments/{id}/members`
   endpoint (only `evaluate` and `snapshot`). `SegmentMemberOut` is declared in `types.ts` as a
   forward-reference for the likely future endpoint, but it is NOT imported into `marketing.ts`
   (would trigger `noUnusedLocals`). If MKT-011 adds `/segments/{id}/members` before MKT-012 ships,
   add `getSegmentMembers(segmentId, snapTs)` to `marketing.ts` and import `SegmentMemberOut`.

2. **Assumption — `redirect_url` field on `TrackingCodeCreateIn`**: The MKT-003 spec defines
   `TrackingCodeCreateIn` with only `code_slug` and `campaign_id`. `redirect_url` is included in
   this spec's `TrackingCodeCreateIn` because the MKT-011 router spec (`§4.8`) references
   `tracking_item.get("redirect_url")` for the 302 target. If MKT-010 stores `redirect_url` as
   part of create, the field must appear in both the backend model and the TS interface. If
   `redirect_url` is not in the final MKT-003 `TrackingCodeCreateIn`, remove it from the TS type.

3. **Assumption — `TrackingCodeOut.status` field**: The MKT-003 spec does not include `status` on
   `TrackingCodeOut` (only `code_slug`, `campaign_id`, `owner_id`, `visit_count`, `order_count`,
   `created_at`). It is added here because the MKT-011 redirect handler checks
   `status != "active"` (`§4.8`) — implying the code can be inactive. If the final Pydantic model
   omits `status`, remove it from `TrackingCodeOut` and from any MKT-013 status-filter logic.

4. **Assumption — `AttachAdCampaignIn` requires `ad_account_id`**: The ads service API
   `get_campaign(account_id, campaign_id)` (`app/services/ad_campaigns.py:35`) requires both
   `account_id` and `campaign_id`. `compute_attribution` (MKT-005) must resolve the ads campaign's
   spend — so the attach payload must carry `ad_account_id`. If MKT-005 resolves the account via a
   `ByCampaignId` GSI (as the router does at `app/routers/ads.py:72`), `ad_account_id` is
   unnecessary in the payload and can be removed from `AttachAdCampaignIn`.

5. **Assumption — no `PUT` methods**: All mutations in the MKT-011 router use `POST` (create/
   action) or `PATCH` (partial update), matching the `api.post` / `api.patch` client methods. No
   `PUT` (full replace) endpoints are defined. If MKT-011 defines any `PUT` endpoint, add the
   corresponding wrapper using `api.put<T>(path, body)`.

6. **Assumption — `ContactListListOut` and `MarketingCampaignListOut` wrapper naming**: The
   function `listMarketingCampaigns` returns `MarketingCampaignListOut` (not a raw
   `MarketingCampaignOut[]`). MKT-013 will destructure `data.items` for the list. This matches
   `PromoCodeListOut` at `frontend/src/api/types.ts:4100–4103` (which has `items` + `next_cursor`)
   and is consistent with `useInfiniteQuery` pagination patterns used elsewhere (e.g.,
   `listPromoCodes` returning `PromoCodeListOut`).

7. **Open — `CampaignReviewIn` admin-only visibility**: `reviewMarketingCampaign` and
   `listPendingMarketingCampaigns` call `/ui/admin/marketing/*` which requires `require_admin_or_root`
   on the backend. If the current user is not admin/root, the backend returns 403. MKT-013 should
   guard the admin review panel with a role check from `useAuthStore` before calling these wrappers.
   MKT-012 does not implement this guard — it just provides the wrappers. Confirm with MKT-013 that
   the role check is added there.
