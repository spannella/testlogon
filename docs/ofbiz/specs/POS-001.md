# POS-001 — POS channel mapping spike & reuse contract

## 1. Summary & Goal

This spike establishes the architectural boundary between the new POS channel and
the existing commerce stack. Its deliverable is not running code but a precise
reuse contract: an enumeration of every POS concept, whether it is NEW or REUSED,
and the exact file:line it delegates to. No new commerce engine is introduced.
Every sale, every stock movement, and every money record resolves through the
existing services unchanged.

The spike unblocks POS-002 (Pydantic models), POS-003 (DDB tables + settings),
and the rest of Milestone 1, which collectively must deliver a flag-off state in
which zero POS code is reachable and zero existing bytes are modified.

## 3. Data Model

### 3.1 POS is a single new DynamoDB table

All new POS rows share one table (`pos`, default name). The table uses generic
`pos_pk` / `pos_sk` attribute names so that heterogeneous row types coexist
under a single `TableDef` without conflicts. Existing tables (`shopping_cart`,
`billing`, `orders`) are never extended with POS-specific attributes.

#### 3.1.1 Row taxonomy

| Row type | `pos_pk` | `pos_sk` | Purpose |
|---|---|---|---|
| Register config | `REGISTER#{register_id}` | `META` | Static terminal config (label, location, currency) |
| Register session | `SESSION#{session_id}` | `META` | Open/closed till with cash float |
| Tender record | `SESSION#{session_id}` | `TENDER#{txn_id}` | Immutable tender line (cash/card/wallet) |
| POS transaction | `TXN#{txn_id}` | `META` | Links cart + order + tenders; authoritative totals |

#### 3.1.2 GSIs (all on `T.pos`)

| GSI name | Partition key | Sort key | Type | Purpose |
|---|---|---|---|---|
| `GSI_REGISTER_OPEN` | `register_id` (S) | `opened_at` (N) | sparse | Find open session per register |
| `GSI_SESSION_TXN` | `session_id` (S) | `created_at` (N) | on TXN rows | List transactions in a session |
| `GSI_CASHIER` | `cashier_sub` (S) | `opened_at` (N) | on SESSION rows | Sessions per cashier |

All three GSIs have numeric sort keys, so **`attr_types` must declare them `"N"`**
(see CLAUDE.md DynamoDB gotcha and `scripts/local-ddb-init.py` :34 docstring).

#### 3.1.3 TableDef entry (to be added to `scripts/local-ddb-init.py`)

```python
TableDef(
    _resolve_table_name(S.pos_table_name, "pos"),
    "pos_pk",
    "pos_sk",
    gsi=[
        {
            "index_name": "GSI_REGISTER_OPEN",
            "partition_key": "register_id",
            "sort_key": "opened_at",
        },
        {
            "index_name": "GSI_SESSION_TXN",
            "partition_key": "session_id",
            "sort_key": "created_at",
        },
        {
            "index_name": "GSI_CASHIER",
            "partition_key": "cashier_sub",
            "sort_key": "opened_at",
        },
    ],
    attr_types={"opened_at": "N", "created_at": "N"},
),
```

Place this entry **after** the `returns` table entry at `scripts/local-ddb-init.py`
:2483–:2492 (the last table def in `_table_defs()`, before the closing `]` at :2493),
following the `_resolve_table_name(S.<name>, "<default>")` pattern used at :2484.
(Note: the `shopping_cart` block is at :102–:107; the `returns` block is at :2483–:2492.)

#### 3.1.4 Reused tables (unchanged)

| Table handle | Usage in POS |
|---|---|
| `T.shopping_cart` | POS service calls `start_cart` / `add_item` / `purchase_cart` |
| `T.orders` / `T.order_items` | Written by `CommerceOrderService` as today |
| `T.billing` | Written by `new_ledger_entry` / `settle_or_reverse_ledger` as today |
| `T.catalog` | Stock decrement path inside `purchase_cart` :498–:538 (unchanged) |
| `T.inventory` / `T.reservations` | Used if `S.inventory_reservations_enabled` is on (orthogonal flag) |

### 3.2 Attribute reference for key row types

**Register row** (`REGISTER#{id}` / `META`):
`register_id`, `label`, `location_id`, `default_currency` (default `"USD"`),
`created_at` (N), `created_by`.

**Session row** (`SESSION#{id}` / `META`):
`session_id`, `register_id`, `cashier_sub`, `status` (`open|closed`),
`opening_float_cents` (N), `closing_float_cents` (N), `expected_cash_cents` (N),
`counted_cash_cents` (N), `over_short_cents` (N), `opened_at` (N, GSI sort key),
`closed_at` (N, optional).

**Tender row** (`SESSION#{session_id}` / `TENDER#{txn_id}#{tender_seq}`):
`tender_id`, `txn_id`, `kind` (`cash|card|wallet`), `amount_cents` (N),
`change_due_cents` (N), `payment_method_id` (optional, for card/wallet),
`card_ref` (optional), `created_at` (N).

**Transaction row** (`TXN#{txn_id}` / `META`):
`txn_id`, `session_id`, `cart_id`, `order_id`, `status` (`tendered|voided|refunded`),
`cashier_sub`, `subtotal_cents` (N), `discount_cents` (N), `tax_cents` (N),
`total_cents` (N), `receipt_id`, `idempotency_key`, `created_at` (N, GSI sort key),
`ledger_sk` (billing table back-ref for `settle_or_reverse_ledger`).
Also carries sparse projection attributes: `register_id` and `session_id` for
`GSI_SESSION_TXN`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Reuse contract — the golden rule

POS **never** writes directly to `T.orders`, `T.billing`, `T.catalog`, or
`T.inventory`. All such writes flow exclusively through the four cited services:

1. `shoppingcart.purchase_cart` (:474) — owns cart status transition, stock
   decrement (:498–:538), and calls `new_ledger_entry` internally for wallet
   transactions.
2. `CommerceOrderService.create_order_from_line_items` (:132) — owns the `orders`
   and `order_items` writes and the `commerce_order_created` audit event (:106).
3. `billing_shared.new_ledger_entry` (:224) — constructs the canonical ledger item
   and returns `(sk, item)`. The caller (`pos_transaction.tender_transaction`) is
   responsible for writing it: `ddb_put(T.billing, led_item)` (see
   `app/routers/billing.py:1136` for the established pattern). POS cash sales pass
   `reason="pos_cash_sale"` and `extra={"provider": "pos_cash"}` so
   `platform_financial_dashboard._provider_for` (:110–:114) returns `"pos_cash"`
   instead of `"unknown"`.
4. `billing_shared.settle_or_reverse_ledger` (:262) / `billing.refund_payment`
   (:1287) — all money-out goes through these.

### 5.2 Cash tender ledger attribution

`new_ledger_entry` is called in `tender_transaction` with:
```python
new_ledger_entry(
    key_name="pk",
    key_value=f"USER#{cashier_sub}",
    entry_type="sale",
    amount_cents=total_cents,
    state="settled",
    reason="pos_cash_sale",
    meta={"txn_id": txn_id, "session_id": session_id, "register_id": register_id},
    extra={"provider": "pos_cash"},
)
```
The `ledger_sk` returned is stored on the `TXN#` row as `ledger_sk` so a void or
refund can call `settle_or_reverse_ledger` with `new_state="reversed"`.

### 5.3 Idempotency

`tender_transaction` is idempotent on `idempotency_key`. The key is stored on the
`TXN#` row; a second call with the same key returns the stored `PosTransactionOut`
without re-running purchase or ledger. The canonical key format is
`sha256(f"{session_id}:{idempotency_key}")[:32]` — consistent with the
`_cart_purchase_idempotency_key` pattern at `shoppingcart.py` :194.

`open_session` is guarded by a DynamoDB conditional put: the `SESSION#` row is
only written if no item with `status="open"` exists for `register_id` in
`GSI_REGISTER_OPEN`. A concurrent second open raises `ConditionalCheckFailedException`
→ HTTP 409. The condition is `attribute_not_exists(pos_pk)` combined with a
prior GSI query for `register_id` + `status=open`. (Atomic enforcement detail
is POS-004's responsibility; the spike establishes the pattern.)

### 5.4 Double-close prevention

`close_session` reads the session row and rejects calls where `status != "open"` →
HTTP 409 `"session already closed"`. The close is a conditional `update_item`
with `ConditionExpression="#status = :open"`.

### 5.5 Over/short calculation

```
expected_cash_cents = opening_float_cents
                    + Σ tender.amount_cents  where tender.kind == "cash"
                    − Σ tender.change_due_cents  where tender.kind == "cash"
                    − Σ cash refunds on this session's transactions
over_short_cents = counted_cash_cents − expected_cash_cents
```

All tender rows live under `SESSION#{session_id}` / `TENDER#*` so a query with
`KeyConditionExpression=pos_pk=SESSION#{id} AND pos_sk begins_with TENDER#`
collects the full set without filtering across rows.

### 5.6 POS flag-off guarantee

When `S.pos_enabled` is `False`:
- Every POS handler calls `_require_pos_enabled()` which raises HTTP 404
  immediately. This matches the `_require_enabled()` pattern in
  `app/routers/inventory.py` (gated by `INVENTORY_RESERVATIONS_ENABLED`) and
  `app/routers/returns_rma.py` (gated by `RETURNS_RMA_ENABLED`). The router
  **is** mounted unconditionally in `app/main.py` (same as those routers at
  `app/main.py:877-878`); conditional `include_router` is not the pattern used.
- `T.pos` handle is constructed at module import time (DDB lazy connection) but
  no code path queries it when the flag is off.
- All existing endpoints remain byte-for-byte identical.

### 5.7 Source system for POS orders

The `source_system` for all POS-originated orders is `"shopping_cart"` because
the POS flow is literally: create cart → add items → purchase cart →
`purchase_cart` returns `cart_id` + `order_id`. This satisfies the allowlist
validation at `commerce_order_service.py` :58 with zero changes. The POS context
is traced via `metadata={"pos_txn_id": txn_id, "pos_session_id": session_id}`.

### 5.8 Card tender

For `kind="card"`, the tender's `payment_method_id` references a row in `T.billing`
(a stored Stripe card). The tender flow calls the existing `charge_once` / wallet
debit path, not a new payment path. The `card_ref` field stores the Stripe
`PaymentIntent.id` for reconciliation. The ledger entry uses
`extra={"provider": "stripe"}` (not `"pos_cash"`).

### 5.9 Wallet tender

For `kind="wallet"`, the tender deducts from the user's in-platform wallet balance
via `billing_shared.apply_balance_delta` (`app/services/billing_shared.py:83`).
Ledger `extra={"provider": "wallet"}`.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity**: All POS writes go to DDB local in dev and real DDB in prod via
the same `T.pos` handle (just as `T.orders`, `T.billing` do). There is no
`dev_mode` branch or mock path in POS logic — the same code runs in both
environments. Billing writes (`new_ledger_entry`, `settle_or_reverse_ledger`) reuse
the existing billing table in both environments.

**Idempotency**: Every state-mutating operation carries an `idempotency_key`. The
`tender_transaction` path uses `sha256(f"{session_id}:{idempotency_key}")[:32]`
stored on the `TXN#` row; a duplicate call reads and returns the stored outcome.
Cart purchase already has `_cart_purchase_idempotency_key` at `shoppingcart.py` :194;
POS relies on this existing guard.

**Security**: All POS endpoints require `Depends(require_ui_session)` (cookie or
Bearer). Register/config creation and report access require
`Depends(require_admin_session)`. No endpoint is public. CSRF is enforced by the
existing `require_ui_session` middleware for cookie-auth callers
(`app/auth/deps.py`). Cash float figures are integer cents — no floating-point
arithmetic in any financial path.

**PII**: `cashier_sub` and `session_id` are stored on `TXN#` rows but no
customer-identifying data beyond `user_sub` (already standard in billing rows).

## 8. Backward Compatibility & Migration

**Flag-off = zero diff**: With `POS_ENABLED=false` (the default), no POS router is
registered and no existing endpoint, service, or table is changed. Existing
`shopping_cart`, `billing`, `orders`, and `catalog` tables are not altered.

**New table, no schema change**: The `pos` DynamoDB table is new. `just restart`
recreates it. There is no migration of existing data. In a production deploy, the
table must be created before the flag is turned on (`CreateTable` call or
infrastructure-as-code); until then the flag remains off and the module is inert.

**`source_system` extension**: If future tickets require `source_system="pos"` in
orders for cleaner query segmentation, that is a backward-compatible additive
change to the allowlist at `commerce_order_service.py` :58 (add `"pos"` to the
set). The current spike uses `"shopping_cart"` to avoid touching that file.

## 10. Open Questions / Assumptions

1. **`source_system="shopping_cart"` for POS orders**: Assumed acceptable for
   Milestone 1. If the dashboard team requires per-channel order segmentation,
   POS-002 / POS-003 must also add `"pos"` to the `source_system` allowlist in
   `commerce_order_service.py` :58. This is a one-line additive change.

2. **Tax calculation**: `pos_default_tax_rate_bps` is a single global rate.
   Real deployments may need per-location or per-item tax rates. Deferred; the
   `tax_cents` field on `PosTransactionOut` is additive and zero by default.

3. **Receipt generation**: `receipt_id` on the transaction row references either
   a future POS receipt service or reuses the existing `app/services/receipts.py`
   (pure-Python PDF). Assumed the receipts service is reused; confirmed in POS-009.

4. **Inventory reservations interplay**: When `S.inventory_reservations_enabled`
   is `True` (it defaults `False` at `settings.py` :839), `purchase_cart` already
   handles reservation release. POS inherits this behavior at no extra cost.
   No new inventory logic is needed at the POS layer.

5. **Multi-tender split**: A single transaction may have cash + card tenders whose
   `sum(amount_cents) - sum(change_due_cents)` must equal `total_cents`. The
   validation helper `tenders_sum_check` (POS-002) enforces this. The ledger
   writes one entry per tender kind (`pos_cash_sale` / Stripe / wallet) — not one
   combined entry — to preserve provider attribution in the dashboard.

6. **Register vs. user_sub**: Registers are not per-user; they are per-location.
   The `register_id` GSI key identifies the physical terminal. The `cashier_sub`
   on a session identifies who opened the till. This is consistent with the
   `host_inventory` pattern (`T.host_inventory`) where hosts have a `user_sub` owner
   but can be shared.

7. **POS-specific `source_system` in `T.orders`**: Deferred. Current decision is
   `"shopping_cart"` to avoid touching the allowlist. Future decision logged here
   as open item.
