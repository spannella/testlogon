# PUR-016 — Route + navigation entries

**Type:** Chore | **Priority:** P2 | **Estimate:** 1 day
**Milestone:** 5 — Frontend Admin UI
**Depends on:** PUR-014 (Suppliers admin page), PUR-015 (Purchase-orders admin page)

---

## 1. Summary & Goal

PUR-016 is the routing glue for the two purchasing admin pages delivered by
PUR-014 and PUR-015. It makes those pages reachable in the browser and visible
in the navigation chrome without touching any other feature module.

Concretely, the ticket delivers three mechanical changes:

1. **Two lazy-loaded `<Route>` declarations** in `frontend/src/App.tsx` —
   `admin/suppliers` → `SuppliersAdmin` and `admin/purchase-orders` →
   `PurchaseOrdersAdmin` — mirroring the existing inventory-admin route at
   `frontend/src/App.tsx:481`.
2. **One new `NavItem`** in the `Sidebar` admin nav group
   (`frontend/src/components/layout/Sidebar.tsx`) labelled "Purchasing" with a
   link to `admin/suppliers`, shown only to admin/root users and only when the
   `VITE_PURCHASING_SCM_ENABLED` flag is on.
3. **One new entry** in the `MobileNav` more-sheet
   (`frontend/src/components/layout/MobileNav.tsx`) following the same
   conditional pattern as the moderation-board entries at `:143-146`.

There are no backend changes and no new DynamoDB tables in this ticket. All
flag/role enforcement relies on work already done by PUR-002 (backend settings
flag), PUR-014 (inline flag + role guard inside `SuppliersAdmin`), and PUR-015
(inline guard inside `PurchaseOrdersAdmin`).

## 2. Context & Current State

### 2.1 Existing inventory-admin route pattern (the direct model)

`frontend/src/App.tsx:45` already lazy-imports `InventoryAdmin`:
```ts
const InventoryAdmin = lazy(() => import("@/pages/shop/admin/InventoryAdmin"));
```
and at `frontend/src/App.tsx:481` registers it unconditionally inside the
`ProtectedRoute`/`AppShell` layout outlet:
```tsx
<Route path="admin/inventory" element={<InventoryAdmin />} />
```
The route is **not** wrapped in a `{showFlag && ...}` conditional in `App.tsx`.
Flag enforcement lives inside the component itself
(`InventoryAdmin.tsx:146-156`): when the flag is off the component renders an
`EmptyState` immediately and issues no API calls. This is the same pattern
PUR-014 spec (`docs/ofbiz/specs/PUR-014.md:317-329`) requires for
`SuppliersAdmin` and that PUR-015 must apply to `PurchaseOrdersAdmin`.

For contrast, `frontend/src/App.tsx:396-401` shows an alternative pattern where
the route itself is conditionally rendered:
```tsx
{showBroadcastNavigation && <Route path="broadcast" element={<BroadcastPage />} />}
```
That pattern is used when the feature is entirely unknown to non-flag users
(hitting the URL would 404). For admin tooling — where a direct URL like
`/admin/suppliers` should show an access-denied empty-state rather than a 404 —
the unconditional-route + inline-guard pattern is preferred, exactly as
`admin/inventory` does.

## 5. Detailed Behavior & Edge Cases

### 5.1 Route declarations in `App.tsx`

Add two lazy imports immediately after the `InventoryAdmin` import at
`frontend/src/App.tsx:45`:

```ts
const SuppliersAdmin = lazy(() => import("@/pages/shop/admin/SuppliersAdmin"));
const PurchaseOrdersAdmin = lazy(() => import("@/pages/shop/admin/PurchaseOrdersAdmin"));
```

Add two `<Route>` elements immediately after `<Route path="admin/inventory" ...>`
at `frontend/src/App.tsx:481`:

```tsx
<Route path="admin/inventory" element={<InventoryAdmin />} />
<Route path="admin/suppliers" element={<SuppliersAdmin />} />
<Route path="admin/purchase-orders" element={<PurchaseOrdersAdmin />} />
```

Both new routes sit inside the existing
`<Route element={<ProtectedRoute><AppShell /></ProtectedRoute>}>` layout outlet
at `App.tsx:316`, so authentication (redirect to `/login` for unauthenticated
users) is inherited from `ProtectedRoute` (`frontend/src/components/ProtectedRoute.tsx:8-17`).
The additional role and flag check is performed inside each page component.

**Why unconditional routes (not `{showFlag && ...}`)?** A conditional route
produces a React Router 404 when the flag is off. An unconditional route with an
inline empty-state is preferred for admin tools so that:
- An admin who navigates to `/admin/suppliers` with the flag off sees an
  actionable "feature not enabled" message, not a cryptic 404.
- The route continues to exist in the router tree even when hidden from the nav,
  so deep-linking from bookmarks works after the flag is turned on without a page
  reload.

### 5.4 Flag-off behaviour

When `VITE_PURCHASING_SCM_ENABLED` is `false` (the default):

- `showPurchasingAdmin` evaluates to `false`.
- The "Purchasing" entry is filtered out of `items` in both `Sidebar` and
  `MobileNav` — it is never rendered.
- The routes `admin/suppliers` and `admin/purchase-orders` are still registered
  in the React Router tree (unconditional), so a direct URL visit renders the
  page's own `EmptyState` ("Purchasing is not enabled"), not a 404.
- No API requests are issued (the page components check the flag before calling
  `useQuery`).

### 5.5 Non-admin user behaviour

When an authenticated non-admin user navigates to `/admin/suppliers` or
`/admin/purchase-orders` directly:

- `ProtectedRoute` passes (user is authenticated).
- The page component evaluates `canAccessGeneralAdminControls(accessToken)` →
  `false`.
- An `EmptyState` with "Access denied — requires admin or root" is rendered
  immediately; no API requests are issued.
- The nav entry is hidden (`showPurchasingAdmin` is false when
  `canAccessGeneralAdminControls` is false).
- The backend would also return 403 on any API call that leaked through (defence
  in depth).

### 5.6 Route conflict avoidance

The path `admin/suppliers` is a new, unique literal segment — no existing route
collides with it. The path `admin/purchase-orders` is similarly unique.
FastAPI-style declaration-order concerns do not apply to React Router v6, which
uses deterministic matching; however, literal segments always rank above dynamic
`/:param` segments, so there is no conflict with any existing `admin/:someId`
route even if one were added later.

### 5.7 Code-splitting guarantee

Both new lazy imports:
```ts
const SuppliersAdmin = lazy(() => import("@/pages/shop/admin/SuppliersAdmin"));
const PurchaseOrdersAdmin = lazy(() => import("@/pages/shop/admin/PurchaseOrdersAdmin"));
```
produce separate Rollup chunks. The `<Suspense fallback={<PageSpinner />}>` at
`App.tsx:298` already wraps all `<Routes>`, so the loading state is automatic.
No changes to the `Suspense` boundary are required.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No environment-specific branching

PUR-016 contains zero `if (process.env.NODE_ENV === "development")` or
`if (import.meta.env.DEV)` branches. The only branch is the Vite build-time
constant `VITE_PURCHASING_SCM_ENABLED`. This constant is evaluated at build time
and tree-shaken — the same binary is deployed to dev and prod; only the env-file
differs. This satisfies the SECOPS-007 dev/prod parity requirement.

### 7.2 Route registration does not widen the attack surface

Registering a route unconditionally in `App.tsx` does not expose a new API
surface. Route guards exist at two independent layers:

1. **Frontend — in-component guard**: both page components check
   `isPurchasingScmEnabled()` and `canAccessGeneralAdminControls(accessToken)`
   before issuing any API calls.
2. **Backend — `require_admin_or_root_csrf`**: all purchasing endpoints in
   `app/routers/purchasing.py` require role ≥ ADMIN. A non-admin user who
   navigates to `/admin/suppliers` directly will see the frontend empty-state
   and, if they somehow bypass it, the backend will return 403.

The defence-in-depth principle means neither layer is the single point of
failure.

### 7.3 Idempotency

PUR-016 makes no network calls and performs no state mutations. The route
registration is idempotent — registering the same path twice would be a React
Router duplicate-route warning but not a functional problem. There is no
idempotency concern specific to this chore.

### 7.4 CSRF

PUR-016 does not introduce any form submissions or API mutations. CSRF
enforcement is handled by the page components (via the `api` client from
`frontend/src/api/client.ts:179-181` — confirmed: CSRF cookie attached at
`:179-181`) and the backend policy middleware.
Navigation links do not carry CSRF tokens and none are needed here.
