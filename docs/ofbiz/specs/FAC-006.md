# FAC-006 — Stock transfers between locations

## 1. Summary & Goal

FAC-006 delivers `app/services/transfers.py`, the stock-transfer service for the OFBiz Facility application. It implements a four-state lifecycle (`requested` → `in_transit` → `completed` / `cancelled`) that physically moves stock between two facility locations by issuing a paired `inventory.adjust` call — decrement the source, increment the destination — exactly once under a conditional idempotency guard.

Concrete deliverables:

1. **`app/services/transfers.py`** — `create_transfer`, `get_transfer`, `list_transfers`, `advance_to_in_transit`, `complete_transfer`, `cancel_transfer`, `list_transfers_for_location`.
2. **`app/routers/fulfillment.py`** (or extension of it) — transfer endpoints under `/ui/fulfillment/transfers`, role-gated per the inventory router split (`require_admin_or_root_csrf` for mutations, `require_ui_session` for reads).
3. **Registration in `app/main.py`** after the `facilities_router` include.
4. **`tests/test_ofb_transfers.py`** — offline hermetic pytest coverage for the core lifecycle, idempotency, overdraw 409, and cancel.

The existing shop, cart, orders, billing, inventory, reservations, returns, and facilities paths are **byte-for-byte unchanged** when `FACILITY_FULFILLMENT_ENABLED` is off. The `T.transfers` table and `S.transfers_table_name` setting are already wired by FAC-002; this ticket adds only the service+router.

## 2. Context & Current State

### Existing inventory adjust primitives

`app/services/inventory.py:209–300` implements `adjust(sku, delta, reason, *, location_id, user_sub)`:

- **Negative guard** (`app/services/inventory.py:255–260`): `new_available = new_on_hand - reserved`; raises `HTTPException(status_code=409, ...)` if `new_available < 0`. A transfer that would overdraw below reserved stock is rejected here — the 409 surfaces to the caller before any stock is moved.
- **Single-writer optimistic update** (`app/services/inventory.py:264–286`): uses a `ConditionExpression="on_hand = :exp_oh AND reserved = :exp_res"` conditional `update_item`. If the row changed under us, the call retries once against fresh state (`app/services/inventory.py:283–285`).
- **Create-on-adjust** (`app/services/inventory.py:225–251`): if the inventory row for `(sku, location_id)` does not yet exist at the destination, a conditional `put_item(ConditionExpression="attribute_not_exists(sku)")` creates it. A concurrent first-write race is handled by falling through to the increment path on `ConditionalCheckFailedException` (`app/services/inventory.py:244–247`). This means `complete_transfer` can introduce a SKU at a new destination location without pre-seeding inventory.
- **Audit** (`app/services/inventory.py:289–298`): `_audit("inventory.adjust", ...)` emits best-effort `audit_event` after each successful adjust. `_audit` is defined at `app/services/inventory.py:92–98`.

## 5. Detailed Behavior & Edge Cases

### 5.1 `create_transfer` — idempotency

```
transfer_id = sha256(idempotency_key.encode())[:32]  if idempotency_key else uuid4().hex
```

The header is written with `ConditionExpression="attribute_not_exists(transfer_id)"`. A second call with the same `idempotency_key` gets `ConditionalCheckFailedException` → the function fetches and returns the existing record unchanged. The SHA-256-derived deterministic ID pattern mirrors `app/services/commerce_order_service.py:67` (which computes `sha256(corr.encode())[:32]` for `order_id`); `facilities.py:create_facility` is a planned FAC-004 deliverable and does not yet exist. The `attribute_not_exists` conditional-put guard mirrors `app/services/inventory.py:242` (create-on-adjust path).

Line items are written in a loop after the header put. Because each line row uses a deterministic SK (`ITEM#1`, `ITEM#2`, …) on the same partition, a repeated `put_item` on a line is idempotent (last-write-wins for items, acceptable since header creation is guarded).

### 5.2 `complete_transfer` — atomic exactly-once sequence

This is the most complex operation. The exact sequence is:

1. **Load** the header + lines via `_load_transfer(transfer_id)`. If header is missing → 404.
2. **Check validity**: `current_status` must be `in_transit`. If `completed` → return current state immediately (idempotent replay). If any other status → 409.
3. **Flip header to `completed`** with a conditional update:
   ```python
   _transition_transfer(transfer_id, "in_transit", "completed",
       actor_sub=actor_sub,
       extra_set={"completed_at": now_ts()})
   ```
   If `_transition_transfer` returns `None`, the row was already `completed` or was concurrently flipped — return the current state (no-op replay). This is the idempotency guard that ensures the dual inventory adjust runs exactly once.
4. **For each line** (in order, using the line items from the initial load):
   ```python
   from app.services import inventory as inv
   inv.adjust(sku, -quantity, reason="transfer_out",
              location_id=from_location_id, user_sub=actor_sub)
   inv.adjust(sku, +quantity, reason="transfer_in",
              location_id=to_location_id,  user_sub=actor_sub)
   ```
   - `transfer_out` adjust raises `HTTPException(409)` if `new_available < 0` (source overdraw; `app/services/inventory.py:256–260`).
   - `transfer_in` adjust uses the create-on-adjust path (`app/services/inventory.py:225–251`) for a first-time SKU at the destination — no pre-seeding required.
5. **Update each line's** `status` to `"moved"` and `picked_quantity` to `quantity` (best-effort `update_item` per line; does not affect the idempotency guarantee since the header flip is already terminal).
6. **Emit audit** `"transfer.completed"` with `transfer_id`, `from_location_id`, `to_location_id`, `line_count`.
7. **Return** the refreshed `TransferOut`.

**Why the header flip comes before the adjusts (not after):** If the process crashes after adjust step 4a (source decremented) but before 4b (destination incremented), stock would be lost with no way to detect it on replay. By flipping the header first and using the initial `lines` snapshot for adjusts, a replay of `complete_transfer` sees `status == "completed"` at step 2 and short-circuits — the caller knows it was already done. The dual adjust is therefore a best-effort side-effect that runs on the first successful completion, not a re-runnable compensating transaction. This matches the `_close_reservation` → `update_item` ordering in `returns_rma.py` where the reservation is closed before the on-hand decrement.

**Partial failure in multi-SKU transfers:** If a line's `transfer_out` raises 409 (overdraw), the header has already been flipped to `completed`. The caller receives a 409, but the transfer record is in an inconsistent `completed` state with some lines not yet adjusted. This is a known limitation; resolution requires either a compensating `cancelled_partial` status or operator intervention. For P0, log the error clearly and surface a 500 with a structured body that includes `transfer_id`, the failed `sku`, and `adjusted_skus` (the ones that succeeded). The operator can then manually adjust. FAC-007 (receiving) introduces the same risk; it is documented as an open question (§10).

**Ordering within the loop:** Process lines in `line_no` order (ascending) for determinism. This ensures the same partial-failure boundary on every retry attempt.

### 5.3 `cancel_transfer` — no inventory movement

Cancellation is valid from `requested` or `in_transit`. In both cases no inventory was adjusted (adjusts only happen in `complete_transfer`), so cancellation is a pure status flip with an optional `reason` stored on the header. No compensation needed.

### 5.4 `advance_to_in_transit` — simple status flip

`requested` → `in_transit`. No inventory change. Intended to model physical handoff of goods to a carrier or inter-warehouse truck. No validation of source stock is performed here — stock sufficiency is checked at completion time by `inventory.adjust`.

### 5.5 Source = destination guard

If `from_location_id == to_location_id`, reject with `HTTPException(422, "from and to location must differ")` at `create_transfer` time. A same-location transfer would result in net zero inventory change but wastes a transfer record.

### 5.6 Multi-SKU overdraw ordering

For a multi-SKU transfer, each SKU is adjusted sequentially. If SKU A succeeds but SKU B fails the overdraw guard, A's decrement has already been applied. The transfer header is already `completed`. This partial-failure state is surfaced as a 500 (not 409) to distinguish "you requested something impossible" from "a race condition degraded the transfer". See §10 for the open question on atomic compensation.

### 5.7 Concurrent complete attempts

Two concurrent `complete_transfer` calls for the same `transfer_id` both read `status=in_transit` and both attempt `_transition_transfer`. Only one wins the conditional update (`ConditionalCheckFailedException` on the loser). The loser sees `None` from `_transition_transfer`, fetches the current record, and returns it — the inventory adjusts run exactly once (from the winner's goroutine).

### 5.8 Transfer against a location with no inventory record

A `transfer_out` from a location where the SKU has no inventory row hits the `existing is None` branch at `inventory.py:225` → `delta < 0` → raises 409 immediately. The transfer is rejected cleanly before any state change.

All DDB calls go through `T.transfers` and `T.inventory` — in dev these are backed by DynamoDB Local (port 8001) or moto in-process; in prod they are real DynamoDB. The `inventory.adjust` calls are already parity-clean per `app/services/inventory.py:1–29` ("identical code in dev and prod"). No `if S.dev_mode` guard is introduced.

### Idempotency

Three layers:

1. **Create idempotency** — `attribute_not_exists(transfer_id)` conditional put. Second call with same `idempotency_key` computes the same SHA-256-derived `transfer_id` and gets `ConditionalCheckFailedException` → returns existing record.
2. **Completion idempotency** — `_transition_transfer` conditions on `status = "in_transit"`. A replay after completion returns `None` from the transition call → the dual `inventory.adjust` is skipped entirely. The guard runs exactly once.
3. **Inventory adjust idempotency** — `inventory.adjust` uses an optimistic conditional update (`on_hand = :exp_oh AND reserved = :exp_res`). Concurrent callers retry against fresh state; there is no external idempotency key for a bare adjust.

### Security

- **Role gate**: all mutation endpoints (`POST /transfers`, `/advance`, `/complete`, `/cancel`) require `require_admin_or_root_csrf` (defined at `app/auth/policy.py:100`, imported via `from app.auth.policy import require_admin_or_root_csrf`). This enforces both role (ADMIN or ROOT) and CSRF token validation (same as `app/routers/inventory.py:48`). Regular users (`require_ui_session`) can only read transfers.
- **Ownership check on reads**: `GET /transfers/{id}` returns the transfer regardless of `owner_sub` when called by an ADMIN/ROOT session. Regular users (ui_session) can read any transfer (transfers are warehouse-internal records, not customer-facing). If future requirements call for user-scoped transfers, a `owner_sub` filter can be added.
- **Source location ownership**: FAC-006 does not verify that `from_facility_id` and `from_location_id` are owned by the calling user's tenant. This is acceptable for P0 (single-tenant context); multi-tenant isolation requires a facility ownership check (a `get_facility` call that validates `owner_sub == session["user_sub"]`) which is a FAC-015 follow-up.
- **Audit trail**: every state transition emits `audit_event` via the best-effort `_audit` wrapper. This mirrors `app/services/inventory.py:92–98` and `app/services/returns_rma.py:85–91` (both use `try: from app.services.alerts import audit_event; audit_event(...) except Exception: pass`). The audit is fire-and-forget; a failure never rolls back the transition.

## 10. Open Questions / Assumptions

1. **Partial-failure on multi-SKU complete (§5.2 / §5.6)**: The "flip header first, then adjust" ordering means a crash between SKU A's decrement and SKU B's decrement leaves the transfer `completed` with partially applied inventory. **Assumption**: This is acceptable for P0 because single-SKU transfers are the common case; multi-SKU failures require operator intervention. A future improvement would be a two-phase commit via a `compensating_adjustments` map on the header (listing which SKUs were decremented/incremented), allowing a background sweep to complete or roll back partial transfers.

2. **Overdraw and header state (§5.2)**: If `transfer_out` raises 409 for the first SKU in a multi-SKU transfer, the header is already `completed`. The spec treats this as a 500 (partial failure). An alternative design is to check all SKUs for stock availability *before* flipping the header (a read-only pre-flight), then flip and adjust. The pre-flight does not guarantee atomicity under concurrent reservations, but it eliminates the partial-completion footgun for the common case. **Assumption for now**: "flip first" is used (matches `_close_reservation` pattern); a pre-flight read is tracked as a follow-up. Tests for overdraw need to exercise single-SKU transfers only, where the issue does not arise.

3. **`to_location_id` GSI**: The current `transfers` table has `GSI_FROM_LOC` but not `GSI_TO_LOC`. Querying "all inbound transfers for a location" requires a Scan. **Assumption**: P0 admin workloads will primarily query by `from_location_id` or `status`. A `GSI_TO_LOC` can be added by FAC-007 or FAC-015 if needed, but requires a new `attr_types` entry in `scripts/local-ddb-init.py` and an `UpdateTable` in prod.

4. **Facility ownership validation**: `create_transfer` does not validate that `from_facility_id` exists in `T.facilities` or is owned by the requesting user. **Assumption**: single-tenant P0 deployment; admin users are trusted. FAC-015 will add ownership checks as part of multi-tenant hardening.

5. **Line-level `short` status**: `TransferItemOut.status` accepts `"short"` for partial-pick scenarios. FAC-006 only sets `"moved"` (full completion) or `"pending"` (initial). Partial-quantity completion is deferred to FAC-008 (pick confirmation) which introduces `confirm_pick(picklist_id, line, picked_qty)`.

6. **`in_transit` semantic**: The `in_transit` state currently has no physical side-effect — it is a workflow marker for "goods have left the source bin but not yet arrived at the destination". The decision to check stock at `complete_transfer` (not at `advance_to_in_transit`) was made to mirror real warehouse practice where the source is decremented only on confirmed receipt. **Assumption**: this is intentional and matches OFBiz behaviour for inter-location transfers.

7. **Cursor encoding**: `list_transfers` and `list_transfers_for_location` need DynamoDB pagination. The existing `app/core/cursor.py` cursor encode/decode module is the correct tool. **Assumption**: cursor encoding from `app.core.cursor` is reused verbatim; no new cursor format is introduced.
