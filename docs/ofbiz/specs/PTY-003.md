## 1. Summary & Goal

PTY-003 adds the complete set of OFBiz-shaped Pydantic request/response models that all downstream Party/CRM service and router tickets will import. The models live exclusively in `app/models.py`, following the file's established convention for every other domain. No service layer, no DynamoDB access, and no router endpoints are introduced in this ticket — the deliverable is the type-safe contract that PTY-004 through PTY-015 are coded against.

Specifically, PTY-003 defines:

1. **Enums** — `PartyType`, `PartyStatus`, `PartyRoleType`, `RelationshipType`, `ContactMechType`, `ContactMechPurpose` — all typed as `(str, Enum)` following the `PmIdeaCategory` / `PmIdeaStatus` pattern already in the file (`app/models.py:7812–7831`).
2. **Data models** — `Party`, `PartyRole`, `PartyRelationship`, `ContactMech` — internal representations carrying the business-logic attributes.
3. **IO (request/response) models** — `CreatePartyIn`, `PartyOut`, `AddRoleIn`, `PartyRoleOut`, `CreateRelationshipIn`, `RelationshipOut`, `AddContactMechIn`, `ContactMechOut`, `OrgAccountOut` — the shapes seen at the API boundary.

Enum validation, normalizer integration (`normalize_email`, `normalize_phone`, `normalize_address_payload`), and Pydantic `field_validator`/`model_validator` guards are all included in this ticket so that the service layer (PTY-004+) can receive already-clean domain objects rather than raw dicts.

#### `CrmContactMechIn`

This is the most complex input model because validation differs per `mech_type`:

```python
class CrmContactMechIn(BaseModel):
    mech_type:      CrmContactMechType
    value:          Optional[str] = None     # for EMAIL and PHONE
    postal_address: Optional[AddressIn] = None  # for POSTAL
    purposes:       List[CrmContactMechPurpose] = Field(default_factory=list)

    @model_validator(mode="after")
    def _normalize_and_validate(self) -> "CrmContactMechIn":
        if self.mech_type == CrmContactMechType.EMAIL:
            if not self.value:
                raise ValueError("value is required for EMAIL contact mechs")
            try:
                self.value = normalize_email(self.value)
            except Exception as exc:
                raise ValueError("Invalid email") from exc
        elif self.mech_type == CrmContactMechType.PHONE:
            if not self.value:
                raise ValueError("value is required for PHONE contact mechs")
            try:
                self.value = normalize_phone(self.value)
            except Exception as exc:
                raise ValueError("Invalid phone") from exc
        elif self.mech_type == CrmContactMechType.POSTAL:
            if self.postal_address is None:
                raise ValueError("postal_address is required for POSTAL contact mechs")
            # value stores the first 16 hex chars of sha256(canonical JSON of normalized address)
            # for GSI2 dedup — matching the PTY-007 service-layer convention (PTY-007 §3)
            import hashlib, json as _json
            _addr = {k: v for k, v in self.postal_address.model_dump().items() if v is not None}
            _canon = _json.dumps(_addr, sort_keys=True)
            self.value = hashlib.sha256(_canon.encode()).hexdigest()[:16]
        return self
```

**Design decision — POSTAL `value` field:** `GSI2PK = "POSTAL#{value}"` on the DynamoDB row needs a canonical string. For POSTAL mechs the `value` field stores the first 16 hex chars of `sha256(json.dumps(normalized_addr, sort_keys=True))` — consistent with the PTY-007 contact-mech service spec (PTY-007 §3, `docs/ofbiz/specs/PTY-007.md:61-64`). Storing only `line1` is insufficient because PTY-007's `find_party_by_contact` hashes the full normalized address dict to produce the GSI lookup key. The full structured address fields are carried as a nested `postal_address: AddressIn` sub-object and stored verbatim on the DynamoDB item by the service layer.

**`normalize_email` / `normalize_phone` must be wrapped in `try/except → ValueError`:** Both functions raise `HTTPException(400, ...)` directly (`app/core/normalize.py:63` and `app/core/normalize.py:69`). The existing codebase pattern in `app/models.py` (e.g. `RegisterStartReq._normalize_phone` at `app/models.py:154-157`) wraps every normalizer call in `try/except Exception as exc: raise ValueError(...) from exc`. Bare `HTTPException` calls inside `model_validator` are NOT safely wrapped by Pydantic v2 and would bypass `ValidationError` handling. The `try/except → ValueError` pattern is mandatory.

**Max-length on `value`:** An explicit `Field(max_length=254)` is not on `value` because the normalizer itself enforces the 254-char email length limit (`app/core/normalize.py:62`). Phone length is constrained by E.164 format.

## 5. Detailed Behavior & Edge Cases

### 5.1 Enum rejection on unknown values

Pydantic v2 `(str, Enum)` fields raise `ValidationError` when an unrecognised string is supplied (e.g. `"VENDOR"` for `CrmPartyRoleType`). The error message identifies the field name and lists valid choices. Downstream service code can always rely on receiving a typed enum member, never a raw string. The one exception is DynamoDB reads: when the service hydrates a `CrmPartyOut` from a DDB item, if a row somehow contains an unrecognised `party_type` value (due to a DB migration in a future milestone), the model constructor will raise `ValidationError`. Services must catch this and either skip the row or raise `500`.

### 5.2 `normalize_email` / `normalize_phone` inside `model_validator` — `ValueError` wrapping required

`normalize_email` raises `fastapi.HTTPException(400, "Invalid email")` (`app/core/normalize.py:63`). When called bare from inside a Pydantic `model_validator`, `HTTPException` is **not** wrapped in `ValidationError` — it escapes Pydantic's validation chain and produces an unformatted 400 response. **This is NOT the correct behaviour.**

The established codebase pattern — `RegisterStartReq._normalize_phone` at `app/models.py:154-157` — wraps the call in `try/except Exception as exc: raise ValueError("Invalid phone") from exc`. The same pattern must be used for both `normalize_email` and `normalize_phone` in `CrmContactMechIn._normalize_and_validate` (see §4.4 corrected validator). The inline email validator at `app/models.py:138-144` also raises `ValueError` directly, never `HTTPException`.

Using `ValueError` inside `model_validator` gives Pydantic v2 the signal it needs to produce a well-formed `422 Unprocessable Entity` response with a `loc` path — the correct API-boundary behaviour.

### 5.3 POSTAL `value` field length

The `line1` portion used as the POSTAL `value` key is capped by `normalize_address_payload`'s `MAX_ADDRESS_LINE_LEN = 120` (`app/services/addresses.py:13` [VERIFIED]). DynamoDB attribute values are limited to 400 KB; 120 chars is well within bounds. The GSI2 partition key `POSTAL#{value}` is thus at most 128 chars.

### 5.4 `CrmRelationshipIn._parties_differ` validator

A self-loop relationship (same `from_party_id` and `to_party_id`) produces a DynamoDB item with `SK = REL#{rel_type}#{same_id}` which would be syntactically valid but semantically meaningless. The model validator rejects it early with a clear error rather than letting a confusing row reach DynamoDB.

### 5.5 `purposes` deduplication

The `purposes` list on `CrmContactMechIn` / `CrmContactMechOut` is not deduplicated at the model layer — it accepts repeated values. The service layer (PTY-006) is responsible for deduplication when writing to DynamoDB. This keeps the model simple and avoids surprising field transforms on read.

### 5.6 `user_sub` ignored for `PARTY_GROUP`

`CrmPartyIn.user_sub` is only meaningful for `PERSON` parties. If `party_type=PARTY_GROUP` is supplied alongside a non-None `user_sub`, the model does not reject it — the service layer (PTY-004) ignores `user_sub` for PARTY_GROUP rows and never writes `GSI3PK`/`GSI3SK` (per PTY-002 spec). A model-level `model_validator` could enforce this, but doing so would prevent `CrmPartyIn` from being used generically for cases where the caller does not yet know the party type. This is left as a service-layer concern.

### 5.7 `CrmPartyIn.correlation_id` max length

`max_length=128` is chosen to be larger than any realistic UUID/hash (32–64 chars) while bounding the hash input. The `sha256(correlation_id)[:32]` computation in the service layer (PTY-004) is safe for any string up to 128 chars.

### 5.8 `AddressIn` embedded in `CrmContactMechIn`

`AddressIn` (`app/models.py:1423` [VERIFIED]) has no validators — it is a plain `AddressBase` passthrough. The actual normalisation (trimming, country defaulting, max-len enforcement) happens in `normalize_address_payload` when the service layer stores the address. The model therefore accepts an untrimmed postal address and delegates cleanup to the service. This matches the existing pattern in `app/services/addresses.py:create_address` (`app/services/addresses.py:76-89` [VERIFIED]), where `normalize_address_payload(payload, require_all=True)` is called against the raw dict from `AddressIn.model_dump()`. The router endpoint at `app/routers/addresses.py:26-27` delegates to that service function — the normalisation is in the service, not the router.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**Dev/prod parity:** Pydantic models contain no `dev_mode` branches, mock paths, or environment checks. The same model classes are used in both environments. This satisfies SECOPS-007.

**Idempotency:** Models are stateless class definitions. Re-deploying or importing them multiple times has no side effects. The `app/models.py` file is loaded once at process startup.

**No secrets in models:** None of the new models carry or log secret values. `user_sub` is a Cognito subject identifier (non-secret opaque string). Contact mech `value` for EMAIL/PHONE contains PII (email address, phone number) but does not carry passwords, tokens, or keys. The models do not log any field — logging is the router/service layer's concern.

**Input length guards:**
- `correlation_id`: max 128 chars (explicit `Field(max_length=128)`)
- `from_party_id` / `to_party_id`: max 64 chars (`Field(..., max_length=64)`)
- `value` (EMAIL): 254-char limit enforced by `normalize_email`
- `value` (PHONE): E.164 format enforced by `normalize_phone`
- Postal fields: max 120 chars enforced by `normalize_address_payload` in the service layer
- `name` on `CrmOrgAccountOut`: max length is enforced by the service layer (PTY-008), not the Out model

**Enum exhaustiveness:** `(str, Enum)` types in Pydantic v2 use `use_enum_values=True` by default when serialising. Unknown incoming strings fail at validation time, preventing injection of arbitrary string values into DynamoDB key expressions.

## 10. Open Questions / Assumptions

1. **Assumption — `Crm`-prefixed naming [VERIFIED]:** The names `CreatePartyIn` and `PartyOut` are already taken by Watch Party video models at `app/models.py:4085` and `app/models.py:4109`. The `Crm`-prefix convention (`CrmPartyIn`, `CrmPartyOut`, etc.) is chosen to avoid shadowing. If a different convention is preferred (e.g. `OFBizPartyIn` or a sub-module split), the names must be changed consistently across PTY-003 through PTY-015 before the first service ticket is implemented.

2. **CORRECTED (pass 3) — POSTAL `value` field uses sha256 of full normalized address, not `line1` only:** The PTY-007 spec (`docs/ofbiz/specs/PTY-007.md:61-64`) definitively specifies `GSI2PK = "POSTAL#{sha256_hex[:16]}"` where the hash is `sha256(json.dumps(normalized_addr, sort_keys=True))[:16]`. The `_normalize_and_validate` validator in `CrmContactMechIn` (§4.4) has been updated accordingly. Using only `line1` would break `find_party_by_contact` in PTY-007 because the GSI lookup key would not match the model-computed `value`.

3. **CORRECTED — `normalize_email`/`normalize_phone` in validators must use `try/except → ValueError`:** The original spec claimed the existing pattern "propagates `HTTPException` as a `ValueError`-compatible exception". This is wrong. The actual `RegisterStartReq._normalize_phone` at `app/models.py:154-157` wraps every normalizer call in `try/except Exception as exc: raise ValueError(...) from exc`. Bare normalizer calls inside `model_validator` are not intercepted by Pydantic v2. The `CrmContactMechIn._normalize_and_validate` validator (§4.4) has been corrected to use this pattern.

4. **Assumption — `purposes` list deduplication deferred to service layer:** The model accepts repeated `purposes` values (e.g. `["BILLING", "BILLING"]`). If deduplication is required at the API boundary (for idempotency of client submissions), a `field_validator` can be added. Currently deferred to PTY-006.

5. **RESOLVED (pass 3) — `CrmOrgAccountOut.name` source is `CrmCreateOrgAccountIn.name` defined by PTY-008:** The PTY-008 spec (`docs/ofbiz/specs/PTY-008.md:560-568`) defines `CrmCreateOrgAccountIn` with `name: str = Field(..., min_length=1, max_length=256)`. The `name` is passed directly to `create_org_account(name, ...)` and stored on the PARTY_GROUP META row — it does NOT flow through `CrmPartyIn`. No `display_name` field needs to be added to `CrmPartyIn` in PTY-003; that addition is correctly deferred to PTY-008.

6. **Assumption — `AddressIn` sub-object not validated in `CrmContactMechIn`:** The embedded `postal_address: Optional[AddressIn]` accepts raw dicts via Pydantic coercion. No max-length guards run at model validation time — those run in `normalize_address_payload` in the service layer. This is consistent with the existing `AddressIn`/`AddressBase` pattern in the codebase. If the acceptance criteria for PTY-003 require all normalisation to happen at model validation time, a `model_validator` in `CrmContactMechIn` should call `normalize_address_payload(self.postal_address.model_dump(), require_all=True)` directly.

7. **Assumption — `CrmPartyStatus.MERGED` is terminal but not enforced at model level:** Transitions from `MERGED` back to `ACTIVE` are not blocked by the model. Status-transition enforcement is the service layer's responsibility (PTY-004). If a model-level `field_validator` is added to enforce allowed transitions, it would need access to the current stored status — impossible in a stateless Pydantic model. This is correctly deferred to the service.
