# PUR-007 — PO approval lifecycle state machine

**Type:** Feature | **Priority:** P0 | **Estimate:** 4 days  
**Milestone:** 3 — Purchase Orders & Approval  
**Depends on:** PUR-006 (purchase-order entity & creation)

---

## 1. Summary & Goal

PUR-007 adds the guarded state-transition layer on top of the purchase-order
entity created by PUR-006. Its core deliverable is a single service function,
`transition_po(po_id, target_status, actor_sub, ...)`, that enforces the
agreed-upon PO lifecycle state machine atomically via a conditional DynamoDB
`update_item`. Each call either succeeds (emits an audit event, updates `status`,
moves the header across the `GSI_STATUS` approval queue) or returns a 409 without
mutating state.

The separate `submit`, `approve`, and `reject` verbs are intentional: submit is
available to any authenticated user who created the PO; approve/reject are
admin-only operations. The ticket does not add HTTP endpoints (those arrive in
PUR-010) and does not add billing or inventory mutations (PUR-008/009).

With `PURCHASING_SCM_ENABLED=false` (the default) every function raises
`HTTPException(404)` and all existing shop/cart/orders/billing/inventory code is
byte-for-byte unchanged.

## 2. Context & Current State

### 2.1 State machine agreed in PUR-001

The lifecycle is documented at `PURCHASING_SCM_TICKETS.md:15` (verified):

```
draft → submitted → approved → ordered → partially_received → received → closed

From submitted : → rejected    (admin only)
From approved  : → rejected    (admin only)
From draft     : → cancelled   (creator or admin)
From submitted : → cancelled   (creator or admin)
From approved  : → cancelled   (creator or admin)
```

Terminal states are `closed`, `rejected`, and `cancelled`. No transition out of
a terminal state is legal.

### 2.2 Atomic conditional-update pattern

The design mirror is `app/services/inventory.py:434–453` (`_close_reservation`),
verified by reading the file. That function uses:

```python
T.reservations.update_item(
    Key={"reservation_pk": ..., "sk": "META"},
    UpdateExpression="SET #status = :new, closed_at = :now ...",
    ConditionExpression="#status = :active",
    ExpressionAttributeNames={"#status": "status"},
    ExpressionAttributeValues={":new": terminal_status, ":active": "active", ":now": now_ts()},
    ReturnValues="ALL_OLD",
)
```

If `ConditionalCheckFailedException` is raised, the function returns `None`
(idempotent no-op). PUR-007 uses the same pattern with `":expected": expected_status`
instead of `":active": "active"`. An illegal-transition guard is layered before
the DDB call so the function can return 409 for wrong-status attempts versus
returning a no-op for already-applied same-transition replays.

### 2.3 `purchase_orders` table and GSIs (established by PUR-002)

From `docs/ofbiz/specs/PUR-006.md:112–117` (which cites `PURCHASING_SCM_TICKETS.md:38`):

- **PK** = `po_id` (S), **SK** = `sk` (S)
- **Header row**: `sk = "META"`; carries `status`, `supplier_id`, `created_at`
- **GSI_STATUS**: partition `status` (S), sort `created_at` (N) — the approval queue
- **GSI_SUPPLIER**: partition `supplier_id` (S), sort `created_at` (N)
- `attr_types={"created_at": "N"}` is declared in `scripts/local-ddb-init.py`
  (per the PUR-002 spec; the pattern mirrors `returns` at `scripts/local-ddb-init.py:2491` — verified)

### 2.6 Admin auth dependency

`app/auth/policy.py:67–68` (verified) defines:

```python

    return require_roles(user, {Role.ADMIN, Role.ROOT})
```

`Role` is a `str, Enum` with no comparison operators (`app/auth/roles.py:8`);

(the router, delivered by PUR-010, passes `Depends(require_admin_or_root)` on
those endpoints). The service itself validates via an `is_admin` boolean argument
to avoid tight coupling between the service module and FastAPI dependency
injection.

## 3. Data Model

### 3.1 No schema changes

PUR-007 adds no new DynamoDB tables, GSIs, or `attr_types` declarations. It
writes to the `purchase_orders` table established by PUR-002 (see
`docs/ofbiz/specs/PUR-006.md:70` — §3 "Data Model" section).

### 3.2 New/modified header attributes written by PUR-007

The following attributes are added to the `SK="META"` header row by transition
operations. They are absent on a freshly created `draft` PO.

| Attribute | Type | Written by | Description |
|---|---|---|---|
| `submitted_by` | S | `submit_po` | `actor_sub` of the submitter |
| `submitted_at` | N | `submit_po` | Unix timestamp |
| `approved_by` | S | `approve_po` | `actor_sub` of the approver |
| `approved_at` | N | `approve_po` | Unix timestamp |
| `rejected_by` | S | `reject_po` | `actor_sub` of the rejector |
| `rejected_at` | N | `reject_po` | Unix timestamp |
| `rejected_reason` | S | `reject_po` | Free-text reason (required) |
| `cancelled_by` | S | `cancel_po` | `actor_sub` of the canceller |
| `cancelled_at` | N | `cancel_po` | Unix timestamp |
| `cancelled_reason` | S | `cancel_po` | Free-text reason (optional) |
| `updated_at` | N | every transition | Updated on every successful transition |

The `status` attribute (already present on `draft` creation) is updated in-place
by the conditional `update_item`. Because `status` is the `GSI_STATUS` partition
key, updating it moves the item to a new GSI partition — this is the mechanism
by which the approval queue is driven.

### 3.3 Transition-log row (optional, deferred)

This ticket does not write a separate audit-trail DDB row. The audit event
emitted through `_audit(...)` → `alerts.audit_event` (which writes to
`T.alerts`) is the complete audit trail for this ticket. A structured
`TRANSITION#{ts}` sub-row could be added in a follow-on ticket without schema
impact.

## 4. API / Service Design

### 4.1 Extension to `app/services/purchase_orders.py`

All functions below are added to the module created by PUR-006. No new file is
created. The module's `_require_enabled`, `_audit`, `_to_int`, and
`_get_all_po_items` helpers are already present (from PUR-006).

### 4.2 Legal-transition table

```python
# Defined at module level in purchase_orders.py
_LEGAL_TRANSITIONS: Dict[str, Set[str]] = {
    "draft":             {"submitted", "cancelled"},
    "submitted":         {"approved", "rejected", "cancelled"},
    "approved":          {"ordered", "rejected", "cancelled"},
    "ordered":           {"partially_received"},   # driven by PUR-008
    "partially_received": {"received"},             # driven by PUR-008
    "received":          {"closed"},               # driven by PUR-007 auto-close
    "closed":            set(),
    "rejected":          set(),
    "cancelled":         set(),
}

# Transitions that require admin/root role
_ADMIN_ONLY_TRANSITIONS: Set[str] = {"approved", "rejected"}
```

### 4.3 Core transition function

```python
def transition_po(
    po_id: str,
    target_status: str,
    actor_sub: str,
    *,
    is_admin: bool = False,
    reason: Optional[str] = None,
    transition_id: Optional[str] = None,
) -> Dict[str, Any]:
    """Atomically advance a PO to target_status.

    Args:
        po_id:          Primary key of the purchase order.
        target_status:  The desired next status value.
        actor_sub:      user_sub of the caller; stored in approved_by / etc.
        is_admin:       Must be True for admin-only transitions (approve/reject).
                        The router layer enforces this via Depends(require_admin_or_root).
        reason:         Required for `rejected`; optional for `cancelled`.
        transition_id:  Optional caller-supplied idempotency key (sha256 of
                        correlation bytes). When present, the function checks
                        whether the PO is already in target_status and returns
                        the current record without a 409 (replay).

    Returns:
        Full PO dict (header + lines) after the transition.

    Raises:
        HTTPException(404) — purchasing_scm_enabled is False or PO not found.
        HTTPException(403) — admin-only transition attempted without is_admin.
        HTTPException(409) — illegal transition (wrong current status, or
                             cancel blocked because quantity_received > 0).
        HTTPException(422) — reason required but not supplied (for reject).
    """
```

**Detailed execution sequence:**

1. `_require_enabled()`.
2. Fetch the header: `T.purchase_orders.get_item(Key={"po_id": po_id, "sk": "META"})`.
   If absent → `HTTPException(404, "Purchase order not found")`.
3. `current_status = header["status"]`.
4. **Replay guard**: if `current_status == target_status`, return
   `get_purchase_order(po_id)` immediately (idempotent no-op; not a 409).
5. **Illegal-transition guard**: if `target_status` not in
   `_LEGAL_TRANSITIONS.get(current_status, set())` → `HTTPException(409,
   f"Cannot transition PO from {current_status!r} to {target_status!r}")`.
6. **Admin guard**: if `target_status in _ADMIN_ONLY_TRANSITIONS and not is_admin`
   → `HTTPException(403, "Approval/rejection requires admin role")`.
7. **Reject reason guard**: if `target_status == "rejected" and not reason`
   → `HTTPException(422, "A reason is required when rejecting a PO")`.
8. **Cancel-after-receive guard**: if `target_status == "cancelled"`:
   - Fetch all line rows (via `_get_all_po_items`).
   - If any line has `quantity_received > 0` → `HTTPException(409,
     "Cannot cancel a PO with received quantities; use close instead")`.
9. Build `UpdateExpression` and extra attributes depending on `target_status`
   (see table below).
10. Issue the conditional `update_item`:
    ```python
    T.purchase_orders.update_item(
        Key={"po_id": po_id, "sk": "META"},
        UpdateExpression="SET #status = :new, updated_at = :now" + extra_set,
        ConditionExpression="#status = :expected",
        ExpressionAttributeNames={"#status": "status"},
        ExpressionAttributeValues={
            ":new": target_status,
            ":expected": current_status,
            ":now": now_ts(),
            **extra_values,
        },
    )
    ```
11. On `ConditionalCheckFailedException`: re-fetch the header.
    - If now `== target_status` (concurrent replay) → return the record.
    - Otherwise → `HTTPException(409, "Concurrent modification; please retry")`.
12. `_audit(f"purchase_order_{target_status}", actor_sub, po_id=po_id, ...)`.
13. Return `get_purchase_order(po_id)`.

**Extra SET expressions per target_status:**

| `target_status` | Extra `SET` clauses | Extra `ExpressionAttributeValues` |
|---|---|---|
| `submitted` | `, submitted_by = :by, submitted_at = :now` | `":by": actor_sub` |
| `approved` | `, approved_by = :by, approved_at = :now` | `":by": actor_sub` |
| `rejected` | `, rejected_by = :by, rejected_at = :now, rejected_reason = :rsn` | `":by": actor_sub, ":rsn": reason` |
| `cancelled` | `, cancelled_by = :by, cancelled_at = :now` + optional reason | `":by": actor_sub` |
| `ordered` | _(none beyond status + updated_at)_ | — |
| `partially_received` | _(none; driven by PUR-008 via `transition_po`)_ | — |
| `received` | _(none; driven by PUR-008 via `transition_po`)_ | — |
| `closed` | _(none; called from PUR-008 auto-close path)_ | — |

### 4.4 Convenience wrappers

These thin wrappers make the caller's intent clear and map to the PUR-010 HTTP
endpoints. Each calls `transition_po` with the appropriate parameters.

```python
def submit_po(po_id: str, actor_sub: str) -> Dict[str, Any]:
    """draft → submitted (any authenticated user)."""
    return transition_po(po_id, "submitted", actor_sub, is_admin=False)


def approve_po(po_id: str, actor_sub: str) -> Dict[str, Any]:
    """submitted → approved (admin/root only)."""
    return transition_po(po_id, "approved", actor_sub, is_admin=True)


def reject_po(po_id: str, actor_sub: str, reason: str) -> Dict[str, Any]:
    """submitted|approved → rejected (admin/root only)."""
    return transition_po(po_id, "rejected", actor_sub, is_admin=True, reason=reason)


def cancel_po(
    po_id: str,
    actor_sub: str,
    *,
    reason: Optional[str] = None,
    is_admin: bool = False,
) -> Dict[str, Any]:
    """draft|submitted|approved → cancelled (creator or admin; blocked if any qty received)."""
    return transition_po(po_id, "cancelled", actor_sub, is_admin=is_admin, reason=reason)
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent replay

The core replay guarantee: **if the PO is already in the target status when
`transition_po` is called, the function returns the current record without a 409
or a second `update_item` call.** This is the explicit step 4 in the execution
sequence above.

This means a network retry after a 5xx does not cause a 409 storm. The caller
simply receives the current state of the PO as confirmation.

### 5.2 Concurrent transition race

Two callers simultaneously trying to move `submitted → approved`:

- Both read `current_status = "submitted"`.
- Both pass the legal-transition guard.
- First caller's `update_item` succeeds; the PO is now `approved`.
- Second caller's `update_item` hits `ConditionalCheckFailedException`.
- PUR-007 re-fetches: `current_status` is now `"approved"` which equals
  `target_status` → treated as a replay → returns the PO (not a 409).

Two callers trying different transitions (e.g., one approves, one rejects):

- The loser's `ConditionalCheckFailedException` produces a re-fetch where
  `current_status != target_status` → `HTTPException(409, "Concurrent
  modification; please retry")`.

### 5.3 Cancel blocked after receiving

`transition_po` fetches all line rows before issuing the conditional update when
`target_status == "cancelled"`. If any `quantity_received > 0` the call returns
`HTTPException(409, "Cannot cancel a PO with received quantities; use close
instead")`. This check uses the already-available `_get_all_po_items` helper
(established by PUR-006).

Note: the check is performed before the conditional `update_item`, so there is a
small TOCTOU window where a concurrent partial receive could race. This is
acceptable for a purchasing workflow (human approval loops); the worst case is a
409 on cancel that prompts a re-fetch. A stricter design would use a DDB
transaction, but that adds complexity disproportionate to the risk.

### 5.4 `received → closed` auto-transition

PUR-008 (receiving) is responsible for setting `status = "partially_received"`
and `status = "received"` when all lines are fully received. It does so by
calling `transition_po(po_id, "received", actor_sub="system")` followed
immediately by `transition_po(po_id, "closed", actor_sub="system")`. The legal
transition table permits `received → closed`, so both calls succeed atomically.

PUR-007 *allows* the `received → closed` transition in `_LEGAL_TRANSITIONS` and
PUR-008 *triggers* it. PUR-007 does not auto-close; it only enforces the rules.

### 5.5 Flag-off behavior

With `S.purchasing_scm_enabled = False`:

- `transition_po(...)` → `HTTPException(404, "Purchasing/SCM is not enabled")`.
- All four router endpoints → 404 (the `_require_enabled` call is the first
  statement in every function).
- Existing shop, cart, orders, billing, and inventory code is byte-for-byte
  unchanged — no call sites in those modules reference `purchase_orders.py`.

### 5.6 Unknown `target_status` string

If a caller passes a completely unknown status string (e.g., `"frobbed"`):

- `_LEGAL_TRANSITIONS.get("draft", set())` is `{"submitted", "cancelled"}`.
- `"frobbed"` is not in that set → 409 (illegal transition).

This is correct: the 409 code means "the current state does not permit this
transition", which is true regardless of whether the target state is unknown.

### 5.7 PO in a terminal state

If a PO is in `closed`, `rejected`, or `cancelled`:

- `_LEGAL_TRANSITIONS["closed"]` etc. all return `set()`.
- Any `target_status` (including `"closed"` again) fails the legal-transition
  guard... unless `target_status == current_status`, in which case the replay
  guard (step 4) fires first and returns the record without a 409. This is
  correct: re-submitting `closed → closed` should be a no-op, not an error.

### 5.8 Missing PO

Step 2 of the execution sequence fetches the header. A missing PO returns 404,
not 409. The 404 is distinct from the "Purchasing/SCM is not enabled" 404 because
the latter fires from `_require_enabled()` before any DDB call.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

All DynamoDB writes in PUR-007 go through `T.purchase_orders` (a `_safe_table`
handle). In dev this resolves to DynamoDB Local at `http://localhost:8001`; in
prod it resolves to real DynamoDB. The code is identical. No `S.dev_mode` branch
exists in `purchase_orders.py`.

The conditional `update_item` pattern (`ConditionExpression="#status = :expected"`)
behaves identically under DynamoDB Local (via moto in tests, via the local Docker
container in dev) and real DynamoDB. There is no mock path for the state machine.

### 7.2 Idempotency design

Two levels of idempotency:

1. **Same target as current** (replay guard, step 4): returns the record without
   any DDB write. Safe for indefinite retries.
2. **Concurrent writer wins** (post-ConditionalCheckFailed re-fetch): the loser
   detects the PO is already in the target state and returns the record as if it
   had succeeded. Safe for two concurrent approval requests.

Callers do not need to supply a `transition_id`; the existing `po_id` + natural
DDB conditional check provides the idempotency boundary.

### 7.3 Security

- **Approval privilege**: `approve` and `reject` set `is_admin=True` only when
  the caller's role is `ADMIN` or `ROOT` (enforced by the PUR-010 router via
  `Depends(require_admin_or_root)`). The service-layer `is_admin` flag is a belt
  for defence in depth; the router is the suspenders.
- **Ownership on cancel**: Regular users (`is_admin=False`) who cancel a PO are
  expected to be the PO creator; ownership is not enforced at the service layer
  in this ticket (it is enforced at the router layer in PUR-010 by comparing
  `header["created_by"] == user.sub` before calling `cancel_po`). Admin users can
  cancel any PO.
- **Reason stored as plain string**: `rejected_reason` and `cancelled_reason` are
  stored verbatim. No special encoding or sanitisation is required beyond the
  Pydantic field validators in `PoRejectIn`.
- **Audit trail**: every successful transition emits an `alerts.audit_event` that
  is persisted to `T.alerts` (the existing alerts table). This is the same
  audit mechanism used by inventory, returns, and all KYC operations.

## 8. Backward Compatibility & Migration

### 8.1 Additive only

PUR-007 only adds new attributes to existing PO header rows (`submitted_by`,
`approved_by`, etc.). It does not remove, rename, or redefine any attribute
written by PUR-006. A PO created before PUR-007 deploys will have none of these
attributes; they will be absent (DynamoDB allows sparse attributes). The
`get_purchase_order` function should use `.get("approved_by")` style access and
return `None` for missing attributes.

### 8.2 No `purchase_orders` table schema change

No new GSIs, attribute definitions, or `attr_types` are required. The existing
`GSI_STATUS` already uses `status` as its partition key — updating `status` in
the header row is sufficient to move the item across GSI partitions. No
backfill or `UpdateTable` call is needed.

### 8.3 Flag transition

With `PURCHASING_SCM_ENABLED=false` (the default), no data is written to the
`purchase_orders` table. Flipping the flag to `true` has no backward-compatibility
implication because there are no existing rows to migrate.

### 8.4 PUR-008 dependency contract

PUR-008 (receiving) will call `transition_po(po_id, "partially_received",
actor_sub="system")` and `transition_po(po_id, "received", actor_sub="system")`
and `transition_po(po_id, "closed", actor_sub="system")` after computing
quantities. The legal transition table in PUR-007 must include:

- `approved → partially_received` (via `ordered` which PUR-008 may skip in a
  direct-receive workflow) — see open question OQ-1 below.
- `ordered → partially_received`
- `partially_received → received`
- `received → closed`

These are all present in `_LEGAL_TRANSITIONS` as defined in section 4.2.

### 9.3 E2E spec (`frontend/e2e/purchasing-po-approval.spec.ts`)

Added by PUR-010 (which adds the HTTP endpoints), but the acceptance criteria
belong here:

- Alice (USER role) creates a draft PO via POST, submits it; the PO transitions
  to `submitted` and appears in the approval queue.
- Alice cannot approve her own PO (403).
- Charlie (ADMIN role) approves the PO; `approved_by` is Charlie's sub.
- Attempting to submit an already-submitted PO is a no-op (200, not 409).
- Charlie rejects a submitted PO; `rejected_reason` is returned.
- Alice cancels a draft PO; attempting to cancel again is a no-op.
- With `PURCHASING_SCM_ENABLED=false` every endpoint returns 404 and the
  navigation item is hidden.

## 10. Open Questions / Assumptions

**OQ-1: `approved → ordered` transition initiator**
The ticket defines `ordered` as a status that precedes `partially_received`.
PUR-008 (receiving) requires the PO be in `approved`/`ordered`/`partially_received`.
It is unclear whether the `approved → ordered` transition (representing the act
of sending the PO to the supplier) is manual (a "Mark as Ordered" button in
PUR-010) or automatic upon approval.

_Assumption:_ `approved → ordered` is a **manual** transition exposed as
`POST .../{po_id}/order` in PUR-010. PUR-008 accepts both `approved` and
`ordered` as legal starting states for receiving. If the manual transition is
removed from scope, PUR-008 can receive directly against `approved` without
ever visiting `ordered`.

**OQ-2: Cancel ownership enforcement at service layer**
This spec defers cancel-ownership enforcement (checking `header["created_by"]
== actor_sub` for non-admin users) to the PUR-010 router layer. If PUR-010 is
delayed, callers of the service function could bypass the check.

_Assumption:_ The service layer accepts `is_admin=False` callers without
ownership check; the router enforces ownership. If this is unacceptable,
`cancel_po` should accept an `owner_sub: Optional[str]` argument and perform the
check when `is_admin=False` and `owner_sub` is provided.

**OQ-3: Transition-log sub-rows**
No `TRANSITION#{ts}` sub-rows are written by this ticket. The audit trail lives
in `T.alerts`. If a structured transition history is needed for the PO detail
view, a follow-on ticket can add `SK=TRANSITION#{ts}` rows without schema
migration.

**OQ-4: `ordered` status as auto-transition**
Should approval automatically fire `approved → ordered` if the organisation does
not have a manual "send PO to supplier" workflow? Left as a product decision.

_Assumption:_ The manual step is kept to allow a review window between approval
and actual order dispatch.

**OQ-5: Transition of `received → closed` via PUR-008**
PUR-008 will call `transition_po` with `actor_sub="system"`. The audit event will
show `actor = "system"`. The alternative is to pass the actual user_sub of the
receiving clerk. This spec assumes `"system"` for the auto-close; the manual
auto-close call in PUR-008 should pass the receiving user_sub through.

_Assumption:_ PUR-008 passes the receiving user's `actor_sub` through to
`transition_po` even for the auto-close step, so the audit trail shows the
clerk who completed the final receipt.
