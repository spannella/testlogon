# ORD-003 — DDB single-table items, GSIs, and table handles

**Type:** Chore | **Priority:** P0 | **Estimate:** 2 days
**Milestone:** 1 — Foundation (flag, data model, tables)

---

## 1. Summary & Goal

ORD-003 is the DynamoDB infrastructure ticket for the order-lifecycle work stream. It has one concrete job: extend the existing `orders` table at `scripts/local-ddb-init.py:287` from a PK-only flat table into a proper single-table design that can house four SK-partitioned row types — order header, status-history events, ship groups, and order adjustments — plus two new lifecycle-specific GSIs needed by admin list views (ORD-011) and the state-machine service (ORD-005).

Alongside the schema changes, ORD-003 must update every caller of `T.orders.get_item` and `T.orders.put_item` that currently omits the sort key (`sk`) field, since adding `sk` to the table definition as a range key breaks the existing PK-only access pattern for those callers.

The entire change is infra-level. No new service logic, no new router, no new Pydantic models (those belong to ORD-004). After ORD-003 merges, `just restart` must recreate the `orders` table with all five GSIs (three existing-style + two new lifecycle) and no `ValidationException`. A smoke pytest confirms round-trip writes across all four row types and both new GSIs.

**Zero-behavior guarantee**: When `ORDER_LIFECYCLE_ENABLED` is off (default), the new GSIs exist but receive no writes. Existing shop/cart/billing flows write only `ORDER`-SK header rows and are byte-for-byte unchanged.

## 3. Data Model

### 3.1 Structural constraint: adding `sk` to the base table

The `orders` table currently has no sort key. Adding `sk` as the base table range key is a breaking schema change: existing items (written without `sk`) are unreachable by `get_item(Key={"order_id": ..., "sk": "ORDER"})`. The migration strategy is:

- **Dev**: `just restart` drops and recreates the table from scratch. No data survives; the E2E session setup re-seeds everything.
- **Prod**: a one-time migration script scans all `orders` items, and for each item lacking an `sk` attribute, writes `sk="ORDER"` back using `update_item` with `ConditionExpression="attribute_not_exists(sk)"` (idempotent, safe to rerun). This must run before any traffic hits code that queries by `sk`. See Section 8.

### 3.2 Extended single-table layout

**Table name**: `orders` (env `ORDERS_TABLE_NAME`, default `"orders"`)  
**Base PK**: `order_id` (S) — unchanged  
**Base SK**: `sk` (S) — **new** in ORD-003  

| Row type | SK value | Written by | Purpose |
|---|---|---|---|
| Order header | `ORDER` | `commerce_order_service.create_order` (`:85`), `file_bundle_checkout.py:98` | One per order; the flat record that exists today |
| Status history | `HIST#{ts:020d}#{event_id}` | ORD-006 (`order_lifecycle.py`) | One per transition; `ts` is `now_ts()` zero-padded to 20 digits; `event_id` is `sha256(order_id|from|to|idempotency_key)[:16]` |
| Ship group | `SHIPGRP#{ship_group_id}` | ORD-009 | One per logical shipment grouping; `ship_group_id` is `uuid4().hex` |
| Order adjustment | `ADJ#{adjustment_id}` | ORD-008 | One per discount/surcharge/tax/shipping line; `adjustment_id` is `uuid4().hex` |

The zero-padding in `HIST#{ts:020d}#{event_id}` ensures chronological sort order for DynamoDB's lexicographic SK comparisons, matching the pattern in `billing_shared.py:221` (`ledger_sk` returns `LEDGER#{ts}#{entry_id}`) [verified: `billing_shared.py:220–221`] which uses the same ordering rationale. Note that the billing ledger uses bare integer timestamps (no zero-padding); `HIST#` uses zero-padding to 20 digits explicitly to guarantee lexicographic chronological order independent of integer width.

### 3.3 GSIs — full five-index definition

After ORD-003, the `orders` table carries five GSIs total. The two existing GSIs are preserved unchanged in index name and attribute types; two new lifecycle GSIs are added.

| Index | GSI PK | GSI SK | PK type | SK type | Populated on |
|---|---|---|---|---|---|
| `GSI_USER` | `user_id` | `created_at` | S | S | `ORDER` rows — unchanged |
| `GSI_STATUS` | `status` | `created_at` | S | S | `ORDER` rows — unchanged (legacy status field) |
| `GSI_ORDER_STATUS` | `lifecycle_status` | `updated_ts` | S | **N** | `ORDER` rows when `ORDER_LIFECYCLE_ENABLED=true` |
| `GSI_ORDER_SHIPDATE` | `ship_date_bucket` | `ship_ts` | S | **N** | `SHIPGRP` rows when `ORDER_LIFECYCLE_ENABLED=true` |

`GSI_ORDER_STATUS` key semantics:
- `lifecycle_status` (S): one of `"created"`, `"approved"`, `"allocated"`, `"picking"`, `"packed"`, `"shipped"`, `"completed"`, `"held"`, `"backorder"`, `"cancelled"`, `"returned"`.
- `updated_ts` (N): integer Unix seconds from `now_ts()` at last lifecycle transition.

`GSI_ORDER_SHIPDATE` key semantics:
- `ship_date_bucket` (S): `"YYYY-MM-DD"` string derived from the expected ship timestamp (UTC). Provides per-day range partitioning.
- `ship_ts` (N): integer Unix seconds of the expected ship-by timestamp; supports numeric range queries (`ship_ts BETWEEN :start AND :end`) within a date bucket.

### 4.3 Smoke helper functions (delivered by ORD-003, consumed by ORD-005+)

To keep the smoke pytest self-contained and to provide a stable accessor pattern for downstream tickets, ORD-003 introduces three thin helper functions in a new file `app/services/order_store.py`. These are **infrastructure accessors only** — no business logic, no flag checks.

```python
# app/services/order_store.py
from __future__ import annotations
from typing import Any, Dict, List, Optional
from boto3.dynamodb.conditions import Key
from app.core.tables import T


def put_order_header(item: Dict[str, Any]) -> None:
    """Write (or overwrite) an order header row. Caller must include sk='ORDER'."""
    T.orders.put_item(Item=item)


def get_order_header(order_id: str) -> Optional[Dict[str, Any]]:
    """Fetch the ORDER-SK header row for an order. Returns None if not found."""
    resp = T.orders.get_item(Key={"order_id": order_id, "sk": "ORDER"})
    return resp.get("Item")


def query_order_rows(
    order_id: str,
    sk_prefix: Optional[str] = None,
) -> List[Dict[str, Any]]:
    """Return all rows under an order_id, optionally filtered by SK prefix.

    sk_prefix examples: "HIST#", "SHIPGRP#", "ADJ#".
    Omit sk_prefix to return all rows including the ORDER header.
    Loops via LastEvaluatedKey to return complete result sets.
    """
    cond = Key("order_id").eq(order_id)
    if sk_prefix:
        cond = cond & Key("sk").begins_with(sk_prefix)
    kwargs: Dict[str, Any] = {"KeyConditionExpression": cond}
    out: List[Dict[str, Any]] = []
    while True:
        resp = T.orders.query(**kwargs)
        out.extend(resp.get("Items", []))
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
    return out
```

These three functions replace the inline `T.orders.get_item(Key={"order_id": ...})` pattern at `returns_rma.py:107` and the direct `put_item` at `commerce_order_service.py:85`; callers can be migrated gradually — they are not required to use `order_store` in ORD-003 itself, but downstream tickets (ORD-005, ORD-006, ORD-008, ORD-009) will use `query_order_rows` to avoid reimplementing the pagination loop.

## 5. Detailed Behavior & Edge Cases

### 5.1 Existing items without `sk`

Orders written before ORD-003 deploys (i.e., items with no `sk` attribute) are unreachable by `get_item(Key={"order_id": ..., "sk": "ORDER"})`. They do not cause errors; they simply exist as orphan rows. In dev this is irrelevant (`just restart` wipes data). In prod, the migration script in Section 8 backfills `sk="ORDER"` before any lifecycle traffic is enabled.

### 5.2 `created_at` (ISO string) vs. `updated_ts` (integer)

The two existing GSIs (`GSI_USER`, `GSI_STATUS`) use `created_at` as their sort key; this is an ISO-8601 string and must remain a string for backward compatibility. The two new GSIs (`GSI_ORDER_STATUS`, `GSI_ORDER_SHIPDATE`) use integer sort keys (`updated_ts`, `ship_ts`) to enable native numeric range queries. The same order header row thus carries two timestamp representations: `created_at` (string, for legacy GSIs) and `updated_ts` (integer, for lifecycle GSI). This is the same dual-representation pattern seen in the `messages` table and `instance_monitoring.py` timeline events.

### 5.3 GSI sparse population

`GSI_ORDER_STATUS` is populated only on rows where `lifecycle_status` is present. With `ORDER_LIFECYCLE_ENABLED=false`, no `lifecycle_status` attribute is written on new order headers, so the GSI receives no writes. DynamoDB sparse GSIs are supported and cost nothing for absent attributes.

`GSI_ORDER_SHIPDATE` is populated only on `SHIPGRP#` rows that carry `ship_date_bucket` and `ship_ts`. The order header row does not carry these attributes. This ensures that a query against `GSI_ORDER_SHIPDATE` for a given `ship_date_bucket` returns only ship group rows, not headers.

### 5.4 `GSI_STATUS` continues to receive writes with flag off

The legacy `status` field is written by `commerce_order_service.create_order` (`line 75`: `"status": "pending_payment"`) unconditionally. The `GSI_STATUS` index continues to be populated whether or not the lifecycle flag is on. When the flag is on, lifecycle transitions also mirror to `status` (per ORD-001 Section 3.6), so `GSI_STATUS` stays current.

### 5.5 `_ensure_table` incremental update path

For prod deployment of the two new GSIs (without dropping the table), `_ensure_table` at `scripts/local-ddb-init.py:2534` handles missing GSIs via `UpdateTable`. [verified: `local-ddb-init.py:2534–2576`] However, the base table sort key (`sk`) cannot be added via `UpdateTable` — it requires a `DeleteTable` + `CreateTable` cycle. In prod this means ORD-003 must be deployed with a migration script (Section 8). In dev `just restart` handles it automatically.

### 5.6 `file_bundle_checkout.py` items without `lifecycle_status`

`file_bundle_checkout.py:98` writes directly to `T.orders` and bypasses `commerce_order_service`. After the ORD-003 caller fix, it writes `sk="ORDER"` but no `lifecycle_status` or `updated_ts`. This is correct: file-bundle orders are not subject to the lifecycle state machine. `GSI_ORDER_STATUS` never indexes them.

### 5.7 SK collision avoidance

All four SK patterns are prefix-distinct:
- `"ORDER"` — exact literal, no prefix
- `"HIST#"` — status history
- `"SHIPGRP#"` — ship groups
- `"ADJ#"` — adjustments

DynamoDB key values are case-sensitive; all values here are uppercase. A `begins_with("HIST#")` filter in `query_order_rows` correctly excludes headers, ship groups, and adjustments.

### 5.8 `updated_ts` type on existing header rows

Rows written before ORD-003 carry no `updated_ts`. After ORD-005 adds lifecycle transitions, `updated_ts` is written as an integer for the first time when `ORDER_LIFECYCLE_ENABLED=true`. Rows that are never transitioned (flag-off orders) remain absent from `GSI_ORDER_STATUS`. This is intentional and requires no backfill.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007 parity

The `TableDef` at `scripts/local-ddb-init.py` is the single schema source of truth for both dev and prod. `_ensure_table` at line 2534 drives both the local bootstrap (via `just restart`) and the incremental prod `UpdateTable` path. There is no dev-only branch in the DDB schema. The two new GSIs (`GSI_ORDER_STATUS`, `GSI_ORDER_SHIPDATE`) are declared in the same `TableDef` used in all environments.

The three caller fixes (`file_bundle_checkout.py`, `returns_rma.py`, `commerce_order_service.py`) apply identically in dev and prod. There is no `dev_mode` branch in any of these write paths.

### Idempotency

- `put_item` on the order header (`sk="ORDER"`) is unconditionally idempotent: DynamoDB overwrites an existing item with the same primary key without error.
- `query_order_rows` is a read and is always idempotent.
- The caller fixes (adding `"sk": "ORDER"` to existing write sites) are purely additive; replaying a write produces the same DDB item.

The smoke pytest in Section 9 verifies idempotency by calling `put_order_header` twice with the same `order_id` and asserting only one item exists in the base table for that key.

### Security

ORD-003 adds no new API surface. The only security-relevant aspect is that the `returns_rma._get_order` fix must not introduce a regression: after the fix, the function still returns `None` (not an exception) for a missing order, which is the existing contract checked by callers.

Ownership enforcement — verifying that `order["user_id"] == caller_sub` — is not implemented in ORD-003 (it belongs to the ORD-011 router). The `order_store.py` helpers expose raw DDB items; callers in downstream tickets are responsible for ownership checks before returning items to API clients.

## 8. Backward Compatibility & Migration

### Dev environment

`just restart` calls `scripts/local-stack-down.sh` + `scripts/local-stack-up.sh` + `scripts/local-ddb-init.py`. The `orders` table is dropped and recreated with the new `TableDef` (PK `order_id`, SK `sk`, five GSIs, `attr_types`). No migration script is needed. All E2E sessions are re-seeded by `e2e_session_setup.py` and `e2e_admin_session_setup.py`, which do not write to the `orders` table.

### Production deployment sequence

1. **Deploy the `_ensure_table` update** (new `TableDef` with five GSIs, no `sk` base sort key change — DDB `UpdateTable` can add new GSIs to an existing table). This is safe because the new GSIs receive no writes until the lifecycle flag is on, and `_ensure_table` skips existing indexes.

2. **Validate GSIs are ACTIVE** by waiting for DynamoDB to finish backfilling (may take minutes on a large table). `_ensure_table` already calls `client.get_waiter("table_exists")` after each `UpdateTable`. [verified: `local-ddb-init.py:2573`]

3. **Add the base sort key (`sk`)** — this requires a table migration, not a schema change via `UpdateTable`. Steps:
   a. Run migration script: scan `orders` table; for each item lacking `sk`, call `update_item` with `UpdateExpression="SET sk = :v"`, `ExpressionAttributeValues={":v": "ORDER"}`, `ConditionExpression="attribute_not_exists(sk)"`. This is idempotent.
   b. Deploy `orders` table definition with `sort_key="sk"`. In a blue/green deployment the new task definition replaces the old. DynamoDB table definitions are not changed by deploying app code — the physical table schema is already correct after step (a).

4. **Deploy caller fixes** (`file_bundle_checkout.py`, `returns_rma.py`, `commerce_order_service.py`) in the same app deploy as step 3. The write-first then read pattern means:
   - Items written after the deploy include `sk="ORDER"`.
   - Items read after the deploy via `get_item(Key={order_id, sk=ORDER})` will find items that already have `sk="ORDER"` from migration or from new writes.

5. **Enable `ORDER_LIFECYCLE_ENABLED=true`** in a subsequent deploy after the migration is verified. Only at this point do `lifecycle_status` and `updated_ts` start populating `GSI_ORDER_STATUS`.

### Flag-off guarantee

With `ORDER_LIFECYCLE_ENABLED=false`:
- `commerce_order_service.create_order` writes exactly one `ORDER`-SK row per order, with no `lifecycle_status`, no `updated_ts`, and no HIST/SHIPGRP/ADJ rows. Verified by the golden-record test in Section 9.
- `returns_rma._get_order` now correctly passes `sk="ORDER"` in the key; for all migrated and new rows, this returns the same item it would have returned before ORD-003 (minus the `sk` field itself, which is invisible to the application).
- No new GSI writes happen.

## 10. Open Questions / Assumptions

1. **Assumption**: Adding `sk` as a base table sort key is an acceptable breaking schema change in prod, managed via the migration script (Section 8). An explicit ops-team sign-off on the migration window is required before ORD-003 is deployed to production.

2. **Corrected**: There are exactly **four** callers that write to or read from `T.orders` outside `commerce_order_service.py`: `file_bundle_checkout.py:98`, `returns_rma.py:107`, `subscription_cycle_orders.py:39`, and `commerce_order_service.py:85`. Verified by `grep -rn "T\.orders"` at spec review time. At implementation time, this grep must be re-run to confirm no additional callers were added since this spec was written.

3. **Assumption**: `order_items` rows do not need a `sk` field and will not be queried from the `orders` table. The `order_items` table retains its own PK/SK (`order_id`, `item_id`) and is never queried via the `orders` table. Confirmed by ORD-001 Section 3.5.

4. **Open question** (resolved by ORD-009): The `GSI_ORDER_SHIPDATE` PK is `ship_date_bucket` (a `YYYY-MM-DD` string derived from the SHIPGRP row's expected ship date). ORD-009 §5 defines `_ship_date_bucket(ship_ts)` as `datetime.fromtimestamp(ship_ts, tz=timezone.utc).strftime("%Y-%m-%d")` — UTC only, no user timezone. ORD-003 only declares the GSI; the write logic is ORD-009's responsibility.

5. **Assumption**: The `HIST#` SK zero-padding width of 20 digits (covering timestamps up to `99999999999999999999` seconds, far beyond any realistic epoch) is sufficient. This matches the approach recommended in ORD-001 Section 3.2 and follows the same pattern as `billing_shared.py:221` (`LEDGER#{ts}#{entry_id}`), which uses bare integer timestamps. Zero-padding is chosen for `HIST#` specifically because it enables lexicographic sort (all history rows in chronological order) without requiring a GSI, unlike the billing ledger.

6. **Assumption**: No new `Tables` dataclass fields or `_safe_table` handles are needed. All four row types share `T.orders`. If a downstream ticket requires an isolated handle for performance reasons (e.g., a long-running HIST scan), a new alias can be added to `tables.py` at that time.

7. **Open question**: Should `order_store.py` live in `app/services/` or `app/core/`? The rationale for `app/services/` is that it imports `T` directly and is a domain-specific accessor (not a general infrastructure utility). The rationale for `app/core/` is that it is a thin accessor with no business logic, similar to `cursor.py`. This spec places it in `app/services/` to be consistent with similarly thin domain accessors (`billing_shared.py`, `commercial_line_items.py`).

8. **Assumption**: The smoke pytest creates the DynamoDB GSIs with `BillingMode="PAY_PER_REQUEST"` (moto default) and does not specify throughput. moto does not enforce throughput limits; the omission is intentional and consistent with every other test in the codebase that creates in-memory tables.
