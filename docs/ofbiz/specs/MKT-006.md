# MKT-006 — Campaign lifecycle state machine

## 1. Summary & Goal

MKT-006 adds a validated status state machine to `app/services/marketing_campaigns.py` (introduced by MKT-004) so that campaign status can only advance through legal transitions. Concretely it delivers:

- A `_CAMPAIGN_TRANSITIONS` dict mapping each current status to the set of permitted next statuses, mirroring the exact structure used for ad campaigns at `app/services/ad_campaigns.py:16–24`.
- A `transition_campaign(owner_id, campaign_id, target_status, *, request=None)` function that (a) fetches the current campaign, (b) validates the transition is legal, (c) runs pre-activation guards when transitioning to `active`, (d) writes the new status atomically, and (e) emits an audit event.
- A `_validate_transition(current, target)` helper that raises a typed error for illegal moves.
- Pre-activation guards invoked only on `→ active`: window check (`start_date ≤ now ≤ end_date` when both are set) and linked-promo-code liveness check (`promo_codes.get_promo_code(id)["active"]` and `expires_at` not in the past).
- Audit events via `app/services/alerts.audit_event` for every legal transition (best-effort, never blocks the transition).
- HTTP 409 surfaced to callers on illegal transitions; HTTP 422 for pre-activation guard failures.

The ticket does not add a router; `transition_campaign` is called by the existing `update_campaign` path (MKT-004's `update_campaign` delegates to `transition_campaign` when `data.status` is set) and later by the dedicated transition endpoint added in MKT-011.

### Marketing campaign status values (MKT-001/MKT-003)

The MKT-003 spec (`docs/ofbiz/specs/MKT-003.md:75–79`) defines the marketing campaign status literals as:

```
"draft" | "scheduled" | "active" | "paused" | "completed" | "archived"
```

Marketing campaigns skip the `pending_review` / `rejected` peer-review path used by ad campaigns. The full transition graph is:

```
draft       → scheduled, active, archived
scheduled   → active, archived
active      → paused, completed, archived
paused      → active, archived
completed   → archived
archived    → (terminal — no outbound transitions)
```

This differs from the ad machine: `pending_review` and `rejected` do not exist; `scheduled` is an intermediate state where the campaign is committed to run but hasn't yet reached its `start_date`.

### `update_campaign` in MKT-004 (integration point)

`docs/ofbiz/specs/MKT-004.md:380–448` defines `update_campaign`. It explicitly defers status-transition validation:

> "The status field is accepted in the update payload; the transition is not validated here — that is MKT-006's responsibility."

After MKT-006 lands, `update_campaign` is modified to call `transition_campaign` when `data.status` is set, instead of writing the status field directly through the generic `update_item` expression builder.

## 3. Data Model

### No new DynamoDB tables

MKT-006 adds no new tables. All state is stored on the existing `MarketingCampaigns` table added by MKT-002.

### Attribute additions to the campaign META row

MKT-006 adds three new optional attributes written during transitions:

| Attribute | Type | Written when | Purpose |
|-----------|------|--------------|---------|
| `status_changed_at` | N (int) | Every legal transition | Timestamp of last status change; supports time-in-state analytics |
| `previous_status` | S (str) | Every legal transition | The status that was just left; enables rollback audit |
| `activated_at` | N (int) | Transition → `active` only | When the campaign first went live; sticky (not overwritten on re-activation after pause) |

`status_changed_at` and `previous_status` are overwritten on every transition. `activated_at` is written once via an `if_not_exists` expression: `activated_at = if_not_exists(activated_at, :now)`.

These attributes do not require GSI entries. They are projected onto `ByOwnerCreatedAt` and `ByStatusCreatedAt` automatically (both GSIs use `PROJECTION ALL`, per MKT-002 spec `docs/ofbiz/specs/MKT-002.md:121`).

### No `attr_types` additions needed

`status_changed_at` and `activated_at` are numeric but are not GSI sort keys — they are regular item attributes. The GSI sort key `created_at` already carries `attr_types={"created_at": "N"}` from MKT-002. No new `attr_types` entries are required in `scripts/local-ddb-init.py`.

### `_validate_transition(current, target)`

```python
class CampaignTransitionError(ValueError):
    """Raised when a campaign status transition is not permitted."""

def _validate_transition(current: str, target: str) -> None:
    """
    Raise CampaignTransitionError if transitioning from `current` to `target`
    is not a legal edge in _CAMPAIGN_TRANSITIONS.
    """
    allowed = _CAMPAIGN_TRANSITIONS.get(current, set())
    if target not in allowed:
        raise CampaignTransitionError(
            f"Cannot transition marketing campaign from '{current}' to '{target}'. "
            f"Allowed: {sorted(allowed) or 'none (terminal state)'}."
        )
```

`CampaignTransitionError` is a `ValueError` subclass so existing `except ValueError` handlers in the router catch it. The router maps it to HTTP 409 (see Section 4, endpoint layer).

### `_check_promo_liveness(promo_code_ids, ts)`

Pre-activation guard. Called only when `target_status == "active"`.

```python
class CampaignActivationError(ValueError):
    """Raised when pre-activation guards fail (e.g. inactive/expired promo code)."""
    def __init__(self, code: str, message: str) -> None:
        self.code = code
        super().__init__(message)

def _check_promo_liveness(promo_code_ids: list[str], ts: int) -> None:
    """
    Validate all linked promo codes are active and not expired at the given
    Unix timestamp `ts`.

    Raises:
        CampaignActivationError — first offending code found
    """
    from app.services.promo_codes import get_promo_code

    for code_id in promo_code_ids:
        promo = get_promo_code(code_id)
        if promo is None:
            raise CampaignActivationError(
                "promo_code_not_found",
                f"Linked promo code '{code_id}' no longer exists.",
            )
        if not promo.get("active", True):
            raise CampaignActivationError(
                "promo_code_inactive",
                f"Linked promo code '{code_id}' has been deactivated.",
            )
        exp = int(promo.get("expires_at") or 0)
        if exp > 0 and exp < ts:
            raise CampaignActivationError(
                "promo_code_expired",
                f"Linked promo code '{code_id}' expired at {exp}.",
            )
```

Logic mirrors `app/services/promo_codes.py:274–288` (the `validate_promo_code` active/expiry checks) but is local to MKT-006: `validate_promo_code` also checks max-uses and per-user limits, which are not relevant to campaign activation.

### `_check_window(start_date, end_date, ts)`

Pre-activation guard. Called only when `target_status == "active"`.

```python
def _check_window(
    start_date: int | None,
    end_date: int | None,
    ts: int,
) -> None:
    """
    Raise CampaignActivationError if the current time falls outside the
    campaign's declared run window.

    Rules:
    - If start_date is set and ts < start_date → not yet started
    - If end_date is set and ts > end_date → already ended
    - If neither is set → always valid (open-ended campaign)
    """
    if start_date and ts < start_date:
        raise CampaignActivationError(
            "window_not_started",
            f"Campaign window does not start until {start_date}; current time is {ts}.",
        )
    if end_date and ts > end_date:
        raise CampaignActivationError(
            "window_ended",
            f"Campaign window ended at {end_date}; current time is {ts}.",
        )
```

### `transition_campaign(owner_id, campaign_id, target_status, *, request=None)`

The primary public function added by MKT-006.

```python
def transition_campaign(
    owner_id: str,
    campaign_id: str,
    target_status: str,
    *,
    request=None,
) -> dict:
    """
    Transition a marketing campaign to `target_status`.

    Steps:
    1. Flag check (raises HTTPException 403 if module is disabled).
    2. Fetch current campaign (raises HTTPException 404 if not found).
    3. Validate the transition is legal (raises CampaignTransitionError on illegal move).
    4. Pre-activation guards when target_status == "active":
       a. Window check (_check_window).
       b. Promo-code liveness check (_check_promo_liveness).
    5. Atomic DynamoDB update_item writing new status, status_changed_at,
       previous_status, and (only once) activated_at.
    6. Best-effort audit event via app.services.alerts.audit_event.
    7. Return the freshly-fetched campaign item.

    Raises:
        HTTPException(403)      — module flag off
        HTTPException(404)      — campaign not found
        CampaignTransitionError — illegal status transition (caller maps to 409)
        CampaignActivationError — pre-activation guard failure (caller maps to 422)
    """
    _require_flag_enabled()

    existing = get_campaign(owner_id, campaign_id)
    if existing is None:
        from fastapi import HTTPException
        raise HTTPException(status_code=404, detail="Campaign not found")

    current_status = str(existing.get("status") or "draft")
    _validate_transition(current_status, target_status)

    ts = now_ts()

    if target_status == "active":
        start_date = existing.get("start_date")
        end_date   = existing.get("end_date")
        _check_window(start_date, end_date, ts)
        promo_code_ids = list(existing.get("promo_code_ids") or [])
        _check_promo_liveness(promo_code_ids, ts)

    # Atomic write: status + bookkeeping fields
    update_expr = (
        "SET #status = :target, "
        "previous_status = :prev, "
        "status_changed_at = :now, "
        "updated_at = :now"
    )
    expr_names  = {"#status": "status"}
    expr_values = {
        ":target":  target_status,
        ":prev":    current_status,
        ":now":     ts,
        ":current": current_status,   # for ConditionExpression
    }

    if target_status == "active":
        update_expr += ", activated_at = if_not_exists(activated_at, :now)"

    T.marketing_campaigns.update_item(
        Key={"pk": f"OWNER#{owner_id}", "sk": f"MKTCAMP#{campaign_id}"},
        UpdateExpression=update_expr,
        ConditionExpression="#status = :current",
        ExpressionAttributeNames=expr_names,
        ExpressionAttributeValues=expr_values,
    )

    # Best-effort audit event
    try:
        from app.services.alerts import audit_event
        audit_event(
            f"marketing.campaign.{target_status}",
            owner_id,
            request,
            outcome="success",
            campaign_id=campaign_id,
            previous_status=current_status,
            new_status=target_status,
            transition_at=ts,
        )
    except Exception:
        pass

    return get_campaign(owner_id, campaign_id) or existing
```

Key design decisions:

- **`ConditionExpression="#status = :current"`** — the conditional write guards against a concurrent transition. If another request changes status between the read and write, DynamoDB raises `ConditionalCheckFailedException`. The caller retries or the user sees a 409. This is preferable to a version-counter scheme (as used in `app/services/kyc_cases.py:228` ← VERIFIED) because marketing campaigns have no `version` field in MKT-004, and adding one now would be a data-model change outside this ticket's scope.
- **`if_not_exists(activated_at, :now)`** — `activated_at` is set once (first activation) and never overwritten on re-activation after pause. This matches the semantics of "when was this campaign first live".
- **`updated_at`** — kept in sync with every write, including transitions; consistent with `app/services/ad_campaigns.py:111` ← VERIFIED.
- **Audit event name** — `f"marketing.campaign.{target_status}"` produces `marketing.campaign.active`, `marketing.campaign.paused`, etc. Ad campaigns use an explicit `event_map` dict at `app/services/ad_campaigns.py:146–150` covering only three statuses (`ad.campaign.paused`, `ad.campaign.resumed`, `ad.campaign.completed`); the `→ active` transition is named `resumed` in the ads module, not `active`. MKT-006 uses a simpler f-string scheme covering all statuses uniformly — this is a deliberate deviation from the ads pattern.

### `update_campaign` modification (MKT-004 + MKT-006 integration)

After MKT-006 lands, `update_campaign` delegates status changes to `transition_campaign`:

```python
def update_campaign(owner_id, campaign_id, data):
    _require_flag_enabled()
    existing = get_campaign(owner_id, campaign_id)
    if existing is None:
        raise HTTPException(status_code=404, detail="Campaign not found")

    updates = {k: v for k, v in data.model_dump(exclude_none=True).items()}
    if not updates:
        return existing

    # Status transitions are delegated to transition_campaign
    if "status" in updates:
        target = updates.pop("status")
        transition_campaign(owner_id, campaign_id, target)
        # Re-fetch after transition before applying remaining field updates
        existing = get_campaign(owner_id, campaign_id) or existing

    if not updates:
        return get_campaign(owner_id, campaign_id) or existing

    # Apply remaining non-status field updates (same expression builder as MKT-004)
    ...
```

If only `status` is being changed, `updates` is empty after popping, and the function returns the post-transition item. If both `status` and other fields are being changed in one call, the transition fires first; subsequent field updates apply to the already-transitioned item.

## 5. Detailed Behavior & Edge Cases

### Full legal transition matrix

| From → | draft | scheduled | active | paused | completed | archived |
|--------|:-----:|:---------:|:------:|:------:|:---------:|:--------:|
| draft | — | ✓ | ✓ | ✗ | ✗ | ✓ |
| scheduled | ✗ | — | ✓ | ✗ | ✗ | ✓ |
| active | ✗ | ✗ | — | ✓ | ✓ | ✓ |
| paused | ✗ | ✗ | ✓ | — | ✗ | ✓ |
| completed | ✗ | ✗ | ✗ | ✗ | — | ✓ |
| archived | ✗ | ✗ | ✗ | ✗ | ✗ | — |

Terminal state: `archived` has no outbound transitions. Any attempted transition from `archived` raises `CampaignTransitionError` with message `"Allowed: none (terminal state)."`.

### Pre-activation guard ordering

The window check runs before the promo-code liveness check. Rationale: window validation is a local computation (no DDB reads beyond the already-fetched campaign row); promo-code liveness requires one `get_item` per linked code. Failing fast on the window check avoids unnecessary DDB reads.

### Window check edge cases

- **Only `start_date` set, no `end_date`**: campaign can activate at or after `start_date` with no expiry.
- **Only `end_date` set, no `start_date`**: campaign can activate immediately but must activate before `end_date`.
- **Neither date set**: window check is a no-op; open-ended campaign.
- **`start_date == end_date`**: the window is a single-second slot; `ts < start_date` fails first.
- **`start_date > end_date`** (malformed window written by a pre-MKT-006 direct DDB write): the start-date check fires first; if `ts >= start_date`, the end-date check then fires. This gracefully rejects activation without a panic.

### Promo-code liveness edge cases

- **Empty `promo_code_ids` list**: no codes to check; guard passes silently.
- **`promo_code_ids` contains a deleted code (DDB item gone)**: `get_promo_code` returns `None` → `CampaignActivationError(code="promo_code_not_found")`. This can happen if a promo code is hard-deleted after being linked.
- **Multiple invalid codes**: only the first offending code raises; the error message names that code.
- **Code with `expires_at = 0`**: treated as no expiry; always passes.

### `paused → active` re-activation

The `→ active` pre-activation guards run again on re-activation. A campaign that was paused because a promo code was deactivated cannot be re-activated until the code is re-activated. This is intentional and the correct semantics.

### Concurrent transition race

Two requests attempt `active → paused` simultaneously. Both read `status="active"`. The first writer's `ConditionExpression="#status = :current"` (`:current = "active"`) succeeds; the second writer sees `ConditionalCheckFailedException`. The caller (MKT-011 router) catches this as a `ClientError` and maps it to HTTP 409 with `detail="Concurrent status update conflict; please retry."`. MKT-006's `transition_campaign` does not catch `ConditionalCheckFailedException` itself — it propagates to the router, which adds a `try/except ClientError` block in MKT-011.

### `update_campaign` with only `status` field

When a `PATCH` body is `{"status": "active"}`, `update_campaign` pops the status, calls `transition_campaign`, and returns the result with no second write. The response body is the full post-transition campaign item, not just `{"ok": true}`.

### `update_campaign` with `status` + other fields

When `{"status": "active", "name": "Summer Sale"}` is passed, the transition fires first; if it raises (illegal transition, guard failure, or concurrent conflict), the name update is never applied. This "transition-first, then other fields" ordering ensures the item is never partially written.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### Dev/prod parity

There is no dev-mode branch in this ticket. `transition_campaign` is a pure DDB operation (one `get_item` + one `update_item`). `T.marketing_campaigns` is wired to DynamoDB Local in dev and real DynamoDB in prod — both via the same `_safe_table` handle. No mock path, no `S.dev_mode` check. This matches the SECOPS-007 requirement that the same code runs in both environments.

The audit-event call in dev writes to the `Alerts` DynamoDB Local table (the `audit_event` function at `app/services/alerts.py:644` ← VERIFIED always writes to `T.alerts` at `app/services/alerts.py:426` ← VERIFIED, which is DynamoDB Local in dev). No SES or external service is involved.

### Idempotency

`transition_campaign` is **not** idempotent in the HTTP-idempotency sense — calling it twice with the same `target_status` from the same `current_status` will succeed the first time and raise `CampaignTransitionError("archived → archived is not permitted")` on the second (since `archived` has no outbound edges). This is correct behavior.

However, the `ConditionExpression` on the `update_item` makes the write safe for concurrent retries: only one concurrent caller succeeds; the others get `ConditionalCheckFailedException`. The winning caller's result is consistent and the item is never left in a partial state.

### Security

- **Ownership check**: `transition_campaign` receives `owner_id` from the caller (`ctx["user_sub"]` in the router). The DDB read uses `PK=OWNER#{owner_id}`, so a user can only transition campaigns they own. There is no server-side ownership re-check inside the function — the PK scoping in the `get_item` and `update_item` is the access control.
- **No money paths**: MKT-006 never calls `new_ledger_entry`, `refund_payment`, or any billing function. Campaign activation/deactivation has no financial side-effect in this ticket.
- **Promo code exposure**: the pre-activation guard calls `get_promo_code(id)` which returns the full promo code item including `discount_value`, `creator_user_id`, etc. The guard reads these fields but never returns the promo code dict to the caller. The response is the campaign item, which already contains only `promo_code_ids` (opaque id list, not promo details).
- **Audit trail**: every legal transition writes an audit event with `outcome="success"`. Illegal transitions do not write audit events (they raise before reaching the audit call).

## 8. Backward Compatibility & Migration

### Data already in `MarketingCampaigns`

MKT-004 creates campaigns with `status: "draft"`. Those items lack `status_changed_at`, `previous_status`, and `activated_at`. All three new attributes are optional; they are only written during a transition. Existing items remain valid — `get_campaign` returns them without error; they just lack the new fields. `MarketingCampaignOut` must use `Optional[int] = None` and `Optional[str] = None` defaults for these fields (enforced by MKT-003's model conventions: `int = 0` for timestamps that default to zero, or `Optional[int] = None` for attributes that may be absent — `activated_at` uses `Optional[int] = None` since `0` would be a misleading "activated at epoch").

### No DDB table changes

No new GSIs, no new tables, no `UpdateTable` call needed. The `MarketingCampaigns` table definition in `scripts/local-ddb-init.py` (added by MKT-002) is unchanged.

### `update_campaign` function signature

The function signature added in MKT-004 does not change. The internal behavior changes (status field is no longer written through the generic expression builder), but callers using `update_campaign` see identical input/output contracts. The `MarketingCampaignUpdateIn` model's `status: Optional[str] = None` field continues to work.

### Before MKT-006 lands

This is acceptable for the dev/staging environment during the implementation window; the `MARKETING_CAMPAIGNS_ENABLED` flag defaults to off, so no production traffic is affected.

## 10. Open Questions / Assumptions

1. **Assumption: `scheduled` is a user-driven state, not time-driven.** The ticket description says `draft → scheduled` is a legal transition, but does not specify whether the system auto-transitions from `scheduled → active` when `start_date` arrives. This spec treats `scheduled` as a purely user-set marker; no background worker auto-advances it. If a background advancement is needed, that is a separate ticket (MKT-0xx).

2. **Assumption: `promo_code_ids` is only checked on `→ active`, not on `→ scheduled`.** The ticket description says "on transition to `active`, validate...linked promo codes are themselves active". Scheduling a campaign that references a not-yet-active promo code may be intentional (user plans to activate both on launch day). This spec applies the guard only to `active`.

3. **Assumption: window guard also applies on `paused → active` re-activation.** The ticket says "validate the campaign window" when transitioning to `active`. A re-activation after pause should respect the window; if the window has already ended, re-activation is refused. This spec implements it that way.

4. **Assumption: `CampaignTransitionError` maps to HTTP 409, not 400.** The ticket says "illegal transitions → 409/ValueError". HTTP 409 (Conflict) better describes a resource-state mismatch than 400 (Bad Request), and matches existing usage at `app/routers/content_boost.py:37` and `app/routers/privacy.py:231`. The choice also leaves 400 available for request-format errors.

5. **Assumption: `ConditionalCheckFailedException` from concurrent writes is surfaced as 409, not 500.** The router (MKT-011) must add a `try/except ClientError` block around `transition_campaign`. This is not explicitly stated in the ticket but is required for correct concurrent-write behavior.

6. **Open question: should `archived` campaigns be deletable or is `archived` the final resting state?** This spec treats `archived` as terminal (matching `app/services/ad_campaigns.py:23`: `"archived": set()`). Hard-delete is out of scope for MKT-006.

7. **Open question: should the transition endpoint be `POST /campaigns/{id}/transition` with a body, or `PATCH /campaigns/{id}` with `{"status": "..."}`?** Both are common REST patterns; the MKT-004 spec's `update_campaign` already accepts `status` as a patch field. This spec supports both: the PATCH path goes through `update_campaign` → `transition_campaign`, and MKT-011 may additionally add a dedicated `POST .../transition` endpoint. The service layer is the same either way.

8. **Assumption: `previous_status` and `status_changed_at` are not surfaced in `MarketingCampaignOut`** (MKT-003 models do not include them). They are internal bookkeeping visible to admins via raw DDB inspection or via MKT-011 admin endpoints, but not in the standard API response. MKT-003's `MarketingCampaignOut` can add them as optional fields in a non-breaking way if needed.
