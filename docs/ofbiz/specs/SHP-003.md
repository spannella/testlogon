# SHP-003 — Shipping Pydantic models

## 1. Summary & Goal

SHP-003 adds all request/response shapes for the Shipping/Logistics module to `app/models.py`. No service, router, or DynamoDB code is written here. The deliverable is a set of 15 Pydantic model classes appended after the Returns/RMA block at `app/models.py:630`, plus a dedicated pytest file (`tests/test_shp_003_models.py`) that round-trips every model with representative payloads and validates rejection of bad inputs.

The models encode four invariants locked in SHP-001:

1. Carrier codes are constrained to the five values supported by the module (`ups`, `fedex`, `usps`, `dhl`, `manual`), aligning with `CARRIER_TRACKING_URLS` at `app/services/carrier_tracking.py:10` plus `manual`.
2. Shipment statuses include the six values actually produced by `map_carrier_status` at `carrier_tracking.py:84` (`label_created`, `picked_up`, `in_transit`, `out_for_delivery`, `delivered`, `exception`), plus `returned` (listed in the docstring at line 87–88 but not yet emitted by any code path), extended with lifecycle states that precede carrier pickup (`draft`, `pending_fulfillment`) and explicit cancellation (`cancelled`).
3. Money fields use non-negative integer cents, consistent with `amount_cents` throughout the commerce stack (e.g. `app/models.py:652` — `ReturnLineOut.amount_cents: int = 0`; `app/models.py:823` — `ApiPackageSkuCreateIn.amount_cents: conint(ge=0, le=100000000)`; `app/services/commerce_order_service.py:81` — DDB item dict field).
4. Weight and dimension fields are non-negative, floating-point for dimensions, integer for weight in ounces.

With `SHIPPING_ENABLED=false` (the default introduced in SHP-002) these models are imported but never exercised — all shipping endpoints return 404 and no write paths are triggered. The models themselves are pure Pydantic and impose zero overhead on existing routes.

## 4. API / Service Design

SHP-003 has no endpoints and no service functions. Its complete output is the addition of 15 model classes to `app/models.py` and a pytest file. The model interfaces they expose to downstream tickets are:

### 4.1 Carrier catalog models

```python
class CarrierIn(BaseModel):
    carrier_code: str = Field(pattern=r"^(ups|fedex|usps|dhl|manual)$")
    display_name: str = Field(min_length=1, max_length=100)

class CarrierOut(BaseModel):
    carrier_id: str
    carrier_code: str
    display_name: str
    online_tracking: bool
    enabled: bool
    created_at: int   # Unix epoch seconds from now_ts()
    updated_at: int
```

`CarrierIn` is used as the request body for `POST /ui/shipping/carriers` (SHP-005). The `pattern` constraint encodes the five valid carrier codes; Pydantic raises `ValidationError` for any other value.

`CarrierOut` is the response body for GET/POST/PATCH on carriers. `online_tracking` is `True` for the four codes present in `CARRIER_TRACKING_URLS` (`carrier_tracking.py:10`) and `False` for `manual`. The `created_at` / `updated_at` timestamps are Unix integer seconds (`now_ts()`), consistent with the pattern on `ReturnOut.created_at` at `app/models.py:666`.

### 4.2 Ship method models

```python
class ShipmentMethodIn(BaseModel):
    method_code: str = Field(pattern=r"^(ground|express|overnight|economy|flat_rate)$")
    method_label: str = Field(min_length=1, max_length=100)
    base_rate_cents: int = Field(ge=0)
    currency: str = Field(default="usd", min_length=3, max_length=3)
    transit_days_min: Optional[int] = Field(default=None, ge=0)
    transit_days_max: Optional[int] = Field(default=None, ge=0)

    @model_validator(mode="after")
    def _transit_days_order(self):
        if self.transit_days_min is not None and self.transit_days_max is not None:
            if self.transit_days_min > self.transit_days_max:
                raise ValueError("transit_days_min must be <= transit_days_max")
        return self

class ShipmentMethodOut(BaseModel):
    carrier_id: str
    carrier_code: str
    method_code: str
    method_label: str
    base_rate_cents: int
    currency: str
    transit_days_min: Optional[int] = None
    transit_days_max: Optional[int] = None
    enabled: bool = True
```

`ShipmentMethodOut` does not inherit from `ShipmentMethodIn` to keep the field order clean (carrier identity fields come first in the response). The `model_validator` on `ShipmentMethodIn` rejects logically impossible transit-day ranges (e.g. min=5, max=2) at input time rather than in the service layer; this is the same defensive-validation approach used on `CatalogStockAdjustIn` at `app/models.py:566` (the `@model_validator(mode="after")` decorator line).

### 4.3 Rate estimation models

```python
class ShippingRateRequest(BaseModel):
    carrier_code: str = Field(pattern=r"^(ups|fedex|usps|dhl|manual)$")
    method_code: str = Field(pattern=r"^(ground|express|overnight|economy|flat_rate)$")
    weight_oz: int = Field(ge=0)
    destination_zip: str = Field(min_length=1, max_length=20)
    origin_zip: Optional[str] = Field(default=None, max_length=20)

class ShippingRateOption(BaseModel):
    carrier_code: str
    method_code: str
    rate_cents: int         # non-negative; 0 = free shipping
    currency: str
    transit_days_min: Optional[int] = None
    transit_days_max: Optional[int] = None
    estimated_delivery: Optional[str] = None  # ISO date string; set when transit days known

class ShippingRateQuote(BaseModel):
    request_id: str         # sha256(carrier_code|method_code|weight_oz|destination_zip)[:16]; stable per input
    options: List[ShippingRateOption]
    currency: str           # canonical currency for all options in this quote
    generated_at: int       # now_ts() at time of computation
```

`ShippingRateRequest` is accepted by `POST /ui/shop/shipping/estimate` (SHP-007) as the request body. `ShippingRateQuote` is the envelope; `options` contains one `ShippingRateOption` per enabled method that matches the filter. In SHP-006 the list always has at most one element (single-method estimate); multi-method batch is future scope.

The `request_id` is a deterministic hash of the rate inputs, making repeated calls to the estimate endpoint idempotent in the response body and cacheable by the caller.

`line_items` in `ShipmentIn` is `List[Dict[str, Any]]` rather than a typed sub-model because the service layer (`create_shipment` in SHP-008) validates contents (required `item_id`, `quantity`, optional `sku`) against the existing `T.order_items` rows. Using a typed inner model here would duplicate that validation and couple the models to the DB schema shape.

`ShipmentOut.status` is a plain `str` (not `Literal`) to avoid having to update the models file if the status machine gains a new state in a follow-up ticket. The service layer is the source of truth for transition legality; the response model just surfaces the raw value.

### 4.6 Package models

```python
class ShipmentPackageContentIn(BaseModel):
    item_id: str = Field(min_length=1, max_length=64)
    sku: Optional[str] = Field(default=None, max_length=256)
    quantity: int = Field(ge=1)

class ShipmentPackageIn(BaseModel):
    weight_oz: int = Field(ge=0)
    length_in: Optional[float] = Field(default=None, ge=0.0)
    width_in: Optional[float] = Field(default=None, ge=0.0)
    height_in: Optional[float] = Field(default=None, ge=0.0)
    contents: List[ShipmentPackageContentIn] = Field(default_factory=list)

class ShipmentPackageOut(BaseModel):
    package_seq: str                        # 1-based padded string e.g. "00001"
    weight_oz: int
    length_in: Optional[float] = None
    width_in: Optional[float] = None
    height_in: Optional[float] = None
    contents: List[ShipmentPackageContentIn] = Field(default_factory=list)
    billed_weight_oz: Optional[int] = None  # computed by SHP-009; absent until packed
    created_at: int = 0
```

`ShipmentPackageContentIn` is used both in `ShipmentPackageIn.contents` (creation-time) and in `ShipmentPackageOut.contents` (read-back). The identical type for both directions is intentional: package contents are an immutable snapshot of what was packed; no separate `ContentOut` class is needed.

Dimensions are `Optional[float]` because not every carrier requires them for rate estimation; when all three are absent the service falls back to weight-only pricing.

`billed_weight_oz` is `None` at creation time and is set by the packing service (SHP-009) when dimensional weight is computed. Exposing it on the response model here allows SHP-009 to write it directly without a new output model.

## 5. Detailed Behavior & Edge Cases

### 5.1 Carrier code constraint scope

The pattern `r"^(ups|fedex|usps|dhl|manual)$"` is duplicated across `CarrierIn`, `ShipmentMethodIn` (only for methods, carrier code is on parent), `ShippingRateRequest`, `ShipGroupIn`, `ShipmentIn`, and `ShipmentTrackingUpdateIn`. This is intentional; each model is a standalone validation unit. A shared `VALID_CARRIER_CODES = Literal["ups", "fedex", "usps", "dhl", "manual"]` type alias would be cleaner but would require a module-level symbol that other files import, creating a coupling point. The pattern string is short enough to duplicate safely.

### 5.2 Shipment status values

The full set of valid status strings (validated by the service layer, surfaced as `ShipmentOut.status: str`) is:

| Status | Phase |
|---|---|
| `draft` | Pre-submission (not yet submitted to fulfillment) |
| `pending_fulfillment` | Order awaiting warehouse pick |
| `label_created` | Label printed; not yet picked up |
| `picked_up` | Carrier has package |
| `in_transit` | Moving through network |
| `out_for_delivery` | On delivery vehicle |
| `delivered` | Successfully delivered |
| `exception` | Carrier exception / delivery failure |
| `returned` | Returned to sender |
| `cancelled` | Shipment voided |

The first two (`draft`, `pending_fulfillment`) and the last (`cancelled`) are shipping-module additions. Of the seven tracking-phase statuses, six (`label_created`, `picked_up`, `in_transit`, `out_for_delivery`, `delivered`, `exception`) are the actual return values of `map_carrier_status` (`carrier_tracking.py:84`). `returned` appears in that function's docstring but is **not returned by any code path** — it is a shipping-module addition alongside `draft` and `cancelled`. Because `ShipmentOut.status` is `str` (not `Literal`), adding statuses to this list requires no model change, only documentation.

### 5.3 Transit-day validation

`ShipmentMethodIn` carries a `@model_validator(mode="after")` that rejects `transit_days_min > transit_days_max` when both are supplied. Neither field is required — carriers may not publish exact ranges. This validator fires only when both are non-`None`.

### 5.4 Currency field size

`ShipmentMethodIn.currency` is constrained to exactly three characters (`min_length=3, max_length=3`) to enforce ISO 4217 format (e.g. `"usd"`, `"eur"`). The service layer stores and returns currency lowercase; the model does not case-normalize — that is the service's responsibility, consistent with how `CommerceOrderService._currency` at `app/services/commerce_order_service.py:23` applies `.upper()` at the service layer.

### 5.5 `ship_to_address` as `Dict[str, Any]`

Both `ShipGroupIn.ship_to_address` and `ShipmentIn.ship_to_address` are `Dict[str, Any]` to accommodate the variety of address shapes in the system (`AddressBase`, `MailingAddress`, raw JSON from checkout). The SHP-008 service validates that at minimum `line1` and `country` are present. The design deliberately avoids tightening this to `AddressIn` at the model layer because address fields vary by market and the existing pattern (`PurchaseShippingIn.address` at `app/models.py:448`) is `Optional[Dict[str, Any]] = None` — the same loose-dict approach, just optional rather than required.

### 5.6 `ShipmentPackageOut.billed_weight_oz` = `None` at creation

When a Shipment is first created, packages have `billed_weight_oz = None`. The packing service (SHP-009) computes dimensional weight and writes it back. Any `ShipmentOut` returned before the packing pass is complete will include packages with `billed_weight_oz = None`. Consumers must treat `None` as "not yet computed" and must not use it for billing calculations until it is set.

### 5.7 `ShippingRateQuote.request_id` determinism

`request_id = sha256(f"{carrier_code}|{method_code}|{weight_oz}|{destination_zip}".encode())[:16]`. If the same inputs are submitted twice the quote response has the same `request_id`. This allows UI clients to detect that nothing changed between two sequential estimate calls without diffing the full `options` list.

### 5.8 `line_items` validation is service-side

`ShipmentIn.line_items` is `List[Dict[str, Any]] = Field(min_length=1)`. This ensures at least one element but does not validate item shape (required keys `item_id`, `quantity`). Reason: validating against the DDB schema requires a database lookup, which belongs in the service layer (SHP-008), not in a Pydantic model. The `Field(min_length=1)` guard prevents the obviously wrong case (empty shipment).

### 5.9 `model_rebuild` after `ShipmentOut`

With the recommended declaration order (§10/item-7: `ShipmentPackageContentIn` → `ShipmentPackageIn` → `ShipmentIn` → `ShipmentItemOut` → `ShipmentPackageOut` → `ShipmentOut`), only `ShipmentOut.packages: List["ShipmentPackageOut"]` needs a forward reference. A single `ShipmentOut.model_rebuild()` call after `ShipmentPackageOut` is defined resolves it. This follows the pattern at `app/models.py:12382` (`SignatureTemplateMigrationCheckIn.model_rebuild()`) and `app/models.py:12891` (`LaunchFromTemplateOut.model_rebuild()`).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007**: Pydantic models are environment-agnostic by definition. There are no `if S.dev_mode` branches and no mock-only model fields. The same `app/models.py` import is used in dev, test, and production.

**Idempotency**: Not applicable to models directly. The `ShippingRateQuote.request_id` (a deterministic hash of inputs) enables idempotency checking at the service call site without state.

**Security / input validation**:
- Carrier code and method code patterns use anchored regex (`^...$`) on `Field(pattern=...)`, which Pydantic evaluates at validation time before any service code runs. Unknown carrier codes never reach the database.
- `tracking_number` has `min_length=1` to prevent storing empty strings as tracking numbers.
- `weight_oz`, `length_in`, `width_in`, `height_in`, and `base_rate_cents` are all `ge=0` — negative physical measurements and negative rates are rejected at the boundary.
- `ship_to_address: Dict[str, Any] = Field(min_length=1)` on `ShipGroupIn` prevents an empty dict reaching address-parsing logic downstream.

**PII**: `ShipmentOut` and `ShipGroupOut` include `ship_to_address`, which may contain name and postal address. These models must not be logged at `INFO` level. The service layer is responsible for redacting PII from audit payloads; the model itself carries no `exclude` config because Pydantic `model_dump` exclusions are fragile across serialization paths.

**Existing models are untouched**: No existing `app/models.py` class is modified. The 15 new classes are appended under a new comment banner. No `model_rebuild()` calls on existing classes are added or removed.

**`PurchaseShippingIn` is not replaced**: The existing `PurchaseShippingIn` at `app/models.py:438` continues to be the shape for the transaction-level shipping sub-record on `purchase_transactions`. `ShipmentTrackingUpdateIn` is a separate shape for the new first-class Shipment entity. **No router registration**: SHP-003 adds no router. No import in `app/main.py` changes. No `include_router` call is added by this ticket. All that changes is `app/models.py` (15 new classes) and `tests/test_shp_003_models.py` (new test file).

**Forward reference resolution**: `ShipmentOut.model_rebuild()` is added near the bottom of the `# Shipping / Logistics` section, after `ShipmentPackageOut` is defined. This is additive — no existing `model_rebuild()` calls are disturbed.

**Declaration order and forward refs**: The recommended declaration order (§10/item-7) is `ShipmentPackageContentIn` → `ShipmentPackageIn` → `ShipmentIn` → `ShipmentItemOut` → `ShipmentPackageOut` → `ShipmentOut`. Only `ShipmentOut.packages: List["ShipmentPackageOut"]` needs a forward ref (resolved by `ShipmentOut.model_rebuild()` after `ShipmentPackageOut` is defined). The `model_rebuild()` follows the pattern at `app/models.py:12382` (`SignatureTemplateMigrationCheckIn.model_rebuild()`) and `app/models.py:12891` (`LaunchFromTemplateOut.model_rebuild()`).

## 10. Open Questions / Assumptions

1. **`ShipmentIn.ship_to_address` loose typing**: Assumed acceptable based on the precedent of `PurchaseShippingIn.address: Optional[Dict[str, Any]]` at `app/models.py:448`. If a tighter typed address sub-model is required, `AddressBase` at `app/models.py:1411` is the natural choice — but changing this later is a non-breaking addition (the service already validates address fields independently).

2. **Method code set is closed**: The pattern `^(ground|express|overnight|economy|flat_rate)$` is assumed to be the complete set for initial scope (per SHP-001 §3.2 table: `ground/express/overnight/economy/flat_rate`). If a new method code is needed (e.g. `same_day`), the pattern on `ShipmentMethodIn`, `ShipmentIn`, `ShipGroupIn`, `ShippingRateRequest`, and `ShipmentTrackingUpdateIn` all require updating. This could be replaced with `min_length=1, max_length=32` to make the set open, at the cost of pushing validation into the service layer.

3. **`ShipmentOut.status` as `str`**: Assumed intentional (not `Literal[...]`) to allow the status machine to evolve without model changes. If strict enum enforcement at the response layer is preferred, a `ShipmentStatus(str, Enum)` class can be introduced alongside the models, following the pattern of `PmIdeaStatus(str, Enum)` at `app/models.py:7828`.

4. **`packages` in `ShipmentIn` is optional**: Assumed that a Shipment can be created without packages (they may be added later via the packing endpoint in SHP-009). If package capture is required at creation time, `Field(min_length=1)` can be added to `ShipmentIn.packages`.

5. **`billed_weight_oz` on `ShipmentPackageOut`**: Placed here (rather than in a separate packing-phase model) on the assumption that SHP-009's packing response reuses `ShipmentPackageOut` directly. If SHP-009 introduces a distinct `PackedShipmentOut`, this field can be moved there without breaking anything.

6. **`ShippingRateQuote.request_id` computation**: The hash formula (`sha256(carrier_code|method_code|weight_oz|destination_zip)[:16]`) is defined here but actually computed in SHP-006's service layer. This spec assumes the service implements it exactly as described to make the `request_id` stable.

7. **Forward reference ordering in `app/models.py`**: The proposed declaration order is `ShipmentPackageContentIn` → `ShipmentPackageIn` → `ShipmentIn` → `ShipmentItemOut` → `ShipmentPackageOut` → `ShipmentOut` → `ShipmentOut.model_rebuild()`. This avoids forward references except for `ShipmentIn.packages: List["ShipmentPackageIn"]` (if declared before `ShipmentPackageIn`) — assumption is the ordering above is used so no forward reference is needed on `ShipmentIn`.
