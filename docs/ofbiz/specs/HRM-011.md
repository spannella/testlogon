# HRM-011 — Frontend types + endpoint wrappers

**Type:** Feature | **Priority:** P1 | **Estimate:** 2 days
**Milestone:** 4 — Frontend

---

## 1. Summary & Goal

HRM-011 delivers the two frontend integration artifacts that allow React pages (HRM-012) and vitest tests to speak to the HR/payroll HTTP surface defined by HRM-009:

1. **TypeScript interfaces** mirroring the nine Pydantic models in `app/models.py` (HRM-003): `PositionOut`, `EmploymentOut`, `PayrollRunOut`, `PayrollLineOut`, and their request counterparts. These are appended to `frontend/src/api/types.ts` under a new `// ─── HR / Payroll ───` section.

2. **Per-domain wrapper module** `frontend/src/api/endpoints/hr.ts` that exposes one typed async function per HRM-009 route (14 routes total), using the shared `api` client (`frontend/src/api/client.ts`) so that CSRF token injection, 401 auto-refresh, impersonation header forwarding, and toast error handling are inherited for free.

3. **Vitest unit test** `frontend/src/api/endpoints/hr.test.ts` that spies on `api.get`, `api.post`, and `api.patch` to assert that every wrapper builds the correct URL, serialises query params as strings, and passes the right request body — without touching real HTTP.

With both `S.hr_enabled` and `S.hr_payroll_enabled` off (the flags' defaults), the backend router returns 404 for all `/ui/hr/*` routes and the frontend will surface the `ApiError` thrown by `client.ts`; `hr.ts` itself is unconditionally importable regardless of flag state, because the feature flag is enforced server-side only.

### 2.3 `frontend/src/api/client.ts` — CSRF + auth injection

`frontend/src/api/client.ts` is the axios-equivalent fetch wrapper. Key properties relevant to HR:

- `api.get<T>(path, params?)` — attaches `Authorization: Bearer <accessToken>`, `X-CSRF-Token: <ui_csrf>`, and impersonation token automatically (`client.ts:165–182`).
- `api.post<T>(path, body?, params?)` — same headers; body is JSON-serialised via `body != null ? JSON.stringify(body) : undefined` (`client.ts:293–298`).
- `api.patch<T>(path, body?)` — same (`client.ts:306–310`).
- 401 auto-refresh (`client.ts:205–247`): one session refresh attempt, then logout.
- 403 geo-block + role error handling (`client.ts:250–266`): surfaces toast with human-readable message; `mapAuthorizationError` (`client.ts:34–64`) is called indirectly via `normalizeErrorDetail` (`client.ts:66–102`, called at `client.ts:263`).

The CSRF token is read from the `ui_csrf` cookie (`client.ts:179`), matching the backend's `enforce_cookie_csrf` contract. All non-GET wrappers (`api.post`, `api.patch`) therefore automatically satisfy the CSRF requirement for HR's non-GET endpoints with no additional work in `hr.ts`.

## 3. Data Model

HRM-011 introduces no DynamoDB tables or items. This ticket is purely frontend. All data schema is owned by HRM-002 (`T.hr` table) and HRM-003 (Pydantic models in `app/models.py`). The TypeScript interfaces defined here mirror those backend models at the API response layer.

The `api.get` function passes params to `URLSearchParams` (`client.ts:159–161`), so string serialisation must happen in the wrapper, not inside `client.ts`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Flag-off behavior in the frontend

When `S.hr_enabled = false`, the backend returns `HTTP 404 {"detail": {"code": "hr_disabled"}}` for every `/ui/hr/*` call. `client.ts` throws `ApiError(404, "hr_disabled")` (via the `!res.ok` branch at `client.ts:269–275`). React Query catches this in `onError` callbacks. `hr.ts` itself has no awareness of the flag — it is always importable and callable. The `ApiError` propagates to HRM-012's query error handlers. No special handling is needed in `hr.ts`.

### 5.2 403 for non-admin callers

`client.ts:250–266` handles 403 by extracting `detail.code` and calling `toast.error(detail)` (via `normalizeErrorDetail` at `client.ts:263`, which calls `mapAuthorizationError` internally at `client.ts:90`). The `mapAuthorizationError` function (`client.ts:34–64`) maps `code="role_required"` to a human-readable string. `hr.ts` wrappers do not suppress 403 errors — they propagate. HRM-012 may choose to hide the `/hr` route entirely for non-admins before attempting any API call (see HRM-012 gating requirements), which makes 403 from `hr.ts` a fallback for direct URL access only.

### 5.3 `listPositions` / `listEmployments` / `listPayrollRuns` — empty params

When `opts` is `undefined` or all opt fields are undefined/null, the `params` object is an empty `Record<string, string>{}`. `api.get(path, {})` builds a URL with no query string. The backend correctly returns the first page with default `limit=50`.

If `opts.limit` is explicitly `0`, `String(0)` = `"0"` is sent to the backend, which will fail Pydantic's `ge=1` validation and return 422. This is an intentional fast-fail from the server (not silently clamped). Callers are expected to pass positive limits or omit the field.

### 5.4 `updatePositionStatus` uses `api.patch`

`PATCH /ui/hr/positions/{id}/status` is the only HR endpoint using `PATCH`. `client.ts:301` implements `api.patch<T>(path, body?)` which sets `method: "PATCH"`. The CSRF token from `ui_csrf` cookie is attached automatically (same `headers.set("X-CSRF-Token", csrf)` block at `client.ts:179`). No special handling needed.

### 5.5 `terminateEmployment` returns 409 on re-terminate

The backend returns HTTP 409 `{"detail": {"code": "employment_already_terminated"}}` for a re-terminate. `client.ts:269–275` throws `ApiError(409, "employment_already_terminated")`. `hr.ts` does not catch this — it propagates to HRM-012's `useMutation.onError` callback. The HRM-012 page should display this as "Already terminated."

### 5.6 `approvePayrollRun` and `postPayrollRun` return 409 on bad transitions

Similarly, 409 `code="payroll_run_invalid_transition"` propagates. `hr.ts` does not attempt to parse transition error codes — that is HRM-012's responsibility.

### 5.7 `createPosition` / `createEmployment` / `createPayrollRun` respond 201

The HTTP response is 201 Created. `api.post` does not special-case 201 vs 200 — both go through the `res.json()` path at `client.ts:283`. The returned `PositionOut` / `EmploymentOut` / `PayrollRunOut` is returned normally.

### 5.8 `getPayrollRunLines` response shape

The backend returns `{"lines": [...]}`, not `{"items": [...]}`. `HrPayrollLinesOut` mirrors this with a `lines: PayrollLineOut[]` field (not `items`). The naming difference from list endpoints is deliberate (lines are subordinate to a specific run, not a paged top-level resource).

### 5.9 Correlation IDs in create requests

`CreatePositionIn`, `CreateEmploymentIn`, and `CreatePayrollRunIn` all carry an optional `correlation_id?: string`. HRM-012 may or may not supply these. When omitted (undefined), `api.post` will JSON-serialise them as absent keys (not `null`), which is what the backend expects (HRM-004/005/007 fall back to `uuid4().hex` when `correlation_id` is absent).

## 6. Feature Flag & Config

HRM-011 introduces no feature flags of its own. The relevant backend flags are:

| Backend setting | Env var | Default | Effect on frontend |
|-----------------|---------|---------|-------------------|
| `S.hr_enabled` | `HR_ENABLED` | `false` | `/ui/hr/*` returns 404; `hr.ts` calls throw `ApiError(404, "hr_disabled")` |

The frontend module `hr.ts` is unconditionally included in the bundle (no dynamic import or tree-shaking based on flag). The flag is enforced server-side only. **Local development:** set `HR_ENABLED=1 HR_PAYROLL_ENABLED=1` in `.env.local` and run `just restart` to activate the HR router with a fresh `hr` table.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 No dev-mode branch in `hr.ts`

`hr.ts` contains no `import.meta.env.DEV` or `VITE_*` conditionals. API paths are the same in dev (proxied to `http://localhost:8000` via Vite's config) and prod (same paths, different origin). The Vite proxy forwards `/ui` to the backend in dev, so `/ui/hr/positions` resolves identically. This is consistent with every other endpoint wrapper in `frontend/src/api/endpoints/`.

### 7.2 CSRF — inherited, not reimplemented

`client.ts:179` reads the `ui_csrf` cookie and sets `X-CSRF-Token` for every request. `hr.ts` never reads cookies, never constructs headers manually, and never bypasses `client.ts`. This is SECOPS-007-compliant: there is no dev-path that skips CSRF.

### 7.3 Bearer token / impersonation forwarding

Admin operators with active impersonation sessions carry `X-IMPERSONATION-TOKEN` from `useImpersonationStore` (`client.ts:173–175`). `hr.ts` inherits this automatically. An impersonating root operator can interact with HR APIs from a regular admin session context. The backend verifies the impersonation token independently; `hr.ts` does not need to know about it.

### 7.4 Type safety as a security property

Using `import type { ... } from "@/api/types"` with strict interfaces means TypeScript rejects calls where `pay_rate_cents` is a float string or `status` is an unknown enum value at compile time. This reduces the chance of sending malformed payloads that could trigger unexpected backend behaviour.

### 7.5 Idempotency at the frontend layer

`createPosition`, `createEmployment`, and `createPayrollRun` all accept an optional `correlation_id`. When HRM-012 supplies a deterministic `correlation_id` (e.g. generated once and stored in React state before the first submission attempt), retrying on network failure is safe — the backend conditional-put at `attribute_not_exists(PK)` is a no-op on replay. `hr.ts` exposes this field in the request type; it does not generate `correlation_id` itself.

## 10. Open Questions / Assumptions

1. **Assumption: `PayrollRunOut` includes a `line_count` field.** HRM-009 §4.5 references `line_count` in test case 18. The corresponding HRM-003 model spec does not explicitly list `line_count` on `PayrollRunOut`. If the backend service returns lines as a nested array (not a count), `PayrollRunOut` should include `lines?: PayrollLineOut[]` and the `HrPayrollLinesOut` wrapper becomes redundant. Verify the exact shape of `PayrollRunOut` returned by `hr_payroll.create_payroll_run` before finalising the TypeScript interface.

2. **Assumption: `PayrollLineOut` includes `party_id`, `pay_period`, and `pay_rate_cents` in addition to `employment_id` and `gross_cents`.** HRM-003 states "lines of `employment_id` → `gross_cents`" but the service likely returns a richer object. If the backend `PayrollLineOut` only has `employment_id` and `gross_cents`, the TypeScript interface must be trimmed accordingly.

3. **Assumption: all four list-endpoint envelope shapes use `items` + `next_cursor` exactly.** HRM-009 §5.5 confirms this: `{"items": [...], "next_cursor": null}`. If any service function uses a different key (e.g. `"positions"` instead of `"items"`), the corresponding TypeScript envelope interface and the wrapper's return type must be updated. Verify against the actual service layer implementations (HRM-005, HRM-006, HRM-007) before shipping.

4. **Assumption: `EmploymentOut.start_date` and `end_date` are Unix epoch integers (not ISO-8601 strings).** HRM-002 declares `start_date`/`end_date` as numeric GSI sort keys (`attr_types="N"`), and `now_ts()` returns integer Unix seconds. If the service layer converts these to ISO strings before returning, the TypeScript types must use `string` instead of `number`. Confirm from HRM-006 implementation.

5. **Assumption: `CreatePayrollRunIn.period_start` and `period_end` are Unix epoch integers.** Same concern as assumption 4. If HRM-007 uses ISO date strings for period boundaries (e.g. "2026-01-01"), the TypeScript type changes to `string`.

6. **Assumption: `approvePayrollRun` and `postPayrollRun` have no request body.** HRM-009 §4.5 shows no request body model for the approve/post endpoints. If HRM-007/008 require a `reason` or `actor_sub` body field (beyond what the authenticated session provides), the wrappers must accept a body parameter and the TypeScript request types must be added to `types.ts`.

7. **Assumption: `api.patch` is the correct HTTP method for `updatePositionStatus`.** HRM-009 §4.3 specifies `PATCH /positions/{position_id}/status`. `client.ts:301` exports `api.patch`. Confirm no HRM-009 implementation changed this to `PUT` before shipping `hr.ts`.

8. **Open question: should `updatePositionStatus` also accept a `correlation_id` in the body?** Status transitions are not currently idempotent in the same way as create operations (HRM-005 uses a state-machine gate, not `attribute_not_exists`). No `correlation_id` field is planned for `UpdatePositionStatusIn`. Confirm with the HRM-005 implementation before finalising.

9. **Assumption: `HrPayrollLinesOut` is a named interface (not an inline type).** HRM-012 will use this type with `useQuery<HrPayrollLinesOut>`. If HRM-009's implementation returns a different structure (e.g., `{"payroll_lines": [...]}` or `{"items": [...]}` for consistency), the interface must be renamed and the wrapper return type updated. Using a named interface (rather than `{lines: PayrollLineOut[]}` inline) makes the rename a single-file change.

10. **Assumption: the `BASE = "/ui/hr"` prefix is final.** HRM-009 §4.1 specifies `prefix="/ui/hr"`. If a future ticket moves the router prefix, both the router and `hr.ts` must be updated in tandem. Using the `const BASE` pattern (same as `contacts.ts:4`) ensures the change is a single-line edit in `hr.ts`.
