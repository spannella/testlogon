# ORD-009 — Ship groups

**Type:** Feature | **Priority:** P1 | **Estimate:** 3 days
**Milestone:** 3 — Adjustments & ship groups

---

## 1. Summary & Goal

ORD-009 adds ship-group support to the order lifecycle state machine introduced by ORD-003 through ORD-007. A ship group is a named logical shipment that owns a subset of an order's line items, carries its own fulfillment sub-status (`allocated → picking → packed → shipped`), and is associated with a shipping method and destination address. Ship-group status advances independently; the order header advances to `shipped` / `completed` only when every ship group has reached the corresponding terminal state.

The three public functions delivered are:

1. `create_ship_group(order_id, ship_method, address_id, item_ids, *, actor, ship_ts=None)` — writes a `SHIPGRP#{ship_group_id}` row to `T.orders`, validates item existence and exclusivity, and returns a `ShipGroup`.
2. `assign_items_to_ship_group(order_id, ship_group_id, item_ids, *, actor)` — atomically reassigns items between groups (merge-move pattern), rejecting double-assignment and unknown item refs.
3. `list_ship_groups(order_id) → List[ShipGroup]` — reads all `SHIPGRP#` rows for an order, newest-first by `sk`.
4. `advance_ship_group(order_id, ship_group_id, target_status, *, actor, reason)` — advances the per-group `ship_status`; when all groups reach `shipped`, calls `transition_order` to advance the order header to `shipped`.
5. `get_ship_group(order_id, ship_group_id) → ShipGroup` — fetches a single SHIPGRP row.

All functions are gated behind `S.order_lifecycle_enabled`. With the flag off, no function is reachable from any active code path and `T.orders` receives zero writes beyond those already present.

The default single-implicit-group behavior (no explicit `create_ship_group` call) is handled by the header roll-up logic: if no SHIPGRP rows exist for an order, `advance_ship_group` is not applicable and `transition_order` may be called directly by ORD-011. Callers that do not create ship groups work identically to before this ticket.

### 2.8 Deterministic ID pattern

`commerce_order_service.py:67` derives `order_id = sha256(correlation_id)[:32]`. ORD-005 derives `event_id = sha256(order_id|from|to|idempotency_key)[:16]`. ORD-009 uses `uuid4().hex` for `ship_group_id` (not a content-hash) because ship groups are imperative creates with no natural idempotency key from the caller — uniqueness is sufficient. A caller that needs idempotent creation passes a `correlation_id` field and ORD-009 derives `ship_group_id = sha256(order_id|correlation_id)[:16]`.

## 3. Data Model

### 3.1 Table: `orders` (no new tables)

All ship-group rows live in the existing `T.orders` table under the `SHIPGRP#` SK namespace introduced by ORD-003. No new DynamoDB table or `T` alias is needed.

**Table**: `orders` (env `ORDERS_TABLE_NAME`, default `"orders"`)
**Base PK**: `order_id` (S)
**Base SK**: `sk` (S) — added by ORD-003

### 3.2 SHIPGRP row schema

| Attribute | DDB type | Required | Description |
|---|---|---|---|
| `order_id` | S | always | PK — parent order |
| `sk` | S | always | `SHIPGRP#{ship_group_id}` |
| `ship_group_id` | S | always | `uuid4().hex` (or `sha256(order_id|correlation_id)[:16]` when idempotent create) |
| `ship_method` | S | always | Carrier/service code; defaults to `""` if not specified |
| `address_id` | S | optional | Opaque reference to `AddressOut.address_id` (`app/models.py:1428`) |
| `item_ids` | L | always | DynamoDB List of strings; empty `[]` = covers all items (implicit group) |
| `ship_status` | S | always | One of `created`, `allocated`, `picking`, `packed`, `shipped`, `cancelled` |
| `ship_date_bucket` | S | optional | `"YYYY-MM-DD"` UTC — `GSI_ORDER_SHIPDATE` PK; absent if ship date unknown |
| `ship_ts` | N | optional | Unix seconds of expected ship timestamp — `GSI_ORDER_SHIPDATE` SK; absent if unknown |
| `tracking_number` | S | optional | Carrier tracking number; set when status advances to `shipped` |
| `tracking_url` | S | optional | Carrier tracking URL |
| `created_at` | N | always | Unix seconds (`now_ts()`) |
| `updated_at` | N | always | Unix seconds (`now_ts()`); updated on every write |
| `actor` | S | always | `user_sub` or `"system"` who created/last updated the group |

**Note on `item_ids` storage**: DynamoDB `SS` (String Set) cannot be empty. `item_ids` is stored as `L` (List) so that an empty list is valid DDB storage. The `ShipGroup` Pydantic model (`docs/ofbiz/specs/ORD-004.md:163`) is neutral on this representation.

### 3.3 GSI_ORDER_SHIPDATE — populated by ORD-009

`GSI_ORDER_SHIPDATE` was declared in ORD-003 but receives no writes until ORD-009. It indexes `SHIPGRP#` rows only:

| Attribute | Type | Role |
|---|---|---|
| `ship_date_bucket` | S | GSI PK — `"YYYY-MM-DD"` derived from `ship_ts` in UTC |
| `ship_ts` | N | GSI SK — integer Unix seconds |

`attr_types={"ship_ts": "N"}` is already declared in `scripts/local-ddb-init.py` by ORD-003. ORD-009 must derive `ship_date_bucket` from `ship_ts` when writing:

```python
from datetime import datetime, timezone

def _ship_date_bucket(ship_ts: int) -> str:
    """Convert Unix timestamp to YYYY-MM-DD bucket (UTC)."""
    return datetime.fromtimestamp(ship_ts, tz=timezone.utc).strftime("%Y-%m-%d")
```

If `ship_ts` is absent, neither `ship_date_bucket` nor `ship_ts` is written to the row (GSI sparse population — no entry in `GSI_ORDER_SHIPDATE`).

### 3.4 Order header — `adjusted_ship_group_count` (informational)

ORD-009 does NOT write a denormalized ship-group count to the order header. The router (ORD-011) computes the list via `list_ship_groups` on demand. The header remains unchanged unless the roll-up logic calls `transition_order` (which updates `lifecycle_status` and `updated_ts` on the header via ORD-005).

_VALID_SHIP_STATUSES = {

def _item_to_ship_group(item: Dict[str, Any]) -> ShipGroup:

        tracking_number=item.get("tracking_number") or None,
        tracking_url=item.get("tracking_url") or None,
        created_at=int(item.get("created_at") or 0),

#### 4.1.4 `create_ship_group`

```python
def create_ship_group(
    order_id: str,
    *,
    ship_method: str = "",
    address_id: Optional[str] = None,
    item_ids: Optional[List[str]] = None,
    actor: str,
    ship_ts: Optional[int] = None,
    correlation_id: Optional[str] = None,
) -> ShipGroup:
    """
    Create a new ship group for an order.

    Parameters
    ----------
    order_id     : str   — The order's SHA-256-derived ID (32 hex chars).
    ship_method  : str   — Carrier/service code (e.g. "GROUND", "EXPRESS_2D").
    address_id   : str | None — Reference to user address (AddressOut.address_id).
    item_ids     : list[str] | None — Order item IDs to assign. None → implicit group (all items).
    actor        : str   — user_sub or "system".
    ship_ts      : int | None — Unix seconds expected ship timestamp; derives ship_date_bucket.
    correlation_id: str | None — Caller-supplied key for idempotent creation.

    Returns
    -------
    ShipGroup

    Raises
    ------
    OrderNotFoundError      — order_id header not found.
    ShipGroupItemNotFoundError — an item_id does not exist on the order.
    ShipGroupItemConflictError — an item_id is already assigned to another ship group.
    """
```

**Implementation steps**:

1. Read order header via `get_order_header(order_id)` from `app/services/order_store.py`. Raise `OrderNotFoundError` (from `app.services.order_lifecycle`) if absent.
2. Validate order is in a pre-shipped lifecycle state (i.e. `lifecycle_status` not in `{shipped, completed, cancelled, returned}`). Raise a typed `ValueError` if the order is terminal.
3. If `item_ids` is non-empty, validate each `item_id` exists in `T.order_items` via `T.order_items.get_item(Key={"order_id": order_id, "item_id": iid})`. Raise `ShipGroupItemNotFoundError` for any missing item.
4. Compute existing assignments: call `_get_assigned_items(order_id)` which calls `query_order_rows(order_id, sk_prefix="SHIPGRP#")` and returns `dict[item_id, ship_group_id]` for all currently assigned items. Raise `ShipGroupItemConflictError(item_id, existing_group_id)` for any duplicate.
5. Derive `ship_group_id`:
   - If `correlation_id` is provided: `ship_group_id = hashlib.sha256(f"{order_id}|{correlation_id}".encode()).hexdigest()[:16]`
   - Else: `ship_group_id = uuid.uuid4().hex`
6. Compute `ship_date_bucket` from `ship_ts` if present (UTC `YYYY-MM-DD`).
7. Build and write the SHIPGRP DDB item via `T.orders.put_item(Item=row)` where `row["sk"] = f"SHIPGRP#{ship_group_id}"`.
8. Emit audit event (best-effort): `audit_event("ship_group_created", actor, None, order_id=order_id, ship_group_id=ship_group_id, ...)`.
9. Return `_item_to_ship_group(row)`.

#### 4.1.5 `assign_items_to_ship_group`

```python
def assign_items_to_ship_group(
    order_id: str,
    ship_group_id: str,
    item_ids: List[str],
    *,
    actor: str,
) -> ShipGroup:
    """
    Replace the item_ids on an existing ship group.

    This is a merge-move: items previously assigned to this group are
    replaced with the new list. Items from *other* groups that appear
    in item_ids are rejected (use two calls: remove from old group first,
    then assign to new group).

    Raises
    ------
    ShipGroupNotFoundError
    ShipGroupItemNotFoundError
    ShipGroupItemConflictError   — item already assigned to a *different* group
    OrderNotFoundError
    """
```

**Implementation steps**:

1. Read the existing SHIPGRP row via `_get_ship_group_item(order_id, ship_group_id)`. Raise `ShipGroupNotFoundError` if absent.
2. Validate each `item_id` exists on the order (same as `create_ship_group` step 3).
3. Build the existing assignment map via `_get_assigned_items(order_id)`. For each requested `item_id`, if it maps to a *different* group (not `ship_group_id`), raise `ShipGroupItemConflictError`. Items currently assigned to this group are acceptable (in-place reassignment is a no-op).
4. Compute `updated_at = now_ts()`. Write updated `item_ids` list back to the SHIPGRP row via `T.orders.update_item(...)`.
5. Emit audit event (best-effort).
6. Return updated `ShipGroup`.

#### 4.1.6 `advance_ship_group`

```python
def advance_ship_group(
    order_id: str,
    ship_group_id: str,
    target_status: str | OrderLifecycleStatus,
    *,
    actor: str,
    reason: str = "",
    tracking_number: Optional[str] = None,
    tracking_url: Optional[str] = None,
) -> ShipGroup:
    """
    Advance ship_status for one group along the fulfillment arc.

    When all non-cancelled groups reach 'shipped', calls transition_order
    to advance the order header lifecycle_status to 'shipped'.

    Raises
    ------
    ShipGroupNotFoundError
    ShipGroupStatusError     — illegal ship_status transition
    OrderNotFoundError
    """
```

**Implementation steps**:

1. Read the SHIPGRP row. Validate `target_status` is a legal next state per `SHIP_GROUP_TRANSITIONS`.
2. Write `ship_status = target_status`, `updated_at = now_ts()`, plus optional `tracking_number` / `tracking_url` (only if `target_status == "shipped"`), via `T.orders.update_item(...)` with `ConditionExpression="ship_status = :current_status"` (optimistic concurrency at the group level).
3. If `target_status == "shipped"`: call `_check_order_rollup(order_id, actor)` — reads all SHIPGRP rows and checks if every non-cancelled group is `shipped`. If yes, calls `transition_order(order_id, "shipped", actor=actor, reason="all ship groups shipped")` from `app.services.order_lifecycle`. `OrderConflictError` from `transition_order` is caught and logged (best-effort: the group advance is not rolled back).
4. Emit audit event (best-effort).
5. Return updated `ShipGroup`.

#### 4.1.7 `list_ship_groups`

```python
def list_ship_groups(order_id: str) -> List[ShipGroup]:
    """
    Return all SHIPGRP rows for an order, newest-first by SK (lexicographic).
    Empty list if no ship groups exist.
    """
    rows = query_order_rows(order_id, sk_prefix="SHIPGRP#")
    # SHIPGRP#{ship_group_id} rows are sorted lexicographically by DynamoDB SK.
    # Reverse to present newest-created last, or leave in natural order.
    return [_item_to_ship_group(r) for r in rows]
```

#### 4.1.9 `_get_assigned_items` — internal helper

```python
def _get_assigned_items(order_id: str) -> Dict[str, str]:
    """
    Return a mapping of item_id → ship_group_id for every item
    currently assigned to any ship group on this order.
    """
    rows = query_order_rows(order_id, sk_prefix="SHIPGRP#")
    assigned: Dict[str, str] = {}
    for row in rows:
        sgid = row.get("ship_group_id", "")
        for iid in (row.get("item_ids") or []):
            assigned[str(iid)] = sgid
    return assigned
```

#### 4.1.10 `_check_order_rollup` — internal helper

```python
def _check_order_rollup(order_id: str, actor: str) -> None:
    """
    If all non-cancelled ship groups are 'shipped', advance the order header.
    Caller wraps in try/except — this is best-effort from advance_ship_group.
    """
    from app.services.order_lifecycle import transition_order, OrderNotFoundError, OrderTransitionError
    groups = list_ship_groups(order_id)
    if not groups:
        return
    active = [g for g in groups if g.ship_status.value != OrderLifecycleStatus.CANCELLED.value]
    if not active:
        return   # all groups cancelled; order cancellation is separate (ORD-010)
    if all(g.ship_status == OrderLifecycleStatus.SHIPPED for g in active):
        try:
            transition_order(
                order_id,
                OrderLifecycleStatus.SHIPPED,
                actor=actor,
                reason="all ship groups shipped",
            )
        except (OrderNotFoundError, OrderTransitionError):
            pass   # header already shipped or order in terminal state — no-op
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Default single-implicit-group behavior

The ticket requires: "a single implicit ship group covering all items when none is created." This is implemented by the **router/client**, not by a background task. When `list_ship_groups(order_id)` returns `[]`, the ORD-011 lifecycle endpoint returns `ship_groups=[]` in `OrderLifecycleOut`. The admin is expected to either (a) create an explicit group covering all items before advancing fulfillment, or (b) call `transition_order` directly from the ORD-011 router without using ship groups. The service does not auto-create an implicit group.

This design keeps the service stateless: `list_ship_groups` never mutates. The no-ship-group path retains the same `transition_order` → `shipped` flow from ORD-005 with no ORD-009 involvement.

### 5.2 Double-assignment guard — `_get_assigned_items` scope

`_get_assigned_items` reads all current SHIPGRP rows in one paginated `query_order_rows` call. Because DDB item reads are not transactional, two concurrent `create_ship_group` calls with overlapping `item_ids` could both pass the exclusivity check before either write completes. The probability is low (admin operations), and the consequence is a double-assignment that is correctable via `assign_items_to_ship_group`. If strict exclusivity is required, it can be enforced by a separate `item_assignments` DDB item (discussed in §10), but this is deferred.

### 5.3 Item count validation on `assign_items_to_ship_group`

When `item_ids` is empty in `assign_items_to_ship_group`, the call succeeds and clears the group's item list (making it an uncovered group). This is intentional: an admin may want to unassign all items from a group before deleting it (ORD-011 provides a delete endpoint). An empty group with `ship_status != SHIPPED` does not block the order roll-up (it is treated as "not contributing items").

### 5.4 Roll-up logic — all-groups-shipped

`_check_order_rollup` is called only when `target_status == "shipped"`. It reads all groups (including the one just updated). The "all active groups shipped" check uses the post-update state from the fresh `list_ship_groups` call, which reflects the just-written update. Because the group `update_item` completes before the roll-up check, the newly-shipped group's status is visible.

If a group is `CANCELLED` it is excluded from the roll-up check (a cancelled sub-shipment should not block the order). The order header is only advanced when `len(active) > 0 and all(g.ship_status == SHIPPED for g in active)`.

### 5.5 Order header state validation before creating ship groups

`create_ship_group` validates that `lifecycle_status` is not in `{shipped, completed, cancelled, returned}`. Creating a ship group on a terminal order is rejected with a clear error rather than silently writing orphan rows. Pre-shipped states (`created`, `approved`, `allocated`, `picking`, `packed`, `held`, `backorder`) are all valid — an admin may partition items across groups during any pre-ship phase.

### 5.6 `ship_ts` and `ship_date_bucket` — optional, not validated against current date

`ship_ts` is a forward-looking expected ship timestamp. It may be in the past (e.g. a ship date that was missed). The service does not validate `ship_ts >= now_ts()`. The `GSI_ORDER_SHIPDATE` index accepts any positive integer.

### 5.7 `tracking_number` / `tracking_url` only writable via `advance_ship_group`

Tracking info is attached when advancing to `shipped` (the `advance_ship_group` call accepts `tracking_number` and `tracking_url` only when `target_status == "shipped"`). Attempting to set them at group creation or on a non-shipping advance is silently ignored — the service strips these fields from the DDB write if `target_status != "shipped"`. This aligns with the OFBiz pattern of binding tracking to the ship event.

### 5.8 `created_at` / `updated_at` as integer Unix seconds

Unlike the order header which uses ISO-8601 strings for `created_at` (for backward compat with existing `GSI_USER` and `GSI_STATUS`), SHIPGRP rows use integer `created_at` / `updated_at` from `now_ts()`. This is consistent with the SST approach used in HIST rows (`ts N`) and across newer DDB items (instance monitoring timeline rows in `app/services/instance_monitoring.py`). The ORD-004 `ShipGroup` model reflects this with `created_at: int = Field(default=0, ge=0)`.

### 5.9 Lifecycle state check before `advance_ship_group`

`advance_ship_group` does not validate the order-level `lifecycle_status` before advancing the group status. The fulfillment arc operates independently of the order header (an order in `allocated` state may have ship groups advancing to `picking`). The only order-header check occurs at the roll-up point: if the order is already `shipped` or terminal, `transition_order` raises `OrderTransitionError`, which the roll-up helper catches and ignores (best-effort). This matches the OFBiz design where warehouse operations can outrun order-level status.

### 5.10 `correlation_id`-based idempotency for `create_ship_group`

If `correlation_id` is provided, `ship_group_id = sha256(order_id|correlation_id)[:16]`. A second `create_ship_group` call with the same `correlation_id` will attempt `put_item` with the same `sk="SHIPGRP#{ship_group_id}"`, overwriting the existing row (DynamoDB `put_item` is replace-on-key-match). For full idempotency, the caller should either check `get_ship_group` first or use a `condition_expression="attribute_not_exists(sk)"` guard. ORD-009 does not add this guard by default — the simpler re-put is a safe no-op when called with identical data, and the ORD-011 router should deduplicate at the HTTP layer via the `Idempotency-Key` header (a future concern).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

`order_ship_groups.py` contains no `if S.dev_mode` branch. All DDB writes go to `T.orders` (wired from `S.orders_table_name` at `app/core/settings.py:1124` [verified], resolving to DynamoDB Local port 8001 in dev and real DynamoDB in prod). The `audit_event` call resolves to `app/services/alerts.py:644` [verified: `alerts.py:644`] in both envs. `now_ts()` (`app/core/time.py:2` [verified]) is deterministic in tests via monkeypatching and uses real `time.time()` in prod.

### 7.2 Idempotency

- **`create_ship_group` with `correlation_id`**: deterministic `ship_group_id = sha256(order_id|correlation_id)[:16]`; replayed `put_item` overwrites with identical data (safe no-op when data is unchanged).
- **`advance_ship_group`**: conditional `update_item` guarded on `ship_status = :current_status`. A replay that arrives after a concurrent write raises a `ClientError(ConditionalCheckFailedException)` → caught and re-raised as `ShipGroupStatusError` (concurrent writes at warehouse level are rare).
- **Roll-up `transition_order`**: `OrderConflictError` and `OrderTransitionError` from the roll-up are caught and ignored — the group status is advanced regardless. The order header may be advanced by a concurrent call or already be in the target state.

### 7.3 Security

**Ownership enforcement**: `order_ship_groups.py` accepts `order_id` and `actor` and does NOT verify the caller owns the order. This is the ORD-011 router's responsibility (checking `order["user_id"] == user.sub` for owner-read endpoints). Admin/root write endpoints bypass ownership via `require_admin_or_root_csrf` (`app/auth/policy.py:100` [verified]). This mirrors the `app/services/kyc_cases.py` pattern where `KycCaseStore.apply_admin_decision` does not re-check admin ownership.

**DynamoDB injection prevention**: All attribute values are passed via `ExpressionAttributeValues`; no user-supplied values are interpolated directly into expression strings.

**`actor` sanitisation**: `actor` is written to the DDB item and audit event. It must be non-empty. The ORD-011 router derives `actor` from `ctx["user_sub"]` (authenticated session sub) for all calls.

## 10. Open Questions / Assumptions

1. **Assumption**: `app/services/order_store.py` (ORD-003) is merged and importable before ORD-009 implementation. If not, ORD-009 can inline the `query_order_rows` loop (same code pattern, remove when ORD-003 lands).

2. **Assumption**: `ShipGroup` Pydantic model (ORD-004) is appended to `app/models.py` before ORD-009. If ORD-004 is not yet merged, ORD-009 must inline or import from a local models stub.

3. **Assumption**: ORD-005 (`transition_order`) is importable from `app.services.order_lifecycle` at ORD-009 merge time. The roll-up helper uses a lazy local import to avoid circular dependencies (`from app.services.order_lifecycle import transition_order, ...` inside `_check_order_rollup`).

4. **Open question — Double-assignment concurrency**: The `_get_assigned_items` → `put_item` sequence is non-transactional. Two concurrent `create_ship_group` calls with overlapping items could both pass the read-check. Mitigation options: (a) accept the race at admin-only frequency with a compensating `assign_items_to_ship_group` call; (b) add a per-item `ITEMASSIGN#{item_id}` row per order using a `ConditionExpression="attribute_not_exists(sk)"` guard on `put_item` for strict exclusivity. Option (b) is deferred as a follow-up optimization.

5. **Assumption**: `item_id` values are the 1-based integer strings `"1"`, `"2"`, etc. from `commerce_order_service.py:88`. Any item_id supplied by the caller is validated against `T.order_items.get_item`. The service does not infer item IDs from the order line count.

6. **Open question — Implicit group auto-creation**: The ticket states "Default behavior: a single implicit ship group covering all items when none is created." The spec above handles this by allowing `transition_order` to be called directly (without ship groups) for the single-shipment case. An alternative is auto-creating an implicit group at order creation. This spec defers auto-creation — it adds complexity (a background task or create_order hook) without clear benefit for the common single-shipment case. Recommendation: implement the no-group path at the ORD-011 router level: if `list_ship_groups` returns `[]`, `advance_ship_group` returns 422 with `code="no_ship_groups"` and the admin calls `transition_order` directly.

7. **Assumption**: `OrderNotFoundError` from `order_lifecycle.py` is re-raised as-is by `create_ship_group` (no wrapping). The ORD-011 router maps all `OrderNotFoundError` instances to 404.

8. **Assumption**: `updated_at` on SHIPGRP rows is an integer (`now_ts()`), not an ISO string, consistent with ORD-004's `ShipGroup.updated_at: int`. This differs from the order header (`updated_at` is ISO string for backward compat). Tests must assert `isinstance(sg.updated_at, int)`.

9. **Open question — Partial order completion**: If one ship group is `shipped` and the other is `cancelled`, the order header is advanced to `shipped` (roll-up fires on the active group). Should a cancelled group prevent roll-up unless an admin explicitly marks the order as partially fulfilled? Recommendation: allow roll-up (partial ship is a valid fulfillment). The `ShipGroup.ship_status == CANCELLED` rows remain as audit evidence. Partial-cancellation refunds (ORD-010) are a separate concern.

10. **Assumption**: `advance_ship_group` uses a per-group optimistic concurrency guard (`ConditionExpression="ship_status = :current_status"`) at the DDB `update_item` call. A `ConditionalCheckFailedException` is caught and raised as `ShipGroupStatusError` so the ORD-011 router returns 409 for concurrent advance conflicts. This mirrors the ORD-005 approach for order-header transitions.
