# POS-012 — Frontend types & endpoint wrappers

**Type:** Feature | **Priority:** P1 | **Estimate:** 2 days
**Dependencies:** POS-011

---

## 1. Summary & Goal

POS-012 is the TypeScript counterpart to the POS-011 router. It delivers:

1. **TypeScript interfaces** in `frontend/src/api/types.ts` that mirror every
   Pydantic model introduced by POS-002 and POS-010 (`RegisterConfig`,
   `RegisterSessionOut`, `PosTransactionOut`, `TenderIn`, `TenderOut`,
   `TenderRequestIn`, `OpenSessionIn`, `CloseSessionIn`, `AddLineItemIn`,
   `RefundTxnIn`, `TenderBreakdownItem`, `SessionReportCashSection`,
   `SessionReportOut`). All monetary fields are `number` (integer cents, never
   strings or floats) and all timestamp fields are `number` (integer Unix seconds).

2. **Endpoint wrapper module** `frontend/src/api/endpoints/pos.ts` that wraps
   every POS-011 route using the shared axios-compatible `api` client from
   `frontend/src/api/client.ts`. The wrappers follow the same style as
   `frontend/src/api/endpoints/cart.ts` and `billing.ts`: plain async functions
   (no class, no side effects) that return typed promises and are consumed by
   React Query hooks in the page layer (POS-013).

With POS-012 complete, the POS-013 register terminal page can import
`@/api/endpoints/pos` and `@/api/types` without any `any` casts and without
knowledge of the HTTP layer. The deliverable is pure TypeScript — no React
components, no routes, no nav changes — those are POS-013's scope.

## 2. Context & Current State

### 2.1 Frontend API client

`frontend/src/api/client.ts` (`:151`) exports a typed `api<T>()` function with
convenience methods `api.get`, `api.post`, `api.put`, `api.patch`, `api.del`. The
function automatically:
- Attaches `Authorization: Bearer <token>` from `useAuthStore` (`:168–170`).
- Reads the `ui_csrf` cookie and injects `X-CSRF-Token` on every request
  (`:179–181`), satisfying the CSRF requirement for non-GET cookie-auth requests
  enforced by the POS-011 router.
- Handles 401 → session refresh → retry (`:205–248`).
- Throws typed `ApiError` on non-2xx (`:269–276`).

All POS wrappers use `api.post`, `api.get`, and `api.del` from this client.
No additional authentication plumbing is required because POS-011 uses standard
`require_ui_session` cookie auth — the same mechanism as every other
`/ui/` endpoint currently wrapped in `frontend/src/api/endpoints/`.

### 2.2 Existing type conventions (`frontend/src/api/types.ts`)

The file is 13 160 lines (`wc -l frontend/src/api/types.ts`). Relevant precedents:

- **Integer cents**: `CartItem.unit_price_cents: number` (`:2075`),
  `CartItem.line_total_cents: number` (`:2076`), `CartTotal.total_cents: number`
  (`:2090`), `CartPurchase.purchased_total_cents: number` (`:2098`). All POS
  monetary fields follow this convention.
- **Integer Unix timestamps**: `InventoryRecord.updated_at: number` (`:2171`),
  `CartSummary.last_activity_at?: number` (`:2031`). The POS-002 spec (§2.3)
  confirms all timestamps are integer Unix seconds via `now_ts()`.
- **Optional fields**: Fields that are nullable on the server use `?: T` (e.g.
  `CartPurchase.purchase_txn_id?: string` at `:2100`). POS session fields like
  `closing_float_cents`, `expected_cash_cents`, `counted_cash_cents`,
  `over_short_cents`, `closed_at` are nullable in `RegisterSessionOut` (POS-002
  spec §4.1) and map to `?: number`.
- **Literal union types**: `TenderIn.kind` is `Literal["cash","card","wallet"]`
  in Pydantic (POS-002 §4.2). The TypeScript mirror uses a string literal union:
  `"cash" | "card" | "wallet"`.
- **Array fields**: `PosTransactionOut.tenders: List[TenderOut]` maps to
  `tenders: TenderOut[]`.
- **OkResp**: Defined at `:2941` as `{ ok: boolean }`. Returned from the void
  endpoint; POS-013 can import it directly.
- **PaginatedList\<T\>**: Defined at `:2209`. Not used by POS routes (POS-011
  lists are unbounded arrays, not paginated), but documented for clarity.

No POS types exist yet in `frontend/src/api/types.ts` (confirmed by grep for
`RegisterConfig`, `PosTransaction`, `TenderIn`, `RegisterSession`).

### 2.3 Existing endpoint wrapper conventions

`frontend/src/api/endpoints/cart.ts` provides the canonical pattern:
- One file per feature domain, named after the domain.
- Named exports only (no default export).
- Each function is a one-liner calling `api.get<T>()` / `api.post<T>()` /
  `api.del<T>()` / `api.patch<T>()` with a URL literal and optional body.
- Path parameters are interpolated with template literals.
- Optional query parameters are passed as `Record<string, string>` (second
  argument to `api.get`).
- No React hooks, no side effects — pure async functions.
- Imports only from `@/api/client` and `@/api/types`.

`frontend/src/api/endpoints/billing.ts` shows the same pattern for a feature
with more endpoints, including a raw-typed inline response shape where no named
type is needed (`:71–77`).

There is no `frontend/src/api/endpoints/pos.ts` yet (confirmed by `ls

### 4.2 Wrapper function signatures

**Register configuration (admin-only routes)**

```ts
// POST /ui/pos/registers
export const createRegister = (body: Omit<RegisterConfig, "register_id" | "created_at" | "updated_at" | "created_by">) =>
  api.post<RegisterConfig>("/ui/pos/registers", body);

// GET /ui/pos/registers
export const listRegisters = () =>
  api.get<RegisterConfig[]>("/ui/pos/registers");
```

`Omit` removes the server-populated fields so the caller cannot accidentally
submit `register_id` or `created_at`. The server ignores them even if present,
but the type-level omission prevents mistakes in POS-013.

**Session lifecycle**

```ts
// POST /ui/pos/sessions/open
export const openSession = (body: OpenSessionIn) =>
  api.post<RegisterSessionOut>("/ui/pos/sessions/open", body);

// POST /ui/pos/sessions/{session_id}/close
export const closeSession = (sessionId: string, body: CloseSessionIn) =>
  api.post<RegisterSessionOut>(`/ui/pos/sessions/${sessionId}/close`, body);

// GET /ui/pos/sessions/{session_id}
export const getSession = (sessionId: string) =>
  api.get<RegisterSessionOut>(`/ui/pos/sessions/${sessionId}`);

// GET /ui/pos/sessions/{session_id}/report?kind=x|z
export const getSessionReport = (sessionId: string, kind: "x" | "z" = "x") =>
  api.get<SessionReportOut>(
    `/ui/pos/sessions/${sessionId}/report`,
    { kind },
  );
```

**Line items**

```ts
// POST /ui/pos/sessions/{session_id}/lines
export const addLineItem = (sessionId: string, body: AddLineItemIn) =>
  api.post<PosTransactionOut>(`/ui/pos/sessions/${sessionId}/lines`, body);

// DELETE /ui/pos/sessions/{session_id}/lines/{sku}
export const removeLineItem = (sessionId: string, sku: string) =>
  api.del<PosTransactionOut>(
    `/ui/pos/sessions/${sessionId}/lines/${encodeURIComponent(sku)}`,

```

`encodeURIComponent` on `sku` matches the pattern used for SKUs in
`frontend/src/api/endpoints/inventory.ts:14` (`encodeURIComponent(sku)`) to
handle SKUs containing `/`, `#`, or spaces.

**Tender**

**Void / refund**

**Receipt (PDF binary)**

```ts
// GET /ui/pos/txns/{txn_id}/receipt  → PDF bytes
export const getReceipt = (txnId: string): Promise<Blob> =>
  fetch(`/ui/pos/txns/${txnId}/receipt`, {
    credentials: "include",
    headers: (() => {
      const csrf = document.cookie.match(/(?:^|; )ui_csrf=([^;]*)/)?.[1];
      return csrf ? { "X-CSRF-Token": decodeURIComponent(csrf) } : {};
    })(),
  }).then((res) => {
    if (!res.ok) throw new Error(`Receipt fetch failed: ${res.status}`);
    return res.blob();
  });
```

The receipt endpoint returns `application/pdf` binary bytes
(`Response(media_type="application/pdf")` per POS-011 §2.6 and the CLAUDE.md
GAP-0209 binary-safe response gotcha). The `api()` client calls `res.json()` on
success (`client.ts:285`), which would corrupt binary PDF data. The receipt
wrapper therefore uses the raw `fetch` API with `credentials: "include"` and
manual CSRF header injection, returning a `Blob` that POS-013 can pass directly
to `URL.createObjectURL()` for an `<iframe>` or anchor download. This is the
only wrapper in the module that bypasses `api()`.

### 4.3 React Query hook conventions

POS-012 does not export hooks directly — hooks live in the page layer (POS-013).
The wrapper functions are designed so the following hook patterns work without
any additional glue:

```ts
// In POS-013 page component:
import { useQuery, useMutation, useQueryClient } from "@tanstack/react-query";
import {
  getSession, openSession, closeSession,
  addLineItem, removeLineItem, tenderSession,
  voidTransaction, refundTransaction,
  getSessionReport, getReceipt,
} from "@/api/endpoints/pos";

// Read queries
const sessionQuery = useQuery({
  queryKey: ["pos", "session", sessionId],
  queryFn: () => getSession(sessionId),
  enabled: !!sessionId,
});

const reportQuery = useQuery({
  queryKey: ["pos", "session", sessionId, "report", kind],
  queryFn: () => getSessionReport(sessionId, kind),
  enabled: !!sessionId && sessionClosed,
});

// Write mutations
const tenderMut = useMutation({
  mutationFn: (body: TenderRequestIn) => tenderSession(sessionId, body),
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: ["pos", "session", sessionId] });
  },
});
```

The `queryKey` scheme `["pos", "session", sessionId, ...]` mirrors the
`["carts"]` / `["catalog", "categories"]` naming in `pages/shop/Cart.tsx:52–55`
and `pages/shop/Catalog.tsx:32–47`.

## 5. Detailed Behavior & Edge Cases

### 5.1 CSRF on mutating wrappers

`api.post()` and `api.del()` both go through `api()` at `client.ts:151` which
reads `ui_csrf` cookie and injects `X-CSRF-Token` unconditionally (`:179–181`).
POS-011 enforces CSRF on all non-GET requests via `require_ui_session`. No
special handling is needed in POS-012 wrappers; this is automatic.

The receipt `fetch()` wrapper manually injects the CSRF header (`§4.2` above)
because it bypasses `api()`. If the `ui_csrf` cookie is absent (unauthenticated
user), the manual header is simply omitted — the server will reject the request
with 401, which is the correct behavior (the fetch fails and `PosTransactionOut`
is never decoded from binary PDF bytes).

### 5.2 Flag-off 404 propagation

When `S.pos_enabled` is false, every POS-011 endpoint returns HTTP 404. The
`api()` client at `client.ts:269–276` converts non-2xx responses to a thrown
`ApiError(status, detail)`. React Query's `useQuery` / `useMutation` surfaces
this as `error.status === 404`. POS-013 must handle this by checking whether
the user navigated to the POS route while the flag is off, displaying an
appropriate "POS not enabled" state. POS-012 itself has no special 404 handling.

### 5.3 Integer cents — no floating-point drift

All monetary `number` fields in `TenderIn`, `TenderRequestIn`, `OpenSessionIn`,
`CloseSessionIn`, and `RefundTxnIn` are integer cents. The POS-013 UI must
format them with `Intl.NumberFormat` (the same `formatCents` utility already
in `pages/shop/Cart.tsx:39–44`) and must never divide or multiply floats before
submitting. The wrapper functions carry no cent-conversion logic.

### 5.4 `idempotency_key` generation in the page layer

`TenderRequestIn.idempotency_key` is required (`min_length=1`). The wrapper
accepts whatever string POS-013 supplies. POS-013 is responsible for generating
a deterministic key per tender attempt, e.g.
`sha256(sessionId + "|" + cartTotal + "|" + Date.now())` for the first attempt,
then persisting that key in component state so retries (e.g. on network error)
re-use the same key and get idempotent replay from the server (POS-006 §AC).
The wrapper does not generate or validate the key.

### 5.5 Receipt blob handling

`getReceipt()` returns `Promise<Blob>`. POS-013 usage:

```ts
const url = URL.createObjectURL(blob);
window.open(url);    // or: <a href={url} download="receipt.pdf">Print</a>
// Revoke after use to free memory:
URL.revokeObjectURL(url);
```

Blob URLs are object-URL scheme (`blob:http://...`) and are immune to
CORS/cookie issues since the browser created them locally from already-fetched
bytes. The PDF is never decoded as text (no UTF-8 corruption — the GAP-0209
concern is fully handled on the server side).

### 5.6 `encodeURIComponent` on path segments

`removeLineItem` encodes the `sku` path segment (`encodeURIComponent(sku)`).
This must be consistent with whatever SKU format the catalog uses. `CatalogItem`
in `frontend/src/api/types.ts:2135` does not specify encoding constraints;
the existing `inventory.ts:14` precedent is followed. If POS-013 populates
line-item state from `CatalogItem.item_id` (a UUID, safe for URLs) rather than
a raw `sku` string, no encoding issues arise. Both `item_id` and `sku` are
supported by `AddLineItemIn`; POS-013 picks whichever the catalog picker returns.

### 5.7 Admin vs cashier — no role switching in the wrapper

`createRegister` and `listRegisters` are admin-gated on the server (POS-011
uses `require_admin_or_root_csrf`). The frontend wrappers do not carry role
metadata; attempting to call them as a non-admin user results in a 403
`ApiError` from `client.ts:263`. POS-013 renders the register-management panel
only for admin/root roles (checked via `useAuthStore`) and places the call
behind a role guard.

### 5.8 `voidTransaction` — no body

The void endpoint `POST /ui/pos/txns/{txn_id}/void` accepts no request body
(POS-011 §4.4). `api.post()` omits `JSON.stringify` when `body` is `undefined`
(`client.ts:294–298`):
```ts
api.post = (path, body?) =>
  api(path, { method: "POST", body: body != null ? JSON.stringify(body) : undefined });
```
Calling `api.post<PosTransactionOut>("/ui/pos/txns/X/void")` with no second
argument sets `body = undefined`, so no `Content-Type` header is added and the
request body is empty. The server handles this correctly.

### 5.9 `Omit<RegisterConfig, ...>` for create request

Using `Omit` on the create-register wrapper ensures the caller cannot pass
`register_id: null` explicitly (even though the server ignores it). TypeScript
will error at compile time if POS-013 accidentally includes a `register_id`
field. The `created_at`, `updated_at`, and `created_by` fields are similarly
omitted because they are server-populated timestamps.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007 parity

POS-012 is pure TypeScript with no `dev_mode` branches. The `api()` client
uses the same CSRF/auth mechanism in dev and prod. The only environment-aware
aspect is `VITE_API_BASE_URL` (used by `withApiBase` in `client.ts:7–14`), which
is set to `""` in dev (routing through the Vite proxy) and to the actual API
base in prod. This is pre-existing infrastructure, not introduced by this ticket.

### 7.2 Idempotency (client role)

The server enforces idempotency for the tender path via `idempotency_key`
(POS-006 §AC, POS-002 §5.7). POS-012's `tenderSession` wrapper forwards the
caller-supplied `idempotency_key` unchanged. The wrapper does not generate,
hash, or truncate the key. POS-013 is responsible for stable key generation and
persistence across retries (see §5.4).

For the other mutating endpoints (void, refund, close session), the server
enforces idempotency via conditional DDB writes. The wrappers make no special
accommodations — retrying a void that already succeeded returns the same
`PosTransactionOut` (the server replays the existing record), which React Query
surfaces as a successful mutation.

### 7.3 Security

- **No PEM/secrets transit.** The POS-012 wrappers handle only UUIDs, integer
  cents, and tender metadata. No cryptographic keys, no PII beyond what the
  existing session carries.
- **CSRF on all non-GET mutations.** Covered automatically by `api()` as
  described in §5.1.
- **Receipt URL is a local blob, not a pre-signed URL.** The PDF bytes are
  fetched once and converted to an object URL locally. No S3 pre-signed URL is
  exposed to the browser; the receipt content is only accessible to the
  authenticated session that fetched it.
- **No API key or X-User-Id bypass.** The POS-011 router uses `require_ui_session`
  (cookie+JWT). The wrappers use `credentials: "include"` so the session cookies
  are always sent. Bearer-token / X-User-Id paths are not supported by POS-011
  and are not attempted by these wrappers.

## 8. Backward Compatibility & Migration

### 8.1 Additive only

POS-012 appends new interfaces to `frontend/src/api/types.ts` (at or near
end-of-file) and adds one new file `frontend/src/api/endpoints/pos.ts`. It does
not modify any existing type, function, or import in any existing file.

With the change applied, existing tests and compilation units are unaffected:
no existing interface is renamed or extended, no existing wrapper is removed or
modified. TypeScript's structural typing means new exports are invisible to

## 10. Open Questions / Assumptions

1. **Assumption: Receipt endpoint is GET, not POST.** POS-011 §4.2 lists it as
   `GET /ui/pos/txns/{txn_id}/receipt`. The receipt wrapper uses `fetch()` with
   `GET`. If POS-013 requires a receipt format selection parameter (PDF vs HTML),
   the wrapper will need a `?format=pdf|html` query parameter and the server must
   be updated accordingly. Assumed: PDF-only for MVP.

2. **Assumption: `listRegisters` returns a plain array, not a paginated shape.**
   POS-011 §4.2 shows response as `List[RegisterConfig]` (plain array). Registers
   are expected to be few in number (one per physical lane). If the server
   returns a `PaginatedList<RegisterConfig>`, the wrapper return type must change
   to `PaginatedList<RegisterConfig>` (already defined at `types.ts:2209`).

3. **Assumption: `listRegisters` is admin-only and not needed from the cashier
   terminal.** The cashier terminal (POS-013) opens a session with a known
   `register_id` (selected at login or passed via URL param). The `listRegisters`
   wrapper is primarily for the admin register-management UI. If cashiers also
   need to enumerate available registers, the same endpoint serves both; CSRF
   is always attached by `api()`.

4. **Assumption: `TenderIn.change_due_cents` defaults to 0.** For card/wallet
   tenders the change is always 0; the interface marks it optional to match
   the typical send pattern. The server enforces that card/wallet tenders cannot
   have non-zero `change_due_cents` (POS-002 §5.2). The TypeScript interface
   does not re-enforce this — validation is server-side only.

5. **Assumption: `AddLineItemIn.sku` and `AddLineItemIn.item_id` are mutually
   exclusive at the server.** The Pydantic `model_validator` in POS-002 §4.2
   enforces this. The TypeScript interface does not replicate the mutual-exclusion
   constraint (TypeScript lacks dependent types for this pattern). POS-013 must
   ensure only one is set before submitting; the server returns 422 otherwise.

6. **Assumption: No `RegisterIn` type needed.** POS-011 §4.2 uses
   `RegisterConfig` (no `register_id`) as the create-request body. The spec
   models this as `Omit<RegisterConfig, "register_id" | "created_at" |
   "updated_at" | "created_by">` in the wrapper signature rather than defining
   a separate `RegisterIn` interface. If POS-013 needs to type a form state
   object distinctly, a `RegisterIn = Omit<RegisterConfig, ...>` named alias can
   be added to types.ts without changing the wrapper.

7. **Assumption: Receipt CSRF injection is correct with manual `fetch`.** The
   `getReceipt` wrapper manually reads `ui_csrf` from `document.cookie` to inject
   `X-CSRF-Token`. This mirrors the logic in `client.ts:16–19` and `:179–181`.
   If the cookie name or CSRF header name changes, both `client.ts` and
   `getReceipt` must be updated in lockstep. Assumed stable for the POS-013
   timeframe.

8. **Open question: Should `getReceipt` accept a format parameter?** The POS-009
   spec notes the receipt is always PDF for MVP. If POS-013 later needs an HTML
   preview (e.g. for screen display before printing), `getReceipt` signature
   would become `(txnId: string, format?: "pdf" | "html") => Promise<Blob |
   string>`. This change is backward-compatible (adding an optional parameter).
