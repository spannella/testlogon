**Type:** Chore | **Priority:** P1 | **Estimate:** 3 days

## 1. Summary & Goal

OFB-018 is the dedicated test layer for the four preceding accounting tickets
(OFB-013 through OFB-016). Its goal is to prove, in hermetic offline pytest
suites, that the GL system built by those tickets satisfies its stated
invariants — and to provide an E2E smoke test that confirms the ROOT-only
statements page renders a balancing trial balance in the real browser stack.

The deliverables are:

| File | Coverage |
|---|---|
| `tests/test_ofb_gl_accounts.py` | OFB-013: chart seed, account CRUD, disable-with-entries guard |
| `tests/test_ofb_gl_posting.py` | OFB-014: balanced entries, idempotent re-post, ledger-type mapping |
| `tests/test_ofb_gl_ar_ap.py` | OFB-015: AR/AP aging buckets, GL control-account tie-out |
| `tests/test_ofb_gl_statements.py` | OFB-016: trial balance equation, P&L, balance-sheet equation, dashboard reconciliation |
| `frontend/e2e/accounting.spec.ts` | E2E smoke: ROOT views the trial balance page and it visually balances |

Nothing in this ticket writes production code. Every assertion targets
interfaces delivered by OFB-013–016 (`app/services/gl_accounts.py`,
`app/services/gl_posting.py`, `app/services/gl_ar_ap.py`,
`app/services/gl_statements.py`) and their associated router endpoints.

### Existing OFB test pattern

`tests/test_ofb_returns_rma.py` and `tests/test_ofb_inventory.py` establish the
canonical offline isolation pattern used in this repo:

- `mock_aws()` context manager wraps `setUp`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Balanced-entry invariant (OFB-014 contract)

Every call to `post_journal_entry` must produce journal lines where
`Σ(amount_cents for line if direction=="debit") == Σ(amount_cents for line if direction=="credit")`. This is enforced inside `gl_posting.py` **before** writing to DynamoDB. A ledger row with an unmapped `type` must raise `KeyError` or a domain error, not silently produce a single-leg entry.

Tests in `test_ofb_gl_posting.py` must cover:
- A standard `catalog_purchase` → Dr Cash / Cr Sales Revenue, balanced.
- A `subscription_charge` with tax split → Dr Cash full / Cr Sales Revenue (net) / Cr Sales Tax Payable (tax), balanced.
- A `refund` → Dr Refunds/Returns (contra) / Cr Cash, balanced.
- A `platform_commission` → Dr Cash / Cr Platform Revenue, balanced.
- An **unknown** type → raises, no DDB write.
- A **dry_run=True** call → returns the would-be journal, writes nothing.

### 5.2 Idempotent re-posting (OFB-014 contract)

The `journal_id` is `sha256(source_entry_id)[:16]`. Writing the header uses a
DynamoDB conditional put: `attribute_not_exists(journal_id)`. A second call
with the same `source_entry_id` returns `None` (skipped), never writes a
duplicate journal entry, and increments the `skipped` counter in
`post_date_range` results.

Tests must call `post_journal_entry` twice on the same source entry and assert:
- Second call returns `None`.
- The `gl_journal` table contains exactly one header row for that `journal_id`.
- The debit/credit line count does not double.

### 5.3 AR aging correctness (OFB-015 contract)

Aging buckets based on `as_of_ts - due_date_ts`:
- **current**: due in the future (diff < 0).
- **1_30**: 0–30 days overdue.
- **31_60**: 31–60 days.
- **61_90**: 61–90 days.
- **90_plus**: > 90 days.

Tests in `test_ofb_gl_ar_ap.py` seed the `gl_ar_subledger` table directly with
open items straddling bucket boundaries (e.g. `due_date_ts = as_of_ts - 25*86400`
for the 1_30 bucket) and assert bucket totals match exactly.

The tie-out test calls `get_ar_control_account_balance()` and asserts it equals
`sum(all AR subledger open amounts)` within zero variance.

### 5.4 Trial balance equation

`compute_trial_balance(start_date, end_date)` must:
1. Query all journal lines in the date range via `GSI_BY_DATE`.
2. Aggregate debits and credits per account code.
3. Return `balanced = (total_debits == total_credits)`.
4. Raise `ValueError("trial balance out of balance")` if not balanced — this
   is a data-integrity failure and must never be silently swallowed.

Test fixture seeds a complete set of balanced journal entries (manually placed
in `gl_journal`) and asserts `balanced == True` and `total_debits == total_credits`.
A second fixture seeds a deliberately unbalanced entry (bypassing
`post_ledger_entry` via raw DDB put) and asserts the `GLTrialBalanceError` is raised.
<!-- CORRECTED (pass 3): post_journal_entry → post_ledger_entry; ValueError → GLTrialBalanceError. -->

### 5.5 Balance-sheet equation

Assets = Liabilities + Equity. The test fixture seeds account balances (via
journal lines) such that the equation holds exactly, then asserts
`balanced == True`. A separate fixture seeds a 1-cent imbalance and
asserts `GLBalanceSheetError` is raised.
<!-- CORRECTED (pass 3): equation_holds → balanced; OFB-016 raises GLBalanceSheetError on
     imbalance rather than returning equation_holds=False. Per OFB-016.md:502-534. -->

### 5.6 Income-statement / dashboard reconciliation

The test seeds ledger entries of types from `GMV_ENTRY_TYPES` and
`REVENUE_ENTRY_TYPES` (defined in
`app/services/platform_financial_dashboard.py:37-50`) into both the `billing`
<!-- CORRECTED: REVENUE_ENTRY_TYPES closes at line 50; line 51 is blank. -->
table and the corresponding posted GL journal lines. It then:
1. Calls `compute_income_statement(start_date, end_date)`.
2. Calls `_aggregate(_scan_ledger_entries(date_set={...}))` from
   `platform_financial_dashboard.py` to get the dashboard figure.
3. Asserts `variance_cents == 0` (zero tolerance for hermetic test data).

### 5.7 `disable_account` guard

Calling `disable_account("1000", actor_sub)` when `gl_journal` contains a `JL#` row
with `account_code = "1000"` must raise `HTTPException(409, "Cannot disable account with posted entries")`.
Calling it on an account with no posted entries sets `is_active = False` and `gsi_active = "false"` in DDB.
System accounts (`is_system=True`) raise `HTTPException(403)` regardless.
<!-- CORRECTED (pass 3): "LINE#" → "JL#" per OFB-014 schema; field is is_active (not enabled);

### 5.8 Flag-off guard

When `S.gl_double_entry_enabled == False`, all endpoints in the accounting

handler directly with the flag off and assert the 404/503 response.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**No AWS divergence**: The GL services introduced by OFB-013–016 must operate
identically against moto (dev) and real DynamoDB (prod). No `S.dev_mode`
branch is permitted inside `gl_accounts.py`, `gl_posting.py`, `ar_subledger.py`,
`ap_subledger.py`, or `gl_statements.py`. Tests verify behavior using moto-backed
tables; the same code runs in prod.
<!-- CORRECTED (pass 3): gl_ar_ap.py → ar_subledger.py + ap_subledger.py (OFB-015 split). -->

**Idempotency by deterministic ID**: The `journal_entry_id` is
`sha256(source_entry_id)[:24]` (24 hex chars), a pure function of the source ledger row.
The conditional-put `attribute_not_exists(PK) AND attribute_not_exists(SK)` means replay of
`post_ledger_entry` for the same row is a safe no-op. Tests assert this

## 8. Backward Compatibility & Migration

**Flag-off behavior**: With `GL_DOUBLE_ENTRY_ENABLED=false` (the default),
all GL service functions are dormant. The billing, cart, orders, and catalog
paths are byte-for-byte unchanged. No new DDB tables are required at startup
if the flag is off (the init script creates them but they remain empty).

**Additive-only table additions**: `gl_accounts`, `gl_journal`, and
`ar_ap_snapshots` (OFB-015 optional materialization) are new tables.
<!-- CORRECTED (pass 3): gl_ar_subledger does not exist; OFB-015 uses virtual derivation.
     ar_ap_snapshots is the only new OFB-015 table. -->
They never modify existing table schemas.
The `billing` table gains no new attributes; the GSI `GSI_LEDGER_DATE` is
already present in production (introduced by GAP-0202 / FIN-013, documented
in `scripts/local-ddb-init.py:64-77`).

**Backfill**: `post_date_range(start_date, end_date)` provides idempotent
historical backfill. Because journal IDs are deterministic, running backfill
multiple times is safe. The backfill is not automatically triggered at startup;
it is run on-demand by a ROOT-initiated API call or CLI command.

**DDB table creation order**: The three new tables must be added to
`scripts/local-ddb-init.py` before any `just up` run that enables the flag.
In production, `UpdateTable` is not required (new tables, not schema changes).
Running `local-ddb-init.py` is idempotent (existing tables are skipped via
`ResourceInUseException` catch).

## 10. Open Questions / Assumptions

1. **Journal ID collision probability**: Assuming `sha256(entry_id)[:16]` (8 bytes, 64-bit space) is sufficient for this platform's transaction volume (~millions, not billions). If collision resistance is a concern, extending to 32 chars should be discussed before OFB-014 implementation.

2. **Tax and fee split amounts**: The test suite assumes that a `catalog_purchase` ledger entry carries `meta.tax_cents` and `meta.fee_cents` fields. If OFB-014 decides not to persist sub-amounts on the ledger row and instead uses a fixed fee rate from `S`, the test fixtures must be updated accordingly.

3. **Dashboard reconciliation tolerance**: The income-statement reconciliation test uses `variance_cents == 0` for hermetic data. The production tolerance constant (for float/Decimal rounding) is assumed to be defined in `gl_statements.py` as `DASHBOARD_RECONCILE_TOLERANCE_CENTS = 0` (strict) or a small value like `1`. OFB-016 must declare this constant explicitly.

4. **AR subledger derivation timing** — **RESOLVED (pass 3)**: OFB-015 definitively chose virtual/on-the-fly derivation. There is no `gl_ar_subledger` table. `test_ofb_gl_ar_ap.py` must seed `T.invoices` and `T.creator_payouts` directly and call the derivation functions (`compute_ar_aging`, `compute_ap_aging`) in `ar_subledger.py` / `ap_subledger.py`. The §3 schema section has been corrected. Tests must set `S.ar_ap_subledgers_enabled = True` (not `S.gl_double_entry_enabled`).

5. **`post_date_range` driving mechanism**: The background GL poster (OFB-014) drives from `GSI_LEDGER_DATE`. This spec assumes `post_date_range` is also callable as a synchronous function (not only via background task) so the E2E `beforeAll` can prime the journal via a `POST /ui/admin/accounting/backfill` endpoint. If the router does not expose a synchronous backfill endpoint, the E2E fixture must seed the journal table via DDB directly (as `e2e_session_setup.py` does for sessions).

6. **`require_root_session` vs `require_root`** — **RESOLVED**: Use `Depends(require_root)` imported from `app.auth.policy`. This is the pattern used by `platform_financial_dashboard.py:167` and other admin-dashboard routers (e.g., `fraud_detection.py`, `billing_config.py`). `require_root_session` (`app.auth.deps:308`) is a separate, older dependency used primarily by tenant-admin endpoints. Do not mix them.

7. **Balance-sheet equity derivation**: Equity = retained earnings = cumulative net income less distributions. The test fixture seeds equity directly. If OFB-016 computes equity dynamically (P&L accumulation), the balance-sheet test must provide a longer history fixture. This spec assumes a simple seeded value for the unit test.

8. **`gl_ar_subledger` vs on-the-fly compute** — **RESOLVED (pass 3)**: OFB-015 spec (`OFB-015.md:§1`) definitively chose the on-the-fly approach. No `gl_ar_subledger` table exists. All aging tests seed `T.invoices` and `T.creator_payouts` directly. §3 schema corrected accordingly.
