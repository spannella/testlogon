# ECM-003 — Storefront integration Pydantic models

**Type:** Feature | **Priority:** P0 | **Estimate:** 2 days  
**Dependencies:** ECM-001 (surface map), ECM-002 (flag scaffold)

---

## 1. Summary & Goal

ECM-003 introduces four new Pydantic response models into `app/models.py` that serve as the shared response contract for the entire ECM integration layer. Every downstream ticket (ECM-004 through ECM-012) serialises its output into one of these shapes; this ticket defines them once, upfront, so later tickets only import rather than invent.

The four models are:

- `StorefrontVariantOut` — a single product variant (SKU, option selections, per-variant effective price, optional availability inline).
- `StorefrontAvailabilityOut` — reservation-adjusted availability projection for one SKU/location pair.
- `CartPricingBreakdownOut` — itemised pricing breakdown for a cart: subtotal, applied pricing-rule lines, discount total, final authoritative total.
- `OrderFulfillmentStatusOut` — post-purchase order state: lifecycle phase, ship groups, and tracking numbers.

Two existing models gain additive optional fields:

- `CatalogItemOut` (`app/models.py:672`) gains `variants` and `availability` (both `Optional`, default `None`).
- `ShoppingCartTotalOut` (`app/models.py:982`) gains `pricing_breakdown` (`Optional`, default `None`).

All new fields are `Optional` with safe defaults so existing serialisers and tests remain byte-for-byte unchanged when `STORE_INTEGRATION_ENABLED` is off. This ticket produces **no new DynamoDB tables, no new routes, and no new settings keys** — those belong to ECM-002 (flags) and later tickets.

## 2. Context & Current State

### 2.1 Existing catalog response shape

`app/models.py:672–688` defines `CatalogItemOut`. All fields are required scalars except `description`, `creator_id`, `stock_count`, `stock_updated_at`, and `position`, which carry `Optional` defaults. There is no variant dimension, no per-location availability, and no pricing-rule breakdown anywhere in the model today.

`app/routers/catalog.py:107–127` defines `_catalog_item_out(item: dict)` which constructs a `CatalogItemOut` directly from the raw DynamoDB item stored in `T.catalog`. The stock badge logic at `catalog.py:94–104` (`_compute_stock_status`) emits four string values: `"unlimited"`, `"in_stock"`, `"low_stock"`, `"out_of_stock"`. These are the only status tokens the frontend (`Catalog.tsx:180`) currently recognises.

### 2.2 Existing cart total shape

`app/models.py:982–985` defines `ShoppingCartTotalOut` with three fields: `cart_id: str`, `total_cents: int`, `currency: str = "USD"`. The router at `app/routers/shoppingcart.py:169–172` constructs it by calling `cart_total_cents(user_sub, cart_id)` from `app/services/shoppingcart.py:301–303`, which is a plain sum of `line_total_cents` across cart items. No pricing rule engine is consulted; the only discount path is the promo-code block inside `purchase_cart` (`shoppingcart.py:549–576`) which runs at purchase time only, not at total-display time.

`ShoppingCartPurchaseOut` (`app/models.py:993–1004`) already carries `discount_cents` and `promo_code_id` at the post-purchase level — but not the breakdown of which rule lines produced that discount. The new `CartPricingBreakdownOut` fills this gap at pre-purchase / cart-total time.

### 2.3 Existing inventory / availability shapes

`app/models.py:584–628` defines `InventoryRecordOut` and `ReservationOut`. `InventoryRecordOut` carries `sku`, `location_id`, `on_hand`, `reserved`, `available`, `reorder_point`, `status`, and `updated_at`. This is the internal service-layer shape returned by `app/services/inventory.py:get_inventory`.

The new `StorefrontAvailabilityOut` is a **storefront-facing projection** of `InventoryRecordOut` — it drops `location_id`, `reorder_point`, and `updated_at` (not relevant to browse), and promotes `low_stock: bool` as a convenience flag instead of requiring the frontend to implement the `<= reorder_point` comparison client-side.

### 2.4 Inventory service availability logic

`app/services/inventory.py:84–89` (`_status_for`) returns `"out_of_stock"` when `available <= 0`, `"low_stock"` when `available <= reorder_point`, and `"in_stock"` otherwise. `"low_stock"` corresponds to `low_stock: True` in the new model. The `stock_status` field on `StorefrontAvailabilityOut` mirrors this vocabulary, keeping it consistent with the existing `_compute_stock_status` tokens already known to the frontend (`catalog.py:94`).

### 2.5 Order / fulfillment — no existing storefront shape

`app/services/commerce_order_service.py:72–84` writes order records to `T.orders` with `status="pending_payment"` and no `lifecycle_status` or `fulfillment_status` field. `app/models.py:655–670` (`ReturnOut`) and `app/models.py:471–481` (`PurchaseTransactionInfo`) are the closest existing shapes, but neither carries ship groups or tracking numbers as a storefront buyer would need them. `PurchaseShippingIn` (`app/models.py:438–448`) carries individual tracking fields but is an admin-input model.

`OrderFulfillmentStatusOut` is thus net-new with no existing counterpart to reuse.

### 2.6 Variant topology — no existing storefront shape

No `StorefrontVariantOut`-equivalent exists anywhere in `app/models.py`. The PRD-001/PRD-007 tickets introduce product variants stored in `T.catalog_products` / `T.catalog_product_versions`, but those internal service models are not yet wired to the storefront. `StorefrontVariantOut` is the bridge model that ECM-004 will populate when `STORE_VARIANT_SELECTION_ENABLED` is on.

### 2.7 ECM-001 forward declarations

The ECM-001 spec (`docs/ofbiz/specs/ECM-001.md:163–204`) already contains pseudocode declarations for all four models in its Section 4.4. This ticket makes those declarations canonical by implementing them precisely in `app/models.py`. The pseudocode is authoritative except where this spec refines field types or validation constraints.

### 2.8 ECM-002 settings context

ECM-002 adds to `app/core/settings.py` (not yet merged): `store_integration_enabled`, `store_variant_selection_enabled`, `store_show_live_availability`, `store_apply_pricing_rules`, `store_show_fulfillment_status` (all `bool`, default `false`). ECM-003 does not read any of these flags; it only defines the response types that later flag-gated code paths return.

## 3. Data Model

ECM-003 introduces **no new DynamoDB tables and no new DDB rows**. It is a pure model definition ticket.

The four new models are pure Pydantic classes serialised to JSON by FastAPI's response serialiser. They carry no `PK`/`SK` and are never persisted directly. The additive fields appended to `CatalogItemOut` and `ShoppingCartTotalOut` are absent from the wire when `None` (FastAPI's default `response_model_exclude_none=False` behaviour means they serialise as `null` unless the router sets `exclude_none=True`, which is fine for optional enrichment).

### 3.1 `StorefrontVariantOut`

```
variant_id:         str          — opaque ID from PRD-007 variant record
sku:                str          — inventory/billing key (equals variant_id for flat products)
option_selections:  Dict[str, str]  — {feature_category_name: selected_value}
                                     e.g. {"Color": "Red", "Size": "M"}
price_cents:        int          — parent base price + sum of per-option deltas; ge=0
availability:       Optional[StorefrontAvailabilityOut] = None
                                 — populated by ECM-005 when STORE_SHOW_LIVE_AVAILABILITY on
```

`option_selections` is a flat string→string map rather than a typed list so the model stays forward-compatible with arbitrary feature category names added later (PRD-003 does not constrain category name vocabulary).

### 3.2 `StorefrontAvailabilityOut`

```
available:          int          — on_hand − reserved; may be 0 if oversold
on_hand:            int
reserved:           int
low_stock:          bool         — True when available > 0 AND available <= reorder_point
                                   (mirrors inventory._status_for logic)
stock_status:       str          — "in_stock" | "low_stock" | "out_of_stock"
                                   (reuses existing catalog.py vocabulary)
```

No `location_id`, `reorder_point`, or `updated_at` — these are internal fields not relevant to storefront display. The `low_stock` convenience bool avoids requiring the frontend to re-implement the threshold comparison.

`stock_status` maps to the same four-value vocabulary that `_compute_stock_status` (`catalog.py:94`) and `_status_for` (`inventory.py:84`) already emit, so the existing `Catalog.tsx:180` badge logic requires no change.

### 3.3 `CartPricingBreakdownOut`

```
cart_id:            str
subtotal_cents:     int          — raw sum of line_total_cents (no discounts applied)
applied_rules:      List[AppliedPricingRuleLineOut] = []
                                 — ordered list of rule lines that reduced the total
discount_cents:     int = 0      — sum of all rule line amounts; ge=0
final_total_cents:  int          — subtotal_cents − discount_cents; the authoritative total
                                   used at purchase by ECM-010 (must equal what purchase_cart charges)
currency:           str = "USD"
```

A sub-model `AppliedPricingRuleLineOut` is introduced in the same block:

```
AppliedPricingRuleLineOut:
  rule_id:          str          — from OFB-020 pricing rule record
  rule_name:        str
  discount_type:    str          — "percentage" | "fixed_amount" | "bulk" | "conditional"
  discount_cents:   int          — how much this rule reduced the total; ge=0
  applies_to_skus:  List[str] = []  — SKUs this rule line applied to (empty = cart-level)
```

`applied_rules` is typed as `List[AppliedPricingRuleLineOut]` (not `List[Dict]`) so callers get IDE type-checking and the spec is precise. When `STORE_APPLY_PRICING_RULES` is off, `applied_rules=[]`, `discount_cents=0`, and `final_total_cents == subtotal_cents`.

The invariant `final_total_cents == subtotal_cents - discount_cents` is enforced by a `@model_validator(mode="after")` on `CartPricingBreakdownOut`.

### 3.4 `OrderFulfillmentStatusOut`

```
order_id:               str
lifecycle_status:       Optional[str] = None   — ORD-005 state machine phase;
                                                  None when STORE_SHOW_FULFILLMENT_STATUS off
fulfillment_status:     Optional[str] = None   — SHP-014 shipping status;
                                                  None when upstream unavailable
ship_groups:            List[ShipGroupFulfillmentOut] = []
tracking_numbers:       List[str] = []         — convenience flat list across all ship groups
```

A sub-model `ShipGroupFulfillmentOut` is introduced in the same block (canonical name
per ESCALATIONS §A row 6 — ECM-003 owns the name; ECM-012 and ECM-014 align to it):

```
ShipGroupFulfillmentOut:
  ship_group_id:      str
  status:             str          — "pending" | "picked" | "packed" | "shipped" | "delivered"
  items:              List[str] = []   — SKUs in this ship group
  carrier:            Optional[str] = None
  tracking_number:    Optional[str] = None
  shipped_at:         Optional[int] = None   — Unix timestamp
  estimated_delivery: Optional[str] = None  — ISO date string
```

`tracking_numbers` is a computed convenience list (all non-None `tracking_number` values from `ship_groups`) for frontends that only need to show a single "Track your order" link. It is populated by the service layer (ECM-012), not by a model validator, so the model itself does not enforce consistency between `ship_groups` and `tracking_numbers`.

### 3.5 Additive fields on existing models

`CatalogItemOut` (`app/models.py:672`) gains at the end of the class body:

```python
# ECM-003: integration layer enrichment (default None = flag off / not enriched)
variants:      Optional[List[StorefrontVariantOut]] = None
availability:  Optional[StorefrontAvailabilityOut] = None
```

`ShoppingCartTotalOut` (`app/models.py:982`) gains:

```python
# ECM-003: pricing rules breakdown (None = flag off or rules not applicable)
pricing_breakdown: Optional[CartPricingBreakdownOut] = None
```

Both additions are additive. Existing serialiser call sites (`_catalog_item_out` at `catalog.py:110`, `ui_cart_total` at `shoppingcart.py:171`) construct these models by keyword, so the new optional fields receive their `None` defaults automatically — zero diff to those lines.

## 5. Detailed Behavior & Edge Cases

### 5.1 All flags off — zero behavioral change

When `STORE_INTEGRATION_ENABLED` is `false` (the default set by ECM-002):

- `CatalogItemOut.variants` is `None` in every response. The JSON payload gains a `"variants": null` key unless the router uses `response_model_exclude_none=True`; if that is undesirable, ECM-006 can set that flag on the enriched path only.
- `CatalogItemOut.availability` is `None`.
- `ShoppingCartTotalOut.pricing_breakdown` is `None`.
- No `OrderFulfillmentStatusOut` is returned anywhere (the route that returns it does not yet exist until ECM-007).

The current test suite (`tests/test_ofb_inventory.py`, `tests/test_catalog_inventory.py`, `tests/test_shoppingcart_*.py`) exercises the existing models directly. None of those tests construct `CatalogItemOut` or `ShoppingCartTotalOut` by positional argument, so adding keyword-only optional fields does not break them.

### 5.2 `CartPricingBreakdownOut` invariant enforcement

The model validator checks `final_total_cents == subtotal_cents - discount_cents`. Callers (ECM-009 `get_cart_pricing_breakdown`) must ensure arithmetic consistency before construction. If the pricing rules engine returns a fractional discount (e.g., percentage of an odd subtotal), the service layer must floor the `discount_cents` result and recompute `final_total_cents = subtotal_cents - discount_cents` — never the other direction — to avoid negative totals. `final_total_cents` has an implicit lower bound of 0 enforced by the validator: if `subtotal_cents - discount_cents < 0`, the validator clamps `discount_cents = subtotal_cents` and `final_total_cents = 0`. This mirrors the floor already in `_calculate_discount` at `app/services/promo_codes.py:376`.

### 5.3 `StorefrontAvailabilityOut` negative available

`available = on_hand - reserved` can be negative if a reservation race occurred before the oversell guard fired. The model must allow negative `available` (no `ge=0` constraint) so that a downstream caller can detect and surface this as `stock_status="out_of_stock"`. The `low_stock` bool is `False` when `available <= 0`; it is only `True` when `available > 0 AND available <= reorder_point`.

### 5.4 `StorefrontVariantOut` price_cents = 0

A free variant (zero price) is valid. `price_cents: int = Field(ge=0)` allows zero. Callers must not confuse `price_cents = 0` with "price unknown" — the latter is represented by a missing variant in the `CatalogItemOut.variants` list.

### 5.5 `OrderFulfillmentStatusOut` partial upstream availability

If the ORD or SHP upstream tables do not yet exist (their tickets are still in progress), `get_order_fulfillment_status` (ECM-012) returns `OrderFulfillmentStatusOut(order_id=..., lifecycle_status=None, fulfillment_status=None, ship_groups=[], tracking_numbers=[])`. The model must validate cleanly in this state — every field except `order_id` is optional with a safe default.

### 5.6 `ShipGroupOut` items list

`items: List[str]` contains SKUs, not order line item IDs. A cart item with `quantity=3` contributes the same SKU once (not three times). Quantity is tracked at the ORD layer, not in the ship group model.

### 5.7 `tracking_numbers` vs `ship_groups`

`tracking_numbers` is a flat convenience list. Callers must not assume it is deduplicated if the same carrier tracking number appears across multiple ship groups (a split shipment that was re-consolidated). The service layer (ECM-012) must deduplicate before constructing `OrderFulfillmentStatusOut`.

### 5.8 Forward compatibility of `option_selections`

`option_selections: Dict[str, str]` stores string values. If a future PRD ticket adds numeric option values (e.g., a "weight" feature category storing `"500g"`), the string representation is used — callers must not parse these values as numerics. This matches the existing `CatalogItemOut.attributes: Dict[str, Any]` (`app/models.py:680`) pattern.

### 5.9 `applied_rules` ordering

`CartPricingBreakdownOut.applied_rules` is ordered by application precedence: rules applied first appear first. ECM-009 (the pricing rule service integration) is responsible for preserving this order. The model itself imposes no ordering constraint.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Parity

ECM-003 defines pure Pydantic models with no I/O. There is no dev/prod divergence in model definitions — the same classes are used in both environments. The only parity concern is downstream: later tickets that populate these models must not introduce dev-mode branches that bypass the model (e.g., returning a raw `dict` instead of a typed instance). The model validator on `CartPricingBreakdownOut` will catch arithmetic errors in both envs.

### 7.2 Idempotency

Not applicable — no state is written.

### 7.3 Security

- `StorefrontVariantOut.price_cents` is server-computed from the variant record. The frontend must never be trusted to supply `price_cents` for a variant (the add-to-cart path in ECM-004 resolves price server-side from `variant_id`, never from a client-supplied value).
- `CartPricingBreakdownOut.final_total_cents` is the authoritative purchase total. ECM-010 must use this value — not the raw cart sum — to charge the buyer when `STORE_APPLY_PRICING_RULES` is on. The `subtotal_cents - discount_cents` invariant is enforced by the model validator to prevent a crafted response from under-charging.
- `OrderFulfillmentStatusOut` must only be returned for orders owned by the requesting `user_sub`. The ownership check lives in ECM-012's service function, not in the model, but is documented here as a non-negotiable security constraint.
- `StorefrontAvailabilityOut` exposes `on_hand` and `reserved` counters. This is intentional (buyers want to know "only 2 left") but must not expose per-user reservation breakdowns. The model carries no `user_sub` field; the service (ECM-005) returns aggregate counts only.

## 8. Backward Compatibility & Migration

### 8.1 `CatalogItemOut` change is additive

Adding `variants: Optional[...] = None` and `availability: Optional[...] = None` to `CatalogItemOut` is backward-compatible. Pydantic ignores extra fields in `model_validate` (the `populate_by_name` config is not set, so there is no `extra=allow` that could cause issues). Existing `_catalog_item_out(item)` at `catalog.py:110` constructs `CatalogItemOut(...)` by keyword; the two new fields default to `None` automatically.

Existing E2E tests in `frontend/e2e/catalog-subscriptions.spec.ts` assert on specific field presence using TypeScript interface checks. Adding optional nullable fields to `CatalogItemOut` does not break these assertions since they only check for fields they know about.

### 8.2 `ShoppingCartTotalOut` change is additive

The same argument applies. `ui_cart_total` at `shoppingcart.py:171` returns a literal `dict`; FastAPI serialises it through `response_model=ShoppingCartTotalOut`. The `pricing_breakdown` key will appear as `null` in responses — no existing test checks that this key is absent.

### 8.3 No DDB schema change — no migration needed

No tables, GSIs, or attribute definitions change in this ticket. `scripts/local-ddb-init.py` is unchanged.

### 8.4 `__all__` and import hygiene

If `app/models.py` defines an `__all__` list (it does not currently), the four new classes and two sub-models (`AppliedPricingRuleLineOut`, `ShipGroupOut`) must be added to it. This is noted as a maintenance point for the implementer.

## 10. Open Questions / Assumptions

1. **`"variants": null` in JSON output.** The ticket says "existing serialisers are unchanged." FastAPI will serialise new optional fields as `null` by default. If the shop frontend's TypeScript types do not expect `variants` or `availability` keys, this is a breaking change to the wire format even though the Pydantic model validates cleanly. **Assumption:** The frontend team will update `frontend/src/api/types.ts` to add optional fields with `| null` types as part of this ticket or ECM-006. If the frontend cannot accept the keys at all, the catalog router must set `response_model_exclude_none=True` — but this would also strip existing optional scalars like `description`. The safer option is to add the keys as optional-nullable in TypeScript immediately.

2. **`AppliedPricingRuleLineOut.discount_type` vocabulary.** The ticket specifies `"percentage" | "fixed_amount" | "bulk" | "conditional"`. OFB-020 (the pricing-rules engine ticket) has not yet been written; this vocabulary is derived from the existing promo-code types at `app/services/promo_codes.py:26` (`VALID_DISCOUNT_TYPES = {"percentage", "fixed_amount", "free_trial"}`) plus the expected OFB rule types (`"bulk"`, `"conditional"`). Note `"free_trial"` exists in promo_codes but is a subscription-oriented type not expected to appear as a pricing-rule line; `"bulk"` and `"conditional"` do not yet exist in any service file. **Assumption:** OFB-020 will use this exact vocabulary. If OFB-020 uses different tokens, the implementer of ECM-003 may use `str` without a `Literal` constraint, deferring enforcement to the OFB-020 spec.

3. **`ShipGroupOut.items` list size.** No upper-bound constraint is defined. A single order with 1000 line items would produce a 1000-element list in a single `ShipGroupOut.items`. **Assumption:** This is acceptable for the initial implementation. Rate limiting on the order endpoint prevents abuse.

4. **`StorefrontVariantOut` maximum list size on `CatalogItemOut`.** A product with 500 color × size combinations would produce a 500-element `variants` list. **Assumption:** ECM-004 (the variant enrichment service) will apply a configurable cap (suggested: 200 variants per item) and log a warning when truncating. This cap is not enforced by the model itself.

5. **`CartPricingBreakdownOut` vs. `ShoppingCartTotalOut.total_cents`.** When `pricing_breakdown` is present, which field is authoritative — `pricing_breakdown.final_total_cents` or `total_cents`? **Assumption:** `pricing_breakdown.final_total_cents` is the authoritative value when present; `total_cents` on the outer model will be set to `final_total_cents` by the service layer so the two are always consistent. The model validator does not enforce this cross-model invariant; that is the service layer's responsibility.

6. **Null vs. absent in `model_dump`.** By default `model.model_dump()` includes keys with `None` values; `model.model_dump(exclude_none=True)` omits them. Tests in section 9.1 assert on `model_dump()` output (with nulls present). If later tickets need exclude-none serialisation, they should call `model_dump(exclude_none=True)` explicitly. **Assumption:** The models are defined without `model_config = ConfigDict(...)` special serialisation flags.
