# OFB-020 — Apply pricing rules at cart total & checkout

## 1. Summary & Goal

OFB-020 wires the pricing-rules engine (introduced by OFB-019's `app/services/pricing_rules.py`) into the two cart-facing code paths that currently compute monetary totals:

1. **Cart-total endpoint** (`GET /ui/shoppingcart/carts/{cart_id}/total` at `app/routers/shoppingcart.py:169`) — must return the rule-discounted total and a breakdown so the frontend can display the savings before checkout.
2. **Cart purchase path** (`purchase_cart` at `app/services/shoppingcart.py:474`) — must apply the same rule evaluation, enforce redemption caps, and persist rule references on the order and its line items.

The goal is to eliminate client/server drift: the discounted total shown in the cart preview is the same total that gets charged and stored on the order. Existing flat promo-code behaviour at `app/services/promo_codes.py` remains byte-for-byte unchanged when the flag is off. When the flag is on, a cart can have **both** a promo code (flat) and active pricing rules; stacking semantics from OFB-019's `apply_stacking` determine the combined discount.

## 2. Context & Current State

### 2.1 Cart total endpoint — currently naive

`app/routers/shoppingcart.py:169–172` is:

```python
@router.get("/carts/{cart_id}/total", response_model=ShoppingCartTotalOut)
async def ui_cart_total(cart_id: str, ctx=Depends(require_ui_session)):
    total = cart_total_cents(ctx["user_sub"], cart_id)
    return {"cart_id": cart_id, "total_cents": total, "currency": "USD"}
```

`cart_total_cents` (`app/services/shoppingcart.py:301–303`) is a simple sum of `line_total_cents` with no rule evaluation. `ShoppingCartTotalOut` (`app/models.py:982–985`) has only `cart_id`, `total_cents`, `currency` — no discount fields. `require_ui_session` is imported from `app.services.sessions` in this router (`app/routers/shoppingcart.py:28`).

### 2.2 Purchase path — existing promo-code hook

`purchase_cart` (`app/services/shoppingcart.py:474–734`) already handles flat promo codes at lines `545–576`. On a valid code it sets `discount_cents` and `resolved_promo` (`app/services/shoppingcart.py:575–576`), then computes `final_total = max(0, total_cents - discount_cents)` at line `578`. The order is created at `581–594` with `metadata` carrying `promo_code_id` and `discount_cents` (`app/services/shoppingcart.py:586–593`). The promo code is redeemed (atomic increment + per-user redemption row) at lines `653–666` (best-effort, `try/except`; `pass` at line `666`).

There is **no** call to any pricing-rules service in this path today.

### 2.3 Order / line-item persistence — no rule fields today

`app/services/commerce_order_service.py:87–104`: each `order_items` row is written with `order_id`, `item_id`, `sku`, `product_type`, `billing_model`, `source_system`, `quantity`, `scope`, `pricing_ref`, `amount_cents`, `created_at`, `correlation_id` (`app/services/commerce_order_service.py:89–102`). There is no `discount_cents`, `original_amount_cents`, `applied_rule_ids`, or `applied_rules` attribute on these rows.

The order META row at `app/services/commerce_order_service.py:72–85` stores `amount_cents` and `metadata` (a free-form dict, written at line `83`). The `metadata` key already carries `promo_code_id` and `discount_cents` for flat codes (set at `app/services/shoppingcart.py:586–593`); rule references will extend the same dict.

### 2.4 PricingRules service interface (from OFB-019)

`app/services/pricing_rules.py` (OFB-019 — **not yet in the codebase**; confirmed absent) exports:
- `resolve_applicable_rules(checkout_type, cart_items, cart_total_cents, user_sub, creator_id, explicit_rule_ids=None) -> list[dict]`
- `compute_discount(rule, cart_items, cart_total_cents, user_sub) -> RuleDiscountResult` — `applied: bool`, `discount_cents: int`, `per_item_discounts`
- `apply_stacking(results) -> StackedDiscountResult` — `total_discount_cents`, `applied_rule_ids`, `per_rule_breakdown`, `final_cart_cents`
- `redeem_rule(rule_id, user_sub, original_price_cents, final_price_cents, cart_id) -> (item|None, err|None)`

`S.pricing_rules_enabled` (`PRICING_RULES_ENABLED`, default `False`, added by OFB-002/OFB-019 — **not yet in `app/core/settings.py`** as of this writing; confirmed absent) gates all paths.

### 2.5 Response models requiring extension

`ShoppingCartTotalOut` (`app/models.py:982–985`) needs discount fields to expose the preview. `ShoppingCartPurchaseOut` (`app/models.py:993–1005`) already has `discount_cents`, `promo_code_id`, `promo_discount_type`, and `original_total_cents` but has no `applied_rule_ids` or `rules_discount_cents` field. `CartPurchaseIn` (`app/models.py:988–991`) accepts `promo_code` and `promo_code_id` but no `rule_ids` (explicit rule activation).

## 3. Data Model

OFB-020 does **not** introduce a new DynamoDB table. It writes new **additive attributes** to existing records in three tables.

### 3.1 `order_items` table — new per-line attributes

Each row in `T.order_items` (`order_items_table_name`, `app/core/settings.py:1125`; table handle at `app/core/tables.py:130,382`) gains three new optional attributes written at order-creation time:

| Attribute | Type | Notes |
|-----------|------|-------|
| `original_amount_cents` | N | Raw `qty * unit_price_cents` before any discount |
| `discount_cents` | N | Discount applied to this line (0 if no rule fired for this SKU) |
| `applied_rule_ids` | SS | DynamoDB string set; rule IDs whose `per_item_discounts` included this SKU |

These attributes are absent on rows created before this feature ships (backward compatible). The `order_items` PK is `order_id` (S) / `item_id` (S) per `scripts/local-ddb-init.py:295`; `item_id` is assigned as `str(idx)` (1-based sequential int) at `app/services/commerce_order_service.py:91`. No schema change is required (no new GSI).

### 3.2 `orders` table — extended metadata

The `metadata` map on the order META row (written at `app/services/commerce_order_service.py:83`; `orders` table handle at `app/core/tables.py:129,381`) gains new keys when pricing rules fire. These are pass-through dict values, not top-level DynamoDB attributes, so no schema migration is needed:

| Key | Type | Notes |
|-----|------|-------|
| `applied_rule_ids` | list[str] | All rule IDs that contributed to the total discount |
| `rules_discount_cents` | int | Total discount from pricing rules only (excludes flat promo code) |
| `promo_discount_cents` | int | Discount from flat promo code only (renamed from existing `discount_cents`) |
| `total_discount_cents` | int | `rules_discount_cents + promo_discount_cents` |

### 3.3 `shopping_cart` table — cart record additional fields

The existing `cart` record (PK=`USER#{user_sub}`, SK=`CART#{cart_id}`; key helpers at `app/services/shoppingcart.py:31–35`) already stores `promo_code_id`, `discount_cents`, `original_total_cents` at purchase time (`app/services/shoppingcart.py:617–620`; `T.shopping_cart.update_item` at line `621`). After this ticket the same `update_item` expression gains three additional conditional attributes:

| Attribute | Type | Notes |
|-----------|------|-------|
| `applied_rule_ids` | SS | Rule IDs from `StackedDiscountResult.applied_rule_ids` |
| `rules_discount_cents` | N | `StackedDiscountResult.total_discount_cents` |
| `total_discount_cents` | N | Combined flat + rules discount |

No GSI changes; no `attr_types` additions needed.

### 3.4 `pricing_rules` table — redemption rows (OFB-019 concern, touched here)

When a rule fires at checkout, `redeem_rule(rule_id, user_sub, ...)` (defined by OFB-019) writes a `REDEEM#{user_sub}#{ts}` row into `T.pricing_rules` and increments `current_uses` on the META record. OFB-020 **calls** this function; it does not define the schema. The table is defined in `scripts/local-ddb-init.py` by OFB-019 (**not yet present** in `scripts/local-ddb-init.py` as of this writing). The `T.pricing_rules` handle is similarly absent from `app/core/tables.py` until OFB-019 ships.

## 4. API / Service Design

### 4.1 New helper in `app/services/shoppingcart.py`

```python
def _apply_pricing_rules(
    user_sub: str, items: list[dict], raw_total_cents: int,
    creator_id: str, checkout_type: str = "shop",
    explicit_rule_ids: list[str] | None = None,
    exclude_rule_ids: set[str] | None = None,
) -> "_RulesResult":
    """Returns _RulesResult(stacked, applied_rule_ids, rules_discount_cents,
    per_rule_breakdown). Never raises — errors return zero-discount result."""
```

Flow: (1) guard on `S.pricing_rules_enabled` — return zero if off; (2) lazy-import `resolve_applicable_rules`, `compute_discount`, `apply_stacking` from `app.services.pricing_rules`; (3) `rules = resolve_applicable_rules(...)` filtered by `exclude_rule_ids`; (4) `compute_discount` per rule; (5) `apply_stacking(applied results)`; (6) return. The lazy import keeps `shoppingcart.py` importable before OFB-019 ships.

### 4.2 Extended `cart_total_cents` (additive, no modification)

New function in `app/services/shoppingcart.py`:

```python
def cart_total_with_rules(user_sub: str, cart_id: str) -> dict:
    """Returns {"cart_id", "raw_total_cents", "total_cents" (discounted),
    "rules_discount_cents", "applied_rule_ids", "per_rule_breakdown", "currency"}.
    Calls _apply_pricing_rules; when flag off, total_cents == raw_total_cents."""
```

The existing `cart_total_cents(user_sub, cart_id) -> int` is **not modified**.

The existing `cart_total_cents(user_sub, cart_id) -> int` function is **not modified**; it is still used internally and by other callers. The new function is additive.

### 4.3 Modified endpoint: `GET /ui/shoppingcart/carts/{cart_id}/total`

`app/routers/shoppingcart.py:169` is updated: when `S.pricing_rules_enabled`, call `cart_total_with_rules` and return its dict; otherwise fall through to the existing `cart_total_cents` call. New `ShoppingCartTotalOut` fields default to `None` / `0` so the flag-off response is byte-for-byte identical to today.

### 4.4 Modified `purchase_cart` in `app/services/shoppingcart.py`

The existing promo-code block (`lines 545–576`; `discount_cents`/`resolved_promo` set at lines `575–576`) is **unchanged**. Immediately after it, a rules block is inserted that calls `_apply_pricing_rules(user_sub, items, total_cents, creator_id or user_sub, exclude_rule_ids={resolved_promo.get("pricing_rule_id")} if resolved_promo else None)`. The existing `final_total` line at line `578` is replaced:

```python
final_total = max(0, total_cents - discount_cents - rules_discount_cents)
```

The `create_order_from_line_items` metadata dict (call at `app/services/shoppingcart.py:581`, dict at lines `586–593`) gains `promo_discount_cents` (the existing `discount_cents` key renamed in the metadata — the flat-promo discount), `rules_discount_cents`, `total_discount_cents`, and `applied_rule_ids`. The cart `update_item` at line `621` (`ConditionExpression="#status = :open"` at line `626`) conditionally adds `applied_rule_ids` (SS), `rules_discount_cents` (N), and `total_discount_cents` (N) when `applied_rule_ids` is non-empty.

Per-line discount attribution is written by a new helper `_annotate_order_items_with_rules(order_id, rules_result, commerce_order_service)` called immediately after `create_order_from_line_items`:

```python
def _annotate_order_items_with_rules(
    order_id: str,
    rules_result: "_RulesResult",
    svc,   # CommerceOrderService instance
) -> None:
    """
    For each per_item_discount in the stacked result, update the matching
    order_items row with original_amount_cents, discount_cents, applied_rule_ids.
    Best-effort: wrapped in try/except so annotation failure never blocks checkout.
    """
```

The function builds a `{sku: {original, discount, rule_ids}}` dict from `rules_result.per_rule_breakdown[*].per_item_discounts`, then does a `query(Key={"order_id": order_id})` on `T.order_items` to resolve `sku → item_id` (sequential 1-based integers assigned in `create_order`), and issues `update_item` calls setting `original_amount_cents`, `discount_cents`, and `applied_rule_ids` (SS) on each affected row. Only SKUs with non-zero discount are updated; others are left untouched (absent `discount_cents` means 0).

### 4.5 Redemption accounting for rule uses

After the promo-code redemption block at `app/services/shoppingcart.py:653–666` (`pass  # best-effort redemption` at line `666`), a parallel best-effort block iterates `applied_rule_ids` and calls `redeem_rule(rule_id, user_sub, original_price_cents, final_price_cents, cart_id)` for each. `redeem_rule` (OFB-019) atomically increments `current_uses` via conditional `update_item` and writes a per-user `REDEEM#{user_sub}#{ts}` row, mirroring `redeem_promo_code` at `app/services/promo_codes.py:398–449` (conditional `update_item` at lines `416–429`). The entire block is wrapped in `try/except` (best-effort, same pattern).

### 4.6 Extended purchase response

`purchase_cart` return dict gains three new keys: `"applied_rule_ids": applied_rule_ids or None`, `"rules_discount_cents": rules_discount_cents or None`, `"total_discount_cents": (discount_cents + rules_discount_cents) or None`.

### 4.7 Pydantic model changes in `app/models.py`

All changes are additive `Optional` fields defaulting to `None`.

**`ShoppingCartTotalOut`** (`app/models.py:982`) gains: `raw_total_cents: Optional[int]`, `rules_discount_cents: Optional[int]`, `applied_rule_ids: Optional[List[str]]`, `per_rule_breakdown: Optional[List[RuleDiscountResultOut]]` (where `RuleDiscountResultOut` is defined by OFB-019).

**`ShoppingCartPurchaseOut`** (`app/models.py:993`) gains: `applied_rule_ids: Optional[List[str]]`, `rules_discount_cents: Optional[int]`, `total_discount_cents: Optional[int]`.

**`CartPurchaseIn`** (`app/models.py:988`) gains: `explicit_rule_ids: Optional[List[str]] = None` for admin/test override of auto-discovery.

## 5. Detailed Behavior & Edge Cases

### 5.1 Promo code that carries a rule reference

When `resolved_promo["pricing_rule_id"]` is set (OFB-019's `enrich_validate_result_with_rule` has run), the flat code's `discount_cents` already reflects the rule's math. To avoid double-counting, the `_apply_pricing_rules` call **excludes** the rule_id that the promo code already applied:

```python
already_applied_via_promo = resolved_promo.get("pricing_rule_id") if resolved_promo else None
rules_result = _apply_pricing_rules(
    ...
    explicit_rule_ids=None,  # auto-discover
    exclude_rule_ids={already_applied_via_promo} if already_applied_via_promo else set(),
)
```

`resolve_applicable_rules` (OFB-019) must accept an `exclude_rule_ids` parameter (clarified as an assumption in §10).

### 5.2 Re-evaluation at purchase vs. preview

Rules are re-evaluated independently at purchase time. If items change between preview and purchase, the purchase total is authoritative; no error is raised for the discrepancy.

### 5.3 Rule deactivated between preview and purchase

`resolve_applicable_rules` filters `active=False` rules; the buyer receives a lower discount than previewed. No hold mechanism exists at this tier.

### 5.4 Per-user cap enforcement timing

`_check_uses` in `resolve_applicable_rules` is advisory (read-before-write). `redeem_rule`'s conditional `update_item` is authoritative for global cap. Strict per-user serialization is deferred (see §10, assumption 2).

### 5.5 `final_total = 0` case

Combined discounts floor at 0. `purchase_history.record_cart_purchase` receives `total_cents=0`; billing ledger records a zero-value `purchase` entry — correct for a fully-discounted order.

### 5.6 Idempotency on re-purchase

Early-return guard at `app/services/shoppingcart.py:483–492` is extended to read `applied_rule_ids` from the DynamoDB cart record and include it in the returned dict.

### 5.7 `_annotate_order_items_with_rules` cross-reference

Only SKUs with non-zero discount receive `update_item` calls; others are untouched (absent `discount_cents` means 0).

### 5.8 Rule breakdown ordering in response

`per_rule_breakdown` is ordered by `priority` ASC (same as `resolve_applicable_rules` output).

### 5.9 Interaction with FIN-001 invoice generation

`create_invoice_safe` at `app/services/shoppingcart.py:708` already receives `amount_cents=int(final_total)` — the correct post-discount total. Individual invoice line items (`lines 699–707`) still use raw `line_total_cents`. The invoice total is accurate; the line breakdown overstates. A negative discount line item can be added in a follow-up (see §10, assumption 3).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 Dev/Prod parity

All DDB reads/writes use `T.pricing_rules`, `T.order_items`, `T.orders`, and `T.shopping_cart`, wired identically in dev (DynamoDB Local port 8001) and prod. There is no `S.dev_mode` branch. `_annotate_order_items_with_rules` and `redeem_rule` are best-effort (`try/except`) — mirrors the `redeem_promo_code` best-effort block at `app/services/shoppingcart.py:653–666` (`pass  # best-effort redemption` at line 666) and `process_order_entitlements` at line 645.

### 7.2 Idempotency

Order creation is idempotent via deterministic `sha256(correlation_id)[:32]` order_id at `app/services/commerce_order_service.py:67`. Cart update uses `ConditionExpression="#status = :open"` guard at `app/services/shoppingcart.py:626`. `_annotate_order_items_with_rules` is idempotent (repeated `update_item` with same values is safe).

### 7.3 Security

Client-supplied `explicit_rule_ids` are validated server-side by `resolve_applicable_rules` (active, non-expired, correct checkout type, within caps). The client never sends a discount amount. `redeem_rule`'s conditional `update_item` (same pattern as `app/services/promo_codes.py:416–429`; `ConditionExpression=Attr("current_uses").lt(max_uses)` at line `421`) prevents over-redemption past `max_uses` under concurrent load. The `REDEEM#{user_sub}#{ts}` audit row records `original_price_cents`, `final_price_cents`, and `cart_id` for reconciliation.

## 10. Open Questions / Assumptions

1. **`exclude_rule_ids` parameter on `resolve_applicable_rules`**: OFB-019's spec (§4.1, `docs/ofbiz/specs/OFB-019.md`) does not mention an `exclude_rule_ids` parameter. OFB-020 assumes OFB-019 will add it to avoid double-counting when a promo code carries a rule reference. If OFB-019 does not, OFB-020 must check `resolved_promo.get("pricing_rule_id")` and subtract that rule's contribution from the `apply_stacking` result manually.

2. **Per-user cap strictness**: `redeem_rule`'s conditional increment (`Attr("current_uses").lt(max_uses)`) is a global cap check, not a per-user cap check. OFB-019's `_check_uses` is a read-only advisory filter at `resolve_applicable_rules` time. Concurrent requests from the same user can theoretically both pass the advisory check and both succeed at `redeem_rule`. This is the same race present in `redeem_promo_code`. Assumed acceptable at this tier; strict per-user serialisation would require a per-user lock or a second conditional expression.

3. **Invoice line items with discounts**: `create_invoice_safe` receives `amount_cents=final_total` (correct total) but individual `line_items` still reflect pre-discount amounts (`app/services/shoppingcart.py:700–706`). The invoice total is accurate but the line itemization overstates. Assumed acceptable for MVP; a discount line item (negative amount) can be added in a follow-up.

4. **`creator_id` for platform-wide rules**: `_apply_pricing_rules` passes `creator_id = _resolve_cart_creator(items) or user_sub`. For carts with mixed creators or no creator info, `user_sub` is used as the fallback. Platform-wide rules (`scope_creator_user_id=""`) are not affected. Creator-scoped rules may not fire for mixed-creator carts. This matches the existing promo-code fallback at `app/services/shoppingcart.py:553–558`.

5. **`GET /ui/shoppingcart/carts/{cart_id}/total` response shape change**: The handler returns a dict with `raw_total_cents` (new) and `total_cents` now means discounted total rather than raw total. Existing consumers reading `total_cents` will silently receive a lower value. This is intentional (the endpoint is meant to return the payable total) but must be communicated to OFB-021 frontend implementors.

6. **Order items `item_id` cross-reference**: `create_order` assigns `item_id = str(idx)` (sequential 1-based int as string). The `_annotate_order_items_with_rules` helper must query order items by `order_id` to resolve `sku → item_id` mapping. This adds one extra DynamoDB query per checkout. Assumed acceptable at this order-item count (<100 items per cart in practice).
