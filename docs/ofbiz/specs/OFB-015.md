# OFB-015 — AR / AP subledgers

## 1. Summary & Goal

OFB-015 adds Accounts Receivable (AR) and Accounts Payable (AP) subledgers derived entirely from data that already exists in the platform: unpaid invoices from `T.invoices`, the per-user billing balance fields from `T.billing`, and outstanding creator payout requests from `T.creator_payouts`. Neither subledger stores any new monetary state; they compute open-item aging views and derive a running control-account balance that must reconcile to zero variance with the GL control accounts posted by OFB-014.

The concrete deliverables are:
- `app/services/ar_subledger.py` — AR aging engine (current / 30 / 60 / 90+ day buckets) over outstanding invoices and unsettled billing-balance due amounts.
- `app/services/ap_subledger.py` — AP aging engine over pending/approved creator payout requests and any reversed/unsettled credit entries owed to creators.
- `app/routers/ar_ap.py` — ROOT-only REST endpoints exposing aging summaries and the GL tie-out reconciliation report.
- New DynamoDB table `ar_ap_snapshots` — point-in-time aging snapshots for trending (optional materialization path; aging is always re-computed live on demand).
- Settings key `AR_AP_SUBLEDGERS_ENABLED` (default `false`) gating the entire feature.

With the flag off, all existing billing, invoices, shop, cart, orders, and payout paths are byte-for-byte unchanged. With the flag on, the subledgers are purely read-only views — they never write to `T.billing` or `T.invoices`.

## 2. Context & Current State

### 2.1 Existing single-entry billing ledger

Every monetary event is written by `new_ledger_entry` in `app/services/billing_shared.py:224`. Each row carries `type`, `state` (`pending`/`settled`/`reversed`), `amount_cents`, `ledger_date`, and optional `provider` and `extra` fields. The billing table uses `pk = "USER#{user_sub}"` / `sk = "LEDGER#{ts}#{entry_id}"` (`billing_shared.py:220–221`). The `GSI_LEDGER_DATE` index (partition = `ledger_date` (S), sort = `sk` (S)) is declared in `scripts/local-ddb-init.py:64–77` with `attr_types={"ledger_date": "S"}` for cross-user day-bucket aggregation.

### 2.2 Balance fields and `compute_due`

`billing_shared.py:15–20` defines `BAL_FIELDS = ["owed_pending_cents", "owed_settled_cents", "payments_pending_cents", "payments_settled_cents"]`. The `BALANCE` row for each user holds these four counters. `compute_due` at `billing_shared.py:158–170` computes:
- `due_settled_cents = owed_settled - payments_settled` — the amount a user still owes from already-settled charges.
- `due_if_all_settles_cents = (owed_settled + owed_pending) - (payments_settled + payments_pending)` — the expected outstanding if all pending items settle.

A positive `due_settled_cents` is an AR open item for the platform; a positive `due_if_all_settles_cents` represents the expected total collectible.

### 2.3 Invoices

`app/services/invoices.py:272` writes invoice records to `T.invoices` (key `pk = "USER#{user_sub}"`, `sk = "INV#{invoice_number}"`). The `status` field starts as `"generated"` (`invoices.py:335`), transitions to `"emailed"` (`invoices.py:481–483`). A `"refunded"` status exists but is only set by `subscription_server.py:mark_invoice_refunded` (line 273) for subscription invoices that had `status="paid"` — it is **not** set by the billing refund path (`billing.py:1323–1324`, which reverses the ledger entry via `settle_or_reverse_ledger` but leaves the invoice status unchanged). The `"paid"` status only appears in the subscription server context; the main invoices service has **no** `"paid"` transition. There is **no** `"overdue"` status today. Invoices created via `create_invoice` carry `ledger_entry_id` linking them to the originating ledger row (`invoices.py:336`).

The `GSI1` index on `T.invoices` (`GSI1PK = "USER#{sub}#TYPE#{type}"`, `GSI1SK` = numeric `created_at`, `scripts/local-ddb-init.py:2273–2278`) allows per-user, per-type listing. `GSI2` (`GSI2PK = "ADMIN_ALL"`, `GSI2SK` = numeric `created_at`) enables system-wide admin listing (`invoices.py:492`). Both GSIs use `attr_types={"GSI1SK": "N", "GSI2SK": "N"}` (`scripts/local-ddb-init.py:2277`).

`list_invoices` at `invoices.py:395–439` paginates via `LastEvaluatedKey`. An invoice is "outstanding" (an AR open item) when `status` is `"generated"` or `"emailed"` — it was issued but not confirmed as paid. The missing `"paid"` status means AR aging must treat all non-refunded invoices as open unless the linked ledger entry has `state = "settled"`.

### 2.4 Creator payouts (AP source)

`app/services/creator_payouts.py` manages payout requests against `T.creator_payouts`. The table is keyed by a single `payout_id` HASH attribute (no range key — `scripts/local-ddb-init.py:980–987`), with `ByUserCreatedAt` GSI (partition = `user_id`, sort = `created_at (N)`) for per-creator listing and `ByStatusCreatedAt` GSI (partition = `status`, sort = `created_at (N)`) for admin queue processing.

`PAYOUT_STATES = {"requested", "approved", "processing", "completed", "rejected", "cancelled", "failed"}` and `ACTIVE_PAYOUT_STATES = {"requested", "approved", "processing"}` (`creator_payouts.py:24–25`). Payouts in `ACTIVE_PAYOUT_STATES` represent platform liabilities (AP open items): the creator has earned the money and the platform is obligated to pay.

`_get_active_payout_total` at `creator_payouts.py:151–170` queries `ByUserCreatedAt` and sums `amount_cents` for active-state payouts. This is the per-creator AP balance. The `BAL_FIELDS` `owed_*` fields in `T.billing` represent creator earnings credited to the creator's platform balance, distinct from payout requests which are the formal AP claim.

The table is keyed by a single `payout_id` HASH attribute (no range key — `scripts/local-ddb-init.py:980–987`). `_is_real_payout` is defined at `creator_payouts.py:45–52` (the function body starts at line 45; the guard is the `return` at line 52). Items with `record_kind` equal to `PAYOUT_METHOD_KIND` (`"payout_method"`) or `PAYOUT_STATE_KIND` (`"payout_state"`) must be excluded from AP open-item scans.

### 2.5 GL control accounts (from OFB-013)

OFB-013 (`docs/ofbiz/specs/OFB-013.md:198–203`) defines:
- Account `1200`: "Accounts Receivable" (asset, debit-normal)
- Account `2000`: "Accounts Payable" (liability, credit-normal)

OFB-014 posts journal entries that debit `1200` when a charge is recognized and credit it when payment settles; it credits `2000` when a creator earns a payout and debits it when the payout completes. OFB-015 must produce running balances for `1200` and `2000` by summing the open items independently and assert that these sums match the corresponding GL account balances.

### 2.6 No existing AR/AP service files

`ls app/services/gl_*.py`, `ls app/services/ar_*.py`, and `ls app/services/ap_*.py` all return nothing — these files do not yet exist. `app/core/tables.py:317–319` shows `T.inventory`, `T.reservations`, `T.returns` (OFB Milestone 3 tables), but no `T.ar_ap_snapshots` or GL tables. `app/core/settings.py:839` (`inventory_reservations_enabled`) and `:846` (`returns_rma_enabled`) show the existing OFB flag pattern; neither `gl_double_entry_enabled` nor any AR/AP flag exists yet — both are delivered by OFB-013 and OFB-015 respectively.

## 3. Data Model

### 3.1 No new tables required for live aging

AR and AP aging are computed on-demand by querying:
- `T.invoices` (GSI2 `ADMIN_ALL / created_at`) for all invoices system-wide, or `GSI1` for per-user.
- `T.billing` BALANCE row per user for `compute_due` — AR balance from billing fields.
- `T.creator_payouts` via `ByStatusCreatedAt` GSI for all active-state payout records (AP open items).

A new persistence table is added only for snapshots.

### 3.2 New table: `ar_ap_snapshots`

Stores point-in-time aging snapshots triggered on demand or by a scheduler. Used for trending in OFB-017's accounting UI.

**Primary key**

| Attribute    | Type | Value |
|--------------|------|-------|
| `pk`         | S    | `"AR"` or `"AP"` — one partition per subledger side |
| `sk`         | S    | `"SNAP#{ts:010d}#{snap_id}"` — timestamp-prefixed for chronological order |

**Item attributes**

| Attribute          | Type | Notes |
|--------------------|------|-------|
| `pk`               | S    | `"AR"` or `"AP"` |
| `sk`               | S    | `"SNAP#{ts}#{snap_id}"` |
| `snap_id`          | S    | `"snap_" + uuid4().hex` |
| `ts`               | N    | Unix timestamp of snapshot (`now_ts()`) |
| `snap_date`        | S    | YYYY-MM-DD UTC of snapshot (for human display) |
| `current_cents`    | N    | Total open items 0–30 days |
| `days_30_cents`    | N    | Open items 31–60 days past due |
| `days_60_cents`    | N    | Open items 61–90 days past due |
| `days_90_plus_cents` | N  | Open items 91+ days past due |
| `total_open_cents` | N    | Sum of all four buckets |
| `control_account_cents` | N | GL account balance from OFB-014 journal entries |
| `variance_cents`   | N    | `total_open_cents - control_account_cents` (must be 0) |
| `open_item_count`  | N    | Number of open items contributing to the total |
| `triggered_by`     | S    | `user_sub` of ROOT user or `"scheduler"` |

**GSI: `GSI_DATE`**

Enables range queries over snapshots for a given subledger side (e.g. all AR snapshots in the last 30 days).

| Index name  | Partition key | Sort key    | Projects | `attr_types` |
|-------------|--------------|-------------|----------|--------------|
| `GSI_DATE`  | `pk` (S)     | `ts` (N)    | ALL      | `{"ts": "N"}` |

`pk` is already the table's HASH key, so `GSI_DATE` is a "local GSI by date" using the same partition. Since DynamoDB does not allow true local secondary indexes with a different hash key, this is a GSI with the same partition key as the table, ordered by `ts` instead of the full `sk`. This allows `query(KeyConditionExpression=Key("pk").eq("AR") & Key("ts").between(t_start, t_end))` for time-range reporting.

## 4. API / Service Design

### 4.1 Service: `app/services/ar_subledger.py`

```python
"""AR subledger — open-item aging from invoices and billing balance fields.

Additive, flag-gated (AR_AP_SUBLEDGERS_ENABLED, default OFF). All public
functions gate on _require_enabled(). Derives AR from:
  1. Outstanding invoices (T.invoices, status != 'refunded', ledger entry
     not state='settled') — the formal open-item view.
  2. Per-user billing BALANCE.due_settled_cents — amounts owed that are
     settled charges but not yet fully paid (billing_shared.compute_due).

SECOPS-007: no dev_mode branches; identical code path dev (moto) and prod.
"""

# ── Aging bucket boundaries (seconds past invoice created_at) ────────────
BUCKET_30_SECS  = 30 * 86_400   # 0–30 days: "current"
BUCKET_60_SECS  = 60 * 86_400   # 31–60 days
BUCKET_90_SECS  = 90 * 86_400   # 61–90 days
# 91+ days: "90_plus"

def _bucket(age_seconds: int) -> str:
    """Return bucket name for an open item of the given age."""

def compute_ar_aging(
    *,
    as_of_ts: Optional[int] = None,
    user_sub: Optional[str] = None,
) -> Dict[str, Any]:
    """Compute AR aging buckets.

    When user_sub is supplied, scans only that user's invoices (GSI1).
    When user_sub is None, performs a system-wide scan via GSI2 (ADMIN_ALL),
    paginating in a loop to avoid the DynamoDB 1MB page-size limit (per
    CLAUDE.md: FilterExpression does not reduce page size).

    Returns:
        {
          "current_cents": int,       # 0–30 days
          "days_30_cents": int,       # 31–60 days
          "days_60_cents": int,       # 61–90 days
          "days_90_plus_cents": int,  # 91+ days
          "total_open_cents": int,
          "open_item_count": int,
          "as_of_ts": int,
          "items": [ArOpenItemOut],   # per-invoice detail, truncated at 500
        }
    Raises HTTPException(503) when AR_AP_SUBLEDGERS_ENABLED=false.
    """

def _invoice_is_open(invoice: Dict[str, Any], as_of_ts: int) -> bool:
    """Return True if the invoice represents an outstanding AR amount.

    An invoice is open when:
    - status is "generated" or "emailed" (not "refunded")
    - AND the linked billing ledger entry (via ledger_entry_id) does NOT
      have state="settled". If ledger_entry_id is absent (pre-OFB-015
      invoices), treat as open conservatively.
    """

def _age_seconds(invoice: Dict[str, Any], as_of_ts: int) -> int:
    """Return how old this open item is in seconds."""

def get_ar_control_account_balance(as_of_ts: Optional[int] = None) -> int:
    """Read the running balance of account 1200 (AR) from T.gl_journal.

    Per OFB-014's schema (docs/ofbiz/specs/OFB-014.md §3.1), gl_journal line
    items (SK prefix "JL#") carry ``account_code`` (e.g. "1200") and ``side``
    ("debit"|"credit"). There are no ``debit_account_code`` / ``credit_account_code``
    header fields. The correct approach is to scan/query JL# line items with
    ``account_code="1200"`` and sum: debit amounts increase AR, credit amounts
    decrease it. The ENTRIES_BY_DATE GSI (partition=ledger_date, sort=posted_at)
    enables date-ranged queries on header rows; line items must then be fetched
    by their SK prefix "JL#{journal_entry_id}". Returns 0 when T.gl_journal is
    empty (OFB-014 not yet run) or if ClientError is raised (table absent).
    Used only when GL_DOUBLE_ENTRY_ENABLED=true.
    """

def reconcile_ar(as_of_ts: Optional[int] = None) -> Dict[str, Any]:
    """Compute AR aging and compare total to GL control account 1200.

    Returns:
        {
          "aging": compute_ar_aging(...),
          "gl_control_account_cents": int,
          "variance_cents": int,   # aging.total_open_cents - gl_control
          "reconciled": bool,      # True iff variance == 0
        }
    """

def save_ar_snapshot(actor_sub: str, as_of_ts: Optional[int] = None) -> Dict[str, Any]:
    """Compute and persist an AR snapshot to T.ar_ap_snapshots.

    Idempotent by content hash: sha256(pk + snap_date + total_open_cents)
    stored as snap_id allows callers to detect duplicate snapshots on the
    same day. Uses conditional put (attribute_not_exists(sk)) to prevent
    double-write; on ConditionalCheckFailedException, returns the existing
    snapshot without error.
    """
```

## 5. Detailed Behavior & Edge Cases

### 5.1 Invoice open-item determination

An invoice qualifies as an AR open item when:
1. `status` is `"generated"` or `"emailed"` — not `"refunded"` and not `"emailed_paid"` (a status we do not introduce here; OFB-015 conservatively treats `"emailed"` as open).
2. The linked billing ledger entry (`ledger_entry_id` → `T.billing` item via `pk = "USER#{user_sub}"`, `sk = "LEDGER#{ts}#{entry_id}"`) does not have `state = "settled"`. If the link is absent (no `ledger_entry_id`), treat conservatively as open.

**Fetching the ledger state:** For each non-refunded invoice, perform a `get_item` on `T.billing` keyed by `USER#{user_sub}` / `ledger_sk`. This is O(1) per invoice. At scale (thousands of invoices), this is `N` point reads. The `ar_aging_scan_limit` setting (default 5000) caps the total invoices scanned in a single request. Callers needing more must paginate via the `cursor` field on the response.

**Invoice age:** Measured from `invoice.created_at` to `as_of_ts` (defaults to `now_ts()`). Age determines the bucket:
- Current (0–30 days): `age_seconds <= 30 * 86_400`
- 30–60 days: `30 * 86_400 < age_seconds <= 60 * 86_400`
- 60–90 days: `60 * 86_400 < age_seconds <= 90 * 86_400`
- 90+ days: `age_seconds > 90 * 86_400`

**Billing BALANCE contribution:** In addition to invoice-based AR, the per-user `compute_due` result (`billing_shared.py:158`) contributes if `due_settled_cents > 0` AND there is no corresponding invoice. To avoid double-counting: if an invoice covers the same `ledger_entry_id` as the `BALANCE` row's settled charge, the invoice item takes precedence. In practice this overlap is rare (some billing charges have no corresponding invoice), but the reconciliation test must account for it.

### 5.2 AP open-item determination

A payout record is an AP open item when `status in {"requested", "approved", "processing"}` — per `ACTIVE_PAYOUT_STATES` (`creator_payouts.py:25`). The `_is_real_payout` guard from `creator_payouts.py:45` must be applied: items with `record_kind in {"payout_method", "payout_state"}` (constants `PAYOUT_METHOD_KIND`/`PAYOUT_STATE_KIND` at `creator_payouts.py:33–38`) are co-located in the same `CreatorPayouts` table and must be excluded.

The AP scan queries `ByStatusCreatedAt` GSI for each of the three active statuses in separate paginated loops. Each loop must exhaust `LastEvaluatedKey` because DynamoDB fetches up to 1MB before applying any filter (CLAUDE.md gotcha). The `ap_aging_scan_limit` (default 5000) caps total records across all three status queries.

### 5.3 GL tie-out and reconciliation

When `GL_DOUBLE_ENTRY_ENABLED=true` (OFB-014 running), the AR reconciliation computes:
- `ar_aging.total_open_cents` — sum of all open invoice amounts.
- `gl_control_account_cents` — net balance of account `1200` in `T.gl_journal`, derived from JL# line items with `account_code="1200"`: sum of debit `amount_cents` minus sum of credit `amount_cents`. A debit to `1200` increases AR (a charge recognized); a credit decreases it (payment received or reversal). Per OFB-014 schema, `amount_cents` on each line is always positive and `side` encodes the direction.

`variance_cents = ar_aging.total_open_cents - gl_control_account_cents`. This should be 0. Non-zero variance indicates either un-posted ledger entries (OFB-014 backfill incomplete) or an inconsistency.

When `GL_DOUBLE_ENTRY_ENABLED=false`, `gl_control_account_cents` returns 0 and `variance_cents` equals `total_open_cents`. The `reconciled` field is `False` and `gl_enabled: false` signals that the variance is expected and not an error.

The same logic applies to AP with account `2000`.

### 5.4 Snapshot idempotency

`save_ar_snapshot` constructs a deterministic `snap_id` from `sha256(f"AR|{snap_date}|{total_open_cents}".encode()).hexdigest()[:16]`. The snapshot's `sk = "SNAP#{ts}#{snap_id}"` uses `now_ts()` for `ts` (not the `as_of_ts` argument), so two snapshots taken on the same day at different times both persist independently. The deduplication is on the `snap_id` within the same `sk` value; since `ts` increments, same-day duplicate calls produce multiple rows with different `sk` values. If strict once-per-day dedup is needed (future), add a GSI on `snap_date`. For now, the caller controls trigger frequency.

### 5.5 Pagination on system-wide aging

The GSI2 `ADMIN_ALL` scan on `T.invoices` may return tens of thousands of items on a busy platform. The service loops via `LastEvaluatedKey` up to `ar_aging_scan_limit` total items, then includes a `next_cursor` in the response. This matches the cursor pattern used by `list_invoices` at `invoices.py:438`. The `cursor` query param on `GET /ui/gl/ar-ap/ar/aging` allows paged navigation for ROOT users.

### 5.6 `as_of` backdating

The `as_of_ts` parameter allows aging as of a past date. For AR: invoices created after `as_of_ts` are excluded. For AP: payouts created after `as_of_ts` are excluded. The age bucket calculation uses `as_of_ts` as the "today" reference. This supports historical reconciliation without a snapshot.

### 5.7 Concurrent mutation safety

The subledgers are read-only views. They never write to `T.billing` or `T.creator_payouts`. The snapshot write is isolated to `T.ar_ap_snapshots`. There is no risk of a subledger query interfering with a live billing or payout transaction.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### SECOPS-007

Neither `ar_subledger.py` nor `ap_subledger.py` contains any `if S.dev_mode` branches. All DynamoDB reads go through the same `T.*` table handles regardless of environment. This follows the pattern established by `inventory.py` and `gl_accounts.py` (OFB-013 spec). The moto-backed DynamoDB in dev is populated identically to production (same GSIs, same key schema).

### Idempotency

- **Live aging queries** (`compute_ar_aging`, `compute_ap_aging`): pure read operations; fully idempotent.
- **Snapshot writes**: `save_ar_snapshot` and `save_ap_snapshot` use `ConditionExpression="attribute_not_exists(pk)"` on `T.ar_ap_snapshots`. For the `ar_ap_snapshots` table, this translates to `attribute_not_exists(sk)` (the unique key per snapshot). A `ConditionalCheckFailedException` on a same-`sk` duplicate is silently swallowed, and the existing snapshot is returned.
- **Reconcile**: read-only; idempotent.

### Security

- All endpoints use `require_root_session` — only ROOT can access aging data and reconciliation reports. These contain aggregated monetary figures across all users and creators.
- The `items` list in `AgingOut` is truncated at 500 entries by default to avoid excessively large responses that could inadvertently leak large volumes of per-user financial data in a single API response. Full enumeration requires pagination via `cursor`.
- `user_sub` and `user_id` filter parameters are accepted but not validated for ownership — the ROOT caller can query any user's AR or AP position. This is appropriate (ROOT = platform finance access) and consistent with the admin invoices listing in `invoices.py:492`.
- `as_of_ts` is limited to the past (rejects future timestamps with `HTTPException(400)`) to prevent speculative forecasting that could be misleading.
- Audit events are emitted when a snapshot is saved: `_audit("ar_snapshot_saved", actor_sub, snap_id=snap_id)` and `_audit("ap_snapshot_saved", actor_sub, snap_id=snap_id)`. Live aging queries are not audited (read-only).

## 8. Backward Compatibility & Migration

### Zero-impact with flag off

With `AR_AP_SUBLEDGERS_ENABLED=false`:
- New table `ar_ap_snapshots` is created at `just restart` but never queried.
- New settings keys hold their defaults.
- No existing router, service, or model is modified.
- `T` gains one new attribute (`ar_ap_snapshots`); 570+ existing attributes are unchanged.
- Billing, invoices, and payout flows are byte-for-byte identical.

### Invoice status gap

Invoices today have no `"paid"` status. The AR open-item determination relies on the linked ledger entry's `state = "settled"` as the payment confirmation signal. This is a correct derivation (the ledger is the source of truth for payment state), but it means AR aging degrades gracefully to "all non-refunded invoices are open" when OFB-014 has not yet posted journal entries for the corresponding ledger rows. Finance stakeholders should understand this during early enablement. A `"paid"` status on invoices (optional future enhancement) would make AR determination self-contained.

### Enabling AR/AP subledgers in production

1. Deploy code (new `ar_ap_snapshots` table created from init script; `T.ar_ap_snapshots` handle present).
2. Ensure `GL_DOUBLE_ENTRY_ENABLED=true` and OFB-014 backfill has completed (otherwise `reconcile_ar`/`reconcile_ap` will show non-zero variance with `gl_enabled: true`).
3. Set `AR_AP_SUBLEDGERS_ENABLED=true` and restart the backend.
4. Optionally trigger initial snapshots via `POST /ui/gl/ar-ap/ar/snapshot` and `POST /ui/gl/ar-ap/ap/snapshot` to establish a baseline.
5. No data migration is needed: the subledgers derive their data from existing tables which are already populated.

## 10. Open Questions / Assumptions

1. **Assumption**: OFB-014's `T.gl_journal` table and `gl_journal_table_name` setting are delivered by OFB-014 (not OFB-013). The `get_ar_control_account_balance` and `get_ap_control_account_balance` functions in this spec reference `T.gl_journal` but gracefully return 0 when that table is empty. OFB-015 must be coded to not hard-fail if `T.gl_journal` does not yet exist (use `try/except ClientError`).

2. **Assumption**: The `AR_AP_SUBLEDGERS_ENABLED` flag is separate from `GL_DOUBLE_ENTRY_ENABLED`. This allows deploying the AR/AP aging views without requiring the full GL double-entry posting engine, which is useful for finance teams who want open-item visibility before OFB-014 is stable. Validate with engineering whether a combined flag is preferred.

3. **Assumption**: Invoices without a `"paid"` status are treated as open items. The ledger entry `state="settled"` is the closest proxy for "paid." This means an invoice that was created for a charge that later settled will correctly disappear from AR. Invoices created for charges that are permanently `"pending"` (unusual but possible in dev) will accumulate in the AR aging view. Confirm with finance stakeholders whether this is acceptable behavior or whether a `"paid"` status should be added to `invoices.py` as a prerequisite.

4. **Assumption**: AP aging covers only creator payout requests (`T.creator_payouts`), not the raw `owed_settled_cents` / `owed_pending_cents` balance fields on `T.billing`. The rationale is that `BAL_FIELDS` represent earnings credited to the creator's platform wallet (an internal liability), while payout requests represent the formal AP claim where the creator has explicitly requested an external transfer. If the `BAL_FIELDS` balances should also appear in AP (as accrued but unpaid creator earnings), a second AP aging view would be needed. Validate scope with finance.

5. **Assumption**: System-wide AR aging using `GSI2 = ADMIN_ALL` scans all invoices on the `T.invoices` table. This table will grow without bound. The `ar_aging_scan_limit=5000` default prevents runaway queries, but the cursor-based pagination means a complete system-wide aging view may require many sequential API calls on large deployments. Consider whether a pre-computed rollup (similar to `platform_financial_dashboard.py` daily rollups at `financial_rollups.py`) is warranted for production at scale.

6. **Open question**: Should `save_ar_snapshot` and `save_ap_snapshot` be callable from a scheduled background task (similar to `start_audit_export_scheduler_task` in `app/services/audit_export_schedule.py`)? This would enable automated daily snapshots for trending without requiring ROOT user interaction. If yes, add a `start_ar_ap_snapshot_task` startup hook to `app/main.py` gated by a new `AR_AP_SNAPSHOT_SCHEDULER_ENABLED` flag. This is not in scope for OFB-015 but should be noted for OFB-017/018.

7. **Assumption**: The `items` list in `AgingOut` is included for drill-through capability. OFB-017's accounting UI will display individual line items. However, truncating at 500 (per the security note in Section 7) means the UI must surface a "pagination required" message for large AR/AP positions. Confirm UX requirements with the OFB-017 designer.
