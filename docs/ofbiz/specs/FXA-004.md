# FXA-004 — Pydantic models for assets, schedules & work orders

## 1. Summary & Goal

FXA-004 adds all Pydantic request/response models needed by the Fixed Assets module to `app/models.py`. No service logic, no router, no DynamoDB I/O — only model declarations. The models anchor every downstream FXA ticket: FXA-005 (asset register service), FXA-006 (depreciation schedule), FXA-007 (router), FXA-012 (work-order service), and FXA-013 (work-order router) all import these shapes directly.

The goal is that after this ticket:

- `from app.models import FixedAssetIn, FixedAssetPatchIn, FixedAssetOut, FixedAssetDisposeIn` all succeed.
- `from app.models import DepreciationPeriodOut, DepreciationScheduleOut` succeed.
- `from app.models import MaintenanceOrderIn, MaintenanceOrderTransitionIn, MaintenanceOrderOut` succeed.
- All models validate required fields, enforce integer-cents money constraints, and reject negative costs and invalid method strings at Pydantic parse time (before any service logic runs).
- `net_book_value_cents` is computed as a property — never stored — and never falls below `salvage_value_cents`.
- `depreciation_method` accepts only the literal string `"straight_line"`; any other value produces a 422 from FastAPI's request validation.

The models are purely additive. With `FIXED_ASSETS_ENABLED=false` (the default from FXA-002) no endpoint calls these models, but they are always importable and have no effect on existing shop/cart/orders/billing/inventory paths.

### 2.3 Integer timestamps: `now_ts()` contract

`app/core/time.py:2` defines `now_ts() -> int: return int(time.time())`. All timestamp fields in the fixed-assets models are declared as `int` (Unix seconds), not `str` or `datetime`. This is consistent with `ReservationOut.created_at: int = 0` at `app/models.py:626`, `ReturnOut.created_at: int = 0` at `app/models.py:666`, and `InventoryRecordOut.updated_at: int = 0` at `app/models.py:592`.

### 2.4 DynamoDB `Decimal` round-trip

DynamoDB stores all numeric attributes as `Decimal`. When a service hydrates a `FixedAssetOut` or `DepreciationPeriodOut` directly from a DDB `get_item` result, integer fields like `acquisition_cost_cents`, `accumulated_depreciation_cents`, and `period_end_ts` will arrive as `Decimal`. The `field_validator(..., mode="before")` `coerce_to_int` pattern (as at `app/models.py:2912`) must be applied to all `int` fields on the three `*Out` models and on `DepreciationPeriodOut` to prevent `ValidationError` at serialization time.

### 2.5 GL account ID fields

FXA-001 (section 3.2, lines 251–254 of `docs/ofbiz/specs/FXA-001.md`) established that the asset row stores four GL account IDs as optional strings:

- `gl_asset_account_id` — OFB-013 Fixed Assets account.
- `gl_accum_depr_account_id` — OFB-013 Accumulated Depreciation contra-asset account.
- `gl_depr_expense_account_id` — OFB-013 Depreciation Expense account.
- `gl_gain_loss_account_id` — OFB-013 Gain/Loss on Disposal account (FXA-011).

These are optional on `FixedAssetIn` (caller may omit them and let FXA-008 supply defaults) and nullable on `FixedAssetOut` (they may not be set on older records).

### 2.6 `net_book_value_cents` derivation rule

The ticket acceptance criteria state: `net_book_value_cents = acquisition_cost_cents - accumulated_depreciation_cents`, floor at `salvage_value_cents`. This is a pure computation, never written to DynamoDB. It is computed as a `@model_validator(mode="after")` or `@property` on `FixedAssetOut`. The FXA-001 spec (section 3.2, line 300) specifies: `max(salvage_value_cents, acquisition_cost_cents - accumulated_depreciation_cents)`.

## 4. API / Service Design

FXA-004 ships no endpoint and no service function. The sole deliverable is new model classes in `app/models.py`. This section defines the exact class signatures so that FXA-005, FXA-006, FXA-007, FXA-012, and FXA-013 can import them without modification.

### 4.1 `FixedAssetIn` — request body for asset creation

```python
class FixedAssetIn(BaseModel):
    name: str = Field(min_length=1, max_length=200)
    asset_class: str = Field(min_length=1, max_length=50)
    # e.g. "equipment", "furniture", "software", "vehicle", "land"
    acquisition_cost_cents: int = Field(gt=0)
    salvage_value_cents: int = Field(ge=0)
    useful_life_months: int = Field(ge=1, le=1200)
    acquired_at: int  # Unix timestamp (int, from now_ts() or caller-supplied)
    depreciation_method: Literal["straight_line"] = "straight_line"
    correlation_id: Optional[str] = Field(default=None, max_length=128)
    gl_asset_account_id: Optional[str] = Field(default=None, max_length=128)
    gl_accum_depr_account_id: Optional[str] = Field(default=None, max_length=128)
    gl_depr_expense_account_id: Optional[str] = Field(default=None, max_length=128)
    gl_gain_loss_account_id: Optional[str] = Field(default=None, max_length=128)

    @model_validator(mode="after")
    def salvage_below_cost(self) -> "FixedAssetIn":
        if self.salvage_value_cents >= self.acquisition_cost_cents:
            raise ValueError(
                "salvage_value_cents must be strictly less than acquisition_cost_cents"
            )
        return self
```

**Validation enforced at parse time:**

- `acquisition_cost_cents` must be `> 0` (`Field(gt=0)`). Zero or negative → 422.
- `salvage_value_cents` must be `>= 0` (`Field(ge=0)`). Negative → 422.
- `useful_life_months` must be in `[1, 1200]` (1 to 100 years). Outside range → 422.
- `salvage_value_cents >= acquisition_cost_cents` → `ValueError` in the `model_validator` → 422 with `detail` containing `"salvage_value_cents must be strictly less than acquisition_cost_cents"`.
- `depreciation_method` not `"straight_line"` → 422 (Literal constraint).
- `acquired_at` is a raw `int` with no upper bound constraint. Callers supply a Unix timestamp; values in the distant future are legal (pre-registration of assets not yet acquired).

### 4.2 `FixedAssetPatchIn` — request body for partial update

```python
class FixedAssetPatchIn(BaseModel):
    name: Optional[str] = Field(default=None, min_length=1, max_length=200)
    asset_class: Optional[str] = Field(default=None, min_length=1, max_length=50)
    gl_asset_account_id: Optional[str] = Field(default=None, max_length=128)
    gl_accum_depr_account_id: Optional[str] = Field(default=None, max_length=128)
    gl_depr_expense_account_id: Optional[str] = Field(default=None, max_length=128)
    gl_gain_loss_account_id: Optional[str] = Field(default=None, max_length=128)
```

Cost, salvage value, useful life, acquired_at, and depreciation_method are **not** patchable after creation — immutable fields in the register. The service (FXA-005) enforces this by ignoring them even if somehow included in the request body; they are simply not present on `FixedAssetPatchIn`, so FastAPI will not accept them without raising a 422 for unknown fields (if the router configures `model_config = ConfigDict(extra="forbid")`). The spec recommends `extra="ignore"` (default Pydantic v2 behavior) for forward-compatibility; the service explicitly reads only the fields present on `FixedAssetPatchIn`.

### 4.3 `FixedAssetOut` — response for a single asset

```python
class FixedAssetOut(BaseModel):
    asset_id: str
    owner_sub: str
    name: str
    asset_class: str
    acquisition_cost_cents: int
    salvage_value_cents: int
    useful_life_months: int
    acquired_at: int
    depreciation_method: str
    status: str  # active | fully_depreciated | disposed
    accumulated_depreciation_cents: int
    net_book_value_cents: int  # computed: see model_validator below
    gl_asset_account_id: Optional[str] = None
    gl_accum_depr_account_id: Optional[str] = None
    gl_depr_expense_account_id: Optional[str] = None
    gl_gain_loss_account_id: Optional[str] = None
    created_at: int = 0
    updated_at: int = 0
    correlation_id: Optional[str] = None

    @field_validator(
        "acquisition_cost_cents",
        "salvage_value_cents",
        "useful_life_months",
        "acquired_at",
        "accumulated_depreciation_cents",
        "created_at",
        "updated_at",
        mode="before",
    )
    @classmethod
    def coerce_decimal_to_int(cls, v: Any) -> int:
        """DynamoDB returns numeric attributes as Decimal; coerce to int."""
        if v is None:
            return 0
        return int(v)

    @model_validator(mode="after")
    def compute_net_book_value(self) -> "FixedAssetOut":
        raw = self.acquisition_cost_cents - self.accumulated_depreciation_cents
        self.__dict__["net_book_value_cents"] = max(self.salvage_value_cents, raw)
        return self
```

The `compute_net_book_value` validator runs after all field validators. Because `FixedAssetOut` is used only for serialization (the service constructs it from a DDB item dict), the `net_book_value_cents` field is populated by the validator and then serialized normally by FastAPI. The service never writes `net_book_value_cents` to DynamoDB — it is a derived field.

**`net_book_value_cents` invariant**: After the validator, `net_book_value_cents >= salvage_value_cents` always holds. When `accumulated_depreciation_cents` equals the depreciable base (`acquisition_cost_cents - salvage_value_cents`), the result equals `salvage_value_cents`. Any over-posting scenario (should not occur in correct service logic but is guarded here) is clamped to `salvage_value_cents`.

## 5. Detailed Behavior & Edge Cases

### 5.1 `depreciation_method` validation

`FixedAssetIn.depreciation_method` is typed as `Literal["straight_line"]` with a default of `"straight_line"`. FastAPI resolves the request body via Pydantic, so:

- Omitting `depreciation_method` from the JSON body → field defaults to `"straight_line"`.
- Supplying `"straight_line"` → accepted.
- Supplying `"declining_balance"`, `""`, or any other string → Pydantic raises `ValidationError` → FastAPI returns HTTP 422 with a body indicating the invalid enum value.

No service-level check is required; the model itself enforces the constraint.

### 5.2 `net_book_value_cents` floor semantics

The `compute_net_book_value` validator on `FixedAssetOut` ensures:

```
net_book_value_cents = max(salvage_value_cents, acquisition_cost_cents - accumulated_depreciation_cents)
```

Scenario table:

| `acquisition_cost_cents` | `salvage_value_cents` | `accumulated_depreciation_cents` | `net_book_value_cents` |
|---|---|---|---|
| 100 000 | 10 000 | 0 | 100 000 |
| 100 000 | 10 000 | 45 000 | 55 000 |
| 100 000 | 10 000 | 90 000 | 10 000 (floor) |
| 100 000 | 10 000 | 95 000 | 10 000 (floor, over-posted guard) |

The over-posted guard (`accumulated_depreciation_cents > depreciable_base`) should not occur in correct service logic (FXA-009 stops incrementing when `fully_depreciated`), but the model clamps it defensively.

### 5.3 Integer-cents with DynamoDB `Decimal` round-trip

All `int`-typed fields on `*Out` models use a `field_validator(..., mode="before")` coercion. Without this, Pydantic v2 raises `ValidationError` when it encounters `Decimal('100000')` from a DDB response. This is the same pattern as `coerce_to_int` at `app/models.py:2912–2918`.

The validator must handle `None` returns defensively: for required fields (e.g. `period`, `amount_cents`) the service guarantees the field is always set, but the validator uses `int(v)` directly and lets `None` propagate as a `ValidationError` if the field is non-optional. For optional fields (`posted_at`, `cost_cents`, etc.) the validator explicitly returns `None` when `v is None`.

### 5.4 `acquired_at` as a caller-supplied timestamp

`FixedAssetIn.acquired_at` is a raw `int` with no `ge`/`le` bounds. The caller supplies the actual acquisition timestamp (which may be in the past for assets registered after the fact). The service does not validate that `acquired_at` is in the past or within some window — this is deliberate, as retroactive asset registration (e.g., capitalizing last year's server purchase) must be supported.

### 5.5 Cross-field consistency on `FixedAssetDisposeIn`

The `proceeds_fields_consistent` validator (`FixedAssetDisposeIn`, section 4.5) runs only if the caller supplies at least one of `proceeds_payment_intent_id` / `proceeds_amount_cents`. Disposal with neither → cash-less disposal, fully legal. Disposal with `proceeds_payment_intent_id` but no `proceeds_amount_cents` → 422. This prevents the service from attempting a Stripe refund with an unknown amount.

### 5.6 `FixedAssetPatchIn` — no cost/life fields

`FixedAssetPatchIn` intentionally omits `acquisition_cost_cents`, `salvage_value_cents`, `useful_life_months`, `acquired_at`, and `depreciation_method`. These fields are economically immutable once an asset is registered and its schedule generated (changing them would invalidate already-posted depreciation journal entries). The FXA-005 service enforces this at the DDB write level, but the model-level omission means the router will never receive these fields via the PATCH body.

If a future ticket (not in scope) needs to correct an erroneous cost at registration, that would require a new `FixedAssetCorrectIn` model and a separate endpoint with an audit trail — not a PATCH on the existing model.

### 5.7 `MaintenanceOrderTransitionIn` — cost vs. status constraint

The `cost_only_on_completion` validator (section 4.9) fires at HTTP request parse time. A UI that sends `target_status="in_progress"` with `cost_cents=5000` will receive a 422 immediately, before the service's state-machine check (`VALID_TRANSITIONS`, FXA-012) runs. This layered approach ensures both the model and the service enforce the invariant independently.

### 5.8 `DepreciationScheduleOut` summary fields

`total_periods`, `posted_periods`, and `remaining_periods` on `DepreciationScheduleOut` are computed by the service (FXA-006) from the list of `DepreciationPeriodOut` items before constructing the response. They are not validator-computed on the model itself — the service assembles the list first, then counts. This avoids a second pass over the list inside the model.

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

**SECOPS-007:** Pure model code has no `if S.dev_mode` branch. The same validation logic runs in dev (DynamoDB Local + moto) and prod (real DynamoDB). DynamoDB returns `Decimal` in both environments, so the `coerce_decimal_to_int` validators fire in both.

**Idempotency:** Models are stateless; they have no idempotency concerns. The idempotency contracts (`asset_id = sha256(correlation_id)[:32]`, `journal_id = sha256(f"{asset_id}:period:{period}")[:32]`) live in the service layer (FXA-005, FXA-009) and are merely documented by the `correlation_id` field on the input models.

**Security:** No PII beyond `owner_sub` (a Cognito opaque sub, not an email address). GL account IDs (`gl_*_account_id`) are internal accounting identifiers, not sensitive. No secrets, tokens, or credentials appear in any model.

**Input length caps** on string fields (e.g. `name: Field(max_length=200)`, `description: Field(max_length=2000)`) prevent oversized DynamoDB attribute writes (DDB attribute values have a 400 KB item limit but reasonable caps protect against accidental large payloads).

## 10. Open Questions / Assumptions

1. **`net_book_value_cents` mutability in `FixedAssetOut`**: Pydantic v2 `BaseModel` fields are mutable by default (unlike `dataclass(frozen=True)`). The `compute_net_book_value` validator sets `self.__dict__["net_book_value_cents"]` directly because `self.net_book_value_cents = ...` would call `__setattr__` and trigger another validation cycle. The assumption is that `ConfigDict(frozen=False)` (the default) is acceptable for `*Out` models. If the team decides to use `ConfigDict(frozen=True)` for `FixedAssetOut`, the validator must use `model_construct` or `object.__setattr__` — the approach should match whatever convention the team adopts for computed fields.

2. **`net_book_value_cents` field declaration**: The field is declared as `net_book_value_cents: int` on `FixedAssetOut`, meaning the caller must supply it at construction time (or it will raise). Because the `model_validator(mode="after")` overwrites it unconditionally, services should pass `net_book_value_cents=0` as a dummy value when constructing from a DDB item. An alternative is to declare it `net_book_value_cents: int = 0` with a default. This spec recommends the default of `0` to avoid requiring the service to supply a throw-away value. Downstream tickets (FXA-005) must not pass a computed value — let the validator compute it.

3. **`FixedAssetPatchIn` extra fields**: Pydantic v2 defaults to `extra="ignore"` — unknown fields in the request body are silently dropped. The spec does not set `ConfigDict(extra="forbid")` on patch models. If the team prefers strict validation (future-field-proof), `extra="forbid"` is a one-line addition.

4. **`acquired_at` timestamp validation**: The spec imposes no upper or lower bound on `acquired_at`. An alternative would be `ge=0` (reject Unix epoch zero or negative timestamps). The assumption is that a bound of `ge=0` is safe and should be added — but the ticket description does not mention it, so it is deferred to FXA-005 if the service layer needs it.

5. **`MaintenanceOrderIn.scheduled_for` as raw `int`**: No `ge` constraint on `scheduled_for`. If the team wants to enforce that scheduled maintenance is in the future, that validation belongs in the service (FXA-012), not the model — maintenance orders can be created for past events (retroactive recording). The spec assumes no temporal constraint on `scheduled_for` at the model level.

6. **`DepreciationScheduleOut` fields `total_periods`, `posted_periods`, `remaining_periods`**: These are computed summary fields supplied by the service. The model could alternatively derive them from `len(periods)` and a count of `posted` items in a `model_validator`. The spec leaves the computation in the service for clarity and testability. If the team prefers model-level derivation, a `model_validator(mode="after")` can compute them without changing the public API shape.

7. **`FixedAssetListOut` field name `items` vs. `assets`**: The spec uses `items` for consistency with other list shapes in the codebase. If the team prefers `assets` (more self-documenting), that is a one-word rename. Either choice is acceptable; the spec assumes `items` to match the pattern used by `DepreciationScheduleOut.periods` and `MaintenanceOrderListOut.items`.
