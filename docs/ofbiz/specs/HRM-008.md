# HRM-008 — Payroll disbursement reuses the single billing/ledger path (no fork)

**Type:** Feature | **Priority:** P0 | **Estimate:** 3 days
**Milestone:** 3 — Payroll & GL Hook

---

## 1. Summary & Goal

HRM-008 adds `post_payroll_run(payroll_run_id, *, actor_sub)` to `app/services/hr_payroll.py`. When called against an `APPROVED` payroll run, it records one **money-out** ledger entry per payroll line by calling the existing primitive `billing_shared.new_ledger_entry(...)` (`app/services/billing_shared.py:224`) with `reason="payroll"` and an `extra` dict carrying `employment_id`, `party_id`, and `payroll_run_id`.

The hard constraints are:

1. **No fork of the billing path.** Payroll disbursement must use the same `new_ledger_entry` / `settle_or_reverse_ledger` primitives that Stripe, PayPal, and CCBill charges use. It must never invent a local ledger writer (the pattern in `app/services/org_billing.py:103` — a hand-rolled `record_org_ledger_entry` that does not call `new_ledger_entry` and does not emit `ledger_date` — is the exact anti-pattern to avoid).

2. **Idempotency per `(payroll_run_id, employment_id)`.** Re-posting an already-`POSTED` run or retrying after a partial failure must never produce duplicate ledger entries. The deterministic correlation id `sha256(f"payroll:{payroll_run_id}:{employment_id}")` drives a `ConditionExpression="attribute_not_exists(sk)"` guard on each `billing` table write.

3. **Atomic status transition only after all lines succeed.** The run transitions `APPROVED → POSTED` in `T.hr` only after every per-line ledger write to `T.billing` completes. A partial failure leaves the run `APPROVED` so the operator can safely retry.

4. **Zero-line runs are valid.** A run with `line_count=0` transitions to `POSTED` immediately with no ledger writes.

The existing shop, cart, orders, subscriptions, and messaging surfaces are byte-for-byte unchanged when `S.hr_payroll_enabled` is `False` (the default).

## 2. Context & Current State

### 2.1 `billing_shared.new_ledger_entry` — the sole money-out primitive

`app/services/billing_shared.py:224` defines:

```python
def new_ledger_entry(
    *,
    key_name: str,
    key_value: str,
    entry_type: str,
    amount_cents: int,
    state: str,
    reason: str,
    meta: Optional[Dict[str, Any]] = None,
    extra: Optional[Dict[str, Any]] = None,
) -> Tuple[str, Dict[str, Any]]:
```

It stamps `ledger_date` (via `ledger_date_for_ts(ts)` at `billing_shared.py:253`) onto every item, which powers the `GSI_LEDGER_DATE` index used by `platform_financial_dashboard.py:147` to aggregate daily financial data. Any code that writes ledger items without calling this function silently breaks the dashboard — as `app/services/org_billing.py:103-123` demonstrates: its hand-rolled `record_org_ledger_entry` uses the same `LEDGER#{ts}#{id}` SK format but never sets `ledger_date`, so org ledger entries do not appear in `GSI_LEDGER_DATE` queries. Payroll must not repeat this mistake.

The function returns `(sk, item)`. The caller is responsible for writing `item` to the correct billing table using `ddb_put(T.billing, item)` — this is the pattern used at `app/routers/billing.py:1136`, `:1244`, `:1316`.

### 2.2 `settle_or_reverse_ledger` — the sole reversal primitive

`app/services/billing_shared.py:262` is the single reversal path:

```python
def settle_or_reverse_ledger(
    table: Any,
    key_name: str,
    key_value: str,
    ledger_sk_value: str,
    new_state: str,
) -> None:
```

A future cancellation of a posted payroll run (e.g., a correction run) must call this function with `new_state="reversed"`, never fork a new money-movement path. HRM-008 writes entries in `state="settled"` (payroll disbursement is settled-on-post, not pending); reversal is a follow-on concern.

### 2.3 Billing table PK convention

`billing_shared.user_pk` at `app/services/billing_shared.py:23-24` returns `f"USER#{user_id}"`. The `T.billing` table uses `pk` (lowercase) as the DynamoDB hash key (`scripts/local-ddb-init.py:68-77`). All existing consumer-side ledger entries use `pk=USER#{user_sub}` as the partition key.

For payroll, each line is a money-out from the **platform/organisation** to the employee. The appropriate `pk` is the platform's own ledger partition: `PAYROLL#{payroll_run_id}`. This keeps all payroll entries in a dedicated partition that does not pollute a user's consumer billing history, while still appearing in the `GSI_LEDGER_DATE` index (since `ledger_date` is denormalized by `new_ledger_entry`). The `key_name` parameter passed to `new_ledger_entry` is `"pk"` and `key_value` is `f"PAYROLL#{payroll_run_id}"`.

Precedent: `app/services/group_treasury.py:642` uses `pk="PLATFORM#ESCROW"` for the escrow wallet partition in the same `T.billing` table. `app/services/ad_billing.py:243` uses `pk="PLATFORM#revenue"`. This single-table pattern supports any string pk prefix.

### 2.5 `T.hr` payroll data layout — HRM-007 deliverable

From the HRM-007 spec (`docs/ofbiz/specs/HRM-007.md`):

- Run META: `PK=PAYROLL#{payroll_run_id}` / `SK=META` — carries `status`, `line_count`, `total_gross_cents`, `period_start`, `period_end`, `currency`.
- Line items: `PK=PAYROLL#{payroll_run_id}` / `SK=LINE#{employment_id}` — carries `employment_id`, `party_id`, `gross_cents`, `pay_rate_cents`, `pay_period`, `currency`, `status`.

Co-location in the same PK partition allows a single `query` to retrieve both the run and all lines in one round-trip.

### 2.6 Deterministic-id idempotency pattern

`app/core/crypto.py:13-14` defines `sha256_str(s: str) -> str` via `hashlib.sha256(s.encode()).hexdigest()`. This produces a 64-hex-character digest. The ledger correlation id per line is:

```
corr_id = sha256_str(f"payroll:{payroll_run_id}:{employment_id}")[:32]
```

This is the same length-32 truncation used in the messaging idempotency pattern (cited in HRM-007 spec §2.7). The resulting `entry_id` is `f"payroll_{corr_id}"` (prefixed to make origin legible in the DDB item). The SK on the billing table becomes `LEDGER#{ts}#{entry_id}` via `billing_shared.ledger_sk(ts, entry_id)` at `billing_shared.py:220-221`.

Because the `entry_id` is deterministic from `(payroll_run_id, employment_id)`, the `LEDGER#{ts}#payroll_{corr_id}` SK will be the same on any retry for the same pair. The idempotency guard is a conditional `put_item` on `T.billing` with `ConditionExpression="attribute_not_exists(sk)"`. On `ConditionalCheckFailedException`, the line is treated as already posted and processing continues. This is equivalent to the one-time-use `RECOVERY#CONSUMED#{jti}` pattern used in `app/services/cart_reminders.py` and the `attribute_not_exists` guard in `app/services/purchase_history.py:233`.

**A note on timestamp determinism:** `billing_shared.ledger_sk` embeds `ts` (the current Unix timestamp). Two retries at different seconds will produce different SK values for the same `entry_id`. The conditional guard checks `attribute_not_exists(sk)` on the *full SK*, so a new-timestamp retry would succeed even if a prior write exists. To make the idempotency guard timestamp-independent, the implementation must check the billing table for an existing entry with the matching `entry_id` *before* calling `new_ledger_entry`, OR must fix the `ts` to a run-stable epoch (the run's `created_at`). See §5.2 for the chosen approach.

## 3. Data Model

HRM-008 introduces no new DynamoDB tables. It writes to two existing tables:

### 3.1 New items written to `T.billing`

One ledger entry per payroll line, persisted at:

```
pk  = "PAYROLL#{payroll_run_id}"      (str, the billing table hash key)
sk  = "LEDGER#{ts}#{entry_id}"         (str, via billing_shared.ledger_sk)
```

| Attribute | DDB type | Value |
|---|---|---|
| `pk` | S | `"PAYROLL#{payroll_run_id}"` |
| `sk` | S | `"LEDGER#{ts_of_posting}#{entry_id}"` — `ts_of_posting` is the run's `created_at` (not `now_ts()`) to keep it stable across retries |
| `entry_id` | S | `f"payroll_{sha256_str('payroll:{run_id}:{employment_id}')[:32]}"` — deterministic |
| `ts` | N | Same integer as embedded in `sk` |
| `type` | S | `"debit"` — money-out from the platform |
| `amount_cents` | N | `line["gross_cents"]` (integer, non-negative) |
| `state` | S | `"settled"` — payroll disbursement is settled-on-post |
| `reason` | S | `"payroll"` — the value HRM-010 maps to a GL journal |
| `ledger_date` | S | `ledger_date_for_ts(ts)` — UTC date string, written by `new_ledger_entry` at `billing_shared.py:253` |
| `employment_id` | S | From `extra` — FK to `EMPLOYMENT#{employment_id}` in `T.hr` |
| `party_id` | S | From `extra` — denormalized PERSON party of the employee |
| `payroll_run_id` | S | From `extra` — FK to `PAYROLL#{payroll_run_id}` in `T.hr` |

The `employment_id`, `party_id`, and `payroll_run_id` are passed via the `extra` dict argument of `new_ledger_entry` (per `billing_shared.py:255-256`: `if extra: item.update(extra)`). This follows the same pattern as `extra={"stripe_payment_intent_id": ..., "provider": "stripe"}` used in `billing.py:1134`.

### 3.2 Updated item in `T.hr` — run META

After all line ledger entries succeed, the run META item (`PK=PAYROLL#{payroll_run_id}` / `SK=META`) is updated:

| Attribute change | From | To |
|---|---|---|
| `status` | `"APPROVED"` | `"POSTED"` |
| `GSI1PK` | `"PAYROLL#APPROVED"` | `"PAYROLL#POSTED"` |
| `posted_by` | absent | `actor_sub` |
| `posted_at` | absent | `now_ts()` at post time |
| `updated_at` | `approved_at` | `now_ts()` at post time |

### 3.3 Updated items in `T.hr` — line items

After all ledger entries succeed, each `LINE#{employment_id}` item's `status` is updated from `"DRAFT"` (or `"APPROVED"` — see §10.1) to `"POSTED"` and a `ledger_sk` attribute is written for back-reference:

| Attribute change | Value |
|---|---|
| `status` | `"POSTED"` |
| `ledger_sk` | The `sk` of the billing entry (`"LEDGER#{ts}#{entry_id}"`) |

This allows operators to cross-reference a payroll line to its ledger entry without scanning the billing table.

### 3.4 No new DynamoDB tables or GSI changes

HRM-008 writes new partitions (`PAYROLL#{payroll_run_id}`) into the existing `T.billing` table. The `GSI_LEDGER_DATE` index in `scripts/local-ddb-init.py:71-74` already covers all items with a `ledger_date` attribute, regardless of `pk` prefix. No schema migration is required.

## 4. API / Service Design

### 4.1 Extended module: `app/services/hr_payroll.py`

HRM-008 adds functions to the file created by HRM-007. The import block gains:

```python
from botocore.exceptions import ClientError

from app.core.crypto import sha256_str
from app.services.billing_shared import (
    new_ledger_entry,
    settle_or_reverse_ledger,
    ddb_put,
    ledger_date_for_ts,
    ledger_sk as billing_ledger_sk,
)
from app.core.tables import T
```

### 4.2 `_line_correlation_id(payroll_run_id, employment_id) -> str`

```python
def _line_correlation_id(payroll_run_id: str, employment_id: str) -> str:
    """Deterministic entry_id for a (run, employment) pair.

    Returns a 32-char hex digest prefixed with 'payroll_', used as
    the entry_id in the billing ledger.  Stable across retries.
    """
    digest = sha256_str(f"payroll:{payroll_run_id}:{employment_id}")[:32]
    return f"payroll_{digest}"
```

### 4.3 `_stable_ts(run: Dict[str, Any]) -> int`

```python
def _stable_ts(run: Dict[str, Any]) -> int:
    """Return the run's created_at as the stable timestamp for ledger SK construction.

    Using created_at (not now_ts()) ensures the LEDGER SK is identical on every
    retry of post_payroll_run for the same run, making the attribute_not_exists(sk)
    idempotency guard timestamp-independent.
    """
    return int(run["created_at"])
```

### 4.4 `post_payroll_run(payroll_run_id, *, actor_sub) -> Dict[str, Any]`

```python
def post_payroll_run(
    payroll_run_id: str,
    *,
    actor_sub: str,
) -> Dict[str, Any]:
    """
    Disburse an APPROVED payroll run by writing one billing ledger entry per line.

    Transitions the run APPROVED → POSTED only after all line ledger entries
    succeed.  Safe to call multiple times: already-POSTED runs are returned
    immediately (no-op); partially posted runs can be retried safely because
    each per-line billing write is guarded by attribute_not_exists(sk).

    Args:
        payroll_run_id: The run to post.
        actor_sub:      user_sub of the admin initiating posting (for audit log).

    Returns:
        Updated run META item with status="POSTED".

    Raises:
        LookupError: if the run does not exist.
        PayrollRunInvalidTransitionError: if status is not APPROVED or POSTED.
    """
```

**Detailed behaviour:**

1. Fetch run via `get_payroll_run(payroll_run_id)`. If `None`, raise `LookupError("payroll_run_not_found")`.

2. `current_status = run["status"]`.

3. If `current_status == "POSTED"`: return the existing item (idempotent re-post is a no-op).

4. If `current_status != "APPROVED"`: raise `PayrollRunInvalidTransitionError(f"{current_status}→POSTED")`. This prevents posting a `DRAFT` run (must approve first).

5. Fetch all lines via `get_payroll_run_lines(payroll_run_id)`.

6. If `len(lines) == 0`: skip to step 9 (zero-line run, transition directly to `POSTED`).

7. `stable_ts = _stable_ts(run)` — use `run["created_at"]` as the timestamp embedded in the billing SK, making it stable across retries.

8. For each `line` in `lines`:

   a. `entry_id = _line_correlation_id(payroll_run_id, line["employment_id"])`.

   b. Build the billing SK: `billing_sk = billing_ledger_sk(stable_ts, entry_id)` — calls `billing_shared.ledger_sk(stable_ts, entry_id)` → `f"LEDGER#{stable_ts}#{entry_id}"`.

   c. Build `extra = {"employment_id": line["employment_id"], "party_id": line["party_id"], "payroll_run_id": payroll_run_id}`.

   d. Call `_, led_item = new_ledger_entry(key_name="pk", key_value=f"PAYROLL#{payroll_run_id}", entry_type="debit", amount_cents=int(line["gross_cents"]), state="settled", reason="payroll", extra=extra)`. The SK generated internally by `new_ledger_entry` uses `now_ts()` (its internal `ts = now_ts()`). We **override** the SK to our `billing_sk` (stable timestamp) before persisting: `led_item["sk"] = billing_sk; led_item["ts"] = stable_ts; led_item["entry_id"] = entry_id`.

   e. Write to `T.billing` with the idempotency guard:
      ```python
      try:
          T.billing.put_item(
              Item=led_item,
              ConditionExpression="attribute_not_exists(sk)",
          )
      except ClientError as exc:
          if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
              pass  # already posted — safe to continue
          else:
              raise
      ```

   f. Update the line status in `T.hr`:
      ```python
      T.hr.update_item(
          Key={"PK": f"PAYROLL#{payroll_run_id}", "SK": f"LINE#{line['employment_id']}"},
          UpdateExpression="SET #status = :posted, ledger_sk = :lsk",
          ExpressionAttributeNames={"#status": "status"},
          ExpressionAttributeValues={":posted": "POSTED", ":lsk": billing_sk},
      )
      ```

9. Transition the run to `POSTED` in `T.hr`:
   ```python
   ts_now = now_ts()
   T.hr.update_item(
       Key={"PK": f"PAYROLL#{payroll_run_id}", "SK": "META"},
       UpdateExpression=(
           "SET #status = :posted, GSI1PK = :gsi1pk, "
           "posted_by = :actor, posted_at = :ts, updated_at = :ts"
       ),
       ExpressionAttributeNames={"#status": "status"},
       ExpressionAttributeValues={
           ":posted": "POSTED",
           ":gsi1pk": "PAYROLL#POSTED",
           ":actor": actor_sub,
           ":ts": ts_now,
       },
   )
   ```

10. Emit audit event best-effort:
    ```python
    try:
        audit_event(
            "payroll_run.posted", actor_sub,
            payroll_run_id=payroll_run_id,
            line_count=len(lines),
        )
    except Exception:
        pass
    ```

11. Return the updated run via `get_payroll_run(payroll_run_id)`.

## 5. Detailed Behavior & Edge Cases

### 5.1 Idempotent re-post (fully posted run)

`post_payroll_run` called on an already-`POSTED` run returns the existing item at step 3, emitting no audit event, performing no DDB writes. This handles:
- UI double-submit (user clicks "Post" twice).
- Retry after a 5xx from the router (the service call completes but the HTTP response is lost).

### 5.2 Stable-timestamp idempotency

`billing_shared.new_ledger_entry` calls `now_ts()` internally (line `:239`). Two retries at different seconds produce different `ts` values in the generated SK, so the same `entry_id` would get a different SK each time — defeating the `attribute_not_exists(sk)` guard.

The solution: call `new_ledger_entry` normally, then **overwrite** `led_item["sk"]`, `led_item["ts"]`, and `led_item["entry_id"]` with the stable values before the `put_item`. This is safe because `new_ledger_entry` returns the item dict before any write; the caller owns the dict and may mutate it. The `ledger_date` is set from `ledger_date_for_ts(stable_ts)` inside `new_ledger_entry` at `:253` — since `stable_ts` is the run's `created_at` (a past timestamp), `ledger_date` will be the run creation date, not the posting date. This is intentional: the GL journal (HRM-010) should book to the period when the run was created, not when it was posted.

### 5.3 Partial failure and safe retry

If the process crashes mid-loop (e.g., after writing 3 of 10 lines), the run remains `APPROVED` in `T.hr`. On retry:
- `current_status == "APPROVED"` → processing continues.
- Lines already in `T.billing` trigger `ConditionalCheckFailedException` → silently skipped.
- Lines not yet in `T.billing` are written normally.
- Once all lines are written, the `APPROVED → POSTED` transition fires.

The operator does not need to manually intervene. The retry is safe because:
1. The line-level idempotency guard is on the billing table.
2. The status transition is the last write (guarded by the full loop completing).

### 5.4 Zero-line run

A run with `line_count=0` (created when no `ACTIVE` employments exist at run time) transitions directly from `APPROVED` to `POSTED` with no billing writes. This is not an error. The audit event still fires.

### 5.5 Negative or zero gross_cents

`PayrollLine.gross_cents` is computed by `_compute_gross` in HRM-007 and is non-negative by construction (proration of a non-negative `pay_rate_cents` over a positive period). However, `post_payroll_run` should guard defensively:

```python
if int(line["gross_cents"]) < 0:
    raise ValueError(
        f"negative gross_cents on line {line['employment_id']}: {line['gross_cents']}"
    )
```

Zero `gross_cents` (e.g., a zero-rate employment or rounding to zero) writes a `0` ledger entry, which is valid. `new_ledger_entry` accepts `amount_cents=0`.

### 5.6 Attempting to post a DRAFT run

If an admin calls `/ui/hr/payroll/{id}/post` on a `DRAFT` run (skipping the approve step), `post_payroll_run` raises `PayrollRunInvalidTransitionError("DRAFT→POSTED")`. The router returns HTTP 409.

### 5.7 Concurrent post attempts

Two admins simultaneously calling `post_payroll_run` on the same `APPROVED` run both proceed through the per-line loop. Each line write is independently guarded by `attribute_not_exists(sk)`, so exactly one caller succeeds per line. Both callers then attempt the `update_item` to set `status=POSTED`. DynamoDB `update_item` is atomic; both writes succeed (last-writer-wins for `posted_by`/`posted_at`). The final state is correct: `status=POSTED` and all lines written exactly once.

If exact "who posted first" semantics are needed, add `ConditionExpression="attribute_exists(PK) AND #status = :approved"` to the `update_item` call — the second concurrent poster gets `ConditionalCheckFailedException` and re-fetches the already-`POSTED` item. This is an open question (§10.2).

### 5.8 The `reason="payroll"` field in the ledger

The `reason` field is the downstream hook for HRM-010's GL posting mapper. When `gl_posting.py` (OFB-013/OFB-014 deliverable) processes a ledger entry, it inspects `reason` and dispatches to the correct journal mapping. A `reason="payroll"` entry maps to:

```
Dr Salaries & Wages Expense (S.hr_payroll_expense_account_code, default "6000")
Cr Cash / Bank (the standard money-out credit account)
```

HRM-008 has no dependency on `gl_posting.py`. It only writes the ledger entry with the correct `reason`. The GL hook is HRM-010's scope.

### 5.9 Balance rows

`billing_shared.new_ledger_entry` does NOT update balance rows; that is a separate `apply_balance_delta` call made by the router in consumer billing flows. For payroll, there is no consumer-side balance to debit — the entries record money going **out** of the platform, not adjusting a user's wallet. Therefore `apply_balance_delta` is NOT called in `post_payroll_run`. The ledger entry is the authoritative record; any platform-level cash balance tracking is the GL journal's responsibility (HRM-010).

## 7. Dev/Prod Parity (SECOPS-007), Idempotency, Security

### 7.1 SECOPS-007: no dev/prod code branches

`post_payroll_run` contains no `if S.dev_mode:` branches. DynamoDB writes to `T.billing` and `T.hr` behave identically in dev (DynamoDB Local port 8001) and production (real DynamoDB via IAM). The `new_ledger_entry` primitive from `billing_shared` already embodies this parity: all billing code in the codebase calls the same function in both environments.

### 7.2 Idempotency summary

| Operation | Guard | Behaviour on duplicate |
|---|---|---|
| Per-line billing write | `attribute_not_exists(sk)` on `T.billing` | `ConditionalCheckFailedException` → skip, continue |
| Run status `APPROVED→POSTED` | `update_item` (unconditional) | Last-writer-wins; both writers return `POSTED` state |
| Re-post of already-POSTED run | Early return at step 3 | No-op, return existing item |

### 7.3 Money isolation

`post_payroll_run` uses exactly one money path: `new_ledger_entry` from `billing_shared.py`. It does not:
- Call `stripe.PaymentIntent.create` or any payment-provider SDK.
- Call `apply_balance_delta` (no wallet balance involved).
- Implement a local ledger writer (the anti-pattern in `org_billing.py:103`).
- Call `settle_or_reverse_ledger` (entries are written as `state="settled"` directly).

Any reversal of a posted run must use `settle_or_reverse_ledger(T.billing, "pk", f"PAYROLL#{payroll_run_id}", billing_sk, "reversed")` per the plan's "one refund mechanism" constraint.

### 7.4 Authorization

The `/post` endpoint requires `require_admin_or_root_csrf` (imported from `app.auth.policy:100`). Regular `USER`-role callers are rejected at the dependency layer with HTTP 403, before `post_payroll_run` is called. The `actor_sub` written to the run's `posted_by` is the authenticated admin's `user.sub` from the FastAPI dependency — never caller-supplied.

### 7.5 Audit trail

`audit_event("payroll_run.posted", actor_sub, ...)` is written to `T.alerts` (via `app.services.alerts:644`) after the `POSTED` status transition. The event carries `payroll_run_id` and `line_count`. It is best-effort (wrapped in `try/except`) so an alert write failure never blocks the posting result.

## 8. Backward Compatibility & Migration

### 8.1 Additive-only changes

With `HR_ENABLED=0` or `HR_PAYROLL_ENABLED=0` (both default):

- `app/services/hr_payroll.py` gains new functions and imports — no existing function signatures change.
- `app/models.py` gains two optional fields on `PayrollRunOut` and one optional field on `PayrollLineOut` (all `Optional[...] = None`) — existing callers see no breaking change.
- No existing router, service, or test file is modified.
- No change to the `billing` or `hr` DynamoDB table schemas.
- Shop, cart, orders, subscription, messaging, and consumer billing surfaces are byte-for-byte unchanged.

### 8.2 `T.billing` new partitions

The `PAYROLL#{payroll_run_id}` partitions are new. They share the same `T.billing` table (name controlled by `S.billing_table_name`, default `"billing"` at `app/core/settings.py:348`). Existing queries against `T.billing` use either a specific `pk=USER#{user_sub}` key condition or the `GSI_LEDGER_DATE` index keyed on `ledger_date`. Neither query path is affected by new `PAYROLL#` partitions — GSI items only appear when `ledger_date` is present, which is exactly what payroll items will have.

### 8.3 DynamoDB table `billing` — no schema change

The `billing` table definition in `scripts/local-ddb-init.py:67-77` already includes the `GSI_LEDGER_DATE` index with `attr_types={"ledger_date": "S"}`. No new GSIs, no new attribute type declarations, no `just restart` required for the billing table.

### 8.4 Forward-compatibility with HRM-010

The `reason="payroll"` ledger entries written by HRM-008 are the input to HRM-010's GL journal mapper. HRM-010 adds a mapping rule in `gl_posting.py`; it does not modify the billing table schema or the ledger entry format. The `extra` fields (`employment_id`, `party_id`, `payroll_run_id`) are available for the journal entry's narrative/memo. HRM-008 makes no assumption about `gl_posting.py` — the GL hook is a downstream consumer.

## 10. Open Questions / Assumptions

1. **Assumption: `T.hr` uses uppercase `PK`/`SK`.** HRM-007 spec §10.3 flags this: if HRM-002 uses lowercase `pk`/`sk`, the service must change key names throughout. Verify against the HRM-002 implementation before writing any code.

2. **Open question: concurrent-post "exactly one poster" semantics.** The current design uses last-writer-wins for `posted_by`/`posted_at`. If the product requires a canonical first-poster, add `ConditionExpression="#status = :approved"` to the `update_item` at step 9 — the losing concurrent poster receives `ConditionalCheckFailedException` and re-fetches the already-`POSTED` item. Deferred pending product decision.

3. **Assumption: `billing_shared.new_ledger_entry` + SK override is the correct approach for stable timestamps.** An alternative is to add a `ts_override` parameter to `new_ledger_entry`. However, mutating the existing primitive would require touching every call site and is out of scope. The caller-side overwrite of `led_item["sk"]`, `led_item["ts"]`, and `led_item["entry_id"]` is simpler, keeps `billing_shared.py` unchanged, and is safe because the dict is owned by the caller. Verify that `new_ledger_entry` does not perform any side effects on the returned dict (confirmed: it returns a newly constructed dict at `billing_shared.py:242-259`).

4. **Assumption: line `status` field transitions with the run.** The HRM-007 spec notes line items have `status` (§3.2 of HRM-007.md: `"Always 'DRAFT' when created; transitions with the run (HRM-008 sets to 'POSTED')"`) but does not define an `APPROVED` status for lines. HRM-008 transitions lines from whatever their current `status` is directly to `"POSTED"` — no intermediate `APPROVED` line status is needed. Verify the HRM-007 implementation does not add a separate approve step for lines.

5. **Assumption: `ddb_put(T.billing, item)` in `billing_shared.py` uses `T.billing` from `app.core.tables`, not a module-level import.** If `billing_shared` imports `T` at module load time (via `from app.core.tables import T`), then the moto test setup must also patch `billing_shared.T.billing` (in addition to `tables_mod.T.billing`) to intercept writes. The test base class in §9.1 includes this patch. Confirm the import pattern in `billing_shared.py` at implementation time.

6. **Assumption: `get_payroll_run_lines` returns all lines without a cursor.** For runs with many employees (>100), the `query` in `get_payroll_run_lines` may need to paginate via `LastEvaluatedKey`. HRM-007's spec (§4.5) defines `get_payroll_run_lines` as a single `query` call without pagination. For the initial implementation this is acceptable (HR-lite with a small employee count). Add pagination if `line_count > 100` is a realistic scenario.

7. **Assumption: payroll ledger entries use `"debit"` as `entry_type`.** Money going out from the platform is a `debit` on the platform's ledger (Dr expense, Cr cash). The `type` field on billing entries is used as a filter in `platform_financial_dashboard.py:_categorise_entry` — confirm it does not cause unintended bucketing by verifying the dashboard's categorisation logic against `reason="payroll"` at implementation time.

8. **Open question: should a run with all lines already posted (partial retry reaching 100% completion) re-fire the `APPROVED → POSTED` update?** Yes — the `update_item` is safe to replay: if the run is already `POSTED`, the `update_item` sets `status="POSTED"` again and overwrites `posted_by`/`posted_at` (last-writer-wins). This is consistent with §5.1. The alternative (checking `status` before the `update_item`) would add a DDB read per retry, which is unnecessary.
