# SEC-011: Open Redirect (SAML RelayState) + Host-Header Trust — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

Two related URL-injection vulnerabilities allow an attacker to redirect authenticated users to attacker-controlled origins after a successful SSO or eIDV flow, or to steal eID callback tokens by forging the server-side callback URL that is handed to the external identity provider.

**Open redirect via SAML RelayState**: The ACS (Assertion Consumer Service) endpoint at `POST /saml/acs` reads the IdP-supplied `RelayState` form parameter and redirects the newly-authenticated user to that URL unconditionally (`app/routers/sso_saml.py:212`). Because there is no validation against an allowlist of same-origin paths or known trusted origins, a crafted SAML flow can send the victim—along with a freshly-set session cookie—straight to `https://attacker.com/capture`.

**Host-header trust**: The eIDV `start_eid_verification` endpoint at `app/routers/kyc_eidv.py:87` computes the provider callback URL from `str(request.base_url)`. Starlette's `request.base_url` is derived from the `Host` (or `X-Forwarded-Host`) HTTP header. An attacker who can influence that header—via a misconfigured reverse proxy, a stolen legitimate HTTP request replay, or a SSRF-like pivot—causes the platform to register `https://attacker.com/v1/kyc/eid/callback` with the external eID provider; when the provider redirects the victim after successful eID verification it sends the `session_id` + `assertion` + `signature` to the attacker.

An analogous but already-fixed pattern exists for magic links (`app/services/magic_links.py:54`) and share links (`app/services/file_share_links.py:138`), both of which correctly use `S.public_base_url`. The eIDV endpoint is the only remaining `request.base_url` usage in the auth flow.

- **Type**: security-fix (open redirect + trust boundary)
- **Severity**: High (CVSS ~7.4 for the RelayState redirect; ~6.8 for host-header eIDV)
- **Status**: Open
- **Area**: `app/routers/sso_saml.py`, `app/routers/kyc_eidv.py`
- **Attacker class**: 🌐 any-user (external IdP controls RelayState in SP-initiated flow); authenticated user or network-level attacker for eIDV
- **Dependencies**: SECOPS-007 (dev/prod parity — fix must work with DDB Local and mock eIDV)

## 2. Current-State Investigation (what exists today)

### 2.1 SAML RelayState — unvalidated redirect

`app/routers/sso_saml.py:73–231` is the ACS handler. The critical path:

```
line 78:  relay_state = form.get("RelayState", "/")
...
line 212: redirect = RedirectResponse(url=str(relay_state or "/"), status_code=303)
          set_session_cookies(redirect, session)
```

No validation is applied between lines 78 and 212. The value is cast to `str` and used verbatim. Since `relay_state` comes from a POST body parameter populated by the IdP's SAML response, any IdP (or a malicious actor who can replay/construct a SAML response) can inject an absolute URL.

The dev-bypass path (`_dev_bypass_acs`, `sso_saml.py:546–579`) has the same flaw at line 568:
```python
redirect = RedirectResponse(url=relay_state or "/", status_code=303)
```

The `prepare_request_data` helper in `app/services/sso_saml_sp.py:180–191` pulls `host` directly from `request.headers.get("host", "localhost")` and uses it to assemble the IdP redirect URL at line 182, which is a related but lower-severity issue (SAML AuthnRequest host forgery).

### 2.2 eIDV callback URL built from Host header

`app/routers/kyc_eidv.py:86–96`:
```python
callback_base = str(request.base_url).rstrip("/")
result = create_verification_session(
    case_id=case_id,
    scheme=body.scheme,
    user_sub=user.sub,
    callback_base=callback_base,
)
```

`request.base_url` in Starlette is `{scheme}://{host}/`. The `scheme` is taken from `request.url.scheme` and `host` from `request.headers["host"]`. If the load balancer passes `X-Forwarded-Host` and the server is configured to trust it (or if `Host` itself is forged in a direct connection test), `callback_base` becomes attacker-controlled. The resulting callback URL—something like `https://attacker.com/v1/kyc/eid/callback?session_id=...`—is sent to the external eIDV provider as the redirect destination. The eIDV provider then sends the signed assertion and signature query parameters to the attacker's server.

### 2.3 Dev vs prod behavior today

In dev mode (`S.dev_mode=True`, `S.kyc_eid_mock_enabled=True`), `create_verification_session` in `app/services/kyc_eidv.py` builds a mock callback URL using the same `callback_base` argument. The vulnerability is present in both environments.

Magic links at `app/services/magic_links.py:54` and file share links at `app/services/file_share_links.py:138` both use `S.public_base_url`—the correct pattern.

## 3. Gap / Threat Analysis

### 3.1 SAML RelayState open redirect — full attack scenario

**Preconditions**: SSO is enabled (`S.sso_saml_enabled=True`), at least one tenant provider exists. The attacker controls a domain they can serve content from.

**Attack steps**:
1. Attacker crafts a malicious SP-initiated login URL: `GET /saml/login?tenant=victim_tenant`. The normal flow sends a `RelayState` of `/` back to the IdP.
2. More directly: attacker constructs a SAML POST to `/saml/acs` with a valid `SAMLResponse` (legitimate IdP-signed) and `RelayState=https://attacker.com/harvest`.
3. Server completes authentication, sets `ui_session`, `ui_csrf`, and `ui_access_token` cookies, then emits `303 Location: https://attacker.com/harvest`.
4. Browser follows the redirect to attacker's site. The request carries the same-site cookies (SameSite=Lax means they travel on top-level cross-site navigations triggered by the server-side redirect). The attacker can exfiltrate the cookie values via Referer headers or query strings appended to the redirect.

**Impact**: Session hijacking of any user performing SSO login. Severity is amplified because SAML logins often originate from enterprise users with elevated trust/access.

**Why current controls fail**: The only guard present is the assertion-replay cache (`_is_assertion_replayed`, line 127), which prevents reuse of the `SAMLResponse` itself—but RelayState is not part of the signed assertion in most SAML deployments, so an attacker can re-use a legitimately-signed response with a changed `RelayState`.

### 3.2 Host-header eIDV callback injection

**Preconditions**: KYC eIDV is enabled. The attacker can make authenticated requests to `/v1/kyc/cases/{case_id}/eid/start` with a crafted `Host` header (valid in penetration testing; possible in prod if the reverse proxy forwards `Host` without normalization or if `X-Forwarded-Host` is accepted).

**Attack steps**:
1. Attacker creates a KYC case (legitimate), then calls `POST /v1/kyc/cases/{case_id}/eid/start` with `Host: attacker.com`.
2. Backend computes `callback_base = "https://attacker.com"` and passes it to `create_verification_session`.
3. The eIDV provider is told to redirect to `https://attacker.com/v1/kyc/eid/callback?session_id=X&assertion=Y&signature=Z`.
4. Victim completes eIDV on the provider's site; provider redirects to attacker's server.
5. Attacker receives `session_id`, `assertion`, and `signature`—enough to call `/v1/kyc/eid/callback` themselves and complete the verification as the victim.

**Code sites that must change**:
- `app/routers/sso_saml.py:78` (RelayState read), `sso_saml.py:212` (redirect), `sso_saml.py:568` (dev-bypass redirect)
- `app/routers/kyc_eidv.py:87` (callback_base derivation)
- `app/services/sso_saml_sp.py:183` (host header in `prepare_request_data`)

## 4. Proposed Design / Fix

### 4.1 RelayState validation

Add a `_validate_relay_state(value: str) -> str` helper that accepts only:
- Empty string or `None` → return `"/"`
- A string that is a relative path (starts with `/`, does not start with `//`) and does not contain `://` → return as-is after stripping leading whitespace
- A full URL whose `netloc` matches `S.public_base_url` (parsed once at startup) → return its path component only (strip origin)
- Everything else → return `"/"`

```python
from urllib.parse import urlparse

def _validate_relay_state(value: str | None, *, public_base_url: str = "") -> str:
    v = (value or "").strip()
    if not v:
        return "/"
    if v.startswith("//") or "://" in v:
        # absolute URL — only allow if it's on our own origin
        try:
            parsed = urlparse(v)
            allowed = urlparse(public_base_url)
            if parsed.netloc and parsed.netloc == allowed.netloc:
                return parsed.path or "/"
        except Exception:
            pass
        return "/"
    if v.startswith("/"):
        return v
    return "/"
```

Apply at `sso_saml.py:78` immediately after reading `RelayState`:
```python
relay_state = _validate_relay_state(
    form.get("RelayState"), public_base_url=S.public_base_url
)
```

Also apply the same guard in `_dev_bypass_acs` at line 568.

### 4.2 Callback base from `S.public_base_url`

In `app/routers/kyc_eidv.py:86–87`, replace:
```python
callback_base = str(request.base_url).rstrip("/")
```
with:
```python
callback_base = S.public_base_url.rstrip("/")
```

`S.public_base_url` defaults to `http://localhost:8000` in dev (`.env.local.example`) and is set to the real HTTPS hostname in prod.

### 4.3 `prepare_request_data` host hardening

`app/services/sso_saml_sp.py:183`: the `http_host` field is used only to build the SP entity ID and ACS URL inside `build_saml_settings`. Those values should come from the provider record (already stored as `sp_entity_id` and `sp_acs_url` in DDB) rather than from the request host. The `prepare_request_data` function is only needed for the mock SP which also has no live cryptographic verification; document that in prod this would be replaced with python3-saml, which should use `S.public_base_url` for the SP base.

### 4.4 Settings change (no new env vars needed)

`S.public_base_url` already exists (`app/core/settings.py:324`). No new fields are required.

### 4.5 Dev/prod parity (SECOPS-007)

- **Dev**: `S.public_base_url = "http://localhost:8000"`. The `_validate_relay_state` guard works the same way — tests that send `RelayState=/dashboard` pass; tests that send `RelayState=https://evil.com` get redirected to `/`.
- **Prod**: `S.public_base_url = "https://app.example.com"`. The same guard applies. No AWS dependency added.
- The mock eIDV provider (`/mock/eid/verify`) is unaffected because it is not the one receiving the callback; the fix only changes what URL is *sent to* the real provider.

### 4.6 Additional host-header hardening across other flows

Beyond the eIDV endpoint, the SAML SP helper `prepare_request_data` at `app/services/sso_saml_sp.py:183` also reads `host` from the request headers:
```python
host = request.headers.get("host", "localhost")
```
This value is used to build the SP entity ID and ACS URL fields inside `build_saml_settings`. In the mock SP those values come from the provider record stored in DDB (the `sp_acs_url` and `sp_entity_id` fields set at provider creation time), so the risk is lower: the host header affects only the runtime request context passed to the SAML lib, not the actual ACS redirect target. However, a future move to a real SAML library (python3-saml) that trusts the `http_host` field for ACS URL construction would re-introduce the host-injection risk. Add a comment and, when python3-saml is integrated, construct `http_host` from `S.public_base_url` instead.

Password-reset links: `app/services/magic_links.py:54` correctly uses `S.public_base_url`:
```python
link = f"{S.public_base_url}/ui/passwordless/verify?token={raw_token}"
```
Share links: `app/services/file_share_links.py:138` uses `S.share_link_base_url` (a separate setting, default `http://localhost:3000/share`). Both of these are the reference implementations to follow.

### 4.7 Alternatives considered

- **Full CSRF state parameter** (sign RelayState with the session key and verify it on return): more robust but requires a round-trip via the IdP's state parameter mechanism, which varies by SAML binding. Overkill for the current mock SP; noted as a future improvement.
- **Trusted allowlist as a Settings field** (e.g. `S.saml_relay_state_allowed_prefixes`): acceptable for multi-domain deployments; not needed for single-domain.
- **Reject all absolute `RelayState` values**: simplest possible fix. Downside: breaks deployments where the IdP sets `RelayState` to an absolute URL on the SP's own origin (legitimate in some enterprise SAML profiles). The origin-check approach is more compatible.

## 5. Testing, Verification & Rollout

### pytest unit tests (`tests/`)

| Test | Expected outcome |
|------|-----------------|
| `test_relay_state_external_url_blocked` — ACS called with `RelayState=https://evil.com` | Response redirects to `/` not `https://evil.com` |
| `test_relay_state_internal_path_allowed` — ACS called with `RelayState=/dashboard` | Response redirects to `/dashboard` |
| `test_relay_state_protocol_relative_blocked` — `RelayState=//evil.com/x` | Redirects to `/` |
| `test_relay_state_empty` — `RelayState=""` | Redirects to `/` |
| `test_relay_state_same_origin_absolute` — `RelayState=https://localhost:8000/x` with matching `public_base_url` | Redirects to `/x` (path only) |
| `test_eid_callback_url_uses_public_base_url` — `start_eid_verification` called with `Host: attacker.com` | `callback_base` in `create_verification_session` is `http://localhost:8000` |
| `test_dev_bypass_acs_relay_validated` | Dev bypass also sanitizes RelayState |

All tests run offline — the mock SAML SP (`MockSamlAuth`) and mock eIDV provider (`build_mock_assertion`) already avoid external calls.

### Playwright E2E (`frontend/e2e/`)

Add `sso-saml-security.spec.ts`:
- Inject a SAML ACS POST with malicious `RelayState` and assert the browser lands on `/` not `attacker.com`.
- Inject a valid ACS POST with `RelayState=/dashboard` and assert the browser lands on `/dashboard`.

These tests can run against the dev stack; the mock SAML bypass (`dev_bypass=1`) will be used since a real IdP is not available.

### Manual QA steps

1. Run `just up` + `just e2e`; confirm the SSO-related spec still passes.
2. Send `curl -X POST /saml/acs -d 'SAMLResponse=...&RelayState=https://evil.com'` (with a dev-bypass header) and confirm the response is `303 Location: /`.
3. Send `curl -X POST /v1/kyc/cases/test/eid/start -H 'Host: attacker.com' ...` and confirm the returned `redirect_url` starts with `http://localhost:8000`.

### Observability

Log a `WARN`-level message (e.g. `"relay_state_rejected: %s"`) when an external URL is stripped so it shows up in the dev log and in CloudWatch in prod. Tie to the existing `audit_event` call already present at `sso_saml.py:219`.

### Observability additions

Beyond the `WARN` log for rejected RelayState values, add an audit event `sso_relay_state_sanitized` that records the original (sanitized) value and the accepted replacement. This feeds into the existing audit trail (the `audit_event` call at `sso_saml.py:219` already writes to `T.alerts`). In prod, these events appear in CloudWatch and can be alerted on: repeated `sso_relay_state_sanitized` events from the same IP indicate an active open-redirect attack attempt.

Similarly, log a `WARN eIDV_callback_base_from_host_header` if `request.base_url` differs from `S.public_base_url` at the time the fix is deployed during a transition period — this helps identify misconfigured load-balancer environments where `Host` normalization is not working correctly.

### Rollout & rollback

- **No schema changes** (no DDB table modifications).
- Deploy as a single atomic PR; zero backward-compat risk since the redirect target changes from an attacker URL to `/`, which was the intended behavior.
- For the eIDV callback fix, ensure `PUBLIC_BASE_URL` is set correctly in the production `.env` file before deploying. Verify with `curl -v POST /v1/kyc/cases/{test_case}/eid/start` and confirm `redirect_url` starts with the production HTTPS hostname.
- Rollback: revert the PR. Risk of rollback: none — re-exposes the vulnerability. No data migration is needed.

### Effort estimate

**S** — two targeted one-liner changes + a small helper function + 6 unit tests + audit event additions. Can be merged in a single half-day sprint. The `prepare_request_data` comment and future python3-saml guidance adds another 30 minutes of documentation work.
