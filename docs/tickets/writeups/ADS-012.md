# ADS-012: Self-Promotion & Content Boosting — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

ADS-012 introduces a one-click "Boost" mechanism that lets creators pay from their wallet to elevate the reach of their own posts, videos, or broadcasts. Unlike the full advertiser campaign system (ADS-001 through ADS-010), content boosting is a self-service, no-configuration path: the creator picks a budget (integer cents) and a duration (seconds), the budget is charged up-front, and the boosted content receives a ranking bonus in any feed or serving pipeline that opts in. This sidesteps the overwhelm of the full campaign manager for creators who just want short-term amplification.

- **Type**: Feature
- **Priority**: Medium
- **Status**: Implemented (backend + router + E2E spec)
- **Owning area**: Ads / Monetization — creator-facing
- **User persona**: Content creator (existing subscriber base, wants incremental reach); platform operator (self-service ad revenue)
- **Cross-referenced tickets**: [[ADS-001]] campaign manager (backend reuses the same billing table but does NOT depend on campaign records), [[ADS-005]] sponsored post rendering ("Promoted" badge in feed), [[ADS-007]] billing engine (wallet/ledger patterns reused directly), [[SECOPS-007]] dev/prod parity

## 2. Current-State Investigation (what exists today)

### 2.1 Service layer — `app/services/content_boost.py` (434 lines)

The service is fully implemented. Key design decisions found in the actual code:

**Storage** (`app/services/content_boost.py:190-213`): Boosts are written to the dedicated `content_boosts` DynamoDB table (name from `S.content_boosts_table_name`, defaulting to `"content_boosts"` — `app/core/settings.py:1153`). Each boost record uses PK `BOOST#{boost_id}` / SK `META`. Two GSIs are maintained:
- `GSI1`: `OWNER#{owner_sub}` → `created_at` — supports `list_boosts()` for the owner dashboard
- `GSI2`: `CONTENT#{content_type}#{content_id}` → `ends_at` — supports `active_boost_for_content()` feed elevation hook

**Wallet integration** (`app/services/content_boost.py:64-92`): Charging and refunding delegate entirely to `app/services/billing_shared.py`. `_wallet_charge()` calls `apply_wallet_delta(T.billing, user_pk(owner_sub), -amount_cents)` then writes a settled ledger debit entry with `entry_type="content_boost_charge"`. `_wallet_refund()` does the reverse with `entry_type="content_boost_refund"`. Race-condition safety is provided by the conditional update in `apply_wallet_delta`; a `ConditionalCheckFailedException` is caught and re-raised as `ValueError("insufficient wallet balance")` at line 189.

**Lifecycle logic** (`app/services/content_boost.py:121-139`): `_effective_status()` computes the live status without a database write. A stored status of `cancelled` or `completed` is final. For an `active` boost, the function compares `spent_cents >= budget_cents` (budget exhausted) or `now >= ends_at` (duration elapsed) and returns `completed` in either case. This means status transitions are lazy — the record is only mutated when `record_spend()` is called (line 297-319) or `cancel_boost()` is called.

**Feed elevation hook** (`app/services/content_boost.py:394-433`): `elevate_feed_items()` accepts a list of feed items, queries `active_boost_for_content()` per item (via `GSI2`), adds `BOOST_RANK_WEIGHT = 1000` to the item's score, and sets `is_boosted: True`. The function is non-destructive (copies items). Integration into actual feed ranking pipelines is the responsibility of feed/serving code that calls this function.

**Notable deviation from ticket spec**: The ticket design (section 3.2) specified `content_type` / `content_id` URL path parameters (`/ui/content/{type}/{id}/boost`). The actual implementation uses a flat POST body: `ContentBoostCreate` model (`app/models.py:10936`) takes `content_type`, `content_id`, `budget_cents`, `duration_seconds`. The router prefix is `/ui/ads/boost`, not `/ui/content/...`.

**Also absent from the service**: Auto-targeting (`_auto_targeting()`), per-content-type ownership validation, and boost analytics (impressions/reach/engagement) aggregation from the ad-impressions table. The ticket spec shows these as required, but the implementation omits them in favour of simpler spend tracking via `record_spend()`.

## 3. Gap / Threat Analysis

### 3.1 Missing features relative to spec

| Gap | Spec Section | Impact |
|-----|-------------|--------|
| No content ownership validation | 3.2 | Any user can boost any `content_id` — no check that the caller owns the post/video/broadcast |
| No stats endpoint (impressions, reach, engagement) | 3.2 `get_boost_stats()` | Creators have no visibility into boost effectiveness beyond spend |
| No `POST /ui/content/{type}/{id}/boost` URL shape | 3.3 | Callers must use flat `POST /ui/ads/boost` with body params; ticket spec's example `curl` commands and E2E test sections 392-396 reference the path-based form |
| `BoostDialog.tsx` and `BoostStatsCard.tsx` missing | 3.8-3.9 | No in-feed Boost button; creators must navigate to the boost management page separately |
| No PostCard "Boost" button integration | 3.8 | Core UX entry point from the feed is absent |
| No `"Promoted"` badge on feed items for non-owners | 3.8 | Consumers cannot distinguish boosted content |
| No auto-targeting logic | 3.2 `_auto_targeting()` | All boosts use no targeting (treated as broad); ticket spec intended audience lookalike targeting |
| E2E spec only 7 tests vs 22 planned | 8.2 | Sections 394 (cancellation), 395 (UI), 396 (concurrent/content types) are absent |
| Unit tests absent (`tests/test_content_boost.py`) | 8.1 | No offline pytest coverage |

### 3.2 Abuse vectors

**Wallet race condition**: `create_boost()` checks balance with `_wallet_balance()` (a separate `GetItem`) then calls `apply_wallet_delta()`. Between those two calls a concurrent deduction could leave the wallet negative. The conditional update inside `apply_wallet_delta` is the true safety net, but the error is caught broadly and re-raised as "insufficient balance" — this is correct, but the broad `except Exception` at line 188 could mask unrelated DDB errors.

**Unlimited boost creation**: A user can create an unlimited number of boosts on the same content simultaneously (no duplicate-boost guard). The ticket spec required a 409 on duplicate active boosts (`/error_handling_matrix`). No `ConditionExpression` prevents this.

**Non-owner elevation**: Because `active_boost_for_content()` takes any `content_type` / `content_id`, a user could boost content they don't own, paying their own wallet to elevate another user's content. This is harmless financially (they pay) but skews feed ranking.

## 4. Proposed Design / Fix

### 4.1 Content ownership validation

Add to `create_boost()` before the wallet charge:

```python
# app/services/content_boost.py — add after argument validation (line ~168)
_verify_content_ownership(owner_sub, content_type, content_id)
```

Mirror the pattern from `app/services/sponsorship_deals.py:295-309` (`_verify_content_ownership` for posts). Extend to `video` and `broadcast` content types by querying `T.video_metadata` and `T.broadcasts` respectively.

### 4.2 Duplicate-boost guard

Add a `ConditionExpression` to `T.content_boosts.put_item()` that checks `attribute_not_exists(pk)` is insufficient (multiple boosts can exist). Instead, query `GSI2` for active boosts before writing — if one exists, raise `ValueError("content already has an active boost")` so the router can return 409.

### 4.3 Stats endpoint

Add `get_boost_stats(boost_id)` to `app/services/content_boost.py`. Query `T.ad_impressions` with `GSI` filter on `campaign_id` (the `GSI2` lookup already links boost to content) or maintain a denormalised counter on the boost record updated via `record_spend()`.

Add a `GET /ui/ads/boost/{boost_id}/stats` endpoint to `app/routers/content_boost.py` protected by owner check.

### 4.4 Frontend BoostDialog and PostCard integration

Create `frontend/src/components/shared/BoostDialog.tsx` and `BoostStatsCard.tsx` per ticket section 3.8. Integrate into `frontend/src/pages/feed/PostCard.tsx` — add owner check using `useAuthStore(s => s.user?.sub) === post.user_id`.

### 4.5 Dev/Prod parity (SECOPS-007)

The service already satisfies SECOPS-007 requirements:
- All DDB access via `T.*` handles wired from `S.*_table_name` settings sourced from env vars
- No external AWS calls (no S3, no KMS, no Cognito) in the boost lifecycle
- `apply_wallet_delta` uses DynamoDB Local in dev, DynamoDB in prod — same code path
- Feature flag: add `CONTENT_BOOST_ENABLED` to `app/core/settings.py` and a `_require_enabled()` guard in the router (pattern already used by `app/routers/ad_creative_affiliate.py:_require_enabled()`)

### 4.6 Alternatives considered

The ticket spec proposed separate URL paths per content type (`/ui/content/post/{id}/boost`). The flat-body approach in the implementation is simpler to route and test, and the content type is already validated against `ALLOWED_CONTENT_TYPES`. No change recommended.

### 5.6 Effort and risks

**Effort**: M total — backend gaps (ownership validation, duplicate guard, stats endpoint): ~1 day; `elevate_feed_items()` wiring into newsfeed router: ~0.5 day; frontend BoostDialog and PostCard integration: ~2 days; E2E spec expansion from 7 to 22 tests: ~1 day; unit tests: ~0.5 day.

**Critical risk**: Feed ranking integration — `elevate_feed_items()` (`app/services/content_boost.py:409`) is implemented and returns a correctly re-ranked list, but it is not called from `app/routers/newsfeed.py`. Creators are being charged for boosts that have no effect on their content's reach. Every boost campaign initiated before this wiring is a misleading charge. Highest-priority fix before public launch.

**Financial risk**: No duplicate-boost guard means a creator could create multiple simultaneous boosts for the same content, paying budget multiple times. Each active boost query via `GSI2` returns all active boosts for the content — the `active_boost_for_content()` function (`app/services/content_boost.py:376`) returns only the newest one for ranking purposes but all are charged. Add a pre-write check to `create_boost()` before the wallet deduction.

**Dev/Prod parity**: Fully satisfied — `T.content_boosts` uses DDB Local in dev with no AWS dependencies. Feature flag `CONTENT_BOOST_ENABLED` (to be added) will follow `S.ad_creative_affiliate_enabled` pattern.
