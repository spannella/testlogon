# ADS-008: Ad Analytics Dashboard — Investigation & Implementation Write-up

## 1. Summary & Classification

ADS-008 delivers a comprehensive analytics dashboard for advertisers: pre-computed daily/hourly rollups of impressions, clicks, spend, and completions; KPI summary cards with period-over-period comparison; time-series line charts; creative/surface/targeting breakdowns; and CSV export. The feature introduces a dedicated `AdAnalyticsRollups` DynamoDB table and a background rollup computation job alongside four read-only API endpoints at `/ui/ads/analytics/`.

- **Type**: Feature
- **Priority**: Medium
- **Status**: Implemented — service, router, frontend page, and DDB table all present
- **Owning area**: Advertising / Analytics
- **Affected personas**: Advertisers (their campaign KPIs)
- **Cross-references**: ADS-001 (account/campaign hierarchy), ADS-004 (raw impression data), ADS-007 (spend data for rollups); downstream: ADS-011 (Advertiser API exposes same analytics), ADS-017 (optimization), ADS-018 (admin platform analytics)
- **Dev/Prod parity (SECOPS-007)**: `ad_analytics_rollups` table on DDB Local in dev, AWS DynamoDB in prod. Rollup computation reads from `ad_billing` (also local). No external services involved.

### 2.5 Rollup Computation Architecture

`compute_hourly_rollup()` (line 168) derives impression/click counts from the billing ledger (`get_campaign_spending()`) rather than scanning the raw `ad_impressions` table. This is a pragmatic dev-mode simplification: the `ad_impressions` table stores events by date partition (`AD_IMP#{date}`) with no campaign-level index, so a full scan per campaign would be expensive. The rollup job is not automatically triggered — it must be called externally (via a cron job or direct API call). There is no scheduled background task in the codebase that calls `compute_hourly_rollup()`.

### 2.6 Dev vs. Prod Behavior

In dev, rollup data is seeded by calling `compute_hourly_rollup()` directly, or by writing rollup items directly to DDB Local for deterministic test data. In prod, the same function runs periodically (intended to be triggered by a cron/EventBridge rule that calls a management endpoint). No prod-specific code paths exist.

## 3. Gap / Threat Analysis

### 3.1 No Automated Rollup Trigger

The most significant gap: `compute_hourly_rollup()` exists but is never called by anything in the running application. Without an automated trigger, the `AdAnalyticsRollups` table will remain empty and all dashboard endpoints will return zeros. The ticket design (§9) describes a "background rollup job" but no such job is registered.

Affected file: There is no scheduled task in `app/main.py`, no cron definition, and no background thread calling `compute_hourly_rollup()`.

### 3.2 Rollup Source Limitation

`compute_hourly_rollup()` (line 176) calls `get_campaign_spending(campaign_id, limit=1000)` to count billing ledger entries. This reads at most 1000 entries regardless of actual volume. For campaigns with more than 1000 impressions/clicks in a period, the rollup will undercount. The `limit=1000` cap is hard-coded without a pagination loop.

Also, the rollup aggregates all historical spend for the campaign rather than filtering to the specific hour being computed. A rollup at 14:00 will include impressions from 00:00–13:59 as well.

### 3.3 GSI `ByAccountDate` Sort Key Type

The `ByAccountDate` GSI uses `date` (String) as its sort key. The `between()` range queries in `_fetch_daily_rollups()` (line 233) rely on lexicographic comparison of ISO date strings (`"2026-05-01"` < `"2026-05-29"`), which works correctly for `YYYY-MM-DD` format. However, hourly dates (`"2026-05-29T14"`) are also stored in the `date` field, and string comparisons across different granularities could produce unexpected results if the account-level GSI queries are used for hourly granularity. The `FilterExpression=Attr("period").eq(granularity)` on line 244 mitigates this.

### 3.4 No Rollup for the `by_creative`, `by_surface`, `by_targeting` Maps

`compute_hourly_rollup()` writes empty dicts (`{}`) for `by_creative`, `by_surface`, and `by_targeting` (lines 201–203). The `get_breakdown()` function depends on these maps being populated. All breakdown endpoint responses will return empty arrays until these maps are populated by a more complete rollup computation.

### 3.5 Authorization — No Cross-Account Leakage

Account ownership is verified before every analytics endpoint via `_require_account_owner()` (ads.py:500, 513, 528, 542). The GSI query by `account_id` correctly scopes results to the verified account. No cross-account data leakage is possible.

### 3.6 CSV Export No Pagination on Timeseries

`export_csv()` (line 143) calls `get_timeseries()` which is bounded by DDB query results. If rollups are not yet populated, the CSV will contain only headers — which is acceptable behavior (documented in the error handling matrix).

## 4. Proposed Design / Fix

### 4.1 Automated Rollup Trigger

Add a FastAPI startup background task that runs `compute_hourly_rollup()` for all active campaigns:

```python
# app/core/ad_analytics_scheduler.py
import asyncio, logging
from datetime import datetime, timezone

logger = logging.getLogger(__name__)

async def _rollup_loop():
    while True:
        await asyncio.sleep(3600)  # run hourly
        try:
            from app.services.ad_campaigns import list_all_active_campaigns
            from app.services.ad_analytics import compute_hourly_rollup
            hour = datetime.now(timezone.utc).strftime("%Y-%m-%dT%H")
            for camp in list_all_active_campaigns():
                compute_hourly_rollup(camp["campaign_id"], camp["account_id"], hour)
        except Exception:
            logger.exception("ad_analytics_rollup_failed")

def start_rollup_scheduler(app):
    @app.on_event("startup")
    async def _start():
        asyncio.create_task(_rollup_loop())
```

Register in `app/main.py` `create_app()`. In dev mode, also provide a `POST /ui/admin/ads/analytics/rollup` endpoint to trigger rollup on demand for tests.

### 4.2 Fix Rollup Source to be Hour-Scoped

`compute_hourly_rollup()` should filter billing entries by the `created_at` timestamp rather than pulling all history:

```python
# Inside compute_hourly_rollup():
hour_start = int(datetime.strptime(hour, "%Y-%m-%dT%H")
                  .replace(tzinfo=timezone.utc).timestamp())
hour_end = hour_start + 3600
entries = [
    e for e in get_campaign_spending(campaign_id, limit=10000)
    if hour_start <= int(e.get("created_at", 0)) < hour_end
]
```

Also add a pagination loop to `get_campaign_spending()` so `limit=10000` does not silently truncate high-volume campaigns (using `LastEvaluatedKey`).

### 4.3 Populate `by_creative` and `by_surface` Maps

Extend `compute_hourly_rollup()` to group filtered billing entries by `meta.creative_id` and `meta.model` (which encodes the surface):

```python
by_creative: Dict[str, Dict] = {}
for e in entries:
    cid = e.get("meta", {}).get("creative_id", "unknown")
    if cid not in by_creative:
        by_creative[cid] = {"impressions": 0, "clicks": 0, "spend_cents": 0}
    if e["entry_type"] == "impression_charge":
        by_creative[cid]["impressions"] += 1
    elif e["entry_type"] == "click_charge":
        by_creative[cid]["clicks"] += 1
    by_creative[cid]["spend_cents"] += int(e.get("amount_cents", 0))
rollup["by_creative"] = by_creative
```

### 4.4 Dev/Prod Parity (SECOPS-007)

The rollup scheduler is pure DynamoDB I/O — no AWS-specific services involved. The same code path runs on DDB Local in dev and AWS DynamoDB in prod. Feature flag: `AD_ANALYTICS_ROLLUP_ENABLED = _to_bool(os.environ.get("AD_ANALYTICS_ROLLUP_ENABLED", "true"))` in `app/core/settings.py`. When false, the scheduler loop exits immediately after startup.

### 5.4 Rollout

- **Phase 1**: Deploy rollup table + service with `AD_ANALYTICS_ROLLUP_ENABLED=false`. Manual rollup via on-demand endpoint only.
- **Phase 2**: Enable analytics API endpoints (`AD_ANALYTICS_ENABLED=true`). Dashboard visible but shows only manually triggered rollup data.
- **Phase 3**: Enable `AD_ANALYTICS_ROLLUP_ENABLED=true` for automated hourly rollups.
- **Rollback**: Set `AD_ANALYTICS_ROLLUP_ENABLED=false` — background task stops; existing rollup data remains queryable.
