# KYC-004: Proof of Residency Verification — Investigation & Implementation Write-up

## 1. Summary & Classification

**KYC-004** adds structured handling for proof-of-residency documents (utility bills, bank statements, government letters, tax documents, lease agreements) with metadata capture (document type, issuing entity, document date), address extraction and fuzzy matching against the user's profile mailing address, and a 90-day recency validation gate. The backend service (`app/services/kyc_residency.py`, 692 lines), router (`app/routers/kyc_residency.py`), and DynamoDB table (`kyc_residency_documents`) are fully implemented. User-facing pages (`KycResidencyVerificationPage.tsx`, `KycResidencyReviewQueuePage.tsx`) exist. Integration into the KYC-001 admin case detail page is the remaining work.

- **Type**: Feature (residency document management with address matching and recency gate)
- **Priority**: Medium — required for enhanced and high_risk intake profiles; standard profiles skip this check
- **Status**: Backend + standalone pages implemented; case detail integration and readiness gate extension pending
- **Persona**: Applicant (USER), KYC reviewer (ADMIN/ROOT)
- **Dependencies**: KYC-001 (admin detail page), KYC-002 (document upload infrastructure pattern). Downstream: KYC-008 (residency verification status feeds risk score).
- **Cross-references**: [[SECOPS-007]] — mock extraction provider in dev (deterministic from filename patterns, `S.kyc_residency_real_extraction_enabled`). [[KYC-023]] — address fields are PII; displayed in admin view but not encrypted at rest in the current implementation (PII encryption for residency docs is a KYC-023 extension).

## 2. Current-State Investigation

### 2.1 Backend Service: `app/services/kyc_residency.py`

The `KycResidencyStore` dataclass (analogous to `KycDocumentVerificationStore`) wraps `T.kyc_residency_documents`. The service is the most complete of the KYC sub-feature services at 692 lines.

**Allowed document types** (line 50–56): `utility_bill`, `bank_statement`, `government_letter`, `tax_document`, `lease_agreement`.

**Status lifecycle**: `pending → verified` (recent + address matches) or `pending → rejected` (old OR mismatch) or `pending → expired` (document date beyond recency window).

**Address matching** (fully implemented):

- `_STREET_ABBREVIATIONS` map (lines 76–96): `st→street`, `ave→avenue`, `blvd→boulevard`, and 16 more including directionals (`n→north`, etc.) and unit types (`apt→apartment`, `ste→suite`).
- `_US_STATES` map (lines 98–113): full US state abbreviation↔full name pairs for all 50 states.
- `_COUNTRY_ALIASES` map (lines 115–126): `us/usa/united states of america → united states`, `uk/gb → united kingdom`, `ca/can → canada`.
- Overall address match: `match` = all fields match; `partial` = city + postal_code match but line1 differs; `mismatch` = city or postal_code mismatch.

**Mock extraction provider** (deterministic, gated by `not S.kyc_residency_real_extraction_enabled`):
- Default filename → extracted address matches the profile.
- `*_mismatch_*` → city changed to "Mismatch City".
- `*_partial_*` → line1 changed.
- `*_expired_*` → `document_date` set to `now - 120 days` (triggering recency failure).
- `*_fail_*` → extraction fails.

**Recency check** (`_check_recency`): Accepts an injectable `now` for deterministic tests. Computes `(now_date - document_date).days`. Configurable threshold via `S.kyc_residency_recency_days` (default 90).

**Profile address loading** (`_load_profile_address`): Calls `app.services.profile.get_profile(user_sub)` and extracts the `mailing_address` dict.

**Auto-decision on extraction**: When extraction completes (mock or real), the service immediately computes the address match and sets `status=verified` if `recency_valid AND address_match.status in (match, partial)`, `status=rejected` otherwise, `status=expired` if not recency-valid.

## 3. Gap / Threat Analysis

### 3.1 Readiness Gate Gap (High Priority)

Without the readiness gate extension, users with `intake_profile=enhanced` or `high_risk` can submit their KYC case without any residency document. This violates AML/CDD (Customer Due Diligence) requirements for enhanced due diligence. The fix is a single check added to `_readiness_for_case` (4 lines of code) and the corresponding query to `kyc_residency_documents`.

The check must use the `ByStatus` GSI with `status=verified` and filter by `case_id` — or list all documents for the user and filter. Because documents are uploaded before case submission, the check queries `T.kyc_residency_documents` directly from the readiness function. For performance, a `user_sub + case_id` filter via `FilterExpression` on the GSI scan is acceptable (low document volume).

### 3.2 Address Matching Edge Cases

**Line1 normalization across systems**: The profile may store `"123 Main St"` while the document reads `"123 MAIN STREET APT 4B"`. After normalization, `123 main street apartment 4b` vs `123 main street` — the SequenceMatcher ratio for these strings is ~0.8, which falls below the `match` threshold but above partial. The current implementation uses exact comparison after normalization, not SequenceMatcher ratio — different from KYC-002's name matching. This is correct for address line1 (structural equality is expected); fuzzy matching would produce false positives for different buildings on the same street.

**Non-US addresses**: The normalization maps cover US state abbreviations and a handful of country aliases. International addresses (e.g., UK postcodes, Canadian provinces) are not covered. The `state` field matching will fall back to case-insensitive string comparison, which may produce `mismatch` for `"ON"` vs `"Ontario"`. Acceptable for MVP; a full international normalization set is a follow-up.

**PO Box addresses**: Some users have PO Box as their mailing address. A document from a utility company will show a street address. The city and postal code may still match even when line1 does not, producing `partial` status. Reviewers must assess these manually.

**Document date in the future**: A user could submit a document with a future `document_date`. The recency check only computes `(now_date - document_date).days` — a negative value would set `recency_days` to a negative number and `recency_valid=True` (technically not expired). The fix: add `document_date <= now_date` validation during upload. The Pydantic model should enforce `document_date <= today`.

### 3.3 Case-Level Readiness Coordination

The residency check in `_readiness_for_case` needs to know whether the current case has a verified residency document. The `kyc_residency_documents` table is keyed by `document_id` with no direct case PK. The query must scan the ByStatus GSI for `status=verified` and filter by `case_id` or `user_sub`. Since a user may have residency documents from multiple cases, the `case_id` field is stored on each document and is the correct filter key.

### 3.4 Compliance and Legal

- **90-day freshness**: Regulators (FCA, FinCEN) typically require address documents dated within 3 months. The 90-day default (`S.kyc_residency_recency_days=90`) is correct. The edge case at exactly 90 days must be `valid` (≤ 90 days), not `expired` — `recency_valid = (recency_days <= threshold)`.
- **Multiple documents**: A user can upload multiple residency documents. The readiness gate passes if ANY document is `verified`. This allows users to submit an expired document alongside a valid one without the gate blocking them.
- **Document removal**: The router allows deleting residency documents (`DELETE /`). If a user deletes their only verified document after the case is submitted, the case remains in `submitted` status — there is no retroactive readiness re-check post-submission. The document must only be deletable while the case is in `draft` or `needs_more_info`.
- **PII storage**: The extracted address is stored in the `kyc_residency_documents` DDB table. The address is PII. Currently it is stored in plaintext. KYC-023 field-level encryption should be extended to cover this table as a follow-up.

## 4. Proposed Design / Fix

### 4.1 Readiness Gate Extension (`app/routers/kyc_cases.py:_readiness_for_case`)

```python
def _readiness_for_case(case: dict) -> dict:
    questionnaire = _questionnaire_status_for_case(case, include_submit_gate=False)
    files = _validate_file_requirements(case)
    signature = _signature_status_for_case(case)

    checks = {
        "questionnaire_submitted": bool(questionnaire.get("submitted")),
        "required_files": bool(files.get("ready_for_submit_gate")),
        "signature_completed": bool(signature.get("ready_for_submit_gate")),
    }
    hint_map = { ... }  # as before

    # KYC-004: enhanced/high_risk profiles require a verified residency document
    intake_profile = str(case.get("intake_profile") or "standard")
    if intake_profile in ("enhanced", "high_risk"):
        from app.services.kyc_residency import STORE as RESIDENCY_STORE
        verified_docs = RESIDENCY_STORE.get_verified_docs_for_case(
            case_id=case["kyc_case_id"]
        )
        checks["residency_document"] = len(verified_docs) > 0
        hint_map["residency_document"] = (
            "Upload a recent proof of address (utility bill, bank statement, etc.) "
            "and ensure it is verified."
        )
```

New service method in `kyc_residency.py`:

```python
def get_verified_docs_for_case(self, case_id: str) -> list[dict]:
    """Return all verified residency documents for a case."""
    response = self._table.query(
        IndexName=S.kyc_residency_documents_status_index_name,
        KeyConditionExpression=Key("status").eq("verified"),
        FilterExpression=Attr("case_id").eq(case_id),
    )
    return list(response.get("Items") or [])
```

### 4.2 Document Date Validation

In `KycResidencyUploadRequest` (Pydantic model in `app/models.py`), add a field validator:

```python
@field_validator("document_date")
@classmethod
def document_date_not_future(cls, v: str) -> str:
    from datetime import date
    parsed = date.fromisoformat(v)
    if parsed > date.today():
        raise ValueError("document_date cannot be in the future")
    return v
```

Query `GET /ui/kyc/residency` for existing documents.

### 4.5 Dev/Prod Parity (SECOPS-007)

The service is already compliant with SECOPS-007:
- Mock extraction gated by `S.kyc_residency_real_extraction_enabled=False` (default).
- Injectable `now` for deterministic recency tests.
- S3/DDB via standard factories.
- No outbound calls in dev mode.

The readiness gate extension introduces a DDB read from `kyc_residency_documents`. In dev, this hits DynamoDB Local (:8001). No new infrastructure.

### 4.6 Alternatives Considered

- **Inline residency on the KYC case** — store residency metadata in `case.files[]` (as the ticket originally proposed with `residency_meta`). Rejected in implementation in favor of a separate table, which allows independent lifecycle management and GSI-based status queries.
- **Synchronous readiness check on every GET** — the readiness check is already called synchronously on `GET /{case_id}/readiness` and at submission time. The extra GSI query adds ~1 RCU per readiness check for enhanced profiles. Acceptable.

### 5.5 Rollout

Feature flag `KYC_RESIDENCY_ENABLED` (default `true` in dev, staged in prod). Critical sequencing:

1. Deploy backend readiness gate extension (controlled by `S.kyc_residency_readiness_gate_enabled=false` initially).
2. Deploy frontend residency upload in wizard.
3. Enable `KYC_RESIDENCY_ENABLED=true` in staging — existing non-residency enhanced cases are NOT re-blocked (readiness gate only applies to new submissions).
4. Enable `kyc_residency_readiness_gate_enabled=true` in production after 1 week of monitoring.

**CAUTION**: Enabling the readiness gate in prod means ALL enhanced/high_risk users who haven't uploaded a residency doc will be blocked from submitting. Notify compliance team before enabling the gate. Consider a grace period where the gate warns but does not block (return `ready_to_submit=true` with a `warnings` list).

**Rollback**: Set `kyc_residency_readiness_gate_enabled=false` — enhanced profiles can submit without residency again. Uploaded docs are preserved.

**Effort**: M (6–8 days) — readiness gate extension (1 day), date validator (0.5 day), admin detail tab (3 days), wizard integration (2 days), E2E (1.5 days).
