# SEC-014: Notification / SMS Toll-Fraud / Email Phishing-Relay — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

Verification codes and enrollment challenges are sent to attacker-supplied phone numbers and email addresses before ownership of those destinations is proven by any other means than a per-account rate limit. This enables three distinct abuses:

1. **SMS pumping / toll fraud** — any authenticated user can enroll an arbitrary E.164 phone number as an MFA device (`POST /sms/devices/begin`, `app/routers/mfa_devices.py:108–142`). A single account can drive many distinct phone numbers (limited only by `S.sms_device_limit`), and the Twilio Verify path (`twilio_start_sms` in `app/services/mfa.py:81`) completely bypasses the per-number daily limit enforced by `sms_daily_limit_exceeded` in `app/services/sms_delivery.py:331`.
2. **Email phishing relay** — any authenticated user can enroll an arbitrary email address as an MFA device (`POST /email/devices/begin`, `mfa_devices.py:230–267`). A verification code is sent to that address from the platform's SES domain, providing a legitimate-looking email origin for phishing.
3. **Removal-challenge spam** — removing an existing MFA device (`/sms/devices/{id}/remove/begin` and `/email/devices/{id}/remove/begin`) re-sends codes to linked destinations; these endpoints are rate-limited per-user but not per-destination across accounts.
4. **Registration SMS to arbitrary number** — `register_resend` in `app/routers/register.py:261–273` sends a Twilio Verify SMS to `body.phone` (caller-supplied) for re-send during registration, with only a per-user `can_send_verification` guard (not a per-number global cap).
5. **Enumeration** — `register_resend` and the password-reset / magic-link flows return generic "ok" responses in most cases, but timing differences and error codes in some paths still reveal whether an email/phone is registered.

- **Type**: security-fix (abuse prevention / anti-fraud)
- **Severity**: Critical (SMS toll-fraud can result in thousands of dollars in Twilio charges per hour; phishing relay damages sender reputation)
- **Status**: Open
- **Area**: `app/routers/mfa_devices.py`, `app/services/mfa.py`, `app/services/sms_delivery.py`, `app/routers/register.py`
- **Attacker class**: 🌐 any authenticated user
- **Dependencies**: SECOPS-007 (dev/prod parity — mock SMS/email in dev, Twilio Verify + SES in prod, same code path)

## 2. Current-State Investigation (what exists today)

### 2.1 SMS enrollment — per-user rate limit but no per-number global cap; Twilio Verify bypasses daily limit

`app/routers/mfa_devices.py:108–142` (SMS enroll begin):

```python
rate_limit_or_429(user_sub, "enroll_sms")   # line 112: per-user rate limit only
phone = normalize_phone(body.phone_e164)
...
send_to = list(dict.fromkeys(list_enabled_sms_numbers(user_sub) + [phone]))
for n in send_to:
    twilio_start_sms(n)    # line 133
```

`rate_limit_or_429(user_sub, "enroll_sms")` is a per-user sliding-window check. There is no check for:
- How many **distinct** phone numbers this user has tried to enroll in the last hour.
- Whether the **target phone number** has received verification messages from **any account** recently (cross-account global cap).

`twilio_start_sms` in `app/services/mfa.py:81–92` in prod mode calls:
```python
twilio.verify.v2.services(S.twilio_verify_service_sid).verifications.create(to=to_e164, channel="sms")
```

This is the Twilio Verify API — a completely separate channel from the direct SNS-based `send_sms` function in `app/services/sms_delivery.py:174`. The `send_sms` function checks `sms_daily_limit_exceeded(phone)` at line 211. `twilio_start_sms` does **not** call `sms_daily_limit_exceeded`. The per-number daily limit is therefore silently bypassed for all Twilio Verify sends — which is the send path for all MFA device enrollment and removal challenges.

### 2.2 Email enrollment — sends to arbitrary unverified email

`app/routers/mfa_devices.py:230–267` (email enroll begin):

```python
rate_limit_or_429(user_sub, "enroll_email")   # per-user only
email = normalize_email(body.email)
...
send_to = list(dict.fromkeys(enabled_emails + [email]))
for e in send_to:
    send_email_code(e, "add-email", code)    # line 265
```

`send_email_code` sends an OTP via SES. The `email` value is the attacker-supplied address. There is no cross-account check of how many times this email has received codes across all accounts. An attacker with 100 accounts can send 100 verification emails to any target email address per rate-limit window.

### 2.3 Registration SMS re-send

`app/routers/register.py:261–273`:
```python
if body.delivery_method == "sms":
    if not can_send_verification(username, "sms"):   # per-username (= per-email) check
        raise HTTPException(429, ...)
    ...
    twilio_start_sms(body.phone)    # line 273 — Twilio Verify, bypasses per-number limit
```

`can_send_verification` is keyed on `username` (the registrant's email), not on `body.phone`. An attacker can create many throwaway email accounts and target a single phone number with registration resend requests. Each registration's SMS resend is permitted because each has a fresh per-username rate limit.

### 2.4 Rate-limit architecture

`sms_daily_limit_exceeded` tracks at `DAILY#{phone}` in `T.sms_delivery` (DDB). This is populated by `record_sms_sent` / `record_sms_dev_logged` — both called only within `send_sms`. Since `twilio_start_sms` uses Twilio's Verify API (not `send_sms`), it never increments this counter and never checks it.

In dev mode (`S.dev_mode=True`), `twilio_start_sms` writes a local code to `_dev_sms_codes[to_e164]` (an in-memory dict, `mfa.py:84`) and logs it — no actual Twilio call is made. The per-number daily limit bypass is therefore only exploitable in production, but the code path is identical.

### 2.5 Enumeration

`register_resend` returns `generic_response = {"status": "ok", "available": True}` regardless of whether the email/username exists (line 96–124 of `register.py`). However, timing side-channels exist: when the user does not exist, the code skips both `create_registration_challenge` and `twilio_start_sms`, returning faster than when it must write to DDB and call Twilio.

The password-reset flow (not audited here but referenced in the ticket) similarly risks timing-based enumeration.

### 2.6 Dev vs prod behavior

- **Dev**: `twilio_start_sms` writes to `_dev_sms_codes` (memory); `send_email_code` logs to `S.dev_email_log`. Rate limits write to DDB Local. All abuse paths exist but do not incur real cost.
- **Prod**: `twilio_start_sms` calls Twilio Verify API (paid). `send_email_code` calls SES (paid + reputation risk). The per-number daily limit is in `T.sms_delivery` (DynamoDB).

## 3. Gap / Threat Analysis

### 3.1 SMS toll-fraud via Twilio Verify

**Precondition**: Attacker has one authenticated account or can register multiple.

**Attack (single account)**: Call `POST /sms/devices/begin` with 10 distinct phone numbers in rapid succession. The per-user `rate_limit_or_429(user_sub, "enroll_sms")` allows (for example) 5 attempts per 10 minutes. Between rate-limit windows, an attacker can hit hundreds of phone numbers per day. Each Twilio Verify initiation charges the platform a carrier termination fee (~$0.05–$2.00 for premium-rate numbers).

**Attack (multiple accounts)**: Create 100 throwaway accounts and target a single premium-rate number with 100 verification codes per rate-limit window. The per-number limit in `T.sms_delivery` is never incremented for Twilio Verify sends and therefore never triggers.

**Blast radius**: At $1.00/SMS to a premium-rate number, 1000 sends = $1000 charge to the platform's Twilio account. Sophisticated attackers route SMS to numbers they control and receive Twilio's carrier payouts, profiting from the arbitrage.

### 3.2 Email phishing relay

**Attack**: Create an account; call `POST /email/devices/begin` with `email=target@victim.com`. The platform sends an email from `noreply@yourplatform.com` with subject "Add email device" to `target@victim.com`. The email body contains a 6-digit OTP that the attacker ignores — but the act of receiving an email from a trusted domain can be combined with social engineering ("Your account has been accessed; here is a code...").

## 4. Proposed Design / Fix

### 4.1 Global per-recipient rate limit for all SMS sends

Add a new function `sms_global_recipient_limit_exceeded(phone: str) -> bool` in `app/services/sms_delivery.py` that reads from `T.sms_delivery` at key `GLOBAL#{phone}` with a rolling window (e.g. 10 messages per 24h across all accounts). This counter must be incremented by **all** SMS send paths — both the SNS `send_sms` path and the Twilio Verify path.

```python
def sms_global_recipient_limit_exceeded(phone: str, window_hours: int = 24) -> bool:
    """Cross-account per-recipient cap — applies to ALL send paths."""
    day_key = now_ts() // (window_hours * 3600)
    resp = T.sms_delivery.get_item(
        Key={"pk": f"GLOBAL#{phone}", "sk": f"WIN#{day_key}"},
        ProjectionExpression="#c",
        ExpressionAttributeNames={"#c": "count"},
    )
    return int((resp.get("Item") or {}).get("count", 0)) >= S.sms_global_recipient_daily_limit

def record_sms_global_recipient(phone: str, window_hours: int = 24) -> None:
    day_key = now_ts() // (window_hours * 3600)
    T.sms_delivery.update_item(
        Key={"pk": f"GLOBAL#{phone}", "sk": f"WIN#{day_key}"},
        UpdateExpression="ADD #c :one SET #ttl = :ttl",
        ExpressionAttributeNames={"#c": "count", "#ttl": "ttl"},
        ExpressionAttributeValues={":one": 1, ":ttl": now_ts() + window_hours * 3600 + 3600},
    )
```

Add a new setting `S.sms_global_recipient_daily_limit` (default 10).

### 4.2 Enforce per-number global cap in `twilio_start_sms`

In `app/services/mfa.py:81`, before calling Twilio or logging the dev code:

```python
def twilio_start_sms(to_e164: str) -> None:
    from app.services.sms_delivery import (
        sms_daily_limit_exceeded, record_sms_global_recipient,
        sms_global_recipient_limit_exceeded
    )
    if sms_daily_limit_exceeded(to_e164):
        raise HTTPException(429, "SMS rate limit exceeded for this number")
    if sms_global_recipient_limit_exceeded(to_e164):
        raise HTTPException(429, "Verification SMS limit exceeded")

    if S.dev_mode:
        ...  # existing dev path
        record_sms_global_recipient(to_e164)
        return
    ...  # existing prod Twilio path
    record_sms_global_recipient(to_e164)
```

### 4.3 Per-user distinct-destination window

In `mfa_devices.py:112`, add a per-user distinct-number rolling check before the enrollment is accepted:

```python
# Block if user has tried > N distinct phone numbers in the last hour
distinct_key = f"DISTINCT_SMS#{user_sub}"
# Store a TTL'd set of distinct phone prefixes attempted this hour
# (simple approach: increment a counter, not enumerate numbers for privacy)
rate_limit_or_429(user_sub, "enroll_sms_distinct", limit=S.sms_distinct_per_user_hourly, window=3600)
```

Add setting `S.sms_distinct_per_user_hourly` (default 5). Similarly for email: `S.email_distinct_per_user_hourly` (default 5).

### 4.4 Per-recipient cross-account email cap

Add `email_global_recipient_limit_exceeded(email: str) -> bool` in a new `app/services/email_delivery.py` (or alongside existing email helpers) following the same pattern as the SMS global cap. Check it in `email_devices_begin` at `mfa_devices.py:234` and in `register_resend` at `register.py:264`.

### 4.5 Registration resend: phone number global cap

`register.py:273`: before `twilio_start_sms(body.phone)`, call:
```python
if sms_global_recipient_limit_exceeded(body.phone):
    raise HTTPException(429, "Too many verification SMS to this number; try again later")
record_sms_global_recipient(body.phone)
```

Note: return the `generic_response` even on 429 to avoid leaking enumeration state — but the caller still receives a 429 status code, which is acceptable (different from 200). The key is that 200 responses for known vs unknown accounts should be timing-neutral (use constant-time dummy `send` simulation).

### 4.6 Dev/prod parity (SECOPS-007)

- **Dev**: `twilio_start_sms` writes to `_dev_sms_codes` (memory) and calls `record_sms_global_recipient` against DDB Local. Rate limit checks read from DDB Local. Playwright E2E tests can exhaust the global cap by sending 10 verification requests and asserting the 11th returns 429.
- **Prod**: same code path hits DDB and Twilio Verify. `S.sms_global_recipient_daily_limit` is set higher in prod (e.g. 20) if legitimate users need more flexibility.
- The mock email log in dev (`S.dev_email_log`) is unchanged; the cross-account email counter writes to `T.sms_delivery` (or a new `T.email_delivery` table if preferred).

### 4.7 Alternatives considered

- **Proof-of-ownership before send (CAPTCHA + first-send to known device)**: More robust but disruptive to UX. Noted as a future improvement; the rate-cap approach is the minimum viable fix for immediate deployment.
- **Block international premium-rate number ranges**: Partial mitigation, easily bypassed with VoIP numbers. Not a substitute for per-number caps.

- Counter `email_global_recipient_blocked_total`.

- Alert: if `sms_global_recipient_blocked_total` > 100 in 5 minutes, page on-call (likely active toll-fraud campaign).

### Rollout & rollback

- Add `S.sms_global_recipient_daily_limit` to `.env.local.example` (value 10) and `.env.example` (value 20 for prod).
- DDB `T.sms_delivery` table receives new `GLOBAL#` and `DISTINCT#` key patterns — no schema change needed (same table, new PK prefixes with TTL).
- Rollout: deploy backend only; global caps start counting from zero.
- Rollback: remove the checks; the DDB counter rows expire via TTL harmlessly.
