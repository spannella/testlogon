# KYC-005: Proof of Funds / Source of Funds — Investigation & Implementation Write-up

## 1. Summary & Classification

**KYC-005** introduces financial verification as a complement to identity (KYC-002) and residency (KYC-004) checks. Users declare their source of funds (income category, declared amount, supporting document) and the system assigns a deterministic verification score (0–100) that drives an auto-decision (`verified` / `needs_more_info` / `rejected`). The backend service (`app/services/kyc_proof_of_funds.py`, 330 lines), router (`app/routers/kyc_proof_of_funds.py`), and DynamoDB table (`kyc_proof_of_funds`) are fully implemented. The user-facing frontend page (`KycProofOfFunds.tsx`) exists. An admin reviewer queue and the integration of the verification result into the KYC-001 case detail page are the remaining work.

- **Type**: Feature (AML source-of-funds declaration and document verification with deterministic scoring)
- **Priority**: Medium — required by AML regulations for enhanced/high_risk profiles; standard profiles typically exempt
- **Status**: Backend + user page implemented; admin reviewer queue integration and case detail panel pending
- **Persona**: Applicant (USER), KYC reviewer/compliance (ADMIN/ROOT)
- **Dependencies**: KYC-001 (admin detail page). Downstream: KYC-008 (risk score uses `risk_contribution_for_status`).
- **Cross-references**: [[SECOPS-007]] — deterministic scoring replaces a real financial verification API; `S.kyc_proof_of_funds_real_analysis_enabled` (default `false`) gates a production provider. [[KYC-023]] — declared amounts and source categories are PII-sensitive; field-level encryption is a KYC-023 follow-up.

## 2. Current-State Investigation

### 2.1 Backend Service: `app/services/kyc_proof_of_funds.py`

**Source categories** (line 29–38): `bank_statement`, `pay_stub`, `sale_of_asset`, `investment`, `business_income`, `inheritance`, `gift`, `savings`. These are category labels for the source of funds, not the document types used in the original ticket design. The simplification is intentional — a single `source_category` field replaces the multi-step questionnaire approach.

**Scoring algorithm** (`_deterministic_score`, lines 53–82):
```
score = 50 (base)
  + 20 if document_s3_key present (document uploaded)
  + 15 if declared_amount_cents present AND > 0
  + 10 if source_category in KNOWN_SOURCE_CATEGORIES
  - 30 if declared_amount_cents > $10,000,000 (suspicious)
  + 5  if note present and non-empty
clamp 0..100
```

**Auto-decision** (`_decision_for_score`, lines 85–90):
- score ≥ 75 → `verified`
- score ≥ 55 → `needs_more_info`
- score < 55 → `rejected`

**Risk contribution** (`_risk_contribution_for_status`, lines 93–100): `verified` = −10 (risk reduction), `needs_more_info` = 0, `rejected` = +15, `expired` = +5. This feeds directly into KYC-008.

**Suspicious amount threshold**: `_SUSPICIOUS_AMOUNT_CENTS = 10_000_000_00` (100 million dollars in cents). Any submission declaring over $10M triggers a −30 score penalty. This is a blunt heuristic; in production, a real AML analysis would be triggered.

**Real analysis gate** (`_real_analysis_enabled`, line 113): checks `S.kyc_proof_of_funds_real_analysis_enabled` (default `False`). The `_real_analysis_score` function (line 119) unconditionally raises `NotImplementedError` — if the flag is ever set to `True` in dev without a real provider, the `create_submission` function falls back to the deterministic mock (lines 149–163). This satisfies SECOPS-007 graceful degradation.

**S3 document storage**: `create_submission` accepts `document_s3_key` (the key of an already-uploaded file). The S3 upload happens before calling this endpoint (via the file manager or a direct S3 pre-signed upload). The service only stores the key reference, not the bytes.

**Validity** (`_DEFAULT_VALIDITY_DAYS = 365`): Submissions expire after 365 days (from `created_at`). Configurable via `S.kyc_proof_of_funds_validity_days`.

### 2.3 DynamoDB Table: `kyc_proof_of_funds`

Defined at `scripts/local-ddb-init.py:225–231`:
- PK: `submission_id` (String, format `pof_{24 hex chars of SHA-256}`)
- GSI `ByStatus`: PK=`status`, SK=`created_at` (N)
- `attr_types={"created_at": "N"}` — present.

Key fields: `submission_id`, `user_sub`, `status`, `source_category`, `declared_amount_cents`, `currency`, `document_s3_key`, `note`, `score`, `risk_contribution`, `reviewer_note`, `created_at`, `updated_at`, `expires_at`.

**Note on submission_id generation** (`create_submission`, line 145): `pof_` + SHA-256 of `{user_sub}:{ts}:{source_category}:{declared_amount_cents}`. This is deterministic — submitting the same payload at the same second produces the same ID. This is intentional for idempotency but means two submissions in the same second with identical parameters are conflated. In practice, `ts = now_ts()` (second-level precision), so rapid re-submissions within the same second are deduplicated.

### 2.4 Frontend Page: `KycProofOfFunds.tsx`

Exists at `frontend/src/pages/kyc/KycProofOfFunds.tsx`. API wrapper at `frontend/src/api/endpoints/kycProofOfFunds.ts`. Route in `App.tsx` — the component is available to users navigating to the KYC flow.

The ticket's original design called for a source-of-funds questionnaire (4 questions rendered inline). The actual implementation is simpler: a single form with `source_category` (dropdown), `declared_amount_cents` (number input), `currency` (text), `document_s3_key` (file path), and `note` (textarea). This is a pragmatic simplification that captures the essential AML signal without the complexity of a multi-step questionnaire.

**Missing frontend pieces**:
1. Admin reviewer queue (list all submissions by status, adjudicate).
2. `FinancialVerificationPanel` tab in `KycCaseDetailPage.tsx`.
3. Risk flags display is absent — the scoring is numeric, not flag-based as the original ticket proposed. The reviewer sees `score` and `risk_contribution` but no per-flag breakdown.

### 2.5 Dev/Prod Behavior

In dev, `_real_analysis_enabled()` returns `False` → deterministic score. The mock score is a function of the submission content (document present, amount, category) — not filename-based as in KYC-002/004. This means E2E tests must submit known payloads to produce known scores. For example, submitting with `source_category="bank_statement"`, `declared_amount_cents=50000`, `document_s3_key="s3/kyc/doc.pdf"`, `note="salary"` yields: `50+20+15+10+5=100` → `verified`.

## 3. Gap / Threat Analysis

### 3.1 Admin Review Gap

There is no admin reviewer queue page for proof-of-funds submissions. Reviewers cannot:
- List pending or `needs_more_info` submissions.
- Adjudicate (override the auto-decision) via the UI.
- See the `risk_contribution` value per submission.

The `GET /admin/submissions` and `POST /admin/submissions/{id}/adjudicate` endpoints exist — they only need a frontend.

### 3.2 Risk Flag Abstraction

The original ticket specified explicit named risk flags (`high_risk_income_source`, `volume_income_mismatch`, etc.) derived from a 4-question questionnaire. The implementation replaced this with a numeric score. The risk contribution field (`risk_contribution`) still feeds into KYC-008, but the granularity of per-flag information is lost. Reviewers see a score number, not actionable named flags. This is a design simplification trade-off — acceptable for an MVP but should be revisited when KYC-008 risk scoring is fully integrated.

### 3.3 Suspicious Amount Heuristic

The `$10M` threshold for the suspicious flag is arbitrary. For a platform handling typical consumer transactions, even $100,000 might warrant review. The threshold should be configurable via `S.kyc_proof_of_funds_suspicious_amount_cents` rather than hard-coded. Currently it is a module-level constant `_SUSPICIOUS_AMOUNT_CENTS` — changing it requires a code deploy.

### 3.4 Submission Expiry

`expires_at = created_at + _DEFAULT_VALIDITY_DAYS * 86400` is stored on the record. There is no background task to scan expired records and transition them to `expired` status (analogous to `expire_stale_calls` for liveness calls). Expired submissions remain in `verified` status indefinitely. This means a verified submission from 2 years ago continues to satisfy any readiness gate check.

**Fix required**: A background expiry task analogous to the liveness call expiry, using `ByStatus` GSI scan for `status=verified` with `FilterExpression: expires_at < now_ts()`.

### 3.5 Case Linkage

Like KYC-002 and KYC-004, submissions have a `user_sub` but not necessarily a `case_id`. The design implies one submission per KYC case, but the table allows multiple submissions per user. When checking proof-of-funds as part of a readiness gate:
- Which submission counts? The most recent `verified` one? Any `verified` one?
- If a user has a verified submission from a previous KYC case cycle, should it satisfy the new case's requirement?

Current answer: the readiness gate is not yet extended for proof-of-funds. When it is added (similar to KYC-004's residency gate), the recommended approach is: any `verified` submission for the `user_sub` within `validity_days` satisfies the gate, regardless of `case_id`. Financial status is user-level, not case-level.

### 3.6 Compliance and Legal

- **AML filing thresholds**: In the US, cash transactions over $10,000 trigger Currency Transaction Reports (CTRs). Declared amounts at or near this threshold should generate additional review flags. The current heuristic only triggers at $10M — far above the regulatory threshold.
- **Structuring detection**: Multiple submissions slightly under the suspicious threshold (e.g., three $9.9M submissions) would not be caught by per-submission scoring. A cross-submission analysis would be needed for full AML compliance — out of scope for this ticket but documented as a known gap.
- **PII classification**: `declared_amount_cents` and `source_category` are sensitive financial information. `document_s3_key` points to a financial document (bank statement, tax return). These should be covered by the KYC-023 field-level encryption extension.
- **Right to erasure**: The GDPR erasure path must delete `kyc_proof_of_funds` records when a user requests data deletion. Currently the purge endpoint (`POST /admin/purge/run`) covers `kyc_cases` only — a companion purge for this table is needed.
- **Reviewer override auditability**: `POST /admin/submissions/{id}/adjudicate` overrides the auto-decision. The override must be written to the audit log with `reviewer_sub`, `original_decision`, `new_decision`, and `reviewer_note`. The current router calls `kyc_proof_of_funds.adjudicate_submission(...)` — verify this function writes an audit event.

## 4. Proposed Design / Fix

### 4.1 Configurable Suspicious Threshold

In `app/core/settings.py` (after line 1072):

```python
kyc_proof_of_funds_suspicious_amount_cents: int = int(
    os.environ.get("KYC_POF_SUSPICIOUS_AMOUNT_CENTS", str(10_000_000_00))
)
```

In `kyc_proof_of_funds.py`, replace `_SUSPICIOUS_AMOUNT_CENTS` constant with a function call:

```python
def _suspicious_amount_cents() -> int:
    from app.core.settings import S
    return getattr(S, "kyc_proof_of_funds_suspicious_amount_cents", 10_000_000_00)
```

This allows operators to tune the threshold without a code deploy.

### 4.2 Submission Expiry Task

Add `expire_stale_submissions()` to `kyc_proof_of_funds.py`:

```python
def expire_stale_submissions(*, now: int | None = None) -> int:
    """Transition verified/needs_more_info submissions past expires_at to expired."""
    ts = now if now is not None else _utcnow_ts()
    expired_count = 0
    for status in ("verified", "needs_more_info"):
        resp = T.kyc_proof_of_funds.query(
            IndexName=S.kyc_proof_of_funds_status_index_name,
            KeyConditionExpression=Key("status").eq(status),
            FilterExpression=Attr("expires_at").lt(ts),
        )
        for item in (resp.get("Items") or []):
            T.kyc_proof_of_funds.update_item(
                Key={"submission_id": item["submission_id"]},
                UpdateExpression="SET #s=:expired, updated_at=:ts",
                ExpressionAttributeNames={"#s": "status"},
                ExpressionAttributeValues={":expired": "expired", ":ts": ts, ":old": status},
                ConditionExpression="#s = :old",
            )
            expired_count += 1
    return expired_count
```

Wire as a periodic task in `app/main.py` (same pattern as liveness call expiry, every 6 hours).

### 4.3 Admin Case Detail Integration

Add "Financial Verification" tab to `KycCaseDetailPage.tsx`. Fetch submissions via `GET /ui/kyc/proof-of-funds/admin/submissions?user_sub={caseDetail.user_sub}`. Display the most recent submission:

- **Source Category** badge (e.g., "Bank Statement")
- **Declared Amount** — formatted as currency (e.g., "$50,000.00")
- **Verification Score** — numeric with color coding: green ≥ 75, yellow 55–74, red < 55
- **Auto-Decision** badge: green "Verified", yellow "Needs More Info", red "Rejected"
- **Risk Contribution** — integer with sign (e.g., "+15 risk" in red, "−10 risk" in green)
- **Supporting Document** — download link (via `/ui/files/download` or direct S3 presigned URL from `document_s3_key`)
- **Note** — free-text note from applicant
- **Adjudicate button** — opens dialog with decision override (Verified / Needs More Info / Rejected) and required reviewer note

React Query key: `["kyc", "pof", caseDetail.user_sub]` with `staleTime: 30_000`.

### 4.4 Admin Reviewer Queue (`KycProofOfFundsReviewQueue.tsx`)

New page at `frontend/src/pages/kyc/KycProofOfFundsReviewQueue.tsx`:
- Filter by `status` (pending/needs_more_info/rejected/verified).
- DataTable: `submission_id`, `user_sub`, `source_category`, `declared_amount_cents` (formatted), `score`, `auto_decision`, `created_at`.
- Click row → adjudicate dialog.

Route: `admin/kyc/proof-of-funds` (add to `App.tsx`).

### 4.5 Readiness Gate Extension

Once proof-of-funds is mature (verified submissions flowing), extend `_readiness_for_case` analogously to KYC-004's residency check:

```python
if intake_profile in ("enhanced", "high_risk"):
    from app.services.kyc_proof_of_funds import get_verified_for_user
    verified_pof = get_verified_for_user(user_sub=case["user_sub"])
    checks["proof_of_funds"] = len(verified_pof) > 0
    hint_map["proof_of_funds"] = "Submit proof of funds documentation to continue."
```

This gate should be behind a separate flag (`KYC_POF_READINESS_GATE_ENABLED`) to allow data collection before making it a hard requirement.

### 4.6 Dev/Prod Parity (SECOPS-007)

The existing implementation satisfies SECOPS-007:
- **Deterministic mock**: Score is purely computational — no external calls.
- **Real provider gate**: `_real_analysis_enabled()` + `_real_analysis_score()` with `NotImplementedError` fallback.
- **S3 document key**: Referenced but not fetched during scoring — only stored as a reference. S3 access for download uses the standard `s3_client()` factory.
- **Injectable `now`**: `create_submission` accepts `now: int | None` for deterministic tests (line 143).

New changes (expiry task, configurable threshold) maintain this parity — no new external dependencies.

### 4.7 Alternatives Considered

- **4-question questionnaire approach** (as originally designed): Rejected in implementation. The questionnaire infrastructure adds complexity without substantially improving the risk signal over a simple category + amount + document combination. If detailed income source categorization is required for AML reporting, the questionnaire approach can be reintroduced as a separate data collection step distinct from the scoring.
- **Real-time AML screening API** (e.g., Refinitiv, LexisNexis): Not in scope for this ticket. Would require a provider abstraction similar to KYC-006 sanctions screening. Planned as a KYC-008 risk engine enhancement.
- **Per-case (not per-user) submissions**: Considered but rejected — financial status is user-level and should carry across KYC case refreshes.

### 5.5 Rollout

Three flags for staged enablement:

1. `KYC_PROOF_OF_FUNDS_ENABLED=true` — enables endpoints (default `true` in dev).
2. `KYC_POF_REAL_ANALYSIS_ENABLED=false` — keeps deterministic mock (never true in dev).
3. `KYC_POF_READINESS_GATE_ENABLED=false` — readiness gate check (enable last, after data collection proves system works).

Deployment sequence:
1. Backend + user page already deployed.
2. Wire expiry task (non-breaking).
3. Deploy admin reviewer queue page + case detail tab.
4. Enable in staging, run E2E suite.
5. Enable `KYC_PROOF_OF_FUNDS_ENABLED=true` in production — users can submit.
6. Monitor submission patterns for 1 week (check suspicious amount rate, rejection rate).
7. Enable `KYC_POF_READINESS_GATE_ENABLED=true` after compliance review of initial submissions.
8. Notify compliance team before gate enables — existing users without a verified POF who have `enhanced` profile will be blocked on their next re-verification cycle.

**Rollback**: Set `KYC_PROOF_OF_FUNDS_ENABLED=false` — endpoints return 404. Existing submissions preserved in DDB.

**Effort**: M (6–8 days) — backend extensions (2 days), admin queue page (2 days), case detail tab (2 days), E2E (1.5 days), readiness gate (0.5 days).
