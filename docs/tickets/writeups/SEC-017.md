# SEC-017: WebAuthn Passkey Register/Remove Requires Step-Up MFA — Investigation & Implementation Write-up

> ~5 pages. Real code read, citations at `file:line`.

## 1. Summary & Classification

The WebAuthn passkey registration endpoints (`POST /ui/webauthn/register/begin` and `/register/finish`) only require a live `require_ui_session` check — any session token, regardless of age or how it was obtained, is sufficient. There is no step-up or "fresh MFA" gate equivalent to those already protecting TOTP device enrollment, SMS device enrollment, API key creation, and device-trust operations. An attacker who steals a session cookie (via XSS, physical access, network interception, or a session-fixation bug) can silently register their own passkey on the victim's account. Once registered, the adversary's passkey survives a password reset (passkeys are independent of passwords), and unless the victim explicitly reviews their registered credentials they will never know a second authenticator exists. The same session-hijack window also lacks a guard on passkey removal — there are no removal endpoints in the router today, but the service layer (`app/services/webauthn.py`) will need them, and they must be step-up gated from day one.

- **Type**: security-fix (critical authentication gap)
- **Priority**: Critical
- **Status**: Open
- **Area**: `app/routers/webauthn.py`, `app/services/webauthn.py`, `app/services/sessions.py`
- **Affected users**: any account that has (or could be convinced to set up) WebAuthn passkeys
- **Attacker class**: 🌐 any-user with a stolen or lingering session token
- **Cross-references**: SEC-009 (MFA device management step-up policy), SECOPS-007 (dev/prod parity)

## 2. Current-State Investigation (What Exists Today)

### 2.1 The registration endpoints

`app/routers/webauthn.py:28–46` (the entire relevant router file):

```python
@router.post("/register/begin", response_model=WebAuthnRegisterBeginResp)
async def webauthn_register_begin(
    req: Request,
    body: WebAuthnRegisterBeginReq,
    ctx=Depends(require_ui_session),           # ← only check
):
    options = registration_options(ctx["user_sub"], ctx["user_sub"])
    audit_event("webauthn_register_begin", ctx["user_sub"], req, outcome="info")
    return {"options": options}

@router.post("/register/finish", response_model=WebAuthnRegisterFinishResp)
async def webauthn_register_finish(
    req: Request,
    body: WebAuthnRegisterFinishReq,
    ctx=Depends(require_ui_session),           # ← only check
):
    out = register_credential(ctx["user_sub"], ctx["user_sub"], body.credential, body.label)
    audit_event("webauthn_register_finish", ctx["user_sub"], req, outcome="success",
                credential_id=out["credential_id"])
    return out
```

Neither endpoint calls `require_fresh_mfa(ctx)`. The `require_ui_session` dependency at `app/services/sessions.py:284` only verifies that a valid, non-revoked session exists and the user is not banned — it says nothing about how recently the session authenticated with MFA.

### 2.2 How `require_fresh_mfa` works

`app/services/sessions.py:629–637`:

```python
def require_fresh_mfa(ctx: Dict[str, str], *, max_age_seconds: Optional[int] = None) -> None:
    required = compute_required_factors(ctx["user_sub"])
    if not required:
        return
    max_age = max_age_seconds or S.ui_stepup_max_age_seconds
    it = T.sessions.get_item(
        Key={"user_sub": ctx["user_sub"], "session_id": ctx["session_id"]}
    ).get("Item") or {}
    verified_at = int(it.get("mfa_verified_at", 0) or 0)
    if not verified_at or (now_ts() - verified_at) > max_age:
        raise HTTPException(401, "Fresh MFA required")
```

If the user has no MFA factors enrolled yet (`compute_required_factors` returns empty), the function returns immediately — this is correct, because you can't require step-up for a user who has no second factor. But once any factor is enrolled, subsequent security-critical operations must pass this check.

### 2.3 How every other security-critical MFA operation is gated

`app/routers/mfa_devices.py` calls `require_fresh_mfa(ctx)` on all write operations:
- Line 60: TOTP enroll begin
- Line 68: TOTP enroll confirm
- Line 82: TOTP device remove
- Line 111: SMS enroll begin
- Line 147: SMS enroll confirm
- Line 174: SMS device remove
- Lines 201, 233, 272, 299, 328: hardware key add/remove/update

`app/routers/api_keys.py:19,26,33,41` gates all API key operations.  
`app/routers/device_trust.py:21,30` gates device trust add/remove.

WebAuthn passkey registration is the single MFA-adjacent operation that skips this check.

### 2.4 Credential storage

`app/services/webauthn.py` stores credentials in DynamoDB keyed by `user_sub`. The `list_credentials` function at line 56 returns all credentials for a user. There is currently no endpoint to remove a credential (no DELETE route in the router); however when removal is implemented it must carry the same step-up requirement.

### 2.5 Audit trail

`webauthn_register_finish` emits an `audit_event` with `outcome="success"` but there is no out-of-band notification (email, push) to the account holder. The audit log exists, but a victim cannot act on what they don't see.

### 2.6 Challenge binding

The registration challenge is stored in the `T.sessions` table under a synthetic session ID `"webauthn_chal_register"` keyed to the requesting `user_sub` (`app/services/webauthn.py:76`). It is deleted on use (`app/services/webauthn.py:142`). This means the challenge is single-use and bound to the correct user — that part is correct. The problem is solely the missing MFA recency check before the challenge is issued.

### 2.7 Dev vs prod behavior

In dev mode, Cognito is disabled (`_cognito_available()` returns `False` when `S.dev_mode=True`). Sessions are created via `create_real_session`. The `require_fresh_mfa` function reads `mfa_verified_at` from DDB — this field is only written by `stamp_mfa_verified` after a successful TOTP/SMS/hardware-key challenge. In dev mode the E2E session setup scripts (`e2e_admin_session_setup.py`, `e2e_session_setup.py`) write sessions directly to DDB; they can optionally set `mfa_verified_at` to satisfy the step-up check in tests.

## 3. Gap / Threat Analysis

### 3.1 Primary attack: hijacked session → persistent account takeover

**Preconditions**: attacker has a valid `ui_session` cookie for the victim (obtained via XSS, physical access, leaked token, or session-fixation).

**Steps**:
1. Attacker calls `POST /ui/webauthn/register/begin` with victim's session cookie → receives a challenge.
2. Attacker calls `POST /ui/webauthn/register/finish` with a credential generated from their own authenticator device → credential stored under victim's `user_sub`.
3. Victim changes password (triggered by noticing suspicious activity) → passkeys are not affected.
4. Victim logs out → attacker's passkey still registered.
5. On next login page, attacker uses `POST /ui/webauthn/authenticate/finish` with their hardware key → creates a fresh session under victim's account.
6. **Outcome**: permanent re-entry capability on a password-changed, logged-out account.

**Impact**: full account takeover persisting through password changes; also enables adding admin MFA factors if the victim is an admin.

### 3.2 Victim lockout

If the attacker additionally removes the victim's existing passkeys (once a removal endpoint exists), the victim cannot use passkey login at all, forcing them onto password/SMS login which the attacker may also control.

### 3.3 Why the current ban check doesn't help

`require_ui_session` at `app/services/sessions.py:309` checks `is_user_currently_banned`. A user who has not been banned presents a valid session, bypasses nothing, and reaches the WebAuthn endpoints.

### 3.4 Why session expiry doesn't help

`mint_access_token` at `app/services/sessions.py:168` issues tokens with TTL `S.ui_access_token_ttl_seconds` (default ~15 min). However, the refresh-token path (`rotate_refresh_token`) can silently re-issue access tokens without MFA re-verification. An attacker with a long-lived refresh token could maintain access indefinitely.

### 3.5 Code sites that must change

| File | Line(s) | Change |
|------|---------|--------|
| `app/routers/webauthn.py` | 32 (register_begin) | Add `require_fresh_mfa(ctx)` call |
| `app/routers/webauthn.py` | 43 (register_finish) | Add `require_fresh_mfa(ctx)` call |

| `app/services/alerts.py` | alert catalogue | Add `webauthn_credential_added` notification event |

## 4. Proposed Design / Fix

### 4.1 Add step-up to existing endpoints

`app/routers/webauthn.py` — import the function (it is already imported in `mfa_devices.py` from the same package):

```python
from app.services.sessions import require_ui_session, require_fresh_mfa
```

Then add the call immediately after session resolution in both handlers:

```python
@router.post("/register/begin", response_model=WebAuthnRegisterBeginResp)
async def webauthn_register_begin(
    req: Request,
    body: WebAuthnRegisterBeginReq,
    ctx=Depends(require_ui_session),
):
    require_fresh_mfa(ctx)                      # ← ADD
    options = registration_options(ctx["user_sub"], ctx["user_sub"])
    audit_event("webauthn_register_begin", ctx["user_sub"], req, outcome="info")
    return {"options": options}

@router.post("/register/finish", response_model=WebAuthnRegisterFinishResp)
async def webauthn_register_finish(
    req: Request,
    body: WebAuthnRegisterFinishReq,
    ctx=Depends(require_ui_session),
):
    require_fresh_mfa(ctx)                      # ← ADD
    out = register_credential(ctx["user_sub"], ctx["user_sub"], body.credential, body.label)
    audit_event("webauthn_register_finish", ctx["user_sub"], req, outcome="success",
                credential_id=out["credential_id"])
    return out
```

### 4.2 Add credential removal endpoint (new)

Add to `app/services/webauthn.py`:

```python
def remove_credential(user_sub: str, credential_id_b64: str) -> None:
    """Remove a passkey credential by its base64url credential_id."""
    _require_webauthn()
    cred_id_bytes = base64.urlsafe_b64decode(credential_id_b64 + "==")
    pk = _credential_pk(cred_id_bytes)
    item = T.webauthn_credentials.get_item(
        Key={"pk": pk, "user_sub": user_sub}
    ).get("Item")
    if not item:
        raise HTTPException(404, "Credential not found")
    T.webauthn_credentials.delete_item(Key={"pk": pk, "user_sub": user_sub})
```

Add to `app/routers/webauthn.py`:

```python
@router.delete("/credentials/{credential_id}")
async def webauthn_credential_remove(
    req: Request,
    credential_id: str,
    ctx=Depends(require_ui_session),
):
    require_fresh_mfa(ctx)
    remove_credential(ctx["user_sub"], credential_id)
    audit_event("webauthn_credential_removed", ctx["user_sub"], req,
                outcome="success", credential_id=credential_id)
    return {"ok": True}
```

### 4.3 Notification on new passkey registration

Add to `app/services/alerts.py` alert catalogue (alongside existing `"mfa_device_added"` etc.):

```python
"webauthn_credential_added": "/security/mfa",
```

In `webauthn_register_finish`, after `audit_event`, emit:
```python
from app.services.alerts import send_user_alert
send_user_alert(ctx["user_sub"], "webauthn_credential_added", {
    "credential_id": out["credential_id"],
    "label": out.get("label", ""),
})
```

### 4.4 Frontend: show step-up prompt on 401 from WebAuthn endpoints

The frontend `api/client.ts` global 401 handler currently triggers full logout. For step-up flows, the pattern used by MFA device management should be reused: the UI catches `401` with body `"Fresh MFA required"` and displays a re-authentication modal rather than logging out. The Security page (`frontend/src/pages/security/`) passkey management section should be updated to use this pattern.

### 4.5 Dev/Prod parity (SECOPS-007)

`require_fresh_mfa` reads `mfa_verified_at` from DDB Local in dev mode — the check is purely DDB-based and not gated on `S.dev_mode`. E2E tests that need to exercise passkey registration must call `stamp_mfa_verified` before the registration flow. A helper function in the test setup can write `mfa_verified_at = now_ts()` directly to the DDB sessions table, which is already done for TOTP tests.

### 4.6 Grace period configuration

`S.ui_stepup_max_age_seconds` controls the window during which a fresh MFA is considered valid (default likely 5–15 minutes). Passkey registration could use a shorter window (e.g., 300 seconds) by passing `max_age_seconds=300` to `require_fresh_mfa`. This is a configuration decision; start with the platform default.

## 5. Testing, Verification & Rollout

### pytest unit tests (`tests/test_webauthn_stepup.py`)

- `test_register_begin_no_mfa_enrolled`: user with no MFA enrolled → `require_fresh_mfa` returns immediately (no factors required) → register/begin succeeds without step-up.
- `test_register_begin_requires_stepup_when_totp_enrolled`: user has a TOTP device; session has no `mfa_verified_at`; `POST /ui/webauthn/register/begin` → `401 Fresh MFA required`.
- `test_register_begin_succeeds_after_stepup`: same user; session has `mfa_verified_at = now_ts()` → succeeds.
- `test_register_begin_stale_stepup`: `mfa_verified_at` is older than `ui_stepup_max_age_seconds` → `401`.
- `test_register_finish_requires_fresh_mfa`: same pattern for `/register/finish`.
- `test_credential_remove_requires_fresh_mfa`: (after implementing removal endpoint) `DELETE /ui/webauthn/credentials/{id}` without step-up → `401`.
- `test_notification_emitted_on_registration`: mock `send_user_alert`; complete a registration; assert called with `"webauthn_credential_added"`.

### Playwright E2E (`frontend/e2e/webauthn-stepup.spec.ts`)

Since Playwright cannot drive a real WebAuthn authenticator in headless mode, these tests use the mocked/stub credential approach:

1. Seed Alice's session without `mfa_verified_at`; attempt `POST /ui/webauthn/register/begin` via `page.request.post`; assert 401.
2. Seed Alice's session with `mfa_verified_at = now_ts()`; assert 200 and `options` field in body.
3. Open the Security page; verify that the "Add Passkey" button triggers a step-up dialog when MFA is enrolled but not fresh.

### Risks & open questions

- Users with WebAuthn enabled but no other MFA factor have no way to satisfy `require_fresh_mfa` (the function returns immediately for no-factor users). This is correct behavior. If WebAuthn itself is the only factor, the user must complete it before registering a _second_ passkey — `webauthn_auth_finish` at line 57–73 could optionally call `stamp_mfa_verified` to satisfy the step-up window.
- Devices without authenticator hardware cannot complete passkey registration at all; the step-up requirement does not change this.

**Effort**: S (backend: ~4 lines added to existing endpoints + a new service function; notifications: ~10 lines; frontend: reuse existing step-up modal pattern).
