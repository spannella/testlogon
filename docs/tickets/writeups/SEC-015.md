# SEC-015: Org/Tenant Isolation & Membership Lifecycle — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

Three interconnected authorization gaps in the organization/tenant layer allow unauthorized actors to gain org membership, perform billing operations without the required role, and retain access to an organization after they have been removed or the org has been archived:

1. **Missing membership check on `add_org_payment_method`** — `app/routers/orgs.py:219–232` does not call `assert_org_membership` before delegating to `_add`, unlike all sibling billing endpoints that do assert `min_role="owner"`. A member with any role (or even a non-member who guesses the `org_id`) can add a payment method to any org.
2. **Invite token not bound to recipient email** — `app/services/org_service.py:236–291` validates the invite token hash but never checks `invite["email"] == user_sub` (the accepting user). A leaked or forwarded invite link can be accepted by any authenticated user, granting them the invited org role without being the intended recipient.
3. **No session/access revocation on member removal or org archival** — `remove_member` at `org_service.py:323–339` and `archive_org` at `org_service.py:178–185` update DDB state but do not revoke the removed user's sessions or add archived-org guards to subsequent API requests. A removed member whose session cookie is still valid (up to `S.ui_session_ttl_seconds = 30 * 24 * 3600`) continues to access org resources.

- **Type**: security-fix (authorization bypass, access control lifecycle)
- **Severity**: High (payment method injection, unauthorized membership); Medium (post-removal/archival access)
- **Status**: Open
- **Area**: `app/routers/orgs.py`, `app/services/org_service.py`
- **Attacker class**: 🌐 any authenticated user (org billing endpoint); 🌐 invite token recipient (invite binding); 🌐 former member with active session (revocation gap)
- **Dependencies**: SEC-008 (trusted IP / session validation infrastructure); SECOPS-007 (dev/prod parity)

## 2. Current-State Investigation (what exists today)

### 2.1 Missing `assert_org_membership` on `add_org_payment_method`

`app/routers/orgs.py:211–232`:

```python
@router.get("/ui/orgs/{org_id}/billing/payment-methods")
def list_org_payment_methods(org_id: str, session=Depends(require_ui_session)):
    from app.services.org_service import assert_org_membership
    from app.services.org_billing import list_org_payment_methods as _list
    assert_org_membership(org_id, session["user_sub"], min_role="owner")    # ✔ guarded
    return _list(org_id)


@router.post("/ui/orgs/{org_id}/billing/payment-methods", status_code=201)
def add_org_payment_method(org_id: str, body: dict, session=Depends(require_ui_session)):
    from app.services.org_billing import add_org_payment_method as _add
    return _add(                                                           # ✘ NO guard
        org_id=org_id,
        user_sub=session["user_sub"],
        ...
    )
```

The GET at line 212 calls `assert_org_membership(..., min_role="owner")` explicitly. The POST at line 219 does not. The service function `add_org_payment_method` in `app/services/org_billing.py` does not contain an independent membership check either (verified by the calling pattern). The sibling DELETE at line 235 also calls `_remove(org_id, session["user_sub"], pm_id)` without a visible assert — worth sweeping the entire billing sub-router.

`assert_org_membership` at `org_service.py:134–140` raises `HTTPException(403)` if the user is not an active member with the required role. Without this call on the POST, any authenticated user who can discover or enumerate an `org_id` (UUIDs are guessable if the table scan is accessible or through other info leaks) can add a payment method to that org.

### 2.2 Invite acceptance not bound to invited email

`app/services/org_service.py:236–291`:

```python
def accept_invite(invite_id: str, user_sub: str, token: str) -> Dict[str, Any]:
    invite = _find_invite(invite_id)
    if not invite:
        raise HTTPException(404, "Invitation not found")
    if invite["status"] != "pending":
        raise HTTPException(409, ...)

    expected_hash = invite.get("token_hash", "")
    actual_hash = f"sha256:{hashlib.sha256(token.encode()).hexdigest()}"
    if expected_hash != actual_hash:
        raise HTTPException(403, "Invalid invitation token")

    if invite.get("expires_at", 0) < now_ts():
        ...
        raise HTTPException(410, "Invitation has expired")

    # NO check: invite["email"] == user_sub
    T.organizations.put_item(Item={
        "org_id": org_id, "sk": f"MEMBER#{user_sub}", ...
    })
```

The invite item contains `invite["email"]` (set at `invite_member:220–231`), but `accept_invite` never compares it to `user_sub`. The `token_hash` check prevents forgery of the token itself, but if:
- The invite email was forwarded to a third party, or
- The invite URL was included in a support ticket, screenshot, or Slack message visible to others,

any authenticated user who obtains the invite URL (`/ui/orgs/{org_id}/invites/{invite_id}/accept?token=...`) can accept it and join the org under their own `user_sub`.

The `list_pending_invites` function (`org_service.py:308–320`) queries by `email` GSI, so existing invite discovery is correctly scoped — but acceptance is not.

### 2.3 No session revocation on membership change or org archival

`app/services/org_service.py:323–339` (`remove_member`):
```python
def remove_member(org_id: str, remover_sub: str, target_sub: str) -> None:
    remover = assert_org_membership(org_id, remover_sub, min_role="admin")
    target = get_org_membership(org_id, target_sub)
    ...
    T.organizations.delete_item(Key={"org_id": org_id, "sk": f"MEMBER#{target_sub}"})
    T.organizations.update_item(Key={"org_id": org_id, "sk": "#META"}, ...)
    # No session invalidation for target_sub
```

`app/services/org_service.py:178–185` (`archive_org`):
```python
def archive_org(org_id: str, user_sub: str) -> None:
    assert_org_membership(org_id, user_sub, min_role="owner")
    T.organizations.update_item(
        Key={"org_id": org_id, "sk": "#META"},
        UpdateExpression="SET #s = :s, updated_at = :now",
        ExpressionAttributeValues={":s": "archived", ...},
    )
    # No session invalidation for all members; no archived-org guard on read endpoints
```

The `assert_org_membership` function at `org_service.py:134–140` checks `membership["status"] == "active"` — so if the MEMBER row is deleted (remove_member) the check will 403 on the next request. However, any cached org response or any endpoint that accesses an org resource without first calling `assert_org_membership` will succeed until the session expires.

For archived orgs: after `archive_org` sets `status="archived"` on the `#META` row, `assert_org_membership` still succeeds because it reads `MEMBER#{user_sub}` (which still exists for all members) and does not check the org's own status. All member-accessible org endpoints — file listing, billing history, member listing — remain accessible to all existing members.

### 2.4 `remove_org_payment_method` and `set_org_default_pm`

Lines 235–246 in `orgs.py` show two more billing endpoints that call `_remove(org_id, session["user_sub"], pm_id)` and `_set(org_id, session["user_sub"], ...)` respectively without visible `assert_org_membership` guards at the router layer. The service-layer implementations in `org_billing.py` should be audited for self-contained guards.

### 2.5 Dev vs prod behavior

All issues exist in both dev and prod. DDB Local and real DynamoDB behave identically for `get_item` / `put_item` / `delete_item` operations. The `require_ui_session` dependency works the same way in both environments (cookie auth). No AWS-specific behavior is relevant here.

## 3. Gap / Threat Analysis

### 3.1 Payment method injection — full attack scenario

**Preconditions**: Attacker is an authenticated user who can enumerate org IDs (e.g. from a previous membership, a public org directory endpoint, or by guessing sequential IDs). Target org has no payment method set.

**Attack**:
1. Attacker calls `POST /ui/orgs/{org_id}/billing/payment-methods` with a Stripe card token referencing a payment method that they control (a prepaid card, or a card number from a test environment).
2. Backend calls `_add(org_id=..., user_sub=attacker_sub, ...)` — which writes the payment method to DDB and potentially sets it as the default.
3. Any subsequent org billing charge (e.g. a subscription renewal, a file-storage charge) may be directed to the attacker-injected payment method, disrupting the org's billing or redirecting charges.

**Why current controls fail**: The `add_org_payment_method` route at line 219 is a POST (non-idempotent, state-changing) with no membership check. The only guard is `require_ui_session`, which confirms the user is logged in but says nothing about their relationship to the org.

### 3.2 Invite token forwarding — full attack scenario

**Attack**:
1. Alice is invited to org `ACME` at role `admin`. The invite URL is sent to `alice@example.com`.
2. Alice forwards the email or screenshot to Bob (a competitor or malicious actor).
3. Bob, who has an account on the platform, navigates to the invite URL and calls `POST /ui/orgs/{org_id}/invites/{invite_id}/accept?token=T`.
4. Backend confirms the token hash but does not check `invite["email"] == "bob@example.com"`. Bob is added as an `admin` member of `ACME`.

**Impact**: Unauthorized org membership with org-owner-granted role. Attacker gains access to org files, billing, messaging, and all org-scoped resources.

### 3.3 Post-removal access

**Scenario**: Alice is removed from org `ACME`. Her `MEMBER#alice` row is deleted. However:
- `assert_org_membership` (called on most endpoints) will now correctly 403 Alice. ✔
- Any endpoint that does **not** call `assert_org_membership` — e.g. direct access to an org file download by S3 key, or a cached React Query response — will succeed until her session expires (up to 30 days).
- After `archive_org`, **all members** retain access because `assert_org_membership` does not check the org's `status` field.

### 3.4 Code sites that must change

| File | Line | Change |
|------|------|--------|
| `app/routers/orgs.py` | 219 | Add `assert_org_membership(..., min_role="owner")` before `_add` |

| `app/services/org_service.py` | 247 | Add `if invite["email"] != user_sub:` check in `accept_invite` |

| `app/services/org_service.py` | 333, 184 | Add session revocation call after membership deletion / org archival |

## 4. Proposed Design / Fix

### 4.1 Add missing `assert_org_membership` guards

In `orgs.py:219`, add before the delegate call:
```python
@router.post("/ui/orgs/{org_id}/billing/payment-methods", status_code=201)
def add_org_payment_method(org_id: str, body: dict, session=Depends(require_ui_session)):
    from app.services.org_service import assert_org_membership
    from app.services.org_billing import add_org_payment_method as _add
    assert_org_membership(org_id, session["user_sub"], min_role="owner")   # ← add this
    return _add(...)
```

Apply the same pattern to `remove_org_payment_method` (line 235) and `set_org_default_pm` (line 243).

**Sweep procedure**: grep `app/routers/orgs.py` for all `@router.{post,patch,delete,put}` endpoints that access an org resource; confirm each either calls `assert_org_membership` at the router layer or in the service function with the appropriate `min_role`.

### 4.2 Bind invite to recipient email

In `org_service.py:247` (after the token hash check and expiry check, before writing the MEMBER row):
```python
# Verify that the accepting user is the intended recipient
invited_email = invite.get("email", "").lower().strip()
accepting_email = user_sub.lower().strip()   # user_sub == email in this system
if invited_email and invited_email != accepting_email:
    raise HTTPException(403, "This invitation was issued to a different email address")
```

Note: `user_sub` is the authenticated user's email address in this platform (see `sso_saml.py:173`: `user_sub = email`). The comparison is therefore between the invite's stored email and the authenticated user's email. Normalize both to lowercase before comparing.

If the platform supports `user_sub` values that are not email addresses (e.g. after full Cognito integration), store the canonical identifier at invite creation time and compare it. The invite item already stores `email` at `invite_item["email"]` (line 221).

**Token expiry**: Invite tokens are already short-lived via `S.org_invite_ttl_seconds`. Consider reducing the default (currently unspecified — set to 7 days or less) to limit the window for token leakage.

**Single-use enforcement**: `accept_invite` already updates `status="accepted"` on success (line 272–277). The `invite["status"] != "pending"` check at line 240 prevents re-use. ✔

### 4.3 Archived-org guard in `assert_org_membership`

In `org_service.py:134–140`:
```python
def assert_org_membership(org_id: str, user_sub: str, min_role: str = "viewer") -> Dict[str, Any]:
    # Check org exists and is not archived
    org = get_org(org_id)
    if not org:
        raise HTTPException(404, "Organization not found")
    if org.get("status") == "archived":
        raise HTTPException(403, "Organization is archived")

    membership = get_org_membership(org_id, user_sub)
    if not membership or membership.get("status") != "active":
        raise HTTPException(403, "Not a member of this organization")
    if ROLE_ORDER.get(membership["org_role"], 0) < ROLE_ORDER.get(min_role, 0):
        raise HTTPException(403, f"Requires {min_role} role or higher")
    return membership
```

This adds one extra DDB `get_item` (the org `#META` read) on every membership assertion. Since `assert_org_membership` is called on every org-scoped request anyway and DDB Local/real DDB `get_item` is fast (~1ms), this is acceptable. If performance is a concern, the org status can be cached in the session's `admin_profile` or a short-lived in-process LRU cache.

### 4.4 Session revocation on removal and archival

After `T.organizations.delete_item(Key={"org_id": org_id, "sk": f"MEMBER#{target_sub}"})` in `remove_member` (line 333):
```python
# Revoke all sessions for the removed user that have org context
from app.services.sessions import revoke_all_sessions_for_user
revoke_all_sessions_for_user(target_sub, reason="org_member_removed", scope={"org_id": org_id})
```

For `archive_org` (line 184), after updating org status:
```python
# Revoke all active sessions for all org members
members_resp = T.organizations.query(
    KeyConditionExpression=Key("org_id").eq(org_id) & Key("sk").begins_with("MEMBER#"),
)
for member in members_resp.get("Items", []):
    revoke_all_sessions_for_user(member["user_sub"], reason="org_archived", scope={"org_id": org_id})
```

**`revoke_all_sessions_for_user` implementation** (to be added to `app/services/sessions.py` if not already present): queries `T.sessions` by `user_sub` GSI and marks all active session items with `revoked_at = now_ts()`. The `require_ui_session` dependency already checks for revocation in the session load path.

**Scope parameter**: The `scope` dict is for audit logging only (it is not used to revoke only org-specific sessions — all sessions for that user are revoked, since session cookies are platform-wide, not org-scoped).

**Performance note**: For large orgs, the archival revocation may involve many DDB writes. Use a DynamoDB batch write (25 items per batch) and log a warning if more than 100 sessions are revoked in one call.

### 4.5 Dev/prod parity (SECOPS-007)

- All fixes are pure DDB read/write operations.
- In dev: DDB Local, `require_ui_session` cookie auth, `assert_org_membership` all behave identically.
- No AWS services or feature flags are introduced.
- The `revoke_all_sessions_for_user` function must work in dev (DDB Local) and prod (DynamoDB) without modification.

### 4.6 Alternatives considered

- **Org-scoped session tokens** (JWT claim includes `org_id` membership): would solve the post-removal access problem at the session layer without a DDB revocation scan. More architecturally significant change; not suitable as a near-term fix.
- **Check archived status only on write endpoints**: weaker than checking on all endpoints; read endpoints can expose sensitive data (billing history, member list) to archived-org members.

### Rollout & rollback

- **No DDB schema changes** for the guard additions and invite email check.
- **No new tables** — session revocation uses the existing `T.sessions` table.
- Rollout: deploy as a single PR; changes are additive (new checks only).
- Risk: The archived-org guard adds one `get_org` DDB read per `assert_org_membership` call. Measure p99 latency of org endpoints before and after; if latency is unacceptable, add an in-process 60-second LRU cache keyed on `org_id → status`.
- Rollback: revert the PR. Risk: re-exposes the three vulnerabilities. No data migration is needed for rollback.

### Effort estimate

**S** — four targeted code changes (add guard, add email check, add archived check, add revocation calls) plus ~8 unit tests and Playwright coverage. The largest risk is the revocation-on-archival bulk-write loop for large orgs; cap at 200 sessions and log a warning to defer the rest. Estimated 1 day including tests.
