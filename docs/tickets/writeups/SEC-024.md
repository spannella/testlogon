# SEC-024: E-commerce Price/Quantity Tampering + Entitlement-After-Refund — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

Two critical weaknesses exist in the e-commerce checkout flow. First, `POST /ui/shoppingcart/carts/{id}/items` accepts a client-supplied `unit_price_cents` field and stores it verbatim; the backend service at `app/services/shoppingcart.py:346` uses the client price without looking up the catalog price, allowing a buyer to purchase any item for any price including zero. Second, when a completed transaction is reverted or a cancellation is approved (`mark_reverted` at `purchase_history.py:469`; `respond_cancel` at `purchase_history.py:537`), the transaction status is flipped to `REVERTED`/`CANCELLED` but entitlements granted by the order — file-bundle access, API credits, digital goods — are never revoked. A buyer can thus purchase a digital item, receive access, request a refund, and retain access permanently.

A confirmed-safe note: IDOR attacks on cart and transaction reads are mitigated by user-PK scoping, promo discounts are capped at item price, and stock decrements use DynamoDB `ConditionExpression` for atomicity. The two issues above are the confirmed exploitable gaps.

- **Type**: Security-fix
- **Priority/Severity**: Critical
- **Status**: Open
- **Owning area**: `app/services/shoppingcart.py`, `app/services/purchase_history.py`, `app/services/commerce_entitlement_orchestrator.py`, `app/routers/shoppingcart.py`, `app/models.py`
- **Who is affected**: 🌐 any authenticated user (buyer); sellers and platform revenue are directly harmed.
- **Cross-references**: SHOP-001 (catalog), SHOP-002 (promo codes), catalog-subscriptions feature. **SECOPS-007** dev/prod parity: DynamoDB Local in dev; same code path.

## 2. Current-State Investigation (what exists today)

### 2.1 Client-Controlled Price — `shoppingcart.py` + `models.py`

**`app/models.py:829-833`** — `ShoppingCartItemIn` accepts a required `unit_price_cents`:

```python
class ShoppingCartItemIn(BaseModel):
    sku: str = Field(min_length=1, max_length=128)
    name: str = Field(min_length=1, max_length=256)
    quantity: conint(ge=1, le=1000) = 1
    unit_price_cents: conint(ge=0, le=100000000)   # client supplies price; only bounded 0..1e8
    ...
```

The constraint `ge=0` explicitly allows a price of **zero**.

**`app/routers/shoppingcart.py:86-99`** — The router calls `add_item` with the entire body dict:

```python
@router.post("/carts/{cart_id}/items", response_model=ShoppingCartItemOut)
async def ui_add_item(cart_id: str, body: ShoppingCartItemIn, ...):
    item = add_item(ctx["user_sub"], cart_id, body.model_dump())   # price from body
```

**`app/services/shoppingcart.py:337-363`** — `add_item` stores the price from the payload without any catalog lookup:

```python
item = _validate_commercial_item_payload(
    {
        ...
        "unit_price_cents": int(payload.get("unit_price_cents", 0)),   # line 346
        ...
    }
)
T.shopping_cart.put_item(Item=item)
```

There is a safe path: `add_catalog_item` at `shoppingcart.py:366-392` reads price from the catalog table:

```python
payload = {
    "sku": f"catalog:{item_id}",
    "unit_price_cents": int(item.get("price_cents", 0)),   # line 390 — catalog price
}
return add_item(user_sub, cart_id, payload)
```

But `add_catalog_item` is called only when the client hits `POST /ui/shoppingcart/carts/{id}/items/catalog`. The non-catalog endpoint `POST /ui/shoppingcart/carts/{id}/items` is the vulnerable path and is exposed in the API without restriction.

**Exploit PoC — Zero-price purchase**:
```http
POST /ui/shoppingcart/carts/cart_abc123/items
Cookie: ui_session=...; ui_csrf=...
x-csrf-token: <csrf_token>
Content-Type: application/json

{
  "sku": "catalog:premium-plan-001",
  "name": "Premium Plan",
  "quantity": 1,
  "unit_price_cents": 0,
  "product_type": "api_package",
  "item_id": "premium-plan-001",
  "entitlement_template_metadata": { ... }
}
```

The cart item is created with price 0. `checkout_cart` at line 555+ sums `line_total_cents` from the stored items, computes `final_total = max(0, total_cents - discount_cents)` = 0, and creates an order for $0.00. `commerce_entitlement_orchestrator.process_order_entitlements` (line 640) is then called and grants the entitlement.

**Update path also vulnerable**: `set_item_quantity` at line 395 does not re-validate price. However, `PATCH /carts/{id}/items/{sku}` only accepts a `quantity` field (`ShoppingCartUpdateQtyIn`), so quantity-change does not re-expose price. The vuln is on the initial `add_item` call only.

**Existing update also vulnerable**: `add_item` at line 317-335 handles the case where the item already exists:
```python
"unit_price_cents": int(payload.get("unit_price_cents", existing.get("unit_price_cents", 0))),   # line 325
```
A subsequent `POST /carts/{id}/items` with the same SKU and `unit_price_cents=0` overwrites the stored price to 0.

**PoC — Buy and Keep**:
1. `POST /carts/{id}/items/catalog` with `item_id = "file-bundle-gold"` → checkout → `process_order_entitlements` grants file-bundle access, `txn_id = "TXN-001"`.
2. User accesses the file bundle — verifies access is active.
3. `POST /ui/purchase-history/{txn_id}/cancel` → `request_cancel` → status = `CANCEL_REQUESTED`.
4. Admin approves: `POST /admin/purchase-history/{txn_id}/cancel/respond` with `decision=APPROVE` → `respond_cancel` → status = `CANCELLED`. No entitlement revoked.
5. User continues to access the file bundle — access remains active.

**Affected entitlement types** based on `catalog_commercialization.py:10`:
- `"file_bundle"` — file share access
- `"api_package"` — API call credits / route allowlist
- `"internal_api_package"` — internal namespace access

## 3. Gap / Threat Analysis

### Threat 1: Price Manipulation — Free or Arbitrary-Price Purchase

**Attacker**: Any authenticated user. No admin or special role required.

**Blast radius**: Any item in the catalog, including high-value API packages, file bundles, and premium subscriptions, can be purchased for $0. Platform revenue goes to zero; digital goods are given away for free. On multi-seller platforms, the creator whose item was purchased at $0 also receives no revenue.

**Why current controls fail**: The `unit_price_cents` field is modeled as user input in `ShoppingCartItemIn`. It is treated as authoritative. There is no server-side lookup of catalog price before storage or checkout. The only protection is an upper bound of `100_000_000` cents ($1M) and a lower bound of `0` — the lower bound is the attack.

**Severity escalation**: The `entitlement_template_metadata` field (`models.py:841`) is also client-supplied. A sophisticated attacker could supply not just price=0 but also a manipulated entitlement scope (e.g., claiming a higher API credit allotment than the catalog item provides) — though this requires understanding the entitlement schema.

### Threat 2: Entitlement Persistence After Refund

**Attacker**: Any authenticated user who has completed a purchase.

**Blast radius**: Unlimited free access to any digital good after a single purchase. For API packages with credit-based billing, the attacker purchases $10 of credits, uses them, refunds, and the credits are restored (or access remains). For file bundles, permanent access with no charge.

**Why current controls fail**: The revocation path simply does not exist in the codebase. `mark_reverted` and `respond_cancel` change the transaction status in DynamoDB but make no call to the entitlement orchestrator.

**Interaction with re-purchase**: A reverted transaction that did not revoke the entitlement means re-purchasing the same item could grant a *second* entitlement grant on top of the existing one. Depending on entitlement additive logic, this could further amplify the exploit.

## 4. Proposed Design / Fix

### 4.1 Derive Price Server-Side for Catalog Items

The fix is at two levels: model and service.

**Model level (`app/models.py`)**: Remove `unit_price_cents` from `ShoppingCartItemIn` (or make it `Optional` and explicitly ignored for catalog items):

```python
class ShoppingCartItemIn(BaseModel):
    sku: str = Field(min_length=1, max_length=128)
    name: str = Field(min_length=1, max_length=256)
    quantity: conint(ge=1, le=1000) = 1
    # unit_price_cents removed — price derived server-side from catalog
    item_id: Optional[str] = None          # if provided, price fetched from catalog
    category_id: Optional[str] = None
    ...
```

**Service level (`app/services/shoppingcart.py`)**: In `add_item`, if `item_id` and `category_id` are present, look up the catalog price:

```python
def add_item(user_sub: str, cart_id: str, payload: Dict[str, Any]) -> Dict[str, Any]:
    ...
    # If catalog item, always use server-side price
    item_id = payload.get("item_id")
    category_id = payload.get("category_id")
    if item_id and category_id:
        catalog_item = T.catalog.get_item(Key=_catalog_item_key(category_id, item_id)).get("Item")
        if not catalog_item or catalog_item.get("entity") != "item":
            raise HTTPException(status_code=404, detail="Catalog item not found")
        server_price = int(catalog_item.get("price_cents", 0))
    else:
        # Free-form item (seller-created, not from catalog): allow client price
        # but require a seller permission check in future
        server_price = int(payload.get("unit_price_cents", 0))

    item = _validate_commercial_item_payload({
        ...
        "unit_price_cents": server_price,   # never from client for catalog items
        ...
    })
    ...
```

This ensures `add_catalog_item` and the direct `add_item` path both use catalog pricing. The `add_catalog_item` convenience function (line 366) continues to work unchanged.

**Transition**: The model change (removing `unit_price_cents` from request body) is a breaking API change. A transitional approach is to accept the field but validate it against catalog price and reject if mismatched, returning HTTP 422 with `"price_mismatch: client supplied X, catalog requires Y"`. This gives clearer error messages than a silent override.

### 4.2 Revoke Entitlements on Cancel/Revert

Add a `revoke_entitlements_for_order` function to `commerce_entitlement_orchestrator.py`:

```python
def revoke_entitlements_for_order(self, order_id: str, *, reason: str) -> Dict[str, Any]:
    """Revoke all entitlements granted by order_id. Called on refund/cancel."""
    order = commerce_order_service.get_order(order_id)
    for line_item in order.get("line_items", []):
        product_type = line_item.get("product_type")
        if product_type == "file_bundle":
            self._revoke_file_bundle_access(line_item, reason=reason)
        elif product_type in ("api_package", "internal_api_package"):
            self._revoke_api_credits(line_item, reason=reason)
    return {"order_id": order_id, "revoked": True, "reason": reason}
```

Call this from both revocation paths:

**`purchase_history.py:mark_reverted`** (after the DynamoDB update, line 497):
```python
_record_event(txn_id, user_sub, "transaction_reverted", {"reason": reason})
# NEW: revoke entitlements
order_id = item.get("order_id")
if order_id:
    try:
        commerce_entitlement_orchestrator.revoke_entitlements_for_order(
            order_id, reason=f"transaction_reverted:{txn_id}"
        )
    except Exception:
        logger.exception("entitlement_revoke_failed txn_id=%s order_id=%s", txn_id, order_id)
        # Do not block the revert; alert ops
```

**`purchase_history.py:respond_cancel`** (inside the `if decision == "APPROVE"` branch, after the DynamoDB update):
```python
if decision == "APPROVE":
    order_id = item.get("order_id")
    if order_id:
        try:
            commerce_entitlement_orchestrator.revoke_entitlements_for_order(
                order_id, reason=f"cancel_approved:{txn_id}"
            )
        except Exception:
            logger.exception("entitlement_revoke_failed_on_cancel txn_id=%s", txn_id)
```

The revocation is best-effort (not blocking the status flip) but must be audited with alerting on failure. An `entitlement_revoke_failed` alert should page ops.

### 4.3 Entitlement Idempotency

`process_order_entitlements` should be idempotent and `revoke_entitlements_for_order` should be idempotent. If called twice for the same order, the second call should be a no-op or verify the current state rather than re-revoking. Use a DynamoDB conditional update: revoke only if the entitlement record has status `"active"`, transition to `"revoked"`.

### 4.4 Dev/Prod Parity (SECOPS-007)

- **Price derivation**: The catalog lookup is against DynamoDB. Dev uses DynamoDB Local; the `catalog` table is seeded by `scripts/local-ddb-seed.py`. Tests should seed catalog items with known prices and assert checkout ignores client-supplied prices.
- **Entitlement revocation**: The entitlement orchestrator runs against DynamoDB Local in dev. No AWS-specific services involved. Same code path.
- **Flag**: No feature flag needed for price derivation (it is strictly fixing a security bug). For entitlement revocation, a `ENTITLEMENT_REVOCATION_ENABLED` flag may be used during rollout, defaulting to `True`.

2. Complete a full purchase, request cancellation, approve as admin. Verify subsequent API access to the entitlement returns 403 or credits are zero.

### Observability

- Counter `cart_price_override_rejected_total{item_type="catalog"}` — fires when client price ≠ catalog price; alerts on probing.
- Counter `entitlement_revoked_total{reason="cancel_approved|transaction_reverted"}`.
- Alert `entitlement_revoke_failed` → PagerDuty/OpsGenie for manual intervention.
- Add `order_id` to the `purchase_transaction` DynamoDB record at checkout time (needed for revocation lookup); verify it is stored at `shoppingcart.py:663` via `record_cart_purchase`.

### Rollout Order

1. **Price server-side derivation** — ship immediately; critical security fix. Coordinate with frontend: the `unit_price_cents` field in the cart-item form should be removed or made read-only (displaying the catalog price).
2. **Entitlement revocation** — ship as a follow-up (within the same sprint). Depends on `revoke_entitlements_for_order` being implemented in the orchestrator. Deploy with `ENTITLEMENT_REVOCATION_ENABLED=true` in staging first, verify no false revocations.
3. **Entitlement idempotency hardening** — can be a follow-up PR after (2) is stable.

**Effort**: M (price fix: 1 day; entitlement revocation: 2–3 days including orchestrator work and tests).

**Rollback**:
- Price fix: revert `ShoppingCartItemIn` model change and `add_item` lookup. No DynamoDB schema change.
- Entitlement revocation: disable `ENTITLEMENT_REVOCATION_ENABLED` flag; existing granted entitlements are unaffected by rollback (safe direction for users; bad for revenue, but no data loss).

**Open questions**:
- Should `unit_price_cents` be retained for explicitly `product_type=None` (freeform seller items) with a seller-authorization check, or removed entirely? The catalog-item `add_catalog_item` path already correctly enforces server price; the freeform path is used by custom/direct-sale flows that may legitimately need a seller-set price.
- What happens to credits that have already been *consumed* by the time the entitlement is revoked? The revocation should transition the entitlement to `"revoked"` (blocking future use) but not retroactively charge for past use — this requires a policy decision by product.
- Is `order_id` reliably stored in the transaction record for all checkout paths (cart checkout, direct checkout, subscription checkout)? A pre-rollout audit of `record_cart_purchase` and analogous functions is recommended.
