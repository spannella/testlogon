# ROOT-AUTH-001: Root Login Hardening — Network Re-Gate (B3) + Bootstrap (B2) — Investigation & Implementation Write-up

## 1. Summary & Classification

Two confirmed gaps in the root session lifecycle: **B3** is an active security bypass — the root network gate is enforced at challenge creation (`POST /auth/root/login`) but not at session minting (`POST /ui/session/finalize`), meaning a root step-up challenge created from an allowed IP can be finalized (and the full root session token issued) from any IP. **B2** is a bootstrap chicken-and-egg — `POST /auth/root/login` refuses to proceed unless root MFA is already configured, but no endpoint or tool exists to configure the initial root MFA factor on a fresh deploy, making root login impossible after first install.

- **Type**: Security-fix (B3 = active bypass) + Hardening (B2 = bootstrap gap)
- **Priority**: HIGH (B3 is a security hole) / HIGH (B2 blocks production bootstrapping)
- **Status**: UNBUILT — neither B3 (re-gate at finalize) nor B2 (bootstrap endpoint) are implemented
- **Attacker class**: 🌐 any-user who has compromised root credentials + access to the root MFA device but is originating from an off-allowlist IP; also a configuration/ops gap (B2)
- **Cross-refs**: SEC-008 (trusted client IP via `X-Forwarded-For` / `TRUSTED_PROXY_CIDRS`); SECOPS-007 (dev/prod parity — bootstrap endpoint must work in dev with DDB Local)

## 2. Current-State Investigation

### 2.1 Root login challenge creation (`app/routers/root_auth.py:16-46`)

```python
@router.post("/login")
async def root_login(req: Request, body: UiSessionStartReq, user_sub: str = ...):
    # Line 23: network gate enforced HERE
    source_ip = enforce_root_network_gate(req)
    rate_limit_login_attempt(user_sub, source_ip)
    required_factors = compute_required_factors(user_sub)
    if not required_factors:
        raise HTTPException(403, "Root MFA must be configured before login")
    challenge_id = create_stepup_challenge(...)
    return UiSessionStartResp(challenge_id=challenge_id, ...)
```

The challenge is created with a `challenge_id` stored in DDB (`T.sessions`, SK `chal_<id>`). The challenge record does NOT store the source IP or a `root_login=true` flag. It contains: `required_factors`, `passed`, `refresh_ttl_seconds`, `risk_score`.

### 2.2 Session finalize (`app/routers/ui_session.py:170-190`)

```python
@router.post("/session/finalize")
async def ui_session_finalize(req: Request, body: UiSessionFinalizeReq, ...):
    chal = load_challenge_or_401(user_sub, body.challenge_id)
    sid = maybe_finalize(req, user_sub, body.challenge_id)
    if sid:
        rotate_session_cookies(req, response, user_sub, sid, ...)
        ...
        return {"status": "ok", "session_id": session_id}
```

`enforce_root_network_gate` is **never called** here. No check for `user_sub == S.root_user_sub`. Any IP that has a valid `challenge_id` (which was issued to a root user after passing the network gate on login) can finalize the session from any origin.

### 2.3 Exploit walkthrough (B3)

1. Attacker knows root credentials (password + TOTP device) and is on a whitelisted IP (e.g., a compromised VPN endpoint).
2. Attacker calls `POST /auth/root/login` from the allowed IP → receives `challenge_id`.
3. Attacker passes MFA → challenge is marked `passed: {totp: true}`.
4. Attacker relays the `challenge_id` (via any side-channel) to a machine on any IP.
5. Remote machine calls `POST /ui/session/finalize` with `challenge_id` → full root session cookies issued with no IP validation.

The `challenge_id` is a random string (generated by `create_stepup_challenge` in `app/services/sessions.py`). It has a TTL (`session_challenge_ttl_seconds`) but is otherwise unpredictable and not IP-bound.

### 2.4 Network gate implementation (`app/auth/root_network.py:60-80`)

`enforce_root_network_gate` reads `S.root_login_allowed_ips` (CIDR list) and `S.root_login_local_only`. It correctly handles trusted-proxy `X-Forwarded-For` (SEC-008 parity) — reads `S.trusted_proxy_cidrs` and only trusts XFF when the direct IP is in the proxy list. The gate logic itself is correct and reusable.

### 2.5 Bootstrap gap (B2) — `app/cli/rootctl.py:253-322`

`_root_reset_mfa_command` **deletes** all TOTP/SMS/email devices and revokes all sessions. It does not enroll new factors. `compute_required_factors(user_sub)` at `app/services/sessions.py` queries the `T.totp`, `T.sms`, and `T.email` tables; if all are empty, it returns `[]`, and `root_auth.py:26` raises 403 "Root MFA must be configured before login."

`reset-password` in rootctl requires an existing valid root session (it calls the `/root/reset-password` endpoint which uses `require_root_session`). After `reset-mfa` clears all factors, a fresh deploy has no path to set credentials.

There is no `bootstrap` command in rootctl, no `POST /auth/root/bootstrap` endpoint, and no `ROOT_BOOTSTRAP_TOKEN` in `app/core/settings.py`.

## 3. Threat Analysis

### B3 — Session finalize IP bypass

- **Impact**: A root session (highest privilege — full DB access, impersonation, rootctl parity) can be minted from any IP once the challenge is created from an allowed IP.
- **Preconditions**: Attacker must (a) know root credentials + TOTP secret/device, AND (b) have access to the network gate allowlist at least once to create the challenge. The window is `session_challenge_ttl_seconds` (typically 300–900s).
- **Why current controls fail**: The challenge TTL is the only time-bound control. The finalize endpoint has no identity of the request beyond the challenge ID and the user's cookie/bearer token.
- **Blast radius**: Full root compromise. All users, all data.
- **Code sites to change**: `app/routers/ui_session.py:170-190` (finalize handler), `app/services/sessions.py` (challenge creation — stamp source IP), `app/services/sessions.py` (maybe_finalize — validate IP).

### B2 — Bootstrap gap

- **Impact**: Fresh production deploy is un-bootstrappable; no root login possible ever.
- **Preconditions**: Fresh deploy or after `rootctl reset-mfa` without re-enrolling.
- **Blast radius**: Ops/deployment blocker; not a direct data-exposure risk, but leaves the platform with no root-level management access.

## 4. Proposed Design / Fix

### B3 — Re-gate root at finalize

**Option A (recommended): Stamp challenge with source IP, verify at finalize**

1. In `create_stepup_challenge` (`app/services/sessions.py`), accept an optional `source_ip: str | None` and `is_root_login: bool = False` parameter. Store both on the DDB challenge item.
2. In `app/routers/root_auth.py`, pass `source_ip=source_ip, is_root_login=True` to `create_stepup_challenge`.
3. In `ui_session_finalize` (`app/routers/ui_session.py:170-190`), after `load_challenge_or_401`:
   ```python
   if chal.get("is_root_login"):
       from app.auth.root_network import enforce_root_network_gate
       current_ip = enforce_root_network_gate(req)
       stored_ip = chal.get("source_ip", "")
       # Optionally enforce exact-match: if stored_ip and current_ip != stored_ip: raise 403
       # Or just re-enforce the gate (allows legitimate IP rotation within the window)
       audit_event("root_finalize_ip_check", user_sub, req, outcome="success",
                   challenge_ip=stored_ip, finalize_ip=current_ip)
   ```
4. Audit denied finalizations as `root_finalize_denied`.

**Option B (stricter): Dedicated `POST /auth/root/finalize` endpoint**

Move all root-specific logic into `app/routers/root_auth.py`. The `POST /ui/session/finalize` endpoint rejects root challenges with a 403 redirect to `/auth/root/finalize`. This isolates all root hardening in one router but requires frontend changes.

**Recommendation**: Option A is simpler and lower-risk; the exact IP match is optional (re-running the network gate is sufficient for the gate invariant even if IP changes within the window).

### B2 — First-run root bootstrap

Add `POST /auth/root/bootstrap` to `app/routers/root_auth.py`:

```python
@router.post("/bootstrap")
async def root_bootstrap(req: Request, body: RootBootstrapReq):
    """
    One-time endpoint. Gated by ROOT_BOOTSTRAP_TOKEN (env secret).
    Allowed only when no root MFA exists and behind the root network gate.
    Creates the root user record, sets initial password, and enrolls the first TOTP factor.
    Returns the TOTP provisioning URI (QR code) for operator to scan.
    Self-disables after first successful use.
    """
    if not S.root_bootstrap_token:
        raise HTTPException(403, "Bootstrap disabled (ROOT_BOOTSTRAP_TOKEN not set)")
    
    enforce_root_network_gate(req)
    
    if not secrets.compare_digest(body.token, S.root_bootstrap_token):
        audit_event("root_bootstrap_denied", S.root_user_sub, req, outcome="denied", reason="bad_token")
        raise HTTPException(403, "Invalid bootstrap token")
    
    root_sub = (S.root_user_sub or "").strip()
    existing_factors = compute_required_factors(root_sub)
    if existing_factors:
        audit_event("root_bootstrap_denied", root_sub, req, outcome="denied", reason="already_configured")
        raise HTTPException(409, "Root already has MFA configured")
    
    # Create root user record if it doesn't exist
    _ensure_root_user_record(root_sub, body.initial_password_hash)
    
    # Enroll first TOTP factor
    totp_provisioning_uri, device_id = _enroll_root_totp(root_sub)
    
    audit_event("root_bootstrap", root_sub, req, outcome="success", device_id=device_id)
    return {"status": "ok", "totp_provisioning_uri": totp_provisioning_uri, "device_id": device_id}
```

**Settings** (`app/core/settings.py`): Add `root_bootstrap_token: str = os.environ.get("ROOT_BOOTSTRAP_TOKEN", "")`. When empty, the endpoint returns 403 (effectively disabled in prod after bootstrap).

**Self-disable strategy**: Setting `ROOT_BOOTSTRAP_TOKEN=""` in env after first use disables the endpoint. Document in `docs/run-deploy.md`.

**`RootBootstrapReq`** model (`app/models.py`): `{ token: str, initial_password_hash: str }` — the operator supplies a bcrypt hash of the desired initial root password.

### Dev/Prod Parity (SECOPS-007)

Both fixes run against DDB Local in dev mode (`DDB_ENDPOINT_URL=http://localhost:8001`). The network gate uses `S.root_login_local_only=True` in dev (`.env.local.example`), which allows loopback addresses. No AWS-specific code is added.

### Rollout

1. Deploy B3 fix: stamp challenge + re-gate at finalize. Zero-downtime; existing in-flight non-root challenges are unaffected (no `is_root_login` flag → no re-gate).
2. Deploy B2 bootstrap endpoint. Set `ROOT_BOOTSTRAP_TOKEN` in env for first-run deploy. After bootstrapping, unset it.
3. Document procedure in `docs/run-deploy.md` and `docs/root-admin-login-plan.md`.

**Effort**: B3 = S (2 code changes, well-understood path); B2 = M (new endpoint, TOTP enrollment helper, settings change, documentation).
