# SEC-002: Webhook Signature/Secret Integrity — Investigation & Implementation Write-up

> ~5 pages. Code citations verified against the live codebase.

## 1. Summary & Classification

Inbound provider webhooks (CCBill, PayPal, UPS, eIDV/KYC) can be forged to grant unpaid financial entitlements — wallet credits, subscription activations, order delivery confirmations, identity-tier upgrades — because signature verification secrets fall back to hardcoded development defaults, IP allow-list policies can be in a non-enforcing "monitor" mode, user identity is derived from an untrusted request field (`custom_id`) rather than a server-side mapping, and replay protection is absent or incomplete on several paths.

- **Type**: security-fix
- **Severity**: Critical
- **Status**: Open
- **Area**: `app/services/billing_ccbill.py`, `app/routers/billing_ccbill.py`, `app/routers/paypal.py`, `app/services/kyc_eidv.py`, `app/routers/ups.py`, `app/routers/billing.py`
- **Attacker class**: 🌐 any-user (can forge webhooks from the internet if HMAC secret is the known default)
- **Cross-references**: [[SEC-003]] (hardcoded fallback secrets); [[SEC-008]] (trusted client IP for CCBill IP allow-list); [[SECOPS-007]] (dev/prod parity — "local" mode must not be reachable in prod)


## 2. Current-State Investigation

### 2a. CCBill — default HMAC secret and IP policy mode (`app/services/billing_ccbill.py:159–172`, `app/routers/billing_ccbill.py:513–554`)

**Secret resolution** (`billing_ccbill.py:166–172`):

```python
def _webhook_signature_secret_for_mode(mode: str) -> str:
    secret = (S.ccbill_webhook_signature_secret or "").strip()
    if secret:
        return secret
    if mode == "local":
        return "local-ccbill-webhook-secret"   # ← hardcoded default
    return ""
```

**Mode selection** (`billing_ccbill.py:159–163`):

```python
def ccbill_webhook_verify_mode() -> str:
    raw_mode = (S.ccbill_webhook_verify_mode or "").strip().lower()
    if raw_mode in {"ip+sig", "sig_only", "local"}:
        return raw_mode
    return "local" if S.dev_mode else "ip+sig"
```

If `S.ccbill_webhook_verify_mode` is not set and `S.dev_mode=False`, mode is `"ip+sig"`. But if `S.ccbill_webhook_verify_mode="local"` is accidentally left in a prod environment (e.g. copied from a dev `.env`), mode becomes `"local"` and the hardcoded secret `"local-ccbill-webhook-secret"` is used.

**IP allow-list enforcement** (`billing_ccbill.py:513–523`):

```python
def webhook_remote_ip_allowed(ip_str: str, *, enforce: bool = False) -> bool:
    if not (enforce or S.ccbill_webhook_ip_enforce):
        return True   # ← passes any IP when neither enforce=True nor flag is set
```

In the webhook handler (`billing_ccbill.py:515`), `enforce=True` is only set when `verify_mode == "ip+sig"`. In `"sig_only"` or `"local"` mode, the IP check is skipped. In `"monitor"` mode (not a named constant but achievable by setting `ccbill_webhook_ip_enforce=False`), IP filtering is silent.

**Ticket's line 515 claim**: The router at `billing_ccbill.py:515` does apply `enforce=True` for `ip+sig` mode. The ticket's description of "monitor" mode maps to the combination of `sig_only` + non-enforced IP, which is a real gap. The exact mechanism is that the default `enforce=False` in `webhook_remote_ip_allowed` means IP filtering is opt-in, not opt-out.

**Replay/dedupe** (`billing_ccbill.py:542–554`): CCBill does have a `mark_webhook_processed` call using a SHA-256 dedupe key. However, the dedupe key is `SHA256(event_type + "|" + raw_body)` — if an attacker constructs a body that hashes identically (via body manipulation) or if two legitimate events have the same body, deduplication fails silently.

### 2b. PayPal — user identity from untrusted `custom_id` (`app/routers/paypal.py:1291–1313`)

```python
def _split_custom_id(s):
    if not s or "|" not in s:
        return None, None
    a, b = s.split("|", 1)
    if b.startswith("LEDGER#"):
        return a, b
    return a, None

purchase_units = resource.get("purchase_units") or []
if purchase_units:
    cid = purchase_units[0].get("custom_id")
    user_id, ledger_sk_hint = _split_custom_id(cid)
```

The `user_id` controlling which account receives the credit is parsed from the `custom_id` field of the webhook payload. PayPal sets `custom_id` at order creation time, but the webhook does not cryptographically bind the `custom_id` to the PayPal order ID. An attacker who can forge a PayPal webhook body (e.g. using the known-default CCBill or a missing PayPal verification) can set `custom_id` to any `user_sub|LEDGER#...` string and credit any account. The ledger_sk_hint (`LEDGER#...`) extracted from `custom_id` is used to update a specific ledger entry — if a real order exists with a matching ledger key, the attacker can direct the credit to themselves.

### 2c. eIDV / KYC — default signing key (`app/services/kyc_eidv.py:202`)

```python
key = str(S.kyc_eid_mock_signing_key or "dev-mock-eid-signing-key").encode("utf-8")
sig = hmac.new(key, raw_payload.encode("utf-8"), hashlib.sha256).hexdigest()
```

`_sign_assertion` (line 196) and `validate_assertion_signature` (line 207) share the same key derivation. If `S.kyc_eid_mock_signing_key` is unset (empty string → falsy), both signing and verification use `"dev-mock-eid-signing-key"`. An attacker can independently compute the HMAC of any assertion payload using the published default key and forge an eIDV response that passes `validate_assertion_signature`, triggering identity verification / tier upgrade.

### 2d. Stripe — dedupe then process race (`app/routers/billing.py:1261–1262`)

```python
if not mark_event_processed(event["id"]):
    return {"received": True, "deduped": True}
```

`mark_event_processed` (line 669) uses a DynamoDB conditional write (`attribute_not_exists(pk)`) — this is correct. However, the Stripe event ID is used as the dedup key. Stripe guarantees event IDs are globally unique, so this path is sound as long as the conditional write is truly atomic. The DDB conditional put correctly uses `attribute_not_exists(pk)` and raises `ConditionalCheckFailedException` on duplicate, so Stripe dedup is implemented correctly. The ticket's concern about a "processing race" is valid only under a split-brain scenario (two backend processes receiving the same event simultaneously) — the conditional write handles that correctly.

**Remaining gap**: downstream credit operations after the dedupe check are not individually idempotent. If `mark_event_processed` returns `True` but the credit write fails and the handler returns 500, Stripe will retry — and the second delivery will also call `mark_event_processed`, get `False`, and return `{"deduped": True}` — so the credit is never applied. This is a **loss scenario**, not a double-credit scenario. Proper fix: use DDB TransactWrite to atomically mark processed + write credit.

### 2e. UPS webhook — no timestamp/replay check (`app/routers/ups.py:91–155`)

The UPS tracking webhook handler (`ups_tracking_webhook` at line 91) verifies the HMAC signature but performs no timestamp validation. There is no `mark_webhook_processed` call. A captured, validly signed UPS delivery event can be replayed indefinitely to re-trigger delivery notifications and potentially mark orders as delivered multiple times if the downstream `apply_tracking_result` call is not idempotent.

### 2f. Dev vs prod behavior today

In dev (`dev_mode=True`): `ccbill_webhook_verify_mode()` returns `"local"`, secret is `"local-ccbill-webhook-secret"`, UPS secret is `_ups_sig_secret()` (checked separately). The `kyc_eid_mock_signing_key` setting is typically empty in dev, so the default `"dev-mock-eid-signing-key"` is used. These defaults are intentional for local testing but become critical if inadvertently deployed to production.


## 3. Gap / Threat Analysis

### Attack A — Forge CCBill NewSale/Renewal (hardcoded secret)

1. Attacker reads the open-source `billing_ccbill.py` and learns `"local-ccbill-webhook-secret"`.
2. Confirms that `S.ccbill_webhook_verify_mode="local"` is set in the target environment (or that `S.dev_mode=True`).
3. Crafts a `POST /api/ccbill/webhook?eventType=NewSaleSuccess` with a body including `subscriptionId`, `billedAmount`, `billedCurrencyCode`, signs it with `HMAC-SHA256(body, "local-ccbill-webhook-secret")`.
4. Backend accepts the signature, credits the wallet / activates subscription for any `user_sub` embedded in the payload.

**Blast radius**: unlimited — attacker can grant any user any number of wallet credits or subscription renewals. `mark_webhook_processed` does prevent exact replay, but each unique body produces a new dedupe key.

### Attack B — Forge PayPal CAPTURE to credit arbitrary user

1. Attacker knows the PayPal order ID format (or creates a real order that PayPal assigns).
2. Constructs a forged `PAYMENT.CAPTURE.COMPLETED` webhook body with `custom_id = "victim_user_sub|LEDGER#..."`.
3. Posts it to `/api/paypal/webhook`. If PayPal signature verification is bypassed (see SEC-003 for empty-secret risk) or if attacker controls the PayPal account, the backend credits `victim_user_sub`.

### Attack C — Forge eIDV assertion for KYC tier upgrade

1. Attacker learns `"dev-mock-eid-signing-key"` from the source.
2. Constructs a JSON assertion with `identity_verified: true`, `tier: "verified"`, `user_sub: "target"`.
3. Signs with `HMAC-SHA256(assertion, "dev-mock-eid-signing-key")`, submits to the eIDV callback endpoint.
4. Backend calls `validate_assertion_signature(raw_assertion, sig)` → returns True → KYC tier upgrade applied.

## 4. Proposed Design / Fix

### 4a. CCBill — fail-closed secret, remove "local" mode in prod

**`app/services/billing_ccbill.py`**:

```python
def _webhook_signature_secret_for_mode(mode: str) -> str:
    secret = (S.ccbill_webhook_signature_secret or "").strip()
    if secret:
        return secret
    if S.dev_mode and mode == "local":
        return "local-ccbill-webhook-secret"   # dev only
    raise RuntimeError(
        "CCBILL_WEBHOOK_SIGNATURE_SECRET must be set in non-dev mode"
    )
```

Add a startup check in `app/main.py` (alongside existing startup validators):

```python
if not S.dev_mode and not S.ccbill_webhook_signature_secret:
    raise RuntimeError("CCBILL_WEBHOOK_SIGNATURE_SECRET required in prod")
```

Also enforce that `ccbill_webhook_verify_mode != "local"` in non-dev.

### 4b. PayPal — server-side order→user mapping

Introduce a DDB item written at order creation:

```
T.billing: pk="PAYPAL_ORDER#{order_id}", sk="USER_MAP", user_sub=..., ledger_sk=..., created_at=...
```

At webhook time, resolve `user_id` by looking up `T.billing.get_item(pk=f"PAYPAL_ORDER#{order_id}", sk="USER_MAP")` instead of parsing `custom_id`. The `custom_id` field can still be set as a fallback for logging, but must never be the sole source of identity for credits.

### 4c. KYC eIDV — remove default signing key

**`app/services/kyc_eidv.py`**:

```python
def _get_signing_key() -> bytes:
    key = (S.kyc_eid_mock_signing_key or "").strip()
    if not key:
        if S.dev_mode:
            raise RuntimeError("KYC_EID_MOCK_SIGNING_KEY must be set even in dev")
        raise RuntimeError("KYC_EID_MOCK_SIGNING_KEY required")
    return key.encode("utf-8")
```

Startup check: refuse to boot if key is absent or equals `"dev-mock-eid-signing-key"` in non-dev.

### 4d. UPS webhook — timestamp tolerance + replay store

```python
# After signature verification:
ts_header = req.headers.get("x-ups-timestamp", "")
if ts_header:
    event_ts = int(ts_header)
    if abs(now_ts() - event_ts) > 300:   # 5-minute tolerance
        raise HTTPException(403, "Timestamp out of tolerance")

dedupe_key = req.headers.get("x-ups-event-id") or hashlib.sha256(raw).hexdigest()
if not _mark_ups_event_processed(dedupe_key):
    return {"received": True, "deduped": True}
```

`_mark_ups_event_processed` follows the same DDB conditional-put pattern as `mark_event_processed` in `billing.py`.

### 4e. Stripe atomic dedupe + credit

Use DDB `TransactWrite` to atomically write the dedupe record and the credit ledger entry:

```python
T.billing.meta.client.transact_write_items(TransactItems=[
    {"Put": {"TableName": T.billing.name,
             "Item": dedupe_item,
             "ConditionExpression": "attribute_not_exists(pk)"}},
    {"Put": {"TableName": T.billing.name, "Item": credit_item}},
])
```

On `TransactionCanceledException` with `ConditionalCheckFailed` reason for the dedupe item: return `deduped=True`. On any other error: return 500 (Stripe retries).

### 4f. Dev/prod parity (SECOPS-007)

All provider integrations use the same code path in dev and prod, selected by `S.dev_mode`:
- **Dev**: DDB Local (port 8001) stores dedupe/order-mapping records; moto handles S3; mock KMS for encryption. The `"local-ccbill-webhook-secret"` is only permitted when `S.dev_mode=True`. The `kyc_eid_mock_signing_key` must be explicitly set even in dev (use a value from `.env.local.example` — a long random hex string).
- **Prod**: AWS DDB for dedupe, AWS Secrets Manager for secrets. No fallback defaults permitted.

### 4g. Alternatives considered

- **Allowlisting webhook events by IP at the load balancer**: valid defence-in-depth but does not address forged secrets or `custom_id` manipulation.
- **Asymmetric signatures (RSA/ECDSA)**: PayPal and newer CCBill APIs support this. Long-term preferred; deferred as a provider-migration effort.


## 5. Testing, Verification & Rollout

### pytest unit tests

1. `test_ccbill_webhook_rejects_default_secret_in_prod`: set `dev_mode=False`, `ccbill_webhook_signature_secret=""` → request signed with `"local-ccbill-webhook-secret"` → HTTP 403.
2. `test_ccbill_webhook_accepts_correct_secret`: configure real secret → correct signature → 200, event processed.
3. `test_ccbill_webhook_dedupe`: send identical body twice → second call returns `{"deduped": True}`.
4. `test_paypal_webhook_credits_correct_user`: create order-user mapping in DDB; fire webhook; assert credit goes to mapped user, not a forged `custom_id` user.
5. `test_paypal_webhook_forged_custom_id_rejected`: no order-user map exists for order_id; forged `custom_id` → no credit issued.
6. `test_eidv_assertion_forged_default_key_rejected`: `dev_mode=False`, `kyc_eid_mock_signing_key=""` → `validate_assertion_signature` raises `RuntimeError` before comparison.
7. `test_ups_replay_rejected`: send UPS webhook event; repeat with same dedupe key → `{"deduped": True}`.
8. `test_ups_stale_timestamp`: send UPS webhook with `x-ups-timestamp` 10 minutes in the past → HTTP 403.
9. `test_stripe_atomic_dedupe_credit`: mock DDB `transact_write_items` to raise `ConditionalCheckFailed` → returns `deduped=True`, no credit written.

All tests use moto DDB, no real payment provider calls. Fully offline.

### Playwright E2E

No direct UI-level E2E test for webhook forgery (these are server-side tests). Optional: an E2E test that confirms a correctly-signed CCBill `NewSaleSuccess` in dev mode (using the dev secret) does credit the wallet, and that an incorrectly-signed one does not — exercising the full route in integration.

### Manual / QA steps

1. Set `CCBILL_WEBHOOK_VERIFY_MODE=local` and `CCBILL_WEBHOOK_SIGNATURE_SECRET=""` with `DEV_MODE=0` → backend startup should fail with `RuntimeError`.
2. With dev stack running, send a forged CCBill webhook signed with the default key → expect HTTP 403 (in dev, but using dev secret; in prod, expect 403 outright if `dev_mode=False`).
3. Create a PayPal order for Alice; fire a webhook with `custom_id=bob_sub|...`; confirm Bob's wallet is not credited.

### Observability

- Metric `webhook_signature_reject_total{provider="ccbill|paypal|ups|eidv"}` on every 403.
- Metric `webhook_replay_total{provider=...}` on every dedupe hit.
- Alert if `webhook_signature_reject_total` spikes (potential active forgery attempt).

### Rollout

1. Add startup-time secret validation checks (fail-safe, no traffic impact). Deploy first.
2. Add PayPal order→user mapping on order creation; deploy before the webhook identity-resolution change.
3. Update `paypal.py` webhook handler to use DDB mapping. Temporarily keep `custom_id` fallback with a WARNING log for orders created before step 2.
4. UPS replay store + timestamp check — independent deploy.
5. Stripe atomic dedupe — deploy during low-traffic window; monitor for `TransactionCanceledException` spike.

**Effort**: M (PayPal order-map schema change is the largest piece). No DDB schema migration for existing data required (new mapping only written for new orders going forward).
