# SEC-008: X-Forwarded-For Spoofing → Rate-Limit / Blocklist / Audit Bypass — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

`app/core/normalize.py:client_ip_from_request` (line 9-18) extracts the client IP from the first value in the `X-Forwarded-For` header with **no validation that the direct peer is a trusted proxy**. Because every security decision in the platform that cares about "who is sending this request" — rate limiting, IP blocklisting, audit logging, device-trust anomaly detection, and the magic-link IP verification — flows through this one function, a single spoofed header can bypass all of them simultaneously.

This is the foundational IP-resolution vulnerability. It must be fixed before any of the per-feature defences (SEC-009 per-account lockout, SEC-003 fail-closed secrets) can be considered reliable.

- **Type**: security-fix (critical/foundational)
- **Priority/Severity**: Critical
- **Status**: Open
- **Owning area**: `app/core/normalize.py` and every caller
- **Attacker class**: 🌐 any network-reachable client (unauthenticated and authenticated)
- **Cross-references**: [[SEC-009]] (per-account lockout depends on correct IP), [[SECOPS-007]] (dev/prod parity), [[ROOT-AUTH-001]] (root network gate already implements a correct variant)

## 2. Current-State Investigation (what exists today)

### 2.1 The vulnerable function (`app/core/normalize.py:9-18`)

```python
 9  def client_ip_from_request(req) -> str:
10      if req is None:
11          return "0.0.0.0"
12      xff = req.headers.get("x-forwarded-for")
13      if xff:
14          for part in xff.split(","):
15              candidate = part.strip()
16              if candidate:
17                  return candidate   # ← returns FIRST value, no proxy validation
18      return req.client.host if req.client else "0.0.0.0"
```

The logic returns the **first** comma-separated value in `X-Forwarded-For` if the header is present. No check is made to see whether `req.client.host` (the TCP peer address) is in a trusted proxy CIDR range. A client can inject any string by sending `X-Forwarded-For: 1.2.3.4` directly; the function returns `"1.2.3.4"` regardless.

### 2.2 The correct implementation (already in `app/auth/root_network.py:25-57`)

```python
25  def _resolve_client_ip(req: Request) -> Tuple[…]:
26      direct_host = req.client.host if req and req.client else ""
27      direct_ip = ipaddress.ip_address(direct_host)
35      trusted_proxy_networks = _parse_cidrs(S.trusted_proxy_cidrs)
36      xff = (req.headers.get("x-forwarded-for") or "").strip()
37      if not xff:
38          return direct_ip, "direct"
40      if not _ip_in_networks(direct_ip, trusted_proxy_networks):
41          # Ignore spoofed XFF from untrusted source.
42          return direct_ip, "direct_untrusted_proxy"
44      first = xff.split(",", 1)[0].strip()   # ← reads first hop
57      return forwarded_ip, "trusted_proxy"
```

This function correctly gates on whether the TCP peer is in `S.trusted_proxy_cidrs` before trusting `X-Forwarded-For`. It is used only for the root-auth network gate (`app/routers/root_auth.py:23`). All other callers use the broken `client_ip_from_request`.

**Note on XFF ordering**: RFC 7239 and de-facto load-balancer convention append the client IP to the left. The rightmost untrusted hop is the most trustworthy when behind a trusted proxy chain. `_resolve_client_ip` reads the first (leftmost) value, which works correctly for a single-proxy deployment but is still vulnerable to header prepending in a multi-hop proxy chain. The fix below addresses both.

### 2.4 Rate-limit middleware detail (`app/middleware/rate_limit.py:95-145`)

```python
100    ip = client_ip_from_request(request)   # ← spoofable

104    if is_blocked(ip):                      # ← bypass: spoof a non-blocked IP
107        return JSONResponse(status_code=403, …)

119    allowlisted = is_allowlisted(ip)        # ← abuse: spoof an allowlisted IP → skip all limits

126    allowed, remaining, reset = check_rate_limit(
127        pk=f"IP#{ip}",                      # ← rotate IP per request → fresh bucket each time
```

Three distinct bypasses from one spoofable value:
1. **Blocklist bypass**: any blocked IP is trivially circumvented by sending a different `X-Forwarded-For`.
2. **Allowlist abuse**: spoof the IP of an allowlisted CIDR (e.g., an internal load balancer) to skip all rate limits.
3. **Rate-limit exhaustion bypass**: rotate a different IP per request; each gets its own fresh sliding-window bucket.

### 2.5 MFA brute-force path (`app/routers/ui_mfa.py:57-69`)

```python
57    enforce_lockout(user_sub, client_ip_from_request(req), "mfa_totp")
```

`enforce_lockout` and `record_lockout_failure` key off `(user_sub, ip, factor)`. Rotating the IP means `enforce_lockout` never sees a previously failed attempt, enabling unlimited TOTP/SMS/email guesses. Combined with `POST /ui/mfa/sms/begin` which resets the per-challenge `sms_code_attempts` counter (line 86-87), an attacker can send infinite SMS codes and guess them without limit.

### 2.6 Magic-link IP binding (`app/services/magic_links.py:89`)

```python
89    current_ip = client_ip_from_request(req)
```

Magic links store the requestor IP; the consume endpoint verifies the current IP matches. Spoofing the victim's IP (learned from a phishing campaign or login log) allows using the victim's magic link from a different machine.

### 2.7 Dev vs. prod

In dev, `DEV_MODE=1`, no reverse proxy in front of uvicorn; `req.client.host` is always `127.0.0.1` from the Vite dev proxy. In prod, uvicorn sits behind an AWS ALB or nginx that sets the real `X-Forwarded-For`. The bug exists in both environments but is exploitable only from outside the local machine in prod.

## 3. Gap / Threat Analysis

### Full attack scenario — brute-force login/MFA bypass

1. Attacker has a target username (email enumerable from registration endpoint).
2. `POST /ui/session/login` with wrong password + `X-Forwarded-For: <random>` → 401, no IP counted.
3. After N password attempts (rotated IPs), lockout is never triggered for any single IP.
4. Once authenticated with a weak password, attacker hits `POST /ui/mfa/sms/begin` (resets `sms_code_attempts=0`), then `POST /ui/mfa/sms/verify` with each `000000`–`999999` → 10^6 guesses, never locked out at the IP level.

### Blocklist evasion scenario

A SECOPS operator adds a known attacker IP to the blocklist. The attacker sends `X-Forwarded-For: 8.8.8.8` (a non-blocked, publicly known IP) — their real IP is blocked but they bypass it by spoofing a trusted-looking address. All downstream SECOPS tooling that keys off the recorded IP in audit events records `8.8.8.8`, poisoning the forensic trail.

### Allowlist privilege escalation

If any CIDR is allowlisted (e.g., `10.0.0.0/8` for internal health checks), spoofing `X-Forwarded-For: 10.0.0.1` bypasses all global rate limits, enabling unlimited automated API abuse.

### Impact

- Critical for auth endpoints: unlimited brute-force of 6-digit OTP codes ≈ guaranteed account takeover given enough time.
- High for rate limits: denial-of-wallet if the platform charges per-request.
- Medium for audit: poisoned forensics impede incident response.

## 4. Proposed Design / Fix

### 4.1 Replace `client_ip_from_request` with the trusted-proxy-aware resolver

**`app/core/normalize.py`** — replace the broken function with an improved version based on `root_network._resolve_client_ip`, generalised to handle a chain of trusted proxies and to read the rightmost untrusted hop:

```python
import ipaddress
from typing import Optional

def client_ip_from_request(req) -> str:
    """Return the best-available client IP.

    If the immediate TCP peer (req.client.host) is in TRUSTED_PROXY_CIDRS,
    walk the X-Forwarded-For list from right to left and return the
    rightmost IP that is NOT in the trusted-proxy CIDR set.
    If no TRUSTED_PROXY_CIDRS are configured, always return the socket peer.
    """
    if req is None:
        return "0.0.0.0"
    peer = req.client.host if req.client else ""
    trusted_cidrs = _parse_trusted_cidrs()   # from S.trusted_proxy_cidrs

    if not trusted_cidrs or not _ip_in_cidrs(peer, trusted_cidrs):
        # Not behind a trusted proxy — use the socket peer directly.
        return peer or "0.0.0.0"

    xff = req.headers.get("x-forwarded-for", "")
    hops = [h.strip() for h in xff.split(",") if h.strip()]
    # Walk right-to-left; return first hop NOT in trusted CIDRs
    for hop in reversed(hops):
        try:
            if not _ip_in_cidrs(hop, trusted_cidrs):
                return hop
        except ValueError:
            continue
    return peer or "0.0.0.0"
```

`_parse_trusted_cidrs()` reads `S.trusted_proxy_cidrs` (already defined in `app/core/settings.py:32`) and caches the result.

**No changes required at any call site** — the function signature is identical. All 32+ call sites continue to work without modification.

### 4.2 Settings (`app/core/settings.py:32`)

`trusted_proxy_cidrs` is already defined. The prod deployment must set `TRUSTED_PROXY_CIDRS` to the ALB/nginx CIDR(s). In dev, leave it empty — the function falls back to the socket peer (`127.0.0.1` from the Vite proxy), which is correct.

### 4.3 Per-account lockout (synergy with SEC-009)

Even with the correct IP, IP-rotation from a botnet can still try multiple IPs. The SEC-009 fix (per-account cumulative attempt counter, not reset by `begin`) is the complementary defence. SEC-008 fixes IP bypass; SEC-009 ensures that even with a valid IP, per-account brute-force is capped.

### 4.4 Dev/Prod parity (SECOPS-007)

- **Dev** (`DEV_MODE=1`, `TRUSTED_PROXY_CIDRS=""` or unset): no proxy check, uses socket peer. The Vite proxy sends requests from `127.0.0.1`; that is the IP used for all rate-limit keys. XFF headers in E2E tests are ignored — correct behaviour.
- **Prod** (`DEV_MODE=0`, `TRUSTED_PROXY_CIDRS="10.0.0.0/8"`): XFF is trusted only when the TCP peer is in the ALB subnet. Real client IPs flow through correctly.
- Same code path both environments; behaviour selected by `TRUSTED_PROXY_CIDRS` value.

### 4.5 Alternatives considered

- **Starlette `ProxyHeadersMiddleware`**: provides the same trusted-proxy XFF resolution and sets `request.client.host` to the resolved IP, so all `req.client.host` calls downstream "just work". **Rejected** for now — changing `req.client.host` is a wider blast radius and requires validating every use of `request.client`; the targeted `client_ip_from_request` replacement is safer.
- **Remove XFF support entirely**: rejected — legitimate prod deployments behind ALBs require it.

### Observability

- Add `ip_resolution_method` (`"direct"` | `"trusted_proxy"` | `"spoofed_xff_ignored"`) to every rate-limit and login-anomaly audit event.
- Alert on a high volume of `ip_resolution_method=spoofed_xff_ignored` events — indicates active probe with spoofed headers.

### Rollout

1. **Phase 1** — deploy the new `client_ip_from_request` with `TRUSTED_PROXY_CIDRS=""` (empty). Zero behaviour change in dev or prod until the CIDR is set.
2. **Phase 2** — set `TRUSTED_PROXY_CIDRS` in prod to the ALB/nginx subnet. Monitor `ip_resolution_method` metrics for one week to confirm correct IP extraction.
3. **Phase 3** — enable per-account lockout (SEC-009) as the complementary defence.

**Rollback**: set `TRUSTED_PROXY_CIDRS=""` to revert to old socket-peer behaviour (same as before the fix when no proxy is configured).

**Risks**: if `TRUSTED_PROXY_CIDRS` is set incorrectly (too broad), the trusted-proxy path is triggered for untrusted peers and XFF is again spoofable. Operator documentation must clearly state what CIDRs to use.
