# SEC-013: Economic / Business-Logic Abuse (idempotency & atomicity) — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

Five distinct non-atomic or non-idempotent write operations in the financial and messaging layers allow an attacker to extract economic value or consume protected content multiple times:

1. **Affiliate commission replay** — `record_affiliate_commission` in `app/services/referrals.py:289` issues an unconditional `put_item`; replaying the same `transaction_id` pays the commission again.
2. **Free-trial unlimited re-subscribe** — `subscribe` in `app/routers/subscription_server.py:853–860` accepts caller-supplied `trial_days` with no check for prior trial claims on the same `(subscriber_id, plan_id)` pair.
3. **Promo per-user limit TOCTOU** — `validate_promo_code` checks per-user usage (`promo_codes.py:287`) but `redeem_promo_code` at line 357 does not re-validate it before writing the redemption; and the global `current_uses` guard is atomic but the per-user guard is not.
4. **Referral attribution race** — `attribute_referral` at `referrals.py:179–203` does a get-then-put with no `ConditionExpression`; two concurrent calls with the same `referred_user_id` can both pass the "existing" check and both write attributions.
5. **View-once re-read race** — `mark_message_viewed` at `app/routers/messaging.py:11344–11348` uses `ADD view_once_seen :uid` with no condition guarding the case where the user has already been added; under a race two concurrent view requests both see the flag as unset and both fanout `view_once_consumed` events.

- **Type**: security-fix (business-logic / economic abuse)
- **Severity**: Critical (affiliate commission, subscription trial); High (promo codes, attribution, view-once)
- **Status**: Open
- **Area**: `app/services/referrals.py`, `app/routers/subscription_server.py`, `app/services/promo_codes.py`, `app/routers/messaging.py`
- **Attacker class**: 🌐 any authenticated user (subscription trial, promo codes); 🌐 referral partner (commission replay, attribution)
- **Dependencies**: SECOPS-007 (dev/prod parity — all DDB writes use DDB Local in dev; conditional writes work identically)

## 2. Current-State Investigation (what exists today)

### 2.1 Affiliate commission replay

`app/services/referrals.py:273–289`:
```python
entry: Dict[str, Any] = {
    "pk": f"AFFILIATE#{referrer_id}",
    "sk": f"COMMISSION#{ts}#{transaction_id}",
    ...
}
tbl.put_item(Item=entry)
```

The sort key incorporates `ts` (the current Unix timestamp) and `transaction_id`. Since `ts = now_ts()` is re-evaluated on each call, two calls with the same `transaction_id` at different times produce different sort keys — DynamoDB happily writes both items. A referral partner (or a compromised webhook consumer) that replays the `transaction_id` for a $100 purchase will collect a commission each time.

There is no `ConditionExpression` on this `put_item`. The global-uses counter at `promo_codes.py:380` shows the correct pattern (`ConditionExpression=Attr("current_uses").lt(max_uses)`), but `record_affiliate_commission` does not follow it.

### 2.2 Free-trial unlimited re-subscribe

`app/routers/subscription_server.py:853–860`:
```python
if body.trial_days:
    trial_start = ts
    trial_end = ts + int(body.trial_days) * 86400
    period_end = trial_end
    status = "trialing"
```

There is no check for whether this `(subscriber_id, plan_id)` pair has ever received a trial before. A subscriber can cancel after using 6 of 14 free trial days, wait, and re-subscribe with `trial_days=14` for another full trial indefinitely. The creator absorbs the content-delivery cost without compensation.

The check for creator self-subscription (`line 832`) and discount code validation (`line 843`) are present, but no per-subscriber-per-plan trial-claim record exists anywhere in the DDB schema for this table.

### 2.3 Promo per-user limit TOCTOU

`app/services/promo_codes.py`:

- `validate_promo_code` (line 239) reads `_query_promo_user_redeems` and compares against `max_uses_per_user` (line 287–291). This is a read-only advisory check.
- `redeem_promo_code` (line 357) atomically increments `current_uses` on the global counter (line 380), but does **not** re-check the per-user limit before writing the REDEEM row at line 407:

```python
_put(redeem_item)   # line 407 — no per-user condition
return redeem_item, None
```

Under a race: two concurrent checkout requests by the same user both call `validate_promo_code` (both pass), then both call `redeem_promo_code`. The atomic `current_uses` increment prevents over-redemption globally, but both per-user REDEEM rows are written, violating the per-user cap.

Additionally, `validate_promo_code` does not re-check `active` or `expires_at` at redeem time (only at validate time). If a code is deactivated between validation and redemption, the redemption still succeeds.

### 2.4 Referral attribution race

`app/services/referrals.py:178–203`:
```python
existing = tbl.get_item(Key={"pk": f"REFERRAL#{referred_user_id}", "sk": "META"}).get("Item")
if existing:
    return None
...
tbl.put_item(Item=item)   # line 203 — no ConditionExpression
```

Two concurrent registration events for the same `referred_user_id` (e.g. two browser tabs submitting simultaneously) both read `existing=None`, both pass the check, and both write `pk=REFERRAL#{referred_user_id} sk=META`. The second write silently overwrites the first with a different `referrer_id`, or two separate items with different referrer attribution could exist if the table's key schema allowed it.

The correct fix is already demonstrated in `create_referral_code` at `referrals.py:102`:
```python
tbl.put_item(Item=item, ConditionExpression="attribute_not_exists(pk)")
```
The `attribute_referral` function at line 203 does not use this pattern.

### 2.5 View-once re-read race

`app/routers/messaging.py:11342–11348`:
```python
if msg.get("view_once") and user_id != msg.get("sender_id"):
    tbl_msgs.update_item(
        Key={"conversation_id": conversation_id, "message_id": message_id},
        UpdateExpression="ADD view_once_seen :uid",
        ExpressionAttributeValues={":uid": {user_id}},
    )
```

DynamoDB's `ADD` on a String Set is idempotent in the sense that adding the same element twice is a no-op at the DDB level. However, the _application-level_ race is: two concurrent `mark_message_viewed` calls both pass the `msg.get("view_once")` check before either has written to DDB. Both calls proceed to the `update_item`; both fanout a `message:view_once_consumed` SSE event (line 11349–11354); and both can return a 200 to the client. The *content delivery* race (whether the client gets the actual media URL) is handled by `_consume_once_media_state_atomic` at line 3738–3781 which *is* guarded with a `ConditionExpression`. But `mark_message_viewed` is a separate endpoint that lacks this guard and triggers the SSE broadcast, creating a double-notification and double read-receipt.

### 2.6 Dev vs prod behavior

All five issues are present in both dev (DDB Local) and prod (real DynamoDB). DynamoDB Local supports all `ConditionExpression` operations identically to production. The fixes are pure DDB conditional write changes — no AWS service differences.

## 3. Gap / Threat Analysis

### 3.1 Commission replay — full attack scenario

**Preconditions**: Attacker is an affiliate partner with a referral code. They have referred at least one paying user. They have access to the webhook or API endpoint that calls `record_affiliate_commission` (or can replay a network request captured via a man-in-the-middle or from a compromised payment provider integration).

**Attack**: Replay `POST /ui/referrals/commission` (or the internal webhook handler) with the same `transaction_id` ten times. Each call writes a new COMMISSION row (`sk = COMMISSION#{different_ts}#{same_transaction_id}`) and `commission_cents` accumulates in the referrer's wallet.

**Blast radius**: Unlimited — each replay multiplies the commission. If commission rate is 20% on a $500 purchase, each replay pays $100. Ten replays = $1000 in fraudulent payouts.

### 3.2 Free trial re-subscribe

**Preconditions**: Any authenticated user with a subscription plan that offers trials.

**Attack**: Subscribe → trial starts → cancel → re-subscribe with `trial_days=14` → repeat indefinitely. Creator receives no revenue; platform absorbs infrastructure cost.

### 3.3 Promo per-user race

**Preconditions**: Attacker has a valid promo code with `max_uses_per_user=1`. They can make concurrent requests (e.g. two browser tabs or a script).

**Attack**: Send two concurrent `POST /ui/promo/validate` requests (both pass), then two concurrent `POST /checkout` requests that both call `redeem_promo_code`. Both REDEEM rows are written; both checkouts proceed at the discounted price.

### 3.4 Enumerate code sites that must change

| File | Line | Change |
|------|------|--------|
| `app/services/referrals.py` | 203 | `put_item` → add `ConditionExpression="attribute_not_exists(pk)"` |
| `app/services/referrals.py` | 275, 289 | Change SK to `COMMISSION#{transaction_id}` (stable); add `ConditionExpression="attribute_not_exists(pk) AND attribute_not_exists(sk)"` |
| `app/routers/subscription_server.py` | 853 | Add check: query `TRIAL_CLAIMED#{subscriber_id}#{plan_id}` before granting trial |
| `app/services/promo_codes.py` | 357–408 | Add per-user conditional write in `redeem_promo_code`; re-check `active` + `expires_at` at redeem time |
| `app/routers/messaging.py` | 11343–11348 | Add `ConditionExpression="NOT contains(view_once_seen, :uid)"` to the `update_item` |

## 4. Proposed Design / Fix

### 4.1 Commission idempotency

Change the sort key from `COMMISSION#{ts}#{transaction_id}` to `COMMISSION#{transaction_id}` (deterministic). Add a `ConditionExpression`:

```python
entry = {
    "pk": f"AFFILIATE#{referrer_id}",
    "sk": f"COMMISSION#{transaction_id}",   # stable key
    ...
}
try:
    tbl.put_item(
        Item=entry,
        ConditionExpression="attribute_not_exists(sk)",
    )
except ClientError as e:
    if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
        logger.info("Commission %s already recorded (idempotent replay)", transaction_id)
        return None   # idempotent — no error
    raise
```

The `attribute_not_exists(sk)` condition checks that no item with this sort key exists. If the commission was already recorded (replay), the write is rejected silently. The DDB table for affiliates uses `pk` + `sk` as the composite key, so the condition is semantically correct.

### 4.2 Trial claim record

Before setting `status = "trialing"` in `subscribe` (`subscription_server.py:856`):

1. Write a `TRIAL_CLAIMED` record atomically:
```python
trial_claim_pk = pk_subscriber(subscriber_id)
trial_claim_sk = f"TRIAL_CLAIMED#{plan_id}"
try:
    ddb_put_item(
        pk=trial_claim_pk, sk=trial_claim_sk,
        item={"claimed_at": ts, "subscription_id": subscription_id},
        condition="attribute_not_exists(sk)",
    )
except ClientError as e:
    if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
        raise HTTPException(400, "Trial already claimed for this plan")
    raise
```

2. This record persists even after cancellation. A second subscription to the same plan by the same subscriber hits the `ConditionalCheckFailedException` and receives a 400.

3. DDB schema: the `TRIAL_CLAIMED#` row is stored in the same subscriptions table under `pk_subscriber(subscriber_id)` — no new table needed.

### 4.3 Promo per-user atomic enforcement

In `redeem_promo_code`, after the global `current_uses` atomic increment, add a per-user conditional put:

```python
max_per = int(promo.get("max_uses_per_user") or 0)
if max_per > 0:
    # Write a unique per-user sentinel; fail if already exists
    sentinel_sk = f"REDEEM_CLAIM#{user_id}"
    try:
        _tbl().put_item(
            Item={"pk": _promo_pk(code_id), "sk": sentinel_sk,
                  "user_id": user_id, "first_redeemed_at": now_ts()},
            ConditionExpression="attribute_not_exists(sk)",
        )
    except ClientError as e:
        if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
            # Rollback: decrement global count
            _tbl().update_item(
                Key={"pk": _promo_pk(code_id), "sk": "META"},
                UpdateExpression="SET current_uses = current_uses - :one",
                ExpressionAttributeValues={":one": 1},
            )
            return None, "You have already used this code"
        raise
```

Also add active + expiry re-check at the start of `redeem_promo_code` (mirroring `validate_promo_code`):
```python
if not promo.get("active", True) or (int(promo.get("expires_at") or 0) > 0 and int(promo.get("expires_at")) < now_ts()):
    return None, "Promo code is no longer valid"
```

**Note on rollback**: The decrement after a rejected per-user sentinel is a best-effort compensation. For strict atomicity, a DynamoDB TransactWrite could be used (`TransactWriteItems` with both the `current_uses` update and the sentinel put as a transaction). This is the preferred long-term fix.

### 4.4 Referral attribution — `attribute_not_exists`

`referrals.py:203`: change plain `put_item` to conditional put:
```python
try:
    tbl.put_item(
        Item=item,
        ConditionExpression="attribute_not_exists(pk)",
    )
except ClientError as e:
    if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
        logger.info("Attribution for %s already exists (race)", referred_user_id)
        return None
    raise
```

### 4.5 View-once guard

`messaging.py:11344–11348`: add a `ConditionExpression` to reject the ADD if the user is already in the set:

```python
try:
    tbl_msgs.update_item(
        Key={"conversation_id": conversation_id, "message_id": message_id},
        UpdateExpression="ADD view_once_seen :uid",
        ConditionExpression="NOT contains(view_once_seen, :uid_str)",
        ExpressionAttributeValues={
            ":uid": {user_id},
            ":uid_str": user_id,   # scalar for contains()
        },
    )
except ClientError as e:
    if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
        # Already consumed — still return success (idempotent)
        pass
    else:
        raise
```

DynamoDB `contains` on a String Set checks set membership; `NOT contains` fails the condition if `user_id` is already in `view_once_seen`, preventing the duplicate fanout event.

### 4.6 Dev/prod parity (SECOPS-007)

All changes are pure DDB conditional write operations. DynamoDB Local supports `ConditionExpression`, `TransactWriteItems`, and String Set `contains` identically to production. No new AWS services or feature flags are required. Tests run fully offline.

### Observability

- Counter `trial_replay_blocked_total` when second trial claim is rejected.
- Audit event `promo_redeem_race_blocked` when per-user sentinel rejects a concurrent redeem.

### Rollback plan

All changes are backward-compatible:
- The commission SK change (`COMMISSION#{transaction_id}`) is a schema change. Any existing `COMMISSION#{ts}#...` items remain queryable but will no longer be added to. Roll forward only; do not revert without also migrating existing rows if commission reporting depends on the SK format.
- Trial claim: adding a new `TRIAL_CLAIMED#` SK row to the subscriptions table is backward-compatible.
- All `ConditionExpression` additions are purely additive and idempotent.

### Effort estimate

**M** — five targeted code changes plus corresponding unit + E2E tests. The most complex part is the promo-code rollback/TransactWrite redesign. Estimated 1.5–2 days.
