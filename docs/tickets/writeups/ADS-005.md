# ADS-005: Newsfeed Sponsored Posts — Investigation & Implementation Write-up

## 1. Summary & Classification

ADS-005 injects native advertising into the newsfeed. Sponsored posts are interleaved with organic posts at a configurable interval (default: every 5 organic posts), rendered with a "Sponsored" badge and CTA button. Users can hide individual ads, view a "Why this ad?" explanation, and report ads. Creators control whether ads appear adjacent to their posts via a per-post `allow_ads_near` field. The injection is gated by `SPONSORED_POSTS_ENABLED` feature flag and gracefully degrades (organic feed only) if the ad engine is unavailable.

- **Type**: feature (newsfeed integration)
- **Priority**: Medium — depends on ADS-004 serving engine
- **Status**: Implemented — `_inject_sponsored_posts` is in `app/routers/newsfeed.py`, `app/services/ad_feedback.py` exists, frontend components `SponsoredPostCard.tsx` and `WhyThisAdDialog.tsx` are present
- **Owning area**: Advertising platform — newsfeed integration
- **Affected personas**: viewers (see sponsored posts), advertisers (native_post creatives served), creators (ad-near control)
- **Cross-references**: ADS-002 (native_post creative format), ADS-004 (serve_ad engine), ADS-007 (impression billing), ADS-008 (sponsored post analytics), ADS-009 (user ad preferences)
- **Dev/prod parity**: [[SECOPS-007]] — `SPONSORED_POSTS_ENABLED` flag; `serve_ad()` uses DDB Local in dev; no external network calls during injection

### 2.1 Feed injection — `app/routers/newsfeed.py`

`_inject_sponsored_posts(posts, viewer_id, interval, max_sponsored)` is implemented at lines 76–112. Key details verified:

- **Feature flag gate** at line 85: `if not getattr(S, "sponsored_posts_enabled", False): return posts`. The setting `S.sponsored_posts_enabled` is defined at `app/core/settings.py:1072` as `bool = os.environ.get("SPONSORED_POSTS_ENABLED", "true").lower() in ("1", "true", ...)` — defaults to `true` in dev (`.env.local.example` likely sets it). The `getattr(..., False)` fallback in the router is defensive but redundant given the settings default.
- **Interval and max from settings** at lines 88–89: `_interval = interval or int(getattr(S, "sponsored_post_interval", 5))` and `_max = max_sponsored or int(getattr(S, "sponsored_post_max_per_page", 3))`.
- **`allow_ads_near` check** at line 103: `if not post.get("allow_ads_near", True)` — skips injection adjacent to posts that opt out.
- **`_fetch_sponsored_post(viewer_id, position, hidden_ids)`** at lines 117–: calls `serve_ad(surface="newsfeed", content_type="post", creator_id="platform", content_id=f"feed_slot_{position}", slot_type="sponsored_post", user_id=viewer_id)`. The `creator_id="platform"` is a platform-level sentinel — this means `get_creator_ad_settings("platform")` will return defaults (allow_ads=True) from `creator_ad_prefs`. The function also accepts `hidden_ids` to filter out already-hidden creatives before injection.
- **Injection result shape** at lines 145+: constructs a post-shaped dict with `is_sponsored=True`, `impression_url`, `click_url`, `creative_id`, `campaign_id`, etc. Compatible with `FeedPost` TypeScript type.

`_inject_sponsored_posts` is called from the `GET /feed` endpoint handler after fetching organic posts.

### 2.2 Ad feedback service — `app/services/ad_feedback.py`

Fully implemented:
- **`record_ad_feedback(user_id, creative_id, campaign_id, feedback_type, reason)`**: validates `feedback_type` against `{"hide", "not_relevant", "repetitive", "offensive"}`, raises `ValueError` on invalid. Stores to `T.billing` with PK `USER#{user_id}`, SK `AD_FEEDBACK#{creative_id}#{ts}`.

## 3. Gap / Threat Analysis

### 3.1 Implementation gaps

1. **`hidden_ids` call on every feed request** — `get_hidden_ad_ids(viewer_id)` is called inside `_inject_sponsored_posts` (or passed in from the feed handler). If called per feed request, this is one DDB query per viewer per page load. The billing table query scans all `AD_FEEDBACK#*` SK entries for the user (could be hundreds over time). A 90-day TTL on feedback records (mentioned in the ticket spec) is not currently implemented — feedback records accumulate forever.

2. **`_inject_sponsored_posts` is synchronous in an async endpoint** — `_fetch_sponsored_post` calls `serve_ad()`, which calls several DDB reads synchronously. If the `GET /feed` endpoint is `async`, the blocking DDB calls inside `_inject_sponsored_posts` block the event loop. With up to 3 injection slots, this is 3 sequential `serve_ad()` calls. Should be parallelized with `asyncio.gather`.

3. **No `comments_enabled=False` enforcement on sponsored posts** — the injection dict sets `comments_enabled=False` but the comments endpoint in `app/routers/newsfeed.py` does not check `is_sponsored` or `comments_enabled` on the post. A viewer could POST a comment to a sponsored post's `post_id` (which is `sponsored_{creative_id}_{position}`) — the comment endpoint would fail with 404 because this is a synthetic ID not in the database. This is benign but could log noisy errors.

4. **Sponsored post `post_id` is synthetic** — `sponsored_{creative_id}_{position}` is generated per-request and not stored in DDB. If a viewer reacts to a sponsored post (react endpoint called with this `post_id`), the reaction write to `T.newsfeed` would fail silently. Reactions on sponsored posts need a separate tracking path (logging to `ad_impressions` as engagement events, not writing to the post table).

5. **Max 3 sponsored posts per page with interval=5** — for a page of 10 organic posts, slots are at positions 5 and 10, yielding 2 sponsored posts (not 3). The `max_sponsored=3` limit is correct defensive programming but the injection interval means it's rarely hit. With a page of 20 organic posts and interval=5, slots are at 5, 10, 15, 20 → 4 slots → capped at 3.

6. **`allow_ads_near` not stored in the newsfeed DDB table schema** — the `CreatePostRequest` has the field and `_post_to_dict` includes it, but it must actually be written to the DDB item during post creation. If the `PutItem` call omits it (filtering out `None` values and relying on default `True`), the field will be absent from DDB — `post.get("allow_ads_near", True)` correctly defaults to `True` in that case, so the behavior is correct but the explicit field is not persisted for posts created with `allow_ads_near=False`.

### 3.2 Security considerations

- `feedback_type` validated server-side — invalid types return 400, not 500.
- "Why this ad?" returns only a vague category — never exposes targeting dimensions.
- CTA URLs from creative are rendered as external links with `target="_blank" rel="noopener noreferrer"` in `SponsoredPostCard` — no server-side redirect.
- Impression beacon uses `POST /ui/ads/track` which requires session auth and CSRF — fake impressions require a valid session.
- The `allow_ads_near` field is set by the post author on their own posts; it cannot be set by a viewer on someone else's post.

## 4. Proposed Design / Fix

### 4.1 TTL on ad feedback records

Add `expires_at` to `record_ad_feedback`:

```python
expires_at = now_ts() + (90 * 86400)  # 90 days
T.billing.put_item(Item={
    "pk": f"USER#{user_id}",
    "sk": f"AD_FEEDBACK#{creative_id}#{ts}",
    ...
    "expires_at": expires_at,
})
```

The `billing` table must have TTL configured on `expires_at` in DDB (`scripts/local-ddb-init.py`). The billing table currently lacks a TTL attribute — add `ttl_attribute="expires_at"` to its `TableDef`. This is additive and backward-compatible.

### 4.2 Parallelize injection calls

If the feed handler is async, use `asyncio.gather`:

```python
import asyncio
async def _inject_sponsored_posts_async(posts, viewer_id, ...):
    hidden_ids = get_hidden_ad_ids(viewer_id)
    slots = [(i, post) for i, post in enumerate(posts)
             if (i + 1) % _interval == 0 and post.get("allow_ads_near", True)][:_max]
    sponsored_results = await asyncio.gather(*[
        asyncio.to_thread(_fetch_sponsored_post, viewer_id, pos, hidden_ids)
        for pos, _ in slots
    ])
    # interleave results into posts list
```

Since `ad_serving.serve_ad` is synchronous (DDB calls via boto3), `asyncio.to_thread` dispatches to a thread pool to avoid event loop blocking.

### 4.3 Reactions on sponsored posts

In the reactions endpoint (`POST /posts/{post_id}/reactions`), check if `post_id` starts with `"sponsored_"` and route to an ad engagement tracker instead of the newsfeed table:

```python
if post_id.startswith("sponsored_"):
    # Extract creative_id, log as engagement event to ad_impressions
    log_ad_engagement(post_id, user_sub, "reaction", emoji)
    return {"ok": True}
```

This prevents silent DDB errors for synthetic post IDs.

### 4.4 Dev/prod parity (SECOPS-007)

Current implementation is SECOPS-007 compliant:
- `SPONSORED_POSTS_ENABLED` flag selects injection on/off — same code path in both environments
- All DDB calls route through `T.*` handles
- Graceful degradation means a DDB outage in prod returns organic feed (not error) — same behavior in dev with DDB Local down
- No mock needed for sponsored posts specifically; the `serve_ad()` mock is handled by ADS-004's dev setup (DDB Local has seeded active campaigns in E2E)

For E2E testing, `SPONSORED_POSTS_ENABLED=true` in `.env.local` and pre-seeded active campaigns (from ADS-001/002/003/004 E2E setup) provide the preconditions for sponsored post injection tests.

### 5.5 Rollout

- Feature flag: `SPONSORED_POSTS_ENABLED` (env var, default `true` in `.env.local.example`)
- Phase 1: backend only — injection code deployed, flag off, no sponsored posts in feed
- Phase 2: limited rollout — flag on for 10% of users; monitor hide rates and feed latency
- Phase 3: GA — full rollout, `SponsoredPostCard` + `WhyThisAdDialog` deployed
- Rollback: `SPONSORED_POSTS_ENABLED=false` — immediate, feed returns organic-only

**Effort estimate**: S (implemented; TTL on feedback and async parallelization are 2–4 hour improvements)

**Risk**: The `ad_feedback` records in the `billing` table accumulate without TTL. At 10M users with 20 hides each over a year, this is 200M billing-table items. Add TTL urgently before launch.
