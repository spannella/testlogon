# VOD-001: Video Metadata Model and DynamoDB Table — Investigation & Implementation Write-up

> Status: **Implemented**. All described components exist in the codebase. This write-up documents what was built, validates parity with design intent, and records gaps worth noting for later tickets.

## 1. Summary & Classification

VOD-001 establishes the foundational data model for video-on-demand assets: a dedicated `VideoMetadata` DynamoDB table, the `VideoMetadataModel` Pydantic model, a state-machine module for lifecycle transitions, and a CRUD store layer. Before this ticket, video files landed in the file manager as opaque blobs with no queryable record of encoding status, technical properties, playback URLs, or content-moderation state. The ticket introduced the persistent join-point between raw S3 objects, the transcoding pipeline (VOD-003), and the viewer-facing playback API (VOD-006).

- **Type**: Feature (foundational data model)
- **Priority**: P0 — all other VOD tickets depend on it
- **Status**: Fully implemented
- **Owning area**: Backend / data layer
- **User persona**: Creator (manages videos), Admin (moderation), System (transcode worker)
- **Dependencies forward**: VOD-002 (upload endpoint writes tickets to this table), VOD-003 (worker transitions status), VOD-005 (worker updates manifest URLs), VOD-006 (listing API reads this table), VOD-010 (DRM fields), VOD-012 (download fields), VOD-015/016 (clip/concat provenance), VOD-017 (gallery fields), VOD-018/019 (ad/purchase tiers)
- **SECOPS-007 parity**: S3 mock (moto in-process via `app/core/dev_s3.py`) replaces real S3 in dev; DynamoDB Local on port 8001 replaces AWS DynamoDB; same code path in both environments

## 2. Current-State Investigation (what exists today)

### 2.1 Pydantic Model — `app/models_video.py`

The file exists and is complete. Key types:

```
VideoStatus  — 12-value Literal (created → probing → pending_encoding → encoding → pending_review → approved → published + failure/archive/delete branches)
VideoSourceType — upload | broadcast_archive | api
VideoVisibility — private | unlisted | public
VideoReviewStatus — pending_review | approved | rejected
```

`VideoMetadataModel` (line 36) carries all fields described in the ticket design: source provenance, technical properties, encoding tracking, output URLs, review, DRM, pricing, download, watermark, clipping, gallery, ad, subtitle tracks. The model has grown considerably beyond the ticket spec to accommodate later VOD tickets (VOD-012 through VOD-021) whose fields were folded in-place rather than kept separate.

Notable divergence from the ticket spec: the original design showed a separate `VideoOut` response model in `models_video.py`. The live codebase uses `VideoDetailOut` defined directly in `app/routers/video_listing.py` (line 67), which is more practical but means the response shape is defined inside a router rather than the models file.

The `@model_validator(mode="before")` described in the design for Decimal coercion is **not present** in the live `VideoMetadataModel`. Instead, Decimal coercion happens in `video_from_item()` in `app/services/video_metadata_store.py` via explicit `int(val)` / `float(val)` helper functions (`_int_or_none`, `_float_or_none`). This is functionally equivalent and arguably cleaner.

### 2.5 State Machine — `app/services/video_state_machine.py`

The file is 40 lines. `validate_transition(from_status, to_status)` (line 32) does a single dict lookup against `_ALLOWED_TRANSITIONS` (line 10) and returns a frozen `TransitionValidationResult(legal, error_code)` dataclass. Implementation matches the ticket design exactly.

One gap: `app/routers/transcode_jobs.py:103` calls `transition_video_status(video_id=body.video_id, to_status="queued")` when a transcode job is submitted. The string `"queued"` is **not in `VideoStatus`** (the Literal only covers the 12 statuses listed in `models_video.py:7`). This call will either silently succeed (DynamoDB does not enforce the Literal) or fail at the `validate_transition` check since the `_ALLOWED_TRANSITIONS` dict has no `"queued"` entry — meaning the `except Exception: logger.warning(...)` at `transcode_jobs.py:104` will swallow the 409 every time a job is submitted. The intent was likely `"pending_encoding"`.

## 3. Gap / Threat Analysis

### 3.1 The "queued" Status Bug

`app/routers/transcode_jobs.py:103` attempts `transition_video_status(..., to_status="queued")`. The string `"queued"` is not a valid `VideoStatus` and is not in `_ALLOWED_TRANSITIONS`. The state machine returns `legal=False` with error code `VIDEO_INVALID_STATE_TRANSITION`, `transition_video_status` raises HTTP 409, and the `except Exception` block on line 104 silently suppresses it. The video's status is never updated to reflect that a transcode job was submitted — it stays in `"created"`. This means `list_videos_by_status("pending_encoding")` will never find videos waiting to be transcoded via the job submission path.

**Fix**: Change `to_status="queued"` to `to_status="pending_encoding"` at `transcode_jobs.py:103`. The corresponding check in `_ALLOWED_TRANSITIONS` permits `created → pending_encoding`.

### 3.2 `TICKET#` Prefix Pollution in VideoMetadata Table

`app/routers/vod.py:189` stores upload tickets directly in the `VideoMetadata` table with `video_id = f"TICKET#{ticket_id}"`. These ticket items share the `ByOwnerCreatedAt` GSI (indexed on `owner_user_id`). The listing functions guard against this with `if isinstance(vid, str) and vid.startswith("TICKET#"): continue` (store line 452) and `Attr("video_id").begins_with("v_")` filters (store line 511). However, since `FilterExpression` runs after the 1MB page fetch, large accumulations of ticket records could inflate DynamoDB read costs and slow listing queries. The cleaner design is to store tickets in a separate table or use a different PK prefix scheme that prevents them from appearing in the GSI.

### 3.3 `UpdateVideoIn` vs `VideoUpdateIn`

`app/models_video.py:183` defines `UpdateVideoIn`. `app/routers/video_listing.py:37` imports `UpdateVideoIn` from `models_video`. However `models_video.py:169` also defines `CreateVideoIn` and line 183 defines `UpdateVideoIn`. Separately, `app/models_video.py` also contains `VideoUpdateIn` at line 137. The two update models (`UpdateVideoIn` at line 183, `VideoUpdateIn` at line 137) have different fields — `VideoUpdateIn` includes `allow_download` and `scheduled_publish_at` while `UpdateVideoIn` includes `encoding_profile_id`, `drm_policy_id`, `entitlement_sku`. This split is intentional (system-facing vs user-facing updates) but the naming is confusing and could lead to importing the wrong one.

### 3.4 Model Growing Too Large

`VideoMetadataModel` now has 50+ fields accumulated from VOD-001 through VOD-021. The `video_to_item` function is 174 lines. This is not a defect, but the accumulation pattern means any future ticket must carefully audit all fields to avoid N+1 DynamoDB writes when only one field changes. The `update_item` pattern (used for `increment_download_count` and `update_clip_fields`) is the correct approach for targeted updates; the fetch-merge-put pattern in `update_video` is only safe under low concurrency.

## 4. Proposed Design / Fix

### 4.1 Fix the "queued" Status Bug

In `app/routers/transcode_jobs.py`, line 103:

```python
# Before:
transition_video_status(video_id=body.video_id, to_status="queued")
# After:
transition_video_status(video_id=body.video_id, to_status="pending_encoding")
```

This is the only code change required; no model or schema changes needed.

### 4.2 Ticket Storage Isolation (future improvement)

For a future hardening pass, move upload tickets to a dedicated `VideoUploadTickets` table. This eliminates GSI pollution, removes the `begins_with("v_")` filter workaround, and allows setting a TTL on tickets without risk of expiring video records.

### 4.3 Dev/Prod Parity (SECOPS-007)

The current implementation already satisfies SECOPS-007. The `S.dev_mode` flag gates the three dev-specific behaviors:
1. moto in-process S3 (started in `app/core/dev_s3.py`, invoked from `main.py`)
2. `/mock/s3/` presigned URL replacement (vod.py:167–168)
3. `http://localhost:8000/mock/s3/` playback URL (vod_playback_url.py:118–135)

No code duplication exists — the same store and state machine code paths run in both environments.
