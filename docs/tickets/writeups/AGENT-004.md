# AGENT-004: Worker Fleet Management UI — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

AGENT-004 provides the fleet-level management layer that sits on top of AGENT-001 through AGENT-003. It adds bulk start/stop operations, per-user aggregate metrics (worker counts, queue depth, throughput), worker configuration templates, an SSE event stream for real-time dashboard updates, and a capacity planning view that compares ticket queue depth against available workers by type. The frontend `FleetDashboard.tsx` is the primary UI entry point for the entire agent orchestration platform.

- **Type**: Feature (management layer / dashboard)
- **Priority**: Medium — enhances usability of AGENT-001 through AGENT-003
- **Status**: Implemented
- **Owning area**: AI Agents / Platform UI
- **User persona**: Developer managing multiple concurrent agent workers; platform admin auditing fleet usage
- **Cross-references**: [[AGENT-001]] (LLM key refs in templates), [[AGENT-002]] (worker CRUD), [[AGENT-003]] (agent state), [[AGENT-005]] (memory tab in WorkerDetailDrawer), [[AGENT-006]] (terminal streaming in drawer), [[SECOPS-007]] (SSE in dev must not leak real AWS events)

## 2. Current-State Investigation (what exists today)

### 2.1 Fleet service

`app/services/agent_fleet.py` (321 lines) is fully present.

**`fleet_status`** (line 32): calls `list_workers(user_id)` from the provisioner, counts workers by status, calls `_count_eligible_tickets` to get queue depth, and returns a `FleetStatusOut`-shaped dict with `total_workers`, `status_counts`, `queue_depth`, and a list of worker summaries.

**`fleet_capacity`** (line 62): returns `queue_by_type` (ticket counts per type filtered by `agent_eligible="yes"`), `workers_by_type` (workers by `agent_type`), `workers_by_state` (workers by `agent_state`), and a `recommended_action` string generated by comparing queue and worker counts.

**`bulk_start`** (line 98): iterates `list_workers(user_id, status="stopped")` and calls `start_worker` for each. Collects errors per worker; returns `{"started": count, "errors": [...]}`. Operations are sequential (not concurrent) — this avoids DDB write throttling but caps throughput at ~10 workers/second.

**`bulk_stop`** (line 116): same pattern over `status="ready"` workers.

**`save_template`** (line 140): stores a worker configuration snapshot as `TEMPLATE#{template_id}` SK in the `agent_workers` table. The template stores `llm_key_id` by reference — not the actual key material. At line 152-157, the item is validated before storage (label, agent_type, tool, etc.). Templates share the table with worker records, distinguished by SK prefix.

**`list_templates`** / `get_template` / `delete_template` / `create_worker_from_template`** (lines 181-241): standard CRUD plus a convenience function that calls `create_worker` with the template's config.

**`_count_eligible_tickets`** (line 288): queries the tickets table for eligible unclaimed tickets. Uses a scan with `FilterExpression` — this will not paginate correctly if the filtered result set is sparse (known DDB issue from CLAUDE.md). A full fix requires a loop over `LastEvaluatedKey`.

### 2.2 Router (AGENT-004)

`app/routers/agent_fleet.py` is imported and registered in `app/main.py:751`. The router provides endpoints at `/ui/agent/fleet/status`, `start-all`, `stop-all`, `events` (SSE), `capacity`, `templates` (CRUD), and `/ui/admin/agent/fleet`. Admin endpoint uses `require_admin_scope` (correct pattern from `app/auth/policy.py:84`).

### 2.3 SSE event stream

The fleet events SSE endpoint delivers `worker:state_change`, `worker:ticket_claimed`, `worker:ticket_completed`, `worker:heartbeat_missed`, `worker:error`, and `fleet:capacity_change` events. Events are pushed via an in-process `asyncio.Queue` per user stored in `_fleet_event_buses[user_id]`. Worker state changes in `transition_agent_state` (AGENT-003) are expected to call `emit_fleet_event(user_id, ...)` to push events; this hook is described in the design but the actual call site in `agent_orchestrator.py` should be verified for completeness.

**Memory-per-connection**: each SSE client holds one `asyncio.Queue`. At 1000 concurrent connections, this is ~4MB of queue overhead — acceptable. If the SSE endpoint is disabled (`AGENT_FLEET_SSE_ENABLED=false`), the frontend falls back to 5-second polling.

### 2.4 Data model

`app/models.py` contains `FleetStatusOut` (line area ~6140), `WorkerSummary`, `BulkActionOut`, `CapacityOut`, `WorkerTemplateIn` (with `@field_validator` for `agent_type`, `compute_type`, `tool`, `repo_url`, `branch_convention`), and `WorkerTemplateOut`. `WorkerTemplateIn.validate_repo_url` ensures `https://` or `git@` — this is the same SSRF guard needed in AGENT-002's provisioner.

### 2.6 DynamoDB access patterns

Templates use the same `agent_workers` table with `TEMPLATE#` SK prefix. The `list_templates` query (line 181) uses `begins_with(sk, "TEMPLATE#")` — efficient range query within the user's partition. No new GSIs are needed because templates are always queried by owner.

The fleet capacity calculation calls `_count_eligible_tickets` which queries the tickets table. If the tickets table has many items, this scan is slow. A purpose-built GSI on `(agent_eligible, status)` would make this sub-10ms.

## 3. Gap / Threat Analysis

### 3.1 User isolation in fleet status

`fleet_status(user_id)` calls `list_workers(user_id)` which queries `PK=USER#{user_id}` — correctly scoped to the authenticated user. The admin fleet endpoint scans across users. The key authorization invariant to verify is that the `user_id` passed to `fleet_status` comes from the session cookie (not a query parameter), which is enforced by `require_ui_session` in the router. Confirmed correct in the router pattern.

### 3.2 Template references stale LLM key

If a user deletes an LLM key that is referenced in a template, `create_worker_from_template` will call `create_worker` with the deleted `llm_key_id`. The provisioner's `get_key(user_id, llm_key_id)` will return `None`, causing a 400 error. This is the correct behavior — the worker is not silently created with a missing credential. However, the template should surface a `status: "stale_key"` flag in the list response so users can fix it proactively.

### 3.3 Bulk action max-worker safeguard missing

The ticket design mentions a maximum of 50 workers per bulk operation, but this is not enforced in the current `bulk_start`/`bulk_stop` implementation. A user with many workers could trigger a long-running bulk stop that holds the event loop for seconds. Fix: add `workers = workers[:50]` and return an error if more workers would be affected.

### 3.4 Sparse eligible-ticket count (DDB FilterExpression)

`_count_eligible_tickets` uses `FilterExpression` on a scan/query. Per CLAUDE.md, DDB fetches up to 1MB before applying `FilterExpression`, so a busy tickets table may require multiple `LastEvaluatedKey` loops to count all eligible tickets. The current implementation likely does a single query and returns a low/incorrect count. Fix: add a pagination loop or use a dedicated counter item that is atomically updated when tickets become eligible/ineligible.

### 3.5 SSE event hook may be missing

The SSE bus architecture requires that `transition_agent_state` (AGENT-003) and `claim_ticket` push events to `_fleet_event_buses[user_id]`. If these hooks are not wired, the SSE stream is silent — the frontend receives no events and falls back to polling. Verify in `agent_orchestrator.py` that `emit_fleet_event` is called at each meaningful state transition.

### 3.6 Template `branch_convention` regex validation

`WorkerTemplateIn.validate_branch_convention` (from the models) checks `^[a-zA-Z0-9_/{}\-]+$`. This rejects dot (`.`) which is valid in branch names (e.g., `hotfix/v1.2.3`). Expand the allowlist to include `.` and `#`.

## 4. Proposed Design / Fix

### 4.1 Template stale-key indicator

In `list_templates`, add a pass that cross-references each template's `llm_key_id` against the user's key list:

```python
key_ids = {k["key_id"] for k in list_keys(user_id)}
for t in templates:
    t["key_valid"] = t.get("llm_key_id", "") in key_ids
```

Frontend displays a warning badge on stale templates.

### 4.2 Bulk action size cap and rate limit

```python
MAX_BULK_WORKERS = 50
BULK_RATE_LIMIT_SECONDS = 30  # enforced via DDB TTL item

def bulk_start(user_id: str) -> Dict[str, Any]:
    workers = list_workers(user_id, status="stopped")
    if len(workers) > MAX_BULK_WORKERS:
        raise ValueError(f"Bulk operations limited to {MAX_BULK_WORKERS} workers")
    ...
```

Rate limit via a `BULK#{user_id}` record in DDB with TTL, or via the existing rate-limiting middleware.

### 4.3 Eligible ticket count pagination

```python
def _count_eligible_tickets(user_id: str) -> int:
    count = 0
    last_key = None
    while True:
        kwargs = {
            "FilterExpression": "agent_eligible = :yes AND agent_worker_id = :empty",
            "ExpressionAttributeValues": {":yes": "yes", ":empty": ""},
            "Select": "COUNT",
        }
        if last_key:
            kwargs["ExclusiveStartKey"] = last_key
        resp = T.tickets.scan(**kwargs)
        count += resp.get("Count", 0)
        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break
    return count
```

### 4.4 SSE emit hook wiring

In `agent_orchestrator.py`, after each call to `transition_agent_state`, add:

```python
from app.services.agent_fleet import emit_fleet_event
emit_fleet_event(user_id, {
    "type": "worker:state_change",
    "data": {"worker_id": worker_id, "old_state": current, "new_state": new_state},
})
```

This is a fire-and-forget dict push to an in-memory asyncio.Queue — no DDB write, minimal latency.

### 4.5 Dev/Prod parity (SECOPS-007)

No AWS-specific calls in the fleet service. SSE is in-memory. DDB operations go through `T.agent_workers` and `T.tickets` which hit DDB Local in dev, AWS DynamoDB in prod. No additional dev/prod branching needed.
