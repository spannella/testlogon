# KYC-008: KYC Risk Scoring Engine — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

KYC-008 replaces the static `intake_profile`-based risk classification with a computed 0–100 risk score built from eight weighted evidence factors. The engine is implemented in `app/services/kyc_risk_scoring.py`, stores results in a dedicated `kyc_risk_scores` DynamoDB table, and triggers auto-approval for low-risk cases and auto-escalation for critical-risk ones. The score feeds the KYC-009 tier system and KYC-012 compliance reporting.

- **Type**: Feature — AML risk-based approach (RBA) compliance
- **Priority**: High — regulators require systematic, evidence-based risk assessment
- **Status**: Implemented. `app/services/kyc_risk_scoring.py` exists (598 lines). Router endpoints are served via `app/routers/risk_scoring.py` (separate file, not a subdirectory of `kyc_cases`). Registered at `app/main.py:568-569`.
- **Owning area**: KYC / Risk management
- **User persona**: KYC reviewers seeing score context; compliance leads monitoring risk distribution; platform auto-approving low-risk cases; developers tuning factor weights
- **Cross-references**: KYC-006 (screening results feed `screening_result` factor), KYC-002 (document quality factor), KYC-004 (address match factor), KYC-005 (source of funds factor), KYC-009 (score triggers tier evaluation), KYC-012 (reports consume score history)
- **SECOPS-007 parity**: All eight factors read from DDB tables; no external HTTP in dev or prod. Factor weights are in-memory constants. DDB Local in dev, AWS DynamoDB in prod.

## 2. Current-State Investigation (what exists today)

### 2.1 Pre-existing static risk classification

Before KYC-008, `app/services/kyc_cases.py:664` contains:

```python
def _risk(case: dict) -> str:
    ip = str(case.get("intake_profile") or "standard").lower()
    if ip == "high_risk": return "high"
    if ip == "enhanced": return "medium"
    return "low"
```

This is a user-supplied static label, not a computed score. The `list_admin_queue()` function at line 646 uses this `_risk()` for the `risk_tier` filter in the admin queue. KYC-008 replaces this static mapping with a real computed tier stored on `kyc_risk_scores`.

### 2.2 Implemented scoring service

`app/services/kyc_risk_scoring.py` (598 lines) is fully implemented:

**Factor weights** (lines 58–67) — eight factors summing to 1.0:
- `country_risk` (0.15), `document_quality` (0.15), `screening_result` (0.25)
- `source_of_funds` (0.15), `verification_call` (0.10), `profile_completeness` (0.05)
- `account_age` (0.05), `address_match` (0.10)

**`KycRiskScoringService.compute_score()`** (lines 102–171) gathers all eight factors, computes `sum(score * weight)` rounded to integer, determines the tier, applies auto-action, and writes the result to `kyc_risk_scores` with a strictly-increasing microsecond sort key (lines 27–39) to prevent collision when multiple scores are written in the same wall-clock second.

**Factor implementations** (lines 332–485): Each `_compute_{factor_name}()` method reads from DDB tables defensively — any exception returns a safe default score rather than crashing. Key integrations:

- `_compute_screening_result()` reads `case["screening"]["status"]` from the case META item — this is the field written by `_write_case_screening_summary()` in `app/services/kyc_sanctions_screening.py:563`
- `_compute_source_of_funds()` falls back to `_proof_of_funds_factor()` (lines 492–521) which lazy-imports `app/services/kyc_proof_of_funds.summarize_proof_of_funds()` for KYC-005 integration
- `_compute_country_risk()` uses two hard-coded sets: `_LOW_RISK_COUNTRIES` (22 countries, lines 73–77) and `_HIGH_RISK_COUNTRIES` (11 countries, lines 79–82)

**Auto-action** (`_apply_auto_action()`, lines 528–573): 
- `tier == "low"` + `all_checks_passed` (all factor scores = 0) + `score <= S.kyc_risk_auto_approve_max_score` → calls `STORE.apply_admin_decision()` from `kyc_cases.py` with `actor_sub="system_auto_approve"`
- `tier == "critical"` + `score >= S.kyc_risk_auto_escalate_min_score` → logs warning and returns `"auto_escalated"` (no DDB mutation beyond logging currently — escalation DDB flag is noted but not yet written to case)

**Sort key uniqueness**: The `_unique_sort_key()` function (lines 31–39) uses `time.time_ns() // 1000` (microseconds) with a thread lock and monotone increment. This is critical because the table PK is `user_sub`, SK is `timestamp` (N); duplicate timestamps within a test run would silently overwrite previous scores.

### 2.3 Router

`app/routers/risk_scoring.py` (separate file, registered at `app/main.py:568-569` as `risk_scoring_user_router` and `risk_scoring_admin_router`). Not `kyc_cases.py` as originally designed — the implementation used a dedicated file. This is architecturally cleaner.

### 2.4 DynamoDB table

`kyc_risk_scores` with:
- PK: `user_sub` (S), SK: `timestamp` (N)
- GSI `case-timestamp-index`: PK=`case_id`, SK=`timestamp` — for `get_scores_for_case()`
- GSI `tier-timestamp-index`: PK=`risk_tier`, SK=`timestamp` — for tier distribution and tier listing

Settings in `app/core/settings.py` (lines 1196–1200): `kyc_risk_scores_table_name`, `kyc_risk_auto_approve_enabled` (default `true`), `kyc_risk_auto_approve_max_score` (default 20), `kyc_risk_auto_escalate_min_score` (default 81), `kyc_risk_scoring_model_version` (default `"v1.0"`).

### 2.5 Tier distribution implementation note

`get_tier_distribution()` (lines 201–241) performs a full table scan to count `auto_approved` and `auto_escalated` actions. In dev mode with small tables this is acceptable; in production with millions of rows this is expensive. A future optimization would be to use a separate counter table or DDB conditional aggregation.

## 3. Gap / Threat Analysis

### 3.1 Regulatory requirement

The Financial Action Task Force (FATF) requires a risk-based approach (RBA) for AML compliance. Static risk tiers set at case creation do not qualify as RBA because they reflect self-reported information rather than evidence gathered during verification. A computed score based on document quality, screening results, and other signals satisfies the RBA requirement.

### 3.2 Auto-approve conditions

The auto-approve guard (`_apply_auto_action()`) requires `all_checks_passed` — meaning every factor score is exactly 0. This is very restrictive: a new account (< 7 days old) scores 100 on `account_age`, which means no new-account case can ever be auto-approved regardless of other factors being clear. This is intentionally conservative for the initial deployment.

The `S.kyc_risk_auto_approve_enabled` flag (default `true`) allows disabling auto-approval without code changes. The max score threshold (`KYC_RISK_AUTO_APPROVE_MAX_SCORE`, default 20) can be tuned via env var.

### 3.3 Auto-escalate gap

Currently `_apply_auto_action()` returns `"auto_escalated"` and logs a warning but does **not** write an escalation flag to the case META item. The ticket spec shows writing `review["escalated"] = True` and `review["escalation_reason"]` to the case — this DDB update is missing from the current implementation. An admin reviewer would see `auto_action_taken="auto_escalated"` in the score record but the case itself shows no escalation indicator in the admin queue.

### 3.4 Factor integration gaps

- **`document_quality`**: Currently reads `files[].verification_state` from the case META. KYC-002 writes extraction confidence to `kyc_document_extractions` table; this factor should also query that table for confidence scores. The current fallback to `verification_state` is reasonable but imprecise.
- **`screening_result`**: Reads from `case["screening"]["status"]`. This depends on `_write_case_screening_summary()` in KYC-006 having fired. If KYC-006 is not yet integrated, this factor returns 40 (`"not_conducted"`).
- **`source_of_funds`**: Falls back to `kyc_proof_of_funds.summarize_proof_of_funds()` if no embedded SOF data on case. This works for standalone KYC-005 submissions but requires KYC-005 to be implemented.

### 3.5 Score collision protection

The microsecond sort key in `_unique_sort_key()` is process-local (thread lock within one uvicorn worker). With `--workers 1` (required in dev per CLAUDE.md), this is safe. In production with multiple workers, simultaneous scores for the same user from different workers could still collide if they happen in the same microsecond. A more robust solution would use a composite SK like `{timestamp}#{score_id}` or a separate auto-increment counter.

## 4. Proposed Design / Fix

### 4.1 Fix auto-escalate case update

In `_apply_auto_action()` at the auto-escalate branch, add the DDB write that the spec calls for:

```python
if tier == "critical" and score >= S.kyc_risk_auto_escalate_min_score:
    try:
        case_resp = T.kyc_cases.get_item(Key={"pk": f"KYC#{case_id}", "sk": "META"})
        case = case_resp.get("Item", {})
        if case:
            T.kyc_cases.update_item(
                Key={"pk": f"KYC#{case_id}", "sk": "META"},
                UpdateExpression=(
                    "SET #r.escalated = :t, #r.escalation_reason = :reason, "
                    "#r.escalated_at = :ts"
                ),
                ExpressionAttributeNames={"#r": "review"},
                ExpressionAttributeValues={
                    ":t": True,
                    ":reason": f"Critical risk score: {score}",
                    ":ts": now_ts(),
                },
            )
    except Exception:
        logger.exception("Auto-escalate case update failed for case %s", case_id)
    return "auto_escalated"
```

### 4.2 Submission integration

In `submit_kyc_case()` at `app/routers/kyc_cases.py:830`, after KYC-006 screening completes:

```python
if S.kyc_risk_scoring_enabled:
    from app.services.kyc_risk_scoring import KycRiskScoringService
    try:
        KycRiskScoringService().compute_score(
            case_id=case_id,
            user_sub=case["user_sub"],
            trigger="submission",
        )
    except Exception:
        logger.exception("Risk scoring failed for case %s — continuing submission", case_id)
```

Wrapping in try/except ensures scoring failure does not block the submission.

### 4.3 Sort key improvement for production

Change the score record SK from `timestamp` to a composite `{timestamp_us}#{score_id}` to guarantee uniqueness across workers:

```python
# Instead of self._table.put_item(Item=item) with timestamp as SK,
# use: sort_key = f"{time.time_ns() // 1000}#{score_id}"
# Store as a String SK to support the composite format.
```

However, this is a breaking schema change. For now, the `_unique_sort_key()` approach is adequate with `--workers 1`.

### 4.4 Dev/prod parity (SECOPS-007)

| Aspect | Dev | Prod |
|--------|-----|------|
| Factor data sources | DDB Local tables | AWS DynamoDB |
| Country risk lists | In-process Python sets | Same sets (hardcoded) |
| KYC-006 screening status | Written by mock screening provider | Written by real provider |
| KYC-005 proof of funds | `kyc_proof_of_funds` service (implemented) | Same |
| Auto-approve | Controlled by `KYC_RISK_AUTO_APPROVE_ENABLED` (default `true` in dev) | Controlled by same env var |
| Table scan in distribution | Small table, cheap in dev | Needs optimization for prod (millions of rows) |

### 4.5 Alternatives considered

- **ML-based scoring**: Using a trained model for risk scoring is more accurate but requires labeled training data, model versioning, and an inference endpoint. Rejected for initial implementation; weighted rule-based scoring is auditable and tunable without retraining.
- **Storing scores on the case META item**: Instead of a separate table, embedding the latest score in `case["risk_score"]`. Rejected because it loses history and prevents the tier distribution queries that require the `ByTier` GSI.

### 5.3 Observability

The service emits structured logs: `kyc.risk.scored` (INFO), `kyc.risk.auto_approved` (INFO), `kyc.risk.auto_escalated` (WARN). Alert on `tier == "critical"` as P1. Add `kyc_risk_score_computed` counter metric with `tier` label to track distribution in production.

### 5.4 Rollout phases

1. Deploy with `KYC_RISK_SCORING_ENABLED=true` but `KYC_RISK_AUTO_APPROVE_ENABLED=false` — scoring runs and stores results but no auto-actions
2. After 2 weeks of data, review score distribution; verify no false auto-approvals would occur
3. Enable `KYC_RISK_AUTO_APPROVE_ENABLED=true` with conservative threshold (score <= 15)
4. Enable `KYC_RISK_AUTO_ESCALATE_ENABLED=true` after escalation DDB write is implemented
5. Tune `KYC_RISK_AUTO_APPROVE_MAX_SCORE` based on false negative rate

### 5.5 Rollback

Set `KYC_RISK_SCORING_ENABLED=false`. Submission proceeds without scoring. Existing scores remain in DDB. The `_risk()` function at `kyc_cases.py:664` continues to provide the static tier for the admin queue filter.
