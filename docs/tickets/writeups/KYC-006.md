# KYC-006: Sanctions & PEP Screening — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

KYC-006 adds automated sanctions and politically-exposed-person (PEP) screening to every KYC case submission. Without it the platform onboards users without checking them against OFAC, EU, and UN sanctions lists or PEP registers, creating serious AML regulatory exposure. The feature introduces a dedicated `kyc_screening_results` DynamoDB table, a `KycSanctionsScreeningStore` service, five admin-facing endpoints, and a hook inside `submit_kyc_case()` that fires the screening pipeline synchronously on every submission.

- **Type**: Feature / AML compliance requirement
- **Priority**: High — regulatory blocking risk; financial platforms must screen against OFAC/UN before onboarding
- **Status**: Implemented (`app/services/kyc_sanctions_screening.py` exists and is wired)
- **Owning area**: KYC / Compliance
- **User persona**: Compliance officers and KYC reviewers reviewing match queues; the platform running automated pre-approval gating; developers needing deterministic test behavior
- **Cross-references**: KYC-001 (admin dashboard integration), KYC-002 (name/DOB sourced from document extraction), KYC-008 (risk scoring consumes screening summary written by this service), KYC-012 (compliance reporting includes screening history)
- **SECOPS-007 parity**: Dev mode uses deterministic `MOCK_WATCHLIST` in-process; prod is gated behind `S.kyc_screening_real_provider_enabled` (default off); same code path throughout, provider selected by flag

## 2. Current-State Investigation (what exists today)

### 2.1 Service implementation

`app/services/kyc_sanctions_screening.py` (749 lines) is fully implemented. Key constants at lines 71–99 define the five screen types (`sanctions_ofac`, `sanctions_eu`, `sanctions_un`, `pep_check`, `adverse_media`) and the three result statuses (`clear`, `potential_match`, `confirmed_match`). The `MOCK_WATCHLIST` (lines 105–155) provides four deterministic test entries:

- `"OFAC Test Person"` → `sanctions_ofac` → `potential_match` (0.92 score)
- `"Sanctioned Person"` → all three sanctions types → `confirmed_match` (1.0 score)
- `"PEP Official"` → `pep_check` → `potential_match` (0.88 score)
- `"Media Flagged"` → `adverse_media` → `potential_match` (0.75 score)

Name matching uses normalized fuzzy comparison with diacritics stripping (`_normalize_name`, `_subject_matches_watchlist` at lines 206–249); DOB and country corroboration nudge the score up by ±0.03/0.02.

`KycSanctionsScreeningStore.screen_case()` (lines 299–358) runs all five screen types sequentially, writes each result as a separate DDB item (PK=`case_id`, SK=`{screen_type}#{iso_ts}#{screening_id}`), then calls `_write_case_screening_summary()` (lines 563–615) which updates the `screening` map on the KYC case META item — this is what `kyc_risk_scoring._compute_screening_result()` reads.

`review_match()` (lines 468–533) performs an atomic conditional update with `attribute_not_exists(reviewed_by) OR reviewed_by = :null` to prevent double-review; raises `KycScreeningAlreadyReviewedError` on `ConditionalCheckFailed` (line 521).

## 3. Gap / Threat Analysis

### 3.1 Regulatory compliance gaps (without this feature)

Without sanctions screening, the platform is exposed to OFAC enforcement actions, EU Regulation No. 2580/2001 violations, and UN Security Council resolution breaches. Platforms knowingly or unknowingly processing transactions for designated persons face civil penalties up to $1M per violation (OFAC). The existing `submit_kyc_case()` flow at `app/routers/kyc_cases.py:830` completes the case submission without any name-based watchlist check.

### 3.2 Requirements detail

**Screening completeness**: All five screen types must run on every submission. A partial screening run (e.g., only OFAC) would not satisfy AML obligations. The current implementation runs all five sequentially in `screen_case()` using a simple loop.

**Profile change re-screening**: When a user's name, DOB, or nationality changes after case approval, the AML profile changes. `_load_subject_identity()` (lines 267–295) reads from `profile` and `users` tables at screen time. The profile-change hook must be wired in the settings update flow; `rescreen_user()` (lines 535–559) delegates back to `screen_case()` with `trigger=TRIGGER_PROFILE_CHANGE`.

**Double-review race condition**: Two admins reviewing the same match simultaneously could create inconsistency. The conditional update in `review_match()` (lines 503–523) uses `ConditionExpression` to prevent this, raising `KycScreeningAlreadyReviewedError` (→ HTTP 409) on the loser.

**Match detail PII exposure**: Non-admin case owners should not see full match details (list names, entity IDs) from watchlists — commercially sensitive and potentially escalating. `public_screening_view()` (lines 708–748) handles this with `include_match=True/False`.

**Confirmed matches blocking approval**: A `confirmed_match` must prevent auto-approval and require explicit admin decision. The `_write_case_screening_summary()` writes `status="confirmed_match"` onto the case, which the risk scoring engine reads with score 100 (highest risk), which blocks auto-approval via `S.kyc_risk_auto_approve_enabled` threshold.

### 3.3 Edge cases

- **Empty name**: `_load_subject_identity()` returns `name=None` for users with no profile. The mock provider returns `clear` when `not ns` (line 231). Production providers should also handle this gracefully rather than erroring.
- **Multiple re-screens**: Each re-screen appends new SK entries (the screening_id suffix ensures uniqueness even within the same second). The `get_results_for_case()` query returns all history, not just the latest.
- **`ByStatus` GSI hot partition**: With many users, `result="potential_match"` becomes a hot partition key. The design acknowledges this; the practical admin queue is expected to stay below 100 items at any time.
- **Concurrent submission and profile update**: If a user submits a case and immediately changes their name, the screening captures the name at submission time (passed as parameter); profile-change re-screening fires separately.

## 4. Proposed Design / Fix

### 4.1 Submission hook (already designed, verify wiring)

After the case status transitions to `submitted` in `submit_kyc_case()` (`app/routers/kyc_cases.py:830`), add:

```python
from app.services.kyc_sanctions_screening import STORE as SCREENING_STORE, RESULT_CLEAR
screening_results = SCREENING_STORE.screen_case(
    case_id=case_id,
    user_sub=case["user_sub"],
    trigger="submission",
)
```

The `_write_case_screening_summary()` call is internal to `screen_case()` so it fires automatically. If the submission itself is fire-and-forget (acceptable: `kyc_screening_enabled` flag gates it), wrap in a try/except so screening failure does not block submission.

### 4.2 Profile-change re-screening

In the profile update endpoint (`app/routers/settings.py` or equivalent), after updating `display_name`, `date_of_birth`, or `nationality`:

```python
sensitive_fields = {"display_name", "date_of_birth", "nationality"}
if changed_fields & sensitive_fields:
    from app.services.kyc_sanctions_screening import STORE as SCREENING_STORE
    from app.services.kyc_cases import STORE as KYC_STORE
    # Find latest approved case for user
    cases = KYC_STORE.list_cases_by_owner(user_sub=user_sub, limit=5)
    approved = next((c for c in cases if c.get("status") == "approved"), None)
    if approved and S.kyc_screening_enabled:
        SCREENING_STORE.rescreen_user(
            case_id=approved["case_id"],
            user_sub=user_sub,
            trigger="profile_change",
        )
```

### 4.3 DDB table definition (correct attr_types)

In `scripts/local-ddb-init.py`, the `kyc_screening_results` table must be defined with:

```python
TableDef(
    _resolve_table_name(S.kyc_screening_results_table_name, "kyc_screening_results"),
    partition_key="case_id",
    sort_key="screen_key",
    gsis=[
        {"index_name": S.kyc_screening_user_index_name, "partition_key": "user_sub", "sort_key": "created_at"},
        {"index_name": S.kyc_screening_status_index_name, "partition_key": "result", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},  # CRITICAL: numeric GSI sort key
)
```

Omitting `attr_types={"created_at": "N"}` causes DynamoDB to store it as String, breaking `ScanIndexForward` queries with numeric predicates.

### 4.4 Dev/prod parity (SECOPS-007)

| Aspect | Dev | Prod |
|--------|-----|------|
| Provider | `MOCK_WATCHLIST` in-process, deterministic | Real HTTP provider (Refinitiv/Dow Jones) |
| Flag | `KYC_SCREENING_REAL_PROVIDER_ENABLED=false` | `KYC_SCREENING_REAL_PROVIDER_ENABLED=true` |
| Code path | Same `_run_provider()` dispatcher | Same `_run_provider()` dispatcher |
| DDB table | DynamoDB Local port 8001 | AWS DynamoDB |
| KMS | Not involved in screening | Not involved in screening |
| Test names | `"OFAC Test Person"`, `"PEP Official"` → predictable outcomes | Real watchlist hits |

The mock path is identical structurally: each screen type produces the same `{result, match_details}` shape. E2E tests rely on the mock names producing predictable outcomes without any mocking library.

### 4.5 Adjudication decision vocabulary

The ticket spec says `false_positive` / `true_match`. The implementation uses `clear` / `confirm` / `escalate`. The router models in `app/models.py` should use `clear`/`confirm`/`escalate` to align with the service constants at `app/services/kyc_sanctions_screening.py:89-92`. If the UI spec says "False Positive" it maps to `clear`; "True Match" maps to `confirm`.

### 4.6 Alternatives considered

- **Async fire-and-forget screening**: Running screening in a background task avoids adding latency to the submission response. Rejected for this phase because the regulatory requirement is that screening must complete before the case enters `under_review`; async introduces a window where the case could be approved before screening completes.
- **Sync external HTTP in submission path**: For real providers, a single 5-second HTTP timeout per screen type would add up to 25 seconds to submission. Solution: parallelize with `asyncio.gather()` in prod, but keep the mock sequential (already sub-200ms total).

### 5.5 Rollback

Set `KYC_SCREENING_ENABLED=false` in `.env.local` or prod config. Submission proceeds without screening. All existing screening records remain in DDB (append-only; never deleted). The admin screening endpoints return existing data but no new screenings are created. The `_write_case_screening_summary()` does not fire, so the risk scoring `screening_result` factor returns `"not_conducted"` score (40).
