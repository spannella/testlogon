# BOT-003: Content & Event Promotion Bot — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

BOT-003 enables bots to intelligently promote a creator's content (videos, posts, broadcasts, calendar time slots) to users in conversation. Creators curate a "content set" of mixed-type items; the promotion engine selects what to send based on a configurable strategy (round-robin, random, newest-first, priority), skips content already purchased by the recipient, and enforces per-conversation daily frequency caps. Bot messages use a new `content_card` message kind carrying structured metadata (thumbnail, title, price, CTA button). The system also hooks into the existing broadcast scheduling infrastructure to automatically send pre-broadcast announcements with countdowns, and into the calendar service to enable in-chat time-slot booking.

- **Type**: Feature
- **Priority**: Medium
- **Status**: Substantially not implemented at the service layer — `app/services/bot_auto_reply.py` (285 lines) exists with a simple rule-matching engine and `process_incoming_message()`, but this is a simplified alternative to BOT-003's promotion strategy engine, not an implementation of it. None of the tables (`bot_content_sets`, `bot_promotion_history`, `bot_promotion_caps`) exist. No `content_card` message kind exists. No `app/services/bot_promotion.py`, `app/services/bot_broadcast_announcer.py`, or `app/routers/bot_promotion.py`.
- **Owning area**: `app/services/bot_promotion.py` (to be created), `app/services/bot_auto_reply.py` (existing, related but distinct), `app/routers/messaging.py:2330` (kind Literal), `frontend/src/pages/bots/`
- **Who is affected**: Creators (configure promotion content and strategy), Users (receive content card messages, time-slot quick replies)
- **Cross-references**: [[BOT-001]] (dependency: `send_bot_message()`, bot CRUD), [[BOT-002]] (dependency: template rendering for announcement text, `quick_replies` for slot buttons), [[SECOPS-007]] (no external deps; dev/prod parity via DDB Local / DDB)

## 2. Current-State Investigation (what exists today)

### 2.1 What `bot_auto_reply.py` actually implements

`app/services/bot_auto_reply.py` (285 lines) is labeled "BOT-003" in its module docstring but implements a simpler auto-reply concept, not the full content promotion engine described in BOT-003:

- **`create_auto_reply_rule()`** (`bot_auto_reply.py:28`): Stores a rule under `PK=BOT#{bot_id}`, `SK=RULE#{rule_id}` in `T.chat_bots` (not a separate table). Fields: `trigger_pattern`, `response_template` (plain text, not a BOT-002 template ID), `match_type` (`contains`, `equals`, `starts_with`, `regex`, `any`), `priority`, `enabled`.
- **`process_incoming_message()`** (`bot_auto_reply.py:167`): Evaluates rules by iterating sorted by priority, calls `_matches_pattern()`, applies in-memory rate limit `_reply_rate_cache[(bot_id, conversation_id)]` with `RATE_LIMIT_SECONDS = 60`. Returns the first matched rule's `response_template` text (or `None`). Does not call `send_bot_message()` — callers must do that.
- **`test_message_against_rules()`** (`bot_auto_reply.py:220`): Like `process_incoming_message()` but without rate limiting, returns all matches.

This is effectively a simpler, in-table version of the keyword trigger from BOT-001 (`evaluate_triggers()` in `chat_bot.py:319`). It reuses the `T.chat_bots` table but under `RULE#` SK prefix, creating a mixed-use table that merges bot configuration and rule records. This is a design concern: deleting a bot via `delete_bot()` in `chat_bot.py:167` cascades by querying `PK=BOT#{bot_id}` on `T.bot_assignments`, but auto-reply rules are stored in `T.chat_bots`. The cascade does NOT delete rules. After `delete_bot()`, orphaned `RULE#` records remain in `T.chat_bots`.

### 2.4 `bot_auto_reply.py` — orphaned rule deletion gap

`delete_bot()` in `chat_bot.py:167` deletes assignments from `T.bot_assignments` via `_query_all_assignments()`, then deletes the bot record from `T.chat_bots`. However, auto-reply rules are stored as `SK=RULE#{rule_id}` items in `T.chat_bots` under the same `PK=BOT#{bot_id}`. The cascade at `chat_bot.py:167-180` does not query for `RULE#` SK prefixes. Orphaned rules will remain indefinitely. Fix: extend `delete_bot()` to also query and delete `SK begins_with RULE#` in `T.chat_bots`.

## 3. Gap / Threat Analysis

### 3.1 All data tables are missing

Three new DynamoDB tables need `TableDef` entries in `scripts/local-ddb-init.py`, three settings in `app/core/settings.py`, and three table handles in `app/core/tables.py`. The `attr_types` gotcha (from CLAUDE.md) applies: `bot_content_sets.GSI1SK = created_at` is numeric; `bot_promotion_history.promoted_at` and `bot_promotion_caps.ttl` are numeric — all must be declared `"N"` in `attr_types`.

### 3.2 `content_card` message kind must be added to `MessageOut`

`messaging.py:2330`'s `kind` Literal must be extended with `"content_card"`. The `MessageOut` model must also add a `content_card: Optional[Dict[str, Any]] = None` field. `_message_out_from_item()` must populate it from `merged_item.get("content_card")`. This is a safe additive change.

### 3.3 Orphaned `bot_auto_reply` rules on bot deletion

Described in 2.4. Until `delete_bot()` is fixed, deleting a bot leaves `RULE#` items in `T.chat_bots` under the deleted `PK=BOT#{bot_id}`. If a new bot is created with the same `bot_id` (UUID collision — practically impossible but theoretically a concern), it would inherit orphaned rules. More practically, the orphan records waste storage.

### 3.4 Table naming inconsistency in `bot_auto_reply.py`

Rules are stored in `T.chat_bots` (the bots table) rather than a dedicated table. This couples the auto-reply feature to the bot table and prevents independent scaling or purging. The long-term fix is a separate `bot_auto_reply_rules` table. For now, the cascade gap is the only immediate bug.

### 3.5 Promotion abuse vectors

- **Frequency cap bypass**: Must be enforced server-side in DDB (`bot_promotion_caps` table) with atomic `ADD` to prevent race conditions. Do not rely on in-memory counters (the `_reply_rate_cache` pattern in `bot_auto_reply.py:line 20` would not survive multi-process deployments).
- **CTA URL open redirect**: `cta_url` must be validated to reject `javascript:`, `data:`, and absolute URLs pointing to external domains not on an allowlist. The `add_content_to_set()` service must enforce this.
- **Creator cross-referencing**: `content_ref_id` must be validated against the actual content tables to ensure the creator owns the referenced video/post/broadcast. Without this, a creator could promote another creator's content.
- **Broadcast announcement spam**: `announce_broadcast()` must be idempotent — storing a `announced_{minutes_before}` flag on the bot_assignments or a dedicated DDB record prevents double-announcements if the background loop runs twice within the same tier window.

### 3.6 Calendar booking race condition

`send_available_slots()` sends quick-reply buttons for available calendar slots. Between the time the message is sent and the user taps a button, the slot may become unavailable. `handle_slot_booking()` must re-check availability atomically before creating the booking.

### 4.3 `app/services/bot_promotion.py` — key design decisions

`select_next_promotion(*, bot_id, user_id, conversation_id)`:
1. Fetch `promotion_config` from bot record.
2. Atomic `ADD` + conditional check on `bot_promotion_caps` (`PK=BOT#{bot_id}#CONV#{conversation_id}`, `SK=DAY#{today}`) to check and increment daily cap atomically; reject if `count >= max_promotions_per_day`. Set `ttl = tomorrow + 7*86400`.
3. Fetch content items from `bot_content_sets`.
4. Fetch promotion history for user (`PK=BOT#{bot_id}#USER#{user_id}`).
5. Filter: exclude items where `purchased=true` (if `skip_purchased`) or `promoted_at > now - cooldown_hours * 3600` (if cooldown set).
6. Apply strategy: round-robin advances an in-item counter stored on the user's history record; random uses `random.choice()`; newest_first and priority sort by `created_at desc` or `priority asc`.
7. Return selected `content_item` dict or `None`.

`send_promotion(*, bot_id, conversation_id, user_id, content_item)`:
- Builds `content_card` payload from `content_item`.
- Calls `create_internal_bot_message(conversation_id, kind="content_card", content_card=payload, ...)` (the helper introduced in BOT-001 fix 4.2).
- Writes promotion history record (`promoted_at`, `impression_count ADD 1`).

`announce_broadcast(*, bot_id, session_id, minutes_before)`:
- Fetches broadcast session from `broadcast.py` service layer.
- Computes countdown text: `"LIVE in {minutes_before} minutes: {title}"`.
- Queries bot assignments for this bot's target conversations.
- Sends a `content_card` message to each (capped at 500).
- Writes an idempotency record to prevent double-announcement.

### 4.4 Fix `delete_bot()` cascade for auto-reply rules (`chat_bot.py:167`)

After the existing assignment cascade, add:

```python
# Delete auto-reply rules stored in T.chat_bots
rules_resp = T.chat_bots.query(
    KeyConditionExpression=Key("pk").eq(f"BOT#{bot_id}") & Key("sk").begins_with("RULE#"),
)
for rule in rules_resp.get("Items", []):
    T.chat_bots.delete_item(Key={"pk": rule["pk"], "sk": rule["sk"]})
```
