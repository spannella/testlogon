# SEC-004: Billing Authorization & Ledger Integrity — Investigation & Implementation Write-up

> ~5 pages. Code citations verified against the live codebase.

## 1. Summary & Classification

The billing subsystem has three classes of defect: (1) **authorization gaps** — wallet deposit/withdraw endpoints accept an optional `user_sub` override that allows a `billing_support` admin to move money between arbitrary accounts with no secondary approval requirement; (2) **ledger integrity gaps** — the tip ledger writes debit and credit entries as two independent best-effort DDB `put_item` calls, meaning one can succeed and the other fail silently, creating unmatched ledger entries (stolen funds or free credits); and (3) **input validation gaps** — while the request model enforces `lock_price_cents` bounds at the Pydantic layer, the `unlock_message` service path reads `lock_price_cents` directly from the stored DDB item with no upper-bound re-validation, and amount positivity is enforced only at the model layer with no defense-in-depth check in service functions.

- **Type**: security-fix
- **Severity**: High
- **Status**: Open
- **Area**: `app/routers/billing.py`, `app/services/tip_ledger.py`, `app/routers/messaging.py`
- **Attacker class**: 🛡️ admin-abuse (`billing_support` admin), ⚙️ config/race (tip ledger); 🌐 any-user (lock price)
- **Cross-references**: [[SEC-005]] (IDOR pattern — same class of "trusting caller-supplied user_sub"); [[SECOPS-007]] (dev/prod parity — DDB TransactWrite works identically with DDB Local and AWS DDB)


## 2. Current-State Investigation

### 2a. Wallet deposit IDOR — `user_sub` override (`app/routers/billing.py:2315–2316`)

```python
@dual_route("POST", "/billing/wallet/deposit")
def wallet_deposit(
    body: WalletDepositReq,
    req: Request = None,
    ctx=Depends(require_ui_session),
    actor: AuthenticatedUser = Depends(get_authenticated_user),
    user_sub: Optional[str] = None,  # ← query parameter
) -> Dict[str, Any]:
    user_id, admin_tags = _billing_write_user_context(ctx, user_sub, actor)
```

The `user_sub` query parameter is optional. When provided and different from the authenticated user's subject, `_billing_write_user_context` (line 468) calls `_require_billing_support_actor(resolved_actor)` which enforces the `billing_support` admin scope. If the actor has that scope, `effective_sub = requested` — the deposit targets any account. The audit tags include `viewed_as_admin: True` and `actor_sub`, but there is no requirement for dual authorization, no rate limit on cross-user operations, and no hard cap on the amount that can be deposited.

**Withdrawal path** (`billing.py:2397–2421`): identical pattern via `_billing_write_user_context`. A `billing_support` admin can drain any user's wallet by withdrawing from their account to a payment method the admin controls, using the admin's own payment methods (the withdrawal charges the `user_id`'s wallet, not the admin's card).

### 2b. `dev_add_charge` — direct settled debit fabrication (`app/routers/billing.py:2238–2257`)

```python
@dual_route("POST", "/billing/_dev/add-charge")
def dev_add_charge(
    body: AddChargeReq,
    req: Request = None,
    ctx=Depends(require_ui_session),
    actor: AuthenticatedUser = Depends(require_billing_admin_operator),
    user_sub: Optional[str] = None,
) -> Dict[str, Any]:
    ...
    led_sk_value, led_item = new_ledger_entry(
        ...
        state=body.state,   # ← caller-controlled; can be "settled"
        ...
    )
```

The endpoint is named `_dev/add-charge` but there is no `S.dev_mode` gate — `require_billing_admin_operator` is a `billing_support` scope check, which is the same scope as the deposit/withdraw endpoints. Any `billing_support` admin in any environment can write a `settled` debit directly to any user's ledger without going through a payment confirmation flow. This bypasses the normal `pending → settled` lifecycle enforced by Stripe/PayPal/CCBill webhook callbacks.

### 2c. Tip ledger — best-effort non-atomic writes (`app/services/tip_ledger.py:88–174`)

```python
def write_tip_ledger(entry: TipLedgerEntry) -> Dict[str, str]:
    # 1. Write debit entry (charge to tipper)
    try:
        T.billing.put_item(Item={...})    # line 134
    except Exception:
        logger.warning("tip_ledger_debit_write_failed", ...)   # silent

    # 2. Write credit entry (income to recipient)
    try:
        T.billing.put_item(Item={...})    # line 155
    except Exception:
        logger.warning("tip_ledger_credit_write_failed", ...)  # silent
```

Lines 133–172. The function's docstring explicitly states "Both writes are best-effort — failure does not propagate to the caller." This means:
- If the debit write fails but the credit write succeeds: the recipient gets paid without the sender being charged (free credit).
- If the debit write succeeds but the credit write fails: the sender is charged but the recipient is not paid (stolen funds / unmatched ledger).
- Both failures are swallowed silently; the `write_tip_ledger` call returns `result = {"debit_entry_id": debit_id, "credit_entry_id": credit_id}` regardless.

The function is called from both `send_text_message` and `create_image_message` (via the attached-tip flow) and from the standalone tip endpoint — all billing-critical paths.

### 2d. Unlock price — no service-layer upper bound (`app/routers/messaging.py:13601–13610`)

```python
msg = _get_message_or_404(conversation_id, message_id)
if not msg.get("lock_price_cents"):
    raise HTTPException(400, "Message is not locked")
...
amount_cents = int(msg["lock_price_cents"])
```

Lines 13601–13610. The `lock_price_cents` stored in DDB was originally validated at message-creation time by the Pydantic model at `app/routers/messaging.py:1858`:

```python
lock_price_cents: Optional[int] = Field(default=None, ge=1, le=100_000)
```

This field is bounded at `le=100_000` (100,000 cents = $1,000 USD) in the request model. However:
1. The stored value is read back from DDB with no re-validation — if an older message pre-dates the `le=100_000` constraint, or if data was written directly to DDB (e.g., via the dev endpoint or a data migration), `amount_cents` could be arbitrarily large.
2. The Pydantic model only validates on the **create** path; there is no validation on the **read + charge** path.

The ticket's mention of "unbounded" reflects this defense-in-depth gap rather than a complete absence of any bound.

### 2e. Positive-amount enforcement

`wallet_deposit` and `wallet_withdraw` accept `amount_cents: int` via `WalletDepositReq` / `WalletWithdrawReq`. The Pydantic models include `ge=1` (deposit must be at least 1 cent). However `app/services/creator_payouts.py` payout functions and the `dev_add_charge` endpoint accept `amount_cents` as `int` with no service-layer `> 0` check.

### 2f. Dev vs prod behavior today

All billing paths use DDB (DDB Local in dev, AWS DDB in prod). `T.billing` is configured from `S.billing_table_name`. The tip ledger uses `T.billing` directly (moto in dev, AWS in prod — identical API). `dev_add_charge` is not gated by `S.dev_mode`, so it is equally available in prod to any `billing_support` admin.


## 3. Gap / Threat Analysis

### Attack A — Admin-initiated money laundering via cross-user deposit

**Precondition**: attacker holds a compromised `billing_support` admin account (or is a malicious insider).

1. `POST /billing/wallet/deposit?user_sub=victim` with `body.payment_method_id` pointing to the admin's own payment method.
2. `_billing_write_user_context` accepts the override; Stripe `PaymentIntent.create` charges the admin's card.
3. Ledger credit is written to `USER#{victim}`, increasing victim's wallet balance.
4. Admin then calls `POST /billing/wallet/withdraw?user_sub=victim` to withdraw from victim's wallet to a payout account the admin controls.

**Net effect**: admin uses victim's wallet as a laundering intermediary — admin charges their own card, parks funds in victim's wallet, then drains it.

**Audit trail**: both operations are logged with `viewed_as_admin: True` and `actor_sub`, so the audit trail exists, but there is no approval gate to prevent it from occurring.

### Attack B — Settled debit forgery via `dev_add_charge`

Any `billing_support` admin calls `POST /billing/_dev/add-charge?user_sub=target` with `body.state="settled"` → directly writes a `settled` debit to any user's ledger, increasing `owed_settled_cents`. If the billing system uses `owed_settled_cents` to block feature access (e.g., "account has outstanding balance"), this can be used to lock out any user.

### Attack C — Tip ledger split to steal payment

Under network or DDB transient failure:
1. Debit write (`USER#{tipper}`) fails (DDB timeout). Warning logged.
2. Credit write (`USER#{recipient}`) succeeds.
3. Result dict is returned with both IDs populated (caller has no idea one write failed).
4. Recipient has earned the tip; tipper's ledger shows no charge.

Alternatively, with the debit succeeding and credit failing: tipper is charged, recipient earns nothing.

## 4. Proposed Design / Fix

### 4a. Remove `user_sub` override from wallet deposit/withdraw

The simplest and safest fix: remove the `user_sub` query parameter from `wallet_deposit` and `wallet_withdraw`, forcing both endpoints to always operate on the authenticated user's own account:

```python
@dual_route("POST", "/billing/wallet/deposit")
def wallet_deposit(
    body: WalletDepositReq,
    req: Request = None,
    ctx=Depends(require_ui_session),
) -> Dict[str, Any]:
    user_id = ctx["user_sub"]   # always the authenticated user
    pk = user_pk(user_id)
    ...
```

If admin-initiated balance adjustments are legitimately needed (e.g., customer service credit/refund), introduce a dedicated, separately-scoped endpoint:

```
POST /billing/admin/credit-adjustment
```

Requirements for this endpoint: (a) requires ROOT role or a dedicated `billing_adjustment` scope (not `billing_support`); (b) requires a `reason` and `reference_ticket_id`; (c) sends an approval notification to a second admin (two-person rule); (d) has a per-day amount cap configured in settings; (e) emits an `audit_event` with full actor/target/amount/reason.

### 4b. Gate `dev_add_charge` on `S.dev_mode`

```python
@dual_route("POST", "/billing/_dev/add-charge")
def dev_add_charge(...):
    if not S.dev_mode:
        raise HTTPException(404, "Not found")
    ...
```

This ensures the endpoint is unreachable in prod regardless of the caller's role. Remove from the OpenAPI spec in non-dev mode (`include_in_schema=False` already used for other dev endpoints — apply the same pattern).

### 4c. Make tip ledger atomic with DDB TransactWrite

Replace the two sequential `put_item` calls in `write_tip_ledger` with a single `transact_write_items`:

```python
from boto3.dynamodb.conditions import Attr

def write_tip_ledger(entry: TipLedgerEntry) -> Dict[str, str]:
    ...
    debit_item = { "pk": f"USER#{entry.tipper_user_id}", "sk": f"LEDGER#{ts}#{debit_id}", ... }
    credit_item = { "pk": f"USER#{entry.recipient_user_id}", "sk": f"LEDGER#{ts}#{credit_id}", ... }

    T.billing.meta.client.transact_write_items(TransactItems=[
        {
            "Put": {
                "TableName": T.billing.name,
                "Item": _serialize_item(debit_item),
                "ConditionExpression": "attribute_not_exists(pk)",   # idempotency guard
            }
        },
        {
            "Put": {
                "TableName": T.billing.name,
                "Item": _serialize_item(credit_item),
                "ConditionExpression": "attribute_not_exists(pk)",
            }
        },
    ])
    return {"debit_entry_id": debit_id, "credit_entry_id": credit_id}
```

The `ConditionExpression: "attribute_not_exists(pk)"` on items keyed by `pk+sk` (where `sk` includes a UUID) is always true for new entries — it provides idempotency against duplicate calls with the same `entry_id`. Exceptions from `transact_write_items` must now **propagate** to the caller (no `try/except` swallow). Callers that currently fire-and-forget `write_tip_ledger` should be updated to handle errors.

### 4d. Re-validate `lock_price_cents` at charge time

In `unlock_message` at line 13610, add:

```python
MAX_LOCK_PRICE_CENTS = 100_000   # $1,000 USD — matches Pydantic model constraint
amount_cents = int(msg["lock_price_cents"])
if amount_cents <= 0 or amount_cents > MAX_LOCK_PRICE_CENTS:
    raise HTTPException(400, f"lock_price_cents out of valid range [1, {MAX_LOCK_PRICE_CENTS}]")
```

Similarly, in `creator_payouts.py` and any service-layer function that processes a money amount, add a guard:

```python
def _require_positive_amount(amount_cents: int, label: str = "amount_cents") -> None:
    if amount_cents <= 0:
        raise ValueError(f"{label} must be > 0, got {amount_cents}")
```

### 4e. Dev/prod parity (SECOPS-007)

- DDB TransactWrite is available in DDB Local (version 1.21.0+ supports transactions). The existing dev stack (`scripts/local-ddb-init.py`) uses DDB Local — no change needed.
- `dev_add_charge` dev-gate uses `S.dev_mode` flag, same as other mock endpoints — consistent with the SECOPS-007 pattern.
- The `billing_support` scope enforcement (`require_billing_support_admin`) runs identically in dev and prod; no mock bypass exists.

### 4f. Alternatives considered

- **Keep `user_sub` override but add mandatory second-approval workflow**: more complex, more useful for customer service. Deferred as the dedicated `credit-adjustment` endpoint (4a). The immediate fix is removal.
- **Optimistic lock on wallet balance**: prevents concurrent double-credits but does not address the fundamental IDOR issue.
- **Saga pattern for tip debit+credit**: full saga with compensating transactions. Overkill for a single-table DDB application; TransactWrite is sufficient.


## 5. Testing, Verification & Rollout

### pytest unit tests

1. `test_wallet_deposit_no_cross_user`: Alice's session calls `POST /billing/wallet/deposit?user_sub=bob` → HTTP 422 (unknown query param) or 403 (user_sub removed from signature).
2. `test_wallet_deposit_self_works`: Alice deposits to her own wallet → 200.
3. `test_dev_add_charge_blocked_in_prod`: `S.dev_mode=False` → `POST /billing/_dev/add-charge` → HTTP 404.
4. `test_dev_add_charge_allowed_in_dev`: `S.dev_mode=True`, billing admin actor → ledger entry written, `owed_settled_cents` updated.
5. `test_tip_ledger_atomic_both_written`: mock `transact_write_items` to succeed → both `debit_entry_id` and `credit_entry_id` returned, both items visible in DDB.
6. `test_tip_ledger_atomic_debit_fail_no_credit`: mock `transact_write_items` to raise `TransactionCanceledException` → exception propagates, no ledger entries written.
7. `test_tip_ledger_credit_orphan_prevented`: verify that after a simulated partial failure, no orphan credit exists (the atomicity guarantee).
8. `test_unlock_message_price_cap_enforced`: inject DDB message with `lock_price_cents=999_999` (above Pydantic max, simulating old data); `POST /unlock` → HTTP 400 "out of valid range".
9. `test_unlock_message_negative_price_rejected`: `lock_price_cents=0` in DDB → HTTP 400.

All tests use moto DDB, no real Stripe calls. Fully offline.

### Playwright E2E

No new spec strictly required. Existing `messaging-features.spec.ts` (section 11 — tips and locks) exercises the tip flow end-to-end in dev; after the TransactWrite change, the same tests should continue to pass. Optional: add a `beforeAll` check that verifies Alice's ledger has matching debit and credit entries after a tip is sent.

### Manual / QA steps

1. With dev stack up: confirm `POST /billing/wallet/deposit?user_sub=other` returns 422 or 403 after removing the parameter.
2. Confirm `POST /billing/_dev/add-charge` with `DEV_MODE=0` returns 404.
3. Send a tip from Alice to Bob; query `GET /billing/history` for both; confirm both debit and credit appear.
4. Simulate DDB transient failure by briefly stopping DDB Local mid-tip; confirm neither entry appears (rollback) and the UI shows an error.

### Observability

- Metric `billing_cross_user_operation_total{operation="deposit|withdraw", actor_role=..., outcome="success|forbidden"}` — use this to detect if cross-user operations occur before the `user_sub` param is fully removed.
- Metric `tip_ledger_transact_fail_total{reason="conditional_check|provision_throughput|other"}` — alert if this rises above baseline after the TransactWrite migration.
- Alert on `dev_add_charge` calls in any non-dev environment (should be zero).

### Rollout

1. Gate `dev_add_charge` on `S.dev_mode` — zero user-visible impact, deploy first.
2. Deploy `lock_price_cents` re-validation at charge time — safe, only rejects out-of-range values.
3. Deploy TransactWrite for tip ledger. Monitor `tip_ledger_transact_fail_total`. Roll back if error rate > 0.1% (add a feature flag `use_transact_tip_ledger=True` to the settings to enable/disable).
4. Remove `user_sub` from deposit/withdraw after the dedicated admin credit-adjustment endpoint is built and tested.

**Effort**: S for items 1–2; M for TransactWrite migration; M–L for admin credit-adjustment endpoint design (two-person approval workflow). Total: M.
