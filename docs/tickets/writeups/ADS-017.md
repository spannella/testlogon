# ADS-017: Ad Performance Optimization — Investigation & Implementation Write-up

## 1. Summary & Classification

ADS-017 delivers automated optimization for the advertising platform: performance-weighted creative rotation, underperformer auto-pause, A/B test statistical significance, suggested bid and budget recommendation, and performance alert generation. Without optimization, advertisers must manually inspect campaign analytics and adjust creative weights themselves — a labor-intensive task that results in wasted impressions on low-CTR creatives and reactive rather than proactive budget management.

- **Type**: Feature
- **Priority**: Medium (7–9 days estimate)
- **Status**: Implemented — `app/services/ad_optimization.py` and `app/routers/ad_optimization.py` both exist and are registered in `app/main.py`. Supporting DDB infrastructure (`T.ad_optimization_recommendations`) is wired.
- **Owning area**: Ad Platform / Advertiser Tools
- **User persona**: Advertisers who manage one or more campaigns and want ROI improvement without manual intervention
- **Dependencies**: ADS-001 (campaigns), ADS-002 (creatives), ADS-004 (serving), ADS-007 (billing), ADS-008 (analytics) — all required upstream; ADS-004/007/008 are independently implemented as of the current branch
- **Cross-references**: [[ADS-008]] (analytics rollups feed `get_creative_stats`), [[ADS-004]] (creative weights consumed by serving engine), [[SECOPS-007]] (dev/prod parity: all DDB writes via `T.*` handles, no direct AWS construct)

## 2. Current-State Investigation (what exists today)

### 2.1 Service Layer: `app/services/ad_optimization.py`

The full optimization service exists and is feature-complete. Key verified functions and line ranges:

**`calculate_creative_weights`** (`ad_optimization.py:123–144`): Computes per-creative rotation weights proportional to CTR with a `MIN_WEIGHT = 0.05` floor and normalizes to sum 1.0. Pure-Python, no external dependencies. Uses `math.erf` via `_normal_cdf` — no `scipy` import contrary to the ticket spec's draft (the pure-Python path was chosen).

**`identify_underperformers`** (`ad_optimization.py:147–169`): Flags creatives with `impressions >= min_impressions` and `ctr < ctr_threshold`. Default thresholds: 1000 impressions, 0.5% CTR (`DEFAULT_AUTO_PAUSE_CTR_THRESHOLD = 0.005`, line 44).

**`get_creative_stats`** (`ad_optimization.py:78–117`): Delegates to `ad_analytics.get_breakdown(dimension="creative", days=days)`, then pads with zeroed entries for creatives with no analytics rows (from `list_creatives(campaign_id)`). Returns deterministically ordered list (sorted by `creative_id`).

**`calculate_suggested_bid`** / **`recommend_daily_budget`** (`ad_optimization.py:193–243`): Deterministic based on targeting specificity score (`_calculate_targeting_specificity`, lines 175–191). No ML or external dependency — behavior is fully reproducible in dev without AWS.

**`ab_test_significance`** (`ad_optimization.py:253–308`): Two-proportion Z-test using `_normal_cdf` (pure Python via `math.erf`). Returns `sample_size_sufficient=False` when either variant has < 100 impressions. Returns `winner=None` when the test is not significant at the configured confidence level.

**`check_performance_alerts`** (`ad_optimization.py:314–367`): Three alert types — `ctr_below_threshold`, `roas_below_threshold`, `budget_overpacing`. Pure function of `campaign_metrics` dict and config thresholds.

**`generate_recommendations`** (`ad_optimization.py:441–596`): The primary entry point. Produces three recommendation kinds: `pause_creative` (one per underperformer), `reallocate_budget` (toward the top-CTR creative), and `adjust_bid` (when campaign CTR < `DEFAULT_CTR_ALERT_THRESHOLD` with ≥ 500 impressions). Each recommendation is stored via `_store_recommendation` into `T.ad_optimization_recommendations` (DDB PK=`CAMP#{campaign_id}`, SK=`REC#{recommendation_id}`). Recommendation IDs are deterministic hashes of `(campaign_id, action, creative_id, salt)` where salt is `str(now_ts())`.

**`apply_recommendation`** (`ad_optimization.py:614–683`): Applies a stored recommendation by mutating the upstream entity. `pause_creative` → `T.ad_creatives.update_item` setting `status="auto_paused"`, `paused_reason`, `paused_at`. Safety: never pauses the last remaining active creative (lines 639–644). `reallocate_budget` → writes `creative_weights` to `T.ad_campaigns`. `adjust_bid` → writes `suggested_bid_cpm_cents` to `T.ad_campaigns`. Both campaign mutations go through `_set_campaign_field` (`ad_optimization.py:703–711`) which uses `T.ad_campaigns.update_item`.

**`update_optimization_config`** (`ad_optimization.py:717–751`): Persists `optimization_config` dict and `auto_optimize_enabled` on the campaign record.

### 2.2 Router: `app/routers/ad_optimization.py`

Router registered in `app/main.py:722–723` under prefix `/ui/ads/optimization`. All endpoints use `require_ui_session` via `_require_campaign_owner` which also enforces account ownership (403 if `acct["owner_sub"] != user_sub`).

Endpoints implemented (all present, verified):
- `POST /ui/ads/optimization/campaigns/{id}/generate` — triggers `generate_recommendations`
- `GET /ui/ads/optimization/campaigns/{id}/recommendations` — lists stored recommendations with optional status filter
- `POST /ui/ads/optimization/campaigns/{id}/recommendations/{rec_id}/apply` — applies and marks `applied`
- `POST /ui/ads/optimization/campaigns/{id}/recommendations/{rec_id}/dismiss` — marks `dismissed`
- `GET /ui/ads/optimization/campaigns/{id}/ab-test` — Z-test between two creatives by query param
- `GET /ui/ads/optimization/campaigns/{id}/suggested-bid` — bid range
- `GET /ui/ads/optimization/campaigns/{id}/budget-recommendation` — budget by desired reach
- `PATCH /ui/ads/optimization/campaigns/{id}/optimization-config` — config update

### 2.3 DynamoDB Infrastructure

`T.ad_optimization_recommendations` table handle exists at `app/core/tables.py:418`. The table uses `ByCampaignCreatedAt` GSI (queried by `campaign_id`) for `list_recommendations` (`ad_optimization.py:427–435`). The table must exist in `scripts/local-ddb-init.py` for dev/E2E; if the table definition is missing, `list_recommendations` will fail with a DDB resource error.

### 2.4 Missing Pieces

**No frontend components yet**: The ticket specifies `frontend/src/pages/ads/OptimizationPanel.tsx`, `frontend/src/components/ads/RecommendationCards.tsx`, `frontend/src/components/ads/ABTestResults.tsx`, and `frontend/src/api/endpoints/adOptimization.ts`. None of these files exist as of the current codebase state. TypeScript types for optimization responses are also absent from `frontend/src/api/types.ts`.

**No background scheduler**: The ticket's architecture diagram mentions a background optimization run. The current implementation is call-on-demand only (via `/generate`). The `auto_optimize_enabled` field is persisted but nothing reads it to trigger a periodic run. A background task or cron hook calling `generate_recommendations` for all campaigns with `auto_optimize_enabled=True` does not exist.

**Dev/prod parity**: All DDB writes use `T.*` table handles backed by `DDB_ENDPOINT_URL` in dev (port 8001, DDB Local) and real DynamoDB in prod — no scattered `if dev:` branches in this service. Bid/budget calculations are fully deterministic with no external dependency, satisfying the SECOPS-007 offline requirement.

## 3. Gap / Threat Analysis

### 3.1 Missing Frontend

The backend is production-ready. Advertisers cannot access optimization through the UI until the frontend panel is built. The four missing files represent approximately 2–3 days of frontend work:

- `frontend/src/api/endpoints/adOptimization.ts`: Six axios wrappers mapping to the implemented backend endpoints
- `frontend/src/api/types.ts` additions: `OptimizationRecommendation`, `ABTestResult`, `SuggestedBid`, `BudgetRecommendation` interfaces
- `OptimizationPanel.tsx`: Campaign detail sub-panel with generate button, recommendation cards, config sliders
- `ABTestResults.tsx`: Two-column display with significance badge, p-value, lift %, winner declaration

### 3.2 Missing Background Scheduler

The `auto_optimize_enabled` campaign field is stored but never actioned. Without a periodic job, enabling auto-optimize has no effect. Implementation requires a FastAPI `BackgroundTasks` startup loop or a cron hook in `scripts/dev.sh`.

### 3.3 Creative Weights Not Consumed by Serving Engine

`apply_recommendation(action="reallocate_budget")` writes `creative_weights` to the campaign record. `app/services/ad_serving.py:serve_ad()` does not read `creative_weights` for weighted random selection — it loads active campaigns but does not implement weighted rotation. This means applying the rotation recommendation has no observable effect on ad delivery.

### 3.4 Recommendation Idempotency

`_rec_id` uses `str(now_ts())` as the salt (`ad_optimization.py:379`). Two rapid calls to `/generate` within the same second produce identical recommendation IDs (SHA-256 is deterministic on same input). DynamoDB PutItem overwrites the existing item. This is intentional — rapid re-generation refreshes the same recommendation — but it means applied/dismissed recommendations can be un-applied by a subsequent generate call that re-opens them with status=`open`. The `_store_recommendation` call at line 566 does not check current status before overwriting.

### 3.5 Abuse Potential

Only the campaign owner can trigger optimization (403 for non-owners). Auto-pause of the last active creative is guarded. No abuse vector exists in the current backend.

## 4. Proposed Design / Fix

### 4.1 Frontend (Primary Gap)

**`frontend/src/api/endpoints/adOptimization.ts`** — six wrappers:
```ts
export const generateRecommendations = (campaignId: string, days?: number) =>
  client.post(`/ui/ads/optimization/campaigns/${campaignId}/generate`, {}, { params: { days } });
export const listRecommendations = (campaignId: string, status?: string) =>
  client.get(`/ui/ads/optimization/campaigns/${campaignId}/recommendations`, { params: { status } });
export const applyRecommendation = (campaignId: string, recId: string) =>
  client.post(`/ui/ads/optimization/campaigns/${campaignId}/recommendations/${recId}/apply`);
export const dismissRecommendation = (campaignId: string, recId: string) =>
  client.post(`/ui/ads/optimization/campaigns/${campaignId}/recommendations/${recId}/dismiss`);
export const getABTest = (campaignId: string, aId: string, bId: string, confidence = 0.95) =>
  client.get(`/ui/ads/optimization/campaigns/${campaignId}/ab-test`, { params: { creative_a_id: aId, creative_b_id: bId, confidence_level: confidence } });
export const getSuggestedBid = (campaignId: string) =>
  client.get(`/ui/ads/optimization/campaigns/${campaignId}/suggested-bid`);
```

**`frontend/src/pages/ads/OptimizationPanel.tsx`** — React Query `useMutation` for generate, `useQuery` for list with status filter. Recommendation cards with `action` type badge (`pause_creative` = orange, `reallocate_budget` = blue, `adjust_bid` = yellow). Apply/dismiss buttons that invalidate `["optimization", campaignId]` query key.

**`frontend/src/components/ads/ABTestResults.tsx`** — receives `campaignId`, `creativeAId`, `creativeBId` as props. Uses `useQuery` to call `getABTest`. Shows significance badge, lift %, z-score, p-value, winner card. "Needs more data" state when `sample_size_sufficient=false`.

### 4.2 Serving Engine Integration

`app/services/ad_serving.py:serve_ad()` should read `campaign.get("creative_weights")` when selecting a creative from `list_approved_creatives`. Replace the current `random.choice(eligible)` with `random.choices(eligible, weights=[creative_weights.get(c["creative_id"], 1.0) for c in eligible])`. This makes `apply_recommendation(action="reallocate_budget")` immediately effective on the next ad request.

### 4.3 Recommendation Idempotency Fix

Add `ConditionExpression="attribute_not_exists(pk) OR #s = :open"` to `_store_recommendation` to prevent overwriting applied or dismissed recommendations. Alternatively, use a different salt that includes the date bucket (e.g., today's UTC date) so recommendations are re-generated daily but not on every API call within the same second.

### 4.4 Background Scheduler

Add a startup background task in `app/main.py` that runs every 6 hours, queries campaigns with `auto_optimize_enabled=True`, and calls `generate_recommendations` for each. In dev this uses DDB Local; in prod it uses real DynamoDB. No AWS-specific SDK call is needed — the existing `T.*` handles are environment-agnostic.

### 4.5 Dev/Prod Parity (SECOPS-007)

All optimization logic is already parity-compliant: DDB via `T.*`, pure-Python math (no scipy), no outbound calls. The only new table (`ad_optimization_recommendations`) must be in `scripts/local-ddb-init.py` with `attr_types={"created_at": "N"}` for the `ByCampaignCreatedAt` GSI to work correctly with integer timestamps.

## 5. Testing, Verification & Rollout

### 5.1 pytest Unit Tests (`tests/test_ad_optimization.py`)

All pure-logic functions can be tested without DDB using `moto` for the persistence layer:

| Test | Verified behavior |
|------|-------------------|
| `test_weights_proportional_to_ctr` | Creative with 3× CTR gets ~3× weight after normalization |
| `test_weights_sum_to_one` | All weight values sum to 1.0 ± 1e-6 |
| `test_min_weight_floor` | Worst performer never drops below `MIN_WEIGHT = 0.05` |
| `test_underperformer_flagged` | Creative with 1500 impressions and 0.3% CTR appears in list |
| `test_underperformer_below_min_impressions` | 500 impressions → not flagged regardless of CTR |
| `test_ab_test_significant` | p-value < 0.05 with 2000 impressions and clear winner |
| `test_ab_test_insufficient_sample` | n < 100 → `significant=False`, `sample_size_sufficient=False` |
| `test_suggested_bid_narrow_targeting` | Interests list + narrow age range → `competition_level="high"` |
| `test_budget_recommendation_scales` | `desired_daily_reach=2000` → ~2× budget vs `1000` |
| `test_generate_stores_recommendations` | `generate_recommendations` returns recs; DDB query confirms persistence |
| `test_apply_pauses_creative` | `apply_recommendation(pause_creative)` → DDB item has `status="auto_paused"` |
| `test_apply_refuses_last_creative` | `apply_recommendation` raises `ValueError` when only one active creative remains |
| `test_dismiss_marks_dismissed` | `dismiss_recommendation` → DDB status = `"dismissed"` |
| `test_non_owner_gets_403` | Router: non-owner `user_sub` → HTTP 403 |

### 5.2 Playwright E2E (`frontend/e2e/ad-optimization.spec.ts`)

The E2E spec file exists at `frontend/e2e/ad-optimization.spec.ts`. Tests cover sections 411–413 (12 tests) per the ticket spec. Key scenarios:
- Seed a campaign with 3 creatives and mock analytics data → POST `/generate` → GET `/recommendations` confirms weight and underperformer fields
- Apply `reallocate_budget` recommendation → GET campaign confirms `creative_weights` updated
- A/B test endpoint with sufficient impressions → `significant` and `winner` populated
- PATCH optimization-config with `ctr_threshold=5.0` → 422
- Non-owner (Bob) accessing Alice's campaign optimization → 403

Tests are runnable offline: DDB Local on port 8001, no outbound calls.

### 5.3 Observability

Add a `recommendations_generated_total` counter (Counter, labels: `campaign_id`, `action`) and `recommendations_applied_total` counter. Tie to the existing Prometheus metrics endpoint at `app/metrics.py`.

### 5.4 Rollout

- **Merge order**: After ADS-001, ADS-002, ADS-008 (analytics). Can start backend development now; DDB table creation is additive.
- **Risk**: Applying `pause_creative` directly mutates creative status. The last-active-creative safety guard (`ad_optimization.py:639–644`) prevents full campaign silence, but careful QA of the apply endpoint is needed before enabling auto-optimize by default.
- **Feature flag**: `auto_optimize_enabled` per-campaign is already a DDB field; no global flag needed. The background scheduler can be behind an env var `AD_AUTO_OPTIMIZE_INTERVAL_HOURS` (set to 0 to disable).
- **Rollback**: Disable the background scheduler; the `/generate` endpoint is stateless. Applied recommendations can be manually reversed by updating creative/campaign fields.
- **Effort**: Backend service and router are complete (L done). Remaining work is frontend (M, ~2–3 days) and serving engine weight integration (S, ~0.5 days).
