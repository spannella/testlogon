# ADS-018: Admin Ad Platform Management — Investigation & Implementation Write-up

## 1. Summary & Classification

ADS-018 provides platform administrators with oversight and control over the advertising system: cross-user listing of advertiser accounts, campaigns, and creatives; account and creative moderation (approve/reject/suspend) with an immutable audit trail; platform-wide revenue and spend metrics; and a kill switch. Without this layer, any advertiser can activate any content and the platform has no revenue visibility, no content policy enforcement, and no emergency stop capability.

- **Type**: Feature
- **Priority**: High (10–12 days estimate)
- **Status**: Partially Implemented — the service layer (`app/services/admin_ad_platform.py`) and router (`app/routers/admin_ad_platform.py`) are both present and registered. However, several capabilities from the ticket spec (house ads, financial report export, platform-wide settings CRUD with kill switch, full revenue-by-content-type breakdown) are absent.
- **Owning area**: Admin / Platform Operations
- **User persona**: Platform administrators (ADMIN role) and root operators (ROOT role) managing the ad system
- **Dependencies**: ADS-001 (ad_accounts/ad_campaigns tables), ADS-002 (ad_creatives), ADS-004 (ad_serving for kill switch), ADS-007 (ad_billing ledger for revenue)
- **Cross-references**: [[ADS-001]], [[ADS-002]], [[ADS-007]], [[SECOPS-007]] (DDB Local in dev; `T.*` handles used throughout)

## 2. Current-State Investigation (what exists today)

### 2.1 Service Layer: `app/services/admin_ad_platform.py`

The service file is implemented and covers the following areas:

**Cross-user listing** (`admin_ad_platform.py:77–136`): Three scan-based functions — `list_all_advertiser_accounts`, `list_all_campaigns`, `list_all_creatives` — each with optional `status`, `owner_sub`/`account_id`/`campaign_id` filters and `limit` cap. Uses `_scan_all` helper (`lines 50–63`) which paginates via `LastEvaluatedKey`. These are table scans (`T.ad_accounts`, `T.ad_campaigns`, `T.ad_creatives`), appropriate for admin views where low frequency justifies the scan cost.

**Account detail** (`admin_ad_platform.py:143–153`): `get_account_detail` returns the account record plus all its campaigns — delegates to `get_ad_account` (from `app/services/ad_accounts`) plus `list_all_campaigns(account_id=...)`.

**Moderation logging** (`admin_ad_platform.py:156–190`): `_log_moderation` writes an immutable event to `T.ad_moderation_log` (`pk=MODERATION#{item_type}#{item_id}`, `sk=EVENT#{ts}#{event_id}`) and calls `audit_event` from `app/services/alerts`. This satisfies the immutability requirement from the ticket spec.

**Account moderation** (`admin_ad_platform.py:202–224`): `moderate_account` delegates to `review_ad_account` from `app/services/ad_accounts` for approve/reject transitions, then logs the event. For `suspend` action, the same `review_ad_account` function is called (the underlying service maps `reject → rejected`, `approve → active`).

**Creative moderation** (`admin_ad_platform.py:227–262`): `moderate_creative` delegates to `review_creative` from `app/services/ad_creatives` for approve/reject. For `suspend`, it applies a direct `T.ad_creatives.update_item` to set `status="rejected"` (line 244), because `review_creative` does not expose a suspend transition. This is a slight semantic mismatch — "suspended" is conflated with "rejected" at the storage level.

**Platform metrics** (`admin_ad_platform.py:278–333`): `get_platform_metrics` scans `T.ad_billing` for `entry_type in ("impression_charge", "click_charge", "conversion_charge")`, aggregates total spend, and splits into `platform_revenue_cents` (30% via `PLATFORM_REVENUE_SHARE_PCT` from `app/services/ad_billing`) and `creator_share_cents`. Also provides counts by status for accounts, campaigns, and creatives via `_count_by_status`.

**Revenue time series** (`admin_ad_platform.py:336–364`): `get_monthly_revenue_series` buckets billing entries by `month_key` field (expected on billing entries) and returns sorted monthly aggregates.

**Top spenders** (`admin_ad_platform.py:367–385`): `get_top_spenders` aggregates spend by `account_id` from billing entries, enriches with account metadata, sorts descending. Limited to `limit` parameter.

### 2.2 Router: `app/routers/admin_ad_platform.py`

Router registered in `app/main.py:744–745` under prefix `/ui/admin/ad-platform`. Auth pattern: most endpoints use `require_admin_or_root` (from `app/auth/policy`); destructive/settings endpoints use `require_root_session`.

Implemented endpoints (verified in router file):
- `GET /ui/admin/ad-platform/accounts` — list all advertiser accounts with filters
- `GET /ui/admin/ad-platform/accounts/{id}` — account detail + campaigns
- `GET /ui/admin/ad-platform/campaigns` — all campaigns
- `GET /ui/admin/ad-platform/creatives` — all creatives
- `POST /ui/admin/ad-platform/accounts/{id}/moderate` — account approve/reject/suspend
- `POST /ui/admin/ad-platform/creatives/{id}/moderate` — creative approve/reject/suspend
- `GET /ui/admin/ad-platform/moderation-history/{type}/{id}` — audit log for item
- `GET /ui/admin/ad-platform/metrics` — platform-wide metrics
- `GET /ui/admin/ad-platform/revenue/monthly` — monthly revenue series
- `GET /ui/admin/ad-platform/top-spenders` — top advertiser accounts by spend

### 2.3 DynamoDB Infrastructure

Tables used:
- `T.ad_moderation_log` (`app/core/tables.py:411`) — immutable moderation events
- `T.ad_billing` (`app/core/tables.py:415`) — ad billing ledger (charge entries)
- `T.ad_accounts` (`app/core/tables.py:407`), `T.ad_campaigns` (`line 408`), `T.ad_creatives` (`line 410`)

All table handles exist. The DDB tables themselves must be defined in `scripts/local-ddb-init.py` for dev operation.

### 2.4 What Is Missing

**House ads system**: The ticket spec defines a `house_ads` service, `ad_house_ads` DDB table, and CRUD endpoints. None exist in the codebase — no `app/services/house_ads.py`, no `T.ad_house_ads` handle, no DDB table definition, no router endpoints. The `ad_serving.py` `HOUSE_AD` constant (`line 30`) is a hardcoded static dict, not a managed system.

**Global ad kill switch**: The ticket specifies a `POST /v1/admin/ads/kill-switch` endpoint and an `ads_enabled` platform setting. No such endpoint or platform settings table exists. The kill switch integration into `serve_ad()` (the `if not settings.get("ads_enabled")` check) is absent.

**Platform settings CRUD**: No `admin_ad_settings.py` service and no settings endpoint for configuring default CPM, revenue share BPS, max ad frequency, moderation policy, blocked categories, etc.

**Financial report export (CSV/JSON)**: The ticket specifies `GET /v1/admin/ads/reports/{type}` with date-range CSV/JSON export. No such endpoint or `generate_financial_report` function exists.

**Revenue by content type**: `get_platform_metrics` does not provide a per-content-type breakdown. `get_monthly_revenue_series` provides monthly buckets only.

**Top earners (creators)**: The ticket specifies a top-earning creators view. `get_top_spenders` covers advertisers but there is no `get_top_earners` function for creator revenue share.

**Frontend**: No `frontend/src/pages/admin/ads/AdminAdDashboard.tsx` or `frontend/src/api/endpoints/adminAds.ts` exists.

**`AdminScope.AD_MANAGEMENT`**: The ticket notes this scope should be added to `app/auth/roles.py` `CANONICAL_ADMIN_SCOPES`. The current router uses `require_admin_or_root` (any admin or root) rather than a specific `AD_MANAGEMENT` scope, which is a broader access grant than the spec intended.

## 3. Gap / Threat Analysis

### 3.1 Absent Kill Switch — High Operational Risk

Without a kill switch, there is no emergency path to stop all ad serving platform-wide. If an advertiser launches objectionable content or a billing bug causes over-charging, admins must manually reject campaigns one by one via the moderation endpoint. At scale this is untenable. The kill switch is the single most critical missing capability.

### 3.2 Scan Performance

All three cross-user listing functions (`list_all_advertiser_accounts/campaigns/creatives`) issue full DynamoDB table scans. In prod with hundreds of thousands of campaigns this becomes prohibitively slow and expensive. The scan pattern is documented as appropriate for admin use (same approach as `admin_compute.py`), but the `limit` default of 200–10000 items means the underlying scan may read far more items than returned. GSI-based pagination should be added once usage scales.

### 3.3 Suspend vs. Rejected Conflation

`moderate_creative(action="suspend")` writes `status="rejected"` to the DDB item (`admin_ad_platform.py:248`). A suspended creative is semantically different from a rejected one: suspension is temporary (pending review or remediation), rejection is final. Advertisers whose creative is suspended would see `status="rejected"` in their own campaign view, which may trigger false-positive rejection notifications from client-side logic that treats `rejected` as permanent.

### 3.4 No Campaign Suspension on Account Suspend

The ticket specifies that suspending an advertiser account should cascade to pause all active campaigns. `moderate_account` calls `review_ad_account` which updates only the account record — it does not query `T.ad_campaigns` to pause active campaigns for that account. A suspended advertiser's campaigns would continue serving ads.

### 3.5 House Ad Fallback Gap

`ad_serving.py:_house_ad_response()` returns a hardcoded `HOUSE_AD` dict (line 30 of `ad_serving.py`). Without a managed house-ads table, platform operators cannot update the house creative, add rotation, or add display rules. This is a low-risk gap operationally (the hardcoded creative works) but limits brand flexibility.

## 4. Proposed Design / Fix

### 4.1 Kill Switch (Highest Priority)

Add a `PlatformAdSettings` item to a platform settings table (or reuse an existing settings pattern):

```python
# app/services/admin_ad_settings.py
def toggle_kill_switch(admin_sub: str, enabled: bool, reason: str) -> dict:
    T.platform_settings.put_item(Item={
        "pk": "PLATFORM_ADS", "sk": "SETTINGS",
        "ads_enabled": enabled, "updated_by": admin_sub,
        "updated_at": now_ts(), "reason": reason,
    })
    audit_event("ad_kill_switch_toggled", admin_sub, None,
                enabled=enabled, reason=reason)
    return {"ads_enabled": enabled}

def get_ad_settings() -> dict:
    item = T.platform_settings.get_item(Key={"pk": "PLATFORM_ADS", "sk": "SETTINGS"}).get("Item")
    return item or {"ads_enabled": True}
```

`ad_serving.serve_ad()` adds at the top: `if not get_ad_settings().get("ads_enabled", True): return _empty_response("ads_globally_disabled")`. Cache the settings read for 60 seconds to avoid a DDB round-trip per impression.

Router endpoint: `POST /ui/admin/ad-platform/kill-switch` with `KillSwitchToggle` body, guarded by `require_root_session`.

### 4.2 Campaign Cascade on Account Suspend

In `moderate_account` after `review_ad_account` succeeds, add:
```python
if action == "suspend":
    active_campaigns = list_all_campaigns(account_id=account_id, status="active", limit=500)
    for c in active_campaigns:
        T.ad_campaigns.update_item(
            Key={"pk": c["pk"], "sk": c["sk"]},
            UpdateExpression="SET #s = :s, updated_at = :u",
            ExpressionAttributeNames={"#s": "status"},
            ExpressionAttributeValues={":s": "paused", ":u": now_ts()},
        )
```

### 4.3 Suspend Status Fix

Add a `"suspended"` status value to `ad_creatives` instead of mapping to `"rejected"`. Update `moderate_creative(action="suspend")` to write `status="suspended"`. The ad serving engine already filters by `approved` status only, so a `suspended` creative is not served.

### 4.4 House Ads (Medium Priority)

Add `app/services/house_ads.py` with `create_house_ad / list_house_ads / get_house_ad / update_house_ad / delete_house_ad`. Add `ad_house_ads` to `scripts/local-ddb-init.py` and `app/core/tables.py`. Modify `ad_serving._house_ad_response()` to call `get_house_ad()` with fallback to the static `HOUSE_AD` dict if the table is empty.

### 4.5 Financial Reports

Add `generate_financial_report(report_type, start_date, end_date, format)` to the service, scanning billing entries within the date range using `month_key` as a filter. For CSV: return a `StreamingResponse` with `text/csv` content type. Endpoint: `GET /ui/admin/ad-platform/reports/{type}`.

### 4.6 `AdminScope.AD_MANAGEMENT`

Add `AD_MANAGEMENT = "ad_management"` to `app/auth/roles.py` `CANONICAL_ADMIN_SCOPES`. Update router auth from `require_admin_or_root` to `require_admin_scope(AdminScope.AD_MANAGEMENT)` for non-destructive endpoints. This allows assigning granular ad-management scope to admins without full ADMIN-level access.

### 4.7 Dev/Prod Parity (SECOPS-007)

All DDB operations use `T.*` handles (DDB Local in dev, real DynamoDB in prod). Kill switch settings would use the same table handle pattern. No AWS-specific code paths. The kill switch `get_ad_settings()` caching should use `functools.lru_cache` with a TTL (or a simple timestamp-based invalidation) — both work identically in dev and prod.

### 5.3 Rollout Order

1. Deploy kill switch endpoint and `serve_ad` check first (fastest path to operational control).
2. Campaign cascade on account suspend.
3. Suspend status fix (non-breaking if done before creative status is relied upon by the UI).
4. House ads managed system.
5. Financial reports.
6. Frontend `AdminAdDashboard.tsx`.

### 5.4 Risks and Open Questions

- **Scan scalability**: Full table scans at `limit=200` are acceptable for early-stage deployment but must be replaced with GSI-based queries before the platform reaches thousands of active accounts.
- **Kill switch caching lag**: If `get_ad_settings()` is cached for 60 seconds, kill switch activation takes up to 60 seconds to propagate to all serving calls. This is acceptable for an emergency stop but should be documented.
- **Rollback**: No DDB schema changes for the kill switch (uses existing platform settings pattern). House ads adds a new table (additive, safe to roll back by disabling the feature).
- **Effort**: Kill switch + cascade fix: S (~1 day). House ads: M (~2 days). Frontend dashboard: L (~3 days). Financial reports: S (~1 day).
