# SEC-019: DynamoDB Expression Built via f-string (Injection Pattern) — Investigation & Implementation Write-up

> ~5 pages. Real code read, citations at `file:line`.

## 1. Summary & Classification

One confirmed instance of a DynamoDB `KeyConditionExpression` constructed with a Python f-string exists in the codebase at `app/services/commerce_entitlement_orchestrator.py:105`. A broader sweep reveals six additional locations where `UpdateExpression` values are constructed via f-string interpolation of field names. While all current instances use internally-controlled strings (not direct user input), the pattern itself is unsafe: DynamoDB's string-based expression API does not sanitize or parameterize injected values, so any future code path that routes user-controlled data into these expressions would be silently exploitable. The correct pattern — using the `boto3.dynamodb.conditions` Key/Attr objects or explicit `ExpressionAttributeNames`/`ExpressionAttributeValues` maps — is already used throughout the rest of the codebase and must be applied uniformly.

- **Type**: security-fix / hardening (injection pattern elimination)
- **Priority**: Medium
- **Status**: Open
- **Area**: `app/services/commerce_entitlement_orchestrator.py`, `app/services/social.py`, `app/services/ad_creative_affiliate.py`, `app/services/messaging_drafts.py`, `app/services/messaging_thread_backfill.py`, `app/services/messaging_threads_store.py`, `app/services/ad_creatives.py`
- **Affected users**: currently no direct user-facing exposure; risk is latent/future
- **Attacker class**: 🌐 any-user (if a user-supplied value ever flows into these expressions)
- **Cross-references**: SECOPS-007 (dev/prod parity — DDB Local behavior is identical to AWS DDB for expression parsing)

## 2. Current-State Investigation (What Exists Today)

### 2.1 Primary instance: `KeyConditionExpression` f-string

`app/services/commerce_entitlement_orchestrator.py:103–116`:

```python
def _load_all_dead_letters(self, *, source_system: str = "shopping_cart") -> List[Dict[str, Any]]:
    try:
        resp = self.dead_letter_table.query(
            KeyConditionExpression=f"pk = '{self._dead_letter_pk(source_system)}'"
        )
```

`_dead_letter_pk(source_system)` at line 30–31 returns `f"ENTITLEMENT_DLQ#{source_system}"`. The `source_system` parameter is passed from callers at lines 119–163, which in turn accept it from callers in router/service layers. Today all callers default to `"shopping_cart"` — an internal constant. However, `process_order_entitlements` at line 167 accepts `source_system: str` as a parameter; if any future API endpoint exposes this parameter to user input, the string lands verbatim inside the `KeyConditionExpression` string.

DynamoDB's string-based `KeyConditionExpression` is a restricted expression language. Injecting a single quote allows breaking out of the literal and constructing arbitrary conditions. For example, if `source_system = "x' OR pk > 'A"` were passed, the expression would become:
```
pk = 'ENTITLEMENT_DLQ#x' OR pk > 'A'
```
This is syntactically valid DynamoDB condition expression syntax — it would widen the query to return all items whose pk sorts after `'A'`, potentially returning dead-letter records for every order in the system.

### 2.2 Secondary instances: `UpdateExpression` field-name interpolation

The remaining six instances involve interpolating a field name (not a value) into an `UpdateExpression` string. This is a different risk profile:

**`app/services/social.py:541,550`**:
```python
UpdateExpression=f"ADD {field} :neg_one"
UpdateExpression=f"SET {field} = :zero"
```
`field` is drawn from the Python list `["follower_count", "following_count"]` — entirely internal. However, `ADD <field> :value` and `SET <field> = :value` where `field` is an arbitrary string could set or increment any attribute on the profile item if `field` were user-controlled.

**`app/services/ad_creative_affiliate.py:273`**:
```python
UpdateExpression=f"SET {field} = if_not_exists({field}, :z) + :one, updated_at = :ts"
```
`field` is drawn from an internal constant in `_increment_config` — not user-accessible.

**`app/services/messaging_drafts.py:204`**:
```python
UpdateExpression=f"SET {set_expr}"
```
`set_expr` is built from a combination of literals and `ExpressionAttributeNames` placeholders (`#text`, `#updated_at`, `#version`) — this is actually the correct parameterized pattern for the _values_ but uses a string format for the expression itself. The risk is that a future change adds user input to `set_expr`.

**`app/services/messaging_thread_backfill.py:121`**:
```python
UpdateExpression=f"SET {MESSAGE_FIELD_THREAD_ID} = :tid, {MESSAGE_FIELD_THREAD_ROOT_ID} = :rid"
```
`MESSAGE_FIELD_THREAD_ID` and `MESSAGE_FIELD_THREAD_ROOT_ID` are module-level string constants — not user-controlled.

**`app/services/messaging_threads_store.py:64`**:
```python
ConditionExpression=f"attribute_not_exists({THREAD_FIELD_ID})"
```
`THREAD_FIELD_ID` is a module-level constant.

**`app/services/ad_creatives.py:159`**:
```python
UpdateExpression=f"SET {url_field} = :u, updated_at = :t"
```
`url_field` is drawn from a small finite set of internal constants (`"thumbnail_url"`, `"preview_url"`, etc.).

### 2.3 The safe pattern (already used elsewhere)

The codebase already uses the correct parameterized pattern in thousands of places. A representative example from `app/services/sessions.py:603–610`:

```python
resp = T.sessions.query(
    KeyConditionExpression=Key("user_sub").eq(user_sub),
    Limit=200,
)
```

For `UpdateExpression` with computed field names, the safe pattern uses `ExpressionAttributeNames`:

```python
T.profile.update_item(
    Key={"user_sub": user_sub},
    UpdateExpression="ADD #cnt :neg_one",
    ExpressionAttributeNames={"#cnt": field},
    ConditionExpression=Attr(field).gt(0),
    ExpressionAttributeValues={":neg_one": -1},
)
```

### 2.4 Dev vs prod behavior

DynamoDB Local (port 8001) and AWS DynamoDB share the same expression parser. Injection payloads that work against Local work identically in production — there is no environment-specific mitigation.

## 3. Gap / Threat Analysis

### 3.1 Current exposure level

All current instances use non-user-derived strings. The risk today is **latent**: the code works correctly because the inputs happen to be safe constants. The danger is:

1. **Accidental escalation**: a developer adds a new API endpoint that passes a query parameter into `source_system` — `_load_all_dead_letters` immediately becomes an injection vector.
2. **Code review blindspot**: the f-string pattern looks unremarkable in a diff; reviewers who are not DynamoDB experts may not flag it.

### 3.2 Exploitation of the `KeyConditionExpression` injection

If `source_system` were user-controlled (e.g., via a `POST /ui/admin/entitlements/dead-letters` endpoint):

**Payload**: `source_system = "' OR attribute_exists(pk) AND pk > '"`  
This yields:
```
pk = 'ENTITLEMENT_DLQ#' OR attribute_exists(pk) AND pk > ''
```
DynamoDB would return all items in the table matching `pk > ''` — effectively a full table scan returning every dead-letter record across all orders, potentially exposing order IDs, user IDs, failure reasons, and cart IDs belonging to other users.

**Payload for data destruction**: In an `UpdateExpression` context with a user-controlled field name, an attacker could target reserved system attributes, delete required keys, or corrupt counts.

### 3.3 Why the fallback in `_load_all_dead_letters` makes it worse

Lines 108–116 implement a fallback: if the `query()` raises an exception, the code falls back to a full `scan()` filtered in Python. An injection payload that causes a DynamoDB `ValidationException` (by producing malformed expression syntax) would silently trigger the scan fallback, which returns all items without any partition key filter — disclosing every dead-letter record.

### 3.4 Blast radius

| Instance | Table affected | Risk if user-controlled |
|----------|---------------|------------------------|
| `commerce_entitlement_orchestrator.py:105` | `dead_letter_table` (entitlements) | Cross-user data read; scan fallback worsens it |
| `social.py:541,550` | `T.profile` | Increment/zero-out any numeric attribute on any user profile |
| `ad_creative_affiliate.py:273` | `T.ad_creative_affiliates` | Increment any attribute on any creative |
| `messaging_drafts.py:204` | draft table | Corrupt/overwrite draft content |
| `messaging_thread_backfill.py:121` | messages table | Corrupt thread ID fields |
| `messaging_threads_store.py:64` | threads table | Bypass `attribute_not_exists` guard |
| `ad_creatives.py:159` | `T.ad_creatives` | Overwrite any URL field |

## 4. Proposed Design / Fix

### 4.1 Fix `_load_all_dead_letters` (primary instance)

`app/services/commerce_entitlement_orchestrator.py:103–116` — replace the f-string with the parameterized Key API:

```python
from boto3.dynamodb.conditions import Key

def _load_all_dead_letters(self, *, source_system: str = "shopping_cart") -> List[Dict[str, Any]]:
    pk_value = self._dead_letter_pk(source_system)
    try:
        resp = self.dead_letter_table.query(
            KeyConditionExpression=Key("pk").eq(pk_value)  # ← parameterized
        )
        items = list(resp.get("Items", []))
    except Exception:
        try:
            scan = self.dead_letter_table.scan()
            items = [
                dict(it) for it in scan.get("Items", [])
                if str(it.get("pk") or "") == pk_value
            ]
        except Exception:
            items = []
    return [dict(it) for it in items]
```

`Key("pk").eq(pk_value)` generates a `ConditionBase` object that boto3 serializes to a parameterized expression with `ExpressionAttributeValues`. There is no string concatenation; quotes in `pk_value` are inert.

### 4.2 Fix `UpdateExpression` field-name interpolations

**`app/services/social.py:539–550`** — use `ExpressionAttributeNames`:

```python
T.profile.update_item(
    Key={"user_sub": user_sub},
    UpdateExpression="ADD #cnt :neg_one",
    ExpressionAttributeNames={"#cnt": field},
    ConditionExpression=Attr(field).gt(0),
    ExpressionAttributeValues={":neg_one": -1},
)
# and for the clamp:
T.profile.update_item(
    Key={"user_sub": user_sub},
    UpdateExpression="SET #cnt = :zero",
    ExpressionAttributeNames={"#cnt": field},
    ExpressionAttributeValues={":zero": 0},
)
```

**`app/services/ad_creative_affiliate.py:271–276`**:

```python
T.ad_creative_affiliates.update_item(
    Key={"pk": _pk(creative_id), "sk": "CONFIG"},
    UpdateExpression="SET #f = if_not_exists(#f, :z) + :one, updated_at = :ts",
    ExpressionAttributeNames={"#f": field},
    ExpressionAttributeValues={":one": 1, ":z": 0, ":ts": now_ts()},
)
```

**`app/services/messaging_thread_backfill.py:119–123`**:

```python
T.messages.update_item(
    Key={...},
    UpdateExpression="SET #tid = :tid, #rid = :rid",
    ExpressionAttributeNames={
        "#tid": MESSAGE_FIELD_THREAD_ID,
        "#rid": MESSAGE_FIELD_THREAD_ROOT_ID,
    },
    ExpressionAttributeValues={":tid": thread_id, ":rid": root_id},
)
```

**`app/services/messaging_threads_store.py:62–65`**:

```python
T.threads.put_item(
    Item={...},
    ConditionExpression="attribute_not_exists(#tid)",
    ExpressionAttributeNames={"#tid": THREAD_FIELD_ID},
)
```

**`app/services/ad_creatives.py:158–160`**:

```python
T.ad_creatives.update_item(
    Key={...},
    UpdateExpression="SET #url = :u, updated_at = :t",
    ExpressionAttributeNames={"#url": url_field},
    ExpressionAttributeValues={":u": url_value, ":t": now_ts()},
)
```

**`app/services/messaging_drafts.py:202–209`** — this is already partially parameterized (uses `#text`, `#updated_at` placeholders in `ExpressionAttributeNames`). The `UpdateExpression=f"SET {set_expr}"` where `set_expr` is a string of those placeholders is low-risk but should be refactored to build the expression without f-string interpolation; replace with a list-join builder:

```python
parts = ["#text = :text", "#updated_at = :updated_at", "#version = #version + :inc", "#ttl_attr = :ttl_attr"]
if client_updated_at is not None:
    parts.append("#client_updated_at = :client_updated_at")
update_expr = "SET " + ", ".join(parts)
T.drafts.update_item(
    Key=...,
    UpdateExpression=update_expr,
    ExpressionAttributeNames=names,
    ExpressionAttributeValues=values,
    ...
)
```

### 4.3 Validation helper for `source_system`

As defense-in-depth, add a validator in `_dead_letter_pk` or its call site to ensure `source_system` only contains safe characters:

```python
import re
_SAFE_SOURCE_SYSTEM = re.compile(r'^[a-z_][a-z0-9_]{0,63}$')

def _dead_letter_pk(source_system: str) -> str:
    if not _SAFE_SOURCE_SYSTEM.match(source_system):
        raise ValueError(f"Invalid source_system value: {source_system!r}")
    return f"ENTITLEMENT_DLQ#{source_system}"
```

### 4.4 Linting enforcement

Add a ruff/pylint rule or a `pre-commit` hook that flags `KeyConditionExpression=f"` or `FilterExpression=f"` patterns:

```bash
# .pre-commit-config.yaml addition:
- repo: local
  hooks:
  - id: no-ddb-fstring
    name: Prohibit f-string DynamoDB expressions
    language: pygrep
    entry: 'KeyConditionExpression\s*=\s*f["\']|FilterExpression\s*=\s*f["\']|UpdateExpression\s*=\s*f["\']|ConditionExpression\s*=\s*f["\']'
    files: \.py$
    args: [--multiline]
```

### 4.5 Dev/Prod parity (SECOPS-007)

All fixes use the `boto3.dynamodb.conditions` Key/Attr API and `ExpressionAttributeNames`/`Values` maps. These work identically against DynamoDB Local (port 8001) and AWS DynamoDB — no dev-mode branching required.
