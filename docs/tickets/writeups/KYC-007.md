# KYC-007: Enhanced Document Signing for KYC — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

KYC-007 adds a structured template library for KYC-specific consent and declaration documents, replacing ad-hoc per-case signature packet creation with a versioned, auto-populated system. It also introduces witness co-signing for high-risk cases and a notary stamp field type. The underlying signature packet infrastructure already exists at `app/routers/signature_packets.py` and `app/services/signature_packet_store.py`; this ticket builds a KYC-specific layer on top of it.

A distinct but related service, `app/services/kyc_document_templates.py`, exists and implements KYC-017 (PDF template library with admin upload and `{{placeholder}}` rendering). KYC-007 is complementary — it concerns the five hard-coded field-set templates (terms of service, AML declaration, PEP declaration, tax compliance, data consent) with auto-population from user profiles, not admin-uploaded PDFs. Both are needed for a complete KYC signing workflow.

- **Type**: Feature — consent/compliance workflow enhancement
- **Priority**: Medium
- **Status**: Partially implemented. The KYC-017 PDF template service exists (`app/services/kyc_document_templates.py`). The KYC-007 field-set template service (`app/services/kyc_signature_templates.py`) is not yet present.
- **Owning area**: KYC / Document Signing
- **User persona**: Applicants completing the KYC flow; compliance officers maintaining standardized consent language; KYC reviewers overseeing high-risk witness co-signing
- **Cross-references**: KYC-001 (admin case detail page), KYC-009 (intake_profile determines required templates), KYC-017 (PDF template library — complementary feature), signature packets system (`app/routers/signature_packets.py`)
- **SECOPS-007 parity**: All template definitions are in-process Python constants; no OCR or external HTTP in dev. Notary stamp images stored in S3 (mock via moto in dev).

## 3. Gap / Threat Analysis

### 3.1 Compliance requirements

**Inconsistent consent language**: Without the template library, each case could be submitted with whatever document the user attaches. AML and GDPR require that consent forms use standardized, legally-reviewed language. Template versioning (with re-signing triggers when the version changes) ensures new legal language propagates to in-flight cases.

**PEP declaration gap**: The `pep_check` screening result from KYC-006 produces a potential match but there is no structured user declaration confirming or denying PEP status. The `pep_declaration` template (with `is_pep` checkbox and conditional `pep_details` field) closes this gap.

**High-risk witness requirement**: For `intake_profile="high_risk"` cases, regulatory best practice requires a second qualified person to co-witness the signing. Without witness co-signing support, the existing system cannot enforce this for high-risk cases.

### 3.2 Feature requirements detail

**Auto-population**: The `auto_populate` hint on each field specifies which profile field provides the value. For example, `full_name` → `display_name`, `email` → `email`, `address` → `mailing_address`. At packet creation time, `auto_populate_fields()` reads the user profile and calls `upsert_packet_field()` for each auto-populated field. Fields that have no profile value (e.g., a user without a mailing address) must be left blank but not error — the signer fills them in manually.

**Idempotent packet creation**: Calling `create-packets` twice for the same case must return the same packet IDs. Implementation must check whether packets for each template type already exist on the case before creating new ones; existing packets should be returned as-is.

**Version migration**: When `template.version` changes (e.g., from `"2026-05-v1"` to `"2026-06-v1"`), cases with signed packets using the old version need to re-sign. The `check_version_migration()` endpoint compares the version stored on the packet against the current constant. The admin can then require re-signing via `migrate_template()`, which invalidates the old packet and creates a new one from the updated template.

**Witness ordering**: The witness must sign *after* the applicant completes signing. The `add_witness_signer()` call should check that the packet is not already completed by the applicant before adding the witness (error 400 `kyc_packet_already_signed`).

**Notary stamp field**: Requires adding `notary_stamp` to the set of valid field types in `app/services/signature_packet_store.py`. The stamp stores `stamp_image_ref` (S3 key), `stamp_number`, `stamp_expiry`, `stamped_at`, and `stamped_by`. In dev mode, the S3 ref resolves to `/mock/s3/...` using the moto-backed bucket.

### 3.3 Edge cases

- **Conditional fields**: `pep_details` in the PEP declaration has `conditional_on="is_pep"`. The frontend must show/hide this field based on the checkbox value. The backend stores the field regardless; the conditional is a UI concern.
- **Profile fields at packet creation time**: Profile data is captured at packet creation, not at signing time. If the user updates their address after creating packets but before signing, the auto-populated value is stale. This is acceptable and documented — the signer reviews the pre-filled value.
- **Multiple cases for same user**: A user may have multiple KYC cases (e.g., after expiry and re-application). Template status is per-case; earlier cases' packets are independent of later cases.
- **Witness field visibility**: Witness-role fields on the packet should not be visible to the applicant signer. The `signer` attribute on witness fields determines which signer sees them; the frontend filters by `signer="applicant"` for the user view.

## 4. Proposed Design / Fix

### 4.1 Template service structure

`app/services/kyc_signature_templates.py` should define:

```python
KYC_TEMPLATE_TYPES: dict[str, dict] = {
    "terms_of_service": { "version": "2026-05-v1", "required_for": ["standard", "enhanced", "high_risk"], ... },
    "aml_declaration": { "version": "2026-05-v1", "required_for": ["standard", "enhanced", "high_risk"], ... },
    "pep_declaration": { "version": "2026-05-v1", "required_for": ["enhanced", "high_risk"], ... },
    "tax_compliance": { "version": "2026-05-v1", "required_for": ["enhanced", "high_risk"], ... },
    "data_consent": { "version": "2026-05-v1", "required_for": ["standard", "enhanced", "high_risk"], ... },
}
```

The `KycSignatureTemplateService.create_packets_for_case()` method:
1. Reads `case["intake_profile"]` to determine required templates
2. For each required template, checks whether a packet already exists on `case["signature"]["packets"]`
3. If not, calls `create_draft_packet()` from `app/services/signature_packet_store.py:91`
4. For each auto-populate field, calls `upsert_packet_field()` at line 133 with the profile value
5. Appends `{template_type, packet_id, version}` to `case["signature"]["packets"]`
6. Returns the list of created/existing packet summaries

### 4.2 Case storage for template packets

The existing `case["signature"]` dict (already used by `create_or_link_signature_packet()` at `kyc_cases.py:1206`) stores a single `packet_id`. This must be extended to store a list of template packets. The case META update should use `list_append` or SET on a new `signature.template_packets` attribute to avoid breaking the existing single-packet check in `_signature_status_for_case()` at line 184.

### 4.3 Witness co-signing flow

`add_witness_signer()` adds a second signer record to the `signature_packet_signers` table:
1. Verify `case["intake_profile"] == "high_risk"` — else 400
2. Verify caller has `ADMIN` or `ROOT` role
3. Verify packet exists and applicant has not yet signed (else 400)
4. Verify no witness already exists for this packet (else 409)
5. Call the existing signer-addition logic on `signature_packets` router
6. Add four witness fields (`witness_name`, `witness_role`, `witness_signature`, `witness_date`) with `signer="witness"` attribute

### 4.4 Dev/prod parity (SECOPS-007)

| Aspect | Dev | Prod |
|--------|-----|------|
| Template definitions | In-process Python constants | Same constants |
| Signature packets DDB | DynamoDB Local | AWS DynamoDB |
| S3 for notary stamp | moto in-process S3 | AWS S3 |
| Notary stamp images | `/mock/s3/{bucket}/{key}` URLs | Pre-signed S3 URLs |
| Feature flags | `KYC_TEMPLATE_SIGNING_ENABLED=true` in `.env.local.example` | Enabled via env |

Feature flags default to `true` in `.env.local.example` so E2E tests run without any additional configuration.

### 4.5 Relationship with KYC-017

KYC-017 (`app/services/kyc_document_templates.py`) allows admins to upload custom PDF templates. KYC-007 provides five hard-coded consent forms. In practice, a case may need both: KYC-007 for the standard compliance declarations and KYC-017 for jurisdiction-specific custom forms. The two systems use independent storage (`signature.template_packets` vs `case["documents"]`) and should not conflict.

### 5.5 Effort and order

- **Effort**: M (10-14 days). Template definitions and auto-population are straightforward; witness co-signing requires careful integration with the existing multi-signer packet system.
- **Order**: Merge after KYC-001. Independent of KYC-006 and KYC-008. Blocks KYC-017 integration (KYC-017 already exists independently but the KYC-007 field-set approach should be consolidated before adding more template complexity).
