# KYC-009: Tiered Verification Levels — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

KYC-009 introduces a five-tier user verification model (0=Unverified to 4=Institutional) that gates platform features based on progressive identity assurance. It adds the `kyc_tier` field to user profiles, a `KycTiersService` with automatic tier evaluation, a `require_kyc_tier()` FastAPI dependency for endpoint-level gating, and a dedicated `/v1/kyc/tiers` router. The system is fully implemented.

- **Type**: Feature — progressive access control / regulatory compliance
- **Priority**: Critical — directly affects which features users can access without a KYC case
- **Status**: Implemented. `app/services/kyc_tiers.py` and `app/routers/kyc_tiers.py` both exist and are registered at `app/main.py:570`. `require_kyc_tier()` exists in `app/auth/deps.py:311`.
- **Owning area**: KYC / Auth / Feature gating
- **User persona**: All users (tier progression as they verify), compliance officers (tier distribution reporting), root admins (tier override for exceptional cases)
- **Cross-references**: KYC-008 (risk score triggers tier evaluation on approval), KYC-001 (admin dashboard shows tier), KYC-011 (tier changes trigger webhooks), KYC-013 (user self-service portal shows tier and requirements), KYC-015 (Tier 4 requires business KYC)
- **SECOPS-007 parity**: All tier logic reads from DDB; no external HTTP. In dev, `KYC_TIER_GATING_ENABLED=true` enables enforcement. With it set to `false`, `get_user_kyc_tier()` returns `KYC_TIER_MAX` (4) — all users pass every tier check.

## 2. Current-State Investigation (what exists today)

### 2.1 Tier service

`app/services/kyc_tiers.py` (256 lines) is fully implemented:

**Constants** (lines 11–25):
```python
KYC_TIER_NAMES = {0: "Unverified", 1: "Basic", 2: "ID Verified", 3: "Enhanced", 4: "Institutional"}
TIER_REQUIREMENTS = {
    1: {"email_verified", "phone_verified"},
    2: {"tier_1", "kyc_case_approved"},
    3: {"tier_2", "proof_of_address", "verification_call", "questionnaire_completed"},
    4: {"tier_3", "business_kyc_approved", "api_access_approved"},
}
```

**`get_user_kyc_tier()`** (lines 28–35): reads `T.users.get_item(Key={"user_sub": user_sub})` and returns `int(item.get("kyc_tier", 0))`. Critical: when `S.kyc_tier_gating_enabled` is `False`, returns `KYC_TIER_MAX` so all gates pass — this is the dev-mode escape hatch.

**Table key discrepancy**: The service accesses `T.users` with `Key={"user_sub": user_sub}`. The ticket spec and `kyc_cases.py` use `Key={"pk": f"USER#{user_sub}", "sk": "PROFILE"}`. The actual users table key schema must be verified against `scripts/local-ddb-init.py`. If the users table uses composite PK+SK, then `Key={"user_sub": user_sub}` will silently miss items. This is a **potential data access bug** that must be audited.

**`check_tier_requirements()`** (lines 63–143): checks email_verified, phone_verified, approved KYC case existence, proof_of_address file type in the approved case's files array, questionnaire response, and verification call completion flag. Tier 4 requirements (`business_kyc_approved`, `api_access_approved`) are not yet checked from real data — they fall through to `unmet.update(...)` without a real data source.

**`upgrade_tier()`** (lines 146–214): performs the DDB update with `list_append` on `kyc_tier_history`, fires `audit_event()` and `write_alert()` for the user. The audit event uses `target_user_sub=user_sub` for admin overrides vs. `actor_sub=user_sub` for auto-upgrades.

**`auto_evaluate_tier()`** (lines 217–234): iterates from `current_tier + 1` to `KYC_TIER_MAX`, calling `check_tier_requirements()` for each. Stops at the first unmet tier — cannot skip tiers. Called after email verification, phone verification, and KYC case approval.

**`list_users_by_tier()`** (lines 237–255): queries `IndexName="ByKycTier"` on `T.users`. The query uses a string `KeyConditionExpression` instead of `boto3.dynamodb.conditions.Key` — this is a stylistic inconsistency but works.

### 2.2 Router

`app/routers/kyc_tiers.py` (76 lines) provides six endpoints under `/v1/kyc/tiers`:
- `GET /me` — user's own tier details
- `GET /me/requirements/{target_tier}` — requirement checklist
- `POST /me/evaluate` — trigger auto-evaluation
- `GET /admin/{user_sub}` — admin view of any user's tier (`require_root_session`)
- `POST /admin/{user_sub}/override` — admin tier override
- `GET /admin/by-tier/{tier}` — list users in a tier

All admin endpoints use `require_root_session` from `app/auth/deps.py:273`. User endpoints use `require_ui_session`.

### 2.3 `require_kyc_tier` dependency

`app/auth/deps.py:311` implements the dependency factory:

```python
def require_kyc_tier(minimum_tier: int):
    async def _check(request: Request):
        user = await get_authenticated_user(request)
        if not S.kyc_tier_gating_enabled:
            return user
        tier = get_user_kyc_tier(user.sub)
        if tier < minimum_tier:
            raise HTTPException(status_code=403, detail={
                "code": "kyc_tier_insufficient",
                "message": f"This action requires {KYC_TIER_NAMES.get(minimum_tier, ...)} verification",
                "current_tier": tier,
                "required_tier": minimum_tier,
                "upgrade_url": "/kyc",
            })
        return user
    return _check
```

The `upgrade_url: "/kyc"` in the 403 response gives frontends a direct link for the user to resolve the blockage.

### 2.4 Feature gating — what is and isn't wired

The dependency exists but its application to existing endpoints is the main outstanding work. The ticket spec calls for adding `require_kyc_tier(N)` to:
- Messaging DM/group creation: Tier 1+
- Newsfeed post/comment: Tier 1+
- Billing payment methods/deposits: Tier 2+
- Broadcast session creation: Tier 3+
- API key creation: Tier 4
- Webhook creation: Tier 4

Whether these have been applied needs verification in each router file. This wiring is the Phase 3 implementation work.

### 2.5 DDB schema change required

The `ByKycTier` GSI on the `users` table must be declared in `scripts/local-ddb-init.py` with `attr_types={"kyc_tier": "N", "kyc_tier_updated_at": "N"}`. Without it, the `list_users_by_tier()` query on the `ByKycTier` GSI will fail with a DynamoDB `ValidationException`.

## 3. Gap / Threat Analysis

### 3.1 Regulatory and business value

Progressive verification addresses abandonment from requiring full KYC upfront. A user can browse content at Tier 0, send messages after verifying email+phone (Tier 1), and make purchases after completing ID verification (Tier 2). This is standard for financial platforms and aligns with the FATF's proportionality principle.

### 3.2 Critical: users table key schema

`get_user_kyc_tier()` uses `Key={"user_sub": user_sub}` while `kyc_risk_scoring._compute_country_risk()` uses `Key={"pk": f"USER#{user_sub}", "sk": "PROFILE"}`. The discrepancy is material — if the table uses `pk`/`sk` keys, the tier service's reads silently return empty items and everyone defaults to Tier 0. This must be verified against the actual table definition in `scripts/local-ddb-init.py` and corrected to use the canonical key schema.

### 3.3 Tier downgrade behavior

The service supports downgrade (passing `new_tier < current_tier` to `upgrade_tier()` is allowed). The `direction = "upgraded" if new_tier > current_tier else "downgraded"` logic at `kyc_tiers.py:200` correctly emits `kyc.tier.downgraded` alert. However, automatic downgrade is not implemented — if a KYC case expires (KYC-016 territory), the tier should be re-evaluated downward. Without KYC-016, tier downgrades are admin-only via the override endpoint.

### 3.4 Race condition in `auto_evaluate_tier()`

The evaluate + upgrade flow is not atomic. Two concurrent calls for the same user could both read `current_tier=0`, both evaluate Tier 1 as eligible, and both call `upgrade_tier()`. The second call would write a duplicate history entry (`from_tier=0 → to_tier=1`) but the final `kyc_tier=1` would be correct. The history duplication is cosmetically undesirable but functionally harmless.

### 3.5 Tier 4 requirements not yet data-backed

`check_tier_requirements()` checks Tier 4 with hardcoded `unmet.update({"business_kyc_approved", "api_access_approved"} - met)` — these conditions are never added to `met` because there's no actual check. KYC-015 (business KYB) must implement the `business_kyc_approved` source; API access approval needs a separate approval workflow. Until then, Tier 4 is admin-override-only.

### 3.6 Feature gating coverage gaps

Without verifying which endpoints have `require_kyc_tier(N)` applied, platform features that should be gated remain open to Tier 0 users. This creates a period where users who have not verified their identity can perform actions that AML regulations require identity verification for (sending money, buying content). The rollout plan must explicitly gate each endpoint.

### 3.7 `KYC_TIER_GATING_ENABLED=false` behavior

When disabled, `get_user_kyc_tier()` returns `KYC_TIER_MAX` (4). This means all users pass all tier checks regardless of their actual tier. This is the correct dev escape hatch behavior and allows E2E tests for features that are gated to run without setting up full KYC verification flows.

## 4. Proposed Design / Fix

### 4.1 Fix users table key schema

Audit `scripts/local-ddb-init.py` for the users table key definition. If it uses `pk`/`sk`:

```python
# In app/services/kyc_tiers.py - correct the GetItem calls:
item = T.users.get_item(Key={"pk": f"USER#{user_sub}", "sk": "PROFILE"}).get("Item")
```

Apply same fix to `upgrade_tier()` (UpdateItem key) and `list_users_by_tier()` (GSI query key condition).

### 4.2 Feature gating rollout (Phase 3)

Apply `require_kyc_tier` to endpoints in priority order:

```python
# app/routers/billing.py — highest AML risk
@router.post("/billing/wallet/deposit")
async def deposit_wallet(
    body: DepositRequest,
    ctx = Depends(require_ui_session),
    _tier = Depends(require_kyc_tier(2)),
):
    ...

# app/routers/messaging.py — user engagement
@router.post("/messaging/conversations/dm")
async def create_dm(
    body: CreateDmRequest,
    ctx = Depends(require_ui_session),
    _tier = Depends(require_kyc_tier(1)),
):
    ...
```

The `_tier` convention (underscore prefix) signals the dependency result is unused — it's purely a guard.

### 4.3 Auto-upgrade trigger wiring

Three trigger points must be connected to `auto_evaluate_tier()`:

1. After email verification in `app/routers/register.py` (or wherever `email_verified` is set)
2. After phone MFA setup in `app/routers/mfa_devices.py`
3. After `apply_admin_decision(decision="approve")` in `app/services/kyc_cases.py:534`

```python
# In apply_admin_decision() at kyc_cases.py:534, after setting status="approved":
if decision == "approve":
    try:
        from app.services.kyc_tiers import auto_evaluate_tier
        auto_evaluate_tier(case["user_sub"])
    except Exception:
        logger.exception("Tier auto-evaluate failed after case approval")
```

### 4.4 ByKycTier GSI declaration

```python
# In scripts/local-ddb-init.py, add to users table GSI list:
{"index_name": "ByKycTier", "partition_key": "kyc_tier", "sort_key": "kyc_tier_updated_at"},
# And in attr_types:
attr_types={"kyc_tier": "N", "kyc_tier_updated_at": "N"},
```

### 4.5 Dev/prod parity (SECOPS-007)

| Aspect | Dev | Prod |
|--------|-----|------|
| Tier gating | `KYC_TIER_GATING_ENABLED=true` (enforced) | Same |
| Tier bypass | Set `KYC_TIER_GATING_ENABLED=false` | Never disable in prod |
| DDB | Local port 8001, `users` table | AWS DynamoDB |
| Tier 4 requirements | Admin-override only (KYC-015 not implemented) | Same until KYC-015 merges |
| Alert delivery | `write_alert()` → DDB alerts table | Same |

For E2E tests that need a user to be at Tier 2 without running the full KYC flow, use `admin_override_tier()` via the root session to set `tier=2` in `beforeAll`. This is the canonical test pattern.

## 5. Testing, Verification & Rollout

### 5.1 Pytest unit tests (`tests/test_kyc_tiers.py`)

- `test_get_user_tier_default_zero`: Fresh user with no `kyc_tier` field → returns 0
- `test_get_user_tier_gating_disabled`: `S.kyc_tier_gating_enabled=False` → returns 4 regardless of DDB value
- `test_check_requirements_tier1_unmet`: User with `email_verified=False` → returns `unmet=["email_verified", "phone_verified"]`, `eligible=False`
- `test_check_requirements_tier1_met`: User with both flags true → `eligible=True` for tier 1
- `test_auto_evaluate_upgrades_tier1`: Seed user with `email_verified=True`, `phone_verified=True` → `auto_evaluate_tier()` upgrades to tier 1, writes history entry
- `test_auto_evaluate_no_skip`: User at tier 0 with tier 2 requirements met but not tier 1 → stays at 0 (can't skip)
- `test_upgrade_tier_writes_history`: Upgrade from 0 to 2 → history entry `{from_tier: 0, to_tier: 2, reason, actor_sub}`
- `test_upgrade_tier_fires_alert`: `write_alert()` called with `event="kyc.tier.upgraded"`
- `test_upgrade_tier_fires_audit`: `audit_event("kyc.tier.changed", ...)` called
- `test_require_kyc_tier_passes`: User at tier 2, endpoint requires tier 1 → dependency passes
- `test_require_kyc_tier_blocks`: User at tier 1, endpoint requires tier 2 → HTTPException 403 with `kyc_tier_insufficient`
- `test_downgrade_fires_downgraded_alert`: `upgrade_tier(new_tier=1)` on user at tier 2 → `write_alert(event="kyc.tier.downgraded")`

### 5.2 Playwright E2E (`frontend/e2e/kyc-tiers.spec.ts`)

Sections 182–186. Key auth patterns:

```typescript
// Section 184.1: admin override
await rootPage.request.post(`/v1/kyc/tiers/admin/${aliceSub}/override`, {
  headers: { "x-csrf-token": sessions.root.csrf_token },
  data: { tier: 3, reason: "Manual verification completed offline" },

const tierResp = await rootPage.request.get(`/v1/kyc/tiers/admin/${aliceSub}`);
expect((await tierResp.json()).current_tier).toBe(3);

// Section 185: feature gating
const dmResp = await alicePage.request.post("/ui/messaging/conversations/dm", {
  headers: { "x-csrf-token": sessions.alice.csrf_token },
  data: { recipient_sub: bobSub },
});
// Alice is at tier 0 in fresh E2E → should get 403
expect(dmResp.status()).toBe(403);

expect(body.detail.code).toBe("kyc_tier_insufficient");
expect(body.detail.upgrade_url).toBe("/kyc");
```

Note: existing messaging E2E tests pass because `KYC_TIER_GATING_ENABLED=true` with existing sessions at tier 0 would block them. The messaging tests must either be updated to pre-set Alice and Bob to tier 1+ in `beforeAll`, or `KYC_TIER_GATING_ENABLED` must default to `false` in test environments (via `.env.local`). The `get_user_kyc_tier()` gating-disabled path returns `KYC_TIER_MAX=4`, so setting `KYC_TIER_GATING_ENABLED=false` in `.env.local` for tests is the least-disruptive approach while the gating rollout is completed incrementally.

### 5.3 Manual QA steps

1. `just restart` to reset DDB
2. Log in as Alice (Tier 0 by default)
3. Attempt to create a DM → verify 403 with `kyc_tier_insufficient`
4. As Root, override Alice to Tier 1 via `POST /v1/kyc/tiers/admin/{alice_sub}/override`
5. Alice creates DM → succeeds
6. Navigate to `/kyc/tiers` → verify tier badge shows "Basic"
7. Submit a KYC case for Alice, approve as Root → verify auto-evaluation upgrades to Tier 2
8. Check alert center → verify "Verification level upgraded to ID Verified" alert

### 5.4 Rollout

**Phase 1** (backend only, no gating): Deploy tier service, router, and `require_kyc_tier` dependency. No endpoints gated yet. Tier evaluation fires on KYC approval.

**Phase 2** (billing gating): Add `require_kyc_tier(2)` to `deposit_wallet` and `create_payment_method`. Lowest abandonment risk; users who need to pay have a KYC case already.

**Phase 3** (messaging gating): Add `require_kyc_tier(1)` to DM and group creation. Higher user impact; requires comms campaign about the new verification requirement.

**Phase 4** (API key and webhook gating): Tier 4 only. Very small user segment.

### 5.5 Rollback

Set `KYC_TIER_GATING_ENABLED=false` — instantly removes all tier enforcement without code deploy. All `require_kyc_tier()` dependencies return immediately. Tier data in DDB is preserved.

### 5.6 Effort and order

- **Effort**: M (10-14 days). Core implemented; key remaining work is users table key schema audit/fix, feature gating application to ~10 endpoints, auto-evaluate trigger wiring, and `ByKycTier` GSI declaration.
- **Order**: Merge after KYC-001 and KYC-008 (risk score triggers tier evaluation). Must merge before KYC-011 (tier change webhooks) and KYC-013 (user self-service portal).
