# SEC-010: Realtime Stream Authorization (SSE/WS IDOR) — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

Four SSE/WebSocket stream endpoints authenticate the requesting user but do not verify the user is a **participant or owner of the specific channel** being subscribed to. This is a real-time Insecure Direct Object Reference (IDOR): any authenticated user can subscribe to another user's private broadcast events, private party events, or broadcast chat stream. The chat stream vulnerability is compounded by a second bug: `_chat_msg_out` is called without a `viewer_user_id`, which means per-viewer redaction rules (locked message text, expired message suppression) are bypassed and content is delivered in clear to any subscriber.

A fourth related issue — `mint_ws_token`/`verify_ws_token` in `app/core/crypto.py` (lines 35-61) is minted and exposed via `GET /ui/ws_token` (`app/routers/misc.py:13-15`) but **never verified** in any WS handshake — means the WS token mechanism is dead code that provides no access control.

- **Type**: security-fix (critical)
- **Priority/Severity**: Critical
- **Status**: Open
- **Owning area**: `app/routers/broadcast.py`, `app/routers/watch_party.py`, `app/routers/misc.py`, `app/core/crypto.py`
- **Attacker class**: 🌐 any authenticated user
- **Cross-references**: [[SEC-005]] (IDOR/broken access control), [[BCAST-004]] (viewer count/health), [[BCAST-015]] (locked/expiry chat messages)

## 2. Current-State Investigation (what exists today)

### 2.1 Broadcast event stream — no viewer access check (`app/routers/broadcast.py:717-737`)

```python
717  @router.get("/sessions/{session_id}/stream")
718  async def broadcast_event_stream_route(session_id: str, ctx: dict = Depends(_ctx)):
719      """SSE stream for real-time broadcast events (viewer count, health updates)."""
720      _ = ctx
721      _ = get_session(session_id)  # 404 if session doesn't exist
722      q = broadcast_sse_subscribe(session_id)
```

`_ctx` resolves the session via `require_ui_session` — the user is authenticated. But line 721 only checks that the broadcast session exists; it does not check whether the authenticated user (`ctx["user_sub"]`) has viewer access to that session. The `check_viewer_access` function (imported and used elsewhere in the file, e.g., lines 500-501 and 584-585 for the playback endpoints) is **not called here**.

Any authenticated user can subscribe to any broadcast session's SSE stream, receiving real-time viewer-count updates, health events, and any other operational events published to that channel. For private/subscription-gated broadcasts this leaks audience data.

**Bug 2 (content redaction bypass)**: `_chat_msg_out` is defined in `app/services/broadcast_chat_store.py:344`:

When `viewer_user_id=None`:
- `is_sender = False` (line 354)
- Expired messages: `not is_sender = True` → `text=None, expired=True` — **correctly redacted** because the viewer is not the sender.
- **Locked messages**: `is_unlocked = False or (None is not None and …) = False` → `text=None` — **also correctly redacted** in this path.

However, the IDOR remains: a non-paying user who never subscribed to the broadcast receives chat messages in real time, including expiry/lock metadata (prices, `lock_description`), even though text is nulled. More critically, if `viewer_user_id` were passed incorrectly (e.g., as `""` empty string), `is_sender = ("" == sender_id)` could accidentally match senders with empty IDs and leak locked text. And the IDOR means a user who should not see the stream at all gets the entire event feed.

The SSE poll loop at lines 1792-1818 streams messages as they arrive via DDB polling, delivering every new message to every subscriber with no access filtering per message.

### 2.3 Watch-party stream — no participant check (`app/routers/watch_party.py:262-281`)

```python
262  @router.get("/{party_id}/stream")
263  async def party_stream_route(party_id: str, session: dict = Depends(require_ui_session)):
264      """SSE stream for real-time party events."""
265      _ = get_party(party_id)  # 404 if not exists
266      q = broadcast_sse_subscribe(party_id)
```

`get_party` only confirms existence; no check that `session["user_sub"]` is a member of the party. A private watch party (accessible only to invited participants) has its real-time events — participant join/leave, playback state changes, chat — exposed to any authenticated user who guesses or enumerates the `party_id`.

The `list_participants` service is imported at line 38 and used in `GET /{party_id}/participants` (line 201-204). It could be called here to verify membership. It is not.

### 2.4 Dead WS token mechanism (`app/routers/misc.py:13-15`, `app/core/crypto.py:35-61`)

```python
# app/routers/misc.py
13  @router.get("/ui/ws_token")
14  async def ui_ws_token(ctx=Depends(require_ui_session)):
15      return {"token": mint_ws_token(ctx["user_sub"], ttl_seconds=120)}
```

`mint_ws_token` produces a signed HMAC token containing `user_sub` and `exp`. `verify_ws_token` in `app/core/crypto.py:44-61` correctly validates it. But **no WS endpoint calls `verify_ws_token`**. The token is minted, handed to the frontend, and silently discarded — the WS handshake is authorized by `require_ui_session` (cookie/Bearer) alone. The dead token mechanism is misleading: it implies a WS auth system exists when it does not, and creates a surface that could be incorrectly relied upon in future code.

### 2.5 Dev vs. prod

All bugs are present identically in dev and prod. No dev flag gates SSE authorization. In dev the broadcast sessions are created by E2E tests and are already accessible to any test user.

## 3. Gap / Threat Analysis

### Scenario A — private broadcast event leak

Creator sets up a subscription-gated broadcast (requires paid subscription to view). Any authenticated free-tier user calls `GET /broadcast/sessions/{id}/stream` with the session ID. They receive real-time viewer-count statistics, health events (bitrate, buffering), and any operational metadata the broadcaster publishes. This leaks audience size and stream health to competitors or data scrapers.

### Scenario B — locked/paid chat content via stream IDOR

A broadcast uses locked chat messages (pay-per-view content). Attacker subscribes to `GET /broadcast/sessions/{id}/chat/stream` without purchasing access. They receive all chat messages in the SSE stream. While `text=None` for locked messages (because `viewer_user_id=None` causes `is_unlocked=False`), they receive `lock_description`, `lock_price_cents`, and the identity of who sent which locked messages — enough to infer content and relationships. If there is any future code path where `viewer_user_id=""` is passed (rather than `None`), all locked text leaks immediately.

### Scenario C — private watch party reconnaissance

User A creates a private watch party for 5 friends. Attacker enumerates or guesses the `party_id` (UUIDs are large but party IDs may be shorter or sequential depending on implementation). Attacker subscribes to `GET /watch-party/{id}/stream` and receives real-time events: who joined, who left, current playback position, chat messages, and co-host grants. This constitutes a surveillance/stalking capability against private social activities.

### Scenario D — dead WS token → future regression

A developer sees `GET /ui/ws_token` in the API spec, assumes WS endpoints require a token, and does not add standard auth to a new WS endpoint, believing the token mechanism provides coverage. The dead code creates a false sense of security.

**Blast radius**: all paid/subscription/private broadcast and watch-party content is accessible to any free authenticated user. In a monetized platform, this is a revenue bypass as well as a privacy violation.

## 4. Proposed Design / Fix

### 4.1 Broadcast event stream — enforce `check_viewer_access`

**`app/routers/broadcast.py:717-737`** — add the same viewer-access check used by the playback endpoint (lines 500-505):

```python
@router.get("/sessions/{session_id}/stream")
async def broadcast_event_stream_route(session_id: str, ctx: dict = Depends(_ctx)):
    session = get_session(session_id)  # 404 if not exists
    from app.services.broadcast_privacy import check_viewer_access
    check_viewer_access(
        session_id=session_id,
        user_sub=ctx["user_sub"],
        creator_id=session.created_by,
        visibility=session.visibility,
    )   # raises HTTPException(403) if not authorized
    q = broadcast_sse_subscribe(session_id)
    …
```

`check_viewer_access` already implements subscription entitlement checks (import confirmed at lines 500 and 584). No new service code needed.

### 4.2 Broadcast chat stream — enforce access check and pass `viewer_user_id`

**`app/routers/broadcast.py:1763-1816`**:

```python
@router.get("/sessions/{session_id}/chat/stream")
async def broadcast_chat_stream_route(session_id, after, poll_ms, ctx=Depends(_ctx)):
    session = get_session(session_id)
    from app.services.broadcast_privacy import check_viewer_access
    check_viewer_access(…, user_sub=ctx["user_sub"], …)  # 403 if not authorized
    …
    async def gen():
        …
        for msg in messages:
            …
            out = _chat_msg_out(msg, viewer_user_id=ctx["user_sub"])  # ← pass user_sub
```

The `viewer_user_id=ctx["user_sub"]` change ensures:
- Locked messages: `is_unlocked = (user_sub in unlocked_by)` — correct per-viewer check.
- Expired messages: `is_sender = (user_sub == sender_id)` — senders see their own expired content.

`ctx` is already in scope; no new dependencies needed.

### 4.3 Watch-party stream — enforce participant membership

**`app/routers/watch_party.py:262-281`** — add participant check:

```python
@router.get("/{party_id}/stream")
async def party_stream_route(party_id: str, session: dict = Depends(require_ui_session)):
    get_party(party_id)  # 404 if not exists
    user_sub = session["user_sub"]
    participants = list_participants(party_id)
    if not any(p.get("user_sub") == user_sub for p in participants):
        raise HTTPException(status_code=403, detail="Not a party participant")
    q = broadcast_sse_subscribe(party_id)
    …
```

`list_participants` is already imported (line 38) and used elsewhere in the file.

For large parties, cache the participant check in the SSE context so repeated reconnects don't re-query DynamoDB on every message.

### 4.4 WS token — wire or remove

**Option A — wire it**: add `verify_ws_token` to the WS handshake dependencies. Any WS endpoint that currently uses `Depends(require_ui_session)` would additionally require a valid `?token=` query parameter:

```python
@router.websocket("/{session_id}/ws")
async def ws_endpoint(ws: WebSocket, token: str = Query(...)):
    payload = verify_ws_token(token)
    if not payload:
        await ws.close(code=4001)
        return
    user_sub = payload["user_sub"]
    …
```

Short-lived tokens (120s) are suitable for WS handshakes; the frontend fetches `GET /ui/ws_token` immediately before connecting.

**Option B — remove it**: delete `app/routers/misc.py:13-15` and the `mint_ws_token`/`verify_ws_token` functions from `app/core/crypto.py`. All WS endpoints use `require_ui_session` (cookie/Bearer) exclusively, which is already working.

**Recommendation**: Option B (remove) unless there is an active plan to use WS tokens (e.g., to support third-party WS clients without cookies). Leaving dead security code in place invites confusion.

### 4.5 Dev/Prod parity (SECOPS-007)

All fixes are pure logic changes — `check_viewer_access` calls and membership lookups use DynamoDB (moto in dev, AWS in prod). No new AWS service dependencies. E2E tests in dev can seed a restricted broadcast session and verify the 403 response. Same code path in both environments.

- `test_mint_verify_roundtrip()` — mint a token; verify it; assert `user_sub` matches.
- `test_expired_token_rejected()` — mint with `ttl_seconds=0`; verify; assert `None`.

### Playwright E2E

`frontend/e2e/sec-010-stream-idor.spec.ts`:
- Alice creates a private broadcast; Bob (not a subscriber) attempts `GET /broadcast/sessions/{id}/stream` — assert the EventSource connection fails with 403.
- Alice sends a locked chat message; Bob connects to the chat stream — assert the SSE event for that message has `text: null` and `is_unlocked: false`.
- Alice creates a private watch party without Bob; Bob attempts `GET /watch-party/{id}/stream` — assert 403.

### Manual QA

1. In dev, create a broadcast session as Alice. Log in as Bob. Open the browser DevTools Network tab and manually connect to `GET /broadcast/sessions/{session_id}/stream`. Before fix: events flow. After fix: 403.
2. Verify the chat stream locked-text redaction: send a locked message as Alice. Subscribe as Bob. Confirm the SSE data payload has `"text":null` and `"is_unlocked":false`.
3. Verify watch-party participant enforcement: create a party as Alice with 2 seats, invite Charlie. Connect as Bob (uninvited) → 403.

### Observability

- Audit event `stream_access_denied` (type: `broadcast_event|broadcast_chat|watch_party`, `user_sub`, `resource_id`) when `check_viewer_access` or participant check fails.
- Prometheus counter: `stream_idor_blocked_total{stream_type="broadcast_event|broadcast_chat|watch_party"}`. Alert if this counter spikes — indicates active probing.
- Log the `viewer_user_id` in every `_chat_msg_out` call for audit purposes.

### Rollout

1. Deploy broadcast event stream auth check first (lowest risk — purely additive 403 for unauthorized users).
2. Deploy chat stream auth check + `viewer_user_id` pass-through (higher value fix; test locked content rendering in dev).
3. Deploy watch-party participant check (test that party owners and participants can still connect).
4. Remove or wire WS tokens as the final clean-up step.

**Rollback**: revert the `check_viewer_access` call. No data migration needed. SSE subscriptions are stateless — no persistent state is affected.

**Risks**: legitimate users who were relying on stream access without proper subscription (e.g., a broadcaster previewing their own stream via a second account) will get 403 after the fix. Ensure `check_viewer_access` allows the session creator to always subscribe. Validate the `created_by` field is correctly populated on all test sessions.

**Effort estimate**: S/M (2–3 days). Three independent endpoint fixes, each 3-5 lines. The WS token decision is the only potentially larger scope item if Option A (wire) is chosen.
