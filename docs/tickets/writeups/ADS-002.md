# ADS-002: Ad Creative Management — Investigation & Implementation Write-up

## 1. Summary & Classification

ADS-002 adds the ad creative layer — the actual assets shown to viewers (banner images, video pre-rolls, sponsored native posts). Advertisers upload creatives, attach them to campaigns, and submit them for admin review. Only approved creatives serve traffic. The ticket also adds A/B rotation weights per creative, and optional links to promo codes and affiliate links. It replaces the hardcoded `DEV_AD_CREATIVES` list in `app/services/ad_placement.py:25` with database-backed creative selection.

- **Type**: feature
- **Priority**: High — ADS-004 (serving engine), ADS-005 (sponsored posts), and ADS-006 (broadcast ads) all depend on approved creatives
- **Status**: Implemented — `app/services/ad_creatives.py` is fully implemented; router, DDB table, and frontend pages are present
- **Owning area**: Advertising platform — creative management subsystem
- **Affected personas**: advertisers (upload/manage), admins (review), viewers (served ads)
- **Cross-references**: ADS-001 (campaigns to attach creatives to), ADS-004 (serving engine selects approved creatives), ADS-005 (native_post format used in feed), ADS-006 (video format used in broadcast), ADS-007 (billing per creative impression), ADS-008 (creative analytics), ADS-015 (affiliate/promo integration)
- **Dev/prod parity**: [[SECOPS-007]] — S3 uploads use in-process moto in dev (`app/core/dev_s3.py`), real S3 in prod; same `boto3` calls via `app/core/aws_clients.py`

`app/services/ad_placement.py:25–47` defines `DEV_AD_CREATIVES`, a list of three hardcoded dicts (`dev_ad_preroll_15s`, `dev_ad_midroll_30s`, `dev_ad_overlay`). ## 3. Gap / Threat Analysis

### 3.1 Implementation gaps

1. **`list_approved_creatives` does a full-table per-campaign scan then client-side filter** — at scale a campaign with hundreds of creatives fetches all statuses before filtering. A DDB `FilterExpression` could reduce data transfer, but DDB charges for items scanned before filter. For MVP with < 50 creatives per campaign this is acceptable; for large campaigns a dedicated `ByStatusCampaign` GSI should be added.

2. **No content-type magic-byte validation** — `_validate_asset` checks only `file.content_type` (MIME header from the browser), not actual file magic bytes. A client could send a malicious payload with `Content-Type: image/jpeg`. A server-side `imghdr` or `python-magic` check would harden this.

3. **Creative limit per campaign** — no max-creatives-per-campaign enforcement, unlike the max-campaigns-per-account gap in ADS-001. At 100 creatives the `list_approved_creatives` fetch becomes expensive.

4. **`ByFormat` GSI currently unused** — no endpoint queries by format. The GSI was defined speculatively; it adds write cost for every creative upsert without current read benefit.

5. **Promo/affiliate ID validation** — `promo_code_id` and `affiliate_link_id` are stored as-is without verifying the referenced record exists in `promo_codes` or `affiliate_links` tables. A stale reference silently has no effect at serve time, but could confuse advertisers who mistype an ID.

6. **No creative archival on campaign archival** — if a campaign is archived, its creatives remain in `approved` status and could theoretically be queried by the serving engine (which filters by campaign `status="active"`, not creative campaign status). `list_campaigns_by_status("active")` handles this correctly in `ad_serving.py` — only active-campaign creatives are candidates. No fix needed.

### 3.2 Security

- File upload size limits are enforced in `_validate_asset` server-side (not just client-side). An attacker cannot bypass by removing the frontend validation.
- S3 key uses `creative_id` prefix (`ads/creatives/{creative_id}/`), generated server-side as a UUID fragment — no path traversal risk.
- Admin review required before creative serves; `status="approved"` check in `list_approved_creatives` is the gating control.
- `cta_url` validator rejects non-HTTP/HTTPS URLs, preventing `javascript:` or `data:` URI injection in CTA links.
- The `body_text` script-tag stripper is defense-in-depth; the primary protection is React's default JSX escaping which prevents rendering raw HTML.
- **MIME type spoofing**: the current `_validate_asset` check reads `file.content_type` from the HTTP header — this is browser-controlled and not verified against file magic bytes. A malicious advertiser could upload an executable disguised as a JPEG. Server-side magic-byte validation (Gap 4.1) is required before the ad platform accepts uploads from untrusted advertisers.
- **S3 object ACL**: uploaded assets should be stored with `ACL="private"` and served via pre-signed URLs in prod (see section 5.7). Public-read S3 ACLs would allow anyone to hot-link ad assets, bypassing impression tracking and potentially exposing advertiser creatives before review approval.

## 4. Proposed Design / Fix

### 4.1 Server-side MIME validation hardening (recommended)

Add magic-byte check using Python's `imghdr` (stdlib) before S3 upload:

```python
import imghdr
def _validate_asset(data: bytes, content_type: str | None, asset_type: str) -> None:
    if asset_type == "image":
        detected = imghdr.what(None, h=data[:32])
        if detected not in ("jpeg", "png", "webp"):
            raise HTTPException(400, "File content does not match declared image type")
        # ... existing size check
```

For video (MP4): check first 8 bytes for `ftyp` box signature.

### 4.2 Promo/affiliate validation on create

In `create_creative`, after storing the item, optionally validate references:

```python
if data.promo_code_id:
    from app.core.tables import T
    pc = T.promo_codes.get_item(Key={"pk": data.promo_code_id}).get("Item")
    if not pc:
        raise HTTPException(400, "promo_code_id not found")
```

This adds a DDB read per creative creation with a promo code. Given infrequency, acceptable.

### 4.3 Creative count limit

In `create_creative` service function, add before `T.ad_creatives.put_item`:

```python
existing = list_creatives(campaign_id)
if len(existing) >= 50:
    raise ValueError("Maximum 50 creatives per campaign")
```

### 4.4 Dev/prod parity (SECOPS-007)

Current implementation satisfies SECOPS-007:
- S3 calls via `app/core/aws_clients.py`; moto intercepts in dev (`dev_s3.py`)
- URL prefix `S.dev_mode` check is the only environment branch; business logic is identical
- Tests can run offline: moto handles S3, DDB Local handles table writes
- Feature flag `AD_CREATIVES_ENABLED` (not yet enforced in the router) should gate endpoints in `.env.local` for phased rollout

### 4.5 Replacing `DEV_AD_CREATIVES`

Once ADS-004 is wired to call `list_approved_creatives()`, the hardcoded `DEV_AD_CREATIVES` fallback in `ad_placement.py` becomes the VOD-only fallback when no paid campaigns exist. ADS-004 already imports `DEV_AD_CREATIVES` as a fallback house-ad pool. This is the correct behavior — no removal needed until ADS-004 goes GA.
