# BOT-001: Bot Framework & Lifecycle — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

BOT-001 establishes the foundational bot framework: creators can define chat bots with their own identity (name, avatar, personality) and assign them to conversations or broadcast sessions. Each bot has a status state machine (`active`/`paused`/`disabled`) and a trigger configuration that evaluates incoming messages to decide whether to respond. Bots send messages that appear inline in conversations via the existing messaging infrastructure, distinguished by a `sender_type="bot"` field and rendered with a "Bot" badge in the UI. This ticket is the foundation that BOT-002 (templates), BOT-003 (promotion), and BOT-004 (AI chat) all depend on.

- **Type**: Feature
- **Priority**: High
- **Status**: Partially implemented — backend service and router exist; critical gaps remain in `_message_out_from_item` population, messaging pipeline hookup, frontend pages, and E2E tests.
- **Owning area**: `app/services/chat_bot.py`, `app/routers/chat_bot.py`, `app/routers/messaging.py`, `frontend/src/pages/bots/`
- **Who is affected**: Creators (configure bots), Users (receive bot messages in conversations)
- **Cross-references**: BOT-002 (templates depend on this), BOT-003 (promotion), BOT-004 (AI), [[SECOPS-007]] (dev/prod parity for feature flag; no external LLM calls in this ticket)

## 2. Current-State Investigation (what exists today)

### 2.1 Backend — what is implemented

`app/services/chat_bot.py` (448 lines) exists and implements the full bot service layer:

- **`create_bot()`** (`chat_bot.py:21`): Creates a bot record under `PK=CREATOR#{creator_id}`, `SK=BOT#{bot_id}` with a `GSI1PK=BOT#{bot_id}` / `GSI1SK=META` secondary index for cross-creator lookup. Enforces `S.bot_max_per_creator` (default 10, `settings.py:1966`). Sets `status="active"` on creation.
- **`get_bot()`** (`chat_bot.py:68`): Queries via GSI1 by `bot_id` alone. Used in message dispatch.
- **`get_bot_for_owner()`** (`chat_bot.py:80`): Fetches by `PK=CREATOR#... SK=BOT#...`; enforces ownership without GSI.
- **`list_bots()`** (`chat_bot.py:89`): Queries `PK=CREATOR#{creator_id}`, `SK begins_with BOT#`.
- **`update_bot()`** (`chat_bot.py:97`): Conditional update with `attribute_exists(pk)` guard; allowed fields include `trigger_config`.
- **`update_bot_status()`** (`chat_bot.py:135`): Full transition matrix — `active→{paused,disabled}`, `paused→{active,disabled}`, `disabled→{active,paused}` — with `InvalidStatusTransition` exception for invalid transitions.
- **`delete_bot()`** (`chat_bot.py:167`): Cascades: queries all assignments via `_query_all_assignments()`, deletes each, then deletes the bot record.
- **`assign_bot()`** (`chat_bot.py:187`): Builds SK based on `target_type` (`CONV#`, `BCAST#`, `SCOPE#ALL_DMS`, etc.) and writes a `GSI1PK=CONV#{conversation_id}` / `GSI1SK=BOT#{bot_id}` record for wildcard-less conversations. Checks for duplicate via `get_item` before writing.
- **`unassign_bot()`** (`chat_bot.py:227`): Deletes by `PK=BOT#{bot_id}`, `SK={assignment_sk}`.
- **`get_bots_for_conversation()`** (`chat_bot.py:251`): Queries GSI1 on `bot_assignments` for `CONV#{conversation_id}`, fetches each bot, filters to `status="active"`.
- **`send_bot_message()`** (`chat_bot.py:283`): Returns a dict with `bot_id`, `bot_name`, `bot_avatar_url`, `sender_type="bot"`, `text`, `kind`. **However, this function does not actually write a DynamoDB message item** — it only returns a dict. Integration into the messaging pipeline is missing (see gaps below).
- **`evaluate_triggers()`** (`chat_bot.py:319`): Walks `priority_order` from `trigger_config`, delegates to `_trigger_matches()` (`chat_bot.py:359`) for `all_messages`, `keyword`, `mention`, `first_message` trigger types.

`app/routers/chat_bot.py` (222 lines) exposes all expected endpoints:

- `POST /ui/bots` (`chat_bot.py:80`) — 201 on success, 409 on `BotLimitExceeded`, 503 when `S.bot_framework_enabled` is false.
- `GET /ui/bots`, `GET /ui/bots/{bot_id}`, `PUT /ui/bots/{bot_id}`, `PATCH /ui/bots/{bot_id}/status`, `DELETE /ui/bots/{bot_id}` — all wrapped in `if not S.bot_framework_enabled: raise 503`.
- `POST /ui/bots/{bot_id}/assignments` (status 201), `DELETE /ui/bots/{bot_id}/assignments/{assignment_sk:path}`, `GET /ui/bots/{bot_id}/assignments`.
- `GET /ui/bots/{bot_id}/stats` — returns `message_count`, `last_active_at`, `assignment_count`.
- `POST /ui/bots/{bot_id}/send` — manual/test send endpoint.

The router is registered in `app/main.py:680` (`app.include_router(chat_bot_router, prefix="/ui")`).

Settings wired in `app/core/settings.py:1963-1966`:
- `bot_framework_enabled` (default `true`, env `BOT_FRAMEWORK_ENABLED`)
- `chat_bots_table_name` (default `chat_bots`)
- `bot_assignments_table_name` (default `bot_assignments`)
- `bot_max_per_creator` (default 10)

DynamoDB tables declared in `scripts/local-ddb-init.py:1559-1591` for `chat_bots` and `bot_assignments` with GSI1 on both.

Table handles in `app/core/tables.py:239-240` (`T.chat_bots`, `T.bot_assignments`) and wired at lines 475-476.

### 2.2 MessageOut — fields declared but never populated

`MessageOut` in `app/routers/messaging.py:2492-2496`:

```python
sender_type: Optional[Literal["user", "bot"]] = None
bot_id: Optional[str] = None
bot_name: Optional[str] = None
bot_avatar_url: Optional[str] = None
quick_replies: Optional[List[Dict[str, str]]] = None
```

These fields exist in the model but **`_message_out_from_item()` at `messaging.py:3870-4230` never reads them from the DDB item**. The `return MessageOut(...)` call at line 4162 does not pass `sender_type`, `bot_id`, `bot_name`, `bot_avatar_url`, or `quick_replies`. Consequently, even if a bot message is stored with these fields, they will always be `None` when read back.

`send_text_message()` at `messaging.py:7852` has no post-send hook that calls `get_bots_for_conversation()` and `evaluate_triggers()`. The bot auto-reply evaluation code lives in `app/services/bot_auto_reply.py` (a partially-implemented BOT-003 stub) with `process_incoming_message()` at line 167, but this is not wired into `send_text_message()` either.

### 2.4 Frontend — partially implemented

`frontend/src/pages/bots/BotManagerPage.tsx` exists. `frontend/src/api/endpoints/bots.ts` exists. However, no E2E spec file `frontend/e2e/chat-bots.spec.ts` exists.

### 2.5 Dev vs prod behavior today

`S.bot_framework_enabled` defaults to `true` in both dev and prod. The `chat_bots` and `bot_assignments` tables are provisioned by `scripts/local-ddb-init.py` which runs against DynamoDB Local in dev and real DynamoDB in prod. No outbound calls are involved in BOT-001, so dev/prod parity is inherently maintained.

## 3. Gap / Threat Analysis

### 3.1 Critical functional gaps

1. **`_message_out_from_item` does not populate bot fields** (`messaging.py:4162-4230`). Every bot message stored with `sender_type`, `bot_id`, `bot_name`, `bot_avatar_url` will silently lose those fields when read back. Frontend "Bot" badge will never render. Fix: add `sender_type=merged_item.get("sender_type")`, `bot_id=merged_item.get("bot_id")`, `bot_name=merged_item.get("bot_name")`, `bot_avatar_url=merged_item.get("bot_avatar_url")`, `quick_replies=merged_item.get("quick_replies")` to the `return MessageOut(...)` call.

2. **`send_bot_message()` returns a dict but does not write to DynamoDB**. The function at `chat_bot.py:283` increments `message_count` and returns a dict, but never calls into the messaging pipeline to actually persist or deliver the message. A caller that relies on `send_bot_message()` producing a conversation-visible message will be disappointed. Fix: `send_bot_message()` must call `send_text_message()` (or the underlying DynamoDB write path) with the `sender_type`, `bot_id`, `bot_name`, `bot_avatar_url` fields injected into the item.

3. **No post-send trigger hook in `send_text_message()`**. After `tbl_msgs.put_item(Item=item)` at `messaging.py:7996`, there is no call to evaluate bot triggers for the incoming message. Fix: after the message is persisted and before the function returns, spawn an async background task: `asyncio.create_task(_run_bot_trigger_evaluation(conversation_id, item, sender_user_id))`.

4. **`evaluate_triggers()` wildcard scope not enforced**. `get_bots_for_conversation()` (`chat_bot.py:251`) only queries GSI1 for direct `CONV#{conversation_id}` assignments. Wildcard scopes (`SCOPE#ALL_DMS`, `SCOPE#ALL_GROUPS`) stored in `bot_assignments` with no `GSI1PK` are never found. Fix: after the GSI query, also query `PK=BOT#{bot_id}` for any bot that should apply via wildcard, or add a separate lookup against all bots for the creator with wildcard assignments.

5. **No `system` sender type**. `MessageOut.sender_type` declares `Literal["user", "bot"]` at `messaging.py:2492` but the ticket design calls for `"system"` as a third option. The Literal must be extended.

6. **Missing E2E tests** (`frontend/e2e/chat-bots.spec.ts` does not exist).

### 3.2 Security considerations

- `send_bot_message()` must be callable only server-side; the `POST /ui/bots/{bot_id}/send` endpoint (`chat_bot.py:210`) requires authentication and bot ownership check, so clients cannot forge `sender_type="bot"`.
- Assignment scope validation (bot can only be assigned to conversations where the creator participates) is not yet enforced in `assign_bot()` (`chat_bot.py:187`). The function creates the assignment without verifying the creator is a participant in the target conversation.

## 4. Proposed Design / Fix

### 4.1 Fix `_message_out_from_item` to pass bot fields (`messaging.py:4162`)

At the `return MessageOut(...)` call (`messaging.py:4162`), add:

```python
sender_type=merged_item.get("sender_type") or None,
bot_id=merged_item.get("bot_id") or None,
bot_name=merged_item.get("bot_name") or None,
bot_avatar_url=merged_item.get("bot_avatar_url") or None,
quick_replies=merged_item.get("quick_replies") or None,
```

This is a backward-compatible, additive change: existing messages without these fields continue to return `None` for all bot-related fields.

### 4.2 Make `send_bot_message()` write to the conversation (`chat_bot.py:283`)

Replace the stub return dict with a real write. The function should build a synthetic `SendTextMessageIn`-compatible dict and call `create_internal_bot_message(conversation_id, text, sender_type, bot_id, bot_name, bot_avatar_url, quick_replies)` — an internal helper (not a FastAPI endpoint, no auth check, no CSRF) that writes the DDB item directly and calls `_fanout_new_message_event()`. This mirrors the pattern used by the scheduled message dispatcher at `messaging.py:737`.

### 4.3 Post-send bot trigger hook in `send_text_message()` (`messaging.py:7852`)

After line 8053 (the `_fanout_new_message_event` call):

```python
if not is_scheduled and S.bot_framework_enabled:
    import asyncio as _asyncio
    _asyncio.create_task(_run_bot_trigger_evaluation(
        conversation_id=conversation_id,
        incoming_item=item,
        sender_id=user_id,
    ))
```

`_run_bot_trigger_evaluation()` is an async wrapper that: (1) calls `get_bots_for_conversation(conversation_id=conversation_id)`, (2) for each active bot calls `evaluate_triggers(bot=b, conversation_id=conversation_id, incoming_message=item)`, (3) on a match, calls `bot_template.render_template()` + `create_internal_bot_message()`. If no template is matched, falls back to `bot.get("trigger_config", {}).get("default_response")` if set.

### 4.4 Dev/Prod parity (SECOPS-007)

BOT-001 has no external dependencies: DynamoDB Local (dev) vs DynamoDB (prod) is handled by `app/core/tables.py` and `app/core/aws.py` using `DDB_ENDPOINT_URL`. The `BOT_FRAMEWORK_ENABLED` flag (default `true`) acts as the feature gate in both environments. No mock vs real divergence is needed.

### 4.5 Frontend: `MessageBubble.tsx`

In `frontend/src/pages/messages/MessageBubble.tsx`, when `message.sender_type === "bot"`:
- Display `message.bot_avatar_url` or a fallback robot icon instead of the user avatar.
- Render `<Badge variant="outline">Bot</Badge>` alongside `message.bot_name`.
- Apply `bg-muted/50` background tint to visually distinguish the bubble.

### 4.6 Tables — no new additions needed

Both `chat_bots` and `bot_assignments` tables are already declared in `scripts/local-ddb-init.py:1559-1591` and `app/core/tables.py:239-240,475-476`.

### 5.5 Rollback plan

Background task is strongly preferred for latency isolation. Should wildcard scope expansion (`ALL_DMS`) be resolved at trigger time or pre-indexed on conversation creation?
