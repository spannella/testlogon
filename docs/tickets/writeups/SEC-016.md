# SEC-016: Security Headers Not Applied (Clickjacking/CSP) + Client-Side Hardening — Investigation & Implementation Write-up

> ~5 pages. Real code read, citations at `file:line`.

## 1. Summary & Classification

Every HTTP response served by the backend ships without the standard browser security headers because the middleware that would set them was written but never registered with FastAPI. This means the application is trivially frameable (clickjacking), browsers can MIME-sniff responses (MIME confusion attacks), there is no Content Security Policy to limit XSS blast radius, and no HSTS to enforce TLS in production. Compounding the server-side gap, the frontend has several independent weaknesses: the service-worker `postMessage` handler in `swMessageHandler.ts` and `useServiceWorkerSync.ts` processes messages from any origin without verifying `event.origin`; multiple `target="_blank"` links carry only `rel="noreferrer"` but omit `noopener`, enabling reverse tabnabbing; `RichContentRenderer` renders backend-supplied HTML via `dangerouslySetInnerHTML` without a client-side DOMPurify pass; and the SSO login button assigns `ssoInfo.sso_login_url` directly to `window.location.href` with no host/scheme validation.

- **Type**: security-fix / hardening
- **Priority**: High
- **Status**: Open
- **Area**: backend middleware (`app/main.py`), frontend (`frontend/src/`)
- **Affected users**: all users and unauthenticated visitors — any page is frameable
- **Attacker class**: 🌐 any-user (clickjacking, XSS); 🌐 unauthenticated (CSP/HSTS)
- **Related**: SECOPS-007 (dev/prod parity), SEC-008 (trusted IP not directly applicable here)

## 2. Current-State Investigation (What Exists Today)

### 2.1 Backend: dead middleware

`app/main.py:348–356` defines:

```python
def _security_headers_middleware(default_csp: str):
    async def _middleware(request: Request, call_next):
        response = await call_next(request)
        response.headers.setdefault("Content-Security-Policy", default_csp)
        response.headers.setdefault("X-Content-Type-Options", "nosniff")
        response.headers.setdefault("X-Frame-Options", "DENY")
        response.headers.setdefault("Referrer-Policy", "strict-origin-when-cross-origin")
        return response
    return _middleware
```

`create_app()` at `app/main.py:383` registers five other middlewares (`CORSMiddleware`, `TenantMiddleware`, `rate_limit_middleware_factory`, `_api_usage_metering_middleware`, `_playback_entitlement_middleware`, `metrics_middleware`) but **never calls `app.middleware("http")(_security_headers_middleware(...))`**. Confirmed by reading `app/main.py:412–422`: no invocation of `_security_headers_middleware` appears anywhere in the file. A full-text grep of the codebase finds zero call sites.

The consequence: every JSON API response and every HTML page served by the backend (`app/static/index.html` via the root route at `app/main.py:391`) arrives in the browser with none of these headers. The application can be framed in an `<iframe>` by any third-party site. The absence of CSP means any XSS that fires has no browser-enforced restriction on data exfiltration or code execution. The absence of `nosniff` allows Internet Explorer / older Edge to reinterpret response content type. HSTS is also entirely absent: a network-level MitM can silently downgrade HTTPS to HTTP on first load for any user without a preloaded HSTS entry.

### 2.2 Frontend: SW postMessage — no origin check

`frontend/src/lib/swMessageHandler.ts:18` registers:
```ts
navigator.serviceWorker.addEventListener("message", (event) => {
  const data = event.data;
  if (!data?.type) return;
  switch (data.type) { ... }
```

`frontend/src/hooks/useServiceWorkerSync.ts:21` registers a second handler:
```ts
const handler = (event: MessageEvent) => {
  const { type, id, error } = event.data ?? {};
  ...
};
navigator.serviceWorker?.addEventListener("message", handler);
```

`frontend/src/lib/pushSetup.ts:82` has a third handler for `sw-updated`.

All three process `event.data` without checking `event.origin`. For service-worker messages the origin concern is lower than for cross-frame `window.postMessage`, but the `message` event on `navigator.serviceWorker` can in principle be triggered from a page in the same origin running a compromised script. The more important mitigation is defense-in-depth: a rogue script that has already XSS'd the page can fake these events. The absence of origin guards means logic that updates Zustand store state (marking queue items done, triggering React Query invalidations) can be driven by injected messages.

### 2.3 Frontend: `target="_blank"` without `noopener`

The following links use `rel="noreferrer"` but omit `noopener`, leaving the child tab able to set `window.opener.location` (reverse tabnabbing):

- `frontend/src/pages/kyc/KycScreeningReviewQueuePage.tsx:100–107` — `match.source_url` (external KYC source link, operator-controlled content)
- `frontend/src/pages/agents/AgentPrList.tsx:197–204` — `pr.pr_url` (GitHub PR URL, semi-trusted)
- `frontend/src/pages/syndicates/SyndicateProfilePage.tsx:142–150` — `profile.website_url` (fully user-controlled)

`rel="noreferrer"` actually implies `noopener` in current browsers (Chrome 88+, Firefox 79+), so the practical risk today is low for modern browsers. However, the spec says they are independent attributes; relying on implied behavior is fragile and wrong per the HTML spec and ESLint `anchor-is-valid` / `no-target-blank` rules. The higher-risk gap is the lines without any `rel` attribute at all (`frontend/src/pages/messages/MessageBubble.tsx:1720`, `1757`; `frontend/src/pages/feed/StoryViewer.tsx:240`; `frontend/src/pages/ads/CreativePreview.tsx:72`).

### 2.4 Frontend: `dangerouslySetInnerHTML` without DOMPurify

`frontend/src/pages/feed/RichContentRenderer.tsx:63,67` renders HTML strings via `dangerouslySetInnerHTML`:

```tsx
return <div className={baseClass} dangerouslySetInnerHTML={{ __html: richHtml }} />;
// ... and
return <div className={baseClass} dangerouslySetInnerHTML={{ __html: markdownHtml }} />;
```

The `richHtml` path comes from `richDocToHtml()` (a client-side ProseMirror-doc-to-HTML converter — internal, controlled input). The `markdownHtml` path uses either the backend-supplied `bodyMarkdownHtml` field (line 27: `if (props.bodyMarkdownHtml?.trim()) return props.bodyMarkdownHtml`) or a naive client-side converter that only wraps paragraphs (lines 28–35 — this path HTML-escapes `<`/`>` itself). The backend-supplied `bodyMarkdownHtml` is the risk: if the server-side sanitizer has any bypass (or is disabled/skipped), the raw HTML lands in the DOM without a client-side guard. `frontend/src/pages/feed/MarkdownComposer.tsx:186` also renders a preview via `dangerouslySetInnerHTML` with no DOMPurify.

### 2.5 Frontend: SSO URL redirect without host validation

`frontend/src/pages/Login.tsx:481` and `:644`:
```ts
onClick={() => { window.location.href = ssoInfo.sso_login_url || "/saml/login"; }}
```

`ssoInfo` is fetched from the backend via `getSsoInfo()`. If the backend or an XSS can poison `sso_login_url` with a `javascript:` URI or an off-host `https://evil.com/phish`, the user's browser navigates there without warning. There is no client-side check that the URL starts with `https://` and matches the expected IdP hostname.

## 3. Gap / Threat Analysis

### 3.1 Clickjacking via missing X-Frame-Options / CSP frame-ancestors

**Scenario**: an attacker hosts `https://evil.com` with:
```html
<iframe src="https://app.example.com/billing/wallet" style="opacity:0;position:absolute;" />
<button style="position:absolute;">Click here for prize</button>
```
The victim clicks the invisible iframe button and triggers a wallet withdrawal or account-deletion confirmation. With no `X-Frame-Options: DENY` or `Content-Security-Policy: frame-ancestors 'none'`, no browser defence fires.

**Blast radius**: any authenticated action reachable through a UI button — payments, profile changes, account deletion, MFA device management.

### 3.2 XSS blast radius without CSP

With no CSP, any stored or reflected XSS (e.g., in `bodyMarkdownHtml`, a future rendering bug, or a third-party script compromise) can: exfiltrate cookies (though `HttpOnly` limits cookie theft), read CSRF tokens from the DOM, make credentialed API calls, redirect to phishing, install a persistent SW. A CSP `script-src 'self'` baseline would contain damage.

### 3.3 SW postMessage injection

An XSS script or a compromised SW registration can dispatch:
```js
navigator.serviceWorker.controller.postMessage({ type: "sync-flush-complete" });
```
Triggering `queryClient.invalidateQueries` is benign, but `sync-item-success` calls `removeFromQueue(data.id)` — potentially discarding a message the user is still composing. `sync-item-dead` triggers a user-facing toast with an attacker-controlled `error` string, which could be used for phishing.

### 3.4 Reverse tabnabbing

User clicks "Website" on `SyndicateProfilePage` (a user-supplied URL) → new tab opens and calls `window.opener.location = "https://phishing.com"`. Even though modern browsers patch this with `noopener` implied by `noreferrer`, some enterprise browsers on older Chromium versions and Safari < 12.1 do not.

### 3.5 HSTS absence (production)

Without `Strict-Transport-Security`, a user who visits `http://` for the first time can be silently downgraded by a network MitM. This is a production-only concern (TLS not used in dev stack).

## 4. Proposed Design / Fix

### 4.1 Register the security-headers middleware

In `app/main.py:create_app()`, after the existing middleware registrations (around line 421), add:

```python
_csp = os.environ.get(
    "CSP_DEFAULT",
    "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; "
    "img-src 'self' data: blob:; connect-src 'self' wss:; frame-ancestors 'none';"
)
app.middleware("http")(_security_headers_middleware(_csp))
```

Also extend `_security_headers_middleware` to emit HSTS in production (when `not S.dev_mode`):

```python
if not S.dev_mode:
    response.headers.setdefault(
        "Strict-Transport-Security",
        "max-age=63072000; includeSubDomains; preload"
    )
response.headers.setdefault("Permissions-Policy", "geolocation=(), camera=(), microphone=()")
```

**Dev/Prod parity (SECOPS-007)**: The middleware runs in both environments; `dev_mode` gates only HSTS (TLS not terminating locally). `CSP_DEFAULT` env var allows operators to extend the policy for CDN/media domains without code changes.

### 4.2 SW postMessage — add origin guard

In `frontend/src/lib/swMessageHandler.ts:18`, `frontend/src/hooks/useServiceWorkerSync.ts:21`, and `frontend/src/lib/pushSetup.ts:82`, add a guard at the top of every handler:

```ts
navigator.serviceWorker.addEventListener("message", (event) => {
  // Guard: only accept messages from our own SW (same origin)
  if (event.origin && event.origin !== window.location.origin) return;
  const data = event.data;
  ...
});
```

Note: `event.origin` is `""` for messages coming from the browser's own SW controller (same-origin). The guard therefore should be `if (event.origin !== "" && event.origin !== window.location.origin) return;`.

### 4.3 Fix `target="_blank"` links

Change all `target="_blank"` links to use `rel="noopener noreferrer"`. The affected files are listed in §2.3. Additionally audit for any missing `rel` attribute entirely (MessageBubble, StoryViewer, CreativePreview) and add `rel="noopener noreferrer"` there.

### 4.4 Add DOMPurify to `RichContentRenderer`

Install DOMPurify (`npm install dompurify @types/dompurify`). In `frontend/src/pages/feed/RichContentRenderer.tsx`, sanitize before render:

```ts
import DOMPurify from "dompurify";
// ...
const markdownHtml = DOMPurify.sanitize(markdownHtmlFromProps(props));
return <div className={baseClass} dangerouslySetInnerHTML={{ __html: markdownHtml }} />;
```

The `richHtml` path from `richDocToHtml()` is client-generated from a ProseMirror doc — still worth sanitizing as defense-in-depth. `MarkdownComposer.tsx:186` should similarly wrap its preview.

### 4.5 Validate SSO URL before redirect

In `frontend/src/pages/Login.tsx`, replace the direct assignment with a validated helper:

```ts
function safeSsoRedirect(url: string | undefined): void {
  if (!url) { window.location.href = "/saml/login"; return; }
  try {
    const parsed = new URL(url);
    if (parsed.protocol !== "https:" && parsed.protocol !== "http:") return;
    // Optionally: restrict to same hostname or known IdP hostnames
    window.location.href = url;
  } catch {
    window.location.href = "/saml/login";
  }
}
// Usage:
onClick={() => safeSsoRedirect(ssoInfo?.sso_login_url)}
```

In production, tighten to `parsed.protocol === "https:"` only.

### 4.6 Backward compatibility

Registering the middleware is a zero-migration change — no data changes, no API changes. The CSP `frame-ancestors 'none'` will break any deliberate embedding; audit with stakeholders first. A `REPORT-URI` or `Content-Security-Policy-Report-Only` header can shadow-deploy the CSP before enforcement.

## 5. Testing, Verification & Rollout

### pytest unit tests

- `tests/test_security_headers.py`:
  - `test_security_headers_present`: call `GET /` (or any `/ui/...` endpoint) via the test client; assert `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, and `Content-Security-Policy` are in the response headers.
  - `test_csp_custom_env`: set `CSP_DEFAULT` env var, verify it appears verbatim.
  - `test_hsts_absent_in_dev`: with `DEV_MODE=1`, assert `Strict-Transport-Security` is absent.
  - `test_hsts_present_in_prod`: with `DEV_MODE=0`, assert HSTS header is present.

### Playwright E2E (`frontend/e2e/security-headers.spec.ts`)

- Intercept the response to `GET /` via `page.route` or `page.goto` + `response.headers()`; assert each header value.
- Open a `data:text/html` page that embeds `<iframe src="http://localhost:3000/login">`, assert the frame navigation is blocked or the frame shows an error (browser refusal visible in console).
- Verify the SW message handler ignores a manually dispatched message from a fake origin (use `page.evaluate` to fire a `MessageEvent` with a non-matching origin).

### Manual / QA steps

1. `curl -si http://localhost:8000/ | grep -i 'x-frame\|csp\|nosniff\|referrer\|hsts'` — before fix shows nothing; after fix shows all headers.
2. Open browser DevTools → Application → Service Workers; trigger a fake `postMessage` via console; verify no state mutation occurs.
3. Click "Website" on a syndicate page; check DevTools shows `rel="noopener noreferrer"` on the anchor.
4. Post a newsfeed item with markdown body containing `<img src=x onerror=alert(1)>`; verify DOMPurify strips the `onerror`.

### Observability

Add a Prometheus counter `security_headers_applied_total` (labeled by header name) incremented each time the middleware runs — useful to confirm middleware is executing in prod.

### Rollout

1. Deploy `Content-Security-Policy-Report-Only` first; monitor violation reports for two weeks.
2. Promote to enforcing CSP; monitor for regressions.
3. DOMPurify and `rel` fixes are independent and can ship immediately.

### Risks & open questions

- CSP `unsafe-inline` for styles may need to be replaced with a nonce strategy if inline styles are stripped; audit Tailwind JIT usage.
- `frame-ancestors 'none'` should be confirmed with product team — are there any legitimate embedding scenarios (partner portals)?

**Effort**: S (the backend fix is two lines; frontend fixes are mechanical; DOMPurify adds one dependency).
