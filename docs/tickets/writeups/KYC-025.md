# KYC-025: KYC Decision Appeals / Disputes — Investigation & Implementation Write-up

## 1. Summary & Classification

KYC-025 adds an appeal/dispute lifecycle to the KYC case state machine. Currently `rejected` is a terminal state with no recourse for the user. The ticket requires a new `appealed` status, user-facing appeal submission, an admin appeals queue with four-eyes enforcement (different reviewer than the original decision-maker), and analytics integration.

- **Type**: Feature
- **Priority**: Medium
- **Status**: UNBUILT — zero implementation exists in the codebase
- **Owning area**: KYC / Compliance
- **User persona**: User who was wrongly rejected; compliance admin reviewing appeals
- **Dependencies**: KYC-001 (case workflow), KYC-023 (encryption), KYC-024 (analytics); MOD-003 appeals system exists but is for enforcement actions, not KYC decisions
- **SECOPS-007 note**: Feature-flag `KYC_APPEALS_ENABLED` must default `true` in dev/test, `false` in prod until fully rolled out.

## 2. Current-State Investigation (what exists today)

### State machine (`app/services/kyc_cases.py`)

The valid case statuses are defined at `app/services/kyc_cases.py:30-37`:
`draft`, `submitted`, `under_review`, `needs_more_info`, `approved`, `rejected`.

The `make_decision` method (`app/services/kyc_cases.py:595-660`) enforces:
- Line 608: `if current_status in {"approved", "rejected"}` → blocks any further transition out of `rejected` unless it is an idempotent re-application of the same decision (same `decision_hash`).
- Line 615: decisions can only be applied from `under_review`.

There is no `appealed` status, no `submit_appeal` function, no appeal record type, and no guard preventing retention purge of appealed cases.

### Retention purge (`app/services/kyc_cases.py:797-820`)

`run_retention_purge` checks `status == "rejected"` and applies `kyc_retention_rejected_days` (default 30 days, `app/core/settings.py:1173`). An open appeal would not block purge today — there is no check for it.

### Existing appeals system (`app/services/appeals.py`, `app/routers/appeals.py`, `app/routers/admin_appeals.py`)

These implement MOD-003 (enforcement action appeals — bans, suspensions). They operate on `T.appeals` / `T.user_enforcement_history` tables, not on `T.kyc_cases`. They are unrelated to KYC decision appeals and cannot be reused directly.

### Router (`app/routers/kyc_cases.py`)

`grep -n "appeal"` returns zero results. There are no appeal endpoints.

### Settings (`app/core/settings.py`)

No `KYC_APPEALS_ENABLED`, `KYC_APPEAL_WINDOW_DAYS`, `KYC_MAX_APPEALS_PER_CASE`, or `KYC_APPEAL_FOUR_EYES` flags exist.

### Frontend

No KYC appeal UI exists. `frontend/e2e/kyc-appeals.spec.ts` does not exist. `frontend/src/pages/kyc/` has no appeal form. The admin KYC queue (`frontend/src/pages/admin/KycQueuePage.tsx`) has no appeal filter.

## 3. Gap / Threat Analysis

### Compliance gap

Most KYC/AML regulatory frameworks (FATF, EU AML directives) require a documented redress process for identity verification rejections. Users rejected due to OCR errors, transient document issues, or false-positive sanctions hits have no recourse today. This is both a UX gap and a regulatory risk.

### Abuse potential

Without a bounded appeal window and max-appeals limit, users could flood the queue with repeated appeals. The four-eyes requirement prevents the original reviewer from rubber-stamping their own decision.

### Purge risk

A rejected case with an open appeal should not be purged. Without the purge guard, a case could be deleted during the appeal window, destroying evidence and blocking the appeal from being resolved.

### Every code site that must change

1. `app/services/kyc_cases.py` — add `appealed` to status list; add `submit_appeal` and `decide_appeal` methods; add purge guard; add appeal sub-record persistence.
2. `app/routers/kyc_cases.py` — add `POST /{case_id}/appeal` and `POST /{case_id}/appeal/decision` endpoints.
3. `app/core/settings.py` — add four settings flags.
4. `scripts/local-ddb-init.py` — add `appealed` to any status-GSI seed assumptions; no new table needed (appeal sub-record stored on case item).
5. `frontend/src/pages/kyc/KycCaseStatusPage.tsx` (or equivalent) — add appeal form for rejected cases.
6. `frontend/src/pages/admin/KycQueuePage.tsx` — add appeals filter/tab.
7. `frontend/src/api/endpoints/kyc.ts` — add `submitAppeal`, `decideAppeal` API functions.
8. `frontend/e2e/kyc-appeals.spec.ts` — new E2E spec.
9. `tests/test_kyc_appeals.py` — new pytest file.

## 4. Proposed Design / Fix

### 4.1 State machine changes (`app/services/kyc_cases.py`)

Add `"appealed"` to the status list at line 37.

Add new method `submit_appeal`:
```python
def submit_appeal(self, *, case_id: str, user_sub: str, justification: str,
                  document_ids: list[str], expected_version: int) -> dict:
    """Transition rejected → appealed. One appeal per case (configurable).
    Checks: case exists, owner matches, status==rejected, within window, max appeals."""
```

Add new method `decide_appeal`:
```python
def decide_appeal(self, *, case_id: str, admin_sub: str, decision: str,
                  reason: str, expected_version: int) -> dict:
    """Admin appeal decision: uphold → rejected, overturn → under_review, approve → approved.
    Four-eyes: admin_sub must differ from case.review.decision_actor_sub."""
```

Purge guard in `run_retention_purge`:
```python
# app/services/kyc_cases.py ~line 818
if status == "rejected":
    # NEW: skip if an appeal is open
    if str(row.get("appeal_status") or "") == "open":
        continue
    eligible = anchor > 0 and anchor <= rejected_cutoff
```

Appeal sub-record stored as `appeal` map on the case item:

```json
    "document_ids": [],
    "appeal_status": "open",
    "reviewer_sub": null,
    "decision": null,
    "decided_at": null,
    "reason": null
  }
}
```

### 4.3 New endpoints (`app/routers/kyc_cases.py`)

```
POST /v1/kyc/cases/{case_id}/appeal
  Auth: require_ui_session (case owner only)
  Body: { justification: str, document_ids: list[str], expected_version: int }
  Success: 200 { ok, appeal_id, status: "appealed" }
  Errors: 403 (not owner), 400 (not rejected / window expired / max appeals), 409 (version conflict)

POST /v1/kyc/admin/cases/{case_id}/appeal/decision
  Auth: require_ui_session + ADMIN/ROOT role
  Body: { decision: "uphold"|"overturn"|"approve", reason: str, expected_version: int }
  Success: 200 { ok, new_status }
  Errors: 403 (four-eyes: original reviewer trying to decide own appeal), 400 (case not appealed)
```

Both endpoints map `kyc_invalid_transition` to HTTP 400 and `kyc_case_update_conflict` to HTTP 409.

### 4.4 Frontend

- Show the rejection reason (`case.review.reason_codes`, `case.review.decision_note`).
- Show "Appeal this decision" button → opens form for justification text.

- Track `appeals_submitted`, `appeals_overturned`, `appeals_upheld`, `overturn_rate`.

### Playwright E2E (`frontend/e2e/kyc-appeals.spec.ts`)

- Section N+0: reject case → user submits appeal → admin (different from original reviewer) overturns → case back to `under_review` → admin approves.
- Section N+1: reject → appeal → admin upholds → terminal (`rejected` again).
- Section N+2: appeal window expiry (`appeal_window_days=0` override) → appeal blocked with 400.
- Section N+3: second appeal blocked when `max_appeals=1`.
- Section N+4: original reviewer attempts to decide own appeal → 403.
- Section N+5: feature flag off (`KYC_APPEALS_ENABLED=false`) → `POST /appeal` returns 404/503.
