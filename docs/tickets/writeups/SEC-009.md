# SEC-009: Account-Takeover Hardening — OTP Brute-Force, Device Trust, Code Compare — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

Six distinct weaknesses in the authentication and MFA subsystem collectively make account takeover substantially easier than the intended security model allows. Most are independent failure modes; any one of them alone could be the decisive factor in an attack. They all operate in the same code path — the MFA challenge/verify cycle — and all share the same IP-spoofing aggravation documented in [[SEC-008]].

- **Type**: security-fix (critical)
- **Priority/Severity**: Critical
- **Status**: Open
- **Owning area**: `app/routers/ui_mfa.py`, `app/routers/password_recovery.py`, `app/routers/mfa_devices.py`, `app/services/device_trust.py`, `app/services/sessions.py`
- **Attacker class**: 🌐 remote attacker (OTP brute-force, device bypass); insider with session access (self-trust device)
- **Cross-references**: [[SEC-008]] (IP spoofing makes per-IP lockout useless without this fix), [[ROOT-AUTH-001]] (root-specific step-up hardening), [[SEC-018]] (account-state revocation propagation)

## 2. Current-State Investigation (what exists today)

### 2.1 OTP/SMS brute-force — no per-account lockout that survives `begin` reset

**SMS begin reset (`app/routers/ui_mfa.py:83-88`)**:

```python
83    if _sessions_table_enabled():
84        T.sessions.update_item(
85            Key={"user_sub": user_sub, "session_id": body.challenge_id},
86            UpdateExpression="SET sms_code_sent_at=:t, sms_code_attempts=:z",
87            ExpressionAttributeValues={":t": now_ts(), ":z": 0},
88        )
```

Calling `POST /ui/mfa/sms/begin` writes `sms_code_attempts=0` to the challenge item. The per-attempt counter on `sms/verify` (`line 109: if attempts >= S.sms_code_max_attempts`) is therefore reset to zero every time `begin` is called. An attacker can call `begin` → `verify` (fail, attempts=1) → `begin` again (reset to 0) → `verify` indefinitely. The `enforce_lockout` call at line 102 keys off `(user_sub, ip, "mfa_sms")` and is trivially bypassed via XFF spoofing (SEC-008).

**TOTP lockout (`app/routers/ui_mfa.py:57-69`)**: `enforce_lockout` calls `check_rate_limit(pk=f"LOCK#{user_sub}#{ip}#{factor}")`. Without a trusted proxy, IP rotation gives a fresh bucket. There is no per-account (IP-independent) counter for TOTP guesses.

**Recovery codes (`app/routers/ui_mfa.py:209-231`)**: 48-bit entropy codes; no per-account global lockout. Each factor has its own `enforce_lockout(user_sub, ip, factor)` call but shares the same IP-dependent key.

### 2.2 Device-trust MFA bypass

**Device token generation (`app/services/device_trust.py:31-32`)**:

```python
31  def _device_token_hash(token: str) -> str:
32      return hashlib.sha256(token.encode("utf-8")).hexdigest()
```

The device token stored in the `ui_device` cookie is a plain `secrets.token_urlsafe` value (not shown, but the `record_device_login` caller at line 39 uses the standard pattern). The token is **not bound to the server secret** or the user identity beyond its storage in the DDB `sessions` table. Consequences:

1. **Stolen cookie = permanent MFA skip**: If an attacker obtains the `ui_device` cookie (via XSS, network sniffing if `Secure` is off per SEC-007, or physical device access), they can use it on a different machine to bypass MFA on every subsequent login, indefinitely, until the TTL (90 days by default, `ui_device_cookie_ttl_seconds` setting).

2. **Self-trust privilege escalation (`app/services/sessions.py:358-366`)**: When a session's device is new or location-mismatched, `require_fresh_mfa` is called. But a malicious user who already has an active session can call any endpoint that writes to `device_trust.trusted=True` (e.g., completing MFA once and having the app set `trusted=True`) — future logins from that device skip MFA even if the device is used from a different IP.

```python
358    if getattr(S, "ddb_sessions_table", ""):
359        device_info = record_device_login(request, resolved_user_sub)
360        if not device_info.get("trusted", False) and (
361            device_info.get("new_device")
362            or device_info.get("location_mismatch")
363            or device_info.get("token_mismatch")
364        ):
365            if compute_required_factors(user_sub):
366                require_fresh_mfa(…)
```

### 2.3 Non-constant-time code comparison

**Email MFA verify (`app/routers/ui_mfa.py:191`)**:

```python
191    if sha256_str(body.code.strip()) != expected:
```

Python's `!=` on strings uses a short-circuit comparison; the time taken is proportional to the length of the common prefix. For a 6-digit numeric code, the ciphertext (SHA-256 hex) is 64 characters; timing differences are measurable over a high-latency-stable network path. This affects:

- `app/routers/ui_mfa.py:191` — email MFA verify
- `app/routers/mfa_devices.py:276` — email MFA enroll verify (`sha256_str(…) != chal.get("email_code_hash")`)
- `app/routers/mfa_devices.py:332` — email remove verify (same pattern)
- `app/routers/password_recovery.py` — various recovery code comparisons (TOTP is safe via `pyotp.verify`; email/SMS code hash comparisons use `!=`)

**TOTP comparison** is handled by `pyotp.TOTP.verify` which is constant-time internally.

### 2.4 Password reset swallows revocation errors (`app/routers/password_recovery.py:150-157`)

```python
150    try:
151        revoke_all_sessions(username)
152    except Exception:
153        pass
154    try:
155        revoke_all_api_keys(username)
156    except Exception:
157        pass
```

After a successful password reset, session and API-key revocation failures are silently swallowed. If DynamoDB is temporarily unavailable or the revocation call throws, the old password was just changed but all existing sessions remain valid. An attacker who triggered the password reset (e.g., via a phishing recovery link) can replay an old session cookie after the reset completes.

### 2.5 Email/phone change without new-address verification (`app/routers/mfa_devices.py:230-267`)

The enroll flow for a new email MFA device sends the verification code to the existing (old) verified email, not to the **new** email address being added. An attacker who has temporary session access (e.g., a shared computer, stolen session) can add their own email as an MFA factor; once added, it becomes a password-reset identity and an MFA factor for future logins.

### 2.6 Step-up finalize lacks atomic "all factors passed" check

`mark_factor_passed` (called from verify endpoints) is a DynamoDB `UpdateExpression` that sets `passed.{factor}=True` on the challenge item. `_challenge_progress` (returned to the caller) then checks whether all required factors are in `passed`. There is no server-side atomic check — two concurrent verify calls for different factors could both read the challenge item, each mark their factor, and both return `progress.all_passed=True` before the other has written. The "finalize session" step that reads `passed` uses a separate `get_item` call, creating a read-then-write gap. A replay attack could submit the same factor twice to force a second `all_passed=True` response that bypasses the second factor.

### 2.7 Dev vs. prod

All bugs are present in dev and prod. In dev, the moto mock DB is local; lockout DDB writes and reads work identically. No flag gates the vulnerability.

## 3. Gap / Threat Analysis

### Per-account OTP brute-force (complete attack)

Precondition: attacker has the target username and has obtained a step-up challenge ID (requires knowing or guessing the password first, OR exploiting the passwordless / magic-link flow to get a challenge).

1. Loop: `POST /ui/mfa/sms/begin` → `POST /ui/mfa/sms/verify?code=000000` (fail) → `begin` again (reset counter) → `verify?code=000001` … → `999999`.
2. Each `begin` costs one SMS send (rate-limited separately by `can_send_verification`), but `verify` is unlocked. 10^6 codes at 1 req/sec = ~11.5 days. At 100 req/sec from a botnet: ~2.8 hours.
3. With XFF spoofing (SEC-008) the IP lockout at line 102 is also bypassed.

### Device-cookie theft (persistent MFA bypass)

Attacker steals `ui_device` cookie (via XSS before SEC-006 fix, or insecure HTTP before SEC-007 fix). Cookie has a 90-day TTL. Every subsequent login from the stolen cookie skips MFA. No mechanism currently exists to detect or revoke a device cookie short of rotating `ui_device_cookie_ttl_seconds` to 0 and forcing all users to re-authenticate.

### Silent revocation failure (post-reset session replay)

Attacker initiates a targeted account takeover: learn victim's email, trigger password reset, deliver a phishing link. Victim resets password. If `revoke_all_sessions` throws (DynamoDB transient error), victim's old session token remains valid. Attacker, who stole the old session token (e.g., from localStorage via XSS in the same attack chain), uses it after the password reset succeeds.

### Code sites that must change

- `app/routers/ui_mfa.py:83-88` — remove attempt counter reset from `begin`
- `app/routers/ui_mfa.py:57, 102, 176` — add per-account IP-independent lockout
- `app/routers/ui_mfa.py:191` — `hmac.compare_digest`
- `app/routers/mfa_devices.py:276, 332` — `hmac.compare_digest`
- `app/services/device_trust.py` — HMAC-bound token
- `app/routers/password_recovery.py:150-157` — fail-closed revocation
- `app/routers/mfa_devices.py:230-267` — verify new address, not old

## 4. Proposed Design / Fix

### 4.1 Per-account cumulative OTP lockout

**Remove the `sms_code_attempts=0` reset from `begin` (`app/routers/ui_mfa.py:86`)**: `begin` should only set `sms_code_sent_at` and send a new code; it must not reset `sms_code_attempts`.

Add a **per-account, IP-independent** attempt counter to `enforce_lockout`/`record_lockout_failure` that keys off `(user_sub, factor)` only — no IP component:

```python
check_rate_limit(pk=f"ACCTLOCK#{user_sub}#{factor}", window_seconds=3600, max_requests=10)
```

This counter is **separate** from the per-IP counter, is not reset by `begin`, and locks the account regardless of IP rotation. After 10 failures in one hour, `enforce_lockout` raises 429 until the window expires.

Codes should be single-use: on successful verify, wipe `email_code_hash`/`sms_code_sent_at` from the challenge item (already done partially at lines 134-142 for SMS success; add the same for email).

### 4.2 HMAC-bound device trust token

**`app/services/device_trust.py`** — bind the issued device token to `(user_sub, device_id)` using the server secret:

```python
import hmac, hashlib
from app.core.settings import S

def _issue_device_token(user_sub: str, device_id: str) -> str:
    raw = f"{user_sub}:{device_id}:{secrets.token_urlsafe(32)}"
    sig = hmac.new(S.api_key_pepper.encode(), raw.encode(), hashlib.sha256).hexdigest()[:16]
    return f"{raw}:{sig}"

def _verify_device_token(token: str, user_sub: str, device_id: str) -> bool:
    parts = token.rsplit(":", 1)
    if len(parts) != 2:
        return False
    raw, sig = parts
    expected = hmac.new(S.api_key_pepper.encode(), raw.encode(), hashlib.sha256).hexdigest()[:16]
    return hmac.compare_digest(sig, expected) and raw.startswith(f"{user_sub}:{device_id}:")
```

The token is cryptographically bound to `user_sub` and `device_id`, so a stolen cookie is valid only for the same user on the same device fingerprint.

Add `TTL` enforcement: re-verify the DDB `first_seen_at + ui_device_cookie_ttl_seconds` on each session check, not just on cookie creation.

Expose a `DELETE /ui/devices/{device_id}` endpoint that sets `trusted=False` and a `DELETE /ui/devices` (revoke all) for account recovery.

### 4.3 Constant-time code comparison

Replace all `sha256_str(code) != expected` comparisons with `hmac.compare_digest`:

```python
import hmac
if not hmac.compare_digest(sha256_str(body.code.strip()), expected):
    …  # fail
```

Apply to: `app/routers/ui_mfa.py:191`, `app/routers/mfa_devices.py:276`, `app/routers/mfa_devices.py:332`, and any recovery-code comparison in `app/routers/password_recovery.py`.

### 4.4 Fail-closed session revocation (`app/routers/password_recovery.py:150-157`)

```python
revoke_all_sessions(username)   # let exception propagate; do NOT swallow
revoke_all_api_keys(username)   # same
# If either throws, the password change is rolled back / the confirm returns 500
# Operator alert is fired; the user retries; revocation is retried
```

For resilience, add a background retry queue: if revocation fails, schedule a re-revocation job with exponential backoff. The immediate response should still be 500 so the client knows the operation is incomplete.

### 4.5 Verify new email/phone before adding as MFA factor

**`app/routers/mfa_devices.py:230-267`** — after the user provides the new email/phone, send a verification code to the **new address** and require it before writing `trusted=True` to the device record. Only after the new-address code is verified should it become a valid MFA factor.

### 4.6 Atomic step-up finalize

Use a DynamoDB `ConditionExpression` on the finalize step to atomically verify all factors passed before issuing the session:

```python
T.sessions.update_item(
    Key={"user_sub": user_sub, "session_id": challenge_id},
    UpdateExpression="SET finalized_at=:t",
    ConditionExpression="attribute_not_exists(finalized_at) AND passed.factor1=:t AND passed.factor2=:t",
    ExpressionAttributeValues={":t": True},
)
```

This prevents replay (second `finalize` call fails with `ConditionalCheckFailedException`) and race conditions.

**Dev/Prod parity (SECOPS-007):** All fixes use DynamoDB (moto in dev, AWS DynamoDB in prod) and HMAC (same code both environments). The `api_key_pepper` secret (already in `.env.local`) drives the device token binding. No AWS-only services required.

### Playwright E2E

`frontend/e2e/sec-009-mfa.spec.ts`:
- Alice submits 11 wrong TOTP codes (rotating XFF) → asserts 429 on the 11th even with fresh IPs.
- After a password reset, Alice's old session cookie returns 401.

### Manual QA

1. Log in as Alice; complete MFA; note `ui_device` cookie value. Log out. Log in again — MFA should be skipped (device trusted). Manually expire the DDB device record; log in again — MFA should be required.
2. Start a recovery flow; intercept `POST /ui/mfa/sms/begin`; resend it; verify `sms_code_attempts` in DynamoDB is not reset (use AWS console or `aws dynamodb get-item --endpoint-url http://localhost:8001`).

### Observability

- Alert on `acctlock_triggered` audit event (10+ OTP failures in 1h for any single account).
- Alert on device cookie token validation failures — indicates either a stolen cookie or a client bug.
- Dashboard: `mfa_verify_failure_total{factor="sms|totp|email"}` broken down by account vs IP lockout trigger.

### Rollout

1. Deploy constant-time compare (zero UX impact, no config change).
2. Deploy fail-closed revocation (may increase 500s in degraded DDB scenarios; acceptable trade-off).
3. Deploy per-account lockout counter without resetting on `begin` (test with Alice's account in dev first).
4. Deploy HMAC device token (invalidates all existing `ui_device` cookies — users re-authenticate device on next login).
5. Deploy new-address email verification (new UX step; coordinate with frontend).

**Rollback**: Step 4 (device token HMAC) can be rolled back by reverting the `_issue_device_token` change; all existing cookies will fail validation and users will need to re-trust their devices (forced MFA on next login — acceptable degraded mode).

**Effort estimate**: M/L (5–7 days). Multiple independent subsystems; device HMAC binding and new-address verification are the most complex.
