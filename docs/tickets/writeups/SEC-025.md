# SEC-025: Broadcast Session IDOR + Moderation Report-Flood + Q&A Vote Race — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

Three distinct weaknesses share the broadcast and moderation subsystems. First, the broadcast session lifecycle endpoints (`start`, `stop`, `DELETE`) check that the caller has the *operator* role but do not verify that the caller *owns* the session, enabling any operator to start/stop/delete any other creator's broadcast session (an IDOR). A `_require_session_owner` helper already exists and is used by privacy-management endpoints but was never applied to the lifecycle routes. Second, moderation report throttling is capped at 8 reports/user/60 s and 20 reports/IP/60 s with no subnet grouping, no cross-account coordinated-flood detection, and no human-review gate before auto-actions triggered by report count thresholds — a coordinated campaign with N accounts and proxy IPs can drive a victim's content past any takedown threshold without any individual account exceeding the per-account limit. Third, the Q&A upvote path in `broadcast_qa.py:214` performs an atomic DynamoDB conditional update to add the voter to the `upvoters` set in a single step but then performs a *separate* unconditional DynamoDB write at lines 245-249 to update the GSI sort key (`GSI1SK`) with the new count — a check-then-write race between two separate calls allows concurrent requests to both succeed at the conditional check and then both write stale counts to the GSI, resulting in double-incremented vote counts and incorrect ranking.

- **Type**: Security-fix
- **Priority/Severity**: High (IDOR: High; Report flood: High; Vote race: Medium)
- **Status**: Open
- **Owning area**: `app/routers/broadcast.py`, `app/routers/moderation.py`, `app/services/broadcast_qa.py`
- **Who is affected**: 🛡️ admin-abuse (IDOR: any operator targeting another creator); 🌐 any-user (moderation flood: coordinated attackers targeting victims); 🌐 any-user (Q&A race: concurrent voters rigging rankings)
- **Cross-references**: **SEC-005** (admin job-retry IDOR — same IDOR pattern in a different subsystem). **SECOPS-007** dev/prod parity. **SEC-008** trusted IP (relevant to moderation IP throttle logic).

**`app/routers/moderation.py:174-221`** — `_enforce_rate_limits`:
```python
user_count = _query_report_count(
    partition_key_name="reporter_user_id",
    partition_key_value=reporter_user_id,
    since_ts=now_ts - RATE_LIMIT_USER_WINDOW_SECONDS,
```

**Gaps**:

1. **No /24 subnet throttle**: `ip_hash` is a hash of the individual IP. Rotating through a /24 (256 addresses) gives an attacker 256 × 20 = 5120 reports per minute before any IP is throttled. With a botnet using a /16, this scales to millions.

2. **No per-content dedup across accounts**: `_find_recent_duplicate` at `moderation.py:287` deduplicates reports from the *same reporter* for the *same content* within `IDEMPOTENCY_WINDOW_SECONDS = 45`. Reports from *different* accounts for the same content are not deduplicated. A coordinated campaign with 8 accounts can file 8 × 8 = 64 reports per minute for a single piece of content.

3. **`report_count` incremented atomically but no auto-takedown threshold check exists**: Looking at `moderation_tickets_store.py:118`, `report_count` is incremented via `ADD #report_count :inc`. There is no code in the current codebase that compares `report_count` against a threshold and automatically takes down content. However, `priority` is set by `score_initial_priority` (line 76) and escalates based on topic severity; a high-`report_count` ticket with `priority="critical"` could trigger auto-actions in a future pipeline. The ticket notes "auto-takedown threshold" — while not currently implemented, the architecture is primed for it and the rate-limiting weakness would directly bypass it when built.

4. **No account-age weighting**: A fresh account (created seconds ago) has the same report weight as an established account. Coordinated attacks routinely use newly-created accounts.

### 2.3 Q&A Upvote TOCTOU — `broadcast_qa.py:214-253`

**`app/services/broadcast_qa.py:214-253`**:

```python
def upvote_question(session_id: str, question_id: str, user_id: str) -> Dict[str, Any]:
    try:
        T.broadcast_qa_questions.update_item(
            Key={"session_id": session_id, "question_id": question_id},
            UpdateExpression=(
                "ADD upvoters :uid "
                "SET upvote_count = if_not_exists(upvote_count, :zero) + :one"
            ),
            ConditionExpression="attribute_not_exists(upvoters) OR NOT contains(upvoters, :uid_str)",
            ...
        )                                    # ← atomic: adds uid to set AND increments count
    except ...:
        pass   # already upvoted — no-op

    # SEPARATE WRITE — not atomic with the above
    question = get_question(session_id, question_id)             # line 240: re-read
    upvote_count = int(question.get("upvote_count", 0))          # line 241: stale if concurrent
    upvote_padded = str(99999999 - upvote_count).zfill(8)
    ...
    T.broadcast_qa_questions.update_item(                         # line 245: unconditional write
        Key={"session_id": session_id, "question_id": question_id},
        UpdateExpression="SET GSI1SK = :sk",
        ExpressionAttributeValues={":sk": f"{upvote_padded}#{created_at}"},
    )
```

**Race condition**:

1. Thread A: conditional update succeeds, `upvote_count` becomes 5.
2. Thread B: conditional update also succeeds *before Thread A's count is committed* (DynamoDB guarantees single-item atomic updates, but the two operations are separate items in the write timeline; DDB does guarantee conditional-update atomicity on the first call — the race is in the *second* unconditional write).

Wait — DynamoDB single-item operations are atomic. The first `update_item` (conditional ADD + SET) is atomic. The second `update_item` (unconditional SET GSI1SK) is also atomic but operates on the *read-then-write* pattern: `get_question` (a separate read call) followed by the update. Between the first write and the `get_question` call, another thread could have incremented `upvote_count`. The `get_question` returns a value that may be one behind. Then the `GSI1SK` update writes an incorrect (stale) count to the sort key.

The specific double-count scenario:
1. Thread A: conditional ADD succeeds → `upvote_count=5`. Thread A calls `get_question` → reads count=5 → computes `GSI1SK="99999994#ts"` → writes it.
2. Thread B (almost simultaneously): conditional ADD also succeeds → `upvote_count=6`. Thread B calls `get_question` → reads count=5 (pre-A's write) → computes `GSI1SK="99999994#ts"` → writes it (same value as A's write, sort key unchanged even though count is 6).
3. Or: Thread B reads count=6 (post-A's write) → writes `GSI1SK="99999993#ts"`, which is correct — but Thread A's write then overwrites with `"99999994#ts"`, reverting the sort key.

The net effect is that `GSI1SK` and `upvote_count` can diverge: the displayed count is correct but the sort order is wrong, causing questions to appear out of order in the ranked Q&A list. In the specific scenario where the conditional update is bypassed by a race (unlikely with DynamoDB's strong-consistency conditional updates, but possible under high concurrency on the read path), `upvote_count` could be off by one.

A more deterministic exploit: a user submits two upvote requests simultaneously. DynamoDB's conditional update guarantees only one succeeds (the second fails the `NOT contains` condition). But `remove_upvote` at line 256 also has the same two-step pattern and could race with `upvote_question` to leave the GSI sort key in an inconsistent state.

## 3. Gap / Threat Analysis

### Threat 1: Broadcast Session Forced Termination / Hijack

**Scenario**: Competitor operator Bob terminates Alice's broadcast during a paid live event. Alice's viewers lose the stream; she may face SLA obligations. Bob can delete Alice's session record, destroying her broadcast history, recording metadata, and associated configuration. If start is triggered on an unpublished session, Alice's RTMP credentials may be activated without her knowledge.

**Impact**: Service disruption, financial loss to creator (lost subscription revenue, tip revenue, pay-per-view revenue), potential contractual liability. Platform trust eroded.

**Preconditions**: Attacker has operator role. In a multi-tenant platform, operator roles may be granted broadly.

### Threat 2: Report-Flood Targeted Censorship / Suspension

**Scenario**: A coordinated group of 20 accounts, each using a different IP address in a /24 subnet, each files 8 reports per minute for a victim's content. Total: 160 reports/minute, all within individual limits. The victim's content `report_count` escalates rapidly. When an auto-takedown pipeline is added (see SEC-025 architecture priming), the victim's content is auto-taken down without any single account hitting the throttle.

**Impact**: Content censorship, creator account suspension, reputational damage, GDPR/platform-abuse liability if the victim challenges the takedown.

**Even without auto-takedown**: High `report_count` escalates the moderation ticket priority, flooding the human review queue with false positives for the victim and degrading the quality of the entire moderation pipeline.

### Threat 3: Q&A Ranking Manipulation

**Scenario**: A malicious question submitter fires 50 concurrent upvote requests for their own question. The conditional update ensures each user counts once, but the GSI sort key becomes stale, causing the question to appear at the wrong position in the ranked list. More practically, a question planted by an attacker with slightly inflated ranking (via the stale GSI) rises to the top of a high-profile broadcast Q&A, guaranteeing it is answered on air.

**Impact**: Manipulation of live broadcast Q&A; brand/reputational risk for creators and the platform.

## 4. Proposed Design / Fix

### 4.1 Ownership Check for Start/Stop/Delete Session

The fix is surgical: add `_require_session_owner` (already implemented at line 1338) to the three lifecycle endpoints. However, `_require_session_owner` currently raises a 403 that says "Only the broadcaster can manage privacy" — which is incorrect for lifecycle operations. Create a more generic version:

```python
def _require_session_owner_or_admin(session_id: str, ctx: dict, action: str = "manage") -> "BroadcastSession":
    """Return the session; raise 403 unless caller owns it, is admin, or is root."""
    session = get_session(session_id)
    if ctx["user_sub"] != session.created_by and ctx.get("role") not in {"admin", "root"}:
        raise HTTPException(
            status_code=403,
            detail={"code": "BROADCAST_FORBIDDEN", "detail": f"Only the session owner can {action} this session."},
        )
    return session
```

Apply to the three routes:

**`start_session_route` (line 361)**:
```python
def start_session_route(session_id: str, ..., ctx: dict = Depends(_ctx)):

    ...
```

```python
def stop_session_route(session_id: str, ..., ctx: dict = Depends(_ctx)):
```

### 4.3 Q&A Upvote — Merge GSI Update into Single Atomic Write

The fix is to eliminate the separate `get_question` + unconditional `SET GSI1SK` writes and instead compute the new sort key atomically. DynamoDB does not support expressions that compute `99999999 - upvote_count` in a single `UpdateExpression` because `SET` cannot reference the result of `ADD` in the same call.

The correct pattern is to merge the GSI sort key update into the *same conditional `update_item`* call by computing the **new** sort key client-side as `99999999 - (current_count + 1)` before the write — since we know the count is increasing by exactly 1:

```python
def upvote_question(session_id: str, question_id: str, user_id: str) -> Dict[str, Any]:
    # Read current count first
    question = get_question(session_id, question_id)
    if not question:
        raise HTTPException(404, "Question not found")

    current_count = int(question.get("upvote_count", 0))
    created_at = int(question.get("created_at", 0))
    # Pre-compute sort key for count+1
    new_padded = str(99999999 - (current_count + 1)).zfill(8)
    new_sk = f"{new_padded}#{created_at}"

    try:
        T.broadcast_qa_questions.update_item(
            Key={"session_id": session_id, "question_id": question_id},
            UpdateExpression=(
                "ADD upvoters :uid "
                "SET upvote_count = if_not_exists(upvote_count, :zero) + :one, "
                "GSI1SK = :new_sk"                          # GSI update in same atomic call
            ),
            ConditionExpression=(
                "(attribute_not_exists(upvoters) OR NOT contains(upvoters, :uid_str)) "
                "AND upvote_count = :expected_count"        # optimistic lock on count
            ),
            ExpressionAttributeValues={
                ":uid": {user_id},
                ":uid_str": user_id,
                ":one": 1,
                ":zero": 0,
                ":new_sk": new_sk,
                ":expected_count": current_count,
            },
        )
    except ConditionalCheckFailedException:
        # Either already voted or count changed (concurrent vote); retry once
        return _retry_upvote(session_id, question_id, user_id)

    # Re-read for the SSE broadcast (no separate write needed)
    question = get_question(session_id, question_id)
    out = _question_out(question)
    broadcast_sse_publish(session_id, {"_type": "qa:upvote", **out})
    return out
```

The `upvote_count = :expected_count` condition adds an optimistic lock: if a concurrent vote changed the count, the condition fails and the caller retries (with updated count). This ensures:
- A user cannot vote twice (existing `NOT contains` guard).
- The GSI sort key is always written in the same atomic operation as the count increment.
- No stale count can be written to `GSI1SK`.

Apply the same single-write pattern to `remove_upvote`.

### Rollout Order

1. **Broadcast IDOR ownership check** — ship immediately; pure authorization bug with zero backward-compatible impact on legitimate use. No operator should be starting/stopping/deleting sessions they do not own.
2. **Q&A atomic upvote** — ship in the same release; non-breaking change to internal DynamoDB write pattern.
3. **Moderation subnet throttle** — ship as a follow-up; requires `MODERATION_REPORT_RATE_LIMIT_SUBNET_MAX` env var configuration and load testing to ensure the threshold does not block legitimate report flows.
4. **Account-age weighting + human-review threshold** — ship after (3); requires product decision on thresholds.

**Effort**: S (IDOR fix: <1 day; Q&A atomic: 1 day); M (moderation hardening: 2–3 days including subnet logic, threshold configuration, and ops runbook).

**Rollback**:
- IDOR fix: revert the `_require_session_owner_or_admin` call additions. Legitimate operators (session owners) are unaffected by rollback.
- Q&A atomic upvote: revert to two-step write. The data-consistency risk (stale GSI) is low-severity and self-correcting on the next vote.
- Moderation subnet throttle: disable via env var (`MODERATION_REPORT_RATE_LIMIT_SUBNET_MAX=9999`).

**Open questions**:
- Should the operator role be narrowed to *only* the owning creator, or should there be a concept of "session co-operator" where the creator explicitly grants another operator permission to control their session? The current `_require_session_owner` pattern (owner OR admin/root) is the correct minimum; co-operator delegation is a product-level extension.
- For moderation: what is the right `REPORT_HUMAN_REVIEW_THRESHOLD`? Too low floods the human review queue with low-signal tickets; too high allows significant harassment to persist. A data-driven baseline from historical report patterns should inform this value before shipping.
- Should the Q&A retry on optimistic lock failure be bounded (e.g., max 3 retries) with a 409 returned to the client on exhaustion, or should it be transparent to the user?
