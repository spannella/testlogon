# SEC-022: Stored Credentials Exposed via API Responses — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

Three distinct credential-exposure paths exist in the project management and file manager subsystems. First, the OAuth callback for Google Drive stores the encrypted refresh-token ciphertext (`refresh_token_ct_b64`) inside the `metadata` dict that is then passed verbatim in `GET /ui/projects/{id}/providers/{p}/credentials` responses. Second, the internal `get_provider_auth_context` function in `provider_credentials.py` returns the AWS `secret_access_key` (and a copy of it as `token`) in plaintext inside the returned dict, creating an information surface for any caller that logs or returns the context. Third, SFTP credentials are decrypted into a Python dataclass in memory with no scrubbing, creating a memory-dump surface.

- **Type**: Security-fix / hardening
- **Priority/Severity**: High
- **Status**: Open
- **Owning area**: `app/services/provider_oauth.py`, `app/services/provider_credentials.py`, `app/routers/filemanager.py`, `app/routers/projects.py`
- **Who is affected**: Any authenticated user who can read their own provider credential via the projects API; any process that logs the auth-context dict. Attacker class: 🌐 authenticated-user (self-access), ⚙️ config / logging side-channel.
- **Cross-references**: **SEC-008** (trusted IP hardening does not mitigate client-side exfil of ciphertext oracle). **SECOPS-007** dev/prod parity: KMS encrypt/decrypt is mocked in dev via `scripts/mock_kms_server.py` (port 7999); prod uses real AWS KMS. The ciphertext oracle attack and the cleartext `secret_access_key` exposure exist in both environments.

## 2. Current-State Investigation (what exists today)

### 2.1 Refresh-Token Ciphertext in `metadata` — `provider_oauth.py` + `projects.py`

**`app/services/provider_oauth.py:305-333`** — The OAuth callback builds a `metadata` dict and stores the encrypted refresh token in it:

```python
metadata: Dict[str, Any] = {
    "token_type": str(body.get("token_type") or "Bearer"),
    "expires_in": expires_in,
    "expires_at": expires_at,
}
if refresh_token:
    from app.core.crypto import kms_encrypt
    metadata["refresh_token_ct_b64"] = kms_encrypt(refresh_token)   # line 314
```

The `stored` object's `.metadata` dict — including `refresh_token_ct_b64` — is then returned directly:

```python
return {
    "provider": stored.provider,
    "scopes": stored.scopes,
    "metadata": stored.metadata,          # line 330: ciphertext included here
    ...
}
```

**`app/routers/projects.py:352-362`** — The GET endpoint returns `out.metadata` without filtering:

```python
@router.get("/providers/{provider}/credentials", response_model=ProviderCredentialOut)
def get_provider_credential_route(provider: str, ...):
    out = get_provider_credential(user, provider, org=org)
    return ProviderCredentialOut(
        ...
        metadata=out.metadata,     # line 359: refresh_token_ct_b64 sent to browser
        ...
    )
```

**`app/routers/projects.py:143-148`** — `ProviderCredentialOut` is defined in the same file:
```python
class ProviderCredentialOut(BaseModel):
    ...
    metadata: Dict[str, Any] = Field(default_factory=dict)
```

The Pydantic model does not strip any keys; all of `metadata` passes through.

**Why ciphertext exposure matters**: Even though the refresh token is KMS-encrypted, returning `refresh_token_ct_b64` to the client enables a *chosen-ciphertext oracle* attack. An attacker who also has access to the KMS decrypt API (e.g., via an exfiltrated AWS key in a separate bug, or a confused deputy attack on the mock KMS in dev mode) can decrypt the refresh token without needing the plaintext credentials. More concretely: in dev mode the mock KMS at port 7999 (`scripts/mock_kms_server.py`) is unauthenticated; if the Vite proxy is misconfigured or the port is reachable, the ciphertext in the browser can be sent to the mock KMS to recover the plaintext. Defense-in-depth requires that ciphertexts never leave the server.

### 2.2 AWS `secret_access_key` Returned in Plaintext — `provider_credentials.py:533-543`

**`app/services/provider_credentials.py:526-543`**:

```python
out = {
    "token": token,
    "provider": cred.provider,
    "org": cred.org,
    "scopes": list(cred.scopes or []),
    "metadata": dict(cred.metadata or {}),
}
if (cred.provider or "").lower() == "s3":
    try:
        payload = json.loads(token)
    except ValueError:
        payload = {}
    if isinstance(payload, dict):
        out["access_key_id"] = str(payload.get("access_key_id") or "")
        out["secret_access_key"] = str(payload.get("secret_access_key") or "")   # line 540
        out["session_token"] = str(payload.get("session_token") or "") or None
        out["token"] = out["secret_access_key"]    # line 542: also copied into "token"
return out
```

This dict is the `get_provider_auth_context` return value. It is consumed internally by file-manager S3 operations, but:

1. The function name (`get_provider_auth_context`) does not signal that its return value is sensitive; a developer adding a new endpoint that calls it and returns the result would silently expose the AWS secret.
2. FastAPI request logging or any structured log that serialises the return value will write the secret to log files.
3. In the current codebase, `get_provider_auth_context` result is fed into boto3 client creation; if an unhandled exception occurs mid-flight and the exception handler logs the local frame, the secret appears in logs.

### 2.3 SFTP Secrets in Memory — `routers/filemanager.py:1357-1369`

**`app/routers/filemanager.py:1350-1373`** — The health-check handler for SFTP mounts decrypts the full credential set into a `SftpConnectionConfig` object:

```python
cred = get_sftp_credential(owner=owner, mount_id=str(mount.auth_credential_ref), include_secret=True, actor_sub=actor_sub)
secret = cred.get("secret") or {}
session = acquire_sftp_session(
    SftpConnectionConfig(
        ...
        password=secret.get("password"),
        private_key=secret.get("private_key"),                  # line 1368
        private_key_passphrase=secret.get("private_key_passphrase"),
        ...
    )
)
```

The `SftpConnectionConfig` dataclass holds the plaintext private key as a Python string attribute. Python's garbage collector does not guarantee immediate memory reclamation. In CPython the object sits in the allocator's free list until the next GC cycle. If the process is killed (OOM, SIGKILL) while this is in scope, or if a memory profiler or core dump is captured, the private key is recoverable. There is no `SecureString` / `mlock` pattern or explicit zeroing (`ctypes.memset`) after the SFTP session is released.

## 3. Gap / Threat Analysis

### Threat 1: Ciphertext Oracle / Refresh-Token Recovery

**Scenario**: Alice authenticates Google Drive via OAuth. The callback stores `refresh_token_ct_b64` in DynamoDB metadata. Alice (or an attacker who has hijacked Alice's session) calls `GET /ui/projects/my-project/providers/google_drive/credentials`. The response JSON contains `"metadata": {"refresh_token_ct_b64": "AAAAAA..."}`. The attacker submits this ciphertext to the dev-mode mock KMS (`http://localhost:7999/decrypt`) — or, in prod, reuses the plaintext `access_token` that was separately exposed — and recovers the Google refresh token. With the refresh token, the attacker can mint new access tokens indefinitely, even after Alice revokes the OAuth connection in the app (because the refresh token was already exfiltrated).

**Impact**: Persistent Google Drive access for the attacker after the victim believes they have disconnected the integration.

**Preconditions**: Valid session cookie (self-access); mock KMS reachable in dev. In prod, requires a separate KMS key compromise, but the ciphertext still adds attack surface.

### Threat 2: AWS Secret Access Key Logging / Accidental Exposure

**Scenario**: An engineer adds a new admin endpoint that returns provider credential metadata. They call `get_provider_auth_context` and return the dict. The response now includes `"secret_access_key": "wJalr..."` in the JSON body. Alternatively, a FastAPI exception handler that logs the exception's local variables writes the secret to CloudWatch Logs.

**Impact**: AWS IAM credential exfiltration; full S3 bucket access for the S3 integration user.

### Threat 3: Memory-Dump SFTP Key Recovery

**Scenario**: Worker process experiences an OOM event or is profiled (e.g., `py-spy dump`). The `SftpConnectionConfig` object containing the plaintext private key is captured in the heap snapshot.

**Impact**: Complete SFTP credential compromise for any active connection at the time of the dump.

### Enumeration of Code Sites to Change

| File | Line(s) | Change |
|------|---------|--------|
| `app/services/provider_oauth.py` | 330 (`"metadata": stored.metadata`) | Strip `*_ct_b64` keys before return; expose `has_refresh_token: bool` |

| `app/models.py` or `app/routers/projects.py` | `ProviderCredentialOut` | Make `metadata` an allowlisted type rather than `Dict[str, Any]` |

## 4. Proposed Design / Fix

### 4.1 Strip Ciphertext from `metadata` Before Returning

Add a helper that removes any key matching a secret pattern:

```python
# app/services/provider_credentials.py  (or app/routers/projects.py)
_SECRET_META_KEYS = frozenset({
    "refresh_token_ct_b64",
    "access_token_ct_b64",
    "secret",
    "private_key",
    "password",
})

def _safe_metadata(meta: dict) -> dict:
    """Return a copy of meta with known-secret keys removed."""
    clean = {}
    for k, v in (meta or {}).items():
        if k in _SECRET_META_KEYS or k.endswith("_ct_b64") or k.endswith("_secret"):
            continue
        clean[k] = v
    return clean
```

In `provider_oauth.py:327-333`, replace `"metadata": stored.metadata` with:
```python
safe_meta = _safe_metadata(stored.metadata)
safe_meta["has_refresh_token"] = "refresh_token_ct_b64" in (stored.metadata or {})
return {
    "provider": stored.provider,
    "scopes": stored.scopes,
    "metadata": safe_meta,
    ...
}
```

Apply the same `_safe_metadata()` filter in `projects.py:346` and `projects.py:359`.

### 4.2 `ProviderCredentialOut` — Typed Metadata

Replace the catch-all `Dict[str, Any]` with a typed `ProviderMetadataOut` model:

```python
class ProviderMetadataOut(BaseModel):
    token_type: Optional[str] = None
    expires_in: Optional[int] = None
    expires_at: Optional[int] = None
    has_refresh_token: bool = False
    # add additional safe fields as providers are added
    model_config = {"extra": "ignore"}   # silently drops any unexpected (secret) keys
```

Setting `extra = "ignore"` means that even if `_safe_metadata` misses a key, Pydantic will not serialise it. This is a defence-in-depth second layer.

### 4.3 Do Not Return `secret_access_key` in Auth-Context Dict

In `provider_credentials.py:533-543`, the S3 branch should build credentials into a separate boto3-ready object rather than a plain dict that could be inadvertently returned:

```python
# Before
out["secret_access_key"] = str(payload.get("secret_access_key") or "")
out["token"] = out["secret_access_key"]

# After — keep secrets in an opaque credential object only
from app.core._aws_credentials import S3ProviderCredentials
out["_s3_credentials"] = S3ProviderCredentials(
    access_key_id=payload.get("access_key_id", ""),
    secret_access_key=payload.get("secret_access_key", ""),
    session_token=payload.get("session_token"),
)
# Remove 'token' from the returned dict for S3 provider; callers use _s3_credentials
out.pop("token", None)
```

Callers that need the actual credentials import `S3ProviderCredentials` and access the typed object. An `S3ProviderCredentials` instance that does not implement `__repr__` or `__str__` will not appear in logs.

Alternatively (simpler, less refactoring): rename the function to `_get_provider_auth_context_internal` and add a module-level `__all__` that excludes it, making it visually clear it is not an API surface. This does not fix the logging risk but creates a friction barrier.

### 4.4 SFTP Secret Zeroing

In `app/routers/filemanager.py`, restructure the health-check to zero sensitive fields after use:

```python
cred = get_sftp_credential(..., include_secret=True, actor_sub=actor_sub)
secret = cred.get("secret") or {}
try:
    session = acquire_sftp_session(
        SftpConnectionConfig(
            password=secret.get("password"),
            private_key=secret.get("private_key"),
            private_key_passphrase=secret.get("private_key_passphrase"),
            ...
        )
    )
    release_sftp_session(session)
finally:
    # Zero secret strings in-place before GC
    for k in ("password", "private_key", "private_key_passphrase"):
        if k in secret:
            secret[k] = "\x00" * len(secret[k] or "")
    del secret
```

For stronger guarantees in future, introduce a `SecretStr` wrapper that zeroes its internal buffer on `__del__`. The Python `secrets` module provides `token_bytes`; for string secrets, `ctypes.memset` can overwrite the CPython string object's internal buffer (with caveats on Python version / implementation).

### 4.5 Dev/Prod Parity (SECOPS-007)

- Dev: mock KMS at port 7999 behaves identically to real KMS for `encrypt`/`decrypt`. The `_safe_metadata` filter and `ProviderMetadataOut` model apply in both environments. The mock KMS should require a local shared secret (`MOCK_KMS_TOKEN`) to prevent unauthenticated decrypt calls even in dev.
- Prod: AWS KMS is not reachable from the browser even if the ciphertext were returned; the defence-in-depth fix (stripping ciphertext) is still correct because it prevents oracle attacks mediated by any other compromised KMS-capable credential.

### 4.6 Backward Compatibility

Removing `secret_access_key` from `get_provider_auth_context` result is an internal-only change (the function is not exposed via the HTTP API). The `metadata` change removes `refresh_token_ct_b64` from the public response — any client that depended on this undocumented field would break, but no legitimate frontend use case needs the ciphertext. Adding `has_refresh_token: bool` preserves the ability to render "Google Drive connected with refresh token" in the UI.

## 5. Testing, Verification & Rollout

### pytest Unit Tests

**`tests/test_provider_credential_security.py`**:

- `test_get_credential_has_refresh_token_flag`: same setup; assert `metadata.has_refresh_token == True`.
- `test_get_credential_no_secret_access_key`: seed an S3 provider credential; assert the GET response does not contain `secret_access_key` at any depth.
- `test_provider_metadata_out_strips_extra`: construct `ProviderMetadataOut(**{"token_type": "Bearer", "refresh_token_ct_b64": "evil"})` → assert `refresh_token_ct_b64` not in serialised output (Pydantic `extra=ignore`).
- `test_s3_auth_context_no_secret_in_dict`: call `get_provider_auth_context` for S3 provider; assert `"secret_access_key"` not in returned dict.
- `test_sftp_credential_zeroed_after_health_check`: mock `acquire_sftp_session`; call health-check endpoint; assert that the `secret` dict no longer contains plaintext values after the call returns.
- `test_oauth_callback_metadata_no_ct_b64`: call the OAuth callback mock; assert the returned `ProviderCredentialOut` dict does not include `refresh_token_ct_b64`.

### Playwright E2E

- Section 1: Connect Google Drive (mock OAuth); `GET /ui/projects/.../providers/google_drive/credentials`; assert response has `has_refresh_token: true` and no `refresh_token_ct_b64`.
- Section 2: Add S3 provider credential with access key; GET it back; assert no `secret_access_key` field in response JSON.

### Manual / QA Steps

1. In dev mode, add a Google Drive connection, then inspect the `GET /ui/projects/.../providers/google_drive/credentials` response in browser DevTools Network tab; confirm no `*_ct_b64` field is present.
2. Search server logs after a key-test failure; confirm no `secret_access_key` appears in INFO-level log lines.
3. Enable structured logging and simulate an S3 FileManager operation; assert no AWS credential leaks in CloudWatch (or local log file).

### Observability

- Add a structured log field `credential_fields_stripped: [list of keys removed]` at DEBUG level when `_safe_metadata` removes keys. This creates a detection signal if previously-unseen secret key names appear.
- Alert on any response body containing `_ct_b64` reaching the access log parser (can be done with a regex WAF rule in production).

### Rollout Order

1. `_safe_metadata` helper + `ProviderMetadataOut` typed model — zero breaking changes, safe to ship immediately.
2. `has_refresh_token: bool` field — additive, ship with (1).
3. S3 auth-context refactor — internal only, ship after (1) is deployed and verified.
4. SFTP zeroing — ship with (3) or independently.
5. Mock KMS auth token — ship to dev stack as follow-on hardening.

**Effort**: S–M (1–2 days for items 1–2; 1 day each for 3–4).

**Rollback**: Items 1–2 are purely subtractive on the response; the only risk is a frontend component that reads `refresh_token_ct_b64` directly (none found). Items 3–4 are backend-only, fully reversible.

**Open questions**:
- Should `secret_access_key` remain accessible to the internal S3 file-manager path via an opaque credential object, or should all S3 operations be mediated through a signing proxy that keeps the secret strictly server-side? The latter is the architecturally correct direction but requires larger refactoring (tracked separately in a future INFRA ticket).
- Are there other providers beyond `google_drive` and `s3` that store secrets in `metadata`? A one-time audit of `provider_credentials.py` to enumerate all `metadata_override` callers is recommended.
