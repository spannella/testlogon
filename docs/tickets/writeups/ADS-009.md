# ADS-009: User Ad Preferences & Ad-Free Tiers — Investigation & Implementation Write-up

## 1. Summary & Classification

ADS-009 gives end-users granular control over their ad experience: an ad-level selector (full/reduced/ad-free), per-category opt-outs (gambling, alcohol, etc.), a personalization toggle, and a platform-wide ad-free subscription tier. The ad-serving engine checks these preferences before serving any ad. A "hide this ad" feedback dialog allows users to report irrelevant or offensive ads.

- **Type**: Feature
- **Priority**: Medium
- **Status**: Not implemented — no `user_ad_prefs.py` service, no `AD_PREFS` DDB record type, no `/ui/ads/preferences` endpoint, no `AdPreferencesSection` frontend component
- **Owning area**: Advertising / User Experience
- **Affected personas**: End users (ad experience), advertisers (reach affected by opt-outs)
- **Cross-references**: ADS-004 (ad serving engine must read preferences), ADS-005 (sponsored post hide/feedback), subscription system (`app/services/subscription_plans.py`), `app/services/ad_placement.py` (existing per-creator ad-free check at line 178)
- **Dev/Prod parity (SECOPS-007)**: `billing` table stores preferences on DDB Local in dev, AWS in prod; no external services. The in-memory LRU cache described in the ticket design must be invalidated on each preference update — for single-worker dev uvicorn this is straightforward; multi-worker prod requires cache invalidation via DDB conditional reads or TTL only.

## 2. Current-State Investigation (what exists today)

### 2.1 What Is Present (Related Infrastructure)

**`app/services/creator_ad_prefs.py`** — This service manages *creator* ad settings (the `AD_SETTINGS` record for creators), not user ad preferences. It stores `allow_ads`, `allowed_ad_categories`, `min_cpm_cents`, and the `AD_BLOCK#{account_id}` advertiser block list — all keyed by `USER#{creator_sub}` in the `billing` table. This is a different concern from user ad preferences and is not ADS-009.

**`app/services/ad_placement.py:178`** — The `get_ad_config()` function checks `has_active_subscription()` when `ads_free_for_subscribers=True` on a video. This is the per-creator, per-video ad-free gate already in place. ADS-009 adds a platform-wide ad-free tier that trumps all surfaces.

**`app/services/ad_feedback.py`** — Records user feedback on individual creatives (hide, not_relevant, repetitive, offensive). This service exists and the `POST /ui/ads/feedback` endpoint is registered at `app/routers/ads.py:378`. The `AdFeedbackIn` model is imported at ads.py:16.

**`app/routers/ads.py:393`** — `GET /ui/ads/why/{creative_id}` returns a vague targeting category ("Based on your activity on the platform"). This is the only user-facing ad transparency endpoint.

### 2.2 What Is Missing

**No `app/services/user_ad_prefs.py`**: The file does not exist. There is no `get_ad_prefs()`, `update_ad_prefs()`, `set_platform_ad_free()`, `is_ad_free()`, or `should_serve_ad()` function anywhere in the codebase.

**No `AD_PREFS` record in `billing` table**: No `sk="AD_PREFS"` items are ever written. The `billing` table schema (in `scripts/local-ddb-init.py`) does not document this record type, though it would not require a schema change (it uses the existing table).

**No `/ui/ads/preferences` endpoint**: Neither `GET /ui/ads/preferences` nor `PATCH /ui/ads/preferences` exists in `app/routers/ads.py`.

**No preference check in ad serving**: `app/services/ad_serving.py` does not call any user preference function. Users with `ad_level="ad_free"` will still receive ads.

**No `AdPreferencesSection` frontend component**: Searching `frontend/src/pages/settings/` and `frontend/src/` finds no `AdPreferencesSection.tsx` or `AdFeedbackDialog.tsx`.

**No `UserAdPreferences` TypeScript type**: `frontend/src/api/types.ts` does not define this interface.

**No platform ad-free subscription plan**: No `PLATFORM_AD_FREE_PLAN` entry in `app/services/subscription_plans.py` or equivalent.

### 2.3 What Is Partially Present

**`ad_feedback` endpoint** (`app/routers/ads.py:378`): The feedback submission endpoint exists (ADS-005 predecessor). ADS-009 extends it with structured `feedback_type` validation and category-based reporting, but the base infrastructure is usable.

### 2.4 Dev vs. Prod Behavior of Missing Code

Once implemented: in dev, `billing` table (DDB Local) stores `AD_PREFS` records; `should_serve_ad()` reads them on each ad request. In prod, same DDB table on AWS. The in-memory LRU cache (60s TTL described in ticket §14.3) must use a process-local dict in dev (single worker) but needs careful consideration for multi-worker prod deployments — TTL-only invalidation (with 60s stale reads) is acceptable for preference changes.

## 3. Gap / Threat Analysis

### 3.1 All ADS-009 Features Are Unimplemented

The gap is total for this ticket: no backend service, no router endpoints, no DDB writes, no frontend component. The `ad_feedback` endpoint is the only functional overlap from a sibling ticket (ADS-005).

### 3.2 Dependencies Not Yet Wired

ADS-009's preference enforcement depends on `app/services/ad_serving.py` calling `should_serve_ad()` before serving. That integration point must be added. Without it, even if preferences are stored, they have no effect on ad delivery.

### 3.3 Platform Ad-Free Plan Requires Subscription System Integration

`set_platform_ad_free(user_sub, until_ts)` must be called by the subscription lifecycle handler when a user subscribes to or renews the platform ad-free plan. This requires coordination with `app/services/subscription_plans.py` and the subscription webhook/renewal flow. There is no hook point in the current subscription service for plan-type `"platform"` with `benefit="ad_free"`.

### 3.4 Category Opt-Out Enforcement Gap

The `AD_CATEGORIES` list must be consistent between the backend service and the ad targeting data. If an ad's `category` field in the `ad_campaigns` table uses different naming than the `excluded_categories` list in `AD_PREFS`, opt-outs will silently fail. The ticket design does not specify how ad categories are stored on campaigns — this needs to be aligned with ADS-001/ADS-003.

### 3.5 Reduced Ads Mode Frequency Cap Logic

The "reduced_ads" level (half frequency caps, no overlay ads) requires modifying frequency cap limits inside `app/services/ad_serving.py`. The ticket design shows `reduced_mode` being passed to frequency cap checks, but the specific logic for halving limits is not specified precisely. Overlay slot detection requires knowing `slot_type` from the serving request.

### 3.6 Abuse Potential

Users cannot set `ad_level="ad_free"` without a subscription (enforced in `update_ad_prefs()` by raising `ValueError`). `set_platform_ad_free()` is internal-only — not exposed via API, called only by the subscription system. The `AD_PREFS` record is session-scoped (no cross-user access). Category exclusions are enforced server-side.

## 4. Proposed Design / Fix

### 4.1 Create `app/services/user_ad_prefs.py`

Exactly as specified in the ticket design (§3.3). Key implementation notes:

- Store `AD_PREFS` at `pk=USER#{user_sub}`, `sk="AD_PREFS"` in `T.billing`.
- `DEFAULT_PREFS = {"ad_level": "full_ads", "excluded_categories": [], "personalized": True, "platform_ad_free_until": 0}`.
- `get_ad_prefs()` checks `platform_ad_free_until` expiry on read (no TTL in DDB, so do it in code).
- `update_ad_prefs()` rejects `ad_level="ad_free"` with `ValueError`.
- `should_serve_ad(user_sub, ad_category)` is the hot-path function called from `ad_serving.py`; must use an in-memory LRU cache with 60s TTL.

```python
# app/services/user_ad_prefs.py
from functools import lru_cache
import time

_pref_cache: dict = {}  # user_sub -> (timestamp, prefs)
_CACHE_TTL = 60

def _cached_prefs(user_sub: str) -> dict:
    entry = _pref_cache.get(user_sub)
    if entry and (time.time() - entry[0]) < _CACHE_TTL:
        return entry[1]
    prefs = get_ad_prefs(user_sub)
    _pref_cache[user_sub] = (time.time(), prefs)
    return prefs
```

On `update_ad_prefs()` or `set_platform_ad_free()`: `_pref_cache.pop(user_sub, None)`.

### 4.2 Add Router Endpoints to `app/routers/ads.py`

```python
# In app/routers/ads.py
@router.get("/preferences")
async def get_preferences(ctx=Depends(require_ui_session)):
    from app.services.user_ad_prefs import get_ad_prefs
    return get_ad_prefs(ctx["user_sub"])

@router.patch("/preferences")
async def update_preferences(body: dict, ctx=Depends(require_ui_session)):
    from app.services.user_ad_prefs import update_ad_prefs
    try:
        return update_ad_prefs(ctx["user_sub"], body)
    except ValueError as exc:
        raise HTTPException(status_code=400, detail=str(exc))
```

The feedback endpoint already exists at ads.py:378; no change needed.

### 4.3 Wire `should_serve_ad()` into `app/services/ad_serving.py`

At the top of `serve_ad()`, before any campaign evaluation:

```python
from app.services.user_ad_prefs import should_serve_ad as _pref_check
pref = _pref_check(user_id, ad_category=context.get("category", ""))
if not pref["serve"]:
    return _empty_response(pref["reason"])
reduced_mode = pref.get("reduced", False)
```

Inside the campaign loop, if `reduced_mode` is True and `slot_type == "overlay"`, skip.

### 4.4 Add `UserAdPreferences` TypeScript Type

In `frontend/src/api/types.ts`:

```typescript
export interface UserAdPreferences {
  ad_level: "full_ads" | "reduced_ads" | "ad_free";
  excluded_categories: string[];
  personalized: boolean;
  platform_ad_free_until: number;
  updated_at?: number;
}
```

### 4.5 Build `AdPreferencesSection.tsx`

New file at `frontend/src/pages/settings/AdPreferencesSection.tsx`. Section within the Settings page with:

- Radio group for ad level (full/reduced; ad-free disabled unless `platform_ad_free_until > Date.now()/1000`)
- Checkbox list for `AD_CATEGORIES`
- Toggle for `personalized`
- Save via `useMutation(updateAdPreferences, { onSuccess: invalidateQueries(["ad-prefs"]) })`
- `data-testid="ad-preferences-section"`

Import and render in `SettingsPage.tsx`.

### 4.6 Platform Ad-Free Subscription Integration

Add a hook in `app/services/subscription_plans.py` (or the subscription activation path) to call `set_platform_ad_free()` when a plan with `benefit="ad_free"` and `plan_type="platform"` is activated. Requires coordination with the subscription team.

### 4.7 Dev/Prod Parity (SECOPS-007)

No mocks needed — `billing` table is DDB-backed in both environments. The in-memory LRU cache needs no special treatment in dev (single uvicorn worker). In prod, accept 60s stale reads rather than building distributed cache invalidation.

### 5.4 Rollout

- **Phase 1**: Backend service + endpoints behind `USER_AD_PREFS_ENABLED=false`. No user-visible change.
- **Phase 2**: Wire `should_serve_ad()` into `ad_serving.py` with `USER_AD_PREFS_ENABLED=true`. Preferences now affect ad delivery.
- **Phase 3**: Deploy `AdPreferencesSection` UI and `PLATFORM_AD_FREE_PLAN_ENABLED=true`.
- **Rollback**: `USER_AD_PREFS_ENABLED=false` — `should_serve_ad()` returns `{"serve": True}` unconditionally; DDB preference records are unaffected.
