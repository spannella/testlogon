# ADS-015: Ad Creative with Affiliate Links & Discounts — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

ADS-015 links ad creatives to the existing affiliate-tracking and promo-code systems. When a creative has an `affiliate_code`, clicking the ad records a click via `app/services/affiliate_links.py` and appends `?ref={code}` to the redirect URL. When it has a `promo_code`, a 24-hour `ad_promo_code` cookie is set on click for auto-apply at checkout. A `promo_value_display` text field drives a badge overlay on the creative ("20% OFF"). ROAS (Return on Ad Spend) links affiliate conversions back to campaigns. Creators hosting ads with affiliate codes earn both ad CPM revenue and affiliate commissions.

- **Type**: Feature
- **Priority**: Medium
- **Status**: Implemented (service, router, models, click-redirect endpoint, frontend page, E2E spec partially written)
- **Owning area**: Ads / Monetization — creative attribution
- **User persona**: Advertiser (wants conversion tracking and ROAS); Creator (wants dual revenue); Consumer (discount auto-apply)
- **Cross-referenced tickets**: [[ADS-002]] creative management, [[ADS-004]] ad serving engine, [[AFFILIATE-001]] referral system, [[SECOPS-007]] dev/prod parity

## 2. Current-State Investigation (what exists today)

### 2.1 Service layer — `app/services/ad_creative_affiliate.py` (474 lines)

The service is fully implemented.

**Storage** (`app/services/ad_creative_affiliate.py:12-23`): Dedicated `ad_creative_affiliates` table (name from `S.ad_creative_affiliates_table_name` → `"AdCreativeAffiliates"`, `app/core/settings.py:1900`). PK = `CREATIVE#{creative_id}`, SK pattern:
- `CONFIG` — the link config (one per creative): `affiliate_code`, `promo_code`, `promo_value_display`, `click_through_url`, counters
- `CLICK#{ts}#{id}` — click attribution records
- `REDEEM#{ts}#{id}` — redemption attribution records

This is a separate table from `ad_creatives` (ADS-002). The creative's core record lives in `T.ad_creatives`; the affiliate/promo attachment lives in `T.ad_creative_affiliates`. The service resolves the creative owner by calling `ad_accounts.get_ad_account(account_id)` (line 70) to verify `owner_sub`.

**Code ownership validation** (`app/services/ad_creative_affiliate.py:77-106`): `validate_codes()` calls `affiliate_links.get_link_by_code(affiliate_code)` and checks `link.get("affiliate_user_id") != advertiser_id`. For promo codes it calls `promo_codes.get_promo_code_by_string(promo_code)` and checks `promo.get("creator_user_id") != advertiser_id`. Expired promo codes are rejected (line 99-103: checks `expires_at < now_ts()`). Returns `None` on success or `(status_code, message)` tuple on failure.

**Feature flag gate** (`app/services/ad_creative_affiliate.py:302`): `S.ad_creative_affiliate_enabled` (from `AD_CREATIVE_AFFILIATE_ENABLED`, default `"1"`, i.e. enabled — `app/core/settings.py:1898`). The flag gates affiliate-click recording and the promo cookie (line 302: `if S.ad_creative_affiliate_enabled and affiliate_code:`), but validation is always performed.

**Click handler** (`app/services/ad_creative_affiliate.py:280-345`): `handle_click()`:
1. Looks up the config record (`get_config(creative_id)` — GetItem on `CREATIVE#{creative_id}` / `CONFIG`)
2. If `affiliate_code` and flag enabled: calls `affiliate_links.record_click(link_id, tracking_code, ip, ua, referrer="ad_creative:{creative_id}")` (line 307-313). Best-effort wrapped in try/except.
3. Appends `?ref={affiliate_code}` to the redirect URL (lines 317-318).
4. Writes a click attribution record to `T.ad_creative_affiliates` with `sk = CLICK#{ts}#{click_id}` (lines 322-332).
5. Returns `{"redirect_url", "affiliate_code", "promo_code", "promo_value_display"}`.

**Redemption handler** (`app/services/ad_creative_affiliate.py:350-430`): `redeem()` validates the promo code at checkout time via `promo_codes.validate_and_redeem()` (exact function name needs verification — the service delegates to `promo_codes`). On success, records a `REDEEM#{ts}#{id}` entry and calls `affiliate_links.record_conversion()` if an affiliate code is set.

## 3. Gap / Threat Analysis

### 3.1 ROAS calculation not implemented

The `app/services/ad_roas.py` file does not exist. No `GET /ui/ads/campaigns/{id}/roas` endpoint exists. The ticket spec (section 3.7) provides a complete design. This is the most significant missing feature — advertisers cannot measure campaign effectiveness via conversion attribution.

### 3.2 E2E spec absent

`frontend/e2e/ad-affiliate-promo.spec.ts` does not exist. Without it, the redirect URL, cookie setting, and attribution recording are untested in the E2E suite.

### 3.3 Promo code cookie is not `httponly`

`httponly=False` at `app/routers/ad_creative_affiliate.py:181` is intentional (frontend JS reads it to auto-fill the promo field). However, this means XSS on any page under the same origin can read the cookie and extract the promo code, potentially allowing a script to claim the discount before the legitimate user reaches checkout. Mitigations: `samesite="lax"` limits cross-site theft; the cookie has a 24-hour max age; promo codes have limited redemption counts. This is an acceptable risk tradeoff.

### 3.4 Affiliate code ownership check uses `affiliate_user_id` field

`validate_codes()` at line 88 checks `link.get("affiliate_user_id") != advertiser_id`. This assumes the `affiliate_links` table stores the owner as `affiliate_user_id`. The field name must match the actual `affiliate_links.create_affiliate_link()` implementation — a mismatch would silently allow any code or always reject codes. This needs cross-checking with `app/services/affiliate_links.py`.

### 3.5 Promo code at creative creation time vs click time

Validation in `validate_codes()` checks if the promo code is expired at the time the affiliate config is saved. But the cookie is set at click time, which may be days later. If the promo code expires between creative creation and click, the cookie is still set but the checkout redemption will fail. The frontend should handle the failure gracefully (show "code expired" rather than a confusing checkout error).

### 3.6 Redirect URL injection risk

`click_through_url` is stored in the config record and used as the redirect destination. If an attacker can update a creative's `click_through_url` to a javascript: or data: URI, the redirect could execute code. Validation at creation time (enforced by Pydantic model `HttpUrl` type or startswith-HTTPS check) must be verified.

### 3.7 Creator dual revenue flow

The ticket spec describes that when an ad with an affiliate code runs on a creator's content, the creator earns both CPM revenue and affiliate commission. The affiliate commission is handled by `affiliate_links.record_conversion()` when a redemption occurs. However, the ad placement revenue (`_credit_ad_revenue()` in `ad_placement.py`) is credited to the `video.owner_user_id`. If the affiliate link belongs to the advertiser (not the creator), the creator only receives CPM revenue; the affiliate commission goes to the advertiser. The "dual revenue" claim in the spec assumes the creator owns the affiliate link — a use-case constraint not enforced in code.

## 4. Proposed Design / Fix

### 4.1 ROAS implementation — `app/services/ad_roas.py` (to create)

```python
def calculate_campaign_roas(
    *, campaign_id: str, start_date: str, end_date: str
) -> Dict[str, Any]:
    # 1. Query T.ad_billing GSI ByCampaign for total spend in date range
    # 2. Get all creative configs for campaign from T.ad_creative_affiliates
    # 3. For each creative with affiliate_code:
    #    query T.affiliate_links CONV# items where campaign_id matches
    # 4. ROAS = sum(conversion_revenue_cents) / ad_spend_cents
```

Requires the `affiliate_links.record_conversion()` function to store `campaign_id` and `creative_id` (currently the `source_id` parameter at line 312 carries `creative_id` — verify the field name in the stored record).

Add `GET /ui/ads/creatives/campaigns/{campaign_id}/roas` to `app/routers/ad_creative_affiliate.py` (or a new `ad_roas.py` router). Owner-gated via campaign → account → `owner_sub` check.

### 4.2 E2E spec — `frontend/e2e/ad-affiliate-promo.spec.ts`

Create with 18 tests matching ticket sections 405-408. Key scenarios:
- Create creative with affiliate code → verify field saved (GET response)
- Click redirect → 302 to URL with `?ref=` param, cookie header present
- Verify affiliate click count incremented
- Redeem promo at checkout → discount applied, redemption recorded
- Non-owner affiliate code → 403
- ROAS: no conversions → `roas: 0`; after recording conversion → `roas > 0`

Auth pattern: `injectAuth(page, "alice")` for owner ops; `injectAuth(page, "bob")` for viewer/consumer ops. Must pre-create affiliate link and promo code for Alice before attaching to creative.

### 4.3 `affiliate_user_id` field name verification

Cross-check `app/services/affiliate_links.py:create_affiliate_link()` for the actual field name used to store the owner. If it is `creator_user_id` (consistent with promo codes), update `validate_codes()` line 88 accordingly.

### 4.4 Redirect URL validation

Add to `app/models.py` `AdAffiliateConfigCreate`:
```python
click_through_url: str = Field(pattern=r"^https?://")
```
Or use Pydantic's `HttpUrl` type which validates scheme and host.

### 4.5 Dev/Prod parity (SECOPS-007)

Already satisfied for existing features:
- All DDB operations via `T.*` handles from `app/core/tables.py`
- `affiliate_links` and `promo_codes` services are DDB-backed (no external APIs)
- The click redirect sets a browser cookie — works identically in dev and prod
- Feature flag `AD_CREATIVE_AFFILIATE_ENABLED` in `app/core/settings.py:1898` gates the active paths

For ROAS: the ad-billing query requires `T.ad_billing` which is DDB Local in dev. No AWS services needed.

### 5.5 Seed requirements for E2E

The planned E2E spec (`frontend/e2e/ad-affiliate-promo.spec.ts`) requires:
- Alice has an affiliate link (created via `POST /ui/affiliate-links`) with a known tracking code
- Alice has a promo code (created via `POST /ui/promos`) with discount type and value
- An ad creative exists for Alice's account (depends on ADS-002 being active, or seeded via DDB direct write)

Because ADS-002 (creative management) is a sibling ticket, the E2E spec will need to either seed the creative record directly in DDB or use a mock creative ID that the `ad_creative_affiliates` table references. The `_resolve_creative()` function at line 54 first queries the `ad_creatives` GSI `ByCampaignId` and falls back to `get_creative_by_id()` — direct DDB seed of the creative record is the offline-safe path for E2E.

### 5.6 Effort and risks

**Effort**: M for remaining gaps — ROAS service: 1 day; ROAS endpoint + model: 0.5 day; E2E spec (18 tests): 1 day; unit tests: 0.5 day. Frontend checkout auto-apply (`ad_promo_code` cookie reading in `CheckoutPage.tsx`): ~0.5 day.

**Risks**:
- **ROAS aggregation data dependency**: ROAS requires `campaign_id` stored on affiliate conversion records (`T.affiliate_links` `CONV#` items). The current `affiliate_links.record_conversion()` signature should be checked to confirm it accepts and stores a `campaign_id` field. If not, ROAS calculation will always return zero conversions even after purchases.
- **Promo cookie auto-apply not yet wired**: The ticket spec (section 3.6) describes JavaScript in `CheckoutPage.tsx` that reads the `ad_promo_code` cookie and auto-fills the promo input. Confirm this code exists in `frontend/src/pages/shop/CheckoutPage.tsx` — the file was not inspected.
- **Affiliate code ownership field mismatch** (section 3.4): `validate_codes()` checks `link.get("affiliate_user_id")` at line 88 but promo codes use `promo.get("creator_user_id")` — inconsistent field naming between the two services. A mismatch in the affiliate field name would silently pass all ownership checks (returning `None` from the dict get).
- **ROAS with ADS-001 dependency**: The ROAS calculation chains from creative → campaign → account → spend. If `T.ad_campaigns` table (ADS-001) is not provisioned in dev, the ROAS query will silently return zero spend. Add defensive fallback to return `"no_campaign_data"` status when the table is missing.
