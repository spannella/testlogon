# VOD-003: Async Transcode Job Queue and Worker — Investigation & Implementation Write-up

> Status: **Implemented**. The full queue and worker exist. This write-up documents the implementation details, the dev/prod split, and two notable bugs.

## 1. Summary & Classification

VOD-003 provides the orchestration layer that bridges a video upload (VOD-002) with actual FFmpeg execution (VOD-004). It introduces:
- A `TranscodeJobs` DynamoDB table for job persistence with conditional state transitions
- A polling worker (`transcode_worker_loop`) that runs as an asyncio task within the FastAPI process, claims jobs, dispatches them to FFmpeg, tracks progress, handles retries with exponential backoff, and uploads outputs to S3 after completion
- REST endpoints to submit jobs, check status, and list jobs by status or video

The design is intentionally dual-mode: in dev, everything runs in-process (no SQS, no Lambda, no ECS); in prod, the same store can be driven by external SQS workers or by the in-process loop.

- **Type**: Feature (async processing infrastructure)
- **Priority**: P0 — without this, video files uploaded in VOD-002 are never transcoded
- **Status**: Fully implemented
- **Owning area**: Backend / transcoding pipeline
- **User persona**: System (automatic pipeline), Creator (status polling), Admin (queue monitoring)
- **Dependencies**: VOD-001 (VideoMetadata table), VOD-002 (source S3 key), VOD-004 (FFmpeg executor), VOD-005 (S3 upload after transcode)
- **SECOPS-007 parity**: In dev, worker runs in-process; in prod, same worker code or SQS-driven Lambda/ECS. Same DynamoDB store, same state machine.

### 2.1 DynamoDB Table — `scripts/local-ddb-init.py:920`

TableDef(

    "job_id",                          # PK: "tj_<uuid4_hex>"
    gsi=[
        {"index_name": "ByStatusCreatedAt", "partition_key": "status", "sort_key": "created_at"},

### 2.2 Job Store — `app/services/transcode_job_store.py`

The store is 349 lines and implements all expected CRUD and state-transition operations:

**`create_job`** (line 31): Generates `tj_<uuid4().hex>`, sets `status="queued"`, `status_created_at=f"queued#{ts}"`, stores `rendition_profiles`, `source_uri`, `watermark_policy`, `drm_policy`, `priority`. Uses `put_item` without a conditional expression — no idempotency guard on duplicate `job_id` (UUID collision is negligible).

**`get_job`** (line 75): Simple `get_item`, raises 404 if not found.

**`claim_job`** (line 86): Critical conditional update:
```python
T.transcode_jobs.update_item(
    ...
    ConditionExpression=(
        "#s = :queued AND "
        "(attribute_not_exists(next_retry_at) OR next_retry_at <= :now)"
    ),
    ExpressionAttributeValues={":running": "running", ":queued": "queued", ":wid": worker_id, ...},
)
```
Returns `True` on success, `False` on `ConditionalCheckFailedException`. This is the core race-condition guard: only one worker can claim a given job, even if multiple workers poll simultaneously. The `next_retry_at` check prevents claiming a job scheduled for future retry before its backoff window has elapsed.

**`update_job_progress`** (line 116): Updates `progress_pct`, `current_rendition`, `renditions_completed`, and optionally `eta_seconds`. No condition — progress can be written by any caller. Throttled by the worker via `transcode_progress_update_interval_seconds`.

**`complete_job`** (line 147): Conditional update requiring `#s = :running` — prevents double-completion.

**`complete_job_with_outputs`** (line 181): Extended completion that atomically stores all VOD-005 output metadata: `output_hls_manifest_uri`, `output_s3_prefix`, `output_total_bytes`, `output_object_count`, `output_upload_duration_seconds`, `output_thumbnail_keys`, `output_playback_url`, `output_playback_expires_at`. Requires `#s = :running AND worker_id = :wid` — the worker_id guard prevents a late-arriving duplicate from overwriting a result already written by the actual completing worker.

**`fail_job`** (line 244): Implements the retry logic. If `attempt + 1 < max_attempts`, transitions back to `queued` with:
```python
next_retry_at = _compute_next_retry_at(new_attempt)
```
`_compute_next_retry_at` (line 344) uses exponential backoff with jitter:
```python
delay = min(MAX_RETRY_DELAY, BASE_RETRY_DELAY * (2 ** attempt))   # 30s, 60s, 120s... capped at 600s
jitter = random.randint(0, delay // 4)
return now_ts() + delay + jitter
```
On terminal failure (`attempt + 1 >= max_attempts`), transitions to `failed`.

**`list_jobs_by_status`** (line 297): Queries `ByStatusCreatedAt` GSI with `ScanIndexForward=True` (oldest first) for FIFO processing. Returns a JSON-encoded cursor string for stateless pagination.

**`list_jobs_by_video`** (line 329): Queries `ByVideoId` GSI, `ScanIndexForward=False` (newest first) — returns all jobs for a video without pagination.

### 2.3 Transcode Worker — `app/services/transcode_worker.py`

The worker is 345 lines and implements the full asyncio background loop.

**`start_transcode_worker_task`** (line 334): Called from `main.py:471` at app startup. If `S.transcode_worker_enabled` is False, registers the task as disabled in `job_registry` and returns. If enabled, calls `asyncio.create_task(transcode_worker_loop())`.

**`transcode_worker_loop`** (line 38): The main polling loop:
1. Initializes `asyncio.Semaphore(max_concurrent)` to limit concurrent FFmpeg processes
2. Polls `list_jobs_by_status("queued", limit=max_concurrent)` every `poll_interval` seconds
3. For each job, checks `next_retry_at` to skip future-scheduled retries
4. Checks `_CONCURRENCY_SEMAPHORE.locked()` to respect the concurrency limit
5. Dispatches `_process_job_with_semaphore(job)` as an asyncio task (non-blocking)
6. Reports poll metrics to `job_registry`

**`execute_transcode_job`** (line 86): End-to-end job execution:
1. Calls `claim_job` — exits gracefully if claim fails (another worker got it)
2. Creates `scratch_dir = Path(S.transcode_scratch_dir) / job_id`
3. Iterates over `renditions`, calling `_run_ffmpeg_for_rendition` for each
4. Calls `write_master_playlist(output_dir)` from `ffmpeg_abr_pipeline.py`
5. Optionally extracts thumbnails via `vod_thumbnail_extractor.extract_thumbnails`
6. Uploads outputs via `vod_s3_uploader.upload_transcode_outputs`
7. Generates playback URL via `vod_playback_url.mint_vod_playback_url`
8. Calls `complete_job_with_outputs` (VOD-005 atomic completion)
9. Attempts `transition_video_status(..., to_status="published")` — wrapped in try/except
10. Attempts `vod_file_bridge.link_video_to_filemanager` (VOD-014)
11. On any exception: calls `abort_incomplete_uploads`, then `fail_job`
12. `finally`: `shutil.rmtree(scratch_dir, ignore_errors=True)` — always cleans up scratch

The scratch directory lifecycle is the critical resource management point. Each job gets an isolated directory `tmp/transcode-scratch/{job_id}/`, which holds the downloaded source file, per-rendition HLS output subdirectories, thumbnails, and encryption keyinfo files. `shutil.rmtree` in the `finally` block ensures cleanup even on crash — unless the process is killed with SIGKILL (no signal handler for that case).

### 2.5 Dev vs Prod Parity (SECOPS-007)

| Concern | Dev Mode | Prod Mode |
|---|---|---|
| Worker process | In-process asyncio task (same uvicorn process) | External: same code as Lambda/ECS task, or same in-process pattern |
| DynamoDB | Local DDB on port 8001 | Real DynamoDB |
| S3 source | moto in-process (`vod/{user}/raw/...`) | Real S3 (`video_upload_bucket`) |
| S3 output | moto in-process (`vod-output` bucket) | Real S3 (`vod_output_bucket`) |
| FFmpeg binary | Local `ffmpeg` on PATH | Same — `get_ffmpeg_path()` uses `shutil.which("ffmpeg")` then `S.ffmpeg_binary_path` |
| Scratch dir | `tmp/transcode-scratch/` relative to CWD | `TRANSCODE_SCRATCH_DIR` env var, absolute path on EFS/NVMe |
| Worker enabled | `TRANSCODE_WORKER_ENABLED=1` (defaults to `DEV_MODE`) | `TRANSCODE_WORKER_ENABLED=0` on API instances; separate worker deployment |

The worker code is strictly identical in both environments. The only gate is `S.transcode_worker_enabled`. In a real prod deployment, API instances set `TRANSCODE_WORKER_ENABLED=0`; separate worker instances set it to `1`. Both talk to the same DynamoDB tables and S3 buckets.

## 3. Gap / Threat Analysis

### 3.1 The "queued" Status Bug

As noted in VOD-001 §3.1: `transcode_jobs.py:103` calls `transition_video_status(video_id=body.video_id, to_status="queued")`. The string `"queued"` is not a valid `VideoStatus` and has no entry in `_ALLOWED_TRANSITIONS`. The 409 is silently swallowed by `except Exception: logger.warning(...)`. The video stays in `"created"` status after job submission.

Additionally, when the worker completes successfully, `transcode_worker.py:202` tries `transition_video_status(video_id=..., to_status="published")`. This works because `"published"` is a valid status; however it requires the video to be in `"approved"` state (per `_ALLOWED_TRANSITIONS`). A newly uploaded video that went through `created → pending_encoding → encoding → pending_review` has never been admin-approved, so the transition `pending_review → published` is also illegal. The transition would raise 409, be swallowed, and the video would stay in `pending_review` with a valid playback URL but not actually published.

The correct workflow after encoding completes is to transition to `pending_review`, not directly to `published`. Admin approval is the gate.

### 3.2 Missing `pending_encoding` Status Transition on Job Submit

The video pipeline should update the video record's status to `pending_encoding` when a transcode job is submitted (signaling "queued for processing"), then to `encoding` when the worker claims the job. Currently, neither transition happens reliably:
- Submit → tries `"queued"` (illegal) → stays `"created"`
- Claim → no status transition code in `claim_job`

This means the `ByStatusCreatedAt` GSI for `pending_encoding` and `encoding` are always empty, breaking admin dashboards that query those statuses.

### 3.3 Concurrency Limit Doesn't Account for Restart

`_CONCURRENCY_SEMAPHORE` is an in-process `asyncio.Semaphore`. If the process restarts mid-transcode, the semaphore resets to `max_concurrent` even if N jobs are still marked `running` in DynamoDB from the previous process run. On restart, the worker will claim up to `max_concurrent` more jobs, potentially running 2× `max_concurrent` jobs simultaneously. The fix is a startup check that re-queues `running` jobs owned by this host's `worker_id` if they are older than `transcode_rendition_timeout_seconds`.

### 3.4 Scratch Directory Under CWD

`TRANSCODE_SCRATCH_DIR` defaults to `tmp/transcode-scratch`. On a production host, this creates files in the application's working directory, which may be on a root volume with limited space. The setting should default to `/tmp/transcode-scratch` or an explicit EFS mount path. This is a configuration concern rather than a code bug.

### 3.5 SQS Integration Path Not Wired

The ticket spec mentions an SQS option for prod (`sqs_client()` factory exists in `app/core/aws_clients.py`). The current `create_job` function writes only to DynamoDB and does not publish to SQS. There is no SQS consumer. For a high-volume production deployment that requires horizontal scaling of the transcoding fleet, SQS would be needed. The current design is appropriate for single-host or small-scale deployments.

## 4. Proposed Design / Fix

### 4.1 Fix Status Transitions in the Job Submission Flow

In `app/routers/transcode_jobs.py`, change line 103:
```python
# Before:
transition_video_status(video_id=body.video_id, to_status="queued")
# After:
transition_video_status(video_id=body.video_id, to_status="pending_encoding")
```

In `app/services/transcode_worker.py`, add status update after `claim_job` succeeds (line 95):
```python
if not claim_job(job_id, wid):
    return
# Add:
try:
    from app.services.video_metadata_store import transition_video_status
    transition_video_status(video_id=job["video_id"], to_status="encoding")
except Exception:
    logger.warning("Could not transition video %s to encoding", job["video_id"])
```

And change the completion transition at line 202 from `to_status="published"` to `to_status="pending_review"`:
```python
transition_video_status(video_id=job["video_id"], to_status="pending_review")
```

### 4.2 Startup Recovery for Orphaned Running Jobs

In `start_transcode_worker_task`, add a one-time recovery scan:
```python
async def _recover_orphaned_jobs():
    wid = _worker_id()
    result = list_jobs_by_status("running", limit=50)
    for job in result.get("items", []):
        if job.get("worker_id") == wid:
            fail_job(job["job_id"], "Worker restarted", int(job.get("attempt", 0)))
```
Call this at the start of `transcode_worker_loop` before entering the poll loop.

### 4.3 Dev/Prod Parity (SECOPS-007)

Already satisfied as documented in §2.5. No changes needed.
