# ADS-010: Content Provider Ad Controls — Investigation & Implementation Write-up

## 1. Summary & Classification

ADS-010 gives content creators (content providers) granular control over advertising on their content. Creators can toggle ads globally and per-content, set minimum CPM floors, block specific advertisers, view their ad revenue breakdown by content, and inspect which advertisers ran on their content (transparency). The ticket extends the basic ADS-003 creator ad preferences into a full content-provider ad management system with a dedicated `content_ad_controls_router` and a `content_ad_controls.py` service.

- **Type**: Feature
- **Priority**: Medium
- **Status**: Substantially implemented — `app/services/content_ad_controls.py` (361 lines), `app/routers/content_ad_controls.py`, and `frontend/src/pages/ads/ContentAdControlsPage.tsx` / `AdRevenueBreakdownCard.tsx` all exist. However, several gaps remain: min-CPM enforcement in ad serving is absent, transparency recording is unhooked from the billing pipeline, and the revenue share is stored in basis points (bps) rather than percentage (conflicting with ADS-007's `PLATFORM_REVENUE_SHARE_PCT=30`).
- **Owning area**: Advertising / Creator Tools
- **Affected personas**: Content creators (revenue and ad control), advertisers (reach constraints)
- **Cross-references**: ADS-003 (creator ad prefs base), ADS-004 (ad serving — min-CPM check), ADS-007 (revenue split — transparency recording), ADS-019 (self-placed ads), `app/services/creator_ad_prefs.py` (base block list)
- **Dev/Prod parity (SECOPS-007)**: `billing` table and `ContentAdOverrides` table (DDB Local in dev, AWS in prod); same code path. No outbound calls.

## 3. Gap / Threat Analysis

### 3.1 Min-CPM Enforcement Not Wired into Ad Serving

`get_creator_revenue_share_bps()` and `get_full_ad_settings()` are defined but the min-CPM check described in ticket §3.4 is not present in `app/services/ad_serving.py`. No call to `get_full_ad_settings()` or `creator_ad_prefs.get_creator_ad_settings()` exists inside the campaign selection loop of the ad-serving engine. Ads with bid below a creator's minimum CPM will still be served.

To verify: search `app/services/ad_serving.py` for `min_cpm` — no results.

### 3.2 `record_transparency()` Never Called

`content_ad_controls.record_transparency()` (line 243) is defined but is never invoked from `app/services/ad_billing.py`. The ticket design (§4.2) specifies calling it from `ad_billing._split_revenue()` after crediting the creator. Without this hook, `get_advertiser_transparency()` will always return an empty array.

### 3.3 Revenue Share Unit Mismatch (`bps` vs `pct`)

`content_ad_controls.py` stores and returns revenue share in basis points (`revenue_share_bps`, default 7000 = 70%). `ad_billing.py` uses `PLATFORM_REVENUE_SHARE_PCT = 30` (a plain integer percentage, line 19). The two systems are not connected: `_split_revenue()` always uses the hard-coded 30% constant and never reads `get_creator_revenue_share_bps()`. Per-creator revenue share overrides (e.g., 80/20 for top creators) have no effect on actual billing.

### 3.4 `apply_content_override_to_config()` Integration Status

`apply_content_override_to_config()` (service line 195) is implemented but its call site in `app/services/ad_placement.py` needs verification. If `ad_placement.py`'s `get_ad_config()` function (around line 178) calls `apply_content_override_to_config()`, per-content overrides will be respected. If not, the overrides table is populated but never consulted during serving.

### 3.5 `_require_content_owner()` Only Enforces for Videos

`content_ad_controls_router.py:31–49` — `_require_content_owner()` only calls `get_video()` for `content_type="video"`. For posts, broadcasts, and other content types, ownership is not verified. Any authenticated user can set overrides for any non-video content ID, potentially setting `ad_enabled=False` on content they don't own.

### 3.6 `revenue-share` PUT Endpoint Lacks Admin Gate

`PUT /ui/ads/content-controls/revenue-share` (router line 116) allows any session user to set their own revenue share to any value between 0 and 10000 bps. The ticket security notes (§7) state "revenue share percentage not modifiable via API (admin-only)". The current implementation contradicts this: any creator can set `revenue_share_bps=10000` (giving themselves 100% of ad revenue and 0% to the platform). This is a significant revenue leakage risk.

## 4. Proposed Design / Fix

### 4.1 Wire Min-CPM Check into Ad Serving (`app/services/ad_serving.py`)

Inside the campaign selection loop, after the advertiser block-list check, add:

```python
# Inside serve_ad() campaign loop:
from app.services.content_ad_controls import get_full_ad_settings
creator_settings = get_full_ad_settings(creator_id)
min_cpm = int(creator_settings.get("min_cpm_cents", 0))
if min_cpm > 0:
    bid_cpm = int(campaign.get("bid_cpm_cents", 0))
    if bid_cpm < min_cpm:
        continue  # Skip this campaign — bid too low
```

Cache `creator_settings` per-creator in the same in-memory LRU as user ad prefs (60s TTL) to avoid a DDB read per ad request.

### 4.2 Call `record_transparency()` from `ad_billing._split_revenue()`

In `app/services/ad_billing.py:_split_revenue()`, after writing the creator credit (line 167):

```python
# After T.billing.put_item(Item=credit_item):
try:
    from app.services.content_ad_controls import record_transparency
    record_transparency(
        creator_id=creator_id,
        account_id=meta.get("account_id", ""),
        company_name="",  # Resolved from ad_accounts if available
        month=month_key,
        impressions=1 if meta.get("model") == "cpm" else 0,
        clicks=1 if meta.get("model") == "cpc" else 0,
        revenue_cents=creator_share,
    )
except Exception:
    pass  # Best-effort; doesn't block billing
```

The `account_id` must be passed through `meta` from the original charge call. Currently `meta` includes `creative_id` and `content_id` but not `account_id`; add it in `_process_charge()`.

### 4.3 Connect Revenue Share to Billing Engine

In `app/services/ad_billing.py:_split_revenue()`, replace the hard-coded `PLATFORM_REVENUE_SHARE_PCT`:

```python
# Resolve creator's negotiated revenue share
try:
    from app.services.content_ad_controls import get_creator_revenue_share_bps
    creator_bps = get_creator_revenue_share_bps(creator_id)
    creator_share_pct = creator_bps / 100  # Convert bps to pct (7000 bps = 70%)
except Exception:
    creator_share_pct = 100 - PLATFORM_REVENUE_SHARE_PCT  # fallback to default
creator_share = int(charge_cents * creator_share_pct / 100)
platform_share = charge_cents - creator_share
```

### 4.4 Gate `revenue-share` PUT on Admin Role

```python
# content_ad_controls.py router:
from app.auth.policy import require_admin_or_root
from app.auth.deps import AuthenticatedUser

@content_ad_controls_router.put("/revenue-share")
def set_revenue_share_endpoint(
    body: RevenueShareIn,
    user: AuthenticatedUser = Depends(require_admin_or_root),
):
    from app.services.content_ad_controls import set_creator_revenue_share_bps
    # Allow admin to set share for any creator; body must include target creator_sub
    return set_creator_revenue_share_bps(body.creator_sub, body.revenue_share_bps)
```

Remove the `ctx=Depends(require_ui_session)` variant. Add `creator_sub` field to `RevenueShareIn` model.

### 4.5 Extend Content Owner Check to Non-Video Types

For `content_type` values other than `video`, verify ownership against posts, broadcasts, etc. by querying the relevant table. If the resource lookup is not feasible synchronously, require an explicit `owner_sub` claim in the request body and compare it against `ctx["user_sub"]`.

### 4.6 Dev/Prod Parity (SECOPS-007)

`content_ad_controls.py` is pure DDB — no mock needed. `record_transparency()` uses atomic DDB `UpdateItem` with `if_not_exists` counters, which works identically on DDB Local and AWS. The `apply_content_override_to_config()` function needs no special dev handling — it reads DDB and merges fields.
