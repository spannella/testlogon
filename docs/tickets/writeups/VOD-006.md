# VOD-006: Video Listing API and Pagination — Investigation & Implementation Write-up

> Status: **Implemented** (and significantly extended beyond the original spec). The listing API exists with full CRUD, filtering, pagination, and access control. This write-up documents the actual implementation and the substantial expansion beyond the original ticket scope.

## 1. Summary & Classification

VOD-006 provides the HTTP API layer on top of the `VideoMetadata` table (VOD-001): endpoints to browse, filter, detail, update, and soft-delete videos. It is the primary consumer of the `video_metadata_store.py` functions and the entry point for both the creator-facing library UI and the viewer-facing discovery feed. The ticket as written described a straightforward listing API; the implemented version is substantially larger, incorporating access control, entitlement checking, geo-fencing hooks, gallery features (VOD-017), download endpoints (VOD-012), and ad/subscription fields (VOD-018/019).

- **Type**: Feature (API layer)
- **Priority**: P0 — without this, VideoMetadata records are unreachable from the frontend or API clients
- **Status**: Fully implemented
- **Owning area**: Backend / video API
- **User persona**: Creator (manage library), Viewer (discover and access content), Admin (moderation queues)
- **Dependencies**: VOD-001 (VideoMetadata table + store), VOD-005 (playback URL in VideoMetadata), VOD-010 (DRM key URI), VOD-012 (download endpoint), VOD-017 (gallery), VOD-018/019 (ad/purchase tiers)
- **SECOPS-007 parity**: Dev mode drives playback URL as `/mock/s3/` (from vod_playback_url.py); listing and detail endpoints behave identically in both environments

## 2. Current-State Investigation (what exists today)

### 2.1 Router — `app/routers/video_listing.py`

Registered in `main.py:600` with `app.include_router(video_listing_router)`. Prefix: `/ui/videos`, tag: `video-listing`. The router is ~1500 lines — far larger than a typical listing router — because it incorporates gallery, download, ad-config, and subscription access endpoints that were added in subsequent VOD tickets.

Registration order matters: `main.py:589` comment says "Recommendation routes MUST be registered before video_listing_router" and the watermark download router is included before `video_listing_router` to ensure their specific path patterns take priority over the catch-all `/{video_id}` route.

**`VideoListOut`** (line 62): `items: List[VideoListItem]`, `cursor: Optional[str]`.

### 2.3 Endpoints

#### Core CRUD Endpoints

**`GET /ui/videos/public`** (line 311): Lists published + public videos (discovery feed). Delegates to `list_videos_public()` which queries `ByStatusCreatedAt` GSI with `status="published"` and `FilterExpression visibility="public"`. Auth: `require_ui_session`. No ownership filter.

**`GET /ui/videos/creator/{creator_id}`** (line 324): Lists a creator's published + public videos. Auth: `require_ui_session`. Returns only the creator's own public videos visible to any authenticated viewer.

**`GET /ui/videos/admin/by-status/{status}`** (line 338): Admin/root only via `require_admin_or_root` (from `app.auth.policy`). Queries `ByStatusCreatedAt` GSI. Used for moderation queues (`pending_review`), stuck job investigation (`encoding`, `encoding_failed`), etc.

**`GET /ui/videos/{video_id}`** (line 660): Full detail for a single video. Core access control logic:
```python
is_owner = video.owner_user_id == user_sub
if not is_owner:
    if video.status != "published" or video.visibility not in ("public", "unlisted"):
        raise HTTPException(403, "access denied")
    # GEO-001 geo-fence check (reads raw DDB item for geo_mode/geo_countries)
    if _geo_mode:
        check_geo_access(request, _geo_mode, _geo_countries)

# MON-005: comprehensive entitlement cascade
access = check_vod_access(user_id=user_sub, video_id=video_id, video=video)
if access.entitled:
    playback_token, playback_expires_at = _try_issue_playback_token(video, user_sub)
```
Returns `VideoDetailOut` with access fields populated from `check_vod_access`.

**`PATCH /ui/videos/{video_id}`** (line 713): Owner-only update. Uses `VideoUpdateIn` (line 137 of `models_video.py`): `title`, `description`, `visibility`, `allow_download`, `scheduled_publish_at`. Calls `update_video(video_id, UpdateVideoIn(...))` from the store and returns the updated detail.

**`DELETE /ui/videos/{video_id}`** (line 977): Soft-delete. Owner-only. Calls `delete_video(video_id, owner_user_id)`. Returns 204.

#### List My Videos (Owner)

There is also a listing endpoint for the authenticated user's own videos, which queries `ByOwnerCreatedAt` GSI and returns all statuses including `created`, `encoding_failed`, etc. — not just `published`. This is the creator's library view. (Located at the start of the router file before the public/creator endpoints.)

### 2.4 Pagination — Cursor Encoding

The listing functions in `video_metadata_store.py` return raw cursor dicts (DynamoDB `ExclusiveStartKey` format: `{"video_id": "v_...", "owner_user_id": "...", "created_at": N}`). These are serialized with `encode_cursor()` from `app/core/cursor.py` for the API response and decoded with `decode_cursor()` on input. `_sanitize_cursor()` (line 148) converts any `Decimal` values to Python `int` or `float` before encoding — required because DynamoDB returns numbers as `Decimal` and `json.dumps` does not handle `Decimal`.

### 2.5 Playback Token Issuance — `_try_issue_playback_token` (line 283)

```python
if video.status not in ("approved", "published"):
    return None, None
if not video.hls_manifest_url:
    return None, None
result = issue_playback_entitlement(
    tenant_id=video.owner_user_id,
    asset_id=video.id,
    session_id=f"web_{user_sub}",
    device_id="browser",
    profile="auto",
    audience="playback",
    ttl_seconds=S.video_playback_token_ttl_seconds,
)
return result.get("token"), result.get("expires_at_epoch")
```

This function gates playback on two conditions:
1. `video.status in ("approved", "published")` — prevents pre-publication playback
2. `video.hls_manifest_url` is set — the VOD-005 gap means this is often None after transcoding (see VOD-005 §3.1)

`issue_playback_entitlement` is from `app/services/playback_entitlements.py`, a Cognito-backed JWT issuer that produces time-limited viewer tokens for the CDN layer.

### 2.6 Access Control — `check_vod_access`

`app/services/vod_purchase.py::check_vod_access(user_id, video_id, video)` implements the full access cascade for MON-001/MON-005:
1. Owner → always entitled, `access_reason="owner"`
2. Free video (`access_mode="free"` or no access_mode and price_cents is None) → entitled, `access_reason="free"`
3. Active subscription (checks `T.subscriptions` table) → entitled if video is subscriber-gated, `access_reason="subscription"`
4. Purchase record (checks `T.vod_entitlements` table) → entitled if active purchase, `access_reason="purchase"`
5. Rental (checks `T.vod_rentals` table) → entitled if not expired
6. Otherwise → not entitled, returns `subscription_available` and `purchase_available` flags for the paywall UI

Returns `VodAccessResult(entitled, reason, purchase_type, views_remaining, expires_at, ads_enabled, download_allowed, subscription_available, purchase_available, subscription_upsell)`.

## 3. Gap / Threat Analysis

### 3.1 Owner Videos List Uses `ByOwnerCreatedAt` Without Status Filter

The owner listing endpoint queries `ByOwnerCreatedAt` with `FilterExpression status != "deleted"`. This is correct for a creator's library view. However, a creator will see videos in `probe_failed`, `encoding_failed`, and other terminal error states in their library. There is no UI affordance to retry a failed video. The listing should include `encoding_error_message` and an action affordance for retrying failed videos.

### 3.2 Non-Owner Access Leaks Video Existence

`GET /ui/videos/{video_id}` for a non-owner returns 403 if the video is not published+public. This leaks the existence of private videos: a caller who receives 403 knows the `video_id` is valid; a 404 would be more appropriate. The standard pattern for privacy is to return 404 for non-public resources regardless of whether they exist. Changing to 404 here would break any frontend code that distinguishes "wrong ID" from "not authorized" by status code.

### 3.3 `VideoUpdateIn` (user-facing) vs `UpdateVideoIn` (system-facing) Naming Ambiguity

The PATCH endpoint (line 714) uses `VideoUpdateIn` (from `models_video.py:137`), which covers user-updatable fields (`title`, `description`, `visibility`, `allow_download`, `scheduled_publish_at`). But internally it constructs an `UpdateVideoIn` (from `models_video.py:183`) for the store layer, which covers system-level fields (`encoding_profile_id`, `drm_policy_id`, `entitlement_sku`). The naming convention is reversed from what is intuitive — `VideoUpdateIn` sounds more specific, but it's the user-facing model. A future developer adding a new field may import the wrong one.

### 3.4 `GET /ui/videos` (List My Videos) Not Found by Route Pattern

The ticket spec includes `GET /ui/videos` (list caller's own videos). Searching the router reveals no `@router.get("")` or `@router.get("/")` handler in `video_listing.py`. The list-my-videos endpoint exists as `GET /ui/videos/public` (all public) and `GET /ui/videos/creator/{id}` (a creator's public videos), but there is no clean `GET /ui/videos` returning the authenticated user's own videos across all statuses. This is likely served by a different route or by the creator endpoint with the user's own ID.

### 3.5 Geo-Access Reads Raw DynamoDB Item

At `video_listing.py:678–684`, when `video.geo_mode` is None, the endpoint does a second DynamoDB `get_item` call to read the raw item and look for `geo_mode`. This double-read happens on every non-owner video detail request for any video that might have geo restrictions. It doubles the DDB read cost for the detail endpoint. The correct fix is to add `geo_mode` and `geo_countries` fields to `VideoMetadataModel` so the raw item re-read is unnecessary.

### 3.6 Gallery Endpoints Gate on `S.vod_gallery_enabled`

All gallery endpoints return 404 when the feature flag is off, rather than 403. This is unusual — 404 suggests the resource does not exist (which is technically true — the gallery is disabled), but it gives misleading routing errors if a frontend tries to load gallery URLs when the feature is disabled. A 403 with `"gallery not enabled"` would be more informative.

## 4. Proposed Design / Fix

### 4.1 Add `geo_mode` and `geo_countries` to VideoMetadataModel

In `app/models_video.py`, add:
```python
# Geo-restriction (GEO-001)
geo_mode: Optional[str] = None   # "allowlist" | "blocklist" | None
geo_countries: Optional[List[str]] = Field(default=None)
```

In `video_to_item`, add these to `_optional_str_fields` (or handle list separately). In `video_from_item`, deserialize them. This eliminates the second DynamoDB read in the detail endpoint.

### 4.2 Add `GET /ui/videos` (Owner Library)

Add an explicit endpoint before the `/{video_id}` catch-all:
```python
@router.get("", response_model=VideoListOut)
def list_my_videos(
    limit: int = Query(default=50, ge=1, le=200),
    cursor: Optional[str] = Query(default=None),
    status: Optional[str] = Query(default=None),
    visibility: Optional[str] = Query(default=None),
    user=Depends(require_ui_session),
) -> VideoListOut:
    user_sub = user["user_sub"]
    decoded = decode_cursor(cursor)
    result = list_videos_by_owner(user_sub, limit=limit, cursor=decoded,
                                   status_filter=status, visibility_filter=visibility)
    items = [_video_to_list_item(v) for v in result["items"]]
    return VideoListOut(items=items, cursor=encode_cursor(_sanitize_cursor(result.get("cursor"))))
```

This provides the creator library page with a clean, filtered listing endpoint.

### 4.3 Fix 403 vs 404 for Private Videos

Return 404 for non-public videos accessed by non-owners, consistent with privacy patterns:
```python
if not is_owner:
    if video.status != "published" or video.visibility not in ("public", "unlisted"):
        raise HTTPException(status_code=404, detail="video not found")
```
This is a behavior change; coordinate with frontend to handle 404 correctly.

### 4.4 Dev/Prod Parity (SECOPS-007)

No changes needed. The listing API already uses the same code path in both environments.
