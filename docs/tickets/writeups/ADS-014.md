# ADS-014: Ad Fraud Prevention — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

ADS-014 inserts a synchronous, rule-based fraud detection pipeline ahead of every ad billing operation. Events scoring at or above a threshold (70 / 100) are flagged as fraudulent, excluded from billing (no advertiser charge, no creator credit), and recorded for admin review. Six rules contribute to the score: click velocity, IP clustering, bot user-agent, invalid traffic (short view time), CTR anomaly, and geo mismatch. Accounts exceeding a 20% rolling fraud rate are auto-suspended. An admin dashboard exposes flagged events, per-account risk scores, and manual suspend/unsuspend actions.

- **Type**: Security / Financial integrity hardening
- **Priority**: High
- **Status**: Implemented (fraud detection service, admin router, models, admin frontend page, E2E spec)
- **Owning area**: Ads platform — billing integrity
- **Attacker class**: Creator running click-farm bots to inflate ad revenue; advertiser buying impressions to game analytics; external bot traffic
- **Cross-referenced tickets**: [[ADS-001]] advertiser accounts, [[ADS-004]] ad serving engine (integration point), [[ADS-007]] ad billing (charge suppression), [[SECOPS-007]] dev/prod parity, [[SECOPS-001]] security event logging, [[SECOPS-002]] GeoIP (geo mismatch rule)

## 2. Current-State Investigation (what exists today)

### 2.1 Legacy `record_ad_impression()` — `app/services/ad_placement.py:233`

The function at line 233 still exists and is called from `app/routers/video_listing.py:1482-1483`. It writes to `T.ad_impressions` unconditionally and calls `_credit_ad_revenue()` on "complete" events (line 284). **Critically: no fraud check is performed here.** The ticket spec (section 2.1) specifically identified this as the unguarded billing path. This is the main residual gap — see section 3.

### 2.2 New fraud service — `app/services/ad_fraud_prevention.py` (659 lines)

The full fraud detection pipeline is implemented. Key details:

**Rule engine** (`app/services/ad_fraud_prevention.py:115-179`): `check_fraud()` orchestrates all six rules. The `count_velocity` parameter (line 128) allows read-only re-evaluation without incrementing counters — useful for admin review endpoints.

**Click velocity** (`app/services/ad_fraud_prevention.py:185-230`): Uses DynamoDB atomic counter: `VEL#{user_id}` / `CR#{creative_id}#{minute_bucket}` with TTL of `ts + 120`. Threshold: >5 events / user / creative / 60s window. Score contribution: 25. Fails open on DDB error (returns 0, not the threshold).

**IP clustering** (`app/services/ad_fraud_prevention.py`): `IP#{ip_address}` / `BUCKET#{five_min_bucket}` pattern with TTL `ts + 600`. Threshold: >50 events / IP / 5 minutes. Score contribution: 25.

**Bot UA** (`app/services/ad_fraud_prevention.py:53-62`): 14 compiled regex patterns including `r"bot"`, `r"selenium"`, `r"puppeteer"`, `r"python-requests"`. The comment notes these are "extended from affiliate_links.py" — the affiliate links service already had basic bot detection that was reused here.

**IVT** (`app/services/ad_fraud_prevention.py`): Flags "complete" events with `view_time_ms < 1000`. Non-complete events (impression, skip) are exempt. Score: 15.

**CTR anomaly** (`app/services/ad_fraud_prevention.py`): Queries campaign metrics for CTR. Implementation exists but the CTR data requires aggregation from `T.ad_campaigns` — the function `_check_ctr_anomaly()` is present and returns 0 when no historical data is available (which is the dev case). Score contribution when triggered: 10.

**Geo mismatch** (`app/services/ad_fraud_prevention.py`): Compares `geo_country` against `targeting_countries` list. Returns 0 when either is empty (no targeting or geo-unresolvable). Score: 5. GeoIP resolution is not performed inside this service — the caller must supply `geo_country`.

**Fraud event recording** (`app/services/ad_fraud_prevention.py:308-405`): `record_fraud_event()` writes to `T.ad_fraud_events` with PK `FRAUD#{date}` / SK `EVENT#{ts}#{event_id}`, GSI1 on `account_id`, GSI2 on `campaign_id`. Also calls `record_account_activity()` to maintain rolling fraud-rate counters for the account.

**Auto-suspension** (`app/services/ad_fraud_prevention.py:484-555`): `suspend_account()` updates the account record (in `T.ad_accounts`) with `status="suspended"`. `maybe_auto_suspend()` is called after every flagged event — it reads the rolling fraud rate and calls `suspend_account()` if the rate exceeds `AUTO_SUSPEND_FRAUD_RATE_BPS = 2000` (20%).

**Account risk scores** (`app/services/ad_fraud_prevention.py:428-482`): `get_account_risk_scores()` scans `RISK#` prefixed records in `T.ad_fraud_events`. `get_account_risk(account_id)` returns the specific account's risk summary.

### 2.3 Integration point — `app/services/ad_serving.py:185-233`

The fraud check is wired into `app/services/ad_serving.py` in the `record_ad_event()` function. Lines 196-230 show:
1. Flag check: `getattr(S, "ad_fraud_detection_enabled", True)` (line 198) — the feature flag is consulted
2. `check_fraud()` called with all parameters including `ip_address`, `user_agent`, `view_time_ms`, `geo_country`
3. On `result.flagged`: `record_fraud_event()` called, `maybe_auto_suspend()` called, early return with `{"flagged": True}` — billing is suppressed

5. Broad `except Exception` at line 233 logs and continues — fraud detection fails open

**Suspended account check**: At `app/services/ad_serving.py:83-88`, `is_account_suspended(account_id)` is called per campaign before ad candidate selection. Suspended accounts serve no ads entirely.

## 3. Gap / Threat Analysis

### 3.1 Critical gap: `record_ad_impression()` in `ad_placement.py` is NOT guarded

`app/services/ad_placement.py:233` — the legacy `record_ad_impression()` function — writes impressions and credits creators with zero fraud validation. It is still called from `app/routers/video_listing.py:1482-1483` via the `POST /ui/videos/{video_id}/ad-impression` endpoint. This is the path for VOD (pre-roll/mid-roll) ad impression events from the video player.

The fraud check is only in `app/services/ad_serving.py:record_ad_event()`, which is the campaign-serving path. The VOD ad-placement path is completely bypassed.

**Impact**: Any user or bot can fire unlimited `POST /ui/videos/{video_id}/ad-impression` requests with `event_type="complete"` and generate unbounded ad revenue credits to any creator without any fraud detection.

### 3.2 `record_ad_impression()` missing new parameters

The function signature at line 233 only accepts `video_id`, `user_id`, `slot_type`, `slot_index`, `creative_id`, `event_type`. It has no `ip_address`, `user_agent`, `view_time_ms`, `campaign_id` parameters. The fraud check in `ad_serving.py` passes all six of these. If/when `record_ad_impression()` is updated, it will need these parameters added.

### 3.3 IP address collection for VPN/proxy abuse

The geo-mismatch rule (weight 5) is the weakest rule by design. A sophisticated click farm using residential proxies or VPNs to spoof geo-locations would evade this rule entirely. No ASN or proxy-detection is implemented (SECOPS-002 covers ASN — a future integration point).

### 3.4 CTR anomaly rule requires historical data

`_check_ctr_anomaly()` is a no-op when no historical campaign data exists (returns 0). For new campaigns in a new dev environment, this rule never contributes. This is acceptable dev behaviour (consistent with SECOPS-007 fail-open for missing data) but means a real-time CTR spike on a brand-new campaign would not trigger the anomaly rule.

### 3.5 Fraud score transparency

The ticket spec (section 5.1) requires that fraud scores are NOT returned to end users in production. In `ad_serving.py:record_ad_event()`, the response includes `"fraud_score": fraud_score` on both clean and flagged events (line 229 for flagged; the clean path at line 240+ should be checked to ensure it omits or gates the score by `S.dev_mode`).

### 3.6 Account suspension does not stop existing active deals

When an account is suspended, `is_account_suspended()` at `ad_serving.py:83` prevents future ad impressions. However, existing DM conversations and campaign records remain. There is no mechanism to pause in-flight campaigns or reverse recent unaudited billing entries.

### 3.7 SECOPS cross-reference: detection event logging

SECOPS-001 (security event logging) is a dependency. Fraud events should be shipped to the security event log for SIEM correlation. Currently they are only written to `T.ad_fraud_events`. A `logger.warning("ad_fraud_detected", ...)` call at line 214 of `ad_serving.py` provides minimal observability.

## 4. Proposed Design / Fix

### 4.1 Guard `record_ad_impression()` — the critical fix

Add fraud check to `app/services/ad_placement.py:record_ad_impression()`:

```python
# app/services/ad_placement.py — extend signature and add pre-billing check
def record_ad_impression(
    *,
    video_id: str,
    user_id: str,
    slot_type: str,
    slot_index: int,
    creative_id: str = "",
    event_type: str = "impression",
    ip_address: str = "",        # NEW
    user_agent: str = "",        # NEW
    view_time_ms: int = 0,       # NEW
    campaign_id: str = "",       # NEW
) -> Dict[str, Any]:
    if getattr(S, "ad_fraud_detection_enabled", True):
        from app.services.ad_fraud_prevention import check_fraud, record_fraud_event
        result = check_fraud(
            user_id=user_id, ip_address=ip_address, user_agent=user_agent,
            creative_id=creative_id, campaign_id=campaign_id,
            view_time_ms=view_time_ms, event_type=event_type,
        )
        if result.flagged:
            record_fraud_event(...)
            return {"ok": True, "event_id": event_id, "flagged": True}
    # existing logic...
```

Update `app/routers/video_listing.py:1482-1487` to extract `ip_address` from `request.client.host` and `user_agent` from `request.headers.get("user-agent", "")` and pass them to `record_ad_impression()`.

### 4.2 Gate fraud score in responses

In `ad_serving.py:record_ad_event()`, only include `fraud_score` in the response when `S.dev_mode` is True. In production the response should be `{"ok": True, "event_id": event_id}` for clean events and `{"ok": True, "event_id": event_id, "flagged": True}` for fraudulent ones (no score leak).

### 4.3 SECOPS-001 logging integration

After `record_fraud_event()` in `ad_serving.py:214`, add:
```python
logger.warning("ad_fraud_detected", extra={
    "event_id": event_id, "fraud_score": result.score,
    "user_id": user_id, "campaign_id": campaign_id, "ip_address": ip_address,
    "rule_scores": result.rule_scores,
})
```
This integrates with SECOPS-001's structured log shipping.

### 4.4 Dev/Prod parity (SECOPS-007)

The fraud service is fully offline-capable:
- All DDB counters use `T.ad_fraud_events` (DDB Local in dev)
- Bot UA checks are pure regex (no network)
- CTR anomaly falls back to 0 when data is absent (fail open)
- Geo mismatch: the caller passes `geo_country`; in dev use `app/services/geoip.py:get_country()` which returns the mock value when configured, or empty string to disable the rule

Feature flag `AD_FRAUD_DETECTION_ENABLED` in `.env.local` controls the pipeline. `AD_FRAUD_DETECTION_ENABLED=1` in `.env.local.example` enables it by default for dev.

### 5.5 Effort and risks

**Effort**: S (critical `record_ad_impression()` guard: 2 hours; score transparency fix: 1 hour; SECOPS-001 logging: 1 hour).

**Risks**:
- Velocity counter DDB failure silently allows the event (fail-open design is intentional per SECOPS-007 rule 3: graceful degradation)
- Bot patterns in `BOT_UA_PATTERNS` are based on well-known strings; sophisticated bots using custom UAs will evade the UA check — the velocity and IP clustering rules are the primary defences
- Auto-suspension is based on rolling 7-day fraud rate and could incorrectly suspend legitimate accounts with bursty traffic patterns — admin unsuspend path provides recovery
