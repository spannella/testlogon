# ADS-007: Ad Billing & Financial Engine — Investigation & Implementation Write-up

## 1. Summary & Classification

ADS-007 implements the complete financial engine for the advertising platform: per-event charging (CPM/CPC/CPA), advertiser wallet management, a 70/30 platform/creator revenue split, budget enforcement with auto-pause, spending alerts at 50/80/100%, invoice generation, and a billing dashboard. It bridges the ad-serving engine (ADS-004) to actual financial ledger entries, making ad inventory monetarily meaningful for both advertisers and content creators.

- **Type**: Feature
- **Priority**: High
- **Status**: Implemented — service and router are both present and functional
- **Owning area**: Advertising / Billing
- **Affected personas**: Advertisers (debit side), content creators (revenue credits), platform (revenue accounting)
- **Cross-references**: ADS-001 (accounts/campaigns), ADS-004 (impression events), ADS-008 (analytics consume spend data); billing infrastructure in `app/services/billing_shared.py`; alert system in `app/services/alerts.py`
- **Dev/Prod parity note (SECOPS-007)**: DynamoDB Local at `:8001` in dev, AWS DynamoDB in prod; same code path; no outbound payment calls on deposit (payment method ID is stored but not charged in dev mode — the `stripe-mock` at `:12111` handles that upstream).

## 3. Gap / Threat Analysis

### 3.1 Open Gaps

**Internal charge endpoints lack access control (security concern).** `POST /ui/ads/internal/charge-impression` (ads.py:447), `charge-click` (460), `charge-conversion` (473) are authenticated only by `require_ui_session` — any logged-in user can post arbitrary charges against any advertiser account by supplying an `account_id`. These are intended for internal service-to-service calls but are exposed on the public `/ui/ads/` prefix. A malicious user who discovers these routes could drain any advertiser's balance to zero.

**Revenue split stores no platform-side ledger entry.** `_split_revenue()` (line 150–169) writes the 70% creator credit to `T.billing` but the 30% platform share is computed and logged but not stored anywhere. There is no audit trail for platform revenue, making reconciliation difficult.

**`_check_budget_and_alert()` re-reads campaign after every charge.** This creates an unbounded DDB read on every impression for campaigns with active budget checks. High-volume campaigns (thousands of impressions/minute) will generate significant read costs. The campaign is freshly fetched from `get_campaign()` on every call.

**`generate_invoice()` uses `FilterExpression` on a GSI scan.** The `ByMonth` GSI (line 265–270) queries all entries for a month and post-filters by `account_id`. At scale, a single month with many advertisers will scan all entries before filtering — each page up to 1MB. The `generate_invoice()` function does not paginate via `LastEvaluatedKey`.

**Daily budget reset not implemented.** The ticket design (§10.4) specifies a background task resetting `spent_today_cents` to 0 at midnight UTC. No such task exists in the codebase — there is no cron, background thread, or FastAPI startup task for this. `spent_today_cents` will monotonically increase indefinitely.

**`AD_BILLING_ENABLED` feature flag not implemented.** The ticket rollout plan (§9.1) specifies an `AD_BILLING_ENABLED` env flag to allow deploying the billing code dormant. `app/core/settings.py` has no such setting; billing is always active once the table exists.

### 3.2 Abuse Potential

The `budget_deposit` endpoint validates minimum ($50) and maximum ($100k) amounts and verifies account ownership. The internal charge endpoints do not verify ownership. The conditional `put_item` guard for spending alerts (line 193–198) prevents duplicate alerts per threshold correctly.

## 4. Proposed Design / Fix

### 4.1 Fix Internal Charge Endpoint Authorization

Move the three `internal/charge-*` endpoints to an admin-only router or add explicit account-ownership verification before processing charges:

```python
# app/routers/ads.py — before each internal charge handler
acct = get_ad_account(body["account_id"])
if not acct or acct["owner_sub"] != ctx["user_sub"]:
    raise HTTPException(403, "You do not own this account")
```

Alternatively, prefix these at `/ui/admin/ads/internal/charge-*` and gate with `require_admin_or_root`.

### 4.2 Platform Revenue Ledger

Add a `platform_revenue` entry type. In `_split_revenue()` after writing the creator credit, write a second entry to a dedicated `AdPlatformRevenue` table (or use the same `ad_billing` table with `PK=PLATFORM#revenue`):

```python
# New entry after creator credit
T.ad_billing.put_item(Item={
    "pk": "PLATFORM#revenue",
    "sk": f"LEDGER#{ts}#{entry_id}",
    "entry_type": "platform_revenue",
    "amount_cents": platform_share,
    "month_key": month_key,
    "campaign_id": meta.get("campaign_id", ""),
    "created_at": ts,
})
```

Register in `app/main.py` `create_app()` via `@app.on_event("startup")`.

### 4.4 Invoice Pagination Fix

Add `LastEvaluatedKey` loop to `generate_invoice()`:

```python
while True:
    query_kwargs = { ... }
    if last_key:
        query_kwargs["ExclusiveStartKey"] = last_key
    resp = T.ad_billing.query(**query_kwargs)
    entries.extend(resp.get("Items", []))
    last_key = resp.get("LastEvaluatedKey")
    if not last_key:
        break
```

### 4.5 Feature Flag

Add to `app/core/settings.py`:

```python
ad_billing_enabled: bool = _to_bool(os.environ.get("AD_BILLING_ENABLED", "true"))
```

Gate `_process_charge()` with `if not S.ad_billing_enabled: return {"ok": True, "skipped": True}`.

### 4.6 Dev/Prod Parity (SECOPS-007)

No mock is needed for the billing engine itself — it writes to DynamoDB, which is already local (DDB Local) in dev and AWS in prod. The `write_alert()` call is similarly DDB-backed. The only prod-only behavior is Stripe charge on deposit — this already flows through the existing Stripe mock at `:12111`, which always returns `requires_payment_method` for off-session intents, so deposit tests must seed balance directly in DDB for E2E tests (consistent with the CLAUDE.md note about wallet deposits).
