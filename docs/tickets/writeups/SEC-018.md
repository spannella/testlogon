# SEC-018: Account-State Revocation Propagation (Ban/Role/Deletion TOCTOU) — Investigation & Implementation Write-up

> ~5 pages. Real code read, citations at `file:line`.

## 1. Summary & Classification

Several account-state transitions — banning a user, downgrading their role from admin to user, initiating account deletion, and cancelling a pending deletion — either take effect too slowly or not at all on active sessions and API keys. The result is a cluster of time-of-check/time-of-use (TOCTOU) windows ranging from seconds (role downgrade cached in a short-lived JWT) to indefinite (a banned user's API key continues to work until it expires). Together they mean that a security operator who bans an account or demotes an admin cannot guarantee the action is effective for up to 15 minutes on cookie-auth paths, and cannot guarantee it at all on the API-key path.

- **Type**: security-fix / hardening
- **Priority**: High
- **Status**: Open
- **Area**: `app/services/sessions.py`, `app/auth/deps.py`, `app/services/account_deletion.py`, `app/routers/privacy.py`
- **Affected users**: all users (ban enforcement); admin users (role downgrade); users who have submitted deletion requests
- **Attacker class**: 🛡️ admin-abuse (privilege escalation window); ⚙️ config (ban bypass via API key)
- **Cross-references**: SEC-009 (MFA/session management), ROOT-AUTH-001, SECOPS-007 (dev/prod parity)

## 2. Current-State Investigation (What Exists Today)

### 2.1 Ban check bypassed on the API-key path

`app/services/sessions.py:284–303` (`require_ui_session`):

```python
async def require_ui_session(request, auth_user, user_sub, ...) -> Dict[str, str]:
    principal = getattr(getattr(request, "state", None), "api_key_principal", None)
    if isinstance(principal, dict):
        principal_sub = str(principal.get("user_sub") or "").strip()
        if principal_sub:
            role = normalize_role(getattr(auth_user, "role", None))
            request.state.user_sub = principal_sub
            request.state.user_role = role.value
            return {
                "user_sub": principal_sub,
                "session_id": f"api_key:{...}",
                "role": role.value,
                "ip": "",
            }                                        # ← returns HERE, before ban check
    # ...
    if role not in {Role.ADMIN, Role.ROOT} and is_user_currently_banned(resolved_user_sub):
        raise HTTPException(403, "account is banned")  # ← only reached by non-API-key paths
```

The `api_key_principal` short-circuit at line 291–303 returns a session context _before_ the `is_user_currently_banned` check at line 309. A user banned via the admin panel can continue to call any API endpoint as long as their API key is valid. `is_user_currently_banned` reads `T.account_state` in `app/services/moderation_policy_engine.py:113`; the check is correct and cheap (single DDB get), but it is simply never reached on the API-key code path.

### 2.2 Role downgrade cached in short-lived JWT

`app/services/sessions.py:168–182` (`mint_access_token`):

```python
def mint_access_token(user_sub: str, session_id: str) -> str:
    role = "root" if _is_root_user(user_sub) else "user"
    auth_level = "high" if role == "root" else "standard"
    payload = {
        "sub": user_sub,
        "sid": session_id,
        "role": role,
        "auth_level": auth_level,
        "exp": now_ts() + access_ttl,
        ...
    }
    return jwt.encode(payload, S.ui_access_token_secret, algorithm="HS256")
```

The role is baked into the JWT. `app/auth/deps.py` reads the role out of the Cognito token or the HS256 cookie token. After an admin is demoted (role written to DDB), their existing `ui_access_token` cookie still carries `role=admin` until it expires — up to `S.ui_access_token_ttl_seconds` (default: 900 seconds / 15 minutes). During this window the demoted admin can call admin-only endpoints.

### 2.3 Deletion request does not revoke sessions

`app/services/account_deletion.py:175–203` (`create_deletion_request`):

```python
def create_deletion_request(user_sub: str, reason: Optional[str] = None) -> Dict[str, Any]:
    ts = now_ts()
    # ... builds item dict, writes to T.account_deletion_requests ...
    T.account_deletion_requests.put_item(Item=item)
    _write_audit(request_id, user_sub, "deletion_requested", {...})
    logger.info(...)
    return item
```

There is no call to `revoke_all_sessions(user_sub)` or revocation of API keys. `revoke_all_sessions` exists at `app/services/sessions.py:599` and is called by password recovery (`app/routers/password_recovery.py:151`) and rootctl (`app/cli/rootctl.py:990, 1076, 1232`) but is not called on deletion request. A hijacked session can therefore:
- Continue to act on the victim's behalf during the grace period.
- Cancel the deletion request via `POST /requests/{request_id}/cancel` at `app/routers/privacy.py:157–176` — which also has no step-up requirement.

### 2.4 Deletion cancel lacks step-up

`app/routers/privacy.py:157–176`:

```python
@router.post("/requests/{request_id}/cancel")
def cancel_deletion_request(
    request_id: str,
    ctx: Dict[str, Any] = Depends(require_ui_session),   # no step-up
) -> DataRequestOut:
    user_sub = ctx["user_sub"]
    item = cancel_deletion(user_sub, request_id)
    ...
```

Any session cookie (even a hijacked one) can cancel the victim's self-initiated deletion request. The deletion request itself requires password verification (`app/routers/privacy.py:144–153`) to create, but the cancel has no equivalent gate.

### 2.5 Soft-deleted email re-registration

After `finalize_deletion` runs (or the scheduled deletion task fires), the user record is marked deleted but the email address may be freed for re-registration. `app/services/account_deletion.py:397` calls the destructive cascade only in production (`S.account_deletion_destructive`). In dev/staging, the email is freed but residual Participant and Contact associations may linger, meaning a re-registering user could inadvertently inherit old data or appear in existing conversation participant lists.

## 3. Gap / Threat Analysis

### 3.1 Banned user retains API access

**Scenario**: Alice is banned by a moderator via the admin panel. The ban is written to `T.account_state`. Alice's webapp session correctly gets a 403 on next request. However, Alice has an API key (issued via `POST /ui/api-keys` before the ban). Every request she makes with `Authorization: Bearer <api_key>` passes through `require_ui_session`, hits the `api_key_principal` short-circuit at line 292, and returns a context dict — completely bypassing the ban check. Alice continues to post content, access files, and interact with other users indefinitely.

**Blast radius**: all API-key-authenticated endpoints — file manager, messaging, commerce catalog, subscriptions, newsfeed.

### 3.2 Demoted admin retains admin endpoints for up to 15 minutes

**Scenario**: Charlie has role ADMIN. A root operator demotes Charlie to USER. Charlie's `ui_access_token` cookie (TTL up to 15 min) still carries `role=admin`. Charlie can call `GET /ui/admin/...` endpoints, impersonate users, and read audit logs until the cookie expires.

**Blast radius**: all admin-gated endpoints — role management, user impersonation, moderation queue, billing overrides, KYC review.

### 3.3 Hijacked session survives deletion request

**Scenario**: Bob suspects his account is compromised and submits a deletion request via the UI. The attacker still holding Bob's session can: (a) cancel the deletion request, or (b) spend the 7-day grace period exporting Bob's data and messaging contacts.

### 3.4 Re-registration inherits stale associations

A deleted user whose email is re-used immediately by a new registration might appear in the "followers" list of users who followed the old account (the follow relationship was keyed by `user_sub` which may differ, but contact records keyed by email would collide).

### 3.5 Code sites that must change

| File | Line(s) | Change |
|------|---------|--------|
| `app/services/sessions.py` | 291–303 | Add `is_user_currently_banned` check on API-key path |
| `app/services/sessions.py` | 168 | Add `role_epoch` field to JWT or add DB role re-read |
| `app/services/account_deletion.py` | 175 (after `put_item`) | Call `revoke_all_sessions(user_sub)` and revoke API keys |
| `app/routers/privacy.py` | 157–176 | Add `require_fresh_mfa(ctx)` to `cancel_deletion_request` |
| `app/services/account_deletion.py` | finalize path | Quarantine/rotate freed email (prefix with `deleted_<ts>_`) |

## 4. Proposed Design / Fix

### 4.1 Fix ban check on API-key path

In `app/services/sessions.py:291–303`, add the ban check immediately before the early return:

```python
principal = getattr(getattr(request, "state", None), "api_key_principal", None)
if isinstance(principal, dict):
    principal_sub = str(principal.get("user_sub") or "").strip()
    if principal_sub:
        # Apply the same ban check as the session-cookie path
        if is_user_currently_banned(principal_sub):
            raise HTTPException(403, "account is banned")
        role = normalize_role(getattr(auth_user, "role", None))
        ...
        return {...}
```

This adds a single DDB `get_item` on every API-key request — the same cost incurred on every session-cookie request (the call at line 309). The `account_state` table is small and hot; this should not materially affect latency.

**Dev/Prod parity (SECOPS-007)**: `is_user_currently_banned` reads `T.account_state` which is DynamoDB Local in dev mode — no AWS dependency; behaviour is identical in both environments.

### 4.2 Immediate role downgrade via session epoch

The root cause of the role-caching problem is that `mint_access_token` hard-codes the role at issuance time. Two complementary fixes:

**Option A — shorten TTL on demotion**: When the admin role is revoked, call `revoke_all_sessions(user_sub)` in addition to updating the role record. The next request from the demoted admin's browser will fail 401 (session revoked), forcing a new login that mints a token with the updated role. This is the simplest and most complete fix, at the cost of forcing the demoted admin to re-authenticate.

**Option B — role epoch in JWT**: Add a `role_epoch` integer to the sessions DDB item, incremented on every role change. Include it in the JWT payload. On each request, after decoding the JWT, verify `jwt_role_epoch == session.role_epoch`; mismatch → 401. This avoids full logout but adds a DDB read on every cookie-auth request.

**Recommended**: Option A for the ban/deletion cases (session revocation is already a clean signal); Option B as an additional safety net for graceful role transitions (avoids jarring logout during meetings). Implement both.

### 4.3 Revoke sessions on deletion request

In `app/services/account_deletion.py:create_deletion_request`, after writing the DDB record:

```python
from app.services.sessions import revoke_all_sessions
from app.services.api_keys import revoke_all_api_keys_for_user

def create_deletion_request(user_sub: str, reason: Optional[str] = None) -> Dict[str, Any]:
    ...
    T.account_deletion_requests.put_item(Item=item)
    _write_audit(request_id, user_sub, "deletion_requested", {...})
    # Revoke all active sessions and API keys immediately
    revoke_all_sessions(user_sub)
    revoke_all_api_keys_for_user(user_sub)   # to be implemented in api_keys service
    logger.info(...)
    return item
```

Because the deletion can be cancelled within the grace period, the cancel flow must allow the user to re-authenticate. The cancel endpoint should check that the caller has a valid _newly-issued_ session (the old sessions were revoked). Since cancel requires the user to re-login, it inherently acts as re-authentication proof — but a `require_fresh_mfa` call adds an extra gate.

### 4.4 Step-up for deletion cancel

`app/routers/privacy.py:157–176` — add the import and call:

```python
from app.services.sessions import require_ui_session, require_fresh_mfa
...
@router.post("/requests/{request_id}/cancel")
def cancel_deletion_request(request_id: str, ctx=Depends(require_ui_session)):
    require_fresh_mfa(ctx)           # ← ADD
    user_sub = ctx["user_sub"]
    ...
```

Because sessions were revoked on deletion request, the user had to re-authenticate to get a session at all. `require_fresh_mfa` ensures the session includes a recent MFA verification, not just a re-login.

### 4.5 Email quarantine on deletion finalization

In `app/services/account_deletion.py` in the destructive cascade path (around line 397), before freeing the email:

```python
rotated_email = f"deleted_{ts}_{user_sub}@__deleted__.invalid"
# Update the user record's email to the rotated value before marking deleted
# This prevents the original email from being re-registered and inheriting associations
```

In dev mode (`not S.account_deletion_destructive`), log the rotation but do not write it, so E2E tests can re-seed the same email.

### 4.6 API key revocation helper

Add `revoke_all_api_keys_for_user(user_sub)` to `app/services/api_keys.py` using the existing `T.api_keys` table (scan by `user_sub` GSI, set `revoked=True` on each). This is already partially implemented for individual key revocation — the batch variant follows the same DDB update pattern as `revoke_all_sessions`.

## 5. Testing, Verification & Rollout

### pytest unit tests (`tests/test_account_state_revocation.py`)

- `test_banned_user_api_key_rejected`: create a user, issue an API key, ban the user via `ban_user()`, then make a request with the API key → expect `403 account is banned`.
- `test_banned_user_session_cookie_rejected`: same with session cookie → already tested; confirm still passes.
- `test_demoted_admin_jwt_invalidated`: create admin, issue JWT with `role=admin`, revoke sessions, attempt admin endpoint → `401 Session revoked` (Option A).
- `test_deletion_request_revokes_sessions`: call `create_deletion_request`; then call `require_ui_session` with the pre-deletion session → `401 Session revoked`.
- `test_deletion_request_revokes_api_keys`: same with API key.
- `test_deletion_cancel_requires_fresh_mfa`: create deletion request; issue new session (no MFA stamp); attempt `POST .../cancel` → `401 Fresh MFA required`.
- `test_deletion_cancel_with_fresh_mfa_succeeds`: fresh session with `mfa_verified_at = now_ts()` → `200`.
- `test_deleted_email_quarantined`: finalize deletion in destructive mode; attempt to find the original email in the users table → not found as original; rotated address stored.

### Playwright E2E (`frontend/e2e/account-state-revocation.spec.ts`)

1. Seed Alice with an API key; ban Alice via rootctl CLI; issue API request with Alice's key → expect 403.
2. Log in as Charlie (ADMIN); rootctl demote Charlie; within the TTL window try an admin endpoint → should 403 after session revocation (Option A) or after next token refresh (Option B).
3. Alice submits deletion request via UI; verify she is redirected to login (session revoked); attempt old session cookie → 401.
4. Alice re-authenticates, completes MFA, cancels deletion → 200.

### Manual QA

```bash

# Before fix: 200; After fix: 403 {"detail": "account is banned"}

# Step 2: deletion revokes session
# In browser: submit deletion request; on next page load verify redirect to /login
```

### Observability

- Add `audit_event("api_key_ban_enforced", user_sub, ...)` when ban fires on API-key path.
- Add `audit_event("deletion_sessions_revoked", user_sub, ...)` in `create_deletion_request`.
- Track `session_revoked` counter in Prometheus (already instrumented via `record_session_revoked` in `app/metrics.py`).

### Rollout plan

1. Fix API-key ban check (§4.1) first — lowest risk, highest impact, self-contained.
2. Ship session revocation on deletion request (§4.3) — watch for user complaints about being logged out on delete.
3. Add step-up to deletion cancel (§4.4).
4. Implement Option A role downgrade with session revocation (§4.2).
5. Email quarantine last (§4.5) — requires coordination with registration service.

### Risks & open questions

- Revoking all sessions on deletion request will log the user out of all devices immediately — UX impact must be communicated (toast: "Your sessions have been revoked. Please log in to cancel the deletion.").
- If the user has no MFA enrolled, `require_fresh_mfa` on cancel returns immediately — the cancel is then gated only on having a valid session (which requires re-auth after revocation).
- The role-epoch approach (Option B) adds a DDB read per request on the cookie path; profile before shipping to confirm latency is acceptable.

**Effort**: M (four independent sub-fixes across three files; API-key ban check is S; deletion revocation is S; role downgrade is M due to epoch logic; email quarantine is S).

## Second-pass verification (2026-06-05)

- [Corrected] §2.1 API-key ban bypass: The write-up's claim that the ban check is never reached for API-key requests is **partially incorrect**. `require_ui_session` in `app/services/sessions.py:291–303` does short-circuit before the sessions.py ban check at line 309, as described. However, `require_ui_session` takes `auth_user: Optional[AuthenticatedUser] = Depends(get_authenticated_user)` as a FastAPI dependency. FastAPI resolves this dependency first; `get_authenticated_user` at `app/auth/deps.py:194–209` also handles the API-key path and calls `_enforce_not_banned(user_sub=user_sub, role=role)` at `app/auth/deps.py:208` before returning. Therefore the ban IS enforced via the deps.py path for API-key users. The sessions.py ban check at line 309 is redundant for this path. Residual risk: if `get_authenticated_user` is called with `role=ADMIN` (from a stale DDB read or future bug), `_enforce_not_banned` skips the check per `app/auth/deps.py:133`.
- [Corrected] §2.2 admin role caching in JWT: The write-up states "their existing `ui_access_token` cookie still carries `role=admin`". However, `mint_access_token` at `app/services/sessions.py:172` only encodes `"root"` or `"user"` — never `"admin"`. An admin user authenticated via the normal cookie flow receives `role=user` in their access token JWT. The `role=admin` value can only appear in a JWT issued by `e2e_admin_session_setup.py` (direct DDB write) or a Cognito token with a `role` claim. The 15-minute window applies to roles carried in any externally-issued JWT. The fix logic remains valid; the specific production scenario should reference Cognito JWT claims as the caching source, not `mint_access_token`.
- [Confirmed] §2.3 deletion request no session revocation: `app/services/account_deletion.py:175–203` (`create_deletion_request`) confirmed — no call to `revoke_all_sessions` or any API key revocation after `put_item` at line 195. Vuln is present.
- [Confirmed] §2.4 deletion cancel lacks step-up: `app/routers/privacy.py:157–176` confirmed — `cancel_deletion_request` uses only `Depends(require_ui_session)` with no `require_fresh_mfa` call. Line numbers match exactly.
- [Confirmed] sessions.py line numbers 284–303 (api_key_principal block) and 309 (ban check) confirmed accurate.
