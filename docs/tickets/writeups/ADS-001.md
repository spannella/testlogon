# ADS-001: Advertiser Accounts & Campaign Manager — Investigation & Implementation Write-up

## 1. Summary & Classification

ADS-001 establishes the advertiser account and campaign-hierarchy foundation for the entire ad platform. Any authenticated user can create an advertiser account (modeled as account ownership, not a new auth role), which gates access to campaign management. The hierarchy is Account → Campaign → Ad Group → Creative (Ad Groups and Creatives land in ADS-003/ADS-002 respectively). Admin and root users review and approve accounts and campaigns before they can serve traffic.

- **Type**: feature (greenfield)
- **Priority**: High — every downstream ADS ticket (ADS-002 through ADS-020) depends on this data model
- **Status**: Implemented — all backend services, the router, DynamoDB tables, and frontend pages are present
- **Owning area**: Advertising platform; backend + frontend
- **Affected personas**: any authenticated user acting as an advertiser; admin/root reviewers
- **Cross-references**: ADS-002 (creatives), ADS-003 (targeting), ADS-004 (serving engine), ADS-007 (billing), ADS-008 (analytics), ADS-011 (advertiser API), ADS-016 (scheduling), ADS-018 (admin ad-platform dashboard)
- **Dev/prod parity**: [[SECOPS-007]] — DynamoDB Local in dev, real DynamoDB in prod; same code path via `app/core/tables.py`

## 3. Gap / Threat Analysis

### 3.1 Implementation completeness

The core ADS-001 scope is fully implemented. The following edge cases and completeness items require verification:

1. **Rate limiting on account creation** — the ticket spec mentions "max 5 accounts per user" but no check is present in `ad_accounts.py`. `list_accounts_by_owner` is not called before `create_ad_account`, so a user can create unlimited accounts. This needs a count check before `T.ad_accounts.put_item`.

2. **Rate limiting on campaign creation** — "max 50 campaigns per account" also not enforced. `list_campaigns(account_id)` is not consulted at campaign creation time.

3. **Budget exhaustion auto-pause** — ticket spec says "campaign auto-pauses when budget exhausted." No background task or pre-serve check implements this in ADS-001; it is deferred to ADS-004/ADS-007.

4. **`AdAccountOut` model** — the response from `create_ad_account` returns a raw `dict`, not a Pydantic model. FastAPI will serialize it but without field filtering; internal DDB fields like `pk`/`sk` will be included in the response unless a `response_model` is set on the endpoint.

5. **Account ownership check on campaign creation** — correctly enforced via `_require_account_owner` at `ads.py:131`.

6. **Non-owner 404 vs 403** — `get_account_endpoint` at line 119 returns 404 when the account belongs to someone else. This is correct (no information leakage) and matches the spec.

### 3.2 Security considerations

- Campaign operations require account ownership, verified server-side via `_require_campaign_owner` (line 67).
- Admin review endpoints require `require_admin_or_root` — a regular USER cannot review accounts.
- `account_balance_cents` is not settable via PATCH or account-create; it only changes via ADS-007 deposit endpoint.
- CSRF protection applies to all non-GET session-auth requests automatically via the existing `require_ui_session` middleware.

### 3.3 Potential abuse

- Without the "max 5 accounts per user" enforcement, a user can spam account creation to fill the admin review queue. A `len(list_accounts_by_owner(owner_sub)) >= 5` check before creation mitigates this.
- Campaign names have max-length (200 chars) validated by Pydantic, preventing XSS through large payloads in the admin review UI.

## 4. Proposed Design / Fix

### 4.1 Missing rate limits (not yet implemented)

Add to `app/services/ad_accounts.py::create_ad_account` before `T.ad_accounts.put_item`:

```python
existing = list_accounts_by_owner(owner_sub)
if len(existing) >= 5:
    raise ValueError("Maximum 5 advertiser accounts per user")
```

Add to `app/services/ad_campaigns.py::create_campaign` before `T.ad_campaigns.put_item`:

```python
existing = list_campaigns(account_id)
if len(existing) >= 50:
    raise ValueError("Maximum 50 campaigns per account")
```

Raise as `ValueError`; the router already converts `ValueError` to HTTP 400 for campaign updates. Add equivalent handling for `create_campaign_endpoint` at `ads.py:127`.

### 4.2 Response model — expose only safe fields

Add `response_model=AdAccountOut` to `POST /ui/ads/accounts` and `GET /ui/ads/accounts/{account_id}` endpoints to strip `pk`/`sk` from responses. Requires `AdAccountOut` in `app/models.py` to omit `pk`, `sk` fields.

### 4.3 Dev/prod parity (SECOPS-007)

The current implementation already satisfies SECOPS-007:
- All DynamoDB calls go through `T.*` handles from `app/core/tables.py`, which reads `DDB_ENDPOINT_URL` from settings.
- In dev: `DDB_ENDPOINT_URL=http://localhost:8001`, `AWS_ACCESS_KEY_ID=test`.
- In prod: standard environment variables, real DynamoDB.
- No `if S.dev_mode:` branches in `ad_accounts.py` or `ad_campaigns.py` — same code path.
- The `scripts/local-ddb-init.py` table definitions are the authoritative schema; prod DynamoDB tables must be created with identical GSI definitions before deployment.

### 4.4 Backward compatibility

No existing endpoints are modified. The new `/ui/ads/*` router prefix is additive. DynamoDB tables are new (no migration needed). The `frontend/src/api/endpoints/ads.ts` file (previously containing only consumer-facing display functions) now includes advertiser management functions — this is additive.

### 4.5 Campaign hierarchy completeness

The ADS-001 ticket explicitly defers ad groups (between campaigns and creatives) to ADS-003. The `ad_campaigns` table SK pattern `CAMPAIGN#{campaign_id}` has no sub-hierarchy items below it. ADS-002 creatives use their own table with PK `CAMP#{campaign_id}`. ADS-003 targeting sets also use PK `CAMP#{campaign_id}`. This co-location by campaign is intentional — it allows all assets for a campaign to be fetched with a table Query on the same PK prefix.

The absence of a `bid_cpm_cents` field on the current `CampaignCreateIn` model means all campaigns default to 500 CPM in the serving engine (`campaign.get("bid_cpm_cents", 500)` in `ad_serving.py`). Adding this field to ADS-001 before ADS-007 (billing) is implemented would make the model complete and allow accurate auction ranking between campaigns with different bid levels. Recommended addition to `CampaignCreateIn`:

```python
bid_cpm_cents: int = Field(default=500, ge=100, le=100_000,
                           description="CPM bid in cents for this campaign")
```

### 4.6 Audit log for admin review actions

The `review_ad_account` and `review_campaign` service functions update the DDB record but write no separate audit trail. Admin review decisions (approve/reject/suspend with reviewer identity and timestamp) should be appended to a separate audit table or to the platform's security events stream (tied to SECOPS-001). At minimum, the `reviewed_by`, `review_notes`, and `updated_at` fields on the account/campaign record serve as a lightweight audit log. For regulatory compliance (ad platform policies require audit trails of moderation decisions), consider writing a secondary `AUDIT#{ts}` SK item to the same DDB table for immutable history.
