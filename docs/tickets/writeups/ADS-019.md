# ADS-019: Creator Self-Placed Ads — Investigation & Implementation Write-up

## 1. Summary & Classification

ADS-019 enables content creators to insert their own promotional content — banners, cards, video segments, text announcements — into their own feed, video, profile, and broadcast surfaces at no cost. This is distinct from paid advertiser campaigns (ADS-001–009) and paid self-promotion boosting (ADS-012). Self-placed promos carry a "Promoted by @creator" label rather than "Sponsored", carry zero billing impact, and are tracked for analytics only.

- **Type**: Feature
- **Priority**: Medium (5–6 days estimate)
- **Status**: Not Implemented — no `app/services/self_promos.py`, no `app/routers/self_promos.py`, no `SelfPromos` DDB table, and no frontend components exist in the codebase. The ticket is classified as "Implemented" in the ticket header, but the code investigation finds zero implementation artifacts.
- **Owning area**: Creator Tools / Ad Platform
- **User persona**: Content creators who want to promote their own content, products, or partner creators within their own distribution channels for free
- **Dependencies**: All upstream infrastructure is already present — `app/services/ad_placement.py` (VOD slots), `app/services/newsfeed_feed_query.py` (feed), `app/services/broadcast_store.py` (broadcast), `app/services/profile.py` (profiles), `T.ad_impressions` (analytics tracking)
- **Cross-references**: [[ADS-010]] (creator ad controls), [[VOD-018]] (ad-supported video, provides `ad_placement.py`), [[SECOPS-007]] (dev/prod parity: DDB Local, no outbound calls)

## 3. Gap / Threat Analysis

### 3.1 Zero-Billing Invariant

The most critical correctness requirement: self-promo impressions and clicks must never create billing ledger entries. The risk arises if the promo impression path accidentally calls `_credit_ad_revenue` from `ad_placement.py` or `new_ledger_entry` from `billing_shared.py`. The implementation must explicitly document and test this invariant. A dedicated E2E test section (section 425 per the ticket spec) scans the billing table after impression/click events and asserts zero promo-related entries.

In dev, this is testable via direct DDB Local scan. In prod, a `self_promo_billing_blocked_total` counter (expected = 0) serves as the observability signal.

### 3.2 Feed Injection Position Logic

The ticket's `inject_feed_promos` pseudocode (`feed_position == i`) is off-by-one: it inserts when the organic post index equals `feed_position`. If a creator sets `feed_position=0`, the promo is prepended before any organic post. If `feed_position=3`, it inserts after the 3rd post. The implementation must handle the case where the feed has fewer than `feed_position` organic posts (insert at end). Also, when multiple promos have `feed_position=0`, only the first should be pinned at top — the secondary should be inserted at its own configured position.

### 3.3 Feed Injection as Mixed-Type Response

Injecting self-promo cards changes the feed response schema from a plain post array to a mixed `{type: "post"|"self_promo", ...}` array. This is a breaking change for any client that expects a homogeneous post array. The frontend feed page (`frontend/src/pages/feed/`) must be updated to handle both types. Any existing E2E tests that assert specific post counts or positions in the feed will break.

### 3.4 Video Slot Integration Complexity

The `calculate_ad_slots` function in `ad_placement.py` currently computes platform ad slots. Injecting self-promo creatives requires fetching `get_video_promos(creator_id, video_id)` and checking whether each slot has a matching self-promo type. The `billing_exempt: true` flag on self-promo slots prevents the billing path. This is a cross-cutting change to the VOD ad-config endpoint, which may have existing E2E tests in `frontend/e2e/vod-ads.spec.ts` that must remain passing.

### 3.5 Rate Limiting and Abuse Prevention

Without a max-active-promos limit, a creator could flood their feed with self-promo cards, degrading the viewer experience. The ticket specifies a maximum of 20 active promos per creator (enforced at activate time in `activate_self_promo`) and a feed injection cap of 1 promo per 5 organic posts. The feed cap is applied in `inject_feed_promos` before returning the mixed feed result.

### 3.6 Cross-Promotion Privacy

When Creator A creates a self-promo referencing Creator B's content (`cross_promo_creator_id`), Creator B is not notified. Viewers see content attributed to Creator B without their knowledge. The current design treats this as equivalent to resharing, which is consistent with the ticket spec's decision (section 10, question 1), but future policy enforcement may require an opt-out mechanism on creator profiles.

## 4. Proposed Design / Fix

### 4.1 DynamoDB Table

Add to `scripts/local-ddb-init.py`:
```python
TableDef(
    os.environ.get("DDB_SELF_PROMOS", "SelfPromos"),
    "pk", "sk",
    gsi=[
        {"index_name": "ByStatusCreatedAt", "partition_key": "status", "sort_key": "created_at"},
        {"index_name": "ByLinkedEvent", "partition_key": "linked_event_id", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
)
```

Add to `app/core/settings.py`: `self_promos_table_name: str = os.environ.get("DDB_SELF_PROMOS", "SelfPromos")`
Add to `app/core/tables.py`: `self_promos: Any` field + `_safe_table(S.self_promos_table_name)` in the `T` init.

### 4.2 Service Layer (`app/services/self_promos.py`)

Core functions needed:
```python
def create_self_promo(creator_id: str, data: dict) -> dict
def get_self_promo(creator_id: str, promo_id: str) -> Optional[dict]
def list_self_promos(creator_id: str, status: Optional[str] = None, cursor: Optional[str] = None, limit: int = 20) -> dict
def update_self_promo(creator_id: str, promo_id: str, updates: dict) -> dict
def delete_self_promo(creator_id: str, promo_id: str) -> None  # soft delete: status="deleted"
def activate_self_promo(creator_id: str, promo_id: str) -> dict  # enforces 20-promo limit
def pause_self_promo(creator_id: str, promo_id: str) -> dict
def record_self_promo_event(promo_id: str, creator_id: str, viewer_id: str, event_type: str) -> None
    # Writes to T.ad_impressions with promo_type="self_promo"
    # Increments impression_count or click_count on promo item via ADD
    # NEVER calls new_ledger_entry or _credit_ad_revenue
def get_feed_promos(creator_id: str) -> list  # active feed_inline promos, sorted by feed_position
def get_video_promos(creator_id: str, video_id: str) -> list  # active video promos
def get_profile_promo(creator_id: str) -> Optional[dict]  # active profile_banner promo
def get_broadcast_promo(creator_id: str, broadcast_id: str) -> Optional[dict]
def activate_event_promos(event_id: str) -> int  # via ByLinkedEvent GSI
def deactivate_event_promos(event_id: str) -> int
def get_promo_analytics(creator_id: str, promo_id: str) -> dict
```

### 4.3 Router (`app/routers/self_promos.py`)

All endpoints under `/ui/self-promos` with `require_ui_session`. Viewer-facing query endpoints (`/feed/{creator_id}`, `/video/{video_id}`, `/profile/{creator_id}`) also use `require_ui_session` but do not enforce creator ownership. Register in `app/main.py`.

### 4.4 Feed Injection

Modify `newsfeed_feed_query.py` feed list function to call `get_feed_promos(creator_id)` and invoke `inject_feed_promos(posts, promos)`. The injected items carry `{"type": "self_promo", "promo": {...}}` structure. Frontend must handle both item types in the feed list render.

### 4.5 Pydantic Models

Add to `app/models.py`:
- `SelfPromoCreateIn`: `title` (max 120), `description` (max 500), `creative_type` (enum), `placement_types` (list of enum), `feed_position` (ge=0), `click_action`, `schedule_start`, `schedule_end`, `linked_event_id`, optional creative/target fields
- `SelfPromoOut`: all fields + `impression_count`, `click_count`, `status`
- `SelfPromoEventIn`: `event_type` (enum: impression/click)
- `SelfPromoAnalyticsOut`: `promo_id`, `impression_count`, `click_count`, `ctr_pct`

Validators: `creative_type` must be in `{"image", "video", "text", "card"}`, `placement_types` elements in `{"feed_inline", "video_preroll", "video_midroll", "video_overlay", "profile_banner", "broadcast_overlay"}`, `click_action` in `{"navigate", "open_post", "open_video", "open_profile", "external_link"}`.

### 4.6 Dev/Prod Parity (SECOPS-007)

All DDB writes via `T.self_promos` handle backed by `DDB_ENDPOINT_URL`. Analytics writes via `T.ad_impressions` (same handle used by VOD ads). No external calls. `promo_type="self_promo"` attribute is a plain DDB string field. Feature enabled by default — no separate feature flag needed per the ticket spec; the endpoint is auth-gated.

### 5.2 Playwright E2E (`frontend/e2e/self-promo-ads.spec.ts`)

35 tests across sections 419–426 per the ticket spec. Key scenarios:
- Creator creates/activates/pauses/deletes promo (section 419)
- Active feed promo appears in `/ui/self-promos/feed/{creator_id}` (section 420)
- Impression recorded → GET analytics shows `impression_count ≥ 1`; billing scan = zero entries (section 421, 425)
- Video promo appears in `/ui/self-promos/video/{video_id}` after activation (section 422)
- Invalid `creative_type="audio"` → 422 (section 423)
- Bob cannot activate/delete/view analytics for Alice's promo (section 424)
- Event-linked activate/deactivate via event endpoint (section 426)

All tests run offline against DDB Local on port 8001. Zero AWS credentials required.

### 5.3 Manual QA Steps

2. Navigate to `/self-promos` as Alice → create a card promo with `placement_types=["feed_inline"]` at `feed_position=3`
3. Activate the promo
4. Navigate to Alice's feed → confirm promo card appears after the 3rd organic post with "Promoted by @alice" label and info icon
5. Click the promo → verify `click_count` increments in analytics
6. Verify billing ledger has no promo-related entries (GET `/ui/billing/history`)
7. Navigate to feed as Bob → verify Bob does not see Alice's self-promo on Bob's own feed (promos are per-creator, not cross-feed)

### 5.5 Rollout Plan

**Phase 1** (independent, ~3 days): `SelfPromos` table, service, router, frontend page, section 419–425 E2E tests. No integration with feed/video/broadcast yet.
**Phase 2** (~2 days): Feed injection in `newsfeed_feed_query.py`, frontend mixed-type rendering, section 420 tests.
**Phase 3** (~1 day): Video slot integration in `ad_placement.py`, broadcast overlay hook, event-linked promos, sections 422/426 tests.

- **Risk**: Feed injection changes the response schema — carefully coordinate with frontend consumers.
- **Rollback**: Table is additive. Disable feed injection by feature flag or simple revert of `newsfeed_feed_query.py` change.
- **Effort**: Full feature is M (5–6 days) per ticket estimate; Phase 1 is achievable in 2–3 days.
