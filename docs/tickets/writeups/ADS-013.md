# ADS-013: Sponsored Content & Creator Partnerships — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

ADS-013 implements a brand-sponsorship deal workflow: an advertiser proposes a paid-content deal to a creator, compensation is held in escrow from the advertiser's wallet, the creator accepts or rejects, content is submitted and linked to the deal, and the advertiser completes the deal triggering a 15% platform-commission split and 85% payout to the creator. A DM conversation is created on acceptance for deal discussion. Submitted content receives an automatic FTC disclosure label that the creator cannot remove.

- **Type**: Feature
- **Priority**: Medium
- **Status**: Implemented (backend service, router, models, frontend pages, E2E spec)
- **Owning area**: Ads / Monetization — brand deals layer
- **User persona**: Advertiser (brand paying for sponsored content); Content creator (earning brand deal revenue); Platform operator (collecting 15% commission)
- **Cross-referenced tickets**: [[ADS-001]] advertiser accounts, [[ADS-007]] billing (escrow/ledger patterns), [[ADS-008]] analytics, [[SECOPS-007]] dev/prod parity

## 2. Current-State Investigation (what exists today)

### 2.1 Service layer — `app/services/sponsorship_deals.py` (604 lines)

The service is fully implemented with a complete state machine.

**State machine** (`app/services/sponsorship_deals.py:28-36`): `DEAL_STATUSES` = `proposed → negotiating → accepted → content_submitted → completed`, plus `rejected` and `cancelled` as terminal states. This is a superset of the ticket spec (which omitted `negotiating` and `rejected` as distinct statuses). The extra `counter_deal()` function at line 484 moves a deal to `negotiating` — not mentioned in the ticket spec but fully implemented.

**DynamoDB schema** (`app/services/sponsorship_deals.py:52-113`): Uses the `T.sponsorship_deals` table handle (wired at `app/core/tables.py:535`). PK = `DEAL#{deal_id}`, SK = `META`. Three GSIs:
- `GSI1`: `ADV#{advertiser_account_id}` → `created_at` (list by advertiser account, line 71)
- `GSI2`: `CREATOR#{creator_sub}` → `created_at` (list by creator, line 100)
- `GSI3`: `DEAL#ALL` → `created_at` (scan all deals, line 83 — used in `list_deals_by_advertiser_sub()` with a client-side `advertiser_sub` filter)

Important: `GSI3` stores `"DEAL#ALL"` as the partition key for all deals. The `list_deals_by_advertiser_sub()` function queries `GSI3` and filters in Python (`out.extend(i for i in resp.get("Items", []) if i.get("advertiser_sub") == advertiser_sub)`) using paginated `LastEvaluatedKey` loop — the correct DDB pattern (respects FilterExpression caveat from CLAUDE.md).

**Escrow** (`app/services/sponsorship_deals.py:135-222`): Three escrow functions:
- `_create_escrow_hold()`: Calls `apply_wallet_delta(T.billing, pk, -amount_cents)`. On `ConditionalCheckFailedException` raises `SponsorshipError(402, ...)`. Writes a `held` state ledger entry with `entry_type="sponsorship_escrow_hold"`.
- `_refund_escrow()`: Credits advertiser wallet + settled ledger entry with `entry_type="sponsorship_escrow_refund"`.
- `_release_escrow()`: Credits creator (85%) and writes a platform commission entry to `user_pk("platform")` — a sentinel user sub used for platform revenue accounting (line 207).
- `_split_escrow_dispute()`: 50/50 split on cancellation after content submission (lines 226-260).

**FTC labeling** (`app/services/sponsorship_deals.py:265-292`): `_add_ftc_label()` only handles `content_type == "post"` (line 272). It imports `app/routers/newsfeed.py:tbl, pk_post, sk_post` (lines 274-276) — a cross-layer dependency (router imported from service). Updates the post item with `sponsored_by`, `deal_id`, `ftc_disclosure = f"Paid partnership with {brand_name}"`. For `video` and `broadcast` content types the function silently no-ops (line 272-273). This is the key gap for non-post content.

**Brand name resolution** (`app/services/sponsorship_deals.py:522-529`): `submit_content()` attempts to look up the company name from `ad_accounts.get_ad_account(deal["advertiser_account_id"])`. Falls back to `advertiser_sub` if the account lookup fails. This creates a dependency on ADS-001 (ad accounts) not yet guaranteed to exist.

**DM creation on acceptance** (`app/services/sponsorship_deals.py:314-330`): `_create_deal_dm()` imports `app/routers/messaging.get_or_create_dm` at runtime (line 322). On failure it returns a fallback ID `f"spdeal_{deal_id}"` (line 329) — a non-functional placeholder that looks like a conversation ID.

**Notifications** (`app/services/sponsorship_deals.py:334-347`): `_notify()` calls `app/services/alerts.write_alert()` wrapped in a broad `except Exception: pass`. All state transitions trigger notifications to the counterparty.

## 3. Gap / Threat Analysis

### 3.1 FTC labeling limited to posts

`_add_ftc_label()` only applies the disclosure to `content_type == "post"` items. For `video` or `broadcast` content, the function is a no-op. If a deal is completed for video content, the FTC disclosure is silently skipped. This is a regulatory risk: video content with paid sponsorship requires the same disclosure.

### 3.2 Cross-layer import (router imported from service)

`app/services/sponsorship_deals.py:274` imports `from app.routers.newsfeed import tbl, pk_post, sk_post`. Services should not import from routers. If the newsfeed router changes its internal variable names, the sponsorship service breaks. The correct fix: move `pk_post`/`sk_post`/`tbl` to a shared service or directly use `T.newsfeed` and construct keys inline.

### 3.3 DM fallback creates phantom conversation IDs

When `_create_deal_dm()` fails (e.g., messaging service unavailable, import error), the deal is accepted with `dm_conversation_id = "spdeal_{deal_id}"` — a string that looks like a real ID but does not correspond to any conversation in `T.conversations`. If the frontend navigates to this ID, it will get a 404. A safer fallback: store `None` for the DM ID and surface a "DM not yet created — retry" action.

### 3.4 Brand name fallback exposes user subs

When the ad account lookup fails, `brand_name = deal["advertiser_sub"]` is used in the FTC disclosure: `"Paid partnership with alice@company.com"`. This leaks PII (the email-formatted user sub) into the public post metadata. Should fall back to a generic label ("a verified brand partner") when the account name is not available.

### 3.5 Escrow hold uses unconditional `apply_wallet_delta`

`_create_escrow_hold()` calls `apply_wallet_delta` (a negative delta) which performs a conditional DDB update. The error handling at line 144-147 catches `ConditionalCheckFailed` by string-matching the exception type name — `"ConditionalCheckFailed" in type(exc).__name__ or "ConditionalCheckFailed" in str(exc)`. This is fragile; DynamoDB raises `client.exceptions.ConditionalCheckFailedException` directly and the type name approach may miss it on some boto3 versions. Should use `from botocore.exceptions import ClientError` and check `e.response["Error"]["Code"] == "ConditionalCheckFailedException"`.

### 3.6 GSI3 full-table scan pattern

`list_deals_by_advertiser_sub()` queries `GSI3PK = "DEAL#ALL"` and Python-filters by `advertiser_sub`. As the platform scales, this GSI partition will grow unboundedly. A better long-term design adds a `GSI4PK = ADV_SUB#{advertiser_sub}` keyed directly on the user sub. For current scale (development) this is acceptable.

## 4. Proposed Design / Fix

### 4.1 Fix FTC labeling for video/broadcast

Extend `_add_ftc_label()` to handle `video` and `broadcast` types:
- For `video`: update `T.video_metadata` item `VIDEO#{content_id}` with `ftc_disclosure`, `sponsored_by`, `deal_id` fields
- For `broadcast`: update `T.broadcasts` item similarly

### 4.2 Remove cross-layer import

Replace the import of `app/routers/newsfeed.pk_post, sk_post, tbl` in the sponsorship service with inline DDB key construction using `T.newsfeed` directly:
```python
# app/services/sponsorship_deals.py ~line 274
from app.core.tables import T
pk = f"POST#{content_id}"
sk = "META"
T.newsfeed.update_item(Key={"pk": pk, "sk": sk}, ...)
```
(The exact key format must be verified against `app/routers/newsfeed.py`.)

### 4.3 Fix DM fallback

Change `_create_deal_dm()` to return `None` on failure instead of a fake ID. Update the caller at `accept_deal()` (line 449) to store `None` without breaking the response.

### 4.4 Fix brand name PII leak

In `submit_content()` (line 521):
```python
brand_name = "a verified brand partner"  # safe default
try:
    acct = get_ad_account(deal["advertiser_account_id"])
    if acct and acct.get("company_name"):
        brand_name = acct["company_name"]
except Exception:
    pass
```

### 4.5 Fix escrow error handling

```python
# app/services/sponsorship_deals.py ~line 143
from botocore.exceptions import ClientError
except ClientError as exc:
    if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
        raise SponsorshipError(402, "Insufficient wallet balance") from exc
    raise
```

### 4.6 Dev/Prod parity (SECOPS-007)

All DDB operations use `T.*` handles from `app/core/tables.py` wired from settings. No external AWS dependencies. The `sponsorship_deals_enabled` flag in `app/core/settings.py:1590` gates the feature.

For prod: ensure `SPONSORSHIP_DEALS_ENABLED=true`, `DDB_SPONSORSHIP_DEALS` points to the production table. No additional AWS services needed beyond DynamoDB.

### 5.7 Effort and risks

**Effort**: XS (bug fixes for the identified gaps: 0.5 day). All major lifecycle functions, models, router, frontend pages, and E2E spec are implemented.

**Risks**:
- **FTC labeling for video/broadcast** — medium regulatory risk; if deals are created for video content before the fix, the FTC disclosure is silently skipped. Priority: fix before enabling for non-post content types.
- **Cross-layer import** (`app/services/sponsorship_deals.py:274` imports from `app/routers/newsfeed`) — structural technical debt; low immediate risk but will break on any refactor of the newsfeed router's internal variable names.
- **DM fallback phantom IDs** — low priority; only surfaces when the messaging service is unavailable (unlikely in normal operation). Impact: `SponsorshipDealDetail.tsx` navigation to the DM may 404.
- **Platform commission sentinel** — `user_pk("platform")` creates a billing ledger entry for a non-existent user. Acceptable as a revenue accounting record if the admin billing dashboard filters for this sentinel. Must document this sentinel in `docs/dynamodb.md`.
- **ConditionalCheckFailedException string matching** — fragile boto3 error detection; low risk on current SDK version but should be fixed to use `botocore.exceptions.ClientError` pattern for long-term robustness.
