# ADS-011: Advertiser API — Programmatic Campaign & Analytics Access — Investigation & Implementation Write-up

## 1. Summary & Classification

ADS-011 provides a programmatic, API-key-authenticated REST interface for advertisers at `/api/v1/ads/`. It enables automation of campaign lifecycle (CRUD, bulk pause/resume/archive, budget updates), creative management, analytics queries (summary, timeseries, breakdown), and — per the ticket design — webhook registration and a sandbox mode. The ticket adds three new API key scopes (`ads:manage`, `ads:read`, `ads:serve`) to the existing API key infrastructure and a dedicated `advertiser_api_router` registered in `app/main.py`.

- **Type**: Feature
- **Priority**: High
- **Status**: Core campaign/creative/analytics API is implemented. Webhooks, sandbox mode, bulk-budget endpoint, rate limiting, and the frontend API documentation page are not implemented.
- **Owning area**: Advertising / Platform API
- **Affected personas**: Technical advertisers, marketing automation teams, third-party integrations
- **Cross-references**: ADS-001 (campaigns/accounts), ADS-002 (creatives), ADS-008 (analytics); API key infrastructure: `app/services/api_keys.py`, `app/services/api_key_capabilities.py`
- **Dev/Prod parity (SECOPS-007)**: API key authentication is pure DDB; no AWS-specific services. Webhook delivery in prod makes HTTP calls to advertiser endpoints; in dev, delivery should be logged to DDB and not make outbound HTTP calls. The `deliver_webhook()` function must check `S.dev_mode` and skip HTTP delivery, writing to a DDB log instead.

### 2.2 API Key Auth Dependency (`app/services/api_key_auth_dependency.py`, 88 lines)

The `require_api_key_principal()` function (line 55) extracts the key from `Authorization: ApiKey <key>` or `X-API-Key` header (not `Bearer ak_...` as described in the ticket design — the ticket spec says `Authorization: Bearer ak_xxx` but the implementation uses `ApiKey` prefix). It:

1. Calls `api_keys.parse_api_key(raw_key)` and `api_keys.check_api_key_allowed()` (with IP allowlist check)
2. Calls `api_keys.effective_api_key_capabilities(item)` to expand capability implications
3. Returns `{"auth_type": "api_key", "user_sub": ..., "api_key_id": ..., "capabilities": [...]}`
4. Stores `request.state.api_key_principal = principal`

## 3. Gap / Threat Analysis

### 3.1 Webhook System Entirely Absent

The full webhook subsystem is missing: no `app/services/ad_webhooks.py`, no `ad_webhooks` DDB table, no webhook CRUD endpoints, no delivery mechanism. This is the largest single gap. Without webhooks, advertisers cannot receive real-time notifications for campaign exhaustion, budget alerts, or creative review completion — all key automation use cases.

### 3.2 No Per-API-Key Rate Limiting

Any API key can make unlimited requests. The ticket design specifies 1000 req/min per key. Without rate limiting, a misconfigured or malicious client could flood the backend with analytics queries or bulk operations, potentially causing DDB hot partitions or exceeding read capacity.

### 3.3 `POST /campaigns/bulk-budget` Missing

`bulk_action()` handles pause/resume/archive. Budget updates for multiple campaigns in a single request are not available. The `AdsApiBulkBudget` Pydantic model does not exist. Advertisers running large-scale campaigns cannot adjust budgets in bulk.

### 3.4 `GET /analytics/by-campaign` Missing

The ticket design lists a per-campaign metrics endpoint. The router only has `by-date` and `breakdown`. The `advertiser_api.py` service has `analytics_by_date()` but no per-campaign aggregation function.

### 3.5 Frontend: `ads:*` Scopes Not Surfaced in API Key UI

Advertisers creating API keys via the Settings → API Keys page cannot select `ads:manage`, `ads:read`, or `ads:serve` scopes because the frontend capability selector does not list them. The API technically works if a key is created with these scopes (e.g., via direct API call), but the UI path is broken.

### 3.6 `Authorization: ApiKey` vs. `Bearer ak_xxx` — Header Mismatch

The ticket design (§5.1) specifies `Authorization: Bearer ak_{key_id}.{secret}` but `api_key_auth_dependency.py:11–13` parses `Authorization: ApiKey <key>` and `X-API-Key`. This inconsistency will confuse API users following the spec. The OpenAPI docs generated from the router will not reflect the correct auth scheme.

### 3.7 `resolve_account()` Returns First Account Only

`advertiser_api.py:81` returns `accounts[0]` — the first account owned by the API key's user. Advertisers with multiple ad accounts have no way to target a specific account via the API. The correct design is to accept `account_id` as a query parameter or embed it in the API key record.

### 3.8 Sandbox Isolation Not Implemented

Sandbox endpoints are absent. Without a sandbox, API integration testing incurs real charges and modifies production campaign state. This blocks programmatic testing workflows.

## 4. Proposed Design / Fix

### 4.1 Implement Webhook Service (`app/services/ad_webhooks.py`)

```python
# app/services/ad_webhooks.py
import hashlib, hmac, json, secrets, uuid
from typing import Any, Dict, List
from app.core.tables import T
from app.core.time import now_ts

WEBHOOK_EVENTS = ["campaign_approved", "campaign_exhausted", "creative_reviewed", "budget_alert"]

def register_webhook(*, advertiser_id: str, url: str, events: List[str]) -> Dict[str, Any]:
    """Validate url (must start with https://), validate events, store in DDB."""
    webhook_id = f"wh_{uuid.uuid4().hex[:12]}"
    signing_secret = secrets.token_urlsafe(32)
    T.ad_webhooks.put_item(Item={
        "pk": f"ADV#{advertiser_id}",
        "sk": f"WEBHOOK#{webhook_id}",
        "webhook_id": webhook_id, "url": url,
        "events": events, "signing_secret": signing_secret,
        "active": True, "created_at": now_ts(), "failure_count": 0,
    })
    return {"webhook_id": webhook_id, "signing_secret": signing_secret, ...}

def deliver_webhook(*, advertiser_id: str, event_type: str, payload: Dict[str, Any]) -> None:
    """Deliver to all matching webhooks. Dev mode: log to DDB, skip HTTP."""
    from app.core.settings import S
    webhooks = _list_webhooks_for_event(advertiser_id, event_type)
    for wh in webhooks:
        if S.dev_mode:
            _log_delivery(wh["webhook_id"], event_type, payload, status_code=0, success=True)
        else:
            _http_deliver(wh, event_type, payload)
```

### 4.3 Add Webhook Endpoints to `app/routers/advertiser_api.py`

```python
@advertiser_api_router.post("/webhooks", status_code=201)
async def create_webhook(body: AdsApiWebhookCreate, principal=Depends(require_api_key_principal)):
    svc.require_scope(principal, "ads:manage")
    account = svc.resolve_account(principal)
    from app.services.ad_webhooks import register_webhook
    return register_webhook(advertiser_id=account["account_id"], url=body.url, events=body.events)
```

Add GET, DELETE, and test-deliver endpoints similarly.

### 4.4 Implement Per-API-Key Rate Limiting

New file `app/services/ads_api_rate_limit.py` using atomic DDB `UpdateItem` counters on the `api_keys` table (per ticket §3.3 design). Call `check_rate_limit(principal["api_key_id"])` at the top of each endpoint handler, or add it as middleware on the `advertiser_api_router`:

```python
@advertiser_api_router.middleware("http")
async def rate_limit_middleware(request: Request, call_next):
    principal = getattr(request.state, "api_key_principal", None)
    if principal:
        check_rate_limit(principal["api_key_id"])
    return await call_next(request)
```

### 4.5 Expose `ads:*` Scopes in Frontend API Key UI

In the API key creation dialog (`frontend/src/pages/security/`), add `ads:manage`, `ads:read`, `ads:serve` to the displayed capability list. Add to `frontend/src/api/types.ts`:

```typescript
export type AdsApiScope = "ads:manage" | "ads:read" | "ads:serve";
```

### 4.6 Fix Auth Header and Multi-Account Selection

1. Update `api_key_auth_dependency.py:_extract_api_key_raw()` to also parse `Authorization: Bearer ak_...` for compatibility with the documented spec:
   ```python
   if auth.lower().startswith("bearer "):
       token = auth.split(" ", 1)[1].strip()
       if token.startswith("ak_"):
           return token
   ```

2. Add optional `account_id` query parameter to campaign/creative/analytics endpoints. When supplied, verify `account["account_id"] == account_id_param`; otherwise fall back to `resolve_account()`.

### 4.7 Sandbox Mode

Add a `POST /sandbox/serve` endpoint that returns a deterministic placeholder ad (a specific dev creative from `ad_placement.py`'s `_DEV_CREATIVE`) without consulting the real campaign table. Sandbox flag: `X-Sandbox: true` header or an API key created with `sandbox=true` field.

### 4.8 Dev/Prod Parity (SECOPS-007)

- Webhook HTTP delivery: gated on `S.dev_mode`. In dev, write to `ad_webhooks` DDB log; no outbound HTTP. In prod, make real HTTP POST with HMAC-SHA256 signature.
- Rate limiting: DDB-backed in both environments (DDB Local / AWS). No mock needed.
- Sandbox: `SANDBOX_*` PK prefixes in DDB for complete isolation; both environments use same logic.
