# SEC-005: Broken Access Control / IDOR Cluster — Investigation & Implementation Write-up

> ~5 pages. Code citations verified against the live codebase.

## 1. Summary & Classification

Six distinct broken-access-control defects exist across the codebase, spanning user-level IDORs (activity feed injection, achievements read) and admin-level scope overreach (KYC masked PII, impersonation audit scan, compute quotas, job retry). One previously-noted defect (signature packet final PDF) has been **partially addressed**: the endpoint at `app/routers/signature_packets.py:861` does check `status == COMPLETED` and requires the caller to be either the packet owner or a registered signer — the ticket's claim that "a signer who hasn't signed can download the completed PDF" is correct in the sense that being a registered signer but having a `status != "completed"` signer record does not block the download (the signer status is not checked, only signer participation). All other defects are confirmed.

- **Type**: security-fix
- **Severity**: High (user IDORs); Medium (admin scope overreach, audit gaps)
- **Status**: Open
- **Area**: `app/routers/activity_feed.py`, `app/routers/achievements.py`, `app/routers/kyc_cases.py`, `app/routers/admin_impersonation.py`, `app/routers/admin_compute.py`, `app/routers/invoices.py`, `app/routers/admin_jobs.py`, `app/routers/signature_packets.py`
- **Attacker class**: 🌐 any-user (activity feed, achievements); 🛡️ admin-abuse (KYC PII, impersonation audit, quotas, jobs); ⚙️ unaudited admin actions
- **Cross-references**: [[SEC-004]] (same structural pattern — trusting caller-supplied user_sub); [[SEC-008]] (trusted IP is a prerequisite for IP-based access restrictions on admin endpoints); [[SECOPS-007]] (dev/prod parity — all these endpoints use DDB which works identically in both environments)


## 2. Current-State Investigation

### 2a. Activity feed injection (`app/routers/activity_feed.py:148–168`)

```python
@router.post("/feed/record")
def record_activity(
    body: RecordActivityIn,
    session=Depends(require_ui_session),
):
    item = activity_feed_service.record_activity(
        user_id=body.user_id,          # ← from request body, not session
        actor_id=body.actor_id,        # ← from request body
        ...
    )
```

The model `RecordActivityIn` (line 50–57) accepts `user_id` and `actor_id` as arbitrary strings from the request body with `min_length=1, max_length=256`. The endpoint requires only a valid UI session (`require_ui_session`). There is no check that `body.user_id == session["user_sub"]` or that `body.actor_id == session["user_sub"]`.

The endpoint's docstring says "for testing/internal use" and "In production, activities are created by service-layer hooks" — but there is **no `S.dev_mode` gate**. The endpoint is registered in `app/main.py` and reachable in production with any authenticated session.

Any authenticated user can inject activity items (follows, likes, comments, etc.) into any other user's activity feed, attributed to any actor. This can be used to: (a) spam another user's feed with fake notifications; (b) fake social proof (e.g., inject fake "1000 people followed you"); (c) poison activity-based recommendation systems.

### 2b. Achievements read — arbitrary `user_sub` in path (`app/routers/achievements.py:228–239`)

```python
@router.get("/ui/achievements/display-badges/{user_sub}")
async def get_display_badges_endpoint(
    user_sub: str,
    ctx: dict = Depends(require_ui_session),
):
    from app.services.achievement_badges import get_display_badges
    from app.services.achievement_progress import get_user_achievements
    badges = get_display_badges(user_sub)
    achievements = get_user_achievements(user_sub)
    total_points = sum(a["points"] for a in achievements)
    return {
        "user_sub": user_sub,
        "display_badges": badges,
        "total_points": total_points,
        "achievement_count": len(achievements),
    }
```

The `user_sub` path parameter is not validated against `ctx["user_sub"]` — any authenticated user can retrieve any other user's achievement badges, points, and achievement history. Depending on the data stored (achievement names can reveal behavioral patterns, like "sent 1000 messages"), this leaks PII-adjacent behavioral data.

**Note on severity**: achievements are social/public data in many platforms. However, the existence of a public-read endpoint should be a deliberate product decision with explicit access control rather than a side effect of not checking ownership. If `display_badges` are intended to be public, the endpoint should be documented as public and moved to a public-read route; if private, it must check ownership.

### 2c. KYC masked PII — unscoped admin read (`app/routers/kyc_cases.py:1557–1588`)

```python
@router.get("/{case_id}/pii/masked")
def get_kyc_pii_masked(
    case_id: str,
    ...
    user: AuthenticatedUser = Depends(get_authenticated_user),
):
    case = STORE.get_case(case_id)
    role = normalize_role(user.role)
    is_owner = case.get("user_sub") == user.sub
    if not is_owner and role not in {Role.ADMIN, Role.ROOT}:
        _raise_kyc_error("kyc_access_forbidden", ...)
```

Lines 1568–1572. The check is: "allow if owner OR any ADMIN or ROOT." There is no `_is_scoped_admin_for_case(user, case)` call — any admin can read masked PII for any case, regardless of case assignment. Compare with the decrypt path at line 1077:

```python
if not _is_scoped_admin_for_case(user, case):
    raise HTTPException(403, ...)
```

The scoped-admin check enforces that the admin's `sub` matches `case["review"]["assigned_admin_sub"]` (unless the admin is ROOT). The masked-PII endpoint bypasses this restriction. While masked PII contains obfuscated values (e.g., `"Joh*** D**"`, last 4 of SSN), it still reveals that a case exists, the number of PII fields collected, the field names, the encryption timestamps, and the KMS key IDs — all sensitive metadata.

### 2d. Impersonation audit — any admin can scan all impersonations (`app/routers/admin_impersonation.py:192–238`)

```python
@router.get("/audit")
def impersonation_audit(
    actor_sub: str | None = Query(default=None),
    ...
    _actor: AuthenticatedUser = Depends(require_impersonation_operator),
):
    if actor_sub:
        r = T.sessions.query(KeyConditionExpression=Key("user_sub").eq(actor_sub), Limit=500)
    else:
        r = T.sessions.scan(Limit=500)   # ← full table scan
```

`require_impersonation_operator` requires the `auth_support` admin scope (line 29–30). Any `auth_support` admin can:
1. Call the audit endpoint with no `actor_sub` to get a `T.sessions.scan` of 500 items, filtered by `purpose == "impersonation"` — revealing who impersonated whom, when, and with what reason/ticket_id, platform-wide.
2. Specify any `actor_sub` to query another admin's impersonation history specifically.

This is a privacy violation: impersonation audit logs are sensitive security records that should be accessible only to ROOT, or to an admin reviewing their own history. An `auth_support` admin should not be able to audit their supervisor's impersonations.

Additionally, the `T.sessions.scan(Limit=500)` only fetches the first 500 session items and then filters in-memory — on a busy platform this will miss older impersonation records and is not paginated correctly.

### 2e. Admin compute quotas — any admin reads any user's quotas (`app/routers/admin_compute.py:158–164`)

```python

async def get_quota(

    user: AuthenticatedUser = Depends(require_admin_or_root),
```

`require_admin_or_root` (from `app/auth/policy.py:67`) requires any ADMIN or ROOT — no specific scope (`billing_support`, `kyc_support`, `auth_support`, etc.) is required. Any admin, regardless of their assigned role scope, can retrieve compute quota information for any user. No audit event is emitted.

### 2g. Job retry — unscoped admin action, missing audit (`app/routers/admin_jobs.py:90–107`)

```python
@router.post("/ui/admin/jobs/retry/{action_id}")
async def retry_failed_job(
    action_id: str,
    user_sub: str = Query(...),   # ← caller-supplied user for action lookup
    ctx: Dict[str, Any] = Depends(require_ui_session),
):
    _require_admin(ctx)   # any ADMIN role check
    result = reschedule_failed_action(user_sub, action_id)
```

`_require_admin` at line 15 checks only that `ctx["role"]` is at least ADMIN — no specific scope. Any admin can retry any user's failed job by supplying that user's `user_sub`. No `audit_event` call is present in this function (confirmed by grep: no `audit_event` in `admin_jobs.py`).

### 2h. Signature packet final PDF — signer status not checked (`app/routers/signature_packets.py:850–883`)

```python
signer_record = get_packet_signer(packet_id, user_sub)
is_owner = packet.get("owner_user_id") == user_sub
if not is_owner and not signer_record:
    _raise_packet_error(403, "signature_packet_not_participant", ...)

if str(packet.get("status") or "") != SignaturePacketStatus.COMPLETED.value:
    raise HTTPException(409, "signature_packet_not_completed")
```

Lines 856–862. The endpoint correctly blocks non-participants and non-completed packets. However, `signer_record` is checked only for existence (`not signer_record`), not for `signer_record["status"] == "completed"`. A signer who has been invited but has not yet signed can download the final PDF once the packet reaches COMPLETED status (which occurs when **all** signers complete). This means a signer who declined or was removed after being added can still access the fully-signed document.

There is also no rate limit on this endpoint — it serves PDF bytes on every request. No download rate limit or per-user download count cap exists.

### 2i. Dev vs prod behavior today

All of these endpoints use DDB (DDB Local in dev, AWS DDB in prod) — behavior is identical in both environments. The IDORs are fully exploitable in production.


## 3. Gap / Threat Analysis

### Attack A — Activity feed spam / fake social proof

Alice (any authenticated user) sends `POST /feed/record` with `body.user_id = "bob_sub"`, `body.actor_id = "alice_sub"`, `body.activity_type = "follow"`. Bob's activity feed shows "alice is now following you" — regardless of whether Alice actually followed Bob. Repeated at scale: inject thousands of fake social events, poisoning any ML recommendation model trained on activity data.

### Attack B — KYC case enumeration via masked PII endpoint

Admin with `kyc_support` scope (but not assigned to a specific case) calls `GET /kyc-cases/{case_id}/pii/masked` for sequential or guessed case IDs. Response reveals case existence, field names (`ssn`, `dob`, `address`), encryption timestamps, and KMS key IDs for every case on the platform — a complete case metadata inventory.

### Attack C — Impersonation audit as insider intelligence

A newly-provisioned `auth_support` admin calls `GET /audit` with no parameters. The `T.sessions.scan` returns up to 500 session items including all impersonation records. The admin discovers which ROOT operators impersonated which users, with what reason and ticket ID — sensitive security audit data that should be restricted to ROOT.

### Attack D — Job retry cross-user action

Admin calls `POST /ui/admin/jobs/retry/{action_id}?user_sub=alice` where `action_id` is a known failed scheduled action. The action is rescheduled under Alice's account with no audit trail. If the action involves billing, notifications, or data mutations, this is an unaudited admin-initiated state change.

## 4. Proposed Design / Fix

### 4a. Activity feed — enforce ownership, add dev gate

```python
@router.post("/feed/record")
def record_activity(
    body: RecordActivityIn,
    session=Depends(require_ui_session),
):
    if not S.dev_mode:
        raise HTTPException(404, "Not found")   # dev/test only
    # In dev mode, still enforce ownership for realistic testing:
    if body.user_id != session["user_sub"]:
        raise HTTPException(403, "Cannot record activity for another user")
    ...
```

In production this endpoint should not exist. The docstring confirms it; add the `S.dev_mode` gate. If internal services need to write activity items, they should call `activity_feed_service.record_activity` directly (service layer) from authenticated backend code, not via an HTTP endpoint.

### 4b. Achievements — explicit access control decision

Two options depending on product intent:
- **Public profile data**: move to `GET /profile/{user_sub}/achievements` with no auth required (or any-user auth); remove from the authenticated-user endpoint.
- **Private data**: add `if user_sub != ctx["user_sub"]: raise HTTPException(403, ...)` at line 231.

Recommendation: make `display_badges` public (social profile feature), make total_points and full achievement list private (own profile only).

### 4c. KYC masked PII — apply `_is_scoped_admin_for_case`

Replace the role check at line 1570:

```python
# Before:
if not is_owner and role not in {Role.ADMIN, Role.ROOT}:

# After:
if not is_owner and not _is_scoped_admin_for_case(user, case):
    audit_event("kyc_pii_masked_denied", user.sub, request, ...)
    _raise_kyc_error("kyc_access_forbidden", ...)
```

`_is_scoped_admin_for_case` returns True for ROOT unconditionally and True for ADMIN only if `user.sub == case["review"]["assigned_admin_sub"]`. This matches the decrypt-path behavior.

### 4d. Impersonation audit — restrict to ROOT for full scan, self-only for auth_support

```python
@router.get("/audit")
def impersonation_audit(
    actor_sub: str | None = Query(default=None),
    _ctx: Dict[str, str] = Depends(require_ui_session),
    _actor: AuthenticatedUser = Depends(require_impersonation_operator),
):
    role = normalize_role(_actor.role)
    # ROOT can query any actor; auth_support can only query themselves
    if role != Role.ROOT:
        if actor_sub and actor_sub != _actor.sub:
            raise HTTPException(403, "auth_support admins may only query their own audit log")
        actor_sub = _actor.sub   # force self-only for non-ROOT
    ...
```

Also fix the scan: replace `T.sessions.scan(Limit=500)` with a GSI query on an `impersonation_purpose` index, or add a separate `ImpersonationLog` table that is queryable by time range with proper pagination.

### 4e. Compute quotas, invoices, job retry — add scope restriction and audit

For **compute quotas** (`admin_compute.py:158`): change `Depends(require_admin_or_root)` to require a specific scope (e.g., `billing_support` for quota reads that are billing-adjacent). Add `audit_event("admin_quota_read", actor.sub, request, target_user_sub=user_sub)`.

For **invoices** (`invoices.py:99`): require `billing_support` scope. Add `audit_event("admin_invoice_list", actor.sub, request, target_user_sub=user_sub)`.

For **job retry** (`admin_jobs.py:90`): replace `_require_admin(ctx)` with `Depends(require_admin_or_root)` (proper FastAPI dependency) and add:

```python
audit_event("admin_job_retry", ctx["user_sub"], request, action_id=action_id, target_user_sub=user_sub)
```

### 4f. Signature packet — check signer completion status; add rate limit

```python
# After existing signer_record check (line 858):
if not is_owner and signer_record:
    signer_status = str(signer_record.get("status") or "")
    if signer_status not in {"completed"}:
        _raise_packet_error(403, "signature_packet_signer_not_completed", ...)
```

Add a SlowAPI (or custom) rate limit: max 10 downloads per `user_sub` per hour on the `final-pdf` endpoint. Alternatively, generate a signed S3 pre-signed URL (TTL 60 seconds) and redirect to it — offloads bandwidth and provides a natural rate limit via URL expiry.

### 4g. Dev/prod parity (SECOPS-007)

All changes are application-logic level, using DDB (DDB Local in dev = same as AWS DDB in prod). The `S.dev_mode` gate on activity feed is the only dev/prod divergence introduced — consistent with the pattern used for other test-only endpoints.

### 4h. Alternatives considered

- **Attribute-based access control (ABAC)**: full ABAC system for KYC/admin endpoints. Long-term goal; the scoped-admin checks already implement a lightweight ABAC for KYC. Extend this pattern rather than building a new framework.
- **GraphQL field-level auth**: not applicable to this FastAPI/REST codebase.
