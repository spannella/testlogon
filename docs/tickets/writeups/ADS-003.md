# ADS-003: Ad Targeting Engine — Investigation & Implementation Write-up

## 1. Summary & Classification

ADS-003 adds targeting definitions to ad campaigns and the creator-side ad preference controls. Advertisers specify who should see their ads (demographics, geography, behavior, content/creator context). The targeting engine evaluates each campaign's targeting sets against a viewer context dict at serve time in ADS-004. Creators separately control whether ads appear on their content at all, which ad categories they allow, and can block specific advertisers. This ticket also introduces the audience-estimation endpoint for advertiser planning.

- **Type**: feature
- **Priority**: High — ADS-004 (serving engine) calls `evaluate_targeting()` on every ad request
- **Status**: Implemented — `app/services/ad_targeting.py` and `app/services/creator_ad_prefs.py` are fully implemented; router, DDB table, and frontend component are present
- **Owning area**: Advertising platform — targeting and creator controls subsystem
- **Affected personas**: advertisers (define targeting), creators (set ad preferences), viewers (see only relevant ads)
- **Cross-references**: ADS-001 (targeting attached to campaigns), ADS-004 (evaluate_targeting called per serve request), ADS-005 (creator prefs checked for newsfeed ads), ADS-009 (viewer-side ad preferences complement creator controls), ADS-010 (extended creator controls)
- **Dev/prod parity**: [[SECOPS-007]] — GeoIP country resolution is mocked in dev (`geo_fail_open_dev`); `S.dev_mode` path returns `"US"` by default; same `evaluate_targeting()` logic runs in both environments

## 2. Current-State Investigation (what exists today)

### 2.1 Pre-targeting baseline

`app/services/ad_placement.py:178` — `get_ad_config()` function checks only two conditions: whether the video is `ad_supported` and whether the viewer is an active subscriber (ad-free). There is no viewer-context evaluation; every non-subscriber sees the same hardcoded creatives regardless of demographics, geography, or content context.

### 2.2 Targeting service — `app/services/ad_targeting.py`

Fully implemented. Key functions:

- **`create_targeting(campaign_id, account_id, data)`**: generates `tgt_{uuid[:12]}` ID, stores to `T.ad_targeting` with PK `CAMP#{campaign_id}`, SK `TARGETING#{target_set_id}`. Writes only non-None optional fields (lines 36–44), preventing null-valued DDB attributes on optional list fields.
- **`get_targeting(campaign_id, target_set_id)`**: `GetItem` by PK/SK.
- **`list_targeting_sets(campaign_id)`**: `Query` with `begins_with(sk, "TARGETING#")`.
- **`update_targeting(campaign_id, target_set_id, data)`**: full replace via `PutItem` after merging non-None fields with existing record.
- **`delete_targeting(campaign_id, target_set_id)`**: `DeleteItem`.
- **`estimate_audience(targeting)`**: deterministic mock implementation — calculates a multiplier by counting how many targeting dimensions are set, applies proportional reductions to a base of 100,000. Returns minimum 100 estimated viewers. Same function runs in dev and prod (no external audience API).
- **`evaluate_targeting(targeting, context)`**: pure Python function, no DDB reads. Checks each dimension sequentially; first non-match returns `False`; all dimensions pass → `True`. Handles age ranges, gender, country codes, device types, content types, creator IDs, exclusions, and `new_user_only` (30-day threshold). Zero external dependencies.

### 2.3 Creator ad preferences — `app/services/creator_ad_prefs.py`

Fully implemented using the existing `billing` table (single-table pattern):

- **`get_creator_ad_settings(creator_sub)`**: `GetItem` on `T.billing` with PK `USER#{creator_sub}`, SK `"AD_SETTINGS"`. Returns defaults `{allow_ads: True, allowed_ad_categories: [], min_cpm_cents: 0}` if record not found.
- **`update_creator_ad_settings(creator_sub, data)`**: `PutItem` with `SK="AD_SETTINGS"`. Full replacement — caller is responsible for merging with existing data if partial update is needed.
- **`block_advertiser(creator_sub, account_id, reason)`**: `PutItem` with SK `AD_BLOCK#{account_id}`.
- **`unblock_advertiser(creator_sub, account_id)`**: `DeleteItem` on block record.
- **`list_blocked_advertisers(creator_sub)`**: `Query` with `begins_with(sk, "AD_BLOCK#")`.
- **`is_advertiser_blocked(creator_sub, account_id)`**: `GetItem` on the block record — returns `True` if item exists.

No new DynamoDB table is required; all creator ad preferences reuse the `billing` table (`T.billing`).

### 2.8 Dev vs prod behavior (SECOPS-007)

`evaluate_targeting()` is pure Python with no external dependencies — identical in dev and prod. The `context` dict passed to `evaluate_targeting()` is assembled in `ad_serving.py` from available request-time data:
- `user_country`: In dev, the GeoIP mock (`app/services/geoip.py`) returns `"US"` or `None` depending on `geo_fail_open_dev`. In prod, MaxMind GeoLite2 DB resolves IP to country code. Same `evaluate_targeting()` call either way.
- `device_type`: Parsed from User-Agent header — same in dev and prod.
- `user_age`/`user_gender`: From user profile — same in dev and prod.

The audience estimation function is a deterministic formula (`estimate_audience`) — no external audience database is called. This satisfies SECOPS-007 for dev (no outbound network), and is also the prod implementation (no external API exists for this feature yet).

## 3. Gap / Threat Analysis

### 3.1 Implementation gaps

1. **`update_creator_ad_settings` is a full PutItem, not a partial update** — a PATCH to just `allow_ads=false` with no `allowed_ad_categories` will overwrite the stored `allowed_ad_categories` with `None`. The endpoint body `CreatorAdSettingsIn` has all fields optional; the service should merge with existing settings. Current behavior: PATCH with `{"allow_ads": false}` clears all other previously-set preferences.

2. **`is_advertiser_blocked` is called per campaign per serve request** — with many active campaigns, this is N `GetItem` calls. The batch pattern (`T.billing.batch_get_item`) or a per-request set (built once from `list_blocked_advertisers`) would reduce latency. For MVP with < 100 campaigns this is acceptable.

3. **`content_types` targeting dimension** — `evaluate_targeting` checks `context.get("content_type")` against `targeting.get("content_types")`. The `content_type` field in the serve-request context is set to the `surface` string (`"newsfeed"`, `"broadcast"`, `"vod"`) in `ad_serving.py:61–63`. The `TargetingCreateIn` validator expects `"newsfeed" | "broadcast" | "vod"`, so these are consistent. However, the field name collision between the `AdServeRequestIn.content_type` (which is a freeform content-category string) and the targeting `content_types` list (which is ad-surface types) could cause confusion in the API.

4. **Audience estimate is a mock formula, not real data** — `estimate_audience` returns a mathematically derived number with no relation to actual registered user counts. This is explicitly acknowledged in the ticket and is appropriate for MVP. A future iteration should query DynamoDB user-count aggregates.

5. **No creator preference check against `allowed_ad_categories`** — `get_creator_ad_settings` returns `allowed_ad_categories` but `ad_serving.py` only checks `allow_ads` (boolean) and `is_advertiser_blocked`. The `allowed_ad_categories` filtering is not implemented in the serving engine. If a creator sets `allowed_ad_categories: ["gaming"]`, ads from non-gaming campaigns still serve.

### 3.2 Security considerations

- Targeting data is stored per campaign; advertisers can only modify their own targeting sets (ownership check via `_require_campaign_owner`).
- `evaluate_targeting()` runs server-side — clients cannot inject false viewer context.
- The "Why this ad?" endpoint at `ads.py:394–400` deliberately returns only `"Based on your activity on the platform"` — never exposing specific targeting dimensions to viewers.
- Block list is private — `is_advertiser_blocked` is called server-side; advertisers never learn which creators blocked them (they simply get no impressions on that content).
- Audience estimates are approximate by design; no individual user data is exposed.

## 4. Proposed Design / Fix

### 4.1 Fix `update_creator_ad_settings` partial update

Replace `PutItem` with `UpdateItem` for partial update semantics:

```python
def update_creator_ad_settings(creator_sub: str, data: CreatorAdSettingsIn) -> dict:
    updates = {k: v for k, v in data.model_dump(exclude_none=True).items()}
    if not updates:
        return {"ok": True}
    updates["updated_at"] = now_ts()
    expr_parts, names, values = [], {}, {}
    for i, (k, v) in enumerate(updates.items()):
        a, va = f"#f{i}", f":v{i}"
        names[a] = k; values[va] = v
        expr_parts.append(f"{a} = {va}")
    T.billing.update_item(
        Key={"pk": f"USER#{creator_sub}", "sk": "AD_SETTINGS"},
        UpdateExpression="SET " + ", ".join(expr_parts),
        ExpressionAttributeNames=names,
        ExpressionAttributeValues=values,
    )
    return {"ok": True}
```

### 4.2 Wire `allowed_ad_categories` in serving engine

In `app/services/ad_serving.py`, after `get_creator_ad_settings`, add:

```python
allowed_cats = creator_settings.get("allowed_ad_categories", [])
# ... later in campaign loop, get campaign's ad_category field:
if allowed_cats:
    camp_cat = campaign.get("ad_category", "")
    if camp_cat and camp_cat not in allowed_cats:
        continue
```

This requires `ad_category` to be a field on campaigns (add to `CampaignCreateIn`/`CampaignOut`) matching the `allowed_ad_categories` enum. Coordinate with ADS-001 for the model addition.

### 4.3 Batch block-list check in serving

Replace per-campaign `is_advertiser_blocked()` with a single pre-fetch:

```python
blocked_accounts = {b["account_id"] for b in list_blocked_advertisers(creator_id)}
# Then in campaign loop:
if campaign["account_id"] in blocked_accounts:
    continue
```

One Query replacing N GetItem calls.

### 4.4 Dev/prod parity (SECOPS-007)

The current implementation is SECOPS-007 compliant:
- No external network calls in targeting evaluation or audience estimation
- GeoIP is abstracted through `app/services/geoip.py` which returns mock country in dev
- `T.ad_targeting` and `T.billing` go through `app/core/tables.py` → DDB Local in dev
- Feature flag `AD_TARGETING_ENABLED` at `app/core/settings.py:1575` gates targeting evaluation; set `false` → `evaluate_targeting` is skipped (all campaigns eligible), enabling gradual rollout

### 5.5 Rollout

- Feature flag `AD_TARGETING_ENABLED` (default `false`) controls whether `evaluate_targeting` is called in `ad_serving.py`. When false, all campaigns are eligible (untargeted serving).
- Phase 1: shadow mode — call `evaluate_targeting` but log result without filtering. Monitor miss rates.
- Phase 2: `AD_TARGETING_ENABLED=true` — targeting filters candidates. Monitor fill rate.
- Rollback: `AD_TARGETING_ENABLED=false` — immediate fallback to untargeted serving.

### 5.6 Observability additions

- **Counter `ad_targeting_created_total`** — in `create_targeting`; no label needed (rate indicates advertiser activity)
- **Counter `ad_targeting_evaluated_total{result}`** — in `evaluate_targeting`; result label is `match` or `miss`; computed from the bool return value in `ad_serving.py`
- **Counter `ad_targeting_dimension_miss_total{dimension}`** — log which dimension caused the miss (age_ranges, country_codes, device_types, etc.); helps advertisers diagnose over-narrow targeting
- **Counter `ad_audience_estimate_requests_total`** — in `estimate_audience`; tracks planning tool usage
- **Counter `ad_advertiser_blocked_total`** — in `block_advertiser`; indicates creator-side dissatisfaction with specific advertisers (P2 alert if a single account is blocked by >50 creators in 1 day)
- **Histogram `ad_targeting_evaluation_duration_ms`** — time spent per `evaluate_targeting()` call; should be sub-millisecond; alert if p99 > 5ms

Log: `targeting_evaluated` at DEBUG level (per-serve-request volume too high for INFO) with fields `campaign_id`, `context_hash`, `result`, `miss_dimension`.

### 5.7 Prod readiness checklist
