# BOT-002: Template & Scheduled Messages — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

BOT-002 adds a template engine and scheduled send system to the bot framework. Creators define reusable message templates with `{variable}` placeholders, quick-reply buttons, and optional A/B group assignments. A background scheduler loop picks up due sends from a DynamoDB GSI and dispatches them via `send_bot_message()`. The ticket depends on BOT-001 (bot CRUD + trigger evaluation) and is itself a prerequisite for BOT-003 (content promotion) and optionally for BOT-004 (AI fallback templates).

- **Type**: Feature
- **Priority**: High
- **Status**: Substantially implemented — backend service (`bot_template.py`), scheduler service (`bot_scheduler.py`), and router (`bot_template.py`) all exist. Key gaps: scheduler is registered but `start_bot_scheduler_task` has a startup-event ordering issue; wildcard target expansion in `dispatch_due_scheduled_sends()` is a stub; `quick_replies` field is declared on `MessageOut` but never populated in `_message_out_from_item()`; frontend template editor and E2E tests are absent.
- **Owning area**: `app/services/bot_template.py`, `app/services/bot_scheduler.py`, `app/routers/bot_template.py`, `app/routers/messaging.py`, `frontend/src/pages/bots/`
- **Cross-references**: [[BOT-001]] (dependency), [[BOT-003]] (downstream), [[BOT-004]] (downstream), [[SECOPS-007]] (no external deps in this ticket; dev/prod parity trivially maintained via DDB Local / DDB)

## 2. Current-State Investigation (what exists today)

### 2.1 `app/services/bot_template.py` (431 lines)

The full template service is implemented:

- **`create_template()`** (`bot_template.py:31`): Validates bot ownership via `get_bot_for_owner()`, enforces `MAX_TEMPLATES_PER_BOT = 50` (`bot_template.py:21`), validates quick replies via `_validate_quick_replies()` (`bot_template.py:383`), auto-detects variables with `_VAR_RE = re.compile(r"\{(\w+)\}")` (`bot_template.py:24`), writes to `T.bot_templates` under `PK=BOT#{bot_id}`, `SK=TEMPLATE#{template_id}` with `GSI1PK=BOT#{bot_id}#CAT#{category}`, `GSI1SK=ts`.
- **`list_templates()`** (`bot_template.py:108`): If `category` is given, queries GSI1 with `ScanIndexForward=False`; otherwise queries primary index.
- **`update_template()`** (`bot_template.py:125`): Conditional update; recomputes `variables_used` and `GSI1PK` if `text` or `category` changed.
- **`resolve_variables()`** (`bot_template.py:215`): `_VAR_RE.sub(_replace, template_text)` — unknown variables are preserved as `{var}` literals; returns `(resolved_text, list_of_unresolved)`.
- **`build_variable_context()`** (`bot_template.py:233`): Lazy — only fetches DDB data for variables present in the template. Resolves `{user_name}` from `T.profile` by `sender_id`, `{creator_name}` from `T.profile` by `creator_id`, `{bot_name}` from bot dict, `{current_time}` and `{current_date}` from `datetime.now(timezone.utc)`, `{subscriber_status}` as `"none"` (stub), `{conversation_name}` as `"Conversation"` (stub).
- **`render_template()`** (`bot_template.py:291`): Combines `build_variable_context()` + `resolve_variables()`, returns `{"rendered_text", "resolved_variables", "unresolved_variables", "quick_replies"}`.
- **`select_ab_template()`** (`bot_template.py:324`): Weighted random selection using `random.choices(templates, weights=[t.get("ab_weight",1)...])`.
- **`get_templates_for_trigger()`** (`bot_template.py:332`): Fetches the linked template, then if it has `ab_group`, fetches all templates for the bot and filters by group name. **Bug**: this scans all templates for the bot rather than querying by `ab_group` via a filter expression — acceptable for small template counts but worth a targeted fix.
- **`record_impression()` / `record_response()`** (`bot_template.py:355,367`): Atomic `ADD` via `update_item`; wrapped in `try/except ClientError` (non-critical).

Variable resolution stubs: `{subscriber_status}` always returns `"none"` (`bot_template.py:283`), `{conversation_name}` always returns `"Conversation"` (`bot_template.py:286`). These require DDB lookups that are not yet implemented.

### 2.2 `app/services/bot_scheduler.py` (380 lines)

- **`create_scheduled_send()`** (`bot_scheduler.py:61`): Verifies bot and template ownership, validates cron with `_parse_cron()` (`bot_scheduler.py:26`), validates timezone via `_validate_timezone()` (`bot_scheduler.py:336`), writes to `T.bot_scheduled_sends` under `PK=BOT#{bot_id}`, `SK=SCHED#{schedule_id}`, with `GSI1PK="BOTSCHED#PENDING"`, `GSI1SK=next_run_at`. Enforces `MAX_SCHEDULES_PER_BOT = 20` (`bot_scheduler.py:18`).
- **`_parse_cron()`** (`bot_scheduler.py:26`): 5-field parser; rejects `* *` (every minute = too frequent). **Gap**: `_next_run_from_cron()` (`bot_scheduler.py:40`) returns `now_ts() + 3600` as a simplification — it is not a real cron calculator. A comment notes "production would use croniter". This means all scheduled sends are dispatched approximately 1 hour after creation, not at the configured time.
- **`dispatch_due_scheduled_sends()`** (`bot_scheduler.py:236`): Queries `GSI1PK="BOTSCHED#PENDING"` with `GSI1SK <= now_ts`. For each due send: fetches bot and template, calls `render_template()`, and only sends if `target_type == "conversation"` with a specific `target_id`. **Wildcard targets (`all_dms`, `all_groups`, `all_broadcasts`) are silently skipped** — the block at lines 276-282 only handles `target_type == "conversation"`. After dispatch, recalculates `next_run_at` (+3600) and updates `GSI1SK`.
- **`run_bot_scheduler_loop()`** (`bot_scheduler.py:302`): Infinite async loop, 60-second sleep, calls `dispatch_due_scheduled_sends()`.
- **`start_bot_scheduler_task()`** (`bot_scheduler.py:312`): Calls `asyncio.create_task(run_bot_scheduler_loop())`. Gated on `S.bot_scheduled_messages_enabled`.

### 2.3 Router registration and startup

`app/main.py:686` registers `bot_template_router` under `/ui`. `app/main.py:687` adds `start_bot_scheduler_task` as a startup handler via `app.add_event_handler("startup", start_bot_scheduler_task)`.

**Bug**: `start_bot_scheduler_task()` calls `asyncio.create_task(...)`. `asyncio.create_task()` requires a running event loop and must be called from a coroutine or from within an async context. The FastAPI `startup` event handler is a synchronous callable registered via `add_event_handler`; `asyncio.create_task()` called from a non-async startup handler may raise `RuntimeError: no running event loop` in some uvicorn configurations. The safe fix is to make `start_bot_scheduler_task` an `async def` and register it with `@app.on_event("startup")` or use `asyncio.ensure_future()`.

### 2.4 `quick_replies` field declared but not populated in `_message_out_from_item`

`MessageOut.quick_replies` is declared at `messaging.py:2496` (`Optional[List[Dict[str, str]]] = None`). The `_message_out_from_item()` function at `messaging.py:4162` does not pass `quick_replies` to the `MessageOut(...)` constructor (lines 4162-4230). Consequently bot messages with quick-reply buttons will render without buttons when read back from the DB.

## 3. Gap / Threat Analysis

### 3.1 Functional gaps

1. **`_next_run_from_cron()` is a stub** (`bot_scheduler.py:40-53`). All schedules fire approximately 60 minutes after creation regardless of the configured cron expression. A real implementation requires `croniter` (pip package) or equivalent. Without it, `0 14 * * *` (daily at 2pm) fires at `now + 3600` instead.

2. **Wildcard target dispatch silently drops sends** (`bot_scheduler.py:276-282`). Sends with `target_type` of `all_dms`, `all_groups`, or `all_broadcasts` are fetched from GSI1 but then the `if sched["target_type"] == "conversation"` guard skips them entirely. The `dispatched` counter will not be incremented for wildcard sends. Fix: call `get_bots_for_conversation()` logic in reverse — resolve the list of conversation IDs for the wildcard scope and fan out.

3. **`quick_replies` not populated in `_message_out_from_item()`** (`messaging.py:4162`). See section 2.4.

4. **`{subscriber_status}` and `{conversation_name}` variables are stubs** (`bot_template.py:283,286`). They always return `"none"` and `"Conversation"` respectively. Fix: `{subscriber_status}` should query `T.subscriptions` for the sender; `{conversation_name}` should query the conversations table.

5. **A/B group lookup scans all templates** (`bot_template.py:347`): `list_templates(bot_id=bot_id)` fetches all templates then filters in Python. With 50 templates per bot this is bounded and acceptable, but a `FilterExpression` on `ab_group` in the DDB query would be cleaner.

6. **Missing `TemplateEditorPage`, `TemplateFormDialog`, `ScheduleManagerPanel`** — no frontend pages exist for BOT-002 beyond `BotManagerPage.tsx`.

7. **No E2E test file** (`frontend/e2e/bot-templates.spec.ts` does not exist).

### 3.2 Security

- **Template text injection**: `resolve_variables()` does `str(context[var_name])` (`bot_template.py:226`). If a profile `display_name` contains markdown or HTML, it will be inserted literally into the message text. The messaging pipeline treats text as plain/markdown already; no HTML injection risk for the SSE pipeline, but a XSS-conscious review of how the frontend renders `rendered_text` in a preview panel is needed.
- **Cron abuse**: `_parse_cron()` rejects `* * * * *` (every-minute). The 1-hour minimum is enforced at parse time (`bot_scheduler.py:35-36`). Max 20 schedules per bot is enforced by `MAX_SCHEDULES_PER_BOT`.
- **Wildcard fan-out cap**: The ticket design specifies 500 conversations max per wildcard send. This cap is not implemented in the current `dispatch_due_scheduled_sends()` — when wildcard expansion is implemented, a `Limit=500` guard must be added to prevent unbounded fan-out.

## 4. Proposed Design / Fix

### 4.1 Fix `_next_run_from_cron()` — add `croniter`

Add `croniter` to `requirements.txt`. Replace `_next_run_from_cron()` (`bot_scheduler.py:40-53`) with:

```python
def _next_run_from_cron(cron_expression: str, timezone: str = "UTC") -> int:
    from croniter import croniter
    from datetime import datetime
    import pytz
    tz = pytz.timezone(timezone)
    now_dt = datetime.now(tz)
    cron = croniter(cron_expression, now_dt)
    return int(cron.get_next(datetime).timestamp())
```

Update `_validate_timezone()` to use `pytz.timezone(tz)` for proper IANA validation.

### 4.2 Implement wildcard fan-out in `dispatch_due_scheduled_sends()`

At `bot_scheduler.py:276`, replace the single-conversation guard with:

```python
target_convs = _resolve_target_conversations(sched)  # returns list[str]
for conv_id in target_convs[:500]:
    rendered = render_template(template=template, creator_id=bot.get("creator_id"), bot=bot)
    send_bot_message(bot_id=sched["bot_id"], conversation_id=conv_id, text=rendered["rendered_text"])
    record_impression(bot_id=sched["bot_id"], template_id=sched["template_id"])
```

`_resolve_target_conversations()` queries the bot_assignments table for the bot's wildcard scope or returns the single `target_id`.

### 4.3 Fix `_message_out_from_item` (`messaging.py:4162`)

As described in BOT-001 fix 4.1 — add `quick_replies=merged_item.get("quick_replies") or None` to the `return MessageOut(...)` call.

### 4.4 Fix `start_bot_scheduler_task` startup registration (`main.py:687`)

Change to an async startup handler:

```python
@app.on_event("startup")
async def _startup_bot_scheduler():
    from app.services.bot_scheduler import start_bot_scheduler_task
    start_bot_scheduler_task()
```

Or make `start_bot_scheduler_task` itself `async def` and use `asyncio.get_event_loop().create_task()`.

### 4.5 Dev/Prod parity (SECOPS-007)

BOT-002 has no external dependencies beyond DDB, which is already abstracted. `croniter` and `pytz` are pure-Python packages with no AWS dependency. Scheduler loop runs in-process in both dev and prod (single-worker `uvicorn` in dev; same pattern in prod). `BOT_SCHEDULED_MESSAGES_ENABLED=false` disables the loop in both environments.

### 4.6 Backend router additions needed

`POST /ui/bots/{bot_id}/templates/{template_id}/preview` and `POST /ui/bots/{bot_id}/templates/{template_id}/send-test` endpoints are not yet implemented in `app/routers/bot_template.py` — only CRUD endpoints exist. These are needed for the template editor UI.

### 5.3 Manual QA

1. Create a bot, create a template `"Hello {user_name}! Welcome!"` with one quick reply `{label:"OK", value:"ok"}`.
2. Assign the template to a `first_message` trigger on the bot.
3. As Bob, open a DM with Alice (creator). Send a message.
4. Verify bot reply appears with `{user_name}` replaced by Bob's display name and a "OK" button.
5. Click "OK"; verify a user message `"ok"` is sent.
6. Create a scheduled send for `cron="* * * * *"` (should be rejected as too frequent — verify 422).

`BOT_TEMPLATES_ENABLED=false` and `BOT_SCHEDULED_MESSAGES_ENABLED=false` disable the features independently. The `bot_templates` and `bot_scheduled_sends` tables are inert if not queried.
