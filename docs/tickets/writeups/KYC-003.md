# KYC-003: Liveness Video Verification Call — Investigation & Implementation Write-up

## 1. Summary & Classification

**KYC-003** implements a live video call scheduled as part of a KYC case, allowing a human verifier to confirm the applicant is physically present and matches their submitted documents. The backend service (`app/services/kyc_liveness_call.py`, 497 lines), router (`app/routers/kyc_liveness_call.py`), and DynamoDB table (`kyc_liveness_calls`) are fully implemented. Two standalone frontend pages exist: `KycLivenessCallSchedulePage.tsx` (applicant-facing) and `KycLivenessCallVerifierPage.tsx` (reviewer/verifier facing). The remaining work is integrating call scheduling and result display into the KYC-001 admin case detail page and the applicant KYC status page.

- **Type**: Feature (live verification call scheduling, outcome recording, recording linkage)
- **Priority**: Medium — required for AML5D-compliant enhanced due diligence profiles
- **Status**: Backend + standalone pages implemented; case detail integration pending (depends on KYC-001)
- **Persona**: KYC verifier (ADMIN/ROOT acting as verifier), applicant (USER)
- **Dependencies**: KYC-001 (admin detail page), KYC-008 (liveness result feeds risk score). No dependency on the call infrastructure from the original ticket — there is no WebRTC integration; the "call" is represented as a scheduled slot with a pass/fail outcome and optional recording reference.
- **Cross-references**: [[SECOPS-007]] — no external video provider; mock recording ref generated in dev (`/mock/s3/{bucket}/{key}`). [[KYC-008]] reads `case.verification_call.result` for risk scoring.

## 2. Current-State Investigation

### 2.1 Backend Service: `app/services/kyc_liveness_call.py`

The `KycLivenessCallStore` dataclass (line 124) wraps `T.kyc_liveness_calls` (DDB table). The call lifecycle is:

```
scheduled -> in_progress -> passed
                         -> failed
          -> cancelled
          -> expired
```

Key operations and their line numbers:

**`schedule_call`** (line 143): Accepts `case_id`, `user_sub`, `scheduled_at`, `duration_minutes`, `verifier_sub`, `note`. Raises `KycLivenessCallConflictError` if an active call (status `scheduled` or `in_progress`) already exists for the case — checked via `ByStatus` GSI scan filtered by `case_id`. Writes a new record with `status=scheduled`.

**`conduct_call`** (verifier endpoint): Transitions `scheduled → in_progress`. Sets `start_ts`.

**`record_outcome`** (verifier endpoint): Transitions `in_progress → passed` or `in_progress → failed`. Requires non-empty `outcome_notes`. Sets `recording_ref` to `_recording_ref(call_id)` if `recording_linked=True`.

**`_recording_ref`** (line 132): In dev (`S.dev_mode=True`) returns `/mock/s3/{bucket}/{call_id}/recording.webm`; in prod returns the raw S3 key. Bucket from `S.kyc_liveness_call_bucket` (default `"local-uploads"` in dev).

**`cancel_call`**: Owner can cancel from `scheduled`; admin/root can cancel from `scheduled` or `in_progress`. Sets `status=cancelled`.

**`expire_stale_calls`**: Background job (not yet wired as a scheduled task) that transitions `scheduled` calls past their `scheduled_at + duration_minutes * 60 + grace_period` to `expired`.

**Views**: `owner_call_view` strips verifier details; `public_call_view(include_verifier=True)` for admin.

### 2.2 Router: `app/routers/kyc_liveness_call.py`

Prefix: `/ui/kyc/liveness-call`. Endpoints (line 1 docstring is authoritative):

**Owner endpoints** (cookie + CSRF via `require_ui_session`):
- `POST /` → schedule a call for a case
- `GET /` → list own calls
- `GET /case/{case_id}` → owner status for a specific case
- `GET /{call_id}` → get one call (owner view)
- `POST /{call_id}/cancel` → cancel own call

**Verifier/reviewer endpoints** (`require_admin_or_root`):
- `GET /admin/by-status` → list calls by status (ByStatus GSI)
- `GET /admin/{call_id}` → get one call with verifier details
- `POST /admin/{call_id}/conduct` → mark in_progress
- `POST /admin/{call_id}/result` → record pass/fail outcome
- `POST /admin/{call_id}/cancel` → admin cancel

Router registered in `app/main.py:117,577` — `app.include_router(kyc_liveness_call_router)`.

**Critical implementation note**: The ticket originally proposed a `KYC_VERIFIER` admin scope in `app/auth/roles.py`. This was **not implemented** — the `AdminScope` enum at `app/auth/roles.py:14` has `AUTH_SUPPORT`, `BILLING_SUPPORT`, `CONTENT_MODERATION`, `CONTENT_MODERATION_SENIOR` only. The router instead uses `require_admin_or_root` (any ADMIN or ROOT user can act as a verifier). This simplification avoids a new scope but means ALL admins can record call outcomes, not just those in a verifier pool.

### 2.3 DynamoDB Table: `kyc_liveness_calls`

Defined at `scripts/local-ddb-init.py:214–219`:
- PK: `call_id` (String, format `kyccall_{16 hex chars}`)
- GSI `ByStatus` (name: `S.kyc_liveness_call_status_index_name`): PK=`status`, SK=`created_at` (N)
- `attr_types={"created_at": "N"}` — present.

Key fields: `call_id`, `case_id`, `user_sub` (applicant), `verifier_sub` (optional), `status`, `scheduled_at`, `duration_minutes`, `start_ts`, `end_ts`, `outcome_notes`, `recording_ref`, `note`, `created_at`, `updated_at`.

### 2.4 Frontend: Standalone Pages Exist

- `frontend/src/pages/kyc/KycLivenessCallSchedulePage.tsx` — applicant schedules/views their call.
- `frontend/src/pages/kyc/KycLivenessCallVerifierPage.tsx` — verifier conducts and records result.
- `frontend/src/api/endpoints/kycLivenessCall.ts` — API wrapper.

These standalone pages work independently of the admin case detail (KYC-001). What is missing:

1. A `VerificationCallPanel` inside `KycCaseDetailPage.tsx` showing call status and a "Schedule Verification Call" button for reviewers.
2. A `ScheduledCallBanner` in the applicant's KYC status page (`KycStatusPage.tsx`) showing countdown and join link.

### 2.5 Dev/Prod Behavior

The service accepts an injectable `now` parameter on `schedule_call` and related methods (line 110–118: `_resolve_now`). This enables deterministic E2E tests that set `now` to a fixed timestamp. In prod, `now_ts()` provides the real Unix timestamp.

The recording reference is a path string — in dev it is a mock path, in prod it would be a real S3 key. There is no actual video recording mechanism; the verifier manually supplies the outcome after an external call.

## 3. Gap / Threat Analysis

### 3.1 Integration Gaps

**Admin case detail**: Reviewers viewing a case in the admin dashboard cannot see whether a verification call has been scheduled, its outcome, or access the recording. `VerificationCallPanel` must be added as a collapsible section inside `KycCaseDetailPage.tsx`. It calls `GET /ui/kyc/liveness-call/case/{case_id}` (owner endpoint — needs an admin variant) or `GET /ui/kyc/liveness-call/admin/by-status?status=all&case_id=...`.

**Applicant KYC status page**: The applicant (`KycStatusPage.tsx`) currently does not show a scheduled call notification or join link. A `ScheduledCallBanner` must be added that polls `GET /ui/kyc/liveness-call/case/{case_id}` and renders a countdown timer plus join link when within the join window.

**Missing admin case-level lookup**: The existing `GET /admin/by-status` takes a `status` query param (GSI PK). To find the call for a specific case, the reviewer must filter by `case_id` over a status-partitioned GSI scan. This is correct but requires that the frontend calls it with a `FilterExpression` on `case_id` or the endpoint exposes a `case_id` filter param (client-side filter, acceptable for low call volumes).

### 3.2 Verifier Pool Absent

The `KYC_VERIFIER` admin scope was not implemented. All admins are de-facto verifiers. This is a pragmatic simplification but has compliance implications:
- Any ADMIN can mark a liveness call as passed/failed, even one unrelated to the original assigned reviewer.
- Auto-assignment logic (pick verifier with fewest active calls) is not implemented.
- Workaround for now: convention that assigned reviewer conducts the call.

If a formal verifier pool is required in the future, adding the scope to `AdminScope` and filtering `require_admin_or_root` is backward-compatible — existing admin roles are unaffected until scope is enforced.

### 3.3 Call Window and Expiry

**Join window**: The ticket requires a "Join Call" button to activate only within 5 minutes of `scheduled_at`. The backend does not enforce this window — it simply allows `conduct_call` to transition `scheduled → in_progress`. The frontend must implement the time-window check client-side and disable/enable the button accordingly.

**Expiry**: `expire_stale_calls` exists in the service but is not wired to a background task in `app/main.py`. Without periodic execution, scheduled calls are never automatically expired. This means a missed call remains in `scheduled` status indefinitely, which:
- Blocks re-scheduling (the conflict check looks for `ACTIVE_STATUSES = {scheduled, in_progress}`).
- Inflates the `ByStatus` GSI's `scheduled` partition.

The fix: wire `expire_stale_calls` as a periodic task (similar to the existing `start_kyc_sla_checker_task` pattern at `app/main.py:528`).

### 3.4 Compliance and Legal

- **Recording consent**: Any recording reference stored on the call record implies the call was recorded. Production deployments must capture explicit consent from both parties (applicant and verifier) before recording. In dev, the recording ref is a mock path — no actual recording is made.
- **PII in outcome_notes**: Verifier notes are stored verbatim and visible to admins. Notes should not contain the applicant's personal information beyond what is needed to describe the call outcome. Reviewer training documentation must cover this.
- **Audit trail**: Every status transition writes a new record via `_audit_state_transition` pattern (implicit in the call lifecycle writes). The KYC-001 timeline pulls from the audit log — call schedule/conduct/result events appear in the case timeline automatically.
- **Double-scheduling race**: The conflict check reads the `ByStatus` GSI and filters by `case_id`. Under concurrent scheduling (two admins clicking "Schedule" simultaneously), both might pass the read check before either has written. The service uses a conditional write (`ConditionExpression: attribute_not_exists(call_id)`) for the new record, but the conflict check is a separate read. A DynamoDB-level constraint via a GSI-derived lock would be needed for strict idempotency. Acceptable for the current call volume.

### 3.5 Code Sites That Must Change

| File | Change |
|---|---|
| `frontend/src/pages/admin/KycCaseDetailPage.tsx` | Add `VerificationCallPanel` section |
| `frontend/src/pages/kyc/KycStatusPage.tsx` | Add `ScheduledCallBanner` |

## 4. Proposed Design / Fix

### 4.1 Admin Case Detail Integration

Add a `VerificationCallPanel` collapsible section at the bottom of `KycCaseDetailPage.tsx`:

```typescript
const { data: callData } = useQuery(
  ["kyc", "liveness-call", "case", caseId],
  () => fetchAdminCaseCall(caseId),  // new endpoint or filtered by-status
  { staleTime: 30_000 }
);
```

States handled:
- No call scheduled → show "Schedule Verification Call" button (admin only).
- Call scheduled → show datetime, verifier name, countdown, "Join Call" link (active within 5 min window), "Cancel" button.
- Call in_progress → show "In Progress" badge, "Record Result" form.
- Call passed/failed → show result badge, outcome_notes, recording link (if present).
- Call cancelled/expired → show terminal state badge, option to re-schedule.

**Schedule dialog**: `scheduled_at` datetime picker (min = now + 1 hour), `duration_minutes` select (5/10/15/30/60), optional `verifier_sub` text input (auto-filled with current user), optional `note`.

### 4.2 New Backend Endpoint: `GET /admin/case/{case_id}`

Add to `app/routers/kyc_liveness_call.py`:

```python
@kyc_liveness_call_router.get("/admin/case/{case_id}", response_model=KycLivenessCallOut)
def admin_get_call_for_case(
    case_id: str,
    _ctx: dict = Depends(require_ui_session),
    user: AuthenticatedUser = Depends(require_admin_or_root),
):
    """Get the active or most-recent call for a KYC case (admin view)."""
    call = STORE.get_call_for_case(case_id)
    if not call:
        raise HTTPException(status_code=404, detail={"code": "kyc_call_not_found"})
    return _out(call)
```

Add `get_call_for_case(case_id)` to `KycLivenessCallStore` — query the `ByStatus` GSI for all statuses, filter by `case_id`, return the most recently updated record. For low volume (1–3 calls per case), this is a multi-GSI-partition read with client-side filter (acceptable).

### 4.3 Stale Call Expiry Task (`app/main.py`)

```python
from app.services.kyc_liveness_call import STORE as LIVENESS_STORE

async def _expire_liveness_calls_task():
    import asyncio
    while True:
        try:
            LIVENESS_STORE.expire_stale_calls()
        except Exception:
            pass
        await asyncio.sleep(300)  # every 5 minutes

app.add_event_handler("startup", lambda: asyncio.ensure_future(_expire_liveness_calls_task()))
```

This mirrors the `start_kyc_sla_checker_task` pattern at `app/main.py:528`. In tests, the task is not started (test client does not run the ASGI lifespan startup events by default).

### 4.4 Dev/Prod Parity (SECOPS-007)

The service already satisfies SECOPS-007:
- **No video provider** — the call is a structured record, not a real video session. No outbound calls.
- **Mock recording ref** — in dev, `S.dev_mode=True` → `_recording_ref` returns `/mock/s3/...`; in prod, returns real S3 key.
- **Injectable `now`** — deterministic time in tests.
- **S3/DDB** — same pattern as KYC-002/004: moto in dev, real AWS in prod, via `app/core/aws_clients.py` and `app/core/tables.py`.

### 4.5 Applicant Status Page Integration

In `KycStatusPage.tsx`, add a `ScheduledCallBanner` queried with `useQuery(["kyc", "liveness-call", "case", caseId], () => getCaseCallStatus(caseId))`:

- `staleTime: 30_000` with `refetchInterval: 60_000` to poll for call status changes.
- Show countdown timer with a `useEffect` decrement loop when a call is scheduled.
- "Join Call" button active when `now >= scheduled_at - 300` (5 minutes before).

### 4.6 Alternatives Considered

- **Real WebRTC integration** — original ticket referenced `CALL-002` (RTCPeerConnection) and `CALL-009` (call recording). Not implemented; the service is a pure scheduling/outcome record system. WebRTC could be added later as a `join_url` in the call record pointing to a WebRTC room.
- **KYC_VERIFIER scope** — not implemented (see section 2.2). Would require changes to `app/auth/roles.py`, admin profile management, and the verifier pool service. Deferred to a follow-up ticket.
