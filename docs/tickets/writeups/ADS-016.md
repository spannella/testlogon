# ADS-016: Ad Scheduling & Dayparting — Investigation & Implementation Write-up

> ~5 pages. Read the real code before writing; cite `file:line`. Be concrete, not generic.

## 1. Summary & Classification

ADS-016 adds two scheduling layers to ad campaigns: dayparting (restricting ads to specific hours of the day and days of the week, per advertiser-specified timezone) and flight scheduling (multiple consecutive budget-and-creative phases within a single campaign). Both are stored directly on the existing campaign record in the `ad_campaigns` table — no new DDB table. The ad serving engine checks dayparting eligibility and active flight before selecting a campaign as a candidate. Budget pacing is adjusted to account for the number of active hours per day rather than assuming 24 hours.

- **Type**: Feature
- **Priority**: Medium
- **Status**: Implemented (service, router, frontend components, models; integrated into ad serving engine)
- **Owning area**: Ads platform — campaign scheduling
- **User persona**: Professional advertiser wanting time-of-day targeting (e.g., restaurant lunch specials, B2B business hours)
- **Cross-referenced tickets**: [[ADS-001]] campaign manager, [[ADS-004]] ad serving engine, [[ADS-007]] budget pacing, [[ADS-017]] performance optimisation (consumes schedule for optimisation), [[SECOPS-007]] dev/prod parity

## 2. Current-State Investigation (what exists today)

### 2.1 Service layer — `app/services/ad_dayparting.py` (425 lines)

The service is fully implemented.

**Core data structures** (`app/services/ad_dayparting.py:26-51`): `VALID_DAYS` (lowercase Monday-Sunday list), `VALID_HOURS` (0-23), and four predefined `SCHEDULE_TEMPLATES`: `"always"` (all days, all hours), `"weekdays_business"` (Mon-Fri 9-17), `"evenings"` (all days 18-23), `"weekends"` (Sat-Sun all hours, weekdays empty).

**Dayparting config validation** (`app/services/ad_dayparting.py:78`): `validate_dayparting_config()` calls `_zone(tz_str)` to verify the IANA timezone string via `ZoneInfo`. Sanitises the schedule by sorting and deduplicating hours. Requires at least one active hour across all days (returns `"Schedule must have at least one active hour"` if total is zero). Returns `(error_str, None)` or `(None, sanitised_dict)`.

**Eligibility check** (`app/services/ad_dayparting.py`): `is_campaign_eligible_now()` accepts an optional injectable `now: Optional[int]` parameter for deterministic testing. `_resolve_now()` at line 57-65 converts a Unix timestamp to a tz-aware `datetime` using the campaign timezone. The function returns `(eligible: bool, debug_info: dict)` with fields `timezone`, `local_time`, `day`, `hour`, `active_hours`. Fails open on invalid timezone: `_zone()` at line 68-72 returns `None` on error; the caller falls back to UTC.

**Flight validation** (`app/services/ad_dayparting.py`): `validate_flights()` accepts the flights list plus `campaign_start` and `campaign_end` date strings. Checks each flight's dates are within campaign bounds, that each has `daily_budget_cents >= 100` and at least one `creative_id`. Detects overlaps by sorting by `start_date` and comparing `sorted_flights[i]["end_date"] > sorted_flights[i+1]["start_date"]`.

**Active flight resolution** (`app/services/ad_dayparting.py`): `get_active_flight()` iterates flights and returns the first where `flight["start_date"] <= today <= flight["end_date"]`. Returns `None` when no flight is active (gap between flights or no flights configured). Also supports injectable `now` for tests.

**Budget pacing** (`app/services/ad_dayparting.py`): `calculate_dayparted_budget()` computes `active_hours_today` (length of the schedule's hour list for the current local day), `hours_remaining` (hours in the active list >= current hour), `hourly_budget_cents = daily_budget_cents // active_hours_today`, `remaining_budget_cents = hourly_budget * hours_remaining`. Without dayparting: assumes 24 active hours.

**Campaign schedule persistence** (`app/services/ad_dayparting.py`): `update_campaign_schedule()` builds a DDB `UpdateExpression` with `SET dayparting = :d, flights = :f, campaign_timezone = :tz` on the campaign record. Uses `T.ad_campaigns` and the campaign `account_id` + `campaign_id` composite key (consistent with ADS-001 campaign storage pattern). Returns the full updated campaign item.

**`get_campaign_schedule()`**: Returns a dict extracting `dayparting`, `flights`, `campaign_timezone` from a campaign item, plus a `pacing` snapshot from `calculate_dayparted_budget()`.

### 2.2 Integration into ad serving — `app/services/ad_serving.py`

The dayparting eligibility check is wired at `app/services/ad_serving.py:98-101`:
```python
if not _is_dayparting_eligible(campaign):
    continue
```

`_is_dayparting_eligible()` is defined at lines 325-357. It:
1. Returns `True` immediately if neither `dayparting` nor `flights` is set (no scheduling config)
2. Imports `is_campaign_eligible_now` and `get_active_flight` from `ad_dayparting` at runtime (lazy import, line 336)
3. On `dayparting`: calls `is_campaign_eligible_now()`, returns `False` if not eligible
4. On `flights`: calls `get_active_flight()`, returns `False` if `None` (no active flight)
5. Wraps the entire block in `try/except Exception` and returns `True` on error (fail open, line 356-357)

This means a mis-configured timezone does not block ad serving — campaigns with bad timezones serve as if always eligible. Intentional per SECOPS-007 graceful degradation rule.

## 3. Gap / Threat Analysis

### 3.1 Missing E2E spec

`frontend/e2e/ad-scheduling.spec.ts` does not exist. The 12 tests in sections 408-410 are entirely unwritten. This is the primary gap.

### 3.2 Missing unit tests

`tests/test_ad_scheduling.py` does not exist. The nine unit tests in the ticket's section 6.1 are unwritten.

### 3.3 `now` injection not threaded to all eligibility paths

`is_campaign_eligible_now()` and `get_active_flight()` both accept injectable `now`. The `_is_dayparting_eligible()` function in `ad_serving.py` (lines 341-356) calls both without passing `now` — it always uses wall-clock time. This is correct for production serving, but makes unit-testing `_is_dayparting_eligible()` dependent on real time. The `GET eligibility` endpoint correctly passes `now` (line 111). No fix required unless `ad_serving.py` unit tests need deterministic time.

### 3.4 Flight overlap validation edge case

`validate_flights()` checks `sorted_flights[i]["end_date"] > sorted_flights[i+1]["start_date"]` (comparing string date values). This works correctly for `YYYY-MM-DD` format. However, it uses `>` (strict), meaning two flights where one ends on `2026-06-14` and the next starts on `2026-06-14` would trigger an overlap error — a same-day transition is treated as overlap. Whether a flight ending and another starting on the same day should be allowed is a product decision. The current behaviour (disallowing) is conservative.

### 3.5 Daily budget pacing integer division

`hourly_budget_cents = daily_budget_cents // total_active` uses integer division. For a $100/day budget with 8 active hours, `hourly_budget = 10000 // 8 = 1250`. But `remaining_budget_cents = hourly_budget * hours_remaining`. If 3 hours remain: `1250 * 3 = 3750` ($37.50). The rounding error means `8 * 1250 = 10000` exactly (no error in this case). For non-divisible cases (e.g., 7 active hours, $100/day): `10000 // 7 = 1428`, `1428 * 7 = 9996` — 4 cents unallocated. Acceptable rounding for budget pacing purposes.

### 3.6 No dayparting-aware budget spend enforcement

`calculate_dayparted_budget()` returns how much budget *should* be available in remaining hours. But the actual serving engine does not call `calculate_dayparted_budget()` — it uses `_has_budget()` in `ad_serving.py` which checks raw `remaining_budget_cents` from the campaign record. The dayparted pacing calculation is exposed via the API but not enforced during serving. This means a dayparted campaign could front-load its budget in the first few active hours.

### 3.7 Flights and `ad_campaigns` table structure dependency

`update_campaign_schedule()` calls `T.ad_campaigns.update_item()` with `account_id` + `campaign_id` key. The `ad_campaigns` table key structure (PK/SK) must match what ADS-001 defines. If ADS-001 uses a different key structure than assumed here (e.g., PK=`ACCT#{account_id}`, SK=`CAMPAIGN#{campaign_id}`), the update will fail silently. The router's `_require_campaign_owner()` already queries a `ByCampaignId` GSI to find the campaign — the returned item has the correct `account_id` — so the update key should be valid.

## 4. Proposed Design / Fix

### 4.1 E2E spec — `frontend/e2e/ad-scheduling.spec.ts` (to create)

**Section 408 — Dayparting API (4 tests)**:
- Set schedule with `weekdays_business` template → 200, schedule persisted
- Invalid timezone → 400
- All-empty schedule → 400
- GET schedule returns what was set

**Section 409 — Flight scheduling API (4 tests)**:
- Set two non-overlapping flights → 200
- Overlapping flights → 400
- Flight outside campaign range → 400
- Eligibility check: configure flights where one is active for today → `active_flight != null`

**Section 410 — Eligibility and pacing (4 tests)**:
- GET eligibility → 200, `eligible`, `timezone`, `day`, `hour` fields present
- GET pacing → `active_hours_today <= 24`, `hourly_budget_cents >= 0`
- GET templates → `weekdays_business`, `evenings`, `weekends`, `always` all present
- Campaign with no dayparting → `eligible: True`

Auth: `injectAuth(page, "alice")`. Pre-create a campaign as Alice in `beforeAll`. Use injectable `now` parameter to test eligibility at a specific time.

### 4.2 Unit tests — `tests/test_ad_scheduling.py` (to create)

Nine pytest tests runnable offline (no DDB needed for pure validation logic):
- `test_validate_valid_config` — no error, sanitised schedule returned
- `test_validate_invalid_timezone` — error message returned
- `test_validate_empty_schedule` — error on all-empty
- `test_eligibility_active_hour` — inject `now` for an active hour → `eligible=True`
- `test_eligibility_inactive_hour` — inject `now` for a non-active hour → `eligible=False`
- `test_flight_active` — `get_active_flight(flights=[...], now=active_ts)` → returns correct flight

### 4.3 Dayparting-aware spend enforcement

To enforce the pacing constraint in serving, `_has_budget()` in `ad_serving.py` should consult `calculate_dayparted_budget()` when the campaign has dayparting configured. This would return the remaining budget for the current day based on active hours, and serve would check against this rather than raw remaining budget. This is a follow-on enhancement (marked for ADS-017 optimisation).

### 4.4 Same-day flight transition

Change the overlap check in `validate_flights()` from `f_end > f_start_next` to `f_end >= f_start_next` to allow same-day transitions. Document this as a product decision in code comments.

### 4.5 Dev/Prod parity (SECOPS-007)

Already fully satisfied:
- Schedule stored on `T.ad_campaigns` (DDB Local in dev, DynamoDB in prod)
- `ZoneInfo` from Python stdlib (no external dependency, no network)
- Injectable `now` parameter enables deterministic testing
- Fail-open on timezone errors (`_zone()` returns `None`, caller falls back to UTC or allows serving)
- Feature flag: `AD_DAYPARTING_ENABLED` in `app/core/settings.py:1611` gates the `ad_dayparting_router` registration in `app/main.py:720-721`

No mock needed for dayparting — it is entirely deterministic computation on campaign data.

### 5.6 Effort and risks

**Effort**: S (E2E spec: 1 day; unit tests: 0.5 day; dayparting-aware spend enforcement: 1 day if pursued).

**Risks**:
- `zoneinfo` IANA database completeness: on minimal container images, `tzdata` package may not be installed. Add `tzdata` to the apt dependencies in `scripts/setup_ubuntu.sh` to ensure all timezones are available.
- Flight overlap check rejects same-day transitions — minor product edge case, easy to fix
- Pacing calculation exposes budget distribution via API — advertisers could infer remaining budget from pacing endpoint; no significant abuse risk but consider rate-limiting the pacing endpoint
- `ad_serving.py:_is_dayparting_eligible()` fails open — a corrupted `dayparting` config does not block serving; monitor for mis-configured campaigns that should be paused but are serving
