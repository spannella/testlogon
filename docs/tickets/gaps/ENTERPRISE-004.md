# ENTERPRISE-004 Gap Analysis — Audit Log Export System

- [HIGH] Background async export worker not implemented — `app/services/` — The ticket's section 3.4 describes `audit_export_worker.py` with `run_audit_export_worker_loop()`; the file does not exist and no startup hook in `app/main.py` references it. Export jobs created via `POST /ui/admin/audit-exports` are only processed synchronously in dev mode (capped at 500 events); in production the job stays in `pending` status indefinitely. — Fix: Create `app/services/audit_export_worker.py`, register its startup coroutine in `app/main.py`, and wire S3 upload in `process_export_job`. — Effort: L

- [HIGH] S3 upload path dead in current pipeline — `app/services/audit_export_pipeline.py:110-116` — `create_export_job` only calls `_process_export_inline()` when `S.dev_mode` is True; when `dev_mode=False` it returns the `pending` job immediately with no code path that ever calls the S3 upload logic from the ticket's `process_export_job()`. The full prod export pipeline exists only in the ticket design doc, not in any deployed file. — Fix: Implement `process_export_job()` in the pipeline file (or the worker) with real S3 upload via `boto3`. — Effort: L

- [MED] `hmac.new()` is the correct Python API but `_compute_manifest_signature` uses it correctly — `app/services/audit_export_pipeline.py:238` — (`hmac.new` is the real stdlib function—confirmed working.) However the manifest `"contains_pii": True` field described in the ticket design is absent from the inline dev-mode manifest written to DynamoDB, so compliance tooling checking for that sentinel will not find it in dev exports. — Fix: Add `"contains_pii": True` to the manifest dict built in `_process_export_inline`. — Effort: S

- [MED] `list_audit_exports` queries only the caller's own exports — `app/routers/audit_export.py:110-116` — The endpoint queries `user-created-index` by `created_by == ctx["user_sub"]`. Root admins cannot see exports created by other root admins; there is no global list. For compliance handoff this is a gap. — Fix: Provide an admin-level `scan` path (with optional `created_by` filter) alongside the per-user query, or add a GSI on `created_at` for full listing. — Effort: S

- [MED] `"file"` audit category absent from adapter registry — `app/services/audit_adapters.py:441-447` — The ticket's section 1.2 and user stories mention file operation events as an exportable category, and `file.uploaded` / `file.shared` appear in the webhook event types. The `ADAPTERS` dict only has `auth`, `moderation`, `broadcast`, `admin`, `billing`; there is no `"file"` adapter and the category is not in `VALID_CATEGORIES`. — Fix: Add a `FileAuditAdapter` that reads from the relevant table (or augments the alerts adapter to include file events), and register it in `ADAPTERS`. — Effort: M

- [LOW] `download_audit_export` returns 410 for all prod exports — `app/routers/audit_export.py:152-168` — The endpoint checks for an `export_content` attribute (set only in dev-mode inline processing) and returns HTTP 410 if absent. In production, the file would be at a presigned S3 URL stored in `download_url`; the endpoint never redirects to that URL. — Fix: After the inline-content check, fall through to `return RedirectResponse(item["download_url"])` when `download_url` is present. — Effort: S

- [LOW] Scheduled recurring export not implemented — `app/routers/audit_export.py` / `app/services/` — The ticket's section 1.2 describes configurable recurring exports (e.g., weekly SOC 2 dumps) with CRON scheduling; no scheduler model, endpoint, or worker loop implements this capability. — Fix: Add a `POST /ui/admin/audit-exports/schedules` endpoint and a cron-style job runner. — Effort: L
