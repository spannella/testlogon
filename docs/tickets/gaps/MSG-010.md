# MSG-010 gaps — Countdown Messages

- [MED] `associated_event_id` is not verified to reference an existing event at creation time — `app/routers/messaging.py:9538` — `send_countdown_message()` stores `associated_event_id` as a raw string without checking that the broadcast/call/calendar event actually exists; a user can create a countdown pointing to a deleted or nonexistent event; when the timer expires and the "Watch Live" or "Join Call" CTA button is clicked, the linked page returns 404, confusing recipients — Fix: for non-custom `associated_event_type` values, add an optional existence check (gated by a setting `countdown_validate_event_id: bool`) that looks up the event in the appropriate DDB table before persisting the message — Effort: M

- [LOW] `CountdownComposerDialog` lacks a live preview of the countdown card — `frontend/src/pages/messages/CountdownComposerDialog.tsx` — the ticket component tree specifies a `PreviewSection` containing a live `CountdownCard` rendering while the user fills in the form; this is absent in the implementation; users cannot see what the card will look like before sending, increasing erroneous submissions — Fix: import `CountdownCard` in `CountdownComposerDialog` and render it conditionally when `title` and `targetDatetime` are both set — Effort: S

- [LOW] no `COUNTDOWN_MESSAGES_ENABLED` check on the frontend ComposeBar button — `frontend/src/pages/messages/ComposeBar.tsx:207` — `countdownOpen` state and the Timer button are always rendered regardless of the backend flag; if `COUNTDOWN_MESSAGES_ENABLED=false`, users see the button, click it, fill the form, and only get a 403 from the backend — Fix: expose `countdown_messages_enabled` via `GET /ui/config` and gate the Timer button in ComposeBar behind it — Effort: S

- [LOW] `target_datetime` in `SendCountdownMessageIn` uses `now_ts()` (integer seconds) in the `@model_validator` but the validator fires at model construction, not at endpoint invocation time — `app/routers/messaging.py:2097-2104` — if the model is constructed in a test at `T=0` and the endpoint is invoked later, the validation window is wrong; conversely, a countdown created exactly at the boundary can pass validation but have `target_datetime == now_ts()` by the time the DDB write completes — Fix: move the `target_datetime > now_ts()` check into the endpoint handler (after `body = SendCountdownMessageIn(...)`) to use the actual request timestamp — Effort: S
