# PLATFORM-011: Global Search — Gap Report

- [HIGH] `_search_messages` authorization check loads only first 500 conversations — `app/routers/search.py:282-284` — `list_user_conversations(user_id, limit=500)` is used to build `allowed_conv_ids`. Users with more than 500 conversations will have later conversations excluded from the auth-check set, causing message search results from those conversations to be silently dropped (not returned). This is a data-visibility gap, not a security gap, but it means search is systematically broken for power users — Fix: paginate `list_user_conversations` until exhausted (or use a participant-indexed GSI query) to build the complete `allowed_conv_ids` set before filtering — Effort: M

- [MED] `_search_tickets` returns tickets where user is `assigned_to` but ticket table schema stores assignee as `assigned_agent_id`, not `assigned_to` — `app/routers/search.py:389-391` — The filter checks `item.get("assigned_to") != user_id`, but inspection of `app/services/tickets.py` and `scripts/local-ddb-init.py` shows the attribute is `assigned_agent_id`. This means the assignee filter never matches → assigned tickets are excluded from search results — Fix: change `item.get("assigned_to")` to `item.get("assigned_agent_id")` in `_search_tickets` — Effort: S

- [MED] `_search_contacts` queries with `owner_id` partition key but contacts table PK is `CONTACT#{owner}#{contact}` — `app/routers/search.py:448-451` — The contacts query uses `Key("owner_id").eq(user_id)` but the contacts table (per `app/core/tables.py` and `scripts/local-ddb-init.py`) uses PK pattern `CONTACT#{owner_user_sub}#{contact_user_sub}` with no `owner_id` attribute. Every `_search_contacts` call returns zero results — Fix: align the query to use the correct PK pattern, e.g., use a GSI on `owner_user_sub` if one exists, or scan with a `begins_with` filter on PK — Effort: M

- [LOW] `GlobalSearchResponse` TypeScript type uses optional fields (`messages?`, `tickets?`, etc.) but backend always returns all domain sections — `frontend/src/api/endpoints/search.ts:41-45` — The optional fields mean callers must null-check every section even though the API always provides them. This creates extra `?.` ceremony across `Header.tsx` and `SearchPage.tsx`, and a future response shape change could silently produce `undefined` for a whole domain — Fix: change optional to required fields (`messages: SearchResultSection`, etc.) to match the guaranteed backend contract — Effort: S

- [LOW] No `recentSearches` field added to `uiStore` for local-first recent-search display — `frontend/src/stores/uiStore.ts` — Ticket section 3.4.3 specifies that `uiStore` gains a `recentSearches: string[]` alongside `recentCommands` for immediate local display while the server history fetch is in-flight. The store only fetches from the server; the Header palette shows no recents while the query is loading — Fix: add `recentSearches: string[]` to `uiStore` state and `partialize`, populated from the search history response on mount — Effort: S
