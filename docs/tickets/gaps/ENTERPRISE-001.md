# ENTERPRISE-001 Gap Analysis — Multi-Tenancy with Tenant Isolation

- [HIGH] `tenant_pk()` helper defined but never called — `app/core/tenant.py:31` — The `tenant_pk()` / `tenant_pk_for()` helpers that prefix DynamoDB PKs with `TENANT#<tid>#` exist in `app/core/tenant.py` but zero service files import or call them; all existing services still use bare PKs (`USER#`, `CONV#`, etc.), so data isolation across tenants is not actually enforced in any table. — Fix: Systematically migrate service layer PK construction to use `tenant_pk()`; add a lint rule/grep CI check to block raw PK construction. — Effort: L

- [HIGH] `AuthenticatedUser` lacks `tenant_id` field — `app/auth/deps.py:126-129` — The dataclass has no `tenant_id` field; sessions are not cross-validated against the request's `request.state.tenant_id`, so a session cookie minted for tenant-A works transparently on tenant-B. Described in ticket section 3.5.3 as a required fix. — Fix: Add `tenant_id: str = "default"` to `AuthenticatedUser`, populate it from the JWT, validate it against `request.state.tenant_id` in `require_ui_session`. — Effort: M

- [HIGH] `TenantMiddleware` blocks root admin from accessing suspended tenants — `app/middleware/tenant.py:131-136` — The middleware returns 503 for `status=="suspended"` with no escape hatch; the ticket design (section 3.4) specifies that root admins must bypass the 503 check, but no bypass is implemented. An attacker could lock root out by suspending the default tenant. — Fix: Check the `Authorization` header / cookie role before returning 503; bypass for authenticated ROOT sessions. — Effort: S

- [MED] Tenant admin member management endpoints absent — `app/routers/tenant_admin.py` — The ticket's section 4.3 specifies seven `/ui/tenant/admin/members/*` endpoints (list, invite, remove, settings, usage, logo upload, favicon upload) and a `require_tenant_admin` dependency; none are implemented in the router or service layer. — Fix: Implement `require_tenant_admin` dependency and mount the tenant-scoped admin sub-router. — Effort: M

- [MED] Domain lookup SK mismatch — `app/middleware/tenant.py:70` vs `app/services/tenant_service.py:add_domain` — Middleware looks up tenant domains with `sk="DOMAIN"` but `add_domain()` writes records with `sk="#TENANT"` (ticket section 3.3.2). The mismatch means custom-domain resolution always falls back to the default tenant. — Fix: Align the SK to `"#TENANT"` in middleware (or vice-versa in the service and DDB init). — Effort: S

- [MED] `TenantOut` model missing `settings_overrides` and `deleted_at`/`suspended_at` fields — `app/models.py:3943` — The response model omits `settings_overrides`, `deleted_at`, `suspended_at`, `suspended_reason`, and `limits` from the ticket's data model (section 3.3.1), exposing an incomplete view to API consumers. — Fix: Add the missing fields (with `Optional`) to `TenantOut`. — Effort: S

- [LOW] In-process domain cache not thread-safe for multi-worker deployments — `app/middleware/tenant.py:31` — The `_DOMAIN_CACHE` dict is module-level; with multiple uvicorn workers each cache is isolated. Cache invalidation via `invalidate_domain_cache()` only clears one worker's memory. — Fix: Document single-worker requirement for dev; for prod recommend Redis or DynamoDB-backed cache with TTL. — Effort: S
