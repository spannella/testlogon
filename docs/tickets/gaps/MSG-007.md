# MSG-007 gaps — Custom Emojis

- [HIGH] sticker upload in `sticker_collections.py` validates MIME only from declared `content_type` header, not magic bytes — `app/services/sticker_collections.py:159-160` — `_ALLOWED_MIME.get((content_type or "").lower())` trusts the caller-supplied MIME type header; an attacker can upload arbitrary binary (e.g. SVG with embedded JavaScript, or an HTML polyglot) by declaring `image/png`; custom emoji service (`custom_emojis.py`) correctly uses magic-byte sniffing via `_detect_content_type()` but sticker service does not — Fix: add a `_detect_content_type(data)` helper to `sticker_collections.py` (mirrors `custom_emojis.py:72`) and reject if sniffed MIME doesn't match declared or allowed list — Effort: S

- [MED] custom emoji in message reactions does not render custom images — `frontend/src/pages/messages/MessageBubble.tsx:903` — the MSG-011 comment notes full emoji picker is used for reactions, but `MessageBubble` renders reactions using `ReactionEmoji` component; no code resolves `custom:shortcode` reaction keys to `<img>` elements; custom emoji reactions display as raw `:shortcode:` text — Fix: in the reaction rendering path, check if reaction key starts with `custom:`, call `resolveCustomShortcodes`, and render `<img>` instead of text — Effort: M

- [MED] no shortcode collision check against built-in Unicode shortcodes at upload time — `app/services/custom_emojis.py` — the service checks uniqueness within the user's scope (GSI1 query) but does not verify the shortcode doesn't shadow a built-in Unicode emoji shortcode from the frontend's `SHORTCODE_MAP`; a user could register `:fire:` as a custom emoji, causing `replaceShortcodes()` to behave unexpectedly depending on resolution order — Fix: maintain a server-side set of reserved shortcodes (derived from emoji-data.ts at build time or hard-coded); reject uploads with `409 shortcode_reserved` if shortcode matches — Effort: M

- [LOW] `CUSTOM_EMOJIS_PERSONAL_ENABLED` and `CUSTOM_EMOJIS_IN_REACTIONS` feature flags absent — `app/core/settings.py:1114-1119` — only `custom_emojis_enabled` exists; the ticket specifies three separate flags; personal uploads and reaction usage cannot be independently disabled — Fix: add `custom_emojis_personal_enabled` and `custom_emojis_in_reactions` bool settings and check them in the relevant endpoints — Effort: S
