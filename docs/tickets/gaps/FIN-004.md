# FIN-004 Gaps

- [CRIT] Implementation aggregates creator EARNINGS (credits) but spec requires consumer SPENDING (debits) — `app/services/consumer_tax_documents.py:4,107-163` — the module docstring says "billing ledger *credit* (earnings) entries"; `_query_credit_entries` applies `FilterExpression: type = "credit"`; `classify_entry` from `creator_earnings.py` is used; the result is a creator 1099-style income summary, not the consumer spending summary (tips paid, subscriptions purchased, unlocks, shop orders) that FIN-004 specifies — Fix: rewrite `_query_credit_entries` to query `type="debit"` entries and replace `classify_entry` with a `classify_category` function mapping debit reasons to consumer categories (subscriptions, tips, purchases, unlocks, deposits) per the ticket spec section 3.3 — Effort: M

- [HIGH] `/receipts/zip` bulk export endpoint not implemented — `app/routers/consumer_tax_documents.py` (all 10 endpoints listed) — no `GET /ui/tax-documents/receipts/zip` endpoint exists; the FIN-004 spec requires bundling individual invoice PDFs for a date range into a ZIP download — Fix: add `export_receipts_zip()` in the service and a `/receipts/zip` router endpoint using Python stdlib `zipfile` and S3 invoice fetches — Effort: M

- [MED] `GET /ui/tax-documents/summary` accepts `date_from`/`date_to` parameters but the DDB ledger range query in `_query_credit_entries` uses a `between` key condition on `sk` with `LEDGER#{ts}` prefixes — `app/services/consumer_tax_documents.py:107-139` — the filter is correct for credit entries but will be wrong once switched to debits (different SK format may apply); also the `FilterExpression` is applied server-side which does not reduce DDB page size, requiring full pagination loop — Fix: verify the ledger SK format for debit entries and ensure the pagination loop covers all pages — Effort: S

- [LOW] No `tax_documents_enabled` feature flag check in router — `app/routers/consumer_tax_documents.py:35-38` — `_ensure_enabled()` checks `S.tax_documents_enabled` which defaults to `true` in `app/core/settings.py`; however the setting defaults to `"false"` in the FIN-004 spec (phased rollout) — Fix: align the default with the spec or document that it is intentionally enabled by default — Effort: S

- [LOW] Frontend `TaxDocumentsPage.tsx` calls `getSpendingSummary` which hits the credit-based backend — `frontend/src/pages/billing/TaxDocumentsPage.tsx` — once the backend scope mismatch (CRIT gap above) is fixed the frontend categories and column labels ("Subscriptions earned" vs "Subscriptions purchased") will need to be updated to reflect consumer spending semantics — Fix: coordinate frontend label updates with the backend fix — Effort: S
