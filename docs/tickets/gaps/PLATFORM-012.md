# PLATFORM-012: Activity Feed — Gap Report

- [CRIT] `POST /feed/record` accepts arbitrary `user_id` from request body (SEC-005 cross-ref) — `app/routers/activity_feed.py:148-170` — Any authenticated user can call `POST /feed/record` with any `user_id` value and inject forged activity entries into another user's feed. The `session=Depends(require_ui_session)` provides `session["user_sub"]` but the handler passes `body.user_id` (caller-controlled) directly to `record_activity()` at line 159, with no ownership check or admin-role gate. Impact: user A can flood user B's activity feed with arbitrary social noise, impersonate actors, or inject misleading tip/follow entries — Fix: replace `user_id=body.user_id` with `user_id=session["user_sub"]` at `activity_feed.py:159`; if an admin injection path is needed for test/debug, gate the free-form `user_id` field behind `require_admin_session` — Effort: S

- [MED] Bell popover lacks per-item "mark read" for activity items — `frontend/src/components/layout/Header.tsx:365-430` — The enhanced popover (PLATFORM-012 section architecture) shows Activity and System tabs but has no per-item read action; only "Mark all read" exists. The API endpoint `POST /ui/alerts/activity/read` (at `activity_feed.py:118-124`) accepts an `up_to` timestamp for bulk-marking, but the per-item interaction described in the ticket ("click notification → mark that item read") is not wired up in the UI — Fix: add `onClick` handler in `ActivityGroupCard.tsx` / `Header.tsx` activity items that calls `markActivitiesRead(item.created_at)` after navigation — Effort: S

- [MED] `ActivityFeed` component does not render grouped/batched cards — `frontend/src/pages/alerts/ActivityFeed.tsx` — The ticket specifies `PostActivityCard` that aggregates likes/comments/tips for the same post into one card with action-specific counts. `ActivityGroupCard.tsx` exists but renders each batch item individually by `activity_type` without cross-type grouping on `target_id`. Users with busy posts still see multiple rows per post rather than one aggregated card — Fix: in `ActivityFeed.tsx`, group incoming items by `(target_type, target_id)` before rendering, passing the whole group to `ActivityGroupCard` for consolidated display — Effort: M

- [LOW] `GET /ui/alerts/activity` endpoint not in the primary `alerts.py` router path — `app/routers/alerts.py:511` vs `app/routers/activity_feed.py:84` — Two separate routers define activity-feed endpoints at overlapping paths. `alerts.py:511` defines another `get_activity_feed()` that delegates to the same service, creating a duplicate route. This causes confusion and may cause FastAPI to use whichever route is registered last — Fix: remove the duplicate definition from `alerts.py:511` and consolidate all activity feed routes in `activity_feed.py` — Effort: S

- [LOW] No E2E tests covering the SEC-005 forgery scenario — `frontend/e2e/activity-feed.spec.ts` — Existing activity feed tests (sections covered in `activity-feed.spec.ts`) do not include a test where user A attempts to record an activity for user B and expects 403 — Fix: add a test using Alice's session to POST `/feed/record` with `user_id=bob_sub` and assert the response records it for Alice only (or returns 403 once the fix is applied) — Effort: S
