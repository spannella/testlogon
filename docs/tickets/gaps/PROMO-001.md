# PROMO-001 gaps

- [HIGH] Promo codes not integrated into subscription checkout — `app/routers/subscription_server.py` (no `promo_code` field in `SubscribeIn`, no call to `validate_promo_code` or `redeem_promo_code`) — Customers entering a promo code at subscription checkout get no discount; the entire new promo system is disconnected from the only checkout flow that exists — Fix: add optional `promo_code: str | None` to `SubscribeIn` and call `promo_codes.validate_promo_code` + `redeem_promo_code` inside the subscribe handler, re-using the TOCTOU guard pattern described in ticket §3 — Effort: M

- [HIGH] Promo codes not integrated into shop checkout — `app/routers/catalog.py` (no checkout/purchase endpoint at all) — `POST /ui/catalog/checkout` does not exist; ticket §5 notes this but marks it in-scope — Customers cannot apply promo codes to shop purchases; `shop` `applies_to` type is orphaned — Fix: either build a catalog checkout endpoint (larger effort) or gate `applies_to: ["shop"]` behind a future-ticket flag — Effort: L

- [MED] `PromoCodeInput` reusable component not built — `frontend/src/components/` (file absent) — Shop and subscription checkout pages cannot embed a standardised code-entry widget; each page must roll its own (or skip it); the shop `Checkout.tsx` has a local inline implementation — Fix: extract `PromoCodeInput` as a shared component with the 5 visual states per ticket §6 — Effort: S

- [MED] Promo code not wired into subscription frontend checkout — `frontend/src/pages/subscriptions/PlanBrowser.tsx:49` uses legacy `discount_code` field from the old `DiscountCodeManager`, not the new promo code API — Customers cannot use new promo codes (with usage limits, expiry, fixed-amount) from the subscription plan browser — Fix: replace or augment the `discount_code` input with a call to `POST /ui/promo-codes/validate`, then pass `promo_code` on subscribe — Effort: S

- [MED] No cross-creator code collision check enforced at read time — `app/services/promo_codes.py:191` `get_promo_code_by_string` queries GSI2; ticket §7 states global uniqueness, but the uniqueness check in `create_promo_code` only runs at creation and could race — Race condition: two creators create the same code simultaneously; both could succeed before either sees the other's item via eventual-consistency GSI; second redemption would validate against the wrong creator's code — Fix: add a condition expression on the GSI2 put or use a global dedup table with a strong-consistency get-item — Effort: S

- [LOW] No `promo_code_id` or `discount_cents` recorded in billing ledger on redemption — `app/services/promo_codes.py:357-410` writes a REDEEM row but does not call `new_ledger_entry` with `promo_code_id` — Revenue reconciliation cannot attribute discount to a specific campaign; ticket §3 step 6 requires billing ledger entry — Fix: add a `new_ledger_entry(…, meta={"promo_code_id": code_id, "discount_cents": discount_applied})` call in `redeem_promo_code()` — Effort: S

- [LOW] SEC-013 cross-ref: per-user limit bypass via concurrent requests not fully mitigated — `app/services/promo_codes.py:379` uses atomic `current_uses` increment with condition, but per-user check (`_query_promo_user_redeems`) is a separate read before the write — TOCTOU window between checking per-user redeems and writing the REDEEM row; two simultaneous redeems for the same user and code could both pass the per-user check before either writes — Fix: use a DDB conditional expression asserting absence of `REDEEM#{user_id}#*` in the same UpdateItem, or implement a per-user+code pessimistic lock via a transact-write — Effort: M
