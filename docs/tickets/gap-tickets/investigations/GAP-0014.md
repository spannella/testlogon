# GAP-0014 Investigation: `_message_out_from_item` never populates bot fields

**Verdict**: Confirmed — `app/routers/messaging.py:4162-4230`

## Code Evidence

`MessageOut` in `app/models.py` declares five bot-specific fields (lines 2492-2496):
```python
sender_type: Optional[Literal["user", "bot"]] = None
bot_id: Optional[str] = None
bot_name: Optional[str] = None
bot_avatar_url: Optional[str] = None
quick_replies: Optional[List[Dict[str, str]]] = None
```

The `_message_out_from_item` function (lines 3870–4230) builds a `MessageOut` at line 4162. The `return MessageOut(...)` call passes **none** of these five fields. Grep for `sender_type`, `bot_id`, `bot_name`, `bot_avatar_url`, `quick_replies` in `messaging.py` returns zero results inside this function or the `return MessageOut(...)` call.

The DDB items written by `send_bot_message` return dict includes these fields:
```python
return {
    "bot_id": bot_id,
    "bot_name": bot["name"],
    "bot_avatar_url": bot.get("avatar_url"),
    "sender_type": "bot",
    "text": text,
    "kind": kind,
}
```
But that dict is never written to DynamoDB (see GAP-0015), so even if `_message_out_from_item` were fixed, bot messages would not appear until GAP-0015 is also fixed.

## Root Cause

The `MessageOut` model was extended with bot fields (likely during BOT-001 model design), but `_message_out_from_item` was not updated to read and forward those fields from the stored DDB item. The function is very long (~360 lines) and the bot fields were simply omitted.

## Exact Fix

In `_message_out_from_item`, inside the `return MessageOut(...)` call at line 4162, add the five missing keyword arguments:

```python
return MessageOut(
    ...  # existing fields
    sender_type=merged_item.get("sender_type"),
    bot_id=merged_item.get("bot_id"),
    bot_name=merged_item.get("bot_name"),
    bot_avatar_url=merged_item.get("bot_avatar_url"),
    quick_replies=merged_item.get("quick_replies") or None,
)
```

All five fields are `Optional` with `None` default, so adding them is backward-compatible — non-bot messages will simply pass `None` for each field (and `exclude_none=True` in `model_dump` will omit them from API responses).

## Blast Radius / Exploit

Any API client or frontend that reads `sender_type`, `bot_id`, `bot_name`, `bot_avatar_url`, or `quick_replies` from `GET /messaging/conversations/{id}/messages` will always receive `None`/absent fields for bot messages. This means:
- Bot messages are indistinguishable from human messages (no `sender_type: "bot"` indicator)
- Bot names and avatars never appear in the UI
- Quick-reply buttons never render

No security exploit — missing data only.

**Note**: This fix has no visible effect until GAP-0015 is also fixed (bot messages aren't written to DDB today).
