# GAP-0023 Investigation: Users table key schema mismatch

## Verdict

**Partially confirmed** — the mismatch exists, but the GAP ticket description
over-states which services are affected.

### Actual key schema of `T.users`

`/home/ubuntu/testlogon/scripts/local-ddb-init.py:49-54`:
```python
TableDef(
    _resolve_table_name(S.users_table_name, "users"),
    "user_sub",          # partition key — no sort key
    gsi=[{"index_name": "ByKycTier", ...}],
    attr_types={"kyc_tier": "N", "kyc_tier_updated_at": "N"},
),
```
The `users` table has a **single-attribute primary key: `user_sub` (string)** — no
sort key, no `pk`/`sk` composite.

### Services that use `Key={"user_sub": user_sub}` — CORRECT

- `app/services/kyc_tiers.py:32,40,65,159,172` — all use `Key={"user_sub": user_sub}` ✓
- `app/services/registration.py:43` ✓
- `app/services/sso_saml_jit.py:19` ✓
- `app/services/kyc_sanctions_screening.py:289` ✓

### Service that uses `Key={"pk": f"USER#{user_sub}", "sk": "PROFILE"}` — WRONG

`app/services/kyc_risk_scoring.py` uses the wrong key format in **three places**:

| Line | Call |
|------|------|
| 335 | `T.users.get_item(Key={"pk": f"USER#{user_sub}", "sk": "PROFILE"})` |
| 434 | `T.users.get_item(Key={"pk": f"USER#{user_sub}", "sk": "PROFILE"})` |
| 451 | `T.users.get_item(Key={"pk": f"USER#{user_sub}", "sk": "PROFILE"})` |

These three calls are in:
- `_compute_country_risk()` (line 335)
- `_compute_profile_completeness()` (line 434)
- `_compute_account_age()` (line 451)

Because the table's PK is `user_sub`, not `pk`, DynamoDB will silently return an empty
`Item` for these calls (no `ValidationException` — DynamoDB accepts any key shape in
`GetItem`; it just returns `{}` when the key doesn't match a real item). The wrapping
`except Exception` blocks then return default-high-risk scores (30, 40, 60 respectively).

The GAP ticket's claim that `kyc_tiers.py` is the problematic service is
**incorrect** — `kyc_tiers.py` uses the right key format consistently. The actual
offender is `kyc_risk_scoring.py`.

## Root Cause

`kyc_risk_scoring.py` was written expecting the `users` table to use a composite
`pk`/`sk` key (the `profile` table pattern, which uses `user_sub` as PK without an
`sk`). The author confused the `users` table (simple `user_sub` PK, holds flat KYC
tier / account metadata) with a hypothetical composite-key profile store.

The `profiles` table (`T.profiles`, SK: none, PK: `user_sub`) also exists as a
separate entity. The risk scoring author may have intended to read from `T.profiles`
rather than `T.users`, or intended the users table to have a composite key.

## Exact Fix

Two options:

**Option A** — fix the key format in `kyc_risk_scoring.py` to match the actual schema:
```python
# Replace all three occurrences:
resp = T.users.get_item(Key={"user_sub": user_sub})
```
Note: `T.users` items written by `registration.py` include `first_name`, `last_name`,
`email`, `created_at` and KYC tier fields but may NOT include `country`, `nationality`,
or `date_of_birth`. Verify that `T.profiles` (via `T.profiles.get_item(Key={"user_sub":
user_sub})`) is the right table for the fields being read.

**Option B** (likely correct) — the risk scorer should read from `T.profiles`:
```python
# _compute_country_risk, _compute_profile_completeness, _compute_account_age:
resp = T.profiles.get_item(Key={"user_sub": user_sub})
```
This must be verified against the fields actually stored in each table.

## Blast Radius / Exploit

- All three `_compute_*` methods in `KycRiskScorer` silently return fallback-high-risk
  values for every user (country_risk → 30, profile_completeness → 40,
  account_age → 60), inflating every user's risk score.
- This does NOT cause a privilege escalation (higher risk → stricter KYC, not looser),
  but it may incorrectly block users from tier upgrades or trigger false-positive
  sanctions alerts.
- Not directly exploitable for financial gain, but causes systematic KYC false
  positives and undermines the risk model.
