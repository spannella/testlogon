# GAP-0009 Investigation: custom base_url SSRF in LLM provider key testing

## Verdict

**Confirmed** — `app/services/llm_provider_keys.py:173` (`test_key()` function)

When `S.dev_mode` is `False` (i.e., production) and `S.agent_llm_key_testing_enabled` is `True`,
`test_key()` constructs a URL directly from the user-supplied `base_url` field and issues an
HTTP GET to it with no SSRF guard:

```python
# app/services/llm_provider_keys.py:206-218
base_url = item.get("base_url") or registry.get("base_url", "")
endpoint = registry.get("test_endpoint", "/models")
url = f"{base_url.rstrip('/')}{endpoint}"
...
with httpx.Client(timeout=10) as client:
    resp = client.get(url, headers=headers)   # <-- arbitrary URL fetch
```

The `base_url` field on `LlmKeyCreateIn` (defined at `app/models.py:4203`) has only a
`max_length=500` constraint — no scheme enforcement and no IP-range block:

```python
class LlmKeyCreateIn(BaseModel):
    ...
    base_url: str = Field(default="", max_length=500)   # no https-only, no RFC-1918 block
```

The `add_key()` service function (`app/services/llm_provider_keys.py:89`) accepts and persists
the raw `base_url` without validation for all providers, not just `custom`:

```python
"base_url": base_url or PROVIDER_REGISTRY[provider]["base_url"],
```

Cross-ref: SEC-001 (SSRF prevention), SEC-022 (outbound HTTP controls). An SSRF utility already
exists at `app/services/webhook_ssrf.py` (`validate_webhook_url`) but is not called here.

## Root Cause

The `base_url` override was added to support OpenAI-compatible "custom" providers without
applying the same SSRF mitigations that were independently implemented for webhook URLs
(`webhook_ssrf.py`). The two features were developed independently with no shared validation
layer for outbound HTTP targets.

## Exact Fix

1. Add a Pydantic `field_validator` to `LlmKeyCreateIn` in `app/models.py`:

```python
from pydantic import field_validator

class LlmKeyCreateIn(BaseModel):
    ...
    base_url: str = Field(default="", max_length=500)

    @field_validator("base_url")
    @classmethod
    def _validate_base_url(cls, v: str) -> str:
        if not v:
            return v
        from app.services.webhook_ssrf import validate_webhook_url
        validate_webhook_url(v)   # raises ValueError on private IPs / non-HTTPS
        return v
```

2. Optionally also validate at persist time in `add_key()` in `app/services/llm_provider_keys.py`
   as a defence-in-depth check for any callers that bypass the Pydantic model.

3. Restrict validation to production: `webhook_ssrf.validate_webhook_url` already allows
   `http://localhost` in dev mode, so dev workflows are unaffected.

## Blast Radius / Exploit

Any authenticated user can:
1. Call `POST /ui/agent/llm-keys` with `provider="custom"` and
   `base_url="http://169.254.169.254/latest/meta-data/"` (AWS IMDSv1).
2. Call `POST /ui/agent/llm-keys/{key_id}/test` to trigger the outbound GET.
3. The response (HTTP 200 with EC2 instance metadata) is returned in the JSON response
   (`"models": []`) or as an error message (`"error": "HTTP 200: ami-id\ninstance-id\n..."`)
   exposing cloud credentials.

Variants: `http://localhost:8001/` (DynamoDB admin panel), `http://localhost:4566/`
(moto S3/Cognito mock), any internal service reachable from the backend host.

The endpoint requires authentication (`require_ui_session`) but any normal user account
(role=USER) is sufficient. No admin privilege is needed.

## Regression Test

```python
import pytest
from app.services.llm_provider_keys import add_key

@pytest.mark.parametrize("bad_url", [

def test_add_key_rejects_ssrf_base_url(bad_url):
    with pytest.raises(ValueError, match="HTTPS|private|blocked"):
        add_key(
            user_id="u1", provider="custom", label="test",
            api_key="sk-test12345", base_url=bad_url
        )

def test_add_key_accepts_https_base_url():
    # Should not raise

        user_id="u1", provider="custom", label="test",

```

Fails before fix (no validation → `add_key` succeeds), passes after.

## Dev/Prod Parity (SECOPS-007)

`test_key()` is a no-op in dev mode (`S.dev_mode = True`) — it returns a mock success without
making any HTTP call (see lines 190–199). The SSRF vulnerability is therefore **production-only**.
The fix via `validate_webhook_url` already contains `dev_mode` awareness and will not break local
workflows. The `field_validator` fires at model-construction time regardless of dev/prod, which
is correct — base_urls should always be HTTPS public endpoints.

## Effort

**S** — Add a `field_validator` reusing the existing `webhook_ssrf.validate_webhook_url` utility.
Single model change, no schema migration, no DynamoDB changes.
