# GAP-0013 Investigation: Abandoned registration permanently blocks email re-use

**Verdict**: Confirmed — `app/services/registration.py:79` and `app/services/registration.py:93-94`

## Code Evidence

`create_user_record` (lines 58–95) performs two writes with no TTL when `verification_required=True`:

**Write 1 — T.users (line 79):**
```python
T.users.put_item(
    Item=item,
    ConditionExpression="attribute_not_exists(user_sub)",
)
```
`item` is a plain dict with no TTL attribute. `with_ttl()` is imported but never called here.

**Write 2 — T.account_state via `set_account_state` (line 94):**
```python
set_account_state(user_sub, status, reason="initial_registration", requested_by=user_sub)
```
`app/services/account_state.py:set_account_state` has no TTL parameter and writes no `expires_at`/TTL attribute.

**Email availability check (line 53-55):**
```python
def is_email_available(email: str) -> bool:
    normalized = normalize_email(email)
    return not _user_exists(normalized)
```
`_user_exists` does a `get_item` on `T.users` — if the unverified record is present, it returns `True` → `is_email_available` returns `False` → user sees 409 "User already exists".

The challenge record itself **does** get a TTL (line 120-137 uses `with_ttl(payload, ttl_epoch=expires)`), but when the challenge expires the unverified `T.users` and `T.account_state` rows remain forever, permanently occupying the email address.

## Root Cause

The user record and account state were created before verification completes to hold the in-progress registration state, but no cleanup mechanism (TTL or background job) was added. Once the challenge expires the records are orphaned with no path to deletion.

## Exact Fix

In `create_user_record`, when `verification_required=True`, add a DynamoDB TTL attribute to both writes using `REGISTRATION_PENDING_TTL_DAYS` (new setting, suggest default = 7 days):

```python
from app.services.ttl import with_ttl

REGISTRATION_PENDING_TTL_DAYS = getattr(S, "registration_pending_ttl_days", 7)
pending_ttl = created_at + REGISTRATION_PENDING_TTL_DAYS * 86400

if verification_required:
    item = with_ttl(item, ttl_epoch=pending_ttl)

T.users.put_item(Item=item, ConditionExpression="attribute_not_exists(user_sub)")
```

For `set_account_state`, add an optional `ttl_epoch` parameter and apply `with_ttl` when provided:
```python
set_account_state(user_sub, status, ..., ttl_epoch=pending_ttl if verification_required else None)
```

On successful verification, the TTL attribute should be removed (DDB `REMOVE` in UpdateExpression) so the record persists normally.

Add a setting to `.env.local.example`:
```
REGISTRATION_PENDING_TTL_DAYS=7
```

## Blast Radius / Exploit

**Denial-of-service on email addresses**: An attacker (or a user who simply abandons registration) can permanently block any email address from being registered. Starting registration with `bob@example.com` and never completing verification leaves that address dead forever. There is no admin UI or API to reset it; the only recovery is a direct DynamoDB manual delete.

**Scope**: affects all users in dev_mode registration path (Cognito disabled) and potentially production if Cognito is not configured.

```python
def test_abandoned_registration_email_reusable_after_ttl(client, freezer):
    # Register alice, don't verify
    client.post("/ui/register", json={"email": "alice@test.local", ...})
    # Advance time past TTL (DDB TTL is async in real DDB, but mock should respect item TTL)
    # Alternatively: directly assert the T.users item has a TTL attribute
    item = T.users.get_item(Key={"user_sub": "alice@test.local"}).get("Item", {})
    assert S.ddb_ttl_attr in item   # fails before fix, passes after
    assert item[S.ddb_ttl_attr] > now_ts()
```

**Additional assertion**: after TTL fires (simulate by deleting item + re-registering), `is_email_available("alice@test.local")` should return `True`.

## Dev/Prod Parity

DynamoDB TTL works identically in AWS DynamoDB and DynamoDB Local (the TTL attribute is stored; local doesn't auto-expire items but the attribute is present for testing). The `with_ttl` helper sets `S.ddb_ttl_attr` which is configured identically in both environments. No parity risk beyond ensuring the `T.users` table has TTL enabled in production (`ttl_attr` set in table configuration).
