# GAP-0029 Investigation: Old POST /ui/privacy/delete-account skips production password verification

## Verdict

**Confirmed** — two delete-account endpoints coexist with materially different security postures:

### New endpoint (correct)
`POST /ui/privacy/account-deletion/request` in `app/routers/account_deletion.py:58–75`:
```python
if not verify_user_password(user_sub, body.password):
    raise HTTPException(status_code=401, detail="Invalid password")
```
`verify_user_password` (`app/services/cognito_auth.py:21`) calls Cognito
`AdminInitiateAuth` in production (`S.dev_mode=False` and Cognito configured).

### Old endpoint (broken)
`POST /ui/privacy/delete-account` in `app/routers/privacy.py:126–154`:
```python
if not body.password:
    raise HTTPException(status_code=401, detail="Password required")

if not S.dev_mode:
    # In production, verify against Cognito
    # For now, this is a placeholder
    pass
```
The password is checked for non-emptiness only.  The `if not S.dev_mode:` block is a comment-only
placeholder — no Cognito call is made.  In production (`dev_mode=False`), any non-empty string
(e.g. `"x"`) is accepted as the password.

Both routes are registered and reachable: `privacy_router` (prefix `/ui/privacy`) is included at
`app/main.py:630`.  A `POST /ui/privacy/delete-account` with `password="x"` will schedule account
deletion for the authenticated user without verifying their real password.

Cross-ref SEC-018: the old route also does not call `revoke_all_sessions` or any session
revocation step on initiation (the new route defers that to the background deletion processor).

## Root Cause

The `account_deletion.py` router (PLATFORM-018) was added as a replacement for the legacy
`privacy.py` deletion endpoint but the old endpoint was never removed.  The placeholder comment
was likely intended as a temporary marker but was shipped without completing the implementation.

## Exact Fix

**Option A (preferred): remove the old endpoint entirely.**

Delete the `request_deletion` handler from `app/routers/privacy.py` (lines 126–154) and update
any frontend references from `/ui/privacy/delete-account` to
`/ui/privacy/account-deletion/request`.

**Option B: patch the old endpoint to call `verify_user_password`.**

```python
# app/routers/privacy.py — replace lines 144–152:
from app.services.cognito_auth import verify_user_password

    if not body.password:
        raise HTTPException(status_code=401, detail="Password required")
    if not verify_user_password(user_sub, body.password):
        raise HTTPException(status_code=401, detail="Invalid password")
```

Option A is cleaner because the new endpoint already has the correct grace-period lifecycle,
retention-hold checks, and audit trail.

## Blast Radius / Exploit

An attacker who has obtained a valid session cookie (e.g., via XSS or session fixation) can
schedule account deletion for the victim without knowing their password.  In the worst case, if
`S.account_deletion_destructive=True` (the production setting), this triggers full data cascade
deletion after the grace period with no recovery path.

Cross-ref SEC-018: absence of immediate session revocation means the window between initiation and
deletion processing leaks an active session.

```python
# 1. Create a session for user Alice.

```

## Dev/Prod Parity

In dev mode (`S.dev_mode=True`), `verify_user_password` intentionally accepts any non-empty
password (consistent with the rest of the stack — same behaviour as the new endpoint).  The fix
closes the gap in production only, which is the intended behaviour per SECOPS-007.

## Effort

**S** — removing the old endpoint (or adding two lines to patch it) plus redirecting frontend
calls and adding a unit test.
