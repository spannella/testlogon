# GAP-0004 Investigation: revenue-share PUT endpoint allows any user to self-set share to 100%

**Verdict**: Partially-confirmed

---

## Evidence

`app/routers/content_ad_controls.py` line 116–120 — the PUT endpoint is protected by `require_ui_session` and writes the calling user's own `revenue_share_bps`:

```python
@content_ad_controls_router.put("/revenue-share")
def set_revenue_share_endpoint(body: RevenueShareIn, ctx=Depends(require_ui_session)):
    from app.services.content_ad_controls import set_creator_revenue_share_bps
    return set_creator_revenue_share_bps(ctx["user_sub"], body.revenue_share_bps)
```

`app/models.py` line 11677 — the `RevenueShareIn` model accepts `revenue_share_bps` in the range `[0, 10000]`:

```python
class RevenueShareIn(BaseModel):
    revenue_share_bps: int = Field(ge=0, le=10000)
```

`app/services/content_ad_controls.py` line 85–98 — the service clamps to `[0, 10000]` but does not enforce a maximum creator-facing cap:

```python
def set_creator_revenue_share_bps(creator_sub: str, revenue_share_bps: int) -> Dict[str, Any]:
    # ...set via a dedicated admin/owner path. Clamped to [0, 10000].
    bps = max(0, min(10000, int(revenue_share_bps)))
    ...
```

**The GAP-0004 claim is partially correct:**

1. Any authenticated creator CAN call `PUT /ui/content-ad-controls/revenue-share` and set their own `revenue_share_bps` to 10000 (100%). This is confirmed.
2. However, the GAP ticket's proposed fix ("gate PUT on require_admin_or_root; add creator_sub to request body") may be overly restrictive. The intended design may be for creators to set their own share, within a platform-defined ceiling. The real gap is that there is **no platform-enforced ceiling** below 10000 bps (e.g., a `MAX_CREATOR_REVENUE_SHARE_BPS` constant like 7000 = 70%), leaving 0% for the platform.

The creator can only modify their **own** share (the endpoint always uses `ctx["user_sub"]`), so the IDOR risk claimed is not present. The actual risk is revenue leakage: a creator sets 10000 bps and the platform earns nothing.

---

## Root Cause

No upper bound is enforced below 10000 bps for the creator-self-service path. The `RevenueShareIn` model and the service both allow the full `[0, 10000]` range, enabling a creator to claim the entire ad revenue share and leave 0% for the platform.

---

## Exact Fix

Define a platform policy constant (e.g., `MAX_CREATOR_REVENUE_SHARE_BPS = 7000`) and enforce it in the service layer:

In `app/services/content_ad_controls.py`:

```python
MAX_CREATOR_REVENUE_SHARE_BPS = 7000  # 70% max creator share; 30% platform floor

def set_creator_revenue_share_bps(creator_sub: str, revenue_share_bps: int) -> Dict[str, Any]:
    bps = max(0, min(MAX_CREATOR_REVENUE_SHARE_BPS, int(revenue_share_bps)))
    ...
```

Optionally update the Pydantic model for the self-service path:

```python
class RevenueShareIn(BaseModel):
    revenue_share_bps: int = Field(ge=0, le=7000)  # 70% max for creator self-service
```

If admins need to set shares above 7000, the admin path (separate endpoint or `require_admin_or_root` dependency) should use a wider-range model.

Note: the GAP ticket's recommendation to gate the entire PUT endpoint on `require_admin_or_root` would break the self-service creator flow entirely. A ceiling is the correct fix unless the intent is full admin-only control.

---

## Blast Radius / Exploit

Any creator can send:

```json
{"revenue_share_bps": 10000}
```

to `PUT /ui/content-ad-controls/revenue-share` to retain 100% of all ad revenue generated on their content, reducing platform share to 0%. This affects all ad impressions and clicks on that creator's content. Platform revenue loss scales with the creator's audience size.
