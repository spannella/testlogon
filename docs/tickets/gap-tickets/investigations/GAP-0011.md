# GAP-0011 Investigation: respond_to_feedback does not inject response or resume agent

**Verdict**: Confirmed — `app/services/terminal_monitor.py:233`

## Code Evidence

`respond_to_feedback` (lines 233–265) only writes the response text to DynamoDB and returns the updated item:

```python
def respond_to_feedback(user_id, worker_id, request_id, response_text):
    ...
    T.agent_feedback.update_item(
        Key={"pk": f"WORKER#{worker_id}", "sk": f"FEEDBACK#{request_id}"},
        UpdateExpression="SET feedback_status = :st, response_text = :rt, responded_at = :ra",
        ExpressionAttributeValues={":st": "responded", ":rt": response_text, ":ra": ts},
    )
    return get_feedback_request(worker_id, request_id)
```

Two actions are missing:

1. **No terminal injection**: There is no `_inject_into_terminal` function anywhere in the codebase (confirmed by grep across all of `app/`). Nothing writes the user's `response_text` into the SSH/VNC terminal stdin.

2. **No state transition**: `transition_agent_state` (in `app/services/agent_orchestrator.py:83`) supports `awaiting_feedback → working` (per `VALID_TRANSITIONS` at line 30), but is never called here. The agent remains stuck in `awaiting_feedback` indefinitely.

The router that calls this (`app/routers/agent_feedback.py:259`) also adds no post-processing — it just returns the updated record.

## Root Cause

The feedback response was implemented as a data-only operation (update DDB record) without the operational side-effects needed to close the feedback loop: injecting text into the running terminal and unblocking the agent state machine.

## Exact Fix

1. Add an `_inject_into_terminal(worker_id, response_text)` helper in `terminal_monitor.py` that calls `get_or_create_buffer(worker_id).append(response_text)` and — if a live WebSocket channel exists for the worker — sends the text as `stdin` to the SSH/VNC session.

2. In `respond_to_feedback`, after the DDB update, call:
   - `get_or_create_buffer(worker_id).append(response_text)` to record the injected response in the output buffer.
   - `agent_orchestrator.transition_agent_state(user_id, worker_id, "working")` to unblock the agent.

Minimal viable fix (no live SSH injection yet, at least unblocks state machine):
```python
# at bottom of respond_to_feedback, after DDB update:
from app.services.agent_orchestrator import transition_agent_state
from app.services.terminal_monitor import get_or_create_buffer

get_or_create_buffer(worker_id).append(f"\n[User response]: {response_text}\n")
try:
    transition_agent_state(user_id, worker_id, "working")
except ValueError:
    pass  # worker may have been manually transitioned; log but don't fail the API call
return get_feedback_request(worker_id, request_id)
```

## Blast Radius / Exploit

Every workflow that calls `POST /agent-feedback/{worker_id}/{request_id}/respond` is silently broken. The agent's `agent_state` stays `awaiting_feedback` forever; no further work is done on the ticket. The agent appears "stuck" with no user-visible error. Users cannot recover without an admin manually resetting the worker state via the orchestrator.

There is no security exploit — this is a functional correctness gap.

## Dev/Prod Parity

The DDB update itself uses the standard boto3 path (`T.agent_feedback.update_item`) which is identical in local mock and AWS DynamoDB. The missing `transition_agent_state` call also uses DDB. No AWS-specific parity risk.

## Effort

M — two additional service calls in `respond_to_feedback`; the harder part is the live terminal injection which requires wiring to the SSH WebSocket session store (which does not yet exist as a queryable registry).
