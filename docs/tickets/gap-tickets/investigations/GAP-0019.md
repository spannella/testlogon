# GAP-0019 Investigation: consumer_tax_documents aggregates creator EARNINGS (credits) instead of consumer SPENDING (debits)

**Date**: 2026-06-05
**Investigator**: Claude Code

---

## Verdict

**Confirmed** — `app/services/consumer_tax_documents.py` is a creator-earnings module masquerading as a consumer-spending module. It queries `type="credit"` ledger entries (income to creators) and reuses `creator_earnings.classify_entry`. The FIN-004 spec unambiguously requires `type="debit"` entries (consumer spending) with a distinct `classify_category` function. This is a data-direction inversion bug.

---

## Evidence

### The FIN-004 spec (authoritative)

`docs/tickets/FIN-004-consumer-tax-documents.md` section 3.3 (Category Classification table, lines 207–215):

```
| Ledger `type` | Ledger `reason` pattern         | Tax Category  |
|---------------|---------------------------------|---------------|
| `debit`       | "Subscription*" / "Plan*"       | subscriptions |
| `debit`       | "Tip*"                          | tips          |
| `debit`       | "Purchase*" / "Cart*"/"Order*"  | purchases     |
| `debit`       | "Unlock*"                       | unlocks       |
| `debit`       | "Deposit*" / "Wallet*"          | deposits      |
| `debit`       | (other)                         | other         |
| `credit`      | (all)                           | Excluded      |
```

Section 1.2 user stories (line 22): "Tax summary endpoint returns **spending** grouped by: subscriptions, tips, purchases, unlocks, deposits."

Section 3.1 data flow: calls `compute_spending_summary()` (not `compute_earnings_summary()`).

### The implementation

`app/services/consumer_tax_documents.py`:

- **Module docstring (lines 1–11)**:
  > "Generates annual tax documents (earnings summary / 1099-style) for creators from their billing ledger **credit** (earnings) entries."

- **`_query_credit_entries` (lines 107–134)**:
  ```python
  "FilterExpression": Attr("type").eq("credit"),
  ```

- **`compute_earnings_summary` (lines 141–197)**:
  ```python
  category = classify_entry(entry)  # imported from creator_earnings.py
  ```

- **`CATEGORIES` constant (line 48)**:
  ```python
  CATEGORIES = ("subscriptions", "tips", "unlocks", "vod_purchases", "other")
  ```
  Note: `vod_purchases` (creator income from VOD sales) instead of `purchases`/`deposits` (consumer spending categories).

- **Router docstring** (`app/routers/consumer_tax_documents.py:3-4`):
  > "Annual **creator-earnings** (1099-style) tax documents derived from billing ledger **credit entries**."

### The correct behavior per spec

The module should query `type="debit"` entries and map them to consumer-spending categories (`subscriptions`, `tips`, `purchases`, `unlocks`, `deposits`) using a `classify_category` function that is completely separate from `creator_earnings.classify_entry`.

### Summary of differences

| Aspect | Implementation (actual) | Spec (FIN-004) |
|--------|------------------------|----------------|
| Ledger `type` filter | `credit` | `debit` |
| Classification function | `creator_earnings.classify_entry` | new `classify_category` |
| Categories | subscriptions, tips, unlocks, vod_purchases, other | subscriptions, tips, purchases, unlocks, deposits, other |
| Audience | Creator receiving money | Consumer spending money |
| PDF title | "ANNUAL EARNINGS TAX SUMMARY" | Consumer spending summary |

## Root Cause

The implementation copied/adapted from the creator-earnings module without reversing the data direction. The module was named `consumer_tax_documents` but implemented creator-earnings logic, likely because both features needed "billing ledger aggregation by category" and the implementer reused the nearest existing pattern.

The naming mismatch is pervasive: the router imports `TaxSpendingSummaryOut` (spending-named model), the endpoint URL is `/ui/tax-documents/summary`, but the service returns earnings data. The Pydantic model `TaxSpendingSummaryOut` has no `spending` vs `earnings` enforcement — it's just field names.

## Exact Fix

### 1. Replace `_query_credit_entries` with a debit query

```python
def _query_debit_entries(*, user_sub: str, date_from: int, date_to: int) -> List[Dict[str, Any]]:
    """Query billing ledger *debit* entries (consumer spending) within [date_from, date_to]."""
    pk = user_pk(user_sub)
    key_cond = Key("pk").eq(pk) & Key("sk").between(
        f"LEDGER#{date_from}#", f"LEDGER#{date_to}#~"
    )
    query_kwargs = {
        "KeyConditionExpression": key_cond,
        "FilterExpression": Attr("type").eq("debit"),
        "Limit": 500,
    }
    collected = []
    for _ in range(40):
        resp = T.billing.query(**query_kwargs)
        collected.extend(resp.get("Items", []))
        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break
        query_kwargs["ExclusiveStartKey"] = last_key
    return collected
```

### 2. Replace `classify_entry` import with a new `classify_category` function

```python
CATEGORIES = ("subscriptions", "tips", "purchases", "unlocks", "deposits", "other")

def classify_category(entry: Dict[str, Any]) -> Optional[str]:
    if entry.get("type") != "debit":
        return None
    reason = entry.get("reason", "").lower()
    if reason.startswith(("subscription", "plan")):
        return "subscriptions"
    if reason.startswith("tip"):
        return "tips"
    if reason.startswith(("purchase", "cart", "order")):
        return "purchases"
    if reason.startswith("unlock"):
        return "unlocks"
    if reason.startswith(("deposit", "wallet")):
        return "deposits"
    return "other"
```

### 3. Rename `compute_earnings_summary` → `compute_spending_summary`

Update call sites in `app/routers/consumer_tax_documents.py` and `app/services/tax_form_1099.py` (which currently imports from `consumer_tax_documents`; note that `tax_form_1099.py` legitimately needs the credit/earnings version, so it should NOT use the renamed function — it should import from `creator_earnings` directly instead).

### 4. Update PDF title

`generate_tax_summary_pdf`: change `"ANNUAL EARNINGS TAX SUMMARY"` to `"ANNUAL SPENDING SUMMARY"`.

---

## Blast Radius / Exploit

- **Users see their income instead of their spending** on the Consumer Tax Documents page. A creator who is also a buyer sees their earnings; a pure consumer sees nothing (no credit entries).
- **IRS / tax compliance**: A consumer relying on this document for expense reporting gets completely wrong data.
- **Threshold gate**: `tax_documents_min_earnings_cents` checks `grand_total_cents` — for credit entries this is the creator's earnings threshold (e.g. $600 1099 threshold), while consumers would have no threshold. Users below the credit threshold are blocked from generating a document even though they may have significant spending.
- **No external exploit** — data is user-scoped; a user sees only their own (wrong) data.

## Regression Test

**pytest** (`tests/test_consumer_tax_documents.py`):

```python
# Fails before fix:
def test_spending_summary_queries_debits(mock_billing_table):
    # Seed one credit and one debit entry for the same user
    mock_billing_table.seed([
        {"pk": "USER#alice", "sk": "LEDGER#1700000000#e1", "type": "credit",
         "amount_cents": 5000, "reason": "Tip received"},
        {"pk": "USER#alice", "sk": "LEDGER#1700000001#e2", "type": "debit",
         "amount_cents": 1000, "reason": "Tip sent"},
    ])
    summary = compute_spending_summary(user_sub="alice", date_from=0, date_to=9999999999)
    # Before fix: grand_total = 5000 (credit), category = tips via creator_earnings
    assert summary["grand_total_cents"] == 1000  # only the debit

# Passes after fix:
    assert summary["grand_total_cents"] == 1000
    assert summary["categories"][1]["category"] == "tips"  # tips debit
    assert summary["categories"][1]["total_cents"] == 1000
```
