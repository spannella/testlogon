# GAP-0015 Investigation: `send_bot_message()` returns a dict but never writes to DynamoDB

**Verdict**: Confirmed — `app/services/chat_bot.py:283-312`

## Code Evidence

`send_bot_message` (lines 283–312):

```python
def send_bot_message(*, bot_id, conversation_id, text, kind="text"):
    bot = get_bot(bot_id=bot_id)
    if not bot or bot["status"] != "active":
        return None

    # Increment message count (on the bot record, not messages table)
    try:
        T.chat_bots.update_item(
            Key={"pk": f"CREATOR#{bot['creator_id']}", "sk": f"BOT#{bot_id}"},
            UpdateExpression="SET message_count = ...",
            ...
        )
    except ClientError:
        pass

    return {
        "bot_id": bot_id,
        "bot_name": bot["name"],
        "bot_avatar_url": bot.get("avatar_url"),
        "sender_type": "bot",
        "text": text,
        "kind": kind,
    }
```

The function:
- Updates `message_count` on the `T.chat_bots` table (cosmetic counter)
- Returns a plain dict

It does **not** call `T.messages.put_item`, `tbl_msgs.put_item`, `send_text_message`, or any function that writes to the messages DynamoDB table. There is no `create_internal_bot_message` helper anywhere in the codebase.

**Callers confirmed to discard the return value:**

1. `app/routers/chat_bot.py:219` — `result = send_bot_message(...)` then returns `result` to the HTTP caller. The API client receives the dict, but no message appears in the conversation.

2. `app/routers/bot_template.py:271-278` — calls `send_bot_message(...)`, checks for `None`, then returns `{"ok": True, "rendered_text": ...}`. The dict is discarded.

3. `app/services/bot_scheduler.py:277-281` — calls `send_bot_message(...)` with result completely discarded (no assignment).

## Root Cause

`send_bot_message` was stubbed with a counter update and metadata dict return, but the actual message persistence step (writing to `T.messages` / the messaging pipeline) was never implemented. All callers assume the function handles persistence.

## Exact Fix

Implement a `create_internal_bot_message` helper in `app/routers/messaging.py` that writes directly to `tbl_msgs` (the messages table), following the same pattern as `send_text_message`. Then call it from `send_bot_message`.

Sketch:
```python
# in app/services/chat_bot.py (or call into messaging.py)
from app.routers.messaging import send_text_message_internal  # or equivalent

def send_bot_message(*, bot_id, conversation_id, text, kind="text"):
    bot = get_bot(bot_id=bot_id)
    if not bot or bot["status"] != "active":
        return None

    ts = now_ts()
    message_id = "m_" + uuid4().hex
    item = {
        "conversation_id": conversation_id,
        "message_id": message_id,
        "sender_id": f"bot:{bot_id}",
        "sender_type": "bot",
        "bot_id": bot_id,
        "bot_name": bot["name"],
        "bot_avatar_url": bot.get("avatar_url"),
        "text": text,
        "kind": kind,
        "created_at": ts,
        "status": "active",
        "quick_replies": bot.get("quick_replies") or [],
    }
    tbl_msgs.put_item(Item=item)   # or call shared messaging helper

    # Update message_count
    T.chat_bots.update_item(...)

    return item
```

Note: `tbl_msgs` lives in `app/routers/messaging.py`. To avoid circular imports, extract the low-level message write into `app/services/messaging.py` or a shared internal helper.

## Blast Radius / Exploit

Every feature that sends bot messages is completely non-functional:
- **Manual bot send** (`POST /bots/{bot_id}/send`) — API returns a dict but no message appears in the conversation
- **Template preview send** (`POST /bots/{bot_id}/templates/{template_id}/send`) — same
- **Scheduled bot sends** (`bot_scheduler.py`) — scheduled messages fire (the scheduler runs), increment the counter, but no visible message is delivered to the conversation

Users and operators have no way to know messages are silently lost; the API returns 200 with data that looks correct.

No security exploit — data loss only.

```python
    bot_id, convo_id = seed_bot["bot_id"], seed_conversation["conversation_id"]

    assert bot_msgs[0]["bot_id"] == bot_id
```

**Playwright (E2E):** Trigger a bot send via the API, then navigate to the conversation and assert the bot message bubble appears with bot name/avatar.

## Dev/Prod Parity

The fix uses `tbl_msgs.put_item` which is the same DynamoDB table used by all other message types. No parity risk. The `T.chat_bots` counter update already works in both environments.

## Effort

M — requires writing a shared internal message creation helper (to avoid circular imports between `chat_bot.py` and `messaging.py`) plus tests. The actual write logic is ~15 lines but the import/refactor aspect adds complexity.
