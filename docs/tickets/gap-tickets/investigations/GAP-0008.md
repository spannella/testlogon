# GAP-0008 Investigation: Commission replay (no idempotency guard on put_item)

## Verdict

**Confirmed** — `app/services/referrals.py:289` (`tbl.put_item(Item=entry)`)

The `record_affiliate_commission()` function builds a commission entry whose sort key is
`COMMISSION#{ts}#{transaction_id}` where `ts = now_ts()` (Unix seconds). If the same
`transaction_id` is submitted at two different wall-clock seconds the SK differs, and DynamoDB
writes two separate commission records — crediting the referrer twice. There is no
`ConditionExpression` or dedup sentinel on this `put_item`.

Relevant code at `app/services/referrals.py:270–289`:

```python
ts = now_ts()
entry = {
    "pk": f"AFFILIATE#{referrer_id}",
    "sk": f"COMMISSION#{ts}#{transaction_id}",  # ts is a wall-clock component
    ...
    "commission_cents": commission_cents,
}
tbl.put_item(Item=entry)   # <-- no ConditionExpression
```

Cross-ref: SEC-013 (financial replay prevention), SEC-004 (billing idempotency).

Note: the `affiliate_links.record_conversion()` function in `app/services/affiliate_links.py:299`
has the same pattern (`T.affiliate_clicks.put_item(Item=conv)` with a random `conv_id` as SK, no
dedup on `order_id`) and is a separate but equivalent vulnerability.

## Root Cause

The SK was designed as a time-bucketed log key rather than a deterministic idempotency key.
Including `ts` in the SK means the same logical `transaction_id` can be stored multiple times.
No dedup sentinel table or `attribute_not_exists` guard was added.

## Exact Fix

**Option A (recommended):** Drop `ts` from the SK, keep `transaction_id` as the sole SK
discriminator, and guard with `ConditionExpression`:

```python
entry = {
    "pk": f"AFFILIATE#{referrer_id}",
    "sk": f"COMMISSION#{transaction_id}",   # deterministic — no ts
    ...
}
try:
    tbl.put_item(
        Item=entry,
        ConditionExpression="attribute_not_exists(pk) AND attribute_not_exists(sk)",
    )
except tbl.meta.client.exceptions.ConditionalCheckFailedException:
    logger.info("commission_duplicate_ignored transaction_id=%s", transaction_id)
    return None   # or return existing entry if caller needs it
```

**Option B (keep ts for audit trail):** Write a deterministic dedup sentinel first:

```python
sentinel_key = {"pk": f"AFFILIATE#{referrer_id}", "sk": f"COMMISSION_DEDUP#{transaction_id}"}
try:
    tbl.put_item(
        Item={**sentinel_key, "created_at": now_ts()},
        ConditionExpression="attribute_not_exists(pk)",
    )
except tbl.meta.client.exceptions.ConditionalCheckFailedException:
    logger.info("commission_duplicate_ignored transaction_id=%s", transaction_id)
    return None
# Only reach here if sentinel was successfully written
ts = now_ts()
entry = {"pk": ..., "sk": f"COMMISSION#{ts}#{transaction_id}", ...}
tbl.put_item(Item=entry)
```

Apply the same fix to `affiliate_links.record_conversion()`: use `order_id` as the deterministic
SK component and add `ConditionExpression="attribute_not_exists(pk)"`.

## Blast Radius / Exploit

An attacker (or buggy caller) that submits `POST /internal/referrals/commission` twice with the
same `transaction_id` and `referred_user_id` (e.g., network retry, idempotent billing hook)
creates two independent commission ledger entries if the two calls land in different wall-clock
seconds. The referrer's commission is double-counted in `list_commissions()` and in any
payout-calculation rollup that sums `commission_cents` across all SK matches. For
`affiliate_links.record_conversion()`, the same double-write also double-increments
`commission_earned_cents` on the link record via the `update_item` accumulator.

The `/internal/referrals/commission` endpoint (`app/routers/referrals.py:140`) is on
`internal_router` (no session auth required in dev), making it trivially callable from any
service that can reach the backend on `localhost:8000`.

## Regression Test

**pytest offline** (`tests/test_referrals.py`):

```python
def test_commission_not_replayed(ddb, attribution):
    # Act: call record_affiliate_commission twice with same transaction_id
    result1 = record_affiliate_commission(
        referred_user_id="bob", transaction_id="txn_abc", source_type="purchase",
        gross_amount_cents=1000
    )
    result2 = record_affiliate_commission(
        referred_user_id="bob", transaction_id="txn_abc", source_type="purchase",
        gross_amount_cents=1000
    )
    # Assert: second call returns None (duplicate suppressed)
    assert result1 is not None
    assert result2 is None
    # Assert: only one commission entry exists in DDB
    items = ddb.query(pk="AFFILIATE#alice").items
    commission_items = [i for i in items if i["sk"].startswith("COMMISSION#")]
    assert len(commission_items) == 1
```

Fails before fix (two entries written), passes after (second write blocked by
`ConditionalCheckFailedException`).

## Dev/Prod Parity (SECOPS-007)

The `referrals` DynamoDB table is used identically in dev (DynamoDB Local) and production.
`put_item` with `ConditionExpression` is a standard DDB feature available in both.
No AWS-specific behaviour change.

## Effort

**S** — One-line change to `put_item` in `record_affiliate_commission()` plus a try/except
handler. Same for `record_conversion()`. No schema changes needed for Option A.
