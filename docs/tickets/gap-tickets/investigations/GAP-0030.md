# GAP-0030 Investigation: No break-glass secret or KMS gate on CLI mutations

## Verdict

**Partially confirmed** — the ticket claim that "only a string-equality requires_root check" is
the sole gate is accurate, but the actual controls are somewhat stronger than the ticket implies.
The gap remains real: there is no `ROOTCTL_BREAK_GLASS_SECRET` env-var check or KMS verification
step anywhere in the code.

### What the code actually does

`_validate_preflight` (`app/cli/rootctl.py:1980–2034`) enforces:
- `reason` must be non-empty.
- `requires_ticket=True` commands also require `--ticket`.
- `requires_confirm=True` commands require `--confirm` matching `target_user_sub`.
- `actor_sub` must be non-empty.
- `requires_root=True` commands check `actor_sub == root_sub` (string equality against
  `ROOT_USER_SUB` env var) — this is the only authentication step.
- Root role cannot be assigned; root identity cannot be mutated via user/admin paths.

### The gap

The "authentication" for `requires_root` commands is `actor_sub == root_sub`, which is a
**string equality check on a caller-supplied argument** — `actor_sub` comes from `--actor-sub`
CLI flag (`argparse`, line 2045).  There is no secret, password, OTP, KMS decryption, or any
second factor.  Anyone who:

1. Has DynamoDB/AWS credentials that allow direct table writes, AND
2. Knows (or guesses) the `ROOT_USER_SUB` env var value,

can pass `--actor-sub <root_sub>` and execute any mutation including password reset, MFA wipe,
and mass session revocation.

`ROOT_USER_SUB` is typically a human-readable email address (`root.admin@testdev.local` in dev),
making it guessable from audit logs or error messages.

No `ROOTCTL_BREAK_GLASS_SECRET` or KMS-based gate exists anywhere in `app/cli/rootctl.py` or
the broader `app/` codebase.

## Root Cause

The CLI was designed with the assumption that AWS IAM controls access to DynamoDB (so only
authorised operators can run the tool at all), and that requiring `--actor-sub` matching a config
value provides a light "who is acting" record for audit.  The design implicitly relies on
infrastructure-layer access control rather than application-layer proof-of-identity.  No
additional secret was specified in the original ROOTCTL-001 ticket implementation.

## Exact Fix

Add a `_require_break_glass_auth()` function and call it from `_validate_preflight` for all
mutating commands:

```python
# app/cli/rootctl.py — add after imports

import hmac

_BREAK_GLASS_ENV = "ROOTCTL_BREAK_GLASS_SECRET"

def _require_break_glass_auth() -> None:
    """Verify ROOTCTL_BREAK_GLASS_SECRET before any write."""
    expected = os.environ.get(_BREAK_GLASS_ENV, "").strip()
    if not expected:
        raise CliPolicyError(
            f"{_BREAK_GLASS_ENV} is not configured; CLI mutations are disabled",
            details={"code": "break_glass_unconfigured"},
        )
    provided = os.environ.get("ROOTCTL_BREAK_GLASS_TOKEN", "").strip()
    if not provided:
        # Fall back to interactive prompt
        try:
            provided = getpass.getpass("Break-glass secret: ").strip()
        except (EOFError, KeyboardInterrupt):
            provided = ""
    if not hmac.compare_digest(provided.encode(), expected.encode()):
        raise CliPolicyError(
            "break-glass authentication failed",
            details={"code": "break_glass_auth_failed"},
        )
```

In `_validate_preflight`, call this before the `actor_sub` check:

```python
    if bool(getattr(args, "mutating", False)):
        _require_break_glass_auth()   # ← add this line
        ...  # existing reason / ticket / confirm / actor_sub checks
```

For higher assurance, `ROOTCTL_BREAK_GLASS_SECRET` should be a KMS-encrypted value resolved at
invocation time using `aws kms decrypt`, but the env-var approach is an acceptable first step.

## Blast Radius / Exploit

Any operator with DynamoDB read/write credentials (e.g., misconfigured IAM role, compromised CI
key, or insider) can run arbitrary rootctl mutations without any additional credential:

- Reset the root user's password and take over the platform root account.
- Wipe all MFA devices for the root user.
- Mass-revoke all user sessions (denial of service).
- Grant or revoke admin roles for arbitrary users.

The risk is proportional to how tightly DynamoDB access is controlled.  In environments where
DynamoDB is accessible from multiple services or EC2 instances (common in dev and staging), this
is a meaningful insider-threat vector.

```python
# 1. Ensure ROOTCTL_BREAK_GLASS_SECRET is set to "correct_secret".

# 3. Run with ROOTCTL_BREAK_GLASS_TOKEN="wrong" → assert CliPolicyError raised.
# 4. Run with ROOTCTL_BREAK_GLASS_TOKEN="correct_secret" → assert command proceeds past the gate.
# Fails before fix: no CliPolicyError raised in cases 2 and 3.
# Passes after fix: gate rejects bad/missing tokens.
```

## Dev/Prod Parity

In dev, set `ROOTCTL_BREAK_GLASS_SECRET=dev-break-glass` in `.env.local`.  The fix must not
break `just e2e` or unit tests; guard the check behind `bool(getattr(args, "mutating", False))`
so read-only commands are unaffected.

Per SECOPS-007: the break-glass secret is a new credential; it must be generated by
`setup_ubuntu.sh` for local dev and stored in the secrets manager for production.
