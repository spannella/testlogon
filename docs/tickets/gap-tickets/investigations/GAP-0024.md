# GAP-0024 Investigation: `ByCase` GSI fallback performs full table scan

## Verdict

**Confirmed** — `/home/ubuntu/testlogon/app/services/kyc_id_scanner.py:615-627`

The `list_scans_for_case()` method has an `except Exception` fallback that calls
`self._table.scan()` unconditionally, returning all scans from every user in the
`kyc_id_scans` table:

```python
def list_scans_for_case(self, case_id: str) -> list[dict[str, Any]]:
    try:
        resp = self._table.query(
            IndexName="ByCase",
            KeyConditionExpression=Key("case_id").eq(case_id),
            ScanIndexForward=False,
        )
        return list(resp.get("Items", []))
    except Exception:
        resp = self._table.scan()               # <-- full table scan, no filter
        items = [i for i in resp.get("Items", []) if i.get("case_id") == case_id]
        items.sort(key=lambda i: _coerce_int(i.get("created_at")), reverse=True)
        return items
```

When the `ByCase` GSI query fails for any reason (GSI not yet backfilled, throttle,
transient error), `self._table.scan()` fetches every item in the `kyc_id_scans` table.
Although the result is then filtered by `case_id`, the full dataset is loaded into
memory on the backend, and any caller that receives the raw boto3 `Items` list (or any
logging/auditing path that captures the `resp` object) can see all users' ID scan data.

Note: the `scan()` call is also vulnerable to DynamoDB's 1MB page limit — it would
silently miss scans beyond the first page without a `LastEvaluatedKey` loop. The
returned list after filtering would therefore be *incomplete* as well as a privacy
hazard.

## Root Cause

Defensive coding pattern intended to tolerate a missing/unprovisioned GSI in
development. The `except Exception` catch-all was too broad and the fallback strategy
(full table scan + in-memory filter) exposes the entire table's contents during an
error condition. The `# pragma: no cover - defensive` comment confirms this was
considered a low-probability path and was not reviewed for security implications.

## Exact Fix

Replace the `except` block with a safe failure:

```python
def list_scans_for_case(self, case_id: str) -> list[dict[str, Any]]:
    try:
        resp = self._table.query(
            IndexName="ByCase",
            KeyConditionExpression=Key("case_id").eq(case_id),
            ScanIndexForward=False,
        )
        return list(resp.get("Items", []))
    except Exception:
        logger.exception(
            "kyc_id_scanner.list_scans_for_case: ByCase GSI query failed for case_id=%s",
            case_id,
        )
        return []
```

This returns an empty list on GSI failure (safe fail) instead of leaking all table data.
The caller can surface this as a transient error to the admin UI.

## Blast Radius / Exploit

- Any KYC reviewer or API caller who triggers `list_scans_for_case()` while the ByCase
  GSI is unavailable (e.g., during a table restore, index rebuild, or throttling event)
  receives ALL users' ID scan records in the application's memory.
- If the result is serialised and returned via the API (e.g., `GET /kyc/cases/{id}/scans`),
  all users' scan metadata (document types, status, timestamps, scan IDs, case IDs) is
  returned to the caller.
- Even if the API layer filters to only return the requested `case_id`, the in-process
  data exposure may be captured by logging, APM tools, or memory dumps.
- An attacker who can reliably trigger GSI query failures (e.g., by crafting requests
  that temporarily exhaust GSI read capacity) could use this as a data exfiltration
  vector.

**pytest (offline, moto)**:
```python
# tests/test_kyc_id_scanner_bycase_fallback.py
from unittest.mock import patch, MagicMock
from app.services.kyc_id_scanner import KycIdScannerStore

def test_list_scans_for_case_returns_empty_on_gsi_failure():
    store = KycIdScannerStore()
    # Mock the table so query raises, and scan would return sensitive data
    mock_table = MagicMock()
    mock_table.query.side_effect = Exception("GSI unavailable")
    mock_table.scan.return_value = {"Items": [
        {"scan_id": "s1", "case_id": "other_case", "user_sub": "victim"},
        {"scan_id": "s2", "case_id": "target_case", "user_sub": "innocent"},
    ]}
    store._table = mock_table

    result = store.list_scans_for_case("target_case")

    # BEFORE fix: returns [{"scan_id": "s2", ...}] (leaks data)
    # AFTER fix: returns [] (safe fail)
    assert result == [], f"Expected [] but got {result}"
    # Ensure scan was NOT called
    mock_table.scan.assert_not_called()
```

## Dev/Prod Parity

In dev mode (DynamoDB Local), GSI failures are rare but possible during local-ddb-init
races. In production (AWS DynamoDB), GSI throttling is more realistic. The fix is
behaviour-identical in both environments. No SECOPS-007 concerns.
