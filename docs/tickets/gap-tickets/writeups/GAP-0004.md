# GAP-0004: Revenue-Share PUT Endpoint Allows Any Creator to Self-Set Share to 100% — Remediation Write-up

> Source ticket: ADS-010 · Severity: CRIT · Effort: S · Status: Open

## 1. Summary & Classification

**Bug statement.** `PUT /ui/content-ad-controls/revenue-share` at `app/routers/content_ad_controls.py:116` allows any authenticated creator to set their own `revenue_share_bps` to any value in `[0, 10000]`, including `10000` (100%). Setting `revenue_share_bps = 10000` means the creator receives the full ad revenue generated on their content; the platform receives 0%. The endpoint uses `require_ui_session` (any registered user) and the `RevenueShareIn` Pydantic model at `app/models.py:11674` validates only that the value is in `[0, 10000]` — there is no platform-enforced ceiling below 10000.

**Verdict (from investigation):** Partially confirmed. The ticket's framing of an IDOR risk (one user modifying another user's share) is incorrect: the endpoint always writes `ctx["user_sub"]` — the calling user's own record — so cross-account modification is not possible. The real vulnerability is that any creator can self-configure a 100% share, bypassing the platform's revenue model. The investigation classifies this as revenue leakage rather than IDOR.

**Severity and area.** Critical / Advertising & Monetisation / Revenue Policy. A single creator setting `revenue_share_bps = 10000` eliminates the platform's margin on all ad impressions and clicks on that creator's content. The impact scales directly with the creator's audience size.

**Related tickets.** ADS-010 (creator ad controls feature), GAP-0003 (charge endpoint access control — same domain), SECOPS-007 (dev/prod parity requirement). The GAP ticket's original proposed fix — "gate PUT on require_admin_or_root; add creator_sub to request body" — is noted as overly restrictive in the investigation; the correct fix is a ceiling, not full admin gating.

## 2. Current-State Investigation (root cause)

### The endpoint: `content_ad_controls.py:116–120`

```python
# app/routers/content_ad_controls.py:116–120
@content_ad_controls_router.put("/revenue-share")
def set_revenue_share_endpoint(body: RevenueShareIn, ctx=Depends(require_ui_session)):
    from app.services.content_ad_controls import set_creator_revenue_share_bps
    return set_creator_revenue_share_bps(ctx["user_sub"], body.revenue_share_bps)
```

The handler always uses `ctx["user_sub"]` as the target, so it correctly scopes writes to the calling user. The problem is `body.revenue_share_bps` — it is validated by Pydantic to be in `[0, 10000]` and passed directly to the service with no further policy constraint.

### The Pydantic model: `models.py:11674–11677`

```python
# app/models.py:11674–11677
class RevenueShareIn(BaseModel):
    """Negotiated revenue share in basis points (0-10000)."""
    revenue_share_bps: int = Field(ge=0, le=10000)
```

The model comment says "Negotiated revenue share" — implying this is admin-set. The full `[0, 10000]` range makes sense for an admin path but not a creator self-service path where the platform must retain a minimum margin.

### The service: `content_ad_controls.py:85–98`

```python
# app/services/content_ad_controls.py:85–98
def set_creator_revenue_share_bps(creator_sub: str, revenue_share_bps: int) -> Dict[str, Any]:
    """Set the creator's negotiated revenue share (basis points).

    Per the ticket, the revenue share is an admin-controlled / negotiated rate and
    is therefore NOT exposed on the creator-facing PATCH settings endpoint; it is
    set via a dedicated admin/owner path. Clamped to [0, 10000].
    """
    bps = max(0, min(10000, int(revenue_share_bps)))
    T.billing.update_item(
        Key={"pk": f"USER#{creator_sub}", "sk": "AD_SETTINGS"},
        UpdateExpression="SET revenue_share_bps = :b, updated_at = :ts",
        ExpressionAttributeValues={":b": bps, ":ts": now_ts()},
    )
    return {"ok": True, "revenue_share_bps": bps}
```

The service docstring says "admin-controlled / negotiated rate" yet the router exposes it to any session-authenticated user via `require_ui_session`. The clamp `min(10000, ...)` is the only guard in the service — it provides no protection against a creator setting `revenue_share_bps = 10000`.

### The default and expected ceiling

`app/models.py:11689` reveals that the `AdRevenueBreakdownOut` response model uses `revenue_share_bps: int = 7000` as its default, suggesting the intended platform standard is 70% creator / 30% platform. The constant `7000` is implied but never enforced as a ceiling for the self-service path.

### Dev vs prod behaviour

The vulnerability is purely logic-based and behaves identically in dev and production. There is no environment-specific path. Any authenticated creator in production can exploit this in a single HTTP request.

## 3. Impact / Exploit / Blast Radius

### Exploit walkthrough

1. Creator logs in with a normal account.
2. Sends:

```http
PUT /ui/content-ad-controls/revenue-share HTTP/1.1
Cookie: ui_session=...; ui_access_token=...
x-csrf-token: <csrf>
Content-Type: application/json

{"revenue_share_bps": 10000}
```

3. `set_creator_revenue_share_bps` stores `revenue_share_bps = 10000` in `T.billing` under `pk=USER#{creator_sub}, sk=AD_SETTINGS`.
4. From this point forward, every call to `_split_revenue()` in `ad_billing.py:141` for ad events on this creator's content credits the full charge to the creator and writes a `0` platform share to the ledger.
5. The platform earns $0 from all future ad activity on this creator's content until an admin manually resets the value.

### Financial blast radius

- A single creator with 1M monthly impressions generating a CPM of $5 represents $5,000/month in platform revenue. Setting `revenue_share_bps = 10000` eliminates the platform's ~$1,500/month margin (30%) for that creator's content indefinitely.
- With a sufficiently large creator or coordinated group of creators, the aggregate revenue loss is unlimited.
- The ledger still records charges against advertisers; the money is simply routed to creators instead of the platform. There is no advertiser-side impact, but the financial statements diverge from the contractual revenue split.

### Auditability

Because the `T.billing` table stores the current `revenue_share_bps` but does not log who changed it or when (beyond `updated_at`), it is difficult to detect how long a creator has been operating with an inflated share. The `updated_at` timestamp can be used for a partial audit, but historical ledger entries already written with the inflated split cannot easily be corrected.

## 4. Fix Design (code-level)

### Introduce a platform ceiling constant in `content_ad_controls.py`

The fix has two components: a constant in the service layer and an updated Pydantic model for the self-service path.

**Service layer (`app/services/content_ad_controls.py:85–98`):**

```python
# app/services/content_ad_controls.py — add constant and update clamp

MAX_CREATOR_REVENUE_SHARE_BPS = 7000  # 70% max creator share; 30% platform floor

def set_creator_revenue_share_bps(creator_sub: str, revenue_share_bps: int) -> Dict[str, Any]:
    """Set the creator's revenue share (basis points).

    Creator self-service: clamped to [0, MAX_CREATOR_REVENUE_SHARE_BPS].
    Admin-controlled values above this ceiling must use a separate admin endpoint
    that bypasses this function (or passes a trusted override flag).
    """
    bps = max(0, min(MAX_CREATOR_REVENUE_SHARE_BPS, int(revenue_share_bps)))
    T.billing.update_item(
        Key={"pk": f"USER#{creator_sub}", "sk": "AD_SETTINGS"},
        UpdateExpression="SET revenue_share_bps = :b, updated_at = :ts",
        ExpressionAttributeValues={":b": bps, ":ts": now_ts()},
    )
    return {"ok": True, "revenue_share_bps": bps}
```

**Pydantic model (`app/models.py:11674–11677`):**

The `RevenueShareIn` model is used by the self-service endpoint. Its upper bound should reflect the creator ceiling. If the admin path requires a wider range, create a separate `AdminRevenueShareIn` model with `le=10000`:

```python
# app/models.py:11674 — update the self-service model
class RevenueShareIn(BaseModel):
    """Creator self-service revenue share in basis points (0–7000 max)."""
    revenue_share_bps: int = Field(ge=0, le=7000)


# app/models.py — add admin-only model
class AdminRevenueShareIn(BaseModel):
    """Admin-controlled revenue share in basis points (0–10000)."""
    creator_sub: str
    revenue_share_bps: int = Field(ge=0, le=10000)
```

**Optional: separate admin endpoint (`content_ad_controls.py`):**

If admins need to grant shares above 7000 bps (e.g., a premium partner with a 90% deal), add an admin endpoint:

```python
# app/routers/content_ad_controls.py — add admin endpoint
from app.auth.policy import require_admin_or_root

@content_ad_controls_router.put("/admin/revenue-share")
def admin_set_revenue_share_endpoint(
    body: AdminRevenueShareIn,
    user: AuthenticatedUser = Depends(require_admin_or_root),
):
    from app.services.content_ad_controls import admin_set_creator_revenue_share_bps
    return admin_set_creator_revenue_share_bps(body.creator_sub, body.revenue_share_bps)
```

With a corresponding service function that uses the full `[0, 10000]` clamp (the existing `min(10000, ...)` logic).

### Dev/Prod parity (SECOPS-007)

The fix is pure business logic in `content_ad_controls.py` and `models.py`. No AWS-specific code paths are involved. `T.billing` is DynamoDB Local in dev and AWS DynamoDB in production; the `update_item` call is identical in both. No parity gap is introduced.

The new Pydantic validation (`le=7000`) is enforced at request parsing time before any DynamoDB interaction, so it behaves identically in dev and production.

### Backward compatibility and migration

**Existing records.** Any creator who previously set `revenue_share_bps > 7000` will retain that value in DynamoDB until an admin resets it. The fix does not retroactively correct stored values; a one-time data migration script should scan `T.billing` for `AD_SETTINGS` records with `revenue_share_bps > 7000` and reset them to `7000` (or flag them for admin review).

**API contract.** The PUT endpoint currently accepts `[0, 10000]`. After the fix, it accepts `[0, 7000]`. Any client that currently sends values in `(7000, 10000]` will receive a `422 Unprocessable Entity` from Pydantic. Given that `revenue_share_bps = 10000` is an exploit, not a legitimate use case, this is an intentional breaking change.

### Alternatives considered

- **Gate the entire PUT endpoint on `require_admin_or_root`** (the GAP ticket's original proposal): Would break the self-service creator flow entirely. Creator should be able to set their own share within a policy ceiling; requiring admin for every adjustment is operationally expensive. Rejected.
- **Store `MAX_CREATOR_REVENUE_SHARE_BPS` in a DynamoDB settings record** to allow runtime configuration: Adds complexity and a read on every share update. Rejected for this fix; a follow-up feature ticket is appropriate.
- **Validate in the router only** (not the service): Service-level validation is more robust because the service can be called from other paths (e.g., admin endpoints, data migrations). The Pydantic model bound serves as the first layer; the `min()` clamp in the service is the safety net.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline — `tests/test_revenue_share_cap.py`)

```python
import pytest
from unittest.mock import patch, MagicMock
from app.services.content_ad_controls import (
    set_creator_revenue_share_bps,

# --- Fails BEFORE fix ---
def test_creator_can_set_share_to_10000_before_fix():
    """Before fix: no ceiling, value is stored as-is up to 10000."""

    """After fix: value above MAX_CREATOR_REVENUE_SHARE_BPS is clamped to ceiling."""

        result = set_creator_revenue_share_bps("creator_1", 10000)

    assert result["revenue_share_bps"] <= 7000


def test_creator_can_set_share_within_ceiling():

    """Edge case: negative values are clamped to 0."""

def test_revenue_share_in_model_rejects_above_7000():
    """After fix: RevenueShareIn Pydantic model rejects values above 7000."""
    from pydantic import ValidationError
    from app.models import RevenueShareIn
    with pytest.raises(ValidationError):
        RevenueShareIn(revenue_share_bps=10000)


def test_revenue_share_in_model_accepts_at_ceiling():
    """After fix: RevenueShareIn model accepts the exact ceiling value."""
    from app.models import RevenueShareIn
    obj = RevenueShareIn(revenue_share_bps=7000)
    assert obj.revenue_share_bps == 7000
```

**Fails-before / passes-after contract:**
- `test_creator_can_set_share_to_10000_before_fix` passes before the fix (documents the broken state) and fails after (the value is clamped to 7000, not 10000).
- `test_creator_cannot_exceed_platform_ceiling` fails before the fix (`revenue_share_bps == 10000`, not `== 7000`) and passes after.
- `test_revenue_share_in_model_rejects_above_7000` fails before the fix (Pydantic allows up to `le=10000`) and passes after (`le=7000`).

### Data migration script (one-time, post-deploy)

```python
# scripts/migrate_revenue_share_cap.py
# Run once after deploying the fix to correct existing over-cap records.
import boto3
from boto3.dynamodb.conditions import Attr
from app.core.settings import S
from app.core.time import now_ts

MAX = 7000
ddb = boto3.resource("dynamodb", endpoint_url=S.ddb_endpoint_url)
table = ddb.Table(S.billing_table_name)

last_key = None
fixed = 0
while True:
    kwargs = {"FilterExpression": Attr("sk").eq("AD_SETTINGS") & Attr("revenue_share_bps").gt(MAX)}
    if last_key:
        kwargs["ExclusiveStartKey"] = last_key
    resp = table.scan(**kwargs)
    for item in resp.get("Items", []):
        table.update_item(
            Key={"pk": item["pk"], "sk": "AD_SETTINGS"},
            UpdateExpression="SET revenue_share_bps = :cap, updated_at = :ts",
            ExpressionAttributeValues={":cap": MAX, ":ts": now_ts()},
        )
        fixed += 1
    last_key = resp.get("LastEvaluatedKey")
    if not last_key:
        break
print(f"Fixed {fixed} records.")
```

### Manual QA steps

1. Log in as a creator. Send `PUT /ui/content-ad-controls/revenue-share` with `{"revenue_share_bps": 10000}`. Confirm response body contains `"revenue_share_bps": 7000` (clamped), not `10000`.
2. Confirm Pydantic validation: send `{"revenue_share_bps": 10001}`. Confirm `422 Unprocessable Entity`.
3. Log in as admin. Send `PUT /ui/admin/ads/revenue-share` (admin endpoint) with `{"creator_sub": "...", "revenue_share_bps": 9000}`. Confirm `9000` is stored (admin path has wider range).
4. Run the migration script. Confirm all `revenue_share_bps > 7000` records are updated to `7000`.

### Observability

Log a structured warning whenever a creator's submitted `revenue_share_bps` is clamped: `"revenue_share_clamped": {"submitted": X, "stored": Y, "user_sub": ...}`. This creates an audit trail of attempted over-cap configurations. Alert if any `revenue_share_bps > MAX_CREATOR_REVENUE_SHARE_BPS` value appears in the billing table (should be zero after migration).

### Rollout & risks

- **Risk:** Existing creators with `revenue_share_bps > 7000` (set via the current unguarded endpoint) continue to receive over-cap payouts until the data migration runs. Run the migration script immediately after deploying the code change.
- **Risk:** The ceiling of 7000 bps (70%) is a product decision. If the business has agreed to a different standard split (e.g., 80/20), the `MAX_CREATOR_REVENUE_SHARE_BPS` constant must be set accordingly before deploy.
- **Rollback:** Revert `MAX_CREATOR_REVENUE_SHARE_BPS` to `10000` in the service and `le=10000` in the Pydantic model. No DynamoDB changes to roll back (existing records retain their stored values).
- **Effort:** S — one constant, one `min()` change in service, one Pydantic bound update, migration script, and tests.
