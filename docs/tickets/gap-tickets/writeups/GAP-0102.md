# GAP-0102: SEC-022 — GitHub Token Must Not Be Stored in DDB Config — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code; `file:line` citations are live.

## 1. Summary & Classification

**Severity**: HIGH
**Source ticket**: AGENT-015
**Owning area**: Compliance & Security Agent / Agent PR Integration
**Status**: Open (no fix deployed as of this write-up)

The ticket spec for AGENT-015 (§7) requires the GitHub review service account token to be stored in AWS Secrets Manager and referenced only by name in any config record, never stored as a raw value. The gap identifies that if a future config extension adds a `github_token` field to the per-user security config stored in DynamoDB, that value would be returned in plaintext via `GET /ui/agents/compliance/config` and persisted openly in the DDB `agent_types` table. The fix is to introduce an indirection pattern: store `github_token_secret_name` (an ARN or Secrets Manager name) and resolve the actual token via KMS/Secrets Manager at execution time; expose only `has_github_token: bool` in GET responses.

**Claim accuracy**: The ticket states the risk is purely prospective — "if future config extension adds plaintext github_token". Code inspection confirms this is accurate: `_DEFAULT_SECURITY_CONFIG` and `_CONFIG_FIELDS` (lines 113–139) do not currently include a `github_token` field. However, `app/core/settings.py:910` shows that `S.github_token` already exists as a plaintext env var read directly into the Settings singleton. The token is already partially mis-handled at the infrastructure level, even though it is not yet surfaced through the DDB config path. The ticket claim is **confirmed with a corrected scope**: the token pattern needs to be fixed in both the DDB config path (future extension) and the existing `S.github_token` env-var path.

**Related tickets**: GAP-0025 (webhook secret stored plaintext in DDB), GAP-0101 (repo_url not validated before token use), GAP-0030 (no break-glass KMS gate on CLI mutations).

## 2. Current-State Investigation (root cause)

### 2.1 `S.github_token` at `app/core/settings.py:910`

```python
github_token: str = os.environ.get("GITHUB_TOKEN", "")
github_webhook_secret: str = os.environ.get("GITHUB_WEBHOOK_SECRET", "")
```

The GitHub token is read from an environment variable and stored as a plain Python string attribute on the `Settings` singleton. Any code that imports `S` can read the token without audit trail or access control. In development the variable is empty, but a misconfigured CI secret or accidental log line would expose it.

### 2.2 `_create_pr_via_api` at `app/services/agent_pr_integration.py:370`

    raise NotImplementedError("Live GitHub API integration not enabled.")

This is the only current consumer of `S.github_token`. In the live path (when `NotImplementedError` is removed), the token would be sent as a bearer header to the GitHub API. There is no scope restriction, rotation helper, or audit event around the token read.

### 2.3 `SecurityAgentConfigOut` at `app/models.py:8296`

```python
class SecurityAgentConfigOut(BaseModel):
    scan_on_pr: bool = True
    ...
    # NO github_token field — not yet present
    updated_at: Optional[int] = None
```

The output model does not yet contain a `github_token` field. This is the safe state. The risk is that a developer adding GitHub-per-user config will copy the pattern from a simpler field and add `github_token: Optional[str] = None`, accidentally leaking it through the GET endpoint.

### 2.4 `UpdateSecurityConfigIn` at `app/models.py` (near SecurityAgentConfigOut)

Similarly no `github_token` field. The gap is latent but the enforcement mechanism (masking pattern) needs to be built now before the first extension lands.

### 2.5 DynamoDB `agent_types` table

The `update_security_config` function at `app/services/agent_compliance.py:400` does:

```python
existing = get_security_config(agent_type_id=...) or dict(_DEFAULT_SECURITY_CONFIG)
normalized = dict(existing)
for key in _CONFIG_FIELDS:
    if key in config:
        normalized[key] = config[key]
T.agent_types.put_item(Item={"pk": ..., "sk": "SECURITY_CONFIG", "security_config": normalized, ...})
```

Any field present in `_CONFIG_FIELDS` will be stored verbatim in DynamoDB. If `github_token` is added to `_CONFIG_FIELDS`, it will be stored in plaintext in DDB — readable by anyone with DynamoDB read IAM permission and visible in any DDB export.

### 2.6 Dev vs prod parity

In dev, `S.dev_mode = True` causes `_create_pr_via_api` to skip the real token usage. In prod, the token is expected to be a live GitHub Personal Access Token or App token with `repo` scope. The security gap is production-only, but the fix must be applied before the execute gate is opened.

## 3. Impact / Exploit / Blast Radius

### 3.1 Credential exfiltration via GET endpoint

If `github_token` is added to `SecurityAgentConfigOut` (a common developer mistake):

1. Any authenticated user calls `GET /ui/agents/compliance/config`.
2. The response includes `"github_token": "ghp_xxxxxxxx"`.
3. With the token, the attacker has access to all repositories the service account can read/write — potentially including private source code, release pipelines, and secrets committed to `.env` files.

### 3.2 DynamoDB data exfiltration

If a DDB backup or snapshot is exfiltrated (S3 export, insider threat, misconfigured S3 bucket ACL), all `agent_types` rows are exposed. Plaintext `github_token` in those rows gives the attacker permanent repo access until the token is rotated.

### 3.3 Log exposure

If `logger.info("Updating config: %s", config)` or similar is ever added, the token is written to CloudWatch Logs, which may be retained for 90+ days and accessible to a broader set of IAM principals than the Secrets Manager secret.

### 3.4 Compliance

OWASP A02:2021 (Cryptographic Failures) and PCI-DSS §8.3.2 (protect service account credentials) are violated if the token is stored or returned in plaintext. The platform's own `compliance_frameworks` default includes `owasp_top_10`.

## 4. Fix Design (code-level)

### 4.1 Secrets Manager indirection pattern

The correct pattern, consistent with GAP-0025 (webhook secrets), is:

- **Store**: `github_token_secret_name` (e.g., `"arn:aws:secretsmanager:us-east-1:123:secret:github-token"`) — an ARN or logical name, never the raw token.
- **Expose**: `has_github_token: bool` — derived at read time by checking if `github_token_secret_name` is non-empty.
- **Resolve**: call `boto3.client("secretsmanager").get_secret_value(SecretId=...)` at execution time inside `_create_pr_via_api`.
- **Dev parity**: in dev mode, resolve from `S.github_token` (env var) so local testing works without Secrets Manager.

### 4.2 `app/services/agent_compliance.py` — add `github_token_secret_name` to config

```python
_DEFAULT_SECURITY_CONFIG: Dict[str, Any] = {
    ...
    "github_token_secret_name": "",  # ADD — empty = not configured
    ...
}
```

**Critically**: `github_token_secret_name` must be added to `_CONFIG_FIELDS` but `github_token` must NEVER be added.

### 4.3 `app/models.py` — expose only `has_github_token`

```python
class SecurityAgentConfigOut(BaseModel):
    ...
    github_token_secret_name: Optional[str] = None   # ADD — write-only reference
    has_github_token: bool = False                    # ADD — read-only derived field
    ...

class UpdateSecurityConfigIn(BaseModel):
    ...
    github_token_secret_name: Optional[str] = None   # ADD — allow setting the reference
```

The `has_github_token` field must be populated at the service layer before constructing the response:

```python
# In agent_compliance router, GET /config:
config = svc.get_effective_config(user_id=user_id)
config["has_github_token"] = bool(config.get("github_token_secret_name"))
# NEVER include the actual token value in config
return SecurityAgentConfigOut(**config)
```

### 4.4 Token resolution in `_create_pr_via_api`

In `app/services/agent_pr_integration.py:363`, replace the direct env-var read with:

```python
import boto3

def _resolve_github_token(user_id: str) -> str:
    """Resolve GitHub token: Secrets Manager in prod, env var in dev."""
    if S.dev_mode:
        return S.github_token  # env var, acceptable in dev
    config = get_effective_config(user_id=user_id)
    secret_name = config.get("github_token_secret_name", "")
    if not secret_name:
        # Fall back to platform-level env var (also should be in Secrets Manager in prod)
        secret_name = os.environ.get("GITHUB_TOKEN_SECRET_NAME", "")
    if not secret_name:
        return ""
    sm = boto3.client("secretsmanager")
    resp = sm.get_secret_value(SecretId=secret_name)
    return resp.get("SecretString", "")

def _create_pr_via_api(
    *, repo_url: str, branch: str, title: str, description: str, user_id: str,
) -> Dict[str, Any]:
    token = _resolve_github_token(user_id)
    if S.dev_mode or not token:
        ...  # mock
    # Real implementation: POST to GitHub API with token
```

### 4.5 Settings cleanup

Remove `github_token: str` from `app/core/settings.py` in production paths. In dev it can remain as a convenience, gated by `if S.dev_mode`. Add:

```python
github_token_secret_name: str = os.environ.get("GITHUB_TOKEN_SECRET_NAME", "")
```

This is the env-var for the Secrets Manager secret name (not the token itself), usable in prod ECS task definitions.

### 4.6 Dev/Prod parity (SECOPS-007)

| Path | Dev | Prod |
|------|-----|------|
| Token source | `S.github_token` env var (empty by default) | AWS Secrets Manager via `_resolve_github_token` |
| Config field stored | `github_token_secret_name: ""` | `github_token_secret_name: "arn:aws:..."` |
| GET config response | `has_github_token: false` | `has_github_token: true` |
| Raw token in DDB | Never | Never |
| Raw token in API response | Never | Never |

Both paths execute `_resolve_github_token`; dev simply gets an empty string from `S.github_token` (no Secrets Manager call). The validation logic is identical in both environments.

### 4.7 Alternatives considered

- **Encrypt token with KMS before storing in DDB**: more complex (requires key management, envelope encryption), and DDB is a poor secret store regardless of encryption — rejected in favour of Secrets Manager, which provides rotation, versioning, and fine-grained IAM.
- **Treat token as global platform secret only** (not per-user): simpler, but prevents multi-tenant deployments where different users have different GitHub org tokens — rejected.
- **Remove `github_token` from Settings entirely**: correct long-term, but breaks dev ergonomics; retain as dev-only fallback.

## 5. Testing, Verification & Rollout

### 5.1 Pytest regression test (fails before / passes after)

Add to `tests/test_agent_compliance.py`:

```python
def test_get_config_never_returns_raw_github_token(client, alice_session):
    """BEFORE fix: if github_token were in config it would be returned.
    AFTER fix: only has_github_token bool is returned, never the raw value."""
    resp = client.get("/ui/agents/compliance/config", headers=alice_session)
    assert resp.status_code == 200
    body = resp.json()
    # Must never contain the raw token key
    assert "github_token" not in body, "Raw github_token must not appear in GET /config"
    # Must contain only the boolean indicator
    assert "has_github_token" in body
    assert isinstance(body["has_github_token"], bool)

def test_update_config_accepts_secret_name_not_raw_token(client, alice_session):
    """PUT /config with github_token_secret_name is accepted.
    Attempting to set github_token (raw) must be rejected or ignored."""
    resp = client.put(
        "/ui/agents/compliance/config",
        json={"github_token_secret_name": "arn:aws:secretsmanager:us-east-1:123:secret:tok"},
        headers=alice_session,
    )
    assert resp.status_code == 200
    body = resp.json()
    assert body["has_github_token"] is True
    assert "github_token" not in body

def test_update_config_ignores_raw_github_token_field(client, alice_session):
    """If a client sends github_token in the body, it must be stripped."""
    resp = client.put(
        "/ui/agents/compliance/config",
        json={"github_token": "ghp_supersecret"},
        headers=alice_session,
    )
    # Either 422 (field not accepted) or 200 with field stripped
    if resp.status_code == 200:
        body = resp.json()
        assert "github_token" not in body
        assert body.get("has_github_token") is False  # wasn't stored
```
