# GAP-0188: `"tip"` and `"unlock"` Checkout Types Not in `VALID_CHECKOUT_TYPES` — Remediation Write-up

> Source ticket: FIN-002 · Severity: HIGH · Effort: M · Status: Open

## 1. Summary & Classification

**Bug statement.** `VALID_CHECKOUT_TYPES` in `app/services/promo_codes.py:25` is
`{"subscription", "vod", "shop"}`. The `"tip"` and `"unlock"` values are absent. Two
consequences follow. First, `create_promo_code` validates `applies_to` against this
set at line 109, so a creator cannot even create a promo code that targets tip or
unlock checkouts: the call returns
`"Invalid applies_to value: tip"` (400). Second, even if such a code were inserted
directly into DynamoDB, `validate_promo_code` would always return
`error_code: "checkout_type_mismatch"` when called with `checkout_type="tip"` or
`checkout_type="unlock"`, because the code's `applies_to` list could never contain
those values (it was blocked at creation time). Additionally, the `PromoValidateIn`
Pydantic model at `app/models.py:3313` uses
`Literal["subscription", "vod", "shop"]` as the type for `checkout_type`, meaning the
API endpoint rejects `checkout_type="tip"` or `checkout_type="unlock"` with a 422
validation error before `validate_promo_code` is even called. Finally, neither
`app/routers/messaging.py` (tip and unlock endpoints) nor `app/routers/newsfeed.py`
(post tip and post unlock endpoints) call `validate_promo_code` at all, so even if the
constant and model were fixed there is no hook point in the payment flows.

**Verdict: Confirmed.** The claim in the ticket is accurate on every point: the set is
`{"subscription", "vod", "shop"}` at `promo_codes.py:25`; the Literal constraint at
`models.py:3313` blocks tip/unlock at the HTTP layer; and neither messaging nor newsfeed
router contain any call to `validate_promo_code`.

**Severity and area.** HIGH / Billing & Promo (FIN-002). Promo codes for tips and
pay-per-view message/post unlocks are a defined monetisation surface. Creators cannot
configure discounts on these transactions, and any campaign planning around tip
promotions ("send a tip this week, get 20% off") is entirely blocked.

**Related tickets.** GAP-0186 and GAP-0187 should ship first (they fix the base model
and add `error_code` to the validation response); this ticket builds on top of both.
No other blocking dependency.

## 2. Current-State Investigation (root cause)

### Constant definition: `app/services/promo_codes.py:25`

```python
VALID_CHECKOUT_TYPES = {"subscription", "vod", "shop"}
```

Used in two places:
1. **`create_promo_code` (line 108–110):** iterates `applies_to` and returns an error
   for any value not in the set. A creator who passes `applies_to=["tip"]` receives
   HTTP 400.
2. **Implicitly in `validate_promo_code` (line 293–298):** if a code were somehow
   created with `applies_to=["tip"]`, the checkout_type check
   `checkout_type not in applies` would only reject codes that do not list the requested
   checkout type — it does not gate against `VALID_CHECKOUT_TYPES` at validation time.
   So adding `"tip"` to the constant is sufficient for the creation and validation
   paths.

### Model constraint: `app/models.py:3313`

```python
class PromoValidateIn(BaseModel):
    code: str
    checkout_type: Literal["subscription", "vod", "shop"]
    item_price_cents: int = 0
    creator_user_id: str
```

The `Literal` annotation is enforced by Pydantic before the router function is entered.
Any request with `checkout_type="tip"` receives a `422 Unprocessable Entity` with body:
```json
{"detail": [{"loc": ["body", "checkout_type"],
             "msg": "unexpected value; permitted: 'subscription', 'vod', 'shop'",
             "type": "value_error.const"}]}
```

### Missing endpoint hooks: `app/routers/messaging.py`

`unlock_message` (line 13592) accepts `UnlockMessageIn` (line 2534) which has only
`payment_method_id`. There is no `promo_code` field and no call to `validate_promo_code`
anywhere in the function body (lines 13592–13728). The same applies to `SendTipIn`
(line 1892): `amount_cents`, `currency`, `note`, `payment_method_id` — no `promo_code`.

The tip endpoint for messages (searching for the send-tip call path in the router)
also contains no promo hook.

### Missing endpoint hooks: `app/routers/newsfeed.py`

`UnlockPostRequest` (line 1828): `post_id`, `payment_method_id`, `idempotency_key` —
no `promo_code`. `PostTipRequest` (line 1844): `amount_cents`, `currency`,
`payment_method_id` — no `promo_code`. Neither `unlock_post` (line 5656) nor `tip_post`
(line 4589) call `validate_promo_code`.

### Dev vs prod parity

The constant and model are pure Python; they apply identically in dev mode and
production. There is no conditional branch in `create_promo_code` or
`validate_promo_code` that varies by environment.

## 3. Impact / Exploit / Blast Radius

**Creator revenue loss.** Creators cannot run discount campaigns for tip-based income
streams. "20% off your first tip this month" and similar promotional flows are
completely blocked.

**Feature gap vs specification.** The FIN-002 spec explicitly names `"tip"` and
`"unlock"` as required checkout surfaces for promo codes. The platform is shipping with
an incomplete implementation of a paid feature.

**No security or financial exploit.** There is no risk of a discount being applied
without authorisation; the risk is the opposite — valid promo codes for tips/unlocks
cannot be applied at all, so no fraudulent discount is possible. The gap is purely a
missing feature, not a security vulnerability.

**Blast radius.** Affects:
- All creators who wish to create tip or unlock promo campaigns.
- All buyers who hold a promo code for a tip or unlock surface and cannot redeem it.
- The `Checkout.tsx` component (used for shop), which would need a parallel integration
  for tip/unlock surfaces once the hook points are added.

## 4. Fix Design (code-level)

### Step 1 — Extend `VALID_CHECKOUT_TYPES` (`app/services/promo_codes.py:25`)

```python
VALID_CHECKOUT_TYPES = {"subscription", "vod", "shop", "tip", "unlock"}
```

This single-line change unblocks code creation for tip and unlock targets.

### Step 2 — Extend the `PromoValidateIn` Literal (`app/models.py:3313`)

```python
class PromoValidateIn(BaseModel):
    code: str
    checkout_type: Literal["subscription", "vod", "shop", "tip", "unlock"]
    item_price_cents: int = 0
    creator_user_id: str
```

This unblocks the `POST /ui/promo-codes/validate` endpoint from rejecting `"tip"` and
`"unlock"` at the HTTP layer.

### Step 3 — Add `promo_code` field to `UnlockMessageIn` and `SendTipIn`
(`app/routers/messaging.py:1892` and `app/routers/messaging.py:2534`)

```python
class SendTipIn(BaseModel):
    amount_cents: int = Field(ge=1, le=100_000)
    currency: str = "USD"
    note: Optional[str] = Field(default=None, max_length=500)
    payment_method_id: Optional[str] = None
    promo_code: Optional[str] = None   # ← new

class UnlockMessageIn(BaseModel):
    payment_method_id: Optional[str] = None
    promo_code: Optional[str] = None   # ← new
```

### Step 4 — Call `validate_promo_code` in `unlock_message` (messaging)

Inside `unlock_message` (line 13592), after the basic guards and before the billing
write, add:

```python
discount_cents = 0
if inp.promo_code and S.promo_codes_enabled:
    from app.services.promo_codes import validate_promo_code, redeem_promo_code
    # creator_user_id is the message sender (the content owner)
    promo_result = validate_promo_code(
        code=inp.promo_code,
        user_id=user_id,
        checkout_type="unlock",
        item_price_cents=amount_cents,
        creator_user_id=_seller_id,
    )
    if not promo_result["valid"]:
        raise HTTPException(422, {
            "error_code": promo_result.get("error_code", "invalid_promo"),
            "message": promo_result.get("message") or "Invalid promo code",
        })
    discount_cents = promo_result["discount_cents"]

amount_cents = max(0, amount_cents - discount_cents)
```

After the successful billing write (at the end of `unlock_message`), record the
redemption:

```python
if inp.promo_code and promo_result and promo_result.get("valid"):
    redeem_promo_code(
        code_id=promo_result["code_id"],
        user_id=user_id,
        original_price_cents=int(msg["lock_price_cents"]),
        final_price_cents=amount_cents,
        checkout_type="unlock",
        checkout_item_id=message_id,
    )
```

### Step 5 — Mirror Step 4 in `unlock_post` (newsfeed) and both tip endpoints

The same pattern applies to `unlock_post` (newsfeed, line 5656) and both tip endpoints
(`SendTipIn` in messaging and `PostTipRequest` in newsfeed). The `checkout_type` passed
to `validate_promo_code` is `"tip"` for tip flows and `"unlock"` for unlock flows. The
`creator_user_id` is the post author or message sender respectively.

For tip flows, the discount reduces the effective amount charged to the tipper but does
not reduce the amount credited to the creator (the platform absorbs the discount delta).
This decision should be documented in a billing ledger field (`promo_discount_cents`) on
the ledger entry, not assumed implicitly.

### Step 6 — Add `promo_code` fields to `UnlockPostRequest` and `PostTipRequest`
(`app/routers/newsfeed.py`)

```python
class UnlockPostRequest(BaseModel):
    post_id: str
    payment_method_id: Optional[str] = None
    idempotency_key: Optional[str] = ...
    promo_code: Optional[str] = None   # ← new

class PostTipRequest(BaseModel):
    amount_cents: int = Field(..., ge=1)
    currency: str = "usd"
    payment_method_id: Optional[str] = None
    promo_code: Optional[str] = None   # ← new
```

### Dev/Prod parity (SECOPS-007)

`validate_promo_code` and `redeem_promo_code` use DynamoDB exclusively with no
dev/prod branching. The `S.promo_codes_enabled` flag gates the entire feature in both
environments identically. The messaging `unlock_message` endpoint is likewise backed
by DynamoDB with no environment split. No new feature flags are required; the existing
`PROMO_CODES_ENABLED` flag (default `"1"`) continues to gate the whole promo feature.

The payment mock in dev mode (`payments.create_payment_intent` / `confirm_payment_intent`
always succeeds) means that promo discounts will be exercised on the accounting path in
dev; the reduced `amount_cents` will be passed to the mock payment processor which
simply records `succeeded`. This is the correct dev behaviour.

### Backward compatibility

All new fields on input models are `Optional` with `None` default. Existing clients
that do not send `promo_code` receive identical behaviour to today. The `VALID_CHECKOUT_TYPES`
set expansion and `Literal` expansion are additive; no existing promo codes are
invalidated.

### Rollout and risks

- **Effort:** M. The constant and model changes are trivial (two lines each). The
  hook-point additions in four endpoints (`unlock_message`, messaging tip endpoint,
  `unlock_post`, newsfeed tip endpoint) require careful integration with each
  payment flow, the PM validation pattern already present in those functions, and
  the `redeem_promo_code` write at the end of each successful transaction.
- **Risk:** Medium. Integrating promo discounts into messaging and newsfeed payment flows
  touches billing ledger writes; the reduced `amount_cents` must be correctly
  reflected in both the buyer debit entry and must be explicitly handled for the
  creator credit entry (the business rule — "platform absorbs the discount delta" vs
  "creator receives discounted amount" — must be decided and documented in the billing
  ledger `reason` field before shipping).
- **Discount type restriction.** Only `percentage` and `fixed_amount` discount types
  are meaningful for tip/unlock surfaces; `free_trial` is subscription-only and
  `buy_x_get_y` does not apply to single-item transactions. The service's existing
  `free_trial` type guard (lines 306–311) already blocks `free_trial` codes on non-
  subscription checkout types. No additional guard is required for tip/unlock.
- **Sequencing:** Ship GAP-0186 and GAP-0187 first (they add `error_code` to
  `PromoValidateOut` and fix the model, both of which this ticket depends on). The
  constant and Literal changes for this ticket are safe to merge independently as a
  preparatory step even before the endpoint hooks land, since an expanded
  `VALID_CHECKOUT_TYPES` only enables code creation — no checkout flow changes yet.
- **Rollback:** Revert the `VALID_CHECKOUT_TYPES` and `Literal` changes; any codes
  created with `"tip"` or `"unlock"` in `applies_to` while the feature was live will
  remain in DynamoDB but become unredeemable (the `applies_to` check in
  `validate_promo_code` will fail them as `checkout_type_mismatch`). A one-off
  migration script to flag these codes as inactive in DynamoDB would be needed only
  if a rollback occurs after meaningful production usage.
