# GAP-0365: Ctrl+Enter send not wired in ComposeBar — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against real code; cites `file:line` throughout.

## 1. Summary & Classification

**Bug**: The `handleKeyDown` handler in `frontend/src/pages/messages/ComposeBar.tsx` only sends a message when `Enter` is pressed without `Shift`. It does not handle `Ctrl+Enter` (Windows/Linux) or `Cmd+Enter` (macOS) as an alternative send trigger. Users who habitually press `Ctrl+Enter` to send (a common convention from email clients, Slack, and other chat platforms) find that the keystroke does nothing — their message stays in the compose area.

**Severity**: HIGH (UX regression — impedes core user flow for a significant subset of users)
**Source ticket**: UX-002
**Status**: Open
**Owning area**: Frontend / ComposeBar component
**Effort**: S
**Related tickets**: None

**Claim verification**: CONFIRMED. `handleKeyDown` at `frontend/src/pages/messages/ComposeBar.tsx:690-695` reads:

```typescript
const handleKeyDown = (e: React.KeyboardEvent) => {
  if (e.key === "Enter" && !e.shiftKey) {
    e.preventDefault();
    void handleSubmit();
  }
};
```

There is no `e.ctrlKey` or `e.metaKey` branch. The handler is attached to the `<textarea>` at line 1777: `onKeyDown={handleKeyDown}`.

**One-line impact**: Users on every OS who press `Ctrl+Enter` or `Cmd+Enter` to send a message are silently ignored, creating a broken send experience for a population of users accustomed to the near-universal "modifier+Enter = send" convention.

## 2. Current-State Investigation (root cause)

### The handler as written

```
frontend/src/pages/messages/ComposeBar.tsx:690-695
```

```typescript
const handleKeyDown = (e: React.KeyboardEvent) => {
  if (e.key === "Enter" && !e.shiftKey) {
    e.preventDefault();
    void handleSubmit();
  }
};
```

The condition `e.key === "Enter" && !e.shiftKey` fires on:
- Plain `Enter` — sends
- No other combination

It explicitly does NOT fire on:
- `Shift+Enter` — inserts a newline (intended behavior, correct)
- `Ctrl+Enter` — no-op (gap)
- `Cmd+Enter` on macOS — no-op (gap)

The handler is bound to the `<textarea>` element at `ComposeBar.tsx:1777`:

```tsx
onKeyDown={handleKeyDown}
```

There is no other keyboard event handler on the textarea or its parent that would catch `Ctrl+Enter`.

### UX convention context

The `Ctrl+Enter` / `Cmd+Enter` send shortcut is a near-universal convention:

- Slack: `Ctrl+Enter` sends when "Send with Enter" mode is off
- Gmail / Outlook: `Ctrl+Enter` sends email
- GitHub comment boxes: `Ctrl+Enter` submits
- Discord: `Ctrl+Enter` can be configured as send

Users who type long, multi-line messages using `Enter` for line breaks and then try `Ctrl+Enter` to send expect consistent behavior. Not supporting this shortcut is a regression relative to user expectations.

### Current `Shift+Enter` behavior

The existing guard `!e.shiftKey` correctly prevents `Shift+Enter` from sending — it falls through and the textarea's default behavior inserts a newline. The fix must preserve this behavior.

### Interaction with `handleSubmit`

`handleSubmit` (defined around `ComposeBar.tsx:600-688`) is already the correct function to call on send — it handles:
- Text trimming and validation
- Optional encryption payload building
- Calling `onSendText` or `onSendImage` based on pending content
- Resetting text and file state after send

The only change needed is an additional entry point into `handleSubmit` from the keyboard handler.

### `metaKey` vs `ctrlKey` consideration

On macOS, `Cmd` is `e.metaKey`; on Windows/Linux, `Ctrl` is `e.ctrlKey`. Both conventions exist simultaneously in the user base. Using `(e.ctrlKey || e.metaKey)` covers all platforms. This is the same pattern used by virtually all cross-platform web text editors (e.g., CodeMirror, Monaco, Draft.js, Slate).

## 3. Impact / Exploit / Blast Radius

### User impact

This is a pure UX gap — no security or financial consequence. However, the impact on affected users is significant:

- **Frequent-send users** who compose multi-line messages are the most affected. Multi-line composition requires `Enter` for line breaks; after finishing, the natural next step is `Ctrl+Enter` to send. These users may think the UI is broken or may resort to using the mouse to click the Send button, degrading the messaging experience.
- **Power users / keyboard-first users** who avoid the mouse are disproportionately affected.
- **Accessibility**: Users with motor impairments who rely on keyboard navigation may have configured assistive technology to trigger send with `Ctrl+Enter`.

### Blast radius

The fix affects `ComposeBar.tsx`, which is used throughout the messaging feature — DMs, group chats, and any other context where `ComposeBar` is rendered. There is no per-conversation or per-mode variant of `handleKeyDown`; the fix applies universally.

### Risk of accidental double-send

The only risk in adding `Ctrl+Enter` is if a user accidentally presses the combination and sends an unfinished message. This is identical to the risk that exists for plain `Enter` send today. No additional guard is needed.

## 4. Fix Design (code-level)

### The fix — one additional condition in `handleKeyDown`

```typescript
// frontend/src/pages/messages/ComposeBar.tsx:690-695 — AFTER FIX

const handleKeyDown = (e: React.KeyboardEvent) => {
  if (e.key === "Enter" && !e.shiftKey) {
    e.preventDefault();
    void handleSubmit();
  } else if (e.key === "Enter" && (e.ctrlKey || e.metaKey)) {
    e.preventDefault();
    void handleSubmit();
  }
};
```

This can equivalently be written more compactly to avoid duplicating `e.preventDefault(); void handleSubmit();`:

```typescript
const handleKeyDown = (e: React.KeyboardEvent) => {
  const plainEnter = e.key === "Enter" && !e.shiftKey && !e.ctrlKey && !e.metaKey;
  const modEnter   = e.key === "Enter" && (e.ctrlKey || e.metaKey);
  if (plainEnter || modEnter) {
    e.preventDefault();
    void handleSubmit();
  }
};
```

The compact form is preferred for maintainability — one call site for `handleSubmit`, one `preventDefault`, and both conditions readable side by side. The `!e.ctrlKey && !e.metaKey` addition to `plainEnter` is optional — plain `Enter` without any modifier is not affected by `ctrlKey/metaKey` being false — but making it explicit documents intent.

The ticket fix suggestion is:

```typescript
if (e.key === "Enter" && (e.ctrlKey || e.metaKey)) { e.preventDefault(); void handleSubmit(); }
```

added to `handleKeyDown` at line 694. This is equivalent; the compact two-condition form above is marginally cleaner.

### `Shift+Enter` still inserts newline

After the fix, the behavior matrix is:

| Keystroke        | Behavior          |
|------------------|-------------------|
| `Enter`          | Send              |
| `Shift+Enter`    | Insert newline    |
| `Ctrl+Enter`     | Send (new)        |
| `Cmd+Enter`      | Send (new)        |
| `Shift+Ctrl+Enter` | No action (falls through; unlikely in practice) |

### Dev/Prod parity (SECOPS-007)

This is a pure frontend change with no backend component. The fix is identical in dev (Vite dev server, port 3000) and prod (built static bundle served by the backend or CDN). There are no feature flags, mock paths, or environment branches involved. The change is fully parity-consistent.

### Backward compatibility

The change adds a new keyboard shortcut that previously did nothing. No existing behavior changes. No API changes. No DynamoDB changes.

### Accessibility enhancement (optional, recommended alongside fix)

Add a `title` attribute or `aria-label` update to the send button tooltip text mentioning the keyboard shortcuts: `"Send message (Enter or Ctrl+Enter)"`. This surfaces the shortcut to users who inspect the UI rather than discovering it by trial and error. This is a separate cosmetic change and not required for the functional fix.

## 5. Testing, Verification & Rollout

### Regression test — Playwright E2E

Add to `frontend/e2e/messaging-features.spec.ts` (or a dedicated `composebar-keyboard.spec.ts`):

```typescript
// Fails before fix (message not sent); passes after fix.

test("Ctrl+Enter sends a message", async ({ page }) => {
  await injectAuth(page, "alice");
  const dmId = await getOrCreateDm(page, "alice", "bob");
  await page.goto(`/messages/${dmId}`);

  const MSG = `ctrl-enter-test-${Date.now()}`;

  // Type a message
  await page.getByPlaceholder(/type a message/i).fill(MSG);

  // Press Ctrl+Enter — should send
  const [response] = await Promise.all([
    page.waitForResponse(r =>
      r.url().includes("/messaging/conversations/") &&
      r.url().includes("/messages") &&
      r.request().method() === "POST"
    ),
    page.getByPlaceholder(/type a message/i).press("Control+Enter"),
  ]);

  expect(response.status()).toBe(201);

  // Message should appear in the conversation view
  await expect(
    page.locator("p").filter({ hasText: MSG })
  ).toBeVisible({ timeout: 5000 });

  // Compose area should be cleared
  await expect(page.getByPlaceholder(/type a message/i)).toHaveValue("");
});


test("Cmd+Enter sends a message on macOS", async ({ page }) => {
  // Same test using Meta key (macOS Cmd)
  await injectAuth(page, "alice");
  const dmId = await getOrCreateDm(page, "alice", "bob");

  expect(response.status()).toBe(201);
  await expect(page.locator("p").filter({ hasText: MSG })).toBeVisible({ timeout: 5000 });

test("Shift+Enter still inserts a newline (not send)", async ({ page }) => {
  await injectAuth(page, "alice");
  const dmId = await getOrCreateDm(page, "alice", "bob");
  await page.goto(`/messages/${dmId}`);

  const textarea = page.getByPlaceholder(/type a message/i);
  await textarea.fill("line one");
  await textarea.press("Shift+Enter");
  await textarea.fill("line one\nline two");  // after Shift+Enter, textarea should allow this

  // No send should have occurred — textarea value still contains content
  await expect(textarea).toHaveValue(/line one/);
});
```

No backend instrumentation needed. The change is frontend-only. Post-deploy, monitor message send event counts (if tracked by analytics) for an uptick indicating users are now successfully using the shortcut.

### Rollback

Revert the two-line addition to `handleKeyDown`. No database changes; no backend changes. Frontend rollback requires rebuilding the static bundle and redeploying.

### Risk

Negligible. The change is a 2-line addition to a condition check. The existing send path (`handleSubmit`) is unchanged. No new state, no new async logic, no new API calls. The only risk is accidentally triggering `handleSubmit` when the condition was not intended — which cannot happen because `ctrlKey/metaKey + Enter` was previously a no-op.
