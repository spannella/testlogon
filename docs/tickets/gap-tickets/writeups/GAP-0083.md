# GAP-0083: Eligible Ticket Count Pagination Incomplete — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Bug statement**: `_count_eligible_tickets` in `app/services/agent_fleet.py` issues a single DynamoDB `scan` with `FilterExpression` and reads only the first page of results. Because DynamoDB applies the filter *after* reading up to 1 MB of data, a sparse table (few eligible tickets among many ineligible items) can return `Count: 0` even when eligible tickets exist — they were simply never loaded into the first page. The function returns a silently incorrect (low) count, causing the fleet capacity dashboard to show stale queue depths.

- **Severity**: HIGH
- **Source ticket**: AGENT-004
- **Status**: Open
- **Owning area**: Agent Fleet Management / Dashboard
- **Verdict**: Claim CONFIRMED. `app/services/agent_fleet.py:288-303` performs a single-page scan with no `LastEvaluatedKey` loop. The same pagination defect also exists in `_count_eligible_by_type` at line 306-318.
- **Impact**: Under-counted queue depth misleads operators into thinking the queue is empty (or low) when in fact there are eligible tickets waiting. This can delay manual intervention, cause workers to idle unnecessarily, and produce incorrect `recommended_action` guidance in fleet capacity responses.
- **Related tickets**: GAP-0081 (orphaned claims make some tickets permanently eligible-but-unclaimed, amplifying the under-count).

### What is present vs. missing

- **Present**: `FilterExpression` correctly filters by `agent_eligible = 'yes'` and absence of `agent_claimed_by`.
- **Present**: `Select="COUNT"` in `_count_eligible_tickets` (correctly avoids loading item attributes for the count variant).
- **Missing**: Pagination loop over `LastEvaluatedKey` in both functions.
- **Missing**: Accumulation of `Count` (or `Items`) across pages.

### DynamoDB pagination mechanics

DynamoDB reads items from the partition sequentially until it has consumed 1 MB of raw item data. It then applies the `FilterExpression`. If the filter is very selective — for example, 5 eligible tickets scattered among 50,000 total ticket records — the first 1 MB page may contain zero eligible tickets entirely by chance, even though eligible tickets exist further into the table. The `LastEvaluatedKey` signals that more data is available, but the current code discards it.

With `Select="COUNT"`, `resp["Count"]` is the count of items on *this page* that passed the filter; `resp["ScannedCount"]` is the raw items read. Both reset to 0 for each page. To get the total count, the caller must sum `Count` across all pages.

### Dev vs. prod

In the local dev stack, the tickets table contains a small number of rows (seeded by tests). `LastEvaluatedKey` is rarely returned because the entire table fits in a single page. The bug is invisible during development. In production with thousands of tickets, the 1 MB page limit is hit frequently, and the count is consistently wrong.

This is a classic "works in dev, broken in prod" defect: dev never saturates the page limit; prod silently truncates.

## 3. Impact / Exploit / Blast Radius

### Who is affected

- **Operators and admins** who rely on the fleet capacity dashboard to decide whether to provision more workers.
- **The automatic recommendation engine** (`fleet_capacity` at line 62-90): uses `_count_eligible_by_type` counts to generate the `recommended_action` string. An under-count leads to "queue is empty, no action needed" when in fact tickets are waiting.
- **The `fleet_status` function** at line 32-59: calls `_count_eligible_tickets` to populate `queue_depth`. An under-count here affects the summary metrics shown on the main fleet dashboard.

### Concrete failure scenario

1. Production has 10,000 tickets in the `tickets` table (claims, META records, history entries all in the same table).
2. Only 12 of those items have `agent_eligible = 'yes'` and no `agent_claimed_by`.
3. A scan page reads 1 MB of data — approximately 700-1,000 items, depending on item size.
4. By chance, none of the 12 eligible tickets fall in the first page (they are scattered by PK ordering).
5. `_count_eligible_tickets` returns 0.
6. Dashboard shows: "Queue depth: 0, No action needed."
7. An operator sees idle workers and no queue, assumes the system is healthy, and does not investigate.
8. In reality 12 tickets are silently backed up; workers are idle; SLA is missed.

### Worst case

If the table grows very large (e.g., after months of accumulation without cleanup), the correct count could be 50+ while the displayed count is persistently 0. Any automation that scales workers down based on queue depth (future feature) would make this worse.

### Non-security consequence

This is a data integrity / operational visibility defect, not a direct security vulnerability. Severity is HIGH because incorrect operational data directly affects business decisions and SLA compliance.

## 4. Fix Design (code-level)

### Primary fix: pagination loop in `_count_eligible_tickets`

```python
# app/services/agent_fleet.py:288-303 — replace

def _count_eligible_tickets(user_id: str) -> int:
    """Count agent-eligible unclaimed tickets with full table pagination."""
    try:
        total = 0
        kwargs: dict = {
            "FilterExpression": (
                "agent_eligible = :yes AND attribute_not_exists(agent_claimed_by)"
            ),
            "ExpressionAttributeValues": {":yes": "yes"},
            "Select": "COUNT",
        }
        while True:
            resp = T.tickets.scan(**kwargs)
            total += resp.get("Count", 0)
            last_key = resp.get("LastEvaluatedKey")
            if not last_key:
                break
            kwargs["ExclusiveStartKey"] = last_key
        return total
    except Exception:
        logger.debug("fleet._count_eligible_tickets failed, returning 0")
        return 0
```

### Fix for `_count_eligible_by_type` (same defect)

```python
# app/services/agent_fleet.py:306-322 — replace

def _count_eligible_by_type(user_id: str) -> Dict[str, int]:
    """Count eligible tickets grouped by type with full pagination."""
    try:
        by_type: Dict[str, int] = {}
        kwargs: dict = {
            "FilterExpression": (
                "agent_eligible = :yes AND attribute_not_exists(agent_claimed_by)"
            ),
            "ExpressionAttributeValues": {":yes": "yes"},
            "ProjectionExpression": "#t",
            "ExpressionAttributeNames": {"#t": "type"},
        }
        while True:
            resp = T.tickets.scan(**kwargs)
            for item in resp.get("Items", []):
                t = item.get("type", "untyped")
                by_type[t] = by_type.get(t, 0) + 1
            last_key = resp.get("LastEvaluatedKey")
            if not last_key:
                break
            kwargs["ExclusiveStartKey"] = last_key
        return by_type
    except Exception:
        logger.debug("fleet._count_eligible_by_type failed, returning {}")
        return {}
```

Note: A `ProjectionExpression` of `"#t"` is added to `_count_eligible_by_type` to retrieve only the `type` attribute, reducing data transfer and improving performance over the full attribute projection. `type` is a DynamoDB reserved word, so `ExpressionAttributeNames` maps it to `#t`.

### Performance consideration

A full-table scan is expensive on a large table. For long-term scalability, the proper fix is a GSI on `agent_eligible` with a sort key of `created_at`. This would turn the count from an O(N_table) scan into an O(N_eligible) query. That schema change is a larger undertaking and should be tracked separately; the pagination loop is the minimal correct fix for the immediate bug.

Document the GSI as a follow-up: `GSI: agent_eligible-index, PK=agent_eligible (S), SK=created_at (N)`, declared with `attr_types={"created_at": "N"}` in `scripts/local-ddb-init.py` (per the DynamoDB gotchas in CLAUDE.md).

### Dev/Prod parity (SECOPS-007)

The pagination loop is pure Python logic over the DynamoDB API. It works identically against DynamoDB Local (dev) and DynamoDB (prod). No feature flag or environment branch is required. The loop simply has no iterations in dev (the whole table fits in one page) and multiple iterations in prod — same code, different data volume.

### Backward compatibility

`_count_eligible_tickets` is a private function called only by `fleet_status` and `fleet_capacity`. The return type remains `int`. No API contract changes. No migration required.

import pytest
from unittest.mock import patch, MagicMock, call

from app.services import agent_fleet as svc


def _make_scan_response(count, last_key=None):
    """Build a mock scan response page."""
    resp = {"Count": count, "ScannedCount": count + 10}
    if last_key:

    return resp

    # This assertion FAILS before the fix when the table has content on page 2
    assert result == 0  # correct with the current (broken) code — demonstrates the bug
    assert mock_T.tickets.scan.call_count == 1  # only one call made


# AFTER FIX: pagination loop accumulates count across all pages
def test_pagination_accumulates_count_across_pages():
    """After fix: count is summed across all pages."""
    mock_T = MagicMock()
    page1 = _make_scan_response(count=3, last_key={"pk": "TOKEN#page2"})

    assert mock_T.tickets.scan.call_count == 3
