# GAP-0013: Abandoned Registration Permanently Blocks Email Re-use — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: AUTH-001. Investigation: docs/tickets/gap-tickets/investigations/GAP-0013.md.

---

## 1. Summary & Classification

**Plain-English statement**: When a user starts registration (email + password submitted, verification email sent) but never clicks the verification link, the `T.users` and `T.account_state` DynamoDB rows are written with no TTL (time-to-live). The verification challenge expires and is garbage-collected, but the user record persists forever. Any subsequent attempt to register with the same email address — whether by the original user from a different device, by the same user after losing access to the original email, or by a different person who legitimately owns that address — returns a 409 "User already exists" with no recovery path.

## 2. Current-State Investigation (root cause)

### The two problematic writes

**Write 1 — `T.users` table** (`app/services/registration.py:79`):

```python
# app/services/registration.py:71-84
item = {
    "user_sub": user_sub,
    "email": user_sub,
    "full_name": full_name.strip(),
    "password_hash": password_hash,
    "created_at": created_at,
}
try:
    T.users.put_item(
        Item=item,
        ConditionExpression="attribute_not_exists(user_sub)",
    )
except Exception as exc:
    raise HTTPException(409, "User already exists") from exc
```

`item` contains no TTL attribute. The `with_ttl` helper is imported at line 19 (`from app.services.ttl import with_ttl`) but never called here.

**Write 2 — `T.account_state` table** (`app/services/registration.py:93-94`):

```python
# app/services/registration.py:93-94
status = "pending_verification" if verification_required else "active"
set_account_state(user_sub, status, reason="initial_registration", requested_by=user_sub)
```

`app/services/account_state.py:28–38` — `set_account_state` has no `ttl_epoch` parameter. It writes a plain item with no TTL attribute:

```python
# app/services/account_state.py:28-38
def set_account_state(user_sub: str, status: str, *, reason: str = "", requested_by: str = "") -> Dict[str, Any]:
    ts = now_ts()
    item = {
        "user_sub": user_sub,
        "status": status,
        "updated_at": ts,
        "reason": reason,
        "requested_by": requested_by,
    }
    T.account_state.put_item(Item=item)
    return get_account_state(user_sub)
```

No `ttl_epoch` parameter, no `with_ttl` call, no TTL attribute written.

### The email availability check

`app/services/registration.py:53–55`:

```python
def is_email_available(email: str) -> bool:
    normalized = normalize_email(email)
    return not _user_exists(normalized)
```

`_user_exists` (lines 41–50) does a `get_item` on `T.users`. If the unverified, orphaned record is present, `_user_exists` returns `True`, `is_email_available` returns `False`, and the registration endpoint returns 409. There is no check for `pending_verification` status; the same code path blocks both "email used by active account" and "email used by abandoned pending registration".

### The challenge TTL — asymmetry

The verification challenge itself does have a TTL. Lines 120–137 (not shown here but confirmed in the investigation) use `with_ttl(payload, ttl_epoch=expires)` when creating the challenge session. The challenge expires; the `T.users` and `T.account_state` records do not. This asymmetry is the root cause.

### How it manifests

In dev: a user who runs `POST /ui/register` without completing verification permanently occupies their email address. The test suite accumulates orphaned records across runs; `just restart` wipes them via a clean DynamoDB restart. In production with a live DynamoDB table, there is no wipe — abandoned registrations accumulate indefinitely.

## 3. Impact / Exploit / Blast Radius

**Denial-of-service on email addresses**: An attacker can permanently reserve any email address by starting a registration and abandoning it. The attack requires no special privileges — the registration endpoint is public. One HTTP request per target address is sufficient.

**Affected users**: Any person who:
- Started registration and lost access to the verification email
- Started registration on one device and switched to another
- Was a target of an attacker pre-registering their email
- Registered in dev/test mode and wants to re-register in production

**Recovery path without the fix**: A ROOT administrator must directly delete the `T.users` item (PK `user_sub = <email>`) and the `T.account_state` item (PK `user_sub = <email>`) via the DynamoDB console or `scripts/rootctl`. There is no admin API endpoint for this. There is no user-facing "resend verification" path that clears the stale record.

**Scope**: Affects all dev-mode registrations (when `COGNITO_USER_POOL_ID` is not configured). In production, if Cognito is not in use (or if `_cognito_available()` returns `False` due to `DEV_MODE=True` — see CLAUDE.md), the same code path applies.

**Compliance**: Depending on jurisdiction, permanently preventing a user from registering with their own email address may constitute a service availability issue under consumer protection regulations.

## 4. Fix Design (code-level)

### Overview

When `verification_required=True`, attach a TTL to both the `T.users` item and the `T.account_state` item. On successful verification, remove the TTL attribute from both records. Add a new setting `REGISTRATION_PENDING_TTL_DAYS` (default: 7).

### Fix 1 — `app/services/registration.py` (`create_user_record`)

```python
# app/services/registration.py — create_user_record, lines 58-95 (modified)

REGISTRATION_PENDING_TTL_DAYS = int(getattr(S, "registration_pending_ttl_days", 7))


def create_user_record(
    *,
    email: str,
    full_name: str,
    password: str,
    verification_required: bool,
) -> Dict[str, str]:
    user_sub = normalize_email(email)
    if _user_exists(user_sub):
        raise HTTPException(409, "User already exists")

    password_hash = _hash_password(password)
    created_at = now_ts()
    pending_ttl = created_at + REGISTRATION_PENDING_TTL_DAYS * 86400

    item = {
        "user_sub": user_sub,
        "email": user_sub,
        "full_name": full_name.strip(),
        "password_hash": password_hash,
        "created_at": created_at,
    }

    # Attach TTL to unverified records so abandoned registrations self-clean.
    if verification_required:
        item = with_ttl(item, ttl_epoch=pending_ttl)

    try:
        T.users.put_item(
            Item=item,
            ConditionExpression="attribute_not_exists(user_sub)",
        )
    except Exception as exc:
        raise HTTPException(409, "User already exists") from exc

    profile = empty_profile()
    profile.update({
        "display_name": full_name.strip() or None,
        "displayed_email": user_sub,
    })
    save_profile(user_sub, profile, audit_entries=[{"event": "register_start", "at": created_at}])

    status = "pending_verification" if verification_required else "active"
    set_account_state(
        user_sub, status,
        reason="initial_registration",
        requested_by=user_sub,
        ttl_epoch=pending_ttl if verification_required else None,
    )
    return {"user_sub": user_sub}
```

### Fix 2 — `app/services/account_state.py` (`set_account_state`)

Add an optional `ttl_epoch` parameter:

```python
# app/services/account_state.py — set_account_state (modified)
from app.services.ttl import with_ttl

def set_account_state(
    user_sub: str,
    status: str,
    *,
    reason: str = "",
    requested_by: str = "",
    ttl_epoch: Optional[int] = None,  # NEW
) -> Dict[str, Any]:
    ts = now_ts()
    item = {
        "user_sub": user_sub,
        "status": status,
        "updated_at": ts,
        "reason": reason,
        "requested_by": requested_by,
    }
    if ttl_epoch is not None:
        item = with_ttl(item, ttl_epoch=ttl_epoch)
    T.account_state.put_item(Item=item)
    return get_account_state(user_sub)
```

### Fix 3 — Remove TTL on successful verification

Wherever `complete_verification` (or equivalent) is called after the user verifies their email, add a DynamoDB `REMOVE` on the TTL attribute for both records:

```python
# After verifying the challenge and confirming the user:
from app.core.settings import S

T.users.update_item(
    Key={"user_sub": user_sub},
    UpdateExpression=f"REMOVE {S.ddb_ttl_attr}",
)
T.account_state.update_item(
    Key={"user_sub": user_sub},
    UpdateExpression=f"REMOVE {S.ddb_ttl_attr}",
)
```

This ensures that verified users are not accidentally expired by a residual TTL.

### Fix 4 — New setting

Add to `app/core/settings.py` (`Settings` dataclass):

```python
registration_pending_ttl_days: int = int(os.environ.get("REGISTRATION_PENDING_TTL_DAYS", "7"))
```

Add to `.env.local.example`:

```
REGISTRATION_PENDING_TTL_DAYS=7
```

### Dev/Prod parity (SECOPS-007)

- `with_ttl` sets `item[S.ddb_ttl_attr] = int(ttl_epoch)`. `S.ddb_ttl_attr` defaults to `"ttl_epoch"` and is configured identically in dev and production via the `DDB_TTL_ATTR` environment variable.
- DynamoDB Local (dev) stores the TTL attribute but does not auto-expire items. This is acceptable — the attribute's presence can be asserted in tests, and the functional cleanup happens in production AWS DynamoDB where TTL expiry runs asynchronously within 48 hours.
- The `T.users` and `T.account_state` tables must have TTL enabled in production. Confirm by running `aws dynamodb describe-time-to-live --table-name <users-table>` — it should return `"TimeToLiveStatus": "ENABLED"` with `"AttributeName": "ttl_epoch"`. If not, enable it: `aws dynamodb update-time-to-live --table-name <users-table> --time-to-live-specification "Enabled=true,AttributeName=ttl_epoch"`. This is a one-time production setup step.
- No behavioral difference between dev and prod for the TTL write itself.

### Backward compatibility

The `set_account_state` signature change adds an optional keyword argument with a default of `None`. All existing callers (none of which pass `ttl_epoch`) are unaffected. No DynamoDB schema migration is required — the TTL attribute is simply absent on existing non-pending records.

### Alternatives considered

- **Background cleanup job**: A scheduled task that periodically scans for `pending_verification` records older than N days and deletes them. Rejected — DynamoDB TTL is simpler, serverless, and does not require a separate process. A background job also has the full-table-scan problem (noted in CLAUDE.md as an antipattern).
- **Check `account_state` in `is_email_available`**: Return `True` (available) for `pending_verification` records. Rejected — this would allow a second registration to overwrite an in-progress unverified registration, potentially locking out the original user if they verify after the second user overwrites the record.
- **Resend-verification endpoint to clear stale records**: Add a "resend verification" flow that deletes the old record and creates a new one. This is a valid additional feature (see GAP-0108) but does not address the root cause — without TTL, a malicious actor can still permanently block an address by abandoning registrations faster than they can be cleared.

### Manual QA steps

1. `just up`
2. `POST /ui/register` with `{"email": "abandoned@test.local", "password": "...", "full_name": "..."}`.
3. Do NOT complete verification.
4. In DynamoDB Shell or AWS console, get the `T.users` item for `user_sub = "abandoned@test.local"` and confirm the `ttl_epoch` attribute is present with a value approximately 7 days in the future.
5. Repeat `POST /ui/register` with the same email — confirm it still returns 409 (the TTL has not elapsed).
6. Manually delete the item (simulating TTL expiry) and confirm `POST /ui/register` now returns 201.
7. Also verify the `T.account_state` item for the same `user_sub` has the same `ttl_epoch`.

### Observability

- No new metrics required for this fix — it is a TTL attribute addition.
- To monitor for orphaned pending registrations in production, add a CloudWatch metric alarm on the `T.users` table's item count filtered by `status = pending_verification`. An abnormally high count (e.g., > 1000) may indicate a registration abuse campaign.

### Production setup prerequisite

Confirm TTL is enabled on `T.users` and `T.account_state` tables:

```

If not enabled, run once before deploying:

  --time-to-live-specification "Enabled=true,AttributeName=ttl_epoch"
aws dynamodb update-time-to-live \
  --table-name <account-state-table-name> \
  --time-to-live-specification "Enabled=true,AttributeName=ttl_epoch"
```

### Rollback

Reverting the fix removes the TTL attribute from new pending registrations. Already-written TTL attributes on existing records will be harmless — DynamoDB will eventually expire those items (or they will persist until manually deleted). No data corruption results from rollback.

### Risks

- **DynamoDB TTL is eventually consistent**: Expired items may remain readable for up to 48 hours after their TTL elapses. During this window, a user whose registration expired 24 hours ago may still see a 409 if they re-register. Mitigation: also check `ttl_epoch < now_ts()` in `is_email_available` to treat TTL-expired-but-not-yet-deleted records as available. This is a future hardening step.
- **Verification after TTL**: If a user completes verification after the TTL has elapsed and DynamoDB has already deleted the record, the verification endpoint will fail to find the user and return an error. Mitigation: the challenge TTL (already set) should be shorter than the user record TTL, ensuring challenges expire before user records are deleted. With default challenge TTL of 24 hours and user record TTL of 7 days, this window is safe.

**Effort**: S — approximately 1–2 hours: two `with_ttl` calls, signature addition to `set_account_state`, new setting, TTL-removal in verification completion, tests.
