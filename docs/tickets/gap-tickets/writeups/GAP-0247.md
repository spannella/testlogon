# GAP-0247: ExtractionResultsPanel Not Integrated into Admin Case Detail — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase; no prior investigation doc exists.

## 1. Summary & Classification

**Claim from ticket**: The `ExtractionResultsPanel` component is absent from
`KycCaseDetailPage.tsx`, so a reviewer cannot see OCR-extracted fields, per-field match
status, or overall confidence score without navigating away to the standalone document
review queue page. The fix is to add a "Document Extraction" tab that calls
`GET /ui/kyc/documents/admin/by-status?case_id=`.

**Verdict: Claim CONFIRMED (with one correction).** `KycCaseDetailPage.tsx` has no
extraction-results section at all — there is no query to any document endpoint, no
`extracted_fields` rendering, and no confidence badges. However the proposed fix endpoint
path is slightly wrong: the correct fix is to call
`GET /ui/kyc/documents/admin/by-status?status=extracted` and then filter client-side, OR
to use the separate `list_documents_for_case` service method (which queries the `ByCase`
GSI). Importantly, no `case_id` query parameter exists on the `by-status` endpoint today
(this is the subject of GAP-0248). The correct fix is therefore either to implement
GAP-0248 first (add `case_id` to the endpoint) or to call a different endpoint. Both paths
are described below.

- **Severity**: HIGH — KYC reviewers working through a case cannot see OCR extraction
  output or document-level match status from within the case view. This forces a context
  switch that breaks workflow and risks human error (reviewer approves a case without seeing
  a name-mismatch warning).
- **Source ticket**: KYC-002
- **Owning area**: Frontend / KYC admin tooling
- **Related tickets**: GAP-0248 (case_id filter, prerequisite), GAP-0246 (DocumentViewer),
  GAP-0250 (VerificationCallPanel), SECOPS-007 (dev/prod parity)

## 2. Current-State Investigation (root cause)

### KycCaseDetailPage layout

`frontend/src/pages/admin/KycCaseDetailPage.tsx` uses a two-column grid: the left column
(lines 431–436) renders `<DocumentViewer>` and `<KycFacialComparisonReview>`. The right
column (lines 438–526) has Case Information, Actions, and Timeline. There is **no** panel,
tab, or accordion that shows document extraction data.

The page imports only from `@/api/endpoints/kyc-admin` (line 39–46) — it does not import
`listKycDocumentsByStatus` from `@/api/endpoints/kycDocuments` and does not call any
document endpoint at all.

### What the standalone queue page does

`frontend/src/pages/kyc/KycDocumentReviewQueuePage.tsx` (admin-accessible, separate route)
calls `listKycDocumentsByStatus(status)` (via `kycDocuments.ts:26`) and renders match
badges and confidence scores using data fields that already exist in `KycDocumentOut`:

- `extracted_fields: Record<string, string>` — OCR field key/value pairs
- `match_results?: Record<string, KycDocumentFieldMatch>` — per-field `match`/`partial`/`mismatch`
- `overall_confidence?: KycDocumentConfidence` — `high`/`medium`/`low`

(`frontend/src/api/types.ts` lines 8243–8245)

The `MatchBadges` component (`KycDocumentReviewQueuePage.tsx:48–64`) already provides the
per-field badge rendering logic, but it is embedded inline in that file rather than in
`components/shared/`. There is no shared `ExtractionResultsPanel` that `KycCaseDetailPage`
could import.

### Why there is no case-scoped document fetch

The admin documents endpoint (`app/routers/kyc_documents.py:90–99`) only accepts `status`
as a filter — there is no `case_id` parameter:

```python
# kyc_documents.py:90-98
@kyc_documents_router.get("/admin/by-status", ...)
async def admin_list_by_status(
    status: str = Query(...),
    limit: int = Query(100, ge=1, le=500),
    _user: AuthenticatedUser = Depends(require_admin_or_root),
) -> KycDocumentListResponse:
    items = STORE.list_by_status(status, limit=limit)
    ...
```

The service layer does have a `list_documents_for_case` method (line 275) that uses the
`ByCase` GSI, but there is no router endpoint that exposes it to admin users. This is
the core of GAP-0248, which this GAP depends on.

### Document status distribution in a typical case

A case may have documents in multiple statuses simultaneously. For example:

| Document type | Status |
|---------------|--------|
| `id_front` | `extracted` (OCR ran, fields available) |
| `id_back`  | `pending`   (uploaded but not yet extracted) |
| `selfie`   | `approved`  (manually reviewed and approved) |

A `by-status?status=extracted` query would return the `id_front` only, requiring three
separate calls to get the full picture. The `ByCase` GSI returns all three in one call.

## 3. Impact / Exploit / Blast Radius

This is a workflow and data-integrity gap, not a security vulnerability.

| Area | Impact |
|------|--------|
| **Reviewer workflow** | To check OCR results, a reviewer must leave the case detail page, open the Document Queue page, filter by status, find the relevant document, then return. Any mid-review state (approve/reject dialog open) is lost. In a high-volume KYC queue this context-switch happens dozens of times per reviewer per day. |
| **False approvals** | A reviewer who does not navigate to the queue will approve or reject a case without seeing that, e.g., the name on the ID does not match the profile — a name-mismatch `match_results` entry stays invisible. In regulated environments (AML/KYC compliance), a false approval driven by incomplete information may constitute a regulatory breach. |
| **Compliance audit** | Audit logs record `kyc_case_approved` or `kyc_case_rejected` timeline events, but do not record that a reviewer examined the OCR extraction results. If the decision is later challenged by a regulator or the user, there is no audit trail showing the reviewer had access to the `low` confidence / `mismatch` badges visible in the queue page. |
| **Confidence-level blindness** | The overall confidence field (`high` / `medium` / `low`) summarises field-level match results into a single risk signal. Hiding this from the case detail view means a reviewer sees documents but not their quality assessment — the single most actionable signal the extraction pipeline produces. |
| **No data exposure** | The extraction data is accessible via the existing queue page; this is a UI gap only. No new data is returned to unauthorized users by this fix. |

## 4. Fix Design (code-level)

The fix requires two parts: (1) a backend endpoint to list documents for an admin by
`case_id`, and (2) a new frontend `ExtractionResultsPanel` component wired into
`KycCaseDetailPage`.

### 4a. Backend — new admin endpoint to list documents by case (dev/prod parity — SECOPS-007)

Add to `app/routers/kyc_documents.py`:

```python
@kyc_documents_router.get(
    "/admin/by-case/{case_id}",
    response_model=KycDocumentListResponse,
)
async def admin_list_documents_for_case(
    case_id: str,
    _user: AuthenticatedUser = Depends(require_admin_or_root),
) -> KycDocumentListResponse:
    """Return all documents for a specific case (admin view with match results)."""
    items = STORE.list_documents_for_case(case_id)
    return KycDocumentListResponse(
        documents=[_out(i, include_match=True) for i in items]
    )
```

`STORE.list_documents_for_case` (line 275 of the service) already queries the `ByCase`
GSI, so no new DynamoDB access code is needed. The endpoint uses the same
`require_admin_or_root` guard as the existing `/admin/by-status` endpoint. Dev and
production follow the same code path; the only environment difference is the DynamoDB
endpoint URL (handled by settings).

### 4b. Frontend — API wrapper

Add to `frontend/src/api/endpoints/kycDocuments.ts`:

```ts
export const adminListDocumentsForCase = (caseId: string) =>
  api.get<KycDocumentListResponse>(`/ui/kyc/documents/admin/by-case/${caseId}`);
```

### 4c. Frontend — `ExtractionResultsPanel` shared component

Create `frontend/src/components/shared/ExtractionResultsPanel.tsx`:

```tsx
import { useQuery } from "@tanstack/react-query";
import { Badge } from "@/components/ui/badge";
import { Card, CardContent, CardHeader, CardTitle } from "@/components/ui/card";
import { adminListDocumentsForCase } from "@/api/endpoints/kycDocuments";
import type { KycDocumentOut, KycDocumentFieldMatch } from "@/api/types";

function matchVariant(m: KycDocumentFieldMatch) {
  if (m.status === "match")    return "default"      as const;
  if (m.status === "partial")  return "secondary"    as const;
  if (m.status === "mismatch") return "destructive"  as const;
  return "outline" as const;
}

function DocumentExtractCard({ doc }: { doc: KycDocumentOut }) {
  const fields   = doc.extracted_fields ?? {};
  const matches  = doc.match_results    ?? {};

  return (
    <Card className="mb-4" data-testid={`extraction-card-${doc.document_id}`}>
      <CardHeader>
        <CardTitle className="text-sm font-medium flex items-center gap-2">
          {doc.document_type}
          {doc.overall_confidence && (
            <Badge
              variant={
                doc.overall_confidence === "high"   ? "default"
                : doc.overall_confidence === "low"  ? "destructive"
                : "secondary"
              }
              data-testid="doc-confidence"
            >
              {doc.overall_confidence} confidence
            </Badge>
          )}
        </CardTitle>
      </CardHeader>
      <CardContent>
        {Object.keys(fields).length === 0 ? (
          <p className="text-sm text-muted-foreground">
            {doc.status === "pending" ? "Extraction not yet run." : "No fields extracted."}
          </p>
        ) : (
          <table className="w-full text-sm" data-testid="extraction-fields">
            <tbody>
              {Object.entries(fields).map(([k, v]) => {
                const m = matches[k];
                return (
                  <tr key={k} className="border-b last:border-0">
                    <td className="py-1 pr-4 font-medium text-muted-foreground w-1/3">{k}</td>
                    <td className="py-1 pr-4">{v}</td>
                    <td className="py-1 text-right">
                      {m && (
                        <Badge variant={matchVariant(m)} data-testid={`match-${k}`}>
                          {m.status}
                        </Badge>
                      )}
                    </td>
                  </tr>
                );
              })}
            </tbody>
          </table>
        )}
      </CardContent>
    </Card>
  );
}

export function ExtractionResultsPanel({ caseId }: { caseId: string }) {
  const q = useQuery({
    queryKey: ["kyc-case-documents", caseId],
    queryFn: () => adminListDocumentsForCase(caseId),
    enabled:  !!caseId,
  });

  if (q.isLoading) {
    return <p className="text-sm text-muted-foreground" data-testid="extraction-loading">Loading documents…</p>;
  }
  if (q.isError) {
    return <p className="text-sm text-destructive" data-testid="extraction-error">Failed to load document extraction results.</p>;
  }
  const docs = q.data?.documents ?? [];
  if (docs.length === 0) {
    return (
      <p className="text-sm text-muted-foreground" data-testid="extraction-empty">
        No documents associated with this case.
      </p>
    );
  }
  return (
    <div data-testid="extraction-results-panel">
      {docs.map((doc) => (
        <DocumentExtractCard key={doc.document_id} doc={doc} />
      ))}
    </div>
  );
}
```

### 4d. Wire into `KycCaseDetailPage`

Add a third tab row beneath the existing two-column grid. The simplest approach
(non-breaking, additive) is to add a collapsible section below the grid:

```tsx
// After the existing two-column grid (line 527) in KycCaseDetailPage.tsx:
import { ExtractionResultsPanel } from "@/components/shared/ExtractionResultsPanel";
import {
  Collapsible,
  CollapsibleContent,
  CollapsibleTrigger,
} from "@/components/ui/collapsible";

// Inside the JSX return, after </div> {/* end two-column grid */}:
<Collapsible defaultOpen>
  <CollapsibleTrigger asChild>
    <Button variant="ghost" className="w-full justify-start mb-2">
      Document Extraction Results
    </Button>
  </CollapsibleTrigger>
  <CollapsibleContent>
    <ExtractionResultsPanel caseId={caseData.kyc_case_id} />
  </CollapsibleContent>
</Collapsible>
```

### Alternatives considered

- **Call `GET /admin/by-status?case_id=…`** — This requires GAP-0248 to be fixed first.
  The dedicated `by-case` endpoint is cleaner and uses a GSI that already exists
  (`ByCase`), making it faster (single query, no post-filter scan).
- **Include documents in the case detail response** — Would require modifying the
  `fetchKycCaseDetail` call and `KycCaseDetail` type. Rejected because it increases
  the already-large admin case response payload on every load, even when the reviewer
  doesn't expand the extraction panel.

## 5. Testing, Verification & Rollout

### Regression test — fails before / passes after

**pytest offline** (`tests/test_kyc_admin_documents_by_case.py`):

```python
def test_admin_list_documents_for_case(client, admin_headers, seeded_kyc_case_with_docs):
    case_id = seeded_kyc_case_with_docs["case_id"]
    resp = client.get(
        f"/ui/kyc/documents/admin/by-case/{case_id}",
        headers=admin_headers,
    )
    assert resp.status_code == 200
    docs = resp.json()["documents"]
    assert len(docs) >= 1
    # extraction fields present on extracted doc
    extracted = next((d for d in docs if d["status"] == "extracted"), None)
    assert extracted is not None
    assert isinstance(extracted["extracted_fields"], dict)
    assert "match_results" in extracted

def test_admin_list_documents_requires_admin(client, user_headers, seeded_kyc_case_with_docs):
    case_id = seeded_kyc_case_with_docs["case_id"]
    resp = client.get(
        f"/ui/kyc/documents/admin/by-case/{case_id}",
        headers=user_headers,
    )
    assert resp.status_code == 403
```

**Before fix**: `GET /ui/kyc/documents/admin/by-case/{id}` returns 404 (route does not
exist). Playwright test of `ExtractionResultsPanel` fails because neither the component
nor the endpoint exists.

**After fix**: Both tests pass. The Playwright test sees `data-testid="extraction-results-panel"`
with at least one `extraction-card-*` child.

When a reviewer opens the `ExtractionResultsPanel` and sees a `low` confidence result
before approving, this is important audit evidence. A future enhancement (out of scope for
