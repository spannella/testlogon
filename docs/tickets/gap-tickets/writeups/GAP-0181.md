# GAP-0181: Per-delivery stats (`webhook_stats`) not recorded — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against real code before writing; cites `file:line`.

## 1. Summary & Classification

**Bug statement**: The `webhook_stats` module exists and exposes a fully working `record_delivery_stat()` function, but the webhook dispatcher loop never calls it. Every webhook delivery — success or failure — silently passes through the dispatcher without incrementing any counter in the `webhook_stats` DynamoDB table. The stats API endpoints therefore return empty or zero-filled responses for all endpoints regardless of actual delivery volume.

- **Severity**: HIGH
- **Source ticket**: ENTERPRISE-005
- **Owning area**: Webhooks / Platform infrastructure
- **Status**: Open (confirmed gap)
- **Verdict**: **Confirmed**. The `record_delivery_stat` function in `app/services/webhook_stats.py` is never imported or called from either `run_webhook_dispatcher_loop` or `run_webhook_dispatcher_once` in `app/services/webhook_dispatcher.py`.
- **One-line impact**: Enterprise customers and platform operators cannot observe webhook delivery reliability because all per-endpoint and global delivery counters remain at zero.
- **Related tickets**: ENTERPRISE-005, PLATFORM-002 (dispatcher), PLATFORM-008 (job dashboard)

## 2. Current-State Investigation (root cause)

### The dispatcher loop (file:line)

`app/services/webhook_dispatcher.py:44–68` contains the main delivery loop:

```python
for delivery in due:
    try:
        ...
        result = await deliver_webhook(...)

        if result["success"]:
            mark_delivery_success(delivery, result)     # line 63
            reset_endpoint_failure_count(...)           # line 64
            _processed += 1
        else:
            handle_delivery_failure(delivery, endpoint, result)  # line 67
            _failed += 1
    except Exception:
        _failed += 1
```

`record_delivery_stat` is defined at `app/services/webhook_stats.py:25` with the signature:

```python
def record_delivery_stat(endpoint_id: str, result: Dict[str, Any]) -> None:
```

It is **never imported and never called** anywhere in `webhook_dispatcher.py`. A module-level search across the production codebase (`app/`) confirms there is no call site for `record_delivery_stat` anywhere outside `webhook_stats.py` itself.

### The one-time runner (file:line)

`app/services/webhook_dispatcher.py:103–138` contains `run_webhook_dispatcher_once`, which is used by the manual "run now" admin action. It duplicates the same delivery loop and is equally missing both call sites (`mark_delivery_success` at line 129 and `handle_delivery_failure` at line 133 both lack a subsequent `record_delivery_stat` call).

### The stats service (file:line)

`app/services/webhook_stats.py:25–72` implements `record_delivery_stat`. The function:
1. Derives an hourly bucket key from the current timestamp (line 33).
2. Increments `total_deliveries`, either `successful` or `failed`, and `latency_sum_ms` using DynamoDB atomic `ADD` (line 37–53).
3. Writes both a per-endpoint record (`STATS#{endpoint_id}`) and a global aggregate (`GLOBAL`), at lines 56–70.

The function is entirely correct — it uses conditional expressions, is exception-safe (swallows errors with `logger.debug`), and correctly consumes the `result` dict that `deliver_webhook` already returns (which contains `success`, `duration_ms`, etc.).

### Why it was never wired

The `webhook_stats.py` module was introduced alongside `webhook_service.py` and `webhook_dispatcher.py` as part of ENTERPRISE-005, but a `record_delivery_stat(endpoint_id, result)` call was omitted from the dispatcher's success and failure branches. The `get_endpoint_stats` and `get_global_stats` endpoints (`app/routers/webhooks.py`) were written and registered, creating a stats API surface with permanently empty responses.

### Runtime behavior

In dev: `T.webhook_stats.update_item(...)` is called against the moto DynamoDB mock. Because the table is created in `scripts/local-ddb-init.py`, calls succeed silently — there is simply no invocation to drive them.

In prod: The AWS DynamoDB table accumulates no records. The stats read endpoints return `total_deliveries: 0, success_rate: 1.0, avg_latency_ms: 0` for every endpoint, giving a false impression of 100% success and zero traffic.

## 3. Impact / Exploit / Blast Radius

### Observability failure

Enterprise plan customers expect delivery stats as part of the ENTERPRISE-005 feature contract. The stats API (`GET /ui/webhooks/endpoints/{id}/stats`, `GET /ui/webhooks/stats/global`) returns valid JSON with all-zero counters. Customers monitoring these endpoints for SLA tracking, incident investigation, or billing audits receive no signal.

### Latent alerting failure

The platform's own reliability monitoring depends on global webhook stats. A silent delivery failure storm (e.g., a misconfigured endpoint that rejects all deliveries) would show up as `success_rate: 1.0` globally because failed_count always stays at zero. Operators would not be alerted until customers reported issues directly.

### Compounding effect with retry logic

`handle_delivery_failure` in `webhook_service.py:792` schedules retries and increments the endpoint's `failure_count`. When the endpoint is revived and deliveries succeed again, `reset_endpoint_failure_count` zeros the counter. This operational flow is correct, but the absence of per-hour stat recording means there is no time-series audit trail of the outage — the per-endpoint failure window is permanently invisible.

### Financial / compliance impact

For paid enterprise integrations where SLA guarantees are tied to delivery success rate, the absence of stats makes SLA measurement impossible from the platform side.

### Blast radius

- All webhook endpoint stats: affected for all users (both dev and prod, historically and going forward).
- No security exposure — this is a data-recording omission, not an authentication or authorization gap.
- No data loss: the delivery state records (in `webhook_deliveries` table) are written correctly; only the aggregate counters are missing.

## 4. Fix Design (code-level)

### Change 1: Wire `record_delivery_stat` in the dispatcher loop

**File**: `app/services/webhook_dispatcher.py`

Add `record_delivery_stat` to the imports at the top and call it after each delivery outcome in both the background loop (`run_webhook_dispatcher_loop`) and the one-shot runner (`run_webhook_dispatcher_once`):

```python
# Add to imports (line ~11)
from app.services.webhook_stats import record_delivery_stat

# In the for-delivery loop, after mark_delivery_success (line ~64):
if result["success"]:
    mark_delivery_success(delivery, result)
    reset_endpoint_failure_count(endpoint_id, user_sub)
    record_delivery_stat(endpoint_id, result)   # <-- ADD
    _processed += 1
else:
    handle_delivery_failure(delivery, endpoint, result)
    record_delivery_stat(endpoint_id, result)   # <-- ADD
    _failed += 1
```

The same two `record_delivery_stat` calls must be added to `run_webhook_dispatcher_once` (lines ~129 and ~133) to keep the one-shot path consistent with the loop.

### Change 2: Record stats for dead-letter deliveries (optional, recommended)

When an endpoint is disabled and the delivery is dead-lettered (`mark_delivery_dead_letter` at line 50), stats are also skipped. A minimal extension records these as failures:

```python
mark_delivery_dead_letter(delivery, reason="endpoint_disabled")
record_delivery_stat(endpoint_id, {"success": False, "duration_ms": 0,
                                    "error": "endpoint_disabled"})
continue
```

This is optional for the initial fix but aligns with the intent of global stats.

### SECOPS-007 dev/prod parity

`record_delivery_stat` writes to `T.webhook_stats`, which resolves to `ddb.Table(S.webhook_stats_table)`. In dev, this points at the DynamoDB Local table created by `scripts/local-ddb-init.py`. In prod, it points at the real AWS DynamoDB table. No conditional branching is needed — the same code path runs in both environments, and moto absorbs the dev calls transparently. No new environment variables, feature flags, or mock adapters are required.

### Backward compatibility

The fix is purely additive: it adds call sites for a function that already exists. Existing DynamoDB records and API response shapes are unchanged. There is no migration required — stats counters will start accumulating from the moment the fix is deployed; historical delivery records (before the fix) will correctly show zero stats.

### Alternatives considered

1. **Record stats inside `mark_delivery_success` / `handle_delivery_failure`**: This co-locates the call at a lower layer, but would tie the stats module to the service module and make it harder to test the dispatcher in isolation. The dispatcher is the natural call site because it has the full `result` dict and the delivery context.
2. **Emit stats via a CloudWatch/Prometheus metric instead of DynamoDB**: Valid for production observability, but the ticket spec and the existing `get_endpoint_stats` API require per-endpoint DynamoDB-backed counters.

### Manual QA steps

1. Start the dev stack (`just up`).
2. Register a webhook endpoint via `POST /ui/webhooks/endpoints`.
3. Trigger an event that dispatches a webhook (e.g., send a message in a monitored conversation).
4. Wait for the dispatcher loop (10 s poll interval) or call the "run now" admin endpoint.
5. `GET /ui/webhooks/endpoints/{id}/stats` — confirm `total_deliveries` is 1, `success_rate` is 1.0 or 0.0 depending on your test endpoint.
6. `GET /ui/webhooks/stats/global` — confirm `total_deliveries_24h` increments.

### Metrics / observability

After the fix, `get_endpoint_stats` and `get_global_stats` begin returning real data. The existing `success_rate` field provides a natural SLO signal. A CloudWatch alarm on the global `failed_count_24h` DynamoDB metric can be added independently.

### Rollback

Remove the two `record_delivery_stat` import and call lines. The dispatcher continues to function correctly; stats revert to empty. No DynamoDB schema or data migration is required for either direction.

### Risks

- **Negligible latency impact**: `record_delivery_stat` swallows all exceptions (line 61 of `webhook_stats.py`), so a DynamoDB outage cannot stall the dispatcher.
- **Double-counting on retry-override**: If a delivery is retried and succeeds on attempt 2, both attempt 1 (failure) and attempt 2 (success) are recorded, which is correct and intentional.

### Effort: S (Small)

Four lines of code change (two imports, two call sites in the loop, two call sites in the one-shot runner). No schema changes. No feature flags needed.

### Sequencing

Can be applied independently of any other open gap. Deploy after `ENTERPRISE-005` table is confirmed present in prod (`scripts/local-ddb-init.py` already registers `webhook_stats`).
