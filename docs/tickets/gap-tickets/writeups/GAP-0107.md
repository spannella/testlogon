# GAP-0107: /check endpoint leaks no unverified hint to frontend — Remediation Write-up

> Claim verified against `app/routers/register.py` and `app/models.py`. Claim is **confirmed**.
> The `/check` endpoint returns only `{"status": "ok", "available": bool}` with no distinction
> between an active account and a `pending_verification` account. The cited line (153) is the
> `@router.post("/check", ...)` decorator, which is the correct location.

## 1. Summary & Classification

**Bug**: `POST /ui/register/check` answers "is this email available?" but cannot distinguish
between two very different "unavailable" states: (a) an email belonging to a fully-verified
active account, and (b) an email that was submitted during a registration that was abandoned
before the verification code was entered. Both return `{"available": false}`. The frontend
therefore cannot offer a "resend code" option for abandoned registrations — it can only
display a dead-end error message.

- **Severity**: HIGH (user-facing registration UX broken for returning-but-unverified users;
  creates orphaned accounts that can never be claimed without admin intervention)
- **Source ticket**: AUTH-001
- **Status**: Open
- **Owning area**: Registration router and model (`app/routers/register.py`,
  `app/models.py`, `app/services/registration.py`, `app/services/account_state.py`)
- **Verdict**: Confirmed. Code inspection confirms the response model `RegisterEmailCheckResp`
  has only `status: str` and `available: bool` (models.py:265-267). The handler at
  register.py:183-184 returns `{"status": "ok", "available": available}` where `available`
  is the boolean result of `is_email_available()`, which returns `not _user_exists(email)` —
  binary, no status distinction.
- **Related tickets**: GAP-0108 (resume path for pending accounts on `/start`), GAP-0109
  (frontend dead-end, direct consumer of this missing field). All three must be fixed
  together to deliver a working recovery flow.

## 2. Current-State Investigation (root cause)

### Registration flow overview

The registration flow has three endpoints: `/start` (creates account + sends code),
`/check` (availability probe, called on email field blur), and `/confirm` (verifies the
code). A user who enters their email on the registration page triggers a debounced call to
`/check` to get instant feedback. If the backend returns `available: false`, the frontend
treats the email as taken and blocks the form. The gap here is that `/check` cannot distinguish
between an email that belongs to a verified, active account (where blocking is correct) and
one that belongs to an abandoned partial registration in the `pending_verification` state
(where the user should be offered a recovery path instead).

### is_email_available — registration.py:53-55

```python
def is_email_available(email: str) -> bool:
    normalized = normalize_email(email)
    return not _user_exists(normalized)
```

`_user_exists` (registration.py:41-50) does a `get_item` on the `users` table and returns
`True` if any item is found. It makes no distinction between the account's verification
status. The function is a boolean gate: exists or does not exist.

### Account state is stored separately

When `create_user_record` runs (registration.py:58-95) it calls:

```python
status = "pending_verification" if verification_required else "active"
set_account_state(user_sub, status, ...)
```

The `account_state` table (keyed by `user_sub`) holds the `status` field. `get_account_state`
from `app/services/account_state.py:16-25` can retrieve it at any time:

```python
def get_account_state(user_sub: str) -> Dict[str, Any]:
    it = T.account_state.get_item(Key={"user_sub": user_sub}).get("Item")
    ...
    return {"status": it.get("status", "active"), ...}
```

The infrastructure to determine `pending_verification` vs `active` already exists. The
`/check` handler simply does not use it.

### /check handler — register.py:153-184

```python
@router.post("/check", response_model=RegisterEmailCheckResp)
async def register_check(req: Request, body: RegisterEmailCheckReq):
    ...
    available = await asyncio.wait_for(
        run_in_threadpool(is_email_available, body.email), timeout=...
    )
    ...
    return {"status": "ok", "available": available}
```

When `available` is `False` the caller receives no information about why. The `RegisterEmailCheckResp`
model (models.py:265-267) only allows `status` and `available`:

```python
class RegisterEmailCheckResp(BaseModel):
    status: str
    available: bool
```

### Dev vs prod

The `account_state` table is populated identically in dev (DynamoDB Local) and prod (AWS
DynamoDB). Both paths call `set_account_state` during registration. The missing information
is equally absent in both environments.

## 3. Impact / Exploit / Blast Radius

### User experience — orphaned accounts

A user who:
1. Starts registration with email `alice@example.com`
2. Closes their browser before entering the verification code

…has an account record and a `pending_verification` state in DynamoDB. If they return later
and try to register again:

- `/check` returns `available: false`
- The frontend (GAP-0109) shows "An account with this email already exists"
- The "Next" button is disabled
- There is no resend button or recovery link
- The user is locked out of their own email address until an admin manually purges the record

This is a full loss of registration for the affected user. In the worst case the user must
contact support, and support must perform a DynamoDB write to either delete the orphaned
record or manually mark it verified.

### Security considerations

The fix adds one new response field (`unverified: bool`). Returning `unverified: true` does
confirm that an email address was used in a past registration attempt. This is a minor
information disclosure — an attacker learns that someone tried to register with that email.
The risk is low because:
- The attacker must already know or guess the email address.
- The information is no more sensitive than a standard "this email is registered" message.
- Rate-limiting on `/check` (already present via `enforce_lockout`) limits enumeration.

The alternative — returning no information — results in a broken UX for legitimate users,
which is the more damaging outcome.

### Blast radius

Affects every user who abandons registration mid-flow. The registration challenge TTL
controls how long the `pending_verification` state persists; any account not confirmed
within that window remains orphaned indefinitely (there is no current cleanup job).

## 4. Fix Design (code-level)

### Step 1 — Add `check_email_status` to registration service

Add to `app/services/registration.py`:

```python
from app.services.account_state import get_account_state

def check_email_status(email: str) -> dict:
    """Return availability and pending-verification flag for an email address."""
    normalized = normalize_email(email)
    if not _user_exists(normalized):
        return {"available": True, "unverified": False}
    state = get_account_state(normalized)
    if state["status"] == "pending_verification":
        return {"available": False, "unverified": True}
    return {"available": False, "unverified": False}
```

### Step 2 — Extend RegisterEmailCheckResp model

In `app/models.py`, change `RegisterEmailCheckResp` (line 265):

```python
class RegisterEmailCheckResp(BaseModel):
    status: str
    available: bool
    unverified: bool = False   # new field — default False preserves backward compat
```

Adding a defaulted field is backward-compatible: existing API clients that do not read
`unverified` continue to work unchanged.

### Step 3 — Update the /check handler

In `app/routers/register.py`, import `check_email_status` and replace the handler body:

```python
from app.services.registration import (
    check_email_status,          # new import
    create_registration_challenge,
    create_user_record,
    is_email_available,
    mark_user_verified,
    verify_registration_code,
)

@router.post("/check", response_model=RegisterEmailCheckResp)
async def register_check(req: Request, body: RegisterEmailCheckReq):
    ip = client_ip_from_request(req)
    enforce_lockout(body.email, ip, "register_check")
    rate_limit_password_recovery(body.email, ip, "register_check")
    generic_response = {"status": "ok", "available": True, "unverified": False}
    try:
        result = await asyncio.wait_for(
            run_in_threadpool(check_email_status, body.email),
            timeout=REGISTER_CHECK_TIMEOUT_SECONDS,
        )
    except asyncio.TimeoutError:
        ...
        return generic_response
    except Exception:
        ...
        return generic_response
    clear_lockout(body.email, ip, "register_check")
    audit_event("register_check", body.email, req, outcome="success",
                available=result["available"], unverified=result["unverified"])
    return {"status": "ok", **result}
```

### Dev/Prod parity (SECOPS-007)

`check_email_status` reads from the `users` table and the `account_state` table. Both tables
exist identically in dev (DynamoDB Local) and prod (AWS DynamoDB). No mock branching is
required. The `get_account_state` helper already handles the case where no state record
exists (returns `{"status": "active", ...}`), so there is no special handling for dev-seeded
users.

### Backward compatibility

The new `unverified` field defaults to `False`. Clients that only read `available` see no
change in behaviour.

### Handling the generic response on error

The handler's error-path `generic_response` at register.py:158 currently returns
`{"status": "ok", "available": True}`. After the fix, it must be updated to include
`"unverified": False` to match the updated response model:

```python
generic_response = {"status": "ok", "available": True, "unverified": False}
```

Returning `available: True` on timeout or error is an intentional design choice in the
existing code to avoid false negatives (blocking users because of transient DynamoDB issues).
The new `unverified` field should follow the same conservative default: `False` on error
means the frontend does not show a resend button for an account state it cannot confirm.

### Interaction with the rate-limit response

The `429 Too Many Requests` path is already handled in the frontend as a separate
`"rate_limited"` state (Register.tsx:254-255). The `/check` endpoint rate-limiting is via
`enforce_lockout` and `rate_limit_password_recovery`; these paths return `generic_response`
before reaching the account-state lookup, so they correctly return `available: True`
(unblocking) rather than a false unavailability. The `unverified` field does not affect the
rate-limit path.

    assert r.json() == {"status": "ok", "available": True, "unverified": False}

### Monitoring and support-team value

Once `unverified: true` is logged in audit events, the support team can identify users who
are stuck in `pending_verification` by querying the audit log for
`register_check outcomes where unverified=true`. This gives a quantitative baseline for how
often the problem occurs and whether the GAP-0108 resume path is being successfully used
after it ships. Track the metric for at least two weeks post-deployment to confirm the
recovery flow is working end-to-end.

2. Register a user but intentionally do not complete email verification.
3. Open DevTools Network tab, navigate to `/register`, enter the same email in the email

4. Inspect the response body — confirm `unverified: true` is present.
5. Repeat with a different email that belongs to an active (fully verified) account —
   confirm `unverified: false`.
6. Repeat with a brand-new email — confirm `available: true, unverified: false`.

### DynamoDB read cost

`check_email_status` performs two DynamoDB `get_item` calls instead of the current one
(`is_email_available` does one). The second call (`get_account_state`) only runs when the
first call confirms the user record exists, so the extra read is avoided for all
`available: true` responses. In production, the `/check` endpoint is called on every email
field change after a 400ms debounce. Two reads per `available: false` response is acceptable
given that false responses are relatively rare (only when the user types an already-registered
email). No caching or batching is needed at this volume.

### Rollout

- **Effort**: S (two small code changes + model field addition + one helper function)
- **Sequencing**: must ship before or alongside GAP-0108 and GAP-0109; the three tickets
  form a complete recovery-flow unit; the backend change is safe to deploy first since the
  frontend gracefully handles the absence of `unverified` (it reads as falsy)
- **Rollback**: revert model and handler changes; `unverified` field disappears from
  response; frontend falls back to GAP-0109 dead-end state (no regression beyond status quo)
- **Risk**: low — additive change; no writes; rate-limiting already in place; the one
  minor information-disclosure trade-off (confirming an email was used in an abandoned
  registration) is accepted as less harmful than the broken UX it resolves
