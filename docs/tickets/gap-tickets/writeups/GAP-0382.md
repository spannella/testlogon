# GAP-0382: Ad impression recording has no deduplication — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`. No prior investigation doc exists for this GAP.

## 1. Summary & Classification

- **Plain-English statement**: The `record_ad_impression` function writes every call unconditionally to DynamoDB with a sort key that includes the current Unix timestamp (`VIDEO#{video_id}#{user_id}#{ts}`), meaning a single authenticated user can call `POST /{video_id}/ad-impression` with `event_type=complete` an unlimited number of times on the same video within a single day, each time triggering a separate billing ledger credit to the creator. There is no per-user-per-slot-per-day deduplication guard of any kind.
- **Severity**: HIGH — direct financial impact. The VOD-018 security section (§6.2) explicitly requires impression deduplication. A malicious viewer (or a compromised account) can inflate creator ad revenue and drain advertiser budgets without bound.
- **Source ticket**: VOD-018. **Status**: Open. **Owning area**: VOD / Ad Billing.
- **Claim verification**: CONFIRMED. `app/services/ad_placement.py:233-287` contains the full `record_ad_impression` function. There is no `ConditionExpression`, no prior-existence check, and no per-user-per-slot lookup before writing. The sort key `f"VIDEO#{video_id}#{user_id}#{ts}"` is unique per millisecond, so every call produces a new item.
- **Related tickets**: GAP-0381 (placeholder creatives), GAP-0074 (attribution race), SEC-013 (economic/business logic abuse).

## 2. Current-State Investigation (root cause)

### The write path

`app/services/ad_placement.py:233-287` — `record_ad_impression`:

```python
def record_ad_impression(
    *, video_id: str, user_id: str, slot_type: str, slot_index: int,
    creative_id: str = "", event_type: str = "impression",
) -> Dict[str, Any]:
    ts = now_ts()
    event_id = f"adimp_{uuid.uuid4().hex}"

    # Write impression record
    try:
        T.ad_impressions.put_item(
            Item={
                "pk": f"AD_IMP#{_date_str(ts)}",
                "sk": f"VIDEO#{video_id}#{user_id}#{ts}",   # ← timestamp in SK = infinite inserts
                ...
                "event_type": event_type,
            }
        )
    except Exception:
        logger.warning("ad_impression_write_failed", ...)

    # On complete: credit creator with ad revenue
    if event_type == "complete":
        _credit_ad_revenue(video_id=video_id, event_id=event_id, ts=ts)

    return {"ok": True, "event_id": event_id}
```

Key observations:
1. **No guard before `put_item`**: the function never queries whether a `complete` event for `(video_id, user_id, slot_index, date)` already exists.
2. **Timestamp-based SK**: `f"VIDEO#{video_id}#{user_id}#{ts}"` is unique per second (since `now_ts()` returns integer seconds). Two calls within the same second would overwrite each other (idempotent by accident), but any two calls in different seconds both succeed and both trigger `_credit_ad_revenue`.
3. **`put_item` without `ConditionExpression`**: DynamoDB's unconditional `put_item` never raises `ConditionalCheckFailedException` — it is the wrong operation for deduplication.
4. **Revenue credit path**: `_credit_ad_revenue` at `app/services/ad_placement.py:290-?` writes a `new_ledger_entry` (billing debit/credit) and increments `ad_revenue_cents` on the video record every time it is called.

### Router wiring

The router endpoint is at `app/routers/video_listing.py:1470-1491`:

```python
@router.post("/{video_id}/ad-impression", response_model=AdImpressionOut)
def record_ad_impression_endpoint(video_id: str, body: AdImpressionIn, user=Depends(require_ui_session)):
    ...
```

No rate limiting, no daily quota, no idempotency key. Any authenticated session can POST to this endpoint in a tight loop.

### Why the deduplication key proposed in the ticket is correct

The GAP ticket proposes the DDB item key:

```
AD_IMP#{date}#USER#{user_id}#VIDEO#{video_id}#SLOT#{slot_index}
```

as the deduplication record. This correctly captures the business invariant: one credit per slot per user per video per calendar day. Using this as both the `pk` and a deterministic `sk` allows a DynamoDB conditional write (`attribute_not_exists(pk)`) to atomically check-and-insert in a single round-trip, with no race condition.

## 3. Impact / Exploit / Blast Radius

### Concrete exploit walkthrough

1. Attacker (or malicious creator-side script posing as a viewer) obtains any valid UI session cookie (e.g., by registering a free account).
2. Identifies a video with `access_mode=ad_supported` owned by a creator they wish to enrich.
3. Writes a simple loop:
   ```bash
   for i in $(seq 1 10000); do
     curl -s -X POST "https://platform/ui/videos/{video_id}/ad-impression" \
       -H "Cookie: ui_session=..." -H "x-csrf-token: ..." \
       -d '{"slot_type":"pre_roll","slot_index":0,"event_type":"complete","creative_id":"dev_ad_preroll_15s"}'
     sleep 0.1
   done
   ```
4. Each call succeeds with `{"ok": true, ...}` and credits the creator `max(1, CPM // 1000)` cents (with `VOD_AD_CPM_CENTS=500`, that is 0 cents due to integer rounding, but with `CPM=1000`, it is 1 cent per call; an attacker targeting premium ad slots at higher CPM rates would see material credits).
5. With CPM at $5 (default), `CPM // 1000 = 0`, so `max(1, 0) = 1 cent` per `complete` event. 10,000 calls = $100 credited to the creator. With CPM at $50 (premium), each call credits 5 cents → 10,000 calls = $500.

### Financial worst case

At the platform's default rate of $5 CPM (500 cents), the per-call credit rounds down to the floor of 1 cent. A single attacker running 86,400 calls per day (one per second) would credit a creator $864/day using a single authenticated account. With multiple accounts (or no rate limit), the ceiling is unbounded.

### Data integrity

Every fraudulent `complete` event also increments `ad_impression_count` and `ad_revenue_cents` on the video metadata record (`video_listing.py:1439`), corrupting the creator analytics dashboard. Even after the billing fraud is reversed, the counters cannot be easily corrected.

### Scope

- Any ad-supported video on the platform is vulnerable.
- The exploit requires only an authenticated session (no admin rights).
- In production the deduplication gap exists from the moment VOD-018 goes live.

## 4. Fix Design (code-level)

### 4.1 Deduplication via a deterministic DDB key and conditional write

The canonical fix is a two-table approach that mirrors the idempotency pattern used elsewhere in the codebase (e.g., `achievement_definitions.py:68` uses `attribute_not_exists`):

**Step 1 — Compute the deduplication key.** For `event_type == "complete"`, construct a deterministic DDB key that encodes the invariant "one credit per slot per user per video per day":

```python
_DEDUP_PK_COMPLETE = "AD_DEDUP#{date}#USER#{user_id}#VIDEO#{video_id}#SLOT#{slot_index}"
```

**Step 2 — Attempt a conditional write to the deduplication table before crediting revenue.** Use `ConditionExpression="attribute_not_exists(pk)"`:

```python
from botocore.exceptions import ClientError

def _try_claim_impression_slot(
    *, date_str: str, user_id: str, video_id: str, slot_index: int, event_id: str, ts: int
) -> bool:
    """Attempt to claim a completion slot for deduplication.
    Returns True if the claim was new (should credit), False if already seen."""
    dedup_pk = f"AD_DEDUP#{date_str}#USER#{user_id}#VIDEO#{video_id}#SLOT#{slot_index}"
    try:
        T.ad_impressions.put_item(
            Item={
                "pk": dedup_pk,
                "sk": "DEDUP",
                "event_id": event_id,
                "created_at": ts,
                "ttl": ts + 86400 * 2,   # 48 h TTL to auto-expire dedup records
            },
            ConditionExpression="attribute_not_exists(pk)",
        )
        return True
    except ClientError as e:
        if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
            return False
        raise
```

**Step 3 — Gate `_credit_ad_revenue` on the deduplication result.** In `record_ad_impression`:

```python
if event_type == "complete":
    date_str = _date_str(ts)
    is_new = _try_claim_impression_slot(
        date_str=date_str, user_id=user_id, video_id=video_id,
        slot_index=slot_index, event_id=event_id, ts=ts,
    )
    if is_new:
        _credit_ad_revenue(video_id=video_id, event_id=event_id, ts=ts)
    else:
        logger.info(
            "ad_impression_duplicate_skipped",
            extra={"video_id": video_id, "user_id": user_id, "slot_index": slot_index},
        )
```

**Step 4 — Add TTL attribute to `AdImpressions` table.** TTL must be enabled on the table. Update `scripts/local-ddb-init.py` to set TTL on the `AdImpressions` table (no schema change needed — TTL is configured at the table level, not per-item). In production, enable DynamoDB TTL on the `AdImpressions` table via Terraform/CloudFormation pointing at the `ttl` attribute.

### 4.2 Impression (`impression`) and `skip` event types

The deduplication requirement in VOD-018 §6.2 targets `complete` events (which trigger revenue). Impression and skip events are informational telemetry and can remain idempotent-write. However, to prevent runaway counter inflation, consider also capping the total `impression` events per slot per user per video per day to a small number (e.g., 3) using an `ADD` atomic counter with a DDB `UpdateItem` condition `#c < :max`. This is lower priority and should be tracked as a follow-on.

### 4.3 Dev/Prod parity (SECOPS-007)

The fix uses only `T.ad_impressions`, which is a DynamoDB table backed by DynamoDB Local in dev (`DDB_ENDPOINT_URL=http://localhost:8001`) and by real AWS DynamoDB in production. The same `put_item` with `ConditionExpression` works identically in both environments — moto and DynamoDB Local both support `ConditionalCheckFailedException`. No feature flag gating is needed; the deduplication is strictly stricter behavior that should be active everywhere.

### 4.4 Backward compatibility

Dedup records written on day D expire after 48 hours. Users who legitimately watch the same video on consecutive days (day D and day D+1) will see a fresh dedup record on D+1 and receive a new credit. This is the intended behavior per the VOD-018 spec.

### Regression test (fails before fix, passes after)

Add to `tests/test_ad_placement.py`:

```python
class TestAdImpressionDeduplication:
    def test_complete_event_credits_once_per_day(self, ddb_tables):
        """GAP-0382: calling record_ad_impression with event_type=complete
        twice for the same user+video+slot on the same day should credit
        revenue exactly once, not twice."""
        from app.services.ad_placement import record_ad_impression

        _seed_video(ddb_tables, "v_dedup1", access_mode="ad_supported")

        # First call — should credit
        result1 = record_ad_impression(
            video_id="v_dedup1", user_id="bob",
            slot_type="pre_roll", slot_index=0,
            creative_id="dev_ad_preroll_15s", event_type="complete",
        )
        assert result1["ok"] is True

        # Second call — same slot same day — should be a no-op for billing
        result2 = record_ad_impression(
            video_id="v_dedup1", user_id="bob",
            slot_type="pre_roll", slot_index=0,
            creative_id="dev_ad_preroll_15s", event_type="complete",
        )
        assert result2["ok"] is True  # API still returns ok (not an error)

        # Revenue should have been credited exactly once
        video_item = ddb_tables.Table("VideoMetadata").get_item(
            Key={"video_id": "v_dedup1"}
        ).get("Item", {})
        first_revenue = int(video_item.get("ad_revenue_cents", 0))
        assert first_revenue > 0, "First complete event should have credited revenue"

        # Call again and confirm revenue does not increase further
        record_ad_impression(
            video_id="v_dedup1", user_id="bob",
            slot_type="pre_roll", slot_index=0,
            creative_id="dev_ad_preroll_15s", event_type="complete",
        )
        video_item2 = ddb_tables.Table("VideoMetadata").get_item(
            Key={"video_id": "v_dedup1"}
        ).get("Item", {})
        second_revenue = int(video_item2.get("ad_revenue_cents", 0))
        assert second_revenue == first_revenue, (
            f"Revenue should not increase on duplicate complete events: "
            f"was {first_revenue}, now {second_revenue}"
        )

    def test_different_users_each_credited(self, ddb_tables):
        """Two different users completing the same ad slot should each
        trigger an independent revenue credit."""
        from app.services.ad_placement import record_ad_impression

        _seed_video(ddb_tables, "v_dedup2", access_mode="ad_supported")

        record_ad_impression(
            video_id="v_dedup2", user_id="alice",
            slot_type="pre_roll", slot_index=0, event_type="complete",
        )
        record_ad_impression(
            video_id="v_dedup2", user_id="bob",
            slot_type="pre_roll", slot_index=0, event_type="complete",
        )

        # Both users contributed, so revenue should reflect two credits
        video_item = ddb_tables.Table("VideoMetadata").get_item(
            Key={"video_id": "v_dedup2"}
        ).get("Item", {})
        revenue = int(video_item.get("ad_revenue_cents", 0))
        assert revenue >= 2, (
            "Both user impressions should have been credited independently"
        )

    def test_different_slots_each_credited(self, ddb_tables):
        """A user completing slot 0 and slot 1 should credit revenue twice."""
        from app.services.ad_placement import record_ad_impression

        _seed_video(ddb_tables, "v_dedup3", access_mode="ad_supported")

        record_ad_impression(
            video_id="v_dedup3", user_id="bob",
            slot_type="pre_roll", slot_index=0, event_type="complete",
        )
        record_ad_impression(
            video_id="v_dedup3", user_id="bob",
            slot_type="mid_roll", slot_index=1, event_type="complete",
        )

        video_item = ddb_tables.Table("VideoMetadata").get_item(
            Key={"video_id": "v_dedup3"}
        ).get("Item", {})
        revenue = int(video_item.get("ad_revenue_cents", 0))
        assert revenue >= 2
```

### Rollback

The fix is additive: it writes a new item to an existing DynamoDB table. If the fix is reverted, the dedup records remain in DynamoDB but no code reads them, so they are inert and will TTL-expire within 48 hours.

### Risks

- **DynamoDB Local TTL**: DynamoDB Local does not automatically expire TTL items (it is advisory). This does not affect correctness in dev; the conditional write still works.
- **Clock skew**: `_date_str(now_ts())` uses UTC. If the server clock is skewed, a call at midnight could appear to land on a different day than the dedup record. This is an acceptable edge case (at worst, one extra credit is issued at a day boundary).
