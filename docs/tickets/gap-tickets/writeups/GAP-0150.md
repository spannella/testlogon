# GAP-0150: No Pytest Unit Tests for Group Call Service — Remediation Write-up

> ~5 pages. Source ticket: CALL-012. No investigation doc exists; code verified directly.

## 1. Summary & Classification

**Claim verification: CONFIRMED.**  The gap ticket states that `tests/test_group_calls.py` does not exist and that the group call service functions are entirely untested at the unit level.  Both assertions are correct: `ls tests/` confirms the file is absent, and the test files that do exist (`test_call_billing.py`, `test_call_recording.py`, `test_messaging_call_lifecycle.py`, etc.) contain no imports from `app.services.group_call_service`.

`app/services/group_call_service.py` (501 lines) implements `create_group_call`, `join_call`, `leave_call`, `end_call`, `relay_signal`, and `update_media_state` — all of which perform DynamoDB writes, enforce authorization rules, and have multiple error paths.  None of these code paths are covered by any automated test.

**Severity**: HIGH — untested service code in a billing-adjacent, multi-participant feature.  Regressions in participant counting, capacity enforcement, auto-end logic, or authorization checks would be invisible until E2E tests (which themselves require the full running stack) catch them.

## 2. Current-State Investigation (Root Cause)

### 2.1 Service Functions and Their Complexity

`app/services/group_call_service.py`:

| Function | Lines | DDB ops | Key invariants to test |
|----------|-------|---------|------------------------|
| `create_group_call` | 74–123 | 1 write | Feature flag check; group size ≥ 3; no existing active call; participant membership |
| `get_call` | 126–129 | 1 read | Returns `None` for missing call |
| `get_active_call_for_conversation` | 132–143 | 1 query (GSI) | Filters non-META rows; returns `None` when no active call |
| `join_call` | 162–232 | 3 writes | Capacity enforcement; rejoin idempotency; `start_ts` set on first join; participant-count increment |
| `leave_call` | 235–277 | 2 writes | Count decrement; auto-end when count reaches 0 |
| `end_call` | 280–306 | triggers `_end_call_internal` | Creator-or-admin-only authorization; duration calculation; participant count |
| `update_media_state` | 374–406 | 1 read + 1 write | Screen-share conflict detection; partial update (only specified fields change) |
| `relay_signal` | 417–444 | in-memory only (dev) | Sender/target must be active participants |

### 2.2 `_get_conversation_participant_ids` — Monkeypatch Target

`group_call_service.py:49–61`:

```python
def _get_conversation_participant_ids(conversation_id: str) -> set[str]:
    tbl_parts = _participants_table()
    resp = tbl_parts.query(
        IndexName="GSI1",
        KeyConditionExpression=Key("GSI1PK").eq(conversation_id),
    )
    items = resp.get("Items") or []
    return {
        str(item.get("user_id") or item.get("participant_id") or "").strip()
        for item in items
        if str(item.get("status") or "").strip() in ("active", "")
    }
```

This function queries a separate `Participants` table using an env-var-resolved table name (`DDB_PARTICIPANTS`, default `"Participants"`).  The `Participants` table is not the `GroupCallSessions` table that moto can easily create in-test.  The gap ticket and CALL-012 spec both note that `monkeypatch` (or `unittest.mock.patch`) is the appropriate tool: replace `_get_conversation_participant_ids` with a stub that returns a pre-configured set of user IDs.

### 2.3 DynamoDB Table Schema

`scripts/local-ddb-init.py:1329–1339` defines the `GroupCallSessions` table:

- PK: `pk` (String, e.g., `"CALL#gc_abc123"`)
- SK: `sk` (String, either `"META"` or `"PART#{user_id}"`)
- GSI `ByConversationCreatedAt`: PK=`conversation_id`, SK=`created_at` (Number)
- GSI `ByStateCreatedAt`: PK=`state`, SK=`created_at` (Number)
- `attr_types={"created_at": "N"}` — required for DynamoDB numeric GSI keys

A test fixture must replicate this schema using moto, including the two GSIs and `attr_types`.

### 2.4 Settings Dependency

`create_group_call` reads `S.group_calls_enabled` and `S.group_call_max_participants` from `app.core.settings.S`.  Tests must either monkeypatch the settings object or set the corresponding env vars in the test fixture:

- `GROUP_CALLS_ENABLED=1`
- `GROUP_CALL_MAX_PARTICIPANTS=8`
- `DDB_GROUP_CALL_SESSIONS=GroupCallSessions` (or the table name used in the fixture)

### 2.5 `_emit_timeline` Side Effect

`join_call`, `leave_call`, `end_call`, and `_end_call_internal` call `_emit_timeline`, which internally imports and calls `emit_call_timeline_event` from `app.services.messaging_call_timeline`.  This in turn touches the `Messages` DynamoDB table.  For unit tests that focus on group call logic, `_emit_timeline` should be patched to a no-op.  The existing pattern in `tests/test_call_billing.py` patches individual service functions rather than entire modules; the same approach applies here.

## 3. Impact / Blast Radius

**Testing gap**: The six core service functions are entirely unvalidated at the unit level.  Developer changes to participant counting, capacity logic, state transitions, or authorization checks will not be caught until E2E tests run — which require the full dev stack and take significantly longer than pytest.

**Risk surface**:
- `join_call` participant-count increment: an off-by-one or race condition in the update expression would cause incorrect counts, potentially allowing over-capacity or under-counting.
- `leave_call` auto-end: if `current <= 0` check is wrong, calls may never auto-end (resource leak in DDB and any real WebRTC infrastructure).
- `end_call` authorization: a bug in the `role not in ("ADMIN", "ROOT")` check could allow any user to end others' calls.
- `create_group_call` group-size check (`len(participant_ids) < 3`): boundary condition — a 2-participant conversation should be rejected; a 3-participant conversation should succeed.

**Compounding factor**: The `useGroupCall.ts` frontend hook is also absent (CALL-012 critical gap).  Without both the hook and the service tests, the entire group call feature has no automated quality coverage at any layer.

### 4.2 Fixture Notes

- The `ddb_table` fixture uses `mock_aws()` context manager (moto v4 API).
- `_patch_table` injects the moto table handle directly into `group_call_service._table`.  This is cleaner than patching env vars and relying on the module-level `_table()` factory to resolve the name at call time.
- `_patch_participants` and `_patch_timeline` are `autouse=True` so every test gets them without extra decoration.
- The settings-reload test (`test_create_group_call_disabled_raises`) must reload the module to pick up the env var change.  This is an acceptable pattern for feature-flag tests.

### 4.3 Dev/Prod Parity (SECOPS-007)

All DynamoDB operations in `group_call_service.py` use the standard boto3 resource pattern against a table resolved from settings.  moto intercepts these calls identically to how it works in other test files (`test_call_billing.py`, `test_call_recording.py`).  No AWS-specific paths or mock branches exist in the service code — the same code runs in dev and production.
