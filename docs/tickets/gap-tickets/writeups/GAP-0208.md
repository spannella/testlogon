# GAP-0208: Chargeback Not Auto-Recorded from Stripe Webhook — Remediation Write-up

> ~5 pages. Fix-oriented. Code verified against the live tree; all `file:line` citations confirmed.

## 1. Summary & Classification

**Gap**: The Stripe webhook handler in `app/routers/billing.py` handles `charge.dispute.funds_withdrawn` and `charge.dispute.funds_reinstated` events (lines 1490–1543) for financial ledger purposes, but never handles the primary `charge.dispute.created` event that should trigger `fd.record_chargeback()`. As a result, the fraud-detection engine's chargeback counter is never incremented from live Stripe events — only from manual admin POSTs to `/v1/admin/fraud/chargebacks`.

- **Severity**: HIGH — the automated chargeback threshold rule in the fraud engine is perpetually blind; the `chargeback_threshold` auto-flag only fires on manual admin input, not on real events.
- **Source ticket**: FIN-015 (`docs/tickets/FIN-015-fraud-detection-dashboard.md`)
- **Status**: Open
- **Owning area**: Billing / Fraud & Risk
- **Verdict**: Claim CONFIRMED with a precision correction. The GAP ticket cites line 687 as the location; line 687 is actually inside `billing_config()` (an unrelated GET endpoint). The real location is the `stripe_webhook` function starting at line 1248 and specifically the `elif event_type.startswith("charge.dispute.")` branch at line 1464. The claim itself is correct: `charge.dispute.created` is not handled and `fd.record_chargeback` is never called from the webhook.
- **Related tickets**: GAP-0207 (fraud eval not called), FIN-015, SECOPS-007

## 2. Current-State Investigation (root cause)

### 2.1 The Stripe webhook handler

`app/routers/billing.py:1248` defines `stripe_webhook` at `POST /api/stripe/webhook`. The handler dispatches on `event["type"]`. The complete dispatch table as of the current code:

| `event_type` prefix/value | Handled | Action |
|---|---|---|
| `setup_intent.succeeded` | Yes (line 1266) | Attach payment method to customer |
| `payment_intent.*` | Yes (line 1332) | Update payment status, sync purchase history |
| `charge.dispute.funds_withdrawn` | Yes (line 1490) | Ledger adjustment, mark_reverted |
| `charge.dispute.funds_reinstated` | Yes (line 1520) | Ledger reversal |
| `charge.dispute.created` | **No** | **Nothing** |
| `charge.dispute.updated` | **No** | **Nothing** |
| `charge.dispute.closed` | **No** | **Nothing** |

The `charge.dispute.created` event is the canonical Stripe webhook fired when a cardholder opens a dispute (chargeback). It fires before `funds_withdrawn`, which arrives only after the card network confirms the fund movement (typically days later).

### 2.2 The `fd.record_chargeback` function

`app/services/fraud_detection.py:512`:

```python
def record_chargeback(*, user_id: str, amount_cents: int = 0, tx_id: str = "") -> Dict[str, Any]:
    """Increment a user's chargeback count and auto-flag over threshold."""
    resp = T.fraud_cases.update_item(
        Key={"pk": f"RISK#USER#{user_id}", "sk": "SCORE"},
        UpdateExpression="SET chargeback_count = if_not_exists(chargeback_count, :z) + :one",
        ExpressionAttributeValues={":z": Decimal("0"), ":one": Decimal("1")},
        ReturnValues="ALL_NEW",
    )
    cb_count = int(resp.get("Attributes", {}).get("chargeback_count", 0))
    config = get_fraud_config()
    threshold = config.get("chargeback_threshold", CHARGEBACK_THRESHOLD)
    ...
    if cb_count >= threshold:
        auto_flag(...)   # creates FLAG row for review queue
```

The function performs an atomic increment on the `RISK#USER#{user_id}` row in the `fraud_cases` table and auto-creates a fraud flag if the chargeback count reaches the configured threshold (default 3). It is currently only reachable via the admin-only endpoint `POST /v1/admin/fraud/chargebacks`.

### 2.3 User resolution from a dispute event

The `charge.dispute.*` handler (line 1464–1543) already resolves `user_id` from the Stripe event by:
1. Retrieving the `Charge` object (`stripe.Charge.retrieve(charge_id)`)
2. Looking up `customer_id` on the charge
3. Calling `user_id_from_customer(customer_id)` — the local DDB lookup that maps Stripe customer IDs to app user IDs

This resolution logic is already present and working for `funds_withdrawn`. The fix does not need to add new resolution code.

### 2.5 The second Stripe webhook endpoint

The codebase has a second Stripe webhook endpoint at `app/routers/billing.py:1559` (`POST /api/billing/webhooks/stripe`) which handles payment incident events (disputes, chargebacks, payment failures) using the `PaymentIncidentTransitionService`. This endpoint does handle `charge.dispute.*` events in its own pipeline (via the `StripePaymentIncidentAdapter`). However, this is the payment-incident tracking system — a separate workflow for managing dispute evidence and response submissions. It does not call `fd.record_chargeback`. The fraud-detection chargeback counter must still be incremented from the primary `stripe_webhook` handler at line 1248 so that the `chargeback_check` rule in `evaluate_transaction` has accurate data.

## 3. Impact / Exploit / Blast Radius

**Scenario**: A user performs a purchase, then files a chargeback with their card issuer. Stripe fires `charge.dispute.created`. The billing router receives the event but falls through to the final `return {"received": True}` without any fraud action. The user can continue transacting normally.

If the same user files a second and third chargeback, the `chargeback_count` in DynamoDB remains at 0. The `chargeback_check` in `evaluate_transaction` (`fraud_detection.py:182`) reads this value and returns no violation. The user's risk score has no chargeback component.

**Financial impact**: Each chargeback incurs a Stripe chargeback fee (typically $15–$25). Multiple chargebacks from the same user are the primary signal for fraudulent users exploiting the platform. Without automated recording, the platform has no way to auto-detect repeat offenders.

**Compliance impact**: Payment processor agreements (Stripe, card networks) require merchants to monitor and respond to chargeback rates. Failure to track chargebacks per-user contributes to exceeding the network's dispute ratio thresholds (Visa: 0.9%, Mastercard: 1.0%), which can result in increased fees, remediation programs, or account termination.

**Blast radius**: All users on the platform; financial and compliance exposure grows linearly with transaction volume.

## 4. Fix Design (code-level)

### 4.1 Add `charge.dispute.created` handling

Within the `stripe_webhook` function at `app/routers/billing.py:1248`, extend the existing `charge.dispute.*` branch to handle `charge.dispute.created`:

```python
# app/routers/billing.py  — import to add near other service imports
from app.services import fraud_detection as fd

# Inside stripe_webhook, within the charge.dispute.* branch (around line 1490):
        elif event_type == "charge.dispute.created":
            # Record chargeback for fraud-detection risk scoring.
            # user_id and pi_id already resolved above (lines 1472-1482).
            if user_id:
                try:
                    fd.record_chargeback(
                        user_id=user_id,
                        amount_cents=amount,
                        tx_id=pi_id or charge_id or "",
                    )
                    audit_event(
                        "billing_dispute_created",
                        user_id,
                        None,
                        outcome="info",
                        charge_id=charge_id,
                        payment_intent_id=pi_id,
                        amount_cents=amount,
                        currency=currency,
                        dispute_id=dispute.get("id"),
                    )
                except Exception:
                    logger.exception(
                        "record_chargeback_failed",
                        extra={"user_id": user_id, "charge_id": charge_id},
                    )
                    # Do not re-raise — chargeback processing must not block
                    # the webhook from returning 200. Stripe retries on non-2xx.
```

The placement is within the existing `elif event_type.startswith("charge.dispute.")` branch, after the `funds_reinstated` clause and before the final `return {"received": True}`.

### 4.2 Idempotency

Stripe may deliver `charge.dispute.created` more than once (retries on non-2xx, or network replay). The existing `mark_event_processed(event["id"])` call at `app/routers/billing.py:1261` provides deduplication at the webhook level — if the event ID has been seen before, the handler returns early with `{"received": True, "deduped": True}`. No additional idempotency guard is needed for `record_chargeback` itself, since double-counting a dispute would require a duplicate event ID, and the existing dedup gate at line 1261 prevents that.

However, if the `STRIPE_EVENT` deduplication table (`billing` table, `pk=STRIPE_EVENT`, `sk={event_id}`) itself has a TTL and the event is replayed after expiry (7 days, per line 675), the dedup would not prevent a second `record_chargeback` call. This is an extremely rare edge case for `charge.dispute.created` events (Stripe delivers them once and does not retry after 7 days), but should be documented as a known risk.

### 4.3 Dev/Prod parity (SECOPS-007)

In dev mode, the Stripe mock (`stripe-mock` on port 12111) does not fire webhooks. Dev testing of the webhook handler requires posting a synthetic event payload directly to `POST /api/stripe/webhook` with a mocked `stripe-signature`. Existing webhook tests already use this pattern.

`fd.record_chargeback` writes to `T.fraud_cases` which points to DynamoDB Local in dev. No AWS-specific behaviour is triggered. The function is safe to call in both environments.

The `audit_event` call uses the existing audit trail infrastructure, which is also environment-agnostic.

### 4.4 Alternatives considered

- **Handle `charge.dispute.updated` and `charge.dispute.closed`**: The `updated` event fires on status changes to the dispute (under review, won, lost). The `closed` event fires on resolution. Updating the chargeback count only on `created` is the correct approach — the count tracks "number of disputes opened", not dispute resolution outcomes. A "won" dispute should not decrement the counter (the user did initiate the dispute). Deferred.
- **Reverse the count on `dispute.closed` with `reason=won`**: Could decrement the counter when a dispute is decided in the merchant's favour. This is a separate enhancement, not required to close the gap.

### 5.5 Rollout and rollback

- **Effort**: S (< 0.5 day; surgical addition inside an existing webhook branch plus one new test file).
- **Rollback**: Removing the `charge.dispute.created` case from the webhook dispatch reverts to prior behaviour. No DDB schema change needed; any `chargeback_count` values already written to `fraud_cases` during the canary are inert.
- **Risk**: Low. The only state mutation is an atomic increment to a counter in the `fraud_cases` table. The `try/except` wrapper ensures that a DDB error in the fraud table never causes the webhook to return non-2xx (which would trigger Stripe retries for a non-fraud reason, double-recording the chargeback).
- **Sequencing**: Should ship alongside or before GAP-0207 (fraud gate on billing paths). If GAP-0207 ships first, the `chargeback_check` rule will read a `chargeback_count` of 0 for all users until this fix is deployed, making the chargeback rule ineffective. Deploy GAP-0208 first or simultaneously to ensure the fraud gate has accurate chargeback data from day one.
