# GAP-0069: Account Suspension Does Not Cascade to Pause Active Campaigns — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase 2026-06-05; claim is **confirmed**.

## 1. Summary & Classification

- **Severity**: HIGH
- **Source ticket**: ADS-018 · **Status**: Open
- **Owning area**: Backend / Admin Ad Platform (`app/services/admin_ad_platform.py:moderate_account`)
- **Verdict**: CONFIRMED. When an admin suspends an advertiser account via
  `moderate_account(action="suspend")`, the account's `status` field is set to `"suspended"` in
  the `ad_accounts` table, but all campaigns belonging to that account remain in `"active"`
  status in the `ad_campaigns` table. The ad serving engine lists campaigns by their own status
  (`list_campaigns_by_status("active")`), so those campaigns continue to be eligible for
  serving. The fraud-suspension check in `serve_ad` (line 83–87) reads account status, but it
  is invoked only via the fraud-prevention service and only for fraud-flagged accounts — not for
  admin-moderation suspensions.
- **Impact (financial + compliance)**: A suspended advertiser's budget continues to be charged,
  the platform continues to take its 30 % revenue share, and end-users continue to see that
  advertiser's creatives. This directly undermines the purpose of account suspension.
- **Related tickets**: GAP-0068 (global kill switch — complementary), GAP-0049 (platform
  revenue accounting), ADS-018 source ticket, SECOPS-007.

## 2. Current-State Investigation (root cause)

### `moderate_account` — the suspension code path

`app/services/admin_ad_platform.py:moderate_account` (lines 202–224):

```python
def moderate_account(
    *, account_id: str, action: str, admin_sub: str,
    reason: str = "", notes: str = "", request=None,
) -> Optional[Dict[str, Any]]:
    acct = get_ad_account(account_id)
    if not acct:
        return None
    prev_status = acct.get("status", "")
    # ad_accounts.review_ad_account maps approve→active, otherwise keeps decision.
    result = review_ad_account(account_id, admin_sub, action, notes or reason)
    if result is None:
        return None
    new_status = result["status"]
    _log_moderation(
        item_type="account", item_id=account_id, action=action,
        admin_sub=admin_sub, reason=reason, notes=notes,
        prev_status=prev_status, new_status=new_status, request=request,
    )
    return {"account_id": account_id, "admin_status": new_status, "status": new_status}
```

`review_ad_account` (`app/services/ad_accounts.py:58–76`) writes the new status to the
account's `META` item and returns. The function has no knowledge of campaigns; it touches only
the `ACCT#{account_id}` / `META` DynamoDB item.

**There is no code after line 215** (`result = review_ad_account(...)`) that iterates over
campaigns. The cascade is simply missing.

### `serve_ad` — the fraud-suspension check is insufficient

`app/services/ad_serving.py:83–87`:

```python
try:
    from app.services.ad_fraud_prevention import is_account_suspended
    if is_account_suspended(account_id):
        continue
except Exception:
    pass
```

`ad_fraud_prevention.is_account_suspended` (line 547–551):

```python
def is_account_suspended(account_id: str) -> bool:
    from app.services.ad_accounts import get_ad_account
    acct = get_ad_account(account_id)
    return bool(acct) and acct.get("status") == "suspended"
```

This check does stop a suspended account's campaigns from being selected — but only on each
`serve_ad` call, per-campaign iteration. It does **not** update the campaign's own status.
This has two failure modes:

1. **Performance**: every `serve_ad` call fetches the account record for every candidate
   campaign. With 200 active campaigns across 200 accounts, a single ad request requires 200
   DynamoDB `get_item` calls to the `ad_accounts` table. The current code already does this,
   but adding the admin-suspension check on top of it makes the latency worse, not better.
2. **Consistency**: the campaign's `status` field remains `"active"` in `ad_campaigns`. Any
   dashboard, report, or billing system that reads `list_campaigns_by_status("active")` will
   still list the suspended account's campaigns as active. The `ByStatusCreatedAt` GSI query
   returns those campaigns even after account suspension.

### Why a campaign-level status update is the correct fix

The proper fix is to set each active campaign's status to `"paused"` (or a new status
`"admin_suspended"`) at the time of account suspension. This:
- Makes the `ByStatusCreatedAt` GSI immediately accurate.
- Removes the O(n_campaigns) per-request DynamoDB reads for account status.
- Allows clean re-activation (change campaigns back to `"paused"` status, then advertiser can
  resume individually) when the account suspension is lifted.
- Is consistent with what advertisers see in their own campaign dashboard.

### `_CAMPAIGN_TRANSITIONS` — status machine allows `active → paused`

`app/services/ad_campaigns.py:16–24`:

```python
_CAMPAIGN_TRANSITIONS = {
    "draft": {"pending_review", "archived"},
    "pending_review": {"active", "rejected"},
    "active": {"paused", "completed", "archived"},
    "paused": {"active", "archived"},
    ...
}
```

`active → paused` is a valid transition. The cascade can use a direct DynamoDB `update_item`
rather than going through `update_campaign` (which requires a `CampaignUpdateIn` Pydantic
model) — a direct write bypasses the user-facing status-machine validation while staying
consistent with the DynamoDB schema.

## 3. Impact / Exploit / Blast Radius

### Concrete scenario

1. Advertiser account `acct_xyz` is found serving CSAM-adjacent creatives.
2. ROOT admin calls `POST /ui/admin/ad-platform/accounts/acct_xyz/moderate`
   with `{"action": "suspend", "reason": "policy violation"}`.
3. `moderate_account` sets `ad_accounts[ACCT#acct_xyz/META].status = "suspended"`.
4. The advertiser has 5 active campaigns, each with 3 approved creatives.
5. Those 15 campaign+creative combinations remain in `ad_campaigns` with `status="active"`.
6. `list_campaigns_by_status("active")` continues to return all 5 campaigns.
7. For the next `serve_ad` call: each campaign is iterated; the fraud-check's
   `is_account_suspended` call fetches the account — and does find `status="suspended"` and
   skips the campaign. So serving is *incidentally* blocked by the fraud check.

**Wait — does the fraud check save us?**

Partially, but not reliably:

- The fraud check is inside a `try/except Exception: pass` block. Any exception (DynamoDB
  unavailable, `ImportError`, coding error) causes the check to be **silently skipped**, and
  the suspended account's campaigns are served.
- The fraud check uses `is_account_suspended` from `ad_fraud_prevention`, not `ad_accounts`.
  If `ad_fraud_prevention` is ever refactored to use a separate "fraud-suspension" flag (rather
  than the shared `status` field), admin suspension would stop blocking ads.
- Campaign-level status remains `"active"` — billing, analytics, and reporting are still wrong
  even when the runtime block works.

### Financial impact

Even with the fraud check blocking runtime serving, the billing system reads campaign status
from `ad_campaigns`. If any billing process runs `list_campaigns_by_status("active")` for a
billing period that crosses the suspension timestamp, the suspended account's campaigns appear
active for that period. Whether this causes over-billing depends on the billing implementation,
but the data is inconsistent.

### Compliance / audit

Audit trails show account status as `"suspended"` but campaign status as `"active"`. An
external auditor reviewing the `ad_campaigns` table would see a mismatch. For GDPR/CCPA
compliance reviews, a suspended account's targeting data should not appear in any "active"
targeting query.

## 4. Fix Design (code-level)

### Approach

In `moderate_account`, after writing the suspension to the account record, scan the
`ad_campaigns` table for all `active` campaigns belonging to that account and update each to
`status="paused"` (with a `suspension_reason` annotation). Store the list of paused campaign
IDs in the moderation log entry.

On un-suspension (`action="approve"` or a new `action="unsuspend"`), the campaigns remain
`paused` — the advertiser must re-activate them manually, which is correct behaviour (they
should review their campaigns before resuming).

### Precise code change

**`app/services/admin_ad_platform.py` — `moderate_account` function (lines 202–224)**

Replace the existing function with:

```python
def moderate_account(
    *, account_id: str, action: str, admin_sub: str,
    reason: str = "", notes: str = "", request=None,
) -> Optional[Dict[str, Any]]:
    """Approve / reject / suspend an advertiser account.

    action ∈ {approve, reject, suspend}. Returns None if account not found.

    For action="suspend", all active campaigns belonging to the account are
    immediately paused (GAP-0069 fix). The paused campaign IDs are stored in
    the moderation log for audit and potential reversal.
    """
    acct = get_ad_account(account_id)
    if not acct:
        return None
    prev_status = acct.get("status", "")
    result = review_ad_account(account_id, admin_sub, action, notes or reason)
    if result is None:
        return None
    new_status = result["status"]

    paused_campaign_ids: List[str] = []
    if action == "suspend":
        # Cascade: pause all active campaigns for this account.
        paused_campaign_ids = _pause_account_campaigns(
            account_id=account_id,
            admin_sub=admin_sub,
            reason=reason or notes,
        )

    _log_moderation(
        item_type="account", item_id=account_id, action=action,
        admin_sub=admin_sub, reason=reason, notes=notes,
        prev_status=prev_status, new_status=new_status, request=request,
    )
    return {
        "account_id": account_id,
        "admin_status": new_status,
        "status": new_status,
        "paused_campaign_ids": paused_campaign_ids,
    }


def _pause_account_campaigns(
    *, account_id: str, admin_sub: str, reason: str = ""
) -> List[str]:
    """Set all active campaigns for account_id to status='paused'.

    Uses a direct DynamoDB update rather than update_campaign() to bypass the
    user-facing status-machine validation. The transition active→paused is
    valid per _CAMPAIGN_TRANSITIONS; only the validation layer is bypassed.

    Returns the list of campaign_ids that were paused.
    """
    ts = now_ts()
    paused: List[str] = []

    # list_all_campaigns scans ad_campaigns filtering by account_id;
    # status=active filter avoids touching already-paused/completed campaigns.
    campaigns = list_all_campaigns(account_id=account_id, status="active", limit=1000)

    for camp in campaigns:
        try:
            T.ad_campaigns.update_item(
                Key={"pk": camp["pk"], "sk": camp["sk"]},
                UpdateExpression=(
                    "SET #s = :paused, admin_paused_by = :admin, "
                    "admin_pause_reason = :reason, admin_paused_at = :ts, "
                    "updated_at = :ts"
                ),
                ExpressionAttributeNames={"#s": "status"},
                ExpressionAttributeValues={
                    ":paused": "paused",
                    ":admin": admin_sub,
                    ":reason": reason or "account suspended",
                    ":ts": ts,
                    ":active": "active",
                },
                ConditionExpression="#s = :active",  # idempotent: skip if already paused
            )
            paused.append(camp["campaign_id"])
            logger.info(
                "ad_campaign_suspended_cascade account_id=%s campaign_id=%s",
                account_id, camp["campaign_id"],
            )
        except T.ad_campaigns.meta.client.exceptions.ConditionalCheckFailedException:
            # Campaign was already paused/completed between list and update — safe to skip.
            pass
        except Exception:
            logger.error(
                "ad_campaign_suspend_cascade_failed account_id=%s campaign_id=%s",
                account_id, camp.get("campaign_id"),
            )

    return paused
```

### Dev/Prod parity (SECOPS-007)

| Concern | Dev | Prod |
|---|---|---|
| `T.ad_campaigns.update_item` | DynamoDB Local | AWS DynamoDB |
| `ConditionExpression` | Supported by DynamoDB Local 2.x | Supported |
| `list_all_campaigns` scan | Full table scan (small in dev) | Full table scan (acceptable for admin action) |
| `_log_moderation` | `T.ad_moderation_log` | Same |

No environment flags needed. The change is identical in both environments.

### Backward compatibility

- The `moderate_account` return dict gains a `paused_campaign_ids` field. The existing router
  (`AdminAdModerationResult` model) does not include this field; it should be added to
  `AdminAdModerationResult` in `app/models.py` as `Optional[List[str]] = None`.
- Campaigns already paused before this fix are unaffected.
- On un-suspension, campaigns remain `paused`. The advertiser's dashboard will show them as
  paused; they must click "Resume" on each one. This is intentional (review before resuming).

### Observability

- `logger.info("ad_campaign_suspended_cascade ...")` already in the fix — search this in logs
  after a suspension action to confirm cascade fired.
- `logger.error("ad_campaign_suspend_cascade_failed ...")` should page on-call if any campaign
  update fails; do not silently swallow errors in prod.

### Rollback

Revert `moderate_account` to the original single-line call to `review_ad_account`. Campaigns
that were paused by the cascade will remain paused; the advertiser must resume them manually.
There is no automated way to reverse the pauses without a second script.

### Migration

No DynamoDB schema changes. The three new fields written to campaign items
(`admin_paused_by`, `admin_pause_reason`, `admin_paused_at`) are optional attributes in
DynamoDB's schema-free model and require no table update.

### Risks

- **Large accounts**: an account with 1000 active campaigns will issue 1000 DynamoDB
  `update_item` calls in the suspension flow. This is an admin action that runs at most a few
  times per day; 1000 DDB writes at ~1ms each takes ~1 second. Acceptable. For very large
  deployments, consider batching with `asyncio.gather` or a background task.
- **Race condition**: between `list_all_campaigns` and each `update_item`, the advertiser could
  activate a new campaign. The `ConditionExpression="#s = :active"` guard catches this by
  checking the campaign is still active at write time. The new campaign would have to be
  re-paused manually in that edge case.

### Effort

**S** (Small) — one new helper function + 10-line modification to `moderate_account`. The test
suite is straightforward.
