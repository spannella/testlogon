# GAP-0328: Auto-revoke fires on any delivery failure, not only definitive 410/404 — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code before writing; cites `file:line`.

## 1. Summary & Classification

**Severity**: HIGH
**Source ticket**: PLATFORM-010
**Owning area**: Push notification delivery / device management
**Status**: Open — logic flaw confirmed in `app/services/push.py`

**Plain-English statement**: When a web-push delivery attempt fails, `send_push_for_alert()` unconditionally deletes the user's push device subscription from DynamoDB. The Web Push specification distinguishes between two types of failures: permanent failures (HTTP 410 Gone = subscription has been deliberately unsubscribed; HTTP 404 Not Found = subscription endpoint does not exist) and transient failures (network timeouts, 429 Too Many Requests, 500 Internal Server Error from the push service). The current code revokes the device on both permanent and transient failures, meaning a brief network outage or a push-service 500 error can silently delete all of a user's web-push subscriptions. They will stop receiving push notifications until they visit the site and re-grant push permission.

**Verdict**: Claim confirmed. The critical decision point is at `app/services/push.py:300–312`. The condition `if not success and not S.dev_mode` triggers revocation on *any* `False` return from `web_push_send()`, but `web_push_send()` returns `False` for all failure types — 410, 404, network timeout, 429, 500 — as confirmed by reading lines 220–235.

**Note**: The ticket refers to lines 300–310; the actual auto-revoke block spans lines 300–312. The description is accurate; only the precise line range is slightly off.

**Related tickets**: GAP-0330 (duplicates this finding for PLATFORM-016; the two tickets describe the same root-cause bug from different source audits), PLATFORM-010.

## 2. Current-State Investigation (root cause)

### `web_push_send()` — all failures return the same `False`

`app/services/push.py:142–235`:

The function returns a plain `bool`. All failure exit paths return `False`:

- **Line 221–222**: Non-2xx HTTP status from the push service (e.g., 400, 429, 500) → `return False`
- **Lines 227–229**: `WebPushException` with "410" or "Gone" in the message → logs "subscription expired (410)" → `return False`
- **Lines 231–233**: `WebPushException` with "404" → logs "subscription not found (404)" → `return False`
- **Lines 234–235**: Any other exception (network error, timeout, etc.) → logs the exception → `return False`

There is no way for the caller to distinguish between a permanent failure (device gone for good) and a transient one (push service temporarily unavailable).

### `send_push_for_alert()` — unconditional revoke on `False`

`app/services/push.py:293–312`:

```python
success = web_push_send(
    tok, title, body,
    url=url,
    tag=alert_type,
    alert_id=alert_id,
    alert_type=alert_type,
)
if not success and not S.dev_mode:
    # Check if subscription is likely expired -- attempt revoke
    try:
        sub = json.loads(tok)
        if "endpoint" in sub:
            revoke_push_device(user_sub, device_id)
            logger.info(
                "Auto-revoked stale push device: user=%s, device=%s",
                user_sub, device_id,
            )
    except (json.JSONDecodeError, TypeError):
        # Placeholder token -- ignore
        pass
```

The comment says "Check if subscription is *likely* expired" but the actual check is only that `tok` is valid JSON containing an `"endpoint"` key — a condition that is always true for a registered web-push subscription. So every valid web-push subscription that fails delivery for *any* reason is immediately deleted.

### Concrete failure scenarios that cause incorrect revocation

1. **Push service 500/503**: The push provider has a brief outage. All web-push sends return `False`. All active web-push subscriptions for every user who receives an alert during that window are deleted.
2. **Network timeout** (pywebpush raises `requests.Timeout`): The `except Exception` block at line 224 catches `Timeout`, logs the error, returns `False`. All matching subscriptions are revoked.
3. **HTTP 429 from push service**: The platform is sending too many pushes and the push service throttles them. Every throttled delivery revokes the subscription, accelerating the problem by eliminating future delivery attempts entirely.
4. **VAPID key rotation**: During a key rotation, all in-flight pushes will fail with a 401 or 403. All subscriptions are revoked, requiring every user to re-opt-in.

## 3. Impact / Exploit / Blast Radius

**Who is affected**: Any user with a registered web-push subscription who receives a push notification during a period of transient delivery failure.

**Blast radius in a real incident**:
- A 60-second push-service outage during which 1,000 alerts are dispatched results in up to 1,000 web-push subscriptions being permanently deleted.
- Users do not receive any in-app notification that their push subscription was revoked.
- Users must navigate to Settings → Notifications → re-enable push, then re-grant browser permission (which requires an explicit user gesture; it cannot be done programmatically).
- From a security perspective, silently downgrading a user from push notifications to no notifications reduces their visibility into security events (login from new device, MFA failure, etc.) — exactly the alerts that are most time-critical.

**Exploitability**: An attacker who can cause push-service errors (e.g., by flooding the push endpoint at the correct moment, or by exploiting a push-service vulnerability) can silently disable push notifications for targeted users, then proceed with account-takeover attempts that the user would normally have been alerted to.

**Financial**: No direct financial impact. Indirect: increased support burden as users report missing notifications.

## 4. Fix Design (code-level)

### 4.1 Introduce a typed result from `web_push_send()`

Replace the `bool` return type with a three-value enum or a named tuple that distinguishes outcome categories. Using a `str` enum is idiomatic and avoids adding a new class dependency:

```python
# app/services/push.py — add near the top of the file, after imports

from enum import Enum

class WebPushResult(str, Enum):
    OK = "ok"
    STALE = "stale"       # 410 Gone or 404 Not Found — revoke the subscription
    TRANSIENT = "transient"  # network error, 429, 5xx — do NOT revoke
```

### 4.2 Update `web_push_send()` to return `WebPushResult`

Change the return type annotation and all exit paths:

```python
def web_push_send(...) -> WebPushResult:
    ...
    # dev mode
    if S.dev_mode:
        ...
        return WebPushResult.OK

    try:
        ...
        if status in (200, 201, 202):
            return WebPushResult.OK
        elif status in (404, 410):
            logger.info("Web push permanent failure: status=%s, endpoint=%s",
                        status, endpoint[:80])
            return WebPushResult.STALE
        else:
            # 429, 5xx, etc.
            logger.warning("Web push transient failure: status=%s, endpoint=%s",
                           status, endpoint[:80])
            return WebPushResult.TRANSIENT

    except Exception as exc:
        exc_str = str(exc)
        if "410" in exc_str or "Gone" in exc_str:
            logger.info("Web push subscription expired (410): endpoint=%s",
                        endpoint[:80])
            return WebPushResult.STALE
        if "404" in exc_str:
            logger.info("Web push subscription not found (404): endpoint=%s",
                        endpoint[:80])
            return WebPushResult.STALE
        logger.exception("Web push send error (transient): endpoint=%s",
                         endpoint[:80])
        return WebPushResult.TRANSIENT
```

### 4.3 Update `send_push_for_alert()` to only revoke on `STALE`

Replace the `if not success` block with a discriminated check:

```python
result = web_push_send(
    tok, title, body,
    url=url,
    tag=alert_type,
    alert_id=alert_id,
    alert_type=alert_type,
)
if result == WebPushResult.STALE and not S.dev_mode:
    # Permanent failure (410/404): subscription is no longer valid.
    try:
        sub = json.loads(tok)
        if "endpoint" in sub:
            revoke_push_device(user_sub, device_id)
            logger.info(
                "Auto-revoked stale push device: user=%s, device=%s",
                user_sub, device_id,
            )
    except (json.JSONDecodeError, TypeError):
        pass
elif result == WebPushResult.TRANSIENT:
    # Transient failure: leave the subscription intact.
    logger.warning(
        "Transient push failure (not revoking): user=%s, device=%s",
        user_sub, device_id,
    )
```

### 4.4 Dev/Prod parity (SECOPS-007)

`web_push_send()` already short-circuits in `dev_mode` at line 192 (`return True` / now `return WebPushResult.OK`). Dev mode never reaches the pywebpush call, so the `WebPushResult` enum change does not alter dev-mode behaviour. The `if ... and not S.dev_mode:` guard in `send_push_for_alert()` (line 300) already prevents revocation in dev mode. The fix preserves this guard unchanged for the `STALE` path.

The `WebPushResult` enum is a pure Python enum with no DynamoDB, S3, or AWS dependency, so it behaves identically in dev and prod.

### 4.5 Backward compatibility

Any caller that currently checks `if not web_push_send(...)` must be updated to check `if result != WebPushResult.OK`. Searching the codebase confirms that `web_push_send()` is called in exactly one place: `send_push_for_alert()` at `push.py:293`. No other caller exists, so the change scope is contained to one file.

### 4.6 Alternatives considered

**Return a tuple `(bool, str)`**: e.g., `(False, "stale")` or `(False, "transient")`. Rejected in favour of the enum because the enum is self-documenting, type-checkable, and easier to extend (e.g., a future `RATE_LIMITED` value would be a one-line addition).

**Retry logic for transient failures**: a future improvement, but out of scope for this gap. The current fix only stops incorrect revocation; adding retries would require a job queue and is a separate feature.

## 5. Testing, Verification & Rollout

### Regression test (pytest offline)

Add to `tests/test_push.py`:

```python
import pytest
from unittest.mock import patch, MagicMock
from app.services.push import (
    WebPushResult,
    web_push_send,
    send_push_for_alert,
    revoke_push_device,
)


class TestWebPushResult:
    """GAP-0328: Only STALE (410/404) results should trigger device revocation."""

    def _make_subscription_tok(self) -> str:
        import json
        return json.dumps({
            "endpoint": "https://push.example.com/sub/abc123",
            "keys": {"p256dh": "AAAA", "auth": "BBBB"},
        })

    def test_transient_failure_returns_transient(self, mocker):
        """Non-410/404 exceptions must return TRANSIENT, not STALE."""
        mocker.patch("app.services.push.S", dev_mode=False,
                     vapid_private_key="key", vapid_public_key="pub",
                     vapid_subject="mailto:a@b.com")

        def _fake_webpush(**kwargs):
            raise ConnectionError("Connection refused")  # transient

        mocker.patch("app.services.push.webpush", side_effect=_fake_webpush)
        result = web_push_send(
            self._make_subscription_tok(), "T", "B"

        assert result == WebPushResult.TRANSIENT

        """410 Gone must return STALE."""
        mocker.patch("app.services.push.S", dev_mode=False,
                     vapid_private_key="key", vapid_public_key="pub",
                     vapid_subject="mailto:a@b.com")

        def _fake_webpush(**kwargs):
            raise Exception("Response 410 Gone: subscription expired")

        mocker.patch("app.services.push.webpush", side_effect=_fake_webpush)
        result = web_push_send(self._make_subscription_tok(), "T", "B")
        assert result == WebPushResult.STALE

    def test_404_returns_stale(self, mocker):
        """404 Not Found must return STALE."""
        mocker.patch("app.services.push.S", dev_mode=False,
                     vapid_private_key="key", vapid_public_key="pub",
                     vapid_subject="mailto:a@b.com")

            raise Exception("Response 404: not found")

        mocker.patch("app.services.push.webpush", side_effect=_fake_webpush)
        result = web_push_send(self._make_subscription_tok(), "T", "B")
        assert result == WebPushResult.STALE

    def test_transient_failure_does_not_revoke_device(self, mocker):
        """FAILS before fix: transient failure revokes device; PASSES after fix: no revocation."""
        import json

        mocker.patch("app.services.push.S",

                     web_push_enabled=True, fcm_enabled=False,
                     vapid_private_key="key", vapid_public_key="pub")

                     return_value={"push_event_types": ["new_message"]})
        mocker.patch("app.services.push.can_send_alert_channel", return_value=True)

        tok = self._make_subscription_tok()
        mocker.patch("app.services.push.T")
        from app.services.push import T as mock_T
        mock_T.push_devices.query.return_value = {"Items": [{
            "token": tok,
            "device_id": "dev1",
            "platform": "web",
        }]}

        revoke_mock = mocker.patch("app.services.push.revoke_push_device")
        mocker.patch("app.services.push.web_push_send",
                     return_value=WebPushResult.TRANSIENT)

        send_push_for_alert("user1", "new_message", "T", "B", "alert1")

        # BEFORE fix: revoke_push_device called once → assertion fails
        # AFTER fix:  revoke_push_device NOT called → assertion passes
        revoke_mock.assert_not_called()

    def test_stale_failure_does_revoke_device(self, mocker):
        """410 failure must still revoke the device after the fix."""
        import json

        mocker.patch("app.services.push.S",
                     dev_mode=False, push_enabled=True,
                     web_push_enabled=True, fcm_enabled=False,

        mocker.patch("app.services.push.get_alert_prefs",

        mocker.patch("app.services.push.T")

            "token": tok,
            "device_id": "dev1",
            "platform": "web",

        revoke_mock.assert_called_once_with("user1", "dev1")
```

**Fails before fix**: `test_transient_failure_returns_transient` returns `False` (not `WebPushResult.TRANSIENT`); `test_transient_failure_does_not_revoke_device` asserts `revoke_mock.assert_not_called()` but the mock is called.
**Passes after fix**: all five assertions pass.

### Manual QA steps

1. Register a web-push subscription in the dev browser.
2. Temporarily patch `web_push_send()` to raise `ConnectionError("network unreachable")`.
3. Trigger an alert that sends a push notification.
4. Confirm via DynamoDB Local Admin that the device row still exists after the failed send.
5. Revert the patch; confirm a successful send still works and the device row is updated.
6. Test the 410 path: patch `web_push_send()` to raise `Exception("Response 410 Gone")`; confirm the device IS deleted after the send.

### Rollout

- **Effort**: S (small — enum type + 3 exit paths changed + 1 conditional updated in caller)
- **Risk**: Low. Permanent failures (410/404) continue to revoke exactly as before; the change only prevents revocation on non-permanent failures.
- **Rollback**: Revert to `bool` return type and `if not success` condition.
- **Sequencing**: GAP-0328 and GAP-0330 are duplicate findings; they should be resolved by a single PR touching `app/services/push.py`. This write-up and the GAP-0330 write-up describe the same code-level fix.
