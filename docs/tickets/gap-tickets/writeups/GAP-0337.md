# GAP-0337: Zero Event Instrumentation in Any Router — Remediation Write-up

> Source ticket: PLATFORM-019 · Severity: HIGH · Effort: M · Status: Open

## 1. Summary & Classification

**Bug statement.** The analytics pipeline (PLATFORM-019) specified four raw event recording functions — `record_page_view`, `record_revenue_event`, `record_subscriber_event`, and `record_engagement_event` — that are called from key router endpoints to populate the `analytics_events` raw table used by the daily rollup engine. None of these functions exist, and none of the `record_*()` call sites are present in any router. The `analytics_events` service file is absent from `app/services/`. As a result, the entire analytics pipeline has no data source: the rollup job (if it existed) would always produce zero-valued metrics.

**Claim verdict: Confirmed, with scope correction.** The ticket cites only `app/routers/newsfeed.py` as the affected file. The actual scope is broader: the PLATFORM-019 gaps document (`docs/tickets/gaps/PLATFORM-019.md`, line 11) names `app/routers/newsfeed.py`, `app/routers/messaging.py`, and `app/routers/profile.py` as locations lacking `record_*()` calls. A codebase-wide grep confirms no `record_page_view`, `record_revenue_event`, `record_subscriber_event`, or `record_engagement_event` call exists in any file under `app/`. The newsfeed router does import and call a separate set of `record_newsfeed_feed_*` Prometheus-style metrics functions (from `app/metrics`) — these are operational request counters used for latency/error dashboards, not the analytics event records described in PLATFORM-019. They do not write to `T.analytics_events` or feed the daily rollup. This distinction is important: the newsfeed router is not entirely uninstrumented, but the analytics-specific `record_*()` calls documented in the ticket spec are absent.

**Severity and area.** HIGH / Analytics & Creator Monetisation. Without raw event data, no creator analytics metric — views, revenue, subscribers, engagement rate, top content — can ever reflect real activity. All `GET /ui/analytics/*` responses are computed from empty rollup tables and return zeros.

**Related tickets.** PLATFORM-019 (parent), GAP-0336 (refresh endpoint no-op — depends on rollup engine which depends on this data), companion PLATFORM-019 gaps "analytics_events.py service not implemented" and "analytics_events table not in DDB init". GAP-0337 depends on the `analytics_events.py` service being created first.

## 2. Current-State Investigation (root cause)

### Confirmed absence of the service module

```
$ ls app/services/ | grep analytics

```

There is no `analytics_events.py`. No `record_page_view`, `record_revenue_event`, `record_subscriber_event`, or `record_engagement_event` function exists anywhere under `app/`.

### What the newsfeed router does instrument (Prometheus counters, not analytics events)

`app/routers/newsfeed.py:29–36` imports from `app/metrics`:

```python
from app.metrics import (
    record_newsfeed_feed_budget_hit,
    record_newsfeed_feed_error,
    record_newsfeed_feed_filter_usage,
```

These are called at the feed query path (lines 5139–5214) for request counts, latency histograms, error rates, and filter usage. They do not write to DynamoDB and do not feed the analytics rollup engine. They are completely separate from the PLATFORM-019 analytics event system.

### The instrumentation points that are missing

Per the PLATFORM-019 ticket §5.3 (referenced in the gaps document), the following call sites must exist:

| Event type | Router | Trigger | Key fields |
|---|---|---|---|
| `page_view` | `newsfeed.py` `get_feed` | On successful feed response | `viewer_id`, `author_id`, `post_id` |
| `post_publish` | `newsfeed.py` `create_post` | After DDB write | `user_id`, `post_id`, `lock_type`, `has_media` |
| `post_like` | `newsfeed.py` `like_post` | After idempotent like write | `user_id`, `post_id`, `author_id` |
| `post_comment` | `newsfeed.py` `create_comment` | After comment write | `user_id`, `post_id`, `author_id` |
| `post_unlock` | `newsfeed.py` `unlock_post` | After successful payment | `user_id`, `post_id`, `author_id`, `amount_cents` |
| `revenue` | `newsfeed.py` `tip_post` | After billing ledger write | `user_id`, `recipient_id`, `amount_cents`, `source=tip` |
| `subscriber` | (subscriptions router) | On plan subscription | `user_id`, `creator_id`, `plan_id`, `amount_cents` |
| `page_view` | `profile.py` | On profile GET | `viewer_id`, `profile_user_id` |

Examining `like_post` at `app/routers/newsfeed.py:4527–4556` as a concrete example:

```python
def like_post(post_id: str, user_id: UserIdDep):
    post = ddb_get_item({"pk": pk_post(post_id), "sk": sk_post()})
    if not post:
        raise HTTPException(status_code=404, detail="Post not found")
    try:
        tbl.put_item(Item={...})
        ddb_update_item(
            key={"pk": pk_post(post_id), "sk": sk_post()},
            update_expr="SET like_count = if_not_exists(like_count, :z) + :one",
            expr_vals={":one": 1, ":z": 0},
            return_values="NONE",
        )
    except ClientError as exc:
        ...
    return {"ok": True}
```

There is no analytics event call here. The `like_count` on the post record is incremented (a denormalized counter used by the rollup service when querying post data), but no event row is written to `analytics_events` for time-series attribution.

### Why this matters for the rollup engine

`app/services/creator_analytics.py:78–96` queries rollup rows from `T.analytics_rollups`. Those rows are populated by `upsert_daily_rollup()`. The rollup engine (to be created as a companion gap) would aggregate raw `analytics_events` rows by `user_id` and `event_date` to compute the daily totals it then writes as rollup rows. Without raw event rows, every aggregation returns zero regardless of actual activity.

### Dev vs prod behaviour

The absence is identical in both environments. No dev-mode mock writes stub event rows. The impact in dev is limited to analytics E2E tests failing silently with zero values; in production it means creator dashboards always show zeros, permanently.

## 3. Impact / Exploit / Blast Radius

**All creator analytics metrics are zero.** Every creator using the platform sees:
- `total_views: 0` on Overview
- `total_revenue_cents: 0` on Revenue
- `subscriber_count: 0` on Subscribers
- `engagement_rate: 0.0` on Engagement

This is true regardless of actual activity. The engagement rate endpoint (`GET /ui/analytics/engagement`) uses `get_engagement_summary()` which reads from `T.analytics_rollups` — those rows are populated from raw events that never arrive.

**Creator trust and monetisation.** Creators set subscription prices, locked-post prices, and ad partnership rates based on analytics. All such decisions are made on fabricated zero data. A creator with 10,000 genuine views sees 0 in the dashboard.

**No security exploit.** This gap does not expose any data or allow unauthorized access. It is a functional completeness failure.

**Blast radius.** Every creator account on the platform. The gap has existed since PLATFORM-019 was first deployed. There is no partial functionality — all event types are absent, not just some.

## 4. Fix Design (code-level)

### Step 1: Create `app/services/analytics_events.py`

This is the prerequisite service. It must exist before any router can call `record_*()`.

```python
# app/services/analytics_events.py (new file)
"""Raw analytics event recording (PLATFORM-019 §5.3).

Writes one DynamoDB item per event to T.analytics_events for later
aggregation by the daily rollup engine.
"""
from __future__ import annotations
import logging
import uuid
from typing import Any, Dict, Optional

from app.core.tables import T
from app.core.time import now_ts

logger = logging.getLogger(__name__)

_TTL_DAYS = 90  # raw events retained 90 days


def _evt_id() -> str:
    return f"evt_{uuid.uuid4().hex}"


def _ttl(ts: int) -> int:
    return ts + _TTL_DAYS * 86400


def _write(event_type: str, user_id: str, fields: Dict[str, Any]) -> None:
    ts = now_ts()
    item: Dict[str, Any] = {
        "pk": f"USER#{user_id}",
        "sk": f"EVT#{ts}#{_evt_id()}",
        "GSI1PK": f"EVT#{event_type}",
        "GSI1SK": str(ts),
        "event_type": event_type,
        "user_id": user_id,
        "event_ts": ts,
        "ttl_epoch": _ttl(ts),
    }
    item.update(fields)
    try:
        T.analytics_events.put_item(Item=item)
    except Exception:
        logger.warning("analytics_events: failed to write %s for %s", event_type, user_id, exc_info=True)


def record_page_view(viewer_id: str, *, author_id: Optional[str] = None, post_id: Optional[str] = None) -> None:
    fields: Dict[str, Any] = {}
    if author_id:
        fields["author_id"] = author_id
    if post_id:
        fields["post_id"] = post_id
    _write("page_view", viewer_id, fields)


def record_revenue_event(user_id: str, *, recipient_id: str, amount_cents: int, source: str, post_id: Optional[str] = None) -> None:
    _write("revenue", user_id, {
        "recipient_id": recipient_id,
        "amount_cents": amount_cents,
        "source": source,
        **({"post_id": post_id} if post_id else {}),
    })


def record_subscriber_event(subscriber_id: str, *, creator_id: str, plan_id: str, amount_cents: int, action: str = "subscribe") -> None:
    _write("subscriber", subscriber_id, {
        "creator_id": creator_id,
        "plan_id": plan_id,
        "amount_cents": amount_cents,
        "action": action,
    })


def record_engagement_event(user_id: str, *, post_id: str, author_id: str, engagement_type: str) -> None:
    _write("engagement", user_id, {
        "post_id": post_id,
        "author_id": author_id,
        "engagement_type": engagement_type,  # "like", "comment", "share", "unlock"
    })
```

**`app/routers/newsfeed.py` — `tip_post` (line ~4589, after billing ledger write):**

The same pattern applies to `create_comment` (engagement_type="comment") and `unlock_post` (revenue event + engagement event).

### Dev/Prod parity (SECOPS-007)

`T.analytics_events` is a standard DynamoDB table. In dev it is DynamoDB Local; in production it is AWS DynamoDB. The `_write()` helper catches all exceptions and logs a warning, so a missing table in dev (before DDB init is updated) will log a warning rather than crashing the endpoint. The TTL field (`ttl_epoch`) is a standard DynamoDB TTL; in dev DynamoDB Local does not enforce TTL expiry (items are retained indefinitely), which is acceptable for development and testing. No mock bypass or feature flag is needed.

### Alternatives considered

- **Write analytics events synchronously vs via SQS:** Synchronous is simpler and sufficient at current scale. SQS fan-out is preferred at high traffic but introduces a dependency not present in the dev stack. The `try/except` guard ensures analytics failures never block the request path, making synchronous write safe.
- **Reuse existing `record_usage_event_and_aggregates` from `usage_metering.py`:** That function writes to the usage metering table (different schema, different purpose). Analytics events have a different key structure and TTL policy. Separate tables and service files are the right design.

### Observability

Add a counter `analytics_events_written_total{event_type}` incremented by each `_write()` call, and a counter `analytics_events_errors_total{event_type}` incremented on exception. ### Rollout & risks

- **Order of operations:** Create `analytics_events.py` and update `local-ddb-init.py` before deploying router call sites. A call site that fires before the table exists will catch the `ResourceNotFoundException` in `_write()` and log a warning — it will not crash.
- **Backfill:** Events before this fix are permanently lost. No backfill is possible from existing data because raw event history was never captured. The analytics dashboard will show accurate data only from the deployment date forward. Communicate this to creators.
- **Performance:** Each instrumented endpoint gains one additional DynamoDB `put_item` call on the critical path. The `try/except` wrapper ensures this never adds latency to the user-visible path on failure. On success, expect ~5ms of added latency at DynamoDB Local speeds; ~1–2ms in production with AWS DynamoDB in the same region.
- **Rollback:** Remove the `record_*()` calls from routers. The `analytics_events` table persists but accumulates no new rows.
- **Effort:** M — new service file (~70 lines), DDB table definition (~6 lines), call sites at ~8 router locations (~40 lines total), test file.
- **Sequence:** (1) `analytics_events.py` + DDB table, (2) router call sites, (3) rollup engine (companion gap), (4) wire refresh endpoint (GAP-0336).
