# GAP-0138: Orphaned Auto-Reply Rules on Bot Deletion — Remediation Write-up

> ~5 pages. Fix-oriented. Code verified against real implementation; all citations checked.

## 1. Summary & Classification

- **Plain-English statement**: When a bot is deleted via `delete_bot()` in `app/services/chat_bot.py`, the cascade deletes the bot's assignment records from `T.bot_assignments` but leaves all auto-reply rules stored under `PK=BOT#{bot_id}` in `T.chat_bots` untouched. These orphaned `RULE#*` items persist in DynamoDB indefinitely, consuming table capacity, and can be inadvertently returned by queries that scan `T.chat_bots` for `SK begins_with RULE#` if a new bot is ever assigned the same `bot_id` (extremely unlikely but theoretically possible due to UUID collision).
- **Severity**: HIGH — data leak and storage integrity defect. No cascade clean-up exists. The orphaned records are invisible to the creator (the bot is gone) but continue to occupy DDB capacity and muddy any audit/forensics of the `T.chat_bots` table.
- **Source ticket**: BOT-003 · **Status**: Open · **Owning area**: `app/services/chat_bot.py:167`, `app/services/bot_auto_reply.py`
- **Verdict from investigation**: **Claim confirmed.** `delete_bot()` at `chat_bot.py:167` queries `T.bot_assignments` to cascade-delete assignments, then deletes the primary bot record. It does not query or delete `RULE#` items in `T.chat_bots`. Auto-reply rules are stored in `T.chat_bots` under `PK=BOT#{bot_id}`, `SK=RULE#{rule_id}` (confirmed in `bot_auto_reply.py:41-58`). After `delete_bot()`, all RULE# items for that bot remain in the table.
- **Related tickets**: BOT-003 (parent), GAP-0136, GAP-0137 (siblings)

## 2. Current-State Investigation (Root Cause)

### 2.1 How auto-reply rules are stored

`create_auto_reply_rule()` at `app/services/bot_auto_reply.py:28` writes items to `T.chat_bots`:

```python
# app/services/bot_auto_reply.py:41-58
item: Dict[str, Any] = {
    "pk": f"BOT#{bot_id}",
    "sk": f"RULE#{rule_id}",
    "rule_id": rule_id,
    "bot_id": bot_id,
    "creator_id": creator_id,
    "trigger_pattern": trigger_pattern,
    "response_template": response_template,
    ...
}
T.chat_bots.put_item(Item=item)
```

The primary key is `PK=BOT#{bot_id}`, `SK=RULE#{rule_id}`. This is the same DynamoDB table (`T.chat_bots`) where the bot's main record lives under `PK=CREATOR#{creator_id}`, `SK=BOT#{bot_id}`.

### 2.2 The `delete_bot()` function

`delete_bot()` at `app/services/chat_bot.py:167`:

```python
# app/services/chat_bot.py:167-180
def delete_bot(*, creator_id: str, bot_id: str) -> bool:
    """Delete a bot and all its assignments."""
    bot = get_bot_for_owner(creator_id=creator_id, bot_id=bot_id)
    if not bot:
        return False

    # Delete all assignments first
    assignments = _query_all_assignments(bot_id=bot_id)
    for a in assignments:
        T.bot_assignments.delete_item(Key={"pk": a["pk"], "sk": a["sk"]})

    T.chat_bots.delete_item(Key={"pk": f"CREATOR#{creator_id}", "sk": f"BOT#{bot_id}"})
    logger.info("Bot deleted: bot_id=%s creator_id=%s", bot_id, creator_id)
    return True
```

The cascade covers `T.bot_assignments` items. There is no query for `T.chat_bots` items with `PK=BOT#{bot_id}` and `SK begins_with RULE#`. After `delete_bot()` completes:

- `CREATOR#{creator_id}` / `BOT#{bot_id}` → deleted (main bot record)
- All `BOT#{bot_id}` / `ASSIGN#*` in `T.bot_assignments` → deleted (assignments)
- `BOT#{bot_id}` / `RULE#*` in `T.chat_bots` → **NOT deleted** (orphaned)

### 2.3 Why the rule items use `PK=BOT#{bot_id}`

Bot auto-reply rules use `PK=BOT#{bot_id}` (not `PK=CREATOR#{creator_id}`) so that `list_auto_reply_rules(bot_id=bot_id)` can query by bot ID alone without knowing the creator ID. This is a valid table design choice but it means the rule items are indexed differently from the main bot record and are invisible to a query keyed on `CREATOR#{creator_id}`.

### 2.4 The `_query_all_assignments()` helper — only covers `T.bot_assignments`

```python
# app/services/chat_bot.py:376-380
def _query_all_assignments(*, bot_id: str) -> list[dict]:
    resp = T.bot_assignments.query(
        KeyConditionExpression=Key("pk").eq(f"BOT#{bot_id}"),
    )
    return resp.get("Items", [])
```

This function is correctly querying `T.bot_assignments`. There is no equivalent helper that queries `T.chat_bots` for `PK=BOT#{bot_id}` items. Creating one and calling it in `delete_bot()` is the fix.

### 2.5 Scale of the problem

A bot with `MAX_SCHEDULES_PER_BOT = 20` auto-reply rules and active usage will have up to 20 orphaned `RULE#` items per deleted bot. On a platform with 10,000 bot deletions over its lifetime, this is up to 200,000 orphaned items. Each item is approximately 400 bytes; at DynamoDB Local pricing (free) this is a testing non-issue, but in production DynamoDB each item incurs storage costs and query overhead.

### 2.6 GSI coverage of orphaned items

Auto-reply rules in `T.chat_bots` have `GSI1PK=BOT#{bot_id}`, `GSI1SK=RULE#{priority}#{rule_id}`. After bot deletion, these GSI entries also persist. A query on the GSI with `GSI1PK=BOT#{bot_id}` would still return the orphaned rules even after the bot is deleted.

## 3. Impact / Exploit / Blast Radius

### 3.1 Data integrity

The orphaned `RULE#` items are permanently resident in `T.chat_bots`. They cannot be accessed via any UI (the bot is deleted) but they remain in the backing store. Any DDB scan of `T.chat_bots` (e.g., for table statistics, data exports, compliance audits) will include ghost data from deleted bots.

### 3.2 Potential bot-ID reuse

Bot IDs are generated as `uuid4().hex` (16-byte random hex). UUID v4 collision probability is negligible (~1 in 2^122 per new ID). However, the orphaned rule records mean that if a collision did occur, the new bot would immediately "inherit" the old bot's auto-reply rules. While the probability is astronomically small, the correct behaviour is that a new bot starts with zero rules — guaranteed by clean cascading deletion.

### 3.3 Auto-reply service correctness

`process_incoming_message()` at `bot_auto_reply.py:167` queries `list_auto_reply_rules(bot_id=bot_id)`, which queries `T.chat_bots` for `PK=BOT#{bot_id}` + `SK begins_with RULE#`. After a bot is deleted, if anything still calls `process_incoming_message(bot_id=<deleted_bot_id>, ...)` (unlikely but possible during a race condition at shutdown), it would return matches against the orphaned rules and potentially trigger auto-replies from a deleted bot.

### 3.4 DDB cost

Storage cost accumulates monotonically. At 20 rules × 400 bytes × 10,000 deletions = ~80 MB of orphaned data. DDB storage pricing is $0.25/GB/month — negligible today, but the problem compounds with scale.

## 4. Fix Design (Code-Level)

### 4.1 Add a `_query_all_auto_reply_rules_raw()` helper

Add a new private helper to `app/services/chat_bot.py` that queries `T.chat_bots` for rule items:

```python
# app/services/chat_bot.py — add after _query_all_assignments (line 380)
def _query_all_auto_reply_rules_raw(*, bot_id: str) -> list[dict]:
    """Query T.chat_bots for all RULE# items for a given bot_id.
    
    Returns raw DDB items with their PK/SK keys needed for delete_item calls.
    Used by delete_bot() to cascade-delete orphaned auto-reply rules.
    """
    resp = T.chat_bots.query(
        KeyConditionExpression=Key("pk").eq(f"BOT#{bot_id}") & Key("sk").begins_with("RULE#"),
    )
    return resp.get("Items", [])
```

### 4.2 Extend `delete_bot()` to cascade-delete rules

**Before** (`app/services/chat_bot.py:167-180`):

```python
def delete_bot(*, creator_id: str, bot_id: str) -> bool:
    """Delete a bot and all its assignments."""
    bot = get_bot_for_owner(creator_id=creator_id, bot_id=bot_id)
    if not bot:
        return False

    # Delete all assignments first
    assignments = _query_all_assignments(bot_id=bot_id)
    for a in assignments:
        T.bot_assignments.delete_item(Key={"pk": a["pk"], "sk": a["sk"]})

    T.chat_bots.delete_item(Key={"pk": f"CREATOR#{creator_id}", "sk": f"BOT#{bot_id}"})
    logger.info("Bot deleted: bot_id=%s creator_id=%s", bot_id, creator_id)
    return True
```

**After**:

```python
def delete_bot(*, creator_id: str, bot_id: str) -> bool:
    """Delete a bot and all its assignments and auto-reply rules."""
    bot = get_bot_for_owner(creator_id=creator_id, bot_id=bot_id)
    if not bot:
        return False

    # Delete all assignments
    assignments = _query_all_assignments(bot_id=bot_id)
    for a in assignments:
        T.bot_assignments.delete_item(Key={"pk": a["pk"], "sk": a["sk"]})

    # Delete all auto-reply rules (stored in T.chat_bots under BOT#{bot_id} / RULE#{rule_id})
    # GAP-0138: previously these were left as orphaned records after bot deletion
    rules = _query_all_auto_reply_rules_raw(bot_id=bot_id)
    for r in rules:
        T.chat_bots.delete_item(Key={"pk": r["pk"], "sk": r["sk"]})
    if rules:
        logger.info(
            "Bot deleted: cascade-deleted %d auto-reply rules for bot_id=%s",
            len(rules), bot_id,
        )

    # Delete the primary bot record
    T.chat_bots.delete_item(Key={"pk": f"CREATOR#{creator_id}", "sk": f"BOT#{bot_id}"})
    logger.info("Bot deleted: bot_id=%s creator_id=%s", bot_id, creator_id)
    return True
```

### 4.3 Add a cascaded deletion for scheduled sends (related cleanup)

While reviewing the cascade gap, the same analysis applies to `T.bot_scheduled_sends`. `delete_bot()` does not delete the bot's scheduled sends from `T.bot_scheduled_sends`. Although GAP-0136 documents the scheduler fix, if a bot with pending wildcard schedules is deleted, the scheduler will continue to pick up those schedules (they query by GSI1, not by creator), fail on `get_bot()` returning `None`, and skip them. This is handled gracefully by `dispatch_due_scheduled_sends()` at `bot_scheduler.py:261-263`:

```python
bot = get_bot(bot_id=sched["bot_id"])
if not bot or bot["status"] != "active":
    continue
```

So the scheduler handles deleted-bot schedules safely. However, the orphaned schedule records in `T.bot_scheduled_sends` accumulate indefinitely. The complete fix should also extend `delete_bot()` to query and delete `T.bot_scheduled_sends` for `PK=BOT#{bot_id}` + `SK begins_with SCHED#`. This is a separate but related cleanup that should be bundled with this fix.

### 4.4 Dev/Prod parity (SECOPS-007)

This fix adds DDB queries and deletes. All operations use `T.chat_bots.query()` and `T.chat_bots.delete_item()`, which route to DynamoDB Local in dev and AWS DynamoDB in prod via the same table handle. No mock paths, no feature flags. The fix is valid in both environments identically. No migration is needed — the fix takes effect for all subsequent bot deletions; existing orphaned records require a one-time cleanup script (see section 5.4).

### 5.3 One-time cleanup script for existing orphaned data

For pre-existing orphaned rules in production, a one-time cleanup script is needed:

```python
#!/usr/bin/env python3
"""scripts/cleanup_orphaned_bot_rules.py — one-time cleanup for GAP-0138."""
import boto3
from boto3.dynamodb.conditions import Key

def cleanup(table_name: str, ddb_endpoint: str | None = None):
    kwargs = {}
    if ddb_endpoint:
        kwargs["endpoint_url"] = ddb_endpoint
    ddb = boto3.resource("dynamodb", region_name="us-east-1", **kwargs)
    table = ddb.Table(table_name)

    # Scan for all items with sk beginning with RULE#
    # These are auto-reply rules; check if their associated bot still exists
    scan_kwargs = {
        "FilterExpression": "begins_with(sk, :prefix)",
        "ExpressionAttributeValues": {":prefix": "RULE#"},
    }
    deleted_count = 0
    while True:
        resp = table.scan(**scan_kwargs)
        for item in resp.get("Items", []):
            bot_id = item.get("bot_id")
            if not bot_id:
                continue
            # Check if the bot still exists (via GSI1)
            bot_check = table.query(
                IndexName="GSI1",
                KeyConditionExpression=Key("GSI1PK").eq(f"BOT#{bot_id}") & Key("GSI1SK").eq("META"),
            )
            if not bot_check.get("Items"):
                # Bot is gone — delete the orphaned rule
                table.delete_item(Key={"pk": item["pk"], "sk": item["sk"]})
                deleted_count += 1
                print(f"Deleted orphaned rule: pk={item['pk']} sk={item['sk']}")
        if "LastEvaluatedKey" not in resp:
            break
        scan_kwargs["ExclusiveStartKey"] = resp["LastEvaluatedKey"]

    print(f"Cleanup complete. Deleted {deleted_count} orphaned rules.")

if __name__ == "__main__":
    import os
    cleanup(
        table_name=os.environ.get("BOT_TABLE_NAME", "chat_bots"),
        ddb_endpoint=os.environ.get("DDB_ENDPOINT_URL"),
    )
```

Run in dev: `DDB_ENDPOINT_URL=http://localhost:8001 python3 scripts/cleanup_orphaned_bot_rules.py`

### 5.4 Rollout and rollback

- **Rollout**: Deploy `chat_bot.py` change. Run cleanup script in production during maintenance window to remove existing orphaned records.
- **Rollback**: Revert `chat_bot.py`. The cascade deletion stops; new bot deletions will again orphan rules. Previously cleaned orphaned records do not return.
- **Risk**: Low. The new `_query_all_auto_reply_rules_raw()` query is read-before-delete — no data loss risk. The delete loop is idempotent.
- **Effort**: S (2–3 hours for implementation, tests, and cleanup script).
