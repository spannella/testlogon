# GAP-0093: `auto_deploy_on_qa_approved` Trigger Not Wired — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: AGENT-010. No prior investigation doc exists.
> All claims verified against the actual source code before writing.

## 1. Summary & Classification

**Bug**: The DevOps agent configuration field `auto_deploy_on_qa_approved` is stored in DynamoDB and surfaced in the schema, but the worker polling loop for AGENT-003 (the background worker that picks up eligible tickets and dispatches deployment workflows) is never called by any background task. Even if a polling loop were running, there is no call path that reacts to a ticket transitioning to `qa_approved` by enqueuing a DevOps deployment run. The net result is that setting `auto_deploy_on_qa_approved: true` has no runtime effect: tickets approved by the QA agent sit in `qa_approved` status indefinitely unless an operator manually triggers a deployment.

**Severity**: HIGH (broken automation guarantee — deployment pipeline stalls silently)
**Source ticket**: AGENT-010 (DevOps/SRE Agent)
**Status**: Open
**Owning area**: Agent services / DevOps automation / worker dispatch

**Claim from GAP-0093 ticket**: "config field `auto_deploy_on_qa_approved` is stored but AGENT-003 polling loop never acts on `qa_approved` status"

**Verdict from investigation**: CLAIM CONFIRMED. The field is stored and normalised at `app/services/agent_devops.py:214`. The `find_devops_eligible_tickets` function at line 340–391 does accept `auto_deploy_on_qa: bool` and correctly widens `eligible_statuses` to include `{"qa_approved", "code_complete"}` at line 377. However, this function is called **only** from the admin HTTP endpoint `GET /ui/agents/types/{type_id}/eligible-tickets` (via `app/routers/agent_devops.py:135`), which is a preview/dashboard endpoint for human operators. There is no background task, cron job, SSE event handler, or webhook handler that polls `find_devops_eligible_tickets` and automatically dispatches `execute_devops_workflow`. The `mark_ticket_qa_approved` function in `app/services/agent_qa.py:979` simply writes the `qa_approved` status to DynamoDB and returns — it emits no event, calls no DevOps callback, and triggers no background task.

**Note**: The ticket's claim is accurate. No line-number correction is needed.

**Related tickets**: GAP-0010 (agent loop not running as background task — same class of wiring gap), SECOPS-007.

## 3. Impact / Exploit / Blast Radius

**Who is affected**: Any team that configures `auto_deploy_on_qa_approved: true` expecting continuous delivery (CD) automation. The symptom is silent: tickets approved by the QA agent accumulate in `qa_approved` status with no deployment triggered and no error emitted.

**Business consequence**:

- The entire CD pipeline stalls silently. Work that passed QA sits undeployed indefinitely.
- Operators who rely on the auto-deploy flag discover the gap only by noticing that deployments are not happening — there is no alert, no error log, and no visible failure.
- In a high-velocity team this could cause a large backlog of approved but undeployed tickets, complicating rollouts and increasing merge conflicts.

**No security exploit**: This is an availability/correctness gap, not a security vulnerability. There is no data breach or privilege escalation risk.

**Blast radius**: All tenants or agent types with `auto_deploy_on_qa_approved: true`. The impact is proportional to the deployment cadence — a team shipping many tickets per day is most affected.

## 4. Fix Design (code-level)

### Two complementary wiring points

The fix requires wiring the trigger in two places: (A) a background polling loop that periodically checks for `qa_approved` tickets and dispatches deployment workflows, and (B) an event-driven trigger inside `mark_ticket_qa_approved` that immediately dispatches a deployment when the flag is set. Option B is the primary fix; Option A provides a catch-up mechanism.

### Option B: Event-driven trigger in `mark_ticket_qa_approved`

Add a dispatch call at the end of `mark_ticket_qa_approved`. The dispatch must be non-blocking (the QA execute endpoint must still return promptly):

```python
# app/services/agent_qa.py

def mark_ticket_qa_approved(
    *, ticket_id: str, agent_sub: str, report: str
) -> Dict[str, Any]:
    result = _set_ticket_status(ticket_id=ticket_id, status="qa_approved", report=report)
    # Trigger auto-deployment if any DevOps agent type is configured for it.
    try:
        _maybe_auto_deploy(ticket_id=ticket_id)
    except Exception:
        # Non-blocking: deployment dispatch failure must never roll back QA approval.
        logger.exception("auto_deploy dispatch failed for ticket %s", ticket_id)
    return result


def _maybe_auto_deploy(*, ticket_id: str) -> None:
    """Dispatch a DevOps workflow for ticket_id if any agent type has
    auto_deploy_on_qa_approved=True and the ticket matches its label sets."""
    from app.services import agent_devops as devops_svc  # avoid circular import at module level

    agent_types = devops_svc.list_agent_types_with_auto_deploy()
    for at in agent_types:
        config = devops_svc.get_devops_config(agent_type_id=at["agent_type_id"])
        if not config:
            continue
        label_sets = {
            "deployment": config.get("deploy_ticket_labels") or ["type:deployment"],
            "infrastructure": config.get("infra_ticket_labels") or ["type:infrastructure"],
            "incident_response": config.get("incident_ticket_labels") or ["type:incident"],
        }
        eligible = devops_svc.find_devops_eligible_tickets(
            label_sets=label_sets,
            auto_deploy_on_qa=True,
            limit=50,
        )
        match = next((t for t in eligible if t["ticket_id"] == ticket_id), None)
        if match:
            _dispatch_auto_deploy(
                ticket_id=ticket_id,
                agent_type_id=at["agent_type_id"],
                operation_type=match["operation_type"],
                config=config,
            )
            break  # first matching agent type wins


def _dispatch_auto_deploy(
    *, ticket_id: str, agent_type_id: str, operation_type: str, config: dict
) -> None:
    """Create a run record and submit for deterministic mock execution."""
    from app.services import agent_devops as devops_svc
    from uuid import uuid4

    agent_sub = f"auto_deploy@{agent_type_id}"
    run_id = f"auto_{uuid4().hex[:12]}"
    # Claim the ticket for the auto-deploy agent.
    try:
        devops_svc.claim_devops_ticket(
            ticket_id=ticket_id, agent_sub=agent_sub, operation_type=operation_type
        )
    except ValueError:
        # Already claimed by another process — skip.
        return
    # Submit workflow execution.
    devops_svc.create_agent_run(
        run_id=run_id,
        agent_type_id=agent_type_id,
        ticket_id=ticket_id,
        triggered_by="auto_deploy_on_qa_approved",
    )
```

### Option A: Background polling loop (catch-up)

Add a periodic task in `app/main.py` (using FastAPI `lifespan`) that calls `find_devops_eligible_tickets` for all DevOps agent types with `auto_deploy_on_qa_approved=True` and dispatches unclaimed `qa_approved` tickets:

```python
# app/main.py (in the lifespan async context manager)

async def _auto_deploy_poll_loop():
    """Catch-up loop: dispatch any qa_approved tickets not yet picked up."""
    import asyncio
    from app.services import agent_devops as devops_svc

    while True:
        await asyncio.sleep(60)  # poll every 60 s
        try:
            _poll_auto_deploy_once()
        except Exception:
            logger.exception("auto_deploy poll loop error")

def _poll_auto_deploy_once():
    from app.services.agent_devops import list_agent_types_with_auto_deploy
    for at in list_agent_types_with_auto_deploy():
        ...  # same body as _maybe_auto_deploy above, iterating all eligible
```

Register in the lifespan:

```python
task = asyncio.create_task(_auto_deploy_poll_loop())
```

### New helper: `list_agent_types_with_auto_deploy`

Add to `app/services/agent_devops.py`:

```python
def list_agent_types_with_auto_deploy() -> List[Dict[str, Any]]:
    """Return all DevOps agent types with auto_deploy_on_qa_approved=True."""
    ensure_tables()
    resp = T.agent_types.scan(
        FilterExpression="agent_type = :t",
        ExpressionAttributeValues={":t": "devops"},
    )
    result = []
    for item in resp.get("Items", []):
        cfg = item.get("devops_config") or {}
        if cfg.get("auto_deploy_on_qa_approved"):
            result.append({"agent_type_id": item.get("agent_type_id", "")})
    return result
```

(A paginating scan is acceptable here since the number of agent types is small and this is a background task, not a hot path.)

### Dev/prod parity (SECOPS-007)

The trigger logic uses DynamoDB Local in dev and real DynamoDB in prod — consistent with the existing pattern. The `_dispatch_auto_deploy` function calls `create_agent_run`, which writes to DynamoDB; this is the same path used by manual deployments. In dev mode `S.agent_devops_execute_commands` remains `False`, so the dispatch creates a run record but does not execute real shell commands. The full pipeline (QA approve → auto-deploy claim → mock workflow → status update) is exercisable offline in pytest via the existing moto mock.

### Backward compatibility

The change adds behaviour where there was none. Existing agent types with `auto_deploy_on_qa_approved: false` (the default) are unaffected. New behaviour only activates when the flag is explicitly set to `true`.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

Add to `tests/test_agent_devops.py`:

```python
import pytest
from unittest.mock import patch, MagicMock
from app.services.agent_qa import mark_ticket_qa_approved
from app.services import agent_devops as devops_svc

def test_mark_ticket_qa_approved_triggers_auto_deploy(seed_devops_agent_type):
    """After qa_approved, _maybe_auto_deploy must be called exactly once."""
    ticket_id = seed_devops_agent_type["ticket_id"]
    agent_type_id = seed_devops_agent_type["agent_type_id"]

    dispatched = []

    with patch(
        "app.services.agent_qa._dispatch_auto_deploy",
        side_effect=lambda **kw: dispatched.append(kw),
    ):
        mark_ticket_qa_approved(
            ticket_id=ticket_id, agent_sub="qa@test", report="All green"
        )

    assert len(dispatched) == 1, "exactly one auto-deploy must be dispatched"
    assert dispatched[0]["ticket_id"] == ticket_id


def test_auto_deploy_not_triggered_when_flag_false(seed_devops_agent_type_no_auto):
    """auto_deploy_on_qa_approved=False must not trigger dispatch."""
    ticket_id = seed_devops_agent_type_no_auto["ticket_id"]
    dispatched = []

    with patch(
        "app.services.agent_qa._dispatch_auto_deploy",
        side_effect=lambda **kw: dispatched.append(kw),
    ):
        mark_ticket_qa_approved(
            ticket_id=ticket_id, agent_sub="qa@test", report="All green"
        )

    assert len(dispatched) == 0


def test_auto_deploy_dispatch_failure_does_not_roll_back_qa_approval(
    seed_devops_agent_type, ticket_store
):
    """A crash in _dispatch_auto_deploy must not propagate to the caller."""
    ticket_id = seed_devops_agent_type["ticket_id"]

    with patch(
        "app.services.agent_qa._maybe_auto_deploy",
        side_effect=RuntimeError("infra down"),
    ):
        result = mark_ticket_qa_approved(
            ticket_id=ticket_id, agent_sub="qa@test", report="All green"
        )

    assert result["status"] == "qa_approved"
    ticket = ticket_store.get_ticket(ticket_id)
    assert ticket["status"] == "qa_approved"
```

**Fails before the fix**: `_maybe_auto_deploy` and `_dispatch_auto_deploy` do not exist; `dispatched` stays empty after `mark_ticket_qa_approved`.

**Passes after the fix**: The dispatch is called exactly once for a matching agent type with the flag enabled.

### Manual QA steps

1. Configure a DevOps agent type with `auto_deploy_on_qa_approved: true` and `deploy_ticket_labels: ["type:deployment"]`.
2. Create a ticket with `labels: ["type:deployment"]` and `status: open`.
3. Run the QA agent mock execution against the ticket (`execute_qa_workflow`, scenario `pass`).
4. Observe ticket transitions: `code_complete` → `qa_in_progress` → `qa_approved`.
5. Confirm a deployment run record is created automatically (check via `GET /ui/agents/types/{id}/deployments`).
6. Confirm the ticket transitions to `deploying` without any manual operator action.

### Observability

- Emit a structured log event `auto_deploy.dispatched` with `ticket_id`, `agent_type_id`, and `run_id` when auto-deploy fires.
- Emit `auto_deploy.skipped` (with reason) when a ticket is eligible but already claimed.
- Emit `auto_deploy.error` (with exception class) when `_maybe_auto_deploy` throws; this surfaces silently swallowed errors.

### Rollout

- **Effort**: M (medium — requires new functions, a background loop, and tests).
- **Risk**: Medium. Auto-deploying on QA approval is a significant automation step. Consider adding a dry-run mode (`auto_deploy_dry_run: true`) that logs what would be deployed without actually claiming tickets, allowing operators to validate the logic before enabling full auto-deploy.
- **Feature flag**: `auto_deploy_on_qa_approved` is already per-agent-type; no additional flag needed. The background loop can be conditionally started only when at least one agent type has the flag enabled, avoiding overhead for deployments that do not use auto-deploy.
- **Sequencing**: Implement after GAP-0010 (coder worker loop) is resolved, to share the background task wiring pattern. Test in staging with a low-risk deployment environment before enabling in production.
