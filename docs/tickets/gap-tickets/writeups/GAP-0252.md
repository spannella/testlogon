# GAP-0252: Readiness Gate Not Extended for Enhanced/High-Risk Profiles — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase; no prior investigation doc exists.

## 1. Summary & Classification

**Claim from ticket**: Users with `intake_profile=enhanced` or `intake_profile=high_risk`
can submit their KYC case without supplying any residency document. The `_readiness_for_case`
function at `app/routers/kyc_cases.py:244` checks only three conditions (questionnaire
submitted, required identity files attached, signature completed) and never checks for a
verified residency document for enhanced or high-risk applicants.

**Verdict: Claim CONFIRMED.** The `_readiness_for_case` function (lines 244–307 of
`app/routers/kyc_cases.py`) unconditionally checks only the three base requirements. There
is no intake-profile branch and no call to any residency-checking helper. Users with
`enhanced` or `high_risk` profiles can reach `submit_kyc_case` (line 895) with no residency
document present, violating AML/CDD enhanced due diligence requirements.

The proposed fix references `RESIDENCY_STORE.get_verified_docs_for_case(case_id)` which
does not exist (see GAP-0253). This write-up designs the fix against the actual residency
store API.

- **Severity**: HIGH (compliance/regulatory) — AML/CDD frameworks require enhanced due
  diligence for high-risk and enhanced profiles; the submit gate is the last automated
  enforcement point.
- **Source ticket**: KYC-004
- **Owning area**: Backend / KYC cases router, `_readiness_for_case` helper
- **Related tickets**: GAP-0253 (`get_verified_docs_for_case` helper missing), GAP-0254
  (ResidencyVerificationTab UI), SECOPS-007
- **Dependency note**: This fix depends on GAP-0253 being implemented first (the residency
  check helper must exist before it can be called from `_readiness_for_case`).

## 2. Current-State Investigation (root cause)

### `_readiness_for_case` — current code

`app/routers/kyc_cases.py` lines 244–307:

```python
def _readiness_for_case(case: dict) -> dict:
    questionnaire = _questionnaire_status_for_case(case, include_submit_gate=False)
    files = _validate_file_requirements(case)
    signature = _signature_status_for_case(case)

    checks = {
        "questionnaire_submitted": bool(questionnaire.get("submitted")),
        "required_files": bool(files.get("ready_for_submit_gate")),
        "signature_completed": bool(signature.get("ready_for_submit_gate")),
    }
    ...
    requirements: list[dict] = [
        { "key": "questionnaire_submitted", ... },
        { "key": "required_files", ... },
        { "key": "signature_completed", ... },
    ]
    missing_requirements = [item["key"] for item in requirements if not item["ready"]]
    ...
    return {
        ...
        "ready_to_submit": all(checks.values()),
        ...
    }
```

There are exactly three entries in `checks` and three entries in `requirements`. No intake
profile is read; no residency store is consulted. The `intake_profile` field sits on the
case dict (written by `STORE.create_case`; patched by `STORE.update_draft`) but is never
inspected inside `_readiness_for_case`.

### Submit gate call site

`submit_kyc_case` (line 895) calls `_readiness_for_case` and gates on
`readiness["ready_to_submit"]` (line 912). If the three base checks pass, the case
transitions from `draft` to `submitted` and a review ticket is created. There is no
secondary gate for enhanced/high_risk profiles.

### `intake_profile` values in use

From the admin queue logic (`list_admin_queue`, lines 716–722):

```python
def _risk(case: dict[str, Any]) -> str:
    intake = str(case.get("intake_profile") or "").strip().lower()
    if intake in {"enhanced", "high_risk"}:
        return "high"
    if intake in {"standard", "medium_risk"}:
        return "medium"
    return "low"
```

The values `enhanced` and `high_risk` are already used as a combined "high" risk tier for
queue prioritization. They are the correct target for the residency requirement.

### Residency store current state (relevant for fix)

`app/services/kyc_residency.py` provides:

- `STORE.list_documents_for_case(case_id)` (line 440): queries the `ByCase` GSI, returns
  all residency documents for a case.
- `STORE.list_by_status(status, limit)` (line 454): queries the `ByStatus` GSI, returns
  documents by status globally (not scoped to a case).

No method named `get_verified_docs_for_case` exists anywhere in the codebase. The helper
must be added as part of GAP-0253 before this readiness gate can call it. The fix here
depends on GAP-0253.

## 3. Impact / Exploit / Blast Radius

**Regulatory non-compliance**: EU/UK AMLD, US FinCEN, and similar AML/CDD frameworks
mandate enhanced due diligence (EDD) for high-risk customers. EDD typically includes proof
of address (residency verification). A platform that classifies a user as `enhanced` or
`high_risk` and then allows them to submit without a verified residency document violates
the spirit and letter of EDD controls.

**Concrete scenario**: A user signs up, selects `intake_profile=high_risk` (or is
programmatically assigned it due to sanctions screening), completes the three base checks,
and submits. The reviewer receives the case with no residency document attached. The
reviewer may approve the case in good faith, believing the system verified residency
automatically. The compliance audit trail shows no residency check occurred.

**Admin override risk**: Even if individual reviewers catch the omission, the submit gate
is the authoritative automated control. Its absence means the platform cannot consistently
enforce EDD requirements across thousands of cases and hundreds of reviewers.

**No financial exploit**: This is a compliance gap, not a financial or authentication
vulnerability. It does not enable unauthorized fund movements or data exfiltration.

## 4. Fix Design (code-level)

### 4b. Update `_readiness_for_case` in `app/routers/kyc_cases.py`

The change adds a fourth check for high-risk/enhanced profiles. The check is skipped when
the intake profile is standard or not set, preserving full backward-compatibility for the
majority of cases.

```python
# app/routers/kyc_cases.py — replace _readiness_for_case (lines 244–307)

def _readiness_for_case(case: dict) -> dict:
    from app.services.kyc_residency import STORE as RESIDENCY_STORE

    questionnaire = _questionnaire_status_for_case(case, include_submit_gate=False)
    files = _validate_file_requirements(case)
    signature = _signature_status_for_case(case)

    intake_profile = str(case.get("intake_profile") or "").strip().lower()
    is_enhanced = intake_profile in {"enhanced", "high_risk"}

    # Residency check — only required for enhanced/high_risk profiles
    residency_verified = False
    if is_enhanced:
        verified_docs = RESIDENCY_STORE.get_verified_docs_for_case(
            str(case.get("kyc_case_id") or "")
        )
        residency_verified = len(verified_docs) > 0

    checks: dict[str, bool] = {
        "questionnaire_submitted": bool(questionnaire.get("submitted")),
        "required_files": bool(files.get("ready_for_submit_gate")),
        "signature_completed": bool(signature.get("ready_for_submit_gate")),
    }
    if is_enhanced:
        checks["residency_verified"] = residency_verified

    hint_map = {
        "questionnaire_submitted": "Submit the linked questionnaire to continue.",
        "required_files": "Attach all required identity files: selfie, id_front, id_back.",
        "signature_completed": "Complete the consent signature packet and wait for final PDF generation.",
        "residency_verified": (
            "Your account type requires a verified proof-of-residency document "
            "(utility bill, bank statement, or similar). "
            "Upload and complete residency verification before submitting."
        ),
    }

    requirements: list[dict] = [
        {
            "key": "questionnaire_submitted",
            "ready": checks["questionnaire_submitted"],
            "missing": ([] if checks["questionnaire_submitted"] else ["questionnaire_submission"]),
            "hint": hint_map["questionnaire_submitted"],
            "refs": {
                "questionnaire_id": questionnaire.get("questionnaire_id"),
                "response_session_id": questionnaire.get("response_session_id"),
                "response_pdf_ref": questionnaire.get("response_pdf_ref"),
            },
        },
        {
            "key": "required_files",
            "ready": checks["required_files"],
            "missing": list(files.get("missing_types") or []),
            "hint": hint_map["required_files"],
            "refs": {
                "present_types": ",".join(files.get("present_types") or []),
            },
        },
        {
            "key": "signature_completed",
            "ready": checks["signature_completed"],
            "missing": (
                []
                if checks["signature_completed"]
                else ["signature_completion", "signature_final_pdf"]
            ),
            "hint": hint_map["signature_completed"],
            "refs": {
                "packet_id": signature.get("packet_id"),
                "final_pdf_ref": signature.get("final_pdf_ref"),
            },
        },
    ]
    if is_enhanced:
        requirements.append(
            {
                "key": "residency_verified",
                "ready": checks["residency_verified"],
                "missing": ([] if checks["residency_verified"] else ["residency_document_verified"]),
                "hint": hint_map["residency_verified"],
                "refs": {},
            }
        )

    missing_requirements = [item["key"] for item in requirements if not item["ready"]]
    missing_hints = [hint_map[key] for key in missing_requirements]

    return {
        "kyc_case_id": case.get("kyc_case_id"),
        "status": case.get("status"),
        "ready_to_submit": all(checks.values()),
        "missing_requirements": missing_requirements,
        "missing_hints": missing_hints,
        "checks": checks,
        "requirements": requirements,
    }
```

Key design decisions:
- The `RESIDENCY_STORE` import is inside the function body to avoid circular imports.
- Standard/medium profiles are completely unaffected — the residency block is skipped.
- The `requirements` list remains index-stable for standard profiles (indices 0, 1, 2
  match the `evidence_snapshot` construction in `submit_kyc_case` lines 926–940). The
  residency check is appended as index 3 only when needed; `submit_kyc_case` accesses
  `requirements[0]`, `requirements[1]`, `requirements[2]` by position — these indices are
  unchanged.

### 4c. Update `submit_kyc_case` — no change needed for gate logic

`submit_kyc_case` (line 912) already gates on `readiness["ready_to_submit"]`, which is
`all(checks.values())`. Adding a fourth check to `checks` automatically extends the gate.
No changes to `submit_kyc_case` itself are required.

### 4d. Dev/Prod parity (SECOPS-007)

`RESIDENCY_STORE.get_verified_docs_for_case` queries `T.kyc_residency_documents` via the
`ByCase` GSI. In dev this points to DynamoDB Local; in prod it points to AWS DynamoDB.
The same boto3 table handle is used in both environments — no environment-specific branches
are introduced.

The `is_enhanced` guard ensures the residency DynamoDB query is only issued for cases where
it is required, keeping the hot path (standard profiles) unaffected.

### Alternatives considered

- **Enforce at document upload time**: Mark the case as "residency_required" at creation
  when `intake_profile in {"enhanced","high_risk"}`. Rejected — this change to the creation
  flow is larger and more disruptive; the submit gate is the right enforcement point.
- **Enforce in a separate pre-submit endpoint**: Add a new `POST /{case_id}/pre-submit`
  endpoint that runs the enhanced checks. Rejected — the existing readiness endpoint is
  already the canonical pre-submit check gate and callers depend on its response shape.
- **Enforce via a separate service layer**: Move the residency check into
  `STORE.submit_case()`. Rejected — business-rule checks belong in the router layer where
  all other readiness checks live; the service layer should remain a thin persistence layer.
