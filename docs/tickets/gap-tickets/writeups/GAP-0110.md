# GAP-0110: SEC-025 IDOR on lifecycle routes — Remediation Write-up

> Claim verified against `app/routers/broadcast.py`. Claim is **partially correct**.
> The three cited line numbers (360, 402, 453) are the three lifecycle route decorators
> (`@router.post("/sessions/{session_id}/start")`, `@router.post(".../stop")`,
> `@router.delete("/sessions/{session_id}")`). All three call `_require_operator_role` (lines
> 369, 411, 455) but do NOT check session ownership. The claim is correct. However, the ticket
> states "any admin/root can … another broadcaster's session", which is precisely what
> `_require_operator_role` allows (it only checks that the caller is admin or root, not that
> they own the session). The suggested fix helper name `_require_operator_and_owner` does not
> yet exist and must be created.

## 1. Summary & Classification

**Bug**: The broadcast lifecycle routes — `start_session_route`, `stop_session_route`, and
`delete_session_route` — verify that the caller holds an admin or root role but do not verify
that the caller created (owns) the session being acted on. Any admin-or-root user can start,
stop, or delete any other broadcaster's session without restriction.

- **Severity**: HIGH (SEC-025 IDOR; privilege-within-role escalation; one admin can sabotage
  another admin's live broadcast)
- **Source ticket**: BCAST-001
- **Status**: Open
- **Owning area**: Broadcast router (`app/routers/broadcast.py`)
- **Verdict**: Confirmed. All three handlers pass `_require_operator_role` and then call the
  provider action functions directly. No ownership check is performed anywhere in the three
  code paths.
- **Claim accuracy note**: Claim is correct on the IDOR. However `broadcast.py` already
  contains a correct ownership-checking helper `_require_session_owner` at line 1338 (used by
  scheduling and privacy routes). The fix should reuse or extend that existing helper rather
  than creating a wholly new `_require_operator_and_owner` — the ticket's suggested name is
  implementation guidance, not a hard requirement.
- **Related tickets**: SEC-025 (parent security finding), BCAST-001 (feature ticket), no
  dependency on GAP-0106 through GAP-0109.

## 2. Current-State Investigation (root cause)

### Access-control model for broadcast sessions

The broadcast system distinguishes two kinds of privileged action:

1. **Session management** (create, schedule, configure privacy, set prices): performed by
   the broadcaster who owns the session. A role check is not required — any authenticated
   user can create a session.
2. **Lifecycle control** (start, stop, delete): guarded by `_require_operator_role`, which
   requires admin or root. The intent was that only privileged operators can trigger
   provider-side actions (start/stop on the media infrastructure). The ownership check was
   apparently never added on the assumption that admin/root users would only act on their
   own sessions.

This assumption breaks down as soon as there is more than one admin user, which is the
normal case in any multi-tenant or multi-broadcaster deployment.

### _require_operator_role — broadcast.py:231-236

```python
def _require_operator_role(ctx: dict) -> None:
    if ctx.get("role") not in {"admin", "root"}:
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail={"code": "BROADCAST_ROLE_FORBIDDEN",
                    "detail": "admin or root role required"},
        )
```

This helper enforces role membership only. It does not fetch the session, does not read
`session.created_by`, and does not compare with `ctx["user_sub"]`.

### start_session_route — broadcast.py:360-399

```python
@router.post("/sessions/{session_id}/start", ...)
def start_session_route(session_id, body, request, ..., ctx=Depends(_ctx)):
    _require_operator_role(ctx)          # role check only — line 369
    ...
    current = start_session_with_provider(
        session_id=session_id,
        actor=ctx["user_sub"],
        ...
    )
```

`start_session_with_provider` is called with the caller's `user_sub` as `actor`, which is
recorded in the audit log. However the function itself does not verify ownership of
`session_id`. The session record is never fetched before the operation begins.

### stop_session_route — broadcast.py:402-450

Identical pattern: `_require_operator_role` at line 411, then `stop_session_with_provider`
called without an ownership check.

### delete_session_route — broadcast.py:453-477

Identical pattern: `_require_operator_role` at line 455, then `delete_session_with_provider`
called without an ownership check.

### Contrast: _require_session_owner — broadcast.py:1338-1346

The privacy and scheduling routes use a different, correct helper:

```python
def _require_session_owner(session_id: str, ctx: dict):
    """Return the session; raise 403 unless caller is the broadcaster (or operator)."""
    session = get_session(session_id)
    if ctx["user_sub"] != session.created_by and ctx.get("role") not in {"admin", "root"}:
        raise HTTPException(
            status_code=403,
            detail={"code": "BROADCAST_PRIVACY_FORBIDDEN",
                    "detail": "Only the broadcaster can manage privacy."},
        )
    return session
```

This helper correctly fetches the session and allows the owner OR an admin/root to act.
The three lifecycle routes use only `_require_operator_role` — they require admin/root but
do not check ownership, meaning a root user who does NOT own the session passes the check.

### The intent vs implementation gap

The design intent (BCAST-001) is that lifecycle operations should be performed by the
broadcaster who owns the session, with admin/root users acting as supervisors. The current
code inverts this: only admin/root can call start/stop/delete (regular users cannot call
these on their own sessions), and there is no ownership gate within the elevated roles.

Whether regular (USER-role) broadcasters should be able to start/stop their own sessions is
a separate design question. The IDOR concern in SEC-025 is specifically that one admin can
affect another admin's session.

### Dev vs prod

The IDOR is path-independent: both dev (DynamoDB Local) and prod (AWS DynamoDB) execute
the same auth checks. The `get_session` call that the fix requires is already used elsewhere
in the same file and works identically in both environments.

## 3. Impact / Exploit / Blast Radius

### Exploit walkthrough

1. Admin A (`alice_admin`) creates broadcast session `sess_xyz` and is live on air.
2. Admin B (`eve_admin`) — a malicious or mistaken operator — calls
   `POST /broadcast/sessions/sess_xyz/stop`.
3. Backend check: `_require_operator_role(ctx)` passes because Eve is admin.
4. `stop_session_with_provider` runs; session is stopped.
5. Alice's live stream drops mid-broadcast. No error is surfaced to Alice.

The same attack works for `start` (starts another admin's session without their knowledge,
potentially exposing their stream key to Eve's actor context) and `delete` (permanently
removes Alice's session record and associated outputs).

### Worst-case consequences

- **Availability**: any admin can terminate any live broadcast at will.
- **Data loss**: `delete_session_route` calls `delete_session_with_provider` which removes
  the session record. Recordings linked to the session may become orphaned or inaccessible.
- **Stream key exposure**: `start_session_with_provider` is passed `actor=ctx["user_sub"]`.
  If the provider API logs or returns the stream key as part of the start response, a
  malicious actor receives credentials belonging to another broadcaster.
- **Compliance**: in multi-tenant platforms with admin users representing different
  organisations, cross-tenant session control is a serious security boundary violation.

### Blast radius

Affects all broadcast sessions. Any user with admin or root role can act on any session.
The number of admin users is expected to be small, so the blast radius in terms of
exploiting accounts is limited — but the impact on any single targeted session is severe
(immediate stream termination or deletion).

## 4. Fix Design (code-level)

### Approach: add an ownership guard to the three lifecycle routes

The existing `_require_session_owner` helper at line 1338 already does what is needed for
the "owner-or-operator" pattern used by privacy routes. However its error code
(`BROADCAST_PRIVACY_FORBIDDEN`) is semantically wrong for lifecycle operations. The cleanest
fix is either:

**Option A** — Extend `_require_session_owner` with a configurable error code, or
**Option B** — Add a dedicated `_require_operator_and_owner` helper as the ticket suggests.

Option B is cleaner for auditing and avoids touching a helper used by many other routes.

#### New helper — broadcast.py (insert after line 236)

```python
def _require_operator_and_owner(session_id: str, ctx: dict):
    """Fetch and return the session; raise 403 unless caller is the session owner.

    Admin or root role is still required (via _require_operator_role called first),
    but this additional check ensures the operator acts only on their own sessions,
    preventing IDOR (SEC-025).
    """
    session = get_session(session_id)
    if session is None:
        raise HTTPException(status_code=404, detail="Session not found")
    if ctx["user_sub"] != session.created_by:
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail={
                "code": "BROADCAST_OWNERSHIP_FORBIDDEN",
                "detail": "You can only perform lifecycle operations on your own sessions.",
            },
        )
    return session
```

#### start_session_route — broadcast.py:360-399

```python
@router.post("/sessions/{session_id}/start", ...)
def start_session_route(session_id, body, request, ..., ctx=Depends(_ctx)):
    _require_operator_role(ctx)
    _require_operator_and_owner(session_id, ctx)   # add this line after line 369
    cid = ...
    ...
```

#### stop_session_route — broadcast.py:402-450

```python
    _require_operator_role(ctx)
    _require_operator_and_owner(session_id, ctx)   # add after line 411
```

#### delete_session_route — broadcast.py:453-477

```python
    _require_operator_role(ctx)
    _require_operator_and_owner(session_id, ctx)   # add after line 455
```

### Consideration: should root be able to act on any session?

SEC-025 as filed is about IDOR between peer admins. Whether a root super-user should have
cross-session authority is a policy decision. Two options:

- **Strict** (recommended): root is also bound by ownership. A root user who is not the
  broadcaster must impersonate the broadcaster account to act on their session.
- **Permissive**: root bypasses ownership. Change the helper condition to
  `ctx["user_sub"] != session.created_by and ctx.get("role") != "root"`.

The strict interpretation is recommended for SEC-025 compliance; a separate "emergency
override" capability can be implemented with explicit logging and justification.

### Dev/Prod parity (SECOPS-007)

`get_session` is a DynamoDB read (`broadcast_store.get_session`). It works identically in
dev (DynamoDB Local) and prod (AWS DynamoDB). No mock branching needed. The three lifecycle
routes are already exercised by the BCAST-001 integration tests; the only change is an
additional 403 for cross-owner calls.

### Backward compatibility

Callers that currently call start/stop/delete on sessions they own are unaffected. Callers
that rely on cross-owner control — an IDOR abuse — will receive a new 403. No DynamoDB
schema changes are required.

## 5. Testing, Verification & Rollout

### Regression tests (pytest offline)

```python
# tests/test_broadcast_lifecycle_ownership.py

def test_owner_can_start_own_session(client, admin_session_alice, seeded_session_alice):
    """Broadcaster can start their own session."""
    r = client.post(
        f"/broadcast/sessions/{seeded_session_alice}/start",
        json={"reason": "test"},
        headers=admin_session_alice,
    )
    assert r.status_code == 202

def test_other_admin_cannot_start_session(
    client, admin_session_alice, admin_session_bob, seeded_session_alice

    """Admin Bob cannot start Admin Alice's session — IDOR prevented."""
    r = client.post(
        f"/broadcast/sessions/{seeded_session_alice}/start",
        json={"reason": "test"},
        headers=admin_session_bob,   # Bob's session, Alice's session_id
    )
    # FAILS before fix (returns 202); passes after fix (returns 403)
    assert r.status_code == 403
    assert r.json()["detail"]["code"] == "BROADCAST_OWNERSHIP_FORBIDDEN"

    client, admin_session_bob, seeded_running_session_alice

    """Admin Bob cannot stop Admin Alice's running session."""
    r = client.post(
        f"/broadcast/sessions/{seeded_running_session_alice}/stop",
        json={"reason": "test"},
        headers=admin_session_bob,

    assert r.status_code == 403  # FAILS before fix

def test_other_admin_cannot_delete_session(
    client, admin_session_bob, seeded_session_alice
```

### Observability

The existing `record_broadcast_action` audit trail already logs `actor` on every action. Add
the ownership check failure to the audit log:

```python
# in _require_operator_and_owner, before raising 403:
record_broadcast_action(
    action="lifecycle_idor_rejected",
    actor=ctx["user_sub"],
    correlation_id="",
    resource_type="session",
    resource_id=session_id,
    metadata={"owner": session.created_by},
)
```

This enables security monitoring to detect enumeration or targeted attacks.

### Interaction with `_require_session_owner` at line 1338

The existing helper at line 1338 uses the message string "Only the broadcaster can manage
privacy." and error code `BROADCAST_PRIVACY_FORBIDDEN`. It also allows admin/root users to
bypass the ownership check:

```python
if ctx["user_sub"] != session.created_by and ctx.get("role") not in {"admin", "root"}:
```

This means it is currently correct for privacy routes (admins can view/change privacy
settings for any session) but incorrect for lifecycle routes (admins should only start/stop
their own sessions). The two helpers serve different security policies and must be separate.
Do not consolidate them into one function.

### Testing the 404 path

The `_require_operator_and_owner` helper calls `get_session(session_id)`. If the session
does not exist, `get_session` returns `None` (or raises, depending on implementation). The
helper must handle this explicitly to avoid an `AttributeError` on `None.created_by`. The
fix includes an explicit `None` check that returns 404, which also prevents information
leakage about which session IDs exist (currently `start_session_with_provider` might raise a
different error for non-existent sessions, leaking error shape differences).

### Rollout

- **Effort**: S (one new ~15-line helper + one line added to each of three routes; estimated
  2-3 hours including test authoring)
- **Sequencing**: can ship independently; no dependency on other GAP tickets; should be
  treated as a security patch and expedited through the review process; consider gating
  behind a feature flag `BROADCAST_LIFECYCLE_OWNER_CHECK_ENABLED` for a staged rollout if
  there is concern about breaking existing operator tooling
- **Rollback**: revert the three `_require_operator_and_owner` call sites; helper can be
  left in place harmlessly; no DB changes to undo
- **Risk**: low for well-behaved clients (owners acting on their own sessions); any existing
  automated ops scripts that perform cross-owner lifecycle operations should be audited;
  confirm with the ops team before deploying to production that no such scripts exist, and
  if they do, update them to use impersonation or a dedicated service account that is the
  session creator
