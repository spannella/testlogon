# GAP-0129: Billing Atomicity Gap in `_write_chat_billing()` — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at
> `app/services/broadcast_chat_rich.py:247–305`. No prior investigation doc exists.

## 1. Summary & Classification

**Bug**: `_write_chat_billing()` in the broadcast chat rich-messaging service (BCAST-015)
writes a payer debit and a recipient credit as two independent DynamoDB `put_item` calls,
each inside its own `try/except`. If the credit write fails after the debit succeeds, the
viewer who unlocked or tipped a broadcast chat message is charged but the broadcaster
receives no payment. The exception is silently swallowed; the function returns as if
billing succeeded. This is the fourth occurrence of the same non-atomic billing pattern
across the broadcast feature set (BCAST-011, BCAST-012, BCAST-014).

- **Severity**: HIGH — financial integrity, silent money loss
- **Source ticket**: BCAST-015
- **Status**: Open
- **Owning area**: Broadcast / Chat / Billing
- **Claim verdict**: Confirmed. Lines 273–303 of `app/services/broadcast_chat_rich.py`
  match the description exactly.
- **One-line impact**: A transient DynamoDB error on the credit step leaves the payer
  debited with no corresponding broadcaster credit.
- **Related tickets**: GAP-0126 (private-chat billing), GAP-0128 (lottery entry fee),
  GAP-0130 (`_find_sort_key` O(n) scan, same file), SECOPS-007.

## 2. Current-State Investigation (root cause)

### Code path

`_write_chat_billing` is at `app/services/broadcast_chat_rich.py:247–305`:

```python
def _write_chat_billing(
    payer_id, recipient_id, amount_cents, reason,
    content_type, content_id, session_id, payment_method_id,
) -> tuple:
    ts = now_ts()
    debit_id = uuid.uuid4().hex
    credit_id = uuid.uuid4().hex
    platform_fee_pct = 20
    creator_amount = int(amount_cents * (100 - platform_fee_pct) / 100)
    meta = { ... }

    try:                                        # line 273
        T.billing.put_item(Item={               # line 274 — DEBIT
            "pk": f"USER#{payer_id}",
            "sk": f"LEDGER#{ts}#{debit_id}",
            "type": "debit",
            "amount_cents": amount_cents,
            ...
        })
    except Exception:                           # line 286
        logger.warning("broadcast_chat_billing_debit_failed ...")
        # ← no re-raise; execution continues

    try:                                        # line 289
        T.billing.put_item(Item={               # line 290 — CREDIT
            "pk": f"USER#{recipient_id}",
            "sk": f"LEDGER#{ts}#{credit_id}",
            "type": "credit",
            "amount_cents": creator_amount,     # ← note: platform fee deducted
            ...
        })
    except Exception:                           # line 302
        logger.warning("broadcast_chat_billing_credit_failed ...")
        # ← no re-raise; debit already written, irrecoverable

    return debit_id, credit_id                  # line 305
```

### Structural issues

1. **Split try/except**: two independent `put_item` calls, not wrapped in any
   transaction. Credit failure after debit success = permanent inconsistency.

2. **Swallowed exceptions**: both `except` blocks call `logger.warning` and return
   normally. The return value `(debit_id, credit_id)` signals success even when one or
   both writes failed.

3. **Platform fee applied only to credit**: the payer is debited `amount_cents` (full
   price), but the creator is credited `creator_amount = amount_cents * 0.80`. The
   platform's 20% share is not explicitly written to any ledger entry. This is a
   separate accounting concern (platform revenue is implicit) but means a reconciler
   cannot verify the debit/credit pair by summing amounts alone — noted here for
   awareness.

4. **Caller does not handle errors**: `unlock_chat_message` at line 192 calls
   `_write_chat_billing` inside no try/except. Because the callee swallows errors,
   the caller always proceeds to the DDB update at line 204 (writing the `unlocked_by`
   map update) even when billing silently failed. This means a user could successfully
   unlock a message without being charged.

### When this function is called

`_write_chat_billing` is called from `unlock_chat_message` (line 192):

```python
# app/services/broadcast_chat_rich.py:192
_write_chat_billing(
    payer_id=user_id,

    session_id=session_id,
    payment_method_id=payment_method_id,

```

A tip-specific billing path (for future BCAST-015 tip feature) would use the same
function. Both paths are affected.

## 3. Impact / Exploit / Blast Radius

### Scenario A — debit succeeds, credit fails

1. Viewer calls `POST /broadcast/{session}/chat/messages/{id}/unlock`.
2. `unlock_chat_message` validates the payment method (line 182–186).
3. `_write_chat_billing` runs. Debit `put_item` succeeds (viewer charged).
4. Transient DDB error on credit `put_item`. Exception swallowed.
5. Function returns normally. Caller proceeds to write `unlocked_by` map.
6. Viewer sees the unlocked message. Broadcaster receives no payment. No alert fires.

### Scenario B — debit fails, credit proceeds

Because neither exception is re-raised, if the debit fails (line 286 swallows it),
execution continues to the credit write (line 290). The broadcaster receives a credit
for a payment that was never collected from the viewer.

The caller (`unlock_chat_message`) then proceeds to mark the message as unlocked —
the viewer gets the content for free.

### Financial impact

At a lock price of $5 (500 cents), creator receives $4 (80% after platform fee). If a
broadcaster has 1,000 locked messages across a busy session and 5% of unlock requests
hit a DDB fault window:

- 50 unlocks × ($4 missing credit) = $200 in lost broadcaster earnings.
- Additionally, if debit failures are swallowed, 50 viewers get free unlocks.

### Security concern — free unlock

Scenario B (debit failure swallowed → billing skipped → message unlocked) is a
functional exploit, not just a reliability concern. A user cannot deliberately trigger
DDB failures, but the code path means that **if DDB returns an error**, content is
released without payment. This elevates the severity beyond a reliability gap.

## 4. Fix Design (code-level)

### Strategy

Replace split `put_item` calls with `TransactWriteItems`. Move the billing write
**before** the `unlocked_by` update so that a billing failure prevents content release.
Remove the `try/except` wrappers so exceptions propagate.

### Change 1 — rewrite `_write_chat_billing`

```python
# app/services/broadcast_chat_rich.py

from app.core.aws import ddb                        # add import
from boto3.dynamodb.types import TypeSerializer as _TS

_ts_serializer = _TS()

def _ddb_av(item: dict) -> dict:
    return {k: _ts_serializer.serialize(v) for k, v in item.items()}


def _write_chat_billing(
    payer_id: str,
    recipient_id: str,
    amount_cents: int,
    reason: str,
    content_type: str,
    content_id: str,
    session_id: str,
    payment_method_id: str,
) -> tuple:
    """Write paired debit/credit billing entries atomically via TransactWriteItems.
    Raises TransactionCanceledException if either write fails.
    """
    ts = now_ts()
    debit_id = uuid.uuid4().hex
    credit_id = uuid.uuid4().hex
    platform_fee_pct = 20
    creator_amount = int(amount_cents * (100 - platform_fee_pct) / 100)
    billing_table_name = T.billing.name

    meta = {
        "content_type": content_type,
        "content_id": content_id,
        "session_id": session_id,
        "payer_id": payer_id,
        "recipient_id": recipient_id,
        "payment_method_id": payment_method_id,
    }

    debit_item = {
        "pk": f"USER#{payer_id}",
        "sk": f"LEDGER#{ts}#{debit_id}",
        "entry_id": debit_id, "ts": ts, "type": "debit",
        "amount_cents": amount_cents, "currency": "USD",
        "state": "settled", "reason": reason, "meta": meta,
    }
    credit_item = {
        "pk": f"USER#{recipient_id}",
        "sk": f"LEDGER#{ts}#{credit_id}",
        "entry_id": credit_id, "ts": ts, "type": "credit",
        "amount_cents": creator_amount, "currency": "USD",
        "state": "settled", "reason": reason, "meta": meta,
    }

    ddb.meta.client.transact_write_items(
        TransactItems=[
            {"Put": {"TableName": billing_table_name, "Item": _ddb_av(debit_item)}},
            {"Put": {"TableName": billing_table_name, "Item": _ddb_av(credit_item)}},
        ]
    )

    return debit_id, credit_id
```

### Change 2 — let billing failure prevent unlock in `unlock_chat_message`

The current `unlock_chat_message` at line 192 calls `_write_chat_billing` and then
unconditionally updates `unlocked_by` (line 204). With the fixed billing function,
a `TransactionCanceledException` will propagate from line 192, short-circuit the
`unlocked_by` update, and return HTTP 500 to the client. The message stays locked.
No additional change to `unlock_chat_message` is needed — the exception propagation
does the right thing.

### Change 3 — consolidate into `billing_utils.write_billing_pair()`

This is the fourth occurrence of this anti-pattern. All three broadcast billing
functions (`_write_private_chat_billing`, `_charge_entry_fee`, `_write_chat_billing`)
should be replaced by a shared utility:

```python
# app/services/billing_utils.py (new file)
from __future__ import annotations
import uuid
from typing import Any, Dict, Tuple

from boto3.dynamodb.types import TypeSerializer
from app.core.aws import ddb
from app.core.settings import S
from app.core.time import now_ts

_serializer = TypeSerializer()

def _av(item: Dict[str, Any]) -> Dict[str, Any]:
    return {k: _serializer.serialize(v) for k, v in item.items()}


def write_billing_pair(
    *,
    payer_id: str,
    recipient_id: str,
    debit_amount_cents: int,
    credit_amount_cents: int,
    reason: str,
    meta: Dict[str, Any],
) -> Tuple[str, str]:
    """Atomically write a debit+credit billing ledger pair.

    Raises botocore.exceptions.ClientError with Code=TransactionCanceledException
    if DynamoDB rejects either write. Callers must NOT wrap this in try/except
    unless they intend to handle the failure explicitly (e.g., return 503).
    """
    ts = now_ts()
    debit_id = uuid.uuid4().hex
    credit_id = uuid.uuid4().hex
    billing_table = S.billing_table_name

    debit = {
        "pk": f"USER#{payer_id}",
        "sk": f"LEDGER#{ts}#{debit_id}",
        "entry_id": debit_id, "ts": ts, "type": "debit",
        "amount_cents": debit_amount_cents, "currency": "USD",
        "state": "settled", "reason": reason, "meta": meta,
    }
    credit = {
        "pk": f"USER#{recipient_id}",
        "sk": f"LEDGER#{ts}#{credit_id}",
        "entry_id": credit_id, "ts": ts, "type": "credit",
        "amount_cents": credit_amount_cents, "currency": "USD",
        "state": "settled", "reason": reason, "meta": meta,
    }

    ddb.meta.client.transact_write_items(
        TransactItems=[
            {"Put": {"TableName": billing_table, "Item": _av(debit)}},
            {"Put": {"TableName": billing_table, "Item": _av(credit)}},
        ]
    )
    return debit_id, credit_id
```

All three callers then become one-liners delegating to `write_billing_pair`.

### Dev/prod parity (SECOPS-007)

`TransactWriteItems` is fully supported by moto v4+ (used by pytest offline tests) and
AWS DynamoDB. No conditional import, no `S.dev_mode` guard, no flag needed. The fix
takes the same code path in dev and prod.

### Alternatives considered

1. **Re-raise after credit failure only**: would prevent the "free unlock" scenario but
   leaves the orphan debit. Rejected — still non-atomic.
2. **Compensating write (reverse debit on credit failure)**: adds a second round-trip
   and another potential failure point. Rejected — DDB native transactions are cleaner.
3. **Idempotency key + retry worker**: write to an outbox table first, process
   asynchronously. Overkill for a synchronous purchase flow; increases latency.
   Rejected.

### Backward compatibility / migration

No schema change. Existing ledger rows are unaffected. The `billing` table key schema
(`pk`, `sk`) is compatible with transactional `Put` operations. No migration required.

### Regression test — billing atomicity (pytest, offline)

```python
# tests/services/test_broadcast_chat_rich_billing.py

def test_chat_billing_atomic_credit_failure_no_orphan_debit(moto_billing_table):
    """
    BEFORE fix: credit exception swallowed; debit row exists, credit missing.
    AFTER fix:  TransactionCanceledException propagates; zero billing rows written.
    """
    from botocore.exceptions import ClientError
    from unittest.mock import patch
    from app.services.broadcast_chat_rich import _write_chat_billing
    from app.core.aws import ddb
    import pytest

    def fail_transact(**kwargs):
        raise ClientError(
            {"Error": {"Code": "TransactionCanceledException",
                       "Message": "Cancelled"},
             "CancellationReasons": []},
            "TransactWriteItems",
        )

    with patch.object(ddb.meta.client, "transact_write_items",
                      side_effect=fail_transact):
        with pytest.raises(ClientError, match="TransactionCanceledException"):
            _write_chat_billing(
                payer_id="user_a",
                recipient_id="broadcaster_b",
                amount_cents=500,
                reason="Broadcast chat message unlock",
                content_type="broadcast_chat_unlock",
                content_id="msg_xyz",
                session_id="sess_xyz",
                payment_method_id="pm_abc",
            )

    for uid in ("user_a", "broadcaster_b"):
        resp = moto_billing_table.query(
            KeyConditionExpression="pk = :pk",
            ExpressionAttributeValues={":pk": f"USER#{uid}"},
        )
        assert resp["Count"] == 0, f"Orphan ledger row for {uid} after atomic failure"
```
