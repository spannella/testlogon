# GAP-0203: `provider` Field Unreliable on Ledger Entries — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code in `app/services/billing_shared.py`,
> `app/routers/billing.py`, `app/routers/paypal.py`, `app/services/billing_ccbill.py`,
> and `app/services/platform_financial_dashboard.py`.

## 1. Summary & Classification

**Claim status: Confirmed.** `new_ledger_entry` in `app/services/billing_shared.py:224`
writes `ledger_date` but has no `provider` parameter and does not accept provider in its
`extra` dict by convention. The Stripe call sites (e.g., `billing.py:1000`, `1099`, `2346`)
pass `extra={"stripe_payment_intent_id": ...}` but never `extra={"provider": "stripe"}`.
The PayPal `new_ledger_entry` wrapper in `paypal.py:126` has no `provider` parameter. The
CCBill wrapper in `billing_ccbill.py:191` also has no `provider` field. As a result,
`_provider_for` in `platform_financial_dashboard.py:110` returns `"unknown"` for virtually
all ledger entries, making the provider breakdown chart useless.

- **Severity**: HIGH
- **Source ticket**: FIN-013
- **Status**: Open
- **Owning area**: Billing / Platform Financial Dashboard
- **One-line impact**: The provider breakdown endpoint (`GET
  /ui/admin/financial-dashboard/provider-breakdown`) labels the vast majority of
  transactions as provider `"unknown"`, providing no useful insight into Stripe vs PayPal
  vs CCBill GMV distribution.

**Related tickets**: GAP-0202 (full billing table scan, same FIN-013 source); cross-ref
SEC-004 (payment provider controls). GAP-0202 must be fixed concurrently because both
involve the ledger write path.

## 2. Current-State Investigation (root cause)

### The aggregation side

`app/services/platform_financial_dashboard.py:110`:

```python
def _provider_for(item: Dict[str, Any]) -> str:
    """Best-effort provider label for a ledger entry. The ledger does not
    always store ``provider`` (it lives on payment-method items), so fall
    back to ``unknown`` when absent."""
    return str(item.get("provider") or "unknown")
```

This function correctly reads the `provider` field if it exists, but concedes in its own
docstring that the field is absent from most entries. The fallback `"unknown"` is silently
used for essentially every ledger row.

### The write side

`app/services/billing_shared.py:224–255`:

```python
def new_ledger_entry(
    *,
    key_name: str,
    key_value: str,
    entry_type: str,
    amount_cents: int,
    state: str,
    reason: str,
    meta: Optional[Dict[str, Any]] = None,
    extra: Optional[Dict[str, Any]] = None,
) -> Tuple[str, Dict[str, Any]]:
    ts = now_ts()
    entry_id = ulidish()
    sk = ledger_sk(ts, entry_id)
    item = {
        ...
        "ledger_date": ledger_date_for_ts(ts),
    }
    if extra:
        item.update(extra)   # <-- provider would be written IF caller passed it
    ...
```

The `extra` dict is a pass-through: any key in it ends up on the DynamoDB item. The
mechanism to write `provider` already exists — callers simply do not use it.

### Aggregate effect

In a production system where all three payment providers route through these wrappers,
100% of ledger entries have `provider` absent. The `by_provider` breakdown in
`_aggregate` (`platform_financial_dashboard.py:183–204`) will produce a single bucket
`{"unknown": {"count": N, ...}}` regardless of how many providers are active. The
provider breakdown chart is effectively a pie chart with one slice.

## 3. Impact / Exploit / Blast Radius

- **Data integrity (reporting)**: Finance and operations teams relying on the provider
  breakdown to reconcile Stripe vs PayPal vs CCBill revenue receive zero signal. Platform
  commission tracking, fee analysis, and provider SLA reporting are all blind to provider
  attribution.
- **Compliance**: Payment processors may require per-provider reconciliation reports for
  contractual purposes. A system that cannot distinguish providers in its own ledger fails
  that requirement.
- **Downstream**: `get_provider_breakdown` → `by_provider` → `success_rate` per provider
  is also used by the payment provider health dashboard (`GAP-0204`/`GAP-0205`); lacking
  `provider` on ledger entries means the health dashboard's financial correlation features
  also lose fidelity.
- **No security exposure**: This is a data-quality gap. There is no authorization bypass or
  financial double-write risk.
- **No money-integrity risk**: `amount_cents` and `state` are correctly written. Only the
  `provider` attribution is missing.

---

## 4. Fix Design (code-level)

### Approach: propagate `provider` at every `new_ledger_entry` call site

The `extra` dict mechanism is the correct vehicle. No schema change to `new_ledger_entry`
is strictly required, but adding an explicit `provider` keyword argument makes the
intention clear and prevents future call sites from omitting it accidentally.

#### Option A (minimal — `extra` dict convention): add `"provider"` to every `extra` dict

At each Stripe call site in `billing.py`, change:

```python
# Before (e.g., line 1000):
extra={"stripe_payment_intent_id": pi["id"]},

# After:
extra={"stripe_payment_intent_id": pi["id"], "provider": "stripe"},
```

At each PayPal call site in `paypal.py`, add to the `extra` dict:

```python
extra={"paypal_payment_token_id": token, "provider": "paypal"},
```

At each CCBill call site in `billing_ccbill.py`, extend the `extra` construction:

```python
extra: Dict[str, Any] = {"provider": "ccbill"}
if ccbill_payment_token_id:
    extra["ccbill_payment_token_id"] = ccbill_payment_token_id
...
```

#### Option B (preferred — explicit parameter on wrappers): add `provider` kwarg

This makes omission a linter/type-checker warning rather than a silent data gap.

**`app/services/billing_ccbill.py:191` — add `provider` to CCBill wrapper:**

```python
def new_ledger_entry(
    user_sub: str,
    entry_type: str,
    amount_cents: int,
    state: str,
    reason: str,
    ccbill_payment_token_id: Optional[str] = None,
    ccbill_transaction_id: Optional[str] = None,
    ccbill_subscription_id: Optional[str] = None,
    meta: Optional[Dict[str, Any]] = None,
    provider: str = "ccbill",             # <-- new, defaults to "ccbill"
) -> Tuple[str, Dict[str, Any]]:
    extra: Dict[str, Any] = {"provider": provider}
    if ccbill_payment_token_id:
        extra["ccbill_payment_token_id"] = ccbill_payment_token_id
    ...
    return new_ledger_entry_shared(..., extra=extra or None)
```

**`app/routers/paypal.py:126` — add `provider` to PayPal wrapper:**

```python
def new_ledger_entry(
    user_id: str,
    entry_type: str,
    amount_cents: int,
    state: str,
    reason: str,
    paypal_payment_token_id: Optional[str] = None,
    meta: Optional[Dict[str, Any]] = None,
    provider: str = "paypal",             # <-- new
) -> Tuple[str, Dict[str, Any]]:
    extra: Dict[str, Any] = {"provider": provider}
    if paypal_payment_token_id:
        extra["paypal_payment_token_id"] = paypal_payment_token_id
    ...
```

**`app/routers/billing.py` — all Stripe call sites**: Add `"provider": "stripe"` to each
`extra` dict. The eight affected lines are: 1000, 1099, 1164, 1492, 1521, 2244, 2346, 2409.

**`app/services/billing_shared.py:224` (optional documentation improvement)**: Add a note
to the `new_ledger_entry` docstring that callers should pass `extra={"provider": ...}` for
provider-originating transactions. This does not change behavior but serves as a code-review
checkpoint.

### Migration: backfilling existing ledger entries

Existing production ledger entries lack `provider`. A one-off migration script can
heuristically fill `provider` based on the presence of sibling attributes:

```python
# scripts/backfill_ledger_provider.py
# For each LEDGER# item missing "provider":
#   if "stripe_payment_intent_id" in item  → provider = "stripe"
#   if "paypal_payment_token_id"  in item  → provider = "paypal"
#   if "ccbill_transaction_id"    in item  → provider = "ccbill"
#   else                                   → provider = "unknown" (leave as-is)
```

This backfill is heuristic but correct for the existing write paths because each provider
always sets its own identifier field.

### Dev/Prod parity (SECOPS-007)

`new_ledger_entry` uses `T.billing` which routes to DynamoDB Local in dev and real DynamoDB
in production via `app/core/tables.py`. The `extra` dict propagation is identical in both
environments. No mock branch or `S.dev_mode` flag is introduced. The CCBill and PayPal
paths are tested by their respective E2E tests (`billing.spec.ts`, `paypal.spec.ts`). These
tests run against the local dev stack and will confirm `provider` is written correctly.

### Alternatives considered

- **Derive provider from payment-method row at query time**: The PM item
  (`sk = PM#<pm_id>`) carries `provider`. The aggregation could join each ledger entry to
  its PM row to look up provider. Rejected: this turns one scan into one scan plus N
  point-reads (one per ledger entry), multiplying DDB cost. Also, not all ledger entries
  have a `payment_method_id`.
- **Separate provider-keyed ledger table**: Long-term architectural improvement (a
  `billing_ledger_by_provider` table or GSI). Correct direction but too disruptive for this
  ticket. The `extra` dict fix is backward-compatible and deployable in hours.
- **Infer from `reason` field**: Reasons like `"wallet_deposit"` or `"tip_debit"` do not
  uniquely identify a provider. Rejected as insufficiently precise.

### Manual QA steps

1. Apply the code changes to all three provider paths.
2. Run `just restart` and seed a wallet deposit (Stripe), a PayPal top-up, and a CCBill
   subscription charge via the dev stack.
3. Call `GET /ui/admin/financial-dashboard/provider-breakdown?start_date=<today>&end_date=<today>`
   as a ROOT user.
4. Verify the response `data` array contains distinct rows for `stripe`, `paypal`, and
   `ccbill` with non-zero `total_cents`.
5. Inspect the DynamoDB Local `billing` table directly (e.g., via DynamoDB Local shell or
   a scan in pytest) to confirm `provider` is present on each new `LEDGER#` item.

### Backfill verification

After running the backfill script on production:

1. Count `LEDGER#` items with `provider = "unknown"` — should be zero (or only entries
   from before any of the three provider paths were introduced).
2. Count by provider and cross-reference with Stripe, PayPal, and CCBill reconciliation
   reports for the same period.

### Rollout and risks

- **Effort**: M (code change is small; the backfill script and production verification add
  complexity).
- **Risk**: LOW for the code change itself — adding a new field to `extra` is backward-
  compatible and cannot break existing reads. The DynamoDB item size increase per entry is
  ~15 bytes (`"provider": "stripe"` or `"paypal"` or `"ccbill"`), negligible.
- **Risk (backfill)**: MEDIUM — a batch update script touching millions of `LEDGER#` rows
  must be rate-limited to avoid consuming all DynamoDB write capacity. Use
  `ProvisionedThroughput` guardrails or run the backfill during low-traffic hours.
- **Rollback**: If the backfill produces incorrect provider assignments, the `provider`
  field can be removed from affected items without breaking financial calculations (the
  dashboard simply falls back to `"unknown"` again). The code-path fix (adding `provider`
  to `extra`) is non-destructive and needs no rollback.
- **Sequencing**: Code change and backfill can be deployed independently. Deploying the
  code change first ensures all new transactions are correctly attributed from day one;
  the backfill fills in historical data afterward.
