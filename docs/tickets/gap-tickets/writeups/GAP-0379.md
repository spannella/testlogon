# GAP-0379: Concat Job Exception Never Calls `fail_job` — Remediation Write-up

> Source ticket: VOD-016 · Severity: HIGH · Effort: S · Status: Open

## 1. Summary & Classification

**Bug statement.** When `execute_concat` in `app/services/video_concatenator.py` raises any exception — S3 download failure, FFmpeg crash, DynamoDB update error, or scratch-disk full — the concat job record in DynamoDB is permanently left in `status = "running"`. The `except Exception` clause at line 308 logs the exception but never calls `fail_job(job_id, ...)`. The job is frozen in `running` forever: no retry, no terminal failure transition, and no user-visible error.

**Verdict:** Confirmed. Lines 308–310 of `app/services/video_concatenator.py` are:

```python
    except Exception:
        logger.exception("Concat job %s failed", job_id)
        raise
```

No call to `fail_job` anywhere in this block. The `fail_job` function exists at `app/services/transcode_job_store.py:244` and handles retry/terminal-failure correctly. This is the exact same defect as GAP-0377 (clip job), applied to the concat pipeline.

**Severity and area.** HIGH / Video Processing. A stuck-running job is never retried; the user's combine-videos creation silently hangs indefinitely with `status = "running"` and no recovery path. The gap is particularly impactful for the concat path because it involves multiple S3 downloads (one per input video), increasing the probability of a transient error.

**Related tickets.** VOD-016 (source feature), GAP-0377 (identical pattern in `video_clipper.py`), GAP-0378 (`-safe 0` security issue in the same file). All three should be fixed in the same PR.

## 2. Current-State Investigation (root cause)

### The job processing loop

`execute_concat` at `app/services/video_concatenator.py:218` orchestrates the full concat pipeline:

1. Downloads all source files from S3 (lines 246–249, one `s3.download_file` call per input).
2. Updates job progress to 10% (line 253).
3. Runs FFmpeg concat via `_run_concat_demuxer` or `_run_concat_filter` (lines 258–264).
4. Updates progress to 70% (line 266).
5. Uploads the output to S3 (lines 269–270).
6. Probes the output duration via `_probe_duration` (line 273).
7. Updates video metadata in DynamoDB (lines 274–287).
8. Updates progress to 80% (line 289).
9. Enqueues a standard transcode job for ABR (lines 292–299).
10. Calls `complete_job(job_id, ...)` (line 303).
11. Updates progress to 100% (line 304).

The `try` block begins at line 240. The `except` clause at line 308 reads:

```python
# app/services/video_concatenator.py:308-312
    except Exception:
        logger.exception("Concat job %s failed", job_id)
        raise
    finally:
        shutil.rmtree(scratch_dir, ignore_errors=True)
```

No state transition is written on failure. The job remains at `status = "running"` — or at whatever partial progress percentage was last written — with no `error_message` and no path to completion.

### What `fail_job` does

`app/services/transcode_job_store.py:244–294` implements the correct retry/fail logic identical to what GAP-0377 describes:

```python
def fail_job(job_id: str, error_message: str, attempt: int) -> Dict[str, Any]:
    ts = now_ts()
    max_attempts = S.transcode_max_attempts
    new_attempt = attempt + 1
    if new_attempt < max_attempts:
        # Exponential backoff: back to queued with next_retry_at
        T.transcode_jobs.update_item(
            ..., ExpressionAttributeValues={
                ":queued": "queued", ":att": new_attempt, ":nra": next_retry_at, ...
            }
        )
    else:
        # Terminal: status = "failed"
        T.transcode_jobs.update_item(
            ..., ExpressionAttributeValues={":failed": "failed", ":att": new_attempt, ...}
        )
    return get_job(job_id)
```

This function is used by the regular transcode worker but never invoked in the concat path.

### How `attempt` reaches `execute_concat`

The `job` dict parameter carries `attempt` (set to `0` at creation by `create_job`). `execute_concat` extracts `job_id`, `video_id`, `owner`, `s3_keys`, `method`, and `est_duration` from `job` at lines 230–235, but does not extract `attempt`. The fix must use `job.get("attempt", 0)` in the `except` block.

### Multi-step failure surface

The concat job has a notably longer failure surface than the clip job:

- Each of N source file S3 downloads (step 1) can fail independently.
- `update_job_progress` (step 2, 4, 8) calls `T.transcode_jobs.update_item` — a DDB failure here also triggers the except block.
- `_run_concat_demuxer` / `_run_concat_filter` (step 3) can time out or crash FFmpeg.
- `s3.upload_file` (step 5) can fail with network errors.
- `T.video_metadata.update_item` (step 7) can fail with conditional check failures.

Any of these — in production, S3 throttling or a spotty network are realistic — leaves the job frozen without the fix.

### Runtime manifestation

After any exception during `execute_concat`:

- `T.transcode_jobs` record: `status = "running"`, `worker_id = <worker>`, `progress_pct` frozen at whatever was last written (e.g., `10` if it failed during or after step 2), no `error_message`, no `completed_at`.
- Worker queue: workers skip jobs already in `running` state (they poll for `status = "queued"`), so the job is invisible for retry.
- User-visible: the combine-result video card stays at `status = "pending_encoding"` or `"created"`, with no error surface.
- No automatic recovery; manual DDB intervention is required to reset the job.

## 3. Impact / Exploit / Blast Radius

**User impact.** Any combine-videos attempt that encounters an infrastructure error — transient S3 error, FFmpeg not installed, disk full, DynamoDB throttle — silently hangs forever. The user's only recourse is to contact support, who must manually update DynamoDB.

**Compounding with large input sets.** The concat job downloads N source files before FFmpeg runs. With the default `S.video_concat_max_inputs = 10`, up to 10 S3 downloads occur sequentially. The probability of at least one transient error grows with N, making this bug more likely to manifest for larger concat jobs — precisely the use case users pay most for.

**Operational accumulation.** In production, each failed but unrecovered concat job leaves an orphaned `running` record. These accumulate over time, polluting job dashboards and potentially confusing worker health checks that count running jobs. A CloudWatch alarm set on `running_job_count > threshold` will fire persistently, degrading the signal-to-noise ratio for real worker failures.

**Security.** No confidentiality or integrity concern. Scratch directories are cleaned by the `finally` block (line 311–312), so no temporary files are left on disk even in the failure case.

**Financial.** No direct financial impact. Indirect impact through user frustration and support cost. For a creator who used credits or a subscription entitlement to trigger a combine operation, a permanently stuck job is a lost entitlement with no self-service remedy.

**Support cost.** Users who encounter the bug will open support tickets. Resolution requires manual DynamoDB intervention (`UPDATE transcode_jobs SET status = 'failed' WHERE job_id = ...`). This is an O(incident) cost per affected user with no automated recovery path.

## 4. Fix Design (code-level)

### Minimal fix: call `fail_job` in the `except` block

The fix is structurally identical to the GAP-0377 fix, applied to `execute_concat`:

```python
# app/services/video_concatenator.py — replace lines 308-310
    except Exception as e:
        logger.exception("Concat job %s failed", job_id)
        try:
            from app.services.transcode_job_store import fail_job
            fail_job(job_id, str(e), job.get("attempt", 0))
        except Exception:
            logger.exception("fail_job itself failed for concat job %s", job_id)
        raise
```

Key design choices:

- **`job.get("attempt", 0)`**: `job` is the parameter of `execute_concat`; it is in scope throughout the function. Default `0` handles the edge case where the job record was created without an `attempt` field.
- **Inner try/except around `fail_job`**: Guards against a DynamoDB failure inside `fail_job` masking the original exception. The original exception is always re-raised.
- **`raise` preserved**: The worker loop still sees the original exception and can log it independently.

### Full corrected function signature (relevant lines only)

```python
async def execute_concat(job: Dict[str, Any]) -> None:
    ...
    job_id = job["job_id"]
    ...
    try:
        # ... existing success path (lines 241-304) unchanged ...
        complete_job(job_id, output_manifest_uri=dest_key)
        update_job_progress(job_id, progress_pct=100)
        logger.info("Concat job %s completed: method=%s", job_id, method)

    except Exception as e:                                          # ← was: except Exception:
        logger.exception("Concat job %s failed", job_id)
        try:                                                        # ← new
            from app.services.transcode_job_store import fail_job  # ← new
            fail_job(job_id, str(e), job.get("attempt", 0))        # ← new
        except Exception:                                           # ← new
            logger.exception("fail_job itself failed for %s", job_id)  # ← new
        raise
    finally:
        shutil.rmtree(scratch_dir, ignore_errors=True)
```

### Dev/Prod parity (SECOPS-007)

`fail_job` calls `T.transcode_jobs.update_item(...)`. In dev, `T.transcode_jobs` is backed by DynamoDB Local (port 8001); in production it is the real DynamoDB table. The `app/core/tables.py` `T` singleton handles this routing via `S.ddb_transcode_jobs_table` and `S.ddb_endpoint_url`. No environment-specific branching is needed.

`execute_concat` is invoked by the same worker process in both dev (inline in FastAPI) and production (ECS task or Lambda). The fix is unconditional and environment-agnostic.

### Interaction with GAP-0378

GAP-0378 adds a `ConcatError` raise inside `_run_concat_demuxer` for path-escape conditions. With this fix in place, that `ConcatError` will also correctly trigger `fail_job`, transition the job to `failed`, and surface the error message in the job record. Without this fix, a GAP-0378-triggered `ConcatError` would also leave the job frozen in `running`. The two fixes are mutually reinforcing and must both be applied for the concat pipeline to have correct error handling end-to-end.

### Alternative considered: wrap at the worker loop level

As with GAP-0377, one could move `fail_job` into the worker polling loop rather than into `execute_concat`. This is rejected for the same reasons: the worker loop is shared across job types, the `job` dict is already in scope inside `execute_concat`, and the fix is simpler and more explicit at the service level. Applying the fix at the service level also means unit tests can exercise the `fail_job` path directly without setting up a full worker loop harness.

### Backward compatibility

No DynamoDB schema changes. `error_message`, `attempt`, and `next_retry_at` attributes are already present in the `transcode_jobs` table (used by the regular transcode path). No migration required.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline — fails before, passes after)

```python
# tests/test_video_concatenator_fail_job.py
import pytest
from unittest.mock import patch, AsyncMock, MagicMock

@pytest.mark.asyncio
async def test_execute_concat_calls_fail_job_on_s3_error(mock_ddb_tables):

        "job_id": "job_concat_001",
        "video_id": "vid_concat_001",
        "tenant_id": "user_001",

                                   "videos/user_001/vid_b/source.mp4"],

        mock_s3 = MagicMock()

        with patch("app.services.transcode_job_store.fail_job") as mock_fail:
            from app.services.video_concatenator import execute_concat
```

**After fix:** all three tests pass.

### Manual QA steps

1. `just restart` to get a clean dev stack.
2. Create two published videos. Stop the backend before the S3 download completes by inserting a temporary delay or by temporarily removing the moto S3 bucket.
3. Submit a combine-videos request via the VideosPage combine dialog.
4. Query the `TranscodeJobs` DynamoDB table:
   - **Before fix:** `status = "running"`, no `error_message`.
   - **After fix:** `status = "queued"` (if attempts < max) with `error_message` populated, or `status = "failed"` if max attempts exhausted.
5. Re-enable S3 and verify the worker picks up and completes the retried job.

### Metrics and observability

- Add a CloudWatch metric filter for `"fail_job itself failed for concat job"` in the worker log group.
- Add a CloudWatch alarm: `status = "running" AND updated_at < now - 3600` (jobs stuck running for more than 1 hour) as a canary for this class of bug in any job type.

### Rollout

- **Effort:** S (small — same two-line pattern as GAP-0377; ship in the same commit).
- **Risk:** Very low. The fix adds a `fail_job` call only in the exception path, which was previously a no-op.
- **Sequencing:** Fix GAP-0377, GAP-0378, and GAP-0379 together in one PR. All three are in the `video_clipper.py` / `video_concatenator.py` files and share a single PR review cycle.
- **Rollback:** Revert the three added lines; the job will again be left in `running` on failure.

### Acceptance criteria

The fix is complete when:
1. A concat job that fails during S3 download transitions to `status = "queued"` (if `attempt < max_attempts`) or `status = "failed"` with `error_message` populated.
2. A concat job that fails mid-FFmpeg also triggers `fail_job` and transitions state correctly.
3. `fail_job` is never called on the success path.
4. All three new pytest tests in `tests/test_video_concatenator_fail_job.py` pass green in CI.
5. Manual QA in dev confirms the job record transitions to `failed` rather than staying `running` after a simulated S3 download error.
