# GAP-0025: Webhook Secret Stored in Plaintext in DynamoDB — Remediation Write-up

> ~5 pages. Fix-oriented. Built on investigation doc: `docs/tickets/gap-tickets/investigations/GAP-0025.md`.
> Note: the GAP ticket description implies the issue is platform-wide; the investigation
> confirms the plaintext storage is **isolated to `kyc_partner_api.py`**. The general-
> purpose `webhook_service.py` already uses KMS encryption correctly.

## 1. Summary & Classification

**Bug statement**: `register_webhook()` in `app/services/kyc_partner_api.py:534-546`
stores the caller-supplied webhook `secret` as a verbatim string in the `kyc_cases`
DynamoDB table with no encryption. Additionally, `list_webhooks()` at line 550-568 does
not redact the `secret` field from query results; any caller who retrieves the webhook
list receives the secret in plaintext. The secret is intended for HMAC-SHA256 signing of
outbound KYC partner webhook deliveries: its exposure allows an attacker to forge
arbitrary KYC status-change events to the partner.

| Field | Value |
|-------|-------|
| Severity | **CRIT** |
| Status | Open |
| Source ticket | KYC-021 |
| Owning area | KYC / partner API / secrets management |
| Investigation verdict | **Partially confirmed** — plaintext in `kyc_partner_api.py:543`; `webhook_service.py` is already fixed |
| Related policy | SEC-022 (secrets must be KMS-encrypted at rest) |
| Effort | M (2-4 hours) |

**One-line impact**: Any principal with DynamoDB read access to the `kyc_cases` table
can retrieve all KYC partner webhook secrets in plaintext and use them to forge `kyc.case.approved` events, granting fraudulent KYC clearance.

**Related tickets**: KYC-021 (partner webhook design), SEC-022 (KMS at-rest encryption
policy), GAP-0009 (SSRF via custom base URL — separate partner API issue).

## 2. Current-State Investigation (root cause)

### What the general webhook service does correctly

`app/services/webhook_service.py:245-250` already implements KMS encryption at
registration time:

```python
# webhook_service.py:245-250 — create_endpoint()
try:
    encrypted_secret = kms_encrypt(plaintext_secret)
except Exception:
    encrypted_secret = f"PLAIN:{plaintext_secret}"   # dev-mode fallback
```

A matching `_decrypt_secret()` at line 506-510 handles both encrypted blobs and the
`PLAIN:` prefix. The `kms_encrypt` / `kms_decrypt` utilities in `app/core/crypto.py`
proxy to the mock KMS server (port 7999) in dev and to real AWS KMS in production.

This pattern is correct, established, and tested. The KYC partner API simply did not
reuse it.

### The plaintext storage in `kyc_partner_api.py`

`register_webhook()` at `app/services/kyc_partner_api.py:534-546`:

```python
T.kyc_cases.put_item(
    Item={
        "pk": _partner_pk(partner_id),
        "sk": _wh_sk(webhook_id),
        "entity_type": "kyc_partner_webhook",
        "webhook_id": webhook_id,
        "partner_id": partner_id,
        "url": str(url),
        "events": list(events),
        "secret": str(secret),          # <-- plaintext, line 543
        "created_at": ts,
    }
)
```

The function returns `{"webhook_id": ..., "url": ..., "events": ..., "created_at": ...}`
at line 547 — it does not include the secret in the return value. However, the secret
is permanently stored in the `kyc_cases` table unencrypted.

### The `list_webhooks()` exposure

`list_webhooks()` at lines 550-568 queries all webhook items for a partner and
constructs an output list. The current implementation:

```python
out.append(
    {
        "webhook_id": str(row.get("webhook_id") or ""),
        "url": str(row.get("url") or ""),
        "events": list(row.get("events") or []),
        "created_at": int(row.get("created_at") or 0),
    }
)
```

Notably, the `secret` field is **not** included in the output dict — so the list
endpoint does not currently return the secret to API callers. However:

1. The raw `row` dict (containing `"secret": "plaintext"`) is iterated in full and any
   logging path that captures `row` exposes the secret.
2. If `list_webhooks()` is ever extended to include the secret for rotation confirmation,
   it would return it in plaintext.
3. The DynamoDB item is the authoritative risk: any principal with table read access
   (DynamoDB console, internal tooling, backups) can read the secret directly.

### Root cause

`kyc_partner_api.py` was implemented after `webhook_service.py` but as a separate,
independent module. The author treated the `secret` as a pass-through opaque string
rather than a sensitive credential requiring at-rest encryption. There is no linter
rule, code review checklist item, or automated check that enforces SEC-022 compliance
for new DynamoDB writes.

### No decrypt path

Unlike `webhook_service.py`, `kyc_partner_api.py` has no `_decrypt_secret()` function.
The `_emit_callback()` function at lines 615-625 delegates to
`webhook_service.dispatch_webhook_event`, which has its own secret management; it does
not read the partner-stored secret directly. This means the plaintext secret is currently
orphaned: it is stored but never read back for signing purposes, making it a dormant
credential leak rather than an actively-used insecure value. However, the leak risk
exists permanently and the secret may be used for signing in future code changes.

## 3. Impact / Exploit / Blast Radius

### Direct credential exfiltration

The `kyc_cases` DynamoDB table PK prefix `KYCPARTNER#` is queryable by any IAM principal
with `dynamodb:Query` on the table. In production this includes:

- The backend application role (broad DynamoDB access by design).
- Any admin or ops principal with DynamoDB console access.
- Any attacker who has exfiltrated IAM credentials via another vector (e.g., SSRF,
  instance metadata, GAP-0022).

A query `KeyConditionExpression=Key("pk").begins_with("KYCPARTNER#")` returns every
partner's webhook configurations with plaintext secrets.

### Webhook forgery

Webhook secrets are used as HMAC-SHA256 signing keys for outbound KYC event deliveries.
An exfiltrated secret allows an attacker to construct valid `X-KYC-Signature` headers
and POST arbitrary `kyc.case.approved` or `kyc.case.rejected` payloads to the partner's
endpoint. Partners that rely on webhook HMAC validation to drive business logic — such
as granting access to services upon KYC approval — would be deceived into granting
access to unverified users.

### The `kyc_cases` table contains co-located PII

Because the `kyc_cases` table uses single-table design with multiple entity types,
a compromise of the table (enabled by exfiltrated credentials from the plaintext
secret) simultaneously exposes KYC case records, document metadata, and user PII stored
under other key prefixes.

### Severity escalation factors

- The `kyc.case.approved` event can grant compliance-gated access.
- KYC fraud (bypassing identity verification) is a regulatory offence (BSA / AML).
- A DynamoDB backup that contains the plaintext secret exposes the secret indefinitely
  even after rotation.

## 4. Fix Design (code-level)

### Fix A: Encrypt on write, decrypt on read

Update `register_webhook()` to encrypt the secret using the established `kms_encrypt` /
`PLAIN:` fallback pattern from `webhook_service.py`:

```python
# app/services/kyc_partner_api.py — register_webhook() after fix

def register_webhook(
    principal: Dict[str, Any],
    *,
    url: str,
    events: List[str],
    secret: str,
) -> Dict[str, Any]:
    partner_id = _partner_id(principal)
    invalid = sorted({e for e in events if e not in _ALLOWED_WEBHOOK_EVENTS})
    if invalid:
        raise HTTPException(status_code=400, detail={
            "code": "kyc_api_webhook_url_invalid",
            "message": f"Invalid event(s): {', '.join(invalid)}",
        })

    from app.core.crypto import kms_encrypt
    try:
        stored_secret = kms_encrypt(secret)
    except Exception:
        stored_secret = f"PLAIN:{secret}"   # dev-mode fallback when KMS mock is unavailable

    ts = now_ts()
    webhook_id = f"wh_{uuid.uuid4().hex[:16]}"
    T.kyc_cases.put_item(
        Item={
            "pk": _partner_pk(partner_id),
            "sk": _wh_sk(webhook_id),
            "entity_type": "kyc_partner_webhook",
            "webhook_id": webhook_id,
            "partner_id": partner_id,
            "url": str(url),
            "events": list(events),
            "secret": stored_secret,        # encrypted
            "created_at": ts,
        }
    )
    # Return plaintext secret once at registration time; never again
    return {
        "webhook_id": webhook_id,
        "url": str(url),
        "events": list(events),
        "created_at": ts,
        "secret": secret,                   # one-time plaintext response
    }
```

### Fix B: Add `_decrypt_kyc_partner_secret()` helper

Add a decrypt helper mirroring `webhook_service._decrypt_secret()` for use when the
secret must be read back (HMAC signing at emit time):

```python
def _decrypt_kyc_partner_secret(stored: str) -> str:
    """Decrypt a KYC partner webhook secret stored in DynamoDB."""
    if stored.startswith("PLAIN:"):
        return stored[6:]
    from app.core.crypto import kms_decrypt
    return kms_decrypt(stored).decode("utf-8")
```

### Fix C: Redact secret from `list_webhooks()` output

`list_webhooks()` currently omits the secret from the output dict. This is the correct
behaviour; ensure it is documented and test-covered so it does not regress:

```python
# In list_webhooks(), explicitly do NOT include "secret" in the output:
out.append({
    "webhook_id": str(row.get("webhook_id") or ""),
    "url": str(row.get("url") or ""),
    "events": list(row.get("events") or []),
    "created_at": int(row.get("created_at") or 0),
    # "secret" intentionally omitted — never expose stored secrets in list responses
})
```

Add a comment to prevent future accidental inclusion.

### Fix D: Secret rotation endpoint (future)

Allow partners to rotate their webhook secret. The rotation endpoint should:
1. Generate or accept a new secret.
2. Encrypt it with `kms_encrypt`.
3. Update the DynamoDB item.
4. Return the new plaintext once.

This is out of scope for the immediate fix but should be tracked as a follow-up.

### Dev/Prod parity (SECOPS-007)

`kms_encrypt` in `app/core/crypto.py:16-20` calls the KMS client from `app/core/aws.py`.
In dev, the mock KMS server runs at port 7999 and is started by
`scripts/mock_kms_server.py`. When `S.kms_key_id` is unset or the mock is unavailable,
`kms_encrypt` raises `RuntimeError("KMS_KEY_ID not set")`, which is caught by the
`except Exception` block and falls back to `PLAIN:{secret}`. This is the same pattern
as `webhook_service.py`. In production, `S.kms_key_id` is populated from the environment
and real AWS KMS is used. No new infrastructure is required.

The `PLAIN:` prefix fallback exists only to prevent development from being blocked by a
missing KMS mock. In production this branch is unreachable because `KMS_KEY_ID` is always
set. A production health check should assert `S.kms_key_id` is non-empty at startup.

### Migration for existing plaintext secrets

Existing webhook registrations in DynamoDB contain plaintext secrets. A one-time
migration script should:

1. Query all items with `entity_type = "kyc_partner_webhook"`.
2. For each item where `secret` does not start with `PLAIN:` and does not look like a
   base64 KMS ciphertext (heuristic: length > 80 characters), encrypt the secret with
   `kms_encrypt` and update the item.
3. Mark the migration as complete in a DynamoDB config row.

This migration should be run once immediately after deploying the fix, before the `PLAIN:`
fallback window closes.

### Manual QA steps

2. Register a KYC partner webhook via `POST /ui/kyc/partner/webhooks` with a known secret.

### Migration script (one-time)

```python
# scripts/migrate_kyc_partner_webhook_secrets.py
from app.core.tables import T
from app.core.crypto import kms_encrypt
import base64

def is_already_encrypted(s):
    if s.startswith("PLAIN:"):
        return True
    try:
        decoded = base64.b64decode(s)
        return len(decoded) > 32  # KMS ciphertexts are at least 45 bytes
    except Exception:
        return False

def migrate():
    resp = T.kyc_cases.scan(
        FilterExpression="entity_type = :t",
        ExpressionAttributeValues={":t": "kyc_partner_webhook"},
    )
    for item in resp.get("Items", []):
        secret = item.get("secret", "")
        if is_already_encrypted(secret):
            continue
        encrypted = kms_encrypt(secret)
        T.kyc_cases.update_item(
            Key={"pk": item["pk"], "sk": item["sk"]},
            UpdateExpression="SET #s = :s",
            ExpressionAttributeNames={"#s": "secret"},
            ExpressionAttributeValues={":s": encrypted},
        )
        print(f"Migrated {item['webhook_id']}")

if __name__ == "__main__":
    migrate()
```

Run once after deploying the code fix.

### Rollback

Remove the `kms_encrypt` call and `_decrypt_kyc_partner_secret` helper; revert the
`put_item` to use `"secret": str(secret)`. No schema changes required. The migration
script cannot be automatically rolled back (already-encrypted secrets would need manual
decryption if the `_decrypt_kyc_partner_secret` helper is removed before secrets are
rotated).

### Risk

**Medium**. The `PLAIN:` fallback means no functionality is broken if KMS is unavailable
in dev. The migration script uses a `scan()` which is appropriate for a one-time
migration on a table that is not expected to have millions of rows. The primary rollback
risk is if the decrypt path is deployed incorrectly; thorough testing of the round-trip
before deploying to production is essential.

### Effort

**M** — estimated 2-4 hours: add encrypt call in `register_webhook()`, add
`_decrypt_kyc_partner_secret()`, add comment in `list_webhooks()`, write four pytest
tests, write migration script, run `just test`.

### Sequencing

1. Deploy code fix (encrypt on write, add decrypt helper, redact from list).
2. Run migration script against production DynamoDB to encrypt existing plaintext secrets.
3. Verify no `PLAIN:` secrets remain in the table.
4. After all partners have been notified and have had time to rotate, consider making the
   `PLAIN:` fallback a hard error in production by checking `S.dev_mode` before falling
   back.
