# GAP-0347: Low-Stock Alert Has No Throttle/Dedup — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`. No investigation doc exists.

## 1. Summary & Classification

**Bug statement.** The `_check_low_stock_alert` function in `app/routers/catalog.py` (lines 611–636) fires `write_alert` unconditionally every time a stock adjustment moves the count at or below the low-stock threshold. On a high-velocity item (e.g., a flash sale), hundreds or thousands of concurrent `PATCH /items/{item_id}/stock` calls can all cross the threshold simultaneously, each one writing a separate alert row. The original SHOP-001 ticket specified a 1-hour TTL sentinel key that would de-duplicate these alerts, but the implementation was never added.

- **Severity**: HIGH — alert flooding can saturate the alert pipeline, obscure real operational signals, and impose runaway DynamoDB write costs.
- **Source ticket**: SHOP-001 (inventory management); cross-ref SEC-024 (e-commerce price/entitlement abuse), GAP-0347
- **Status**: Open
- **Owning area**: Shop / Catalog / `app/routers/catalog.py`
- **Claim verdict**: CONFIRMED. `_check_low_stock_alert` at line 611 calls `write_alert` with no guard, no TTL, and no sentinel check. A grep for `ConditionExpression`, `attribute_not_exists`, `TTL`, `ttl`, or `sentinel` in `app/routers/catalog.py` returns zero results for the low-stock code path. The stock-alerts feature flag `S.catalog_stock_alerts_enabled` (settings.py:790) exists but only provides a global on/off switch — it does not prevent per-event flooding within an enabled window.
- **Related tickets**: SHOP-001, SEC-024, SECOPS-007 (dev/prod parity)

## 2. Current-State Investigation (root cause)

### Code path

Stock is adjusted via `PATCH /ui/catalog/items/{item_id}/stock` (`adjust_stock`, line 656). After every successful update, `_check_low_stock_alert` is called with the updated item and new stock count (lines 686 and 713 for the absolute and delta branches respectively).

`_check_low_stock_alert` (lines 611–636):

```python
def _check_low_stock_alert(item: dict, new_stock: int) -> None:
    if not S.catalog_stock_alerts_enabled:
        return
    threshold = int(item.get("low_stock_threshold") or S.catalog_default_low_stock_threshold)
    if new_stock <= threshold and new_stock >= 0:
        try:
            from app.services.alerts import write_alert
        except Exception:
            return
        creator_id = item.get("creator_id")
        if creator_id:
            try:
                write_alert(
                    creator_id,
                    event="catalog.low_stock",
                    outcome="warning",
                    title=f"Low stock: {item.get('name', 'Unknown item')} ({new_stock} remaining)",
                    details={
                        "item_id": item.get("item_id"),
                        "item_name": item.get("name"),
                        "stock_count": new_stock,
                        "threshold": threshold,
                    },
                )
            except Exception:
                pass
```

The condition `new_stock <= threshold and new_stock >= 0` remains true for every sale once stock crosses the threshold. At stock = 5 (the default threshold `S.catalog_default_low_stock_threshold`, settings.py:789), any subsequent sale at stock 5, 4, 3, 2, 1, or 0 each triggers another alert.

### Alert write path

`write_alert` writes a row to `T.alerts` (the DynamoDB `alerts` table, PK `user_sub`, SK `alert_id`). Each call generates a new `alert_id` (UUID), so there is no natural de-duplication. For a creator with 1000 stock-decrement events per hour, this writes 995 spurious alert rows (1000 − 5 initial valid threshold-crossing writes). The alerts UI and alert delivery pipeline process each row independently.

### What the DDB catalog table looks like

The `shopping_catalog` table (local-ddb-init.py:96–100) has a `GSI1` index with `GSI1PK`/`GSI1SK` but no dedicated sentinel or dedup table. There is no existing `alert_sentinels` or similar table. The sentinel must either live in the existing `T.alerts` table or in a new lightweight sentinel table. Using a dedicated sentinel record in the same `T.alerts` table (with a fixed SK pattern and a TTL attribute) is the cleanest approach that avoids adding a new table.

### Dev vs. production behavior difference (SECOPS-007)

In dev (`S.dev_mode = True`), `S.catalog_stock_alerts_enabled` defaults to `true` (settings.py:790). In production it is also `true` unless overridden by `CATALOG_STOCK_ALERTS_ENABLED=0`. Both paths execute identically — there is no mock divergence here. The fix must also apply identically in both environments.

## 3. Impact / Exploit / Blast Radius

### Alert storm

A single flash-sale event for a popular item with, say, an initial stock of 1000 units and a threshold of 5 generates up to 996 alert writes in rapid succession. At scale across multiple creators and items, this can:

1. **Saturate the DynamoDB `alerts` table** write capacity — in production (provisioned WCU) this triggers throttled write errors and partial delivery failures. In dev (on-demand) the bill spikes.
2. **Flood the in-app alert notification system** — each `write_alert` call may trigger a push notification, email, or SMS depending on the user's alert preferences (`app/services/alerts.py`). A creator receiving 996 "Low stock" SMS messages in an hour is a serious UX failure and a potential carrier-abuse vector.
3. **Mask real alerts** — the alerts UI, which paginates, will show hundreds of identical low-stock rows, pushing unrelated security or billing alerts off the first page.

### Economic abuse vector (cross-ref SEC-024)

If alert delivery incurs per-message costs (SMS/email) billed to the platform, an adversary who controls a seller account could deliberately trigger thousands of tiny stock decrements just below the threshold to generate platform-billed notifications at scale. Cost amplification ratio = (threshold value) × (stock-decrement events).

### Data integrity

Because each alert row has a unique UUID SK, none of them can be individually deduped after the fact without a full scan. Remediation after a flood requires manual DDB cleanup.

## 4. Fix Design (code-level)

### 4a. Sentinel strategy

Use a conditional `put_item` with `attribute_not_exists` on a sentinel key in `T.alerts` plus a DynamoDB TTL attribute. The sentinel key is:

- **PK**: `ALERT_SENTINEL#{creator_id}` (a synthetic user_sub-shaped prefix that will never match a real user)
- **SK**: `LOW_STOCK#{item_id}`

When the sentinel does not exist, the `put_item` succeeds → alert fires. When it already exists (within the 1-hour TTL window), `put_item` raises `ConditionalCheckFailedException` → alert is suppressed. DynamoDB TTL automatically expires the sentinel after 1 hour.

### 4b. Updated `_check_low_stock_alert`

Replace lines 611–636 of `app/routers/catalog.py` with:

```python
_LOW_STOCK_SENTINEL_TTL_SECONDS = 3600  # 1 hour


def _check_low_stock_alert(item: dict, new_stock: int) -> None:
    if not S.catalog_stock_alerts_enabled:
        return
    threshold = int(item.get("low_stock_threshold") or S.catalog_default_low_stock_threshold)
    if new_stock > threshold or new_stock < 0:
        return
    creator_id = item.get("creator_id")
    if not creator_id:
        return

    item_id = str(item.get("item_id") or item.get("SK") or "unknown")
    sentinel_pk = f"ALERT_SENTINEL#{creator_id}"
    sentinel_sk = f"LOW_STOCK#{item_id}"
    expires_at = now_ts() + _LOW_STOCK_SENTINEL_TTL_SECONDS

    try:
        T.alerts.put_item(
            Item={
                "user_sub": sentinel_pk,
                "alert_id": sentinel_sk,
                "ttl": expires_at,
                "sentinel": True,
            },
            ConditionExpression="attribute_not_exists(user_sub) AND attribute_not_exists(alert_id)",
        )
    except Exception as exc:
        # ConditionalCheckFailedException means sentinel already exists — suppress alert
        if "ConditionalCheckFailed" in type(exc).__name__ or "ConditionalCheckFailed" in str(exc):
            return
        # Unexpected DDB error: log and suppress to avoid breaking the stock adjustment
        return

    try:
        from app.services.alerts import write_alert
        write_alert(
            creator_id,
            event="catalog.low_stock",
            outcome="warning",
            title=f"Low stock: {item.get('name', 'Unknown item')} ({new_stock} remaining)",
            details={
                "item_id": item_id,
                "item_name": item.get("name"),
                "stock_count": new_stock,
                "threshold": threshold,
            },
        )
    except Exception:
        pass
```

### 4c. DynamoDB TTL on the alerts table

DynamoDB TTL must be enabled on the `alerts` table. Add to `scripts/local-ddb-init.py` after the table creation for `alerts`:

```python
# Enable TTL on alerts table so sentinel records auto-expire
try:
    ddb_client.update_time_to_live(
        TableName=_resolve_table_name(S.alerts_table_name, "alerts"),
        TimeToLiveSpecification={"Enabled": True, "AttributeName": "ttl"},
    )
except Exception:
    pass  # TTL may already be enabled; ignore
```

In production (AWS), TTL is enabled via Terraform/CDK on the real DynamoDB table. Sentinel records with `ttl < now()` are automatically purged by DynamoDB's background TTL sweeper (typically within a few minutes of expiry). The `ttl` attribute name matches what will be used for the sentinel; existing alert rows that do not carry a `ttl` attribute are unaffected by TTL.

### 4d. Dev/prod parity (SECOPS-007)

The sentinel write uses `T.alerts`, which maps to `DDB_ENDPOINT_URL` (localhost:8001) in dev and to the real AWS DynamoDB endpoint in production. The code path is identical. The only prod-only step is enabling TTL on the real table in IaC. DynamoDB Local supports TTL attribute setting but does not actually expire items — this is acceptable in dev because tests can inspect the sentinel record directly and the 1-hour window is only meaningful in production-scale conditions.

### 4e. Alternatives considered

- **In-process `functools.lru_cache` or Python set keyed on `(creator_id, item_id)`**: Rejected. Multiple uvicorn workers (even with `--workers 1` in dev, but production runs multiple) each have separate in-process state. A cache in one worker would not prevent another worker from firing the alert.
- **Separate `alert_sentinels` DynamoDB table**: Functionally equivalent but adds operational overhead. Reusing `T.alerts` with a synthetic PK prefix is simpler and requires no new table or IaC resource.
- **Check-then-write (read sentinel before writing)**: Rejected. Subject to TOCTOU race — two concurrent requests can both read "no sentinel" before either writes it. The `ConditionExpression` on `put_item` is an atomic test-and-set, the correct approach.

## 5. Testing, Verification & Rollout

### Regression test (fails before / passes after fix)

Add to `tests/test_catalog.py` (offline, moto-backed):

```python
@pytest.mark.parametrize("call_count", [1, 5, 10])
def test_low_stock_alert_fires_once_per_ttl_window(mock_catalog_item, mock_alerts_table):
    """Only the first threshold-crossing call within 1 hour should write an alert."""
    item = mock_catalog_item(item_id="item-1", creator_id="creator-1",
                              low_stock_threshold=5)
    # Call _check_low_stock_alert 10 times, all below threshold
    for i in range(10):
        _check_low_stock_alert(item, new_stock=3)

    # Exactly one real alert row should exist (sentinel rows have sentinel=True)
    alerts = [
        row for row in mock_alerts_table.scan()["Items"]
        if not row.get("sentinel")
    ]
    assert len(alerts) == 1
    assert alerts[0]["event"] == "catalog.low_stock"

def test_low_stock_alert_fires_again_after_ttl_expiry(mock_catalog_item, mock_alerts_table, freeze_time):
    """After the 1-hour TTL expires, a new threshold-crossing should fire a new alert."""
    item = mock_catalog_item(item_id="item-2", creator_id="creator-2",
                              low_stock_threshold=5)
    _check_low_stock_alert(item, new_stock=3)
    # Manually expire sentinel by deleting it from the mock table
    mock_alerts_table.delete_item(
        Key={"user_sub": "ALERT_SENTINEL#creator-2", "alert_id": "LOW_STOCK#item-2"}
    )
    _check_low_stock_alert(item, new_stock=2)
    alerts = [r for r in mock_alerts_table.scan()["Items"] if not r.get("sentinel")]
    assert len(alerts) == 2  # Two alerts after two TTL windows
```

The first test fails on the current code (returns 10 alerts) and passes after the fix (returns 1). The `freeze_time` fixture advances the clock beyond `_LOW_STOCK_SENTINEL_TTL_SECONDS` to simulate expiry.

### Manual QA steps

2. Create a catalog category and item with `low_stock_threshold=2`.
3. Set stock to 10 via `PATCH /ui/catalog/items/{item_id}/stock` (absolute=10).
4. Send 8 consecutive decrement requests (delta=-1 each), crossing the threshold at stock=2.

### Observability

The sentinel write's `ConditionalCheckFailedException` is silently swallowed by design (the alert is merely suppressed, not an error). Add a CloudWatch metric increment for `low_stock_alert.suppressed` in a future observability pass (SECOPS-001) if alert suppression rate needs monitoring.

### Rollout and risks

- **Effort**: S (small) — approximately 30 lines of code changed.
- **Risks**: The `put_item` sentinel write is a new DDB write per threshold-crossing event. For items already below the threshold (stock never rises back above), the sentinel fires once and then is suppressed for 1 hour. This is the intended behavior. If TTL is not enabled on the `alerts` table in production, sentinel records accumulate indefinitely — the TTL enablement step must ship first (or simultaneously) with the code change.
- **Migration**: No data migration required. Existing alert rows (without `ttl`) are unaffected.
- **Rollback**: Revert `_check_low_stock_alert` to unconditional `write_alert` call. The sentinel rows in DDB are harmless orphans; they will eventually be cleaned up if TTL is enabled.
- **Sequencing**: Enable DynamoDB TTL on `alerts` table in IaC → deploy backend change.
