# GAP-0011: `respond_to_feedback` Does Not Inject Response or Resume Agent — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: AGENT-006. Investigation: docs/tickets/gap-tickets/investigations/GAP-0011.md.

---

## 1. Summary & Classification

**Plain-English statement**: When a user submits a response to an agent feedback request via `POST /agent-feedback/{worker_id}/{request_id}/respond`, the backend updates the DynamoDB record and returns the updated item — but it never injects the response text into the running agent terminal, and it never transitions the agent state machine from `awaiting_feedback` back to `working`. The agent remains permanently blocked.

**One-line impact**: Every feedback-response submitted through the UI is a no-op at the operational level — the agent stays frozen in `awaiting_feedback` indefinitely with no automatic recovery path.

## 2. Current-State Investigation (root cause)

### Code path

`POST /agent-feedback/{worker_id}/{request_id}/respond`
→ `app/routers/agent_feedback.py:250–275` (router handler `respond_to_feedback`)
→ `app/services/terminal_monitor.py:233–265` (service function `respond_to_feedback`)

The router (`app/routers/agent_feedback.py:258–265`) calls the service and immediately returns the result:

```python
# app/routers/agent_feedback.py:258-265
item = svc.respond_to_feedback(
    user_id=user_id,
    worker_id=worker_id,
    request_id=request_id,
    response_text=body.response_text,
)
return _item_to_out(item)
```

The service function (`app/services/terminal_monitor.py:233–265`) performs exactly two operations:

1. Reads the existing record and validates it is in `"pending"` status (lines 243–248).
2. Issues a DynamoDB `update_item` to set `feedback_status = "responded"`, `response_text`, and `responded_at` (lines 251–258).
3. Returns the updated item via `get_feedback_request(worker_id, request_id)` (line 265).

```python
# app/services/terminal_monitor.py:251-265
T.agent_feedback.update_item(
    Key={"pk": f"WORKER#{worker_id}", "sk": f"FEEDBACK#{request_id}"},
    UpdateExpression="SET feedback_status = :st, response_text = :rt, responded_at = :ra",
    ExpressionAttributeValues={
        ":st": "responded",
        ":rt": response_text,
        ":ra": ts,
    },
)
logger.info("Responded to feedback %s for worker %s", request_id, worker_id)
return get_feedback_request(worker_id, request_id)
```

### What is missing

**Missing action 1 — Terminal injection**: No function named `_inject_into_terminal` exists anywhere in `app/`. A grep across all Python files under `app/` returns zero matches. The `TerminalOutputBuffer` (defined at `app/services/terminal_monitor.py:104`) has an `append()` method that stores text in the in-memory ring buffer. Calling `get_or_create_buffer(worker_id).append(response_text)` would at minimum record the injected response in the buffer so subsequent pattern-matching rounds can see it. A live SSH stdin inject requires a WebSocket session registry (also absent — see GAP-0012).

**Missing action 2 — State transition**: The agent state machine is implemented in `app/services/agent_orchestrator.py`. `VALID_TRANSITIONS` at line 26–34 explicitly lists `"awaiting_feedback": {"working", "paused", "error", "idle"}` — the `awaiting_feedback → working` transition is valid. `transition_agent_state(user_id, worker_id, "working")` (line 83) exists and is fully implemented but is never called from `respond_to_feedback`.

### How it manifests

In dev, the agent worker card in the Worker Fleet UI shows `awaiting_feedback` forever. In production, no amount of feedback responses will unblock the agent; operators must manually intervene via a direct DynamoDB write or an admin state-override endpoint. There is no user-visible error — the API returns HTTP 200 with the updated feedback record, giving every appearance of success.

## 3. Impact / Exploit / Blast Radius

**Functional impact**: Every call to `POST /agent-feedback/{worker_id}/{request_id}/respond` is silently a no-op at the operational level. The agent state remains `awaiting_feedback`; no further ticket work is performed.

**Scope**: All users of the agent framework (AGENT-006 feature). Any workflow where an agent emits `[AGENT_FEEDBACK_NEEDED]` or an operator manually creates a feedback request will be permanently blocked after the first unresolved request.

**Recovery path without the fix**: A ROOT or ADMIN operator must directly update the `agent_state` field in the `T.agent_workers` DynamoDB table. There is no admin UI endpoint for this. The only mechanism is `transition_agent_state`, callable from an internal script or a break-glass CLI.

**Security**: No security exploit. This is a functional correctness gap — data is written correctly to the feedback table; the side-effects that complete the feedback loop are simply absent.

**Financial / SLA risk**: Agents performing time-sensitive tasks (e.g., automated coding workflows, ticket processing pipelines) will stall indefinitely, potentially causing SLA breaches and accumulating idle worker compute costs.

## 4. Fix Design (code-level)

### Minimal viable fix (unblocks state machine; no live SSH injection yet)

In `app/services/terminal_monitor.py`, add two side-effect calls at the end of `respond_to_feedback`, immediately after the DynamoDB update:

```python
# app/services/terminal_monitor.py — respond_to_feedback, after line 258

# 1. Record the injected response in the output buffer so subsequent
#    pattern-matching rounds have context.
buf = get_or_create_buffer(worker_id)
buf.append(f"\n[User response]: {response_text}\n")

# 2. Transition the agent back to working so it can proceed.
from app.services import agent_orchestrator
try:
    agent_orchestrator.transition_agent_state(user_id, worker_id, "working")
except ValueError:
    # Worker may have been manually transitioned or deleted; log, don't fail.
    logger.warning(
        "Could not transition worker %s to working after feedback response: already in %s",
        worker_id,
        "non-awaiting_feedback state",
    )
```

The `user_id` parameter is already present in `respond_to_feedback`'s signature and threaded through from the router, so no signature changes are required.

### Full fix (adds live SSH stdin injection)

The full fix requires a session registry mapping `worker_id → active WebSocket channel`. This should be implemented in a subsequent ticket as part of GAP-0012 resolution, but the interface contract can be defined now:

```python
# app/services/terminal_ws_registry.py (new file)
from typing import Dict, Optional, Callable, Awaitable

# worker_id -> coroutine that accepts a string and sends it to SSH stdin
_registry: Dict[str, Callable[[str], Awaitable[None]]] = {}

def register_worker_ws(worker_id: str, send_fn: Callable) -> None:
    _registry[worker_id] = send_fn

def unregister_worker_ws(worker_id: str) -> None:
    _registry.pop(worker_id, None)

def get_worker_ws_send(worker_id: str) -> Optional[Callable]:
    return _registry.get(worker_id)
```

Then `respond_to_feedback` can attempt live injection:

```python
send_fn = terminal_ws_registry.get_worker_ws_send(worker_id)
if send_fn:
    import asyncio
    asyncio.create_task(send_fn(response_text + "\n"))
```

This is optional for the initial fix — buffer append plus state transition is the highest-priority correction.

### Dev/Prod parity (SECOPS-007)

- `T.agent_feedback.update_item` uses the standard boto3 path, identical under DynamoDB Local (port 8001) and AWS DynamoDB. No parity difference.
- `transition_agent_state` writes to `T.agent_workers` via the same boto3 path. Identical in both environments.
- `get_or_create_buffer` is in-process memory. In dev this is a single uvicorn worker process (`--workers 1`); in production, if multiple uvicorn workers are used, the buffer is per-process. This is an existing limitation of the monitoring subsystem (noted in CLAUDE.md under "moto S3 workers") and is not introduced by this fix.
- No feature flag is required; the behavior change is purely additive.

### Backward compatibility

The DDB schema is unchanged. The only behavioral change is that `respond_to_feedback` now has side effects. The API response shape is identical. There is no migration required.

### Alternatives considered

- **Async background task**: Could defer the state transition to a background task to keep the HTTP response fast. Rejected — the state transition is a single DDB conditional update (~5 ms latency); deferring it introduces a race window where a second feedback request could be created before the transition completes.
- **Event bus / SSE**: Could publish a `feedback_responded` SSE event and handle the transition in a subscriber. Rejected as over-engineering for the initial fix; can be added later for real-time UI updates.

### Observability

- Add a structured log entry: `logger.info("Agent %s transitioned to working after feedback response %s", worker_id, request_id)` — searchable in CloudWatch / local uvicorn logs.
- Emit a CloudWatch metric `AgentFeedbackResponded` (count=1) at call time for alerting on feedback-response volume.

### Rollback

The fix adds two side-effect calls. Rolling back means reverting to the single-DDB-write behavior. No schema migration required. If the state transition causes unexpected errors in production (e.g., workers already transitioned by another path), the `except ValueError: pass` guard prevents HTTP 500s — the fix is safe to deploy.

### Risks

- **Race condition**: If two simultaneous responses are submitted for the same request (unlikely given the `"pending"` status guard), both will attempt `transition_agent_state`. The second call will hit a `ValueError` (invalid transition from `working` → `working`) which is caught and logged. No data corruption results.
- **Missing worker record**: If the worker was deleted between feedback creation and response, `transition_agent_state` will raise `LookupError`. The `except ValueError` guard does not catch `LookupError`; add `except (ValueError, LookupError)` in the fix.

### Sequencing

1. Implement this fix (GAP-0011) — unblocks the state machine immediately.
2. Implement GAP-0012 (WebSocket hook) in parallel or follow-on — adds live terminal stdin injection.
3. Implement the `terminal_ws_registry` for live injection as a follow-on to GAP-0012.

**Effort**: M — approximately 2–3 hours of development plus test writing.
