# GAP-0056: No Per-API-Key Rate Limiting — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against live code at `app/routers/advertiser_api.py`,
> `app/middleware/rate_limit.py`, `app/services/rate_limit_config.py`,
> `app/services/api_key_auth_dependency.py`. No investigation doc exists.

## 1. Summary & Classification

**Gap**: The advertiser API router (`/api/v1/ads/*`) has no rate limit keyed to the
individual API key identity. Any valid API key can issue an unlimited number of requests
within a rolling window, constrained only by coarse per-IP and per-cookie-user limits
that do not apply to programmatic API-key callers at all.

- **Severity**: HIGH
- **Source ticket**: ADS-011
- **Owning area**: Advertiser API / Platform infrastructure
- **Status**: Open
- **Related tickets**: GAP-0057 (ads:* scope UI gap); PLATFORM-001 (rate-limit framework)
- **Verdict**: Claim confirmed. The gap is exactly as described. The existing rate-limit
  middleware never extracts an API key identity; it only reads the `ui_access_token` JWT
  cookie. API-key requests carry no such cookie, so the per-user layer is skipped entirely
  and only the broad IP-window (`api_public` group, 300 req/60 s per IP) applies.

**One-line impact**: A single API key can exhaust the analytics query budget in seconds,
causing DynamoDB read hot-partitions and billing anomalies with no per-tenant throttle.
This also blocks the ADS-011 compliance requirement that specified 1 000 req/min per key.

## 2. Current-State Investigation (root cause)

### Rate-limit middleware identity extraction

`app/middleware/rate_limit.py:62–84` (`_extract_user_from_request`) reads a signed
`ui_access_token` cookie to obtain `user_sub`:

```python
# rate_limit.py:70–83
token = cookies.get(access_cookie_name)
if not token:
    return ("", "")
payload = jwt.decode(token, access_secret, algorithms=["HS256"])
user_sub = str(payload.get("sub", ""))
```

API-key requests never carry that cookie, so `_extract_user_from_request` returns
`("", "")`. The middleware then falls through to the per-IP bucket only
(`ENDPOINT#api_public#IP#{ip}`, `rate_limit_config.py:85–92`).

### `api_public` group definition

`app/services/rate_limit_config.py:85–92`:

```python
"api_public": {
    "paths": ["/api/*"],
    "window_seconds": 60,
    "max_requests_per_user": 300,   # dead code — user_sub always ""
    "max_requests_per_ip": 600,
    "bypass_roles": ["root"],
},
```

The `max_requests_per_user` limit is effectively dead: because `user_sub` is empty the
middleware skips the per-user branch entirely (`rate_limit.py:183–225` requires
`if user_sub:`).

### `require_api_key_principal` produces a principal but the middleware never sees it

`app/services/api_key_auth_dependency.py:55–81` populates `request.state.api_key_principal`
with `api_key_id` and `user_sub` — but this runs _after_ the ASGI middleware has already
evaluated rate limits (middleware wraps the entire application; FastAPI dependencies run
during route dispatch). The middleware therefore never has access to `api_key_id`.

### Advertiser router: no per-router dependency

`app/routers/advertiser_api.py:36` defines the router with no rate-limit dependency:

```python
advertiser_api_router = APIRouter(prefix="/api/v1/ads", tags=["Advertiser API"])
```

Every endpoint depends only on `require_api_key_principal`. There is no
`rate_limit_group(...)` dependency call anywhere in the file. The router currently
contains 18 endpoint functions across account, campaigns, budget, creatives, and
analytics sub-resources. Each endpoint independently authenticates via
`Depends(require_api_key_principal)` but none carry any rate-limit dependency.

### Key API endpoints most vulnerable to bulk abuse

The analytics endpoints are the highest-cost targets:

- `GET /api/v1/ads/analytics/by-date` (advertiser_api.py:191–200) — queries up to
  365 days of ad event data, scanning potentially millions of DynamoDB items per call.
- `GET /api/v1/ads/analytics/breakdown` (advertiser_api.py:203–213) — aggregates by
  dimension across the same time window.
- `GET /api/v1/ads/campaigns` (advertiser_api.py:59–67) — returns all campaigns for
  the account; no server-side pagination enforced in the query path.

Each of these calls the corresponding `svc.*` function in `app/services/advertiser_api.py`
which performs direct DynamoDB queries. Without per-key throttling, a single key
issuing 60 analytics requests per second would consume the entire provisioned read
throughput for the `AdEvents` table in the first minute.

### What the `rate_limit_group` dependency factory does

`app/middleware/rate_limit.py:292–398` (`rate_limit_group`) is a FastAPI dependency
intended for explicit router use. It does accept `ctx = Depends(require_ui_session)`.
Because the advertiser router uses `require_api_key_principal` (not `require_ui_session`),
this dependency cannot be dropped in without modification — it would break because
`require_ui_session` would reject the API-key-only request.

## 3. Impact / Exploit / Blast Radius

**Who is affected**: Every tenant using the advertiser API; the platform's DynamoDB tables
and billing infrastructure.

**Exploit walkthrough**:

1. Attacker obtains a valid API key (their own legitimate account key, or a stolen key).
2. They run a tight loop against `GET /api/v1/ads/analytics/by-date?days=365` —
   the most expensive endpoint, which scans a full year of ad event records.
3. The per-IP limit (600 req/60 s) does not apply if the attacker distributes requests
   across even two source IPs (each gets 600). In a typical cloud egress environment with
   NAT gateways, multiple source IPs are trivially available.
4. Each analytics scan hits DynamoDB with up to O(N) read capacity units per campaign.
   At 1 000 requests per minute per key, a moderately large advertiser can exhaust the
   provisioned RCU allocation for the `AdEvents` table in under 30 seconds.
5. A DynamoDB hot partition on the `AdEvents` table or `AdAccounts` table degrades all
   advertiser API and organic ad-serving reads for every tenant.

**Financial**: An attacker who boosts their own campaign analytics throughput could
interfere with CPM attribution writes, creating billing discrepancies between billed
impressions and recorded events.

**Availability**: DDB `ProvisionedThroughputExceededException` or `RequestThrottled`
errors propagate back as 500s to all users sharing the same table partition.

**Data integrity**: No direct data corruption, but the rate-limit absence means there is
no signal to detect scraping of competitor campaign metadata (if access control also has
gaps).

**Compliance**: The ADS-011 specification explicitly listed 1 000 req/min per-key as a
design requirement. Shipping without it is a requirements gap, not just a hardening
concern.

## 4. Fix Design (code-level)

### Approach: API-key identity injection in the rate-limit middleware

The cleanest fix is to extend `_extract_user_from_request` to also check for an API key
header and produce a compound identity, then add an `ads_api` group to the endpoint group
registry. This keeps all rate-limit logic in one place.

#### 4.1 Extend middleware identity extraction

In `app/middleware/rate_limit.py`, update `_extract_user_from_request` to return a
three-tuple `(user_sub, role, api_key_id)`. Add lightweight API-key-header detection
(no DDB validation — just header parsing for the key_id prefix, the same approach used
in `api_key_auth_dependency.py`):

```python
def _extract_user_from_request(request: Request) -> tuple[str, str, str]:
    """Return (user_sub, role, api_key_id). Any field may be empty."""
    api_key_id = ""
    try:
        auth = (request.headers.get("authorization") or "").strip()
        raw = ""
        if auth.lower().startswith("apikey "):
            raw = auth.split(" ", 1)[1].strip()
        else:
            raw = (request.headers.get("x-api-key") or "").strip()
        if raw:
            # key_id is the first 32-char segment before ':'
            api_key_id = raw.split(":", 1)[0][:64]
    except Exception:
        pass

    # Cookie-based user extraction (existing logic)
    try:
        ...existing cookie logic...
        return (user_sub, role, api_key_id)
    except Exception:
        return ("", "", api_key_id)
```

#### 4.2 Add `ads_api` endpoint group

In `app/services/rate_limit_config.py`, add a dedicated group after `api_public`:

```python
"ads_api": {
    "description": "Advertiser programmatic API (/api/v1/ads/*) — per-API-key throttle",
    "paths": ["/api/v1/ads/*"],
    "window_seconds": 60,
    "max_requests_per_api_key": 1000,   # 1 000 req/min per key (ADS-011 spec)
    "max_requests_per_ip": 2000,
    "bypass_roles": ["root"],
},
```

Note: `api_public` matches `/api/*` which is a superset of `/api/v1/ads/*`. Because
`match_path_to_group` uses `fnmatch` and iterates the dict in insertion order, placing
`ads_api` _before_ `api_public` in `ENDPOINT_GROUPS` ensures the more-specific pattern
wins.

#### 4.3 Enforce per-key bucket in the middleware

In the Layer 2 section of the middleware, after extracting `api_key_id` from the new
three-tuple return, add a per-key check analogous to the per-user check:

```python
# Per-API-key check (for API-key-authenticated requests)
if api_key_id and group_cfg.get("max_requests_per_api_key"):
    max_per_key = group_cfg["max_requests_per_api_key"]
    window = group_cfg.get("window_seconds", 60)
    try:
        k_allowed, k_remaining, k_reset = check_rate_limit(
            pk=f"ENDPOINT#{group_name}#APIKEY#{api_key_id}",
            window_seconds=window,
            max_requests=max_per_key,
        )
    except Exception:
        if S.rate_limit_fail_open:
            k_allowed, k_remaining, k_reset = True, -1, 0
        else:
            return JSONResponse(status_code=503, ...)

    if not k_allowed:
        retry_after = max(1, k_reset - now_ts())
        _log_event_async(group_name, "api_key", api_key_id, ...)
        return JSONResponse(
            status_code=429,
            content={"detail": {"code": "rate_limited", "group": group_name,
                                "retry_after": retry_after, ...}},
            headers={"Retry-After": str(retry_after), ...},
        )
```

The `check_rate_limit` function (`app/services/rate_limit_store.py`) already accepts any
string primary key, so no changes are needed there.

#### 4.4 Save-override support for `ads_api`

No code changes needed: `save_group_override` (rate_limit_config.py:177) writes to DDB
using the group name as key, so operators can adjust the 1 000 req/min cap at runtime
without a redeploy.

### Dev/Prod parity (SECOPS-007)

The rate-limit store (`rate_limit_store.py`) uses DynamoDB in both dev and prod, backed
by DynamoDB Local in dev and real DynamoDB in prod. The new `ENDPOINT#ads_api#APIKEY#*`
keys use the same fixed-window counter pattern as all other groups; no special mocking
is required. In dev mode, `get_group_config` already applies the `* 1000` multiplier to
`max_requests_per_api_key` if the key is of `int` type, so E2E tests are not affected.

### Alternatives considered

- **Per-router FastAPI dependency**: Adding `rate_limit_group("ads_api")` as a dependency
  on `advertiser_api_router` would work, but the existing `rate_limit_group` factory
  calls `Depends(require_ui_session)`, which would fail for API-key-only requests. It
  would need a parallel `rate_limit_group_api_key` factory — more code to maintain.
  Middleware-level extraction is simpler and consistent with PLATFORM-001 design intent.
- **Separate Redis/in-memory store**: Overkill for the DynamoDB-backed store already in
  use; would introduce a new infrastructure dependency.

## 5. Testing, Verification & Rollout

### Regression test (pytest offline)

Add to `tests/test_rate_limit_ads_api.py`:

```python
import pytest
from unittest.mock import patch, MagicMock
from fastapi.testclient import TestClient
from app.main import app

API_KEY_HEADER = {"x-api-key": "testkey123:secret"}

def _make_principal():
    return {
        "auth_type": "api_key",
        "user_sub": "u_test",
        "api_key_id": "testkey123",
        "capabilities": ["ads:read"],
    }

@pytest.mark.parametrize("call_count,expected_429", [(999, False), (1001, True)])
def test_per_key_rate_limit(call_count, expected_429, monkeypatch):
    """Rate limiter returns 429 once per-key window is exceeded (1000 req/min)."""
    counter = {"n": 0}

    def fake_check_rate_limit(pk, window_seconds, max_requests):
        counter["n"] += 1
        over = counter["n"] > max_requests
        return (not over, max(0, max_requests - counter["n"]), 0)

    with patch("app.services.rate_limit_store.check_rate_limit", fake_check_rate_limit), \
         patch("app.services.api_key_auth_dependency.require_api_key_principal",
               return_value=_make_principal()):
        client = TestClient(app)
        last = None
        for _ in range(call_count):
            last = client.get("/api/v1/ads/account", headers=API_KEY_HEADER)
        if expected_429:
            assert last.status_code == 429
            assert last.json()["detail"]["code"] == "rate_limited"
        else:
            assert last.status_code != 429
```

**Fails before fix**: The counter never triggers 429 because `_extract_user_from_request`
returns `("", "", "")` and no per-key bucket is checked.

**Passes after fix**: The `ads_api` group's `max_requests_per_api_key=1000` is enforced.

### Manual QA

1. Start the dev stack (`just up`).
2. Create an API key via the UI (Settings → Security → API Keys) with `ads:read` scope.
3. Run `for i in $(seq 1 1010); do curl -s -o /dev/null -w "%{http_code}\n" \
   -H "x-api-key: <key>" http://localhost:8000/api/v1/ads/account; done | grep 429` —
   should see 429s after the 1 000th request within a 60-second window.
4. Verify `Retry-After` header is present on 429 responses.
5. Verify that a second key from the same IP is _not_ affected by the first key's counter.
6. Verify that key A and key B from the same user (same `user_sub`) have independent
   per-key buckets — they should each get 1 000 req/min independently.
7. Verify that admin-panel DDB override of `max_requests_per_api_key` takes effect
   within 60 seconds (cache TTL) without a backend restart.
8. Confirm X-RateLimit-Limit, X-RateLimit-Remaining, and X-RateLimit-Reset headers
   are present and accurate on non-throttled responses under the new `ads_api` group.

### Metrics / observability

- Rate-limit events are already logged to `T.rate_limits` via `log_rate_limit_event`;
  filter on `endpoint_group = "ads_api"` and `identity_type = "api_key"`.
- Add a CloudWatch metric filter or Prometheus counter on `rate_limited` events per
  `api_key_id` to catch coordinated abuse.

### Rollout

1. Land the middleware and config changes behind `S.rate_limit_per_endpoint_enabled`
   (already gating Layer 2 logic) — no flag change needed.
2. Set initial DDB override for `ads_api` to a generous cap (e.g. 5 000 req/min) via
   admin UI, so existing high-volume integrations are not immediately throttled.
3. Monitor for 429s over 48 hours; ratchet down to the ADS-011 spec value of 1 000 req/min.

**Effort**: S (small). Middleware changes are ~50 lines; config entry is ~6 lines.
**Sequencing**: Deploy after PLATFORM-001 is confirmed stable in production (it already is).
**Rollback**: Set `S.rate_limit_per_endpoint_enabled = False` via env var restart, or
delete the `ads_api` DDB config entry to remove the group entirely.

### Risk assessment

The only noteworthy deployment risk is a false-positive throttle on an existing
high-volume legitimate integration if the initial cap is set too low. Mitigated by
starting at a high override (5 000 req/min) and ratcheting down. The change does not
affect any non-`/api/v1/ads/*` paths — the per-IP `api_public` group continues to
cover all other `/api/*` paths as before. The new `ads_api` group takes precedence
over `api_public` only because it is inserted earlier in the `ENDPOINT_GROUPS` dict,
making `fnmatch("/api/v1/ads/campaigns", "/api/v1/ads/*")` match before
`fnmatch("/api/v1/ads/campaigns", "/api/*")` is evaluated. Existing per-IP protections
remain untouched as a secondary safety net for callers whose keys cannot be identified
(e.g. malformed key header that still reaches the endpoint via a misconfigured reverse
proxy that does not verify the key before forwarding).
