# GAP-0345: `rotate-secrets` is Still a Placeholder — Remediation Write-up

## 1. Summary & Classification

**Gap**: The `rotate-secrets` command in `app/cli/rootctl.py` is registered as a
fully mutation-guarded, root-only, ticket-required command but its handler is
`_placeholder_mutation_command` — a no-op that returns a JSON scaffold with no
actual key rotation logic. When an operator runs
`python -m app.cli.rootctl root rotate-secrets --reason "…" --ticket …`,
the command succeeds silently without rotating any secret. `UI_ACCESS_TOKEN_SECRET`,
`API_KEY_PEPPER`, and the KMS break-glass key are never regenerated.

- **Severity**: HIGH
- **Source ticket**: ROOTCTL-001
- **Owning area**: Security / Root CLI / Backend
- **Status**: Open

**Claim accuracy**: Confirmed. `app/cli/rootctl.py:2134–2144` shows the command is
parsed and its `mutating=True, requires_root=True, requires_ticket=True` guards are
active, but `handler=_placeholder_mutation_command` at line 2138 is the no-op stub
defined at line 1962–1977. No key derivation, no environment file writes, no KMS
re-key calls are present anywhere in `rootctl.py` or any imported module for this
path.

**One-line impact**: Signing secrets are never rotated, meaning compromised tokens or
hashed API keys can never be invalidated at the cryptographic boundary — a permanent
gap in the incident response playbook.

**Related tickets**: ROOTCTL-001, SEC-018 (token revocation), GAP-0341 (account deletion)

## 2. Current-State Investigation (Root Cause)

### 2.1 The placeholder

`app/cli/rootctl.py:1962`:
```python
def _placeholder_mutation_command(args: argparse.Namespace) -> Dict[str, Any]:
    shared = _shared_opts(args)
    return {
        "ok": True,
        "group": str(args.group),
        "command": str(args.command),
        "dry_run": shared.dry_run,
        "request_id": shared.request_id,
        "correlation_id": shared.correlation_id,
        "actor_sub": str(getattr(args, "actor_sub", "") or ""),
        "target_user_sub": str(getattr(args, "target_user_sub", "") or ""),
        "requested_role": str(getattr(args, "role", "") or ""),
        "reason": str(getattr(args, "reason", "") or ""),
        "ticket": str(getattr(args, "ticket", "") or ""),
        "message": f"{args.group} {args.command} command scaffold is policy-guarded",
    }
```

The function returns `ok: True` so the CLI exits with code 0. Operators who run the
command receive confirmation-like output but nothing is rotated. No error, no warning.

### 2.2 What needs to be rotated

Three secrets govern session and API key security:

**`UI_ACCESS_TOKEN_SECRET`** (env var, `app/core/settings.py:98`):
HS256 JWT signing key for `ui_access_token` cookies. Used by:
- `app/services/sessions.py:182` — `jwt.encode(..., S.ui_access_token_secret)`
- `app/services/sessions.py:212` — `jwt.decode(..., S.ui_access_token_secret)`
- `app/routers/admin_impersonation.py:123` — impersonation token signing
- `app/routers/messaging.py:7202` — thread cursor HMAC seed (fallback)
- `app/services/provider_oauth.py:35, 523` — OAuth state HMAC seed

If this secret is compromised, an attacker can forge `ui_access_token` cookies for
any user sub, bypassing all cookie-based authentication.

**`API_KEY_PEPPER`** (env var, `app/core/settings.py:45`):
HMAC pepper appended to raw API key secrets before hashing
(`app/services/api_keys.py:34`). If the pepper is known, the attacker can reverse
the one-way hash for any key whose raw bytes are guessed. Rotation invalidates all
existing hashes and forces re-issuance of all API keys.

**`KMS_KEY_ID`** (env var, `app/core/settings.py:178`):
AWS KMS customer-managed key used by `app/core/crypto.py:19` to encrypt sensitive
field values (TINs, SSH credentials, file mount secrets). Rotation of the KMS key
requires re-encrypting all ciphertexts stored in DynamoDB.

### 2.3 Why rotation is security-critical

- **Token compromise**: If `UI_ACCESS_TOKEN_SECRET` leaks (e.g. in a config-store
  breach or memory dump), every signed session token ever issued is potentially forged.
  Rotating the secret immediately invalidates all live `ui_access_token` JWTs; clients
  are forced to re-authenticate.
- **API key exposure**: If a database dump exposes hashed API keys alongside known
  plaintexts (e.g. test keys), the attacker can reconstruct the pepper. Rotating the
  pepper + forcing key re-issuance closes this window.
- **Incident response gap**: Without a working `rotate-secrets` command, the incident
  response playbook has no automated path to rotate secrets. The only option is a
  manual environment variable update + server restart, which is error-prone and leaves
  an undocumented gap in the audit trail.

### 2.4 Dev vs. prod

In dev, secrets are short fixed strings in `.env.local`
(e.g. `UI_ACCESS_TOKEN_SECRET=dev-local-secret`). In prod, they are injected from
AWS Systems Manager Parameter Store or Secrets Manager. The rotation implementation
must handle both cases.

## 3. Impact / Exploit / Blast Radius

**Scenario 1 — Leaked `UI_ACCESS_TOKEN_SECRET`**

An attacker reads the secret from a misconfigured S3 bucket or EC2 metadata endpoint.
They forge:
```python
jwt.encode({"sub": "admin@example.com", "role": "ROOT"}, leaked_secret, algorithm="HS256")
```
and attach it as a `ui_access_token` cookie. Every `require_ui_session` endpoint
accepts the request. The attacker has root-level access to the entire application.
Without `rotate-secrets` working, this window never closes.

**Scenario 2 — API key database dump**

An attacker exfiltrates the billing table, recovers hashed API keys, and brute-forces
the pepper offline. Once the pepper is known, they can replay any API key ever seen
in transit. A working `rotate-secrets` would force all existing keys to hash to
different values, invalidating the attacker's lookup table.

**Blast radius**: All authenticated users; all API integrations; all administrative
operations. A compromised `UI_ACCESS_TOKEN_SECRET` is a full platform takeover.

## 4. Fix Design (Code-Level)

### 4.1 Overall approach

The `rotate-secrets` command must:
1. Generate new secret values (using `secrets.token_urlsafe`).
2. Persist them to the secret store (Parameter Store in prod, `.env.local` in dev).
3. Immediately invalidate all active sessions (cookie-auth and Bearer-auth).
4. Write an immutable audit record via `audit_event`.
5. Return a dry-run-safe result that tells the operator what *would* have been rotated.

KMS key rotation is delegated to AWS `kms.enable_key_rotation()` /
`kms.schedule_key_deletion()` rather than implemented in-process, because re-encrypting
all KMS ciphertexts is a separate migration job.

### 4.2 Implement `_rotate_secrets_command`

Replace `handler=_placeholder_mutation_command` at `app/cli/rootctl.py:2138` with
`handler=_rotate_secrets_command`. Add the implementation:

```python
def _rotate_secrets_command(args: argparse.Namespace) -> Dict[str, Any]:
    from app.services.sessions import revoke_all_sessions_global   # see §4.3

    shared = _shared_opts(args)
    root_sub = _validate_preflight(args)

    scope = str(getattr(args, "scope", "all") or "all")
    # scope: "all" | "ui_access_token" | "api_key_pepper" | "ws_token"
    valid_scopes = {"all", "ui_access_token", "api_key_pepper", "ws_token"}
    if scope not in valid_scopes:
        raise ValueError(f"Invalid scope. Choose from: {valid_scopes}")

    rotated: Dict[str, Any] = {}
    new_values: Dict[str, str] = {}

    def _should_rotate(key: str) -> bool:
        return scope == "all" or scope == key

    if _should_rotate("ui_access_token"):
        new_values["UI_ACCESS_TOKEN_SECRET"] = secrets.token_urlsafe(48)
        rotated["ui_access_token_secret"] = "rotated"

    if _should_rotate("api_key_pepper"):
        new_values["API_KEY_PEPPER"] = secrets.token_urlsafe(32)
        rotated["api_key_pepper"] = "rotated"
        rotated["api_keys_invalidated"] = (
            "All API key hashes are now stale. Keys must be re-issued."
        )

    if _should_rotate("ws_token"):
        new_values["WS_TOKEN_SECRET"] = secrets.token_urlsafe(32)
        rotated["ws_token_secret"] = "rotated"

    if shared.dry_run:
        return {
            "ok": True, "dry_run": True,
            "would_rotate": list(new_values.keys()),
            "actor_sub": root_sub,
            "request_id": shared.request_id,
        }

    # Persist to secret store
    _persist_secrets(new_values)   # see §4.4

    # Invalidate all active UI sessions so they must re-authenticate with new secret
    if "UI_ACCESS_TOKEN_SECRET" in new_values:
        try:
            revoked = revoke_all_sessions_global()
            rotated["sessions_revoked"] = revoked
        except Exception as e:
            rotated["session_revoke_warning"] = str(e)

    ts = now_ts()
    audit_event(
        "rotate_secrets",
        root_sub,
        None,
        outcome="success",
        scope=scope,
        rotated_keys=list(rotated.keys()),
        request_id=shared.request_id,
        correlation_id=shared.correlation_id,
    )

    return {
        "ok": True,
        "dry_run": False,
        "rotated": rotated,
        "actor_sub": root_sub,
        "request_id": shared.request_id,
        "ts": ts,
        "note": "Backend processes must be restarted to pick up the new secret values.",
    }
```

Add `--scope` argument to the `rotate-secrets` subparser:
```python
rotate.add_argument(
    "--scope",
    default="all",
    choices=("all", "ui_access_token", "api_key_pepper", "ws_token"),
    help="Which secrets to rotate (default: all)",
)
```

### 4.3 Session revocation after `UI_ACCESS_TOKEN_SECRET` rotation

Rotating the JWT signing key immediately invalidates all `ui_access_token` cookies
(they will fail `jwt.decode` with a signature error). However, the DynamoDB `sessions`
table retains session rows for TTL-based expiry. These rows should also be purged to
prevent confusion. Add to `app/services/sessions.py`:

```python
def revoke_all_sessions_global() -> int:
    """Scan and delete all active session rows. Used after secret rotation.
    Returns count of deleted rows."""
    from boto3.dynamodb.conditions import Key
    count = 0
    last_key = None
    while True:
        kwargs: Dict[str, Any] = {"FilterExpression": "attribute_exists(session_id)"}
        if last_key:
            kwargs["ExclusiveStartKey"] = last_key
        resp = T.sessions.scan(**kwargs)
        for item in resp.get("Items", []):
            try:
                T.sessions.delete_item(
                    Key={"user_sub": item["user_sub"], "session_id": item["session_id"]}
                )
                count += 1
            except Exception:
                pass
        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break
    return count
```

### 4.4 Secret persistence (`_persist_secrets`)

```python
def _persist_secrets(new_values: Dict[str, str]) -> None:
    """Write new secret values to the active secret store."""
    if S.dev_mode:
        # Dev: update .env.local in place
        env_path = _find_env_local()
        if env_path and env_path.exists():
            _update_env_file(env_path, new_values)
        else:
            raise RuntimeError(".env.local not found; cannot persist secrets in dev mode")
    else:
        # Prod: write to AWS Systems Manager Parameter Store
        import boto3
        ssm = boto3.client("ssm", region_name=S.aws_region)
        for key, value in new_values.items():
            param_name = f"/app/{S.app_env}/{key}"
            ssm.put_parameter(
                Name=param_name,
                Value=value,
                Type="SecureString",
                Overwrite=True,
            )
```

`_update_env_file` parses `.env.local` line by line and replaces matching `KEY=value`
pairs, leaving all other lines intact.

### 4.5 Dev / Prod Parity (SECOPS-007)

The `if S.dev_mode` branch in `_persist_secrets` writes to `.env.local` (dev) while
the prod branch writes to SSM Parameter Store. Both paths use the same `new_values`
dict and the same rotation logic — only the persistence destination differs. The KMS
key is never directly handled by this command (AWS KMS has its own key rotation APIs
that operate outside the application layer).

### 4.6 Alternatives Considered

- **Rotate via environment variable updates without session revocation**: Not acceptable.
  If the secret is compromised, live sessions using the old secret remain valid until
  they expire (up to 30 days). Session revocation must be coupled to rotation.
- **Re-encrypt all API key hashes on rotation**: This would require iterating every
  API key record in DynamoDB and re-hashing, which risks leaving a gap if the scan is
  incomplete. The correct approach is to mark all existing key hashes stale and require
  re-issuance. This is a business policy decision documented in the `rotated` output.
- **Rotate KMS key in-band**: AWS KMS automatic key rotation should be enabled on the
  CMK via `enable_key_rotation()`. Re-encrypting existing DynamoDB ciphertexts is a
  separate offline migration job that falls outside this command's scope.

### 5.2 Manual QA Steps

1. Run `python -m app.cli.rootctl root rotate-secrets --actor-sub root@test \
   --reason "test rotation" --ticket TEST-001 --dry-run`.
   Verify output contains `"would_rotate"` and no `.env.local` is modified.
2. Run without `--dry-run`. Verify `.env.local` is updated with new values for
   `UI_ACCESS_TOKEN_SECRET` and `API_KEY_PEPPER`.
3. Restart the backend. Verify existing `ui_access_token` cookies are rejected
   (401 on next API call) because the signing secret has changed.
4. Verify the audit log contains an event `rotate_secrets` with `outcome: success`.

### 5.3 Observability

- `audit_event("rotate_secrets", ...)` writes to the alerts/audit table with
  `outcome=success`, `scope`, and list of rotated keys.
- In prod, add a CloudWatch Logs metric filter on `rotate_secrets` to page on-call
  if the command is run outside of an approved change window.
- Add a `sessions_revoked` count to the return value so operators know how many
  forced re-logins were triggered.

### 5.4 Rollout

- **Effort**: L (Large) — approximately 120 lines of new handler code, a new
  `_persist_secrets` helper, a `revoke_all_sessions_global` function in sessions.py,
  `.env.local` update logic, SSM Parameter Store integration in prod, and test coverage.
- **Backward compat**: The CLI interface gains a new `--scope` argument; existing
  invocations without `--scope` default to `all` (safe).
- **Rollback**: The command now performs real mutations; rollback means reverting the
  secret values manually and restarting the backend — there is no automated undo.
  Document this explicitly in operator runbooks.
- **Risk**: HIGH for the operation itself (intended — forcing all users to re-login is
  disruptive). Risk of the implementation is low (generation uses `secrets.token_urlsafe`,
  persistence uses SSM or file write with rollback on error).
- **Sequencing**: Implement before next security audit. Coordinate with infrastructure
  team on SSM Parameter Store path naming convention. Requires a maintenance window in
  prod due to forced session invalidation.
