# GAP-0135: `_next_run_from_cron()` is a stub — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`. Build on the
> investigation doc (docs/tickets/gap-tickets/investigations/GAP-0135.md) if it exists.

## 1. Summary & Classification

**Bug statement**: `_next_run_from_cron()` in `app/services/bot_scheduler.py` ignores the
parsed cron expression entirely and returns `now_ts() + 3600` (current time plus exactly one
hour) for every schedule. A bot configured with `0 14 * * *` (fire daily at 14:00 UTC) will fire
approximately 60 minutes after the schedule is created, not at 14:00 UTC. After firing it will
reschedule for an additional hour ahead, never converging to the correct time.

**Claim accuracy**: Confirmed. `app/services/bot_scheduler.py:40–53` shows the complete stub:

```python
def _next_run_from_cron(cron_expression: str, timezone: str = "UTC") -> int:
    """Calculate next run timestamp from cron expression.

    For simplicity, we compute a rough next-run based on current time + interval.
    A full cron engine (like croniter) would be used in production.
    """
    parsed = _parse_cron(cron_expression)
    if not parsed:
        raise ValueError("Invalid cron expression")

    ts = now_ts()
    # Simple heuristic: next run = now + 3600 (1 hour) minimum
    # This is a simplified implementation; production would use croniter
    return ts + 3600
```

The comment explicitly flags this as a placeholder. `croniter` is not in `requirements.txt`.

- **Source ticket**: BOT-002
- **Status**: Open
- **Owning area**: Bot scheduler / task scheduling
- **Related tickets**: BOT-002, SECOPS-007

## 2. Current-State Investigation (root cause)

### Call sites for `_next_run_from_cron()`

`app/services/bot_scheduler.py` calls the function at three points:

| Line | Context |
|---|---|
| 102 | `create_scheduled_send()` — sets `next_run_at` on new schedule record |
| 176 | `update_scheduled_send()` — recalculates `next_run_at` after edit |
| 285 | `_dispatch_due_schedules()` — reschedules after each successful fire |

In all three cases the result is stored in the DynamoDB item's `next_run_at` field and in
`GSI1SK = next_run` (used by the background dispatch loop to find due schedules via
`KeyConditionExpression = Key("GSI1PK").eq("BOTSCHED#PENDING") & Key("GSI1SK").le(now)`).

### The bug in detail

Given cron expression `0 14 * * *` (14:00 UTC daily):

1. Creator POSTs `create_scheduled_send` at 09:00 UTC.
2. `_next_run_from_cron("0 14 * * *")` returns `09:00 + 3600 = 10:00 UTC`.
3. Item stored with `next_run_at = 10:00`.
4. Background dispatch loop runs at 10:01 UTC, finds the schedule due.
5. Bot message sent at 10:01 UTC (wrong — should be 14:00).
6. Schedule rescheduled: `_next_run_from_cron` called again → next_run = `10:01 + 3600 = 11:01`.
7. Next fire at 11:01, then 12:01, 13:01, 14:01, ... — fires every hour, not once per day.

For a `*/5 * * * *` expression (every 5 minutes), the stub is doubly wrong: it never fires more
frequently than every hour, AND the `_parse_cron()` validator at line 35–36 rejects it anyway
(`parts[0] == "*"` check, though `*/5` does NOT match `"*"` literally so this expression would
actually pass validation but still fire only hourly).

### `_parse_cron()` limitations (line 25–37)

The custom parser is a minimal field-splitter. It:
- Rejects expressions where the first field is `*` AND the second is `*` (prevents sub-hourly).
- Does not validate field ranges, step syntax (`*/5`), or list syntax (`1,3,5`).
- Returns a dict of raw field strings but this dict is never read by `_next_run_from_cron()`.

The parsed dict is called but never used:
```python
parsed = _parse_cron(cron_expression)  # validated for format only
if not parsed:
    raise ValueError("Invalid cron expression")

ts = now_ts()
return ts + 3600   # parsed fields completely ignored
```

### Missing dependency

`croniter` (PyPI: `croniter`) is a well-maintained pure-Python library that computes the exact next
occurrence of a 5-field cron expression, supports timezones via `pytz`/`zoneinfo`, handles step
and list syntax, and is battle-tested in production schedulers (Airflow, APScheduler, etc.).
It is not listed in `/home/ubuntu/testlogon/requirements.txt`.

## 3. Impact / Exploit / Blast Radius

### Functional impact

- Every bot scheduled send fires at the wrong time: approximately 1 hour after creation, then every
  hour thereafter regardless of the configured cron expression.
- A `0 9 * * 1` (Monday 9 AM) schedule fires 60 minutes after creation, then every hour forever.
- A `0 0 1 * *` (first of month midnight) schedule fires 60 minutes after creation.
- Creators building time-sensitive notification bots (e.g., daily digest at 08:00) receive an
  entirely broken feature.

### Security / financial impact

Rapid incorrect re-firing could generate spam: a schedule intended to fire once daily generates 24
messages per day. Depending on message quotas and rate limits, this could:
- Exhaust creator message quotas prematurely.
- Spam conversation participants with repeated identical bot messages.
- If tips or content purchases are triggered by bot messages, generate unintended billing.

### Scale of affected schedules

All `bot_scheduled_sends` records in `T.bot_scheduled_sends` where `enabled = True` are affected
from the moment of creation. The impact begins immediately upon BOT-002 deployment and worsens
over time as schedules accumulate.

## 4. Fix Design (code-level)

### Step 1: Add `croniter` to `requirements.txt`

```
# requirements.txt — add after existing entries
croniter==2.0.5
```

`croniter` 2.x supports Python 3.12, has no compiled extension dependencies, and uses
`python-dateutil` (already a transitive dependency of `boto3`). Pinning to `2.0.5` ensures
reproducible builds; the minimum functional version is `1.4.0`.

### Step 2: Replace `_next_run_from_cron()` in `app/services/bot_scheduler.py`

```python
# bot_scheduler.py:40-53 — replace the stub with:

from croniter import croniter, CroniterBadCronError  # top of file

def _next_run_from_cron(cron_expression: str, timezone: str = "UTC") -> int:
    """Return the next Unix timestamp (integer seconds) at which the cron fires.

    Args:
        cron_expression: Standard 5-field cron (minute hour dom month dow).
                         Example: "0 14 * * *" = every day at 14:00.
        timezone: IANA timezone name, default "UTC".
                  Example: "America/New_York".

    Raises:
        ValueError: If the cron expression is invalid.
    """
    parsed = _parse_cron(cron_expression)
    if not parsed:
        raise ValueError(f"Invalid cron expression: {cron_expression!r}")

    import datetime
    try:
        import zoneinfo
        tz = zoneinfo.ZoneInfo(timezone)
    except (ImportError, zoneinfo.ZoneInfoNotFoundError):
        try:
            import pytz
            tz = pytz.timezone(timezone)
        except Exception:
            raise ValueError(f"Unknown timezone: {timezone!r}")

    now_utc = datetime.datetime.now(datetime.timezone.utc)
    # croniter expects a naive local datetime as the base; convert accordingly
    now_local = now_utc.astimezone(tz)

    try:
        cron = croniter(cron_expression, now_local, hash_use_datetime=True)
        next_dt_local = cron.get_next(datetime.datetime)
    except (CroniterBadCronError, ValueError) as exc:
        raise ValueError(f"Invalid cron expression: {cron_expression!r}") from exc

    # Convert back to UTC and return integer Unix timestamp
    next_dt_utc = next_dt_local.astimezone(datetime.timezone.utc)
    return int(next_dt_utc.timestamp())
```

### Step 3: Update `_validate_timezone()` to use `zoneinfo`

The existing `_validate_timezone()` helper (if present in the file) should validate using the same
`zoneinfo.ZoneInfo` constructor used by `_next_run_from_cron()` so that the validation and the
computation agree on which timezone names are valid.

### Step 4: Keep `_parse_cron()` as a pre-validation guard

The existing `_parse_cron()` provides a fast first check (correct number of fields, sub-minute
frequency rejection) before the heavier `croniter` call. This is preserved as-is; `croniter` will
also raise `CroniterBadCronError` on malformed expressions.

### Edge cases handled by `croniter`

| Expression | Before fix | After fix |
|---|---|---|
| `0 14 * * *` | Fires in 60 min, then hourly | Fires next 14:00 UTC |
| `0 9 * * 1` | Fires in 60 min, then hourly | Fires next Monday 09:00 |
| `*/30 * * * *` | Fails `_parse_cron` (first field `*` — wait, `*/30 ≠ *`) | Fires at next :00 or :30 |
| `0 0 1 * *` | Fires in 60 min, then hourly | Fires next 1st of month 00:00 |
| `0 14 * * *` at 14:01 | Fires in 60 min | Fires next day at 14:00 |

### Dev/Prod parity (SECOPS-007)

`_next_run_from_cron()` has no AWS-specific code path. It uses wall-clock time from Python's
`datetime` module. In dev, `now_ts()` returns the local machine's Unix time (the same as in prod).
`croniter` is a pure-Python library and behaves identically in both environments. The function
does not use any feature flags or mock paths.

The only parity consideration is timezone data: `zoneinfo` requires the system to have IANA
timezone data installed. On Ubuntu 22.04+, this is available via `tzdata` package. The fallback
to `pytz` handles environments without system tzdata. Both dev Ubuntu and prod containers should
have `tzdata` installed; verify in the Dockerfile or `setup_ubuntu.sh`.

### Backward compatibility

Existing schedule records in DynamoDB have incorrect `next_run_at` values (approximately
`creation_time + 3600`). A migration step should update them:

```python
# scripts/migrate_bot_schedule_next_run.py
for sched in scan_all_enabled_schedules():
    corrected = _next_run_from_cron(sched["cron_expression"], sched.get("timezone", "UTC"))
    T.bot_scheduled_sends.update_item(
        Key={"pk": sched["pk"], "sk": sched["sk"]},
        UpdateExpression="SET next_run_at = :nra, GSI1SK = :nra",
        ExpressionAttributeValues={":nra": corrected},
    )
```

### Regression test (pytest, offline — no DynamoDB needed)

```python
# tests/test_bot_scheduler_cron.py
import pytest
from unittest.mock import patch
import datetime


class TestNextRunFromCron:
    """GAP-0135: _next_run_from_cron must return the correct next-occurrence timestamp."""

    @pytest.fixture(autouse=True)
    def freeze_now(self, monkeypatch):
        """Fix 'now' to 2026-01-01 09:00:00 UTC for deterministic assertions."""
        fixed_ts = 1767178800  # 2026-01-01 09:00:00 UTC
        monkeypatch.setattr("app.services.bot_scheduler.now_ts", lambda: fixed_ts)
        # Also fix datetime.datetime.now used by croniter path
        self.fixed_utc = datetime.datetime(2026, 1, 1, 9, 0, 0, tzinfo=datetime.timezone.utc)

    def test_daily_14_utc_next_occurrence(self):
        """
        FAILS BEFORE FIX: returns 2026-01-01 10:00:00 (now+3600).
        PASSES AFTER FIX: returns 2026-01-01 14:00:00 UTC.
        """
        from app.services.bot_scheduler import _next_run_from_cron
        result = _next_run_from_cron("0 14 * * *", "UTC")

        expected_dt = datetime.datetime(2026, 1, 1, 14, 0, 0, tzinfo=datetime.timezone.utc)
        expected_ts = int(expected_dt.timestamp())

        assert result == expected_ts, (
            f"Expected next run at 14:00 UTC (ts={expected_ts}), "
            f"got ts={result} ({datetime.datetime.utcfromtimestamp(result)} UTC)"
        )

    def test_daily_14_utc_past_14_schedules_next_day(self):
        """When now is 14:01, next occurrence must be the NEXT day at 14:00."""
        from app.services.bot_scheduler import _next_run_from_cron

        # now = 2026-01-01 14:01 UTC
        fixed_ts = int(
            datetime.datetime(2026, 1, 1, 14, 1, 0, tzinfo=datetime.timezone.utc).timestamp()
        )
        with patch("app.services.bot_scheduler.now_ts", return_value=fixed_ts):
            with patch(
                "datetime.datetime",
                wraps=datetime.datetime,
            ):
                # Can't easily monkeypatch datetime.datetime.now in croniter;
                # test via integration: verify result > 14:01 and == next-day 14:00
                result = _next_run_from_cron("0 14 * * *", "UTC")

        next_day_14 = int(
            datetime.datetime(2026, 1, 2, 14, 0, 0, tzinfo=datetime.timezone.utc).timestamp()
        )
        assert result == next_day_14

    def test_weekly_monday_9am_correct(self):
        """0 9 * * 1 from Thursday 09:00 UTC should fire next Monday."""
        from app.services.bot_scheduler import _next_run_from_cron

        # 2026-01-01 is a Thursday
        result = _next_run_from_cron("0 9 * * 1", "UTC")

        # Next Monday is 2026-01-05
        expected_ts = int(
            datetime.datetime(2026, 1, 5, 9, 0, 0, tzinfo=datetime.timezone.utc).timestamp()
        )
        assert result == expected_ts, (
            "Weekly Monday 09:00 schedule must fire on the upcoming Monday"
        )

    def test_invalid_expression_raises(self):
        """Invalid cron expressions must raise ValueError."""
        from app.services.bot_scheduler import _next_run_from_cron
        with pytest.raises(ValueError):
            _next_run_from_cron("not a cron", "UTC")

    def test_invalid_timezone_raises(self):
        """Unknown timezone names must raise ValueError."""
        from app.services.bot_scheduler import _next_run_from_cron
        with pytest.raises(ValueError):
            _next_run_from_cron("0 14 * * *", "Imaginary/Zone")

    def test_result_is_always_in_future(self):
        """Next run must always be strictly after now."""
        from app.services.bot_scheduler import _next_run_from_cron
        from app.core.time import now_ts

        result = _next_run_from_cron("0 14 * * *", "UTC")
        assert result > now_ts(), "next_run must be in the future"

    def test_stub_behaviour_no_longer_present(self):
        """
        Explicit guard: result must NOT be now_ts() + 3600.
        This fails before fix and passes after fix.
        """
        from app.services.bot_scheduler import _next_run_from_cron
        from app.core.time import now_ts

        result = _next_run_from_cron("0 14 * * *", "UTC")
        stub_value = now_ts() + 3600
        assert result != stub_value, (
            f"_next_run_from_cron returned stub value now+3600={stub_value}; "
            "the stub has not been replaced"
        )
```
