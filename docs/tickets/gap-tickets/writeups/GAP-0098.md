# GAP-0098: trigger_review In-Memory Lock Not Distributed — Remediation Write-up

> Claim accuracy note: The ticket cites `app/services/agent_pm.py:714` as the location.
> Code inspection confirms this is CORRECT. `_RUNNING_REVIEWS` is declared at line 714 as a
> module-level `set[str]`. `trigger_review` checks and mutates this set at lines 730–732 and
> 762. The comment at line 713 explicitly says "so a manual trigger can't double-run." The
> claim is accurate. One important nuance: the dev stack runs with `--workers 1` by default
> (`scripts/run_local_mock_backend.sh:70`), so the bug is latent in dev but fully exploitable
> in any multi-worker or multi-instance production deployment.

## 1. Summary & Classification

**Bug**: `trigger_review` in `app/services/agent_pm.py` uses a process-local Python `set` (`_RUNNING_REVIEWS`) as a guard against concurrent review executions. The set lives in the memory of a single uvicorn worker process. In a production deployment with multiple uvicorn workers (`UVICORN_WORKERS > 1`) or horizontally-scaled backend containers (ECS, Kubernetes), each process maintains its own independent, isolated copy of the set. Two requests arriving at different workers simultaneously both find the set empty, both pass the guard, and both launch duplicate review cycles, creating redundant feature ideas and potentially double-charging any billable downstream work.

- **Severity**: HIGH
- **Source ticket**: AGENT-013
- **Owning area**: Agent PM service / concurrency control
- **Status**: Open
- **Verdict**: Confirmed — claim matches the code exactly
- **One-line impact**: Two concurrent POST `/ui/agent/pm/{agent_id}/trigger-review` requests in production bypass the single-execution guard and double-run the review loop.
- **Related tickets**: GAP-0100 (concurrent audit trigger race — identical root-cause pattern in compliance service), GAP-0081 (double-write claim race), SECOPS-007 (dev/prod parity)

## 2. Current-State Investigation (root cause)

### The in-memory lock

`app/services/agent_pm.py:713–762`:

```python
# Module-level guard so a manual trigger can't double-run for a user (E2E 675.4).
_RUNNING_REVIEWS: set[str] = set()


def is_review_running(*, user_id: str, agent_id: str) -> bool:
    return f"{user_id}:{agent_id}" in _RUNNING_REVIEWS


def trigger_review(*, user_id: str, agent_id: str, count: int = 3) -> Dict[str, Any]:
    ensure_tables()
    key = f"{user_id}:{agent_id}"
    if key in _RUNNING_REVIEWS:           # line 730: CHECK
        raise PmValidationError("REVIEW_IN_PROGRESS", "A review session is already running")
    _RUNNING_REVIEWS.add(key)             # line 732: ACQUIRE (non-atomic with check)
    try:
        ...  # creates feature ideas
    finally:
        _RUNNING_REVIEWS.discard(key)    # line 762: RELEASE
```

The comment at line 713 acknowledges the purpose — preventing double-run — but `set` is a CPython in-process data structure. It is not visible across OS processes, threads in separate workers, or network nodes.

### The race window in a single process

Even within a single Python process with asyncio concurrency, the check-then-add at lines 730–732 is not atomic. Two coroutines could interleave:

```
coroutine A: key not in _RUNNING_REVIEWS  → True (proceeds)
             [context switch here]
coroutine B: key not in _RUNNING_REVIEWS  → True (proceeds)
coroutine A: _RUNNING_REVIEWS.add(key)
coroutine B: _RUNNING_REVIEWS.add(key)
```

In the current implementation the mock body of `trigger_review` is synchronous (no `await` between check and add), so this intra-process race does not manifest today. But as soon as the production async worker dispatch is wired (per the AGENT-013 design), an `await` in the body creates the window.

### Dev vs prod divergence (SECOPS-007)

`scripts/run_local_mock_backend.sh:70`:
```
exec uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers "${UVICORN_WORKERS:-1}"
```

Dev defaults to 1 worker because moto's in-process S3 state is per-process (noted in CLAUDE.md). The E2E test suite (675.4) relies on the in-memory set working correctly and passes. In production, where `UVICORN_WORKERS` is set to the number of CPU cores (typically 4–16 on a production node), or where multiple ECS task instances run, the in-memory set provides zero concurrency protection. The gap is latent in dev and fully active in prod — a textbook SECOPS-007 parity failure.

### Scope of `is_review_running`

The `is_review_running` function (line 717) is exposed as a read endpoint (`GET /ui/agent/pm/{agent_id}/review-status`). In a multi-worker deployment, this endpoint returns `false` on any worker that did not start the review — giving the user and any monitoring system a false "no review running" signal. This compounds the race: the check endpoint itself is unreliable as a status signal.

### Comparison with GAP-0100

GAP-0100 (`trigger_audit` in `agent_compliance.py`) has a similar race but at the DynamoDB layer — `get_running_audit` followed by `put_item` with no conditional expression. Both gaps need a conditional DDB write as the fix; they should be fixed together in the same PR.

## 3. Impact / Exploit / Blast Radius

**Exploit walkthrough (production, 2 workers)**:

1. User sends two near-simultaneous POST requests to `/ui/agent/pm/{agent_id}/trigger-review` (e.g., double-click in the UI, or two browser tabs).
2. Request A arrives at worker 1: `key not in _RUNNING_REVIEWS` (empty set in worker 1) → `add(key)` → starts creating ideas.
3. Request B arrives at worker 2 within milliseconds: `key not in _RUNNING_REVIEWS` (empty set in worker 2) → `add(key)` → starts a second set of ideas concurrently.
4. Both reviews complete. The user has `2 × count` feature ideas, all duplicated with different `idea_id`s but identical titles and descriptions.

**Financial blast radius**: When `S.pm_agent_execute_commands` is `True` (production path per the AGENT-013 design comment), `trigger_review` dispatches real Playwright browsing sessions and LLM calls. Each worker invocation is billed per call-minute and per LLM token. Double execution doubles cost with no user benefit. For a count=10 review with a 5-minute execution time at typical LLM pricing, a double-trigger could add $10–50 of unplanned cost per incident.

**Data integrity**: Duplicate feature ideas pollute the backlog. The `create_feature_idea` function does not deduplicate by title — it always creates a new item with a fresh `idea_id`. The `prioritize_backlog` and sprint-planning agents then see two identical tickets and may schedule work for both. Neither the PM agent nor any background task cleans up duplicates.

**Availability**: A malicious user could send many concurrent requests, spawning a large number of parallel review loops that exhaust thread/worker capacity or LLM rate limits.

**Status endpoint unreliability**: `GET /ui/agent/pm/{agent_id}/review-status` returns `is_running: true/false` by reading `_RUNNING_REVIEWS`. In multi-worker mode, this endpoint returns the state of one worker's memory — not the global state. The frontend may show "no review running" while a review is active on a different worker.

## 4. Fix Design (code-level)

### Recommended fix: DynamoDB conditional put_item (distributed optimistic lock)

Replace the module-level `set` with a short-lived lock item in DynamoDB. The `attribute_not_exists` condition on `put_item` makes lock acquisition atomic at the DynamoDB storage layer, which is safe across processes, workers, and horizontally-scaled instances.

**Add to `app/services/agent_pm.py`**:

```python
import time
from botocore.exceptions import ClientError

_LOCK_SK_PREFIX = "REVIEW_LOCK#"
_LOCK_TTL_SECONDS = 300  # 5 minutes: covers worst-case review duration


def _lock_sk(agent_id: str) -> str:
    return f"{_LOCK_SK_PREFIX}{agent_id}"


def _acquire_review_lock(*, user_id: str, agent_id: str) -> bool:
    """Atomically acquire a per-user-agent review lock in DynamoDB.

    Returns True if the lock was acquired (no concurrent review running).
    Returns False if the lock is already held (ConditionalCheckFailedException).
    Raises on unexpected DynamoDB errors.
    """
    expires_at = int(time.time()) + _LOCK_TTL_SECONDS
    try:
        T.agent_feature_ideas.put_item(
            Item={
                "pk": _user_pk(user_id),
                "sk": _lock_sk(agent_id),
                "lock_type": "review_running",
                "locked_at": now_ts(),
                "expires_at": expires_at,
                "ttl": expires_at,
            },
            ConditionExpression="attribute_not_exists(pk) AND attribute_not_exists(sk)",
        )
        return True
    except ClientError as exc:
        if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
            return False
        raise


def _release_review_lock(*, user_id: str, agent_id: str) -> None:
    """Release the review lock. Best-effort; TTL handles cleanup on crash."""
    try:
        T.agent_feature_ideas.delete_item(
            Key={"pk": _user_pk(user_id), "sk": _lock_sk(agent_id)}
        )
    except Exception:
        pass
```

**Update `trigger_review`** (replace lines 729–762):

```python
def trigger_review(*, user_id: str, agent_id: str, count: int = 3) -> Dict[str, Any]:
    ensure_tables()
    if not _acquire_review_lock(user_id=user_id, agent_id=agent_id):
        raise PmValidationError("REVIEW_IN_PROGRESS", "A review session is already running")
    try:
        config = get_pm_config(user_id=user_id)
        max_ideas = _to_int(config.get("max_ideas_per_review"), 5)
        n = min(max(1, int(count)), max_ideas)
        focus = config.get("focus_areas") or ["ux"]
        created: List[Dict[str, Any]] = []
        for i in range(n):
            category = IDEA_CATEGORIES[i % len(IDEA_CATEGORIES)]
            area = focus[i % len(focus)]
            idea = create_feature_idea(
                user_id=user_id, agent_id=agent_id,
                worker_id=f"worker_{agent_id}",
                title=f"Improve {area} ({category}) #{i + 1}",
                description=f"Mock review suggestion for the {area} area focusing on {category}.",
                category=category,
                priority_suggestion=IDEA_PRIORITIES[i % len(IDEA_PRIORITIES)],
                user_impact=f"Expected to improve {area} engagement.",
                evidence=[{"type": "screenshot", "description": f"{area} flow review"}],
            )
            created.append(idea)
        return {
            "ok": True, "agent_id": agent_id,
            "ideas_created": len(created), "ideas": created,
            "completed_at": now_ts(),
        }
    finally:
        _release_review_lock(user_id=user_id, agent_id=agent_id)
```

**Update `is_review_running`** to query DDB instead of reading the module-level set:

```python
def is_review_running(*, user_id: str, agent_id: str) -> bool:
    """Check whether a review lock is currently held for this user+agent (distributed)."""
    ensure_tables()
    resp = T.agent_feature_ideas.get_item(
        Key={"pk": _user_pk(user_id), "sk": _lock_sk(agent_id)}
    )
    item = resp.get("Item")
    if not item:
        return False
    # Treat expired locks as not running (DynamoDB TTL may lag up to 48 h)
    return int(item.get("expires_at", 0)) > int(time.time())
```

The module-level `_RUNNING_REVIEWS` set can be removed entirely, or retained as a comment for historical context. The DDB lock is now the single authoritative guard.

### TTL setup

Add to `scripts/local-ddb-init.py` (and the production Terraform/CDK table definition):

```python
client.update_time_to_live(
    TableName="agent_feature_ideas",
    TimeToLiveSpecification={"Enabled": True, "AttributeName": "ttl"},
)
```

Without TTL, a worker crash between `_acquire_review_lock` and `_release_review_lock` leaves the lock item permanently, blocking all future reviews for that user+agent until manually deleted.

### Dev/Prod parity (SECOPS-007)

The `conditional put_item` with `attribute_not_exists` is identical between DynamoDB Local (dev) and AWS DynamoDB (prod). No feature flag is needed. The `ttl` attribute is ignored by DynamoDB Local (it does not implement TTL expiry) but causes no errors and is harmless in dev.

**Alternative rejected — Redis distributed lock**: Requires adding a Redis dependency (ElastiCache in prod, Redis container in dev). Not justified when DynamoDB is already present.

**Alternative rejected — asyncio.Lock**: Fixes intra-process concurrency within a single worker but not cross-process or cross-instance. Not a sufficient fix for the production scenario.

**Alternative rejected — database row-level locking via PostgreSQL**: The project uses DynamoDB, not a relational database. Changing persistence layers solely for a lock is disproportionate.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

```python
# tests/services/test_agent_pm_review_lock.py
import time
import pytest
from unittest.mock import patch, MagicMock
from botocore.exceptions import ClientError
from app.services import agent_pm as svc


def _ccf_error():
    return ClientError(
        {"Error": {"Code": "ConditionalCheckFailedException", "Message": "cond"}},
        "PutItem",
    )


class TestReviewLockAcquisition:
    def test_first_acquire_succeeds(self, mocker):
        """Conditional put_item succeeds the first time."""
        mock_put = mocker.patch.object(
            svc.T.agent_feature_ideas, "put_item", return_value={}
        )
        assert svc._acquire_review_lock(user_id="u1", agent_id="a1") is True
        # Verify ConditionExpression was used (atomic guard)
        call_kwargs = mock_put.call_args.kwargs
        assert "ConditionExpression" in call_kwargs

    def test_second_acquire_rejected(self, mocker):
        """ConditionalCheckFailedException returns False, not raises."""
        mocker.patch.object(
            svc.T.agent_feature_ideas, "put_item", side_effect=_ccf_error()
        )
        assert svc._acquire_review_lock(user_id="u1", agent_id="a1") is False

    def test_trigger_review_raises_when_lock_held(self, mocker):
        """FAILS before fix: concurrent calls with separate _RUNNING_REVIEWS sets both succeed."""
        mocker.patch.object(svc, "_acquire_review_lock", return_value=False)
        with pytest.raises(svc.PmValidationError, match="REVIEW_IN_PROGRESS"):
            svc.trigger_review(user_id="u1", agent_id="a1")

    def test_lock_released_after_success(self, mocker):
        """Lock is released in the finally block even on success."""
        release_mock = mocker.patch.object(svc, "_release_review_lock")
        mocker.patch.object(svc, "_acquire_review_lock", return_value=True)
        mocker.patch.object(svc, "get_pm_config", return_value={"max_ideas_per_review": 1})
        mocker.patch.object(
            svc, "create_feature_idea", return_value={"idea_id": "x", "title": "t"}
        )
        svc.trigger_review(user_id="u1", agent_id="a1", count=1)
        release_mock.assert_called_once_with(user_id="u1", agent_id="a1")

    def test_lock_released_after_exception(self, mocker):
        """Lock is released in the finally block even when body raises."""
        release_mock = mocker.patch.object(svc, "_release_review_lock")
        mocker.patch.object(svc, "_acquire_review_lock", return_value=True)
        mocker.patch.object(svc, "get_pm_config", side_effect=RuntimeError("boom"))
        with pytest.raises(RuntimeError):
            svc.trigger_review(user_id="u1", agent_id="a1", count=1)
        release_mock.assert_called_once()

    def test_is_review_running_uses_ddb(self, mocker):
        """is_review_running queries DDB; returns True when lock item exists and is not expired."""
        future_ts = int(time.time()) + 300
        mocker.patch.object(
            svc.T.agent_feature_ideas,
            "get_item",
            return_value={"Item": {"expires_at": future_ts}},
        )
        assert svc.is_review_running(user_id="u1", agent_id="a1") is True

    def test_is_review_running_false_when_expired(self, mocker):
        """is_review_running returns False for an expired lock (TTL may lag)."""
        past_ts = int(time.time()) - 10
        mocker.patch.object(
            svc.T.agent_feature_ideas,
            "get_item",
            return_value={"Item": {"expires_at": past_ts}},
        )
        assert svc.is_review_running(user_id="u1", agent_id="a1") is False
```

**Tests that FAIL before the fix**: `test_trigger_review_raises_when_lock_held` (the old implementation uses `_RUNNING_REVIEWS`, not `_acquire_review_lock`), `test_is_review_running_uses_ddb` (the old implementation reads the module-level set, not DDB).

**Tests that PASS after the fix**: All seven tests pass with the DDB-backed lock.

### Manual QA steps

1. `just up` with `UVICORN_WORKERS=2` set in the shell.
2. In two concurrent terminal tabs (or with `curl &`):
   ```bash
   curl -s -X POST http://localhost:3000/ui/agent/pm/agent_alice/trigger-review \
     -H "Cookie: ..." -H "x-csrf-token: ..." -H "Content-Type: application/json" \
     -d '{"count":3}' &
   curl -s -X POST http://localhost:3000/ui/agent/pm/agent_alice/trigger-review \
     -H "Cookie: ..." -H "x-csrf-token: ..." -H "Content-Type: application/json" \
     -d '{"count":3}'
   wait
   ```
3. **Before fix**: both responses return HTTP 200 with 3 ideas each; `list_feature_ideas` shows 6 duplicate ideas.
4. **After fix**: one response is HTTP 200 (3 ideas); the other is HTTP 409 `"A review session is already running"`. `list_feature_ideas` shows exactly 3 ideas.

### Observability

Emit `logger.warning("review_lock_contention user_id=%s agent_id=%s", user_id, agent_id)` when `ConditionalCheckFailedException` fires. Alert on contention rate > 3/min in production — sustained contention signals either a stuck lock (worker crashed) or a UI-level retry bug sending rapid duplicate requests.

### Rollout

- **Effort**: S (small — approximately 70 lines; no DynamoDB schema change beyond enabling TTL)
- **Risk**: Low — the DDB conditional write is atomic; the only observable change is that the 409 response is now reliably delivered for concurrent requests, rather than occasionally
- **Sequencing**: Apply alongside GAP-0100 (trigger_audit lock) in a single "agent distributed locking" PR to share reviewer context
- **Rollback**: Remove `_acquire_review_lock` call and restore `_RUNNING_REVIEWS` check; single-worker deployments are unaffected; multi-worker deployments revert to the race condition; the lock items in DDB are cleaned up by TTL within 5 minutes
