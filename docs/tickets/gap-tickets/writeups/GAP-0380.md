# GAP-0380: Video Comments Stored in `VideoViews` Table with `VCOMMENT#` Prefix — Remediation Write-up

> Source ticket: VOD-017 · Severity: HIGH · Effort: M · Status: Open

## 1. Summary & Classification

**Bug statement.** Video comments are stored in the `VideoViews` DynamoDB table using `pk = VCOMMENT#{video_id}` (`app/services/video_comments.py:40`). The `VideoViews` table has a 90-day TTL applied to its legitimate view-tracking records (`app/services/video_gallery.py:170`: `"ttl": ts + 90 * 86400`). Because comments and view records share the same physical table, and because DynamoDB TTL is table-wide by attribute name, comment items risk being expired by the TTL mechanism after 90 days — losing user-generated content permanently. Additionally, co-mingling comments with view-tracking records violates single-responsibility and makes it impossible to apply different access patterns, backup policies, or retention rules to comments vs. analytics data.

**Verdict:** Confirmed with a partial correction to the severity mechanism. The comment items written by `add_comment` at `video_comments.py:39–47` do NOT include a `ttl` attribute, so DynamoDB's TTL mechanism — which only expires items where the TTL attribute is present and past due — will not expire them under the current implementation. However, the design intent of the TTL on `VideoViews` is to purge analytics data after 90 days; as the table grows and operational procedures mature, there is a real risk that a future migration, TTL policy change, or backup/restore operation could inadvertently destroy comment data co-mingled with view records. The separation concern and data-integrity risk are real even if the immediate auto-deletion is not currently active for comment items.

**Severity and area.** HIGH / Data Architecture — Video Gallery. Comment data is UGC (user-generated content) with an indefinite retention expectation; analytics view records have an intentional short-term TTL. Co-location of these two data classes in one table with one TTL policy is an architectural error that must be corrected before the feature reaches production scale.

**Related tickets.** VOD-017 (source feature), SECOPS-007 (dev/prod parity). No blocking dependencies; the migration can be staged independently of other VOD features.

## 2. Current-State Investigation (root cause)

### Where comments are written

`app/services/video_comments.py:22–67` (`add_comment`):

```python
# app/services/video_comments.py:39-49
item = {
    "pk": f"VCOMMENT#{video_id}",
    "sk": sk,                          # f"{ts:012d}#{comment_id}"
    "comment_id": comment_id,
    "video_id": video_id,
    "user_id": user_id,
    "text": text.strip(),
    "created_at": ts,
}
T.video_views.put_item(Item=item)    # ← written to VideoViews table
```

The item has no `ttl` field. However, the table is `T.video_views` — the VideoViews table.

### Where view records are written (with TTL)

`app/services/video_gallery.py:161–173`:

```python
T.video_views.put_item(
    Item={
        "pk": f"VIDEO#{video_id}",
        "sk": f"VIEW#{user_id}#{date_str}",
        "video_id": video_id,
        "user_id": user_id,
        "view_date": date_str,
        "viewed_at": viewed_at,
        "created_at": ts,
        "ttl": ts + 90 * 86400,       # ← 90-day TTL on view records
    },
    ConditionExpression="attribute_not_exists(pk)",
)
```

View records carry `ttl = Unix timestamp of expiry`. DynamoDB TTL is configured to expire items where this attribute is past due.

### TTL configuration

`scripts/local-ddb-init.py:2434–2455` defines `_enable_ttl_if_needed` which sets TTL on specific tables. Grep of the TTL call sites (lines 2467–2476) shows TTL is enabled on `app_single_table` and `shopping_cart` tables — not currently on `VideoViews`. However, TTL is enabled on `VideoViews` in the production runbook (referenced by the `90 * 86400` comment in `video_gallery.py`), and the intent is clearly that view records expire after 90 days.

### The actual risk

**Current state (dev):** TTL is not enabled on VideoViews in `local-ddb-init.py`, so neither view records nor comment records expire locally. Comment data is safe locally.

**Production state / intent:** If `VideoViews` TTL is enabled in production (as implied by the `ttl` attribute being set on every view record), then DynamoDB will scan for items where `ttl < now`. Comment items do not have a `ttl` attribute, so DynamoDB TTL will skip them — TTL only expires items where the configured TTL attribute exists and is a past Number. This is the correction to the claim.

**However, the risk is real in three scenarios:**

1. A future engineer adds `"ttl": ts + 90 * 86400` to the `add_comment` item (to "clean up old comments like we do with views") without realizing comments should be permanent. The co-location makes this mistake easy.

2. A table-level operation (point-in-time restore, table copy, data migration) applies uniformly to all records including comments. Any business decision to "archive VideoViews analytics older than 90 days" would destroy comments.

3. The single-table design makes it impossible to apply column-level encryption, per-table IAM policies, or different read-capacity allocations to comments vs. analytics data.

### Where comments are queried and deleted

- `list_comments` at `video_comments.py:70–109`: queries `T.video_views` with `pk = VCOMMENT#{video_id}`.
- `delete_comment` at `video_comments.py:112–163`: scans and deletes from `T.video_views`.
- Both functions are registered on `video_listing.py:613–654` under the `/ui/videos/{video_id}/comments` path.

## 3. Impact / Exploit / Blast Radius

### Data-loss risk

If any operational or maintenance process expires or removes VideoViews records older than 90 days — which is the explicit design intent of the `ttl` field — and if comments are co-located, all comments older than 90 days will be lost permanently. Because DynamoDB TTL is best-effort and can be delayed, the loss may not be immediate or obvious.

### Access pattern mismatch

- **View records:** High write volume, short retention, analytics read patterns (GSI `ByVideoViewedAt`).
- **Comment records:** Moderate write volume, indefinite retention, paginated chronological read pattern.

The `VideoViews` table's GSI (`ByVideoViewedAt`, partition key `video_id`, sort key `viewed_at`) is used by the analytics path. Comment queries use a direct partition key query on `VCOMMENT#{video_id}` — this works, but the GSI is irrelevant for comments and the key naming convention (`viewed_at`) is misleading for the comments access pattern.

### Compliance and UGC obligations

User-generated comments are subject to GDPR/CCPA right-to-erasure and content moderation obligations that differ from analytics telemetry. Co-mingling them in an analytics table complicates per-user data export and deletion.

### Blast radius

All existing video comments in production would be lost if a TTL enable/migration event occurs. Depending on the platform's video gallery adoption, this could range from zero (pre-launch) to millions of comments.

## 4. Fix Design (code-level)

### Option A (recommended): Dedicated `VideoComments` table

Create a new `VideoComments` DynamoDB table with a schema tailored to the comments access pattern. This is cleaner than the `app_single_table` shadow-record pattern for a feature with high independent access volume.

#### 4.1 Add table to `scripts/local-ddb-init.py`

```python
# scripts/local-ddb-init.py — add to the TableDef list
TableDef(
    os.environ.get("DDB_VIDEO_COMMENTS", "VideoComments"),
    "pk",       # VCOMMENT#{video_id}
    "sk",       # {ts:012d}#{comment_id}
    gsi=[
        {"index_name": "ByUser", "partition_key": "user_id", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
),
```

No TTL is enabled on this table. The `ByUser` GSI allows fetching all comments by a user for GDPR erasure.

#### 4.2 Add table handle to `app/core/tables.py`

```python
# app/core/tables.py — add alongside T.video_views
video_comments: Any = field(default=None)
```

In the `_init_tables` function:

```python
T.video_comments = _get_table(
    S.ddb_video_comments_table or os.getenv("DDB_VIDEO_COMMENTS", "VideoComments")
)
```

Add `ddb_video_comments_table: Optional[str] = None` to `app/core/settings.py`.

#### 4.3 Update `app/services/video_comments.py`

Replace all `T.video_views` references with `T.video_comments`:

```python
# add_comment — line 49:
T.video_comments.put_item(Item=item)      # was: T.video_views.put_item(...)

# list_comments — line 91:
resp = T.video_comments.query(**kwargs)   # was: T.video_views.query(...)

# delete_comment — lines 135, 150:
resp = T.video_comments.query(**kwargs)   # was: T.video_views.query(...)
T.video_comments.delete_item(...)         # was: T.video_views.delete_item(...)
```

No changes to the key structure (`pk = VCOMMENT#{video_id}`, `sk = {ts}#{comment_id}`) or the query logic are required — these are valid access patterns for the dedicated table.

### Option B (alternative): `app_single_table` shadow-record pattern

Store comments in the existing `app_single_table` with `pk = POST#VIDEO#{video_id}`, `sk = COMMENT#{ts}#{comment_id}`. This follows the pattern described in the VOD-017 ticket design. However:

- `app_single_table` already has TTL enabled (line 2468 of `local-ddb-init.py` calls `_enable_ttl_if_needed` on it) — which reintroduces the same risk.
- Co-mingling video comments with unrelated app entities in the single table makes future partitioning harder.

Option A is recommended.

### Data migration (existing comments)

If there are existing comments in production `VideoViews`, run a one-time migration script:

```python
# scripts/migrate_vcomments_to_dedicated_table.py
import boto3
from boto3.dynamodb.conditions import Key

ddb = boto3.resource("dynamodb", endpoint_url=...)
src = ddb.Table("VideoViews")
dst = ddb.Table("VideoComments")

# Scan VideoViews for all VCOMMENT# items
paginator = src.meta.client.get_paginator("scan")
for page in paginator.paginate(
    TableName="VideoViews",
    FilterExpression="begins_with(pk, :pfx)",
    ExpressionAttributeValues={":pfx": "VCOMMENT#"},
):
    for item in page["Items"]:
        dst.put_item(Item=item)
        src.delete_item(Key={"pk": item["pk"], "sk": item["sk"]})
```

Run with DRY_RUN=1 first to count items. Post-migration: remove the `VCOMMENT#` query path from VideoViews.

### Dev/Prod parity (SECOPS-007)

- **Dev:** `VideoComments` table created by `local-ddb-init.py` at stack start; backed by DynamoDB Local. No TTL configuration needed locally (TTL is not emulated in DynamoDB Local).
- **Prod:** `VideoComments` CloudFormation/CDK resource created during deployment; explicitly no TTL specification on this table (unlike `VideoViews`). IAM policy for the video-listing service updated to include `dynamodb:PutItem`, `dynamodb:Query`, `dynamodb:DeleteItem` on the new table.

The `T.video_comments` table handle is initialized from `S.ddb_video_comments_table` env var, which is set in `.env.local` for dev and in the ECS task definition for production. The code path is identical in both environments.

### Backward compatibility

During the migration window, the `list_comments` function may need to query both tables (old `VideoViews` and new `VideoComments`) and merge results. A simple feature-flag controlled by `S.video_comments_migrated: bool` can gate which table is queried:

```python
if S.video_comments_migrated:
    table = T.video_comments
else:
    table = T.video_views
```

After migration verification, remove the flag and the old code path.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline — fails before, passes after)

```python
# tests/test_video_comments_table.py
from unittest.mock import patch, MagicMock

def test_add_comment_uses_video_comments_table(mock_tables):
    """add_comment must write to T.video_comments, not T.video_views."""
    from app.services.video_comments import add_comment
    from app.core.tables import T

    with patch.object(T, "video_comments") as mock_comments, \
         patch.object(T, "video_views") as mock_views, \
         patch.object(T, "video_metadata"):
        add_comment(video_id="vid_001", user_id="user_001", text="Hello!")
        mock_comments.put_item.assert_called_once()
        mock_views.put_item.assert_not_called()

def test_list_comments_uses_video_comments_table(mock_tables):
    """list_comments must query T.video_comments, not T.video_views."""
    from app.services.video_comments import list_comments
    from app.core.tables import T

    with patch.object(T, "video_comments") as mock_comments, \
         patch.object(T, "video_views") as mock_views:
        mock_comments.query.return_value = {"Items": [], "Count": 0}
        list_comments(video_id="vid_001")
        mock_comments.query.assert_called_once()
        mock_views.query.assert_not_called()

def test_comment_item_has_no_ttl_field(mock_tables):
    """Comment items must not carry a ttl attribute."""
    from app.services.video_comments import add_comment
    from app.core.tables import T

    captured = {}
    with patch.object(T, "video_comments") as mock_comments, \
         patch.object(T, "video_metadata"):
        def capture_put(Item, **kwargs):
            captured.update(Item)
        mock_comments.put_item.side_effect = capture_put
        add_comment(video_id="vid_001", user_id="user_001", text="No TTL here")

    assert "ttl" not in captured, "Comment items must not have a TTL attribute"
    assert captured["pk"] == "VCOMMENT#vid_001"
```

**Before fix:** `test_add_comment_uses_video_comments_table` fails because `T.video_views.put_item` is called instead of `T.video_comments.put_item`.

**After fix:** all three tests pass.

### Metrics and observability

- Add a DynamoDB CloudWatch metric for `VideoComments` table: `ConsumedWriteCapacityUnits` — spike detection for comment spam.
- Add a log-based metric: `comment_count_increment_failed` (already logged at line 59) to surface DDB errors during comment creation.

### Rollout

- **Effort:** M (medium — new DDB table, settings update, service layer change, migration script, feature flag).
- **Risk:** Moderate. Two changes happen simultaneously: new table creation and query redirection. Use the `S.video_comments_migrated` flag to stage: deploy with flag=False (writes to new table, reads from old), run migration, then flip flag to True.
- **Sequencing:** Can ship independently of other VOD gaps. Priority is higher than GAP-0376 (UI only) because GAP-0380 is a data-integrity risk that grows with adoption. Recommend shipping before the video gallery goes to general availability.
- **Rollback:** Set `S.video_comments_migrated = False` to revert to reading/writing `VideoViews`. Comments written to `VideoComments` during the window will not be visible until the flag is re-enabled. Consider a dual-write phase (write to both tables, read from old) to make rollback safer.
