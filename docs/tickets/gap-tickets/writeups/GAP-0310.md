# GAP-0310: No time-window enforcement on message edit — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at `app/routers/messaging.py:11003`
> and `app/core/settings.py`.

## 1. Summary & Classification

**Bug**: The `PATCH /conversations/{conversation_id}/messages/{message_id}` endpoint
(`edit_message` function at `app/routers/messaging.py:11003`) enforces several content-level
guards (message must be `kind=text`, not revoked, sender must match, not encrypted) but
imposes no time limit on how long after sending a message can be edited. A sender can alter a
message days, months, or years after it was sent. This undermines message integrity, opens
audit-trail gaps in compliance contexts, and allows a bad actor to retroactively modify
incriminating message content.

- **Severity**: HIGH — integrity and compliance gap; unrestricted edit window creates audit
  evasion risk and violates typical messaging platform edit policies.
- **Source ticket**: MSG-001
- **Status**: Open
- **Owning area**: Messaging / Router
- **Claim verdict**: CONFIRMED. `edit_message` at lines 11003–11104 contains no time-window
  check. The ticket's suggested fix references `app/routers/messaging.py:11003` and
  `S.message_edit_window_seconds`; the function exists exactly at that line and the settings
  field `message_edit_window_seconds` does NOT exist in `app/core/settings.py` (only
  `payout_hold_period_seconds` and similar fields are present). The fix requires both a new
  settings field AND a guard in the router.
- **Related tickets**: MSG-001, SECOPS-007.


## 2. Current-State Investigation (root cause)

### `edit_message` code path

```python
# app/routers/messaging.py:11002–11020
@router.patch("/conversations/{conversation_id}/messages/{message_id}", response_model=MessageOut)
def edit_message(
    conversation_id: str,
    message_id: str,
    inp: EditMessageIn,
    req: Request = None,
    user_id: str = Depends(get_messaging_user_id),
):
    require_participant_active(user_id, conversation_id)

    msg = _get_message_or_404(conversation_id, message_id)
    if msg.get("kind") != "text":
        raise HTTPException(400, "Only text messages can be edited")
    if isinstance(msg, dict) and msg.get("revoked_at"):
        raise HTTPException(400, "Cannot edit a revoked message")
    if msg.get("sender_id") != user_id:
        raise HTTPException(403, "Only the sender can edit this message")
    if bool(msg.get("is_encrypted")):
        _raise_encrypted_edit_unsupported()
    # ^^^ NO time-window check here
    ...
```

After the four guards above, the function proceeds directly to write an edit history record
and update the message text. There is no check comparing `now_ts()` to the message's
`created_at` timestamp.

### Settings missing `message_edit_window_seconds`

`app/core/settings.py` does not define `message_edit_window_seconds`. Searching for it returns
no results:

```
$ grep -n "message_edit_window" app/core/settings.py
(no output)
```

The closest existing field is `payout_hold_period_seconds` (line 1487), which follows the
same integer-with-env-var pattern. The edit window field must be added.

### How edit history is currently stored

Edit history is written at lines 11041–11050 to `tbl_edits` with a TTL:

```python
tbl_edits.put_item(
    Item={
        "message_key": _message_key(conversation_id, message_id),
        "edited_at": str(ts),
        "edited_by": user_id,
        "old_text": old_text,
        "new_text": new_text,
        "ttl": ts + EDITS_TTL_SEC,
    }
)
```

`EDITS_TTL_SEC` is defined at the top of the file. The TTL on edit history records is separate
from the question of whether edits should be allowed at all. Both can coexist: edits are
allowed within a time window; the history of allowed edits is stored with TTL.

### Runtime manifestation

A user can:
1. Send a message: `"Let's meet for coffee"` at T+0.
2. The recipient reads and relies on the message.
3. At T+7 days, the sender edits the message to `"I never said that"`.
4. The conversation now shows the edited text; the only indication of an edit is a small
   `edited_at` timestamp if the UI renders it.

In a legal/compliance context (e.g., harassment report, contract dispute), the message history
is unreliable. In a helpdesk context, agents relying on message content for support decisions
can be misled.

The bug is identical in dev and prod. The edit path has no dev-mode branch.


## 3. Impact / Exploit / Blast Radius

### Integrity violation

The primary harm is retrospective falsification. A user in a dispute or under investigation
can alter their own message history at any point. While `tbl_edits` stores the old text, the
edit history has a TTL (`EDITS_TTL_SEC`), so after the TTL expires, the original text is
permanently lost.

### Compliance / legal hold interaction

In jurisdictions with e-discovery obligations or platform content-retention requirements
(GDPR, US subpoena compliance), message content must be preserved as it was at the time of
sending. Unlimited edits with expiring history means the original content is not reliably
retained. The messaging archive system (`test_messaging_archive_*.py`) may or may not capture
the pre-edit text before TTL expiry depending on polling frequency.

### Social engineering / financial fraud

In a platform where messages are used to agree on prices, terms, or commitments (e.g., a
creator agreeing to a custom content delivery at a certain price), retroactive edits can be
used to alter the agreed terms after delivery.

### Blast radius

Affects all users who send text messages. The edit endpoint is authenticated (requires session
cookie or Bearer token), so only the original sender can exploit it. No cross-user impact.
Severity is bounded to the sender's own message history.


## 4. Fix Design (code-level)

### Step 1 — Add `message_edit_window_seconds` to `app/core/settings.py`

Add alongside the existing messaging settings:

```python
# app/core/settings.py — in the messaging section
message_edit_window_seconds: int = int(
    os.environ.get("MESSAGE_EDIT_WINDOW_SECONDS", str(15 * 60))  # default: 15 minutes
)
```

A default of 15 minutes (900 seconds) is consistent with industry norms (Telegram: 48h,
Slack: workspace-configurable, Discord: unlimited but audited). The default can be adjusted
via env var without a code deploy.

Setting `MESSAGE_EDIT_WINDOW_SECONDS=0` in dev/test environments disables the window
(unlimited editing), preserving backward compatibility for existing E2E tests that may edit
messages without caring about timing.

### Step 2 — Add time-window guard in `edit_message`

Insert immediately after the existing guards at `app/routers/messaging.py:11018`:

```python
# app/routers/messaging.py — insert after line 11020 (after encrypted check)
if S.message_edit_window_seconds > 0:
    created_at = int(msg.get("created_at") or 0)
    age_seconds = now_ts() - created_at
    if age_seconds > S.message_edit_window_seconds:
        raise HTTPException(
            400,
            f"Message can no longer be edited. Edit window is "
            f"{S.message_edit_window_seconds} seconds.",
        )
```

The guard is:
- Gated on `S.message_edit_window_seconds > 0`, so `0` means "unlimited" (dev/test default).
- Computed as `now_ts() - created_at` where `created_at` is the integer Unix timestamp stored
  on the message at creation time.
- Returns HTTP 400 with a message that does not expose internal timestamps.

### Full revised function head

```python
@router.patch("/conversations/{conversation_id}/messages/{message_id}", response_model=MessageOut)
def edit_message(
    conversation_id: str,
    message_id: str,
    inp: EditMessageIn,
    req: Request = None,
    user_id: str = Depends(get_messaging_user_id),
):
    require_participant_active(user_id, conversation_id)

    msg = _get_message_or_404(conversation_id, message_id)
    if msg.get("kind") != "text":
        raise HTTPException(400, "Only text messages can be edited")
    if isinstance(msg, dict) and msg.get("revoked_at"):
        raise HTTPException(400, "Cannot edit a revoked message")
    if msg.get("sender_id") != user_id:
        raise HTTPException(403, "Only the sender can edit this message")
    if bool(msg.get("is_encrypted")):
        _raise_encrypted_edit_unsupported()

    # NEW: time-window enforcement
    if S.message_edit_window_seconds > 0:
        created_at = int(msg.get("created_at") or 0)
        if now_ts() - created_at > S.message_edit_window_seconds:
            raise HTTPException(
                400,
                f"Message can no longer be edited. Edit window is "
                f"{S.message_edit_window_seconds} seconds.",
            )

    # existing logic continues unchanged...
    old_text = msg.get("text") or ""
    ...
```

### Dev/Prod parity (SECOPS-007)

The guard uses `S.message_edit_window_seconds`, which is resolved from the `MESSAGE_EDIT_WINDOW_SECONDS`
environment variable. In dev (`.env.local`), setting `MESSAGE_EDIT_WINDOW_SECONDS=0` disables
the window so existing E2E tests continue to pass without modification. In production, the
variable is set to the desired policy (e.g., 900 for 15 minutes). The code path is identical in
both environments — there is no mock branch or dev-only bypass. This satisfies SECOPS-007.

`.env.local.example` should be updated to include:
```
MESSAGE_EDIT_WINDOW_SECONDS=0   # 0 = unlimited in dev; set to e.g. 900 (15m) in prod
```

### Frontend impact

The frontend `ConversationView` / message bubble edit UI should disable or hide the "Edit"
option for messages older than the window. This can be computed client-side:
```ts
const canEdit = message.kind === "text"
  && message.sender_id === currentUser.id
  && !message.is_encrypted
  && (editWindowSeconds === 0 || Date.now() / 1000 - message.created_at <= editWindowSeconds);
```
The backend remains the authoritative enforcement point; the frontend change is UX only.

The `editWindowSeconds` value can be served from an existing or new settings endpoint, or
hardcoded on the frontend as a constant matching the backend default.

### Backward compatibility

- `MESSAGE_EDIT_WINDOW_SECONDS=0` (default in dev) preserves existing behavior for all existing
  tests and development workflows.
- The API response for an out-of-window edit attempt is a 400 (not 422 or 403), consistent with
  the existing guard responses in the same function.
- Existing edit history records in `tbl_edits` are unaffected.

### Manual QA steps

2. `just restart`.
3. Send a message via the UI.
4. Immediately click Edit — should succeed.
5. Wait 61 seconds, click Edit — should receive an error toast ("Message can no longer be
   edited" or similar).
6. Restore `MESSAGE_EDIT_WINDOW_SECONDS=0` for normal dev workflow.

### Metrics / observability

Add an `audit_event("messaging_message_edit_rejected_window", ...)` call in the 400 branch to
track how often users attempt to edit expired messages. This feeds into abuse detection.

### Rollout

1. Deploy settings change and backend guard with `MESSAGE_EDIT_WINDOW_SECONDS=900` in staging.
2. Monitor for 24 hours; confirm no unexpected 400s from legitimate users.
3. Deploy to production.
4. Announce in creator/user comms: "Messages can be edited within 15 minutes of sending."
5. Update frontend to hide/disable edit control on expired messages (UX improvement, not
   security-critical since backend enforces).

### Rollback

Remove the guard block (~6 lines) from `edit_message`, or set
`MESSAGE_EDIT_WINDOW_SECONDS=0` in the production environment to restore unlimited editing
instantly without a code deploy. The `MESSAGE_EDIT_WINDOW_SECONDS=0` escape hatch is the
preferred rollback mechanism because it takes effect within one process restart cycle (no
redeploy required). Monitor the edit endpoint's HTTP 400 rate for 24 hours after rollout;
a spike in 400s may indicate the window is too short for the user population's habits,
in which case increasing the value (e.g., `3600` for 1 hour) is a safe intermediate step
rather than disabling the window entirely.

### Effort estimate: S (Small)

Two files changed: `settings.py` (1 field), `messaging.py` (~6 lines). `.env.local.example`
update (1 line). Two to three pytest tests. Estimated 1–2 hours implementation, 0.5 hours
review.

### Sequencing

Fully independent. Can be deployed at any time without dependency on other GAP tickets. Should
be coordinated with a frontend UI update (disable Edit control) in the same release to avoid
user confusion when the backend rejects edits that the UI still shows as possible.

### Additional hardening consideration

Beyond the time window, consider adding a per-message edit count cap (e.g., maximum 5 edits)
stored alongside `edited_at` on the message record. This prevents an actor from repeatedly
editing the same message within the window to cycle through content versions. The count cap can
be enforced with a DynamoDB `ConditionExpression` on the `update_item` call at
`app/routers/messaging.py:11053`:
```
ConditionExpression="attribute_not_exists(edit_count) OR edit_count < :max"
```
This is a separate enhancement beyond the scope of GAP-0310 but should be filed as a follow-on
ticket once the basic time-window enforcement is in production.
