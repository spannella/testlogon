# GAP-0137: `start_bot_scheduler_task` May Raise RuntimeError at Startup — Remediation Write-up

> ~5 pages. Fix-oriented. Code verified against real implementation; all citations checked.

## 1. Summary & Classification

- **Plain-English statement**: `start_bot_scheduler_task()` at `app/services/bot_scheduler.py:312` is a synchronous function that calls `asyncio.create_task()`. When this function is invoked outside an active event-loop context — for example, from a pytest test that calls `start_bot_scheduler_task()` directly, or from any code path that runs before `uvicorn` has established its event loop — the call raises `RuntimeError: no running event loop`. Additionally, because the function is registered as a `startup` handler via the bare synchronous `app.add_event_handler("startup", start_bot_scheduler_task)` pattern, a developer calling the function outside Starlette's startup context (such as in a unit test or health-check script) will hit this error without any warning.
- **Severity**: HIGH — in the current Starlette/uvicorn deployment configuration the error does not surface at runtime because Starlette's `startup()` coroutine runs all handlers (both sync and async) within an active event loop. However the code is fragile: it relies on an undocumented invariant (a running loop is present whenever startup handlers execute) that is not enforced by the function signature. Any test, script, or alternative deployment path that calls `start_bot_scheduler_task()` directly will crash at the `asyncio.create_task()` call with `RuntimeError`. This is a correctness and portability defect.
- **Claim accuracy note**: The GAP ticket states the function "may raise RuntimeError at startup." Investigation confirms the risk is real but narrower than "at startup under normal uvicorn operation." The `RuntimeError` materialises specifically when the function is called without a running event loop — which occurs in unit tests and direct-call scenarios, but NOT during normal Starlette-managed startup where the handler is called from within the `async def startup()` coroutine. The writeup corrects this nuance and addresses the underlying fragility regardless.
- **Source ticket**: BOT-002 · **Status**: Open · **Owning area**: `app/services/bot_scheduler.py`, `app/main.py:687`
- **Related tickets**: BOT-002 (parent), GAP-0136 (sibling: wildcard dispatch), SECOPS-007 (dev/prod parity)

## 2. Current-State Investigation (Root Cause)

### 2.1 The function definition

```python
# app/services/bot_scheduler.py:312-318
def start_bot_scheduler_task() -> None:
    """Called from main.py startup to launch background scheduler."""
    if not S.bot_scheduled_messages_enabled:
        logger.info("bot_scheduler: disabled by BOT_SCHEDULED_MESSAGES_ENABLED")
        return
    asyncio.create_task(run_bot_scheduler_loop())
    logger.info("bot_scheduler: background loop started")
```

`asyncio.create_task()` (CPython docs) requires a running event loop — it calls `asyncio.get_running_loop()` internally and raises `RuntimeError: no running event loop` if none exists.

### 2.2 The registration pattern

`app/main.py:687`:

```python
app.add_event_handler("startup", start_bot_scheduler_task)
```

This registers `start_bot_scheduler_task` as a synchronous startup handler. Starlette 0.36.3 (the version in `requirements.txt`) calls startup handlers from within `async def startup()` (verified via `inspect.getsource(Router.startup)`):

```python
async def startup(self) -> None:
    for handler in self.on_startup:
        if is_async_callable(handler):
            await handler()
        else:
            handler()   # ← sync handlers called here
```

Because `startup()` is itself a coroutine that is awaited by uvicorn's ASGI lifespan machinery, a running event loop IS present when `handler()` executes. This means `asyncio.create_task()` succeeds in normal production operation.

### 2.3 Conditions that trigger the RuntimeError

The `RuntimeError` manifests in the following scenarios, all of which are realistic:

1. **Direct call in a unit test** — any test that calls `start_bot_scheduler_task()` outside a `pytest-asyncio` or `anyio` async context (e.g., in a synchronous test function or in a module-level import side-effect) will crash.
2. **Calling from a startup script or CLI tool** — if a deployment script, health-check probe, or `rootctl` command imports and calls `start_bot_scheduler_task()` before establishing a loop, the crash occurs.
3. **Python 3.10+ deprecation path** — `asyncio.get_event_loop()` in Python 3.10+ emits a `DeprecationWarning` when called from a non-async context and will eventually raise `RuntimeError` in future Python versions. While the code uses `create_task` (not `get_event_loop`), the underlying reliance on a running loop is the same.
4. **Any alternative ASGI server** — ASGI servers other than uvicorn (e.g., Hypercorn, Daphne) may call startup handlers differently. If such a server calls sync handlers before establishing a loop, the crash occurs.

### 2.4 Comparison with the same pattern in billing_dunning

`app/services/billing_dunning.py:294-302` uses the identical pattern:

```python
def start_billing_dunning_task() -> None:
    ...
    asyncio.create_task(billing_dunning_loop())
```

This confirms the pattern is widespread in the codebase. The fix must follow a consistent approach to avoid divergence.

### 2.5 The correct pattern

`asyncio.create_task()` must be called from a coroutine or from a function that is itself awaited within an async context. The safe pattern for registering background tasks is:

```python
async def _startup_handler() -> None:
    asyncio.create_task(run_bot_scheduler_loop())
```

An `async def` handler registered via `app.add_event_handler()` will be awaited by Starlette's `startup()` (the `is_async_callable(handler)` branch), guaranteeing that the running loop is present via normal Python semantics — not as an undocumented side-effect of the call stack.

## 3. Impact / Exploit / Blast Radius

### 3.1 Primary impact: test suite crashes

Any pytest test that exercises `start_bot_scheduler_task()` in a synchronous context will crash with `RuntimeError: no running event loop`. This silently prevents bot scheduler tests from running and can mask other issues discovered only under scheduler operation.

### 3.2 Secondary impact: startup failure under alternative deployment

If the application is deployed using an ASGI server that invokes startup handlers differently (e.g., a custom ASGI middleware, a test harness, or a future uvicorn version), `start_bot_scheduler_task()` will crash at startup, bringing down the application. This is a latent reliability risk that is currently hidden by the specific behaviour of uvicorn 0.29.0 + Starlette 0.36.3.

### 3.3 Debugging difficulty

The traceback from `RuntimeError: no running event loop` inside `asyncio.create_task()` does not clearly identify `bot_scheduler.py` as the source. It appears deep in asyncio internals. A developer debugging a startup regression would need to trace through the asyncio stack to find `start_bot_scheduler_task` as the origin.

### 3.4 Blast radius

The bot scheduler background loop (`run_bot_scheduler_loop`) is the only mechanism that dispatches scheduled sends. If `start_bot_scheduler_task()` crashes at startup and the exception is swallowed (which it would be, since Starlette wraps startup handlers in a try/except in some versions), no scheduled messages are ever delivered. This would be indistinguishable from GAP-0136 (wildcard skip) from the creator's perspective.

## 4. Fix Design (Code-Level)

### 4.1 Make `start_bot_scheduler_task` an async function

The minimal, correct fix is to change `start_bot_scheduler_task` from a synchronous to an asynchronous function:

**Before** (`app/services/bot_scheduler.py:312-318`):
```python
def start_bot_scheduler_task() -> None:
    """Called from main.py startup to launch background scheduler."""
    if not S.bot_scheduled_messages_enabled:
        logger.info("bot_scheduler: disabled by BOT_SCHEDULED_MESSAGES_ENABLED")
        return
    asyncio.create_task(run_bot_scheduler_loop())
    logger.info("bot_scheduler: background loop started")
```

**After**:
```python
async def start_bot_scheduler_task() -> None:
    """Called from main.py startup to launch background scheduler.

    Must be async so asyncio.create_task() is called within a running event loop.
    Register with app.add_event_handler("startup", start_bot_scheduler_task) — Starlette
    will await this because is_async_callable() returns True for coroutine functions.
    """
    if not S.bot_scheduled_messages_enabled:
        logger.info("bot_scheduler: disabled by BOT_SCHEDULED_MESSAGES_ENABLED")
        return
    asyncio.create_task(run_bot_scheduler_loop())
    logger.info("bot_scheduler: background loop started")
```

This is a one-line change (`def` → `async def`). No changes to `app/main.py:687` are needed — Starlette's `add_event_handler` accepts both sync and async callables; it will now `await` the function because `is_async_callable()` returns `True` for `async def` functions.

### 4.2 Apply the same fix to `billing_dunning.py` (related defect)

For consistency and to prevent a parallel defect from surfacing, `start_billing_dunning_task()` at `app/services/billing_dunning.py:294` should receive the identical `async def` treatment:

```python
async def start_billing_dunning_task() -> None:
    ...
    asyncio.create_task(billing_dunning_loop())
```

This is outside the strict scope of GAP-0137 but is the correct remediation pattern for all similar startup task launchers in the codebase.

### 4.3 Alternative approaches considered

**Option A: Use `asyncio.get_event_loop().create_task()`** — This is deprecated in Python 3.10+ and will raise a `DeprecationWarning` when called from a synchronous context. Rejected.

**Option B: Use `asyncio.ensure_future()`** — `ensure_future()` accepts both coroutines and futures, and it also calls `get_event_loop()` internally. Same deprecation risk as Option A. Rejected.

**Option C: Wrap in a lambda inside `main.py`** — Register `lambda: asyncio.ensure_future(run_bot_scheduler_loop())` as the startup handler. This is harder to test, less readable, and doesn't fix the underlying synchronous function signature. Rejected.

**Option D: Use `@app.on_event("startup")` decorator** — FastAPI's `@app.on_event("startup")` is equivalent to `app.add_event_handler("startup", ...)` and is deprecated in FastAPI 0.95+ in favor of `lifespan`. Since the existing codebase uses `add_event_handler` consistently, changing the registration style would introduce inconsistency. Rejected in favor of the minimal change.

### 4.4 Dev/Prod parity (SECOPS-007)

This fix has no AWS-specific paths. `asyncio.create_task()` behavior is identical in dev (single-worker uvicorn) and prod. The `BOT_SCHEDULED_MESSAGES_ENABLED` flag gates the task in both environments. Changing to `async def` does not affect the dev/mock behaviour of the scheduler loop itself.

## 5. Testing, Verification & Rollout

### 5.1 Regression test (pytest, offline)

**File**: `tests/test_bot_scheduler_startup.py`

```python
"""
Regression test for GAP-0137 — start_bot_scheduler_task must be async.

Fails before fix: calling start_bot_scheduler_task() in a sync context crashes with
    RuntimeError: no running event loop
Passes after fix: the function is async and can be awaited safely.
"""
import asyncio
import inspect
import pytest
from unittest.mock import patch


def test_start_bot_scheduler_task_is_async():
    """
    GAP-0137: start_bot_scheduler_task must be an async coroutine function.
    Before fix: inspect.iscoroutinefunction returns False.
    After fix: inspect.iscoroutinefunction returns True.
    """
    from app.services.bot_scheduler import start_bot_scheduler_task
    assert inspect.iscoroutinefunction(start_bot_scheduler_task), (
        "start_bot_scheduler_task must be an async def so Starlette awaits it "
        "and asyncio.create_task() is called within a running event loop. "
        "Without this, calling the function from a non-async context raises "
        "RuntimeError: no running event loop."
    )


@pytest.mark.asyncio
async def test_start_bot_scheduler_task_creates_task_when_enabled():
    """
    GAP-0137: When BOT_SCHEDULED_MESSAGES_ENABLED=True, start_bot_scheduler_task
    must create an asyncio Task without raising RuntimeError.
    Passes after fix because the function is async and asyncio.create_task() is
    called from within a running event loop.
    """
    from app.services.bot_scheduler import start_bot_scheduler_task

    with patch("app.services.bot_scheduler.S") as mock_s, \
         patch("app.services.bot_scheduler.run_bot_scheduler_loop") as mock_loop:

        mock_s.bot_scheduled_messages_enabled = True
        # mock_loop returns a coroutine that immediately completes
        async def _dummy_loop():
            pass
        mock_loop.return_value = _dummy_loop()

        # Before fix: this would raise RuntimeError: no running event loop
        # when called from a sync test (even in pytest-asyncio context the
        # sync def would fail)
        await start_bot_scheduler_task()
        mock_loop.assert_called_once()


@pytest.mark.asyncio
async def test_start_bot_scheduler_task_returns_early_when_disabled():
    """
    GAP-0137: When BOT_SCHEDULED_MESSAGES_ENABLED=False, no task is created.
    """
    from app.services.bot_scheduler import start_bot_scheduler_task

    with patch("app.services.bot_scheduler.S") as mock_s, \
         patch("app.services.bot_scheduler.asyncio") as mock_asyncio:

        mock_s.bot_scheduled_messages_enabled = False
        await start_bot_scheduler_task()
        mock_asyncio.create_task.assert_not_called()


def test_calling_sync_create_task_outside_event_loop_raises_runtime_error():
    """
    Demonstrates that a sync function calling asyncio.create_task() outside
    an async context raises RuntimeError — the exact failure mode GAP-0137 fixes.
    This test passes both before and after the fix (it documents the root cause).
    """
    import asyncio

    async def dummy():
        pass

    def bad_sync_startup():
        asyncio.create_task(dummy())

    with pytest.raises(RuntimeError, match="no running event loop"):
        bad_sync_startup()
```

Run with: `.venv/bin/pytest tests/test_bot_scheduler_startup.py -v`

The key test is `test_start_bot_scheduler_task_is_async`: it fails before the fix (the function is `def`, not `async def`) and passes after.

### 5.4 Rollout and rollback

- **Rollout**: Deploy as a backend-only, single-line change. No DDB migration, no frontend change.
- **Rollback**: Revert `async def` to `def` in `bot_scheduler.py`. The function will revert to the current behaviour (works in Starlette startup, fails outside it).
- **Risk**: Extremely low. The only change is making the function awaitable; the body is identical. Starlette 0.36.3's `add_event_handler` correctly handles async handlers.
- **Effort**: S (less than 1 hour, including test writing).
