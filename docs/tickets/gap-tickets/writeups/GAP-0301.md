# GAP-0301: `/internal/dev-tools/ffmpeg-health` endpoint absent — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Severity**: HIGH · **Source ticket**: MEDIA-002 · **Status**: Open · **Effort**: S  
**Owning area**: Backend — internal dev-tools router / FFmpeg management

The `/internal/dev-tools/ffmpeg-health` HTTP endpoint does not exist. The `ffmpeg_manager` service already exposes a fully-formed `validate_ffmpeg()` function that returns a structured health dict, but that function is never called from any HTTP route. The `internal_devtools.py` router has four endpoints (email messages, SMS conversations, billing ledger, billing summary) but nothing for FFmpeg.

**Claim verification**: Confirmed accurate. A full-text search across all router files for `ffmpeg` and `ffmpeg-health` returns zero results. The function `validate_ffmpeg` at `app/services/ffmpeg_manager.py:129` is defined and fully implemented but has no wired caller in any router.

**Impact**: The Dev Tools UI (port 3001) cannot surface FFmpeg binary status. Monitoring integrations — CI health dashboards, deployment smoke-tests, on-call runbooks — have no structured signal for whether the FFmpeg binary is present, version-correct, and codec-complete. An operator deploying to a host that is missing `libx264` has no immediate way to detect the gap short of attempting a real transcode and parsing a raw error log.

**Related tickets**: MEDIA-002 (FFmpeg binary manager), MEDIA-003 (ABR pipeline), GAP-0033 (FFmpeg S3 URI), GAP-0034 (HLS manifest URL not populated — related health surface).

## 2. Current-State Investigation (root cause)

### 2.1 The router file: `app/routers/internal_devtools.py`

```
app/routers/internal_devtools.py:24   router = APIRouter(prefix="/internal/dev-tools", ...)
app/routers/internal_devtools.py:78   @router.get("/email/messages", ...)
app/routers/internal_devtools.py:101  @router.get("/sms/conversations", ...)
app/routers/internal_devtools.py:120  @router.get("/billing/ledger", ...)
app/routers/internal_devtools.py:144  @router.get("/billing/summary", ...)
```

Four endpoints are registered. There is no fifth endpoint for `/ffmpeg-health`. The file ends at line 161.

### 2.2 The capability that should be wired: `app/services/ffmpeg_manager.py`

`validate_ffmpeg()` at line 129 already does everything a health endpoint needs:

- Calls `get_ffmpeg_info()` (line 131) which runs `ffmpeg -version` and `ffmpeg -codecs` via `subprocess.run` with a 5-second timeout.
- Returns a structured dict with keys: `status` (`"healthy"` | `"degraded"` | `"unavailable"`), `path`, `version`, `codecs`, `missing_required`, `missing_recommended`, `issues`.
- `get_ffmpeg_info()` is decorated with `@lru_cache(maxsize=1)` (line 80) so repeated HTTP health checks are cheap; `clear_cache()` exists for test isolation.

The `REQUIRED_CODECS` set is `{"libx264", "aac"}` (line 31). `MIN_VERSION` is `(5, 0)` (line 34). If either is absent the status is `"degraded"` rather than `"unavailable"`.

### 2.3 Dev-mode gate: `_require_devtools_enabled()`

Every endpoint in the router calls `_require_devtools_enabled()` (lines 28–33), which raises HTTP 404 when `S.dev_mode` is `False`. This is the SECOPS-007-compliant pattern: the entire `/internal/dev-tools/` surface is invisible in production, so no AWS-specific parity logic is needed for a read-only binary check.

### 2.4 Why the gap occurred

The MEDIA-002 ticket specified the FFmpeg binary manager as infrastructure for the ABR pipeline; it did not explicitly call out a dev-tools health route. The gap audit identified that the `validate_ffmpeg()` function was never surfaced. The dev-tools router was extended for email/SMS/billing in subsequent tickets but the FFmpeg route was never added.

### 2.5 Runtime manifestation

In the local dev stack: the Dev Tools UI calls `/internal/dev-tools/*` to populate its status panels. A panel for FFmpeg cannot be built because the backend returns 404 for `/internal/dev-tools/ffmpeg-health`. Any CI check that tries to `GET /internal/dev-tools/ffmpeg-health` receives 404 and cannot distinguish "FFmpeg absent" from "endpoint absent".

## 3. Impact / Exploit / Blast Radius

This is an **observability gap**, not a security vulnerability.

**Developer impact**: A developer who installs the project on a host lacking FFmpeg 5.x (e.g., Ubuntu 20.04 with FFmpeg 4.4) will receive a `500` or cryptic error only when a transcode is actually triggered, not at deploy time. The missing health endpoint means there is no way to distinguish "binary not installed" from "binary present but wrong version" or "binary present but missing libx264".

**CI/CD impact**: Smoke tests cannot reliably detect broken FFmpeg installations post-deploy. If the transcode pipeline (`app/services/ffmpeg_abr_pipeline.py`) fails because of a missing codec, the failure surfaces as a generic internal error at the user-facing video upload endpoint rather than as a labelled infrastructure failure.

**On-call impact**: Runbooks that instruct operators to `curl /internal/dev-tools/ffmpeg-health` will fail with 404, adding confusion during an incident.

**Blast radius**: Entirely contained to the dev/monitoring tooling layer. No user data is at risk. No security boundary is crossed. The worst case is that a broken FFmpeg deployment goes undetected until users experience failed video uploads.

## 4. Fix Design (code-level)

### 4.1 Response model

Add a `DevtoolsFfmpegHealthOut` Pydantic model to `app/models.py` (adjacent to the other `Devtools*` models):

```python
class DevtoolsFfmpegHealthOut(BaseModel):
    status: Literal["healthy", "degraded", "unavailable"]
    path: str
    version: str
    codecs: list[str]
    missing_required: list[str]
    missing_recommended: list[str]
    issues: list[str]
```

### 4.2 New endpoint in `app/routers/internal_devtools.py`

Import `validate_ffmpeg` and `DevtoolsFfmpegHealthOut`, then add at the end of the router (after line 161):

```python
from app.services.ffmpeg_manager import validate_ffmpeg
# (add DevtoolsFfmpegHealthOut to the existing models import block)

@router.get("/ffmpeg-health", response_model=DevtoolsFfmpegHealthOut)
def get_devtools_ffmpeg_health() -> DevtoolsFfmpegHealthOut:
    """Return FFmpeg binary status and codec availability (dev mode only)."""
    _require_devtools_enabled()
    _audit_devtools_access("ffmpeg-health")
    result = validate_ffmpeg()
    return DevtoolsFfmpegHealthOut(**result)
```

No additional parameters are needed; `validate_ffmpeg()` introspects the binary path from `S.ffmpeg_binary_path` (via `get_ffmpeg_info()` which reads that setting). The `@lru_cache` on `get_ffmpeg_info` means the subprocess fork happens at most once per worker process lifetime.

### 4.3 Dev/Prod parity (SECOPS-007)

`_require_devtools_enabled()` enforces that `S.dev_mode is True`. In production (`DEV_MODE=0`) the route returns 404 before any FFmpeg interaction. No conditional import, no `if S.dev_mode` branching inside the logic itself — the gate is fully centralised in the existing helper, consistent with all other devtools endpoints. This satisfies the SECOPS-007 requirement that internal tooling surfaces be completely absent (404) in production.

If a future requirement arises to expose a lightweight health check in production (e.g., for Kubernetes liveness probes), that should be a separate `GET /internal/health/ffmpeg` route under a different prefix with its own auth gate — not by relaxing the devtools gate.

### 4.4 Cache invalidation hook (optional enhancement)

Add a `DELETE /internal/dev-tools/ffmpeg-health/cache` endpoint that calls `clear_cache()` to force a fresh probe after a binary upgrade. This is low-effort and useful for integration tests, but is not required for the minimum fix.

### 4.5 Alternatives considered

**Alternative A — expose `validate_ffmpeg` directly from an existing health route**: The FastAPI app already has a `GET /health` endpoint. Embedding FFmpeg status there would make it visible in production without the devtools gate. Rejected: production health endpoints should be lightweight and must not fork subprocesses or expose internal binary paths to unauthenticated callers.

**Alternative B — background-task caching on startup**: Pre-call `get_ffmpeg_info()` at application startup and store the result in a module-level variable. Rejected: `get_ffmpeg_info` already uses `@lru_cache(maxsize=1)`, which achieves the same effect without startup coupling.

### 5.3 Observability

No new persistent metrics are required. The endpoint is debug-only. Operators can call it from runbooks or CI smoke tests.

To improve signal for ongoing monitoring, consider:

- **Log the probe result at startup**: Call `get_ffmpeg_info()` once in the FastAPI `lifespan` startup handler and log `"FFmpeg available: {info.available} version={info.version} codecs={info.codecs}"`. This produces a single structured log line visible in `just status` output, giving operators instant feedback on binary health at deploy time without needing to make an HTTP request.
- **CI smoke-test step**: Add a step to the CI pipeline that curls the endpoint after deployment and fails the pipeline if `status` is `"unavailable"` or if `missing_required` is non-empty. This catches broken FFmpeg installations immediately rather than at first video upload.
- A Playwright test in the Dev Tools UI spec could assert that the FFmpeg status panel renders non-empty status text and that the `codecs` list is visible.

### 5.4 Rollback

The change is additive (new endpoint only). Rolling back means removing the `@router.get("/ffmpeg-health")` handler; all other endpoints are unaffected.

### 5.5 Dev Tools UI integration (future)

Once the backend endpoint exists, the Dev Tools React app (`frontend/dev-tools/`) should add an FFmpeg status card. The card should:
- Call `GET /internal/dev-tools/ffmpeg-health` on page load.
- Display `status`, `version`, `codecs` in a monospace table.
- Render `missing_required` and `issues` in a red warning box if non-empty.
- Show a "Refresh" button that POSTs to an optional `/internal/dev-tools/ffmpeg-health/cache/clear` endpoint (calls `clear_cache()`) and then refetches.

This gives operators a single glance at FFmpeg health without needing curl or reading raw logs.

### 5.6 Considerations for multi-worker deployments

`get_ffmpeg_info()` uses `@lru_cache(maxsize=1)` at the module level. In a multi-worker deployment (multiple `uvicorn` workers), each worker process has its own LRU cache. A `DELETE /cache` action would only clear the cache for the worker that handled the request. This is acceptable because: (a) the dev stack uses `--workers 1`, and (b) in production the devtools gate (`_require_devtools_enabled()`) returns 404 before the cache is ever touched.

### 5.7 Relationship to GAP-0034 (HLS manifest URL not populated)

GAP-0034 notes that `VideoMetadataModel.hls_manifest_url` is never populated after the ABR pipeline completes because the pipeline callback does not write the CDN URL back to DynamoDB. That gap affects production. GAP-0301 (this ticket) is the dev/monitoring companion: even if GAP-0034 were fixed and production videos had real HLS URLs, operators still need a structured health check to confirm the FFmpeg binary that drives the pipeline is functional. The two fixes are independent and should be sequenced in parallel.

### 5.8 Response model placement

The `DevtoolsFfmpegHealthOut` model should be added to `app/models.py` adjacent to the existing `DevtoolsEmailMessagesOut`, `DevtoolsSmsConversationsOut`, `DevtoolsBillingLedgerOut`, and `DevtoolsBillingLedgerSummaryOut` models. These are currently defined around line 800 in `app/models.py` (the exact line number may vary). Keeping all `Devtools*` response models together aids discoverability and makes it obvious that they are all gated behind the devtools route guard.

**Sequencing**: No dependencies. Can be merged independently of MEDIA-003 and the ABR pipeline work. Should be done before any CI health check integration is wired.
