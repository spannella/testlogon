# GAP-0060: FTC Labeling Limited to Post Content Type Only — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against live code at
> `app/services/sponsorship_deals.py:265–292` (`_add_ftc_label`),
> `app/core/tables.py`, `app/models_video.py`,
> `scripts/local-ddb-init.py`. No investigation doc exists.

## 1. Summary & Classification

**Gap**: `app/services/sponsorship_deals.py:_add_ftc_label` (lines 265–292) applies the
FTC "paid partnership" disclosure only to `content_type == "post"` content. For the
two other allowed sponsorship content types (`"video"` and `"broadcast"`), the function
returns immediately at line 271 without writing any disclosure. Sponsored video and
broadcast content therefore silently ships without the legally mandated FTC label.

- **Severity**: HIGH (compliance/legal)
- **Source ticket**: ADS-013
- **Owning area**: Sponsorship Deals / Compliance
- **Status**: Open
- **Related tickets**: ADS-013 (sponsorship deals feature)
- **Verdict**: Claim confirmed. The early-return at `if content_type != "post": return`
  is present in the live code at line 271. The GAP ticket states the line is 272; the
  actual line is 271 — a one-line discrepancy, but the substance is identical. Claim is
  accurate.

**One-line impact**: Any video or broadcast piece of content linked to a sponsorship deal
reaches the audience without the FTC "Paid partnership with X" disclosure that U.S. law
requires, exposing the platform and its creators to FTC enforcement action.

## 2. Current-State Investigation (root cause)

### `_add_ftc_label` — early return for non-post content

`app/services/sponsorship_deals.py:265–292`:

```python
def _add_ftc_label(content_type: str, content_id: str, *, brand_name: str, deal_id: str) -> None:
    """Apply FTC disclosure to the linked content (server-side, immutable).

    For ``post`` content this updates the newsfeed post META item with
    ``sponsored_by``, ``deal_id`` and ``ftc_disclosure``.
    """
    if content_type != "post":       # <--- LINE 271: silent skip for video/broadcast
        return
    try:
        from app.routers.newsfeed import tbl as feed_tbl, pk_post, sk_post

        disclosure = f"Paid partnership with {brand_name}"
        feed_tbl.update_item(
            Key={"pk": pk_post(content_id), "sk": sk_post()},
            UpdateExpression=(
                "SET sponsored_by = :b, deal_id = :d, ftc_disclosure = :f, updated_at = :u"
            ),
            ExpressionAttributeValues={
                ":b": brand_name,
                ":d": deal_id,
                ":f": disclosure,
                ":u": str(now_ts()),
            },
        )
    except Exception:
        pass
```

The docstring says "For `post` content this updates..." — the intent was always to extend
this to other types but the implementation was never completed.

### `_add_ftc_label` is called from `submit_content` — unconditionally

`sponsorship_deals.py:531`:

```python
_add_ftc_label(deal["content_type"], content_id, brand_name=brand_name, deal_id=deal_id)
```

This is the correct call site — it is reached for all `content_type` values. Only the
implementation inside `_add_ftc_label` is deficient.

### Sponsorship deals allow `video` and `broadcast` content types

`sponsorship_deals.py:361` (`create_deal`) accepts any `content_type` string without
restriction. The ADS-013 spec permits deals for `"post"`, `"video"`, and `"broadcast"`.

### `video` content type — target table and schema

`VideoMetadata` table — PK: `video_id` (no composite key). The model
(`app/models_video.py:36–43`) and the DDB init (`scripts/local-ddb-init.py:888–930`)
confirm that `T.video_metadata` is accessible via `T.video_metadata.update_item` with
`Key={"video_id": content_id}`. There are no existing `sponsored_by`, `deal_id`, or
`ftc_disclosure` fields in the model — they will be added as free-form DynamoDB
attributes (the table is schemaless except for the key; the model is a Pydantic read
model that can tolerate unknown fields via `extra = "allow"` or by reading raw DDB
items).

### `broadcast` content type — target table and schema

`BroadcastSessions` table — PK: `session_id` (no SK, see
`scripts/local-ddb-init.py:686–695`). `T.broadcast_sessions` can be updated with
`Key={"session_id": content_id}`. Like the video table, there are no existing FTC
fields; they will be new free-form attributes.

### The `except Exception: pass` pattern is intentional (best-effort)

The existing `post` path wraps the `update_item` in `try/except Exception: pass` —
"FTC labeling is best-effort; do not fail the submission if the content is not a
newsfeed post or cannot be updated." The same pattern must be maintained for video and
broadcast: a failure to label should not block the deal submission. However, unlike
content_boost's equivalent, here the best-effort choice has compliance implications that
should be logged at minimum.

## 3. Impact / Exploit / Blast Radius

**Who is affected**: Creators who accept sponsorship deals for video or broadcast
content; advertisers using the platform; platform users watching sponsored content.

**Regulatory exposure**:

Under the FTC's Endorsement Guides (16 CFR Part 255, revised 2023), material connections
between creators and brands must be clearly and conspicuously disclosed. The FTC has
specifically extended these requirements to:
- Sponsored YouTube/video content: mandatory on-screen disclosure.
- Sponsored livestreams and broadcasts: must label the broadcast with "paid partnership"
  or equivalent.

A platform that stores sponsorship deal data but fails to apply the disclosure server-side
becomes an accessory to the creator's non-compliance. The FTC can pursue both the creator
and the platform operator.

**Concrete failure scenario**:

1. Advertiser and creator negotiate a `deal` with `content_type = "video"`.
2. Creator submits a video with `content_id = "vid_abc"` via `submit_content`.
3. `_add_ftc_label("video", "vid_abc", ...)` executes, hits `if content_type != "post": return`,
   and exits.
4. The video's DynamoDB record has no `ftc_disclosure` field.
5. The video player UI reads the item and displays no disclosure badge.
6. A regulator or journalist views the video, sees no disclosure, and files a complaint.

**Volume**: Every completed sponsorship deal with `content_type != "post"` is silently
missing its label. This is not a theoretical edge case — the ADS-013 feature was built
to support video and broadcast deals.

**Data integrity**: `deal["content_id"]` in a completed deal points to content that the
advertiser believes is labeled. It is not. The `completed_at` deal event in the audit
trail does not record whether the FTC label was actually applied.

## 4. Fix Design (code-level)

### Approach: extend `_add_ftc_label` to handle all three content types

The fix is contained within `_add_ftc_label`. No changes to `submit_content` or the
router are required.

#### 4.1 Revised `_add_ftc_label`

```python
def _add_ftc_label(content_type: str, content_id: str, *, brand_name: str, deal_id: str) -> None:
    """Apply FTC disclosure to the linked content (server-side, immutable).

    Covers 'post' (newsfeed), 'video' (VideoMetadata), and 'broadcast'
    (BroadcastSessions). Failures are best-effort and logged but do not
    block deal submission.
    """
    import logging as _logging
    _logger = _logging.getLogger(__name__)

    disclosure = f"Paid partnership with {brand_name}"
    ts = str(now_ts())

    if content_type == "post":
        try:
            from app.routers.newsfeed import tbl as feed_tbl, pk_post, sk_post
            feed_tbl.update_item(
                Key={"pk": pk_post(content_id), "sk": sk_post()},
                UpdateExpression=(
                    "SET sponsored_by = :b, deal_id = :d, ftc_disclosure = :f, updated_at = :u"
                ),
                ExpressionAttributeValues={
                    ":b": brand_name,
                    ":d": deal_id,
                    ":f": disclosure,
                    ":u": ts,
                },
            )
        except Exception:
            _logger.warning(
                "ftc_label: failed to label post content_id=%s deal_id=%s",
                content_id, deal_id, exc_info=True,
            )

    elif content_type == "video":
        try:
            T.video_metadata.update_item(
                Key={"video_id": content_id},
                UpdateExpression=(
                    "SET sponsored_by = :b, deal_id = :d, ftc_disclosure = :f, updated_at = :u"
                ),
                ExpressionAttributeValues={
                    ":b": brand_name,
                    ":d": deal_id,
                    ":f": disclosure,
                    ":u": ts,
                },
            )
        except Exception:
            _logger.warning(
                "ftc_label: failed to label video content_id=%s deal_id=%s",
                content_id, deal_id, exc_info=True,
            )

    elif content_type == "broadcast":
        try:
            T.broadcast_sessions.update_item(
                Key={"session_id": content_id},
                UpdateExpression=(
                    "SET sponsored_by = :b, deal_id = :d, ftc_disclosure = :f, updated_at = :u"
                ),
                ExpressionAttributeValues={
                    ":b": brand_name,
                    ":d": deal_id,
                    ":f": disclosure,
                    ":u": ts,
                },
            )
        except Exception:
            _logger.warning(
                "ftc_label: failed to label broadcast content_id=%s deal_id=%s",
                content_id, deal_id, exc_info=True,
            )

    else:
        _logger.error(
            "ftc_label: unknown content_type=%s for deal_id=%s — no FTC label applied",
            content_type, deal_id,
        )
```

Key design decisions in this implementation:

1. **`T.video_metadata` and `T.broadcast_sessions` are used directly** — both are
   already imported via `from app.core.tables import T` at line 22, which is already
   present in `sponsorship_deals.py`. No new imports required.

2. **`updated_at` stored as string** — the existing post path uses `str(now_ts())`.
   This is kept consistent across all three branches rather than using `Decimal` to
   avoid introducing an inconsistency in the video/broadcast tables.

3. **`except Exception: pass` replaced by `except Exception: _logger.warning(...)`** —
   the best-effort behavior is preserved (the function does not raise), but failures are
   now surfaced in the application log. This is a minimal improvement over the silent
   pass that existed in the original post path.

4. **`else` branch logs an error** — if a new content type is added to the system and
   `_add_ftc_label` is not updated, the omission is now observable in logs.

#### 4.2 Frontend rendering of FTC disclosure for video and broadcast

The fix writes `ftc_disclosure` to the DDB record. The frontend must read and display
it. This is outside the scope of the backend service fix but is a required companion
task:

- **Video player page**: Read `ftc_disclosure` from the video metadata API response and
  display a "Paid partnership with X" banner below the video title.
- **Broadcast viewer**: Read from the broadcast session response; display a persistent
  "Sponsored" badge.
- **API model update**: `app/models_video.py` `VideoMetadataModel` and any broadcast
  session Pydantic model should add `ftc_disclosure: Optional[str] = None` fields so
  the values are included in API responses.

These frontend changes are a follow-on task; the backend labeling is the critical
compliance fix.

### Dev/Prod parity (SECOPS-007)

- `T.video_metadata` maps to `VideoMetadata` in DynamoDB Local (dev) and AWS DynamoDB
  (prod) via the settings-driven table name (`S.video_metadata_table_name`).
- `T.broadcast_sessions` maps to `BroadcastSessions` similarly.
- Both tables exist in the local dev stack (verified via `scripts/local-ddb-init.py`).
- No mock-specific code paths needed. The `try/except` best-effort wrapper handles
  missing tables in test environments gracefully.

### Backward compatibility

- `ftc_disclosure`, `sponsored_by`, `deal_id` are new attributes on existing DynamoDB
  items. DynamoDB is schemaless; adding attributes to existing items is backward-compatible.
- Items written before this fix have no `ftc_disclosure` attribute; the frontend must
  handle `null` / missing gracefully.
- Existing deals that completed before the fix cannot be retroactively labeled without
  a migration script (see section 5).

### Retroactive migration (post-deploy)

For deals completed before this fix where `content_type` was `"video"` or `"broadcast"`:

```python
# scripts/migrate_ftc_labels.py (one-time, safe to re-run)
import boto3
from app.core.tables import T
from app.services.sponsorship_deals import get_deal, _add_ftc_label, DEAL_STATUSES

def migrate():
    # Scan all deals in 'completed' status via GSI3
    last = None
    migrated = 0
    while True:
        kwargs = {
            "IndexName": "GSI3",
            "KeyConditionExpression": ...,
            "FilterExpression": "deal_status = :c",
            "ExpressionAttributeValues": {":c": "completed"},
        }
        if last:
            kwargs["ExclusiveStartKey"] = last
        resp = T.sponsorship_deals.query(**kwargs)
        for item in resp.get("Items", []):
            if item.get("content_type") in ("video", "broadcast"):
                _add_ftc_label(
                    item["content_type"],
                    item["content_id"],
                    brand_name=item.get("advertiser_sub", "Unknown Brand"),
                    deal_id=item["deal_id"],
                )
                migrated += 1
        last = resp.get("LastEvaluatedKey")
        if not last:
            break
    print(f"Migrated FTC labels for {migrated} completed deals.")
```

### Rollout

1. Deploy the backend `_add_ftc_label` fix.
2. Run the migration script against production to backfill missing labels.
3. Deploy the frontend disclosure display (video player, broadcast viewer) in the
   same or subsequent release.
4. Monitor warning logs for FTC labeling failures post-deploy.

**Effort**: S (small). ~40 lines of Python in one service function; model field
additions are trivial. Frontend work is a separate M-effort task.
**Risk**: Low. Best-effort pattern means no deals are blocked; failure is logged.
**Sequencing**: Deploy the backend fix as soon as possible (compliance blocker).
