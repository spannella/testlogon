# GAP-0215: `call_billing_timer.py` Reads Platform Fee from Env Var Instead of Billing Config — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: FIN-018. No prior investigation doc.
> Claim verified against actual code.

## 1. Summary & Classification

**Severity**: HIGH
**Source ticket**: FIN-018 (Billing Configuration UI)
**Owning area**: `app/services/call_billing_timer.py`, `app/core/settings.py`
**Status**: Open — no fix applied

**Claim verification**: CONFIRMED with one clarifying correction. The as-built gap states that `call_billing_timer.py:183` reads the fee from `S.call_billing_platform_fee_percent` and that "billing_config `fee_call_bps` (if it exists in the config schema) is ignored." The code was verified: line 183 is `platform_fee_bps = S.call_billing_platform_fee_percent * 100` in `start_call_billing`, and line 297 in `process_heartbeat` contains the same fallback. The clarification: `fee_call_bps` does NOT exist in the billing_config allowlist (`_ALLOWLIST` in `billing_config.py`). The gap claim uses "if it exists" correctly — it does not exist. The fix therefore requires both adding a `fee_call_bps` key to the billing config allowlist AND replacing the env-var reads in `call_billing_timer.py`.

**Related tickets**: GAP-0214 (fee BPS settings not wired to live billing fee calculations) is the companion gap from FIN-018. GAP-0214 covers tip/unlock/subscription fee paths; GAP-0215 covers the per-minute call billing path. Together they mean the entire Billing Configuration UI has no effect on any transaction.

## 2. Current-State Investigation (root cause)

### Two independent sites read the env-var fee, not billing config

**Site 1 — `start_call_billing` (line 183)**

`app/services/call_billing_timer.py`, lines 182–206:

```python
platform_fee_bps = S.call_billing_platform_fee_percent * 100  # percent -> bps

table = _call_table()
table.update_item(
    Key={"call_id": call_id},
    UpdateExpression=(
        "SET billing_start_ts = :bst, "
        "last_billed_ts = :lbt, "
        "platform_fee_bps = :pfb, "
        ...
    ),
    ExpressionAttributeValues={
        ":bst": ts,
        ":lbt": ts,
        ":pfb": platform_fee_bps,
        ...
    },
)
```

At call start, the platform fee percentage is read from `S.call_billing_platform_fee_percent` (an env-var-backed integer, default 20, from `app/core/settings.py:1502`), multiplied by 100 to produce BPS, and written to the call session record. Any value set in the Billing Configuration UI for a `fee_call_bps` config key (which does not yet exist) would be ignored.

**Site 2 — `process_heartbeat` (line 297) and `finalize_call_billing` (line 413)**

Both functions contain the same fallback pattern:

```python
# process_heartbeat:297
platform_fee_bps = session.platform_fee_bps or (S.call_billing_platform_fee_percent * 100)

# finalize_call_billing:413
platform_fee_bps = session.platform_fee_bps or (S.call_billing_platform_fee_percent * 100)
```

The intent of `session.platform_fee_bps or (...)` is to use the value locked in at call-start time (correct behaviour — the fee rate should not change mid-call). However, the locked-in value itself was sourced from `S`, not from billing config. So even if an admin changes the call fee in the billing config UI, calls that started before the change will correctly use the old rate, but calls that start after the change will still use the env-var value — they never read billing config.

### `fee_call_bps` does not exist in the billing config allowlist

`app/services/billing_config.py`, lines 118–199 (`_ALLOWLIST`): the dict contains `fee_tips_bps`, `fee_unlocks_bps`, `fee_subscriptions_bps`, `fee_catalog_bps`, `fee_ad_revenue_bps`, `min_payout_cents`, etc. There is no `fee_call_bps` entry. An attempt to `PATCH /ui/admin/billing-config` with `{"fee_call_bps": 1500}` would return HTTP 400 `"unknown config key: fee_call_bps"` from `update_billing_config`.

### The settings value

`app/core/settings.py:1502`:

```python
call_billing_platform_fee_percent: int = int(
    os.environ.get("CALL_BILLING_PLATFORM_FEE_PERCENT", "20")
)
```

This is an integer percentage (0–100), not BPS (0–10000). The multiplication by 100 in `start_call_billing` converts percent to BPS. The new `fee_call_bps` config key should store BPS directly (0–10000) to be consistent with all other fee keys in the allowlist.

### Dev vs. prod

The env-var default is 20% in both environments. The call billing fee is therefore correct by accident in dev and incorrect by design in prod — an admin who changes the call fee via the UI in production expects the change to take effect within the cache TTL (60 seconds) but it never does. A backend restart is required to change the call fee in production, which requires engineering involvement and causes downtime.

## 3. Impact / Exploit / Blast Radius

### Operational impact

Per-minute call billing is the highest-ticket transaction type on most creator platforms. Call sessions can run for 60–120 minutes at rates of $1–$10 per minute. A misconfigured platform fee — or a promotional "zero fee" weekend for calls that an admin sets via the UI — has a significant P&L effect per session.

**Concrete example**: Default env-var fee is 20% (2000 BPS). Admin sets `fee_call_bps = 0` for a promotional campaign via the billing config UI. The change is stored in DDB, appears correctly when reading `GET /ui/admin/billing-config`, but `start_call_billing` still reads `S.call_billing_platform_fee_percent = 20` and locks in 2000 BPS. The promotion fails silently — creators lose 20% of all call revenue during the "zero fee" period. The admin has no indication the change did not take effect.

**Inverse scenario**: Admin increases call fee from 20% to 30% to recoup costs. Same silent failure — every new call session is still billed at the old 20% rate. Platform under-collects revenue.

### No security exploit

Fee manipulation via the billing config requires ROOT role. There is no unauthenticated path to alter the call fee. The gap is a configuration-correctness issue, not a privilege escalation vector.

### Blast radius

All paid call sessions initiated after the billing config is changed. Existing in-progress sessions are unaffected (they already have `platform_fee_bps` locked in their session records from `start_call_billing`).

## 4. Fix Design (code-level)

### Overview

1. Add `fee_call_bps` to the billing config `_ALLOWLIST` with the env-var default as its fallback.
2. In `start_call_billing`, replace `S.call_billing_platform_fee_percent * 100` with `get_fee_bps("call")`.
3. Add `"call"` to `_FEE_FIELD_BY_ENTRY_TYPE` in `billing_config.py`.
4. Keep the existing `session.platform_fee_bps or (...)` fallback in `process_heartbeat` and `finalize_call_billing` — but the fallback now calls billing config instead of the settings object.

### Step 1 — Add `fee_call_bps` to the billing config allowlist (`app/services/billing_config.py`)

In the `_ALLOWLIST` dict after `fee_ad_revenue_bps`, add:

```python
"fee_call_bps": {
    "kind": "int",
    "default": lambda: int(_env_default("call_billing_platform_fee_percent", 20)) * 100,
    "validate": lambda k, v: _validate_bps(k, v),
},
```

The default lambda converts the existing env-var `CALL_BILLING_PLATFORM_FEE_PERCENT` (percent integer) to BPS by multiplying by 100. This ensures a fresh deployment with no DB override uses the same fee as before the fix — no surprise fee change on deploy.

### Step 2 — Add `"call"` to `_FEE_FIELD_BY_ENTRY_TYPE` (`app/services/billing_config.py`)

```python
_FEE_FIELD_BY_ENTRY_TYPE = {
    "tip_debit": "fee_tips_bps",
    "tip_credit": "fee_tips_bps",
    "unlock_debit": "fee_unlocks_bps",
    "subscription_charge": "fee_subscriptions_bps",
    "subscription": "fee_subscriptions_bps",
    "catalog_purchase": "fee_catalog_bps",
    "ad_revenue": "fee_ad_revenue_bps",
    "call": "fee_call_bps",             # NEW
}
```

### Step 3 — Replace env-var read in `start_call_billing` (`app/services/call_billing_timer.py`)

```python
from app.services.billing_config import get_fee_bps   # add to imports

def start_call_billing(
    *,
    call_id: str,
    rate_cents_per_min: int,
    caller_id: str,
    callee_id: str,
) -> None:
    ...
    ts = now_ts()
    # BEFORE: platform_fee_bps = S.call_billing_platform_fee_percent * 100
    platform_fee_bps = get_fee_bps("call")   # reads DDB override or env default
    ...
```

### Step 4 — Update the fallback in `process_heartbeat` and `finalize_call_billing`

The `or (S.call_billing_platform_fee_percent * 100)` fallback in both functions is a defensive guard for cases where `session.platform_fee_bps` was never written (e.g., calls started before billing was wired up). Replace with the billing config accessor:

```python
# process_heartbeat:297 — replace:
platform_fee_bps = session.platform_fee_bps or get_fee_bps("call")

# finalize_call_billing:413 — same replacement
platform_fee_bps = session.platform_fee_bps or get_fee_bps("call")
```

This preserves the semantics: if the session already has a locked-in fee (set at call-start), use it. If not (legacy or missing), fall back to the current billing config value.

### Step 5 — Update `EDITABLE_KEYS` (automatic)

`EDITABLE_KEYS` is derived from `_ALLOWLIST.keys()` at line 201:

```python
EDITABLE_KEYS: Tuple[str, ...] = tuple(_ALLOWLIST.keys())
```

Adding `fee_call_bps` to `_ALLOWLIST` automatically adds it to `EDITABLE_KEYS`, and `BillingConfigOut` in models.py will include it if the model is updated to include the field. A companion frontend change is needed to surface this key in the billing config UI.

### Dev/Prod parity (SECOPS-007)

`get_fee_bps("call")` calls `get_billing_config()`, which reads from `T.billing_config` (DynamoDB). In dev mode, DynamoDB Local is used; in production, the real table is used. The in-memory cache with TTL is process-scoped and behaves identically in both environments. The env-var-backed default `_env_default("call_billing_platform_fee_percent", 20) * 100` ensures the default value is consistent with the existing env-var in both environments — no new env var is required.

**No mock-specific branching** is introduced. The change does not interact with `S.dev_mode` or any feature flag.

### Backward compatibility

**DDB schema**: No new table or index needed. `fee_call_bps` is stored as part of the existing `CURRENT` item in `billing_config` table.

**API**: `BillingConfigOut` and `BillingConfigPatch` in models.py must be updated to include `fee_call_bps`. If these are Pydantic models with an explicit field list (rather than `model_config = ConfigDict(extra="allow")`), add:

```python
fee_call_bps: Optional[int] = Field(default=None, ge=0, le=5000)
```

Existing API consumers that read billing config will see a new field — additive, not breaking.

**Running call sessions**: Sessions that started before this fix have `platform_fee_bps` already locked in their DDB record from the old `start_call_billing`. The `session.platform_fee_bps or ...` fallback preserves their rate. Only new sessions benefit from the fix.

### Alternatives considered

- **Use `S.call_billing_platform_fee_percent` as the billing config default**: This is effectively what the fix does (the default lambda reads `S.call_billing_platform_fee_percent`). The env var is retained as the default-of-last-resort; billing config overrides it.
- **Keep env var and add a separate runtime config**: Would require two sources of truth — explicitly rejected by FIN-018 design, which aims to consolidate all billing parameters into DDB.
- **Change `CALL_BILLING_PLATFORM_FEE_PERCENT` to BPS**: Would be a breaking change to all existing `.env.local` files and deployment configs. The conversion in the default lambda is safer.

```python

from unittest.mock import patch, MagicMock

def test_start_call_billing_uses_billing_config(mock_call_sessions_table, mock_billing_config):
```

### Manual QA steps

1. Start dev stack (`just up`).
2. `GET /ui/admin/billing-config` — confirm `fee_call_bps` is present in the response (default 2000).
3. `PATCH /ui/admin/billing-config` with `{"fee_call_bps": 1000}`. Confirm 200 with `fee_call_bps: 1000`.
4. Initiate a paid call via `POST /messaging/calls/initiate` (seed caller wallet and creator rate first).
5. Read the call session record directly from DDB: `T.message_call_sessions.get_item(...)`. Confirm `platform_fee_bps = 1000` (not 2000).
6. Process one billing heartbeat. Check the creator credit ledger entry — confirm `amount_cents = rate - (rate * 10%)`.
7. Reset `fee_call_bps` to 2000, start a new call, confirm the updated rate is used.

### Rollout

1. Add `fee_call_bps` to `_ALLOWLIST` and `_FEE_FIELD_BY_ENTRY_TYPE` in `billing_config.py`.
2. Update `BillingConfigOut` and `BillingConfigPatch` models in `app/models.py`.
3. Replace both `S.call_billing_platform_fee_percent * 100` occurrences in `call_billing_timer.py` with `get_fee_bps("call")`.
4. No DDB schema change needed.
5. After deploy: `GET /ui/admin/billing-config` should show `fee_call_bps: 2000` (matching the existing env-var default). No observable behaviour change for calls started after deploy unless an admin has previously changed the config.

**Effort**: S (1–2 days, including model and frontend label update).
**Rollback**: Revert the three changes. `start_call_billing` returns to reading `S.call_billing_platform_fee_percent`. The `fee_call_bps` key remains in DDB but is ignored (harmless).
**Risk**: Low. The default value of `fee_call_bps` is explicitly set to match the existing env-var default, so the fee applied to new calls is unchanged on deploy unless an admin has already configured a different value. The `session.platform_fee_bps` lock-in mechanism ensures in-flight calls are unaffected.

### Sequencing relative to GAP-0214

GAP-0214 (tip/unlock fee wiring) and GAP-0215 (call fee wiring) are independent and can be deployed in either order. Recommend deploying GAP-0215 first because its scope is smaller (two files, two sites), the S/M effort is lower, and it serves as a confidence-building deployment for the larger GAP-0214 change. Both should be preceded by Finance confirming the intended BPS values and using the billing config UI to set them to their desired values before the code changes go live.
