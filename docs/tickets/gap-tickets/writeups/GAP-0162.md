# GAP-0162: Achievement progress hooks never wired into action handlers — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code before writing; all citations are live file:line references.

## 1. Summary & Classification

**Bug statement**: The achievement and gamification system (ENGAGE-001) ships `advance_progress` and `update_streak` service functions, but not a single action handler anywhere in the codebase calls them. Post creation, tipping, reactions, comments, follows, subscriptions, unlocks, encrypted messages, calendar shares, and broadcast starts all complete without ever touching achievement progress. Achievements can only ever be unlocked via the admin endpoint (`POST /ui/achievements/admin/advance`), which itself has a separate authorization bug (GAP-0161).

**Severity**: HIGH  
**Source ticket**: ENGAGE-001  
**Status**: Open  
**Owning area**: Backend — multiple routers (`app/routers/newsfeed.py`, `app/routers/messaging.py`, `app/routers/social.py`, `app/routers/broadcast.py`, `app/routers/subscription_server.py`)  
**Effort**: L (integration work across many routers)

**Verdict**: Claim **confirmed**. A codebase-wide search for `advance_progress` and `update_streak` returns only their definitions in `app/services/achievement_progress.py` and the single call site in `app/routers/achievements.py:282`. No router, service, or background task outside of the achievements module calls these functions.

**Impact in one line**: The entire ENGAGE-001 auto-unlock feature is dead on arrival — every metric tracked by the system stays at 0 forever unless an operator manually advances it, making the gamification layer cosmetic decoration with no connection to actual user behavior.

**Related tickets**: GAP-0161 (admin endpoint privilege escalation — the only current unlock path is also insecure), ENGAGE-001 (parent).

### Feature flag default

`app/core/settings.py:1903`:
```python
achievements_enabled: bool = os.environ.get("ACHIEVEMENTS_ENABLED", "0") not in ("0", "false", "False")
```

The flag defaults to `False`. Both `advance_progress` and `update_streak` short-circuit to a no-op when the flag is off (checked at the top of each function in `app/services/achievement_progress.py:36` and `:98`). However, the hooks still need to be present in the calling code so that enabling the flag in production immediately activates the feature without a re-deploy.

### Why the hooks are absent

The ENGAGE-001 implementation delivered the achievement service, DynamoDB tables, and API endpoints but did not complete the second phase: wiring calls from existing action handlers into the achievement pipeline. This is a classic integration gap where the feature itself works in isolation but is never connected to the event stream.

### Dev vs prod

The gap manifests identically in both environments. Since `ACHIEVEMENTS_ENABLED` defaults to `0`, the missing hooks produce no runtime error — they simply do not fire. The bug becomes observable the moment an operator sets `ACHIEVEMENTS_ENABLED=1` in any environment and notices that user progress never changes.

## 3. Impact / Exploit / Blast Radius

This is a **functional completeness** gap rather than a security vulnerability, but its severity is HIGH because:

1. **Entire feature is non-functional**: No user will ever earn an achievement through normal use. The UI (badges, leaderboard, progress bars) will show zeros indefinitely.
2. **Only escape hatch is insecure**: The one path that does work (`POST /ui/achievements/admin/advance`) lacks correct authorization (GAP-0161), making the combination particularly hazardous.
3. **Silent failure at feature flag enable**: An operator who enables `ACHIEVEMENTS_ENABLED=1` in production expecting the feature to work will get no error, no log warning — just permanently empty achievement state. Users will experience the broken feature before engineering is alerted.
4. **Data integrity**: If achievements are eventually wired after real user events have already occurred (post_count already 50, etc.), those historical actions will never be credited. There is no backfill mechanism.

**Blast radius**: All users on any deployment where `ACHIEVEMENTS_ENABLED=1` is set. No data corruption, no financial impact, no security risk — purely a feature availability and user-experience failure.

## 4. Fix Design (code-level)

### Design principle

Each hook must be:
- Wrapped in `try/except Exception` so that an achievement failure never bubbles up to the user-facing response.
- Called **after** the primary action succeeds (commit-then-hook pattern).
- Conditioned on the feature flag via `advance_progress` / `update_streak` themselves (they already short-circuit when `achievements_enabled=False`), so no additional flag check is needed at the call site.

### Hook template

```python
# After primary action succeeds, add:
try:
    from app.services.achievement_progress import advance_progress
    advance_progress(user_id, "post_count")
except Exception:
    logger.debug("achievement hook failed: post_count", exc_info=True)
```

For streaks (posting_streak), use `update_streak` instead of `advance_progress`.

### Per-integration-point changes

**1. Post creation — `app/routers/newsfeed.py` inside `create_post` (around line 3630)**

Insert after the fan-out / post-count increment block:
```python
if not is_scheduled:
    # ... existing fan-out code ...
    try:
        from app.services.achievement_progress import advance_progress, update_streak
        advance_progress(user_id, "post_count")
        update_streak(user_id, "posting_streak")
    except Exception:
        logger.debug("achievement hook: post_count/posting_streak", exc_info=True)
```

### Dev/Prod parity (SECOPS-007)

All hooks use the same `advance_progress` / `update_streak` service calls in both dev and prod. The feature flag `ACHIEVEMENTS_ENABLED` determines behaviour; no mock-specific path is needed. DynamoDB calls in dev go to DynamoDB Local at port 8001 and in prod to AWS DynamoDB — the code path is identical.

### Backward compatibility / migration

No DynamoDB migration is required for the hooks themselves. Because `current_value` uses `if_not_exists(current_value, :zero)`, the first call after deployment correctly initialises the counter. Historical events before the deploy will not be credited — a backfill script can be written separately if needed, using existing DDB records (post_count on the profile table, reaction maps on posts, etc.) as source data.

### Feature flag rollout

1. Deploy the code changes with `ACHIEVEMENTS_ENABLED=0` — no behaviour change.
2. Seed achievement definitions via `POST /ui/achievements/admin/seed` (ROOT only).
3. Enable `ACHIEVEMENTS_ENABLED=1` in a staging environment and run through manual QA.
4. Enable in production; monitor achievement_unlocked alerts and leaderboard updates.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline, fails-before / passes-after)

Add to `tests/test_achievement_hooks.py`:

```python
"""Achievement progress hook integration tests.

These tests confirm that the action handlers call advance_progress.
They FAIL before the hooks are added and PASS after.
"""
import pytest
from unittest.mock import patch, call
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

def _root_headers() -> dict:
    return {"X-User-Sub": "root@test.local", "X-User-Role": "ROOT"}

def _user_headers(sub: str = "alice@test.local") -> dict:
    return {"X-User-Sub": sub}


@patch("app.services.achievement_progress.advance_progress")
def test_create_post_calls_advance_progress(mock_advance):
    """POST /posts must call advance_progress with post_count."""
    resp = client.post(
        "/posts",
        json={"body": "Hello world", "visibility": "public"},
        headers=_user_headers(),
    )
    # Accept any 2xx — we only care about the side-effect
    assert resp.status_code < 300
    metric_calls = [c.args[1] for c in mock_advance.call_args_list]
    assert "post_count" in metric_calls, (
        f"advance_progress was not called with post_count; got {metric_calls}"
    )


@patch("app.services.achievement_progress.advance_progress")
def test_add_reaction_calls_advance_progress(mock_advance, existing_post_id):
    """POST /posts/{id}/reactions must call advance_progress with reaction_count."""
    resp = client.post(
        f"/posts/{existing_post_id}/reactions",
        json={"emoji": "👍"},
        headers=_user_headers("bob@test.local"),
    )
    assert resp.status_code < 300
    metric_calls = [c.args[1] for c in mock_advance.call_args_list]
    assert "reaction_count" in metric_calls, (
        f"advance_progress not called with reaction_count; got {metric_calls}"
    )
```

Before the hooks are added, `mock_advance` is never called → the `assert "post_count" in metric_calls` line fails. After the hooks are added, it passes.

### Manual QA steps

1. Set `ACHIEVEMENTS_ENABLED=1` in `.env.local` and restart backend.
2. Seed definitions: `POST /ui/achievements/admin/seed` with root credentials.
3. Create a post as Alice → `GET /ui/achievements/progress` should show `post_count >= 1`.
4. Add a reaction as Bob → `reaction_count >= 1`.
5. Send a tip → `tip_count >= 1`.
6. Confirm that after threshold is crossed, `GET /ui/achievements` includes the newly unlocked badge.
7. Check SSE stream — an `achievement_unlocked` event should appear within 1 second.

### Observability

- Log `INFO achievement_hook: user={sub} metric={key} new_value={n}` on successful advance (inside `advance_progress`, which already logs at `INFO` on unlock).
- Emit a counter metric `achievements.progress_advanced{metric_key}` to Prometheus for trend analysis.
