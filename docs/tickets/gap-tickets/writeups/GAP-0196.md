# GAP-0196: Admin Queue Tab Absent from PayoutDashboard — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code; claim confirmed.

## 1. Summary & Classification

**Plain-English statement**: The admin payout queue endpoints (`GET/POST /v1/admin/payouts/...`) are fully implemented and registered in the backend, but the single `PayoutDashboard.tsx` page that all users land on contains no role-aware branching and no "Admin Queue" tab. Administrators must process payout requests — approve, reject, complete — by issuing raw API calls (curl or Swagger UI) rather than through the UI. This makes the day-to-day operational workflow impractical.

- **Severity**: HIGH
- **Source ticket**: FIN-009
- **Status**: Open — backend complete, frontend absent
- **Owning area**: Payments / Payouts UI
- **Verdict**: Confirmed. The backend router at `app/routers/admin_payouts.py` exists and is registered in `app/main.py:621`. The frontend file `frontend/src/pages/payouts/PayoutDashboard.tsx` has 623 lines with no import of `useAuthStore`, no `Tabs`/`TabsList` primitives, and no calls to any admin endpoint.
- **Impact**: Every payout approval or rejection today requires direct API access. Because admins cannot easily see the payout queue, payouts can sit in `requested` status indefinitely, leading to creator dissatisfaction and potential SLA breaches.
- **Related tickets**: FIN-009 (parent), SECOPS-007 (dev/prod parity)

## 2. Current-State Investigation (root cause)

### Backend — fully implemented

`app/routers/admin_payouts.py` defines five endpoints, all guarded by `require_admin_or_root` from `app/auth/policy.py`:

```
GET  /v1/admin/payouts          — list queue, filter by status
GET  /v1/admin/payouts/stats    — pending/approved counts + totals
POST /v1/admin/payouts/{id}/approve
POST /v1/admin/payouts/{id}/reject   (accepts reason in body or query param)
POST /v1/admin/payouts/{id}/complete — mark paid
POST /v1/admin/payouts/{id}/mark-paid — alias for /complete
```

The router is registered at `app/main.py:621`:
```python
app.include_router(admin_payouts_router)
```

The prefix is `/v1/admin/payouts` (line 34 of `admin_payouts.py`). Note this uses the `/v1/` prefix, not `/ui/`, which means it goes through Cognito Bearer-token auth rather than the cookie-session path. This is intentional — admin tooling typically runs in an authenticated headless context — but the frontend needs to use Bearer-token requests when calling these endpoints.

Backend models used (`app/models.py`):
- `PayoutListOut` / `PayoutOut` — lines ~2490–2512
- `PayoutStatsOut` — line 2513
- `PayoutRejectIn` — line 2520
- `PayoutMarkPaidIn` — line 2524
- `PayoutActionOut`

### Frontend — gap

`frontend/src/pages/payouts/PayoutDashboard.tsx` imports only the six user-facing wrappers from `api/endpoints/payouts.ts`:

```ts
import {
  getPayoutBalance, requestPayout, cancelPayout,
  listPayouts, getEarningsSummary, getEarningsTransactions,
} from "@/api/endpoints/payouts";
```

There is no import of `useAuthStore` (the Zustand store that exposes `role`), no `Tabs` primitive, and no reference to any `/v1/admin/payouts` path. The page renders a flat layout: balance cards, request form, earnings breakdown, payout history, transactions. An administrator who visits `/payouts` sees the identical page as a regular creator.

The API wrapper file `frontend/src/api/endpoints/payouts.ts` likewise contains no admin functions (confirmed: the 57-line file ends with `getEarningsTransactions`). There are also no TypeScript types for `PayoutStats`, `PayoutQueueItem`, or `AdminPayoutAction` in `frontend/src/api/types.ts`.

### Why it breaks at runtime

When an admin navigates to `/payouts` they land on a creator-centric view. They can see their own balance (which is likely zero) and submit a payout request (which they don't need). The backend queue endpoints respond correctly when called directly, but there is simply no UI path to reach them.

## 3. Impact / Exploit / Blast Radius

This is an **operational gap**, not an exploit surface. The risk profile is:

1. **Revenue / SLA risk**: Payout requests accumulate in `requested` status with no admin-visible queue. Creators waiting for approval receive no feedback and may churn.
2. **Audit gap**: Approvals and rejections with reasons are designed to be auditable, but if admins use raw API calls there is no standardised reason capture, increasing the chance of incomplete rejection explanations.
3. **Error amplification**: A single mis-targeted `POST /v1/admin/payouts/{wrong_id}/approve` in a terminal session is permanent. A UI with a confirmation dialog (as specified in FIN-009) prevents accidental mass-approval.
4. **Blast radius**: Limited to administrative operations. Regular creator workflows are unaffected. No data corruption risk from the gap itself.

There is no privilege-escalation angle; the backend correctly enforces `require_admin_or_root` on every queue endpoint.

## 4. Fix Design (code-level)

### 4a. Frontend API wrappers (`frontend/src/api/endpoints/payouts.ts`)

Add five new exported functions using the authenticated `api` client. Because `/v1/admin/payouts` requires a Bearer token, and the `api` client (axios instance in `api/client.ts`) sends the `ui_access_token` cookie as a Bearer token for same-origin requests, no extra configuration is needed:

```ts
export interface AdminPayoutQueueItem extends Payout {
  user_sub: string;
  user_email?: string;
}
export interface AdminPayoutListResp {
  items: AdminPayoutQueueItem[];
  next_cursor?: string;
}
export interface PayoutStats {
  pending_count: number;
  approved_count: number;
  total_pending_cents: number;
  total_approved_cents: number;
}
export interface AdminPayoutActionResp { ok: boolean; payout_id: string; status: string; }

export const adminListPayouts = (params?: { status?: string; limit?: number; cursor?: string }) => {
  const p: Record<string, string> = {};
  if (params?.status) p.status = params.status;
  if (params?.limit) p.limit = String(params.limit);
  if (params?.cursor) p.cursor = params.cursor;
  return api.get<AdminPayoutListResp>("/v1/admin/payouts", p);
};
export const adminGetPayoutStats = () =>
  api.get<PayoutStats>("/v1/admin/payouts/stats");
export const adminApprovePayout = (payoutId: string) =>
  api.post<AdminPayoutActionResp>(`/v1/admin/payouts/${payoutId}/approve`);
export const adminRejectPayout = (payoutId: string, reason: string) =>
  api.post<AdminPayoutActionResp>(`/v1/admin/payouts/${payoutId}/reject`, { reason });
export const adminCompletePayout = (payoutId: string) =>
  api.post<AdminPayoutActionResp>(`/v1/admin/payouts/${payoutId}/complete`);
```

### 4b. PayoutDashboard — role-aware tabs

Wrap the existing page content in a `Tabs` component. The `useAuthStore` hook already exposes `user.role`. Gate the "Admin Queue" tab on `role === "ADMIN" || role === "ROOT"`:

```tsx
import { Tabs, TabsContent, TabsList, TabsTrigger } from "@/components/ui/tabs";
import { useAuthStore } from "@/stores/authStore";
import { adminListPayouts, adminGetPayoutStats, adminApprovePayout,
         adminRejectPayout, adminCompletePayout } from "@/api/endpoints/payouts";

export default function PayoutDashboard() {
  const { user } = useAuthStore();
  const isAdmin = user?.role === "ADMIN" || user?.role === "ROOT";
  // ... existing state ...

  return (
    <div className="mx-auto w-full max-w-6xl space-y-6 p-4 md:p-6">
      <div className="flex items-center gap-3">
        <Wallet className="h-7 w-7 text-primary" />
        <h1 className="text-2xl font-bold tracking-tight">Payouts</h1>
      </div>

      <Tabs defaultValue="my-payouts">
        <TabsList>
          <TabsTrigger value="my-payouts">My Payouts</TabsTrigger>
          {isAdmin && <TabsTrigger value="admin-queue">Admin Queue</TabsTrigger>}
        </TabsList>

        <TabsContent value="my-payouts">
          {/* existing balance cards, request form, earnings, history */}
        </TabsContent>

        {isAdmin && (
          <TabsContent value="admin-queue">
            <AdminPayoutQueue />
          </TabsContent>
        )}
      </Tabs>
    </div>
  );
}
```

The `AdminPayoutQueue` sub-component would:
- Call `adminGetPayoutStats()` for a stats summary card (pending count, total amount)
- Call `adminListPayouts({ status: statusFilter })` with a `<Select>` to switch between `requested`, `approved`, `all`
- Render a table with columns: Date, Creator (user_sub), Amount, Method, Status, and an Actions column with Approve/Reject/Complete buttons
- Include a `RejectReasonDialog` state-driven dialog that collects a mandatory reason string before confirming rejection (matching the FIN-009 spec requirement)
- Invalidate `["admin", "payouts"]` query keys on mutation success

### 4c. Dev/Prod parity (SECOPS-007)

The backend uses the `/v1/` prefix (Bearer token auth path). In dev mode the Vite proxy configuration (`frontend/vite.config.ts`) already proxies all paths to `localhost:8000`, so the admin endpoints are reachable in development without any changes. In production the same proxy rule applies via the Nginx/load-balancer layer. No feature flag or environment-specific code path is needed.

The `require_admin_or_root` dependency on the backend resolves the role from the same JWT that the frontend `useAuthStore` reads, so both checks are consistent.

### 4d. Alternatives considered

- **Separate admin page** (`/admin/payouts`): cleaner separation, but the existing `/payouts` route is already in `App.tsx` and admins should also be able to see their own creator payouts. A tabbed single-route design keeps the surface minimal.
- **Backend route change to `/ui/admin/payouts`**: would allow cookie-session auth instead of Bearer. Rejected because the existing `/v1/admin/payouts` router is already tested and registered; changing its prefix would require a migration.

### Metrics / observability

Add a `payout_admin_action_total{action="approve|reject|complete"}` counter to `app/metrics.py` inside each admin endpoint. Alert if `approved + completed < requested * 0.8` over a 24-hour window (queue backup indicator).

The existing `PayoutStatsOut` model already captures `pending_count` and `total_pending_cents` (line 2513 of `app/models.py`). Wire these into a CloudWatch or Prometheus dashboard metric so that on-call responders can see queue depth without logging in to the admin UI. Additionally, the Stats card in the `AdminPayoutQueue` sub-component should auto-refresh every 30 seconds (`refetchInterval: 30_000`) to reflect any approvals made by another admin in a concurrent session.

### Error handling and edge cases

- **Concurrent approvals**: Two admins approving the same payout simultaneously. The `approve_payout` service function should use a DynamoDB conditional write (`ConditionExpression: attribute_exists(payout_id) AND #status = :requested`) to prevent double-approval. If the condition fails, return a user-friendly error "This payout was already actioned."
- **Missing reject reason**: The `PayoutRejectIn` model (line 2520 of `app/models.py`) accepts an empty reason string. The frontend dialog should enforce a minimum 10-character reason before enabling the Submit button. The backend should mirror this with `min_length=10` on the `reason` field to prevent API-level bypass.
- **Load-more pagination**: The queue table should honour the `next_cursor` field from `PayoutListOut`. The existing creator payout table already has a "Load more" button stub at line 517 of `PayoutDashboard.tsx` that is non-functional; the admin queue should implement this properly using `useInfiniteQuery`.

### Rollout

**Effort**: M (2–3 days). Backend is complete. Frontend work is the only deliverable.
**Sequencing**: No migration required. The tab is invisible to non-admins, so it can be deployed to production immediately with no user-facing change for creators.
**Rollback**: Remove the `{isAdmin && ...}` blocks; backend endpoints remain unaffected.
**Risk**: Low — additive UI change only. The backend's existing `require_admin_or_root` gate prevents any privilege escalation if the frontend role-check were bypassed.
