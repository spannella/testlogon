# GAP-0006: Legacy record_ad_impression() Has No Fraud Check — Remediation Write-up

> ~5 pages. Fix-oriented. Grounded in the investigation doc
> (docs/tickets/gap-tickets/investigations/GAP-0006.md) and real code at
> app/services/ad_placement.py:233.

---

## 1. Summary & Classification

**Bug statement.** The `record_ad_impression()` function in
`app/services/ad_placement.py` writes ad impression/completion/skip events and
credits creator revenue on every `event_type="complete"` call — with no
call to the fraud-detection service before doing so. Any authenticated user
can replay unlimited POST requests to drive unbounded ledger credits to their
own account.

| Field | Value |
|-------|-------|
| Severity | **CRITICAL** |
| Source ticket | ADS-014 |
| Status | Open |
| Owning area | Ads / Monetisation |
| Investigation verdict | **Confirmed** |

**One-line impact.** Authenticated users can self-generate unlimited ad-revenue
credits by replaying `POST /ui/videos/{id}/ad-impression` with
`event_type=complete`, bypassing the fraud gate that exists on every other
ad-serving path.

**Related tickets.** ADS-004 (ad serving engine), ADS-020 (broadcast ads),
GAP-0007 (broadcast stub), SEC-014 (rate-limiting), GAP-0082 (injection via
ticket context — separate but same "no gate" pattern).

## 2. Current-State Investigation (root cause)

### Code path

The router endpoint lives at `app/routers/video_listing.py:1470`:

```python
@router.post("/{video_id}/ad-impression", response_model=AdImpressionOut)
def record_ad_impression_endpoint(
    video_id: str,
    body: AdImpressionIn,
    user=Depends(require_ui_session),
):
    from app.services.ad_placement import record_ad_impression
    result = record_ad_impression(
        video_id=video_id,
        user_id=user_sub,
        slot_type=body.slot_type,
        slot_index=body.slot_index,
        creative_id=body.creative_id,
        event_type=body.event_type,
    )
```

The caller passes six arguments. None of them include `ip_address`,
`user_agent`, or `view_time_ms` — the three signals required by the fraud
checker — because `record_ad_impression()` does not accept them.

### Service function signature (`app/services/ad_placement.py:233–241`)

```python
def record_ad_impression(
    *,
    video_id: str,
    user_id: str,
    slot_type: str,
    slot_index: int,
    creative_id: str = "",
    event_type: str = "impression",  # "impression" | "complete" | "skip"
) -> Dict[str, Any]:
```

No `ip_address`, `user_agent`, or `view_time_ms` parameter. The function
proceeds directly to write to `T.ad_impressions` and, if
`event_type == "complete"`, calls `_credit_ad_revenue()` at line 285:

```python
    # On complete: credit creator with ad revenue
    if event_type == "complete":
        _credit_ad_revenue(video_id=video_id, event_id=event_id, ts=ts)
```

There is no fraud gate between the function entry and this call.

### The fraud gate that does exist — but on a different path

`app/services/ad_serving.py:186` (the server-side `record_ad_event()` function
called during VOD ad serving) contains the proper guard:

```python
if getattr(S, "ad_fraud_detection_enabled", True):
    try:
        from app.services import ad_fraud_prevention as fraud
        result = fraud.check_fraud(
            user_id=user_id,
            ip_address=ip_address,
            user_agent=user_agent,
            ...
        )
        if result.flagged:
            fraud.record_fraud_event(...)
            return {"ok": False, "blocked": True, ...}
```

`check_fraud()` exists and is fully implemented at
`app/services/ad_fraud_prevention.py:115`. It runs six independent fraud rules
(click-velocity, IP clustering, geo-mismatch, bot-agent detection,
view-time anomaly, frequency-cap). That entire stack is simply never called for
player-reported impression events.

### Why the gap exists

`record_ad_impression()` was written as a lightweight tracking helper for
CREATOR-003/ADS-014's first pass, before `ad_fraud_prevention.py` existed. The
fraud service was retrofitted only into `ad_serving.py` (the internal
server-side path). The player-facing endpoint was never updated to match.

### `AdImpressionIn` model also lacks fraud signals (`app/models.py`)

The request body model accepted by the endpoint has no `view_time_ms` field,
meaning the player cannot forward the actual view duration to the backend for
bot detection. The fraud checker's `view_time_ms` rule (short view times indicate
bots) cannot fire because the signal is simply absent from the request contract.
Adding `view_time_ms: int = Field(default=0, ge=0)` to `AdImpressionIn` is a
prerequisite for the fix.

### How `_credit_ad_revenue()` accumulates ledger entries

`_credit_ad_revenue()` (line 290) reads the video's CPM rate, computes
`max(1, cpm // 1000)` cents, writes a `LEDGER#CREDIT` entry to
`T.billing`, and increments `ad_revenue_cents` on the video metadata record.
Each call is unconditional — there is no existence check, no per-event
idempotency key, and no daily spend cap. An attacker firing 10,000 requests
produces 10,000 ledger entries and a matching 10,000-increment on the
video's `ad_revenue_cents` counter.

### Dev vs prod

Both paths are active in dev mode (`S.vod_ads_enabled = True` by default in
`.env.local.example`). The exploit is reproducible locally. In production the
incentive is higher (real CPM rates, real ledger credits that accumulate toward
payout thresholds).

## 3. Impact / Exploit / Blast Radius

### Exploit walkthrough

1. Attacker authenticates as any `role=USER` account (no elevated privilege
   needed — `require_ui_session` at `video_listing.py:1474`).
2. Attacker uploads or identifies a video they own (`video_id = "vid_abc"`).
3. Attacker sends repeated requests:
   ```
   POST /ui/videos/vid_abc/ad-impression
   {"slot_type":"preroll","slot_index":0,"creative_id":"","event_type":"complete"}
   ```
4. Each call to `_credit_ad_revenue()` credits `max(1, cpm // 1000)` cents.
   At `DEFAULT_CPM_CENTS = 500` that is `max(1, 0) = 1 cent` per call. At a
   higher configured CPM (e.g., 5000 cents = $50 CPM) that rises to 5 cents
   per call.
5. At 1,000 requests/second (trivially achievable with `curl --parallel`) the
   attacker earns $0.36/hour at default CPM or $180/hour at a $50 CPM.
6. There is no rate limit on the endpoint (see GAP-0056). The credits accumulate
   in the billing ledger and can be withdrawn.

### Additionally

- Any `video_id` is accepted — the endpoint does not verify that the caller
  owns the video before recording the impression (though the revenue credit goes
  to the video owner, not the caller, so the primary risk is against the
  platform's ad budget rather than other users' accounts).
- Because `event_type` is also caller-supplied and not validated against
  the impression lifecycle, any combination can be fired in any order.
- No audit trail distinguishes fraudulent completions from legitimate ones in
  `T.ad_impressions` because the fraud-event table (`T.ad_fraud_events`) is
  never written to by this path.

### Financial worst case

With a platform advertiser budget of $10,000/month and a bot script firing
completions at 50 req/s, the budget is exhausted in roughly 5 hours (at $5
CPM). The platform absorbs the cost without any real ad view occurring.

## 4. Fix Design (code-level)

### Step 1 — Extend the service function signature

In `app/services/ad_placement.py:233`, add three optional keyword arguments:

```python
def record_ad_impression(
    *,
    video_id: str,
    user_id: str,
    slot_type: str,
    slot_index: int,
    creative_id: str = "",
    event_type: str = "impression",
    # NEW: fraud-signal fields
    ip_address: str = "",
    user_agent: str = "",
    view_time_ms: int = 0,
) -> Dict[str, Any]:
```

### Step 2 — Insert the fraud gate before revenue credit

Immediately after the function's opening docstring and before writing to
`T.ad_impressions`, add (mirrors the pattern at `ad_serving.py:196–224`):

```python
    # ── Fraud detection (ADS-014) ───────────────────────────────────────
    if getattr(S, "ad_fraud_detection_enabled", True):
        try:
            from app.services import ad_fraud_prevention as fraud
            result = fraud.check_fraud(
                user_id=user_id,
                ip_address=ip_address,
                user_agent=user_agent,
                creative_id=creative_id,
                view_time_ms=view_time_ms,
                event_type=event_type,
            )
            if result.flagged:
                fraud.record_fraud_event(
                    user_id=user_id,
                    ip_address=ip_address,
                    creative_id=creative_id,
                    event_type=event_type,
                    score=result.score,
                    details=result.details,
                )
                return {"ok": False, "event_id": "", "blocked": True,
                        "reason": "fraud_detected"}
        except Exception:
            logger.warning(
                "ad_fraud_check_failed video=%s user=%s", video_id, user_id
            )
```

The `except Exception` ensures that a fraud-service outage does not block
legitimate impressions (fail-open), which matches the behaviour in
`ad_serving.py`. This is intentional — availability is preferred over a hard
block. A stricter policy (fail-closed) can be introduced behind a second
feature flag if desired.

### Step 3 — Forward signals from the router

In `app/routers/video_listing.py:1482–1490`, extend the call:

```python
    result = record_ad_impression(
        video_id=video_id,
        user_id=user_sub,
        slot_type=body.slot_type,
        slot_index=body.slot_index,
        creative_id=body.creative_id,
        event_type=body.event_type,
        # NEW
        ip_address=request.client.host if request.client else "",
        user_agent=request.headers.get("user-agent", ""),
        view_time_ms=body.view_time_ms,
    )
```

Add `view_time_ms: int = Field(default=0, ge=0)` to the `AdImpressionIn`
Pydantic model in `app/models.py` (the existing model already at line ~4175).
Add `request: Request` to the endpoint signature (FastAPI injects it
automatically).

### Step 4 — Extend `AdImpressionOut`

Return `blocked: bool = False` so the player can handle a blocked response
gracefully without treating it as an HTTP error.

### Dev/Prod parity (SECOPS-007)

`T.ad_impressions` and `T.ad_fraud_events` are DynamoDB tables present in both
DynamoDB Local (dev) and production. `check_fraud()` performs only DynamoDB
reads/writes — no external HTTP calls, no AWS-specific services. The feature
flag `S.ad_fraud_detection_enabled` defaults to `True`; setting it to `False`
in `.env.local` allows developers to skip fraud checks during load testing
without code changes.

### Alternatives considered

- **Rate-limit only (GAP-0056):** Insufficient — a distributed botnet generates
  fraud from many IPs, each below the per-IP rate limit. Rate limits also do
  not distinguish between a fast legitimate viewer (multiple impressions on
  a long video with multiple ad slots) and a bot flooding completions on a
  single slot.
- **Fail-closed on fraud-service error:** Higher protection — block the
  impression if `check_fraud()` raises — but risks blocking legitimate users
  during fraud-service degradation. Deferred to a follow-on feature flag
  (`S.ad_fraud_fail_closed`).
- **Move impression recording server-side (remove player endpoint):** Ideal
  long-term: server records the impression at serve time, not at player-report
  time. This eliminates the player-reported vector entirely and is the
  recommended architectural goal. Requires a larger refactor of the player SDK
  and the creative overlay flow. Not suitable as a fast fix for this ticket.
- **Add idempotency key to impressions:** An `event_id` passed by the player
  and used as a DDB condition could deduplicate replays at the storage layer
  even without fraud detection. This is a complementary, not alternative, fix.
  The fraud gate fires earlier (before any DDB write) and is therefore cheaper.
  Both should eventually exist.

### Manual QA steps

1. Start dev stack (`just up`).
2. Authenticate as Alice; obtain a `video_id` for a video Alice owns.
3. Fire `POST /ui/videos/{id}/ad-impression` with `event_type=complete` 10
   times; observe ledger credit equals 10 × 1 cent before fix.
4. Apply fix; repeat; observe all 10 calls return `{"ok": false,
   "blocked": true}` (because dev DDB velocity table has no prior impressions
   to exceed threshold — adjust `mock_fraud_blocked` to test actual flow,
   or set `AD_FRAUD_DETECTION_ENABLED=false` in `.env.local` to confirm
   passthrough).

### Metrics / observability

Add a `logger.info("ad_impression_blocked ...")` in the blocked branch.
Monitor `ad_impression_blocked_count` in dashboards. Alert if block rate
exceeds 5% of completions (indicates either a fraud wave or a misconfigured
fraud threshold).

### Rollback

Set `AD_FRAUD_DETECTION_ENABLED=0` in `.env.local` / production env to
disable the gate without deploying a revert.

### Risks

- **Fail-open behaviour:** If the fraud service is down, all impressions proceed
  unblocked. Acceptable given the existing behaviour is already fully unblocked.
- **Latency:** `check_fraud()` performs 3–4 DynamoDB reads. At p99 this adds
  ~15 ms to the impression endpoint. Acceptable for a fire-and-forget player
  event.

### Effort

**S** — Three optional parameters + guarded `check_fraud()` call + router
forwarding. Fraud service fully exists. Estimated: 2–3 hours development,
1 hour testing.

### E2E test (Playwright, optional supplement)

A lightweight Playwright test in `frontend/e2e/ads.spec.ts` can cover the
HTTP layer:

```ts
test("ad impression blocked by fraud returns non-200 or blocked=true", async ({ request }) => {
  // Requires: backend running, alice session seeded
  const resp = await request.post(`/ui/videos/${VIDEO_ID}/ad-impression`, {
    headers: { "x-csrf-token": sessions.alice.csrf_token },
    data: {
      slot_type: "preroll", slot_index: 0,
      creative_id: "", event_type: "complete",
      view_time_ms: 0,   // zero view time — triggers view_time rule
    },
  });
  // After fix: response body contains blocked=true or ok=false
  const body = await resp.json();
  expect(body.blocked ?? body.ok === false).toBeTruthy();
});
```

Note: because the fraud service uses DDB velocity counters that accumulate
across requests, the fraud gate fires reliably only after multiple rapid
requests in tests. A mock override (`S.ad_fraud_detection_enabled = True`
combined with a pre-seeded velocity record) is more reliable in isolation.

### Sequencing

1. This fix (GAP-0006) — adds fraud gate to `record_ad_impression()`.
2. GAP-0056 (per-API-key rate limiting) — layered defence at the HTTP layer.
3. Add idempotency key to `AdImpressionIn` and `record_ad_impression()` —
   complementary dedup at the storage layer.
4. ADS-014 follow-on — move impression recording fully server-side (removes
   the player-reported attack surface entirely).
