# GAP-0127: Self-Entry Check Executes After Fee Charge — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at
> `app/services/broadcast_lottery.py`. No prior investigation doc exists.

## 1. Summary & Classification

**Ticket claim**: "Broadcaster attempting to enter own lottery is charged the entry fee
before `BROADCASTER_CANNOT_ENTER` 403 is raised; fee write succeeds with no entry
record."

**Claim verdict: INCORRECT (claim is inaccurate — the bug does not exist in the current
code).** The self-entry guard at line 194 of `app/services/broadcast_lottery.py`
executes before the `_charge_entry_fee()` call at line 231. No fee is charged when the
broadcaster tries to enter their own lottery; the 403 is raised first.

The ticket was filed based on a prior as-built review of BCAST-014. The implementation
appears to have been corrected after that review, and the guard was moved to its proper
position. This write-up documents the current state, confirms the guard is correctly
placed, notes the residual risks in the surrounding code, and recommends a regression
test to prevent accidental regression.

- **Severity**: HIGH (as filed; downgraded to LOW/informational given current state)
- **Source ticket**: BCAST-014
- **Status**: Open (but code is already correct — ticket should be closed as "Fixed in
  implementation")
- **Owning area**: Broadcast / Lottery
- **Related tickets**: GAP-0128 (real atomicity gap in the same function), SECOPS-007.

## 2. Current-State Investigation (root cause)

### Claimed vs actual code path

The ticket claims the order is:

1. Charge entry fee (`_charge_entry_fee`)
2. Check `user_id == broadcaster_id` → raise 403

The **actual** order in `app/services/broadcast_lottery.py:166–238` (`enter_lottery`):

```
line 177  get_lottery_entry()          # idempotency check (existing entry)
line 182  _enforce_lottery_entry_rate_limit()
line 186  _enforce_chat_mute()
line 188  get_lottery_config()
line 194  if user_id == config["broadcaster_id"]:  # ← GUARD IS HERE
line 196      raise HTTPException(403, BROADCASTER_CANNOT_ENTER)
line 201  if config["status"] != "open": raise 409
line 209  max_entries check: raise 409
line 219  closes_at check: raise 409
line 228  entry_fee_cents = int(config.get("entry_fee_cents", 0) or 0)
line 231  fee_payment_id = _charge_entry_fee(...)  # ← FEE CHARGE IS HERE
```

The broadcaster guard fires at line 194, well before any fee is charged at line 231.
When `user_id == config["broadcaster_id"]`, `HTTPException(403)` is raised immediately
and the function never reaches `_charge_entry_fee`.

### Why the ticket may have been filed

The BCAST-014 as-built review likely observed an earlier version of `enter_lottery`
where the guard appeared after the fee call. The current implementation corrects this
ordering. There is no evidence of a compensating unit test that would have caught the
regression, which is itself a residual risk.

### Residual risk 1 — no test prevents order regression

Although the guard is currently in the right place, there is no unit test that asserts
the broadcaster receives a 403 **without** a billing write. If a future developer
refactors `enter_lottery` and accidentally moves the guard below the fee call, the bug
will silently reappear.

### Residual risk 2 — fee write itself is non-atomic (GAP-0128)

Even if the broadcaster guard were to regress, the underlying `_charge_entry_fee`
function contains its own billing atomicity gap (GAP-0128). The two issues are
independent but share the same function. The fix for GAP-0128 is tracked separately.

### Residual risk 3 — config fetch timing

Between `get_lottery_config()` (line 188) and `_charge_entry_fee()` (line 231) there
is no re-fetch of the config. If the broadcaster ID were somehow changed between these
two points (unlikely via normal API paths), the guard would use a stale value. This is
a theoretical TOCTOU issue, but it is not exploitable under the current single-table
DynamoDB model because broadcaster IDs are immutable once the lottery is created.

## 3. Impact / Exploit / Blast Radius

### Current state (code is correct)

A broadcaster calling `POST /broadcast/{session}/lottery/{id}/enter` receives HTTP 403
before any billing write is attempted. No financial impact exists from this specific
ordering issue today.

### If the guard were to regress

If a future change moved the `user_id == config["broadcaster_id"]` check below
`_charge_entry_fee`, the scenario would be:

1. Broadcaster calls `enter_lottery` on their own lottery.
2. `_charge_entry_fee` writes a debit ledger entry (broadcaster's wallet charged).
3. `_charge_entry_fee` writes a credit ledger entry (broadcaster's wallet credited — to
   themselves, net zero at the wallet level, but still two spurious ledger writes).
4. `if user_id == config["broadcaster_id"]` raises HTTP 403.
5. No `LENTRY#` item is written. The entry count is not incremented.
6. Ledger has a phantom debit+credit pair with no corresponding entry record.

In practice the net wallet impact would be zero (debit and credit are to the same user),
but the ledger would contain spurious entries that corrupt reconciliation reports and
audit logs.

### Who is affected

- **Broadcasters**: spurious wallet transactions; potential support tickets.
- **Finance team**: reconciliation reports show unmatched fee records with no entry.
- **Auditors**: LEDGER rows without a corresponding `LENTRY#` row.

### Blast radius (if regression occurs)

Limited to broadcasters who attempt to enter their own lottery — an unusual action
unlikely to occur frequently in production.

## 4. Fix Design (code-level)

### Primary recommendation — do nothing to product code

The guard is already correctly placed. No product code change is required.

### Add a regression-prevention guard test

To prevent the ordering from regressing, add a unit test that verifies:

```python
# tests/services/test_broadcast_lottery_self_entry.py

def test_broadcaster_cannot_enter_own_lottery_no_billing_side_effect(
    moto_billing_table, moto_broadcast_chat_messages_table
):
    """
    Broadcaster calling enter_lottery on their own lottery MUST:
    1. Receive HTTP 403.
    2. NOT have any billing ledger entry written.
    """
    from fastapi import HTTPException
    from app.services.broadcast_lottery import create_lottery, enter_lottery
    import pytest

    broadcaster_id = "broadcaster_abc"
    session_id = "sess_self_entry"

    # Seed a lottery
    config = create_lottery(
        session_id=session_id,
        broadcaster_id=broadcaster_id,
        display_name="Broadcaster",
        title="My Lottery",
        outcomes=[{"outcome_id": "o1", "payload_type": "text",
                   "display_label": "Win", "weight_bps": 10000}],
        entry_fee_cents=100,
    )
    lottery_id = config["lottery_id"]

    # Attempt self-entry
    with pytest.raises(HTTPException) as exc_info:
        enter_lottery(
            session_id=session_id,
            lottery_id=lottery_id,
            user_id=broadcaster_id,        # same as broadcaster_id
            display_name="Broadcaster",
            payment_method_id=None,
        )

    assert exc_info.value.status_code == 403
    assert exc_info.value.detail["code"] == "BROADCASTER_CANNOT_ENTER"

    # No billing row must have been written
    resp = moto_billing_table.query(
        KeyConditionExpression="pk = :pk",
        ExpressionAttributeValues={":pk": f"USER#{broadcaster_id}"},
    )
    assert resp["Count"] == 0, (
        "Broadcaster self-entry must not produce billing rows"
    )
```

**Fails before correct ordering** (if guard were moved below fee call): the broadcaster
is charged before raising 403; `Count` would be 2 (debit + credit).

**Passes with current ordering**: 403 is raised before any billing write; `Count == 0`.

### Dev/prod parity (SECOPS-007)

No code change is needed. The guard relies only on an in-memory comparison
(`user_id == config["broadcaster_id"]`) against data fetched from DynamoDB, which
behaves identically in dev (local DDB) and production (AWS DynamoDB).

### Alternatives considered

1. **Add a database constraint that prevents broadcaster entry**: Not feasible with
   DynamoDB's attribute-level condition expressions in this schema; the broadcaster ID
   is stored on the config item, not the entry item. A `ConditionExpression` on the
   `LENTRY#` write could check that `user_id != broadcaster_id`, but this would require
   fetching the broadcaster ID into the write call and complicates the DDB expression.
   The in-memory guard is simpler and runs earlier in the flow.

2. **Re-check broadcaster ID inside `_charge_entry_fee`**: Defence-in-depth, but
   changes the single-responsibility boundary of that function (it should only charge
   fees, not enforce lottery eligibility rules). Rejected in favour of the existing
   guard + regression test approach.

3. **API-level guard in the router before calling `enter_lottery`**: The router
   currently delegates all eligibility logic to the service layer, which is the right
   architectural boundary. Adding a duplicate guard in the router would split
   enforcement logic across two layers and could silently break if one is updated
   without the other. Rejected.

### Backward compatibility / migration

No change to product code; no migration needed. The regression test is a net-new
addition to the test suite.

## 5. Testing, Verification & Rollout

### Regression test

See Section 4 above. The test is offline (pytest + moto) and does not require the dev
stack to be running.

### Manual QA steps

1. Start the dev stack (`just up`).
2. Seed a lottery with `entry_fee_cents=200` using the broadcaster's authenticated
   session (`POST /broadcast/{session}/lottery/create`).
3. Attempt to enter that lottery using the **same** broadcaster session (same cookies):
   `POST /broadcast/{session}/lottery/{id}/enter`.
4. Confirm the response is HTTP 403 with body `{"code": "BROADCASTER_CANNOT_ENTER",
   "message": "Broadcaster cannot enter their own lottery"}`.
5. Confirm the billing table has no ledger row for the broadcaster via the DynamoDB
   admin UI at `http://localhost:8001`.
6. Confirm no `LENTRY#` item was written for the broadcaster in the
   `BroadcastChatMessages` table.
7. As a control: enter the same lottery from a different viewer account and confirm
   HTTP 200 and both a ledger debit (viewer) and credit (broadcaster) row exist.

### Observability

Because this is currently not a bug, no new alerting is needed. The regression test
in CI is the primary safeguard against future order regression.

However, as a defence-in-depth measure, the following observability additions are
recommended regardless:

- Add a structured log at INFO level when a self-entry attempt is blocked:
  `logger.info("broadcast.lottery.self_entry_blocked session=%s user=%s lottery=%s", ...)`.
  This provides an audit trail for support queries.
- Add a counter metric `broadcast.lottery.self_entry_blocked` — a spike could indicate
  a client UI bug exposing the "Enter" button to the broadcaster.

### Rollout

- Close the ticket as "Fixed in implementation — guard already correctly placed."
- Add the regression test as a PR to the broadcast-lottery test suite, bundled with
  the GAP-0128 billing-atomicity fix for the same file.
- No deployment of new product code is required.

### Effort

**S** (Small) — write one or two pytest tests, add one log statement. Estimated 1–2
hours.

### Sequencing

- This ticket can be closed independently.
- Bundle the regression test with the GAP-0128 fix PR, which changes the same
  `_charge_entry_fee` function. Having both tests in the same PR provides a complete
  behavioral test harness for all billing-critical paths in `enter_lottery`.
- Consider a follow-up audit of other lottery eligibility checks (max entries,
  `closes_at`, `status != open`) to confirm they also precede any fee-charging code.
  If any such check were found after `_charge_entry_fee`, it would constitute a new
  HIGH gap on the same pattern.
- Cross-reference with GAP-0129 to confirm that once the billing functions are made
  atomic, no remaining eligibility checks execute after money is moved.
