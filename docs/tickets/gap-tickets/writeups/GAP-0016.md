# GAP-0016: `useCallBillingHeartbeat.ts` Hook Does Not Exist — Remediation Write-up

> ~5 pages. Fix-oriented. Cites real file:line. Built on the verified investigation at
> `docs/tickets/gap-tickets/investigations/GAP-0016.md`.

## 1. Summary & Classification

**Plain-English statement**: During a connected paid call, the frontend never sends periodic
`PATCH /messaging/messages/calls/{call_id}/heartbeat` requests to the backend. The hook
responsible for scheduling this loop — `useCallBillingHeartbeat.ts` — was never written.
As a result, the backend billing engine never fires mid-call billing cycles, and the
call can run indefinitely regardless of the caller's wallet balance.

- **Severity**: CRIT
- **Source ticket**: CALL-011
- **Status**: Open
- **Owning area**: Frontend (React hooks) / Billing
- **Verdict**: **Confirmed** — the hook file does not exist; no call site for `sendCallHeartbeat`
  exists anywhere in the frontend codebase.
- **One-line impact**: All paid calls incur zero mid-call billing; balance enforcement is
  completely bypassed until the call ends.
- **Related tickets**: GAP-0147 (no billing props wired into `ConversationView`), GAP-0215
  (platform-fee read bug in `call_billing_timer.py`), CALL-011 (source feature ticket).

## 2. Current-State Investigation (Root Cause)

### Backend — fully implemented

The heartbeat endpoint is complete and correct. `app/routers/call_billing.py:148` defines:

```
PATCH /messaging/messages/calls/{call_id}/heartbeat
```

The handler validates the session, confirms `call.state == "connected"` and `call.paid == True`,
then delegates to `app/services/call_billing_timer.py:process_heartbeat()`. The `HeartbeatOut`
response model at `app/routers/call_billing.py:47-58` carries every field a polling loop needs:

| Field | Purpose |
|---|---|
| `next_bill_in_seconds` | When to send the next heartbeat |
| `warn_low_balance` | Whether to show a low-balance warning |
| `minutes_remaining` | Remaining funded minutes |
| `action` | `"ok"` or `"end_call"` — the enforcement signal |
| `balance_remaining_cents` | Current wallet balance |

When `action == "end_call"` (line 176-190), the router also calls
`messaging_call_lifecycle.end_call(...)` server-side, so the session is terminated even if
the client fails to handle the signal.

### Frontend API wrapper — implemented but unused

`frontend/src/api/endpoints/callBilling.ts:70-74` exports:

```typescript
export const sendCallHeartbeat = (callId: string) =>
  api.patch<HeartbeatResponse>(
    `/messaging/messages/calls/${callId}/heartbeat`,
    { client_ts: Math.floor(Date.now() / 1000) },
  );
```

This wrapper is syntactically correct and routes to the right endpoint. However, a full-text
search across all `.ts` and `.tsx` files in `frontend/src/` for `sendCallHeartbeat` returns
only this definition — zero call sites.

### The missing hook

`frontend/src/hooks/` (28 files as of the investigation) contains presence heartbeats
(`useViewerHeartbeat.ts`), recording (`useCallRecording.ts`), and connection quality
(`useConnectionQuality.ts`), but no `useCallBillingHeartbeat.ts` and no equivalent inline
logic anywhere else.

`frontend/src/pages/messages/CallSessionOverlay.tsx:131-148` runs a display timer via
`window.setInterval` to show elapsed seconds on the UI — but this is a pure UI counter that
never calls `sendCallHeartbeat`. The relevant code block is:

```typescript
// CallSessionOverlay.tsx:131-147 — display-only timer; no billing
function CallTimer({ running }: { running: boolean }) {
  const [elapsed, setElapsed] = React.useState(0);
  React.useEffect(() => {
    if (!running) { setElapsed(0); return; }
    const interval = window.setInterval(() => setElapsed((e) => e + 1), 1000);
    return () => window.clearInterval(interval);
  }, [running]);
  // ... render "MM:SS"
}
```

### Why the gap manifests at runtime

1. `process_heartbeat()` is called only from the heartbeat endpoint. No background server task
   calls it. If the client never sends the PATCH, it is never invoked.
2. `finalize_call_billing()` runs at call end but must charge the entire duration in one shot.
   If duration × rate exceeds wallet balance, the charge either fails silently or leaves the
   platform unpaid and the creator unpaid.
3. The `action="end_call"` enforcement path never triggers. A caller with $1 can run a
   multi-hour paid call with no enforcement.

## 3. Impact / Exploit / Blast Radius

### Financial impact

Every paid call that takes place today produces zero mid-call revenue for the platform and
for creators. The platform collects nothing until `finalize_call_billing` is reached (at
call end). If the caller's balance is below the accumulated cost, finalization fails; the
creator is underpaid or not paid at all.

### Exploit walkthrough

No attacker is required — the gap is available to every caller by default:

1. Caller navigates to a paid creator's conversation and initiates a call.
2. Call transitions to `state="connected"`.
3. Caller's wallet has, say, $0.50; the creator charges $1.00/min.
4. Mid-call: no heartbeats are sent, so no balance checks occur.
5. At 30 minutes elapsed, caller ends the call. `finalize_call_billing` tries to charge
   $30.00 against a $0.50 balance. The charge fails or truncates.
6. The creator receives at most $0.50 instead of $30.00. The platform's revenue share is also
   lost.

### Denial-of-service variant

A caller can run very long calls — up to `max_duration_minutes` (default 120) or indefinitely
if that guard is also absent — knowing the enforcement mechanism is broken.

### Availability / compliance

Paid-call billing is a contractual feature advertised to creators. Its silent non-function is
a breach of service terms and creates creator-support disputes at scale.

## 4. Fix Design (Code-Level)

### 4.1 Create `frontend/src/hooks/useCallBillingHeartbeat.ts`

The hook uses a self-rescheduling `setTimeout` (not `setInterval`) so that the next interval
adapts to the `next_bill_in_seconds` value returned by the server:

```typescript
import * as React from "react";
import { sendCallHeartbeat } from "@/api/endpoints/callBilling";
import type { HeartbeatResponse } from "@/api/endpoints/callBilling";

interface UseCallBillingHeartbeatOptions {
  callId: string | null;
  /** Only fire when the call is connected AND the rate is paid (rate_cents_per_minute > 0). */
  enabled: boolean;
  /** Default interval in seconds before the first server response. */
  defaultIntervalSeconds?: number;
  onEndCall?: () => void;
  onLowBalance?: (minutesRemaining: number) => void;
}

export function useCallBillingHeartbeat({
  callId,
  enabled,
  defaultIntervalSeconds = 30,
  onEndCall,
  onLowBalance,
}: UseCallBillingHeartbeatOptions): HeartbeatResponse | null {
  const [lastResponse, setLastResponse] =
    React.useState<HeartbeatResponse | null>(null);
  const timerRef = React.useRef<ReturnType<typeof setTimeout> | null>(null);
  const nextIntervalRef = React.useRef(defaultIntervalSeconds);
  const enabledRef = React.useRef(enabled);
  enabledRef.current = enabled;

  const sendHeartbeat = React.useCallback(async () => {
    if (!callId || !enabledRef.current) return;
    try {
      const resp = await sendCallHeartbeat(callId);
      setLastResponse(resp);
      nextIntervalRef.current = Math.max(
        10,
        resp.next_bill_in_seconds || defaultIntervalSeconds,
      );
      if (resp.action === "end_call") {
        onEndCall?.();
      } else if (resp.warn_low_balance) {
        onLowBalance?.(resp.minutes_remaining);
      }
    } catch {
      // Network error — keep the loop running; server-side heartbeat_timeout handles it.
    }
  }, [callId, defaultIntervalSeconds, onEndCall, onLowBalance]);

  React.useEffect(() => {
    if (!enabled || !callId) return;

    // Immediate first heartbeat on connect.
    void sendHeartbeat();

    const schedule = () => {
      timerRef.current = setTimeout(async () => {
        await sendHeartbeat();
        if (enabledRef.current) schedule();
      }, nextIntervalRef.current * 1000);
    };
    schedule();

    return () => {
      if (timerRef.current !== null) clearTimeout(timerRef.current);
    };
  }, [enabled, callId, sendHeartbeat]);

  return lastResponse;
}
```

Key design decisions:
- `self-rescheduling setTimeout` rather than `setInterval` avoids overlapping requests when
  the server latency exceeds the interval.
- `enabledRef` is a ref (not a dep) to avoid cancelling/restarting the timer on every render.
- Network errors are silently swallowed; the backend's `heartbeat_timeout` field handles
  lapsed heartbeats server-side.
- An immediate heartbeat fires on mount so the server knows the call is active from the
  first second.

### 4.2 Wire the hook into `CallSessionOverlay.tsx`

In `frontend/src/pages/messages/CallSessionOverlay.tsx`, the `state === "connected"` and
`session.paid` are already available (or derivable from the `CallBillingStatusOut` returned
by `getCallBilling`). Add:

```typescript
import { useCallBillingHeartbeat } from "@/hooks/useCallBillingHeartbeat";

// Inside the main component, after call state is established:
const heartbeat = useCallBillingHeartbeat({
  callId: session?.call_id ?? null,
  enabled: callState === "connected" && Boolean(session?.paid),
  onEndCall: () => onEnd(),   // existing end-call callback
  onLowBalance: (mins) =>
    toast.warning(`Low balance — approximately ${mins} minute(s) remaining`),
});
```

The `CallBillingOverlay.tsx` component already accepts `HeartbeatResponse`-shaped props and
can be passed `heartbeat` directly to render real-time balance information.

### 4.3 Dev/Prod parity (SECOPS-007)

The heartbeat endpoint is identical in dev and prod; it reads `S.call_billing_enabled` (a
feature flag) and hits DynamoDB. The frontend hook has no environment-specific path — it
always calls `sendCallHeartbeat`. The `call_billing_enabled` flag must be `true` in both
`.env.local` (for dev testing) and the production secrets. No additional SECOPS-007 changes
are needed; there is no AWS-specific path in the hook itself.

### 4.4 Alternatives considered

- **Server-side background task polling for inactive heartbeats**: Would not eliminate the
  client-side gap; the billing contract requires the client to assert presence (the heartbeat
  doubles as a liveness signal). Rejected.
- **Billing only at call end**: Already the current (broken) behavior. Rejected because it
  allows infinite balance-free calls.

  await page.route("**/heartbeat", (route) =>
    route.fulfill({ status: 200, json: { action: "end_call", next_bill_in_seconds: 30 } })

### Observability

- Add `logger.info("call_heartbeat_received", extra={call_id, elapsed_seconds, action})` to
  `process_heartbeat()` in `call_billing_timer.py` (if not already present).
- Alert on calls with `state=connected` and no heartbeat in the last 90 seconds (indicates
  either a client regression or a network outage).

### Rollout risks and sequencing

1. **Deploy the hook** — no backend change; zero risk to existing sessions.
2. **Enable `call_billing_enabled`** in prod once the hook is verified in staging.
3. **Backward compat**: Calls initiated before the hook deploy will not have had any
   heartbeats sent. `finalize_call_billing` handles this gracefully — it charges from
   `billing_start_ts` using the accumulated time. No migration needed.

### Interaction with other GAPs

This fix does not stand alone in making paid calls financially sound:

- **GAP-0215** (`call_billing_timer.py` reads `platform_fee` from `S.call_billing_enabled`
  flag rather than a dedicated `platform_fee_bps` setting): must be fixed so the platform's
  revenue share is correctly computed on each heartbeat billing cycle.
- **GAP-0147** (no billing props wired into `ConversationView.tsx`): the `CallBillingOverlay`
  and `CallBillingSummary` components that visualise heartbeat responses are not mounted;
  users cannot see their remaining balance during a call. The `lastResponse` returned by
  `useCallBillingHeartbeat` should feed these components once they are wired in.

The recommended sequencing is: fix GAP-0215 first (backend correctness), then deploy
`useCallBillingHeartbeat` (mid-call enforcement), then wire GAP-0147 (billing UI).

### Heartbeat failure modes

The hook's error-suppression on network failures deserves explicit design justification.
Three failure scenarios:

1. **Transient network error**: The hook logs a warning and continues the loop. The backend
   detects lapsed heartbeats via a `heartbeat_timeout` field set at call creation. If no
   heartbeat arrives within `2 * heartbeat_interval_seconds`, the backend's call expiry
   task (`expire_stale_calls`) terminates the session automatically (GAP-0249 covers that
   background task).

2. **Server-side 402 (balance depleted)**: The `sendCallHeartbeat` wrapper receives the 402
   and throws. The `catch` block currently swallows it. The hook must distinguish 402 from
   generic network errors and call `onEndCall()` on 402:
   ```typescript
   } catch (err: unknown) {
     if ((err as { response?: { status?: number } }).response?.status === 402) {
       onEndCall?.();
     }
     // Other errors: suppress and retry
   }
   ```

3. **Backend restart during call**: The call session is persisted in DynamoDB, so the session
   survives a backend restart. The heartbeat loop will resume successfully after reconnect
   because `call_id` is stable.
