# GAP-0255: Submission Expiry Background Task Missing — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase; no prior investigation doc exists.

## 1. Summary & Classification

**Claim from ticket**: Verified residency submissions from over a year ago remain in
`verified` status indefinitely. A stale submission continues to satisfy the residency gate
check, allowing a user whose address has changed years ago to reuse an old verification.
The fix is to add `expire_stale_submissions()` to the service and wire it as a periodic
asyncio task in `app/main.py` every 6 hours.

**Verdict: Claim CONFIRMED.** Searching the entire `app/` directory tree for
`expire_stale_submissions`, `expire_stale`, or any related term in the context of residency
documents returns zero results. `app/services/kyc_residency.py` has no expiry or staleness
method. `app/main.py` has no startup handler referencing anything from
`kyc_residency`. The `kyc_residency_documents` table has no TTL attribute configured in
`scripts/local-ddb-init.py`. Documents in `verified` status accumulate indefinitely.

The claim about the 1-year cutoff is consistent with the `kyc_retention_approved_days`
setting in `app/core/settings.py` (line 1175, default 365 days), which is used only for
the case-level purge (`run_retention_purge`) and has no residency-document equivalent.

- **Severity**: HIGH (compliance/regulatory) — proof-of-residency documents are
  point-in-time snapshots; AML/CDD frameworks require periodic re-verification. An
  indefinitely valid residency document means a user who moves house retains full EDD
  clearance forever.
- **Source ticket**: KYC-005
- **Owning area**: Backend / `app/services/kyc_residency.py`, `app/main.py`
- **Related tickets**: GAP-0252 (residency readiness gate), GAP-0253 (helper), GAP-0249
  (liveness expiry task — same pattern), SECOPS-007
- **Claim accuracy**: Confirmed. No stale-submission expiry exists anywhere in the codebase.

## 2. Current-State Investigation (root cause)

### `KycResidencyStore` — no expiry method

`app/services/kyc_residency.py` defines `KycResidencyStore` (line 317). The complete list
of public methods is:

- `upload_document` — create a pending record
- `get_document` — get one by document_id
- `list_documents_for_owner` — owner's documents
- `list_documents_for_case` — all docs for a case (ByCase GSI)
- `list_by_status` — all docs of a given status globally (ByStatus GSI)
- `run_extraction` — run/re-run extraction pipeline
- `review_document` — admin approve/reject

No method touches `updated_at` or any timestamp to mark old `verified` documents as
`expired`. There is no concept of "document age" in the existing API.

### Status lifecycle — no expiry transition

The status lifecycle defined in the module docstring (lines 14–22) is:

```
pending  -> verified  (recent + extracted address matches the profile)
         -> rejected  (too old OR address mismatch)
         -> expired   (document date older than the recency window)
```

The `expired` status exists but it is only ever set by `_decide_status` (line 603), which
is called inside `run_extraction`. There is no path that transitions a document from
`verified` to `expired` after the initial extraction. Once a document is marked `verified`,
it stays `verified` forever, regardless of how old the document becomes relative to today's
date.

### `list_by_status` — expiry candidates live in the verified partition

`list_by_status("verified", limit=100)` (line 454) queries the ByStatus GSI
(`PK=status="verified"`, `SK=created_at DESC`). This is the data source for the expiry
task: iterate the `verified` partition, check document age (today minus `document_date`),
and transition to `expired` for those over the threshold.

### Recency check is already implemented

`_check_recency` (line 588) is already correct:

```python
def _check_recency(self, document_date: str, *, now: Any = None) -> tuple[bool, int]:
    d = _parse_iso_date(document_date)
    if d is None:
        return (False, 0)
    today = _today(now)
    days = (today - d).days
    if days < 0:
        days = 0
    valid = days <= S.kyc_residency_recency_days
    return (valid, days)
```

Default `S.kyc_residency_recency_days` is set in `app/core/settings.py`. The recency check
is injectable with `now`, which is the essential test seam for a background task.

### `app/main.py` — no KYC residency startup handler

Searching all 806 lines of startup handlers in `app/main.py` for any reference to
`kyc_residency` returns zero results. The related KYC startup handlers are:

```python
app.add_event_handler("startup", start_kyc_sla_checker_task)     # line 528
app.add_event_handler("startup", start_kyc_analytics_precompute_task)  # line 586
```

The `kyc_liveness_call_router` (line 577, from `kyc_liveness_call.py`) is registered but
also has no expiry task (addressed in GAP-0249). The residency router is registered too but
with no associated background task.

### `kyc_retention_approved_days` — not applied to residency

`app/core/settings.py` line 1175 defines `kyc_retention_approved_days: int = 365`. This
setting is used only in `KycCaseStore.run_retention_purge` (line 799–875 of
`kyc_cases.py`) to purge approved KYC cases after one year. It is not consulted anywhere
in `kyc_residency.py`. The residency service has no equivalent `kyc_residency_expiry_days`
setting.

## 3. Impact / Exploit / Blast Radius

**Regulatory exposure — address changes undetected**: A user who verified their address in
January 2024 and moved in March 2024 retains `verified` residency status permanently. Any
subsequent readiness gate check (GAP-0252) would report `residency_verified=True` even
though the user's profile address no longer matches the old document. AML/CDD frameworks
(EU AMLD, FinCEN CDD Rule) require that customer due diligence is kept current.

**Stale evidence in admin review**: Admin reviewers see the document status as `verified`
on the case detail page. They have no automatic signal that the document is 18 months old.
Without a staleness transition, reviewers must manually calculate document age to determine
whether to request re-verification.

**ByStatus GSI growth**: The `verified` partition of the ByStatus GSI grows monotonically.
Queries over it (used by the admin review queue and the new residency tab in GAP-0254)
become slower over time as the partition grows with historical documents.

**No security exploit**: This is a compliance and data quality gap. It does not enable
unauthorized access or fund exfiltration.

**Recency cutoff interaction**: After this fix is deployed, the `list_by_status` query
used by `get_verified_docs_for_case` (GAP-0253) will naturally shrink as old documents
are transitioned to `expired`. The readiness gate (GAP-0252) will then re-block users
whose only verified document has expired, prompting them to re-upload. This is the
intended compliance behavior.

## 4. Fix Design (code-level)

### 4a. Add `expire_stale_submissions` to `KycResidencyStore`

Insert after `review_document` (line 567) in `app/services/kyc_residency.py`:

```python
def expire_stale_submissions(
    self, *, now: Any = None, limit: int = 500
) -> list[str]:
    """Expire verified residency documents whose document_date is outside the
    recency window.

    Iterates the ByStatus GSI 'verified' partition and re-applies the recency
    check. Any document that fails (too old) is transitioned to STATUS_EXPIRED.

    Injectable ``now`` for deterministic tests.
    Returns list of expired document_ids.
    """
    expired_ids: list[str] = []
    items = self.list_by_status(STATUS_VERIFIED, limit=limit)
    ts = now_ts()
    for item in items:
        recency_valid, _ = self._check_recency(
            str(item.get("document_date") or ""), now=now
        )
        if not recency_valid:
            document_id = str(item.get("document_id") or "")
            if not document_id:
                continue
            self._apply_update(
                document_id,
                {
                    "status": STATUS_EXPIRED,
                    "updated_at": ts,
                },
            )
            logger.info(
                "kyc.residency.expired document_id=%s document_date=%s",
                document_id,
                item.get("document_date"),
            )
            expired_ids.append(document_id)
    return expired_ids
```

Key design notes:

- Uses `STATUS_VERIFIED = "verified"` (existing module constant, line 60) and
  `STATUS_EXPIRED = "expired"` (line 62).
- `_check_recency` is already injectable with `now` — this makes the task fully
  deterministic in tests.
- Uses `_apply_update` (line 571) — the same update path used by `run_extraction` and
  `review_document`. No DynamoDB-specific code is duplicated.
- Does not touch `review` sub-object — the review decision remains visible for audit.
- Processes at most `limit=500` documents per invocation. The background loop calls this
  every 6 hours; with a 365-day recency window and typical upload rates, the `verified`
  partition is bounded.

### 4b. Add the background loop function and startup wrapper

Append to the end of `app/services/kyc_residency.py`:

```python
# ── Background expiry task (KYC-005) ──────────────────────────────────────

import asyncio as _asyncio

_SUBMISSION_EXPIRY_INTERVAL_SECONDS: int = 6 * 3600  # 6 hours


async def _expire_submissions_loop() -> None:
    """Periodic background task: expire verified residency docs outside the recency window."""
    logger.info("kyc.residency.expiry_loop.started")
    while True:
        try:
            expired = STORE.expire_stale_submissions()
            if expired:
                logger.info(
                    "kyc.residency.expiry_loop.expired count=%d document_ids=%s",
                    len(expired),
                    expired[:10],
                )
        except Exception:  # pragma: no cover — never crash the loop
            logger.exception("kyc.residency.expiry_loop.error")
        await _asyncio.sleep(_SUBMISSION_EXPIRY_INTERVAL_SECONDS)


def start_kyc_residency_expiry_task() -> None:
    """Register the residency submission expiry loop at app startup."""
    import asyncio

    asyncio.ensure_future(_expire_submissions_loop())
    logger.info("kyc.residency.expiry_loop.registered interval_hours=6")
```

The loop is always enabled (no feature flag gate) because expiring stale residency documents
is a compliance requirement, not an optional feature. Operators who need to disable it must
do so by setting `KYC_RESIDENCY_RECENCY_DAYS` to a very large value (e.g., 36500, or
100 years) rather than by disabling the loop, which would be incorrect.

### 4d. Add `kyc_residency_recency_days` to settings (if not already present)

`_check_recency` references `S.kyc_residency_recency_days`. Verify this setting exists in
`app/core/settings.py`. If absent, add:

```python

    os.environ.get("KYC_RESIDENCY_RECENCY_DAYS", "365")

```

Default 365 days (1 year) aligns with the ticket's stated recency window and
`kyc_retention_approved_days`. Operators can reduce this to 90 days (`KYC_RESIDENCY_RECENCY_DAYS=90`)
to enforce stricter recency policies.

### 4e. Dev/Prod parity (SECOPS-007)

`expire_stale_submissions` calls:

1. `list_by_status(STATUS_VERIFIED)` — queries `T.kyc_residency_documents` via the ByStatus
   GSI. Same table handle (`T.kyc_residency_documents`) in dev and production.
2. `_apply_update(document_id, ...)` — `T.kyc_residency_documents.update_item(...)`. Same
   path in both environments.

No environment-specific branches. In dev, `DDB_ENDPOINT_URL=http://localhost:8001` causes
the boto3 client to point to DynamoDB Local; in production the endpoint is absent and boto3
uses the AWS regional endpoint.

### Alternatives considered

- **DynamoDB TTL on `document_date + recency_days`**: TTL deletes items; expired documents
  should remain in `expired` status for audit. Rejected.
- **On-demand expiry inside `get_verified_docs_for_case`**: Check recency at read time and
  transition lazily. Rejected — this makes read operations write side-effects, violating
  the principle of command-query separation. It would also fail to expire documents that
  are no longer queried (e.g., abandoned cases).
- **Larger retention: only purge in `run_retention_purge`**: The existing purge removes
  entire case records, not just residency documents. Rejected — the goal is to transition
  document status (so the readiness gate re-blocks the user) not to delete records.
- **6-hour vs 24-hour interval**: The ticket specifies 6 hours. A 24-hour interval would
  be acceptable for a 365-day recency window (day-level precision is sufficient), but 6
  hours keeps the ByStatus GSI `verified` partition pruned more aggressively and aligns
  with the ticket specification.

### Manual QA steps

1. Run `just up`.
2. Upload a residency document with `document_date="2023-01-01"` (over a year ago). Run
   extraction. Confirm status becomes `verified`.
3. Wait for the background loop to run (default 6 h in production; set
   `KYC_RESIDENCY_EXPIRY_INTERVAL_SECONDS=30` in `.env.local` for quick QA).
4. `GET /ui/kyc/residency/{document_id}` — confirm status is now `expired`.
5. If the case has `intake_profile=enhanced`, `GET /v1/kyc/cases/{case_id}/readiness` —
   confirm `checks.residency_verified=false` and `missing_requirements` contains
   `residency_verified`.
6. Check backend logs for
   `kyc.residency.expiry_loop.expired count=1 document_ids=['kycres_...']`.

### Metrics / observability

- Log `kyc.residency.expiry_loop.expired count=%d document_ids=%s` at INFO for monitoring.
  A spike (>50 per run) indicates a backlog of old unmanaged documents — appropriate for
  initial deployment after the fix, but worth alerting on in steady state.
- Log `kyc.residency.expiry_loop.error` at ERROR on loop iteration failures.
- Consider a Prometheus counter `kyc_residency_doc_expired_total` (increment by
  `len(expired)` inside the loop) for SLA monitoring dashboards.
- `GET /ui/kyc/residency/admin/by-status?status=verified` count shrinking after deployment
  is the health-check confirmation that the task is running correctly.

### Backlog drain on first deployment

On first deployment in a production system with an accumulated `verified` partition, the
first loop run may expire hundreds or thousands of documents in a single 6-hour window.
To spread the load:

1. Set `KYC_RESIDENCY_RECENCY_DAYS=730` (2 years) initially.
2. Gradually decrease to `365` over 2 deployment cycles to phase in the tighter window.

Or: pre-run `STORE.expire_stale_submissions(limit=5000)` via a one-off admin script before
enabling the background task, to drain the historical backlog atomically.
