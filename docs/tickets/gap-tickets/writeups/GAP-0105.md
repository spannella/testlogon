# GAP-0105: No Automatic Cost Collection Schedule — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code; `file:line` citations are live.

## 1. Summary & Classification

**Severity**: HIGH
**Source ticket**: AGENT-018
**Owning area**: Accountant / Cost Tracking Agent
**Status**: Open (no fix deployed as of this write-up)

The Accountant Agent (AGENT-018) provides LLM cost tracking, budget management, and over-budget alerts. `POST /ui/agents/accountant/costs/collect` (`app/routers/agent_accountant.py:298`) triggers a single on-demand collection cycle. No asyncio background task is registered in `app/main.py` to run `collect_costs` automatically on a recurring schedule, even when `S.accountant_agent_execute_commands = True`. Cost data is therefore only fresh when an operator manually calls the collect endpoint; budgets are not evaluated automatically and over-budget alerts are never generated unless triggered by hand.

**Claim accuracy**: The ticket names `app/main.py` as the location and describes the missing task as one that calls `run_cost_collection_if_enabled` gated by `S.accountant_agent_execute_commands`. Code inspection confirms: (1) no such function `run_cost_collection_if_enabled` exists — the actual callable is `collect_costs` in `agent_accountant.py:1093`; (2) no accountant startup task appears in `app/main.py`. The ticket's description of the gap is accurate; the specific function name `run_cost_collection_if_enabled` is a design aspiration, not an existing symbol. **Claim is confirmed with a minor correction: the function to call is `collect_costs`, not `run_cost_collection_if_enabled` (which does not exist yet).**

**Related tickets**: GAP-0048 (no daily spent-today-cents reset task), GAP-0010 (agent loop not running as background task), GAP-0050 (compute_hourly_rollup never called), GAP-0104 (no scheduled-publish background loop).

## 2. Current-State Investigation (root cause)

### 2.1 `collect_costs` at `app/services/agent_accountant.py:1093`

```python
def collect_costs(*, user_id: str) -> Dict[str, Any]:
    """Run a collection cycle.

    In execute mode this would poll provider usage/billing APIs + AWS Cost
    Explorer. In mock mode (default, always in E2E) it simply re-evaluates
    budgets against already-recorded costs and returns the alerts created.
    """
    ensure_tables()
    alerts = check_budgets(user_id=user_id)
    return {
        "ok": True,
        "executed": bool(S.accountant_agent_execute_commands),
        "alerts_created": len(alerts),
        "alerts": alerts,
        "collected_at": now_ts(),
    }
```

The function is correct and functional. It calls `check_budgets`, which evaluates all budgets for the user and creates alert records for over-budget conditions. The problem is that this function is only called from the HTTP endpoint — there is no scheduled caller.

### 2.2 `POST /costs/collect` at `app/routers/agent_accountant.py:298`

```python
@agent_accountant_router.post("/costs/collect")
async def collect(
    session: Dict[str, Any] = Depends(require_ui_session),
):
    return svc.collect_costs(user_id=_uid(session))
```

This is the sole call site of `collect_costs`. It is user-scoped (requires session auth), meaning it evaluates budgets for the authenticated user only. A background loop would need to iterate all users with accountant configs or use a different approach (see §4).

### 2.3 `S.accountant_agent_execute_commands` at `app/core/settings.py:2300`

```python
accountant_agent_execute_commands: bool = os.environ.get(
    "ACCOUNTANT_AGENT_EXECUTE_COMMANDS", "0"
) not in ("0", "false", "False")
```

Defaults to `False`. When `True`, `collect_costs` is expected to poll real provider APIs (AWS Cost Explorer, OpenAI usage endpoints, etc.). The docstring says "In execute mode this would poll...". The actual real-provider calls are not yet implemented (the function always calls `check_budgets` in both modes). The gate is wired for when real polling is added.

### 2.4 `S.accountant_agent_auto_alert` at `app/core/settings.py:2299`

```python
accountant_agent_auto_alert: bool = os.environ.get("ACCOUNTANT_AGENT_AUTO_ALERT", "0") not in ("0", "false", "False")
```

A separate flag for automatic alert generation exists in settings. The gap ticket references only `execute_commands`, but `auto_alert` is the more directly relevant flag for automatic budget evaluation without real provider polling.

### 2.5 `app/main.py` — no accountant startup task

Reviewing all `add_event_handler("startup", ...)` lines in `app/main.py` (lines 521–806) confirms that `start_billing_reconcile_task`, `start_billing_dunning_task`, `start_unified_scheduler_task`, and many others are registered, but no accountant or cost-collection task is among them. The accountant router is imported at line 785 but no background task is started.

### 2.6 `check_budgets` scope concern

`check_budgets(user_id=user_id)` evaluates budgets for a single user. A platform-wide background loop must either:
- Enumerate all users who have accountant configs and call `check_budgets` for each, or
- Run without a user scope, using a cross-user GSI scan.

The current design uses per-user DynamoDB keys (`pk = "ACONF#{user_id}"`), so a cross-user scan is needed. This is a design consideration for the background loop (see §4.3).

## 3. Impact / Exploit / Blast Radius

### 3.1 Budget overruns go undetected

Without automatic collection, a user could burn through 100% of a budget between manual `POST /collect` calls. The `auto_pause_on_exceed` flag (checked at `app/services/agent_accountant.py:855`) only fires when budgets are evaluated. If evaluation never happens automatically, workers are never auto-paused and costs accumulate unchecked.

### 3.2 Alert fatigue from stale data

When an operator does eventually call `POST /collect`, all overruns since the last call are detected simultaneously. If a budget was exceeded for 3 days, all 3 days of overage generate alerts at once, creating noise that makes it hard to identify when the breach occurred.

### 3.3 Compliance and SLA exposure

Platform operators may have contractual or regulatory obligations to alert on cost overruns within a defined time window (e.g., "alert within 1 hour of breach"). Without an automatic loop, this SLA cannot be met.

### 3.4 Blast radius

All users who have configured budgets via `POST /ui/agents/accountant/budgets` are affected — their budgets are never automatically evaluated. With `accountant_agent_auto_alert = True` (non-default but expected for production), the gap means the setting has no effect.

## 4. Fix Design (code-level)

### 4.1 Add `run_cost_collection_if_enabled` wrapper

The ticket specifies calling `run_cost_collection_if_enabled`. Create this function in `app/services/agent_accountant.py` after `collect_costs` (after line 1108):

```python
def run_cost_collection_if_enabled() -> None:
    """Platform-wide cost collection loop body.

    Evaluates budgets for all users who have accountant configs when
    accountant_agent_auto_alert is True. Real provider polling is
    additionally gated by accountant_agent_execute_commands.

    Designed to be called from a periodic background task.
    """
    if not S.accountant_agent_auto_alert and not S.accountant_agent_execute_commands:
        return
    ensure_tables()
    # Scan all accountant config records to find active users
    config_items: List[Dict[str, Any]] = []
    scan_kwargs: Dict[str, Any] = {
        "FilterExpression": Attr("sk").eq("ACCOUNTANT_CONFIG"),
        "ProjectionExpression": "pk, owner_sub",
    }
    while True:
        resp = T.agent_types.scan(**scan_kwargs)
        config_items.extend(resp.get("Items", []))
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        scan_kwargs["ExclusiveStartKey"] = lek

    evaluated = 0
    for item in config_items:
        user_id = item.get("owner_sub") or item.get("pk", "").replace("ACONF#", "")
        if not user_id:
            continue
        try:
            collect_costs(user_id=user_id)
            evaluated += 1
        except Exception as exc:
            logger.error("Cost collection failed for user=%s: %s", user_id, exc)

    logger.info("Cost collection loop completed: evaluated %d users", evaluated)
```

### 4.2 Add `start_cost_collection_task`

Add to `app/services/agent_accountant.py`:

```python
import asyncio

_COST_COLLECTION_INTERVAL_SECONDS = 3600  # 1 hour

async def _cost_collection_loop() -> None:
    """Background coroutine: run cost collection every hour."""
    while True:
        try:
            run_cost_collection_if_enabled()
        except Exception as exc:
            logger.error("Cost collection loop unhandled error: %s", exc)
        await asyncio.sleep(_COST_COLLECTION_INTERVAL_SECONDS)


def start_cost_collection_task() -> None:
    """Register the hourly cost collection background loop at app startup."""
    try:
        loop = asyncio.get_event_loop()
    except RuntimeError:
        loop = asyncio.new_event_loop()
        asyncio.set_event_loop(loop)
    loop.create_task(_cost_collection_loop())
    logger.info(
        "Cost collection background task started (interval=%ds, auto_alert=%s, execute=%s)",
        _COST_COLLECTION_INTERVAL_SECONDS,
        S.accountant_agent_auto_alert,
        S.accountant_agent_execute_commands,
    )
```

### 4.3 Register the task in `app/main.py`

In the import block (near the existing agent router imports around line 785):

```python
from app.services.agent_accountant import start_cost_collection_task  # ADD
```

In the startup section (near line 806):

```python
app.add_event_handler("startup", start_cost_collection_task)  # ADD
```

### 4.4 Gate logic for dev vs prod

The loop calls `run_cost_collection_if_enabled`, which checks:

```python
if not S.accountant_agent_auto_alert and not S.accountant_agent_execute_commands:
    return
```

In dev, both flags default to `False`, so the loop runs but does nothing (just sleeps). This is correct: the task is registered in dev but is a no-op, matching the pattern of other background tasks (e.g., `start_broadcast_scheduler_task` which also checks a flag before acting).

If an engineer wants the loop to run in dev for testing, they set `ACCOUNTANT_AGENT_AUTO_ALERT=1` in `.env.local` — no code change needed.

### 4.5 Configurable interval via settings

For production tuning, make the interval configurable:

```python
# app/core/settings.py
accountant_cost_collection_interval_seconds: int = int(
    os.environ.get("ACCOUNTANT_COST_COLLECTION_INTERVAL_SECONDS", "3600")
)
```

In `_cost_collection_loop`:

```python
await asyncio.sleep(S.accountant_cost_collection_interval_seconds)
```

### 4.6 Dev/Prod parity (SECOPS-007)

| Aspect | Dev | Prod |
|--------|-----|------|
| Task registered | Yes — same code path | Yes |
| Active gate | Both flags `False` → no-op | `auto_alert=True` → runs |
| DynamoDB | Local (port 8001) | AWS DynamoDB |
| Real provider calls | Never (`execute_commands=False`) | When `execute_commands=True` |
| Interval | 3600s (configurable) | 3600s (configurable) |

The task registration code and loop body are identical; environment configuration determines whether work is done.

### 4.7 Alternatives considered

- **AWS EventBridge Scheduler / Lambda** (dedicated cost collection Lambda): correct for large-scale production. Rejected for this fix for the same reason as GAP-0104 — it requires infrastructure changes inconsistent with the existing background-task pattern in the codebase. Plan for migration to EventBridge in a follow-up infrastructure ticket.
- **Unified Scheduler** (`app/services/unified_scheduler.py`): the existing unified scheduler could host this job. Rejected in the minimum fix because it would require understanding the unified scheduler's job model and registration format. The standalone `start_cost_collection_task` pattern is simpler and matches the majority of background tasks.
- **User-triggered only**: accept the status quo and document that operators must call `POST /collect` manually. Rejected — the ticket explicitly requires automation and `accountant_agent_auto_alert` exists specifically for this purpose.
- **Per-user asyncio tasks**: spawn one task per user at startup. Rejected — user list is not known at startup, grows over time, and tasks would need to be created as new users configure the accountant.

### 5.5 Rollout and risks

- **Effort**: S (small) — one new function and wrapper in `agent_accountant.py`, one import and one `add_event_handler` in `main.py`.
- **Backward compatibility**: existing manually-triggered `POST /collect` remains functional. The background loop is purely additive.
- **First-run behaviour**: on first deploy, the loop evaluates all users immediately at startup, then every hour. For users with long-overdue budget breaches, many alerts may be generated at once. Consider adding a "last_collected_at" timestamp to skip users collected within the last hour.
- **Rollback**: remove the `add_event_handler` line. The background function can remain in the service file without harm.
- **Risk**: The scan of `agent_types` table for all `sk = "ACCOUNTANT_CONFIG"` rows is a FilterExpression scan — expensive on a large table (see CLAUDE.md gotcha: FilterExpression doesn't reduce page size). Mitigate with a GSI on `sk` or by storing accountant config under a fixed GSI partition key. Add to the tech-debt backlog.
- **Sequencing**: this fix is self-contained. Ship alongside `ACCOUNTANT_AGENT_AUTO_ALERT=1` configuration in the staging environment after validating that `check_budgets` correctly detects breaches in end-to-end tests.
