# GAP-0257: FinancialVerificationPanel Missing from Admin Case Detail — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Gap**: The KYC admin case detail page (`frontend/src/pages/admin/KycCaseDetailPage.tsx`) has no "Financial Verification" tab or panel. Reviewers adjudicating a KYC case cannot see the applicant's proof-of-funds score, declared source category, declared amount, risk contribution, or adjudication status without leaving the case view and navigating to a separate page.

- **Severity**: HIGH
- **Source ticket**: KYC-005
- **Area**: Frontend (admin case review workflow) + backend (missing `admin/submissions?user_sub=` endpoint)
- **Status**: Confirmed — the gap exists exactly as described. `KycCaseDetailPage.tsx` has no Financial Verification content anywhere in its 685 lines.
- **Impact**: Reviewers must make approval/rejection decisions on KYC cases without seeing whether the applicant has a verified (or suspicious) source of funds. This breaks the holistic review workflow and can lead to approvals of high-risk profiles or rejections of legitimate ones.
- **Related tickets**: KYC-005 (parent feature), GAP-0256 (standalone proof-of-funds queue page), KYC-008 (risk score aggregation), SECOPS-007 (dev/prod parity).

**Claim verdict**: Confirmed exactly. `KycCaseDetailPage.tsx` imports only `fetchKycCaseDetail`, `approveKycCase`, `rejectKycCase`, `requestKycInfo`, and `KycFacialComparisonReview`. There is no import of anything related to proof-of-funds. The page renders a two-column layout (document viewer + case info/actions/timeline) with no tabs for financial data. The referenced backend endpoint `GET /ui/kyc/proof-of-funds/admin/submissions?user_sub=` does not exist in `app/routers/kyc_proof_of_funds.py`.

## 2. Current-State Investigation (root cause)

### 2.1 What KycCaseDetailPage.tsx renders today

`frontend/src/pages/admin/KycCaseDetailPage.tsx` (685 lines) renders:

- **Left column** (lines 432–436): `DocumentViewer` (file tabs with zoom/rotate controls) and `KycFacialComparisonReview`.
- **Right column** (lines 439–526): "Case Information" card (user, status, questionnaire link, signature link, decision), "Actions" card (Approve/Reject/Request Info buttons), `CaseTimeline`.
- Three dialogs for Approve / Reject / Request Info (lines 529–682).

There is no `<Tabs>` component wrapping the right column or the full page. There is no reference to `kyc_proof_of_funds`, `kycProofOfFundsApi`, `ProofOfFundsSubmission`, or any financial verification data anywhere in the file.

### 2.2 Missing backend endpoint

The natural query for the financial verification tab is "fetch all proof-of-funds submissions for this case's user". `app/services/kyc_proof_of_funds.py:194` exposes `list_submissions_for_user(user_sub)` which performs a DynamoDB key-condition query by `user_sub`. However, `app/routers/kyc_proof_of_funds.py` (102 lines) exposes only:

- `GET /submissions` — caller's own submissions (line 58)
- `GET /review/by-status/{status}` — admin listing by status (line 78), no user filter

There is no `GET /ui/kyc/proof-of-funds/admin/submissions?user_sub=` endpoint. An admin reviewer viewing a case cannot fetch that case's user's proof-of-funds data through the existing API without also knowing which status to query.

### 2.3 Architectural gap in case detail

The KYC case (`kyc_cases` DynamoDB table) stores `user_sub` as the case owner. The case detail API (`fetchKycCaseDetail`, which calls `GET /ui/kyc/cases/admin/{caseId}`) returns a `KycCaseDetail` object that includes `user_sub`. The frontend already has `caseData.user_sub` available on line 448. The only missing pieces are:

1. A backend endpoint that accepts `user_sub` as a query parameter and returns the user's proof-of-funds submissions (needed so the admin can fetch financial data for any user, not just themselves).
2. A frontend tab component in `KycCaseDetailPage.tsx` that calls that endpoint and renders the results.

### 2.4 Risk data that reviewers are missing

`app/services/kyc_proof_of_funds.py` stores per-submission: `score` (0–100), `declared_amount_cents`, `source_category`, `risk_contribution` (`−10` for verified, `0` for needs_more_info, `+15` for rejected, `+5` for expired), `status`, and `reviewer_note`. A reviewer approving a case without seeing these fields may unknowingly approve a user who declared $50M in income (which received a −30 score penalty and was auto-rejected) or whose source of funds is under review.

### 2.5 Dev vs prod parity

All data involved is in DynamoDB (Local in dev, real in prod). The `list_submissions_for_user` service function uses `app/core/tables.py:T.kyc_proof_of_funds` with DynamoDB Key-condition expression. No new AWS services are required. The fix is SECOPS-007-compliant with no environment-specific code paths.

## 3. Impact / Exploit / Blast Radius

### 3.1 Reviewers approving cases without complete financial picture

A KYC reviewer sees Document Viewer + Facial Comparison + Timeline. They approve a case. The applicant's proof-of-funds submission may be in one of several states:

- `rejected` (risk_contribution = +15): the case-level risk score is elevated, but the reviewer sees nothing
- `needs_more_info` (risk_contribution = 0): outstanding financial review, but reviewer approves the case anyway
- No submission at all: the applicant never submitted financial documentation, but the reviewer cannot tell this from the case view

Under strict AML/EDD requirements, a reviewer approving a case must confirm that source-of-funds verification has passed. The absence of this panel is a compliance control failure.

### 3.2 AML continuous monitoring gap

When a user later updates their profile (see GAP-0259) and re-screening is triggered, the re-screening result changes the risk score. If the reviewer cannot see the current financial verification status alongside the screening result in one view, they cannot make a coherent risk decision.

### 3.3 Operational efficiency

Reviewers must context-switch to the standalone proof-of-funds queue (once GAP-0256 is fixed) to check a specific user's financial data, then manually navigate back to the case view. In high-volume queues, this round-trip multiplies review time.

## 4. Fix Design (code-level)

### 4.1 Backend: add `GET /admin/submissions?user_sub=` endpoint

This endpoint is shared with GAP-0256 but described there as well. Add to `app/routers/kyc_proof_of_funds.py`:

```python
from app.auth.deps import AuthenticatedUser

@kyc_proof_of_funds_router.get("/admin/submissions")
def admin_list_submissions_for_user(
    user_sub: str,
    _user: AuthenticatedUser = Depends(require_admin_or_root),
):
    """List all proof-of-funds submissions for a given user. Admin/root only."""
    return {"submissions": kyc_proof_of_funds.list_submissions_for_user(user_sub)}
```

Also fix the type annotation on `adjudicate` (line 90): `session: dict` → `_user: AuthenticatedUser`, and line 97: `session.sub` → `_user.sub`.

### 4.2 Frontend: add `getAdminSubmissionsForUser` to the API wrapper

In `frontend/src/api/endpoints/kycProofOfFunds.ts`, add:

```typescript
getAdminSubmissionsForUser: (userSub: string) =>
  api.get<ProofOfFundsSubmissionList>(
    `/ui/kyc/proof-of-funds/admin/submissions?user_sub=${encodeURIComponent(userSub)}`
  ),
```

### 4.3 Frontend: add FinancialVerificationPanel component

Create `frontend/src/pages/admin/KycFinancialVerificationPanel.tsx` (or inline it in `KycCaseDetailPage.tsx`). The panel:

- Accepts `userSub: string` as a prop.
- Uses `useQuery(["kyc-proof-of-funds-admin", userSub], () => kycProofOfFundsApi.getAdminSubmissionsForUser(userSub))`.
- Renders a summary row: total submissions, latest status badge, active risk contribution.
- Renders a table of submissions with columns: date, source category, declared amount, score (colored 0–100 bar or badge), status badge, risk contribution (red for positive, green for negative).
- Shows a "No submissions" state if the array is empty.
- Does not include adjudication controls (those belong on the standalone review queue page, GAP-0256).

### 4.4 Frontend: wire into KycCaseDetailPage.tsx

Convert the right column of `KycCaseDetailPage.tsx` from a plain `<div className="lg:col-span-2 space-y-6">` stack (line 439) to a `<Tabs>` container with at minimum two tabs: "Overview" (existing content) and "Financial Verification" (new panel). Example structure around line 439:

```tsx

import KycFinancialVerificationPanel from "./KycFinancialVerificationPanel";

// replace the right column div with:
<div className="lg:col-span-2 space-y-6">
  <Tabs defaultValue="overview">
    <TabsList>
      <TabsTrigger value="overview">Overview</TabsTrigger>
      <TabsTrigger value="financial">Financial Verification</TabsTrigger>
    </TabsList>
    <TabsContent value="overview">
      {/* existing Case Information, Actions, Timeline cards */}
    </TabsContent>
    <TabsContent value="financial">
      <KycFinancialVerificationPanel userSub={caseData.user_sub} />
    </TabsContent>
  </Tabs>
</div>
```

### 4.5 Dev/Prod parity (SECOPS-007)

No new AWS services. Uses existing `T.kyc_proof_of_funds` DynamoDB table with key-condition on `user_sub` (PK). In dev: DynamoDB Local at port 8001. In prod: DynamoDB. The scoring remains deterministic (mock) unless `S.kyc_proof_of_funds_real_analysis_enabled = True` is set in prod, which gates a real financial verification API as described in KYC-005.

### 4.6 Alternatives considered

- **Embedding raw submissions in the case detail API response**: Rejected. The case detail API is already large and the proof-of-funds data is owned by a separate service. Keeping them as separate queries follows the existing fetch pattern (facial comparison is also a separate query via `KycFacialComparisonReview`).
- **Showing the summarized risk contribution only**: Rejected. A compliance reviewer needs to see the underlying submissions (declared amounts, categories, documents) to make an informed decision, not just an aggregate number.

### 5.1 Regression test (pytest, fails before / passes after)

Add `tests/test_kyc_proof_of_funds_admin_submissions.py`:

```python
"""
Regression test for GAP-0257: admin submissions endpoint for per-user lookup.

Fails before the fix: GET /ui/kyc/proof-of-funds/admin/submissions?user_sub= returns 404.
Passes after the fix: returns a list of submissions for the given user.
"""
import pytest
from fastapi.testclient import TestClient
from fastapi import FastAPI
from app.routers.kyc_proof_of_funds import kyc_proof_of_funds_router
from app.auth.policy import require_admin_or_root
from app.auth.deps import AuthenticatedUser
from app.auth.roles import Role

FAKE_SUB = [
    {"submission_id": "pof_aaa", "user_sub": "u_001", "status": "verified", "score": 95}
]


@pytest.fixture()
def client(monkeypatch):
    app = FastAPI()
    app.include_router(kyc_proof_of_funds_router)
    app.dependency_overrides[require_admin_or_root] = lambda: AuthenticatedUser(
        sub="admin_x", role=Role.ADMIN
    )
    monkeypatch.setattr(
        "app.services.kyc_proof_of_funds.list_submissions_for_user",
        lambda user_sub: FAKE_SUB if user_sub == "u_001" else [],
    )
    return TestClient(app)


def test_admin_submissions_for_user(client):
    """Fails before fix (404 or missing route), passes after."""
    resp = client.get("/ui/kyc/proof-of-funds/admin/submissions?user_sub=u_001")
    assert resp.status_code == 200
    data = resp.json()
    assert "submissions" in data
    assert data["submissions"][0]["submission_id"] == "pof_aaa"


def test_admin_submissions_empty_for_unknown_user(client):
    resp = client.get("/ui/kyc/proof-of-funds/admin/submissions?user_sub=nobody")
    assert resp.status_code == 200
    assert resp.json()["submissions"] == []


def test_admin_submissions_requires_auth(monkeypatch):
    """Without admin override, unauthenticated request must be rejected."""
    app = FastAPI()
    app.include_router(kyc_proof_of_funds_router)
    client = TestClient(app, raise_server_exceptions=False)
    resp = client.get("/ui/kyc/proof-of-funds/admin/submissions?user_sub=u_001")
    assert resp.status_code in (401, 403)
```
