# GAP-0206: `toggle_provider` Does Not Enforce Payment Initiation Gate — Remediation Write-up

> ~5 pages. Fix-oriented. Code verified against the live tree; all `file:line` citations confirmed.

## 1. Summary & Classification

**Gap**: The payment-provider enable/disable system (`toggle_provider` / `is_provider_enabled`) is fully implemented and correctly updates DynamoDB, but none of the billing charge paths in `app/routers/billing.py` or `app/routers/billing_ccbill.py` call `is_provider_enabled()` before processing a payment. Disabling a provider via the admin toggle has no real-time effect on new transactions.

- **Severity**: HIGH — a disabled provider (e.g., one under active incident or deliberate shutdown) continues to accept new payment initiations.
- **Source ticket**: FIN-014 (`docs/tickets/FIN-014-payment-provider-health.md`)
- **Status**: Open
- **Owning area**: Billing / Platform Finance
- **Verdict**: Claim CONFIRMED. `is_provider_enabled` (`app/services/payment_provider_health.py:439`) is defined and callable but is never imported or called in `app/routers/billing.py`. The admin toggle endpoint at `app/routers/payment_provider_health.py:155` works correctly; the enforcement gate on the charge path is the missing half.
- **Related tickets**: SEC-004 (payment security controls), GAP-0207 (fraud eval not called), SECOPS-007 (dev/prod parity)

## 2. Current-State Investigation (root cause)

### 2.1 The toggle mechanism — what works

`app/services/payment_provider_health.py:399–436` implements `toggle_provider`, which writes a `CONFIG` row to the `payment_provider_health` DynamoDB table with `enabled: bool`. The companion `is_provider_enabled` at line 439 reads that row:

```python
# app/services/payment_provider_health.py:439
def is_provider_enabled(provider: str) -> bool:
    """Whether a provider is currently accepting new payment initiation."""
    return bool(get_provider_config(provider).get("enabled", True))
```

The default return is `True` — a provider that has never been configured is considered enabled. This is deliberate; the function only returns `False` after an admin explicitly disables it via the toggle endpoint.

The toggle endpoint at `app/routers/payment_provider_health.py:155` is correctly protected by `require_root` and updates the DDB config row. That half of the system is complete.

### 2.2 The charge paths — what is missing

`app/routers/billing.py` contains four live payment-initiation paths:

| Function | Line | Provider | Description |
|---|---|---|---|
| `pay_balance` | 946 | stripe | Off-session PaymentIntent for outstanding balance |
| `charge_once` | 1046 | stripe | Direct one-time charge |
| `create_checkout_session` | 1206 | stripe | Stripe Checkout session |
| `wallet_deposit` | 2316 | stripe | Wallet top-up via PaymentIntent |

Each of these calls `ensure_stripe_configured()` (which merely checks that `stripe.api_key` is set and configures `stripe.api_base` for the mock in dev) and then immediately calls into the Stripe SDK. None of them call `is_provider_enabled("stripe")` first.

```python
# app/routers/billing.py:946-947  (pay_balance — representative example)
def pay_balance(body: PayBalanceReq, ...) -> Dict[str, str]:
    ensure_stripe_configured()          # checks API key only
    user_id, admin_tags = _billing_write_user_context(ctx, user_sub, actor)
    # ... no is_provider_enabled() call before creating PaymentIntent
    pi = stripe.PaymentIntent.create(...)
```

`app/services/payment_provider_health` is not imported anywhere in `app/routers/billing.py`. A global search confirms no call to `is_provider_enabled` anywhere in the billing router:

```
grep -n "is_provider_enabled" app/routers/billing.py
# → (no output)
```

The same absence exists in `app/routers/billing_ccbill.py` and `app/routers/billing_paypal.py`. There are three distinct payment provider routers in the codebase, each handling different provider SDKs, and none of them check provider status before initiating a charge.

### 2.3 The `is_provider_enabled` default-true behaviour

The function at `app/services/payment_provider_health.py:439` defaults to `True` when no CONFIG row exists in DynamoDB:

```python
def is_provider_enabled(provider: str) -> bool:
    return bool(get_provider_config(provider).get("enabled", True))
```

`get_provider_config` performs a DynamoDB `get_item` on `pk=PROVIDER#{provider}`, `sk=CONFIG`. In a fresh dev environment or a new production deployment, no CONFIG rows exist for any provider. The function correctly defaults to `enabled=True` in this case, meaning:
- A provider that has never been explicitly disabled is treated as enabled.
- A provider that has been explicitly disabled by an admin returns `False`.
- The guard only fires when an operator has taken deliberate action.

This design is correct. The only problem is that the guard is never reached.

### 2.4 Runtime behaviour

When an admin calls `POST /ui/admin/payment-providers/stripe/toggle` with `{"enabled": false}`, the `CONFIG` row in DynamoDB is updated to `enabled: false`. However, the next call to `POST /ui/billing/pay-balance` (or any other charge endpoint) proceeds unconditionally. The disable flag is read only by the monitoring dashboards and health-check endpoints — never by the hot path.

In dev mode the Stripe mock (`stripe-mock` on port 12111) always returns `requires_payment_method` for off-session intents, so the bug is not visible in typical dev testing. The disable toggle produces a UI change in the admin panel but causes no observable difference in payment outcomes, which is precisely why the gap was missed during integration testing.

## 3. Impact / Exploit / Blast Radius

**Scenario A — incident mitigation failure**: A Stripe outage triggers a large wave of card errors. The on-call engineer disables Stripe via the admin panel to stop the bleeding. Customers continue submitting payments; each attempt hits the real Stripe API, returns an error, and the billing state machine records a failed payment. User experience degrades and retry storms compound the outage.

**Scenario B — security / compliance**: If a payment provider is disabled because of a regulatory compliance hold or fraud investigation, new charges should stop immediately. With the gate absent, charges continue to flow.

**Scope**:
- All users with autopay or an active billing cycle.
- All four Stripe payment-initiation endpoints in `billing.py`.
- CCBill and PayPal charge paths in their respective routers.
- No financial data is corrupted (the transaction still fails at Stripe), but the intent of the operator toggle is fully defeated.

**Worst case**: A provider disabled due to active fraud or compliance investigation keeps accepting new transactions, creating legal and financial liability.

**Incident prolongation**: During an active outage, a Stripe degradation causes card errors. The ops team disables Stripe to stop retry storms and reduce error noise. Without the gate, the billing endpoints continue to attempt charges, generating Stripe API errors, triggering dunning notices, and potentially incrementing payment failure counters — all of which must be manually reversed after the incident resolves.

**SLA and contractual risk**: If the platform's SLA includes a commitment to halt billing operations when a payment provider is under maintenance, the absence of this gate is a direct SLA violation. Payment processor agreements may also require merchants to implement provider circuit-breakers as part of their integration obligations.

## 4. Fix Design (code-level)

### 4.1 Import the guard in billing.py

Add a single import alongside the existing payment-provider health imports:

```python
# app/routers/billing.py  — add to imports block near line 74
from app.services.payment_provider_health import is_provider_enabled
```

### 4.2 Add guard to each charge function

Each function that initiates an outbound payment call should check provider status immediately after resolving the user context and before any Stripe SDK call. A helper keeps the pattern DRY:

```python
# app/routers/billing.py  — add near top of file after imports
def _require_provider_enabled(provider: str) -> None:
    if not is_provider_enabled(provider):
        raise HTTPException(
            status_code=503,
            detail=f"Payment provider '{provider}' is currently disabled. "
                   "Please try again later or contact support.",
        )
```

Then add one call at the top of each charge path:

```python
# pay_balance (line 946)
def pay_balance(body: PayBalanceReq, ...) -> Dict[str, str]:
    ensure_stripe_configured()
    _require_provider_enabled("stripe")   # ADD
    ...

# charge_once (line 1046)
def charge_once(body: StripeChargeReq, ...) -> Dict[str, Any]:
    ensure_stripe_configured()
    _require_provider_enabled("stripe")   # ADD
    ...

# create_checkout_session (line 1206)
def create_checkout_session(body: BillingCheckoutReq, ...) -> Dict[str, str]:
    ensure_stripe_configured()
    _require_provider_enabled("stripe")   # ADD
    ...

# wallet_deposit (line 2316)
def wallet_deposit(body: WalletDepositReq, ...) -> Dict[str, Any]:
    ensure_stripe_configured()
    _require_provider_enabled("stripe")   # ADD
    ...
```

Apply the same pattern to `app/routers/billing_ccbill.py` and `app/routers/billing_paypal.py` for their respective providers (`"ccbill"`, `"paypal"`).

### 4.3 Dev/Prod parity (SECOPS-007)

`is_provider_enabled` reads from the `payment_provider_health` DynamoDB table via `T.payment_provider_health`. In dev, DynamoDB Local is used; in prod, the real DynamoDB table. The behaviour is identical — the `CONFIG` row either exists (and its `enabled` field is honoured) or does not (default `True`). No mock-specific branch is needed.

The `_require_provider_enabled` helper raises `HTTPException(503, ...)` in both environments. The only dev-specific consideration is that a freshly seeded dev environment has no `CONFIG` rows, so providers default to enabled — consistent with the current behaviour and safe for development.

**Feature flag**: `is_provider_enabled` already contains the only gate needed. No new env var or feature flag is required. If a gradual rollout is needed, the check can be wrapped with `if S.payment_provider_gate_enabled:` temporarily, but given the fix is purely additive (new 503 responses) it should be safe to enable immediately.

### 4.4 Alternatives considered

- **Dependency injection at the router level** (a `Depends(require_provider_enabled)` that reads the provider from the route path): cleaner for future generic provider routing, but requires a significant refactor of the payment-path signatures. Deferred.
- **Middleware**: Would catch all routes, but provider is not always in the URL. Rejected.
- **Per-provider sub-router**: Would cleanly scope the guard, but requires router restructuring. Out of scope for this gap.

### 5.3 Metrics and observability

- Log the disabled-provider rejection at `INFO` level: `logger.info("payment_provider_disabled_rejected", extra={"provider": provider, "user_id": user_id})`.
- Add `audit_event("billing_provider_gate_blocked", user_id, req, outcome="blocked", provider=provider)` to create an audit trail entry for compliance.
- No new DynamoDB reads are introduced beyond the one already present in `get_provider_config`. The read is a single `get_item` (not a query or scan) with key `pk=PROVIDER#stripe`, `sk=CONFIG`. Latency overhead is negligible (~1ms in DynamoDB Local, ~2ms in production with DAX caching).

### 5.4 Caching consideration

`is_provider_enabled` performs a DynamoDB read on every charge request. For platforms with high transaction throughput, this adds a DDB read to every payment path. A simple in-process TTL cache (60 seconds) can reduce this overhead:

```python
import time
_provider_status_cache: dict[str, tuple[bool, float]] = {}
_CACHE_TTL = 60.0

def is_provider_enabled(provider: str) -> bool:
    now = time.monotonic()
    cached = _provider_status_cache.get(provider)
    if cached and now - cached[1] < _CACHE_TTL:
        return cached[0]
    result = bool(get_provider_config(provider).get("enabled", True))
    _provider_status_cache[provider] = (result, now)
    return result
```

The 60-second TTL means a disable action takes up to 60 seconds to propagate across worker processes. This is acceptable for incident-response scenarios. The cache is process-local, so with `--workers 1` (the current dev config) there is no cross-process coherence issue.

### 5.5 Rollout and rollback

- **Effort**: S (< 1 day; isolated changes to 4 functions in 3 files).
- **Rollback**: Removing the `_require_provider_enabled` calls restores the prior behaviour immediately; no migration needed.
- **Risk**: Low. The only new failure mode is a 503 returned to users when a provider is explicitly disabled. This is the intended behaviour and is triggered only by operator action.
- **Sequencing**: Can ship independently. No dependency on other GAP tickets. Pair with GAP-0207 (fraud gate) in the same release for a complete billing-path security hardening.
