# GAP-0367: Title length mismatch causes unhandled 500 — Remediation Write-up

> ~5 pages. Fix-oriented. Claim verified against actual code (no investigation doc exists).

## 1. Summary & Classification

**Severity**: HIGH  
**Source ticket**: VOD-002  
**Owning area**: VOD upload / presign endpoint  
**Status**: Open  
**Claim verdict**: CONFIRMED — the mismatch is present exactly as described.

The `VideoUploadPresignIn` Pydantic model (`app/routers/vod.py`, line 72) declares `title: Optional[str] = Field(default=None, max_length=500)`. The `VideoMetadataModel` that ultimately persists the title to DynamoDB enforces `max_length=256` (confirmed in `app/models_video.py`). A client that submits a title between 257 and 500 characters receives HTTP 201 from the presign endpoint, but any subsequent operation that validates the title through the model will raise an unhandled `ValidationError`, producing an HTTP 500 response. The gap creates a latent server-error vector that is trivially reproducible.

**Related tickets**: VOD-002.  
**No dependency on GAP-0366, GAP-0368, GAP-0369** — this is an independent validation-layer gap.

---

## 2. Current-State Investigation (root cause)

### Conflicting max_length declarations

**`app/routers/vod.py`, line 72** (presign request model — the entry-point validator):
```python
title: Optional[str] = Field(default=None, max_length=500)
```

**`app/models_video.py`** (the canonical `VideoMetadataModel` — the persistence validator):
```python
title: str = Field(..., min_length=1, max_length=256)
```

The two field declarations are owned by different modules and evolved independently. The `VideoUploadPresignIn` model was likely written with a rough "500 characters seems generous" estimate, while `VideoMetadataModel.title` was set to 256 to match typical database column widths and UI truncation budgets. Neither file references the other, so the mismatch went undetected through code review.

### Code path

1. `POST /ui/videos/upload/presign` accepts `VideoUploadPresignIn`. Pydantic validates against `max_length=500`.
2. Inside `vod_presign_upload` (`app/routers/vod.py`, lines 151–158), the router calls `create_video(owner_user_id=..., title=video_title, ...)`. `video_title` is `inp.title or inp.filename`.
3. `create_video` (`app/services/video_metadata_store.py`) instantiates `VideoMetadataModel(title=video_title, ...)`.
4. If `len(video_title) > 256`, Pydantic raises `ValidationError` inside `create_video`, which propagates as an unhandled exception.
5. FastAPI converts the unhandled `ValidationError` to HTTP 500 with a generic error body (in production the detail is suppressed; in dev the stack trace is visible).

### Where the title also gets stored in the ticket record

Additionally, `vod_presign_upload` writes `title: video_title` directly into the DynamoDB ticket item (`T.video_metadata.put_item`, line ~200). The DynamoDB string has no inherent length limit, so the ticket write succeeds. The failure occurs only at the `VideoMetadataModel` instantiation step.

### Dev vs prod parity

Both environments share the same Pydantic models and the same `create_video` call. The 500 fires identically in dev and production. In dev the response includes a Python stack trace; in production the body is `{"detail": "Internal Server Error"}`, making the root cause opaque.

## 3. Impact / Exploit / Blast Radius

### Direct impact

A user or automated client that sends a title with 257–500 characters receives HTTP 500 on the presign step. The critical question is whether orphaned DynamoDB records are left behind. Reading `vod_presign_upload` carefully:

**`app/routers/vod.py`, line 152**: `video = create_video(...)` is called **first**, before the ticket is written.  
**`app/routers/vod.py`, lines 189–208**: The ticket is written to DynamoDB only **after** `create_video` returns.

Inside `create_video`, `VideoMetadataModel` is instantiated before any DynamoDB write. When Pydantic raises `ValidationError` at instantiation time (for title > 256), execution never reaches the DynamoDB `put_item` call. **No orphaned records are created.** The failure is clean from a data-integrity standpoint.

However, the HTTP 500 is returned after the server has already validated auth, content-type, and file size — all of which succeeded. The title validation is the last check before any I/O, so the 500 occurs late in the request lifecycle, making it particularly confusing to diagnose.

**Call trace for a 300-character title**:

```
POST /ui/videos/upload/presign  {title: "A" * 300, content_type: "video/mp4", ...}
  → VideoUploadPresignIn validation: max_length=500 → OK
  → content type allowlist check → OK
  → create_video(title="A" * 300)
    → VideoMetadataModel(title="A" * 300)
      → Pydantic ValidationError: title max_length=256 violated
    ← unhandled exception propagates
  ← FastAPI: HTTP 500 {"detail": "Internal Server Error"}
```

### Usability / API contract consequence

From the caller's perspective, a title of up to 500 characters is explicitly documented as valid by the Pydantic model's `max_length` annotation (and by any auto-generated OpenAPI schema at `GET /openapi.json`). Getting HTTP 500 for a value within the documented envelope is a broken API contract. The OpenAPI spec generated by FastAPI reflects the Pydantic model annotations directly, so the current spec advertises `maxLength: 500` on the `title` field of `VideoUploadPresignIn`. Any SDK or client generated from this spec will permit titles up to 500 characters and will be surprised by the server error.

The correct API contract behaviour for an invalid input is HTTP 422 (Unprocessable Entity) with a structured Pydantic validation error body that identifies the failing field and constraint. After the fix, clients receive this well-formed error and can adjust their input accordingly. HTTP 500 gives clients no actionable information — they cannot distinguish a transient server error from a permanent validation failure, which can lead to unnecessary retries that amplify the 500 rate.

### Security consequence

No direct security exploit. The 500 does not expose sensitive data beyond the stack trace in dev mode. However, a malicious client could deliberately send 257-character titles in a tight loop to trigger repeated 500s. While this is not a denial-of-service vector (the endpoint fails early, before any DynamoDB write), it does pollute error monitoring with spurious server faults, potentially masking genuinely critical errors. In production, where the stack trace is suppressed, the 500 response body is `{"detail": "Internal Server Error"}` — indistinguishable from a real infrastructure fault, which reduces operator confidence in the error-rate signal.

### Blast radius

Every `POST /ui/videos/upload/presign` call with `len(title) > 256`. This includes any client that reads `max_length=500` from the OpenAPI spec and trusts it. In practice, most titles are short, so the blast radius is limited to edge cases: (a) automated ingestion pipelines that pass through long content titles from external catalogues, (b) mobile/web clients that let users enter very long titles, and (c) E2E or integration tests that use randomly generated titles without length bounds. The issue is particularly relevant for clients that do not perform client-side validation and rely entirely on the server's documented limits to reject invalid input.

## 4. Fix Design (code-level)

### Minimal change

**File**: `app/routers/vod.py`, line 72

Change:
```python
title: Optional[str] = Field(default=None, max_length=500)
```
To:
```python
title: Optional[str] = Field(default=None, max_length=256)
```

This aligns the presign input model's limit with the `VideoMetadataModel`'s limit, so Pydantic's request-validation layer returns HTTP 422 (Unprocessable Entity) with a structured error body for over-length titles, rather than propagating to an HTTP 500.

### Why 256, not 500

The canonical `VideoMetadataModel.title` is `max_length=256`. Changing the model to 500 would require a broader impact assessment: every DynamoDB index that stores `title` as a key or sort key, every search/typeahead field, every third-party integration that consumes the title (e.g., Stripe product names for pay-per-view charges, ad copy that includes video titles), and every UI component that truncates or displays the title. DynamoDB itself does not enforce string field length, but string keys used in GSI sort expressions do have effective size constraints. UI components such as `<h1>` headings and sidebar previews typically budget for a maximum of 60–80 visible characters. Lowering the input limit to 256 is the safe, conservative choice that matches the already-deployed persistence model without any downstream audit.

### SECOPS-007 dev/prod parity

Pure model change — no AWS path is involved. Dev and production share the same request model, so the fix applies to both simultaneously. No conditional or feature flag needed.

### Backward compatibility

Clients currently sending titles > 256 characters will start receiving HTTP 422 instead of HTTP 500. HTTP 422 is the correct status for invalid input; clients should already be handling it. This is a breaking change only for clients that relied on the (broken) `max_length=500` envelope, which they should not have.

### Alternatives considered

- **Raise `VideoMetadataModel.title` max_length to 500**: Requires auditing all downstream consumers of `title` for safe handling of longer strings. Rejected as scope-creep for a single router fix.
- **Truncate to 256 inside the endpoint**: Silent data loss is worse than a clear validation error. Rejected.
- **Keep 500 in model, add explicit truncation guard in `create_video`**: Defeats the purpose of declarative validation. Rejected.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

Create `tests/test_vod_title_validation.py`:

```python
"""GAP-0367 regression: presign endpoint must reject titles over 256 chars with 422."""
import pytest
from unittest.mock import patch, MagicMock
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

def _session():
    return {"user_sub": "u_test", "role": "USER", "admin_profile": None}

@pytest.fixture(autouse=True)
def mock_session():
    with patch("app.routers.vod.require_ui_session", return_value=_session()):
        yield

def test_title_exactly_256_chars_is_accepted():
    """256-char title must return 422 only if content_type invalid; with valid ct, 200/201."""
    # This test verifies we don't over-restrict
    with (
        patch("app.routers.vod.create_video", return_value=MagicMock(id="vid_001")),
        patch("app.routers.vod.T"),
        patch("app.routers.vod._s3"),
    ):
        resp = client.post(
            "/ui/videos/upload/presign",
            json={
                "filename": "test.mp4",
                "content_type": "video/mp4",
                "file_size_bytes": 1024,
                "title": "A" * 256,
            },
        )
    # Should NOT be 422 (256 is within limit)
    assert resp.status_code != 422 or "title" not in resp.text

def test_title_over_256_chars_returns_422():
    """FAILS before fix (returns 500), PASSES after fix (returns 422)."""
    resp = client.post(
        "/ui/videos/upload/presign",
        json={
            "filename": "test.mp4",
            "content_type": "video/mp4",
            "file_size_bytes": 1024,
            "title": "B" * 257,
        },
    )
    assert resp.status_code == 422, (
        f"Expected 422 for title > 256 chars, got {resp.status_code}. "
        "This is GAP-0367: max_length=500 in presign model allows titles the "
        "VideoMetadataModel rejects with a 500."
    )
    body = resp.json()
    # Should explain the title constraint, not be a generic 500
    assert resp.status_code != 500

def test_title_500_chars_returns_422():
    """Explicitly tests the old permitted-but-broken upper bound."""
    resp = client.post(
        "/ui/videos/upload/presign",
        json={
            "filename": "test.mp4",
            "content_type": "video/mp4",
            "file_size_bytes": 1024,
            "title": "C" * 500,
        },
    )
    assert resp.status_code == 422
```

**Before fix**: `test_title_over_256_chars_returns_422` gets `status_code == 500` because the invalid title passes the input model (max_length=500), reaches `create_video`, causes `VideoMetadataModel` instantiation to raise a Pydantic `ValidationError`, and FastAPI converts that unhandled exception to HTTP 500. The assertion `assert resp.status_code == 422` fails.

**After fix**: The input model now rejects a 257-character title at the request-parsing stage with HTTP 422. The `create_video` call is never reached. The assertion passes.

The `test_title_exactly_256_chars_is_accepted` test acts as a boundary test to confirm the fix does not over-restrict. It verifies that the threshold is correctly set at 256 (inclusive) rather than, for example, 255.

### OpenAPI documentation side-effect

The fix automatically updates the OpenAPI schema at `GET /openapi.json`: the `title` field in `VideoUploadPresignIn` will report `maxLength: 256` instead of `maxLength: 500`. Any client generated from the spec will automatically pick up the correct limit.

### Rollout

- **Effort**: S (single-line change + tests).
- **Risk**: Very low. The only clients affected are those sending 257–500 character titles, who were already receiving HTTP 500. They will now receive HTTP 422, which is strictly more informative and correctly characterises the error as a client-side input problem rather than a server fault.
- **Sequencing**: Can ship independently of all other VOD GAPs. This fix has no dependencies and no interaction with the state-machine bugs in GAP-0366/0368/0369.
- **Rollback**: Revert the one-line change. No data migration needed — the bug never successfully writes any record for the failing case, so there is no corrupted data to clean up.

### Defensive audit recommendation

The same class of mismatch (input model `max_length` greater than persistence model `max_length`) could exist in other creation endpoints. A targeted audit should compare `max_length` annotations in all `*In` request models under `app/routers/` against the corresponding persistence model definitions in `app/models_video.py`, `app/models.py`, and related files. Particular attention should be paid to `description` (currently `max_length=5000` in `VideoUploadPresignIn` vs. the `VideoMetadataModel` field), which may have a similar mismatch. This audit should be included as part of the GAP-0367 fix PR review checklist.
