# GAP-0326: No toll-fraud global spending cap (SEC-014) — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code before writing; cites `file:line`.

## 1. Summary & Classification

**Severity**: HIGH
**Source ticket**: PLATFORM-007
**Owning area**: SMS delivery infrastructure / financial controls
**Status**: Open — no fix present in current codebase

**Plain-English statement**: The SMS delivery service has a per-phone-number daily message count limit, but there is no platform-wide ceiling on total daily SMS spend. An attacker who controls or can enumerate many phone numbers — or who triggers the system to send to many distinct recipients — can cause arbitrarily large AWS SNS SMS charges without any server-side kill switch. SEC-014 mandates a configurable global daily cost cap (`SMS_DAILY_COST_CAP_USD`) that halts all outbound SMS once the estimated platform spend exceeds the threshold.

**Verdict**: Claim confirmed. The `sms_daily_limit_per_number` setting at `app/core/settings.py:201` and the corresponding `sms_daily_limit_exceeded()` check at `app/services/sms_delivery.py:331–333` both operate on a single phone number in isolation. No global-spend accumulator, no global cap setting, and no global-cap check exist anywhere in the codebase.

**Related tickets**: SEC-014 (security requirement), GAP-0039 (per-account rate limits), PLATFORM-007 (SMS delivery tracking).

## 2. Current-State Investigation (root cause)

### Settings — only a per-number limit exists

`app/core/settings.py:196–203`:
```python
# SMS Delivery Tracking (PLATFORM-007)
sms_daily_limit_per_number: int = int(os.environ.get("SMS_DAILY_LIMIT_PER_NUMBER", "10"))
sms_suppression_enabled: bool = ...
sms_cost_per_segment_usd: float = float(os.environ.get("SMS_COST_PER_SEGMENT_USD", "0.00645"))
```

There is no `SMS_DAILY_COST_CAP_USD` or any equivalent setting. The cost-per-segment constant is present (used only for reporting in `get_sms_delivery_stats()`), but it is never consulted on the hot send path.

### `send_sms()` — the only enforced guard is per-number

`app/services/sms_delivery.py:174–256` is the consolidated production send function. The function performs, in order:

1. Suppression check via `is_sms_suppressed(phone)` (`sms_delivery.py:200–206`)
2. Per-number daily limit via `sms_daily_limit_exceeded(phone)` (`sms_delivery.py:209–216`)
3. Dev-mode short-circuit (`sms_delivery.py:219–231`)
4. Real SNS publish (`sms_delivery.py:238–256`)

`sms_daily_limit_exceeded` (`sms_delivery.py:331–333`):
```python
def sms_daily_limit_exceeded(phone: str) -> bool:
    return sms_daily_count(phone) >= S.sms_daily_limit_per_number
```

`sms_daily_count` (`sms_delivery.py:316–328`) reads from `DAILY#{phone}` / `DAY#{day_key}` — a per-number partition. There is no global counter item and no global check.

### Global segment counter exists only in reporting

`get_sms_delivery_stats()` (`sms_delivery.py:347–420`) paginates the `ByStatus` GSI and sums `total_segments`, then multiplies by `sms_cost_per_segment_usd` to produce `estimated_cost_usd`. This value is returned to admin dashboards but is never read by `send_sms()`.

### Toll-fraud mechanics

A toll-fraud pump attack works by routing SMS OTP or alert messages to premium-rate short-code or internationally-routed numbers controlled by the attacker. With 10 messages per number per day and no global cap, an attacker can fan out across as many phone numbers as they can trigger in the system. At $0.00645/segment × 10 messages/number × N numbers, cost scales linearly with N, with no hard stop anywhere in the server.

## 3. Impact / Exploit / Blast Radius

**Who is affected**: The platform operator (AWS billing). No user data is compromised, but a successful attack can produce a five- or six-figure AWS bill in a single day.

**Concrete exploit walkthrough**:
1. Attacker creates multiple accounts or uses an account they control with access to any feature that sends SMS (alert preferences, MFA enrollment, admin test-send endpoint).
2. For each account, they configure phone numbers they either own or that forward to premium-rate routes.
3. They trigger alert-based SMS sends (e.g., by generating login-failure events at scale, or by using the admin SMS test endpoint if accessible).
4. Per-number limit of 10 is hit, but attacker rotates to a fresh number.
5. At $0.00645/segment × 10 segments/number, each number costs $0.0645/day. With 100,000 numbers (achievable via automated registration), the daily bill reaches $6,450. With premium-rate international routes, actual carrier cost is often 10–100× higher than the SNS price.
6. No server-side check stops the spend from climbing.

**Financial worst case**: Uncapped. AWS SNS does not have an automatic per-account SMS spend limit that matches arbitrary traffic. AWS does offer an account-level monthly SMS spend limit, but it must be manually set in the AWS Console and is not surfaced through this codebase.

**Availability impact**: At sufficient scale, SNS soft limits can throttle the account, degrading legitimate SMS for all users.

**Compliance**: SEC-014 explicitly mandates a configurable `SMS_DAILY_COST_CAP_USD` kill switch. Absence means a compliance gap against an existing internal security requirement.

## 4. Fix Design (code-level)

### 4.1 Add the global-cap setting

`app/core/settings.py` — add immediately after `sms_cost_per_segment_usd`:

```python
# Global platform-wide daily SMS spend cap (0 = disabled).
# When the estimated cumulative daily segment cost exceeds this threshold,
# send_sms() returns status="rate_limited" for all subsequent sends.
sms_daily_cost_cap_usd: float = float(
    os.environ.get("SMS_DAILY_COST_CAP_USD", "0")
)
```

A default of `0` means "disabled", ensuring backward compatibility. Production deployments set this to a meaningful value (e.g., `50.00` for $50/day).

### 4.2 Add the global segment accumulator

`app/services/sms_delivery.py` — add two functions after `sms_daily_limit_exceeded`:

```python
# DynamoDB key for the global daily segment counter
_GLOBAL_DAILY_PK = "DAILY#GLOBAL"

def _global_daily_segments() -> int:
    """Return today's total platform-wide SMS segment count."""
    day_key = now_ts() // 86400
    try:
        resp = T.sms_delivery.get_item(
            Key={"pk": _GLOBAL_DAILY_PK, "sk": f"DAY#{day_key}"},
            ProjectionExpression="#c",
            ExpressionAttributeNames={"#c": "count"},
        )
        item = resp.get("Item")
        return int(item.get("count", 0)) if item else 0
    except Exception:
        return 0  # Fail open: don't block sends on counter read failure


def sms_global_cost_cap_exceeded() -> bool:
    """Return True if platform-wide daily SMS cost estimate has hit the cap."""
    cap = S.sms_daily_cost_cap_usd
    if not cap or cap <= 0:
        return False
    segments = _global_daily_segments()
    estimated = segments * S.sms_cost_per_segment_usd
    return estimated >= cap
```

### 4.3 Increment the global counter on successful send

In `record_sms_sent()` (`sms_delivery.py:41–77`), add after the per-number `DAILY#{phone}` increment:

```python
# Increment global daily segment counter
segs = _estimate_segments(body)
day_key = ts // 86400
try:
    T.sms_delivery.update_item(
        Key={"pk": _GLOBAL_DAILY_PK, "sk": f"DAY#{day_key}"},
        UpdateExpression=(
            "SET #c = if_not_exists(#c, :z) + :segs, "
            "#ts = :ts, ttl_epoch = :ttl"
        ),
        ExpressionAttributeNames={"#c": "count", "#ts": "updated_at"},
        ExpressionAttributeValues={
            ":segs": segs,
            ":z": 0,
            ":ts": ts,
            ":ttl": ts + 7 * 86400,
        },
    )
except Exception:
    logger.exception("Failed to increment global SMS segment counter")
```

Note: `record_sms_dev_logged()` should also increment the global counter so that dev mode faithfully exercises the cap logic. A separate `DAILY#GLOBAL` counter in dev mode isolates dev traffic from prod.

### 4.4 Wire the cap check into `send_sms()`

In `send_sms()` (`sms_delivery.py:174`), add the global cap check **before** the per-number limit check so that the cheapest guard runs first:

```python
# Global platform-wide cost cap (SEC-014).
if S.sms_daily_cost_cap_usd and S.sms_daily_cost_cap_usd > 0:
    try:
        if sms_global_cost_cap_exceeded():
            SMS_RATE_LIMITED.inc()
            logger.warning(
                "SMS blocked: global daily cost cap exceeded "
                "(cap=%.2f USD)", S.sms_daily_cost_cap_usd
            )
            return {"number": phone, "message_id": None, "status": "rate_limited"}
    except Exception:
        logger.exception("Global cost cap check failed; proceeding")
```

Position: between the suppression check and the per-number limit check (after line 216 in the current file).

### 4.5 Dev/Prod parity (SECOPS-007)

The global cap check calls `T.sms_delivery.get_item()` against `T.sms_delivery`, which in dev mode is DynamoDB Local (port 8001) and in production is real AWS DynamoDB. The code path is identical; no mocking is needed. The global counter is incremented via `record_sms_sent()`, which is already called in both dev (`record_sms_dev_logged` path) and prod (real SNS path). The new `sms_daily_cost_cap_usd` setting reads from an environment variable, so local `.env.local` can set `SMS_DAILY_COST_CAP_USD=50` and production secrets manager can supply the production value. The fail-open pattern on DDB read errors is consistent with the existing per-number limit (which also uses a `try/except` block that logs and continues on failure).

### 4.6 Backward compatibility and alternatives

Setting `SMS_DAILY_COST_CAP_USD=0` (the default) disables the cap entirely, so existing deployments without the variable set are unaffected. The alternative of using AWS SNS account-level spend limits was rejected because it requires manual AWS Console configuration outside the deployment pipeline and cannot be changed dynamically per environment. A per-user daily limit (rather than a global one) was also considered but rejected because toll-fraud attacks work across many user accounts; only a global ceiling stops the attack.

### Regression test (pytest offline)

Add to `tests/test_sms_delivery.py`:

```python
import pytest
from unittest.mock import patch, MagicMock
from app.services import sms_delivery


def _make_send_context(cap_usd: float, existing_segments: int):
    """Return a context manager dict for patching."""
    return {
        "app.services.sms_delivery.S": MagicMock(
            dev_mode=False,
            alerts_sms_enabled=True,

        ),
        "app.services.sms_delivery._global_daily_segments": MagicMock(
            return_value=existing_segments
        ),

class TestGlobalCostCap:
    """GAP-0326: global SMS cost cap must block sends when threshold is exceeded."""

    def test_cap_disabled_when_zero(self, mocker):
        """cap=0 means disabled; sends proceed regardless of segment count."""
        # Patch: 10,000 segments already sent, but cap=0 (disabled)
        mocker.patch("app.services.sms_delivery._global_daily_segments",
                     return_value=10_000)
        mocker.patch.object(sms_delivery.S, "sms_daily_cost_cap_usd", 0.0)
        mocker.patch.object(sms_delivery.S, "dev_mode", True)
        result = sms_delivery.send_sms("+15551234567", "hello")
        assert result["status"] == "dev_logged"  # not rate_limited

    def test_cap_blocks_when_exceeded(self, mocker):
        """FAILS before fix: cap=$0.50, 100 segments already sent at $0.00645 ea = $0.645 > cap."""
        mocker.patch("app.services.sms_delivery._global_daily_segments",
                     return_value=100)
        mocker.patch.object(sms_delivery.S, "sms_daily_cost_cap_usd", 0.50)
        mocker.patch.object(sms_delivery.S, "sms_cost_per_segment_usd", 0.00645)
        mocker.patch.object(sms_delivery.S, "dev_mode", False)
        mocker.patch.object(sms_delivery.S, "alerts_sms_enabled", True)
        mocker.patch.object(sms_delivery.S, "sms_suppression_enabled", False)
        mocker.patch.object(sms_delivery.S, "sms_daily_limit_per_number", 1000)
        result = sms_delivery.send_sms("+15551234567", "hello")
        # BEFORE fix: status="sent" (no cap check) → FAIL
        # AFTER fix:  status="rate_limited"         → PASS
        assert result["status"] == "rate_limited"

    def test_cap_allows_when_under(self, mocker):
        """Under cap: send proceeds normally."""
        mocker.patch("app.services.sms_delivery._global_daily_segments",
                     return_value=10)
        mocker.patch.object(sms_delivery.S, "sms_daily_cost_cap_usd", 1.00)
        mocker.patch.object(sms_delivery.S, "sms_cost_per_segment_usd", 0.00645)
        mocker.patch.object(sms_delivery.S, "dev_mode", True)
        result = sms_delivery.send_sms("+15551234567", "hello")
        assert result["status"] == "dev_logged"
```

**Fails before fix**: `test_cap_blocks_when_exceeded` returns `"sent"` because `send_sms()` has no global cap check.
**Passes after fix**: the new `sms_global_cost_cap_exceeded()` guard returns `True` and the function returns `"rate_limited"`.

### Manual QA steps

1. Set `SMS_DAILY_COST_CAP_USD=0.10` in `.env.local` and restart the backend.
2. Send 16 SMS messages (16 × $0.00645 = $0.1032 > $0.10) using the admin SMS test endpoint while watching `status` in the response.
3. The 16th send should return `{"status": "rate_limited"}`.
4. Check the backend log for the `WARNING: SMS blocked: global daily cost cap exceeded` message.
5. Increment to $0.50 cap and confirm sends resume (global counter resets at midnight via the `DAY#{day_key}` TTL-bounded key).

### Observability

The existing `SMS_RATE_LIMITED` Prometheus counter (`app/metrics.py`) is incremented on cap hit (same as per-number rate limit). An alert on `sms_rate_limited_total` spike catches both per-number and global-cap events. A separate label (`reason="global_cap"`) should be added to distinguish them in dashboards.

### Rollout

- **Effort**: M (medium — two new functions, one setting, one atomic DDB write per send)
- **Risk**: Low. Fail-open on DDB read errors means the cap cannot block legitimate traffic due to transient DDB failures.
- **Rollback**: Set `SMS_DAILY_COST_CAP_USD=0` or remove the variable; the check becomes a no-op immediately.
- **Sequencing**: Deploy backend change first; set cap value in production environment variables via secrets manager; monitor `sms_rate_limited_total` for the first 24 hours.
- **Migration**: No DDB schema changes are required. The `DAILY#GLOBAL` partition is a new key pattern within the existing `sms_delivery` table; it coexists with all current key patterns without migration.
