# GAP-0273: `kyc.case.needs_info` Event Never Dispatched — Remediation Write-up

> Claim status: **CLAIM OK** — confirmed by code inspection. `request_more_info()` in
> `app/services/kyc_cases.py:524–584` writes the DynamoDB update and returns without calling
> `_emit_kyc_event_safe`. The `kyc.case.needs_info` event is registered in the webhook registry
> and has all notification infrastructure wired (in-app alert title, email subject, SSE handler),
> but the dispatch call is absent from both the service layer and the router.

---

## 1. Summary & Classification

**Bug/Gap**: When an admin requests additional information from a user during KYC review via
`POST /v1/kyc/cases/admin/cases/{case_id}/request-info`, the `kyc.case.needs_info` webhook
event is never emitted. The case status transitions to `needs_more_info` and the DynamoDB item
is updated correctly, but the user receives no in-app notification, no email, and no webhook
delivery to tell them what information is needed.

**Severity**: HIGH — KYC-011. In a real KYC workflow, the `needs_more_info` state is the
primary feedback channel between the reviewer and the applicant. Without the event, the user
has no way to know their case is stalled awaiting their response unless they poll manually.
This can cause significant review queue backlog and user frustration, and may constitute a
regulatory non-compliance (timely communication of case status is required by many AML/KYC
frameworks).

**Verdict**: Confirmed. The gap is in `KycCaseStore.request_more_info()` at
`app/services/kyc_cases.py:524–584`. The function ends at line 584 with
`return self.get_case(case_id)` after a successful `update_item`, with no event emission.
The router handler `admin_request_more_info` at `app/routers/kyc_cases.py:1086–1162` also
contains no `_emit_kyc_event_safe` call.

**Related tickets**: GAP-0272 (`kyc.case.approved/rejected`), GAP-0274 (`kyc.case.created`),
KYC-011, SECOPS-007.

## 2. Current-State Investigation (Root Cause)

### The service-layer function

`app/services/kyc_cases.py:560–584` (inside `request_more_info`):

```python
        try:
            self._table.update_item(
                Key={"pk": _case_pk(case_id), "sk": "META"},
                UpdateExpression=(
                    "SET #status=:status, review=:review, updated_at=:updated_at, version=:version, "
                    "gsi_owner_sk=:gsi_owner_sk, gsi_status_pk=:gsi_status_pk, gsi_status_sk=:gsi_status_sk"
                ),
                ExpressionAttributeNames={"#status": "status"},
                ExpressionAttributeValues={
                    ":status": "needs_more_info",
                    ...
                },
                ConditionExpression="version = :expected_version",
            )
        except ClientError as exc:
            if _is_conditional_conflict(exc):
                raise KycCaseConflictError("kyc_case_update_conflict") from exc
            raise
        return self.get_case(case_id)   # line 584 — no event emitted
```

The function also stores the requested items and note in the `review` map:

```python
        review["requested_items"] = [str(item) for item in requested_items]
        review["last_request_info_note"] = str(note)
```

These fields are exactly the payload that `kyc.case.needs_info` consumers expect
(`requested_items`, `note`) — they are computed but never forwarded to `emit_kyc_event`.

### The correct pattern (submit_case)

`app/services/kyc_cases.py:412–417` shows the established pattern:

```python
        _emit_kyc_event_safe(
            event="kyc.case.submitted",
            user_sub=owner_sub,
            case_id=case_id,
            submitted_at=ts,
        )
        return self.get_case(case_id)
```

`request_more_info` follows the exact same structure (DDB update → return case) but is
missing the `_emit_kyc_event_safe` call.

### Router also silent

`app/routers/kyc_cases.py:1086–1162` (`admin_request_more_info`) calls
`STORE.request_more_info(...)` at line 1123, then calls `_ensure_request_info_ticket_message`
and `_audit_state_transition`, but never calls `_emit_kyc_event_safe`.

The `_emit_kyc_event_safe` helper is defined at
`app/services/kyc_cases.py:17–27` and is imported only once outside tests
(via the `kyc_webhooks` lazy import chain); the router does not import it at all.

### Notification infrastructure is complete

`app/services/kyc_webhooks.py` already handles `kyc.case.needs_info`:

- Line 42: `"kyc.case.needs_info": "Additional information needed"` (in-app title).
- Line 62: `"kyc.case.needs_info": "Additional information needed for your verification"` (email subject).
- Lines 335–342: `emit_kyc_event` dispatcher handles the event, writes in-app alert, sends email.

Everything is wired; the only missing piece is the call site in `request_more_info`.

## 3. Impact / Exploit / Blast Radius

**Direct user impact**: A user whose KYC application enters `needs_more_info` status
receives zero notification. They do not know:
  - That their application is blocked.
  - What documents or information are specifically required.
  - That they need to take action before the review window expires.

**Review queue bottleneck**: Without notification, users do not re-submit, and the case
remains in `needs_more_info` indefinitely. This clogs the admin review queue with stale
cases (visible in the `stale_queue_count` metric in `get_metrics_snapshot`).

**Webhook integrations**: External compliance systems subscribed to `kyc.case.needs_info`
webhooks (e.g., a CRM that tracks outstanding KYC items) receive no signal. Automated
follow-up campaigns or customer-success workflows fail silently.

**Email channel**: The `needs_info` email is configured in `_EMAIL_SUBJECTS` and is the
most actionable of all KYC emails (it tells the user exactly what to provide). Its absence
is arguably a more severe UX gap than the missing approval/rejection emails.

**Blast radius**: All KYC cases that transition to `needs_more_info` after go-live — 100%
of "request info" admin actions are affected, for every user, with no exception path.

## 4. Fix Design (Code-Level)

### Minimal targeted fix

Add `_emit_kyc_event_safe` call in `request_more_info()`, immediately after the successful
DDB update and before the return:

**File**: `app/services/kyc_cases.py`

```python
# Locate the end of the try/except block in request_more_info():
        except ClientError as exc:
            if _is_conditional_conflict(exc):
                raise KycCaseConflictError("kyc_case_update_conflict") from exc
            raise

# ADD immediately before `return self.get_case(case_id)`:
        _emit_kyc_event_safe(
            event="kyc.case.needs_info",
            user_sub=str(existing.get("user_sub") or ""),
            case_id=case_id,
            requested_items=requested_items,
            note=note,
            requested_by=admin_sub,
            requested_at=ts,
        )
        return self.get_case(case_id)
```

All required variables (`existing`, `case_id`, `requested_items`, `note`, `admin_sub`, `ts`)
are already in scope at the end of `request_more_info`. `existing` is bound at line 534
(`existing = self.get_case(case_id)`). The `user_sub` of the case is `existing["user_sub"]`.

The `_emit_kyc_event_safe` wrapper serializes list values (`requested_items`) as a
comma-joined string before passing to `write_alert` (see `kyc_webhooks.py:226–227`) so no
special handling is needed for the list argument.

### Idempotency consideration

The function has an early-return path at lines 539–543:

```python
        if (
            str(existing.get("status") or "") == "needs_more_info"
            and str(review.get("last_request_info_hash") or "") == request_hash
        ):
            return existing
```

This idempotent path returns `existing` **without** a DDB write and thus must **not** emit
an event (it's a replay-safe guard). The fix must be placed **after** the try/except block,
not at the function's entry, to preserve this guarantee.

### Dev/Prod parity (SECOPS-007)

Same analysis as GAP-0272: `_emit_kyc_event_safe` is unconditionally dev/prod parity-correct.
In dev mode the webhook delivery is a no-op (no registered endpoints in a fresh dev stack),
and the in-app alert writes to DynamoDB Local on port 8001. No AWS-specific path is touched.
No feature flag is required.

### Alternative considered

Placing the emit call in the **router** (`admin_request_more_info` at `kyc_cases.py:1086`)
after `STORE.request_more_info(...)` returns. This would work but is inconsistent with the
`submit_case` pattern, which emits from the service layer. Emitting from the service layer
is preferable because it keeps notification dispatch co-located with the state transition and
ensures the event fires even if the router is refactored or the function is called directly
from other service code (e.g., ticket sync events via `sync_from_ticket_event`).

## 5. Testing, Verification & Rollout

### Regression test (fails-before / passes-after)

Add to `tests/test_kyc_cases_store.py`:

```python
class TestRequestMoreInfoEmitsEvent:
    """GAP-0273: request_more_info must emit kyc.case.needs_info event."""

    def _make_store_under_review(self):
        from app.services.kyc_cases import KycCaseStore
        store = KycCaseStore(_table=_FakeTable())
        case = store.create_case(user_sub="usr_alice")
        # Manually set status to under_review
        key = ("KYC#" + case["kyc_case_id"], "META")
        store._table.items[key]["status"] = "under_review"
        return store, case["kyc_case_id"], case["user_sub"]

    def test_needs_info_event_emitted(self):
        store, case_id, user_sub = self._make_store_under_review()
        version = int(store.get_case(case_id)["version"])

        emitted = []
        import app.services.kyc_cases as svc
        with patch.object(svc, "_emit_kyc_event_safe", side_effect=lambda **kw: emitted.append(kw)):
            store.request_more_info(
                case_id=case_id,
                expected_version=version,
                admin_sub="admin_charlie",
                requested_items=["proof_of_address", "selfie_retake"],
                note="Documents are unclear",
                request_hash="hashxyz",
            )

        assert len(emitted) == 1, (
            f"Expected 1 event, got {len(emitted)}. "
            f"GAP-0273: kyc.case.needs_info was never dispatched before fix."
        )
        ev = emitted[0]
        assert ev["event"] == "kyc.case.needs_info"
        assert ev["user_sub"] == user_sub
        assert ev["case_id"] == case_id
        assert "proof_of_address" in str(ev.get("requested_items", ""))

    def test_idempotent_re_request_does_not_emit_again(self):
        store, case_id, user_sub = self._make_store_under_review()
        version = int(store.get_case(case_id)["version"])

        emitted = []
        import app.services.kyc_cases as svc
        with patch.object(svc, "_emit_kyc_event_safe", side_effect=lambda **kw: emitted.append(kw)):
            store.request_more_info(
                case_id=case_id, expected_version=version,
                admin_sub="admin_charlie",
                requested_items=["selfie_retake"],
                note="Please retake selfie",
                request_hash="hash_repeat",
            )
            # Idempotent: same hash, case already in needs_more_info
            store.request_more_info(
                case_id=case_id, expected_version=version + 1,
                admin_sub="admin_charlie",
                requested_items=["selfie_retake"],
                note="Please retake selfie",
                request_hash="hash_repeat",
            )

        assert len(emitted) == 1, "Idempotent re-request must not emit a second event"

    def test_event_carries_requested_items_and_note(self):
        store, case_id, user_sub = self._make_store_under_review()
        version = int(store.get_case(case_id)["version"])
        items = ["utility_bill", "bank_statement"]
        note_text = "Need two forms of address proof"

        emitted = []
        import app.services.kyc_cases as svc
        with patch.object(svc, "_emit_kyc_event_safe", side_effect=lambda **kw: emitted.append(kw)):
            store.request_more_info(
                case_id=case_id, expected_version=version,
                admin_sub="admin_charlie",
                requested_items=items, note=note_text, request_hash="hash_adr",
            )

        assert emitted[0]["note"] == note_text
```

**Before fix**: `assert len(emitted) == 1` fails with `0`.
**After fix**: all assertions pass.
