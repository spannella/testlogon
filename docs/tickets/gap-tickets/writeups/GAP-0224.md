# GAP-0224: Host Inventory Not Cleaned Up on Instance Termination — Remediation Write-up

> Source ticket: INFRA-003 · Severity: HIGH · Effort: S · Status: Open

## 1. Summary & Classification

**Bug statement.** When a user terminates an EC2 instance via `terminate_instance()` in `app/services/ec2_launcher.py`, the corresponding host-inventory entry — if one was created by the auto-registration path (GAP-0223) — is never deleted. The `host_id` stored on the instance record is retrieved at no point during termination; `host_inventory.delete_host()` is never called. The stale host entry persists indefinitely in the user's host inventory after the instance is gone, pointing at an IP address that no longer exists.

**Verdict (from investigation):** Confirmed. The ticket claim is accurate. `terminate_instance()` (lines 320–355) performs a DDB status update, disassociates the security group (lines 343–350), logs the event, and returns — without any call to `host_inventory.delete_host()`. The `item["host_id"]` field is never read during termination.

**Severity and area.** HIGH / Infrastructure / Host Inventory Integrity. Stale host entries accumulate over time, approach the per-user host limit, and expose phantom connection targets in the SSH terminal quick-connect picker. Users trying to SSH into a terminated instance receive connection errors with no explanation that the underlying instance no longer exists.

**Related tickets.** INFRA-003 (EC2 launcher spec), GAP-0223 (auto-registration — the source of the host entries that must be cleaned up), GAP-0222 (real EC2 launch path — must work for the full lifecycle to be correct in production).

## 2. Current-State Investigation (root cause)

### `terminate_instance()` at lines 320–355

```python
def terminate_instance(user_sub: str, instance_id: str) -> Dict[str, Any]:
    item = get_instance(user_sub, instance_id)
    if not item:
        raise InstanceNotFound(f"Instance {instance_id} not found")

    if item["status"] in ("terminated", "terminating"):
        raise InvalidInstanceState(...)

    ec2_id = item["ec2_instance_id"]
    if S.ec2_mock_enabled:
        _mock_store.terminate(ec2_id)

    now = now_ts()
    T.ec2_instances.update_item(
        Key={"user_sub": user_sub, "sk": f"INSTANCE#{instance_id}"},
        UpdateExpression="SET #st = :st, terminated_at = :ta",
        ...
    )

    # Disassociate from its security group so the SG can be deleted (INFRA-009)
    sg_id = item.get("security_group_id")
    if sg_id:
        try:
            from app.services.security_groups import disassociate_instance
            disassociate_instance(user_sub, sg_id, instance_id)
        except Exception:
            logger.exception("sg_disassociate_failed ...")

    item["status"] = "terminated"
    item["terminated_at"] = now
    logger.info("ec2_terminated user_sub=%s instance_id=%s", user_sub, instance_id)
    return item
```

The function retrieves `item` at line 322 which contains `host_id`. However `item.get("host_id")` is never read anywhere in the function. The security-group disassociation block (lines 343–350) provides the exact pattern that should be mirrored for host inventory cleanup.

### `host_inventory.delete_host()` signature

`app/services/host_inventory.py:324–331`:

```python
def delete_host(user_sub: str, host_id: str) -> bool:
    """Hard-delete a host entry. Returns True if it existed."""
    raw = _get_raw(user_sub, host_id)
    if not raw:
        return False
    T.host_inventory.delete_item(Key={"user_sub": user_sub, "sk": _sk(host_id)})
    _audit("remote_host.deleted", user_sub, host_id=host_id, protocol=raw.get("protocol", ""))
    return True
```

The function is safe to call with a `host_id` that does not exist (returns `False` without raising). It also emits an audit event, providing a complete deletion trail.

### How stale entries accumulate

Every instance that is auto-registered (post GAP-0223 fix) produces one host-inventory entry. Each termination leaves that entry orphaned. A user who repeatedly launches and terminates instances (e.g., one per day for a month) accumulates 30 orphaned entries, each pointing at an IP that AWS has likely reassigned to another customer's instance. The per-user host limit (`S.host_inventory_max_per_user`) will be reached, blocking future auto-registrations and preventing the user from adding legitimate hosts.

### Auto-terminate path is also affected

The background task `check_idle_instances()` at line 385 calls `terminate_instance(item["user_sub"], item["instance_id"])` for each idle instance (line 406). Because `terminate_instance` does not clean up the host inventory, auto-terminations also leave orphaned entries. Since auto-termination runs silently on a 5-minute polling cycle, these entries accumulate with no user-visible trigger.

### Dev vs prod behaviour

Identical in both environments. In dev, mock instances are terminated and the mock store updates the in-memory status, but the DDB record is still updated and the host inventory cleanup is still skipped. In production with real EC2 (post GAP-0222 fix), the same code path runs. The stale host entries are equally problematic in both environments because they consume host inventory slots and pollute the SSH terminal picker.

## 3. Impact / Exploit / Blast Radius

### User-experience degradation

The SSH terminal quick-connect picker (INFRA-001) surfaces all entries in `T.host_inventory`. After each terminated instance, a dead entry labelled `"<instance_label> (EC2)"` remains in the picker. Clicking it produces an SSH connection timeout. Users with many past instances have a confusing list of non-functional hosts mixed with their live ones.

### Host inventory limit exhaustion

`S.host_inventory_max_per_user` caps the number of hosts a user can save. Once reached, `host_inventory.create_host()` raises `HostLimitExceeded`, which prevents further auto-registration (GAP-0223 fix). A power user who launches and terminates 20 instances will hit the limit and be unable to register new hosts — even manually. This is an effective resource denial caused by the cleanup gap.

### IP address reuse

AWS recycles Elastic IPs and auto-assigned public IPs. A stale host entry may point at an IP that AWS has since assigned to a different customer's instance. If the user stored SSH credentials associated with that host in a connected workflow (e.g., via the SSH key association path), an accidental connect attempt against the recycled IP could reach an unintended host.

### Blast radius

Every user who has launched and terminated EC2 instances since the INFRA-003 feature was deployed. The impact scales with the number of terminated instances per user. Auto-terminated instances (idle checker) compound the accumulation silently.

## 4. Fix Design (code-level)

### Primary fix: delete host inventory entry in `terminate_instance()`

Add the following block to `app/services/ec2_launcher.py` inside `terminate_instance()`, immediately after the security-group disassociation block (after line 350, before the `item["status"] = "terminated"` line at 352):

```python
# Delete auto-registered host inventory entry (INFRA-001 / GAP-0224)
host_id = item.get("host_id", "")
if host_id:
    try:
        from app.services import host_inventory
        host_inventory.delete_host(user_sub, host_id)
        logger.info(
            "ec2_host_deregistered user_sub=%s instance_id=%s host_id=%s",
            user_sub, instance_id, host_id,
        )
    except Exception:
        # Cleanup failure must not block termination
        logger.exception(
            "ec2_host_deregister_failed user_sub=%s instance_id=%s host_id=%s",
            user_sub, instance_id, host_id,
        )
```

This mirrors the existing security-group disassociation pattern exactly: check the field, guard the call in `try/except`, log success and failure.

### Guard on empty `host_id`

The `if host_id:` guard handles three cases correctly:
1. Instances launched before GAP-0223 is deployed (host_id = "") — no-op, no inventory entry to delete.
2. Instances where auto-registration failed (host_id = "") — no-op.
3. Instances with a valid host_id — calls `delete_host`, which is also safe if the entry was manually deleted beforehand (returns `False`, does not raise).

### Back-fill cleanup for existing orphaned entries

For instances already in `status = "terminated"` with a non-empty `host_id`, run a one-time migration:

```python
# scripts/backfill_ec2_host_cleanup.py (one-time migration)
import boto3
from app.services import host_inventory
from app.core.tables import T

resp = T.ec2_instances.scan(
    FilterExpression="attribute_exists(host_id) AND #st = :term AND host_id <> :empty",
    ExpressionAttributeNames={"#st": "status"},
    ExpressionAttributeValues={":term": "terminated", ":empty": ""},
)
for item in resp.get("Items", []):
    try:
        host_inventory.delete_host(item["user_sub"], item["host_id"])
        print(f"Cleaned up host_id={item['host_id']} for instance={item['instance_id']}")
    except Exception as e:
        print(f"Failed to clean up host_id={item['host_id']}: {e}")
```

### SSH key disassociation

When an instance is terminated, any SSH key associations that reference this instance's `host_id` should also be cleaned up. `ssh_key_manager.disassociate_key_from_host()` is safe to call with a non-existent host_id (it reads the key's `associated_hosts` list and removes the host_id). Add this to the termination cleanup block:

```python
# Disassociate SSH key from this host (INFRA-002)
ssh_key_id = item.get("ssh_key_id", "")
if ssh_key_id and host_id:
    try:
        from app.services import ssh_key_manager
        ssh_key_manager.disassociate_key_from_host(user_sub, ssh_key_id, host_id)
    except Exception:
        logger.exception(
            "ec2_key_disassociate_failed user_sub=%s instance_id=%s key_id=%s",
            user_sub, instance_id, ssh_key_id,
        )
```

### Dev/Prod parity (SECOPS-007)

`host_inventory.delete_host()` writes to `T.host_inventory` which is DynamoDB Local in dev and real AWS DynamoDB in production. The `try/except` guard ensures that a missing `T.host_inventory` table in dev (e.g., before `local-ddb-init.py` is run) does not break termination. The flag `S.ec2_mock_enabled` is not checked here — cleanup runs in both mock and real modes because the DDB host inventory record exists regardless of whether the underlying EC2 instance is real or mocked.

### Alternatives considered

**Soft-delete instead of hard-delete.** Adding a `terminated: true` flag to the host inventory entry rather than deleting it. Rejected: this would still consume the user's host inventory slot, and a soft-deleted entry in the SSH terminal picker would be confusing. `delete_host` already emits an audit event providing the deletion trail.

**Delete from a background task that scans for terminated instances.** A cron-style cleanup job could scan for terminated instances with non-empty `host_id` and delete orphaned inventory entries. Rejected as primary fix because it introduces a cleanup delay window and adds background-task complexity. The synchronous approach at the point of termination is simpler and more reliable.

### Manual QA steps

1. Start the local dev stack (`just up`).
2. Launch an instance via `POST /ui/ec2/instances` with `ami_id=ami-ubuntu-2204`.
3. Confirm a host inventory entry is created (`GET /ui/hosts`) with `source=ec2_auto`.
4. Terminate the instance (`DELETE /ui/ec2/instances/{instance_id}`).
5. Re-fetch `GET /ui/hosts` and confirm the `ec2_auto` entry is gone.
6. Verify the SSH terminal picker no longer shows the dead host.

### Metrics and observability

Log metric filter on `ec2_host_deregister_failed` — alert operations if cleanup is failing (may indicate a DDB permission issue or table not found). Consider a daily reconciliation query: count DDB records in `T.host_inventory` with `source = ec2_auto` joined against `T.ec2_instances` — any orphan (host exists but instance is terminated) indicates a cleanup failure.

### Rollback

The cleanup block is guarded by `if host_id:` and wrapped in `try/except`. In the worst case (unexpected failure in `delete_host`), the exception is logged and the termination proceeds. The impact of a rollback is simply a return to the pre-fix behaviour (no cleanup), which is the current state.

### Effort and sequencing

Effort: **S** (1–2 hours). Must be sequenced after or alongside GAP-0223 (auto-registration) — both fixes work independently but achieve full lifecycle correctness only together. Run the back-fill migration script after deployment to clean up existing orphaned entries. The SSH key disassociation addition should be coordinated with GAP-0221 (audit events) and GAP-0220 (SSH key auth wiring) to complete the INFRA-002 lifecycle.
