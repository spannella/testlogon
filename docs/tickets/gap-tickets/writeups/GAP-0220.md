# GAP-0220: `stored_key` auth type not wired into SSH terminal — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code before writing.

## 1. Summary & Classification

**Plain-English statement**: The Browser SSH terminal (`app/routers/browser_ssh_terminal.py`) supports two `authType` values: `"password"` and `"private_key"`. The INFRA-002 ticket introduced a `"stored_key"` auth type in which the user's private key never leaves the server — the browser sends only a `keyId`, the backend fetches and decrypts the key from KMS-encrypted storage (`app/services/ssh_key_manager.py:get_decrypted_private_key`), and injects it into the Paramiko connection. This flow is not wired: `"stored_key"` is not in the `authType` allowlist at `browser_ssh_terminal.py:666`, there is no handler branch for it in the WebSocket connect path, and `get_decrypted_private_key` is never called from the terminal router. The entire security guarantee — "private key never reaches the browser" — is therefore not delivered.

**Severity**: HIGH — The `stored_key` feature is the only safe way to use a managed SSH key through the browser terminal. Without it, users must paste plaintext private keys over the WebSocket (the existing `"private_key"` flow), which exposes keys to browser memory, browser history, and any XSS vector. The host inventory (`app/services/host_inventory.py:record_connection`) also has an SSO-style "connect via stored key" path that is similarly unreachable from the terminal.

**Status**: Open. Source ticket: INFRA-002. Effort: M. Owning area: Browser SSH terminal / Host inventory.

**Claim verdict**: Confirmed. `browser_ssh_terminal.py:666`:
```python
if auth_type not in {"password", "private_key"}:
    return False, None, _error_payload(
        code="invalid_auth_type",
        message="authType must be one of: password, private_key",
        request_type="connect",
    )
```
`"stored_key"` is absent from the set. The `_validate_connect_payload` function (line 635) enforces this allowlist. `get_decrypted_private_key` (`app/services/ssh_key_manager.py:271`) exists and is functional but is never imported by `browser_ssh_terminal.py`. The protocol documentation endpoint (`GET /api/browser-ssh/protocol`, line 520) also documents only `["password", "private_key"]`, making the omission visible to API clients. No correction to the claim is required.

**Related tickets**: INFRA-002 (source), INFRA-001 (host inventory), SECOPS-007.

## 2. Current-State Investigation (root cause)

### The existing `private_key` flow (what works today)

When `authType == "private_key"`, the client sends the raw PEM text in the `privateKey` field of the WebSocket `connect` message. `_validate_connect_payload` (line 682–694) verifies it looks like a valid PEM block, then `_create_ssh_bridge` passes it as `private_key` to `ParamikoSshBridge`. Inside `ParamikoSshBridge.connect()` (line 130–131):

```python
if self._auth_type == "private_key":
    connect_kwargs["pkey"] = self._load_private_key(paramiko)
```

The key PEM is loaded via `io.StringIO` directly in the bridge. This works — but the private key material has traversed the network (from browser to server over WebSocket) and sits in server memory as a plaintext string.

### What `stored_key` is supposed to do

The `ssh_key_manager` service (`app/services/ssh_key_manager.py`) provides:

- `store_private_key(user_sub, key_id, pem_bytes)` — KMS-encrypts and stores a key in DDB.
- `get_decrypted_private_key(user_sub, key_id) -> Optional[str]` (line 271) — decrypts and returns the PEM. Updates `last_used_at` and `use_count`.
- `associate_key_with_host(user_sub, key_id, host_id)` — links a key to a managed host for automatic connection.

The intended `stored_key` flow is:
1. Browser sends `{"type":"connect","payload":{"host":"...","authType":"stored_key","keyId":"key_abc123"}}`.
2. Server receives `keyId`, verifies the key belongs to the authenticated user, calls `get_decrypted_private_key(user_sub, key_id)`, and uses the returned PEM as `private_key` in `ParamikoSshBridge`.
3. The PEM never appears in the browser or in WebSocket traffic. Only the opaque `keyId` crosses the wire.

### Root cause: validation gate blocks `stored_key` unconditionally

`_validate_connect_payload` (line 666) contains:

```python
if auth_type not in {"password", "private_key"}:
    return False, None, _error_payload(
        code="invalid_auth_type",
        message="authType must be one of: password, private_key",
        request_type="connect",
    )
```

This returns immediately for `"stored_key"`, never reaching any handling code. Even if a handler were added in the `msg_type == "connect"` branch (line 828–965), the payload would never reach it because validation rejects it first.

There is also no `elif self._auth_type == "stored_key":` branch in `ParamikoSshBridge.connect()` (line 111–146). The bridge's `connect()` method falls through to `else: connect_kwargs["password"] = self._password` for any auth type that is not `"private_key"`, which would cause a Paramiko authentication failure with `password=None`.

### `record_connection` not called on `stored_key` path

`app/services/host_inventory.py:record_connection` (line 419) is called from the host inventory router but not from `browser_ssh_terminal.py`. When a `stored_key` connection is used against a managed host (one stored in the host inventory), the connection event is not recorded in the host's `last_connected_at` field and connection history, breaking the audit trail and "recent connections" UI.

The `associate_key_with_host` service function links a `key_id` to a `host_id`. On a `stored_key` connection, the terminal should look up whether the `key_id` has an associated host (via `app/services/ssh_key_manager.py:get_key_metadata`) and, if so, call `record_connection`.

### Dev vs prod behaviour

Both environments are affected identically: `"stored_key"` is rejected by the validation gate in both. There is no dev-mode shortcut. The `ssh_key_manager` KMS path uses `kms_decrypt` from `app/core/crypto.py`, which is backed by the mock KMS server (`scripts/mock_kms_server.py` on port 7999) in dev and by real AWS KMS in prod. This means the full `stored_key` flow can be tested end-to-end in dev once the terminal wiring is added.

## 3. Impact / Exploit / Blast Radius

**Security impact** — absence of the feature:
- Users who want to use the browser SSH terminal with managed keys are forced to paste private key PEM text directly into the browser. Any XSS vulnerability in the frontend, any browser extension with page access, or any network interception (if TLS is misconfigured) can exfiltrate the private key.
- Private keys pasted into the WebSocket connection also appear in browser developer tools (Network tab), making them visible to anyone with access to the user's browser during a session.

**Functional impact**:
- The `host_inventory` "connect via stored key" feature advertised in the INFRA-002 docs is not available through the browser terminal.
- The `key_use_count` and `last_used_at` fields on stored keys are never updated via the terminal path, making usage analytics inaccurate.

**Blast radius**: All users of the browser SSH terminal who have keys in `ssh_key_manager`. No data corruption; impact is security posture and feature availability.

## 4. Fix Design (code-level)

### Step 1 — Add `stored_key` to the validation allowlist

In `_validate_connect_payload` (`browser_ssh_terminal.py:666`):

```python
# Before:
if auth_type not in {"password", "private_key"}:

# After:
if auth_type not in {"password", "private_key", "stored_key"}:
```

Then add a validation branch for `stored_key` payload (after the `private_key` branch at line 681):

```python
elif auth_type == "stored_key":
    key_id = payload.get("keyId")
    if not isinstance(key_id, str) or not key_id.strip():
        return False, None, _error_payload(
            code="invalid_key_id",
            message="keyId is required for stored_key auth",
            request_type="connect",
        )
```

Update the returned normalized payload to include `keyId`:

```python
return True, {
    "host": host.strip(),
    "port": port,
    "username": username.strip(),
    "authType": auth_type,
    "password": payload.get("password"),
    "privateKey": payload.get("privateKey"),
    "keyId": payload.get("keyId"),        # <-- add
    "passphrase": passphrase,
}, None
```

### Step 2 — Resolve the key in the connect handler

In the `msg_type == "connect"` branch of the WebSocket handler (line 828), after `_validate_connect_payload` and before `_create_ssh_bridge`, add:

```python
# app/routers/browser_ssh_terminal.py (in the connect block, before _create_ssh_bridge)
if normalized["authType"] == "stored_key":
    from app.services.ssh_key_manager import get_decrypted_private_key
    key_id = normalized.get("keyId", "")
    pem = get_decrypted_private_key(session_user_sub, key_id)
    if pem is None:
        await websocket.send_json({
            "type": "error",
            "payload": _error_payload(
                code="key_not_found",
                message="SSH key not found or access denied.",
                request_type="connect",
            ),
        })
        if session_slot_acquired:
            _release_user_session_slot(session_user_sub)
            session_slot_acquired = False
        continue
    # Inject PEM into normalized dict as private_key for bridge construction
    normalized["privateKey"] = pem
    normalized["authType"] = "private_key"   # bridge uses "private_key" branch
```

This approach reuses the existing `ParamikoSshBridge` `"private_key"` path without any changes to the bridge itself — the key is resolved server-side and injected as `privateKey` before the bridge is constructed. The `authType` is normalised to `"private_key"` for the bridge call only; the original `"stored_key"` is preserved in `normalized` for audit logging purposes (log it before the override).

### Step 3 — `record_connection` for managed hosts

After a successful `stored_key` connection, check if the key is associated with a managed host and record the connection:

```python
# After session_connected = True (line 930), for stored_key:
if original_auth_type == "stored_key":
    from app.services.ssh_key_manager import get_key_metadata
    from app.services.host_inventory import record_connection
    key_meta = get_key_metadata(session_user_sub, key_id)
    if key_meta:
        associated_host_id = key_meta.get("associated_host_id")
        if associated_host_id:
            try:
                record_connection(session_user_sub, associated_host_id)
            except Exception:
                logger.warning(
                    "browser_ssh record_connection failed",
                    extra=_session_log_context(session_id=ws_session_id,
                                               user_sub=session_user_sub),
                )
```

Store `original_auth_type = normalized["authType"]` and `key_id` before overwriting in Step 2.

### Step 4 — Update protocol documentation

Update the `GET /api/browser-ssh/protocol` endpoint (line 514–549) to reflect the new `authType`:

```python
"authType": ["password", "private_key", "stored_key"],
"example_stored_key": {
    "type": "connect",
    "payload": {
        "host": "example.internal",
        "port": 22,
        "username": "alice",
        "authType": "stored_key",
        "keyId": "key_abc123",
    },
},
```

### Dev/Prod parity (SECOPS-007)

`get_decrypted_private_key` calls `kms_decrypt` which uses:
- Dev: mock KMS server on port 7999 (`scripts/mock_kms_server.py`)
- Prod: real AWS KMS

The terminal code path is identical in both environments — no `if S.dev_mode` branch needed. For E2E tests, pre-seed a key via `store_private_key(user_sub, key_id, pem)` directly in the test `beforeAll`, bypassing the browser UI, then test `stored_key` auth over the WebSocket.

The `_redact_connect_payload` function (line 578) already redacts `privateKey`. It should also redact `keyId` to avoid logging key IDs in audit trails (though `keyId` is not secret, consistency is valuable):

```python
if "keyId" in redacted:
    redacted["keyId"] = f"***REDACTED***({len(str(redacted.get('keyId') or ''))} chars)"
```

### Security note: key ownership verification

`get_decrypted_private_key(user_sub, key_id)` (line 271) fetches by `Key={"user_sub": user_sub, "sk": f"KEY#{key_id}"}`. DynamoDB will return `None` if the key does not belong to `user_sub`, so ownership is implicitly enforced by the DDB access pattern. No additional authorization check is needed. The `None` return triggers the "key not found or access denied" error response in Step 2.

### Rollout

- **Effort**: M — ~60 lines of changes across `_validate_connect_payload`, the WebSocket connect handler, and the protocol doc endpoint. Existing `ParamikoSshBridge` and `get_decrypted_private_key` are unchanged.
- **Backward compat**: Fully additive. Existing `password` and `private_key` flows are untouched. No DDB schema changes.
- **Migration**: None required.
- **Rollback**: Remove `"stored_key"` from the validation allowlist. The `get_decrypted_private_key` call and associated handler are dead code once the constant is excluded; they can be removed in the same rollback.
- **Risk**: Low for backend. The main risk is the frontend SSH terminal UI needing a new "Stored Key" option and a key-picker dropdown; that UI work is a separate frontend ticket (INFRA-002 follow-up). The backend fix can ship independently: the `stored_key` flow becomes available via the raw WebSocket API immediately, even if the frontend UI is not yet updated.
- **Sequencing**: Can ship independently. No dependency on other GAP tickets. Recommend shipping alongside any INFRA-002 frontend work so both layers go live together.
