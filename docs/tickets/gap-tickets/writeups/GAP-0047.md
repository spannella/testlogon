# GAP-0047: BROADCAST_PREROLL_ENABLED and BROADCAST_MIDROLL_ENABLED Flags Absent from Code Paths — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Claim (from ticket):** The feature flags `BROADCAST_PREROLL_ENABLED` and `BROADCAST_MIDROLL_ENABLED` are absent from `app/core/settings.py`, so broadcast ad features cannot be independently gated for rollout.

**Verdict: Claim is partially incorrect and partially confirmed.** The two settings attributes — `broadcast_preroll_enabled` and `broadcast_midroll_enabled` — **do exist** in `app/core/settings.py` at lines 535-536, introduced as part of the ADS-006 implementation:

```python
# app/core/settings.py:534-536
# Broadcast Ad Breaks (ADS-006)
broadcast_preroll_enabled: bool = os.environ.get("BROADCAST_PREROLL_ENABLED", "1") not in ("0", "false", "False")
broadcast_midroll_enabled: bool = os.environ.get("BROADCAST_MIDROLL_ENABLED", "1") not in ("0", "false", "False")
```

However, neither `build_pre_roll` (in `app/services/broadcast_ads.py`) nor `trigger_ad_break_route` (in `app/routers/broadcast_ads.py`) ever reads these settings. The flags are **defined but never consulted**. Setting `BROADCAST_PREROLL_ENABLED=0` or `BROADCAST_MIDROLL_ENABLED=0` in the environment has no effect; pre-roll ads are always served (subject only to subscriber ad-free) and mid-roll breaks are always triggerable.

The real gap is therefore: **the settings attributes exist but are not wired into the two code paths that need them.** The ticket's phrasing ("flags absent from settings.py") is inaccurate; the accurate description is "flags defined but unused by the affected functions."

### Background: How feature flags work in this codebase

All feature flags in this project are declared as `bool` fields in `app/core/settings.py`'s `Settings` dataclass. They are read from environment variables, defaulting to enabled (`"1"`) or disabled (`"0"`) based on the feature's maturity. Flags are accessed via the singleton `S` (imported from `app.core.settings`). The pattern is pervasive: `MESSAGING_ENCRYPTED_MESSAGES_ENABLED`, `SIGNATURE_PDF_ENABLED`, `NEWSFEED_MARKDOWN_ENABLED`, etc. all follow this convention. The broadcast ad flags were defined as part of the same convention but the wiring step — importing `S` and checking `S.broadcast_preroll_enabled` / `S.broadcast_midroll_enabled` in the service/router — was omitted.

## 2. Current-State Investigation (root cause)

### Settings definition (confirmed present)

`app/core/settings.py` lines 534-536:
```python
broadcast_preroll_enabled: bool = os.environ.get("BROADCAST_PREROLL_ENABLED", "1") not in ("0", "false", "False")
broadcast_midroll_enabled: bool = os.environ.get("BROADCAST_MIDROLL_ENABLED", "1") not in ("0", "false", "False")
```

Both flags default to `True` (enabled). They are correctly named and would be available as `S.broadcast_preroll_enabled` and `S.broadcast_midroll_enabled` throughout the codebase.

### Pre-roll code path (not gated)

`app/services/broadcast_ads.py:86-121`, function `build_pre_roll`:

```python
def build_pre_roll(session, viewer_id: str) -> Dict[str, Any]:
    if is_ad_free(viewer_id, session.created_by):
        return {"pre_roll": None, "ad_free": True}

    if not session.pre_roll_enabled:          # <-- per-session toggle, not global flag
        return {"pre_roll": None, "ad_free": True}

    ad = serve_broadcast_ad(...)
    ...
```

There is no `from app.core.settings import S` in `broadcast_ads.py` and no read of `S.broadcast_preroll_enabled`. The only gate is `session.pre_roll_enabled`, which is a per-session field set by the broadcaster via `PATCH /broadcast/sessions/{id}/ad-config`. This means:
- There is no global operator kill-switch for pre-roll.
- Setting `BROADCAST_PREROLL_ENABLED=0` in `.env.local` or in a production environment variable has zero effect.
- A broadcaster can always enable pre-roll on their own session even if the platform intends to disable the feature globally.

### Mid-roll code path (not gated)

`app/routers/broadcast_ads.py:185-218`, function `trigger_ad_break_route`:

```python
@router.post("/sessions/{session_id}/ad-break", response_model=AdBreakOut)
async def trigger_ad_break_route(session_id: str, ctx: dict = Depends(_ctx)):
    session = get_session(session_id)
    if session.created_by != ctx["user_sub"] and ctx.get("role") not in {"admin", "root"}:
        raise HTTPException(403, ...)
    if session.status != "live":
        raise HTTPException(400, ...)
    if session.ad_break_active:
        raise HTTPException(400, ...)
    payload = start_ad_break(session)
    ...
```

There is no check against `S.broadcast_midroll_enabled`. A broadcaster can trigger mid-roll ad breaks even when the operator has set `BROADCAST_MIDROLL_ENABLED=0`.

Similarly, `app/routers/broadcast_ads.py:123-141` (`update_ad_config_route`) allows setting `pre_roll_enabled=True` on a session without checking `S.broadcast_preroll_enabled` first.

### Why the flags exist in settings but not in the code

The likely sequence: the settings attributes were added speculatively during ADS-006 design (a common practice when scaffolding feature flags), but the wiring step — importing `S` in the service/router and guarding on `S.broadcast_preroll_enabled` — was never completed.

## 3. Impact / Exploit / Blast Radius

**Operational impact (current):**
An operator who wants to disable pre-roll or mid-roll ads platform-wide — e.g. for a compliance review, a partner contract restriction, or a QA test run — cannot do so by setting the environment variables. The only workaround is to edit code and redeploy. This defeats the primary purpose of feature flags, which is to allow operational changes without code changes. Specifically:

- **Pre-roll:** Setting `BROADCAST_PREROLL_ENABLED=0` and restarting the backend has no effect. Pre-roll ads are served to all non-subscriber viewers as long as the per-session `pre_roll_enabled=True` flag is set by the broadcaster.
- **Mid-roll:** Setting `BROADCAST_MIDROLL_ENABLED=0` and restarting the backend has no effect. Broadcasters can still trigger mid-roll ad breaks via `POST /broadcast/sessions/{id}/ad-break`.
- **Config PATCH:** Setting `BROADCAST_PREROLL_ENABLED=0` does not prevent broadcasters from setting `pre_roll_enabled=True` on their session via `PATCH /sessions/{id}/ad-config`.

The net result is that a platform operator has no runtime control over broadcast ad delivery without a code deployment.

**Financial/legal impact:**
If the platform enters a jurisdiction that prohibits advertising to certain audiences (e.g. minors), or if an advertiser contract requires an emergency ad pause, the lack of a working kill-switch means ads continue to serve. This is a compliance risk, not just an operational inconvenience.

**Rollout risk:**
The flags were presumably added to allow incremental rollout. Without wiring, the platform cannot do a gradual rollout (e.g. "enable pre-roll only for 10% of sessions") or a dark launch. All broadcasters are immediately exposed to the full ad experience as soon as they create a session with `pre_roll_enabled=True`.

**No user data exposure or privilege escalation.** The blast radius is operational: wrong ad delivery behaviour, inability to do emergency ad shutoff.

**Mid-roll specific:** The `BROADCAST_MIDROLL_ENABLED=0` setting also fails to prevent broadcasters from updating `mid_roll_ad_break_duration_seconds` via `PATCH /sessions/{id}/ad-config`. The config endpoint does not check the midroll flag either.

## 4. Fix Design (code-level)

Two independent wiring changes are needed.

### Change 1 — Gate `build_pre_roll` on `S.broadcast_preroll_enabled`

In `app/services/broadcast_ads.py`, add the settings import and an early-exit guard:

```python
# Add to imports at top of file
from app.core.settings import S

# In build_pre_roll, after the ad_free check and before the session check:
def build_pre_roll(session, viewer_id: str) -> Dict[str, Any]:
    # Ad-free subscribers (and the broadcaster) skip pre-roll entirely.
    if is_ad_free(viewer_id, session.created_by):
        return {"pre_roll": None, "ad_free": True}

    # Global platform kill-switch for pre-roll (BROADCAST_PREROLL_ENABLED).
    if not S.broadcast_preroll_enabled:
        return {"pre_roll": None, "ad_free": True}

    if not session.pre_roll_enabled:
        return {"pre_roll": None, "ad_free": True}
    ...
```

Placing the global flag check **after** the ad_free check ensures subscribers still get the correct `ad_free=True` flag even when the global feature is disabled, and the platform can disable pre-roll without altering subscriber experience semantics.

### Change 2 — Gate `trigger_ad_break_route` on `S.broadcast_midroll_enabled`

In `app/routers/broadcast_ads.py`, add the settings import and an early-exit guard inside `trigger_ad_break_route`:

```python
# Add to imports at top of file
from app.core.settings import S

# Inside trigger_ad_break_route, after the broadcaster check:
@router.post("/sessions/{session_id}/ad-break", response_model=AdBreakOut)
async def trigger_ad_break_route(session_id: str, ctx: dict = Depends(_ctx)):
    session = get_session(session_id)
    if session.created_by != ctx["user_sub"] and ctx.get("role") not in {"admin", "root"}:
        raise HTTPException(403, ...)

    # Global platform kill-switch for mid-roll (BROADCAST_MIDROLL_ENABLED).
    if not S.broadcast_midroll_enabled:
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail={"code": "MIDROLL_DISABLED", "detail": "Mid-roll ad breaks are not enabled on this platform"},
        )
    ...
```

### Change 3 — Gate `update_ad_config_route` on the relevant flag

The `PATCH /sessions/{id}/ad-config` endpoint allows setting `pre_roll_enabled=True`. If the global pre-roll flag is off, that field should be ignored (or rejected):

```python
# Inside update_ad_config_route, after the broadcaster auth check:
if body.pre_roll_enabled is True and not S.broadcast_preroll_enabled:
    raise HTTPException(
        status_code=status.HTTP_400_BAD_REQUEST,
        detail={"code": "PREROLL_DISABLED", "detail": "Pre-roll ads are not enabled on this platform"},
    )
```

### Dev/Prod parity (SECOPS-007)

Both flags are read from environment variables with no mock/dev distinction. Default is `"1"` (enabled), so dev behaviour is unchanged until an operator explicitly sets the variable. The same code path is taken in dev and prod. No separate mock is needed.

To verify in dev: add `BROADCAST_PREROLL_ENABLED=0` to `.env.local`, restart backend, and confirm that `POST /broadcast/sessions/{id}/ad-join` returns `pre_roll: null`.

### Alternatives considered

- **Per-session flag only (no global flag):** This already exists (`session.pre_roll_enabled`). The global flag serves a different purpose: it prevents broadcasters from enabling a feature the platform has administratively disabled.
- **Feature flag service (e.g. LaunchDarkly):** Overkill for this. Simple environment-variable-backed booleans are consistent with how every other feature flag in settings.py works.
- **Soft disable (silently return no ad without error on midroll):** Chosen for pre-roll (consistent UX — viewer just doesn't see ad). For mid-roll trigger, an HTTP 403 is more appropriate so the broadcaster knows the action is unavailable rather than silently doing nothing.
