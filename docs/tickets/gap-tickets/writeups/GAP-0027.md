# GAP-0027: DMCA Waiting-Period Background Timer Not Wired to Startup — Remediation Write-up

## 1. Summary & Classification

**Plain-English statement**: US copyright law (17 U.S.C. § 512(g)(2)) requires a platform to restore taken-down content after a 10–14 business day waiting period when a user files a valid DMCA counter-notice, unless the original claimant files suit. The platform has a fully implemented service function, `process_expired_dmca_waiting_periods`, that performs this restoration by scanning for expired claims and resolving them automatically. However, this function is never called by anything in a running server. No background task, no startup hook, no periodic job — the function exists in isolation. Claims that enter the `waiting_period` status remain stuck there indefinitely, and content is never restored.

- **Severity**: Critical (CRIT)
- **Source ticket**: MOD-002
- **Status**: Open
- **Owning area**: Moderation / DMCA / Platform Compliance
- **Effort**: S

**Verdict**: Confirmed. The investigation (`docs/tickets/gap-tickets/investigations/GAP-0027.md`) verified that `process_expired_dmca_waiting_periods()` at `app/services/dmca_claims.py:617` is complete and functional, but no `add_event_handler("startup", ...)` registration for a DMCA timer appears anywhere in `app/main.py` or the rest of the codebase.

**One-line impact**: Every DMCA counter-notice ever filed leaves content permanently suppressed because the platform never checks whether the 14-day window has elapsed.

**Related tickets**: MOD-002 (source), MOD-003 (user appeals, related compliance workflow), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (Root Cause)

### The implemented service function

`app/services/dmca_claims.py:617` defines `process_expired_dmca_waiting_periods() -> int`:

```python
def process_expired_dmca_waiting_periods() -> int:
    """Scan for claims in waiting_period whose waiting_period_expires_at <= now.
    Auto-resolves them with resolution="restored" and restores content.
    Returns the number of claims processed.
    """
    ts = now_ts()
    processed = 0
    exclusive_start_key = None

    while True:
        kwargs: Dict[str, Any] = {
            "IndexName": "ByWaitingPeriodExpiry",
            "KeyConditionExpression": (
                Key("status").eq("waiting_period")
                & Key("waiting_period_expires_at").lte(ts)
            ),
            "Limit": 25,
        }
        if exclusive_start_key:
            kwargs["ExclusiveStartKey"] = exclusive_start_key

        resp = T.dmca_claims.query(**kwargs)
        items = resp.get("Items", [])
        for item in items:
            claim_id = item.get("claim_id", "")
            try:
                resolve_dmca_claim(
                    claim_id=claim_id,
                    resolution="restored",
                    resolution_notes="Waiting period expired — content automatically restored",
                    admin_user_id="system",
                )
```

The function is complete: it uses the `ByWaitingPeriodExpiry` GSI, pages through results, calls `resolve_dmca_claim`, and returns a count of processed items.

### The missing startup wiring

`app/main.py` lines 482–483 include the DMCA routers:

```python
app.include_router(dmca_router)
app.include_router(admin_dmca_router)
```

But unlike every other periodic background task, there is no `add_event_handler("startup", ...)` call for any DMCA timer. The file `app/main.py` contains the following startup registrations for similar background jobs (lines 521–527):

```python
app.add_event_handler("startup", start_billing_dunning_task)
app.add_event_handler("startup", start_filemgr_purge_task)
app.add_event_handler("startup", start_scheduled_messages_task)
app.add_event_handler("startup", start_broadcast_scheduler_task)
app.add_event_handler("startup", start_broadcast_reminder_task)
app.add_event_handler("startup", start_deletion_scheduler_task)
app.add_event_handler("startup", start_kyc_sla_checker_task)
```

A search across all of `app/` for `_dmca_timer`, `dmca_timer_loop`, `start_dmca`, and `process_expired_dmca` finds only the single function definition in `dmca_claims.py`. No async wrapper, no `create_task` call, and no registration exist.

### How waiting periods are set

`app/services/dmca_claims.py` line 257 sets `waiting_period_expires_at = ts + DMCA_WAITING_PERIOD_DAYS * 86400` (14 days by default) when a counter-notice is filed, and line 269 stores this as a numeric attribute on the DynamoDB item. Claims correctly transition to `status="waiting_period"`. The GSI is properly structured to query by `(status, waiting_period_expires_at)`. Everything up to this point is correct. The only missing piece is the periodic check.

### Root cause

The implementation of `process_expired_dmca_waiting_periods` was completed per section 3.7 of the MOD-002 ticket spec. However, the final wiring step — creating an `async` loop wrapper and registering it as a FastAPI startup event — was omitted. The pattern is the same as all other background jobs; it was simply not applied to the DMCA timer.

The `add_event_handler` pattern used by all other background tasks in `app/main.py` (lines 521–527 and beyond) is: write an `async def _xxx_loop()` that wraps the service function in a `while True: ... await asyncio.sleep(interval)` loop, then write `def start_xxx_task()` that calls `asyncio.get_event_loop().create_task(...)`, then register `start_xxx_task` with `app.add_event_handler("startup", ...)`. This three-step pattern was applied to billing dunning, file-manager purge, scheduled messages, broadcast reminders, deletion scheduling, KYC SLA checking, carrier polling, and others — but not to the DMCA timer. The DMCA service function sits dormant, unreachable from any running context.

## 3. Impact / Exploit / Blast Radius

**Legal compliance failure**: 17 U.S.C. § 512(g)(2)(C) requires the service provider to "replace the removed material and cease disabling access to it not less than 10, nor more than 14, business days following receipt of the counter notice, unless its designated agent first receives notice from the person who submitted the notification ... that such person has filed an action seeking a court order." Without the background timer, the platform is in breach of this statutory obligation for every counter-notice ever received.

**Permanent wrongful suppression**: A user who files a legitimate counter-notice correctly following all instructions will never have their content restored, despite the law requiring it. From the user's perspective, the counter-notice mechanism is completely broken.

**Abuse vector**: A malicious actor can file a DMCA claim against a competitor's content knowing that even a meritless claim will permanently suppress the content because the counter-notice restoration path is dead. There is no additional technical exploitation needed — the missing timer alone is sufficient to cause indefinite suppression.

**Scope**: Every claim that has ever transitioned to `waiting_period` status and whose `waiting_period_expires_at` timestamp has passed is affected. In production, this potentially represents every counter-notice filed since MOD-002 was deployed.

**Secondary impact**: The `ByWaitingPeriodExpiry` GSI exists specifically to support this background query. Its presence in the DynamoDB table definition (`scripts/local-ddb-init.py`) but complete lack of a call site is strong evidence that this gap was always known to be outstanding.

**User trust erosion**: The DMCA counter-notice mechanism is prominently communicated to creators as a tool to challenge meritless takedowns. If creators discover that counter-notices are silently ignored — their content never restored despite following the process — the resulting trust damage to the platform may be significant and public.

**Accumulated backlog in production**: If MOD-002 has been deployed for weeks or months, there is a growing backlog of claims whose `waiting_period_expires_at` has elapsed. Once the timer is wired and the server restarts, the first execution of `process_expired_dmca_waiting_periods` will process all of them in a batch. Because the function uses `Limit=25` and pages via `LastEvaluatedKey`, large backlogs will be processed over multiple loop iterations without overwhelming DynamoDB. However, operators should be aware that the first run after deployment may trigger a large number of `resolve_dmca_claim` calls — each of which writes to the `dmca_claims` table and potentially triggers notification side-effects. A one-time backfill run with monitoring is recommended before the first automated loop invocation.

## 4. Fix Design (Code-Level)

### Async loop wrapper

Add an async timer loop to `app/routers/dmca.py` (or a new `app/services/dmca_timer.py`):

```python
# app/routers/dmca.py — add after imports

import asyncio
import logging
from app.services.dmca_claims import process_expired_dmca_waiting_periods

_DMCA_TIMER_LOGGER = logging.getLogger(__name__)
_DMCA_TIMER_INTERVAL_SECONDS = 3600  # check every hour


async def _dmca_timer_loop() -> None:
    """Hourly loop: auto-resolve expired DMCA waiting periods."""
    while True:
        try:
            processed = process_expired_dmca_waiting_periods()
            if processed:
                _DMCA_TIMER_LOGGER.info(
                    "dmca_timer: auto-resolved %d expired waiting period(s)",
                    processed,
                )
        except Exception:
            _DMCA_TIMER_LOGGER.exception("dmca_timer: unhandled error during sweep")
        await asyncio.sleep(_DMCA_TIMER_INTERVAL_SECONDS)


def start_dmca_timer_task() -> None:
    """Register the DMCA waiting-period timer as a background asyncio task."""
    asyncio.get_event_loop().create_task(_dmca_timer_loop())
```

### Startup registration

In `app/main.py`, add the import and registration alongside the existing DMCA router imports and startup handlers:

```python
# Near app/main.py:133–134 (existing DMCA imports):
from app.routers.dmca import router as dmca_router, start_dmca_timer_task

# Near app/main.py:527 (after start_deletion_scheduler_task):
app.add_event_handler("startup", start_dmca_timer_task)
```

### Dev/Prod Parity (SECOPS-007)

`process_expired_dmca_waiting_periods` writes exclusively to the `dmca_claims` DynamoDB table using `T.dmca_claims` (the table handle from `app/core/tables.py`). This resolves to DynamoDB Local on port 8001 in dev and to AWS DynamoDB in production. There are no mock paths, environment-specific branches, or new AWS services introduced by this fix. The timer interval (`_DMCA_TIMER_INTERVAL_SECONDS = 3600`) is the same in both environments. No parity concern is introduced.

### Interval configuration

The interval is currently hardcoded at 3600 seconds. For production hardening, this can be made configurable by adding `dmca_timer_interval_seconds: int = 3600` to `app/core/settings.py` and reading `S.dmca_timer_interval_seconds` in the loop. This is optional for the initial fix but recommended for operational flexibility.

### Backward compatibility

The fix is purely additive. No existing code paths change. No DynamoDB schema changes are required. The `ByWaitingPeriodExpiry` GSI is already provisioned and functional.

### Alternative considered

Running `process_expired_dmca_waiting_periods` as a cron-triggered Lambda or external scheduler was considered. This is architecturally cleaner in a microservices environment but is inconsistent with how all other periodic platform tasks are structured (they all use in-process `asyncio` loops registered at FastAPI startup). The in-process approach is adopted for consistency and is simpler to test.

### Manual QA steps

1. Start the dev stack: `just up`.
2. As a test user, create and approve a DMCA claim on content.
3. File a counter-notice: `POST /ui/dmca/claims/{id}/counter-notice`.
4. Back-date `waiting_period_expires_at` in DynamoDB to `now_ts() - 1`.
5. Wait up to 2 seconds (the timer fires immediately after the loop's first `asyncio.sleep`).
6. Verify: `GET /ui/dmca/claims/{id}` returns `status="resolved"` and `resolution="restored"`.

### Metrics and observability

- The `INFO` log line `"dmca_timer: auto-resolved N expired waiting period(s)"` provides an operational signal. In production, set a CloudWatch alarm for `processed == 0` for more than 14 days as a signal that no counter-notices are being filed (could indicate a broken counter-notice path).
- The `EXCEPTION` log in the error handler provides a signal for unexpected failures in the timer loop.

### Rollback

The fix is additive. Rollback is a code revert followed by a server restart. No DynamoDB changes to undo.

### Risks

- **Race condition on startup**: If `start_dmca_timer_task` is called before the DynamoDB table is available, the first loop iteration will log an exception and sleep. Subsequent iterations will succeed. Risk is low.
- **Duplicate timers in multi-worker mode**: `uvicorn` is started with `--workers 1` in dev per the CLAUDE.md conventions. In production, if multiple workers are used, each worker spawns its own timer. The `resolve_dmca_claim` function must be idempotent (the transition guard in `VALID_TRANSITIONS` prevents double-resolution). Verify idempotency before enabling multi-worker production deployment.

A `DEV_DMCA_TIMER_INTERVAL_SECONDS` env var override is a clean way to make the interval configurable for testing.
