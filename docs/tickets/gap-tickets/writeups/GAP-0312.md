# GAP-0312: Presign Endpoint Does Not Validate That `s3_key` Matches the Presigned Key — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at `app/routers/messaging.py`.

## 1. Summary & Classification

**Bug statement**: The two-step voice-message upload flow (presign then create) does not verify that the `s3_key` submitted in `create_voice_message` is the same key that was issued by `presign_voice_message`. An authenticated user can call `/presign` to obtain a legitimate upload URL for their own `s3_key`, then call `/voice-message` with a completely different `s3_key` — pointing to another user's uploaded audio, a system object, or a non-existent path — and the message will be written to DynamoDB and fanned out to all conversation participants as a genuine voice message.

**Severity**: HIGH  
**Source ticket**: MSG-002 (GAP-0312)  
**Owning area**: Messaging / File Upload Security  
**Status**: Open — no fix deployed

**Verdict**: Claim **confirmed**. Code inspection of `messaging.py:8331–8453` shows that `presign_voice_message` returns a `(message_id, upload_url, s3_key)` tuple but does not persist the mapping anywhere. `create_voice_message` accepts `body.s3_key` (a free-form string with no validation beyond Pydantic `str` type) and writes it directly to `"audio_url"` in DynamoDB without cross-checking the presigned key.

**Impact in one line**: An attacker can craft voice messages that play back arbitrary S3 objects they do not own, or flood conversations with references to non-existent objects, causing broken audio playback for all participants.

**Related tickets**: GAP-0312 (this ticket), SECOPS-007 (dev/prod parity), GAP-0033 (ffmpeg receives S3 URI directly — similar supply-chain pattern).

## 2. Current-State Investigation (Root Cause)

### Presign step — key is ephemeral

`presign_voice_message` (line 8331) allocates a `msg_id` and derives the `s3_key` from it:

```python
# messaging.py:8342-8359
msg_id = "m_" + uuid.uuid4().hex
ext = "webm"
if "mp4" in body.content_type:
    ext = "mp4"
# ...
s3_key = f"voice-messages/{conversation_id}/{msg_id}.{ext}"
if S.dev_mode:
    upload_url = f"/mock/s3/{S3_BUCKET_IMAGES}/{_vm_pq(s3_key, safe='/')}"
else:
    upload_url = s3.generate_presigned_url(
        ClientMethod="put_object",
        Params={"Bucket": S3_BUCKET_IMAGES, "Key": s3_key, "ContentType": body.content_type},
        ExpiresIn=300,
    )
return {"message_id": msg_id, "upload_url": upload_url, "s3_key": s3_key}
```

The response includes `s3_key` and `message_id`. Neither is stored in DynamoDB, a cache, or any server-side record. The endpoint returns and forgets.

### Create step — s3_key is blindly trusted

`create_voice_message` (line 8362) accepts a `CreateVoiceMessageRequest`:

```python
# models.py:1943-1952
class CreateVoiceMessageRequest(BaseModel):
    message_id: str = Field(pattern=r"^m_[a-f0-9]{32}$")
    s3_key: str                           # <-- free-form string, no path constraint
    content_type: str
    size_bytes: int = Field(ge=1)
    duration_seconds: float = Field(ge=0.5, le=300)
    waveform_data: List[float] = Field(min_length=10, max_length=200)
    consumption_policy: Literal["none", "listen_once"] = "none"
    reply_to_message_id: Optional[str] = None
    send_at: Optional[int] = None
```

The `s3_key` field has no `pattern`, `min_length` constraint tying it to the presigned `message_id`, or path prefix restriction. Inside the handler:

```python
# messaging.py:8411
"audio_url": body.s3_key,
```

`body.s3_key` is written verbatim to `audio_url` in the DynamoDB item without any check against what `presign_voice_message` issued.

### No S3 existence or ownership check

There is no `s3.head_object()` call to verify the key actually exists in S3. In dev mode, the URL becomes `/mock/s3/my-chat-images/<s3_key>` (line 4077), which will return whatever the moto mock has at that path. In production, the URL would be a raw S3 key that might point to any object in the shared bucket — including objects owned by other users.

### Path traversal potential

Because `s3_key` has no path prefix enforcement, a crafted value such as `../../../other-user/private/audio.webm` or `user-uploads/alice/sensitive-photo.jpg` would be accepted. In dev mode this would cause an incorrect mock URL; in production it would surface a presigned GET URL for the wrong object when `_message_out_from_item` generates the playback URL.

## 3. Impact / Exploit / Blast Radius

**Exploit walkthrough**:

1. Attacker Alice calls `POST /messaging/conversations/{cid}/voice-message/presign` with valid content-type and size. Server returns `{ message_id: "m_aaa...", s3_key: "voice-messages/{cid}/m_aaa....webm", upload_url: "..." }`.
2. Alice **does not** upload to the presigned URL.
3. Alice calls `POST /messaging/conversations/{cid}/voice-message` with the same `message_id` but substitutes `s3_key: "voice-messages/{other-cid}/m_bob_private_voice.webm"` — a key she learned from intercepting another API call or by guessing the deterministic path structure.
4. Server writes `audio_url = "voice-messages/{other-cid}/m_bob_private_voice.webm"` to DynamoDB and fans out a `message:new` SSE event.
5. Bob's client receives the voice message and the frontend generates a presigned GET URL pointing to Bob's own private voice memo, which plays back for all participants.

**Variant — denial of service**: Attacker submits `s3_key: "nonexistent/path/garbage.webm"`. All recipients receive broken audio player entries. Repeated attacks can degrade conversation quality for targeted users.

**Variant — content injection**: In dev mode, the mock S3 bucket is shared. An attacker who has previously uploaded an arbitrary binary (e.g. via the file-manager upload) can craft an `s3_key` pointing to that binary and deliver it as a voice message, bypassing audio content-type enforcement.

**Blast radius**: Affects all conversations where voice messages are enabled (`S.voice_message_enabled`). Any authenticated user can exploit this, not just admins. The attack requires no privilege escalation.

## 4. Fix Design (Code-Level)

### Strategy

Store the `(message_id → s3_key, owner_user_id, conversation_id, expires_at)` binding in DynamoDB at presign time, and verify it in `create_voice_message`. Use the TTL feature (matching the presigned URL expiry, 300 seconds) to automatically clean up stale records. This is the canonical server-side CSRF-style token pattern for two-step upload flows.

### DynamoDB table: `voice_message_presigns`

Add a new table to `scripts/local-ddb-init.py`:

```python
TableDef(
    name=S.voice_presign_table,               # env var: VOICE_PRESIGN_TABLE
    pk="message_id",                           # "m_<hex>"
    sk=None,
    attr_types={},
    ttl_attr="expires_at",                     # automatic cleanup after 300s
)
```

### Presign endpoint — store the binding

```python
# messaging.py:8331 — presign_voice_message (add after generating s3_key)
import boto3

PRESIGN_TABLE = os.getenv("VOICE_PRESIGN_TABLE", "voice_message_presigns")
_tbl_vm_presigns = ddb.Table(PRESIGN_TABLE)

# After computing s3_key and upload_url:
_tbl_vm_presigns.put_item(Item={
    "message_id": msg_id,
    "s3_key": s3_key,
    "user_id": user_id,
    "conversation_id": conversation_id,
    "expires_at": ts + 300,  # matches presigned URL TTL
})
```

### Create endpoint — verify the binding

```python
# messaging.py:8362 — create_voice_message (add after require_participant_active)

def _verify_voice_presign(
    message_id: str, s3_key: str, user_id: str, conversation_id: str
) -> None:
    try:
        item = _tbl_vm_presigns.get_item(
            Key={"message_id": message_id}
        ).get("Item")
    except Exception:
        item = None

    if not item:
        raise HTTPException(400, "voice_presign_not_found")
    if item.get("s3_key") != s3_key:
        raise HTTPException(400, "voice_presign_key_mismatch")
    if item.get("user_id") != user_id:
        raise HTTPException(403, "voice_presign_owner_mismatch")
    if item.get("conversation_id") != conversation_id:
        raise HTTPException(400, "voice_presign_conversation_mismatch")
    if int(item.get("expires_at", 0) or 0) < now_ts():
        raise HTTPException(400, "voice_presign_expired")


# In create_voice_message, before writing the DDB item:
_verify_voice_presign(mid, body.s3_key, user_id, conversation_id)
```

### Model tightening (defense in depth)

Add a `pattern` validator to `CreateVoiceMessageRequest.s3_key` to enforce the expected path structure, independent of the token check:

```python
# models.py:1945
s3_key: str = Field(
    pattern=r"^voice-messages/[^/]+/m_[a-f0-9]{32}\.(webm|mp4|ogg|wav)$",
    min_length=10,
    max_length=500,
)
```

This rejects the `../` traversal and cross-user path injection at the Pydantic validation layer before any database access.

### Dev/Prod parity (SECOPS-007)

- **Dev mode**: The `VOICE_PRESIGN_TABLE` table is created by `scripts/local-ddb-init.py` (no special mock path needed; DynamoDB Local handles it).
- **Prod mode**: The same code path runs against real DynamoDB with TTL enabled on the `expires_at` attribute.
- No feature flag needed — the fix is always-on. The presign record is cheap (one DDB PutItem on presign, one GetItem on create) and self-cleaning via TTL.
- The `PRESIGN_TABLE` env var follows the existing pattern (`S.ddb_sessions_table`, etc.) and must be added to `app/core/settings.py` and `scripts/local-ddb-init.py`.

### Backward compatibility

Existing clients that call `presign` and then `create` in sequence are unaffected (normal flow). Clients that skip `presign` and call `create` directly will receive HTTP 400 (`voice_presign_not_found`), which is the intended behavior — the two-step flow is mandatory. No migration required.

### Manual QA

1. Call `POST .../voice-message/presign` → capture `message_id` and `s3_key`.
2. Upload audio to the presigned URL.
3. Call `POST .../voice-message` with the correct `message_id` + `s3_key` → expect 201.
4. Repeat step 3 with a modified `s3_key` → expect 400 `voice_presign_key_mismatch`.
5. Wait 310 seconds (TTL expiry) → repeat step 3 with correct key → expect 400 `voice_presign_expired`.

### Metrics / Observability

- Counter `messaging_voice_presign_mismatch_total` incremented on each rejection (label: `reason` = `key_mismatch | owner_mismatch | expired | not_found`).
- Alert if ratio of `voice_presign_mismatch_total` / `voice_create_total` exceeds 1% in a rolling 5-minute window (indicates active exploitation or client bug).

### Rollout

- Effort: **M** (1 day backend + DDB table, 0.5 days tests).
- Feature flag: `VOICE_PRESIGN_VALIDATION_ENABLED` env var (default `true`). Can be set to `false` to disable while verifying DDB table creation in prod.
- Rollback: set flag to `false`; no DDB schema change to undo (TTL cleans up presign records automatically).
- Risk: low for correct clients; breaking for clients that skip the presign step entirely (which is itself invalid usage).
