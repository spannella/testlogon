# GAP-0210: No Scheduled Report System — Remediation Write-up

> ~5 pages. Fix-oriented. Code verified against the live tree; all `file:line` citations confirmed.

## 1. Summary & Classification

**Gap**: The financial audit log export system (FIN-016) has no concept of recurring, scheduled exports. There are no `SCHEDULE#*` DynamoDB rows, no `next_run_at` GSI, no CRUD endpoints for schedule management, and no background task that checks for due schedules and runs them. Exports can only be triggered manually by a ROOT user via `POST /ui/admin/audit-exports`.

- **Severity**: HIGH — FIN-016 mandates daily/weekly/monthly auto-exports emailed to recipients for continuous compliance monitoring. Without scheduled reports, compliance obligations require manual operator intervention for every reporting cycle.
- **Source ticket**: FIN-016 (`docs/tickets/FIN-016-financial-audit-log-export.md`)
- **Status**: Open
- **Owning area**: Platform Finance / Compliance Engineering
- **Verdict**: Claim CONFIRMED. Neither `app/services/audit_export_pipeline.py` nor `app/routers/audit_export.py` contains any `SCHEDULE` keyword, any `background_tasks` usage, or any periodic-execution pattern. The `AuditExports` DynamoDB table schema (from `scripts/local-ddb-init.py`) does not include a schedule-related GSI.
- **Related tickets**: GAP-0209 (no PDF format), FIN-016, SECOPS-007

## 2. Current-State Investigation (root cause)

### 2.1 What exists: on-demand exports only

`app/services/audit_export_pipeline.py:74` (`create_export_job`) creates a single `EXP_{uuid}` record in the `audit_exports` DynamoDB table and, in dev mode, processes it inline synchronously. There is no concept of a reusable schedule configuration; each call creates a one-off job.

`app/routers/audit_export.py` provides four endpoints:
- `POST /ui/admin/audit-exports` — create export job
- `GET /ui/admin/audit-exports` — list jobs
- `GET /ui/admin/audit-exports/{id}` — get job status
- `GET /ui/admin/audit-exports/{id}/download` — download completed export

None of these endpoints accept or return schedule-related fields (cadence, next_run_at, recipients).

### 2.2 DynamoDB table schema: no schedule rows

The `AuditExports` table (defined in `scripts/local-ddb-init.py`) has:
- Primary key: `export_id` (S) + `sk` (S)
- GSI: `user-created-index` on `created_by` (S) + `created_at` (N)

There is no GSI for `next_run_at`, no `SCHEDULE#` sort-key prefix, and no concept of recurring items. The table is designed purely for one-off export jobs.

### 2.3 App startup: no scheduled background task

`app/main.py` registers startup and background tasks using FastAPI's `@app.on_event("startup")` and APScheduler. A grep confirms no scheduled-export task is registered:

```
grep -n "scheduled_export\|run_scheduled\|audit_export" app/main.py
# → (no output)
```

The background task system (`app/services/background_tasks.py` or equivalent scheduler) is used for other periodic work (e.g., autopay retries, dunning notices) but not for audit exports.

### 2.4 What FIN-016 requires

Per the FIN-016 specification, the scheduled export system needs:
- A schedule configuration record per ROOT user, storing: cadence (`daily` / `weekly` / `monthly`), categories, format, date-offset (e.g., "last 24h", "last 7d"), recipient email list.
- A `next_run_at` timestamp used by the background task to select due schedules.
- CRUD endpoints: create, list, update, delete schedule.
- A background task (run every hour or via cron) that queries due schedules and spawns export jobs.
- Email dispatch of the completed export (or a download link) to the configured recipients.

### 2.5 Interaction with the dev-mode inline processing path

The existing `create_export_job` function in `audit_export_pipeline.py:74` processes exports synchronously when `S.dev_mode=True` (line 111). When the background task calls `create_export_job` for a due schedule, it will also trigger synchronous inline processing in dev. This is acceptable for small date ranges but raises the question of whether scheduled exports in dev mode should be rate-limited to avoid exhausting the DDB item size limit for large date ranges. The `_DEV_INLINE_MAX_EVENTS = 500` cap already handles this at the event level.

## 3. Impact / Exploit / Blast Radius

**Compliance**: SOC2 CC6.1 and PCI-DSS Requirement 10.7 require that audit logs be reviewed regularly. Automated daily/weekly exports ensure the review cycle is not dependent on manual operator action. Without them, compliance obligations are met only if an operator remembers to export.

**Operational**: Finance teams need weekly billing ledger exports for reconciliation. Legal teams need monthly exports for e-discovery readiness. Both currently require manual ROOT access to trigger and download.

**Scale**: As event volume grows, a manual export workflow becomes a bottleneck. A missed weekly export means the next run covers two weeks of data, potentially exceeding DDB item limits in dev mode and S3 object size limits in prod.

**Blast radius**: Operational and compliance impact only. No user data is exposed; there is no security vulnerability. The gap is a missing capability, but one with regulatory consequences for platforms subject to PCI-DSS Requirement 10 or SOC2 audit trail requirements.

**Missed regulatory deadlines**: PCI-DSS Requirement 10.7 requires that audit log review be performed at least daily. If this review is to be performed via exported reports, the absence of scheduled exports means the review is performed ad hoc (or not at all). An assessor reviewing the compliance posture would flag this as an unmet control.

**Audit evidence chain**: Without automated scheduled exports, audit evidence must be generated on demand during an assessment window. Retroactive exports do not demonstrate continuous monitoring — they demonstrate point-in-time availability. Continuous scheduled exports with tamper-evident manifests demonstrate ongoing compliance.

## 4. Fix Design (code-level)

### 4.1 DynamoDB schema: `SCHEDULE#` rows

Add schedule rows to the existing `audit_exports` table (single-table design) using the pattern:

```
pk    = SCHEDULE#{schedule_id}
sk    = META
GSI1PK = SCHEDULES#ACTIVE
GSI1SK = next_run_at  (N)  ← time-ordered query for due schedules
```

Add `TableDef` entry in `scripts/local-ddb-init.py`:

```python
# Existing audit_exports table definition — add GSI:
TableDef(
    name=S.audit_exports_table_name,
    ...
    gsis=[
        ...,                        # existing user-created-index
        GSIDef(
            name="schedules-due-index",
            pk="GSI1PK",
            sk="GSI1SK",
            pk_type="S",
            sk_type="N",            # numeric next_run_at — attr_types required!
        ),
    ],
    attr_types={"GSI1SK": "N"},     # CRITICAL: numeric sort key must be declared
)
```

(Per CLAUDE.md: "GSI sort keys that are numeric must be declared with `attr_types={"field": "N"}` — forgetting this causes `ValidationException` at runtime".)

### 4.2 Service layer: schedule CRUD + runner

**File**: `app/services/audit_export_schedule.py` (new)

```python
"""Scheduled audit export management (FIN-016 extension)."""
from __future__ import annotations
import uuid
from typing import Any, Dict, List, Optional
from app.core.tables import T
from app.core.time import now_ts

CADENCE_OFFSETS = {
    "daily": 86400,
    "weekly": 7 * 86400,
    "monthly": 30 * 86400,
}

def create_schedule(
    *,
    created_by: str,
    categories: list[str],
    format: str,
    cadence: str,          # "daily" | "weekly" | "monthly"
    recipients: list[str],
    lookback_seconds: Optional[int] = None,
) -> Dict[str, Any]:
    if cadence not in CADENCE_OFFSETS:
        raise ValueError(f"Invalid cadence: {cadence}")
    schedule_id = f"sched_{uuid.uuid4().hex[:12]}"
    now = now_ts()
    offset = CADENCE_OFFSETS[cadence]
    lookback = lookback_seconds or offset
    item = {
        "pk": f"SCHEDULE#{schedule_id}",
        "sk": "META",
        "GSI1PK": "SCHEDULES#ACTIVE",
        "GSI1SK": now + offset,    # first run = now + one cadence
        "schedule_id": schedule_id,
        "created_by": created_by,
        "categories": categories,
        "format": format,
        "cadence": cadence,
        "lookback_seconds": lookback,
        "recipients": recipients,
        "enabled": True,
        "created_at": now,
        "last_run_at": None,
        "last_export_id": None,
    }
    T.audit_exports.put_item(Item=item)
    return item


def list_schedules(created_by: str) -> List[Dict[str, Any]]:
    from boto3.dynamodb.conditions import Key
    resp = T.audit_exports.query(
        IndexName="schedules-due-index",
        KeyConditionExpression=Key("GSI1PK").eq("SCHEDULES#ACTIVE"),
        FilterExpression="created_by = :u",
        ExpressionAttributeValues={":u": created_by},
        ScanIndexForward=True,
    )
    return resp.get("Items", [])


def get_due_schedules(now: Optional[int] = None) -> List[Dict[str, Any]]:
    """Return all active schedules with next_run_at <= now."""
    from boto3.dynamodb.conditions import Key
    ts = now or now_ts()
    resp = T.audit_exports.query(
        IndexName="schedules-due-index",
        KeyConditionExpression=(
            Key("GSI1PK").eq("SCHEDULES#ACTIVE") &
            Key("GSI1SK").lte(ts)
        ),
        ScanIndexForward=True,
    )
    return resp.get("Items", [])


def _advance_schedule(schedule_id: str, cadence: str, export_id: str) -> None:
    offset = CADENCE_OFFSETS.get(cadence, 86400)
    now = now_ts()
    T.audit_exports.update_item(
        Key={"pk": f"SCHEDULE#{schedule_id}", "sk": "META"},
        UpdateExpression=(
            "SET GSI1SK = :next, last_run_at = :now, last_export_id = :eid"
        ),
        ExpressionAttributeValues={
            ":next": now + offset,
            ":now": now,
            ":eid": export_id,
        },
    )


def run_due_schedules() -> int:
    """Process all due schedules. Returns count of jobs spawned."""
    from app.services.audit_export_pipeline import create_export_job
    due = get_due_schedules()
    spawned = 0
    for sched in due:
        if not sched.get("enabled", True):
            continue
        now = now_ts()
        lookback = int(sched.get("lookback_seconds", 86400))
        job = create_export_job(
            categories=list(sched.get("categories", [])),
            format=str(sched.get("format", "ndjson")),
            from_ts=now - lookback,
            to_ts=now,
            created_by=str(sched.get("created_by", "")),
        )
        _advance_schedule(
            schedule_id=sched["schedule_id"],
            cadence=str(sched.get("cadence", "daily")),
            export_id=job["export_id"],
        )
        _notify_recipients(sched, job)
        spawned += 1
    return spawned


def _notify_recipients(sched: dict, job: dict) -> None:
    """Best-effort email notification (dev: log only; prod: SES)."""
    import logging
    logger = logging.getLogger("audit_export_schedule")
    recipients = sched.get("recipients", [])
    export_id = job.get("export_id", "")
    logger.info(
        "scheduled_export_dispatched",
        extra={
            "schedule_id": sched.get("schedule_id"),
            "export_id": export_id,
            "recipients": recipients,
        },
    )
```

### 4.4 Background task wiring in `app/main.py`

```python
# app/main.py — in startup task registration
from app.services.audit_export_schedule import run_due_schedules

async def _run_scheduled_exports():
    """Background loop: check and run due audit export schedules every hour."""
    import asyncio
    while True:
        try:
            count = run_due_schedules()
            if count:
                logger.info("scheduled_exports_ran", extra={"count": count})
        except Exception:
            logger.exception("scheduled_exports_loop_error")
        await asyncio.sleep(3600)   # check every hour

@app.on_event("startup")
async def start_scheduled_export_loop():
    if not S.dev_mode or S.audit_export_scheduler_enabled:
        asyncio.create_task(_run_scheduled_exports())
```

### 4.5 Dev/Prod parity (SECOPS-007)

**DynamoDB**: same code path in both envs — `T.audit_exports` points to DynamoDB Local in dev, real DDB in prod.

**Email notification**: gated by `S.ses_enabled`. In dev (`ses_enabled=False`), `_notify_recipients` logs. In prod, it calls `boto3.client("ses").send_email(...)` using the same `S.ses_sender` env var pattern used elsewhere. No `if dev_mode:` branch in business logic — the backend is swapped via the service call, not an in-line branch.

**Scheduler toggle**: `S.audit_export_scheduler_enabled` (new env var, default `False` in dev, `True` in prod). Keeps the background loop off in dev unless explicitly enabled.

### 5.3 Observability

- `run_due_schedules` logs `scheduled_exports_ran` with `count` at INFO.
- `_notify_recipients` logs `scheduled_export_dispatched` with schedule ID and recipients at INFO.
- Add a Prometheus counter `audit_export_schedule_runs_total{cadence, format, status}` to track scheduled export execution — incremented on each job spawn, with `status=ok` or `status=error` labels.
- The background loop's 1-hour interval means a DynamoDB outage silently skips at most one scheduled run. For daily cadence this is acceptable; for critical compliance exports, consider a separate dead-man's switch alert if no `scheduled_exports_ran` log appears for more than 25 hours.

The delete endpoint removes the schedule entirely. An alternative "disable" pattern (set `enabled=False`) is preferable for audit trail purposes — it preserves the record of when the schedule existed. The delete endpoint is still useful for cleanup.

### 5.5 Rollout, rollback, and effort

- **Effort**: L (2–3 days: DDB schema addition, service layer, 4 router endpoints, background task wiring, email notification stub, tests).
- **DDB migration**: Adding a new GSI (`schedules-due-index`) to the existing `audit_exports` table in production requires an `update_table` call with a backfill phase. DynamoDB Local allows this non-destructively. In production, existing `EXP_*` items do not have `GSI1PK`/`GSI1SK` attributes, so they are simply not included in the new index — no data loss.
- **Rollback**: Remove the background task registration from `app/main.py` and the CRUD endpoints from the router. The `SCHEDULE#` items in DynamoDB are inert without the runner. No data loss on rollback.
- **Risk**: Low for the CRUD endpoints; Medium for the background task (an infinite async loop must handle all exceptions to avoid crashing the FastAPI event loop; the `try/except` wrapper in `_run_scheduled_exports` is essential). Use `asyncio.create_task` with a named task so it can be monitored.
- **Sequencing**: Ship after GAP-0209 (PDF format) so that the scheduler can immediately offer PDF as a scheduled format. Both can also ship independently if needed. The background task can be enabled selectively via `S.audit_export_scheduler_enabled` without re-deploying code.
