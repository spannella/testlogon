# GAP-0320: Frontend i18n Packages Not Installed; No t() Calls Exist — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase; no prior investigation doc exists.

## 1. Summary & Classification

**Bug statement**: The gap ticket asserts that i18n packages are not installed and no `t()`
calls exist. **The claim is substantially inaccurate as filed.** The actual state of the
codebase is:

- The three required packages (`i18next`, `react-i18next`, `i18next-browser-languagedetector`)
  **are installed** in `frontend/package.json`.
- A full i18n configuration exists at `frontend/src/i18n/index.ts` with three locales (en, es,
  fr), a `LanguageDetector`, and `useSuspense: false`.
- Three locale JSON files exist at `frontend/src/i18n/locales/{en,es,fr}.json`, each with
  ~135 translation keys covering navigation, auth, messaging, billing, feed, settings, and
  other domains.
- `main.tsx` already imports `./i18n` before the React render call.
- A `LanguageSwitcher` component exists at
  `frontend/src/components/shared/LanguageSwitcher.tsx` and uses `useTranslation`.
- 10 component files use `useTranslation` / `t()`: the `Sidebar`, `MobileNav`, `RTLProvider`,
  `LanguageSwitcher`, and `SettingsPage` components.

The actual gap — which is real and HIGH severity — is the **partial adoption**: only 10 of 541
page/component `.tsx` files use `useTranslation`. The remaining ~530 files contain hardcoded
English strings. The locale dictionaries cover ~135 keys, but the application has thousands of
user-visible strings across 541 component files. The "no t() calls exist" claim overstates the
problem, but the underlying remediation work (full migration of hardcoded strings) is genuine
and large in scope.

**Revised claim verdict**: CLAIM INACCURATE (packages are installed and partial t() adoption
exists). The root gap — incomplete migration leaving ~98% of UI strings untranslated — is
confirmed.

**Severity**: HIGH (regulatory/compliance requirement for multilingual markets; accessibility
obligation)  
**Source ticket**: PLATFORM-003  
**Owning area**: Frontend / UX  
**Related tickets**: SECOPS-007 (dev/prod parity — not applicable here; i18n is purely
frontend).

## 2. Current-State Investigation (root cause)

### Package installation — `frontend/package.json`

The packages are present:

```json
"i18next": "^26.3.0",
"i18next-browser-languagedetector": "^8.2.1",
"i18next-http-backend": "^4.0.0",
"react-i18next": "^17.0.8"
```

All four packages are installed; `i18next-http-backend` is installed but not used (the
implementation uses static imports instead of HTTP lazy-loading, which is the correct choice
for a bundled SPA).

### i18n configuration — `frontend/src/i18n/index.ts`

The configuration initialises i18next with:
- `LanguageDetector` reading from `localStorage` → `navigator`
- Three locales: en (default), es, fr
- `useSuspense: false` (correct for a statically-bundled SPA)
- `fallbackLng: "en"`

This is a correct, production-ready configuration.

### Locale dictionaries — `frontend/src/i18n/locales/*.json`

Each file contains 135 keys covering:
- `common.*` (12 keys: save, cancel, delete, loading, error, etc.)
- `nav.*` (38 keys: all sidebar navigation labels)
- `auth.*` (11 keys: login, register, logout, etc.)
- `messages.*` (10 keys: compose, send, noConversations, etc.)
- `settings.*` (7 keys)
- `billing.*` (4 keys)
- `feed.*` (4 keys)
- `errors.*` (5 keys)
- `profile.*` (4 keys)
- `calendar.*` (3 keys)
- `files.*` (3 keys)
- `contacts.*` (3 keys)

ES and FR translations exist for all 135 keys. The dictionaries are a **skeleton**: they cover
navigation labels and common actions but omit the thousands of strings inside page bodies,
form labels, error messages, confirmation dialogs, table headers, and tooltip text across 541
component files.

### Current t() adoption

```
Files using useTranslation:   10 / 541 total TSX files
Approximate t() call sites: ~50 (nav labels + settings page headings)
Keys in locale files:        135
Estimated total UI strings:  4,000–8,000 (typical for a SaaS app of this scale)
```

The `Sidebar.tsx` uses `t("nav.dashboard")`, `t("nav.messages")`, etc. for all navigation
labels. `SettingsPage.tsx` uses `t("settings.title")` and `t("settings.description")`. The
remaining 531 component files use hardcoded English strings directly in JSX.

### Root cause of partial adoption

The i18n infrastructure was set up correctly (likely as part of PLATFORM-003 or a related
ticket) but the migration of existing components was never completed. The gap ticket was
written before or without reading the current code, resulting in the inaccurate "no packages /
no t() calls" characterisation.

## 3. Impact / Exploit / Blast Radius

**Functional impact**: Non-English users who select Spanish or French see a translated sidebar
and settings page headings, but all page content — form labels, button text, error messages,
table headers, confirmation dialogs, marketing copy — remains in English. This creates a
confusing partially-translated experience that is worse than a fully-English experience for
users who discover the language switcher.

**Regulatory/compliance impact**: Many jurisdictions (EU, Quebec, parts of APAC) require SaaS
products targeting those markets to provide native-language interfaces. Incomplete i18n
constitutes a compliance gap in those markets.

**Accessibility impact**: Screen reader users relying on `lang` attribute heuristics for TTS
voice selection will have incorrect pronunciation for UI strings rendered in the wrong language.

**SEO impact**: Server-rendered or SSR-seeded pages with hardcoded English strings will not
rank correctly in non-English search markets.

**Blast radius**: Affects all non-English-speaking users. Does not affect security or data
integrity. No sensitive data is exposed.

## 4. Fix Design (code-level)

Given the scale of the work (~530 files, thousands of strings), this is a multi-sprint effort.
The fix design below specifies the approach, tooling, and prioritisation framework rather than
attempting to list every string.

### 4.1 Tooling and conventions

**Extraction tool**: Use `i18next-scanner` or `i18next-parser` to scan `.tsx` files for
hardcoded strings and generate a draft `en.json`. Configuration:

```js
// i18next-scanner.config.js
module.exports = {
  input: ["src/**/*.{ts,tsx}"],
  output: "./",
  options: {
    func: { list: ["t", "i18n.t"], extensions: [".ts", ".tsx"] },
    lngs: ["en", "es", "fr"],
    ns: ["translation"],
    defaultLng: "en",
    resource: {
      loadPath: "src/i18n/locales/{{lng}}.json",
      savePath: "src/i18n/locales/{{lng}}.json",
    },
    nsSeparator: false,
    keySeparator: ".",
    interpolation: { prefix: "{{", suffix: "}}" },
  },
};
```

**Key naming convention** (extend the existing flat-namespace pattern):

```
<domain>.<component>.<description>
```

Examples:
```
messages.conversationView.typeAMessage   → "Type a message..."
billing.paymentMethods.addNewCard        → "Add new card"
files.manager.uploadFiles                → "Upload Files"
tickets.create.subjectPlaceholder        → "Describe your issue..."
```

**Component migration pattern** (the pattern already used in Sidebar and SettingsPage):

```tsx
// Before
<Button>Save changes</Button>

// After
import { useTranslation } from "react-i18next";
const { t } = useTranslation();
<Button>{t("common.saveChanges")}</Button>
```

For plurals:

```tsx
// Before
`${count} comment${count !== 1 ? "s" : ""}`

// After (using existing feed.comments_one / feed.comments_other pattern)
t("feed.comments", { count })
```

### 4.2 Prioritisation (phased migration)

**Phase 1 — Authentication and onboarding (Sprint 1, ~2 days)**

Files: `Login.tsx`, `Register.tsx`, `ForgotPassword.tsx`, `ResetPassword.tsx`,
`MfaChallenge.tsx`, `VerifyEmail.tsx`

These are the first pages every user sees. Translating them has the highest user-facing impact
per component migrated. Extend the existing `auth.*` namespace.

**Phase 2 — Navigation and shell (Sprint 1, already mostly done)**

Files: Already covered by `Sidebar.tsx`, `MobileNav.tsx`. Add remaining labels to
`Header.tsx`, `MobileHeader.tsx`, toast messages in `AppShell.tsx`.

**Phase 3 — Core feature pages (Sprints 2–4)**

Priority order (highest traffic first):
1. `MessagesPage`, `ConversationView`, `ConversationList`, `ComposeBar`
2. `FeedPage`, `PostCard`, `CommentsThread`
3. `BillingPage`, `PaymentMethods`, `BillingHistory`
4. `FilesPage`, `FileManager`
5. `CalendarPage`, `EventCard`
6. `SettingsPage` (already partially done), `ProfilePage`

**Phase 4 — Admin and secondary pages (Sprint 5+)**

`AdminRoles.tsx`, `ImpersonationPage.tsx`, `ModerationBoard.tsx`, `TicketsPage.tsx`, and all
remaining pages.

### 4.3 Translation workflow for es and fr

After extracting English keys with `i18next-scanner`, the generated draft `es.json` and
`fr.json` will contain the English string as the value (marked for translation). A professional
translation pass (or a machine-translation + human-review pass) fills in the values. The
existing 135 keys already have correct es/fr translations as a baseline.

### 4.4 Dev/Prod parity (SECOPS-007)

i18n is a purely frontend concern. The locale files are bundled into the Vite output and served
as static assets. There is no backend i18n path and no AWS-backed service involved. SECOPS-007
does not apply to this gap.

The only runtime difference between dev and prod is locale file loading: the current
implementation uses static imports (`import en from "./locales/en.json"`), which means locale
files are bundled at build time. This is correct for dev and prod — no `i18next-http-backend`
dynamic loading is needed, and the installed `i18next-http-backend` package can be removed to
reduce bundle size.

### 4.5 RTL support

`RTLProvider.tsx` already imports `useTranslation` and calls `i18n.dir()` to set the `dir`
attribute. Arabic and Hebrew locales are listed in `_RTL_LOCALES` set in `i18n/index.ts`. When
those locales are added to the dictionaries, RTL layout will work automatically.

## 5. Testing, Verification & Rollout

### Regression tests

**Unit test — locale completeness**:

```typescript
// frontend/src/i18n/__tests__/locales.test.ts
import en from "../locales/en.json";
import es from "../locales/es.json";
import fr from "../locales/fr.json";

describe("Locale completeness", () => {
  const enKeys = Object.keys(en);

  it("es has all keys that en has", () => {
    const missing = enKeys.filter((k) => !(k in es));
    expect(missing).toEqual([]);
  });

  it("fr has all keys that en has", () => {
    const missing = enKeys.filter((k) => !(k in fr));
    expect(missing).toEqual([]);
  });

  it("no key has an empty translation", () => {
    for (const [key, val] of Object.entries(es)) {
      expect(val, `es["${key}"] is empty`).not.toBe("");
    }
    for (const [key, val] of Object.entries(fr)) {
      expect(val, `fr["${key}"] is empty`).not.toBe("");
    }
  });
});
```

This test **passes before and after the fix for the existing 135 keys**. As new keys are added,
the test enforces that all three locales are updated in the same commit.

**Playwright smoke test — language switcher**:

```typescript
// frontend/e2e/i18n.spec.ts
test("switching to Spanish shows translated nav labels", async ({ page }) => {
  await injectAuth(page, "alice");
  await page.goto("/settings");
  // Before fix: Nav labels remain in English after switching language.
  // After fix (Phase 1+): At minimum the nav labels switch language.
  await page.getByRole("combobox", { name: /language/i }).selectOption("es");
  await page.waitForTimeout(300);  // i18next applies synchronously but wait for re-render
  // Check one translated nav label that already exists in es.json
  const sidebar = page.locator("[data-testid='sidebar']");
  await expect(sidebar.getByText("Mensajes")).toBeVisible();  // nav.messages in es
});

test("switching to French shows translated nav labels", async ({ page }) => {
  await injectAuth(page, "alice");
  await page.goto("/settings");
  await page.getByRole("combobox", { name: /language/i }).selectOption("fr");
  await page.waitForTimeout(300);
  const sidebar = page.locator("[data-testid='sidebar']");
  await expect(sidebar.getByText("Messages")).toBeVisible();  // "Messages" in fr is same word
});
```

### Manual QA steps

1. `just up` (dev stack).
2. Log in as Alice, go to Settings → Language, switch to "Español".
3. Verify: sidebar navigation labels change to Spanish (Mensajes, Contactos, etc.).
4. Navigate to any non-migrated page (e.g., Billing) — verify English content is still shown
   (falls back to en key value, not raw key string).
5. After each phase of migration: repeat step 2–4 for the newly migrated pages.

### Coverage metric

Track migration progress with a CI check that measures the ratio of components using
`useTranslation` to total component files:

```bash
# scripts/check-i18n-coverage.sh
TOTAL=$(find frontend/src/pages -name "*.tsx" | wc -l)
TRANSLATED=$(grep -rl "useTranslation" frontend/src/pages --include="*.tsx" | wc -l)
COVERAGE=$(echo "scale=1; $TRANSLATED * 100 / $TOTAL" | bc)
echo "i18n coverage: $COVERAGE% ($TRANSLATED / $TOTAL)"
# Fail CI if coverage drops below the current watermark
MINIMUM=2  # raise this after each sprint
if (( $(echo "$COVERAGE < $MINIMUM" | bc -l) )); then
  echo "ERROR: i18n coverage below minimum $MINIMUM%"; exit 1
fi
```

Start the minimum at 2% (current state: 10/541 ≈ 1.85%), raise it by ~5% per sprint.

### Rollout

**Phase 1**: Migrate auth pages (Login, Register, ForgotPassword) in one PR. Update locale
files for all three languages in the same PR. CI locale-completeness test ensures no language
is left behind.

**Phase 2+**: One PR per feature domain (messages, billing, files, etc.). Each PR updates
`en.json`, `es.json`, and `fr.json` together. Raise the CI coverage watermark in the same PR.

**Risk**: Low — i18n migration is a display-layer change with no backend impact. The `t()`
function falls back to the key string if a translation is missing, so a missed key produces an
ugly but non-breaking UI rather than an error.

**Rollback**: Revert the frontend PR. No backend changes; no DynamoDB migrations.

**Effort estimate**: L (Large) — the infrastructure is in place; the migration itself is 4–6
sprints of frontend work across 530+ files. Individual phases can be shipped incrementally.
