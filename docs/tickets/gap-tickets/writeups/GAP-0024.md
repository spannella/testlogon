# GAP-0024: `ByCase` GSI Fallback Performs Full Table Scan — Remediation Write-up

> ~5 pages. Fix-oriented. Built on investigation doc: `docs/tickets/gap-tickets/investigations/GAP-0024.md`.

## 1. Summary & Classification

**Bug statement**: `KycIdScannerStore.list_scans_for_case()` in
`app/services/kyc_id_scanner.py:615-627` has an `except Exception` handler that, on any
failure of the `ByCase` GSI query, falls back to a full `self._table.scan()` with no
filter condition. Although the scan result is post-filtered by `case_id` in application
memory, the entire `kyc_id_scans` table — containing scan records for every user on the
platform — is loaded into the backend process before filtering. Under any error condition
that triggers the fallback, every user's ID scan metadata is accessible to the
requesting caller.

**One-line impact**: Any KYC reviewer can trigger a full dump of all users' scan records
by exploiting a GSI failure condition, either accidentally (GSI backfilling, throttle) or
deliberately (crafted requests that exhaust GSI read capacity).

## 2. Current-State Investigation (root cause)

### Code path today

`list_scans_for_case()` is defined at `app/services/kyc_id_scanner.py:615-627`:

```python
def list_scans_for_case(self, case_id: str) -> list[dict[str, Any]]:
    try:
        resp = self._table.query(
            IndexName="ByCase",
            KeyConditionExpression=Key("case_id").eq(case_id),
            ScanIndexForward=False,
        )
        return list(resp.get("Items", []))
    except Exception:
        resp = self._table.scan()               # full table scan, no filter
        items = [i for i in resp.get("Items", []) if i.get("case_id") == case_id]
        items.sort(key=lambda i: _coerce_int(i.get("created_at")), reverse=True)
        return items
```

The `except Exception` block catches every possible error: `ClientError` (throttle,
index not found, validation error), `ConnectionError`, `BotoCoreError`, or any other
exception. When any of these fires, the code calls `self._table.scan()` with no
arguments — no `FilterExpression`, no `Limit`, no pagination loop.

### Why the fallback is doubly dangerous

**1. Full data exposure in process memory**: DynamoDB's `scan()` returns items up to the
1MB page limit. On a busy production `kyc_id_scans` table, the first page may contain
hundreds or thousands of scan records from users who have no relation to `case_id`. All
of these are loaded into application memory. Any logging framework, APM agent, or memory
profiler that captures the `resp` object will record every user's scan data.

**2. Incomplete results even for the target case**: DynamoDB `scan()` without a
`LastEvaluatedKey` pagination loop only returns the first 1MB of the table. If the scan
result is truncated, scans associated with `case_id` that fall beyond the first page are
silently omitted. The caller receives an incomplete result while also having inadvertently
accessed data for unrelated users.

**3. Exploitable by deliberate throttling**: GSI read capacity can be exhausted by
crafting many concurrent `list_scans_for_case()` calls for valid but scan-heavy cases.
Once the GSI is throttled, subsequent calls fall into the `except` block and receive the
full table dump. This is a low-effort data exfiltration technique for any user with KYC
reviewer role.

### The `# pragma: no cover - defensive` comment

The investigation notes that the fallback block carries a `pragma: no cover` comment,
indicating it was intentionally excluded from test coverage. This confirms the author
treated it as a safe dead-code fallback, which it is not.

### Root cause

The fallback was written as a development convenience: during local-ddb-init races or
when the `ByCase` GSI has not yet been declared, the scan provides a working result.
The security implications of applying that fallback in production (where the table
contains real PII and thousands of user records) were not considered.

## 3. Impact / Exploit / Blast Radius

### Data exposed in the fallback

Each item in `kyc_id_scans` contains: `scan_id`, `case_id`, `user_sub`, `document_type`,
`status`, `created_at`, and potentially extraction metadata (field confidence scores,
document expiry dates, verification state). This is regulated PII under GDPR Article
9 (biometric / identity document processing).

### Caller surface

`list_scans_for_case()` is called from the KYC admin case detail endpoint
(`GET /kyc/cases/{case_id}/scans` or equivalent). The callers are KYC reviewers and
admin users. In a scenario where the GSI is degraded, every reviewer who opens any
case detail page triggers a full table scan and receives — in the API response — all
scan records whose `case_id` matches the requested case after in-memory filtering. The
rest of the loaded records are not sent to the client but are present in the process
memory and in any request log that captures the boto3 response object.

### Worst case

An attacker with KYC reviewer access (e.g., a compromised reviewer account or a
malicious insider) deliberately exhausts the `ByCase` GSI read capacity by sending many
requests in rapid succession. All subsequent genuine review requests fall into the
fallback and trigger full table scans. Over time, every KYC reviewer's case opens result
in all scan records being processed (and potentially logged) server-side, constituting a
systematic GDPR data breach.

### Availability impact

`scan()` on a large table consumes substantially more read capacity units than a targeted
GSI query. Each full-table scan fallback accelerates DynamoDB RCU consumption, potentially
throttling the entire `kyc_id_scans` table and cascading to other scan-related features.

## 4. Fix Design (code-level)

### Minimal fix (recommended)

Replace the three-line `except` block with a safe error return:

```python
# app/services/kyc_id_scanner.py:615-627 — after fix
def list_scans_for_case(self, case_id: str) -> list[dict[str, Any]]:
    try:
        resp = self._table.query(
            IndexName="ByCase",
            KeyConditionExpression=Key("case_id").eq(case_id),
            ScanIndexForward=False,
        )
        return list(resp.get("Items", []))
    except Exception:
        logger.exception(
            "kyc_id_scanner.list_scans_for_case: ByCase GSI query failed for case_id=%s",
            case_id,
        )
        return []
```

`logger.exception()` captures the full exception traceback for operational debugging.
Returning `[]` is safe: the admin UI can display "No scans available (database error)"
instead of silently returning incorrect data.

### Why returning `[]` is the correct safe failure

The three alternatives — scan + filter, raise and propagate, or return a synthetic error
item — all have worse properties than `[]`:

- **scan + filter**: the current unsafe behaviour; ruled out.
- **raise `ClientError`**: would cause the router to return 500, which may trigger
  client-side retry storms and does not give the UI a recoverable state.
- **Return synthetic error item**: invents data; confuses callers that check `len(result)`.

An empty list on error is the standard "fail safe" pattern used elsewhere in the codebase
(e.g., paginated list endpoints that return `{"items": [], "next_cursor": null}` on
DynamoDB errors).

### Pagination hardening (complementary fix)

The `try` block's current `query()` call also lacks a `LastEvaluatedKey` pagination loop.
For cases with more than ~400 scans (1MB / ~2.5KB per item), the query silently truncates.
The complementary fix:

```python
def list_scans_for_case(self, case_id: str) -> list[dict[str, Any]]:
    items: list[dict[str, Any]] = []
    last_key: dict | None = None
    try:
        while True:
            kwargs: dict[str, Any] = {
                "IndexName": "ByCase",
                "KeyConditionExpression": Key("case_id").eq(case_id),
                "ScanIndexForward": False,
            }
            if last_key:
                kwargs["ExclusiveStartKey"] = last_key
            resp = self._table.query(**kwargs)
            items.extend(resp.get("Items", []))
            last_key = resp.get("LastEvaluatedKey")
            if not last_key:
                break
    except Exception:
        logger.exception(
            "kyc_id_scanner.list_scans_for_case: ByCase GSI query failed for case_id=%s",
            case_id,
        )
        return []
    return items
```

This is a medium-complexity enhancement; the minimal fix (removing the scan fallback) is
sufficient to close the CRIT security issue and can be shipped independently.

### Dev/Prod parity (SECOPS-007)

In dev mode (DynamoDB Local), the `ByCase` GSI may be absent during a race between
`local-ddb-init.py` and the first service call. In production (AWS), the GSI is always
present once the table is created but may be throttled under load. In both environments
the correct behaviour on query failure is to log and return `[]`, not to fall back to a
full scan. No environment-specific code path is needed. No feature flag required.

### Backward compatibility

The change affects only the error path. All callers that receive an empty list on GSI
failure must handle it gracefully (show an empty state in the UI). No schema migrations.
No DynamoDB table changes.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline, moto)

```python
# tests/test_kyc_id_scanner_bycase_fallback.py
from unittest.mock import patch, MagicMock
import pytest
from app.services.kyc_id_scanner import KycIdScannerStore


@pytest.fixture
def scanner_with_failing_gsi():
    store = KycIdScannerStore()
    mock_table = MagicMock()
    mock_table.query.side_effect = Exception("GSI ByCase unavailable")
    # scan() would return sensitive data from other users
    mock_table.scan.return_value = {"Items": [
        {"scan_id": "s1", "case_id": "other_case",  "user_sub": "victim-user"},
        {"scan_id": "s2", "case_id": "target_case", "user_sub": "innocent-user"},
        {"scan_id": "s3", "case_id": "target_case", "user_sub": "innocent-user-2"},
    ]}
    store._table = mock_table
    return store


def test_list_scans_for_case_returns_empty_on_gsi_failure(scanner_with_failing_gsi):
    """
    BEFORE fix: returns filtered scan list (leaks data, scan() was called).
    AFTER fix:  returns [] and scan() is never called.
    """
    result = scanner_with_failing_gsi.list_scans_for_case("target_case")

    assert result == [], f"Expected safe empty list, got: {result}"
    scanner_with_failing_gsi._table.scan.assert_not_called()


def test_list_scans_for_case_logs_exception_on_gsi_failure(
    scanner_with_failing_gsi, caplog
):
    import logging
    with caplog.at_level(logging.ERROR):
        scanner_with_failing_gsi.list_scans_for_case("target_case")
    assert any("ByCase GSI query failed" in r.message for r in caplog.records)


def test_list_scans_for_case_normal_path_unchanged(ddb_tables):
    """Normal (non-error) path still returns scan records via GSI query."""
    from app.core.tables import T
    from app.core.time import now_ts

    scan_item = {
        "scan_id": "scan-abc",
        "case_id": "case-xyz",
        "user_sub": "user-normal",
        "status": "pending",
        "created_at": now_ts(),
    }
    T.kyc_id_scans.put_item(Item=scan_item)
    store = KycIdScannerStore()
    result = store.list_scans_for_case("case-xyz")
    assert any(r["scan_id"] == "scan-abc" for r in result)
```

**Before fix**: `test_list_scans_for_case_returns_empty_on_gsi_failure` fails because
`result` is `[{"scan_id": "s2", ...}, {"scan_id": "s3", ...}]` (the two matching items
from the full scan) and `scan.assert_not_called()` fails.
**After fix**: all three tests pass.

### Manual QA steps

1. Start the dev stack (`just up`).
2. Create a KYC case and upload a scan document.
3. In a test, mock the DynamoDB GSI to raise `ClientError` and call the scans endpoint.
4. Verify the endpoint returns HTTP 200 with `{"items": []}` and that no scan records
   for other users appear in the response.
5. Verify that `logger.exception(...)` produces an ERROR-level log entry with the
   `case_id`.

### Observability

The `logger.exception()` call in the fix provides automatic traceback logging. Add a
CloudWatch metric filter on `kyc_id_scanner.list_scans_for_case` + `ByCase GSI query
failed` to alert on-call when this error occurs in production. A spike in this metric is
an indicator of either GSI capacity issues or a deliberate exploitation attempt.

### Rollback

Restore the original three-line `except` block. No DynamoDB table changes. Rollback
restores the unsafe but functional fallback behaviour.

### Risk

**Near-zero**. The change only affects the error path. In normal operation (GSI healthy),
behaviour is identical. On error, callers receive `[]` instead of a potentially partial
scan dump. The only operational risk is a KYC reviewer seeing an empty scan list during
a GSI outage instead of partial data; this is the correct trade-off for a security fix.

### Effort

**S** — estimated 15-30 minutes: replace three lines in the `except` block, add
`logger.exception(...)`, write two pytest tests, run `just test`.

### Sequencing

Apply immediately — this is the smallest and safest CRIT fix in this batch. It can be
deployed independently. Coordinate with GAP-0260 (declare `ByCase` GSI `attr_types` for
numeric sort key in `local-ddb-init.py`) to reduce the likelihood of the GSI failure
occurring in the first place, making the safe fallback path a true last resort rather
than a common code path.

### Why the `# pragma: no cover` comment is itself a risk signal

The `# pragma: no cover - defensive` comment on the `except` block confirms that the
fallback path has never been executed in any test run. In normal software this means the
path is dead code; in security-sensitive code it means the path has never been reviewed
for data exposure. Any `except` block that loads sensitive data and is intentionally
excluded from coverage should be treated as a high-priority audit target. The fix
eliminates the unsafe code and can remove the `pragma` comment entirely.

### Secondary fix: remove the `pragma` comment

After applying the safe `return []` fix, remove the `# pragma: no cover - defensive`
comment from the `except` block. The new code is simple enough to be covered by the
mock-based unit test (`mock_table.query.side_effect = Exception`) and should be
included in coverage reporting rather than excluded.

```python
    except Exception:
        logger.exception(
            "kyc_id_scanner.list_scans_for_case: ByCase GSI query failed for case_id=%s",
            case_id,
        )
        return []
        # No pragma: no cover — this path IS tested and MUST be safe
```

### Broader pattern: audit all `except` blocks that call `scan()`

As a follow-up to this fix, a one-time codebase audit should search for any other
`except` block that falls back to a DynamoDB `scan()`:

```bash
grep -rn "\.scan(" app/services/ | grep -v "^Binary file"
```

Each result should be reviewed to confirm it does not expose cross-user data on error.
The `ByCase` pattern in `kyc_id_scanner.py` may be duplicated in other KYC services
that were written around the same time.
