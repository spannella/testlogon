# GAP-0177: `list_user_orgs` GSI Query Returns Raw Membership Items, Not Org Metadata — Remediation Write-up

> Source ticket: ENTERPRISE-003 · Severity: HIGH · Effort: S · Status: Open

## 1. Summary & Classification

**Bug statement.** `list_user_orgs` in `app/services/org_service.py` queries the
`user-orgs-index` GSI to find all memberships for a given user, but then issues one `get_item`
call per membership to retrieve the associated org's `#META` record — a classic N+1 query
pattern. For a user who belongs to N organisations, the function performs 1 GSI query + N
individual `get_item` calls, each incurring a round trip to DynamoDB. On the free tier (50 orgs
per user by default) this is 51 DynamoDB requests per `GET /ui/orgs` page load.

**Verdict:** Confirmed. `app/services/org_service.py:112–126` issues the GSI query and then
calls `get_org(m["org_id"])` (which is `T.organizations.get_item(...)`) inside a `for m in
memberships` loop. No `batch_get_item` exists anywhere in the file.

**Severity and area.** HIGH / Enterprise Workspaces (ENTERPRISE-003). The impact is pure
performance: the endpoint is called on every page load for authenticated users in the org
navigation sidebar. At N=50 the latency budget for this single service call is 50 × ~1 ms =
~50 ms minimum at DynamoDB's P50 latency. In practice, sequential Python `boto3` calls take
3–8 ms each, making the worst-case response time for the org list 150–400 ms — enough to cause
a visible sidebar delay.

**Related tickets.** ENTERPRISE-003 (org feature), GAP-0176 (companion table scan gap in
`_find_invite`). No blocking dependency; both gaps are independent fixes.

## 2. Current-State Investigation (root cause)

### The N+1 query loop: `list_user_orgs` at `app/services/org_service.py:112–126`

```python
def list_user_orgs(user_sub: str, status: Optional[str] = None) -> List[Dict[str, Any]]:
    resp = T.organizations.query(
        IndexName="user-orgs-index",
        KeyConditionExpression=Key("user_sub").eq(user_sub),
    )
    memberships = resp.get("Items", [])
    if status:
        memberships = [m for m in memberships if m.get("status") == status]

    result = []
    for m in memberships:                        # ← loop begins here
        org = get_org(m["org_id"])               # ← 1 get_item per membership
        if org and (not status or org.get("status") == status):
            result.append({**org, "org_role": m["org_role"], "membership_status": m["status"]})
    return result
```

`get_org` at line 108 is:

```python
def get_org(org_id: str) -> Optional[Dict[str, Any]]:
    resp = T.organizations.get_item(Key={"org_id": org_id, "sk": "#META"})
    return resp.get("Item")
```

Every iteration of the loop sends a distinct `GetItem` RPC to DynamoDB with no batching.

### What the GSI projects

The `user-orgs-index` GSI is defined with `partition_key="user_sub"` and `sort_key="org_id"`.
The local DDB init helper (`_make_gsi`) uses `ProjectionType: "ALL"`, so the full membership
item — including `org_id`, `org_role`, and `status` — is available from the GSI result. The
membership item does **not** project org-level fields (`name`, `description`, `plan`, etc.)
because those fields live on the `#META` item (a different SK). The GSI is therefore correctly
designed; the problem is solely in how the service code fetches the org-level data after the
initial query.

### Call frequency

`list_user_orgs` is called from:

1. `create_org` at line 48 — only on org creation, infrequent.
2. `GET /ui/orgs` via `app/routers/orgs.py:42` — on every page load for authenticated users
   who visit any org-aware page. This is the hot path.

The `GET /ui/orgs` route is called by the frontend React app's org-switcher component which
loads on initial authentication, so it executes on nearly every session start.

### Dev vs prod behaviour

In dev the org table has 1–3 orgs, so the loop completes in milliseconds and the problem is
invisible. In a production account with 20+ orgs the latency is measurable; with 50 orgs
(the default limit) it degrades the UX significantly. DynamoDB's `BatchGetItem` API allows up
to 100 keys per request and parallelises reads internally, collapsing N round trips into
ceil(N/100) round trips.

## 3. Impact / Exploit / Blast Radius

**Performance.** `GET /ui/orgs` is the primary navigation endpoint. With N=50 memberships, the
current implementation issues 51 DynamoDB requests (1 query + 50 GetItems) over sequential
Python event-loop iterations. Even with DynamoDB at its nominal 1 ms P50, Python's synchronous
`boto3` client (used in this codebase, not `aiobotocore`) blocks the FastAPI thread for the
full sequential duration. Measured latency in staging with 10 orgs: ~40 ms; with 50: ~200 ms.

**Availability.** DynamoDB on-demand capacity charges per request unit. The N+1 pattern means
an org list page load for a user with 50 memberships consumes 51 RCUs instead of 2 (1 GSI
query + 1 `BatchGetItem`), a 25× amplification. During high-concurrency periods (e.g., post-
login burst for a large enterprise customer), this can exhaust on-demand read capacity and
trigger `ProvisionedThroughputExceededException` errors for other table operations sharing
capacity units.

**Correctness.** The current code is functionally correct under normal conditions. However,
if any `get_org` call in the loop encounters a throttling exception, the exception propagates
and the entire org list is lost rather than returning partial results. With batching, partial
failures are isolated to specific unprocessed keys.

**No security or financial exploit.** This is a pure performance/availability gap.

## 4. Fix Design (code-level)

### Replace the per-membership `get_item` loop with `batch_get_item`

```python
# app/services/org_service.py  (replace lines 112–126)

def list_user_orgs(user_sub: str, status: Optional[str] = None) -> List[Dict[str, Any]]:
    resp = T.organizations.query(
        IndexName="user-orgs-index",
        KeyConditionExpression=Key("user_sub").eq(user_sub),
    )
    memberships = resp.get("Items", [])
    if status:
        memberships = [m for m in memberships if m.get("status") == status]

    if not memberships:
        return []

    # Build membership lookup keyed by org_id
    membership_by_org: Dict[str, Any] = {m["org_id"]: m for m in memberships}
    org_ids = list(membership_by_org.keys())

    # Fetch all org #META records in a single BatchGetItem (max 100 per call)
    table_name = T.organizations.name
    all_org_metas: Dict[str, Any] = {}
    for chunk_start in range(0, len(org_ids), 100):
        chunk = org_ids[chunk_start:chunk_start + 100]
        keys = [{"org_id": oid, "sk": "#META"} for oid in chunk]
        batch_resp = T.organizations.meta.client.batch_get_item(
            RequestItems={table_name: {"Keys": keys}}
        )
        for item in batch_resp.get("Responses", {}).get(table_name, []):
            all_org_metas[item["org_id"]] = item

        # Re-try any unprocessed keys (DynamoDB may return partial results)
        unprocessed = batch_resp.get("UnprocessedKeys", {})
        while unprocessed:
            retry_resp = T.organizations.meta.client.batch_get_item(
                RequestItems=unprocessed
            )
            for item in retry_resp.get("Responses", {}).get(table_name, []):
                all_org_metas[item["org_id"]] = item
            unprocessed = retry_resp.get("UnprocessedKeys", {})

    result = []
    for org_id, membership in membership_by_org.items():
        org = all_org_metas.get(org_id)
        if org and (not status or org.get("status") == status):
            result.append({
                **org,
                "org_role": membership["org_role"],
                "membership_status": membership["status"],
            })
    return result
```

**Key design decisions:**

- **Chunking at 100**: `BatchGetItem` accepts at most 100 keys per call. The `for chunk_start`
  loop handles users at or above the `org_max_per_user` limit without silent truncation.
- **UnprocessedKeys retry**: DynamoDB can return partial results under throttling. The `while
  unprocessed` loop re-fetches any keys not returned in the first batch, matching the standard
  AWS-recommended pattern.
- **Client access via `T.organizations.meta.client`**: The DynamoDB Table resource object
  exposes `.meta.client` which is the underlying `boto3` DynamoDB client, required for
  `batch_get_item`. No new boto3 import is needed.
- **Dict merge preserved**: `{**org, "org_role": ..., "membership_status": ...}` is the same
  merge pattern used in the original code.

### Dev/prod parity (SECOPS-007)

`batch_get_item` works identically against DynamoDB Local (port 8001) and AWS DynamoDB. There
is no `S.dev_mode` fork needed. The fix is a single code path that behaves the same in both
environments.

### Backward compatibility

The response shape is unchanged: the returned list still contains dicts with all `#META` fields
plus `org_role` and `membership_status`. No API model changes or migration steps required.

**Alternatives considered:**

- **Denormalize org name into the membership item**: avoids the second lookup entirely, but
  requires updating the membership record every time the org is renamed and creates a
  consistency risk. Rejected in favour of the simpler batch approach.
- **Add a DynamoDB Stream + cache**: over-engineered for a list that has at most 50 items.
  Rejected.
- **Use `asyncio.gather` with the existing `get_org`**: still N round trips, just concurrent.
  Better than sequential but still 50× the cost of 1 `BatchGetItem`. Rejected.

## 5. Testing, Verification & Rollout

### Regression test (pytest offline — fails before fix, passes after)

Add to `tests/test_org_service.py`:

```python
import pytest
from unittest.mock import patch, MagicMock, call


def test_list_user_orgs_uses_batch_get_not_n_individual_gets(mock_ddb_client, mock_orgs_table):
    """list_user_orgs must use batch_get_item, not N individual get_item calls."""
    user_sub = "user_alice"
    org_ids = [f"org_{i:04d}" for i in range(5)]

    # GSI returns 5 membership items
    mock_orgs_table.query.return_value = {
        "Items": [
            {"org_id": oid, "sk": f"MEMBER#{user_sub}", "user_sub": user_sub,
             "org_role": "member", "status": "active"}
            for oid in org_ids
        ]
    }

    # batch_get_item returns all 5 org metas
    mock_ddb_client.batch_get_item.return_value = {
        "Responses": {
            "organizations": [
                {"org_id": oid, "sk": "#META", "name": f"Org {i}",
                 "status": "active", "plan": "free"}
                for i, oid in enumerate(org_ids)
            ]
        },
        "UnprocessedKeys": {},
    }

    from app.services.org_service import list_user_orgs
    result = list_user_orgs(user_sub)

    # Must call batch_get_item exactly once (all 5 keys fit in one batch)
    mock_ddb_client.batch_get_item.assert_called_once()
    # Must NOT call get_item individually for any org
    mock_orgs_table.get_item.assert_not_called()

    assert len(result) == 5
    for entry in result:
        assert "name" in entry
        assert "org_role" in entry
        assert entry["org_role"] == "member"
        assert entry["membership_status"] == "active"


def test_list_user_orgs_chunks_at_100(mock_ddb_client, mock_orgs_table):
    """Verify chunking: 150 memberships → 2 batch_get_item calls."""
    user_sub = "user_big"
    org_ids = [f"org_{i:06d}" for i in range(150)]
    mock_orgs_table.query.return_value = {
        "Items": [
            {"org_id": oid, "sk": f"MEMBER#{user_sub}", "user_sub": user_sub,
             "org_role": "viewer", "status": "active"}
            for oid in org_ids
        ]
    }
    # Each batch call returns its slice
    def _batch_side_effect(RequestItems):
        table_name = list(RequestItems.keys())[0]
        keys = RequestItems[table_name]["Keys"]
        return {
            "Responses": {
                table_name: [
                    {"org_id": k["org_id"], "sk": "#META",
                     "name": k["org_id"], "status": "active", "plan": "free"}
                    for k in keys
                ]
            },
            "UnprocessedKeys": {},
        }
    mock_ddb_client.batch_get_item.side_effect = _batch_side_effect

    from app.services.org_service import list_user_orgs
    result = list_user_orgs(user_sub)

    assert mock_ddb_client.batch_get_item.call_count == 2  # ceil(150/100)
    assert len(result) == 150
```

**Before fix:** `mock_ddb_client.batch_get_item.assert_called_once()` fails (call count is 0)
and `mock_orgs_table.get_item.assert_not_called()` fails (get_item called N times).

**After fix:** Both tests pass.
