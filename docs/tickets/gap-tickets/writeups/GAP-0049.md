# GAP-0049: Platform Revenue (30% Share) Not Written to Any Ledger — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Claim (from ticket):** `app/services/ad_billing.py:_split_revenue` calculates the platform's 30% revenue share but never writes it to any ledger; no audit trail exists for platform-side ad revenue; reconciliation is impossible.

**Verdict: Claim confirmed.** The function at `ad_billing.py:150-169` computes both `platform_share` and `creator_share`, writes the creator share to `T.billing`, but silently discards the `platform_share` variable after computing it. The `T.ad_billing` table is never written to in `_split_revenue` (only in `_process_charge` before calling `_split_revenue`). There is no `PLATFORM#revenue` row or similar anywhere in the codebase.

- **Severity:** HIGH (financial audit / reconciliation failure)
- **Source ticket:** ADS-007
- **Owning area:** Ad Billing / Platform Finance
- **Status:** Open
- **Effort:** S
- **Related tickets:** GAP-0048 (same service file), GAP-0008 (commission replay — related reconciliation gap), GAP-0050 (analytics uses revenue data)

### Background: The revenue split model

The platform applies a 70/30 revenue share on all ad charges: creators receive 70% of the advertiser's charge as a credit to their `T.billing` ledger (`ad_revenue_credit` entries), and the platform retains 30% as operating revenue. Both sides of this split should be written to a durable ledger immediately when the charge is processed. In the current implementation, only the creator's 70% is persisted; the platform's 30% is computed, stored temporarily in a local variable, and discarded when the function returns. This asymmetry means the platform's own ad revenue is invisible to every financial system that relies on DynamoDB ledger data.

## 2. Current-State Investigation (root cause)

### The split function in full

`app/services/ad_billing.py:150-169`:

```python
def _split_revenue(*, charge_cents: int, creator_id: str, meta: dict, ts: int) -> None:
    """Split ad revenue between platform and creator."""
    platform_share = max(0, (charge_cents * PLATFORM_REVENUE_SHARE_PCT) // 100)
    creator_share = charge_cents - platform_share

    # Credit creator via existing billing ledger
    if creator_share > 0 and creator_id:
        try:
            _sk, credit_item = new_ledger_entry(
                key_name="pk",
                key_value=user_pk(creator_id),
                entry_type="ad_revenue_credit",
                amount_cents=creator_share,
                state="settled",
                reason="Ad revenue share",
                meta={**meta, "platform_share_pct": PLATFORM_REVENUE_SHARE_PCT},
            )
            T.billing.put_item(Item=credit_item)
        except Exception:
            logger.warning("ad_revenue_creator_credit_failed", extra={"creator_id": creator_id})

    # platform_share is computed but NEVER written to any table
```

`platform_share` is computed on line 152 and referenced only by the `meta` dict passed to the creator credit entry. After the function returns, the platform's share is invisible to any audit, reporting, or reconciliation system.

### Call site

`_split_revenue` is called from `_process_charge` at `ad_billing.py:142`:

```python
# 4. Revenue split
_split_revenue(charge_cents=charge_cents, creator_id=creator_id, meta=meta, ts=ts)
```

The `_process_charge` function itself writes the advertiser charge to `T.ad_billing` (lines 110-123) and debits the account balance (lines 126-131), but the revenue split is fully delegated to `_split_revenue`, which only writes one of the two derived records.

### What is missing

For each charge of `charge_cents`:
- **Written:** Advertiser debit ledger entry (`T.ad_billing`, `pk=ACCT#{account_id}`)
- **Written:** Creator credit ledger entry (`T.billing`, `pk=USER#{creator_id}`)
- **NOT written:** Platform revenue credit entry (should go to `T.ad_billing` or a dedicated platform revenue table)

The proposed fix in the ticket suggests `pk=PLATFORM#revenue` in `T.ad_billing`, which follows the existing PK naming convention of that table (`ACCT#...` for advertiser records). Using the same table avoids a new table dependency and keeps all ad-related financial records queryable in one place.

### Revenue share constants

`PLATFORM_REVENUE_SHARE_PCT = 30` at `ad_billing.py:19`. For a $1.00 charge (`charge_cents=100`), `platform_share = 30` cents, `creator_share = 70` cents. Neither integer division truncation nor rounding creates a gap: `max(0, 100 * 30 // 100) = 30`, `creator_share = 70`.

For very small charges (e.g. CPM model: `charge_cents = max(1, bid_cpm_cents // 1000)`), `platform_share` could be as low as 0 for a `charge_cents=1` or `charge_cents=2` input. The `max(0, ...)` guard already handles this; when `platform_share == 0`, no entry needs to be written (the `if platform_share > 0:` guard in the fix below handles this case).

The constant `PLATFORM_REVENUE_SHARE_PCT` and the `charge_cents * pct // 100` formula must be the single source of truth. The fix preserves this — it does not introduce a second copy of the calculation.

## 3. Impact / Exploit / Blast Radius

**Financial audit failure:**
The platform's own revenue from ad billing is not recorded in any ledger. Finance cannot independently verify how much the platform earned from advertising without cross-joining advertiser charge records and applying the 70/30 split formula manually — an error-prone process that defeats the purpose of a ledger.

**Reconciliation impossibility:**
The `generate_invoice` function at `ad_billing.py:260-308` aggregates advertiser charges for monthly billing but does not include platform revenue totals. Any "platform revenue for month X" query returns zero or requires an outside calculation.

**Tax and compliance risk:**
Revenue from advertising must typically be reported for tax purposes. Without a ledger entry per transaction, any tax calculation must reconstruct revenue from the advertiser charge table, which is reliable today but could diverge if the revenue share percentage changes, if adjustments/refunds are applied, or if back-dated charges occur.

**No user-facing exploit.** This is a pure financial-record integrity gap. Users and advertisers are not directly affected; advertiser balances and creator credits are written correctly. The platform's own accounting is the affected party.

**Interaction with GAP-0050 (analytics rollups):** `compute_hourly_rollup` in `ad_analytics.py:200` computes `revenue_cents = int(spend * 0.7)` directly from the advertiser charge amount rather than from a ledger query. This means analytics does not depend on the missing platform revenue record for its rollup calculation. However, any future reconciliation job that compares the sum of `platform_revenue_credit` entries against `sum(advertiser_charges) * 0.30` will find a gap covering the entire period before this fix is deployed. The expected discrepancy is 30% of all ad spend to date.

**Blast radius:**
- Every charge ever processed since ADS-007 was deployed is missing a corresponding platform revenue record.
- All `ad_analytics` and `generate_invoice` summaries that try to compute platform revenue return incorrect (zero or absent) figures.
- Any future reconciliation task (compare `sum(platform_revenue)` vs `sum(advertiser_charges) * 0.30`) will find a non-zero discrepancy for every historical charge.

## 4. Fix Design (code-level)

### Change 1 — Write platform revenue entry in `_split_revenue`

In `app/services/ad_billing.py`, extend `_split_revenue` to write a platform revenue ledger entry to `T.ad_billing`:

```python
def _split_revenue(*, charge_cents: int, creator_id: str, meta: dict, ts: int) -> None:
    """Split ad revenue between platform and creator."""
    platform_share = max(0, (charge_cents * PLATFORM_REVENUE_SHARE_PCT) // 100)
    creator_share = charge_cents - platform_share

    # Credit creator via existing billing ledger
    if creator_share > 0 and creator_id:
        try:
            _sk, credit_item = new_ledger_entry(
                key_name="pk",
                key_value=user_pk(creator_id),
                entry_type="ad_revenue_credit",
                amount_cents=creator_share,
                state="settled",
                reason="Ad revenue share",
                meta={**meta, "platform_share_pct": PLATFORM_REVENUE_SHARE_PCT},
            )
            T.billing.put_item(Item=credit_item)
        except Exception:
            logger.warning("ad_revenue_creator_credit_failed", extra={"creator_id": creator_id})

    # NEW: Write platform revenue record to ad_billing table
    if platform_share > 0:
        try:
            entry_id = f"rev_{uuid.uuid4().hex[:12]}"
            month_key = datetime.fromtimestamp(ts, tz=timezone.utc).strftime("%Y-%m")
            T.ad_billing.put_item(Item={
                "pk": "PLATFORM#revenue",
                "sk": f"LEDGER#{ts}#{entry_id}",
                "entry_id": entry_id,
                "entry_type": "platform_revenue_credit",
                "amount_cents": platform_share,
                "state": "settled",
                "reason": "Platform ad revenue share (30%)",
                "meta": {
                    **meta,
                    "creator_id": creator_id,
                    "creator_share_cents": creator_share,
                    "charge_cents": charge_cents,
                    "platform_share_pct": PLATFORM_REVENUE_SHARE_PCT,
                },
                "month_key": month_key,
                "created_at": ts,
            })
        except Exception:
            logger.warning("ad_revenue_platform_credit_failed", extra={"charge_cents": charge_cents})
```

**Key design choices:**
- `pk="PLATFORM#revenue"` — follows the `ACCT#...` / `USER#...` convention already in the table; uses a non-user PK namespace that won't collide.
- `sk=f"LEDGER#{ts}#{entry_id}"` — identical SK format to advertiser charge entries, enabling unified time-range queries and the existing `generate_invoice` query patterns.
- `month_key` — written so the existing `ByMonth` GSI can be queried for platform monthly summaries.
- Wrapped in `try/except` with a warning log — consistent with the creator credit path; a failure to write the platform record must not block the advertiser charge (which is the primary financial event).

### Change 2 — `generate_invoice` platform summary (optional, same PR)

Extend `generate_invoice` to also return `platform_revenue_cents` for a given month:

```python
platform_revenue = sum(
    int(e.get("amount_cents", 0))
    for e in entries
    if e.get("entry_type") == "platform_revenue_credit"
)
return {
    ...
    "total_charges_cents": grand_total,
    "total_deposits_cents": deposits,
    "platform_revenue_cents": platform_revenue,  # NEW
    "entry_count": len(entries),
}
```

However this requires querying `pk="PLATFORM#revenue"` with `month_key` filter (the `ByMonth` GSI queries by `month_key` so it works). This is a backward-compatible addition.

### Backfill consideration

All historical charges since ADS-007 deployment are missing platform revenue records. A one-time backfill script can reconstruct them by scanning `T.ad_billing` for all `entry_type in ("impression_charge", "click_charge", "conversion_charge")` entries, computing 30% of each `amount_cents`, and writing the corresponding `PLATFORM#revenue` record — with a `ConditionExpression("attribute_not_exists(pk)")` guard on each SK to avoid double-counting.

This backfill is out-of-scope for this remediation but should be tracked in a follow-on ticket.

### Dev/Prod parity (SECOPS-007)

The write goes to `T.ad_billing`, which uses the DynamoDB Local endpoint in dev and AWS DynamoDB in prod. No mock, no flag. The `T` table handle wires automatically to the correct endpoint via `app/core/tables.py`. The existing `T.ad_billing.put_item` call on line 110 of `_process_charge` uses exactly the same table handle; the new write is identical in form. No SECOPS-007 parity gap exists.

import pytest
from unittest.mock import patch, MagicMock, call


class TestSplitRevenuePlatformEntry:
    def _run_split(self, charge_cents=100, creator_id="creator_001"):
        from app.services.ad_billing import _split_revenue

        mock_ad_billing = MagicMock()

             patch("app.services.ad_billing.new_ledger_entry") as mock_nle:
            mock_t.billing = mock_billing
            mock_t.ad_billing = mock_ad_billing
            mock_nle.return_value = ("sk_123", {"pk": f"USER#{creator_id}", "sk": "sk_123"})
            _split_revenue(
                charge_cents=charge_cents,
                creator_id=creator_id,
                meta={"campaign_id": "camp_001"},
                ts=1748000000,
            )
        return mock_ad_billing

    def test_platform_revenue_entry_written(self):
        """_split_revenue must write a platform_revenue_credit to T.ad_billing."""
        mock_ad_billing = self._run_split(charge_cents=100)
        # FAILS BEFORE FIX: put_item never called on ad_billing in _split_revenue
        mock_ad_billing.put_item.assert_called_once()
        item = mock_ad_billing.put_item.call_args[1]["Item"]

        assert item["entry_type"] == "platform_revenue_credit"

        """Platform gets exactly 30% (integer division, rounded down)."""
        mock_ad_billing = self._run_split(charge_cents=333)
        item = mock_ad_billing.put_item.call_args[1]["Item"]
        # 333 * 30 // 100 = 99
        assert item["amount_cents"] == 99

    def test_creator_share_correct(self):
        """Creator gets charge_cents minus platform_share."""
        from app.services.ad_billing import _split_revenue
        from unittest.mock import patch, MagicMock
        mock_billing = MagicMock()
        with patch("app.services.ad_billing.T") as mock_t, \
             patch("app.services.ad_billing.new_ledger_entry") as mock_nle:
            mock_t.billing = mock_billing
            mock_t.ad_billing = MagicMock()

                charge_cents=100, creator_id="c", meta={}, ts=1748000000

    def test_platform_entry_has_month_key(self):
        """Platform revenue entry includes month_key for ByMonth GSI."""
        mock_ad_billing = self._run_split(charge_cents=200)
        item = mock_ad_billing.put_item.call_args[1]["Item"]
        assert "month_key" in item
        assert len(item["month_key"]) == 7  # "YYYY-MM"

    def test_platform_entry_failure_does_not_raise(self):
        """A DynamoDB error on platform write is swallowed (warning logged)."""
        from app.services.ad_billing import _split_revenue
        mock_ad_billing = MagicMock()
        mock_ad_billing.put_item.side_effect = Exception("DDB error")
        with patch("app.services.ad_billing.T") as mock_t, \
             patch("app.services.ad_billing.new_ledger_entry") as mock_nle:
            mock_t.billing = MagicMock()
            mock_t.ad_billing = mock_ad_billing
            mock_nle.return_value = ("sk", {"pk": "USER#c", "sk": "sk"})

            _split_revenue(charge_cents=100, creator_id="c", meta={}, ts=1748000000)

**Fails before fix:** `test_platform_revenue_entry_written` — `mock_ad_billing.put_item` is never called in `_split_revenue` (only in `_process_charge`).
**Passes after fix:** All five tests pass.

### Rollout

- **Effort:** S (approximately 2-3 hours: code change + tests + optional `generate_invoice` extension)
- **Risk:** Low. The write is behind a `try/except`; a DynamoDB failure is logged but does not break the charge. The PK `PLATFORM#revenue` is a new namespace in an existing table — no schema change required.
- **Migration/backfill:** Historical charges are not retroactively credited. A follow-on backfill ticket should scan existing charge entries and generate the missing platform records with a `ConditionExpression` idempotency guard.
- **Rollback:** Remove the new `if platform_share > 0:` block from `_split_revenue`. No DynamoDB structural cleanup needed.
- **Sequencing:** Can be merged independently or bundled with GAP-0048 (same file). No dependency on GAP-0050.
