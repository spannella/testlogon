# GAP-0231: Event Timeline Not Implemented — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code; file:line citations are from
> the live codebase at `/home/ubuntu/testlogon`.

## 1. Summary & Classification

**Gap**: The INFRA-008 ticket design specifies an event timeline for compute resources
(EC2 instances and K8s pods). Each lifecycle event — launch, stop, start, reboot,
terminate, auto-terminate — is supposed to be written to the same DynamoDB table
under a sort-key pattern `TIMELINE#{instance_id}#{ts}#{event_id}`. A dedicated
`GET /ui/compute/monitoring/instances/{id}/timeline` endpoint is also specified.
Neither the `record_timeline_event()` service function nor the API endpoint exist in
any file in the repository.

**Severity**: HIGH. Owning area: Infrastructure / Compute (INFRA-008).
**Status**: Open. **Source ticket**: INFRA-008.

**Claim accuracy**: Confirmed. Zero timeline-related code appears in
`app/services/ec2_launcher.py`, `app/services/k8s_launcher.py`,
`app/services/instance_monitoring.py`, or `app/routers/instance_monitoring.py`.
`grep -rn "TIMELINE" app/` returns hits only in unrelated files (messaging, KYC).

**Impact**: Operators and users cannot view a chronological audit trail of instance
lifecycle events. Debugging production issues (unexpected shutdowns, auto-terminate
firings) requires manually correlating CloudWatch/application logs.

**Related tickets**: INFRA-008 (parent), GAP-0237 (missing ByGlobalStatus GSI),
GAP-0222 (real EC2 launch path stub), SECOPS-007 (dev/prod parity).


## 2. Current-State Investigation (root cause)

### EC2 service — no timeline writes

`app/services/ec2_launcher.py` implements `launch_instance` (line 116),
`stop_instance` (line 261), `start_instance` (line 290), `terminate_instance`
(line 320), and `reboot_instance` (line 358). Each function follows the same
pattern: validate the current state, call the mock or real compute backend,
update the item in `T.ec2_instances`, and emit a structured log message. No function
calls any timeline recording function. The representative example from
`terminate_instance` is:

```python
# ec2_launcher.py:336-354
T.ec2_instances.update_item(
    Key={"user_sub": user_sub, "sk": f"INSTANCE#{instance_id}"},
    UpdateExpression="SET #st = :st, terminated_at = :ta",
    ExpressionAttributeNames={"#st": "status"},
    ExpressionAttributeValues={":st": "terminated", ":ta": now},
)
item["status"] = "terminated"
item["terminated_at"] = now
logger.info("ec2_terminated user_sub=%s instance_id=%s", user_sub, instance_id)
return item
```

The auto-terminate background path `check_idle_instances` (line 385) scans for idle
running instances and calls `terminate_instance` but also skips timeline recording.
The `reboot_instance` function (line 358) likewise only updates `last_activity_at`
and logs; no timeline item is written.

### K8s service — identical gap

`app/services/k8s_launcher.py` implements `launch_pod` (line 112) and
`terminate_pod` (line 260). The K8s service follows the identical pattern: DDB writes
plus log calls and nothing else. There is no equivalent of `stop_instance` or
`start_instance` for pods (K8s pods are terminated, not stopped), so the relevant
lifecycle transitions are launch and terminate only. The `check_expired_pods`
background task (line 289) auto-terminates pods past their TTL without recording any
event. Like the EC2 service, `logger.info("k8s_pod_terminated ...")` is the only
record produced.

### Monitoring router — no timeline endpoint

`app/routers/instance_monitoring.py` implements five endpoints under the
`/ui/compute/monitoring` prefix: `ingest_metric`, `seed_metrics`, `latest_metric`,
`metric_series`, and `instance_health`. There is no `/instances/{id}/timeline` route.
The service module `app/services/instance_monitoring.py` similarly has no
`record_timeline_event` or `list_timeline_events` function. The monitoring system is
entirely metric-focused (CPU, memory, disk, network) and has no awareness of
lifecycle state changes.

### DynamoDB schema — table exists but timeline key pattern is unused

`app/core/tables.py` line 484 wires `T.ec2_instances` and line 495 wires
`T.k8s_pods`. Both tables use `PK=user_sub`, `SK=INSTANCE#` / `SK=POD#`. The
INFRA-008 design calls for timeline items to share the same table under
`SK=TIMELINE#{instance_id}#{ts}#{event_id}`. This is a common single-table pattern
where the same PK hosts multiple item types distinguished by SK prefix.
Currently no such items are ever written; the table is entirely free of
`TIMELINE#` sort-key entries.

### Dev vs prod — parity exists only by omission

`ec2_launcher.py` line 176 forks between `if S.ec2_mock_enabled:` (calls the
in-process mock store) and `raise NotImplementedError` (the real AWS path not yet
implemented). The real AWS compute path is a stub (see also GAP-0222). Timeline
recording must be inserted before this conditional so it runs regardless of
which backend is selected. Because timeline writes go to DynamoDB only — not the
compute backend — they are backend-agnostic by nature, satisfying SECOPS-007.


## 3. Impact / Exploit / Blast Radius

**Operational**: Without a timeline, operators lose the ability to answer:
- "When did this instance last change state and why?"
- "Was this a user-initiated stop or an auto-terminate triggered by idle timeout?"
- "Which background task terminated my pod — the TTL checker or a manual delete?"
- "Was there a pattern of frequent stop/start cycles indicating instability?"

All of these questions currently require manually correlating application logs
(`ec2_terminated`, `k8s_pod_terminated`, etc.) across log aggregation systems. In
production, those log entries may be rotated, batched, or delayed.

**Compliance / audit**: INFRA-008 explicitly included the timeline as an audit
feature for privileged compute operations. Without it, there is no immutable
application-layer record of who triggered which lifecycle event and when. Log
entries in CloudWatch or a log aggregator can be excluded from the product's audit
trail. The timeline in DynamoDB is owned by the application and can be exported,
retained, and queried independently.

**Debugging auto-terminate false positives**: The `check_idle_instances` function
(ec2_launcher.py line 385) terminates any running instance where
`now - last_activity_at > auto_terminate_after`. If `last_activity_at` is incorrectly
zero — for example, because a future code path fails to set it — instances are
silently destroyed with no application-layer explanation. A timeline entry
`auto_terminated` with `detail={"idle_seconds": N}` would immediately identify the
root cause in a support investigation.

**K8s TTL false positives**: The `check_expired_pods` loop (k8s_launcher.py
line 289) terminates pods past their `expires_at` timestamp. If `expires_at` is
miscalculated due to a timezone or arithmetic bug, pods are terminated prematurely
with no trace beyond a log line. A `ttl_expired` timeline event makes the TTL value
and termination time visible in the UI.

**No financial/security exploit path**: This is a missing observability feature, not
an access-control vulnerability. The blast radius is confined to operational
visibility, audit completeness, and support quality.


## 4. Fix Design (code-level)

### 4.1 New service function `record_timeline_event`

Add to `app/services/ec2_launcher.py` (and an identical copy or shared helper for
`k8s_launcher.py`):

```python
# app/services/ec2_launcher.py — new helper (insert after imports)

def record_timeline_event(
    user_sub: str,
    resource_id: str,        # instance_id or pod_id
    event_type: str,         # "launched" | "stopped" | "started" | "rebooted"
                             # | "terminated" | "auto_terminated" | "ttl_expired"
    *,
    detail: dict | None = None,
) -> None:
    """Write one TIMELINE item to the compute table.

    SK pattern: TIMELINE#{resource_id}#{ts}#{event_id}
    No exception is raised on failure — timeline writes are best-effort
    and must never block the main operation.
    """
    from app.core.time import now_ts
    import uuid
    now = now_ts()
    event_id = uuid.uuid4().hex[:12]
    try:
        T.ec2_instances.put_item(Item={
            "user_sub":    user_sub,
            "sk":          f"TIMELINE#{resource_id}#{now}#{event_id}",
            "resource_id": resource_id,
            "event_type":  event_type,
            "ts":          now,
            "event_id":    event_id,
            "detail":      detail or {},
        })
    except Exception:
        logger.exception(
            "timeline_write_failed user_sub=%s resource_id=%s event=%s",
            user_sub, resource_id, event_type,
        )
```

The same function (or a thin shared version in `app/services/compute_timeline.py`)
is called from `k8s_launcher.py` with `T.k8s_pods`.

### 4.4 New API endpoint

Add to `app/routers/instance_monitoring.py`:

```python
@instance_monitoring_router.get(
    "/instances/{instance_id}/timeline",
    response_model=InstanceTimelineOut,   # new model in models.py
)
async def instance_timeline(
    instance_id: str,
    limit: int = Query(default=50, ge=1, le=200),
    session: Dict = Depends(require_ui_session),
):
    _enabled_guard()
    user_sub = session["user_sub"]
    try:
        events = svc.list_timeline_events(user_sub, instance_id, limit=limit)
    except svc.InstanceNotOwned:
        raise HTTPException(status_code=404, detail="Instance not found")
    return InstanceTimelineOut(instance_id=instance_id, events=events)
```

`list_timeline_events` in the service layer queries with
`Key("user_sub").eq(user_sub) & Key("sk").begins_with(f"TIMELINE#{instance_id}#")`
and returns items sorted by `ts` descending.

### 4.5 Models

Add to `app/models.py`:

```python
class TimelineEventOut(BaseModel):
    event_id:   str
    event_type: str
    ts:         int
    detail:     dict = {}

class InstanceTimelineOut(BaseModel):
    instance_id: str
    events:      List[TimelineEventOut]
```

### 4.6 Dev/Prod parity (SECOPS-007)

`record_timeline_event` is placed before the `if S.ec2_mock_enabled:` branch in each
lifecycle function so it executes on both mock and real AWS paths. The function itself
only writes to DynamoDB (`T.ec2_instances`), which is always available regardless of
the compute backend. No environment-specific branching is needed inside the timeline
function.

### 4.7 DynamoDB — no new table needed; no GSI needed for the owner-scoped query pattern

The `TIMELINE#` SK prefix sits in the same table as instance items.
`Key("user_sub").eq(user_sub) & Key("sk").begins_with(f"TIMELINE#{instance_id}#")`
is a range-key prefix scan on the existing table — efficient and requires no new GSI
for the owner-scoped query because `user_sub` is already the partition key. The
`begins_with` condition eliminates all non-timeline items without a full partition
scan.

A global secondary index on `resource_id` or `event_type` would be needed only for
admin cross-user queries (e.g., "show me all auto-terminate events across all users
in the last hour"). That use case is out of scope for this ticket and is covered by
GAP-0237's ByGlobalStatus GSI work.

The `ts` component embedded in the SK guarantees that a `query` with
`ScanIndexForward=False` returns events newest-first without a client-side sort,
satisfying the most common display requirement.

### 4.8 `scripts/local-ddb-init.py` — no table change required

`_resolve_table_name(S.ec2_instances_table_name, "ec2_instances")` (ddb-init line
1773) and its K8s counterpart (line 1850) create the existing tables. Because
timeline items share the same table with the same `user_sub` PK and a new SK prefix,
no schema alteration is required. The tables are created once; new item types are
simply added.

If a GSI on `ts` is added later for date-range queries, `attr_types={"ts": "N"}`
must be added to the `TableDef` at that point (per the CLAUDE.md DynamoDB gotcha).

### Alternatives considered

- **Separate `timeline` table**: Adds a table and a table handle; avoided to reduce
  operational overhead and keep the single-table pattern consistent with the rest of
  the compute domain.
- **DynamoDB Streams + Lambda**: Overkill for this feature. A synchronous call at the
  lifecycle write site is simpler, cheaper, and avoids an eventual-consistency window
  that could leave a recording gap if a Lambda invocation is delayed.
- **Store timeline in CloudWatch Logs Insights**: Not application-owned, not
  queryable via the product API, requires IAM permissions that are not always
  available in dev environments. Rejected.


## 5. Testing, Verification & Rollout

### Pytest regression test (fails before fix, passes after)

```python
# tests/services/test_ec2_timeline.py
import pytest
from moto import mock_dynamodb
from app.services.ec2_launcher import launch_instance, stop_instance, terminate_instance
from app.core.tables import T

@mock_dynamodb
def test_timeline_events_written(ddb_tables):
    user_sub = "test_user"
    item = launch_instance(
        user_sub, label="t", instance_type="t3.micro",
        ami_id="ami-amazon-linux-2"
    )
    instance_id = item["instance_id"]

    # Query timeline items
    resp = T.ec2_instances.query(
        KeyConditionExpression=(
            Key("user_sub").eq(user_sub)
            & Key("sk").begins_with(f"TIMELINE#{instance_id}#")
        )
    )
    assert len(resp["Items"]) == 1           # launched event
    assert resp["Items"][0]["event_type"] == "launched"

    stop_instance(user_sub, instance_id)
    terminate_instance(user_sub, instance_id)
    resp2 = T.ec2_instances.query(
        KeyConditionExpression=(
            Key("user_sub").eq(user_sub)
            & Key("sk").begins_with(f"TIMELINE#{instance_id}#")
        )
    )
    types = {i["event_type"] for i in resp2["Items"]}
    assert types == {"launched", "stopped", "terminated"}
```

Before the fix: `assert len(resp["Items"]) == 1` fails — zero items are written.
After the fix: all three assertions pass.

### Manual QA steps

1. `just restart` — clean stack.
2. Launch an EC2 instance via `POST /ui/compute/ec2/instances`.
3. Stop it: `POST /ui/compute/ec2/instances/{id}/stop`.
4. Call `GET /ui/compute/monitoring/instances/{id}/timeline`.
5. Confirm response contains two events: `launched` and `stopped`, with correct `ts`
   values.
6. Terminate the instance and re-query — three events now.
7. Verify the same sequence for a K8s pod via the pod-specific table.

### Observability

No new metrics are strictly required. The existing structured log messages
(`ec2_launched`, `ec2_stopped`, etc.) already cover observability for the event
types. The timeline endpoint can be measured by adding a counter to the existing
`record_browser_ssh_session_lifecycle` pattern.

### Rollout

- **Effort**: S (the core change is small; the bulk is plumbing + tests).
- **Risk**: Low. Timeline writes are best-effort (exceptions are swallowed). A
  DynamoDB outage cannot break the lifecycle operations.
- **Migration**: No data migration. The SK prefix is new; existing items are
  unaffected.
- **Rollback**: Remove the `record_timeline_event` calls. No schema rollback needed.
- **Sequencing**: Can be merged independently of GAP-0237 (cross-user admin GSI),
  which is a separate follow-up.
