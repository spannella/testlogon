# GAP-0201: Platform Benchmarks Endpoint Absent — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code in `app/routers/creator_analytics.py`,
> `app/services/engagement_rate.py`, `app/models.py`, and `app/main.py`.

## 1. Summary & Classification

**Claim status: Confirmed.** Neither the GET endpoint, the POST endpoint, the backing service
function, nor the Pydantic response model cited in the ticket exist anywhere in the codebase.

- **Severity**: HIGH
- **Source ticket**: FIN-012
- **Status**: Open
- **Owning area**: Analytics / Creator Platform
- **One-line impact**: Creators cannot benchmark their engagement rate against platform-wide
  statistics; the `GET /ui/analytics/engagement/benchmarks` surface is wholly absent, so a
  creator has no way to understand whether their 4.2% engagement rate is excellent or
  average.

**Related tickets**: GAP-0201 (this ticket) is one of four HIGH gaps under FIN-012. The
companion gaps (benchmarks UI absent, `EngagementBadge` component absent, no daily rollup
background task) are blocked on this fix. There is no dependency on GAP-0202 through
GAP-0205 (different subsystems), though the daily rollup task noted in FIN-012 LOW gap is
a prerequisite for meaningful benchmark data.

## 2. Current-State Investigation (root cause)

### What was searched

A grep for `benchmarks`, `compute_platform_benchmarks`, `get_platform_benchmarks`, and
`EngagementBenchmarks` across the entire `app/` tree returned zero results:

```
grep -rn "benchmarks\|EngagementBenchmarks" app/ → (no output)
```

### What exists today

`app/routers/creator_analytics.py` (425 lines) implements seven creator-facing analytics
endpoints and three engagement-rate endpoints:

- `GET /ui/analytics/engagement` — per-creator engagement summary (line 344)
- `GET /ui/analytics/engagement/history` — time-series rollup (line 375)
- `PUT /ui/analytics/engagement/public` — opt-in toggle (line 392)

None of these is a benchmark endpoint. The router imports from
`app/services/engagement_rate.py` only the four names:
`VALID_PERIOD_DAYS`, `get_engagement_history`, `get_engagement_summary`,
`get_public_engagement`, `set_public_engagement_visibility` (lines 52–58).

`app/services/engagement_rate.py` (384 lines) contains `calculate_engagement_rate_bps`,
`build_engagement_rollup_fields`, `get_engagement_summary`, `get_engagement_history`,
`get_public_engagement`, and visibility helpers. There is no function that aggregates
platform-wide rates across all creators, no `compute_platform_benchmarks`, and no
`get_platform_benchmarks`.

`app/models.py` has no `EngagementBenchmarksOut` model; a grep for `BenchmarksOut` returns
nothing.

`app/main.py` wires 30+ background startup tasks (lines 521–806) but none relates to
computing engagement benchmarks.

### Root cause

The FIN-012 ticket specified two endpoints and a daily compute job that were simply never
implemented. The engagement-rate service was implemented (per-creator rate, history, public
toggle) but the platform-aggregate layer was not written. This is a complete feature gap,
not a regression or partial implementation.

### How it manifests

Any client calling `GET /ui/analytics/engagement/benchmarks` receives a FastAPI 404.
The `POST /internal/analytics/engagement/compute-benchmarks` endpoint similarly does not
exist. Admin operators have no way to trigger a benchmark recompute. Creators viewing their
engagement dashboard see their own rate but have no percentile context.

---

## 3. Impact / Exploit / Blast Radius

This gap is a missing-feature availability issue, not a security or money-integrity issue.
There is no exploit path. The blast radius is:

- **All creators** on the platform cannot compare their engagement rate to the platform
  average or understand their percentile standing.
- **Product/marketing** cannot report platform-wide engagement health metrics.
- **Dependent UI**: `EngagementRateSection.tsx` has no benchmarks card (companion FIN-012
  gap), so the creator analytics page remains incomplete.
- **Data integrity**: There is no data corruption risk. Existing per-creator rollups are
  unaffected. The benchmarks table simply does not exist yet.

The missing daily compute job (FIN-012 LOW gap: `upsert_daily_rollup` only runs on explicit
refresh) compounds this gap: even after the benchmark function is implemented, it will only
produce useful statistics if the daily rollup pipeline is first wired as a background task.

## 4. Fix Design (code-level)

### Step 1 — Add Pydantic models (`app/models.py`)

Add two new response models. Place them near the existing engagement models (search for
`EngagementRateOut`):

```python
class EngagementBenchmarksOut(BaseModel):
    average_rate: float        # percent, e.g. 3.7
    median_rate: float
    p25_rate: float
    p75_rate: float
    sample_size: int           # number of creators with data
    my_percentile: Optional[float] = None  # null when caller has no rollup data
    computed_at: int           # Unix timestamp of last benchmark compute
    date: str                  # YYYY-MM-DD the benchmark covers
```

No request body model is needed for the GET endpoint; `POST /internal/.../compute-benchmarks`
needs only an optional `date` query parameter.

### Step 2 — Implement `compute_platform_benchmarks` (`app/services/engagement_rate.py`)

```python
# At the top of engagement_rate.py, add a DDB key constant:
_BENCHMARK_PK = "PLATFORM#BENCHMARKS"

def compute_platform_benchmarks(date_str: Optional[str] = None) -> Dict[str, Any]:
    """Aggregate all creator daily rollup records for date_str to compute
    platform-wide engagement percentiles. Stores result under
    pk=PLATFORM#BENCHMARKS, sk=<date_str> in the analytics_rollups table.
    Returns the computed benchmark payload.
    """
    from boto3.dynamodb.conditions import Key
    target = date_str or _today()

    # Scan all DAILY#<target> rows across all creators.
    # Because the analytics_rollups table is keyed by CREATOR#<id>, we need
    # a GSI or a scan. A GSI (GSI_DATE) on sk=DAILY#<date> is the correct
    # long-term solution (see migration note below). For the initial
    # implementation a filtered scan over the analytics_rollups table is
    # acceptable (the table is bounded to analytics data only, unlike the
    # billing table).
    rates: List[int] = []
    kwargs: Dict[str, Any] = {}
    while True:
        resp = T.analytics_rollups.scan(**kwargs)
        for item in resp.get("Items", []):
            if item.get("sk") != f"DAILY#{target}":
                continue
            bps = _to_int(item.get("engagement_rate_bps", 0))
            if bps > 0:
                rates.append(bps)
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek

    if not rates:
        return {"date": target, "sample_size": 0, "average_rate": 0.0,
                "median_rate": 0.0, "p25_rate": 0.0, "p75_rate": 0.0,
                "computed_at": now_ts()}

    rates.sort()
    n = len(rates)
    avg_bps = int(sum(rates) / n)
    median_bps = rates[n // 2]
    p25_bps = rates[max(0, int(n * 0.25) - 1)]
    p75_bps = rates[min(n - 1, int(n * 0.75))]
    computed_at = now_ts()

    item = {
        "pk": _BENCHMARK_PK,
        "sk": target,
        "average_rate_bps": avg_bps,
        "median_rate_bps": median_bps,
        "p25_rate_bps": p25_bps,
        "p75_rate_bps": p75_bps,
        "sample_size": n,
        "computed_at": computed_at,
    }
    T.analytics_rollups.put_item(Item=item)
    return item


def get_platform_benchmarks(date_str: Optional[str] = None) -> Optional[Dict[str, Any]]:
    """Read the pre-computed benchmark record for date_str (default: today).
    Returns None if no benchmark has been computed yet.
    """
    target = date_str or _today()
    try:
        resp = T.analytics_rollups.get_item(
            Key={"pk": _BENCHMARK_PK, "sk": target}
        )
        return resp.get("Item")
    except Exception:
        logger.exception("Failed to read platform benchmarks for %s", target)
        return None
```

The `my_percentile` value for a requesting user is computed at query time by comparing
their `engagement_rate_bps` from `get_engagement_summary` against the stored `rates` list,
or approximated via the quartile thresholds.

### Step 3 — Add router endpoints (`app/routers/creator_analytics.py`)

```python
# Add imports at top of file:
from app.services.engagement_rate import (
    ...,
    compute_platform_benchmarks,
    get_platform_benchmarks,
)
from app.models import EngagementBenchmarksOut

# New internal router for cron/ops triggers:
internal_router = APIRouter(prefix="/internal/analytics", tags=["analytics-internal"])

@router.get("/engagement/benchmarks", response_model=EngagementBenchmarksOut)
def analytics_engagement_benchmarks(
    date: Optional[str] = Query(default=None),
    session=Depends(require_ui_session),
):
    """Return platform-wide engagement benchmarks with the caller's percentile."""
    target = _validate_date(date) if date else _today()
    bench = get_platform_benchmarks(target)
    if bench is None:
        raise HTTPException(status_code=503, detail="Benchmarks not yet computed. Try again later.")

    # Caller's own rate for my_percentile.
    user_id = session["user_sub"]
    my_summary = get_engagement_summary(user_id, 30)
    my_bps = my_summary["engagement_rate_bps"]

    avg_bps = _to_int(bench.get("average_rate_bps", 0))
    med_bps = _to_int(bench.get("median_rate_bps", 0))
    p25_bps = _to_int(bench.get("p25_rate_bps", 0))
    p75_bps = _to_int(bench.get("p75_rate_bps", 0))
    sample_size = _to_int(bench.get("sample_size", 0))

    # Approximate percentile via quartile brackets.
    if sample_size == 0 or my_bps == 0:
        my_pct = None
    elif my_bps <= p25_bps:
        my_pct = round(my_bps / max(p25_bps, 1) * 25.0, 1)
    elif my_bps <= med_bps:
        my_pct = round(25.0 + (my_bps - p25_bps) / max(med_bps - p25_bps, 1) * 25.0, 1)
    elif my_bps <= p75_bps:
        my_pct = round(50.0 + (my_bps - med_bps) / max(p75_bps - med_bps, 1) * 25.0, 1)
    else:
        my_pct = round(min(99.9, 75.0 + (my_bps - p75_bps) / max(avg_bps, 1) * 25.0), 1)

    return EngagementBenchmarksOut(
        average_rate=bps_to_percent(avg_bps),
        median_rate=bps_to_percent(med_bps),
        p25_rate=bps_to_percent(p25_bps),
        p75_rate=bps_to_percent(p75_bps),
        sample_size=sample_size,
        my_percentile=my_pct,
        computed_at=_to_int(bench.get("computed_at", 0)),
        date=target,
    )


@internal_router.post("/engagement/compute-benchmarks")
def trigger_compute_benchmarks(
    date: Optional[str] = Query(default=None),
):
    """Internal endpoint: recompute platform-wide engagement benchmarks.
    Called by the daily cron task and by ops tooling. No auth (internal prefix
    is not exposed by the Vite proxy in production).
    """
    target = date or _today()
    result = compute_platform_benchmarks(target)
    return {"ok": True, "date": target, "sample_size": result.get("sample_size", 0)}
```

Register `internal_router` in `app/main.py` alongside the existing `creator_analytics`
routers.

### Step 4 — Wire daily background task (`app/main.py`)

```python
# In app/main.py, add near other analytics/rollup startup hooks:
from app.services.engagement_rate import compute_platform_benchmarks

async def _daily_benchmark_loop():
    import asyncio
    from app.services.engagement_rate import compute_platform_benchmarks, _today
    while True:
        try:
            compute_platform_benchmarks(_today())
            logger.info("platform_engagement_benchmarks_computed")
        except Exception:
            logger.exception("platform benchmark compute failed")
        await asyncio.sleep(86400)  # once per day

def start_engagement_benchmark_task():
    import asyncio
    asyncio.ensure_future(_daily_benchmark_loop())

app.add_event_handler("startup", start_engagement_benchmark_task)
```

### Dev/Prod parity (SECOPS-007)

`compute_platform_benchmarks` reads and writes to `T.analytics_rollups`, which resolves to
DynamoDB Local in dev (port 8001, `AWS_ACCESS_KEY_ID=test`) and to the real AWS DynamoDB
table in production. No mock-only or dev-only code paths are introduced. The
`/internal/analytics/...` prefix is not proxied by Vite (only `/api`, `/ui`, `/mock`,
`/internal` are proxied — the last is proxied, so this endpoint is callable in dev via
port 3000; in production the `/internal` prefix should be firewalled to the VPC only, per
SECOPS-007). The daily background task runs in both environments equally; `S.dev_mode` is
not consulted because benchmark computation is read-only and non-destructive.

### Alternatives considered

- **Pre-aggregated GSI on `analytics_rollups`**: Would allow a GSI query on
  `sk = DAILY#<date>` rather than a table scan. Correct long-term choice; deferred because
  it requires a DDB table migration. The scan is acceptable today (analytics_rollups is a
  bounded analytics-only table, not the billing table).
- **In-memory computation on every request**: Rejected — too slow at scale; the pre-compute
  + daily job pattern is consistent with `compute_daily_rollup` in the financial dashboard.
- **Separate `benchmarks` DynamoDB table**: Rejected — the existing `analytics_rollups`
  table can hold benchmark rows using the `PLATFORM#BENCHMARKS` partition key; no new table
  provisioning needed.

### Metrics and observability

Log line `platform_engagement_benchmarks_computed` (structured) should appear once per day

production. Alert if absent for more than 26 hours.

### Rollout and risks

- **Effort**: M (estimated 2–3 days including tests and UI companion work).
- **Risk**: LOW. Read-only scan against `analytics_rollups` (analytics-only table); worst
  case is a slow compute run if the table is large. No payment or session data is touched.
- **Rollback**: Remove the router registration and startup task from `main.py`; the
  `PLATFORM#BENCHMARKS` rows in DynamoDB are inert if no code reads them.
- **Sequencing**: Must be deployed before the companion benchmarks UI card (FIN-012 MED
  gap). The daily rollup background task (FIN-012 LOW gap) should be deployed first so
  `engagement_rate_bps` fields are populated on rollup rows before the benchmark compute
  runs.
