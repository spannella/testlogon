# GAP-0374: Admin DRM Key Revocation Endpoints Missing — Remediation Write-up

> ~5 pages. Fix-oriented. Cites real file:line. No investigation doc exists for this ticket.

## 1. Summary & Classification

**Plain-English statement**: The DRM router (`app/routers/vod_drm.py`) implements only
two endpoints — `GET /v1/vod/drm/key/{key_id}` and `GET /v1/vod/drm/info/{asset_id}`.
The spec (§4.3 and §6.5–6.7) requires admin-only revocation endpoints:
`POST /drm/keys/revoke` (revoke a specific key by ID) and
`POST /drm/keys/{asset_id}/revoke-all` (revoke all keys for an asset). Neither exists.
When a content key is compromised — e.g., via a screen-capture piracy event, a
compromised subscriber account, or a leaked key from a former employee — operators have
no mechanism to invalidate it short of a full redeployment or root-secret rotation
(which rotates every key on the platform simultaneously).

- **Severity**: HIGH
- **Source ticket**: VOD-010
- **Status**: Open
- **Owning area**: Backend / DRM Router / Admin / `app/routers/vod_drm.py`
- **Verdict**: **Confirmed** — `app/routers/vod_drm.py` contains exactly two route
  definitions (lines 33 and 106). There are no POST routes, no revocation logic, no
  `require_admin_session` imports, and no `ContentKeys` or `DrmRevoked` DynamoDB table
  in `scripts/local-ddb-init.py`. A `grep -rn "revoke.*drm\|drm.*revoke"` across the
  entire `app/` directory returns zero results.
- **One-line impact**: Compromised DRM keys cannot be invalidated without rotating the
  root secret, which forces a mass re-encryption of all content on the platform.
- **Related tickets**: VOD-010 (source), GAP-0372 (tenant isolation in derivation),
  GAP-0373 (tenant validation at serve time). Revocation is most effective after both
  companion fixes ship.

## 2. Current-State Investigation (Root Cause)

### What exists in `vod_drm.py`

The entire router is 141 lines with two endpoints:

```
GET  /v1/vod/drm/key/{key_id}    — serve decryption key (line 33)
GET  /v1/vod/drm/info/{asset_id} — return DRM metadata (line 106)
```

There are no imports for `require_admin_session` or any admin dependency. There is no
`POST` or `DELETE` route. The router imports only:

```python
from app.services.vod_drm_keys import (
    VodDrmKeyError, derive_content_key, derive_key_id,
    is_drm_enabled, validate_key_id,
)
```

There is no revocation service or revocation table.

### Why HKDF-based derivation makes revocation non-trivial

The current design derives keys deterministically from `(root_secret, asset_id)` via
HKDF. There is no per-key storage: the server can always re-derive any key on demand.
This means "revoking" a key in the traditional sense (deleting a record) does not work —
the derivation function would still produce the same bytes.

The correct approach is a **blocklist pattern**: maintain a `DrmKeyRevocations` DynamoDB
table keyed by `(tenant_id, asset_id)` (or `key_id`) with an optional `revoked_at`
timestamp. The key server checks this table before serving a key and returns 403 if a
revocation record exists. The derived key itself need not be deleted.

### Missing DynamoDB table

A `grep` of `scripts/local-ddb-init.py` confirms no `DrmKeyRevocations`,
`ContentKeyRevocations`, `DrmRevoked`, or similar table exists. The table must be
created as part of this fix.

### Existing patterns for analogous revocation

The playback entitlement service already implements in-memory JTI revocation
(`app/services/playback_entitlements.py:82-108`). The pattern there — storing revoked
JTIs with expiry, checking before serving — is a direct template for DRM key
revocation. The difference is that playback token revocation is ephemeral (in-memory,
lost on restart); DRM key revocation must be durable (DynamoDB) because a leaked AES
key remains usable indefinitely until actively blocked.

Admin endpoints with `require_admin_session` dependency already exist in the codebase
(e.g., `app/routers/admin_entitlements.py`, `app/routers/admin_roles.py`). The pattern
is well-established.

## 3. Impact / Exploit / Blast Radius

**Scenario 1 — Compromised subscriber account**: A creator's premium video key is
extracted by a piracy service operating subscriber accounts. Without revocation, the
piracy service can continue decrypting and redistributing new segments indefinitely.
The only fix available today is rotating `VOD_DRM_KEY_ROOT`, which invalidates every
key on the platform, forcing a mass re-encryption job that may take hours or days for
large libraries.

**Scenario 2 — Targeted leak during security incident**: An attacker exploits GAP-0372
or GAP-0373 (before those fixes ship) and harvests keys for a specific creator's
catalogue. After the security gap is patched, the already-leaked keys remain valid
forever because there is no revocation mechanism.

**Scenario 3 — Legal takedown**: A content owner issues a DMCA takedown for a specific
video. The operator can delete the video record and S3 segments, but the previously
distributed AES key remains functional against any cached copy of the encrypted
segments. Without revocation, DRM provides no post-distribution protection for
taken-down content.

**Blast radius of missing feature**: Any DRM-encrypted video on the platform. The longer
this gap remains open, the larger the set of potentially leaked keys with no revocation
path.

## 4. Fix Design (Code-Level)

### New DynamoDB table: `DrmKeyRevocations`

Add to `scripts/local-ddb-init.py`:

```python
TableDef(
    _resolve_table_name(S.drm_revocations_table_name, "DrmKeyRevocations"),
    pk="revocation_id",     # hash key: "{tenant_id}#{asset_id}" or "{key_id}"
    sk="revoked_at",        # sort key: integer Unix timestamp
    attr_types={"revoked_at": "N"},
    gsi=[
        GsiDef("TenantAssetIndex", pk="tenant_asset_id", sk="revoked_at",
               attr_types={"revoked_at": "N"}),
    ],
)
```

Add to `app/core/settings.py`:
```python
drm_revocations_table_name: str = os.environ.get("DRM_REVOCATIONS_TABLE", "DrmKeyRevocations")
```

Add to `app/core/tables.py`:
```python
drm_revocations: TableHandle = field(default_factory=lambda: ...)
```

### New service: `app/services/vod_drm_revocations.py`

```python
"""DRM key revocation service (GAP-0374).

Maintains a durable DynamoDB blocklist for revoked DRM keys.
The key server checks this before serving any decryption key.
"""
from __future__ import annotations
from app.core.tables import T
from app.core.time import now_ts


class DrmKeyRevokedError(Exception):
    pass


def is_key_revoked(*, tenant_id: str, asset_id: str) -> bool:
    """Return True if any revocation record exists for tenant+asset."""
    result = T.drm_revocations.query(
        KeyConditionExpression="tenant_asset_id = :k",
        ExpressionAttributeValues={":k": f"{tenant_id}#{asset_id}"},
        Limit=1,
        IndexName="TenantAssetIndex",
    )
    return bool(result.get("Items"))


def revoke_key(
    *,
    tenant_id: str,
    asset_id: str,
    reason: str,
    actor_sub: str,
) -> dict:
    """Write a revocation record for a specific tenant+asset."""
    ts = now_ts()
    record = {
        "revocation_id": f"{tenant_id}#{asset_id}#{ts}",
        "tenant_asset_id": f"{tenant_id}#{asset_id}",
        "tenant_id": tenant_id,
        "asset_id": asset_id,
        "revoked_at": ts,
        "reason": reason,
        "revoked_by": actor_sub,
    }
    T.drm_revocations.put_item(Item=record)
    return record


def revoke_all_keys_for_asset(
    *,
    asset_id: str,
    reason: str,
    actor_sub: str,
) -> list[dict]:
    """Revoke keys for an asset across all tenants (admin-level operation)."""
    # Scan for all tenant+asset combinations for this asset_id.
    # For most assets this is O(1) tenants; for shared assets may be more.
    result = T.drm_revocations.scan(
        FilterExpression="asset_id = :a",
        ExpressionAttributeValues={":a": asset_id},
    )
    ts = now_ts()
    record = {
        "revocation_id": f"*#{asset_id}#{ts}",
        "tenant_asset_id": f"*#{asset_id}",  # wildcard sentinel
        "tenant_id": "*",
        "asset_id": asset_id,
        "revoked_at": ts,
        "reason": reason,
        "revoked_by": actor_sub,
    }
    T.drm_revocations.put_item(Item=record)
    return [record]
```

### New admin endpoints in `app/routers/vod_drm.py`

```python
from app.auth.deps import require_admin_session
from app.services.vod_drm_revocations import revoke_key, revoke_all_keys_for_asset
from pydantic import BaseModel, Field

class RevokeKeyIn(BaseModel):
    tenant_id: str = Field(min_length=1)
    asset_id: str = Field(min_length=1)
    reason: str = Field(default="admin_revocation", min_length=1)

class RevokeAllKeysIn(BaseModel):
    reason: str = Field(default="admin_revocation", min_length=1)


@router.post("/keys/revoke")
def admin_revoke_key(
    body: RevokeKeyIn,
    admin=Depends(require_admin_session),
):
    """Revoke the DRM key for a specific tenant+asset (spec §6.5)."""
    record = revoke_key(
        tenant_id=body.tenant_id,
        asset_id=body.asset_id,
        reason=body.reason,
        actor_sub=admin["user_sub"],
    )
    return {"ok": True, "revocation": record}


@router.post("/keys/{asset_id}/revoke-all")
def admin_revoke_all_keys(
    asset_id: str,
    body: RevokeAllKeysIn,
    admin=Depends(require_admin_session),
):
    """Revoke all tenant keys for an asset (spec §6.6-6.7)."""
    records = revoke_all_keys_for_asset(
        asset_id=asset_id,
        reason=body.reason,
        actor_sub=admin["user_sub"],
    )
    return {"ok": True, "revocations": records}
```

### Wire revocation check into key serve path

In `get_decryption_key`, add a revocation check immediately after asset/tenant
validation and before key derivation:

```python
from app.services.vod_drm_revocations import is_key_revoked

# After tenant_id validation (new, post-GAP-0373):
if is_key_revoked(tenant_id=token_tenant_id, asset_id=asset.strip()):
    raise HTTPException(
        status_code=403,
        detail={"code": "key_revoked",
                "message": "this content key has been administratively revoked"},
    )
```

### Dev/Prod parity (SECOPS-007)

The `DrmKeyRevocations` table follows the standard DynamoDB Local pattern
(SECOPS-007 rule 1): `T.drm_revocations` is created by `scripts/local-ddb-init.py` and
accessed via `app/core/tables.py`. In dev, DynamoDB Local on `:8001` is used. In
production, the same boto3 client factory in `app/core/aws.py` points to real
DynamoDB. No `if dev:` branching in business logic. No new AWS service type — stays
within the existing DynamoDB pattern. The `is_key_revoked` DDB query must handle
`ResourceNotFoundException` gracefully (table not yet created in a rollout gap) and
fail-open with a logged warning, consistent with SECOPS-007 rule 3.

### Metrics / observability

  content is still being probed).
- `vod_drm_revocation_created_total` — counter on successful revocations.
- An admin audit log entry should be written for every revocation, consistent with the

### Rollout

- **Effort**: M (2 engineer-days: DDB table, service, router endpoints, tests)
- **Risk**: Low for the new endpoints (additive). Medium for the revocation check
  wired into the key serve path (adds a DDB read on every key serve). Mitigate with a
  feature flag `VOD_DRM_REVOCATION_ENABLED` defaulting to `True` in production,
  `True` in dev. If the DDB table is unavailable, fail-open (log, continue serving)
  to avoid blocking legitimate playback during an outage — this is consistent with
  SECOPS-007 rule 3.
- **Sequencing**: Can be deployed independently of GAP-0372/GAP-0373, but revocation is
  only meaningful once tenant isolation (GAP-0372/GAP-0373) is in place. Recommended
  order: GAP-0372 + GAP-0373 → GAP-0374.
- **Rollback**: Remove the `is_key_revoked` check from `get_decryption_key` and the
  two admin endpoints. The DDB table can remain (no harm). No data migration required.
