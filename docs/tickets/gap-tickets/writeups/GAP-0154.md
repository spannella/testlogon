# GAP-0154: Conversion Attribution Chain Broken — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at app/services/commerce_order_service.py, app/routers/commercial_checkout.py, app/services/unified_checkout.py, and app/routers/affiliate_links.py.

## 1. Summary & Classification

**Plain-English statement:** The affiliate conversion attribution chain is completely disconnected. When a visitor clicks an affiliate link, a tracking cookie (`afl_ref`) is set with the affiliate tracking code. When that visitor later completes a purchase via the unified checkout endpoint, the `afl_ref` cookie is never read, never passed to `record_conversion`, and the affiliate therefore never earns commission. Conversions can only be manually attributed by calling the test endpoint `POST /ui/affiliates/links/{link_id}/conversions`, which is explicitly documented as "for testing/manual attribution." Organic attribution through normal product flows is absent.

- **Severity:** HIGH — affiliate commission is a financial obligation; zero automatic conversion attribution means affiliates are never paid for traffic they drive.
- **Source ticket:** CREATOR-004
- **Status:** Open
- **Owning area:** Affiliate Links / Checkout / Commerce

**Claim verdict:** Confirmed. `app/services/commerce_order_service.py` contains zero references to `afl_ref`, `record_conversion`, or `affiliate`. The `create_unified_checkout_session` function in `app/services/unified_checkout.py` does not accept a `Request` object, so it cannot read cookies at all. The checkout router at `app/routers/commercial_checkout.py:43` does receive a `Request` parameter but never extracts `afl_ref` from it and does not pass it downstream.

**Related tickets:** GAP-0155 (afl_ref cookie set with `Secure=True` in dev — compounds this gap in local testing), CREATOR-004, SECOPS-007.

## 2. Current-State Investigation (Root Cause)

### The `record_conversion` function exists but is stranded

`app/services/affiliate_links.py:272` implements `record_conversion(link_id, order_id, amount_cents)`:
- Looks up the link by `link_id`; returns `None` if not found or inactive.
- Calculates commission: `amount_cents * commission_percent // 100`.
- Writes a conversion record to `T.affiliate_clicks` with GSI for link-scoped queries.
- Updates `T.affiliate_links` aggregate counters (`conversion_count`, `revenue_cents`, `commission_earned_cents`).

The function is correct and complete. It is imported in two places:
1. `app/routers/affiliate_links.py:23` — used at line 161 by the manual test endpoint.
2. `app/services/ad_creative_affiliate.py:423` — used for ad-click attribution (a separate flow).

For organic checkout-triggered attribution, it is never called.

### The `afl_ref` cookie is set but never read

`app/routers/affiliate_links.py:204–211` (the `/r/{tracking_code}` redirect endpoint) sets:
```python
response.set_cookie(
    key="afl_ref",
    value=tracking_code,
    max_age=S.affiliate_cookie_duration_days * 86400,
    httponly=True,
    samesite="lax",
    path="/",
)
```

Critically, `httponly=True` means JavaScript cannot read this cookie — it can only be sent by the browser to the server in HTTP request headers. This is correct from a security perspective, but it means attribution must be done server-side at the checkout endpoint.

No server-side code reads the `afl_ref` cookie from any checkout request.

### The checkout flow does not pass `Request` to the service layer

`app/routers/commercial_checkout.py:43`:
```python
@router.post("/ui/checkout/session", response_model=UnifiedCheckoutSessionOut)
async def ui_create_checkout_session(
    body: UnifiedCheckoutSessionIn,
    req: Request = None,           # Request IS available here
    ctx=Depends(require_ui_session)
):
    out = create_unified_checkout_session(ctx["user_sub"], body)  # req is NOT forwarded
    ...
```

The `Request` object (`req`) is captured but passed only to `audit_event`. It is not forwarded to `create_unified_checkout_session` in `app/services/unified_checkout.py:58`:
```python
def create_unified_checkout_session(user_id: str, body: UnifiedCheckoutSessionIn) -> Dict[str, Any]:
```

The service function signature does not accept a `Request` object, so there is no mechanism for the service to read cookies from the incoming request.

### Order completion vs. session creation

The current checkout flow only creates an order in `pending_payment` status (stored in DynamoDB). There is no separate "order completed" webhook or callback from the Stripe mock that would trigger attribution. In the mocked dev environment, `create_order` always succeeds synchronously, making "order creation" effectively the same as "purchase completion" for local testing purposes.

In production, the Stripe webhook (`payment_intent.succeeded`) would be the authoritative completion event and is the correct place to attribute conversions against the `afl_ref` cookie — but since there is no cookie-to-order bridge in the checkout endpoint, the tracking code is lost before the webhook even fires.

The fix must capture the `afl_ref` tracking code at checkout session creation time (when the cookie is available in the request) and store it with the order, so downstream payment completion webhooks can look it up and call `record_conversion`.

## 3. Impact / Exploit / Blast Radius

### Financial impact: affiliates earn no commission

Every purchase made by a visitor who arrived via an affiliate link goes unattributed. The affiliate receives no commission. Over time this means:
- Affiliates see a 0% conversion rate in their dashboard, regardless of traffic quality.
- Affiliates will churn from the platform, believing their links are ineffective.
- The platform retains the full purchase amount but violates its implicit or explicit commission agreement.

### No over-attribution risk

The bug is under-attribution (zero conversions), not over-attribution. There is no risk of paying commission multiple times. The financial risk is to affiliates, not to the platform's treasury.

### Blast radius

- Affects every purchase made through `POST /ui/checkout/session` (cart, direct, and subscription checkout paths) by a visitor with a valid `afl_ref` cookie.
- The file-bundle checkout (`POST /ui/checkout/session/file-bundle`) delegates through `create_unified_checkout_session` and is equally affected.
- Direct purchase via the billing Stripe checkout (`POST /billing/checkout_session`) is also affected but is a separate code path not covered by this ticket.
- The ad-creative affiliate flow (`app/services/ad_creative_affiliate.py:423`) uses its own attribution mechanism and is not affected by this gap.

## 4. Fix Design (Code-Level)

### Step 1: extract `afl_ref` cookie in the checkout router

Modify `app/routers/commercial_checkout.py:43` to read the `afl_ref` cookie from the incoming request and pass the tracking code to the service:

```python
@router.post("/ui/checkout/session", response_model=UnifiedCheckoutSessionOut)
async def ui_create_checkout_session(
    body: UnifiedCheckoutSessionIn,
    req: Request = None,
    ctx=Depends(require_ui_session),
):
    afl_ref = req.cookies.get("afl_ref") if req else None   # <-- ADD THIS
    out = create_unified_checkout_session(ctx["user_sub"], body, afl_ref=afl_ref)  # <-- PASS IT
    audit_event(
        "checkout_session_created",
        ctx["user_sub"],
        req,
        outcome="success",
        order_id=out.get("order_id"),
        checkout_session_id=out.get("checkout_session_id"),
        source=out.get("source"),
        line_item_count=len(out.get("line_items") or []),
        afl_ref=afl_ref,                                    # <-- INCLUDE IN AUDIT LOG
    )
    return out
```

Apply the same change to `ui_create_file_bundle_checkout_session` at line 58.

### Step 2: accept and propagate `afl_ref` through the service layer

Modify `create_unified_checkout_session` in `app/services/unified_checkout.py:58` to accept the optional tracking code and store it in the order metadata:

```python
def create_unified_checkout_session(
    user_id: str,
    body: UnifiedCheckoutSessionIn,
    afl_ref: Optional[str] = None,    # <-- ADD PARAMETER
) -> Dict[str, Any]:
    ...
    metadata = {
        **metadata,
        "checkout_session_id": checkout_session_id,
    }
    if afl_ref:
        metadata["afl_ref"] = afl_ref                       # <-- STORE WITH ORDER

    order = commerce_order_service.create_order_from_line_items(
        user_id=user_id,
        source_system=SOURCE_TO_ORDER_SOURCE[source],
        line_items=line_items,
        correlation_id=correlation_id,
        metadata=metadata,
    )
    ...
```

`afl_ref` is now stored in the order's `metadata` field in DynamoDB, bridging the gap between cookie-capture time and payment-webhook time.

### Step 3: call `record_conversion` on order completion

Add an order-completion attribution step. In the dev/mock environment where order creation is synchronous, this can be done immediately after `create_order_from_line_items`:

```python
# app/services/unified_checkout.py — after order creation, inside create_unified_checkout_session

    if afl_ref:
        try:
            from app.services.affiliate_links import get_link_by_code, record_conversion
            link = get_link_by_code(afl_ref)
            if link and link.get("status") == "active":
                record_conversion(
                    link_id=link["link_id"],
                    order_id=order["order_id"],
                    amount_cents=order["amount_cents"],
                )
        except Exception:
            logger.warning(
                "affiliate conversion attribution failed for order %s afl_ref %s",
                order.get("order_id"), afl_ref, exc_info=True
            )
```

In production with a real Stripe webhook flow, this call should move to the `payment_intent.succeeded` webhook handler, using `metadata["afl_ref"]` retrieved from the order record. The `try/except` wrapper ensures attribution failure never aborts the checkout.

### Dev/Prod parity (SECOPS-007)

- **Dev:** `afl_ref` cookie is set by the `/r/{tracking_code}` redirect endpoint. In dev (HTTP), the cookie is currently dropped due to `Secure=True` (GAP-0155); after GAP-0155 is fixed, the cookie will be set and readable in HTTP dev environments. The `record_conversion` call targets DynamoDB Local (via `DDB_ENDPOINT_URL=http://localhost:8001`), which works identically to production.
- **Production:** The cookie is set over HTTPS with `Secure=True` (appropriate). Cookie extraction at checkout time works the same way. For production, the `record_conversion` call should be deferred to the Stripe webhook for accuracy, but as an interim fix, calling it at checkout creation is acceptable for the mocked payment flow.

No mock or dev-only branching is required for this fix. The `get_link_by_code` → `record_conversion` call path uses the same DynamoDB table in both environments.

### Backward compatibility

- **No API contract change.** The checkout endpoint request/response shapes are unchanged. `afl_ref` is read from cookies, not from the request body.
- **No database migration.** The `metadata` field in orders is already a schemaless dict; adding `afl_ref` is additive.
- **Idempotency:** `record_conversion` writes a new conversion record each time it is called for a given order. To prevent double-attribution (if checkout is retried), the conversion write should use a deduplication key based on `order_id`. Check `app/services/affiliate_links.py:272` for whether this is already handled; if not, add a `ConditionExpression="attribute_not_exists(order_id)"` guard on the conversion item write.

from unittest.mock import patch, MagicMock
import pytest

        mock_T.order_items.put_item = MagicMock()

### Rollout

- **Effort:** S (Small) — changes span 2 files, approximately 40 lines including error handling.
- **Risk:** Low. The fix is additive and wrapped in `try/except`. No existing code path changes.
- **Dependencies:** GAP-0155 should be fixed in the same PR or immediately prior — without that fix, `afl_ref` cookies cannot be set in the local HTTP dev environment, making end-to-end testing of this fix difficult.
- **Sequencing:** Fix GAP-0155 first (cookie `secure` flag), then this gap. Both are small and can be combined into one PR.
