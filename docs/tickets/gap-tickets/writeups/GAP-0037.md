# GAP-0037: admin_capabilities System Is Dead Code — Remediation Write-up

## 1. Summary & Classification

**Plain-English statement**: The `rootctl` CLI exposes an `admin permissions set` command (`_admin_permissions_set_command`) that writes a list of named capabilities (`billing_ops`, `billing_read`, `file_metadata`, `file_content`, `user_support`, `impersonation`) to a DynamoDB field `admin_capabilities` on the user record. However, the runtime enforcement layer — `require_admin_scope` and `admin_profile_has_scope` in `app/auth/policy.py` and `app/auth/roles.py` — reads `admin_profile` from the JWT claim, not `admin_capabilities` from DynamoDB. The two systems are completely disconnected: writing `admin_capabilities` to DynamoDB has zero effect on what an admin user can do at the API level. The capability management CLI is dead code.

- **Severity**: HIGH
- **Source ticket**: ADMIN-PERMS-001
- **Status**: Open
- **Owning area**: Admin Permissions / RBAC / rootctl CLI
- **Effort**: M
- **Claim verdict**: CLAIM OK — confirmed. `_admin_permissions_set_command` at `app/cli/rootctl.py:1657` writes to `admin_capabilities` in DynamoDB. The enforcement layer at `app/auth/policy.py:122` (`require_admin_scope`) reads `admin_profile` from JWT claims. No code path bridges `admin_capabilities` in DynamoDB to `admin_profile` in JWT.

**One-line impact**: Any operator who runs `rootctl admin permissions set` believing they are restricting an admin user's scope is mistaken; the admin retains full `GENERAL` (all-access) profile because the token-minting path never consults `admin_capabilities`.

**Related tickets**: ADMIN-PERMS-001 (source), GAP-0038 (grant command also skips admin_profile), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (Root Cause)

### The CLI write path (dead)

`app/cli/rootctl.py:1657–1743` defines `_admin_permissions_set_command`. It:

1. Validates that the target user exists and has `role=admin` (line 1671–1677).
2. Parses the supplied capabilities against `ADMIN_CAPABILITIES` (line 1679) — a set defined at line 51: `{"billing_ops", "billing_read", "file_metadata", "file_content", "user_support", "impersonation"}`.
3. Writes to DynamoDB (line 1700–1711):

```python
T.users.update_item(
    Key={"user_sub": target_user_sub},
    UpdateExpression="SET admin_capabilities=:caps, admin_caps_updated_at=:ts, ...",
    ExpressionAttributeValues={
        ":caps": new_caps,   # e.g. ["billing_read", "file_metadata"]
        ...
    },
)
```

The DynamoDB field is `admin_capabilities`. The emitted audit event key is `admin_capabilities_updated_cli`.

The command is further gated by `ROOTCTL_ADMIN_CAPABILITIES_ENABLED` env flag (line 1658). When the flag is off (the default), the command raises `CliPolicyError("admin capability commands are disabled")` immediately. This means the feature is both non-functional when enabled and completely blocked when disabled.

### The enforcement read path (independent)

`app/auth/policy.py:122–169` defines `require_admin_scope`. When an endpoint uses `Depends(require_admin_scope(AdminScope.BILLING_SUPPORT))`, the dependency:

1. Reads `admin_profile` from the `AuthenticatedUser` object (line 137):
   ```python
   profile = normalize_admin_profile(getattr(user, "admin_profile", None))
   ```
2. Checks via `admin_profile_has_scope(profile, normalized_scope)` (line 138).

`admin_profile` on `AuthenticatedUser` comes from `_extract_admin_profile_from_claims` at `app/auth/deps.py:148`, which reads `claims.get("admin_profile")` from the JWT payload. The JWT is minted by `mint_access_token` at `app/services/sessions.py:168`, which produces:

```python
payload = {
    "sub": user_sub,
    "sid": session_id,
    "role": role,        # "root" or "user" only — no "admin" variant
    "auth_level": "high" if role == "root" else "standard",
    "exp": now_ts() + access_ttl,
    "iat": now_ts(),
}
```

**`admin_profile` is never written into the payload by `mint_access_token`.** The only code that writes `admin_profile` into a JWT is `e2e_admin_session_setup.py` (test scaffolding that writes tokens directly) and the impersonation token path at `app/routers/admin_impersonation.py:123`. Normal login sessions never receive an `admin_profile` claim.

### The disconnection

```
CLI write:  admin_capabilities (DDB field, list of strings)
                    ↕  no bridge
JWT claim:  admin_profile ({"type": "general"} or {"type": "scoped", "scopes": [...]})
```

`normalize_admin_profile` at `app/auth/roles.py:75` deserializes the `admin_profile` JWT claim into an `AdminProfile` dataclass. It has no awareness of `admin_capabilities` in DynamoDB. There is no service call that reads `admin_capabilities` and converts it to an `admin_profile` claim at login time.

### Why the capability names don't match

The capability names are also semantically misaligned:
- `admin_capabilities`: `billing_ops`, `billing_read`, `file_metadata`, `file_content`, `user_support`, `impersonation`
- `AdminScope` enum (enforced): `auth_support`, `billing_support`, `content_moderation`, `content_moderation_senior`

Even if the bridging code were written, it would need a capability→scope mapping table, since the names do not correspond one-to-one.

## 3. Impact / Exploit / Blast Radius

### Security consequence

Every admin user — regardless of what `admin_capabilities` is set to via the CLI — receives a JWT with no `admin_profile` claim. `normalize_admin_profile(None)` returns `AdminProfile(type=GENERAL)` (the fallback branch at `app/auth/roles.py:91`). `admin_profile_has_scope` for a `GENERAL` profile always returns `True` (line 122–123 of `roles.py`):

```python
def admin_profile_has_scope(profile: AdminProfile, scope: AdminScope | str) -> bool:
    ...
    if profile.type is AdminProfileType.GENERAL:
        return True   # GENERAL admins pass every scope check
```

Consequence: **every admin user currently has full general admin access**, including endpoints that are supposed to be restricted to `auth_support`, `billing_support`, `content_moderation`, and `content_moderation_senior` scopes. The scope enforcement system exists and is correctly coded, but is never triggered because the GENERAL fallback absorbs all real-world sessions.

### What a scoped admin should be blocked from

Based on the enforcement sites found in the codebase:
- `require_admin_scope("billing_support")` guards billing dispute resolution, credit adjustments, and payout reviews (`app/routers/billing.py:105`, `app/routers/admin_entitlements.py:21`).
- `require_admin_scope("auth_support")` guards impersonation start/stop (`app/routers/admin_impersonation.py:25`).
- `require_admin_scope("content_moderation")` guards DMCA takedown, content appeals, video review, messaging compliance exports, and file manager admin access (`app/routers/admin_dmca.py:41`, `app/routers/admin_appeals.py:37`, `app/routers/admin_video_review.py:35`, `app/routers/messaging.py:248–250`, `app/routers/filemanager.py:282`).
- `require_admin_scope("content_moderation_senior")` gates permanent ban capability (`app/routers/admin_moderation.py:47`).

A first-tier support admin who should only see `auth_support` actions can currently issue permanent bans, export private messages, and approve financial refunds — all via the existing admin API surface.

### Blast radius

- All admin accounts are currently fully privileged regardless of intended scope.
- Operators who ran `rootctl admin permissions set` to restrict an admin user achieved nothing. The restriction is invisible to the enforcement layer.
- Compliance and least-privilege requirements are unmet: even "read only" billing admins can perform destructive content moderation actions.

## 4. Fix Design (Code-Level)

### Option A (recommended): bridge admin_capabilities → admin_profile in token minting

The fix requires two coordinated changes:

**Step 1: mint_access_token reads admin_capabilities from DDB and writes admin_profile to JWT**

In `app/services/sessions.py`, the `mint_access_token` function must look up the user record and include `admin_profile` when the user is an admin. A capability→scope mapping table is needed.

```python
# app/services/sessions.py

_CAPABILITY_TO_SCOPE = {
    "billing_ops":    "billing_support",
    "billing_read":   "billing_support",
    "user_support":   "auth_support",
    "impersonation":  "auth_support",
    "file_content":   "content_moderation",
    "file_metadata":  "content_moderation",
}

def _build_admin_profile_claim(user_sub: str, user_item: dict) -> dict | None:
    """Return admin_profile JWT claim for admin users, or None for root/user."""
    role = normalize_role(user_item.get("role"))
    if role is not Role.ADMIN:
        return None
    caps = list(user_item.get("admin_capabilities") or [])
    if not caps:
        # No capabilities set → general admin (full access, current default behavior)
        return {"type": "general"}
    # Map capabilities to canonical scopes
    scopes = sorted({_CAPABILITY_TO_SCOPE[c] for c in caps if c in _CAPABILITY_TO_SCOPE})
    if not scopes:
        return {"type": "general"}
    return {"type": "scoped", "scopes": scopes}


def mint_access_token(user_sub: str, session_id: str) -> str:
    if not S.ui_access_token_secret:
        return ""
    access_ttl = _access_ttl_seconds_for_user(user_sub)
    user_item = T.users.get_item(Key={"user_sub": user_sub}).get("Item") or {}
    role_str = (user_item.get("role") or "").lower()
    role = "root" if _is_root_user(user_sub) else (role_str if role_str in ("admin", "user") else "user")
    auth_level = "high" if role == "root" else "standard"
    payload = {
        "sub": user_sub,
        "sid": session_id,
        "role": role,
        "auth_level": auth_level,
        "exp": now_ts() + access_ttl,
        "iat": now_ts(),
    }
    admin_profile = _build_admin_profile_claim(user_sub, user_item)
    if admin_profile is not None:
        payload["admin_profile"] = admin_profile
    return jwt.encode(payload, S.ui_access_token_secret, algorithm="HS256")
```

**Step 2: Enable the ROOTCTL_ADMIN_CAPABILITIES_ENABLED flag by default**

In `.env.local.example` and `.env.example`:
```
ROOTCTL_ADMIN_CAPABILITIES_ENABLED=1
```

**Step 3: Align ADMIN_CAPABILITIES set with canonical AdminScope values**

The current capability set in `rootctl.py` (`billing_ops`, `billing_read`, `file_metadata`, etc.) does not match `AdminScope` enum values. The recommended alignment is:

```python
# app/cli/rootctl.py:51
ADMIN_CAPABILITIES = {
    "auth_support",
    "billing_support",
    "content_moderation",
    "content_moderation_senior",
}
```

This makes the CLI capability names identical to the `AdminScope` values, eliminating the need for a mapping table. The `_CAPABILITY_TO_SCOPE` map in sessions.py becomes an identity mapping.

**Step 4 (alternative if Step 3 is rejected)**: Retain the current capability names but maintain the mapping table in `sessions.py` as designed above.

### Option B (rejected): remove the capability system and use admin_profile directly via CLI

The grant command could accept `--admin-profile-type general|scoped` and `--scope auth_support billing_support ...` directly, writing `admin_profile` to DDB and having `mint_access_token` read it. This eliminates the capability→scope translation but requires changing the `grant` and `permissions set` CLI interface. Rejected because Option A is backward-compatible with existing `rootctl admin permissions set` invocations.

### Dev/Prod parity (SECOPS-007)

`mint_access_token` already calls `T.users.get_item`, which goes through `app/core/tables.py` using DynamoDB Local in dev and real DynamoDB in prod. The DDB read is env-agnostic. No mock branch is needed — the same token-minting code runs in both environments, and the test suite runs offline against DynamoDB Local. The `ROOTCTL_ADMIN_CAPABILITIES_ENABLED` flag should be `1` in both `.env.local.example` (dev) and the production environment configuration.

### Backward compatibility

- Existing admin users who have no `admin_capabilities` set → `mint_access_token` returns `admin_profile: {"type": "general"}` → all scope checks pass → no behavior change.
- Admin users who had `admin_capabilities` set via the now-functional CLI → receive a scoped JWT on next login.
- The change takes effect at next token refresh (15-minute TTL by default). No session migration is needed.

def test_admin_with_capabilities_gets_scoped_profile():

        "user_sub": "admin@example.com",

    from app.auth.roles import AdminProfile, AdminScope, AdminProfileType, admin_profile_has_scope

def test_general_admin_passes_all_scope_checks():

    for scope in AdminScope:
        assert admin_profile_has_scope(general, scope), f"General admin blocked from {scope}"

### Observability

- `audit_event("admin_capabilities_updated_cli", ...)` is already emitted at line 1713.
- Add a log line in `mint_access_token` when a scoped profile is written to the token: `logger.info("mint_access_token admin_profile_type=%s sub=%s", admin_profile.get("type"), user_sub)`.
- Prometheus counter `admin_scope_denied_total` (already instrumented at `app/metrics.py`) will correctly increment when scoped admins are rejected, providing visibility into scope enforcement.

### Rollout sequence

1. Align `ADMIN_CAPABILITIES` set in `rootctl.py` with `AdminScope` values (or create mapping table).
2. Update `mint_access_token` in `sessions.py` to include `admin_profile`.
3. Enable `ROOTCTL_ADMIN_CAPABILITIES_ENABLED=1` in `.env.local.example` and production config.
4. Deploy.
5. Re-run `e2e_admin_session_setup.py` to regenerate test session tokens.
6. Run `just e2e` to verify no regressions.
7. For existing admin users: their next login automatically picks up the new token format. Scope restrictions take effect at next token refresh (15 minutes).

### Rollback

Remove the `admin_profile` injection from `mint_access_token`. All admin users revert to `GENERAL` (full access). Rollback is safe because the pre-fix state is "all admins have full access."

### Risks

- **New scoped admin is locked out of previously accessible endpoints**: If an admin had been informally relied upon for tasks outside their intended scope, the new enforcement will break those workflows. Requires a capabilities audit before production deployment.
- **DDB read latency in token minting**: The new `T.users.get_item` call in `mint_access_token` adds a DynamoDB read on every token refresh. At p99 DynamoDB GetItem latency (~5ms), this is negligible but should be monitored.

### Effort

**M** — bridging code in `sessions.py` (~30 lines), capability set alignment in `rootctl.py` (~10 lines), `.env` updates, tests, and rollout coordination. Estimated: 1–2 days.
