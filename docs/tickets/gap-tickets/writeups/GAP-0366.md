# GAP-0366: "queued" status bug silently swallowed — Remediation Write-up

> ~5 pages. Fix-oriented. Claim verified against actual code (no investigation doc exists).

## 1. Summary & Classification

**Severity**: HIGH  
**Source ticket**: VOD-001  
**Owning area**: VOD pipeline / transcode job submission  
**Status**: Open  
**Claim verdict**: CONFIRMED — the bug is exactly where the ticket says it is.

When a user submits a transcode job via `POST /ui/transcode-jobs`, the router attempts to advance the video's lifecycle status from `probing` to `"queued"`. The string `"queued"` is **not a valid `VideoStatus` literal** — the state machine has no such value. The `transition_video_status` call therefore raises an `HTTPException(409)`, which is immediately swallowed by a bare `except Exception` block. The video record stays in `"probing"` (or whatever pre-transition state it was in). The job itself is created successfully, but the video-metadata row is never updated, so the `ByStatusCreatedAt` GSI partition for `"pending_encoding"` stays empty.

**Related tickets**: GAP-0368 (identical root cause, identical line, duplicate coverage), VOD-001, VOD-003.

## 2. Current-State Investigation (root cause)

### Code path

**`app/routers/transcode_jobs.py`, lines 91–106**

```python
# Create the job
job = create_job(
    video_id=body.video_id,
    tenant_id=tenant_id,
    rendition_profiles=body.rendition_profiles,
    source_uri=source_uri,
    watermark_policy=body.watermark_policy,
    drm_policy=body.drm_policy,
    priority=body.priority,
)

# Transition video status to queued          ← line 101 comment
try:
    transition_video_status(video_id=body.video_id, to_status="queued")   # line 103
except Exception:
    logger.warning("Could not transition video %s to queued", body.video_id)
```

### State machine definition

**`app/services/video_state_machine.py`, lines 10–22**

```python
_ALLOWED_TRANSITIONS: Dict[VideoStatus, Set[VideoStatus]] = {
    "created":          {"probing", "deleted"},
    "probing":          {"pending_encoding", "probe_failed", "deleted"},
    "probe_failed":     {"probing", "deleted"},
    "pending_encoding": {"encoding", "deleted"},
    "encoding":         {"pending_review", "encoding_failed", "deleted"},
    ...
}
```

The literal `"queued"` does not appear anywhere in `_ALLOWED_TRANSITIONS` — not as a key and not as a reachable target from any state. The `VideoStatus` type alias (`app/models_video.py`, lines 7–20) lists twelve values; `"queued"` is not among them.

### What happens at runtime

1. `transition_video_status` calls `validate_transition(current.status, "queued")`.
2. `validate_transition` returns `TransitionValidationResult(legal=False, error_code="VIDEO_INVALID_STATE_TRANSITION")`.
3. The service raises `HTTPException(status_code=409, detail={...})`.
4. The `except Exception` at line 104 catches it silently; a `WARNING` is logged but no error is propagated to the caller.
5. The HTTP response to the client is HTTP 201 with a valid `TranscodeJobOut` body.
6. The video record remains in `"probing"` (or `"pending_encoding"` if probing already advanced it).

### Why "queued" was used

The confusion between job-domain vocabulary and video-metadata vocabulary is understandable. The `TranscodeJobs` table (a separate DynamoDB table) uses `status = "queued"` as the initial job status (`app/services/transcode_job_store.py`, line 51). The author of `transcode_jobs.py:103` apparently carried this string across into the video-metadata transition call without cross-checking the state machine. The two status namespaces are entirely separate: job statuses (`queued`, `running`, `completed`, `failed`) describe the transcode process, while video statuses (`created`, `probing`, `pending_encoding`, `encoding`, ...) describe the video's position in the editorial and delivery lifecycle.

### Full call chain

```
POST /ui/transcode-jobs
  → submit_transcode_job()                          [transcode_jobs.py:65]
    → create_job(...)                               [transcode_job_store.py:42]  — OK
    → transition_video_status(to_status="queued")   [transcode_jobs.py:103]
      → get_video(video_id)                         [video_metadata_store.py:373]
      → validate_transition(current.status, "queued")  [video_state_machine.py:32]

        → TransitionValidationResult(legal=False)
      → raise HTTPException(409)                    [video_metadata_store.py:376]

      logger.warning(...)                           — exception swallowed
  → return TranscodeJobOut(...)                     [transcode_jobs.py:107] — HTTP 201
```

The client sees a successful 201. The DynamoDB `VideoMetadata` row is unchanged.

### Dev vs prod parity

Both dev and production share the same `video_state_machine.py` and `transition_video_status` call path. There is no dev-mode short-circuit — the bug fires identically in both environments. DynamoDB Local (dev) and AWS DynamoDB (prod) both enforce the `validate_transition` check before any write.

## 3. Impact / Exploit / Blast Radius

### Direct operational impact

- Every transcode job submission leaves the video in its pre-submission status.
- The `ByStatusCreatedAt` GSI in the `VideoMetadata` DynamoDB table has a `"pending_encoding"` partition that is always empty. Any admin dashboard, monitoring query, or SLA alert that polls `status = "pending_encoding"` to count queued videos will permanently report zero — masking backlogs and making SLA alerts unreliable.
- Downstream workers (or an admin reviewer) that gate on `status == "pending_encoding"` before processing will skip those videos entirely.

### User-facing consequence

A video that completes probing but whose status never advances to `"pending_encoding"` appears perpetually "processing" in the player page. The `VideoPlayerPage.tsx` renders the `<ProcessingState />` spinner for all statuses in `["created", "probing", "pending_encoding", "encoding"]`. If the status stays `"probing"`, the spinner never resolves and the video never enters the review/publish workflow.

### Security / financial consequence

No direct monetary or security exploit — this is a correctness/availability gap. However, videos that are never published cannot generate subscription or per-view revenue, so any video that passes through the broken path is silently lost from the monetisation pipeline.

### Blast radius

Affects every video upload that reaches the job-submission step, which is every non-trivial VOD flow.

## 4. Fix Design (code-level)

### Minimal change

**File**: `app/routers/transcode_jobs.py`, line 103

Change:
```python
transition_video_status(video_id=body.video_id, to_status="queued")
```
To:
```python
transition_video_status(video_id=body.video_id, to_status="pending_encoding")
```

The comment on line 101 should also be updated to match:
```python
# Transition video status to pending_encoding
```

The `except Exception` guard is appropriate only for non-fatal side effects. Because an invalid status transition is always a programming error (not a transient infrastructure fault), the exception suppression should be tightened — but tightening the guard is a separate concern from this fix.

### SECOPS-007 dev/prod parity

The fix is a pure string literal change on a code path that is shared between dev and production. No mock/dev conditional is involved. After the fix, `transition_video_status` will succeed for any video currently in `"probing"` state (the normal post-probe state), and will log a warning only for genuinely unexpected states (e.g., a video still in `"created"`).

### Backward compatibility

No migration required. Existing stuck videos in `"probing"` state can be manually advanced via the admin API. No DynamoDB schema changes are needed.

### Alternatives considered

- **Add `"queued"` to the state machine**: Rejected. The state machine was intentionally designed without `"queued"` as a video status. The transcode-job table has its own `status` field with `"queued"`. Conflating the two status namespaces would widen the state space without value and force the discovery feed (`list_videos_by_status`) to handle a new status that has no UI meaning.
- **Remove the `except` guard entirely**: Would surface the 409 to the client as an HTTP 409, which is better than silent failure but would break the HTTP 201 contract the client expects from a job-creation endpoint. The preferred approach is to fix the literal; the guard itself can be tightened separately.
- **Validate `to_status` against `VideoStatus` literals at the `transition_video_status` call site**: Pydantic could enforce this if `to_status` were typed as `VideoStatus` rather than `str`. Adding `VideoStatus` typing to the parameter signature of `transition_video_status` would make the bug a type-check error rather than a runtime failure. This is a worthwhile hardening step but is independent of the one-line fix.

### Hardening: type-annotate `transition_video_status`

As a follow-up to the fix, the signature of `transition_video_status` in `app/services/video_metadata_store.py` (line 365) should be tightened:

```python
# Before:
def transition_video_status(*, video_id: str, to_status: str, ...) -> VideoMetadataModel:

# After:
def transition_video_status(*, video_id: str, to_status: VideoStatus, ...) -> VideoMetadataModel:
```

With `to_status: VideoStatus`, passing `"queued"` would be a mypy/pyright type error, catching this class of bug statically before it reaches runtime. This hardening does not block the GAP-0366 fix but should be included in the same PR.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

Create `tests/test_transcode_jobs_status_transition.py`:

```python
"""GAP-0366 regression: job submission must advance video to pending_encoding."""
import pytest
from unittest.mock import patch, MagicMock
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

def _make_session():
    return {"user_sub": "u_test", "role": "USER", "admin_profile": None}

@pytest.fixture(autouse=True)
def mock_deps(monkeypatch):
    video_mock = MagicMock()
    video_mock.owner_user_id = "u_test"
    video_mock.status = "probing"
    video_mock.id = "vid_001"
    video_mock.tenant_id = "u_test"
    video_mock.source_s3_key = "vod/u_test/raw/2026/01/vid_001/test.mp4"

    calls = []

    with (
        patch("app.routers.transcode_jobs.get_video", return_value=video_mock),
        patch("app.routers.transcode_jobs.create_job", return_value={
            "job_id": "job_001", "video_id": "vid_001", "tenant_id": "u_test",
            "status": "queued", "created_at": 0, "updated_at": 0, "attempt": 0,
        }),
        patch(
            "app.routers.transcode_jobs.transition_video_status",
            side_effect=lambda **kw: calls.append(kw),
        ) as mock_transition,
        patch("app.routers.transcode_jobs.require_ui_session",
              return_value=_make_session()),
    ):
        yield mock_transition, calls

def test_submit_job_transitions_to_pending_encoding(mock_deps):
    """FAILS before fix (to_status='queued'), PASSES after fix (to_status='pending_encoding')."""
    _, calls = mock_deps
    resp = client.post(
        "/ui/transcode-jobs",
        json={
            "video_id": "vid_001",
            "rendition_profiles": [{"name": "360p"}],
        },
        cookies={"ui_session": "fake", "ui_csrf": "tok"},
        headers={"x-csrf-token": "tok"},
    )
    assert resp.status_code == 201
    assert len(calls) == 1, "transition_video_status must be called exactly once"
    assert calls[0]["to_status"] == "pending_encoding", (
        f"Expected to_status='pending_encoding', got '{calls[0]['to_status']}'"
    )
```

**Before fix**: `calls[0]["to_status"]` equals `"queued"` → the `assert to_status == "pending_encoding"` assertion fails with a message clearly naming the wrong literal.  
**After fix**: `calls[0]["to_status"]` equals `"pending_encoding"` → assertion passes.

Note that the test uses `patch("app.routers.transcode_jobs.transition_video_status")` (patching the name as it is imported in the module under test, not the origin module). This is the standard Python mock pattern for injected function references and ensures the mock intercepts the actual call in `submit_transcode_job`.

### Observability and alerting

After the fix, the `WARNING: Could not transition video X to queued` log line should never appear for normal job submissions. It can be searched in the structured log output with:

```
grep "Could not transition video" .logs/uvicorn.log
```

In production, set up a CloudWatch Logs Metric Filter or a Datadog log monitor for this specific warning string and alert if it fires more than once per hour. A persistent occurrence post-deploy would indicate either (a) a video is being submitted for transcoding from a state from which `"pending_encoding"` is unreachable (e.g., already `"encoding"`, already `"deleted"`), or (b) a DynamoDB throttle on the write. The two cases have different remediation paths — (a) requires an admin status fix; (b) requires capacity scaling. Parsing the logged `video_id` from the warning message enables rapid triage.

Additionally, set up a metric on the `ByStatusCreatedAt` GSI item count for `status = "pending_encoding"` in the `VideoMetadata` table. In a healthy system, this count should move non-zero shortly after a job is submitted and drop back toward zero as the worker processes jobs. A count stuck at zero for more than the worker's poll interval is a signal that either the submit-side or the worker-side transitions are failing.

### Rollout

- **Effort**: S (single-line change + test).
- **Risk**: Very low. The fix aligns the code with the documented state machine. The only scenario where the fix changes behaviour from a success to a failure is if a video is somehow in a state from which `"pending_encoding"` is unreachable (e.g., already `"encoding"` or `"deleted"`). In those cases the old code also silently failed, so the visible behaviour is unchanged — only the log message differs.
- **Sequencing**: Ship this fix in the same commit as GAP-0368 (which targets the same line) and in the same deployment as GAP-0369 (which fixes the worker-completion transition). All three are required to achieve end-to-end correct video lifecycle management.
- **Rollback**: Revert the one-line change. No data migration needed.

### Data repair for stuck videos

Any video that was submitted for transcoding before this fix was deployed may be stuck in `"probing"` status indefinitely. A one-time repair script should:

1. Query the `TranscodeJobs` table for all jobs with `status IN ("queued", "running", "completed")`.
2. For each job, look up the corresponding video record.
3. If the video status is `"probing"` (indicating the submit-time transition never happened), advance it to `"pending_encoding"` via a direct `transition_video_status` call using an admin actor.
4. If the job is `"completed"` but the video is still in `"probing"` or `"pending_encoding"`, advance it to `"pending_review"` (the correct post-completion state, per GAP-0369 fix).

This repair should be run as a migration task in the deployment pipeline, not as ad-hoc DynamoDB edits, to ensure the audit trail is preserved.
