# GAP-0043: list_campaigns_by_status Does Not Use ByStatusCreatedAt GSI — Remediation Write-up

## 1. Summary & Classification

**Plain-English statement**: The ticket claims that `list_campaigns_by_status` in `app/services/ad_campaigns.py` performs an implicit full-table scan instead of using the `ByStatusCreatedAt` GSI. Investigation of the actual code reveals that the function **does** issue a `Query` against `IndexName="ByStatusCreatedAt"`. However, the `ByStatusCreatedAt` GSI on the `AdCampaigns` DynamoDB table is defined with `partition_key="status"` and `sort_key="created_at"`, and the `create_campaign` function at line 35–61 stores `created_at` as a numeric Unix timestamp. The DDB table definition at `scripts/local-ddb-init.py:1073–1077` correctly declares `attr_types={"created_at": "N"}` for this table. So the GSI is present and the Query is correct — the original ticket claim about a scan is inaccurate. The actual risk is a different, subtler problem: campaigns created before the `status` attribute was indexed (i.e., items that never had `status` written at creation time) will be silently absent from the GSI, causing valid active campaigns to be missed by the serving engine.

- **Severity**: HIGH
- **Source ticket**: ADS-004
- **Status**: Open
- **Owning area**: Ads Platform / Campaign Management
- **Effort**: S
- **Claim verdict**: CLAIM CORRECTED — the code at `app/services/ad_campaigns.py:80–86` already uses `IndexName="ByStatusCreatedAt"` with a `KeyConditionExpression`. The original gap ticket's claim that the function performs a full table scan is wrong. The real gap is that `create_campaign` does not write `status` as a top-level attribute to the item's GSI-eligible position in a way that DynamoDB requires to index it — specifically, `status` is stored in the item dict (line 51) but the `ByStatusCreatedAt` GSI partition key is `status`, which DynamoDB will index automatically as long as the attribute is present. That part is fine. However, the function never writes a `status` attribute using the GSI-projected fields, and there is no `ScanIndexForward=True` path. The more actionable gap is the lack of pagination: `list_campaigns_by_status("active")` returns only the first DynamoDB page (up to 1 MB / ~4,000 items) without following `LastEvaluatedKey`, meaning large-scale deployments silently miss campaigns beyond the first page.

**One-line impact**: At scale, `list_campaigns_by_status("active")` returns only the first DynamoDB page of active campaigns; campaigns on subsequent pages are never served, starving those advertisers of impressions without any error signal.

**Related tickets**: ADS-004 (source), GAP-0042 (serve_ad depends on the completeness of this list), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (Root Cause)

### The function under examination

`app/services/ad_campaigns.py:80–86`:

```python
def list_campaigns_by_status(status: str) -> list[dict]:
    resp = T.ad_campaigns.query(
        IndexName="ByStatusCreatedAt",
        KeyConditionExpression=Key("status").eq(status),
        ScanIndexForward=False,
    )
    return resp.get("Items", [])
```

The GSI query is correctly formed: it queries by `status` (the GSI partition key) with no sort-key condition, `ScanIndexForward=False` (newest first). This is not a full table scan.

### DynamoDB table definition

`scripts/local-ddb-init.py:1068–1078`:

```python
TableDef(
    _resolve_table_name(S.ad_campaigns_table_name, "AdCampaigns"),
    "pk",
    "sk",
    gsi=[
        {"index_name": "ByStatusCreatedAt", "partition_key": "status", "sort_key": "created_at"},
        {"index_name": "ByCampaignId", "partition_key": "campaign_id", "sort_key": "created_at"},
    ],
    attr_types={"created_at": "N"},
),
```

The GSI `ByStatusCreatedAt` exists with the correct key schema, and `created_at` is declared as type `N` (numeric) — matching `now_ts()` which returns an integer Unix timestamp. No schema issue exists.

### The real gap: missing pagination

The `query()` call returns a response dict with `Items` (first page, up to 1 MB) and optionally `LastEvaluatedKey` (pagination cursor). The function ignores `LastEvaluatedKey`. For a platform with thousands of active campaigns, DynamoDB will return only the first ~4,000 items (1 MB / ~250 bytes per campaign item) in a single response.

`serve_ad` at `app/services/ad_serving.py:73` calls:

```python
active_campaigns = list_campaigns_by_status("active")
```

If there are 10,000 active campaigns and the first DynamoDB page returns 4,000, the remaining 6,000 are silently excluded from every serve request. This is not a query correctness bug — the GSI is used — but a result-completeness bug.

### Secondary gap: campaign creation does not write to GSI index keys consistently

`app/services/ad_campaigns.py:35–61`, `create_campaign` builds the item dict and includes `"status": "draft"`. The `status` attribute is present, so DynamoDB will index the item in `ByStatusCreatedAt` immediately. There is no secondary gap here. However, `update_campaign` (lines 89–116) uses `UpdateExpression SET` which atomically updates `status` when a status transition occurs — this also correctly updates the GSI because DynamoDB maintains GSI projections on `update_item` calls.

### Serve frequency

`serve_ad` is called on every ad slot request — potentially thousands of times per second at scale. Each call invokes `list_campaigns_by_status("active")`, which issues a DynamoDB GSI query. There is no in-process cache or TTL-bounded cache on the result. At 1,000 RPS serving rate this generates 1,000 DynamoDB GSI queries per second — a significant cost and latency driver independent of the pagination gap. This is noted as a separate optimisation opportunity.

## 3. Impact / Exploit / Blast Radius

**Missed impressions**: Campaigns beyond the first DynamoDB page (sorted by `created_at DESC`) are never entered into the `candidates` list in `serve_ad`. Those campaigns receive zero impressions despite having approved budgets, active status, and valid targeting. Advertisers are charged nothing (no impressions means no billing), but they receive no reach, violating advertiser SLAs.

**Revenue loss**: If 40% of active campaigns are on page 2+ of the GSI result, the platform serves ads for only 60% of the eligible inventory. At $10 average CPM and 1M daily impressions, 400,000 missed impressions represent $4,000/day in lost revenue.

**Unfair auction**: `serve_ad` selects the winner by `bid_cpm_cents` score (highest bid wins). If high-bidding newer campaigns fall on page 2 (because `ScanIndexForward=False` means newest-first — wait, this actually puts the *newest* campaigns on page 1 and *oldest* on page 2). Campaigns that have been active longer (lower `created_at`) are excluded first, which means long-running campaigns with large budgets may be perpetually missed.

**Silent failure**: No error is logged, no metric incremented, and no alert fires when `LastEvaluatedKey` is non-null. The bug is completely invisible without explicit instrumentation.

## 4. Fix Design (code-level)

### Replace single-page query with full paginated scan of the GSI

Replace the current `list_campaigns_by_status` in `app/services/ad_campaigns.py`:

```python
def list_campaigns_by_status(status: str, limit: int = 2000) -> list[dict]:
    """Return all campaigns with the given status, paginating through all DynamoDB pages.

    Args:
        status: Campaign status to filter by (e.g. "active").
        limit: Hard cap on total items returned to prevent unbounded memory use in
               extremely large deployments. Default 2000; adjust via config if needed.
    """
    items: list[dict] = []
    kwargs: dict = {
        "IndexName": "ByStatusCreatedAt",
        "KeyConditionExpression": Key("status").eq(status),
        "ScanIndexForward": False,
    }
    while True:
        resp = T.ad_campaigns.query(**kwargs)
        items.extend(resp.get("Items", []))
        last_key = resp.get("LastEvaluatedKey")
        if not last_key or len(items) >= limit:
            break
        kwargs["ExclusiveStartKey"] = last_key
    return items[:limit]
```

Key design decisions:

- **Hard limit**: `limit=2000` prevents runaway memory use if tens of thousands of campaigns become active simultaneously. The value should be derived from a config setting (`S.ad_serving_max_active_campaigns`) so it can be tuned without a code deploy.
- **ScanIndexForward=False**: Retained to preserve newest-first ordering (most recently created campaigns are fetched first, which maps to most recently approved campaigns — useful for fairness).
- **Logging**: Add `logger.warning("ad_campaign_list_truncated status=%s count=%d", status, limit)` when `len(items) >= limit` to alert ops.

### Caching (optional, recommended)

For production scale, wrap `list_campaigns_by_status` with a short TTL in-process cache:

```python
import functools, time

_CAMPAIGN_CACHE: dict[str, tuple[float, list[dict]]] = {}
_CAMPAIGN_CACHE_TTL_SECONDS = 30  # refresh at most every 30s

def list_campaigns_by_status(status: str, limit: int = 2000) -> list[dict]:
    cached_ts, cached_items = _CAMPAIGN_CACHE.get(status, (0.0, []))
    if time.time() - cached_ts < _CAMPAIGN_CACHE_TTL_SECONDS:
        return cached_items
    items = _list_campaigns_by_status_uncached(status, limit)
    _CAMPAIGN_CACHE[status] = (time.time(), items)
    return items
```

This reduces DynamoDB GSI reads from 1,000/s to 1 per 30 s per status value. A 30-second cache is acceptable for ad serving (campaigns do not need millisecond-precision activation).

**SECOPS-007 parity**: The cache is a Python in-process dict. With `--workers 1` (dev/test) it is safe. In production with multiple uvicorn workers, each worker maintains its own cache — acceptable for ad serving (worst case: a campaign activates on worker A but worker B still serves the old list for up to 30s). For strict consistency, use Redis or DynamoDB DAX as the cache backend behind a feature flag. The pagination fix must be deployed regardless of the caching decision.

### Dev/Prod parity

DynamoDB Local (port 8001) supports `ExclusiveStartKey` pagination and respects `Limit` per page. The pagination loop behaves identically in dev and production. No dev-only branching is needed.

### Backward compatibility

No API surface changes. The function signature gains an optional `limit` parameter with a sensible default. All existing call sites (`serve_ad`, `get_serving_stats`) continue to work without modification.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline — fails before fix, passes after)

Add to `tests/test_ad_campaigns.py`:

```python
def test_list_campaigns_by_status_paginates(ddb_mock):
    """list_campaigns_by_status must return campaigns from all DynamoDB pages."""
    from app.services.ad_campaigns import list_campaigns_by_status, create_campaign
    from app.models import CampaignCreateIn
    from app.core.tables import T
    from unittest.mock import patch, call

    account_id = "acct_test_pagination"
    # Create 3 campaigns and mark them all active
    campaign_ids = []
    for i in range(3):
        data = CampaignCreateIn(
            name=f"Campaign {i}",
            objective="awareness",
            budget_cents=10000,
            budget_type="lifetime",
        )
        item = create_campaign(account_id, data)
        campaign_ids.append(item["campaign_id"])
        T.ad_campaigns.update_item(
            Key={"pk": f"ACCT#{account_id}", "sk": f"CAMPAIGN#{item['campaign_id']}"},
            UpdateExpression="SET #s = :s",
            ExpressionAttributeNames={"#s": "status"},
            ExpressionAttributeValues={":s": "active"},
        )

    # Patch T.ad_campaigns.query to simulate pagination:
    # first call returns items[0] + LastEvaluatedKey, second call returns items[1:3]
    original_query = T.ad_campaigns.query
    call_count = [0]
    all_items = T.ad_campaigns.query(
        IndexName="ByStatusCreatedAt",
        KeyConditionExpression=__import__(
            "boto3.dynamodb.conditions", fromlist=["Key"]
        ).Key("status").eq("active"),
    )["Items"]

    def mock_query(**kwargs):
        call_count[0] += 1
        if call_count[0] == 1:
            return {"Items": all_items[:1], "LastEvaluatedKey": {"pk": "sentinel"}}
        else:
            return {"Items": all_items[1:], "Count": len(all_items[1:])}

    with patch.object(T.ad_campaigns, "query", side_effect=mock_query):
        result = list_campaigns_by_status("active")

    assert len(result) == 3, f"Expected 3 campaigns, got {len(result)}"
    assert call_count[0] == 2, "Expected two DynamoDB Query calls (pagination)"
```

**Fails before fix**: The original function calls `T.ad_campaigns.query` only once and returns `resp.get("Items", [])`, which is `all_items[:1]` (1 item). `len(result) == 1 != 3`.

**Passes after fix**: The paginated loop follows `LastEvaluatedKey` and makes a second call, accumulating all 3 items.

### Caching consideration — dev/prod parity

The in-process `_CAMPAIGN_CACHE` described in Section 4 uses a Python `dict`. In dev mode (`--workers 1`, per CLAUDE.md), a single worker process owns the cache and it behaves deterministically. In production with multiple uvicorn workers (each has its own cache), the 30-second staleness window means campaign activations propagate to all workers within 30 seconds. This is acceptable for ad serving — sub-minute activation latency is standard. If strict single-digit-second activation is required (e.g., for time-critical campaign launches), the cache can be backed by Redis with `S.redis_url` gated behind a feature flag (`S.ad_campaign_cache_enabled`).

### Rollout

- **Effort**: S (< half day for pagination fix; M for caching if included).
- **Risk**: Low. The fix adds iteration; the first-page behaviour is identical to current behaviour. The cache addition is optional and can be a follow-up PR behind a feature flag.
- **Rollback**: Revert to single-page query; campaigns beyond page 1 are missed again, but no data is corrupted. The risk of rollback is therefore the same as the current state — no regressions introduced.
- **Sequencing**: Deploy the pagination fix before any campaign scale milestone that could push active campaign count beyond ~4,000. Deploy the cache separately after validating the pagination fix in production.
- **Monitoring**: After deploy, add a CloudWatch metric for `ByStatusCreatedAt` GSI `ConsumedReadCapacityUnits`. If pages consumed drop (due to caching), this metric should decrease proportionally.
