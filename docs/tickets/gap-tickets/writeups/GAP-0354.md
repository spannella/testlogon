# GAP-0354: `POST /ui/discover/reindex` Is Self-Only — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code before writing; all cites are `file:line`.

## 1. Summary & Classification

**Bug statement**: The discovery re-index endpoint (`POST /ui/discover/reindex`) only re-indexes the currently authenticated user. There is no admin-level endpoint to bulk-reindex all users. This means that after a deployment, a data-migration, or an index corruption event, operators have no way to rebuild the discovery index for all users — they would need every individual user to self-trigger a re-index, which is operationally impossible.

- **Severity**: HIGH
- **Source ticket**: SOC-003 §4 ("add an admin/root-gated `POST /ui/discover/admin/reindex-all` endpoint backed by `reindex_all_users()`")
- **Status**: Open — confirmed missing. No `reindex_all_users` function exists in `app/services/discovery.py`; no admin path exists in `app/routers/discovery.py`.
- **Owning area**: Backend / Discovery Service + Discovery Router
- **Investigation verdict**: Confirmed exactly as stated. The gap ticket's location `POST /ui/discover/reindex` and proposed fix are accurate.
- **Related tickets**: GAP-0353 (discovery index not updated on profile change — companion gap). SECOPS-007 applies to the DynamoDB scan path and the admin role gate.

## 2. Current-State Investigation (Root Cause)

### The existing endpoint is self-only

`app/routers/discovery.py:70–75`:

```python
@router.post("/reindex")
async def discover_reindex_user(
    user: AuthenticatedUser = Depends(get_authenticated_user),
):
    count = index_user_for_discovery(user.sub)
    return {"ok": True, "tokens_indexed": count}
```

`user.sub` is hardcoded as the target — no `user_id` parameter is accepted. Any authenticated user can call this; only their own profile is re-indexed.

### No admin-level endpoint exists

A full-text search of `app/routers/discovery.py` confirms there is no route with any of the words `admin`, `all`, `bulk`, or `reindex-all`. There is no function named `reindex_all_users` anywhere in the codebase:

```bash
grep -rn "reindex_all" app/   # → (no results)
```

### No admin auth dependency in the discovery router

`app/routers/discovery.py` imports only `get_authenticated_user` from `app.auth.deps`. It does not import `require_admin_or_root`, `require_root`, or any role-check from `app.auth.policy`. Adding admin-gated endpoints requires importing the policy helpers that already exist in the codebase.

### Profile table scan pattern

`index_user_for_discovery` in `app/services/discovery.py:48–96` fetches a single user by `T.profile.get_item(Key={"user_sub": user_id})`. To index all users a scan of `T.profile` with pagination is required. The profile table uses `user_sub` as the partition key; a full scan is necessary (no GSI that would enumerate all users efficiently without one).

### Dev vs prod

In dev, `T.profile` points to DynamoDB Local (port 8001); in prod to the AWS-managed table. The scan code path is identical. SECOPS-007 requires that the same code run in both environments — no dev-only shortcut is acceptable.

## 3. Impact / Exploit / Blast Radius

**Operational risk — index rebuild is impossible**: If the `DiscoveryIndex` table is emptied (e.g., table recreation after a terraform apply, a botched data migration, a DynamoDB TTL misconfiguration), there is no way to repopulate it short of writing custom one-off scripts or having every user manually visit a page that most users don't know exists.

**Stale data accumulation**: GAP-0353 means that every profile update produces a divergence between the profile table and the discovery index. Without a bulk-reindex endpoint, accumulated staleness cannot be corrected until each user individually triggers a self-reindex.

**No security or financial blast radius**: This gap is operational, not a security vulnerability. An attacker cannot exploit the absence of this endpoint. The risk is entirely availability of the search feature.

**Operational blast radius**: Platform operators, on-call engineers, and support staff cannot correct discovery data in production without deploying a hotfix script. This adds hours of MTTR for any search-outage incident.

## 4. Fix Design (Code-Level)

### 4.1 Add `reindex_all_users()` to `app/services/discovery.py`

```python
def reindex_all_users(*, batch_size: int = 50) -> Dict[str, int]:
    """Scan the profile table and re-index every user for discovery.

    Returns {"users_indexed": int, "tokens_total": int, "errors": int}.
    This is an O(n) full scan — call only from admin/root-gated endpoints.
    """
    import logging as _log
    logger = _log.getLogger(__name__)

    users_indexed = 0
    tokens_total = 0
    errors = 0
    scan_kwargs: Dict[str, Any] = {"ProjectionExpression": "user_sub"}
    last_key = None

    while True:
        if last_key:
            scan_kwargs["ExclusiveStartKey"] = last_key
        resp = T.profile.scan(**scan_kwargs)
        items = resp.get("Items", [])
        for item in items:
            user_sub = item.get("user_sub")
            if not user_sub:
                continue
            try:
                count = index_user_for_discovery(user_sub)
                tokens_total += count
                users_indexed += 1
            except Exception:
                logger.warning("reindex_all: failed for user %s", user_sub, exc_info=True)
                errors += 1
        last_key = resp.get("LastEvaluatedKey")
        if not last_key:
            break

    return {"users_indexed": users_indexed, "tokens_total": tokens_total, "errors": errors}
```

Key design choices:
- Uses `ProjectionExpression="user_sub"` to minimize read-unit consumption (only the partition key is fetched per page; `index_user_for_discovery` then fetches the full profile item individually).
- Paginates via `LastEvaluatedKey` — handles tables with thousands of users without hitting the 1 MB DynamoDB scan limit.
- Non-fatal per-user errors: one bad profile item cannot abort the entire batch.

### 4.2 Add the admin endpoint to `app/routers/discovery.py`

Add the import at the top of the router file:

```python
from app.auth.policy import require_admin_or_root
from app.services.discovery import reindex_all_users
```

Add the endpoint:

```python
@router.post("/admin/reindex-all")
async def discover_admin_reindex_all(
    user: AuthenticatedUser = Depends(require_admin_or_root),
):
    """Bulk-reindex all users in the discovery index.

    Admin or root access required. Long-running: executes synchronously in the
    request handler. For large datasets (>10k users) consider calling this from
    a background task or a CLI script using the same service function.
    """
    result = reindex_all_users()
    return {"ok": True, **result}
```

`require_admin_or_root` is already defined in `app/auth/policy.py:67`:

```python
async def require_admin_or_root(user: AuthenticatedUser = Depends(get_authenticated_user)) -> AuthenticatedUser:
    ...
```

No new auth infrastructure is needed.

### 4.3 Dev/prod parity (SECOPS-007)

- `T.profile` resolves to the same DynamoDB table handle in both dev (`DDB_ENDPOINT_URL=http://localhost:8001`) and prod (AWS). The scan code is identical.
- The `require_admin_or_root` dependency works in both environments: in dev it validates the role from the `ui_access_token` JWT cookie; in prod from Cognito JWT or the same cookie path.
- No environment-specific branch or `dev_mode` flag is needed. The endpoint is additive; it does not change any existing behaviour.

### 4.4 Async/background variant (optional, for very large datasets)

For platforms with > 50k users, the synchronous scan could time out (uvicorn default 30s). Add a FastAPI `BackgroundTasks` variant:

```python
@router.post("/admin/reindex-all-async")
async def discover_admin_reindex_all_async(
    background_tasks: BackgroundTasks,
    user: AuthenticatedUser = Depends(require_admin_or_root),
):
    background_tasks.add_task(reindex_all_users)
    return {"ok": True, "message": "Reindex started in background"}
```

This returns immediately and runs the scan in a thread. The current stack size (< 10k users in dev) does not require this; it is an upgrade path.

### 4.4b Token cleanup during bulk reindex

An optional enhancement to `reindex_all_users` is to delete stale token items for users whose display names have changed. The current `index_user_for_discovery` call only overwrites existing tokens for the new name but does not delete tokens for the old name. A full cleanup would require querying the `DiscoveryIndex` for all `USER#<user_id>` items (via a GSI or a filtered scan on the secondary key), computing the diff between existing and current tokens, and deleting the obsolete ones. This is a future enhancement; the immediate priority is ensuring new tokens are written.

### 4.5 CLI / script equivalent

For break-glass use without HTTP access, add to `scripts/rootctl` or a new `scripts/discovery_reindex.py`:

```python
#!/usr/bin/env python3
"""Reindex all users for discovery. Run via: .venv/bin/python scripts/discovery_reindex.py"""
import os, sys
sys.path.insert(0, os.path.dirname(os.path.dirname(__file__)))
from app.services.discovery import reindex_all_users
result = reindex_all_users()
print(result)
```

### 4.6 Alternatives considered

- **Per-user batch API (admin calls reindex for each user_id in a list)**: More flexible but requires the caller to enumerate all users externally. The full scan endpoint is simpler for the "rebuild everything" case and is the right operator tool for an emergency rebuild.
- **DynamoDB Streams fan-out**: Streams on the profile table could automatically trigger re-indexing on every profile write. Would eliminate both GAP-0353 and GAP-0354. Requires Lambda or Kinesis infrastructure not present in this stack; out of scope for this ticket. The admin endpoint provides a complementary bulk-repair tool even if Streams is eventually adopted.
- **No admin endpoint, rely on GAP-0353 fix**: Once GAP-0353 is fixed (index updated on every profile save), new divergences stop accumulating. But historical divergences — all profiles updated between the SIGN-001 deployment and the GAP-0353 fix — still require a one-time bulk repair. The admin endpoint is the correct tool for that repair step.
- **Scheduled nightly reindex**: run `reindex_all_users` via cron each night to keep the index fresh. This would also repair divergences caused by GAP-0353. The downside is that search results lag up to 24 hours behind profile updates. The GAP-0353 event-driven fix is the primary solution; a nightly job is useful only as a safety net and is documented in §4.5 (CLI/script variant).

### Effort and risk

**Effort**: S (as stated in the gap ticket). The service function `reindex_all_users` is ~30 lines; the endpoint is ~10 lines.

**Rollout**: Additive endpoint — no existing behaviour changes. Deploy with GAP-0353 fix for maximum effect.

**Risks**: Full table scan is O(n) in profile count. On a large DynamoDB table (> 100k items) a synchronous scan may exhaust the HTTP request timeout. Mitigate by converting to the `BackgroundTasks` variant (§4.4) for deployments with large user bases. In dev with seed data (< 100 profiles) the synchronous endpoint completes in < 1 s.

**Rate limiting**: Each user's reindex writes N tokens to the `DiscoveryIndex` table, where N is the number of prefix tokens generated from their display name. For a 10,000-user platform with average display names of 2 words, this is approximately 10,000 × 16 tokens = 160,000 write units per bulk reindex call. On a table provisioned at 5 WCU this will take ~32 seconds and will consume provisioned capacity. Run bulk reindex during off-peak hours in production. In on-demand mode the cost is absorbed automatically.

**Access control audit**: Every call to `POST /ui/discover/admin/reindex-all` is an admin action. Add an audit log entry at the start of the endpoint:

```python
from app.services.alerts import audit_event
audit_event("discovery_bulk_reindex_started", user.sub, None, outcome="started")
```

This ensures the operation is traceable in the security audit log alongside other admin actions.
