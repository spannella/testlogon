# GAP-0152: dashboard_sse_publish Has No Call Sites — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at app/services/dashboard_sse.py and all tip ledger write paths.

## 1. Summary & Classification

**Plain-English statement:** The creator dashboard's real-time SSE push infrastructure was implemented completely — the publish function, subscription/unsubscription lifecycle, and the SSE HTTP endpoint (`GET /ui/dashboard/stream`) all exist and are wired. However, `dashboard_sse_publish` is never called anywhere in the application. When a creator receives a tip (earnings update) or crosses a milestone threshold, no SSE event is pushed to their open dashboard stream. The dashboard can receive a heartbeat keepalive, but it never receives real-time `earnings:update` or `milestone:reached` events; those updates are only visible after a manual page refresh.

- **Severity:** HIGH — real-time earnings feedback is a core creator experience feature; silent failure degrades perceived platform quality and may affect creator trust.
- **Source ticket:** CREATOR-003
- **Status:** Open
- **Owning area:** Creator Dashboard / Tip Ledger / Milestone Detection

**Claim verdict:** Confirmed. Exhaustive grep across all `.py` files finds zero invocations of `dashboard_sse_publish` outside its own definition. The function is defined at `app/services/dashboard_sse.py:39` and is never imported or called by any other module.

**Related tickets:** GAP-0153 (check_milestone has no call sites — the two gaps compound each other), CREATOR-003, SECOPS-007.

## 2. Current-State Investigation (Root Cause)

### The publish function is fully implemented but orphaned

`app/services/dashboard_sse.py:39–53`:
```python
def dashboard_sse_publish(user_id: str, event: Dict[str, Any]) -> None:
    """Publish an event to all subscribers of a user's dashboard stream."""
    subs = _DASHBOARD_SUBSCRIBERS.get(user_id)
    if not subs:
        return
    dead = []
    for q in list(subs):
        try:
            q.put_nowait(event)
        except asyncio.QueueFull:
            dead.append(q)
    for q in dead:
        subs.discard(q)
        if not subs:
            _DASHBOARD_SUBSCRIBERS.pop(user_id, None)
```

The supporting infrastructure is also complete:
- `dashboard_sse_subscribe(user_id)` at line 11: enqueues a new `asyncio.Queue(maxsize=100)` and enforces max-1 connection policy.
- `dashboard_sse_unsubscribe(user_id, q)` at line 29: cleans up on disconnect.
- `GET /ui/dashboard/stream` in `app/routers/creator_dashboard.py:169`: the SSE HTTP endpoint that streams events from the queue with a 30-second keepalive.

The entire pipeline exists and is production-quality. The only missing piece is the call from the event-producing code back into `dashboard_sse_publish`.

### Where the calls should be: tip ledger write

The primary earnings event hook should fire inside `write_tip_ledger` in `app/services/tip_ledger.py:88`. This function is the central chokepoint for all tip receipts across every tipping surface:
- Direct message tip: `app/routers/messaging.py:7940–7941`
- Image message tip: `app/routers/messaging.py:8208–8209`
- Message tip-on-send (broadcast): `app/routers/messaging.py:8813–8814`
- Newsfeed post tip: `app/routers/newsfeed.py:4630–4631`
- Newsfeed comment tip: `app/routers/newsfeed.py:5623–5624`
- Broadcast tip: `app/services/broadcast_tip_store.py:149`

`write_tip_ledger` at line 88 already writes both the debit (tipper) and credit (recipient) ledger entries. The recipient's `user_id` is available as `entry.recipient_user_id`. Placing the `dashboard_sse_publish` call here means all tipping surfaces benefit automatically.

### Where the calls should be: milestone detection

`dashboard_sse_publish` should also be called from `check_milestone` in `app/services/milestones.py:49`, after a successful new milestone write (when the DynamoDB `put_item` succeeds and `ConditionalCheckFailedException` is not raised, meaning a genuinely new milestone was recorded). This is covered in detail in GAP-0153, but the dependency is noted here: GAP-0152 and GAP-0153 should be fixed in the same PR since `check_milestone` itself also has no call sites.

### Why the bug manifests

1. Creator opens `/dashboard`, which opens an SSE connection to `GET /ui/dashboard/stream`.
2. Another user tips the creator.
3. `write_tip_ledger` writes debit + credit to DynamoDB.
4. No call to `dashboard_sse_publish` is made.
5. The creator's SSE stream receives only keepalive comments (`: keepalive\n\n`) every 30 seconds.
6. The earnings counter on the dashboard is stale until the creator refreshes the page or the React Query polling interval fires (if one is configured).

The bug is purely a missing function call. There is no architectural problem.

## 3. Impact / Exploit / Blast Radius

### Creator experience degradation

Real-time earnings notifications are a core differentiator for creator platforms. When a creator is streaming live or actively engaging with fans, the absence of immediate earning updates:
- Prevents creators from acknowledging tips in real time, reducing fan engagement.
- Degrades trust in the platform's reliability; creators may believe tips are not being processed.
- Makes milestone celebration (confetti animation, achievement unlocking) impossible in real time — milestones only appear after a full page reload.

### No financial or security exploit

The missing SSE publish does not cause financial data loss. Tip ledger entries are written correctly to DynamoDB regardless of whether the SSE event fires. Earnings are accurately recorded; the gap is purely a display/notification failure.

### Blast radius

- Affects all creators with an open dashboard SSE connection.
- Every tipping surface (messages, posts, comments, broadcasts) is affected — six distinct code paths all fail to push events.
- Milestone events are also never pushed (see GAP-0153), compounding the user-visible impact.
- No data loss, no security exposure, no financial miscalculation.

## 4. Fix Design (Code-Level)

### Change 1: call `dashboard_sse_publish` from `write_tip_ledger`

In `app/services/tip_ledger.py`, add a publish call at the end of `write_tip_ledger`, after both ledger entries are written and the `result` dict is populated:

```python
# app/services/tip_ledger.py — inside write_tip_ledger(), after the two try/except ledger writes

    # Notify recipient's dashboard stream (best-effort, same as ledger writes)
    try:
        from app.services.dashboard_sse import dashboard_sse_publish
        dashboard_sse_publish(
            entry.recipient_user_id,
            {
                "type": "earnings:update",
                "amount_cents": entry.amount_cents,
                "currency": entry.currency,
                "content_type": entry.content_type,
                "content_id": entry.content_id,
                "tip_payment_id": entry.tip_payment_id,
            },
        )
    except Exception:
        logger.warning("dashboard_sse_publish failed for tip", exc_info=True)

    return result
```

Key design decisions:
- **Lazy import inside `try/except`:** Prevents circular imports (tip_ledger → dashboard_sse is safe, but the guard is cheap insurance) and avoids a hard failure if the SSE module is unavailable.
- **Best-effort only:** The ledger write is the source of truth; SSE delivery is fire-and-forget. Consistency of accounting is unaffected by SSE failures.
- **Placed after both ledger writes:** The credit must be recorded before the notification is sent; the recipient should never see a notification for a tip that failed to write.

### Change 2: call `dashboard_sse_publish` from `check_milestone`

In `app/services/milestones.py`, inside `check_milestone`, after the successful `put_item` (after the `ConditionExpression` write succeeds, before the `return milestone`):

```python
# app/services/milestones.py — inside check_milestone(), after logger.info(...), before return milestone

    try:
        from app.services.dashboard_sse import dashboard_sse_publish
        dashboard_sse_publish(
            user_id,
            {
                "type": "milestone:reached",
                "milestone_id": milestone["milestone_id"],
                "metric": metric,
                "threshold": achieved_threshold,
                "formatted": milestone["formatted"],
                "achieved_at": now,
            },
        )
    except Exception:
        logger.warning("dashboard_sse_publish failed for milestone", exc_info=True)

    return milestone
```

### Dev/Prod parity (SECOPS-007)

`dashboard_sse_publish` is a pure in-process, in-memory operation — it places a dict onto an `asyncio.Queue`. There is no AWS API call, no DynamoDB write, and no environment-specific code path. The function works identically in dev (uvicorn single worker) and in production.

The only environment-specific consideration is the `--workers 1` requirement documented in CLAUDE.md: moto's in-process S3 state is per-process, and similarly the `_DASHBOARD_SUBSCRIBERS` dict is per-process. In production, if multiple uvicorn workers are run, each worker has its own subscriber dict, and a tip processed by worker A will not reach a client connected to worker B. This is a pre-existing architectural limitation (the same constraint applies to the existing alerts SSE at `app/services/alerts_sse.py`), not introduced by this fix. In production, a Redis pub/sub backend would be needed for multi-worker deployments — outside scope of this fix.

### Backward compatibility

No database migrations, no API contract changes. The SSE event payload shapes (`earnings:update`, `milestone:reached`) are new event types sent over an existing SSE stream; the frontend can ignore unknown event types gracefully.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

```python
"""Regression test for GAP-0152: dashboard_sse_publish called on tip ledger write."""
import asyncio
from unittest.mock import patch, MagicMock
import pytest

from app.services.tip_ledger import TipLedgerEntry, write_tip_ledger


def test_write_tip_ledger_publishes_sse_event(monkeypatch):
    """FAILS before fix (no publish call); PASSES after fix."""
    published_events = []

    def mock_publish(user_id, event):
        published_events.append((user_id, event))

    monkeypatch.setattr(
        "app.services.dashboard_sse.dashboard_sse_publish",
        mock_publish,
    )

    # Mock DynamoDB writes to avoid needing a real table
    with patch("app.services.tip_ledger.T") as mock_T:
        mock_T.billing = MagicMock()
        mock_T.billing.put_item = MagicMock()

        entry = TipLedgerEntry(
            tipper_user_id="user_alice",
            recipient_user_id="user_bob",
            amount_cents=500,
            content_type="message",
            content_id="msg_abc123",
        )
        write_tip_ledger(entry)

    # After fix: one event published to recipient's dashboard stream
    assert len(published_events) == 1, "Expected exactly one SSE publish call"
    uid, event = published_events[0]
    assert uid == "user_bob"
    assert event["type"] == "earnings:update"
    assert event["amount_cents"] == 500
    assert event["content_type"] == "message"


def test_write_tip_ledger_sse_failure_does_not_propagate(monkeypatch):
    """SSE publish failure must not cause tip ledger write to raise."""
    def mock_publish_raises(user_id, event):
        raise RuntimeError("SSE queue unavailable")

    monkeypatch.setattr(
        "app.services.dashboard_sse.dashboard_sse_publish",
        mock_publish_raises,
    )

    with patch("app.services.tip_ledger.T") as mock_T:
        mock_T.billing = MagicMock()
        mock_T.billing.put_item = MagicMock()

        entry = TipLedgerEntry(
            tipper_user_id="user_alice",
            recipient_user_id="user_bob",
            amount_cents=100,
            content_type="post",
            content_id="post_xyz",
        )
        # Must not raise even when SSE publish fails
        result = write_tip_ledger(entry)

    assert "debit_entry_id" in result
    assert "credit_entry_id" in result
```

**Fails before fix:** `published_events` is empty after `write_tip_ledger` returns, so the `len == 1` assertion fails.
**Passes after fix:** `dashboard_sse_publish` is called exactly once with the recipient's user ID and an `earnings:update` event dict.

### Rollout

- **Effort:** S (Small) — two files, two try/except blocks, approximately 20 lines of new code.
- **Risk:** Very low. Both changes are wrapped in `try/except` and are best-effort. No existing behaviour changes; only adds new event emission.
- **Sequencing:** Should be fixed alongside GAP-0153 (`check_milestone` call sites) in the same PR, since `milestone:reached` events require both fixes.
- **Rollback:** Remove the `dashboard_sse_publish` calls. No state is persisted by SSE publish; rollback has no data cleanup requirement.
