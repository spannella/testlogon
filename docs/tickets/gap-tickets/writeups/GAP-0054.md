# GAP-0054: Dynamic Per-Creator Revenue Share Not Connected to Billing Engine — Remediation Write-up

## 1. Summary & Classification

**Gap**: `app/services/ad_billing.py` uses a hardcoded module-level constant
`PLATFORM_REVENUE_SHARE_PCT = 30` for all ad revenue splits. The per-creator revenue share
system — stored as `revenue_share_bps` in the `billing` table and retrievable via
`get_creator_revenue_share_bps` in `content_ad_controls.py` — is never consulted during
billing. Every creator receives exactly 70% of ad revenue regardless of any negotiated rate.

**Severity**: HIGH  
**Source ticket**: ADS-010  
**Owning area**: Ad Billing / Revenue Share  
**Status**: Open — claim confirmed against live code.

`ad_billing.py` line 19: `PLATFORM_REVENUE_SHARE_PCT = 30` (hardcoded).  
`ad_billing.py` line 152: `platform_share = max(0, (charge_cents * PLATFORM_REVENUE_SHARE_PCT) // 100)`  
`content_ad_controls.py` lines 78–82: `get_creator_revenue_share_bps` exists and reads `billing` table.  
No import of `content_ad_controls` or `get_creator_revenue_share_bps` exists anywhere in `ad_billing.py`.

**One-line impact**: Per-creator negotiated revenue-share contracts are completely ignored;
all creators are billed at the platform default 70/30 split regardless of their configured
rate.

**Related tickets**: GAP-0053 (transparency also missing from billing), GAP-0052 (min CPM
floor also missing from serving engine), GAP-0049 (platform revenue share not written to
its own ledger).

## 2. Current-State Investigation (root cause)

### Hardcoded constant in _split_revenue

`app/services/ad_billing.py`, lines 18–19:

```python
# Revenue share: platform takes this percentage, creator gets remainder
PLATFORM_REVENUE_SHARE_PCT = 30
```

This constant is used in `_split_revenue` (line 152):

```python
platform_share = max(0, (charge_cents * PLATFORM_REVENUE_SHARE_PCT) // 100)
creator_share = charge_cents - platform_share
```

And it is also embedded in the credit ledger entry metadata (line 165):

```python
meta={**meta, "platform_share_pct": PLATFORM_REVENUE_SHARE_PCT},
```

The value 30 is used in exactly three places: the split computation, the metadata field,
and in `app/services/admin_ad_platform.py` for admin reporting (lines 300, 320, 355).

### The per-creator BPS system exists but is disconnected

`app/services/content_ad_controls.py`, lines 78–82:

```python
def get_creator_revenue_share_bps(creator_sub: str) -> int:
    """Return the creator's revenue share in basis points (default 7000)."""
    resp = T.billing.get_item(Key={"pk": f"USER#{creator_sub}", "sk": "AD_SETTINGS"})
    item = resp.get("Item") or {}
    return _to_int(item.get("revenue_share_bps"), DEFAULT_REVENUE_SHARE_BPS)
```

`DEFAULT_REVENUE_SHARE_BPS = 7000` (line 41), i.e., 70% creator share = 30% platform share.
The BPS default is consistent with the hardcoded constant, but the function is never called
from `ad_billing.py`.

The admin path to set this: `set_creator_revenue_share_bps` (lines 85–98 of
`content_ad_controls.py`) is fully implemented. An admin can set a creator's rate to any
value from 0–10000 bps. But those writes have no downstream effect because the billing
engine never reads them.

### Revenue share BPS referenced only in creator-facing endpoint

The only call site of `get_creator_revenue_share_bps` is in
`app/routers/content_ad_controls.py` line 113, which returns the value to the creator UI
for display. This confirms that the BPS system exists as a display-only artifact — the
billing engine ignores it entirely.

### Impact of the disconnect

If a creator negotiated a 90% revenue share (`revenue_share_bps=9000`), they would receive
70% instead. If a lower-tier creator was set to 60% (`revenue_share_bps=6000`), they would
receive 70% — actually overpaid relative to contract. The constant 70% means some creators
are underpaid and others are overpaid depending on their negotiated BPS.

## 3. Impact / Exploit / Blast Radius

**Financial**: Every creator with a non-default negotiated rate is billed incorrectly.
For a creator with `revenue_share_bps=9000` (90% share) who earns $10,000/month in ad
revenue, the platform overfills its own ledger by $2,000/month relative to contract. For a
creator with `revenue_share_bps=5000` (50% split), the platform underpays by $2,000/month
— a direct breach of contract.

**Scale**: Any creator given a custom rate through the admin path is affected. Given that
`set_creator_revenue_share_bps` is wired into the admin API, it is reasonable to assume
that premium-tier creators have been given non-default rates.

**Audit risk**: The `platform_share_pct` embedded in each credit ledger entry always reads
`30`, meaning finance audits of those ledger records will show an incorrect platform share
for any non-default-rate creator. Correcting historical ledger entries after the fact is
non-trivial.

**Exploit angle**: A malicious advertiser creating a campaign on a high-payout creator's
content cannot directly exploit this, but a creator who was promised 90% and discovers they
received 70% has a valid breach-of-contract claim. The platform bears full financial liability.

## 4. Fix Design (code-level)

### Strategy

Replace the hardcoded `PLATFORM_REVENUE_SHARE_PCT` calculation in `_split_revenue` with a
per-creator BPS lookup. The lookup adds one DynamoDB `get_item` per charge event. For
production scale, a short in-memory cache (LRU by creator_id) would be appropriate, but
that is a follow-on optimization. The correctness fix is the priority.

### BPS to platform-percentage conversion

```
creator_share_pct = revenue_share_bps / 100   (in percent)
platform_share_pct = 100 - creator_share_pct
```

In integer arithmetic (to avoid floating-point rounding in financial calculations):

```python
creator_share = (charge_cents * creator_bps) // 10000
platform_share = charge_cents - creator_share
```

This is equivalent to the current formula but parameterized by `creator_bps` instead of
the hardcoded constant.

### Revised _split_revenue

```python
def _split_revenue(
    *, charge_cents: int, creator_id: str, account_id: str, meta: dict, ts: int
) -> None:
    """Split ad revenue between platform and creator using the creator's negotiated BPS."""
    from datetime import datetime, timezone

    # Resolve per-creator revenue share (ADS-010 / GAP-0054)
    creator_bps = PLATFORM_DEFAULT_CREATOR_BPS  # fallback
    if creator_id:
        try:
            from app.services.content_ad_controls import get_creator_revenue_share_bps
            creator_bps = get_creator_revenue_share_bps(creator_id)
        except Exception:
            logger.warning("revenue_share_bps_lookup_failed creator=%s", creator_id)

    creator_share = (charge_cents * creator_bps) // 10000
    platform_share = charge_cents - creator_share

    if creator_share > 0 and creator_id:
        try:
            _sk, credit_item = new_ledger_entry(
                key_name="pk",
                key_value=user_pk(creator_id),
                entry_type="ad_revenue_credit",
                amount_cents=creator_share,
                state="settled",
                reason="Ad revenue share",
                meta={**meta, "platform_share_pct": platform_share * 100 // charge_cents
                              if charge_cents > 0 else PLATFORM_REVENUE_SHARE_PCT,
                      "revenue_share_bps": creator_bps},
            )
            T.billing.put_item(Item=credit_item)
        except Exception:
            logger.warning("ad_revenue_creator_credit_failed",
                           extra={"creator_id": creator_id})
```

Add the new module-level constant alongside the existing one to avoid breaking the admin
reporting code that imports `PLATFORM_REVENUE_SHARE_PCT`:

```python
# Keep for backward compatibility with admin reporting module
PLATFORM_REVENUE_SHARE_PCT = 30  # legacy default (percent)
# Creator revenue share default in basis points (7000 bps = 70%)
PLATFORM_DEFAULT_CREATOR_BPS = 7000
```

### Admin reporting (admin_ad_platform.py)

`app/services/admin_ad_platform.py` imports `PLATFORM_REVENUE_SHARE_PCT` (line 29) and
uses it for rollup calculations (lines 300, 320, 355). Those calculations are for
aggregate reporting and should ideally also use per-creator rates, but since the rollup
sums across all creators, an approximate platform default is acceptable as-is. No change
to `admin_ad_platform.py` is required for this fix; the GAP-0049 ticket covers the
platform revenue ledger separately.

### serve_ad: upgrade to get_full_ad_settings (combined with GAP-0052)

If GAP-0052 is being fixed simultaneously (recommended), change `serve_ad` to call
`get_full_ad_settings` instead of `get_creator_ad_settings`. The `revenue_share_bps`
returned could then be cached in the serving context and passed down through
`track_ad_event` → `charge_impression` → `_process_charge` → `_split_revenue`,
eliminating the DynamoDB lookup in the hot billing path. This is an optimization for a
follow-on PR, not required for correctness.

### Dev / Prod parity (SECOPS-007)

The fix adds one DynamoDB `get_item` call via `T.billing` (already routed through
`app/core/tables.py`). In dev this is DynamoDB Local; in prod it is real DynamoDB. No new
AWS service dependency is introduced. The call is wrapped in a `try/except` that falls back
to the platform default BPS, so the function never raises in either environment.
SECOPS-007 is satisfied.

### Backward compatibility

Existing ledger entries have `platform_share_pct: 30` in their metadata. These are
historical records and should not be retroactively altered. Going forward, new entries will
carry the correct per-creator `revenue_share_bps` in the metadata, making auditing
straightforward. A migration guide for existing creators' ledger records can be produced
as a data analysis task if contractual obligations require it.

**Before fix**: `test_per_creator_revenue_share[9000-10000-9]` fails because the hardcoded
30% constant produces `7` cents for creator instead of `9`.

**After fix**: All parametrized cases pass.

   `{"revenue_share_bps": 9000}` (admin endpoint).
2. Simulate an impression charge (or trigger via `POST /ui/ads/track?event=impression`).
3. Query the creator's billing ledger: `GET /ui/billing/history`.
4. Confirm the `ad_revenue_credit` entry has `amount_cents = bid_cpm_cents / 1000 * 90 / 100`.
5. Also check that `revenue_share_bps: 9000` appears in the ledger entry's `meta` field.

### Observability

Log the resolved BPS at INFO level in `_split_revenue` (sampling 1% of events):
```python
logger.debug("revenue_split creator=%s bps=%d creator_share=%d platform_share=%d",
             creator_id, creator_bps, creator_share, platform_share)
```

Add a Prometheus counter `ad_revenue_split_total{bps_bucket}` to track the distribution
of BPS values across charges, enabling detection of misconfigured rates.

### Rollout

- **Effort**: M (2 days of code + 2 days of tests + financial audit)
- **Risk**: MEDIUM — this changes the amount written to creator credit ledger entries.
  Before deploying, audit all creators with non-default `revenue_share_bps` values and
  confirm that the new calculations match the contractual obligations.
- **Sequencing**: Coordinate with GAP-0053 (transparency fix adds `account_id` to
  `_split_revenue` signature; both changes touch the same function). Fix both in one PR
  to minimize merge conflicts.
- **Rollback**: Revert `_split_revenue`; no DynamoDB schema changes needed. The existing

- **Financial reconciliation**: After deploy, export all `ad_revenue_credit` entries for
