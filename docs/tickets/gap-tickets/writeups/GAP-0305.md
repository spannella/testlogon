# GAP-0305: Frontend entirely absent (MOD-003 User Appeals) — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Severity**: HIGH · **Source ticket**: MOD-003 · **Status**: Open · **Effort**: L  
**Owning area**: Frontend — React pages, API client, routing, navigation

The MOD-003 User Appeals System backend is fully implemented: `app/routers/appeals.py`, `app/routers/admin_appeals.py`, `app/services/appeals.py`, and all required DynamoDB tables (`Appeals`, GSIs in `scripts/local-ddb-init.py:631–641`) are wired and registered in `app/main.py`. However, zero frontend code exists for the appeals system. A search across all of `frontend/src/` finds no file referencing "appeal" or "Appeal". The gaps are:

- `frontend/src/api/endpoints/appeals.ts` — API client functions: absent.
- `frontend/src/pages/appeals/AppealFormPage.tsx` — user appeal submission form: absent.
- `frontend/src/pages/appeals/MyAppealsPage.tsx` — user's appeal history list: absent.
- `frontend/src/pages/admin/AppealReviewQueuePage.tsx` — admin moderation queue: absent.
- Routes in `frontend/src/App.tsx` (`/appeals`, `/appeals/new`, `/admin/appeals`): absent.
- Sidebar nav links in `frontend/src/components/layout/Sidebar.tsx`: absent.
- Alert rendering for `moderation_ban`/`moderation_warning` events in `frontend/src/pages/alerts/AlertsPage.tsx` does not render an "Appeal this decision" link because `enforcement_id` is not present in the alert details (a separate but related gap).

**Claim verification**: Confirmed accurate. The gap ticket's claim that "the backend is fully wired but users have no browser surface to submit or track appeals" is correct. The backend routers exist and compile (`app/routers/appeals.py`, `app/routers/admin_appeals.py`); `app/main.py` imports and registers them. The `appeals_enforcement.py` file cited in MOD-003 section 4 is NOT present as a separate file — `reverse_enforcement` and `modify_enforcement` are inlined in `app/services/appeals.py` as `_reverse_enforcement` and `_modify_enforcement`. This structural deviation from the ticket is a separate (MED) gap but does not affect the HIGH frontend gap.

**Related tickets**: MOD-003 (design spec), GAP-0304 (DMCA rate limit), GAP-0303 (content_url SSRF).

## 2. Current-State Investigation (root cause)

### 2.1 What the backend provides

**User-facing endpoints** (registered at prefix `/v1/appeals`):
- `POST /v1/appeals` — file an appeal (`AppealCreateIn` → `AppealCreateOut`)
- `GET /v1/appeals` — list authenticated user's appeals (`AppealListOut`)
- `GET /v1/appeals/{appeal_id}` — get one appeal (`AppealOut`)
- `POST /v1/appeals/{appeal_id}/withdraw` — withdraw pending appeal (`AppealWithdrawOut`)

**Admin-facing endpoints** (registered at prefix `/v1/admin/appeals`):
- `GET /v1/admin/appeals` — paginated queue with status filter
- `GET /v1/admin/appeals/stats` — queue statistics (`AppealQueueStatsOut`)
- `GET /v1/admin/appeals/{appeal_id}` — full context (`AppealDetailOut`)
- `POST /v1/admin/appeals/{appeal_id}/claim` — claim for review
- `POST /v1/admin/appeals/{appeal_id}/decide` — record decision (`upheld`/`modified`/`reversed`)

All of these are live and return correct JSON. Running `curl http://localhost:8000/v1/appeals` (with a valid session) returns a 200 with `{"items":[],"next_cursor":null}`. Running `curl http://localhost:8000/v1/admin/appeals/stats` returns the queue stats. The API is fully functional.

### 2.2 What the frontend is missing

**`frontend/src/api/endpoints/appeals.ts`**: No file exists. The MOD-003 design (section 4.6) specified this file with 12 exported functions (`submitAppeal`, `listMyAppeals`, `getAppeal`, `withdrawAppeal`, `listAppealQueue`, `getAppealDetail`, `claimAppeal`, `decideAppeal`, `getAppealQueueStats`). Without this file, React Query hooks and page components cannot call the appeals API.

**`frontend/src/pages/appeals/AppealFormPage.tsx`**: Absent. Users who receive a `moderation_ban` or `moderation_warning` alert have no UI to submit an appeal. The `enforcement_id` in the alert details (if present) is intended to deep-link to `/appeals/new?enforcement_id=enf_xxx`. The form itself does not exist.

**`frontend/src/pages/appeals/MyAppealsPage.tsx`**: Absent. Users cannot see the status of appeals they have filed, cannot withdraw a pending appeal, and cannot see admin decisions or decision notes.

**`frontend/src/pages/admin/AppealReviewQueuePage.tsx`**: Absent. Admins have no browser interface to view the queue, claim appeals, see the enforcement context (original ticket, content snapshot, user history), or record decisions. Admins must use the raw API directly (curl or Swagger UI at `/docs`).

**`frontend/src/App.tsx` routes**: No routes for `/appeals`, `/appeals/new`, or `/admin/appeals` exist. Even if the page components were created, they would return 404 from the React Router.

**`frontend/src/components/layout/Sidebar.tsx`**: No "My Appeals" link in the user section and no "Appeal Queue" link in the admin section with badge count.

### 2.3 Why the gap occurred

The appeals backend was implemented in a focused backend-only sprint. The frontend was scoped as a follow-on task ("section 4.6–4.8 frontend files"). The sprint ended without the frontend tasks being picked up. The result is a backend feature that is entirely inaccessible to real users. Admins must use the API directly, which is not sustainable for a moderation workflow.

### 2.4 Related gap: `enforcement_id` absent from alert details

Even after the frontend pages exist, the "Appeal this decision" deep-link in enforcement alerts will not work unless `enforcement_id` is included in the alert `details` dict. Currently `app/services/moderation_policy_engine.py` lines 20–33 (`issue_warning_notification`) and lines 59–110 (`apply_ban`) do not pass `enforcement_id` into the `details` dict. This is a separate gap (also in the MOD-003 gap list as a HIGH item) but must be resolved alongside the frontend work to make the end-to-end flow functional.

## 3. Impact / Exploit / Blast Radius

This is an **availability / user rights gap**, not a security vulnerability in the traditional sense, though it has meaningful compliance and legal implications.

**User impact**: Users who receive warnings or bans have no way to appeal except through the general helpdesk chat, which has no structured workflow, no link to the original enforcement context, and no SLA. The appeals system was built specifically to provide due process — its absence means the due-process guarantee is a backend fiction, not a real user-facing capability.

**Admin impact**: Moderation admins must use the raw REST API or Swagger UI to manage the appeal queue. The admin queue provides full context (enforcement record, original moderation ticket, content snapshot, user history) that is not accessible without the frontend detail view. Practical consequence: appeals accumulate without review.

**Compliance / legal impact**: Platform terms of service and in several jurisdictions consumer protection law require a mechanism for users to contest account actions. The backend exists; users simply cannot reach it. In a legal discovery context, demonstrating that the appeals system is "fully implemented" but has no frontend would be embarrassing and potentially damaging.

**No data-integrity risk**: All backend data structures are correct. No data is corrupted or lost. The gap is purely presentational.

## 4. Fix Design (code-level)

The MOD-003 design document (section 4.6–4.8) provides a complete specification. The following summarises the implementation plan with precise file targets.

### 4.1 `frontend/src/api/endpoints/appeals.ts` (new, ~80 lines)

Export typed functions wrapping the axios client for all 9 API operations. Interfaces: `Appeal`, `AppealDetail`, `AppealDecisionResult`, `AppealQueueStats`. Key patterns:

```typescript
import client from "../client";

export async function submitAppeal(data: {
  enforcement_id: string;
  appeal_text: string;
}): Promise<{ ok: boolean; appeal_id: string; status: string; created_at: number }> {
  const resp = await client.post("/v1/appeals", data);
  return resp.data;
}

export async function listMyAppeals(params?: {
  status?: string; limit?: number; cursor?: string;
}): Promise<{ items: Appeal[]; next_cursor?: string }> {
  const { data } = await client.get("/v1/appeals", { params });
  return data;
}
// ... withdrawAppeal, getAppeal, listAppealQueue, getAppealDetail,
// claimAppeal, decideAppeal, getAppealQueueStats
```

The `client` instance at `frontend/src/api/client.ts` already attaches CSRF headers and handles 401 → logout, so no additional auth wiring is needed.

### 4.2 `frontend/src/pages/appeals/AppealFormPage.tsx` (new, ~180 lines)

A user-facing form page. Key design points:

- Reads `enforcement_id` from the query string (`useSearchParams`).
- On mount, fetches enforcement details from the admin endpoint or from a new lightweight `/v1/enforcements/{id}` endpoint (or simply shows the ID and lets the user describe the appeal without pre-fetching enforcement details to avoid an extra endpoint).
- Uses React Hook Form + Zod with `appeal_text` field (min 5 chars, max 5000 chars).
- On submit: calls `submitAppeal()` via `useMutation`, shows success toast with appeal ID, redirects to `/appeals`.
- Error handling: 409 "appeal already exists" → banner; 429 "pending appeal exists" → banner with Retry-After guidance.

```tsx
// Simplified structure
export default function AppealFormPage() {
  const [searchParams] = useSearchParams();
  const enforcementId = searchParams.get("enforcement_id") ?? "";
  const navigate = useNavigate();
  const { register, handleSubmit, formState } = useForm<{ appeal_text: string }>({
    resolver: zodResolver(z.object({ appeal_text: z.string().min(5).max(5000) }))
  });
  const { mutate, isPending } = useMutation({
    mutationFn: (data: { appeal_text: string }) =>
      submitAppeal({ enforcement_id: enforcementId, appeal_text: data.appeal_text }),
    onSuccess: () => { toast.success("Appeal submitted"); navigate("/appeals"); },
    onError: (err: AxiosError) => { /* show error banner */ },
  });
  // render form...
}
```

### 4.3 `frontend/src/pages/appeals/MyAppealsPage.tsx` (new, ~150 lines)

A list page showing the user's own appeals. Key design points:

- `useQuery({ queryKey: ["my-appeals"], queryFn: listMyAppeals })`.
- Status badge: `submitted` (yellow), `under_review` (blue), `upheld` (red), `reversed` (green), `modified` (orange), `withdrawn` (grey).
- Withdraw button for `submitted`/`under_review` appeals → calls `withdrawAppeal()` with confirm dialog.
- Decision note visible for resolved appeals.
- Empty state with "No appeals yet" message.

### 4.4 `frontend/src/pages/admin/AppealReviewQueuePage.tsx` (new, ~350 lines)

An admin-only queue page. Key design points:

- Stats header: `useQuery(["appeal-queue-stats"], getAppealQueueStats)` — shows `total_submitted`, `total_under_review`, `oldest_submitted_age_minutes`.
- Paginated list: `useInfiniteQuery` on `listAppealQueue` with `status` filter tabs.
- Detail panel (right side or modal): `useQuery(["appeal-detail", id], () => getAppealDetail(id))` — shows `enforcement_record`, `moderation_ticket` title, content snapshot, user enforcement history, user appeal history.
- Claim button: `useMutation(claimAppeal)`.
- Decision panel: `AppealDecisionIn` form with `decision` radio (`upheld` / `modified` / `reversed`), `decision_note` textarea, and conditional `modified_enforcement_type`/`modified_duration_days` fields.
- Uses `require_admin_scope(AdminScope.CONTENT_MODERATION)` on the backend; frontend gate via `user.role >= ADMIN` check from auth store.

### 4.5 `frontend/src/App.tsx` — add routes (lines near 423–424)

### 4.6 `frontend/src/components/layout/Sidebar.tsx` — nav links

In the user section (after the "Alerts" link), add:
```typescript

```

In the admin section, add with badge:

### 4.7 `frontend/src/pages/alerts/AlertsPage.tsx` — enforcement alert deep-link

For alerts where `event === "moderation_ban"` or `event === "moderation_warning"` and `alert.details.enforcement_id` is present, render an "Appeal this decision" button:

```tsx
{(alert.event === "moderation_ban" || alert.event === "moderation_warning") &&
  alert.details?.enforcement_id && (
    <Button variant="outline" size="sm" asChild>
      <Link to={`/appeals/new?enforcement_id=${alert.details.enforcement_id}`}>
        Appeal this decision
      </Link>
    </Button>
)}
```

Note: `enforcement_id` will only be present after the backend fix in `app/services/moderation_policy_engine.py` (a companion fix, not in scope for this gap but needed for the deep-link to work end-to-end).

### 4.8 Dev/Prod parity (SECOPS-007)

All frontend pages call the same `/v1/appeals` and `/v1/admin/appeals` backend endpoints in dev and production. No mock-only code paths are introduced in the frontend. The `client.ts` axios instance already handles auth (cookie CSRF in browser, Bearer in API tests) identically in both environments. The admin pages are gated by the existing role check in the auth store; no new feature flags are required.

### 5.5 Rollback

All changes are additive (new files, new routes, new nav links). Rolling back means deleting the four new files and removing the route and nav entries from `App.tsx` and `Sidebar.tsx`. No database migration required. The backend endpoints remain but are simply unreachable from the browser.

### 5.6 Effort and sequencing

**Effort**: L (Large) — estimated 2–3 days for a single engineer: 1 day for `appeals.ts` + page components, 0.5 days for routing/nav/alert rendering, 1 day for `AppealReviewQueuePage.tsx` (the most complex component), 0.5 days for E2E tests.

**Sequencing**:
1. `frontend/src/api/endpoints/appeals.ts` — prerequisite for all page components.
2. `AppealFormPage.tsx` and `MyAppealsPage.tsx` — user-facing; lower complexity.
3. `App.tsx` routes and `Sidebar.tsx` nav — enables navigation.
4. `AppealReviewQueuePage.tsx` — admin-facing; highest complexity; requires the claim/decide flow.
5. `AlertsPage.tsx` deep-link — requires the companion backend fix in `moderation_policy_engine.py` that adds `enforcement_id` to alert details.

The first three steps can ship as a user-visible MVP before the admin queue is complete, allowing users to file and track appeals while admins use the raw API temporarily.
