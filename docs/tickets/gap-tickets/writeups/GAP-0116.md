# GAP-0116: SEC-010 IDOR — Chat SSE Stream Missing `check_viewer_access` — Remediation Write-up

> ~5 pages. Fix-oriented. Real code verified against the codebase; cite `file:line`.

## 1. Summary & Classification

**Gap**: The broadcast live-chat SSE stream endpoint (`GET /broadcast/sessions/{session_id}/chat/stream`) does not call `check_viewer_access` before opening the stream. Any authenticated user — including those who should be blocked from a `private` broadcast — can subscribe to the real-time chat event feed by navigating directly to the stream URL.

**Severity**: HIGH
**Source ticket**: BCAST-005
**Status**: Open
**Owning area**: `app/routers/broadcast.py` → `broadcast_chat_stream_route`
**Related tickets**: GAP-0117 (chat send endpoint also missing the guard), GAP-0118 (locked message text in stream), BCAST-011 (Go-Private feature that introduced `check_viewer_access`)

**Verdict**: Claim confirmed. The route handler at `app/routers/broadcast.py:1763` discards the session context with `_ = ctx` after the `get_session()` call and never invokes `check_viewer_access`.

**One-line impact**: A user excluded from a private broadcast can silently read every chat message — including broadcaster locked-message teasers — via the SSE channel.


## 2. Current-State Investigation (root cause)

### Route handler (as-is)

`app/routers/broadcast.py:1763–1822`:

```python
@router.get("/sessions/{session_id}/chat/stream")
async def broadcast_chat_stream_route(
    session_id: str,
    after: Optional[str] = Query(default=None),
    poll_ms: int = Query(default=500, ge=200, le=3000),
    ctx: dict = Depends(_ctx),
):
    """SSE stream for real-time broadcast chat messages."""
    _ = ctx                                         # <-- ctx thrown away
    session = get_session(session_id)
    if session.status not in ("live", "ready"):
        raise HTTPException(...)
    ...
    async def gen():
        ...
        out = _chat_msg_out(msg)                    # <-- no viewer_user_id
        ...
    return StreamingResponse(gen(), media_type="text/event-stream")
```

Two problems are visible in this block:

1. **`check_viewer_access` is never called.** The `ctx` dict is silently discarded (`_ = ctx`). No code path leads to `broadcast_privacy.check_viewer_access`.

2. **`_chat_msg_out` is called without `viewer_user_id`** (see `app/routers/broadcast.py:1806`). This is the independent GAP-0118 issue but it compounds here: even if the guard were added, locked-message text would still be fully exposed.

### Contrast with guarded routes

`mint_playback_url_route` (line 492) and `viewer_join_route` (line 568) both call:

```python
from app.services.broadcast_privacy import check_viewer_access
check_viewer_access(
    session_id,
    ctx["user_sub"],
    creator_id=session.created_by,
    visibility=session.broadcast_privacy_visibility,
    invite_token=invite_token,
)
```

The chat stream is the only session-scoped endpoint that omits this check.

### `check_viewer_access` semantics

`app/services/broadcast_privacy.py:224–254`:

```python
def check_viewer_access(session_id, viewer_id, *, creator_id, visibility, invite_token=None):
    visibility = (visibility or "public").strip().lower()
    if visibility != "private":
        return                      # public/unlisted: no-op
    if viewer_id == creator_id:
        return
    if is_allowlisted(session_id, viewer_id):
        return
    if invite_token and redeem_invite_token(session_id, invite_token, viewer_id):
        return
    raise HTTPException(403, ...)
```

For `public` and `unlisted` sessions the function is a no-op, so adding the call has **zero performance or behavioural impact** on the common case. It only matters when `visibility == "private"`.

### Why `invite_token` is needed on the stream

The chat stream is opened by the viewer's browser at the same time as (or just after) the playback URL is minted. By that point the viewer has already been enrolled in the allowlist via `redeem_invite_token`. Subsequent calls to `check_viewer_access` will hit the `is_allowlisted` branch and succeed. Passing `invite_token=None` is therefore safe for re-entering viewers; the query parameter should be accepted optionally for new sessions so the allowlist is populated consistently.

### Connection between GAP-0116 and GAP-0118

GAP-0116 (the privacy guard) and GAP-0118 (the viewer-aware `_chat_msg_out` call) are in the same function and must be fixed together. Fixing GAP-0116 alone (adding the privacy gate) is necessary but insufficient: once inside the stream, a legitimate but non-paying viewer would still receive locked-message teaser text because `_chat_msg_out(msg)` omits `viewer_user_id`. The two changes are therefore a logical pair. GAP-0118's write-up covers the `_chat_msg_out` argument in depth; the fix design section below includes the fix as Change 2 for completeness.

### `fetch_chat_messages_after` — no viewer filtering

`_store_fetch_after` (`app/services/broadcast_chat_store.py:288–305`) is the polling function used by the SSE generator. It returns raw DynamoDB items without any viewer-level filtering. That is correct — filtering must happen at the output serialisation layer (`_chat_msg_out`), not at the storage layer. This confirms that passing `viewer_user_id` to `_chat_msg_out` is the right boundary for the fix.


## 3. Impact / Exploit / Blast Radius

### Exploit walkthrough

1. Broadcaster Alice sets `visibility=private` on session `sess_abc` and grants access only to viewer Carol.
2. Excluded viewer Bob obtains the `session_id` (e.g., from a leaked URL, browser history, or by guessing the UUID format used by the application — UUIDs are not secret by design).
3. Bob opens `GET /broadcast/sessions/sess_abc/chat/stream?poll_ms=500` with a valid auth cookie from any account (even a freshly registered free account).
4. The `get_session(session_id)` call at line 1772 succeeds — the session record is not access-controlled.
5. The `session.status not in ("live", "ready")` check passes — the session is live. No further gating occurs.
6. Bob's browser receives a live SSE stream of every `chat:message` event, including:
   - Plain text messages from all viewers and the broadcaster.
   - Locked-message *teasers* (the `lock_description` field — the broadcaster's marketing copy for paywalled content).
   - Tip notifications (`chat:tip` events with amounts and sender identities).
   - Reaction counts and reply thread structure (`reactions_counts`, `reply_to_preview`).
7. Bob can also reconstruct the viewer engagement picture (who is active, what they are reacting to) and monitor the broadcaster's locked-message unlock rate indirectly by watching for `unlock` events in the companion history endpoint.

### Worst case

If the broadcaster uses the `private` visibility to run an adult content or subscription-gated session, excluded users can read all chat messages without paying the access fee. This directly undermines the monetization premise of BCAST-011 and exposes participant identities to uninvited viewers, creating potential regulatory and GDPR/CCPA exposure.

### Additional IDOR surface

The `session_id` is the only required parameter. There is no proof-of-connection requirement (e.g., having previously called `viewer_join_route`). An attacker who enumerates or guesses session IDs can monitor any private broadcast chat in real time. The stream stays open until the server or client drops it; a single long-lived connection continuously receives all messages with no further authentication after the initial HTTP upgrade.

### Blast radius

- All sessions where `broadcast_privacy_visibility == "private"`.
- `public` and `unlisted` sessions are unaffected (the guard is a no-op for them).
- Estimated scope: any broadcaster who has adopted Go-Private mode since BCAST-011 shipped.
- Compounded by GAP-0117: an excluded viewer can both read (via stream) and write (via send) to a private broadcast, effectively giving them full bidirectional chat access with no payment or allowlist requirement.


## 4. Fix Design (code-level)

### Change 1 — Add `check_viewer_access` to `broadcast_chat_stream_route`

**File**: `app/routers/broadcast.py`, function `broadcast_chat_stream_route` (line ~1763).

Replace:

```python
async def broadcast_chat_stream_route(
    session_id: str,
    after: Optional[str] = Query(default=None),
    poll_ms: int = Query(default=500, ge=200, le=3000),
    ctx: dict = Depends(_ctx),
):
    """SSE stream for real-time broadcast chat messages."""
    _ = ctx
    session = get_session(session_id)
    if session.status not in ("live", "ready"):
        raise HTTPException(...)
```

With:

```python
async def broadcast_chat_stream_route(
    session_id: str,
    after: Optional[str] = Query(default=None),
    poll_ms: int = Query(default=500, ge=200, le=3000),
    invite_token: Optional[str] = Query(default=None),
    ctx: dict = Depends(_ctx),
):
    """SSE stream for real-time broadcast chat messages."""
    session = get_session(session_id)
    if session.status not in ("live", "ready"):
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail={"code": "BROADCAST_NOT_LIVE", "message": "Chat stream is only available for live broadcasts"},
        )
    # Go-Private access gating (BCAST-011 / GAP-0116)
    from app.services.broadcast_privacy import check_viewer_access
    check_viewer_access(
        session_id,
        ctx["user_sub"],
        creator_id=session.created_by,
        visibility=session.broadcast_privacy_visibility,
        invite_token=invite_token,
    )
```

Note that the `status` check is moved **before** the access check so that clients receive the correct `BROADCAST_NOT_LIVE` error (not a privacy denial) when the session is not live. The `invite_token` query parameter mirrors the existing signature of `mint_playback_url_route` and `viewer_join_route` for consistency.

### Change 2 — Pass `viewer_user_id` to `_chat_msg_out` inside the generator

This is the companion fix for GAP-0118, but it must be included here to avoid a partial repair. Inside the `gen()` async generator (line ~1806):

```python
# Before
out = _chat_msg_out(msg)

# After
out = _chat_msg_out(msg, viewer_user_id=ctx["user_sub"])
```

Because `ctx` is a plain dict captured at handler construction time, it is safe to reference inside the closure. The dict is constructed once by `require_ui_session` before the generator starts; it does not change during the connection lifetime. `_chat_msg_out` with a `viewer_user_id` will:

- Redact `text=None` for locked messages the caller has not unlocked.
- Apply expiry suppression correctly (sender always sees their own expired messages).
- Compute `my_reactions` correctly (the subset of reactions authored by this viewer).

Without `viewer_user_id`, all three of these per-viewer personalisation features produce incorrect results for every message in the stream.

### Alternative considered: move access check to the SSE generator body

An alternative design would be to check access inside `gen()` on every poll iteration. This would allow the broadcaster to revoke access mid-stream (e.g., by removing a viewer from the allowlist). However, the current `viewer_join_route` and `mint_playback_url_route` both check access only at connection time, establishing a consistent pattern. Adopting a per-poll check in the chat stream would create an inconsistency and add a DynamoDB read every 500ms per connected viewer. The connection-time check is the correct approach; mid-stream revocation can be handled via a separate "kick viewer" SSE event type if needed in a future ticket.

### Dev/Prod parity (SECOPS-007)

`check_viewer_access` is a pure DynamoDB read against `T.broadcast_allowlist`. The table is wired from `app/core/tables.py` and is present in both the dev DynamoDB-local stack and the production DynamoDB table. No feature flag or mock bypass exists in the function. The fix is therefore **environment-neutral**: the same code path runs in dev and production.

The `invite_token` query parameter is optional and defaults to `None`, so existing clients that do not pass the token continue to work. Viewers who were previously auto-enrolled in the allowlist via `redeem_invite_token` (during `viewer_join_route`) will pass the `is_allowlisted` branch without needing to re-submit the token.

### Backward compatibility

- No database migrations required.
- No model changes required.
- Public and unlisted sessions: `check_viewer_access` returns immediately; zero latency impact.
- Private sessions: one `GetItem` against `broadcast_allowlist` on stream open. This is a cold-path operation (SSE connections are long-lived; the check runs once per connection).


## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

Add to `tests/test_broadcast_chat_privacy.py` (new file):

```python
import pytest
from unittest.mock import patch, MagicMock
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

ALICE = "alice_sub"
BOB   = "bob_sub"
SESSION = "sess_priv_001"

def _inject_session(sub):
    """Return session cookie headers for a user."""
    ...  # use existing injectAuth helper pattern from conftest.py

@pytest.fixture(autouse=True)
def _private_session(mock_ddb):
    """Seed a live private session owned by Alice."""
    mock_ddb["broadcast_sessions"].put_item(Item={
        "session_id": SESSION,
        "status": "live",
        "created_by": ALICE,
        "broadcast_privacy_visibility": "private",
    })

def test_stream_blocked_for_non_allowlisted_viewer():
    """GAP-0116: excluded viewer must receive 403 when opening the chat stream."""
    resp = client.get(
        f"/broadcast/sessions/{SESSION}/chat/stream",
        headers=_inject_session(BOB),
    )
    assert resp.status_code == 403
    assert resp.json()["detail"]["code"] == "BROADCAST_PRIVATE_ACCESS_DENIED"

def test_stream_allowed_for_allowlisted_viewer(mock_ddb):
    """Allowlisted viewer can open stream."""
    from app.services.broadcast_privacy import add_to_allowlist
    add_to_allowlist(SESSION, BOB, added_by=ALICE)
    resp = client.get(
        f"/broadcast/sessions/{SESSION}/chat/stream",
        headers=_inject_session(BOB),
    )
    # SSE response means at least a 200 was received
    assert resp.status_code == 200

def test_stream_allowed_for_creator():
    resp = client.get(
        f"/broadcast/sessions/{SESSION}/chat/stream",
        headers=_inject_session(ALICE),
    )
    assert resp.status_code == 200
```

**Fails before the fix** (`_ = ctx` discards the auth context; `check_viewer_access` is never called; Bob gets 200).
**Passes after the fix** (Bob receives 403; Alice and allowlisted users receive 200).

### Observability

Log line in `check_viewer_access` at `app/services/broadcast_privacy.py:248` (the `raise HTTPException` path) provides structured output: `"broadcast.privacy.deny session=… viewer=…"`. Add a metric counter `broadcast_chat_stream_access_denied_total` in `app/metrics.py` alongside the existing `record_broadcast_output_error`.

Add a structured access log line at the top of the SSE generator closure to record when a stream connection is established. This gives operators a complete picture: a `stream_opened` event followed by a disconnect (or long session) allows detection of unusual patterns (e.g., a viewer who connects to the stream but never joins as a viewer in `viewer_join_route`).

```python
logger.info(
    "broadcast.chat.stream_opened session=%s viewer=%s",
    session_id, ctx["user_sub"],
)
```

This log line is placed after `check_viewer_access` succeeds, so it fires only for authorised connections.
