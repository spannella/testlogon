# GAP-0136: Wildcard Target Dispatch Silently Skips Sends — Remediation Write-up

> ~5 pages. Fix-oriented. Code verified against real implementation; all citations checked.

## 1. Summary & Classification

- **Plain-English statement**: When the bot scheduler's background dispatch loop (`dispatch_due_scheduled_sends`) processes a scheduled send whose `target_type` is a wildcard scope (`all_dms`, `all_groups`, or `all_broadcasts`), the loop silently discards the send without delivering any messages. The schedule record is still updated (`last_run_at`, `next_run_at`) as if delivery succeeded — the caller gets back a `dispatched` count that never reflects wildcard deliveries.
- **Severity**: HIGH — wildcard scheduled sends are a documented, creatable feature (creators can call `POST /ui/bots/{bot_id}/scheduled-sends` with `target_type=all_dms`) but the messages are never delivered. No error is raised, no log warning is emitted, and the creator receives no feedback that their send was silently dropped.
- **Source ticket**: BOT-002 · **Status**: Open · **Owning area**: `app/services/bot_scheduler.py`
- **Verdict from investigation**: **Claim confirmed.** Lines 276-282 of `bot_scheduler.py` contain a guard `if sched["target_type"] == "conversation" and sched.get("target_id")` that handles exactly one target type. All other target types (`all_dms`, `all_groups`, `all_broadcasts`) fall through without action. The `dispatched` counter is incremented regardless — actually, closer inspection reveals it is only incremented if the guard passes (line 294), so wildcard sends are silently skipped AND are not counted as dispatched. The problem is worse than a counter discrepancy: the schedule's `GSI1SK` (next_run_at) IS advanced even for skipped wildcard sends (lines 286-293), so the scheduler continuously picks them up, re-skips them, and advances their next_run, burning DDB capacity.
- **Related tickets**: BOT-002 (parent), GAP-0137 (sibling: startup bug), GAP-0138 (sibling: orphaned rules)

## 2. Current-State Investigation (Root Cause)

### 2.1 The dispatch loop

`dispatch_due_scheduled_sends()` at `app/services/bot_scheduler.py:236` is the background function that:

1. Queries `GSI1PK="BOTSCHED#PENDING"` with `GSI1SK <= now_ts` to find due schedules.
2. For each item, loads the bot and template.
3. Calls `render_template()`.
4. **Conditionally** sends the message — the relevant block is at lines 275-282:

```python
# app/services/bot_scheduler.py:275-282
# Send bot message (for single conversation target)
if sched["target_type"] == "conversation" and sched.get("target_id"):
    send_bot_message(
        bot_id=sched["bot_id"],
        conversation_id=sched["target_id"],
        text=rendered["rendered_text"],
    )
    record_impression(bot_id=sched["bot_id"], template_id=sched["template_id"])
```

5. Regardless of whether step 4 fired, advances `next_run_at` and updates `GSI1SK` (lines 285-293).
6. Increments `dispatched`.

The `dispatched` counter at line 294 is inside the outer `try` block but outside the inner `if` check, so it increments for every item processed, whether or not any message was actually sent.

### 2.2 How wildcard target types are created

`create_scheduled_send()` (`bot_scheduler.py:61`) accepts `target_type` as a free string parameter. The function validates bot ownership, template existence, and cron syntax but does not restrict `target_type` to `"conversation"`. A call with `target_type="all_dms"` and `target_id=None` passes all validation, writes to DDB with `GSI1PK="BOTSCHED#PENDING"`, and is thereafter eligible for dispatch.

`create_bot_assignment()` in `chat_bot.py:187` similarly accepts `target_type` values of `all_dms`, `all_groups`, `all_broadcasts`, and the SK builder at `chat_bot.py:383` correctly stores them as `SCOPE#ALL_DMS`, etc. The assignment infrastructure is ready; the scheduler dispatch is not.

### 2.3 What `_resolve_target_conversations` should do (stub is absent)

The BOT-002 write-up at section 4.2 states that `_resolve_target_conversations()` should be implemented. No such function exists anywhere in the codebase. The resolution logic would need to:

- For `target_type="conversation"` with `target_id`: return `[target_id]`.
- For `target_type="all_dms"`: query `T.bot_assignments` for assignments of this bot with `SK=SCOPE#ALL_DMS`, then resolve conversation IDs assigned to the bot's creator. A practical implementation queries the conversations table for all active DMs involving the creator, capped at 500.
- For `target_type="all_groups"`: same, but for group conversations.
- For `target_type="all_broadcasts"`: query `T.bot_assignments` for `SCOPE#ALL_BROADCASTS` and resolve broadcast session IDs.

### 2.4 The double-advance bug

Even for wildcard skips, lines 285-293 execute:

```python
# app/services/bot_scheduler.py:285-293
next_run = _next_run_from_cron(sched["cron_expression"], sched.get("timezone", "UTC"))
T.bot_scheduled_sends.update_item(
    Key={"pk": item["pk"], "sk": item["sk"]},
    UpdateExpression="SET last_run_at = :lra, next_run_at = :nra, GSI1SK = :nra",
    ExpressionAttributeValues={
        ":lra": current_ts,
        ":nra": next_run,
    },
)
dispatched += 1
```

This means a wildcard scheduled send: (a) silently delivers zero messages, (b) advances its `next_run_at` by +3600 seconds (the stub cron offset), and (c) inflates the `dispatched` counter. In production with many wildcard schedules, this creates a busy-loop pattern that burns DDB write capacity and produces misleading dispatch metrics.

### 2.5 Dev vs. prod parity today

The bug is identical in dev and prod. Both environments use the same `bot_scheduler.py` code path. `S.bot_scheduled_messages_enabled` gates the entire loop; when enabled, the silent-skip behavior is active in both environments.

## 3. Impact / Exploit / Blast Radius

### 3.1 Functional impact

Every creator who creates a wildcard scheduled send gets zero message deliveries. There is no error, no notification, and no observable indication of failure. From the creator's dashboard perspective the schedule appears healthy (it has a valid `next_run_at`, `last_run_at` is updated, `enabled=true`). This is a silent data-correctness failure: the platform promises delivery and silently drops it.

### 3.2 Worst-case scenario

A creator creates a scheduled promotional broadcast (`target_type=all_dms`, `cron="0 9 * * *"`) expecting daily morning messages to all their subscribers. The scheduler runs hourly, picks up the record, skips delivery, advances `next_run_at`, logs nothing, and increments `dispatched`. The creator sees their schedule is "running" (last_run_at is updated) but receives zero subscriber engagement — because zero messages were sent. The creator has no mechanism to diagnose this.

### 3.3 DynamoDB cost amplification

With `_next_run_from_cron()` returning `now + 3600` (stub implementation), each wildcard schedule triggers:
- 1 DDB GSI1 query (to find due sends)
- 1 DDB `get_item` per bot
- 1 DDB `get_item` per template
- 1 DDB `update_item` to advance `next_run_at`

For N wildcard schedules across all bots, this is 4N DDB operations per hour, all producing zero business value. A platform with 1,000 active wildcard schedules would generate 4,000 wasted DDB operations per hour.

### 3.4 Metrics corruption

`dispatch_due_scheduled_sends()` returns `{"dispatched": N, "failed": 0}` for N wildcard skips. Any dashboard tracking "successful dispatches per hour" will show inflated numbers, masking the real delivery rate.

## 4. Fix Design (Code-Level)

### 4.1 Add `_resolve_target_conversations()`

Add a new function to `app/services/bot_scheduler.py` that resolves a schedule item's target into a list of conversation IDs:

```python
# app/services/bot_scheduler.py — add after line 363 (_schedule_dict)
_WILDCARD_SCOPE_LIMIT = 500

def _resolve_target_conversations(sched: dict) -> list[str]:
    """Resolve a scheduled send's target into a list of conversation IDs.

    For wildcard scopes (all_dms, all_groups, all_broadcasts), query the
    bot_assignments table for the bot's creator conversations.
    Returns at most _WILDCARD_SCOPE_LIMIT conversation IDs.
    """
    from app.services.chat_bot import get_bot
    from boto3.dynamodb.conditions import Key as _Key

    target_type = sched["target_type"]
    target_id = sched.get("target_id")

    if target_type == "conversation" and target_id:
        return [target_id]

    # Wildcard: resolve via conversations table scoped to the bot's creator
    bot = get_bot(bot_id=sched["bot_id"])
    if not bot:
        return []

    creator_id = bot.get("creator_id", "")

    if target_type == "all_dms":
        kind_filter = "dm"
    elif target_type == "all_groups":
        kind_filter = "group"
    elif target_type == "all_broadcasts":
        kind_filter = "broadcast"
    else:
        logger.warning(
            "bot_scheduler: unknown target_type=%s schedule_id=%s",
            target_type, sched.get("schedule_id"),
        )
        return []

    # Query conversations where creator is a participant
    # Uses the conversations GSI keyed on creator participant
    try:
        resp = T.conversations.query(
            IndexName="GSI1",
            KeyConditionExpression=_Key("GSI1PK").eq(f"USER#{creator_id}"),
            FilterExpression="kind = :k",
            ExpressionAttributeValues={":k": kind_filter},
            Limit=_WILDCARD_SCOPE_LIMIT,
        )
        items = resp.get("Items", [])
        return [item["conversation_id"] for item in items if item.get("conversation_id")]
    except Exception:
        logger.exception(
            "bot_scheduler: failed to resolve wildcard target_type=%s bot_id=%s",
            target_type, sched["bot_id"],
        )
        return []
```

### 4.2 Replace the silent-skip guard in `dispatch_due_scheduled_sends()`

Replace lines 275-282 of `app/services/bot_scheduler.py`:

**Before** (lines 275-282):
```python
# Send bot message (for single conversation target)
if sched["target_type"] == "conversation" and sched.get("target_id"):
    send_bot_message(
        bot_id=sched["bot_id"],
        conversation_id=sched["target_id"],
        text=rendered["rendered_text"],
    )
    record_impression(bot_id=sched["bot_id"], template_id=sched["template_id"])
```

**After**:
```python
# Resolve target conversation IDs (handles both single and wildcard targets)
target_conv_ids = _resolve_target_conversations(sched)
if not target_conv_ids:
    logger.warning(
        "bot_scheduler: no target conversations resolved for schedule_id=%s "
        "target_type=%s — skipping send",
        sched.get("schedule_id"), sched["target_type"],
    )
else:
    for conv_id in target_conv_ids[:_WILDCARD_SCOPE_LIMIT]:
        send_bot_message(
            bot_id=sched["bot_id"],
            conversation_id=conv_id,
            text=rendered["rendered_text"],
        )
    record_impression(bot_id=sched["bot_id"], template_id=sched["template_id"])
    logger.info(
        "bot_scheduler: dispatched schedule_id=%s target_type=%s conv_count=%d",
        sched.get("schedule_id"), sched["target_type"], len(target_conv_ids),
    )
```

The `[:_WILDCARD_SCOPE_LIMIT]` slice (500) is the fan-out cap specified in the BOT-002 design. This prevents unbounded send storms for creators with thousands of subscribers.

### 4.3 Fix the `dispatched` counter inflation

Currently `dispatched += 1` runs even for skipped wildcards. After the fix the counter should reflect actual delivery attempts. Add a `sent_count` local variable and only increment `dispatched` if at least one conversation was targeted:

```python
# replace dispatched += 1 at line 294
sent_count = len(target_conv_ids) if target_conv_ids else 0
dispatched += 1 if sent_count > 0 else 0
```

### 4.4 DDB table dependency

`_resolve_target_conversations()` queries `T.conversations`. This table handle must exist in `app/core/tables.py`. Verify with:

```bash
grep "conversations" app/core/tables.py
```

If it exists (likely, given the messaging feature), no new table or schema change is needed. If the GSI1 key scheme for conversations does not match `GSI1PK=USER#{user_id}`, adjust the query to use the correct index name and key expression for that table.

### 4.5 Dev/Prod parity (SECOPS-007)

No AWS-specific paths are introduced by this fix. `_resolve_target_conversations()` uses `T.conversations.query()`, which routes to DynamoDB Local in dev (via `DDB_ENDPOINT_URL`) and to AWS DynamoDB in prod via the same `T.*` table handle abstraction. No feature flags are needed for this fix — it is a correctness fix to existing functionality that should be enabled in all environments. The `BOT_SCHEDULED_MESSAGES_ENABLED` flag already gates the entire scheduler loop; when disabled the fix code is never reached.

### 4.6 Backward compatibility

The change is purely additive at the DDB level (no schema changes). Existing `target_type=conversation` schedules continue to work identically — `_resolve_target_conversations()` returns `[target_id]` for them, and the loop iterates once. Wildcard schedules that were previously silently skipped will now deliver messages — this is the intended behavior, and there is no migration concern.

### 5.4 Rollout and rollback

- **Rollout**: Deploy the fix as a backend-only change. No DDB migration, no schema change, no frontend change.
- **Rollback**: Revert `bot_scheduler.py`. Wildcard schedules revert to silent skipping.
- **Risk**: The fix changes silent-skip to active delivery. If a creator had inadvertently created wildcard schedules expecting no delivery (unlikely), messages will now be delivered. Recommend: audit DDB `bot_scheduled_sends` for wildcard records before deploying, notify affected creators.
- **Effort**: S (2–4 hours for implementation + tests).
