# GAP-0123: Billing Atomicity Gap in `_write_private_billing()` — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase. No prior investigation doc exists.

## 1. Summary & Classification

**Claim verdict: Confirmed.** `_write_private_billing()` in `app/services/broadcast_private.py` (line 300–357) executes the viewer debit and creator credit as two independent `put_item` calls, each wrapped in its own `try/except` that swallows all exceptions. A failure on the credit write after a successful debit leaves the viewer charged and the creator unpaid, with no error surfaced to the caller.

- **Severity**: HIGH
- **Source ticket**: BCAST-011
- **Status**: Open
- **Owning area**: Broadcast Private Session Billing (`app/services/broadcast_private.py`)
- **Impact (financial)**: Partial write failures cause money to be debited from the viewer's wallet with no corresponding credit to the creator. In the reverse scenario (debit fails, credit succeeds) the creator is paid without the viewer being charged. Both are financial integrity violations.
- **Related tickets**: BCAST-011 (private session billing), SECOPS-007 (dev/prod parity), GAP-0124 (related private session lifecycle gap)
- **Dependencies**: DynamoDB `TransactWriteItems` API is available in both DynamoDB Local (dev) and AWS DynamoDB (production).

## 2. Current-State Investigation (root cause)

`_write_private_billing` is called from `end_private_session` in `broadcast_private.py:185–192`. It receives the viewer ID, creator ID, amount, and payment method ID, and is responsible for writing two DynamoDB records atomically: a debit entry in the viewer's billing ledger and a credit entry in the creator's billing ledger.

The current implementation (lines 300–357):

```python
def _write_private_billing(
    viewer_id, creator_id, amount_cents, private_session_id, session_id, payment_method_id
) -> tuple[str, str]:
    ts = now_ts()
    debit_id = uuid.uuid4().hex
    credit_id = uuid.uuid4().hex
    reason = "Private session"
    meta = { ... }

    try:
        T.billing.put_item(Item={
            "pk": f"USER#{viewer_id}",
            "sk": f"LEDGER#{ts}#{debit_id}",
            ...
            "type": "debit",
            ...
        })
    except Exception:
        logger.warning("private_billing_debit_failed viewer=%s amount=%d", viewer_id, amount_cents)

    try:
        T.billing.put_item(Item={
            "pk": f"USER#{creator_id}",
            "sk": f"LEDGER#{ts}#{credit_id}",
            ...
            "type": "credit",
            ...
        })
    except Exception:
        logger.warning("private_billing_credit_failed creator=%s amount=%d", creator_id, amount_cents)

    return debit_id, credit_id
```

Both failure modes are silently absorbed:

1. **Debit succeeds, credit fails**: The viewer's ledger shows a debit. The creator's ledger has no corresponding credit. The function returns `(debit_id, credit_id)` as if both succeeded. The caller writes `billing_debit_entry_id` and `billing_credit_entry_id` to the private session record, giving the appearance of a complete billing transaction. The discrepancy is invisible until a manual reconciliation query or a financial audit.

2. **Debit fails, credit succeeds**: The creator is credited without the viewer being charged. This is a revenue loss for the platform.

3. **Both fail**: The session is marked `"ended"` with billing IDs that reference non-existent ledger entries. The private session record is inconsistent.

The caller `end_private_session` (lines 154–228) does not inspect the return value of `_write_private_billing` for validity. After the billing write, it unconditionally proceeds to update the private session status to `"ended"` (line 194–210). There is no rollback of the session state if billing fails.

**Dev vs. production behavior**: DynamoDB Local fully supports `TransactWriteItems` with the same semantics as production AWS DynamoDB. The fix does not introduce any dev/production divergence.

## 3. Impact / Exploit / Blast Radius

### Financial integrity violations

The billing ledger is the source of truth for all wallet balances and creator payouts. A debit without a credit means:
- The viewer is charged (their wallet balance decreases or their payment method is billed).
- The creator never receives the funds.
- The platform's internal reconciliation (sum of debits vs. sum of credits) goes out of balance.

### Exploit scenario (adversarial)

An attacker who can trigger a transient DynamoDB error mid-session (e.g., through throttling induced by high write traffic on the billing table) could cause the credit write to fail after the debit succeeds. This would result in "free" private sessions from the creator's perspective: the creator's wallet never fills, but the viewer's wallet is charged. Over many sessions this could constitute systematic financial fraud.

A more realistic non-adversarial scenario: during a DynamoDB partition rebalance or a brief capacity issue, the second `put_item` is rejected with `ProvisionedThroughputExceededException`. The first write succeeded. The `try/except` silently drops the error; no retry is attempted.

### Blast radius

Every `end_private_session` call (one per private broadcast session) is potentially affected. Private sessions can be monetarily significant — rates of $1–$100+ per minute for 5–60 minute sessions are configurable. A single missed credit could be worth hundreds of dollars.

The function is also called from the billing heartbeat for live per-minute billing within an ongoing session. If that heartbeat path also calls `_write_private_billing` (or a similar wrapper), the exposure multiplies.

## 4. Fix Design (code-level)

### 4.1 Replace dual `put_item` with `TransactWriteItems`

DynamoDB `TransactWriteItems` is ACID: either both items are written or neither is. A failure raises `TransactionCanceledException`, which must be caught and re-raised as an HTTP 500 to the caller. The caller must be updated to handle this exception and set the private session status to an error state rather than `"ended"`.

The fix requires switching from the DynamoDB resource API (`T.billing.put_item`) to the low-level DynamoDB client API, because `TransactWriteItems` is only available on the client, not on Table resources.

```python
import boto3
from app.core.settings import S
from botocore.exceptions import ClientError

def _write_private_billing(
    viewer_id: str,
    creator_id: str,
    amount_cents: int,
    private_session_id: str,
    session_id: str,
    payment_method_id: str,
) -> tuple[str, str]:
    """Write paired debit/credit billing ledger entries atomically.

    Uses DynamoDB TransactWriteItems so that either both entries are
    committed or neither is. Raises RuntimeError on failure so the
    caller can mark the session as billing_failed instead of ended.
    """
    ts = now_ts()
    debit_id = uuid.uuid4().hex
    credit_id = uuid.uuid4().hex
    reason = "Private session"
    meta = {
        "content_type": "private_call",
        "private_session_id": private_session_id,
        "session_id": session_id,
        "viewer_id": viewer_id,
        "creator_id": creator_id,
        "payment_method_id": payment_method_id,
    }

    billing_table_name = S.billing_table_name  # e.g. "billing"

    ddb_client = boto3.client(
        "dynamodb",
        region_name=S.aws_region or "us-east-1",
        endpoint_url=S.ddb_endpoint_url or None,  # dev: "http://localhost:8001"
    )

    debit_item = {
        "pk": {"S": f"USER#{viewer_id}"},
        "sk": {"S": f"LEDGER#{ts}#{debit_id}"},
        "entry_id": {"S": debit_id},
        "ts": {"N": str(ts)},
        "type": {"S": "debit"},
        "amount_cents": {"N": str(amount_cents)},
        "currency": {"S": "USD"},
        "state": {"S": "settled"},
        "reason": {"S": reason},
    }

    credit_item = {
        "pk": {"S": f"USER#{creator_id}"},
        "sk": {"S": f"LEDGER#{ts}#{credit_id}"},
        "entry_id": {"S": credit_id},
        "ts": {"N": str(ts)},
        "type": {"S": "credit"},
        "amount_cents": {"N": str(amount_cents)},
        "currency": {"S": "USD"},
        "state": {"S": "settled"},
        "reason": {"S": reason},
    }

    try:
        ddb_client.transact_write_items(
            TransactItems=[
                {"Put": {"TableName": billing_table_name, "Item": debit_item}},
                {"Put": {"TableName": billing_table_name, "Item": credit_item}},
            ]
        )
    except ClientError as exc:
        error_code = exc.response["Error"]["Code"]
        logger.error(
            "private_billing_transact_failed viewer=%s creator=%s amount=%d error=%s",
            viewer_id, creator_id, amount_cents, error_code,
        )
        raise RuntimeError(
            f"Billing transaction failed ({error_code}): viewer={viewer_id} amount={amount_cents}"
        ) from exc

    logger.info(
        "private_billing_settled viewer=%s creator=%s amount=%d debit=%s credit=%s",
        viewer_id, creator_id, amount_cents, debit_id, credit_id,
    )
    return debit_id, credit_id
```

### 4.2 Update `end_private_session` to handle billing failure

The caller must propagate `RuntimeError` from `_write_private_billing` rather than silently succeeding:

```python
# app/services/broadcast_private.py:184-210 — end_private_session
try:
    debit_id, credit_id = _write_private_billing(
        viewer_id=item["viewer_id"],
        creator_id=_get_session_creator(session_id),
        amount_cents=total_billed_cents,
        private_session_id=private_session_id,
        session_id=session_id,
        payment_method_id=item.get("payment_method_id", ""),
    )
except RuntimeError as exc:
    # Mark session as billing_failed rather than ended
    T.broadcast_private_sessions.update_item(
        Key={"pk": f"BCAST#{session_id}", "sk": f"PRIVATE#{private_session_id}"},
        UpdateExpression="SET #st = :status, billing_error = :err",
        ExpressionAttributeNames={"#st": "status"},
        ExpressionAttributeValues={
            ":status": "billing_failed",
            ":err": str(exc)[:500],
        },
    )
    raise HTTPException(status_code=500, detail="Billing transaction failed; session marked billing_failed.")
```

This approach ensures the session never reaches `"ended"` status without confirmed billing, giving operators a queryable `"billing_failed"` state to alert on and investigate.

### 4.3 SECOPS-007 dev/prod parity

The `ddb_endpoint_url` setting (`S.ddb_endpoint_url`) maps to `http://localhost:8001` in dev and is empty in production (which causes boto3 to use the real AWS DynamoDB endpoint). This is the same pattern used throughout the codebase for all DynamoDB client instantiation. DynamoDB Local supports `TransactWriteItems` with identical semantics to production.

### 4.4 Alternatives considered

- **Application-level two-phase commit**: Complex, fragile, not needed when the database supports atomic transactions natively.
- **Idempotency key + retry loop**: Could address transient failures but does not provide atomicity — the debit could still succeed and the credit fail between retries.
- **Single ledger entry**: Combining debit and credit into one item would destroy the per-user ledger model required for wallet balance queries.

## 5. Testing, Verification & Rollout

### Regression test (fails before fix, passes after)

Add to `tests/test_broadcast_private_billing.py`:

```python
import pytest
from unittest.mock import patch, MagicMock
from botocore.exceptions import ClientError
from app.services.broadcast_private import _write_private_billing

def make_client_error(code: str):
    return ClientError(
        {"Error": {"Code": code, "Message": "mocked"}},
        "TransactWriteItems",
    )

def test_billing_atomicity_both_items_written(ddb_mock_billing_table):
    """Both debit and credit must appear in the billing table after a successful call.

    FAILS BEFORE FIX: items may be written separately; no atomicity guarantee.
    PASSES AFTER FIX: TransactWriteItems ensures both items exist together.
    """
    debit_id, credit_id = _write_private_billing(
        viewer_id="user_v",
        creator_id="user_c",
        amount_cents=500,
        private_session_id="priv_001",
        session_id="sess_001",
        payment_method_id="pm_test",
    )
    table = ddb_mock_billing_table
    debit_items = table.query(
        KeyConditionExpression="pk = :pk",
        ExpressionAttributeValues={":pk": {"S": "USER#user_v"}},
    )["Items"]
    credit_items = table.query(
        KeyConditionExpression="pk = :pk",
        ExpressionAttributeValues={":pk": {"S": "USER#user_c"}},
    )["Items"]
    assert len(debit_items) == 1
    assert len(credit_items) == 1
    assert debit_items[0]["type"]["S"] == "debit"
    assert credit_items[0]["type"]["S"] == "credit"


def test_billing_raises_on_transaction_canceled():
    """A TransactionCanceledException must propagate as RuntimeError.

    FAILS BEFORE FIX: exception is silently swallowed by try/except.
    PASSES AFTER FIX: RuntimeError is raised and caller receives 500.
    """
    with patch("boto3.client") as mock_boto:
        mock_client = MagicMock()
        mock_boto.return_value = mock_client
        mock_client.transact_write_items.side_effect = make_client_error(
            "TransactionCanceledException"
        )
        with pytest.raises(RuntimeError, match="Billing transaction failed"):
            _write_private_billing(
                viewer_id="user_v",
                creator_id="user_c",
                amount_cents=500,
                private_session_id="priv_002",
                session_id="sess_002",
                payment_method_id="pm_test",
            )


def test_billing_no_partial_write_on_failure():
    """After a transaction failure, neither debit nor credit item must exist.

    FAILS BEFORE FIX: debit may exist even though credit failed.
    PASSES AFTER FIX: transaction failure means zero items written.
    """
    # This test is verified by the atomic nature of TransactWriteItems.
    # Use moto to confirm: raise exception during transact_write_items,
    # then query both partitions and assert no items.
    import boto3
    from moto import mock_aws

    with mock_aws():
        client = boto3.client("dynamodb", region_name="us-east-1")
        client.create_table(
            TableName="billing",
            KeySchema=[
                {"AttributeName": "pk", "KeyType": "HASH"},
                {"AttributeName": "sk", "KeyType": "RANGE"},
            ],
            AttributeDefinitions=[
                {"AttributeName": "pk", "AttributeType": "S"},
                {"AttributeName": "sk", "AttributeType": "S"},
            ],
            BillingMode="PAY_PER_REQUEST",
        )
        with patch("boto3.client", return_value=client), \
             patch.object(client, "transact_write_items",
                          side_effect=make_client_error("TransactionCanceledException")):
            with pytest.raises(RuntimeError):
                _write_private_billing("v", "c", 100, "p", "s", "pm")
        items_v = client.query(
            TableName="billing",
            KeyConditionExpression="pk = :pk",
            ExpressionAttributeValues={":pk": {"S": "USER#v"}},
        )["Items"]
        items_c = client.query(
            TableName="billing",
            KeyConditionExpression="pk = :pk",
            ExpressionAttributeValues={":pk": {"S": "USER#c"}},
        )["Items"]
        assert items_v == []
        assert items_c == []
```

### Manual QA steps

1. Run `just restart` to reset state.
2. Start a broadcast session as Alice; have Bob request a private session.
3. Alice accepts the request; Bob's WebRTC connects (simulate via API if needed).
4. End the private session via `POST /sessions/{id}/private/{rid}/end`.
5. Check the billing table in DynamoDB Local: both `USER#alice` (credit) and `USER#bob` (debit) ledger entries must be present.
6. Verify the private session record has `status="ended"`, `billing_debit_entry_id`, and `billing_credit_entry_id` set.

### Observability

- Structured log at INFO: `private_billing_settled viewer=X creator=Y amount=Z debit=A credit=B`.
- Structured log at ERROR (with full context) on `TransactionCanceledException`.
- Alert: query DynamoDB for `broadcast_private_sessions` items with `status="billing_failed"` — any nonzero count requires immediate investigation.
- Add a metric: `broadcast/billing/transaction_failures` (counter).

### Rollout

- **Effort**: S (self-contained change to one function + its caller).
- **Feature flag**: No new flag; this is a correctness fix that should be deployed unconditionally.
- **Migration**: Existing sessions with `status="ended"` but potentially missing credit entries should be audited: cross-join the `private_sessions` table with the billing table on `billing_debit_entry_id` and look for sessions where the debit exists but the credit does not.
- **Risk**: Low for the happy path. The one new failure mode — `RuntimeError` propagating to the caller — is the correct behavior and now produces a 500 rather than silent data corruption.
- **Sequencing**: This fix is independent of GAP-0121/GAP-0122 and can be merged in any order.
