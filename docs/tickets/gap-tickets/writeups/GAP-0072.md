# GAP-0072: BROADCAST_ADS_BILLING_ENABLED Feature Flag Missing — Remediation Write-up

## 1. Summary & Classification

**Claim status: Confirmed.**

`app/core/settings.py` defines dozens of feature flags for every major subsystem — including `broadcast_preroll_enabled`, `broadcast_midroll_enabled`, `broadcast_tipping_enabled`, and others — but contains no `broadcast_ads_billing_enabled` field whatsoever. A search of the entire codebase returns zero matches for this identifier. As a result, when the billing integration fix from GAP-0071 is implemented, there is no environment-variable-controlled switch to enable or disable it independently of code deployments.

- **Severity**: HIGH (deployment risk: all-or-nothing release of revenue-affecting code)
- **Source ticket**: ADS-020
- **Owning area**: Platform Config / Ads / Monetization
- **Status**: Open
- **Impact**: The billing integration described in GAP-0071 cannot be safely deployed without this flag. A dark launch (deploy code; enable only in prod; roll back by flipping one env var) is impossible.
- **Related tickets**: GAP-0071 (the fix that requires this flag), GAP-0048 (daily spend reset not automated), SECOPS-007 (dev/prod parity).


## 2. Current-State Investigation (root cause)

### Settings file survey

`app/core/settings.py` (2419 lines) contains the `Settings` dataclass. Lines 534–537 define the two existing broadcast-ads flags:

```python
# Broadcast Ad Breaks (ADS-006)
broadcast_preroll_enabled: bool = os.environ.get("BROADCAST_PREROLL_ENABLED", "1") not in ("0", "false", "False")
broadcast_midroll_enabled: bool = os.environ.get("BROADCAST_MIDROLL_ENABLED", "1") not in ("0", "false", "False")
broadcast_ad_events_table_name: str = os.environ.get("DDB_BROADCAST_AD_EVENTS", "BroadcastAdEvents")
```

There is no corresponding `broadcast_ads_billing_enabled` field. This was never added when ADS-020 was stubbed — the assumption was that billing would always be off until explicitly wired, but there is no infrastructure to turn it on without a code change.

### Why this is HIGH severity

ADS-020's billing integration calls `charge_impression` (debit advertiser balance) and `_split_revenue` (credit creator balance). Both are irreversible DynamoDB writes. Deploying the fix from GAP-0071 without a kill switch means that if a bug causes double-charges or incorrect CPM calculation in production, the only remediation is rolling back the entire deployment — which takes minutes to hours and leaves the system in a partially charged state.

The existing pattern in this codebase — `broadcast_tipping_enabled`, `broadcast_preroll_enabled`, `billing_dunning_enabled`, `payment_incidents_rollout_enabled` — is precisely to guard new money-moving code behind a boolean flag with a safe default of `False` in production until explicitly enabled.

### Dev vs. prod

In dev, `.env.local` sets `DEV_MODE=1` but has no mechanism to selectively disable billing unless a flag exists. Currently billing calls simply do not happen because `record_ad_event` never calls them. After GAP-0071 is fixed, billing becomes active globally unless a flag is added.


## 3. Impact / Exploit / Blast Radius

### Deployment risk

Without this flag, the GAP-0071 billing fix goes live atomically with its deployment. Any bug in `charge_impression` — wrong CPM divisor, wrong account ID mapping, off-by-one in `bid_cpm_cents // 1000` — causes incorrect advertiser debits from the moment of deployment. There is no runtime rollback path. The only recourse is a full deployment rollback, which on typical CI/CD pipelines takes 5–15 minutes during which incorrect charges continue.

### Staged rollout is impossible

Industry best practice for revenue-critical features is to enable them for a small percentage of traffic first (canary), observe error rates and balance changes, then ramp up. Without a flag this is structurally impossible: every request hitting the billing path after deployment incurs charges. The pattern already established in this codebase for analogous situations — `payment_incidents_rollout_enabled` (line 350), `payment_incidents_rollout_providers` (line 351) — uses explicit env-var-driven rollout controls. The broadcast ads billing path deserves the same treatment.

### Double-charge risk during incident response

When a billing bug surfaces in production, the standard response is to disable the affected code path immediately while preserving all other functionality. Without `broadcast_ads_billing_enabled`, the only way to stop erroneous `charge_impression` calls is to redeploy with the billing code removed or commented out — an operation that is slow, risky, and cannot be done from the AWS console or a simple `kubectl set env` command.

If the billing code path has an exception that is swallowed (the current best-effort try/except in `record_ad_event` would catch it), charges may have been partially written. A flag provides a single-lever response: set `BROADCAST_ADS_BILLING_ENABLED=0`, roll the service, investigate at leisure.

### Creator credit volatility

`_split_revenue` writes to the main `T.billing` table (the same table used by subscription payments, tips, unlocks, and all other billing operations). An advertising bug that floods this table with incorrect `ad_revenue_credit` rows cannot be halted without either a code rollback or a direct DynamoDB intervention. Creator wallet balances could be inflated, triggering early withdrawal requests against funds that should not exist. The billing table is the financial system of record; writes to it must always be controllable.

### Compliance and audit

SECOPS-007 requires that AWS-backed paths be selectable at runtime via settings rather than hardcoded into the deployed binary. This is not merely a deployment convenience — it is a security and operational control that allows incident responders to act without access to source code or build infrastructure. A missing feature flag for a money-moving path is a SECOPS-007 violation regardless of whether the billing code is correct.

### Blast radius quantification

Assuming a modest broadcast platform with 10,000 concurrent viewers during a peak event, each generating one pre-roll impression every 30 minutes: that is approximately 333 impression charges per minute. A CPM of $5 (500 cents) means each impression charges 0.5 cents. At 333 impressions/minute, a billing bug that double-charges would over-debit advertisers by $1.67/minute — $100/hour — silently, with no operator-visible signal until advertiser account balances go negative and campaigns are auto-paused. The flag eliminates this entire risk class.


## 4. Fix Design (code-level)

### settings.py change

Insert immediately after line 537 (after `broadcast_ad_events_table_name`):

```python
# Broadcast ad billing (ADS-020) — guards charge_impression + fraud integration.
# Default False: must be explicitly enabled in production after smoke testing.
broadcast_ads_billing_enabled: bool = os.environ.get(
    "BROADCAST_ADS_BILLING_ENABLED", "0"
) not in ("0", "false", "False")
```

The default of `"0"` matches the pattern used by `billing_dunning_enabled` and `payment_incidents_shadow_mode` — other money-moving flags that default off.

### .env.local.example change

Add to the "Broadcast Ad Breaks" section:

```bash
# ADS-020: enable advertiser billing + creator revenue splits for broadcast ad events.
# Set to 1 only after confirming smoke tests pass in staging.
BROADCAST_ADS_BILLING_ENABLED=0
```

### Usage in service layer (GAP-0071 integration)

In `app/services/broadcast_ads.py`, the billing calls are gated:

```python
from app.core.settings import S

if S.broadcast_ads_billing_enabled and not fraud_flagged and event_type == "impression":
    charge_impression(...)
```

The fraud-check path (always active, no flag required) is independent, consistent with the principle that safety checks should not be gated behind the same switch as revenue logic.

### Dev/Prod parity (SECOPS-007)

The flag is read from an environment variable via `os.environ.get`, identical to every other settings field. In dev (`.env.local`), it defaults to `0`. In production (ECS task definition or Secrets Manager injected env), it is set to `1` explicitly. No mock-only code path is introduced: the same `charge_impression` function runs in both environments, hitting DynamoDB Local (dev) or real DynamoDB (prod) based on `DDB_ENDPOINT_URL`. This satisfies the SECOPS-007 requirement that dev and prod share the same code path, with environment configuration as the only difference.

### Alternatives considered

- **Hardcode to False until ready**: The current implicit state. Rejected because it is invisible — the billing path becomes unconditionally enabled after GAP-0071 is merged with no runtime control.
- **Database-level feature flag**: Use a DDB config item rather than env var. Rejected for this flag because: (a) the `Settings` singleton is frozen at startup — adding a database-polled flag would require a different mechanism; (b) other flags of equal or greater consequence (`payment_incidents_rollout_enabled`, `billing_dunning_enabled`) all use env vars; consistency is more important than hot-reload here.
- **Separate `broadcast_ads_fraud_enabled` flag**: Splitting billing and fraud into two flags. Rejected because fraud checks have no financial side effects and should always run. A single billing flag is sufficient; fraud runs unconditionally.


## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

```python
import importlib
import os


def test_broadcast_ads_billing_enabled_defaults_false():
    """Flag must default to False to protect production deployments."""
    # Ensure env var is absent
    os.environ.pop("BROADCAST_ADS_BILLING_ENABLED", None)
    # Reload settings to pick up environment state
    import app.core.settings as settings_mod
    # Access via fresh import
    from app.core.settings import S
    assert S.broadcast_ads_billing_enabled is False, (
        "broadcast_ads_billing_enabled must default to False "
        "(safe default for money-moving code)"
    )


def test_broadcast_ads_billing_enabled_reads_env_var(monkeypatch):
    """Flag must be True when env var is '1'."""
    monkeypatch.setenv("BROADCAST_ADS_BILLING_ENABLED", "1")
    # Re-create Settings to pick up the new env var
    from app.core.settings import Settings
    s = Settings()
    assert s.broadcast_ads_billing_enabled is True


def test_broadcast_ads_billing_enabled_false_values(monkeypatch):
    """Flag must be False for '0', 'false', 'False'."""
    for v in ("0", "false", "False"):
        monkeypatch.setenv("BROADCAST_ADS_BILLING_ENABLED", v)
        from app.core.settings import Settings
        s = Settings()
        assert s.broadcast_ads_billing_enabled is False, f"Expected False for value '{v}'"
```

The first test fails before the fix (because `broadcast_ads_billing_enabled` does not exist on `Settings`) and passes after. The second and third tests validate the env-var parsing logic matches existing flag conventions.

### Integration test with GAP-0071 fix

Add to `tests/test_broadcast_ads.py` (depends on GAP-0071 fix being applied):

```python
def test_billing_disabled_by_default_no_charge_calls(monkeypatch):
    """With flag at default (False), no charge_impression call must be made
    even when all required billing parameters are present."""
    # Do NOT set BROADCAST_ADS_BILLING_ENABLED — verify it defaults off
    os.environ.pop("BROADCAST_ADS_BILLING_ENABLED", None)
    from app.core.settings import Settings
    s = Settings()
    assert s.broadcast_ads_billing_enabled is False

    # Now verify the service path honours the flag
    charge_mock = MagicMock()
    with patch("app.services.ad_billing.charge_impression", charge_mock), \
         patch.object(broadcast_ads.T, "broadcast_ad_events") as ddb_mock, \
         patch("app.services.ad_fraud_prevention.check_fraud",
               return_value=MagicMock(flagged=False, score=0, rule_scores={})):
        ddb_mock.put_item = MagicMock()
        broadcast_ads.record_ad_event(
            session_id="s1", creative_id="cr1", user_id="u1",
            event_type="impression", account_id="acct1",
            campaign_id="camp1", bid_cpm_cents=5000,
        )
    charge_mock.assert_not_called()
```

This test verifies end-to-end that the flag read from settings correctly gates the billing call. It fails before GAP-0072 is fixed (because `S.broadcast_ads_billing_enabled` raises `AttributeError`) and passes after.

### Manual QA steps

1. Start the dev stack with default `.env.local` (no `BROADCAST_ADS_BILLING_ENABLED` set).
2. Confirm `GET /internal/config` (or Python shell `from app.core.settings import S; S.broadcast_ads_billing_enabled`) returns `False`.
3. Set `BROADCAST_ADS_BILLING_ENABLED=1` in `.env.local`, restart backend.
4. Confirm the value is now `True`.
5. With GAP-0071 fix deployed and flag enabled: trigger a broadcast ad event via `POST .../track` and verify a charge row appears in `T.ad_billing`.
6. Set `BROADCAST_ADS_BILLING_ENABLED=0`, restart, repeat step 5 — confirm no charge row is written.
7. Confirm the frontend-facing `AdEventOut` response shape is unchanged in both flag states (billing is backend-only).

### Observability

- Log `broadcast_ads_billing_enabled` value at backend startup alongside other feature flags (the startup log already emits selected config values).
- Add a Prometheus gauge or CloudWatch metric emitted at startup: `feature_flag{name="broadcast_ads_billing_enabled"} 0|1` — makes the flag state visible in dashboards without querying env vars.

### Rollout sequencing

This ticket must be merged and deployed **before** GAP-0071. The flag defaults to `False`, so deploying GAP-0071 on top of an already-running instance that has this flag at `False` is safe: no billing calls will fire until an operator explicitly sets `BROADCAST_ADS_BILLING_ENABLED=1`.

Rollback: set `BROADCAST_ADS_BILLING_ENABLED=0` and restart — billing halts immediately without code change or deployment.

### Naming conventions and consistency

All broadcast feature flags in `settings.py` follow the pattern `broadcast_{feature}_enabled`. The flag name `broadcast_ads_billing_enabled` follows this convention. It is deliberately more specific than `broadcast_ads_enabled` (which could be mistaken for a kill switch on all ad functionality including fraud detection, analytics, and pre-roll selection). The billing flag controls exclusively the `charge_impression` → `_split_revenue` pipeline, not ad serving.

### Long-term flag lifecycle

Once the billing integration has been running in production for 90 days without incidents, the flag can optionally be promoted to a permanent-on default (`"1"` instead of `"0"`) or removed entirely. Until then, keeping it as an explicit env var provides a fast incident response lever. The decision to remove the flag should be made by the monetization team after reviewing billing error rates and advertiser balance accuracy over that window.
