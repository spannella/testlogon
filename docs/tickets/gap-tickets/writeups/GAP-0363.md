# GAP-0363: execute_split writes ledger credit entries for each member but never calls `apply_wallet_delta` — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against real code; cites `file:line` throughout.

## 1. Summary & Classification

**Bug**: `execute_split` in `app/services/syndicate_revenue_split.py` correctly writes a `LEDGER#…` credit entry to the billing DynamoDB table for each syndicate member, but it never calls `apply_wallet_delta` to increment the `wallet_balance_cents` field on each member's `WALLET` row. The ledger is a historical record; the wallet balance is what the payout and wallet-balance endpoints actually read. Members receive a ledger entry showing they earned money but their spendable wallet balance stays at $0.

**Severity**: HIGH
**Source ticket**: SYND-003 (second-pass as-built review)
**Status**: Open
**Owning area**: Backend / syndicate revenue split service
**Effort**: S
**Related tickets**: GAP-0362 (assert → RuntimeError for split invariants), GAP-0026 (revenue split hooks absent from billing flows)

**Claim verification**: CONFIRMED. The per-member write loop at `app/services/syndicate_revenue_split.py:231-261` calls `T.billing.put_item(Item={...})` to write a ledger entry but contains no call to `apply_wallet_delta`. The `billing_shared` module is not even imported in `syndicate_revenue_split.py` — confirming the wallet delta path is entirely absent.

**One-line impact**: Every bundle-subscription revenue split silently produces a correct ledger entry but no spendable balance increment; members see $0 in their wallet despite having accrued earnings.

There is no `apply_wallet_delta` call anywhere in this loop or elsewhere in the function.

### How the wallet balance works

`apply_wallet_delta` in `app/services/billing_shared.py:185-213` performs an atomic DynamoDB `update_item` that increments `wallet_balance_cents` on the `USER#{user_id} / WALLET` row:

```python
# billing_shared.py:192-202 (deposit path)
result = table.update_item(
    Key={"pk": pk, "sk": WALLET_SK},  # sk = "WALLET"
    UpdateExpression=(
        "SET wallet_balance_cents = if_not_exists(wallet_balance_cents, :z) + :d, "
        "currency = :c, updated_at = :t"
    ),
    ExpressionAttributeValues={":z": 0, ":d": delta_cents, ":c": currency, ":t": now_ts()},
    ReturnValues="ALL_NEW",
)
```

The `LEDGER#…` rows written by `execute_split` are separate items in the billing table and have no effect on the `WALLET` row. Any endpoint that reads a user's wallet balance (`GET /ui/billing/wallet`, payout checks, locked-message purchase checks) reads only the `WALLET` sk item. It will never see the ledger entries.

### Runtime manifestation

1. Admin triggers a revenue split for a syndicate with three members (Alice, Bob, Carol).
2. `execute_split` runs successfully, returns HTTP 200 with a split record showing e.g. `{"distributions": [{"user_id": "alice", "amount_cents": 283}, ...]}`
3. Alice logs into her dashboard and checks her wallet: **$0.00**.
4. Alice checks her billing history (ledger entries): shows `+$2.83 Syndicate bundle revenue share`.
5. The discrepancy is confusing but invisible until a member tries to spend their earnings (payout, locked-message purchase) — at which point they fail with "Insufficient balance."

## 3. Impact / Exploit / Blast Radius

### Financial impact

Every revenue event routed through `execute_split` silently fails to credit members' spendable balances. On a platform with active syndicate subscriptions, this means:

- 100% of syndicate revenue-share payouts are effectively frozen — members can never withdraw their earnings.
- If the platform has collected subscription revenue and issued split ledger entries, members have a contractual claim to funds that the system shows as earned but cannot be spent or withdrawn.
- The platform's `wallet_balance_cents` totals across all users underreport actual liabilities, distorting financial reporting.

### Who is affected

- Every member of every syndicate that has received a bundle-subscription payment.
- The platform's finance team / compliance reporting, since the ledger and wallet balance are inconsistent.
- Any feature that gates on wallet balance (e.g., locked message unlock, advertising spend) will incorrectly block members who have earned a balance.

### Is this exploitable?

No malicious exploit is possible. The bug is purely a data-loss omission — funds are recorded in ledger history but never become spendable. However, the consequence is effectively equivalent to the platform silently not paying members.

### Worst case

A syndicate with high revenue (e.g., 1000+ subscribers at $9.99/month) runs for months before someone notices. The total unspendable earnings could be thousands of dollars per member. Correcting this retroactively requires either a one-time compensating `apply_wallet_delta` call for each affected user (using the ledger entries as the source of truth) or a full financial audit and manual adjustment.

## 4. Fix Design (code-level)

### Add import

```python
# app/services/syndicate_revenue_split.py — top of file, after existing imports

from app.services.billing_shared import apply_wallet_delta, user_pk
```

### Add `apply_wallet_delta` call inside the per-member loop

The wallet delta must be applied AFTER the ledger entry is written successfully (so that if the ledger write fails, the wallet is not credited without a corresponding record):

```python
# app/services/syndicate_revenue_split.py:231-261 — AFTER FIX

for dist in distributions:
    dist["display_name"] = display_names.get(dist["user_id"], dist["user_id"])
    entry_id = uuid4().hex
    try:
        T.billing.put_item(Item={
            "pk": f"USER#{dist['user_id']}",
            "sk": f"LEDGER#{ts}#{entry_id}",
            "entry_id": entry_id,
            "ts": ts,
            "type": "credit",
            "amount_cents": int(dist["amount_cents"]),
            "currency": currency,
            "state": "settled",
            "reason": LEDGER_REASON,
            "meta": {
                "syndicate_id": syndicate_id,
                "split_id": split_id,
                "subscription_id": subscription_id,
                "invoice_id": invoice_id,
                "source_type": source_type,
                "split_mode": effective_mode,
                "percentage_bps": int(dist["percentage_bps"]),
            },
        })
        # Credit the member's spendable wallet balance.           <-- ADD
        apply_wallet_delta(                                        # <-- ADD
            T.billing,                                             # <-- ADD
            user_pk(dist["user_id"]),                             # <-- ADD
            int(dist["amount_cents"]),                            # <-- ADD
        )                                                         # <-- ADD
        dist["ledger_entry_id"] = entry_id
    except Exception:
        logger.warning(
            "syndicate_split_ledger_write_failed",
            extra={"user_id": dist["user_id"], "syndicate_id": syndicate_id},
        )
        dist["ledger_entry_id"] = ""
```

### Why inside the try/except?

`apply_wallet_delta` with a positive delta (deposit) uses `if_not_exists` and cannot fail with a `ConditionalCheckFailedException`. The only failure mode is a genuine DynamoDB connectivity error, which will be caught by the existing `except Exception` and logged. This is consistent with the existing error handling in the loop.

### Ordering: ledger first, wallet second

Writing the ledger entry first ensures that if the wallet delta call fails (e.g., transient DDB error), the ledger entry exists as a recovery record — an operator can rerun the wallet delta using the ledger as the source of truth. Writing the wallet delta first would leave the wallet credited without a corresponding ledger entry if the ledger write then fails.

### Dev/Prod parity (SECOPS-007)

`apply_wallet_delta` and `T.billing` are used identically in dev (DynamoDB Local port 8001) and prod (AWS DynamoDB). There are no `dev_mode` branches in `billing_shared.py`. The `user_pk` helper is a pure string formatter (`f"USER#{user_id}"`). The fix is fully parity-consistent.

### Retroactive correction

Existing split ledger entries for already-executed splits must be reconciled. A one-time migration script should:

1. Query all `LEDGER#` entries in `T.billing` with `reason == "Syndicate bundle revenue share"` per user.
2. Compare the sum of those credits against each user's `wallet_balance_cents`.
3. For the shortfall, call `apply_wallet_delta` with the difference.

This migration can be run as a separate `scripts/migrate_split_wallet_balances.py` with a dry-run mode before applying any writes.

### Backward compatibility

No API contract changes. No schema changes. The `execute_split` return shape is unchanged. The wallet balance increase is a new write-path side-effect that was always intended to happen.

Run `scripts/migrate_split_wallet_balances.py --dry-run` to estimate total underbalance across all affected users before applying. Target: sum of all `LEDGER#` credit entries with `reason == "Syndicate bundle revenue share"` minus current `wallet_balance_cents` for each affected user. Apply corrections in a maintenance window with backend writes disabled.

### Rollback

Remove the two added lines (`apply_wallet_delta` call) and the import. No schema changes; rollback is instant.

### Risk

**Low for new splits**: `apply_wallet_delta` with a positive delta is always safe (uses `if_not_exists`; cannot overdraft). **Medium for retroactive migration**: the migration script must be idempotent (checking current balance against sum of ledger credits) to avoid double-crediting if run more than once.
