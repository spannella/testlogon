# GAP-0042: allowed_ad_categories Enforcement Missing in Serving Engine — Remediation Write-up

## 1. Summary & Classification

**Plain-English statement**: Creators can configure an `allowed_ad_categories` whitelist that is supposed to restrict which ad campaigns may display on their content. The `get_creator_ad_settings` helper is correctly called in `serve_ad` to check `allow_ads`, but the `allowed_ad_categories` list that is also returned is never consulted. The campaign-filtering loop in `serve_ad` at `app/services/ad_serving.py:79–126` checks blocked advertisers, budget, dayparting, targeting, and frequency caps, but contains no step that compares the campaign's category against the creator's `allowed_ad_categories` whitelist. As a result, a creator who has set `allowed_ad_categories=["sports"]` will still receive ads from unrelated categories such as `gambling` or `alcohol`.

- **Severity**: HIGH
- **Source ticket**: ADS-003
- **Status**: Open
- **Owning area**: Ads Platform / Ad Serving Engine
- **Effort**: S
- **Claim verdict**: CLAIM OK — confirmed. `app/services/ad_serving.py:68–70` calls `get_creator_ad_settings` and checks `allow_ads`, but `creator_settings.get("allowed_ad_categories")` is never referenced in the `serve_ad` function. The category field on a campaign is stored at the time of creation (via `CampaignCreateIn`) but not yet visible in `CampaignCreateIn` in the current model (see GAP-0044 notes), though the serving engine already reads `bid_cpm_cents` from the raw DDB item, implying the `category` attribute would also be read from raw item data once written.

**One-line impact**: Creators' content category preferences are silently ignored, meaning adult-classified creators can receive children's advertising (and vice versa), violating creator contracts and potentially FTC advertising guidelines.

**Related tickets**: ADS-003 (source), GAP-0041 (settings storage race that could corrupt the whitelist), GAP-0044 (bid_cpm_cents missing from CampaignCreateIn — campaign creation also does not persist a `category` field), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (Root Cause)

### serve_ad — existing creator check

`app/services/ad_serving.py:67–70`:

```python
# 1. Check creator allows ads
creator_settings = get_creator_ad_settings(creator_id)
if not creator_settings.get("allow_ads", True):
    return _empty_response("creator_ads_disabled")
```

`creator_settings` is a dictionary with three keys: `allow_ads`, `allowed_ad_categories`, and `min_cpm_cents`. After the `allow_ads` guard, the variable is never read again in `serve_ad`. `allowed_ad_categories` and `min_cpm_cents` are fetched but discarded.

### Campaign loop — no category filter

`app/services/ad_serving.py:79–126` iterates `active_campaigns` and applies six independent filters:

1. Fraud suspension check (lines 83–88).
2. Creator block check (lines 91–92).
3. Budget check (lines 95–96).
4. Dayparting / flight check (lines 99–103).
5. Targeting check (lines 105–107).
6. Frequency cap check (lines 110–111).

There is no step 2a or 2b that reads `creator_settings["allowed_ad_categories"]` and compares it against a `category` field on the campaign item.

### Missing campaign category field

`app/models.py:4296–4303` — `CampaignCreateIn`:

```python
class CampaignCreateIn(BaseModel):
    name: str = Field(..., min_length=1, max_length=200)
    objective: str = Field(..., pattern=r"^(awareness|traffic|conversions)$")
    budget_cents: int = Field(..., ge=100)
    budget_type: str = Field(..., pattern=r"^(daily|lifetime)$")
    start_date: Optional[int] = None
    end_date: Optional[int] = None
```

`CampaignCreateIn` has no `category` field. Campaigns stored in DynamoDB will therefore have no `category` attribute unless one is added. The `allowed_ad_categories` whitelist enforcement cannot be complete until campaigns carry a `category` attribute.

Similarly, `CampaignOut` at `app/models.py:4305–4319` omits `category`.

### Creator settings model

`app/models.py:5059–5063`:

```python
class CreatorAdSettingsIn(BaseModel):
    allow_ads: Optional[bool] = None
    allowed_ad_categories: Optional[List[str]] = None
    min_cpm_cents: Optional[int] = Field(default=None, ge=0)
```

The `allowed_ad_categories` field is a list of strings — no canonical taxonomy is enforced at the model level. The `@field_validator("allowed_ad_categories")` at line 5064 (not shown above) presumably validates each entry; that validation is not the source of the gap.

`get_creator_ad_settings` returns `allowed_ad_categories` as `[]` when no item exists in DynamoDB, which is the correct "no restriction" default.

### Summary of root cause

There are two compounding gaps:

1. `CampaignCreateIn` / `create_campaign` never stores a `category` field on the campaign DynamoDB item.
2. `serve_ad` never reads `creator_settings["allowed_ad_categories"]` and never compares it against anything.

Both must be fixed together for the feature to work end-to-end.

## 3. Impact / Exploit / Blast Radius

**Creator trust / compliance**: Creators who operate under specific content agreements (e.g., "family-friendly" channels that explicitly allow only `education` and `entertainment` ads) will be served `alcohol`, `gambling`, or `adult` category ads if those campaigns are active. This is a direct breach of creator agreements.

**FTC / regulatory**: In the United States and EU, advertising on children-targeted content from categories like gambling or dietary supplements is heavily regulated. If the platform cannot demonstrate that category restrictions are enforced at the serving layer, it is liable for every non-compliant impression.

**Advertiser targeting waste**: Campaigns targeted at `sports` audiences may be displayed on technology/SaaS creator content because the platform never filters by category alignment. Click-through rates and conversion rates for advertisers suffer, directly affecting platform revenue.

**Blast radius**: Every `serve_ad` call for every creator who has configured `allowed_ad_categories` is affected. The `allowed_ad_categories` default is `[]` (empty list, meaning "no restriction"), so creators who have not set a whitelist are unaffected. However, any creator who has explicitly configured the field is silently receiving non-matching ads.

## 4. Fix Design (code-level)

### Step 1 — Add `category` to CampaignCreateIn and CampaignOut

In `app/models.py`, extend the campaign models:

```python
# Valid ad categories — extend as the taxonomy grows
AD_CATEGORIES = frozenset({
    "arts", "automotive", "beauty", "education", "entertainment",
    "fashion", "finance", "food", "gaming", "health", "home",
    "humor", "legal", "music", "news", "pets", "real_estate",
    "sports", "technology", "travel",
    # Sensitive categories (require explicit opt-in)
    "adult", "alcohol", "gambling", "political", "tobacco",
})

class CampaignCreateIn(BaseModel):
    name: str = Field(..., min_length=1, max_length=200)
    objective: str = Field(..., pattern=r"^(awareness|traffic|conversions)$")
    budget_cents: int = Field(..., ge=100)
    budget_type: str = Field(..., pattern=r"^(daily|lifetime)$")
    start_date: Optional[int] = None
    end_date: Optional[int] = None
    category: str = Field(default="general")  # NEW

    @field_validator("category")
    @classmethod
    def validate_category(cls, v: str) -> str:
        if v not in AD_CATEGORIES | {"general"}:
            raise ValueError(f"Unknown ad category: {v}")
        return v

class CampaignOut(BaseModel):
    campaign_id: str
    account_id: str
    name: str
    objective: str
    budget_cents: int
    budget_type: str
    daily_budget_cents: int = 0
    spent_today_cents: int = 0
    lifetime_spent_cents: int = 0
    status: str
    start_date: Optional[int] = None
    end_date: Optional[int] = None
    created_at: int
    updated_at: int
    category: str = "general"  # NEW
    bid_cpm_cents: int = 500   # also add — see GAP-0044
```

In `app/services/ad_campaigns.py`, add `category` to the item dict in `create_campaign`:

```python
item = {
    ...
    "category": data.category,
    ...
}
```

### Step 2 — Add min_cpm_cents check and category filter in serve_ad

In `app/services/ad_serving.py`, immediately after the existing creator block check (line 91), add:

```python
# Category whitelist check
allowed_categories = creator_settings.get("allowed_ad_categories") or []
if allowed_categories:
    campaign_category = campaign.get("category", "general")
    if campaign_category not in allowed_categories:
        continue

# Min CPM floor check (ADS-003)
creator_min_cpm = int(creator_settings.get("min_cpm_cents", 0))
if creator_min_cpm > 0:
    campaign_bid = int(campaign.get("bid_cpm_cents", 500))
    if campaign_bid < creator_min_cpm:
        continue
```

The `allowed_categories` guard is deliberately `if allowed_categories:` — an empty list means "no restriction", which is the correct default for creators who have never set a whitelist.

The `min_cpm_cents` floor check is included here because `get_creator_ad_settings` already returns it and it suffers the same omission — the value is fetched but never applied. This is a two-for-one fix in the same code path.

### Dev/Prod parity (SECOPS-007)

`serve_ad` runs in both dev (DynamoDB Local) and production (AWS DynamoDB). The fix adds pure Python logic (dict comparison, integer comparison) with no AWS-specific branching. The `get_creator_ad_settings` and `list_campaigns_by_status` calls already handle dev/prod parity internally. No mock-specific code path is introduced.

### Backward compatibility

- Existing campaigns in DynamoDB have no `category` attribute. The fix reads `campaign.get("category", "general")`, so existing items are treated as category `"general"` (the default).
- Creators who have not set `allowed_ad_categories` (the majority) have an empty list, and the `if allowed_categories:` guard skips the filter entirely, producing no behavioral change.
- A data migration script can back-fill `category = "general"` on existing campaign items during off-hours if clean querying is needed.

## 5. Testing, Verification & Rollout

### Manual QA steps

1. Start dev stack: `just up`.
2. Create a campaign with `category="gambling"` via `POST /ui/ads/accounts/{id}/campaigns`.
3. Approve the campaign via admin endpoint so status becomes `active`.
4. Set creator ad settings: `PATCH /ui/ads/creator-settings {"allowed_ad_categories": ["sports"]}`.
5. Call `GET /ui/ads/serve?surface=feed&creator_id=...&...` — verify response has `is_house_ad: true`.
6. Change creator settings to `allowed_ad_categories: ["gambling"]` and repeat — verify `filled: true` with the gambling campaign.

### Playwright E2E test (supplemental)

Add to `frontend/e2e/ads-category.spec.ts` (new spec):

```typescript
test("creator category whitelist blocks non-matching campaign", async ({ page }) => {
  await injectAuth(page, "alice");
  // Set allowed_ad_categories to ["sports"] for Alice
  await page.request.patch("/ui/ads/creator-settings", {
    headers: { "x-csrf-token": sessions["alice"].csrf_token },
    data: { allowed_ad_categories: ["sports"] },
  });
  // Request an ad serve in Alice's feed context
  const resp = await page.request.get(
    `/ui/ads/serve?surface=feed&creator_id=${ALICE_SUB}&content_id=post_001&slot_type=in_feed&user_id=${ALICE_SUB}`
  );
  const body = await resp.json();
  // If a non-sports campaign is the only active one, must return house ad
  expect(body.is_house_ad).toBe(true);
});
```

This test requires seeding a non-sports campaign in `beforeAll` and relies on the category attribute being written at campaign creation time — which itself depends on the GAP-0044 fix. The E2E spec should be added in the same release that includes both GAP-0042 and GAP-0044 fixes.

### Rollout

- Deploy model change and serving-engine change together in a single release to avoid a window where campaigns have `category` but serving doesn't filter.
- The `category` field in `CampaignCreateIn` defaults to `"general"`, so existing API clients that omit the field continue to work without modification.
- Ad operations teams should be notified before deployment so they can review existing `allowed_ad_categories` settings and confirm they match the new canonical category taxonomy.
- **Effort**: S (< 1 day).
- **Risk**: Low. Empty `allowed_ad_categories` (the default) produces identical behaviour to today. Only creators who have explicitly set the whitelist are affected, and even then the worst case is that previously-served non-matching campaigns stop being served — which is the intended behaviour.
