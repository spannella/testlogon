# GAP-0226: Auto-registration in Host Inventory Never Happens — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at `app/services/k8s_launcher.py`.

## 1. Summary & Classification

**Plain-English statement**: When a user launches a Kubernetes pod through the K8s launcher service, the pod is stored in the `k8s_pods` DynamoDB table but is never automatically registered as a host entry in the `host_inventory` table. The `host_id` field is initialized to an empty string and never updated. As a result, the user cannot use the Host Inventory's quick-connect, SSH terminal integration, or connection-profile features to reach the container they just launched.

- **Severity**: HIGH
- **Source ticket**: INFRA-004
- **Status**: Open
- **Owning area**: Remote Compute / Host Inventory (Infrastructure)
- **Verdict**: Claim **confirmed**. The code at `app/services/k8s_launcher.py:196-197` initializes `"host_id": ""` and then calls `T.k8s_pods.put_item(Item=item)` at line 206 without any call to `host_inventory.create_host`. No subsequent code anywhere in the module performs the registration.
- **Impact**: Pods launched via K8s are invisible to the Host Inventory. Users are forced to manually add the container as a host or know the raw `service_hostname` value. Feature parity with EC2-launched instances (which are intended to be similarly accessible) is broken.
- **Related tickets**: GAP-0227 (inverse: no cleanup on termination), INFRA-004 (K8s pod launcher), INFRA-001 (Host Inventory).

## 2. Current-State Investigation (root cause)

### Code path

`launch_pod` in `app/services/k8s_launcher.py` (lines 112-213) is the sole entry point for creating a K8s pod. After calling the mock (or real) K8s API, it builds the DynamoDB item dict:

```python
# k8s_launcher.py:178-206
item: Dict[str, Any] = {
    ...
    "service_hostname": result["service_hostname"],
    "ssh_port": 22,
    "ssh_key_id": ssh_key_id or "",
    "host_id": "",            # <-- always empty, never backfilled
    ...
}
T.k8s_pods.put_item(Item=item)
```

The `host_id` field documents the intent: the pod record should carry a reference to the corresponding host inventory entry so that `terminate_pod` can delete it (see GAP-0227). The field exists, the design intent is explicit, but the call to create the inventory entry is simply absent.

The `host_inventory` service (`app/services/host_inventory.py`) has a fully implemented `create_host` function that accepts a `source` parameter (e.g. `"k8s_auto"`) and a `group` parameter for organizational labeling. The function validates the hostname, writes to DynamoDB, and returns a dict that includes `host_id`. The function is importable from `app.services.host_inventory` — no circular dependencies exist between `k8s_launcher` and `host_inventory`.

### Why it is broken

There are three structural omissions:

1. No import of `host_inventory.create_host` in `k8s_launcher`.
2. No call to `create_host` after `T.k8s_pods.put_item(Item=item)` at line 206.
3. No write-back of the returned `host_id` into the `k8s_pods` record (which would enable cleanup in `terminate_pod`).

### Dev vs prod

In dev mode (`S.k8s_mock_enabled = True`) the mock K8s store creates the pod in memory and returns a `service_hostname` of the form `{pod_name}.{namespace}.svc.cluster.local`. This hostname is valid for `validate_hostname` in the host inventory service (dot-separated DNS label). In production the real K8s client would return a comparable `service_hostname`. The registration gap therefore exists in both environments.

---

## 3. Impact / Exploit / Blast Radius

This is a **functionality gap** rather than a security vulnerability. The direct consequences are:

- **Discovery**: Users who launch pods through the "New Container" UI flow cannot find those containers in the Host Inventory grid or Quick Connect panel. They must navigate to the K8s pods page separately, copy the `service_hostname`, and manually create a host entry.
- **Terminal integration**: The connection-profile feature (`app/services/connection_profiles.py`) resolves a connection target either from a stored `hostname` or from an `instance_id` referencing an EC2 instance. K8s pods have no equivalent path — the container is unreachable via Quick Connect or connection profiles.
- **Operational confusion**: The `host_id: ""` field stored on every pod record signals incomplete state. Any future automation (e.g. bulk-connect tooling, admin dashboards) that iterates pod records and expects a non-empty `host_id` will silently skip or error.
- **Cascade to GAP-0227**: Because `host_id` is never set, the cleanup fix for GAP-0227 (`if item["host_id"]: delete_host(...)`) will never trigger even after GAP-0226 is fixed unless both fixes are applied together.
- **Blast radius**: Every K8s pod ever created — across all users — lacks a host inventory entry. There is no automatic migration; existing pods will continue to have `host_id: ""` until they are terminated and relaunched after the fix.

## 4. Fix Design (code-level)

### Change: `app/services/k8s_launcher.py`

After storing the pod in DynamoDB, call `create_host` and write the resulting `host_id` back to the pod record. The write-back uses `update_item` so it is atomic and does not overwrite the rest of the pod record.

```python
# After T.k8s_pods.put_item(Item=item) at line 206:

from app.services.host_inventory import create_host, HostValidationError

try:
    host = create_host(
        user_sub,
        label=f"{label} (K8s)",
        hostname=result["service_hostname"],
        port=22,
        protocol="ssh",
        username=image_info.get("username", "ubuntu"),
        description=f"Auto-registered K8s pod {pod_id} (preset={preset})",
        group="K8s Containers",
        source="k8s_auto",
    )
    host_id = host["host_id"]
    # Write host_id back into the pod record
    T.k8s_pods.update_item(
        Key={"user_sub": user_sub, "sk": f"POD#{pod_id}"},
        UpdateExpression="SET host_id = :hid",
        ExpressionAttributeValues={":hid": host_id},
    )
    item["host_id"] = host_id
    logger.info(
        "k8s_pod_host_registered user_sub=%s pod_id=%s host_id=%s",
        user_sub, pod_id, host_id,
    )
except HostValidationError:
    logger.warning(
        "k8s_pod_host_register_failed user_sub=%s pod_id=%s hostname=%s",
        user_sub, pod_id, result.get("service_hostname"),
    )
```

### Dev/Prod parity (SECOPS-007)

- **Dev mode** (`S.k8s_mock_enabled = True`): The mock store returns a deterministic `service_hostname` (e.g., `ws-abc123-p_12345678.user-abc.svc.cluster.local`). `validate_hostname` in `host_inventory` accepts DNS labels, so registration succeeds in dev with no additional mock wiring.
- **Prod mode**: The real K8s client will return a real cluster hostname. The `create_host` call is identical; no feature flag is needed because the `host_inventory` service itself has no dev-only codepath.
- **KMS / encryption**: The host inventory stores no secrets (see the security note in `host_inventory.py:15-21`). No KMS call is required here.
- **Failure isolation**: If `create_host` fails (e.g., the host_inventory table is unavailable), the pod is already stored. The `except HostValidationError` guard ensures the pod launch succeeds even when registration fails; operators will see a `k8s_pod_host_register_failed` warning in logs. This mirrors the pattern used in other services (e.g., spending-alert failures in `compute_billing.py:119-123`).
- **Host inventory limit**: `create_host` enforces `S.host_inventory_max_per_user` (default: unlimited unless set). Auto-created hosts count against this limit. If the limit is exceeded, the `except` block catches `HostLimitExceeded` and logs a warning — extend the except clause to include `HostLimitExceeded`.

### Backward compatibility

Existing pod records have `host_id: ""`. No migration is needed because those pods will be terminated through their TTL eventually. If an admin wants to retroactively register running pods, a one-time migration script can iterate the `k8s_pods` table for running pods with `host_id == ""` and call `create_host` for each.

## 5. Testing, Verification & Rollout

### Regression test (fails-before / passes-after)

Add to `tests/test_k8s_launcher.py`:

```python
import pytest
from unittest.mock import patch, MagicMock
from app.services import k8s_launcher


def test_launch_pod_registers_host_inventory(monkeypatch, ddb):
    """GAP-0226: launch_pod must create a host inventory entry and store host_id."""
    created_hosts = []

    def fake_create_host(user_sub, *, label, hostname, port, protocol,
                         username, description, group, source):
        host_id = f"h_auto_{len(created_hosts)}"
        created_hosts.append({
            "host_id": host_id, "hostname": hostname, "source": source
        })
        return {"host_id": host_id}

    monkeypatch.setattr(
        "app.services.k8s_launcher.create_host", fake_create_host, raising=False
    )

    pod = k8s_launcher.launch_pod(
        "user_alice",
        label="My Pod",
        image="ubuntu-ssh",
        preset="small",
    )

    # Before fix: len(created_hosts) == 0 and pod["host_id"] == ""
    # After fix:  len(created_hosts) == 1 and pod["host_id"] starts with "h_auto_"
    assert len(created_hosts) == 1, "create_host must be called once"
    assert pod["host_id"].startswith("h_auto_"), "pod record must carry host_id"
    assert created_hosts[0]["source"] == "k8s_auto"
    assert created_hosts[0]["hostname"].endswith(".svc.cluster.local")
```

This test fails before the fix (pod["host_id"] == "", created_hosts is empty) and passes after.

### Manual QA steps

1. Run `just restart` to reset DynamoDB state.
2. In the React app, navigate to the Remote > Containers page and launch a new pod (image: ubuntu-ssh, preset: small).
3. Navigate to Remote > Hosts and verify a new entry with label "{pod name} (K8s)" appears in the "K8s Containers" group.
4. Confirm the host entry shows the correct `service_hostname`, port 22, protocol SSH.
5. Click Quick Connect on the host entry — confirm no error about missing host.
6. Terminate the pod (GAP-0227 fix should remove the host entry; validate together).

### Metrics / observability

- Add a counter metric `k8s_pod_host_registered_total` (increment on success) and `k8s_pod_host_register_failed_total` (increment on failure) to `metrics.py`.
- Existing `k8s_pod_launched` log line already provides traceability; add `host_id=%s` to it after backfill.

### Rollout

- **Effort**: S (< 1 day)
- **Risk**: Low. The change is additive; failure of `create_host` does not block pod launch.
- **Sequencing**: Deploy alongside GAP-0227 so that the `terminate_pod` cleanup can immediately use the newly populated `host_id` field. If deployed alone, GAP-0227 still requires the field to be non-empty to trigger cleanup.
- **Rollback**: Removing the `create_host` call restores previous behavior. Host inventory entries created by the new code must be deleted manually (or via a cleanup script) on rollback.
