# GAP-0353: Discovery Index Not Populated on Profile Update — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code before writing; all cites are `file:line`.

## 1. Summary & Classification

**Bug statement**: When a user updates their profile (display name, username, description, photo URL), the discovery index (`DiscoveryIndex` DynamoDB table) is never refreshed. The user's old `TOKEN#<prefix>` index entries remain stale, and any new display-name tokens are never written. A user who renames themselves becomes unsearchable under their new name and still appears under their old one until a manual re-index is triggered.

- **Severity**: HIGH
- **Source ticket**: SOC-003 §4.6 ("call `index_user_for_discovery(user_sub)` at end of `apply_profile_update`")
- **Status**: Open — confirmed missing.
- **Owning area**: Backend / Profile Service + Discovery Service
- **Investigation verdict**: Confirmed exactly as stated. `apply_profile_update()` ends at `app/services/profile.py:311` with `return updated` and calls nothing related to discovery.
- **Related tickets**: GAP-0354 (missing admin bulk-reindex endpoint — companion gap). SECOPS-007 relevant for the `DiscoveryIndex` DynamoDB table path in prod vs dev.

## 2. Current-State Investigation (Root Cause)

### `apply_profile_update` ends without calling the indexer

`app/services/profile.py:294–312`:

```python
def apply_profile_update(user_sub: str, updates: Dict[str, Any], *, replace: bool) -> Dict[str, Any]:
    current = get_profile(user_sub)
    base = empty_profile() if replace else current
    normalized = normalize_profile_payload(updates)
    updated = {**base, **normalized}

    audit_entries: List[Dict[str, Any]] = []
    ts = now_ts()
    for field in PROFILE_FIELDS:
        if current.get(field) != updated.get(field):
            audit_entries.append({"ts": ts, "field": field, "from": current.get(field), "to": updated.get(field)})

    save_profile(user_sub, updated, audit_entries)
    return updated          # ← function ends here; no discovery call
```

There is no `import` of anything from `app.services.discovery` or `app.services.profile_discoverability` (beyond the discoverability _state_ check imported at the top). The indexer function exists and is fully working.

### The indexer exists and is correct

`app/services/discovery.py:48–96`, `index_user_for_discovery(user_id: str)`:

- Fetches the profile item from `T.profile`.
- Resolves the discoverability state from `T.account_state`.
- Builds prefix tokens from `display_name` (and `username` if present).
- Batch-writes one item per token into `tbl_discovery` (the `DiscoveryIndex` DynamoDB table) keyed by `TOKEN#<token>` / `USER#<user_id>`.

The function returns the number of tokens written and is already safe to call multiple times (each call overwrites existing token items via `put_item`).

### The only write-time caller is the manual re-index endpoint

`app/routers/discovery.py:70–75`:

```python
@router.post("/reindex")
async def discover_reindex_user(
    user: AuthenticatedUser = Depends(get_authenticated_user),
):
    count = index_user_for_discovery(user.sub)
    return {"ok": True, "tokens_indexed": count}
```

This is the sole path that calls `index_user_for_discovery` for a single user. It is self-service: a user must visit `/ui/discover/reindex` themselves after a profile update for their new name to become searchable. No user knows to do this.

### What happens at registration

The registration path (wherever it calls `save_profile` or `apply_profile_update` for the first time) is also affected, but that is a separate concern. The immediate gap is that _existing_ users who update their profile are silently dropped from or remain stale in the index.

### Dev vs prod

In dev mode, `tbl_discovery` points to the local DynamoDB (`DDB_DISCOVERY_INDEX=DiscoveryIndex`, env-configured in `app/services/discovery.py:19–20`). In prod it points to the AWS-managed table. The behaviour of the missing call is identical in both environments.

## 3. Impact / Exploit / Blast Radius

**Discovery failures**: Any user who changes their display name after account creation is no longer findable by their new name via `GET /ui/discover/search`. They continue to appear under their old name's tokens — creating ghost entries that return stale data to searchers.

**Scale**: Every profile update operation on the platform silently desyncs the index. On a platform with active users changing display names, bio, or profile photos (photo URL is indexed as `photo_url` on the token items), the `DiscoveryIndex` table becomes increasingly stale over time.

**User-reported symptoms**: "I can't find my friend after they changed their name" / "I appear with my old name in search."

**Blast radius**: Pure read-time availability of discovery search for the affected user. No financial, security, or data-integrity consequences beyond stale search results.

## 4. Fix Design (Code-Level)

### 4.1 Add a non-fatal `index_user_for_discovery` call at the end of `apply_profile_update`

`app/services/profile.py:311` — change from:

```python
    save_profile(user_sub, updated, audit_entries)
    return updated
```

to:

```python
    save_profile(user_sub, updated, audit_entries)

    # Refresh discovery index so search reflects new display_name / photo.
    # Non-fatal: a discovery write failure must not roll back the profile save.
    try:
        from app.services.discovery import index_user_for_discovery
        index_user_for_discovery(user_sub)
    except Exception:
        import logging
        logging.getLogger(__name__).warning(
            "discovery reindex failed after profile update for %s", user_sub, exc_info=True
        )

    return updated
```

The lazy import (`from app.services.discovery import ...` inside the try block) avoids a circular-import risk: `discovery.py` imports `T.profile`, and `profile.py` should not have a top-level dependency on `discovery.py`. A local import resolves this cleanly and is already the pattern used elsewhere in the codebase (e.g., `app/services/social.py:87–89`).

### 4.2 Guard: only re-index when discovery-relevant fields change

To avoid unnecessary DynamoDB writes on every minor profile update (e.g., address changes), add a check before calling the indexer:

```python
DISCOVERY_FIELDS = {"display_name", "username", "description", "title", "profile_photo_url"}

_changed_fields = {e["field"] for e in audit_entries}
if _changed_fields & DISCOVERY_FIELDS:
    try:
        from app.services.discovery import index_user_for_discovery
        index_user_for_discovery(user_sub)
    except Exception:
        logger.warning("discovery reindex failed for %s", user_sub, exc_info=True)
```

This is a minor optimization; even without it the function is idempotent.

### 4.3 Dev/prod parity (SECOPS-007)

`index_user_for_discovery` already handles dev vs prod via the `DDB_DISCOVERY_INDEX` environment variable:

```python
# app/services/discovery.py:19–20
DDB_DISCOVERY_INDEX = os.getenv("DDB_DISCOVERY_INDEX", "DiscoveryIndex")
tbl_discovery = ddb.Table(DDB_DISCOVERY_INDEX)
```

In dev, `ddb` is pointed at `http://localhost:8001` (DynamoDB Local). In prod it is the real AWS table. The same code path is used in both environments — no special dev-mode branch is needed. The fix satisfies SECOPS-007 without any additional work.

### 4.4 Backward-compat / migration

Existing profiles that have already diverged from the index can be corrected by calling `POST /ui/discover/reindex` (self-service) or by the new admin bulk-reindex endpoint (GAP-0354). No DynamoDB schema change is required.

Old token items written under a previous display name are not deleted by a subsequent `index_user_for_discovery` call — the batch writer only creates or overwrites items for the new token set. A user who was formerly named "Alice Doe" and becomes "Alice Smith" will have both sets of tokens in the index until a full reindex is run. The stale "doe"-prefixed tokens will return the user in searches for their old name. This is a known limitation of the prefix-token design and is tracked separately under the discovery-token cleanup story. For this fix, the priority is ensuring new tokens are written; stale-token cleanup can follow in a subsequent pass.

### 4.5 Alternatives considered

- **Async background task**: fire the indexer as a FastAPI `BackgroundTask` so the HTTP response returns before the DynamoDB write. Advantage: faster response for the caller. Disadvantage: harder to test, and the write is cheap (~5–50 ms on LAN). A synchronous call is simpler and the extra latency is acceptable for a profile-update path. If the profile table ever grows beyond 1M items and individual `index_user_for_discovery` calls become measurably slow, converting to a `BackgroundTask` is a straightforward follow-on change.
- **DynamoDB Streams trigger**: index updates via a Streams consumer on the profile table. Correct at scale but requires Lambda/Kinesis infrastructure not present in this stack. The Streams approach would also eliminate both GAP-0353 and GAP-0354 at once. Overkill for the current architecture but the right long-term direction.
- **Cron job that re-indexes all users hourly**: would fix staleness but is not responsive (minutes-to-hours lag between a name change and search reflecting it). Not an acceptable user experience. Useful as a complementary safety net once the event-driven fix is in place.
- **Invalidate-then-rebuild pattern**: delete all `TOKEN#*` items for `USER#<sub>` before writing new ones. Eliminates stale-name tokens immediately but requires an extra read-then-delete pass; the current `put_item` overwrite is simpler and sufficient given that the `DiscoveryIndex` is not the system of record.

### Effort and risk

**Effort**: S (as stated in the gap ticket). The code change is approximately 10 lines in `profile.py`. The corresponding pytest tests add another ~40 lines. The Playwright E2E test requires an existing profile-update UI flow that already exists at `/settings/profile`.

**Rollout**: Zero risk to profile saves — the `try/except` ensures the indexer failure cannot roll back a profile write. Deploy as a normal backend release. Pair the deployment with a one-time invocation of `POST /ui/discover/admin/reindex-all` (GAP-0354) to repair all profiles that were updated before this fix was deployed.

**Risk**: Slightly increased DynamoDB write traffic on profile updates. At typical scale (profile updates are low-frequency) the impact is negligible. The `DISCOVERY_FIELDS` guard in §4.2 further limits writes to relevant changes only. In the worst case, a discovery DynamoDB endpoint error (e.g., table not yet created in a new environment) is caught by `try/except` and logged; the profile write still succeeds. Operators should verify that `DDB_DISCOVERY_INDEX` points to the correct table in all environments before deploying.

### Observability additions

Add a structured log line at the call site so that DevOps can measure indexer health:

```python
import logging as _log
_logger = _log.getLogger(__name__)
# Inside the try block, after the index call:
_logger.info("discovery_reindex user_sub=%s tokens=%d", user_sub, count)
```

This enables a simple log-based metric (`discovery_reindex` log line count) as a proxy for the rate of profile updates that touch discovery-relevant fields.

### One-time repair procedure

After deploying the fix, run the admin reindex endpoint to backfill all profiles that were never indexed or whose index is stale:

```bash
# Authenticated as root
curl -X POST https://<host>/ui/discover/admin/reindex-all \
     -H "x-csrf-token: <csrf>" \
     --cookie "ui_session=<sid>; ui_csrf=<csrf>; ui_access_token=<jwt>"
# Expected: {"ok": true, "users_indexed": N, "tokens_total": M, "errors": 0}
```

This is a non-destructive idempotent operation and can be re-run at any time without risk.
