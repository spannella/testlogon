# GAP-0113: Chat stream lacks viewer access check (BCAST-002) — Remediation Write-up

## 1. Summary & Classification

**Bug statement**: The broadcast chat SSE endpoint
`GET /ui/broadcast/sessions/{session_id}/chat/stream` authenticates the caller but never validates
whether they are permitted to view the session. For private broadcasts, any authenticated user can
subscribe to the real-time chat stream and receive all chat messages — including locked-content
messages whose text is returned without the `viewer_user_id` parameter that `_chat_msg_out` needs
to apply per-viewer visibility rules.

- **Severity**: HIGH (SEC-010 IDOR)
- **Source ticket**: BCAST-002 (second-pass as-built review)
- **GAP ID**: GAP-0113
- **Owning area**: Broadcast router — chat SSE stream
- **Status**: Open
- **Effort**: S

**Claim verdict**: Confirmed. `app/routers/broadcast.py:1763-1822` shows `_ = ctx` at line 1771
(caller identity discarded) and `_chat_msg_out(msg)` at line 1806 called without `viewer_user_id`.
The session existence check at line 1772 only verifies the session exists and is live/ready; no
access control is applied. Compare with the REST chat history endpoint at line 1596, which does
not call `check_viewer_access` either (a related but separate gap not covered here) but at least
passes `viewer_user_id=ctx["user_sub"]` to `_store_get_history`.

**Note on the ticket claim**: The ticket cites `broadcast.py:1763` as the location. Code
investigation confirms this is exactly the `broadcast_chat_stream_route` function definition. The
claim is accurate.

**Impact in one line**: Any authenticated user can subscribe to any private session's live chat
stream and read all messages, including the plain text of locked messages that other subscribers
have paid to unlock.

**Related tickets**: BCAST-002, GAP-0112 (SSE event stream IDOR), GAP-0114 (locked message leakage
via `_chat_msg_out`), GAP-0111 (session enumeration), SECOPS-007.

## 2. Current-State Investigation (root cause)

### Vulnerable handler

`app/routers/broadcast.py`, lines 1763–1822 (key lines shown):

```python
@router.get("/sessions/{session_id}/chat/stream")
async def broadcast_chat_stream_route(
    session_id: str,
    after: Optional[str] = Query(default=None),
    poll_ms: int = Query(default=500, ge=200, le=3000),
    ctx: dict = Depends(_ctx),
):
    """SSE stream for real-time broadcast chat messages."""
    _ = ctx                                      # ← line 1771 — discards caller identity
    session = get_session(session_id)
    if session.status not in ("live", "ready"):
        raise HTTPException(403, ...)
    ...
    async def gen():
        ...
        while True:
            messages = await anyio.to_thread.run_sync(
                lambda: _store_fetch_after(session_id, cursor, 50)
            )
            if messages:
                for msg in messages:
                    ...
                    out = _chat_msg_out(msg)      # ← line 1806 — no viewer_user_id
                    payload = json.dumps(out, ...)
                    yield f"event: {event_type}\ndata: {payload}\n\n"
```

Two distinct problems appear at lines 1771 and 1806:

**Problem 1 (line 1771)**: `_ = ctx` discards the caller's identity. There is no call to
`check_viewer_access`, so private sessions are completely open to any authenticated subscriber.

**Problem 2 (line 1806)**: `_chat_msg_out(msg)` is called without `viewer_user_id`. When
`viewer_user_id` is `None` (or absent), the `_chat_msg_out` function in
`app/services/broadcast_chat_store.py:344` sets `is_sender = False` and treats every caller as a
stranger. For locked messages, `is_unlocked` is set to `False` and `text` is set to `None`... but
only when `viewer_user_id is not None` (line 410: `is_sender or (viewer_user_id is not None and
viewer_user_id in unlocked_by)`). When `viewer_user_id` is `None`, `is_sender` is False and the
second condition is also False, so `is_unlocked = False` and `text = None`. This particular
interaction means locked message *text is already suppressed when viewer_user_id is None*, but the
root access control problem (the session membership check) remains wide open. GAP-0114 documents
the `_chat_msg_out` viewer_user_id gap as a separate issue.

### Contrast with the REST history endpoint

The REST history endpoint at line 1596 (`get_chat_history_route`) correctly passes
`viewer_user_id=ctx["user_sub"]` to `_store_get_history`. It also lacks a `check_viewer_access`
call, but that is a separate medium-severity gap (not this ticket). The SSE stream is worse because
it provides continuous delivery as new messages arrive.

### Why the session-status check is not sufficient

The check `if session.status not in ("live", "ready")` only prevents access to ended or unstarted
sessions. It does not check the *visibility* setting. A private live session passes this check
regardless of the caller.

### Dev vs prod path

The `_store_fetch_after` function queries DynamoDB (`T.broadcast_chat` table) using a sort key
range query. This runs identically on DynamoDB Local and AWS DynamoDB.

## 3. Impact / Exploit / Blast Radius

### Concrete exploit walkthrough

1. Attacker uses `GET /ui/broadcast/sessions?status=live` (GAP-0111) to enumerate private session
   IDs — or guesses/infers the ID from a direct link.
2. Connects to `GET /ui/broadcast/sessions/{session_id}/chat/stream` with a valid auth cookie.
3. The endpoint immediately starts streaming every new chat message from the session.
4. The attacker receives the real-time chat feed including:
   - All chat messages from viewers who have not locked them.
   - Locked message metadata (`lock_price_cents`, `lock_description`, `message_id`) — though text
     is suppressed when `viewer_user_id=None`.
   - Tip amounts and tipping activity.
   - Lottery entries and outcomes.
   - Product link promotions.
5. For sessions with `after=` set to an early sort key (e.g. `"0000000000000"`), the attacker
   can also replay the entire historical chat during the polling loop.

### Combined with GAP-0114

If the GAP-0114 fix lands first (adding `viewer_user_id` to `_chat_msg_out` in the SSE path),
the locked message text would be exposed for any message the attacker has "unlocked" — but the
attacker is not paying because they are not a legitimate subscriber. The access control gap
(GAP-0113) must be fixed first or simultaneously with the `viewer_user_id` gap (GAP-0114) to
prevent the combination from becoming worse.

### Affected population

All broadcast sessions with `visibility=private` or `visibility=unlisted` that have active or
recent chat messages. Public sessions are unaffected (access is intended to be open).

## 4. Fix Design (code-level)

### Change 1: Add `check_viewer_access` before streaming

```python
@router.get("/sessions/{session_id}/chat/stream")
async def broadcast_chat_stream_route(
    session_id: str,
    after: Optional[str] = Query(default=None),
    poll_ms: int = Query(default=500, ge=200, le=3000),
    invite_token: Optional[str] = Query(default=None),
    ctx: dict = Depends(_ctx),
):
    """SSE stream for real-time broadcast chat messages."""
    session = get_session(session_id)
    if session.status not in ("live", "ready"):
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail={"code": "BROADCAST_NOT_LIVE",
                    "message": "Chat stream is only available for live broadcasts"},
        )
    # SEC-010: gate private sessions before opening the stream
    from app.services.broadcast_privacy import check_viewer_access
    check_viewer_access(
        session_id,
        ctx["user_sub"],
        creator_id=session.created_by,
        visibility=session.broadcast_privacy_visibility,
        invite_token=invite_token,
    )
    viewer_user_id = ctx["user_sub"]   # capture for use inside gen()
    ...
```

### Change 2: Pass `viewer_user_id` to `_chat_msg_out` inside the generator

Inside `gen()`, replace:

```python
out = _chat_msg_out(msg)
```

with:

```python
out = _chat_msg_out(msg, viewer_user_id=viewer_user_id)
```

This ensures that per-viewer rules (locked message redaction, expiry visibility, reaction
personalisation) are applied correctly for the streaming consumer, not just for the REST history
endpoint. This change is closely related to GAP-0114 and should land in the same commit.

### Variable capture note

The `viewer_user_id` variable must be captured in the outer function scope before the inner
`gen()` coroutine is defined. Python closures capture variables by reference, but since
`viewer_user_id` is assigned once and not mutated, the closure is safe. The `session_id` variable
is already used this way throughout the generator.

### Dev/Prod parity (SECOPS-007)

`check_viewer_access` in `app/services/broadcast_privacy.py` reads from the `broadcast_sessions`
DynamoDB table to check allowlist entries. Both DynamoDB Local (dev) and AWS DynamoDB (prod) store
the same schema. The allowlist data is seeded correctly by the existing tests. No
environment-specific branch is introduced. The `broadcast_privacy_visibility` field is set on the
session record at creation time in both environments.

### Feature flag

None required. The fix is a pure hardening. Public/unlisted sessions continue to be accessible to
any authenticated user because `check_viewer_access` short-circuits when `visibility != "private"`.

### Alternatives considered

- **Check session membership in `_store_fetch_after`**: Pushing the access check into the data
  layer would mix authorization into the storage layer and make it harder to test. Rejected.
- **Return 200 but stream empty events for non-authorised callers**: Leaks session existence and
  keeps the connection open indefinitely. Rejected.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

Add to `tests/test_broadcast_chat_stream_access.py`:

```python
import pytest
from unittest.mock import patch, MagicMock, AsyncMock
from fastapi.testclient import TestClient
from app.main import app

def _private_session(session_id="sess_prv", creator="alice"):
    m = MagicMock()
    m.id = session_id
    m.created_by = creator
    m.broadcast_privacy_visibility = "private"
    m.status = "live"
    return m

def test_chat_stream_private_session_rejects_non_member():
    """Non-allowlisted user must get 403 on private session chat stream.

    Fails before fix (receives 200), passes after fix (receives 403).
    """
    with (
        patch("app.routers.broadcast.get_session",
              return_value=_private_session()),
        patch("app.routers.broadcast._ctx",
              return_value={"user_sub": "bob", "role": "user", "admin_profile": None}),
        patch("app.services.broadcast_privacy.is_allowlisted", return_value=False),
        patch("app.services.broadcast_privacy.redeem_invite_token", return_value=False),
    ):
        client = TestClient(app, raise_server_exceptions=False)
        resp = client.get("/ui/broadcast/sessions/sess_prv/chat/stream")

    assert resp.status_code == 403, (
        f"Expected 403 for non-member on private chat stream; got {resp.status_code}"
    )
    assert resp.json()["detail"]["code"] == "BROADCAST_PRIVATE_ACCESS_DENIED"


def test_chat_stream_locked_message_redacted_for_non_payer():
    """Locked message text must be None in SSE output for user who has not paid.

    This tests the viewer_user_id fix (Change 2) alongside the access check.
    Fails before fix (text may be exposed), passes after fix (text=None).
    """
    session = _private_session()
    session.broadcast_privacy_visibility = "public"   # bypass access check for this test

    locked_msg = {
        "message_id": "msg1",
        "session_id": "sess_prv",
        "sender_id": "carol",
        "sender_display_name": "Carol",
        "text": "secret locked content",
        "kind": "text",
        "created_at": 1700000000,
        "deleted": False,
        "sort_key": "sk001",
        "lock_price_cents": 100,
        "lock_description": "Unlock to see",
        "unlocked_by": {},           # bob has NOT unlocked
    }

    captured = []

    async def fake_fetch(session_id, cursor, limit):
        if not captured:             # yield once then stop
            captured.append(True)
            return [locked_msg]
        raise asyncio.CancelledError()

    import asyncio
    with (
        patch("app.routers.broadcast.get_session", return_value=session),
        patch("app.routers.broadcast._ctx",
              return_value={"user_sub": "bob", "role": "user", "admin_profile": None}),
        patch("app.routers.broadcast._store_fetch_after",
              side_effect=fake_fetch),
    ):
        client = TestClient(app, raise_server_exceptions=False)
        with client.stream("GET", "/ui/broadcast/sessions/sess_prv/chat/stream") as resp:
            for line in resp.iter_lines():
                if line.startswith("data:"):
                    import json
                    data = json.loads(line[5:])
                    if data.get("message_id") == "msg1":
                        assert data.get("text") is None, "Locked text must be None for non-payer"
                        assert data.get("is_unlocked") is False
                        break
```

### Manual QA steps

1. Alice creates a private broadcast session (visibility=private) and starts streaming chat.
2. As Bob (not on allowlist), connect to the chat stream endpoint:
   - Before fix: Bob receives 200 and the chat events stream.
   - After fix: Bob receives 403.
3. Alice adds Bob to the allowlist and Bob reconnects — should receive 200.
4. As Alice (creator), connect — should receive 200 at all times.
5. Verify a public session chat stream still works for any user.
6. Verify locked messages in the stream have `text=null` / `is_unlocked=false` for non-paying
   Bob (even after fix, Bob should not see locked content he has not paid for).

### Observability

Add a counter metric `broadcast.chat_stream.access_denied` when the 403 is raised. This enables
detection of enumeration attempts.

### Connection lifecycle and chat history replay attack

The `after` query parameter accepted by `broadcast_chat_stream_route` allows a client to specify
a sort key from which to begin replaying chat history. A caller who sets `after` to a very early
sort key (e.g. the string `"0"`) would receive the entire chat backlog from the beginning of the
session during the first polling cycle, before any new messages arrive. This means the SSE stream
is not merely a "new messages only" endpoint — it is a full-replay channel for the session's chat
history. Without the access check (pre-fix), an attacker could therefore replay the entire chat
history of a private session, not just future messages. After the fix, `check_viewer_access`
blocks this replay path for non-authorised callers before the generator is entered.

The REST history endpoint `GET /chat` (line 1596) also lacks a `check_viewer_access` call — this
is a separate medium-severity gap mentioned in the BCAST-002 gap list but not in scope here. The
SSE stream is higher priority because it provides continuous delivery.

### SSE generator closure and `viewer_user_id` capture

The `broadcast_chat_stream_route` function defines `gen()` as an inner async generator. In Python,
inner functions close over variables in the enclosing scope by reference. After the fix,
`viewer_user_id = ctx["user_sub"]` is assigned in the outer function scope before `gen()` is
defined, so the generator correctly references the caller's identity throughout its lifetime.
Because `viewer_user_id` is assigned once and never reassigned in the outer scope, there is no
closure-staleness risk. The same pattern is used for `session_id` and `cursor` in the existing
generator.

This capture also serves a secondary benefit: if a future change adds per-user filtering to the
chat fetch query (e.g. suppressing deleted messages only for their sender), `viewer_user_id` is
already available in the generator without any additional plumbing.

### Rollback

Revert the router change. No database migration or schema change involved.

### Risks & effort

- **Risk**: Invite-token experience. Viewers connecting via a chat embed widget may not have
  called `/viewers/join` first. The `invite_token` query parameter added in Change 1 allows
  them to authenticate the chat stream independently — this mirrors the playback-url endpoint
  behaviour.
- **Effort**: S — approximately 1.5 hours including test authoring. Both changes are in a single
  handler.
- **Sequencing**: GAP-0113 (access check) and GAP-0114 (`viewer_user_id`) should be applied
  together in the same commit because they are in the same handler and interact. Apply before next
  production deploy. GAP-0112 (SSE event stream) can be applied in the same batch.
