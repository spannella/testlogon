# GAP-0285: `start_kyc_questionnaire` and KYC Email Notifications Do Not Call Localization Functions — Remediation Write-up

## 1. Summary & Classification

**Ticket**: GAP-0285 | **Source**: KYC-020 | **Severity**: HIGH | **Status**: Open | **Effort**: M
**Owning area**: KYC — questionnaire endpoint and admin decision notifications (`app/routers/kyc_cases.py`)

KYC-020 §4.9 specifies that:
1. The `POST /{case_id}/start-questionnaire` endpoint must accept a `?lang=` query parameter and, using `kyc_translation_service.resolve_locale_for_user()` + `localize_questionnaire()`, return the questionnaire content in the user's locale.
2. All KYC case-status transition email notifications (approval, rejection, needs-more-info) must call `localize_email()` on the user's locale before dispatching.

Neither integration exists today. `start_kyc_questionnaire` (router line 690) accepts no `lang` parameter and calls no localization function. `admin_request_more_info` (line 1086) and `_admin_decide_case` (line 1165), which are the two paths that send status-change notifications, contain no calls to `kyc_translation_service`. The entire `KycTranslationService` — with its fully implemented `localize_questionnaire()` (lines 363–405) and `localize_email()` (lines 420–434) — is never imported into `kyc_cases.py`.

**Verdict**: Confirmed. The claim is accurate. A full-file `grep` of `kyc_cases.py` for `kyc_translation`, `localize_questionnaire`, `localize_email`, and `resolve_locale` returns no matches. The `kyc_translations` router (`app/routers/kyc_translations.py`) is wired for admin CRUD; the localization service is not wired into the user-facing KYC case flow at all.

**Related tickets**: GAP-0284 (N+1 query in `_bulk_fetch` that will be hit once this integration is wired), GAP-0320 (platform-level i18n packages not installed), GAP-0321 (locale field absent from user profile model).

## 2. Current-State Investigation (root cause)

### 1. `start_kyc_questionnaire` — no `lang` parameter, no localization

`app/routers/kyc_cases.py` lines 690–757:

```python
@router.post("/{case_id}/start-questionnaire", response_model=KycCaseEnvelope)
def start_kyc_questionnaire(
    case_id: str,
    body: KycStartQuestionnaireRequest,
    request: Request,
    _ctx: dict[str, str] = Depends(require_ui_session),
    user: AuthenticatedUser = Depends(get_authenticated_user),
):
    ...
    version = QNR_REPO.get_published_by_slug(body.published_slug)
    ...
    return _wrap_case(updated)
```

There is no `lang` query parameter. The endpoint fetches the questionnaire version from `QNR_REPO.get_published_by_slug(...)` and returns the case (not the questionnaire content itself). The response model is `KycCaseEnvelope`, which wraps the case item — not the questionnaire questions. This means `localize_questionnaire` would apply to the questionnaire body as returned by a separate `GET /questionnaire/{id}` endpoint, not to the `start-questionnaire` response itself.

However, the ticket's intent (per KYC-020 §4.9) is that the user's locale be stored on the questionnaire response session so that downstream question rendering picks up the locale. The localization also applies when returning questionnaire status and when the admin-side review exposes questionnaire summaries.

### 2. Email notifications — no `localize_email` calls

`admin_request_more_info` (line 1086–1162) calls `STORE.request_more_info(...)` and `_ensure_request_info_ticket_message(...)`. No email dispatch code is present in this path.

`_admin_decide_case` (lines 1165–1258) calls `STORE.apply_admin_decision(...)`. After the decision is applied, line 1247 hooks into `kyc_monitoring.create_review_schedule` for approved cases. No email notification call exists for either approval or rejection.

The `KycTranslationService.localize_email(event, language, variables)` function is fully implemented (lines 420–434 of `kyc_translations.py`) and returns `(subject, body)` with variable substitution. The email dispatch mechanism (platform-level alert emails) exists in `app/services/alerts.py`. The missing piece is that neither `admin_request_more_info` nor `_admin_decide_case` calls `localize_email` before the alert dispatch.

### 3. The `KycTranslationService` is never imported in `kyc_cases.py`

Confirmed by inspection of all 27 import statements in `kyc_cases.py` (lines 1–67). The service is exported as `kyc_translation_service` (singleton) from `app/services/kyc_translations.py` but is not referenced anywhere in the router. There is also no import of `resolve_locale_for_user`.

### Scope clarification on the `start-questionnaire` endpoint

The `start-questionnaire` endpoint does not return the questionnaire JSON body — it returns a `KycCaseEnvelope`. The questionnaire content (questions list) is fetched separately by the frontend via the questionnaire API. The localization integration therefore has two sub-tasks:

1. **Locale resolution and storage**: Resolve the user's locale at questionnaire-start time and store it on the `questionnaire` sub-object of the case, so that downstream questionnaire rendering and the PDF export step use the correct locale.
2. **Locale-aware email notifications**: When the admin makes a decision or requests more info, fetch the user's stored or resolved locale and call `localize_email` before dispatching the email.

## 3. Impact / Exploit / Blast Radius

**Regulatory / compliance**: KYC-020 §4.9 is a legal and UX requirement. KYC processes operate in jurisdictions where applicants have a right to receive instructions in their native language. Sending all KYC emails in English regardless of user locale is a compliance deficiency in markets where localized communication is required (EU GDPR Recital 39, various financial services regulations).

**User experience**: Users who set a non-English locale in their profile receive:
- Questionnaire UI labels always in English (because the locale is never resolved or stored at start time).
- Approval/rejection/needs-more-info emails always in English.
This affects all users with non-English locales — potentially a significant fraction of the user base depending on markets served.

**No security or data-integrity impact**: This is a missing-feature gap. No data is exposed or corrupted. The worst case is a regulatory non-compliance finding and user confusion, not a security breach.

**Blast radius**: Contained to KYC questionnaire and notification paths. Non-KYC features are unaffected.

## 4. Fix Design (code-level)

### Part 1: Add locale resolution to `start_kyc_questionnaire`

**File**: `app/routers/kyc_cases.py`

Add an import for the translation service singleton and the `Request` object's `Accept-Language` header:

```python
# Add after line 67 (existing imports):
from app.services.kyc_translations import kyc_translation_service
```

Extend the `start_kyc_questionnaire` endpoint to accept an optional `lang` query parameter and resolve + store the locale on the response session:

```python
@router.post("/{case_id}/start-questionnaire", response_model=KycCaseEnvelope)
def start_kyc_questionnaire(
    case_id: str,
    body: KycStartQuestionnaireRequest,
    request: Request,
    lang: str | None = Query(default=None, description="BCP-47 language code override"),
    _ctx: dict[str, str] = Depends(require_ui_session),
    user: AuthenticatedUser = Depends(get_authenticated_user),
):
    case = STORE.get_case(case_id)
    if not case:
        ...
    if case.get("user_sub") != user.sub:
        ...

    # --- NEW: resolve and store locale ---
    accept_lang = request.headers.get("accept-language")
    if lang:
        resolved_locale = kyc_translation_service.normalize_locale(lang)
    else:
        resolved_locale = kyc_translation_service.resolve_locale_for_user(
            user.sub, accept_language=accept_lang
        )
    # -------------------------------------

    qref = case.get("questionnaire") or {}
    existing_qid = str(qref.get("questionnaire_id") or "").strip()
    existing_rid = str(qref.get("response_session_id") or "").strip()
    if existing_qid and existing_rid:
        existing_session = QNR_REPO.get_response_session(
            questionnaire_id=existing_qid, response_session_id=existing_rid
        )
        if existing_session and str(existing_session.get("status") or "") != "submitted":
            audit_event("kyc_questionnaire_start", user.sub, request,
                        outcome="success", kyc_case_id=case_id, reused_existing=True)
            return _wrap_case(case)

    version = QNR_REPO.get_published_by_slug(body.published_slug)
    if not version:
        ...

    response_session_id = f"resp_{uuid4().hex}"
    session = QNR_REPO.put_response_session(
        response_session_id=response_session_id,
        questionnaire_id=str(version.get("questionnaire_id")),
        version_id=str(version.get("version_id")),
        respondent_id=user.sub,
    )
    try:
        updated = STORE.update_case_links(
            case_id=case_id,
            owner_sub=user.sub,
            expected_version=int(case.get("version") or 0),
            questionnaire={
                "questionnaire_id": str(version.get("questionnaire_id") or ""),
                "version_id": str(version.get("version_id") or ""),
                "response_session_id": str(session.get("response_session_id") or ""),
                "response_pdf_ref": None,
                "locale": resolved_locale,   # ← NEW: stored for downstream rendering
            },
        )
    except KycCaseConflictError:
        ...
    ...
    return _wrap_case(updated)
```

The `"locale"` field is stored on the `questionnaire` sub-object of the case item. The questionnaire rendering endpoint (called by the frontend to fetch questions) can then read `case["questionnaire"]["locale"]` and call `localize_questionnaire` before returning the question list.

### Part 2: Locale-aware email notifications

Add a helper function to `kyc_cases.py` that dispatches a KYC notification email in the user's locale:

```python
def _send_kyc_notification_email(
    *,
    user_sub: str,
    event: str,
    variables: dict,
    accept_language: str | None = None,
) -> None:
    """Send a KYC status-change email in the user's preferred locale."""
    try:
        locale = kyc_translation_service.resolve_locale_for_user(
            user_sub, accept_language=accept_language
        )
        subject, body = kyc_translation_service.localize_email(
            event=event, language=locale, variables=variables
        )
        if subject and body:
            from app.services.alerts import send_alert_email
            send_alert_email(user_sub=user_sub, subject=subject, body=body)
            logger.info(
                "kyc.notification_email_sent user_sub=%s event=%s locale=%s",
                user_sub, event, locale,
            )
    except Exception:
        logger.exception(
            "kyc.notification_email_failed user_sub=%s event=%s",
            user_sub, event,
        )
```

Call this helper from the two relevant paths:

**`admin_request_more_info`** (after `_ensure_request_info_ticket_message`, line ~1149):

```python

```

**`_admin_decide_case`** (after `_ensure_decision_ticket_updates`, line ~1232):

### Dev/Prod parity (SECOPS-007)

`resolve_locale_for_user` calls `app.services.profile.get_profile` which reads from DynamoDB. In dev this hits DynamoDB Local; in production it hits AWS DynamoDB. Both paths are identical. The `localize_email` function reads from the `kyc_translations` DynamoDB table, which also works identically in both environments.

If no translations are seeded for a locale, `localize_email` falls back to the English translation, then to the key itself. This graceful degradation means the feature can be deployed before translations are fully seeded, with English always available as the fallback.

The `send_alert_email` call is wrapped in a try/except so email dispatch failures never block the admin decision response.

### Backward compatibility

Adding `lang` as an optional query parameter with `default=None` is backward-compatible. All existing callers that omit `lang` continue to work as before (locale resolved from user profile → Accept-Language → default English). The `"locale"` field added to the `questionnaire` sub-object is additive and does not break existing case items that lack the field.

Feature flag `KYC_TRANSLATION_NOTIFICATIONS_ENABLED` (default `false`) can gate the email dispatch path to allow deployment before translation content is seeded.
