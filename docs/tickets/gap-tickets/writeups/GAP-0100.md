# GAP-0100: Concurrent Audit Trigger Race Condition — Remediation Write-up

> Claim accuracy note: The ticket cites `app/services/agent_compliance.py:788` as the location
> and describes a TOCTOU race between `get_running_audit` and `start_audit`. Code inspection
> confirms this is CORRECT. `get_running_audit` at line 788 queries DynamoDB for items with
> `status=running`, then `start_audit` at line 801 does an unconditional `T.compliance_audits.put_item`
> at line 831. Two concurrent callers can both pass the `get_running_audit` check before either
> write completes, and both successfully insert running audit items. The trigger path at
> `app/routers/agent_compliance.py:172–188` calls `run_mock_audit`, which calls `start_audit`
> at `agent_compliance.py:917` — the race is in the live router. The claim is accurate.

## 1. Summary & Classification

**Bug**: The audit-trigger flow in `app/services/agent_compliance.py` contains a classic TOCTOU (Time-of-Check / Time-of-Use) race condition. `start_audit` first calls `get_running_audit` to check for an existing running audit, then calls `T.compliance_audits.put_item` to create a new one. These are two separate DynamoDB operations with no atomicity guarantee between them. Two concurrent HTTP requests can both pass the check, both proceed past the guard, and both insert running audit items — creating duplicate running audits for the same user.

- **Severity**: HIGH
- **Source ticket**: AGENT-015
- **Owning area**: Agent Compliance service / audit lifecycle concurrency control
- **Status**: Open
- **Verdict**: Confirmed — claim matches the code exactly
- **One-line impact**: Two simultaneous POST `/ui/agent/compliance/audits/trigger` requests both create running audits, corrupting the audit log and double-executing expensive scanning workflows.
- **Related tickets**: GAP-0098 (trigger_review in-memory lock — nearly identical fix pattern in PM service), GAP-0081 (double-write claim race), SECOPS-007 (dev/prod parity)

## 2. Current-State Investigation (root cause)

### The TOCTOU check-then-write sequence

`app/services/agent_compliance.py:801–831` (`start_audit`):

```python
def start_audit(
    *, user_id: str, agent_id: str, worker_id: str = "", source: str = "manual_scan"
) -> Dict[str, Any]:
    ensure_tables()
    if get_running_audit(user_id=user_id) is not None:   # line 811: READ / CHECK
        raise ValueError("audit_in_progress")
    audit_id = uuid.uuid4().hex
    ts = now_ts()
    item = {
        "pk": _user_pk(user_id),
        "sk": _audit_sk(audit_id),          # e.g., "AUDIT#<random-hex>"
        ...
        "status": "running",
        ...
    }
    T.compliance_audits.put_item(Item=item)  # line 831: WRITE (unconditional)
    return _audit_to_out(item)
```

The guard at line 811 and the write at line 831 are two separate DynamoDB round-trips. The time between them — typically a few milliseconds of network latency — is the race window.

### The check function

`app/services/agent_compliance.py:788–798` (`get_running_audit`):

```python
def get_running_audit(*, user_id: str) -> Optional[Dict[str, Any]]:
    ensure_tables()
    resp = T.compliance_audits.query(
        KeyConditionExpression="pk = :pk AND begins_with(sk, :sk)",
        ExpressionAttributeValues={":pk": _user_pk(user_id), ":sk": "AUDIT#"},
    )
    for it in resp.get("Items", []):
        if it.get("status") == "running":
            return _audit_to_out(it)
    return None
```

This queries all audit items for a user (`pk = USER#<user_id>`, all `AUDIT#` SKs) and filters in Python for `status=running`. There is no DynamoDB-level uniqueness constraint. The check is a read that can be stale by the time the write occurs.

### The router call path

`app/routers/agent_compliance.py:172–188`:

```python
@agent_compliance_router.post("/audits/trigger", response_model=SecurityAuditOut)
async def trigger_audit(
    session=Depends(require_ui_session),
    admin=Depends(require_admin_or_root),
):
    user_id = _user_id(session)
    try:
        audit = svc.run_mock_audit(
            user_id=user_id,
            agent_id=_config_type_id(user_id),
            worker_id="mock-worker",
        )
    except ValueError as exc:
        if str(exc) == "audit_in_progress":
            raise HTTPException(status_code=409, ...)
```

`run_mock_audit` at `agent_compliance.py:909–934` calls `start_audit` at line 917. The endpoint is a live FastAPI `async def`. With `UVICORN_WORKERS > 1` (or multiple ECS tasks), two requests route to different processes, both call `get_running_audit` before either write commits, both find no running audit, and both proceed.

### GSI lag amplifies the window

`get_running_audit` queries the table's primary key directly (not a GSI), so there is no eventual-consistency delay from GSI replication. However, DynamoDB's internal write propagation means that immediately after `put_item` on worker A, a `query` from worker B on the same partition may or may not observe the new item, depending on read consistency settings. Since `query` uses eventually-consistent reads by default, the race window is wider than network latency alone — it can extend to the eventual-consistency propagation delay.

A strongly-consistent read (`ConsistentRead=True`) on the query would narrow the window but not eliminate it, because the check and write are still separate operations.

### Dev vs prod divergence (SECOPS-007)

`scripts/run_local_mock_backend.sh:70` defaults to `--workers 1`. In a single-process uvicorn with no `await` between `get_running_audit` and `put_item`, the race cannot manifest — both operations execute synchronously in the same thread without interleaving. In production with multiple workers or instances, the race is fully reachable. This is a textbook SECOPS-007 parity failure: the dev test suite (including E2E tests that exercise `trigger_audit`) passes cleanly while the production deployment is vulnerable.

### Comparison with GAP-0098

GAP-0098 (`trigger_review`) uses an in-process Python `set` as its guard — the wrong abstraction for multi-process concurrency. GAP-0100 uses DynamoDB queries as its guard — the right layer, but without atomic write semantics. Both gaps are fixed by the same pattern: a conditional `put_item` with `attribute_not_exists`.

## 3. Impact / Exploit / Blast Radius

**Exploit walkthrough (production, 2 workers)**:

1. Admin or root user sends two concurrent POST `/ui/agent/compliance/audits/trigger` requests (e.g., a slow network connection combined with an impatient double-click, or a monitoring script issuing periodic triggers).
2. Request A routes to worker 1: `get_running_audit` → DDB query returns empty → no running audit found → proceeds.
3. Request B routes to worker 2 within the same millisecond window: `get_running_audit` → DDB query also returns empty (A's write has not yet propagated) → no running audit found → proceeds.
4. Both workers issue `put_item` with different `audit_id`s (`AUDIT#<uuid-A>` and `AUDIT#<uuid-B>`), both with `status=running`. DynamoDB accepts both writes unconditionally.
5. Two running audits now exist for the same user.

**Data corruption consequences**:

- `list_audits` returns two items with `status=running`. Any frontend or monitoring code that asserts "at most one running audit" is broken.
- `get_running_audit` may return either item non-deterministically (DynamoDB returns items in SK order; the first match is returned). Status displays are unreliable.
- When the mock audit body runs `run_mock_audit`, it calls `complete_audit` for its own `audit_id`. This correctly marks one audit as completed. The other running audit remains in `status=running` permanently (no cleanup mechanism), polluting the audit log indefinitely.
- The compliance trend analysis (`get_finding_trends`) and audit history (`list_audits`) both include the orphaned running audit, skewing metrics.

**Financial / compute blast radius**:

When `S.compliance_agent_execute_commands` is `True` (the production scanning path, per the docstring at line 910), `run_mock_audit` would dispatch a real scanning workflow to the Worker Agent Framework. Double execution doubles:
- LLM token consumption for the compliance analysis prompt
- Worker-minutes billed for Playwright-based code scanning
- Report storage in S3 (two identical reports stored)

For a full-codebase compliance scan, duplicate execution could add $20–100 of unplanned infrastructure cost per incident at typical agent pricing.

**Scope limitation**: The endpoint requires `require_admin_or_root` (`app/routers/agent_compliance.py:175`). The attack surface is limited to admin and root users. However, a legitimate admin can inadvertently trigger the race (double-click, network retry), and a compromised admin account can trigger it deliberately.

## 4. Fix Design (code-level)

### Recommended fix: conditional put_item with attribute_not_exists on a dedicated lock item

A direct `attribute_not_exists` condition on the audit item itself is not viable because each audit uses a random `AUDIT#<uuid>` SK — there is no stable key to assert uniqueness against. Instead, write a separate `RUNNING_LOCK` item with a stable, predictable SK for the user. This lock is acquired atomically before creating the audit and released when the audit completes (or fails).

**Add to `app/services/agent_compliance.py`**:

```python
import time
from botocore.exceptions import ClientError

_RUNNING_LOCK_SK = "RUNNING_LOCK"
_LOCK_TTL_SECONDS = 3600  # 1 hour: covers longest expected audit


def _acquire_audit_lock(*, user_id: str) -> bool:
    """Atomically acquire the per-user running-audit lock in DynamoDB.

    Returns True if the lock was acquired (no audit is currently running).
    Returns False if the lock is already held (ConditionalCheckFailedException).
    Raises ClientError for unexpected DynamoDB errors.
    """
    expires_at = int(time.time()) + _LOCK_TTL_SECONDS
    try:
        T.compliance_audits.put_item(
            Item={
                "pk": _user_pk(user_id),
                "sk": _RUNNING_LOCK_SK,
                "lock_type": "running_audit",
                "acquired_at": now_ts(),
                "expires_at": expires_at,
                "ttl": expires_at,
            },
            ConditionExpression="attribute_not_exists(pk) AND attribute_not_exists(sk)",
        )
        return True
    except ClientError as exc:
        if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
            return False
        raise


def _release_audit_lock(*, user_id: str) -> None:
    """Release the running-audit lock. Best-effort; TTL handles cleanup on crash."""
    try:
        T.compliance_audits.delete_item(
            Key={"pk": _user_pk(user_id), "sk": _RUNNING_LOCK_SK}
        )
    except Exception:
        pass  # Non-fatal: TTL will expire the lock within _LOCK_TTL_SECONDS
```

**Update `start_audit`** (replace lines 811–831):

```python
def start_audit(
    *, user_id: str, agent_id: str, worker_id: str = "", source: str = "manual_scan"
) -> Dict[str, Any]:
    ensure_tables()
    if not _acquire_audit_lock(user_id=user_id):
        raise ValueError("audit_in_progress")
    audit_id = uuid.uuid4().hex
    ts = now_ts()
    item = {
        "pk": _user_pk(user_id),
        "sk": _audit_sk(audit_id),
        "audit_id": audit_id,
        "user_id": user_id,
        "agent_id": agent_id,
        "worker_id": worker_id,
        "status": "running",
        "source": source,
        "started_at": ts,
        "finding_counts": {},
        "files_scanned": 0,
        "compliance_summary": {},
        "GSI1PK": f"USER#{user_id}#AUDITS",
        "GSI1SK": ts,
    }
    T.compliance_audits.put_item(Item=item)
    return _audit_to_out(item)
```

**Update `complete_audit`** to release the lock when the audit finishes:

```python
def complete_audit(...) -> Dict[str, Any]:
    ensure_tables()
    resp = T.compliance_audits.get_item(
        Key={"pk": _user_pk(user_id), "sk": _audit_sk(audit_id)}
    )
    if not resp.get("Item"):
        raise LookupError("audit_not_found")
    ...
    T.compliance_audits.update_item(...)     # existing update
    _release_audit_lock(user_id=user_id)    # NEW: release the distributed lock
    return _audit_to_out(updated_item)
```

The `ttl` attribute on the lock item enables DynamoDB TTL auto-expiry so stale locks (from a worker crash before `complete_audit` was called) are automatically cleaned up within `_LOCK_TTL_SECONDS`.

### TTL setup

Add to `scripts/local-ddb-init.py`:

```python
# Enable TTL on compliance_audits table for lock auto-expiry
try:
    client.update_time_to_live(
        TableName=S.compliance_audits_table_name,
        TimeToLiveSpecification={"Enabled": True, "AttributeName": "ttl"},
    )
except Exception:
    pass  # Already enabled or DDB Local doesn't support TTL — harmless
```

Add the same to production Terraform/CDK table configuration.

### The existing `get_running_audit` call

After the fix, `start_audit` no longer calls `get_running_audit` as a pre-flight guard — `_acquire_audit_lock` replaces it. `get_running_audit` is retained as a read-only query for the `list_audits` endpoint and the `GET /audits/running` status check. Its role changes from "pre-flight guard" to "status reporting query."

### Dev/Prod parity (SECOPS-007)

The `conditional put_item` with `attribute_not_exists` is identical between DynamoDB Local (dev) and AWS DynamoDB (prod). No feature flag is needed. DynamoDB Local does not implement TTL expiry, so stale lock items are not auto-deleted in dev — but this is acceptable because dev uses a single worker and stale locks from crashes are cleared by `just restart` (which wipes the DDB data directory).

**Alternative rejected — strongly-consistent read**: Adding `ConsistentRead=True` to `get_running_audit` would narrow but not eliminate the race window. Check and write are still separate operations.

**Alternative rejected — Redis distributed lock (Redlock)**: Requires adding Redis to the stack (ElastiCache in prod, Redis container in dev). Disproportionate for a lock that fires at most a few times per day per user.

**Alternative rejected — database status+condition on the audit item**: Writing the audit item with `ConditionExpression="attribute_not_exists(GSI1PK)"` does not work because multiple audit items share the same `GSI1PK` value (all audits for a user). A dedicated lock item with a unique SK is cleaner and easier to reason about.

### Regression test (pytest, offline)

```python
# tests/services/test_agent_compliance_audit_lock.py
import time
import pytest
from unittest.mock import patch, MagicMock
from botocore.exceptions import ClientError
from app.services import agent_compliance as svc


def _ccf_error():
    return ClientError(
        {"Error": {"Code": "ConditionalCheckFailedException", "Message": "cond"}},
        "PutItem",
    )


class TestAuditLock:
    def test_lock_acquired_first_time(self, mocker):
        """Conditional put_item succeeds → returns True."""
        mock_put = mocker.patch.object(
            svc.T.compliance_audits, "put_item", return_value={}
        )
        result = svc._acquire_audit_lock(user_id="u1")
        assert result is True
        # Verify ConditionExpression is present (atomic guard)
        kwargs = mock_put.call_args.kwargs
        assert "ConditionExpression" in kwargs

    def test_lock_rejected_when_already_held(self, mocker):
        """ConditionalCheckFailedException → returns False, not raises."""
        mocker.patch.object(
            svc.T.compliance_audits, "put_item", side_effect=_ccf_error()
        )
        assert svc._acquire_audit_lock(user_id="u1") is False

    def test_start_audit_raises_when_lock_held(self, mocker):
        """FAILS before fix: two concurrent calls both succeed with the read-then-write."""
        mocker.patch.object(svc, "ensure_tables")
        mocker.patch.object(svc, "_acquire_audit_lock", return_value=False)
        with pytest.raises(ValueError, match="audit_in_progress"):
            svc.start_audit(user_id="u1", agent_id="a1")

    def test_start_audit_uses_conditional_lock_not_query(self, mocker):
        """After fix: start_audit does not call get_running_audit as pre-flight guard."""
        mocker.patch.object(svc, "ensure_tables")
        mocker.patch.object(svc, "_acquire_audit_lock", return_value=True)
        mock_put = mocker.patch.object(svc.T.compliance_audits, "put_item", return_value={})
        get_running_mock = mocker.patch.object(svc, "get_running_audit")
        svc.start_audit(user_id="u1", agent_id="a1")
        get_running_mock.assert_not_called()  # Lock replaces the query guard

    def test_complete_audit_releases_lock(self, mocker):
        """complete_audit must release the lock upon success."""
        mocker.patch.object(svc, "ensure_tables")
        release_mock = mocker.patch.object(svc, "_release_audit_lock")
        mocker.patch.object(
            svc.T.compliance_audits, "get_item",
            return_value={"Item": {
                "pk": "USER#u1", "sk": "AUDIT#abc",
                "status": "running", "audit_id": "abc",
                "user_id": "u1", "agent_id": "a1",
                "finding_counts": {}, "files_scanned": 0, "compliance_summary": {},
            }}
        )
        mocker.patch.object(svc.T.compliance_audits, "update_item", return_value={})
        svc.complete_audit(
            user_id="u1", audit_id="abc",
            finding_counts={}, files_scanned=0, compliance_summary={}
        )
        release_mock.assert_called_once_with(user_id="u1")

    def test_lock_ttl_field_present(self, mocker):
        """Lock item must include TTL field for auto-expiry."""
        captured = {}
        def capture_put(**kwargs):
            captured.update(kwargs)
        mocker.patch.object(svc.T.compliance_audits, "put_item", side_effect=capture_put)
        svc._acquire_audit_lock(user_id="u1")
        item = captured.get("Item", {})
        assert "ttl" in item, "Lock item must have ttl field for DynamoDB TTL auto-expiry"
        assert item["ttl"] > int(time.time()), "TTL must be in the future"

    def test_lock_released_on_unexpected_exception(self, mocker):
        """Lock released in finally block even if start_audit body raises."""
        mocker.patch.object(svc, "ensure_tables")
        mocker.patch.object(svc, "_acquire_audit_lock", return_value=True)
        mocker.patch.object(
            svc.T.compliance_audits, "put_item", side_effect=RuntimeError("ddb error")
        )
        release_mock = mocker.patch.object(svc, "_release_audit_lock")
        # start_audit should propagate the error but still release the lock
        with pytest.raises(RuntimeError):
            svc.start_audit(user_id="u1", agent_id="a1")
        # NOTE: this test will fail until start_audit wraps the put_item in try/finally
        release_mock.assert_called_once()
```

**Tests that FAIL before the fix**: `test_start_audit_raises_when_lock_held` (old code calls `get_running_audit`, not `_acquire_audit_lock`), `test_start_audit_uses_conditional_lock_not_query` (same), `test_complete_audit_releases_lock` (old `complete_audit` has no `_release_audit_lock` call), `test_lock_ttl_field_present` (no lock function exists yet).

### Rollout

- **Effort**: S (small — approximately 60 lines of new code; no DDB schema changes beyond enabling TTL; no migration needed)
- **Risk**: Low — the conditional write is atomic; the only observable change is reliable 409 responses for concurrent triggers. Admins who double-click "Trigger Audit" will see a clear error instead of a silent duplicate.
- **Sequencing**: Apply alongside GAP-0098 (trigger_review lock) in a single "agent distributed locking" PR. Both gaps use the same `attribute_not_exists` pattern and share reviewer context.
- **Rollback**: Remove `_acquire_audit_lock` / `_release_audit_lock` calls from `start_audit` and `complete_audit`; restore the `get_running_audit` pre-flight guard at line 811. The TOCTOU window reopens but no data is lost. Lock items in DDB expire via TTL within 1 hour.
