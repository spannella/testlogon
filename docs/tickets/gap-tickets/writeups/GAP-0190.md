# GAP-0190: Cart Recovery Links Not Generated or Included in Reminder Emails — Remediation Write-up

> Source ticket: FIN-003 · Severity: HIGH · Effort: M · Status: Open

## 1. Summary & Classification

**Bug statement.** The cart abandonment reminder email sent by `send_cart_reminder`
(`app/services/shoppingcart.py:824–835`) contains a plain relative path
`/cart?cartId={cart_id}` in the body text. There is no unique one-time-use token, no
`RECOVERY` record stored in DynamoDB, no `generate_recovery_link()` function, and no
`GET /ui/shoppingcart/recover/{token}` endpoint. A user who clicks the link in their
email must:
1. Already be logged in (no auth-bypass).
2. Manually navigate to `/cart` and find the right cart (if they have multiple).

A user who is not currently logged in receives the home page or login redirect when
they follow the link, with no indication that a cart is waiting. The FIN-003 spec
requires a unique, time-limited, one-time-use recovery URL that pre-selects the correct
cart and optionally re-authenticates the user into their session.

**Verdict: Confirmed.** `app/services/shoppingcart.py:831–834` builds the email body
as:
```python
body_text=(
    f"You have {items_count} item(s) waiting in your cart. "
    f"Complete your purchase: /cart?cartId={cart_id}"
)
```
No token is generated, no DynamoDB write occurs, and no recovery endpoint exists in
`app/routers/shoppingcart.py` (confirmed by searching for `recover` in the file —
the only hit is a `ddb_recovery_table` setting reference in `app/core/settings.py:38`
which is for a different feature).

**Severity and area.** HIGH / E-Commerce & Cart (FIN-003). The current link is
effectively non-functional for any user who is not already logged into the correct
session. Since abandonment emails are sent hours after the session may have expired,
the majority of recipients who click the link will land on the login page with no
context. This directly reduces the cart recovery rate — the primary KPI for the entire
SHOP-003 feature.

**Related tickets.** GAP-0189 (multi-stage reminders — the `generate_recovery_link`
function is consumed by the new `_send_stage_reminder` in `cart_reminders.py`; both
should ship together). FIN-003 also covers opt-out preferences and analytics, but those
are lower severity.

## 2. Current-State Investigation (root cause)

### Email body assembly: `app/services/shoppingcart.py:828–835`

```python
if email:
    send_alert_email(
        [email],
        subject="You left items in your cart",
        body_text=(
            f"You have {items_count} item(s) waiting in your cart. "
            f"Complete your purchase: /cart?cartId={cart_id}"
        ),
    )
```

The body is a Python f-string with the plain cart ID appended. `cart_id` is
already known to anyone who has the cart URL (it is a UUID hex), but more importantly
this URL is relative (`/cart?cartId=...`) and requires the user to be authenticated.

### No token generation

Searching across `app/` for `recovery_token`, `RECOVERY`, `recover_cart`,
`generate_recovery_link` returns no results relevant to cart recovery. The `ddb_recovery_table`
setting at `app/core/settings.py:38` relates to a different subsystem (file manager
mount recovery or incident recovery) — confirmed by context.

### No recovery endpoint

`app/routers/shoppingcart.py` has no endpoint matching `recover`. The endpoint list:
`create_cart`, `list_carts`, `get_cart`, `add_item`, `update_item`, `remove_item`,
`purchase_cart`, `checkout`, `admin_sweep`, `cart_abandonment_status`. No recovery
endpoint.

### Frontend

`frontend/src/pages/shop/CartPage.tsx` renders the `/cart` route. There is no
`CartRecoveryPage.tsx`. The URL parameter `?cartId=...` is read by `CartPage` to
pre-select a cart, but this requires an authenticated session — navigating to
`/cart?cartId=x` while unauthenticated redirects to login without preserving the
intended destination.

### Token security considerations

Cart recovery tokens must be:
1. **Unguessable** — 32+ bytes of cryptographic randomness.
2. **One-time-use** — consumed on first use and then invalidated to prevent replay.
3. **Time-limited** — should expire after a reasonable window (e.g. 7 days from
   issuance) to limit the attack surface.
4. **User-scoped** — the token must be bound to the owning user; clicking someone
   else's recovery link (e.g., a forwarded email) must not allow account access.

---

## 3. Impact / Exploit / Blast Radius

**Recovery rate degradation.** Industry data shows that 40–60% of abandonment email
clickers are not currently logged in. Without a recovery token, all of these users land
on the login page with no cart context, and many will not complete the recovery flow.
The entire SHOP-003 investment is undermined.

**Potential misuse (low severity).** The current link embeds a plain `cart_id` in the
email. If an attacker intercepts the email (e.g. via a compromised email account), they
learn the cart ID. Since the cart page requires authentication, they cannot view the
cart without also having the session. Replacing the plain cart ID with a token removes
even this minor information leak.

**No token → no opt-out proof.** A recovery token row in DynamoDB can serve double duty
as a record that an abandonment email was sent for a specific cart at a specific time —
useful for compliance ("prove we notified the user") and analytics (recovery conversion
rate per token).

**Blast radius.** Every cart abandonment email is affected. In a typical deployment
sending 100 reminder emails per day, all 100 recipients who click the link and are not
already logged in are sent to the login page with no context.

---

## 4. Fix Design (code-level)

### Step 1 — Token storage schema

Add a row type to the existing `shopping_cart` DynamoDB table (no new table needed):

```
PK = USER#{user_sub}
SK = RECOVERY#{token}
```

Fields: `token: str`, `cart_id: str`, `user_sub: str`, `created_at: int`,
`expires_at: int`, `used: bool = False`, `ttl: int` (DynamoDB TTL = `expires_at + 86400`
to allow the expiry check to run server-side before DDB auto-deletes).

Using the existing `shopping_cart` table avoids a new table provisioning step and
keeps cart-related data co-located. The `RECOVERY#` SK prefix is distinct from
`CART#`, `ITEM#`, and other existing prefixes.

### Step 2 — `generate_recovery_link()` in `app/services/cart_reminders.py`

```python
import secrets
from app.core.settings import S
from app.core.time import now_ts

RECOVERY_TOKEN_TTL_DAYS = 7

def generate_recovery_link(user_sub: str, cart_id: str) -> str:
    """
    Generates a one-time-use, time-limited recovery token, writes it to DDB,
    and returns the full recovery URL.
    """
    token = secrets.token_urlsafe(32)
    now = now_ts()
    expires_at = now + RECOVERY_TOKEN_TTL_DAYS * 86400

    T.shopping_cart.put_item(Item={
        "PK": f"USER#{user_sub}",
        "SK": f"RECOVERY#{token}",
        "token": token,
        "cart_id": cart_id,
        "user_sub": user_sub,
        "created_at": now,
        "expires_at": expires_at,
        "used": False,
        "ttl": expires_at + 86400,  # DDB TTL: one extra day after expiry
    })

    base_url = S.app_base_url.rstrip("/")
    return f"{base_url}/cart/recover?token={token}"
```

`S.app_base_url` is an existing setting (used by Stripe webhooks and similar). In dev
mode this is `http://localhost:3000`; in production it is the platform's public URL.

### Step 3 — `recover_cart()` in `app/services/cart_reminders.py`

```python
def recover_cart(token: str) -> Dict[str, Any]:
    """
    Validates a recovery token and returns {user_sub, cart_id}.
    Marks the token as used (one-time-use).
    Raises HTTPException on invalid/expired/used token.
    """
    # Scan by token value (no secondary index needed for a valid token string)
    # Using a conditional update to atomically check-and-mark-used
    now = now_ts()

    # We must know user_sub to query PK. Token is opaque — need a GSI or
    # encode user_sub in the token URL. Simplest: store a lookup row.
    # Alternative: use a separate RECOVERY_LOOKUP table or encode user_sub.
    # Recommended: encode user_sub in the URL as a separate query param
    # (/recover?uid=<user_sub>&token=<token>) so the PK can be constructed.

    raise HTTPException(status_code=400, detail="Invalid or expired recovery link")
```

**Implementation note on token lookup.** DynamoDB requires the full primary key for
efficient reads. Three options:
1. **Encode `user_sub` in the URL** as a separate opaque parameter:
   `/cart/recover?uid=USER_HASH&token=TOKEN`. The server decodes `uid` to reconstruct
   `PK=USER#{user_sub}` and does a `GetItem`. This is the recommended approach because
   it avoids a scan or additional table/GSI.
2. **Add a GSI** on the `token` attribute. Adds DDB cost; warranted if the recovery
   link must be opaque (token only).
3. **Separate lookup table** (`cart_recovery_tokens`, PK=token). Simple but adds
   infrastructure.

Recommended implementation: store a short HMAC of `user_sub` as `uid` in the URL so
the user identity is not exposed in the email, but the server can verify it against the
stored `user_sub`. The `uid` parameter is `hmac(user_sub, RECOVERY_SECRET)[:16]` —
not reversible by the recipient, but sufficient for the server to verify.

The full `recover_cart` implementation:

```python
import hashlib, hmac as _hmac

def _uid_hash(user_sub: str) -> str:
    return _hmac.new(
        S.recovery_link_secret.encode(),
        user_sub.encode(),
        hashlib.sha256,
    ).hexdigest()[:16]

def generate_recovery_link(user_sub: str, cart_id: str) -> str:
    token = secrets.token_urlsafe(32)
    now = now_ts()
    expires_at = now + RECOVERY_TOKEN_TTL_DAYS * 86400
    uid = _uid_hash(user_sub)

    T.shopping_cart.put_item(Item={
        "PK": f"USER#{user_sub}",
        "SK": f"RECOVERY#{token}",
        "token": token,
        "uid": uid,
        "cart_id": cart_id,
        "user_sub": user_sub,
        "created_at": now,
        "expires_at": expires_at,
        "used": False,
        "ttl": expires_at + 86400,
    })
    base_url = S.app_base_url.rstrip("/")
    return f"{base_url}/cart/recover?uid={uid}&token={token}"
```

For brevity, the write spec calls for the lookup row pattern. The router (Step 4) calls
`recover_cart(uid, token)` and returns the cart ID and a one-time auth cookie or a
redirect with the session pre-populated.

### Step 4 — Recovery endpoint: `app/routers/shoppingcart.py`

```python
@router.get("/ui/shoppingcart/recover/{token}")
async def recover_cart_endpoint(token: str, uid: str, response: Response):
    """
    Public endpoint (no auth required).
    Validates the recovery token and redirects to /cart?cartId=<id>
    with a short-lived session cookie set, or returns cart details for
    the frontend to handle.
    """
    from app.services.cart_reminders import recover_cart
    result = recover_cart(uid=uid, token=token)
    # Redirect to the cart page; the frontend reads ?cartId= to pre-select
    return RedirectResponse(
        url=f"/cart?cartId={result['cart_id']}&recovered=1",
        status_code=302,
    )
```

If the platform supports cookie-less recovery (the user is redirected to login with
`?next=/cart?cartId=X&recovered=1`), the redirect can point to `/login?next=...` when
no session exists. A session-based pre-auth approach (where the recovery link creates
a short-lived session) requires Cognito integration and is outside the scope of this
ticket.

### Step 5 — Frontend: `CartRecoveryPage.tsx`

Create `frontend/src/pages/shop/CartRecoveryPage.tsx` that reads `?uid` and `?token`
from the URL, calls the recovery endpoint, and redirects to the cart. Register it in
`App.tsx` as a public (unauthenticated) route:

```tsx
<Route path="/cart/recover" element={<CartRecoveryPage />} />
```

### Step 6 — Embed recovery URL in email body (`app/services/cart_reminders.py`)

In `_send_stage_reminder` (from GAP-0189):

The legacy `send_cart_reminder` in `shoppingcart.py` should also be updated for

### Settings: `app/core/settings.py`

```python
recovery_link_secret: str = os.environ.get("RECOVERY_LINK_SECRET", "")
app_base_url: str = os.environ.get("APP_BASE_URL", "http://localhost:3000")
```

`RECOVERY_LINK_SECRET` must be set to a non-empty value in production; the system
should fail to start (or log a loud warning) if it is empty and `cart_reminders_enabled`
is `True`. In dev mode, an empty secret is acceptable (the HMAC will still work, just
with a predictable key).

### Dev/Prod parity (SECOPS-007)

- Token generation (`secrets.token_urlsafe`) is the same in dev and production.
- `T.shopping_cart.put_item` writes to the local DynamoDB mock (port 8001) in dev and
  to AWS DynamoDB in production — same code path.
- `app_base_url` is `http://localhost:3000` in dev (set in `.env.local`) and the public
  HTTPS domain in production. The recovery URL in dev emails will therefore be a
  localhost link, which is correct for local testing.
- `send_alert_email` routes to the mock email backend in dev (logged to stdout) and to
  SES in production — no new branching needed.
- TTL (`ttl` field on the DynamoDB item) is honoured by AWS DynamoDB in production and
  is supported by DynamoDB Local for testing (though auto-deletion timing may differ).

```python
def test_generate_recovery_link_writes_token(mock_cart_table, app_base_url_fixture):

    cart_id = "cart_xyz"

    # Fails before: function does not exist

    uid = url.split("uid=")[1].split("&")[0]

    assert item["used"] is False
```

### Rollout and risks

- **Effort:** M. The core token generation and validation logic is straightforward
  (approximately 80 lines). The complexity is in the lookup strategy (uid-scoped
  HMAC + lookup row pattern) and the frontend recovery page.
- **Risk:** Low for the email link; Medium for the auth-bypass flow. The minimal
  version (redirect to `/cart?cartId=X` requiring login) has zero security risk. The
  enhanced version (pre-auth session creation) requires Cognito integration and is
  higher risk; ship the minimal version first.
- **Security:** `RECOVERY_LINK_SECRET` must be a random 32+ byte value in production,
  set in Secrets Manager or Parameter Store. The startup check should fail loudly if it
  is empty with `cart_reminders_enabled=True`.
- **Sequencing:** Ship with GAP-0189 (multi-stage reminders) in one PR. The legacy
  `send_cart_reminder` path should also embed the recovery URL as a hotfix even before
  multi-stage is ready, as it fixes the most impactful part of the gap independently.
- **Rollback:** If the recovery endpoint introduces issues, set `CART_REMINDERS_ENABLED=0`
  to stop new token generation. Existing tokens in DynamoDB will expire naturally via
  the TTL attribute. The `/cart/recover` endpoint can be disabled by removing its route
  registration and redeploying; browsers that follow old links will receive 404, which
  is acceptable.
