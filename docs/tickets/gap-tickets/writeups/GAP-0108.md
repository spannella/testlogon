# GAP-0108: /register/start has no resume path for pending_verification accounts — Remediation Write-up

> Claim verified against `app/routers/register.py` and `app/services/registration.py`.
> Claim is **confirmed**. The cited line (114) is correct: the `create_user_record` call at
> line 115 immediately raises HTTP 409 when the email already exists as a `pending_verification`
> account, and the handler silently swallows it and returns `generic_response` with no new
> challenge. There is no resume branch.

## 1. Summary & Classification

**Bug**: `POST /ui/register/start` called with an email that already has a
`pending_verification` record in DynamoDB silently returns the generic success response
(`{"status": "ok", "verification_required": true, ...}`) without issuing a new verification
code. The user believes the registration restarted but no email is sent; they proceed to
`/verify`, enter any code, and fail. The only real exit is the `/resend` endpoint, but the
frontend never navigates there because it thinks `/start` succeeded.

- **Severity**: HIGH (registration flow permanently broken for users who attempt to re-register
  with an abandoned email; orphaned accounts accumulate with no self-service recovery)
- **Source ticket**: AUTH-001
- **Status**: Open
- **Owning area**: Registration router (`app/routers/register.py`) and registration service
  (`app/services/registration.py`)
- **Verdict**: Confirmed. The duplicate-email 409 raised inside `create_user_record` is
  caught at register.py:121-124 and causes a silent `return generic_response`.
- **Related tickets**: GAP-0107 (exposing `unverified` in `/check` — prerequisite for the
  frontend to know to call this path), GAP-0109 (frontend recovery UI — uses the result of
  this fix).

## 2. Current-State Investigation (root cause)

### Why abandoned registrations are common

The registration flow sends a time-limited verification code by email. Users frequently:
- Close the tab before the code arrives
- Lose the email in spam
- Switch devices mid-flow
- Have a browser crash during the verify step

In each case a `pending_verification` account is left in DynamoDB and a valid challenge token
sits in the `sessions` table. The challenge has a TTL, but the user record and account state
persist indefinitely. There is currently no background job to purge stale
`pending_verification` accounts after their challenges expire, so orphaned records accumulate
over the lifetime of the deployment.

### create_user_record — registration.py:58-95

```python
def create_user_record(*, email, full_name, password, verification_required):
    user_sub = normalize_email(email)
    if _user_exists(user_sub):
        raise HTTPException(409, "User already exists")    # line 67
    ...
    set_account_state(user_sub, "pending_verification", ...)
```

The function raises 409 unconditionally if the user record already exists. It does not check
whether the existing account is `pending_verification` vs `active`.

### register_start — register.py:113-150

```python
verification_required = True
try:
    create_user_record(                        # line 115
        email=username,
        full_name=body.full_name,
        password=body.password,
        verification_required=verification_required,
    )
except HTTPException:                          # line 121
    audit_event("register_start", username, req, outcome="failure",
                reason="duplicate_or_invalid")
    clear_lockout(username, ip, "register_start")
    return generic_response                    # line 124 — silent success; no challenge issued
```

The `except HTTPException` block does not differentiate between 409 (duplicate email) and
other HTTP errors. Both result in `return generic_response`. After the return the caller
receives `{"status": "ok", "verification_required": true, "delivery_medium": null}` —
indistinguishable from a successful first-time registration — but no email was sent.

### The /resend endpoint exists but is unreachable

`register_resend` (register.py:241-307) correctly creates a new registration challenge and
sends the email. However the frontend transitions to the verify step based solely on the
`/start` response (`verification_required: true`), not on whether a new code was actually
dispatched. The user will be stuck on the verify screen with no valid code.

### Dev vs prod

The Cognito path (`use_cognito = True`, lines 88-111) hits a different code branch: Cognito
itself returns 409 for a duplicate user and the handler again returns `generic_response`. The
dev path (`use_cognito = False`) falls into the `create_user_record` block described above.
Both paths exhibit the same silent-success behaviour; only the Cognito 409 is explicit while
the dev 409 is implicit via the `create_user_record` raise.

## 3. Impact / Exploit / Blast Radius

### User experience

Every user who:
1. Starts registration
2. Fails to complete email verification (app crash, closed tab, phone died)
3. Returns to register again with the same email

…is permanently locked out of self-service registration. The account exists but cannot be
verified, cannot be logged into, and cannot be re-registered. Support must manually delete or
patch the DynamoDB record.

### Orphan accumulation

Without a resume path, every abandoned partial registration creates a permanent orphaned
account. If the platform sends promotional emails, users who never completed registration
receive them because the profile record exists with `status: pending_verification`.

### Security considerations

The resume path must **not** allow an attacker to hijack another user's pending registration:
- The fix must refuse to send a new challenge if the target account's state is `active` (not
  `pending_verification`).
- Existing rate-limiting (`can_send_verification`, `enforce_lockout`) already limits how
  frequently codes can be requested.
- No password change should occur during resume; the existing password hash must remain.

### Blast radius

Affects every user who abandons registration before verification. The effect is silent and
therefore hard to notice without support tickets.

## 4. Fix Design (code-level)

### Approach: add a resume branch in register_start before create_user_record

The change is entirely within `app/routers/register.py` and `app/services/registration.py`.
A feature flag `REGISTRATION_ALLOW_RESUME_UNVERIFIED` gates the behaviour to allow safe
rollout.

#### Step 1 — Add setting to app/core/settings.py

```python
registration_allow_resume_unverified: bool = os.environ.get(
    "REGISTRATION_ALLOW_RESUME_UNVERIFIED", "1"
) not in ("0", "false", "False")
```

Default `True` — the resume path should be on by default (the current no-resume state is the
bug, not the desired behaviour).

#### Step 2 — Add get_pending_user helper to registration.py

```python
from app.services.account_state import get_account_state

def get_pending_user(email: str) -> bool:
    """Return True if the email exists and is in pending_verification state."""
    normalized = normalize_email(email)
    if not _user_exists(normalized):
        return False
    return get_account_state(normalized)["status"] == "pending_verification"
```

#### Step 3 — Insert resume branch in register_start (register.py, before line 113)

```python
# Resume path for pending_verification accounts
if S.registration_allow_resume_unverified:
    from app.services.registration import get_pending_user
    if get_pending_user(username):
        # Do NOT create a new user record — account already exists.
        # Re-issue a verification challenge just like /resend does.
        if can_send_verification(username, "email"):
            mfa_setup: list[str] = []
            if body.enable_sms_mfa:
                mfa_setup.append("sms")
            if body.enable_totp_mfa:
                mfa_setup.append("totp")
            code = create_registration_challenge(
                user_sub=username,
                channel="email",
                send_to=username,
                mfa_setup=mfa_setup,
                sms_phone=body.phone,
            )
            send_email_code(username, "Registration", code)
            audit_event("register_start", username, req, outcome="success",
                        verification_required=True, delivery_medium="email",
                        reason="resume_pending")
        else:
            audit_event("register_start", username, req, outcome="warning",
                        reason="resume_rate_limited")
        clear_lockout(username, ip, "register_start")
        return generic_response  # same shape; new code was sent
```

This block runs before `create_user_record`, so the 409 branch is never reached for
`pending_verification` accounts. The `generic_response` returned is identical in shape to the
normal first-registration response; the frontend transitions to the verify step and this time
a real code was sent.

#### Active accounts are unaffected

If the account's state is `active`, `get_pending_user` returns `False` and execution falls
through to `create_user_record`, which raises 409, caught and returned as `generic_response`
as before. An active account owner cannot trigger a new verification code via `/start`.

### Dev/Prod parity (SECOPS-007)

`get_pending_user` reads from `users` and `account_state` tables — both exist in dev and
prod. The Cognito code path (lines 88-111) runs before this block. When `use_cognito` is
`True` the existing Cognito exception handling fires first; the resume branch is only reached
on the dev/non-Cognito path. To handle prod Cognito correctly, the Cognito 409 exception
handler (lines 98-106) should also be extended to check account state and re-send:

```python
# Inside the `if exc.status_code == 409:` Cognito branch:
if S.registration_allow_resume_unverified and get_pending_user(username):
    # same challenge-re-issue logic as above
    ...
    return generic_response
```

Both code paths are covered; the feature flag controls both.

### Backward compatibility

When `REGISTRATION_ALLOW_RESUME_UNVERIFIED=0` the behaviour is identical to today.

### Password update consideration

The resume path re-issues a challenge but does NOT update the password stored in the user
record. This is intentional: the user who abandoned the original registration is presumed
to be the same person returning to complete it. If the re-submitting user provides a
different password on the second `/start` call, that password is silently ignored by the
resume branch. This is the correct behaviour — changing the password during a re-issue would
allow anyone who knows an email address is in `pending_verification` state to set an
arbitrary new password by calling `/start`. A user who wants to change their password can do
so after completing verification via the normal password-change flow. This constraint should
be documented in the API reference and communicated to frontend engineers so the UI does not
imply the password can be changed at this step.

### Manual QA steps

1. `just up`
2. Register with a new email; do not enter the verification code (leave tab open at verify
   screen).
3. Open a second tab, go to `/register`, enter the same email and password, click Next.
4. Confirm an email is received in the mock mail log (`just logs` or SMTP mock).
5. Switch back to the first tab, enter the new code — confirm registration completes.
6. Repeat the test but enter a different password on the second `/start` call; confirm the
   account is accessible only with the original password after verification.

### Observability

Add `reason="resume_pending"` to the audit event so support teams can distinguish resumes
from first-time registrations in the audit log.

### Cleanup of orphaned accounts (complementary change)

While the resume path fixes the self-service recovery problem, orphaned `pending_verification`
accounts whose challenge TTL has expired should be periodically cleaned up. This is a
separate task (not part of this ticket) but should be filed and tracked alongside this fix.
The cleanup job would:
1. Scan `account_state` for rows with `status=pending_verification` and
   `updated_at < now - MAX_CHALLENGE_TTL`.
2. Delete the corresponding `users`, `account_state`, `sessions` (challenge rows), and
   `profiles` records.
3. Run as a scheduled Lambda or a cron-triggered admin endpoint.

Without this cleanup, the DynamoDB table accumulates records indefinitely, and the resume
path will find and re-issue codes for accounts whose challenges expired weeks ago. The
`can_send_verification` rate-limiter already protects against code spam, but the cleanup
provides a cleaner long-term baseline.

### Rate-limiting and abuse prevention

The resume path calls `can_send_verification(username, "email")` before re-issuing a
challenge. This is the same guard used by the `/resend` endpoint and prevents a caller from
triggering unlimited code sends by repeatedly calling `/start` with the same
`pending_verification` email. The existing `enforce_lockout` and `rate_limit_password_recovery`
checks at lines 79-80 also apply before the resume branch is reached. No additional
rate-limiting is required specifically for the resume path.

### Rollout

- **Effort**: S (single router change + one helper function + one settings field)
- **Sequencing**: ship alongside GAP-0107 (unverified hint) and GAP-0109 (recovery UI);
  the resume path works server-side even before the frontend change, so the backend can ship
  first and be validated via API tests
- **Rollback**: set `REGISTRATION_ALLOW_RESUME_UNVERIFIED=0` in the environment; no DB
  migration to undo; all existing accounts and sessions are unaffected
- **Risk**: low — the resume path only fires for `pending_verification` accounts; all other
  accounts follow the unchanged code path; rate-limiting (`can_send_verification`,
  `enforce_lockout`) protects against code-spray abuse; the password of the existing
  pending account is not updated by the resume path (the caller's supplied password is
  ignored in favour of the already-stored hash)
