# GAP-0204: `check_and_alert` Never Called — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code in
> `app/services/payment_provider_health.py`, `app/main.py`, and
> `app/services/billing_dunning.py` (background task pattern reference).

## 1. Summary & Classification

**Claim status: Confirmed.** `check_and_alert` is defined at
`app/services/payment_provider_health.py:569` but is never imported or called from any
other file in the codebase. There is no background task, no startup hook in `app/main.py`,
and no API endpoint that invokes it. The function exists purely as dead code.

- **Severity**: HIGH
- **Source ticket**: FIN-014
- **Status**: Open
- **Owning area**: Payment Provider Health Monitoring
- **One-line impact**: Alert thresholds configured by admins (error rate, latency) are
  checked only when explicitly called — which never happens — so payment provider
  degradation (Stripe down, PayPal latency spike) goes undetected until a human opens the
  health dashboard.

**Related tickets**: GAP-0205 (companion: `check_and_alert` builds the alert payload but
never sends it). These two gaps must be fixed together; fixing GAP-0204 without GAP-0205
means the function runs but its output is still discarded. FIN-014 HIGH: `toggle_provider`
enforcement gap is a separate ticket.

## 2. Current-State Investigation (root cause)

### The function

`app/services/payment_provider_health.py:569–592`:

```python
def check_and_alert(provider: str) -> Optional[Dict[str, Any]]:
    """Return alert details if the provider exceeds configured thresholds."""
    prov = normalize_provider(provider)
    status = get_provider_status(prov)
    config = get_provider_config(prov)
    if status["total_success"] + status["total_failure"] == 0:
        return None

    breaches: List[str] = []
    if status["error_rate_bps"] >= _to_int(config["alert_error_rate_threshold"]):
        breaches.append("error_rate")
    if status["avg_latency_ms"] >= _to_int(config["alert_latency_threshold_ms"]):
        breaches.append("latency")
    if not breaches:
        return None
    return {
        "provider": prov,
        "status": status["status"],
        "breaches": breaches,
        "error_rate_bps": status["error_rate_bps"],
        "avg_latency_ms": status["avg_latency_ms"],
        "alert_email": config["alert_email"],
        "at": now_ts(),
    }
```

The function is correct in structure: it reads health datapoints via `get_provider_status`
(which queries the GSI on `payment_provider_health` table), compares against configured
thresholds, and returns a rich dict when thresholds are breached. Crucially, it returns the
dict — it does not act on it (GAP-0205). And this function is never called automatically.

### Background task pattern

The project uses an async loop pattern established by `app/services/billing_dunning.py`:

```python
async def _dunning_loop(interval: int):
    while True:
        try:
            process_dunning_queue()
        except Exception:
            logger.exception("Billing dunning loop failed")
        await asyncio.sleep(interval)

def start_billing_dunning_task() -> None:
    from app.services.job_registry import register_task
    if not S.billing_dunning_enabled:
        ...
    asyncio.ensure_future(_dunning_loop(S.billing_dunning_interval_seconds))
```

The `start_*_task()` function is then registered in `main.py`. This is the exact pattern
the fix should follow.

### Dev vs prod manifestation

In dev the `payment_provider_health` table is empty (no health datapoints seeded by
default), so `check_and_alert` would return `None` anyway. The gap is invisible in dev.
In production, where `record_provider_event` is called from the payment and webhook paths,
the table accumulates real datapoints, thresholds are exceeded during incidents, and
admins expect proactive alerts — which never arrive.

## 3. Impact / Exploit / Blast Radius

- **Availability**: When Stripe begins returning errors at a rate above the configured
  `alert_error_rate_threshold` (default 5%), admins receive no notification. The window
  from first degradation to human detection depends entirely on how often someone opens the
  health dashboard manually. P1 incidents can go undetected for hours.
- **Financial**: Continued payment processing against a degraded provider results in
  failed charges, unhappy users, and potential SLA breach with the payment processor.
- **Data integrity**: No data is corrupted. `check_and_alert` is read-only.
- **No security exposure**: The function does not bypass authorization. The gap is purely
  an operational blind-spot.
- **Compounding with GAP-0205**: Even after this fix (wiring the background call), the
  alert payload is returned but not delivered (GAP-0205). Both fixes are needed for
  end-to-end alert delivery.
- **Blast radius**: All three providers (`stripe`, `paypal`, `ccbill`) are unmonitored.
  Any of them can degrade or go fully down without triggering a notification.

## 4. Fix Design (code-level)

### Step 1 — Implement the background task in `payment_provider_health.py`

Add a `start_provider_health_check_task()` function following the project's standard
background-task pattern:

```python
# app/services/payment_provider_health.py — add at end of file

import asyncio as _asyncio

_HEALTH_CHECK_INTERVAL_SECONDS = 300  # 5 minutes


async def _provider_health_loop(interval: int = _HEALTH_CHECK_INTERVAL_SECONDS) -> None:
    """Periodic background loop: check all providers against alert thresholds.

    Runs every ``interval`` seconds. Calls ``check_and_alert`` for each of
    the three known providers. When a breach is detected, the alert payload
    is passed to ``_dispatch_alert`` (see GAP-0205 fix) for email delivery.
    """
    while True:
        for prov in PROVIDERS:
            try:
                alert = check_and_alert(prov)
                if alert:
                    _dispatch_alert(alert)  # implemented by GAP-0205 fix
                    logger.warning(
                        "provider_health_alert provider=%s status=%s breaches=%s",
                        prov, alert.get("status"), alert.get("breaches"),
                    )
            except Exception:
                logger.exception("provider_health_check failed for %s", prov)
        await _asyncio.sleep(interval)


def start_provider_health_check_task(
    interval: int = _HEALTH_CHECK_INTERVAL_SECONDS,
) -> None:
    """Register the provider health check background task.

    Called from ``app.main.start_application`` at startup. Respects
    ``S.payment_provider_health_enabled``: if the feature flag is off,
    registers the task as disabled in the job registry but does not start it.
    """
    from app.services.job_registry import register_task

    description = (
        "Checks payment provider health thresholds every 5 minutes and "
        "dispatches alerts when error rate or latency exceed configured limits."
    )

    if not S.payment_provider_health_enabled:
        register_task(
            "payment_provider_health_check",
            interval,
            enabled=False,
            description=description,
        )
        logger.info("Payment provider health check disabled (flag off)")
        return

    register_task(
        "payment_provider_health_check",
        interval,
        enabled=True,
        description=description,
    )
    _asyncio.ensure_future(_provider_health_loop(interval))
    logger.info(
        "Payment provider health check started interval_seconds=%d providers=%s",
        interval, PROVIDERS,
    )
```

Note: `_dispatch_alert` is a stub that will be implemented as part of GAP-0205. For GAP-0204
in isolation, `_dispatch_alert` can be a no-op that simply logs: `def _dispatch_alert(alert): logger.info("alert_dispatched %s", alert)`.

### Step 2 — Register the task in `app/main.py`

```python
# app/main.py — add import near other health-check task imports:
from app.services.payment_provider_health import start_provider_health_check_task

# Add event handler near other startup hooks (e.g., after line 806):
app.add_event_handler("startup", start_provider_health_check_task)
```

### Dev/Prod parity (SECOPS-007)

The background loop calls `check_and_alert` → `get_provider_status` → `_query_datapoints`,
which queries `T.payment_provider_health`. In dev this resolves to DynamoDB Local; in
production, to the real DynamoDB table. No mock branch is needed. The loop respects the
existing `S.payment_provider_health_enabled` feature flag (already used by
`record_provider_event`), providing a clean on/off mechanism. The 5-minute interval is
appropriate for both environments; in dev it fires but returns `None` immediately because
no datapoints are seeded, incurring no visible side effects.

The `_HEALTH_CHECK_INTERVAL_SECONDS` constant can be exposed via
`app/core/settings.py` as `S.provider_health_check_interval_seconds` (defaulting to 300)
to allow environment-specific tuning without code changes, consistent with how
`S.billing_dunning_interval_seconds` works.

### Alternatives considered

- **Cron job external to the app**: Kubernetes CronJob or AWS EventBridge rule calling
  `POST /internal/provider-health/check`. Cleaner separation of concerns in microservices.
  Rejected for now because all other polling tasks in this codebase use the in-process
  `asyncio.ensure_future` pattern; changing patterns adds operational complexity.
- **Call `check_and_alert` synchronously from `record_provider_event`**: Would fire after
  every health datapoint write. Too frequent (potentially hundreds of times per minute
  during normal operation); creates unnecessary DDB reads.
- **Webhook-triggered check**: Trigger `check_and_alert` from the billing webhook handler
  when it detects a failed charge. More responsive but misses latency-only degradation and
  adds latency to the webhook path.

### Manual QA steps

1. Apply the code changes.
2. Run `just restart` and tail the uvicorn log: `tail -f .logs/uvicorn.log`.
3. Confirm the startup log line:
   `"Payment provider health check started interval_seconds=300 providers=['stripe', 'paypal', 'ccbill']"`.
4. Seed a Stripe health failure by calling
   `POST /ui/admin/payment-health/stripe/record-event` with `success=false` enough times
   to exceed the threshold (default 5%), then wait ≤ 5 minutes and observe the warning log
   line `provider_health_alert provider=stripe`.
5. Check the job registry endpoint (if present) to confirm `payment_provider_health_check`
   is listed as `enabled=true`.

### Metrics and observability

- Log `provider_health_alert` (structured, with `provider`, `status`, `breaches`) on each
  alert cycle. Monitor this log key in production to detect recurring incidents.
- Optionally add a Prometheus/CloudWatch counter `provider_health_check_total` (labels:
  `provider`, `breached=true/false`) incremented each check cycle.
- Alert on absence of the log line `provider_health_check` for more than 10 minutes as a
  liveness indicator for the loop.

### Rollout and risks

- **Effort**: S (the background loop and startup registration are approximately 40 lines).
- **Risk**: LOW. The loop is read-only (calls `get_provider_status` and `get_provider_config`,
  no writes). If the DDB table is empty or the query fails, the exception is swallowed and
  the loop continues. The only observable side effect is the warning log and (after GAP-0205)
  an email.
- **Rollback**: Set `PAYMENT_PROVIDER_HEALTH_ENABLED=0` in `.env.local` / production env.
  The `start_provider_health_check_task` function respects this flag and skips the
  `ensure_future` call. Or remove the `add_event_handler` line in `main.py`.
- **Sequencing**: Deploy GAP-0204 (wiring the call) first. Deploy GAP-0205 (alert delivery)
  second. The stub `_dispatch_alert` logging is safe in the interim window between the two
  deployments.
