# GAP-0219: Two-phase treasury dissolution is not atomic — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code before writing.

## 1. Summary & Classification

**Plain-English statement**: `app/services/group_treasury.py:dissolve_treasury()` distributes treasury funds to contributors and escrow via a sequence of independent DynamoDB `put_item` and `update_item` calls. The treasury balance is zeroed as the very last operation (line 616). If the process crashes, the network drops, or any intermediate DDB write fails after at least one contributor wallet has been credited, the function leaves the system in a partially-distributed state: some contributors have received their refunds, some have not, and the treasury still shows a non-zero balance. A retry of the entire function double-credits anyone who already received a refund in the first attempt.

**Severity**: HIGH — Financial integrity defect. Double-credit on retry, or a permanent stuck treasury with non-zero balance and partially-distributed funds, causes incorrect wallet balances and erodes user trust. Cross-references SEC-004 (financial atomicity requirement).

**Status**: Open. Source ticket: GROUP-004. Effort: L. Owning area: Group treasury / Billing.

**Claim verdict**: Confirmed with a minor clarification. The ticket states "balance is zeroed last (line:616)". The actual balance-zero `update_item` is at line 616 of `app/services/group_treasury.py`. The ticket's characterisation of the non-atomicity is accurate. The fix direction in the ticket ("use DDB TransactWriteItems for batches of up to 25") is also sound and is elaborated here. No correction to the claim is required.

**Related tickets**: GROUP-004 (source), GAP-0218 (fundraising donations — also treasury-crediting), SEC-004.

## 2. Current-State Investigation (root cause)

### The `dissolve_treasury` function (lines 487–635)

The function performs the following sequence, all as independent DDB operations with no transactional wrapper:

1. **Lines 517–519**: `T.billing.query(...)` — read all contributor records.
2. **Lines 524–574** (per contributor loop): For each contributor with `total_contributed_cents > 0`:
   - `apply_wallet_delta(T.billing, pk_user, share)` — credits the contributor's personal wallet (an `update_item` with `ADD wallet_balance_cents :share`).
   - `T.billing.put_item(...)` — writes a personal ledger credit entry.
   - `T.billing.put_item(...)` — writes a treasury ledger debit entry.
3. **Lines 578–613** (escrow): If any escrow amount remains:
   - `apply_wallet_delta(T.billing, "PLATFORM#ESCROW", escrow_amount)` — credits the escrow wallet.
   - Two more `put_item` calls for ledger entries.
4. **Line 616–620** (balance zero):
   ```python
   T.billing.update_item(
       Key={"pk": pk_group, "sk": WALLET_SK},
       UpdateExpression="SET wallet_balance_cents = :z, updated_at = :t",
       ExpressionAttributeValues={":z": 0, ":t": ts},
   )
   ```

That is 3N + 3 individual DDB writes (where N = number of contributors), none of which are coordinated.

### Failure modes

**Crash after contributor 1 of N is credited but before contributor 2**: Treasury balance is still non-zero. Retry re-queries contributors, finds them all again, and re-credits contributor 1 (double-credit). No idempotency guard exists on `apply_wallet_delta`.

**Crash after all contributors are credited but before the treasury-zero**: The treasury balance reads as non-zero. Any subsequent call to `dissolve_treasury` — e.g., triggered by an admin retry — will recalculate the full `remaining` balance and re-credit every contributor.

**Crash after treasury-zero but before escrow ledger is written**: Escrow wallet balance is correct but ledger entry is missing. Financial reconciliation will be incorrect.

**DDB throttle mid-loop**: If DynamoDB returns a `ProvisionedThroughputExceededException` on the 12th contributor (out of 20), the first 11 are already credited. The error propagates as an unhandled exception (no retry logic in the loop), leaving the function in a partial state.

### Why TransactWriteItems alone is insufficient for large groups

DDB `TransactWriteItems` is limited to 25 items per call. For a group with 30 contributors, a single transaction cannot cover all operations. The ticket's fix suggestion is correct: TransactWriteItems for batches of ≤25 contributors, combined with a saga-pattern `dissolution_state` marker for larger groups.

### Existing idempotency check: absent

`dissolve_treasury` has no guard against being called twice. There is no `status` field on the treasury wallet record to indicate that dissolution has started or completed. A second call on an already-zeroed treasury returns early:
```python
if remaining <= 0:
    return {"ok": True, "refunded_count": 0, "escrow_cents": 0}
```
This only works if the treasury-zero write (step 4) succeeded. If the process crashed before that, `remaining > 0` and the function runs again in full.

## 3. Impact / Exploit / Blast Radius

**Direct financial impact**:
- **Double-credit**: A contributor who should receive $50 receives $100 (or more, on repeated retries). Platform bears the loss.
- **Stuck treasury**: A treasury with a non-zero balance that has already partially distributed cannot be cleanly resolved without manual DDB surgery.
- **Missing ledger entries**: Reconciliation tools see mismatched wallet balances and ledger totals, triggering false-positive fraud alerts or, worse, masking real fraud.

**Blast radius**: All groups that undergo dissolution while the system is under load, experiencing DDB throttling, or subject to any infrastructure disruption. The risk increases with group size (more contributors = more writes = more failure points).

**Attack vector**: This is not directly user-exploitable (dissolution is triggered by admin/root action), but a malicious group admin who times a dissolution during a known maintenance window could trigger partial distribution and then appeal for manual resolution. The impact is primarily operational and financial rather than a direct user-facing exploit.

## 4. Fix Design (code-level)

The fix has three components: (A) a `dissolution_state` marker to enable idempotent retries, (B) TransactWriteItems batching for the core distribution loop, and (C) a saga-pattern resume path for large contributor lists.

### Component A — `dissolution_state` marker

Before any money moves, write a `dissolution_in_progress` marker to the treasury wallet record using a conditional put (fails if dissolution is already in progress or complete):

```python
def _begin_dissolution(pk_group: str, ts: int) -> str:
    """Mark dissolution as in-progress. Returns dissolution_id for saga tracking.
    Raises HTTPException(409) if already in progress or complete."""
    dissolution_id = ulidish()
    try:
        T.billing.update_item(
            Key={"pk": pk_group, "sk": WALLET_SK},
            UpdateExpression=(
                "SET dissolution_state = :state, "
                "dissolution_id = :did, "
                "dissolution_started_at = :t"
            ),
            ConditionExpression=(
                "attribute_not_exists(dissolution_state) OR "
                "dissolution_state = :none_val"
            ),
            ExpressionAttributeValues={
                ":state": "in_progress",
                ":did": dissolution_id,
                ":t": ts,
                ":none_val": "none",
            },
        )
    except ClientError as exc:
        if exc.response["Error"]["Code"] == "ConditionalCheckFailedException":
            raise HTTPException(409, "Dissolution already in progress or complete.")
        raise
    return dissolution_id
```

The conditional write prevents concurrent dissolution attempts. On retry after a crash, the caller must first inspect the current `dissolution_state` and call a `resume_dissolution(dissolution_id)` path.

### Component B — TransactWriteItems batching (≤25 contributors)

Replace the per-contributor loop with batched `transact_write_items` calls. Each batch contains at most 25 items (DDB limit). Crucially, the wallet credit and both ledger entries for a given contributor are written in the same transaction — either all three succeed or none do.

```python
def _batch_transact(items_to_write: list[dict]) -> None:
    """Write up to 25 DDB put/update items in a single transaction."""
    assert len(items_to_write) <= 25, "TransactWriteItems limit is 25"
    T.billing.meta.client.transact_write_items(
        TransactItems=items_to_write
    )
```

Build each contributor's three DDB writes as a `Put`/`Update` triple:

```python
def _contributor_transact_items(
    pk_user: str, pk_group: str, share: int, uid: str,
    ts: int, group_id: str
) -> list[dict]:
    """Return the three TransactItems entries for one contributor refund."""
    credit_entry_id = ulidish()
    debit_entry_id = ulidish()
    return [
        # 1. Wallet credit (conditional: wallet must exist)
        {
            "Update": {
                "TableName": T.billing.name,
                "Key": {"pk": {"S": pk_user}, "sk": {"S": WALLET_SK}},
                "UpdateExpression": "ADD wallet_balance_cents :share",
                "ExpressionAttributeValues": {":share": {"N": str(share)}},
            }
        },
        # 2. Personal ledger entry
        {
            "Put": {
                "TableName": T.billing.name,
                "Item": _to_ddb_item({
                    "pk": pk_user, "sk": ledger_sk(ts, credit_entry_id),
                    "entry_id": credit_entry_id, "ts": ts,
                    "type": "dissolution_refund", "amount_cents": share,
                    "state": "settled", "reason": "Group dissolution refund",
                    "direction": "credit", "category": "refund",
                    "group_id": group_id, "currency": "usd", "created_at": ts,
                }),
                "ConditionExpression": "attribute_not_exists(pk)",  # idempotency
            }
        },
        # 3. Treasury ledger entry
        {
            "Put": {
                "TableName": T.billing.name,
                "Item": _to_ddb_item({
                    "pk": pk_group, "sk": ledger_sk(ts, debit_entry_id),
                    "entry_id": debit_entry_id, "ts": ts,
                    "type": "dissolution_return", "amount_cents": share,
                    "state": "settled", "reason": f"Dissolution refund to {uid}",
                    "direction": "debit", "category": "dissolution_return",
                    "actor_user_id": uid, "currency": "usd", "created_at": ts,
                }),
                "ConditionExpression": "attribute_not_exists(pk)",
            }
        },
    ]
```

The `ConditionExpression: attribute_not_exists(pk)` on ledger entries makes them idempotent — a retry with the same `entry_id` will fail the condition and `transact_write_items` will raise `TransactionCanceledException` with the cancellation reason `ConditionalCheckFailed` only for that item. This signals "already written" and can be safely ignored.

### Component C — Saga pattern for N > 8 contributors

With 3 items per contributor, 8 contributors exhaust the 25-item limit (8*3 = 24 items, plus the treasury-zero write = 25). For N > 8, process contributors in batches of 8, recording completed batches in a `dissolution_progress` attribute:

```python
# On the WALLET_SK record, store progress:
# dissolution_completed_user_ids: ["uid1", "uid2", ...]
# dissolution_state: "in_progress" | "completing" | "complete"
```

After each batch of 8 completes, `update_item` appends their `user_id`s to `dissolution_completed_user_ids`. On retry, skip contributors whose `user_id` is already in that list.

The final batch (which zeros the balance) is also a transaction: wallet zero + escrow credit + escrow ledger + state marker set to `complete` — all in one `transact_write_items` call.

### Updated `dissolve_treasury` skeleton

```python
def dissolve_treasury(group_id: str) -> Dict[str, Any]:
    balance_info = get_treasury_balance(group_id)
    remaining = balance_info["balance_cents"]
    if remaining <= 0:
        return {"ok": True, "refunded_count": 0, "escrow_cents": 0}

    ts = now_ts()
    pk_group = _group_pk(group_id)
    dissolution_id = _begin_dissolution(pk_group, ts)   # A: marker (conditional)

    # ... calculate shares as before ...

    completed_uids: set[str] = set()
    batch: list[dict] = []

    for contributor in contributors:
        uid = contributor.get("user_id", "")
        if uid in completed_uids:
            continue
        share = ...
        if share <= 0:
            continue
        batch.extend(_contributor_transact_items(user_pk(uid), pk_group, share, uid, ts, group_id))
        if len(batch) >= 24:              # flush when near limit
            _batch_transact(batch)        # B: atomic batch
            completed_uids.add(uid)
            _record_progress(pk_group, completed_uids)  # C: saga checkpoint
            batch = []

    # Final transaction: remaining contributors + escrow + balance-zero + state=complete
    if escrow_amount > 0:
        batch.extend(_escrow_transact_items(pk_group, escrow_amount, group_id, ts))
    batch.append(_treasury_zero_item(pk_group, ts, dissolution_id))   # zeroing as last item in final tx
    _batch_transact(batch)
    return {"ok": True, ...}
```

### Dev/Prod parity (SECOPS-007)

`T.billing` targets DynamoDB Local in dev and AWS DynamoDB in prod. `transact_write_items` is supported by DynamoDB Local (the Java implementation supports all TransactWrite operations). No `if S.dev_mode` branch is needed. The fix works identically in both environments.

def test_no_double_credit_on_retry(moto_ddb, group_with_three_contributors):
    """If dissolution fails mid-loop, retry must not double-credit contributors."""
    group_id, contributor_ids = group_with_three_contributors
    from app.services.group_treasury import dissolve_treasury
    from app.services.billing_shared import get_wallet_balance, user_pk
    from app.core.tables import T

    # Record balances before dissolution
    before = {uid: get_wallet_balance(T.billing, user_pk(uid)) for uid in contributor_ids}

    # Run dissolution (succeeds cleanly with new atomic implementation)
    dissolve_treasury(group_id)

    # Record balances after
    after = {uid: get_wallet_balance(T.billing, user_pk(uid)) for uid in contributor_ids}

    # Verify each contributor was credited exactly once
    for uid in contributor_ids:

    # because balance is now 0 (early return) OR marker blocks it
    dissolve_treasury(group_id)  # should return early or raise 409
    after_retry = {uid: get_wallet_balance(T.billing, user_pk(uid)) for uid in contributor_ids}
    assert after_retry == after, "Retry must not double-credit contributors"

### Rollout

- **Effort**: L (large) — The transact-write batching and saga-state machinery require careful implementation and thorough testing. Estimated 2–3 engineering days.
- **Backward compat**: Existing treasury records do not have `dissolution_state`. The conditional write in `_begin_dissolution` uses `attribute_not_exists(dissolution_state) OR dissolution_state = :none_val`, so old records without the attribute satisfy the condition and dissolution proceeds normally.
- **Migration**: No schema migration. The new attributes are written on first dissolution.
- **Rollback**: The non-atomic implementation can be restored by reverting `dissolve_treasury`. The `dissolution_state` attribute on existing records should be cleared if a rollback occurs mid-saga (add a ROOT endpoint `DELETE /ui/root/groups/{id}/dissolution-state` for this).
- **Risk**: Medium. The `transact_write_items` API has a stricter throughput profile than individual `put_item` calls. For groups with many contributors, dissolution may be slower (more round trips). Test with production-scale contributor counts. For groups with > ~100 contributors, consider an async/background dissolution job instead of a synchronous request handler.
- **Sequencing**: GAP-0219 is independent of GAP-0218. Can be deployed in isolation. Cross-reference SEC-004 for any additional security review requirements around financial transaction atomicity.
