# GAP-0232: Dangerous-Rule Block Covers Only SSH Port 22; VNC (5900–5999), RDP (3389), and IPv6 (::/0) Are Not Blocked — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code; file:line citations are from
> the live codebase at `/home/ubuntu/testlogon`.

## 1. Summary & Classification

**Gap**: `app/services/security_groups.py` contains `is_dangerous_rule()`, which
blocks only one specific threat: `0.0.0.0/0` → TCP port 22 (SSH). The INFRA-009
ticket design mandates that the same guard also reject rules opening VNC ports
(5900–5999), RDP (port 3389), and any rule sourced from `::/0` (IPv6 any-host).
Those three cases are completely absent from the current implementation.

**Severity**: HIGH. Owning area: Infrastructure / Security Groups (INFRA-009).
**Status**: Open. **Source ticket**: INFRA-009. **Effort**: S.

**Claim accuracy**: Confirmed. `app/services/security_groups.py` lines 145–157
contain the complete text of `is_dangerous_rule`. No RDP, VNC, or IPv6 checks appear
anywhere in the file.

**Impact**: A user can create a security group rule that exposes VNC or RDP to the
public internet, or opens any TCP/UDP port from the IPv6 wildcard address. The
platform guard designed to prevent this is silently bypassed.

**Related tickets**: INFRA-009 (parent), SECOPS-007 (dev/prod parity), GAP-0231
(compute timeline, separate concern).


## 2. Current-State Investigation (root cause)

### The guard — exactly one condition checked

`app/services/security_groups.py` lines 145–157:

```python
def is_dangerous_rule(rule: Dict[str, Any]) -> bool:
    """True if the rule opens SSH (port 22) to 0.0.0.0/0 inbound over TCP."""
    source = rule.get("source", "")
    protocol = rule.get("protocol")
    direction = rule.get("direction", "inbound")
    port_from = int(rule.get("port_from", 0) or 0)
    port_to   = int(rule.get("port_to",   0) or 0)
    return (
        source == "0.0.0.0/0"
        and direction == "inbound"
        and protocol == "tcp"
        and port_from <= 22 <= port_to
    )
```

The function is called at line 169 inside `_prepare_rule`:

```python
if S.security_groups_block_dangerous_rules and is_dangerous_rule(rule):
    raise DangerousRule(
        "SSH (port 22) open to 0.0.0.0/0 is not recommended. "
        "Use 'platform_only' or a specific CIDR."
    )
```

`S.security_groups_block_dangerous_rules` (settings.py line 2065) defaults `True`,
so the guard is active — but it only checks one of four required conditions.

### Missing condition 1: RDP (TCP 3389)

`port_from <= 3389 <= port_to` is never evaluated. A rule such as
`{protocol: "tcp", port_from: 3389, port_to: 3389, source: "0.0.0.0/0",
direction: "inbound"}` passes `is_dangerous_rule` and is stored in DynamoDB
without error.

### Missing condition 2: VNC (TCP 5900–5999)

VNC uses a range. A rule opening `port_from=5900, port_to=5999` with
`source="0.0.0.0/0"` is not caught. The current check only tests whether port 22
falls inside the range; it does not test whether the range overlaps any VNC port.

The correct test for VNC is: `port_from <= 5999 and port_to >= 5900` — i.e., any
range that intersects `[5900, 5999]`.

### Missing condition 3: IPv6 any-host (::/0)

`source == "0.0.0.0/0"` is the only wildcard tested. The string `"::/0"` compares
unequal, so IPv6-wildcard rules for any port — including SSH — pass the guard
unchanged. `normalize_cidr` (called at line 138) accepts `::/0` as a valid CIDR,
so the value is well-formed and stored successfully.

### Dev vs prod parity — guard applies to DDB mock only

In dev mode the rules are stored in DynamoDB Local and never translated to real AWS
VPC security groups. In production they would be applied via the EC2
`AuthorizeSecurityGroupIngress` API. The guard lives in the service layer
(before the mock/real branch), so it correctly applies to both paths — but only for
the single condition it currently checks.


## 3. Impact / Exploit / Blast Radius

**Threat model**: A user creates a security group with a rule that opens VNC
(port 5901) or RDP (port 3389) to `0.0.0.0/0`. The rule is stored without
objection. When the security group is attached to an EC2 instance at launch time
(`launch_instance`, ec2_launcher.py line 147 calls `resolve_for_launch`), the
permissive rule is associated with the instance record in DynamoDB. In production
that would translate directly to an AWS VPC `AuthorizeSecurityGroupIngress` API call
opening the port to the internet.

**Concrete exploit walk-through**:
1. Authenticated user calls `POST /ui/compute/security-groups` to create an SG.
2. User calls `POST /ui/compute/security-groups/{sg_id}/rules` with body:
   `{"protocol":"tcp","direction":"inbound","port_from":3389,"port_to":3389,
   "source":"0.0.0.0/0","action":"allow"}`.
3. Server calls `_prepare_rule` → `is_dangerous_rule`. Current check:
   `port_from <= 22 <= port_to` evaluates `22` against the range `[3389, 3389]` →
   `False`. Guard is bypassed. Response: 201.
4. User calls `POST /ui/compute/ec2/instances` with `security_group_id=<sg_id>`.
5. Instance launches with the RDP-open rule attached. In production VPC context,
   port 3389 is reachable from any IP on the internet.

**IPv6 variant**: Steps 2–5 with `source: "::/0"`. The check
`source == "0.0.0.0/0"` evaluates to `False` for `::/0`. Even the original SSH
guard is bypassed: a rule opening SSH to `::/0` is not caught by the current code.

**VNC range bypass**: A rule with `port_from=5900, port_to=5999` results in
`port_from <= 22 <= port_to` → `5900 <= 22` → `False`. The VNC range is not caught.
VNC has a well-documented history of authentication bypasses and unencrypted session
traffic; exposing it publicly is equivalent to exposing the desktop.

**Worst case in multi-tenant SaaS**: In a hosted platform where multiple organizations
share the compute infrastructure, a malicious tenant crafts permissive rules. This
either (a) in dev/mock mode: stores a rule that misleads operators about the platform's
security posture, or (b) in production: creates a real VPC rule that exposes the EC2
instance to public internet attacks. RDP vulnerabilities such as BlueKeep (CVE-2019-0708)
and DejaBlue (CVE-2019-1182) and VNC remote code execution vulnerabilities make
public exposure of ports 3389 and 5900–5999 a critical risk.

**Retroactive stored rules**: Existing rules created before the fix are not
re-validated. Any RDP/VNC/IPv6 rule stored today remains in DynamoDB after the fix
is deployed. See section 4 for the retroactive scan option.


## 4. Fix Design (code-level)

### 4.1 Extend `is_dangerous_rule` — preferred approach (simple, configurable)

Replace lines 145–157 in `app/services/security_groups.py`:

```python
# Dangerous port ranges: (low, high) inclusive.  Any rule whose port range
# overlaps one of these AND whose source is a public wildcard is blocked.
_DANGEROUS_PORT_RANGES: list[tuple[int, int]] = [
    (22,   22),          # SSH
    (3389, 3389),        # RDP
    (5900, 5999),        # VNC
]

_DANGEROUS_SOURCES: frozenset[str] = frozenset({"0.0.0.0/0", "::/0"})


def is_dangerous_rule(rule: Dict[str, Any]) -> bool:
    """True if the rule opens a sensitive port range to the public internet
    (IPv4 or IPv6 wildcard) inbound over TCP.

    Covers: SSH (22), RDP (3389), VNC (5900-5999), and any IPv6 wildcard source.
    """
    source    = rule.get("source", "")
    protocol  = rule.get("protocol")
    direction = rule.get("direction", "inbound")
    port_from = int(rule.get("port_from", 0) or 0)
    port_to   = int(rule.get("port_to",   0) or 0)

    if source not in _DANGEROUS_SOURCES:
        return False
    if direction != "inbound":
        return False
    if protocol not in ("tcp", "all"):
        return False

    for range_low, range_high in _DANGEROUS_PORT_RANGES:
        # Ranges overlap when: port_from <= range_high AND port_to >= range_low
        if port_from <= range_high and port_to >= range_low:
            return True

    return False
```

Update the error message inside `_prepare_rule` (line 170) to be generic:

```python
raise DangerousRule(
    "This rule opens a sensitive port (SSH/RDP/VNC) to the public internet "
    "(0.0.0.0/0 or ::/0). Use 'platform_only' or a specific CIDR."
)
```

### 4.2 Configurable blocklist via settings (optional hardening)

For operator flexibility, expose `_DANGEROUS_PORT_RANGES` as an env var
`SG_DANGEROUS_PORT_RANGES` (comma-separated `low:high` pairs). Default value
covers SSH, RDP, VNC as above. The service reads and parses this at startup.
This is optional for the initial fix; the hard-coded list covers the immediate gap.

### 4.3 Dev/Prod parity (SECOPS-007)

`is_dangerous_rule` is called inside `_prepare_rule` which executes before any
mock/real branch. No change required for parity — the guard already applies on both
paths. The IPv6 fix is equally effective in DDB-local dev mode and in the production
VPC path.

### Alternatives considered

- **Separate check functions per port/source**: More readable but duplicates the
  `direction` and `protocol` checks; rejected in favour of the range-overlap table.
- **Allowlist instead of blocklist**: Would require enumerating every permissible
  (port, source) combination; too broad for a simple guard, better suited to a
  future policy-as-code system.
- **Only block `::/0` for SSH**: Partial. Keeping parity with the IPv4 guard for
  all sensitive ports is more consistent and easier to audit.


## 5. Testing, Verification & Rollout

```python

@pytest.mark.parametrize("rule", [
    # Original: SSH over IPv4 wildcard (must still pass)

     "source":"0.0.0.0/0"},
    # NEW: RDP over IPv4

     "source":"0.0.0.0/0"},
    # NEW: VNC (single port) over IPv4

     "source":"0.0.0.0/0"},
    # NEW: VNC (full range) over IPv4
    {"protocol":"tcp","direction":"inbound","port_from":5900,"port_to":5999,
     "source":"0.0.0.0/0"},
    # NEW: SSH over IPv6 wildcard
    {"protocol":"tcp","direction":"inbound","port_from":22,"port_to":22,
     "source":"::/0"},
    # NEW: RDP over IPv6 wildcard
    {"protocol":"tcp","direction":"inbound","port_from":3389,"port_to":3389,
     "source":"::/0"},
    # NEW: wide range that overlaps VNC
    {"protocol":"tcp","direction":"inbound","port_from":5000,"port_to":6000,
     "source":"0.0.0.0/0"},
])
def test_is_dangerous_rule_blocked(rule):
    assert is_dangerous_rule(rule) is True


# --- CASES THAT MUST BE ALLOWED ---

@pytest.mark.parametrize("rule", [
    # Specific CIDR — not public
    {"protocol":"tcp","direction":"inbound","port_from":22,"port_to":22,
     "source":"10.0.0.0/8"},
    # Outbound SSH — direction not inbound
    {"protocol":"tcp","direction":"outbound","port_from":22,"port_to":22,
     "source":"0.0.0.0/0"},
    # HTTP/HTTPS — not a sensitive port
    {"protocol":"tcp","direction":"inbound","port_from":443,"port_to":443,
     "source":"0.0.0.0/0"},
    # UDP RDP — protocol not tcp
    {"protocol":"udp","direction":"inbound","port_from":3389,"port_to":3389,
     "source":"0.0.0.0/0"},
    # platform_only source
    {"protocol":"tcp","direction":"inbound","port_from":22,"port_to":22,
     "source":"platform_only"},
])
def test_is_dangerous_rule_allowed(rule):
    assert is_dangerous_rule(rule) is False
```

**Before the fix**: the four `NEW` blocked cases return `False` — tests fail.
**After the fix**: all assertions pass.

### Retroactive scan for existing dangerous rules

A one-time migration script should scan `T.security_groups` for stored rule items
and flag any that satisfy the updated `is_dangerous_rule`. The script should not
auto-delete (user-created rules should require operator confirmation) but should
produce a report for the security team. This is out of scope for the initial fix
but should be included in the rollout plan.

```python
# scripts/scan_dangerous_rules.py (one-time script, not production code)
from app.services.security_groups import is_dangerous_rule
# Scan T.security_groups for all RULE# SK items
# For each: call is_dangerous_rule on the stored rule dict
# Output: list of (user_sub, sg_id, rule_id, protocol, port_from, port_to, source)
```

### Observability

The existing `DangerousRule` exception is caught at the router level and returned
as an HTTP 400 error response. No new metrics are required initially; the existing
error counter for `POST /ui/compute/security-groups/*/rules` will capture rejections.

For production hardening, add a tagged counter:
`security_group_dangerous_rule_blocked_total{port_class=ssh|rdp|vnc,source_type=ipv4_any|ipv6_any}`.
This allows alerting if a surge of dangerous rule attempts is observed (possible
automated probe of the platform).

### Rollout

- **Effort**: S (< 30 lines of logic changed; test file extended by ~40 lines).
- **Risk**: Low. The only behavioral change is that previously-accepted VNC/RDP/IPv6
  rules are now rejected at rule-creation time. No existing stored rules are modified
  or deleted by deploying this fix.
- **Backward compatibility**: Rules already stored in DynamoDB are not re-validated
  on read. They remain effective in dev/mock mode. In production, a retroactive scan
  (above) should be run to identify and remediate existing dangerous rules.
- **Rollback**: Revert the changes to `is_dangerous_rule` and the error message. No
  data migration is needed.
- **Sequencing**: Independent of all other GAPs. Can be merged and deployed
  immediately. The retroactive scan can be run as a follow-up operation after
  deployment.
