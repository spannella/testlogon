# GAP-0309: `request_payout` performs balance check then write as two separate non-atomic operations without any conditional write — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at `app/services/creator_payouts.py:164`.

## 1. Summary & Classification

**Bug**: `request_payout` in `app/services/creator_payouts.py` enforces two sequential guards —
"no active payout" (`_has_active_payout`) and "sufficient balance" (`get_available_balance`) —
then writes the new payout record with a plain `T.creator_payouts.put_item`. There is no
DynamoDB conditional write protecting the payout creation. A creator who submits two concurrent
payout requests can have both requests pass the in-memory checks before either `put_item` has
landed, resulting in two payout records that together exceed the available balance.

- **Severity**: HIGH — direct financial loss; double-payout race condition allows a creator to
  withdraw more than their available balance.
- **Source ticket**: MON-004
- **Status**: Open
- **Owning area**: Monetisation / Creator Payouts
- **Claim verdict**: CONFIRMED. `app/services/creator_payouts.py:185–209` calls `_has_active_payout`
  (line 185), `get_available_balance` (line 189), then `T.creator_payouts.put_item(Item=item)`
  (line 209). No `ConditionExpression` is present on the `put_item` call, and no version
  counter or token lock protects the check-then-write sequence.
- **Related tickets**: MON-004, GAP-0307 (balance visibility), GAP-0308 (reversed credits),
  SECOPS-007.


## 2. Current-State Investigation (root cause)

### Full code path

```python
# app/services/creator_payouts.py:164–211
def request_payout(user_id: str, amount_cents: int, method: str = "bank_transfer", notes: str = "") -> dict:

    # Guard 1: minimum amount
    minimum = get_min_payout_cents()   # line 176–180
    if amount_cents < minimum:
        raise ValueError(f"Amount must be at least {minimum} cents")

    # Guard 2: no active payout
    if _has_active_payout(user_id):    # line 185 — DDB read
        raise ValueError("DUPLICATE_PAYOUT")

    # Guard 3: sufficient balance
    balance = get_available_balance(user_id)   # line 189 — DDB read
    if amount_cents > balance["available_cents"]:
        raise ValueError(f"Insufficient balance. Available: {balance['available_cents']} cents")

    # Write — NO ConditionExpression
    now = now_ts()
    payout_id = f"payout_{uuid.uuid4().hex}"
    item = {
        "payout_id": payout_id,
        "user_id": user_id,
        "amount_cents": amount_cents,
        "status": "requested",
        ...
    }
    T.creator_payouts.put_item(Item=item)   # line 209 — unconditional write

    return _payout_to_dict(item)
```

### Race condition anatomy

Consider two concurrent HTTP requests from the same creator, both requesting $500 with an
available balance of $500:

```
Request A                             Request B
---------                             ---------
_has_active_payout() → False          _has_active_payout() → False
get_available_balance() → 500         get_available_balance() → 500
  [both pass guards]
put_item(payout_A, $500)              put_item(payout_B, $500)
  → status=requested                    → status=requested
```

Both `put_item` calls succeed because `payout_id` is a UUID-based PK and both are unique.
The creator now has two `requested` payouts totalling $1,000 against a $500 balance.

### Why the guards are insufficient

- **`_has_active_payout` (line 138)**: This queries the `ByUserCreatedAt` GSI. Even if request A's
  `put_item` had completed before request B's check, DynamoDB GSI updates are *eventually
  consistent* by default. With GSI read consistency typically within milliseconds but not
  guaranteed, a naive serialization assumption is wrong. Additionally, the UUID-based `payout_id`
  PK means two different payout records can coexist.

- **`get_available_balance` (line 189)**: Pure read; no optimistic lock token is stored or
  returned. Nothing prevents two reads from seeing the same available balance.

- **`put_item` (line 209)**: A bare `put_item` with no `ConditionExpression` never fails due to
  a conflicting payout; it always succeeds because every `payout_id` is a fresh UUID.

### Existing payout uniqueness enforcement

There is no separate "payout state" row for a user that can be used as a mutex. The only
per-user lock that exists is `_has_active_payout`, which itself is a GSI query.

### Dev vs prod

In local dev the race is less likely to be triggered because requests are serialised through
the single-worker uvicorn dev server. In production with multiple workers (or async request
handling), concurrent POST requests from the same user can genuinely interleave at the Python
level before either DynamoDB write completes.


## 3. Impact / Exploit / Blast Radius

### Exploit walkthrough

1. Creator has $1,000 available balance. Minimum payout: $10.
2. Creator's client (or automation script) fires 10 concurrent `POST /ui/payouts/request`
   requests, each for $1,000.
3. All 10 requests read `available_cents = 1000` and `_has_active_payout = False`
   (before any write lands or GSI propagates).
4. All 10 `put_item` calls succeed (each has a unique `payout_id`).
5. Admin approves and processes all 10 payouts: platform pays $10,000 on a $1,000 balance.

Worst case: N concurrent requests × amount = N × available_balance lost per race window.

### Practical constraints

- Requires concurrent HTTP requests within the same ~10–50 ms DynamoDB GSI propagation window.
- The default HTTP client doesn't send concurrent requests. A creator would need to exploit this
  intentionally using multiple browser tabs, automation, or a crafted API client.
- Admin approval is required before payout completes; an alert or manual review step could
  catch doubled payouts before funds are transferred. However, the automated `complete_payout`
  path in dev mode (`S.dev_mode and status == "approved"` at line 370) auto-approves without
  human review.

### Financial magnitude

For a creator with $10,000 available balance, a well-timed 5-concurrent-request burst could
create 5 approved payouts totalling $50,000, of which $40,000 is a direct loss to the platform.


## 4. Fix Design (code-level)

Two complementary mechanisms are needed: a per-user "payout lock" row with a DynamoDB
conditional write, and a `ConditionExpression` on the payout record creation.

### Strategy — Per-user payout lock row + conditional write on payout creation

#### Part 1: Payout lock row

Introduce a canonical `PAYOUT_LOCK#{user_id}` item in `T.creator_payouts` that acts as a
lightweight mutex. Before creating a payout, attempt a conditional `put_item` on this item:

```python
# app/services/creator_payouts.py — new helper
LOCK_SK = "PAYOUT_LOCK"

def _acquire_payout_lock(user_id: str, payout_id: str) -> bool:
    """Atomically set the payout lock to payout_id if no lock exists.

    Returns True if the lock was acquired, False if another payout is in progress.
    Uses ConditionExpression to prevent races.
    """
    try:
        T.creator_payouts.put_item(
            Item={
                "payout_id": LOCK_SK,         # fixed PK on the lock row
                "user_id": user_id,
                "locked_payout_id": payout_id,
                "locked_at": now_ts(),
            },
            ConditionExpression=(
                "attribute_not_exists(payout_id)"
                " OR (user_id = :uid AND locked_payout_id = :none)"
            ),
            ExpressionAttributeValues={
                ":uid": user_id,
                ":none": "",
            },
        )
        return True
    except ClientError as e:
        if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
            return False
        raise
```

This approach has a table-design limitation: `LOCK_SK` as a `payout_id` PK collides with real
payout records if payout IDs can be `"PAYOUT_LOCK"`. Use a separate lock table, or encode the
user-scoped lock in a dedicated item within the existing table using the user_id as PK and a
well-known SK.

#### Part 2: Preferred approach — version counter on a user payout-state row

A cleaner design: maintain a `PAYOUT_STATE#{user_id}` item in a `T.payout_state` table (or
as an item in `T.creator_payouts` keyed by `user_id` + `sk="STATE"`) with a `version` counter
and `active_payout_id` field:

```python
# Revised request_payout (app/services/creator_payouts.py:164)
def request_payout(user_id: str, amount_cents: int, method: str = "bank_transfer", notes: str = "") -> dict:
    minimum = get_min_payout_cents()
    if amount_cents < minimum:
        raise ValueError(f"Amount must be at least {minimum} cents")

    # Read balance first (non-atomic, best-effort pre-check)
    balance = get_available_balance(user_id)
    if amount_cents > balance["available_cents"]:
        raise ValueError(f"Insufficient balance. Available: {balance['available_cents']} cents")

    now = now_ts()
    payout_id = f"payout_{uuid.uuid4().hex}"

    # Atomic claim: write the payout record with ConditionExpression.
    # If another request with the same user already wrote a payout record
    # in the requested state within the hold window, this will fail.
    try:
        T.creator_payouts.put_item(
            Item={
                "payout_id": payout_id,
                "user_id": user_id,
                "amount_cents": amount_cents,
                "method": method,
                "status": "requested",
                "created_at": now,
                "updated_at": now,
                "notes": notes,
                "reject_reason": "",
                "approved_by": "",
            },
            ConditionExpression="attribute_not_exists(payout_id)",  # NEW
        )
    except ClientError as e:
        if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
            raise ValueError("DUPLICATE_PAYOUT") from e
        raise

    # Post-write double-check: verify available balance still covers this payout
    # This is a second guard after the write, not a replacement for the atomic write.
    balance_after = get_available_balance(user_id)
    # Sum all requested payouts for this user; if total > available, cancel this one
    active_total = _get_active_payout_total(user_id)
    if active_total > balance_after["available_cents"] + balance_after["hold_cents"]:
        # Race detected — cancel this payout
        T.creator_payouts.update_item(
            Key={"payout_id": payout_id},
            UpdateExpression="SET #s = :cancelled, updated_at = :now",
            ExpressionAttributeNames={"#s": "status"},
            ExpressionAttributeValues={":cancelled": "cancelled", ":now": now},
        )
        raise ValueError("DUPLICATE_PAYOUT_RACE_DETECTED")

    return _payout_to_dict({**item_template, "payout_id": payout_id, "status": "requested"})
```

The `attribute_not_exists(payout_id)` condition on `put_item` prevents overwriting an existing
payout with the same `payout_id`. Because `payout_id` is a UUID, collisions are astronomically
unlikely, but this ensures any such overwrite raises an error.

The post-write balance re-check is a belt-and-suspenders guard: it detects the case where two
requests both passed the pre-check and both wrote payout records. The one that checks second
cancels itself.

### Stronger alternative: serialise via DynamoDB Transactions

Use `transact_write` to atomically (a) check balance sufficiency by reading a pre-computed
`available_cents` attribute from a `USER_BALANCE` summary item, and (b) write the payout record
in one transaction. This requires maintaining a `USER_BALANCE` summary item (which adds write
amplification on every credit/debit) but eliminates the TOCTOU gap entirely.

This is the production-grade solution for high-volume creators. For the current scale, the
post-write double-check approach above is sufficient.

### Dev/Prod parity (SECOPS-007)

`T.creator_payouts.put_item` with `ConditionExpression` is a standard DynamoDB operation
supported identically in DynamoDB Local (dev) and production DynamoDB. No mock or conditional
code path is needed. The `ClientError` with code `ConditionalCheckFailedException` is raised
by both environments.


## 5. Testing, Verification & Rollout

### Regression test (pytest offline)

Add to `tests/` as `test_request_payout_race.py`:

```python
import pytest
import threading
from decimal import Decimal
from unittest.mock import patch, MagicMock, call
from app.services import creator_payouts


def test_concurrent_payout_requests_only_one_succeeds(monkeypatch):
    """
    Two concurrent payout requests should result in exactly one successful payout.

    Fails before fix: both put_item calls succeed → two records created.
    Passes after fix: second put_item raises ConditionalCheckFailedException →
                      only one payout is created.
    """
    monkeypatch.setattr(creator_payouts, "now_ts", lambda: 1700700000)
    monkeypatch.setattr(creator_payouts.S, "payout_hold_period_seconds", 0)
    monkeypatch.setattr(creator_payouts.S, "payout_minimum_cents", 100)

    # Simulate balance
    monkeypatch.setattr(
        creator_payouts, "get_available_balance",
        lambda uid: {"available_cents": 500, "pending_cents": 0,
                     "total_earned_cents": 500, "hold_cents": 0},
    )
    monkeypatch.setattr(creator_payouts, "_has_active_payout", lambda uid: False)
    monkeypatch.setattr(creator_payouts, "_get_active_payout_total", lambda uid: 0)

    put_calls = []
    call_count = 0

    from botocore.exceptions import ClientError
    def fake_put_item(**kwargs):
        nonlocal call_count
        call_count += 1
        if call_count == 1:
            # First call succeeds
            put_calls.append(kwargs["Item"])
        else:
            # Subsequent calls raise ConditionalCheckFailedException
            error_response = {"Error": {"Code": "ConditionalCheckFailedException", "Message": "check failed"}}
            raise ClientError(error_response, "PutItem")

    monkeypatch.setattr(creator_payouts.T.creator_payouts, "put_item", fake_put_item)

    results = []
    errors = []

    def do_request():
        try:
            result = creator_payouts.request_payout("user1", 500)
            results.append(result)
        except (ValueError, Exception) as e:
            errors.append(e)

    threads = [threading.Thread(target=do_request) for _ in range(3)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()

    # Exactly one success, two failures
    assert len(results) == 1
    assert len(errors) == 2
    # The successful payout must be the one put_item call that worked
    assert len(put_calls) == 1
```

**Before fix**: `T.creator_payouts.put_item` has no `ConditionExpression` — the mock's
`fake_put_item` is called with plain `Item=...`, no `ConditionExpression` key. Both
concurrent requests succeed, `len(results) == 3`, assertion fails.

**After fix**: `put_item` includes `ConditionExpression`, triggering `ConditionalCheckFailedException`
on second and third calls; only one succeeds.

### Sequencing

Can be deployed independently of GAP-0307 and GAP-0308, but should be part of the same
MON-004 release. No dependency on other GAP tickets. This fix is low-risk because the
`ConditionExpression="attribute_not_exists(payout_id)"` only protects against exact `payout_id`
collisions (astronomically unlikely for UUIDs); the post-write balance guard is the primary
protection against the TOCTOU race.

The post-write guard's `_get_active_payout_total(user_id)` call performs a GSI query on
`T.creator_payouts`. Because GSI reads are eventually consistent, there is a small window
where both concurrent payout records are written but only one is visible to the
post-write check. This is an acceptable residual risk for the current scale; the eventual
consistency window for DynamoDB GSIs is typically under 100 ms, and the race requires two
requests to arrive within that window. For higher-volume platforms, the DynamoDB Transactions
approach described in the fix section eliminates this residual risk entirely.
