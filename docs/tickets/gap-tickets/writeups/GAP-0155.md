# GAP-0155: afl_ref Cookie Set with Secure=True in Dev — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at app/routers/affiliate_links.py:204 and app/core/settings.py.

## 1. Summary & Classification

**Plain-English statement:** The affiliate redirect endpoint (`GET /r/{tracking_code}` in `app/routers/affiliate_links.py`) sets the `afl_ref` attribution cookie without a `secure` parameter. When Starlette's `set_cookie` is called without `secure=...`, it defaults to `secure=False`. The ticket claims the cookie is set with `Secure=True` — this specific claim is **inaccurate**. However, the real gap is the absence of `secure=not S.dev_mode`: in production (HTTPS) the cookie should be `Secure=True`, but currently it is always `Secure=False`, meaning it will be sent over HTTP connections in production and is not as hardened as it should be. In dev (HTTP), the cookie is set and works correctly today (because `Secure=False` allows HTTP delivery). The claim's direction is inverted: the production path is under-secured, not the dev path.

- **Severity:** HIGH (reduced from the ticket's concern, but the prod direction is a real security weakness)
- **Source ticket:** CREATOR-004
- **Status:** Open
- **Owning area:** Affiliate Links / Cookie Security
- **Claim verdict:** **Claim corrected.** The ticket states `secure=True` is set in dev. The actual code at `app/routers/affiliate_links.py:204–211` sets no `secure` argument, so Starlette defaults to `secure=False` in all environments. The fix direction stated in the ticket (`set secure=not S.dev_mode`) is still correct and necessary — but to fix the production exposure, not the dev exposure.

**Related tickets:** GAP-0154 (conversion attribution — the cookie must be reliably set for attribution to work), CREATOR-004, SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (Root Cause)

### Actual code at the cited location

`app/routers/affiliate_links.py:204–211`:
```python
response.set_cookie(
    key="afl_ref",
    value=tracking_code,
    max_age=S.affiliate_cookie_duration_days * 86400,
    httponly=True,
    samesite="lax",
    path="/",
)
```

No `secure` parameter is passed. Starlette's `Response.set_cookie` signature has `secure: bool = False` as its default, so the `Set-Cookie` header emitted is:

```
Set-Cookie: afl_ref=<code>; Max-Age=2592000; Path=/; HttpOnly; SameSite=lax
```

The `Secure` attribute is absent.

### What the ticket claim expected to find

The ticket states the cookie is set with `Secure=True` in dev. This is not the case. The confusion may stem from the fact that:
1. Other cookies in the codebase (session cookies, CSRF cookies) use `S.ui_cookie_secure` which is `False` by default in dev — the distinction between "missing secure" and "secure=False" was conflated.
2. A prior iteration of the affiliate redirect code may have included `secure=True` explicitly, which was removed.

Regardless of the discrepancy, the fix direction in the ticket is correct and necessary.

### The `ui_cookie_secure` pattern (the model to follow)

Session cookies in `app/services/sessions.py:82–106` use `secure=S.ui_cookie_secure`:
```python
response.set_cookie(
    key="ui_session",
    value=session_id,
    ...
    secure=S.ui_cookie_secure,
    ...
)
```

`app/core/settings.py:92`:
```python
ui_cookie_secure: bool = os.environ.get("UI_COOKIE_SECURE", "0") not in ("0", "false", "False")
```

This setting defaults to `False` (dev-safe) and is set to `True` in production via environment variable. The `afl_ref` cookie does not use this pattern; it has no analogous setting.

The ticket's fix suggestion — `secure=not S.dev_mode` — is slightly different from the `ui_cookie_secure` pattern but produces the same practical result in the current environment configuration: `dev_mode=True` → `secure=False` (HTTP-safe), `dev_mode=False` (production) → `secure=True`.

### Why the absence of `secure=True` in production matters

Without `Secure=True` in production:
1. If a user visits the affiliate redirect URL over HTTP (e.g. due to a misconfigured HSTS or a non-HTTPS request), the cookie is sent over HTTP and is visible to network observers — breaking the `httponly` benefit since the cookie value is a tracking code, not a credential, but it represents a real information leak.
2. More importantly, the `afl_ref` cookie will be transmitted over HTTP requests to the same domain, violating the security expectation for cookies that carry business-significant data (affiliate attribution = financial obligation).
3. In environments where HSTS is enforced and all traffic is HTTPS, the impact is lower, but the cookie should still be marked `Secure` to be consistent with production hardening standards.

### The `ad_promo_code` cookie comparison

`app/routers/ad_creative_affiliate.py:176–183` sets a similar attribution cookie without `secure`:
```python
response.set_cookie(
    "ad_promo_code",
    promo_code,
    max_age=S.ad_creative_affiliate_promo_cookie_max_age,
    path="/",
    httponly=False,
    samesite="lax",
)
```

This cookie does not have `httponly=True` (intentional — it's read by JavaScript for promo code prefill). It also lacks `secure=...`. This is a related but separate issue.

## 3. Impact / Exploit / Blast Radius

### Production: cookie sent over HTTP (under-secured)

Without `Secure=True` in production:
- An attacker performing a man-in-the-middle attack on an HTTP connection to the same origin domain can observe the `afl_ref` cookie value (the tracking code). Tracking codes are not credentials, but they reveal affiliate identity, which is mildly sensitive.
- If HSTS is not enforced perfectly (e.g. subdomains, IP-based access), the cookie is transmitted in cleartext HTTP responses/requests.

### Dev: no impact from the missing secure flag (claim correction)

In the local HTTP dev environment (port 3000/8000), because `secure` is not set (defaults `False`), the cookie is correctly sent over HTTP and is readable by the backend. The affiliate redirect, cookie-setting, and downstream checkout attribution (once GAP-0154 is fixed) all work as expected in dev. There is no dev-environment breakage from this gap.

### Compound impact with GAP-0154

GAP-0154 (conversion attribution chain broken) is a more severe issue. This gap (GAP-0155) is a prerequisite fix for clean end-to-end testing of the attribution fix in dev. If GAP-0155 were as described (cookie dropped due to `Secure=True` on HTTP dev), it would block GAP-0154 testing entirely. Since the claim is corrected (no `Secure=True` is set), GAP-0154 can be tested in dev today without needing GAP-0155 first — but GAP-0155 must still be fixed for correct production hardening.

### Blast radius

- Affects only the `afl_ref` cookie set by the affiliate redirect endpoint.
- No other cookies, endpoints, or user data are affected.
- No financial loss, authentication bypass, or data integrity risk.

## 4. Fix Design (Code-Level)

### Option A: use `secure=not S.dev_mode` (ticket recommendation)

Modify `app/routers/affiliate_links.py:204–211`:

```python
response.set_cookie(
    key="afl_ref",
    value=tracking_code,
    max_age=S.affiliate_cookie_duration_days * 86400,
    httponly=True,
    samesite="lax",
    path="/",
    secure=not S.dev_mode,    # <-- ADD THIS
)
```

This produces `Secure=True` in production (`DEV_MODE=0` or unset) and `Secure=False` in local dev (`DEV_MODE=1`).

### Option B: use `secure=S.ui_cookie_secure` (matches existing pattern)

Add a dedicated setting or reuse `S.ui_cookie_secure`:

```python
response.set_cookie(
    key="afl_ref",
    value=tracking_code,
    max_age=S.affiliate_cookie_duration_days * 86400,
    httponly=True,
    samesite="lax",
    path="/",
    secure=S.ui_cookie_secure,    # <-- matches session cookie pattern
)
```

This approach is slightly preferable because:
1. It uses an explicitly named, independently overridable setting.
2. Operators can set `UI_COOKIE_SECURE=1` in staging environments that run over HTTPS to test with `Secure=True` without changing `DEV_MODE`.
3. It is consistent with the pattern used in `sessions.py` and `device_trust.py`.

**Recommendation: Option B** — use `secure=S.ui_cookie_secure`. This aligns with the project's existing pattern and avoids coupling the security attribute to the dev-mode flag (which controls many other things beyond cookie security).

### Dev/Prod parity (SECOPS-007)

The key parity assertion:
- **Dev (HTTP, `UI_COOKIE_SECURE=0`):** `secure=False` → cookie is set and readable. Affiliate redirect flow works end-to-end. This is the same behaviour as today (no regression).
- **Production (HTTPS, `UI_COOKIE_SECURE=1`):** `secure=True` → cookie is only sent over HTTPS connections. The `samesite="lax"` attribute remains unchanged. The `afl_ref` cookie behaviour matches the security posture of session cookies.
- **Staging over HTTPS:** Can be tested with `UI_COOKIE_SECURE=1` and `DEV_MODE=1` independently — this is the advantage of Option B over Option A.

No mock or special dev code path is required. The same `set_cookie` call runs in all environments; only the `secure` attribute value differs based on the environment setting.

### Full set_cookie call after fix (Option B)

```python
# app/routers/affiliate_links.py:204 — affiliate_redirect()
response.set_cookie(
    key="afl_ref",
    value=tracking_code,
    max_age=S.affiliate_cookie_duration_days * 86400,
    httponly=True,
    samesite="lax",
    path="/",
    secure=S.ui_cookie_secure,
)
```

Ensure `from app.core.settings import S` is present in the import block (it already is, at line 13: `from app.core.settings import S`).

### Backward compatibility

- **No API contract change.** The response headers change only in environments where `UI_COOKIE_SECURE=1`.
- **No database migration.** Cookies are client-side state.
- **No frontend change.** The `afl_ref` cookie is `httponly=True`; JavaScript does not read it.
- **Existing affiliates unaffected.** Previously recorded clicks and conversions are unaffected.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

```python
"""Regression test for GAP-0155: afl_ref cookie secure attribute matches ui_cookie_secure setting."""
from unittest.mock import patch, MagicMock
import pytest
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app, base_url="http://testserver")


def test_afl_ref_cookie_secure_false_in_dev(monkeypatch):
    """
    FAILS before fix: cookie has no explicit secure param (defaults False, OK in dev but wrong approach).
    PASSES after fix: secure=S.ui_cookie_secure is set and resolves to False in dev.
    """
    from app.core.settings import S
    monkeypatch.setattr(S, "ui_cookie_secure", False)

    with patch("app.routers.affiliate_links.get_link_by_code") as mock_link, \
         patch("app.routers.affiliate_links.record_click"):
        mock_link.return_value = {
            "link_id": "link_test",
            "tracking_code": "TESTCODE",
            "status": "active",
            "destination_url": "https://example.com/product",
        }
        response = client.get("/r/TESTCODE", follow_redirects=False)

    assert response.status_code == 302
    set_cookie_header = response.headers.get("set-cookie", "")
    assert "afl_ref=TESTCODE" in set_cookie_header
    # In dev (ui_cookie_secure=False), Secure attribute must NOT appear
    assert "Secure" not in set_cookie_header.split(";")[0].upper() or \
           "secure" not in set_cookie_header.lower(), \
        "Cookie must not have Secure flag in dev mode"


def test_afl_ref_cookie_secure_true_in_prod(monkeypatch):
    """
    FAILS before fix: secure param is not set, so Secure attribute is absent regardless of setting.
    PASSES after fix: Secure attribute is present when ui_cookie_secure=True.
    """
    from app.core.settings import S
    monkeypatch.setattr(S, "ui_cookie_secure", True)

    with patch("app.routers.affiliate_links.get_link_by_code") as mock_link, \
         patch("app.routers.affiliate_links.record_click"):
        mock_link.return_value = {
            "link_id": "link_prod",
            "tracking_code": "PRODCODE",
            "status": "active",
            "destination_url": "https://example.com/product",
        }
        response = client.get("/r/PRODCODE", follow_redirects=False)

    assert response.status_code == 302
    set_cookie_header = response.headers.get("set-cookie", "")
    # After fix: Secure attribute must be present
    assert "secure" in set_cookie_header.lower(), (
        f"Cookie must have Secure flag in production. Got: {set_cookie_header}"
    )


def test_afl_ref_cookie_always_has_httponly_and_samesite():
    """httponly and samesite=lax must be present in all environments."""
    with patch("app.routers.affiliate_links.get_link_by_code") as mock_link, \
         patch("app.routers.affiliate_links.record_click"):
        mock_link.return_value = {
            "link_id": "link_1",
            "tracking_code": "CODE1",
            "status": "active",
            "destination_url": "/",
        }
        response = client.get("/r/CODE1", follow_redirects=False)

    set_cookie_header = response.headers.get("set-cookie", "").lower()
    assert "httponly" in set_cookie_header
    assert "samesite=lax" in set_cookie_header
```

**Fails before fix (prod test):** No `secure` argument means `Secure` is never in the `Set-Cookie` header regardless of `ui_cookie_secure` value. The `test_afl_ref_cookie_secure_true_in_prod` assertion `"secure" in set_cookie_header` fails.
**Passes after fix:** With `secure=S.ui_cookie_secure`, the `Secure` attribute appears in the header when `ui_cookie_secure=True` and is absent when `False`.

### Rollout

- **Effort:** S (Small) — one line change in one file (`secure=S.ui_cookie_secure` added to `set_cookie`).
- **Risk:** Minimal. In dev, behaviour is unchanged (cookie still set, `Secure=False`). In production, `Secure=True` is added — this is strictly more correct. No cookie that was previously set will break; the change only affects new `afl_ref` cookie sets after deployment.
- **Dependencies:** Should be shipped in the same PR as GAP-0154 to form a complete affiliate attribution fix. Both gaps are small.
- **Rollback:** Remove the `secure=S.ui_cookie_secure` argument. The cookie reverts to `Secure=False` in all environments.
