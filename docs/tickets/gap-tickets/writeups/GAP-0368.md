# GAP-0368: "queued" status transition silently fails on job submission — Remediation Write-up

> ~5 pages. Fix-oriented. Claim verified against actual code (no investigation doc exists).

## 1. Summary & Classification

**Severity**: HIGH  
**Source ticket**: VOD-003  
**Owning area**: VOD pipeline / transcode job submission  
**Status**: Open  
**Claim verdict**: CONFIRMED — same root cause as GAP-0366, same file and line.

GAP-0368 is the VOD-003 re-identification of the same defect already catalogued as GAP-0366 (VOD-001). Both tickets point to `app/routers/transcode_jobs.py:103` and prescribe the same fix: replace `to_status="queued"` with `to_status="pending_encoding"`. This write-up documents the gap from the VOD-003 perspective (which frames the impact as the `ByStatusCreatedAt` GSI for `"pending_encoding"` remaining perpetually empty, breaking admin dashboards and the worker poll loop) and provides a standalone regression test that exercises the full state-machine path.

**Relationship to GAP-0366**: Identical root cause. The two tickets differ only in the source audit cycle (VOD-001 vs VOD-003) and in the specific downstream impact described. When GAP-0366 is fixed, GAP-0368 is automatically resolved. Both writeups are retained for traceability.

## 2. Current-State Investigation (root cause)

### The defect — same line, same file

**`app/routers/transcode_jobs.py`, lines 101–105**:

```python
# Transition video status to queued
try:
    transition_video_status(video_id=body.video_id, to_status="queued")   # line 103
except Exception:
    logger.warning("Could not transition video %s to queued", body.video_id)
```

### State machine — "queued" is not a VideoStatus

**`app/services/video_state_machine.py`, lines 10–22**: The `_ALLOWED_TRANSITIONS` dictionary is keyed on `VideoStatus` literals. The `VideoStatus` type is defined in `app/models_video.py` (lines 7–20) as a `Literal` of twelve values: `"created"`, `"probing"`, `"probe_failed"`, `"pending_encoding"`, `"encoding"`, `"encoding_failed"`, `"pending_review"`, `"approved"`, `"rejected"`, `"published"`, `"archived"`, `"deleted"`. The string `"queued"` is absent from both the type alias and the transition table.

`validate_transition(current_status, "queued")` therefore always returns `TransitionValidationResult(legal=False)`, causing `transition_video_status` to raise `HTTPException(409)`. The bare `except Exception` on line 104 consumes the exception.

### GSI impact (the VOD-003 framing)

The `VideoMetadata` DynamoDB table has a `ByStatusCreatedAt` GSI with `status` as the partition key (`scripts/local-ddb-init.py`, lines 889–920). For the admin dashboard and SLA monitoring to show "pending encoding" videos, the table must contain rows with `status = "pending_encoding"`. Because `transition_video_status` always fails silently, no video row ever reaches that status through this code path.

**`app/services/transcode_job_store.py`** has its own separate `status` field and its own `ByStatusCreatedAt` GSI on the `TranscodeJobs` table (line 921 in `local-ddb-init.py`). That `status` begins as `"queued"` (job store) and is correct for the jobs table. The confusion arises because the same string `"queued"` is used as a job status in the transcode-jobs domain but is **not** a valid video-metadata status. The bug author used the job-domain vocabulary when writing the video-metadata transition call.

### Worker poll loop impact

`transcode_worker_loop` (`app/services/transcode_worker.py`, line 60) polls `list_jobs_by_status("queued", ...)` — this queries the `TranscodeJobs` table, not `VideoMetadata`. The worker therefore **finds and processes jobs correctly**. However, after `claim_job` transitions the job to `"running"`, the video-metadata row is still in `"probing"`. When `execute_transcode_job` completes and calls `transition_video_status(..., to_status="published")` (line 203 of `transcode_worker.py`), it attempts the transition `probing → published`, which is also illegal (the state machine requires `probing → pending_encoding → encoding → pending_review → approved → published`). That call too is wrapped in a `try/except` (lines 200–205), so the video is never marked `"published"` either. This is the separate bug catalogued in GAP-0369.

## 3. Impact / Exploit / Blast Radius

### Primary impact

Every video submitted for transcoding since the VOD-003 feature was shipped has its video-metadata status frozen in `"probing"` (or `"created"` if the probe step was skipped). The `VideoPlayerPage.tsx` renders `<ProcessingState />` for `"probing"` indefinitely:

```ts
// app/frontend/src/pages/videos/VideoPlayerPage.tsx, line 368–372
const isProcessing =
  video &&
  ["created", "probing", "pending_encoding", "encoding"].includes(video.status);
```

Users who have uploaded and "submitted" a transcode see a perpetual "Video is being processed…" spinner.

### Admin dashboard impact

Any admin view or analytics query reading `ByStatusCreatedAt` with `status = "pending_encoding"` returns zero rows, hiding the true queue depth. This breaks:

- SLA monitoring ("how many videos have been waiting for encoding for > N minutes?")
- Admin batch-approval workflows that filter for `pending_encoding` videos
- Any capacity-planning query that tracks encoding queue depth over time

### Data integrity

The video-metadata and transcode-job tables are now in an inconsistent state: the jobs table knows a job exists in `"queued"` (and transitions through `"running"` and `"completed"`), but the video-metadata table never reflects these state changes. After the worker finishes, the job is in `"completed"` but the video is still `"probing"`.

### Financial consequence

Videos that never reach `"published"` cannot be served to subscribers or pay-per-view purchasers, directly reducing revenue for any creator who has uploaded a video.

### Compound effect with GAP-0369

Even after this fix is applied in isolation, videos will correctly reach `"pending_encoding"` after job submission. However, when the worker completes the job, it attempts to transition directly to `"published"` (GAP-0369). That call is also illegal and also swallowed silently, so the video never reaches `"published"`. The full pipeline is only correct when both GAP-0368 and GAP-0369 are fixed together. Shipping GAP-0368 alone will advance the video one step further in the state machine but will not result in published videos.

## 4. Fix Design (code-level)

### Minimal change (identical to GAP-0366)

**File**: `app/routers/transcode_jobs.py`, line 103

```python
# Before (broken):
transition_video_status(video_id=body.video_id, to_status="queued")

# After (correct):
transition_video_status(video_id=body.video_id, to_status="pending_encoding")
```

Update the comment on line 101 to match:

```python
# Transition video status to pending_encoding
```

### SECOPS-007 dev/prod parity

No AWS-specific code paths are involved. The call to `transition_video_status` runs identically in both dev (DynamoDB Local port 8001) and production (AWS DynamoDB). There is no `if S.dev_mode` branching in `video_metadata_store.py` or `video_state_machine.py`. No feature flag is needed. The fix is a pure string-literal substitution with no infrastructure coupling.

### Type safety hardening

In conjunction with the fix, the `to_status` parameter of `transition_video_status` (`app/services/video_metadata_store.py`, line 367) should be tightened from `str` to `VideoStatus`:

```python
# Before:
def transition_video_status(*, video_id: str, to_status: str, ...) -> VideoMetadataModel:

# After (with import from app.models_video):
def transition_video_status(*, video_id: str, to_status: VideoStatus, ...) -> VideoMetadataModel:
```

With this typing in place, mypy or pyright would flag `to_status="queued"` as a type error at the call site in `transcode_jobs.py`, making the bug class statically detectable. This hardening applies equally to GAP-0366 and GAP-0368, since both are caused by the same incorrect literal at the same call site.

### Additional hardening (optional, not blocking)

The `except Exception` guard on line 104 is appropriate for transient infrastructure errors (e.g., DynamoDB throttle). However, a hard-coded string literal producing an `HTTPException(409)` is a programming error, not a transient failure. A tighter guard would re-raise programming errors:

```python
try:
    transition_video_status(video_id=body.video_id, to_status="pending_encoding")
except HTTPException:
    # State transition rejected — log and continue (job was still created)
    logger.warning(
        "Could not transition video %s to pending_encoding — unexpected status",
        body.video_id,
    )
except Exception:
    logger.warning(
        "Infra error transitioning video %s to pending_encoding",
        body.video_id,
    )
```

This is a separate improvement and not required to close GAP-0368.

### Backward compatibility

No migration required. Videos currently stuck in `"probing"` need to be manually advanced via the admin status-override endpoint.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

Create `tests/test_gap_0368_status_transition.py`:

```python
"""
GAP-0368 regression test.

The job-submission endpoint must call transition_video_status with
to_status='pending_encoding', not the invalid 'queued' string.

This test also verifies the GSI-facing consequence: after a job is submitted,
querying VideoMetadata with status='pending_encoding' would find the video.
"""
import pytest
from unittest.mock import patch, call, MagicMock
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)


def _session():
    return {"user_sub": "u_gap0368", "role": "USER", "admin_profile": None}


def _mock_video():
    v = MagicMock()
    v.owner_user_id = "u_gap0368"
    v.status = "probing"
    v.id = "vid_gap0368"
    v.tenant_id = "u_gap0368"
    v.source_s3_key = None
    return v


def test_job_submission_calls_pending_encoding_transition():
    """
    FAILS before fix: transition called with to_status='queued' (invalid).
    PASSES after fix: transition called with to_status='pending_encoding'.
    """
    transition_calls = []

    with (
        patch("app.routers.transcode_jobs.require_ui_session",
              return_value=_session()),
        patch("app.routers.transcode_jobs.get_video",
              return_value=_mock_video()),
        patch("app.routers.transcode_jobs.create_job", return_value={
            "job_id": "job_g368",
            "video_id": "vid_gap0368",
            "tenant_id": "u_gap0368",
            "status": "queued",
            "created_at": 1000000,
            "updated_at": 1000000,
            "attempt": 0,
        }),
        patch(
            "app.routers.transcode_jobs.transition_video_status",
            side_effect=lambda **kw: transition_calls.append(kw),
        ),
    ):
        resp = client.post(
            "/ui/transcode-jobs",
            json={
                "video_id": "vid_gap0368",
                "rendition_profiles": [{"name": "720p", "height": 720}],
            },
        )

    assert resp.status_code == 201, f"Expected 201, got {resp.status_code}: {resp.text}"
    assert len(transition_calls) == 1, "transition_video_status should be called once"

    to_status = transition_calls[0].get("to_status")
    assert to_status == "pending_encoding", (
        f"GAP-0368: expected to_status='pending_encoding', got '{to_status}'. "
        "The string 'queued' is not a valid VideoStatus and causes a silent 409."
    )


def test_invalid_queued_literal_is_rejected_by_state_machine():
    """
    Confirms the state machine rejects 'queued' from 'probing'.
    Uses the real validate_transition so the test never depends on mocked behaviour.
    """
    from app.services.video_state_machine import validate_transition

    result = validate_transition("probing", "queued")  # type: ignore[arg-type]
    assert not result.legal, (
        "State machine must not accept 'queued' as a valid video status transition"
    )

    result_correct = validate_transition("probing", "pending_encoding")
    assert result_correct.legal, (
        "State machine must accept 'probing' -> 'pending_encoding'"
    )
```

**Before fix**: `to_status == "queued"` → `assert to_status == "pending_encoding"` fails with a message that identifies the wrong literal.  
**After fix**: `to_status == "pending_encoding"` → assertion passes.

The second test (`test_invalid_queued_literal_is_rejected_by_state_machine`) is purely informational and will pass both before and after the fix. It confirms that the state machine itself is correctly designed and that the bug is solely in the router's use of the wrong literal — not in the state machine accepting an invalid value.

The test uses `patch("app.routers.transcode_jobs.transition_video_status")` to intercept the call at the import boundary in `transcode_jobs.py`. Because `transition_video_status` is imported at module load time (`from app.services.video_metadata_store import ... transition_video_status`), patching the name in the calling module's namespace is the correct approach. Patching `app.services.video_metadata_store.transition_video_status` instead would not intercept the call because `transcode_jobs` holds its own reference to the function object.

### Manual QA steps

1. `just restart`.
2. Upload a video; wait until `status == "probing"` (check via `GET /ui/videos/{video_id}`).
3. `POST /ui/transcode-jobs` with that `video_id`.
4. **Before fix**: `GET /ui/videos/{video_id}` still shows `status == "probing"`.
5. **After fix**: `GET /ui/videos/{video_id}` shows `status == "pending_encoding"`.
6. Query DynamoDB Local: `aws dynamodb query --table-name VideoMetadata --index-name ByStatusCreatedAt --key-condition-expression "status = :s" --expression-attribute-values '{":s":{"S":"pending_encoding"}}' --endpoint-url http://localhost:8001` — expect at least one item.

### Observability

- Log line `WARNING: Could not transition video X to queued` should disappear after the fix. Any reappearance indicates a video in an unexpected state. Add a CloudWatch Metrics/Datadog log monitor to alert if this warning fires more than once per hour in production.
- Monitor the `VideoMetadata` table's `ByStatusCreatedAt` GSI item count for `status = "pending_encoding"`. In a healthy deployment, this count rises each time a job is submitted and falls as the worker claims jobs. A count permanently stuck at zero after the fix is deployed means either the fix was not deployed correctly, or a second code path (e.g., a different router or an admin endpoint) is also using the wrong status string.
- The `TranscodeJobs` table's `ByStatusCreatedAt` GSI for `status = "queued"` should show the same cardinality as the `VideoMetadata` `pending_encoding` partition in steady state. A divergence between the two indicates a split-brain condition and warrants investigation.
- For the player page, monitor `GET /ui/videos/{video_id}` responses where `status` is `"probing"` for videos that have an associated completed or queued job. Any such condition post-deployment indicates a stuck video that needs manual repair.

### Rollout

- **Effort**: S (identical one-line fix to GAP-0366 — both tickets are resolved by the same commit).
- **Sequencing**: Fix in the same commit as GAP-0366. GAP-0369 (worker completion transition) is a follow-on fix that should be deployed in the same sprint. All three fixes (GAP-0366, GAP-0368, GAP-0369) should ship together to make the full video lifecycle correct end-to-end.
- **Rollback**: Revert the commit. No data migration.

### Data repair for pre-existing stuck videos

Deploying this fix prevents future videos from getting stuck, but it does not repair videos already frozen in `"probing"` or `"created"`. An operational repair script (run once, in a migration task) should:

1. Scan or query the `VideoMetadata` table for videos with `status IN ("created", "probing")` that have an associated `TranscodeJobs` entry.
2. Cross-reference each video's `video_id` against the `TranscodeJobs` table (query by `video_id` using the `ByVideoCreatedAt` or similar index).
3. For videos with a `"completed"` job, advance the video status directly to `"pending_review"` (bypassing intermediate states since the encoding is already done).
4. For videos with a `"queued"` or `"running"` job, advance only to `"pending_encoding"` and let the worker handle the rest.
5. Log all repairs with the actor set to `"migration/gap-0368-repair"` for audit-trail clarity.
