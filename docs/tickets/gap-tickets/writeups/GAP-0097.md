# GAP-0097: Backlog Scan Misses Sparse Tickets — Remediation Write-up

> Claim accuracy note: The ticket cites `app/services/agent_project.py:685` as the location.
> Code inspection confirms this is CORRECT. `_scan_backlog_tickets` at line 685 calls
> `tickets_svc.STORE.list_tickets` / `list_space_tickets` with a fixed `Limit=min(limit,100)`
> and no pagination loop. `_query_headers_by_index` at `app/services/tickets.py:421` returns a
> `next_cursor` that `_scan_backlog_tickets` ignores entirely. The claim is accurate.

## 1. Summary & Classification

**Bug**: `_scan_backlog_tickets` in `app/services/agent_project.py` fetches at most one DynamoDB page (up to 100 items) per status bucket. When any status partition contains more than 100 tickets, items beyond the first page are silently dropped. The AI backlog-prioritisation and sprint-planning features therefore operate on an incomplete, truncated view of the actual backlog, potentially missing high-priority work items entirely.

- **Severity**: HIGH
- **Source ticket**: AGENT-012
- **Owning area**: Agent Project Management service / backlog prioritisation
- **Status**: Open

- **One-line impact**: High-volume projects silently lose backlog visibility beyond 100 tickets per status; critical tickets are never surfaced to the PM agent's prioritisation loop.
- **Related tickets**: GAP-0083 (eligible-ticket-count pagination incomplete — same root cause pattern in a different function), SECOPS-007 (dev/prod parity)

## 2. Current-State Investigation (root cause)

### The incomplete scan function

`app/services/agent_project.py:685–705` (`_scan_backlog_tickets`):

```python
def _scan_backlog_tickets(
    *, space_id: Optional[str], statuses: List[str], limit: int
) -> List[Dict[str, Any]]:
    seen: Dict[str, Dict[str, Any]] = {}
    for status in statuses:
        try:
            if space_id:
                page = tickets_svc.STORE.list_space_tickets(
                    space_id=space_id, status=status, limit=min(limit, 100)
                )
            else:
                page = tickets_svc.STORE.list_tickets(status=status, limit=min(limit, 100))
        except Exception:  # pragma: no cover - defensive
            continue
        for t in page.get("tickets", []):
            tid = t.get("ticket_id")
            if tid and tid not in seen:
                seen[tid] = t
        if len(seen) >= limit:
            break
    return list(seen.values())[:limit]
```

The function issues exactly one `list_tickets` (or `list_space_tickets`) call per status. The response contains a `next_cursor` field when more items exist, but `_scan_backlog_tickets` never reads `page.get("next_cursor")` and never issues a follow-up call.

### The pagination machinery exists but is not used

`app/services/tickets.py:421–438` (`_query_headers_by_index`):

```python
def _query_headers_by_index(self, *, index_name, pk, key_expr, limit, cursor):
    params = {
        "IndexName": index_name,
        "KeyConditionExpression": key_expr,
        "ExpressionAttributeValues": {":pk": pk},
        "ScanIndexForward": False,
        "Limit": limit,
    }
    decoded = self._decode_cursor(cursor)
    if decoded and ...:
        params["ExclusiveStartKey"] = decoded["lek"]
    resp = self._table.query(**params)
    items = resp.get("Items", [])
    lek = resp.get("LastEvaluatedKey")
    if lek:
        next_cursor = self._encode_cursor({"index": index_name, "pk": pk, "lek": lek})
    return items, next_cursor
```

The store already supports cursor-based pagination. `list_tickets` and `list_space_tickets` both accept a `cursor` parameter and return `next_cursor` in their response dict. Moreover, `_query_all_headers_by_index` at `tickets.py:514–529` already implements the full exhaustive loop:

```python
def _query_all_headers_by_index(self, *, index_name, pk, key_expr, limit=100):
    all_items = []
    cursor = None
    while True:
        items, next_cursor = self._query_headers_by_index(...)
        all_items.extend(items)
        if not next_cursor:
            break
        cursor = next_cursor
    return all_items
```

The complete solution already exists in the store layer — `_scan_backlog_tickets` simply does not use it.

### The default status set and effective page budget

`app/services/agent_project.py:63`:
```python
_BACKLOG_STATUSES = ("open", "in_progress", "code_complete", "qa_in_progress", "blocked")
```

`get_backlog(limit=100)` iterates all five statuses with `limit=min(100,100)=100` per call. Each status is a separate GSI partition in the `tickets` table. If the `open` partition alone contains 150 items, only the first 100 are returned by the single-page call. The remaining 50 — which may include the highest-priority open tickets — are silently discarded. The `if len(seen) >= limit: break` early-exit only applies when the accumulated count across all statuses reaches `limit`; it does not trigger within a single status scan.

### DynamoDB filtering characteristics

Neither `list_tickets` nor `list_space_tickets` uses a `FilterExpression` on top of the GSI query — they query a status-partitioned GSI directly (`gsi2pk = STATUS#<status>`). This means DynamoDB returns all items in the status partition sequentially, and the `Limit` parameter controls how many items DynamoDB returns before the cursor. There is no filter sparseness amplification here (unlike the CLAUDE.md warning about FilterExpression). The missed-items problem is purely a pagination omission: the caller stops after one page.

### Dev vs prod divergence (SECOPS-007)

In dev, the E2E test suites accumulate tickets across repeated runs. The `just restart` command wipes and re-seeds the database, but between restarts, each `just e2e` run adds tickets without cleanup. After many runs, the `open` status partition can exceed 100 items, triggering the bug in the development environment as well. In production the problem manifests for any project that has generated more than 100 tickets in any single status bucket — which is routine for teams using the platform continuously for several months.

## 3. Impact / Exploit / Blast Radius

**Functional impact — backlog prioritisation**:

The `prioritize_backlog` function (`agent_project.py`, called by the PM agent) calls `get_backlog` internally to obtain the candidate set for scoring. With only 100 tickets per status visible, the scoring and ranking loop operates on a biased sample. The bias is systematic: `_query_headers_by_index` uses `ScanIndexForward: False` (newest-first by GSI sort key). The oldest tickets in each status bucket are the ones most likely to be dropped — i.e., tickets that have been open the longest are paradoxically the least visible to the prioritisation agent.

**Worst case — critical ticket invisibility**:

A team has 300 open tickets. A severity-critical security regression ticket was filed two months ago and remains open. Because it is not in the 100 most recently modified open tickets, `get_backlog` never returns it. The PM agent recommends sprints that exclude this ticket indefinitely. The security issue goes unscheduled.

**Sprint planning and idea conversion**:

Both `plan_sprint` and `convert_idea_to_ticket` (in the same service) depend on `get_backlog` results to avoid duplicating work already in the backlog. With a truncated backlog, `convert_idea_to_ticket` may create duplicate tickets for work that is already present but invisible.

**No direct security exploit**: The gap is a correctness and data completeness failure rather than a security vulnerability. However, if the PM agent is used to track compliance or security work items, incomplete backlog visibility is a compliance risk.

**Effort estimation inaccuracy**: The `calculate_priority_score` function uses backlog size as part of its weighting. An artificially truncated backlog produces inflated scores for the visible subset, further distorting prioritisation.

## 4. Fix Design (code-level)

### Option A (recommended): add `list_all_tickets_by_status` to `TicketStore`

The `TicketStore` class in `app/services/tickets.py` already has `_query_all_headers_by_index`. Expose a public method that wraps it for the specific access pattern needed by `_scan_backlog_tickets`.

**Add to `TicketStore` in `app/services/tickets.py`**:

```python
def list_all_tickets_by_status(
    self,
    *,
    status: str,
    space_id: Optional[str] = None,
    limit: int = 500,
) -> List[Dict[str, Any]]:
    """Return up to ``limit`` tickets for a given status, exhausting all pages.

    Unlike ``list_tickets`` / ``list_space_tickets`` which return a single page,
    this method follows ``LastEvaluatedKey`` until all matching items are fetched
    or ``limit`` is reached.
    """
    per_page = min(100, limit)
    if space_id:
        index_name = S.tickets_space_status_index_name
        pk = _space_status_index_pk(space_id, status)
        key_expr = "gsi_space_status_pk = :pk"
    else:
        index_name = S.tickets_status_index_name
        pk = _status_index_pk(status)
        key_expr = "gsi2pk = :pk"
    raw_headers = self._query_all_headers_by_index(
        index_name=index_name, pk=pk, key_expr=key_expr, limit=per_page
    )
    assembled = self._assemble_headers(raw_headers)
    return assembled[:limit]
```

**Update `_scan_backlog_tickets` in `app/services/agent_project.py`**:

```python
def _scan_backlog_tickets(
    *, space_id: Optional[str], statuses: List[str], limit: int
) -> List[Dict[str, Any]]:
    seen: Dict[str, Dict[str, Any]] = {}
    per_status_limit = max(limit, 500)  # fetch enough per status to satisfy overall limit
    for status in statuses:
        try:
            tickets = tickets_svc.STORE.list_all_tickets_by_status(
                status=status,
                space_id=space_id or None,
                limit=per_status_limit,
            )
        except Exception:  # pragma: no cover - defensive
            continue
        for t in tickets:
            tid = t.get("ticket_id")
            if tid and tid not in seen:
                seen[tid] = t
        if len(seen) >= limit:
            break
    return list(seen.values())[:limit]
```

### Option B: inline cursor loop

If adding a new store method is undesirable, loop `list_tickets` with `cursor` inline in `_scan_backlog_tickets`:

```python
cursor: Optional[str] = None
while True:
    page = tickets_svc.STORE.list_tickets(status=status, limit=100, cursor=cursor)
    for t in page.get("tickets", []):
        ...
    cursor = page.get("next_cursor")
    if not cursor or len(seen) >= limit:
        break
```

Option A is preferred because it reuses the already-tested exhaustive loop in the store, is cleaner, and makes the intent explicit in a named method.

### Performance note

`_assemble_headers` issues one `get_item` per ticket header (to retrieve the full ticket body from the items table). For 500 tickets this is 500 sequential DynamoDB `get_item` calls. This is acceptable for a background agent operation but should be bounded. The `limit=500` cap in `list_all_tickets_by_status` is a pragmatic guard. A future optimisation is to use `batch_get_item` (up to 100 items per call, 5 calls for 500 items) to reduce latency by 10×, but that is a separate performance ticket.

### Dev/Prod parity (SECOPS-007)

Both `list_all_tickets_by_status` and the inline cursor loop use standard DynamoDB `query` calls with `Limit` and `ExclusiveStartKey`. These are identical between DynamoDB Local (dev) and AWS DynamoDB (prod). No feature flag or environment-specific code path is needed.

```python
# tests/services/test_agent_project_backlog.py
import pytest
from unittest.mock import patch, MagicMock
from app.services import agent_project as svc


def _make_ticket(i):
    return {"ticket_id": f"ticket_{i:03d}", "status": "open", "title": f"Ticket {i}"}


class TestScanBacklogPagination:
    def test_fetches_beyond_first_page_via_new_method(self):
        """FAILS before fix: only first 100 tickets returned from a 150-ticket bucket."""
        all_150 = [_make_ticket(i) for i in range(150)]

        with patch.object(
            svc.tickets_svc.STORE,
            "list_all_tickets_by_status",
            return_value=all_150,
        ):
            results = svc._scan_backlog_tickets(
                space_id=None, statuses=["open"], limit=150
            )
        assert len(results) == 150, f"Expected 150, got {len(results)}"

    def test_respects_limit_cap(self):
        """Even with 200 items available, limit=100 is honoured."""
        all_200 = [_make_ticket(i) for i in range(200)]

        with patch.object(
            svc.tickets_svc.STORE,
            "list_all_tickets_by_status",
            return_value=all_200,
        ):
            results = svc._scan_backlog_tickets(
                space_id=None, statuses=["open"], limit=100
            )
        assert len(results) == 100

    def test_multiple_statuses_aggregated(self):
        """Tickets from different status buckets are combined correctly."""
        open_tickets = [_make_ticket(i) for i in range(60)]
        inprogress_tickets = [_make_ticket(i + 100) for i in range(60)]

        def fake_list_all(*, status, space_id=None, limit):
            if status == "open":
                return open_tickets
            if status == "in_progress":
                return inprogress_tickets
            return []

        with patch.object(
            svc.tickets_svc.STORE,
            "list_all_tickets_by_status",
            side_effect=fake_list_all,
        ):
            results = svc._scan_backlog_tickets(
                space_id=None, statuses=["open", "in_progress"], limit=120
            )
        assert len(results) == 120

    def test_deduplication_across_status_calls(self):
        """Same ticket_id appearing in two statuses is deduplicated."""
        t = _make_ticket(1)
        with patch.object(
            svc.tickets_svc.STORE,
            "list_all_tickets_by_status",
            return_value=[t],
        ):
            results = svc._scan_backlog_tickets(
                space_id=None, statuses=["open", "in_progress"], limit=10
            )
        assert len(results) == 1
```

**Tests that FAIL before the fix**: `test_fetches_beyond_first_page_via_new_method` — the old `_scan_backlog_tickets` calls `list_tickets` (not `list_all_tickets_by_status`), so the patch has no effect and the function returns at most 100 items. `test_multiple_statuses_aggregated` also fails for the same reason when total expected > 100.

**Tests that PASS after the fix**: All four tests pass because `list_all_tickets_by_status` is used and returns all items.
