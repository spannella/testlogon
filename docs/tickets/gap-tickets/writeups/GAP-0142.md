# GAP-0142: Missing SSE Fanout for `call.missed` — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Gap statement**: When a WebRTC call invite times out — either via the caller-side UI timer (`ConversationView.tsx:821-829`) or the server-side backstop (`_expire_stale_invites`, `messaging.py:13318-13347`) — the resulting `call.missed` lifecycle event is written to DynamoDB and a timeline system message is emitted, but no SSE fanout is sent to the conversation participants. The callee's ringing overlay therefore remains visible until the next SSE poll (up to 1-3 seconds, configurable by the long-poll interval), and under network-partition conditions the callee may never learn that the call timed out.

- **Severity**: HIGH
- **Source ticket**: CALL-007
- **Status**: Open — confirmed in production code.
- **Owning area**: `app/routers/messaging.py` — `timeout_call_endpoint` (line 14028) and `_expire_stale_invites` (line 13318).
- **Investigation verdict**: Claim is fully confirmed. Both code paths — the HTTP endpoint and the background-loop backstop — call `timeout_call()` but do not follow up with `fanout_event_to_conversation`. Every other call-lifecycle transition in the same file (e.g., decline at line 13551, end at line 13715) does call `fanout_event_to_conversation` immediately after the lifecycle mutation.
- **Related tickets**: GAP-0143 (callee-side local timer — the belt to this suspender), CALL-007 parent.

## 2. Current-State Investigation (root cause)

### 2.1 The `timeout_call_endpoint`

`app/routers/messaging.py:14028-14059`:

```python

        raise _call_error_to_http(exc)
```

After `timeout_call()` succeeds, the endpoint returns immediately. There is no call to `fanout_event_to_conversation`.

### 2.2 The `_expire_stale_invites` backstop

`app/routers/messaging.py:13318-13347`:


Same omission: `timeout_call` is called, the timeline event is written to DynamoDB, but no SSE event is pushed to callee or caller.

### 2.3 `timeout_call` in the service layer

`app/services/messaging_call_lifecycle.py:404-453`: the function updates the call session state to `"missed"` and calls `timeline_emitter` (which writes a `call.missed` system message to the Messages table). It does **not** — and correctly should not — do SSE fanout; fanout is the router/background-loop's responsibility, as seen in the decline/end endpoints.

### 2.4 Correct pattern already in use

The `decline_invite` endpoint around line 13551 and the `end_call` endpoint around line 13715 both follow the correct pattern:

```python
record, event = decline_invite(...)
fanout_event_to_conversation(
    conversation_id=record.conversation_id,
    sender_id=user_id,
    event_type="call.decline",
    payload={
        "call_id": record.call_id,
        "from_state": event.from_state,
        "reason": event.reason,
        "event_ts": event.event_ts,
        ...
    },
    respect_mute=False,
)
```

The `timeout_call_endpoint` and `_expire_stale_invites` are missing this exact block.

### 2.5 Runtime manifestation

When the caller-side 30-second timer fires (`ConversationView.tsx:821`):
1. Caller's UI dispatches `REMOTE_DECLINE` locally (transitions to `timeout` phase immediately — good).
2. Caller calls `POST /messages/calls/{call_id}/timeout` — succeeds, writes DDB record.
3. **No SSE event sent.** Callee's SSE stream does not receive a `call.missed` event.
4. Callee continues ringing until the next SSE poll cycle delivers the timeline system message (which the frontend SSE handler does process) — up to 1-3 seconds delay.
5. If the callee's SSE connection is temporarily disconnected (mobile background, network flap), the `call.missed` event is never delivered at all.

## 3. Impact / Exploit / Blast Radius

**UX degradation**: The callee's ringing overlay continues to ring after the intended timeout. With the default `messaging_webrtc_call_ringing_timeout_seconds = 30` (`app/core/settings.py:1149`), the callee may experience an extra 1-3 second ring under normal conditions, or an indefinite ring under adverse network conditions.

**Device resource waste**: The callee's device is holding open a WebRTC media capture (microphone/camera) for the duration of the ring. Indefinite ringing holds device resources longer than intended, draining battery and monopolising media permissions.

**Secondary dependency**: GAP-0143 adds a client-side guard timer, but that is a fallback. If GAP-0142 is fixed, GAP-0143 becomes a safety net rather than the primary mechanism. Fixing only GAP-0143 (client guard) leaves a DDB inconsistency window and does not reduce server-side notification latency.

**Compliance**: Call-state records in DynamoDB reaching the `missed` state but participants not being notified creates audit-log inconsistency — the conversation timeline has a `call.missed` system message but the SSE archive may have no corresponding fanout event.

**Blast radius**: Every DM and group conversation using WebRTC calling. Effect scales with call volume; one-off missed calls are mildly annoying; high-volume platforms (e.g., a support desk that rings agents) can leave dozens of ringing overlays open simultaneously.

## 4. Fix Design (code-level)

### 4.1 `timeout_call_endpoint` — add fanout

In `app/routers/messaging.py` at approximately line 14042 (immediately after `record, event = timeout_call(...)`):

```python
try:
    record, event = timeout_call(
        call_id=call_id,
        actor_user_id=user_id,
        reason=body.reason,
        idempotency_key=body.idempotency_key,
    )
    # GAP-0142: fanout call.missed so callee dismisses ringing immediately
    fanout_event_to_conversation(
        conversation_id=record.conversation_id,
        sender_id=user_id,
        event_type="call.missed",
        payload={
            "call_id": record.call_id,
            "caller_user_id": record.caller_user_id,
            "callee_user_id": record.callee_user_id,
            "from_state": event.from_state,
            "reason": event.reason,
            "event_ts": event.event_ts,
        },
        respect_mute=False,
    )
    ...
    return CallActionOut(...)
except CallLifecycleError as exc:
    raise _call_error_to_http(exc)
```

### 4.2 `_expire_stale_invites` backstop — add fanout

In `app/routers/messaging.py` at approximately line 13335, within the inner `try` block:

```python
try:
    updated, event = timeout_call(
        call_id=call_id,
        actor_user_id="system",
        reason="server_timeout",
    )
    # GAP-0142: fanout so callee dismisses ringing overlay
    fanout_event_to_conversation(
        conversation_id=updated.conversation_id,
        sender_id="system",
        event_type="call.missed",
        payload={
            "call_id": updated.call_id,
            "caller_user_id": updated.caller_user_id,
            "callee_user_id": updated.callee_user_id,
            "from_state": event.from_state,
            "reason": event.reason,
            "event_ts": event.event_ts,
        },
        respect_mute=False,
    )
    logger.info("Server timeout expired stale invite call_id=%s", call_id)
except CallLifecycleError:
    pass
```

Note: `timeout_call` returns `(record, event)` — the current backstop discards the return value. Update the assignment accordingly.

### 4.3 `fanout_event_to_conversation` signature

`fanout_event_to_conversation` is defined at `app/routers/messaging.py:5465`. The call pattern is already established throughout the file. The `payload` dict should include `caller_user_id` and `callee_user_id` so the frontend SSE handler in `ConversationView.tsx:869-884` can determine whether the current user is the callee and dispatch `REMOTE_DECLINE`.

### 4.4 Dev/prod parity (SECOPS-007)

`fanout_event_to_conversation` dispatches to the in-process SSE connection registry, which operates identically in dev and prod. No mock or flag is needed. The fix is purely additive — two additional function calls, each with the same code path in all environments.

### 4.5 Backward compatibility

The fanout emits a new SSE event of type `call.missed` to conversation participants. The frontend already handles `call.missed` at `ConversationView.tsx:880-884`. No schema changes. No DynamoDB migrations.
