# GAP-0112: SSE event stream lacks viewer access check (BCAST-002) — Remediation Write-up

## 1. Summary & Classification

**Bug statement**: The broadcast SSE endpoint `GET /ui/broadcast/sessions/{session_id}/stream`
accepts any authenticated user and immediately subscribes them to the real-time event queue for
that session — without checking whether the caller is permitted to view the session. For private
broadcasts (visibility=`private`), this allows an arbitrary authenticated user to receive live
viewer-count updates, health telemetry, ad-break signals, and other real-time events intended
only for the session creator and explicitly invited viewers.

- **Severity**: HIGH (SEC-010 IDOR)
- **Source ticket**: BCAST-002 (second-pass as-built review)
- **GAP ID**: GAP-0112
- **Owning area**: Broadcast router — SSE event stream
- **Status**: Open
- **Effort**: S

**Claim verdict**: Confirmed. `app/routers/broadcast.py:717-737` shows the SSE handler acquires
`ctx` via `Depends(_ctx)` but immediately discards it with `_ = ctx` before subscribing the caller
to the queue. The `check_viewer_access` call that guards the `/viewers/join` and `/playback-url`
endpoints at lines 500-507 and 584-591 is entirely absent here.

**Impact in one line**: Any authenticated user can subscribe to the real-time SSE feed of any
private broadcast and receive continuously updated viewer counts, health metrics, and ad-break
control signals.

**Related tickets**: BCAST-002, GAP-0111 (session enumeration), GAP-0113 (chat stream IDOR),
GAP-0114 (locked message leakage), GAP-0115 (BCAST-004 duplicate of this gap), SECOPS-007.

## 2. Current-State Investigation (root cause)

### Vulnerable handler

`app/routers/broadcast.py`, lines 717–737:

```python
@router.get("/sessions/{session_id}/stream")
async def broadcast_event_stream_route(session_id: str, ctx: dict = Depends(_ctx)):
    """SSE stream for real-time broadcast events (viewer count, health updates)."""
    _ = ctx                            # ← caller identity intentionally discarded
    _ = get_session(session_id)        # 404 if session doesn't exist — no access check
    q = broadcast_sse_subscribe(session_id)

    async def gen():
        try:
            yield "event: hello\ndata: {}\n\n"
            while True:
                try:
                    item = await asyncio.wait_for(q.get(), timeout=15.0)
                    event_type = item.pop("_type", "update")
                    yield f"event: {event_type}\ndata: {json.dumps(item, ...)}\n\n"
                except asyncio.TimeoutError:
                    yield ": ping\n\n"
        finally:
            broadcast_sse_unsubscribe(session_id, q)

    return StreamingResponse(gen(), media_type="text/event-stream")
```

`_ = ctx` is the tell: the author knew `ctx` needed to be captured for FastAPI's dependency
injection to fire (forcing authentication), but never wired it into an access check. The session
existence check `get_session(session_id)` raises a 404 if unknown but performs no visibility gate.

### How other endpoints handle access control

The playback-URL minting endpoint at line 492 and the viewer-join endpoint at line 568 both
import and call `check_viewer_access`:

```python
# mint_playback_url_route (line 500)
from app.services.broadcast_privacy import check_viewer_access
check_viewer_access(
    session_id,
    ctx["user_sub"],
    creator_id=session.created_by,
    visibility=session.broadcast_privacy_visibility,
    invite_token=invite_token,
)

# viewer_join_route (line 584)
from app.services.broadcast_privacy import check_viewer_access
check_viewer_access(
    session_id,
    ctx["user_sub"],
    creator_id=session.created_by,
    visibility=session.broadcast_privacy_visibility,
    invite_token=invite_token,
)
```

The `check_viewer_access` function in `app/services/broadcast_privacy.py:224-254` raises
`HTTPException(403, ...)` when `visibility == "private"` and the caller is not the creator,
is not on the allowlist, and holds no valid invite token.

### What the SSE stream leaks

The SSE queue is populated by the broadcast state machine and health monitor. Each event includes:
- `viewer_count` updates (real-time audience size)
- `health` snapshots (bitrate, dropped frames, connection quality)
- `ad_break_start` / `ad_break_end` signals (ad-break timing, duration)
- `session_end` / `session_start` lifecycle events

For private celebrity or business sessions this data is commercially sensitive and privacy-related.

### Dev vs prod path

In dev, `broadcast_sse_subscribe` adds an `asyncio.Queue` to the in-process `_BROADCAST_SUBSCRIBERS`
dict (`app/services/broadcast_sse.py`). In production, the same in-process dict is used (uvicorn
runs with `--workers 1` per the project constraint). The vulnerability is present on both paths.

## 3. Impact / Exploit / Blast Radius

### Concrete exploit walkthrough

1. Attacker registers a normal account (or exploits GAP-0111 to enumerate `session_id` values for
   private sessions).
2. Issues a streaming GET: `GET /ui/broadcast/sessions/{session_id}/stream` with a valid session
   cookie.
3. The server returns HTTP 200 with `Content-Type: text/event-stream` and begins delivering events.
4. The attacker sits on the stream indefinitely (or reconnects on timeout) and receives:
   - Live viewer-count data (competitive intelligence — how many people are watching a private
     investor briefing, for example).
   - Ad-break timing signals — allows ad injection or timing-based analysis.
   - Health metrics — can infer whether the broadcast is degraded.

### Additional vector via session enumeration

Combined with GAP-0111 (which exposes all session IDs via the status filter), the attacker can
first enumerate all private sessions and then subscribe to their SSE feeds without any invite
token.

### Blast radius

- All broadcast sessions with `visibility=private` or `visibility=unlisted` are affected.
- Public sessions are unaffected (the fix should allow unrestricted access for public/unlisted
  sessions, matching the existing behaviour of the viewer-join endpoint).
- The SSE stream does not leak message text or user PII directly; the damage is metadata
  exfiltration and competitive intelligence.

## 4. Fix Design (code-level)

### Minimal change to `broadcast_event_stream_route`

Replace the `_ = ctx` discard with a proper access check, following the exact same pattern used at
lines 500 and 584:

```python
@router.get("/sessions/{session_id}/stream")
async def broadcast_event_stream_route(
    session_id: str,
    invite_token: Optional[str] = Query(default=None),
    ctx: dict = Depends(_ctx),
):
    """SSE stream for real-time broadcast events (viewer count, health updates)."""
    session = get_session(session_id)   # 404 if not found
    from app.services.broadcast_privacy import check_viewer_access
    check_viewer_access(
        session_id,
        ctx["user_sub"],
        creator_id=session.created_by,
        visibility=session.broadcast_privacy_visibility,
        invite_token=invite_token,
    )
    q = broadcast_sse_subscribe(session_id)

    async def gen():
        try:
            yield "event: hello\ndata: {}\n\n"
            while True:
                try:
                    item = await asyncio.wait_for(q.get(), timeout=15.0)
                    event_type = item.pop("_type", "update")
                    yield f"event: {event_type}\ndata: {json.dumps(item, separators=(',', ':'), default=str)}\n\n"
                except asyncio.TimeoutError:
                    yield ": ping\n\n"
        finally:
            broadcast_sse_unsubscribe(session_id, q)

    return StreamingResponse(gen(), media_type="text/event-stream")
```

The key changes are:
1. `session = get_session(session_id)` stores the result (instead of discarding it) so we can read
   `session.created_by` and `session.broadcast_privacy_visibility`.
2. `check_viewer_access(...)` is called with the same arguments used by the viewer-join and
   playback-url endpoints — no new logic is needed.
3. An `invite_token` query parameter is added so that holders of a valid invite token can still
   connect to the SSE stream for private sessions. This mirrors the viewer-join signature.
4. `_ = ctx` is removed.

### `check_viewer_access` behaviour recap

- `visibility != "private"` → returns immediately (public/unlisted sessions are accessible to any
  authenticated user, which is the existing intended behaviour).
- `viewer_id == creator_id` → returns immediately (creator always has access).
- `is_allowlisted(session_id, viewer_id)` → returns immediately.
- Valid `invite_token` → auto-enrolls viewer and returns.
- Otherwise → raises `HTTPException(403, "BROADCAST_PRIVATE_ACCESS_DENIED")`.

### Dev/Prod parity (SECOPS-007)

`check_viewer_access` is a pure Python function backed by DynamoDB calls to
`T.broadcast_sessions` (the allowlist sub-items). DynamoDB Local in dev and AWS DynamoDB in
production behave identically. No AWS-specific branch is involved. The `broadcast_privacy_visibility`
field is stored on the session record in both environments. The fix therefore provides identical
protection in dev and prod.

### Feature flag

No feature flag is required. The fix is a pure access-control tightening; existing public and
unlisted session SSE clients are unaffected (the check short-circuits immediately for non-private
sessions).

### Allowlist data model recap

Allowlist entries for a session are stored as separate DynamoDB items with a sort key of the
form `ALLOWLIST#{viewer_id}` in the `broadcast_sessions` table. `is_allowlisted` in
`broadcast_privacy.py` performs a `get_item` call for that key. `redeem_invite_token` validates
the token's HMAC, checks the remaining-uses counter, and writes the viewer onto the allowlist in
a single conditional update. Both operations are idempotent with respect to re-entry: a viewer
already on the allowlist gets an immediate `True` return regardless of token presence.

This design means the SSE access check carries the same cost as the viewer-join access check —
one DynamoDB `get_item` per connection attempt. For public sessions the cost is zero (short
circuit). For private sessions with long-lived SSE connections (clients reconnect every ~30s on
timeout) the allowlist check fires on each new TCP connection; this is acceptable at current
scale and is consistent with the playback-url endpoint's behaviour.

### Alternatives considered

- **Require explicit viewer registration before SSE**: Enforce that the caller has already called
  `/viewers/join`. This is too strict — it breaks tooling that subscribes to the SSE for monitoring
  before joining, and it adds an ordering dependency not present in the current API contract.
- **Return 200 but strip sensitive fields from SSE events for non-authorised callers**: This is
  complex, error-prone, and leaks the session's existence. Rejected in favour of the simple 403.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

Add to `tests/test_broadcast_sse_access.py`:

```python
import pytest
from unittest.mock import patch, MagicMock
from fastapi.testclient import TestClient
from app.main import app

def _make_private_session(session_id="sess_private", creator="alice"):
    m = MagicMock()
    m.id = session_id
    m.created_by = creator
    m.broadcast_privacy_visibility = "private"
    m.status = "live"
    return m

# ── BEFORE fix: non-member can connect to private session SSE ────────
def test_sse_stream_private_session_rejects_non_member():
    """Non-allowlisted user must receive 403 on private session SSE stream.

    Fails before fix (receives 200), passes after fix (receives 403).
    """
    from app.services.broadcast_privacy import check_viewer_access
    import httpx

    session = _make_private_session()
    with (
        patch("app.routers.broadcast.get_session", return_value=session),
        patch("app.routers.broadcast._ctx",
              return_value={"user_sub": "bob", "role": "user", "admin_profile": None}),
        patch("app.services.broadcast_privacy.is_allowlisted", return_value=False),
        patch("app.services.broadcast_privacy.redeem_invite_token", return_value=False),
    ):
        client = TestClient(app, raise_server_exceptions=False)
        resp = client.get("/ui/broadcast/sessions/sess_private/stream")

    assert resp.status_code == 403, (
        "Expected 403 for non-member on private session SSE; "
        f"got {resp.status_code}. Fix has not been applied."
    )
    assert resp.json()["detail"]["code"] == "BROADCAST_PRIVATE_ACCESS_DENIED"


def test_sse_stream_public_session_allows_any_user():
    """Public sessions must remain accessible to any authenticated user."""
    session = _make_private_session(session_id="sess_public")
    session.broadcast_privacy_visibility = "public"

    with (
        patch("app.routers.broadcast.get_session", return_value=session),
        patch("app.routers.broadcast._ctx",
              return_value={"user_sub": "bob", "role": "user", "admin_profile": None}),
        patch("app.routers.broadcast.broadcast_sse_subscribe", return_value=MagicMock()),
        patch("app.routers.broadcast.broadcast_sse_unsubscribe"),
    ):
        client = TestClient(app)
        # Use stream=True to avoid blocking on the generator
        with client.stream("GET", "/ui/broadcast/sessions/sess_public/stream") as resp:
            assert resp.status_code == 200
```

**Fails-before**: `test_sse_stream_private_session_rejects_non_member` receives 200 (the handler
ignores `ctx` and subscribes unconditionally).
**Passes-after**: The handler calls `check_viewer_access`, which raises 403 for Bob on Alice's
private session.

### Manual QA steps

1. Alice creates a private broadcast session.
2. As Bob (not on allowlist), attempt `GET /ui/broadcast/sessions/{alice_session_id}/stream`.
   - Before fix: receives 200 + SSE events.
   - After fix: receives 403 with `BROADCAST_PRIVATE_ACCESS_DENIED`.
3. Alice adds Bob to the allowlist via the existing allowlist management endpoint.
4. Bob retries the SSE stream — should now receive 200.
5. Bob uses an `invite_token` on a fresh private session — should receive 200 (auto-enrolled).
6. Alice's own SSE subscription to her private session must still work.
7. A public session SSE subscription by any user must still work.

### Observability

Log a warning metric `broadcast.sse.access_denied` when `check_viewer_access` raises. This allows
detection of probing attempts against private sessions.

### Connection lifecycle and reconnect semantics

SSE clients typically reconnect automatically when the server closes the stream or the TCP
connection drops (browser `EventSource` reconnects with `Last-Event-ID`). After the fix, a viewer
who had a valid connection to a private session's SSE stream and whose allowlist membership is
subsequently revoked will receive a 403 on the next reconnect. This is the correct behaviour:
access revocation propagates within one SSE timeout cycle (up to 15 seconds per the ping interval
at line 731). The `broadcast_sse_unsubscribe` call in the `finally` block of the generator ensures
the queue is cleaned up even when the stream terminates with a 403 before any events are delivered.
No memory leak occurs in the `_BROADCAST_SUBSCRIBERS` dict because `broadcast_sse_subscribe` is
not called until after `check_viewer_access` returns successfully.

### Rollback

Revert the one-line router change. No schema or data migrations involved.

### Risks & effort

- **Risk**: Invite-token flow. If a viewer has a valid invite token but forgot to call
  `/viewers/join` first, they can still pass the `invite_token` query parameter to the SSE
  endpoint and get enrolled automatically (same as the playback-url endpoint). This is intentional
  and matches the existing design.
- **Risk**: Long-lived SSE connections for public sessions. Public sessions (`visibility=public`)
  are unaffected — `check_viewer_access` short-circuits and the only cost is one field read from
  the already-fetched session object. No DynamoDB calls are made for public sessions.
- **Risk**: Frontend widget compatibility. Any frontend component that subscribes to the SSE
  stream directly (e.g. an embedded player iframe or a third-party analytics widget) must send
  the caller's auth cookie or Bearer token. The endpoint already requires authentication via
  `Depends(_ctx)`, so this is not a new requirement. The `invite_token` query parameter provides
  a token-based fallback for embed contexts where cookies are not forwarded cross-origin.
- **Effort**: S — approximately 1 hour. The fix is a two-line change plus test authoring.
- **Sequencing**: Apply before the next production deployment. Can be shipped independently of the
  other BCAST-002 fixes (GAP-0113, GAP-0114), but all three should ideally land in the same
  release to close the entire BCAST-002 access-control gap set atomically.
