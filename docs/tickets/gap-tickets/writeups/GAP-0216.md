# GAP-0216: Catalog item listing and search do not enforce `geo_mode`/`geo_countries` — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code before writing.

## 1. Summary & Classification

**Plain-English statement**: The `GET /ui/catalog/categories/{cat_id}/items` endpoint (list catalog items for a category) and the `GET /ui/catalog/items/search` endpoint (full-text catalog search) never call `check_geo_access()`. A creator who has configured per-content geo-restrictions via the `geo_rules` CRUD (e.g., only allow viewers from `["US", "CA"]` or block viewers from `["CN", "RU"]`) will find those restrictions silently ignored when viewers browse or search the catalog.

**Severity**: HIGH — Content licensing and OFAC/export-control obligations may require geo gating. Revenue consequences if geo-fenced premium content is delivered to blocked regions. Related to GEO-001 (source ticket) and SECOPS-007 (dev/prod parity for AWS-backed enforcement).

**Status**: Open. Source ticket: GEO-001. Owning area: Catalog / Geo-blocking.

**Claim verdict**: Confirmed. `app/routers/catalog.py` has zero imports of `geo_check` or `check_geo_access`. Neither `list_items` (line 374) nor `search_items` (line 441) fetches or inspects `geo_mode`/`geo_countries` fields. No correction to the original claim is required.

**Related tickets**: GAP-0217 (platform-level block list env-var only), SECOPS-007 (dev/prod parity).

## 2. Current-State Investigation (root cause)

### What GEO-001 built

`app/services/geo_check.py` exports `check_geo_access(request, geo_mode, geo_countries)`. It resolves the viewer's country from IP (with dev-mode `X-Geo-Country` header override) and raises `HTTPException(403)` when the viewer's country violates the supplied restriction. It is already wired into:

- `app/routers/video_listing.py:683–684` — per-video detail endpoint
- `app/routers/broadcast.py:485–488` and `broadcast.py:580–582` — two broadcast endpoints

The `geo_rules` router (`app/routers/geo_rules.py`) provides CRUD at `/ui/geo/catalog/{catalog_id}` (lines 441–503) that writes `geo_mode` and `geo_countries` into the DynamoDB `geo_rules` table — exactly the same pattern used for video and broadcast geo rules.

### What catalog.py does not do

`app/routers/catalog.py` never imports `check_geo_access` and contains no reference to `geo_mode` or `geo_countries`. Walking the two affected request paths:

**`list_items` (`GET /ui/catalog/categories/{cat_id}/items`, line 374–394)**:
```python
@router.get("/categories/{category_id}/items", response_model=CatalogItemListOut)
async def list_items(
    category_id: str,
    ctx=Depends(require_ui_session),
    ...
):
    category = _get_category_meta(category_id)      # loads DDB META record
    creator_id = category.get("creator_id")
    if creator_id and not can_access_creator(...):   # subscription check only
        raise HTTPException(status_code=403, ...)
    items, lek = _query_page(...)                    # fetches items
    ...
```

`_get_category_meta` loads the `CAT#{category_id}` / `META` record from DynamoDB. Even if `geo_mode` and `geo_countries` were stored there, the endpoint never reads or passes them to `check_geo_access`.

**`search_items` (`GET /ui/catalog/items/search`, line 441–470)**:
```python
@router.get("/items/search", response_model=CatalogItemListOut)
async def search_items(q: str = Query(...), ctx=Depends(require_ui_session), ...):
    ...
    resp = T.catalog.scan(**kwargs)
    for item in items:
        if item.get("entity") != "item":
            continue
        if _catalog_matches(query_tokens, item):
            matches.append(_catalog_item_out(item))
    ...
```

This is a full-table scan with no geo check at all. An item belonging to a geo-fenced catalog appears in search results regardless of the viewer's country.

### Where geo rules would live for catalog

`app/routers/geo_rules.py` already has endpoints for video (`/ui/geo/videos/{video_id}`) and broadcast (`/ui/geo/broadcasts/{broadcast_id}`) at lines 369–503. It stores restrictions in the `geo_rules` DynamoDB table keyed by content type and ID. An analogous path for catalog (`/ui/geo/catalog/{catalog_id}`) exists at line 441, writing to the same table pattern. The enforcement step — loading those rules and calling `check_geo_access()` inside `catalog.py` — is simply absent.

### Dev vs prod behaviour

In dev, `S.dev_mode = True` and `geo_check.py` accepts the `X-Geo-Country` header override. This means the gap is testable in the dev stack using that header. In production, MaxMind is the resolver. Because the catalog endpoints never call `check_geo_access` in either environment, the bug is identical in both — the dev environment does not accidentally mask it.

## 3. Impact / Exploit / Blast Radius

**Who is affected**: Any creator who uses the GEO-001 geo-restriction feature and sells catalog items. Any viewer who should be blocked from a region-restricted catalog.

**Concrete exploit**:
1. Creator calls `PATCH /ui/geo/catalog/{catalog_id}` with `{"geo_mode":"allow","geo_countries":["US"]}` — intending to restrict their digital-goods catalog to US buyers only (licensing requirement).
2. Viewer connecting from a blocked IP calls `GET /ui/catalog/categories/{cat_id}/items`.
3. Server returns the full item list. Geo restriction is never evaluated.
4. Same viewer calls `GET /ui/catalog/items/search?q=exclusive` — blocked items appear in results.

**Worst case**: A creator must comply with export-control regulations (e.g., digital goods under OFAC jurisdiction) and relies on the geo feature to block embargoed countries. Those restrictions are bypassed entirely through the catalog API. Compliance exposure is on the platform.

**Blast radius**: Catalog endpoints only. Video and broadcast are unaffected (already enforce). Platform-level block (`S.geo_platform_block_countries`) is also enforced in `geo_check.py` — but only if called. Since the catalog endpoints never call `check_geo_access`, the platform-level block is also bypassed for catalog item access.

**Data integrity**: No data is corrupted. The gap is an access-control omission, not a mutation defect.

## 4. Fix Design (code-level)

### Step 1 — Store geo rules on the catalog category

Geo restrictions for catalog should be stored on the category's `META` DynamoDB record (analogous to video/broadcast). The `geo_rules` router already has a `/ui/geo/catalog/{catalog_id}` endpoint (line 441) that writes `geo_mode`/`geo_countries` to the `geo_rules` table, keyed as `CONTENT#catalog#{catalog_id}`. The catalog `list_items` endpoint must load this record.

Alternatively (simpler and consistent with the existing meta pattern) store `geo_mode`/`geo_countries` directly on the `CAT#*/META` DDB record via the existing `geo_rules` update endpoint, removing the need for an extra DDB read.

The recommended approach is a secondary lookup in the geo_rules table, matching the video/broadcast pattern. This avoids patching the catalog schema and keeps geo data in one place.

### Step 2 — Enforce in `list_items`

In `app/routers/catalog.py`, add the `check_geo_access` call immediately after the category is loaded and subscription access is verified:

```python
# In list_items, after subscription check:
from app.services.geo_check import check_geo_access   # add to module imports

# After can_access_creator check:
_geo_mode, _geo_countries = _load_catalog_geo_rules(category_id)
if _geo_mode:
    check_geo_access(request, _geo_mode, _geo_countries)
```

Where `_load_catalog_geo_rules` is a small helper:

```python
def _load_catalog_geo_rules(catalog_id: str):
    """Return (geo_mode, geo_countries) for this catalog, or (None, None)."""
    try:
        item = T.geo_rules.get_item(
            Key={"pk": f"CONTENT#catalog#{catalog_id}", "sk": "GEO"}
        ).get("Item") or {}
    except Exception:
        return None, None
    return item.get("geo_mode"), item.get("geo_countries")
```

The `request: Request` parameter must be added to `list_items`:

```python
async def list_items(
    category_id: str,
    request: Request,        # <-- add
    ctx=Depends(require_ui_session),
    ...
):
```

### Step 3 — Enforce in `search_items`

`search_items` scans all items across all categories. Each item has a `category_id` field. Geo-rules should be checked per item (or per category batch). To avoid N+1 geo lookups, cache loaded rules in a dict keyed by `category_id` within the request:

```python
async def search_items(
    q: str = Query(...),
    request: Request,        # <-- add
    ctx=Depends(require_ui_session),
    ...
):
    ...
    _geo_cache: dict = {}

    for item in items:
        if item.get("entity") != "item":
            continue
        cat_id = item.get("category_id", "")
        if cat_id not in _geo_cache:
            _geo_cache[cat_id] = _load_catalog_geo_rules(cat_id)
        geo_mode, geo_countries = _geo_cache[cat_id]
        if geo_mode:
            try:
                check_geo_access(request, geo_mode, geo_countries)
            except HTTPException:
                continue          # skip blocked items instead of aborting
        if _catalog_matches(query_tokens, item):
            matches.append(_catalog_item_out(item))
    ...
```

For search, silently skipping geo-blocked items (rather than returning a 403) is the correct UX — the viewer should simply not see items they cannot access.

### Dev/Prod parity (SECOPS-007)

`check_geo_access` already implements the parity split:
- Dev: accepts `X-Geo-Country` header override (`geo_check.py:41–44`), falls back to `get_mock_country`, then to MaxMind.
- Prod: `X-Geo-Country` is ignored (header override gated on `S.dev_mode`); always uses MaxMind (or fails-closed if MaxMind unavailable).

No additional env-var gating is needed for this fix. The fix calls the same `check_geo_access` function in both environments, satisfying SECOPS-007.

### Impact on `CatalogItemOut` model and `geo_mode` field

The current `CatalogItemOut` Pydantic model (`app/models.py:574–591`) does not expose `geo_mode` or `geo_countries` to the viewer. This is intentional: viewers should not be told which countries are allowed or blocked, only whether they are permitted. If creator tooling needs to see a category's geo settings, that should be surfaced via the existing `GET /ui/geo/catalog/{catalog_id}` admin endpoint (accessible only to the category owner), not via the item-listing response.

No changes to `CatalogItemOut`, `CatalogCategoryOut`, or `CatalogItemCreateIn` are required for this fix. The geo enforcement is a read-time gate, not a data model change.

### Feature flag

`S.geo_blocking_enabled` (default `True`, controlled by `GEO_BLOCKING_ENABLED` env var) is honoured by `check_geo_access` at line 34 of `geo_check.py`. Setting `GEO_BLOCKING_ENABLED=0` disables all geo enforcement globally, including for catalog, without any code change.

### Alternatives considered

- Middleware-level geo check: rejected because catalog items are per-creator with per-item geo rules; a global middleware cannot load per-content rules without knowing the content ID ahead of time.
- Storing `geo_mode`/`geo_countries` in the `CatalogItemCreateIn` model and per item: too granular and duplicates data; category-level restriction is the appropriate granularity consistent with the existing geo_rules design.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

Add to `tests/test_catalog_geo.py`:

```python
"""Regression test for GAP-0216: catalog list_items and search_items must enforce geo rules."""
import pytest
from fastapi.testclient import TestClient
from unittest.mock import patch

def test_list_items_geo_blocked(client: TestClient, alice_session):
    """Viewer from blocked country must get 403 from list_items."""
    # Create category + item
    cat_resp = client.post("/ui/catalog/categories", json={"name": "GeoTest"}, cookies=alice_session)
    cat_id = cat_resp.json()["category_id"]
    client.post(f"/ui/catalog/categories/{cat_id}/items",
                json={"name": "Secret Item", "price_cents": 100}, cookies=alice_session)

    # Seed geo rule for this catalog: allow US only
    client.patch(f"/ui/geo/catalog/{cat_id}",
                 json={"geo_mode": "allow", "geo_countries": ["US"]}, cookies=alice_session)

    # Request from CN (blocked country) — should get 403 after fix
    resp = client.get(f"/ui/catalog/categories/{cat_id}/items",
                      cookies=alice_session, headers={"X-Geo-Country": "CN"})
    # FAILS BEFORE FIX: returns 200
    # PASSES AFTER FIX: returns 403
    assert resp.status_code == 403
    assert resp.json()["detail"]["code"] == "geo_blocked"


def test_search_items_excludes_geo_blocked(client: TestClient, alice_session):
    """Items from geo-blocked categories must not appear in search results."""
    cat_resp = client.post("/ui/catalog/categories",
                           json={"name": "GeoSearch"}, cookies=alice_session)
    cat_id = cat_resp.json()["category_id"]
    unique_name = "ExclusiveUSOnlyItem_GAP0216"
    client.post(f"/ui/catalog/categories/{cat_id}/items",
                json={"name": unique_name, "price_cents": 500}, cookies=alice_session)
    client.patch(f"/ui/geo/catalog/{cat_id}",
                 json={"geo_mode": "allow", "geo_countries": ["US"]}, cookies=alice_session)

    # CN viewer searches
    resp = client.get("/ui/catalog/items/search",
                      params={"q": "ExclusiveUSOnly"},
                      cookies=alice_session, headers={"X-Geo-Country": "CN"})
    assert resp.status_code == 200
    # FAILS BEFORE FIX: item appears in results
    # PASSES AFTER FIX: results list is empty
    names = [i["name"] for i in resp.json()["items"]]
    assert unique_name not in names
```

Both tests fail (200 returned, no geo check) before the fix. After the fix, the first returns 403 and the second returns an empty item list.

2. As Alice, create a catalog category and item, then call `PATCH /ui/geo/catalog/{cat_id}` with `{"geo_mode":"allow","geo_countries":["US"]}`.
3. Browse to the catalog page from the browser with `X-Geo-Country: CN` injected (e.g., via a browser extension or curl with the header).

### Observability

`check_geo_access` logs the block event via `HTTPException` with `detail.code = "geo_blocked"`. Application-level middleware or access log aggregation can alert on 403s from catalog endpoints. Add a metric counter `catalog_geo_blocked_total{endpoint="list_items|search"}` if a Prometheus hook is available.

### Rollout

- **Effort**: S (small) — the fix is ~20 lines across two functions plus the helper. The DDB geo_rules table and `check_geo_access` machinery already exist.
- **Backward compatibility**: Items previously accessible to all viewers remain accessible (no geo rule stored = `geo_mode is None` = no enforcement). Only items whose category has an active geo rule are affected.
- **Migration**: No DDB schema change required. Existing `geo_rules` table pattern covers catalog.
- **Rollback**: Set `GEO_BLOCKING_ENABLED=0` in `.env` to disable all geo enforcement instantly without code deployment.
- **Risk**: Low. The fix adds a read (one DDB `get_item` per category, cached across the request for search) and delegates to already-tested `check_geo_access`. The only new failure mode is a DDB read error in `_load_catalog_geo_rules`, which is caught and returns `(None, None)` (fail-open), preserving current behaviour.
- **Sequencing**: Depends on GEO-001 being deployed (already is). No dependency on GAP-0217. Can ship independently.

### Note on the `can_access_creator` subscription check

The existing `list_items` endpoint already enforces a creator-subscription gate at line 383:
```python
if creator_id and not can_access_creator(ctx["user_sub"], creator_id):
    raise HTTPException(status_code=403, detail="Subscription required to view this catalog.")
```
The geo check should run after this check (as shown in the fix above), so subscription access is verified before geo resolution, avoiding an unnecessary GeoIP lookup for users who do not have subscription access. This ordering matches the pattern used in `video_listing.py` where auth and subscription checks precede the `check_geo_access` call.
