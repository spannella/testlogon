# GAP-0185: TOCTOU window between status check and atomic increment — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against real code before writing; cites `file:line`.

## 1. Summary & Classification

**Bug statement**: `consume_share_link` in `app/services/file_share_links.py` performs pre-flight validity checks (revoked, expired, used, password) against a stale DynamoDB snapshot read at line 297, then executes an atomic `update_item` at line 318. The gap ticket claims that `is_revoked` and `expires_at` are missing from the `ConditionExpression`. **This claim is inaccurate**: the actual code at lines 321–323 already includes both predicates. However, a real — and distinct — TOCTOU window remains: the password verification at line 311 occurs entirely outside the `ConditionExpression`, and the `max_downloads` ceiling is sourced from the stale pre-read item rather than from the atomic update's current DDB state.

- **Severity**: HIGH (residual TOCTOU; original claim partially inaccurate)
- **Source ticket**: FILES-001
- **Owning area**: File manager / Public share links
- **Status**: Open (partially fixed — `is_revoked`/`expires_at` already in `ConditionExpression`; password check and stale `max_downloads` not atomic)
- **Verdict**: **Claim corrected**. The specific fix described in the ticket (`add & Attr("is_revoked").ne(True) & Attr("expires_at").gt(now_ts())`) is already present at lines 322–323. The residual TOCTOU involving password verification and stale `max_downloads` is the true remaining gap.
- **One-line impact**: In a concurrent download scenario, two callers with the correct password can simultaneously pass the pre-check, both reaching the atomic update — the update's `ConditionExpression` catches the over-limit case, but a successful file decrypt begins before the condition check completes, potentially leaking content to an extra caller before the 410 is returned.
- **Related tickets**: GAP-0184 (rate limiting, same service/router), FILES-001

## 2. Current-State Investigation (root cause)

### The consume_share_link flow (file:line)

`app/services/file_share_links.py:291–347` implements the full flow:

**Step 1 — Stale snapshot read** (line 297):
```python
item = _get_link(link_id)
```
This is a plain DynamoDB `get_item` (eventually consistent by default). The returned item is a point-in-time snapshot.

**Step 2 — Pre-flight checks against snapshot** (lines 299–313):
```python
if bool(item.get("is_revoked")):          # line 299 - stale read
    raise HTTPException(410, "link_revoked")
if _is_expired(item):                      # line 302 - stale read
    raise HTTPException(410, "link_expired")
if _is_used(item):                         # line 305 - stale read
    raise HTTPException(410, "link_used")

password_hash = item.get("password_hash")  # line 309
if password_hash:
    if not password or not _verify_password(password, str(password_hash)):
        raise HTTPException(403, "invalid_password")  # line 313
```

**Step 3 — Atomic update** (lines 317–326):
```python
updated = _table().update_item(
    Key={"link_id": link_id, "sk": SK_META},
    UpdateExpression="SET download_count = download_count + :one",
    ConditionExpression=Attr("download_count").lt(max_downloads)
    & Attr("is_revoked").ne(True)
    & Attr("expires_at").gt(now_ts()),
    ExpressionAttributeValues={":one": 1},
    ReturnValues="ALL_NEW",
)
```

### What the ticket says vs. what the code contains

The ticket fix reads: *"fold the `is_revoked` and `expires_at` checks into the `ConditionExpression`"*. Examining lines 321–323:

```python
ConditionExpression=Attr("download_count").lt(max_downloads)
& Attr("is_revoked").ne(True)            # already present
& Attr("expires_at").gt(now_ts()),       # already present
```

Both predicates are already present. The ticket's suggested fix has been applied (presumably during the initial ENTERPRISE-005/FILES-001 implementation). **The ticket claim is inaccurate**: the specific issue it describes is not present in the current code.

### The residual TOCTOU gaps

**Gap A — Password verification is outside the atomic operation**

The password check (line 311, `_verify_password(password, str(password_hash))`) uses `password_hash` from the stale snapshot. An attacker cannot easily exploit this because password hashes cannot be revoked or changed after link creation in the current service (there is no "change password" endpoint for share links). The practical risk is low, but the architectural gap is real: the password check is not part of the conditional update.

**Gap B — `max_downloads` sourced from stale item**

At line 315: `max_downloads = _int(item.get("max_downloads"), 1)`. This value is read from the snapshot obtained at line 297. The ConditionExpression at line 321 uses `Attr("download_count").lt(max_downloads)` with this stale value as the comparison target in `:max_downloads`. If two concurrent callers both read `download_count=0, max_downloads=1` and both pass the pre-check (`_is_used` returns `False`), they both reach the atomic update. The ConditionExpression with `download_count < 1` means only one of the two updates succeeds — DynamoDB's conditional write is correct here. However, both callers have already called `_verify_password` (which is expensive bcrypt and happens before the atomic gate), and both proceed to trigger the S3 `get_object` and `kms_decrypt` at lines 337–339 before the second caller's `update_item` raises `ConditionalCheckFailedException`. The file content is fetched and decrypted for both callers even though only one will receive a successful HTTP response.

**Gap C — S3 fetch and decrypt before commit confirmation**

Lines 334–347 (S3 `get_object`, `decrypt_file_content`) execute against the `new_item = updated.get("Attributes", item)` which is the *result* of the successful `update_item`. This is actually correct for the caller whose `update_item` succeeds — they get the latest state. For the concurrent loser, the `update_item` raises `ConditionalCheckFailedException` at line 328, and they never reach line 334. So the content leak path is: caller passes pre-check → both reach `update_item` → one succeeds → both now proceed differently. The content is only decrypted after the atomic write succeeds, so this gap does not cause actual double-download. The real risk is CPU/KMS cost on the second caller's pre-flight (bcrypt + DynamoDB read) with no useful work done.

### Summary of what is and is not broken

| Check | In ConditionExpression? | TOCTOU risk |
|---|---|---|
| `is_revoked` | Yes (line 322) | Covered atomically |
| `expires_at` | Yes (line 323) | Covered atomically |
| `download_count < max_downloads` | Yes (line 321) | Covered atomically |
| Password correct | No | Low risk (hash immutable) |
| S3 decrypt after commit | After `update_item` | Correct order |

## 3. Impact / Exploit / Blast Radius

### Concurrent download race (over-download prevention)

The ConditionExpression `download_count < max_downloads` ensures only one `update_item` wins when two concurrent requests race on a single-download link. The loser receives `ConditionalCheckFailedException` → `HTTP 410 link_used`. **No double-download of file content is possible via this path.** The atomic guard is correct.

### bcrypt CPU amplification under concurrency

For a password-protected link, each concurrent caller runs `bcrypt.checkpw` before reaching the DynamoDB atomic gate. A single-download password-protected link targeted by two concurrent correct-password requests causes two bcrypt operations (each ~100ms of CPU) even though only one download succeeds. Without IP-based rate limiting (GAP-0184), this can be used to amplify bcrypt CPU cost at no attacker cost.

### Eventual-consistency read risk

`_get_link` at line 297 uses a default `get_item` call which is eventually consistent in DynamoDB. In theory, a revocation event (`is_revoked` set to `True`) could be invisible in the stale read but would be caught by the ConditionExpression. Similarly, `expires_at` in the past is caught by the conditional update. In practice, the ConditionExpression makes the pre-checks redundant for correctness — their sole remaining value is fast-path rejection (avoiding the bcrypt cost for obviously invalid links) and improved error response clarity (the pre-checks return specific error codes; the ConditionExpression maps all failures to `link_used`).

### Financial

Concurrent requests hitting the S3 + KMS + DynamoDB path before the condition check can inflate AWS costs. Without rate limiting (GAP-0184), this is exploitable for cost amplification.

### Blast radius

- All public share link downloads.
- Correctness is intact (no actual double-file-download); the remaining issues are cost amplification and residual architectural TOCTOU.

## 4. Fix Design (code-level)

### Change 1: Use strongly consistent read for `_get_link`

**File**: `app/services/file_share_links.py`

Replace the default (eventually consistent) read with a strongly consistent read:

```python
def _get_link(link_id: str) -> Dict[str, Any]:
    resp = _table().get_item(
        Key={"link_id": link_id, "sk": SK_META},
        ConsistentRead=True,   # <-- ADD: prevent stale revocation reads
    )
    item = resp.get("Item")
    if not item:
        raise HTTPException(404, "link_not_found")
    return item
```

This closes the eventual-consistency window for the pre-checks, ensuring that a revocation or expiry that occurred milliseconds before the download attempt is visible.

### Change 2: Differentiate ConditionExpression failure codes

Currently `ConditionalCheckFailedException` is mapped uniformly to `link_used` (line 329). After adding strong reads, the pre-checks remain for fast-path user-friendly errors (revoked → 410, expired → 410, wrong password → 403). The ConditionExpression is the correctness guarantee; the pre-checks are the UX layer. No change is needed to the ConditionExpression itself — it is already complete.

### Change 3: Move max_downloads read inside atomic operation (optional, low priority)

The stale `max_downloads` used in the ConditionExpression is not exploitable (the value cannot be changed after link creation), but for full correctness, `max_downloads` could be expressed as a comparison against the stored attribute rather than a client-side value:

```python
# Current (stale client-side value):
ConditionExpression=Attr("download_count").lt(max_downloads)

# Improved (all server-side, no stale client value):
# Use a reference attribute expression — not natively supported by DynamoDB
# for "download_count < max_downloads" without passing max_downloads as a value.
# The current form is acceptable because max_downloads is immutable post-creation.
```

Because `max_downloads` is write-once (set at `create_share_link`, never updated), the stale-read risk is zero in practice. No change is recommended here.

### SECOPS-007 dev/prod parity

- `ConsistentRead=True` works identically against DynamoDB Local (dev) and AWS DynamoDB (prod). It increases read cost in prod (strongly consistent reads count as 2x read capacity units) but is appropriate for a security-critical download gate.
- No environment flag or conditional is needed — the same consistent-read is correct in both environments.
- The change is inside `_get_link`, a private function called only from `consume_share_link` and `get_share_link_info`. Both benefit from consistent reads.

### Backward compatibility

`ConsistentRead=True` is a read behavior change only. No DynamoDB schema, item structure, or API response shape is affected. The read latency may increase by ~1–2ms in prod (DynamoDB consistent reads add one round-trip hop). This is acceptable for a security-critical download endpoint.

### Alternatives considered

1. **Remove the pre-checks entirely and rely only on the ConditionExpression**: Cleaner but loses UX differentiation (all failures → `link_used`). Kept as a future simplification option.
2. **Use DynamoDB Transactions (`transact_write`)**: Stronger atomicity but adds transaction overhead and is overkill here since the `update_item` ConditionExpression already provides the necessary atomic guarantee.
3. **Add password check inside ConditionExpression**: DynamoDB ConditionExpressions cannot run bcrypt. Password verification must remain in application code. The current order (verify password before incrementing) is correct; the risk of CPU amplification is addressed by GAP-0184's rate limiting.

### Regression test (fails before fix, passes after)

**File**: `tests/test_share_link_toctou.py` (new file)

```python
"""GAP-0185: consume_share_link must use ConsistentRead=True."""
from unittest.mock import patch, MagicMock, call
import pytest
from fastapi import HTTPException

from app.services.file_share_links import consume_share_link


def _make_item(*, is_revoked=False, download_count=0, max_downloads=1,
               expires_at=9999999999, password_hash=None):
    return {
        "link_id": "test-link",
        "sk": "META",
        "is_revoked": is_revoked,
        "download_count": download_count,
        "max_downloads": max_downloads,
        "expires_at": expires_at,
        "password_hash": password_hash,
        "encrypted_s3_key": "share-links/test-link/encrypted",
        "encryption_key_wrapped": "loc:AAEC+A==:deadbeef" * 2,

        "file_size_bytes": 10,
        "content_type": "text/plain",
        "owner_sub": "u1",

def test_get_link_uses_consistent_read():
    """_get_link must pass ConsistentRead=True to DynamoDB get_item."""
    mock_table = MagicMock()
    mock_table.get_item.return_value = {"Item": _make_item()}

         patch("app.services.file_share_links._is_expired", return_value=False), \
         patch("app.services.file_share_links._is_used", return_value=True):

        with pytest.raises(HTTPException):
            consume_share_link(link_id="test-link")

        # Check that get_item was called with ConsistentRead=True
        call_kwargs = mock_table.get_item.call_args
        assert call_kwargs is not None, "get_item was not called"
        kwargs = call_kwargs.kwargs if call_kwargs.kwargs else call_kwargs[1]
        # Accept positional or keyword arg
        all_args = {**dict(zip(["Key", "ConsistentRead"], call_kwargs.args)),
                    **call_kwargs.kwargs}
        assert all_args.get("ConsistentRead") is True, (
            "Expected ConsistentRead=True in get_item call; "
            "got: " + repr(call_kwargs)

    ce_block = source[ce_start:ce_start + 300]
    assert "is_revoked" in ce_block, "is_revoked must be inside ConditionExpression"
    assert "expires_at" in ce_block, "expires_at must be inside ConditionExpression"


def test_concurrent_single_download_link_only_one_succeeds():
    """Only one of two concurrent callers should succeed on a max_downloads=1 link."""
    from botocore.exceptions import ClientError

    item = _make_item(max_downloads=1, download_count=0)
    call_count = {"update": 0}

    def mock_update_item(**kwargs):
        call_count["update"] += 1
        if call_count["update"] > 1:
            # Simulate second concurrent caller hitting ConditionCheckFailed
            error_response = {"Error": {"Code": "ConditionalCheckFailedException"}}
            raise ClientError(error_response, "UpdateItem")
        # Return successful update result with updated attributes
        updated_item = {**item, "download_count": 1}
        return {"Attributes": updated_item}

    mock_table = MagicMock()
    mock_table.get_item.return_value = {"Item": item}
    mock_table.update_item.side_effect = mock_update_item

    with patch("app.services.file_share_links._table", return_value=mock_table), \
         patch("app.services.file_share_links._unwrap_key", return_value=b"\x00" * 32), \

            consume_share_link(link_id="test-link")
```

### Metrics / observability

`ConditionalCheckFailedException` is already caught and logged at line 329 (as `HTTPException(410)`). After adding `ConsistentRead=True`, add a counter increment in `_get_link` for monitoring:

```python
logger.debug("share link get_item (consistent)", extra={"link_id": link_id})
```

The 410 response rate on the download endpoint is the key SLO metric: a sudden spike indicates either an attack or a bug in link state management.

### Rollback

Remove `ConsistentRead=True` from the `get_item` call in `_get_link`. No data migration or schema change needed.

### Risks

- **Increased DynamoDB read cost in prod**: Strongly consistent reads consume 2x read capacity units. For a link that receives at most a handful of downloads, this is negligible. If share links ever scale to millions of downloads per day, this cost should be re-evaluated.
- **Latency impact**: Minimal. DynamoDB strongly consistent reads add approximately 1–3ms of additional latency compared to eventually consistent reads.
- **No correctness regression**: The ConditionExpression already provides the atomic safety net. The consistent read improves the pre-check accuracy for better UX error codes and closes the theoretical eventual-consistency window.

### Effort: S (Small)

One line change (`ConsistentRead=True` in `_get_link`). Tests are offline/pytest only.

### Sequencing

Apply together with GAP-0184 (rate limiting) in the same PR — both touch `app/services/file_share_links.py` and `app/routers/file_share_links.py`. The rate-limiting fix (GAP-0184) is a prerequisite for fully closing the bcrypt CPU amplification risk that this TOCTOU exposes to concurrent callers.
