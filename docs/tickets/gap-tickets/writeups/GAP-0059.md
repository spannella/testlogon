# GAP-0059: No Duplicate Active Boost Guard — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against live code at
> `app/services/content_boost.py`, `app/routers/content_boost.py`,
> `scripts/local-ddb-init.py`. No investigation doc exists.

## 1. Summary & Classification

**Gap**: `app/services/content_boost.py:create_boost` (lines 147–213) allows a user to
create multiple simultaneous active boosts for the same `(content_type, content_id)`
pair. There is no guard that checks whether an active boost already exists before
charging the wallet and writing a new boost record. An owner can stack multiple active
boosts for the same content, paying the full budget amount repeatedly with no validation
or error.

- **Severity**: HIGH
- **Source ticket**: ADS-012
- **Owning area**: Content Boost / Billing
- **Status**: Open
- **Related tickets**: GAP-0058 (ownership validation, must be fixed first);
  ADS-012 (content boost feature)
- **Verdict**: Claim confirmed. `create_boost` makes no query to the existing GSI2
  (`CONTENT#{type}#{id}` partition key) before writing. The `active_boost_for_content`
  read function (line 376) does exist and correctly finds active boosts, but is never
  called from the write path.

**One-line impact**: A creator (or attacker with ownership, if GAP-0058 is also present)
can accidentally or deliberately pay the boost budget multiple times for the same
content, causing double-charges, distorted ranking weights, and confusing billing records.

## 2. Current-State Investigation (root cause)

### `create_boost` — no pre-write duplicate check

`app/services/content_boost.py:147–213` transitions directly from input validation to
wallet charge:

```python
# content_boost.py:176–212
if _wallet_balance(owner_sub) < budget_cents:
    raise ValueError("insufficient wallet balance")
try:
    _wallet_charge(owner_sub, budget_cents, ...)
except Exception:
    raise ValueError("insufficient wallet balance")

item = {
    "pk": _pk(bid),
    "sk": "META",
    ...
    "GSI2PK": f"CONTENT#{content_type}#{content_id}",
    "GSI2SK": Decimal(int(ends_at)),
}
T.content_boosts.put_item(Item=item)
return _boost_out(item, now=ts)
```

There is no query to GSI2 before the `put_item`. The `active_boost_for_content` function
at line 376 that would detect an existing active boost is never invoked in this path.

### GSI2 is correctly set up for the check

`app/services/content_boost.py:208–210`:

```python
# GSI2: content lookup for the elevation hook (ends_at as range key)
"GSI2PK": f"CONTENT#{content_type}#{content_id}",
"GSI2SK": Decimal(int(ends_at)),
```

Every created boost writes a `GSI2PK` of `CONTENT#{type}#{id}`. The
`active_boost_for_content` function (line 376–391) queries this GSI in descending order
(`ScanIndexForward=False`) and iterates items calling `is_boost_active`. This read path
is fully functional — it is simply never called before a write.

### `active_boost_for_content` is the correct guard

```python
# content_boost.py:376–391
def active_boost_for_content(content_type, content_id, *, now=None):
    res = T.content_boosts.query(
        IndexName="GSI2",
        KeyConditionExpression=Key("GSI2PK").eq(f"CONTENT#{content_type}#{content_id}"),
        ScanIndexForward=False,
    )
    for raw in res.get("Items", []):
        if is_boost_active(raw, now=now):
            return _boost_out(raw, now=now)
    return None
```

Calling this before `_wallet_charge` and raising `ValueError` if it returns a non-None
value is the minimal fix.

### DynamoDB table schema supports the check

`scripts/local-ddb-init.py:687–695` (for `BroadcastSessions`) and the `content_boosts`
table (referenced via `T.content_boosts` in the service) both have GSI2 set up with
`GSI2PK` and `GSI2SK`. The query path is functional in both local DynamoDB and AWS
DynamoDB.

### Race condition between check and write

DynamoDB does not natively support compare-and-set on a GSI. The check-then-write
pattern has a TOCTOU (time-of-check/time-of-use) window. However, this is acceptable
for the boost use case:

- The same user is unlikely to issue two simultaneous boost-create requests in the
  millisecond window between the GSI query and the `put_item`.
- In the event of a race where two boosts slip through, the worst case is a
  double-charge — which was already the status quo without the guard. The guard
  eliminates the common case (serial duplicate clicks / programmatic retry loops).
- A stronger guarantee can be provided via a DynamoDB Conditional Expression on the
  `put_item` if the product requirement demands it (see section 4, alternatives).

## 3. Impact / Exploit / Blast Radius

**Who is affected**: Any creator who accidentally submits the boost form twice (e.g. by
double-clicking), and any attacker who intentionally stacks boosts.

**Exploit walkthrough — accidental double-charge**:

1. Creator opens the boost dialog, enters $50 budget, and clicks "Boost".
2. The frontend button is not debounced (not a frontend bug, but a common UX issue).
3. Two POST requests reach the backend within 100 ms.
4. Both pass the wallet balance check (balance $100 > $50 each time, before the debit
   settles).
5. Two boost records are written for `CONTENT#post#post_001`.
6. Creator's wallet is debited $100 ($50 x 2).
7. Feed serving applies `BOOST_RANK_WEIGHT = 1000` twice? No — `active_boost_for_content`
   returns only the first active boost, so ranking is not further elevated. But the
   second boost budget is still consumed by `record_spend` calls in the serving path,
   meaning the creator pays double without any additional benefit.

**Exploit walkthrough — intentional stacking**:

1. Attacker creates 10 boosts for the same post, each with a $10 budget.
2. Each boost independently calls `record_spend` as the serving pipeline runs.
3. The attacker pays $100 total. However, only one boost is ever returned by
   `active_boost_for_content` (the newest `ends_at`), so the extra spend flows into
   completed-status boosts that deliver no additional elevation.
4. Net effect: attacker wastes $90, potentially filling the DDB `content_boosts` table
   with stale records.

**Blast radius for legitimate creators**:

- Wallet drained unexpectedly due to unintended duplicate submissions.
- Billing ledger has multiple `content_boost_charge` entries for the same content within
  a short window — confusing for support and audit.
- `list_boosts` (GSI1 query) returns multiple active records for the same content,
  confusing the creator dashboard.

**Data integrity**: Multiple active boosts for the same content create ambiguity in
`active_boost_for_content` (it returns "newest wins" but the selection is arbitrary if
`ends_at` values are identical to within the resolution of the current timestamp).

## 4. Fix Design (code-level)

### Approach: query GSI2 before write, raise ValueError if active boost found

This is the minimal-change, lowest-risk fix. It fully eliminates the common case of
duplicate boosts with no schema changes.

#### 4.1 Add duplicate check in `create_boost`

In `app/services/content_boost.py`, add the following block after the input validation
and after `_verify_content_ownership` (from GAP-0058 fix) but before the wallet charge:

```python
def create_boost(
    owner_sub: str,
    *,
    content_type: str,
    content_id: str,
    budget_cents: int,
    duration_seconds: int,
    now: int | None = None,
) -> dict[str, Any]:
    if content_type not in ALLOWED_CONTENT_TYPES:
        raise ValueError(...)
    if not content_id:
        raise ValueError(...)
    if budget_cents <= 0:
        raise ValueError(...)
    if duration_seconds <= 0:
        raise ValueError(...)

    # GAP-0058: ownership check (see companion fix)
    _verify_content_ownership(owner_sub, content_type, content_id)

    # GAP-0059: duplicate active boost guard
    ts = _now(now)
    existing = active_boost_for_content(content_type, content_id, now=ts)
    if existing is not None:
        raise ValueError(
            f"an active boost already exists for this content "
            f"(boost_id={existing['boost_id']}, "
            f"expires={existing['ends_at']})"
        )

    # Wallet charge and DDB write follow unchanged
    bid = f"boost_{uuid.uuid4().hex[:12]}"
    ends_at = ts + duration_seconds
    ...
```

Note that `ts = _now(now)` is moved up from its original location (line 169) to allow
passing it to `active_boost_for_content`. The value is identical — it is just computed
earlier.

#### 4.2 Router error mapping (no change needed)

The existing `except ValueError as exc: raise HTTPException(400, ...)` in
`app/routers/content_boost.py:33–34` already maps `ValueError` to HTTP 400. The new
duplicate-boost error message is descriptive enough for the frontend to display.

Optionally, add a distinct HTTP 409 (Conflict) for the duplicate case — this is more
RESTful but requires a custom exception class:

```python
# In content_boost.py, define:
class DuplicateBoostError(ValueError):
    pass

# In the guard:
raise DuplicateBoostError(
    f"active boost already exists (boost_id={existing['boost_id']})"
)

# In the router:
except DuplicateBoostError as exc:
    raise HTTPException(status_code=409, detail=str(exc))
except ValueError as exc:
    raise HTTPException(status_code=400, detail=str(exc))
```

HTTP 409 is preferable as it allows the frontend to distinguish "invalid input" from
"resource conflict" and offer an appropriate UX (e.g. "You already have an active boost
for this post — cancel it before creating a new one").

#### 4.3 Stronger guarantee: DynamoDB Conditional Expression (optional, high-effort)

For a race-free guarantee, replace the `T.content_boosts.put_item(Item=item)` with a
`put_item` that uses a `ConditionExpression` on the GSI2 PK:

```python
# This requires a separate item-existence check on the MAIN table (pk/sk),
# NOT directly on a GSI attribute (DDB does not support conditional writes
# scoped to a GSI).
#
# Alternative: use an auxiliary lock item in a separate table:
T.content_boosts.put_item(
    Item={
        "pk": f"BOOSTLOCK#{content_type}#{content_id}",
        "sk": "LOCK",
        "owner_sub": owner_sub,
        "expires_at": Decimal(ends_at),
    },
    ConditionExpression="attribute_not_exists(pk)",
)
```

This is the true ACID guarantee but requires a schema addition (a new "lock" item pattern
in the boosts table). It is out of scope for this gap and should be tracked as a
follow-on hardening task.

### Dev/Prod parity (SECOPS-007)

The `active_boost_for_content` GSI2 query uses `T.content_boosts`, which maps to
`ContentBoosts` in both DynamoDB Local (dev) and AWS DynamoDB (prod). No mock paths or
conditional code are needed. The `now` parameter is injectable in both environments for
test determinism.

### Alternatives considered

- **Frontend debounce only**: Insufficient — a determined user or API caller can
  still submit duplicates. The guard must be server-side.
- **Cancel existing boost on new create**: Replaces the old boost instead of rejecting
  the second. Rejected — it is a destructive action (refunds the old boost budget) that
  should require explicit user action. HTTP 409 with a message pointing to the existing
  boost is less surprising.
- **Allow multiple boosts but cap count per content**: Adds complexity for no benefit.
  The ADS-012 spec is clear: one active boost per content item at a time.

## 5. Testing, Verification & Rollout

### Regression test (pytest offline)

```python
# tests/test_content_boost_duplicate.py
import pytest
from unittest.mock import patch, MagicMock
from decimal import Decimal
from app.services.content_boost import create_boost, STATUS_ACTIVE

OWNER = "user_alice"
POST_ID = "post_001"

def _mock_active_boost():
    return {
        "boost_id": "boost_existing",
        "owner_sub": OWNER,
        "content_type": "post",
        "content_id": POST_ID,
        "budget_cents": 1000,
        "spent_cents": 0,
        "remaining_cents": 1000,
        "duration_seconds": 3600,
        "starts_at": 1000000,
        "ends_at": 1003600,
        "status": STATUS_ACTIVE,
        "created_at": 1000000,
    }

def test_duplicate_active_boost_rejected(monkeypatch):
    """Creating a second active boost for the same content is rejected."""
    with patch("app.services.content_boost.active_boost_for_content",
               return_value=_mock_active_boost()), \
         patch("app.services.content_boost._verify_content_ownership"), \
         patch("app.services.content_boost._wallet_charge") as mock_charge:
        with pytest.raises(ValueError, match="active boost already exists"):
            create_boost(
                OWNER,
                content_type="post",
                content_id=POST_ID,
                budget_cents=500,
                duration_seconds=1800,
            )
        mock_charge.assert_not_called()   # wallet NOT charged

def test_new_boost_allowed_when_no_existing(monkeypatch):
    """Boost creation proceeds normally when no active boost exists."""
    with patch("app.services.content_boost.active_boost_for_content",
               return_value=None), \
         patch("app.services.content_boost._verify_content_ownership"), \
         patch("app.services.content_boost._wallet_balance", return_value=10000), \
         patch("app.services.content_boost._wallet_charge"), \
         patch("app.core.tables.T.content_boosts") as mock_tbl:
        mock_tbl.put_item.return_value = {}
        result = create_boost(
            OWNER,
            content_type="post",
            content_id=POST_ID,
            budget_cents=500,
            duration_seconds=1800,
        )
        assert result["owner_sub"] == OWNER

def test_boost_allowed_after_previous_completed(monkeypatch):
    """A new boost is allowed once the previous one is completed."""
    completed_boost = {**_mock_active_boost(), "status": "completed"}
    with patch("app.services.content_boost.active_boost_for_content",
               return_value=None), \
         patch("app.services.content_boost._verify_content_ownership"), \
         patch("app.services.content_boost._wallet_balance", return_value=10000), \
         patch("app.services.content_boost._wallet_charge"), \
         patch("app.core.tables.T.content_boosts") as mock_tbl:
        mock_tbl.put_item.return_value = {}
        result = create_boost(
            OWNER,
            content_type="post",
            content_id=POST_ID,
            budget_cents=500,
            duration_seconds=1800,
        )
        assert result is not None
```

**Fails before fix**: `test_duplicate_active_boost_rejected` will not raise `ValueError`
because the check is absent; `mock_charge.assert_not_called()` will fail.

**Passes after fix**: The guard raises `ValueError("active boost already exists...")`;
the wallet is never charged.

### Metrics / observability

- Log on `ValueError("active boost already exists")` responses: these indicate
  either UI bugs (no debounce) or programmatic abuse.
- Monitor `content_boost_charge` ledger entries per-user per-day; alert if any user
  accumulates more than 3 charges per content item within a day (would indicate the
  guard is being bypassed via rapid cancellations).

### Rollout

- Deploy with the same release as GAP-0058 (ownership check). The duplicate guard
  calls `active_boost_for_content`, which requires a correct GSI2 index on the
  `ContentBoosts` table — this index already exists (verified via `local-ddb-init.py`).
- No schema migrations needed.
- **Rollback**: Remove the `active_boost_for_content` guard block in `create_boost`.

**Effort**: S (small). ~12 lines of new Python in one service file; optional 5-line
router change for HTTP 409.
**Sequencing**: Merge after GAP-0058 so the ordering of checks in `create_boost` is:
ownership first, then duplicate guard.

### Risk assessment

The pre-write GSI2 query adds one DynamoDB `Query` call (≤1 ms on a sparse table) to
every boost-creation request. This is negligible for an infrequent user action.

The TOCTOU window between the GSI2 read and the `put_item` write is small but non-zero.
In practice, the window is bounded by the time between the GSI2 query response and the
`put_item` — typically under 5 ms in the same AWS region. The probability of two
concurrent boost-create requests for the same content from the same user within this
window is extremely low in normal use. For determined adversarial use (e.g. a script
hammering the endpoint), the GAP-0056 per-key rate limit (when deployed) will throttle
the requests before a race can be exploited at scale.

If a TOCTOU race does slip through, the outcome is two active boosts for the same
content — which was the status quo before this fix. The fix therefore improves the
situation without introducing new failure modes. The Conditional Expression approach
(section 4.3) remains the correct long-term mitigation for the race.

A final edge case: `active_boost_for_content` queries GSI2 with `ScanIndexForward=False`
and returns the first active boost found. If there are multiple active boosts (from
prior missing guard), the function returns only the most recently ending one. The guard
correctly detects any of them as "existing active boost" and blocks the new create.
Post-fix deployment, the system will naturally converge to a clean state as existing
duplicate boosts expire or are cancelled.
