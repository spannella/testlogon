# GAP-0121: `_upload_to_s3` Helper Missing — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase. No prior investigation doc exists.

## 1. Summary & Classification

**Claim verdict: Confirmed.** The ticket states that a stub comment `# Upload to S3 would happen here in production` exists inside the broadcast recording worker, and that no `_upload_to_s3` helper is implemented anywhere in the codebase. Both assertions are accurate.

- **Severity**: HIGH
- **Source ticket**: BCAST-006
- **Status**: Open
- **Owning area**: Broadcast Recording Pipeline (`app/services/broadcast_recording_worker.py`)
- **Impact**: All broadcast recordings complete their FFmpeg transcode pipeline locally but the output MP4 and HLS manifest files are never persisted to S3. The `mp4_s3_key` / `s3_manifest_key` values written to DynamoDB point to S3 paths that do not exist. Any download or playback URL derived from these keys returns 403/404 from CloudFront/S3.
- **Related tickets**: GAP-0122 (MP4 upload specifically), BCAST-006 (recording pipeline), BCAST-008 (MP4 download feature), SECOPS-007 (dev/prod parity)
- **Dependencies**: Requires `S.broadcast_recording_vod_bucket` to be set in production; in dev mode `broadcast-vod` bucket must be pre-created by `start_s3_mock`.

## 2. Current-State Investigation (root cause)

The recording pipeline is invoked from `stop_session_with_provider()` in `app/services/broadcast_orchestrator.py:154–175`. On session stop, `process_recording(recording_id)` calls these steps in order:

```
inventory_segments → concatenate_segments → transcode_recording
  → generate_mp4 → generate_thumbnail → finalize_recording
```

Inside `app/services/broadcast_recording_worker.py`, `generate_mp4` (line 96) handles two branches:

**Mock path (lines 102–110)**: if `_should_mock()` is True (no FFmpeg binary) or `concat_path is None`, a placeholder key is returned with `mp4_size_bytes: 0`. No S3 interaction occurs here by design.

**Production path (lines 112–135)**: FFmpeg is invoked successfully via `subprocess.run`. After FFmpeg exits at line 124, the output MP4 exists at `mp4_path` on local disk. The S3 key is computed at line 129:

```python
mp4_key = f"{recording.session_id}/recording/full.mp4"
# Upload to S3 would happen here in production
return {
    "mp4_s3_key": mp4_key,
    "mp4_size_bytes": mp4_size,
    "mp4_generated_at": _now_ts(),
}
```

The comment on line 130 is a placeholder; there is no call to any upload helper. A search across the entire `app/` tree finds no function named `_upload_to_s3` anywhere. The gap extends to `transcode_recording` (line 91–93) and `generate_thumbnail` (line 143–150), which similarly only return S3 key strings without uploading. `finalize_recording` (line 153–186) persists these phantom keys to DynamoDB via `update_recording_status`, so `s3_manifest_key`, `s3_thumbnail_key`, and `mp4_s3_key` are all stored as real-looking paths pointing to non-existent objects.

The `inventory_segments` function (line 46–58) also contains a comment `# Production: list S3 objects under the archive prefix` with no implementation — this means the concatenation step always receives an empty segment list in non-mock production runs, so FFmpeg's input is also empty. The full pipeline is therefore broken end-to-end in production: no segments are found, no output is produced, and even if it were, nothing would be uploaded.

**Dev vs. production discrepancy**: In dev mode with `broadcast_recording_mock_on_no_ffmpeg=True` and no FFmpeg binary, `_should_mock()` returns True and the pipeline skips all FFmpeg steps, returning zero-byte metadata. The moto S3 mock is active but the `broadcast-vod` bucket is not in `_dev_buckets` (see `app/main.py:509–516`) — it lists `filemgr_bucket`, `video_upload_bucket`, and `vod_output_bucket` but not `S.broadcast_recording_vod_bucket`. If the upload were implemented, it would fail in dev because the target bucket does not exist in moto.

## 3. Impact / Exploit / Blast Radius

This is a functional correctness gap, not a security vulnerability. The impact is:

1. **All broadcast recording VODs are permanently unavailable.** Any viewer clicking a recording link (e.g., `GET /sessions/{id}/recordings/{rid}`) receives a URL built from `mp4_s3_key` that resolves to a 403 or NoSuchKey S3 error. The session status shows `"ready"` in DynamoDB, which is misleading.

2. **Storage accumulation on the recording host.** The MP4 file written to the local filesystem (typically `/tmp` or a container-ephemeral path) is never cleaned up after a failed upload. On long-running worker hosts this leads to disk exhaustion.

3. **HLS manifest and thumbnails are equally broken.** `s3_manifest_key` and `s3_thumbnail_key` stored in DDB are also phantom paths. A viewer attempting to stream the recording via HLS receives the same 403/404.

4. **Downstream VOD post in newsfeed is silently wrong.** `broadcast_orchestrator.py:234–254` creates a newsfeed VOD post on `status == "ready"` using `recording_playback_url=None`. Since the manifest key is stored but no URL is derivable (the object doesn't exist), the newsfeed post will show a non-playable video card.

5. **No financial or security consequence.** Billing for private sessions and tip flows is separate from the recording pipeline. This gap does not expose PII or enable privilege escalation.

**Blast radius**: Every broadcast session that completes with `broadcast_recording_enabled=True` is affected. In production this would be 100% of recorded sessions.

## 4. Fix Design (code-level)

### 4.1 Add `_upload_to_s3` helper to `broadcast_recording_worker.py`

The helper must use `S.s3_endpoint_url` for dev (moto) and the standard AWS endpoint in production, honoring the SECOPS-007 dev/prod parity rule: the same code path must run in both environments, with the endpoint URL being the only environmental difference.

```python
import boto3
from app.core.settings import S

def _upload_to_s3(local_path: str, *, bucket: str, key: str) -> None:
    """Upload a local file to S3.

    In dev mode the S.s3_endpoint_url points to the moto mock;
    in production it is empty and boto3 uses the real AWS endpoint.
    Raises RuntimeError on any boto3 error so the caller can set
    recording status to 'failed'.
    """
    endpoint = S.s3_endpoint_url or None
    s3 = boto3.client(
        "s3",
        region_name=S.aws_region or "us-east-1",
        endpoint_url=endpoint,
    )
    try:
        s3.upload_file(local_path, bucket, key)
        logger.info("S3 upload complete: s3://%s/%s (%s)", bucket, key, local_path)
    except Exception as exc:
        raise RuntimeError(f"S3 upload failed for s3://{bucket}/{key}: {exc}") from exc
```

### 4.2 Call `_upload_to_s3` inside `generate_mp4`

Replace the stub comment at `broadcast_recording_worker.py:130`:

```python
    mp4_key = f"{recording.session_id}/recording/full.mp4"
    # --- BEFORE (stub) ---
    # Upload to S3 would happen here in production

    # --- AFTER ---
    _upload_to_s3(mp4_path, bucket=S.broadcast_recording_vod_bucket, key=mp4_key)
```

### 4.3 Apply the same pattern to `generate_thumbnail` and `transcode_recording`

`generate_thumbnail` at line 148–150 returns a key without uploading the thumbnail JPEG. A similar `_upload_to_s3(thumbnail_path, bucket=S.broadcast_recording_vod_bucket, key=thumbnail_key)` call is needed after FFmpeg frame extraction.

`transcode_recording` produces ABR rendition files. Each rendition's `.m3u8` + `.ts` segments must be uploaded. After the FFmpeg ABR pipeline completes, the worker must iterate the output directory and call `_upload_to_s3` for each file.

### 4.4 Add `broadcast_recording_vod_bucket` to `_dev_buckets` in `app/main.py`

SECOPS-007 requires the same code path in dev and prod. To enable this, the moto mock must have the target bucket pre-created:

```python
# app/main.py:509 — _dev_buckets list
_dev_buckets = [b for b in [
    _S.filemgr_bucket,
    os.environ.get("UPLOAD_BUCKET", ""),
    os.environ.get("S3_BUCKET_IMAGES", ""),
    _S.video_upload_bucket,
    _S.vod_output_bucket or "vod-output",
    _S.filemgr_bucket or "filemgr",
    _S.broadcast_recording_vod_bucket or "broadcast-vod",  # ADD THIS
] if b]
```

### 4.5 Fix `inventory_segments` to list actual S3 objects

The upload fix is moot unless the pipeline can actually find segment files. `inventory_segments` must be implemented to list objects at `recording.s3_archive_prefix` in the archive bucket. This is prerequisite work for GAP-0122 / BCAST-006.

### 4.6 Alternatives considered

- **Async background upload via SQS**: Adds latency and complexity; not needed for a batch recording pipeline that is already invoked inline (`broadcast_recording_worker_inline=True`).
- **Multipart upload**: Appropriate for large MP4s (>100 MB) but can be introduced in a follow-up; `upload_file` uses multipart automatically via boto3's managed transfer when files exceed the threshold.

### Regression test (fails before fix, passes after)

Add to `tests/test_broadcast_recording_worker.py`:

```python
import pytest
from unittest.mock import patch, MagicMock, call
from app.services.broadcast_recording_worker import generate_mp4, _upload_to_s3
from app.services.broadcast_recording import RecordingRecord

@pytest.fixture
def recording():
    return RecordingRecord(
        recording_id="rec_test",
        session_id="sess_test",
        profile_id="prof_test",

        status="processing",
        s3_archive_prefix="sess_test/archive/",

        created_at=1000000,

def test_generate_mp4_calls_upload(recording, tmp_path):
    """generate_mp4 must call _upload_to_s3 after FFmpeg succeeds.

    Fails before fix: no call to _upload_to_s3.
    Passes after fix: upload is called with correct bucket and key.
    """
    concat_path = str(tmp_path / "concat.ts")
    mp4_path = str(tmp_path / "concat.mp4")
    # Create fake concat file and mp4 file
    open(concat_path, "w").close()
    open(mp4_path, "w").close()

    with patch("app.services.broadcast_recording_worker._should_mock", return_value=False), \
         patch("app.services.broadcast_recording_worker.S") as mock_s, \
         patch("subprocess.run") as mock_run, \
         patch("app.services.broadcast_recording_worker._upload_to_s3") as mock_upload, \

        result = generate_mp4(recording, concat_path)

    # Must have called upload with the right bucket and key
    mock_upload.assert_called_once()
    _, kwargs = mock_upload.call_args
    assert kwargs["bucket"] == "broadcast-vod"
    assert kwargs["key"].endswith("full.mp4")
    assert result["mp4_size_bytes"] == 12345

def test_upload_to_s3_uses_s3_endpoint_url(tmp_path):
    """_upload_to_s3 must pass S.s3_endpoint_url to the boto3 client."""
    local_file = tmp_path / "test.mp4"
    local_file.write_bytes(b"data")

    with patch("app.services.broadcast_recording_worker.S") as mock_s, \
         patch("boto3.client") as mock_client:
        mock_s.s3_endpoint_url = "http://localhost:4566"
        mock_s.aws_region = "us-east-1"
        mock_boto = MagicMock()
        mock_client.return_value = mock_boto
        _upload_to_s3(str(local_file), bucket="broadcast-vod", key="sess/full.mp4")

    mock_client.assert_called_once_with(
        "s3",
        region_name="us-east-1",
        endpoint_url="http://localhost:4566",

    mock_boto.upload_file.assert_called_once()
```

### Manual QA steps

1. Run `just restart` to wipe DynamoDB and re-seed.
2. Start a broadcast session and push at least 1 HLS segment via the ingest endpoint.
3. Stop the session. Check the recording status via `GET /sessions/{id}/recordings` — it should transition `processing → ready`.
4. Fetch the `mp4_s3_key` from the recording record.
5. Issue a `HEAD` request to the S3 URL: it must return 200 with a `Content-Length > 0`.
6. In dev mode, use `boto3.client("s3", endpoint_url="http://localhost:4566").list_objects(Bucket="broadcast-vod")` to verify the object exists.

### Observability

- Add `record_broadcast_session_action(provider="recording", action="s3_upload", result="success"/"failure")` calls in `_upload_to_s3`.
- Log `mp4_size_bytes` and upload duration at INFO level.
- Alert on `recording.status == "failed"` with `error_code == "RuntimeError"` in DDB.

### Rollout

- **Effort**: M (the helper itself is S; wiring it to all three upload sites and fixing `inventory_segments` is M).
- **Feature flag**: `broadcast_recording_enabled` already gates the pipeline; no new flag needed.
- **Backward compatibility**: Existing `"ready"` recordings in DDB with missing S3 objects cannot be retroactively fixed without re-running the pipeline. A backfill script should mark such recordings as `"failed"`.
- **Risk**: Low. The fix is additive — it adds an upload call that was always intended. The only risk is credential misconfiguration in production (`AWS_ACCESS_KEY_ID` not set for the S3 role), which will surface as `NoCredentialsError` in the recording worker log.
- **Sequencing**: Should be merged together with GAP-0122 (which extends the same function) and after a working `inventory_segments` implementation, since without segments there is nothing to upload.
