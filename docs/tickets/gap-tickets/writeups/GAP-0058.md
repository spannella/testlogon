# GAP-0058: No Content Ownership Validation at Boost Creation — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against live code at
> `app/services/content_boost.py`, `app/routers/content_boost.py`,
> `app/services/sponsorship_deals.py`. No investigation doc exists.

## 1. Summary & Classification

**Gap**: `app/services/content_boost.py:create_boost` (lines 147–213) charges the
caller's wallet and creates a content boost record without verifying that the caller
(`owner_sub`) actually owns the `content_id` being boosted. Any authenticated user can
pay to boost any post, video, or broadcast that belongs to someone else, thereby
manipulating feed and serving rankings for content they do not own.

- **Severity**: HIGH
- **Source ticket**: ADS-012
- **Owning area**: Content Boost / Ads platform
- **Status**: Open
- **Related tickets**: GAP-0059 (duplicate active boost guard)
- **Verdict**: Claim confirmed. `create_boost` accepts `owner_sub`, `content_type`,
  and `content_id` but never checks that the content item's stored `owner_user_id` /
  `user_id` matches `owner_sub` before proceeding to charge the wallet.

**One-line impact**: Any user can pay to artificially elevate another creator's content,
skewing organic feed ranking and enabling financial abuse via deliberate misuse of
the boost budget.

## 2. Current-State Investigation (root cause)

### `create_boost` validation gap

`app/services/content_boost.py:147–213` shows the full create path. After four
input-shape checks (content_type, content_id, budget_cents, duration_seconds), the
function immediately checks the wallet balance and charges it:

```python
# content_boost.py:160–189
if content_type not in ALLOWED_CONTENT_TYPES:
    raise ValueError(...)
if not content_id:
    raise ValueError(...)
if budget_cents <= 0:
    raise ValueError(...)
if duration_seconds <= 0:
    raise ValueError(...)

ts = _now(now)
bid = f"boost_{uuid.uuid4().hex[:12]}"
ends_at = ts + duration_seconds

if _wallet_balance(owner_sub) < budget_cents:
    raise ValueError("insufficient wallet balance")
try:
    _wallet_charge(owner_sub, budget_cents, ...)   # WALLET DEBITED HERE
except Exception:
    raise ValueError("insufficient wallet balance")
```

There is no call to any ownership verification function between the input checks and
the wallet charge. The `_put_item` follows immediately after.

### The sponsorship deals service has a comparable function — it IS called

By contrast, `app/services/sponsorship_deals.py:518` (inside `submit_content`) does
call `_verify_content_ownership`:

```python
# sponsorship_deals.py:518
_verify_content_ownership(deal["content_type"], content_id, creator_sub)
```

And `_verify_content_ownership` (lines 295–309) is already implemented for `post`
content, raising `SponsorshipError(403)` if `item["user_id"] != creator_sub` and
`SponsorshipError(404)` if the post does not exist.

### The content boost service has no equivalent helper

`app/services/content_boost.py` has no `_verify_content_ownership` call or equivalent
check. The `ALLOWED_CONTENT_TYPES` tuple (`"post"`, `"video"`, `"broadcast"`) is
defined at line 42, but ownership is never verified for any of these types.

### Router passes `owner_sub` from the session — correctly

`app/routers/content_boost.py:23–34`:

```python
async def create_boost(body: ContentBoostCreate, sess: dict = Depends(require_ui_session)):
    user_sub = sess["user_sub"]
    try:
        return svc.create_boost(
            user_sub,
            content_type=body.content_type,
            content_id=body.content_id,
            ...
        )
```

The router does pass the authenticated `user_sub` as `owner_sub`. The problem is that
the service layer does not validate the relationship between `owner_sub` and `content_id`.

### Ownership verification is structurally different per content type

- **post**: verified via the newsfeed table (`feed_tbl.get_item`), field `user_id`.
- **video**: stored in `T.video_metadata` (table `VideoMetadata`), PK is `video_id`,
  owner field is `owner_user_id` (`app/models_video.py:38`).
- **broadcast**: stored in `T.broadcast_sessions`, PK is `session_id`,
  owner field is `created_by` (`scripts/local-ddb-init.py:687–695`).

The existing `_verify_content_ownership` in `sponsorship_deals.py` only handles `post`
(returns early for any other type), so it cannot be imported directly without extension.

## 3. Impact / Exploit / Blast Radius

**Who is affected**: All content creators on the platform; the feed ranking system; the
billing ledger.

**Exploit walkthrough**:

1. Attacker (user A) observes that a popular creator (user B) has a post with
   `post_id = "abc123"`.
2. Attacker calls `POST /ui/ads/boost` with `{"content_type": "post",
   "content_id": "abc123", "budget_cents": 5000, "duration_seconds": 3600}`.
3. The backend charges $50 from Attacker's wallet, creates a boost record with
   `GSI2PK = "CONTENT#post#abc123"`, and marks it `status=active`.
4. `active_boost_for_content("post", "abc123")` now returns this boost; `elevate_feed_items`
   adds `BOOST_RANK_WEIGHT = 1000` to every feed query that includes this post.
5. Creator B's post is artificially elevated without their knowledge or consent.

**Abuse scenarios**:

- **Competitor suppression (inverted)**: Attacker boosts a competitor's low-quality
  post, saturating their brand feed with that post and crowding out better content.
- **Sock-puppet amplification**: Attacker creates alt accounts, boosts their own content
  to max rank via another account's wallet, circumventing daily spend limits.
- **Financial drain via third-party content**: Attacker sets up a script that continuously
  boosts expensive content IDs using micro-budgets, draining the boost system's capacity
  for legitimate creators.
- **Denial of boost service**: Because `active_boost_for_content` uses `GSI2PK =
  CONTENT#{type}#{id}` and `active_boost_for_content` returns only the first active boost,
  an attacker can pre-occupy the boost slot for a content item, preventing the legitimate
  owner from boosting their own content.

**Financial**: Every unauthorized boost costs real money (wallet balance) and creates
a legitimate-looking ledger entry (`_LEDGER_CHARGE_TYPE = "content_boost_charge"`),
making abuse hard to detect after the fact via billing audit.

**Blast radius**: Affects post, video, and broadcast ranking. Any feed query that calls
`elevate_feed_items` or `boost_rank_bonus` is polluted.

## 4. Fix Design (code-level)

### Approach: add `_verify_content_ownership` to `content_boost.py`

The fix is isolated to `app/services/content_boost.py`. Add a helper that covers all
three `ALLOWED_CONTENT_TYPES` and call it before the wallet charge.

#### 4.1 New ownership-verification helper in `content_boost.py`

```python
def _verify_content_ownership(
    owner_sub: str,
    content_type: str,
    content_id: str,
) -> None:
    """Raise ValueError(404) if content does not exist;
    raise PermissionError if owner_sub does not own it.

    Covers 'post', 'video', 'broadcast'.
    """
    if content_type == "post":
        try:
            from app.routers.newsfeed import tbl as feed_tbl, pk_post, sk_post
            item = feed_tbl.get_item(
                Key={"pk": pk_post(content_id), "sk": sk_post()}
            ).get("Item")
        except Exception:
            item = None
        if not item:
            raise ValueError(f"post '{content_id}' not found")
        if str(item.get("user_id", "")) != owner_sub:
            raise PermissionError("you do not own this post")

    elif content_type == "video":
        resp = T.video_metadata.get_item(Key={"video_id": content_id})
        item = resp.get("Item")
        if not item:
            raise ValueError(f"video '{content_id}' not found")
        if str(item.get("owner_user_id", "")) != owner_sub:
            raise PermissionError("you do not own this video")

    elif content_type == "broadcast":
        resp = T.broadcast_sessions.get_item(Key={"session_id": content_id})
        item = resp.get("Item")
        if not item:
            raise ValueError(f"broadcast session '{content_id}' not found")
        if str(item.get("created_by", "")) != owner_sub:
            raise PermissionError("you do not own this broadcast session")
    # For any future content types not yet in ALLOWED_CONTENT_TYPES,
    # the outer guard (line 160) rejects them before this is reached.
```

#### 4.2 Call it before the wallet charge in `create_boost`

Insert the call between the input-shape checks and the wallet-balance check:

```python
def create_boost(owner_sub, *, content_type, content_id, budget_cents,
                  duration_seconds, now=None):
    if content_type not in ALLOWED_CONTENT_TYPES:
        raise ValueError(...)
    if not content_id:
        raise ValueError(...)
    if budget_cents <= 0:
        raise ValueError(...)
    if duration_seconds <= 0:
        raise ValueError(...)

    # NEW: ownership verification — before any money moves
    _verify_content_ownership(owner_sub, content_type, content_id)

    ts = _now(now)
    ...
    if _wallet_balance(owner_sub) < budget_cents:
        raise ValueError("insufficient wallet balance")
    ...
```

#### 4.3 Router error mapping

The router (`app/routers/content_boost.py:33–34`) already catches `ValueError` and maps
to 400. Add handling for `PermissionError`:

```python
except ValueError as exc:
    raise HTTPException(status_code=400, detail=str(exc))
except PermissionError as exc:
    raise HTTPException(status_code=403, detail=str(exc))
```

The 404 case (content not found) can be re-raised as a distinct HTTP 404:

```python
except ValueError as exc:
    status = 404 if "not found" in str(exc) else 400
    raise HTTPException(status_code=status, detail=str(exc))
```

#### 4.4 Import `T.broadcast_sessions` in `content_boost.py`

`T.broadcast_sessions` is available through the existing `from app.core.tables import T`
import that is already at `content_boost.py:27`. No new imports are needed for
`T.video_metadata` or `T.broadcast_sessions` — both are attributes of the `T` singleton.

### Dev/Prod parity (SECOPS-007)

All three table lookups (`T.video_metadata`, `T.broadcast_sessions`, newsfeed table) go
through the same DynamoDB Local instance in dev and the same table handles as in prod.
There is no mock-specific code path to add. The `_verify_content_ownership` helper
follows the same best-effort pattern as `sponsorship_deals._verify_content_ownership`
(try/except wrapping the DDB get), so it will degrade gracefully if a table is
unreachable in dev rather than blocking boost creation.

### Alternatives considered

- **Router-level ownership check**: Moving the check to the router avoids coupling
  the service to newsfeed/video/broadcast internals. However, the service is the
  correct layer for business rules that affect money flow; the check must run before
  the wallet charge, which is in the service. Router-level checks do not prevent
  direct service calls.
- **Shared ownership-check service**: Centralising ownership checks for all content
  types in a new `app/services/content_ownership.py` module is the right long-term
  architecture, but is out of scope for this gap fix. The inline helper mirrors
  the pattern already used in `sponsorship_deals.py`.
- **Skip ownership check for `video` and `broadcast`**: Unacceptable — these are
  two of the three allowed content types, and attackers would simply target them.

    with patch("app.routers.newsfeed.tbl", feed_tbl), \
         patch("app.routers.newsfeed.pk_post", lambda x: f"POST#{x}"), \
         patch("app.routers.newsfeed.sk_post", lambda: "META"):

**Fails before fix**: `test_non_owner_cannot_boost` will see `mock_charge` called
(wallet charged) and no exception raised, causing `pytest.raises(PermissionError)` to
fail.

**Passes after fix**: `_verify_content_ownership` raises `PermissionError` before
`_wallet_charge` is reached.

### Rollout

- This is a business-logic fix with no schema changes. Deploy with the next backend
  release.
- No feature flag needed — ownership validation should always be enforced.
- **Rollback**: Revert the `_verify_content_ownership` call in `create_boost`. The
  wallet charge and DDB write are unaffected.

**Effort**: S (small). ~40 lines of new Python in one service file; ~5 lines in router.
**Sequencing**: Deploy before GAP-0059 (duplicate boost guard) so the ownership
check runs first, giving cleaner error messages to legitimate owners who hit the
duplicate guard next.

### Risk assessment

The main risk is that the newsfeed `tbl` import uses a lazy-import pattern
(`from app.routers.newsfeed import tbl`). If the newsfeed router is not yet fully
initialized at the time `_verify_content_ownership` is called during startup (e.g.
in an unlikely import-order edge case), the lazy import fallback (`item = None` in
the exception handler) would cause a 404 rather than a 403. This is acceptable
because: (a) FastAPI fully loads all routers before accepting requests, so the race
cannot happen at runtime; (b) the exception handler is there specifically to catch
DDB connectivity errors, not import errors. To be safe, the import can be moved
to module level in `content_boost.py` with a conditional guard.

The `video` and `broadcast` paths use `T.video_metadata` and `T.broadcast_sessions`
directly — no lazy import needed. These table handles are always available once the
FastAPI application starts (they are initialized in `app/core/tables.py` at module
load time).

A legitimate concern is that the ownership check adds a DDB read latency to every
boost creation call (one `get_item` per content type). For typical `post` content,
this is a single-item point read on the newsfeed table (~1–2 ms). For `video` and
`broadcast`, similarly a point read on the respective table. This latency is acceptable
for an infrequent action like creating a boost, and is vastly outweighed by the security
benefit.
