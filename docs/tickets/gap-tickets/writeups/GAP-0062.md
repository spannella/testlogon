# GAP-0062: ROAS Calculation Service Not Implemented — Remediation Write-up

> ~5 pages. Fix-oriented. Claim verified directly against the code before writing; cites file:line.

## 1. Summary & Classification

**Claim status: Confirmed.** Neither `app/services/ad_roas.py` nor a `GET /ui/ads/campaigns/{id}/roas` endpoint exists anywhere in the codebase. The optimization service (`app/services/ad_optimization.py:340-348`) reads a `roas` key from a metrics dict and fires an alert when it falls below threshold, but that key is never populated — `app/services/ad_analytics.py` does not compute or store ROAS in its rollup or summary outputs. Advertisers have no way to retrieve Return on Ad Spend data from the platform.

- **Severity**: HIGH  
- **Source ticket**: ADS-015  
- **Owning area**: Ads / Ad Analytics  
- **One-line impact**: The entire ROAS measurement loop (conversion value attribution → ROAS calculation → advertiser-facing reporting endpoint) is absent; the optimization alert for `roas_below_threshold` is permanently dormant because no code ever populates the `roas` field in campaign metrics.  
- **Related tickets**: ADS-015 (parent feature), GAP-0063 (missing E2E spec for ADS-015 promo/redirect flows).

### Conversion data that does exist (and could feed ROAS)

`app/services/affiliate_links.py:272-329` accumulates `revenue_cents` on the link record whenever a conversion is recorded (line 307: `revenue_cents = if_not_exists(...) + :rev`). The raw material for ROAS is therefore present in DynamoDB but is never aggregated and surfaced.

`app/services/ad_analytics.py:186-210` builds hourly rollups with `spend_cents` and a placeholder `revenue_cents = int(spend * 0.7)` (line 200 — a hard-coded 70% estimate, not actual conversion revenue). This means the rollup table contains spend data but its `revenue_cents` column is synthetic and does not reflect real attribution.

### Why `roas_below_threshold` alerts never fire

`app/services/ad_optimization.py:340`:

```python
roas = m.get("roas", 0)   # always returns 0 — key never set by analytics
if roas < roas_threshold and m.get("spend_cents", 0) > 1000:
    ...  # never reached for roas check
```

The `check_performance_alerts` function receives `campaign_metrics` from callers that source the dict from `ad_analytics.get_summary(...)`. Because `get_summary` never produces a `roas` key, the condition `roas < roas_threshold` evaluates as `0 < 1.0` — always True — but the second condition `spend_cents > 1000` suppresses a false-positive alert. Once real spend exceeds 1000 cents the alert would fire continuously with ROAS = 0, flooding the notification system.

### Dev vs prod

The gap exists identically in both environments. No mocking or feature-flag path provides a stub implementation.

## 3. Impact / Exploit / Blast Radius

### Advertiser impact

Advertisers cannot evaluate whether their ad spend generates positive return. This is a table-stakes feature for any self-serve ad platform. Without ROAS data, advertisers have no objective basis for adjusting budgets, creatives, or targeting — impairing campaign performance and platform revenue.

### Platform integrity

The optimization alert system (`ad_optimization.py`) is broken in two ways simultaneously:
1. ROAS alerts never fire (because `roas = 0` always).
2. Once any campaign accumulates more than $10 spend, the alert would spam with `roas_below_threshold` at every check interval until the feature is fixed.

This is a latent operational reliability risk, not just a missing feature.

### Financial risk

There is no security or direct financial exploit, but the absence of ROAS reporting can mask campaigns that are net-negative for the platform's revenue-share model (see GAP-0026) — advertisers would have less incentive to pause ineffective campaigns.

## 4. Fix Design (code-level)

### New service: `app/services/ad_roas.py`

```python
"""ROAS (Return on Ad Spend) calculation service (ADS-015 / GAP-0062).

Aggregates affiliate conversion revenue attributed to a campaign and
computes the ROAS ratio: total_conversion_value_cents / total_spend_cents.

Conversion revenue is sourced from the ad_creative_affiliates table
(REDEEM#* rows written by ad_creative_affiliate.redeem_affiliate_discount).
Spend is sourced from ad_analytics rollups (ad_analytics_rollups table).
"""

from __future__ import annotations

import logging
from typing import Any, Dict, List, Optional

from boto3.dynamodb.conditions import Key

from app.core.tables import T
from app.core.time import now_ts
from app.services.ad_campaigns import get_campaign
from app.services.ad_analytics import get_summary

logger = logging.getLogger(__name__)


def _fetch_campaign_creatives(campaign_id: str) -> List[str]:
    """Return all creative IDs belonging to a campaign."""
    resp = T.ad_creatives.query(
        IndexName="GSI1",
        KeyConditionExpression=Key("GSI1PK").eq(f"CAMP#{campaign_id}"),
        ProjectionExpression="creative_id",
    )
    return [item["creative_id"] for item in resp.get("Items", [])]


def _fetch_conversion_revenue(creative_id: str, since_ts: int) -> int:
    """Sum final_price_cents across all REDEEM# rows for a creative since since_ts."""
    total = 0
    kwargs: Dict[str, Any] = dict(
        KeyConditionExpression=(
            Key("pk").eq(f"ACAFF#{creative_id}") &
            Key("sk").begins_with("REDEEM#")
        ),
        ProjectionExpression="final_price_cents, created_at",
    )
    while True:
        resp = T.ad_creative_affiliates.query(**kwargs)
        for item in resp.get("Items", []):
            if int(item.get("created_at", 0)) >= since_ts:
                total += int(item.get("final_price_cents", 0))
        lek = resp.get("LastEvaluatedKey")
        if not lek:
            break
        kwargs["ExclusiveStartKey"] = lek
    return total


def calculate_campaign_roas(
    *,
    campaign_id: str,
    account_id: str,
    days: int = 30,
) -> Dict[str, Any]:
    """Calculate ROAS for a campaign over the last `days` days.

    Returns:
        {
            "campaign_id": str,
            "spend_cents": int,
            "conversion_revenue_cents": int,
            "roas": float,          # conversion_revenue / spend; 0.0 if spend == 0
            "conversion_count": int,
            "days": int,
            "computed_at": int,
        }
    """
    campaign = get_campaign(campaign_id)
    if not campaign:
        return {}

    summary = get_summary(account_id, campaign_id=campaign_id, days=days)
    spend_cents = int(summary.get("spend_cents", 0))

    since_ts = now_ts() - days * 86400
    creative_ids = _fetch_campaign_creatives(campaign_id)

    conversion_revenue_cents = 0
    conversion_count = 0
    for cid in creative_ids:
        resp = T.ad_creative_affiliates.query(
            KeyConditionExpression=Key("pk").eq(f"ACAFF#{cid}") & Key("sk").begins_with("REDEEM#"),
            ProjectionExpression="final_price_cents, created_at",
        )
        for item in resp.get("Items", []):
            if int(item.get("created_at", 0)) >= since_ts:
                conversion_revenue_cents += int(item.get("final_price_cents", 0))
                conversion_count += 1

    roas = round(conversion_revenue_cents / spend_cents, 4) if spend_cents > 0 else 0.0

    return {
        "campaign_id": campaign_id,
        "spend_cents": spend_cents,
        "conversion_revenue_cents": conversion_revenue_cents,
        "roas": roas,
        "conversion_count": conversion_count,
        "days": days,
        "computed_at": now_ts(),
    }
```

### New endpoint in `app/routers/ad_creative_affiliate.py`

Add after existing stats endpoint (around line 180):

```python
@router.get("/campaigns/{campaign_id}/roas")
def get_campaign_roas(
    campaign_id: str,
    days: int = 30,
    session: dict = Depends(require_ui_session),
):
    """Return ROAS metrics for a campaign. Advertiser must own the campaign."""
    from app.services.ad_campaigns import get_campaign
    from app.services.ad_roas import calculate_campaign_roas

    campaign = get_campaign(campaign_id)
    if not campaign:
        raise HTTPException(404, "Campaign not found")
    if campaign.get("advertiser_sub") != session["user_sub"]:
        raise HTTPException(403, "Not your campaign")

    result = calculate_campaign_roas(
        campaign_id=campaign_id,
        account_id=campaign["account_id"],
        days=days,
    )
    return result
```

### Fix the optimization alert `roas` key

Update `app/services/ad_optimization.py` (or wherever `check_performance_alerts` is called) to pass a `roas` value from `calculate_campaign_roas` rather than reading it from the analytics summary dict. Alternatively, add the ROAS calculation to `get_summary` directly:

In `app/services/ad_analytics.py`, at the end of `get_summary` (after line 67), add:

```python
    # Compute ROAS from actual conversion data.
    from app.services.ad_roas import calculate_campaign_roas
    if campaign_id:
        roas_data = calculate_campaign_roas(
            campaign_id=campaign_id, account_id=account_id, days=days
        )
        result["roas"] = roas_data.get("roas", 0.0)
        result["conversion_revenue_cents"] = roas_data.get("conversion_revenue_cents", 0)
```

This closes the loop: `check_performance_alerts` will now see a real `roas` value.

### Dev/Prod parity (SECOPS-007)

- All DynamoDB reads in `ad_roas.py` use `T.*` table handles, which resolve to DynamoDB Local in dev and to real DynamoDB in prod. No AWS-specific code path divergence.
- No KMS, S3, or Cognito calls involved.
- The new endpoint is gated by `require_ui_session` which works identically in both environments (cookie auth in dev, same cookie auth or bearer in prod).
- No feature flag required; the service is purely additive.

### DynamoDB table dependency

`calculate_campaign_roas` queries `T.ad_creative_affiliates` for `REDEEM#` rows and `T.ad_creatives` via GSI1 for creative IDs belonging to the campaign. Both tables must exist and have the expected GSI definitions. Verify in `scripts/local-ddb-init.py` that:

- `ad_creative_affiliates` has a GSI on `pk` (campaign creative lookup) — or adjust the query to use `ACAFF#{creative_id}` PK directly after fetching creative IDs from the campaign.
- `ad_creatives` has `GSI1PK = CAMP#{campaign_id}` indexed with the correct `attr_types`.

If the GSI does not exist in the local DDB init script, add it as part of the GAP-0062 implementation PR.

### Observability

- Add a structured log line at the start of `calculate_campaign_roas`: `logger.info("roas_calculated campaign_id=%s roas=%.4f spend_cents=%d conversions=%d", campaign_id, roas, spend_cents, conversion_count)`.
- This allows a CloudWatch/Datadog metric filter to track ROAS calculation frequency and surface anomalies (e.g., always-zero ROAS across all campaigns after the feature ships would indicate a conversion attribution bug).
- Add a histogram metric for `roas_endpoint_latency_ms` — the endpoint performs two DynamoDB reads (analytics rollup + affiliate creative scan), and the scan iterates via `LastEvaluatedKey`. For campaigns with many creatives, latency could be significant. The histogram lets ops set a p99 SLA alert.

### Paging and performance note

`_fetch_campaign_creatives` queries the `ad_creatives` GSI and `calculate_campaign_roas` then queries `T.ad_creative_affiliates` once per creative ID in a sequential loop. For campaigns with O(100) creatives this could be O(100) DynamoDB queries per ROAS request. For the initial implementation this is acceptable (most campaigns have fewer than 10 creatives), but the endpoint should document a rate limit or add response caching (e.g., a 5-minute TTL on the result keyed by `campaign_id:days`) before scaling to enterprise advertisers.

An alternative implementation would aggregate conversion revenue at write time — incrementing a `campaign_conversion_revenue_cents` counter on the campaign record inside `ad_creative_affiliate.redeem_affiliate_discount`. This reduces ROAS query time to a single DynamoDB read but requires a write-time change to the redemption path. The read-time aggregation approach is simpler to implement correctly and is the recommended first iteration.

### Rollout

- **Effort**: M (Medium) — new service file (~120 lines), one new endpoint, small addition to `get_summary`, possible `local-ddb-init.py` GSI addition.
- **Risk**: Low — purely additive; no existing behaviour is modified until `get_summary` is updated to include `roas`. That final step can be gated behind a short-lived feature flag `ROAS_IN_SUMMARY_ENABLED`.
- **Sequencing**: (1) Merge `ad_roas.py` + endpoint, (2) run unit + integration tests, (3) enable the endpoint in staging and run the new E2E section 414 tests (from GAP-0063), (4) enable `ROAS_IN_SUMMARY_ENABLED` in staging, (5) confirm optimization alerts no longer misfire with `roas=0`, then promote to prod.
- **Rollback**: Remove the endpoint registration from `ad_creative_affiliate.py` and set `ROAS_IN_SUMMARY_ENABLED=0`. No data migration required. The `record_conversion` path in `affiliate_links.py` is unchanged and continues to accumulate `revenue_cents` correctly regardless of whether the ROAS endpoint is enabled.
