# GAP-0351: No Visual PDF Viewer — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code before writing; all cites are `file:line`.

## 1. Summary & Classification

**Bug statement**: The Document Signing UI (`SignaturePacketComposer`) shows a blank grey placeholder box labelled "PDF editor canvas" where a real PDF render should appear. This placeholder was committed as part of the SIGN-001 implementation and represents an intentional stub that was never replaced with a working viewer. The gap was identified during the second-pass as-built review of SIGN-001. Signers and senders interact with an empty rectangle: they click to drop field overlays onto invisible, imaginary page content rather than onto the actual document. Field positions are meaningful only if the operator already knows what the PDF looks like; for general users the workflow is unusable without visual reference.

- **Severity**: HIGH
- **Source ticket**: SIGN-001, §1b ("render source PDF pages with page thumbnails")
- **Status**: Open — no `react-pdf`, `pdfjs-dist`, or equivalent package is installed; the component contains no PDF rendering logic at all.
- **Owning area**: Frontend / Document Signing
- **Investigation verdict**: Confirmed exactly as stated. The ticket says lines 609–629; those exact lines are the blank `<div>` canvas placeholder described below.
- **Related tickets**: GAP-0352 (no signature drawing canvas — in the same component). No SECOPS-007 implications because the viewer is purely client-side; no new AWS-backed paths are created.

## 2. Current-State Investigation (Root Cause)

### The placeholder

`frontend/src/pages/files/SignaturePacketComposer.tsx:604–631` (complete "PDF editor canvas" section):

```tsx
<div className="space-y-2">
  <div className="flex items-center justify-between text-xs text-muted-foreground">
    <span>PDF editor canvas</span>           {/* label only */}
    <span>status: {packet?.status ?? "none"}</span>
  </div>
  <div
    ref={canvasRef}
    onClick={(ev) => void onCanvasClick(ev)}
    className="relative h-[520px] rounded-md border border-dashed bg-slate-50"
    data-testid="signature-canvas"
  >
    {(packet?.fields ?? []).map((field) => (
      <div
        key={field.field_id}
        className="absolute rounded border border-blue-600 bg-blue-100/60 px-1 text-[10px] text-blue-900"
        style={{
          left: `${Math.max(0, field.x) * 100}%`,
          top:  `${Math.max(0, field.y) * 100}%`,
          width: `${Math.max(0.05, field.width) * 100}%`,
          height:`${Math.max(0.03, field.height) * 100}%`,
        }}
      >
        {field.field_type}
      </div>
    ))}
  </div>
</div>
```

The outer `<div>` at line 609 (`data-testid="signature-canvas"`) is a fixed-height `520 px` grey box (`bg-slate-50`). It renders field overlay badges (the `field.field_type` labels) but no PDF page content sits behind them — the background is literally the Tailwind `slate-50` colour.

### Root cause — missing dependency and render logic

`frontend/package.json` (full file) contains no reference to any PDF rendering library:

- `react-pdf` — absent
- `pdfjs-dist` — absent
- `@react-pdf/renderer` — absent (wrong direction anyway; this is for PDF generation, not viewing)
- `pdf-lib` — absent

No import of `Document`, `Page`, or any PDF-related symbol appears anywhere in `SignaturePacketComposer.tsx` (confirmed by grepping the file for "pdf", "PDF", "canvas", "pdfjs").

The component stores the source path as a plain string in `sourcePath` state (line 111) but never fetches or renders the file. The `canvasRef` on line 126 points to the plain HTML `<div>`, not an HTML5 canvas element.

### Runtime behaviour

In dev and prod the result is identical: the user sees a dashed-border grey box. Clicking anywhere drops a field overlay (blue badge) at normalized coordinates, but since there is no visual reference to the actual PDF pages those coordinates are essentially random from the user's perspective. For a signer (fill mode), the "signer-fill-panel" is rendered in the left column (fields list) so signers can still fill text values, but they have no visual confirmation of where on the document a "signature" field falls.

## 3. Impact / Exploit / Blast Radius

**User experience**: Any user acting as a sender cannot accurately place signature fields on the PDF. Fields created via click land at arbitrary positions relative to the invisible document. This effectively breaks the primary document signing UX for the sender role.

**Signer impact**: Signers filling fields see the same blank box. They can type values via the left-column form but cannot verify the field is actually placed on the right page area (e.g., signature line vs. a sensitive data block).

**Data integrity**: Completed PDFs generated by the backend (`downloadSignaturePacketFinalPdf`) will place the rendered signatures at whatever `(x, y, width, height)` coordinates the sender happened to click. Without visual context, misplaced fields are likely, and once a packet is `completed` the final PDF is immutable.

**Compliance / legal**: E-signature compliance (ESIGN Act, eIDAS) assumes that signers can see the document they are signing. A blank viewer undermines that assumption and could create legal challenges to the validity of signatures produced by this workflow.

**Blast radius**: Affects every user who creates or signs a document via the web UI. The backend API and the data model are unaffected; only the frontend rendering is missing.

## 4. Fix Design (Code-Level)

### 4.1 Install `react-pdf`

```bash
npm install react-pdf
npm install --save-dev @types/react-pdf   # if typedefs not bundled
```

`react-pdf` (backed by `pdfjs-dist`) is the standard React wrapper for Mozilla PDF.js. It is MIT-licensed, tree-shakeable, and works in both Vite and SSR contexts.

### 4.2 Expose a signed PDF URL endpoint (backend, read-only)

The component currently stores only the _path_ string (e.g., `/contracts/nda.pdf`). To render the PDF in the browser, the frontend needs a fetch-able URL. The backend already serves a mock S3 URL for image messages (`_message_out_from_item` in `app/routers/messaging.py`). A similar pattern is needed here:

Add to `app/routers/signing.py` (or wherever signature-packet endpoints live):

```python
@router.get("/packets/{packet_id}/source-url")
async def get_source_pdf_url(
    packet_id: str,
    user: AuthenticatedUser = Depends(require_ui_session),
):
    """Return a short-lived pre-signed S3 URL for the source PDF."""
    packet = get_signature_packet(packet_id, viewer_sub=user.sub)  # 403/404 handled inside
    if S.dev_mode:
        url = f"/mock/s3/{packet.source_path.lstrip('/')}"
    else:
        url = generate_presigned_url(S.filemgr_bucket, packet.source_path, expires=300)
    return {"url": url}
```

Dev/prod parity (SECOPS-007): in `dev_mode=True` the URL points to the existing `/mock/s3/` proxy; in production it returns a 5-minute presigned S3 URL. Same code path, single flag.

### 4.3 Frontend — replace the blank `<div>` with a `react-pdf` viewer

In `SignaturePacketComposer.tsx`, add:

```tsx
import { Document, Page, pdfjs } from "react-pdf";
import "react-pdf/dist/Page/AnnotationLayer.css";
import "react-pdf/dist/Page/TextLayer.css";

pdfjs.GlobalWorkerOptions.workerSrc = new URL(
  "pdfjs-dist/build/pdf.worker.min.mjs",
  import.meta.url,
).toString();
```

Add state:

```tsx
const [pdfUrl, setPdfUrl] = React.useState<string | null>(null);
const [numPages, setNumPages] = React.useState<number>(0);
```

After `loadPacket` succeeds, fetch the source URL:

```tsx
if (detail.status !== "draft" || detail.source_path) {
  const { url } = await apiFetch(`/ui/signing/packets/${detail.packet_id}/source-url`);
  setPdfUrl(url);
}
```

Replace the blank `<div>` at `SignaturePacketComposer.tsx:609–629` with:

```tsx
<div className="relative overflow-auto rounded-md border">
  {pdfUrl ? (
    <Document
      file={pdfUrl}
      onLoadSuccess={({ numPages }) => setNumPages(numPages)}
    >
      {Array.from({ length: numPages }, (_, i) => i + 1).map((pageNum) => (
        <div key={pageNum} className="relative">
          <Page pageNumber={pageNum} width={canvasWidth} renderAnnotationLayer={false} renderTextLayer={false} />
          {/* Field overlays, filtered to this page */}
          {(packet?.fields ?? [])
            .filter((f) => (f.page ?? 1) === pageNum)
            .map((field) => (
              <div
                key={field.field_id}
                className="absolute rounded border border-blue-600 bg-blue-100/60 px-1 text-[10px] text-blue-900"
                style={{
                  left: `${field.x * 100}%`,
                  top:  `${field.y * 100}%`,
                  width: `${field.width * 100}%`,
                  height:`${field.height * 100}%`,
                }}
              >
                {field.field_type}
              </div>
            ))}
        </div>
      ))}
    </Document>
  ) : (
    <div
      ref={canvasRef}
      onClick={(ev) => void onCanvasClick(ev)}
      className="relative h-[520px] bg-slate-50"
      data-testid="signature-canvas"
    >
      <span className="absolute inset-0 flex items-center justify-center text-xs text-muted-foreground">
        {packet ? "Loading PDF…" : "Load a packet to see the document"}
      </span>
    </div>
  )}
</div>
```

The original click-to-place handler (`onCanvasClick`) should remain wired to the page `<div>` wrapping each `<Page>` component so coordinate calculation still works relative to the rendered page dimensions.

### 4.4 Backward compatibility

Field coordinates are stored as normalized 0–1 floats relative to page dimensions. Existing packets are unaffected; the viewer simply shows the PDF behind the already-correct overlays. The `onCanvasClick` handler computes `(ev.clientX - rect.left) / rect.width` which normalizes to 0–1 regardless of the actual pixel size of the container, so field placements are scale-independent and will correctly overlay fields that were created before the PDF viewer was added.

### 4.5 Multi-page documents

The current field model includes a `page` field (`SignaturePacketField.page`, integer, 1-indexed). The blank-div placeholder has always rendered all fields on a single virtual page. With the `react-pdf` viewer, each `<Page>` component represents one actual PDF page and fields are filtered by `(f.page ?? 1) === pageNum`. This correctly distributes fields across pages for multi-page documents. No backend change is needed; `page` is already stored in DynamoDB.

The `onCanvasClick` handler will need a `currentPage` state variable so that fields created by clicking are assigned to the correct page:

```tsx
const [currentPage, setCurrentPage] = React.useState(1);
// Inside createSignaturePacketField call:
page: currentPage,  // was hardcoded to 1
```

### 4.5 Alternatives considered

- **`pdf-lib`** — document manipulation library, not a viewer; rejected.
- **`<iframe>` pointing at PDF URL** — cross-origin concerns and inability to overlay absolutely-positioned divs; rejected.
- **Backend-generated PNG thumbnails** — adds server complexity; react-pdf is client-side and avoids a new backend endpoint beyond the pre-sign URL; rejected.

### Effort and risk

**Effort**: L (as stated in the gap ticket). The `react-pdf` library is mature but adds ~300 KB to the JS bundle (gzip ~100 KB). The worker file must be served; Vite's `new URL(...)` pattern handles this automatically. No backend migration needed; existing packet data is forward-compatible.

**Rollout**: Can be shipped behind a `SIGNATURE_PDF_VIEWER_ENABLED` feature flag (check `import.meta.env.VITE_SIGNATURE_PDF_VIEWER` at the `pdfUrl` branch). Disable flag in environments where PDF serving is not yet configured.

**Risks**: Pre-signed S3 URL expiry (5 min) may surprise users who leave the page open; mitigate with a `refetch on focus` React Query pattern on the URL query. Large multi-page PDFs (50+ pages) can be slow; lazy-render pages not in viewport using an `IntersectionObserver` wrapper around each `<Page>` component.

The `pdfjs-dist` worker file must be served from the same origin as the app to avoid CORS issues. The `new URL("pdfjs-dist/build/pdf.worker.min.mjs", import.meta.url)` Vite pattern copies the worker into the `dist/assets/` directory automatically. Verify this works in the production build via `vite build --mode production` before deploying.

**Bundle size**: `pdfjs-dist` adds approximately 300 KB to the bundle (100 KB gzip). This is acceptable for a dedicated document-signing page. If bundle size is a concern, the `react-pdf` import can be placed in a lazily-loaded component so the library is only downloaded when the user navigates to the signing page.
