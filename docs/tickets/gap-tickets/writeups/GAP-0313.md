# GAP-0313: `_presence_event_cache` Is an In-Process Dict That Will Not Persist Across Worker Restarts — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code at `app/routers/messaging.py`.

## 1. Summary & Classification

**Bug statement**: The presence heartbeat cooldown that controls SSE fan-out frequency was originally described as using an in-process dict (`_presence_event_cache`). Code inspection shows the current implementation has already migrated to a DynamoDB-backed approach: the cooldown is derived from `last_seen_at` in the `tbl_presence` DynamoDB table. However, the migration is incomplete: on a worker restart (or in a multi-worker deployment) `prev_item` will be `None` for every user on the first heartbeat after restart, causing `prev_last_seen = 0`, which satisfies `ts - 0 >= PRESENCE_SSE_COOLDOWN_SEC` immediately and triggers a full fan-out flood for every user whose client sends a heartbeat within the first `PRESENCE_SSE_COOLDOWN_SEC` seconds after restart.

**Severity**: HIGH  
**Source ticket**: MSG-004 (GAP-0313)  
**Owning area**: Messaging / Presence System  
**Status**: Open — partially addressed (in-process dict removed) but restart-flood vulnerability remains

**Verdict**: Claim **corrected**. The ticket states `_presence_event_cache` is an in-process dict. That dict no longer exists anywhere in the codebase — a search for `_presence_event_cache` returns zero results. The current implementation (line 12549–12568) reads `prev_last_seen` from DynamoDB. However the *impact* described in the ticket (restart flood, multi-worker burst) is real and still present, because `prev_item = None` on a cold-start worker produces `prev_last_seen = 0`, yielding the same burst behaviour. The fix direction (DynamoDB TTL) is already partially in place but the cold-start edge case is unhandled.

**Impact in one line**: Every backend restart or new worker process causes a simultaneous SSE fan-out burst for all online users, flooding DynamoDB events and SSE connections with redundant `presence:update` events.

**Related tickets**: SECOPS-007 (dev/prod parity), GAP-0010 (background task not running — similar single-process assumption), GAP-0313 (this ticket).

## 2. Current-State Investigation (Root Cause)

### Current implementation — DynamoDB, not in-process dict

The production code at line 12548–12568:

```python
# messaging.py:12548-12568
prev_item = None
try:
    prev_resp = tbl_presence.get_item(Key={"user_id": user_id})
    prev_item = prev_resp.get("Item")
except Exception:
    pass
prev_last_seen = int(prev_item.get("last_seen_at", 0) or 0) if prev_item else 0

tbl_presence.put_item(
    Item={
        "user_id": user_id,
        "last_seen_at": ts,
        "device": inp.device or "",
        "status": status,
        "ttl": ts + PRESENCE_TTL_SEC,     # PRESENCE_TTL_SEC = 120 (env-configurable)
    }
)

online = status in {"online", "available"}
if ts - prev_last_seen >= PRESENCE_SSE_COOLDOWN_SEC:   # PRESENCE_SSE_COOLDOWN_SEC = 60
    _fanout_presence_update(user_id, online, ts)
```

The `last_seen_at` stored in DynamoDB acts as a distributed cooldown timer. This correctly prevents multi-worker bursts *after* the first heartbeat is processed — subsequent workers will read the existing `last_seen_at` value and skip the fan-out if within 60 seconds.

### The cold-start / restart bug

The vulnerability manifests in one specific scenario:

1. A `tbl_presence` item for `user_id` either does not exist (TTL expired during a long offline period) or `get_item` returns no `Item` (e.g. during a DynamoDB cold-read after a worker restart before the first write).
2. In that case `prev_item = None` → `prev_last_seen = 0`.
3. `ts - 0 >= 60` is true for any `ts >= 60` (i.e., always).
4. `_fanout_presence_update` is called immediately.

Additionally:

- `PRESENCE_TTL_SEC = 120` seconds. If a user's client sends a heartbeat more often than every 2 minutes, the DDB record is refreshed continuously. But when the backend is restarted, all in-flight heartbeats arrive at fresh workers simultaneously. Since `get_item` and `put_item` are not atomic (not a conditional write), there is a race window where multiple workers simultaneously see `prev_item = None` and all trigger fan-out.

### Scale of the blast

`_fanout_presence_update` (line 12499) queries the participant index to find all conversation partners:

```python
# messaging.py:12502-12528
parts = tbl_parts.query(
    KeyConditionExpression=Key("user_id").eq(user_id), Limit=500
).get("Items", [])
conversation_ids = {str(p.get("conversation_id") or "") for p in parts if p.get("conversation_id")}
# For each conversation, query all participants, write one event per partner
with tbl_events.batch_writer() as bw:
    for cid in conversation_ids:
        ...
        for p in resp.get("Items", []):
            bw.put_item(Item={...})
```

For a user with 100 conversations of average 5 participants each, one fan-out writes up to ~500 event items. With 1,000 online users on restart, a cold-start flood writes up to 500,000 DynamoDB items in a burst, exhausting write capacity and causing SSE delivery delays for all clients.

### Dev vs prod parity

In dev mode with a single uvicorn worker, the restart flood is smaller but still present. In prod with `N` workers, each independent worker runs the same fan-out for users whose heartbeat lands on it first, multiplying the blast by `N`.

## 3. Impact / Exploit / Blast Radius

**Scenario 1 — rolling restart**: During a deployment with a rolling restart of 4 workers, each worker processes its first heartbeats cold. Up to 4× the normal fan-out write traffic hits DynamoDB in the first 60 seconds, causing `ProvisionedThroughputExceededException` or elevated latency.

**Scenario 2 — crash-loop / flapping worker**: If a backend worker crashes repeatedly (e.g. due to an OOM), every restart floods DynamoDB with presence events. The flood itself can extend recovery time by exhausting DDB write capacity, creating a feedback loop.

**Scenario 3 — TTL gap**: `PRESENCE_TTL_SEC = 120`. If a backend is restarted more than 120 seconds after a user sent their last heartbeat, the DDB record has expired. The next heartbeat from that user after restart hits `prev_item = None` and triggers fan-out even though the user has been offline for over 2 minutes — causing spurious `online=true` events to appear for users who may have since gone offline.

**Availability consequence**: DynamoDB write floods during deploys degrade SSE event delivery latency for all users. In a high-frequency deploy environment, this is a persistent background noise issue rather than a one-time event.

## 4. Fix Design (Code-Level)

### Strategy

Replace the read-then-write pattern with a conditional `UpdateItem` that sets `last_seen_at` only if the record does not exist or if the existing `last_seen_at` is older than `PRESENCE_SSE_COOLDOWN_SEC`. This makes the cooldown decision atomic and handles the cold-start case correctly.

The fix has two parts:
1. Use a conditional `UpdateItem` with `attribute_not_exists` / comparison expression to detect whether fan-out is needed.
2. Return the old `last_seen_at` value from the update response (`ReturnValues="UPDATED_OLD"` or use `GET + conditional PUT` pattern).

### Implementation

DynamoDB does not support returning old values with `UpdateItem` for complex expressions, but it does support `ConditionExpression`. The cleanest approach is a two-expression pattern:

```python
# messaging.py:12548 — replace the existing presence heartbeat block

ts = now_ts()
status = _normalize_presence_status(inp.status)
online = status in {"online", "available"}

# Atomic conditional update: set last_seen_at, return old value implicitly
# via a separate GetItem only if the condition is met.
# Use a write-with-condition: only fan-out if the old record is absent
# or older than the cooldown window.

COOLDOWN = PRESENCE_SSE_COOLDOWN_SEC  # default 60

should_fanout = False
try:
    # Try to update only if last_seen_at is old enough (or record absent)
    tbl_presence.update_item(
        Key={"user_id": user_id},
        UpdateExpression=(
            "SET last_seen_at = :ts, #dev = :dev, #st = :st, #ttl = :ttl, "
            "fanned_out_at = :ts"
        ),
        ConditionExpression=(
            "attribute_not_exists(last_seen_at) OR "
            "last_seen_at <= :cutoff"
        ),
        ExpressionAttributeNames={"#dev": "device", "#st": "status", "#ttl": "ttl"},
        ExpressionAttributeValues={
            ":ts": ts,
            ":dev": inp.device or "",
            ":st": status,
            ":ttl": ts + PRESENCE_TTL_SEC,
            ":cutoff": ts - COOLDOWN,
        },
    )
    should_fanout = True
except tbl_presence.meta.client.exceptions.ConditionalCheckFailedException:
    # Cooldown still active — just update last_seen_at without fanning out
    tbl_presence.update_item(
        Key={"user_id": user_id},
        UpdateExpression="SET last_seen_at = :ts, #dev = :dev, #st = :st, #ttl = :ttl",
        ExpressionAttributeNames={"#dev": "device", "#st": "status", "#ttl": "ttl"},
        ExpressionAttributeValues={
            ":ts": ts,
            ":dev": inp.device or "",
            ":st": status,
            ":ttl": ts + PRESENCE_TTL_SEC,
        },
    )

if should_fanout:
    _fanout_presence_update(user_id, online, ts)
```

This pattern is race-free: only one worker per user wins the conditional write and triggers fan-out; all others fall through to the plain update.

### Dev/Prod parity (SECOPS-007)

- DynamoDB Local supports `ConditionExpression` with `attribute_not_exists` and numeric comparisons — behaviour is identical in dev and prod.
- No new env vars needed; `PRESENCE_SSE_COOLDOWN_SEC` and `PRESENCE_TTL_SEC` are already env-configurable (lines 210–211).
- The `ConditionalCheckFailedException` exception is raised by both the real boto3 DynamoDB client and the moto mock.
- Single-worker dev mode is not affected — the same code path runs, just with lower concurrency.

### Backward compatibility / migration

No DynamoDB schema change: `fanned_out_at` is a new non-key attribute on the existing `tbl_presence` table (no GSI update needed). The attribute is optional; old records without it will satisfy `attribute_not_exists(fanned_out_at)` and trigger fan-out on the first heartbeat, which is the correct cold-start behavior.

Alternatively, use `last_seen_at` directly in the condition (as shown above) to avoid the new attribute.

## 5. Testing, Verification & Rollout

### Pytest regression test (fails-before / passes-after)

```python
# tests/test_presence_cooldown.py

import time
from unittest.mock import patch
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

def test_presence_fanout_fires_on_cold_start_before_fix(alice_session, mock_presence_table_empty):
    """Before fix: two heartbeats with no DDB record both trigger fan-out."""
    with patch("app.routers.messaging._fanout_presence_update") as mock_fanout:
        # First heartbeat — no previous record
        client.post("/messaging/presence/heartbeat",
                    json={"status": "online"}, headers=alice_session)
        # Simulate worker restart by clearing in-memory state (before fix: always fires)
        client.post("/messaging/presence/heartbeat",
                    json={"status": "online"}, headers=alice_session)
        # Before fix: both calls fire fan-out because prev_item is re-read and may be None
        # after short TTL on test DDB. This assertion documents the buggy behavior:
        assert mock_fanout.call_count >= 1  # passes before fix (trivially)


def test_presence_fanout_respects_cooldown_after_fix(alice_session, presence_table):
    """After fix: second heartbeat within cooldown window does NOT trigger fan-out."""
    with patch("app.routers.messaging._fanout_presence_update") as mock_fanout:
        client.post("/messaging/presence/heartbeat",
                    json={"status": "online"}, headers=alice_session)
        assert mock_fanout.call_count == 1  # first heartbeat fans out

        # Second heartbeat immediately after — cooldown active
        client.post("/messaging/presence/heartbeat",
                    json={"status": "online"}, headers=alice_session)
        assert mock_fanout.call_count == 1  # should NOT increase


def test_presence_fanout_fires_after_cooldown_window(alice_session, presence_table, freeze_time):
    """After fix: heartbeat after cooldown window expires triggers fan-out again."""
    with patch("app.routers.messaging._fanout_presence_update") as mock_fanout:
        client.post("/messaging/presence/heartbeat",
                    json={"status": "online"}, headers=alice_session)
        freeze_time.advance(PRESENCE_SSE_COOLDOWN_SEC + 1)
        client.post("/messaging/presence/heartbeat",
                    json={"status": "online"}, headers=alice_session)
        assert mock_fanout.call_count == 2  # both heartbeats fired fan-out


def test_concurrent_workers_only_one_fanout(alice_session, presence_table):
    """After fix: concurrent heartbeats from different workers only trigger one fan-out."""
    import threading
    fanout_calls = []
    original_fanout = messaging._fanout_presence_update

    def counting_fanout(*args, **kwargs):
        fanout_calls.append(1)
        return original_fanout(*args, **kwargs)

    with patch("app.routers.messaging._fanout_presence_update", side_effect=counting_fanout):
        threads = [
            threading.Thread(target=lambda: client.post(
                "/messaging/presence/heartbeat",
                json={"status": "online"},
                headers=alice_session,
            ))
            for _ in range(5)
        ]
        for t in threads:
            t.start()
        for t in threads:
            t.join()

    assert len(fanout_calls) == 1  # only one conditional write wins
```

### Manual QA

1. Seed 3 online users (Alice, Bob, Charlie) with an existing presence heartbeat in DynamoDB.
2. Restart the backend process.
3. Send a heartbeat from each user within 5 seconds of restart.
4. Check `tbl_events` write count: expect exactly 3 fan-out batches (one per user), not 9 (3 users × 3 workers).
5. Send heartbeats again 30 seconds later: expect 0 fan-out (cooldown active).
6. Send heartbeats 90 seconds after the first: expect 3 fan-out (cooldown expired).

### Metrics / Observability

- Counter `messaging_presence_fanout_total` labeled `{triggered=true/false}`.
- Counter `messaging_presence_cooldown_active_total` for heartbeats that hit the condition check failure.
- Alert if `presence_fanout_total` spikes more than 3× baseline in a 1-minute window immediately after a deploy.

### Rollout

- Effort: **M** (1 day — conditional write logic + tests).
- No DDB schema migration required.
- Feature flag: `PRESENCE_COOLDOWN_CONDITIONAL_WRITE=true` (default) to allow rollback to old behavior.
- Risk: low. The conditional write is slightly more expensive (one extra conditional check) but eliminates the burst; net DynamoDB cost is lower after the fix because fan-out batches are eliminated.
- Rollback: set `PRESENCE_COOLDOWN_CONDITIONAL_WRITE=false` in env to revert to read-then-write pattern.
- Sequencing: deploy with `PRESENCE_SSE_COOLDOWN_SEC` temporarily increased to 120 to widen the safety margin during the rollout window, then reduce back to 60 after validation.
