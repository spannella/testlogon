# GAP-0086: `create_feedback_request` Does Not Pause Agent — Remediation Write-up

> Source ticket: AGENT-006 · Severity: HIGH · Effort: S · Status: Open

## 1. Summary & Classification

**Bug statement.** When the terminal monitor detects a `feedback_needed` pattern in agent output and calls `create_feedback_request`, the agent worker's state is never transitioned from `working` to `awaiting_feedback`. The agent therefore continues its processing loop uninterrupted — consuming compute, potentially overwriting work, and generating duplicate feedback records — while a pending question waits unacknowledged in DynamoDB.

**Verdict (confirmed).** The code at `app/services/terminal_monitor.py:191–230` creates and persists the feedback record but contains no call to `agent_orchestrator.transition_agent_state(user_id, worker_id, "awaiting_feedback")`. The `transition_agent_state` function at `app/services/agent_orchestrator.py:83–121` is fully implemented and enforces the `working → awaiting_feedback` edge in the `VALID_TRANSITIONS` table, but it is simply never invoked from the feedback creation path.

**Severity and area.** HIGH / Agent Orchestration & Feedback Loop. Affects every autonomously running coder, QA, reviewer, and devops agent that encounters an ambiguous situation or explicit `[AGENT_FEEDBACK_NEEDED]` signal. The bug degrades human-in-the-loop oversight, the primary correctness gate for agent work.

**Related tickets.** AGENT-006 (Terminal Monitoring & Feedback Loop — parent feature). No blocking dependencies; the state machine is already wired for the `awaiting_feedback` state, so the fix is a one-line call addition.

## 2. Current-State Investigation (root cause)

### The feedback creation path: `terminal_monitor.py:191–230`

```python
# app/services/terminal_monitor.py:191–230
def create_feedback_request(
    user_id: str,
    worker_id: str,
    ticket_id: str,
    *,
    question: str,
    terminal_context: str = "",
    detected_pattern: str = "",
    timeout_seconds: int = DEFAULT_FEEDBACK_TIMEOUT_SECONDS,
    timeout_action: str = "skip",
) -> Dict[str, Any]:
    """Create a feedback request when the agent needs human input."""
    request_id = uuid4().hex
    ts = now_ts()
    item = {
        ...
        "feedback_status": "pending",
        ...
    }
    T.agent_feedback.put_item(Item=item)     # ← persists record
    logger.info(...)
    return item
    # ← NO call to transition_agent_state here
```

The function correctly constructs and persists the `WORKER#{worker_id}/FEEDBACK#{request_id}` item, setting `feedback_status = "pending"`. However it returns immediately after `put_item` without touching the worker's `agent_state`.

### The state machine: `agent_orchestrator.py:26–34`

```python
# app/services/agent_orchestrator.py:26–34
VALID_TRANSITIONS: Dict[str, set] = {
    "idle":             {"claiming", "paused"},
    "claiming":         {"working", "idle", "error"},
    "working":          {"awaiting_feedback", "completing", "paused", "error", "idle"},
    "awaiting_feedback": {"working", "paused", "error", "idle"},
    "completing":       {"idle", "error"},
    "paused":           {"idle", "working"},
    "error":            {"idle"},
}
```

The `working → awaiting_feedback` edge at line 29 is well-defined. `transition_agent_state` at line 83 performs a DynamoDB conditional update with a `ConditionExpression` that prevents concurrent state overwrites. The function is correct and ready to be called.

### The router path: `agent_feedback.py:203–221`

The HTTP endpoint `POST /ui/feedback/{worker_id}` at `app/routers/agent_feedback.py:203–221` also calls `svc.create_feedback_request` directly. It too skips the state transition, meaning even manually triggered feedback requests (used in testing) leave the agent in `working` state.

### State machine background

The `VALID_TRANSITIONS` table at `agent_orchestrator.py:26–34` was clearly designed with `awaiting_feedback` as a first-class state. The `awaiting_feedback → working` back-edge exists for when a human responds and the agent resumes. The `awaiting_feedback → paused` and `awaiting_feedback → error` edges provide escape hatches. The absence of the `working → awaiting_feedback` transition call in `create_feedback_request` is therefore a missing wiring step — the state machine exists and is correct, but nothing connects the feedback creation event to the state machine.

This is a common integration gap in systems where the state machine is built in one iteration and the business logic that should drive it is built in another. The `create_feedback_request` function was implemented as a pure DDB write without the orchestration call, and no test existed to catch the missing side effect.

### Runtime manifestation

1. Agent terminal emits `[AGENT_FEEDBACK_NEEDED]`.
2. `PatternMatcher.match()` returns `{"signal": "feedback_needed", ...}`.
3. Caller invokes `create_feedback_request(...)` — record written.
4. Agent state in DDB remains `working` — the orchestrator loop, seeing `working`, continues dispatching new steps.
5. On the next pattern-match cycle the same or a different `feedback_needed` signal fires again, writing a second (and third…) feedback record.
6. The UI lists multiple `pending` requests for the same ticket; responding to any one of them does not stop the flood.

In dev mode the effect is masked because `run_mock_workflow` never polls live terminal output. The bug fully manifests only when `S.agent_coder_execute_commands = True` and an agent is processing real terminal output.

## 3. Impact / Exploit / Blast Radius

**Operational correctness.** A `working` agent that should be blocked waiting for a human decision continues consuming worker credits, advancing through workflow steps, and potentially committing and pushing code based on an ambiguous requirement. The feedback mechanism — the entire human-in-the-loop safety valve — is bypassed.

**Duplicate feedback records.** Without a state gate, the monitor loop can fire `create_feedback_request` on every polling cycle (typically every few seconds) for the duration of the window. A 4-hour `DEFAULT_FEEDBACK_TIMEOUT_SECONDS` window with a 5-second poll cycle produces up to ~2,880 duplicate pending records per stuck agent. These flood the feedback list UI and make it impossible to identify the canonical question.

**Financial.** Worker execution billed against user quota continues running. If the external coding tool (Claude Code, Codex) is invoked per-step and the agent keeps executing, token costs accumulate unboundedly.

**Data integrity.** An agent that proceeds past an ambiguous branch point may create a PR with the wrong design decision baked in, requiring manual rollback. For agents operating on production repositories this represents a real data-corruption risk.

**Blast radius.** Every user with at least one autonomously running agent worker with `AGENT_CODER_EXECUTE_COMMANDS=1` is affected the first time any feedback pattern fires. Dev-mode deployments are not affected because `run_mock_workflow` does not poll terminal output.

## 4. Fix Design (code-level)

### Primary change: `app/services/terminal_monitor.py`

Import `agent_orchestrator` (already available in the service layer) and call `transition_agent_state` immediately after `T.agent_feedback.put_item`:

```python
# app/services/terminal_monitor.py — patched create_feedback_request

from app.services import agent_orchestrator as orchestrator  # add at top of file

def create_feedback_request(
    user_id: str,
    worker_id: str,
    ticket_id: str,
    *,
    question: str,
    terminal_context: str = "",
    detected_pattern: str = "",
    timeout_seconds: int = DEFAULT_FEEDBACK_TIMEOUT_SECONDS,
    timeout_action: str = "skip",
) -> Dict[str, Any]:
    """Create a feedback request when the agent needs human input."""
    request_id = uuid4().hex
    ts = now_ts()
    item = { ... }  # unchanged
    T.agent_feedback.put_item(Item=item)

    # NEW: pause the agent so it stops processing until the human responds.
    try:
        orchestrator.transition_agent_state(user_id, worker_id, "awaiting_feedback")
    except ValueError as exc:
        # Worker may already be in awaiting_feedback (duplicate signal) or
        # in a terminal state (error/idle). Log and continue — the feedback
        # record is still useful even if the transition is a no-op.
        logger.warning(
            "Could not transition worker %s to awaiting_feedback: %s", worker_id, exc
        )

    logger.info(
        "Created feedback request %s for worker %s (ticket %s)",
        request_id, worker_id, ticket_id,
    )
    return item
```

The `try/except ValueError` is essential: if the agent is already in `awaiting_feedback` (a duplicate pattern match fired before the state update propagated) or has transitioned to `error` or `idle` via a concurrent path, `transition_agent_state` raises `ValueError`. Swallowing that specific error and logging it preserves the feedback record while avoiding an unhandled exception that would prevent the record from being returned to the caller.

### Secondary change: resume on response — `respond_to_feedback`

`respond_to_feedback` at `terminal_monitor.py:233` sets `feedback_status = "responded"` but does not transition the agent back to `working`. The operator or a polling loop must do this manually. To close the loop completely, add the symmetric `awaiting_feedback → working` transition:

```python
# app/services/terminal_monitor.py — patched respond_to_feedback

def respond_to_feedback(
    user_id: str, worker_id: str, request_id: str, response_text: str
) -> Dict[str, Any]:
    ...  # existing validation + DDB update unchanged

    # NEW: resume the agent now that a human has answered.
    try:
        orchestrator.transition_agent_state(user_id, worker_id, "working")
    except ValueError as exc:
        logger.warning(
            "Could not resume worker %s to working after feedback response: %s",
            worker_id, exc,
        )
    return get_feedback_request(worker_id, request_id)
```

### Dev/Prod parity (SECOPS-007)

`transition_agent_state` writes to `T.agent_workers` (DynamoDB). In dev mode this is DynamoDB Local on port 8001, in production it is the real AWS DynamoDB table specified by `S.ddb_agent_workers_table`. No AWS-specific path divergence exists; the same code path runs in both environments. The `try/except ValueError` guard ensures that moto's DynamoDB mock (used in pytest) behaves identically to the real service — both raise a Python `ValueError` for invalid transitions. No feature flag is needed.

### Backward compatibility / migration

The `agent_workers` DynamoDB table already stores `agent_state`; no schema migration is required. Workers in flight when the patch is deployed will continue with their current `agent_state`; the next `create_feedback_request` call will attempt the `working → awaiting_feedback` transition. Workers already in `idle` or `error` will log a warning but otherwise be unaffected.

### Alternatives considered

**Option A — Gate on state before writing the record.** If the worker is already `awaiting_feedback`, skip writing a new record entirely. This prevents the duplicate-record flood but discards potentially distinct questions. Rejected: the first recorded question is often stale context; the most recent one is the relevant one.

**Option B — Deduplicate in `create_feedback_request` by querying for existing `pending` records.** More complex and introduces a read-before-write that is not atomic under concurrent invocations. Rejected in favour of the simpler state-machine gate.

        user_id=user_id, worker_id=worker_id, ticket_id="T-001",

All three tests fail against the current code (first two because `agent_state` is never changed; third because without the try/except the second call would raise `ValueError`). All three pass after the fix.

### Manual QA steps

1. Start the dev stack: `just up`.
2. Create a coder agent with `AGENT_CODER_EXECUTE_COMMANDS=1` in `.env.local` (or temporarily via env override).
3. Trigger a workflow against a ticket whose subject contains `[AGENT_FEEDBACK_NEEDED]`.
4. Observe the terminal monitor polling loop via the Dev Tools UI (`http://localhost:3001`).
5. Verify the worker card shows state `awaiting_feedback` (not `working`) within the next polling cycle.
6. Submit a response via the Feedback UI; verify state returns to `working`.

### Metrics / observability

- Add a `feedback_pause_total` counter (Prometheus label `worker_id`) incremented inside `create_feedback_request` after the successful transition. Alert if a single worker accumulates > 10 in 5 minutes (indicator of a pattern storm, not human input).
- Add a `feedback_resume_total` counter in `respond_to_feedback` after the `working` transition to measure the human response rate.
- Log level for the `ValueError` catch should be `WARNING`, not `DEBUG`, so it surfaces in CloudWatch without paging.
- The Dev Tools UI (`http://localhost:3001`) should reflect the `awaiting_feedback` state immediately after creation. If the worker card still shows `working` after submitting a feedback request via the UI, that is a regression indicator for this bug.

### Rollout

- **Effort**: S (< 1 day). Two targeted function edits plus tests.
- **Risk**: Low. The only new failure mode is a `ValueError` being swallowed during a state-transition edge case, which is handled explicitly.
- **Sequencing**: Can be deployed independently. No schema migration. No frontend change required. Deploy backend, run `just test`, confirm no regressions.
- **Rollback**: Revert the two function edits; the feedback mechanism degrades back to current behaviour (records created, agent not paused) rather than failing hard.
