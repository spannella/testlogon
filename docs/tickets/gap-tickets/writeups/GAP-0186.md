# GAP-0186: `PromoValidateOut` Missing FIN-002 Extended Fields — Remediation Write-up

> Source ticket: FIN-002 · Severity: HIGH · Effort: S · Status: Open

## 1. Summary & Classification

**Bug statement.** The `PromoValidateOut` Pydantic model (the response shape of
`POST /ui/promo-codes/validate`) is missing six fields that the FIN-002 specification
requires: `error_code`, `discount_pct`, `original_price_cents`, `buy_x`, `get_y`, and
`free_item_description`. Because the model does not declare these fields, the endpoint
can never return them even if the service layer were to produce them. The frontend
`Checkout.tsx` receives only `{ valid, code_id, discount_type, discount_cents,
final_price_cents, free_trial_days, message }` and therefore cannot render
type-specific discount badges (e.g. "10% off" vs "$5 off" vs "buy 2 get 1 free") or
surface structured error states to the user.

**Verdict: Confirmed.** `app/models.py:3318–3325` defines the class; none of the six
fields appear anywhere in the model. The `PromoValidateOut` TypeScript interface in
`frontend/src/api/types.ts:3959–3967` mirrors the same truncated shape, confirming the
gap spans both layers.

**Severity and area.** HIGH / Billing & Promo (FIN-002). The missing `discount_pct`
field is the most immediately user-visible gap: a percentage-type promo code (the
most common type) cannot have its percentage displayed in the checkout UI; the user
sees only the derived `discount_cents` amount with no indication of what rate was
applied. The `buy_x`/`get_y` and `free_item_description` fields block future discount
types entirely. The `original_price_cents` and `error_code` fields are load-bearing for
GAP-0187 (structured error codes) and any refund-audit trail that needs to record the
pre-discount price.

**Related tickets.** GAP-0187 (error_code on failure paths — shares the same model and
the `fail` dict initialiser, so both fixes belong in one PR). GAP-0188 (tip/unlock
checkout types — the `PromoValidateIn` Literal constraint also requires updating to
allow `"tip"` and `"unlock"`, which is a separate line in the same model file). No
other blocking dependency; the model change for this ticket can ship independently and
the downstream behaviour improves immediately.

## 2. Current-State Investigation (root cause)

### Model definition: `app/models.py:3318–3325`

```python
class PromoValidateOut(BaseModel):
    valid: bool
    code_id: Optional[str] = None
    discount_type: Optional[str] = None
    discount_cents: int = 0
    final_price_cents: int = 0
    free_trial_days: int = 0
    message: Optional[str] = None
```

Seven fields, all populated by `validate_promo_code` in `app/services/promo_codes.py`.
There is no `error_code`, `discount_pct`, `original_price_cents`, `buy_x`, `get_y`, or
`free_item_description` anywhere in this class definition.

### Router: `app/routers/promo_codes.py:140–154`

```python
@router.post("/ui/promo-codes/validate", response_model=PromoValidateOut)
async def validate_code(body: PromoValidateIn, ctx: Dict = Depends(require_ui_session)):
    ...
    result = validate_promo_code(code=..., ...)
    return PromoValidateOut(**result)
```

The router uses `PromoValidateOut` as both the `response_model` (controls OpenAPI
schema and response serialisation) and as the constructor target. Any extra key in
`result` is silently dropped by Pydantic during `PromoValidateOut(**result)`. The
pattern is therefore doubly blocking: the model omits the fields, and even if
`validate_promo_code` were to produce them today, they would be stripped before
reaching the client.

### Service layer: `app/services/promo_codes.py:324–332` (success path)

```python
return {
    "valid": True,
    "code_id": promo["code_id"],
    "discount_type": dtype,
    "discount_cents": discount_cents,
    "final_price_cents": final_price,
    "free_trial_days": trial_days,
    "message": None,
}
```

The success dict also omits all six extended fields. For a `percentage`-type discount,
`discount_value` (the raw percentage integer, e.g. `10` for 10%) is available on the
`promo` dict but is never placed into the return payload.

### Frontend: `frontend/src/api/types.ts:3959–3967`

```typescript
export interface PromoValidateOut {
  valid: boolean;
  code_id: string | null;
  discount_type: string | null;
  discount_cents: number;
  final_price_cents: number;
  free_trial_days: number;
  message: string | null;
}
```

The TypeScript interface mirrors the truncated backend model exactly. `Checkout.tsx:116`
uses only `result.message` for the error string and `result.discount_cents` /
`result.final_price_cents` for the price display — no badge rendering for discount
type is attempted because the fields it would need (`discount_pct`) do not exist on
the type.

### Runtime behaviour

When a creator runs a 10%-off promo and a buyer applies it at checkout, the response is:

```json
{"valid": true, "code_id": "pc_abc123", "discount_type": "percentage",
 "discount_cents": 500, "final_price_cents": 4500, "free_trial_days": 0,
 "message": null}
```

The `discount_type: "percentage"` field is present but the `discount_pct: 10` field is
not, so the checkout UI can show "$5.00 off" but not "10% off" — the user has no way to
verify the rate matches the advertised code. The mismatch matters particularly when a
creator advertises "20% off" in a social post: the checkout shows only the derived
dollar amount, which can differ from the expected percentage depending on the cart total,
giving the user no way to confirm the right code was applied.

For `buy_x_get_y` codes (a planned discount type), the checkout would show
`discount_type: "buy_x_get_y"` and `discount_cents: 0` (since the discount is applied
per-item, not as a flat amount) — entirely uninformative. Without `buy_x`, `get_y`, and
`free_item_description` in the response, the checkout page cannot even explain to the
user what qualifying condition they need to meet.

The `original_price_cents` field is also absent from the response, which creates a
subtle audit problem: the frontend knows `item_price_cents` (sent in the request) and
`final_price_cents` (in the response), but it infers the original price from its own
local state rather than from a server-confirmed value. If the item price changes between
when the page loaded and when the promo was applied (e.g. a flash sale ended), the
derived "savings" line shown in the UI will be incorrect.

## 3. Impact / Exploit / Blast Radius

**UX degradation.** Percentage-based and tiered discount codes cannot display the
applicable rate in the checkout flow. Users cannot confirm the code was applied at the
expected rate, reducing trust in the promo feature.

**Frontend extensibility blocked.** The FIN-002 spec defines `buy_x`/`get_y` and
`free_item_description` specifically so that the Checkout UI can render BOGO badges
("Buy 2, Get 1 Free – Free item: Premium Sticker Pack"). Without these model fields the
frontend has no path to implement BOGO rendering even when the backend discount
calculation is shipped.

**Audit trail incompleteness.** `original_price_cents` in the response would let the
frontend write a local audit line showing "original $X → discount $Y → final $Z".
Currently the frontend must infer `original_price_cents` from `item_price_cents` passed
into the request, which breaks if the price changes between page load and promo
application.

**No security/financial exploit.** The gap does not allow a buyer to obtain an
unintended discount; the `discount_cents` value in the response is correctly computed
by `_calculate_discount`. The impact is UX and feature incompleteness, not financial
integrity.

**Blast radius.** Every consumer of `POST /ui/promo-codes/validate` is affected: the
shop `Checkout.tsx`, and any future surfaces (subscription flow, messaging tip unlock)
that need to render discount breakdowns.

## 4. Fix Design (code-level)

### Step 1 — Extend `PromoValidateOut` in `app/models.py`

```python
class PromoValidateOut(BaseModel):
    valid: bool
    code_id: Optional[str] = None
    discount_type: Optional[str] = None
    discount_cents: int = 0
    discount_pct: Optional[int] = None          # populated when discount_type="percentage"
    original_price_cents: int = 0               # item_price_cents as received
    final_price_cents: int = 0
    free_trial_days: int = 0
    buy_x: Optional[int] = None                 # for buy_x_get_y type
    get_y: Optional[int] = None
    free_item_description: Optional[str] = None
    error_code: Optional[str] = None            # machine-readable; see GAP-0187
    message: Optional[str] = None
```

All new fields are `Optional` with `None` default so the change is fully backward-
compatible: clients that ignore unknown fields (including the current frontend) continue
to work without modification.

### Step 2 — Populate the new fields in `validate_promo_code` (`app/services/promo_codes.py`)

The function already has `item_price_cents` in scope. The `promo` dict carries
`discount_value` (the raw percentage integer for `percentage` type) and
`buy_x`/`get_y`/`free_item_description` when present. The success return dict should be
extended:

```python
discount_pct = None
buy_x = get_y = free_item_desc = None

if dtype == "percentage":
    discount_pct = int(promo.get("discount_value") or 0)
elif dtype == "buy_x_get_y":
    buy_x = int(promo.get("buy_x") or 0)
    get_y = int(promo.get("get_y") or 0)
    free_item_desc = promo.get("free_item_description")

return {
    "valid": True,
    "code_id": promo["code_id"],
    "discount_type": dtype,
    "discount_cents": discount_cents,
    "discount_pct": discount_pct,
    "original_price_cents": item_price_cents,
    "final_price_cents": final_price,
    "free_trial_days": trial_days,
    "buy_x": buy_x,
    "get_y": get_y,
    "free_item_description": free_item_desc,
    "error_code": None,
    "message": None,
}
```

The `fail` dict initialised at line 251 also needs `original_price_cents`,
`discount_pct`, `buy_x`, `get_y`, `free_item_description`, and `error_code` populated
(see GAP-0187 for `error_code`). Minimum addition:

```python
fail = {
    "valid": False,
    "code_id": None,
    "discount_type": None,
    "discount_cents": 0,
    "discount_pct": None,
    "original_price_cents": item_price_cents,
    "final_price_cents": item_price_cents,
    "free_trial_days": 0,
    "buy_x": None,
    "get_y": None,
    "free_item_description": None,
    "error_code": None,
    "message": None,
}
```

### Step 3 — Extend the TypeScript type in `frontend/src/api/types.ts`

```typescript
export interface PromoValidateOut {
  valid: boolean;
  code_id: string | null;
  discount_type: string | null;
  discount_cents: number;
  discount_pct: number | null;
  original_price_cents: number;
  final_price_cents: number;
  free_trial_days: number;
  buy_x: number | null;
  get_y: number | null;
  free_item_description: string | null;
  error_code: string | null;
  message: string | null;
}
```

### Step 4 — Use the new fields in `Checkout.tsx`

After the model and type changes, `Checkout.tsx` can render:

```tsx
{promoResult && promoResult.discount_pct !== null && (
  <Badge variant="secondary">{promoResult.discount_pct}% off</Badge>
)}
{promoResult && promoResult.buy_x && (
  <Badge variant="secondary">
    Buy {promoResult.buy_x} get {promoResult.get_y} free
    {promoResult.free_item_description && ` – ${promoResult.free_item_description}`}
  </Badge>
)}
```

### Dev/Prod parity (SECOPS-007)

`validate_promo_code` in `app/services/promo_codes.py` is a pure DynamoDB read with no
AWS-path vs dev-path branching; the change propagates identically to both environments.
The feature is guarded by `S.promo_codes_enabled` (environment variable, default `"1"`);
no new flag is required. The extended fields are `Optional` throughout so rolling
deployment (where old and new pod versions coexist behind an ALB) will not break any
existing client.

### Backward compatibility

The model extension is additive-only. Old frontend builds that do not know about
`discount_pct` will receive the new fields in the JSON payload and silently ignore
them (TypeScript optional fields with no strict-null enforcement at runtime). New
frontend builds that expect `discount_pct` will receive `null` from old backend pods,
which should be treated as "no rate to display" — the same graceful degradation as an
absent field.

## 5. Testing, Verification & Rollout

### Regression test (pytest, fails-before / passes-after)

Add to `tests/test_promo_codes.py` (or create it):

```python
def test_validate_out_contains_discount_pct(client, auth_headers):
    # Create a percentage promo code
    resp = client.post("/ui/promo-codes", json={
        "code": "PCT10TEST",
        "discount_type": "percentage",
        "discount_value": 10,
        "applies_to": ["shop"],
    }, headers=auth_headers)
    assert resp.status_code == 201

    # Validate it
    resp = client.post("/ui/promo-codes/validate", json={
        "code": "PCT10TEST",
        "checkout_type": "shop",
        "item_price_cents": 1000,
        "creator_user_id": auth_headers["X-User-Sub"],
    }, headers=auth_headers)
    data = resp.json()
    assert data["valid"] is True
    # Fails before the fix (field absent → KeyError or None where int expected)
    assert data["discount_pct"] == 10
    assert data["original_price_cents"] == 1000
    assert data["final_price_cents"] == 900
    assert data["discount_cents"] == 100

def test_validate_out_invalid_contains_original_price(client, auth_headers):
    resp = client.post("/ui/promo-codes/validate", json={
        "code": "DOESNOTEXIST",
        "checkout_type": "shop",
        "item_price_cents": 500,
        "creator_user_id": "x",
    }, headers=auth_headers)
    data = resp.json()
    assert data["valid"] is False
    # Fails before the fix
    assert data["original_price_cents"] == 500
    assert data["final_price_cents"] == 500
```

**Fails before:** `data["discount_pct"]` raises `KeyError` (field absent in response
JSON) because `PromoValidateOut` does not declare the field and the endpoint strips it.

**Passes after:** model and service both include the field; Pydantic serialises it
correctly.

### Manual QA steps

2. Log in as Alice, navigate to `/promo-codes`, create a 10%-off code for `shop`.
3. Add a catalog item worth $50 to the cart and go to checkout.
4. Apply the promo code: confirm the checkout UI shows "10% off" badge beside the
   discount line (this badge currently cannot render because `discount_pct` is absent).
5. Check the browser network tab (Network → XHR → `/ui/promo-codes/validate` response):
   confirm `discount_pct: 10` appears in the JSON response after the fix.
6. Confirm `original_price_cents: 5000` in the response matches the cart item price.
7. Apply an expired or wrong-creator code: confirm `original_price_cents` equals the
   cart total and `final_price_cents` matches (no phantom discount applied to the error
   response).
8. Confirm `discount_type: "fixed_amount"` codes return `discount_pct: null` (the field
   is present but null, not absent).
9. Confirm `discount_type: "free_trial"` codes return `free_trial_days: N` as before
   (regression: existing fields must still be populated).

### Metrics / observability

No new metrics needed. The existing `/ui/promo-codes/validate` request counter and the
OpenAPI schema will reflect the new fields automatically once deployed.

### Rollout and risks

- **Effort:** S (small — model extension + service dict + TypeScript type + UI
  rendering, all well-isolated).
- **Risk:** Low. Additive-only change; no DynamoDB schema migration required. The
  `buy_x`/`get_y` fields will be `null` until the service layer supports BOGO discount
  type — that is safe.
- **Sequencing:** Ship GAP-0186 and GAP-0187 together (they share the same model edit
  and `fail` dict). GAP-0188 (tip/unlock checkout types) can follow independently.
- **Rollback:** Remove the new fields from `PromoValidateOut` and the service dict;
  redeploy. Frontend degrades gracefully (badges disappear, core checkout still works).
