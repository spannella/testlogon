# GAP-0225: Real K8s Launch Path Raises `NotImplementedError` — Remediation Write-up

> Source ticket: INFRA-004 · Severity: HIGH · Effort: L · Status: Open

## 1. Summary & Classification

**Bug statement.** When the platform is deployed in production mode (`K8S_MOCK_ENABLED=0` or `DEV_MODE=0`), every attempt to launch a container pod via `launch_pod()` in `app/services/k8s_launcher.py` raises `NotImplementedError("Real K8s launch not implemented yet")` at line 176. Similarly, `get_pod_logs()` raises `NotImplementedError("Real K8s logs not implemented yet")` at line 257. No real Kubernetes Python client is imported or integrated anywhere in the module. The INFRA-004 container compute feature is completely non-functional in any non-mock environment.

**Verdict (from investigation):** Confirmed. The ticket claim is accurate. Both `raise NotImplementedError` statements exist at lines 176 and 257 respectively. Additionally, `terminate_pod()` (lines 260–286) follows the silent no-op pattern for the non-mock path — it calls `_mock_store.delete_pod()` only when `S.k8s_mock_enabled` is true and otherwise proceeds silently to the DDB update without calling the Kubernetes API. This third gap is not mentioned in the ticket but has the same root cause and must be fixed alongside the others.

**Severity and area.** HIGH / Infrastructure / Container Compute. Without a real K8s client path, the container (pod) compute feature is entirely non-functional in production. Launch requests crash with 500; log fetches crash with 500; and terminations silently fail to delete the actual Kubernetes pod while marking it as "terminated" in DDB — creating resource leaks and cost overruns identical in nature to the EC2 silent-noop pattern documented in GAP-0222.

**Related tickets.** INFRA-004 (K8s launcher spec), GAP-0226 (auto-registration in host inventory never happens for K8s pods — parallel to GAP-0223 for EC2), GAP-0227 (host inventory not cleaned up on pod termination — parallel to GAP-0224), GAP-0238 (quota not enforced in K8s launcher).

## 2. Current-State Investigation (root cause)

### The broken launch path

`app/services/k8s_launcher.py:164–176`:

```python
# 5. Launch (mock or real)
if S.k8s_mock_enabled:
    result = _mock_store.create_pod(
        pod_name=k8s_pod_name,
        namespace=namespace,
        image=image,
        cpu=preset_info["cpu_millicores"],
        memory_mb=preset_info["memory_mb"],
        env_vars=env_vars or {},
        ssh_pub_key=None,
    )
else:
    raise NotImplementedError("Real K8s launch not implemented yet")
```

`S.k8s_mock_enabled` is defined at `app/core/settings.py:2117`:

```python
k8s_mock_enabled: bool = os.environ.get(
    "K8S_MOCK_ENABLED",
    os.environ.get("DEV_MODE", "1")
) not in ("0", "false", "False")
```

Same defaulting logic as EC2: in a production environment where `DEV_MODE=0` and `K8S_MOCK_ENABLED` is unset, `k8s_mock_enabled` evaluates to `False`, triggering `NotImplementedError` on every `launch_pod` call.

### The broken log-fetch path

`app/services/k8s_launcher.py:254–257`:

```python
if S.k8s_mock_enabled:
    return _mock_store.get_logs(k8s_pod_name, namespace, tail=tail)

raise NotImplementedError("Real K8s logs not implemented yet")
```

Unlike the launch path, this is an unconditional raise when mock is disabled — there is no `else` wrapper. Any request to `GET /ui/k8s/pods/{pod_id}/logs` in production will 500.

### The silent no-op in `terminate_pod()`

`app/services/k8s_launcher.py:268–286`:

```python
if S.k8s_mock_enabled:
    _mock_store.delete_pod(k8s_pod_name, namespace)

now = now_ts()
T.k8s_pods.update_item(
    Key={"user_sub": user_sub, "sk": f"POD#{pod_id}"},
    UpdateExpression="SET #st = :st, terminated_at = :ta",
    ...
)
```

In production, the real Kubernetes `delete_namespaced_pod` API is never called. The DDB record is updated to "terminated" but the Kubernetes pod continues running and consuming cluster resources until it either expires via its TTL (controlled by the pod spec, not the application) or is manually deleted. For pods launched with `DEFAULT_TTL_SECONDS = 14400` (4 hours), this means up to 4 hours of unintended resource consumption per "terminated" pod.

### Missing kubernetes Python client

The module imports (`app/services/k8s_launcher.py:1–16`) contain no reference to the `kubernetes` package. A `pip show kubernetes` in the project venv would show the package is not installed. The `requirements.txt` (or `pyproject.toml`) does not list `kubernetes` as a dependency.

### What a real `create_namespaced_pod` call requires

The Kubernetes Python client (`kubernetes.client.CoreV1Api().create_namespaced_pod()`) requires a `V1Pod` spec containing at minimum: `metadata.name`, `metadata.namespace`, `spec.containers[0].name`, `spec.containers[0].image`, `spec.containers[0].resources`. The module already computes all of these values: `k8s_pod_name`, `namespace`, `image` (from `IMAGE_ALLOWLIST`), `cpu_millicores`, `memory_mb`. Kubeconfig or in-cluster service-account credentials are loaded via `kubernetes.config.load_incluster_config()` (when running inside the cluster) or `kubernetes.config.load_kube_config()` (for external access with a kubeconfig file).

### Background TTL checker also affected

`check_expired_pods()` at line 289 calls `terminate_pod()` for expired pods. Because `terminate_pod()` does not call the real K8s API, the background TTL checker also fails to actually delete expired pods in production — the same split-brain problem documented for EC2's `check_idle_instances()`.

## 3. Impact / Exploit / Blast Radius

### Availability

Every user who attempts to launch a container pod in production receives HTTP 500. Every attempt to fetch pod logs in production also 500s. These are the two primary interactive operations of the INFRA-004 feature.

### Resource and cost leak

Pods whose DDB records are marked "terminated" continue running on the Kubernetes cluster, consuming CPU and memory allocations. If the cluster uses node auto-scaling, accumulated zombie pods can trigger node scale-up events, increasing cloud cost. The background TTL checker calls `terminate_pod()` every 5 minutes, which updates DDB but never calls `delete_namespaced_pod` — so even pods past their TTL accumulate indefinitely.

### Security surface

A pod running beyond its TTL retains any open ports (including SSH port 22 from the `ubuntu-ssh` image). If the user injected an SSH public key via the `env_vars` mechanism or startup config, the pod remains accessible at its cluster IP even after the user believes it is terminated. The cluster ingress/service configuration may also expose the pod port externally depending on the cluster's network policy.

### Blast radius

All production K8s compute traffic. Same scope as GAP-0222 for EC2. In dev mode the bug is entirely masked. The terminate silent-noop compounds the launch crash: even if the launch crash is the only initially visible symptom, any pods that did reach "running" state (e.g., via direct DDB injection for testing) would accumulate as zombie pods if terminated through the platform.

## 4. Fix Design (code-level)

### Step 1 — add `kubernetes` to project dependencies

`requirements.txt` (or `pyproject.toml` `[project.dependencies]`):

```
kubernetes>=28.1.0
```

This is the official CNCF-maintained Python client for Kubernetes. It is actively maintained, available on PyPI, and version-compatible with K8s clusters 1.24+.

### Step 2 — implement `_get_k8s_core_v1()` in `k8s_launcher.py`

Add a lazy-initialised helper that loads credentials from the environment:

```python
def _get_k8s_core_v1():
    """Return a CoreV1Api client. Loads in-cluster config if KUBERNETES_SERVICE_HOST
    is set (running inside a pod); otherwise falls back to kubeconfig."""
    try:
        from kubernetes import client as k8s_client, config as k8s_config
    except ImportError:
        raise RuntimeError(
            "kubernetes package not installed. "
            "Run: pip install kubernetes>=28.1.0"
        )
    import os
    if os.environ.get("KUBERNETES_SERVICE_HOST"):
        k8s_config.load_incluster_config()
    else:
        kubeconfig = os.environ.get("KUBECONFIG", "")
        k8s_config.load_kube_config(config_file=kubeconfig or None)
    return k8s_client.CoreV1Api()
```

### Step 3 — implement `_real_k8s_launch()`

Add the real launch helper above `launch_pod`:

```python
def _real_k8s_launch(
    *,
    pod_name: str,
    namespace: str,
    image: str,
    cpu_millicores: int,
    memory_mb: int,
    env_vars: dict,
    ssh_pub_key: str | None,
) -> Dict[str, Any]:
    from kubernetes import client as k8s_client
    core_v1 = _get_k8s_core_v1()

    env_list = [
        k8s_client.V1EnvVar(name=k, value=str(v))
        for k, v in (env_vars or {}).items()
    ]
    if ssh_pub_key:
        env_list.append(k8s_client.V1EnvVar(name="SSH_PUBLIC_KEY", value=ssh_pub_key))

    container = k8s_client.V1Container(
        name="workspace",
        image=image,
        env=env_list,
        resources=k8s_client.V1ResourceRequirements(
            requests={
                "cpu": f"{cpu_millicores}m",
                "memory": f"{memory_mb}Mi",
            },
            limits={
                "cpu": f"{cpu_millicores * 2}m",
                "memory": f"{memory_mb * 2}Mi",
            },
        ),
        ports=[k8s_client.V1ContainerPort(container_port=22)],
    )
    pod_spec = k8s_client.V1Pod(
        metadata=k8s_client.V1ObjectMeta(
            name=pod_name,
            namespace=namespace,
            labels={"app": "platform-workspace", "managed-by": "ec2-launcher"},
        ),
        spec=k8s_client.V1PodSpec(
            containers=[container],
            restart_policy="Never",
        ),
    )

    # Ensure namespace exists
    try:
        core_v1.create_namespace(
            k8s_client.V1Namespace(
                metadata=k8s_client.V1ObjectMeta(name=namespace)
            )
        )
    except Exception:
        pass  # Already exists

    pod = core_v1.create_namespaced_pod(namespace=namespace, body=pod_spec)

    return {
        "pod_name": pod.metadata.name,
        "namespace": pod.metadata.namespace,
        "status": pod.status.phase or "pending",
        "pod_ip": pod.status.pod_ip or "",
        "service_hostname": f"{pod_name}.{namespace}.svc.cluster.local",
    }
```

### Step 5 — implement real log fetch in `get_pod_logs()`

Replace lines 254–257:

```python
if S.k8s_mock_enabled:
    return _mock_store.get_logs(k8s_pod_name, namespace, tail=tail)

# Real K8s logs
core_v1 = _get_k8s_core_v1()
try:
    log_str = core_v1.read_namespaced_pod_log(
        name=k8s_pod_name,
        namespace=namespace,
        tail_lines=tail,
    )
    return log_str.splitlines() if log_str else []
except Exception as exc:
    logger.exception("k8s_log_fetch_failed pod=%s namespace=%s", k8s_pod_name, namespace)
    raise PodNotFound(f"Could not fetch logs for pod {k8s_pod_name}: {exc}") from exc
```

### Step 6 — implement real pod deletion in `terminate_pod()`

Replace lines 268–273:

```python
if S.k8s_mock_enabled:
    _mock_store.delete_pod(k8s_pod_name, namespace)
else:
    core_v1 = _get_k8s_core_v1()
    try:
        from kubernetes import client as k8s_client
        core_v1.delete_namespaced_pod(
            name=k8s_pod_name,
            namespace=namespace,
            body=k8s_client.V1DeleteOptions(grace_period_seconds=0),
        )
    except Exception:
        # Log but do not block DDB status update
        logger.exception(
            "k8s_pod_delete_failed pod=%s namespace=%s", k8s_pod_name, namespace
        )
```

### Dev/Prod parity (SECOPS-007)

`S.k8s_mock_enabled` provides the flag-selected fork. Mock mode (dev, CI, testing) continues to use `_MockK8sStore`. Production mode uses the real `kubernetes` client. The `_get_k8s_core_v1()` helper auto-detects in-cluster vs out-of-cluster configuration via `KUBERNETES_SERVICE_HOST`, meaning the same code runs correctly whether deployed inside the target cluster or accessing it from an external machine with a kubeconfig. No production-only code paths; no hardcoded cluster addresses.

### Alternatives considered

**Use the Kubernetes HTTP REST API directly (requests / httpx) instead of the Python client.** Rejected: the `kubernetes` client handles TLS cert verification, bearer-token authentication, and API version negotiation automatically. Reimplementing this manually introduces security risk.

**Deploy pods via kubectl subprocess calls.** Rejected: `kubectl` is not guaranteed to be present in the application container, and subprocess calls are harder to test and maintain.

**Fabric8 Java client via subprocess.** Not applicable (Python service).

import pytest
from unittest.mock import MagicMock, patch


@pytest.fixture()

    k8s_launcher.S.k8s_mock_enabled = True

**Before fix:** `test_launch_pod_raises_without_fix` raises `NotImplementedError`; `test_get_pod_logs_raises_without_fix` also raises; `test_terminate_pod_calls_k8s_delete` and `test_ttl_checker_calls_delete_in_prod` both assert that `delete_namespaced_pod` was called, but it never is.

### Manual QA steps

1. Deploy to an environment with access to a real or local-cluster Kubernetes instance (e.g., `kind`, `minikube`, or `k3s`).
2. Set `K8S_MOCK_ENABLED=0` in the backend environment.
3. Issue `POST /ui/k8s/pods` with `image=ubuntu-ssh` and `preset=small`.
4. Confirm the API returns 200 with a `pod_id`.
5. Use `kubectl get pods -n user-<sub-prefix>` to confirm the pod exists in the cluster.
6. Issue `GET /ui/k8s/pods/{pod_id}/logs` and confirm log lines are returned.
7. Issue `DELETE /ui/k8s/pods/{pod_id}` and confirm `kubectl get pods` no longer shows the pod.

### Infrastructure prerequisites

Before deploying to production:
- Ensure the application's Kubernetes service account has RBAC permissions: `create`/`delete`/`get`/`list` on `pods` and `namespaces` in namespaces matching the `user-*` pattern.
- Set `KUBECONFIG` (for external access) or deploy inside the cluster (for in-cluster auth via `KUBERNETES_SERVICE_HOST`).
- Add `kubernetes>=28.1.0` to the container image build.

### Metrics and observability

- Add CloudWatch (or Prometheus) counter on `k8s_pod_launched` log lines to track real launch rate vs mock launch rate.
- Add metric filter on `k8s_pod_delete_failed` to alert on failed pod terminations (which would otherwise result in zombie pods).
- Track DDB records with `status = "terminated"` and a `terminated_at` within the last hour — if any still show running in the K8s API, the cleanup path is broken.

### Rollback

Set `K8S_MOCK_ENABLED=1` to revert to mock mode instantly. The `kubernetes` package is a pure-Python library with no runtime side-effects when mock mode is active.

### Effort and sequencing

Effort: **L** (3–5 days: Kubernetes client integration + RBAC policy design + in-cluster auth setup + integration testing against `kind`/`minikube` + production cluster access review). Sequencing: fix GAP-0225 before deploying GAP-0226 (K8s auto-host-registration) and GAP-0227 (K8s host cleanup on termination), as both depend on pod launch/terminate working correctly in production. Coordinate with cluster operations team for RBAC policy creation before production deployment.
