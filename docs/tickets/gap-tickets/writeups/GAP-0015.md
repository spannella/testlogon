# GAP-0015: `send_bot_message()` Returns a Dict but Never Writes to DynamoDB — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: BOT-001. Investigation: docs/tickets/gap-tickets/investigations/GAP-0015.md.

---

## 1. Summary & Classification

**Plain-English statement**: `send_bot_message()` in `app/services/chat_bot.py` is the single function responsible for delivering a bot-authored message into a conversation. It updates a cosmetic `message_count` counter on the bot record and returns a plain Python dict — but it never writes anything to the `T.messages` (messages) DynamoDB table. Callers receive a dict that looks like a successfully created message, but no message is ever stored, no message appears in the conversation, and no SSE fan-out fires. The entire bot messaging feature is silently non-functional.

## 2. Current-State Investigation (root cause)

### The function

`app/services/chat_bot.py:283–312` — `send_bot_message`:

```python
def send_bot_message(
    *,
    bot_id: str,
    conversation_id: str,
    text: str,
    kind: str = "text",
) -> dict | None:
    bot = get_bot(bot_id=bot_id)
    if not bot or bot["status"] != "active":
        return None

    # Increment message count
    try:
        T.chat_bots.update_item(
            Key={"pk": f"CREATOR#{bot['creator_id']}", "sk": f"BOT#{bot_id}"},
            UpdateExpression="SET message_count = if_not_exists(message_count, :zero) + :one, updated_at = :ua",
            ExpressionAttributeValues={":zero": 0, ":one": 1, ":ua": now_ts()},
        )
    except ClientError:
        pass  # Non-critical

    return {
        "bot_id": bot_id,
        "bot_name": bot["name"],
        "bot_avatar_url": bot.get("avatar_url"),
        "sender_type": "bot",
        "text": text,
        "kind": kind,
    }
```

The function performs exactly one DDB write: incrementing `message_count` on the `T.chat_bots` table. This is metadata on the bot record itself, not a message. The function then returns a dict. There is no `T.messages.put_item`, no call to any messaging service, no SSE publish, and no `conversation` record update (e.g., `last_message_at`).

### Three confirmed callers, all affected

**Caller 1 — `app/routers/chat_bot.py:219`**:
```python
result = send_bot_message(bot_id=bot_id, conversation_id=body.conversation_id, text=body.text)
if not result:
    raise HTTPException(409, "Bot is not active")
return result
```
The endpoint returns the dict to the HTTP caller. The caller receives a 200 with a dict that looks like a message (it has `bot_id`, `text`, `sender_type`) but no message has been written anywhere. The API is a semantic lie.

**Caller 2 — `app/routers/bot_template.py:271–278`**:
```python
msg = send_bot_message(
    bot_id=bot_id,
    conversation_id=body.conversation_id,
    text=result["rendered_text"],
)
if not msg:
    raise HTTPException(409, "Bot is not active")
return {"ok": True, "rendered_text": result["rendered_text"]}
```
The `msg` dict is not used further; only `rendered_text` is returned. The send has no observable effect other than incrementing the counter.

**Caller 3 — `app/services/bot_scheduler.py:277–281`**:
```python
if sched["target_type"] == "conversation" and sched.get("target_id"):
    send_bot_message(
        bot_id=sched["bot_id"],
        conversation_id=sched["target_id"],
        text=rendered["rendered_text"],
    )
    record_impression(bot_id=sched["bot_id"], template_id=sched["template_id"])
```
The return value is completely discarded. The scheduler fires correctly (cron triggers, template renders, impression is recorded) but no message is delivered.

### Circular import constraint

The messages table handle (`tbl_msgs`) and the high-level `send_text_message` function are defined in `app/routers/messaging.py`. A direct import from `chat_bot.py` into `messaging.py` callers, or vice versa, risks a circular import:

- `chat_bot.py` → `messaging.py` (for message write)
- `messaging.py` → `chat_bot.py` (potentially, for bot-related message processing)

The safe pattern used throughout this codebase is to extract shared write logic into `app/services/` rather than importing from a router into a service. The fix must either:
1. Extract a `write_message_to_ddb(item)` helper into `app/services/messaging.py` (or similar), OR
2. Import only the DynamoDB table handle directly (not a function) from `app/core/tables.py` — which is already done throughout services.

Option 2 is simpler: `T.messages` is the DynamoDB table resource; it is accessible from `app/core/tables.py` in any service file without circularity.

## 3. Impact / Exploit / Blast Radius

**Complete feature non-functionality**: The bot messaging system has zero functional output. Every API endpoint that allows sending bot messages — manual send, template send, scheduled send — silently succeeds and delivers nothing.

**Users affected**:
- **Bot creators** who set up automated responses see no messages delivered.
- **Bot recipients** (conversation participants) receive no bot messages.
- **Scheduled message users** see the schedule execute (last_run_at updates, next_run_at advances) but no message appears in the target conversation.

**Deceptive success responses**: `POST /bots/{bot_id}/send` returns HTTP 200 with a payload that looks like a valid message object. There is no error signal. Operators and developers would have to manually inspect DynamoDB to discover that nothing was written.

**Financial implication**: Bot creators paying for platform usage (message volume billing, bot subscription tiers) see their `message_count` counter incremented — implying usage — while no actual messages are delivered. This is an inaccurate usage accounting.

**Security**: No security exploit. The gap is data-loss only.

## 4. Fix Design (code-level)

### Strategy

Write the message item directly to `T.messages` (from `app/core/tables.py`) inside `send_bot_message`. Use the same item schema as `send_text_message` in `messaging.py` so the item is compatible with `_message_out_from_item` (and therefore with the GAP-0014 fix).

Additionally, update the conversation's `last_message_at` and `last_message_id` fields so the conversation list sidebar is kept current.

### Revised `send_bot_message` in `app/services/chat_bot.py`

```python
# app/services/chat_bot.py — revised send_bot_message
from uuid import uuid4
from app.core.tables import T          # already imported
from app.core.time import now_ts       # already imported
from botocore.exceptions import ClientError  # already imported


def send_bot_message(
    *,
    bot_id: str,
    conversation_id: str,
    text: str,
    kind: str = "text",
) -> dict | None:
    """Send a message as a bot. Writes to T.messages and returns the item dict, or None."""
    bot = get_bot(bot_id=bot_id)
    if not bot or bot["status"] != "active":
        return None

    ts = now_ts()
    message_id = "m_" + uuid4().hex
    quick_replies = bot.get("quick_replies") or []

    item = {
        "conversation_id": conversation_id,
        "message_id": message_id,
        "sender_id": f"bot:{bot_id}",
        "sender_type": "bot",
        "bot_id": bot_id,
        "bot_name": bot["name"],
        "bot_avatar_url": bot.get("avatar_url"),
        "text": text,
        "kind": kind,
        "created_at": ts,
        "status": "active",
        "is_encrypted": False,
        "view_once": False,
        "tip_amount_cents": 0,
    }
    if quick_replies:
        item["quick_replies"] = quick_replies

    # Write message to the messages table
    T.messages.put_item(Item=item)

    # Update conversation metadata (last_message_at, last_message_id)
    try:
        T.conversations.update_item(
            Key={"conversation_id": conversation_id, "participant_id": f"bot:{bot_id}"},
            UpdateExpression=(
                "SET last_message_at = :lma, last_message_id = :lmi, "
                "updated_at = :ua"
            ),
            ExpressionAttributeValues={
                ":lma": ts,
                ":lmi": message_id,
                ":ua": ts,
            },
        )
    except ClientError:
        pass  # Non-critical; conversation metadata is best-effort

    # Increment message count on bot record (existing logic, preserved)
    try:
        T.chat_bots.update_item(
            Key={"pk": f"CREATOR#{bot['creator_id']}", "sk": f"BOT#{bot_id}"},
            UpdateExpression=(
                "SET message_count = if_not_exists(message_count, :zero) + :one, "
                "updated_at = :ua"
            ),
            ExpressionAttributeValues={":zero": 0, ":one": 1, ":ua": ts},
        )
    except ClientError:
        pass

    return item
```

### SSE fan-out (follow-on)

The messaging pipeline in `messaging.py` calls `_publish_message_event(...)` after writing a message to trigger real-time SSE delivery to conversation participants. `send_bot_message` in the service layer does not have direct access to the SSE publisher (which runs in the router layer). Two options:

1. **For the initial fix**: Accept that bot messages appear only on the next page refresh/poll (React Query refetches on focus and network reconnect). This is consistent with the current gap — any improvement over zero messages is acceptable.
2. **For a complete fix**: Extract `_publish_message_event` into a shared service in `app/services/messaging_events.py` and call it from `send_bot_message`. This is the recommended follow-on.

The initial fix (option 1) is sufficient to unblock all three callers.

### Dev/Prod parity (SECOPS-007)

- `T.messages.put_item` uses the standard boto3 path via `app/core/tables.py`. This is identical in dev (DynamoDB Local, port 8001) and production (AWS DynamoDB). No parity risk.
- `T.conversations.update_item` — same.
- The `message_id` generation (`"m_" + uuid4().hex`) matches the pattern used by `send_text_message` in `messaging.py`, ensuring schema consistency.
- No mock path, no feature flag, no environment-specific branching. The fix is the same code path in all environments.

### Backward compatibility

- Callers currently receive a plain dict from `send_bot_message`. The revised function returns the full DDB item dict — a superset of the current return value. All existing callers either return the value directly (caller 1, returns a superset), ignore it (caller 3), or use a specific field (`rendered_text` in caller 2 — note: `rendered_text` is not in `send_bot_message`'s return value; caller 2 uses the template renderer's output, not `send_bot_message`'s return). No caller is broken.
- The `bot_scheduler.py` caller discards the return value entirely; the side effect (message written to DDB) is the only behavioral change.
- No DynamoDB table schema changes required. `T.messages` uses the same key schema (`conversation_id` PK, `message_id` SK) as all other message types.

### Alternatives considered

- **Call `send_text_message` from `messaging.py`**: Reuse the full text-message pipeline. Rejected due to circular import risk (`chat_bot.py` imports from a router). The extraction into a shared `app/services/messaging_events.py` module is the correct long-term design but is a larger refactor.
- **HTTP client self-call**: Have `send_bot_message` call the platform's own `POST /messaging/conversations/{id}/messages` endpoint. Rejected — introduces HTTP overhead, authentication complexity (bot needs a service token), and coupling to the server's own network stack.
- **Stub test flag**: Add a dev-mode flag that skips the DDB write. Rejected — SECOPS-007 requires the same code path in dev and prod.

### Observability

- `T.messages.put_item` is the canonical write path already monitored by backend metrics.
- Add a structured log at `INFO` level: `logger.info("Bot message %s written to conversation %s (bot: %s)", message_id, conversation_id, bot_id)`.
- Monitor `message_count` on bot records in production as a sanity proxy — if `message_count` increments without a corresponding message appearing in the conversation, the fix has not yet been deployed.

### Rollout

- Deploy GAP-0014 and GAP-0015 fixes together in the same release. GAP-0014 alone has no visible effect; GAP-0015 alone causes bot message data to be written but with missing fields in the API response. Both fixes are required for the feature to be functionally complete.
- The `send_bot_message` change is backward-compatible: callers that relied on the dict-only return will now receive a richer dict (with `message_id`, `created_at`, etc.) which is a superset of the previous return value.

### Rollback

Reverting the fix restores the previous no-op behavior. Any bot message items already written to `T.messages` (post-deploy) will remain in DynamoDB — they will appear in conversation message lists. A rollback does not delete these items; they are valid messages and should not be deleted.

### Risks

- **Conversation key schema**: The `T.conversations.update_item` call uses `participant_id: f"bot:{bot_id}"` as the sort key. If the bot is not a participant in the conversation (its record does not exist in `T.conversations`), the update may create a ghost participant entry. Mitigation: check participant existence before updating, or use `ConditionExpression="attribute_exists(conversation_id)"` on the update. The `except ClientError: pass` guard prevents a non-existent key from failing the message write.
- **SSE fan-out absence**: Real-time delivery is not implemented in the initial fix. Conversation participants must reload or navigate away and back to see bot messages. This is a known limitation and should be documented in the release notes.

**Effort**: M — approximately 2–4 hours: ~30 lines of code in `send_bot_message`, plus test suite (~3–4 hours including fixture setup).
