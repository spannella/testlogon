# GAP-0304: Claimant rate-limit not enforced — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`.

## 1. Summary & Classification

**Severity**: HIGH · **Source ticket**: MOD-002 · **Status**: Open · **Effort**: S  
**Owning area**: Backend — DMCA claims service (`app/services/dmca_claims.py`)

The `file_dmca_claim()` function at `app/services/dmca_claims.py:79` creates a new DMCA claim record for every authenticated request without any per-claimant rate limit. The ticket design (MOD-002) specified a check against the `ByClaimantCreatedAt` GSI to enforce a maximum number of claims per claimant email within a 24-hour window and to return HTTP 429 if the limit is exceeded. That check is entirely absent from the implementation.

**Claim verification**: Confirmed accurate. `file_dmca_claim()` calls `T.dmca_claims.put_item()` at line 134 after building the claim record. Between the function entry at line 79 and the `put_item` at line 134 there is no call to `list_claims_by_claimant()` (which exists at line 436 and uses the `ByClaimantCreatedAt` GSI), nor any equivalent GSI query, nor any 429 response. The `ByClaimantCreatedAt` GSI is defined in `scripts/local-ddb-init.py:626` and the `list_claims_by_claimant()` function is fully implemented but is only used by listing endpoints — never by the creation path.

**Impact**: Any authenticated user can file an unlimited number of DMCA claims in rapid succession. Each claim immediately hides the target content via `hide_content_for_dmca()` and increments the target user's strike counter. A single actor can suppress an entire creator's video library and trigger the repeat-infringer ban in a matter of seconds. This is both an abuse vector (targeted harassment / coordinated takedown attacks) and a financial risk (every claim triggers an alert, a moderation audit event, and potential ban enforcement).

**Related tickets**: MOD-002 (DMCA claims), GAP-0303 (content_url SSRF), GAP-0027 (waiting period timer not wired).

## 2. Current-State Investigation (root cause)

### 2.1 `file_dmca_claim()` — no rate-limit gate

The function signature shows it receives `claimant_user_id` (the authenticated user's sub) and the raw input dict (which includes `claimant_email`). Both the user sub and the claimant email are available for a rate-limit check, but neither is checked.

### 2.2 The GSI and listing function that should be called

`app/services/dmca_claims.py:436–455` — `list_claims_by_claimant()`:

```python
def list_claims_by_claimant(
    claimant_email: str,
    limit: int = 20,
    cursor: Optional[str] = None,
) -> Dict[str, Any]:
    kwargs: Dict[str, Any] = {
        "IndexName": "ByClaimantCreatedAt",
        "KeyConditionExpression": Key("claimant_email").eq(claimant_email),
        "ScanIndexForward": False,
        "Limit": min(limit, 100),
    }
    ...
    resp = T.dmca_claims.query(**kwargs)
    items = [_claim_out(i) for i in resp.get("Items", [])]
```

The GSI is keyed on `claimant_email` with a `created_at` sort key (numeric, `attr_types={"created_at": "N"}` at `scripts/local-ddb-init.py:629`). A 24-hour lookback query is therefore straightforward: add a `KeyConditionExpression` range condition on `created_at >= (now_ts() - 86400)`.

### 2.3 No settings variable for the limit

`app/core/settings.py` has no `dmca_max_claims_per_day` or equivalent variable. The limit must be added so it can be tuned without a code change.

### 2.4 Why the gap occurred

The `list_claims_by_claimant()` function was written as part of the listing/admin inspection API (so admins can review all claims from a given email). The rate-limit check that would call it on the creation path was mentioned in the MOD-002 design but was not translated into a pre-creation guard in `file_dmca_claim()`. The function exists; the call site does not.

### 2.5 Impact on `claimant_user_id` vs `claimant_email`

The rate limit should be keyed on **both** the authenticated user sub (`claimant_user_id`) and the `claimant_email` from the request body. Keying only on email allows a bad actor to rotate email addresses while using the same account. Keying only on user sub misses cases where a user provides multiple email addresses. The GSI is indexed on `claimant_email`; a secondary check on `claimant_user_id` can be done via the `ByClaimantCreatedAt` equivalent on user sub, or via a filter on the same GSI results. The simplest effective fix is to:

1. Key the primary rate check on `claimant_user_id` (authenticated identity — cannot be spoofed).
2. Store `claimant_user_id` on the DDB item (already done — line 120: `"claimant_user_id": claimant_user_id`).
3. Query the existing GSI by `claimant_email` AND add a filter on `claimant_user_id` for belt-and-suspenders, or add a separate GSI on `claimant_user_id`.

The minimal fix — checking `claimant_email` only — already closes most of the gap since `claimant_email` is a required field validated by the Pydantic model.

## 3. Impact / Exploit / Blast Radius

### 3.1 Abuse scenario — targeted creator harassment

An adversary with a valid account:

1. Finds a creator's video (e.g., `content_url: /videos/vid_abc123`).
2. Files 3+ DMCA claims in rapid succession, each with the same `content_url` but different `original_work_description` values (no duplicate detection in `file_dmca_claim`).
3. After the 3rd claim (default `dmca_strike_threshold = 3`), `apply_ban()` is called automatically: the creator's account is banned (`T.account_state` `status="banned"`) and an alert is sent.
4. All of the creator's matching content is hidden via `hide_content_for_dmca()`.

Total time: under 10 seconds with a simple loop script. The adversary does not need any special role — any authenticated user can file claims.

### 3.2 Financial and operational impact

Each claim creates a DynamoDB item, fires a `write_alert()` call, and writes a `write_moderation_audit_event()` entry. A flood of 1,000 claims would:
- Create 1,000 DDB items (storage cost).
- Generate 1,000 alert notifications for the target creator.
- Generate 1,000 audit log entries.
- Cause the moderation queue to be flooded, burying legitimate claims.

### 3.3 Data integrity

If the same `content_url` is claimed multiple times, `resolve_content_from_url()` resolves to the same `(content_type, content_id)`. `hide_content_for_dmca()` is idempotent for the content hide (it just overwrites DynamoDB fields), but the strike counter is incremented on every claim:

```python
# dmca_claims.py:149
strike_number = count_strikes(target_user_id) + 1 if target_user_id else 1
```

Multiple claims increment the counter, bypassing the strike threshold check with artificial strikes.

## 4. Fix Design (code-level)

### 4.1 New setting: `app/core/settings.py`

Add after the existing DMCA settings (line 1479):

```python
dmca_max_claims_per_claimant_per_day: int = int(
    os.environ.get("DMCA_MAX_CLAIMS_PER_CLAIMANT_PER_DAY", "10")
)
```

Default of 10 claims per day per claimant email is generous enough for legitimate bulk takedowns while blocking trivial abuse.

### 4.2 New helper: `_check_claimant_rate_limit()` in `app/services/dmca_claims.py`

Add before `file_dmca_claim()`:

```python
from fastapi import HTTPException

def _check_claimant_rate_limit(claimant_email: str, claimant_user_id: str) -> None:
    """Enforce per-claimant daily rate limit.

    Queries ByClaimantCreatedAt GSI for claims filed in the last 24 hours.
    Raises HTTP 429 if the claimant has reached the configured limit.

    Note: keyed on claimant_email (GSI PK). For belt-and-suspenders, also
    checks claimant_user_id via a filter expression.
    """
    cutoff = now_ts() - 86400  # 24 hours ago
    limit = S.dmca_max_claims_per_claimant_per_day

    kwargs: Dict[str, Any] = {
        "IndexName": "ByClaimantCreatedAt",
        "KeyConditionExpression": (
            Key("claimant_email").eq(claimant_email)
            & Key("created_at").gte(cutoff)
        ),
        "Limit": limit + 1,  # fetch one extra to detect overage
        "ScanIndexForward": False,
    }

    resp = T.dmca_claims.query(**kwargs)
    items = resp.get("Items", [])

    # Count claims by this specific user_id (in case email was reused
    # by different user_ids — unusual but possible in dev/test environments)
    count = sum(
        1 for it in items
        if str(it.get("claimant_user_id") or "") == claimant_user_id
        or str(it.get("claimant_email") or "") == claimant_email
    )

    if count >= limit:
        logger.warning(
            "DMCA claim rate limit reached: email=%s user=%s count=%d limit=%d",
            claimant_email, claimant_user_id, count, limit,
        )
        raise HTTPException(
            status_code=429,
            detail={
                "code": "dmca_rate_limit_exceeded",
                "message": (
                    f"You have reached the maximum of {limit} DMCA claims "
                    "in a 24-hour period. Please wait before filing more claims."
                ),
            },
            headers={"Retry-After": "86400"},
        )
```

### 4.3 Wire into `file_dmca_claim()`

At line 91 (immediately after `ts = now_ts()` and before constructing the item dict), add:

```python
def file_dmca_claim(inp: Dict[str, Any], claimant_user_id: str) -> Dict[str, Any]:
    ts = now_ts()
    claim_id = f"dmca_{uuid4().hex}"

    # Rate-limit check — must come before any writes
    _check_claimant_rate_limit(
        claimant_email=inp["claimant_email"],
        claimant_user_id=claimant_user_id,
    )

    content_type = inp.get("content_type", "other")
    ...
```

### 4.4 Dev/Prod parity (SECOPS-007)

The rate-limit check runs identically in both dev and production. The `DMCA_MAX_CLAIMS_PER_CLAIMANT_PER_DAY` environment variable defaults to `10`; production deployments may set it lower (e.g., `3`) or higher depending on business requirements. No `if S.dev_mode` branching is used — the same code path runs in both environments, satisfying SECOPS-007. Integration tests that need to exceed the limit can set the env var to a high number or mock `S.dmca_max_claims_per_claimant_per_day` directly.

### 4.5 Idempotency of rate check

The check is a read-only query followed by a conditional raise. If two concurrent requests from the same claimant arrive simultaneously and both pass the check before either `put_item` completes, a race condition could allow `limit + 1` claims. For a 24-hour sliding window with a modest default of 10, this race is tolerable. If stronger enforcement is needed, a DynamoDB conditional write with a count attribute can be used, but that adds complexity disproportionate to the threat.

### 5.4 Observability

The `_check_claimant_rate_limit` function emits a `logger.warning` with the claimant email, user ID, and count when the limit is triggered. This feeds into the application log aggregator. A future enhancement would add a Prometheus counter `dmca_claim_rate_limited_total` and an alert when it spikes (indicating a coordinated takedown campaign).

### 5.5 Rollback

Remove `_check_claimant_rate_limit()` and the call to it from `file_dmca_claim()`. Remove the `dmca_max_claims_per_claimant_per_day` setting (or leave it — unused settings are harmless). No database migration required.
