# GAP-0275: Production Comparison Raises `KycFacialComparisonError("comparison_service_error")` Unconditionally — Remediation Write-up

> Claim status: **CLAIM OK** — confirmed by code inspection. `_production_compare()` at
> `app/services/kyc_facial_comparison.py:230–232` contains a single statement:
> `raise KycFacialComparisonError("comparison_service_error")`. When `S.dev_mode` is `False`
> (any production deployment), the `compare_faces()` function calls `_production_compare`
> unconditionally (line 341), which raises immediately. The router maps this to HTTP 500
> (`_FACE_COMPARISON_ERROR_STATUS["comparison_service_error"] = 500`). No AWS Rekognition or
> alternative provider is wired. This is a hard production blocker for the KYC facial
> comparison feature.

---

## 1. Summary & Classification

**Bug/Gap**: The production facial comparison code path in
`app/services/kyc_facial_comparison.py` raises an unconditional exception. Any deployment with
`DEV_MODE=0` (i.e., every real production environment) will return HTTP 500 on every call to
`POST /v1/kyc/cases/{case_id}/compare-face`. The deterministic mock comparison used in dev is
correctly gated behind `S.dev_mode`, but no real provider — AWS Rekognition, Azure Face API,
or any other — is implemented to handle the production branch.

**Severity**: HIGH — KYC-014. Effort: L. The facial comparison step is a core KYC gate;
without it, no user can complete the facial liveness verification required for tier-2+ KYC
approval. In production with `dev_mode=False`, 100% of comparison attempts fail with HTTP 500.

**Verdict**: Confirmed. The stub is at `app/services/kyc_facial_comparison.py:230–232`:

```python
def _production_compare(selfie_meta: dict[str, Any], id_meta: dict[str, Any]) -> int:
    """Production comparison placeholder (would call AWS Rekognition CompareFaces)."""
    raise KycFacialComparisonError("comparison_service_error")
```

The call site at line 338–341 unconditionally routes to this stub in non-dev mode:

```python
    if S.dev_mode:
        raw_score = _mock_compare(selfie_meta, id_meta)
    else:
        raw_score = _production_compare(selfie_meta, id_meta)  # always raises
```

**Related tickets**: GAP-0271 (mock MRZ expiry), GAP-0272/0273/0274 (KYC event dispatch),
KYC-014, SECOPS-007.

## 2. Current-State Investigation (Root Cause)

### The stub

`app/services/kyc_facial_comparison.py:230–232`:

```python
def _production_compare(selfie_meta: dict[str, Any], id_meta: dict[str, Any]) -> int:
    """Production comparison placeholder (would call AWS Rekognition CompareFaces)."""
    raise KycFacialComparisonError("comparison_service_error")
```

This function never returns an integer; it always raises. The docstring acknowledges it is a
placeholder.

### The call site

`app/services/kyc_facial_comparison.py:338–341`:

```python
    if S.dev_mode:
        raw_score = _mock_compare(selfie_meta, id_meta)
    else:
        raw_score = _production_compare(selfie_meta, id_meta)
```

`S.dev_mode` is `True` when `DEV_MODE=1` in `.env.local` (the default for local development).
In any real deployment, `DEV_MODE` is unset or `0`, so `S.dev_mode = False`, and the `else`
branch executes unconditionally.

### What the mock does (correct reference implementation)

`app/services/kyc_facial_comparison.py:206–227` (`_mock_compare`): derives a deterministic
score from selfie filename keywords or a CRC32 hash of file references. Returns an integer
in `[0, 100]`. The `_decide()` function at line 235 then maps the score to a `(result,
effective_score)` tuple: `>= 70 → pass`, `50-69 → review`, `< 50 → fail`. This is the
contract that `_production_compare` must satisfy: return an integer in `[0, 100]`.

### Relevant settings

`app/core/settings.py:1246–1254`:

```python
kyc_face_comparison_enabled: bool  # default True — feature gate at router level
kyc_face_auto_compare: bool        # default False — auto-trigger on file upload
```

There is no `kyc_face_comparison_rekognition_enabled` or `kyc_face_comparison_mock_enabled`
flag. The only parity switch is `S.dev_mode`.

### Router error handling

`app/routers/kyc_cases.py:1379–1387`:

```python
_FACE_COMPARISON_ERROR_STATUS: dict[str, int] = {
    ...
    "comparison_service_error": 500,
}
```

When `_production_compare` raises `KycFacialComparisonError("comparison_service_error")`,
the router catches it at line 1406 and returns HTTP 500. This is correct HTTP error handling,
but the 500 is always returned in production.

### Attempt count

`compare_faces` increments `attempt_number` (`existing = _get_comparisons(case_id)`,
`attempt_number = len(existing) + 1`) before calling `_production_compare`. Because the
function raises before writing the DDB record, each failed attempt does **not** consume one
of the 3 allowed attempts (`MAX_SELFIE_ATTEMPTS = 3`). However, because the attempt count is
computed by counting stored records, the 500 loop is "free" — a user could spam the endpoint
indefinitely in production without exhausting their retries, all returning 500.

## 3. Impact / Exploit / Blast Radius

**Production availability**: Every call to `POST /v1/kyc/cases/{case_id}/compare-face` returns
HTTP 500 in any environment where `DEV_MODE != 1`. This includes staging, pre-prod, and
production deployments.

**KYC completion gate blocked**: Facial comparison is a required step in the KYC approval
pipeline. Without a successful comparison, users cannot advance their case to the tier-gated
features (higher withdrawal limits, subscription access, etc.). The entire KYC feature is
functionally broken for non-dev deployments.

**Retry exhaustion not enforced**: As noted above, failed attempts do not write to DDB, so
the 3-attempt limit does not protect against spam in production. An attacker or buggy client
can call the endpoint repeatedly, generating 500s but never being locked out.

**Admin override workaround exists**: `admin_override_comparison` at line 395 allows an admin
to manually override the comparison result for a case. This provides a manual escape hatch
but is not scalable and requires admin intervention for every user.

**Data integrity**: No data is corrupted; the DDB record is only written on successful
comparison. The case remains in its prior state.

## 4. Fix Design (Code-Level)

### Full implementation — AWS Rekognition `CompareFaces`

Replace the stub with a real call to `boto3.client("rekognition").compare_faces()`. The
Rekognition API expects S3 object references (bucket + key), which are available from the
case file references already stored on the KYC case.

**File**: `app/services/kyc_facial_comparison.py`

```python
def _production_compare(selfie_meta: dict[str, Any], id_meta: dict[str, Any]) -> int:
    """Production facial comparison via AWS Rekognition CompareFaces.

    Expects both selfie_meta and id_meta to carry 'node_id' values that are
    S3 keys of the form '<bucket>/<key>' or plain '<key>' (bucket resolved
    from S.kyc_documents_bucket).
    """
    import boto3

    bucket = S.kyc_documents_bucket
    if not bucket:
        raise KycFacialComparisonError("comparison_service_error")

    def _s3_ref(meta: dict[str, Any]) -> dict[str, Any]:
        path = str(meta.get("node_id") or "").lstrip("/")
        # If path starts with the bucket name, strip it.
        if path.startswith(bucket + "/"):
            key = path[len(bucket) + 1:]
        else:
            key = path
        return {"S3Object": {"Bucket": bucket, "Name": key}}

    rek = boto3.client("rekognition", region_name=S.aws_region or "us-east-1")
    try:
        resp = rek.compare_faces(
            SourceImage=_s3_ref(selfie_meta),   # selfie = source
            TargetImage=_s3_ref(id_meta),       # id_front = target
            SimilarityThreshold=0.0,            # return all matches; we threshold ourselves
        )
    except rek.exceptions.InvalidParameterException as exc:
        logger.warning("kyc.face.rekognition.invalid_param %s", exc)
        raise KycFacialComparisonError("comparison_service_error") from exc
    except Exception as exc:  # network errors, throttle, etc.
        logger.error("kyc.face.rekognition.error %s", exc)
        raise KycFacialComparisonError("comparison_service_error") from exc

    face_matches = resp.get("FaceMatches") or []
    if not face_matches:
        # No match found at any threshold — score 0.
        return 0
    # Rekognition returns Similarity as a float 0–100.
    best_similarity = max(float(m.get("Similarity") or 0.0) for m in face_matches)
    return max(0, min(100, int(round(best_similarity))))
```

### Feature flag approach (SECOPS-007 compliant intermediate)

Before full Rekognition integration is available (e.g., during testing or in environments
where IAM permissions are not yet granted), introduce a `KYC_FACE_USE_MOCK_IN_PROD` flag
as a safety valve instead of a hard raise:

**File**: `app/core/settings.py` (add one line in the KYC Facial Comparison section):

```python
# When True, uses the mock comparison even in non-dev mode (for staging environments
# where Rekognition is not yet provisioned). MUST be False in production.
kyc_face_comparison_use_mock: bool = os.environ.get(
    "KYC_FACE_COMPARISON_USE_MOCK", "false"
).lower() in ("1", "true", "yes", "on")
```

**File**: `app/services/kyc_facial_comparison.py` — replace the `if/else` block:

```python
    if S.dev_mode or S.kyc_face_comparison_use_mock:
        raw_score = _mock_compare(selfie_meta, id_meta)
    else:
        raw_score = _production_compare(selfie_meta, id_meta)
```

This allows staging environments to set `KYC_FACE_COMPARISON_USE_MOCK=true` and operate
end-to-end, while production keeps the flag `false` and uses the real Rekognition path.

### IAM permissions required

The backend's IAM role (or the local AWS credentials `AWS_ACCESS_KEY_ID=test` in dev against
moto) must have:

```json
{
  "Effect": "Allow",
  "Action": ["rekognition:CompareFaces"],
  "Resource": "*"
}
```

S3 images referenced by the KYC case must be accessible from the same account as Rekognition.
If images are encrypted at rest with a customer-managed KMS key, the IAM role must also have
`kms:Decrypt` on the relevant key.

### Dev/Prod Parity (SECOPS-007)

| Environment | `S.dev_mode` | `S.kyc_face_comparison_use_mock` | Path taken |
|---|---|---|---|
| Local dev / E2E | `True` | any | `_mock_compare` |
| Staging (pre-Rekognition) | `False` | `True` | `_mock_compare` (safe fallback) |
| Staging (Rekognition ready) | `False` | `False` | `_production_compare` (real) |
| Production | `False` | `False` | `_production_compare` (real) |

The mock and production paths share the same `_decide()` scoring logic and the same DDB write
path. The only difference is how `raw_score` is obtained. This is correct parity: same code
executes post-score in all environments.

### Error codes and HTTP status

The existing `_FACE_COMPARISON_ERROR_STATUS["comparison_service_error"] = 500` mapping is
correct for Rekognition unavailability. The client-facing API contract does not change.

### Rollout

- **Effort**: L — requires Rekognition integration, IAM provisioning, staging validation,
  and potentially updating the KYC file storage architecture (files must be in S3 with the
  correct bucket/key format for Rekognition).
- **Risk**: Medium. Rekognition has variable accuracy across demographics; the threshold
  values (`THRESHOLD_AUTO_PASS = 70`, `THRESHOLD_AUTO_FAIL = 50`) must be validated against
  a representative test dataset before go-live. Consider A/B testing against the mock scores.
- **Migration**: No DDB changes. Existing comparison attempt records are unaffected.
- **Intermediate state**: Deploy `KYC_FACE_COMPARISON_USE_MOCK=true` on staging immediately
  so the full pipeline is testable. Set `KYC_FACE_COMPARISON_ENABLED=false` in production
  until the Rekognition implementation passes staging validation, preventing the 500-on-every-
  call regression from affecting production users.
- **Sequencing**: This is the longest-effort KYC gap. Should be tracked separately from the
  event-dispatch gaps (GAP-0272/0273/0274) which are trivial by comparison. Recommended
  sequencing: (1) add feature flag safety valve (S), (2) implement and test Rekognition call
  in staging (M), (3) production rollout with gradual traffic ramp (M).
