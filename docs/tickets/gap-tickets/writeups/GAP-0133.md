# GAP-0133: No post-send trigger hook in `send_text_message()` — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`. Build on the
> investigation doc (docs/tickets/gap-tickets/investigations/GAP-0133.md) if it exists.

## 1. Summary & Classification

**Bug statement**: After a text message is persisted to DynamoDB and its SSE fan-out is dispatched,
`send_text_message()` returns without invoking bot trigger evaluation. Bot auto-reply logic
(`evaluate_triggers()`, `get_bots_for_conversation()`) exists in `app/services/chat_bot.py` but is
never called from the message send path. All bots configured with keyword, mention, or
all-messages triggers are effectively inert for every real-time conversation message.

**Claim accuracy**: Confirmed. A full-text search of `app/routers/messaging.py` finds zero
references to `evaluate_triggers`, `get_bots_for_conversation`, `_run_bot_trigger`, or
`chat_bot` anywhere in the file. The suggested fix location (line ~8053) is accurate — the message
is written at `tbl_msgs.put_item()` at line 7996 and the natural injection point is after the
fan-out block at lines 8042–8053, before the audit event at line 8055.

- **Severity**: HIGH — bots are entirely non-functional for live messages
- **Source ticket**: BOT-001
- **Status**: Open
- **Owning area**: Messaging / Bot subsystem
- **Related tickets**: BOT-001, GAP-0134 (wildcard scope resolution also broken), SECOPS-007

## 2. Current-State Investigation (root cause)

### End of `send_text_message()` — the missing hook

`app/routers/messaging.py:7996–8079` shows the full post-write sequence:

```python
# 7996: message written to DynamoDB
tbl_msgs.put_item(Item=item)
_sync_gallery_index_message(item)

# 7999-8011: conversation preview / search index update
preview_text = "[Encrypted message]" if is_encrypted else message_text[:140]
_send_single_destination_message(...)

# 8013-8040: build MessageOut response object

# 8039-8040: apply receipts (non-scheduled only)
if not is_scheduled:
    message = _apply_message_receipts(message, item, participants)

# 8042-8053: SSE fan-out (non-scheduled only)
if not is_scheduled:
    _fanout_new_message_event(...)

# 8055-8068: audit event
audit_event("messaging_message_sent", ...)

# 8069-8077: lifecycle archive event
_emit_message_lifecycle_archive_event_or_503(...)

# 8078: quota metering
_meter_message_send(...)

# 8079: return
return message
```

There is no call to `get_bots_for_conversation()` or `evaluate_triggers()` anywhere in this
function or in any helper it calls. The bot infrastructure — trigger config, assignment table
queries, template rendering — exists entirely in `app/services/chat_bot.py` but is orphaned.

### The bot infrastructure (what exists but is never called)

**`app/services/chat_bot.py:251–263`** — `get_bots_for_conversation()`:
Queries `T.bot_assignments` GSI by `CONV#{conversation_id}`. Returns active bot dicts.

**`app/services/chat_bot.py:319–352`** — `evaluate_triggers()`:
Walks `bot["trigger_config"]["triggers"]` and returns a `template_id` if any trigger matches.
Supports `all_messages`, `keyword`, `mention`, and `first_message` trigger types.

**`app/services/chat_bot.py:283–312`** — `send_bot_message()`:
Constructs a bot message dict and increments `message_count` in DDB, but notably returns a dict
rather than writing to the messages table — another gap (GAP-0015 equivalent for this service) that
would need to be addressed alongside this fix.

### `evaluate_triggers()` is callable but unreachable from message flow

`chat_bot.py:319–352` contains working trigger evaluation logic. The function correctly handles
`all_messages`, `keyword`, `mention`, and `first_message` event types, iterates triggers in
priority order, and returns the `response_template_id` of the first matching rule. None of this
code has a defect — it simply is never invoked. The same applies to `get_bots_for_conversation()`
(line 251): a correct DynamoDB query function that is never called outside of tests.

The gap is purely a missing wiring call at the end of `send_text_message()`. The entire bot
trigger infrastructure was written to be called but the integration step was omitted.

### Why the hook is missing

BOT-001 implemented the bot infrastructure (DDB tables, CRUD endpoints, trigger config, assignment,
trigger evaluation, template rendering) but did not wire the message-receive event into the send
path. The gap is a missing integration call, not a logic error in the existing code. The author
comment at the top of `chat_bot.py` references the BOT-001 spec but the equivalent
"call from messaging" integration task appears to have been deferred and subsequently overlooked.

### Scheduled messages

The `is_scheduled` flag path returns early from fan-out. Bot triggers should also be deferred for
scheduled messages — they should fire at delivery time, not at send-queue time. The fix must guard
on `if not is_scheduled:` before calling the bot hook, consistent with how SSE fan-out is guarded.

## 3. Impact / Exploit / Blast Radius

### Functional impact

- Any creator who configures a bot for auto-reply, keyword response, or welcome messages receives
  zero response. Bots appear to be set up correctly in the admin UI but never respond.
- Creators who have paid for or promoted bot features receive no value.
- The `message_count` field on bots is never incremented for real traffic (only when
  `send_bot_message()` is explicitly called by a future caller, which currently doesn't exist).

### Security / financial impact

None directly. Bots are additive functionality; their absence does not expose data or enable
unauthorized access.

### Blast radius

All conversations where at least one active bot with a trigger config is assigned are affected.
Given that `get_bots_for_conversation()` is the primary query path, any conversation without a
direct bot assignment produces zero extra DynamoDB traffic at runtime, so the absence of the hook
has no performance footprint today.

## 4. Fix Design (code-level)

### Approach

Spawn an `asyncio.create_task()` for bot evaluation after the SSE fan-out block. Using a background
task ensures the bot response does not block the HTTP response to the sender. Failures in bot
evaluation must not propagate errors to the message send (fire-and-forget with exception capture).

### Proposed inner helper function (add to `messaging.py`)

```python
async def _run_bot_trigger_evaluation(
    *,
    conversation_id: str,
    message_item: dict,
) -> None:
    """Evaluate bot triggers for a newly delivered message.

    Runs as an asyncio background task after message write + fan-out.
    Failures are logged and swallowed to avoid breaking the send path.
    """
    try:
        from app.services.chat_bot import (
            get_bots_for_conversation,
            evaluate_triggers,
            send_bot_message,
        )
        bots = get_bots_for_conversation(conversation_id=conversation_id)
        for bot in bots:
            template_id = evaluate_triggers(
                bot=bot,
                conversation_id=conversation_id,
                incoming_message=message_item,
                event_type="message",
            )
            if template_id:
                from app.services.bot_template import get_template, render_template
                template = get_template(bot_id=bot["bot_id"], template_id=template_id)
                if template:
                    rendered_text = render_template(template, context={"message": message_item})
                    _bot_result = send_bot_message(
                        bot_id=bot["bot_id"],
                        conversation_id=conversation_id,
                        text=rendered_text,
                    )
                    # TODO: write the bot message to tbl_msgs (GAP-0015 companion)
    except Exception:
        logger.exception(
            "bot_trigger_evaluation_failed conversation_id=%s", conversation_id
        )
```

### Injection point in `send_text_message()` (after line 8053)

```python
    # Existing SSE fan-out block ends here (line 8053)
    # ↓ NEW: spawn bot trigger evaluation for non-scheduled, non-encrypted messages
    if not is_scheduled and not is_encrypted:
        import asyncio
        asyncio.create_task(
            _run_bot_trigger_evaluation(
                conversation_id=conversation_id,
                message_item=item,
            )
        )
```

Encrypted messages are excluded from bot evaluation because bots cannot read ciphertext.

### Dependency on GAP-0134

The inner `get_bots_for_conversation()` call (GAP-0134) only retrieves directly-assigned bots via
`CONV#{conversation_id}` GSI. Wildcard-scoped bots (`SCOPE#ALL_DMS`, `SCOPE#ALL_GROUPS`) are not
found. Fixing GAP-0133 first means wildcard bots remain non-functional until GAP-0134 is also
fixed. The two fixes should be merged together.

### `send_bot_message()` gap (companion to GAP-0015)

The existing `send_bot_message()` in `chat_bot.py` increments the counter and returns a dict, but
does not call `tbl_msgs.put_item()`. The proposed fix above notes a `# TODO` for this. A companion
change must write the bot's reply to DynamoDB and fan it out as an SSE event. This is out of scope
for GAP-0133 strictly (which is about the hook being called) but must be done alongside or the bot
"reply" will be invisible to participants.

### Dev/Prod parity (SECOPS-007)

`get_bots_for_conversation()` queries `T.bot_assignments`, which resolves to DynamoDB Local in dev
and DynamoDB in prod via `app/core/tables.py`. There is no mock or dev-only code path in the bot
service. The `asyncio.create_task()` call works identically in both environments under `uvicorn
--workers 1` (required in dev due to moto's in-process state; bot tables are separate from S3/moto
so this constraint does not apply, but the single-worker requirement is already in place).
