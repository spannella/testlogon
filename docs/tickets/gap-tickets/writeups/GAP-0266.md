# GAP-0266: Submission hook calling `compute_score()` unverified — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: KYC-008. Owning area: KYC risk-scoring pipeline.

## 1. Summary & Classification

**Bug**: The KYC-008 specification requires `KycRiskScoringService.compute_score()` to be called
automatically when a user submits a KYC case (the "submission hook"). The gap audit noted that
"whether the call is stitched at line 830 is not confirmed." Code inspection confirms the hook
is **absent**: neither `submit_kyc_case` (router) nor `submit_case` (service) calls
`compute_score()` after the case transitions to `submitted` status.

**Claim accuracy**: The original ticket's line-number reference (`app/routers/kyc_cases.py:830`)
is inaccurate — at current file length (1710 lines) line 830 falls inside the file-attachment
flow, not `submit_kyc_case`. However, the underlying gap claim is **confirmed correct**: there
is no `compute_score()` call anywhere in the submission pathway.

- **Severity**: HIGH
- **Source ticket**: KYC-008
- **Status**: Open
- **Owning area**: KYC case lifecycle + risk-scoring engine
- **One-line impact**: Every submitted KYC case starts with a stale or absent risk score,
  forcing manual intervention before automated approve/escalate decisions can fire.
- **Related tickets**: GAP-0265 (auto-escalate flag not written), KYC-008 (risk scoring engine),
  KYC-006 (sanctions screening — upstream dependency of `screening_result` factor)

## 2. Current-State Investigation (root cause)

### Submission pathway — code trace

**Router** `app/routers/kyc_cases.py`, `submit_kyc_case` (line 896–971):

```python
updated = STORE.submit_case(
    case_id=case_id,
    owner_sub=user.sub,
    expected_version=body.expected_version,
    evidence_snapshot=evidence_snapshot,
)
# ... audit + metric calls only; no compute_score
return _wrap_case(updated)
```

The function calls `STORE.submit_case(...)`, logs an audit event, emits a metric, and returns.
No risk-score call is present anywhere between lines 941 and 971.

**Service** `app/services/kyc_cases.py`, `submit_case` (line 344–418):

```python
_emit_kyc_event_safe(
    event="kyc.case.submitted",
    user_sub=owner_sub,
    case_id=case_id,
    submitted_at=ts,
)
return self.get_case(case_id)
```

The service fires a webhook event and returns the refreshed case. No `KycRiskScoringService`
import or `compute_score()` call is present.

### Where `compute_score()` IS called today

Searching the entire `app/` tree for `KycRiskScoringService` reveals three call sites:

| File | Line | Trigger |
|---|---|---|
| `app/services/kyc_id_scanner.py` | 603–609 | After ID document scan (`_feed_risk_scoring`) |
| `app/services/kyc_liveness_call.py` | 416–418 | After liveness call completion |
| `app/routers/risk_scoring.py` | 262, 298 | Manual admin trigger via API |

None of these fire at case submission time. The sanctions screening service
(`kyc_sanctions_screening.py`) writes a `screening` summary onto the case META item
(via `_write_case_screening_summary`), but does not call `compute_score()` itself — and,
crucially, the screening call itself is not triggered from the submission flow either. The
`_compute_screening_result` factor (line 368–388 in `kyc_risk_scoring.py`) therefore finds
`case["screening"]` absent and returns the fallback score of 40 ("not_conducted").

### Runtime manifestation

1. User submits a fully-complete KYC case.
2. No risk score is computed; `kyc_risk_scores` table has no row for the user/case.
3. The reviewer queue shows the case without a risk tier or score badge.
4. `_apply_auto_action()` (auto-approve/auto-escalate logic) is never reached.
5. Every case requires manual reviewer assignment regardless of actual risk profile.

In dev mode the gap is invisible unless you explicitly check `GET /v1/kyc/risk-scores/cases/{id}`.
In production the consequence is that KYC-008's automated triage is dead — all submitted cases
land in the manual queue.

## 3. Impact / Exploit / Blast Radius

**Compliance / operational**: The risk-based triage promised by KYC-008 does not function at
all. Low-risk cases that should auto-approve (score ≤ 30, all factors clear) remain in the
manual queue indefinitely. High-risk cases that should auto-escalate (score ≥ 81, tier
"critical") are not flagged. Reviewer workload is inflated by the entire volume of submitted
cases.

**Financial**: Delayed approvals block users from accessing Tier 2+ features (billing,
subscriptions), directly impacting revenue from those feature gates once GAP-0268's gating
is applied.

**Data integrity**: Without a baseline score at submission, `previous_score` / `previous_tier`
comparisons (tracked in the score history for trend analysis) are absent for the first record.
Admin override scores appear to be the "first" score, obscuring the automated baseline.

**Blast radius**: Every KYC case submission since deployment. The gap has no confidentiality
or injection vector — it is a missing call, not a logic error in an existing call.

## 4. Fix Design (code-level)

### Change 1 — Add submission hook in `submit_kyc_case` router

In `app/routers/kyc_cases.py`, after `_wrap_case(updated)` is prepared but before it is
returned, add a best-effort risk-score call:

```python
# KYC-008: trigger risk scoring at submission time.
try:
    from app.services.kyc_risk_scoring import KycRiskScoringService
    KycRiskScoringService().compute_score(
        case_id=case_id,
        user_sub=user.sub,
        trigger="submission",
    )
except Exception:
    logger.warning("kyc.risk.submission_rescore_failed case_id=%s", case_id, exc_info=True)

return _wrap_case(updated)
```

Placement: immediately after line 970 (`_emit_kyc_metric(...)`) and before the `return`.
The `try/except` ensures the risk-score failure never blocks case submission — consistent with
the `_feed_risk_scoring` pattern used in `kyc_id_scanner.py` (line 601–609).

### Change 2 — Ensure sanctions screening fires before compute_score

The `_compute_screening_result` factor reads `case["screening"]["status"]`. If the screening
summary is absent, the factor scores 40 ("not_conducted") instead of reflecting actual risk.
The submission hook should optionally trigger a screening run first:

```python
try:
    from app.services.kyc_sanctions_screening import STORE as _SCREENING
    _SCREENING.screen_case(
        case_id=case_id,
        user_sub=user.sub,
        trigger="submission",
    )
except Exception:
    logger.warning("kyc.screening.submission_failed case_id=%s", case_id, exc_info=True)
```

This call writes the `screening` summary to the case META before `compute_score()` reads it,
ensuring the screening factor is accurate on the first score. If KYC-006 screening has already
run (e.g. from a prior document upload event), `screen_case` appends a new result; idempotency
is acceptable because screening is append-only.

### Dev/Prod parity (SECOPS-007)

Both `KycRiskScoringService` and `KycSanctionsScreeningStore` are already flag-gated for
dev vs. prod:

- `S.kyc_screening_real_provider_enabled` (default `False`) — mock screening used in dev.
- `S.kyc_risk_scoring_model_version` — same code path, different weights possible in prod.

No new feature flags are needed. The added calls follow the same lazy-import, best-effort
`try/except` pattern already established in the codebase, satisfying SECOPS-007's requirement
that dev and prod exercise the same code paths.

### Backward compatibility

Adding a best-effort call to an existing endpoint does not break any existing API contract.
DynamoDB write failures in the risk-score table are swallowed and logged. Existing test cases
that do not seed `kyc_risk_scores` will continue to pass; the new call is additive.

## 5. Testing, Verification & Rollout

### Automated test coverage gap

The current test suite has no test that exercises the end-to-end path from `POST /{case_id}/submit`
through to a DynamoDB row in `kyc_risk_scores`. The only existing risk-scoring tests exercise
`KycRiskScoringService` in isolation. Adding the submission hook test as described below closes
this gap and provides a canary for any future regression where the hook is accidentally removed.

The test should be placed in a new `tests/test_kyc_submission_hook.py` rather than appended to
the existing `kyc_risk_scoring` unit tests, because it crosses two service boundaries (the KYC
case submission pipeline and the risk-scoring engine) and requires mocking both the cases table
and the risk-scores table simultaneously.

### Regression test (pytest offline)

Add to `tests/test_kyc_submission_hook.py`:

```python
def test_compute_score_called_on_submission(
    mocked_kyc_case_table, mocked_risk_scores_table, client, alice_session
):
    """compute_score must be called automatically when a KYC case is submitted."""
    # Arrange: create a KYC case in draft status and attach required evidence
    case_id = seed_draft_case_with_evidence(alice_session)

    # Act: submit the case
    resp = client.post(
        f"/ui/kyc/cases/{case_id}/submit",
        json={"expected_version": 1},
        headers=alice_session,
    )
    assert resp.status_code == 200

    # Assert: a risk score row exists for this case
    scores = mocked_risk_scores_table.query(
        IndexName="case-timestamp-index",
        KeyConditionExpression=Key("case_id").eq(case_id),
    )
    assert len(scores["Items"]) >= 1, (
        "Expected compute_score() to be called on submission but found no risk score row."
    )
    assert scores["Items"][0]["trigger"] == "submission"
```

**Fails before fix**: `scores["Items"]` is empty because `compute_score()` is never called.
**Passes after fix**: The hook fires immediately after `submit_case`, writing a row with
`trigger="submission"`.

### Observability

The existing `kyc.risk.scored` log line (emitted inside `compute_score`) will appear in
uvicorn logs immediately after each submission. Add a Prometheus counter increment in the
`except` branch: `logger.warning("kyc.risk.submission_rescore_failed ...")` ensures failures
surface in log-based alerting.

### Sequencing with other KYC gaps

GAP-0266 (submission hook) should be deployed as part of a coordinated KYC-scoring PR
that also includes:
- GAP-0267 residual fix: `_compute_country_risk` and `_compute_profile_completeness` key
  pattern correction — otherwise the first score will have two factors returning incorrect
  defaults (country always 30, profile completeness always 80).
- GAP-0270: display_name fallback in `_load_crosscheck_profile` — otherwise the
  `cross_reference` scan factor (which `compute_score` reads from the case META) will score
  0 for users without structured names, making the screening result inaccurate.

Deploying the submission hook without the supporting fixes means the first automated risk
scores are computed but inaccurate. This is still better than no scores at all (the current
state), but the fixes should be coupled in a single PR to avoid a period of systematically
biased scoring.

### Observability

After the fix is deployed, the following signals confirm it is working:

1. **Structured log**: `kyc.risk.scored` entries with `trigger=submission` appear in uvicorn
   logs immediately after each `POST /ui/kyc/cases/{id}/submit` request.
2. **API**: `GET /v1/kyc/risk-scores/cases/{case_id}` returns at least one record where
   `trigger="submission"` for every newly-submitted case.
3. **Dashboard**: The KYC-024 analytics funnel should show `risk_scored_count` increasing
   proportionally with `submitted_count` (currently they diverge because scoring never fires
   at submission time).

A missing `trigger=submission` entry for a submitted case indicates the hook failed silently
and the `except` branch logged a `warning`. Set up a log-based alert on
`kyc.risk.submission_rescore_failed` to catch DynamoDB availability issues.

### Rollout

The change is a single additive call wrapped in `try/except`. It can be deployed without a
feature flag. Effort: **S** (< half-day including test). Pair with the GAP-0267 and GAP-0270
fixes in the same PR for a complete first-score accuracy improvement.

### Alternatives considered

**Alternative A: Call `compute_score` inside `submit_case` (service layer)**. Keeping the
hook in the service rather than the router would ensure it fires even if the router is
bypassed (e.g., by internal tooling). However, `submit_case` is called from the
auto-approve path in `_apply_auto_action` as well, which would create a recursive scoring
loop. Placing the hook in the router, after `_wrap_case(updated)` is resolved, avoids this
and mirrors the pattern used by the KYC-016 monitoring schedule hook at the same callsite.

**Alternative B: Event-driven via `kyc.case.submitted` webhook**. `_emit_kyc_event_safe`
fires `kyc.case.submitted` from inside `submit_case`. A webhook consumer could call
`compute_score` asynchronously. This is architecturally cleaner but requires `kyc_webhooks`
to be running as a separate consumer process — not available in dev mode or the current
architecture. Synchronous in-process call is correct for now.

**Alternative C: Schedule as a FastAPI background task**. Using `BackgroundTasks.add_task`
would make the response latency independent of scoring time. However, background tasks are
process-local and not retried on failure; a crash after the response means the score is
silently skipped. The `try/except` synchronous pattern is simpler and more reliable for
a low-frequency endpoint like case submission.

### Risks

- **Performance**: `compute_score()` performs up to 8 DynamoDB `get_item` calls plus one
  `put_item`. On median case submissions this adds ~40–80 ms. Acceptable given KYC submission
  is a rare, deliberate user action (typically once per user per year).
- **Ordering with screening**: If `screen_case` is added first (Change 2), a transient
  screening failure will log a warning but not prevent the score from running with the
  "not_conducted" default for that factor. The design degrades gracefully.
- **First-time score accuracy**: The very first scoring run at submission time uses whatever
  profile and case data is present at that moment. Subsequent scoring (from ID scanner
  and liveness call hooks) will refine the score. This is acceptable; the submission score
  provides an initial risk tier that allows the reviewer queue to prioritize cases.
- **Dependency ordering**: `_compute_screening_result` reads `case["screening"]`. If Change 2
  (screening before scoring) is omitted, the first score has `screening_result.score = 40`
  ("not_conducted") instead of the actual screening result. Recommend shipping both changes
  together to avoid a period of inaccurate first scores.
