# GAP-0355: `emit_social_alert()` Never Called from Social Event Triggers — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual code before writing; all cites are `file:line`.

## 1. Summary & Classification

**Bug statement**: `app/services/social_alerts.py` contains a fully-implemented `emit_social_alert()` function with self-notification suppression, per-type preference checks, alert batching, channel routing, and SSE real-time publish. Despite this, zero callers exist outside the module itself (the only internal call is in `process_mention_alerts` for the `mention` type). As a result, social events — reactions, comments, tips, follows, and subscriptions — never produce an entry in the `alerts` DynamoDB table and the in-app bell badge stays permanently silent for all social activity.

- **Severity**: HIGH
- **Source ticket**: SOC-004
- **Status**: Open — confirmed. `grep -rn "emit_social_alert" app/` returns only `social_alerts.py` itself.
- **Owning area**: Backend / Social Events, Newsfeed Router, Messaging Router, Social Service
- **Investigation verdict**: Confirmed exactly as stated. The gap ticket's description and proposed call sites are accurate.
- **Related tickets**: None with hard dependencies. SECOPS-007 applies to the `alerts` DynamoDB write path (identical in dev and prod via `T.alerts`).

## 2. Current-State Investigation (Root Cause)

### The two alert delivery systems

The codebase has two distinct notification systems for social events. The first is `put_notification()` in `app/routers/newsfeed.py:2419`, which writes items to the `app_single_table` under `GSI3PK=NOTIF#<user_id>` and is consumed by `GET /feed/notifications`. This system predates the social alerts redesign and is newsfeed-specific. The second is `emit_social_alert()` in `app/services/social_alerts.py:167`, which writes to the dedicated `alerts` table (via `write_alert` from `app.services.alerts`), supports batching, per-type preferences, SSE real-time publish to the bell badge, email/push channel routing, and is the intended long-term system for all social notifications. The gap is that SOC-004 built the second system completely but never wired it to the event handlers.

### `emit_social_alert` is fully implemented but has zero external callers

`app/services/social_alerts.py:167–230` contains the complete implementation:

```python
def emit_social_alert(
    *,
    recipient_user_id: str,
    alert_type: str,
    actor_user_id: str,
    actor_display_name: str,
    batch_key: Optional[str] = None,
    title: str,
    details: Dict[str, Any],
    action_url: Optional[str] = None,
) -> Optional[Dict[str, Any]]:
    # 1. Don't notify self
    if recipient_user_id == actor_user_id:
        return None
    # 2. Check per-type preference
    if not _is_alert_type_enabled(recipient_user_id, alert_type):
        return None
    # 3. Batch or write individual alert
    ...
    # 4. SSE real-time publish
    ...
```

Running `grep -rn "emit_social_alert" app/` confirms the only two occurrences are:
- `social_alerts.py:167` — the function definition.
- `social_alerts.py:687` — called from `process_mention_alerts()` (internal, for `@mention` events only).

No import of `emit_social_alert` exists in any router or service file outside this module.

### Each social event only calls `put_notification` (newsfeed-internal GSI3 system)

All five event categories use `put_notification`, which writes to the newsfeed GSI3 notification table — a separate, newsfeed-specific notification system — rather than the `alerts` table backed by `emit_social_alert`.

### The two notification systems are disjoint

| System | Table | Read by | Bell badge? |
|---|---|---|---|
| `put_notification()` in newsfeed.py | `app_single_table` via `GSI3PK=NOTIF#<id>` | `GET /feed/notifications` | Newsfeed-specific |
| `emit_social_alert()` in social_alerts.py | `alerts` table (`T.alerts`) | `GET /ui/alerts` | Global bell badge |

Users never see social alerts in the global alerts inbox (bell icon) because `emit_social_alert` is never called.

## 3. Impact / Exploit / Blast Radius

**User-facing impact**: Every social interaction — someone reacting to your post, commenting, following you, tipping you, or subscribing — produces zero notification in the alerts inbox. The bell badge on the header never increments for social events. This breaks a core social-network feature expectation.

**Revenue impact**: Tip notifications are part of the financial feedback loop. Users who receive message tips and post tips have no visibility that they received money until they manually check their billing history. This reduces the perceived value of the tipping feature.

**Engagement impact**: Follows and new-subscriber alerts are primary re-engagement drivers on social platforms. Silent follows mean creators don't know their audience is growing; silent subscriptions hide revenue events.

**Blast radius**: Every user on the platform. No security or financial risk from the absence of the calls (missing alerts can't be exploited). The risk is entirely product engagement and completeness.

---

## 4. Fix Design (Code-Level)

The fix is to add `emit_social_alert()` calls at the six event sites identified in the gap ticket. Each call is wrapped in a `try/except` so a notification failure cannot break the primary action.

### 4.1 Profile helper

All call sites need `actor_display_name`. Add a shared helper to avoid N DynamoDB reads:

```python
# In a shared location, e.g. app/services/profile_identity.py (already exists as get_profile_identity)
def _display_name(user_sub: str) -> str:
    from app.services.profile import get_profile_identity
    return get_profile_identity(user_sub).get("display_name") or user_sub
```

### 4.2 Reactions — `app/routers/newsfeed.py:4712`

After the `ddb_update_item` call in `add_reaction`, add:

```python
    # Social alert: notify post owner of new reaction
    post_author = post.get("user_id")
    if post_author and post_author != user_id:
        try:
            from app.services.social_alerts import emit_social_alert, BATCH_KEY_PATTERNS
            emit_social_alert(
                recipient_user_id=post_author,
                alert_type="post_reaction",
                actor_user_id=user_id,
                actor_display_name=_display_name(user_id),
                batch_key=BATCH_KEY_PATTERNS["post_reaction"].format(post_id=post_id),
                title=f"{_display_name(user_id)} reacted to your post",
                details={"post_id": post_id, "emoji": req.emoji},
                action_url=f"/feed/posts/{post_id}",
            )
        except Exception:
            logger.warning("reaction alert failed post_id=%s", post_id, exc_info=True)
```

### 4.8 Dev/prod parity (SECOPS-007)

`emit_social_alert` writes to `T.alerts` (configured via `app/core/tables.py`). In dev this is DynamoDB Local (port 8001); in prod it is AWS-managed. The same code path runs in both environments; no `dev_mode` branch is needed. The `try/except` wrapper around every call site ensures that a missing `alerts` table in a test environment does not break the primary action.

### Sequencing and effort

**Effort**: M (as stated in the gap ticket). Six call sites across three files. Each change is 10–15 lines.

**Sequencing**: Can be deployed independently of GAP-0353 and GAP-0354. No migrations; no schema changes. The `alerts` DynamoDB table must exist in all environments before deploying — confirm with `scripts/local-ddb-init.py` that the table is provisioned. In dev the table name is set via `S.alerts_table_name`.

**Rollout**: Low risk. Every call site is wrapped in `try/except`; a failure in `emit_social_alert` cannot break the primary action (reaction/comment/tip/follow/subscription). Roll out incrementally: reactions first (highest volume, most visible), then follows and tips. Monitor the `alerts` table write volume after each rollout stage to catch unexpected spikes.

**Risk**: Batching in `emit_social_alert` is per `batch_key`. If a post receives 100 reactions in quick succession, DynamoDB conditional writes may produce some missed updates under high concurrency. This is an existing design trade-off in the batching logic (`_batch_alert` uses a conditional write with `attribute_exists` check), not introduced by this fix.

**Self-notification suppression**: `emit_social_alert` already suppresses notifications where `recipient_user_id == actor_user_id` (line 190). All six call sites naturally pass the actor's own sub as `actor_user_id`, so users will never receive notifications about their own reactions, follows, or tips without any additional guard needed at the call site.

**Per-type preferences**: `emit_social_alert` checks `_is_alert_type_enabled(recipient_user_id, alert_type)` before writing. The supported `SOCIAL_ALERT_TYPES` list at `social_alerts.py:32–43` includes all six types we are wiring: `new_follower`, `post_liked`, `post_reaction`, `post_comment`, `comment_reply`, `post_tip`, `message_tip`, `subscription_started`. All types are covered without any changes to the preferences schema.

**SSE real-time delivery**: `emit_social_alert` calls `sse_publish_alert` (imported from `app.services.alerts`) after writing the alert item, so the bell badge will update in real-time for users who have an active SSE connection. Users without an active connection will see the alert on next page load via the standard `GET /ui/alerts` poll.
