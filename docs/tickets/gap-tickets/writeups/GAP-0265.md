# GAP-0265: Auto-Escalate Does Not Write Escalation Flag to Case — Remediation Write-up

> ~5 pages. Fix-oriented. Read the real code before writing; cite `file:line`. No investigation
> doc exists for this gap; code verification was performed as part of this write-up.

## 1. Summary & Classification

**Gap**: The `_apply_auto_action` method in `app/services/kyc_risk_scoring.py` logs a
warning and returns `"auto_escalated"` when a case scores in the critical tier, but it
never writes the escalation flag (`review.escalated`, `review.escalation_reason`,
`review.escalated_at`) to the KYC case in DynamoDB. The KYC-008 design spec requires a
`STORE.update_case_links()` call to persist these fields so that admins, monitoring
dashboards, and audit logs can distinguish escalated cases from ordinary submitted ones.

**Verdict**: Confirmed. The critical-tier branch at
`app/services/kyc_risk_scoring.py:564` reads:

```python
if tier == "critical" and score >= S.kyc_risk_auto_escalate_min_score:
    try:
        logger.warning(
            "kyc.risk.auto_escalated case_id=%s score=%s tier=%s",
            case_id, score, tier,
        )
        return "auto_escalated"
    except Exception:
        logger.exception("Auto-escalate failed for case %s", case_id)
    return "none"
```

The `try` block contains only a `logger.warning` call and an immediate `return`. There is
no DDB write. The fields `review.escalated`, `review.escalation_reason`, and
`review.escalated_at` are never set on the case record. The KYC-008 spec (`docs/tickets/
KYC-008-risk-scoring-engine.md`, lines 280–292) explicitly shows a `STORE.update_case_links`
call and an `audit_event` call inside this branch — both are absent.

- **Severity**: HIGH
- **Source ticket**: KYC-008 / GAP-0265
- **Status**: Open
- **Claim accuracy**: **Claim OK** — the gap is exactly as described.
- **Owning area**: KYC / Risk Scoring Engine
- **Impact**: Critical-risk cases are silently logged but not flagged in DynamoDB.
  Admins reviewing the queue see no `escalated` marker. Dashboard queries for escalated
  cases return zero results. Regulatory audit trails show no escalation record. The
  `auto_escalate_rate` metric tracks the count in-memory via scan, but that count is lost
  on restart and is not query-able per-case.
- **Related tickets**: No blocking dependencies. This is a self-contained fix within the
  risk scoring service.

## 2. Current-State Investigation (root cause)

### 2.1 Exact code path

`app/services/kyc_risk_scoring.py`, `_apply_auto_action` method (line 528):

```python
def _apply_auto_action(
    self,
    *,
    case_id: str,
    score: int,
    tier: str,
    all_checks_passed: bool,
) -> str:
    """Apply auto-approve or auto-escalate based on score and tier."""
    if (
        S.kyc_risk_auto_approve_enabled
        and tier == "low"
        and all_checks_passed
        and score <= S.kyc_risk_auto_approve_max_score
    ):
        # Auto-approve                          ← DDB write present (lines 543–560)
        try:
            from app.services.kyc_cases import STORE
            ...
            STORE.apply_admin_decision(...)     # ← write exists
            return "auto_approved"
        except Exception:
            ...
        return "none"

    if tier == "critical" and score >= S.kyc_risk_auto_escalate_min_score:
        # Auto-escalate                         ← NO DDB write
        try:
            logger.warning(
                "kyc.risk.auto_escalated case_id=%s score=%s tier=%s",
                case_id, score, tier,
            )
            return "auto_escalated"              # ← immediate return, no write
        except Exception:
            logger.exception("Auto-escalate failed for case %s", case_id)
        return "none"

    return "none"
```

The auto-approve branch (lines 543–561) correctly fetches the case from DDB and calls
`STORE.apply_admin_decision`. The auto-escalate branch (lines 564–571) contains only a
logging call. The structural asymmetry is clear: the engineer implemented the approve side
but left the escalate side as a stub.

### 2.2 The `update_case_links` method

`app/services/kyc_cases.py:291` — `update_case_links` accepts a `review_ticket_id`
parameter and writes the review sub-map atomically. However, it does not accept
arbitrary `review.*` fields. The escalation flags must be injected into the review map
before calling `update_case_links`, as demonstrated in the approve path which passes
the whole `review` dict through the `signature` / `review_ticket_id` mechanism.

Looking at the method signature more carefully, the current `update_case_links` builds
a `review` dict at line 314:

```python
review = dict(existing.get("review") or _empty_review_ref())
if review_ticket_id is not None:
    review["ticket_id"] = review_ticket_id
```

It then writes `review` in the UpdateExpression. The fix can set `review["escalated"]`,
`review["escalation_reason"]`, and `review["escalated_at"]` before calling the method,
OR it can extend `update_case_links` with dedicated escalation parameters. The preferred
approach (minimal change, no new method signature) is to call a dedicated
`escalate_case()` method that mirrors the pattern used by `apply_admin_decision`.

### 2.3 The `auto_escalate_enabled` setting — absent

The KYC-008 spec (`docs/tickets/KYC-008-risk-scoring-engine.md`, line 1112) shows:

```
KYC_RISK_AUTO_ESCALATE_ENABLED | false | Gates auto-escalate action
```

Searching `app/core/settings.py` for `kyc_risk_auto_escalate_enabled` returns no match.
Only `kyc_risk_auto_escalate_min_score` (line 1199) exists. The auto-approve path
checks `S.kyc_risk_auto_approve_enabled` before acting. The auto-escalate path has no
equivalent feature flag, meaning it would execute unconditionally in prod once the DDB
write is added. The fix must also add `kyc_risk_auto_escalate_enabled` to settings.

### 2.4 `audit_event` call is also absent

The KYC-008 spec (line 290) shows `audit_event("kyc_auto_escalated", ...)` inside the
escalate branch. This call is absent from the current implementation. Without it, there
is no audit trail in the `T.alerts` table for auto-escalation events.

## 3. Impact / Exploit / Blast Radius

### 3.1 Operational / compliance

Every critical-risk case that triggers auto-escalation is logged at WARN level in the
application log but leaves no permanent, query-able record in DynamoDB. An admin
checking the case in the review queue sees no escalation marker. There is no way to
filter the admin queue by `escalated: true`. Compliance reports cannot include a count
of auto-escalated cases. Regulatory audits cannot verify that critical-risk cases
received enhanced scrutiny.

### 3.2 Senior reviewer assignment

The escalation flow is intended to flag cases for ROOT or senior compliance staff. Since
`review.escalated` is never written, there is no mechanism to automatically assign
escalated cases to the senior admin pool or to surface them at the top of the review
queue. Critical-risk cases are indistinguishable from ordinary submitted cases in the queue.

### 3.3 Dashboard and metrics gap

`get_tier_distribution()` (lines 201–241) counts `auto_escalated` by scanning the entire
`kyc_risk_scores` table in memory. This scan-based count is correct in isolation (the
score record stores `auto_action_taken: "auto_escalated"`), but no corresponding field
exists on the case itself. The dashboard can report "X cases were auto-escalated" from
the score history, but cannot link that count back to case queue management.

### 3.4 Security risk

A critical-risk applicant (e.g., flagged on sanctions screening) could be auto-escalated,
but because no DDB flag is written, the case is not differentiated from a standard
submission. If an admin processes it without realising it should have received enhanced
scrutiny (dual-reviewer, senior sign-off), the compliance control fails silently.

## 4. Fix Design (code-level)

### 4.1 Add `kyc_risk_auto_escalate_enabled` to `app/core/settings.py`

Near line 1199 where `kyc_risk_auto_escalate_min_score` is defined:

```python
kyc_risk_auto_escalate_enabled: bool = (
    os.environ.get("KYC_RISK_AUTO_ESCALATE_ENABLED", "true").lower() == "true"
)
kyc_risk_auto_escalate_min_score: int = int(
    os.environ.get("KYC_RISK_AUTO_ESCALATE_MIN_SCORE", "81")
)
```

Default `true` matches the auto-approve default; set `KYC_RISK_AUTO_ESCALATE_ENABLED=false`
in dev `.env.local.example` if the platform is not yet ready for auto-escalation in dev
environments.

### 4.2 Add `escalate_case()` to `app/services/kyc_cases.py`

Mirror the `apply_admin_decision` pattern (lines ~430–500) with a lighter update:

```python
def escalate_case(
    self,
    *,
    case_id: str,
    score: int,
    reason: str,
    actor_sub: str = "system_auto_escalate",
) -> dict[str, Any] | None:
    """Write escalation flag to case review sub-map. Does not change case status."""
    from app.core.time import now_ts

    existing = self.get_case(case_id)
    if not existing:
        return None

    current_status = str(existing.get("status") or "")
    # Only flag submitted/under_review cases; skip approved/rejected
    if current_status not in {"submitted", "under_review", "needs_more_info"}:
        return existing

    ts = now_ts()
    review = dict(existing.get("review") or {})
    review["escalated"] = True
    review["escalation_reason"] = reason
    review["escalated_at"] = ts
    review["escalated_by"] = actor_sub

    try:
        self._table.update_item(
            Key={"pk": _case_pk(case_id), "sk": "META"},
            UpdateExpression=(
                "SET review = :review, updated_at = :updated_at"
            ),
            ExpressionAttributeValues={
                ":review": review,
                ":updated_at": ts,
                ":current_status": current_status,
            },
            ConditionExpression="attribute_exists(pk) AND #status = :current_status",
            ExpressionAttributeNames={"#status": "status"},
        )
    except ClientError as exc:
        if _is_conditional_conflict(exc):
            # Status changed concurrently (e.g., already approved); acceptable
            logger.warning(
                "kyc.escalate_case: condition failed for case %s (status changed?)",
                case_id,
            )
            return self.get_case(case_id)
        raise
    return self.get_case(case_id)
```

Note: the `version` field is intentionally **not** incremented here. The escalation flag
is an administrative annotation, not a user-visible state change. Incrementing version
would invalidate any concurrent user draft operation.

### 4.3 Fix `_apply_auto_action` — `app/services/kyc_risk_scoring.py:564`

```python
if tier == "critical" and score >= S.kyc_risk_auto_escalate_min_score:
    if not S.kyc_risk_auto_escalate_enabled:
        return "none"
    # Auto-escalate: flag for senior review
    try:
        from app.services.kyc_cases import STORE
        escalated = STORE.escalate_case(
            case_id=case_id,
            score=score,
            reason=f"Critical risk score: {score} (tier: critical)",
        )
        if escalated:
            from app.services.alerts import audit_event as _ae
            _ae(
                "kyc_auto_escalated",
                "system_auto_escalate",
                None,
                outcome="success",
                namespace="kyc",
                kyc_case_id=case_id,
                score=score,
                tier=tier,
            )
            logger.warning(
                "kyc.risk.auto_escalated case_id=%s score=%s tier=%s",
                case_id, score, tier,
            )
            return "auto_escalated"
    except Exception:
        logger.exception("Auto-escalate failed for case %s", case_id)
    return "none"
```

The `audit_event` import mirrors the pattern used in the auto-approve branch (line 545:
`from app.services.kyc_cases import STORE`). The `request=None` argument is accepted by
`audit_event` when called from a background/async context.

### 4.4 Dev/Prod parity (SECOPS-007)

- `STORE.escalate_case()` writes to `T.kyc_cases` — the same DynamoDB table used
  throughout the service, backed by DynamoDB Local / moto in dev and real DynamoDB in prod.
  Same code path, no dev-only branch.
- `audit_event` writes to `T.alerts` — same table in both environments.
- The new `KYC_RISK_AUTO_ESCALATE_ENABLED` setting allows the flag to be disabled in dev
  environments where critical-risk test scores would spam escalation records.
