# GAP-0372: Tenant ID Absent from HKDF Key Derivation — Remediation Write-up

> ~5 pages. Fix-oriented. Cites real file:line. No investigation doc exists for this ticket.

## 1. Summary & Classification

**Plain-English statement**: `app/services/vod_drm_keys.py:derive_content_key` derives
an AES-128 HLS encryption key from only two inputs: the global root secret and the
`asset_id`. There is no `tenant_id` component in the HKDF salt or info string. On a
multi-tenant platform, any two tenants who upload videos with the same `asset_id` value
(possible via re-upload, ID collision, or deliberate attack) receive **identical
decryption keys**. A viewer entitled to Tenant A's video can therefore decrypt Tenant B's
stream, breaking content isolation between creators.

- **Severity**: HIGH
- **Source ticket**: VOD-010
- **Status**: Open
- **Owning area**: Backend / DRM / Key Derivation / `app/services/vod_drm_keys.py`
- **Verdict**: **Confirmed** — `app/services/vod_drm_keys.py:57-78` calls
  `derive_content_key(asset_id, key_slot)` with no `tenant_id` parameter. The HKDF info
  string is `"{asset_id}:{key_slot}"` (line 77) with no tenant namespace.
- **One-line impact**: Two tenants with the same `asset_id` receive the same AES-128 key;
  cross-tenant content decryption is possible.
- **Related tickets**: VOD-010 (source), GAP-0373 (companion: tenant validation at serve
  time), GAP-0371 (token refresh; independent but related to the same DRM flow).

## 2. Current-State Investigation (Root Cause)

### Key derivation function

`app/services/vod_drm_keys.py:57-78`:

```python
def derive_content_key(asset_id: str, key_slot: int = 0) -> bytes:
    if not asset_id or not asset_id.strip():
        raise VodDrmKeyError("invalid_asset_id", "asset_id must be non-empty")
    root = _get_root_secret()
    salt = b"vod-drm-content-key-v1"
    info = f"{asset_id.strip()}:{key_slot}".encode("utf-8")
    return _hkdf_sha256(ikm=root, salt=salt, info=info, length=16)
```

The HKDF invocation is:
- **IKM**: root secret (global, shared across all tenants)
- **Salt**: fixed literal `b"vod-drm-content-key-v1"` (static, never changes)
- **Info**: `"{asset_id}:{key_slot}"` — **no tenant namespace**

The key ID function has the same omission (`app/services/vod_drm_keys.py:81-100`):

```python
def derive_key_id(asset_id: str, key_slot: int = 0) -> str:
    ...
    context = f"key-id:{asset_id.strip()}:{key_slot}".encode("utf-8")
    digest = hmac.new(root, context, hashlib.sha256).hexdigest()
    return digest[:32]
```

And the IV derivation (`app/services/vod_drm_keys.py:121-139`):

```python
def derive_iv(asset_id: str, key_slot: int = 0) -> bytes:
    ...
    info = f"{asset_id.strip()}:{key_slot}".encode("utf-8")
    return _hkdf_sha256(ikm=root, salt=salt, info=info, length=16)
```

All three derivation functions share the same structural flaw: they are keyed on
`asset_id` alone.

### How asset IDs are assigned

`app/routers/video_listing.py:_try_issue_playback_token` calls
`issue_playback_entitlement` with `tenant_id=video.owner_user_id`. This means the backend
already knows the correct `tenant_id` at token issue time and already embeds it in the
playback entitlement JWT (`app/services/playback_entitlements.py:238`). The tenant_id
is not, however, threaded through to the key derivation call.

### Asset ID collision surface

`VideoMetadataModel` uses `id` as the asset identifier. Video IDs are generated by the
upload pipeline. If two creators independently upload a video that results in the same
`asset_id` (e.g., the pipeline uses a deterministic ID based on filename, or an attacker
crafts a re-upload that targets a known video ID), both will receive the same AES-128
key. An attacker could:

1. Purchase or subscribe to their own content on Tenant A.
2. Obtain the key for `asset_id=video_123` via the DRM key server.
3. Use that key to decrypt any segment of any tenant's video with the same `asset_id`.

Even without deliberate collision, the probability of accidental collision grows with
platform scale. For a production platform with millions of video assets, NIST recommends
domain-separated derivation inputs exactly to prevent this class of issue.

### Missing `tenant_id` in key URI

`app/services/vod_drm_keys.py:103-118` (`get_key_uri`) builds the `#EXT-X-KEY` URI:

```python
def get_key_uri(asset_id: str, key_slot: int = 0) -> str:
    key_id = derive_key_id(asset_id, key_slot)
    base_url = (S.vod_drm_key_server_base_url or "...").rstrip("/")
    return f"{base_url}/key/{key_id}?asset={asset_id}"
```

No `tenant_id` query parameter is embedded in the URI. This means the key server endpoint
(`GET /v1/vod/drm/key/{key_id}`) never receives the tenant, making per-tenant validation
at serve time structurally impossible without first fixing the derivation.

## 3. Impact / Exploit / Blast Radius

**Affected assets**: Every DRM-enabled video (`drm_enabled=True`). Non-encrypted videos
(clear-text HLS) are not affected since there is no key to derive.

**Concrete exploit (deliberate collision)**:

1. Attacker knows the `asset_id` of a premium video owned by Tenant B (e.g., `v_abc123`).
   Asset IDs may be discoverable via the public `/v1/vod/drm/info/{asset_id}` endpoint,
   which requires no authentication and returns the key URI structure.
2. Attacker creates their own account (Tenant A), uploads a file, and registers it with
   `asset_id=v_abc123` in their own tenant namespace (or observes that the platform
   auto-assigns a matching ID during re-upload).
3. Attacker is entitled to their own video → obtains a valid playback token for
   `asset_id=v_abc123` from the token issuer.
4. Attacker calls `GET /v1/vod/drm/key/{key_id}?asset=v_abc123&token=<their_token>`.
5. Server validates token `asset_id == "v_abc123"` ✓ and returns the AES key.
6. Because the derivation is tenant-agnostic, the returned key is **identical** to the
   key used to encrypt Tenant B's content.
7. Attacker decrypts Tenant B's premium segments offline.

**Confidentiality violation**: Creator revenue depends on content protection. A
successful exploit bypasses the subscription/PPV gating entirely, exposing paid content
with no trace in the billing or entitlement systems.

**Scale**: If asset IDs are sequential or predictable, an attacker who controls one
entitlement can probe and extract keys for any asset on the platform. The DRM layer
provides zero cross-tenant isolation in this case.

## 4. Fix Design (Code-Level)

### Approach: include `tenant_id` in HKDF salt (domain separation)

The standard approach for domain-separated HKDF is to bind the salt to the tenant
context. We use `sha256(f"{tenant_id}|{asset_id}")` as the salt so that identical
`asset_id` values under different tenants produce cryptographically independent keys.

#### Updated `derive_content_key` signature

```python
def derive_content_key(asset_id: str, tenant_id: str, key_slot: int = 0) -> bytes:
    """Derive a 16-byte AES-128 content key, scoped to a specific tenant.

    Salt is sha256("{tenant_id}|{asset_id}") to prevent cross-tenant key reuse.
    """
    if not asset_id or not asset_id.strip():
        raise VodDrmKeyError("invalid_asset_id", "asset_id must be non-empty")
    if not tenant_id or not tenant_id.strip():
        raise VodDrmKeyError("invalid_tenant_id", "tenant_id must be non-empty")

    import hashlib as _hashlib
    root = _get_root_secret()
    salt_input = f"{tenant_id.strip()}|{asset_id.strip()}".encode("utf-8")
    salt = _hashlib.sha256(salt_input).digest()  # 32 bytes
    info = f"{asset_id.strip()}:{key_slot}".encode("utf-8")
    return _hkdf_sha256(ikm=root, salt=salt, info=info, length=16)
```

Apply the same change to `derive_key_id` and `derive_iv` — both must accept and
incorporate `tenant_id` in their salt or info string to maintain isolation.

#### Update `get_key_uri` to embed `tenant_id` in the URI

```python
def get_key_uri(asset_id: str, tenant_id: str, key_slot: int = 0) -> str:
    key_id = derive_key_id(asset_id, tenant_id, key_slot)
    base_url = (S.vod_drm_key_server_base_url or "http://localhost:8000/v1/vod/drm").rstrip("/")
    return f"{base_url}/key/{key_id}?asset={asset_id}&tenant={tenant_id}"
```

The router `app/routers/vod_drm.py:get_decryption_key` must then accept and validate the
`tenant` query parameter (see GAP-0373 for the router-level validation fix, which is a
required companion to this change).

#### Update all call sites

The primary call site is in the HLS manifest assembly path. Search result shows
`derive_content_key(asset)` is called at `app/routers/vod_drm.py:89`. The call site
must obtain the tenant from the validated playback token claim:

```python
# After existing asset_id validation (line 68 in vod_drm.py):
token_tenant_id = (claims.get("tenant_id") or "").strip()
...
content_key = derive_content_key(asset, tenant_id=token_tenant_id)
```

### Key rotation migration

Because changing the salt formula changes all derived keys, this is a **key rotation
event**. All in-flight HLS sessions will need re-keying. The migration plan:
1. Deploy the new derivation alongside a `key_schema_version` flag in settings.
2. On first deploy, re-encrypt (re-segment) all published DRM videos in a background job
   using the new derivation, writing a new `drm_key_schema_version` field on each video
   record.
3. The key server reads `key_schema_version` from the DDB video record and routes to the
   old or new derivation function accordingly for a migration window.
4. After all videos are migrated, remove the version branch and the old derivation.

### Dev/Prod parity (SECOPS-007)

`derive_content_key` is pure Python cryptography — no AWS calls. It runs identically in
dev and prod. The `VOD_DRM_KEY_ROOT` secret should be provisioned via AWS Secrets Manager
in production (consistent with SECOPS-007 rule for secrets at rest); in dev it is read
from `.env.local`. No new dev mock is required.

## 5. Testing, Verification & Rollout

### Regression test — fails before / passes after

**pytest offline** (`tests/test_vod_drm_tenant_isolation.py`):

```python
"""GAP-0372: Cross-tenant key isolation regression test.

BEFORE fix: derive_content_key("asset-x") == derive_content_key("asset-x")
  for any two callers regardless of tenant.
AFTER fix: derive_content_key("asset-x", "tenant-a") !=
  derive_content_key("asset-x", "tenant-b")
"""
import os
os.environ.setdefault("VOD_DRM_KEY_ROOT", "test-root-key-for-gap-0372")
os.environ.setdefault("DEV_MODE", "1")
os.environ.setdefault("UI_ACCESS_TOKEN_SECRET", "test-secret")

def test_same_asset_different_tenant_produces_different_keys():
    from app.services.vod_drm_keys import derive_content_key
    key_a = derive_content_key("asset-shared", tenant_id="tenant-alice")
    key_b = derive_content_key("asset-shared", tenant_id="tenant-bob")
    assert key_a != key_b, (
        "Cross-tenant key collision: same asset_id produces same key "
        "for different tenants (GAP-0372 not fixed)"
    )

def test_same_asset_same_tenant_is_deterministic():
    from app.services.vod_drm_keys import derive_content_key
    k1 = derive_content_key("asset-shared", tenant_id="tenant-alice")
    k2 = derive_content_key("asset-shared", tenant_id="tenant-alice")
    assert k1 == k2, "Key derivation is not deterministic for same tenant+asset"

def test_different_asset_same_tenant_produces_different_keys():
    from app.services.vod_drm_keys import derive_content_key
    k1 = derive_content_key("asset-a", tenant_id="tenant-alice")
    k2 = derive_content_key("asset-b", tenant_id="tenant-alice")
    assert k1 != k2

def test_empty_tenant_id_raises():
    from app.services.vod_drm_keys import VodDrmKeyError, derive_content_key
    import pytest
    with pytest.raises(VodDrmKeyError, match="tenant_id must be non-empty"):
        derive_content_key("asset-x", tenant_id="")
```

**The `test_same_asset_different_tenant_produces_different_keys` test fails on the current
codebase** because the current signature is `derive_content_key(asset_id, key_slot=0)`
with no `tenant_id` parameter, so two calls with different `tenant_id` arguments would
either raise `TypeError` (too many args) or — if the parameter were silently ignored —
return equal keys.

### Metrics / observability

Add a `vod_drm_key_tenant_id_missing_total` counter incremented whenever the key server
is called without a tenant claim in the token (should be 0 post-fix; non-zero indicates
old tokens in circulation).

### Rollout

- **Effort**: M (2 engineer-days including the migration job)
- **Risk**: HIGH at migration point (all DRM videos must be re-keyed). Stage in
  pre-production with a representative video corpus first.
- **Sequencing**: Must be deployed **together with GAP-0373** (tenant validation at
  serve time). Deploying this fix alone changes derived keys but the router still does
  not validate tenant, leaving the `tenant` param unenforced. Both fixes should ship
  in the same PR.
- **Rollback**: Revert to old `derive_content_key(asset_id)` signature and re-run
  migration job to restore old keys. Migration window must be kept open until rollback
  risk passes.
