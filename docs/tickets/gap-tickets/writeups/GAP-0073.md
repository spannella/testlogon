# GAP-0073: LivePlayer.tsx adJoinMutation Triggered by session State Instead of sessionId — Remediation Write-up

## 1. Summary & Classification

**Claim status: Partially confirmed — the code location and dependency array are confirmed; the stated fix direction requires correction.**

The gap ticket states that `adJoinMutation` fires on `[session]` and the fix is to change the dependency to `[sessionId, isAuthenticated]`. Inspection of the actual code at `frontend/src/pages/broadcast/LivePlayer.tsx` lines 138–142 confirms the `[session]` dependency. However, the impact description — "if sessionMutation fails, adJoinMutation never fires" — correctly identifies the coupling problem but the recommended dependency `[sessionId, isAuthenticated]` mirrors what `sessionMutation` already uses (lines 133–136). The correct fix is to make `adJoinMutation` fire on the same trigger as `sessionMutation` (`[sessionId, isAuthenticated]`) but independently, not downstream of `session` state being populated.

- **Severity**: HIGH
- **Source ticket**: ADS-020
- **Owning area**: Frontend / Broadcast
- **Status**: Open
- **Impact**: When `sessionMutation` fails or returns a session shape that the component does not set on `session` state, `adJoinMutation` never fires. Pre-roll overlay never mounts. Advertiser pays for a broadcast slot that delivers zero impressions. E2E tests 369.1/369.2 fail.
- **Related tickets**: GAP-0071 (billing integration), GAP-0072 (billing flag), GAP-0063 (E2E spec absent).


## 2. Current-State Investigation (root cause)

### Actual code

`frontend/src/pages/broadcast/LivePlayer.tsx`, lines 131–147:

```tsx
// ─── Initialize ───────────────────────────────────────────────

useEffect(() => {
  if (!sessionId || !isAuthenticated) return;
  sessionMutation.mutate();
}, [sessionId, isAuthenticated]);

useEffect(() => {
  if (!session || !isAuthenticated) return;
  adJoinMutation.mutate();
  // eslint-disable-next-line react-hooks/exhaustive-deps
}, [session]);

useEffect(() => {
  if (!session || !isAuthenticated) return;
  playbackMutation.mutate();
}, [session]);
```

### Dependency chain analysis

The component's initialization flow is:

```
sessionId + isAuthenticated
       ↓
  sessionMutation.mutate()
       ↓ (on success)
  setSession(data)       ← sets `session` state
       ↓ (React re-render, session becomes non-null)
  adJoinMutation.mutate()   ← fires only because session changed
  playbackMutation.mutate() ← same
```

`adJoinMutation` is chained downstream of `session` state, not downstream of `sessionId`. This introduces three concrete failure modes:

**Failure mode 1**: `sessionMutation` returns an error (session not found, auth failure, network error). `setSession` is never called. `session` remains `null`. `adJoinMutation` never fires. Pre-roll is permanently skipped.

**Failure mode 2**: `sessionMutation` returns but the `onSuccess` callback throws before `setSession` is reached (defensive: unlikely, but the eslint-disable comment on line 141 hints the author was aware of dependency complexity).

**Failure mode 3**: During rapid re-navigation (user navigates away and back), `sessionId` may change while `session` still holds the old value from the previous session. `adJoinMutation` fires against the new `sessionId` but with stale data context.

### Why the claim is partially corrected

The gap ticket's stated fix — change `[session]` to `[sessionId, isAuthenticated]` — is correct in direction but needs clarification: the `adJoinMutation` effect should fire independently of whether `sessionMutation` succeeded, using `sessionId` and `isAuthenticated` as its triggers. The guard `if (!session || !isAuthenticated) return` must change to `if (!sessionId || !isAuthenticated) return`.

The `playbackMutation` effect (lines 144–147) has the same `[session]` dependency and same problem — but is out of scope for this ticket. However, the fix should not inadvertently change it.

### Dev vs. prod behaviour

This is a frontend timing bug. It reproduces identically in dev (Vite) and production (built bundle). The only difference is that in dev, the sessionMutation failure is more visible via browser dev tools. In production, the failure is silent — the pre-roll simply does not appear.


## 3. Impact / Exploit / Blast Radius

### Pre-roll never mounts on playback error

The most common trigger: a viewer opens a broadcast link before the host starts the session. `sessionMutation` fails with 404. `session` is never set. `adJoinMutation` never fires. The pre-roll creative is never fetched. When the host eventually starts the session and the viewer refreshes, this depends on whether `sessionId` or `isAuthenticated` changes — if they don't (same URL, same auth), neither effect re-fires and `adJoinMutation` still does not run.

### Revenue impact

If the pre-roll does not fire, no impression event is sent to `POST .../ads/{creativeId}/track`. No impression row is written to `BroadcastAdEvents`. When GAP-0071 is fixed, no charge occurs. Advertisers who purchased pre-roll inventory receive zero delivery, but their campaigns show zero impressions — which could trigger advertiser disputes and refund requests.

### E2E test failures

The gap ticket references tests 369.1/369.2. Without the fix, any test that simulates a session load failure path and then expects `adJoinMutation` to have fired will fail.

### Blast radius

Affects every viewer who encounters any `sessionMutation` failure before the pre-roll fires. In practice this includes: first-time viewers arriving early, viewers with stale URLs, and any scenario where the backend session endpoint returns a transient error.


## 4. Fix Design (code-level)

### Minimal fix (recommended)

Change the `adJoinMutation` effect in `frontend/src/pages/broadcast/LivePlayer.tsx` to depend on `sessionId` and `isAuthenticated` rather than `session`:

**Before (lines 138–142)**:
```tsx
useEffect(() => {
  if (!session || !isAuthenticated) return;
  adJoinMutation.mutate();
  // eslint-disable-next-line react-hooks/exhaustive-deps
}, [session]);
```

**After**:
```tsx
useEffect(() => {
  if (!sessionId || !isAuthenticated) return;
  adJoinMutation.mutate();
  // eslint-disable-next-line react-hooks/exhaustive-deps
}, [sessionId, isAuthenticated]);
```

This makes `adJoinMutation` fire immediately when the component mounts with valid `sessionId` and `isAuthenticated` — the same condition that triggers `sessionMutation`. The two calls now run in parallel. `adJoin` on the backend does not depend on `sessionMutation` having completed: it only needs a valid `sessionId` and an authenticated user.

### Secondary improvement (recommended alongside)

Remove the `// eslint-disable-next-line react-hooks/exhaustive-deps` comment. With `[sessionId, isAuthenticated]` as the dependency array, all values referenced inside the effect (`sessionId`, `isAuthenticated`, `adJoinMutation.mutate`) are either in the array or are stable mutation functions. The disable comment is no longer needed and was only there to suppress the warning about the `[session]` dependency not including `adJoinMutation`.

### Guard condition change

The new guard `if (!sessionId || !isAuthenticated) return` is already the same pattern as the `sessionMutation` effect. This is correct: the ad-join call requires only a valid session ID and authentication, not a fully resolved session object.

### Does `adJoinMutation` need the session object?

The mutation function calls `adJoin(sessionId!)` (line 116), which uses `sessionId` from the component's `useParams` — not from `session` state. The `onSuccess` callback uses only `data.ad_free` and `data.pre_roll`, which come from the API response. There is no dependency on `session` state at all. The `[session]` dependency was a mistake — an implicit assumption that `adJoin` should wait for `getSession` to complete, which is not required by the API contract.

### playbackMutation has the same problem

Lines 144–147 show `playbackMutation` also depends on `[session]`:

```tsx
useEffect(() => {
  if (!session || !isAuthenticated) return;
  playbackMutation.mutate();
}, [session]);
```

`mintPlaybackUrl(sessionId!)` (line 92) also uses `sessionId` from `useParams`, not from `session` state. Fixing `playbackMutation` is technically out of scope for this ticket but is the same one-line change and should be done in the same commit to avoid a second incident. The write-up notes this for completeness; the primary scope remains `adJoinMutation`.

### Frontend-only, no backend change required

The backend `POST /ui/broadcast/sessions/{session_id}/ad-join` endpoint (router line 147) accepts only `session_id` (path param) and the authenticated user context. It does not require any prior `GET /sessions/{session_id}` call to have succeeded. The decoupling is valid from the API contract perspective and requires no backend changes.

### Dev/Prod parity (SECOPS-007)

This is a pure frontend change with no server-side component. The fix applies identically in dev (Vite HMR rebuild) and production (Vite build output). No environment variables or feature flags are involved.

### Race condition between adJoin and sessionMutation

Making both calls fire from the same trigger introduces a benign race: both hit the backend simultaneously. This is acceptable because:
- `adJoin` and `getSession` are independent endpoints.
- `adJoin`'s `onSuccess` only sets `preRoll` and `adFree` state — it does not depend on `sessionMutation` having set `session`.
- `getSession`'s `onSuccess` only sets `session` state — it does not depend on `adJoin` having completed.
- Both mutations have independent error handling.

### Alternatives considered

- **Chain adJoin in sessionMutation.onSuccess**: Call `adJoinMutation.mutate()` directly inside `sessionMutation.onSuccess`. This preserves sequential ordering but couples the two mutations more tightly, making future refactoring harder and making `adJoin` dependent on session-fetch success (the original problem). Rejected.
- **useMemo to derive sessionId from session**: Wrap the `adJoinMutation` effect trigger in a memo that reacts to `sessionId` independently. Unnecessary complexity for a two-line fix. Rejected.


## 5. Testing, Verification & Rollout

### Regression test (Playwright E2E)

Add to `frontend/e2e/broadcast.spec.ts` (or a new `broadcast-player.spec.ts`):

```typescript
test("adJoinMutation fires even when sessionMutation returns 404", async ({ page }) => {
  // Intercept getSession to simulate 404
  await page.route("**/ui/broadcast/sessions/bad-session-id", route => {
    route.fulfill({ status: 404, body: JSON.stringify({ detail: "Not found" }) });
  });

  // Capture adJoin call
  const adJoinPromise = page.waitForRequest(
    req => req.url().includes("/ad-join") && req.method() === "POST",
    { timeout: 5000 }
  );

  await injectAuth(page, "alice");
  await page.goto("/live/bad-session-id");

  // adJoinMutation should fire even though sessionMutation failed
  const adJoinReq = await adJoinPromise;
  expect(adJoinReq).toBeTruthy();
});

test("adJoinMutation fires on valid session load", async ({ page }) => {
  // Normal path: both sessionMutation and adJoinMutation fire
  const adJoinPromise = page.waitForRequest(
    req => req.url().includes("/ad-join") && req.method() === "POST",
    { timeout: 8000 }
  );
  const sessionPromise = page.waitForRequest(
    req => req.url().includes("/ui/broadcast/sessions/") &&
           !req.url().includes("/ad-join") &&
           req.method() === "GET",
    { timeout: 8000 }
  );

  await injectAuth(page, "alice");
  await page.goto("/live/test-session-id");

  await Promise.all([adJoinPromise, sessionPromise]);
  // Both requests fire concurrently — neither depends on the other completing
});
```

**Before fix**: the first test times out waiting for the `/ad-join` request because `adJoinMutation` never fires after a session 404.
**After fix**: both tests pass.

### Manual QA steps

1. Open a live broadcast URL for a session that doesn't exist yet.
2. Observe network tab — confirm `/ad-join` POST fires immediately (before any session data is returned).
3. Confirm "Session not found" error is shown for the player, but pre-roll logic ran (check `preRollDone` state or `adFree` state).
4. Now create the session and refresh — confirm both session fetch and ad-join fire correctly.

### Observability

- Add a console log (or structured event) in `adJoinMutation.onSuccess` and `adJoinMutation.onError` to confirm the call count in production.
- The existing `setPreRollDone(true)` in `onError` (line 127) ensures playback is not blocked by ad-join failure — this is already correct and does not need to change.

### Rollout

Single frontend file change. Ship in the next frontend build. No backend changes, no database migrations, no feature flags required. The risk is very low: the change makes `adJoinMutation` fire earlier (in parallel with `sessionMutation`) rather than later (after it), which is strictly an improvement. The worst case — `adJoin` returning before the session is loaded — is already handled by the existing state management (`setAdFree`, `setPreRoll` are independent of `session`).

**Effort**: S (< 0.5 days: two-line component change, Playwright test addition, optional Vitest unit test).

### Interaction with GAP-0071 and GAP-0072

When the billing integration (GAP-0071) is deployed with the feature flag (GAP-0072), ad events will only be charged if `adJoinMutation` fires and an impression event is sent. With the current broken `[session]` dependency, every session-fetch failure silently prevents the entire ad pipeline from running — no `adJoin`, no pre-roll, no impression event, no billing. After this fix, `adJoin` runs independently and the impression event is sent even if the session fetch fails temporarily. This is the correct behavior: ad delivery and billing should be decoupled from session metadata fetching wherever the API contract permits it.

### SECOPS-007 parity note

This is a pure client-side React timing fix. There is no AWS-backed path to consider for dev/prod parity. The fix applies identically to both Vite dev (HMR) and production build outputs. No environment variable, feature flag, or mock path is introduced or modified.
