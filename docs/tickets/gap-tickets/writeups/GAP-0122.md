# GAP-0122: MP4 Never Uploaded to S3 in Production Path — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase. No prior investigation doc exists.

## 1. Summary & Classification

**Claim verdict: Confirmed.** The ticket cites `broadcast_recording_worker.py:130` as the exact location of the stub comment `# Upload to S3 would happen here in production`. The comment is present at that line inside `generate_mp4`. FFmpeg runs, the local MP4 is produced, file size is measured — but no S3 upload call is made.

- **Severity**: HIGH
- **Source ticket**: BCAST-008
- **Status**: Open
- **Owning area**: Broadcast Recording Worker (`app/services/broadcast_recording_worker.py`)
- **Impact**: Progressive MP4 download files generated by FFmpeg remux are never persisted to S3. The `mp4_s3_key` field stored in DynamoDB is a phantom path. Any API endpoint that constructs a presigned URL from this key will produce a URL that resolves to S3's `NoSuchKey` (404) or a CloudFront 403.
- **Related tickets**: GAP-0121 (umbrella `_upload_to_s3` helper gap), BCAST-006 (recording pipeline), BCAST-008 (MP4 download feature), SECOPS-007 (dev/prod parity)
- **Dependencies**: Requires `_upload_to_s3` helper (see GAP-0121), `S.broadcast_recording_vod_bucket` configuration, and the `broadcast-vod` bucket added to `_dev_buckets` in `app/main.py`.

## 2. Current-State Investigation (root cause)

`generate_mp4` in `app/services/broadcast_recording_worker.py` (line 96–135) is responsible for remuxing the concatenated transport stream to a progressive MP4 suitable for download. The function follows a two-branch structure:

**Mock path (lines 102–110)**: triggered when `_should_mock()` is `True` or `concat_path` is `None`. Returns placeholder metadata with `mp4_size_bytes: 0`. No filesystem or S3 interaction. This branch is exercised in dev environments where FFmpeg is absent.

**Production path (lines 112–135)**: FFmpeg is invoked at lines 116–124 with `-c copy -movflags +faststart`. After a successful run (`returncode == 0`), the output file exists at `mp4_path` on the local disk. The file size is measured via `os.path.getsize(mp4_path)` at line 128. Then:

```python
mp4_key = f"{recording.session_id}/recording/full.mp4"
# Upload to S3 would happen here in production          ← line 130
return {
    "mp4_s3_key": mp4_key,
    "mp4_size_bytes": mp4_size,
    "mp4_generated_at": _now_ts(),
}
```

The key is computed, the local file is measured, but there is no boto3 call. The function returns as if the upload succeeded. The caller, `process_recording` (line 192–266), passes this result to `finalize_recording`, which writes `mp4_s3_key` and `mp4_size_bytes` to DynamoDB (`update_recording_status`, line 181). The recording record therefore reports a valid-looking S3 path with a nonzero size, but the object does not exist in S3.

Additionally, the local `mp4_path` file is never deleted after the function returns. In a containerised environment or a long-running worker, this leads to disk consumption proportional to the number of sessions processed.

**How the broken key surfaces to users**: The recording retrieval endpoint (`GET /sessions/{session_id}/recordings/{recording_id}`) returns the `mp4_s3_key`. Client code (or a presigning endpoint) attempts to construct a download URL. In dev, `broadcast-vod` is not in the moto bucket list (`app/main.py:509–516`), so even a correctly implemented upload would fail unless the bucket is added. In production, the key points to a nonexistent object, so S3 returns 404.

**Relationship to GAP-0121**: GAP-0121 is the broader umbrella: no `_upload_to_s3` helper exists anywhere in the codebase. GAP-0122 is the specific call site where the MP4 upload is missing. Both must be fixed together; the helper defined in GAP-0121 is the implementation primitive that GAP-0122 wires in.

## 3. Impact / Exploit / Blast Radius

1. **MP4 download feature (BCAST-008) is entirely non-functional in production.** The feature was added specifically to allow viewers and creators to download recordings as progressive MP4. Because the file is never uploaded, this feature has never worked in any environment where FFmpeg is available and `broadcast_recording_mp4_auto_generate=True`.

2. **Storage leak on the recording worker host.** Each processed session with a non-empty `concat_path` will leave a `.mp4` file on the worker's local disk (or container overlay filesystem). For a worker processing many sessions, this can exhaust available disk space and eventually cause the FFmpeg subprocess to fail, poisoning subsequent recordings.

3. **False positive recording status.** The recording's `status` is set to `"ready"` by `finalize_recording` even though the MP4 is missing from S3. Operators monitoring DynamoDB or API responses will not detect the breakage without actually trying to download the file.

4. **Newsfeed VOD post points to a missing asset.** `process_recording` at line 234 creates a newsfeed VOD post via `create_vod_post` when the recording reaches `"ready"`. This post links to the recording. Because the MP4 is missing, the post shows a broken download link to all viewers of the creator's feed.

5. **Blast radius**: All broadcast sessions processed with `broadcast_recording_mp4_auto_generate=True` and a non-mock FFmpeg path are affected. In a production deployment with FFmpeg available this is every recorded session. The defect is silent — no error is raised, no alert is fired.

## 4. Fix Design (code-level)

### 4.1 Implement `_upload_to_s3` (prerequisite from GAP-0121)

The helper must live in `broadcast_recording_worker.py` and must be SECOPS-007 compliant: the same code path runs in dev (against moto via `S.s3_endpoint_url`) and in production (against real AWS S3 with `endpoint_url=None`).

```python
import boto3
from app.core.settings import S

def _upload_to_s3(local_path: str, *, bucket: str, key: str) -> None:
    """Upload local_path to s3://bucket/key.

    Uses S.s3_endpoint_url when set (dev/moto); falls back to real AWS endpoint
    when empty (production). Raises RuntimeError on failure.
    """
    s3 = boto3.client(
        "s3",
        region_name=S.aws_region or "us-east-1",
        endpoint_url=S.s3_endpoint_url or None,
    )
    try:
        s3.upload_file(local_path, bucket, key)
        logger.info("uploaded s3://%s/%s from %s", bucket, key, local_path)
    except Exception as exc:
        raise RuntimeError(
            f"S3 upload failed: s3://{bucket}/{key} from {local_path}: {exc}"
        ) from exc
```

### 4.2 Wire `_upload_to_s3` into `generate_mp4` and clean up local file

Replace the stub comment at line 130 with the upload call. Add local file cleanup regardless of upload outcome:

```python
    mp4_key = f"{recording.session_id}/recording/full.mp4"
    try:
        _upload_to_s3(mp4_path, bucket=S.broadcast_recording_vod_bucket, key=mp4_key)
    finally:
        # Clean up local file whether upload succeeded or not
        try:
            _os.remove(mp4_path)
        except OSError:
            pass
    return {
        "mp4_s3_key": mp4_key,
        "mp4_size_bytes": mp4_size,
        "mp4_generated_at": _now_ts(),
    }
```

The `try/finally` ensures the local file is always removed after the upload attempt. If the upload raises `RuntimeError`, it propagates up to `process_recording`'s outer `except Exception` handler (line 258), which sets `status="failed"` with the error message. This is the correct outcome: a failed upload should not result in a `"ready"` recording.

### 4.3 Add `broadcast_recording_vod_bucket` to `_dev_buckets`

SECOPS-007 mandates that the same code path runs in dev. The moto mock must have the target bucket available:

```python
# app/main.py ~line 509
_dev_buckets = [b for b in [
    _S.filemgr_bucket,
    os.environ.get("UPLOAD_BUCKET", ""),
    os.environ.get("S3_BUCKET_IMAGES", ""),
    _S.video_upload_bucket,
    _S.vod_output_bucket or "vod-output",
    _S.filemgr_bucket or "filemgr",
    _S.broadcast_recording_vod_bucket or "broadcast-vod",  # NEW
] if b]
```

### 4.4 Extend `generate_thumbnail` and `transcode_recording` consistently

While not explicitly called out by GAP-0122 (which is specifically the MP4 upload), the same pattern must be applied to the thumbnail upload in `generate_thumbnail` (lines 138–150) and the HLS manifest/segment uploads in `transcode_recording` (lines 75–93) to avoid a cascade of identical gaps being opened. These are addressed by GAP-0121 as the umbrella ticket.

### 4.5 Alternatives considered

- **Defer upload to an SQS consumer**: Not needed for a pipeline that already runs inline. Introduces message ordering complexity without benefit.
- **Presign a PUT URL for FFmpeg to upload directly**: Overly complex and would break the `mp4_size_bytes` measurement, which must happen after the file is created locally.
- **Use `shutil` instead of boto3 `upload_file`**: Only valid for local/NFS paths. boto3's `upload_file` handles multipart for large files automatically and is the standard pattern.

## 5. Testing, Verification & Rollout

### Regression test (fails before fix, passes after)

Add to `tests/test_broadcast_recording_worker.py`:

```python
import os
import pytest
from unittest.mock import patch, MagicMock, ANY
from app.services.broadcast_recording_worker import generate_mp4
from tests.factories import make_recording_record  # thin factory or direct RecordingRecord

def test_generate_mp4_uploads_to_s3(tmp_path):
    """generate_mp4 must call _upload_to_s3 after FFmpeg, not leave the file on disk.

    FAILS BEFORE FIX: _upload_to_s3 is never called; mp4 file remains on disk.
    PASSES AFTER FIX: _upload_to_s3 called with correct args; mp4 file removed.
    """
    from app.services.broadcast_recording import RecordingRecord
    rec = RecordingRecord(
        recording_id="rec_0001",
        session_id="sess_0001",
        profile_id="prof_0001",
        created_by="user_0001",
        status="processing",
        s3_archive_prefix="sess_0001/archive/",
        retention_days=30,
        created_at=1000000,
    )
    concat_ts = tmp_path / "concat.ts"
    concat_ts.write_bytes(b"\x47" * 188)  # minimal TS sync byte
    mp4_path = tmp_path / "concat.mp4"
    mp4_path.write_bytes(b"\x00\x00\x00\x20ftyp")  # ftyp box header

    upload_calls = []

    def fake_upload(local_path, *, bucket, key):
        upload_calls.append((local_path, bucket, key))

    with patch("app.services.broadcast_recording_worker._should_mock", return_value=False), \
         patch("app.services.broadcast_recording_worker.S") as mock_s, \
         patch("subprocess.run") as mock_run, \
         patch("app.services.broadcast_recording_worker._upload_to_s3", side_effect=fake_upload), \
         patch("os.path.getsize", return_value=4096):
        mock_s.ffmpeg_binary_path = "ffmpeg"
        mock_s.broadcast_recording_vod_bucket = "broadcast-vod"
        mock_run.return_value = MagicMock(returncode=0, stderr="")
        result = generate_mp4(rec, str(concat_ts))

    assert len(upload_calls) == 1, "Expected exactly one S3 upload call"
    local, bucket, key = upload_calls[0]
    assert bucket == "broadcast-vod"
    assert key == "sess_0001/recording/full.mp4"
    assert result["mp4_s3_key"] == key
    assert result["mp4_size_bytes"] == 4096
    # Local file must be removed after upload
    assert not os.path.exists(local), "Local mp4 file should be cleaned up after upload"
```

### Manual QA steps

1. Run `just restart` to clear state.
2. Configure a test session with `broadcast_recording_mp4_auto_generate=True` and a real FFmpeg binary in the test environment.
3. Push a valid HLS `.ts` segment via the ingest endpoint; stop the session.
4. Observe the recording worker log: you should see `"uploaded s3://broadcast-vod/..."`.
5. Use `aws s3 ls s3://broadcast-vod/ --endpoint-url http://localhost:4566` (dev) to verify the object exists.
6. Issue a `GET /sessions/{id}/recordings/{rid}` and verify `mp4_s3_key` is reachable via a presigned URL returning 200.
7. Verify the local `/tmp/...concat.mp4` file is gone after the pipeline completes.

### Observability & metrics

- Emit a structured log line at INFO: `recording.mp4.uploaded session_id=X recording_id=Y bytes=Z elapsed_ms=W`.
- If upload fails, set `status="failed"` with `error_code="S3UploadFailed"` in DynamoDB; existing error-state queries surface this.
- Consider adding a CloudWatch metric `broadcast/recording/mp4_upload_failures` in production.

### Rollout

- **Effort**: S (the core change is 5–10 lines; the surrounding cleanup and bucket registration are another 5 lines).
- **Feature flag**: Existing `broadcast_recording_mp4_auto_generate` flag gates this code path; set it to `False` in production until the fix is deployed and tested.
- **Migration**: Existing DDB records with status `"ready"` but a missing S3 object cannot be retroactively fixed. A one-off script querying recordings where `mp4_size_bytes > 0` and `mp4_s3_key` is set, then issuing a `HEAD` object check, can identify broken records and mark them `"failed"` for re-processing.
- **Risk**: Low. The change adds a boto3 call that should have always been there. The only regression risk is an IAM misconfiguration (`s3:PutObject` not granted on `broadcast-vod`) which will fail loudly rather than silently.
- **Sequencing**: Merge after GAP-0121 (which defines `_upload_to_s3`) and after adding `broadcast_recording_vod_bucket` to `_dev_buckets`.
