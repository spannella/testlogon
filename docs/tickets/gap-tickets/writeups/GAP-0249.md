# GAP-0249: `expire_stale_calls` Not Wired as Background Task — Remediation Write-up

> ~5 pages. Fix-oriented. Verified against actual codebase; no prior investigation doc exists.

## 1. Summary & Classification

**Claim from ticket**: A function named `expire_stale_calls` is not wired as a periodic
`asyncio` background task at startup, causing missed liveness-verification calls to remain
in `scheduled` status indefinitely. The fix is to wire it at `app/main.py:528` following
the `start_kyc_sla_checker_task` pattern.

**Verdict: Claim CONFIRMED (with naming correction).** The function exists in
`app/services/kyc_liveness_call.py` but is named `expire_due_calls` (line 361), not
`expire_stale_calls` as the ticket states. Functionally the claim is correct: the method
marks calls whose `scheduled_at + kyc_liveness_call_expiry_seconds <= now` as `expired`,
but there is no code in `app/main.py` (confirmed by grep) that creates an asyncio task
or startup handler to call this method periodically. The `ByStatus` GSI `scheduled`
partition will therefore grow unboundedly, and `schedule_call` — which blocks when an
active call already exists for the case — will permanently block re-scheduling for any
case that had a missed call.

- **Severity**: HIGH — a single missed/abandoned call permanently blocks that case from
  ever scheduling a new verification call. The user is stuck with `kyc_call_already_scheduled`
  (409) forever until an admin manually cancels the stale call.
- **Source ticket**: KYC-003
- **Owning area**: Backend / KYC liveness-call service, app startup
- **Related tickets**: GAP-0250 (VerificationCallPanel), SECOPS-007 (dev/prod parity)
- **Naming correction**: ticket says `expire_stale_calls`; actual method is `expire_due_calls`.

## 2. Current-State Investigation (root cause)

### The `expire_due_calls` method

`app/services/kyc_liveness_call.py` lines 361–372:

```python
def expire_due_calls(self, *, now: Any = None, limit: int = 200) -> list[str]:
    """Expire scheduled calls past their expiry window (deterministic ``now``)."""
    ref_now = _resolve_now(now)
    cutoff_seconds = max(0, int(S.kyc_liveness_call_expiry_seconds))
    expired: list[str] = []
    for item in self.list_by_status(STATUS_SCHEDULED, limit=limit):
        sched = _coerce_int(item.get("scheduled_at"))
        if sched and ref_now >= sched + cutoff_seconds:
            call_id = str(item.get("call_id") or "")
            self._apply_update(call_id, {"status": STATUS_EXPIRED, "updated_at": ref_now})
            expired.append(call_id)
    return expired
```

Default expiry window: `S.kyc_liveness_call_expiry_seconds` defaults to `86400` (24 hours)
per `app/core/settings.py` line 1375–1377. A call is marked `expired` when
`now >= scheduled_at + 86400`.

### The scheduler is never called

Grepping `app/main.py` for `expire_due_calls`, `expire_stale`, or any reference to
`kyc_liveness_call` in the startup event handlers yields zero results. The only startup
handlers registered near line 528 are:

```
app.add_event_handler("startup", start_kyc_sla_checker_task)   # line 528
app.add_event_handler("startup", start_kyc_analytics_precompute_task)  # line 586
```

The `kyc_liveness_call_router` is registered at line 577, but no background-task startup
handler is registered alongside it.

### Reference pattern: `start_kyc_sla_checker_task`

`app/services/kyc_case_assignment.py` lines 743–749 demonstrates the canonical pattern:

```python
def start_kyc_sla_checker_task() -> None:
    import asyncio
    if S.kyc_assignment_enabled and S.kyc_sla_checker_enabled:
        asyncio.ensure_future(kyc_sla_checker_loop())
        logger.info("KYC SLA checker started")
```

The loop function above calls the service method on a timed interval and is guarded by
feature flags from `app/core/settings.py`. `app/main.py:528` registers this via
`app.add_event_handler("startup", start_kyc_sla_checker_task)`.

### `expire_due_calls` correctness analysis

The method (lines 361–372) iterates `list_by_status(STATUS_SCHEDULED)` and applies an
update for each item where `scheduled_at + cutoff_seconds <= now`. With the default
`cutoff_seconds = 86400` (24 h), a missed call must be at least one day old to be expired.

The method accepts an injectable `now` parameter (via `_resolve_now(now)` which calls
`now_ts()` when `None`), making it deterministic in unit tests — this is a well-designed
seam that makes the background task easy to test.

One subtlety: `list_by_status` paginates with `Limit=min(limit, 500)`, and
`expire_due_calls` passes `limit=200` by default. If there are more than 200 stale calls,
a single run will only expire the first 200 (ordered by `created_at` descending, i.e.,
the 200 most recently scheduled stale calls). Over subsequent 60-second intervals all
stale calls will eventually be expired, so this is acceptable for the default use case.
For a large backlog following an outage, the operator can reduce
`KYC_LIVENESS_CALL_EXPIRY_INTERVAL_SECONDS` to 0 to drain faster, or call
`expire_due_calls(limit=2000)` manually via the `rootctl` CLI.

### Conflict-check block

`schedule_call` in `app/services/kyc_liveness_call.py` raises
`KycLivenessCallConflictError` when `ACTIVE_STATUSES = {STATUS_SCHEDULED, STATUS_IN_PROGRESS}`
contains an existing call for the case (line 68). `STATUS_EXPIRED` is in `TERMINAL_STATUSES`
(line 71) and would unblock scheduling — but only if the call is actually transitioned
to `expired`. Without the background task, the transition never happens.

## 3. Impact / Exploit / Blast Radius

| Area | Impact |
|------|--------|
| **User stuck in conflict loop** | Any user who misses or abandons their scheduled call cannot reschedule. `POST /ui/kyc/liveness-call` returns 409 `kyc_call_already_scheduled` indefinitely. |
| **Admin intervention required** | The only escape valve is for an admin to manually cancel the stale call via `POST /ui/kyc/liveness-call/admin/{call_id}/cancel`. There is no admin UI for this (GAP-0250 fixes the visibility gap). |
| **ByStatus GSI growth** | The `scheduled` partition of the `ByStatus` GSI grows monotonically. Each `list_by_status("scheduled")` call (used by admin review queue and `expire_due_calls` itself) scans a larger and larger partition, increasing DynamoDB read costs O(n) over time. |
| **Risk scoring** | `verification_call.result` remains unset for expired calls; `KycRiskScoringService` weights the absence of a verification-call result against the user's overall risk score. A stale `scheduled` call looks like an in-progress check, which may artificially suppress the risk penalty that should be applied when verification failed. |
| **Rate of accumulation** | In a production system with even moderate KYC volume, dozens of calls may go unattended daily (system outages, user no-shows). Within weeks the `scheduled` partition could contain hundreds of phantom records. |

No security exploit path exists; this is a data-integrity and availability issue.

## 4. Fix Design (code-level)

### 4a. Add a startup wrapper function in `app/services/kyc_liveness_call.py`

Append to the end of `app/services/kyc_liveness_call.py` (after line 458):

```python
# ── Background expiry task ─────────────────────────────────────────────────

import asyncio as _asyncio

_EXPIRY_INTERVAL_SECONDS: int = 60  # run every minute


async def _expire_calls_loop() -> None:
    """Periodic background task: expire scheduled calls past their window."""
    logger.info("kyc.liveness_call.expiry_loop.started")
    while True:
        try:
            expired = STORE.expire_due_calls()
            if expired:
                logger.info(
                    "kyc.liveness_call.expiry_loop.expired count=%d call_ids=%s",
                    len(expired),
                    expired[:10],   # truncate for log safety
                )
        except Exception:  # pragma: no cover — never crash the loop
            logger.exception("kyc.liveness_call.expiry_loop.error")
        await _asyncio.sleep(_EXPIRY_INTERVAL_SECONDS)


def start_kyc_liveness_expiry_task() -> None:
    """Register the liveness-call expiry loop at app startup."""
    if not S.kyc_liveness_call_enabled:
        logger.info("kyc.liveness_call.expiry_loop.disabled")
        return
    _asyncio.ensure_future(_expire_calls_loop())
    logger.info("kyc.liveness_call.expiry_loop.registered")
```

This mirrors the `start_kyc_sla_checker_task` / `kyc_sla_checker_loop` pattern exactly.
The loop is guarded by the existing `S.kyc_liveness_call_enabled` flag (default `true`).

### 4b. Register the startup handler in `app/main.py`

Add the import alongside the existing KYC liveness-call router import (line 117 area):

```python
from app.services.kyc_liveness_call import start_kyc_liveness_expiry_task
```

Register the startup handler after the SLA checker (line 528 area), keeping KYC-related
handlers grouped together:

```python
# app/main.py — after line 528
app.add_event_handler("startup", start_kyc_sla_checker_task)
app.add_event_handler("startup", start_kyc_liveness_expiry_task)   # ← new
```

### 4c. Dev/Prod parity (SECOPS-007)

`expire_due_calls` calls `self.list_by_status(STATUS_SCHEDULED)` (queries DynamoDB) and
`self._apply_update(call_id, ...)` (updates DynamoDB). Both paths use the same boto3
table handle (`T.kyc_liveness_calls`) which points to DynamoDB Local (`localhost:8001`)
in dev and the real DynamoDB service in production, determined by `S.ddb_endpoint_url`.
No environment-specific branches are introduced by this fix.

The `S.kyc_liveness_call_enabled` flag provides a single kill-switch for both the HTTP
endpoints and the background task, ensuring that disabling the feature in one environment
disables it everywhere.

### 4d. Optional: configurable interval

Add to `app/core/settings.py`:

```python
kyc_liveness_call_expiry_interval_seconds: int = int(
    os.environ.get("KYC_LIVENESS_CALL_EXPIRY_INTERVAL_SECONDS", "60")
)
```

Replace the hard-coded `60` in `_EXPIRY_INTERVAL_SECONDS` with `S.kyc_liveness_call_expiry_interval_seconds`.

### Alternatives considered

- **On-demand expiry during `schedule_call`** — Expire stale calls lazily when a new
  scheduling attempt hits a conflict. Rejected because it only clears conflicts for the
  same case and does nothing for cases whose users never retry. The GSI partition
  continues to grow.
- **DynamoDB TTL** — Set a `ttl` attribute on each call record so DynamoDB auto-deletes
  it after the expiry window. Rejected because DynamoDB TTL deletes items, not transitions
  them. Expired calls should remain visible in the `expired` status for audit and risk
  scoring. TTL would silently erase call history.
- **Admin manual cancel only** — Rejected as it requires human intervention for every
  missed call and does not scale.

### Re-scheduling after expiry: end-to-end test

A critical acceptance criterion is that a user can re-schedule after a call is expired:

```python
def test_reschedule_after_expiry(client, user_headers, kyc_liveness_ddb_table, now_fixed):
    """After expire_due_calls runs, the same case can accept a new scheduled call."""
    stale_at = now_fixed - 86401
    kyc_liveness_ddb_table.put_item(Item={
        "call_id": "kyccall_block001",
        "case_id": "case_reschedule",
        "user_sub": "user_test",
        "status": "scheduled",
        "scheduled_at": stale_at,
        "updated_at": stale_at,
    })
    # Before expiry: scheduling attempt conflicts
    resp = client.post(
        "/ui/kyc/liveness-call",
        json={"case_id": "case_reschedule", "scheduled_at": now_fixed + 3600, "duration_minutes": 30},
        headers=user_headers,
    )
    assert resp.status_code == 409
    assert resp.json()["detail"]["code"] == "kyc_call_already_scheduled"

    # Expire the stale call
    STORE.expire_due_calls(now=now_fixed)

    # After expiry: scheduling succeeds
    resp2 = client.post(
        "/ui/kyc/liveness-call",
        json={"case_id": "case_reschedule", "scheduled_at": now_fixed + 3600, "duration_minutes": 30},
        headers=user_headers,
    )
    assert resp2.status_code == 201
    assert resp2.json()["status"] == "scheduled"
```

### Manual QA steps

1. Run `just up`.
2. Via API: `POST /ui/kyc/liveness-call` with `scheduled_at = now() - 86401` (or set
   `KYC_LIVENESS_CALL_EXPIRY_SECONDS=30` and wait 31 seconds for a fresh call).
3. Wait one loop interval (default 60 s, or 30 s with the test override).
4. `GET /ui/kyc/liveness-call/{call_id}` — confirm status is now `expired`.
5. `POST /ui/kyc/liveness-call` for the same case — confirm it succeeds (no conflict).
6. Check backend logs for `kyc.liveness_call.expiry_loop.expired count=1`.

### Metrics / observability

- Log `kyc.liveness_call.expiry_loop.expired count=%d call_ids=%s` at INFO so monitoring
  can alert on unexpectedly high expiry rates. A spike (>50 expirations per run) indicates
  a prior system outage.
- Log `kyc.liveness_call.expiry_loop.error` at ERROR with exception details on loop
  iteration failures. The loop must never crash — the `except Exception` ensures
  continuity, but the log line is the only visibility into silent failures.
- Add a Prometheus counter `kyc_liveness_call_expired_total` (increment by
  `len(expired)` inside `_expire_calls_loop`) for production dashboards.
- Use `GET /ui/kyc/liveness-call/admin/by-status?status=scheduled` as a health-check
  gauge: if the count grows monotonically over 24+ hours despite the loop running, that
  indicates a misconfiguration (e.g. `KYC_LIVENESS_CALL_EXPIRY_SECONDS` set to a
  very large value in prod).

### Backlog drain procedure

If the system is first deployed after an extended period where calls accumulated without
expiry, operators can drain the backlog by temporarily setting
`KYC_LIVENESS_CALL_EXPIRY_INTERVAL_SECONDS=5` and `KYC_LIVENESS_CALL_EXPIRY_SECONDS=86400`
and restarting the backend. The loop will run every 5 seconds until the backlog is cleared,
then return to normal cadence.
